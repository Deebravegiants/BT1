### Title
PoA Bridge withdrawal status matched by `assetId` only (ignoring index/destination/amount) causes cross-withdrawal status/hash misreport for batched same-token withdrawals - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves the completion status of a specific withdrawal by matching the POA Bridge indexer's response purely on `assetId` (`near_token_id`), discarding the `index`, `destinationAddress`, and `amount` that uniquely identify which withdrawal is being queried. When a single NEAR intents transaction contains two or more withdrawals of the same token (e.g., split to two different destination addresses), every one of those withdrawals resolves to the *same* first matching entry returned by the indexer, so the SDK reports one withdrawal's completed transaction hash as the completion proof for a different, unrelated withdrawal.

### Finding Description
`describeWithdrawal` in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, and that helper (mirrored in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`) does: [1](#0-0) [2](#0-1) 

The match is `withdrawals.find((w) => nep141:${w.data.near_token_id} === criteria.assetId)` — it returns the *first* withdrawal in the API response with the same token id, irrespective of which `index` (or destination address/amount) the caller is asking about. This is explicitly acknowledged in the code comment as a known limitation: [3](#0-2) 

The SDK's own `createWithdrawalIdentifiers` helper assigns a distinct `index` per withdrawal per bridge route specifically so multiple withdrawals through the same bridge in one NEAR transaction can be tracked independently: [4](#0-3) 

But `PoaBridge.describeWithdrawal` never consults that `index`, even though the indexer's response payload (`data.address`, `data.amount`) contains the information needed to disambiguate — it is simply not used. This is confirmed by the test suite itself, whose title makes the limitation explicit: [5](#0-4) 

This breaks the equality "a status/hash reported for withdrawal N is the on-chain outcome for withdrawal N" — instead, the SDK reports the on-chain outcome of an arbitrary matching withdrawal (by token) as the outcome for every same-token withdrawal in the batch.

### Impact Explanation
`watchWithdrawal` in `packages/intents-sdk/src/core/withdrawal-watcher.ts` trusts `describeWithdrawal`'s `completed` status/`txHash` at face value and resolves the watcher's promise with that hash: [6](#0-5) 

If an integrator processes two same-token, different-destination withdrawals from one intent (a legitimate, supported flow via `createWithdrawalIdentifiers`), both `describeWithdrawal` calls converge on the same first-matched indexer record. Concretely: withdrawal #0 (destination A) completes on-chain first; when the watcher for withdrawal #1 (destination B, still pending or routed elsewhere) polls, it also receives the "completed" status and destination-A's `txHash`, because the lookup only filters by `assetId`. The integrator/consumer of the SDK — which relies on `watchWithdrawal`/`describeWithdrawal` to mark a specific withdrawal as settled and release/credit downstream — will incorrectly mark withdrawal #1 as completed using a transaction hash that has nothing to do with it. This is a concrete status/hash misreport that can make an integrator credit or reconcile a withdrawal that never actually happened, which is a High-severity category (misreport causing double credit/refund) per the impact bar for this analysis.

### Likelihood Explanation
No malicious actor is required — any ordinary user or integrator who batches multiple same-token withdrawals to different addresses within one NEAR intents transaction (a supported, documented pattern per `createWithdrawalIdentifiers`'s per-route indexing) will trigger the collision as soon as the indexer returns more than one entry for that token for the transaction. The condition is purely a function of normal usage patterns, not attacker-controlled input, making it a reliably reproducible defect rather than a theoretical edge case.

### Recommendation
In `findMatchingWithdrawal` (both `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` and `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`), disambiguate matches using more than `assetId`: incorporate `destinationAddress` and/or `amount` (and preferably a stable ordering keyed to `index`) so each queried withdrawal identifier resolves to its own indexer record. At minimum, when multiple candidates share the same `assetId`, the code should refuse to return `completed` for any of them until they can be uniquely disambiguated, rather than silently returning first-match data as truth for all of them.

### Proof of Concept
1. Build one NEAR intents transaction with two `ft_withdraw` intents for the same token (`nep141:eth.omft.near`) — one to destination address A with amount 100, another to destination address B with amount 200 — via the SDK's normal withdrawal flow; `createWithdrawalIdentifiers` assigns `index: 0` and `index: 1` respectively under the `poa_bridge` route (see `packages/intents-sdk/src/core/withdrawal-watcher.ts:80-107`).
2. The POA Bridge indexer processes and completes withdrawal to address A first, returning a `withdrawals` array whose first (or only currently visible) COMPLETED entry has `data.address = A`, `data.transfer_tx_hash = "hash-A"`.
3. Call `describeWithdrawal` for `index: 1` (destination B, still pending). `findMatchingWithdrawal` matches on `assetId` alone and returns the entry for A, so the function returns `{ status: "completed", txHash: "hash-A" }` for withdrawal #1 as demonstrated by the existing test `"matches withdrawal by assetId, not by index"` at `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.test.ts:1054-1111`, which passes an unrelated `index`/withdrawal criteria and still receives a matching completed result solely based on `assetId`.
4. `watchWithdrawal` resolves with `hash-A` as if it were proof of the B-destined withdrawal's completion, even though B's transfer has not occurred — the wrong on-chain outcome is reported for withdrawal #1.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
