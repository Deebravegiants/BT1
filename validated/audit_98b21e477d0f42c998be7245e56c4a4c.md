### Title
Tron `IntentGatewayV2.placeOrder` credits escrow with requested amount instead of actual tokens received, breaking accounting for fee-on-transfer/rebasing tokens - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` credits the internal `_orders[commitment][token]` escrow ledger with the *requested* (fee-reduced) input amount rather than the amount actually received by the contract after the `safeTransferFrom` call. For fee-on-transfer, deflationary, or rebasing ERC20 input tokens, the contract's real token balance will diverge from what the ledger records, and subsequent `withdraw()` calls (triggered by relayed `RedeemEscrow`/`RefundEscrow` cross-chain messages) will attempt to move more tokens than the contract actually holds.

### Finding Description
In `placeOrder` (no-predispatch branch), the contract pulls tokens from the user and immediately writes the pre-fee-reduced escrow entry without verifying the amount that actually landed in the contract: [1](#0-0) 

Compare this with the canonical EVM implementation (`evm/src/apps/IntentGatewayV2.sol`), which explicitly measures the balance delta around the transfer specifically to defend against fee-on-transfer tokens: [2](#0-1) 

The Tron contract omits this balance-based accounting entirely — it just uses `order.inputs[i].amount` for the transfer and `reducedInputs[i].amount` for the escrow credit, assuming a 1:1, non-rebasing, non-fee-on-transfer, non-deflationary token. The predispatch branch of the same Tron contract does check `IERC20(token).balanceOf(dispatcher)` for dust purposes, but still credits `_orders[commitment][token] += reducedInputs[i].amount` (the *requested* amount) rather than the amount actually swept to the gateway: [3](#0-2) 

Later, when a relayed `RedeemEscrow`/`RefundEscrow` post request is delivered, `withdraw()` transfers out the amount recorded in the cross-chain `WithdrawalRequest.tokens[i].amount` (which mirrors the escrow ledger) via a raw low-level `token.call(transfer, beneficiary, amount)`: [4](#0-3) 

If the token is fee-on-transfer or rebasing and the contract's actual balance is lower than the ledger's recorded amount, this ERC20 `transfer` call will revert (insufficient balance) for standard tokens, or for tokens that silently truncate the transfer, the `_orders[body.commitment][token] -= amount` bookkeeping subtraction will still assume the full amount left the contract, permanently corrupting the escrow ledger for that commitment and any other input tokens bundled with it. Because `onAccept` for `RedeemEscrow`/`RefundEscrow` requires successful execution of `withdraw()`, and this path is driven entirely by a relayed, permissionless-to-trigger cross-chain message once submitted by any user placing an order with such a token, the tokens become permanently stuck: neither the solver (redeem) nor the original user (refund) can ever extract them, since every retry recomputes the same over-stated `amount` from the immutable `WithdrawalRequest`/order commitment.

### Impact Explanation
Funds placed into escrow via `placeOrder` using a fee-on-transfer or rebasing ERC20 token become permanently unrecoverable once escrowed on the Tron IntentGatewayV2: the escrow ledger `_orders[commitment][token]` will always overstate the real token balance held by the contract, so any subsequent `withdraw()` invocation (whether legitimate fill, refund, or cancellation) reverts or corrupts accounting, permanently freezing user or solver funds. This satisfies "permanent freezing of funds" under a single submitted order/transaction, with no privileged or malicious actor required — an ordinary user placing an order with such a token triggers the bug organically.

### Likelihood Explanation
Likelihood is dependent on such tokens being accepted as valid `TokenInfo.token` inputs; nothing in `placeOrder` restricts input tokens to "safe" standard ERC20s, so any user or integrator can submit an order using a fee-on-transfer or rebasing token and immediately create an under-collateralized/over-stated escrow entry, at which point the freeze is deterministic and unavoidable once the withdraw path executes.

### Recommendation
Apply the same balance-delta accounting used in `evm/src/apps/IntentGatewayV2.sol` (measure `balanceOf(address(this))` before and after `safeTransferFrom`, and use the observed delta, not the requested amount, for both the commitment computation and the `_orders` escrow credit) to the Tron `IntentGatewayV2.placeOrder`, in both the predispatch and non-predispatch branches.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 token (e.g., 1% burn on transfer) and use it as an `order.inputs[0].token` in `placeOrder` on the Tron `IntentGatewayV2`.
2. `placeOrder` calls `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)`; the contract actually receives `amount * 0.99`, but `_orders[commitment][token]` is credited with the full `reducedInputs[i].amount` (based on the pre-fee `amount`). [5](#0-4) 
3. When a `RedeemEscrow`/`RefundEscrow` message referencing this commitment is delivered via `onAccept` → `withdraw()`, the contract attempts `token.call(transfer, beneficiary, amount)` for the full (overstated) amount, exceeding the token balance actually held, causing the transfer to fail/behave incorrectly and leaving escrowed funds permanently stuck. [6](#0-5)
