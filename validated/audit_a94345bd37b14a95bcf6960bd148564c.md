### Title
Webhook shop identity not bound to HMAC, enabling cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by HMAC-validating only the raw request body, then trusts the `shop-domain` header — which is *not* covered by that HMAC — to identify which merchant the webhook belongs to. An attacker who legitimately installs the app on their own store can capture a valid `(raw_body, hmac)` pair signed with the app's single, shop-independent `client_secret`, then replay that same body/HMAC to the app's webhook endpoint while substituting an arbitrary victim `shop-domain` header, causing the app to process attacker-controlled webhook data under a victim shop's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop` is read independently from the `shopify-shop-domain` header with no cryptographic tie to the signed payload [2](#0-1) . `Registry.process` validates only `Utils::HmacValidator.validate(request)` — i.e., the body/HMAC pair — before dispatching to the app's handler using `request.shop` as the tenant identifier: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [3](#0-2) . `HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` and the app's `Context.api_secret_key` [4](#0-3) , so **the identity binding "shop authenticated == shop the body was signed for" never holds** — the `client_secret` is the same across all shops that install the app, and the HMAC says nothing about which shop the body came from. Any merchant who installs the app therefore possesses a valid `(body, hmac)` for that same secret and can relabel it with a different `shop-domain` header value to make it appear the webhook came from a different (victim) shop.

### Impact Explanation
This breaks the tenant boundary the gem's webhook processing pipeline is supposed to enforce: `handler.handle` receives `data.shop` as the trusted tenant key documented for app authors to use directly (e.g., to look up sessions or dispatch background jobs scoped to that shop) [5](#0-4) . An attacker-installed app instance can forge webhook payloads (arbitrary topic-appropriate JSON body) that are accepted as authentic and attributed to any victim `shop-domain` value of the attacker's choosing, since nothing in the verified bytes constrains the shop. This is a cross-tenant identity confusion at the authentication layer of the webhook feature, matching the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any attacker who can install the target app on their own development/store account (a very low bar, and the normal path for any potential customer of an app) — no privileged credentials, TLS interception, or social engineering are required. The only requirement is capturing one legitimate webhook fired to their own store and replaying it with a modified header to the app's public webhook endpoint.

### Recommendation
Bind the shop identity into the authenticated bytes before trusting it. Include the `shop-domain` (and ideally `topic`/`webhook-id`) header value in the signable string computed by `Webhooks::Request#to_signable_string`, or otherwise verify the value out-of-band (e.g., cross-check `request.shop` against session/shop records established via OAuth for that specific installation, not merely against a globally-valid HMAC) before dispatching to the handler in `Webhooks::Registry.process`.

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker.myshopify.com`.
2. Trigger any webhook topic the app subscribes to (e.g. `orders/create`) and capture the resulting HTTP request: raw body `B` and header `X-Shopify-Hmac-Sha256: H` — valid because `H = HMAC-SHA256(client_secret, B)` and `client_secret` is shared across all installs of the app.
3. Replay a POST to the app's webhook endpoint with the same body `B` and header `H`, but replace `X-Shopify-Shop-Domain: attacker.myshopify.com` with `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Webhooks::Request` parses the forged headers [6](#0-5) ; `HmacValidator.validate` succeeds because it only checks `B` against `H` [4](#0-3) ; `Registry.process` calls the app handler with `shop: "victim.myshopify.com"` and attacker-chosen `body` [3](#0-2) , causing the app to act as though the victim shop sent this webhook data.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

```markdown
If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
```
