### Title
Webhook `shop`, `topic`, and `webhook_id` fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable content from the raw body only, but exposes `shop`, `topic`, `webhook_id`, and `api_version` as plain, unauthenticated HTTP headers. `Registry.process` validates the HMAC and then forwards these unauthenticated header values directly to the app's webhook handler, breaking the identity binding between "the payload that was actually signed" and "the tenant/topic the app attributes it to."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are read straight out of request headers with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` validates only the body's HMAC via `Utils::HmacValidator.validate(request)`, then hands the *unauthenticated* `shop`, `topic`, and `webhook_id` header values straight to the registered handler: [3](#0-2) 

`HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` (the raw body for webhooks) against the HMAC — it never incorporates `shop`, `topic`, or `webhook_id`: [4](#0-3) 

This is the direct analog of the reported bug class: a field that is *acted on* (the `shop` value used to attribute/route the webhook payload to a tenant) is not covered by the authenticator (the HMAC) that is supposed to prove the request's integrity/origin. The equality that should hold is:

`shop_that_HMAC_authenticates == shop_the_app_attributes_the_payload_to`

but in this implementation the HMAC only authenticates `raw_body`, while `shop` (and `topic`/`webhook_id`) come from headers with no such coverage, so:

`shop_that_HMAC_authenticates (∅, not bound) != shop_the_app_attributes_the_payload_to (attacker-controlled header)`

Because Shopify signs webhooks with the single, app-wide `client_secret` (the same secret for every shop that has the app installed), any tenant that has the app installed — an "unprivileged" party relative to other tenants of the same app — legitimately receives genuine `(raw_body, hmac)` pairs for their own store's events. That tenant can then resend that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`/`x-shopify-webhook-id`) header to claim the payload belongs to a different shop. `HmacValidator.validate` will still pass, because it never looks at those headers, and `Registry.process` will invoke the handler with `shop: <victim shop>` despite the signed bytes never having been produced for, or bound to, that shop.

### Impact Explanation
This is a cross-tenant data-integrity/confusion vulnerability: a malicious or curious merchant on a multi-tenant app can cause the app to process/attribute webhook data (order, customer, or other event payloads they legitimately received for their own store) as though it originated from a different, victim shop, purely by resending an HTTP request to the app's public webhook callback URL with forged headers. Depending on how the host app uses `WebhookMetadata#shop` to look up sessions/tokens or write to per-tenant storage, this can lead to cross-tenant data corruption/exfiltration, satisfying the "cross-tenant access" Critical-impact bar defined by the rules.

### Likelihood Explanation
The webhook endpoint is, by design, a public unauthenticated HTTP endpoint reachable by any internet user who knows or guesses it (commonly documented, predictable paths). The attacker needs no `api_secret_key`, no access token, and no privileged account — only the ability to receive one legitimate webhook for a shop where the app is installed (trivial for anyone who installs the app on a development/test store) and to replay it with modified headers. This is squarely an unprivileged-internet-user analog.

### Recommendation
Include the tenant-identifying and routing fields (`shop`, `topic`, `webhook_id`) in the HMAC-signed content, or otherwise cryptographically bind them to the raw body (e.g., verify that the `shop` returned from a data lookup, such as the shop stored for a previously registered webhook ID, matches the header before trusting it). At minimum, document that consumers of `ShopifyAPI::Webhooks::Registry.process` must independently verify that `data.shop` corresponds to a shop with an active, expected installation before trusting the payload's attribution, since the HMAC in this gem provides body integrity only, not header/tenant authentication.

### Proof of Concept
1. Shop A has the vulnerable app installed. Shopify sends a legitimate webhook to the app's endpoint:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of raw_body using app client_secret>
   x-shopify-shop-domain: shop-a.myshopify.com
   Body: {"id": 123, "note": "..."}
   ```
2. The app owner (or any user who can intercept/replay this request, e.g. via browser dev tools or a proxy since it's just an HTTP POST to a public URL) resends the exact same body and `x-shopify-hmac-sha256` value, but changes the header:
   ```
   x-shopify-shop-domain: shop-b.myshopify.com
   ```
3. `ShopifyAPI::Utils::HmacValidator.validate(request)` recomputes the HMAC over `raw_body` only (`Request#to_signable_string`) and it matches, since the body wasn't altered.
4. `ShopifyAPI::Webhooks::Registry.process` calls the handler with `WebhookMetadata.new(..., shop: "shop-b.myshopify.com", ...)`, even though the payload was never produced for, or authorized in association with, Shop B — demonstrating the broken `shop` identity binding described above.
