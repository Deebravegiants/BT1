### Title
Unchecked NEAR Transfer in Staking Pool Withdrawal Leaves Accounting Desynced on Failure - (File: staking-pool/src/internal.rs)

### Summary
The external ERC20 report flags a missing success check on a token transfer that lets the contract silently believe a payment succeeded when it may have failed. In `core-contracts`, the analogous root cause exists in `staking-pool/src/internal.rs`'s `internal_withdraw`, which decrements the user's internal `unstaked` balance and the pool's `last_total_balance` *before* issuing the NEAR transfer, and never attaches a callback to verify the transfer's outcome and roll back state on failure.

### Finding Description
`internal_withdraw` mutates internal accounting first, then fires a bare `Promise::new(account_id).transfer(amount)` with no `.then(...)` callback: [1](#0-0) 

Contrast this with the rest of the same contracts' pattern, where every cross-contract `Promise` that risks fund loss is followed by a callback that calls `is_promise_success()` and reverts/repairs state on failure — e.g. `lockup/src/owner.rs::withdraw_from_staking_pool` chained to `on_staking_pool_withdraw` [2](#0-1)  and its callback restoring state only conditionally on success [3](#0-2) , or `lockup/src/foundation.rs::termination_withdraw` chained to `on_withdraw_unvested_amount` [4](#0-3) [5](#0-4) .

`internal_withdraw` is reachable from the public, unprivileged entrypoints `withdraw` and `withdraw_all` in `staking-pool/src/lib.rs`: [6](#0-5) 

Because NEAR native transfers are asynchronous promises that can fail for reasons outside the caller's control (e.g., insufficient prepaid gas forwarded to the receipt, receiving account issues, or protocol-level receipt failures), an attacker or any unprivileged caller can trigger a scenario where the `Promise::new(account_id).transfer(amount)` fails while the contract has already deducted `account.unstaked` and `self.last_total_balance` and persisted that state via `self.internal_save_account`. There is no callback to detect the failure and restore the account's `unstaked` balance, meaning the withdrawn funds are neither delivered to the user nor recoverable through the contract's accounting.

### Impact Explanation
This matches the "Permanent freezing, unrecoverable lock, or irrevocable loss of user or protocol funds in ... unstake-withdraw ... flows" critical impact category. If the transfer fails post-accounting-update, the user's balance is silently and permanently reduced by `amount` with no compensating credit and no path to reclaim the lost NEAR, since the state was already committed and there's no promise-result check to reverse it.

### Likelihood Explanation
Likelihood depends on the frequency of promise-transfer failures for arbitrary receiver accounts, which is generally low under normal conditions on NEAR, but the missing callback is a genuine structural gap compared to every other value-transferring flow in this codebase — all of which explicitly guard against this failure mode with `is_promise_success()` callbacks. This is a real, reachable root cause via unprivileged `withdraw`/`withdraw_all` calls, not merely theoretical, though the failure trigger itself (a NEAR-native transfer promise failing) is less commonly exploitable at will compared to the original ERC20 non-compliant token scenario, since it does not depend on a "malicious token" the attacker fully controls.

### Recommendation
Do not mutate `account.unstaked`, `self.last_total_balance`, or persist account state before the transfer completes. Instead, chain `Promise::new(account_id).transfer(amount)` with `.then(ext_self::on_withdraw(...))`, and perform the account/`last_total_balance` mutation (or its rollback) only inside that callback, gated on `is_promise_success()`, mirroring the pattern already used for `on_staking_pool_withdraw` and `on_withdraw_unvested_amount` in `lockup/src`.

### Proof of Concept
1. Unprivileged user has an `unstaked` balance available for withdrawal (post-unstaking delay).
2. User calls `withdraw(amount)` or `withdraw_all()` on the staking-pool contract.
3. `internal_withdraw` immediately decrements `account.unstaked` and `self.last_total_balance`, persists the account via `internal_save_account`, then issues `Promise::new(account_id).transfer(amount)` with no callback.
4. If the transfer receipt fails (e.g., due to insufficient gas forwarded by the runtime for the transfer action, or any other cross-shard/receipt-level failure), the contract has no mechanism to detect this failure and restore `account.unstaked`.
5. The user's recorded unstaked balance is permanently reduced with no NEAR delivered and no recovery path — an irrevocable loss of funds reachable through a fully public, unprivileged entrypoint.

    pub(crate) fn internal_withdraw(&mut self, amount: Balance) {
        assert!(amount > 0, "Withdrawal amount should be positive");

        let account_id = env::predecessor_account_id();
        let mut account = self.internal_get_account(&account_id);
        assert!(
            account.unstaked >= amount,
            "Not enough unstaked balance to withdraw"
        );
        assert!(
            account.unstaked_available_epoch_height <= env::epoch_height(),
            "The unstaked balance is not yet available due to unstaking delay"
        );
        account.unstaked -= amount;
        self.internal_save_account(&account_id, &account);

        env::log(
            format!(
                "@{} withdrawing {}. New unstaked balance is {}",
                account_id, amount, account.unstaked
            )
            .as_bytes(),
        );

        Promise::new(account_id).transfer(amount);
        self.last_total_balance -= amount;
    }

    /// Called after the foundation tried to withdraw the terminated unvested balance.
    pub fn on_withdraw_unvested_amount(
        &mut self,
        amount: WrappedBalance,
        receiver_id: AccountId,
    ) -> bool {
        assert_self();

        let withdraw_succeeded = is_promise_success();
        if withdraw_succeeded {
            env::log(
                format!(
                    "Termination Step: The withdrawal of the terminated unvested amount of {} to @{} succeeded.",
                    amount.0, receiver_id
                )
                    .as_bytes(),
            );
            // Decreasing lockup amount after withdrawal.
            self.lockup_information.termination_withdrawn_tokens += amount.0;
            let unvested_amount = self.get_terminated_unvested_balance().0;
            if unvested_amount > amount.0 {
                // There is still unvested balance remaining.
                let remaining_balance = unvested_amount - amount.0;
                self.vesting_information =
                    VestingInformation::Terminating(TerminationInformation {
                        unvested_amount: remaining_balance.into(),
                        status: TerminationStatus::ReadyToWithdraw,
                    });
                env::log(
                    format!(
                        "Termination Step: There is still terminated unvested balance of {} remaining to be withdrawn",
                        remaining_balance
                    )
                        .as_bytes(),
                );
                if self.get_account_balance().0 == 0 {
                    env::log(b"The withdrawal is completed: no more balance can be withdrawn in a future call");
                }
            } else {
                self.foundation_account_id = None;
                self.vesting_information = VestingInformation::None;
                env::log(b"Vesting schedule termination and withdrawal are completed");
            }
        } else {
            self.set_termination_status(TerminationStatus::ReadyToWithdraw);
            env::log(
                format!(
                    "Termination Step: The withdrawal of the terminated unvested amount of {} to @{} failed",
                    amount.0, receiver_id,
                )
                .as_bytes(),
            );
        }
        withdraw_succeeded
    }

        let account_id = env::predecessor_account_id();
        let account = self.internal_get_account(&account_id);
