### Title
Case-sensitive Bitcoin address equality check is bypassed by later bech32 lowercasing, allowing Omni Bridge BTC withdrawals to be misdelivered to the bridge's own deposit address - ([File: packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts])

### Summary
`OmniBridge.validateWithdrawal` guards against a user withdrawing a token to that token's own bridge deposit address by calling `compareAddresses(destTokenAddress, args.destinationAddress, assetInfo.blockchain)`. For Bitcoin, `compareAddresses` performs a case-sensitive `a === b` string comparison, which is correct for legacy base58 addresses but wrong for bech32 (`bc1...`) addresses, which are case-insensitive per BIP173. Separately, `deriveOmniWithdrawIntentParams` (called later, when the actual withdrawal intent is built) explicitly lowercases any `bc1`-prefixed destination address before it becomes the on-chain `recipient`. Because the validation check runs on the pre-normalized (mixed/upper-case) address while the on-chain transfer runs on the post-normalized (lowercased) address, an attacker-or-mistaken destination address that only differs from the bridge's token deposit address by letter case passes the "not the token's own address" check but resolves, on-chain, to the exact same address as the bridge's deposit account.

### Finding Description
The equality check meant to protect the equality "destination address ≠ token's own bridge address" is evaluated on data that is not the data ultimately used to build the transfer:

1. `compareAddresses` for `Chains.Bitcoin` uses exact string equality: [1](#0-0) 

2. `OmniBridge.validateWithdrawal` uses this comparison to reject a withdrawal whose destination equals the bridge's cached BTC deposit/token address: [2](#0-1) 

3. Later, when the intent is actually constructed (a separate call path, `createWithdrawalIntents` → `deriveOmniWithdrawIntentParams`), any `bc1`-prefixed address is silently lowercased before being wrapped into the `recipient` OmniAddress that goes on-chain: [3](#0-2) 

Since bech32 checksum validity is unaffected by letter case (an all-uppercase `BC1Q...` address decodes to the identical payload as its lowercase form), a user or a maliciously/incorrectly constructed `destinationAddress` in upper/mixed case that is case-insensitively identical to the bridge's BTC deposit address will:
- Fail to trigger `DestinationAddressMatchesTokenAddressError` in `validateWithdrawal`, because `compareAddresses` does a byte-for-byte comparison against the canonical (lowercase) `destTokenAddress`.
- Then get silently lowercased in `deriveOmniWithdrawIntentParams`, becoming byte-for-byte identical to the bridge's own deposit address.

The result: the withdrawal intent is built and signed with a `recipient` that is literally the Omni Bridge's own BTC deposit account — the exact condition the check was designed to prevent — with no on-chain mechanism to distinguish this from a legitimate transfer.

### Impact Explanation
This breaks the "address validated" vs "address paid" equality: the address that passed the anti-self-address check is not byte-identical to the address that is actually paid on-chain. The consequence is user funds withdrawn to the bridge's own custody address instead of the user-controlled destination, with no automated recovery path (classified by the rules as: funds delivered to a wrong address/chain/contract with no recovery — Critical impact).

### Likelihood Explanation
The bech32 case behavior is a well-known, easily reproducible property of BIP173 addresses (uppercase-only encodings are valid and decode identically to lowercase). No privileged access or race condition is required — a caller only needs to supply the destination address in upper/mixed case matching the bridge's deposit address. Because `estimateWithdrawalFee`/`processWithdrawal` in `sdk.ts` also runs `validateWithdrawal` before constructing intents, the vulnerable check is on the default path for every BTC Omni Bridge withdrawal.

### Recommendation
Normalize (lowercase) bech32-prefixed Bitcoin addresses once, at the earliest point (ideally inside `validateAddress`/`compareAddresses`, or immediately upon receiving `destinationAddress`), before any equality check or intent construction, so the same canonical string is used for both validation and the on-chain payload. Alternatively, make `compareAddresses` for `Chains.Bitcoin` bech32-address-aware (case-insensitive compare when both strings share a `bc1` prefix) matching the same canonicalization rule applied later in `deriveOmniWithdrawIntentParams`.

### Proof of Concept
1. Suppose the Omni Bridge's cached BTC deposit/token address is `bc1qexampletokenaddress...` (lowercase, as returned by `getCachedDestinationTokenAddress`/`getAddress`).
2. Caller invokes `sdk.processWithdrawal` (or `estimateWithdrawalFee`) with `destinationAddress: "BC1QEXAMPLETOKENADDRESS..."` (same address, all uppercase — a valid bech32 encoding per BIP173).
3. `OmniBridge.validateWithdrawal` calls `compareAddresses(destTokenAddress, args.destinationAddress, Chains.Bitcoin)`, which does `a === b` on `"bc1qexample..."` vs `"BC1QEXAMPLE..."` → `false`. No `DestinationAddressMatchesTokenAddressError` is thrown; validation succeeds.
4. `createWithdrawalIntents` → `deriveOmniWithdrawIntentParams` runs `/^bc1/i.test(destinationAddress)` → true → lowercases the address to `"bc1qexampletokenaddress..."`, identical to the bridge's own deposit address, and uses it to build `recipient` for the `ft_withdraw` intent.
5. The signed intent instructs the bridge to withdraw BTC to its own deposit address instead of a genuinely external, user-controlled address, with the self-address safety check having been silently bypassed.
