## Analysis: LDAP empty-password authentication bypass analog

The `Bind(username, password)` call here maps directly to `go-ldap`'s underlying `SimpleBind`, which implements RFC 4513. Per that spec, a bind request with a non-empty DN and a **zero-length password is defined as an "unauthenticated bind,"** and compliant LDAP servers (Active Directory by default, per the original advisory) will return success without verifying any credential. Chainlink's `ldapAuthenticator.CreateSession` and `TestPassword` pass the raw user-supplied `sr.Password` / `password` directly into `conn.Bind(...)` with no check for an empty string before doing so: [1](#0-0) [2](#0-1) 

This is the exact bug class described in the report: no application-level rejection of empty passwords before the LDAP simple bind is attempted, relying entirely on the upstream server to refuse unauthenticated binds.

### Title
LDAP session authentication bypass via unauthenticated (empty password) bind - (File: core/sessions/ldapauth/ldap.go)

### Summary
`ldapAuthenticator.CreateSession` (used by the internet-facing `/sessions` endpoint) and `ldapAuthenticator.TestPassword` forward the client-supplied password verbatim to `conn.Bind(searchBaseDN, password)` without first verifying that the password is non-empty [1](#0-0) . Per RFC 4513 §5.1.2, a bind with a valid DN and an empty password is an "unauthenticated bind" which many LDAP servers (default AD configuration) will report as success. This lets an unprivileged client obtain a fully authenticated Chainlink session for any known/guessable email without knowing the real password, exactly mirroring GHSA-5hmm-x8q8-w5jh / CVE-2020-26214.

### Finding Description
The Chainlink node's LDAP-mode `AuthenticationProvider.CreateSession` is invoked from the public session-creation HTTP handler [3](#0-2) , which binds the JSON body's `Email`/`Password` straight through to `sessions.SessionRequest` and calls `AuthenticationProvider().CreateSession(ctx, sr)`. In the LDAP implementation, the request's `sr.Password` is passed unmodified into `conn.Bind(searchBaseDN, sr.Password)` [1](#0-0) . There is no guard anywhere in `ldap.go` rejecting an empty-string password before the bind attempt (confirmed by search — no `len(sr.Password) == 0` / `len(password) == 0` check exists in this file, unlike the local/OIDC bcrypt paths where `CheckPasswordHash` inherently fails on empty input [4](#0-3) ). If `conn.Bind` returns `nil` (success) because the upstream directory permits unauthenticated binds for a valid DN, `CreateSession` proceeds to call `FindUser`, assign the account's real role from the directory, and issue a legitimate, fully privileged local session cookie [5](#0-4) . The identical unguarded pattern also exists in `TestPassword`, used for other credential-verification flows [6](#0-5) .

### Impact Explanation
An unprivileged/unauthenticated network client who knows or guesses a valid user email (admin accounts are commonly enumerable, e.g. `admin@...`) can obtain a valid session cookie with that user's full role (potentially `admin`) by submitting an empty `"password"` field, provided the operator's LDAP/AD server is configured to accept unauthenticated binds — the default posture for Active Directory. This is a full authentication bypass leading to complete node compromise (job creation/deletion, key management, fund-moving actions) without any credential knowledge, matching CWE-287 and the severity of the original advisory.

### Likelihood Explanation
Likelihood depends on the LDAP backend configuration being the default/common "unauthenticated bind allowed" posture (default for Active Directory, as explicitly called out in the original advisory). Chainlink's LDAP mode itself does not add any independent server-side protection against this — it fully defers correctness to the upstream directory's bind semantics, so any deployment using LDAP auth in its default AD configuration is exposed. The attack requires only a single unauthenticated HTTP POST to `/sessions` with a known email and empty password.

### Recommendation
In `ldapAuthenticator.CreateSession` and `ldapAuthenticator.TestPassword`, explicitly reject empty passwords before calling `conn.Bind`, e.g.:
```go
if sr.Password == "" {
    return "", errors.New("password must not be empty")
}
```
placed immediately before the `conn.Bind(searchBaseDN, sr.Password)` call in `core/sessions/ldapauth/ldap.go` (both in `CreateSession` and `TestPassword`), mirroring the upstream `alerta` fix that returns 401 for empty-password auth attempts.

### Proof of Concept
1. Configure the node with `LDAP` authentication against an Active Directory (or any LDAP server permitting unauthenticated binds) with a known valid user email, e.g. `admin@example.com`.
2. Send: `POST /sessions` with body `{"email":"admin@example.com","password":""}`.
3. `ldapAuthenticator.CreateSession` calls `conn.Bind(searchBaseDN, "")` [7](#0-6) ; the AD server treats this as an unauthenticated bind and returns success.
4. The handler proceeds to fetch the user's real role via `FindUser`, creates an `ldap_sessions` row, and returns a valid session cookie — granting the attacker the target user's full privileges without ever knowing their password.

**Caveat:** I was not able to inspect the `go-ldap` library's exact `SimpleBind`/`Bind` wire-level behavior in this index (it's a third-party dependency), so I cannot 100% confirm whether the library adds any client-side guard against zero-length-password binds before sending the request; per RFC 4513 the LDAP protocol behavior itself is server-controlled, which is consistent with the original advisory's framing ("only deployments where LDAP servers are configured to allow unauthenticated binds... are affected"). If you need certainty about the `go-ldap` client internals, a Devin session with full dependency access could verify this further.

// TestPassword tests if an LDAP login bind can be performed with provided credentials, returns nil if success
func (l *ldapAuthenticator) TestPassword(ctx context.Context, email string, password string) error {
	conn, err := l.ldapClient.CreateEphemeralConnection()
	if err != nil {
		return errors.New("unable to establish connection to LDAP server with provided URL and credentials")
	}
	defer conn.Close()

	// Attempt to LDAP Bind with user provided credentials
	escapedEmail := ldap.EscapeFilter(strings.ToLower(email))
	searchBaseDN := fmt.Sprintf("%s=%s,%s,%s", l.config.BaseUserAttr(), escapedEmail, l.config.UsersDN(), l.config.BaseDN())
	err = conn.Bind(searchBaseDN, password)
	if err == nil {
		return nil
	}
	l.lggr.Infof("Error binding user authentication request in TestPassword call LDAP Bind: %v", err)

	// Fall back to test local users table in case of supported local CLI users as well
	var hashedPassword string
	if err := l.ds.GetContext(ctx, &hashedPassword, "SELECT hashed_password FROM users WHERE lower(email) = lower($1)", email); err != nil {
		return errors.New("invalid credentials")
	}
	if !utils.CheckPasswordHash(password, hashedPassword) {
		return errors.New("invalid credentials")
	}

	return nil
}

	return err == nil
