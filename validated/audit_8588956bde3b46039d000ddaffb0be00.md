### Title
Webhook `shop-domain` header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook by validating only the raw request body against the shared `api_secret_key` HMAC: [1](#0-0) 

The signable content is defined as the raw body alone — none of the identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) are part of the HMAC input: [2](#0-1) 

Yet `request.shop`, used as the tenant identity handed to the app's handler, is read straight from an unauthenticated HTTP header: [3](#0-2) [4](#0-3) 

and is passed unmodified into `WebhookMetadata` for the handler to act on: [5](#0-4) 

The broken identity binding, stated as an equality that the gem fails to enforce:
`shop authenticated-by-HMAC == shop used-for-tenant-routing`
In reality the HMAC only proves `body authenticated-by-HMAC == body-bytes-received`; the `shop` value is never bound into that computation, so any request carrying a body/HMAC pair that is valid for *some* installation of the app (all installations share the same `api_secret_key`, since HMAC verification in `HmacValidator.validate`/`compute_signature` uses only `Context.api_secret_key`, not a per-shop secret) will pass verification regardless of which shop's domain is asserted in the header: [6](#0-5) [7](#0-6) 

### Impact Explanation
This is a cross-tenant identity confusion: an attacker who controls (or has installed the app on) one shop can capture a legitimately-HMAC-signed webhook body/signature pair generated for their own tenant (e.g. by triggering any subscribed topic, including low-privilege/mandatory GDPR topics), and replay it to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` will still pass because it only checks the raw body against the shared app secret, and the app-supplied handler will process the payload believing it originated from the victim shop (`request.shop`), because nothing in the verified bytes ties the payload to a specific tenant. Depending on how the host app trusts `WebhookMetadata#shop` (e.g., to look up/mutate per-shop records, or to key off `dest`/`shop` for tenant-scoped writes), this enables cross-tenant data injection or state corruption — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Reachable by any unprivileged internet user who can install the app on any shop (including a throwaway/dev shop they control) and can send arbitrary HTTP requests to the app's public webhook endpoint. No access token, `client_secret`, or privileged credentials are required — only a validly-signed body for *any* tenant of the app, since the secret is shared across all merchant installations. The only work required is capturing one's own outbound webhook body+HMAC and replaying it with a modified `shop-domain` header.

### Recommendation
Bind the shop identity into the HMAC-verified content, or otherwise cryptographically tie the asserted `shop-domain` to the request: e.g., verify the shop against a value obtained independently (a stored access-token/session lookup keyed by a value in the verified payload) rather than trusting `request.shop` as-is, or include `shop-domain` in `to_signable_string` so tampering invalidates the HMAC. At minimum, the gem's documentation should explicitly warn integrators that `WebhookMetadata#shop` is unauthenticated and must be cross-checked against a known installed shop before being used for tenant-scoped side effects.

### Proof of Concept
```ruby
# Attacker owns/controls shop-a.myshopify.com and has installed the target app there.
# Any webhook fired for shop-a produces a valid (body, hmac) pair signed with the
# app's single shared api_secret_key.

raw_body = '{"id": 1}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# Attacker now sends this exact body+hmac to the app's webhook endpoint,
# but swaps the shop-domain header to the victim's shop:
spoofed_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not covered by HMAC
  "x-shopify-webhook-id" => "attacker-controlled",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: spoofed_headers)

# Passes verification: HmacValidator only checks raw_body against the shared secret.
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
# The app's handler now believes this event originated from victim-shop.
```
