### Title
Webhook shop-domain header not bound to HMAC signature enables cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` only signs/verifies the raw request body via HMAC, but the `shop` (and `topic`, `webhook_id`, `api_version`) values are taken from HTTP headers that are never included in the signable string. `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` when dispatching to the handler, even though only the body — not the shop identity — was cryptographically verified.

### Finding Description
`Utils::VerifiableQuery#to_signable_string` for `Webhooks::Request` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are read straight from attacker-visible/attacker-suppliable headers and are not part of that signable string: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC purely over `verifiable_query.to_signable_string` (i.e., the raw body) and compares it against the `hmac-sha256` header: [3](#0-2) 

`Registry.process` only calls `Utils::HmacValidator.validate(request)` and then immediately dispatches to the handler using `request.shop` as the tenant identity, with no separate binding check between the verified body and the claimed shop: [4](#0-3) 

The broken identity equality is:
`shop used by handler.handle(shop: request.shop, ...)` ≠ `shop that the HMAC-verified body actually originated from`.

Because the HMAC only proves "this body was signed with our `client_secret` at some point," and not "this body was sent for shop X," any raw body + valid signature pair that an attacker can obtain (e.g., a webhook delivered to their own endpoint for their own store, captured on the wire they control) can be replayed to the same endpoint with the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header rewritten to a victim shop. `HmacValidator.validate` still succeeds (body/signature unchanged), and `Registry.process` will hand the handler a `WebhookMetadata` claiming to be from the victim shop while carrying the attacker's own payload data.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce for webhook delivery: a host application that keys per-tenant logic off `WebhookMetadata#shop` (as the gem's own API surface encourages, since `shop` is the only tenant identifier exposed on the webhook object) can be made to apply attacker-supplied webhook data to a different (target) tenant's records — a cross-tenant data-confusion/cross-tenant access primitive, which meets the Critical bar for "cross-tenant access."

### Likelihood Explanation
Exploitation requires the attacker to first obtain at least one legitimate `raw_body` + `hmac-sha256` pair, which they can do without any special access simply by installing the app on their own (attacker-controlled) shop and capturing the webhook Shopify sends to the app's public HTTP endpoint (this is traffic destined for the attacker's own tenant, not interception of a third party's TLS session, so it does not require the excluded "TLS interception" or "leaked credentials" preconditions). From there, replaying the exact same bytes with a different `shop-domain` header against the same public endpoint is trivial for any unprivileged internet user, since the endpoint has no authentication other than the HMAC that this class does not bind to the shop.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook_id`) header values in the HMAC-signable material, or otherwise cryptographically bind the shop claim to the signed payload (e.g., require host apps to compare the header shop against an expected value tied to the delivery URL/path rather than trusting the header outright). At minimum, document and enforce that `WebhookMetadata#shop` must never be trusted as an authenticated tenant identifier unless the shop value is included in what `HmacValidator` verifies.

### Proof of Concept
1. Attacker installs the app on shop `attacker.myshopify.com` and captures a legitimate webhook delivery to the app's public callback URL:
   - Headers: `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac>`, body `B`.
2. Attacker resends an HTTP POST to the same callback URL with the identical body `B` and identical `X-Shopify-Hmac-Sha256` header, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Webhooks::Request.new` accepts this (all required headers present): [5](#0-4) 
4. `Registry.process` calls `HmacValidator.validate(request)`, which succeeds because it only checks `@raw_body` against the unchanged signature: [6](#0-5) 
5. The registered handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and the attacker's body data, despite `victim.myshopify.com` never having sent this webhook.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
