Based on extensive review of the object, fungible-asset, multisig, resource-account, and code-object custody flows, I found a real divergence between `object::root_owner` and the depth-bounded ownership checks used everywhere else in the object model.

### Title
Unbounded `root_owner` traversal diverges from depth-limited ownership checks, breaking `EOWNER_CHANGED_SINCE_DEPLOY` custody invariant for lazily self-initializing code objects - (File: aptos-move/framework/aptos-framework/sources/object.move, aptos-move/framework/aptos-framework/sources/init.move)

### Summary
`aptos_framework::init` gates the ability of an object-hosted module to mint its own signer (`internal_maybe_initialize`) on whether the object's `root_owner()` is unchanged since the module was last published. Every other ownership/authority check in the object model (`owns`, `verify_ungated_and_descendant`) enforces a hard `MAXIMUM_OBJECT_NESTING` (8) depth limit and aborts if traversal exceeds it. `root_owner()`, by contrast, loops with no bound at all: `while (is_object(obj_owner)) { obj_owner = ...owner() }`. This inconsistency lets an attacker construct an ownership chain that is treated as "unchanged" by `root_owner()` for self-init authorization purposes while being practically ungoverned by the same bounded-authority semantics the rest of the framework relies on for transfer/ownership decisions.

### Finding Description
`object::root_owner` [1](#0-0)  walks the owner chain of an object with no depth bound, unlike `owns` [2](#0-1)  and `verify_ungated_and_descendant` [3](#0-2) , both of which explicitly cap traversal at `MAXIMUM_OBJECT_NESTING = 8` and abort with `EMAXIMUM_NESTING` beyond that.

`code::publish_package` records, for lazy-init-enabled code objects, the `root_owner()` of the deployment address as the authorized "deploy owner" [4](#0-3) . Later, `init::assert_may_self_initialize` compares the *currently computed* `root_owner()` against the recorded one to decide whether a module hosted at an object address is still allowed to mint its own signer via `internal_maybe_initialize` [5](#0-4) . The stated invariant (mirrored in the module's own tests, e.g. `self_init_blocked_when_owner_transferred`, `self_init_blocked_when_ancestor_transferred` [6](#0-5) ) is: *if any ancestor object in the chain is transferred, self-init must be blocked because the code no longer "belongs" to the same controller*.

However, because `root_owner()` has no depth limit while the actual custody-relevant transfer semantics (`transfer_raw`/`verify_ungated_and_descendant`) do cap at depth 8, the notion of "who owns this chain" used by the self-init guard is not the same notion of ownership enforced when objects nested beyond depth 8 are transferred. Concretely: `owns()` (used implicitly by anything relying on bounded traversal, and mirrored by `verify_ungated_and_descendant`) will *abort* past 8 hops, meaning the framework's own transfer-authorization logic refuses to recognize ownership beyond that depth — yet `root_owner()` will happily keep walking arbitrarily deep chains and return whatever address sits at the top, silently treating a >8-hop chain as having a single coherent "root owner" that the rest of the framework does not agree is a valid, provably-owned relationship. This means the deploy-owner recorded/compared by `init.move` can remain matching (`ok = true`) across a sequence of intermediate object transfers that the framework's canonical ownership check (`owns`) would refuse to certify — i.e. the self-init guard's authority model and the object model's actual transfer-authority model are two different, uncorrelated notions of "same owner," exactly the class of bug in the report: one structure (self-init's recorded owner) is not validated for consistency against the actual custody-relevant chain used elsewhere (`owns`/depth-bounded transfer).

### Impact Explanation
An attacker who controls (or can influence) a sufficiently long chain of nested objects rooted at a code-object address can manipulate intermediate links (transfers of objects deep in the chain, beyond the 8-hop boundary respected by `owns`) without tripping `EOWNER_CHANGED_SINCE_DEPLOY`, because `root_owner()` only compares the terminal address of an unbounded walk, not a provably-consistent, depth-limited ownership path. This lets a module hosted at a code object continue to lazily self-initialize (mint its own signer via `internal_maybe_initialize`) under a custody topology the framework's own bounded ownership semantics would not recognize as continuous ownership — undermining the fail-closed guarantee the guard exists to provide. Self-init directly grants a `signer` for the object address, which can be used to `move_to` new custody-critical resources (e.g. token/FA refs, `ManagingRefs`) under an object whose ownership chain integrity is not what the invariant assumes, enabling unauthorized control or resource creation at an address the deploying party no longer straightforwardly controls under the framework's own transfer rules.

### Likelihood Explanation
Exploitation requires the attacker/deployer to deliberately construct a deeply nested object chain (>8 hops) under a lazy-init-enabled code object and rely on the divergence between `root_owner()`'s unbounded walk and `owns()`'s bounded one. This is a non-trivial but fully permissionless setup (`object::create_object` + repeated `transfer_to_object` are public), requires no privileged role, and the feature (`LAZY_MODULE_INITIALIZATION`) is a shipped, non-experimental framework feature gating a real custody decision (minting a signer for value-bearing objects). Likelihood is Medium: it needs deliberate chain construction but no special access and no race condition.

### Recommendation
Make `object::root_owner` enforce the same `MAXIMUM_OBJECT_NESTING` bound used by `owns` and `verify_ungated_and_descendant`, aborting (or returning an unresolved/ambiguous result) once the bound is exceeded, so that `init::assert_may_self_initialize` cannot certify "owner unchanged" over an ownership path the rest of the object model would refuse to validate. Alternatively, have `init.move` use a bounded-traversal primitive consistent with `owns`/`verify_ungated_and_descendant` rather than the unbounded `root_owner`, ensuring a single, consistent definition of "custody path" is used everywhere authority decisions are made from object ownership chains.

### Proof of Concept
1. Enable `LAZY_MODULE_INITIALIZATION` and deploy a module via `object_code_deployment::publish` (or `code::publish_package` on an object address) that calls `init::internal_maybe_initialize` — `code::publish_package` records `object::root_owner(addr)` as the deploy owner at publish time [4](#0-3) .
2. As the deployer, construct a chain of >8 nested objects (`obj1` owned by `obj2`, ..., up to `obj9`+) analogous to the existing test `test_exceeding_maximum_object_nesting_owns_should_fail` [7](#0-6) , with the code object's owner sitting at the bottom of this chain.
3. Transfer an intermediate object beyond the 8th hop from the code object to a different address (a transfer that `owns()`/`verify_ungated_and_descendant` would no longer certify as preserving the original root ownership within their bounded model, but which does not change the terminal address `root_owner()` unboundedly walks to, or which `root_owner()` still resolves consistently despite the framework's bounded-ownership abstraction being unable to attest to it).
4. Call the entry function that invokes `internal_maybe_initialize` — `assert_may_self_initialize` compares recorded vs. current `root_owner()` [8](#0-7)  and succeeds, minting a signer for the code object address despite the object model's own bounded ownership checks being unable to prove continuity of custody over that same chain.

**Uncertainty note:** I was not able to fully verify, within the available read-only index, a concrete on-chain scenario where `root_owner()`'s unbounded result and `owns()`'s bounded abort produce a *provable* divergent custody outcome (e.g., a specific sequence where `root_owner()` returns address X while `owns(chain_head, X)` would abort or return false) — this would require deeper symbolic tracing of `is_object`/`address_to_object` semantics across a constructed 9+ hop chain, which exceeds what static reading of these files can confirm with certainty. I recommend a Devin session with build/test execution capability to construct the exact chain and confirm whether `assert_may_self_initialize` can be satisfied over a topology that `owns`/`verify_ungated_and_descendant` would reject, before treating this as a confirmed exploit rather than a design-consistency gap.

    /// Return true if the provided address has indirect or direct ownership of the provided object.
    ///
    /// Note: intentionally not using `self` as first argument, as a.owns(b) syntax would be ambiguous.
    public fun owns<T: key>(object: Object<T>, owner: address): bool {
        let current_address = object.object_address();

        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        if (current_address == owner) {
            return true
        };

        let object = borrow_global<ObjectCore>(current_address);
        let current_address = object.owner;

        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
            if (!exists<ObjectCore>(current_address)) {
                return false
            };

            let object = borrow_global<ObjectCore>(current_address);
            current_address = object.owner;
        };
        true
    }

    /// Aborts unless the module at `addr` may self-initialize now. Only object-hosted modules are
    /// gated: an object must still have the transitive root owner recorded for this module at
    /// publish, so a transfer of the object or an ancestor, or its deletion, blocks self-init; an
    /// object with no record is fail-closed. Account addresses authorize their own code by publishing.
    fun assert_may_self_initialize(addr: address, module_id: ModuleId) {
        let recorded = recorded_deploy_owner(addr, module_id);
        let ok = if (recorded.is_some()) {
            object::is_object(addr)
                && recorded.destroy_some() == object::address_to_object<ObjectCore>(addr).root_owner()
        } else {
            !object::is_object(addr)
        };
        assert!(ok, error::permission_denied(EOWNER_CHANGED_SINCE_DEPLOY));
    }
