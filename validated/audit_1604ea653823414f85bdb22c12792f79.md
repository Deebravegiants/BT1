## Analysis

The rules explicitly call out "a field acted on but not covered by the HMAC" as a valid analog category, and this exact pattern exists in the webhook processing path. [1](#0-0) 

`Request#hmac` reads the `hmac-sha256` header, and `Request#to_signable_string` returns **only** `@raw_body`. The `shop` (and `topic`, `webhook_id`, `api_version`) values come from separate HTTP headers that are never included in the signed bytes: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.to_signable_string` (the raw body) against the HMAC: [3](#0-2) 

`Registry.process` validates that HMAC, then immediately forwards `request.shop` — the unauthenticated header value — as the tenant identity to the app's handler, with no cross-check against the shop that the webhook was actually registered/delivered for: [4](#0-3) 

### Title
Webhook shop-domain header is not bound to the HMAC, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `Registry.process` uses the separate, unsigned `shopify-shop-domain` header as the tenant identity passed to the host application's webhook handler.

### Finding Description
The HMAC computed by `HmacValidator.validate` authenticates only the byte content of `@raw_body`. It never covers the `shop`, `topic`, or `webhook_id` values, which are all read from independent HTTP headers via `shopify_header`. Any unprivileged internet user who possesses one valid `(raw_body, hmac)` pair signed by Shopify — trivially obtainable by installing the target app on their own attacker-controlled shop and capturing one legitimate webhook delivery — can resend that identical body/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header (and `topic`/`webhook_id`) with a victim shop's domain. `Utils::HmacValidator.validate` will still succeed because it only recomputes the signature over `@raw_body`, and `Registry.process` will pass the attacker-chosen `shop` value straight into `WebhookMetadata` for the handler to act on:

`equality broken: shop authenticated by HMAC (none) != shop acted on by the handler (request.shop header)`

### Impact Explanation
This breaks the identity binding between "the entity that Shopify's signature vouches for" and "the tenant the host application believes the event is about." Any host application that uses the webhook's `shop` field to select a merchant's session/access token, update per-tenant records, or otherwise route information ends up processing attacker-controlled events under another merchant's tenant identity — i.e., cross-tenant data injection/access, using only a self-installed free/dev shop as the credential source.

### Likelihood Explanation
High. No secrets, access tokens, or privileged accounts are needed — only installing the app on a shop the attacker controls (a normal, unprivileged action) to obtain one valid signed webhook body, and then replaying it with a rewritten header. The `hmac-sha256` header format, capture, and replay do not require intercepting TLS or any other privileged access.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header values in the signable string alongside the raw body so the HMAC binds the header metadata to the body, or have `Registry.process` cross-verify `request.shop` against the shop that owns the currently active/expected webhook registration before invoking the handler.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering a legitimate webhook delivery with a valid `x-shopify-hmac-sha256` header signed over some `raw_body`.
2. Attacker captures `(raw_body, hmac)`.
3. Attacker POSTs the same `raw_body` and `hmac` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` passes (it only checks `raw_body` vs `hmac`).
5. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...))`, causing the host app to act as if the event came from the victim's shop.
