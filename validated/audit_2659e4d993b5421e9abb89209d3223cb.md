### Title
Webhook `shop` and `topic` identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by verifying the HMAC over the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values, which are taken from HTTP headers and passed straight into `WebhookMetadata` (and thus into the host application's tenant-dispatch logic), are never included in the signed payload. An attacker who has legitimately obtained any single valid `(raw_body, hmac)` pair — trivial to acquire since any merchant who installs the app receives real, validly-signed webhooks for their own store — can replay that exact body/HMAC to the app's public webhook endpoint while forging the `shop-domain` (and `topic`) header to point at a different, victim tenant. `Utils::HmacValidator.validate` will report the request as authentic even though the tenant attribution is entirely attacker-controlled.

### Finding Description
`Registry.process` performs authentication like this: [1](#0-0) 

The HMAC check calls into `Utils::HmacValidator.validate`, which computes the signature only over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only the raw HTTP body — it does not include `shop`, `topic`, `webhook_id`, or `api_version`, all of which are parsed independently from headers and exposed via separate accessors: [3](#0-2) 

Those header-derived, *unsigned* values are then handed directly to the handler as the tenant identity for the event: [4](#0-3) [5](#0-4) 

This is the same bug class as the referenced report: an identity/authorization field (`shop`) is asserted and acted upon, but the mechanism meant to bind trust to it (the HMAC) never actually covers it. Compare this to `Auth::Oauth::AuthQuery`, where the analogous `shop` field for the OAuth callback *is* explicitly included in the signed string: [6](#0-5) 

showing that the library is capable of, and elsewhere does, bind `shop` into the signature — but omits doing so for webhooks.

Equality that should hold but doesn't:
`shop` used for tenant dispatch (`WebhookMetadata#shop`) == `shop` cryptographically bound by the HMAC over `to_signable_string`.

Before attacker action: a webhook's `shop` header happens to match the shop whose body was actually signed by Shopify because Shopify itself sets both consistently.
After attacker action: the attacker sends the exact same signed `raw_body`+`hmac` (obtained from a webhook fired for their own, legitimately installed store) to the app's webhook endpoint, but with a different `shop-domain` (and optionally `topic`) header. `HmacValidator.validate` still returns `true` because it only recomputes/verifies the hash of `raw_body`. The host application's handler now processes attacker-supplied `shop`/`topic` metadata as authenticated, cross-tenant.

### Impact Explanation
This is a cross-tenant authenticity break: a value that determines which merchant's data is affected (`shop`) is not cryptographically bound to the signature that is supposed to authenticate the whole request. Any host application relying on `WebhookMetadata#shop` (or `#topic`) to select which tenant's session/data to update — the intended and documented usage pattern of this gem — can be made to attribute an event to an arbitrary shop chosen by the attacker, without needing the `api_secret_key`. This matches the Critical bar of "cross-tenant access" in the rules.

### Likelihood Explanation
Any entity that can install the app on their own store (a normal, unprivileged action for a public app) can trigger legitimate webhook deliveries and thus capture a valid `(body, hmac)` pair signed with the app's shared `api_secret_key`. Because the webhook endpoint is a public HTTP endpoint (that's its purpose), replaying the captured body with a forged `shop-domain`/`topic` header requires no special access, no interception of TLS, and no knowledge of the secret itself. Likelihood is high for any multi-tenant app using this gem's webhook dispatch as documented.

### Recommendation
Bind `shop`, `topic`, `webhook_id`, and `api_version` into the signed content checked in `Webhooks::Request#to_signable_string`/`HmacValidator`, or — at minimum — cross-verify that the `shop`/`topic` values supplied in headers match values embedded in the verified body (e.g., most Shopify webhook payloads carry `shop_id`/equivalent fields inside the JSON body itself) before constructing `WebhookMetadata`. Alternatively, document explicitly that host applications must not trust `WebhookMetadata#shop`/`#topic` for tenant selection without independent verification, and provide a helper that performs that verification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` (fully legitimate, unprivileged action).
2. Shopify fires a real webhook to the app's endpoint; attacker captures the exact HTTP body and the `X-Shopify-Hmac-Sha256` header value — this HMAC is valid because it is signed with the app's shared `api_secret_key`.
3. Attacker replays the identical body + `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally a different `X-Shopify-Topic`).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `raw_body`, so validation succeeds: [7](#0-6) 
5. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built using the attacker-forged `shop`/`topic` header values and passed to the handler as authenticated data: [4](#0-3) 
6. Any host application logic keyed off `data.shop` (e.g., "look up session for this shop and apply the webhook body") now operates on the wrong tenant using attacker-controlled attribution.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
