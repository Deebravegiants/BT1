### Title
Webhook `X-Shopify-Shop-Domain` header is not covered by HMAC, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop` value attached to that same request (used to attribute the webhook payload to a specific merchant/tenant) is taken from an HTTP header that is excluded from the signed material. This breaks the intended binding `hmac == HMAC(secret, raw_body + shop)`; in this gem it is only `hmac == HMAC(secret, raw_body)`, so `shop` can be swapped freely without invalidating the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic tie to the signed body: [2](#0-1) 

`Utils::HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` against the HMAC: [3](#0-2) 

`Registry.process` uses this validator as the sole authentication gate before dispatching to the app's handler, and then constructs `WebhookMetadata` directly from the unauthenticated `shop` header alongside the authenticated body: [4](#0-3) 

Because `shop` is never bound into the HMAC, any party who possesses one valid `(raw_body, hmac)` pair for the app's secret — trivially obtainable by installing the app on their own (attacker-controlled) Shopify development store and capturing a legitimately delivered webhook — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header value (e.g. a victim merchant's shop). `HmacValidator.validate` still returns `true` because it never looks at the `shop` header, and `Registry.process` calls the app's handler with `WebhookMetadata.new(... shop: request.shop ...)` pointing at the victim shop but carrying attacker-chosen body content.

### Impact Explanation
This breaks the tenant-isolation guarantee the gem is expected to provide: "an HMAC-valid webhook for topic T with body B truly originated from Shopify for shop S." Instead the equality actually enforced is `HMAC-valid(B) ⇒ B is genuine`, with **no** guarantee about `S`. Any downstream app logic that uses `WebhookMetadata#shop` to key per-tenant records (order/customer/inventory updates, uninstall/redact handling, etc.) can be made to apply attacker-supplied data under a victim shop's identity — a cross-tenant data injection/confusion condition reachable by an unauthenticated internet user who only needs their own (free) Shopify dev store to mint a valid signature.

### Likelihood Explanation
High. Any unprivileged individual can create a free Shopify partner/development store, install the target app there, and receive a legitimately HMAC-signed webhook for their own shop. Swapping the `shop-domain` header and replaying the request to the target app's public webhook endpoint requires no secret and no privileged access — only a normal HTTP client.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the signed material that `Utils::HmacValidator` verifies, or independently authenticate the `shop` header against the session/shop that owns the given API secret before trusting it in `WebhookMetadata`. At minimum, document and enforce that `Registry.process` must not treat `request.shop` as authenticated, and require callers to cross-check it against their own webhook-subscription records for the shop that installed the app.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`) with body `B`. Shopify delivers a request with a valid `x-shopify-hmac-sha256` signature over `B`.
2. Attacker captures this `(B, hmac)` pair.
3. Attacker sends a POST to the app's webhook endpoint with:
   - body = `B` (unchanged, so HMAC still validates)
   - `x-shopify-hmac-sha256` = captured signature (unchanged)
   - `x-shopify-shop-domain` = `victim-shop.myshopify.com` (swapped)
   - `x-shopify-topic` = original topic
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which computes `HMAC(secret, B)` and compares to the (still-matching) signature — validation **succeeds**.
5. The registered handler is invoked with `WebhookMetadata` whose `shop` is `victim-shop.myshopify.com` but whose `body` is attacker-controlled `B`, demonstrating the tenant-binding break: ` [4](#0-3) `.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
