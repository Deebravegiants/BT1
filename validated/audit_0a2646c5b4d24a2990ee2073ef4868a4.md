### Title
Unchecked Low-Level `transfer` Return Data in Tron `IntentGatewayV2` Allows Escrow to Be Drained Without Delivering Tokens - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron-specific fork of `IntentGatewayV2` replaces the `SafeERC20`-based transfers used in the canonical EVM contract with manual low-level `.call()` invocations that only check whether the external call reverted, not whether the ERC20 `transfer` actually returned `true`. This is the same bug class as the referenced Sherlock report (unchecked `safeTransfer`/`safeTransferFrom` return value leading to fund loss), except here it manifests as failing to decode the boolean returndata of a raw `.call`, which a non-compliant/failing ERC20 can exploit to make the gateway believe a payout succeeded when it did not.

### Finding Description
In `withdraw()` and the `SweepDust` handler of `evm/tron/contracts/apps/IntentGatewayV2.sol`, token payouts are performed with:

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [1](#0-0) [2](#0-1) [3](#0-2) 

This pattern only verifies that the low-level call did not revert (`success == true`); it never decodes and checks the `bool` returndata that a spec-compliant ERC20 `transfer` returns. Per EIP-20, `transfer` can return `false` on failure instead of reverting (e.g., insufficient balance in some non-standard implementations, blacklisted/paused recipients in tokens like some stablecoin variants, or any token deliberately built to signal failure via a `false` return). With this code, such a `false` return is silently treated as a successful transfer:

- `_orders[body.commitment][token] -= amount;` still runs unconditionally right after the unchecked call in `withdraw()` [4](#0-3) , permanently decrementing the escrow accounting for tokens that were never actually delivered to the beneficiary/filler.
- `_filled[body.commitment] = beneficiary;` is set before the transfer even executes [5](#0-4) , marking the order as filled/redeemed regardless of transfer outcome.
- The `SweepDust` handler likewise emits `DustSwept` and moves on even if the underlying `transfer` returned `false` [6](#0-5) .

By contrast, the canonical (non-Tron) `IntentGatewayV2.sol` and `IntentsBase.sol` used across other EVM chains rely on OpenZeppelin's `SafeERC20.safeTransfer`, which does check the returned boolean and reverts on `false`: [7](#0-6) 

The Tron variant's deviation from `SafeERC20` for outbound transfers is the root cause — it downgrades a check that should assert delivery success to a check that only asserts the call didn't throw.

### Impact Explanation
This directly threatens escrowed user/solver funds inside the `IntentGatewayV2` cross-chain intents system, one of the explicitly in-scope reachable paths (intents escrow and bids). If a whitelisted or listed input/output token ever returns `false` instead of reverting on transfer failure (a real, documented ERC20 behavior class, and plausible on Tron given its distinct token ecosystem, e.g., TRC20 tokens with non-standard implementations), then:
- A solver/filler calling `onAccept`/`withdraw` for `RedeemEscrow` can have their fill marked complete and the escrow debited without ever receiving the tokens, resulting in permanent loss of the filled tokens for the solver while the order is marked as settled.
- A user calling `RefundEscrow`/cancel flows can lose their refund the same way, with `_filled` set and escrow decremented despite the beneficiary receiving nothing — functionally a full loss of the escrowed principal with no recovery path since `_filled` already blocks re-processing.

This is a concrete, permanent freezing/loss of escrowed funds, satisfying the acceptance bar for the audit scope (unbacked accounting divergence + fund loss from a normal, unprivileged relayer-delivered message).

### Likelihood Explanation
Likelihood is conditional on at least one token integrated with the Tron `IntentGatewayV2` returning `false` on failed transfer rather than reverting. This is common enough among ERC20/TRC20 tokens (older/non-standard implementations, some fee/permission-gated tokens) that it is a realistic risk for a permissionless intents system accepting arbitrary listed tokens, and any unprivileged party (order filler, relayer delivering the `RedeemEscrow`/`RefundEscrow` post, or the destination-chain solver) can trigger the vulnerable code path by simply completing the normal order lifecycle — no privileged role is required.

### Recommendation
Replace the manual `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` and the `SweepDust` handler with `SafeERC20.safeTransfer`, matching the canonical `IntentsBase.sol` implementation, so that both a reverting call and a `false` boolean return cause the transaction to revert instead of silently marking escrow as settled.

### Proof of Concept
1. List an ERC20/TRC20 token in an intent order whose `transfer()` implementation returns `false` on failure (e.g., recipient blacklisted, or a custom token deliberately crafted this way) instead of reverting.
2. A filler fills the order or the destination sends a `RedeemEscrow`/`RefundEscrow` POST that reaches `onAccept` → `withdraw()` [8](#0-7) .
3. Inside `withdraw()`, the token's `transfer` call returns `(true, false)` — i.e., the low-level call succeeds (`success == true`) but the ABI-decoded boolean payload is `false`.
4. Because only `success` is checked, `if (!success) revert TransferFailed();` does not trip [1](#0-0) , so `_orders[body.commitment][token] -= amount` executes and `_filled[body.commitment]` remains set from earlier in the function, permanently marking the order fulfilled.
5. The beneficiary never receives the tokens, yet the escrow is drained/zeroed and the order can never be retried, resulting in an irrecoverable loss of the escrowed amount.
