On the Solidity side, `from` is hardcoded to `abi.encodePacked(msg.sender)` in `_buildDispatchPost` [1](#0-0) , so an EVM sender cannot spoof `message.from` as someone else's address — this narrows (but does not eliminate) the impact of the pattern I was investigating in `pallet-hyper-fungible-token`.

### Title
Unsigned cross-chain calldata execution in `pallet-hyper-fungible-token::on_accept` dispatches arbitrary runtime calls without cryptographic authentication - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`on_accept` decodes an ABI `Message.data` field into `SubstrateCalldata { signature: Option<Vec<u8>>, runtime_call: Vec<u8> }` and, when `signature` is `None`, dispatches the attacker-supplied `runtime_call` with `RawOrigin::Signed(origin)` where `origin` is derived purely from the untrusted `message.from` bytes carried in the ISMP POST body, with no cryptographic proof that the destination-chain account was ever intended to authorize this call.

### Finding Description
In `on_accept`, when calldata is present and no `signature` is supplied, the origin used to dispatch the decoded `RuntimeCall` is computed directly from `message.from`: [2](#0-1) 

`message.from` is part of the ABI-encoded `Message` struct that is embedded in the ISMP POST request body — a field the *source-chain sender fully controls the encoding of at the application layer* (it is not part of the ISMP envelope's cryptographically-authenticated routing metadata; only `source`/consensus proof verification protects the request's origin chain and module, not the semantic `from` inside the opaque `body`). Although in the reference `HyperFungibleToken.sol` implementation `from` is hardcoded to `abi.encodePacked(msg.sender)` [1](#0-0) , this pallet is designed to be paired with *any* peer contract/pallet across arbitrary EVM and Substrate state machines that speaks the same wire `Message` ABI. Nothing in `on_accept` (or in the trait/type documentation) enforces that the paired contract also pins `from == msg.sender`; the pallet's own doc explicitly frames `EvmToSubstrate` as the *sole* authentication mechanism for the unsigned path: "Authenticates incoming EVM-originated runtime calls by mapping an EVM address to a substrate account" [3](#0-2) . This mirrors the CVE's root cause: a security-critical function (`dispatch`) trusts an implicit, unchecked assumption about the *type/provenance* of its input (that `message.from` is an authenticated identity) instead of validating it, and any custom or future peer/adapter contract that does not enforce `from == msg.sender` turns this into full unauthenticated arbitrary-call execution as any destination account.

Even bounding the analysis strictly to the shipped `HyperFungibleToken.sol`/`WrappedHyperFungibleToken.sol` peers (where `from` is pinned to `msg.sender`), the unsigned path still lets any account dispatch **any** runtime call (subject only to `BaseCallFilter`) as its own mapped account, purely by sending itself a token transfer with attacker-chosen `data`, with **no signature check at all** — i.e., the "unsigned calldata" branch is not an optional convenience, it is a bypass of the entire `MultiSignature` verification block that exists for the signed branch [4](#0-3) . This is intentional self-dispatch by design docs ("If no signature is provided, the origin is derived from the sender address in the cross-chain message") but combined with `BaseCallFilter::contains` being the *only* remaining gate, any dispatchable not explicitly filtered out becomes reachable cross-chain without replay protection tied to a real signature, and any deployer who reuses this pallet with a peer contract that does not rigidly pin `from` inherits a full unauthenticated-RCE-as-any-account bug — the "type validation" (that `from` is authenticated) is enforced only by convention in a sibling, out-of-repo-boundary contract, not by the pallet itself.

### Impact Explanation
If any current or future peer implementation (EVM or Substrate) fails to hard-pin `message.from` to the authenticated sender identity — which the pallet's own code does nothing to enforce or even check — an attacker can dispatch arbitrary `RuntimeCall`s as any target account on the destination chain, limited only by `BaseCallFilter`. This is unauthorized app action / potential unbacked mint or fund theft depending on what calls the runtime's `BaseCallFilter` permits (e.g. `Assets::transfer`, `Balances::transfer`, governance-adjacent calls not filtered). Even under the narrower, currently-shipped-peer assumption, an unsigned "self-dispatch" bypasses the entire cryptographic-signature-verification code path that exists specifically to authenticate calldata execution, which is inconsistent with the strong authentication otherwise required and increases the pallet's attack surface for any future dispatchable added to the runtime's call filter without this cross-chain path in mind.

### Likelihood Explanation
Reachable by any unprivileged sender simply by calling `send()` on the paired EVM/Substrate contract with a crafted `data` payload — no special privileges, relayer collusion, or consensus proof forgery required, since normal ISMP delivery (real consensus proof + real relayer) carries the payload as designed. The severity is contingent on `BaseCallFilter`'s configured allow-list and on whether any deployed peer implementation fails to pin `from`, which cannot be fully verified from this pallet's code alone (it depends on runtime configuration and on peer contracts that may exist outside the reference implementations reviewed here).

### Recommendation
Do not treat the absence of a signature as implicit authentication. Either (a) require a `signature` unconditionally for `SubstrateCalldata` execution and remove the unsigned fallback origin-derivation branch, or (b) if unsigned self-dispatch is intentional, cryptographically bind `message.from` to the ISMP request's verified origin (e.g., derive it solely from data provided by the `IsmpHost`/router as part of the message envelope rather than from attacker-controlled `body` bytes), and document/enforce in-pallet (not just in a sibling contract's convention) that `from` must equal the authenticated sender for every supported peer type.

### Proof of Concept
1. Deploy/target a peer contract or pallet (EVM or Substrate) paired with `pallet-hyper-fungible-token` that does not pin `message.from == msg.sender`/authenticated sender (or, for the shipped peer, simply call `send()` as yourself).
2. Craft `SendParams.data = abi.encode(SubstrateCalldata { signature: None, runtime_call: <SCALE-encoded RuntimeCall> })` targeting any dispatchable not excluded by `BaseCallFilter`.
3. Relay the message through Hyperbridge normally; `on_accept` decodes `substrate_data`, takes the `else` branch (no signature) at [5](#0-4) , derives `origin` from `message.from`, and dispatches the call with `RawOrigin::Signed(origin)` at [6](#0-5)  — with no signature verification performed anywhere in this branch.

I was not able to fully verify whether any *other* peer contract/pallet in this repo (beyond the two EVM implementations checked) sets `message.from` to something other than the authenticated sender, nor could I confirm the exact `BaseCallFilter` configuration used in the Nexus/Gargantua runtimes within the available index; a Devin session with full repo access would be needed to enumerate all peer implementations and the concrete call-filter allow-list to fully bound severity.
