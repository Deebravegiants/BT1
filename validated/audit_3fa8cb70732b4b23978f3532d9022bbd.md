### Title
Bad-debt supply-index write-down clamps to `SUPPLY_INDEX_FLOOR_RAW`, leaving wiped suppliers a phantom claim that drains the next depositor's cash - (File: contracts/pool/src/interest.rs)

### Summary
When `clean_bad_debt` (or a seizure) socializes bad debt larger than the total supplied value, `apply_bad_debt_to_supply_index` reduces the supply index to reflect a total wipeout — but then clamps the index up to `SUPPLY_INDEX_FLOOR_RAW` (`RAY/1000`) instead of reaching zero. Every pre-existing supply position keeps its share count, so each surviving supplier retains a small but nonzero residual claim worth `shares × RAY/1000`. The moment any new liquidity enters the market, those phantom claims become withdrawable and are paid out of the fresh depositor's principal. This mirrors the CVE-2021-4155 class: a size/claim extension that fails to zero out the stale allocation, exposing value the holder is no longer entitled to.

### Finding Description
`apply_bad_debt_to_supply_index` computes `remaining = total_supplied_value - min(bad_debt, total_supplied_value)` and multiplies the supply index by `remaining / total_supplied_value` — on a full wipeout that factor is `0` — but the result is floored at `SUPPLY_INDEX_FLOOR_RAW` via `new_supply_index.max(Ray::from(SUPPLY_INDEX_FLOOR_RAW))` (interest.rs:80-88). The wipeout is triggered from `seize::apply` on `AccountPositionType::Borrow` entries (ops/seize.rs:24-28), which is invoked by the controller's `clean_bad_debt` path through `execute_bad_debt_cleanup` → `pool_seize_positions_call` (controller/src/positions/liquidation/bad_debt.rs:14-49), an in-scope unprivileged entrypoint per the engagement rules.

Crucially, supplier share counts are never burned or rescaled — only the index moves. The pool's own tests prove the consequence:

- `test_raw_cache_floor_clamp_strands_claim_without_supply_guard` (contracts/pool/tests/interest.rs:373-428): after `apply_bad_debt_to_supply_index` clamps the index to `RAY/1000`, a wiped supplier's `resolve_withdrawal(i128::MAX, old_scaled)` still yields `gross > 0`; when a fresh deposit equal to the stranded claim is made, `require_reserves` passes and the wiped supplier withdraws exactly the fresh deposit, leaving `cash < fresh_claim`.
- `test_raw_cache_seizure_residual_would_drain_fresh_cash_without_supply_guard` (interest.rs:431-494): same pattern through the seizure path — Alice's wiped position extracts exactly Bob's fresh deposit; post-withdrawal `cash < bob_claim`, i.e., the books are insolvent.

The `require_reserves` guard reads the cash book, not the actual share liabilities, so once `cash > 0` the stranded claims settle at floor valuation against real tokens.

### Impact Explanation
Theft of user funds / protocol insolvency. A residual claim that should be economically zero can be converted into real tokens the instant the market receives new liquidity (a `supply`, a `repay`, a `recapitalize`, or liquidation proceeds). The aggregate stranded claim equals `floor(total_supply_shares × RAY/1000)`, paid for entirely by whoever next funds the pool — the pool's own test asserts `S_old drains exactly the fresh deposit` and `cash can no longer cover fresh supplier claim: funds lost`.

### Likelihood Explanation
The trigger is a wipeout-scale bad-debt event: `bad_debt >= total supplied value` for that (hub, token) book, reachable when an account's collateral in other assets cannot cover its debt after price moves, and `clean_bad_debt` or a liquidation seizure runs on it. Creating bad debt requires genuine under-collateralization, so it is not purely attacker-instantiated — but no privilege is needed to submit `clean_bad_debt` once the state exists, and any pre-existing supplier (including an attacker who supplies beforehand) holds the stranded claim. Medium likelihood, consistent with the source advisory's Medium severity.

### Recommendation
When `capped == total_supplied_value` (full wipeout), do not clamp the index to `SUPPLY_INDEX_FLOOR_RAW`; instead treat the market as fully written down — either set the supply index to zero (and gate subsequent mint/burn against a zero index) or burn the outstanding supply shares to zero alongside the debt burn, so no residual scaled position survives. If the floor is retained to keep index math nonzero, then all supply positions must be proportionally zeroed at cleanup time so `unscale_supply_floor` returns 0 for wiped suppliers, and `require_reserves`/solvency checks should compare liabilities, not just cash.

### Proof of Concept
The contract's own test-suite encodes the exploit end to end:

```rust
// contracts/pool/tests/interest.rs — test_raw_cache_floor_clamp_strands_claim_without_supply_guard
// 1. Alice supplies 1000 units (old_scaled = 1000 * RAY shares).
// 2. Bad debt >= total supply is socialized:
apply_bad_debt_to_supply_index(&mut cache, Ray::from(5_000 * RAY));
// supply_index clamps UP to RAY/1000 instead of 0:
assert_eq!(cache.supply_index().raw(), SUPPLY_INDEX_FLOOR_RAW);
// 3. Alice's wiped position still unwraps to a positive claim:
let stranded = cache.unscale_supply_floor(old_scaled); // > 0
// 4. Bob deposits fresh cash == stranded amount.
// 5. Alice resolves a full withdrawal; require_reserves passes on the book;
let (burn, gross) = cache.resolve_withdrawal(i128::MAX, old_scaled);
cache.require_reserves(gross);
cache.burn_supply(burn);
cache.debit_cash(gross);
// gross == Bob's deposit exactly; afterwards cash < Bob's claim — insolvent.
```

Through the live entrypoints the same sequence is: attacker/supplier holds supply shares → `clean_bad_debt` on an underwater account writes the index down to the floor → anyone calls `supply` on the pool → the wiped supplier calls `withdraw` (`amount = 0` full-close sentinel) and is paid from the fresh deposit.
