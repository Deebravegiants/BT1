### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0)  , and `HmacValidator.validate` computes the HMAC solely over that signable string [2](#0-1) . The `shop` value used to route/attribute the webhook, however, is read straight from the unauthenticated `shopify-shop-domain` HTTP header [3](#0-2)  and passed unchanged into `WebhookMetadata` that the application's handler trusts as the webhook's tenant identity [4](#0-3) [5](#0-4) . This breaks the binding: `shop header validated == shop the payload actually pertains to`, since the HMAC only certifies "this body was produced by the app's secret," not "this body belongs to this shop."

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook exclusively via `Utils::HmacValidator.validate(request)`, which authenticates `request.hmac` against `request.to_signable_string` (the raw body) using `Context.api_secret_key` [6](#0-5) . Because `to_signable_string` is only the raw body [1](#0-0) , the `shopify-shop-domain` header is never mixed into the signed material. Since a single app's `api_secret_key` is shared across every shop that installs the app, any valid `(raw_body, hmac)` pair obtained from one legitimately delivered webhook (e.g., one delivered to a shop the requester installed the app on) remains a cryptographically valid pair for that body regardless of which shop-domain header accompanies it.

An attacker who is simply a merchant that installed the app (an "unprivileged" party from the app's perspective, holding no special credentials for other shops) can:
1. Capture one genuine webhook delivery to their own store, including its valid `x-shopify-hmac-sha256` value for a chosen body.
2. Replay the same raw body and HMAC value to the app's webhook endpoint, but change `x-shopify-shop-domain` (or `shopify-shop-domain`) to a victim shop's domain.
3. `HmacValidator.validate` still returns `true`, because it only checks the body/HMAC pair against the shared app secret — it never checks that the header-derived `shop` is the one that actually produced that body.
4. `Registry.process` forwards `request.shop` (the attacker-controlled victim domain) into `WebhookMetadata`, and the handler processes the payload as if it originated from the victim's shop [7](#0-6) .

This is the same bug class as the analog report: a field that is acted upon (`shop`) is not covered by the integrity check (`HMAC` over body only), so an attacker who can produce *any* valid body/HMAC pair can rebind it to a different tenant identity.

### Impact Explanation
This allows cross-tenant data confusion/injection: an app that uses `data.shop` from `WebhookMetadata` to key persisted records (as shown in the gem's own documentation example, `perform_later(topic: data.topic, shop_domain: data.shop, ...)` [8](#0-7) ) can be made to write/act on attacker-controlled webhook content under a victim shop's identity, since the gem provides no mechanism to bind the verified body to the specific shop claimed in headers. This matches the Critical impact category of cross-tenant access.

### Likelihood Explanation
Exploitation requires only: (a) being a merchant who has installed the app (a normal, unprivileged action available to anyone), and (b) knowledge of a victim shop's `myshopify.com` domain (public information, often guessable or discoverable). No access to `api_secret_key`, access tokens, or the victim's credentials is needed — only replay of a body/HMAC pair the attacker legitimately received for their own installation. The gem provides no shop-binding check to prevent this, so likelihood is high for any app that trusts `data.shop` from `WebhookMetadata` for tenant-sensitive operations.

### Recommendation
Bind the shop identity into the verified material, e.g., by requiring/checking that the shop header of an incoming webhook corresponds to a shop with a currently valid installation/session known to the app before trusting `WebhookMetadata#shop`, or by including the shop domain in the value that is HMAC-verified where feasible. At minimum, document prominently (and ideally enforce in `Registry.process`) that `request.shop`/`data.shop` must be cross-checked by the consuming application against its own registered/installed-shop list before being used as a tenant key.

### Proof of Concept
1. App merchant "attacker-shop.myshopify.com" installs the app and receives a legitimate webhook:
   ```
   POST /callback/orders/create
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC for body B>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   Body: B
   ```
2. Attacker replays the exact same body `B` and HMAC value to the same endpoint, only substituting the shop header:
   ```
   POST /callback/orders/create
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <same valid HMAC for body B>
   x-shopify-shop-domain: victim-shop.myshopify.com
   Body: B
   ```
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` [9](#0-8) , which passes because it only checks `body` against the shared `api_secret_key` [2](#0-1) .
4. The handler receives `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` [7](#0-6)  and processes attacker-supplied content as though it belongs to the victim shop.
