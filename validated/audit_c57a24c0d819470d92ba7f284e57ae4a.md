### Title
Webhook shop-domain header is trusted as tenant identity without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [2](#0-1) , and `HmacValidator.validate` verifies the HMAC exclusively against that signable string [3](#0-2) . The `shop` value returned by `Request#shop` is read directly from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header [4](#0-3) , which is never included in the HMAC-signed bytes. `Registry.process` validates only the body's HMAC and then forwards the untouched, attacker-controlled header value as the tenant identity to the app's handler: `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` [5](#0-4) .

### Finding Description
The identity binding that should hold is: `shop attributed to the webhook == shop that produced the HMAC-signed payload`. Instead, the gem verifies `HMAC(secret, raw_body) == received_hmac` but binds tenant identity to `headers["shop-domain"]`, a value that is disjoint from the signed bytes.

Since the API secret (`Context.api_secret_key`) is shared across every shop that installs the app (webhooks aren't signed per-shop with per-shop keys), any party who can install the app on their own store (an unprivileged internet user, since app installation only requires clicking "Install" on a Shopify store they control) will receive genuine webhook deliveries with valid `X-Shopify-Hmac-SHA256` signatures for their own shop. That attacker can then:

1. Capture one legitimate webhook delivery to their own shop (raw body + valid HMAC).
2. Replay the exact same body and HMAC value to the target application's webhook endpoint, but substitute the `X-Shopify-Shop-Domain` header with a victim shop's domain.
3. `HmacValidator.validate` still succeeds because it only checks the body bytes against the secret — it never inspects or binds the `shop` header. `Request#shop` returns the attacker-supplied victim domain unchanged.
4. `Registry.process` passes this forged `shop` value straight into `WebhookMetadata`, and the app's handler (per the gem's own documented usage pattern, e.g., `perform_later(topic:, shop_domain: data.shop, webhook: data.body)`) uses it to route the webhook payload/business logic to the victim tenant's account/session.

This lets a low-privilege attacker inject data or trigger side effects (e.g., mandatory GDPR topics like `customers/redact`, `shop/redact`, `app/uninstalled` state transitions, or any custom handler logic keyed by shop) attributed to a shop the attacker does not control, i.e., a cross-tenant identity confusion enabled purely by the HMAC/tenant-identity mismatch inside this gem.

### Impact Explanation
This is a cross-tenant access vulnerability: an attacker who only controls their own (attacker-owned) shop installation can forge webhook deliveries that the receiving application will process as if they originated from an arbitrary victim shop, because the gem's own `HmacValidator`/`Webhooks::Request`/`Registry.process` chain never binds the `shop` header to the signed material.

### Likelihood Explanation
Any developer using an app that has installed the app on a Shopify store (trivial, unprivileged action) can generate at least one validly-signed webhook body/HMAC pair for their own shop, then replay it with a modified `shop-domain` header against the app's public webhook endpoint. No access token, `api_secret_key`, or privileged access is required — only observation of one's own legitimate webhook traffic.

### Recommendation
Bind the `shop` identity into the HMAC-verified material, or otherwise cross-check `request.shop` against a value derived from a secret the attacker cannot control (e.g., verify the shop against the topic/webhook registration state per-shop, or require the shop domain to be part of the signed payload before trusting it in `WebhookMetadata`). At minimum, document/enforce that `data.shop` must never be treated as authenticated without a secondary verification step (e.g., confirming an active, previously-registered session exists for that shop before acting).

### Proof of Concept
```ruby
# Step 1: Attacker installs the app on their own store "attacker-shop.myshopify.com"
# and receives (or triggers, e.g. via updating a product) a legitimate webhook:
raw_body = '{"id":1,"note":"hello"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), api_secret_key, raw_body)

# Step 2: Attacker replays the exact same body/HMAC to the app's public webhook
# endpoint, but swaps the shop-domain header to the victim's shop:
forged_headers = {
  "x-shopify-topic" => "products/update",
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled, unsigned
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (body/HMAC pair is valid)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
# The app now believes this payload legitimately originated from victim-shop.
```
