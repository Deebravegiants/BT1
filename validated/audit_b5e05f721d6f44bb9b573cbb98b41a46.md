### Title
Missing Chainlink min/max circuit-breaker validation in `SimplexPaymaster` allows mispriced gas payments during a price crash - ([File: evm/src/utils/SimplexPaymaster.sol])

### Summary
`SimplexPaymaster` prices ERC-20 gas payments using Chainlink `latestRoundData()` for both the native-asset and token oracles, but its `_getOraclePrice` helper only rejects non-positive answers and stale timestamps — it never checks the returned price against the aggregator's `minAnswer`/`maxAnswer` circuit-breaker bounds. If the real market price falls below (or spikes above) a feed's configured bound, Chainlink continues returning the clamped bound value as if it were current, and the paymaster will silently accept it as ground truth for every incoming `UserOperation`.

### Finding Description
`_getOraclePrice` is the sole gate on Chainlink data used for pricing: [1](#0-0) 

It reverts on `answer <= 0` and on staleness (`block.timestamp - updatedAt > maxOracleAge`), but performs no sanity check that `answer` is still inside the aggregator's live circuit-breaker range. Both the token/USD and native/USD prices computed here feed directly into `_tokenPrice`, which determines how many ERC-20 tokens a UserOperation's sender must pay for a given amount of native gas: [2](#0-1) 

`_tokenPrice` is invoked from `_fetchDetails`, which the ERC-4337 `EntryPoint` calls during validation of every UserOperation that names this paymaster — a path reachable by any unprivileged bundler/solver submitting a UserOp, with no governance gating: [3](#0-2) 

If the stablecoin (`tokenUsd`) feed's price crashes below its Chainlink `minAnswer` floor (e.g. a USDC/USDT de-peg event, mirroring the Venus/LUNA precedent cited in the source report), the aggregator keeps returning the artificially high floor value instead of the real, lower price. Since `tokenPrice = nativeUsd * 10^tokenDecimals * markup / tokenUsd`, an inflated `tokenUsd` denominator produces an under-priced `tokenPrice`, so `_erc20Cost` (used in `_prefund`) charges the solver/sender fewer stablecoin units than the native gas actually cost: [4](#0-3) 

This directly breaks the paymaster's own documented invariant that "the paymaster must not subsidise an honest op" (asserted in its test suite): [5](#0-4) 

The same unchecked oracle read is also used to size `amountOutMin` in the treasury-only `swapAndDeposit` recycling path, compounding the mispricing risk to the contract's stablecoin-to-native conversions: [6](#0-5) 

### Impact Explanation
Any UserOperation sender/solver interacting with `SimplexPaymaster` during a stablecoin de-peg (or any circuit-breaker-clamped price move) can pay less in tokens than the actual native gas cost, draining the paymaster's EntryPoint deposit and treasury-held surplus over time — a direct loss of protocol funds. Because the paymaster is fully permissionless for ordinary UserOps (any registered token, any sender), this is exploitable by an unprivileged solver without any special access, satisfying the "concrete theft or fund loss" bar.

### Likelihood Explanation
Exploitation requires only that one of the registered token/USD or the native/USD Chainlink feed be driven into its circuit-breaker floor/ceiling by real market conditions (e.g., a stablecoin de-peg below `minAnswer`), which is a documented, recurring real-world Chainlink behavior (as in the Venus/LUNA incident referenced in the report). No governance compromise or privileged role is needed — a solver merely needs to submit UserOps while the feed is clamped, which they can detect by simply calling `latestRoundData()` themselves.

### Recommendation
In `_getOraclePrice`, fetch the underlying aggregator's `minAnswer`/`maxAnswer` (via `AggregatorV2V3Interface`/`aggregator()` proxy call) and revert if `answer <= minAnswer` or `answer >= maxAnswer`, in addition to the existing staleness and positivity checks. Alternatively, cross-check the primary feed against a secondary oracle source (e.g., a TWAP) before accepting the price for `_tokenPrice`/`swapAndDeposit` calculations.

### Proof of Concept
1. Chainlink's `USDC/USD` (or similar) aggregator hits its configured `minAnswer` floor during a de-peg event and keeps returning that floor value from `latestRoundData()` while `updatedAt` is refreshed each round (so it never appears "stale").
2. A solver submits a UserOperation naming the affected stablecoin as the paymaster token; `_fetchDetails` calls `_tokenPrice` → `_getOraclePrice`, which accepts the floor price without reverting since `answer > 0` and not stale.
3. `tokenPrice` is computed using the inflated `tokenUsd` floor value, yielding a `prefundAmount`/`erc20Cost` lower than the true USD-equivalent of the gas consumed.
4. The solver's UserOp executes normally, paying the discounted token amount while the paymaster is debited the full real native gas cost from its EntryPoint deposit — a net loss to the paymaster/treasury, repeatable for every UserOp submitted while the feed remains clamped.

    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
