### Title
Webhook `shop` identity not covered by HMAC signature, enabling cross-tenant spoofing of webhook origin - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop` (tenant identity), `topic`, `webhook_id`, and `api_version` fields are all read from unauthenticated HTTP headers that are never included in the signed bytes.

### Finding Description
`Webhooks::Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)` [1](#0-0) , which in turn calls `validate_signature`, comparing `verifiable_query.hmac` against a signature computed over `verifiable_query.to_signable_string` [2](#0-1) .

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [3](#0-2) . The `shop`, `topic`, `webhook_id`, and `api_version` values used downstream are pulled directly from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) via `shopify_header`, and are **not** part of the signed payload [4](#0-3) .

After HMAC validation succeeds (which only proves the *body* bytes are authentic), `Registry.process` passes `request.shop` — the unauthenticated header value — straight into the tenant-identifying `WebhookMetadata` object handed to the app's handler: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [5](#0-4) .

Equality that should hold but doesn't: `shop verified by HMAC == shop used to attribute the webhook to a tenant`. In fact: `shop header parsed by request.shop` is disjoint from `bytes verified by HmacValidator (raw_body only)`.

### Impact Explanation
This is a broken binding between the bytes that are cryptographically verified (the body) and the field the host application uses to route data to a specific merchant/tenant (`shop`, taken from an unauthenticated header). If a merchant/attacker's own store can trigger a body-for-body-identical webhook payload (e.g., they control content of certain webhook payloads, such as `themes/publish`, `products/update`, or any topic where the body content is attacker-influenced), the same valid HMAC over that body can be replayed with the `shopify-shop-domain` header rewritten to name a *different* shop. Any downstream Devin/host code that trusts `WebhookMetadata#shop` for data isolation (e.g., using it as the tenant key to look up which merchant's session/data to update) can be tricked into associating data intended for shop A with tenant B — a cross-tenant integrity/confidentiality issue in the webhook processing pipeline that this gem exposes as its documented API.

### Likelihood Explanation
Exploitability depends on an attacker being able to produce (or capture) a request whose body content is identical or attacker-chosen for two different shops, and then relay it with a spoofed `shop-domain` header to the app's webhook endpoint while the HMAC (computed only over the body, with the app's secret) is unmodified. Because Shopify's own real HMAC generation is over the raw body and does not bind shop/topic/webhook-id into the signature, the app has no cryptographic assurance that these header values correspond to the entity that actually produced/signed the body. This does not require possession of `api_secret_key` — it only requires the ability to relay/replay a webhook body cross-shop with a modified header, which is plausible for a merchant who owns multiple shops or via header injection at a reverse proxy.

### Recommendation
Bind the `shop`, `topic`, and `webhook_id` header values into the object used to authorize/attribute a webhook, or independently re-verify that the `shop-domain` header matches an expected/registered value before trusting it for tenant attribution; alternately, document explicitly that `WebhookMetadata#shop` is not covered by the HMAC and must not be used as a sole tenant-authorization signal by consuming applications.

### Proof of Concept
1. Attacker (or a merchant operating shop-a and shop-b) captures a legitimate webhook POST from Shopify for `shop-a.myshopify.com` with body `B` and valid header `shopify-hmac-sha256` = HMAC(secret, B).
2. Attacker resends the same body `B` and same HMAC header to the app's webhook endpoint, but sets `shopify-shop-domain: shop-b.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` succeeds because it only verifies `B` against the HMAC [3](#0-2) .
4. `Registry.process` invokes the handler with `WebhookMetadata.new(... shop: "shop-b.myshopify.com" ...)` [5](#0-4) , causing the host app to process shop-a's data under shop-b's tenant context.
