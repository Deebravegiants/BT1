### Title
Webhook shop-domain header not covered by HMAC, allowing shop-identity spoofing on otherwise-valid webhook payloads - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `HmacValidator.validate` verifies that HMAC against the body alone [1](#0-0) . The `shop` accessor, however, is derived independently from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header [2](#0-1) , which is never included in the signable string used for HMAC verification [3](#0-2) . The identity binding broken is: `hmac_verified_bytes == raw_body` while `identity_used_by_host_app == shop_domain_header`, i.e. the byte range actually verified by the HMAC does not equal the byte range from which the tenant/shop identity is derived.

### Finding Description
Shopify's webhook HMAC scheme is meant to prove that a request's *entire* payload — including which shop it concerns — was generated by Shopify using the app's `client_secret`. In this gem, `HmacValidator.validate` (via `Utils::VerifiableQuery`) recomputes an HMAC over `verifiable_query.to_signable_string` and compares it to `verifiable_query.hmac` [4](#0-3) . For `Webhooks::Request`, `to_signable_string` is simply `@raw_body` [1](#0-0) , and `hmac` is pulled from the `hmac-sha256` header [5](#0-4) . Meanwhile, `shop` — the value host applications use to look up the tenant/session and route the payload — comes straight from the `shop-domain` header with no cryptographic tie to the HMAC-verified body [2](#0-1) .

Because HTTP headers are not part of the signed material, an unprivileged internet user who intercepts, replays, or otherwise obtains **any** single genuine, validly-signed webhook body from Shopify (bodies are not secret; they are plain JSON payloads, and many webhook topics are low-sensitivity, e.g. `app/uninstalled` test pings, product updates, etc.) can resend that exact body with a *different* `shop-domain` header value. `HmacValidator.validate` will still report success because it only checks the untouched raw body against the untouched HMAC header — the shop header substitution is completely invisible to the verification step.

### Impact Explanation
If the host application (following this gem's documented pattern of using `Webhooks::Request#shop` to identify which merchant/tenant a webhook belongs to, e.g. loading that shop's stored session/access token to act on the payload) trusts `request.shop` once `HmacValidator.validate` returns true, an attacker can cause the application to process a legitimately-signed payload under an attacker-chosen shop identity. This breaks the tenant boundary this gem is responsible for asserting: it lets a request "verified" as authentic (HMAC valid) be attributed to any shop domain of the attacker's choosing, i.e. cross-tenant confusion at the very primitive (`HmacValidator` + `Webhooks::Request`) that host apps rely on for webhook authentication. Depending on how the host app acts on `shop` (e.g. fetching/using that shop's persisted access token to perform further actions, or writing data keyed by the attacker-supplied shop), this can escalate to acting with another merchant's access token or corrupting another tenant's data — a cross-tenant access impact.

### Likelihood Explanation
Medium-to-high. No secret material is required — the attacker only needs one previously-observed valid signed webhook body (bodies are not confidential; e.g. captured via logs, network path, or a malicious middleware/proxy on the app's own infra, or simply their own store's outgoing webhook body for a topic they control) and can replay it with a forged `shop-domain` header any number of times, since headers are not covered by the signature and there is no nonce/timestamp binding in `to_signable_string`.

### Recommendation
Include the `shop-domain` header (and ideally other identity-relevant headers like `topic`, `webhook-id`) in the HMAC-signable material for webhook requests, or otherwise cryptographically bind the shop identity to the verified payload before exposing `Request#shop` to callers. At minimum, document/require host apps not to trust `shop-domain` independent of a separately-authenticated session, but the safer fix is to make `to_signable_string` (or an additional verification step) incorporate the shop-domain header bytes so a header swap invalidates the HMAC.

### Proof of Concept
1. Attacker's own store (or any observed source) receives a legitimate Shopify webhook: body `B`, header `X-Shopify-Hmac-Sha256: H`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`. `H` is a valid HMAC of `B` under the app's `client_secret`.
2. Attacker resends the exact same request to the app's webhook endpoint, keeping body `B` and header `H` unchanged, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. App calls `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim-shop.myshopify.com", hmac-sha256: H...})` then `ShopifyAPI::Utils::HmacValidator.validate(request)`.
4. `to_signable_string` returns `B` (unchanged), `hmac` returns `H` (unchanged) → `validate` returns `true`.
5. `request.shop` now returns `"victim-shop.myshopify.com"` even though the payload was never actually signed for that shop — the app processes the payload as if it legitimately concerns `victim-shop.myshopify.com`.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
