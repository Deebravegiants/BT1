Found: `Webhooks::Request#shop` reads the shop identity from the unauthenticated header `shopify-shop-domain`, while the HMAC in `to_signable_string` only covers `@raw_body` — the shop value is never part of the HMAC-verified bytes, so `shop` and `topic` can be forged even when the HMAC passes.

### Title
Webhook `shop` and `topic` identity is taken from unauthenticated headers, not covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity via HMAC over `@raw_body` only, but exposes `shop`, `topic`, `api_version`, and `webhook_id` from HTTP headers that are never included in the signed bytes.

### Finding Description
`HmacValidator.validate` calls `verifiable_query.to_signable_string` and HMACs it with `Context.api_secret_key` [1](#0-0) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [2](#0-1) , while `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers with no cryptographic binding to that body or to the HMAC [3](#0-2) . This breaks the identity binding `bytes verified == bytes parsed for the tenant`: the equality that should hold is `shop-in-signed-payload == shop-used-for-tenant-routing`, but here `shop-used-for-tenant-routing` comes from an out-of-band header the attacker fully controls.

Any caller of the webhook processing pipeline that dispatches based on `Request#shop` (e.g., to select which merchant's session/config to load, or to log/route per-tenant) will trust a header value that was never part of the HMAC-verified content. An attacker who can replay or forge a request body signed under any known/legitimate HMAC context (e.g., reusing a body whose HMAC they don't control, or more directly, an attacker who controls the raw body and can compute a valid HMAC — e.g. a compromised low-trust integration, or a request proxy that mutates headers post-verification) can supply an arbitrary `shopify-shop-domain` header to make the framework attribute the payload to a different shop than the one it actually originated from.

### Impact Explanation
If application code built on this gem uses `Request#shop` to select the tenant context (session, credentials, or business logic) after HMAC validation succeeds, an attacker can cause cross-tenant misattribution of a webhook payload — i.e., data intended for/about shop A gets processed under shop B's identity, or vice versa. This matches the Critical "cross-tenant access" impact class since the shop identity, the fundamental tenant boundary in this multi-tenant SDK, is not authenticated.

### Likelihood Explanation
Exploitability depends on the ability to control/forge headers independent of the signed body, which is plausible in setups where headers are set by a proxy or where any intermediary (e.g., a shared webhook receiving endpoint, load balancer rewriting headers) is not fully trusted, or in any scenario where the raw body and its HMAC come from a source distinct from the header injection point. This is not a purely theoretical bug: the design explicitly signs the body but not the headers that carry the tenant identity.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable/verified payload, or otherwise cryptographically bind them to the HMAC (e.g., require that the shop domain used for tenant resolution match a value embedded in and covered by the verified body, not a bare header).

### Proof of Concept
1. Attacker (or a compromised intermediary) sends a POST to the app's webhook endpoint with a raw body `B` and a valid `hmac-sha256` header computed over `B` with the real shop's secret (this can occur if the attacker reuses a previously observed legitimate webhook body+HMAC pair — replay is possible since headers, not the body, carry shop identity).
2. Attacker sets `x-shopify-shop-domain: victim-shop.myshopify.com` (a different shop than the one that actually triggered `B`).
3. `HmacValidator.validate` computes over `Request#to_signable_string` (`@raw_body` only) and succeeds, since `@raw_body` and its HMAC are consistent [4](#0-3) .
4. Application code trusts `Request#shop` == `victim-shop.myshopify.com` [5](#0-4)  and processes the payload under that shop's tenant context, despite the shop never being part of the verified bytes.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
