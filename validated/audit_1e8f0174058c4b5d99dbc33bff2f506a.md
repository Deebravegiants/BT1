### Title
Unbounded ancestry-chain walk over attacker-supplied GRANDPA headers causes an infinite loop before any signature check - (File: `modules/consensus/grandpa/primitives/src/justification.rs`)

### Summary
`AncestryChain::ancestry` walks backward from a target block hash to a base hash by following `parent_hash` pointers taken from an attacker-supplied `Vec<Header>` (`votes_ancestries` / `unknown_headers`), with no cycle detection and no depth bound. `verify_grandpa_finality_proof` calls this walk **twice** — before the GRANDPA justification's cryptographic signatures are ever checked. A relayer submitting a permissionless GRANDPA consensus update (`ConsensusMessage::StandaloneChain`/`Relaychain`/`Polkadot`, dispatched through `update_client` → `GrandpaConsensusClient::verify_consensus`) can supply a cyclic pair of self-consistent headers that never reaches the required base hash, causing the loop to run forever. This is the direct analog of CVE-2025-32399 (unchecked loop condition on attacker-controlled input causing infinite loop).

### Finding Description
`AncestryChain::new` indexes an arbitrary `Vec<H>` of headers by their own computed hash, with no validation that they form a real, acyclic chain: [1](#0-0) 

`ancestry()` then walks backward purely by following `parent_hash`, with no visited-set / cycle check and no maximum iteration bound: [2](#0-1) 

Because a header's hash is computed from its own fields, an attacker can freely construct two headers `H1`/`H2` whose `parent_hash` point at each other (`H1.parent_hash == H2.hash()`, `H2.parent_hash == H1.hash()`), append them into `unknown_headers`, and make one of them line up with the required `target` hash (max-numbered header, whose hash must equal `finality_proof.block`). Nothing forces this cycle to also pass through the trusted `base`/`from` hash.

Critically, `verify_grandpa_finality_proof` invokes `headers.ancestry(...)` **before** verifying the justification's authority signatures: [3](#0-2) 

So the attacker does not need any valid GRANDPA authority signatures at all — only a self-consistent, attacker-crafted `unknown_headers` list and a `justification` blob that merely decodes (its `commit.target_hash` must equal `finality_proof.block`, but the precommit signatures inside it are never checked before the ancestry walk runs).

This function is reached from a fully permissionless path: `GrandpaConsensusClient::verify_consensus` (`modules/ismp/clients/grandpa/src/consensus.rs:169-173` for `StandaloneChain`, and `verify_parachain_headers_with_grandpa_finality_proof` for `Polkadot`/`Relaychain`) is called by `pallet_ismp`'s `update_client` handler: [4](#0-3) 

`update_client` is invoked from `handle_unsigned`/message-dispatch paths that anyone can submit via a `ConsensusMessage` — there is no authorization check prior to `verify_consensus`.

The identical unbounded-walk pattern is duplicated in `verify_fraud_proof` (`modules/ismp/clients/grandpa/src/consensus.rs:309-320`) and in `GrandpaJustification::verify_with_voter_set`'s own `ancestry_chain.ancestry(...)` call (`modules/consensus/grandpa/primitives/src/justification.rs:125-127`), so multiple entry points share the same root cause.

### Impact Explanation
This runs inside on-chain (WASM) block execution as part of processing a submitted ISMP consensus message. An infinite loop here is not bounded by normal weight-metering short-circuits (the loop body itself never returns), so a single malicious/crafted consensus-update transaction can hang block execution for the GRANDPA consensus client's runtime, halting processing of that extrinsic (and, depending on execution model, potentially the whole block). At minimum this makes the affected consensus route unable to process any further legitimate finality proofs/state updates — i.e., "a route unable to deliver messages" — which is explicitly one of the accepted impact categories. Given this is triggerable pre-authentication (before any real GRANDPA signature is checked) by any address able to submit a consensus message, this is a high-value, cheap DoS vector reachable by any unprivileged relayer.

### Likelihood Explanation
High. No signatures, no state history, and no special privileges are required — the attacker only needs to construct two self-consistent header structs with reciprocal `parent_hash` values and place them in `unknown_headers`/`votes_ancestries`, along with a decodable justification whose `commit.target_hash` matches the crafted target header's hash. All of this is fully computable offline and submitted as a normal consensus-update message.

### Recommendation
Bound `AncestryChain::ancestry` with either (a) a fixed maximum iteration count derived from `ancestry.len()` (since a valid acyclic path can visit at most `len()` distinct headers), returning an error once exceeded, or (b) a `visited: BTreeSet<Hash>` that rejects re-encountering a hash. Additionally, reorder `verify_grandpa_finality_proof` (and the analogous fraud-proof path) to validate the justification's cryptographic signatures and authority-set membership before performing any ancestry walk over attacker-controlled headers, so unauthenticated header graphs can never reach the unbounded traversal.

### Proof of Concept
1. Construct header `H_target` such that `H_target.hash() == commit.target_hash` for an otherwise-arbitrary `GrandpaJustification` (the attacker crafts both the header and the justification, so this is trivial to satisfy) and set `H_target.number()` to the maximum in the set.
2. Construct `H_evil1` and `H_evil2` with `H_evil1.parent_hash = H_evil2.hash()` and `H_evil2.parent_hash = H_evil1.hash()`, neither equal to the trusted `consensus_state.latest_hash`.
3. Set `H_target.parent_hash = H_evil1.hash()`.
4. Submit `unknown_headers = [H_target, H_evil1, H_evil2]` and the justification as a `ConsensusMessage::StandaloneChain` (or `Polkadot`/`Relaychain`) consensus update via the normal ISMP message-submission path.
5. `verify_grandpa_finality_proof` computes `target = H_target`, then calls `headers.ancestry(from, target.hash())`, which walks `H_target → H_evil1 → H_evil2 → H_evil1 → H_evil2 → ...` forever, since `from` (the trusted hash) is never reached and no cycle/iteration bound exists — before the justification's signatures are ever verified.

I was not able to execute this against a live runtime to observe the actual weight/limit behavior (e.g., whether the host's WASM execution environment has any external watchdog that would abort a truly infinite Rust loop); this assessment is based on static code-path analysis of the loop and its call graph.

	/// Initialize the ancestry chain given a set of relay chain headers.
	pub fn new(ancestry: &[H]) -> AncestryChain<H> {
		let ancestry: BTreeMap<_, _> = ancestry.iter().cloned().map(|h: H| (h.hash(), h)).collect();

		AncestryChain { ancestry }
	}

	/// Fetch a header from the ancestry chain, given it's hash. Returns [`None`] if it doesn't
	/// exist.
	pub fn header(&self, hash: &H::Hash) -> Option<&H> {
		self.ancestry.get(hash)
	}
}

	fn ancestry(
		&self,
		base: H::Hash,
		block: H::Hash,
	) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
		let mut route = vec![block];
		let mut current_hash = block;
		while current_hash != base {
			match self.ancestry.get(&current_hash) {
				Some(current_header) => {
					current_hash = *current_header.parent_hash();
					route.push(current_hash);
				},
				_ => return Err(finality_grandpa::Error::NotDescendent),
			};
		}
		Ok(route)
	}
