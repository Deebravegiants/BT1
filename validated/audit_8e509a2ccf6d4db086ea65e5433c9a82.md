### Title
Webhook shop identity (`shop`, `topic`, `api_version`, `webhook_id`) is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw body only, while the shop identity and other routing metadata come from unauthenticated HTTP headers that are never covered by the signature. `Registry.process` validates only the body HMAC and then blindly forwards the header-derived `shop` to the app's webhook handler, so the "which tenant does this event belong to" binding is not enforced by the signature check.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all read directly from HTTP headers with no cryptographic binding to the request: [2](#0-1) 

`HmacValidator.validate_signature` verifies `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e. only the body bytes are checked; the header values are not part of the signed message: [3](#0-2) 

`Registry.process` performs that body-only HMAC check and then dispatches to the app handler using the unauthenticated `request.shop`: [4](#0-3) 

This is exactly the "field acted on but not covered by the HMAC" pattern named in the bug-class hint: the equality the code implicitly assumes is `shop-domain header == the shop that produced this signed body`, but the code only proves `HMAC(body, secret) == received signature`; it never proves the header-carried `shop` was the origin of that specific signed payload. By contrast, `Auth::Oauth::AuthQuery#to_signable_string` correctly folds `shop` into the signed string, so the shop identity there *is* bound to the HMAC: [5](#0-4) 

### Impact Explanation
Because `shop` is unauthenticated, an attacker who has legitimate access to any one merchant install of the app (i.e., an ordinary, unprivileged app user, not requiring `api_secret_key` or an access token) can capture a genuinely HMAC-signed webhook body that the app sent to their own store's endpoint, and replay it to the app's public webhook endpoint with a forged `x-shopify-shop-domain` (or `shopify-shop-domain`) header naming a different, victim shop. `HmacValidator.validate` still returns `true` because it only checks the body bytes, and `Registry.process` will invoke the app's handler with `WebhookMetadata` claiming to be from the victim shop. If the host app's handler uses this `shop` value to look up/act on per-tenant data (a normal and expected usage pattern for webhook handlers), this results in cross-tenant confusion/cross-tenant action taken under another merchant's identity — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only: (1) being an app user/merchant capable of triggering at least one legitimate webhook delivery to capture a valid `(body, hmac)` pair (generic/templated bodies, e.g., `app/uninstalled` with `{}`, make this trivial and shop-independent), and (2) sending a crafted HTTP POST to the app's public webhook endpoint with forged headers. No secrets, tokens, or privileged access are needed, making this reachable by any unprivileged internet user who can install the app once.

### Recommendation
Bind the tenant/routing identity into the signed message, or otherwise cryptographically verify it, before trusting header-derived values:
- Include `shop`, `topic`, and `webhook_id` (or reconstruct trust via Shopify's per-webhook subscription lookup) as part of what's verified against the signature, not just the raw body, or
- Cross-check the header `shop` against Shopify (e.g., via `get_webhook_id`-style API lookup) before dispatching to the handler, or
- Document explicitly and enforce in `Registry.process` that consuming apps must not treat `WebhookMetadata#shop` as trusted unless independently re-verified.

### Proof of Concept
1. App owner subscribes to a webhook with a shop-independent payload, e.g. `app/uninstalled`, delivered as raw body `"{}"`.
2. Attacker (a normal merchant with the app installed) intercepts the delivery and records the valid header `x-shopify-hmac-sha256` for body `"{}"`, computed as:
```ruby
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_SECRET, "{}")
```
(the app's secret is fixed and shared across all shops, so this signature is valid for `"{}"` regardless of shop).
3. Attacker POSTs to the app's public webhook endpoint with:
```
x-shopify-topic: app/uninstalled
x-shopify-hmac-sha256: <captured hmac from step 2>
x-shopify-shop-domain: victim-shop.myshopify.com
```
and body `"{}"`.
4. `ShopifyAPI::Webhooks::Registry.process` builds `Request.new(raw_body: "{}", headers: forged_headers)`; `Utils::HmacValidator.validate` returns `true` (body matches signature); `handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))` is invoked — the app now processes an `app/uninstalled` (or any other captured topic/body) event attributed to `victim-shop.myshopify.com`, even though that shop never sent or authorized this request.
