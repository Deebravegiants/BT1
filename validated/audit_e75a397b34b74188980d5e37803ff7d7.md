## Title
Permissionless `fillOrder()` enables front-running of solver auction winners, allowing MEV bots to steal escrowed order inputs by copying a pending fill at the minimum accepted price - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.fillOrder()` is the on-chain analog of `buyCollateralFromAuction()`: it is a permissionless, first-caller-wins function that transfers valuable escrowed assets to whoever successfully calls it first. Unless `Params.solverSelection` is enabled, there is no on-chain binding between the off-chain "auction" (bids collected via the Hyperbridge coprocessor) and the actual fill, so any address monitoring the mempool can copy a pending solver's `fillOrder` calldata, resubmit it with higher gas/priority fee, and win the fill itself — capturing the escrowed input tokens intended for the legitimate winning solver.

### Finding Description
`fillOrder(Order calldata order, FillOptions calldata options)` only enforces solver-identity checks when `_params.solverSelection` is true: [1](#0-0) 

When `solverSelection` is disabled (the default/permissionless mode described in the docs), the function performs no check on `msg.sender` at all — it only validates the order hasn't expired, hasn't been filled, and that output amounts meet the minimum required: [2](#0-1) 

`_fillSameChain` / `_fillCrossChain` then immediately mark the order filled and release the escrowed inputs to `msg.sender` as soon as the *minimum required* output is supplied — no better-price guarantee is enforced on-chain: [3](#0-2) [4](#0-3) 

The documentation confirms that the "auction" (competing solver bids) is an off-chain/Hyperbridge-hosted process with no on-chain enforcement unless `solverSelection` is turned on: [5](#0-4) 

Because a solver's winning `fillOrder` transaction (with its calldata specifying `options.outputs`) is visible in the public mempool before inclusion, any third party can extract that calldata, resubmit an identical (or minimally adjusted, at-minimum) transaction with a higher gas price, and land first. This is functionally identical to the reported `buyCollateralFromAuction()` issue: a permissionless "claim collateral/escrow at a computed price" function with no commit-reveal or session binding, vulnerable to copy-and-frontrun by anyone racing the mempool.

### Impact Explanation
A front-runner can:
1. Steal the arbitrage/fill opportunity from the legitimate solver who performed price discovery and won the off-chain auction, taking the escrowed input tokens for themselves while paying only the bare minimum required output — denying the order's beneficiary any surplus that the honest winning solver might have provided.
2. Grief solvers who submit `fillOrder` transactions (they lose gas and the opportunity), discouraging solver participation in the auction, which undermines the competitive pricing model central to the Intent Gateway's value proposition.

This results in unauthorized diversion of escrowed order value away from the intended solver/beneficiary via an economically motivated MEV attack, matching the "unauthorized app action" / value-diversion bar reachable by a single, unprivileged, submitted transaction from an intent solver.

### Likelihood Explanation
High for any deployment where `solverSelection` is disabled (the simpler default mode documented for same-chain and basic cross-chain swaps). Front-running/copy-trading of visible mempool transactions is a well-known, cheap, and automatable MEV strategy requiring no special access — only mempool visibility and marginally higher gas.

### Recommendation
- Bind fills to a specific authorized solver even when `solverSelection` is nominally "disabled" by defaulting to a lightweight commit-reveal or requiring `msg.sender` to match an off-chain-selected solver address embedded in the order/commitment.
- Alternatively, use a private mempool / flashbots-style relay for solver fill submissions, or require solvers to stake/commit before revealing fill parameters, reducing copy-and-frontrun exposure.
- Document clearly that permissionless (`solverSelection = false`) mode is inherently racey and should only be used when the value of MEV-extractable surplus is acceptable, and recommend `solverSelection = true` for high-value order flows.

### Proof of Concept
1. Deploy `IntentGatewayV2` with `Params.solverSelection = false` (permissionless mode).
2. User places an order via `placeOrder`, escrowing input tokens; solvers observe `OrderPlaced` and compete off-chain via bids.
3. Solver A submits a `fillOrder(order, options)` transaction with output amounts equal to `order.output.assets` (minimum required, or with a modest surplus) — visible in the public mempool.
4. Attacker (any address) copies Solver A's calldata verbatim, submits it as their own transaction with a higher gas price, and it is mined first.
5. `fillOrder` succeeds for the attacker per the check flow in `evm/src/apps/IntentGatewayV2.sol` lines 443-483 (no `msg.sender` restriction when `solverSelection` is false); `_fillSameChain`/`_fillCrossChain` releases the escrowed inputs to the attacker.
6. Solver A's original transaction now reverts with `Filled()` (per `_filled[commitment] != address(0)` check), losing gas and the fill opportunity, while the attacker captured the escrow for providing only the bare minimum output.

## Solver Selection

When `solverSelection` is enabled in the intent gateway parameters, orders are protected from unauthorized fills. At order placement, the user specifies a `session` key — a temporary keypair generated for this order. Only a solver explicitly authorized by the session key can fill the order.

### `SolverAccount`

The SolverAccount is a smart account designed for solvers that combines [ERC-4337](https://eips.ethereum.org/EIPS/eip-4337) (account abstraction), [EIP-7702](https://eips.ethereum.org/EIPS/eip-7702), and [ERC-7821](https://eips.ethereum.org/EIPS/eip-7821) (batch execution) to batch `gateway.select(...)` and `gateway.fillOrder(...)` into a single atomic UserOperation. Solvers delegate their EOA to the SolverAccount via EIP-7702 and submit bundled operations through the ERC-4337 EntryPoint.
