### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) identity fields are not covered by the HMAC signature, allowing tenant spoofing in `WebhookMetadata` - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw JSON body, then trusts the `shop-domain` HTTP header — which is not covered by that HMAC — as the tenant identity passed to the host application's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `#hmac` is derived from the `hmac-sha256` header: [1](#0-0) 

`Registry.process` validates the request using `Utils::HmacValidator.validate(request)`, which calls `to_signable_string` and compares against a signature computed from that string alone: [2](#0-1) [3](#0-2) 

The identity binding that should hold is: `hmac == HMAC(secret, raw_body ‖ shop ‖ topic ‖ webhook_id)`, i.e. the tenant (`shop`) that the handler acts on should be cryptographically bound to the same signature that authenticates the payload. In this gem, the actual equality enforced is only `hmac == HMAC(secret, raw_body)`; `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated headers via `shopify_header`: [4](#0-3) [5](#0-4) 

`request.shop` (and the other header-derived fields) are then forwarded, unverified, into `WebhookMetadata` and handed to the host application's handler as the authoritative tenant identifier: [2](#0-1) [6](#0-5) 

Because the app's webhook secret (`api_secret_key`) is shared across every shop that installs the app (it is not per-shop), an attacker who legitimately installs the app on their own store can obtain webhook deliveries with a body and HMAC that are valid under the app's secret. Since the HMAC covers only the body, that same `(body, hmac)` pair remains valid if replayed with the `shopify-shop-domain` header rewritten to a victim shop, and `Registry.process` will accept it and hand the handler a `WebhookMetadata` claiming the victim shop as the source.

### Impact Explanation
This breaks the tenant/shop identity binding that the host application relies on to know which merchant's data a webhook body belongs to, enabling cross-tenant data confusion: a handler that stores or acts on `data.body` keyed by `data.shop` can be made to associate one shop's payload with another shop's identity. This matches the "Critical – cross-tenant access" impact category, since it is a break of the tenant isolation the gem is expected to provide via HMAC verification.

### Likelihood Explanation
Requires the attacker to be a legitimate installer of the target app on their own shop (an unprivileged/normal Shopify merchant — no special access needed), to capture one valid `(raw_body, hmac)` pair delivered to their own endpoint, and to replay it with a forged `shop-domain` header to the app's webhook endpoint. No `client_secret`, access token, or credential compromise is required, only routine merchant installation, satisfying the unprivileged-internet-user constraint.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the value that is HMAC-verified, e.g. include the `shop-domain` header (and other identity headers) in `to_signable_string`, or independently verify that `shop` matches an expected/authorized value (e.g. the shop associated with the currently active session) before invoking the handler, rather than trusting the raw header value implicitly.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook POST with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker resends the exact same body `B` and hmac header `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B) == H` — this passes because `B` and `H` are unchanged.
4. `Registry.process` builds `WebhookMetadata.new(shop: request.shop, ...)` using the forged `shop-domain` header and invokes the host app's handler, which now processes/stores data `B` under the identity of `victim-shop.myshopify.com`.
