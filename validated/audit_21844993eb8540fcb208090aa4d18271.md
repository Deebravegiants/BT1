### Title
Missing empty-body check in `onAccept` causes an out-of-bounds panic that permanently blocks delivery of a crafted cross-chain message - ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
`ExtrinsicIntents.onAccept` (and the identical pattern in `IntentGatewayV2.onAccept`) reads `incoming.request.body[0]` to determine the `RequestKind` before any length check on `body`. Any unprivileged sender on a counterparty chain can dispatch an ISMP POST request whose `to` field targets this contract's address on the destination chain with an **empty body**. When a relayer delivers that request, `body[0]` triggers Solidity's out-of-bounds array-access panic (`Panic(0x32)`), unconditionally reverting `onAccept`. This mirrors the bug class in CVE-2019-12412: a malformed/degenerate message causes a hard crash deep in a parsing step that is reachable by any unprivileged party sending data into the protocol, rather than a clean, recoverable error.

### Finding Description
`onAccept` is the ISMP delivery entrypoint invoked by the host for every POST request whose `to` address matches this contract, regardless of who dispatched it on the source chain: [1](#0-0)

`incoming.request.body[0]` is read and cast to `RequestKind` **before** `_authenticate(incoming.request)` (source validation) is ever called. Destination routing in the ISMP model is purely address-based (`to` field), not sender-based — any account on any registered counterparty state machine can dispatch a POST request with `to = <this contract's address>` and `body = ""`. There is no upstream check anywhere in `HandlerV2.handlePostRequests` that rejects an empty body before invoking the destination module: [2](#0-1) 

The identical unguarded pattern exists in the Tron/EVM intents gateway: [3](#0-2) 

Because `body[0]` on a zero-length `bytes` value always panics in Solidity, `onAccept` for that specific request commitment can **never** succeed — the panic is deterministic and independent of relayer, batch composition, or retries.

### Impact Explanation
Once a request with `to = ExtrinsicIntents`/`IntentGatewayV2` and empty body is committed on any source chain and its consensus/membership proof becomes provable, it is a permanently undeliverable message: every attempt to deliver it via `HandlerV2.handlePostRequests` reverts on the `body[0]` panic. This satisfies the "route unable to deliver messages" impact class:
- If the module's `onAccept` call is not isolated with try/catch inside the host's `dispatchIncoming` path, the panic reverts the **entire batch transaction**, so any other legitimate requests bundled with the poisoned one in the same MMR-proof batch also fail to deliver, forcing relayers to hand-pick around the malicious commitment for as long as it remains unexpired.
- Even if the delivery call is isolated, the poisoned request itself can never be marked delivered or refunded through the normal completion path, since `onAccept` is the only entrypoint that processes it and it always panics.
This is a denial-of-service on the messaging route to this application, triggerable by any unprivileged sender able to dispatch a cross-chain message — directly analogous to the CVE's null-pointer crash from a degenerate multipart request.

### Likelihood Explanation
High. Dispatching an ISMP POST request with an arbitrary `to` and empty `body` from a counterparty chain requires no special privilege — any account able to call the standard dispatch entrypoint on any already-registered source-chain state machine can do it, and the attacker fully controls whether the destination is `ExtrinsicIntents`/`IntentGatewayV2` and whether the body is empty.

### Recommendation
Add an explicit length check at the top of `onAccept` (and the Tron `IntentGatewayV2.onAccept`) before indexing `body[0]`, e.g. `if (incoming.request.body.length == 0) revert InvalidRequestBody();`, and ensure the host's `dispatchIncoming`/module-invocation path isolates per-request delivery failures (try/catch) so a single malformed request cannot block delivery of unrelated requests in the same batch or permanently strand its own commitment without a recovery/timeout path.

### Proof of Concept
1. On a registered counterparty state machine, call the standard ISMP dispatch function with `to = <ExtrinsicIntents address on destination chain>`, `body = 0x` (empty), and any valid timeout/fee.
2. Wait for consensus finality and obtain the membership proof for the request commitment.
3. Submit `HandlerV2.handlePostRequests` (optionally batched with other legitimate requests to the same destination) with this leaf included.
4. `EvmHost` routes the request to `ExtrinsicIntents.onAccept`, which executes `RequestKind(uint8(incoming.request.body[0]))` on a zero-length `bytes` — Solidity reverts with `Panic(0x32)` (array out-of-bounds), and the request commitment remains permanently undelivered while `_authenticate`/source checks are never reached to reject it earlier.

    function handlePostRequests(IHost host, PostRequestMessage calldata request) external notFrozen(host) {
        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(request.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 requestsLen = request.requests.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](requestsLen);

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // check destination
            if (!leaf.request.dest.equals(host.host())) revert InvalidMessageDestination();
            // check time-out
            if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.request.hash());
        }

        bytes32 root = host.stateMachineCommitment(request.proof.height).overlayRoot;
        if (root == bytes32(0)) revert StateCommitmentNotFound();
        bool valid = MerkleMountainRange.VerifyProof(root, request.proof.multiproof, leaves, request.proof.leafCount);
        if (!valid) revert InvalidProof();

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // duplicate request?
            if (host.requestReceipts(leaf.request.hash()) != address(0)) revert DuplicateMessage();
            host.dispatchIncoming(leaf.request, _msgSender());
        }
    }
