Same-token batch withdrawal status collision via `findMatchingWithdrawal` first-match-by-assetId - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal` calls `findMatchingWithdrawal`, which matches an indexer entry to a withdrawal solely by `` `nep141:${w.data.near_token_id}` === assetId ``, with no use of `amount`, `address`, or `WithdrawalIdentifier.index`. When a single `MultiPayload` contains two withdrawals of the same token to different destinations, both `watchWithdrawal` calls resolve to the same first array entry, causing an integrator to receive an identical `(status, txHash)` for two distinct legs.

### Finding Description
Broken equality: `describeWithdrawal(wid_A).txHash` should equal the destination tx hash for A's specific `(amount, destinationAddress)` leg, and `describeWithdrawal(wid_B).txHash` should equal B's leg — these must differ when A and B differ in amount/address. Instead, both resolve to `withdrawals.find(w => nep141:${w.data.near_token_id} === assetId)`'s single first match [1](#0-0) .

Code path: `watchWithdrawal` (packages/intents-sdk/src/core/withdrawal-watcher.ts) polls `bridge.describeWithdrawal({...args.wid, logger})` for each `WithdrawalIdentifier` independently [2](#0-1) . `describeWithdrawal` fetches the indexer response and calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, explicitly commenting "Response list is unsorted, so we match by assetId instead of index" [3](#0-2) . The matcher's own docstring acknowledges: "multiple withdrawals of the same token in a single transaction are not supported" [4](#0-3) . A second, independent implementation of the same flawed matcher exists in `waitForWithdrawalCompletion.ts`, carrying the identical limitation and identical fix comment [5](#0-4) .

Attacker input: as an ordinary user, submit a `MultiPayload` intent whose withdrawal params include two legs of the same `assetId` (e.g., `nep141:usdc.omft.near`) with different `amount`/`destinationAddress` (index 0 → A, index 1 → B). `createWithdrawalIdentifiers` assigns per-route sequential `index` values but never threads that index into `describeWithdrawal`'s matching logic [6](#0-5) . When the PoA indexer returns two COMPLETED entries sharing `near_token_id` but differing in `amount`/`transfer_tx_hash`/`address`, `Array.prototype.find` always returns the first element in array order — regardless of which `WithdrawalIdentifier` invoked it — so both index-0 and index-1 calls receive the identical entry.

Existing guards do not catch this: there is no cross-check between `withdrawal.data.amount` and `args.withdrawalParams.amount`, no `address` comparison, and no use of `args.index`. The existing test `"matches withdrawal by assetId, not by index"` [7](#0-6)  only demonstrates disambiguation works when `assetId` differs between legs — it does not (and cannot) show correct behavior when both legs share `assetId`, confirming the gap is real and untested for the colliding-token case.

### Impact Explanation
An integrator polling both withdrawal identifiers via `watchWithdrawal`/`describeWithdrawal` will receive the same `txHash` for both A's and B's withdrawal, at least one of which is wrong. This is a status/hash misreport that leads an integrator to credit or refund a party based on the wrong (or duplicate) `transfer_tx_hash`, potentially crediting/refunding one leg twice while the other appears "complete" with someone else's proof and no further signal that it needs separate reconciliation. This matches the High-severity category ("a status or hash misreport making an integrator credit or refund twice"); under aggravated conditions (repeated batches of same-token multi-destination withdrawals) this is fully repeatable by any user constructing such a batch, since it stems purely from array ordering in the indexer response, which the caller cannot control but can trigger by shape of the withdrawal batch.

### Likelihood Explanation
Precondition: an unprivileged user must submit an intent with ≥2 withdrawal legs sharing the same `assetId` (same token, same `near_token_id`) but different destinations/amounts — a normal, permitted intent shape (e.g., splitting USDC to two recipients). No indexer collusion is required; this is the documented ordinary behavior of the POA bridge indexer returning an unsorted list. The attack costs only the price of submitting a valid multi-leg withdrawal with a repeated `assetId`, and is deterministically reproducible every time (not a race condition) because `find` always picks the same first element for both calls.

### Recommendation
Extend `findMatchingWithdrawal` (both in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` and `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`) to disambiguate among same-`assetId` candidates using `amount` (and ideally `destinationAddress`), consuming matched entries so they aren't reused across multiple calls for the same batch, as suggested in the existing code comment ("matching could be done by sorting both API results and withdrawal params by amount"). Until amount-based (or index-based, once POA API supports it) disambiguation lands, the SDK should explicitly reject/flag batches with duplicate `assetId` across legs in `createWithdrawalIdentifiers`/`supports()` rather than silently reporting ambiguous status.

function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}
