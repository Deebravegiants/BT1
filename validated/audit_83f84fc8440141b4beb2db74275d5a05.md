### Title
Withdrawal status/tx-hash misattribution in batched same-asset POA withdrawals - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal()` and the analogous `waitForWithdrawalCompletion()` helper identify which withdrawal record in a NEAR transaction belongs to a given `WithdrawalIdentifier` by matching **only on `assetId`**, not on the specific withdrawal (amount/destination/index) requested. When a single NEAR transaction contains more than one withdrawal of the same token (which the SDK's own batch withdrawal API allows), the lookup can return the wrong array element, so the SDK reports a `txHash`/status for the caller's withdrawal that actually belongs to a different withdrawal in the same batch.

### Finding Description
`findMatchingWithdrawal()` in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:418-427` selects a withdrawal from the POA API response using only:
```
return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
``` [1](#0-0) 

This is called from `describeWithdrawal()`:
```
const withdrawal = findMatchingWithdrawal(
    response.withdrawals,
    args.withdrawalParams.assetId,
);
...
if (withdrawal.status === "COMPLETED") {
    return { status: "completed", txHash: withdrawal.data.transfer_tx_hash };
}
``` [2](#0-1) 

The code comment itself acknowledges the equality is not unique:
```
// Response list is unsorted, so we match by assetId instead of index
```
and
```
NOTE: Currently only matches by assetId. This means multiple withdrawals
of the same token in a single transaction are not supported.
``` [3](#0-2) 

The equality that should hold is: *the withdrawal record returned for identifier `(tx, index)` is the same withdrawal that identifier actually refers to (same destination address, same amount)*. Instead, the code only checks `assetId` equality, so when `withdrawals.length > 1` for the same asset, `Array.find` deterministically returns the **first** matching entry regardless of which index/destination the caller asked about. Both callers of this record (`index` 0 and `index` 1, say, with different destination addresses/amounts of the same token) will resolve to the identical (first) entry.

The identical bug pattern (matching only by `assetId`, not by amount/destination) is duplicated in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts:144-153`:
```
function findMatchingWithdrawal(
    withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
    criteria: WithdrawalCriteria,
): ... {
    return withdrawals.find(
        (w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
    );
}
``` [4](#0-3) 

The SDK explicitly supports batching multiple withdrawals — potentially of the same asset to different destinations/amounts — into a single signed intent and NEAR transaction (`signAndSendWithdrawalIntent` accepts `WithdrawalParams[]`, and `sdk.ts` builds an intents array from all of them before publishing atomically):
```
public async signAndSendWithdrawalIntent(
    args: SignAndSendWithdrawalArgs<WithdrawalParams> | SignAndSendWithdrawalArgs<WithdrawalParams[]> ...
``` [5](#0-4) 
Each withdrawal in the batch gets its own `WithdrawalIdentifier` (with a distinct `index`) via `createWithdrawalIdentifier`, but `describeWithdrawal` never uses that `index` to disambiguate — it discards it and re-derives the match purely from `assetId`.

### Impact Explanation
An integrator/caller polling `describeWithdrawal` (or `waitForWithdrawalCompletion`) per-index for a batch that contains two or more withdrawals of the *same token* to *different destinations/amounts* can receive the wrong `transfer_tx_hash` and/or the wrong terminal status (`completed`/`failed`) for a given index. Concretely:
- Withdrawal A (destination X, amount 100) and Withdrawal B (destination Y, amount 200), same asset, in one tx.
- Both `describeWithdrawal({index: 0, ...})` and `describeWithdrawal({index: 1, ...})` calls resolve to the **same** underlying POA record (whichever the API happens to place first in its unsorted list).
- If an integrator credits/reconciles per-withdrawal accounting keyed by the reported `txHash`/status (a legitimate downstream use of this SDK API), this directly produces the report kind called out in the rules as material: *"a status or hash misreport making an integrator credit or refund twice."* One withdrawal can be reported "completed" (using another withdrawal's `transfer_tx_hash`) while the other withdrawal, which actually completed, is reported as still pending or with the wrong hash — an unauthorized equality break between the on-chain outcome and the reported outcome for a specific withdrawal identifier.

This does not require any relayer/bridge-operator misbehavior or malicious peer assumptions — it is a straightforward correctness bug reachable by any caller who legitimately uses the SDK's documented batch-withdrawal feature with same-asset entries, which is exactly the "unprivileged caller" trigger required by the rules.

### Likelihood Explanation
The batch withdrawal capability is a first-class, documented SDK feature (`SignAndSendWithdrawalArgs<WithdrawalParams[]>`), and there is no validation anywhere in `sdk.ts` or `poa-bridge.ts` that rejects batches containing multiple withdrawals of the same `assetId`. Any caller building a multi-destination sweep/payout batch using the same POA-bridged token (a realistic, common pattern — e.g., paying out several users in the same stablecoin) will trigger this. The bug is deterministic (not probabilistic/race-dependent): it manifests every time `withdrawals.length` for that assetId in the POA API response exceeds 1.

### Recommendation
Disambiguate withdrawal matching in `findMatchingWithdrawal` (both in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` and `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`) using more of the identifying data available on `WithdrawalIdentifier`/`WithdrawalCriteria` — e.g., match on `assetId` **and** `amount` **and** `destinationAddress` (and consume/remove matched entries so repeated same-asset entries aren't matched twice), or track consumption of already-matched withdrawal records across the batch so identical `(assetId, index)` calls cannot silently collide.

### Proof of Concept
1. Build a batch withdrawal with `signAndSendWithdrawalIntent({ withdrawalParams: [ {assetId: "nep141:usdc.omft.near", amount: 100n, destinationAddress: "X"}, {assetId: "nep141:usdc.omft.near", amount: 200n, destinationAddress: "Y"} ], ... })`.
2. After the NEAR tx settles, call `bridge.describeWithdrawal(identifierForIndex0)` and `bridge.describeWithdrawal(identifierForIndex1)` (both derived via `createWithdrawalIdentifier`, differing only by `index`).
3. Because `findMatchingWithdrawal` only filters on `` `nep141:${near_token_id}` === assetId ``, both calls return the same array element from the POA `getWithdrawalStatus` response (the first one satisfying the asset match), so both report the same `transfer_tx_hash`/status even though the two withdrawals settled independently to different destinations/hashes on-chain — reproducing the mismatch documented in the code's own "NOTE" comment.

function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
