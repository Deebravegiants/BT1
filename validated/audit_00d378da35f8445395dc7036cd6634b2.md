## Title
Webhook shop-domain header is not covered by HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates the webhook HMAC over the raw request body only. The `shop` (and `topic`, `webhook_id`, `api_version`) values are read from HTTP headers that are never part of the signed content. Since a single app `api_secret_key` is shared across every shop that installs the app, an attacker who controls one installation (their own shop) can capture a legitimately-signed webhook body/HMAC pair generated by their own store activity, then replay it to the app's webhook endpoint with the `shop-domain` header swapped to a victim shop. The signature still validates, and the forged shop value is propagated into the handler as authoritative.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is parsed from the `shopify-shop-domain` / `x-shopify-shop-domain` header independently, and is not part of that signable string: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e., it authenticates the byte content but binds nothing to the `shop` field: [3](#0-2) 

`Registry.process` passes the (unauthenticated) `request.shop` straight through to the app's handler as trusted metadata after only checking the HMAC: [4](#0-3) 

The identity binding broken is: `HMAC(raw_body, api_secret_key) valid` should imply `shop header == shop that generated raw_body`, but the gem only proves `HMAC(raw_body, api_secret_key) valid`; the `shop` header is unauthenticated and independently attacker-controlled. Because the app's `api_secret_key` is the same for all shops that install the app, any merchant/attacker who has installed the app on their own store can legitimately trigger events (e.g. `orders/create`, `app/uninstalled`, `products/update`) to obtain a raw body + valid HMAC pair signed with the shared secret, then resend that exact body/HMAC to the app's webhook endpoint while substituting the victim's shop domain in the header.

### Impact Explanation
This breaks tenant isolation (cross-tenant access): the webhook handler, and by extension the host application built on top of `ShopifyAPI::Webhooks::Registry.process`/`WebhookMetadata`, receives `shop: <victim-shop>` with a validated HMAC even though the body actually originated from the attacker's own shop. Typical webhook consumers key their side effects (session lookup, data deletion on `app/uninstalled`, order/customer record updates) off `WebhookMetadata#shop`, since the gem's own contract implies "HMAC passed ⇒ this event is authentically about `shop`." An attacker can leverage this to inject spoofed webhook payloads attributed to a victim shop domain, without any access token, without the app's `client_secret`, and without privileged access — only their own (attacker-controlled) shop installation is required.

### Likelihood Explanation
Requires only an attacker-controlled shop install of the target app (a normal, unprivileged capability), plus the ability to capture their own outgoing webhook body and replay it with a modified header to the same public webhook endpoint. No secrets, tokens, or elevated privileges are needed — this is directly reachable through the gem's own `Webhooks::Request`/`Registry` code path.

### Recommendation
Bind the identity fields to the signed content instead of trusting separate headers. Short term, either: (1) validate that the shop present in the parsed webhook body (when available) matches the header `shop`, or (2) require host applications to independently confirm the resolved `shop` corresponds to a session/shop that this specific HMAC/topic/webhook-id combination could plausibly originate from (e.g. cross-check against Shopify's webhook delivery IP allowlist or re-fetch webhook_id via the Admin API before trusting `shop`). Longer term, document explicitly in `Webhooks::Request`/`Registry` that `shop` is not authenticated by HMAC and must not be used as a sole tenant-scoping key without additional verification, and consider incorporating shop/topic/webhook-id into the signable string contract if/when Shopify's webhook signing scheme supports it.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Attacker triggers a webhook-generating action on their store (e.g., updates a product), causing Shopify to POST a body `B` to the app's webhook endpoint with header `x-shopify-shop-domain: attacker.myshopify.com` and a valid `x-shopify-hmac-sha256` computed over `B` using the app's shared `api_secret_key`.
3. Attacker captures `B` and the HMAC value (e.g., via a proxy they control, or by replaying their own already-delivered webhook, which they are fully entitled to observe).
4. Attacker resends the exact same raw body `B` and HMAC to the app's public webhook endpoint but changes the `x-shopify-shop-domain` header to `victim-shop.myshopify.com`.
5. `Webhooks::Request.new` parses this into an object whose `hmac` validates successfully via `HmacValidator.validate`, because `to_signable_string` only covers `B`, not the shop header.
6. `Registry.process` invokes the app's handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, causing the host application to act on victim-shop data/session using attacker-supplied body content.
