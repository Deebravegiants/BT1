### Title
EIP712 signature over `EmporiumOperation`s does not bind `feeStructure.feeToken`, allowing a relay/caller to redirect wallet `flatFee` payment into an arbitrary ERC20 - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.verifyWallet()` validates the signer's EIP712 signature over `emporiumMessage`, the hash of `stack.ops`, `stack.maxFee`, and `stack.deadline`, and only bounds the fee numerically (`flatFee <= maxFee`). It never binds the *token* in which the fee is actually paid. Since `circomData` (including `feeStructure.feeToken` and `erc20TokenAddresses`) is supplied by the caller/relay invoking `Hinkal.transact`, not by the signer, the fee-token selection is entirely unauthenticated. This lets a relay redirect the wallet's `doSendToRelay` fee payment into any token present in `circomData.erc20TokenAddresses`, at up to `maxFee` raw units — a value the signer only intended for one specific token's decimals/price.

### Finding Description
`verifyWallet` computes the signed digest as: [1](#0-0) 

This EIP712 payload (`EMPORIUM_SIGNATURE_TYPEHASH`) only commits to `circomData.emporiumMessage`, the hash of `stack.ops`, `stack.maxFee`, and `stack.deadline`: [2](#0-1) 

The only fee-related check performed against the signature is a numeric ceiling: [3](#0-2) 

However, `feeStructure` (including `feeToken`) and `erc20TokenAddresses` are part of `circomData`, which is built and submitted by whoever calls `Hinkal.transact` (the relay/caller), not by the wallet signer. `payRelayFees` then picks whichever `erc20TokenAddresses[i]` equals `feeStructure.feeToken` (with a negative `deltaAmountChanges[i]`) as the fee token and pulls `flatFee` units of it directly from the signer's wallet: [4](#0-3) 

`sendToRelayFromWallet` invokes `IHinkalWallet(signerAddress).doSendToRelay(...)`, which the wallet executes unconditionally for any `erc20TokenAddress` as long as the caller is the registered Emporium contract (`onlyEmporium`), with no further validation of which token or why: [5](#0-4) 

Because `feeStructure.feeToken` is outside the equality the signer actually signs (`EMPORIUM_SIGNATURE_TYPEHASH`), and only the numeric `maxFee` bound is enforced, the relay can freely choose *which* token the wallet pays `flatFee` in — as long as that token appears in `erc20TokenAddresses` with a negative delta for that transaction (a value also fully controlled by the transaction builder/relay, independent of the signed `ops`). This breaks the intended equality "amount debited from wallet as fee == amount the signer explicitly authorized for a specific token," since the signer's authorization is token-agnostic while the actual debit is token-specific and attacker-selected.

### Impact Explanation
This is unauthorized asset movement from a user's `HinkalWallet` that the wallet owner/signer never approved for that specific asset. A relay can set `feeStructure.feeToken` to a high-value token (e.g. WBTC) instead of the token the user intended (e.g. USDC), and drain up to `maxFee` raw units of that high-value token from the wallet via `doSendToRelay`, causing real economic loss disproportionate to what the signature authorized. This matches the "High — theft ... of protocol/relay fees" / "moving assets a wallet owner or prover never authorised" criterion.

### Likelihood Explanation
Exploitation requires only that the party submitting the `Hinkal.transact()` call (a relay or any caller building `circomData`, which is unprivileged and untrusted per the trust model) chooses a `feeStructure.feeToken` different from what the user intended and includes that token in `erc20TokenAddresses` with a qualifying negative delta. No special privileges, admin/owner/relay-whitelist bypass, or race condition are required beyond normal relay operation flow — it's a natural consequence of the missing binding in the EIP712 payload. This makes it moderately likely in an adversarial-relay setting, which the protocol explicitly must defend against (nullifier/root/calldataHash checks exist precisely to prevent an untrusted relay from tampering with `circomData`).

### Recommendation
Include `feeStructure` (at minimum `feeToken` and `flatFee`, or the whole struct) inside the EIP712 typed struct that `stack.signerAddress` signs (`EMPORIUM_SIGNATURE_TYPEHASH`), so any change to the fee token invalidates the signature. Alternatively, restrict `payRelayFees`'s wallet-fee token strictly to a token explicitly whitelisted/signed by the wallet owner rather than inferring it opportunistically from `erc20TokenAddresses`.

### Proof of Concept
1. User signs an `EmporiumSignature` off-chain authorizing `ops`, `maxFee = 1e18`, `deadline`, intending fee to be paid in USDC (6 decimals, so 1e18 wei would be an absurd amount of USDC — assume a more realistic example: user intends `maxFee` denominated for USDC with 6 decimals, e.g., `maxFee = 5_000_000` = 5 USDC).
2. A malicious relay builds `circomData` for the same `emporiumMessage`/`ops`/`maxFee`/`deadline` (so the signature over `EMPORIUM_SIGNATURE_TYPEHASH` still verifies), but sets `feeStructure.feeToken = WBTC` and includes `WBTC` in `circomData.erc20TokenAddresses` with a negative `amountChanges` entry (satisfying `deltaAmountChanges[i] < 0`), and `feeStructure.flatFee = 5_000_000` (still `<= maxFee`, so `FeeExceedsSignedMax` does not revert).
3. `verifyWallet` passes (signature and numeric bound are satisfied — no field ties fee amount to a specific token/decimals).
4. `payRelayFees` calls `sendToRelayFromWallet(relay, signerAddress, 5_000_000, WBTC)`, and `HinkalWallet.doSendToRelay` (gated only by `onlyEmporium`) transfers `5_000_000` units (i.e., 0.05 WBTC, worth thousands of dollars) instead of 5 USDC (a few dollars) from the user's wallet to the relay.
5. The user's wallet loses far more value than authorized, in a token they never approved for fee payment.
