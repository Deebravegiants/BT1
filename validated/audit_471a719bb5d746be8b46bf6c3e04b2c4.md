### Title
Webhook `shop-domain` header is trusted for tenant identity without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `Utils::HmacValidator.validate` in `Registry.process` only proves that the *body bytes* were signed with `api_secret_key`; it proves nothing about the `shop`, `topic`, `webhook_id`, or `api_version` headers [2](#0-1) . Yet `request.shop`, read straight from the `X-Shopify-Shop-Domain`/`Shopify-Shop-Domain` header [3](#0-2) , is handed to the handler as the trusted tenant identity via `WebhookMetadata.new(... shop: request.shop ...)` [2](#0-1) . The gem's own documentation instructs host apps to use `data.shop` directly to key their per-tenant logic (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), treating it as an authenticated field [4](#0-3) [5](#0-4) .

This breaks the required binding: `HMAC-verified(bytes)` should equal `bytes acted on for tenant identity`, but here `HMAC-verified(raw_body) ≠ shop used for tenant routing`.

### Finding Description
The equality that should hold is:
```
verified(raw_body) == identity_used_for_dispatch(shop header)
```
but the implementation only verifies `raw_body` against `hmac-sha256` [6](#0-5) [7](#0-6) , while `shop`, `topic`, `webhook_id`, and `api_version` are parsed from unauthenticated headers and passed through unchanged [8](#0-7) .

Any unprivileged internet user who controls a legitimate shop that has this app installed can capture one real webhook delivery for their own shop (a valid `raw_body` + `hmac-sha256` pair, e.g. for `orders/create` with a low-information body, or `app/uninstalled` with an empty `{}` body). They can then replay that exact `raw_body`/HMAC pair to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header for a victim shop. Because the shop header is never part of `to_signable_string`, `Utils::HmacValidator.validate` still returns `true`, and `Registry.process` will dispatch the handler with `data.shop` set to the attacker-chosen victim domain [2](#0-1) .

### Impact Explanation
For topics whose body carries little or no shop-identifying content (e.g. `app/uninstalled`, `shop/redact`, or any topic where the fields sent match another store, since `fields` filtering can reduce the body to near nothing per `docs/usage/webhooks.md`), this lets an attacker forge webhook events attributed to a shop they don't operate. If a host app's handler uses `data.shop` to look up per-tenant records, revoke installs, delete data, or otherwise act (as the gem's own example handler does), this becomes a cross-tenant data-integrity/authentication issue: an outsider can trigger app-side state changes scoped to a victim shop's session/tenant record without ever possessing that shop's credentials. This matches the "Critical: cross-tenant access" impact category, contingent on how the host app's handler consumes `data.shop`.

### Likelihood Explanation
Requires the attacker to have — or briefly install — the app on any single shop to capture one legitimate `(raw_body, hmac)` pair for a topic with an identity-independent body, then replay that pair with a spoofed shop header to the app's public webhook endpoint. This needs no credentials belonging to the victim shop and no access to `api_secret_key`; it is exploitable by any unprivileged actor able to install/uninstall an app on a store they control and send one crafted HTTP request. Likelihood is Medium-High for topics with generic/empty bodies, lower for topics whose body content is shop-specific enough to be self-limiting.

### Recommendation
Include the shop domain (and ideally topic/webhook_id) in the HMAC-signed material, or independently bind the header value to the verified payload before trusting it — e.g. verify that `shop` is present as an authenticated claim rather than a raw unauthenticated header, similar to how `to_signable_string` should cover every field that is subsequently acted upon. At minimum, document that host applications must not treat `data.shop` as authenticated unless it is cross-checked against server-side state (e.g. a shop the app is confirmed to be currently installed on).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and registers for a topic with a low-information body (e.g. `app/uninstalled`, body `{}`).
2. Attacker uninstalls the app, triggering Shopify to send a legitimate webhook: `raw_body = "{}"`, `X-Shopify-Hmac-Sha256 = HMAC(api_secret_key, "{}")`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures this exact request (they control the endpoint's network path or run their own receiving proxy) and resends it to the app's public webhook route, replacing only the `X-Shopify-Shop-Domain` header with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC solely over `raw_body = "{}"` and succeeds because the body/HMAC pair is unchanged [9](#0-8) .
5. The handler is invoked with `WebhookMetadata` where `shop == "victim-shop.myshopify.com"`, even though Shopify never sent this event for that shop [10](#0-9) .

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
