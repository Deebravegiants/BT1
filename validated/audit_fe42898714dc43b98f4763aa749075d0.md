### Title
Webhook shop-domain identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook's authenticity using `Utils::HmacValidator.validate`, but the HMAC only covers the raw request body. The `shop` (and `topic`/`webhook_id`) values that identify *which tenant* the webhook belongs to are taken from HTTP headers that are never included in the signed payload, so an attacker who can produce (or replay) any validly-signed body can attach an arbitrary shop domain to it.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors read directly from headers, with no cryptographic binding to the signed content: [2](#0-1) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` (i.e., just the body) using the single, app-wide `Context.api_secret_key`, which is shared across every shop that has this app installed: [3](#0-2) 

`Registry.process` checks only this body-HMAC and then immediately forwards the *unauthenticated* `request.shop` value to the app's handler as the tenant identity: [4](#0-3) 

Because the HMAC secret (`api_secret_key`) is identical for all shops using the app, any merchant who installs the app can capture a legitimately-signed webhook delivered to their own store (or produce one with a known/empty body such as `"{}"`) and replay it to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop. `HmacValidator.validate` will still pass, because it only checks that the body matches the shared secret — it says nothing about which shop the body was really sent for. The gem then hands this forged `shop` value straight to `WebhookMetadata` and the app's handler as trusted tenant data.

This is the "field acted on but not covered by the HMAC" class of bug: the identity used to route/act on the webhook (`shop`) is disjoint from the identity actually verified by the signature (only the body bytes, under a secret shared across tenants).

### Impact Explanation
This breaks the equality "shop verified by the signature" == "shop the handler acts on." An unprivileged user who has installed the app on any shop (no special privileges needed beyond a normal, self-service app install) can craft webhook deliveries that the gem reports as validly signed while presenting an arbitrary victim shop domain. Any consuming app that trusts `WebhookMetadata#shop` (as the library's own API is designed to be used) for tenant-scoped operations (e.g., looking up a stored session/access token for that shop, updating shop-specific records, or triggering shop-scoped GDPR/data actions) can be tricked into acting as if the event came from a different, unrelated merchant — i.e., cross-tenant access via a forged event, which is one of the qualifying "Critical - cross-tenant access" outcomes.

### Likelihood Explanation
Requires only a functioning app installation, which is available to any unprivileged internet user who installs the target app, plus the ability to POST directly to the app's public webhook endpoint with attacker-controlled headers (webhook endpoints are ordinary public HTTP endpoints). No access token, `api_secret_key`, or privileged account is needed — the attacker only needs one legitimately-signed body (trivial for constant/empty bodies) and can freely vary the `shop` header.

### Recommendation
Include the shop domain (and ideally topic/webhook id) as part of the signed material, or independently authenticate the shop by cross-referencing it against the app's own installed-shop records (e.g., verify a session exists for `request.shop`) before invoking the handler, rather than trusting the header value once the body-only HMAC passes. At minimum, document prominently in `WebhookMetadata`/`Registry.process` that `shop` is unauthenticated and must be independently verified by the consuming application before being used for tenant-scoped actions.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and receives a real webhook delivery with body `{}` and headers:
   - `X-Shopify-Hmac-Sha256: <valid HMAC of "{}" under the app's shared api_secret_key>`
   - `X-Shopify-Shop-Domain: attacker.myshopify.com`
2. Attacker resends the identical body and HMAC header to the app's public webhook endpoint, changing only:
   - `X-Shopify-Shop-Domain: victim.myshopify.com`
3. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-199`) calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the body against the shared secret.
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` even though the request never touched Shopify for that shop, demonstrating that the shop identity is not bound to the signature.
