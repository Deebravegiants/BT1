This confirms the vulnerability. The gem's docs explicitly claim `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" [1](#0-0) , and the handler is documented to trust `data.shop` as "The shop domain of the webhook" [2](#0-1) . But the HMAC signature only ever covers the raw body, never the shop/topic/webhook_id headers.

### Title
Webhook `shop`, `topic`, and `webhook_id` are trusted from unauthenticated headers while the HMAC only covers the request body, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `hmac` and `to_signable_string` solely from the raw HTTP body, while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from HTTP headers that are never included in the signed content. `ShopifyAPI::Webhooks::Registry.process` validates only the body HMAC and then dispatches the handler using these unauthenticated header values, letting any party who can produce a validly-signed body (e.g., a legitimate app installer receiving genuine webhooks for their own shop) replay that exact body with a forged `shop-domain` header to impersonate a different tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [3](#0-2) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from HTTP headers with no cryptographic binding to the signature: [4](#0-3) 

`Utils::HmacValidator.validate` computes the signature exclusively from `verifiable_query.to_signable_string` (i.e., the raw body) and compares it against the `hmac` header: [5](#0-4) 

`Registry.process` checks only this body HMAC, then immediately builds `WebhookMetadata` using `request.shop`, `request.topic`, and `request.webhook_id` — none of which were validated — and passes it to the app's handler: [6](#0-5) 

The identity binding that should hold is: `shop-header == shop-covered-by-hmac`. In reality, only `body == hmac-signed-bytes` is enforced; the `shop-domain` header is completely outside the signed envelope. Because the webhook signing secret (`Context.api_secret_key`, the app's `client_secret`) is a single shared secret used for every shop that has the app installed — not per-shop — any unprivileged internet user can install the target app on their own store, capture a genuine, validly-HMAC-signed webhook body that Shopify sends them, and replay that exact `(body, hmac)` pair to the app's public webhook endpoint while substituting `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) with a victim shop's domain. `HmacValidator.validate` still succeeds because the body and hmac are untouched and were computed with the correct (shared) secret, so `Registry.process` invokes the app's handler believing the payload originated from the victim tenant.

### Impact Explanation
This breaks the tenant isolation the whole webhook processing model relies on. Any app that uses `request.shop` to select which tenant's database/records to update, credit, or refund (a documented and expected usage per the gem's own webhook docs) can be made to apply attacker-controlled data to a shop the attacker doesn't control, since `data.shop` is documented as reliable ("The shop domain of the webhook") yet is never authenticated. This is cross-tenant access/data injection achieved without any credential belonging to the victim or the app — only requiring the attacker to install the app on any shop they control.

### Likelihood Explanation
Likelihood is high: the attacker only needs to be able to install the target app on a shop they own (a normal, unprivileged action available to any merchant) and send one crafted HTTP request to the app's public webhook route. No access token, `client_secret`, or victim credentials are needed, and the shared-secret nature of webhook signing across all shops for a given app is inherent to Shopify's signing scheme as implemented here.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, or otherwise cross-check the header-derived `shop` against an authenticated identifier before dispatching to the handler — e.g., require the caller to supply and verify the expected shop (already known from the registration/session) rather than trusting `X-Shopify-Shop-Domain` unconditionally. At minimum, document prominently that `data.shop` is not authenticated by the HMAC check and that consuming apps must independently verify shop ownership/subscription (e.g., against their own webhook subscription records) before trusting it for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and subscribes to a webhook topic the app cares about (e.g., `orders/create`).
2. Shopify sends the attacker a legitimate webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the app's shared secret), and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker resends the exact same request to the app's public webhook endpoint, keeping body `B` and header `H` unchanged, but replacing `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` whose `to_signable_string` is still `B`; `Utils::HmacValidator.validate` recomputes the HMAC over `B` and it matches `H`, so validation passes.
5. `Registry.process` calls the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: parsed(B), ...)`, i.e., the app processes attacker-supplied data as if it belongs to `victim-shop.myshopify.com`.
