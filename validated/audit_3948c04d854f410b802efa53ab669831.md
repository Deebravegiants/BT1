### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by HMAC-validating the raw request body, then hands the handler an unauthenticated `shop` value taken straight from the `shopify-shop-domain` HTTP header. Because the header is never part of the signed material, any request bearing a valid `(body, hmac)` pair - trivially obtainable by installing the (public) app on an attacker-owned store - can be replayed with an arbitrary victim shop domain in the header and will still pass validation, letting the attacker attribute forged webhook content to any other tenant of the app.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` values are all read from unauthenticated headers instead: [2](#0-1) 

`HmacValidator.validate` computes and compares the HMAC only over `verifiable_query.to_signable_string` (i.e. the raw body) using the app's shared `api_secret_key`: [3](#0-2) 

`Registry.process` treats a passing HMAC check as full authentication, then constructs `WebhookMetadata` using the header-derived, unauthenticated `request.shop`: [4](#0-3) 

The equality the code is supposed to enforce is: `shop_header == shop_that_the_HMAC_was_computed_for`. Instead the implementation only enforces `hmac(raw_body, api_secret_key) == received_hmac`, which is independent of the `shop` header entirely. Since the `api_secret_key` is shared across every installation of the app (it is not per-shop), a `(raw_body, hmac)` pair that is valid for one shop is valid for the same body on **every** shop. The gem's own documentation confirms that `data.shop` is meant to be trusted as "the shop domain of the webhook" and used directly by host applications (e.g., to attribute a job to a shop): [5](#0-4) 

### Impact Explanation
This breaks the tenant boundary the HMAC check is supposed to guarantee. An attacker who is an ordinary, unprivileged internet user can install the target public app on their own store (no special privilege needed) and thereby receive genuine, correctly-signed webhooks from Shopify for their own body content. By replaying that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with any victim shop's domain, `Registry.process` will accept the request as valid and invoke the host's handler with `data.shop` set to the victim shop and `data.body` set to attacker-chosen content. Any host application that follows the documented usage pattern (persisting/acting on `data.shop` + `data.body` as a unit) will store or act on forged data attributed to a different tenant - a cross-tenant data-integrity/confusion vulnerability.

### Likelihood Explanation
The `api_secret_key` is shared across all shops using a given app, so no theft of any shop-specific secret is required. The only prerequisites are: (1) the app is public/installable by anyone, and (2) the attacker installs it once on their own store to harvest a valid `(topic, raw_body, hmac)` triple, then replays it against the app's public webhook endpoint with a forged shop header. This requires no access token, no `api_secret_key` leakage, and no privileged account - only normal, self-service app installation, making it readily reachable by an unprivileged internet user.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) to the authenticated material, e.g. by including them in the signed payload verification, or at minimum by requiring the caller to independently confirm that `request.shop` corresponds to a shop with an active, known installation/session before trusting it, and document this requirement clearly. Shopify's own recommended webhook verification could additionally deliver a per-shop signing context so that a signature from one shop cannot be replayed as another.

### Proof of Concept
1. Attacker installs the public app on `attacker-shop.myshopify.com`, triggering a real webhook, e.g. `orders/create`, from Shopify to the app's callback URL. Attacker captures the exact raw body `B` and the header `x-shopify-hmac-sha256: H` (valid because `H = HMAC-SHA256(api_secret_key, B)`).
2. Attacker crafts a new HTTP request to the same app callback URL with:
   - Body: `B` (unchanged, so `H` remains valid)
   - Header `x-shopify-hmac-sha256: H` (unchanged)
   - Header `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
   - Header `x-shopify-topic: orders/create`
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed by the host controller exactly as documented, and passed to `ShopifyAPI::Webhooks::Registry.process`.
4. `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(api_secret_key, B)`, which equals `H`, so validation succeeds despite the shop header being forged.
5. The registered handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing attacker-controlled content to be processed/stored as if it originated from `victim-shop.myshopify.com`.
