## Analog Found

### Title
Escrowed input tokens become permanently frozen if the fill beneficiary (filler) or refund beneficiary (order user) is blacklisted by a compliant ERC20 (e.g. USDC) - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentsBase._withdraw` (and the equivalent `IntentGatewayV2.withdraw` on the Tron variant) transfers escrowed order tokens directly to a hardcoded `beneficiary` address decoded from the cross-chain `WithdrawalRequest` body via `IERC20(token).safeTransfer(beneficiary, amount)`. That beneficiary is fixed at order-fill/cancel time and baked into an already-dispatched ISMP message — there is no way to redirect it, mirroring the `recoverERC20`/`recipient()` pattern flagged in the source report, but here applied to the escrow settlement path itself rather than an admin-recovery utility.

### Finding Description
On a cross-chain fill, `ExtrinsicIntents.fillOrder` embeds the solver's own address as the beneficiary of the `RedeemEscrow` message dispatched back to the source chain: [1](#0-0) 

When that message is delivered on the source chain, `onAccept` decodes the `WithdrawalRequest` and calls `_withdraw`, which unconditionally pushes tokens to `beneficiary` with `safeTransfer`: [2](#0-1) 

The same fixed-beneficiary pattern applies to `RefundEscrow` on cancellation, where the beneficiary is `order.user`: [3](#0-2) 

If USDC (or any blacklist-capable ERC20) is used as an input token and the filler's (or user's) address gets blacklisted between order placement/fill and settlement, `safeTransfer` inside `_withdraw` reverts. `EvmHost.dispatchIncoming` treats this as a normal delivery failure: it deletes the request receipt and returns without reverting the batch, explicitly "so that it can be retried": [4](#0-3) 

The intent, per the host's design, is that failures like this are transient and a later retry with different execution conditions would succeed. But the beneficiary address here is not a runtime parameter of the retry — it is embedded in the previously-signed/dispatched message body (`WithdrawalRequest.beneficiary`), which cannot be altered by anyone. Every retry replays the identical `safeTransfer(beneficiary, amount)` and reverts identically. There is no `onlyRecipient`-style escape hatch, no alternate beneficiary parameter, and no admin/governance sweep for these specific escrowed order funds (the `SweepDust` action only sweeps protocol fee "dust," not user/solver escrow).

### Impact Explanation
The escrowed input tokens for that specific order (already reserved in `_orders[commitment][token]`) become permanently locked in the `IntentGateway`/`ExtrinsicIntents` contract:
- A filler who has already delivered output tokens to the user on the destination chain can never redeem the escrowed input tokens if their receiving address is later blacklisted.
- A user who cancels an order can never recover their escrow if their own address is blacklisted.

This is a concrete permanent freezing of funds triggered by an external, unprivileged condition (a compliant stablecoin issuer blacklisting an address), reachable from the ordinary intents fill/cancel flow available to any solver or user — no privileged actor is required.

### Likelihood Explanation
Any solver interacting with USDC-denominated orders is at risk the moment their receiving address is blacklisted by the issuer for any reason (their own or unrelated compliance action) before the cross-chain settlement message lands. Given USDC is explicitly one of the protocol's supported tokens and the Intent Gateway is a core, permissionless, unprivileged user-facing flow, this is a realistically reachable condition, not a contrived edge case.

### Recommendation
Do not let a single failed transfer to a fixed beneficiary permanently block escrow release. Options:
- Allow the beneficiary (or a delegate they control) to supply an alternate receiving address for the escrowed funds when the original transfer fails, similar to adding an `onlyRecipient`-gated redirect parameter as recommended in the source report.
- On `safeTransfer` failure inside `_withdraw`, fall back to an internal "credit" balance the beneficiary (or a substitute address they control) can claim later via a separate `claim(address to)` function, rather than reverting the whole settlement and relying on futile retries.
- Alternatively, expose a governance/timelocked rescue path scoped specifically to stuck per-order escrow (not just protocol dust) that can redirect funds to a user-approved address after some grace period.

### Proof of Concept
1. User places a cross-chain order escrowing USDC as input, on the Intent Gateway (`evm/src/apps/intentsv2/ExtrinsicIntents.sol`).
2. Solver `S` fills the order on the destination chain via `fillOrder`, delivering output tokens to the user; the contract dispatches `RedeemEscrow` with `beneficiary = S` back to the source chain (`ExtrinsicIntents.sol:207-212`).
3. Before the `RedeemEscrow` message is delivered/relayed, Circle blacklists `S`'s address in USDC.
4. A relayer delivers the message; `EvmHost.dispatchIncoming` calls `onAccept` → `_withdraw`, which calls `IERC20(usdc).safeTransfer(S, amount)`; USDC's `transfer` reverts because `S` is blacklisted.
5. `dispatchIncoming` catches the failure, deletes the receipt, and returns normally — the message is nominally "retryable" (`evm/src/core/EvmHost.sol:809-816`), but every retry replays the same fixed `beneficiary = S` and reverts identically forever.
6. The escrowed USDC recorded in `_orders[commitment][usdc]` is now permanently unreachable — `S` cannot claim it (already delivered output for nothing) and no other party can redirect or reclaim it.

```text
    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
```
