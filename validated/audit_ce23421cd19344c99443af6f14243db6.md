## Title
Webhook shop identity (and topic) not covered by the HMAC signature enables cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented to "verify the request did indeed come from Shopify" before invoking the app's webhook handler, but the HMAC signature computed by `Utils::HmacValidator` only covers the raw request body, not the `shop-domain` (or `topic`/`webhook-id`) header. Any actor who can obtain one genuinely-signed webhook body/HMAC pair (e.g., by installing the target app on their own store) can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header, and the gem will report it as a validated Shopify webhook for that arbitrary shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from unauthenticated headers: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the HMAC solely against `verifiable_query.to_signable_string`, i.e., the body: [3](#0-2) 

`Registry.process` uses this validation as its sole authenticity gate, then dispatches the handler using the (unauthenticated) `request.shop`: [4](#0-3) 

The documented contract explicitly promises full request authenticity ("This will verify the request did indeed come from Shopify") and instructs apps to key their per-tenant work off `data.shop`: [5](#0-4) [6](#0-5) 

**Identity binding broken (equality that should hold but doesn't):**
`shop_header_value == shop_that_produced_the_signed_body`

Before the attack: for a legitimate webhook, both sides are the same shop, so the equality trivially holds.
After the attack: the attacker keeps the body/HMAC pair genuinely produced for their own shop (`attacker-shop.myshopify.com`) but sets `shop_header_value = "victim-shop.myshopify.com"`. `HmacValidator.validate` still returns `true` because it never inspects the header, so `Registry.process` proceeds and calls the handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"` even though the signed content actually originated from the attacker's own shop.

### Impact Explanation
This breaks the tenant-identity boundary the gem is supposed to enforce for webhook processing. Any app that follows the documented pattern of using `data.shop` to route/attribute webhook data to a specific merchant (as shown in the gem's own usage doc) can be made to process attacker-controlled data as if it originated from an arbitrary victim shop, since `Registry.process`'s "HMAC validated" guarantee does not actually bind the shop (or topic) to the signed bytes. This is a cross-tenant data-injection/spoofing primitive that satisfies the "cross-tenant access" impact category, achievable by an unprivileged actor who only needs to install the target public app on their own store (a normal, unprivileged action) to obtain one valid signed webhook.

### Likelihood Explanation
Any Shopify Partner/developer can install a public app onto a free development or trial store, receive a real webhook to their own endpoint (or a controlled proxy), and then replay the intercepted request body/HMAC to the app's public webhook URL with a modified `X-Shopify-Shop-Domain` header. No secrets, tokens, or privileged access are required beyond normal app installation, and the gem itself performs no additional check tying the header to the signed payload.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signed material verified by `HmacValidator`, or otherwise cryptographically/logically bind `request.shop` to the entity that produced the HMAC (e.g., cross-check against the shop associated with the specific webhook subscription/session that was registered, rather than trusting the header value at face value). At minimum, the documentation's claim that `process` "will verify the request did indeed come from Shopify" should be scoped explicitly to body integrity only, and callers should be warned not to trust `data.shop` for tenant attribution without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and registers a webhook (e.g., `orders/create`).
2. Shopify delivers a webhook to the app's endpoint with headers `X-Shopify-Hmac-Sha256: <hmac-of-body>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, and a JSON body.
3. Attacker captures this raw HTTP request (they control the receiving proxy/endpoint since it is their own store/app installation).
4. Attacker resends the identical body and `X-Shopify-Hmac-Sha256` value to the app's public webhook endpoint, but replaces the header with `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses this normally, `HmacValidator.validate` returns `true` (it only checks the body), and `Registry.process` invokes the app's handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, causing the app to process attacker-controlled data attributed to a shop the attacker does not control.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
