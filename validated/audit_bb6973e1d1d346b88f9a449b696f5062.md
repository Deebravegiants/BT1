### Title
Unbounded Token Pull in `ExternalActionSwap`/`LifiExternalAction` Allows Theft of Residual Balances - (File: `contracts/external-actions/swaps/ExternalActionSwap.sol`, `contracts/external-actions/swaps/LifiExternalAction.sol`)

### Summary
`ExternalActionSwap.swap()` computes `inputAmount` from the proven `deltaAmounts[0]` [1](#0-0)  and forwards it to `callRouter`, but `LifiExternalAction.callRouter` never uses `inputAmount` to bound what the router actually pulls from the contract — it just measures `swappedAmount` as the output-token balance delta after an opaque `router.call(externalActionMetadata)` [2](#0-1) . The router holds an unlimited `approve` on the input token from `approveUnlimited` [3](#0-2) [4](#0-3) , so the amount actually pulled is dictated entirely by the off-chain-built `externalActionMetadata`, not by the committed `inputAmount`.

### Finding Description
This mirrors the reported bug class: a contract that "shouldn't hold any tokens" ends up holding leftover balance after an external-liquidity/swap operation, and that leftover is not accounted for or refunded, letting a later, unrelated caller sweep it.

In `ExternalActionSwap.swap()`, Hinkal transfers exactly `uint256(-deltaAmountChanges[i])` of the input token to the `ExternalActionSwap` contract before `runAction` is invoked [5](#0-4) . Inside `swap()`, `inputAmount` is derived from this committed delta [1](#0-0) , but it is only used for optional fee subtraction — it is never enforced against what the router actually consumes. `callRouter` for LI.FI simply calls the router with attacker/user-supplied calldata and measures `swappedAmount` purely from the output-token balance diff [6](#0-5) . There is no `require` anywhere verifying `getERC20OrETHBalance(inputToken)` decreased by exactly `inputAmount`.

Because the router has unlimited approval over `ExternalActionSwap`'s entire balance of the input token, any residual/leftover balance of that token sitting in the contract (from dust left by earlier swaps that under-consumed their committed `inputAmount`, rounding, partial fills, or stray transfers) is fully spendable by any subsequent `transact()` call whose `externalActionMetadata` instructs the router to pull more than that caller's own committed `inputAmount`. Hinkal's top-level balance equation only checks Hinkal's own balance changes against `circomData.amountChanges` [7](#0-6) ; it has no visibility into, or constraint on, what happens to funds once they leave Hinkal and sit inside `ExternalActionSwap`.

`externalActionMetadata` is part of the `calldataHash` commitment [8](#0-7) , so it is authorized in the sense that it matches what the caller's own proof commits to — but that only proves the *caller* authorized the router calldata, not that the router calldata is limited to that caller's committed `inputAmount`. The mismatch between the "amount proven/committed" (`amountChanges`/`inputAmount`) and "amount actually movable by the router" (unbounded, governed by unlimited approval + arbitrary calldata) is the root cause, structurally identical to the Ramses report's mismatch between "balance transferred to the adapter" and "amount actually consumed by `_addLiquidity`."

### Impact Explanation
Any ERC20 balance stranded in `ExternalActionSwap` — e.g., dust from a legitimate user's swap where the router doesn't consume 100% of the transferred `inputAmount`, or from rounding/slippage in LI.FI execution — becomes permanently exposed to theft by any subsequent caller who crafts `externalActionMetadata` requesting a larger pull than their own committed amount. This is direct, unauthorized theft of another user's leftover shielded-swap input funds (or of protocol dust), satisfying the "theft of user funds / unauthorized asset movement" criterion (Critical/High).

### Likelihood Explanation
Likelihood depends on residual balance actually accumulating in `ExternalActionSwap` (e.g., LI.FI routes that don't fully consume `inputAmount`, native-ETH refunds not swept, or failed sub-swaps leaving dust) — this is plausible given aggregator behavior (partial fills, rounding) but not guaranteed on every call. Once any such residue exists, exploitation requires only a normal, unprivileged `transact()` call with attacker-controlled `externalActionMetadata`; no special privileges are required.

### Recommendation
Enforce that the input-token balance change measured inside `callRouter` equals (not merely is bounded by) the committed `inputAmount`, e.g., record `getERC20OrETHBalance(inputToken)` before and after the router call and `require` the decrease equals `inputAmount`. Refund/sweep any unspent input-token balance back to `msg.sender` (Hinkal) after the swap so no value can ever accumulate in `ExternalActionSwap`, analogous to the recommended Ramses fix of refunding remaining balances after liquidity addition.

### Proof of Concept
1. User A calls `transact()` with `externalActionId` pointing at `LifiExternalAction`, `amountChanges[0] = -1000` USDC. Hinkal transfers 1000 USDC to `ExternalActionSwap`.
2. User A's `externalActionMetadata` calls the LI.FI router, but due to slippage/partial-fill behavior the router only pulls 990 USDC via its `approveUnlimited` allowance; 10 USDC remains stranded in `ExternalActionSwap`. `swap()` doesn't detect or refund this since it only measures output-token delta.
3. Attacker B (or A themselves in a later tx) calls `transact()` with a real but tiny `amountChanges[0] = -1` USDC (proven/committed correctly), but supplies `externalActionMetadata` whose router calldata pulls 11 USDC from `ExternalActionSwap` (1 from what Hinkal just transferred + the 10 USDC stranded dust) via the unlimited approval.
4. `callRouter` measures `swappedAmount` purely from the output-token balance increase (reflecting the full 11 USDC swapped), which is forwarded entirely to attacker B as their UTXO output. Hinkal's balance equation only validates that Hinkal's own balance dropped by 1 USDC as committed — it never detects that `ExternalActionSwap` gave away 11 USDC worth of value.
5. Attacker B has stolen the 10 USDC of residual/dust value belonging to no one but sitting unclaimed due to the missing balance-conservation check inside the swap external action.

    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
