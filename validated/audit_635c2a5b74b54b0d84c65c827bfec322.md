### Title
`withdraw()` in the Tron `IntentGatewayV2` trusts a low-level `call()` success flag instead of the ERC20 return value, permanently freezing user escrow on transfer failure - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2` releases escrowed tokens with a raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only checks the low-level `success` boolean, never decoding/validating the ERC20 `bool` return value. This mirrors the root cause of the referenced Foundation finding: code treats "the external call did not revert" as proof that the operation actually completed, when a non-reverting call can still signal failure (a `false` return, or no return data handled incorrectly) without reverting.

### Finding Description
`withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` finalizes escrow settlement for both `RedeemEscrow` (solver payout) and `RefundEscrow` (user refund) flows: [1](#0-0) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;
    ...
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
    ...
    _orders[body.commitment][token] -= amount;
```

`_filled[body.commitment]` is set to "done" *before* the loop, escrow accounting (`_orders[...][token] -= amount`) is decremented regardless of whether `transfer()` actually moved funds, and the only guard is `success` — the boolean returned by `token.call(...)`. For any ERC20 whose `transfer()` returns `false` on failure instead of reverting (a widely-documented non-standard-but-legal behavior, e.g. the ZRX token cited in the original report), the low-level `call` reports `success = true` even though no tokens were transferred. The function proceeds to mark the order filled/refunded, decrement escrow, and emit `EscrowReleased`/`EscrowRefunded` — permanently losing track of the fact that the beneficiary never received the tokens.

This exact pattern (`token.call(...)` with only `success` checked) is repeated in the same file's `SweepDust` handler and the transaction-fee payout inside `withdraw()`: [2](#0-1) [3](#0-2) 

Notably, the EVM mainline `IntentGatewayV2`/`IntentsBase` (`evm/src/apps/intentsv2/IntentsBase.sol`) uses OpenZeppelin's `SafeERC20.safeTransfer`, which decodes and reverts on a `false` return: [4](#0-3) 

The Tron port imports `SafeERC20` and even declares `using SafeERC20 for IERC20;` (`evm/tron/contracts/apps/IntentGatewayV2.sol:38-56`) but does not use it in `withdraw`/`SweepDust`, instead reverting to a raw `.call()` that only checks call-level success — reintroducing exactly the class of bug the mainline contract already guards against.

### Impact Explanation
This is reachable by an unprivileged relayer delivering a cross-chain `RedeemEscrow`/`RefundEscrow` message (via `onAccept`), or by an unprivileged party triggering the source-chain `cancelOrder` → `onGetResponse` path — both of which call `withdraw()`. If the escrowed token is a non-standard ERC20 that returns `false` instead of reverting on transfer failure (paused token, blacklist rejection, insufficient balance due to a prior bug, or any legal ERC20 implementation with that semantic), the escrowed funds are never actually delivered to the solver or the refunded user, yet:
- the order is marked `_filled` (finalized), preventing any retry/cancellation path from firing again,
- the escrow accounting is decremented as if paid out,
- `EscrowReleased`/`EscrowRefunded` events are emitted claiming success.

The result is a permanent freezing/loss of the user's or solver's escrowed funds with no recovery path — the exact "concrete theft or permanent freezing of funds" impact category, matching the severity of the referenced M-08 finding.

### Likelihood Explanation
Likelihood is contingent on at least one order using a non-reverting-on-failure ERC20 as an input/fee token on Tron deployments of this gateway — a realistic condition for a permissionless, multi-token intents system that does not restrict which ERC20s can be escrowed. No malicious actor coordination is required; the failure can also be triggered by ordinary token-level conditions (temporary pause, blacklist, insufficient balance from rounding/fee-on-transfer edge cases) that cause `transfer()` to return `false` rather than revert.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `evm/tron/contracts/apps/IntentGatewayV2.sol` (`withdraw()`'s token loop, its fee payout, and `SweepDust`) with OpenZeppelin's `SafeERC20.safeTransfer`, which is already imported and aliased (`using SafeERC20 for IERC20;`) but unused in these paths. This decodes and validates the ERC20 return value (reverting on `false`), consistent with the mainline `IntentsBase._withdraw` implementation, and prevents finalizing escrow state before confirming the transfer actually succeeded.

### Proof of Concept
1. Register/escrow an ERC20 token in the Tron `IntentGatewayV2` whose `transfer()` implementation returns `false` on failure instead of reverting (e.g., pause the token, or have the contract run low on liquidity for a fee-charging variant).
2. Place a cross-chain order with that token as an input; a solver fills it on the destination chain, triggering a `RedeemEscrow` message back to the source (Tron) chain.
3. Relayer delivers the `RedeemEscrow` request; `onAccept` calls `withdraw(body, false)`.
4. Because the token's `transfer()` call to the solver's address returns `false` (without reverting), `token.call(...)` returns `success = true`; the code does not detect the `false` payload.
5. `_filled[commitment]` is set, `_orders[commitment][token]` is decremented, and `EscrowReleased` is emitted — yet the solver's ERC20 balance is unchanged. The escrowed tokens are now permanently unrecoverable: the order is finalized so `RefundEscrow`/`cancelOrder` paths can no longer apply, and no additional payout is triggered.
