## Title
Wrong `sender_is_receiver` parameter reused for nested `Delegate`/`DelegateV2` inner actions causes underpriced gas fees for meta‑transactions - (File: `runtime/runtime/src/config.rs`)

### Summary
`total_send_fees()` computes the gas SEND fee for every action in a transaction, choosing between the discounted "sender-is-receiver" (`sir`) fee and the normal fee via the `sender_is_receiver` boolean argument. For `Delegate`/`DelegateV2` actions it recurses into the inner actions but incorrectly forwards the *outer* `sender_is_receiver` value instead of recomputing it from the delegate action's own `sender_id`/`receiver_id`. The sibling function `total_prepaid_send_fees()` gets this right by recomputing the flag locally. This mirrors the reported bug class: reusing a parameter value that is contextually correct for the outer check but wrong for the nested/inner check, causing the wrong (cheaper) fee/validation path to be taken.

### Finding Description
`total_send_fees` at [1](#0-0)  takes `sender_is_receiver` as a parameter and applies it uniformly to every action, including nested delegate actions: [2](#0-1) 

For both `Delegate` and `DelegateV2`, the recursive call reuses the **outer** `sender_is_receiver` (computed from the outer transaction's `signer_id`/`receiver_id`) to price the fees of the **inner** actions, whose correct discount eligibility depends on `delegate_action.sender_id == delegate_action.receiver_id`, not the outer signer/receiver relationship.

This is proven wrong by the parallel, structurally identical function `total_prepaid_send_fees`, which recomputes the flag for the inner actions explicitly: [3](#0-2) 

`total_send_fees` is invoked from `calculate_tx_cost` (called by `tx_cost`, used during `process_transaction`/`verify_and_charge_tx_ephemeral`) with the *outer* transaction's `sender_is_receiver`: [4](#0-3) 

`sender_is_receiver` there is `receiver_id == signer_id` of the **outer** transaction (relayer vs. the meta‑tx signer account), which is unrelated to whether the *inner* `delegate_action.sender_id` equals `delegate_action.receiver_id` (the actual account pair the inner actions execute between).

### Impact Explanation
The `sir` (sender-is-receiver) SEND fee is intentionally cheaper than the general SEND fee because self-directed actions do not require cross-shard forwarding. Because `total_send_fees` blindly propagates the outer flag into the inner-action pricing:

- If a user submits a transaction where `signer_id == receiver_id` (a legitimate, permissionless case — e.g., a user self-signs a `Delegate`/`DelegateV2` action instead of using a real relayer) but the wrapped `delegate_action.sender_id != delegate_action.receiver_id` (the inner actions actually target a different account), the inner actions are priced with the **cheap `sir` fee** even though they are genuinely cross-account actions that should be billed the more expensive, non-`sir` SEND fee.
- This results in **underpriced execution/gas accounting** for the wrapped inner actions (Transfer, FunctionCall, AddKey, DeployContract, etc.) of a meta-transaction — the signer pays less gas than the protocol's own fee schedule requires for cross-account SEND costs, which is a concrete underpriced-execution / gas-accounting divergence directly reachable from an ordinary submitted transaction.
- The reverse mis-billing (overcharging) is also possible depending on the specific signer/receiver combination, but the economically exploitable direction—underpayment—is the security-relevant one, since it lets a normal user obtain execution for less gas than intended, a form of "free or underpriced execution."

Note: I could not fully verify from the index whether some other layer of the codebase (e.g., a check requiring `tx.receiver_id == delegate_action.sender_id`) constrains which `(signer_id, receiver_id, delegate_action.sender_id, delegate_action.receiver_id)` combinations are actually accepted on-chain, since I only have partial visibility into `SignedDelegateAction`/receipt-construction validation. If such a constraint always forces `receiver_id == delegate_action.sender_id`, the exploitable window narrows to cases where `delegate_action.sender_id == delegate_action.receiver_id` (a self-directed delegate action) combined with `signer_id == receiver_id`, i.e., a self-relayed, self-targeting delegate wrapping a genuinely different-receiver inner action — this needs confirmation with the full receipt-construction code, which is not fully indexed here.

### Likelihood Explanation
This requires no special privileges — any account can construct and sign its own `SignedTransaction` containing a `Delegate`/`DelegateV2` action and choose the relationship between the outer `signer_id`/`receiver_id` and the inner `delegate_action.sender_id`/`receiver_id`. No validator or peer collusion is needed; it is purely a client-side transaction construction issue reachable through the standard transaction-submission path (`Runtime::apply` → `process_transactions` → `tx_cost`/`calculate_tx_cost`).

### Recommendation
In `total_send_fees` (`runtime/runtime/src/config.rs`), for the `Delegate` and `DelegateV2` match arms, recompute `sender_is_receiver` for the inner actions from the delegate action's own `sender_id`/`receiver_id` (as already correctly done in `total_prepaid_send_fees`) instead of reusing the outer parameter, e.g.:
```rust
Delegate(signed_delegate_action) => {
    let delegate_action = &signed_delegate_action.delegate_action;
    let inner_sir = delegate_action.sender_id == delegate_action.receiver_id;
    let delegate_cost = fees.fee(ActionCosts::delegate).send_fee(sender_is_receiver);
    delegate_cost
        .checked_add(total_send_fees(config, inner_sir, &delegate_action.get_actions(), &delegate_action.receiver_id)?)
        .unwrap()
}
```
Apply the analogous fix for `DelegateV2`. Because this affects gas-fee accounting, this change is consensus-relevant and would need to be gated behind a protocol feature/version to avoid breaking existing chain state agreement, similar to how `fix_ml_dsa_cost_charging` gates the ML-DSA cost fix nearby in the same file (`runtime/runtime/src/config.rs:71-81`).

### Proof of Concept
Conceptual PoC (exact reachability of the specific account-id combination needs to be confirmed against `SignedDelegateAction`/receipt-construction validation code not fully available in the index):
1. Alice (`alice.near`) wants to send a `Transfer` action to Bob (`bob.near`) via a `DelegateV2` meta-transaction, but self-signs and self-submits it rather than using an external relayer, setting the outer `SignedTransaction{ signer_id: alice.near, receiver_id: alice.near, actions: [DelegateV2(delegate_action{ sender_id: alice.near, receiver_id: bob.near, actions: [Transfer{...}] })] }`.
2. `calculate_tx_cost` computes outer `sender_is_receiver = (receiver_id == signer_id) = true` (alice == alice).
3. `total_send_fees` is called with `sender_is_receiver = true` and recurses into the `DelegateV2` branch, reusing `true` for the inner `Transfer` action targeting `bob.near`, applying the cheaper `sir` SEND fee to a transfer that is genuinely cross-account (alice → bob).
4. Compare against `total_prepaid_send_fees`, which for the same actions computes `inner_sender_is_receiver = (alice.near == bob.near) = false` and would apply the correct, more expensive non-`sir` fee — demonstrating the discrepancy and confirming the `total_send_fees` computation undercharges relative to the codebase's own correct reference implementation.

pub fn total_prepaid_send_fees(
    config: &RuntimeConfig,
    actions: &[Action],
) -> Result<ParameterCost, IntegerOverflowError> {
    let mut result = ParameterCost::ZERO;
    for action in actions {
        use Action::*;
        let delta = match action {
            Delegate(signed_delegate_action) => {
                let delegate_action = &signed_delegate_action.delegate_action;
                let sender_is_receiver = delegate_action.sender_id == delegate_action.receiver_id;

                total_send_fees(
                    config,
                    sender_is_receiver,
                    &delegate_action.get_actions(),
                    &delegate_action.receiver_id,
                )?
            }
            DelegateV2(signed_delegate_action) => {
                let delegate_action =
                    VersionedDelegateActionRef::from(&signed_delegate_action.delegate_action);
                let sender_is_receiver =
                    delegate_action.sender_id() == delegate_action.receiver_id();

                total_send_fees(
                    config,
                    sender_is_receiver,
                    &delegate_action.get_actions(),
                    delegate_action.receiver_id(),
                )?
            }
            _ => ParameterCost::ZERO,
        };
        result = result.checked_add_result(delta)?;
    }
    Ok(result)
}

/// Like [`tx_cost`], for callers that have the transaction's fields but not a
/// `Transaction` (e.g. the indexer prices transaction views).
pub fn calculate_tx_cost(
    receiver_id: &AccountId,
    signer_id: &AccountId,
    signer_public_key: &PublicKey,
    actions: &[Action],
    config: &RuntimeConfig,
    current_gas_price: Balance,
) -> Result<TransactionCost, IntegerOverflowError> {
    let sender_is_receiver = receiver_id == signer_id;
    let fees = &config.fees;
    let mut burnt: ParameterCost =
        fees.fee(ActionCosts::new_action_receipt).send_fee(sender_is_receiver);
    burnt = burnt.checked_add_result(total_send_fees(
        config,
        sender_is_receiver,
        actions,
        receiver_id,
    )?)?;
