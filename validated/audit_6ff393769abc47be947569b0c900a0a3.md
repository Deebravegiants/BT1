### Title
Unrestricted `CallDispatcher.dispatch()` allows anyone to drain the dispatcher's held ETH/token balance via arbitrary calls - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch(bytes)` is `external` with no caller restriction, mirroring the `Burve::uniswapV3MintCallback` bug class: a privileged, fund-moving function that decodes attacker-supplied calldata and executes it unconditionally, with no check that the caller is the trusted app contract that is supposed to invoke it.

### Finding Description
`CallDispatcher` is the shared utility contract used by `IntentGatewayV2`, `HyperFungibleToken`, and `WrappedHyperFungibleToken` to execute arbitrary predispatch/output/calldata-execution calls on behalf of orders and cross-chain messages [1](#0-0) . Its `dispatch` function decodes an array of `Call{to, value, data}` structs and blindly executes `to.call{value: call.value}(call.data)` for each entry, with no `onlyOwner`/`onlyGateway`/`onlyHost`-style modifier restricting `msg.sender`: [2](#0-1) 

The contract also unconditionally accepts native ETH via `receive() external payable {}` [3](#0-2) , meaning it can and does hold ETH balance at various points (e.g. tokens/ETH forwarded to it by `IntentGatewayV2.placeOrder` before predispatch execution and before the sweep-back transfer calls, or ETH sent to it directly/mistakenly by any third party) [4](#0-3) . `HyperFungibleToken`/`WrappedHyperFungibleToken` also route arbitrary decoded calldata through the same unrestricted `dispatch()` call during `onAccept` [5](#0-4) .

Because `dispatch()` performs no authentication of its caller and blindly forwards `call.value` (drawn from the CallDispatcher's own current ETH/token balance) to any attacker-chosen `to`/`data`, any external account can call `CallDispatcher.dispatch()` directly — completely bypassing `IntentGatewayV2`'s order/escrow logic and `HyperApp`'s `onlyHost`/source-authentication checks — and instruct the dispatcher to send out whatever ETH or approved/held token balance it currently has to an attacker-controlled address. This is structurally identical to the `Burve::uniswapV3MintCallback` flaw: an externally reachable function that performs a fund-transferring action based on attacker-supplied parameters, with no restriction limiting the caller to the intended privileged party (the pool in Burve's case, `IntentGatewayV2`/`HyperFungibleToken`/`host` in this case).

### Impact Explanation
Any ETH that accumulates in `CallDispatcher` — whether temporarily in-flight during a legitimate `placeOrder`/`onAccept` predispatch execution, or from accidental/direct sends via its permissive `receive()` — can be swept out by an unrelated attacker calling `dispatch()` directly with a `Call[]` specifying an arbitrary recipient and the dispatcher's full balance as `value`. Since `CallDispatcher` is a shared, reusable component across `IntentGatewayV2` and multiple `HyperFungibleToken` deployments, this is a direct theft-of-funds vector reachable from a single unprivileged transaction, matching the report's "High/High" classification for unrestricted privileged callbacks.

### Likelihood Explanation
`dispatch()` is a plain external function requiring no special permission, proof, or state — any address can call it in any transaction as soon as the `CallDispatcher` holds a nonzero balance (which can be induced by simply sending ETH to it, since `receive()` accepts value unconditionally from anyone).

### Recommendation
Restrict `CallDispatcher.dispatch()` to only be callable by the specific set of authorized app contracts that are expected to invoke it (e.g. an allowlist of registered `IntentGatewayV2`/`HyperFungibleToken` instances, or bind a single dispatcher instance to one owner app set at construction and enforce `msg.sender == owner`), analogous to the `Burve` fix of restricting `uniswapV3MintCallback` to `msg.sender == pool`. Additionally avoid leaving retrievable ETH/token balances on the dispatcher between calls, or ensure any balance held cannot be misappropriated by a non-owner caller.

### Proof of Concept
1. An attacker (or any third party) sends ETH directly to the `CallDispatcher` contract address, or waits for a legitimate `IntentGatewayV2.placeOrder`/`onAccept` flow to (momentarily) leave a balance on it.
2. The attacker calls `CallDispatcher.dispatch(encoded)` directly, where `encoded` decodes to a `Call[]` with `to = attacker`, `value = address(dispatcher).balance`, `data = ""`.
3. Since `dispatch()` has no caller check, `to.call{value: call.value}(call.data)` executes successfully, transferring the dispatcher's ETH balance to the attacker [6](#0-5) .

     * @dev Receive function to accept ETH transfers

    receive() external payable {}

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
