### Title
Webhook shop-tenant identity not covered by HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature validated by `HmacValidator.validate` authenticates the *bytes of the body* but not the `shop`, `topic`, `webhook_id`, or `api_version` values, which are all taken straight from unauthenticated HTTP headers and then handed to the app's webhook handler as the tenant identity.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
which returns only `@raw_body`. Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled directly from HTTP headers with no cryptographic binding to that body: [2](#0-1) 

`Registry.process` validates only this body-only HMAC, then immediately forwards the header-derived, unauthenticated `request.shop` value to the application's webhook handler as the tenant identity: [3](#0-2) 

The identity binding that should hold is:
`shop authenticated by the HMAC (i.e., the shop whose install produced this exact body+signature)` == `shop asserted in WebhookMetadata.shop and acted on by the handler`

Because the HMAC only covers the body, this equality is not enforced: any request with a *valid* `(raw_body, hmac)` pair — regardless of which shop it originally came from — combined with an attacker-chosen `x-shopify-shop-domain` header passes `HmacValidator.validate` and reaches the handler with a forged `shop`.

### Impact Explanation
All shops installing a given app share the same `Context.api_secret_key`, so a valid `(body, hmac)` pair generated for one shop's webhook delivery is cryptographically valid for the app's endpoint regardless of which shop's domain is stamped in the header. An unprivileged attacker who installs the app on their own store (a normal, unprivileged action) will receive a legitimate webhook delivery from Shopify — a real body and its correct HMAC. They can replay that exact `(body, hmac)` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header with a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the body bytes, and `Registry.process` passes the attacker-controlled `shop` straight into `WebhookMetadata`. Any app that uses `WebhookMetadata.shop` to select which tenant's records/session to update (a normal and expected usage pattern) will apply attacker-supplied webhook data under the wrong tenant, constituting cross-tenant data injection/confusion — a Critical-impact cross-tenant access issue per this gem's own trust model for `Registry.process`.

### Likelihood Explanation
Any internet user can self-serve install most Shopify apps on their own store to legitimately receive at least one signed webhook delivery, and replaying an HTTP POST with modified headers requires no special privilege, no secret, and no social engineering. The only constraint is that the attacker must reuse a body they've legitimately received (they cannot forge arbitrary bodies), but many webhook topics (e.g., `app/uninstalled`, `shop/update`) or bodies with attacker-influenced content (e.g., an order they place in their own shop) still carry meaningful data (shop-level fields) that becomes dangerous once mis-attributed to another tenant.

### Recommendation
Include the security-relevant headers (`shop`, `topic`, `webhook_id`, `api_version`, and ideally a delivery-specific nonce/timestamp) in the value that is HMAC-verified, or otherwise cryptographically bind the header-derived `shop` to the verified body (e.g., require the app to independently confirm, out of band, that the shop domain in the header corresponds to a shop with an active installation matching the delivered `webhook_id`) before passing it to the handler as trusted tenant identity.

### Proof of Concept
1. Install the target app on attacker-owned store `attacker.myshopify.com`.
2. Trigger a webhook (e.g. update shop settings) so Shopify sends a signed request to the app’s webhook endpoint with a real `x-shopify-hmac-sha256` computed over the JSON body using the app's shared `api_secret_key`.
3. Capture the raw body and the `x-shopify-hmac-sha256` header value from that delivery.
4. Replay an HTTP POST to the same webhook endpoint with the identical body and `x-shopify-hmac-sha256`, but set `x-shopify-shop-domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` (`lib/shopify_api/webhooks/registry.rb:190`), which passes because only the body is checked; `WebhookMetadata.shop` is set to `victim.myshopify.com` (`lib/shopify_api/webhooks/registry.rb:198-199`), and the app's handler processes the attacker's data as if it belonged to the victim shop.
