### Title
Missing L2-sequencer-uptime check when pricing gas via Chainlink feeds in `SimplexPaymaster` — ([File: evm/src/utils/SimplexPaymaster.sol])

### Summary
`SimplexPaymaster` prices ERC-20 gas payment (for intent-solver UserOperations) with Chainlink `AggregatorV3Interface` feeds via `_getOraclePrice`, checking only `answer > 0` and `block.timestamp - updatedAt <= maxOracleAge` [1](#0-0) . The contract is deployed on Arbitrum, Base and (planned) Optimism — Chainlink-supported Optimistic-rollup L2s that require checking the Chainlink L2 Sequencer Uptime Feed to detect sequencer outages, per Chainlink's L2 data-feed guidance referenced in the external report. No such check exists anywhere in the contract or its deployment scripts.

### Finding Description
`_getOraclePrice` is the sole gate on price freshness/validity for both the native/USD and token/USD feeds used throughout pricing: `_tokenPrice` combines the two feed reads for `getTokenPrice`/`estimateTokenCost` and for the actual gas-cost calculation charged to solver UserOperations, and the same helper backs the oracle-bounded slippage check in the fee-recycling swap path (`swapAndDeposit`) [2](#0-1) .

On Arbitrum/Optimism/Base, if the L2 Sequencer goes down, transactions (including price-feed updates relayed on-chain) stop landing, but the aggregator's `latestRoundData()` can still return the *last* round that was pushed before the outage, with an `updatedAt` that has not yet exceeded `maxOracleAge` (deployment config sets a 24h-style buffer for stablecoin feeds — `MAX_ORACLE_AGE = 7 days`, deploy default `90_000` seconds) [3](#0-2) [4](#0-3) . During and immediately after a sequencer outage/restart the underlying price can diverge sharply from the on-chain "last known good" value, yet `_getOraclePrice` treats it as valid because it only checks staleness relative to wall-clock time, not sequencer liveness.

This is exactly the missing-check class from the referenced report (`PriceOracle.sol` on IronBank): a Chainlink consumer on L2 without validating `sequencerUptimeFeed.latestRoundData()` / the grace period after a sequencer restart.

The path is reachable by any unprivileged actor: an intent solver's UserOperation goes through EntryPoint → `SimplexPaymaster` validation/postOp, which calls `_tokenPrice` → `_getOraclePrice` to compute how much ERC-20 the solver is charged for gas, and the fee-recycling keeper's `swapAndDeposit` similarly bounds slippage against the same stale/incorrect price.

### Impact Explanation
A stale-but-"fresh-enough" price during a sequencer outage lets the paymaster mis-price gas:
- If native/USD moves against token/USD during the outage and the stale round undercharges, solvers (or anyone crafting a UserOperation through this permissionless paymaster) can drain the paymaster's EntryPoint deposit/treasury surplus by paying artificially cheap stablecoin for gas.
- Conversely, an overcharge griefs solvers relying on the paymaster to sponsor gas, degrading solver liquidity for intents.
- The same stale price feeds the slippage bound in `swapAndDeposit`, so the fee-recycling swap could execute at a bad rate, causing treasury value loss.

This is a Medium-severity oracle-manipulation/fund-drain vector limited to the paymaster's own token/native reserves and EntryPoint deposit, not a protocol-wide freeze, but it is a concrete path to fund loss reachable by any permissionless solver/UserOperation submitter on the affected L2s.

### Likelihood Explanation
Likelihood depends on an L2 sequencer outage occurring while a stale round sits within `maxOracleAge` and diverges materially from spot price — a known, recurring event class on Arbitrum/Optimism (documented sequencer downtime incidents exist). Given `SimplexPaymaster` is actively deployed/configured for Arbitrum and Base (and slated for Optimism) per the SDK chain registry and deploy scripts, and the check is entirely absent, exploitation only requires timing a UserOperation with a real (not adversary-caused) sequencer disruption — Medium likelihood, standard for this bug class on Chainlink L2 deployments.

### Recommendation
Add a Chainlink L2 Sequencer Uptime Feed check in `_getOraclePrice` (or a shared modifier called before any price read): read `sequencerUptimeFeed.latestRoundData()`, revert if `answer != 0` (sequencer down), and enforce a grace period (e.g., Chainlink's recommended `GRACE_PERIOD_TIME`) after `startedAt` before trusting subsequent price updates, per Chainlink's L2 sequencer-feed example referenced in the source report.

### Proof of Concept
1. Deploy `SimplexPaymaster` on Arbitrum with `nativeOracle`/token oracles as in `DeploySimplexPaymaster.s.sol`.
2. Simulate/observe an Arbitrum Sequencer outage; the last Chainlink round before the outage remains within `maxOracleAge` (e.g., 90,000s buffer configured at deploy) for the outage's duration.
3. During the outage, submit a UserOperation with `SimplexPaymaster` paymasterData (mode `0x00`/`0x02`); `_getOraclePrice` in `_tokenPrice` (called from the paymaster's gas-charging path) accepts the stale round because `block.timestamp - updatedAt <= maxOracleAge` still holds, at [5](#0-4) .
4. If the real off-chain price has since diverged, the solver is charged a mispriced amount of stablecoin for gas, draining or overcharging the paymaster's economics — with no Sequencer Uptime Feed check to prevent it.

Note: I was unable to find any `sequencerUptimeFeed`/`SequencerUptimeFeed` reference anywhere in the indexed codebase (`grep_search` for `Sequencer|sequencerUptimeFeed|AggregatorV2V3Interface` returned no hits in EVM contracts), confirming the absence of this control across the codebase, not just an oversight in one file.

```text
    function _tokenPrice(TokenConfig memory cfg) internal view returns (uint256) {
        uint256 nativeUsd = _getOraclePrice(nativeOracle, nativeOracleDecimals);
        uint256 tokenUsd = _getOraclePrice(cfg.tokenOracle, cfg.tokenOracleDecimals);

        return (nativeUsd * (10 ** cfg.tokenDecimals) * (10_000 + markupBps)) / (tokenUsd * 10_000);
    }

    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
