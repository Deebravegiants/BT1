### Title
Unbounded per-request memory growth in Vault and Confidential Relay gateway handlers from unauthenticated fan-out requests - (File: core/services/gateway/handlers/vault/handler.go, core/services/gateway/handlers/confidentialrelay/handler.go)

### Summary
Both the Vault gateway handler (`core/services/gateway/handlers/vault/handler.go`) and the Confidential Relay gateway handler (`core/services/gateway/handlers/confidentialrelay/handler.go`) accept arbitrary, unprivileged HTTP user requests at `HandleJSONRPCUserMessage` and insert a new entry into an in-memory `activeRequests` map keyed by the caller-supplied `req.ID` (bounded only to 200 bytes in length), with no cap on the number of concurrently outstanding entries. [1](#0-0) [2](#0-1) 

### Finding Description
`newActiveRequest` in each handler unconditionally stores the request (including its full JSON-RPC params, a per-request response map, and callback) in `h.activeRequests[req.ID]`, protected only by a mutex, never by a maximum-size check:

```go
func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		...
	}
	ar := &activeRequest{... responses: map[string]*jsonrpc.Response[json.RawMessage]{}}
	h.activeRequests[req.ID] = ar
``` [3](#0-2) 

The same pattern exists in the confidential relay handler. [4](#0-3) 

Each entry remains in the map until a `requestTimeout` cleanup pass runs (`removeExpiredRequests`, invoked on a periodic ticker) or all node responses complete/quorum is reached. [5](#0-4) [6](#0-5) 

By contrast, the generic `RequestCache` used elsewhere in the gateway explicitly enforces `maxCacheSize` and rejects new requests once full. [7](#0-6)  The vault and confidential-relay handlers do not reuse this bounded cache and have no equivalent limit.

The vault handler does perform request authorization (`h.requestProcessor.ProcessRequest`) before creating the active request for most methods, but the `MethodPublicKeyGet` path explicitly bypasses authorization ("Public key requests don't require authorization") and still allocates an `activeRequest` when the value isn't cached. [8](#0-7)  The confidential relay handler's `HandleJSONRPCUserMessage` performs no authorization at all before calling `newActiveRequest`; attestation/authorization checks happen deeper (e.g. for capability execution), but the top-level user-facing entry point immediately allocates the map entry for any distinct `req.ID`. [2](#0-1) 

This mirrors the CVE-2022-42314 bug class: an unprivileged, low-cost caller (analogous to a "guest") can force the trusted component (the gateway process, analogous to `xenstored`) to accumulate memory proportional to attacker-controlled requests rather than any bounded/authenticated quota, because the enforcement point (request timeout eviction) is time-based, not count-based.

### Impact Explanation
An unauthenticated or minimally-privileged client hitting the gateway's user-facing HTTP endpoint can repeatedly submit JSON-RPC requests with unique `id` values (up to 200 bytes each, plus arbitrary params up to `MaxRequestBytes`, e.g. 100KB per the sample gateway config [9](#0-8) ) faster than the `requestTimeout`/cleanup ticker (default 5s cleanup period, request timeout order of ~10-14s) can evict them. Because there is no cap on the number of concurrently tracked `activeRequests`, sustained flooding grows gateway memory unboundedly, risking OOM/DoS of the gateway process, which is shared infrastructure serving the whole DON/workflow fleet — a much broader-impact analog of the xenstored OOM in the report.

### Likelihood Explanation
Likelihood is moderate-to-high: reaching this code path requires only network access to the gateway's public HTTP JSON-RPC endpoint (no prior authentication needed for the confidential-relay path, and the vault handler's uncached public-key path also bypasses authorization). Generating unique request IDs and firing many concurrent HTTP requests is trivial for any external actor.

### Recommendation
Add an explicit maximum concurrent `activeRequests` bound (mirroring `RequestCache.maxCacheSize`) to both the vault and confidential-relay handlers, rejecting new requests once the limit is reached, and/or apply a per-sender/global rate limiter on inbound user messages before `newActiveRequest` is called (similar to the existing per-node/global rate limiting already applied to node responses in `HandleNodeMessage`). Consider migrating both handlers onto the shared, already-bounded `RequestCache` abstraction.

### Proof of Concept
1. Send a burst of JSON-RPC requests to the gateway's vault or confidential-relay endpoint (`ProcessRequest` → `HandleJSONRPCUserMessage`), each with a unique `id` (≤200 chars) and maximal allowed payload size.
2. Repeat faster than the handler's cleanup ticker interval (`defaultCleanUpPeriod`) can expire and remove entries.
3. Observe `h.activeRequests` map growing without bound, consuming proportional memory in the gateway process until resource exhaustion/OOM, denying service to legitimate DON traffic. [10](#0-9)  (note: `defaultCleanUpPeriod = 5 * time.Second`), giving a multi-second attacker window per cycle in which arbitrarily many entries can be inserted with no upper bound.

	var expiredRequests []*activeRequest

func (h *handler) HandleJSONRPCUserMessage(ctx context.Context, req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) error {
	if req.ID == "" {
		return errors.New("request ID cannot be empty")
	}
	if len(req.ID) > 200 {
		// Arbitrary limit to prevent abuse
		return errors.New("request ID is too long: " + strconv.Itoa(len(req.ID)) + ". max is 200 characters")
	}

	h.lggr.Debugw("handling vault request", "method", req.Method, "requestID", req.ID, "request", req)
	if req.Method == vaulttypes.MethodPublicKeyGet {
		// Public key requests don't require authorization,
		// Let's process this request right away.
		// Note we cache this value quite aggressively so don't need to worry about DoS.
		publicKeyResponseBytes, cachedPublicKey := h.getCachedPublicKey()
		if cachedPublicKey == nil {
			// Not found in cache. Fetch from nodes.
			ar, err := h.newActiveRequest(req, callback)
			if err != nil {
				h.lggr.Errorw("failed to create new activeRequest", "error", err)
				return err
			}
			return h.handlePublicKeyGet(ctx, ar)
		}
		h.lggr.Debugw("returning cached public key response")
		return h.handlePublicKeyGetSynchronously(ctx, req, publicKeyResponseBytes, callback)
	}

	if !vaulttypes.IsGatewaySecretsMethod(req.Method) {
		return h.sendImmediateUserResponse(ctx, req, callback, api.UnsupportedMethodError, errors.New("this method is unsupported: "+req.Method))
	}

	_, cachedPublicKey := h.getCachedPublicKey()
	authorized, err := h.requestProcessor.ProcessRequest(ctx, &req, cachedPublicKey)
	if err != nil {
		if vaultcap.IsInvalidVaultParamsError(err) {
			return h.sendImmediateUserResponse(ctx, req, callback, api.InvalidParamsError, err)
		}
		h.lggr.Errorw("request not authorized", "method", req.Method, "requestID", req.ID, "hasAuth", req.Auth != "", "error", err)
		return errors.New("request not authorized: " + err.Error())
	}
	authorizedOwner := authorized.AuthResult.AuthorizedOwner()

	h.lggr.Debugw("handling authorized vault request", "method", req.Method, "requestID", req.ID, "authorizedOwner", authorizedOwner)
	ar, activeRequestErr := h.newActiveRequest(req, callback)
	if activeRequestErr != nil {
		return activeRequestErr
	}
