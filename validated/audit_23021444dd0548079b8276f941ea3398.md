## Analysis

This is exactly the bug class the report describes: a component caches an address that a governing registry can later change, breaking the correspondence between the two sides of a flow and stranding funds. In `pallet-hyper-fungible-token`, `on_timeout` looks up the refund asset via `ContractToAsset::<T>::get(dest, &to)` at `modules/pallets/hyper-fungible-token/src/module.rs:236-237`, using the *destination contract address embedded in the original request* — not a live, re-resolved mapping keyed by asset ID. `update_token` (`modules/pallets/hyper-fungible-token/src/lib.rs:384-430`) lets governance repoint or remove a chain's `token_contract` for an asset at any time, and on repoint it deletes the old `ContractToAsset` entry (`ContractToAsset::<T>::remove(chain, old_contract)`, line 410) before inserting the new one.

If a `send` is dispatched while pointed at contract A, and governance calls `update_token` to repoint that chain to contract B (or remove the chain) before the message times out, the in-flight request's `to`/`dest` on timeout no longer resolves in `ContractToAsset`, so `on_timeout` returns `HftError::UnknownContractOnTimeout` and the escrowed/burned funds are never refunded. This mirrors the report precisely: one side (the dispatch that already locked funds) is bound to an address the governing registry later invalidates, and there is no fallback path (like `Quest`'s hard-coded receipt address) to reconcile it — the refund path is asset-ID-independent and solely keyed by the stale contract address. ### Title
Stale `ContractToAsset` lookup on timeout permanently strands escrowed/burned funds after `update_token` repoints a chain - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`pallet-hyper-fungible-token`'s `send` locks or burns a user's asset and dispatches a cross-chain `PostRequest` whose `to` field is the token contract address resolved from `TokenContracts` at dispatch time. If that request later times out, `on_timeout` re-derives the local asset solely from `ContractToAsset::<T>::get(dest, &to)`, keyed by the contract address that was current when the message was sent. `update_token` allows `CreateOrigin` to change or remove that per-chain contract mapping at any time, deleting the old `ContractToAsset` entry. A timeout for a message dispatched before the update can then never resolve an asset, so the refund path fails and the already-escrowed/burned funds are permanently unrecoverable.

### Finding Description
`send` (`modules/pallets/hyper-fungible-token/src/lib.rs:241-325`) escrows the native asset or burns/locks the non-native asset immediately, then dispatches a `PostRequest` to `token_contract`, the address read from `TokenContracts` at that moment. Should the request time out, `on_timeout` (`modules/pallets/hyper-fungible-token/src/module.rs:218-296`) recovers which local asset to refund purely from `ContractToAsset::<T>::get(dest, &to)`, where `to` is the address baked into the original request body, not a live re-resolution against the current registry state.

`update_token` (`modules/pallets/hyper-fungible-token/src/lib.rs:384-430`) is callable by `CreateOrigin` at any time and, for each chain in `add_chains`, first removes the *old* `ContractToAsset` reverse mapping (`ContractToAsset::<T>::remove(chain, old_contract)`) before inserting the new one; `remove_chains` deletes the mapping outright. There is no coordination between in-flight (already dispatched, not yet timed out) requests and this update — the pallet has no way to know a message referencing the old contract address is still outstanding.

This is the same root cause as the referenced Quest Protocol bug: one side of a two-party interaction caches an address at the time an action was taken (the `Quest`'s immutable `RabbitHoleReceipt` reference / here, the request's baked-in `to` contract address), while the authoritative registry (the `QuestFactory` / here, `TokenContracts`+`ContractToAsset`) is mutable and can diverge from it. When the two disagree, the party holding the stale reference (the user whose funds are escrowed, or minted receipt) can no longer complete the flow through the intended recovery path.

### Impact Explanation
A user who called `send` before an `update_token`/chain-removal has their tokens escrowed (native) or burned (non-native). If the outbound `PostRequest` subsequently times out — which can happen for ordinary reasons (relayer delay, destination congestion, or intentional governance-driven decommissioning of a contract) — `on_timeout` cannot resolve `local_asset_id` and errors with `HftError::UnknownContractOnTimeout`, so the refund transfer never executes. The escrowed native balance remains locked in the pallet account with no code path to release it back to the sender, and for burned non-native assets the user has no burned tokens and receives nothing back: this is a permanent freezing/loss of user funds, reachable by an ordinary user's `send` extrinsic combined with a foreseeable governance maintenance action (repointing or decommissioning a chain's token contract), which is within Hyperbridge's normal token-registry lifecycle rather than a malicious-admin scenario.

### Likelihood Explanation
Token contract addresses are expected to be updated over the life of the protocol (upgrades, redeployments, migrations) via the documented `update_token` extrinsic, and cross-chain message timeouts are a routine, non-adversarial occurrence (relayer downtime, congestion, deliberate cancellation). Any `send` in flight at the moment a legitimate `update_token` call repoints or removes the destination chain's entry for that asset is affected — no attacker action is required beyond ordinary use combined with a foreseeable operational action, making this readily triggerable in production.

### Recommendation
Do not derive the refund asset solely from the volatile `ContractToAsset` reverse mapping keyed by contract address. Instead, either (a) embed the local `AssetId` directly in the dispatched `Message`/`PostRequest` body so `on_timeout` can decode it without any registry lookup, or (b) retain a per-request record (e.g., a `PendingSends` map keyed by commitment or nonce) captured at `send` time that pins the asset, decimals, and destination contract for that specific request, and have `on_timeout` consult that record instead of the live `ContractToAsset` mapping. Additionally, `update_token` should refuse to remove/repoint a chain's contract for an asset while requests referencing the old contract may still be outstanding, or provide an explicit migration/reconciliation path (analogous to fetching the "receipt contract" from the originating call rather than the mutable global registry, as recommended in the referenced report).

### Proof of Concept
1. Governance registers `MYTOKEN` for `StateMachine::Evm(1)` pointing at contract `A` via `register_token`, populating `TokenContracts[Evm(1)][MYTOKEN] = A` and `ContractToAsset[Evm(1)][A] = MYTOKEN` (`modules/pallets/hyper-fungible-token/src/lib.rs:327-376`).
2. A user calls `send` with `asset_id = MYTOKEN`, `destination = Evm(1)`. Their balance is escrowed/burned and a `PostRequest{ dest: Evm(1), to: A, ... }` is dispatched (`modules/pallets/hyper-fungible-token/src/lib.rs:241-325`).
3. Before this request is delivered, governance calls `update_token` to repoint `Evm(1)` to a new contract `B` (e.g. after a redeploy). This removes `ContractToAsset[Evm(1)][A]` and inserts `ContractToAsset[Evm(1)][B] = MYTOKEN` (`modules/pallets/hyper-fungible-token/src/lib.rs:407-411`).
4. The original request to `A` times out and `on_timeout` is invoked with `to = A`, `dest = Evm(1)`. `ContractToAsset::<T>::get(Evm(1), A)` now returns `None`, so the call returns `Err(HftError::UnknownContractOnTimeout)` (`modules/pallets/hyper-fungible-token/src/module.rs:236-237`), and the user's escrowed/burned funds are never returned.

	fn on_timeout(&self, request: Request) -> Result<Weight, anyhow::Error> {
		match request {
			Request::Post(PostRequest { body, to, dest, .. }) => {
				let message = Message::abi_decode(&body).map_err(HftError::DecodeError)?;

				// Refund the original sender
				let from_bytes = message.from.as_ref();
				let mut sender_bytes = [0u8; 32];
				if from_bytes.len() == 32 {
					sender_bytes.copy_from_slice(from_bytes);
				} else if from_bytes.len() == 20 {
					sender_bytes[12..].copy_from_slice(from_bytes);
				} else {
					Err(HftError::InvalidSenderLength(from_bytes.len()))?
				}
				let beneficiary: T::AccountId = sender_bytes.into();

				// Look up the asset from the destination contract address
				let local_asset_id = ContractToAsset::<T>::get(dest, &to)
					.ok_or(HftError::UnknownContractOnTimeout)?;

				let decimals = if local_asset_id == T::NativeAssetId::get() {
					T::Decimals::get()
				} else {
					<T::Assets as fungibles::metadata::Inspect<T::AccountId>>::decimals(
						local_asset_id.clone(),
					)
				};
				let erc_decimals = Precisions::<T>::get(local_asset_id.clone(), dest)
					.ok_or(HftError::DecimalsNotConfigured(dest))?;
				let amount = convert_to_balance::<
					<<T as Config>::NativeCurrency as Currency<T::AccountId>>::Balance,
				>(
					U256::from_big_endian(&message.amount.to_be_bytes::<32>()),
					erc_decimals,
					decimals,
				)
				.map_err(|e| HftError::InvalidAmountConversion(format!("{e:?}")))?;

		pub fn update_token(
			origin: OriginFor<T>,
			update: TokenUpdate<AssetId<T>>,
		) -> DispatchResult {
			T::CreateOrigin::ensure_origin(origin)?;

			let local_decimals = if update.asset_id == T::NativeAssetId::get() {
				T::Decimals::get()
			} else {
				<T::Assets as fungibles::metadata::Inspect<T::AccountId>>::decimals(
					update.asset_id.clone(),
				)
			};

			for (chain, config) in update.add_chains {
				// This pallet bridges substrate <-> EVM only; reject non-EVM peers.
				if !matches!(chain, StateMachine::Evm(_)) {
					return Err(Error::<T>::NonEvmPeerChain.into());
				}
				ensure!(
					config.decimals >= local_decimals,
					Error::<T>::ErcDecimalsBelowLocal
				);
				// Remove old reverse mapping if it exists
				if let Some(old_contract) = TokenContracts::<T>::get(chain, update.asset_id.clone())
				{
					ContractToAsset::<T>::remove(chain, old_contract);
				}

				let token_contract = config.token_contract.0.to_vec();
				TokenContracts::<T>::insert(
					chain,
					update.asset_id.clone(),
					token_contract.clone(),
				);
				ContractToAsset::<T>::insert(chain, token_contract, update.asset_id.clone());
				Precisions::<T>::insert(update.asset_id.clone(), chain, config.decimals);
			}

			for chain in update.remove_chains {
				if let Some(old_contract) = TokenContracts::<T>::get(chain, update.asset_id.clone())
				{
					ContractToAsset::<T>::remove(chain, old_contract);
				}
				TokenContracts::<T>::remove(chain, update.asset_id.clone());
				Precisions::<T>::remove(update.asset_id.clone(), chain);
			}
