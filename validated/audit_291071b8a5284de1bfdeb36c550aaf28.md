### Title
`compareAddresses` does raw string equality for BCH while `createWithdrawMemo` strips the `bitcoincash:` prefix, letting a self-transfer bypass `DestinationAddressMatchesTokenAddressError` - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.validateWithdrawal` compares the caller-supplied `destinationAddress` against `tokenInfo.origin_chain_address` via `compareAddresses`, which for `Chains.BitcoinCash` does plain `a === b` string comparison without normalizing the CashAddr `bitcoincash:` prefix [1](#0-0) . `createWithdrawIntentPrimitive` (via `createWithdrawMemo`) strips that same prefix before encoding the address into the signed `memo` [2](#0-1) . This divergence lets an attacker supply `bitcoincash:<origin_chain_address>` as the destination, pass validation, and end up with a signed intent whose memo address equals the token's own `origin_chain_address`.

### Finding Description
The invariant that should hold: the address checked by `compareAddresses(tokenInfo.origin_chain_address, args.destinationAddress, blockchain)` in `validateWithdrawal` [3](#0-2)  must equal the address literally encoded in the signed memo by `createWithdrawIntentPrimitive` [4](#0-3) .

For BCH, `compareAddresses` falls into the generic `a === b` branch shared with Bitcoin/Near/etc, with no CashAddr-prefix normalization, unlike its TON/Tron/hex-address branches which do normalize equivalent textual forms [5](#0-4) . Meanwhile `createWithdrawMemo` explicitly strips a `bitcoincash:` prefix before building the memo string that gets signed as part of the `ft_withdraw` intent's `memo` field [6](#0-5) , confirmed by the existing test asserting `bitcoincash:qpm2q...` → memo `WITHDRAW_TO:qpm2q...` [7](#0-6) .

Attacker input: `destinationAddress = "bitcoincash:" + tokenInfo.origin_chain_address` (a BCH token whose `origin_chain_address` is the bare, unprefixed CashAddr payload). `validateAddress` accepts this as a well-formed BCH address (it auto-adds the prefix if missing, so both prefixed and unprefixed forms are valid format) [8](#0-7) . Then `compareAddresses("origin_addr", "bitcoincash:origin_addr", BitcoinCash)` returns `false` because the raw strings differ, so `DestinationAddressMatchesTokenAddressError` is never thrown [3](#0-2) . `createWithdrawalIntents` then calls `createWithdrawIntentPrimitive`, whose memo strips the prefix, producing `WITHDRAW_TO:origin_addr` — a signed intent for a self-transfer to the token's own on-chain address, exactly the scenario `DestinationAddressMatchesTokenAddressError` is designed to block.

Existing guards do not catch this: `validateAddress` only checks format, not canonicalization against `origin_chain_address`; `compareAddresses` for BCH has no prefix-stripping logic (unlike Tron/TON/hex chains where the code explicitly normalizes to compare canonical forms).

Note: BCH support in the POA bridge's `getSupportedTokens` responses is currently commented out in tests ("BCH tests commented out until POA Bridge API supports BCH"), meaning BCH is not yet a live route through this bridge, but the code path (`Chains.BitcoinCash` in `caip2Mapping`/`tokenPrefixMapping`, `validateBchAddress`, `compareAddresses` BCH branch, and the memo-stripping logic) is fully implemented and would trigger this exact behavior the moment a `bch.omft.near`-style token is added to the supported list.

### Impact Explanation
A self-transfer to the token's own origin-chain contract/deposit address is precisely the class of loss `DestinationAddressMatchesTokenAddressError` exists to prevent (funds sent to an address with no ability to be credited/recovered by the user, matching "funds delivered to a wrong address ... with no recovery"). Here the bug causes the signed `ft_withdraw` intent's `memo` to encode that dangerous address while the validation layer believes it is a different, safe address — a mismatch between what was validated and what was actually signed and broadcast to the relayer. This is repeatable for every BCH withdrawal attempt once BCH is supported by the bridge's token list.

### Likelihood Explanation
Preconditions: (1) POA bridge must list a BCH token (`bch.omft.near` or similar) with a non-`"native"` `origin_chain_address`, which is not yet the case based on current test fixtures/comments; (2) attacker must know or guess the token's `origin_chain_address` (a public field returned by `getSupportedTokens`) and prepend `bitcoincash:` to it. Both conditions are trivial for any user calling the public SDK once BCH is enabled — no privileged access, no relayer/RPC compromise needed. The current absence of a live BCH route in the POA bridge somewhat limits present-day exploitability, but the code is production code (not test/generated) that will silently reactivate the bug the moment BCH support is turned on.

### Recommendation
Normalize BCH CashAddr prefixes before comparison in `compareAddresses` (e.g., strip/lowercase `bitcoincash:` on both sides, mirroring the same stripping done in `createWithdrawMemo`), or better, share a single canonicalization function between `createWithdrawIntentPrimitive`/`createWithdrawMemo` and `compareAddresses`/`validateWithdrawal` so the address that is validated is guaranteed to be byte-identical to the address ultimately encoded in the signed memo.

import { PoaBridge } from "./poa-bridge";
import { createWithdrawIntentPrimitive } from "./poa-bridge-utils";
import { DestinationAddressMatchesTokenAddressError } from "../../classes/errors";

it("BCH prefix mismatch bypasses self-transfer check", async () => {
  vi.mocked(poaBridge.httpClient.getSupportedTokens).mockResolvedValueOnce({
    tokens: [{
      intents_token_id: "nep141:bch.omft.near",
      origin_chain_address: "qpm2qsznhks23z7629mms6s4cwef74vcwvy22gdx6a", // unprefixed
      min_withdrawal_amount: "0",
      // ...other required fields
    }],
  });

  const bridge = new PoaBridge({ envConfig, xrplRpcUrls: [] });

  // Side 1: validation passes (should have thrown)
  await expect(bridge.validateWithdrawal({
    assetId: "nep141:bch.omft.near",
    amount: 1000n,
    destinationAddress: "bitcoincash:qpm2qsznhks23z7629mms6s4cwef74vcwvy22gdx6a",
  })).resolves.toBeUndefined(); // BUG: expected to throw DestinationAddressMatchesTokenAddressError

  // Side 2: the signed memo equals the token's own origin_chain_address
  const intent = createWithdrawIntentPrimitive({
    assetId: "nep141:bch.omft.near",
    destinationAddress: "bitcoincash:qpm2qsznhks23z7629mms6s4cwef74vcwvy22gdx6a",
    destinationMemo: undefined,
    amount: 1000n,
  });
  expect(intent.memo).toBe("WITHDRAW_TO:qpm2qsznhks23z7629mms6s4cwef74vcwvy22gdx6a");
  // i.e. intent.memo's address === tokenInfo.origin_chain_address, a self-transfer
});

function createWithdrawMemo({
	receiverAddress,
	xrpMemo,
}: {
	receiverAddress: string;
	xrpMemo: string | undefined;
}) {
	// Strip "bitcoincash:" prefix from BCH CashAddr addresses
	const normalizedAddress = receiverAddress
		.toLowerCase()
		.startsWith("bitcoincash:")
		? receiverAddress.slice("bitcoincash:".length)
		: receiverAddress;

	const memo = ["WITHDRAW_TO", normalizedAddress];

	if (xrpMemo != null && xrpMemo !== "") {
		memo.push(xrpMemo);
	}

	return memo.join(":");
}
