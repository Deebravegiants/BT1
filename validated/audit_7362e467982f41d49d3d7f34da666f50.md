### Title
Crafted strategy route can poison the caller authorization tree and drain unrelated wallet assets - (File: `contracts/controller/src/strategies/swap.rs`)

### Summary

The controller accepts opaque `StrategySwap` bytes and forwards them to the configured router without decoding or constraining the pool/venue addresses embedded in the route. [1](#0-0) [2](#0-1)  A route-selected contract can request an unrelated `token.transfer(victim, attacker, amount)` beneath the caller’s `swap_collateral` authorization; simulation records that transfer as a child authorization, and executing with that signed tree transfers the victim’s wallet asset. [3](#0-2) [4](#0-3)  The controller’s exact input authorization and measured output checks bound only the routed collateral, not unrelated token transfers authorized deeper in the call tree. [5](#0-4) [6](#0-5) 

### Finding Description

`swap_collateral` authenticates `caller`, verifies that it owns or controls the account, and then withdraws the selected collateral before invoking the route. [7](#0-6) [8](#0-7)  `require_authorized_caller` applies `caller.require_auth()`, establishing a caller authorization root for the strategy invocation. [9](#0-8)  `swap_tokens` then authorizes only the controller-to-router transfer of `token_in`, but passes the attacker-controlled `swap` byte payload directly to `router.execute_strategy`. [2](#0-1)  That authorization protects the controller’s routed input; it does not prevent route-selected third-party code from requesting another token transfer from the original caller under the caller’s authorization tree. [10](#0-9) [11](#0-10)  The harness demonstrates the resulting authorization poisoning: recording mode places the unrelated wallet-token transfer under the caller’s `swap_collateral` entry, and enforcing mode executes it when that tree is signed. [12](#0-11) [13](#0-12) 

### Impact Explanation

A malicious route can steal arbitrary token balances from the strategy caller’s wallet while still returning valid swap output and leaving the lending operation successful. [14](#0-13)  The stolen asset need not be listed by the lending protocol, and neither the route minimum output nor the final account-risk check bounds the additional transfer. [15](#0-14) [16](#0-15)  This is direct theft of user funds, with the loss limited only by the token balances and malicious transfer amounts disclosed in the signed authorization tree. [17](#0-16) 

### Likelihood Explanation

The path is reachable through `swap_collateral`, and the same opaque route argument is accepted by `multiply`, `swap_debt`, and `repay_debt_with_collateral`. [18](#0-17) [19](#0-18)  An attacker must induce a user to submit a crafted route payload and sign the authorization tree that simulation returns, but an honest simulation includes the malicious child transfer rather than rejecting it. [20](#0-19) [21](#0-20)  The exploit does not require a compromised router, leaked key, privileged account, or protocol insolvency prerequisite; it relies on user-controlled opaque route bytes selecting executable third-party code. [2](#0-1) [22](#0-21) 

### Recommendation

Constrain executable route destinations to governance-allowlisted venue/pool contracts and token contracts before invoking the router, or change the strategy interface so the controller/router can validate and enforce that allowlist before executing the decoded payload. [23](#0-22) [22](#0-21)  Until venue allowlisting exists, clients must decode the route, simulate the complete transaction, and reject any authorization tree containing calls other than the expected strategy/input transfer; this is a client mitigation rather than an on-chain fix. [24](#0-23) 

### Proof of Concept

1. Alice creates a debt-free account and supplies USDC collateral.
2. The attacker deploys a contract whose invoked swap function calls `token.transfer(Alice, attacker, wallet_balance)` on an unrelated wallet token. [25](#0-24) 
3. Alice calls `swap_collateral(caller=Alice, account_id=AliceAccount, current=hubUSDC, amount=50_000_000_000, new=hubETH, swap=crafted_route)`, where `crafted_route` selects the attacker’s contract as a hop pool while still promising fair ETH output. [26](#0-25) 
4. Simulation records the attacker’s `wallet_token.transfer(Alice → attacker, WALLET_BALANCE)` as a child of Alice’s `swap_collateral` authorization. [27](#0-26) 
5. When Alice signs the recorded tree, the swap succeeds, Alice’s unrelated wallet-token balance becomes zero, the attacker receives `WALLET_BALANCE`, and Alice’s account receives the fair ETH output. [14](#0-13) [13](#0-12)

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {

    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),

            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),

/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
