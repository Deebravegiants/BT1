### Title
Webhook `shop` (and topic/webhook-id/api-version) identity is trusted from unauthenticated headers while only the raw body is HMAC-covered, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while the `shop`, `topic`, `webhook_id`, and `api_version` fields used to identify the tenant are read directly and unauthenticated from HTTP headers [2](#0-1) . `Registry.process` validates only that HMAC against the body, then forwards the header-derived `shop` straight to the app's handler as trusted tenant identity [3](#0-2) . This breaks the intended binding `shop-domain header == shop bound by the HMAC-signed payload`.

### Finding Description
The `HmacValidator.validate` call in `Registry.process` verifies `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)` [4](#0-3) . For `Webhooks::Request`, `to_signable_string` is simply the raw body bytes [1](#0-0) , so the signature says nothing about which shop, topic, webhook-id, or api-version accompanied that body — those come from `x-shopify-*`/`shopify-*` headers that are parsed with no cryptographic linkage to the signed content [5](#0-4) .

This is confirmed by contrast with `Auth::Oauth::AuthQuery`, the other `VerifiableQuery` implementer in this codebase: there, `shop` is explicitly folded into `to_signable_string` and thus bound by the HMAC [6](#0-5) . The webhook path has no analogous binding for `shop`.

Because the app's HMAC secret (`api_secret_key`) is the single shared secret for the whole app, valid `(raw_body, hmac)` pairs are freely computable/known for any request the attacker can get genuinely signed by Shopify for a shop they control (e.g., their own install of the target app, or any webhook they can trigger for their own store). An unprivileged internet user who operates their own shop can capture a genuinely-signed webhook `(raw_body, hmac)` from their own store, then replay it to the app's public webhook endpoint with the `x-shopify-shop-domain` header swapped to a victim shop. `HmacValidator.validate` still passes because it only checks the body/secret pair, and `Registry.process` forwards the attacker-chosen `shop` straight into `WebhookMetadata` used by the host app for tenant routing/authorization [7](#0-6) , exactly as the library's own documented usage pattern demonstrates (`shop_domain: data.shop`) [8](#0-7) .

### Impact Explanation
Any host application that follows this gem's documented pattern and uses `data.shop` from `WebhookMetadata` to select which merchant's session/access token/data record to update is exposed to cross-tenant confusion: an attacker-controlled body (from their own shop) can be attributed to a victim shop merely by forging a header, since the header carrying tenant identity is never authenticated by the gem's own HMAC check. This crosses the tenant boundary the HMAC check is meant to enforce and matches the cross-tenant-access impact category.

### Likelihood Explanation
Exploitability requires only: (1) the attacker possesses a legitimately app-signed webhook `(body, hmac)` pair for a shop they control (trivial for anyone who installs the app on their own dev/test store and triggers the relevant topic), and (2) the ability to POST to the app's public webhook endpoint with a crafted `x-shopify-shop-domain` header — no access token, secret, or privileged account is needed. This is realistically reachable by any unprivileged internet user who can install the target app.

### Recommendation
Bind the tenant/topic identity fields into the HMAC-verified content, or otherwise re-derive/cross-check `shop` from a source that Shopify itself protects (e.g., verify the shop domain is one currently associated with a registered/active install and cross-reference against a server-side record keyed by `webhook_id`/subscription rather than trusting the header value in isolation). At minimum, document loudly that `WebhookMetadata#shop`/`#topic`/`#webhook_id` are NOT covered by `HmacValidator.validate` and must not be used for authorization decisions without additional server-side verification (e.g., matching against the shop's known session/webhook registration).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a webhook topic (e.g. `orders/create`), capturing the raw POST body `B` and header `x-shopify-hmac-sha256: H` sent to the app's public webhook URL. `H` is a valid HMAC of `B` under the app's shared `api_secret_key`.
2. Attacker replays the exact same request to the same public webhook URL, but sets `x-shopify-shop-domain: victim.myshopify.com` (keeping body `B` and header `H` unchanged).
3. `ShopifyAPI::Webhooks::Request.new` parses `shop` as `victim.myshopify.com` from the header [5](#0-4) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (== `B`, unaffected by header change) and compares to `H` — validation succeeds [9](#0-8) .
5. `handler.handle` is invoked with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)` [10](#0-9) , and any host app logic keyed on `data.shop` (as shown in the gem's own docs) now acts as if this attacker-supplied body came from the victim shop.
