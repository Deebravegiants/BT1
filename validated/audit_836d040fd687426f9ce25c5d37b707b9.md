### Title
Missing upper-bound validation on `protocolFeeBps` in `IntentGatewayV2` param updates can permanently brick order placement - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentsBase._updateParams` (reached via a `UpdateParams` cross-chain governance message delivered through `onAccept`) writes the new `Params` struct — including `protocolFeeBps` — directly to storage after calling `_validateParams(update.params)`. While the per-destination fee override array is explicitly capped (`if (feeBps >= 10_000) revert InvalidInput();`), the base `protocolFeeBps` field on the primary `Params` struct is not visibly subjected to the same `< 10_000` bound in the code path that could be inspected. This mirrors the reported class of bug: a fee parameter that feeds directly into a subtraction (`originalAmount - protocolFee`) with no cap, where an out-of-range value causes underflow/revert rather than a validated, sane fee.

### Finding Description
`_updateParams` in [1](#0-0)  validates the incoming `Params` via `_validateParams(update.params)` and then unconditionally assigns `_params = update.params`. The destination-specific override loop explicitly enforces `feeBps < 10_000`: [2](#0-1) 

However, the top-level `protocolFeeBps` field of `_params` — the value actually consumed as the *default* fee whenever no destination override is set — has no confirmed equivalent bound applied before being stored. This is directly analogous to the original report: `minLicenseFee` exists but `maxLicenseFee` does not, and an out-of-range value flows into arithmetic that assumes a sane range.

Downstream, `placeOrder` in `IntentGatewayV2.sol` consumes this value without re-validating it: [3](#0-2) 
```
uint256 protocolFee = (originalAmount * protocolFeeBps) / 10_000;
uint256 reducedAmount = originalAmount - protocolFee;
```
If `protocolFeeBps` is ever set to `>= 10_000` (100%+), then for any `originalAmount`, `protocolFee > originalAmount`, and `reducedAmount = originalAmount - protocolFee` underflows. Solidity ≥0.8 reverts on unchecked-block-free underflow, so every subsequent `placeOrder` call with a nonzero input amount reverts.

The SDK layer independently treats an unbounded on-chain value as a real risk it must defend against: `readProtocolFeeHaircutBps` explicitly throws if the value read from the deployed gateway is `>= 10_000`, calling it "implausible" — [4](#0-3) , and `grossUpForProtocolFee`/`readProtocolFeeBps` in the quoting module add the same defensive guard client-side — [5](#0-4) . The existence of these off-chain guards suggests the contract's own on-chain enforcement of this invariant for the base `protocolFeeBps` field was not confirmed to be airtight at the point of assignment in `_updateParams`.

### Impact Explanation
If `protocolFeeBps` is ever pushed to `>= 10_000` (e.g. a governance encoding error, a decimal/bps unit mix-up, or a malformed `ParamsUpdate` message that passes whatever bound `_validateParams` does enforce for other fields but not this one), `IntentGatewayV2.placeOrder` becomes permanently unusable for any order carrying a nonzero input amount and a nonzero effective fee — a full denial of service on the intents gateway ("a route unable to deliver messages" / permanent freezing of the order-placement path) until another governance-gated `UpdateParams` message can be dispatched and delivered to correct it. Given the multi-hop, ISMP-relayed nature of this parameter update (dispatched from `pallet-intents-coprocessor`, relayed, and applied via `onAccept`), recovery requires another full cross-chain round trip while the gateway is bricked for ordinary users on that chain.

### Likelihood Explanation
Medium. This requires a `protocolFeeBps` value `>= 10_000` to reach `_params`, which is presumably gated by governance today, and the analog is only actionable if `_validateParams`'s existing checks do not already bound the base `protocolFeeBps` (I could not fully confirm the body of `_validateParams` from the index due to tool limits). It is nonetheless the same missing-cap bug class as the audit report, applied to the strongest analogous fee field reachable in this codebase — the `IntentGatewayV2` protocol fee — and the SDK's defensive re-checks suggest the authors themselves consider the on-chain value untrustworthy without independent bounding.

### Recommendation
Add an explicit `protocolFeeBps < 10_000` (and any relevant `surplusShareBps` equivalent) check inside `_validateParams`, mirroring the bound already applied to per-destination `destinationFeeBps` overrides in `_updateParams`. Consider also defining a stricter `maxProtocolFeeBps` ceiling (e.g. well below 10,000) so that even a "valid" but unreasonably high fee cannot be set, consistent with the original report's recommendation to pair `min`/`max` bounds on any governance-configurable fee.

### Proof of Concept
1. Governance/coprocessor dispatches an `UpdateParams` cross-chain message with `params.protocolFeeBps = 10_000` (or higher) and no destination-specific override.
2. `onAccept` → `_updateParams` calls `_validateParams(update.params)`; if this function does not bound `protocolFeeBps`, the update is accepted and `_params.protocolFeeBps = 10_000` is stored — see [6](#0-5) .
3. Any user calls `placeOrder` with a nonzero-amount input token and no per-destination fee override: [7](#0-6) 
4. `protocolFee = (originalAmount * 10_000) / 10_000 = originalAmount`; `reducedAmount = originalAmount - protocolFee = 0` (or reverts on underflow for `protocolFeeBps > 10_000`), causing either zero-value escrow corruption or an outright revert — bricking order placement until governance issues a corrective `UpdateParams` message.

export async function readProtocolFeeHaircutBps(evmRpcUrl: string, gatewayAddress: string): Promise<bigint> {
	const result = await rpcCall(evmRpcUrl, {
		id: 1,
		jsonrpc: "2.0",
		method: "eth_call",
		params: [{ to: gatewayAddress, data: SELECTOR_GATEWAY_PARAMS }, "latest"],
	})
	const hex = result.result
	if (typeof hex !== "string" || hex.length < 2 + 64 * GATEWAY_PARAMS_WORDS) {
		throw new PhantomRpcError(`IntentGateway.params() returned no usable result from ${gatewayAddress} on ${evmRpcUrl}`)
	}
	const start = 2 + 64 * GATEWAY_PARAMS_FEE_WORD
	const protocolFeeBps = BigInt(`0x${hex.slice(start, start + 64)}`)
	if (protocolFeeBps >= 10_000n) {
		throw new PhantomRpcError(`IntentGateway ${gatewayAddress} reports an implausible protocol fee: ${protocolFeeBps} bps`)
	}
	return protocolFeeBps
}

export async function readProtocolFeeBps(
	chainConfigService: ChainConfigService,
	source: IntentQuoteChainContext,
): Promise<bigint> {
	const gatewayAddress = chainConfigService.getIntentGatewayAddress(source.stateMachineId)
	if (!gatewayAddress || gatewayAddress === "0x" || gatewayAddress === zeroAddress) {
		throw new Error(`IntentGatewayV2 is not configured for chain ${source.stateMachineId}`)
	}

	const gatewayParams = (await source.client.readContract({
		address: gatewayAddress,
		abi: IntentGatewayV2.ABI,
		functionName: "params",
	})) as GatewayParams

	const protocolFeeBps = Array.isArray(gatewayParams)
		? BigInt(gatewayParams[4] as bigint | number | string)
		: BigInt((gatewayParams as GatewayParamsObject).protocolFeeBps ?? 0)
	if (protocolFeeBps < 0n || protocolFeeBps >= BPS_DENOMINATOR) {
		throw new Error(`Invalid IntentGateway protocol fee: ${protocolFeeBps} bps`)
	}
	return protocolFeeBps
}

/** Mirrors the gateway's floored fee deduction. */
export function deductProtocolFee(amount: bigint, protocolFeeBps: bigint): bigint {
	if (protocolFeeBps <= 0n) return amount
	const fee = (amount * protocolFeeBps) / BPS_DENOMINATOR
	return amount - fee
}

/** Conservatively grosses a net amount up so protocol-fee deduction cannot leave it short. */
export function grossUpForProtocolFee(netAmount: bigint, protocolFeeBps: bigint): bigint {
	if (protocolFeeBps <= 0n) return netAmount
	if (protocolFeeBps >= BPS_DENOMINATOR) throw new Error("protocolFeeBps must be less than 10,000")
	return divCeil(netAmount * BPS_DENOMINATOR, BPS_DENOMINATOR - protocolFeeBps)
