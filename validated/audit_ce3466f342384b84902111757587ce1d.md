### Title
Global `evm_version = "cancun"` compilation forces transient-storage opcodes onto IntentGatewayV2 deployments on chains that may not support Cancun, risking broken/undeployable app contracts - (File: evm/foundry.toml)

### Summary
`evm/foundry.toml` sets a single, project-wide `evm_version = "cancun"` (with `solc = "0.8.30"`) for every contract under `evm/src/**`, which is then deployed identically to a long list of heterogeneous EVM chains (Ethereum, Optimism, Arbitrum, Base, BSC, Gnosis, Soneium, Polygon, Unichain, Inkchain, Sei, Pharos) via the same deployment scripts. [1](#0-0) 
`IntentGatewayV2.sol` and its bases (`IntentsBase.sol`, `SolverAccount.sol`) contain multiple uses of transient storage (`tstore`/`tload`), a Cancun-specific EVM feature that did not exist prior to the Cancun/Dencun hardfork. [2](#0-1) 

This mirrors the reported bug class: compiling with a hardfork target newer than what some target deployment chains actually support results in contracts that either fail to deploy (invalid opcode at deploy-time bytecode validation) or, worse, deploy but behave unpredictably if the chain silently treats unsupported opcodes differently.

### Finding Description
Unlike the audited `LiquidityBorrowingManager.sol` case (which was about `PUSH0`/Shanghai), here the risk is broader: the project's single `foundry.toml` profile compiles *all* contracts — including `IntentGatewayV2`, an unprivileged, user/solver-reachable intents/escrow contract — with `evm_version = "cancun"`, which emits `TLOAD`/`TSTORE` (and potentially `MCOPY`) opcodes wherever the Solidity source uses transient storage. Not every chain the project targets for deployment (per `[rpc_endpoints]`/`[etherscan]` in the same file — BSC, Gnosis, Soneium, Polygon, Unichain, Inkchain, Sei, Pharos, Arbitrum) is guaranteed to have upgraded to full Cancun/Dencun opcode support at the time of deployment; several L2s/sidechains have historically lagged Ethereum L1 hardfork adoption (this is exactly the class of risk the original report flags for Arbitrum + `PUSH0`).

If a target chain's EVM does not yet recognize `TLOAD`/`TSTORE` (opcodes `0x5c`/`0x5d`), any call path in `IntentGatewayV2` that exercises transient storage will revert with an invalid-opcode exception. Because `IntentGatewayV2` is the intents escrow/order contract that end users and solvers directly call to create, fill, and settle cross-chain orders, a revert here on an affected chain means:
- The contract may still deploy (bytecode with unknown opcodes is generally accepted at deploy time; failure occurs at execution time when that specific code path runs), but core intents functionality (order creation/fill/settlement, guarded by the same transient-storage reentrancy/state pattern) becomes permanently broken for that chain's deployment.
- Funds already escrowed in the contract (source-chain deposits awaiting solver fulfillment) could become **permanently stuck** if the transient-storage-guarded function is the only path to release escrow, until a redeploy without the incompatible opcode. There is no fallback path in `IntentGatewayV2` that avoids the transient-storage-guarded logic once it is embedded in a shared internal function/modifier.

### Impact Explanation
If any of the currently-configured non-Ethereum target chains in `evm/foundry.toml` (`bsc`, `gnosis`, `soneium`, `polygon`, `unichain`, `inkchain`, `sei`, `arbitrum`, `pharos-testnet`) lack full TLOAD/TSTORE support at the EVM-execution level when `IntentGatewayV2` is deployed, user funds escrowed in the intents flow can be **permanently frozen** (High/Medium depending on which specific chain and whether the affected path gates fund release) since the reachable call is an unprivileged user/solver transaction into a token-custody contract — this satisfies the "permanent freezing of funds" acceptance bar.

### Likelihood Explanation
Medium. The team clearly deploys to a wide array of L2s/sidechains/alt-EVMs (visible from the extensive `[rpc_endpoints]`/`[etherscan]` chain list and the separate `tron/tronbox.js`, which explicitly pins `evmVersion: "istanbul"` for TRON precisely because TRON's TVM doesn't support newer opcodes — showing the team is otherwise aware of this exact hazard class but did not apply an equivalent per-chain `evm_version` override in `evm/foundry.toml` for the main EVM deployment, which uses one blanket `cancun` setting for every listed chain). [3](#0-2) 
Whether this actually triggers depends on the real-time Cancun/Dencun support status of each specific chain at deployment time, which cannot be fully confirmed from the codebase alone.

### Recommendation
- Do not use one global `evm_version` for all target chains in `evm/foundry.toml`. Use per-chain Foundry profiles (or a lower common-denominator target such as `paris`/`shanghai`) for any contract path that must deploy to chains without confirmed Cancun/Dencun support, mirroring the approach already taken for TRON (`evmVersion: "istanbul"`).
- Avoid using transient storage (`tstore`/`tload`) in shared library/base logic (`IntentsBase.sol`, `SolverAccount.sol`) that is compiled once and deployed to multiple chains with different opcode-support levels, or gate its use behind chain-specific feature detection/build variants.
- Before each multichain deployment, verify each target chain's actual EVM-execution opcode support (not just RPC availability) against the compiler's `evm_version` target.

### Proof of Concept
Not independently reproducible from static code alone since it depends on the live opcode-support status of each third-party chain; a Devin agent with terminal/RPC access should:
1. For each chain in `evm/foundry.toml`'s `[rpc_endpoints]` (`bsc`, `gnosis`, `soneium`, `polygon`, `unichain`, `inkchain`, `sei`, `arbitrum`, `pharos-testnet`), call `eth_getBlockByNumber("latest")`/chain docs to confirm Cancun/Dencun activation.
2. Deploy `IntentGatewayV2` (compiled with `solc 0.8.30`, `evm_version=cancun` per `evm/foundry.toml`) to a testnet fork of any chain lacking Cancun support and exercise the transient-storage-guarded function path to confirm an invalid-opcode revert. [4](#0-3) [3](#0-2)
