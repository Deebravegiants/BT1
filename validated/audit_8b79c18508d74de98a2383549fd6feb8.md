### Title
Insolvent-account repayment trim floors kept legs to whole debt-token units, making debt permanently unliquidatable when one debt unit exceeds the collateral-backed quote - ([File: contracts/controller/src/positions/liquidation/math.rs](contracts/controller/src/positions/liquidation/math.rs))

### Summary
The original Isomorph issue was a liquidatable-amount computation whose division truncated the result, leaving debt that could never be liquidated. XOXNO Lending contains the same bug class: on an insolvent account, `normalize_repayment_plan` trims any offered repayment above the collateral-backed quote via `process_excess_payment` with `keep_within_quote = true`, which floors the kept amount to whole debt-token base units (`div_floor(price).to_token_floor(decimals)`). If the quote is worth less than one base unit of every debt token the account owes, every possible offer is either trimmed to zero or is below the quote yet impossible to express in the token's granularity — so `liquidate` always reverts with `InvalidPayments`, and because the stuck collateral is typically worth more than the ~$5 `clean_bad_debt` dust ceiling, no permissionless path can clear the resulting bad debt.

### Finding Description
For an insolvent account (`total_collateral < total_debt`), `estimate_liquidation_amount` returns the collateral-backed quote `floor(C / (1 + base))`, and `normalize_repayment_plan` sets `insolvent = true` and trims any offered payment above that quote by calling `process_excess_payment(..., insolvent)` at `contracts/controller/src/positions/liquidation/math.rs:196-205`. Inside `process_excess_payment`, the `keep_within_quote` branch computes the kept leg as `usd.checked_sub(excess).div_floor(price).to_token_floor(decimals).min(entry.amount)` at `math.rs:668-672` — a floor to whole debt-token units — and drops the leg entirely when the result is zero (`math.rs:685-686`). The refunded offer is never pulled, and `liquidate` then reverts on the empty plan via `require_non_empty_payments` at `contracts/controller/src/positions/liquidation/mod.rs:66`.

The rescue mechanism `seize_all` (`math.rs:209-212`) requires `repay_usd > 0`, so it cannot fire once the trim has zeroed every leg. There is also no analog of `whole_unit_repayment` for insolvent accounts: `math.rs:188-191` applies the whole-unit quote raise only on the solvent path, so a quote that backs less than one whole debt unit is never promoted. The behavior is partially acknowledged in `docs/reference/formulas.md` ("a leg whose kept amount rounds to zero is dropped ... bad-debt cleanup takes the unbacked residue"), but that claim is false whenever the retained collateral exceeds the socialization dust threshold: permissionless `clean_bad_debt` requires `total_collateral <= 5 WAD` while the stuck collateral can be worth arbitrarily more (bounded only by one unit of the collateral token versus one unit of the debt token), and the alternative `force_socialize_bad_debt` is privileged.

### Impact Explanation
Permanent bad debt / protocol insolvency. Any liquidator calling `liquidate(liquidator, account_id, debt_payments, seize_mode)` on such an account reverts regardless of `debt_payments` or `SeizeMode` (the leg-dropping logic is mode-independent), so the unbacked debt can never be reduced by the only permissionless mechanism that touches it. Since the residual collateral exceeds the `clean_bad_debt` eligibility bound, the debt sits on the book indefinitely, overstating the market's borrow utilization and leaving suppliers' claims unbacked — exactly the "protocol will accumulate bad debt that is not liquidatable" impact of the reference report, realized through truncation to whole token units instead of insufficient division precision.

### Likelihood Explanation
Requires three conditions: an account becomes insolvent (collateral crash or accrued interest, no attacker action needed); every debt token the account owes has a base unit whose USD value exceeds the collateral-backed quote — natural for coarse-decimal assets (0–2 decimals, e.g. a token priced in the hundreds of dollars per unit) which the listing rules explicitly admit (`MIN_ASSET_DECIMALS = 0`); and the remaining collateral is worth more than ~$5, which holds precisely because a single debt unit already exceeds the quote. Any user can verify the state via `get_liquidation_estimate`, which reports a zero payment. No privileged access, timing, or oracle manipulation is required to reach the stuck state, though reaching insolvency is opportunistic rather than attacker-forced — consistent with a Medium/High severity for an insolvency-class rounding defect.

### Recommendation
On the insolvent path, mirror the fix suggested in the original report: avoid flooring the kept repayment to whole base units when doing so would leave the plan empty. Concretely, in `process_excess_payment` with `keep_within_quote = true`, compute the kept amount with ceiling-style rounding at the smallest representable unit (keep `max(1, kept)` when the pre-floor value is positive) or allow a kept leg priced at one base unit and let `seize_all` absorb the sub-unit gap. Alternatively, when the trim empties all legs on an insolvent account, promote the plan to a one-unit repayment against the collateral or route the position to bad-debt cleanup regardless of the `total_collateral <= 5 WAD` cap. The relevant code is `normalize_repayment_plan` and `process_excess_payment` in `contracts/controller/src/positions/liquidation/math.rs`.

### Proof of Concept
1. Governance lists a debt token `D` with 0 decimals priced at $2,000 per unit, and a collateral token `C` priced at $100 per unit with normal decimals and an 80% liquidation threshold.
2. A victim supplies 10 units of `C` ($1,000 collateral) and borrows 1 unit of `D` ($2,000 debt) — for example via near-limit LTV borrow followed by a collateral price drop, or simply after interest accrual — reaching `C_usd < D_usd` and `HF < 1`.
3. `estimate_liquidation_amount` takes the insolvent branch (`math.rs:186-188`): the quote is `floor(1000 / (1 + base)) ≈ $950`.
4. Any liquidator calls `liquidate(liquidator, victim_id, [(hub_d, 1)], SeizeMode::Transfer)` — the minimum possible offer, 1 unit worth $2,000. Since $2,000 > $950 quote, `process_excess_payment` runs with `keep_within_quote = true`; the kept amount is `floor((2000 - 1050) / 2000)` → `to_token_floor` at 0 decimals → `0`, so the leg is dropped, `repaid` is empty, `seize_all` stays false (`repay_usd == 0`), and `liquidate` reverts `InvalidPayments` at `mod.rs:66`.
5. No offer below 1 unit exists, and offering more units only deepens the refund. `clean_bad_debt` reverts because `total_collateral = $1,000 > 5 WAD`. The $2,000+accruing debt is permanently unliquidatable; only the privileged `force_socialize_bad_debt` can clear it.

This mirrors the existing unit test `an_insolvent_trim_drops_a_leg_whose_smallest_unit_exceeds_the_backed_quote` (`contracts/controller/tests/positions/liquidation_math.rs:858-868`), which demonstrates the dropped-leg/refunded-offer mechanics but stops short of checking that the account has no remaining permissionless resolution path.
