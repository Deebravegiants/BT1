### Title
Webhook `shop-domain` and `topic` headers are trusted but not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only signs the raw request body, while `shop`, `topic`, and `webhook_id` are read straight from unauthenticated HTTP headers and then trusted by `ShopifyAPI::Webhooks::Registry.process`. Since the same `api_secret_key` is shared across every shop that installs the app, a valid `(body, hmac)` pair obtained from any single real webhook delivery can be replayed against the same public webhook endpoint with a forged `shop-domain` (and/or `topic`) header, and the signature check will still pass.

### Finding Description
`Registry.process` validates the webhook exclusively via `Utils::HmacValidator.validate(request)`: [1](#0-0) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`, and for `Webhooks::Request` that method returns only the raw HTTP body — it does not include the shop, topic, or webhook id: [2](#0-1) 

Meanwhile, `shop`, `topic`, and `webhook_id` are pulled directly from attacker-controllable HTTP headers with no cryptographic binding to the signed body: [3](#0-2) 

After HMAC validation succeeds, `Registry.process` looks up the handler by `request.topic` and invokes it with `shop: request.shop` taken straight from those unauthenticated headers: [1](#0-0) 

The equality the HMAC is supposed to enforce is: `hmac == HMAC(secret, body ‖ shop ‖ topic)`. What is actually enforced is `hmac == HMAC(secret, body)`, then `shop`/`topic` are trusted independently. Because `api_secret_key` (`Context.api_secret_key`) is a single app-wide secret shared by all merchants using the app (not a per-shop secret), any entity that can obtain one legitimately-signed `(body, hmac)` pair — e.g., by installing the app on their own store and registering any webhook topic whose delivery they can observe on the app's own logs/replay it — can resend that exact body/hmac to the app's public webhook endpoint while substituting a different `shop-domain` header (a victim shop) and/or `topic` header. The HMAC check still passes because it never covered those fields, and the handler is invoked believing the event legitimately originated from the victim shop/topic.

### Impact Explanation
This breaks the tenant isolation the HMAC is supposed to guarantee for webhook delivery: a low-privilege actor (any merchant capable of installing the app once) can make the app process data as belonging to an arbitrary other shop or under an arbitrary registered topic. For mandatory compliance webhooks such as `shop/redact`, `customers/redact`, and `customers/data_request`, this can cause the handler to execute privacy-critical actions (e.g., redaction/deletion) against the wrong tenant, or let an attacker fabricate believable "shop X sent webhook Y" events to any handler registered by the host app. This is a cross-tenant identity-confusion vulnerability at the webhook-processing boundary.

### Likelihood Explanation
Exploitation requires no secrets, tokens, or privileged access — only the ability to (a) obtain a single valid `(body, hmac)` pair from any real webhook delivered to the target app (trivial for an attacker who installs the app themselves and triggers/observes any webhook), and (b) send an HTTP POST directly to the app's public webhook endpoint with modified `shopify-shop-domain`/`shopify-topic` headers. Nothing in the gem restricts the source IP or otherwise ties the delivery to Shopify's infrastructure, and the signable string is documented/implemented as body-only, so this is a straightforward, repeatable attack path.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signed material (or otherwise cryptographically bind them to the request, e.g., by requiring them as part of the same signed structure the way `AuthQuery#to_signable_string` binds `code`/`host`/`shop`/`state`/`timestamp`), so that any tampering with those headers invalidates the signature.

### Proof of Concept
1. Attacker installs the app on their own (attacker-controlled) shop `attacker.myshopify.com` and lets the app register a webhook, e.g. `customers/redact`.
2. Shopify delivers a real webhook to the app's endpoint with body `B` and header `shopify-hmac-sha256: H` computed as `HMAC-SHA256(api_secret_key, B)`, plus `shopify-shop-domain: attacker.myshopify.com`.
3. Attacker captures `(B, H)` (e.g., from their own server logs, since it was delivered to their own endpoint) and replays it directly to the same public webhook endpoint, but changes the header to `shopify-shop-domain: victim.myshopify.com` (and/or a different `shopify-topic`).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(api_secret_key, B)` — identical to `H` since the body is unchanged — and the check passes.
5. The registered handler for that topic is invoked with `shop: "victim.myshopify.com"` [4](#0-3) , even though the payload was never actually generated for `victim.myshopify.com`.
