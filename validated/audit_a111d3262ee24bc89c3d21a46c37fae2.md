### Title
Unprivileged single-transaction reserve-ratio manipulation corrupts PNL skim and LP mint/burn accounting - ([File: program/src/processor.rs])

### Summary
Raydium's constant-product AMM has no external price oracle, but `calc_take_pnl` effectively uses the pool's own instantaneous spot price (current vault reserves) as a "floor price" reference to decide how much value has appreciated since the last checkpoint (`target_orders.calc_pnl_x/calc_pnl_y`) and must be skimmed off into the `need_take_pnl_*` reserve. Because this spot price is read live from the coin/pc vault balances at the moment `Deposit`, `Withdraw`, or `WithdrawPnl` execute, and because Solana transactions can atomically chain a swap instruction immediately before it, an unprivileged actor can transiently distort the reserve ratio in the same transaction that triggers this pnl computation.

### Finding Description
`Calculator::calc_take_pnl` (aliased as `Processor::calc_take_pnl`) computes:
- `current_price = x1/y1` from live vault balances [1](#0-0) 
- `x2 = sqrt(last_k * current_price)`, `y2 = x2*y1/x1`, and takes `diff_x = x1-x2`, `diff_y = y1-y2` scaled by `pnl_numerator/pnl_denominator` as the amount to move from `total_pc/coin_without_take_pnl` into `amm.state_data.need_take_pnl_pc/coin` [2](#0-1) 

This function is invoked with fresh vault balances inside `process_deposit` at [3](#0-2)  and `process_withdraw` at [4](#0-3) , and the resulting *already-adjusted* `total_pc_without_take_pnl`/`total_coin_without_take_pnl` is what feeds the LP mint calculation in `Deposit` (`InvariantPool` at lines 1243-1250) and the LP burn/payout calculation in `Withdraw` (`InvariantPool` at lines 1751-1761). Because `x1`/`y1` are derived straight from `amm_coin_vault.amount`/`amm_pc_vault.amount` read at call time [5](#0-4) , an attacker who executes a large `SwapBaseIn`/`SwapBaseOut` immediately before `Deposit`/`Withdraw` in the same atomic transaction can force `current_price` far from the pool's fee-accrual baseline. This causes `calc_take_pnl` to slice off a `diff_x`/`diff_y` that reflects the attacker's own transient price distortion rather than genuine trading-fee profit, corrupting `total_pc_without_take_pnl`/`total_coin_without_take_pnl` before the mint/burn math consumes them, and permanently moving pool value into `need_take_pnl_pc/coin` (withdrawable only by the privileged `pnl_owner` via `process_withdrawpnl`, gated at [6](#0-5) ). This is the direct structural analog of the report's floor-price manipulation: a critical financial computation trusts a manipulable, unauthenticated, atomically-controllable price signal instead of a manipulation-resistant reference.

### Impact Explanation
LP depositors/withdrawers in the same block/transaction as the manipulation receive incorrect mint/burn amounts because the invariant math operates on a `total_pc_without_take_pnl`/`total_coin_without_take_pnl` pair that has been distorted by an attacker-chosen swap immediately prior. In the direction where `diff_x`/`diff_y` is inflated, real LP-backing reserves are shifted into the `need_take_pnl_*` bucket disproportionately, degrading the constant-product backing for all existing LP holders and effectively transferring pool value out of LP hands via the privileged pnl channel — an insolvency/fund-safety issue triggered entirely by an unprivileged party's chosen transaction ordering, not a genuine trading-fee event.

### Likelihood Explanation
Any unprivileged user can construct a single transaction containing a `SwapBaseIn`/`SwapBaseOut` (or `V2` variants) instruction followed by `Deposit` or `Withdraw` (and even `WithdrawPnl`, which anyone can trigger permissionlessly for accounting purposes even though payout is gated) targeting the same `AmmInfo`/vault accounts — all reachable with attacker-chosen amounts and no additional privilege, since these are the four standard swap instructions plus `Deposit`/`Withdraw` explicitly in scope.

### Recommendation
Do not let `calc_take_pnl` use the live, atomically-manipulable vault balances as the price reference for pnl skimming inside the same instruction that also uses those balances for LP mint/burn math. Either (a) snapshot/checkpoint the price used for pnl-taking independently of the current instruction's fresh reserve read, (b) require pnl-taking to occur in its own dedicated instruction executed at arm's length from swaps (with an anti-manipulation delay/checkpoint), or (c) bound the maximum single-transaction price deviation `calc_take_pnl` will act upon.

### Proof of Concept
1. Attacker submits one transaction with two instructions against the same AMM pool:
   - Instr 1: `SwapBaseIn`/`SwapBaseInV2` with a large `amount_in` (attacker-chosen) that pushes `amm_coin_vault`/`amm_pc_vault` far from their fee-accrual baseline ratio, per `swap_token_amount_base_in` math at [7](#0-6) .
   - Instr 2: `Deposit` (or `Withdraw`) on the same pool. `process_deposit`/`process_withdraw` immediately reads the just-mutated vault balances via `calc_total_without_take_pnl_no_orderbook` and feeds them into `calc_take_pnl` as `x1`/`y1` before computing `mint_lp_amount`/`coin_amount`/`pc_amount`.
2. Because `x1`/`y1` reflect the attacker's own swap rather than a manipulation-resistant checkpoint, `calc_take_pnl`'s `diff_x`/`diff_y` computation is skewed, causing an inflated/incorrect amount to be subtracted from `total_pc_without_take_pnl`/`total_coin_without_take_pnl` at [8](#0-7)  right before that same, now-corrupted total is used for the deposit/withdraw invariant math.
3. Repeating this pattern across pools/transactions systematically siphons LP-backing value into `need_take_pnl_pc/coin`, degrading LP token backing without a corresponding genuine trading-fee event.

    pub fn swap_token_amount_base_in(
        amount_in: U128,
        total_pc_without_take_pnl: U128,
        total_coin_without_take_pnl: U128,
        swap_direction: SwapDirection,
    ) -> U128 {
        let amount_out;
        match swap_direction {
            SwapDirection::Coin2PC => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (coin + amount_in) * (pc - amount_out) = coin * pc
                // => amount_out = pc - coin * pc / (coin + amount_in)
                // => amount_out = ((pc * coin + pc * amount_in) - coin * pc) / (coin + amount_in)
                // => amount_out =  pc * amount_in / (coin + amount_in)
                let denominator = total_coin_without_take_pnl.checked_add(amount_in).unwrap();
                amount_out = total_pc_without_take_pnl
                    .checked_mul(amount_in)
                    .unwrap()
                    .checked_div(denominator)
                    .unwrap();
            }
            SwapDirection::PC2Coin => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (pc + amount_in) * (coin - amount_out) = coin * pc
                // => amount_out = coin - coin * pc / (pc + amount_in)
                // => amount_out = (coin * pc + coin * amount_in - coin * pc) / (pc + amount_in)
                // => amount_out = coin * amount_in / (pc + amount_in)
                let denominator = total_pc_without_take_pnl.checked_add(amount_in).unwrap();
                amount_out = total_coin_without_take_pnl
                    .checked_mul(amount_in)
                    .unwrap()
                    .checked_div(denominator)
                    .unwrap();
            }
        }
        return amount_out;
    }
