### Title
Webhook `shop` (and `topic`) identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by verifying the HMAC over the raw request body, but the `shop` (and `topic`) values that are handed to the app's handler as the trusted tenant identifier are taken from unauthenticated HTTP headers that are never included in the signed payload. This is the same identity-binding class of bug as the report's `onlyOwner`/`onlyAllowedCaller` mismatch: the check that is performed (HMAC over body) does not cover the value that is actually acted upon (`shop`).

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers with no cryptographic binding to the body: [2](#0-1) 

`Registry.process` validates only this body-bound HMAC and then dispatches the handler using the unauthenticated `request.shop` and `request.topic`: [3](#0-2) 

`HmacValidator.validate` confirms it checks `verifiable_query.hmac` against `verifiable_query.to_signable_string` only: [4](#0-3) 

The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify" and that host apps receive `data.shop` as one of the trusted webhook fields: [5](#0-4) [6](#0-5) 

Because the HMAC is computed with the app's single shared `client_secret` across every shop that installs the app, any shop (including one an unprivileged attacker legitimately installs the app on, e.g. a free/dev store) can obtain a genuinely-signed `(raw_body, hmac)` pair from Shopify. The attacker can then replay that exact body+HMAC to the app's webhook endpoint while swapping the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header to any victim shop domain. `Utils::HmacValidator.validate` still succeeds because it never inspects the headers, and `Registry.process` forwards the forged `shop` to the handler as if it were authenticated.

**Identity binding broken:** `shop_covered_by_hmac == shop_used_by_handler` should hold, but here `shop_covered_by_hmac = ∅` (only body bytes are signed) while `shop_used_by_handler = header value`, so the equality fails and the two can diverge under attacker control.

### Impact Explanation
A host app that follows this gem's documented contract (trusting `data.shop`/`data.topic` from `WebhookMetadata` because `Registry.process` claims to "verify the request did indeed come from Shopify") can be made to process attacker-supplied webhook bodies under the identity of a victim shop it has no relationship with. Depending on how the host app keys its data (e.g., "create/update record for `data.shop`"), this enables cross-tenant data injection/corruption attributed to a shop the attacker doesn't control — a cross-tenant integrity break stemming directly from this gem's incomplete identity binding.

### Likelihood Explanation
Exploitation requires only: (1) the attacker installs the app on any shop they control (a normal, low-privilege action available to any internet user who can create a Shopify dev/free store), (2) capturing one genuine webhook HTTP request from their own shop, and (3) replaying it with a modified shop-domain header to the app's public webhook endpoint. No access to the app's `client_secret`, tokens, or victim credentials is required.

### Recommendation
Include the `shop` (and ideally `topic`) values in the HMAC-covered signable content, or independently verify the `shop`/`topic` headers against a source that is cryptographically tied to the request (e.g., have `Request#to_signable_string` incorporate the relevant headers, matching Shopify's message-authentication for these fields), and document clearly that consumers must not trust `data.shop`/`data.topic` unless such binding is enforced.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; Shopify sends a real webhook: body `B`, headers include `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B`) and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker replays this exact HTTP POST to the app's public webhook endpoint but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (and/or a different `X-Shopify-Topic`), keeping body `B` and `X-Shopify-Hmac-Sha256: H` unchanged.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` — validation succeeds (`lib/shopify_api/webhooks/registry.rb:190`, `lib/shopify_api/utils/hmac_validator.rb:12-31`).
4. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: parsed(B), ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), so the app processes attacker-controlled body content as if it belonged to `victim.myshopify.com`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
