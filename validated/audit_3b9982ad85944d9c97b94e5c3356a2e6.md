### Title
Webhook shop identity spoofed via unsigned `shopify-shop-domain` header — HMAC covers only the body, not the shop binding - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body alone, while the `shop` value dispatched to the app's webhook handler is read from an HTTP header that is never included in that signable string. This breaks the binding "shop authenticated == shop acted upon": the HMAC proves the body came from a holder of the API secret, but it proves nothing about which shop header accompanied that body.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (the raw body) and compares it against the `hmac-sha256` header value — the shop header plays no role in the signature: [3](#0-2) 

`Registry.process` validates only this body HMAC, then hands `request.shop` straight to the app's handler as the tenant identifier, with no additional check that this shop is the one that actually produced the signed body: [4](#0-3) 

Because the shop is not covered by the signature, any two values (body+hmac from one tenant, shop header claiming to be a different tenant) that satisfy the HMAC check will be accepted and passed to the handler as if they belonged together. This is exactly the identity-binding break called out in the rules: "a field acted on but not covered by the HMAC."

### Impact Explanation
A public/multi-tenant app receives a genuine `(raw_body, hmac)` pair from Shopify for any shop where the attacker has installed the app themselves (attackers can freely install public apps on their own development/trial stores and legitimately receive real, correctly-signed webhooks). Because the `shop` header is not part of the signed payload, the attacker can replay that valid `(raw_body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value naming a victim shop. `Registry.process` will pass HMAC validation (since only the body is checked) and will invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop domain, alongside body content the attacker actually controls (their own store's data). Any handler that uses `data.shop` as the tenant key for storage/lookup (the intended and documented use of `WebhookMetadata`) will attribute attacker-controlled webhook data to the victim tenant, i.e. cross-tenant data injection/corruption without ever needing the app's access token or client secret.

### Likelihood Explanation
Exploitation requires only the ability to (a) install the target app on an attacker-controlled shop to legitimately receive a signed webhook, and (b) send an arbitrary HTTP POST with attacker-chosen headers to the app's public webhook endpoint — both are available to any unprivileged internet user/merchant, no leaked secrets or privileged access needed. The likelihood is bounded only by whether the host application relies on `Registry.process`/`WebhookMetadata#shop` as its sole tenant-identity source, which is exactly what this gem's API surface encourages.

### Recommendation
Bind the shop identity to the signed payload rather than trusting an unsigned header:
- Include `shop` (and ideally `topic`, `webhook_id`) in the HMAC-signable string computed in `Request#to_signable_string`, matching what the app is expected to independently trust, or
- After HMAC validation, cross-check `request.shop` against a shop already known to be authorized for this app installation (e.g., verify a stored offline session/access-token exists for that shop) before dispatching to the handler, or
- At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be used as a sole tenant key without additional verification.

### Proof of Concept
1. Install the target public app on attacker-owned shop `attacker.myshopify.com`. Trigger a webhook topic the app subscribes to (e.g. `orders/create`) and capture the legitimate request: raw body `B`, header `shopify-hmac-sha256: H` (valid signature of `B` under the app's real secret), and header `shopify-shop-domain: attacker.myshopify.com`.
2. Send a new POST to the app's webhook endpoint with the same body `B` and the same `shopify-hmac-sha256: H`, but replace the header with `shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` builds successfully; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and succeeds — the forged shop header is never checked.
4. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the host app to process/store attacker-controlled webhook content under the victim tenant's identity. [5](#0-4)
