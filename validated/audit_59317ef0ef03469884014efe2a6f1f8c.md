### Title
Webhook shop/topic/webhook_id fields are not covered by HMAC verification, enabling cross-tenant webhook spoofing via replay - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating an HMAC over the raw request body, but the `shop`, `topic`, `webhook_id`, and `api_version` values that are trusted and forwarded to the app's handler are taken from unauthenticated HTTP headers that are never part of the signed content.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` computes/compares the HMAC exclusively over that signable string [2](#0-1) . However, `shop`, `topic`, `webhook_id`, and `api_version` are read directly from HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, `shopify-api-version`) with no cryptographic binding to the HMAC at all [3](#0-2) .

`Registry.process` validates only the HMAC, then trusts `request.topic` to select the handler and forwards `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` verbatim into `WebhookMetadata`, which the host application's handler acts on (e.g., to identify which tenant/shop the payload belongs to) [4](#0-3) . The documented handler contract explicitly exposes `data.shop` as "The shop domain of the webhook" for host apps to key their tenant logic on [5](#0-4) .

Because the HMAC only signs the body, an attacker who has legitimately received one valid `(raw_body, hmac)` pair (e.g., from their own shop's webhook subscription) can replay that exact body+hmac to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header for a different, target shop, or an arbitrary `x-shopify-topic`/`x-shopify-webhook-id` header. `HmacValidator.validate` will still return `true` since the body is untouched, yet `WebhookMetadata.shop`/`.topic` used by the handler carry unauthenticated, attacker-chosen values. This is structurally identical to the reported class of bug: the signed artifact (body/hmac) does not bind to the fields (`shop`, `topic`) that the downstream logic actually keys tenant identity or handler dispatch on, exactly as the Krystal report's `userOrder` was signed but not bound to the `ExecuteParams` actually executed.

### Impact Explanation
An unauthenticated internet attacker who possesses one valid webhook body+HMAC pair (trivially obtainable by installing the target app on their own store and capturing a real webhook delivery) can forge requests to the app's webhook endpoint that appear to originate from a different, arbitrary shop domain. Any host application that uses `WebhookMetadata#shop` to select which tenant's data to update (the exact pattern this gem documents and recommends) can be tricked into attributing attacker-controlled body content to another merchant's tenant — a cross-tenant data injection.

### Likelihood Explanation
Exploitation requires only that the attacker have access to their own shop's webhook stream (a normal capability of an unprivileged merchant/app installer) and can send arbitrary HTTP requests to the public webhook endpoint, which is by design internet-reachable. No credentials, access tokens, or `client_secret` are needed.

### Recommendation
Bind `shop`, `topic`, `webhook_id`, and `api_version` into the HMAC-signed content (or otherwise cryptographically verify these header values, e.g., cross-check `shop` against a known/allow-listed store, and validate `webhook_id` uniqueness/topic consistency against Shopify's registered subscription) before constructing `WebhookMetadata` and dispatching to handlers.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; capture one legitimate webhook POST, e.g. topic `orders/create`, body `{"id":1}"`, and its valid `x-shopify-hmac-sha256` header.
2. Replay the identical raw body and HMAC header to the app's webhook endpoint, but replace `x-shopify-shop-domain` with `victim.myshopify.com`.
3. `Registry.process` calls `HmacValidator.validate(request)` [6](#0-5)  — passes, since only the body is signed.
4. `WebhookMetadata.new(shop: request.shop, ...)` is built with `shop == "victim.myshopify.com"` [7](#0-6)  and passed to the app's handler, which processes attacker-controlled body content as if it belonged to `victim.myshopify.com`.
