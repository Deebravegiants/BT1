### Title
Webhook `shop` (tenant) header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes/validates the webhook HMAC over the raw body only, but the `shop`, `topic`, `webhook_id`, and `api_version` values that host applications use for tenant identification and routing come from unauthenticated headers. Anyone who can obtain one genuine `(raw_body, hmac)` pair — trivially, by installing the app on their own store, since the HMAC secret (`api_secret_key`) is shared across all shops of the app, not shop-specific — can replay that exact body+signature to the app's public webhook endpoint while swapping the `X-Shopify-Shop-Domain` header to a victim shop domain. The signature still validates because it never covered the header, and the host app's handler receives `WebhookMetadata#shop` set to the victim's domain.

### Finding Description
`Utils::HmacValidator.validate` calls `verifiable_query.to_signable_string`, and for webhooks that method is defined to return only `@raw_body` [1](#0-0) . The `shop` accessor, however, is pulled straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cross-check against the signed content [4](#0-3) . `Registry.process` uses exactly this unauthenticated `shop` value to construct the `WebhookMetadata` object handed to the app-defined handler [3](#0-2) . The documented handler contract explicitly tells app developers to trust `data.shop` as "The shop domain of the webhook" and to use it directly (e.g., `shop_domain: data.shop`) [5](#0-4) , so this gem is the boundary where the shop-identity binding is expected to be enforced but isn't.

The identity equality that should hold is: `shop attested in HMAC-signed content == shop delivered to the handler`. Instead the gem only enforces `HMAC(raw_body) == received_hmac`, leaving `shop` completely unbound to the signature.

### Impact Explanation
Because `api_secret_key` is one shared secret per app (not per shop), any unprivileged user who installs the app on a store they control can capture a fully valid `(raw_body, hmac)` pair from their own legitimate webhook deliveries. They can then replay this pair against the app's public webhook endpoint with an arbitrary `shop-domain` header pointing at a different, victim shop. Since the gem validates only the body's HMAC, `Registry.process` will accept the request and invoke the app's handler with `data.shop` set to the victim's domain and `data.body` containing the attacker-controlled (but originally-legitimate-for-attacker) payload. Any host application that follows the documented pattern of using `data.shop` to select the tenant record/session for processing (as shown in the gem's own docs) will apply the attacker's webhook body under the victim shop's identity — a cross-tenant data confusion/injection primitive.

### Likelihood Explanation
Exploitation requires only: (1) the ability to install the app on an attacker-controlled shop (normal, unprivileged install flow) to obtain one genuine signed webhook body/HMAC pair, and (2) the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with a forged header — both are unprivileged-internet-user actions with no access token, `client_secret`, or leaked credential needed.

### Recommendation
Bind the tenant-identifying header (and ideally `topic`/`webhook_id`) into the signable content, or independently verify that the `shop-domain` header matches a shop value embedded in/derivable from the signed body (e.g., cross-check against the resource owner returned by looking up the webhook subscription by `webhook_id` via the Admin API) before trusting `request.shop` in `WebhookMetadata`.

### Proof of Concept
1. Install the app on attacker-owned shop `attacker.myshopify.com`; trigger a webhook (e.g., `orders/create`) and capture the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sends — this HMAC is valid because it's computed with the app's single shared `api_secret_key`.
2. Replay this exact request to the app's webhook endpoint, keeping `raw_body` and `X-Shopify-Hmac-Sha256` unchanged, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request#hmac`/`#to_signable_string` only reference the body [6](#0-5) , so `Utils::HmacValidator.validate` returns `true`.
4. `Registry.process` builds `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: <attacker's data>, ...)` and invokes the host app's handler [7](#0-6) , which — per the gem's documented usage — will process/persist the attacker's payload under the victim shop's tenant context.
