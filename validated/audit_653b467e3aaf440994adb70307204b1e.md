### Title
Webhook `shop` identity is not bound to the HMAC signature, allowing shop-spoofing on genuinely-signed webhook payloads - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats `Utils::HmacValidator.validate(request)` as proof that a webhook request is authentic for the shop it claims to be from. In reality, the HMAC only covers the JSON body, not the `shop-domain` header, so the "shop" identity that is handed to the app's handler is unauthenticated.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` computes/compares the HMAC exclusively over that signable string: [2](#0-1) 

`request.shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic tie to the HMAC: [3](#0-2) 

`Registry.process` validates the HMAC and then forwards the unauthenticated `request.shop` straight into `WebhookMetadata`, which the app's handler is documented to trust as "the shop domain of the webhook": [4](#0-3) [5](#0-4) 

The identity binding that should hold is: `shop authenticated by HMAC == shop delivered to the handler`. Because the HMAC is computed with the app-wide `api_secret_key` over the body only, and every shop that installs the app shares that same secret, `Utils::HmacValidator.validate` proves only "this body was signed with our app's secret" — it does not prove "this body came from the shop named in this header." Any actor who can obtain one genuinely-signed webhook (e.g., a merchant/developer on their own store, or anyone who owns/controls a shop with the app installed) can replay that exact `raw_body` + `hmac` pair to the app's webhook endpoint while substituting an arbitrary value for the `shopify-shop-domain` header. `HmacValidator.validate` still returns `true` (it never inspects `shop`), and `Registry.process` will happily construct `WebhookMetadata` claiming the payload belongs to whatever shop the attacker put in the header.

### Impact Explanation
This breaks the shop-authenticated vs. shop-used-as-tenant-key equality that host applications rely on to scope data by tenant. If a host app uses `data.shop` from the documented `WebhookMetadata` (as shown in the gem's own webhooks doc) to select which merchant's session/access token/row to update, an attacker can cause events genuinely signed for their own shop to be attributed to (and processed as) a different, victim shop — i.e., cross-tenant data confusion/corruption using only the attacker's own legitimately-issued webhook traffic. No access token, `client_secret`, or privileged access is required; only receipt of one webhook to a shop the attacker controls (trivially achievable by installing/using the app on their own store).

### Likelihood Explanation
Any user with the ability to have the app installed on a shop they control receives valid `(body, hmac)` pairs from Shopify. Forging the `shop` header on the replayed request is a one-header change requiring no cryptographic material beyond what the attacker legitimately possesses (their own signed webhook). This is fully triggerable by an unprivileged internet user with a store, over the internet, against the app's public webhook endpoint.

### Recommendation
Bind `shop` (and ideally `topic`) into the value that is HMAC-verified, or otherwise authenticate the shop out-of-band before trusting it — e.g., include the shop domain and topic in `to_signable_string`, or require `Registry.process` to cross-check the header-derived `shop` against a per-shop webhook secret / a shop registered for that specific webhook subscription, instead of relying on the single, app-wide secret to vouch for shop identity.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and registers for `orders/create`.
2. Attacker triggers an order, and Shopify sends a webhook request to the app with body `B`, `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker (as the receiver of their own webhook) resends the exact same `B`/`H` to the app's webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-22`) passes because it only checks `B` against `H`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) invokes the app handler with `WebhookMetadata` whose `shop` is `victim-shop.myshopify.com`, even though the payload actually originated from `attacker-shop.myshopify.com`.
