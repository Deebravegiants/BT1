### Title
Webhook `shop-domain` header (and `topic`/`webhook-id`) is trusted for tenant routing without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only signs the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers and passed downstream to the app's webhook handler without any cryptographic binding to the verified payload.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook solely via `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` — implemented as `@raw_body` only: [1](#0-0) 

Meanwhile `shop`, `topic`, and `webhook_id` are pulled straight out of the (attacker-controllable, unsigned) headers: [2](#0-1) 

After HMAC validation succeeds, `Registry.process` forwards `request.shop` (and `request.topic`) directly to the app-supplied handler as the tenant identifier, with no further correlation to the signed body: [3](#0-2) 

The intended binding is: *bytes cryptographically verified* (`raw_body` + `hmac`) == *bytes used to identify which tenant the event belongs to* (`shop` header). Because `shop` is outside the signed material, that equality never actually holds — the gem simply assumes the header is trustworthy. Any party who can obtain one valid `(raw_body, hmac)` pair — trivially available to any merchant who installs the app on their own store, since they will receive legitimate webhooks for their own shop with a valid HMAC over the body — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. The HMAC check still passes (it only checks the body), but the handler will process the event as if it originated from the victim shop named in the forged header.

### Impact Explanation
This is a cross-tenant identity-binding failure: an unprivileged app user (a merchant who has legitimately installed the app and can therefore harvest one valid signed webhook body) can inject fabricated webhook events attributed to any other shop by simply changing the shop-domain header. Any host application logic that trusts `WebhookMetadata#shop` to look up sessions, update records, or take action "on behalf of" that shop (as documented in `docs/usage/webhooks.md`) can be manipulated into acting on a victim tenant's data using attacker-supplied event content, i.e., cross-tenant access/injection.

### Likelihood Explanation
Likelihood is limited by the fact that Shopify's real webhook infrastructure only ever sends webhooks with the correct shop-domain header for the shop that generated them — a passive attacker cannot normally cause Shopify to send a webhook for shop B with body content of shop A. However, this gem does not defend against a hostile actor who directly POSTs to the app's public webhook endpoint outside of Shopify's delivery pipeline: since the HMAC never covers `shop`/`topic`/`webhook-id`, any attacker with knowledge of one valid `(body, hmac)` pair (obtainable by installing the app on their own store) can forge the routing headers freely and have them accepted as authentic by `Registry.process`.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signed material (or otherwise cryptographically bind them to the verified body) before `Registry.process` extracts and forwards them to handlers — mirroring the same-tenant guarantee this gem already enforces for OAuth's `AuthQuery#to_signable_string`, which does sign `shop` (`lib/shopify_api/auth/oauth/auth_query.rb`, lines 33-43). At minimum, document loudly that `WebhookMetadata#shop` is not authenticated and must not be trusted for tenant-sensitive operations without independent verification.

### Proof of Concept
1. Install the app on an attacker-controlled shop `attacker.myshopify.com`; trigger any subscribed webhook topic, capturing the raw request body `B` and the valid `x-shopify-hmac-sha256` header `H` that Shopify computed over `B` using the app's `client_secret`.
2. Replay the exact request to the app's webhook endpoint, keeping body `B` and header `H` unchanged, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `B` — it passes because `B` and `H` are unmodified: [4](#0-3) 
4. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built with `shop == "victim.myshopify.com"` and passed to the app's handler, even though the payload data actually originated from the attacker's own shop.
