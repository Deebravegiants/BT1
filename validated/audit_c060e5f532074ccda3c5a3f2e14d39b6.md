The unauthenticated `shop` header is then propagated directly into `WebhookMetadata` and handed to the app's handler as the tenant identifier [3](#0-2) [4](#0-3) , and the gem's own documentation instructs apps to use `data.shop` directly to key business logic (e.g., `shop_domain: data.shop`) [5](#0-4) .

### Title
Webhook shop-domain header is not covered by HMAC, allowing cross-tenant spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, never including the `x-shopify-shop-domain` (or `shopify-shop-domain`) header. `Registry.process` validates only that HMAC and then trusts the header value as the shop for handler dispatch, breaking the equality `shop authenticated by HMAC == shop delivered to the handler`.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the HMAC over `verifiable_query.to_signable_string`, and for webhooks that string is defined as just `@raw_body`: [6](#0-5) [7](#0-6) 

The `shop` accessor is read straight from an HTTP header with no cryptographic binding to the signature: [8](#0-7) 

`Registry.process` only checks the HMAC validity, then immediately forwards `request.shop` (the unauthenticated header) into `WebhookMetadata` and on to the registered handler: [9](#0-8) 

Because the HMAC secret (`Context.api_secret_key`, the app's single `client_secret`) is shared across every shop that installs the app, any merchant that has installed the app can trigger a genuine, validly-signed webhook for their own store, capture the raw body and its valid HMAC, then replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header naming a different, victim shop. `HmacValidator.validate` will still pass (it never looks at the header), and the handler will receive `data.shop` set to the attacker-chosen victim domain. The gem's own documented usage pattern encourages apps to key their business logic on `data.shop` directly: [5](#0-4) 

This breaks the identity binding that the shop asserted in the transport-level header must equal the shop bound into the cryptographically verified payload — the header is a field acted upon (tenant routing) but not covered by the HMAC.

### Impact Explanation
An attacker (any merchant who installs the app on their own store) can forge webhook events attributed to a different tenant shop of their choosing. Since apps commonly use `data.shop` to look up/update per-tenant records, enqueue tenant-scoped jobs, or make API calls against that shop's stored session/access token, this enables cross-tenant data confusion/injection — e.g. injecting fabricated order/customer/redact events into another merchant's data pipeline, or triggering `customers/redact`/`shop/redact` compliance workflows against a shop that never sent them. This matches the "cross-tenant access" Critical impact category, since the attacker's traffic is attributed to a shop it does not own.

### Likelihood Explanation
Likelihood is high: no privileged credentials, access tokens, or `api_secret_key` knowledge are required — merely installing the app on any shop (which is the app's normal, open onboarding flow) is enough to obtain a validly-HMAC-signed webhook body. Forging the header afterward is a trivial HTTP replay.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a webhook subscription (e.g. `orders/create`).
2. Shopify sends a webhook to the app's endpoint with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)` — the same `client_secret` is used for all shops on the app.
3. Attacker captures `B` and `H` (e.g., via a local test webhook or side channel they control).
4. Attacker POSTs directly to the app's public webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged, still valid), but `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because only `B` is checked [6](#0-5) .
6. The handler receives `WebhookMetadata` with `shop == "victim-shop.myshopify.com"` [3](#0-2)  and processes the forged event as if it originated from the victim shop.
