### Title
Excess native token (`msg.value`) overpayment is never refunded in `placeOrder`, permanently trapping user funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder()` accepts native token (`msg.value`) to cover native-token order inputs and, optionally, the solver/relayer fee swap via Uniswap. Unlike the canonical EVM implementation, it never refunds any leftover `msg.value` to the caller after escrowing inputs and paying fees, so any overpayment is stranded in the contract.

### Finding Description
`placeOrder` tracks `uint256 msgValue = msg.value;` and decrements it as it consumes native tokens for `predispatch.assets`, `order.inputs`, and `order.fees` (via the Uniswap `swapETHForExactTokens` call). At the end of the function, however, there is no `_sendValue(msg.sender, msgValue)` or equivalent refund of the remaining `msgValue`. [1](#0-0) [2](#0-1) 

This is a direct regression compared to the primary EVM `IntentGatewayV2.sol`, which explicitly refunds unspent native tokens to the caller after escrow and fee handling:
```solidity
// Refund any unspent native tokens to the user.
if (msgValue > 0) {
    _sendValue(msg.sender, msgValue);
}
``` [3](#0-2) 

The Tron contract's `placeOrder` ends with the `OrderPlaced` event emission and `return` with no corresponding refund step for `msgValue`. [4](#0-3) 

Because `swapETHForExactTokens{value: msgValue}(order.fees, ...)` is called with the *entire remaining* `msgValue` (not just the exact amount needed), Uniswap only consumes what is required to buy `order.fees` worth of the fee token and refunds the surplus ETH back to the caller of the swap — i.e., to the `IntentGatewayV2` contract itself, not the original user. That surplus (and any leftover `msgValue` when `order.fees == 0`) then sits permanently in the contract's balance, unreachable via any user-facing function.

### Impact Explanation
Any user who overestimates the required `msg.value` when calling `placeOrder` (e.g., using the same "amount + fee buffer" pattern documented for the standard EVM version, or from a quoting/slippage mismatch) permanently loses the excess native token. There is no reachable function in the Tron `IntentGatewayV2` that returns this trapped balance to the depositor; the contract has no user-triggered sweep/refund path for the native token. This is a straightforward path to permanent freezing/loss of user funds reachable from a single unprivileged `placeOrder` call, matching the severity class of the referenced report (Medium — unvalidated `msg.value` leading to loss of excess value).

### Likelihood Explanation
Likelihood is fairly high in practice: users/integrators must pass `msg.value` exactly matching consumed native amounts to avoid loss, with no protocol-enforced equality check (`InvalidInput` is not raised on `msgValue > 0` after processing). Any client that reproduces the "amount + nativeFee buffer" UX pattern documented elsewhere in this repo for other contracts (e.g., WrappedHyperFungibleToken's WETH mode) risks stranding funds here, since this specific Tron contract silently keeps the surplus instead of reverting or refunding.

### Recommendation
At the end of `placeOrder` (and any other payable entry point in `evm/tron/contracts/apps/IntentGatewayV2.sol` that accumulates a decremented `msgValue`), add a refund of any leftover native balance to `msg.sender`, mirroring the primary EVM implementation's `_sendValue(msg.sender, msgValue)` pattern used in `evm/src/apps/IntentGatewayV2.sol`. Alternatively, require `msgValue == 0` after all consumption steps and revert otherwise, to force exact payment and eliminate any surplus-retention ambiguity.

### Proof of Concept
1. User calls `placeOrder(order, graffiti)` with a native-token input (`order.inputs[i].token == bytes32(0)`) and sends `msg.value = order.inputs[i].amount + 1 ether` (accidental overpayment or defensive buffering as documented elsewhere in the SDK).
2. Inside `placeOrder`, `msgValue` is decremented only by the exact required amount for `order.inputs[i].amount`: `msgValue -= order.inputs[i].amount;`. [5](#0-4) 
3. If `order.fees == 0`, the `if (order.fees > 0)` fee-swap branch is skipped entirely, leaving the full `1 ether` surplus in `msgValue` untouched. [6](#0-5) 
4. Function completes, emitting `OrderPlaced`, with no refund of the residual `1 ether`, which remains locked in the `IntentGatewayV2` contract's native balance with no user-callable withdrawal path. [7](#0-6)
