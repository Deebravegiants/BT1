### Title
Webhook shop-domain header is not covered by HMAC, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC signature validated by `Utils::HmacValidator.validate` in `Registry.process` binds solely to the request body. The `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are read directly from unauthenticated HTTP headers and are never included in the signed data, yet `Registry.process` forwards `request.shop` to the app's handler as the authenticated tenant identity.

### Finding Description
`lib/shopify_api/webhooks/request.rb` L20-23 defines `shop` as `shopify_header("shop-domain")`, sourced straight from request headers with no cryptographic binding. `to_signable_string` (L35-38) returns `@raw_body` alone. `Utils::HmacValidator.validate_signature` (`lib/shopify_api/utils/hmac_validator.rb` L26-31) computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it only against the body-derived signable string. In `Registry.process` (`lib/shopify_api/webhooks/registry.rb` L188-199), once `Utils::HmacValidator.validate(request)` passes, the code immediately builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` and calls the app handler — using the unauthenticated `shop` header as if it were verified.

The identity binding that should hold is: `shop authenticated by HMAC == shop delivered to handler`. In fact the equality that holds is only `HMAC(raw_body, client_secret) == received_hmac`; the `shop` header is completely outside that equality. Because a single app's `client_secret` is shared across every merchant/shop that installs the app, any shop that has legitimately installed the app can capture a genuine webhook delivery (valid body + valid HMAC computed with the shared `client_secret`), then replay that same body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header with a different, victim shop's domain. `Registry.process` will accept it as valid (the HMAC check only inspects the body) and hand the handler a `WebhookMetadata` claiming the body originated from the victim shop.

### Impact Explanation
This breaks the tenant boundary the gem is documented to enforce. `docs/usage/webhooks.md` explicitly tells developers that `Registry.process` "will verify the request did indeed come from Shopify" and that `data.shop` is "The shop domain of the webhook" — developers are expected to trust `data.shop` for shop-scoped side effects (the doc's own example does `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`). An attacker controlling one legitimate installation can forge webhook deliveries attributed to any other shop using the app, causing cross-tenant data corruption/injection (e.g., orders/products/customer data processed under the wrong shop's tenant context) purely by exploiting this gem's `Request`/`Registry` verification contract, without needing the target's access token or `client_secret`.

### Likelihood Explanation
Likelihood is high for any app author who follows the documented usage pattern: any existing (even low-privilege, free-tier) install of the target app gives the attacker a valid body+HMAC pair signed with the app's real (shared) `client_secret`; forging headers on an HTTP POST requires no special access.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) headers in the signable data verified by HMAC, or bind the verified body to the header-derived shop via a canonical string that Shopify itself signs, or require host apps to disregard `data.shop` in favor of information already validated in the trusted body — but the safer fix is to make `Webhooks::Request#to_signable_string` incorporate the identity fields it exposes on `WebhookMetadata`, so verification failure invalidates the whole tuple, not just the body.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and `victim-shop.myshopify.com` (attacker only needs presence of any install of the app that gets a normal webhook delivered to it, or attacker's own dev/trial shop with the app installed).
2. Shopify delivers a genuine webhook to the attacker's shop endpoint: `raw_body = B`, `Shopify-Hmac-Sha256: H = HMAC-SHA256(client_secret, B)`.
3. Attacker captures `(B, H)` and POSTs it to the app's webhook route with headers changed: `Shopify-Shop-Domain: victim-shop.myshopify.com`, keeping `Shopify-Hmac-Sha256: H` and body `B` unchanged.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds successfully (`lib/shopify_api/webhooks/request.rb` L45-63).
5. `Registry.process` calls `Utils::HmacValidator.validate(request)` — `validate_signature` recomputes `HMAC(B, client_secret)` = `H`, matches, returns `true` (`lib/shopify_api/utils/hmac_validator.rb` L26-31).
6. `Registry.process` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and invokes the app's handler, which — per the documented pattern — treats `data.shop` as the authenticated tenant, applying body `B`'s content to the wrong shop's tenant data.
