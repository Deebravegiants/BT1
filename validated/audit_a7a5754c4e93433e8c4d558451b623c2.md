### Title
Webhook `shop` (and `topic`/`webhook-id`) identity is not covered by the HMAC signature, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `api_version`, and `webhook_id` are read from unsigned HTTP headers. `Registry.process` trusts `request.shop` for tenant identification after validating only the body's HMAC. This mirrors the Perpetual bug pattern: a value that is acted upon (`shop`, used to route/attribute the webhook event) is not part of the data actually covered by the authentication check (the HMAC), so the "authenticated bytes" and "bytes trusted for identity" are not equal.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhook requests, `to_signable_string` returns only `@raw_body`: [2](#0-1) 

But `shop`, `topic`, `api_version`, and `webhook_id` are parsed straight from HTTP headers, which are never included in the signed content: [3](#0-2) 

`Registry.process` validates only this body HMAC, then unconditionally trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the `WebhookMetadata` that is handed to the app's handler as the authoritative tenant/event identity: [4](#0-3) 

Because the app's `api_secret_key` is shared across every shop installing the app (it is not a per-shop secret), any request whose **body** hashes correctly under that shared secret will pass HMAC validation regardless of which `shop`, `topic`, or `webhook_id` header is attached. An unprivileged party who can obtain (or produce) any single valid `(raw_body, hmac)` pair for the app — e.g. from their own shop's legitimate webhook deliveries — can freely swap the `x-shopify-shop-domain` header to name an arbitrary victim shop, and `Registry.process` will still accept it as validated and forward it to the handler as if it came from that victim shop.

This is the exact analog of the reported bug class: the field that identity/authorization decisions are made on (`shop`) is not bound by the same cryptographic check that is used to establish trust (the body HMAC).

### Impact Explanation
This breaks the equality `shop authenticated by HMAC == shop trusted by the handler for tenant routing`. An attacker (any user who can trigger/capture at least one valid webhook body+HMAC pair for the shared app secret, e.g., by installing the app on their own shop) can forge webhook deliveries attributed to a different, arbitrary shop domain. Depending on how the host application uses `WebhookMetadata.shop` (e.g., to look up sessions, trigger data deletion, toggle settings, or process GDPR/compliance actions for "that shop"), this enables cross-tenant data manipulation — a Critical-severity outcome per the impact taxonomy (cross-tenant access).

### Likelihood Explanation
Exploitability requires only: (1) being a legitimate/unprivileged user of the app on some shop who can observe at least one real webhook delivery (topic + raw body + `x-shopify-hmac-sha256`), and (2) resending it with a modified `shop`/`topic`/`webhook-id` header set naming the victim. No access token, `client_secret`, or privileged account is required — only externally observable webhook traffic and the ability to make an HTTP POST to the app's public webhook endpoint. Topics with static or shop-independent bodies (e.g., minimal `{}` payloads) make this trivial; even topics with body content are exploitable if the attacker's own shop can produce a body byte-for-byte identical (or the app only inspects the header `shop`, which is common).

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the value that is HMAC-verified (or independently bind the header-derived `shop` to a value cryptographically tied to the request, e.g. requiring the app to cross-check `shop` against its own session/shop lookup rather than trusting the header verbatim). At minimum, document prominently that `Registry.process`'s `shop` is unauthenticated and must be revalidated by the host application against its known merchant list before being used for any tenant-scoped action.

### Proof of Concept
1. App installed on `attacker.myshopify.com`; attacker triggers/observes a legitimate webhook delivery with topic `T`, raw body `B` (e.g., `{}`), and header `x-shopify-hmac-sha256: H` — valid because `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker resends an HTTP POST to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256: H` (unchanged)
   - Header `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
   - Header `x-shopify-topic: T`
3. `ShopifyAPI::Webhooks::Request.new` parses headers, and `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(api_secret_key, B)`, which equals `H` — validation succeeds: [5](#0-4) 
4. `Registry.process` calls the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: T, body: parsed_body, ...)`, and the app acts as if the event genuinely originated from `victim-shop.myshopify.com`.
