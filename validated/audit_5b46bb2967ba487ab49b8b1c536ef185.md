### Title
Missing recipient validation before burn in `HyperFungibleToken.send` can permanently freeze bridged funds - (File: `sdk/packages/core/contracts/apps/HyperFungibleToken.sol`)

### Summary
`HyperFungibleToken.send` burns the caller's tokens and dispatches a cross-chain POST request without validating that `params.to` decodes to a usable, non-zero recipient address. This mirrors the reported `mintForToken` issue: a state-changing, fund-affecting function accepts an unchecked "to" and only surfaces the problem later, after value has already left the user irrevocably.

### Finding Description
`send()` performs `_burn(msg.sender, params.amount)` immediately, then packages `params.to` verbatim into the cross-chain `Message.to` field and dispatches the request — there is no check that `params.to` is a valid, non-zero 20-byte address at this point: [1](#0-0) 

Validation of the recipient only happens on the destination chain inside `onAccept`, via `_toAddr`, which only checks the byte length (must be exactly 20) — it does not reject the all-zero address: [2](#0-1) [3](#0-2) 

If `params.to` decodes to `address(0)` (e.g. `abi.encodePacked(address(0))`, a common caller mistake or a bug in an integrating frontend/relayer/router that forwards a zero recipient), `onAccept` will call `_mint(address(0), amount)`. OpenZeppelin's ERC20 `_mint` explicitly reverts on a zero-address receiver (`ERC20InvalidReceiver`), confirmed present in the compiled contract's ABI/errors used by the SDK bindings. This means the destination-side mint can never succeed for that message.

Because the burn on the source chain already happened inside the same `send()` call, before any of this is known, the tokens are gone from the source chain's supply. The only recovery path is the timeout refund in `onPostRequestTimeout`, which re-mints to the original sender: [4](#0-3) 

but this requires the caller to have set a non-zero `params.timeout` and for that timeout window to elapse and be proven via `HandlerV2.handlePostRequestTimeouts`. Several call sites in the test-suite and documented usage pass `timeout: 0`: [5](#0-4) 

If `timeout == 0` is treated by the dispatcher/host as "no timeout" (never expires), a request whose destination `to` is the zero address can never be delivered (perpetual revert) and can never time out — the burned funds are permanently unrecoverable.

### Impact Explanation
Any unprivileged caller of `send()` (or a relayer/router/composability layer built on top of `HyperFungibleToken`/`BridgeToken`) that passes a zero recipient address burns real value on the source chain that can never be minted on the destination chain, and — absent a finite timeout — can never be refunded either. This is a permanent loss of user funds via a self-inflicted or integrator-caused zero-address parameter, exactly the class of bug flagged in the original `mintForToken` report: an externally reachable function performs an irreversible transfer-affecting action without validating the recipient.

### Likelihood Explanation
`send()` is a fully public, unprivileged entry point on every `HyperFungibleToken`/`BridgeToken`/`WrappedHyperFungibleToken` deployment. A zero `to` can arise from integrator bugs, default/uninitialized variables in calling contracts, or user error, and nothing in `send()` or the SDK's `TeleportParams`/`SendParams` construction path enforces non-zero recipients before the burn executes.

### Recommendation
Validate `params.to` before burning in `send()` — decode it the same way `onAccept` will (`_toAddr` or an equivalent check for the destination's address format) and revert if it resolves to the zero address, before calling `_burn`. This prevents irrecoverable burns for messages that are guaranteed to fail delivery.

### Proof of Concept
1. Caller invokes `HyperFungibleToken.send({ dest: <supported chain>, to: abi.encodePacked(address(0)), amount: X, timeout: 0, relayerFee: 0, data: "" })`.
2. `_burn(msg.sender, X)` executes immediately, destroying the caller's tokens on the source chain. [6](#0-5) 
3. The request is delivered on the destination chain; `onAccept` decodes `beneficiary = address(0)` and calls `_mint(address(0), X)`, which reverts per OpenZeppelin's zero-address check, so delivery can never succeed. [7](#0-6) 
4. With `timeout: 0` (no expiry), `onPostRequestTimeout` is never invoked, so the refund path in step above is unreachable, leaving amount `X` burned on the source chain with no corresponding mint anywhere — a permanent loss of funds.

```text
    function onAccept(IncomingPostRequest calldata incoming) public virtual override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }
```

```text
    function _toAddr(bytes memory b) internal pure returns (address addr) {
        if (b.length != 20) revert InvalidAddress(b.length);
        // casting to 'bytes20' is safe because we already checked length
        // forge-lint: disable-next-line(unsafe-typecast)
        return address(bytes20(b));
    }
```
