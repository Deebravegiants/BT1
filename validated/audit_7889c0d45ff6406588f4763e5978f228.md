### Title
Webhook Tenant Spoofing via Unsigned `shop-domain` Header - (File: lib/shopify_api/webhooks/request.rb)

### Summary
The webhook HMAC validation in this gem verifies only the raw request body, not the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers, which are trusted as-is by `Registry.process`. Because Shopify webhook HMACs are computed with an app-wide `client_secret` shared across all shops that installed the app (not a per-shop secret), any unprivileged user who installs the app on their own store can capture a validly-signed webhook payload from Shopify and forge the `shop-domain` header pointing to a different, victim tenant when forwarding it to the app's webhook endpoint. The HMAC check still passes because it only covers `@raw_body`.

### Finding Description
`Utils::HmacValidator.validate` computes the expected signature over `verifiable_query.to_signable_string` and compares it to the supplied `hmac` [4](#0-3) . For webhooks, `Webhooks::Request#to_signable_string` is defined to return only `@raw_body` [1](#0-0) , meaning the `hmac-sha256` header only attests to the JSON body bytes. The `shop`, `topic`, `webhook_id`, and `api_version` accessors read directly from HTTP headers that are entirely outside the HMAC's coverage [2](#0-1) .

`Registry.process` uses this unvalidated `request.shop` value as the tenant identity passed to the app's registered handler after confirming only that the HMAC (over the body) is valid [3](#0-2) . This breaks the intended identity binding: `HMAC-verified bytes == webhook content attributed to the shop`. In reality, the equality that holds is only `HMAC-verified bytes == raw_body`, while `shop` is asserted, not proven.

Because Shopify signs webhooks per-app (using the app's `client_secret`) rather than per-shop, a legitimate installer of the app (an "unprivileged internet user" with respect to any other merchant's tenant) can receive a genuine, validly-HMAC'd webhook for their own shop and then replay that exact body/HMAC pair to the app's webhook endpoint with a forged `x-shopify-shop-domain` header naming a different shop. `HmacValidator.validate` still returns true, and `Registry.process` will invoke the handler believing the payload originates from the victim shop.

### Impact Explanation
This crosses a tenant boundary: an attacker can cause the application to process attacker-controlled webhook data as if it belonged to a different merchant's shop, since only `request.shop` (unauthenticated) — not any HMAC-bound value — determines which tenant's data/session/state the handler updates. Depending on how the host app uses `WebhookMetadata#shop`/`data.shop` (e.g., to look up sessions, update order/customer state, or trigger side effects for that shop), this enables cross-tenant data injection or corruption, matching the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Any user able to install the app on their own store (an ordinary Shopify merchant, requiring no special privilege or leaked secret) can obtain genuinely signed webhook payloads for their own shop. Because the HMAC's signable content is body-only [1](#0-0) , replaying that payload with a modified `shop-domain` header against the app's public webhook endpoint is straightforward and does not require the app's `client_secret`, an access token, or any credential belonging to the victim shop.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) to the HMAC-verified content, e.g. by including these header values in the signable string, or by cross-checking `request.shop` against a shop already known to have installed the app (verified installation record) before dispatching to handlers, rather than trusting the raw header value implicitly.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com`, a shop they legitimately control.
2. Shopify sends a real webhook to the app's endpoint, HMAC-signed over the JSON body with the app's `client_secret`, with header `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker captures this `(raw_body, hmac)` pair.
4. Attacker crafts a new HTTP request to the same webhook endpoint using the identical `raw_body` and `x-shopify-hmac-sha256` header, but sets `x-shopify-shop-domain: victim.myshopify.com`.
5. `Webhooks::Request.new` accepts the forged headers [5](#0-4) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `@raw_body` against the HMAC [6](#0-5) .
6. The handler is invoked with `shop: request.shop` equal to `"victim.myshopify.com"` [7](#0-6) , causing the app to process attacker-supplied data as belonging to the victim tenant.
