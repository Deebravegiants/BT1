The strongest analog to the "emissions for null epochs" pattern in alt.fun is the treatment of LT donated directly to a curve `Pair`: donated LT never enters the graduation math, is never drained by `Router.graduate`, and — because `Pair.sol` exposes no `skim`/rescue function and `Router.graduate`/`Pair.transferAsset` are permanently gated to `Bonding`'s one-shot pre-`Curve` call — the donated value is stuck in the contract forever, exactly like the Sherlock report's "no shares to split emissions with."

### Title
Direct LT donations to a curve `Pair` are permanently and irrecoverably locked, with no path to ever move them out - (File: `packages/contracts/src/Pair.sol`, `packages/contracts/src/Router.sol`, `packages/contracts/src/Bonding.sol`)

### Summary
Any unprivileged wallet can call `IERC20(lt).transfer(pairAddr, amount)` on a token's curve `Pair` before or during that token's `Curve`/`Graduating` lifecycle. `Pair.sol` has no `skim`, `sweep`, or owner-recovery function for the asset (LT) side [1](#0-0) , and the only privileged extraction path, `Router.graduate`, is deliberately restricted to `assetReserve - virtualLtReserve` — the curve-raised amount only — explicitly leaving any donated LT behind [2](#0-1) . `Bonding._prepareGraduationLiquidity` calls `Router.graduate` exactly once per token, from `_enterGraduating`, which is unreachable once the token's lifecycle passes `Curve` [3](#0-2) . Once graduation completes there is no remaining code path with `BONDING_ROLE` that can call `transferAsset` on that pair again, so any LT donated to the pair — before, during, or never followed by graduation — is permanently stuck.

### Finding Description
- `Router.graduate(token, amount)` transfers exactly `assetReserve - virtualLtReserve` out of the pair, by design, so "anything `IERC20.transfer`-donated to the pair stays put" — this is stated directly in the code's own natspec and tests [4](#0-3) .
- The same natspec on `Router.graduate` explicitly documents the donation is "locked" as a *trust assumption*, reachable only via `Pair.transferAsset`, gated `onlyRouter`, itself gated `BONDING_ROLE`, itself only ever called from `_prepareGraduationLiquidity`, which is "unreachable once the token's lifecycle has flipped past `Curve`" [5](#0-4) .
- `Pair.sol` has no `skim`/rescue function at all — only `transferAsset`/`transferToken` (both `onlyRouter`) and the balance/reserve views [1](#0-0) .
- This is confirmed as the expected/tested behavior in `GraduationInvariants.t.sol`: `assertEq(IPair(pairAddr).assetBalance(), donation, "donated LT must remain locked in the curve pair")` [6](#0-5) .
- If the token *never graduates* (e.g., low-interest launch that never crosses either trigger), the pair's only privileged extraction path (`_prepareGraduationLiquidity` → `Router.graduate`) never fires at all, so the donated LT is stranded with certainty and no expiry — analogous to the "null epoch" in the source report where emissions are provisioned but never claimed because there was never a mechanism to hand them back.
- Even if the token *does* graduate, the donation is excluded from `ltFromPair` by construction (`ltFromPair = assetReserve - virtualLtReserve`, computed from *stored* reserves that a raw `transfer` never mutates) [7](#0-6) , so the donation survives graduation untouched and becomes permanently unreachable the moment the lifecycle flips.

### Impact Explanation
Any LT sent directly to a `Pair` by a trader, LP, or creator (e.g. a mis-aimed transfer, an attempted "boost" of a token they believe they're supporting, or an automated bot mistakenly targeting the pair address instead of `Zap`) is permanently and irrecoverably lost. There is no owner function, no sweep, and no future code path (by explicit design intent per the natspec) that can move this value out of the pair. This is a permanent freezing of user funds — the same class of impact as the source report's burnt emissions, just triggered by direct-transfer donation rather than epoch-based staking.

### Likelihood Explanation
Reachable by any unprivileged address with a single ERC20 `transfer` call to a publicly known pair address (pair addresses are emitted/discoverable via `Bonding.launch`/`Factory`). No special role, timing, or governance action is required. The protocol's own documentation and tests acknowledge and rely on this exact behavior ("donated LT must remain locked in the curve pair"), confirming the root cause is real and not a hypothetical edge case.

### Recommendation
Add a permissionless or owner-only rescue path for LT that lands in a `Pair` beyond its accounted `assetReserve` — e.g., a `Pair.skimAsset(recipient)` gated by `onlyRouter`/`BONDING_ROLE` that transfers `assetBalance() - assetReserve` to a configurable recipient (treasury, or a refund-to-sender scheme keyed off a donation-tracking event), mirroring how HyperSwap V2's own `skim()` handles pre-seed dust. At minimum, expose a way for the protocol owner to recover stuck LT after a token has permanently failed to graduate, rather than leaving it inaccessible by construction.

### Proof of Concept
1. `Bonding.launch(...)` a token normally; note its `pairAddr`.
2. An unprivileged attacker/wallet mints or acquires LT and calls `IERC20(lt).transfer(pairAddr, X)` directly (no `Bonding`/`Zap` call involved) — `_pool.assetReserve` is untouched since only `Pair.mint`/`Pair.swap` mutate it.
3. Confirm `IPair(pairAddr).assetBalance() > IPair(pairAddr).getReserves()` (assetReserve): the donated `X` sits in the pair's real balance but outside stored reserves.
4. Whether or not the token subsequently graduates (`Bonding.triggerGraduation`/threshold-crossing buy → `finalizeGraduation`), `Router.graduate` only ever drains `ltFromPair = assetReserve - virtualLtReserve`, explicitly excluding `X` — see `test_graduate_leavesDonationBehind` and `test_inv_donation_zeroGapPreserved`, which assert the donation remains in the pair's balance after graduation completes [4](#0-3) [8](#0-7) .
5. Post-graduation, `info.lifecycle == Lifecycle.Graduated` permanently blocks any further call into `_enterGraduating`/`Router.graduate` for this token, and `Pair.sol` has no other function capable of moving the asset token out — `X` is permanently unrecoverable.

```text
    /// @notice Transfer exactly `amount` of LT out of the pair to the caller.
    ///         Called by `Bonding._prepareGraduationLiquidity` during graduation
    ///         with `amount = stored assetReserve - virtualLtReserve` (i.e. the
    ///         real LT raised by the curve, excluding the virtual seed).
    /// @dev    Donation-resistant: passing an explicit `amount` instead of
    ///         draining `assetBalance()` ensures any LT that was donated
    ///         directly to the pair via `IERC20.transfer` is left behind and
    ///         excluded from LP seeding.
    ///
    ///         "Locked" here is a trust-assumption claim, not an on-chain
    ///         guarantee. `Pair.transferAsset` is gated by `onlyRouter`, and
    ///         `Router` only exposes it via this function and `sell`. Both
    ///         require `BONDING_ROLE`, which only `Bonding` holds. `Bonding`
    ///         in turn only calls `graduate` from
    ///         `_prepareGraduationLiquidity` — which is unreachable once the
    ///         token's lifecycle has flipped past `Curve`. So the leftover
    ///         is unreachable as long as (a) `BONDING_ROLE` is not granted
    ///         to any other address, and (b) future `Bonding` upgrades
    ///         preserve the lifecycle gate.
    function graduate(
        address token,
        uint256 amount
    ) external onlyRole(BONDING_ROLE) {
        address asset = assetTokenFor(token);
        address pairAddr = factory.getPair(token, asset);
        if (pairAddr == address(0)) revert PairNotFound();
        IPair(pairAddr).transferAsset(msg.sender, amount);
    }
```

```text
    /// @dev Burns unsold curve tokens, drains real raised LT, computes
    ///      `tokensForLP` for zero-gap LP seeding, burns the LP excess.
    ///
    ///      Price equality: `tokensForLP / ltFromPair = tokenReserve / assetReserve`,
    ///      with `ltFromPair = assetReserve - virtualLtReserve` (the LT
    ///      actually raised by the curve, excluding the launch-time virtual
    ///      seed; the seed is recovered as `Pair.k() / TOTAL_SUPPLY`, see
    ///      `_launchTimeVirtualLtReserve`). Substituting gives LP price =
    ///      `assetReserve / tokenReserve` = curve close marginal price.
    ///      Donations of LT directly to the pair don't move the stored
    ///      `assetReserve`, so they're excluded from `ltFromPair`.
    ///
    ///      Token-side donations are handled by `unsoldBurned`: any tokens
    ///      sitting in the pair beyond the curve's accounting are burned.
    ///
    ///      With virtual `tokenReserve = totalSupply` and `curveSupply = 75%`,
    ///      the parabola `tokensForLP(sold) = sold·(S−sold)/S` peaks at
    ///      `S/4 = LP_RESERVE` when `sold = S/2`, so `tokensForLP ≤ LP_RESERVE`
    ///      is mathematically invariant. The cap is defensive.
    function _prepareGraduationLiquidity(
        address tokenAddress
    ) internal returns (uint256 tokensForLP, uint256 ltFromPair, uint256 lpBurned, uint256 unsoldBurned) {
        address pairAddr = _s().tokenInfo[tokenAddress].pair;
        (uint256 tokenReserve, uint256 assetReserve) = IPair(pairAddr).getReserves();

        unsoldBurned = IPair(pairAddr).tokenBalance();
        if (unsoldBurned > 0) {
            Token(tokenAddress).burn(pairAddr, unsoldBurned);
        }

        ltFromPair = assetReserve - _launchTimeVirtualLtReserve(tokenAddress, pairAddr);
        if (ltFromPair > 0) {
            _s().router.graduate(tokenAddress, ltFromPair);
        }

        tokensForLP = assetReserve == 0 ? 0 : (ltFromPair * tokenReserve) / assetReserve;
        if (tokensForLP > LP_RESERVE) tokensForLP = LP_RESERVE;

        lpBurned = LP_RESERVE - tokensForLP;
        if (lpBurned > 0) {
            Token(tokenAddress).burn(address(this), lpBurned);
        }
    }
```
