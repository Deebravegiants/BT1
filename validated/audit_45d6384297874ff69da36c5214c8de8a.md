### Title
Storage-deposit charge coalescing in `execute_postponed_deposits` silently drops legitimate charges for a contract address reused after termination - (File: substrate/frame/revive/src/metering/storage.rs)

### Summary
`RawMeter::execute_postponed_deposits` sorts and coalesces per-contract `Charge` entries, and when it encounters a `Terminated` marker adjacent to an `Alive{amount}` entry for the same account, it unconditionally subtracts that `amount` from `total_deposit` and marks the slot `Terminated` — regardless of whether the `Alive` entry was recorded *before* or *after* the termination in the call stack. If a contract self-destructs and a new contract instance is later deployed at the *same account address* within the same transaction (call stack), the new instance's legitimate storage charge is coalesced away as if it belonged to the dead instance, so the origin is never actually charged (`E::charge` is skipped) for real storage the live contract's `ContractInfo` records as deposited.

### Finding Description
`execute_postponed_deposits` sorts `self.charges` by contract account and merges entries for the same account using `Vec::sort_by`, which is a stable sort, so charges for the same contract retain their original push order [1](#0-0) .

The merge logic treats any `(Alive, Terminated)` or `(Terminated, Alive)` pair for the same contract identically: it subtracts the `Alive` side's `amount` from `self.total_deposit` and forces the coalesced slot to `Terminated`, discarding the `Alive` entry entirely: [2](#0-1) 

Crucially, this branch is symmetric — it does not distinguish "charge occurred before termination" (correct: those charges are moot because `terminate()` already folded the whole balance into a single refund, see line 450-452) from "charge occurred after termination" (a *new* contract instance at the same address doing real, chargeable storage work). In the latter case, discarding the charge and subtracting it from `total_deposit` is wrong: the new instance is alive, its `ContractInfo.storage_byte_deposit`/`storage_item_deposit` were already updated by `Contribution::update_contract` inside `absorb` [3](#0-2) , but the corresponding balance is never moved from the origin because the loop that calls `E::charge` only iterates over the surviving `self.charges` entries after coalescing [4](#0-3) , and the entry was removed.

`terminate()` itself only pushes a bare `Charge::Terminated` marker (no amount) and separately folds the refund directly into `total_deposit`: [5](#0-4) 
This design is sound for the *intended* case (undoing charges recorded for the same living instance before it destructs), but the coalescing code applies the same "undo" rule even when the `Alive` charge is chronologically *after* the `Terminated` marker, i.e. belongs to a different contract lifetime that happens to reuse the same account address (e.g. via deterministic/salted contract-address derivation and a self-destruct-then-redeploy pattern within one call stack, `address.rs` uses salt-based derivation per the codebase, though I was not able to fully confirm within this pass whether redeploying at an identical address after termination in the same transaction is currently permitted by the address-collision guard in `Pallet::instantiate`/`address.rs`).

There is also a related but separate latent issue: the `(Terminated, Terminated)` branch is a `debug_assert!(false, ...)` with no corresponding runtime handling in release builds [6](#0-5) ; in a release/production runtime this assertion is compiled out and the second `Terminated` charge is silently dropped with no defined semantics, which is a robustness gap but not by itself an asset-theft path since no amount is attached to a `Terminated` marker.

### Impact Explanation
If reachable, the effect is that `total_deposit` (the amount reserved/held from the origin account, returned by `execute_postponed_deposits`) is under-counted by the live-contract's real storage charge, and `E::charge` is never invoked to move that balance from the origin. Meanwhile `ContractInfo` for the live contract records the deposit as backed. This breaks the core invariant that "storage deposits must remain fully backed" — the contract's recorded deposit is not actually held/reserved from any account, i.e. unbacked deposit accounting, which can later be redeemed via a legitimate refund path (e.g. terminating that contract or shrinking its storage) for balance that was never paid in.

### Likelihood Explanation
Exploitability hinges entirely on whether a contract can be terminated and a new contract instance can be re-instantiated at the exact same account address within the same call stack (same transaction) before `execute_postponed_deposits` runs at the top level. I found `substrate/frame/revive/src/address.rs` uses salt-based address derivation (grep hits for `salt`/CREATE2-style patterns), which is suggestive of Ethereum-style "metamorphic contract" address reuse, but I did not verify within this session whether pallet-revive's `instantiate` path rejects deploying to an address that was used-then-terminated in the same block/transaction. This is the key open precondition; without confirming it, the practical likelihood cannot be rated with full confidence. If address reuse in the same call stack is possible, the bug is deterministically and repeatably triggerable by any unprivileged contract-calling account.

### Recommendation
Track charges per contract *instantiation* rather than per raw account address (e.g. tag `Charge` entries with an instantiation nonce/generation, or flush/reset the `charges` accounting for an address the moment `terminate()` is recorded so charges appended afterward are never coalesced with the stale `Terminated` marker). At minimum, when merging `(Terminated, Alive{amount})` where the `Alive` entry occurs *after* the `Terminated` marker in program order, the amount should be charged normally (as belonging to a new instance) instead of being subtracted/discarded.

### Proof of Concept
Rust unit test plan (extending `substrate/frame/revive/src/metering/storage/tests.rs`):
1. Construct a `Root` `RawMeter`.
2. Simulate contract account `C`: absorb a nested meter with `own_contribution` producing `Charge{contract: C, Alive{amount: Charge(100)}}` (instance #1 writes).
3. Call `meter.terminate(C, refunded)` (instance #1 self-destructs) — appends `Charge{contract: C, Terminated}`.
4. Absorb another nested meter for a *new* instance at the same address `C` producing `Charge{contract: C, Alive{amount: Charge(50)}}` (instance #2 writes, occurring after termination in push order).
5. Call `execute_postponed_deposits` and assert:
   - `E::charge` (via `TestExt`) is invoked with `amount = Charge(50)` for contract `C` (expected/correct behavior), **currently fails** because the entry is coalesced away.
   - Returned `total_deposit` includes the 50 charge for instance #2 (currently under-counted).

		// However, with this complete information there is no need to recalculate `max_charged` for
