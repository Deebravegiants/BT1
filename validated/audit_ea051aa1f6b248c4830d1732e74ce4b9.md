This confirms the vulnerability: `docs/usage/webhooks.md` explicitly documents `ShopifyAPI::Webhooks::Registry.process` as verifying "the request did indeed come from Shopify" (line 125), and `WebhookMetadata.shop` is presented to handler authors as a trusted field with no caveat that it is unauthenticated. This is a genuine gem-level identity-binding flaw, not a host-app misuse issue.

### Title
Webhook `shop` domain field is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload from the raw request body only, while the `shop` (and `topic`) values are read from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates only that HMAC before forwarding `request.shop` to the app's `WebhookHandler` as trusted `WebhookMetadata.shop`, breaking the intended binding `shop-that-signed-the-payload == shop-delivered-to-handler`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . The `shop` accessor, however, is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never part of the signed string: [2](#0-1) .

`Registry.process` only validates the HMAC over the body, then constructs `WebhookMetadata` using `request.shop` taken directly from the header, and hands it to the developer's handler as authenticated data: [3](#0-2) . The `WebhookMetadata` struct and its docs present `shop` as reliable identification of which merchant the webhook belongs to: [4](#0-3) , and the usage docs state that `Registry.process` "will verify the request did indeed come from Shopify:" [5](#0-4) , with no caveat that `shop` is excluded from that verification.

Contrast this with `Auth::Oauth::AuthQuery`, where `shop` **is** part of `to_signable_string` and thus is bound by the HMAC: [6](#0-5) . The webhook path lacks this equivalent binding.

The broken identity equality is:
`shop-domain-that-produced(HMAC-secret, raw_body) == shop-domain-delivered-to-handler`

Both sides are equal only by coincidence in the legitimate case; nothing in `HmacValidator.validate` or `Registry.process` enforces it.

### Impact Explanation
An attacker who legitimately installs the app on their **own** shop (a normal, unprivileged action requiring no special access) can capture a genuine webhook delivery for their shop, consisting of `(raw_body, hmac)`, both of which validate correctly against `Context.api_secret_key`, since the secret is a single app-wide value, not per-shop. The attacker can then replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still passes because it never looks at the shop header [7](#0-6) , and the forged `shop` value flows straight into the handler as trusted `WebhookMetadata.shop`. If the host application keys any write/queue/cache/authorization operation off `data.shop` (as the documented example does — `perform_later(topic: data.topic, shop_domain: data.shop, ...)`, see `docs/usage/webhooks.md` lines 24-27), this becomes cross-tenant data injection/corruption: the attacker's payload is processed as though it originated from the victim's store.

### Likelihood Explanation
High. Getting a valid `(body, hmac)` pair requires nothing more than installing the app on a shop the attacker controls (or triggering any webhook topic on it), which is an ordinary unprivileged action available to anyone who can install a Shopify app. No secrets, tokens, or elevated access are needed to construct the forged request; only header substitution.

### Recommendation
Bind the `shop` (and ideally `topic`, `api_version`, `webhook_id`) values into the signed material, or explicitly document that `Request#shop` is unauthenticated and must be independently cross-checked by the host application (e.g., against the shop of an installed session) before being trusted. At minimum, `Registry.process` should not label the resulting `shop` as verified, and the docs claiming the request "did indeed come from Shopify" should be corrected to clarify that only the body's origin is verified, not the claimed shop domain.

### Proof of Concept
```ruby
# Attacker installs app on their own shop "attacker.myshopify.com" and receives
# a real webhook. They capture:
raw_body = '{"id": 1, "note": "hello"}'
valid_hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
)

# Attacker replays the same body/hmac but swaps the shop-domain header:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
# HMAC validation passes because the shop header was never signed.
```
