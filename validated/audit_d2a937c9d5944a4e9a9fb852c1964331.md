### Title
Griefing via repeated dust Deposit/Withdraw permanently zeroes out PnL accrual through `calc_take_pnl` precision loss - (File: `program/src/processor.rs`)

### Summary
`Processor::calc_take_pnl` computes the trading-fee PnL owed to the pool owner by comparing the current invariant `(x1, y1)` against the last recorded snapshot `(target.calc_pnl_x, target.calc_pnl_y)`. The computed PnL amounts are floor-divided and, whenever either the pc-side or coin-side result rounds to zero, the function discards *both* deltas (`delta_x = 0; delta_y = 0;`) instead of carrying the residual forward. Critically, the caller (`process_deposit`/`process_withdraw`) still advances the snapshot `target_orders.calc_pnl_x`/`calc_pnl_y` to the post-operation pool state regardless of whether any PnL was captured. An attacker who repeatedly triggers Deposit/Withdraw with small amounts can keep the accrued invariant growth below the rounding threshold on every call, causing the snapshot to be perpetually reset forward while `need_take_pnl_pc`/`need_take_pnl_coin` never increase — permanently erasing the pool owner's legitimately earned PnL for that period.

### Finding Description
`calc_take_pnl` restores the last snapshot to native decimals, computes the growth in the invariant since the last snapshot (`diff_x`, `diff_y`), and derives `pc_pnl_amount`/`coin_pnl_amount` via floor division: [1](#0-0) 

The `if pc_pnl_amount != 0 && coin_pnl_amount != 0` gate means that if **either** token side rounds down to zero (e.g. because the two vault tokens have different decimals, or because the elapsed trading volume since the last snapshot is small), `need_take_pnl_pc`/`need_take_pnl_coin` are not incremented for **either** token, and `delta_x`/`delta_y` are forced to zero: [2](#0-1) 

Despite the PnL not being captured, the caller unconditionally advances the reference snapshot to the current pool state minus the (zeroed) delta, e.g. in `process_deposit`: [3](#0-2) 

and equivalently in `process_withdraw`: [4](#0-3) 

Both `process_deposit` and `process_withdraw` are permissionless, unprivileged-user-reachable instructions that call `calc_take_pnl` on every invocation: [5](#0-4) 

Because the snapshot always advances to "current state" regardless of whether the PnL differential was captured, any k-growth (owner-owed trading fee accrual) that occurred between two closely-spaced Deposit/Withdraw calls and that rounds under the native-decimal threshold is permanently discarded — there is no mechanism to carry forward the truncated remainder as described in the analogous MultiRewards bug. An attacker who repeatedly submits minimal-amount Deposit followed by Withdraw (or vice versa) can keep resetting the snapshot before the differential ever reaches a whole native unit on both sides, indefinitely suppressing `need_take_pnl_pc`/`need_take_pnl_coin` growth. This is the same "residual amount is silently discarded instead of carried over" root cause as the referenced report's `rewardPerTokenStored` truncation, applied to Raydium's PnL accrual accumulator instead of a reward-per-token accumulator.

### Impact Explanation
This causes a permanent, unrecoverable loss of the pool owner's/pool-creator's earned PnL fee for every period an attacker chooses to grief, since `WithdrawPnl` can only ever transfer out whatever has accumulated in `need_take_pnl_pc`/`need_take_pnl_coin`, and the underlying accrual mechanism (`calc_take_pnl`) can be kept perpetually at zero by cheap dust transactions. This matches the "Medium" impact classification of the original report: continuous build-up of unclaimable/irrecoverable amounts, escalating to full denial of PnL accrual under attacker-favorable conditions (e.g. mismatched token decimals or low trading volume between grief transactions).

### Likelihood Explanation
Medium. The attack only requires the ability to submit ordinary Deposit/Withdraw transactions with small amounts — no privileged signer, no special accounts, and no reliance on validator or off-chain behavior. The precision-loss condition is more easily triggered here than in the original report because the `&&` gate zeroes both deltas whenever only one side rounds down, and pools frequently pair tokens with differing decimals (e.g. 6 vs 9), making the zero-rounding condition common rather than rare.

### Recommendation
Do not advance `target_orders.calc_pnl_x`/`calc_pnl_y` to the full current invariant when `delta_x`/`delta_y` are zero due to rounding. Instead, retain the un-captured residual growth in the snapshot (i.e., only advance the snapshot by the amount of PnL actually deposited/withdrawn, not by the full diff), so that residual invariant growth accumulates across calls instead of being reset and discarded on every Deposit/Withdraw.

### Proof of Concept
1. Create a pool where `coin_decimals` and `pc_decimals` differ (or where trade volume is low relative to `sys_decimal_value` scaling), matching the existing in-repo precision test `test_calc_pnl_precision` in `program/src/processor.rs` which already demonstrates `delta_x`/`delta_y` becoming vanishingly small under realistic pool amounts.
2. An attacker (any unprivileged user) repeatedly calls `Deposit` with the minimum allowed amount, then `Withdraw` shortly after, each time invoking `calc_take_pnl` via `process_deposit`/`process_withdraw`.
3. Each time either `pc_pnl_amount` or `coin_pnl_amount` computed in `calc_take_pnl` rounds to zero, `need_take_pnl_pc`/`need_take_pnl_coin` stay unchanged while `target_orders.calc_pnl_x`/`calc_pnl_y` are reset to the current pool state (`process_deposit`, lines 1352-1371 / `process_withdraw`, lines 1818-1838), discarding the invariant growth that occurred since the last snapshot.
4. Repeating this indefinitely keeps `need_take_pnl_pc`/`need_take_pnl_coin` at (or near) zero forever, so `WithdrawPnl` never yields the pool owner's rightfully accrued trading-fee PnL.
