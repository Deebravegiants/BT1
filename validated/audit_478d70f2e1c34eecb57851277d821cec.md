This confirms the documented API contract directly: `docs/usage/webhooks.md` line 125 explicitly states that `Registry.process` "will verify the request did indeed come from Shopify" — but the actual implementation only verifies the raw body bytes, not the `shop` field that the handler receives and acts on.

### Title
Webhook shop-domain identity spoofing via HMAC binding gap enabling cross-tenant webhook injection - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , so `Utils::HmacValidator.validate` only authenticates the body bytes against the app's shared `api_secret_key` [2](#0-1) . The `shop` value, which is read from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header [3](#0-2) , is never part of the signed data, yet `Registry.process` passes it straight into `WebhookMetadata` that the host app's handler trusts as the authenticated tenant identity [4](#0-3) .

### Finding Description
This is the direct analog of the reported bug class: an identity field (`shop`, the tenant binding) is acted upon by the code but not covered by the cryptographic authentication (HMAC), just as `withdrawnDividendPerOwner` was updated for an owner identity that the transfer logic no longer bound correctly to the actual current owner.

The equality that should hold is:
`shop authenticated by HMAC == shop delivered to the handler as WebhookMetadata.shop`

But in practice:
- `HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`, which for `Webhooks::Request` is exactly `@raw_body` [1](#0-0) .
- `shop`, `topic`, `webhook_id`, and `api_version` are all read from HTTP headers that are never mixed into that signable string [5](#0-4) .
- `Registry.process` only checks `Utils::HmacValidator.validate(request)` and then unconditionally forwards `request.shop` (and `request.topic`, `request.webhook_id`, `request.api_version`) to the handler [4](#0-3) .
- The gem's own documentation states that `process` "will verify the request did indeed come from Shopify" [6](#0-5) , and instructs handler authors to trust `data.shop` as the shop domain of the webhook [7](#0-6) .

Because `api_secret_key` is a single secret shared by the app across every shop that installs it (it is not a per-shop secret), any shop that has installed the app can legitimately obtain a validly HMAC-signed `(topic, raw_body, hmac)` triple for its own events. An attacker who controls such an installation can then replay that exact triple to the app's public webhook endpoint while substituting the `shopify-shop-domain` header for an arbitrary victim shop domain. `Utils::HmacValidator.validate` still passes because it never inspected the header, and `Registry.process` will dispatch the handler with `WebhookMetadata.shop` set to the attacker-chosen victim domain, together with the attacker's own body content.

### Impact Explanation
This breaks the tenant boundary the gem is documented to enforce for webhook processing: an unprivileged internet user who merely has their own (possibly free/trial) shop install the target app can forge webhook events "from" any other shop, since the shop identity is never bound to the authenticated payload. Depending on how the host app's handler uses `data.shop` (e.g., to look up the tenant's session/store record and write orders/products/customer data, or to trigger side effects scoped to that shop), this results in cross-tenant data injection/corruption — classified as Critical (cross-tenant access) per the scope's impact criteria.

### Likelihood Explanation
Likelihood is high for any app that has at least one attacker-controlled or attacker-installable shop (a very low bar — anyone can create a free Shopify dev/trial store and install a public or even unlisted app). No access token, `api_secret_key`, or privileged account is required; the attacker only needs to trigger any webhook-producing action in their own shop and replay the resulting valid HMAC-signed request with a modified `shop-domain` header against the app's public webhook endpoint.

### Recommendation
Bind the shop identity into the authenticated data instead of trusting an unauthenticated header:
- Extend `Webhooks::Request#to_signable_string` (or `HmacValidator`) so the HMAC verification is scoped to the specific delivery, e.g., by cross-checking the `shop` header against Shopify's response for that `webhook_id`/topic via API, or by requiring hosts to independently confirm the shop is the one that owns the webhook subscription (e.g., via `webhook_id` lookup) before trusting `WebhookMetadata.shop`.
- At minimum, document explicitly and prominently that `shop`, `topic`, `webhook_id`, and `api_version` headers are **not** covered by the HMAC and must not be trusted for tenant attribution without additional verification, correcting the current documentation which states the opposite (that `process` verifies the request "did indeed come from Shopify") [8](#0-7) .

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, obtaining valid webhook deliveries signed with the app's shared `api_secret_key`.
2. Attacker triggers an event (e.g., updates a product) causing Shopify to POST a legitimately HMAC-signed webhook to the app, e.g.:
   ```
   POST /callback/products/update
   shopify-topic: products/update
   shopify-hmac-sha256: <valid HMAC of raw_body>
   shopify-shop-domain: attacker.myshopify.com
   shopify-webhook-id: <id>
   <raw_body JSON>
   ```
3. Attacker captures this exact `raw_body` and `shopify-hmac-sha256` value, then replays it to the same endpoint with the header changed:
   ```
   POST /callback/products/update
   shopify-topic: products/update
   shopify-hmac-sha256: <same valid HMAC>
   shopify-shop-domain: victim-shop.myshopify.com
   shopify-webhook-id: <same id>
   <same raw_body JSON>
   ```
4. `ShopifyAPI::Webhooks::Request.new` accepts the headers, `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the HMAC [1](#0-0) .
5. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic: "products/update", shop: "victim-shop.myshopify.com", body: <attacker's body>, ...))` [9](#0-8) , causing the host app to process attacker-controlled data as though it originated from `victim-shop.myshopify.com`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
