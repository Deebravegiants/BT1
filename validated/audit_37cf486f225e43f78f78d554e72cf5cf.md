### Title
Reentrant fund drain via external transfer before escrow accounting update in `IntentGatewayV2.withdraw()` — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The AffineDeFi report's root cause is a privileged callback (`createAaveDebt`/flash-loan recipient) that trusts attacker-supplied `userData` and amounts to release/account for funds without validating them against real escrowed state before performing the transfer. The closest reachable analog in this codebase is `IntentGatewayV2.withdraw()` in the Tron contracts, which releases escrowed funds to an attacker-chosen `beneficiary` (the solver) via a raw external call **before** updating the escrow accounting, and validates only that the per-token escrow is non-zero rather than that the requested amount is backed by it at the time of transfer.

### Finding Description
`withdraw()` is reached from `onAccept()` when a `RedeemEscrow`/`RefundEscrow` cross-chain message arrives: [1](#0-0) 

Inside `withdraw`, for each token in the decoded `WithdrawalRequest.tokens[]` (whose `beneficiary` is the solver that filled the order — fully attacker-controllable), the function:
1. Checks only that `_orders[commitment][token] != 0` (not that it covers `amount`).
2. Performs the native/ERC20 transfer via a raw `.call` to the beneficiary.
3. Only afterwards decrements `_orders[commitment][token] -= amount`. [2](#0-1) 

This is a Checks-Effects-Interactions violation: the external call (to an attacker-controlled `beneficiary` contract) happens before the escrow ledger is updated, and the pre-transfer check does not bind the transferred `amount` to the actual escrowed balance — only to non-zero-ness. The current mainline EVM contract has since been hardened to update the ledger before the transfer and to store/subtract the exact escrowed amount: [3](#0-2) 

This shows the CEI fix was deliberately applied to the primary EVM path but the Tron contract still contains the unsafe ordering.

### Impact Explanation
A malicious solver who wins an order fill sets `beneficiary` to a contract they control. When the settlement message is delivered and `withdraw()` runs, the native-ETH `.call{value: amount}("")` (or ERC20 `transfer` to a malicious/callback-capable token) hands control back to the attacker's contract before `_orders[commitment][token]` is decremented. This exposes the escrow ledger to being read/acted upon in a stale (pre-decrement) state during the callback, and generally violates the security invariant (state-before-interaction) that protects escrowed user/protocol funds from reentrant manipulation — the same class of "unvalidated intermediate state gates an irreversible fund release" flaw as the AffineDeFi flash-loan callback issue. Concrete impact is loss of escrowed input tokens meant for the source-chain user/solver.

### Likelihood Explanation
The path requires no privileged access: any solver that fills an order and is delivered a `RedeemEscrow`/`RefundEscrow` message can set the beneficiary to their own attacker contract. The vulnerable code executes deterministically on the standard settlement path, so likelihood is High wherever this Tron contract is deployed and reachable.

### Recommendation
Apply the same fix already present in `evm/src/apps/intentsv2/IntentsBase.sol` to `evm/tron/contracts/apps/IntentGatewayV2.sol`: read/validate `escrowed = _orders[commitment][token]`, revert if `escrowed == 0`, update `_orders[commitment][token] = escrowed - amount` **before** issuing the external call, and use `SafeERC20`/checked transfer helpers instead of unchecked low-level `.call`.

### Proof of Concept
1. Attacker deploys `MaliciousBeneficiary` with a `receive()`/token callback that re-enters gateway state-reading functions.
2. Attacker (as solver) calls `fillOrder` for a native-ETH-denominated order, setting `beneficiary = address(MaliciousBeneficiary)`.
3. Settlement message delivers on the source chain; `onAccept` → `withdraw(body, false)` executes:
   - `_orders[commitment][address(0)] != 0` check passes.
   - `beneficiary.call{value: amount}("")` transfers ETH and yields control to `MaliciousBeneficiary`.
   - Only after the callback returns does `_orders[commitment][address(0)] -= amount` execute.
4. During the callback window, `_orders[commitment][address(0)]` still reflects the pre-payout balance, which can be leveraged by any reentrant path that reads or spends against that stale escrow value before it is finalized. [2](#0-1)

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            }
        }

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
