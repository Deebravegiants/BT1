### Title
Phantom order price oracle can be biased by a liquidity-dominant (or Sybil-colluding) solver whose weighted-median quote sets the published index rate - ([File: sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts])

### Summary
Hyperbridge's intent gateway publishes a market rate by having solvers ("fillers") bid on periodically-generated "phantom orders" (dummy orders that can never actually be filled). `aggregatePhantomBids` collapses every leg's bids into one on-chain-consumed price via `weightedMedian`, weighted purely by each solver's own self-reported/on-chain-read inventory in the output token. Exactly as in the Entropy report's "provider colludes/dominates to bias a value that looks like normal random variance," a solver that concentrates enough inventory in a leg's output token (or Sybils several delegated accounts, each independently funded) can set the published `medianPrice` — and therefore `lowestPrice`/`highestPrice` — to any value it likes, unilaterally and undetectably, since the result is indistinguishable from a legitimately competitive quote.

### Finding Description
`weightedMedian` is a *selection*, not a blend: it walks bids sorted by price and returns the exact price of whichever bid pushes cumulative weight past 50% of total weight [1](#0-0) . The test suite documents the property explicitly: "the high-liquidity solver pulls the median to its price" and a solver with weight 100 out of 102 sets the reported price to its own quote regardless of two other honest quotes [2](#0-1) . Weight is computed per leg strictly from the solver's own destination-chain token balance (plus any Uniswap V4 position it owns), read live via `getBalance`/`readPosition` [3](#0-2) , and de-duplication only collapses multiple bids from the *same* EVM `solver` address — a solver operating multiple funded, delegated `SolverAccount`s (Sybils) is dedup'd per-address, not per-controller, so nothing prevents concentrating >50% of a leg's counted weight without collusion from anyone else at all [4](#0-3) .

This is a direct structural analog of the Entropy report's core issue: an untrusted party (here, the solver, one of the actors explicitly in scope) whose privileged input (its self-controlled inventory / quote) directly determines a value the protocol commits on-chain as ground truth, with the manipulation looking exactly like ordinary market variance and therefore being undetectable ("very difficult to detect... outwardly identical to low-probability events").

The published snapshot is not cosmetic — it is a load-bearing price oracle. The indexer turns the medianPrice directly into pool exchange rates: `medianPrice * 10**(18-outDecimals) * 10**inDecimals / standardAmount` [5](#0-4) , and per-chain samples are merged into the pool's canonical `sellRate`/`buyRate` [6](#0-5) . Those pool rates are the exact numbers the SDK's `quoteIntent` returns to real users placing real orders, explicitly documented as "the pool rate is depth-weighted from fresh chain samples," used with "no automatic fallback to another price source" [7](#0-6) .

### Impact Explanation
A solver that dominates or Sybils its way to majority counted weight on a leg can set the published exchange rate to an arbitrary, self-chosen value that no honest counterparty quoted. Any user or integrator relying on `quoteIntent`/indexed pool rates to size a real `IntentGatewayV2` order is misled about fair value; the manipulating solver can quote a rate that looks attractive enough to draw order flow, then fill the real order (a distinct on-chain transaction, governed only by the solver's own honest quote at fill time) at the true, worse-for-the-user rate baked into the order — extracting value exactly as in the exploit scenario in the reference report, where the privileged party biases a trusted output to profit at counterparties' expense. Because `lowestPrice`/`highestPrice` are overwritten to equal the manipulated median, downstream consumers also lose the one signal (dispersion across bids) that could otherwise flag an outlier.

### Likelihood Explanation
No governance action, validator collusion, or privileged role is required — any solver capable of funding a delegated `SolverAccount` with the target-leg's output token (or several such accounts under one controller) can win the weighted median on legs where liquidity is thin, which is common for newer or lower-volume pairs. The mechanism is explicitly acknowledged in code comments as a known edge case for the *zero-weight* case ("a solver with no inventory sets the rate for free") but the symmetric *majority-weight* case — a well-funded or Sybil solver setting the rate deliberately — has no mitigation at all.

### Recommendation
- Short term: cap any single solver's (or address-cluster's) contribution to a leg's weighted median (e.g., a maximum weight share per solver per snapshot), and/or require a minimum number of distinct, unrelated solvers with meaningful weight before a leg's median is trusted, publishing a confidence/dispersion indicator alongside the price so downstream consumers can detect concentrated influence.
- Long term: source phantom-order pricing from multiple independent signals (e.g., cross-reference against external DEX/CEX oracles) rather than trusting a single self-reported-inventory-weighted median from the same solver population that also fills real orders, and consider decoupling "who can quote" from "how much their quote counts" more robustly (e.g., staked/bonded, slashable solver identities) to raise the cost of concentrating weight.

### Proof of Concept
1. Attacker deploys and delegates several `SolverAccount`s (E7702) to distinct EOAs, each funded with the target leg's output token on the destination chain, so their combined balance exceeds 50% of all counted weight for that leg (verified via `getBalance` reads at aggregation time) [3](#0-2) .
2. Each account submits a distinct signed bid on the current `CurrentPhantomOrder` commitment for that chain, quoting an arbitrary favorable `outputs[i].amount` for the leg being targeted; `countedSolvers` only dedups identical `solver` addresses, so distinct funded addresses all count [4](#0-3) .
3. When `PhantomBidWindowExhausted` fires, `aggregatePhantomBids` computes `weightedMedian` over the leg's quotes; per the documented/tested behavior, whichever bid pushes cumulative weight ≥50% sets `medianPrice` (and thus `lowestPrice`/`highestPrice`) verbatim to the attacker's chosen number [1](#0-0) [2](#0-1) .
4. The indexer renormalizes this into the pool's published `sellRate`/`buyRate` [5](#0-4) , which real users' `quoteIntent` calls read to size real orders [7](#0-6) , letting the attacker extract value from any user who places an order against the manipulated quote.

```typescript
export function weightedMedian(entries: { price: bigint; weight: bigint }[]): bigint {
	const sorted = [...entries].sort((a, b) => (a.price < b.price ? -1 : a.price > b.price ? 1 : 0))
	const totalWeight = sorted.reduce((acc, e) => (e.weight > 0n ? acc + e.weight : acc), 0n)

	if (totalWeight === 0n) {
		return sorted[Math.floor(sorted.length / 2)].price
	}

	let cumulative = 0n
	for (const entry of sorted) {
		if (entry.weight <= 0n) continue
		cumulative += entry.weight
		if (cumulative * 2n >= totalWeight) return entry.price
	}
	return sorted[sorted.length - 1].price
```
