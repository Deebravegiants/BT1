## Title
SimplexPaymaster oracle pricing has no Arbitrum/L2 sequencer-uptime check, allowing stale-price gas payment exploitation - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster` is a permissionless ERC-4337 paymaster deployed via a generic, config-driven deployment script (`native oracle` and per-token oracle addresses are supplied at deploy time), so it can be — and per the SDK's Chainlink feed registry is — deployed on Arbitrum and other L2s (`EVM-42161` is a listed Chainlink feed target alongside Base/Optimism). Its Chainlink price reads only validate staleness against `maxOracleAge` and a positive answer; they never check an L2 Sequencer Uptime Feed, so any user submitting a `UserOperation` can pay gas at a stale/incorrect price during a sequencer outage.

### Finding Description
`_getOraclePrice` is the sole gate on Chainlink data used to price every gas payment: [1](#0-0) 

It reverts only on `answer <= 0` or `block.timestamp - updatedAt > maxOracleAge`. There is no call to a Chainlink `SequencerUptimeFeed`/`AggregatorV2V3Interface` to confirm the L2 sequencer is up, nor any grace-period check after a restart, which is Chainlink's documented requirement for any L2 price consumer (the exact bug class in the source report).

This price feeds directly into the amount charged to `UserOperation` senders and swapped by the treasury: [2](#0-1) [3](#0-2) 

`_fetchDetails` is invoked from the standard `PaymasterERC20` flow for every permissionless `UserOperation` that names this paymaster, so any unprivileged actor reaches the unchecked oracle read at will — no privileged role is required, matching the reachability bar (an ordinary bundler/user submission).

`swapAndDeposit`, which converts accrued stablecoin surplus into native gas deposits at an oracle-derived minimum output, has the same gap: [4](#0-3) 

If the Arbitrum (or Base/Optimism) sequencer goes down, Chainlink feeds on that chain stop receiving fresh updates but the last-reported price can remain within `maxOracleAge` (heartbeats up to 24h are explicitly tolerated per the contract's own comments) for the outage's duration. During that window `_getOraclePrice` treats the frozen price as valid.

### Impact Explanation
While the sequencer is down (or during the post-restart grace period once it resumes), the contract keeps computing `tokenPrice` from a frozen, off-market Chainlink answer instead of reverting. An attacker who can predict or trigger favorable divergence between the frozen oracle price and the real native-asset/token market rate can:
- Submit `UserOperations` that under-pay in the registered stablecoin relative to the true gas cost, draining the paymaster's `EntryPoint` deposit funded by other users/the treasury.
- Trigger `swapAndDeposit` at a stale `amountOutMin`, allowing an MEV-style extraction of value during the swap since the "protection" price is itself wrong.

This is a real loss-of-funds vector against the paymaster's own balance (EntryPoint deposit, treasury surplus), not merely a stale-quote inconvenience, satisfying the Medium bar for unbacked value extraction via a mispriced oracle.

### Likelihood Explanation
Sequencer downtimes on Arbitrum/Base/Optimism, while infrequent, are a recurring, publicly observable event (and have occurred historically on these networks). Any actor monitoring sequencer status can time UserOperation submissions (or direct RPC submission to the L2 node, bypassing normal sequencer ordering during downtime is not even required — stale reads persist through the whole outage window) to exploit the frozen price. No special privilege, governance action, or race condition is needed; only a public UserOperation submission through the standard permissionless paymaster path.

### Recommendation
Add an L2 Sequencer Uptime Feed check (Chainlink's `AggregatorV2V3Interface` sequencer feed) inside `_getOraclePrice`, reverting if `answeredInRound`/`startedAt` indicates the sequencer is down or if less than Chainlink's recommended grace period (e.g., 1 hour) has elapsed since it came back up, mirroring Chainlink's official L2 oracle consumption pattern. Make the sequencer-feed address and grace period configurable per-deployment (similar to `maxOracleAge`) so chains without such a feed (e.g., non-L2 deployments) can disable the check explicitly rather than it being silently absent everywhere.

### Proof of Concept
1. Deploy `SimplexPaymaster` on Arbitrum via `DeploySimplexPaymaster.s.sol` with a Chainlink `nativeOracle`/token oracle (`evm/script/DeploySimplexPaymaster.s.sol` lines 14-52).
2. Simulate an Arbitrum sequencer outage (feed's `updatedAt` stops advancing) while `block.timestamp` keeps advancing but stays within `maxOracleAge` (e.g., 90,000s per the default deploy config).
3. Call `getTokenPrice`/submit a `UserOperation` using stale-favorable pricing; `_getOraclePrice` (`evm/src/utils/SimplexPaymaster.sol` lines 662-676) returns the frozen answer without reverting, letting the operation prefund at an incorrect rate, and `testStaleOracleReverts`/`testNonPositiveOraclePriceReverts` in `evm/tests/foundry/SimplexPaymasterTest.t.sol` (lines 245-263) confirm no sequencer-liveness check exists — only staleness and sign checks are exercised.

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
