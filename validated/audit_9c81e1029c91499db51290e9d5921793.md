### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook shop-spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (and `topic`, `api_version`, `webhook_id`) values acted on by the app entirely from unauthenticated HTTP headers, while the HMAC signature verified by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body. This breaks the intended binding of "shop that produced this HMAC" == "shop the app attributes the webhook to."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `Request#shop` (used downstream to identify the tenant) is read straight from the `x-shopify-shop-domain` / `shopify-shop-domain` header, with no cryptographic binding to the body or to the HMAC: [2](#0-1) 

`HmacValidator.validate` computes the signature exclusively from `to_signable_string` (i.e., the raw body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` validates only this body-based HMAC, then immediately trusts `request.shop` (along with `request.topic`, `request.api_version`, `request.webhook_id`) to build the `WebhookMetadata` that is handed to the app's registered handler: [4](#0-3) 

Because the shop header is not part of the signed payload, any HTTP request carrying a body+HMAC pair that is valid for *some* shop (e.g., one legitimately produced for the attacker's own store, which they fully control and can trigger webhooks from) can be replayed to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop. The signature still validates (it only checks the body), but the app's webhook handler will process/attribute the event as if it came from the victim's tenant. This is exactly the "field acted on but not covered by the HMAC" binding break: the equality the code implicitly assumes is `hmac_owner(shop) == request.shop`, but the implementation only enforces `hmac_owner(body) == hmac`, leaving `request.shop` completely unauthenticated.

### Impact Explanation
If the integrating app uses `WebhookMetadata#shop` (as most Shopify apps do) to select which merchant's record to update/delete/create in its own database, an attacker who controls one shop (installable by anyone, no special privilege) can forge the tenant context of a webhook and cause the app to write/act on data under a different shop's identity — a cross-tenant access/data-integrity issue, one of the explicitly listed Critical impacts ("cross-tenant access").

### Likelihood Explanation
Exploitation only requires: (1) installing the app on an attacker-owned shop to legitimately obtain a valid `raw_body` + HMAC pair for some webhook topic, and (2) sending that captured body/HMAC to the app's public webhook endpoint with a modified `x-shopify-shop-domain` header pointing at the victim shop. No access token, `client_secret`, or privileged account is required — this fits squarely within an "unprivileged internet user" threat model.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signed material, or otherwise cryptographically bind the `shop` value to the payload before trusting it, e.g. by cross-checking `request.shop` against the shop associated with the specific `webhook_id`/subscription server-side, or by only trusting shop attribution from data embedded within the verified JSON body rather than from headers. At minimum, document that consumers must independently verify the `shop` returned in `WebhookMetadata` matches an expected/registered tenant rather than trusting it implicitly.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com` and capture a legitimate webhook delivery: raw body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(secret, B)`.
2. Send a POST to the app's webhook endpoint with the same body `B` and header `H`, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `HmacValidator.validate` succeeds because it only checks `H` against `HMAC(secret, B)`. [5](#0-4) 
4. `Registry.process` builds `WebhookMetadata` with `shop: request.shop` = `"victim-shop.myshopify.com"`, even though the payload actually originated from `attacker-shop.myshopify.com`. [6](#0-5) 
5. The app's handler processes the (attacker-controlled) payload under the victim's tenant identity.
