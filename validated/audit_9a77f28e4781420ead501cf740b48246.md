### Title
Webhook `shop-domain` header is trusted for tenant identification but excluded from the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC that `Utils::HmacValidator.validate` checks never covers the `shopify-shop-domain` (or `topic`, `api-version`, `webhook-id`) header. `Registry.process` nonetheless trusts `request.shop` as the authenticated tenant identity when dispatching to the app's webhook handler. Any party able to obtain one genuinely-signed webhook delivery for the app (e.g. by installing the app on their own store) can replay that exact body/HMAC pair while substituting an arbitrary `shop-domain` header, causing the app to process the payload as if it came from a different merchant.

### Finding Description
The HMAC validation flow is:
- `HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to `verifiable_query.hmac` using `OpenSSL.secure_compare` [1](#0-0) .
- For webhooks, `to_signable_string` is defined as just `@raw_body`, and `shop` is read directly from an unsigned header with no cross-check against the signed content [2](#0-1) .
- `Registry.process` validates the HMAC and then immediately forwards `request.shop` (the unsigned header value) into `WebhookMetadata`, which is handed to the app's registered handler as the identified tenant [3](#0-2) .

The equality that should hold is: `shop bound by the HMAC == shop acted upon by the handler`. Instead, the gem verifies `HMAC(raw_body)` but acts on `shop` taken from an independent, unauthenticated header — breaking that binding. Any actor who can obtain a legitimately-signed webhook for *some* shop that has the app installed (this is simply the normal, unprivileged act of installing a public/embedded app on any store) possesses a valid `(raw_body, hmac)` pair. Because `shop` is excluded from the signed content, that pair remains valid for any other `shop-domain` header value. Replaying it against the app's webhook endpoint with the victim shop's domain in the header passes `HmacValidator.validate` unchanged and results in `WebhookMetadata#shop` reporting the victim's domain to the handler.

### Impact Explanation
This breaks the tenant-identity binding the whole HMAC check exists to enforce, letting an attacker who controls (or briefly installs the app on) their own store make the app process a webhook — with attacker-controlled topic/body content bounded by whatever genuine payload they captured — under an arbitrary victim shop identity. Any host-app logic keyed on `WebhookMetadata#shop` (e.g. per-shop data handling, mandatory `shop/redact`/`customers/redact` compliance actions, cache/session invalidation, billing state) can be triggered for the wrong tenant, i.e. cross-tenant access/confusion, without ever needing the app's `client_secret`, an access token, or any credential belonging to the victim.

### Likelihood Explanation
Exploitation requires no privileged material: an attacker only needs to be able to receive one valid webhook delivery for the app (trivially achievable by installing the app on any store they control, which is the intended unprivileged entry point of a merchant-facing Shopify app) and then send an HTTP POST with a modified `shopify-shop-domain`/`x-shopify-shop-domain` header to the app's webhook endpoint. No timing race, no secret leakage, and no host-application misuse of the documented API is required — `Registry.process` is used exactly as intended.

### Recommendation
Include the shop domain (and other identifying headers such as topic/webhook-id) in the HMAC-signed content, or otherwise cryptographically bind them, e.g. by having `to_signable_string` incorporate the `shop-domain` header alongside the raw body, so that a signature valid for one shop cannot be replayed with a different shop identity substituted in.

### Proof of Concept
1. Install the target app on an attacker-controlled store `attacker.myshopify.com`; trigger any subscribed webhook topic and capture the resulting HTTP request, including its genuine `x-shopify-hmac-sha256` header and raw body.
2. Replay that captured request to the app's webhook endpoint, changing only the `x-shopify-shop-domain` header to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because `Request#to_signable_string` returns only `@raw_body`, unaffected by the header change [4](#0-3) .
4. The registered handler is invoked with `WebhookMetadata.new(... shop: request.shop ...)` reporting `victim-shop.myshopify.com` [5](#0-4) , causing the app to perform shop-scoped processing for a tenant that never sent the webhook.
