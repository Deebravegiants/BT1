### Title
`queued_bytes` desynchronizes from real page sizes across the v5→v6 storage migration, letting senders bypass the delivery-fee escalation threshold - (File: cumulus/pallets/xcmp-queue/src/migration/v6.rs)

### Summary
`unversioned::UncheckedMigrateV5ToV6::on_runtime_upgrade` seeds the newly introduced `queued_bytes` field to `0` for every existing outbound channel, even when that channel already has non-empty pages sitting in `OutboundXcmpMessages` between `first_index` and `last_index`. Because `Pallet::send_fragment` only ever *adds* to `queued_bytes` (it never resyncs against the real page contents), any channel with a pre-migration backlog will have a `queued_bytes` value that understates the true byte total for as long as that backlog remains in the queue, weakening the delivery-fee-factor escalation check in `send_fragment`.

### Finding Description
`UncheckedMigrateV5ToV6::translate` maps every pre-existing `v5::OutboundChannelDetails` into the new v6 struct with `queued_bytes: 0` regardless of `first_index`/`last_index`: [1](#0-0) . If a channel had, say, 3 pages already stored under `OutboundXcmpMessages[recipient, 0..3]` at the time of the upgrade, `queued_bytes` becomes `0` even though the real occupied size is the sum of those pages' encoded lengths.

Post-migration, `Pallet::send_fragment` never recomputes `queued_bytes` from the actual stored pages — it only increments it by the newly appended fragment/page length: [2](#0-1) . This means any unprivileged user who triggers an XCM send (via `send_xcm` -> `SendXcm::deliver` -> `send_fragment`) after the upgrade will keep accumulating `queued_bytes` on top of the wrong `0` baseline, so the tracked value stays lower than the real byte count of the channel by exactly the pre-migration backlog size.

The only place `queued_bytes` is reset to a value consistent with reality is when the channel fully drains (`first_index == last_index`), where it's explicitly zeroed: [3](#0-2) . Until that full drain happens, `take_outbound_messages` only ever *subtracts* real page lengths via `saturating_sub`, which cannot correct an already-understated counter (it just saturates at 0 sooner than it should): [4](#0-3) .

The fee-escalation check that is scoped in this question relies directly on this drifting counter: [5](#0-4) 
Because `queued_bytes` is undercounted relative to `threshold = max_total_size / THRESHOLD_FACTOR`, `increase_fee_factor` is triggered later than it should be (or not at all) while the pre-migration backlog is still resident in the channel. No signature, origin, or weight check is relevant here — this is a pure state-accounting gap between the migration and the ordinary `send_fragment` code path, both of which are legitimate, unprivileged-reachable code.

Note the v6→v7 migration (`cumulus/pallets/xcmp-queue/src/migration/v7.rs`) does the exact same zero-seeding of `queued_bytes` and comments it as `// Corrects itself over time.` [6](#0-5) , confirming that maintainers are aware `queued_bytes` can start out of sync after a migration and rely on it "correcting" only once a channel fully drains — the same limitation applies to `UncheckedMigrateV5ToV6`, just without an explicit comment.

### Impact Explanation
For any HRMP channel that already has queued outbound pages at the moment of the v5→v6 upgrade, `queued_bytes` starts at `0` instead of the real backlog size. Any unprivileged account can then call `send_xcm` (teleport, reserve transfer, arbitrary XCM program, etc.) targeting that sibling, causing `send_fragment` to be invoked and the counter to keep understating true occupancy. As a result, `Self::increase_fee_factor` is not triggered when it should be, so delivery fees for that channel stay artificially low relative to actual congestion until the pre-existing backlog is fully drained (`first_index == last_index`, at which point `queued_bytes` is force-reset to `0`, coincidentally correct at that instant). This is not a fund-theft or double-spend issue, but it does defeat the intended anti-congestion/fee-escalation economic control for the duration the stale backlog persists, which can be extended indefinitely by a sender who keeps the channel non-empty.

### Likelihood Explanation
Requires only that a parachain upgrades cumulus-pallet-xcmp-queue from storage v5 to v6 while it has any non-empty outbound HRMP channel (a very common, not edge-case, production condition — busy channels almost always have queued pages). No governance or privileged action from the attacker is needed post-upgrade: ordinary `send_xcm` calls from any signed account, precompile, or XCM execution path exercise `send_fragment`. The divergence is fully deterministic and reproducible in a unit test.

### Recommendation
When performing the v5→v6 (and similarly v6→v7) translation, compute `queued_bytes` by summing the encoded lengths of the existing `OutboundXcmpMessages` pages for `first_index..last_index` for each channel instead of hard-coding `0`, so the invariant `queued_bytes == sum(page lengths)` holds immediately after the migration.

### Proof of Concept
Rust unit test in `cumulus/pallets/xcmp-queue/src/tests.rs` (or a new migration test module):
1. Set `StorageVersion` to 5, and use `v5::OutboundXcmpStatus` storage alias to insert an `OutboundChannelDetails` for a sibling `ParaId` with `first_index = 0`, `last_index = 3`.
2. Directly insert three non-trivial pages into `OutboundXcmpMessages::<Test>` for indices `0..3` (simulating pre-existing backlog).
3. Run `UncheckedMigrateV5ToV6::<Test>::on_runtime_upgrade()`.
4. Assert immediately: `status_for(sibling).queued_bytes == 0` while `actual_queued_bytes(sibling, &status_for(sibling)) > 0` — proving the desync exists right after migration.
5. Call `send_xcm::<XcmpQueue>(...)` a few times and assert at each step that `status.queued_bytes != actual_queued_bytes(sibling, &status)`, demonstrating the drift persists across ordinary sends.
6. Drain via repeated `XcmpQueue::take_outbound_messages(1, &[])` until the channel is empty, and assert `queued_bytes == 0 == actual_queued_bytes(...)` only once `first_index == last_index`, confirming the counter is wrong for the entire time the pre-migration backlog exists.
