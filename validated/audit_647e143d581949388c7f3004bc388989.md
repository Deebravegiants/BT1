### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity claimed via headers is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers that are never included in the signed content. `Registry.process` validates the HMAC over the body alone and then forwards `request.shop` unauthenticated into the app's `WebhookHandler#handle` callback as the tenant identity for the event.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`, which for webhooks is defined as just `@raw_body`: [1](#0-0)  Meanwhile `shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header without being part of the signable string: [2](#0-1) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e., body-only HMAC) before constructing `WebhookMetadata` with `shop: request.shop` and dispatching it to the app-provided handler: [3](#0-2)  `WebhookMetadata` is the struct contract the gem hands to host applications as the authenticated event identity: [4](#0-3) 

The identity binding that should hold is: `shop claimed in WebhookMetadata.shop == shop that produced/authorized the signed body`. Because the header is outside the HMAC, this equality is never checked. `client_secret` (the HMAC key) is shared across every shop that installs a given app — it is not shop-specific. Consequently, any merchant who has installed the app (an unprivileged holder of one legitimate, validly-signed webhook body/HMAC pair from their own shop) can replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary victim `shop-domain` header. `Utils::HmacValidator.validate` will pass (it only re-derives the signature from the body and the app's single shared secret), and the handler will receive `WebhookMetadata.shop` set to the attacker-chosen victim shop.

### Impact Explanation
This breaks the tenant boundary the gem is documented to provide: host applications key their data (installation records, order/customer data, redaction/uninstall actions, etc.) off `WebhookMetadata.shop`, trusting that the gem has authenticated it. An attacker-merchant can inject events attributed to a shop they do not own — e.g., trigger `app/uninstalled` or GDPR redact-style webhooks (whose bodies are shop-agnostic or attacker-influenced) and replay them with a forged victim `shop-domain`, causing the host app to act on the victim tenant's data (deletion, state changes, cross-tenant data corruption). This is a cross-tenant access violation stemming purely from this gem's webhook verification contract.

### Likelihood Explanation
Requires only that the attacker's own shop has the app installed (a normal, unprivileged condition — no access token, `client_secret`, or leaked credentials needed) and the ability to capture one legitimately-delivered webhook body+HMAC and replay it with a modified header, both of which are trivial for any app-installing merchant.

### Recommendation
Include the shop domain (and preferably topic/webhook_id/api_version) in the signable content used for HMAC validation, or otherwise cryptographically bind the claimed `shop` header to the specific installation/secret before constructing `WebhookMetadata`, e.g., by verifying `request.shop` against the shop associated with the specific per-shop access token/session rather than trusting the header outright.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; trigger a webhook whose topic/body is shop-agnostic or attacker-influenced (e.g., an event with attacker-controlled cart/checkout data).
2. Capture the raw POST: headers `x-shopify-hmac-sha256: <valid-hmac>`, `x-shopify-shop-domain: attacker.myshopify.com`, and the raw body.
3. Replay the identical body and `hmac` header to the app's webhook endpoint, but change `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the (unchanged) body against the (unchanged) HMAC — validation succeeds. `WebhookMetadata.shop` is now `victim.myshopify.com`, and the host app's handler processes the event as if it originated from the victim tenant.
