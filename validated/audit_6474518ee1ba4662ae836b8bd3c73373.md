This confirms the analog exists. `Zap._swapOnUniswapV2` reads `amountOut = IUniswapV2Pair(pair).getAmountOut(amountIn, tokenIn)` from the pair's live reserves at execution time and then immediately uses that exact same value as the output amount passed to `pair.swap()` [1](#0-0) . This is invoked by both `_buyOnUniswapV2` and `_sellOnUniswapV2` for every post-graduation trade routed through `Zap.buy`/`Zap.sell` [2](#0-1) .

### Title
Post-graduation swaps in `Zap._swapOnUniswapV2` use a self-referencing quote as the actual swap amount, making the user-supplied `minTokensOut`/`minUsdcOut` the only real slippage protection and leaving buyers/sellers exposed to sandwich attacks - (File: `packages/contracts/src/Zap.sol`)

### Summary
`_swapOnUniswapV2` calls `pair.getAmountOut(amountIn, tokenIn)` against the *live* HyperSwap pair reserves and feeds that value straight into `pair.swap(...)` as the exact output/input amounts [3](#0-2) . Exactly as in the Sherlock finding (`get_dy()` used both to compute the "protective" minimum and to price the actual `exchange()`), this quote-then-execute-with-the-same-formula pattern provides no independent slippage floor at the swap layer itself — the only protection against price movement is the caller-supplied `minTokensOut` / `minUsdcOut` checked afterward in `Zap._buyInternal`/`_sellInternal`.

### Finding Description
`_buyOnUniswapV2` and `_sellOnUniswapV2` both funnel through `_swapOnUniswapV2`, which:
1. Reads the pair's current reserves via `getAmountOut(amountIn, tokenIn)`.
2. Transfers `amountIn` to the pair.
3. Calls `pair.swap(amount0Out, amount1Out, address(this), "")` using that exact just-computed quote as the swap output [3](#0-2) .

There is no independent, protocol-enforced minimum baked into the swap call itself (`amount0Out`/`amount1Out` are simply whatever the live quote says) — this differs structurally from `Bonding._pairRebalance`, where `min0=1, min1=1` is *deliberately* loose because the ratio is set by the same atomic-tx caller and there's no third party to defend against (per the `AGENTS.md` note) [4](#0-3) . In `Zap`'s case, by contrast, the swap venue is *externally influenceable* (the HyperSwap V2 TOKEN/LT pool, in scope per the prompt's "pre-creating or pre-seeding the HyperSwap V2 TOKEN/LT pair" bullet), so the quote-at-execution-time pattern is exactly the vulnerable shape from the report: a third party (a sandwiching bot) can move the pair's reserves between when Alice's transaction is broadcast and when it lands, and the `getAmountOut` call inside her own transaction will simply reflect the post-front-run price — it can never "catch" the manipulation because it's not an independent oracle, it's the same AMM formula being executed.

The overall protection for the end user therefore reduces entirely to the caller-supplied `minTokensOut` (buy, checked at `Zap.sol` line 256) or `minUsdcOut` (sell, checked at line 460) [5](#0-4) [6](#0-5) . This is standard, correct design *only if* front-ends and integrators always populate a tight, non-zero `minTokensOut`/`minUsdcOut`. If a caller (bot, integrator, or a user via a front-end default) submits `0` or a very loose bound — as the codebase's own tests repeatedly do, e.g. `zap.sell(tokenAddr, sellerTokens, 0)` [7](#0-6)  and `zap.buy(tokenAddr, buyAmount, 0, referrer)` [8](#0-7)  — the swap executes at whatever price the pair currently reports, with zero on-chain floor, and the trader absorbs the full sandwich loss. This mirrors the Sherlock report precisely: the "protection" (`get_dy` there, `getAmountOut` here) is mathematically identical to the execution formula, so it degenerates to a pass-through whenever the caller doesn't independently supply a tight bound.

### Impact Explanation
Any unprivileged trader calling `Zap.buy`/`Zap.sell` (or their permit variants) on a graduated token with a loose or zero `minTokensOut`/`minUsdcOut` can be sandwiched by an MEV bot: front-run to move the HyperSwap pair's reserves unfavorably, have the victim's swap execute at the manipulated `getAmountOut` price with no independent floor, then back-run to capture the spread. This is a direct value-extraction/theft-of-trader-funds impact, consistent with the "Accept only concrete theft ... of trader ... funds" validation criterion. Because `Zap` is the only sanctioned production entry point for retail post-graduation swaps (the HyperSwap router itself is bypassed intentionally per the AGENTS.md non-standard-ABI note), every post-graduation trade through the front end is exposed to this pattern whenever slippage bounds are loose.

### Likelihood Explanation
Medium-High. Post-graduation is the terminal, most heavily traded state for a successful token (curve exhausted or USD threshold hit), so trade volume through this path is significant. The likelihood of a victim submitting a loose bound is realistic: the repo's own default UX/test pattern uses `0` liberally, and unlike the Curve-pool report where a knowledgeable integrator might reasonably expect `get_dy` to be a "quote," here it's even more subtly self-referencing since it's used inline in the exact same call that executes the trade. Any MEV-aware bot watching the HyperSwap pair can trivially detect and sandwich a pending `Zap` swap given the transparent quote-then-swap pattern.

### Recommendation
Do not rely solely on caller-supplied `minTokensOut`/`minUsdcOut` as the only defense at the V2 swap boundary. At minimum:
- Enforce a non-zero, meaningfully-bounded `minTokensOut`/`minUsdcOut` at the `Zap` level for post-graduation trades (reject `0` or trivially loose bounds), or
- Pass the caller's slippage bound down into `_swapOnUniswapV2` and check it against `amountOut` immediately after computing the quote and before executing `pair.swap`, so the check is explicit at the swap layer rather than only after refunds/fees are applied further up the call stack, or
- Add a TWAP- or oracle-based sanity check independent of the pair's instantaneous reserves for the swap venue, analogous to the original report's suggested fix of requiring `get_dy > 105% * amountIn` before trusting the live quote.

### Proof of Concept
1. Token `T` graduates; `Bonding.graduatedPair(T)` points to the live HyperSwap `T`/`LT` pair.
2. Alice calls `Zap.sell(T, tokenAmount, 0)` (or any loose `minUsdcOut`), which routes to `_sellOnUniswapV2` → `_swapOnUniswapV2(T, lt, tokenAmount)` [9](#0-8) .
3. Bob observes Alice's pending transaction in the mempool and front-runs it with a swap on the same HyperSwap pair that shifts reserves unfavorably for Alice's direction.
4. Alice's transaction lands; `_swapOnUniswapV2` calls `getAmountOut(tokenAmount, T)` against the now-manipulated reserves, computes a depressed `amountOut`, and executes `pair.swap` at that depressed rate [3](#0-2) . Because `minUsdcOut` was `0`/loose, the downstream check `if (usdcOut < minUsdcOut) revert SlippageExceeded();` never fires [6](#0-5) .
5. Bob back-runs to restore the pool and pocket the spread extracted from Alice — the classic sandwich, enabled by the absence of any independent floor at the point the swap quote is generated and consumed in the same call.

    function _swapOnUniswapV2(
        address tokenIn,
        address tokenOut,
        uint256 amountIn
    ) internal returns (uint256 amountOut) {
        Bonding bonding_ = _s().bonding;
        // `graduatedPair` is keyed by the launched token only; check `tokenIn`
        // first (sell direction) then fall back to `tokenOut` (buy direction).
        address pair = bonding_.graduatedPair(tokenIn);
        if (pair == address(0)) pair = bonding_.graduatedPair(tokenOut);

        bool inIsToken0 = IUniswapV2Pair(pair).token0() == tokenIn;
        // Quote from the pair so the output tracks its live fee instead of a
        // hardcoded rate, keeping `amountOut` consistent with the K-check.
        amountOut = IUniswapV2Pair(pair).getAmountOut(amountIn, tokenIn);

        IERC20(tokenIn).safeTransfer(pair, amountIn);

        (uint256 amount0Out, uint256 amount1Out) = inIsToken0 ? (uint256(0), amountOut) : (amountOut, uint256(0));
        IUniswapV2Pair(pair).swap(amount0Out, amount1Out, address(this), new bytes(0));
    }
