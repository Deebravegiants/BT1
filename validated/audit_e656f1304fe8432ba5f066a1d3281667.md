Based on my investigation of the in-scope `contracts/**` and `circuits/**` code, I found a valid critical analog to the "signature replayable / unverified signed parameters" bug class — but it is stronger than the original report: it is a **complete authorization bypass**, not merely a replay.

### Title
Unauthenticated arbitrary-call execution via the vacuous `MainEVMCircuitMin` proof combined with the zero-signer bypass in `EmporiumUpgradeable.verifyWallet` - (File: `circuits/MainEVMCircuitMin.circom`, `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
The Krystal report's root cause is that a value-carrying action was accepted without actually checking it matched anything the authorized party signed. The same equality break exists here: for the Emporium "Min" dimension path (`tokenNumber == 0`), the circuit that is supposed to prove the caller controls a shielded key proves *nothing at all*, and the Solidity-side wallet-signature check is itself skipped whenever `signerAddress == address(0)`. Together, these let any unprivileged EOA execute arbitrary calls (with attacker-chosen `value`) from the `Emporium` contract's own funds.

### Finding Description
`HinkalHelper.formInputForCircom` routes to `formInputEmporiumMin` whenever `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0`: [1](#0-0) 

That input path only feeds `emporiumMessage`, `timeStamp`, and `calldataHash` into the proof, and is verified by `MainEVMCircuitMin`, which contains **no signature verification at all** — no `SignatureVerifier`, no nullifier check, no linkage of `calldataHash`/`outTimeStamp` to any private signal: [2](#0-1) 

Compare this to the normal-dimension circuit `MainEVMCircuit`, which does enforce `sigVerifier` (EdDSA over `signedMessageHash`) and nullifier/Merkle-root equalities: [3](#0-2) 

`dimensionsCheck` forces `erc20TokenAddresses`, `amountChanges`, `inputNullifiers`, `outCommitments` etc. to be **empty arrays** when `dimensions.tokenNumber == 0`, so none of these fields constrain anything either: [4](#0-3) 

`calldataHash` itself is only checked for internal consistency (`getHashedCalldata(circomData) == circomData.calldataHash`) — a pure hash-of-calldata check computable by anyone, with no secret involved: [5](#0-4) 

Thus a Groth16 proof for `MainEVMCircuitMin` requires **no private key, no nullifying key, no UTXO ownership** — any party can generate a valid proof for arbitrary `calldataHash`/`outTimeStamp` values using only public circuit artifacts.

This trivial proof is enough to reach `Hinkal.transact()` → `EmporiumUpgradeable.runAction()`, whose only remaining authorization gate is `verifyWallet`. That function accepts `signerAddress == address(0)` and returns **immediately with zero checks**, only marking `emporiumMessage` as used: [6](#0-5) 

With `signerAddress == address(0)`, `runAction` executes attacker-supplied `ops` as stateless calls, spending the Emporium contract's own ETH/token balance (`op.endpoint.call{value: op.value}(op.callData)`), restricted only to blocking the `callHinkalWallet`/`doSendToRelay` selectors: [7](#0-6) 

The equality broken: the protocol assumes "a valid Groth16 proof + `CircomData` implies the caller is an authorized key holder / wallet owner", but for this specific dimension/action combination the proof carries no such guarantee, and the Solidity fallback path also carries none.

### Impact Explanation
This is a proof-verification-bypass / unauthorized-asset-movement vulnerability (Critical per the rubric): an unprivileged attacker can trigger arbitrary external calls with attacker-chosen `value` funded from the `Emporium` contract's balance (which accumulates relay fees and in-flight token/ETH balances per `getBalancesForArray`/`handleOut`), without holding any shielded key, wallet key, or role. This can drain protocol/relay funds or any user funds temporarily routed through the Emporium contract during multi-step operations.

### Likelihood Explanation
High — requires only public circuit artifacts (proving key) to fabricate a `MainEVMCircuitMin` proof (no secret needed) and constructing a standard `Hinkal.transact()` call with a crafted `CircomData`/`EmporiumStack(signerAddress=address(0))`. No privileged role, relayer, or third-party key is required, satisfying the "unprivileged EOA" constraint.

### Recommendation
- Remove/disable the `Min` circuit path for the Emporium action, or add real ownership constraints to `MainEVMCircuitMin` (e.g., require an EdDSA signature over `calldataHash`/`emporiumMessage` bound to a registered key), and bind `calldataHash`/`emporiumMessage` into an actual circuit constraint instead of leaving them as free public signals.
- In `EmporiumUpgradeable.verifyWallet`, never allow full authorization bypass for `signerAddress == address(0)`; require the containing ZK proof to have genuinely authenticated the caller (i.e., forbid dispatching to `runAction` unless `tokenNumber > 0`/a real signature-bearing circuit was used, or require explicit funding/ownership checks before permitting external calls funded by the Emporium contract's balance).

### Proof of Concept
1. Attacker (no relationship to Hinkal, no shielded balance) computes a `CircomData` struct with `erc20TokenAddresses = []`, `amountChanges = []`, `inputNullifiers = []`, `outCommitments = []`, `onChainCreation = []`, `slippageValues = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, and `externalActionData.externalActionMetadata = abi.encode(EmporiumStack{v:0,r:0,s:0, signerAddress:address(0), ops:[EmporiumOperation({endpoint: attacker, invokeWallet:false, value: X, callData: ""})], maxFee:0, deadline:0})`.
2. Attacker computes `calldataHash = getHashedCalldata(circomData)` (pure function, no secret) and sets it in `circomData`.
3. Attacker generates a Groth16 proof for `MainEVMCircuitMin` with any `messageSeed`, satisfying the only constraint `message === Poseidon(messageSeed)` — no private key required.
4. Attacker calls `Hinkal.transact(a, b, c, dimensions{tokenNumber:0,...}, circomData)`.
5. `performHinkalChecks` passes (hash matches, dimensions match zero-length arrays), `verifyProof` passes (trivial circuit satisfied), dispatch reaches `EmporiumUpgradeable.runAction`.
6. `verifyWallet` sees `signerAddress == address(0)` and returns without any check.
7. `runAction` executes the attacker's op, sending `X` wei from the Emporium contract to the attacker's address.

Note: I was not able to fully trace the exact dispatch code inside `Hinkal.sol` that routes `externalActionData.externalActionId` to `externalActionMap[...].runAction(...)` (only lines 1–60 of `Hinkal.sol` were inspected), so the precise call plumbing from `transact()` to `runAction()` should be re-verified, though `ExternalActionBaseUpgradeable.onlyAllowedRecipient` confirms `runAction` is only callable by an allow-listed caller (presumably the `Hinkal` contract itself), which does not mitigate this issue since the attacker reaches it through the legitimate `transact()` entrypoint.
