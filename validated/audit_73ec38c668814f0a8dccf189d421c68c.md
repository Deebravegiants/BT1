### Title
Capture-replay of cross-chain calldata authorization via `frame_system` account-nonce reuse - ([File: modules/pallets/hyper-fungible-token/src/module.rs])

### Summary
`HyperFungibleToken::on_accept` executes user-supplied calldata (a signed `runtime_call`) on behalf of a bridged token's beneficiary, using the beneficiary's ordinary `frame_system` account nonce as the anti-replay value. Because this nonce is shared with, and can be reset by, normal account lifecycle events (reaping/killing an account and later recreating it resets `frame_system::AccountNonce` to `0`), a previously captured, already-executed signed calldata payload can become valid again and be re-executed through a brand-new ISMP `PostRequest`. This mirrors the reported Apache APISIX `hmac-auth` issue: a signed authorization token is checked against a mutable counter instead of a value that is guaranteed never to repeat, letting an attacker "re-use a token forever."

### Finding Description
`on_accept` in [1](#0-0)  authenticates only the source chain/contract pair via `ContractToAsset::<T>::get(source, &from)`; the `body`/`data` payload of the bridged message (which contains the optional `SubstrateCalldata { signature, runtime_call }`) is otherwise attacker-influenced content carried across the bridge.

When calldata is present, the pallet recovers the intended origin and verifies a signature over `(nonce, runtime_call)` where the nonce is read live from chain state: [2](#0-1) 

After a successful dispatch, the nonce is advanced with the ordinary system-account API: [3](#0-2) 

This uses `frame_system::Pallet::<T>::account_nonce` / `inc_account_nonce`, i.e. the exact same nonce counter that `frame_system::CheckNonce` uses for ordinary signed extrinsics from that account, and that Substrate resets to `0` when an account is reaped (balance and reference count drop to zero) and later recreated. There is no separate, monotonically non-resettable "bridge nonce" or expiry/timestamp bound into the signed payload, and no commitment/idempotency tag (unlike the relayer-fee claim flows, which key off content-derived commitments — see `modules/pallets/relayer/src/outbound_request.rs` and `outbound_consensus.rs`, which explicitly document commitment-based replay protection).

Because a fresh `PostRequest` from the same whitelisted `(source, from)` pair receives its own unique ISMP-level commitment (built from `source, dest, nonce, from, to, timeout_timestamp, body` at the ISMP layer), pallet-ismp's request-receipt de-duplication (`modules/ismp/core/src/handlers/request.rs`) does not block re-delivery of an *old* `SubstrateCalldata` payload embedded in a *new* request. If the beneficiary account's on-chain nonce has since returned to the value that was originally signed (via reaping/recreation, or via any other mechanism that could desynchronize the live nonce from its monotonically-increasing intent), an old signed `runtime_call` becomes valid again and is dispatched a second time with `RawOrigin::Signed(beneficiary)`.

### Impact Explanation
A successfully replayed `runtime_call` executes with the full authority of `RawOrigin::Signed(beneficiary)`, subject only to the runtime's `BaseCallFilter`. Depending on what call was originally signed (e.g., a `Balances::transfer_allow_death`, an approval, a governance vote, or any other filtered-but-permitted call), this allows an unauthorized, unintended re-execution of a financial or state-changing action attributable to the beneficiary — a concrete "unauthorized app action" per the validation criteria. This is reachable by a permissionless message dispatcher/relayer needing only to resubmit previously observed on-chain calldata inside a new cross-chain transfer to the same recipient.

### Likelihood Explanation
Exploitation requires the target beneficiary account to pass through a nonce-reset condition (reaping to zero balance/references, then recreation) while an old signed `SubstrateCalldata` remains available (it is public, since it travels on-chain in a prior `PostRequest`). This is a real, if not universally triggerable, condition in Substrate-based chains (existential-deposit sweeps, temporary/ephemeral accounts, or an attacker deliberately draining and later refunding an account they don't fully control but can observe) and does not require any privileged role — it can be attempted by an ordinary relayer or dispatcher. It is not "always exploitable," which keeps it at Medium rather than higher severity.

### Recommendation
Do not use the shared `frame_system` account nonce as the replay-protection value for cross-chain-authorized calldata. Introduce a dedicated, monotonically increasing (non-resettable) per-account nonce namespace specific to `hyper-fungible-token` calldata execution (independent of account reaping), and/or bind an expiry/timeout and the source chain/request identity into the signed payload so a captured signature cannot become valid again after nonce resets or across accounts.

### Proof of Concept
1. Beneficiary account `B` bridges a call, signing `(nonce=N, runtime_call=X)`; the message is delivered, `X` executes once, and `B`'s `frame_system` nonce advances from `N` to `N+1`.
2. `B`'s account is later reaped (balance and reference counters reach zero), resetting `frame_system::Account::<T>::get(B).nonce` to `0`, and is subsequently recreated (e.g., receives a new existential deposit) causing further transactions to occur such that its nonce again equals `N` — or, more directly, is reaped to `0` and then a bridged transfer is used to top it back up while a new inbound bridge message reuses `N` if `N == 0` in the simplest case.
3. An attacker (or the relayer network on behalf of anyone) resubmits the original, previously observed `SubstrateCalldata { signature, runtime_call: X }` inside a brand-new `PostRequest` bridging any (even minimal) token amount to `B`.
4. `on_accept` reads `nonce = account_nonce(B) == N`, reconstructs the same signed message, the signature verifies again, and `X` is dispatched a second time as `RawOrigin::Signed(B)` — demonstrated conceptually by the existing test `should_receive_asset_with_calldata` in [4](#0-3) , which only checks that an *immediate* re-submission (nonce already incremented to `1`) fails — it does not cover the case where the nonce cycles back to the originally-signed value after an account reset.

Note: I was not able to fully verify, within the indexed content available, the exact existential-deposit/reaping configuration of every runtime that includes this pallet, nor whether any runtime-level guard (e.g., minimum-nonce floor, `frame_system::Account` never-killed policy) is applied on top of `pallet-hyper-fungible-token` in production runtimes; confirming the precise reaping trigger conditions would require a full runtime configuration review beyond what the index exposes.

#[test]
fn should_receive_asset_with_calldata() {
	new_test_ext().execute_with(|| {
		// First send to escrow funds
		let params = SendParams {
			asset_id: HftNativeAssetId::get(),
			destination: StateMachine::Evm(1),
			recipient: BoundedVec::try_from(BOB.as_slice().to_vec()).unwrap(),
			timeout: 0,
			amount: SEND_AMOUNT,
			relayer_fee: Default::default(),
			call_data: None,
		};

		HyperFungibleToken::send(RuntimeOrigin::signed(ALICE), params).unwrap();

		// Build a runtime call: transfer from beneficiary to a final recipient
		let final_recipient = AccountId32::new([5u8; 32]);
		let runtime_call =
			crate::runtime::RuntimeCall::Balances(pallet_balances::Call::transfer_allow_death {
				dest: final_recipient.clone(),
				value: SEND_AMOUNT,
			})
			.encode();

		// Sign with sr25519
		let (pair, ..) = sp_core::sr25519::Pair::generate();
		let beneficiary_bytes = pair.public().0;
		let payload = (0u64, runtime_call.clone()).encode();
		let message_hash = sp_io::hashing::keccak_256(&payload);
		let raw_signature = pair.sign(&message_hash);
		let multisignature = MultiSignature::Sr25519(raw_signature).encode();

		let substrate_data = SubstrateCalldata { signature: Some(multisignature), runtime_call };

		let module = HyperFungibleToken::default();
		let post = PostRequest {
			source: StateMachine::Evm(1),
			dest: StateMachine::Kusama(100),
			nonce: 0,
			from: hft_contract(),
			to: pallet_hyper_fungible_token::PALLET_ID.to_bytes(),
			timeout_timestamp: 1000,
			body: {
				let msg = Message {
					from: alloy_primitives::Bytes::from(vec![0x11u8; 20]),
					to: alloy_primitives::Bytes::from(beneficiary_bytes.to_vec()),
					amount: {
						let bytes = convert_to_erc20(SEND_AMOUNT, 18, 10).to_big_endian();
						alloy_primitives::U256::from_be_bytes(bytes)
					},
					data: alloy_primitives::Bytes::from(substrate_data.encode()),
				};
				Message::abi_encode(&msg)
			},
		};

		module.on_accept(post.clone()).unwrap();

		// The calldata transferred tokens from beneficiary to final_recipient
		let final_balance = pallet_balances::Pallet::<Test>::free_balance(final_recipient);
		assert_eq!(final_balance, SEND_AMOUNT);

		// Replay should fail (nonce incremented)
		let result = module.on_accept(post);
		assert!(result.is_err());
	});
}
