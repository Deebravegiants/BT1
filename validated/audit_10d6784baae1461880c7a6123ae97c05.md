### Title
XCMP messages silently and permanently dropped when weight meter is exhausted mid-page, while HRMP watermark still advances past them - ([File: cumulus/pallets/xcmp-queue/src/lib.rs], [File: cumulus/pallets/parachain-system/src/lib.rs])

### Summary
`Pallet::enqueue_xcmp_messages` drops the tail of a batch when `search_best_by` finds the weight meter cannot afford the full batch, returning `Err(())` which stops processing of the remainder of the page. Critically, `enqueue_inbound_horizontal_messages` in `parachain-system` advances the `HrmpWatermark` unconditionally based on message metadata included in the inherent, regardless of whether `handle_xcmp_messages` actually enqueued all of them, so dropped messages can never be redelivered by the relay chain.

### Finding Description
`enqueue_xcmp_messages` computes `best_batch_footprint` via `batches_footprints.search_best_by(...)`, which binary-searches for the largest batch whose required weight fits in the remaining `meter` budget [2](#0-1) . If `best_batch_footprint.msgs_count < xcms.len()`, only the affordable prefix is enqueued via `T::XcmpQueue::enqueue_messages(xcms.iter().take(best_batch_footprint.msgs_count)...)`, and the function returns `Err(())`, causing `handle_xcmp_messages`'s inner loop to `break` and abandon the rest of that page for that sender [3](#0-2) [4](#0-3) . The dropped messages are never re-parsed or re-enqueued; the cursor `data` has already advanced past their bytes.

The critical missing safeguard is downstream: in `cumulus_pallet_parachain_system::Pallet::enqueue_inbound_horizontal_messages`, `HrmpWatermark::<T>::put(last_processed_block)` is set unconditionally after invoking `T::XcmpMessageHandler::handle_xcmp_messages`, and `last_processed_block` is derived only from the `sent_at` metadata of the messages present in the inherent — not from whether those messages were actually processed successfully [5](#0-4) . Because the relay chain's `check_hrmp_watermark` only requires the watermark to be monotonically increasing and to land on a block with messages (it has no way to know whether a parachain's runtime dropped some content) [6](#0-5) , once the parachain advances its own watermark past the block containing the dropped messages, the relay chain will never re-deliver those HRMP messages — they are gone permanently, and any assets that a legitimate reserve-transfer message was meant to deposit remain effectively lost/unreachable at the destination side.

The `messages_collection_size_limit()` used in `do_create_inherent` to decide which/how many messages to include in a block is purely PoV/size-based (1/6 of max block proof size) [7](#0-6) , and is not correlated with the `ReservedXcmpWeight` budget used by `handle_xcmp_messages` to actually process those messages [8](#0-7) . This means a page can be selected by size that nonetheless cannot be fully processed within the available weight, especially if per-message enqueue weight cost (driven by `T::WeightInfo::enqueue_xcmp_messages`, which factors in `msgs_count`, `size_in_bytes`, and `new_pages_count`) is disproportionate to raw byte size for certain message shapes.

### Impact Explanation
If triggered, the tail of a page's XCM messages — which may include legitimate `ReserveAssetDeposited`/`DepositAsset` instructions from other senders sharing the same channel/page batching window — are enqueued nowhere, are never retried, and the HRMP watermark advances past them, meaning the relay chain will not re-present them in a future inherent. Since delivery fees for HRMP are already paid/settled by the sender's chain when the message was sent (fees for XCMP are handled by the sending side, independent of destination processing), the destination-side drop constitutes silent, permanent loss of the intended cross-chain state transition (e.g., asset deposit), which can leave sender-side accounting (e.g., burnt reserve on sender chain for a teleport, or reserve-held assets for a reserve-transfer) permanently unbacked/unreachable on the destination.

### Likelihood Explanation
Reaching this requires: (1) a page of concatenated XCMP messages large enough, or shaped adversarially enough (e.g., many messages just under `XCM_BATCH_SIZE`, sized so that `T::WeightInfo::enqueue_xcmp_messages`'s weight grows faster than proportional to the size limit used at inherent-construction time) to exhaust the `ReservedXcmpWeight` budget mid-page; and (2) that page containing multiple senders/messages such that an innocent party's messages land after the point of exhaustion. This is feasible without any privileged/relayer access — a sending parachain's normal outbound queue construction (driven by ordinary users submitting multiple XCM-triggering extrinsics, e.g. several `pallet-xcm` reserve-transfer calls in the same block) determines message ordering and sizes, and this is a purely receiving-side accounting gap independent of whether the trigger is adversarial or simply a heavy but legitimate burst of traffic. The existing test `xcm_enqueueing_starts_dropping_on_out_of_weight` explicitly demonstrates and accepts the drop-on-out-of-weight behavior [9](#0-8) , but no accompanying test verifies that the HRMP watermark is *not* advanced past dropped messages, or that dropped messages remain redeliverable.

### Recommendation
Correlate `HrmpWatermark` advancement with actual processing success: `handle_xcmp_messages` (or a wrapper) should report how many messages/bytes per sender were actually enqueued versus dropped due to out-of-weight, and `enqueue_inbound_horizontal_messages` should only advance `last_processed_block`/`HrmpWatermark` up to the point that was verifiably processed, retrying the remainder in a subsequent block (analogous to how DMP's `ProcessedDownwardMessages` reflects true processed count). Alternatively, size the inherent-construction budget (`messages_collection_size_limit`) to be provably weight-safe relative to `ReservedXcmpWeight`, guaranteeing `handle_xcmp_messages` can never run out of weight for any page admitted into a block.

### Proof of Concept
Integration test plan (xcm-emulator or unit test against `cumulus-pallet-parachain-system` + `cumulus-pallet-xcmp-queue`):
1. Configure `ReservedXcmpWeight` to a small but realistic bound.
2. Build a single HRMP page containing N `ReserveAssetDeposited`/`DepositAsset`-style messages from a sender `ParaId`, sized so that `T::WeightInfo::enqueue_xcmp_messages` for the full batch exceeds `ReservedXcmpWeight`, forcing `enqueue_xcmp_messages` to return `Err(())` partway through.
3. Call `enqueue_inbound_horizontal_messages` with this page as inherent data.
4. Assert: `EnqueuedMessages`/message queue does NOT contain all N messages (some dropped) — confirms drop.
5. Assert: `HrmpWatermark::<T>::get()` equals `relay_parent_number` for that block (i.e., advanced past the dropped messages) — confirms the watermark does not reflect the drop.
6. Assert: no mechanism exists to re-include the dropped messages in any subsequent `do_create_inherent` call (since `drop_processed_messages` uses `LastProcessedHrmpMessage`, which was also advanced past all messages in the page) — confirms permanent, unrecoverable loss.

	/// Check that the candidate of the given recipient controls the HRMP watermark properly.
	pub(crate) fn check_hrmp_watermark(
		recipient: ParaId,
		relay_chain_parent_number: BlockNumberFor<T>,
		new_hrmp_watermark: BlockNumberFor<T>,
	) -> Result<(), HrmpWatermarkAcceptanceErr<BlockNumberFor<T>>> {
		// First, check where the watermark CANNOT legally land.
		//
		// (a) For ensuring that messages are eventually processed, we require each parablock's
		//     watermark to be greater than the last one. The exception to this is if the previous
		//     watermark was already equal to the current relay-parent number.
		//
		// (b) However, a parachain cannot read into "the future", therefore the watermark should
		//     not be greater than the relay-chain context block which the parablock refers to.
		if new_hrmp_watermark == relay_chain_parent_number {
			return Ok(());
		}

		if new_hrmp_watermark > relay_chain_parent_number {
			return Err(HrmpWatermarkAcceptanceErr::AheadRelayParent {
				new_watermark: new_hrmp_watermark,
				relay_chain_parent_number,
			});
		}

		if let Some(last_watermark) = HrmpWatermarks::<T>::get(&recipient) {
			if new_hrmp_watermark < last_watermark {
				return Err(HrmpWatermarkAcceptanceErr::AdvancementRule {
					new_watermark: new_hrmp_watermark,
					last_watermark,
				});
			}

			if new_hrmp_watermark == last_watermark {
				return Ok(());
			}
		}

		// Second, check where the watermark CAN land. It's one of the following:
		//
		// (a) The relay parent block number (checked above).
		// (b) A relay-chain block in which this para received at least one message (checked here)
		let digest = HrmpChannelDigests::<T>::get(&recipient);
		if !digest
			.binary_search_by_key(&new_hrmp_watermark, |(block_no, _)| *block_no)
			.is_ok()
		{
			return Err(HrmpWatermarkAcceptanceErr::LandsOnBlockWithNoMessages {
				new_watermark: new_hrmp_watermark,
			});
		}
		Ok(())
