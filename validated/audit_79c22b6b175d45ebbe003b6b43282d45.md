### Title
Escrow credited from claimed order amount instead of verified received balance, enabling fake-token order griefing of solvers - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.placeOrder` on the Tron deployment credits the internal `_orders[commitment][token]` escrow accounting using the order-placer's claimed input amount (`reducedInputs[i].amount`), without verifying that the ERC20 `transferFrom` call actually delivered that amount of real tokens to the contract. This is the same bug class as the `TokenSaleProposalCreate::createTier` DAO-pool report: an attacker-chosen ERC20 with a spoofed `transferFrom` can make the escrow accounting believe funds were deposited when they were not.

### Finding Description
In the non-predispatch branch of `placeOrder`: [1](#0-0) 
the contract calls `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then unconditionally credits `_orders[commitment][token] += reducedInputs[i].amount` — the *claimed* amount, not a measured balance delta. Contrast this with the sibling EVM implementation, which snapshots the balance before/after the transfer and uses the actual delta for both the commitment hash and escrow accounting: [2](#0-1) 

The predispatch branch of the Tron contract likewise derives `balance`/`dust` from `IERC20(token).balanceOf(dispatcher)` — a value fully controlled by the (potentially malicious) token contract's own storage — rather than by measuring what the gateway itself actually received: [3](#0-2) 

Since `order.inputs[i].token` is fully attacker-controlled (any address can be specified as the input token when placing an order), a malicious order placer can supply a custom ERC20 whose `transferFrom`/`balanceOf` are overridden to report a fake successful transfer/balance without moving real value. `_orders[commitment][token]` is later paid out to whoever fills/redeems the order via `withdraw`, using another unchecked low-level `token.call(...transfer...)`: [4](#0-3) 

### Impact Explanation
A malicious user can `placeOrder` with a fabricated ERC20 as `order.inputs[*].token`, causing the gateway to record an escrow balance that is not backed by any real tokens. An honest solver, observing the `_orders` mapping / on-chain escrow accounting, fills the order by providing real `output` assets to the beneficiary. When the solver later attempts to redeem the escrowed "input" tokens through `withdraw` (triggered by `RedeemEscrow`), it receives worthless/fake tokens instead of real value, resulting in a direct loss of the solver's real assets. This is a theft-of-funds vector against solvers/relayers who interact with the `IntentGatewayV2` in good faith, matching the report's "permanent DOS/loss for naive participants" impact class.

### Likelihood Explanation
Any unprivileged address can call `placeOrder` with an arbitrary token address; deploying a malicious ERC20 with a spoofed `transferFrom`/`balanceOf` is trivial and requires no special privileges or governance access. The only precondition is that a solver chooses to fill the fraudulent order, which is a normal, expected interaction pattern for the intents system (solvers select and fill orders based on advertised inputs/outputs).

### Recommendation
In `placeOrder` (both branches), record the token balance of `address(this)` (or the dispatcher, for the predispatch flow) immediately before and after the transfer, and credit `_orders[commitment][token]` using the measured delta rather than the caller-claimed `order.inputs[i].amount`/`reducedInputs[i].amount`, mirroring the fix already present in `evm/src/apps/IntentGatewayV2.sol` (lines 320-322). Apply the same before/after balance verification to the predispatch sweep path (lines 416-446) instead of trusting `IERC20(token).balanceOf(dispatcher)` as a proxy for actual value received.

### Proof of Concept
1. Attacker deploys `FakeToken`, an ERC20 whose `transferFrom` always returns `true` and never debits the caller's balance (or whose `balanceOf` is hardcoded to always look sufficient).
2. Attacker calls `placeOrder` with `order.inputs = [{token: FakeToken, amount: 1000e18}]` and a legitimate, attractive `order.output` (e.g., requesting 900 DAI on the destination chain).
3. `placeOrder` calls `FakeToken.safeTransferFrom(attacker, address(this), 1000e18)`, which succeeds without moving real value, and then executes `_orders[commitment][FakeToken] += 1000e18` regardless.
4. A solver observes the order, believing 1000 `FakeToken` are escrowed as collateral/payment, and calls `fillOrder`/dispatches the required output assets (e.g., transfers 900 real DAI to the beneficiary).
5. The solver later triggers `withdraw` via `RedeemEscrow` to claim the escrowed `FakeToken`; `token.call(...transfer...)` on the malicious contract can also be made to "succeed" while transferring nothing of value, leaving the solver with a worthless token and a net loss of the real assets they provided.
