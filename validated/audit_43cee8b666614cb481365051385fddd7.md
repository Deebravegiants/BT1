### Title
Permissionless bandwidth-subscription purchases let anyone evict another payer's still-live, unconsumed prepaid allowance via the FIFO eviction cap - ([File: modules/pallets/bandwidth/src/lib.rs])

### Summary
`pallet-bandwidth`'s `on_accept` (purchase handler) and `push_subscription` accept any purchase message from the registered `BandwidthManager` for a source chain and unconditionally append a new `Subscription` to the `(app_chain, app)` FIFO list, evicting the oldest entry once the list hits the 1024-item cap. Because purchasing is permissionless (anyone with fee tokens on the source EVM chain can call `BandwidthManager.purchase()` for *any* `app_chain`/`app` pair — this is explicitly the "sponsorship" feature), an attacker can repeatedly buy the cheapest tier for a victim app to fill its queue to 1024 entries and evict the victim's legitimately paid, unconsumed, higher-value subscription before it is ever drained by the gate. This mirrors the Cooler `roll()` bug-class: an unprivileged party can repeatedly invoke a permissionless action (purchase / roll) with no cap tied to the counterparty's interests, degrading or destroying value for someone else (the lender / the paying app) who has no way to prevent it short of disabling the feature.

### Finding Description
- `push_subscription` in `modules/pallets/bandwidth/src/lib.rs:400-437` appends every purchase to `Allowance::<T>` for `(app_chain, app)`, and when the list is already at `MAX_SUBSCRIPTIONS` (1024, `modules/pallets/bandwidth/src/types.rs:21`) it evicts index 0 — the oldest entry — regardless of its remaining size, tier, or how close it is to being drained by the gate:
```rust
let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
    let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
        Some(list.remove(0))
    } else {
        None
    };
    let _ = list.try_push(new_sub);
    evicted
});

- Purchasing has no access control tied to who the beneficiary app is. `on_accept` only checks that the request came from the registered `BandwidthManager` contract for the source chain — it does not check who paid or restrict which `(chain, app)` pair may be credited:
```rust

- The docs explicitly confirm this sponsorship model is intentional and that *anyone* can pay for *any* app on *any* chain:
> "This means a buyer on Ethereum can credit an app on Base by dispatching a purchase whose payload sets `chain = "EVM-8453"`." [3](#0-2) 

- The docs also acknowledge the eviction mechanic exists and describe it as only a practical concern under "pathological repeat-buy behavior," implicitly assuming a single benign buyer, not an adversarial one:
> "Pushing onto a full list (1024 entries) evicts the oldest entry and emits `SubscriptionEvicted` with the lost bytes so the loss is auditable on-chain. In practice this only happens under pathological repeat-buy behavior — at the default of one purchase per cycle, 1024 buys is years of headroom." [4](#0-3) 

Because same-tier (or any-tier) repurchases never stack — "queue" instead — and eviction is strictly FIFO by insertion order rather than by remaining value or size, an attacker who buys the cheapest configured tier (`TierOne`, whatever bytes/duration/price governance set) 1024 times in rapid succession against a target `(app_chain, app)` forces every pre-existing subscription for that app off the list, including a large, expensive, unconsumed subscription the legitimate app owner or sponsor just purchased. The victim's paid-for allowance is permanently lost (there is no re-credit; eviction just deletes the row and emits `SubscriptionEvicted` for audit only), even though the app never had a chance to consume any of it.

This is the same bug class as the Cooler `roll()` finding: a permissionless, repeatable action available to any party lets that party unilaterally impose an outcome (here: destruction of another party's already-paid state) that the affected party ("the lender"/paying app) cannot block, with no cap that accounts for the victim's stake — only a cap (1024) that exists for storage-bounding reasons, not economic protection.

### Impact Explanation
This is a permanent freezing/loss-of-funds bug for the sponsor/app that purchased bandwidth: prepaid, unconsumed bandwidth (a real economic asset, paid for in the fee token via `BandwidthManager.sol`) can be destroyed by a third party with no economic benefit to the app being griefed, and no way for the app to defend itself beyond either being lucky enough to be consumed before eviction, or paying for enough headroom to always sit near the front of a 1024-deep queue that any attacker can also grow. Given `TierOne` pricing can be set arbitrarily low by governance (there is no minimum), the cost to mount 1024 tiny purchases against one victim app may be far below the value of the subscription being evicted, making this a cheap, targeted denial-of-service / funds-loss vector against any bandwidth-metered app (which, per the design doc, includes "future modules like bandwidth"-gated system messages — i.e., this can degrade delivery of legitimate cross-chain traffic for an app once its allowance is wiped).

### Likelihood Explanation
High feasibility: purchasing is fully permissionless from any EVM chain with a registered `BandwidthManager`, requires no special privilege, and the only cost is 1024 cheap-tier purchases (bounded, deterministic, and cheap if governance has configured any low-price tier). No proof, timing, or race condition beyond simple repeated transaction submission is required. The attack is directly reachable by "an unprivileged message dispatcher" exactly as scoped (a party dispatching purchase requests through the standard ISMP dispatch path).

### Recommendation
- Evict by remaining value/priority rather than strict FIFO, or reject/refund purchases that would evict an unexpired subscription with nonzero `remaining_bytes` still belonging to a *different* payer than the one causing the eviction.
- Alternatively, scope subscription slots per-payer (or track a per-purchaser sub-queue) so one purchaser's cheap repeat-buys cannot evict another purchaser's subscription.
- Consider a minimum tier price floor and/or a cooldown / rate limit on purchases per `(source, app)` pair to make griefing economically costly, and/or increase `MAX_SUBSCRIPTIONS` dynamically or price eviction risk into the tier design (e.g., require newer/larger purchases to displace only strictly cheaper/smaller ones).
- At minimum, emit a distinguishable warning/refuse when a purchase would evict a subscription that is not the purchaser's own and that still has a large unconsumed balance, mirroring the Cooler recommendation of gating the "roll"/repeat action so it cannot be exercised purely at the expense of a counterparty who has no say in it.

### Proof of Concept
1. Governance registers a `BandwidthManager` for chain `S` and configures `TierOne` with minimal `bytes`/`duration_secs` and (on the EVM side) a very low or near-zero markup/price.
2. Victim app `App_V` (or its sponsor) purchases a large `TierFour` subscription (large `bytes`, long `duration_secs`) for `(app_chain = S, app = App_V)`, landing as entry N in the FIFO list (`Allowance::<T>[S][App_V]`).
3. Attacker, with no relationship to `App_V`, calls `BandwidthManager.purchase()` from any EVM account on chain `S`, setting `msg.chain = S`, `msg.app = App_V`, tier = `TierOne`, `months = 1`, repeated 1024 times (or however many are needed to reach the cap and push past entry N).
4. Each purchase dispatches a `PurchaseMessage` that lands in `on_accept` → `push_subscription`, which appends to the same list and, once the cap of 1024 is hit, evicts index 0 each time — eventually evicting `App_V`'s large `TierFour` subscription while it still has full `remaining_bytes` and has not expired.
5. `SubscriptionEvicted { app_chain: S, app: App_V, tier: TierFour, lost_bytes: <full amount> }` is emitted, and `App_V`'s `remaining()`/`allowances()` view no longer includes that subscription — the prepaid bandwidth is unrecoverable, even though `App_V` never had the chance to consume it via the gate (`BandwidthGate::try_consume`). 		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}

	impl<T: Config> IsmpModule for Pallet<T> {
		fn on_accept(&self, request: PostRequest) -> Result<Weight, anyhow::Error> {
			let manager = BandwidthManager::<T>::get(&request.source).ok_or_else(|| {
				anyhow::anyhow!(format!("no bandwidth manager registered for {:?}", request.source))
			})?;

			if request.from != manager.0.to_vec() {
				return Err(anyhow::anyhow!(format!(
					"purchase from unauthorised sender on {:?}: expected {:x?}, got {:x?}",
					request.source, manager.0, request.from
				)));
			}

			let msg = PurchaseMessage::try_from(request.body.as_slice())?;
			let tier = TierIndex::try_from(msg.tier)
				.map_err(|_| anyhow::anyhow!(format!("unknown tier discriminant {}", msg.tier)))?;
			let cfg = Tiers::<T>::get(tier)
				.ok_or_else(|| anyhow::anyhow!(format!("tier {:?} is not configured", tier)))?;

			let bytes = cfg.bytes.saturating_mul(msg.months as u128);
			let duration = cfg.duration_secs.saturating_mul(msg.months as u64);

			let key = AppKey::truncate_from(msg.app);
			let expires_at = Self::push_subscription(&msg.chain, &key, tier, bytes, duration);

			Self::deposit_event(Event::BandwidthCredited {
				app_chain: msg.chain,
				app: key,
				paid_from: request.source,
				tier,
				bytes,
				expires_at,
			});

			Ok(Weight::zero())
		}

## Sponsorship

The purchase message carries its own `chain` (the _credit chain_) which is **independent of the source chain** that sent the message. This means a buyer on Ethereum can credit an app on Base by dispatching a purchase whose payload sets `chain = "EVM-8453"`.

The pallet keys allowance storage by `(app_chain, app)` taken from the message body, not by `request.source`. The event `BandwidthCredited` carries both — `app_chain` (where the credit lands) and `paid_from` (where the payment came from) — so the cross-chain payer is auditable.
