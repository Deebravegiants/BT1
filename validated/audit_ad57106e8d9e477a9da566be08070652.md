### Title
Excess native `msg.value` sent to `EvmHost.dispatch`/`fundRequest` is not refunded to the caller and is trapped as host balance - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest` all accept native `msg.value` and swap it via Uniswap V2's `swapETHForExactTokens` for an exact `fee`/`amount` of `feeToken()`. `swapETHForExactTokens` only spends what is required and refunds any unused ETH — but that refund is paid to `msg.sender` from the router's perspective, which is `EvmHost` itself, not the original caller who supplied the `msg.value`. Any overpayment is therefore silently retained by `EvmHost` instead of being returned to the user.

### Finding Description
In `dispatch(DispatchPost)`: [1](#0-0) 

and identically in `dispatch(DispatchGet)`: [2](#0-1) 

and in `fundRequest`: [3](#0-2) 

In each case, the full `msg.value` is forwarded to `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`. The Uniswap V2 router refunds unused ETH to whoever called it — here that is `EvmHost` (`address(this)` in the router's execution context), not the end user who sent the transaction. `EvmHost` never checks its own balance delta or forwards any leftover ETH back to `_msgSender()`. There is no `receive()`/fallback-triggered refund path and no post-swap balance check in these three functions.

This is directly analogous to the reported `Factory.sol`/`NFTCollection.sol` issue: a `payable` function accepts `msg.value >= requiredAmount` without enforcing equality or refunding the difference, so any amount above what's strictly needed is absorbed by the contract rather than returned to the payer.

The codebase itself demonstrates the correct pattern elsewhere: `IntentGatewayV2.placeOrder` explicitly tracks `msgValue -= amounts[0]` after the swap and calls `_sendValue(msg.sender, msgValue)` to refund any leftover native token: [4](#0-3) 

`EvmHost` has no equivalent refund logic in its three swap-consuming entry points.

### Impact Explanation
Any unprivileged caller who dispatches a POST/GET request or funds a request with native token (a normal, documented usage pattern per the developer docs recommending `dispatch{value: msg.value}(...)`) permanently loses any ETH sent beyond what the swap consumes to acquire the exact `fee`. Since users must estimate slippage/price-impact conservatively (or simply send a safety margin, as shown in the `IntentGatewayV2` "5 ETH for a fee swap" test pattern), overpayment is a realistic and even encouraged behavior. The excess ETH becomes stuck in `EvmHost` and can only leave via the governance-controlled `withdraw()` function, which pays out to an arbitrary `beneficiary` chosen by cross-chain governance — not automatically or reliably back to the original depositor. This is a permanent, unrecoverable-by-default loss of user funds, reachable from a single, ordinary transaction with no special privileges.

### Likelihood Explanation
High likelihood: this path is triggered by the standard, documented "Native Token Payment" flow for `dispatch()`/`fundRequest()` that the project's own docs recommend to app developers, and slippage/price movement between fee quoting and execution makes exact-value transactions unreliable in practice, so users are effectively encouraged to send a buffer above the estimated cost.

### Recommendation
After the `swapETHForExactTokens` call in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, compute the actual ETH spent (`amounts[0]` returned by the router) and refund `msg.value - amounts[0]` back to `_msgSender()`, mirroring the pattern already implemented in `IntentGatewayV2.placeOrder`/`_fillCrossChain`.

### Proof of Concept
1. A user calls `EvmHost.dispatch{value: 5 ether}(DispatchPost{... fee: 10e18 feeToken ...})` estimating the swap will need up to 5 ETH worth of ETH to guarantee acquiring `10e18` fee tokens under slippage.
2. Uniswap's `swapETHForExactTokens` spends only, say, 0.8 ETH to acquire the exact `10e18` feeToken, and refunds the remaining 4.2 ETH — to `EvmHost` (the router's caller), per lines 921-932 of `evm/src/core/EvmHost.sol`.
3. `EvmHost.dispatch` never reads back the refunded balance nor forwards it to `_msgSender()`.
4. The user's transaction succeeds, `EvmHost`'s ETH balance permanently increases by 4.2 ETH, and the user has no path to reclaim it except through cross-chain governance's `withdraw()`, which is not guaranteed to identify or compensate the specific overpaying user.
