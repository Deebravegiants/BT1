## Title
Unauthenticated Pipeline Run Resume Endpoint Allows Unprivileged State Manipulation of Job Runs - (File: core/web/router.go, core/web/pipeline_runs_controller.go)

### Summary
The `PATCH /v2/resume/:runID` route is registered on the `unauthedv2` group, meaning it requires **no authentication whatsoever** (no session, no API token, no external-initiator signature), yet it invokes `App.ResumeJobV2`, a state-changing call that finalizes a pending pipeline task and resumes job execution. This mirrors the LibDiamond.sol pattern in the referenced report: a function capable of mutating protocol/application state (`addFunctions`/`setContractOwner` there, `ResumeJobV2` here) is reachable without any access-control check gating who may call it.

### Finding Description
In `core/web/router.go`, `v2Routes` explicitly separates authenticated and unauthenticated route groups: [1](#0-0) 

The `resume` endpoint is deliberately placed in the `unauthedv2` group — with no `auth.Authenticate(...)` middleware, no session cookie check, no API token check, and no `RequiresXRole` wrapper — unlike every other mutating v2 route (jobs, keys, bridges, transfers, etc.) which are all wrapped in `authv2` with role-based middleware (`auth.RequiresEditRole`, `auth.RequiresAdminRole`, etc.), as seen throughout the same file: [2](#0-1) 

The handler itself, `PipelineRunsController.Resume`, only parses the `runID` (a UUID that identifies a specific pipeline `taskID`) and a JSON body (`pipeline.ResumeRequest`), then calls `prc.App.ResumeJobV2` directly — with no caller identity check, no signature validation, and no ownership/ACL check tying the caller to the job or task: [3](#0-2) 

The audit log entry name itself, `audit.UnauthedRunResumed`, confirms this is a knowingly-unauthenticated action path — the intent appears to be that historically this endpoint was meant only for specific bridge/webhook callback flows validated by an unguessable task UUID, but there is no rate limiting, no HMAC/signature verification of the resume payload, and no scoping to the specific bridge/task that created the pending run. Any unprivileged network client that can guess or observe a `runID` (UUID) can inject arbitrary `ResumeRequest` results (including errors or successful results) to finalize a pipeline task, exactly as an attacker in LibDiamond could call `addFunctions`/`setContractOwner` without any permission check because the modifier was simply absent.

### Impact Explanation
An unauthenticated actor can:
- Force-complete (or force-fail) any pending pipeline run for which they can obtain/guess the `runID`, injecting attacker-controlled data as the "result" of an external task (e.g., bridge or HTTP task).
- Corrupt or manipulate the outcome of OCR/pipeline jobs consuming that resumed data, since `ResumeJobV2` accepts arbitrary result payloads from the request body (`pipeline.ResumeRequest`), which then flow into the pipeline's downstream tasks (potentially influencing on-chain reports or transactions produced by the node).
- Cause denial-of-service by repeatedly resuming/erroring runs, or by resuming runs before the intended external system responds (race condition), corrupting the job's pipeline outcome.

This satisfies the "unauthorized job run" bar from the validation criteria: an unprivileged client can trigger/complete a job run's execution flow without any authentication.

### Likelihood Explanation
Likelihood depends on whether `runID` values (UUIDs) are effectively unguessable secrets in practice; if so, exploitation requires leaking or predicting the UUID (e.g., via logs, timing, or a separate information disclosure). However, the endpoint provides **zero defense-in-depth** — there is no authentication layer at all, so any leak of a runID (via logging, monitoring dashboards, error messages, or a compromised/observing party in the resume flow) directly grants full write capability with no additional barrier. This is a design gap analogous to relying solely on "security through obscurity" of the UUID rather than actual access control.

### Recommendation
- Require authentication for the resume endpoint or, at minimum, verify a per-task shared secret/HMAC bound to the originating job/bridge rather than a bare externally-supplied UUID.
- If external systems (e.g., bridges) must call this endpoint without a chainlink node user session, use a dedicated `AuthenticateExternalInitiator`-style credential (as already exists for other external-initiator flows in `core/web/auth/auth.go`) instead of leaving it fully unauthenticated.
- Add rate limiting specific to this unauthenticated route beyond the generic unauthenticated rate limiter, and ensure `runID`s are single-use/expire promptly to reduce replay/guessing windows.

### Proof of Concept (Steps in order to reproduce the vulnerability)
1. Start a node and create a job whose pipeline includes a task awaiting external resumption (producing a pending pipeline run with a `taskID`/`runID`).
2. Obtain or guess the `runID` UUID (e.g., via a monitoring endpoint, logs, or brute force given a sufficiently constrained window).
3. As an unauthenticated client (no session cookie, no `X-API-Key`/`X-API-Secret` headers), send: `PATCH /v2/resume/<runID>` with a crafted JSON body matching `pipeline.ResumeRequest` (e.g., `{"value": "<attacker-controlled result>"}`).
4. Observe that `core/web/pipeline_runs_controller.go` `Resume` processes the request and calls `App.ResumeJobV2` successfully, returning `200 OK` — confirming that the pipeline run state was mutated without any authentication or authorization check. [4](#0-3) [5](#0-4)

```go
// Resume finishes a task and resumes the pipeline run.
// Example:
// "PATCH <application>/jobs/:ID/runs/:runID"
func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)
}
```
