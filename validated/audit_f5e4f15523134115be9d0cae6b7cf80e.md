Confirmed: `Webhooks::Request#hmac`/`to_signable_string` (used by `Utils::HmacValidator.validate`) signs only the raw body, while `shop`, `topic`, `webhook_id`, and `api_version` come from unauthenticated headers and are used unchanged by `Registry.process` to attribute and route the event.### Title
Webhook shop, topic, and webhook-id are not covered by the HMAC signature, allowing cross-tenant event spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body via `Utils::HmacValidator.validate(request)`. The `shop`, `topic`, `webhook_id`, and `api_version` values consumed afterwards to route and attribute the event are read directly from HTTP headers, which are never included in the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, and its `to_signable_string` method returns only `@raw_body`: [1](#0-0) 

The `hmac` value is likewise computed only over the body via the `shopify-hmac-sha256` header: [2](#0-1) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from request headers with no cryptographic binding to the body or to each other: [3](#0-2) 

`Registry.process` validates only the HMAC (i.e., only the body) and then dispatches the handler using these unauthenticated header values, constructing `WebhookMetadata` with `request.topic`, `request.shop`, `request.webhook_id`, and `request.api_version`: [4](#0-3) 

`Utils::HmacValidator.validate` and `validate_signature` confirm the signature check only compares `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e., only the body is authenticated: [5](#0-4) 

Because the identity-critical fields (`shop-domain`, `topic`, `webhook-id`) are excluded from the HMAC, the binding "HMAC-verified bytes == the event attributed to `shop`" does not hold. An unprivileged internet user who legitimately installs the target app on their own store receives real, validly-HMAC-signed webhook deliveries for their own shop from Shopify. They can capture one such delivery (body + valid HMAC header) and replay it to the app's webhook endpoint while swapping the `shopify-shop-domain` (and optionally `shopify-topic`/`shopify-webhook-id`) headers to point at a victim shop. `Registry.process` will accept the HMAC as valid (since the body is unchanged and the secret matches) and will invoke the registered handler believing the event originated from — and pertains to — the victim shop.

### Impact Explanation
This breaks the equality that the app's webhook handler relies on: `authenticated_bytes (body signed by client_secret) == event attributed to shop X`. Any app logic that uses `WebhookMetadata#shop` to look up per-tenant state, trigger per-tenant side effects (e.g., processing `orders/create`, `app/uninstalled`, `customers/data_request`, GDPR webhooks, billing events, or updating shop-scoped records) can be tricked into acting on behalf of, or against, a shop the attacker does not control — a cross-tenant access/confusion condition. Depending on how the hosting app is written (which is out of this gem's control but directly enabled by this gap), this can range from data confusion to a full cross-tenant data/state corruption, satisfying the "cross-tenant access" criterion for Critical severity.

### Likelihood Explanation
Likelihood is realistic: the attacker only needs to be able to install the app themselves (an ordinary, unprivileged action any Shopify merchant/developer can perform) to obtain one or more legitimately signed webhook bodies. No access to `api_secret_key`, access tokens, or any privileged credential is required — they merely reuse a validly-signed body they already legitimately received under their own tenant, with forged headers. The library provides no header-binding or replay/shop-consistency protection to prevent this.

### Recommendation
Include the identity-relevant header values (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed material, or otherwise cryptographically bind them to the raw body before trusting them (Shopify's HMAC header is computed only over the body by protocol, so the gem should instead enforce out-of-band verification, e.g., cross-checking `shop` against a known/allow-listed value tied to the delivery, or requiring the consuming application to independently verify shop identity before trusting `WebhookMetadata#shop`). At minimum, document prominently that `WebhookMetadata#shop`/`#topic`/`#webhook_id` are NOT covered by the HMAC and must not be trusted as authenticated without additional verification by the host application.

### Proof of Concept
1. Attacker installs the target Shopify app on their own development/test store (`attacker-shop.myshopify.com`) and triggers a webhook event (e.g., `orders/create` with a minimal/predictable body such as `{}` or a body they fully control the content of, like a metafield update they made).
2. Shopify delivers the webhook to the app's endpoint with a valid `shopify-hmac-sha256` computed over that exact body using the shared `client_secret`, plus headers `shopify-shop-domain: attacker-shop.myshopify.com`, `shopify-topic: orders/create`, `shopify-webhook-id: <id>`.
3. Attacker captures this raw request (body + `hmac-sha256` header value) and replays it directly to the app's webhook endpoint, but rewrites `shopify-shop-domain` to `victim-shop.myshopify.com` (and optionally alters `shopify-topic`/`shopify-webhook-id`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (the unchanged raw body) and finds it matches — validation succeeds: [6](#0-5) 
5. The registered handler executes with `WebhookMetadata` reporting `shop: "victim-shop.myshopify.com"`, even though the event body and signature were never actually produced for that shop — demonstrating that the gem provides no protection against shop/topic spoofing despite HMAC validation passing.

            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
