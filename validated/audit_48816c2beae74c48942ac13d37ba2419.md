### Title
Decimal-truncation of small cross-chain amounts causes permanent loss of escrowed/burned funds in `pallet-hyper-fungible-token` - ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
`pallet-hyper-fungible-token`'s `on_accept`/`on_timeout` handlers convert an incoming ERC20-denominated `U256` amount to the local (substrate) balance via integer division, with no minimum-amount check. When the remote EVM token's decimals exceed the local asset's decimals by enough, a small but non-zero amount truncates to `0`, while the source chain has already burned or escrowed the real value before dispatch — mirroring the SolverVaults decimal-truncation report.

### Finding Description
`convert_to_balance` divides the raw ERC20 `U256` amount by `10^(erc_decimals - local_decimals)` and stringifies/parses the result into the local balance type, with no lower bound enforced: [1](#0-0) 

This is invoked unconditionally in the unprivileged, message-driven `on_accept` path (any relayer can deliver a proven cross-chain post from a registered peer contract): [2](#0-1) 

and again in `on_timeout` when refunding the original sender: [3](#0-2) 

On the sending side, the local asset was burned or moved into escrow for the full nominal amount before the message was dispatched (`send` in `lib.rs`), and the corresponding EVM contract mirrors that by burning/locking its own balance before dispatching the `Message` to this pallet. There is no minimum-transfer check anywhere in `send`, `on_accept`, or `on_timeout`, and no rounding-up/precision-preserving scheme (e.g., WAD-scaling) is used — exactly the bug class described in the external report, applied here to `pallet_hft`'s decimal-precision boundary instead of SolverVaults' deposit/withdraw boundary.

Concretely: if `erc_decimals - local_decimals >= k`, any inbound amount `< 10^k` (in ERC20 units) divides to `0`. Since `mint_into`/`transfer` are called with `amount = 0`, the beneficiary receives nothing, yet the sender already paid/burned the corresponding real value on the source chain. The `README.md` documents that `Precisions` is exactly the per-chain EVM decimals used to scale at this boundary, confirming decimal mismatches across chains are an expected, reachable condition: [4](#0-3) 

The same truncation-to-zero risk applies to `convert_to_erc20`'s inverse direction is safe (it multiplies, so it never zeroes out), but the pallet-side `convert_to_balance` (dividing) is the vulnerable leg, hit whenever the remote/ERC decimals are configured higher than the local asset's decimals (a legitimate, admin-approved configuration per `register_token`/`ChainConfig`, not attacker-controlled, but exploitable by any unprivileged sender choosing a dust amount).

### Impact Explanation
Any unprivileged user calling `send` (or delivering a proof via `on_accept`) with a small enough amount causes the beneficiary to receive `0` local tokens while the equivalent value was burned/escrowed on the remote chain. This is a concrete, permanent loss of funds for legitimate senders/relayed messages, matching the "unbacked mint / permanent freezing of funds" impact bar. It also lets any address spam `on_accept`/`on_timeout` calls that mint/transfer `0` with no revert, since there's no minimum-amount guard, wasting storage/events similar to the original report's secondary concern.

### Likelihood Explanation
Likelihood is medium: it requires per-(asset, chain) `Precisions` where `erc_decimals` meaningfully exceeds the local asset's decimals (e.g., an 18-decimal EVM token bridged to a low-decimals substrate asset), which is a normal, admin-sanctioned configuration rather than an edge case. Any user (accidentally or via a scripted/malicious dust-amount transfer) can trigger the truncation without any special privilege, and the loss is deterministic given the divisor, decimals gap and amount — no probabilistic conditions are needed.

### Recommendation
- Enforce a minimum transferable amount in `send` (and validate `amount` after conversion is non-zero in `on_accept`/`on_timeout`), rejecting/reverting when the scaled result would be `0`.
- Alternatively, avoid lossy division entirely by tracking/settling amounts in a common high-precision unit (e.g., always store/dispatch amounts scaled to 18 decimals, matching what `VWAPOracle._normalizeAmount` already does elsewhere in this codebase) and only truncate for display, never for accounting.
- Add an explicit check in `convert_to_balance` that returns an error when the division would round to zero for a non-zero input, rather than silently proceeding to mint/transfer 0.

### Proof of Concept
1. Admin registers asset `X` with `native = false`, local decimals `= 2`, and `ChainConfig.decimals = 18` for EVM chain `C` (a legitimate, plausible configuration since USDC/other tokens differ across chains and the pallet is designed to scale for exactly this case).
2. A user calls `send` from EVM chain `C`'s `HyperFungibleToken` contract with `amount = 1` (1 wei, i.e., `10^-18` of a token), which is non-zero, burns/locks on the EVM side, and dispatches a `Message` with `amount = 1` (U256) to the pallet's module id.
3. On delivery, `module.rs::on_accept` calls `convert_to_balance(U256::from(1), erc_decimals=18, local_decimals=2)`, which computes `1 / 10^16 = 0`.
4. `mint_into(local_asset_id, beneficiary, 0)` succeeds, `TokenReceived { amount: 0 }` is emitted, and the beneficiary receives nothing — while the sender's tokens were already burned/escrowed on chain `C`, resulting in a full loss of the transferred value.

```rust
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
```
