I have enough evidence now to determine the analog vulnerability. `CallDispatcher.dispatch()` is a completely permissionless, shared, singleton contract used across `IntentGatewayV2`, `IntentGatewayV2SameChain`, `ExtrinsicIntents`/`IntrinsicIntents`, and any other app configured with the same `_params.dispatcher` address. ### Title
Unrestricted caller on shared `CallDispatcher.dispatch()` allows theft of any assets left on the dispatcher between predispatch/postdispatch legs - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher.dispatch(bytes memory encoded)` executes an arbitrary, caller-supplied `Call[]` array with no access control whatsoever [1](#0-0) . It is deployed once and shared by every `IntentGatewayV2`/`IntentGatewayV2SameChain`/`ExtrinsicIntents` instance via `_params.dispatcher` [2](#0-1) . This is the same bug class as `atlasSolverCall()` not checking its caller — except here there is no check at all, not even a spoofable one.

### Finding Description
During `placeOrder` (predispatch) and `_execute` (postdispatch), the gateway transfers assets to the `CallDispatcher` and then calls `dispatch()` on it to run user-/solver-supplied calldata, expecting to sweep back whatever remains afterward [3](#0-2) . Because `dispatch()` is `external` with no `onlyGateway`/`msg.sender` restriction, and the dispatcher is a single shared contract instance across all order flows and all deployed gateway apps, any address can call `CallDispatcher.dispatch()` directly with an arbitrary `Call[]` targeting `address(this)` (the dispatcher) to move out any ETH or ERC-20 balance the dispatcher happens to hold — for example, tokens from a swap that produced an asset not enumerated in the gateway's known `inputs`/`outputs` list (so the gateway's sweep loop never reclaims it), dust from a partially-failed predispatch step, or accidentally-sent funds. The sweep logic in `_execute`/`placeOrder` only sweeps tokens it already knows about from the order's `inputs`/`outputs` arrays [4](#0-3) , so any calldata-driven swap that yields an unlisted token (e.g., a DEX router returning an unexpected intermediate/reward token, or leftover approval-drained balance) is stranded on the dispatcher and immediately grabbable by anyone via a direct `dispatch()` call, since the target only needs `extcodesize > 0` [5](#0-4) .

### Impact Explanation
Funds stranded on the shared `CallDispatcher` (native ETH via its `receive()` or ERC-20 balances) can be permanently stolen by any unprivileged address, since `dispatch()` performs no caller authentication analogous to `SolverBase`'s (weak) sender check. Given the dispatcher is shared across every intents app on a chain, this is a protocol-wide, unbounded-value theft vector rather than one scoped to a single order.

### Likelihood Explanation
Reaching this requires only sending a single unprivileged transaction directly to the public `CallDispatcher.dispatch()` function once any balance sits on it — reachable any time an order's predispatch/postdispatch calldata swap yields a token not in the declared `inputs`/`outputs` set, or when a solver's postdispatch call leaves partial dust before the gateway's own sweep call executes later in the same order flow (e.g., a solver forgetting to fully drain into the sweep-enumerated set, or a token whose `transfer` silently no-ops leaving balance uncounted).

### Recommendation
Restrict `CallDispatcher.dispatch()` to only be callable by the authorized gateway/app contract(s) that own it (an `onlyOwner`/allow-listed-caller pattern, mirroring the `atlasSolverCall` fix of moving trust decisions to the caller-verified entry point), or deploy a dedicated, non-shared dispatcher instance per gateway with a hardcoded caller check (e.g., `msg.sender == gateway`).

### Proof of Concept
1. A gateway order's predispatch or postdispatch `Call[]` performs a DEX swap through `CallDispatcher.dispatch(...)`, and the swap returns a small amount of an intermediate/reward token not present in `order.inputs`/`order.output.assets`.
2. The gateway's post-dispatch sweep in `_execute`/`placeOrder` only iterates over the known `inputs`/`outputs` token list [4](#0-3) , so the unlisted token balance remains on the `CallDispatcher`.
3. Any attacker calls `CallDispatcher.dispatch(abi.encode([Call({to: token, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, balance)})]))` directly — this succeeds because `dispatch()` has no caller restriction [1](#0-0) , draining the stranded tokens to the attacker.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

                    sweepCalls[sweepCount] = Call({to: address(this), value: balance, data: ""});
