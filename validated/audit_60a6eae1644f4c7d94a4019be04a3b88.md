### Title
Unvalidated destination chain in `placeOrder` permanently freezes escrowed funds - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.placeOrder()` escrows a user's input tokens for an intent order and stamps the order with a caller-supplied `order.destination` state-machine identifier, but never checks that a corresponding `IntentGateway` instance/deployment is actually registered for that destination via `_instances` before accepting the escrow. This mirrors the reported class of bug in `RenovaItemBase.sol`/`WormholeBaseUpgradeable.sol`, where `wormholeBridgeOut()` allowed selecting an unconfigured `dstWormholeChainId`, burning the item with no valid receiver — except here the analogous failure is a stuck, permanently-frozen escrow instead of a burn.

### Finding Description
`placeOrder` in `IntentGatewayV2.sol` performs input-length, duplicate-output-token, and fee-related checks, then unconditionally escrows tokens for any `order.destination` value supplied by the caller [1](#0-0) . It never calls `instance()`/`_instance()` to confirm a gateway is registered for `order.destination` before crediting the escrow at the end of the function [2](#0-1) .

Contrast this with the sibling token-bridge app `HyperFungibleToken.sol`, whose `_buildDispatchPost` explicitly guards against sending to an unconfigured chain: `bytes memory dest = _supportedChains[params.dest]; if (dest.length == 0) revert UnsupportedChain();` [3](#0-2)  — precisely the check the external report's remediation (`_wormholeRemotes[dstWormholeChainId] != bytes(0)`) recommends. `IntentGatewayV2.placeOrder` has no equivalent guard.

The only place destination validity is checked is `_instance()`, which reverts with `UnknownInstance` if no gateway is registered for that state-machine id [4](#0-3) . That function is used by `fillOrder`'s cross-chain routing and — critically — by the cross-chain `cancelOrder` path on the source chain, which builds a GET-request storage key using `instance(order.destination)`/`_instance(order.destination)` to prove non-fill on the destination before releasing the escrow [5](#0-4) . If `order.destination` was never registered, this call reverts every time, for the life of the contract.

### Impact Explanation
Because `placeOrder` accepts any `order.destination` bytes value without checking `_instances`, a user (or a griefer front-running/crafting a UI bug) can escrow real value against a destination chain identifier that has no deployed `IntentGateway`:
- No solver can ever fill the order on that destination, since no such contract exists there.
- The cross-chain cancellation path unconditionally reverts, because it depends on `instance(order.destination)` succeeding to build the storage-proof key for the GET request.
- The same-chain cancellation path is unusable since `order.source != order.destination` in this scenario.

Result: the user's escrowed tokens (any input assets, including native token) are permanently locked with no recovery path — a direct freezing-of-funds vulnerability reachable by a single `placeOrder` transaction from any unprivileged caller.

### Likelihood Explanation
`placeOrder` is a fully public, unprivileged entry point that any user or dApp can call with an arbitrary `order.destination`. No governance or relayer action is required to trigger the freeze — a single malformed/mistyped destination identifier, or a chain that Hyperbridge governance has not yet (or will never) provision an `IntentGateway` instance for, is sufficient. This is analogous in ease-of-trigger to the original report's `dstWormholeChainId` misconfiguration.

### Recommendation
Add a destination-validity check in `placeOrder` before escrowing tokens, mirroring the pattern already used in `HyperFungibleToken.sol` and available via `_instance()`/`instance()` in `IntentsBase.sol`: e.g. `if (_instances[keccak256(order.destination)] == address(0) && keccak256(order.destination) != keccak256(order.source)) revert UnknownInstance();` (allowing the same-chain case) prior to Phase 3 escrow crediting in `evm/src/apps/IntentGatewayV2.sol`.

### Proof of Concept
1. Attacker/user calls `placeOrder(order, graffiti)` on the source-chain `IntentGatewayV2`, setting `order.destination` to a state-machine id for which `_instances[keccak256(order.destination)] == address(0)` (e.g., a chain id Hyperbridge governance has not yet registered a gateway for).
2. `placeOrder` proceeds through fee computation and escrow crediting with no destination check [2](#0-1) ; tokens are locked in `_orders[commitment][token]`.
3. No solver can call `fillOrder`, because there is no `IntentGateway` deployed on the unregistered destination chain to receive/process the fill.
4. After `order.deadline`, the user attempts `cancelOrder` from the source chain; internally this needs `instance(order.destination)` (via `_instance`) to build the storage proof key for the destination GET request, which reverts with `UnknownInstance` [4](#0-3) .
5. The escrowed tokens remain locked in the `IntentGatewayV2` contract indefinitely — no code path can ever release them.
