### Title
Multi-Token Escrow Withdrawal Permanently Reverts on a Single Blacklisted/Paused Token Transfer, Freezing Unrelated Escrowed Funds and Fees - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.withdraw()` iterates over every escrowed output token (and separately the transaction-fee token) for an order and performs a raw `.call` transfer for each. Any single transfer failure — e.g., a USDC-style blacklist, a paused ERC-20, or a beneficiary address sanctioned by one of the tokens involved — causes the whole function to `revert TransferFailed()`, rolling back release of **all** other tokens in that same order (including tokens the beneficiary could otherwise freely receive) and the escrowed relayer/tx fees.

### Finding Description
`withdraw(WithdrawalRequest memory body, bool isRefund)` is the internal handler invoked from `onAccept()` when a `RedeemEscrow` or `RefundEscrow` ISMP request is delivered: [1](#0-0) 

Inside `withdraw`, the loop over `body.tokens` transfers each escrowed asset to the beneficiary and unconditionally reverts the *entire* call if any single transfer fails: [2](#0-1) 

The same all-or-nothing pattern applies to the transaction-fee redemption right after the token loop: [3](#0-2) 

`onAccept` is invoked by the host via a low-level `.call`, and on failure the host deletes the request receipt so the message can be retried: [4](#0-3) 

This retry mechanism only helps for *transient* failures. If the failure is caused by a token-level, address-level, or protocol-level block (e.g., the beneficiary is blacklisted on one of several output tokens, or one output token is permanently paused/deprecated), every future retry of the same `RedeemEscrow`/`RefundEscrow` message will fail identically, since `body.tokens` and `body.beneficiary` are fixed and immutable in the message body. The escrow for *all* tokens in that order — not just the problematic one — plus the associated relayer fee, becomes permanently unretrievable.

This directly parallels the reported bug class: a loop that must fully succeed across multiple independent token transfers, where one non-cooperative token/account causes the entire batch (rewards in the original report, escrow release here) to be irrecoverably stuck.

### Impact Explanation
This is reachable by any unprivileged solver/relayer delivering a `RedeemEscrow` or `RefundEscrow` message that was legitimately dispatched from the source/destination `IntentGatewayV2` (via `fillOrder`/`cancelOrder` flows) — no privileged role is required to trigger the withdrawal path, and the attacker only needs to cause one of the escrowed tokens (or fee token) to be non-transferable to the specific beneficiary (e.g., by having a token issuer blacklist that beneficiary, or by the order itself specifying an already-paused/deprecated token as one of several outputs). The result is a permanent freeze of legitimately escrowed user/solver funds and protocol fees for that order — the beneficiary can never redeem any of the multi-token escrow, even the portions in fully functional tokens, since `withdraw()` provides no partial-success or per-token isolation. This meets the "permanent freezing of funds" bar.

### Likelihood Explanation
Multi-output-token orders are a first-class feature of the Intents system (see `TokenInfo[] outputs`/`inputs` throughout `IntentGatewayV2`), and USDC-style blacklisting or token pausing is a realistic, externally-triggerable event, not attacker-privileged. No governance or admin compromise is needed — a normal solver/relayer submitting the natural completion of an order is enough to hit the stuck state once any one token in the order becomes non-transferable to the beneficiary.

### Recommendation
Adopt a pull/withdrawal-credit pattern instead of push-transfer-in-a-loop: on `withdraw()`, credit each token amount to a per-beneficiary claimable balance mapping regardless of individual transfer outcome, and let the beneficiary (or fee receiver) later call a separate function to pull each token individually. Alternatively, wrap each per-token transfer in try/catch (or check success without reverting the whole loop) so a failure on one token only skips that token's release (leaving it claimable later) while other tokens and fees in the same order are still released.

### Proof of Concept
1. An order escrows two output tokens: `USDC` and `DAI`, destined to `beneficiary`.
2. Before the fill is finalized, `beneficiary` gets added to USDC's blacklist (or the order intentionally lists a token that is later paused).
3. The solver fills the order; the destination gateway dispatches a `RedeemEscrow` request back to the source chain's `IntentGatewayV2`.
4. `onAccept` → `withdraw(body, false)` executes the loop in `evm/tron/contracts/apps/IntentGatewayV2.sol:697-714`; the USDC `.call` transfer to the blacklisted `beneficiary` fails, `success == false`, and the function reverts with `TransferFailed()`.
5. `EvmHost.dispatchIncoming`'s low-level `.call` reports failure, `_requestReceipts[commitment]` is deleted for retry (`evm/core/EvmHost.sol:811-816`), but every retry hits the same USDC blacklist condition and fails identically.
6. The DAI escrow and the accrued transaction fee — both otherwise redeemable — remain permanently locked alongside the USDC amount, with no code path to release them independently.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }
