### Title
Duplicate/collided ownerReference UID keys in `indexByUID` cause `newBlockingOwnerDeletionRefs` to miss a genuine block-owner-deletion escalation, bypassing the delete-authorization loop - ([File: plugin/pkg/admission/gc/gc_admission.go])

### Summary
`indexByUID` builds a `map[types.UID]metav1.OwnerReference` from the *old* object's owner references, but since map keys collide on duplicate (including empty-string) UIDs, the map only retains the last-inserted entry for that UID. `newBlockingOwnerDeletionRefs` then looks up each new blocking ref by its UID against this lossy map, so when two old owner references share a UID and the last one in the slice was already `blockOwnerDeletion:true`, a genuinely-transitioning (`false`→`true`) reference sharing that UID is misdiagnosed as "already blocking" and silently excluded from the returned set, skipping the per-owner delete-authorization check at lines 138-152.

### Finding Description
The admission plugin `gcPermissionsEnforcement.Validate` [1](#0-0)  computes `newBlockingRefs := newBlockingOwnerDeletionRefs(...)` and only authorizes owners appearing in that returned slice [2](#0-1) .

`indexByUID` indexes the *old* owner references purely by `ref.UID`, with no duplicate detection; a later ref in the slice silently overwrites an earlier one that shares the same UID [3](#0-2) . `newBlockingOwnerDeletionRefs` then looks up each new blocking ref in this map by UID alone to decide whether it was previously blocking [4](#0-3) .

Exploit flow:
1. Attacker (with only update rights on the dependent object, plus legitimate finalizer/delete rights on some owner `X`) creates the dependent with `ownerReferences = [{uid:"", name:"Y", blockOwnerDeletion:false}, {uid:"", name:"X", blockOwnerDeletion:true}]`. On `Create`, `oldObj` is `nil`, so `newBlockingOwnerDeletionRefs` returns `blockingNewRefs` unfiltered — only `X` is blocking, and the attacker is legitimately authorized for `X`, so creation succeeds. `Y` is stored with a duplicate (empty) UID and `blockOwnerDeletion:false`.
2. Attacker then PATCHes the object, flipping `Y`'s `blockOwnerDeletion` to `true` while leaving `X` unchanged: `ownerReferences = [{uid:"", name:"X", blocking:true}, {uid:"", name:"Y", blocking:true}]`.
3. In the diff, `indexedOldRefs := indexByUID(oldRefs)` iterates the stored slice `[Y(false), X(true)]`; since both share UID `""`, `indexedOldRefs[""]` ends up as `X`'s entry (`blocking:true`) because it was inserted last.
4. When the loop processes new ref `Y` (blocking `true`), it looks up `indexedOldRefs[""]`, gets `X`'s stale `blocking:true` value, computes `wasNotBlocking = false`, and therefore does **not** add `Y` to `ret`.
5. `Y`'s real transition from `false`→`true` is never surfaced to the authorization loop at lines 138-152, so no delete/finalizer check is performed against `Y`'s referenced owner, even though the attacker has no permission over it.

This is a real logic defect: the diff function assumes owner reference UIDs are unique identifiers, but nothing upstream in this admission plugin (and no evidence found of uniqueness enforcement in `ValidateOwnerReferences`) rejects duplicate or empty UIDs in the `ownerReferences` list, so the assumption is not enforced at the API boundary.

### Impact Explanation
This lets an attacker set `blockOwnerDeletion=true` on an ownerReference pointing at a resource they do not have delete/finalizer permission over, without triggering the intended authorization gate. `blockOwnerDeletion=true` prevents the garbage collector from deleting the dependent until the reference is removed, which can be used to protect/persist a dependent object (e.g., a pod or its finalizer chain) against legitimate deletion by cluster operators or controllers that rely on owner-reference-driven GC — an authorization-bypass class issue (unauthorized escalation of a protected field / persistence primitive), matching the "admission control bypass leading to persisted protected field" bounty category.

### Likelihood Explanation
Requires only namespace-scoped RBAC to create/update the dependent resource plus legitimate delete/finalizer permission on some unrelated owner object (`X`) that the attacker controls to seed a duplicate/collided UID entry at creation time. No cluster-admin, node, or webhook access needed. The sequence (Create then Patch) is fully reproducible via standard API calls; the only non-trivial requirement is crafting duplicate/empty UID values in `ownerReferences`, which are attacker-controlled fields not tied to real object identity by this admission plugin.

### Recommendation
Make `indexByUID` (or its caller) detect and reject/collapse duplicate UIDs instead of silently overwriting, e.g., index using a stable, unique key derived from `(UID, APIVersion, Kind, Name)` or explicitly detect duplicate UIDs in the old and new reference lists and treat any ambiguous match conservatively (i.e., always include the ref in `newBlockingRefs` when its identity cannot be uniquely resolved). Additionally, consider validating/rejecting `ownerReferences` entries with duplicate or empty UIDs in `ValidateOwnerReferences`.

### Proof of Concept
Unit test in `plugin/pkg/admission/gc/gc_admission_test.go`:
1. Build `oldRefs = []metav1.OwnerReference{ {UID:"", Name:"Y", BlockOwnerDeletion:pointer(false)}, {UID:"", Name:"X", BlockOwnerDeletion:pointer(true)} }`.
2. Build `newRefs = []metav1.OwnerReference{ {UID:"", Name:"X", BlockOwnerDeletion:pointer(true)}, {UID:"", Name:"Y", BlockOwnerDeletion:pointer(true)} }`.
3. Call `newBlockingOwnerDeletionRefs(newObjWithRefs(newRefs), oldObjWithRefs(oldRefs))`.
4. Assert the returned slice contains an entry for `Y` (asserting `ret` includes a ref with `Name == "Y"`); current implementation fails this assertion, proving `Y`'s block-transition is dropped due to the UID collision, i.e., the delete-authorization loop at lines 138-152 would never be reached for `Y`'s owner.

func (a *gcPermissionsEnforcement) Validate(ctx context.Context, attributes admission.Attributes, o admission.ObjectInterfaces) (err error) {
	// // if the request is in the whitelist, we skip mutation checks for this resource.
	if a.isWhiteListed(attributes.GetResource().GroupResource(), attributes.GetSubresource()) {
		return nil
	}

	// if we aren't changing owner references, then the edit is always allowed
	if !isChangingOwnerReference(attributes.GetObject(), attributes.GetOldObject()) {
		return nil
	}

	// if you are creating a thing, you should always be allowed to set an owner ref since you logically had the power
	// to never create it.  We still need to check block owner deletion below, because the power to delete does not
	// imply the power to prevent deletion on other resources.
	if attributes.GetOperation() != admission.Create {
		deleteAttributes := authorizer.AttributesRecord{
			User:            attributes.GetUserInfo(),
			Verb:            "delete",
			Namespace:       attributes.GetNamespace(),
			APIGroup:        attributes.GetResource().Group,
			APIVersion:      attributes.GetResource().Version,
			Resource:        attributes.GetResource().Resource,
			Subresource:     attributes.GetSubresource(),
			Name:            attributes.GetName(),
			ResourceRequest: true,
			Path:            "",
		}
		decision, reason, err := a.authorizer.Authorize(ctx, deleteAttributes)
		if decision != authorizer.DecisionAllow {
			return admission.NewForbidden(attributes, fmt.Errorf("cannot set an ownerRef on a resource you can't delete: %v, %v", reason, err))
		}
	}

	// Further check if the user is setting ownerReference.blockOwnerDeletion to
	// true. If so, only allows the change if the user has delete permission of
	// the _OWNER_
	newBlockingRefs := newBlockingOwnerDeletionRefs(attributes.GetObject(), attributes.GetOldObject())

func indexByUID(refs []metav1.OwnerReference) map[types.UID]metav1.OwnerReference {
	ret := make(map[types.UID]metav1.OwnerReference)
	for _, ref := range refs {
		ret[ref.UID] = ref
	}
	return ret
}
