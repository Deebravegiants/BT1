### Title
Webhook `shop-domain` header is trusted as the tenant identifier but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop` (and `topic`, `webhook_id`, `api_version`) values are read from unauthenticated HTTP headers. `Registry.process` validates the HMAC and then hands `request.shop` straight to the app's handler as the tenant identifier, so the value an app uses to select "which shop this event belongs to" is never bound to the value the HMAC actually verifies.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read from headers, not from the signed body: [2](#0-1) 

`Registry.process` validates the HMAC over `request` (i.e. over the raw body via `to_signable_string`) and, once that check passes, forwards `request.shop` (a header value that was never part of the signed content) to the developer's handler as the trusted tenant identifier: [3](#0-2) 

The equality the gem should guarantee but does not is:
`shop bound by HMAC == shop delivered to the handler as WebhookMetadata#shop`.

In practice, `hmac(secret, raw_body)` only proves "this body was produced by someone who knows `api_secret_key`" — it says nothing about which shop the header claims the event is for. The documentation explicitly tells integrators to trust `data.shop` as the shop domain of the webhook and use it directly (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`): [4](#0-3) 

Because the header is never mixed into the signature, an attacker who can obtain one validly-HMAC'd webhook body (e.g. because they are themselves a merchant with the app installed, and thus legitimately receive real signed webhook deliveries for their own shop) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (or `shopify-shop-domain`) header value naming a different, victim shop. `HmacValidator.validate` will still return `true` because it never inspects the shop header: [5](#0-4) 

This is the same class of bug as the reported `InvestToken` issue: one binding (the value cryptographically verified) diverges from the value that is actually acted upon (the value used to route/authorize per-tenant processing), letting an authenticated-but-wrong-tenant actor make the system apply data under a different tenant's identity.

### Impact Explanation
This breaks the shop/tenant identity binding for webhook delivery: any app that keys its per-shop side effects (e.g. cache invalidation, database updates, queued jobs, session/token lookups) off `WebhookMetadata#shop` as recommended by this gem's own documentation can be made to process a validly-signed payload under an attacker-chosen shop domain, producing cross-tenant data corruption/access. This satisfies the "cross-tenant access" Critical impact category, since it lets one authenticated shop (or anyone possessing a captured/leaked webhook body+HMAC) impersonate another tenant purely by manipulating an HTTP header that the gem never authenticates.

### Likelihood Explanation
Requires the attacker to already possess a valid `(raw_body, hmac)` pair — most straightforwardly, a merchant who legitimately installed the app and receives real webhooks for their own store can extract one such pair from their own traffic and replay it against the app's webhook endpoint with a forged `shop-domain` header. No access to `api_secret_key` or an access token is needed, only knowledge of the app's public webhook callback URL and one captured legitimate delivery, making this practically reachable by any unprivileged actor who is or has been a merchant using the app.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header values in the HMAC-signable content, or otherwise cryptographically bind them to the body before validating, so that `HmacValidator.validate` fails if the shop header has been altered independently of the signed body. At minimum, document prominently that `data.shop` is unauthenticated and must not be trusted for tenant-selection without corroborating it against server-side state (e.g. the shop associated with the request's URL/path or session store).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and lets Shopify deliver a legitimate webhook (e.g. `orders/create`) to the app's callback endpoint, capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header value Shopify sent.
2. Attacker replays the exact same raw body and HMAC header to the same callback endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses `shop` as `"victim-shop.myshopify.com"` while `hmac` still matches because `to_signable_string` only returns `raw_body`, which is unchanged.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which returns `true` (see `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/utils/hmac_validator.rb:12-22`), and then invokes the developer's handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker's own order data>, ...)`.
5. Any app logic that uses `data.shop` to locate/update per-tenant records (as the gem's own documented example does) now operates on `victim-shop.myshopify.com`'s data using content the attacker fully controls.

          unless handler

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
