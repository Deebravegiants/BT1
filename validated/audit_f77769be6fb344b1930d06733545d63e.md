Based on my investigation, the documentation confirms that gas is always charged at transaction conversion time regardless of the `fix_ml_dsa_cost_charging` flag, and the flag only controls whether the *compute* (a separate resource-usage accounting used for chunk `compute_limit`/congestion, not gas) is mirrored on the receiver shard.

### Title
Uncharged compute for delegate signature verification when `fix_ml_dsa_cost_charging` is disabled - (File: runtime/runtime/src/actions.rs)

### Summary
When `fix_ml_dsa_cost_charging` is false, `apply_delegate_action` skips adding `delegate_signature_verification_compute` to `result.compute_usage` before calling `signed_delegate_action.verify()` [1](#0-0) . This means the compute-limit accounting (separate from gas) on the receiver shard does not reflect the real CPU cost of verifying an ML-DSA-65 signature, since gas for the verification is charged elsewhere at transaction conversion time on the signer shard [2](#0-1) .

### Finding Description
`apply_delegate_action` conditionally meters `delegate_signature_verification_compute` into `result.compute_usage` only if `apply_state.config.wasm_config.fix_ml_dsa_cost_charging` is true, before calling `signed_delegate_action.verify()`, which performs the actual (possibly expensive ML-DSA-65) cryptographic verification [1](#0-0) . The code comment itself documents that "[w]ithout the fix the compute is instead mis-charged on the signer shard (which never runs this verify), letting the work escape the receiver shard's budget" [3](#0-2) .

However, according to the design documentation, the *gas* cost of ML-DSA-65 signature verification for delegate actions is charged unconditionally at transaction conversion time via `ml_dsa_65_verification_cost`, "per signature, including each `Delegate` action's inner signer" [2](#0-1) . This is a fixed, protocol-feature-gated 100 Ggas surcharge added to the transaction's burnt gas independent of the `fix_ml_dsa_cost_charging` flag. The flag only affects the separate `compute_usage` accounting used to prevent the chunk's compute budget (`compute_limit`) from being exceeded due to mismatches between where gas is charged (signer shard) and where the actual CPU work happens (receiver shard). This is a known, intentional, protocol-version-gated accounting nuance rather than an entirely uncharged/free-of-cost operation — gas is still burnt for every ML-DSA-65 delegate signature regardless of the flag.

### Impact Explanation
When the flag is disabled, an attacker who submits `DelegateActionV2` receipts with ML-DSA-65 public keys does cause verification compute to run on the receiver shard without a matching compute-budget deduction there. This could in principle let the receiver shard do more real CPU work per chunk than its `compute_limit` intends, since the compute for this operation is credited to the wrong shard. This is a genuine metering-completeness/compute-limit-accuracy issue as described in the code comment, but it does not constitute a fully free/unmetered execution: the attacker still pays gas (and thus balance) for every such signature at conversion time, bounding the economic feasibility of large-scale spam. The security-relevant effect is bounded to a possible discrepancy between charged compute and actual compute per chunk on receiver shards, matching a "gas/compute metering imprecision" class rather than a full DoS with zero cost to the attacker.

### Likelihood Explanation
Exploitability requires: (1) `PostQuantumSignatures` active so ML-DSA-65 keys/signatures are accepted at all [4](#0-3) , and (2) the specific protocol version/config combination where `fix_ml_dsa_cost_charging` is false while ML-DSA-65 delegate actions are otherwise valid. Both flags are protocol-version-gated in `core/parameters/src/config_store.rs` and `runtime_configs/*.yaml`/`.snap` snapshots, meaning whether this window actually exists in any deployed protocol version is determined entirely by the parameter tables, which I was not able to fully cross-reference against `fix_ml_dsa_cost_charging`'s activation version relative to `PostQuantumSignatures`'s activation version within the available context. If the fix was shipped in the same protocol version as (or before) ML-DSA-65 activation, this window never exists on any live network, and the finding is only theoretically reachable in constructed test configs (e.g., `random_config.rs`), not through unprivileged submission on a real network.

### Recommendation
Confirm via `core/parameters/src/config_store.rs` whether any stabilized protocol version has `PostQuantumSignatures` enabled while `fix_ml_dsa_cost_charging` is false. If such a version exists/existed on a live network, backport `fix_ml_dsa_cost_charging` to activate at or before `PostQuantumSignatures`. If no such version exists on any live/testnet chain (i.e., the fix is bundled atomically with ML-DSA-65 stabilization), this is not exploitable in practice and only matters for internal config-generation/test tooling.

### Proof of Concept
Integration test plan (mirroring `test-loop-tests/src/tests/ml_dsa_verification_cost.rs`): construct a runtime config where `PostQuantumSignatures` is active and `fix_ml_dsa_cost_charging` is false (if representable via `config_store.rs`/`random_config.rs`), submit a chunk containing many `DelegateActionV2` receipts signed with ML-DSA-65 keys, and assert that `result.compute_usage` for `apply_delegate_action` does not increase despite `signed_delegate_action.verify()` running full ML-DSA verification, while gas gets burnt normally at conversion — demonstrating the compute/gas accounting divergence described in the code comment at [5](#0-4) .

pub(crate) fn apply_delegate_action(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    action_receipt: &VersionedActionReceipt,
    sender_id: &AccountId,
    signed_delegate_action: VersionedSignedDelegateActionRef<'_>,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    // The inner delegate signature is verified below, here on the receiver shard.
    // Meter its verification compute against this shard's `compute_limit`; the gas
    // for it was already burnt at tx conversion on the signer shard. Without the
    // fix the compute is instead mis-charged on the signer shard (which never runs
    // this verify), letting the work escape the receiver shard's budget. See
    // `signature_verification_cost`.
    if apply_state.config.wasm_config.fix_ml_dsa_cost_charging {
        let verify_compute = delegate_signature_verification_compute(
            &apply_state.config.fees,
            signed_delegate_action.delegate_action().public_key(),
        );
        result.compute_usage = safe_add_compute(result.compute_usage, verify_compute)?;
    }
    if !signed_delegate_action.verify() {
        result.result = Err(ActionErrorKind::DelegateActionInvalidSignature.into());
        return Ok(());
    }
