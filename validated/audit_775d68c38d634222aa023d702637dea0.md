### Title
Unbounded, attacker-fed `BidCache` in the intents-coprocessor RPC watcher causes RPC-node OOM - ([File: modules/pallets/intents-coprocessor/rpc/src/lib.rs])

### Summary
`pallet_intents_rpc`'s `BidCache` inserts a new heap-allocated entry for every `place_bid` extrinsic seen entering the local transaction pool, with no maximum entry count and no maximum aggregate size — only a time-based sweep (`remove_expired`) bounds it. Since `place_bid` accepts up to a 1 MiB opaque payload and the deposit/validity checks inside the dispatchable are *not* evaluated at pool-admission time, an unprivileged party can flood any node running this RPC extension with many large, distinct `place_bid` transactions and grow `BidCache` far faster than the periodic TTL sweep can drain it, exhausting the node's memory. This is the same bug class as CVE-2025-2240 (SmallRye's `meterMap`): every externally observed call creates a new map entry that is never capacity-bounded.

### Finding Description
`BidCache` is a process-local `RwLock<HashMap<H256, OrderBids>>` populated by `run_bid_watcher`, which subscribes to the node's transaction-pool import stream and, for every transaction recognized as a `place_bid` call via `extract_bid`, inserts a new `BidEntry { filler, user_op }` keyed by `commitment`: [1](#0-0) 

The only mitigation against unbounded growth is a periodic `remove_expired()` call that evicts entries whose `first_seen` is older than a fixed TTL: [2](#0-1) 

Critically, this eviction is time-based, not count- or size-based, so the cache's memory footprint at any instant is bounded only by *(insertion rate) × (TTL)*, not by any hard cap. `run_bid_watcher` fires on every transaction entering the local ready pool: [3](#0-2) 

The `place_bid` extrinsic itself allows a payload of up to 1 MiB: [4](#0-3) 

The pallet-level checks that would normally throttle spam — the `Currency::reserve` deposit check, the phantom-order window check, `InvalidUserOp`, etc. — all run inside the dispatchable body, which only executes at block-authoring/execution time, not at transaction-pool admission (`validate_transaction`) time. `extract_bid` only requires the extrinsic to decode as a signed `place_bid` call; it performs no validation against on-chain state, balances, or windows: [5](#0-4) 

So any signed account that can merely afford the length/weight-based transaction fee (not the storage deposit, and not a valid order/commitment) can get a `place_bid` transaction into a node's ready pool and thereby trigger a fresh `BidCache` insertion of up to ~1 MiB. Using multiple accounts/nonces (sybil), an attacker can push many such transactions into the mempools of RPC nodes running this extension, each generating a distinct `(commitment, filler)` cache entry that survives until the TTL sweep runs and expires it — and if submission rate exceeds `cache_size_drained_per_sweep / cleanup_interval`, the cache grows without bound, exactly mirroring the SmallRye `meterMap` OOM pattern: an externally-triggerable code path creates a new object per call with no cap on total objects retained.

### Impact Explanation
Any node exposing the `intents_getBidsForOrder`/`intents_subscribeBids` RPC (i.e., running `pallet_intents_rpc`'s watcher against its local transaction pool) can be driven out of memory by an unprivileged attacker submitting a stream of large, distinct `place_bid` transactions, none of which need to be economically backed or valid on-chain. This is a denial-of-service against RPC infrastructure that intent solvers/fillers rely on for sub-second bid discovery, degrading or crashing that service (CWE-1325 / unbounded resource consumption), matching the High-severity DoS impact of the referenced advisory.

### Likelihood Explanation
Likelihood is High: the attack requires only the ability to submit ordinary signed extrinsics that decode as `place_bid` calls (any funded account, payload up to 1 MiB, arbitrary/garbage `commitment`), no special privileges, and no on-chain success is required — the transaction only needs to be admitted into a node's ready pool to trigger the cache insertion via the import-notification stream. The pallet's economic/validity guards (deposit reservation, phantom-window check) do not run at pool-admission time and thus provide no defense against this specific vector.

### Recommendation
Bound `BidCache` by both entry count and aggregate payload size (e.g., an LRU/bounded map with a hard cap on total commitments and/or total bytes, evicting oldest/least-relevant entries immediately when the cap is hit, in addition to the existing TTL sweep). Additionally, consider validating `place_bid` transactions more strictly before caching (e.g., checking against `CurrentPhantomOrder`/known order commitments, and rejecting when the pool already holds too many entries for that filler or globally) so that pool admission cost tracks actual protocol-level cost rather than just the flat transaction fee.

### Proof of Concept
1. Fund N accounts with just enough balance to pay the transaction fee for a `place_bid` call carrying a payload near the 1 MiB cap (no need to fund the storage deposit reserved inside the dispatchable, since that check never runs at pool-admission time).
2. From each account, submit repeated `place_bid(commitment, user_op)` extrinsics with fresh, unique `commitment` values (arbitrary `H256`, no relation to any real order) and near-max-size `user_op` payloads, using sequential nonces to keep each transaction valid and admissible to the pool.
3. Target these transactions at a node's RPC endpoint or let them propagate via gossip to any node running `pallet_intents_rpc`'s `run_bid_watcher`.
4. Observe `BidCache`'s `HashMap<H256, OrderBids>` size grow roughly linearly with submitted transactions (~1 MiB each) until it exceeds the `cleanup_interval`-bounded drain rate, driving the RPC process's memory usage up until OOM.

/// In-memory bid cache.
pub struct BidCache {
	bids: RwLock<HashMap<H256, OrderBids>>,
	ttl: Duration,
}

impl BidCache {
	pub fn new(ttl: Duration) -> Self {
		Self { bids: RwLock::new(HashMap::new()), ttl }
	}

	pub fn insert(
		&self,
		commitment: H256,
		filler: Vec<u8>,
		user_op: Vec<u8>,
	) -> Result<(), String> {
		let entry = BidEntry { filler: filler.clone(), user_op };

		let mut bids = self.bids.write().map_err(|e| format!("BidCache lock poisoned: {e}"))?;
		let order = bids
			.entry(commitment)
			.or_insert_with(|| OrderBids { first_seen: Instant::now(), entries: Vec::new() });
		if let Some(existing) = order.entries.iter_mut().find(|e| e.filler == filler) {
			*existing = entry;
		} else {
			order.entries.push(entry);
		}
		Ok(())
	}

	pub fn remove_expired(&self) -> Result<(), String> {
		let now = Instant::now();
		let mut bids = self.bids.write().map_err(|e| format!("BidCache lock poisoned: {e}"))?;
		bids.retain(|_commitment, order| now.duration_since(order.first_seen) < self.ttl);
		Ok(())
	}

pub fn extract_bid<T, Extra>(encoded: &[u8]) -> Option<(H256, Vec<u8>, Vec<u8>)>
where
	T: pallet_intents_coprocessor::Config,
	T::RuntimeCall: frame_support::traits::IsSubType<pallet_intents_coprocessor::Call<T>>
		+ DecodeWithMemTracking,
	T::AccountId: Encode + From<[u8; 32]> + DecodeWithMemTracking,
	Extra: DecodeWithMemTracking,
{
	let xt = sp_runtime::generic::UncheckedExtrinsic::<
		sp_runtime::MultiAddress<T::AccountId, ()>,
		T::RuntimeCall,
		sp_runtime::MultiSignature,
		Extra,
	>::decode(&mut &encoded[..])
	.ok()?;

	let filler = match &xt.preamble {
		sp_runtime::generic::Preamble::Signed(address, _, _) => match address {
			sp_runtime::MultiAddress::Id(id) => id.encode(),
			_ => return None,
		},
		_ => return None,
	};

	match xt.function.is_sub_type()? {
		pallet_intents_coprocessor::Call::place_bid { commitment, user_op } =>
			Some((commitment.clone(), filler, user_op.to_vec())),
		_ => None,
	}
}
