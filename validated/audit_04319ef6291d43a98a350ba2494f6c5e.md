### Title
Attacker can front-run a `dest` account with a small vesting claim to permanently block the victim's legitimate vested claim - ([File: polkadot/runtime/common/src/claims/mod.rs])

### Summary
`process_claim` in the claims pallet checks `T::VestingSchedule::vesting_balance(&dest).is_some()` to reject vesting claims when `dest` already has a vesting schedule, but `dest` is an attacker/caller-chosen `T::AccountId` unrelated to the Ethereum signer's identity. Because the check is on `dest`, not on ownership of `dest`, any unprivileged party holding any valid Ethereum claim mapped with a vesting schedule (even a dust claim) can call `claim`/`claim_attest` with `dest` set to a victim's target account and permanently poison it against any future vested claim into that same `dest`.

### Finding Description
`claim`/`claim_attest` are unsigned extrinsics (`ensure_none(origin)`) where `dest: T::AccountId` is fully attacker/caller-controlled and only cryptographically bound to the Ethereum signature over `dest` itself — i.e., the *signer* proves they control an Ethereum key, but nothing ties `dest` to any real-world relationship between the Ethereum claimant and the destination Substrate account: [1](#0-0)

The vesting-branch check is `T::VestingSchedule::vesting_balance(&dest).is_some()` — this only inspects whether `dest` *currently* has a vesting schedule, never whether the *claim being processed* semantically belongs to whoever is entitled to `dest`. Since `Vesting`/`Claims` storage is keyed by `EthereumAddress` (the signer), and `dest` is a free parameter of the call, any account holding a legitimate Ethereum claim that has an associated `Vesting` entry (even a dust value, e.g. from `mint_claim` by root/genesis with minimal `value` and any `vesting_schedule`) can call `claim(dest=X, sig)` to install a vesting schedule on account `X` first. This calls `add_vesting_schedule`, which places a `VestingSchedule` on `dest` — a storage side-effect that is *global to the account*, not to any specific claim or signer.

Once that vesting schedule exists on `X`, a subsequent legitimate claimant (who separately owns a real Ethereum claim mapped with `Vesting` entry, and wants their DOT sent to the same `dest = X`) calling `claim`/`claim_attest`/`attest` with `dest = X` will hit `vesting_balance(&dest).is_some() == true` and get `Error::VestedBalanceExists`, permanently blocking their claim's processing into that destination. The claim (`Claims::<T>` keyed by the *victim's* Ethereum address) is untouched/not consumed, so the victim's DOT is not literally destroyed, but they can never successfully call `claim`/`claim_attest`/`attest` with that specific `dest` account — the call always reverts with `VestedBalanceExists` as long as the attacker's vesting schedule (or any lock from `pallet-vesting`) remains on `dest`.

Existing protections examined and found insufficient:
- `ensure_none(origin)` only ensures the call is unsigned/valid per `validate_unsigned`, it does not bind `dest` to the correct owner.
- `eth_recover` cryptographically verifies the Ethereum signature over `dest`'s bytes, but this signature is over the *attacker's own* valid claim keyed to the *attacker's* Ethereum address — it says nothing about whether `dest` belongs to that attacker in any social/economic sense. The protocol design intentionally allows arbitrary `dest`, so any Ethereum-address holder can sign a message directing their claim to any Substrate account, including someone else's.
- There's no per-claim/per-signer marker preventing multiple different Ethereum claims from targeting the same `dest`; the only cross-check is the coarse "does `dest` already have *any* vesting schedule" check, which triggers on the state left by the *first* mover, not the intended owner.

### Impact Explanation
This is a denial-of-claim on a specific `dest` account for any vested claim: the victim's `claim`/`claim_attest`/`attest` call targeting that `dest` will permanently fail with `VestedBalanceExists` as long as the attacker's vesting schedule remains active on that account (vesting schedules only clear once fully vested, which can be a very long time or indefinite depending on the schedule chosen by the attacker via `mint_claim`'s root-configured parameters, or more realistically via any legitimately-obtained dust vesting claim). This blocks the victim from ever completing their vested Ethereum claim to that specific destination account through the on-chain claims flow, though the victim can work around it by choosing a different, fresh destination account for a subsequent claim attempt (assuming they haven't hard-committed to `dest = X` for external reasons, e.g. an exchange withdrawal address or a pre-announced/publicized address).

### Likelihood Explanation
The precondition that the attacker holds a valid Ethereum claim with an associated `Vesting` entry (even dust) requires that such a claim exists in `Claims`/`Vesting` storage — these are populated via genesis config or root-only `mint_claim`, not by ordinary users. This significantly limits real-world attacker feasibility: the "attacker" must already be one of the pre-registered Ethereum-address holders from the original claims genesis dataset (real historical DOT sale participants), not an arbitrary unprivileged actor with no dependency on privileged setup. Given the claims pallet was seeded once (largely a legacy/historical feature for the original DOT token distribution), the practical attack surface for new exploitation today is very limited — an attacker needs to already control one of the finite, already-allocated Ethereum claims with a vesting component, which is a closed and historical set, not something obtainable at will by any unprivileged actor. The scenario is technically reachable via only user-signed/unsigned extrinsics (`claim`), satisfying the reachable-path requirement, but real-world exploitability depends on possession of one of these pre-existing, non-renewable claim slots.

### Recommendation
Bind the vesting-schedule collision check (and ideally the whole claim) to the claim's intended recipient rather than solely to arbitrary account state. Options: track which Ethereum address/claim installed the existing vesting schedule on `dest`, and only reject if a *different, unrelated* claim already exists for that `dest`; or disallow `add_vesting_schedule` collisions from unrelated claims by, e.g., requiring `dest` to prove specific opt-in/ownership before an unrelated Ethereum claim can install a vesting lock on it, or by using `merge_schedules`-style semantics (as newer pallet-vesting versions support) instead of hard-failing on any pre-existing schedule.

### Proof of Concept
Rust unit test in `polkadot/runtime/common/src/claims/tests.rs`:
1. In `new_test_ext()`/genesis, register two Ethereum claims: attacker's key (`six`) with a small `value` and a `vesting_schedule = Some((V, v_per_block, start))`, and a legitimate/large claim for Alice's key with its own `vesting_schedule = Some((BIG, ...))`.
2. Call `Claims::claim(RuntimeOrigin::none(), 42, sig_from_six(42))` — assert `Ok(())`, and assert `Vesting` lock now exists on account `42` via `<Test as Config>::VestingSchedule::vesting_balance(&42).is_some()`.
3. Call `Claims::claim(RuntimeOrigin::none(), 42, sig_from_alice(42))` — assert it returns `Err(Error::<Test>::VestedBalanceExists)`, despite Alice's Ethereum address being completely unrelated to account `six`'s.
4. Assert Alice's original claim entry in `Claims`/`Vesting` storage (keyed by her Ethereum address) still exists untouched, confirming her legitimate claim is now permanently stuck for `dest = 42` (repeat call yields the same error indefinitely).

	fn process_claim(signer: EthereumAddress, dest: T::AccountId) -> sp_runtime::DispatchResult {
		let balance_due = Claims::<T>::get(&signer).ok_or(Error::<T>::SignerHasNoClaim)?;

		let new_total =
			Total::<T>::get().checked_sub(&balance_due).ok_or(Error::<T>::PotUnderflow)?;

		let vesting = Vesting::<T>::get(&signer);
		if let Some(_) = vesting {
			if T::VestingSchedule::vesting_balance(&dest).is_some() {
				return Err(Error::<T>::VestedBalanceExists.into());
			}

			// A vesting schedule installs a balance lock, which requires the account to stay alive,
			// otherwise it is dusted and the lock placed on a non-existent account. The `dest` may
			// already hold funds, so a small claim that tops an existing account over the ED is
			// valid.
			let free_after = CurrencyOf::<T>::free_balance(&dest).saturating_add(balance_due);
			ensure!(
				free_after >= CurrencyOf::<T>::minimum_balance(),
				Error::<T>::ClaimBelowExistentialDeposit,
			);
		}

		// We first need to deposit the balance to ensure that the account exists.
		let _ = CurrencyOf::<T>::deposit_creating(&dest, balance_due);

		// Check if this claim should have a vesting schedule.
		if let Some(vs) = vesting {
			// This can only fail if the account already has a vesting schedule or its balance is
			// below the existential deposit, both of which are checked above.
			T::VestingSchedule::add_vesting_schedule(&dest, vs.0, vs.1, vs.2)
				.map_err(|_| Error::<T>::VestedBalanceExists)?;
		}
