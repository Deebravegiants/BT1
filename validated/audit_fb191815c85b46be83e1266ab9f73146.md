### Title
Webhook HMAC Does Not Bind the `shop`, `topic`, or `webhook_id` Identity Fields, Enabling Cross-Tenant Webhook Forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC verified in `Utils::HmacValidator.validate` authenticates the *body bytes* but not the `shop-domain`, `topic`, or `webhook-id` headers that `Webhooks::Registry.process` subsequently trusts as the tenant identity for dispatching the webhook payload. Any actor who can obtain one genuinely-signed `(body, hmac)` pair for the app's shared `api_secret_key` (e.g., by installing the app on their own shop and receiving one real webhook) can replay that exact body/hmac while substituting an arbitrary `shop-domain` header, causing the host application's handler to process attacker-controlled data under a victim shop's identity.

### Finding Description
`Webhooks::Request` exposes `shop`, `topic`, and `webhook_id` purely from HTTP headers: [1](#0-0) 

But the signable string used for HMAC verification only covers the raw body, never these headers: [2](#0-1) 

`HmacValidator.validate` computes the signature strictly over `to_signable_string`: [3](#0-2) 

`Webhooks::Registry.process` validates only this body-bound HMAC, then unconditionally forwards `request.shop`, `request.topic`, and `request.webhook_id` — none of which were part of the signed data — to the handler as trusted metadata: [4](#0-3) 

This is exactly the bug class described in the analog report: a value the application acts on (`shop`, used as the tenant/session key for the webhook data) is not bound by the same authentication mechanism (`hmac`) that is checked before trusting the request. Because `api_secret_key` is shared across every shop that installs the app, any merchant with a legitimately-signed `(body, hmac)` pair — trivially obtainable by triggering one real webhook to their own store — can resend that exact `body`/`hmac` pair to the app's webhook endpoint with a forged `shop-domain` (and/or `topic`/`webhook-id`) header. `HmacValidator.validate` will still pass because it only checks the body bytes, and `Registry.process` will hand the attacker-controlled body to the handler labeled as coming from an arbitrary victim shop.

Formally, the broken identity-binding equality is:
`shop_authenticated_by_hmac ("") != shop_acted_on_by_handler (request.shop header)`

### Impact Explanation
This breaks the tenant boundary the webhook subsystem is meant to enforce. A host application that keys any state (order data, GDPR erasure requests, inventory updates, session/webhook-driven access grants) off `WebhookMetadata#shop` can be made to apply attacker-supplied data to another merchant's tenant, since the gem asserts the request is authentic for that shop when it has verified nothing about the shop at all. This is a cross-tenant confusion vulnerability reachable by any actor who can install the app on their own store (an ordinary, unprivileged merchant relationship) — no access token, `client_secret`, or privileged account is required.

### Likelihood Explanation
Exploitation requires only: (1) installing the app as any shop (a normal unprivileged action for a public/multi-tenant app) to receive one genuinely HMAC-signed webhook, and (2) replaying the identical body/hmac while swapping the `shop-domain` (and optionally `topic`/`webhook-id`) HTTP headers when POSTing to the app's webhook endpoint. Because `to_signable_string` never varies these headers, the check in `HmacValidator.validate` cannot detect the substitution.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the request before `Webhooks::Registry.process` trusts them, so that any tampering with these fields invalidates the signature.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers any webhook event (e.g., `orders/create`), capturing the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header `H` that Shopify computed with the app's `api_secret_key`.
2. Attacker crafts a new HTTP request to the app's webhook endpoint using the exact same body `B` and HMAC header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally a different `X-Shopify-Topic`).
3. `Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed; `to_signable_string` still returns `B`.
4. `Utils::HmacValidator.validate(request)` recomputes HMAC over `B` and matches `H`, returning `true` per [3](#0-2) .
5. `Webhooks::Registry.process` proceeds and invokes the handler with `shop: "victim-shop.myshopify.com"` and attacker-chosen body content, per [4](#0-3) , despite the data never originating from that shop.
