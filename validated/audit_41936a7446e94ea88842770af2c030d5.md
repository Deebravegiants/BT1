### Title
Attacker-controlled, unbounded `circomData.timeStamp` in `EmporiumUpgradeable.handleOut` lets an attacker mint two identical commitments for the same stealth address, permanently freezing one leaf via nullifier collision - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.handleOut` builds the output UTXO's `timeStamp` directly from the caller-supplied `circomData.timeStamp` with no check against `block.timestamp`, a per-signer counter, or any other freshness constraint. Because the on-chain commitment is `hash4(amount, token, stealthAddress, timeStamp)` and the nullifier used to spend a note is a pure function of `(commitment, nullifyingPrivateKey)` — independent of the leaf's merkle position — two `runAction` calls that reproduce the same `(A, T, S, Ts)` tuple insert two distinct leaves that collapse to the same nullifier, making the second spend permanently impossible.

### Finding Description
Equality that must hold: for any two genuinely distinct notes N1 ≠ N2 owned by the same key, their nullifiers `nullifier(N1) ≠ nullifier(N2)` so each can be independently spent (SINGLE_SPEND per leaf). This is broken because the commitment/nullifier scheme derives the nullifier only from the commitment value and the spender's private key, not from the tree index: [1](#0-0) 

The commitment itself is `Poseidon(amount, erc20TokenAddress, publicKey/stealthAddress, timeStamp)`, matched identically on-chain in `HinkalBase.createOnchainCommitment`: [2](#0-1) [3](#0-2) 

In `EmporiumUpgradeable.handleOut`, the output UTXO's timestamp is taken verbatim from `circomData.timeStamp`, a fully attacker-supplied field, with no monotonic counter, `block.timestamp` binding, or per-signer nonce: [4](#0-3) 

Replay protection in `verifyWallet` is keyed only on `circomData.emporiumMessage`, which is independent of `circomData.timeStamp`, so the attacker can vary `emporiumMessage` across two `runAction` calls while holding `timeStamp` (and every other input) fixed: [5](#0-4) 

Attacker's exact call sequence: craft two `EmporiumOperation[]` stacks (e.g., wrap/unwrap the same fixed amount of WETH twice) so that `balanceChange` resolves to the same amount `A` for the same token `T` in both `runAction` invocations, set `circomData.stealthAddressStructure` to the victim's public stealth address `S` in both calls, and set `circomData.timeStamp` to the same value `Ts` in both calls while using two different `emporiumMessage` values to defeat `usedMessages`. Both calls succeed and insert leaves with identical commitment `hash4(A,T,S,Ts)` at different tree positions. When the victim later spends either leaf (using their private key that corresponds to `S`), the derived nullifier is identical for both leaves because it is a function of `(commitment, nullifyingPrivateKey)` only, not of the merkle path. The second leaf's nullifier is then rejected as already used, permanently freezing that leaf's value.

Notably, developers were aware duplicate-commitment collisions were possible: `DepositOnChainUtxosExternalAction` explicitly offsets `circomData.timeStamp + utxoIndex` to avoid duplicate commitments *within a single call*: [6](#0-5) [7](#0-6) 

However, `EmporiumUpgradeable.handleOut` has no equivalent mitigation, and neither contract prevents collisions *across separate calls*, since there is no state tracking previously used `(A,T,S,Ts)` tuples or requiring `timeStamp` to be monotonic/derived from `block.timestamp`.

None of the existing guards stop this: `performHinkalChecks`/`dimensionsCheck` validate array shapes, not timestamp freshness; `verifyProof` only checks that the supplied commitment matches the circuit's Poseidon computation over the attacker-chosen inputs — it does not reject repeated inputs; `rootHashExists` only checks the merkle root used for spending inputs, unrelated to output commitment uniqueness; and `insertNullifiers`/the `nullifiers` mapping correctly reject the second spend by design — that rejection is exactly the freezing mechanism, since the underlying leaf is otherwise legitimate and unspent.

### Impact Explanation
The attacker can permanently lock funds addressed to any known victim stealth address by ensuring two Emporium-derived output UTXOs share the same `(amount, token, stealthAddress, timeStamp)` tuple. Whichever of the two leaves is spent first "burns" the shared nullifier, so the other leaf's tokens become permanently unspendable by the legitimate owner — a permanent freezing of shielded user funds, matching the Critical category ("permanent freezing of user funds"). If the attacker targets their own stealth address instead, the impact is self-inflicted and not exploitable against a third party, but the victim-targeted variant is fully attacker-controlled and repeatable against any victim address the attacker chooses.

### Likelihood Explanation
Preconditions: attacker needs only the ability to call `EmporiumUpgradeable.runAction` twice as an unprivileged, allowed-recipient caller (per the threat model, any EOA can do this), craft two `EmporiumOperation[]` stacks that produce the same numeric `balanceChange` for the same token, and set the same `circomData.timeStamp` and target `stealthAddressStructure` in both calls while varying `emporiumMessage`. This requires no privileged role, no relayer collusion, and no exotic preconditions — reproducing an identical `balanceChange` (e.g., wrap/unwrap a fixed ETH amount to WETH twice) is trivial and cheap (gas cost only), making the attack fully repeatable against arbitrary victims.

### Recommendation
Do not let `outUtxo.timeStamp` be arbitrary attacker input. Bind it to `block.timestamp` (as `_createProoflessDepositCommitments` already does) or to a strictly monotonic, per-output nonce/counter enforced by the contract, so that no two commitments produced by different `runAction` calls (or even within the same call) can collide for a given `(amount, token, stealthAddress)` triple.

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable` and a mock endpoint that lets the attacker deterministically produce a fixed `balanceChange = A` for token `T` (e.g., a mock WETH wrap/unwrap flow).
2. Call `runAction` with `circomData.timeStamp = Ts`, `circomData.stealthAddressStructure = victimS`, `circomData.emporiumMessage = m1`; capture the inserted leaf/commitment `C1 = hash4(A, T, victimS, Ts)`.
3. Call `runAction` again with identical `A, T, victimS, Ts` but `circomData.emporiumMessage = m2 ≠ m1`; assert it succeeds (no `UsedMessage` revert) and inserts a second leaf `C2 == C1` at a different tree index — assert `C1 == C2` (equality that should have been broken but is not).
4. Using the victim's `nullifyingPrivateKey`, compute nullifier for leaf at index of `C1` and for leaf at index of `C2` via the same circuit logic (`Signature` + `NullifierCalculator`); assert `nullifier(C1) == nullifier(C2)`.
5. Simulate spending the first leaf (mark nullifier used); attempt to spend the second leaf with a valid merkle proof to its own leaf index; assert the transaction reverts due to nullifier-already-used, demonstrating permanent freezing of the second leaf's value.

template OriginalCommitmentCalculator() {
  signal input amount;
  signal input erc20TokenAddress;
  signal input publicKey;
  signal input timeStamp;
  signal output out;

  component calcIsAmountZero = IsZero();
  calcIsAmountZero.in <== amount;

  component calcCommitment = Poseidon(4);
  calcCommitment.inputs[0] <== amount;
  calcCommitment.inputs[1] <== erc20TokenAddress;
  calcCommitment.inputs[2] <== publicKey;
  calcCommitment.inputs[3] <== timeStamp;
