### Title
Webhook `shop`, `topic`, and `webhook_id` identifiers are trusted from unauthenticated headers while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` from HTTP headers, but `to_signable_string` (used by the HMAC check) only returns the raw body. `Registry.process` validates the HMAC and then trusts these header-derived values to route and label the webhook payload to a specific tenant, without those values being part of what was cryptographically verified.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from headers with no cryptographic binding to the signed payload: [2](#0-1) 

`Registry.process` validates only `Utils::HmacValidator.validate(request)` (which in turn calls `to_signable_string`, i.e. body-only) and then immediately trusts `request.shop`/`request.topic` to construct the metadata handed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string`: [4](#0-3) 

Binding broken (as an equality): the gem implicitly asserts `HMAC_valid(raw_body) == authenticated(shop_header, topic_header, webhook_id_header)`. In reality `HMAC_valid(raw_body)` says nothing about the headers — only the body bytes are verified, not the shop/topic/webhook_id bytes that the app relies on for tenant routing.

This is analogous to the report's core theme: an identity-relevant field ("shop"/tenant) that a downstream consumer treats as authorized is not actually covered by the same check that gates high-risk/other fields — here the "high risk" analog is per-tenant data attribution, and the "uncovered field" is the shop-domain header.

### Impact Explanation
An unprivileged actor who can install the target app on their own store (a fully legitimate, low-privilege action requiring no secrets) will receive genuine Shopify-signed webhooks for their own shop — i.e., valid `(raw_body, hmac)` pairs signed with the app's `api_secret_key`, which the attacker never needs to know. Because the HMAC signature is computed over the body only, the same `(raw_body, hmac)` pair remains valid for *any* value of the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, and `X-Shopify-Webhook-Id` headers. The attacker can replay the captured body+hmac to the app's public webhook endpoint while substituting a victim shop's domain in the `shop-domain` header. `Registry.process` will pass this HMAC check and hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop, while the actual JSON body content is fully attacker-controlled (since it originated from the attacker's own store data). This is a cross-tenant data-injection primitive: the app will process attacker-authored data (e.g., customer records, order data, product data) under another merchant's tenant identity, corrupting or forging state for a shop the attacker does not control.

### Likelihood Explanation
Any developer/merchant can install a target Shopify app on their own free development store to legitimately receive real signed webhooks, requiring no privileged credentials, tokens, or secrets — only normal, unauthenticated app-install actions available to any internet user. Capturing and replaying an HTTP POST with a modified header is trivial. The only gating factor is whether the host application actually differentiates behavior by `shop` from the webhook payload (which is the intended and documented use of `WebhookMetadata#shop`), making this a broadly reachable pattern for apps built on this gem's documented webhook API.

### Recommendation
Bind the shop/topic/webhook identifiers to the signed payload verification, e.g. by including the relevant headers (shop-domain, topic, webhook-id) in the HMAC-signed material, or by requiring the host app to independently confirm the `shop` header corresponds to a shop for which this specific webhook subscription/HMAC pair was registered before trusting it for tenant-scoped writes. At minimum, document prominently that `Webhooks::Request#shop`/`#topic`/`#webhook_id` are NOT covered by the HMAC and must not be trusted for authorization/tenant-routing decisions without additional verification (e.g., cross-checking against `Context.host_name`/an allow-list of shops known to this app instance, or verifying the shop is actually installed with a stored offline session before using it as a tenant key).

### Proof of Concept
1. Attacker installs the vulnerable Shopify app on their own store `attacker-shop.myshopify.com`.
2. Attacker triggers a real event (e.g., updates a customer record with attacker-chosen name/email) causing Shopify to send a legitimately signed webhook: `raw_body = {"customer": {...attacker-controlled...}}`, `X-Shopify-Hmac-Sha256 = HMAC_SHA256(api_secret_key, raw_body)`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures this exact `raw_body` and `X-Shopify-Hmac-Sha256` value.
4. Attacker sends a new HTTP POST directly to the app's public webhook endpoint with the same `raw_body` and `X-Shopify-Hmac-Sha256`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the (unchanged) HMAC — see `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/utils/hmac_validator.rb:12-22`.
6. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON>, ...)` — see `lib/shopify_api/webhooks/registry.rb:198-199` — and the host application processes attacker-controlled data as belonging to the victim tenant.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
