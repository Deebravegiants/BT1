### Title
Webhook shop-domain (and topic/webhook-id) header is trusted for tenant attribution without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates only the raw JSON body against the HMAC signature. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values, which are taken directly from unauthenticated HTTP headers, are never part of the signed payload. Any party who can obtain one valid `(body, hmac)` pair for the app's shared `client_secret` (e.g. by installing the app on their own store and receiving a genuine webhook) can replay that same body/HMAC pair while substituting an arbitrary `shop-domain` header, and the gem will accept it as authentic and hand it to the merchant's webhook handler attributed to a different, victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 

`to_signable_string` returns only `@raw_body`. The `shop`, `topic`, `webhook_id`, and `api_version` accessors are all read straight from HTTP headers with no cryptographic binding: [2](#0-1) 

`Registry.process` verifies the request using `HmacValidator.validate`, which internally calls `to_signable_string` (i.e. only the body) against the secret, and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the HMAC solely from `verifiable_query.to_signable_string` (the body) and compares it to the `hmac` header: [4](#0-3) 

This breaks the identity binding: `shop header == tenant the webhook is attributed to` is never checked against `shop covered by HMAC == tenant Shopify actually generated the webhook for`. Contrast this with `ShopifyAPI::Auth::Oauth::AuthQuery`, where `shop` **is** included in `to_signable_string` and therefore is bound by the HMAC: [5](#0-4) 

No such protection exists for the webhook path.

Because a public app uses a single `client_secret` shared across all installed shops, a low-privilege attacker who has legitimately installed the app on their own store will receive genuine webhooks whose HMAC is computed with that same shared secret and whose signed content is only the JSON body. The attacker can then replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while swapping the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header to point at a victim shop. `Utils::HmacValidator.validate` will still pass because it only checks the body, and `Registry.process` will hand the handler a `WebhookMetadata` whose `shop` field claims to be the victim, when in reality the payload never originated from or was ever intended for that shop.

### Impact Explanation
This is a cross-tenant identity-binding failure: the gem lets an unprivileged multi-tenant attacker (a merchant who has installed the same public app) forge the shop attribution of a cryptographically "valid" webhook. Any host application that uses `WebhookMetadata#shop` (as documented/intended) to scope database writes, trigger shop-specific side effects (e.g. `app/uninstalled`, `shop/redact`, order/customer data handlers), or determine which merchant's access token/session to use, will process attacker-controlled data under a victim shop's identity. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Moderate-to-high likelihood: obtaining a valid `(body, hmac)` pair requires only installing the target public app on an attacker-controlled store (or replaying any webhook they have legitimately received), which is available to any unprivileged internet user for public apps. Forging the `shop-domain` header on the replay is trivial since it's just an HTTP header with no additional server-side check tying it to the signature.

### Recommendation
Bind the tenant-identifying fields to the signature. Options:
- Include `shop`, `topic`, and `webhook_id` (or at minimum `shop`) in the signable string used for HMAC verification, mirroring what `AuthQuery#to_signable_string` does for OAuth.
- Alternatively, if Shopify's webhook signature intentionally covers only the body (per Shopify's documented HMAC scheme), the gem should not silently expose `request.shop`/`request.topic` as trusted, verified fields via `WebhookMetadata`; instead it should require host applications to additionally verify the shop against a known/installed-shop list before processing, and the gem's documentation/API should make this non-guarantee explicit rather than implying the value is authenticated by `Registry.process`.

### Proof of Concept
1. Attacker installs the target public app on `attacker.myshopify.com`, obtaining a legitimate webhook delivery with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
2. Attacker sends a POST to the app's webhook endpoint with the same body `B` and same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com` and any desired `x-shopify-topic`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(client_secret, B)` and matches `H` — validation succeeds because `to_signable_string` only inspects `B`. [6](#0-5) 
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the attacker-controlled `shop` header and invokes the registered handler with `shop: "victim.myshopify.com"`. [7](#0-6) 
5. The host application's handler, trusting `data.shop`, performs actions (data writes, deletions, triggering flows) as if the request genuinely originated from `victim.myshopify.com`, even though it did not.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
