### Title
`IntentGatewayV2.placeOrder` (Tron) escrows the requested amount instead of the actual amount received for fee-on-transfer tokens, causing escrow-ledger insolvency - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
In `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder`, when there is no predispatch call, tokens are pulled from the user with `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and the escrow ledger is credited with `reducedInputs[i].amount` — a value computed purely from the user-specified `order.inputs[i].amount` minus the protocol fee, with no check of the contract's actual token balance change. [1](#0-0) 

For any fee-on-transfer ERC20 used as an input asset, the gateway physically receives `amount - transferFee`, but records `reducedInputs[i].amount` (based on face-value `amount`) in `_orders[commitment][token]`. This is the exact root-cause pattern in the `wfCashERC4626` report: crediting a ledger with more than was actually received for a fee-on-transfer asset.

### Finding Description
The sibling implementation `evm/src/apps/IntentGatewayV2.sol::placeOrder` correctly guards against this by taking a balance snapshot before the transfer and using the actual balance delta to mutate `order.inputs[i].amount` before computing the commitment/escrow: [2](#0-1) 

The Tron variant, however, computes `reducedInputs` and the `commitment` hash *before* any tokens are transferred, using the caller-supplied `order.inputs[i].amount` directly: [3](#0-2) 

Then in the non-predispatch branch it performs the transfer and unconditionally increments escrow by the pre-computed `reducedInputs[i].amount`, without verifying the actual balance received:
```solidity
} else {
    IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
}
// Store reduced amount (after protocol fees) in escrow
_orders[commitment][token] += reducedInputs[i].amount;
``` [1](#0-0) 

If `token` charges a transfer fee, `address(this)` balance increases by less than `order.inputs[i].amount`, but `_orders[commitment][token]` is still incremented by the full (fee-adjusted-only-for-protocol-fee) amount. The escrow ledger entry no longer corresponds to actual funds held by the contract.

### Impact Explanation
This is the same class of bug as the `wfCashERC4626` finding: an accounting ledger (escrow map) is credited more than the contract actually custodies. As more orders using a fee-on-transfer input asset are placed, the aggregate escrowed amount recorded in `_orders` grows to exceed the contract's real token balance. When solvers fill orders and later redeem the escrow (via the `RedeemEscrow` incoming request path, or cancellation/refund paths that read `_orders[commitment][token]`), payouts computed from the inflated ledger value will eventually fail to be fully backed by the contract's real balance — later solvers/users are unable to redeem their full entitlement, i.e. a permanent, protocol-level insolvency/fund-freezing condition triggered by ordinary, unprivileged `placeOrder` calls with a fee-on-transfer ERC20 as input. This matches the "concrete... permanent freezing of funds" acceptance criterion, reachable by any unprivileged order-placer/token bridger.

### Likelihood Explanation
Likelihood depends on whether fee-on-transfer tokens are permitted/whitelisted as intent input assets on Tron deployments. Given `IntentGatewayV2` accepts an arbitrary ERC20 `token` address supplied in `order.inputs[i].token` with no allow-list check visible in the reviewed code, and the surrounding EVM codebase explicitly builds and tests for fee-on-transfer support (see `FeeOnTransferToken` test contract and `testPlaceOrder_FeeOnTransferToken_*` tests in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`), fee-on-transfer tokens are treated as a supported asset class for this app family. The Tron variant simply lacks the balance-delta safeguard that the main EVM variant already implements for exactly this scenario, making exploitation as simple as placing an order with any deflationary/fee-on-transfer token.

### Recommendation
Mirror the main EVM implementation's pattern in the Tron contract: snapshot `IERC20(token).balanceOf(address(this))` before `safeTransferFrom`, and after the transfer, use the actual balance delta as the "received" amount. Compute `reducedInputs`/protocol fees and the escrow commitment from that actual-received amount rather than from the caller-supplied `order.inputs[i].amount`, consistent with how `evm/src/apps/IntentGatewayV2.sol` (lines 291-329) already treats this for both the predispatch and non-predispatch paths.

### Proof of Concept
1. Admin/governance registers (or a user simply supplies) a deflationary ERC20 `FOT` with e.g. a 2% transfer fee as a valid input token for `IntentGatewayV2` (Tron).
2. User calls `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000e18}`, no predispatch.
3. `protocolFeeBps == 0` path: `reducedInputs[0].amount = 1000e18`, `commitment` computed with this value.
4. `IERC20(FOT).safeTransferFrom(msg.sender, address(this), 1000e18)` executes; contract's actual `FOT` balance only increases by `980e18` (2% fee retained by token).
5. `_orders[commitment][FOT] += 1000e18` — the ledger now claims 1000e18 escrowed while the contract holds only 980e18.
6. Repeat across multiple orders/users; the aggregate deficit accumulates as `sum(order.inputs.amount * feeRate)`.
7. When solvers fill orders and the corresponding `RedeemEscrow` request releases `_orders[commitment][FOT]` to the solver/beneficiary, the contract's real `FOT` balance is insufficient to honor all outstanding escrow entries — later redemptions revert or are only partially fulfilled, permanently freezing/loss of funds for the affected parties.
