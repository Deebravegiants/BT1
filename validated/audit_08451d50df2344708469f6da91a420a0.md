## Title
`CallDispatcher.dispatch()` has no caller authentication, letting anyone drain tokens left in the shared dispatcher after a cross-chain calldata delivery - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
The reported Mimo `SuperVault` bug is a "trusted callback with attacker-controlled state" pattern: `executeOperation()` only checks that `msg.sender == lendingPool`, but never verifies that *this specific* invocation corresponds to a flash-loan the vault itself requested, so anyone can drive the receiver's privileged internal logic with self-chosen parameters. The Hyperbridge analog is `CallDispatcher.dispatch()`, which has **no caller check whatsoever** (not even the `onlyHost`/`onlyApp` pattern used everywhere else in the codebase), while several `IApp` implementations can leave real token balances sitting in this same shared, singleton contract.

### Finding Description
`CallDispatcher.dispatch()` is `external` with zero access control: [1](#0-0) 

Any address, unprivileged, can call it directly at any time with an arbitrary ABI-encoded `Call[]`, and the calls execute *as the CallDispatcher itself* (`to.call{value: call.value}(call.data)`), i.e. against whatever balance the dispatcher happens to hold at that moment.

`HyperFungibleToken.onAccept` (and its upgradeable/wrapped variants) mint or unlock tokens to a recipient `to` and then execute attacker-... actually sender-supplied `message.data` through this same dispatcher, but — unlike `IntentGatewayV2`, which always sweeps residual dispatcher balances back to itself after `_execute()` — these token bridge callbacks perform **no sweep-back** step: [2](#0-1) [3](#0-2) 

The documented usage pattern explicitly directs integrators to mint tokens to the `CallDispatcher` address so that follow-up calldata (e.g. a DEX swap) can spend them: [4](#0-3) 

The docs themselves flag the risk of leftover balance, but only recommend "exact amounts" for approvals as mitigation — this does not address dust from slippage-bound swaps (e.g. `swapExactTokensForTokens` from the code example), rounding, partial fills on the target router, or a bug/oversight in the supplied `Call[]`: [5](#0-4) 

Because `CallDispatcher` is a single shared, cross-app singleton (per the "Existing `CallDispatcher` deployments are listed on the contract addresses page" note) and `dispatch()` performs no ownership/session accounting of "whose" balance it is holding, any tokens left behind by one relayed cross-chain message (through no fault other than normal slippage on a DEX call embedded in `message.data`) are immediately and permanently up for grabs by the first caller — attacker or otherwise — who invokes `dispatch()` with a `Call` that transfers the dispatcher's balance to themselves. This is functionally identical to the SuperVault flaw: a "receiver"-style contract executes attacker-chosen call data because it authenticates nothing about who may drive its execution or under what conditions.

### Impact Explanation
Any residual ERC-20/native balance left in the shared `CallDispatcher` — arising from normal, expected slippage or partial execution of a legitimate cross-chain transfer's attached calldata — can be permanently stolen by an unrelated third party monitoring the dispatcher's balance, since `dispatch()` has no authorization gate and the token bridge apps that route funds through it (`HyperFungibleToken`/`WrappedHyperFungibleToken`) do not sweep dust back. This is concrete theft of user funds routed through the token bridge's calldata-execution feature.

### Likelihood Explanation
Likelihood is high in practice: any user who uses the documented "swap on receive" pattern with slippage tolerance (a normal, encouraged usage per the docs) will routinely leave some dust in the shared dispatcher; because the dispatcher is a public, unauthenticated, and shared deployment across all apps and users, an attacker only needs to watch the dispatcher's token balances and race to call `dispatch()` — no proof forgery, consensus manipulation, or privileged role is required, matching the "unprivileged message dispatcher/relayer" reachability bar.

### Recommendation
Add access control to `CallDispatcher.dispatch()` so only the authorized caller for the in-flight operation may invoke it (e.g., a per-call, single-use authorization token/commitment set immediately before the call and cleared after, analogous to the `isFlash` boolean recommended for `SuperVault`), or deploy a fresh, ephemeral dispatcher instance per operation instead of a shared singleton. Additionally, have `HyperFungibleToken`/`WrappedHyperFungibleToken`'s `onAccept` sweep any residual balance from the dispatcher back to the intended beneficiary (mirroring `IntentGatewayV2._execute`'s dust-sweeping pattern) so no value can persist in the shared contract between transactions.

### Proof of Concept
1. Alice sends a cross-chain transfer via `HyperFungibleToken.send()`/`WrappedHyperFungibleToken.send()` with `to = CallDispatcher` and `data` encoding a DEX swap call with normal slippage protection (as shown in the docs' example).
2. On the destination chain, a relayer delivers the message; `onAccept` mints/unlocks Alice's tokens to the `CallDispatcher`, then calls `ICallDispatcher(_dispatcher).dispatch(message.data)`, which executes the swap. Due to slippage, the swap consumes slightly less than the full minted amount, leaving dust in the `CallDispatcher`.
3. Mallory, watching the `CallDispatcher`'s token balances, immediately calls `CallDispatcher.dispatch()` directly with a `Call[]` of `token.transfer(mallory, amount)`, since `dispatch()` performs no caller check.
4. Mallory receives Alice's leftover funds; there is no sweep-back mechanism to recover them and no way to identify or restrict the theft since `dispatch()` treats every caller identically.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.
