### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) header is trusted for tenant routing but is not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used to identify and route the webhook to a tenant's handler come from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then unconditionally trusts these header-derived values when constructing the `WebhookMetadata` passed to the app's handler.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read directly from HTTP headers with no cryptographic binding to the signed content: [2](#0-1) 

`Registry.process` validates the HMAC (over the body only) and then immediately forwards the unauthenticated header values, including `request.shop`, into `WebhookMetadata` that is handed to the app's business logic as the trusted tenant identifier: [3](#0-2) 

The identity binding broken here is: `shop authenticated (HMAC-covered bytes) != shop used as the tenant/session key (header value)`. Because the api_secret_key is shared across all shops that install a given app, any raw body + HMAC pair that is valid for the attacker's own shop (or any shop under the attacker's control, e.g. a partner development store) remains a byte-for-byte valid HMAC regardless of which `x-shopify-shop-domain` header value is sent alongside it — the header plays no role in the signature. An attacker who controls the delivery of at least one legitimately-HMAC-signed webhook (from their own store/app installation) can replay that same body+HMAC pair to the app's public webhook endpoint while substituting the `shop-domain` header for a victim tenant's domain. `Utils::HmacValidator.validate` will report the request as valid (since it only checks `verifiable_query.to_signable_string`, i.e., the body): [4](#0-3) 

and the app's handler will process attacker-controlled body content under the identity of a different tenant (`data.shop`), leading to cross-tenant data confusion.

### Impact Explanation
This breaks the tenant-authentication boundary the gem is expected to enforce for multi-tenant webhook processing: `data.shop` is documented and used by consumers of this library (see the `Webhooks::Registry` tests) as the authenticated identity of the shop the event pertains to, yet it is never covered by the signature check that is supposed to authenticate the message. This enables cross-tenant access/confusion — an attacker can cause the app to process attacker-supplied, validly-signed webhook content under a victim shop's identity.

### Likelihood Explanation
Exploitation requires only: (1) the attacker controls at least one shop where the target app is installed (or any store able to trigger a webhook of the target app, e.g. a free development/partner store — no privileged credentials on the app itself are required), and (2) the ability to relay/re-send that legitimately-received body+HMAC to the app's public webhook endpoint with a modified `x-shopify-shop-domain` header, which any unprivileged internet user able to send HTTP requests can do once they observe such traffic reaching their own environment/proxy.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header values in the signed/verified content, or otherwise cryptographically bind the reported shop to the request before trusting it (e.g., cross-check `shop` against an allow-list of shops with an active session/installation, or require the caller to separately verify shop identity via a mechanism not solely dependent on headers). At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be used as the sole tenant key.

### Proof of Concept
1. Attacker installs the target app on their own (attacker-controlled) shop, `attacker-shop.myshopify.com`, and triggers a webhook whose registered topic yields a body that does not itself strongly bind to the originating shop (many event bodies contain only resource IDs, not the shop domain).
2. Attacker captures the raw body and the corresponding `x-shopify-hmac-sha256` value delivered by Shopify to their own endpoint/proxy.
3. Attacker sends this exact `raw_body` + `x-shopify-hmac-sha256` to the target app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because it only hashes `raw_body`:
```ruby
# lib/shopify_api/utils/hmac_validator.rb
computed_signature = compute_signature(verifiable_query.to_signable_string, secret) # == HMAC(raw_body)
```
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)`, and the app processes attacker-controlled data as if it came from the victim shop.
