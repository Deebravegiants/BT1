## Analysis Result

### Title
Meta-transaction (`DelegateAction`) deposit refunds are routed to the delegating sender instead of the relayer who actually paid the attached balance - (File: `runtime/runtime/src/actions.rs`)

### Summary
NEAR's meta-transaction feature (NEP-366, `Action::Delegate`) lets a relayer pay all gas and token costs on behalf of a `sender_id` who signs the inner actions. This is structurally identical to the reported bug class: one account (the relayer / `msg.sender`-equivalent) funds a cross-boundary operation, while another account (`sender_id` / the token-owner-equivalent) is recorded as the "predecessor" of the resulting receipt. If that receipt fails, the balance refund goes to the recorded predecessor — the sender who signed, not the relayer who actually paid — exactly mirroring the reported "refund goes to token owner instead of fee payer" defect.

### Finding Description
When a `DelegateAction` is unwrapped on the sender's shard, `apply_delegate_action` builds a brand-new inner receipt that carries the delegated actions to the final receiver: [1](#0-0) 

This new receipt is constructed as a plain `ReceiptEnum::Action(ActionReceipt { .. })` (the V1 receipt variant), never as an `ActionReceiptV2`, and no `refund_to` is set. The `predecessor_id` of this receipt is set to `sender_id` (the account that signed the `DelegateAction`), even though the relayer is the one who actually purchased all attached gas and deposits, as the code comment itself states: [2](#0-1) 

If execution of this inner receipt on the receiver's shard fails (e.g. a `FunctionCall` with an attached deposit hits `non_existing_function`, insufficient gas, or a contract-level revert), the runtime generates a deposit refund. The refund target is computed via `balance_refund_receiver()`, which only honors an explicit `refund_to` on `ActionReceiptV2`; for plain `ActionReceipt` (V1, which is what `apply_delegate_action` always creates) it falls back to `predecessor_id`: [3](#0-2) 

and the actual refund-emission code in the runtime: [4](#0-3) 

Since `predecessor_id` for the inner receipt is `sender_id` (Alice), any failed-execution deposit refund is paid to Alice, even though the relayer funded the deposit. Although nearcore does have a generic mechanism to redirect refunds — the `refund_to` field on `ActionReceiptV2`, settable by a contract via the `promise_refund_to` host function (as exercised in `test_refund_to`) — `apply_delegate_action` never uses it to point refunds back at the relayer. [5](#0-4) 

nearcore's own architecture documentation explicitly acknowledges this exact effect and its financial-incentive risk: [6](#0-5) 

### Impact Explanation
A relayer that services meta-transactions with an attached deposit (e.g. funding a token transfer, storage deposit, or any `FunctionCall`/`Transfer` action requiring balance) bears the risk that, whenever the delegated action fails on the receiver's shard, the deposit is refunded to the delegating `sender_id`, not to the relayer who funded it. This is a genuine unauthorized balance transfer from the relayer to the sender: the sender receives tokens they never funded. As documented, this creates a direct financial incentive for a malicious signer to craft delegate actions with a high attached deposit that is engineered to fail on the receiver shard, extracting funds from the relayer.

### Likelihood Explanation
This requires no privileged access — any account can sign a `DelegateAction` with an attached deposit action designed to fail (e.g. targeting a nonexistent method, insufficient attached gas for a contract call, or a contract that reverts under certain conditions) and submit it to any relayer. The relayer only needs to be induced to accept and forward the meta-transaction, which is the intended, expected relayer workflow. The core team has documented awareness of this exact risk but places the burden of mitigation entirely on relayer implementations to "check" beforehand, rather than fixing it at the protocol/runtime level using the already-existing `refund_to` mechanism.

### Recommendation
When constructing the inner receipt in `apply_delegate_action`, emit an `ActionReceiptV2` (or equivalent) with `refund_to` explicitly set to the relayer (the outer receipt's `signer_id`), so any deposit-refund generated by a failed inner receipt routes back to whoever actually funded the deposit, consistent with how gas refunds already correctly return to the relayer via `signer_id`.

### Proof of Concept
1. Relayer R receives a `SignedDelegateAction` from sender S targeting receiver B, with an inner `FunctionCall` action attaching a deposit and calling a method engineered to fail (e.g., wrong method name or insufficient gas for `B`'s logic).
2. R wraps it into a transaction, signs it, and submits it; R pays for the attached deposit and gas as part of `verify_and_charge_transaction`.
3. `apply_delegate_action` runs on S's shard, creates the inner receipt with `predecessor_id = S`, `signer_id = R` — matching [7](#0-6) .
4. The inner receipt executes on B's shard and fails; `refund_unspent_gas_and_deposits` issues a `Receipt::new_balance_refund(receipt.balance_refund_receiver(), deposit_refund)`, which resolves to `predecessor_id = S` per [8](#0-7) .
5. S receives the deposit refund that R paid for, confirming the fund-misdirection.

```rust
    pub fn refund_to(&self) -> &Option<AccountId> {
        match self.receipt() {
            ReceiptEnum::Action(_)
            | ReceiptEnum::Data(_)
            | ReceiptEnum::PromiseYield(_)
            | ReceiptEnum::PromiseResume(_)
            | ReceiptEnum::GlobalContractDistribution(_) => &None,
            ReceiptEnum::ActionV2(action_receipt_v2)
            | ReceiptEnum::PromiseYieldV2(action_receipt_v2) => &action_receipt_v2.refund_to,
        }
    }

    pub fn balance_refund_receiver(&self) -> &AccountId {
        self.refund_to().as_ref().unwrap_or_else(|| self.predecessor_id())
    }
```

```markdown
## Balance refunds in meta transactions

Unlike gas refunds, the protocol sends balance refunds to the predecessor
(a.k.a. sender) of the receipt. This makes sense, as we deposit the attached
balance to the receiver, who has to explicitly reattach a new balance to new
receipts they might spawn.

In the world of meta transactions, this assumption is also challenged. If an
inner action requires an attached balance (for example a transfer action) then
this balance is taken from the relayer.

The relayer can see what the cost will be before submitting the meta transaction
and agrees to pay for it, so nothing wrong so far. But what if the transaction
fails execution on Bob's shard? At this point, the predecessor is `Alice` and
therefore she receives the token balance refunded, not the relayer. This is
something relayer implementations must be aware of since there is a financial
incentive for Alice to submit meta transactions that have high balances attached
but will fail on Bob's shard.
```
