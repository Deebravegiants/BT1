Audit Report

## Title
CORS Origin Allowlist Bypass via Improper Suffix Matching in Gateway HTTP Server - (File: core/services/gateway/network/httpserver.go)

## Summary
`isAllowedOrigin` in `core/services/gateway/network/httpserver.go` validates wildcard CORS allowlist entries (e.g. `*.remix.com`) using a raw `strings.HasSuffix(originHost, allowedHost)` check after stripping the `*.` prefix, without verifying that the matched suffix begins at a domain-label boundary. [1](#0-0)  This allows an attacker-registered domain such as `evilremix.com` to satisfy an allowlist entry of `*.remix.com`, since `strings.HasSuffix("evilremix.com", "remix.com")` returns `true` even though `evilremix.com` is not a subdomain of `remix.com`.

## Finding Description
The function loops over `s.config.CORSAllowedOrigins`, and for entries with a `*.` prefix strips it and performs a bare suffix comparison against the request's `Origin` header host: [2](#0-1)  There is no check that the character preceding the matched suffix is a `.`, so `originHost` merely needs to end with the same characters as `allowedHost`, not actually be a subdomain of it. This function is called directly from `handleRequest` using the unauthenticated, attacker-controlled `Origin` request header, and on a match, `Access-Control-Allow-Origin` is set to the attacker's own origin value: [3](#0-2)  No authentication, prior trust relationship, or privileged access is required to trigger this — it is a normal HTTP request with a crafted `Origin` header against the Gateway's user-facing HTTP endpoint. Existing exact-match and scheme/port checks do not mitigate this because they run before the flawed wildcard branch and don't affect it.

## Impact Explanation
An unauthenticated remote attacker who registers any domain sharing a trailing substring with an operator-configured wildcard entry (e.g. `notremix.com`, `evilremix.com` vs. `*.remix.com`) can have their origin treated as trusted by the Gateway's CORS policy. This is a concrete allowlist-bypass vulnerability that grants an attacker-controlled origin CORS access to the Gateway's user-facing API — falling into the "allowlist bypass" impact class for cross-origin trust boundaries. The severity is bounded by what CORS actually grants here: since `Access-Control-Allow-Credentials` is not set and the Gateway API's authorization is JWT/message-signature based (via the `Authorization` header) rather than cookie/session based, the practical impact is that a malicious webpage can make cross-origin JSON-RPC calls to the Gateway API on behalf of a visiting user's browser and read the response, but cannot exfiltrate cookies or session state absent additional context — this bounds impact below full account takeover but still represents a genuine, code-level security boundary violation. [3](#0-2) 

## Likelihood Explanation
Likelihood is realistic but conditional: it requires the operator to have configured at least one wildcard entry in `CORSAllowedOrigins`, a documented and supported feature exercised directly in the test suite. [4](#0-3)  Given that precondition, exploitation is trivial — attacker registers any domain ending in the allowlisted suffix and sends a request with a crafted `Origin` header, requiring no privileged access to Chainlink infrastructure.

## Recommendation
Change the wildcard comparison in `isAllowedOrigin` to require a domain-label boundary, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost) {
        return true
    }
}
```
This ensures `originHost` is either exactly `allowedHost` or a proper subdomain of it, closing the suffix-substring bypass.

## Proof of Concept
1. Start the Gateway HTTP server with `CORSEnabled: true` and `CORSAllowedOrigins: []string{"https://*.remix.com"}`, following the pattern in `startNewServer` in `core/services/gateway/network/httpserver_test.go`.
2. Send a `POST` request to the server's configured path with header `Origin: https://evilremix.com`.
3. Observe that the response contains `Access-Control-Allow-Origin: https://evilremix.com`, `Access-Control-Allow-Methods: GET, POST, OPTIONS`, and `Access-Control-Allow-Headers: Content-Type`, despite `evilremix.com` not being a subdomain of `remix.com`.
4. Add a Go unit test analogous to `TestHTTPServer_HandleRequest_CORSEnabled_FromNotAllowedOriginWildcards` in `core/services/gateway/network/httpserver_test.go`, asserting that an origin like `https://evilremix.com` against allowlist `https://*.remix.com` is currently (incorrectly) accepted, to lock in the regression once fixed.

func (s *httpServer) isAllowedOrigin(origin string) bool {
	originScheme, originHost, originPort, err := s.splitURL(origin)
	if err != nil {
		s.lggr.Debug("error parsing origin URL", err)
		return false
	}
	for _, allowed := range s.config.CORSAllowedOrigins {
		// probably better to do this once when server starts and store it in a map
		// this is an easier solution so we don't have to apply more changes to the code
		// just need to be careful when specifying allowed origins in the config file
		allowedScheme, allowedHost, allowedPort, err := s.splitURL(allowed)
		if err != nil {
			s.lggr.Debug("error parsing allowed origin URL", err)
			continue
		}
		// skip if the scheme doesn't match at all
		if originScheme != allowedScheme {
			continue
		}
		// skip if the port doesn't match at all
		if originPort != allowedPort {
			continue
		}
		// check for exact host match (e.g., remix.com)
		if originHost == allowedHost {
			return true
		}
		// check for wildcard host match (e.g., *.remix.com)
		if strings.HasPrefix(allowedHost, "*.") {
			allowedHost = allowedHost[2:]
			if strings.HasSuffix(originHost, allowedHost) {
				return true
			}
		}
	}
	return false
}
