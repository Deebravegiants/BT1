### Title
Potential missing G2 subgroup check in `alt_bn128_pairing_check` host function - (File: `runtime/near-vm-runner/src/logic/alt_bn128.rs`)

### Summary
The `alt_bn128_pairing_check` WASM host function, directly callable by any deployed smart contract, decodes G2 points via `decode_g2` which only validates that the point lies on the twist curve using `bn::AffineG2::new(x, y)`, without any explicit call verifying the point belongs to the correct prime-order (r) subgroup, mirroring the bug class reported for G2 points in `pairing_certificate.rs`.

### Finding Description
`decode_g2` in [1](#0-0)  constructs a `bn::G2` point solely through `bn::AffineG2::new(x, y)`, which validates that `(x, y)` satisfies the twist curve equation but performs no explicit `[r]P = O` subgroup-membership check in this code path. This point is then fed directly into `pairing_check`, which computes `bn::pairing_batch(&elements) == bn::Gt::one()` at [2](#0-1) . The doc comments on the exposed host function claim "If point coordinates are not on curve, point is not in the subgroup, ... the function returns `AltBn128InvalidInput`" at [3](#0-2) , but the actual decode path shown does not contain any explicit subgroup check call, only the on-curve construction. This function is wired up as a first-class WASM import reachable from any contract call at [4](#0-3)  and implemented identically in both the near-vm-runner logic and the wasmtime runner at [5](#0-4) .

This differs materially from the reported analog: in zksync-crypto the missing check was in witness-generation code, not enforced on-chain (subgroup checks were later confirmed to be enforced separately at the circuit level). In nearcore, `alt_bn128_pairing_check` **is** the on-chain, consensus-executed verification primitive itself — there is no separate circuit-level enforcement layer. Contracts (e.g. zk-SNARK verifiers, bridges, or rollup light clients built on NEAR) that rely on this host function to validate Groth16/BN254-style proofs would inherit any subgroup-check gap directly into their trust model.

### Impact Explanation
If the underlying `bn`/`zeropool-bn` crate's `AffineG2::new` truly performs only an on-curve check (as the local decode wrapper implies) without enforcing subgroup membership, an attacker could submit points on the curve but outside the intended order-r subgroup to a contract that uses `alt_bn128_pairing_check` to validate SNARK proofs, threshold signatures, or bridge attestations. This could allow forging proofs that satisfy the pairing equation without corresponding to a legitimate witness/statement, enabling unauthorized withdrawals, unauthorized state transitions, or bypass of access controls in any downstream verifier contract — i.e., concrete token theft or unauthorized state change, satisfying the "Accept" criteria.

### Likelihood Explanation
The `alt_bn128_pairing_check` host function is reachable from any account via a normal `FunctionCall` action to any contract that imports it, with no special privileges required. Exploitability, however, depends entirely on whether the `zeropool-bn` crate used here (`bn::AffineG2::new`) internally enforces subgroup membership as part of point construction — this could not be conclusively verified from the indexed nearcore repository alone, since the crate is an external dependency and its source is not part of the in-scope codebase. If the crate does perform the subgroup check internally, this specific call site would not be vulnerable and the doc comment claim would be accurate. Given this uncertainty, likelihood should be treated as unconfirmed pending verification of the crate's internal behavior.

### Recommendation
Explicitly verify whether `zeropool-bn`'s `AffineG2::new`/`AffineG2::from(G2)` construction enforces `[r]P = O` for G2 points. If it does not, add an explicit subgroup-membership check in `decode_g2` (`runtime/near-vm-runner/src/logic/alt_bn128.rs`) immediately after curve validation, before the point is used in `pairing_check`, mirroring the explicit `blst_p2_affine_in_g2` check already performed for BLS12-381 in [6](#0-5) .

### Proof of Concept
Not constructed — exploitation requires confirming the internal subgroup-enforcement behavior of the external `zeropool-bn` crate (`bn::AffineG2::new`), which is outside the indexed nearcore repository and could not be inspected here. A concrete PoC would require crafting a G2 point on the BN254 twist that is outside the prime-order subgroup, feeding it through `alt_bn128_pairing_check` from a test contract, and demonstrating that a forged pairing equation is accepted as valid.

pub(crate) fn pairing_check(
    elements: &[[u8; PAIRING_CHECK_ELEMENT_SIZE]],
) -> Result<bool, InvalidInput> {
    let elements: Vec<(bn::G1, bn::G2)> = elements
        .iter()
        .map(|chunk| {
            let (g1, g2) = stdx::split_array(chunk);
            let g1 = decode_g1(g1)?;
            let g2 = decode_g2(g2)?;
            Ok((g1, g2))
        })
        .collect::<Result<Vec<_>, InvalidInput>>()?;

    let res = bn::pairing_batch(&elements) == bn::Gt::one();

    Ok(res)
}

fn decode_g2(raw: &[u8; 2 * POINT_SIZE]) -> Result<bn::G2, InvalidInput> {
    let (x, y) = stdx::split_array(raw);
    let x = decode_fq2(x)?;
    let y = decode_fq2(y)?;
    if x.is_zero() && y.is_zero() {
        Ok(bn::G2::zero())
    } else {
        bn::AffineG2::new(x, y)
            .map_err(|_err| InvalidInput::new("invalid g2", raw))
            .map(bn::G2::from)
    }
}

pub fn alt_bn128_pairing_check(
    ctx: &mut Ctx,
    memory: &mut [u8],
    value_len: u64,
    value_ptr: u64,
) -> Result<u64> {
    ctx.result_state.gas_counter.pay_base(alt_bn128_pairing_check_base)?;
    let data = get_memory_or_register(
        &mut ctx.result_state.gas_counter,
        memory,
        &ctx.registers,
        value_ptr,
        value_len,
    )?;

    let elements = alt_bn128::split_elements(&data)?;
    ctx.result_state.gas_counter.pay_per(alt_bn128_pairing_check_element, elements.len() as u64)?;

    let res = alt_bn128::pairing_check(elements)?;

    Ok(res as u64)
}
