## Title
Webhook shop identity spoofing via HMAC that only covers the body, not the `shop-domain` header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw request body when computing/verifying the webhook HMAC, but the `shop` (tenant identity) is read from an unauthenticated HTTP header that is never included in the signed material. `Registry.process` trusts this unauthenticated `shop` value and hands it straight to the app's webhook handler as the tenant identifier, breaking the binding `hmac == sign(body ‖ shop)` that a correct implementation must enforce.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop` is parsed straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header with no cryptographic binding to the signature: [2](#0-1) 

`HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (i.e., the body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (the unauthenticated header) as the tenant identity passed to the app's handler: [4](#0-3) 

The equality the gem is supposed to guarantee is: `verify(hmac, secret) == true` implies `(body, shop)` as delivered to the handler is exactly what Shopify sent for that `shop`. In reality the gem only guarantees `verify(hmac, secret, body) == true`; `shop` is completely outside that proof. Because the same app secret signs webhooks for every shop installed on the app, and Shopify webhook payloads are frequently non-secret business data (order/product/customer JSON, which an attacker can obtain by installing the app themselves, or having a legitimate shop trigger events), an attacker who owns/controls one shop (shop A) can:
1. Cause a legitimate webhook to be generated for shop A (valid `body` + valid `hmac`, since the app secret is shared across shops of the same app).
2. Replay that exact `body`/`hmac` pair to the app's public webhook endpoint, but with the `shopify-shop-domain` header rewritten to shop B (the victim shop that also installed the app).
3. `HmacValidator.validate` succeeds because it only checks the body, and `Registry.process` builds `WebhookMetadata` with the attacker-controlled `shop: "shop-b.myshopify.com"`.

Any host application that follows this gem's documented pattern (verify HMAC via `Utils::HmacValidator`/`Registry.process`, then look up the session/tenant using `request.shop`) will process attacker-supplied data under a victim tenant's identity — a cross-tenant identity confusion entirely caused by this gem's `Request`/`HmacValidator` design, not by any host misuse.

### Impact Explanation
This breaks the tenant/authentication boundary that `shop` is supposed to represent, matching the Critical "cross-tenant access" category: attacker-controlled webhook content can be attributed to and processed under a shop the attacker doesn't operate, potentially triggering tenant-scoped side effects (e.g., data writes, notifications, billing events, or session/state updates keyed by `shop`) in host apps that rely on this gem's webhook verification as an integrity guarantee for the shop field.

### Likelihood Explanation
Exploitability requires only: (a) attacker access to a single legitimate install of the target app (trivial for public apps, including free/dev-store installs), and (b) the ability to POST directly to the app's public webhook endpoint with custom headers — both are unprivileged, internet-reachable actions requiring no access token, secret, or privileged account. The only nontrivial step is obtaining one valid `(body, hmac)` pair, which is provided for free by Shopify itself whenever any event fires for the attacker's own shop instance of the app.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the signed/verified material, or otherwise cryptographically bind them to the raw body before trusting `request.shop`, e.g. by changing `Request#to_signable_string` to incorporate the shop-domain header, or by validating that the header matches a shop already known to be associated with the delivered body/topic through an independent authenticated channel.

### Proof of Concept
1. App has two shops installed: `attacker-shop.myshopify.com` (attacker-owned) and `victim-shop.myshopify.com`.
2. Attacker triggers any subscribed webhook event on their own shop, capturing the raw POST body and the `x-shopify-hmac-sha256` header sent by Shopify (both are valid because the app's single `api_secret_key` signs webhooks for all its installed shops).
3. Attacker replays:
```
POST /webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <captured-valid-hmac>
x-shopify-shop-domain: victim-shop.myshopify.com
x-shopify-webhook-id: <any>

<captured-valid-body>
```
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)` [5](#0-4)  which passes because it only checks the body's HMAC.
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)` [6](#0-5) , causing the host app to process attacker-controlled data as if it originated from `victim-shop`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
