### Title
Webhook `shop-domain` header is not covered by HMAC verification, enabling cross-tenant webhook replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, while `shop`, `topic`, and `webhook_id` are read from separate, unauthenticated HTTP headers. `ShopifyAPI::Utils::HmacValidator.validate` in `ShopifyAPI::Webhooks::Registry.process` only checks the HMAC over the raw body, so the identity of the shop that "owns" a webhook is never bound to the cryptographic signature.

### Finding Description
`ShopifyAPI::Webhooks::Request` exposes `shop` from the `shopify-shop-domain`/`x-shopify-shop-domain` header [1](#0-0) , but the signable string used for HMAC verification is only the raw request body: [2](#0-1) .

`HmacValidator.validate` computes the signature strictly from `verifiable_query.to_signable_string` (the body) and the app's secret, and compares it to the `hmac` header [3](#0-2) . The `shop`, `topic`, and `webhook_id` header values are never included in the signed material.

`Registry.process` validates only the HMAC, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the `WebhookMetadata` that is dispatched to the app's handler: [4](#0-3) .

Because the shop identity that the handler acts on (`data.shop`) is taken from a header outside the cryptographic binding, the equality the code implicitly relies on — "the shop that signed this body == the shop named in `shop-domain`" — is never actually checked. Any party capable of obtaining one genuinely-signed webhook body/HMAC pair for the app (e.g., a merchant who has installed the app and thus legitimately receives webhooks for their own store) can resubmit that exact body+HMAC to the app's webhook endpoint while substituting a different `shop-domain` (and/or `topic`/`webhook-id`) header. `HmacValidator.validate` still succeeds because it never looks at those headers, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload belongs to a different shop than the one that actually produced it.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: a genuine payload from shop A can be replayed and attributed to shop B (or to a different topic than the one Shopify actually signed for), causing the host application's handler to perform shop-B-scoped side effects (e.g. updating records, triggering `shop/redact`-style compliance actions, or business logic keyed off `data.shop`) using attacker-controlled shop/topic values while still passing the library's HMAC check. This is cross-tenant data/action confusion driven entirely by a field excluded from the HMAC, matching the "field acted on but not covered by the HMAC" class.

### Likelihood Explanation
Requires only that the attacker have installed the app on at least one shop (unprivileged, self-service on Shopify) and be able to capture/replay one legitimate webhook body+HMAC pair to the app's public webhook endpoint. No access to `api_secret_key`, access tokens, or privileged accounts is needed — the attack path relies solely on this gem's `HmacValidator`/`Registry.process` logic accepting headers it never authenticates.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signed material verified by `HmacValidator`, or otherwise cryptographically bind them (e.g., derive/verify them from a signed claim rather than raw headers) so that `Registry.process` cannot dispatch a `WebhookMetadata` whose `shop`/`topic`/`webhook_id` were not covered by the HMAC that authenticated the body.

### Proof of Concept
1. App is installed on `shop-a.myshopify.com`; a legitimate Shopify webhook is delivered with body `B`, headers `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-topic: orders/create`, and a valid `x-shopify-hmac-sha256` computed over `B`.
2. Attacker (who owns `shop-a.myshopify.com` or intercepted the delivery) resends the exact same body `B` and HMAC header to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `shop-b.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into a request object; `Utils::HmacValidator.validate` succeeds because it only recomputes the HMAC over body `B`, ignoring the shop header [5](#0-4) .
4. `Registry.process` dispatches `WebhookMetadata.new(topic: ..., shop: "shop-b.myshopify.com", body: ..., ...)` to the registered handler, which now acts on shop B's tenant context using shop A's payload data [6](#0-5) .
