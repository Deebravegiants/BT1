### Title
Webhook shop-domain (tenant identity) header is not covered by HMAC validation, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then blindly trusts the `shop-domain` (and `topic`, `webhook_id`, `api_version`) HTTP headers to build the `WebhookMetadata` passed to the app's handler. Because those headers are not part of the signed material, an attacker who can obtain one valid `(body, hmac)` pair for their own shop can replay it to the same endpoint with an arbitrary `shop-domain` header and have it accepted as authentic for a different, victim tenant.

### Finding Description
`Registry.process` validates the webhook using `Utils::HmacValidator.validate(request)`: [4](#0-3) 

`HmacValidator.validate` computes and compares the HMAC exclusively against `verifiable_query.to_signable_string`: [5](#0-4) 

For `Webhooks::Request`, `to_signable_string` is defined as just the raw HTTP body, `@raw_body`: [2](#0-1) 

Meanwhile, `topic`, `shop`, `webhook_id`, and `api_version` — the fields that `Registry.process` uses to select the handler and populate `WebhookMetadata` — are read directly from client-supplied HTTP headers with no cryptographic binding to the HMAC: [3](#0-2) [6](#0-5) 

This breaks the identity binding the equality: `HMAC-verified(body)` should imply `shop == tenant-that-triggered-the-event`, but the gem only proves `HMAC(secret, body) == received`, and `shop` is taken from a completely separate, unauthenticated header. The gem's own documentation explicitly instructs the host application to treat `data.shop` as the trusted tenant identity for the webhook and to act on it (e.g., enqueue background jobs keyed by `shop_domain: data.shop`): [7](#0-6) 

Since a legitimate app receives real, Shopify-signed webhooks for every shop that installs it (including a shop the attacker themselves creates/controls), the attacker can capture a genuine `(raw_body, HMAC)` pair from their own shop's webhook delivery and resend the identical body and HMAC to the same public endpoint while swapping the `shop-domain` header (and, independently, `topic`) to a value denoting a different, victim shop. `HmacValidator.validate` still returns `true` because it never inspected the header, so `Registry.process` invokes the handler with attacker-controlled body content attributed to the victim's `shop` identity.

### Impact Explanation
This crosses a tenant boundary: an unprivileged internet user (an app installer on their own shop) can inject webhook events — with a payload of their choosing (any body they can get Shopify to sign, e.g. from their own store's real events) — that the host application attributes to an arbitrary other shop domain via `data.shop`. Any host logic that uses `data.shop` for tenant resolution (e.g., looking up the victim's session/access token, writing records into the victim's tenant data store, or triggering side effects "as" the victim) is exposed to cross-tenant data injection/corruption. This matches the "cross-tenant access" criterion for Critical impact.

### Likelihood Explanation
Exploitation requires only: (1) the attacker installs the app on their own shop (a normal, unprivileged action any Shopify merchant/developer can take), (2) they capture one legitimate webhook delivery (raw body + `X-Shopify-Hmac-Sha256`), and (3) they POST it back to the app's public webhook endpoint with a forged `shop-domain` header. No secrets, tokens, or privileged access are needed, and the app's endpoint is by design publicly reachable to accept Shopify's webhook deliveries.

### Recommendation
Bind the tenant-identifying header(s) into the signed material, or otherwise cross-check them against a value independently known to be authentic (for example, only accept `shop` values for shops with an active registration/session, and additionally verify the request originates from Shopify's documented IP ranges as defense in depth). At minimum, the gem should document prominently that `data.shop`/`data.topic` are not authenticated by the HMAC and must not be trusted for tenant routing without additional verification (such as confirming the shop already has a stored, valid session/webhook registration before acting on the payload).

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and registers for a webhook topic (e.g. `orders/create`).
2. Attacker triggers a real event on their own shop; Shopify delivers a webhook to the app's public endpoint with headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid HMAC over raw_body>`, and some `raw_body`.
3. Attacker captures this exact `raw_body` and `X-Shopify-Hmac-Sha256` value.
4. Attacker replays an HTTP POST to the same endpoint with the identical `raw_body` and `X-Shopify-Hmac-Sha256`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate(request)` returns `true` (it only checked `raw_body` against the HMAC) [8](#0-7) ; `Registry.process` calls the handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"` [9](#0-8) , causing the host app to act on attacker-controlled data as if it originated from the victim's shop.
