### Title
Consensus relayer rewards are silently lost when `StateMachinesCostPerBlock` is unset or removed mid-span, instead of being settled up to the cutoff - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`pallet-consensus-incentives::process_message` only computes and pays a reward, and only advances the `LastRewardedHeight` watermark, when `StateMachinesCostPerBlock::<T>::get(state_machine_id)` returns `Some`. Any block span a relayer advances while the map entry is absent (never configured, or removed via `remove_incentives`) is dropped forever: no reward is paid for it, and — critically — the watermark is not moved to reflect that the span has occurred, so the reward computation for that state machine is structurally identical to the analog vulnerability in the Concur `MasterChef.updatePool()` finding, where crossing an end condition (`block.number >= endBlock`) causes the function to update `lastRewardBlock` (or in this case, simply do nothing) without ever crediting the accrued difference.

### Finding Description
`process_message` is the sole entry point that both computes the relayer's `$BRIDGE` reward and mutates the `LastRewardedHeight` watermark used as the baseline for the next reward calculation:

```rust
fn process_message(...) -> Result<(), Error<T>> {
    if let Some(block_cost) = StateMachinesCostPerBlock::<T>::get(state_machine_id) {
        let reward = Self::calculate_reward(&state_machine_id, block_cost)?;
        ...
        LastRewardedHeight::<T>::mutate(state_machine_id, |watermark| {
            *watermark = Some(watermark.unwrap_or_default().max(state_machine_height.height));
        });
    }
    Ok(())
}
``` [1](#0-0) 

When `StateMachinesCostPerBlock` has no entry for a state machine — either because governance never called `update_cost_per_block`, or because it later called `remove_incentives` — the entire `if let Some(...)` body is skipped. Crucially, the watermark update is *inside* that same conditional, so `LastRewardedHeight` does not advance for any `StateMachineUpdated` event processed while the cost is unset:

```rust
pub fn remove_incentives(origin: OriginFor<T>, state_machine_id: StateMachineId) -> DispatchResult {
    T::IncentivesOrigin::ensure_origin(origin)?;
    StateMachinesCostPerBlock::<T>::remove(state_machine_id.clone());
    ...
}
``` [3](#0-2) 

`calculate_reward` always prices the reward as `(latest_height - baseline) * cost_per_block`, where `baseline` is `LastRewardedHeight` or, if unset, `previous_commitment_height` [4](#0-3) . Because the watermark freezes exactly when the cost is removed, the block span a relayer delivers between the last rewarded height and the point `remove_incentives` fires is never paid — the same "any rewards that it would normally be entitled to prior to reaching the cutoff will not be attributed" pattern the Concur report describes for `MasterChef.updatePool()`. Unlike Concur's `endBlock`, which is a fixed, known-in-advance parameter, `remove_incentives` is an unsigned, arbitrary-timing governance action, so the loss window is unbounded and unpredictable for the relayer who is mid-flight on a delivery.

### Impact Explanation
This is a loss-of-yield bug for an unprivileged consensus relayer: work already performed (advancing a state machine's proven height on Hyperbridge, which is required infrastructure for all downstream cross-chain messaging) goes permanently uncompensated for the span straddling the governance action, with no way to reclaim it since the watermark silently swallows the gap rather than recording it. The magnitude scales with how many blocks pass between the relayer's last rewarded submission and the incentive removal — potentially the relayer's entire unclaimed backlog for that chain. This matches the Medium severity the original Concur report received for the loss-of-yield characterization.

### Likelihood Explanation
Requires no attacker action — it triggers whenever governance calls `remove_incentives` (a normal, expected operational lever documented in the pallet's own README) at a moment when a relayer has already advanced a state machine's height past its last-rewarded checkpoint but has not yet submitted the reward-triggering update. Given rewards are only paid once per accepted `StateMachineUpdated` event and relayers race for first-submission, any timing overlap between an in-flight advance and a `remove_incentives` call reproduces the loss deterministically.

### Recommendation
Decouple the watermark update from the presence of `block_cost`. When `StateMachinesCostPerBlock` returns `None`, still advance `LastRewardedHeight` to the state machine's `latest_height` recorded at the time of removal (or record a "reward owed up to height X" entry priced at the last-known `cost_per_block` before removal) so no accrued span is discarded. Alternatively, capture and settle any outstanding, already-accrued reward for the last known `cost_per_block` at the moment `remove_incentives` executes, mirroring the mitigation Concur adopted: settle up to the cutoff before disabling further accrual.

### Proof of Concept
1. Governance calls `update_cost_per_block(state_machine_id, 100)`.
2. A relayer submits a consensus proof advancing `state_machine_id` from height 1000 → 1010; `on_executed` fires, `process_message` pays `10 * 100` and sets `LastRewardedHeight = 1010`.
3. Governance calls `remove_incentives(state_machine_id)` while the external chain has already progressed further (or is about to).
4. A relayer (possibly the same one, possibly a competitor) submits a consensus proof advancing the state machine from 1010 → 1030. `on_executed` fires `process_message`; `StateMachinesCostPerBlock::get` returns `None`, so the `if let Some(...)` body — including the reward transfer and the `LastRewardedHeight` mutation — never executes.
5. The 20-block span (1010 → 1030) is never priced, never paid, and `LastRewardedHeight` remains frozen at 1010. If governance re-enables the incentive later, the *next* relayer to submit any update sweeps the entire frozen backlog as a windfall unrelated to their own work, while the relayer who actually delivered blocks 1010→1030 receives nothing for it. 	/// Calculate the reward for a message based on the state machine id
	fn calculate_reward(
		state_machine_id: &StateMachineId,
		block_cost: <T as pallet_ismp::Config>::Balance,
	) -> Result<<T as pallet_ismp::Config>::Balance, Error<T>> {
		let host = <T::IsmpHost>::default();
		let latest_height = host
			.latest_commitment_height(state_machine_id.clone())
			.map_err(|_| Error::<T>::CouldNotGetStateMachineHeight)?;
		let previous_height =
			host.previous_commitment_height(state_machine_id.clone()).unwrap_or_default();

		// Use the rewarded watermark as the baseline and fall back to the previous height until
		// the first reward is recorded for this chain. The watermark only moves forward, so a
		// height that is rolled back and later resubmitted is not paid for a second time.
		let baseline = LastRewardedHeight::<T>::get(state_machine_id).unwrap_or(previous_height);

		let blocks = latest_height.saturating_sub(baseline);

		let blocks_as_balance: <T as pallet_ismp::Config>::Balance = blocks.saturated_into();
		let reward = blocks_as_balance.saturating_mul(block_cost);

		Ok(reward)
