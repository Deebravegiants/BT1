### Title
Webhook `shop-domain` and `topic` headers are excluded from HMAC verification, allowing cross-tenant webhook replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature validated by `Utils::HmacValidator.validate` in `Registry.process` authenticates the body bytes only. The `shop`, `topic`, `api_version`, and `webhook_id` values are read straight from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) with no cryptographic binding to that signature.

### Finding Description
In `lib/shopify_api/webhooks/request.rb`, `hmac` is computed over `shopify-hmac-sha256`, and `to_signable_string` returns `@raw_body` exclusively [4](#0-3) . The `shop`, `topic`, `api_version`, and `webhook_id` accessors simply read from `@headers`, which are attacker-controlled HTTP headers on the inbound request and are never included in the signable string [5](#0-4) .

`Registry.process` validates only `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` (i.e., body only) and compares it against the `hmac` header using `OpenSSL.secure_compare` [6](#0-5) . After that check passes, `Registry.process` dispatches to the handler using `request.topic` and `request.shop` taken directly from headers, with no further verification that those values match what was actually signed [3](#0-2) .

This breaks the intended identity binding: `signed_content == body_only`, but `dispatch_identity == (header_shop, header_topic)`. Any request whose body produces a valid HMAC for the app's secret (e.g., a legitimate webhook the requester received for their own shop/store) can have its `shop-domain` and `topic` headers rewritten to a different shop or topic while keeping the same body and HMAC, and the library will still accept it as valid and route it to the corresponding handler tagged with the attacker-chosen shop/topic in `WebhookMetadata`.

### Impact Explanation
This allows cross-tenant impersonation at the application layer that consumes this gem: a webhook payload legitimately delivered for shop A can be replayed with the `shop-domain` header (and/or `topic`) rewritten to shop B, and the gem will report it as an authentic, HMAC-verified webhook for shop B. Any host application that trusts `WebhookMetadata#shop`/`#topic` for tenant-scoped actions (e.g., data deletion on `shop/redact`, GDPR handlers, per-shop state updates) can be tricked into performing those actions against the wrong tenant, since the library provides no guarantee that the claimed shop/topic was part of the signed content.

### Likelihood Explanation
Exploitation requires only possession of one genuine webhook body+HMAC pair for any topic (attacker's own development store webhooks are sufficient, since same api_secret_key is used for all shops calling the app) and the ability to replay an HTTP POST with modified headers to the app's webhook endpoint. No access to `api_secret_key`, access tokens, or privileged accounts is needed — this is exploitable by any unprivileged party who can trigger or capture one webhook delivery for the target app and knows another shop's domain to target.

### Recommendation
Include the authenticated identity fields (at minimum `shop-domain` and `topic`) in the signable content used for HMAC verification, or otherwise cryptographically bind the header values to the signed body (e.g., verify that headers match values embedded in the signed body/payload) before dispatching to handlers in `Registry.process`.

### Proof of Concept
1. Attacker's app receives a legitimate webhook for their own shop `attacker.myshopify.com` with body `{}`, headers including `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: shop/redact`, and a valid `x-shopify-hmac-sha256` computed by Shopify over that body with the app's shared secret.
2. Attacker resends the identical body and HMAC header to the same webhook endpoint, but changes `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body normally [7](#0-6) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the (unchanged) body against the (unchanged) HMAC [8](#0-7) .
4. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` reporting `shop: "victim.myshopify.com"`, even though nothing about that value was ever signed [9](#0-8) .
