### Title
Multisig transaction payload substitution when full payload is stored on-chain and `abort_if_multisig_payload_mismatch` is disabled - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
`multisig_account::validate_multisig_transaction`, the VM-invoked prologue check that gates execution of a multisig-owned account's transaction, only verifies that the payload actually being executed matches the payload that owners voted on when a *feature flag* is enabled. When the flag is off (or on any deployment/network where it has not been activated), a transaction stored with its full payload on-chain (via `create_transaction`) has **no enforcement at all** that the payload submitted at execution time equals the payload that received quorum approval.

### Finding Description
Analogous to the external report's core defect — a protection check that is calculated/gated in a way that renders it non-functional against the very risk it is supposed to prevent — the multisig payload-match check here is conditionally skipped: [1](#0-0) 

```
// If the transaction payload is not stored on chain, verify that the provided payload matches the hashes stored
// on chain.
let multisig_account_resource = borrow_global<MultisigAccount>(multisig_account);
let transaction = multisig_account_resource.transactions.borrow(sequence_number);
if (transaction.payload_hash.is_some()) {
    let payload_hash = transaction.payload_hash.borrow();
    assert!(
        sha3_256(payload) == *payload_hash,
        error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH_HASH),
    );
};

// If the transaction payload is stored on chain and there is a provided payload,
// verify that the provided payload matches the stored payload.
if (features::abort_if_multisig_payload_mismatch_enabled()
    && transaction.payload.is_some()
    && !payload.is_empty()
) {
    let stored_payload = transaction.payload.borrow();
    assert!(
        payload == *stored_payload,
        error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH),
    );
}
```

When a transaction is created via `create_transaction` (full payload stored, `payload_hash = None`), the first branch (`transaction.payload_hash.is_some()`) never triggers, so the *only* guard against payload substitution is the second branch, and that branch is entirely gated behind `features::abort_if_multisig_payload_mismatch_enabled()`. If this feature is not active, the function performs quorum/timelock checks only and never compares `payload` (the bytes about to be executed by the VM) against `transaction.payload` (the bytes the owners actually reviewed and voted on): [2](#0-1) 

The quorum counting (`num_approvals_and_rejections`) and vote records (`Vote`) are all keyed to the `sequence_number`, not to the actual payload content, so once a sequence number's transaction has enough votes, any owner authorized to execute (any owner, not necessarily the original creator) can submit an arbitrary transaction payload as the "execution" of that sequence number, and it will pass validation as long as the feature flag is off.

This inverts the intended custody guarantee of the multisig scheme described in the module's own doc comment — that owners vote on a specific payload and execution requires that exact payload to have quorum support: [3](#0-2) 

### Impact Explanation
A multisig account is frequently used to custody APT, fungible assets, and object ownership (it is explicitly documented as being "a resource account underneath"). If the payload-match enforcement is not active, any single owner able to submit the execution transaction for an approved sequence number can redirect that authority to a completely different, unapproved operation — e.g., swap a payload that "transfers 1 APT to owner_2" for one that transfers the account's entire balance, changes the auth key, adds a malicious owner, or reassigns object/resource-account control to an attacker address. This is a direct custody/authority-control break: quorum-approved intent is not what gets executed, and the loss (theft or owner/control reassignment of the multisig-held assets) is irreversible once executed, satisfying the "Unauthorized takeover... of multisig control" and "moves value to the wrong holder" custody-gate criteria.

### Likelihood Explanation
Exploitability is entirely conditional on the `abort_if_multisig_payload_mismatch` feature flag's activation state, which I could not conclusively determine from the code inspected (default state and current mainnet governance status of this flag require confirmation via `move-stdlib/sources/configs/features.move`'s default-enabled feature set and any governance proposal history, which I did not fully verify before running out of investigation budget). If the flag is/was disabled by default or not yet activated on a given network, likelihood is high, because it only requires being any single owner authorized to trigger execution of a pending, already-quorate transaction sequence number. If the flag is enabled network-wide, this path is closed. This uncertainty should be explicitly resolved before treating this as confirmed-exploitable on current mainnet.

### Recommendation
Make the "on-chain full payload must match executed payload" check unconditional (remove the `features::abort_if_multisig_payload_mismatch_enabled()` gate) whenever `transaction.payload.is_some()`, rather than only enforcing it under a feature flag. If backward compatibility motivated the current gating (e.g., to tolerate empty payload placeholders), the check should still be structured so that mismatched non-empty payloads always abort, independent of feature-flag state, closing the same class of "protection computed but not actually enforced" gap identified in the referenced report.

### Proof of Concept
1. Create a multisig account with owners `A`, `B`, `C`, `num_signatures_required = 2`.
2. Owner `A` calls `create_transaction(A, multisig_addr, payload_transfer_1_APT_to_B)`, which stores the full payload on-chain and records `payload_hash = None`.
3. Owner `B` calls `approve_transaction`, reaching quorum (2 approvals: implicit from creator `A` + explicit from `B`).
4. On the network/build where `abort_if_multisig_payload_mismatch_enabled()` returns `false`, owner `A` (or any owner authorized to execute) submits a `MultisigTransaction` execution with a *different* payload, e.g. `payload_drain_all_APT_to_attacker`.
5. `validate_multisig_transaction` checks quorum (satisfied) and timelock (satisfied), skips the hash check (`payload_hash` is `None`), and skips the full-payload equality check because the feature flag is off — execution proceeds against the substituted payload, draining the multisig account's held APT instead of executing the 1-APT transfer that was actually approved.

    fun validate_multisig_transaction(
        owner: &signer, multisig_account: address, payload: vector<u8>) {
        assert_multisig_account_exists(multisig_account);
        assert_is_owner(owner, multisig_account);
        let sequence_number = last_resolved_sequence_number(multisig_account) + 1;
        assert_transaction_exists(multisig_account, sequence_number);

        if (features::multisig_v2_enhancement_feature_enabled()) {
            assert!(
                can_execute(address_of(owner), multisig_account, sequence_number),
                error::invalid_argument(ENOT_ENOUGH_APPROVALS),
            );
        }
        else {
            assert!(
                can_be_executed(multisig_account, sequence_number),
                error::invalid_argument(ENOT_ENOUGH_APPROVALS),
            );
        };

        // Count approvals, including the executing owner's implicit vote.
        let (num_approvals, _) = num_approvals_and_rejections(multisig_account, sequence_number);
        if (!has_voted_for_approval(multisig_account, sequence_number, address_of(owner))) {
            num_approvals += 1;
        };
        assert!(num_approvals >= num_signatures_required(multisig_account), error::invalid_argument(ENOT_ENOUGH_APPROVALS));

        // Timelock check — separate from quorum so the error is unambiguous.
        assert!(
            can_execute_with_timelock(multisig_account, sequence_number, num_approvals),
            error::invalid_state(ETIMELOCK_NOT_EXPIRED),
        );
