### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authenticated once the HMAC check passes, and then trusts the `shop` value taken from an HTTP header that is not part of the signed payload. Because the HMAC only covers the raw request body, any HMAC-valid webhook body can be replayed with an attacker-chosen `X-Shopify-Shop-Domain` header, breaking the binding "shop that generated/authorized this webhook == shop attributed to it by the gem."

### Finding Description
`ShopifyAPI::Webhooks::Request#hmac` returns the value from the `hmac-sha256` header, and `#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` fields are all read straight from headers and are never included in the signed string: [2](#0-1) 

`HmacValidator.validate` confirms only that `HMAC(secret, raw_body) == received_hmac`; it says nothing about which shop that body belongs to: [3](#0-2) 

`Registry.process` uses this validation result to gate execution, then immediately forwards the unauthenticated `request.shop`/`request.topic` values to the app's handler as trusted identity data: [4](#0-3) 

The gem's own documentation reinforces that developers are expected to treat a passed `process` call as proof the request "did indeed come from Shopify" for the shop in question, and to key downstream processing off `data.shop`: [5](#0-4) [6](#0-5) 

Because the app's `api_secret_key` is shared across all shops that install the app, an unprivileged attacker who installs the app on their own (attacker-controlled) shop can legitimately obtain HMAC-valid webhook deliveries for that shop. The attacker then replays the exact `raw_body` + `hmac-sha256` header to the victim app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` still passes (it never inspects the shop header), and `Registry.process` calls the handler with `shop: <victim-shop>` and attacker-controlled body content, i.e. cross-tenant data injected under someone else's identity.

### Impact Explanation
This breaks the identity binding "shop authenticated by HMAC == shop attributed to the resulting data," letting an attacker forge webhook events attributed to a shop they do not control. Depending on how the host app trusts `data.shop` (order sync, inventory updates, GDPR data-request routing, uninstall handling, etc.), this enables cross-tenant data corruption/injection into a victim merchant's records — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Any developer/user who can install the app on their own shop (common for public apps, free-trial or self-serve installs) can trivially capture one legitimate signed webhook and replay it with a modified shop header, since nothing in the gem enforces the shop-header/HMAC binding. No access token, secret, or privileged account of the victim is required.

### Recommendation
Bind the shop identity to the HMAC verification: either include the `shop-domain` (and ideally `topic`, `webhook_id`, `api_version`) header values in the signed string that is verified, or independently cross-check `request.shop` against an app-side record of shops that are expected to be sending webhooks for the given `webhook_id`/HMAC before dispatching to the handler.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`), receiving a POST with a valid `X-Shopify-Hmac-Sha256` header computed over the raw JSON body using the app's shared `api_secret_key`.
2. Attacker resends the identical `raw_body` and `hmac-sha256` value to the victim app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses the forged shop header; `Utils::HmacValidator.validate(request)` succeeds because it only checks `HMAC(secret, raw_body)`, per [7](#0-6) .
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: request.parsed_body, ...)`, causing the host app to process attacker-controlled data as if it originated from the victim shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
