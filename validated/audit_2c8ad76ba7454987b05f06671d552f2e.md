### Title
Webhook shop-domain spoofing via HMAC that only signs the body, not the shop header - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from `@raw_body` alone. The `shop` (tenant identity) is taken from an HTTP header that is completely outside the signed payload. Any actor holding one legitimately-signed webhook (raw_body + hmac pair, obtainable by installing the app on their own store) can replay that exact body/hmac pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header. `ShopifyAPI::Webhooks::Registry.process` will pass HMAC validation (the body/hmac pair is untouched and genuine) and will hand the forged shop value to the app's handler as if it were the origin store.

### Finding Description
- `Request#hmac` decodes the `hmac-sha256` header and `Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 
- `Request#shop` is read directly from `shopify-shop-domain`/`x-shopify-shop-domain` with no cross-check against the signed bytes: [2](#0-1) 
- `Utils::HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it to the received hmac — it never incorporates `shop`, `topic`, `webhook_id`, or `api_version`: [3](#0-2) 
- `Registry.process` relies solely on that HMAC check, then trusts `request.shop` and forwards it to the app's handler as the webhook's tenant identity: [4](#0-3) 
- The documented handler contract explicitly treats `data.shop` as the authoritative shop domain to key application-side jobs/records on: [5](#0-4) 

The broken identity binding is:
`HMAC-verified bytes (raw_body)` ≠ `shop identity acted upon (shopify-shop-domain header)`

Since the gem never binds the `shop` header into the HMAC computation, verifying the HMAC only proves "Shopify signed this exact body at some point for some shop" — it does not prove which shop the body belongs to. An attacker who has legitimately received (or can trigger, e.g. via their own store's webhook subscription) a genuine `(raw_body, hmac)` pair can resend it to the app's webhook endpoint with a different `shop-domain` header value, and `Registry.process` will accept it and dispatch it under the attacker-chosen shop identity.

### Impact Explanation
This is a cross-tenant identity confusion: the host application's webhook handler (per the gem's own documented pattern) uses `data.shop` to attribute incoming webhook payloads (orders, customers, inventory, GDPR redact requests, etc.) to a specific tenant's records/queues. An attacker who legitimately installs the app on their own store obtains valid `(raw_body, hmac)` pairs signed with the app's shared secret (this is Shopify's normal webhook delivery to the attacker's own callback endpoint — no `api_secret_key` leak required). Replaying that pair with a forged shop-domain header lets the attacker inject attacker-controlled webhook content attributed to an arbitrary victim shop domain into the host app, e.g., faking `customers/redact` or `orders/create` events for another tenant, corrupting per-tenant data pipelines, triggering wrongful data deletion/redaction, or polluting another merchant's records. This satisfies the "cross-tenant access" criterion.

### Likelihood Explanation
Moderate-to-high: the only prerequisite is the ability to install the app on any single shop (attacker's own store) to receive one valid signed webhook body — no secrets, tokens, or privileged access to the target shop are required. The header substitution is trivial (a normal HTTP replay with one header changed), and nothing in `Request`, `HmacValidator`, or `Registry.process` detects it.

### Recommendation
Include the shop-domain (and ideally topic/webhook-id) as part of the HMAC-covered signable string, or independently verify that the `shop` associated with the delivered webhook subscription matches the value in `x-shopify-shop-domain` before trusting it (e.g., cross-check against the shop that owns the webhook subscription via `webhook_id`, or bind these header values into `to_signable_string` used by `HmacValidator`). At minimum, document that `data.shop` from `Registry.process` is not cryptographically authenticated and host apps must independently verify tenant ownership before acting on it.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker.myshopify.com"
# and captures a genuine webhook delivery (body + valid hmac):
raw_body = '{"id":1,"note":"pwned"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_secret, raw_body) # captured from real Shopify delivery, secret unknown to attacker

headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),      # untouched, still valid
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged - not covered by HMAC
  "x-shopify-webhook-id" => "any-id",
  "x-shopify-api-version" => "2024-01",
}

# Sent to the app's webhook endpoint:
ShopifyAPI::Webhooks::Registry.process(
  ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
)
# HmacValidator.validate passes because to_signable_string == raw_body (unchanged).
# Handler receives data.shop == "victim-shop.myshopify.com" though the request never originated from that shop.

module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end

      sig { returns(String) }
      def topic
        T.cast(shopify_header("topic"), String)
      end

      sig { returns(String) }
      def shop
        T.cast(shopify_header("shop-domain"), String)
      end

      sig { returns(String) }
      def api_version
        T.cast(shopify_header("api-version"), String)
      end

      sig { returns(String) }
      def webhook_id
        T.cast(shopify_header("webhook-id"), String)
      end

      sig { override.returns(String) }
      def to_signable_string
        @raw_body
      end

      sig { returns(T::Hash[String, T.untyped]) }
      def parsed_body
        JSON.parse(@raw_body)
      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

      private

      sig { params(name: String).returns(T.untyped) }
      def shopify_header(name)
        @headers["shopify-#{name}"] || @headers["x-shopify-#{name}"]
      end
    end
  end
end

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook
