### Title
`validateStellarAddress` accepts any `G`-prefixed 56-char string without base32/CRC16 checksum verification, letting unrecoverable withdrawals be built to non-existent Stellar accounts - ([File: packages/intents-sdk/src/lib/validateAddress.ts])

### Summary
`validateStellarAddress` in `packages/intents-sdk/src/lib/validateAddress.ts` only checks a shape regex `/^G[A-Z0-9]{55}$/` and never decodes the base32 payload or verifies the CRC16-XModem checksum, unlike other address validators in the same file (Bitcoin, Tron, Litecoin, Dash all verify checksums) and unlike `stellarAddressToBytes` in `packages/internal-utils/src/utils/stellarAddressToBytes.ts`, which does perform proper base32 decode + CRC16 verification but is not used by `validateAddress`. Because `HotBridge.createWithdrawalIntents` forwards `args.withdrawalParams.destinationAddress` verbatim as `receiver` into `this.hotSdk.buildGaslessWithdrawIntent(...)`, a syntactically well-formed but checksum-invalid Stellar string that has no real underlying keypair can be validated as "true" and used to build a real withdrawal intent.

### Finding Description
The broken equality: `validateAddress(address, Chains.Stellar) === true` should imply "this string base32-decodes to a valid Stellar payload with a correct CRC16-XModem checksum, i.e., it corresponds to (or could correspond to) a real ed25519-keyed account ID," but the actual implementation only checks [1](#0-0) 

a bare regex on shape/charset. Every other checksum-bearing chain in this file (Bitcoin base58, Tron base58, Litecoin base58, Dash) explicitly decodes and verifies the checksum bytes, e.g. Bitcoin: [2](#0-1) 

and the repo even contains a correct Stellar CRC16 implementation in `stellarAddressToBytes`, which decodes base32, splits payload/checksum, recomputes CRC16-XModem, and throws on mismatch: [3](#0-2) 

but `validateStellarAddress` never calls it.

Exploit flow: an attacker (an ordinary user setting their own withdrawal destination, or a counterparty whose `destinationAddress` string an integrator forwards) supplies a 56-character string starting with `G` using only uppercase letters/digits, with arbitrary/garbage trailing bytes such that the base32 decode is not a valid checksum (i.e., it does not satisfy the CRC16-XModem check). This passes the regex and thus `validateAddress`, which is used by `HotBridge.validateWithdrawal`: [4](#0-3) 

and separately `HotBridge.createWithdrawalIntents` uses the same unchecksummed `destinationAddress` directly as `receiver` when calling the HOT SDK to build the actual withdrawal intent: [5](#0-4) 

Existing guards do not catch this: `validateAddress` itself is the weak link (format-only, as its own doc-comment states); `compareAddresses` only guards against the destination equaling the token contract address, not against checksum validity; and the only other Stellar-specific guard, the trustline check `this.hotSdk.stellar.isTrustlineExists(...)`, lives inside the third-party HOT SDK and is not part of this repo's validation path — its behavior on a checksum-invalid address is unverified and out of scope. Nothing in `createWithdrawalIntents` re-validates the address before submitting it to `buildGaslessWithdrawIntent`.

### Impact Explanation
If a checksum-invalid but shape-valid string is accepted, the SDK will construct and submit a real `mt_withdraw` intent (via `buildGaslessWithdrawIntent`) with `receiver` set to that garbage string. Since Stellar accounts must exist with a valid keypair, funds routed to such a "receiver" cannot be delivered to any real, recoverable account. This matches the Critical category: funds delivered to a wrong/non-existent address with no recovery path, and it is fully repeatable per call — any withdrawal request with a malformed-but-regex-passing Stellar address triggers this.

### Likelihood Explanation
Preconditions: the attacker only needs control over the `destinationAddress` string passed into a Stellar-route HOT bridge withdrawal — trivially available to any unprivileged SDK caller or any integrator who forwards an unvalidated user-supplied string. No special route/token state, no privileged access, and no cost beyond constructing a 56-character string matching `/^G[A-Z0-9]{55}$/` with an incorrect checksum (statistically likely for almost any string not deliberately checksummed, since checksum space is 1/65536 vs. 32^55 valid shapes). Highly feasible and repeatable.

### Recommendation
Rewrite `validateStellarAddress` to decode the address with base32 and verify the CRC16-XModem checksum (and version byte) rather than relying on a shape-only regex — e.g., reuse the existing `stellarAddressToBytes` (or equivalent) from `packages/internal-utils/src/utils/stellarAddressToBytes.ts`, returning `false` (catching the thrown error) instead of `true` for any address that fails to decode or fails the checksum.

// packages/intents-sdk/src/lib/validateAddress.spec.ts (new test)
import { validateAddress } from "./validateAddress";
import { Chains } from "./caip2";

test("accepts a shape-valid but checksum-invalid Stellar address", () => {
  // 56 chars total, starts with 'G', uses only [A-Z0-9], but the trailing
  // bytes do not satisfy CRC16-XModem when base32-decoded.
  const garbage = "G" + "A".repeat(55); // adjust so it fails stellarAddressToBytes()
  expect(validateAddress(garbage, Chains.Stellar)).toBe(true); // BROKEN: should be false
});

// packages/intents-sdk/src/bridges/hot-bridge/hot-bridge.test.ts (new test)
test("forwards unchecksummed Stellar address verbatim to buildGaslessWithdrawIntent", async () => {
  const garbage = "G" + "A".repeat(55);
  const buildGaslessWithdrawIntent = vi.fn().mockResolvedValue({
    amounts: ["1000"],
  });
  const bridge = new HotBridge({
    envConfig,
    hotSdk: { buildGaslessWithdrawIntent } as any,
  });

  await bridge.createWithdrawalIntents({
    withdrawalParams: {
      assetId: STELLAR_NEP245_ASSET_ID,
      destinationAddress: garbage,
      amount: 1000n,
    },
    feeEstimation: { amount: 0n, quote: null, underlyingFees: {} },
  });

  expect(buildGaslessWithdrawIntent).toHaveBeenCalledWith(
    expect.objectContaining({ receiver: garbage }),
  );
});
```
Both assertions demonstrate the broken equality: `validateAddress(garbage, Chains.Stellar) === true` while `garbage` has no valid underlying Stellar keypair, and the same unchecksummed string is what actually gets signed into the withdrawal intent via `receiver`.

function validateBtcBase58Address(address: string): boolean {
	const decoded: Uint8Array = base58.decode(address);

	// version (1) + hash160 (20) + checksum (4) = 25 bytes
	if (decoded.length !== 25) return false;

	const version = decoded[0];
	// 0x00 = P2PKH mainnet, 0x05 = P2SH mainnet
	if (version !== 0x00 && version !== 0x05) return false;

	const payload = decoded.subarray(0, 21);
	const checksum = decoded.subarray(21, 25);
	const expectedChecksum = sha256(sha256(payload)).subarray(0, 4);

	for (let i = 0; i < 4; i++) {
		if (checksum[i] !== expectedChecksum[i]) return false;
	}
	return true;
```

export function stellarAddressToBytes(encoded: string): Uint8Array {
	if (typeof encoded !== "string") {
		throw new TypeError("encoded argument must be of type String");
	}

	const decoded = base32.decode(encoded);
	const payload = decoded.slice(0, -2);
	const data = payload.slice(1);
	const checksum = decoded.slice(-2);

	if (encoded !== base32.encode(decoded)) {
		throw new Error("invalid encoded string");
	}

	const expectedChecksum = calculateChecksum(payload);

	if (!verifyChecksum(expectedChecksum, checksum)) {
		throw new Error("invalid checksum");
	}

	return new Uint8Array(data);
}
