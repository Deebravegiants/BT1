Confirmed: `message.from` is always exactly 20 bytes (`abi.encodePacked(msg.sender)`) as produced by the legitimate EVM-side `HyperFungibleToken`/`WrappedHyperFungibleToken` contracts. However, `pallet-hyper-fungible-token::on_accept` does not enforce that length — it trusts the ABI-decoded `Message.from` field verbatim regardless of source, and the panic path is reachable whenever the *source contract address itself* is attacker-controlled (i.e., anyone who can get `ContractToAsset`/the source-contract mapping to point at a contract they control, or any EVM-side app that reuses this `Message` ABI shape but doesn't fix `from` to 20 bytes) supplies a `from` field of length 0–19 while `source.is_evm()` and `message.data` decodes to `SubstrateCalldata{ signature: None, .. }`.

### Title
Panic via unchecked `message.from` length underflow in `pallet-hyper-fungible-token::on_accept` - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`on_accept` in `modules/pallets/hyper-fungible-token/src/module.rs` computes `&from_bytes[from_bytes.len() - 20..]` to derive the EVM sender address used for unsigned calldata dispatch, without validating that `from_bytes.len() >= 20`. Since `message.from` is an attacker-influenced ABI-decoded byte string (only implicitly constrained to 20 bytes by well-behaved EVM sender contracts, not by this pallet), a crafted `PostRequest` whose body decodes to a `Message` with a short `from` field causes `from_bytes.len() - 20` to underflow, panicking the runtime call — the same unchecked-length/NULL-style panic class as CVE-2024-32661 (FreeRDP `rdp_write_logon_info_v1`), just manifesting as a Rust arithmetic/slice-index panic instead of a NULL pointer dereference.

### Finding Description [1](#0-0) 

The relevant code path:
```
} else {
    let from_bytes = message.from.as_ref();
    if source.is_evm() {
        T::EvmToSubstrate::convert(H160::from_slice(
            &from_bytes[from_bytes.len() - 20..],

    } else { ... }

```
`message.from` comes straight from `Message::abi_decode(&body)` [2](#0-1)  — an ABI `bytes` field whose length is entirely attacker-chosen at the encoding layer. The only length check the pallet applies is on `message.to` (`to_bytes.len() == 32` or `== 20`, else a typed error) [3](#0-2) ; no equivalent check exists for `message.from`.

This branch executes when `message.data` is non-empty, decodes to a valid `SubstrateCalldata`, and `substrate_data.signature` is `None` [4](#0-3) . If `source.is_evm()` and `from_bytes.len() < 20`, `from_bytes.len() - 20` underflows `usize`, causing a debug-assert panic (`attempt to subtract with overflow`) or, in release mode, wraps to a huge value that still panics via out-of-bounds slice indexing. Either way the extrinsic call panics instead of returning a typed `DispatchError`.

Contrast this with the surrounding codebase's established defensive pattern for exactly this bug class — e.g. the `Signature::verify` length checks in `modules/utils/crypto/src/verification.rs` [5](#0-4) , the `as_utf8_string` deserializer fix explicitly citing a production panic from `copy_from_slice` on mismatched lengths [6](#0-5) , and the numerous BEEFY/Pharos/GRANDPA regression fixes for unchecked indices (`modules/consensus/beefy/verifier/src/lib.rs:229-236`, `modules/consensus/pharos/primitives/src/spv.rs` nibble/depth bounds, `modules/pallets/bandwidth/src/lib.rs:538-545`) — all of which replaced raw indexing/subtraction on attacker-controlled data with explicit length checks or `get`. This one call site in the HFT module was missed.

### Impact Explanation
A panic inside `on_accept`, invoked from pallet-ismp's dispatch of an inbound `PostRequest`, aborts the extrinsic executing message delivery. Depending on how the runtime's dispatch wraps module callbacks, this can deny message delivery for this and potentially co-batched requests, since ISMP module callback panics are not caught as ordinary `DispatchError`s the same way validated errors are — this is a "route unable to deliver messages" condition per the analog rules, reachable by an unprivileged relayer submitting a message once a malicious/compromised source contract (or any non-standard sender of this same wire format) produces a short `from` field. It does not by itself mint or steal funds, but it can be used to reliably deny/griefing-attack message delivery for the token module.

### Likelihood Explanation
Exploitability requires: (1) a registered source contract address (`ContractToAsset`) that emits `Message.from` shorter than 20 bytes — not possible from the canonical `HyperFungibleToken.sol`/`WrappedHyperFungibleToken.sol` contracts, which always encode `abi.encodePacked(msg.sender)` (exactly 20 bytes). This significantly limits likelihood: on the canonical, audited counterpart contracts this is unreachable in practice, since `from` is fixed by the EVM ABI encoding, not attacker-supplied independently of `msg.sender`. Exploitation would require either a non-standard/malicious counterpart contract being registered as a trusted source for some asset (which itself requires a privileged registration step, out of scope per the rules excluding malicious-admin/governance paths) or a bug elsewhere that lets `from` diverge from `msg.sender`'s 20 bytes. Given the current search, I could not find a reachable path where an ordinary unprivileged actor controls `message.from`'s length independent of a trusted, already-registered source contract.

### Recommendation
Add an explicit length check on `from_bytes` (require `== 20` when `source.is_evm()`, else return a typed `HftError` such as `InvalidSenderLength`) before the subtraction, mirroring the existing `to_bytes` length validation, to eliminate the underflow/panic entirely regardless of what any current or future source contract encodes.

### Proof of Concept
Not fully constructible as a standalone unprivileged PoC: it requires a registered EVM source contract (via `ContractToAsset`) that encodes `Message.from` with fewer than 20 bytes, which the standard, audited `HyperFungibleToken.sol`/`WrappedHyperFungibleToken.sol` contracts never do (they use `abi.encodePacked(msg.sender)`, always 20 bytes). Conceptually:
1. Register (via normal, non-privileged asset/contract registration flow if one allows arbitrary third-party contracts as sources) or otherwise get a contract whose `send()`-equivalent encodes `Message{ from: <bytes of length < 20>, to: <valid>, amount: X, data: SubstrateCalldata{ signature: None, runtime_call: <any> }.encode() }`.
2. Relay this as a `PostRequest` with `source` set to that EVM chain.
3. Call `on_accept` (via normal ISMP relay/dispatch) — `from_bytes.len() - 20` underflows and panics.

Given the inability to independently confirm an unprivileged, standard-contract-only path that supplies a `from` field shorter than 20 bytes, this finding's real-world severity is uncertain and likely Low/Medium rather than a clean High/Critical "message dispatcher" bug — I flag this uncertainty explicitly rather than overstating confidence.
