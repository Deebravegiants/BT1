Confirmed: `ExtrinsicIntents` (used by `IntentGatewayV2`, both same-chain and Tron variants) does not override `onPostRequestTimeout` — `HyperApp.onPostRequestTimeout` reverts by default [1](#0-0) . This confirms the analog: `_cancelFromDest` irreversibly writes `_filled[commitment]` before the cross-chain refund message is guaranteed to be delivered, exactly mirroring the `isReadyForPayout`-before-`updateDistribution` bug class.

### Title
Destination-side order cancellation permanently locks source-chain escrow if the RefundEscrow POST request times out - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`_cancelFromDest` marks `_filled[commitment] = order.user` on the destination chain and then dispatches a `RefundEscrow` message to the source chain, but the gateway never implements `onPostRequestTimeout`, so if the dispatched message is never delivered and times out, there is no path to retry the refund or unlock the source-chain escrow.

### Finding Description
`_cancelFromDest` sets the terminal `_filled` state before the cross-chain message that actually moves funds is confirmed delivered: [2](#0-1) 

This is the same ordering flaw as the external report: an irrevocable "done" flag (`_filled[commitment]`, analogous to `isReadyForPayout`) is set on the destination chain before the corresponding action (the source-chain refund, analogous to `updateDistribution`) is guaranteed to complete. `cancelOrder` on either chain reverts for any commitment once `_filled[commitment] != address(0)`: [3](#0-2) 

So once `_cancelFromDest` executes, the destination gateway can never re-dispatch a fresh `RefundEscrow` for that order — the one dispatch that already happened is the only chance to unlock the source-chain escrow.

If that `PostRequest` never gets delivered before its timeout (e.g., relayer congestion, fee too low, destination liveness issue on Hyperbridge, or challenge-period/consensus delay), a relayer or user must submit a timeout message to the *source* chain's host, which calls `dispatchTimeOut` → `onPostRequestTimeout` on the sending app (here, the destination-chain `ExtrinsicIntents` instance) to notify it and refund the relayer fee: [4](#0-3) 

But `ExtrinsicIntents` (and by extension `IntentGatewayV2`) never overrides `onPostRequestTimeout`; it inherits `HyperApp`'s default which unconditionally reverts: [1](#0-0) 

A reverting callback also means the host does not delete the request commitment, so the timeout can be resubmitted forever, but it will always revert — there is no code path in `ExtrinsicIntents` that resets `_filled[commitment]` back to `address(0)` to allow retrying the refund dispatch. Meanwhile the escrowed input tokens sit untouched on the source chain (`_orders[commitment][token]` is unchanged — the source chain never received and processed a `RefundEscrow` or `RedeemEscrow` message), and the destination-side `_filled` marker forever blocks any further cancellation attempt for that commitment.

### Impact Explanation
Once a `_cancelFromDest` dispatch times out, the user's escrowed input tokens on the source chain become permanently unrecoverable: `_filled[commitment]` is already non-zero so `cancelOrder` reverts with `Filled()` on any chain for that commitment, and there is no `onPostRequestTimeout` handling to reset destination state or otherwise recreate the refund path. This is a permanent freezing-of-funds condition reachable by a single unprivileged user action (calling `cancelOrder` from the destination chain) combined with ordinary message-delivery failure/timeout, which is a normal, expected occurrence in the ISMP messaging model (the whole reason timeouts and `onPostRequestTimeout` exist).

### Likelihood Explanation
POST request timeouts are a first-class, documented part of ISMP's design (network congestion, insufficient relayer fees, destination liveness, or execution failures are explicitly called out as causes) [5](#0-4) , so this is not a rare edge case — it is a routine failure mode the protocol otherwise handles via `onPostRequestTimeout`. Any user cancelling from the destination chain, or a relayer under-quoting the relayer fee, or a race where Hyperbridge/destination liveness stalls past `order` semantics, can trigger this outcome.

### Recommendation
Implement `onPostRequestTimeout` in `ExtrinsicIntents`/`IntentGatewayV2` for the `RefundEscrow`/`RedeemEscrow` dispatch paths, decoding the original `WithdrawalRequest` from the timed-out request body and resetting `_filled[commitment]` to `address(0)` (mirroring the pattern already used in `WrappedHyperFungibleToken`/`HyperFungibleToken`, which correctly refund on timeout) so that a fresh cancellation/refund dispatch can be retried. Alternatively, require that the underlying dispatch succeed and be delivered (or add an explicit recovery/retry function gated on proof of timeout) before permanently marking `_filled`.

### Proof of Concept
1. User calls `cancelOrder(order, options)` on the destination chain after `order.deadline`, routing to `_cancelFromDest`.
2. `_filled[commitment] = order.user` is set, and a `RefundEscrow` `DispatchPost` is sent via `_post` (see `evm/src/apps/intentsv2/ExtrinsicIntents.sol:297-307`).
3. The relayer fee is insufficient, or Hyperbridge/destination liveness stalls, and the request's `timeout_timestamp` passes without delivery to the source chain.
4. A relayer submits the timeout proof to the destination chain's `EvmHost`, which calls `dispatchTimeOut` → `onPostRequestTimeout` on the destination `ExtrinsicIntents` instance (`evm/src/core/EvmHost.sol:885-906`).
5. `onPostRequestTimeout` is unimplemented and reverts (`HyperApp.onPostRequestTimeout`, `sdk/packages/core/contracts/apps/HyperApp.sol:138-140`); the transaction reverts every time it is retried.
6. `_filled[commitment]` remains permanently `order.user` on the destination chain; no further `cancelOrder` call for this commitment can succeed (`Filled()` revert), and the escrowed input tokens on the source chain (`_orders[commitment][token]`) are never released — funds are permanently frozen.

    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
        }

        _filled[commitment] = address(uint160(uint256(order.user)));

        _post(
            order, _body(RequestKind.RefundEscrow, commitment, order.inputs, order.user), options.relayerFee, msg.value
        );
    }

    function dispatchTimeOut(
        PostRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onPostRequestTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit PostRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }
