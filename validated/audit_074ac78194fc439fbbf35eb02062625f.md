### Title
Unsigned Emporium stateless relay lets attacker pull victim's ERC20 allowance via `DepositOnChainUtxosExternalAction.runAction` - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction` allows the *outer* transactor to embed an arbitrary `EmporiumOperation.callData` blob in `circomData.externalActionData.externalActionMetadata` and, when `EmporiumStack.signerAddress == address(0)`, executes it with **zero signature verification** via `op.endpoint.call(op.callData)`. If the target is `DepositOnChainUtxosExternalAction`, that contract blindly trusts the caller-supplied `circomData.originalSender` field as the account to pull tokens `from`, with no cryptographic or ZK-circuit binding between that field and the real prover. This lets an attacker with only the `isAllowedRecipient[Emporium]==true` config and a pre-existing victim ERC20 allowance to Emporium steal the victim's tokens.

### Finding Description
The broken equality: `DepositOnChainUtxosExternalAction.runAction`'s `userAddress = circomData.originalSender` must equal the account that produced the outer ZK proof for `Hinkal.transact`, but nothing enforces this for the *nested* `circomData` value.

Path:
1. Attacker calls `Hinkal.transact` with an outer `circomData` whose `externalActionId` resolves to `EmporiumUpgradeable` and `erc20TokenAddresses.length == 0` (the "Emporium Min" circuit path). `performHinkalChecks` only validates the **outer** `circomData.originalSender == msg.sender` (attacker) [1](#0-0) , and `getHashedCalldata`/`calldataHash` merely commits `externalActionData` (including the whole crafted metadata blob) as an opaque hash the attacker freely picks off-chain [2](#0-1)  — it does not constrain the semantic content of any nested `circomData.originalSender`.
2. Because `erc20TokenAddresses.length == 0`, `Hinkal.transact`'s balance/slippage loop over `circomData.erc20TokenAddresses` never executes, so no outer-level accounting catches the token movement performed deep inside Emporium [3](#0-2) .
3. `EmporiumUpgradeable.runAction` decodes the attacker-controlled `EmporiumStack` and, since `stack.signerAddress == address(0)`, `verifyWallet` returns immediately after marking `usedMessages` — no ECDSA check is performed at all [4](#0-3) .
4. The loop then falls into the "Stateless Interaction" branch and does `op.endpoint.call{value: op.value}(op.callData)` with attacker-chosen `callData` [5](#0-4) .
5. If `op.endpoint == DepositOnChainUtxosExternalAction` and `isAllowedRecipient[Emporium] == true`, the `onlyAllowedRecipient` modifier passes because it only checks `msg.sender` (Emporium) against the allow-list, not any relation to the fabricated `circomData` [6](#0-5) .
6. Inside `DepositOnChainUtxosExternalAction.runAction`, `userAddress = circomData.originalSender` is taken directly from the attacker-fabricated struct and used as the `from` of `transferERC20TokenFrom(tokenAddress, userAddress, msg.sender, tokenTotal)` [7](#0-6) . If `originalSender` is set to the victim and the victim has an ERC20 allowance to Emporium, `safeTransferFrom(victim, Emporium, amount)` succeeds without any signature, proof, or check that the victim authorized this specific call.
7. Back in `EmporiumUpgradeable.runAction`, the resulting balance increase on Emporium is converted into an output UTXO addressed to the attacker's `circomData.stealthAddressStructure` and transferred to `msg.sender` (attacker) via `handleOut` [8](#0-7) .

None of the existing guards catch this: `verifyProof`/`calldataHash` only bind the attacker's own chosen bytes (they don't constrain semantic content), `dimensionsCheck`/`checkOnchainCreation` operate on the outer circomData's `erc20TokenAddresses`/`onChainCreation` arrays which are empty here, and `onlyAllowedRecipient` on both `EmporiumUpgradeable` and `DepositOnChainUtxosExternalAction` only checks the immediate caller's identity, never the `originalSender` field's provenance.

### Impact Explanation
Direct theft of a victim's ERC20 tokens they approved to the Emporium contract, with the tokens routed to the attacker's own stealth address/output UTXO — a call the victim never authorized (no signature, no proof, no interaction). This is Critical: direct theft of user funds and execution of a transfer the wallet owner never authorized, exploitable repeatably against any victim with a standing Emporium allowance, for as long as `isAllowedRecipient[Emporium]` remains true on `DepositOnChainUtxosExternalAction`.

### Likelihood Explanation
Preconditions per the question (both accepted as given environment state): `DepositOnChainUtxosExternalAction._isAllowedRecipient[Emporium] == true` and a victim ERC20 allowance to Emporium. Both are plausible real deployment states, since Emporium is designed specifically to orchestrate stateless calls into other allow-listed external actions, and users are expected to approve Emporium for various flows. Attacker cost is a single `Hinkal.transact` call with a self-generated proof over their own UTXO (feasible since the Emporium-min circuit's public inputs are just `emporiumMessage`, `timeStamp`, `calldataHash`, none of which constrain the victim's identity). Repeatable per victim allowance.

### Recommendation
`DepositOnChainUtxosExternalAction.runAction` (and any external action reachable through Emporium's stateless branch) must not trust a caller-supplied `originalSender`/`from` field for token pulls unless it is cryptographically bound to the real depositor — either require `msg.sender` == the account paying, or require `EmporiumStack.signerAddress` to be non-zero and signature-verified whenever an op could move a third party's funds, and reject `signerAddress == address(0)` for any operation whose `callData` targets a function performing `transferFrom` on an address other than the immediate proof owner. Additionally, bind `circomData.originalSender` inside nested/forwarded action calldata to the outer proof's verified identity.

### Proof of Concept
Foundry fork test:
1. Deploy/point at real `Hinkal`, `EmporiumUpgradeable`, `DepositOnChainUtxosExternalAction`; set `isAllowedRecipient[Emporium] = true` on `DepositOnChainUtxosExternalAction`.
2. `victim` approves `Emporium` for `amount` of a test ERC20, never calls `transact`/`prooflessDeposit`.
3. Attacker builds `fabricatedCircomData` with `originalSender = victim`, `erc20TokenAddresses = [token]`, matching `externalActionData.externalActionMetadata = abi.encode(uint256[][]{[amount]})`; encodes `op.callData = abi.encodeCall(DepositOnChainUtxosExternalAction.runAction, (fabricatedCircomData, [int256(0)]))`.
4. Attacker builds outer `circomData` with `erc20TokenAddresses.length == 0`, `externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionData.externalActionMetadata = abi.encode(EmporiumStack{signerAddress: address(0), ops: [op], ...})`, generates a valid proof for their own dummy UTXO/emporiumMessage.
5. Attacker calls `Hinkal.transact(a,b,c,dimensions,circomData)`.
6. Assert `token.balanceOf(victim)` decreased by `amount`, `token.transferFrom(victim, Emporium, amount)` executed, and the resulting `utxoOut.stealthAddressStructure == attacker`'s structure — while `victim` never called `transact` or `prooflessDeposit` and never signed anything.
