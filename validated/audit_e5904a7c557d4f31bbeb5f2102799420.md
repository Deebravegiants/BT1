### Title
Zero-cost self-relay of oversized ISMP messages can JIT-inflate Reputation Asset to steal Collator seats and treasury block rewards - (File: `modules/pallets/messaging-incentives/src/lib.rs`)

### Summary
`pallet-messaging-incentives` mints `ReputationAsset` to whoever's signature is recovered as the delivering relayer on every executed ISMP message, scaled purely by `max(body_size, 32) × MintPerByte` [1](#0-0) , with no fee, cost, or usefulness check on the message itself, and `pallet-collator-manager::new_session` ranks collator candidates purely by their controller's Reputation Asset balance snapshotted at the session boundary, before burning it back to zero [2](#0-1) . Since a POST/GET dispatch's only mandatory cost is an optional relayer fee (`fee: 0` is explicitly permitted for self-relay) [3](#0-2) , and the per-byte protocol fee on `EvmHost` has been removed [4](#0-3) , an unprivileged actor can self-dispatch and self-relay large zero-fee messages to inflate their Reputation Asset balance just-in-time before a session boundary, exactly analogous to the JIT-liquidity pattern in the referenced report: cheaply and momentarily inflate a metric that determines an outsized share of a reward, capture it at the measurement instant, and repeat every cycle since the position resets to zero afterward at no cost.

### Finding Description
The reward-determining "position" here is the Reputation Asset balance, and the "snapshot" is `pallet-collator-manager::new_session`, called every session boundary via `SessionManager::new_session` [5](#0-4) . Candidates are ranked strictly by `T::ReputationAsset::balance(&controller_account)` with no time-weighting, no minimum holding period, and no decay [6](#0-5) . Immediately after selection, the full reputation balance of every account in the new set is burned to zero [7](#0-6) , so the "position" only needs to exist for the instant of the snapshot — this mirrors the tight-range LP position that only needs to exist for the instant a reward is measured before being burned/rebalanced.

Reputation is minted in `pallet-messaging-incentives::on_executed`, called on every executed ISMP message batch, proportional to `bytes = max(body_size, 32)` × `MintPerByte`, with the relayer recovered purely from the message's `signer` field [1](#0-0) . There is no requirement that the message be economically meaningful, carry a non-zero fee, or be delivered to an unrelated third party — an attacker can dispatch a POST request with a large body from a source chain to a destination they also control (or even to any accepting module), sign the delivery message themselves, and collect reputation proportional to bytes at essentially only gas cost (no mandatory relayer fee, and the per-byte protocol fee has been explicitly removed from `EvmHost`) [4](#0-3) . `MintPerByte` is a flat governance-set rate with no per-account cap, no rate limiting, and no dedup across messages (unlike the BEEFY prover's per-account, per-height dedup) [8](#0-7) .

By contrast, every other reward-bearing mechanism in Hyperbridge ties payment to a genuinely scarce, race-won, or fee-paid action: BEEFY proof rewards are deduplicated per account per finality target [9](#0-8) ; consensus relaying only pays the first submitter for a given state update [10](#0-9) ; outbound request/consensus delivery rewards are keyed by commitment and claimed exactly once [11](#0-10) . Messaging-incentives reputation is uniquely unbounded by real scarcity — it scales only with self-controllable byte count.

### Impact Explanation
Winning a Collator seat grants block-production rewards (`0.7 $BRIDGE` per authored block, ~4,000,000 $BRIDGE/year pool) [12](#0-11)  plus network-level trust (fisherman veto authority, block inclusion). An attacker who cheaply inflates Reputation right before a session boundary can displace legitimate operators for that session, extracting treasury-funded block rewards without performing the genuine cross-chain relaying/proving work reputation is meant to measure. Because reputation is burned every session regardless of outcome [7](#0-6) , the attacker has zero ongoing carrying cost and can repeat the JIT-mint before every subsequent session — directly paralleling the "rinse and repeat, no funds at risk" mechanic in the referenced report. This is Medium-to-High severity: it does not directly mint or steal escrowed user/bridge funds, but it does misappropriate treasury-funded collator rewards and can displace genuine, reputation-earning operators, degrading decentralization and potentially seating a validator who has not proven real, useful relaying capacity (weakening the fisherman fraud-detection layer collators are also responsible for).

### Likelihood Explanation
Requires only an unprivileged actor able to dispatch and self-relay ISMP messages between two chains they control (or into any module that accepts arbitrary bodies), with `MintPerByte` set to a non-zero governance rate — which is the default expected production configuration since the pallet exists specifically to reward relayers. No special access, staking, or approval is needed to dispatch messages or to sign a delivery as the recovered relayer [13](#0-12) . The main friction is gas cost for the message payload size and Bandwidth-Gate metering if the source chain's app is bandwidth-metered rather than allowlisted; however, self-controlled cheap chains/messages and the option to size the body just above the 32-byte floor threshold at scale still make repeated exploitation economically favorable relative to the size of the collator reward captured.

### Recommendation
Do not let a single-block/session snapshot of a freely mintable balance solely determine collator selection. Options: (1) time-weight or checkpoint reputation accrual over the full session rather than an instantaneous balance (e.g., track minimum balance held throughout the session, or accrue directly rather than via a transient mintable asset); (2) require Reputation Asset to originate only from deliveries with a non-zero, economically meaningful fee paid by an unrelated party, mirroring how outbound-delivery rewards are gated by real destination state proofs; (3) rate-limit or cap `MintPerByte` accrual per account per session; (4) require a minimum holding period (analogous to locking LP positions in the referenced remediation) before reputation counts toward collator ranking.

### Proof of Concept
1. Attacker controls (or cheaply uses) two ISMP-connected chains, A and B, and sets themselves as the relayer signer.
2. Shortly before a Hyperbridge session boundary, attacker dispatches a POST request from A to B with a large body and `fee = 0` (self-relay is explicitly supported) [3](#0-2) .
3. Attacker relays and delivers the message to Hyperbridge/destination themselves, signing with their own key so `relayer_for` recovers their controller account.
4. `pallet-messaging-incentives::on_executed` mints `bytes × MintPerByte` Reputation Asset to the attacker's controller [14](#0-13) ; repeat with several large messages to outrank other candidates.
5. At the session boundary, `pallet-collator-manager::new_session` ranks all bonded candidates by this inflated Reputation Asset balance and selects the attacker into the collator set [15](#0-14) .
6. The attacker's Reputation Asset is burned to zero as part of selection [7](#0-6) , but the attacker has already secured the collator seat (and its block rewards) for that session, at a cost limited to gas for self-dispatched, self-relayed low-value messages. This can be repeated every session.

```rust
	fn on_executed(
		messages: Vec<MessageWithWeight>,
		_events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let rate = MintPerByte::<T>::get();
		if !rate.is_zero() {
			for mw in &messages {
				let bytes = Self::message_bytes(&mw.message);
				let bytes_balance: BalanceOf<T> = (bytes as u128).saturated_into();
				let amount = rate.saturating_mul(bytes_balance);
				if amount.is_zero() {
					continue;
				}
				if let Some(relayer) = Self::relayer_for(&mw.message) {
					match T::ReputationAsset::mint_into(&relayer, amount) {
						Ok(_) =>
							Self::deposit_event(Event::ReputationMinted { relayer, bytes, amount }),
						Err(err) => log::warn!(
							target: "messaging-incentives",
							"reputation mint failed for {bytes}b: {err:?}",
						),
					}
				}
			}
		}
```

```rust
			T::IncentivesManager::reset_incentives();

			let desired_collators = core::cmp::max(
				pallet_collator_selection::DesiredCandidates::<T>::get(),
				<T as pallet_collator_selection::Config>::MinEligibleCollators::get(),
			) as usize;

			// Rank candidate controllers that have session keys by reputation, highest first.
			// We keep every eligible candidate, even those with no reputation, so the set never
			// shrinks below what's needed to keep producing blocks; reputation only orders them.
			let mut candidates = pallet_collator_selection::CandidateList::<T>::get()
				.into_iter()
				.map(|info| info.who)
				.filter(|stash_account| !Unbonding::<T>::contains_key(stash_account))
				.filter_map(|stash_account| Controller::<T>::get(&stash_account))
				.filter(|controller_account| {
					!RemovedValidators::<T>::contains_key(controller_account) &&
						pallet_session::NextKeys::<T>::get(controller_account.clone().into())
							.is_some()
				})
				.map(|controller_account| {
					(T::ReputationAsset::balance(&controller_account), controller_account)
				})
				.collect::<Vec<_>>();

			candidates.sort_by_key(|(balance, _)| *balance);

			// Invulnerables always collate unless root has removed them; the highest reputation
			// candidates fill the rest.
			let mut new_set: Vec<T::AccountId> =
				pallet_collator_selection::Invulnerables::<T>::get()
					.into_iter()
					.filter(|validator| !RemovedValidators::<T>::contains_key(validator))
					.collect();
			for (_, controller) in candidates.into_iter().rev().take(desired_collators) {
				if !new_set.contains(&controller) {
					new_set.push(controller);
				}
			}

			if new_set.is_empty() {
				return None;
			}

			for account_id in &new_set {
				let balance = T::ReputationAsset::balance(account_id);
				if balance.is_zero() {
					continue;
				}
				let result = T::ReputationAsset::burn_from(
					account_id,
					balance,
					Preservation::Expendable,
					Precision::Exact,
					Fortitude::Polite,
				);

				if result.is_ok() {
					Self::deposit_event(Event::ReputationReset {
						who: account_id.clone(),
						amount: balance,
					});
				}
			}
```

```markdown
1. `pallet-ismp` finishes executing a batch of messages and invokes
   [`FeeHandler::on_executed`].
2. This pallet reads the current `MintPerByte` rate. If it is zero, nothing
   happens (the pallet stays installed but inactive).
3. For each `Request`/`Response` message it:
   - Computes `bytes = max(body_size, 32)` — the same floor `pallet-bandwidth`
     uses, so trivial payloads can't game the mint by costing zero.
   - Multiplies `bytes × MintPerByte` to get the mint amount.
   - Recovers the relayer's account from the sr25519 signature on the message's
     `signer` field.
   - Mints that amount of `ReputationAsset` to the relayer.
4. Consensus messages and any non-Request/Response variants are skipped.
5. `pays_fee = Pays::No` on the dispatch info — the relayer is never charged
   here.
```

```text
### Prover-Bound Proofs

Each SP1 proof commits a nonce into its public values, and the runtime requires that nonce to equal the extrinsic signer. This binds a proof to the prover that produced it:

- A proof **cannot be stolen** — copying the proof bytes from the mempool and submitting them under a different account is rejected, because the committed account no longer matches the signer.
- Reward **deduplication is per-account** — an account is rewarded at most once per finality target, so a single prover cannot mint many byte-distinct variants of one proof (e.g. via Groth16 re-randomization) to sweep multiple uncle slots.
```
