### Title
Webhook `shop-domain` and `topic` headers are not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Webhooks::Registry.process` verifies the HMAC using only that body before trusting the `shop`, `topic`, and `webhook_id` values taken from unauthenticated HTTP headers. Because the HMAC is computed with the app's single `client_secret` shared across every merchant/shop that has the app installed, the body+HMAC pair legitimately observed for one shop's webhook remains cryptographically valid when replayed with a different `shop-domain` header, letting the header-derived shop identity diverge from the identity actually authenticated by the signature.

### Finding Description
The gem's webhook HMAC check is: [1](#0-0) 
which signs only `@raw_body`. The `shop`, `topic`, `api_version`, and `webhook_id` fields are read straight off attacker/network-controllable HTTP headers with no cryptographic binding to the body: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` and `request.topic` to dispatch the payload to the registered handler: [3](#0-2) 

The identity binding that should hold is: `shop authenticated by HMAC == shop stored/acted upon by the handler`. Here the HMAC only authenticates the byte content of the body; it never authenticates which shop or topic that body is claimed to belong to. The `client_secret` used to compute the HMAC is a single app-level secret shared by *all* installed shops, not a per-shop secret, so a valid `(raw_body, hmac)` pair generated by Shopify for merchant A's webhook remains fully valid when resent by anyone who observed it (e.g., merchant A themselves, a shared/misconfigured proxy log, or a public webhook endpoint response) but with the `shop-domain` header rewritten to shop B's domain. `HmacValidator.validate` and `validate_signature` never reference `shop` at all: [4](#0-3) 

This is unlike the OAuth callback path, where `shop` *is* included in the signable string and therefore is bound by the HMAC: [5](#0-4) 

The webhook path has no equivalent binding for `shop`/`topic`, so the equality "HMAC-authenticated payload == payload attributed to shop X" can be broken purely by header manipulation, matching the report's bug class (a field acted on but not covered by the HMAC).

### Impact Explanation
Any unprivileged internet user who can obtain one valid `(raw_body, x-shopify-hmac-sha256)` pair for the app (trivially available to any merchant who has the app installed, since they can see their own webhook deliveries/logs, or via a proxy/CDN that logs bodies) can replay it against the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` header. The application-level handler receives `WebhookMetadata` with `shop` set to the attacker-chosen value and a body it will treat as authentic, since the gem's own verification step raised no error. Downstream, apps commonly use `request.shop`/`data.shop` to look up the shop's session/access token and write incoming webhook data into that shop's tenant record — this can inject or corrupt data attributed to a *different* merchant's tenant, i.e., cross-tenant data injection. This matches the "cross-tenant access" Critical impact category, since the gem's documented, unmodified API flow (`Request.new` + `Registry.process`) is what performs the improper trust.

### Likelihood Explanation
Likelihood is high for the class of attacker who is any real merchant with the app installed (unprivileged relative to other tenants): they can capture a legitimate webhook body+HMAC from their own shop's normal traffic (no secret access needed) and simply resend it with a modified `shop-domain` header pointing at another shop. No access to `api_secret_key`, access tokens, or TLS interception of another tenant is required — only observation of one's own webhook traffic, which is inherent to using the product.

### Recommendation
Bind the claimed shop (and topic) to the HMAC-verified content, e.g., by requiring host applications to cross-check `request.shop` against the shop associated with the webhook's `topic`/subscription id server-side (via a lookup keyed by `webhook_id` from Shopify's API) rather than trusting the header value directly, or by having `Registry.process` reject processing unless the caller supplies an expected shop to compare against. At minimum, document prominently that `shop`, `topic`, and `webhook_id` in `WebhookMetadata` are **not** authenticated by the HMAC and must not be used as a trust boundary without an independent shop verification step.

### Proof of Concept
1. Attacker (a legitimate merchant `shop-a.myshopify.com` with the app installed) triggers a normal event (e.g., creates an order) and observes the resulting webhook POST that Shopify sends to the app, capturing the exact `raw_body` and the `x-shopify-hmac-sha256` header value (visible to them via their own network tooling, browser devtools on a webhook-relay dashboard, or a logging proxy they control in front of their own install).
2. Attacker resends that exact `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: shop-b.myshopify.com` (a different merchant) and keeps/adjusts `x-shopify-topic` as desired.
3. `ShopifyAPI::Webhooks::Request.new` parses these headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `raw_body` [1](#0-0)  — verification succeeds because the body is unmodified.
4. The registered handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` [6](#0-5)  using the attacker-supplied `shop-b.myshopify.com`, causing the host application to process/attribute merchant-A-originated data as belonging to merchant B.
