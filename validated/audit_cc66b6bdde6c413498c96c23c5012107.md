### Title
Webhook shop-domain and topic headers are not covered by the HMAC signature, allowing shop identity spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the shop identity used for tenant routing (`request.shop`) comes from the unsigned `x-shopify-shop-domain`/`shopify-shop-domain` header. `Webhooks::Registry.process` validates the HMAC over the body only, then trusts the header-derived shop value to dispatch the webhook to the handler. This is the same bug class as the JOJO report: a field that business logic acts on (`shop`) is not covered by the integrity check (HMAC), so the two can be made to disagree.

### Finding Description
The signed material for a webhook request is defined as: [1](#0-0) 

Only `@raw_body` is included; the `shop-domain`, `topic`, `api-version`, and `webhook-id` headers are excluded from `to_signable_string` even though they are all read out of unauthenticated request headers: [2](#0-1) 

`Registry.process` verifies only this body-based HMAC and then immediately trusts `request.shop`/`request.topic` to route the payload to a handler and construct `WebhookMetadata`: [3](#0-2) 

The identity binding that should hold is:
`shop_bound_by_hmac == shop_used_by_handler`

But in this implementation:
`shop_bound_by_hmac = ∅` (the HMAC only binds the body bytes) while `shop_used_by_handler = header["shopify-shop-domain"]` (fully attacker-controlled once a valid body+HMAC pair is obtained).

Because the HMAC never binds to `shop`, any request whose **body** produces a valid HMAC for the app's secret will be accepted regardless of which shop's header is attached to it. An attacker who operates their own installed app instance receives genuine webhook deliveries — real `raw_body` + real `hmac-sha256` pairs, computed with the app's shared secret, for their own shop. They can then replay that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header (and `x-shopify-topic`/`webhook-id`) with a different, victim shop's domain. `HmacValidator.validate` still succeeds because it only recomputes/checks the signature over `raw_body`: [4](#0-3) 

The handler then executes business logic under the impersonated victim shop's identity (`data.shop`), even though the actual signed content originated for a different tenant.

### Impact Explanation
This breaks the tenant/shop identity binding the HMAC is supposed to guarantee, letting an attacker (any party able to install the app once, i.e. an unprivileged internet user with respect to any other merchant) cause webhook-triggered app logic to run under an arbitrary other shop's identity. Depending on how the host app keys data/actions by `data.shop` (order sync, uninstall handling, billing state, etc.), this enables cross-tenant data confusion/corruption — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is bounded by needing at least one genuine `(raw_body, hmac)` pair, which any shop that installs the app can obtain immediately and repeatedly (webhooks fire routinely, e.g. on `app/uninstalled`, `orders/create`, etc.), then replay against the app's public webhook endpoint with a forged shop header. No secret, token, or privileged access is required beyond a normal, low-privilege app installation.

### Recommendation
Include the tenant-identifying fields (`shop`, `topic`, `webhook_id`, `api_version`) in the signable string used for HMAC verification, or otherwise cryptographically bind the shop domain to the payload before it is trusted in `Registry.process`. At minimum, `to_signable_string` should not diverge from the set of fields later consumed as authenticated (mirroring the JOJO fix of using one, consistent formula/binding for both computation and consumption).

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com`; capture a real webhook delivery with body `B` and header `x-shopify-hmac-sha256: H` (valid for the app's secret).
2. Send a POST to the app's webhook endpoint with the same body `B` and header `H`, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this successfully; `Utils::HmacValidator.validate(request)` returns `true` because it only checks `B` against `H` (per `hmac_validator.rb` lines 26-31), never checking the shop header.
4. `Registry.process` dispatches to the registered handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, causing the app to process the webhook as though it were sent by `victim-shop.myshopify.com`.
