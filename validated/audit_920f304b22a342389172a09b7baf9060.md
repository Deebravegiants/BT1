### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, while the `shop` identity used to route the event to the app's handler is taken from an HTTP header that is never included in the signed material. This breaks the intended binding between "the shop the HMAC proves the request came from" and "the shop the app processes the payload for."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`#shop` is read from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is not part of the signable string and therefore not covered by the HMAC at all: [2](#0-1) 

`Registry.process` validates only the HMAC (over the body) and then immediately trusts `request.shop` to construct the `WebhookMetadata` passed to the app's handler, without any additional binding between the verified body and the shop identity: [3](#0-2) 

Because the HMAC is computed with `Context.api_secret_key` over the body only [4](#0-3) , any HMAC-valid `(body, hmac)` pair obtained from a legitimate webhook delivery — including one addressed to a shop the attacker legitimately controls (e.g., the attacker's own store that has the app installed) — remains valid for that same body no matter what value is placed in the `shop-domain` header. An attacker who operates their own shop with the app installed receives real, correctly-signed webhooks. They can capture the `(raw_body, hmac)` pair from one of these deliveries and replay it directly to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` will still pass because it only checks the body against the secret, and `WebhookMetadata.shop` will report the victim's domain to the handler.

This is exactly the "field acted on but not covered by the HMAC" class described in the report: the identity binding `shop authenticated by HMAC == shop used by the handler` does not hold, because the header carrying `shop` was never fed into the signature.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` to determine which merchant's data/session the webhook payload applies to (the documented and expected usage pattern, since the payload itself typically does not repeat the shop domain), an attacker can inject an event that is processed as belonging to a different, victim shop. Depending on the handler's logic (e.g., updating locally cached order/product/customer state, triggering uninstall/GDPR flows, or app-billing/plan updates keyed by shop), this enables cross-tenant data injection or corruption using only a webhook payload the attacker legitimately received for their own store. This matches the "cross-tenant access" impact category.

### Likelihood Explanation
Moderate-to-high: the attacker only needs their own Shopify store with the target app installed (no special privileges, no access to the app's `client_secret` or any victim credentials) to obtain a validly-signed `(body, hmac)` pair, and then a single HTTP POST with a forged `shop-domain` header to exploit it. The exploit does not require guessing any secret since the HMAC value is reused verbatim.

### Recommendation
Bind the shop identity to the signed material, e.g. include the resolved shop domain in the value that is HMAC-verified (or independently verify that the shop domain in the header matches an expected/known value for the delivered `webhook_id`/topic before trusting it), rather than trusting an unauthenticated header for tenant attribution downstream of body-only HMAC verification.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`. Shopify delivers a real webhook, e.g. `orders/create`, to the app's endpoint with headers including a valid `x-shopify-hmac-sha256` computed over the JSON body using the app's `api_secret_key`.
2. Attacker captures the raw request body `B` and the valid HMAC value `H` for that delivery.
3. Attacker sends a new POST to the same webhook endpoint with:
   - Body: the same `B`
   - Header `x-shopify-hmac-sha256: H` (unchanged, still valid for `B`)
   - Header `x-shopify-shop-domain: victim.myshopify.com` (forged)
   - Header `x-shopify-topic`/`x-shopify-webhook-id` as desired
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H` [5](#0-4) .
5. The handler is invoked with `WebhookMetadata.new(... shop: request.shop ...)` reporting `victim.myshopify.com` [6](#0-5) , causing the app to process attacker-controlled data as if it belongs to the victim shop.
