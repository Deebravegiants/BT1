### Title
`DirectBridge.describeWithdrawal` unconditionally reports every NEAR-withdrawal index as `completed` with the shared intent tx hash, hiding per-recipient delivery failure - ([File: packages/intents-sdk/src/bridges/direct-bridge/direct-bridge.ts])

### Summary
`DirectBridge.describeWithdrawal` returns `{ status: "completed", txHash: args.tx.hash }` without reading `args.withdrawalParams`, without querying the NEAR receipt chain, and without any per-index differentiation. When a single intent batches two `ft_withdraw` intents to different `destinationAddress`es (two `WithdrawalIdentifier`s, index 0 and 1, sharing the same `tx.hash`), the method returns byte-identical "completed" results for both indexes even if one of the underlying `ft_transfer` calls fails downstream (e.g. an unregistered/implicit recipient causing a promise failure and an internal-balance refund inside `intents.near`), because that failure happens in an async receipt scheduled after the parent transaction already returned `SuccessValue`.

### Finding Description
Broken equality: for `describeWithdrawal(wid0)` vs `describeWithdrawal(wid1)` where `wid0.withdrawalParams.destinationAddress !== wid1.withdrawalParams.destinationAddress` but `wid0.tx.hash === wid1.tx.hash`, the expected invariant is that each result reflects the actual delivery outcome of that specific `ft_withdraw` intent. The actual code: [1](#0-0) 

completely ignores `args.withdrawalParams` and `args.index`, so `describeWithdrawal(wid0) === describeWithdrawal(wid1)` whenever `tx.hash` matches — regardless of whether the on-chain outcome for the two recipients actually diverged.

Root cause: a NEAR `execute_intents` call that includes multiple `ft_withdraw` intents finishes and returns `SuccessValue` for the top-level `FunctionCall` receipt as soon as it schedules the internal-balance debits and the cross-contract `ft_transfer`/`storage_deposit` promises; the eventual success or failure of each scheduled `ft_transfer` (and any compensating refund of the sender's internal balance on failure) happens in receipts processed after the parent transaction's outcome is already finalized as success. `createWithdrawalIdentifier` assigns distinct `index` values per withdrawal within the `NearWithdrawal` route: [2](#0-1) 

but `describeWithdrawal` never uses that index (or the tx receipt outcomes) to disambiguate which `ft_withdraw` in the batch actually landed. Compare this to every other bridge in the repo that lands off-chain, which polls an indexer/HTTP status keyed by nonce/index (e.g. `HotBridge.describeWithdrawal` fetches nonces per `args.index` and queries bridge status), confirming that per-index verification is the expected pattern that `DirectBridge` skips entirely: [3](#0-2) 

None of the existing guards prevent this: `validateWithdrawal` only checks address validity and, for **explicit** named accounts, that the account exists on NEAR — it does not verify NEP-141 storage registration on the token contract, and implicit accounts skip this check entirely: [4](#0-3) 

`estimateWithdrawalFee` does compute a `storageDepositFee` from `getNearNep141StorageBalance`/`getNearNep141MinStorageBalance`, but `createWithdrawalIntents` blindly trusts whatever `feeEstimation` object it is handed: [5](#0-4) 

Since callers may invoke `createWithdrawalIntents` directly with any `feeEstimation`, or storage state can change between quote and execution, one leg of a multi-withdrawal batch can fail to register storage while the other succeeds — and `describeWithdrawal` cannot tell them apart.

### Impact Explanation
An integrator polling `describeWithdrawal` per `WithdrawalIdentifier` receives `{status:"completed", txHash: tx.hash}` for both index 0 and index 1 even when only one `ft_transfer` actually reached its destination and the other was refunded internally to the sender inside `intents.near`. This is a status misreport that can cause an integrator to credit (or release an off-chain/associated on-chain obligation for) a destination address that never received funds, matching the "status or hash misreport making an integrator credit or refund twice" High-impact category. The attacker (the withdrawing user themself) controls which of the two destination addresses is unregistered, making this fully repeatable per intent.

### Likelihood Explanation
Preconditions: a single intent batching two (or more) `NearWithdrawal`-route withdrawals to different NEP-141 recipients, where at least one recipient lacks sufficient token storage balance (trivial to arrange — e.g., a fresh implicit/unregistered account, or a `createWithdrawalIntents` call using a stale/zero `storageDepositFee`). No special privilege is required — this is an ordinary SDK caller supplying two `withdrawalParams`. Cost is only gas for one NEAR transaction. Fully repeatable for any batch of NEAR-native withdrawals.

### Recommendation
`DirectBridge.describeWithdrawal` should verify the actual on-chain outcome of the specific `ft_withdraw` intent identified by `args.index`/`args.tx`, e.g., by fetching the transaction's receipts/outcomes from `nearProvider` and inspecting the relevant receipt (or by tracking the token balance delta on the recipient, or looking for the internal-balance refund event) instead of unconditionally returning `completed`.

import { describe, it, expect } from "vitest";
import { DirectBridge } from "./direct-bridge";

describe("DirectBridge.describeWithdrawal per-index truth", () => {
  it("returns identical status for two different destinations sharing one tx hash", async () => {
    const bridge = new DirectBridge({ envConfig: {} as any, nearProvider: {} as any });

    const tx = { hash: "shared-tx-hash", accountId: "user.near" };

    const wid0 = bridge.createWithdrawalIdentifier({
      withdrawalParams: {
        assetId: "nep141:usdt.tether-token.near",
        amount: 1000n,
        destinationAddress: "recipientA.near", // succeeds
        feeInclusive: false,
      },
      index: 0,
      tx,
    });

    const wid1 = bridge.createWithdrawalIdentifier({
      withdrawalParams: {
        assetId: "nep141:usdt.tether-token.near",
        amount: 1000n,
        destinationAddress: "unregistered-recipient.near", // ft_transfer panics -> refunded internally
        feeInclusive: false,
      },
      index: 1,
      tx,
    });

    const status0 = await bridge.describeWithdrawal(wid0);
    const status1 = await bridge.describeWithdrawal(wid1);

    // Both report "completed" with the same tx hash despite representing
    // divergent real-world outcomes (one delivered, one refunded).
    expect(status0).toEqual({ status: "completed", txHash: "shared-tx-hash" });
    expect(status1).toEqual({ status: "completed", txHash: "shared-tx-hash" });
    expect(status0).toEqual(status1); // integrator cannot distinguish success vs refund
  });
});

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
