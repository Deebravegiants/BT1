### Title
Webhook shop-domain identity is not bound to the HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authenticated once `Utils::HmacValidator.validate(request)` succeeds, then dispatches the handler using `request.shop`, which is read from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header [1](#0-0) . However the HMAC that is verified only covers the raw request body, not the shop-domain header, so the "authenticated" identity (`shop`) is never actually bound to the cryptographic proof.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

`shop` is a completely separate accessor pulled straight from a header, with no cryptographic tie to the HMAC: [3](#0-2) 

`Utils::HmacValidator.validate` computes `HMAC(api_secret_key, verifiable_query.to_signable_string)` and compares it to the `hmac` header — i.e., it only proves the *body* bytes were signed by someone possessing `Context.api_secret_key`; it says nothing about which shop the body belongs to: [4](#0-3) 

`Registry.process` uses this weak guarantee to gate everything, then forwards the unauthenticated `shop` value into the handler: [1](#0-0) 

The critical detail is that the app's `api_secret_key` (the HMAC key) is **shared across every shop that installs the app** — it is not per-tenant. Any merchant can install the same public/dev app on their own store and legitimately receive real webhooks for their own shop, each delivered with a valid `raw_body` + `hmac-sha256` pair computed with that same shared secret. Because the shop-domain header sits entirely outside the signed content, that same `(raw_body, hmac)` pair remains cryptographically valid no matter what shop-domain header accompanies it. An attacker-merchant can therefore:

1. Install the target app on their own shop A and capture a legitimate webhook delivery — raw body B and its accompanying valid `x-shopify-hmac-sha256` header H.
2. Replay a new POST to the app's webhook endpoint using the same body B and header H, but with `x-shopify-shop-domain` swapped to shop B (any other shop that installed the app, e.g. a competitor or the attacker's second/faked install).
3. `Utils::HmacValidator.validate` succeeds (it only checks B and H, both attacker-supplied/kept-genuine), `Registry.process` calls the handler with `shop: "shop-b.myshopify.com"` even though the payload actually originated (was HMAC-signed) for shop A.

This breaks the equality that application authors are implicitly promised by this gem's API: `hmac_valid? == (body, shop) both authentic-for-shop`. In reality the gem only proves `hmac_valid? == body authentic-for-app` (any tenant of the app), while `shop` is unauthenticated attacker-controlled input passed straight to `WebhookMetadata#shop` and downstream handler logic.

### Impact Explanation
Applications that follow this gem's documented API build their webhook handlers on the assumption that a webhook which passes `HmacValidator.validate` carries a trustworthy `shop` value (this is exactly how `Registry.process`/`WebhookMetadata` present it — shop is handed to the handler alongside a "validated" hmac in the same call). Because `shop` is not bound to the signature, an attacker who is nothing more than a normal merchant/tenant of the app can forge webhook events attributed to a different tenant. Depending on the topic this enables cross-tenant data corruption or disclosure: e.g., forging `orders/create`/`customers/create` payloads that get written into another shop's records, or forging mandatory GDPR topics like `shop/redact` / `customers/redact` to trigger deletion of another shop's data. This is a cross-tenant authentication/identity-binding bypass, matching the Critical - cross-tenant access category.

### Likelihood Explanation
The only "credential" needed is being a merchant who has installed the app at all (any store can typically install a public/dev app), which is explicitly not a privileged account or leaked secret — it's the normal unprivileged-tenant capability. No TLS interception, social engineering, or access to `api_secret_key`/access tokens is required: the attacker obtains a legitimate `(body, hmac)` pair simply by receiving their own webhooks, then modifies one HTTP header on replay.

### Recommendation
Bind the shop identity into the signed content that `HmacValidator` verifies, or otherwise cryptographically tie the `shop` header to the specific delivery:
- Include the shop domain (and ideally topic/webhook-id) in `Webhooks::Request#to_signable_string`, verifying it against a value independently known to the app (e.g., cross-check `request.shop` against the shop record associated with the delivery, using a per-shop secret/session lookup) rather than trusting the header outright once the body HMAC passes.
- At minimum, document prominently that `HmacValidator.validate` only authenticates the body and that `request.shop` must be independently verified (e.g., matched against a shop known to have this webhook subscription/ID) before being used for any per-tenant action, and consider exposing a helper that performs that cross-check.

### Proof of Concept
```ruby
# Attacker installs the target app on their own shop "attacker.myshopify.com"
# and legitimately receives a real webhook, capturing:
raw_body = '{"id":123,"note":"legit payload from attacker shop"}'
valid_hmac = "<value from x-shopify-hmac-sha256 header of the genuine delivery>"

# Attacker replays the same body/hmac but swaps the shop-domain header
forged_headers = {
  "x-shopify-topic"       => "shop/redact",              # or any subscribed topic
  "x-shopify-hmac-sha256" => valid_hmac,                  # unchanged, still valid: signs only raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-chosen target tenant
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# Passes because HmacValidator only checks raw_body against Context.api_secret_key,
# which is shared across all shops of this app.
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(topic: "shop/redact",
#      shop: "victim-shop.myshopify.com", body: parsed(raw_body), ...))
# The handler now acts on "victim-shop.myshopify.com" using attacker-supplied body content,
# even though the HMAC only ever proved authenticity for "attacker.myshopify.com"'s delivery.
```
