### Title
Missing uint112 headroom check leaves `_seedDirectMint` able to silently overflow HyperSwap V2's packed reserve slot — ([File: packages/contracts/src/Bonding.sol])

### Summary
The OpenVM `hintstore` bug is a class of "partial range-check" bug: each limb is checked to fit a byte, but the reassembled 32-bit value can still exceed the field modulus, letting an attacker steer a derived pointer/address to an unintended location. `Bonding.sol` has the same shape of defect around the HyperSwap V2 pair's packed `uint112` reserve slots: it only range-checks the **launch-time** `virtualLtReserve` against `type(uint112).max/4` [1](#0-0) , but the value that actually gets written into the HyperSwap V2 pair at graduation (`ltFromPair`, and by extension `tokensForLP`) is never re-checked against `uint112` bounds at the point it is transferred and `mint`-ed.

### Finding Description
`_deployAndSeed` bounds `virtualLtReserve` once, at launch, to `type(uint112).max/4`, reasoning that "the raised LT reserve peaks at 3× virtualLtReserve" so 4x headroom is safe [2](#0-1) . This bound is derived purely from the curve's own bonding-curve math (assetReserve capped at 3× the virtual seed at 100% sell-out), and is enforced only once, at launch, against `virtualLtReserve` — never against the actual quantity later pushed into the V2 pair.

At graduation, `_prepareGraduationLiquidity` computes `ltFromPair = assetReserve - virtualLtReserve` from the **live stored `assetReserve`** [3](#0-2) , and `_seedDirectMint`/`_seedRebalancing` transfer that raw `ltFromPair` (and `tokensForLP`) directly to the HyperSwap V2 `Pair` and call `mint()` [4](#0-3) , whose reserves are packed into `uint112` slots (as confirmed by the `getReserves()` decoding in `_seedRebalancing` itself: `(uint112 r0, uint112 r1,) = IUniswapV2Pair(pair).getReserves();`) [5](#0-4) . Standard UniswapV2-style `_update()` in the V2 pair truncates `balance` into `uint112` via an implicit downcast — exactly the "byte-limb but not full-value" range-check gap the OpenVM report describes: the guard exists but is checked against the wrong/earlier value, not the value that is ultimately written into the bounded slot.

Because the launch-time check only bounds the LT quantity at launch (`virtualLtReserve`), and never re-validates the sum actually deposited at graduation time against `type(uint112).max`, any of the following can push the real transferred amount past the checked assumption without tripping any later guard:
- `setTokenImplementation` changing `TOTAL_SUPPLY` for tokens launched under a different implementation (explicitly flagged by the contract's own natspec as breaking the `_launchTimeVirtualLtReserve` derivation) [6](#0-5) , corrupting the recovered `virtualLtReserve` and thus `ltFromPair` for pre-rotation tokens.
- The "4x headroom" assumption is derived from an internal invariant (3x sellout) that is asserted only in a comment, not re-checked at the point of use — i.e., it's a design invariant, not an enforced range check on the value that crosses into the `uint112`-bounded external contract.

### Impact Explanation
If the quantity actually written into the HyperSwap V2 `Pair`'s packed reserve exceeds `type(uint112).max`, the underlying V2 pair's reserve accounting silently wraps/truncates (the classic UniswapV2 `uint112` overflow behavior), corrupting the pair's stored reserves relative to its real token balances. This desyncs the constant-product invariant from actual balances, which can be exploited to drain the pool via mispriced swaps once the LP is opened, or brick pool accounting (permanent freezing of LP/trader funds) — matching the impact bar of "LP seeded away from curve close price" / "permanent freezing of LP funds."

### Likelihood Explanation
Low-to-medium. The bound was clearly considered a real risk by the developers (hence the explicit `ExchangeRateTooLow` guard and its natspec) [7](#0-6) , but the guard is checked against a value one derivation step removed (`virtualLtReserve` at launch) from the value that is actually deposited (`ltFromPair`/`tokensForLP` at graduation, after `setTokenImplementation` rotations or other divergence between the checked invariant and the real transferred amount). This mirrors the OpenVM finding precisely: a range check exists, but it is checked on the wrong intermediate value, so the invariant it's meant to guarantee downstream is not actually enforced at the point of use.

### Recommendation
Re-validate the actual amounts crossing into the HyperSwap V2 pair (`tokensForLP`, `ltFromPair` in `_seedDirectMint` / `_seedRebalancing`) directly against `type(uint112).max` immediately before `transfer`/`mint`, rather than relying solely on the launch-time bound on `virtualLtReserve`. This closes the gap between "the value we checked" and "the value that actually gets packed into the bounded slot," the same fix pattern OpenVM applied (checking the value that is actually used, not a proxy for it).

### Proof of Concept
Conceptual PoC (cannot be fully executed without the vendored `IUniswapV2Pair`/HyperSwap V2 pair implementation, which is outside `packages/contracts/src` and not indexed here):
1. Launch a token with an LT whose `exchangeRate()` is just above the `ExchangeRateTooLow` floor, so `virtualLtReserve` is close to `type(uint112).max/4`.
2. Have the protocol owner call `setTokenImplementation` to a new `Token` implementation with a different `TOTAL_SUPPLY` (the code explicitly permits this and warns pre-rotation tokens' `_launchTimeVirtualLtReserve` derivation becomes wrong) [8](#0-7) .
3. Trade the pre-rotation token to full curve sell-out / USD threshold, triggering `_enterGraduating` → `_prepareGraduationLiquidity`, which now recovers a corrupted `_launchTimeVirtualLtReserve` (divided by the new `TOTAL_SUPPLY`) and computes an inflated `ltFromPair` [3](#0-2) .
4. `finalizeGraduation` → `_seedDirectMint` transfers this inflated `ltFromPair` into the HyperSwap V2 pair and calls `mint()`, where the pair's `uint112` reserve packing overflows/truncates [4](#0-3) .

This PoC is speculative in one respect: I could not verify the exact HyperSwap V2 `Pair._update` implementation (it is a vendored/external contract, excluded from `packages/contracts/src` per the analog rules) to confirm it uses an unchecked/implicit `uint112` downcast rather than a `SafeCast`-guarded one. If HyperSwap's V2 fork added an explicit overflow revert in `_update` (unlike stock UniswapV2), this specific overflow path would revert instead of silently wrapping, though it would still **permanently brick `finalizeGraduation`** for that token (a stuck graduation → frozen LT/tokens on `Bonding`), which independently satisfies the "permanent freezing of funds" impact bar.

    ///         Existing clones bake their impl in at deploy time and are unaffected.
    /// @dev    Reverts unless the new impl exposes the same `TOTAL_SUPPLY`
    ///         as the current one. `_launchTimeVirtualLtReserve` recovers the
    ///         launch-time virtual LT reserve as `Pair.k() / TOTAL_SUPPLY`,
    ///         so a rotation that changes `TOTAL_SUPPLY` would mis-derive the
    ///         reserve for tokens launched before the rotation, breaking
    ///         their graduation math. Tokens launched AFTER a (mismatched)
    ///         rotation would still derive correctly because their `Pair.k`
    ///         is set off the new `TOTAL_SUPPLY`, but mixing pre- and post-
    ///         rotation tokens under a single derivation rule isn't safe.
    function setTokenImplementation(
        address newImpl
    ) external onlyOwner {
        if (newImpl == address(0)) revert ZeroAddress();
        BondingStorage storage $ = _s();
        if (Token(newImpl).TOTAL_SUPPLY() != Token($.tokenImplementation).TOTAL_SUPPLY()) {
            revert InvalidInput();
        }
        address old = $.tokenImplementation;
        $.tokenImplementation = newImpl;
        emit TokenImplementationUpdated(old, newImpl);
    }
