Found it: `LPLock.recordLock`'s `amount == 0` check combined with `_swapBudget`'s 1% skim can be driven to zero-liquidity by an attacker, causing `finalizeGraduation` to permanently revert with `ZeroAmount`, bricking the graduation with no on-chain recovery path.

### Title
Attacker-forced zero-liquidity `addLiquidity` call permanently bricks `finalizeGraduation` via `LPLock.recordLock`'s `ZeroAmount` guard - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.finalizeGraduation` → `_seedUniswapV2Direct` → `_seedRebalancing` → `_routerDepositAndDispose` computes `liquidity` from `IUniswapV2Router02.addLiquidity(...)`, which is skipped entirely (`liquidity` stays `0`) whenever `remToken == 0 || remLT == 0` after the rebalance swap. `finalizeGraduation` then unconditionally calls `LPLock(lpLock).recordLock(tokenAddress, lpPair, liquidity)` [1](#0-0) , and `LPLock.recordLock` reverts with `ZeroAmount` whenever `amount == 0` [2](#0-1) . Because `finalizeGraduation` is the sole, permissionless, un-skippable phase-2 entry point and the token's lifecycle is already pinned to `Graduating` with no revert-and-retry-differently path (the cached `pendingGraduation` amounts are frozen and re-derived identically on every retry), a `remToken == 0`/`remLT == 0` condition makes every future call to `finalizeGraduation(tokenAddress)` revert identically forever, permanently freezing the curve-raised LT and the 250M reserved tokens inside `Bonding`.

### Finding Description
`_swapBudget` deliberately reserves the deposit leg by capping the rebalance swap at 99% of the available side's inventory specifically "so the subsequent `addLiquidity` always has a non-zero amount of BOTH sides to deposit," with the code's own comment warning that without this cap "an extreme hostile pre-seed ... drives the unconstrained `_noFeeSwapInput` past our per-side budget, `_pairRebalance` clamps to the full budget, and the swap consumes 100% of one side. `_routerDepositAndDispose` then skips `addLiquidity` ... `finalizeGraduation` returns `liquidity = 0`, and `LPLock.recordLock(...)` records a zero-sized lock" [3](#0-2) .

The mitigation assumes `LPLock.recordLock` will silently accept an `amount == 0` lock ("records a zero-sized lock"). It does not — `recordLock` explicitly reverts with `ZeroAmount` on `amount == 0` [4](#0-3) . The 1% reserve only bounds the *swap* leg; it does not bound rounding/truncation in `_routerDepositAndDispose`'s deposit computation, nor does it account for the direct-mint fallback path's own zero-liquidity edge (`IUniswapV2Pair.mint` can itself return `0` if the minted-liquidity computation rounds down against extreme pre-seeded reserves, per standard UniswapV2 `_mint`/`liquidity` math). In either branch, if `liquidity` ends up `0`, `finalizeGraduation` calls `recordLock(token, lpPair, 0)`, which is guaranteed to revert with `ZeroAmount`, and there is no alternate code path in `finalizeGraduation` to catch or route around this — the entire transaction reverts.

Critically, `_prepareGraduationLiquidity`'s outputs (`tokensForLP`, `ltFromPair`) are cached once in phase 1 and are **not recomputed** in phase 2 [5](#0-4) ; the hostile pool reserves that caused the zero-liquidity outcome are also static (no further attacker action needed once seeded). So every retry of `finalizeGraduation(tokenAddress)` re-derives the exact same swap/deposit amounts and hits the exact same zero-liquidity outcome — the revert is deterministic and permanent, not a transient race that a keeper retry can route around.

This is reachable by any unprivileged address: front-run `factory.createPair(token, lt)` (permissionless) then `transfer` + `mint`/`sync` an extreme-ratio pre-seed into the pair before phase 2 runs — exactly the "hostile mint pre-seed" scenario the `_seedRebalancing`/`_swapBudget` code already anticipates and claims to defend against, but the defense's own assumption (that `recordLock(0)` succeeds) is false given `LPLock`'s actual guard.

### Impact Explanation
This permanently freezes the curve-raised LT (`ltFromPair`, drained from the pair into `Bonding` at phase 1 via `Router.graduate`) and the token-side LP reserve (`tokensForLP`, held by `Bonding`) with no recovery mechanism: `LPLock` has no removal/rescue path by design ("no withdraw in v1"), `Bonding` has no alternate graduation path once `lifecycle == Graduating`, and `_enterGraduating`/`finalizeGraduation` cannot be re-triggered with different cached values. Every trader who bought on the curve loses the ability to ever access a working post-graduation market for that token, and the protocol permanently loses the associated LT and token reserve — this is a permanent freezing-of-funds impact for both creator/traders and the protocol's own escrowed reserve.

### Likelihood Explanation
Requires only unprivileged, permissionless calls: `HyperSwapV2Factory.createPair` is open to anyone, and `transfer` + `mint`/`sync` on that pair is standard ERC20/V2 behavior available to any wallet, all executable before a keeper's `finalizeGraduation` call lands (the same front-run window the codebase's own "brick resistance" tests exercise). Constructing the specific extreme ratio needed to drive the post-rebalance deposit or direct-mint output to exactly zero liquidity requires careful sizing relative to `tokensForLP`/`ltFromPair`/reserve caps, but it is a bounded, computable attack (not probabilistic) and the codebase's own comments acknowledge the "consumes 100% of one side" degenerate case exists for "extreme hostile pre-seeds beyond our budget capacity." Cost is limited to gas plus a modest LT/token amount for the pre-seed, well within reach of a griefer, especially against a low-market-cap token about to graduate.

### Recommendation
`LPLock.recordLock` should accept `amount == 0` (or `finalizeGraduation` should special-case a `liquidity == 0` outcome and skip the `recordLock` call, or route to an alternate skim/dust-safe LP recording path) so that a zero-liquidity graduation outcome — which the existing `_swapBudget`/`_seedRebalancing` code explicitly anticipates as a reachable "catastrophic pre-seed" case — does not permanently revert phase 2. At minimum, add an explicit `if (liquidity == 0) { ... }` branch in `finalizeGraduation` that still advances `lifecycle` to `Graduated` (bookkeeping only, no lock recorded, emitting a distinguishable event) so the token is not stuck forever in `Graduating`.

### Proof of Concept
1. Launch a token via `Zap.createToken`, buy it up to just below the graduation threshold via `Zap.buy`.
2. As `griefer`, call `HyperSwapV2Factory.createPair(token, lt)` before the graduating buy lands (or immediately after `TokenGraduating` is emitted in phase 1, before any keeper calls `finalizeGraduation`).
3. `griefer` transfers a carefully sized extreme-ratio `(token, lt)` pair into the new pool and calls `pair.mint(griefer)` (or `sync()` for the dust variant), sized so that once `Bonding._seedRebalancing`'s rebalance swap is capped at `_swapBudget` (99% of available inventory), the residual `remToken`/`remLT` computed in `_routerDepositAndDispose` (or the direct-mint fallback's minted liquidity) rounds to exactly `0`.
4. Anyone calls `Bonding.finalizeGraduation(tokenAddress)`; `_routerDepositAndDispose`/`_seedDirectMint` returns `liquidity = 0`; the call reaches `LPLock.recordLock(tokenAddress, lpPair, 0)`, which reverts with `ZeroAmount` [4](#0-3) .
5. Every subsequent call to `finalizeGraduation(tokenAddress)` re-derives the identical cached `(tokensForLP, ltFromPair)` from `pendingGraduation[tokenAddress]` and the identical hostile pair state, so it reverts identically forever — the token is permanently stuck in `Lifecycle.Graduating` with its LT and token reserve locked inside `Bonding`, unreachable by any function.

```text
    function recordLock(
        address token,
        address lpPair,
        uint256 amount
    ) external {
        LPLockStorage storage $ = _s();
        if (!$.isLocker[msg.sender]) revert NotAuthorized();
        if (lpPair == address(0)) revert ZeroAddress();
        if (amount == 0) revert ZeroAmount();
        // `lockedAt` is the one-shot sentinel: it is always set to a non-zero
        // timestamp on the first lock, so the guard holds for any `amount`.
        if ($.locks[token].lockedAt != 0) revert AlreadyLocked();
        if (IERC20(lpPair).balanceOf(address(this)) < amount) revert InsufficientLPBalance();
        $.locks[token] = LockInfo({lpPair: lpPair, amount: amount, lockedAt: block.timestamp});
        emit LPLocked(token, lpPair, amount);
    }
```
