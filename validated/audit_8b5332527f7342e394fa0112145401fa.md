Found `Webhooks::Request#shop` critically important: the `shop` value used to identify the tenant for a webhook is read directly from the `X-Shopify-Shop-Domain` header, and this header is **not** included in the HMAC-signed payload — only `@raw_body` is signed (`to_signable_string` returns `@raw_body`).

### Title
`Webhooks::Request#shop` (shop-domain header) is not covered by the webhook HMAC, breaking the shop⇄payload binding - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies webhook authenticity by validating the HMAC over the raw request body only, then trusts the `shop` value taken from the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) HTTP header to route the webhook to the tenant-specific handler.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string`, and for `Webhooks::Request` that method returns only `@raw_body`: [1](#0-0) 
Meanwhile `shop` (the tenant identifier) is read straight from the HTTP headers, not from the signed body: [2](#0-1) 
`Registry.process` verifies the HMAC and, if valid, immediately dispatches the handler using `request.shop` from the (unsigned) header: [3](#0-2) 

The identity binding the library is supposed to enforce is: `HMAC-verified bytes == bytes used to determine the tenant (shop)`. Because the header carrying `shop` is outside the HMAC-signed payload, an attacker who can influence or spoof this header (e.g. a host application that passes through arbitrary headers, a proxy misconfiguration, or a compromised/duplicated endpoint receiving legitimate Shopify traffic for one shop but forwarding it under a different `shop-domain` header) can cause `WebhookMetadata.shop` — and therefore the tenant context handed to the app's own webhook handler — to diverge from the shop whose data actually produced the signed body. This is the exact bug-class from the report: a field (`shop`) that is *acted on* (used to key the tenant's DB writes) but *not covered by the verification* (HMAC only signs `@raw_body`).

### Impact Explanation
If the host application trusts `WebhookMetadata#shop` to select/scope a merchant's `Session`/tenant record (a very common pattern, since HMAC validity is treated as proof of shop-authenticity), this breaks the equality `verified_shop == acted_on_shop`, enabling one shop's webhook payload to be recorded/applied to another shop's tenant record — a cross-tenant data-integrity/authentication issue. This matches the report's underlying pattern: an identity field is trusted operationally without being bound by the cryptographic check that is supposed to authenticate it.

### Likelihood Explanation
Exploitability depends entirely on whether the surrounding host infrastructure (load balancer, ingress, custom middleware) allows the `X-Shopify-Shop-Domain` header to be set/overridden independently of the signed body — the gem itself does nothing to prevent or detect this mismatch, and does not cross-check `shop` against any signed field (e.g. shop domain embedded in the body for topics that include it). This is a design gap in the gem rather than a guaranteed exploit in all deployments, so likelihood is moderate and infrastructure-dependent.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`) header values in the HMAC-signed material used by `to_signable_string`, or otherwise require the caller to cross-verify the header-derived `shop` against a shop identifier embedded in the signed body before dispatching to a tenant-specific handler.

### Proof of Concept
1. Attacker (or misconfigured intermediary) forwards a legitimately-signed webhook body from Shop A but rewrites/duplicates the request with `X-Shopify-Shop-Domain: shop-b.myshopify.com`.
2. `Utils::HmacValidator.validate(request)` succeeds because it only checks `@raw_body`, which is untouched. [4](#0-3) 
3. `Registry.process` calls the handler with `WebhookMetadata.new(... shop: request.shop ...)`, where `request.shop` now reads `shop-b.myshopify.com`. [5](#0-4) 
4. The app's handler, trusting the "verified" webhook, writes/updates data under Shop B's tenant context, even though the payload originated for Shop A.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
