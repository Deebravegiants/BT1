## Finding

### Title
Webhook shop/topic/webhook_id identity is trusted from unauthenticated headers while HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop`, `topic`, `webhook_id`, and `api_version` values that are handed to the app's webhook handler entirely from HTTP headers, but `to_signable_string` — the value the HMAC is computed and verified over — returns only the raw request body. This is the same class of bug as the referenced report: a value that downstream code treats as authenticated (the tenant/shop identity) is accessed/trusted through a channel (headers) that is disjoint from the value that is actually cryptographically bound (the body).

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes/compares the HMAC solely against `to_signable_string`: [2](#0-1) 

Yet `Registry.process` treats a passing HMAC check as proof the whole request — including the header-derived `shop`, `topic`, `webhook_id`, and `api_version` — came from Shopify for that specific shop, and forwards those header values unauthenticated into the handler: [3](#0-2) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors all read from HTTP headers, which are not part of `to_signable_string`: [4](#0-3) 

The documentation reinforces the false guarantee, telling integrators that calling `Registry.process` "will verify the request did indeed come from Shopify": [5](#0-4) 

and that `data.shop` is a trustworthy field to key business logic on: [6](#0-5) 

Because the app's `client_secret`/`api_secret_key` is shared across every shop that installs the app, any merchant (an unprivileged party with respect to other tenants) can install the app on their own store, receive a webhook with a valid HMAC over a body they control, and then replay that exact `raw_body`/HMAC pair to the app's public webhook endpoint while substituting the `shopify-shop-domain` (and/or `shopify-topic`, `shopify-webhook-id`) header to name a victim shop. `HmacValidator.validate` will still succeed because it never looks at those headers, and `Registry.process` will invoke the handler with `WebhookMetadata.shop` set to the victim's domain.

The identity binding that should hold is:
`shop_header_used_by_handler == shop_that_the_HMAC_actually_authenticates`
but in this implementation the right-hand side does not exist — the HMAC authenticates nothing about the shop, topic, or webhook id at all, only the body bytes.

### Impact Explanation
This breaks the tenant boundary that `Registry.process`/`WebhookMetadata` is documented to provide: an attacker who is a legitimate (but unprivileged, non-victim) merchant of the app can make the app believe attacker-controlled webhook data originated from a different, victim shop. If the host app uses `data.shop` (as the docs instruct) to key per-tenant state — e.g., to decide which shop's session/access token to look up, which shop's data to overwrite, or to trigger shop-scoped side effects like `app/uninstalled` cleanup — this yields cross-tenant data corruption/spoofing driven entirely by an unprivileged internet user. This matches the Critical "cross-tenant access" impact class in scope.

### Likelihood Explanation
Likelihood is Medium: exploitation requires the attacker to (a) install the target app on their own shop to obtain a legitimately-HMAC-signed webhook body, and (b) send a crafted HTTP request with a different `shopify-shop-domain`/`shopify-topic` header to the app's public webhook callback URL — both trivially achievable by any developer/merchant who can install a Shopify app, with no access to the app's `client_secret` or any victim credentials required.

### Recommendation
Bind the shop/topic/webhook identity into the HMAC-verified material, or otherwise establish shop identity from an authenticated source instead of `Request#shop`/`#topic`/`#webhook_id`/`#api_version`. Options:
- Have `to_signable_string` return a canonical representation that includes the shop domain, topic, and webhook id headers alongside the body, and update the verification/registration flow to match Shopify's documented header set actually intended to be trusted.
- If Shopify's real HMAC only ever covers the body (matching Shopify's actual webhook design), update the documentation and `WebhookMetadata` contract to explicitly warn that `shop`/`topic`/`webhook_id` are unauthenticated header values that must be cross-checked against the app's own webhook subscription registry (e.g., confirm the `webhook_id` was actually registered for the claimed `shop`) before being used for any tenant-sensitive decision.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and lets Shopify deliver a real webhook, e.g. `orders/create`, with body `B` and header `shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
2. Attacker replays the exact same `B`/`H` to the app's public webhook endpoint but sets `shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `shopify-topic`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC-SHA256(client_secret, B) == H` — this passes because `B` and `H` are unchanged. [7](#0-6) 
4. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled>, ...)`, and any app logic that trusts `data.shop` per the documented contract now acts on attacker data under the victim shop's identity.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
