### Title
Webhook `shop`/`topic` identity not bound by HMAC, enabling cross-tenant webhook spoofing via header substitution - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body (`to_signable_string` returns `@raw_body`), while the tenant-identifying `shop-domain` header, the `topic` header, and the `webhook-id`/`api-version` headers are read directly and trusted without being included in the signed content. An unprivileged internet user who can obtain any single valid `(raw_body, hmac)` pair signed with the app's `client_secret` — for example a webhook payload for their own trial/development shop, which Shopify legitimately delivers to them — can replay that exact body+HMAC to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. `HmacValidator.validate` will accept it because it never inspects the header values, and `Registry.process` will invoke the registered handler with attacker-chosen `shop` bound to Shopify-body content the attacker did not actually receive for that shop.

### Finding Description
`HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it only to the `hmac` field: [4](#0-3) 

For webhooks, `to_signable_string` is defined as just the raw body: [5](#0-4) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from attacker-controllable HTTP headers with no cryptographic binding to the signature: [6](#0-5) 

`Registry.process` trusts these header-derived values directly to authorize dispatch and to build the metadata handed to the app's business logic: it raises only if the HMAC over the body fails, then looks up the handler by the unauthenticated `topic` and constructs `WebhookMetadata` using the unauthenticated `shop`: [3](#0-2) 

The identity binding that should hold is: `shop_that_HMAC_authenticates == shop_the_handler_acts_on`. Because the HMAC covers only bytes of the body, this equality does not hold — the `shop` (and `topic`) the handler acts on is whatever the attacker puts in the header, not what the signature actually authenticates. This is the same class of defect as the reported bug: an identity/authorization-relevant attribute (`admin`/here `shop`) is mutable/settable through a path that bypasses the check that is supposed to bind it (the `ensureContract` check there; the HMAC-over-body-only here).

### Impact Explanation
This breaks the tenant boundary the HMAC is meant to enforce for a multi-tenant Shopify app: any internet user who can capture one legitimate `(body, hmac)` webhook pair (e.g., from their own shop, or from any shop that installed the same app and whose webhook traffic they can observe, including over plaintext logs, browser devtools proxies, or their own test store) can replay it against the app's public webhook receiver endpoint with a forged `shop-domain` header, causing the app to process that payload as if it belongs to a different, arbitrary shop/tenant. Depending on the handler (e.g., `customers/redact`, `shop/redact`, `orders/*` handlers that write to per-shop storage), this enables cross-tenant data corruption or triggering of privileged per-shop side effects (like redaction of another shop's data) under an attacker-chosen shop identity, which the gem itself asserts is authenticated (`Registry.process` only raises on HMAC failure, implying "authenticity of the message, including its shop attribution" was checked).

### Likelihood Explanation
Exploitation requires no secrets: the attacker only needs one valid webhook body+HMAC pair for any shop that runs the target app (trivially obtainable by installing the app on the attacker's own free/dev shop, since Shopify signs the webhook with the same `client_secret` for all shops using that app) and network access to the app's webhook endpoint, which is public by design. No `api_secret_key`, access token, or privileged account is needed beyond what any developer/merchant already can obtain for their own store.

### Recommendation
Include the tenant/message-identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed content, or otherwise cryptographically bind them to the body (e.g., include them as part of `to_signable_string`), so that `HmacValidator.validate` fails if any of these attacker-visible headers are altered relative to what Shopify actually signed for that delivery.

### Proof of Concept
1. App developer installs their own Shopify app on shop `attacker-shop.myshopify.com` and registers a webhook handler for `customers/redact` via `ShopifyAPI::Webhooks::Registry.add_registration`.
2. Shopify delivers a legitimate webhook to the app for `attacker-shop.myshopify.com`: headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: customers/redact`, `x-shopify-hmac-sha256: <valid HMAC over raw body>`, plus the raw JSON body.
3. Attacker captures this exact `(raw_body, hmac)` pair (from their own store's webhook logs/traffic — no secret needed).
4. Attacker POSTs to the app's public webhook endpoint the same `raw_body` and `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `HmacValidator.validate` calls `to_signable_string`, which returns only `raw_body`, computes the HMAC over it, and it matches — validation succeeds. `Registry.process` invokes the handler with `WebhookMetadata` where `shop == "victim-shop.myshopify.com"`, an identity the attacker was never authenticated for.
