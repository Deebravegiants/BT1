Confirmed: `Utils::VerifiableQuery` requires only `hmac` and `to_signable_string`, and `Webhooks::Request#to_signable_string` returns only `@raw_body`. All identity fields (`shop`, `topic`, `webhook_id`, `api_version`) are read straight from HTTP headers and are never part of the signed bytes, yet `Registry.process` trusts `request.shop`/`request.topic` for dispatch after only checking the body's HMAC.

### Title
Webhook shop/topic identity not bound to HMAC allows cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` values used for dispatch and handed to the app's handler are read from unauthenticated HTTP headers and are never included in the HMAC-signed bytes [2](#0-1) .

### Finding Description
`Webhooks::Request` includes `Utils::VerifiableQuery`, whose `to_signable_string` for this class returns only `@raw_body` [3](#0-2) . The `hmac`, `topic`, `shop`, `api_version`, and `webhook_id` accessors are all parsed independently from HTTP headers, outside the signed payload [4](#0-3) . `HmacValidator.validate` only recomputes the HMAC over `to_signable_string` and compares it to the `hmac` header [5](#0-4) , so it proves that the *body bytes* were signed with the app's `client_secret` — it proves nothing about which shop or topic that signature was originally issued for. `Registry.process` then dispatches using the unauthenticated `request.shop` and `request.topic` values directly: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [6](#0-5) .

Because the app's `client_secret` (and thus the HMAC key) is identical for every shop that installs the app, a valid `(raw_body, hmac)` pair captured from one legitimately-installed shop (e.g., an attacker's own development/trial store, or a webhook payload obtained via a public endpoint/log) remains cryptographically valid when replayed with the `shop`/`topic`/`webhook-id` headers rewritten to name a different, victim shop. The gem provides no mechanism, and performs no check, binding the claimed `shop` header to the signature — breaking the equality that should hold: `shop authenticated by HMAC == shop acted upon by the handler`.

### Impact Explanation
This breaks tenant isolation for any host application that trusts `WebhookMetadata#shop` (or `#topic`) to select the tenant record to mutate — which is the intended, documented usage of `Registry.process`. An attacker who can obtain one valid signed webhook body (trivial: install the app on a shop they control, or generically observe/replay a body of a topic they can generate) can forge webhooks that Registry.process will accept and dispatch as originating from an arbitrary victim shop domain, since the shop identity is not part of what is cryptographically verified. This can lead to cross-tenant data corruption or unauthorized actions (e.g., processing "customers/data_request" or "shop/redact" mandatory compliance webhooks, or any handler that keys off `data.shop`, against a victim's tenant), satisfying the "cross-tenant access" impact class.

### Likelihood Explanation
Likelihood is bounded by the need to first obtain one valid `(body, hmac)` pair signed with the app's secret — reachable without any privileged credentials by installing the app on an attacker-owned store (a normal, unprivileged flow for any public app) or by generating a webhook with attacker-controlled body content for a topic under the attacker's own shop, then replaying it against the same public webhook endpoint with a forged shop header. No access to `api_secret_key` or any merchant token is required.

### Recommendation
Either bind the shop/topic identity into the signed payload verification path (e.g., independently look up the shop associated with the webhook via a Shopify-side confirmation call, or require callers to cross-check `request.shop` against the app's own list of installed shops before trusting it), or clearly document that `WebhookMetadata#shop`/`#topic` are unauthenticated and must not be used as the sole tenant selector without additional server-side verification. At minimum, `Registry.process` should not silently hand unauthenticated `shop`/`topic` values to handlers as if they were part of the verified payload.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a legitimate webhook, e.g. for `orders/create`, with body `B` and header `X-Shopify-Hmac-SHA256: H` (valid because `H = HMAC(client_secret, B)`).
2. Attacker resends the exact same `B`/`H` to the app's public webhook endpoint, but replaces `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com` and, if desired, changes `X-Shopify-Topic`/`X-Shopify-Webhook-Id`.
3. `Utils::HmacValidator.validate(request)` succeeds because it only checks `H` against `B` [7](#0-6) ; `request.shop` and `request.topic` are taken from the forged headers unchecked [8](#0-7) .
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host app to act on the victim tenant using attacker-supplied body content.
