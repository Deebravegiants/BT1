## Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) headers are not covered by the HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request **body**. The `shop` (and `topic`, `webhook_id`, `api_version`) values are read directly from HTTP headers that are **not included** in the signed payload, then handed to the app's handler as trusted tenant identity. An attacker who legitimately receives webhooks for their own (attacker-controlled) shop can replay the exact same valid `body` + `hmac` pair while substituting an arbitrary `shop-domain` header, causing the gem to report the event as belonging to a victim shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body:

```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

`shop` is parsed straight from a header with no cryptographic binding to the body:

```ruby
sig { returns(String) }
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [2](#0-1) 

`Registry.process` validates only the HMAC of that request (i.e., only the body), then forwards the unauthenticated `shop` value to the app's handler as the identified tenant:

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [3](#0-2) 

Because Shopify webhook HMACs use the same app-wide `api_secret_key` for every shop that has the app installed (there is no per-shop signing key in this gem), any unprivileged merchant who has the app installed can obtain a genuine `(body, hmac)` pair for their own shop's webhooks, then replay that same pair while overwriting the `shopify-shop-domain` (or `x-shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` will still succeed because it only re-computes and compares the HMAC of `@raw_body`:

```ruby
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [4](#0-3) 

This breaks the identity binding: **`shop header value` == `shop that produced/authorized the body`** is never enforced — the gem validates "these bytes are authentic for this secret" but the "which shop this belongs to" field is never verified as tied to those same bytes.

### Impact Explanation
This is a cross-tenant confusion/spoofing primitive: a host application that (reasonably, given the gem's API) trusts `WebhookMetadata#shop` to route webhook processing per-tenant (e.g., updating tenant-scoped billing state, disabling a plan, processing `app/uninstalled`, GDPR data requests, or fulfilling per-shop business logic keyed off `data.shop`) can be made to attribute an attacker-crafted event to a shop the attacker does not control, since the gem itself asserts the request passed HMAC validation. This satisfies the Critical "cross-tenant access" impact criterion, since the authenticity guarantee the gem provides (`HmacValidator.validate`) is being relied upon by downstream apps to also vouch for the `shop` field, when in fact it does not.

### Likelihood Explanation
Any merchant with the target app installed can trivially capture one legitimate webhook (body + valid signature) from their own store — no special access, TLS interception, or secret leakage required — and replay it with a modified `shop-domain` header against the app's webhook endpoint. This requires only standard HTTP client tooling.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`, `api_version`) values as part of the string covered by the HMAC comparison used in webhook processing, or independently verify that the reported `shop` matches a shop that has an active, previously-established session/installation record before trusting `WebhookMetadata#shop`. At minimum, the gem's documentation should explicitly warn that `shop` on `WebhookMetadata` is unauthenticated and must be cross-checked against known installed shops by the consuming app.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker.myshopify.com`.
2. Attacker triggers an event (e.g., `orders/create`) and captures the resulting webhook: raw body `B` and header `shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker replays the exact same request to the app's webhook endpoint, keeping body `B` and header `shopify-hmac-sha256: H` unchanged, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(api_secret_key, B) == H` — this still passes.
5. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, i.e., the app processes attacker-supplied data attributed to the victim shop. [5](#0-4) [3](#0-2)

      end

      sig { returns(T::Hash[String, T.untyped]) }

      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end
