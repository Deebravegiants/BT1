## Title
Webhook `shop-domain` (and topic/API-version) Headers Are Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

## Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop-domain` header — the value the gem hands to the app's webhook handler as the tenant identifier — is never included in the signed bytes. Since a single app has one `api_secret_key` shared across every installed shop, anyone who can obtain (or produce) a validly-HMAC-signed body for their own shop's webhook can replay that body with a forged `x-shopify-shop-domain` header pointing at a victim shop, and the signature check will still pass.

## Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` values are all read straight from unauthenticated headers: [2](#0-1) 

`HmacValidator` verifies the signature purely against `verifiable_query.to_signable_string` (i.e. the body) with the app's shared secret: [3](#0-2) 

`Registry.process` trusts the HMAC check as the sole authenticity gate, then dispatches the handler using `request.shop` taken directly from the unauthenticated header: [4](#0-3) 

This breaks the intended identity binding: `shop-domain claimed in header == shop-domain authenticated by HMAC`. In reality the binding only holds for `body == HMAC-verified bytes`; the shop identity riding alongside it is unauthenticated. Because the `api_secret_key` is per-app (not per-shop), a valid signature computed for shop A's webhook body remains valid when the same body/signature pair is replayed with shop B's domain in the header — the gem has no mechanism to detect the mismatch.

## Impact Explanation
This is a cross-tenant identity confusion: an app relying on `WebhookMetadata#shop` (built directly from `request.shop`) to scope side effects (e.g. mandatory compliance webhooks like `customers/redact` or `shop/redact`, or any handler that writes/deletes data keyed by shop) can be made to act on behalf of a shop the attacker does not control, using a signature the attacker legitimately obtained from their own store's traffic. This matches the Critical "cross-tenant access" impact category, since it lets an unprivileged actor cause the app to process events under another merchant's identity without ever possessing that merchant's credentials.

## Likelihood Explanation
Exploitation requires an attacker to control at least one shop that can trigger webhooks to the same app (trivial — install the app on a free development store, or trigger any subscribed webhook topic), capture the resulting `(raw_body, hmac)` pair, and resend it directly to the app's public webhook endpoint with a rewritten `shop-domain` header. No secret material is needed since the HMAC is body-only and thus reusable across shops on the same app.

## Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-signable string, or otherwise cryptographically bind the header-derived `shop` value to the verified payload before it is exposed via `WebhookMetadata`, so that a signature valid for one shop's webhook cannot be replayed with a different shop's identity.

## Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a subscribed webhook topic (or crafts any JSON body); Shopify (or the attacker, if they can compute HMAC using knowledge of their own installation flow for a topic they can also self-trigger) delivers `raw_body` with header `x-shopify-hmac-sha256: <valid-hmac-of-raw_body-using-shared-secret>`.
2. Attacker captures this `(raw_body, hmac)` pair.
3. Attacker POSTs the same `raw_body` and `hmac` header directly to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` in [5](#0-4)  passes because it only checks `raw_body` against the shared `api_secret_key`.
5. `Registry.process` in [4](#0-3)  dispatches to the handler with `shop: "victim-shop.myshopify.com"`, letting the attacker's payload be processed under the victim's tenant context.
