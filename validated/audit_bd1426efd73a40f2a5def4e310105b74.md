### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) headers are not covered by the HMAC signature, allowing tenant spoofing on webhook delivery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used by `ShopifyAPI::Webhooks::Registry.process` to route and label the webhook come from unsigned HTTP headers. This breaks the binding "shop verified by HMAC == shop trusted for tenant routing," letting anyone who has legitimately received one valid `(body, hmac)` pair for their own store replay that exact request with a forged `X-Shopify-Shop-Domain` header pointing at a different (victim) shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Registry.process` validates the HMAC over that signable string, then builds the metadata handed to the app's handler using `request.shop`, `request.topic`, and `request.webhook_id`, none of which are part of what was HMAC-verified: [2](#0-1) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all pulled directly from attacker-suppliable HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) with no cross-check against the signed body: [3](#0-2) 

The identity binding that should hold is:
`shop_authenticated (bound into HMAC) == shop_used_for_tenant_dispatch (WebhookMetadata#shop)`

In this implementation that equality does not hold — `shop_used_for_tenant_dispatch` is taken from a header that is entirely outside the HMAC's scope, so it can be swapped freely as long as the `(raw_body, hmac)` pair stays intact.

### Impact Explanation
An unprivileged internet user who installs the target app on their own (attacker-controlled) shop will receive genuine webhook deliveries from Shopify for real events on that shop — each with a valid `X-Shopify-Hmac-SHA256` computed over the body using the app's real secret. Because the signature covers only the body, the attacker can capture one such `(body, hmac)` pair and replay it directly to the app's public webhook endpoint while substituting the `shopify-shop-domain` header (and, if useful, `shopify-topic`/`shopify-webhook-id`) with a victim shop's domain or an arbitrary value. `Utils::HmacValidator.validate` still passes because it only checks the body against the signature, and `Registry.process` will invoke the app's handler believing the event belongs to the victim shop. Any app logic that trusts `WebhookMetadata#shop` for tenant identification (e.g., updating per-shop settings, revoking data, crediting/debiting a shop record) can be tricked into acting on the wrong tenant — a cross-tenant integrity/confidentiality violation.

### Likelihood Explanation
Likelihood is high for any app that exposes a public webhook endpoint (a documented, required configuration for this gem) and trusts `WebhookMetadata#shop`/`topic` for dispatch, since:
- No credentials beyond running one's own normal, unprivileged Shopify store are required.
- The webhook endpoint is by design public and reachable by anyone on the internet.
- Nothing in `Webhooks::Request` or `Registry` binds the header-derived shop/topic to the signed payload.

### Recommendation
Include the header values that drive dispatch (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signable content, or otherwise cryptographically bind them to the body (e.g., verify them against fields embedded in the JSON payload) before using them for tenant routing in `Registry.process` and `WebhookMetadata`.

### Proof of Concept
1. Attacker creates their own development/test shop and installs the target app, enabling delivery of a real webhook (e.g. `orders/create`) to the app's public endpoint.
2. Attacker captures the full legitimate request: raw JSON body `B` and header `X-Shopify-Hmac-SHA256: H` (valid because `HMAC-SHA256(secret, B) == H`).
3. Attacker resends an HTTP POST to the same endpoint with the identical body `B` and header `H`, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "shopify-shop-domain" => "victim-shop.myshopify.com", "shopify-hmac-sha256" => H})` is constructed; `Utils::HmacValidator.validate(request)` succeeds since it only checks `B` against `H`: [4](#0-3) 
5. `Registry.process(request)` dispatches to the registered handler with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, causing the app to process attacker-supplied data under the victim shop's identity.
