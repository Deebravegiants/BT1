### Title
Webhook `shop`, `topic`, and `webhook_id` fields are trusted from unauthenticated HTTP headers while the HMAC signature only covers the raw body, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` from HTTP headers, but the HMAC signature validated by `Utils::HmacValidator` only covers the raw request body. Any shop that legitimately receives real, validly-signed webhook deliveries from Shopify for its own events can replay that exact (body, HMAC) pair to the app's webhook endpoint while substituting a different `shop-domain` header. The signature will still validate — because it never covered the shop/topic identity — and the handler will be invoked believing the event belongs to a different tenant.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the HMAC solely against `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw body: [2](#0-1) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from request headers, which are never included in the signed material: [3](#0-2) 

`Registry.process` validates only the HMAC of the request, then immediately trusts `request.shop` (a header value) to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The identity binding that should hold is:
`shop authenticated by HMAC == shop acted upon by the handler`

In this implementation that equality never holds, because the HMAC is computed over the body alone while `shop` (and `topic`/`webhook_id`) come from unauthenticated headers. Any actor who can obtain one legitimately-signed (body, HMAC) pair — which every shop installing the app receives continuously as normal Shopify webhook traffic for its own store — can resend that exact body with the HMAC unchanged but the `shop-domain` (and/or `topic`/`webhook-id`) header altered to name a different shop. `Utils::HmacValidator.validate` still returns `true` because the signable string (the body) is unmodified, so `Registry.process` dispatches the handler with attacker-chosen `shop`/`topic` metadata paired with body content the attacker did not need the `client_secret` to produce.

### Impact Explanation
This breaks the tenant boundary the HMAC check is supposed to enforce: a shop with no special privileges relative to other tenants of the same app can cause the host application's webhook handler to process events under a spoofed `shop` value. Since apps commonly key data updates, order/inventory sync, and access-token lookups off `WebhookMetadata#shop`, this can lead to cross-tenant data corruption or disclosure — writing another merchant's data, or triggering privileged per-shop actions (e.g. reprocessing billing/order state) using a legitimate signed payload attributed to the wrong store. This matches the "cross-tenant access" critical-impact category, since no access token, `api_secret_key`, or other privileged credential is needed — only externally observable, replayable HTTP traffic that any shop naturally receives.

### Likelihood Explanation
Any merchant that has installed the app is, from Shopify's perspective, an "unprivileged internet user" with respect to other merchants' data. Such a user has continuous, legitimate access to valid (body, HMAC) pairs — every real webhook Shopify sends to the app for their store is delivered over plain HTTP(S) to their own network/server, or can be observed via the app's public webhook endpoint if the developer logs/echoes raw payloads. Replaying that exact body against the app's webhook endpoint with a modified `shop-domain` (or `topic`/`webhook-id`) header requires no cryptographic secret at all — the HMAC needs no recomputation. The only precondition is that the host application (built on this gem, per its documented API) trusts `WebhookMetadata#shop`/`#topic` as returned by this library, which is exactly the gem's documented contract in `docs/usage/webhooks.md`.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, and ideally `webhook-id`) in the signable material used by `HmacValidator`, or otherwise bind them to the signed body (e.g., by having `Registry.process` reject requests where the header-derived `shop` does not match a shop value embedded in, and covered by, the signed payload). At minimum, document prominently that `WebhookMetadata#shop`/`#topic` are unauthenticated header values and must not be trusted for tenant-scoping decisions unless cross-checked against an independently known session/shop record.

### Proof of Concept
1. Shop A installs the app and receives (from Shopify) a real webhook: `raw_body = '{"id": 1}'`, headers include `x-shopify-hmac-sha256: <valid HMAC of raw_body with the shared client_secret>`, `x-shopify-shop-domain: shop-a.myshopify.com`.
2. The attacker (operator of shop A, or anyone who intercepts/replays this legitimate delivery) resends the identical `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers successfully (headers are only checked for presence, not integrity): [5](#0-4) 
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because `to_signable_string` returns only `raw_body`, unchanged from the legitimate delivery.
5. The handler is invoked with `WebhookMetadata.new(shop: "shop-b.myshopify.com", ...)`, causing the host application to act on shop A's data as if it belonged to shop B.

```ruby
      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
```
