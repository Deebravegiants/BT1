## Analysis

The `WithdrawProxy` report describes a bug class where a value used to gate/route sensitive behaviour (`totalAssets()`) can be set by an unprivileged path that bypasses the intended trusted-source binding (`PublicVault.transferWithdrawReserve`). The closest reachable analog in this Ruby gem is the webhook processing pipeline, where the tenant identity (`shop`) is *acted on* by the app but is **not covered by the HMAC signature** that the gem uses to assert "this request came from Shopify."

### Root cause

`ShopifyAPI::Webhooks::Request` extracts `hmac` and computes `to_signable_string` from the raw body only: [1](#0-0) 

Critically, `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers, which are never included in `to_signable_string`: [2](#0-1) 

`Utils::HmacValidator.validate` only verifies `verifiable_query.hmac` against `verifiable_query.to_signable_string` (i.e. the raw body bytes), using `Context.api_secret_key`: [3](#0-2) 

`Registry.process` performs exactly this body-only check, then immediately trusts `request.shop` (a header, not covered by the HMAC) to build the `WebhookMetadata` handed to the app's handler: [4](#0-3) 

The gem's own documentation asserts the stronger guarantee that `Registry.process` "will verify the request did indeed come from Shopify," and explicitly tells integrators that `data.shop` is "The shop domain of the webhook" — implying it's an authenticated, trustworthy field: [5](#0-4) [6](#0-5) 

### The broken identity binding

The equality the gem should enforce is:

`bytes cryptographically verified by HMAC == bytes the tenant identity (shop) is derived from`

but the actual state is:

`bytes cryptographically verified by HMAC (raw body) != bytes shop is derived from (x-shopify-shop-domain header)`

Since `api_secret_key` is a single static per-app secret (not per-shop), any legitimately-signed `(body, hmac)` pair obtained from a genuine Shopify delivery — for example, one delivered to an attacker's own dev/test store where the app is installed — remains **valid** even when replayed directly to the app's public webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop. `HmacValidator.validate` will pass (body/hmac untouched), yet `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload belongs to the victim shop.

### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers. `HmacValidator` only proves the body was signed with the app's static `api_secret_key`; it proves nothing about which shop the request is for. `Webhooks::Registry.process` nonetheless treats `request.shop` as trustworthy and forwards it to the app's handler as the webhook's shop of origin.

### Finding Description
Any entity that can obtain one genuinely Shopify-signed `(raw_body, x-shopify-hmac-sha256)` pair — e.g. an attacker who installs the target app on their own store and captures a webhook delivery — can replay that exact body/HMAC pair directly to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (and `x-shopify-topic`/`x-shopify-webhook-id`) header. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` will still return `true` because it only recomputes the HMAC over the raw body, and `Registry.process` will dispatch the handler with `WebhookMetadata.shop` set to the attacker-chosen victim shop domain, per `lib/shopify_api/webhooks/registry.rb` lines 188-200.

### Impact Explanation
This breaks the tenant boundary the gem's documentation promises ("will verify the request did indeed come from Shopify" / `data.shop` is "the shop domain of the webhook"). A host application that reasonably trusts `data.shop` (as instructed by the gem's own usage docs) to select which tenant's records to update will process an attacker-controlled payload under another merchant's tenant identity — cross-tenant data corruption/injection reachable purely through the gem's documented API and public webhook endpoint.

### Likelihood Explanation
Requires only: (1) the ability to install/run the target app on an attacker-controlled store to obtain one legitimately-signed webhook of any topic, and (2) direct HTTP access to the app's public webhook endpoint (which by design is unauthenticated and internet-reachable). No `api_secret_key`, access token, or privileged account is required.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-covered signable string (or otherwise cryptographically bind them to the payload), and/or require the caller to independently confirm `request.shop` corresponds to an actual installed/authorized shop before trusting it, mirroring the recommendation pattern from the referenced report of not inferring safety/identity from data that sits outside the verified boundary.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`; Shopify delivers a real webhook with body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's `api_secret_key`).
2. Attacker captures `(B, H)` and issues a direct POST to the app's `/webhook` endpoint with `raw_body: B`, header `x-shopify-hmac-sha256: H` (unchanged, still valid), but `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it checks `B` against `H` only (`lib/shopify_api/utils/hmac_validator.rb` lines 12-22, `lib/shopify_api/webhooks/request.rb` lines 10-38).
4. `Registry.process` invokes the app handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)` (`lib/shopify_api/webhooks/registry.rb` lines 198-199), causing the host app to process attacker-controlled webhook data under the victim tenant's identity.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
