## Finding

### Title
Webhook `shop` identity is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authenticated once `Utils::HmacValidator.validate(request)` returns true, and then hands the caller's handler a `WebhookMetadata` object built from `request.shop`. However, the HMAC signature only covers the raw request body — it does not cover the `shop-domain` header. An attacker who can produce (or simply replay) a validly-signed webhook body for their own tenant can freely rewrite the `x-shopify-shop-domain` / `shopify-shop-domain` header to any other shop, and the library will report that forged shop identity to the host application as authenticated.

### Finding Description
The equality that should hold is: `HMAC-verified(bytes) == identity claimed to the application (shop)`. In this gem it does not:

- `Webhooks::Request#to_signable_string` returns only the raw body: `to_signable_string` → `@raw_body`. [1](#0-0) 

- `Webhooks::Request#shop` is read straight from an attacker-controlled header, independent of the signed bytes: [2](#0-1) 

- `HmacValidator.validate` only calls `validate_signature`, which HMACs `verifiable_query.to_signable_string` (i.e., the body) and compares it to the received `hmac`. It never touches `shop`: [3](#0-2) 

- `Registry.process` gates entirely on this body-only HMAC check, then constructs `WebhookMetadata` using the unauthenticated `request.shop` and dispatches it to the app's handler as trusted data: [4](#0-3) 

Because `shop` is excluded from the signable string, two different byte-streams — "this body really came from shop A" and "this body really came from shop B" — collapse to the same accepted signature as long as the body itself is unmodified. The `shop` field is exactly the kind of "field acted on but not covered by the HMAC" the report's bug class describes: `WrappedVault` failed to move the internal accounting (Dahlia shares) when the externally-visible balance (wrapped shares) moved; here the externally-reported identity (`shop`) is not moved/bound together with the thing that was actually authenticated (the body).

### Impact Explanation
Any party that can obtain one legitimately HMAC-signed webhook payload for their own installed shop (which is trivial — install the app on a store you control and capture the webhook Shopify sends you) can replay that exact body with a rewritten shop-domain header. `Registry.process` will pass validation and invoke the app's handler with `WebhookMetadata#shop` set to the attacker-chosen value. If the host application uses `data.shop` from `Registry.process` to select which tenant's data to update (a documented, expected usage pattern per the gem's own webhook docs, which describe `process` as verifying "the request did indeed come from Shopify"), this results in cross-tenant data confusion/write, i.e., cross-tenant access — one of the explicitly in-scope Critical impacts.

### Likelihood Explanation
Exploitation requires only an app installation the attacker already legitimately controls (unprivileged internet user relative to the target tenant) plus the ability to send an arbitrary HTTP request to the app's own webhook endpoint with attacker-controlled headers and a captured valid `(body, hmac)` pair — no access token, `api_secret_key`, or victim credentials are needed. The only mitigating factor is that this depends on the host application trusting `WebhookMetadata#shop` for tenant selection without independently correlating it against the specific webhook subscription/endpoint that was hit, which is the intended and documented usage of `Registry.process`.

### Recommendation
Bind `shop` (and ideally `topic`) into the signed material verified for webhooks, or otherwise cryptographically tie the header-supplied shop to the HMAC check — e.g., include the `shop-domain` header in `to_signable_string` for `Webhooks::Request`, or have `Registry.process` independently validate that `request.shop` matches an expected/registered shop for the resolved handler/session before constructing `WebhookMetadata`.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com`; trigger any webhook topic the app is registered for and capture the raw POST: headers (`x-shopify-hmac-sha256`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic`) and raw body.
2. Replay the exact same request to the app's webhook endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com` (leave body/HMAC untouched).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` → true (HMAC only covers the unchanged body), then builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and invokes the registered handler with that value.
4. Any handler logic keyed on `data.shop` (e.g., "look up victim-shop's session/settings and apply this webhook's data") now operates in the wrong tenant's context, confirming cross-tenant identity confusion caused solely by the shop field not being covered by the HMAC.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
