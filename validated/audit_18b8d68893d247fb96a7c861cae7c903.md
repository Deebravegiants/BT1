### Title
RAY-value overflow during accrual permanently freezes a saturated market, stranding all supplier funds and making attacker debt uncollectible — ([File: common/src/rates/index.rs](common/src/rates/index.rs))

### Summary
A heap overflow writes more data than a fixed buffer can hold. The on-chain analog here is the fixed-width `i128` RAY domain: interest accrual computes `borrowed * borrow_index` and `supplied * supply_index` as i128/RAY products. When a market's scaled borrow balance is large enough that compounded interest pushes `borrowed × borrow_index` past `i128::MAX`, the accrual panics with `MathOverflow` — and because every market operation calls `interest::global_sync` before mutating, the market freezes permanently with no recovery path.

### Finding Description
`update_borrow_index` caps the index at `MAX_BORROW_INDEX_RAY` (10^36), but the value product `borrowed * new_borrow_index` is computed before/regardless of that cap inside `calculate_supplier_rewards` (`common/src/rates/index.rs:80-81`) and inside utilization/shortfall math via `scaled_to_original` (`common/src/rates/scaling.rs:14-16`), which routes to `mul_div_*` in `common/src/math/fp_core.rs` and panics with `GenericError::MathOverflow` when the product does not fit i128 (`fp_core.rs:107-118`).

Every pool entrypoint runs `synced_market → interest::global_sync` first (`contracts/pool/src/ops/mod.rs:30-34`), which calls `accrue_step` per chunk (`contracts/pool/src/interest.rs:39-53`). Once the stored `borrowed` scaled shares times the next borrow index overflow, that panic is unconditional and permanent: it does not depend on caller input, only on ledger time having advanced past the cliff.

The integration test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-356`) demonstrates exactly this: a ~170-billion-token market at ~98% utilization panics with `MATH_OVERFLOW` inside `update_indexes`, and subsequent `try_withdraw_raw` and `try_repay` both fail with the same error while `borrow_index < MAX_BORROW_INDEX_RAY` (the cap never engages). `docs/reference/formulas.md:432-437` acknowledges the cliff: "Value overflow can occur before the index ceiling and block repayment/withdrawal because those operations accrue first."

Once frozen:
- `repay`, `withdraw`, `borrow`, `supply`, `seize_positions`, `claim_revenue`, `recapitalize`, `net_settle`, `flash_loan` all revert — every path loads a synced cache.
- Controller `liquidate`, `clean_bad_debt`, and `update_indexes` revert for any position touching the market, since they call the pool's accrue-first entrypoints.
- The bad-debt write-down (`apply_bad_debt_to_supply_index`) and `recapitalize` recovery paths are equally unreachable — both go through the same `global_sync`.

### Impact Explanation
Permanent freezing of user funds and protocol insolvency on an attacker-influenced path. A whale that supplies near the admitted cap (~170.14 billion whole tokens at the i128/10^(27-d) bound) and borrows to high utilization creates a market whose debt value grows ~9%/yr-compounding toward the i128 RAY ceiling while the index cap sits 10^9× above the starting index — the value product overflows first. After the cliff, all suppliers' deposits are permanently locked, and the attacker's own debt can never be repaid, liquidated, or written down: the attacker keeps the borrowed tokens while the position can never be closed. This is a "write overflows the buffer and corrupts/bricks the structure" primitive applied to the fixed i128 domain.

### Likelihood Explanation
Medium. The attack requires governance to have admitted a cap near the arithmetic maximum (the test had to `lift_caps` to reach the sizes needed), a very large capital commitment, and sustained high utilization over multiple years of accrual. No privileged action is needed at trigger time — `update_indexes` is permissionless and any later legitimate user's transaction detonates the panic. The trigger is irreversible: nothing can shrink `borrowed` or roll back the index once the product exceeds the domain, and `update_borrow_index`'s index ceiling does not bound the value product.

### Recommendation
Bound the admitted exposure so `borrowed × MAX_BORROW_INDEX_RAY` (and `supplied × MAX_SUPPLY_INDEX_RAY`) always fits i128: enforce a scaled-shares ceiling on `mint_debt`/`mint_supply` in `contracts/pool/src/cache/shares.rs` derived from `i128::MAX / MAX_*_INDEX_RAY`, independent of the asset-unit cap. Alternatively, make `accrue_step` saturate the *value* products (as `mul_div_floor_saturating` already does for `update_supply_index` at `common/src/rates/index.rs:41`) so accrual stalls at the index cap instead of trapping every entrypoint — combined with a `seize_positions`/recapitalize path that can still run when accrual is saturated.

### Proof of Concept
1. Governance lists an 18-decimal asset with a borrow/supply cap near the admitted maximum (the cap→scaled conversion itself is valid; per `docs/reference/formulas.md:413-417` an admitted borrow cap cannot saturate).
2. Attacker calls controller `supply` with ~1e29 base units (~170B whole tokens) and `borrow` for ~98% of it via a second account.
3. Time passes; each permissionless `update_indexes` compounds the borrow index. Because `borrowed × borrow_index` reaches i128::MAX while `borrow_index << 10^36`, the next accrual panics in `calculate_supplier_rewards`/`scaled_to_original`.
4. Permanent state: `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, `recapitalize` all revert with `MathOverflow` (error 33) — as asserted by `large_positions_and_long_horizons.rs:343-356`. Supplier deposits and the borrower's debt are frozen forever.

Caveat: `docs/reference/formulas.md` documents this cliff as an arithmetic limit, so the finding may be treated as a known limitation rather than a fixable defect; the report is included because the freeze is reachable end-to-end by an unprivileged borrower and the index cap fails to prevent it.
