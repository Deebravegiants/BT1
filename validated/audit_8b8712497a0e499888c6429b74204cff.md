### Title
Post-creation PodGroup priority escalation via Update bypassing admission and validation - ([File: plugin/pkg/admission/priority/admission.go])

### Summary
`Plugin.Admit` only routes `podGroupResource` requests through `admitPodGroup` on `admission.Create`, leaving `admission.Update` completely unchecked by the priority admission controller. Because `ValidatePodGroupUpdate` in `pkg/apis/scheduling/validation/validation.go` also only validates `ObjectMeta` and never checks immutability of `Spec.Priority`/`Spec.PriorityClassName`, an authenticated user with only `update` RBAC on `podgroups` can directly set an arbitrary `spec.Priority`/`spec.PriorityClassName` on an existing PodGroup with no re-validation against PriorityClass authorization.

### Finding Description
`Plugin.Admit` dispatches based on resource and operation: [1](#0-0) 
Only `admission.Create` triggers `admitPodGroup`; any `admission.Update` on `podgroups` falls through to `return nil`, meaning the priority-consistency check ("priority set in the pod group must match the priority computed based on the priority class") in `admitPodGroup` is never invoked for updates: [2](#0-1) 

Contrast this with `admitPod`, whose comment explicitly documents the expected safety net: "API validation prevents mutations to Priority and PriorityClassName, so any other changes will fail update validation and not be persisted" — and indeed `core.Pod`'s validation enforces this invariant on update. [3](#0-2) 

For PodGroup, no equivalent invariant exists. `ValidatePodGroupUpdate` only validates `ObjectMeta`: [4](#0-3) 

And the registry strategy's `ValidateUpdate`/`PrepareForUpdate` do not restore or immutable-check `Spec.Priority`/`Spec.PriorityClassName` — they only reset `Status` and drop feature-gated fields: [5](#0-4) 

As a result, a user with `update` RBAC on `podgroups` can submit an Update request setting `spec.Priority` to any integer (e.g. the value of a restricted/system PriorityClass) and/or `spec.PriorityClassName` to a PriorityClass they are not authorized to reference, and the request passes both admission (no-op on Update) and validation (only checks ObjectMeta) unchanged.

### Impact Explanation
This is a genuine admission/validation-completeness bypass leading to unauthorized priority escalation: a namespace-scoped, unprivileged-but-authenticated user with `update` permission on `podgroups` (no cluster-admin, no PriorityClass RBAC) can directly forge `spec.Priority`/`spec.PriorityClassName` to arbitrary values (including values matching high or system-reserved priority classes) after creation, entirely bypassing the priority admission controller's intended enforcement that priority values must be derived from an authorized PriorityClass. This affects the PodGroup itself and, by extension, all pods scheduled/gang-scheduled under it, since scheduling and preemption decisions for the group are driven by `Spec.Priority`. This matches the Kubernetes bug bounty class of "admission/validation bypass leading to privilege escalation" (persisted invalid/protected field + unauthorized elevation of scheduling priority).

### Likelihood Explanation
Preconditions are minimal: `update` verb on `podgroups` in a namespace, which is a common, low-privilege RBAC grant for workload-owning users/service accounts (they typically already have `create`/`update` on their own PodGroups). The exploit requires only a single `PUT`/`PATCH` request against `kube-apiserver` and is fully deterministic/repeatable — no race conditions, no timing dependency, and no reliance on any other component behavior.

### Recommendation
- In `Plugin.Admit` (`plugin/pkg/admission/priority/admission.go`), route `admission.Update` for `podGroupResource` (and `compositePodGroupResource`) into a dedicated update-path admission check that re-derives priority from `Spec.PriorityClassName` and enforces that `Spec.Priority`/`Spec.PriorityClassName` are unchanged from the old object (mirroring the pattern used for `admitPod`'s Update handling).
- Alternatively/additionally, add immutability validation for `Spec.Priority` and `Spec.PriorityClassName` in `ValidatePodGroupUpdate` (and the analogous `ValidateCompositePodGroupUpdate`) in `pkg/apis/scheduling/validation/validation.go`, using `apivalidation.ValidateImmutableField`, and have the `podGroupStrategy.PrepareForUpdate` in `pkg/registry/scheduling/podgroup/strategy.go` restore `Spec.Priority`/`Spec.PriorityClassName` from the old object before persisting, as is done for `Status`.

### Proof of Concept
Integration/unit test plan (extending `plugin/pkg/admission/priority/admission_test.go`):
1. Create a `PriorityClass` "low" (value 10) and "high" (value 1000, or a system-reserved-like value).
2. Create a `PodGroup` with `priorityClassName: "low"`; call `Plugin.Admit` with `admission.Create` and assert `spec.Priority == 10`.
3. Build an Update `admission.Attributes` for the same PodGroup with `spec.Priority` forged to `1000` and/or `spec.PriorityClassName` set to `"high"`, operation `admission.Update`.
4. Call `Plugin.Admit` with this Update attributes and assert it returns `nil` (no error) and the object's `spec.Priority`/`spec.PriorityClassName` remain the attacker-forged values — demonstrating the admission plugin performs no check on Update.
5. Separately call `validation.ValidatePodGroupUpdate(newPodGroup, oldPodGroup)` with the same forged spec diff and assert it returns an empty `field.ErrorList`, confirming no validation-layer safety net exists either.
6. Expected (vulnerable) result: both admission and validation allow the mutation through untouched, confirming the bypass. After applying the recommended fix, both should reject the request with a `Forbidden`/`Invalid` error when `spec.Priority`/`spec.PriorityClassName` are changed on update without matching the authorized PriorityClass.

```go
func (p *Plugin) admitPodGroup(attributes admission.Attributes) error {
	if !utilfeature.DefaultFeatureGate.Enabled(features.GenericWorkload) {
		return nil
	}

	pg, ok := attributes.GetObject().(*scheduling.PodGroup)
	if !ok {
		return errors.NewBadRequest("resource was marked with kind PodGroup but was unable to be converted")
	}

	priorityClassName, priority, preemptionPolicy, err := p.establishPriority(attributes, &pg.Spec.PriorityClassName)
	if err != nil {
		return err
	}
	// Reject if the pod group already contained a priority that differs from the one computed from the priority class.
	if pg.Spec.Priority != nil && *pg.Spec.Priority != priority {
		return admission.NewForbidden(attributes, fmt.Errorf("priority set in the pod group (%d) must match the priority computed (%d) based on the priority class set in the spec", *pg.Spec.Priority, priority))
	}
	pg.Spec.Priority = &priority
	pg.Spec.PriorityClassName = priorityClassName
```

```go
func (*podGroupStrategy) PrepareForUpdate(ctx context.Context, obj, old runtime.Object) {
	newPodGroup := obj.(*scheduling.PodGroup)
	oldPodGroup := old.(*scheduling.PodGroup)
	newPodGroup.Status = oldPodGroup.Status
	dropDisabledPodGroupFields(newPodGroup, oldPodGroup)
}

func (*podGroupStrategy) ValidateUpdate(ctx context.Context, obj, old runtime.Object) field.ErrorList {
	newPodGroup := obj.(*scheduling.PodGroup)
	oldPodGroup := old.(*scheduling.PodGroup)
	return validation.ValidatePodGroupUpdate(newPodGroup, oldPodGroup)
}
```
