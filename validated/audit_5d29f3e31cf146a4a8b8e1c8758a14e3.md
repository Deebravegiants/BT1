### Title
Webhook `shop` field is trusted from an unauthenticated header while only the raw body is HMAC-covered, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking the HMAC over the raw request body [1](#0-0) . The `shop` value that is handed to the host application's handler, however, comes straight from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header and is never included in the signed payload [2](#0-1) . This breaks the identity binding `shop (authenticated by HMAC) == shop (acted on by handler)`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [3](#0-2) , and `HmacValidator.validate` computes/compares the HMAC exclusively against that signable string [4](#0-3) . The `shop` accessor is read directly from the `shop-domain` header without any cryptographic binding to the signed body [5](#0-4) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching to the handler, and then forwards `request.shop` verbatim into `WebhookMetadata` [1](#0-0) . `WebhookMetadata.shop` is a plain, unauthenticated `String` field [6](#0-5) .

The gem's own documentation tells integrators that `Registry.process` "will verify the request did indeed come from Shopify" [7](#0-6)  and describes `data.shop` as "The shop domain of the webhook" [8](#0-7) , encouraging host apps to trust `data.shop` as an authenticated tenant identifier (e.g., to look up that shop's offline access token and enqueue per-tenant work, as shown in the doc's own sample handler at lines 24-27). Because the HMAC signature is computed with the app's single shared `api_secret_key` and does not incorporate the `shop` header at all, the same `(raw_body, hmac)` pair remains valid no matter what value is placed in the `shop-domain` header.

An unprivileged attacker who can install the target app on their own (attacker-controlled) shop — a normal, unprivileged action — can trigger a real webhook delivery for their own shop, capture the resulting `(raw_body, hmac)` pair, and replay it against the app's public webhook endpoint with the `shop-domain` header rewritten to a victim shop. `HmacValidator.validate` will still pass because it only checks the body, and `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the victim's domain, even though the payload was never generated for or signed on behalf of that shop.

Equality broken: `shop (bytes verified by HMAC)` != `shop (bytes acted on by the handler / used to key host-app tenant lookups)`.

### Impact Explanation
Any host application that uses `data.shop` from `WebhookMetadata` to select which shop's session/access token to use, or to attribute/write per-tenant data (a documented, expected pattern per the gem's own usage docs), can be made to process an attacker-controlled payload under a victim shop's identity. Depending on the handler's logic this yields cross-tenant data confusion/corruption — for example enqueuing jobs, writing state, or making authenticated API calls "on behalf of" a shop the attacker does not control, using a body the attacker fully controls (their own store's legitimate webhook content). This matches the Critical "cross-tenant access" impact category, since the tenant boundary (`shop`) is not actually authenticated even though the gem's HMAC check gives the impression that the whole request, including its stated shop, has been verified.

### Likelihood Explanation
Likelihood is high in terms of accessibility: any developer/attacker can install the app for free on their own store (a normal, unprivileged action), obtain a legitimately-signed webhook body/HMAC pair for events they trigger themselves (e.g., updating a product, creating an order), and then send an HTTP request to the target app's public webhook endpoint with an altered `shop-domain` header, since nothing in this gem checks that header against the signature or against any known/expected shop list. The actual severity realized depends on what the specific host application does with `data.shop`, but the gem provides no protection or guidance against this, and its own example handler passes the unauthenticated `shop` straight into downstream logic.

### Recommendation
Include the `shop` (and ideally `topic`, `api-version`, `webhook-id`) header values in the HMAC-signed payload used by `Request#to_signable_string`, or otherwise cryptographically bind them (e.g., HMAC over `"#{shop}\n#{raw_body}"` or a canonicalized header+body blob) so that a valid signature can only be produced for the exact `shop` value being asserted. At minimum, document prominently that `data.shop` is not covered by HMAC verification and must be independently checked by the host application against its own list of installed/authenticated shops before being used for any tenant-scoped operation.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`) they legitimately own. Shopify signs the payload with the app's shared `api_secret_key`:
   ```
   POST /callback/orders/create
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC over raw_body>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   Body: {"id": 1, ...}
   ```
2. Attacker replays the exact same `raw_body` and `x-shopify-hmac-sha256` to the same endpoint, but changes only the shop header:
   ```
   POST /callback/orders/create
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <same valid HMAC, unchanged>
   x-shopify-shop-domain: victim-shop.myshopify.com
   Body: {"id": 1, ...}   (identical bytes)
   ```
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses `shop` from the header [5](#0-4) ; `HmacValidator.validate` recomputes the HMAC over the unchanged `raw_body` and it matches [4](#0-3) .
4. `Registry.process` accepts the request and calls the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", ...)` [1](#0-0) , even though this payload was never issued for, or authorized by, `victim-shop.myshopify.com`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
