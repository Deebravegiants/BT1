### Title
Duplicate `circomData.timeStamp` in `EmporiumUpgradeable.handleOut` lets two on‑chain UTXOs collapse to one spendable nullifier, permanently freezing one leaf's backing tokens - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`handleOut` stamps the on‑chain UTXO with `circomData.timeStamp` verbatim (not `block.timestamp`, and with no per‑call offset), so two separate Emporium ops that share the same `amount`, `erc20TokenAddresses[i]`, `stealthAddressStructure.stealthAddress` and `timeStamp` produce byte‑identical commitments at two different Merkle leaves. Because the spending nullifier is a pure function of `(commitment, signature)` with no dependence on leaf index or Merkle path, the second leaf becomes permanently unspendable once the first is spent.

### Finding Description
The broken equality is: two distinct leaf indices `L1 ≠ L2` in the Hinkal Merkle tree end up with `commitment(L1) == commitment(L2)`, which the protocol's nullifier scheme assumes is impossible/unique per spendable UTXO ("SINGLE_SPEND" invariant: one leaf ↔ one future nullifier).

- `EmporiumUpgradeable.handleOut` builds the outgoing UTXO as: [1](#0-0) 
using `circomData.timeStamp` directly, which is a fully attacker/integrator‑controlled `CircomData` field (part of the proof's public input, not forced to `block.timestamp`).

- `HinkalBase.createOnchainCommitment` then computes the leaf purely from these four values: [2](#0-1) 
with no leaf-index or nonce mixed in, so two calls with identical `(amount, token, stealthAddress, timeStamp)` yield an identical `commitment`, inserted at two different tree positions via `insertMany` inside `insertCommitments`.

- When the owner later spends either leaf, the circuit (`MainEVMCircuit.circom`) computes the nullifier solely from the commitment and the recipient's private key: [3](#0-2) 
`signature = Poseidon(nullifyingPrivateKey, commitment)`, `nullifier = Poseidon(commitment, signature)` — neither depends on the Merkle path/leaf index used to prove membership (`calcTransactionRootHash`/`calcEqual` in `circuits/MainEVMCircuit.circom` lines 136-148 only check *some* valid root, not leaf uniqueness).

- `HinkalBase.insertNullifiers` enforces global uniqueness of the nullifier value itself: [4](#0-3) 
So once the owner spends one of the two identical leaves, the nullifier is marked used, and any proof spending the other (structurally identical) leaf reverts with `"Nullifier cannot be reused"`, even though it corresponds to real, distinct ERC20 tokens transferred into Hinkal by a separate `handleOut` call.

Notably, the sibling contract `DepositOnChainUtxosExternalAction` already recognizes and mitigates exactly this hazard by deliberately de‑duplicating timestamps within a batch: [5](#0-4) 
(`timeStamp: circomData.timeStamp + utxoIndex`), and its doc comment explicitly states commitments "are fully determined by the caller, because their timestamps come from `circomData.timeStamp` rather than from the block." `EmporiumUpgradeable.handleOut` has no equivalent protection — it neither forces `block.timestamp` (as `_createProoflessDepositCommitments` does, `contracts/Hinkal.sol` line 342) nor offsets by any per-call counter.

Attacker's exact call: submit two `Hinkal.transact` → `EmporiumUpgradeable.runAction` calls whose Emporium ops each yield the same positive `balanceChange` for the same `erc20TokenAddresses[i]`, with identical `stealthAddressStructure` and identical `circomData.timeStamp` (e.g., `0`, a natural default many SDKs would use). Both pass `performHinkalChecks`/`dimensionsCheck`/`checkOnchainCreation` (none of which constrain timestamp uniqueness across calls) and both succeed, inserting two identical-commitment leaves. `performHinkalChecks` and the circuit's `inTotal + amountChanges === outTotal` only bind internal consistency per transaction, not cross-transaction leaf uniqueness.

### Impact Explanation
The real ERC20 tokens backing the second (or any subsequent) colliding leaf become permanently unspendable — `insertNullifiers` will always reject the duplicate nullifier once the first identical leaf is spent, and there is no code path that lets the owner produce a different nullifier for a genuinely different leaf sharing the same commitment. This is a permanent freeze of legitimate token balances held by the Hinkal contract, matching the Critical category ("permanent freezing of user funds"). It is repeatable for every duplicate `(amount, token, stealthAddress, timeStamp)` combination created through the Emporium/handleOut path, and since on‑chain commitment details are emitted in cleartext (`NewCommitment` event with `abi.encode(utxo, ...)` in `HinkalBase.insertCommitments`), a third party can also learn the exact tuple of a target's existing UTXO and intentionally mint a colliding duplicate to freeze it (at the cost of funding the matching `balanceChange` themselves).

### Likelihood Explanation
No privileged role is required. The only precondition is two Emporium-routed calls sharing token, stealth address, amount, and `timeStamp` — plausible either through accidental integrator reuse of a sentinel `timeStamp` (as flagged in the question) or deliberate griefing using publicly emitted UTXO data. The attacker needs only to fund a real `handleOut`-eligible balance change (their own capital or the victim's normal flow), no special contract privilege, and can perform this in an ordinary `transact` call.

### Recommendation
Bind on-chain-created commitments to a value guaranteed unique per insertion, e.g. force `timeStamp = block.timestamp` (as `_createProoflessDepositCommitments` already does) or mix in a monotonically increasing per-call/per-UTXO nonce (as `DepositOnChainUtxosExternalAction` does with `+ utxoIndex`) inside `EmporiumUpgradeable.handleOut` before constructing the `UTXO`, rather than trusting caller-supplied `circomData.timeStamp` directly.

### Proof of Concept
Hardhat fork test:
1. Deploy Hinkal stack with `EmporiumUpgradeable` registered as an external action.
2. Craft Emporium op #1: swap/action that yields `balanceChange = X` of `tokenA`, `stealthAddressStructure = S`, `circomData.timeStamp = 0`. Call `transact` → assert a `NewCommitment` event for `commitment1 = hash4(X, tokenA, S.stealthAddress, 0)` at leaf index `L1`.
3. Craft Emporium op #2 with identical `X`, `tokenA`, `S`, `timeStamp = 0` (independent real balance increase funded separately). Call `transact` → assert `NewCommitment` for `commitment2` at leaf `L2`, and assert `commitment1 == commitment2`.
4. Generate a valid spend proof for `S`'s owner using `L1`'s Merkle path; call `transact` to spend it — assert success and nullifier `N` recorded true in `nullifiers[N]`.
5. Generate a spend proof for the same owner using `L2`'s Merkle path (different siblings/path, same commitment) — assert the derived nullifier equals `N`, and the second `transact` call reverts with `"Nullifier cannot be reused"`.
6. Assert Hinkal's `tokenA` balance still holds the second `X` worth of tokens indefinitely (no code path ever decreases it for `L2`), confirming permanent freeze.

    function insertNullifiers(
        uint256[][] calldata inputNullifiers,
        bool[] calldata onChainCreation
    ) internal {
        for (uint256 i = 0; i < inputNullifiers.length; i++) {
            for (uint256 j = 0; j < inputNullifiers[i].length; j++) {
                if (onChainCreation[i] == true) break;
                if (inputNullifiers[i][j] != 0) {
                    require(
                        !nullifiers[inputNullifiers[i][j]],
                        "Nullifier cannot be reused"
                    );
                    nullifiers[inputNullifiers[i][j]] = true;
                    emit Nullified(inputNullifiers[i][j]);
                }
            }
        }
    }
