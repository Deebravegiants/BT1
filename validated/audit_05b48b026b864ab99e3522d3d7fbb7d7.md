### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers that are never included in the HMAC computation. `HmacValidator.validate` therefore only proves that the body bytes were signed by Shopify with the app's `api_secret_key` — it proves nothing about which shop, topic, or webhook the body belongs to. An attacker who can obtain one validly-signed webhook body (e.g. by installing the app on their own shop and receiving their own legitimate webhooks) can replay that exact body to the app's webhook endpoint with an arbitrary `shop-domain`/`topic`/`webhook-id` header, and the signature will still validate because none of those headers participate in the HMAC.

### Finding Description
The identity binding that should hold is: `hmac == HMAC(secret, body || shop || topic || webhook_id)`, i.e. the authenticated bytes should equal the bytes the application actually acts on (topic dispatch + tenant attribution). Instead, the gem only enforces `hmac == HMAC(secret, body)`:

- `to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 
- `shop`, `topic`, `webhook_id`, `api_version` are parsed from headers with no cryptographic binding: [2](#0-1) 
- `HmacValidator.validate_signature` signs/verifies only `to_signable_string`: [3](#0-2) 
- `Registry.process` trusts `request.shop`/`request.topic`/`request.webhook_id` once the (body-only) HMAC check passes, and hands them to the app's handler as authenticated metadata: [4](#0-3) 
- `WebhookMetadata.shop` is a plain, unauthenticated `String` field that the handler is expected to trust for tenant scoping: [5](#0-4) 
- The documented handler contract explicitly tells app developers to key their per-shop data storage/enqueue logic off `data.shop`: [6](#0-5) 

Because the `api_secret_key` is shared by the app across every shop that installs it (a single Shopify app serves many merchants with one client secret), any tenant of the app can produce a body whose HMAC is valid under that shared secret. That attacker-obtained valid `(body, hmac)` pair is then portable to any `shop-domain`/`topic`/`webhook_id` header combination, since those fields are outside the signed content.

Before the attack: `shop` header value == tenant the body's data actually belongs to (assuming Shopify is the only sender).
After the attack: `shop` header value (attacker-chosen) != tenant the body's data actually belongs to (attacker's own shop), yet `HmacValidator.validate` still returns `true`.

### Impact Explanation
This breaks the tenant-isolation guarantee the gem is expected to provide to embedding applications: a request that only proves "this body was signed with the app's secret" is treated as also proving "this body belongs to shop X." An attacker who is a legitimate (even free-trial) installer of the app can:
1. Trigger a real webhook on their own shop (e.g. `orders/create`) and capture the exact raw body + valid HMAC signature Shopify sent for it.
2. Replay that raw body verbatim to the app's webhook endpoint, substituting the `x-shopify-shop-domain` header (and optionally `topic`/`webhook-id`) with a victim shop's domain / a different topic.
3. `HmacValidator.validate` passes because it only checks the body bytes, and `Registry.process` dispatches the attacker-controlled body as if it were the victim shop's authenticated data (`WebhookMetadata#shop == victim shop`).

Any downstream logic that uses `data.shop` to select which merchant's database row/job/cache to write into (exactly as the gem's own documentation recommends: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) will attribute attacker-controlled data to another tenant — a cross-tenant data-injection/corruption primitive, matching the Critical "cross-tenant access" bucket.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install/use the app on some shop (the normal, unprivileged path for any merchant/app-store user) and be able to send arbitrary HTTP requests with attacker-chosen headers to the app's public webhook callback URL (which is, by design, a public unauthenticated internet endpoint that receives POSTed webhooks). No access to the app's `api_secret_key`, session, or any credential belonging to the victim shop is required — only a webhook the attacker legitimately received for their own tenant.

### Recommendation
Bind the tenant/topic identity into the signed content that `HmacValidator` checks, e.g. by including `shop`, `topic`, and `webhook_id` in `to_signable_string` (mirroring Shopify's `X-Shopify-Shop-Domain`/`X-Shopify-Topic`/`X-Shopify-Webhook-Id` as canonicalized, signed metadata) rather than trusting them as bare headers, or by requiring the consuming application to separately verify `request.shop` against a shop it has an active, previously-established install/session for before acting on the payload. At minimum, document prominently that `WebhookMetadata#shop`/`#topic`/`#webhook_id` are **not** cryptographically bound to the webhook body and must not be used alone for tenant attribution.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers `orders/create`. Shopify sends a webhook to the app's callback with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid HMAC of raw_body>`, and some `raw_body` (attacker can fully control the order's content on their own shop, e.g. set `note` to arbitrary attacker-controlled text).
2. Attacker captures this exact raw HTTP request.
3. Attacker resends the identical `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. Inside the gem: `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds a `Request` whose `shop` returns `"victim-shop.myshopify.com"` while `to_signable_string` still returns the original `raw_body` [7](#0-6) .
5. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, raw_body)` and finds it matches the (unchanged) `x-shopify-hmac-sha256` header — validation succeeds [8](#0-7) .
6. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's order data>, ...)`, and any app logic that stores/queues this per `data.shop` now attributes attacker-controlled order data to the victim shop's tenant.
