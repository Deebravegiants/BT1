### Title
Legacy BCH address regex in `validateBchAddress` accepts corrupted base58Check checksums, allowing withdrawal to an unverified BCH address - ([File: packages/intents-sdk/src/lib/validateAddress.ts])

### Summary
`validateBchAddress` treats any string matching `/^1[1-9A-HJ-NP-Za-km-z]{25,34}$/` or `/^3[1-9A-HJ-NP-Za-km-z]{25,34}$/` as valid without ever base58-decoding it or verifying the double-SHA256 checksum, unlike the CashAddr branch which calls `verifyBchChecksum`, and unlike the sibling `validateBtcBase58Address` which does perform full base58 decode + checksum verification for the same address shapes. This lets an attacker-supplied legacy-format string with a corrupted/invalid checksum pass validation and be embedded verbatim into the `WITHDRAW_TO:<address>` memo signed on-chain by `createWithdrawIntentPrimitive`/`createWithdrawMemo`.

### Finding Description
The claimed equality is: *validated `destinationAddress` == a byte-correct, checksummed BCH legacy address*. This equality is broken.

- `validateBchAddress` (packages/intents-sdk/src/lib/validateAddress.ts, lines 214-225) tests the legacy branch purely with a regex on the base58 alphabet and length range; there is no `base58.decode`, no double-SHA256 checksum computation, and no version-byte check — nothing like the 25-byte-decode-and-4-byte-checksum-compare done in `validateBtcBase58Address` (lines 140-158) for the structurally identical Bitcoin case.
- Only the CashAddr path (`validateBchCashAddr` → `verifyBchChecksum`, lines 231-310) performs checksum verification.
- `PoaBridge.validateWithdrawal` (packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts, lines 181-188) calls `validateAddress(args.destinationAddress, assetInfo.blockchain)` and only throws `InvalidDestinationAddressForWithdrawalError` if it returns `false` — for the legacy-regex path it will always return `true` regardless of checksum correctness.
- `PoaBridge.createWithdrawalIntents` (poa-bridge.ts, lines 142-162) calls `createWithdrawIntentPrimitive` unconditionally with `args.withdrawalParams` (no re-validation), which in turn calls `createWithdrawMemo` (packages/intents-sdk/src/bridges/poa-bridge/poa-bridge-utils.ts, lines 28-49) to build `memo = "WITHDRAW_TO:" + normalizedAddress`, embedding the attacker-chosen string byte-for-byte (no BCH-prefix stripping happens for legacy addresses; that only applies to `bitcoincash:` addresses).
- This memo is then packaged into the signed `ft_withdraw` intent (`intent: "ft_withdraw"`, `memo`) that the user's wallet signs.

Attacker input: a string like `"1BvBMSEYstWetqTFn5Au4m4GFg7xJaNVN3"` with one character of the trailing checksum bytes flipped so that, when base58-decoded, the last 4 bytes no longer equal `SHA256(SHA256(payload))[0:4]`. This still matches the legacy regex (25-34 base58 chars starting with `1` or `3`) and is accepted by `validateBchAddress`.

No other guard catches this: `supports()` only checks assetId/routeConfig; `compareAddresses` only checks equality against the token's origin address, not general validity; there is no on-chain checksum verification inside the intents contract for arbitrary memo strings (the memo is opaque to `intents.near`, interpreted only by the PoA bridge relayer/bch node off-chain).

### Impact Explanation
The user's own signed `ft_withdraw` intent embeds an unchecksummed, potentially garbage BCH address in the `WITHDRAW_TO` memo. Depending on how the off-chain PoA relayer/BCH node handles an invalid-checksum legacy address, funds can be misrouted or become unrecoverable, and — critically — the format check that is supposed to catch this in the SDK (`validateAddress`) silently passes. This matches "funds delivered to a wrong address/chain/contract with no recovery" (Critical), and the victim is the withdrawing user themselves. It is repeatable on every withdrawal call using a legacy BCH address, since the check is purely client-side format validation with no external mitigation identified in-repo.

### Likelihood Explanation
Preconditions: the user (or an integrator calling on the user's behalf) must supply a destination address for `nep141:bch.omft.near` withdrawals. Any ordinary SDK caller can pass an arbitrary string satisfying the legacy regex — no special privilege, RPC compromise, or relayer collusion needed; this is purely a client-side SDK format-validation gap. Constructing such a string is trivial (flip one base58 character of a real legacy address's checksum bytes). This is a genuine gap in a documented "FORMAT only" validator's own stated guarantee, and it diverges from the checksum-verifying sibling functions (`validateBtcBase58Address`, `validateBchCashAddr`) in the same file, indicating an oversight rather than intended behavior.

### Recommendation
In `validateBchAddress`'s legacy branch (packages/intents-sdk/src/lib/validateAddress.ts, lines 214-221), replace the bare regex test with a full base58Check decode and checksum verification, mirroring `validateBtcBase58Address`: decode with `base58.decode`, require length 25, verify the version byte (0x00 for P2PKH / 0x05 for P2SH), and compare the last 4 bytes against `sha256(sha256(payload)).subarray(0,4)`.

### Proof of Concept
```ts
import { describe, it, expect } from "vitest";
import { base58 } from "@scure/base";
import { sha256 } from "@noble/hashes/sha2";
import { validateBchAddress } from "../src/lib/validateAddress";
import { createWithdrawIntentPrimitive } from "../src/bridges/poa-bridge/poa-bridge-utils";

function corruptLegacyChecksum(): string {
  // Start from a known-valid legacy P2PKH address, decode, flip a checksum byte, re-encode.
  const valid = "1BvBMSEYstWetqTFn5Au4m4GFg7xJaNVN3"; // matches legacy BCH/BTC regex
  const decoded = base58.decode(valid);
  const corrupted = new Uint8Array(decoded);
  corrupted[24] ^= 0xff; // flip last checksum byte -> checksum now invalid
  return base58.encode(corrupted);
}

describe("BCH legacy checksum bypass", () => {
  it("validateBchAddress incorrectly accepts a corrupted-checksum legacy address", () => {
    const corrupted = corruptLegacyChecksum();
    expect(/^1[1-9A-HJ-NP-Za-km-z]{25,34}$/.test(corrupted)).toBe(true);

    // Equality being tested: "validated address" should equal "checksum-correct address" — it doesn't.
    const decoded = base58.decode(corrupted);
    const payload = decoded.subarray(0, 21);
    const checksum = decoded.subarray(21, 25);
    const expected = sha256(sha256(payload)).subarray(0, 4);
    const checksumIsActuallyValid = checksum.every((b, i) => b === expected[i]);
    expect(checksumIsActuallyValid).toBe(false); // confirm it's genuinely corrupted

    expect(validateBchAddress(corrupted)).toBe(true); // BUG: should be false
  });

  it("createWithdrawIntentPrimitive embeds the invalid address verbatim into signed memo", () => {
    const corrupted = corruptLegacyChecksum();
    const intent = createWithdrawIntentPrimitive({
      assetId: "nep141:bch.omft.near",
      destinationAddress: corrupted,
      destinationMemo: undefined,
      amount: 1000n,
    });
    expect(intent.memo).toBe(`WITHDRAW_TO:${corrupted}`);
  });
});
```
