### Title
Bandwidth-allowance griefing via FIFO eviction cap lets any purchaser destroy another app's prepaid bandwidth - ([File: modules/pallets/bandwidth/src/lib.rs])

### Summary
`pallet-bandwidth` credits an app's prepaid message-bandwidth allowance in a per-`(chain, app)` FIFO list bounded to `MAX_SUBSCRIPTIONS = 1024` [1](#0-0) . `app` and `app_chain` are attacker-chosen fields decoded straight out of the purchase message body with no ownership check tying the purchase to any particular payer [2](#0-1) , and `BandwidthManager.sol::purchase(app, tier, quantity, appChain)` is callable by anyone naming any `app`/`appChain` (per `evm/tests/foundry/BandwidthManagerTest.t.sol`). When the FIFO list for a `(chain, app)` key is full, the next push evicts the oldest entry regardless of how much unused, already-paid-for balance it still holds [3](#0-2) . This is the same bug class as the referenced report: a capped, shared per-recipient resource that any unprivileged third party can fill with cheap entries, permanently destroying a victim's legitimate entry in that resource.

### Finding Description
`Allowance<T>` stores a `BoundedVec<Subscription, MaxSubscriptions>` keyed by `(StateMachine, AppKey)`, described in the module docs as "chronological insertion order; the gate drains the front" and "Pushes onto a full list evict the oldest entry" [4](#0-3) [5](#0-4) .

`push_subscription` is the sole insertion path used both by real purchases (`on_accept`) and admin `force_credit`: [6](#0-5) 
When the list has reached the 1024 cap, `list.remove(0)` unconditionally evicts the oldest `Subscription`, whatever its `remaining_bytes` — the event even documents this: "The 1024-cap pushed out the oldest subscription. `lost_bytes` is what the user paid for and won't get to use." [7](#0-6) 

`on_accept` decodes `msg.chain` (app_chain) and `msg.app` directly from the untrusted PurchaseMessage body — the only check performed is that the ISMP request came from the registered `BandwidthManager` contract on the source chain, not that the purchaser is the app itself or any authorized party for that app: [8](#0-7) 

Because `AppKey`/chain are fully attacker-controlled and the cheapest configured `TierIndex` (e.g. `TierOne`) can be purchased repeatedly and cheaply, any unprivileged bandwidth purchaser can:
1. Target a victim app's `(app_chain, app)` key.
2. Buy the cheapest tier repeatedly (up to and beyond 1024 times) for that exact key.
3. Once the list is at capacity, each further cheap purchase evicts the oldest entry in FIFO order — which will eventually be the victim's own large, mostly-unused, legitimately-purchased subscription, since eviction is oldest-first and blind to remaining value.

This directly parallels the referenced LockingPositionDelegate bug: a bounded per-recipient slot count (`maxTokenIdsDelegated` there, the 1024-entry FIFO here) that any unprivileged actor can fill/rotate with negligible-value entries to deny or destroy a legitimate holder's larger allocation.

### Impact Explanation
`BandwidthGate::try_consume` is the hook the ISMP router consults on every inbound message for gas/bandwidth accounting; insufficient balance causes the message to be rejected [9](#0-8) . If a victim app's paid-for, unused bandwidth subscription is evicted before being consumed, that app:
- Permanently loses the prepaid, already-paid value (`lost_bytes`) it purchased — a concrete loss of funds/value.
- Can be driven into `GateError::NoAllowance`/`Insufficient`, causing the router to reject its ISMP messages — i.e., "a route unable to deliver messages" for that app until it repurchases, which itself is then vulnerable to the same griefing loop from the same attacker.

This meets the required bar of concrete freezing of paid funds (destroyed prepaid bandwidth) and denial of message delivery for the targeted app, for the cost of some number of cheap tier purchases by an unprivileged "bandwidth purchaser."

### Likelihood Explanation
`purchase()` on `BandwidthManager.sol` is a fully public, unprivileged entry point (confirmed by `BandwidthManagerTest.t.sol`, where an arbitrary `BUYER` calls `purchase(APP, TIER, quantity, APP_CHAIN)` naming an arbitrary `app`/chain). No check anywhere in `pallet-bandwidth` restricts who may credit which `(chain, app)` key, and the FIFO cap is a fixed, publicly known constant (`MAX_SUBSCRIPTIONS = 1024`). An attacker only needs to know a victim's `(app_chain, app)` identifier (public, since it's the destination app address) and be willing to pay for repeated cheap purchases — an inexpensive, deterministic, always-available attack path, not requiring any race condition or privileged access.

### Recommendation
- Do not allow eviction of a subscription while it still has unconsumed `remaining_bytes`; either reject the push (forcing the purchaser to wait/consume) or size the cap so it cannot realistically be exhausted for an actively-used app, or store `(payer, chain, app)` so one purchaser's own subscriptions age out first rather than any global FIFO shared with all purchasers.
- Alternatively, weight eviction by remaining value rather than strict insertion order (e.g., only evict entries at/near expiry, or evict the entry with least remaining bytes rather than the oldest).
- Consider requiring that only the app itself (or an authorized relationship) can credit its own `(chain, app)` allowance, closing the "anyone can target anyone's bucket" surface.
- Emit/alert when `SubscriptionEvicted.lost_bytes` is non-trivial so this griefing pattern is detectable and actionable by governance.

### Proof of Concept
1. Victim app `V` on chain `C` legitimately purchases a large, expensive `TierFour` bandwidth subscription via `BandwidthManager.sol::purchase(V, TierFour, 1, C)`. `pallet-bandwidth::on_accept` appends it to `Allowance[C][V]` at whatever position is next in the FIFO (`push_subscription`) [2](#0-1) .
2. Attacker `A` (no special privileges) repeatedly calls `purchase(V, TierOne, 1, C)` — the cheapest tier — targeting the *same* `(C, V)` key, up to and beyond `MAX_SUBSCRIPTIONS = 1024` total entries for that key.
3. Once `Allowance[C][V]` reaches 1024 entries, every subsequent cheap purchase by `A` triggers `list.remove(0)` in `push_subscription`, evicting whichever entry is currently oldest [10](#0-9) . By continuing to purchase, `A` rotates the FIFO until `V`'s original `TierFour` subscription becomes the oldest and is evicted — emitting `SubscriptionEvicted { lost_bytes: <V's remaining bytes> }` — destroying it regardless of how much of it `V` had actually used.
4. `V`'s app is left with only whatever dust `TierOne` entries `A` left behind (or none), and any inbound ISMP message for `V` that needs more bandwidth than remains now fails `BandwidthGate::try_consume` with `GateError::Insufficient`/`NoAllowance`, blocking message delivery for `V` until it repurchases — at which point `A` can repeat the attack.

This was validated by reading the pallet source directly; I was not able to fully verify the exact `TierOne` pricing configured in production deployments (governance-set on the EVM side), so the precise attacker cost is unconfirmed, but the mechanism itself has no economic or access-control mitigation in the code shown.

		/// Append a fresh subscription with a fixed expiry. If the list
		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}

		fn on_accept(&self, request: PostRequest) -> Result<Weight, anyhow::Error> {
			let manager = BandwidthManager::<T>::get(&request.source).ok_or_else(|| {
				anyhow::anyhow!(format!("no bandwidth manager registered for {:?}", request.source))
			})?;

			if request.from != manager.0.to_vec() {
				return Err(anyhow::anyhow!(format!(
					"purchase from unauthorised sender on {:?}: expected {:x?}, got {:x?}",
					request.source, manager.0, request.from
				)));
			}

			let msg = PurchaseMessage::try_from(request.body.as_slice())?;
			let tier = TierIndex::try_from(msg.tier)
				.map_err(|_| anyhow::anyhow!(format!("unknown tier discriminant {}", msg.tier)))?;
			let cfg = Tiers::<T>::get(tier)
				.ok_or_else(|| anyhow::anyhow!(format!("tier {:?} is not configured", tier)))?;

			let bytes = cfg.bytes.saturating_mul(msg.months as u128);
			let duration = cfg.duration_secs.saturating_mul(msg.months as u64);

			let key = AppKey::truncate_from(msg.app);
			let expires_at = Self::push_subscription(&msg.chain, &key, tier, bytes, duration);

			Self::deposit_event(Event::BandwidthCredited {
				app_chain: msg.chain,
				app: key,
				paid_from: request.source,
				tier,
				bytes,
				expires_at,
			});

impl<T: Config> BandwidthGate for Pallet<T> {
	fn try_consume(
		source: &ismp::host::StateMachine,
		app: &[u8],
		bytes: u32,
	) -> Result<(), GateError> {
		let key = AppKey::truncate_from(app.to_vec());
		if Allowlist::<T>::contains_key(source, &key) {
			return Ok(());
		}

		let need: u128 = bytes.into();
		let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();

		let total = pallet::Allowance::<T>::mutate(source, &key, |list| {
			// Sweep expired in-place. Order-preserving.
			list.retain(|s| s.expires_at > now);

			if list.is_empty() {
				return Err(GateError::NoAllowance);
			}

			let total: u128 = list.iter().map(|s| s.remaining_bytes).sum();
			if total < need {
				return Err(GateError::Insufficient { remaining: total, required: need });
			}

			// Drain from the front in insertion order. Once a sub is
			// fully consumed, pop it and continue with the next.
			// `get_mut` defends against a malformed list that satisfies
			// the `total >= need` precheck but is structurally empty;
			// we'd otherwise panic via `list[0]`.
			let mut left = need;
			while left > 0 {
				let Some(head) = list.get_mut(0) else {
					return Err(GateError::NoAllowance);
				};
				let take = head.remaining_bytes.min(left);
				head.remaining_bytes = head.remaining_bytes.saturating_sub(take);
				left = left.saturating_sub(take);
				if head.remaining_bytes == 0 {
					list.remove(0);
				}
			}

			Ok(total)
		})?;

		Self::deposit_event(Event::BandwidthConsumed {
			source: *source,
			app: key,
			bytes: need,
			remaining: total - need,
		});
		Ok(())
	}
