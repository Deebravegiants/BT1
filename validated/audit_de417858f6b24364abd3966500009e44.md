### Title
Min-circuit path with empty `erc20TokenAddresses` lets any attacker drain ERC20/ETH balances held by Emporium via unconstrained CASE-2 calls - (File: `contracts/CircomDataBuilder.sol`, `contracts/Hinkal.sol`, `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
When `circomData.externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `circomData.erc20TokenAddresses.length == 0`, `formInputForCircom` routes to `formInputEmporiumMin`, producing a public-input vector of only `[emporiumMessage, timeStamp, calldataHash]`. This lets an attacker submit a self-generated `MainEVMCircuitMin` proof (which only constrains `message <== Poseidon(1)([messageSeed])`) together with an `EmporiumStack` whose `signerAddress == address(0)`, bypassing all balance-conservation and signature checks and sweeping any ERC20/ETH balance sitting on the Emporium contract to themselves.

### Finding Description
The broken equality: Hinkal.sol's per-token conservation check
```
balanceDif == (onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount
``` [1](#0-0) 
is asserted **zero times** because the loop bound is `circomData.erc20TokenAddresses.length`, which is forced to `0` by `dimensionsCheck` when `dimensions.tokenNumber == 0`.

Path:
1. `formInputForCircom` selects the Min path solely based on `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0` [2](#0-1) .
2. `MainEVMCircuitMin` only pins `message <== Poseidon(1)([messageSeed])`; it has no nullifier, commitment, or balance logic [3](#0-2) . An attacker picks their own `messageSeed`, computes `message`, and sets `circomData.emporiumMessage = message`, producing a proof that verifies trivially.
3. `Hinkal.transact` runs `performHinkalChecks` (only length-consistency and calldata-hash checks, no token-count minimum) [4](#0-3) , then `verifyProof` succeeds, then the balance loop at lines 97-147 is skipped entirely because `erc20TokenAddresses.length == 0` [5](#0-4) .
4. `_externalTransact` calls `EmporiumUpgradeable.runAction` with the same empty `erc20TokenAddresses`, so `balancesBefore`/`balancesAfter` are length-0 arrays and the internal `balanceChange` check (lines 132-151) never fires [6](#0-5) .
5. `verifyWallet` is called with `stack.signerAddress == address(0)`, which returns immediately after marking the message used - **no signature is checked at all** [7](#0-6) .
6. Because `signerAddress == address(0)`, every op falls into "CASE 2: Stateless Interaction", which only blocks the `callHinkalWallet`/`doSendToRelay` selectors and otherwise performs an arbitrary `op.endpoint.call{value: op.value}(op.callData)` with `msg.sender == Emporium` [8](#0-7) . There is no endpoint whitelist - `onlyAllowedRecipient` only checks that `msg.sender` (i.e. Hinkal) is allowed to invoke `runAction` [9](#0-8) .

The attacker sets `op.endpoint = victimToken`, `op.callData = abi.encodeWithSelector(IERC20.transfer.selector, attacker, victimToken.balanceOf(Emporium))`. This executes `victimToken.transfer(attacker, amount)` with `msg.sender == Emporium`, draining any residual/in-flight ERC20 (or ETH via `op.value`) balance held by Emporium that is outside the current transaction's (empty) `erc20TokenAddresses` list - completely unconstrained by any proof, nullifier, or balance check.

### Impact Explanation
Critical - direct theft of shielded/in-flight user funds. Any ERC20 or ETH balance that legitimately sits on the Emporium contract as an intermediate/in-flight state (e.g., between multi-step CASE-2 operations, or residual dust from prior swaps/actions not included in a later transaction's `erc20TokenAddresses`) can be swept to an attacker with zero authorization, zero signature, and zero balance accounting. The attack is repeatable for every token/ETH balance that accumulates on Emporium and is bounded only by attacker gas cost and the availability of an admin-registered verifier for `buildVerifierId({0,0,0}, HINKAL_EMPORIUM_ACTION_ID)` pointing at `MainEVMCircuitMin`.

### Likelihood Explanation
Preconditions: (1) the protocol has registered a Min-circuit verifier for the Emporium action with `tokenNumber == 0` (required for the Min path to even be usable, which the code's existence of `formInputEmporiumMin`/`IVerifierEVMMin0v4` implies is intended functionality); (2) Emporium is holding some stranded/in-flight token or ETH balance. Given this, the attack requires only: generating a snarkjs proof for `MainEVMCircuitMin` with a self-chosen seed (trivial, no special knowledge needed), and crafting an `EmporiumStack` with `signerAddress = address(0)` and a single CASE-2 `transfer` call. No privileged role, victim key, or relay access is required. Cost is a single transaction's gas.

### Recommendation
Do not allow the Min-circuit/empty-`erc20TokenAddresses` path to invoke `EmporiumUpgradeable.runAction` with unconstrained CASE-2 calls. Either (a) require `erc20TokenAddresses.length > 0` whenever `stack.ops` contains non-`invokeWallet` calls, so the balance-diff loop in both `Hinkal.transact` and `EmporiumUpgradeable.runAction` actually executes over every token touched by the ops, or (b) require `signerAddress != address(0)` (i.e. a valid EIP-712 signature) whenever the Min-circuit/empty-token path is used with CASE-2 stateless calls, or (c) restrict CASE-2 `op.endpoint` calls to a pre-approved allowlist of endpoints that cannot directly move Emporium's own token balances.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable`, register `HINKAL_EMPORIUM_ACTION_ID -> Emporium`, register a `MainEVMCircuitMin` verifier for `buildVerifierId(Dimensions(0,0,0), HINKAL_EMPORIUM_ACTION_ID)`.
2. Simulate a prior legitimate operation (or direct `deal`) that leaves `victimToken` balance `X` sitting on the `Emporium` contract, outside any pending UTXO's `erc20TokenAddresses` tracking.
3. As attacker, pick `messageSeed`, compute `message = Poseidon(messageSeed)` off-chain (snarkjs), set `circomData.emporiumMessage = message`, `circomData.erc20TokenAddresses = []`, `dimensions = {tokenNumber:0, nullifierAmount:0, outputAmount:0}`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionMetadata = abi.encode(EmporiumStack({signerAddress:address(0), ops:[EmporiumOperation({endpoint:address(victimToken), invokeWallet:false, value:0, callData: abi.encodeWithSelector(IERC20.transfer.selector, attacker, X)})], maxFee:0, deadline:0}))`.
4. Generate real Groth16 proof `(a,b,c)` for `MainEVMCircuitMin` with these public inputs.
5. Call `Hinkal.transact(a,b,c,dimensions,circomData)`.
6. Assert: `victimToken.balanceOf(Emporium) == 0` and `victimToken.balanceOf(attacker) == X` afterward, while `balanceDif == amountChanges[i] + utxoAmount` was never evaluated (loop bound 0) - i.e., no `require` in `Hinkal.transact`'s conservation loop ever ran for `victimToken`.

    function formInputForCircom(
        uint256 chainId,
        address verifyingContract,
        CircomData calldata circomData
    ) internal pure returns (uint256[] memory) {
        if (
            circomData.externalActionData.externalActionId ==
            HINKAL_EMPORIUM_ACTION_ID &&
            circomData.erc20TokenAddresses.length == 0
        ) {
            return formInputEmporiumMin(circomData);
        } else {
            return formInputNormal(chainId, verifyingContract, circomData);
        }

    function formInputEmporiumMin(
        CircomData calldata circomData
    ) internal pure returns (uint256[] memory input) {
        input = new uint256[](circomData.publicSignalCount);

        uint16 index = 0;

        input[index++] = circomData.emporiumMessage;

        input[index++] = circomData.timeStamp;
        input[index++] = circomData.calldataHash;
    }
