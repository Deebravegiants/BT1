### Title
Webhook `shop` Identity Is Not Bound to the HMAC Signature, Enabling Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from an HTTP header that is never part of the HMAC-signed material, then `ShopifyAPI::Webhooks::Registry.process` passes that unauthenticated value straight to the host application's webhook handler as the record's tenant. This is the same class of defect described in the external report: an authority/identity field is used to act on data (attributing a webhook event to a shop) while that field is not covered by the cryptographic check that is supposed to prove authenticity.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw request body: [1](#0-0) 

`HmacValidator.validate` computes the HMAC exclusively over that signable string and compares it to the `hmac-sha256` header: [2](#0-1) 

Meanwhile, `Request#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is completely outside the signed bytes: [3](#0-2) 

`Webhooks::Registry.process` validates only the body HMAC and then forwards the unauthenticated `request.shop` value directly to the application handler as the event's tenant identity: [4](#0-3) 

The equality the gem should guarantee is:
`shop that produced/authorized this signed payload == shop attributed to the resulting webhook event`

Because the header is never mixed into the signable string, this equality is not enforced: an attacker who can obtain any single genuine `(body, hmac)` pair from Shopify for the app's client secret (e.g., by owning a store that installs the app and captures its own legitimate webhook deliveries) can replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (or `shopify-shop-domain`) header value. `HmacValidator.validate` will still succeed, since it never inspects the header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event belongs to a shop the attacker never controls.

### Impact Explanation
This breaks the tenant boundary between merchants installed on the same app: an attacker-controlled shop can forge webhook events (e.g., `app/uninstalled`, `shop/update`, `customers/data_request`, or any topic the app subscribes to) that host applications will process as if they originated from a victim shop, because the only integrity check (body HMAC) does not bind the shop identity. Any host logic that trusts `WebhookMetadata#shop` to select/mutate per-tenant records (session revocation, GDPR data handling, plan/billing state, etc.) can be manipulated cross-tenant, which matches the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Exploitation only requires the attacker to be a legitimate (even free/trial) merchant capable of installing the app once to capture one genuine signed webhook body, and then replay that body to the app's public webhook endpoint with a forged shop-domain header — no access token, `api_secret_key`, or privileged account is required beyond normal merchant self-service. This is a low-effort, unprivileged-internet-facing attack path.

### Recommendation
Bind the shop identity to the signature: include the shop domain (and ideally topic/webhook id) in the value that is HMAC-verified, or have `Registry.process`/host applications independently verify that `request.shop` corresponds to a shop with an active, stored session/installation before trusting it, rejecting the event otherwise.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. updates the shop) so Shopify sends `POST /webhooks` with body `B` and header `x-shopify-hmac-sha256: H` (valid for `B` under the app's `api_secret_key`), plus `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker replays the exact same request to the app's webhook endpoint, only changing the header to `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present); `HmacValidator.validate` succeeds because it only recomputes HMAC over body `B`, which is unchanged.
4. `Registry.process` calls the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host app to process a forged event as if it came from `victim-shop`.
