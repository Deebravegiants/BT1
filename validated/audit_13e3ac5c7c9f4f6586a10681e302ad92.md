### Title
Webhook `shop` Attribution Not Covered by HMAC Allows Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, but the `shop` identifier that the handler uses to attribute the event to a tenant is read from an unauthenticated HTTP header and is never included in the signed content.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers with no cryptographic linkage to the body: [2](#0-1) .

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)` (which calls `to_signable_string`, i.e. body-only) and then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) . `HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest` over `verifiable_query.to_signable_string` using `Context.api_secret_key` [4](#0-3) , which is the app's single `client_secret` shared across every installed shop — it is not shop-specific.

Because `shop` is never part of the signed bytes, the equality the code implicitly assumes — "shop the HMAC authenticates" == "shop the handler acts on" — does not hold. Contrast this with the OAuth callback flow, where `AuthQuery#to_signable_string` explicitly includes `shop` in the signed parameters, binding the shop to the HMAC [5](#0-4) . The webhook path deliberately omits this binding.

Any party who can obtain one valid `(body, hmac)` pair for the shared app secret — e.g., the operator of their own shop installation, who receives real webhooks with a valid `X-Shopify-Hmac-Sha256` header computed with the same `client_secret` — can replay that exact `(body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header. `HmacValidator.validate` will still return `true` because it never inspects the header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event belongs to a different, unrelated merchant shop.

### Impact Explanation
This breaks the shop/session-key identity binding used by every consuming app: handlers built on this gem (e.g., mandatory `shop/redact`, `customers/redact`, `customers/data_request`, or any custom order/product webhook) key persisted data and side effects on `WebhookMetadata#shop`. A holder of one shop's valid webhook credentials can inject events attributed to a victim shop, enabling cross-tenant data pollution/actions (e.g., triggering `customers/redact`-style logic or writing attacker-controlled order data under another merchant's shop key) — a cross-tenant access impact within the specified Critical category.

### Likelihood Explanation
Likelihood is moderate: the attacker must already be an authenticated installer of the app on at least one shop (to legitimately obtain a valid body+HMAC pair using the app's shared secret) but needs no access to any other merchant's credentials, token, or `client_secret` value itself. No TLS interception or privileged access is required — only a normal HTTP POST to the app's public webhook endpoint with a modified `shop-domain`/`x-shopify-shop-domain` header.

### Recommendation
- Include the shop domain (and ideally `topic`/`webhook_id`) in the HMAC-signed payload comparison, or otherwise cryptographically bind the `shop-domain` header to the request (e.g., require the receiving app to confirm the shop against a previously stored, authenticated session/install record before trusting `WebhookMetadata#shop`).
- At minimum, document prominently that `request.shop` is unauthenticated and must be cross-checked by the host application against known installed shops before being used for any tenant-scoped action.
- Consider deriving the shop identity solely from data that is part of the signed body when the topic payload includes it, rather than from headers.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and receives a legitimate webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC_SHA256(client_secret, B)`).
2. Attacker sends a new HTTP request to the app's webhook endpoint with the same body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers and body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC_SHA256(client_secret, B)` and finds it equal to `H` — validation passes [6](#0-5) .
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` and performs tenant-scoped actions as if the event genuinely originated from `victim.myshopify.com` [7](#0-6) .

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
