## Title
Reentrant escrow drain via check-effects-interactions violation in Tron `IntentGatewayV2.withdraw()` - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2`'s internal `withdraw()` function performs the token transfer to the beneficiary **before** decrementing the corresponding escrow accounting entry, unlike the audited/patched EVM `IntentsBase._withdraw()` path. This CEI (checks-effects-interactions) ordering mirrors the root cause of the Platypus Finance exploit: a balance/solvency-relevant state variable is read and acted upon, but the debit of that state happens only after an external call that can reenter, so a reentrant call observes stale, unspent escrow accounting.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `withdraw()` is invoked from `onAccept()` for `RedeemEscrow`/`RefundEscrow` messages and from `cancelOrder()` for same-chain cancellations: [1](#0-0) 

The loop body:
1. Checks `_orders[body.commitment][token] == 0` (a "solvency"-style non-zero check),
2. Performs the **external transfer/call to `beneficiary`** — either a raw native-token `.call{value: amount}("")` or a low-level `token.call(...transfer...)` to an arbitrary attacker-supplied token address (tokens are chosen by the user at `placeOrder`),
3. **Only afterward** decrements `_orders[body.commitment][token] -= amount`.

Because the escrow accounting is not decremented until after the external call, any reentrancy triggered during that external call (a malicious ERC/TRC-20 `transfer` hook, or the native-token `.call` to a malicious beneficiary contract) executes with `_orders[body.commitment][token]` still showing the pre-withdrawal (full) balance. This is structurally identical to Platypus Finance's `emergencyWithdraw()`, which checked solvency against state that had not yet reflected the in-flight effect, letting the attacker extract collateral while retaining the borrowed principal.

By contrast, the more recently hardened EVM path in `IntentsBase._withdraw()` correctly decrements storage before making the external transfer: [2](#0-1) 
and the accompanying reentrancy regression tests confirm this ordering was deliberately fixed for the EVM contracts: [3](#0-2) 

The Tron contract, however, still uses the vulnerable transfer-then-decrement order: [4](#0-3) 

The `beneficiary` argument comes directly from `WithdrawalRequest.beneficiary`, which for `RedeemEscrow` is the solver's address (attacker-controlled, since any solver can fill an order) and for `RefundEscrow`/same-chain cancel is the order's `user` (also attacker-controlled, since anyone can place an order as their own beneficiary). The escrowed `token` is likewise attacker-chosen at `placeOrder` time, so an attacker can freely choose a malicious token contract with a reentrant `transfer`/`transferFrom` hook, or set `beneficiary` to a contract that reenters on receiving native TRX.

### Impact Explanation
If reentrancy into `withdraw()` (or any function reachable from the malicious token/beneficiary callback that reads `_orders[...]`) is achievable before the decrement executes, an attacker can drain escrowed input tokens beyond the amount actually owed — a direct theft of escrowed user/solver funds, which the "concrete theft" bar in the validation criteria requires. The `_filled[commitment]` guard is set once at the top of `withdraw()` and correctly blocks duplicate cross-chain message delivery for the same commitment (via `cancelOrder`'s `_filled` check before dispatch), so the primary exploitable surface is per-call reentrancy across the `body.tokens` loop or into any other path (e.g., a same-chain `cancelOrder` call that reads `_orders`) that trusts the not-yet-decremented value during the same top-level transaction.

### Likelihood Explanation
Medium-to-High: the token and beneficiary in every escrow payout are fully attacker-controlled (order placer chooses input tokens and beneficiary; solver chooses to fill with itself as beneficiary), and the vulnerable ordering exists in every `withdraw()` code path (`RedeemEscrow`, `RefundEscrow`, and same-chain cancel), not confined to an edge case. The `IntentGatewayV2Test.sol`/`IntentGatewayV2SameChainTest.sol` fee-on-transfer tests confirm attacker-supplied tokens are a first-class, tested scenario for this contract family, underscoring that non-standard token behavior is expected and reachable. Exploitability specifically depends on whether a reentrant external call during that `.call(...)` can reach a state-mutating function that reads the stale `_orders` entry within the same transaction — I could not fully verify from available context whether the Tron `HandlerV2`/ISMP delivery path marks a request as delivered before or after invoking `onAccept` (needed to rule out reentrant re-delivery of the same message), so likelihood should be validated by an engineer who can trace that call path plus the multi-token loop reentrancy scenario end-to-end.

### Recommendation
Reorder `withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` to decrement `_orders[body.commitment][token]` **before** performing the native-value call or token `transfer`, matching the CEI-safe pattern already used in `IntentsBase._withdraw()` (`evm/src/apps/intentsv2/IntentsBase.sol`, lines 461-469). Additionally, add a nonReentrant guard around `onAccept`/`withdraw`/`cancelOrder` as defense-in-depth, and validate that the ISMP delivery path (`HandlerV2` / host `onAccept` dispatch) marks a request as consumed prior to invoking the app callback.

### Proof of Concept
Conceptual PoC (mirrors the reentrancy tests already present for the EVM contracts, e.g. `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol`, but targeting the un-patched Tron `withdraw()`):
1. Attacker places an order (`placeOrder`) with `order.inputs` containing a malicious TRC-20 token whose `transfer()` callback re-enters the gateway, and/or sets the beneficiary to an attacker-controlled contract.
2. Attacker fills/cancels so that `withdraw()` is invoked with `body.tokens` including the malicious token/native value.
3. During the `beneficiary.call{value: amount}("")` or `token.call(...transfer...)` step (before `_orders[commitment][token] -= amount` executes), the malicious contract's fallback/hook reenters a path that reads/acts on `_orders[commitment][token]` while it is still at its pre-withdrawal value.
4. If that reentrant path is reachable (e.g. the same-chain `cancelOrder` → `withdraw` path, or a duplicate in-flight message not yet marked delivered), the attacker extracts the escrowed amount more than once, draining the gateway's escrow for that token.

I could not execute or fully trace the ISMP delivery/commitment-marking order in this environment to conclusively prove step 3/4 end-to-end; a Devin session with full repo/tooling access should reproduce this with a Foundry test analogous to `IntrinsicIntentsReentrancyTest.sol` but targeting `evm/tron/contracts/apps/IntentGatewayV2.sol`.
