### Title
Webhook HMAC does not bind the `shop` (or `topic`/`webhook-id`) header, enabling cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from unauthenticated HTTP headers and forwarded to the app's webhook handler as the tenant-identifying fields. Because the HMAC covers only the body, any actor who can obtain one legitimate `(body, hmac)` pair signed with the shared app `client_secret` — e.g. by triggering a webhook on their own, unprivileged shop installation — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header. The signature still validates, and the handler processes the payload attributed to a shop that never sent it.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

and `hmac`, `shop`, `topic`, `webhook_id`, `api_version` are all pulled independently from headers: [2](#0-1) 

`HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string` (i.e., the raw body) and compares it to the received `hmac`: [3](#0-2) 

`Registry.process` calls this validator and, if it passes, immediately trusts `request.shop` (along with `topic`, `api_version`, `webhook_id`) to build `WebhookMetadata` passed to the app's handler — with no separate check binding `shop` to the signed content: [4](#0-3) 

The binding that should hold is:

`shop_bound_by_hmac == shop_used_by_handler`

but in this code:

`shop_bound_by_hmac = ∅ (HMAC only covers @raw_body)` while `shop_used_by_handler = request.shop (unauthenticated header)`

Since the `client_secret`/`api_secret_key` used to sign webhooks is shared across every shop that installs the app (it is an app-level, not per-shop, secret), any unprivileged party who installs the app on their own store can trigger a real webhook, capture the legitimate `(raw_body, x-shopify-hmac-sha256)` pair Shopify sent for their own shop, and then POST that identical body+HMAC to the app's webhook endpoint again while changing only the `shop-domain` (and optionally `topic`/`webhook-id`) header to a victim shop's domain. `HmacValidator.validate` still succeeds because the signed bytes (the body) are unchanged, and `Registry.process` hands the handler a `WebhookMetadata` claiming the data came from the victim shop.

### Impact Explanation
This is a cross-tenant identity-binding break: the gem authenticates *content* but not the *sender/shop claim* that the host application uses to route/attribute the webhook. Any app built on top of `ShopifyAPI::Webhooks::Registry.process` that trusts `data.shop` from `WebhookMetadata` (the documented, intended usage) will process attacker-controlled — but validly-HMAC'd — data under an arbitrary shop identity, without the attacker ever needing the app's `client_secret` or any victim credentials. This satisfies the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is high for any multi-tenant app: obtaining a legitimate `(body, hmac)` pair requires nothing more than installing the app on one's own store (a normal, unprivileged action available to any merchant) and capturing one webhook delivery. The replay itself is a single forged HTTP POST to the app's public webhook endpoint with a substituted `shop-domain` header — no cryptographic material needs to be recovered.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) values as part of the signed material verified against the HMAC, or otherwise cryptographically bind the header-derived `shop` to the specific delivery (e.g., verify the claimed shop against a `Content-Type`/nonce/webhook-id uniqueness check tied to a persisted delivery record for that shop), so that a captured signature for shop A cannot be replayed while claiming to be shop B.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` (fully legitimate, unprivileged action).
2. Attacker triggers any subscribed webhook topic (e.g., `orders/create`) on their own store and captures the raw request Shopify sends to the app's webhook endpoint, including the `x-shopify-hmac-sha256` header and raw body.
3. Attacker resends the identical body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `OpenSSL::HMAC.hexdigest(..., raw_body)` against the received HMAC — this still matches because the body/HMAC pair is untouched.
5. `Registry.process` builds `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)` and invokes the app's handler, which now processes attacker-controlled data as if it originated from `victim-shop.myshopify.com`.
