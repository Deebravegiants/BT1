Audit Report

## Title
CORS wildcard allowlist bypass via naive suffix match allows malicious origin impersonation - ([File: core/services/gateway/network/httpserver.go])

## Summary
The Gateway's user-facing HTTP server's `isAllowedOrigin` function implements wildcard CORS origin matching using `strings.HasSuffix(originHost, allowedHost)` without verifying a subdomain boundary (`.`) precedes the match. This allows an attacker who registers a domain ending in the same characters as an operator's configured wildcard suffix (e.g. `evilethereum.org` matching `*.ethereum.org`) to be treated as a valid subdomain and receive a reflected `Access-Control-Allow-Origin` header.

## Finding Description
In `isAllowedOrigin`, when an allowed origin entry starts with `*.`, the code strips the prefix and performs a bare suffix comparison: [1](#0-0) . This has no boundary check, so `strings.HasSuffix("evilethereum.org", "ethereum.org")` returns `true` even though `evilethereum.org` is not a subdomain of `ethereum.org`. The successful match is then reflected directly into the response header in `handleRequest`: [2](#0-1) , setting `Access-Control-Allow-Origin` to the exact spoofed `Origin` value along with permissive `Access-Control-Allow-Methods`/`Access-Control-Allow-Headers`. There is no other validation layer (no allowlist normalization, no domain-label comparison) between the operator's configured wildcard string and this raw suffix check, so the flaw is not mitigated elsewhere in the request path.

## Impact Explanation
This allows an attacker-controlled origin to impersonate a trusted subdomain and issue credentialed/cross-origin JSON requests to the Gateway's `/user` endpoint that should only be permitted from genuine subdomains of the operator-configured allowlist entry. This is a concrete "gateway request impersonation / allowlist bypass" class impact against the internet-facing Gateway component, reachable without any privileged access — an unprivileged external actor only needs to register a cheap domain with the right suffix and send an HTTP request with a spoofed `Origin` header.

## Likelihood Explanation
Exploitation requires only registering an inexpensive domain ending in the configured wildcard suffix and sending a normal HTTP request with a crafted `Origin` header — no credentials, node compromise, or privileged role needed. It is reachable whenever an operator enables `CORSEnabled` with a wildcard entry in `CORSAllowedOrigins`, which is a supported and demonstrated configuration pattern (as shown in the integration test config and the existing wildcard unit tests) rather than a discouraged misconfiguration. The vulnerability is in the matching *logic* itself, not caused by operator error.

## Recommendation
Enforce a proper subdomain boundary in the wildcard branch: after stripping `*.`, check `originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost)` instead of a bare `strings.HasSuffix`. Alternatively, split `originHost` on `.` and compare the trailing labels exactly against `allowedHost`'s labels, or use a vetted domain-matching library.

## Proof of Concept
1. Start the Gateway HTTP server with `CORSEnabled = true` and `CORSAllowedOrigins = ["https://*.ethereum.org"]` (as demonstrated in `TestHTTPServer_HandleRequest_CORSEnabled_FromAllowedOriginWildcards` at `core/services/gateway/network/httpserver_test.go` lines 152-166, which can be adapted with origin `https://evilethereum.org`).
2. Send a `POST` request to the server's configured path with header `Origin: https://evilethereum.org`.
3. Observe `isAllowedOrigin` returns `true` because `strings.HasSuffix("evilethereum.org", "ethereum.org")` is `true`.
4. Observe response contains `Access-Control-Allow-Origin: https://evilethereum.org`, confirming the bypass.
