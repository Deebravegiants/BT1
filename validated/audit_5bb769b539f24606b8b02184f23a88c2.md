### Title
`_withdraw` reverts entirely on a single failed token transfer, permanently freezing all escrowed order funds - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._withdraw` iterates over every token in a `WithdrawalRequest.tokens` array and releases escrow via `IERC20.safeTransfer` (or a native `_sendValue`) for each entry in a single loop, with no per-token failure isolation. If any one token in that array cannot be transferred — e.g. the beneficiary is blacklisted by a USDT-style token, the token is paused, or any other ERC20 in the order reverts on transfer — the entire function reverts, and none of the other (otherwise transferable) tokens in that order are released either.

### Finding Description
`_withdraw` is the single choke point for releasing escrowed order funds for both same-chain and cross-chain intents: [1](#0-0) 

```
function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
    ...
    uint256 len = body.tokens.length;
    for (uint256 i; i < len; i++) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (amount == 0) continue;

        uint256 escrowed = _orders[body.commitment][token];
        if (escrowed == 0) revert UnknownOrder();

        _orders[body.commitment][token] = escrowed - amount;
        if (token == address(0)) {
            _sendValue(beneficiary, amount);
        } else {
            IERC20(token).safeTransfer(beneficiary, amount);
        }
    }
    ...
}
```

`Order.inputs` (and therefore `WithdrawalRequest.tokens`) is a `TokenInfo[]`, so a single order can escrow multiple distinct tokens (e.g. USDC + USDT), as seen in `placeOrder`'s input-transfer loop [2](#0-1) . `_withdraw` is invoked from every code path that releases escrow:

- `IntrinsicIntents` same-chain fill and partial fill, which builds `escrowedInputs` across all input tokens and calls `_withdraw(body, false, isFullyFilled)` [3](#0-2) .
- Cross-chain `RedeemEscrow`/`RefundEscrow` delivery via `ExtrinsicIntents.onAccept`, and `cancelOrder`, which release all of an order's escrowed inputs at once through the same `WithdrawalRequest.tokens` array.

Because `safeTransfer` bubbles up any revert from the underlying `transfer` call (blacklist check, pause, insufficient allowance in a malicious/non-standard implementation, or `IERC20TransferFail`-style checks as in the audited LooksRare `_transferTokenOut`), a single problematic token in the array reverts the entire `_withdraw` call — including the `_orders[...] -= amount` state updates for the earlier tokens in the loop (transaction atomicity), and, on `finalize=true`, the transaction-fee payout and `_filled[commitment]` marking as well.

This mirrors the referenced LooksRare `YoloV2` finding exactly: `withdrawDeposits`/`claimPrizes` loop over all of a user's deposits in one transaction and call `_transferTokenOut`, so one blacklisted/failing ERC20 transfer blocks release of every other token too. `IntentsBase._withdraw`'s single-loop, no-isolation design is architecturally the same pattern.

### Impact Explanation
If any single input token in a multi-token order becomes untransferable to the beneficiary (recipient blacklisted by a stablecoin issuer, token paused, token implements non-standard/failing `transfer`), the entire escrow for that order — including unrelated, perfectly-transferable tokens — becomes permanently stuck in the `IntentGatewayV2`/`IntentsBase` contract. This applies to:
- Solvers who fill an order and are owed multiple escrowed input tokens (loss of legitimate fill proceeds).
- Users refunding via `cancelOrder` or `RefundEscrow` after a cross-chain cancellation, who lose access to all their escrowed inputs, not just the failing one.
- Same-chain partial fills, where a partial withdrawal of `escrowedInputs` across several tokens can be blocked entirely by one bad token.

This is a permanent freezing-of-funds condition reachable by a single order placement/fill/cancel with no privileged action required, satisfying the Medium/High bar of "permanent freezing of funds."

### Likelihood Explanation
Likelihood is moderate to high given the protocol's own token model: `IntentGatewayV2`/`IntentsBase` support arbitrary whitelisted-or-not `TokenInfo[]` combinations per order (no evidence in the reviewed code of a restriction preventing USDT-class blacklistable tokens, or any token whose `transfer` can legitimately revert, from being combined with other tokens in a single order's `inputs`/`output.assets`). Any regulated/blacklistable stablecoin (USDT, USDC after sanctions, etc.) used as one of several inputs is enough to trigger the freeze for the whole order once the beneficiary address is blacklisted after order placement, or simply if the token pauses/reverts for unrelated reasons.

### Recommendation
Isolate per-token transfer failures in `_withdraw` (and the equivalent Tron `withdraw` function) so that one failing transfer doesn't block the others:
- Wrap each token transfer in a try/catch (or low-level `call` with failure handling) and, on failure, leave that token's escrow balance intact (do not decrement `_orders[...]`) while still releasing the successfully-transferable tokens and finalizing the order.
- Emit an event recording which token(s) failed to transfer, and expose a separate `retryWithdraw`/`sweepFailedToken` entry point that lets the beneficiary specify exactly which tokens to withdraw (mirroring the LooksRare-recommended fix of letting the caller select tokens to withdraw), so a stuck token doesn't block release of the rest, and doesn't block `finalize` (fee payout, `_filled` marking) either.

### Proof of Concept
1. Solver/user places a cross-chain order (`ExtrinsicIntents`/`IntrinsicIntents`) with `order.inputs = [USDC: 1000, USDT: 1000]`, escrowed in `IntentsBase._orders[commitment]`.
2. Before the order is filled or cancelled, the beneficiary address (solver on fill, or original user on refund) is blacklisted by Tether for an unrelated reason.
3. On fill completion (`RedeemEscrow` delivered via `onAccept`) or on `cancelOrder`/`RefundEscrow`, `_withdraw` is invoked with `body.tokens = [USDC, USDT]`.
4. The loop first decrements `_orders[commitment][USDC]` and calls `safeTransfer` successfully, then reaches USDT and `safeTransfer` reverts because the beneficiary is blacklisted.
5. The whole transaction reverts, rolling back the USDC decrement too — no re-entry path releases only the USDC, since `WithdrawalRequest.tokens` for that commitment is fixed by the original order's `inputs`/message body and there is no user-controlled "skip this token" option. Both USDC and USDT remain permanently locked in the contract.
