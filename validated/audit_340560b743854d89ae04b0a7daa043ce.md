### Title
Balance conservation bypass via `one_yocto_on_promise` subsidy exemption in `promise_batch_action_function_call_weight` - (File: runtime/near-vm-runner/src/logic/logic.rs)

### Summary
`promise_batch_action_function_call_weight` contains a `skip_deduct` branch that, when `config.one_yocto_on_promise` is enabled and the calling contract's `current_account_balance` is zero, allows attaching exactly `1` yoctoNEAR to an outgoing `FunctionCall` action without deducting it from the sender's balance. The skipped amount is only added to a bookkeeping counter (`subsidized_amount`) while the actual promise action still carries the full `amount` to the receipt that gets dispatched to the receiver, meaning value is created without a corresponding debit.

### Finding Description
In `runtime/near-vm-runner/src/logic/logic.rs` (`promise_batch_action_function_call_weight`, ~lines 3096-3121): [1](#0-0) 

```
let skip_deduct = amount == Balance::from_yoctonear(1)
    && self.config.one_yocto_on_promise
    && self.result_state.current_account_balance.is_zero();
if skip_deduct {
    self.result_state.subsidized_amount = self.result_state.subsidized_amount
        .checked_add(amount).expect("subsidized_amount overflow");
} else {
    self.result_state.deduct_balance(amount)?;
}
self.ext.append_action_function_call_weight(
    receipt_idx, method_name, arguments, amount, gas, GasWeight(gas_weight),
)?;
```

Regardless of whether `deduct_balance` runs, `append_action_function_call_weight` is always called with the full `amount` (`1` yoctoNEAR). This is what gets serialized into the outgoing `FunctionCall` action of the receipt. When that receipt is later applied at the receiver, the receiver's account is credited with the attached deposit (`function_call.deposit`), as seen in `action_function_call` in `runtime/runtime/src/function_call.rs` where the outcome/account balance flow assumes `deposit` was already conserved on the sender side (`account.amount().checked_add(function_call.deposit)` check at the top only guards for overflow, not conservation) [2](#0-1) .

Because the sender's `current_account_balance` was zero before the call and is never actually decremented in the `skip_deduct` path, the sender's balance remains zero after emitting the promise, yet the receipt sent onward still carries a real `1`-yoctoNEAR deposit. The only trace of the missing debit is the informational `subsidized_amount` counter, which is fed into `result.subsidized_amount` in `action_function_call` (`runtime/runtime/src/function_call.rs:223-224`) via `safe_add_balance`, but this is accumulated as metadata, not subtracted from any global supply/burn ledger before the receipt with the real deposit is dispatched. Every subsequent call from the same zero-balance account can repeat this indefinitely because the precondition (`current_account_balance.is_zero()`) is preserved across calls.

This is not standard/original NEAR protocol logic — mainline nearcore has no `one_yocto_on_promise` config flag or `skip_deduct`/`subsidized_amount` subsidy mechanism for promise actions; this appears to be a deliberately or erroneously introduced exemption.

### Impact Explanation
Each subsidized call mints exactly 1 yoctoNEAR that is delivered to the receipt's receiver without ever being debited from the sender, violating global supply conservation. While the per-call amount is minimal (1 yoctoNEAR), the exploit is fully repeatable — an attacker's zero-balance account can issue an unbounded number of such promises across many function calls/receipts (bounded only by gas/transaction throughput), accumulating unconserved value system-wide. This matches the NEAR bounty "balance/supply violation — token minting out of thin air" impact class, since new value enters the receiver's balance with no origin balance decrease.

### Likelihood Explanation
Preconditions are trivially attacker-controlled: any ordinary account can deploy a contract, drive its `current_account_balance` to zero (e.g., a freshly created contract account with no attached balance, or after spending down to zero), and then repeatedly call a method that invokes `promise_batch_action_function_call_weight` with `amount = 1`. The only gate is the protocol config flag `config.one_yocto_on_promise`; if enabled for the current protocol version, there is no additional permission, signature, or validator cooperation required — this is reachable purely through normal RPC-submitted transactions/contract calls, making it fully repeatable and low-cost (only requiring gas for the calls).

### Recommendation
Remove the `skip_deduct`/`one_yocto_on_promise` exemption entirely, or, if intended as a legitimate feature, ensure the subsidized amount is conserved: either (a) require `deduct_balance` to still run (rejecting the call if the balance is insufficient, consistent with normal accounting), or (b) if the amount is genuinely meant to be minted for zero-balance UX cases, account for it in a system-wide, protocol-enforced compensating burn (e.g., debiting a genesis/subsidy pool) rather than a per-execution informational counter, and ensure that counter is reconciled against total supply before the receipt with the real deposit is dispatched, not merely recorded as metadata.

### Proof of Concept
Integration test plan (in `runtime/runtime/src/tests/apply.rs` or an equivalent runtime integration test):
1. Deploy a contract account `attacker.test` with `current_account_balance == 0` and `config.one_yocto_on_promise = true` for the active protocol version.
2. Have the contract, in its method, call `promise_batch_action_function_call_weight` with `amount = 1` yoctoNEAR N times (e.g., N = 1000), targeting `receiver.test`.
3. Record `total_supply` (sum of all account balances + locked balances in the trie) before executing the transaction and after all resulting receipts are fully applied.
4. Assert (expected to fail on current code, confirming the bug):
   - `receiver.test`'s balance increased by exactly N yoctoNEAR.
   - `attacker.test`'s balance remains 0 (never debited).
   - Global `total_supply_after == total_supply_before` (conservation) — this assertion FAILS, demonstrating `total_supply_after == total_supply_before + N`, i.e., N yoctoNEAR minted with no source debit.
   - `result.subsidized_amount == N` is tracked but never subtracted from `total_supply` or burned anywhere in the apply pipeline.
