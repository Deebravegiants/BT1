### Title
Webhook shop-domain identity spoofing via HMAC that only covers the body, not the `shop` header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates an inbound webhook solely by checking `Utils::HmacValidator.validate(request)` against `request.to_signable_string`, which is defined as `@raw_body` only. The `shop` (tenant identity), `topic`, `api_version`, and `webhook_id` values are read straight from HTTP headers and are never included in the HMAC-signed material, yet they are handed to the app's `WebhookHandler` as validated data.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` value [1](#0-0) . For webhooks, `Webhooks::Request#to_signable_string` returns only `@raw_body`, while `shop`, `topic`, `api_version`, and `webhook_id` are pulled from request headers (`shopify-shop-domain`/`x-shopify-shop-domain`, etc.) and are not part of the signed bytes at all [2](#0-1) .

`Registry.process` treats a passing HMAC check as proof the whole request is authentic, then constructs `WebhookMetadata` directly from those unauthenticated headers and forwards it to the app-supplied handler: `raise ... unless Utils::HmacValidator.validate(request)` followed immediately by `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [3](#0-2) . The gem's own documentation tells integrators that `process` "will verify the request did indeed come from Shopify" and that `data.shop` is "The shop domain of the webhook" to be trusted by the handler [4](#0-3) , encouraging patterns like `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` that key tenant-scoped business logic off `data.shop` [5](#0-4) .

The broken identity binding is: `shop header used by handler == shop bound by HMAC`, but in fact `shop header used by handler != any field covered by HmacValidator.validate`. An unprivileged attacker who legitimately installs the target app on their own shop (any free/dev shop, no special privilege needed) will receive genuinely Shopify-signed webhooks — valid `(raw_body, hmac)` pairs computed with the app's real `client_secret` — for their own shop. Because the HMAC never covers the `shop-domain` header, the attacker can replay that exact raw body and HMAC to the app's webhook endpoint while substituting an arbitrary victim's `shop-domain` (and `webhook-id`/`topic`, if desired) in the headers. `HmacValidator.validate` still returns true because it only recomputes/compares against `@raw_body`, so `Registry.process` calls the handler with `shop: <attacker-chosen victim shop>` and body content the attacker fully controls (subject to it being a real signed payload from their own installation, e.g. an `orders/create` or `app/uninstalled` body).

### Impact Explanation
This breaks the tenant boundary the whole webhook mechanism is supposed to enforce: an unprivileged user (any shop owner able to install the app) can inject webhook events that the host application will process as if they originated from a completely different, victim shop. Depending on the handler logic the docs encourage (`shop_domain: data.shop` driving DB writes, uninstall/GDPR flows, order/customer state), this is a cross-tenant data-integrity/access issue — the impact category matches "cross-tenant access" from spoofed tenant identity, since the identity binding (HMAC ↔ shop) that the library implies exists is absent.

### Likelihood Explanation
Likelihood is high for any app that follows the gem's documented pattern of trusting `data.shop`/`WebhookMetadata#shop` after `Registry.process` succeeds. The only requirement is that the attacker be able to install the target app once on a shop they control (which is generally open to any internet user for public apps) and control an HTTP client capable of crafting arbitrary headers — no access token, `client_secret`, or victim credentials are needed.

### Recommendation
Bind the trust boundary correctly: either (a) include `shop`, `topic`, and `webhook_id` in the HMAC-signed material for webhooks (requires coordination with Shopify's signing, likely not changeable by the gem alone), or (b) document/enforce that `Registry.process`/`WebhookMetadata` only guarantees body integrity, and require callers to independently verify `request.shop` against a known/installed shop list (e.g., cross-check with stored sessions) before trusting it in `handle`. At minimum, update `docs/usage/webhooks.md` to stop stating the shop header is verified, and consider surfacing a warning in `Webhooks::Registry.process`/`Webhooks::Request` that only the raw body is authenticated.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and enables the `orders/create` webhook.
2. Shopify sends the attacker's app endpoint a legitimately signed webhook: headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw_body>`, plus `raw_body` containing arbitrary order JSON the attacker crafted for their own store.
3. Attacker captures this exact `(raw_body, hmac)` pair (e.g., via a debug proxy on their own server) and replays it directly to the same app endpoint, only changing the `x-shopify-shop-domain` header to `victim-shop.myshopify.com`.
4. `Webhooks::Request.new` parses this into `shop = "victim-shop.myshopify.com"`, `hmac = <unchanged>` [6](#0-5) .
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC only over `raw_body` and succeeds since `raw_body` is unmodified [7](#0-6) .
6. The app's handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body, and processes it as a legitimate event for the victim's tenant.
