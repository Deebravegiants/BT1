### Title
Webhook HMAC signature does not cover the `shop`, `topic`, or `webhook_id` fields, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes/verifies the webhook HMAC exclusively over the raw request body, while the shop identity (`x-shopify-shop-domain`), topic, API version, and webhook id are all read directly from unauthenticated HTTP headers. `Webhooks::Registry.process` trusts `request.shop` to attribute the incoming event to a tenant without that value ever being covered by the signature check.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Registry.process` validates the request purely through this body-only HMAC and then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`, `request.api_version`) — all sourced from headers that are excluded from the signable string — to build the `WebhookMetadata` passed to the app's handler: [2](#0-1) 

The identity binding that should hold is:
`shop authenticated by HMAC == shop the handler acts on`

Here, the equality is broken: the HMAC only authenticates `raw_body` bytes, but the handler acts on the `shop-domain` header, which is never part of the signed material. Anyone who can obtain one legitimately-signed `(raw_body, hmac)` pair — e.g. an attacker who installs the app on their own store and receives any real webhook delivery — can replay that exact body/HMAC to the app's public webhook endpoint while substituting a different `x-shopify-shop-domain` header. `HmacValidator.validate` will still pass because it only recomputes the HMAC over `@raw_body`: [3](#0-2) 

The handler then executes with `data.shop` set to the attacker-chosen victim shop, even though nothing about the victim shop was ever verified.

### Impact Explanation
This crosses the "cross-tenant access" boundary called out as Critical impact: any app that scopes actions, session lookups, or record updates in its webhook handler by `WebhookMetadata#shop` can be manipulated into processing/attributing events under a different, unrelated merchant's identity — using only a webhook payload the attacker legitimately received for their own store. No access token, `client_secret`, or leaked credential is required.

### Likelihood Explanation
Webhook endpoints are public HTTP endpoints by design (no bearer-auth gate other than this HMAC check), and an attacker only needs to be a normal (even free-trial) merchant with the app installed to obtain one valid `(raw_body, hmac)` pair to replay with a forged `shop-domain` header. This requires no privileged access and no interaction with the victim.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed/verified material — or otherwise cryptographically bind them to the request — rather than relying solely on a body-only HMAC while trusting separate, unauthenticated headers for identity attribution.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com` and capture a real webhook delivery: raw body `B` and header `x-shopify-hmac-sha256: H` (valid for the app's `api_secret_key`).
2. Replay a POST to the app's webhook endpoint with the same body `B` and header `x-shopify-hmac-sha256: H`, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `HmacValidator.validate` recomputes HMAC over `B` only and succeeds.
4. `Registry.process` dispatches the handler with `WebhookMetadata#shop == "victim.myshopify.com"`, causing the app to act as if the event originated from the victim shop.
