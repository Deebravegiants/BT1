### Title
Webhook shop identity not covered by HMAC allows cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and exposes the HMAC-signable content as the raw request body only, while the `shop` (tenant) attribute is read from an unauthenticated header. `ShopifyAPI::Webhooks::Registry.process` validates only the body's HMAC and then hands the handler a `WebhookMetadata` struct whose `shop` field comes straight from that unauthenticated header. Any unprivileged actor who can install the target app on their own (or any) shop can obtain a validly-HMAC'd webhook body/signature pair and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to an arbitrary victim shop, causing the app to process attacker-controlled data as if it originated from the victim tenant.

### Finding Description
The identity binding that must hold is:

`shop attributed to the verified payload (WebhookMetadata#shop) == shop that actually produced the HMAC-verified bytes`

This binding is broken because the HMAC only covers the raw body, not the shop header: [1](#0-0) [2](#0-1) 

`to_signable_string` returns only `@raw_body`; the `shop` accessor reads directly from `shopify_header("shop-domain")`, a value that plays no role in the HMAC computation.

`HmacValidator.validate` verifies exactly that raw-body signable string against the app's single, app-wide `api_secret_key` (the same secret used for every merchant that installs the app): [3](#0-2) 

`Registry.process` then trusts `request.shop` unconditionally and forwards it to the handler: [4](#0-3) [5](#0-4) 

Because the same `api_secret_key` signs webhooks for every shop that has the app installed, an unprivileged user needs only to install the app on a shop they control (a normal, free action for a public/dev app) to obtain a `(body, hmac)` pair that is valid under the app's shared secret. They can then send this exact body+HMAC to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain`/`X-Shopify-Hmac-Sha256` headers so the `shop` value points at any other shop (including ones that never installed the app). `HmacValidator.validate` will accept it because it never inspects the shop header, and `Registry.process` will dispatch a `WebhookMetadata` claiming the forged shop, body, topic, etc.

### Impact Explanation
This is a cross-tenant confusion vulnerability at the trust boundary this gem is responsible for: the entire purpose of `Webhooks::Registry.process`/`HmacValidator` is to let the host application trust `WebhookMetadata#shop` and `#body` as authentically originating from that shop. Because the shop identity is not cryptographically bound to the verified bytes, an attacker can inject arbitrary attacker-chosen payloads (e.g., `orders/create`, `app/uninstalled`, `customers/data_request`) that the app will process as if they came from a victim merchant, leading to cross-tenant data corruption, forged business events, or triggering victim-shop-scoped side effects (e.g., uninstall handling, data deletion flows) without the victim's shop ever sending anything.

### Likelihood Explanation
Any user can install a public/development instance of a Shopify app (no privileged credentials, access tokens, or `client_secret` needed) and thereby receive real, validly-signed webhooks. Forging the `shop-domain` header on a replayed request is trivial and requires no cryptographic material beyond what the attacker already legitimately possesses from their own shop's webhook deliveries.

### Recommendation
Bind the shop domain into the value that is actually HMAC-verified, or otherwise cryptographically tie the claimed shop to the signature — e.g., include the `shop-domain` header (and topic) in `to_signable_string`, or cross-check the shop against Shopify's known/expected shop for that HMAC via an out-of-band authenticated channel, before constructing `WebhookMetadata` and invoking the handler in `ShopifyAPI::Webhooks::Registry.process`.

### Proof of Concept
1. Attacker installs the target public app on their own shop `attacker.myshopify.com`; app subscribes to a webhook topic (e.g. `orders/create`).
2. Shopify delivers a real webhook to the app's endpoint: body `B`, header `X-Shopify-Hmac-Sha256: HMAC(api_secret_key, B)`, header `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker captures this exact `(B, HMAC)` pair and resends it to the same app endpoint, only changing `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers (only presence, not correctness, of shop header is checked in `initialize`), `HmacValidator.validate` succeeds because it only checks `B` against the shared `api_secret_key`, and `Registry.process` calls the handler with `WebhookMetadata.new(... shop: "victim.myshopify.com", body: B ...)` — the app now processes attacker-crafted data attributed to a shop the attacker never controls.
