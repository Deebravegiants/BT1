### Title
Webhook processing trusts unauthenticated `shop`/`topic`/`webhook_id` headers not covered by the HMAC - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authenticated once `Utils::HmacValidator.validate(request)` succeeds, but the HMAC computed by `Request#to_signable_string` only covers the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values that are handed to the app's handler are read straight from unauthenticated HTTP headers, so the binding `hmac_verified_bytes == bytes_the_handler_acts_on` does not hold.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all derived from HTTP headers that are never mixed into the signable string: [2](#0-1) 

`Registry.process` validates only the body HMAC and then dispatches directly on the unauthenticated `request.topic`/`request.shop`, forwarding the unauthenticated `shop`, `webhook_id`, and `api_version` values into `WebhookMetadata` that the app's handler code trusts as the origin of the payload: [3](#0-2) 

Because the HMAC secret (`client_secret`) is shared across every shop that has installed the app, any merchant who has legitimately installed the app can generate a genuinely-signed webhook body for their own shop (e.g. by triggering an order/customer event) and capture the resulting `(raw_body, hmac)` pair. Replaying that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) to name a different, victim tenant shop passes `HmacValidator.validate` unchanged, since only the body is checked. The handler then receives `WebhookMetadata` claiming the payload originated from the victim shop, even though the header value was never bound to the signature.

### Impact Explanation
If a host application's webhook handler uses `WebhookMetadata#shop` to key storage, look up sessions/access tokens, or make authorization decisions (the documented and expected usage pattern shown in `docs/usage/webhooks.md` and `WebhookMetadata`), an attacker-controlled shop-domain header lets one tenant's genuinely-signed webhook body be attributed to a different tenant. This is a cross-tenant data/identity confusion: the gem asserts an identity (`shop`) that was never covered by the cryptographic check it just performed, which is exactly the same class of bug as the reported `isTimeout` false positive — a check that signals "verified" for a case it does not actually verify.

### Likelihood Explanation
Exploitation only requires the capability any regular merchant already has: installing the app on their own store to receive legitimately HMAC-signed webhooks, then replaying the captured body with edited headers to the shared webhook endpoint. No access to the app's `client_secret`, TLS interception, or privileged account is required, satisfying the "unprivileged internet user" bar.

### Recommendation
Bind the identity fields to the signature instead of trusting headers independently of the HMAC:
- Include `shop`, `topic`, and `webhook_id` (in addition to the body) in the signable string used by `HmacValidator`, or
- Have `Registry.process` cross-check `request.shop` against an expected/allow-listed shop associated with the delivery (e.g., validated against the shop that owns the registered webhook subscription) before dispatching, rather than trusting the header verbatim.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook event so Shopify sends a real request with a valid `X-Shopify-Hmac-Sha256` computed over some `raw_body` using the app's `client_secret`.
2. Capture that `(raw_body, hmac)` pair.
3. POST to the app's webhook endpoint with the same `raw_body` and `X-Shopify-Hmac-Sha256`, but set `X-Shopify-Shop-Domain: victim.myshopify.com` (and, if desired, a different `X-Shopify-Topic`).
4. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers, and `HmacValidator.validate(request)` in `Registry.process` succeeds because only `raw_body` is checked: [4](#0-3) 
5. The registered handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` for data that actually originated from `attacker.myshopify.com`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
