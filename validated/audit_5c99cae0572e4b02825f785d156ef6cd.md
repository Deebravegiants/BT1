### Title
Token donation to a curve `Pair` permanently disables the supply-trigger graduation path, freezing curve-raised LT and the LP reserve - (File: `packages/contracts/src/Router.sol`, `packages/contracts/src/Pair.sol`, `packages/contracts/src/Bonding.sol`)

### Summary
Any unprivileged trader can permanently disable the "supply" graduation trigger (`tokenBalance() == 0`) for a bonding-curve token by donating the launched `Token` directly to its `Pair` via a plain ERC20 `transfer`. This inflates `Pair.tokenBalance()` (the real ERC20 balance) above the pair's stored virtual `tokenReserve`, which permanently disarms the overflow-cap branch in `Router._computeBuy` that is the *only* mechanism that ever lets `tokenBalance()` reach exactly `0`. If the token's LT never appreciates enough to cross the USD trigger (the documented "flat/bear market" scenario), the token is stuck in `Lifecycle.Curve` forever — all curve-raised LT and the 250M `LP_RESERVE` tokens never reach the HyperSwap pool, and holders can never exit to a liquid market.

### Finding Description
`Router._computeBuy` (`packages/contracts/src/Router.sol:127-148`) computes the uncapped `tokensOut` from the constant-product formula and only overrides it with the "overflow cap" (`tokensOut = realBalance`) when `tokensOut > realBalance`:

```
uint256 realBalance = pair.tokenBalance();
if (tokensOut > realBalance) {
    tokensOut = realBalance;
    ...
}
```

`tokensOut` from the uncapped formula is mathematically bounded strictly below the pair's stored virtual `reserveToken` (it asymptotically approaches `reserveToken` but a finite `amountIn` can never reach it, per the constant-product math `tokensOut = reserveToken - k/newReserveAsset`). In the honest flow, `realBalance` (the real ERC20 balance held by the pair) tracks `reserveToken - LP_RESERVE` exactly, so `realBalance < reserveToken` always — this is asserted as an explicit invariant in `test_inv_virtualReserveAlwaysExceedsRealBalance` (`packages/contracts/test/GraduationInvariants.t.sol:362-377`). Because `realBalance < reserveToken`, the cap branch is guaranteed to eventually trigger on the closing buy, forcing `tokensOut = realBalance` and draining `tokenBalance()` to exactly `0` — this is what makes the supply trigger (`packages/contracts/src/Bonding.sol:689`, `IPair(pair).tokenBalance() == 0`) reachable at all.

Any address can break this invariant for free by simply calling `Token(tokenAddr).transfer(pairAddr, amount)` with `amount` large enough (as demonstrated by the project's own `test_donation_realBalanceExceedsReserveToken` in `packages/contracts/test/Zap.t.sol:967-977`, which the test-suite explicitly stages via `_stageDonationAttack`). Once a donation pushes `tokenBalance() > reserveToken`, `tokensOut` (bounded below `reserveToken`) can *never* exceed `tokenBalance()` again, so the overflow-cap branch in `_computeBuy` never fires again. Since donations and legitimate buys shift `tokenBalance()` and `reserveToken` by the same amount per buy (both decrease by `tokensOut`), the gap created by the donation is a **permanent constant offset** — it does not shrink as more buys occur. `tokenBalance()` can therefore never reach `0` again through any sequence of buys, so `canGraduate`'s supply leg (`packages/contracts/src/Bonding.sol:689`) is permanently disarmed for that token.

The USD leg (`packages/contracts/src/Bonding.sol:691-694`) is the only remaining path to graduation, and it depends entirely on the paired BounceTech LT's `exchangeRate()` crossing `graduationThresholdUsd`. The project's own documentation (`docs/contracts-scope.md:71`) explicitly acknowledges the supply trigger exists specifically to "handle flat/bear markets where $9K is never reached" — i.e., the protocol's own threat model assumes there are realistic conditions where the USD leg alone will never fire. Under exactly those conditions, a token griefed this way is permanently stuck in `Lifecycle.Curve`: `finalizeGraduation`/`triggerGraduation` never become reachable, and all LT raised by traders on the curve plus the 250M `LP_RESERVE` tokens held by `Bonding` remain frozen with no path to the HyperSwap pool and no withdrawal mechanism (`Bonding.sol` has no owner-level graduation override or reserve-recovery path).

### Impact Explanation
This is a permanent freeze of protocol funds reachable by any unprivileged address: the curve-raised LT (traders' deposited value) and the 250M `LP_RESERVE` tokens per affected launch become permanently unreachable if the LT's exchange rate never independently crosses the USD threshold. Creators also lose the ability to ever have their token progress to a liquid, tradeable HyperSwap pool. This matches the project's own severity bar for graduation-availability bugs (see the amount of defensive engineering the codebase already invests in "brick resistance" for `finalizeGraduation`), but this particular vector — using an ERC20 donation to permanently disarm the supply trigger before graduation is ever entered — is not covered by any of the existing donation-resistance tests, which only verify that `previewLtUntilGraduation` and `Zap.buy`/`sell` don't underflow/revert (`packages/contracts/test/Zap.t.sol:939-1007`); none of them assert that the token can still eventually graduate via the supply leg after a large donation.

### Likelihood Explanation
The attack requires the attacker to acquire and donate more of the launched `Token` than the gap between `reserveToken` and the honest `realBalance` (i.e., more than roughly the amount already sold on the curve, since the invariant `realBalance < reserveToken` must be flipped). This is achievable early in a token's life when little has been sold (small buy on the curve mints a comparatively large token amount out relative to `reserveToken`, per the `sold·(S-sold)/S` parabola), making the attack cheapest right after launch, before the anti-snipe delay window even closes if the attacker is the creator's own second wallet, or immediately after trading opens for any griefer targeting a specific token. No special role or permission is required — only `IERC20.transfer`.

### Recommendation
`Router._computeBuy`'s overflow-cap branch should not rely solely on the comparison `tokensOut > realBalance`; it should also handle (or `Bonding`/`Pair` should reject) the case where `realBalance >= reserveToken` (i.e., a real balance already at or above the virtual reserve), for example by capping `tokensOut` at `min(uncapped tokensOut, realBalance, reserveToken - 1)` and by adding a dedicated supply-trigger path that reads `min(tokenBalance(), reserveToken - LP_RESERVE)` rather than raw `tokenBalance()`, so a donation cannot desynchronize the invariant that the supply trigger depends on. Alternatively, reject direct `Token` transfers into `Pair` from anyone other than `Router`/`Bonding`, or have `_prepareGraduationLiquidity`/`canGraduate` recompute the supply trigger from `reserveToken - LP_RESERVE_remaining` (derived state) instead of a live `balanceOf` read that donations can permanently corrupt.

### Proof of Concept
1. Creator launches a token via `Zap.createToken` with the minimum seed; `Bonding.launch` opens the curve with `reserveToken = 1,000,000,000e18`, `realBalance = 750,000,000e18`.
2. Attacker (any unprivileged wallet) buys a portion of the curve via `Bonding.buy`/`Zap.buy` sized so that `tokensOut > 250,000,000e18` — the project's own helper `_stageDonationAttack` (`packages/contracts/test/Zap.t.sol:944-965`) does exactly this, buying with `drainLtSpent = _initialVirtualLt()` LT to receive `tokensOut = 500,000,000e18` tokens.
3. Attacker calls `Token(tokenAddr).transfer(pairAddr, tokensOut)` to donate all the purchased tokens back to the pair. `IPair(pairAddr).tokenBalance()` (real ERC20 balance) now exceeds `reserveToken`, exactly as asserted by `test_donation_realBalanceExceedsReserveToken` (`packages/contracts/test/Zap.t.sol:967-977`).
4. From this point on, no finite `Bonding.buy` call can ever push `tokensOut` (bounded below `reserveToken`) above the now-inflated `realBalance`, so `Router._computeBuy`'s cap branch (`packages/contracts/src/Router.sol:141-147`) never executes again, and `IPair.tokenBalance()` can never return `0` again — the supply leg of `canGraduate` (`packages/contracts/src/Bonding.sol:689`) is permanently `false`.
5. If the paired LT's `exchangeRate()` never independently rises enough to satisfy the USD leg (`packages/contracts/src/Bonding.sol:691-694`), `canGraduate` returns `false` forever; `triggerGraduation` and the inline post-buy trigger in `_executeBuy` never fire; `finalizeGraduation` is never reachable. The curve-raised LT and the 250M `LP_RESERVE` tokens sit permanently in `Bonding`/`Pair` with no recovery path.
