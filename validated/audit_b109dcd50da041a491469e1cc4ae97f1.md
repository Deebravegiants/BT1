Based on my investigation, I've identified a valid analog vulnerability.

### Title
Cross-Tenant Webhook Impersonation via `shop` Header Not Bound to HMAC Signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
Shopify webhook authenticity is validated via HMAC, but the HMAC computation covers only the raw request body, not the `shop`, `topic`, `webhook_id`, or `api_version` headers. When `Registry.process` accepts a webhook, it forwards the unauthenticated `shop` header value straight to the app's handler as if it were verified, allowing a valid signature captured from one shop's webhook to be replayed with a spoofed `shop` header identifying a different tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, whose contract is that `hmac` authenticates `to_signable_string`. Here, `to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers, entirely outside the signed data: [2](#0-1) 

`HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` (the body) against the received HMAC: [3](#0-2) 

`Registry.process` treats a passing HMAC check as authenticating the entire request, then dispatches `request.shop` — the unauthenticated header — to the app's handler as the tenant identity: [4](#0-3) 

This is the exact bug class from the report: an identity-critical field (`shop`, the tenant binding) is *acted upon* by the library (passed to the handler as trusted tenant context) but is *not covered* by the cryptographic check (`hmac` binds only to `raw_body`). The equality that should hold — `shop_authenticated == shop_acted_upon` — is broken: `HmacValidator.validate` authenticates `(body, hmac)`, while `Registry.process` acts on `(body, shop_header)`, and `shop_header` is disjoint from what was verified.

### Impact Explanation
Any unprivileged user who can install the app on their own shop (a normal, unprivileged merchant) legitimately receives Shopify-signed webhooks for their own shop — i.e., they possess a valid `(raw_body, hmac)` pair signed with the app's shared secret. Because the `shop` header is not part of the signed payload, the attacker can replay that exact valid body+HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `Utils::HmacValidator.validate` still returns `true` (it only checks the body), and `Registry.process` calls the handler with `shop: <victim shop>` and the attacker-controlled body content, both of which the host application will treat as authentic data belonging to the victim tenant. This lets the attacker inject/forge webhook events (e.g., `orders/create`, `app/uninstalled`, `customers/redact`) attributed to a different, arbitrary shop, causing cross-tenant data corruption or state confusion — a cross-tenant boundary violation.

### Likelihood Explanation
The precondition (attacker installs the app on their own store, a normal unprivileged action) is trivial to satisfy for any public app. No access token, `client_secret`, or leaked credential is required — the attacker only needs a validly-signed webhook that Shopify already sent them for their own tenant, and the ability to POST an HTTP request to the app's public webhook endpoint with modified headers. This is a straightforward, reliably reproducible replay.

### Recommendation
Bind the `shop` (and ideally `topic`/`api_version`/`webhook_id`) to the same trust boundary as the HMAC by including them in the signed payload verification path, or by requiring the host app to independently confirm the `shop` header corresponds to a shop with a currently active, matching webhook registration/session before trusting it. At minimum, document prominently that `WebhookMetadata#shop` is not itself HMAC-verified and must not be trusted as an authenticated tenant identifier without additional shop-registration cross-checking by the consuming application.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g. by creating an order), capturing the raw POST body `B` and the valid `X-Shopify-Hmac-Sha256` header `H` that Shopify computed over `B` using the app's shared secret.
2. Attacker sends a new POST request to the app's webhook endpoint with:
   - Body: the same `B` (or any body producing a validly-known `H`, or reusing `B` verbatim)
   - Headers: `X-Shopify-Hmac-Sha256: H`, `X-Shopify-Topic: orders/create`, `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only recomputes HMAC over `B` — the `shop` header is irrelevant to this check (`lib/shopify_api/webhooks/request.rb` lines 35-38, `lib/shopify_api/utils/hmac_validator.rb` lines 26-31).
4. The handler registered for `orders/create` is invoked with `WebhookMetadata` where `shop == "victim-shop.myshopify.com"`, even though the request was neither sent nor signed by Shopify on behalf of that shop — the app processes forged, cross-tenant webhook data.
