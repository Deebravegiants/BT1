### Title
Wrong destination-tx/status reported for batched POA withdrawals sharing the same asset - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` (and the standalone `waitForWithdrawalCompletion` in `internal-utils`) resolve which withdrawal record in the POA Bridge API response belongs to a given `WithdrawalIdentifier` by matching **only on `assetId`** — never on `index`, `amount`, or `destinationAddress`. When a batch of withdrawals in the same NEAR transaction contains two or more entries for the same token (e.g., two BTC withdrawals to different addresses/amounts in one `processWithdrawal` batch call), `findMatchingWithdrawal` returns the *first* API record with a matching `near_token_id`, regardless of which of the batch's withdrawals it actually corresponds to.

### Finding Description
`findMatchingWithdrawal` in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:418-427` is:
```ts
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
```
It is invoked from `describeWithdrawal` at `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:313-343`, using `args.withdrawalParams.assetId` as the only matching key even though `args.index` (from `WithdrawalIdentifier`, see `packages/intents-sdk/src/shared-types.ts:409-423`) is available on the same identifier object and is never used. The exact same limitation exists in the standalone helper `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts:144-153`, used by `sdk.waitForWithdrawalCompletion` for batch withdrawal completion tracking.

The equality that should hold is: *the destination tx hash reported for withdrawal at array index `i` must correspond to the on-chain withdrawal the caller actually created at index `i`* (same amount, same destination). Instead, the code substitutes *any* withdrawal record whose token matches, breaking that equality whenever ≥2 withdrawals of the same asset exist in one batch — e.g. `processWithdrawal({ withdrawalParams: [ {assetId:"nep141:btc.omft.near", amount:100000n, destinationAddress:"addrA"}, {assetId:"nep141:btc.omft.near", amount:900000n, destinationAddress:"addrB"} ] })`. Both `describeWithdrawal` calls (index 0 and index 1) query the same POA `getWithdrawalStatus` response and `find()` on it, so **both resolve to the same, first-matching withdrawal record** — the withdrawal for index 1 is reported as completed with the txHash and effectively the identity belonging to index 0's withdrawal (or vice versa depending on API ordering, which the code comment explicitly states is "unsorted").

This is exactly the "status/hash misreport" bug class named in scope: an integrator relying on `sdk.processWithdrawal`'s `destinationTx` array (or `waitForWithdrawalCompletion`'s per-criteria promises) to credit/mark-complete a withdrawal by index will attribute the wrong destination chain tx hash to the wrong recipient/amount, potentially crediting/confirming completion for the wrong leg of the batch (e.g. marking the large withdrawal to `addrB` as "completed with txHash X" when `X` actually belongs to the small withdrawal to `addrA`).

### Impact Explanation
This maps to the in-scope Critical/High impact class: "a status or hash misreport making an integrator credit or refund twice" (or, symmetrically, an integrator marking a withdrawal complete using a foreign tx hash, causing incorrect bookkeeping / double-processing risk when both withdrawals of the same asset in a batch settle around the same time). The comment in the code (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:410-416`) explicitly acknowledges: *"Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported."* — i.e. the authors are aware the invariant does not hold, but the SDK's public batch API (`processWithdrawal`, `waitForWithdrawalCompletion`, `createWithdrawalCompletionPromises`) does not prevent or reject callers from submitting exactly that unsupported shape; nothing validates or rejects duplicate-asset batches before they reach `describeWithdrawal`.

### Likelihood Explanation
Reaching this requires only calling the public, documented batch withdrawal API (`sdk.processWithdrawal` / `sdk.waitForWithdrawalCompletion`) with two `WithdrawalParams` entries sharing the same `assetId` routed through the POA bridge — a normal usage pattern per the SDK's own README batch-withdrawal example (`packages/intents-sdk/README.md:521-563`), not an attacker action against the protocol itself. No malicious relayer/solver/admin behavior is required; it is triggered by an integrator's own legitimate batch composition.

### Recommendation
Extend `findMatchingWithdrawal` (in both `poa-bridge.ts` and `internal-utils/.../waitForWithdrawalCompletion.ts`) to disambiguate by more than `assetId` alone — e.g. also match on `amount` (and `destinationAddress` when available), or track and consume matched withdrawal indices so the same API record cannot satisfy two different `describeWithdrawal`/`findMatchingWithdrawal` calls, or explicitly reject/validate batches containing duplicate `assetId` entries at `processWithdrawal`/`signAndSendWithdrawalIntent` time until proper per-item correlation (e.g. an `external_id`/memo returned by the POA API) is available.
