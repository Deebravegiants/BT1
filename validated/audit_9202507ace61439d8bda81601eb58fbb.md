`handleConsensus` is a public, unauthenticated entrypoint on `HandlerV2` — anyone can call it with an arbitrary consensus proof bytestring, which flows into the BEEFY verifier's `Codec.Encode(commitment)`. [1](#0-0) 

### Title
Quadratic CPU/gas blow-up in `Codec.Encode(Commitment)` via unbounded BEEFY payload array reassembly - (File: evm/src/consensus/Codec.sol)

### Summary
`Codec.Encode` SCALE-encodes a BEEFY `Commitment` by iteratively calling `bytes.concat` inside a `for` loop over `commitment.payload`, re-copying the entire accumulated buffer on every iteration instead of using a single pre-sized buffer or an efficient append strategy.

### Finding Description
`Codec.Encode(Commitment memory commitment)` builds up the encoded payload with: [2](#0-1) 
Each call to `bytes.concat` in Solidity allocates a brand-new `bytes` array in memory and copies both operands into it — there is no in-place append. Because `payload` on the left-hand side grows by one element's worth of bytes each iteration and is fully recopied on every subsequent iteration, the total work is O(n²) in the number of `Payload` entries in `commitment.payload`, mirroring the exact bug class described in the Bandit advisory (repeated `IO.iodata_length`/re-traversal of a left-nested, ever-growing accumulator).

This function is invoked from `verifyMmrUpdateProof` in `evm/src/consensus/EcdsaBeefy.sol`: [3](#0-2) 
`payloadLength` (the size of `commitment.payload`) is attacker-controlled: it comes straight from `relayProof.signedCommitment.commitment`, which is decoded from the raw `proof` bytes supplied to the completely permissionless `handleConsensus(IHost host, bytes calldata proof)` entrypoint: [4](#0-3) 
There is no cap anywhere in this path on `commitment.payload.length` or on the size of each `Payload.data` field before `Codec.Encode` is invoked — the only prior checks are the authority-set id match and the `checkParticipationThreshold` on `sigLen` (the vote count), neither of which bounds the payload array.

### Impact Explanation
Because `handleConsensus` is unauthenticated and reachable by any address (no relayer whitelist, no fee gate visible in this function), an attacker can submit a proof whose `Commitment.payload` array contains a very large number of small `Payload` entries. Each additional entry costs O(current buffer size) in both gas (memory expansion + copy) and CPU, so the total cost to fully process the array is quadratic. On EVM this manifests primarily as excessive gas consumption up to the block gas limit for a single transaction — sufficient to make `handleConsensus` calls with adversarial payloads gas-griefing/DoS the consensus-update path (denying legitimate BEEFY consensus advancement, which blocks all cross-chain message delivery through that consensus client) rather than a pure off-chain CPU-pinning DoS, but the underlying root cause (repeated `bytes.concat` re-copy in a loop over an attacker-sized array) is architecturally identical to the reported Bandit flaw. This matches the "route unable to deliver messages" acceptance criterion for the exercise, since a griefed/expensive consensus update path stalls state updates and thus message delivery for the affected state machine.

### Likelihood Explanation
Likelihood is high: `handleConsensus` requires no privilege, no bond, and no prior state; the attacker only needs to submit calldata with a bloated `payload` array (each entry can be as small as a 2-byte id + minimal data) while still passing (or failing after the encode cost is already paid) the validator-set/threshold checks. Since Solidity charges gas per operation, the attacker mostly harms themselves via gas cost unless the goal is to make legitimate relayer submissions cross the block gas limit by crafting a payload that is expensive but not so large it can't be included — the same "large frame count with tiny payload" spirit as the original Bandit report, adapted to metered gas rather than free CPU.

### Recommendation
Rewrite `Codec.Encode(Commitment memory commitment)` to precompute the total encoded length and write into a single pre-allocated buffer once (or accumulate lengths/pointers first and do a single `abi.encodePacked`/`bytes.concat` at the end), eliminating the repeated re-copy of the growing accumulator. Additionally, consider bounding `commitment.payload.length` to the small number of well-known payload IDs (e.g. MMR root) actually expected by the protocol, rejecting proofs with excess payload entries before entering the loop.

### Proof of Concept
Not independently executed (no terminal/EVM access in this environment); the root-cause chain is demonstrated purely via static code paths cited above: `handleConsensus` (unauthenticated) → `IConsensusV2(host.consensusClient()).verify` → `verifyMmrUpdateProof` → `Codec.Encode(commitment)`, where `commitment.payload.length` is fully attacker-controlled proof data and `Codec.Encode`'s loop body performs a `bytes.concat` re-copy of the whole accumulated buffer per iteration.
