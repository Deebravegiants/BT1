## Title
Webhook `topic` and `shop` headers are not bound to the HMAC, enabling cross-tenant webhook forgery - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a request as authentic once `Utils::HmacValidator.validate(request)` succeeds, and then dispatches to a handler and builds `WebhookMetadata` using the request's `topic` and `shop` values. However, `Webhooks::Request#to_signable_string` returns only the raw JSON body, so the HMAC signs solely the body — never the `x-shopify-topic` or `x-shopify-shop-domain` headers that the library uses for handler dispatch and tenant identification.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

and `topic`/`shop` are read straight from HTTP headers with no cryptographic binding: [2](#0-1) 

`HmacValidator.validate` computes the signature purely over `verifiable_query.to_signable_string`: [3](#0-2) 

`Registry.process` uses this validation as its sole authenticity gate, then routes on the unauthenticated `topic` header and forwards the unauthenticated `shop` header straight to the handler: [4](#0-3) 

The identity binding that should hold is:
`shop/topic that Shopify actually generated the HMAC-signed body for == shop/topic delivered to the handler`

Because only the body is signed, an attacker who obtains any one genuine `(raw_body, hmac)` pair (trivially achievable by installing the app on a shop they control, which any unprivileged internet user can do, and capturing the webhook Shopify sends them) can replay that exact body/HMAC to the app's public webhook endpoint while freely rewriting the `x-shopify-shop-domain` and `x-shopify-topic` headers. `Utils::HmacValidator.validate` still returns `true` because it only checks the raw body against the shared `api_secret_key`, and `Registry.process` will happily dispatch the forged topic/shop to the registered handler.

### Impact Explanation
This breaks the tenant/topic identity binding that `Registry.process` implicitly promises by gating on `HmacValidator.validate`: a caller reasonably assumes that once the HMAC check passes, `topic` and `shop` on the resulting `WebhookMetadata` are also authentic. In practice an attacker can:
- Make the app believe an attacker-controlled payload originated from a victim's shop (`shop` field forged), causing cross-tenant data confusion/corruption in any host application that keys persistence, session lookup, or entitlement checks off `WebhookMetadata#shop`.
- Redirect a body to a different topic handler than the one Shopify actually delivered it for (`topic` header forged), invoking application logic (e.g. mandatory GDPR handlers, `app/uninstalled`, billing webhooks) with attacker-chosen but validly-"signed" content.

This matches the Critical "cross-tenant access" bucket in scope, since it lets one tenant's traffic be attributed to another tenant purely through this gem's own webhook-processing code path.

### Likelihood Explanation
Any internet user can install the target app on their own free/dev shop, capture one legitimate webhook delivery (body + `x-shopify-hmac-sha256`), and replay it with modified `shop-domain`/`topic` headers to the app's public webhook endpoint. No access token, `client_secret`, or privileged account is required — only the ability to install the app once, which is the normal unprivileged entry point for any Shopify app.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or otherwise bind them to the request) as part of the signable content verified by `HmacValidator`, or independently verify that the `shop`/`topic` headers match values the application already trusts (e.g. cross-check `shop` against an existing session/installation record) before constructing `WebhookMetadata` or dispatching to a handler in `Registry.process`.

### Proof of Concept
1. Install the target Shopify app on an attacker-owned development shop `attacker.myshopify.com`.
2. Trigger a webhook (e.g. `orders/create`) with attacker-controlled body content; capture the raw POST body and the `x-shopify-hmac-sha256` header Shopify sends.
3. Replay the exact same raw body and `x-shopify-hmac-sha256` value to the app's public webhook endpoint, but set:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: customers/data_request` (or any other registered topic)
4. `Utils::HmacValidator.validate` returns `true` (it only checks the unchanged body), and `Registry.process` dispatches the forged topic to its handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though Shopify never sent this data for that shop/topic.
