### Title
Webhook shop attribution is trusted from unsigned headers while only `@raw_body` is HMAC-covered - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` proves nothing about the `shop-domain`, `topic`, `api-version`, or `webhook-id` headers. `Request#initialize` only checks that these headers are *present*, never that they match what was actually signed, so `Registry.process` builds `WebhookMetadata` (and dispatches to a handler) using shop/topic values that were never covered by the signature.

### Finding Description
The intended binding is: `hmac_valid?(request) == true` implies `request.shop`, `request.topic`, `request.api_version`, and `request.webhook_id` are the values Shopify actually generated for that signed payload. In reality:

- `to_signable_string` returns `@raw_body` only: [1](#0-0) 
- `shop`, `topic`, `api_version`, `webhook_id` are all read straight from headers via `shopify_header`, with no relation to `@raw_body`: [2](#0-1) [3](#0-2) 
- `initialize` only verifies these headers exist, never that they are well-formed or tied to the signed body: [4](#0-3) 
- `HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` (i.e. HMAC over body only) and compares it to the `hmac-sha256` header: [5](#0-4) 
- `Registry.process` gates only on this body-HMAC check, then dispatches purely from the unsigned `request.topic` header and builds `WebhookMetadata` from the unsigned `request.shop`, `request.api_version`, `request.webhook_id`: [6](#0-5) 

Exploit flow: an attacker with their own development shop legitimately receives a real Shopify webhook (`raw_body`, `x-shopify-hmac-sha256`, `x-shopify-topic`, `x-shopify-shop-domain`, ...) signed with the app's shared `api_secret_key`. Because none of the routing/attribution headers are inside the signed string, the attacker can replay the exact same `raw_body`/HMAC pair to the app's public webhook endpoint while substituting `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) with a victim shop's domain. `HmacValidator.validate` still returns `true` because it only re-hashes `@raw_body`, so `Registry.process` accepts the forged attribution and calls `handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...))` as if Shopify itself sent that event for the victim shop.

No existing guard closes this gap: `HmacValidator.validate` only checks the body; `ShopValidator` isn't invoked in this path at all; there is no comparison between the header shop and any session or previously-registered webhook shop; Sorbet signatures only enforce type (`String`), not provenance or well-formedness.

### Impact Explanation
Any handler logic keyed off `WebhookMetadata#shop` (e.g., session/token cleanup on `app/uninstalled`, GDPR data deletion on `customers/redact` or `shop/redact`, billing/subscription state changes) can be triggered for an arbitrary victim shop domain chosen by the attacker, using only a webhook the attacker legitimately received for their own shop. This is a cross-tenant authentication bypass: the app treats attacker-forged shop/topic attribution as authentic Shopify origin data. It is repeatable indefinitely — a single captured (body, hmac) pair can be replayed against any number of forged victim shop domains and topics recognized by the registry.

### Likelihood Explanation
Preconditions are low-cost and fully within the described attacker capability: register a development shop, install the target app, and receive one real webhook of any registered topic. No `api_secret_key` or other credential is needed since the attacker reuses a genuinely-signed body/HMAC pair rather than forging a new signature. The app's webhook endpoint is public by design (it must accept unauthenticated POSTs from "Shopify"), so nothing prevents the attacker from posting directly to it with modified headers.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the value signed/verified, or otherwise cryptographically bind them to the payload (e.g., validate `shop` against an existing session/registration for the topic before dispatch) rather than trusting header presence alone in `Request#initialize`.

### Proof of Concept
```ruby
# test/webhooks/registry_shop_spoof_test.rb
require_relative "../test_helper"

class ShopSpoofTest < Test::Unit::TestCase
  def setup
    ShopifyAPI::Context.setup(
      api_key: "key", api_secret_key: "secret", host_name: "app.com",
      scope: "read_products", is_embedded: true, is_private: false, api_version: "unstable"
    )
    @raw_body = '{"id":123}'
    @hmac = Base64.encode64(
      OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), "secret", @raw_body)
    ).strip

    received = []
    handler = Class.new do
      define_method(:handle) { |data:| received << data.shop }
    end.new
    ShopifyAPI::Webhooks::Registry.add_registration(
      topic: "app/uninstalled", delivery_method: :http, path: "/wh", handler: handler
    )
    @received = received
  end

  def test_same_signature_two_different_shops
    request1 = ShopifyAPI::Webhooks::Request.new(
      raw_body: @raw_body,
      headers: {
        "x-shopify-topic" => "app/uninstalled",
        "x-shopify-hmac-sha256" => @hmac,
        "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
        "x-shopify-api-version" => "2023-01",
        "x-shopify-webhook-id" => "1",
      },
    )
    request2 = ShopifyAPI::Webhooks::Request.new(
      raw_body: @raw_body,
      headers: {
        "x-shopify-topic" => "app/uninstalled",
        "x-shopify-hmac-sha256" => @hmac, # identical signature
        "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged
        "x-shopify-api-version" => "2023-01",
        "x-shopify-webhook-id" => "2",
      },
    )

    ShopifyAPI::Webhooks::Registry.process(request1)
    ShopifyAPI::Webhooks::Registry.process(request2)

    assert_equal(["attacker-shop.myshopify.com", "victim-shop.myshopify.com"], @received)
  end
end
```
Both calls pass `Utils::HmacValidator.validate` (same body/HMAC), yet `WebhookMetadata#shop` differs — proving the verified value (body/HMAC) and the acted-upon value (`shop`) diverge.
