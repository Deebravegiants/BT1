## Analysis

The rPGP advisory describes a bug class: **crafted/malformed inputs reaching unvalidated arithmetic causing a Rust panic that halts a program with no fund-safety impact but a denial-of-service.** The closest analog on alt.fun is Solidity's equivalent of a "panic" — an unguarded arithmetic overflow/`revert` deep in the HyperSwap pre-seed rebalance math, reachable by an unprivileged attacker's pre-seed shape, that can permanently brick `Bonding.finalizeGraduation` — exactly the property the codebase's own comments and `AGENTS.md` call "the load-bearing security property" that "MUST never revert."

### The bug [1](#0-0) 

```solidity
function _noFeeSwapInput(
    uint256 reserveIn, uint256 reserveOut, uint256 targetN, uint256 targetD, uint256 maxSwap
) internal pure returns (uint256) {
    if (reserveIn == 0 || reserveOut == 0 || targetN == 0 || targetD == 0 || maxSwap == 0) return 0;
    uint256 product = Math.mulDiv(reserveIn * reserveOut, targetN, targetD);
    ...
```

`reserveIn * reserveOut` is a raw `uint256` multiply performed **before** being handed to `Math.mulDiv`, and the subsequent `Math.mulDiv(product, targetN, targetD)` still requires the *final result* to fit in 256 bits — OZ's `Math.mulDiv` reverts if it doesn't. The function's own natspec acknowledges this: "Constructed adversarial inputs that violate this would `revert` rather than silently truncate" [2](#0-1) .

This is called from `_pairRebalance`, which only guards against `s == 0` and `expectedOut == 0` — it does **not** guard against `_noFeeSwapInput` itself reverting: [3](#0-2) 

The call chain from the permissionless entry point is: `finalizeGraduation` → `_seedUniswapV2Direct` → `_seedRebalancing` → `_pairRebalance` → `_noFeeSwapInput`, in the Regime-3 hostile-mint-pre-seed branch [4](#0-3) .

An attacker can reach Regime 3 by front-running as documented in `AGENTS.md`: create the HyperSwap pair, transfer TOKEN/LT to it at a chosen ratio, then `pair.mint(attacker)` — baking arbitrary large `(reserveIn, reserveOut)` into the pool before `finalizeGraduation` runs [5](#0-4) . If the attacker sizes the pre-seed reserves large (e.g. by first buying up the curve's sellable supply and holding a large LT position) while the graduation's cached `targetD` (`tokensForLP`/`ltFromPair`) is small — plausible whenever a highly leveraged/volatile LT's `exchangeRate()` spikes and the USD trigger fires on a tiny amount of real LT raised — the product `reserveIn * reserveOut * targetN / targetD` exceeds `type(uint256).max`, and `Math.mulDiv` reverts.

### Impact

Because `_seedUniswapV2Direct` is the *only* path out of `Lifecycle.Graduating` [6](#0-5) , an uncaught revert here permanently bricks `finalizeGraduation`. The token is stuck in `Graduating` forever: all curve-raised LT and the 250M reserved tokens remain parked in `Bonding` [7](#0-6) , unreachable by any other function, and every trader/holder is permanently frozen out (buys/sells revert with `TokenIsGraduating`). This directly violates the documented brick-resistance guarantee: "`_seedUniswapV2Direct` MUST never revert under any pre-seed shape... because a brick locks every holder in `Graduating` forever" [8](#0-7) .

### Title
Unguarded arithmetic overflow in `Bonding._noFeeSwapInput`'s raw `reserveIn * reserveOut` multiply can permanently brick `finalizeGraduation` via a hostile HyperSwap pre-seed - (File: `packages/contracts/src/Bonding.sol`)

### Summary
`_noFeeSwapInput`, used by the hostile-pre-seed rebalance defense inside `finalizeGraduation`, computes `Math.mulDiv(reserveIn * reserveOut, targetN, targetD)`. `Math.mulDiv` only protects the internal 512-bit multiply/divide — if the final quotient doesn't fit in 256 bits it reverts. An attacker who front-runs graduation by minting hostile LP into the HyperSwap pair with sufficiently large, imbalanced `(reserveIn, reserveOut)`, paired with a graduation whose cached `tokensForLP`/`ltFromPair` is small, can force this revert. Unlike the `s == 0` / `getAmountOut == 0` cases, this failure mode is not caught by `_pairRebalance`'s fallback logic, so it propagates all the way up and permanently reverts `finalizeGraduation`.

### Finding Description
- `_noFeeSwapInput` (packages/contracts/src/Bonding.sol:1507-1522) performs a raw `reserveIn * reserveOut` multiplication outside `Math.mulDiv`'s safe 512-bit path, then feeds it into `Math.mulDiv(product, targetN, targetD)`, whose result must still fit in `uint256`.
- `_pairRebalance` (Bonding.sol:1414-1429) only special-cases `s == 0` and `expectedOut == 0`, both of which fall back to `_seedDirectMint`. It has no protection against `_noFeeSwapInput` itself reverting from an oversized product.
- `finalizeGraduation` → `_seedUniswapV2Direct` → `_seedRebalancing` (Bonding.sol:1321-1353) invokes `_pairRebalance` unconditionally in the Regime-3 (mint pre-seed) branch, whenever the pre-existing hostile pool reserves diverge from the target ratio.
- Reserves `(reserveIn, reserveOut)` are entirely attacker-controlled via the documented front-run: `factory.createPair` + `transfer` + `pair.mint(attacker)` [9](#0-8) . `targetN`/`targetD` are the graduation's cached `(tokensForLP, ltFromPair)`, which can be arbitrarily small when the USD trigger fires with a tiny real-LT-raised amount against a heavily-pumped LT `exchangeRate()`.

### Impact Explanation
A successfully bricked `finalizeGraduation` permanently freezes: the token's curve-raised LT (drained from the pair into `Bonding` in phase 1), the 250M reserved tokens earmarked for LP, and all trader token balances (which can no longer be sold, since `Lifecycle.Graduating` blocks trading and there is no other function to complete or roll back graduation). This is a permanent freezing-of-funds outcome, matching the High-severity bar.

### Likelihood Explanation
Requires the attacker to (a) win the front-run window between phase 1 (`_enterGraduating`) and phase 2 (`finalizeGraduation`) — a window the protocol's own threat model treats as reliably attacker-reachable (it's the premise of the entire pre-seed-defense subsystem) — and (b) size the pre-seed reserves and/or wait for a graduation whose `targetD` is small enough that the product overflows. The second condition depends on real-world LT volatility (large `exchangeRate()` spikes make tiny `ltFromPair` graduations plausible) and on the attacker's own token/LT holdings; it is not guaranteed on every graduation but is a concrete, constructible scenario the code's own comments acknowledge as possible ("Constructed adversarial inputs that violate this would revert").

### Recommendation
Compute the full `reserveIn * reserveOut * targetN / targetD` using a genuinely overflow-safe 512-bit path (e.g., a `mulDiv3`/two-step `mulDiv` that never performs a raw `uint256 * uint256` outside of protected multiplication), and/or explicitly bound `reserveIn`/`reserveOut`/`targetN`/`targetD` before the call so the final quotient is provably `< 2^256`. Wrap `_noFeeSwapInput`'s call site so that any revert (not just `s == 0`) falls back to `_seedDirectMint`, preserving the documented "never revert" brick-resistance guarantee.

### Proof of Concept
1. Launch a token paired to a highly volatile/leveraged LT; let it approach the USD graduation threshold with a very small real-LT-raised amount (achievable when `exchangeRate()` is large), so `_enterGraduating` caches a tiny `ltFromPair`/`tokensForLP`.
2. Attacker front-runs phase 2: calls `factory.createPair(token, lt)`, transfers a large, deliberately imbalanced amount of TOKEN and LT to the pair (acquired via ordinary curve buys / LT purchases), then calls `pair.mint(attacker)`.
3. Keeper or anyone calls `Bonding.finalizeGraduation(tokenAddress)`. Inside `_seedRebalancing`, the pool is far from ratio, so `_pairRebalance` is invoked with `reserveIn`/`reserveOut` set to the attacker's inflated reserves and `targetN`/`targetD` set to the tiny cached values.
4. `_noFeeSwapInput`'s `Math.mulDiv(reserveIn * reserveOut, targetN, targetD)` computes a quotient exceeding `type(uint256).max` and reverts, propagating through `_pairRebalance` → `_seedRebalancing` → `_seedUniswapV2Direct` → `finalizeGraduation`.
5. Every subsequent call to `finalizeGraduation` for this token reverts identically (the hostile reserves are unchanged), permanently trapping the token in `Lifecycle.Graduating` with its LT and 250M tokens frozen in `Bonding`.

    function _pairRebalance(
        RebalanceParams memory p
    ) internal returns (bool) {
        uint256 s = _noFeeSwapInput(p.reserveIn, p.reserveOut, p.targetN, p.targetD, p.maxSwap);
        if (s == 0) return false;

        // Quote from the pair so the output tracks its live fee; a value
        // derived from a stale fee rate would trip the pair's K-check.
        uint256 expectedOut = IUniswapV2Pair(p.pair).getAmountOut(s, p.tokenIn);
        if (expectedOut == 0) return false;

        IERC20(p.tokenIn).safeTransfer(p.pair, s);
        (uint256 amount0Out, uint256 amount1Out) = p.tokenInIs0 ? (uint256(0), expectedOut) : (expectedOut, uint256(0));
        IUniswapV2Pair(p.pair).swap(amount0Out, amount1Out, address(this), new bytes(0));
        return true;
    }

    function _noFeeSwapInput(
        uint256 reserveIn,
        uint256 reserveOut,
        uint256 targetN,
        uint256 targetD,
        uint256 maxSwap
    ) internal pure returns (uint256) {
        if (reserveIn == 0 || reserveOut == 0 || targetN == 0 || targetD == 0 || maxSwap == 0) {
            return 0;
        }
        uint256 product = Math.mulDiv(reserveIn * reserveOut, targetN, targetD);
        uint256 newIn = Math.sqrt(product);
        if (newIn <= reserveIn) return 0;
        uint256 s = newIn - reserveIn;
        return s > maxSwap ? maxSwap : s;
    }

### The exploit

A vanilla UniswapV2 pair is deployable by anyone: `factory.createPair(token, lt)` is permissionless, and after creation anyone can call `pair.mint(to)` against pre-transferred tokens. So between phase 1 (`_enterGraduating` flips lifecycle to `Graduating` and caches `tokensForLP / ltFromPair`) and phase 2 (`finalizeGraduation` mints LP via `pair.mint(lpLock)`), an attacker can:

1. Front-run by calling `factory.createPair(token, lt)` themselves
2. `transfer(pair, smallToken)` and `transfer(pair, smallLT)` at any ratio they choose
3. Call `pair.mint(attacker)` — they now own LP at a hostile reserve ratio

When our `pair.mint(lpLock)` runs in phase 2 against this non-empty pair, V2's mint formula picks up the existing reserves:

```
liquidity = min(amount0 · totalSupply / reserve0, amount1 · totalSupply / reserve1)
```

The `min(...)` arm whose denominator is bigger relative to its numerator wins, and the OTHER arm's "excess" deposit is donated pro-rata to existing LP holders — i.e. to the attacker. Two harms:

- **Wrong opening price.** Post-mint reserves are `(R_attacker + T_a, R_attacker + T_b)`, so the LP opens at `(R_a + T_a) / (R_b + T_b)`, NOT at the curve close `T_a / T_b`. A `$15` LT pre-seed at 50% off curve close opens the pool ~454 bps off.
- **LP capture.** The wasted-side excess goes to the attacker's LP claim. A `1 wei + 1 LT` pre-seed (~`$1` attack budget) captures ~34 bps of LP.

A cheaper variant skips step 3 entirely: `transfer(pair, dust) + pair.sync()` forces the stored reserves to the dust ratio without minting any LP, leaving the pair at `reserves > 0 && totalSupply == 0`. Regime 1 below covers both shapes by keying on supply rather than reserves.

### Brick-resistance contract

`_seedUniswapV2Direct` MUST never revert under any pre-seed shape. The brick-resistance contract is the load-bearing security property — it ranks above the LP-capture defense, because a brick locks every holder in `Graduating` forever. The pre-seed defense is layered to honour this:

- **Regime 1/2 don't touch the router.** Even if the V2 router is misbehaving, the empty + donation paths run on direct pair calls.
- **`_pairRebalance` falls back to a direct mint when no swap can run.** `_noFeeSwapInput` may return `s == 0`, or the pair's fee-charging `getAmountOut(s)` may round to zero, against a pre-seed whose swap-output side is dust — `pair.swap` would otherwise revert with `INSUFFICIENT_OUTPUT_AMOUNT`. In either case `_pairRebalance` returns `false`, and `_seedRebalancing` overpowers the dust with a direct `transfer + pair.mint` at the cached `tokensForLP / ltFromPair` ratio (`_seedDirectMint`), opening the pool on-ratio. This is safe specifically because the swap only rounds to zero when the reserves are negligible against this graduation's inventory: the V2 `min()` donation to the attacker's pre-existing LP is then bounded by `max(reserveToken/tokensForLP, reserveLT/ltFromPair)`, which vanishe ... (truncated)
- **`_routerDepositAndDispose` uses `min0=1, min1=1`.** Slippage protection on `addLiquidity` exists to defend against a third party moving the pool ratio between quote and execution; here we set the ratio ourselves in `_pairRebalance` in the same atomic tx, so there's no third party to defend against. The `=1` (rather than `=0`) trips V2's degenerate-ratio guard so the call can't silently land at near-zero.
- **No external dependency on the router slot being correct post-deploy.** `uniswapV2Router` is set at `initialize` time alongside `uniswapV2Factory` and is rejected if zero. There's no live setter — rotation requires a UUPS upgrade so the change is visible on-chain ahead of any in-flight graduation.

### Dynamic LP Seeding (zero price gap)

The problem: the reserve asset (LT) has a varying USD price, so the exact number of LP tokens needed to make the DEX pool open at the last curve price is not known ahead of time. Naively seeding the LP with the full 250M reserve would create a large price gap that arbitrage bots would immediately close, transferring value out of the protocol.

Our approach: compute the exact `tokensForLP` at graduation time so the LP opens at **precisely** the last curve price. Burn whatever is left of the 250M reserve.

`_graduate()` performs, in order:

1. Read `(reserve0, reserve1)` from the Pair **before** any state mutation.
2. Burn any unsold real curve tokens from the pair (`unsoldBurned`). This also burns any tokens donated to the pair via direct ERC20 transfer.
3. Recover `virtualLtReserve = Pair.k() / Token.TOTAL_SUPPLY()` and compute `ltFromPair = reserve1 - virtualLtReserve` — the real LT raised by the curve, excluding the launch-time virtual seed AND any LT donated to the pair. Drain exactly that amount via `Router.graduate(token, ltFromPair)`. Donated LT remains in the curve pair, reachable only via `Pair.transferAsset` which is gated by `Router`'s `BONDING_ROLE`.
4. Compute `tokensForLP = (ltFromPair × reserve0) / reserve1` — the unique amount that sets the LP price `ltFromPair / tokensForLP` equal to the last curve price `reserve1 / reserve0`. Capped at `lpReserveTotal` as a defensive guard (parabola math proves `tokensForLP ≤ lpReserveTotal` by construction).
