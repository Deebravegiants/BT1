### Title
Anyone can permanently block an `EvmHost` fee-token migration by donating dust of the old fee token - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.updateHostParamsInternal` refuses to change `feeToken` unless the host's current balance of the *old* fee token is exactly zero. Because any address can transfer an arbitrary (even 1-wei) amount of the old fee token to the host contract at any time, an unprivileged attacker can front-run/re-grief the cross-chain-governance call that migrates the fee token, permanently reverting `updateHostParams` whenever it attempts to change `feeToken`. This is the same "balance-guard griefing" bug class as the PoolTogether `VaultBooster.setBoost` finding: a strict `balance == 0` (or `balance <= X`) check inside a config-update function that anyone can violate with a trivial token transfer.

### Finding Description
`updateHostParamsInternal` is the internal logic invoked by `updateHostParams`, which is `restrict`ed to `_hostParams.hostManager` — the address that receives cross-chain governance requests dispatched from the Hyperbridge chain (via `HostManager.sol`/`onAccept`). Inside it: [1](#0-0) 

```solidity
address oldFeeToken = feeToken();
if (oldFeeToken != address(0) && oldFeeToken != params.feeToken) {
    uint256 balance = IERC20(oldFeeToken).balanceOf(address(this));
    if (balance != 0) revert CannotChangeFeeToken();
}
```

This check requires the host's balance of the *previous* fee token to be exactly `0` before the fee token can be changed to a different, non-zero address. Since `IERC20.balanceOf(address(this))` is a raw ERC-20 balance and `transfer()` is permissionless, any user holding the old fee token can send as little as `1 wei` to the host contract at any moment. As long as that dust remains (or is re-sent every time governance sweeps it via `withdraw`), the balance check in `updateHostParamsInternal` will keep reverting with `CannotChangeFeeToken`, blocking the entire `updateHostParams` governance message for that update — not just the fee-token field, since the whole struct is validated and applied atomically in one function.

This mirrors the reported PoolTogether bug: `VaultBooster.setBoost()` checked `_initialAvailable > balance` and reverted if a front-runner shrank the balance via `liquidate()`; here, an attacker *grows* the balance via a plain transfer to violate a `balance != 0` guard, but the effect is identical — a config-critical state transition is DoS'd indefinitely by an unprivileged party for the cost of dust.

Note: `_hostParams.hostManager` restriction means only cross-chain governance can *call* `updateHostParams`, but the attack does not require calling that function — it only requires sending tokens directly to the host contract, which any unprivileged holder of the old fee token can do. ### Impact Explanation
If Hyperbridge governance ever needs to migrate the fee token on an `EvmHost` deployment (e.g., the current fee token becomes compromised, deprecated, depegged, or otherwise unusable), an attacker can indefinitely prevent that migration by continuously donating trivial amounts of the old fee token to the host. Governance's `withdraw()` sweep (also `restrict`ed to `hostManager`) can zero the balance, but the attacker can immediately re-donate 1 wei before/after the next `updateHostParams` message lands, since messages are asynchronous cross-chain deliveries with predictable timing (proof submission, relaying). This is a griefing/DoS on a core protocol parameter update path (route/parameter unable to be reconfigured), which can leave the host stuck depending on a token the protocol needs to move away from — a liveness/freezing issue for the fee/config-management route rather than a direct fund-theft, matching Medium severity per the precedent judged in the original report.

### Likelihood Explanation
The attack requires no special privileges — only holding a tiny amount of the current fee token (typically a common asset like DAI/USDC) and calling a standard ERC-20 `transfer` to the host address, which is public information. It can be repeated cheaply and indefinitely, and does not require front-running precision beyond ensuring the balance is non-zero at the moment the governance message executes, which is trivially satisfiable by keeping the host's balance topped up at all times.

### Recommendation
Do not gate the fee-token change on the host's own token balance. Instead:
- Decouple balance sweeping from parameter updates: perform an explicit `withdraw`/sweep of the old fee token as part of (or immediately before, atomically in the same transaction as) the `updateHostParamsInternal` call, rather than requiring a pre-existing zero balance that anyone can violate.
- Alternatively, when `feeToken` changes, automatically sweep any residual old-fee-token balance to a beneficiary (or to `_hostParams.admin`/treasury) within `updateHostParamsInternal` itself, removing the external griefable precondition entirely.

### Proof of Concept
1. Governance sets `feeToken = DAI` initially via `updateHostParams`.
2. Protocol accrues/collects DAI fees over time; governance later withdraws all DAI (`withdraw()`), bringing `IERC20(DAI).balanceOf(host) == 0`.
3. An attacker (holding just 1 wei of DAI) calls `DAI.transfer(hostAddress, 1)` — no permission required.
4. Hyperbridge governance dispatches a cross-chain `updateHostParams` message changing `feeToken` from `DAI` to `USDC`. When `HostManager` delivers it and calls `updateHostParamsInternal`, the check `oldFeeToken != params.feeToken` is true and `balanceOf(host) == 1 != 0`, so the call reverts with `CannotChangeFeeToken`.
5. The attacker repeats step 3 after every governance `withdraw()` attempt, permanently blocking the fee-token migration. [1](#0-0)
