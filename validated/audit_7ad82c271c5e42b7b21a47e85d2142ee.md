Webhook shop-domain/topic spoofing via unsigned headers trusted after body-only HMAC check - (File: lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, then unconditionally trusts the `shop`, `topic`, `webhook_id`, and `api_version` values taken from HTTP headers to build the `WebhookMetadata` object handed to the host app's handler. Because those header fields are never included in the signed content, any request bearing a raw body/HMAC pair that is valid for the app's shared `client_secret` can carry attacker-chosen shop and topic identity. This breaks the equality "shop the HMAC vouches for" == "shop the handler receives," letting an app's own merchant (or anyone who can obtain one valid raw_body/HMAC pair) forge webhook events attributed to a different, arbitrary shop — a cross-tenant identity-binding violation analogous to the "custodian can act outside its documented authority" issue in the reference report.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are read directly from HTTP headers with no cryptographic binding to the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC only over `to_signable_string` (i.e., the raw body) using the app's `api_secret_key` (the app's single shared `client_secret`, not a per-shop secret): [3](#0-2) 

`Registry.process` performs this body-only HMAC check and then dispatches the handler using the unauthenticated `request.shop` and `request.topic`: [4](#0-3) 

Equality that should hold but doesn't: `shop_bound_by_signature == shop_delivered_to_handler`. Before the attack: a legitimate webhook for shop A has `(raw_body_A, hmac_A, headers{shop: A, topic: T})`, and `hmac_A` is valid for `raw_body_A` under the app's shared secret. After the attack: the attacker resends `(raw_body_A, hmac_A)` unchanged but with `headers{shop: B, topic: T'}`. `HmacValidator.validate` still returns `true` (it re-derives the HMAC from `raw_body_A` only), yet `Registry.process` now calls the handler with `WebhookMetadata.new(topic: T', shop: B, ...)` — the app is told this event came from shop B though the signature never attested to B or T'.

Because the client_secret is shared across all shops installed on the app (not per-shop), any actor who can legitimately install the app on their own shop (an unprivileged, non-credentialed action available to any internet user) receives genuine webhook deliveries with a valid `(raw_body, hmac)` pair for their own shop. That pair can then be replayed with a modified `shop-domain`/`topic` header to make the gem believe the event originated from a different tenant.

### Impact Explanation
This is a cross-tenant confusion: an unprivileged actor who installs the app once can cause the host application's webhook handler to process attacker-controlled payloads while believing they belong to any other shop of their choosing (e.g., faking `shop/redact`, `orders/create`, `app/uninstalled` for a victim shop domain). Depending on how the host app trusts `data.shop` (commonly used as the tenant/session key to look up and act on that shop's stored data or access token), this can lead to cross-tenant data corruption, spoofed mandatory-compliance webhooks, or triggering privileged per-shop workflows for a shop the attacker does not control — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is meaningful but bounded: no cryptographic secret needs to be stolen, but the attacker must be able to install (or otherwise generate a legitimate webhook delivery for) the target app at least once to obtain one valid `(raw_body, hmac)` pair, and must be able to deliver a crafted HTTP request with modified headers directly to the app's public webhook endpoint (bypassing Shopify's own delivery infrastructure, which the gem does nothing to enforce since it never validates source IP or ties headers to the signature). This is realistic for any app open to public installation (the common case for public Shopify apps).

### Recommendation
Short term: document that `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` are not covered by the HMAC and must not be trusted as tenant/topic identifiers without additional verification by the host app (e.g., cross-checking against a known/expected shop or webhook id recorded at registration time).
Long term: extend `Request#to_signable_string` (or add a secondary check in `Registry.process`) to bind the shop domain, topic, and webhook id into the value that is authenticated, so `HmacValidator.validate` fails if any of those headers are altered relative to what Shopify actually signed/delivered.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker.myshopify.com`, causing Shopify to deliver a genuine webhook: raw body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's `client_secret`), `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`.
2. Attacker replays this exact `(B, H)` pair to the app's public webhook endpoint but sets `x-shopify-shop-domain: victim.myshopify.com` and/or a different registered `x-shopify-topic`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC from `B` alone via `to_signable_string` and returns `true` because `B` and `H` are unchanged. [5](#0-4) 
4. The registered handler is invoked with `WebhookMetadata` carrying `shop: "victim.myshopify.com"`, even though the signature never attested to that shop, letting the attacker inject webhook data attributed to a shop they do not control.
