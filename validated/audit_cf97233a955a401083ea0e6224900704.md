### Title
Unchecked empty `Commitment.payload` array causes a panic in the `From<Commitment> for SpCommitment` conversion, reachable via `BeefyConsensusProofs::submit_proof` — ([File: evm/rust/src/conversions.rs])

### Summary
`pallet-beefy-consensus-proofs::submit_proof` is a signed, permissionless extrinsic that accepts attacker-supplied ABI-encoded bytes and, for the "naive"/ECDSA proof type, decodes them into a `BeefyConsensusProof` Solidity struct and converts it into the SCALE `ConsensusMessage` used by the BEEFY verifier. That conversion path unconditionally calls `.next().expect(...)` on the iterator over the commitment's `payload` array without checking whether it is empty first — directly analogous to CVE-2021-3596, where `ReadSVGImage()` used the return value of `xmlCreatePushParserCtxt()` without checking it could be null/failed, causing a crash.

### Finding Description
`pallet_beefy_consensus_proofs::Pallet::verify_and_apply` dispatches on the first proof byte: [1](#0-0) 

For `types::PROOF_TYPE_NAIVE`, the raw bytes after the type byte are ABI-decoded as `ismp_abi::ecdsa_beefy::BeefyConsensusProof` and then converted with `.into()` into `beefy_verifier_primitives::ConsensusMessage`: [2](#0-1) 

That `Into` conversion chain is:
`BeefyConsensusProof -> ConsensusMessage` (`value.relay.into()`) [3](#0-2) 

`RelayChainProof -> MmrProof`, which converts `value.signedCommitment.commitment.into()` [4](#0-3) 

`Commitment -> SpCommitment`, the vulnerable conversion: [5](#0-4)

`Commitment.payload` is a Solidity dynamic array (`Payload[]`) supplied entirely by the caller inside the ABI-encoded proof bytes. Solidity ABI decoding of a well-formed but empty dynamic array succeeds (it just yields zero elements) — `abi_decode_params` does not reject an empty `payload` array. When `payload` is empty, `iter.next()` returns `None` and `.expect("commitment has at least one payload entry")` panics, before any BEEFY signature or MMR verification has run. This is executed inside a runtime dispatchable (`submit_proof`), so the panic occurs during on-chain transaction execution.

This is the same bug class as CVE-2021-3596: a fallible/optional return value (`iter.next()` returning `Option::None`, analogous to `xmlCreatePushParserCtxt()` potentially returning NULL) is used directly via `.expect()` without a defensive check, and the input that triggers the missing value is attacker-controlled and reaches the vulnerable code from an unprivileged, single-transaction entry point.

### Impact Explanation
A panic inside `on_initialize`/extrinsic execution in a Substrate/FRAME runtime is caught by `frame_executive`'s panic handling per-extrinsic in most configurations, but this specific pallet call wraps the verification logic; a panic here would abort execution of that transaction/block-building step and, depending on the runtime's `#[frame_support::transactional]`/panic-handling configuration around `verify_and_apply`, can disrupt block authoring/validation (denial of service for the BEEFY consensus update pipeline). At minimum, it lets an unprivileged, single signed transaction reliably crash/interrupt the code path responsible for advancing the BEEFY consensus state and thus blocks delivery of subsequent ISMP messages that depend on that consensus client being updated — a "route unable to deliver messages" condition, which the validation rules classify as in-scope impact.

### Likelihood Explanation
High: `submit_proof` is a normal signed extrinsic (`ensure_signed`), requiring no special privilege — any account holding minimal balance for a transaction fee can call it. Crafting a `BeefyConsensusProof` with `signedCommitment.commitment.payload = []` requires only producing valid Solidity ABI encoding for an otherwise-arbitrary struct (the surrounding signature/authority checks are never reached because the panic occurs before verification). No cryptographic material or trusted party involvement is needed to trigger this.

### Recommendation
Replace the `.expect(...)` in `From<Commitment> for SpCommitment` (`evm/rust/src/conversions.rs`) with a fallible conversion (e.g. `TryFrom`) that returns an error/`Result` when `value.payload` is empty, and propagate that error through `RelayChainProof -> MmrProof -> ConsensusMessage` conversions so `verify_and_apply` can reject the proof with `Error::<T>::AbiDecodeFailed` (or a new dedicated error) instead of panicking, matching the pattern already used elsewhere in the codebase (e.g., the `beefy_verifier::verify_mmr_leaf` fix for empty `leaf_indices`, and the GRANDPA/Pharos/RLP trie decoders that were hardened to return typed errors instead of panicking on adversarial proof shapes).

### Proof of Concept
1. Construct `BeefyConsensusProof { relay: RelayChainProof { signedCommitment: SignedCommitment { commitment: Commitment { payload: vec![], blockNumber: 0, validatorSetId: 0 }, votes: vec![] }, latestMmrLeaf: <any>, mmrProof: vec![], proof: vec![] }, parachain: <any> }`.
2. ABI-encode it as the Solidity `BeefyConsensusProof` tuple to get `abi_payload`.
3. Submit `proof = [PROOF_TYPE_NAIVE] ++ abi_payload` via `BeefyConsensusProofs::submit_proof(origin, proof)` from any signed account.
4. `verify_and_apply` decodes the ABI payload successfully (empty dynamic array is valid ABI), then calls `.into()` on the decoded `BeefyConsensusProof`, which walks into `From<Commitment> for SpCommitment` and panics at `iter.next().expect("commitment has at least one payload entry")`.

Note: I could not execute this end-to-end in a live node to confirm the exact panic-handling/unwind behavior of the parachain runtime (whether it aborts only the extrinsic or affects block production), since I only have static/index-based code access; this should be validated by reproducing the transaction in a running Devin/test node to confirm the concrete blast radius.
