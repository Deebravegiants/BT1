### Title
Emporium's unsigned stateless-op path lets an attacker pull a victim's stale ERC20 allowance and mint it as the attacker's own shielded UTXO - (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction` executes arbitrary `op.endpoint.call(op.callData)` for any `EmporiumOperation` with `invokeWallet=false`, and `verifyWallet` skips all signature verification whenever `stack.signerAddress == address(0)` [1](#0-0) . An attacker can therefore submit their own `transact` call with a `CircomData.externalActionData.externalActionMetadata` encoding a stack with `signerAddress=address(0)` and a single unsigned op `token.transferFrom(victimWallet, address(Emporium), amount)`, pulling tokens the victim previously and separately approved to the Emporium address, and then declare `amountChanges[i] = +amount` in their own proof to make the on-chain balance bookkeeping treat the pulled funds as the attacker's own deposit.

### Finding Description
The equality enforced on-chain is `balanceDif == amountChanges[i] + utxoAmount` (checked in `Hinkal.sol` for direct transacts, and analogously via `balanceChange`/`deltaAmountChanges` inside `EmporiumUpgradeable.runAction`) [2](#0-1) . This check only constrains the *numeric* delta of the ERC20 `balanceOf` against the attacker-declared `amountChanges[i]`; it never verifies *whose* funds produced that delta.

`EmporiumUpgradeable.runAction` is only gated by `onlyAllowedRecipient`, which restricts `msg.sender` to the main Hinkal contract, not the content of `stack.ops` [3](#0-2) . Inside the ops loop, when `op.invokeWallet == false` ("CASE 2: Stateless Interaction"), the contract performs a raw `op.endpoint.call{value: op.value}(op.callData)` with only a check that the selector isn't `callHinkalWallet`/`doSendToRelay` [4](#0-3) . Crucially, `verifyWallet` — the only function that authenticates `stack.ops` via an EIP-712 signature — returns immediately without checking anything if `stack.signerAddress == address(0)` [5](#0-4) . It only marks `emporiumMessage` used, which is an attacker-chosen nonce with no bearing on authorization of the call content.

Exploit flow:
1. Victim, in some earlier interaction, leaves a nonzero `ERC20.allowance(victimWallet, Emporium)` (precondition given).
2. Attacker crafts their own `transact` call with `circomData.externalActionData.externalActionMetadata` = ABI-encoded `EmporiumStack{ signerAddress: address(0), ops: [ { endpoint: token, invokeWallet: false, value: 0, callData: transferFrom(victimWallet, Emporium, amount) } ] }`.
3. `verifyWallet` short-circuits (no signature needed), `runAction` executes the op: since `msg.sender` of the low-level call is the Emporium contract, `token.transferFrom(victimWallet, Emporium, amount)` succeeds against the victim's stale allowance, increasing Emporium's own token balance by `amount`.
4. `deltaAmountChanges[i]` (derived from the attacker's own `circomData.amountChanges[i] = +amount`, computed in `Hinkal.sol::_calculateDeltaAmount`) is positive, so the `balanceChange -= deltaAmountChanges[i]` adjustment (only applied when `deltaAmountChanges[i] < 0`) is skipped [6](#0-5) .
5. `handleOut` pays the entire `balanceChange` (= `amount`, sourced from the victim) to `msg.sender`, i.e. the attacker, and mints a fresh UTXO for the attacker of that amount [7](#0-6) .
6. The circuit-side constraint `inTotal + amountChanges[i] === outTotal` is satisfied purely by the attacker's own chosen `outAmounts`, with `inTotal = 0` (no UTXO of the attacker's is spent) — this constraint enforces internal ledger consistency, not the provenance of the on-chain balance change, so it does not catch the theft.

None of the existing guards (`onlyAllowedRecipient`, `verifyWallet`, the balance-diff `require`, `BalanceChangeShouldBePositive`) check that the balance increase originated from funds the *caller* (or a party who signed the op) actually owns or authorized moving. The `EMPORIUM_SIGNATURE_TYPEHASH` mechanism exists specifically to authenticate `stack.ops`, but it is entirely bypassable by setting `signerAddress = address(0)`.

### Impact Explanation
Critical — direct theft of a third party's ERC20 tokens (the victim's residual allowance to Emporium) that get converted into the attacker's own shielded UTXO balance inside Hinkal, with no valid signature or proof-of-ownership over the moved funds. This is repeatable against any victim/token/spender pair where a non-zero, unrevoked allowance to the Emporium contract exists, until the allowance is exhausted or revoked.

### Likelihood Explanation
Requires only that some victim previously executed an approval to the Emporium contract (e.g., via a prior legitimate stateless Emporium op or manual approval) and never revoked or fully consumed it — a common ERC20 UX pattern (residual approvals are extremely common in practice). The attacker needs no special privileges: any EOA can call `transact`, craft the `CircomData`/`externalActionMetadata`, and generate a valid proof for their own (empty/zero) UTXO inputs. Attacker cost is limited to gas and generating one proof; the attack is fully deterministic and repeatable per victim/token.

### Recommendation
Do not allow unauthenticated `EmporiumOperation`s. Remove the early-return bypass in `verifyWallet` when `signerAddress == address(0)`; either require every stateless op set to be signed by a party (e.g., the CircomData submitter authenticated via the proof, or require `op.endpoint` calls made with `Emporium` as `msg.sender` to be restricted to a fixed allowlist of endpoints known not to accept arbitrary `from` addresses), or forbid stateless ops from calling `transferFrom`/`transfer`-style functions on arbitrary tokens where `Emporium` is `msg.sender` unless the funds source is verified to be the caller/prover themselves. At minimum, disallow selectors matching common "pull funds from arbitrary address" patterns (`transferFrom`, `permit`, etc.) in the stateless path, or require `stack.signerAddress` to be non-zero and match the transacting `msg.sender`.

### Proof of Concept
Foundry fork/unit test plan:
1. Deploy `EmporiumUpgradeable`, a mock ERC20, `Hinkal` core, and register Emporium as an allowed recipient.
2. As `victim`, call `mockToken.approve(address(emporium), 1000e18)` (simulating a stale approval from an earlier session) — do not have victim sign or authorize anything further.
3. As `attacker`, build `CircomData` with `externalActionData.externalActionMetadata` encoding `EmporiumStack{signerAddress: address(0), ops: [{endpoint: address(mockToken), invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transferFrom, (victim, address(emporium), 1000e18))}]}` and `amountChanges[i] = 1000e18`; generate a locally valid proof for the attacker's own (zero-input) UTXO set with `outTotal = inTotal(0) + amountChanges(1000e18)`.
4. Call `Hinkal.transact(...)` as attacker, routing to `EmporiumUpgradeable.runAction`.
5. Assert: before — `mockToken.balanceOf(victim) == V`, `mockToken.balanceOf(attacker) == A`; after — `mockToken.balanceOf(victim) == V - 1000e18`, `mockToken.balanceOf(attacker) == A + 1000e18`, and no calldata/signature in the transaction was ever signed by `victim`.
6. Assert the broken equality explicitly: `balanceChange (1000e18, sourced from victim's transferFrom) == amountChanges[i] (1000e18, attacker-declared) + utxoAmount (0, no attacker UTXO spent)` holds numerically while `AUTHORITY: from == victim` was never authorized by attacker's signature or proof — demonstrating the funds source/authorization gap.
