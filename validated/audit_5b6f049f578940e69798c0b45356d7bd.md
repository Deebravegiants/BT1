## Title
Unsigned ISMP message batches can be poisoned so a single fee-charge failure reverts all bundled (unrelated) messages, causing a griefing DoS - (File: `modules/pallets/ismp/src/impls.rs`, `modules/pallets/ismp/src/fee_handler.rs`, `modules/pallets/ismp/src/lib.rs`)

### Summary
`pallet-ismp`'s `handle_unsigned` extrinsic accepts an arbitrary `Vec<Message>` batch from *anyone* (unsigned origin), executes all of them, and then charges a per-message fee to each message's embedded signer via `WeightFeeHandler::on_executed`. The whole call is wrapped in `#[frame_support::transactional]`, and `on_executed` aborts the *entire loop* the first time a fee transfer fails. Because the fee transfer uses `ExistenceRequirement::KeepAlive`, an attacker can trivially make their own message's fee-charge fail (by leaving their signer account with a balance just below `fee + existential deposit`), and if that message is bundled together with other, unrelated but legitimate/valid messages in the same batch, the failure rolls back the *entire* batch — including the legitimate messages that had already passed proof verification. This mirrors the reported bug class: a party can manipulate a balance associated with a shared/batched operation so that a downstream fee-settlement step fails, and the failure propagates to block/void other parties' otherwise-valid work.

### Finding Description
`handle_unsigned` calls `Self::execute(messages)` and is marked transactional: [1](#0-0) 

`execute()` first runs `handle_incoming_message` for every message (verifying proofs and mutating storage/commitments), collects events, and only *after* all of that succeeds calls the configured `FeeHandler::on_executed`, propagating any error as `Error::ErrorChargingFee`: [2](#0-1) 

`WeightFeeHandler::on_executed` iterates every message in the batch and, for `Request`/`Response` messages, decodes the embedded `signer` to recover the fee-paying account, then does:
```rust
C::transfer(&account, &treasury_account, fee, ExistenceRequirement::KeepAlive)
    .map_err(|_| DispatchError::Other("Failed to transfer fee to treasury"))?;
``` [3](#0-2) 

Because of the `?`, a single failing transfer aborts the loop and returns `Err`, which `execute()` converts into `Error::ErrorChargingFee`, which — combined with `#[frame_support::transactional]` on `handle_unsigned` — rolls back *all* storage effects of *every* message in the batch, not just the offending one.

`handle_unsigned` takes a `Vec<Message>` and is validated purely by `validate_unsigned`, which itself calls `Self::execute` to check validity, with no restriction that all messages must originate from (or benefit) the same relayer/account: [4](#0-3) 

The message `signer` field is attacker-controlled data embedded in the request/response payload itself (a signature over the request/response set), not tied to `msg.sender`/transaction submitter identity in any privileged way — anyone with a validly-signed message (their own, or one they observed being gossiped/relayed by someone else) can include it in a batch they submit. Since `KeepAlive` transfers fail whenever the resulting balance would drop below the existential deposit, an attacker fully controls whether their own embedded-signer account's fee transfer succeeds by simply funding that account with `fee + ED - 1`.

### Impact Explanation
An attacker can:
1. Prepare their own validly-proven message (a cheap request/response) whose embedded `signer` account is deliberately funded with a balance just below `fee + existential deposit`.
2. Bundle it in the same `handle_unsigned` extrinsic together with an unrelated, legitimate, time-sensitive message (e.g., another relayer's request/response delivery, or a consensus/state update that needs to land before a challenge/timeout window closes).
3. Submit the batch. `execute()` processes and commits state for all messages internally, but the trailing `FeeHandler::on_executed` fails on the attacker's poisoned message, causing `Error::ErrorChargingFee` and a full transactional rollback of the whole batch — including the legitimate message's delivery/verification.

This is a denial-of-service/griefing vector against the shared, permissionless `handle_unsigned` execution path: a party can force a fee-settlement failure (self-controlled balance manipulation) to void otherwise-valid protocol operations bundled alongside it, exactly analogous to the report's pattern where withdrawing too much intentionally starves a shared fee-collection step and DoSes protocol operability for others.

### Likelihood Explanation
Reaching this requires only: (a) the ability to submit an unsigned `handle_unsigned` extrinsic with a multi-message batch (permissionless, by design — "permits anyone execute ISMP messages for free"), and (b) control over the balance of the account referenced as `signer` in one's own message. Both are trivially available to any unprivileged actor with a small amount of the native token. The main constraint is that the attacker needs to get their poison message batched together with a target message, which depends on relayer/mempool batching behavior — the current reference relayer implementation submits one message per extrinsic, reducing default exposure, but nothing in the protocol enforces single-message batches, and the extrinsic explicitly accepts and is designed to process `Vec<Message>`.

### Recommendation
- Do not let a single message's fee-charge failure abort the whole batch: catch per-message transfer errors, skip/zero-fee that specific message (or emit an event) without failing `on_executed`/`execute()` as a whole.
- Alternatively, decouple validity/state-application of a message from its fee settlement — settle fees best-effort (e.g., `ExistenceRequirement::AllowDeath` or explicit "insufficient funds" bookkeeping rather than reverting the batch), so unrelated messages in the same batch aren't held hostage.
- Consider requiring per-relayer/per-sender batches (i.e., reject batches with heterogeneous, unrelated fee payers) to reduce the ability to poison unrelated messages.

### Proof of Concept
1. Attacker controls `AccountA`, funds it with exactly `fee + ED - 1` (so `ExistenceRequirement::KeepAlive` will fail for the exact `fee`).
2. Attacker crafts/signs a minimal valid `PostRequest`/`RequestMessage` whose signature recovers to `AccountA`, with a valid consensus proof (can even be a trivial no-op state read) so `handle_incoming_message` succeeds for it.
3. Attacker observes or independently constructs another valid, unrelated `RequestMessage`/`ConsensusMessage` (e.g., a legitimate relayer's pending delivery, or a state update) with a valid proof.
4. Attacker submits `Ismp::handle_unsigned(messages: [poison_message, legitimate_message])`.
5. `execute()` processes both messages successfully (commitments inserted, MMR leaves pushed, events collected), then calls `WeightFeeHandler::on_executed`, which fails transferring `fee` from `AccountA` (`KeepAlive` violated) and returns `Err`.
6. `execute()` returns `Error::ErrorChargingFee`; because `handle_unsigned` is `#[frame_support::transactional]`, all storage writes for both messages are rolled back — the legitimate message's delivery is voided along with the attacker's own poison message, at zero cost repeatable by the attacker (`handle_unsigned` is fee-free/unsigned).

	pub fn execute(messages: Vec<Message>) -> Result<Vec<events::Event>, Error<T>> {
		let host = Pallet::<T>::default();

		let message_results = messages
			.iter()
			.map(|msg| handle_incoming_message(&host, msg.clone()))
			.collect::<Result<Vec<_>, _>>()
			.map_err(|err| {
				log::debug!(target: "ismp", "Handling Error {:#?}", err);
				Pallet::<T>::deposit_event(Event::<T>::Errors { errors: vec![err.into()] });
				Error::<T>::InvalidMessage
			})?;

		let messages_with_weights = message_results
			.iter()
			.zip(messages)
			.map(|(result, message)| MessageWithWeight { message, weight: result.weight() })
			.collect::<Vec<_>>();

		let events = message_results
			.into_iter()
			// check that requests will be successfully dispatched
			// so we can not be spammed with failing txs
			.map(|result| match result {
				MessageResult::Request { events, .. } |
				MessageResult::Response { events, .. } |
				MessageResult::Timeout { events, .. } => events,
				MessageResult::ConsensusMessage(events) => events.into_iter().map(Ok).collect(),
				MessageResult::FrozenClient(_) => vec![],
			})
			.flatten()
			.collect::<Result<Vec<_>, _>>()
			.map_err(|err| {
				log::debug!(target: "ismp", "Handling Error {:#?}", err);
				Pallet::<T>::deposit_event(Event::<T>::Errors { errors: vec![err.into()] });
				Error::<T>::InvalidMessage
			})?;

		T::FeeHandler::on_executed(messages_with_weights, events.clone())
			.map_err(|_| Error::<T>::ErrorChargingFee)?;
