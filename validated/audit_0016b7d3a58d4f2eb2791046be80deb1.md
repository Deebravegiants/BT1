### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook shop spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw request body via HMAC, while the `shop` (and `topic`/`api-version`/`webhook-id`) values used downstream to identify the tenant are taken directly from unauthenticated HTTP headers that are never included in the signed content. This breaks the identity binding `HMAC-verified body == shop attributed to that body`, letting an attacker who possesses one validly-signed webhook payload (e.g., from their own shop's installation) replay it with a forged `x-shopify-shop-domain`/`shopify-shop-domain` header to make the app process the event as if it came from a different (victim) shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors read directly from HTTP headers, none of which participate in signature computation: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e., the raw body only) and compares it against the `hmac` header using `OpenSSL.secure_compare`: [3](#0-2) 

`Registry.process` accepts the request once this body-only HMAC check passes, then constructs `WebhookMetadata` directly from the unauthenticated `request.shop`, `request.topic`, and `request.api_version` values and dispatches it to the app's handler: [4](#0-3) 

Because the shop-domain header is never part of the signed payload, the equality the app relies on — "HMAC-authenticated payload belongs to shop X" — does not actually hold. An unprivileged attacker who has legitimately received one valid `(raw_body, hmac)` pair (trivially obtainable by installing the app on their own store and triggering any webhook, e.g. `orders/create`) can replay that exact body and HMAC to the merchant's webhook endpoint while substituting the `shop-domain` header with an arbitrary victim shop that also has the app installed. `HmacValidator.validate` still passes because it only checks the body/secret pair, and `Registry.process` forwards `request.shop` (the attacker-controlled header) as the trusted tenant identifier to the handler.

### Impact Explanation
This is a cross-tenant identity-binding break: the gem authenticates the body but the host application (following the gem's documented `WebhookMetadata.shop`/`Request#shop` API) is given an unauthenticated shop identifier to key its business logic on (e.g., write order data, trigger fulfillment, mark app-uninstalled state, or update settings) for any shop, not just the one whose secret validated the payload. An attacker can inject forged, "HMAC-valid" webhook events attributed to a victim merchant's shop domain, resulting in cross-tenant data confusion/injection — matching the Critical/High "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is realistic but requires two conditions: (1) the attacker must obtain at least one genuinely signed `(body, hmac)` pair for some topic, which is easy if the same app is installed on any shop the attacker controls (including a free/dev store), and (2) the app's webhook endpoint must be reachable with attacker-controlled headers, which is the normal case for any public app webhook route. No access token, `client_secret`, or privileged account is required — only the ability to receive one legitimate webhook from the app for a shop the attacker controls.

### Recommendation
Bind the shop (and ideally topic/webhook-id) to the HMAC-verified content instead of trusting header values independently of the signature. Since the HMAC algorithm/format is fixed by Shopify (body-only signing), the gem/host application should not treat `Request#shop` as a trusted tenant key on its own; at minimum, the gem should surface this constraint clearly, and/or cross-check the header-derived shop against another authenticated source (e.g., verifying the shop is one that has a valid stored session/access token for this app, and rejecting mismatched or unknown-shop webhook headers) before invoking the handler.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw JSON body `B` and the valid `x-shopify-hmac-sha256` header `H` computed by Shopify over `B` with the app's real `client_secret`.
2. Attacker sends a POST to the app's webhook endpoint with the same body `B` and header `H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `Webhooks::Request.new` parses this, and `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) recomputes HMAC over `B` only and it matches `H`, so validation succeeds.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) builds `WebhookMetadata` with `shop: request.shop` = `"victim.myshopify.com"` and dispatches to the app's handler, which now processes attacker-supplied data as an authenticated event for `victim.myshopify.com`.
