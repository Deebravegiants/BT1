### Title
Unsigned `handle_unsigned` GetRequest batches force full membership/state-proof verification during mempool validation with no batch-size bound - Denial of Service ([File: modules/pallets/state-coprocessor/src/lib.rs])

### Summary
`pallet_state_coprocessor::Pallet::validate_unsigned` re-runs the entire `handle_get_requests` verification pipeline — including MMR membership verification and per-key state-proof verification for every `GetRequest` in the batch — every time an unsigned extrinsic is gossiped or (re-)validated in the transaction pool, before it is ever included in a block. Because `GetRequestsWithProof.requests` is an unbounded `Vec<GetRequest>` [1](#0-0) , an unprivileged relayer can submit a single unsigned extrinsic carrying a very large batch of `GetRequest`s and force this expensive verification to run repeatedly, unbounded by block weight, on every node that validates or re-validates the transaction.

### Finding Description
`handle_unsigned` is dispatched via `ensure_none(origin)` (permissionless, unsigned) and simply calls `Self::handle_get_requests(message)`: [2](#0-1) 

Critically, `validate_unsigned` — which is invoked by every node's transaction-pool logic whenever the extrinsic is received/gossiped/re-validated, not just at block execution — calls the exact same `handle_get_requests` function to decide validity: [3](#0-2) 

`handle_get_requests` performs, for every element of the caller-supplied `requests: Vec<GetRequest>`:
- a dedup pass,
- an MMR/state membership proof check via `verify_membership` over the whole batch,
- and, per request, a full `verify_state_proof` state-trie verification plus bandwidth-gate bookkeeping, [4](#0-3) 

There is no cap on `requests.len()` anywhere in this struct or in `validate_unsigned`/`handle_unsigned` — unlike block-inclusion, which is bounded by `#[pallet::weight(...)]` and the block weight limit, mempool `validate_unsigned` execution is not gated by the extrinsic's declared weight; it simply runs the full function body synchronously on every validating node. A single crafted unsigned transaction with thousands of `GetRequest`s (each carrying proof-verifiable keys) will make every node that receives it (via gossip, or re-validation on each new block) perform thousands of cryptographic membership/state-proof checks purely to decide whether to accept the transaction into its pool — work that is done again on every re-broadcast and every block-import re-validation cycle, since transaction-pool validity is re-checked repeatedly as new blocks arrive.

This mirrors the mlflow class of bug: an unauthenticated, permissionless endpoint (`/graphql` batched queries there; unsigned `handle_unsigned`/`validate_unsigned` here) accepts an unbounded batch parameter and performs per-item expensive work for each entry, tying up worker/validation resources across the network from a single submitted message.

### Impact Explanation
This is a resource-exhaustion / Denial-of-Service vector reachable by any unprivileged party able to submit an unsigned extrinsic (which is by design permissionless for `handle_unsigned`/relayers). Because the expensive verification runs at mempool-validation time (potentially many times per transaction lifetime, on every full node), an attacker can degrade block production and transaction propagation network-wide without ever paying transaction fees (the entire point of the unsigned "free" delivery mechanism), by submitting large or many large `GetRequestsWithProof` batches with syntactically valid-but-maximally-sized proof data. This can stall message delivery for other relayers/apps (a legitimate "route unable to deliver messages" condition) and burn CPU on validator/collator nodes.

### Likelihood Explanation
The `requests` field is fully attacker-controlled and there's no explicit size limit found in the `GetRequestsWithProof` struct, the `Config` bound, or `validate_unsigned`/`handle_unsigned`. Any address capable of forming a syntactically valid `Proof`/`GetRequest` batch (which does not require having real, verifiable proof content to reach the CPU-consuming portion of `verify_membership`/`verify_state_proof`, since these checks run for each element before rejecting) can trigger this. This makes exploitation straightforward to attempt from a single account with no special privileges. Whether it fully succeeds (i.e., actual proof verification cost vs. early-exit failure cost) could not be independently confirmed here since I could not inspect the full cost characteristics of `verify_membership`/`verify_state_proof` for malformed/large inputs, or definitively confirm whether Substrate's transaction-pool applies any implicit longevity/priority-based early rejection or extrinsic size caps at the runtime/node level that might partially mitigate this. This uncertainty should be verified by a background engineer with access to the full node configuration (`TransactionByteFee`, `BlockLength`, mempool `longevity`, and `pallet_transaction_payment`/extrinsic size limits) which are configured outside the files retrievable here.

### Recommendation
- Enforce an explicit maximum batch size (`BoundedVec` with a `MaxGetRequestsPerBatch: Get<u32>` bound, or an early length check) on `GetRequestsWithProof.requests` before any proof-verification work begins, both in `handle_get_requests` and, critically, at the very start of `validate_unsigned` so the check happens before any cryptographic work.
- Consider having `validate_unsigned` perform only cheap, non-cryptographic sanity checks (batch-size bound, structural validity, duplicate-hash check) and defer full proof verification to actual block execution (`handle_unsigned`), rather than duplicating the entire expensive verification pipeline at mempool-validation time.
- Apply a similar audit to `pallet_ismp::handle_unsigned`'s `Vec<Message>` parameter and its `ValidateUnsigned` path (not fully confirmed here due to iteration limits) to ensure the core ISMP unsigned dispatch path has equivalent batch-size bounding.

### Proof of Concept
1. Craft a single unsigned extrinsic calling `pallet_state_coprocessor::handle_unsigned` with a `GetRequestsWithProof` whose `requests` vector contains a very large number (e.g., tens of thousands) of distinct `GetRequest` entries, each with a unique `keys` payload, paired with a `source`/`response` `Proof` sized to make verification traverse the full request set.
2. Submit the extrinsic to a node's RPC (`author_submitExtrinsic`) as would be done in the existing test harness pattern shown in `parachain/simtests/src/pallet_ismp.rs` (`subxt::dynamic::tx("Ismp", "handle_unsigned", ...)`), adapted for the `StateCoprocessor` pallet: [5](#0-4) 
3. Observe that `validate_unsigned` invokes the full `handle_get_requests` verification loop over the entire batch synchronously before returning transaction validity, and that this same cost recurs on every peer that receives/re-validates the gossiped transaction — independent of whether the transaction is ever included in a block.

		let state_root = host.state_machine_commitment(source.height)?;

		// Verify membership proof to ensure that requests where committed on source chain
		let commitments = requests
			.iter()
			.map(|get| hash_request::<<T as Config>::IsmpHost>(&Request::Get(get.clone())))
			.collect();
		source_state_machine.verify_membership(&host, commitments, state_root, &source)?;

		// Verify response proof
		let dest_state_machine = validate_state_machine(&host, response.height)?;
		let state_root = host.state_machine_commitment(response.height)?;

		// Insert GetResponses into mmr
		let mut responses = vec![];
		// Total payload bytes across this batch, used to mint reputation to
		// the relayer named in `address`. Each response contributes its
		// abi-encoded size — the same quantity the bandwidth gate charges —
		// so the mint stays proportional to the work paid for.
		let mut total_bytes: u32 = 0;
		for req in requests {
			let values: Vec<StorageValue> = dest_state_machine
				.verify_state_proof(&host, req.keys.clone(), state_root.state_root, &response)?
				.into_iter()
				.map(|(key, value)| StorageValue { key, value })
				.collect();

			let response = GetResponse { get: req, values };

			// Meter the app's bandwidth using the full size of the
			// abi-encoded GetResponse. Charged after proof verification
			// so the value sizes are final.

				&response.get.from,
				bytes,
			)
			.map_err(|err| Error::Custom(alloc::format!("bandwidth gate: {err}")))?;
			total_bytes = total_bytes.saturating_add(bytes);
