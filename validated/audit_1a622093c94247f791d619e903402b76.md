### Title
Webhook `shop-domain`, `topic`, and `webhook-id` headers are not covered by the HMAC signature, allowing cross-tenant event spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, while the `shop`, `topic`, and `webhook_id` values that the library extracts and hands to the app's handler are taken from unauthenticated HTTP headers that the HMAC never covers.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Registry.process` validates the request using `Utils::HmacValidator.validate(request)`, which — per `HmacValidator#validate_signature` — computes the HMAC exclusively over `to_signable_string` (i.e., the raw body), and then immediately trusts `request.shop` and `request.topic` to dispatch the event to the app's handler: [3](#0-2) [4](#0-3) 

The equality this breaks is: **shop that produced/authorized the signed payload == shop attributed to the event by the library**. Because the header carrying the tenant identity (`shop-domain`) sits entirely outside the HMAC's coverage, the library cannot actually prove that the body it validated originated from the shop named in the header — it only proves the body bytes are unmodified and were signed with the app's secret at some point in time, for some shop.

### Impact Explanation
Any two shops that both have the app installed share the same `api_secret_key` (the app's own secret, not shop-specific). An unprivileged holder of a legitimately-signed webhook payload from *their own* shop installation can resend that exact body/HMAC pair to the app's webhook endpoint while substituting a different `shopify-shop-domain` header value. `HmacValidator.validate` will still pass (body/HMAC untouched), and `Registry.process` will hand the handler a `WebhookMetadata` object asserting the victim shop as `shop`, causing the host application to process/store data under the wrong tenant. This is a cross-tenant data-integrity break driven purely by a gap in what the HMAC signs, matching the "field acted on but not covered by the HMAC" identity-binding failure class.

### Likelihood Explanation
Likelihood depends on how strictly the host application trusts `data.shop` from `WebhookMetadata` versus independently confirming shop identity (e.g., checking against a known-shop allowlist before persisting). The library itself provides no such secondary binding, so any app that follows the documented `Registry.process` flow inherits this gap by default. Exploitation requires the attacker to possess at least one genuinely-signed webhook body (obtainable by installing the app on their own store, which any merchant can do), so this is not a fully unauthenticated exploit but does not require the app's `api_secret_key`, an access token, or any privileged credential.

### Recommendation
Include `shop-domain`, `topic`, and `webhook-id` header values in the HMAC-signed material (or otherwise cryptographically bind them, e.g., by validating them against an independently obtained shop/session record) before dispatching to handlers in `ShopifyAPI::Webhooks::Registry.process`, so header-only fields cannot be swapped without invalidating the signature.

### Proof of Concept
1. Install the app on Shop A (attacker-controlled) and capture a legitimate webhook POST, e.g. `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the app's secret).
2. Replay the exact same request to the app's public webhook endpoint, but change the header `X-Shopify-Shop-Domain` from `shop-a.myshopify.com` to `shop-b.myshopify.com` (a victim shop that also has the app installed).
3. `ShopifyAPI::Webhooks::Registry.process` computes the HMAC only over the unchanged body `B`, so `Utils::HmacValidator.validate` returns `true`.
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "shop-b.myshopify.com", body: parsed(B), ...)` and processes/stores Shop A's data as if it belonged to Shop B, corrupting per-tenant state in the host application.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
