### Title
Missing `BorrowPositions` storage entry silently defaults to an empty debt book, letting a borrower withdraw all collateral and strand bad debt - (File: contracts/controller/src/storage/account.rs)

### Summary
The Suricata bug is a null-dereference: a helper assumed optional certificate fields were present. The XOXNO analog is the opposite face of the same bug class: an absent storage entry is silently substituted with a default-empty value instead of being distinguished from a real empty state. `get_debt_positions` returns `Map::new(env)` when the `ControllerKey::BorrowPositions(account_id)` entry is absent (account.rs:71-73), and `try_get_account` only requires `AccountMeta` plus NFT ownership to resolve — it never checks that the position maps actually exist (account.rs:153-161). Soroban persistent entries expire independently, so an account whose `BorrowPositions` entry archives while its `AccountMeta`/`SupplyPositions` entries stay live is reconstructed as a debt-free account.

### Finding Description
`Account::debt_free()` is defined as `borrow_positions.is_empty()` (common/src/types/controller.rs:360-362). Every solvency gate — `borrow`, `withdraw`, and the strategies — is evaluated against the reconstructed `Account`, so an empty debt map yields `total_debt == 0` and `health_factor == i128::MAX` (risk/totals.rs:203-207). The withdraw path therefore passes its post-action checks unconditionally for such an account, and `clean_bad_debt`/`liquidate` see HF = MAX and refuse to touch it.

Meanwhile the debt is not actually gone from the protocol's books: spoke usage rows (`SpokeUsageRaw.borrowed_scaled_ray`) and the pool's global `borrowed` total are separate storage entries that still carry the scaled debt. The borrower can call `withdraw(caller, account_id, withdrawals, to)` with zero amounts (full position) and pull out every collateral leg while the pool still accounts the liability. The result is a fully collateral-drained account with unbacked borrow usage — direct protocol insolvency equal to the outstanding debt.

The same missing-field defaulting applies on the supply side (`get_supply_positions`, account.rs:63-68): an account whose `SupplyPositions` entry archives while `BorrowPositions` survives reports `total_collateral == 0`, making it permanently liquidatable at HF = 0 with zero seizable collateral — collateral that still physically backs the position cannot be claimed back by liquidation because the plan iterates only the (empty) stored map.

### Impact Explanation
Permanent protocol insolvency: the attacker withdraws the full collateral backing a live debt, and no unprivileged path (`liquidate`, `clean_bad_debt`) can claw it back because the reconstructed account reports HF = `i128::MAX` / zero collateral. The pool keeps the borrow usage on its books with no counterparty. Alternatively, the expired-supply-map case permanently freezes/forfeits a borrower's collateral while making the debt collectible only socially.

### Likelihood Explanation
Requires a per-entry TTL/archival divergence between an account's `BorrowPositions` (or `SupplyPositions`) entry and its `AccountMeta`. Soroban persistent entries carry independent TTLs; entries are renewed only when touched, and `renew_account` renewal scope is bounded. A dormant leveraged account (borrowed, never touched) is the natural victim/attack setup — the attacker simply stops renewing the debt-side entry while keeping meta alive via cheap touches on other paths, or waits for natural divergence. Not exploitable on demand, hence Medium rather than Critical, but the defaulting pattern removes any on-chain signal distinguishing "no debt" from "debt record unavailable."

Note: I could not fully verify the TTL-renewal scope of `renew_account`/`get_user` within the tool-call budget; if every account-related key is co-renewed on any touch, the trigger window narrows but the missing-entry defaulting remains a latent inconsistency risk.

### Recommendation
Fail closed on divergence instead of defaulting: when `AccountMeta` exists, treat a missing `BorrowPositions`/`SupplyPositions` entry as an error (or archive-restore requirement), not an empty map. Concretely, in `get_debt_positions`/`get_supply_positions` (contracts/controller/src/storage/account.rs:63-73) distinguish `has` vs `get` for accounts with stored metadata, and panic with a dedicated error when a meta-bearing account's position map is absent. At minimum, make `debt_free()`/`is_empty()` conservative in the presence of nonzero spoke usage for that account's markets.

### Proof of Concept
1. Attacker supplies collateral in market A and borrows in market B via `supply`/`borrow`, obtaining `account_id`.
2. Attacker keeps the account metadata alive (e.g., periodic cheap calls that touch `AccountMeta`) while letting the `ControllerKey::BorrowPositions(account_id)` persistent entry expire to archive; or exploits natural TTL divergence on a dormant account.
3. `try_get_account` returns `Some(account)` with `borrow_positions` defaulting to an empty `Map`; `debt_free()` is true; `calculate_account_risk_totals` yields `total_debt = 0`, `health_factor = i128::MAX` (risk/totals.rs:203-207).
4. Attacker calls `withdraw(caller, account_id, [(hubA, 0)], to)` — zero means full withdrawal — passing all solvency checks and receiving the entire collateral.
5. Pool-side `borrowed`/`SpokeUsageRaw.borrowed_scaled_ray` for market B still show the debt; the account now holds no collateral and no recorded debt, so `liquidate` reverts (`HealthFactorTooHigh`) and `clean_bad_debt` cannot socialize what the account no longer records. The loss is borne by suppliers of market B.
