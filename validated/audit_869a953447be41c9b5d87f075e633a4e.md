## Title
Unchecked ERC20 transfer return value in Tron IntentGatewayV2 can permanently freeze escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` releases escrowed order tokens, transaction fees, and swept dust to beneficiaries using a raw low-level `.call()` to the token's `transfer` function, checking only that the call did not revert (`success`) but never decoding/validating the returned boolean. ERC20/TRC20 tokens that return `false` on a failed transfer instead of reverting will pass this check silently, while the internal escrow accounting is unconditionally decremented as if the transfer succeeded.

### Finding Description
In `withdraw()`, `IntentGatewayV2` releases each escrowed token to the beneficiary via:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [1](#0-0) 

`success` here only reflects whether the external call reverted, not whether the token contract's `transfer` returned `true`. A non-standard-but-common token that returns `false` instead of reverting on a failed transfer (e.g., insufficient balance in the sending contract, an internal pause, blacklist, or any other soft-failure condition) will make `success == true` even though no tokens moved. Immediately after this unchecked call, escrow accounting is unconditionally decremented:
```solidity
_orders[body.commitment][token] -= amount;
``` [2](#0-1) 

and the order is marked filled at the top of the function (`_filled[body.commitment] = beneficiary;`) regardless of whether the transfer actually delivered funds. [3](#0-2) 

The same unchecked pattern also releases protocol transaction fees:
```solidity
(bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
if (!success) revert TransferFailed();
delete _orders[body.commitment][TRANSACTION_FEES];
``` [4](#0-3) 

and the `SweepDust` handler used to sweep accumulated protocol dust to a beneficiary:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, req.beneficiary, amount));
if (!success) revert TransferFailed();
``` [5](#0-4) 

By contrast, the main EVM `IntentGatewayV2`/`IntentsBase` implementation consistently uses OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom`, which properly reverts on a `false` return value:
```solidity
IERC20(token).safeTransfer(beneficiary, amount);
...
IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
``` [6](#0-5) 

The Tron contract, despite importing `SafeERC20` and declaring `using SafeERC20 for IERC20;` [7](#0-6) , and correctly using `safeTransferFrom` for inbound token pulls [8](#0-7) , does not apply the same safety to any outbound transfer in `withdraw()` or the `SweepDust` handler, instead reverting to raw `.call()` + selector encoding.

### Impact Explanation
This is reachable by any relayer delivering a legitimate `RedeemEscrow`/`SweepDust` cross-chain message via `onAccept`/`onGetResponse` — no privileged role is required to trigger `withdraw()`, only a valid ISMP-delivered message that the intent-fill/cancel flow already produces during normal solver settlement. If the escrowed token silently returns `false` on failure (a known real-world pattern for several tokens, and plausible for TRC20 tokens deployed on Tron which this file specifically targets), the beneficiary receives no tokens while:
- the escrow ledger `_orders[commitment][token]` is decremented to zero,
- the order is marked `_filled`,
- `EscrowReleased`/`EscrowRefunded` is emitted as if settlement succeeded.

Because the order is now recorded as filled/refunded, there is no remaining code path to re-claim the un-transferred tokens — they remain stranded in the contract's balance with no accounting entry pointing to them, constituting a permanent freeze of user/solver funds.

### Likelihood Explanation
Likelihood depends on encountering a token whose `transfer` returns `false` rather than reverting on failure, which is a well-documented class of ERC20/TRC20 behavior. Given this is the Tron-specific contract deployed for TRC20 token interactions, and the flow is triggered by the standard, unprivileged intent-fill settlement path, the probability of a user/solver-supplied or protocol-permitted token exhibiting this behavior is non-negligible for a Medium-severity classification.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` outbound-transfer patterns in `withdraw()` and the `SweepDust` handler with `IERC20(token).safeTransfer(...)`, consistent with the inbound `safeTransferFrom` usage already present in the same file and with the mainline `IntentsBase._withdraw` implementation.

### Proof of Concept
1. Deploy (or use) a TRC20/ERC20 token whose `transfer(to, amount)` returns `false` on failure instead of reverting (e.g., insufficient allowance/balance in an internal accounting layer, paused state, or blacklist check that fails "gracefully").
2. Place an order on the Tron `IntentGatewayV2` escrowing this token as an input, per `placeOrder`.
3. Have a solver fill the order on the destination chain; the resulting `RedeemEscrow` message is delivered to the Tron gateway's `onAccept`, invoking `withdraw()`.
4. Arrange (or await) a transient/permanent condition in the token that causes its internal `transfer` to return `false` without reverting when called by the gateway (e.g., a pause flag toggled between escrow and withdrawal).
5. `withdraw()` observes `success == true` (external call did not revert) and proceeds to decrement `_orders[commitment][token]` to zero and mark `_filled[commitment] = beneficiary`, while the beneficiary's on-chain token balance is unchanged.
6. The tokens remain in the `IntentGatewayV2` contract's balance with no escrow entry or order state referencing them — they are permanently unrecoverable by the intended beneficiary through any existing contract function.
