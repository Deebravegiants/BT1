## Analysis

Confirmed: `account::verify_signed_message` at [1](#0-0)  performs only signature verification against the account's current authentication key — it never touches or consumes any on-chain state (no nonce table, no "used signature" marker). It is a pure, side-effect-free verification helper.

`usdk::transfer_from` at [2](#0-1)  builds the `Approval` challenge using `nonce: account::get_sequence_number(from)` — the **account's real transaction sequence number** — and calls `verify_signed_message`. Crucially, nothing in `transfer_from` increments, marks, or otherwise invalidates that sequence number. The Aptos VM only bumps an account's sequence number when *that account* is the transaction sender/fee-payer of a validated transaction; `transfer_from` is invoked by `spender`, not by `from`, so `from`'s sequence number is untouched by this call.

### Title
Unbounded replay of `transfer_from` permit-style approval in `usdk` stablecoin example — (File: `aptos-move/move-examples/fungible_asset/stablecoin/sources/usdk.move`)

### Summary
`usdk::transfer_from` implements an EIP-2612-style "permit" pattern to let a `spender` move funds out of `from`'s primary fungible store using an off-chain signature. The replay-protection field (`nonce`) is bound to `from`'s account sequence number, which is not modified by this function. Unlike the reported DAI/AAVE bug (front-running griefs a single intended call), the root cause here is the mirror-image and more severe issue: the same signed `Approval` message remains valid indefinitely and can be **replayed by the same authorized spender an unbounded number of times**, draining `from`'s balance repeatedly rather than the intended one-time amount.

### Finding Description
`transfer_from` constructs the challenge message: [3](#0-2) 
and verifies it via `account::verify_signed_message`, which is stateless (only checks the ed25519/multi-ed25519 signature against the current auth key) — [4](#0-3) .

The intended anti-replay value is `account::get_sequence_number(from)`. This value changes only when `from` itself submits/pays for a transaction (standard VM prologue behavior), not as a side effect of `transfer_from`. Since `transfer_from` is called by `spender` (not `from`), executing it does not consume or invalidate the nonce it just validated. If `from` is a dormant, resource, or infrequently-active account (a common case for custody-style holders, vaults, or automated depositors), its sequence number can remain constant for long periods, meaning a single signed `Approval` can be submitted many times by the same `spender` to repeatedly call `primary_fungible_store::transfer_with_ref` and drain the store — [5](#0-4) .

This breaks the core custody invariant that an owner-signed authorization should transfer exactly the authorized amount once; instead, the authorization becomes an unbounded standing withdrawal right for `amount` funds per replay, held by `spender`, until `from` happens to transact.

### Impact Explanation
This directly corrupts custody accounting: repeated invocation of `transfer_from` with an unexpired, unconsumed signature drains `from`'s fungible-asset holdings beyond the amount the owner authorized, moving value to `spender`/`to` without further owner consent. Since this is example/reference code in `move-examples`, real-world impact depends on whether a deployed stablecoin/fungible-asset issuer copies this pattern verbatim — a plausible scenario given it's shipped as a template. If used in a live deployment, this is a critical, high-value fund-drain vector on any FA holder who ever signs a `transfer_from` approval.

### Likelihood Explanation
Likelihood is high in any deployment that reuses this pattern as-is: exploitation requires no privileged access — only that the `spender` who is legitimately handed a valid signed approval chooses to submit the same transaction multiple times (trivial, since Aptos entry functions accepting `vector<u8>` proofs are not automatically deduplicated by the VM once validated). No front-running or race condition is needed, making this strictly easier to exploit than the original permit-griefing bug.

### Recommendation
Do not bind replay protection to the account's global transaction sequence number for an approval that is consumed by a *different* signer. Instead:
- Maintain a dedicated per-account "approval nonce" or "used signature hash" resource in the `usdk` module, explicitly incremented/marked inside `transfer_from` before or after the transfer succeeds.
- Alternatively, include a single-use, caller-supplied nonce value that is checked-and-recorded in a `Table<address, Table<u64,bool>>` (or similar) at the start of `transfer_from`, aborting on reuse.
- Add an explicit `deadline`/expiration field to `Approval` as defense in depth.

### Proof of Concept
1. `owner` (`from`) signs one `Approval { owner: from, to, nonce: N, chain_id, spender, amount }` where `N = account::get_sequence_number(from)` at signing time, and hands the signature to `spender` for a legitimate one-time transfer.
2. `spender` calls `usdk::transfer_from(spender, proof, from, scheme, pubkey, to, amount)`. It succeeds; `amount` moves from `from` to `to`.
3. `from`'s account sequence number is unchanged (only `spender`'s sequence number, the transaction sender, was incremented by the VM).
4. `spender` calls `usdk::transfer_from` again with the identical arguments. `account::get_sequence_number(from)` is still `N`, so the `Approval` struct reconstructed inside the function is byte-identical, and `verify_signed_message` succeeds again — transferring another `amount` from `from` to `to`.
5. Repeat until `from`'s store is exhausted, entirely without any new authorization from `from`.

**Caveat / uncertainty**: This is example/template code (`aptos-move/move-examples/fungible_asset/stablecoin`), not part of the core `aptos-framework` deployed at genesis, so mainnet relevance depends on downstream adoption of this exact contract. I could not find a nonce-consumption mechanism anywhere in this module or in `account::verify_signed_message`/`multisig_account.move`'s analogous uses of `account::get_sequence_number`-as-nonce (e.g., `multisig_account::create_with_existing_account` has the same pattern but is a one-time, idempotent account-creation action where replay has no effect, so it is not vulnerable in the same way).

    public fun verify_signed_message<T: drop>(
        account: address,
        account_scheme: u8,
        account_public_key: vector<u8>,
        signed_message_bytes: vector<u8>,
        message: T,
    ) acquires Account {
        let auth_key = get_authentication_key(account);
        // Verify that the `SignerCapabilityOfferProofChallengeV2` has the right information and is signed by the account owner's key
        if (account_scheme == ED25519_SCHEME) {
            let pubkey = ed25519::new_unvalidated_public_key_from_bytes(account_public_key);
            let expected_auth_key = ed25519::unvalidated_public_key_to_authentication_key(&pubkey);
            assert!(
                auth_key == expected_auth_key,
                error::invalid_argument(EWRONG_CURRENT_PUBLIC_KEY),
            );

            let signer_capability_sig = ed25519::new_signature_from_bytes(signed_message_bytes);
            assert!(
                ed25519::signature_verify_strict_t(&signer_capability_sig, &pubkey, message),
                error::invalid_argument(EINVALID_PROOF_OF_KNOWLEDGE),
            );
        } else if (account_scheme == MULTI_ED25519_SCHEME) {
            let pubkey = multi_ed25519::new_unvalidated_public_key_from_bytes(account_public_key);
            let expected_auth_key = multi_ed25519::unvalidated_public_key_to_authentication_key(&pubkey);
            assert!(
                auth_key == expected_auth_key,
                error::invalid_argument(EWRONG_CURRENT_PUBLIC_KEY),
            );

            let signer_capability_sig = multi_ed25519::new_signature_from_bytes(signed_message_bytes);
            assert!(
                multi_ed25519::signature_verify_strict_t(&signer_capability_sig, &pubkey, message),
                error::invalid_argument(EINVALID_PROOF_OF_KNOWLEDGE),
            );
        } else {
            abort error::invalid_argument(EINVALID_SCHEME)
        };
    }

        proof: vector<u8>,

        let transfer_ref = &borrow_global<Management>(usdk_address()).transfer_ref;
        // Only use with_ref API for primary_fungible_store (PFS) transfers in this module.
        primary_fungible_store::transfer_with_ref(transfer_ref, from, to, amount);
