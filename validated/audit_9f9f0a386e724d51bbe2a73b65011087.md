### Title
Debt-index accrual overflows `i128` and permanently freezes a high-utilization market - ([File: common/src/rates/index.rs])

### Summary
`update_indexes` is permissionless and forwards the caller-selected `assets` to the pool. During each accrual chunk, `calculate_supplier_rewards` multiplies total scaled debt by both the old and new borrow indexes. Once `borrowed * borrow_index` exceeds the `i128` range, the call panics with `MathOverflow` before the configured borrow-index cap can contain the state. Because every affected pool operation synchronizes the market first, subsequent repayments, withdrawals, borrows, liquidations, bad-debt cleanup, and revenue operations for that market also revert. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
The pool’s `accrue` operation loads each requested market and invokes `interest::global_sync`. Long elapsed intervals are split into bounded chunks, but each chunk calls `accrue_step`, whose reward calculation computes `borrowed.mul(old_borrow_index)` and `borrowed.mul(new_borrow_index)`. Both results must fit in `i128`; otherwise the fixed-point multiplication raises `MathOverflow`. [4](#0-3) [5](#0-4) [6](#0-5) 

This is a value-domain overflow rather than an attacker-controlled memory overwrite: the analog is that a carefully structured market state causes a remote arithmetic trap inside request processing. The critical ordering flaw is that total-debt reconstruction occurs before the index ceiling can safely stop growth, so a sufficiently large RAY-scaled debt balance can cross the `i128` value ceiling first. [7](#0-6) [8](#0-7) 

### Impact Explanation
A crossed market becomes permanently unusable. `synced_market` calls `Cache::load` followed by `global_sync`; repayment then calls `load_leg`, and withdrawal does the same before resolving user shares. Therefore the same overflow aborts exits and debt repayment, while borrowing, liquidation, supply, flash, and keeper paths touching that market also encounter accrual first. The repository’s regression test demonstrates that both `withdraw` and `repay` subsequently fail with `MathOverflow`. [9](#0-8) [10](#0-9) [11](#0-10) [12](#0-11) 

The result is permanent freezing of supplier and borrower funds in the affected `(hub_id, asset)` market, satisfying the accepted impact class. [13](#0-12) 

### Likelihood Explanation
An unprivileged caller can invoke `controller.update_indexes(caller, [hub_asset])`; the controller requires only caller authorization and then calls the pool’s owner-restricted `update_indexes`. Creating the vulnerable state requires a very large debt market and sustained high utilization, as reflected by the existing proof test’s billion-token, 98%-utilization fixture. Markets whose configured supply/borrow caps cannot admit that scale are not exposed, but the accrual code itself contains no fallback once the permitted scale is reached. [1](#0-0) [14](#0-13) 

### Recommendation
Make accrual saturation-aware before evaluating debt value. In `accrue_step`/`calculate_supplier_rewards`, use a non-panicking checked product or bound `new_borrow_index` so `borrowed * index` remains representable, then derive rewards from the bounded index consistently. Also apply the same explicit ceiling policy to the supply side and add an invariant test proving that accrual, repay, withdraw, liquidation, and revenue operations remain callable at the maximum configured market scale. [3](#0-2) [15](#0-14) 

### Proof of Concept
The existing harness test constructs a billion-unit 18-decimal market, borrows 98% of it, advances the ledger timestamp in accrual steps, and calls permissionless `update_indexes` until accrual fails with `MathOverflow`. It then verifies that withdrawal and repayment hit the same overflow. [16](#0-15)

// tests/test-harness/tests/controller/large_positions_and_long_horizons.rs

assert_contract_error(
    t.try_repay(ALICE, "BIG18", 1.0),

pub fn calculate_supplier_rewards(
    env: &Env,
    params: &MarketParams,
    borrowed: Ray,
    new_borrow_index: Ray,
    old_borrow_index: Ray,
) -> (Ray, Ray) {
    let old_total_debt = borrowed.mul(env, old_borrow_index);
    let new_total_debt = borrowed.mul(env, new_borrow_index);

    let accrued_interest = new_total_debt.checked_sub(env, old_total_debt);

    let protocol_fee = params.reserve_factor.apply_to_ray(env, accrued_interest);
    let supplier_rewards = accrued_interest.checked_sub(env, protocol_fee);

    (supplier_rewards, protocol_fee)

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();

/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);

        }

        "the index cap did not engage before the value overflow"
