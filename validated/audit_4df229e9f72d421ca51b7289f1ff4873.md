Audit Report

## Title
Plaintext JWT bearer token disclosed via wholesale request/response logging in gateway vault handler - ([File: core/capabilities/vault/gw_handler.go])

## Summary
`GatewayHandler.HandleGatewayMessage` logs the entire inbound `*jsonrpc.Request[json.RawMessage]` at Debug level and the entire outbound `*jsonrpc.Response[json.RawMessage]` at Info level, without stripping the `Auth` field. Since `req.Auth` carries the caller-supplied JWT bearer token used for vault JSON-RPC authorization, this results in plaintext credential disclosure in node logs when debug logging is enabled.

## Finding Description
`HandleGatewayMessage` logs the request object wholesale: [1](#0-0) 
and the response wholesale: [2](#0-1) 

`req` is a `*jsonrpc.Request[json.RawMessage]` (from `chainlink-common/pkg/jsonrpc2`) which carries an `Auth` field populated with the caller's raw JWT token, as shown throughout the vault test suite and jwt auth code: [3](#0-2) [4](#0-3) 

The HTTP gateway entrypoint extracts the bearer token from the `Authorization` header and forwards it into the request, ultimately reaching `req.Auth`: [5](#0-4) 

Elsewhere in the same package, developers are careful to avoid logging `req.Auth` directly, logging only a boolean presence flag instead: [6](#0-5) 

This demonstrates the team recognizes `Auth` as sensitive, yet the `Debugw("received message from gateway", "req", req)` and `Infow("Sent message to gateway", "resp", response)` calls in `gw_handler.go` log the entire struct via the structured zap-style logger without any redaction wrapper, `MarshalLogObject`, or field stripping. No custom redaction for `jsonrpc.Request`/`Response` was found in this repo.

## Impact Explanation
A leaked JWT is a full authentication credential for vault secret operations (create/update/delete/list, keyed to a workflow owner/org). If logs are shared, aggregated, or accessible to less-privileged log-viewing roles/support staff, a party with log read access could extract and replay the token (subject to expiry) to impersonate the original caller and perform unauthorized vault secret create/update/delete/list operations. This maps to the "key/secret exfiltration" impact class relevant to Chainlink's gateway/vault security scope. Severity is capped as it is a passive disclosure requiring separate read-access to logs, not a direct network compromise.

## Likelihood Explanation
Triggering the log line requires no extra privilege from the requesting client — any unprivileged/authenticated caller of the vault JSON-RPC gateway endpoint (`vault_secretsList`, `vault_secretsCreate`, etc.) with an `Authorization: Bearer <jwt>` header will have their token embedded in the `req` log line at Debug level and again in `resp`/response context at Info level. Exploiting the leak additionally requires that the node operator has Debug (or Info) logging enabled and that an attacker/insider has subsequent read access to the emitted logs. This is a real, reachable code defect (not hypothetical) and contradicts the security discipline shown in `authorizer.go`, which deliberately avoids logging `req.Auth` in the same code path.

## Recommendation
Redact or strip the `Auth` field before logging the request/response in `HandleGatewayMessage` — e.g., log a sanitized copy with `Auth` cleared, or log only non-sensitive fields (method, ID, gatewayID), mirroring the `"hasAuth", req.Auth != ""` pattern already used in `authorizer.go`. Consider a reusable redacting wrapper/`MarshalLogObject` implementation for `jsonrpc.Request`/`Response` so this protection is enforced centrally across all gateway handlers rather than per call site.

## Proof of Concept
1. Run a Chainlink node with the vault gateway capability configured and `Log.Level = 'debug'`.
2. As an unprivileged client, send a valid vault JSON-RPC request (e.g., `vault_secretsList`) to the gateway HTTP endpoint with `Authorization: Bearer <jwt-token>`.
3. `httpserver.go` extracts the bearer token and forwards it as `jsonrpc.Request.Auth` (core/services/gateway/network/httpserver.go:226-234).
4. `GatewayHandler.HandleGatewayMessage` logs the full request object at Debug (core/capabilities/vault/gw_handler.go:182).
5. Inspect the node's debug log output; the caller's JWT appears in plaintext in the `"req"` field.

Note: this finding assumes `jsonrpc.Request`/`Response` (defined in the external `chainlink-common` module) do not implement custom zap-marshaling that suppresses the `Auth` field; that module's source was not available for direct inspection in this repo's index, but the observed pattern of the project explicitly avoiding logging `req.Auth` elsewhere (`authorizer.go`) strongly suggests no such automatic redaction exists upstream.
