### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` authenticates nothing but the JSON payload bytes. The `shop` (and `topic`, `webhook-id`) values used downstream to identify the tenant are read straight from HTTP headers that are never part of the signed data.

### Finding Description
`Registry.process` gates handling on the HMAC check and then trusts `request.shop` unconditionally: [1](#0-0) 

`Request#to_signable_string` only covers `@raw_body`, while `Request#shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is completely outside of the HMAC computation: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e. against the raw body: [3](#0-2) 

This breaks the identity binding: `HMAC(raw_body, api_secret_key) == valid` should imply `shop-domain header == shop that Shopify actually delivered the webhook for`. Because the header is not part of the signed bytes, an attacker who owns any shop that has this app installed can capture one of their own genuine, correctly-signed webhook deliveries (body + valid HMAC, since they legitimately receive events from their own store) and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop's domain. The HMAC still validates (it only covers the body), but `WebhookMetadata.shop` — and any per-tenant routing/lookups the host app performs based on it — now reflects the attacker-chosen shop instead of the shop that actually generated the signed payload.

### Impact Explanation
This is a cross-tenant identity-binding failure: verified bytes (raw body) are decoupled from the field host applications use to select a tenant (`shop`). Any host app that uses `WebhookMetadata#shop` to look up per-shop records, permissions, or state (a documented, expected usage pattern of this field) can be made to apply attacker-controlled payload data to a different merchant's tenant context, i.e. cross-tenant access/data injection using only a signature the attacker legitimately possesses for their own shop.

### Likelihood Explanation
The prerequisite is modest: the attacker only needs to install/operate the app on any shop (their own), which is available to any unprivileged internet user for public apps, then capture and replay one webhook with a modified header — no access to `api_secret_key` or another merchant's token is required.

### Recommendation
Include the shop-domain (and topic/webhook-id, or at minimum the shop) in the signed material verified for webhooks, e.g. compute/verify the HMAC the same way Shopify does (body-only) but additionally require an out-of-band binding of `shop` to the registered webhook subscription/session for that shop, or reject/log any mismatch between the header-derived shop and the shop the receiving endpoint is scoped to before invoking handlers. At minimum, document loudly that `request.shop` is unauthenticated header data and must not be trusted for tenant selection without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a genuine event (e.g. `orders/create`), receiving a real webhook POST with a valid `X-Shopify-Hmac-Sha256` for the JSON body.
2. Attacker replays the exact same body + HMAC header to the app's webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the body against the secret — validation succeeds (`lib/shopify_api/utils/hmac_validator.rb:12-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
4. The handler receives `WebhookMetadata.new(... shop: request.shop ...)` with `shop == "victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though the payload never originated from that shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
