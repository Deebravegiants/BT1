### Title
Webhook HMAC signature covers only the request body, not the `shop-domain`/`topic` headers, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body. The `shop`, `topic`, `api_version`, and `webhook_id` values that are handed to the app's handler — and that the host application uses to attribute the webhook to a specific merchant/tenant — come from unauthenticated HTTP headers that are never included in the signed data.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate_signature` computes the HMAC over exactly that signable string and compares it to the `hmac-sha256` header: [2](#0-1) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from HTTP headers with no cryptographic binding to the body or the signature: [3](#0-2) 

`Registry.process` trusts these header-derived values after only checking that the HMAC over the body is valid, and passes them straight to the app-provided handler as the tenant identifier for the event: [4](#0-3) 

Because every shop that has this app installed shares the same `client_secret` (`Context.api_secret_key`), the HMAC over a given body is identical regardless of which shop it originated from. This breaks the intended identity binding:
`shop authenticated by the request == shop the handler attributes the event to`
In reality: `shop verified by HMAC (none, since shop isn't signed) != shop asserted by the "shopify-shop-domain" header (fully attacker-controlled)`.

An unprivileged internet user can:
1. Install the target app on their own (attacker-controlled) development/trial shop — a normal, unprivileged action any Shopify user can perform.
2. Receive one legitimate webhook delivery from Shopify for their own shop, capturing the raw body and its valid `x-shopify-hmac-sha256` value (both are computed with the app's shared secret and are valid for that exact body regardless of shop).
3. Replay that exact body + HMAC pair to the app's webhook endpoint, but substitute the `x-shopify-shop-domain` header (and/or `x-shopify-topic`) with a victim shop's domain / a different topic of their choosing among topics that accept the same body shape.
4. `Utils::HmacValidator.validate` succeeds (it only checks the body against the shared-secret HMAC), and `Registry.process` invokes the handler with `shop: <victim-shop>` even though the payload never actually came from or was authenticated for that shop.

### Impact Explanation
This is a cross-tenant identity-confusion vulnerability: an attacker can make the app process arbitrary attacker-chosen webhook bodies "as if" they belong to a victim merchant's shop, because the tenant identifier (`shop`) is never covered by the signature that is supposed to authenticate the request. Downstream host applications (per this gem's own documented usage pattern) key their business logic and data writes off `data.shop`, e.g. enqueuing jobs scoped to `shop_domain: data.shop`: [5](#0-4) 

Depending on the topics registered, this can be used to inject/forge data attributed to a victim tenant, trigger uninstall/reinstall side effects, or otherwise corrupt per-shop state — a cross-tenant access impact, which is explicitly listed as Critical impact in scope.

### Likelihood Explanation
Likelihood is high for an app that accepts more than one shop's webhooks (i.e., virtually any multi-tenant Shopify app): obtaining one genuine signed body/HMAC pair only requires installing the app on any shop the attacker controls (a free, self-service, unprivileged action), and no possession of `api_secret_key` or any victim credential is required — the attacker only reuses a signature that Shopify itself already computed and delivered to them for their own store.

### Recommendation
Include the identifying headers (at minimum `shop-domain`, and ideally `topic` and `webhook_id`) in the data covered by the HMAC verification, e.g. by having `to_signable_string` return a canonical concatenation of the raw body with the shop/topic headers, and update `HmacValidator`/webhook signature validation accordingly. If the header content itself cannot be changed (since Shopify controls the outbound webhook format), the gem should additionally require that the `shop` reported in the webhook headers be cross-checked against an independent source of truth (e.g., the registered webhook_id must map to a known `shop` recorded at registration time) before invoking the handler, rather than trusting the header value implicitly for tenant attribution.

### Proof of Concept
```
# Attacker installs the app on their own shop "attacker.myshopify.com"
# Shopify sends a legitimate webhook, e.g. for topic "customers/create":
POST /webhooks
x-shopify-topic: customers/create
x-shopify-hmac-sha256: <valid-hmac-for-body>
x-shopify-shop-domain: attacker.myshopify.com
x-shopify-webhook-id: abc-123
Body: {"id": 1, "email": "attacker@example.com"}

# Attacker replays the exact same body+hmac, changing only the shop header:
POST /webhooks
x-shopify-topic: customers/create
x-shopify-hmac-sha256: <same-valid-hmac-for-same-body>   # still valid, since HMAC is body-only
x-shopify-shop-domain: victim-shop.myshopify.com          # attacker-controlled, unauthenticated
x-shopify-webhook-id: abc-123
Body: {"id": 1, "email": "attacker@example.com"}

# ShopifyAPI::Webhooks::Registry.process(request) succeeds:
#   Utils::HmacValidator.validate(request) => true (body/secret match)
#   handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
# The app's handler now processes attacker-controlled data as belonging to victim-shop.myshopify.com.
```
