### Title
Stale owner check lets a previous position-NFT holder keep withdrawing and borrowing after transfer - (File: contracts/controller/src/account.rs)

### Summary
Access-control decisions for `withdraw`, `borrow`, `multiply`, `migrate_from_blend`, and delegate management compare the caller against `account.owner`, an `Address` written once at account creation in `create_account_with`. Position ownership, however, lives in the position-NFT contract (`owner_of` is authoritative — the NFT header even states "the token owner (`owner_of`) is the account owner"). The controller itself acknowledges this by providing a separate `require_account_owner` that re-reads `storage::account_owner` (the NFT) instead of trusting `account.owner`. Because `process_withdraw`/`process_borrow` use `require_owner_or_delegate(env, account_id, caller, &account.owner)` — not the NFT-derived owner — an unprivileged user who sells/transfers their position NFT can keep acting on the account as the stale stored `owner`.

### Finding Description
The authentication predicate `is_owner_or_delegate` in `contracts/controller/src/account.rs` (lines 115-127) returns `true` when `caller == owner`, where `owner` is `account.owner` loaded from `storage::get_account`. That field is set once in `create_account_with` (lines 64-70) and is never resynced on NFT transfer — the NFT's `transfer`/`approve` are stock OZ entrypoints with no controller hook to update `account.owner`.

Meanwhile `process_withdraw` (supply.rs:147-150) and `process_borrow` (debt.rs:40-43) authorize solely via `require_owner_or_delegate(env, account_id, caller, &account.owner)`. The codebase already treats these as different authorities: `require_account_owner` (account.rs:143-148) exists precisely because NFT ownership — not `account.owner` — is live truth, and is used for `renew_account`/`add_delegate`.

This mirrors the CVE-2019-11187 bug class: the access-control check authenticates the wrong principal (stale stored owner) rather than the actual owner, granting account control to a party who no longer holds it.

### Impact Explanation
After transferring/selling a position NFT, the seller calls `withdraw(account_id, withdrawals, to: Some(attacker))`. `require_owner_or_delegate` passes because `caller == account.owner`. `require_external_recipient` only rejects protocol contracts, not arbitrary attacker addresses. The attacker drains all collateral of the account now owned by the buyer — direct theft of user funds. Symmetrically, `borrow` with `to` lets the ex-owner mint debt against the victim's collateral and take the proceeds. Severity: Critical/High.

### Likelihood Explanation
Fully reachable by any unprivileged address: `transfer` the NFT (or have it moved), then call `withdraw`/`borrow`. Requires only that `account.owner` is not refreshed — nothing in `load_or_create_account`, `get_account`, or the NFT `transfer` path updates it. The only caveat I could not fully confirm in this pass is whether `storage::get_account`/`account_owner` reconciliation elsewhere rewrites `account.owner` on load; the presence of a distinct `require_account_owner` and the "account owner = NFT owner" documentation indicate it does not.

### Recommendation
In `is_owner_or_delegate`/`require_owner_or_delegate`, resolve the current owner via `storage::account_owner(env, account_id)` (NFT `owner_of`) instead of the stored `account.owner`, or assert `caller == account_owner` in `process_withdraw`/`process_borrow`. Also clear delegate lists keyed to the old owner on NFT transfer, or key delegates to the live NFT owner.

### Proof of Concept
1. Alice calls `supply` with `account_id = 0`; account 1 is created with `account.owner = Alice`; NFT id 1 minted to Alice.
2. Alice calls position-NFT `transfer(Alice, Bob, 1)`. `account.owner` in storage remains `Alice`.
3. Alice calls `withdraw(account_id = 1, withdrawals = [all collateral], to = Some(Alice))`.
4. `require_authorized_caller` passes (Alice authenticates); `require_owner_or_delegate` passes (`caller == account.owner`); the pool pays Bob's collateral to Alice. The same path works for `borrow` to extract debt proceeds against Bob's collateral.
