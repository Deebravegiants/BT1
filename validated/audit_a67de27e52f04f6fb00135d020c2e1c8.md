### Title
Ephemeral container admission bypasses SA secret allowlist via VolumeMounts to pre-existing Secret volumes - ([File: plugin/pkg/admission/serviceaccount/admission.go])

### Summary
`Plugin.Validate` routes ephemeral-container updates (`a.GetOperation() == admission.Update && a.GetSubresource() == "ephemeralcontainers"`) to `limitEphemeralContainerSecretReferences` instead of the full `limitSecretReferences` check used on pod Create. `limitEphemeralContainerSecretReferences` only inspects `Env`/`EnvFrom` secret references on the added ephemeral containers and never inspects `VolumeMounts`, so an ephemeral container can freely mount any Secret-backed `Volume` already present in `pod.Spec.Volumes` without any SA-allowlist check being performed at update time.

### Finding Description [1](#0-0) routes ephemeral container updates directly to the specialized checker instead of `limitSecretReferences`. That checker [2](#0-1) iterates `pod.Spec.EphemeralContainers` and only validates `container.Env` and `container.EnvFrom` `SecretKeyRef`/`SecretRef` names against `mountableSecrets` built from `serviceAccount.Secrets`; it never examines `container.VolumeMounts`. By contrast, the Create-path `limitSecretReferences` explicitly walks `pod.Spec.Volumes` for `Secret` volume sources and rejects any that are not in the SA's allowlist [3](#0-2) , but that function is never invoked for the `ephemeralcontainers` subresource path.

Given RBAC granting only `verb=update, resource=pods, subresource=ephemeralcontainers`, an attacker can `PATCH /api/v1/namespaces/ns/pods/p/ephemeralcontainers` adding an ephemeral container whose `volumeMounts` reference an existing `Volume` in the pod spec backed by a Secret that the pod's ServiceAccount does not reference in `.secrets`. Because `limitEphemeralContainerSecretReferences` never checks `VolumeMounts`, the request is admitted and the attacker's ephemeral container process can read that Secret's contents from the mounted path.

### Impact Explanation
This is a scoped secret-disclosure bypass of the ServiceAccount admission's secret allowlist enforcement (mirrors the CVE-2023-2728 root cause: incomplete parity between the ephemeral-container path and the full pod-create secret-reference check). It falls under the "admission bypass leading to sensitive data disclosure" bounty class — an attacker with only ephemeral-container update rights can read Secret data the pod's SA was never authorized to reference, when `enforceMountableSecrets` is turned on for that SA.

### Likelihood Explanation
Requires: (1) `LimitSecretReferences`/`EnforceMountableSecretsAnnotation` enabled for the SA (opt-in, disabled by default per `NewServiceAccount`), (2) the target pod already has a Secret-backed `Volume` in its spec (created earlier, e.g., before the enforcement flag was set, or via a legitimate container's mount) that is not in the SA's `.secrets`, and (3) attacker RBAC limited to `pods/ephemeralcontainers` update. Given these preconditions, exploitation is straightforward and repeatable via a single PATCH request; the primary limiting factor is that ephemeral containers can only mount volumes already declared in `pod.Spec.Volumes` (they cannot add new volumes), so the volume must already exist in the pod — this narrows exploitation mainly to TOCTOU windows (SA allowlist tightened after pod creation) or pods that had `enforceMountableSecrets` disabled at creation time and enabled later.

### Recommendation
Extend `limitEphemeralContainerSecretReferences` to also validate `container.VolumeMounts` against volumes with `Secret` sources in `pod.Spec.Volumes`, matching the logic already present in `limitSecretReferences`, so that any Secret-backed volume mounted by an added ephemeral container is checked against the SA's `mountableSecrets` allowlist.

### Proof of Concept
Table-driven unit test in `plugin/pkg/admission/serviceaccount/admission_test.go`:
1. Create a ServiceAccount `sa1` with `Secrets: []{Name: "allowed-secret"}` and `enforce-mountable-secrets` annotation (or `LimitSecretReferences=true`).
2. Create a Pod referencing `sa1`, with `Spec.Volumes` containing a Secret volume `v1` backed by `unauthorized-secret` (representing a pre-existing volume not in the SA allowlist).
3. Build an `admission.Attributes` with `Operation=Update`, `Subresource="ephemeralcontainers"`, object being the same pod with an added `EphemeralContainer` whose `VolumeMounts` references `v1`.
4. Call `Plugin.Validate` and assert it returns a `Forbidden` error (currently it will return `nil`, i.e., test fails, demonstrating the bug).
5. Add a companion case mirroring the CVE-2023-2728 regression (ephemeral container `Env.ValueFrom.SecretKeyRef` to an unauthorized secret) to confirm that path is already rejected, isolating the gap to the `VolumeMounts` variant.

```go
func (s *Plugin) limitSecretReferences(serviceAccount *corev1.ServiceAccount, pod *api.Pod) error {
	// Ensure all secrets the pod references are allowed by the service account
	mountableSecrets := sets.NewString()
	for _, s := range serviceAccount.Secrets {
		mountableSecrets.Insert(s.Name)
	}
	for _, volume := range pod.Spec.Volumes {
		source := volume.VolumeSource
		if source.Secret == nil {
			continue
		}
		secretName := source.Secret.SecretName
		if !mountableSecrets.Has(secretName) {
			return fmt.Errorf("volume with secret.secretName=\"%s\" is not allowed because service account %s does not reference that secret", secretName, serviceAccount.Name)
		}
	}
```
