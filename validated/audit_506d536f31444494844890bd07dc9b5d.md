The documentation explicitly states `Registry.process` "will verify the request did indeed come from Shopify" and presents `data.shop` as a trusted field for tenant dispatch (`shop_domain: data.shop`), yet the HMAC computation only covers the raw body, never the `shop`, `topic`, `webhook_id`, or `api_version` headers.### Title
Webhook `shop` (tenant) identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC-signable string as only the raw HTTP body (`to_signable_string` returns `@raw_body`), while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then dispatches the handler using these unauthenticated header values, including `shop`, as the tenant identifier.

### Finding Description
The identity binding that should hold is:
`shop authenticated by HMAC == shop used to dispatch/attribute the webhook data`.

In `lib/shopify_api/webhooks/request.rb`: [1](#0-0) [2](#0-1) 

`shop` comes from the `x-shopify-shop-domain`/`shopify-shop-domain` header, but `to_signable_string` (the value HMAC-verified) is only `@raw_body`. The header is never included in the signed material.

`HmacValidator.validate_signature` confirms the HMAC only covers `to_signable_string`: [3](#0-2) 

`Registry.process` validates the HMAC, then constructs `WebhookMetadata` using `request.shop` (the unauthenticated header) as the tenant key handed to the app's handler: [4](#0-3) 

The documentation explicitly instructs developers to trust `Registry.process` to "verify the request did indeed come from Shopify" and then use `data.shop` as the tenant/shop domain for persistence (`perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), confirming the library's documented contract presents `data.shop` as a verified value tied to the HMAC-verified request, when in fact it is not bound to the signature at all.

Because `Context.api_secret_key` is a single, app-wide secret (not per-shop), any body+HMAC pair that is valid for one shop is a valid HMAC for every other shop the app is installed on. A malicious merchant who has legitimately installed the app in their own store can trigger arbitrary webhook events with attacker-chosen JSON body content, capture the resulting (body, HMAC) pair delivered to their own callback endpoint, and then replay that identical body/HMAC pair to the victim's webhook endpoint while substituting the `x-shopify-shop-domain` header with the victim shop's domain. The HMAC check in `Registry.process` still passes (since it only checks the body against the shared secret), and the handler is invoked believing the (attacker-controlled) payload originated from the victim's shop.

### Impact Explanation
This breaks the cross-tenant isolation guarantee the HMAC check is documented to provide. An attacker with a legitimate but unprivileged installation of the app can inject spoofed data attributed to a completely different, victim shop into the host application's per-shop data store (e.g., fake order/customer/product state, triggering mandatory redact/data-request flows for a shop they don't control, or causing state corruption keyed by `shop`). This satisfies the Critical "cross-tenant access" impact category — the identity boundary between shop tenants is not enforced by the gem despite being presented to developers as verified.

### Likelihood Explanation
Likelihood is high for any app relying on this gem's default webhook processing exactly as documented: no special credentials, tokens, or privileged access are needed — only an ordinary "install the app on your own store" capability that is available to any internet user who can install a public Shopify app, combined with the ability to send an arbitrary HTTP request with attacker-controlled headers to the app's public webhook endpoint.

### Recommendation
Include the shop domain (and ideally topic/webhook id/api version) headers in the HMAC-signed material used by `VerifiableQuery#to_signable_string` for webhook requests, or bind the verified `shop` value to a canonical per-shop key derived from a source Shopify signs (or require an app-level or per-shop secret rotation scheme), so that the shop attribution used for dispatch is cryptographically bound to the same value that was HMAC-verified.

### Proof of Concept
1. App merchant A installs the target app; app registers an `orders/create` webhook.
2. Merchant A creates an order on their own shop `attacker-shop.myshopify.com`, triggering Shopify to POST a webhook to the app with body `B` and header `x-shopify-hmac-sha256: H` (`H = HMAC-SHA256(api_secret_key, B)`), `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures `(B, H)` (they own the endpoint/traffic for their own store).
4. Attacker sends a new POST request to the same webhook endpoint with unchanged body `B` and header `x-shopify-hmac-sha256: H`, but with `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only checks `H` against `B` — `lib/shopify_api/utils/hmac_validator.rb:26-31` and `lib/shopify_api/webhooks/request.rb:35-38`.
6. `Registry.process` invokes the app handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` — `lib/shopify_api/webhooks/registry.rb:188-200` — causing the app to process attacker-controlled data as if it came from the victim's shop.
