## Title
Malicious/reverting destination `IApp.onAccept` receiver can permanently block delivery of an untimed-out `PostRequest`, freezing the value locked on the source chain — analog of Sherlock #`teller` "lender can revert to prevent borrower from paying the loan" ([File: evm/src/core/EvmHost.sol])

## Summary
`EvmHost.dispatchIncoming(PostRequest,...)` delivers an incoming POST request by making a low-level `.call` into the destination `IApp.onAccept`. If that call reverts, the host silently swallows the failure, deletes the just-written `_requestReceipts[commitment]` entry "so it can be retried", and returns without reverting the batch [1](#0-0) . This is structurally identical to the reported Teller bug: the *recipient* of a value-bearing call (there, the lender's `tokensReceived` hook; here, the destination app's `onAccept`) can deterministically revert to block settlement of a transaction whose source-chain-side effects (escrow, burn, lock) have already been committed.

## Finding Description
`dispatchIncoming` for POST requests:
```solidity
_requestReceipts[commitment] = relayer;
(bool success,) = address(destination).call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));
if (!success) {
    // so that it can be retried
    delete _requestReceipts[commitment];
    return;
}
``` [2](#0-1) 

The comment and design intent ("so it can be retried") assume any failure is transient (e.g. out-of-gas, temporary state mismatch) and that a relayer can simply resubmit. But nothing prevents the destination app's `onAccept` from *deterministically* reverting for a specific request forever — e.g. because the message encodes a `beneficiary`/recipient address that is a contract crafted to always revert on the token transfer performed inside `onAccept` (the exact ERC-777/`tokensReceived` pattern from the source report, generalized to any external call/transfer made inside an app's `onAccept`).

Concrete instances of apps whose `onAccept` performs an external transfer to an address taken from the message body, any of which reverting blocks delivery of that specific message forever:
- `WrappedHyperFungibleToken.onAccept` / `WrappedHyperFungibleTokenUpgradeable.onAccept`: transfers underlying ERC-20 (or unwrapped native ETH) to `beneficiary = _toAddr(message.to)`, then optionally dispatches arbitrary `message.data` via `ICallDispatcher` [3](#0-2) .
- `IntentGatewayV2`/`IntentsBase._withdraw` (called from `onAccept` for `RedeemEscrow`/`RefundEscrow` messages): transfers escrowed tokens to `body.beneficiary` [4](#0-3) ; the Tron variant's `withdraw()` similarly `.call`s `IERC20.transfer` to the beneficiary and reverts the whole `onAccept`/`onGetResponse` path with `TransferFailed()` if that call fails [5](#0-4) .

Whether this is exploitable against a *third party* (not just self-harm) depends on whether the message's timeout mechanism can save the locked value. Per the project's own relayer documentation, some POST requests (e.g., relayer fee withdrawal messages) are explicitly dispatched with **no timeout** — "This request will not timeout, allowing it to be submitted to the destination chain at any time" [6](#0-5) . For any message class dispatched without a timeout (or with a timeout whose own `onPostRequestTimeout` callback can *also* be made to revert — see `HandlerV2`/`IHandlerV2` docs: "If callback reverts, no refund occurs. Timeout can be resubmitted until callback succeeds" [7](#0-6) ), a deterministically-reverting recipient has **no recovery path at all**: the message can be resubmitted by any relayer indefinitely, but will always fail identically, and the value already locked on the source chain (escrow, burn, or accrued fee) is permanently unredeemable.

## Impact Explanation
This matches the "route unable to deliver messages" / "permanent freezing of funds" categories explicitly accepted by scope. An attacker who controls the destination address referenced in a cross-chain message body (which they typically do, since they are the order creator / message recipient in flows like `IntentGatewayV2` cross-chain fills, or the intended beneficiary of a bridged token transfer) can engineer that address to revert only under the exact conditions of the crafted message (e.g., check `msg.data` / calldata against the transfer amount, or simply always revert), permanently bricking delivery of that specific request. For token-bridge (`WrappedHyperFungibleToken`) and intent-settlement (`IntentGatewayV2`) messages that either lack a timeout or whose timeout callback is also attacker-controlled, this permanently locks the escrowed/locked asset with no relayer or protocol-level remedy — the exact "borrower can never repay, lender seizes/traps collateral forever" outcome from the source report, translated to "sender can never have the request delivered or timed out, locked value is frozen forever."

## Likelihood Explanation
Medium: it requires the attacker to be the entity that controls the destination-side recipient/beneficiary address encoded in the message (which is normal and expected for most flows — users/solvers pick their own beneficiary), and requires a message class that either has no timeout or whose timeout callback path is also attacker-influenced. This is a design-level gap (fail-open retry semantics assuming transient failures) rather than a one-off logic bug, and is reachable by any unprivileged party who dispatches a cross-chain message naming themselves (or a contract they deploy) as the destination-side recipient.

## Recommendation
- Do not let a reverting destination callback (`onAccept`/`onPostRequestTimeout`/`onGetResponse`) silently block protocol-level bookkeeping (fee crediting, receipt state) indefinitely with no alternate resolution path.
- For messages that intentionally omit a timeout, add an explicit escape hatch (e.g., allow delivery to fall back to crediting a pull-based balance for the beneficiary, or allow the original sender/payer to reclaim locked funds after some governance-configurable grace period) instead of relying purely on "can be retried."
- Where possible, use a pull-based settlement pattern (as already recommended for the original Teller finding) for value transfers performed inside `onAccept`, e.g. record an internal credit that the beneficiary must separately withdraw, rather than pushing tokens synchronously as part of the callback whose success gates delivery/refund bookkeeping.

## Proof of Concept
1. Attacker deploys `MaliciousRecipient`, a contract with no `receive()`/fallback (or one that reverts unconditionally, or conditionally on `msg.value == X` / calldata matching a specific amount).
2. Attacker (as a normal user) places a cross-chain `IntentGatewayV2` order or triggers a `WrappedHyperFungibleToken.send()` with `beneficiary = MaliciousRecipient` and dispatches with `timeout = 0` (or, more generally, any message class the app dispatches without a timeout).
3. On the destination chain, a relayer submits the `PostRequest`; `EvmHost.dispatchIncoming` calls `MaliciousRecipient`'s app (`onAccept`), which reverts while trying to push the escrowed/bridged tokens to it: [8](#0-7) .
4. `_requestReceipts[commitment]` is deleted "so it can be retried"; any relayer resubmits the same request — it fails identically every time because `MaliciousRecipient` always reverts.
5. Because there is no timeout for this message (or the timeout callback path is equally blockable), the value already escrowed/burned on the source chain in anticipation of this delivery is permanently unredeemable — a stuck request with no recovery path, matching the "lender can permanently prevent the borrower's repayment" bug class from the source report.

**Note on verification limits:** I was able to confirm the `dispatchIncoming`/`onAccept` retry-on-failure pattern and the "no timeout" relayer-withdrawal documentation, and multiple `onAccept` implementations that push tokens to a message-supplied beneficiary. I was not able to fully trace, within the available tool budget, every message-dispatch call site across `IntentGatewayV2`/`ExtrinsicIntents` to enumerate exactly which specific cross-chain message types (`RedeemEscrow`, `RefundEscrow`, standard token `send`) are dispatched with `timeout = 0` versus a nonzero timeout, nor whether `onPostRequestTimeout` for those same apps can itself be forced to revert by the same attacker-controlled beneficiary. A background Devin session with full repo access could confirm the exact timeout values used by `IntentsBase._post`/`ExtrinsicIntents` and `WrappedHyperFungibleToken.send`, which would determine whether the frozen-funds impact is unconditional (no timeout at all) or bounded by an eventually-triggerable timeout refund.

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }

        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);

            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
