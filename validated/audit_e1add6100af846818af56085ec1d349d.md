### Title
Hardcoded 18-decimal `MinWithdrawal` floor in `pallet-ismp-relayer` can freeze relayer fee withdrawals when the currency uses fewer decimals - (File: modules/pallets/relayer/src/lib.rs)

### Summary
The relayer fee withdrawal pallet uses a fixed `MinWithdrawal` fallback of `10 * 10^18` raw units whenever a per-`StateMachine` `MinimumWithdrawalAmount` has not explicitly been set by governance. This constant assumes the configured `pallet_ismp::Config::Currency` has 18 decimals, mirroring the Y2K `CarouselFactory`/`Carousel` bug where a fixed numeric fee-floor is applied without regard to the underlying asset's decimals.

### Finding Description
`MinWithdrawal` is a hardcoded `Get<U256>` implementation: [1](#0-0) 

It's consumed as the fallback threshold inside `Pallet::<T>::withdraw` when no explicit `MinimumWithdrawalAmount` has been configured for the destination `StateMachine`: [2](#0-1) 

`BalanceOf<T>` is explicitly documented as being `pallet_ismp::Config::Currency`'s balance type, "the runtime's BRIDGE token in production", but the pallet is generic and reusable across runtimes: [3](#0-2) 

If a downstream runtime configures `pallet_ismp::Config::Currency` to a token with fewer decimals (e.g., a 6-decimal stablecoin) instead of an 18-decimal token, and governance has not yet called `set_minimum_withdrawal` for that specific `StateMachine`, the default `MinWithdrawal::get()` value of `10 * 10^18` raw units becomes astronomically large relative to that currency's actual decimal precision — effectively an unreachable balance. `set_minimum_withdrawal` itself takes a raw `u128` amount with no decimals-awareness check, so an admin unaware of the currency's decimals could also misconfigure it: [4](#0-3) 

This is the same bug class as the reported Y2K `CarouselFactory`/`Carousel` relayer-fee issue: a single global numeric threshold is applied uniformly without normalizing for the underlying asset's decimals, which becomes either negligible or prohibitive depending on the token used.

### Impact Explanation
If the default 18-decimal threshold is left active for a `StateMachine` backed by a low-decimal currency, relayers can accumulate fees via `accumulate_fees` (per-message accrual) but can never satisfy `available_amount >= MinWithdrawal::get()`, permanently freezing their earned relayer fees for that destination until governance notices and calls `set_minimum_withdrawal` with a corrected value. This matches the "permanent freezing of funds" criterion, though it is remediable by a subsequent governance extrinsic rather than being unrecoverable protocol-wide.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires (a) a runtime configuring `pallet_ismp::Config::Currency` with non-18 decimals, and (b) governance omitting to set a chain-specific `MinimumWithdrawalAmount` before relayers begin accruing fees on that destination. Because relayer fee accrual/withdrawal is reachable by any unprivileged relayer that has delivered a message (`accumulate_fees` is `ensure_none` and processed via `validate_unsigned`), the freezing condition itself needs no privileged action — only the initial default is a governance/config gap.

### Recommendation
Compute `MinWithdrawal`'s default relative to the actual configured currency's decimals (e.g., derive from `T::Currency`'s metadata or an explicit `Config::Decimals` constant) rather than hardcoding `10 * 10^18`, and validate `set_minimum_withdrawal` inputs against the currency's decimals to prevent similarly-shaped misconfiguration.

### Proof of Concept
1. Deploy a runtime with `pallet_ismp::Config::Currency` set to a 6-decimal asset.
2. Do not call `set_minimum_withdrawal` for a given `StateMachine`.
3. A relayer delivers messages and accumulates fees via `accumulate_fees`, e.g. total of 1,000 currency units (1000 * 10^6 raw = 1_000_000_000), far below `MinWithdrawal::get()` = `10 * 10^18`.
4. Any call to `withdraw` for that `StateMachine` reverts with `Error::<T>::NotEnoughBalance` regardless of how much the relayer has legitimately earned, since 10^18-scale threshold can never be reached at 6-decimal precision without an unrealistic accrual volume. [2](#0-1)
