### Title
POST request dispatch lets the caller set an arbitrary, unauthenticated fee-refund beneficiary (`payer`), diverging from the `_msgSender()`-bound accounting used for GET requests - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)` stores the caller-supplied `post.payer` field as the timeout-refund beneficiary instead of binding it to the account that actually funded the request (`_msgSender()`), which is what the sibling `dispatch(DispatchGet)` function correctly does. This lets any unprivileged caller redirect relayer-fee refunds to an arbitrary third-party address while paying with their own funds, or let an untrusted integrator/relayer silently capture refunds owed to the real payer.

### Finding Description
When a POST request is dispatched, the fee is unconditionally pulled from the transaction's actual sender: [1](#0-0) 

but the `FeeMetadata` record used to determine who is refunded on timeout is built from the caller-supplied, unauthenticated `post.payer` field rather than from `_msgSender()`: [2](#0-1) 

Contrast this with the GET-request dispatch path in the very same contract, which correctly ties the refund identity to the real fee payer: [3](#0-2) 

This is structurally identical to the Snipe-IT bug class: a field that represents "who owns/paid for this action" (`created_by` in Snipe-IT, `FeeMetadata.sender`/refund beneficiary here) is populated directly from unauthenticated, caller-controlled request data instead of being derived from the authenticated caller identity. `dispatch(DispatchPost)` is a fully public, unrestricted entrypoint (`external payable notFrozen`, no `restrict` modifier), reachable by any unprivileged dispatcher/relayer/app integrator in a single transaction.

When the request later times out, the refund is paid strictly to whatever address was recorded as `FeeMetadata.sender`, with no re-validation against the entity that funded the transfer: [4](#0-3) 

The library-level documentation also assumes this field is only used when the named `payer` itself grants an approval to the Host, implying `payer` should represent the funding party: [5](#0-4) 
but the implementation never enforces that `payer == _msgSender()` nor pulls funds from `payer`, so the field can be freely set to any address.

### Impact Explanation
Any application, integrator, or relayer that wraps `IDispatcher.dispatch()` on behalf of end users (as the SDK's own reference apps do, always setting `payer: msg.sender`) — [6](#0-5)  
— relies on the Host to correctly bind the refund beneficiary to whoever actually funded the fee. Because `EvmHost.dispatch(DispatchPost)` trusts the caller-supplied `payer` value unconditionally, a malicious or compromised integrator contract (or any direct caller of the Host) can set `payer` to its own address (or any arbitrary address) while the fee tokens are pulled from a different account/context, permanently diverting the relayer-fee refund away from the true payer on timeout. This is a concrete misdirection/loss of funds (CWE-863: Incorrect Authorization) affecting the fee-refund accounting path that every POST-dispatching app and end user depends on.

### Likelihood Explanation
`dispatch(DispatchPost)` is a completely permissionless, frequently used entrypoint invoked on every cross-chain POST message (the core of Hyperbridge messaging, token bridging, and intents flows). No special privilege, governance, or malicious-admin condition is required — a single unprivileged transaction with a crafted `payer` field is sufficient, making this trivially and repeatedly reachable by any message dispatcher/relayer/integrator.

### Recommendation
Bind the `FeeMetadata.sender` used for timeout refunds to `_msgSender()` (as already done in `dispatch(DispatchGet)`), or explicitly require and enforce that `post.payer == _msgSender()` unless a Host-verified `permit`/approval-based delegation from `payer` is presented at dispatch time. At minimum, remove reliance on caller-supplied `payer` for refund routing without a corresponding authorization check (e.g., signature or `transferFrom(payer, ...)` proving `payer`'s consent).

### Proof of Concept
1. Attacker (or a malicious integrator contract) calls `EvmHost.dispatch(DispatchPost)` directly, setting `post.fee = X` and `post.payer = attackerAddr2` (any address they control, or in the integrator case, silently different from the real end user who funded/approved the fee).
2. `dispatch` pulls `X` fee tokens from `_msgSender()` (the actual transaction sender / integrator contract) via `safeTransferFrom` — [1](#0-0) .
3. `_requestCommitments[commitment]` is stored with `sender: post.payer` (attacker-controlled), not the real fee payer — [7](#0-6) .
4. If the request times out, `dispatchTimeOut` refunds the entire fee to `meta.sender` (`attackerAddr2`), not to whichever account actually supplied the tokens — [8](#0-7) , permanently misdirecting the refund away from the true fee payer.

    function dispatchTimeOut(
        PostRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onPostRequestTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit PostRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
