### Title
Webhook shop-domain header is trusted for tenant identification but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates its HMAC over the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used to identify the tenant and dispatch the webhook are taken directly from unauthenticated HTTP headers. The equality the library implicitly claims to enforce — "the shop that is cryptographically bound to this request equals the shop the handler is told to act on" — does not actually hold, because the shop identity is never part of the signed content.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read straight from HTTP headers, none of which are covered by that signable string: [2](#0-1) 

`Registry.process` validates only the body HMAC via `Utils::HmacValidator.validate(request)`, then immediately forwards the unauthenticated `request.shop` (along with `request.topic`, `api_version`, `webhook_id`) to the app-supplied handler as trusted tenant metadata: [3](#0-2) 

`HmacValidator.validate_signature` confirms the check is purely `HMAC(secret, to_signable_string)`, i.e. `HMAC(secret, raw_body)`: [4](#0-3) 

`WebhookMetadata.shop` is a plain `String` field with no further verification, and the interface handed to host applications documents it as the authoritative shop for the event: [5](#0-4) 

The bug-class analog to the UMIP report is the same "field acted on but not covered by the HMAC" pattern: the report's `ancillaryData`/proposal-identity mismatch is about a value that downstream logic treats as an identity anchor (tenant/proposer) without it being bound by the verification mechanism. Here, `shop` is the tenant/identity anchor consumed by `WebhookMetadata` and the host handler, but it is excluded from the HMAC that is supposed to authenticate the whole webhook request.

Because the app's `client_secret` (and therefore the webhook-signing secret) is shared across every shop that installs the same app, any merchant who has legitimately installed the app can:
1. Trigger a webhook on their own store to obtain a valid `(raw_body, X-Shopify-Hmac-Sha256)` pair signed with the app's secret.
2. Replay that exact body/HMAC pair to the app's public webhook endpoint, but with the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header rewritten to name a victim shop.
3. Because `HmacValidator.validate` only checks the body against the secret — it never checks that the header-derived `shop` was part of what was signed — the forged request passes validation and `Registry.process` invokes the handler with `WebhookMetadata.shop` set to the victim's domain.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to provide to host applications: `Critical - cross-tenant access`. A single unprivileged installer of a multi-tenant app can inject attacker-chosen webhook payloads that the host application will process as if they originated from a different, victim merchant's shop, because the only identity binding (`shop`) is taken from a header outside the HMAC's scope. Depending on how the host app uses `WebhookMetadata.shop` (e.g., looking up the victim's session/access token to act on their store, or writing attacker data into the victim's record), this can lead to data corruption, unauthorized actions taken with the victim shop's stored access token, or privacy violations (e.g., forging `customers/data_request` or `shop/redact` compliance webhooks, which are handled through the same unauthenticated path).

### Likelihood Explanation
Any merchant/developer who can install the app (an "unprivileged internet user" in the sense that no elevated credentials of the platform or another tenant are required) can generate a valid signed body on their own store and replay it with modified shop-identifying headers. No knowledge of `client_secret` is required because the attacker legitimately receives a valid signature for their own webhook and simply changes header fields the verification never covered. This requires no TLS interception, no leaked credentials, and no access to another tenant's data — only ordinary use of the app as an installed merchant plus the ability to send raw HTTP requests to the app's public webhook endpoint.

### Recommendation
Include the identity-relevant headers (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-covered signable content, or otherwise cryptographically bind them (e.g., verify `shop` against a value embedded in the signed body, or require the host app be given only a validated, header-independent shop reference). At minimum, document prominently that `WebhookMetadata.shop` is derived from an unauthenticated header and must be independently validated (e.g., cross-checked against an existing session/install record) before being trusted for tenant-scoped operations.

### Proof of Concept
1. Install the vulnerable app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook subscription (e.g. `orders/create`) to receive a real webhook POST with a valid `X-Shopify-Hmac-Sha256` header computed over the JSON body using the shared `client_secret`.
2. Capture the raw body and HMAC header from that request.
3. Replay the identical body and HMAC value to the app's webhook endpoint, but replace the `X-Shopify-Shop-Domain` header with `victim.myshopify.com` (and optionally change `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate(request)` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) succeeds because it only checks `raw_body` against the secret.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) builds `WebhookMetadata` with `shop: "victim.myshopify.com"` and invokes the host's handler, which now processes attacker-supplied data as if it came from the victim shop.
