Confirmed: the tron `IntentGatewayV2.placeOrder` at `evm/tron/contracts/apps/IntentGatewayV2.sol#L471-L488` discards the router's return value and never re-adjusts or refunds `msgValue`, unlike the main EVM version which does capture `amounts[0]` and refunds any leftover `msgValue` back to `msg.sender` at the end of the function [1](#0-0) .

### Title
Unrefunded native-token change from `swapETHForExactTokens` becomes permanently stuck in the tron `IntentGatewayV2` contract - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
In the tron variant of `IntentGatewayV2.placeOrder`, when a user pays the order fee in native token, the contract calls the configured `IUniswapV2Router02.swapETHForExactTokens{value: msgValue}(...)` to swap the full `msgValue` for an exact amount of fee tokens, but discards the return value and never captures or refunds any leftover ETH. This mirrors the reported Aura Finance `depositSingle` bug pattern: the underlying swap wrapper (e.g. `UniV3UniswapV2Wrapper` / `UniV4UniswapV2Wrapper`) refunds unused input ETH to its `msg.sender`, but that `msg.sender` is the `IntentGatewayV2` contract, not the end user, so the refund is trapped in the gateway.

### Finding Description
`placeOrder` computes `msgValue` from `msg.value` and, when the order has a native-token fee payment path, forwards the entire remaining `msgValue` to the fee-token router:
```solidity
IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msgValue}(
    order.fees, path, address(this), block.timestamp
);
``` [2](#0-1) 

Compare this to the return-value-aware equivalent in the standard EVM `IntentGatewayV2.sol`, which captures `amounts[0]` (the actual amount spent) and subtracts it from `msgValue` before finally refunding any leftover `msgValue` to `msg.sender`:
```solidity
uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msgValue}(
    order.fees, path, address(this), block.timestamp
);
msgValue -= amounts[0];
...
if (msgValue > 0) {
    _sendValue(msg.sender, msgValue);
}
``` [3](#0-2) 

In the tron file, this return-value capture and the trailing "refund any unspent native tokens to the user" step are both absent — the function proceeds directly to `_orders[commitment][TRANSACTION_FEES] = order.fees;` and then emits `OrderPlaced` [4](#0-3) .

The router implementations used for this call (`UniV3UniswapV2Wrapper.swapETHForExactTokens` and `UniV4UniswapV2Wrapper.swapETHForExactTokens`) both only spend an exact amount out of the supplied `msg.value` and push the unused remainder back via a native transfer to their `msg.sender` — which, when invoked from `IntentGatewayV2`, is the `IntentGatewayV2` contract itself:
```solidity
if (spent < msg.value) {
    uint256 refund = msg.value - spent;
    IWETH(weth).withdraw(refund);
    (bool success,) = msg.sender.call{value: refund}("");
    if (!success) revert RefundFailed();
}
``` [5](#0-4) 
```solidity
uint256 refundETH = address(this).balance - balanceBefore;
if (refundETH > 0) {
    (bool success,) = msg.sender.call{value: refundETH}("");
    require(success, "ETH refund failed");
}
``` [6](#0-5) 

Because the router refunds unused ETH into `IntentGatewayV2`'s own balance and `placeOrder` never reads that refund back into `msgValue` accounting nor forwards it to the placing user, the excess ETH the user submitted for `order.fees` (any amount above the actual swap cost) accumulates as untracked ETH inside the `IntentGatewayV2` contract, exactly analogous to the reported `Omnipool`/Aura issue where a refund meant for the depositor lands on an intermediary contract instead.

### Impact Explanation
Every `placeOrder` call that pays fees in native token and overestimates the ETH needed for `swapETHForExactTokens` (which is expected in normal quoting since `order.fees` is a fixed token amount but the ETH price/slippage varies) permanently loses the unspent portion of the user's ETH into the `IntentGatewayV2` contract's balance, with no accounting variable or sweep mechanism recovering it for that user. This is a direct, repeatable loss of user funds on every affected order (Medium/High impact depending on typical fee overpayment margins), and since there's no state tracking these amounts per-user, they cannot be individually recovered — only an admin sweep (if one exists) could claim them as protocol dust, which is not the intended beneficiary.

### Likelihood Explanation
This triggers on any unprivileged `placeOrder` call on the tron deployment where `order.fees > 0` and the caller elects to pay via native ETH (`msgValue > 0` at that point), which is a normal, expected code path documented for fee payment flexibility. No special conditions or malicious actors are required — a single ordinary user transaction with typical slippage/quote buffer on the ETH-to-fee-token swap reproduces the loss every time.

### Recommendation
Mirror the standard `evm/src/apps/IntentGatewayV2.sol` implementation in the tron contract: capture the `amounts` array returned by `swapETHForExactTokens`, subtract the actual `amounts[0]` spent from `msgValue`, and add a final refund step that sends any residual `msgValue` back to `msg.sender` before emitting `OrderPlaced`.

### Proof of Concept
1. Deploy the tron `IntentGatewayV2` with a configured `uniswapV2Router` pointing to `UniV3UniswapV2Wrapper` (or `UniV4UniswapV2Wrapper`).
2. User calls `placeOrder` with `order.fees = 100` fee-token units and sends `msg.value` intentionally higher than the exact ETH cost to acquire 100 fee-token units (e.g., due to slippage buffer in the client quote).
3. Inside `placeOrder`, `swapETHForExactTokens{value: msgValue}(order.fees, path, address(this), ...)` is invoked; the wrapper spends only the exact ETH needed and refunds the difference back to `address(this)` (the `IntentGatewayV2` contract) as shown in `UniV3UniswapV2Wrapper.sol#L143-149`.
4. `placeOrder` never reads this refund back into `msgValue`, and there is no subsequent `_sendValue(msg.sender, msgValue)` call as exists in the standard `evm/src/apps/IntentGatewayV2.sol#L394-397`.
5. Verify post-transaction: `address(intentGateway).balance` increases by the refunded amount while the user's balance decreases by their full `msg.value`, confirming the excess ETH is trapped in the contract instead of returning to the user.
