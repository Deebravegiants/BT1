## Analysis

The JOJO bug class is: **a single "offending" element inside a batched operation causes the entire batch to revert**, even though the other elements in the batch are individually valid — a global check with no per-item isolation, reachable by an ordinary unprivileged actor.

The closest reachable analog in Hyperbridge is `HandlerV2.handlePostRequests()` (and its siblings `handleGetResponses`, `handlePostRequestTimeouts`, `handleGetRequestTimeouts`), which is invoked directly by any permissionless relayer to deliver a *batch* of ISMP messages proven together against a single MMR root.

### Title
Permissionless self-relay can be weaponized to revert an entire batched `handlePostRequests`/`handleGetResponses` delivery via `DuplicateMessage`, denying delivery for all co-batched (unrelated) requests - ([File: evm/src/core/HandlerV2.sol])

### Summary
`handlePostRequests` processes a relayer-submitted batch of `PostRequestLeaf`s under one Merkle Mountain Range proof and, in the second loop, reverts the *whole call* the instant any single leaf is found to already have a receipt: [1](#0-0) 
Because message delivery is explicitly documented as permissionless and self-relayable by any party, an attacker can observe a pending relayer batch transaction (which bundles many unrelated apps'/senders' requests under one proof) and front-run it by delivering just one of its leaves individually. When the larger batch transaction then lands, the pre-existing receipt for that one leaf trips `DuplicateMessage`, reverting delivery for every other request bundled in that same transaction. [2](#0-1) 

### Finding Description
`handlePostRequests` first verifies a single MMR multiproof covering all leaves in the batch, then loops a second time to check duplicates and dispatch: [3](#0-2) 
The duplicate check `if (host.requestReceipts(leaf.request.hash()) != address(0)) revert DuplicateMessage();` is unconditional on the whole call — exactly the JOJO pattern where a per-item condition (`(rateList[i]-oldRate).abs() <= maxChange`) triggers a `require`/`revert` that aborts processing for the entire batch rather than just the offending item. [1](#0-0) 
The same "all reverts because one item fails" structure is repeated in `handleGetResponses` (duplicate response), `handlePostRequestTimeouts`, and `handleGetRequestTimeouts` (unknown-message / not-timed-out checks), and is explicitly documented as atomic-by-design for `batchCall`: [4](#0-3) 
Self-relaying — delivering an individual message ahead of the relayer network — is a first-class, fully permissionless feature: [5](#0-4) 
Since a relayer bundles multiple senders' messages into one MMR-proved batch to save gas, and the delivery of any one leaf ahead of time is legitimate and permissionless, any third party can grief a bundled batch transaction by delivering one leaf out of it first: the batch's `DuplicateMessage` check then reverts the whole transaction, and none of the co-batched (otherwise valid, non-expired) requests get delivered in that transaction. `handlePostRequestTimeouts`/`handleGetRequestTimeouts` loops also unconditionally `revert` on the first `UnknownMessage`/`MessageNotTimedOut` encountered mid-loop: [6](#0-5) 
so an attacker can similarly poison a timeout batch by causing (or waiting for) one of its entries to already be delivered/undelivered relative to the others.

### Impact Explanation
This is a repeatable griefing/DoS vector on the message-delivery route itself: an unprivileged actor can force relayer batch transactions to revert on demand at near-zero cost (the cost of delivering one already-batched leaf individually), forcing relayers to detect the collision, recompute a new MMR multiproof excluding the duplicated leaf, and resubmit. Every request bundled alongside the targeted one is delayed — potentially past its own `timeout`, in which case it can never be delivered at all and must instead go through the timeout path, `MessageTimedOut()`. This satisfies the "route unable to deliver messages" impact category: batched delivery throughput/availability for arbitrary unrelated senders can be degraded or blocked by a single unprivileged party repeatedly targeting relayer batches.

### Likelihood Explanation
Likelihood is meaningful but bounded: it requires the attacker to observe pending relayer batch calldata (mempool visibility, or predictability of relayer batching behavior) and to already control (or be willing to pay gas to deliver) one leaf that is also present in the victim batch — feasible since self-relay of one's own dispatched message, or of any known pending request, is permissionless and requires no special access. It scales with batch size: larger relayer batches (more valuable to attack, more collateral damage per revert) are also easier to intersect with an attacker-controlled/observed leaf.

### Recommendation
Do not let a per-leaf failure abort the whole batch. In `handlePostRequests`/`handleGetResponses`/`handlePostRequestTimeouts`/`handleGetRequestTimeouts`, skip (rather than revert on) leaves that are already delivered/duplicated or otherwise individually invalid, continuing to process the remaining leaves in the same call, and emit a per-leaf event/return value indicating the skip. This isolates the fault to the offending leaf, matching the audit's original JOJO recommendation of confining the effect of an out-of-bounds item instead of reverting the entire batched operation.

### Proof of Concept
1. Relayer builds a `PostRequestMessage` batch containing leaves `[A, B, C]` (from three different, unrelated apps) proven under one MMR root/height, and broadcasts the `handlePostRequests` transaction.
2. Attacker observes this pending transaction (public mempool or predictable relaying pattern) and submits their own `handlePostRequests` (or single-leaf) transaction that delivers leaf `B` alone, landing first.
3. `host.requestReceipts(B.hash())` is now non-zero.
4. The original relayer's batch transaction executes: proof verification for `[A, B, C]` succeeds (membership only), but the dispatch loop hits `if (host.requestReceipts(leaf.request.hash()) != address(0)) revert DuplicateMessage();` on leaf `B` — [1](#0-0)  — reverting delivery of `A` and `C` as well, even though neither was duplicated or invalid.
5. Repeating this against every relayer batch containing more than one message denies timely delivery for all bundled requests, forcing per-leaf resubmission and, for any leaf whose `timeout()` elapses in the interim, permanent inability to deliver that request via `handlePostRequests` (only the timeout path remains) — [7](#0-6) .

    function handlePostRequests(IHost host, PostRequestMessage calldata request) external notFrozen(host) {
        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(request.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 requestsLen = request.requests.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](requestsLen);

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // check destination
            if (!leaf.request.dest.equals(host.host())) revert InvalidMessageDestination();
            // check time-out
            if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.request.hash());
        }

        bytes32 root = host.stateMachineCommitment(request.proof.height).overlayRoot;
        if (root == bytes32(0)) revert StateCommitmentNotFound();
        bool valid = MerkleMountainRange.VerifyProof(root, request.proof.multiproof, leaves, request.proof.leafCount);
        if (!valid) revert InvalidProof();

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // duplicate request?
            if (host.requestReceipts(leaf.request.hash()) != address(0)) revert DuplicateMessage();
            host.dispatchIncoming(leaf.request, _msgSender());
        }
    }

## Self Relayed Requests

Self-relaying allows you to deliver POST requests to the destination chain yourself, instead of relying on the Hyperbridge relayer network. This is useful when you want full control over delivery timing, need to save on relayer fees, or want to guarantee delivery for critical requests.

The `@hyperbridge/sdk` provides tools to track POST requests and automatically generates the calldata needed to execute [`handlePostRequests()`](/developers/evm/api/ihandler#handlepostrequests) on the destination chain's [`IHandler`](/developers/evm/api/ihandler) contract.

To learn how to self-relay requests:

1. **[Get Started with the SDK](/developers/sdk/getting-started)** - Install and set up the Hyperbridge SDK
2. **[Track POST Requests](/developers/sdk/tracking/post-requests)** - Monitor request status and extract delivery calldata
3. **[IsmpClient API](/developers/sdk/api/ismp-client)** - Use the [`postRequestStatusStream()`](/developers/sdk/api/ismp-client#postrequeststatusstream) method to get calldata when `HYPERBRIDGE_FINALIZED` status is reached

The SDK automatically generates the [`PostRequestMessage`](/developers/evm/api/ihandler#postrequestmessage) proof and calldata you need to call the [`IHandler.handlePostRequests()`](/developers/evm/api/ihandler#handlepostrequests) function on the destination chain. You can make your users self-relay requests or run a server which can relay requests on behalf of users.
