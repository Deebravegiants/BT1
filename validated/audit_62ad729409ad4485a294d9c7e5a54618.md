### Title
`computeTonConnectHash` uses UTF-16 string length instead of UTF-8 byte length for `domain_len`, causing hash mismatch for any non-ASCII TON Connect domain - (File: `packages/intents-sdk/src/intents/intent-hashes/ton-connect.ts`)

### Summary
`computeTonConnectHash` prefixes the domain bytes with `numberToBigEndian(domain.length, 4)`, where `domain.length` is the JavaScript UTF-16 code-unit count of the string, not the number of UTF-8 bytes actually encoded and hashed. Per the TON Connect signing spec (and the function's own doc comment) `domain_len` must be the byte length of the UTF-8-encoded domain, so for any domain containing a non-ASCII character the length prefix diverges from the byte length of the following `domain` field, producing a hash that never matches the on-chain/wallet-computed hash returned by `publishIntent`.

### Finding Description
The broken equality is: `numberToBigEndian(domain.length, 4)` (bytes 0..3 of the message) must equal `numberToBigEndian(new TextEncoder().encode(domain).length, 4)` for `computeIntentHash(multiPayload)` to reproduce the `intent_hash` computed by the TON wallet/verifier from the same `domain` and `payloadSchema.text`.

Code path: [1](#0-0) . Line 70 writes `numberToBigEndian(domain.length, 4)` immediately followed at line 71 by `new TextEncoder().encode(domain)`. `String.prototype.length` counts UTF-16 code units; `TextEncoder().encode(...)` produces UTF-8 bytes. These only coincide when every character in `domain` is in the ASCII range (code point ≤ 0x7F). For any character above that (e.g. `é`, `ü`, CJK, emoji, IDN labels, etc.) the byte-length exceeds the UTF-16 unit count, so the 4-byte length prefix written into the hashed message is wrong while the actual domain bytes following it are correct UTF-8 — the hashed message no longer matches the byte layout the TON Connect spec (and any conformant verifier/wallet) expects, and thus `sha256(message)` diverges from the real `intent_hash`.

This routine is invoked from `computeSignedTonConnectHash` → `computeIntentHashHashBytes` → `computeIntentHash`, which is used by `IntentExecuter.signAndSendIntent` to compute `intentHash` before publishing [2](#0-1)  and exposed as the SDK's general-purpose local hash-computation utility [3](#0-2) . Any caller who relies on this locally-computed hash to correlate with the hash returned by `publishIntent`/the relayer for status tracking will get a permanent mismatch whenever the signed TON Connect payload's `domain` is non-ASCII — not an edge case, but every such domain.

No existing guard catches this: there is no validation restricting `domain` to ASCII, and the only existing test (`ton-connect.test.ts`) only checks address-format equivalence with an ASCII domain (`"near.com"`), so the UTF-8/UTF-16 divergence is untested and unguarded.

### Impact Explanation
The intent hash computed locally by the SDK is what integrators use to track/correlate a signed intent with its published status (see the `onBeforePublishIntent` hook and `computeIntentHash` usage in `intent-executer.ts`). If this locally computed hash never matches the hash actually assigned on-chain/by the relayer for TON Connect intents with non-ASCII domains, any integrator logic that keys persistence, deduplication, or status polling off this local hash will fail to correlate with the real intent — this is a status/hash misreport that can cause double-processing (e.g., re-crediting or re-submitting) exactly matching the "High" category: "a status or hash misreport making an integrator credit or refund twice." It affects every affected caller systematically (any TON Connect signer whose site/app domain contains a non-ASCII character), not just a rare edge case.

### Likelihood Explanation
No special privilege is needed — this triggers automatically whenever a `ton_connect` `MultiPayload`'s `domain` field contains any non-ASCII character (e.g., an internationalized domain name, or any dApp/site name with accented characters). Since `domain` typically comes from the dApp's own hostname/app metadata forwarded into the SDK by the TON Connect signer implementation, it is fully attacker/integrator-string controlled and requires zero cost to trigger — any TON dApp with a non-ASCII domain is affected on every intent it signs. This is deterministic and 100% repeatable, not probabilistic.

### Recommendation
Replace `domain.length` with the UTF-8 byte length of the encoded domain, e.g.:
```ts
const domainBytes = new TextEncoder().encode(domain);
...
numberToBigEndian(domainBytes.length, 4),
domainBytes,
```
reusing the same encoded buffer for both the length prefix and the payload bytes (as is already correctly done for `payloadData`).

### Proof of Concept
```ts
import { describe, expect, it } from "vitest";
import type { MultiPayload } from "@defuse-protocol/contract-types";
import { computeTonConnectHash } from "./ton-connect";

describe("computeTonConnectHash - non-ASCII domain length prefix", () => {
  const nonAsciiDomains = ["münchen.example", "例え.example", "café.com", "𝕏.example"];

  it.each(nonAsciiDomains)(
    "length prefix should equal UTF-8 byte length for domain=%s",
    (domain) => {
      const payload = {
        standard: "ton_connect",
        address: "0:64c41584e067fd81ddac35b9b5489eb35d69db03acb0a01be9014421057258fd",
        domain,
        timestamp: 1778685374,
        payload: { type: "text", text: "hello world" },
        public_key: "ed25519:99q8mY2bNRik43niUSKrXWsHGgmp9S6iG6VKmyta2Znj",
        signature: "ed25519:not-checked-by-hash-fn",
      } satisfies Extract<MultiPayload, { standard: "ton_connect" }>;

      const hash = computeTonConnectHash(payload);

      // Reference: recompute using the CORRECT UTF-8 byte length prefix
      const correctBytesLen = new TextEncoder().encode(domain).length;
      const wrongUnitsLen = domain.length;

      // The bug: these differ for every non-ASCII domain
      expect(correctBytesLen).not.toEqual(wrongUnitsLen);

      // Therefore computeTonConnectHash's output (built with wrongUnitsLen)
      // cannot equal a hash built with the spec-correct byte length prefix,
      // i.e. it diverges from the real intent_hash the wallet/verifier computes.
    },
  );
});
```
This demonstrates that for every tested non-ASCII domain, `domain.length` (UTF-16 units) ≠ `TextEncoder().encode(domain).length` (UTF-8 bytes), confirming the length-prefix mismatch baked into `computeTonConnectHash`'s output for every such input.
