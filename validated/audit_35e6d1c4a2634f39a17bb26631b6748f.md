Audit Report

## Title
Unauthenticated LOOP registry discovery, metrics-proxy, and pprof-proxy endpoints bypass Chainlink node API authentication - (File: core/web/router.go)

## Summary
`NewRouter` builds an `api` route group with only rate limiting and session middleware (no authentication), and registers `loopRoutes(app, api)` directly on it, while `v2Routes` explicitly separates sensitive endpoints into an `authv2` sub-group requiring `auth.Authenticate`. This means `/discovery`, `/plugins/:name/metrics`, and `/plugins/:name/debug/pprof/*` are reachable by any client with network access to the node's API port without any credentials.

## Finding Description
In `core/web/router.go`, the `api` group is created with only rate limiting and cookie session support: <cite repo="AYontt/chainlink--003" path="core/web/router.go" start="77-85" />. `loopRoutes(app, api)` is registered directly on this group at line 91, with no authentication middleware applied: <cite repo="AYontt/chainlink--003" path="core/web/router.go" start="230-236" />. In contrast, `v2Routes` deliberately splits routes into `unauthedv2` (only the resume-run patch endpoint) and `authv2`, which wraps `metricRoutes` (the node's own pprof handlers) behind `auth.Authenticate`: <cite repo="AYontt/chainlink--003" path="core/web/router.go" start="238-248" /> and <cite repo="AYontt/chainlink--003" path="core/web/router.go" start="444-447" />.

The `discoveryHandler` returns internal plugin hostnames/ports as Prometheus service-discovery JSON with no auth check: <cite repo="AYontt/chainlink--003" path="core/web/loop_registry.go" start="52-65" />. `pluginMetricHandler` proxies to the internal LOOP plugin's `/metrics` endpoint and returns the raw body: <cite repo="AYontt/chainlink--003" path="core/web/loop_registry.go" start="95-128" />. `pluginPPROFHandler` and `pluginPPROFPOSTSymbolHandler` proxy arbitrary pprof profile/symbol requests (CPU profile, heap, goroutine, trace, with attacker-controlled `seconds`/`debug`/`gc` query params) to the internal plugin process and stream the results back: <cite repo="AYontt/chainlink--003" path="core/web/loop_registry.go" start="150-215" />. None of these handlers check session, API token, or role — they are gated only by whether the named plugin exists in the registry.

## Impact Explanation
This maps to the in-scope "node API authentication bypass" category. An unauthenticated client that can reach the node's API port can enumerate internal plugin topology via `/discovery`, pull internal Prometheus metrics via `/plugins/:name/metrics`, and — most significantly — trigger pprof profile/trace captures (`seconds` parameter controls duration) against LOOP plugin processes repeatedly, each held open by the reverse-proxy's `doRequest` for up to `seconds + 30` seconds, consuming plugin CPU/memory and node goroutines per request, and potentially exposing runtime stack/heap contents through profile data. This is a genuine broken authentication boundary distinct from a pure DDoS exclusion, since it also permits disclosure of internal service topology and profiling data that is normally gated behind authentication for the equivalent node-facing `metricRoutes`.

## Likelihood Explanation
High. `loopRoutes(app, api)` is called unconditionally inside `NewRouter` for every node with the default web server enabled, with no feature flag or dev-only gate. Any client capable of reaching the node's normal API port (default 6688) can invoke these three endpoint families without any credentials, and can repeat requests at will (rate-limited only by the same limiter applied to all API traffic).

## Recommendation
Move `loopRoutes` registration to occur under an authenticated group, e.g. reuse the `authv2`-style pattern: `r.Group("/", auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateByToken, auth.AuthenticateBySession))` and wire `/discovery`, `/plugins/:name/metrics`, and `/plugins/:name/debug/pprof/*` through it, mirroring how `metricRoutes(authv2)` is protected for the primary node's own pprof endpoints. If `/discovery` and `/plugins/:name/metrics` must remain reachable by an external Prometheus scraper without session/API-token auth, consider a separate listener/port bound to a private network interface, or a scrape-specific bearer token, rather than exposing them on the general public API port unauthenticated.

## Proof of Concept
1. Start a Chainlink node with default `WebServer` config and at least one LOOP plugin registered (e.g., a Solana/Median LOOPP).
2. Without any `Cookie` or `X-API-KEY`/`X-API-SECRET` header, issue:
   - `curl http://<node-host>:6688/discovery` → returns HTTP 200 with JSON listing internal plugin hostnames/ports.
   - `curl http://<node-host>:6688/plugins/<plugin-name>/metrics` → returns HTTP 200 with the plugin's raw Prometheus metrics.
   - `curl "http://<node-host>:6688/plugins/<plugin-name>/debug/pprof/profile?seconds=30"` → returns HTTP 200 with a CPU profile after 30s, consuming plugin resources, with no authentication challenge at any step.
3. Compare to `curl http://<node-host>:6688/v2/users` (an `authv2` route), which returns `401 Unauthorized` without credentials, confirming the inconsistency in authentication enforcement between `v2Routes` and `loopRoutes`.
