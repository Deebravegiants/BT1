### Title
Malicious input token in an order can permanently block escrow release/refund for solvers in `IntentsBase::_withdraw` - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase::_withdraw`, which is invoked from the cross-chain `RedeemEscrow`/`RefundEscrow` ISMP message handler (`ExtrinsicIntents::onAccept`) and from the same-chain fill/cancel paths (`IntrinsicIntents`), iterates over an order's escrowed tokens and calls `IERC20(token).safeTransfer(beneficiary, amount)` for each token in a single loop. If the order creator includes a malicious/poison token among `order.inputs`, that single token's revert on transfer causes the whole `_withdraw` call — and therefore the entire escrow release covering all other, legitimate tokens — to revert, permanently blocking a solver from ever claiming an already-earned reward.

### Finding Description
`_withdraw` decrements escrow accounting and transfers out every token in `body.tokens` inside one loop, with no isolation between individual transfers: [1](#0-0) 

This function is the sole path used to release solver rewards after a cross-chain fill. On the destination chain, `_fillCrossChain` immediately marks the order as filled and dispatches a `RedeemEscrow` message to the source chain carrying `order.inputs` as the tokens to release to the solver: [2](#0-1) 

When that message is delivered via Hyperbridge, `onAccept` authenticates it and calls `_withdraw` with `beneficiary = solver` and `tokens = order.inputs`: [3](#0-2) 

An intent creator can construct `order.inputs` to include legitimate tokens (e.g., USDC) plus a malicious token engineered to revert on `transfer` once the order has been filled (e.g., after the destination `_filled` flag would be set, or on any transfer past a certain block). A solver evaluating profitability from the legitimate token amount fills the order cross-chain, irrevocably delivering output assets to the beneficiary on the destination chain — `_filled[commitment]` is set there before any output transfer even completes. When the `RedeemEscrow` message later reaches the source chain, the malicious token's `transfer` reverts inside `_withdraw`, reverting the entire withdrawal, including the legitimate USDC release to the solver.

Because delivery of the ISMP message is deterministic given the same request, retried deliveries fail identically — the escrow can never be released to the solver. Worse, the cross-chain cancellation/refund path is also foreclosed: `_cancelFromSource` dispatches a GET query to check `_filled[commitment]` on the destination, and since the destination already recorded the solver as filler (`_fillCrossChain` sets `_filled[commitment] = msg.sender` unconditionally, before any output transfer), `onGetResponse` sees a non-empty value and reverts with `Filled()`: [4](#0-3) 

The result is that the escrowed input tokens (including the legitimate ones) become permanently frozen: unclaimable by the solver who already delivered value, and unrefundable to the user since the order is recorded as filled.

### Impact Explanation
High. A malicious intent creator can craft honeypot orders that appear profitable (legitimate token + a tiny poison token in `order.inputs`), lure a solver into delivering real value on the destination chain, and then permanently freeze the solver's earned escrow on the source chain via the poison token's revert. This is a direct theft-by-freezing vector against intent solvers and permanently locks funds in the `IntentGateway`/`IntentsBase` contract with no recovery path once filled.

### Likelihood Explanation
Medium. It requires an order creator to deliberately include a malicious token, which is straightforward to author (a token that reverts conditionally, e.g., after the order's `_filled` state would be set on destination, or that can be "armed" post-order-placement by an upgradeable/owner-controlled token). Solvers who don't rigorously validate every input token, or who trust apparently-standard ERC20s, are exposed. The upside for the attacker (freezing a solver's already-delivered value) makes this an attractive, repeatable attack.

### Recommendation
Do not let a single token transfer failure abort the whole withdrawal. In `_withdraw` (and the equivalent `withdraw` loop in the Tron variant), transfer each token via a low-level call and, on failure, skip/credit that specific token (e.g., track it as claimable separately or emit a per-token failure event) rather than reverting the entire function. This ensures legitimate tokens in the same order are always deliverable to the beneficiary regardless of any other malicious token in the same escrow bucket, matching the fix pattern already applied for the equivalent EVM `IntentVault` issue.

### Proof of Concept
1. Attacker deploys `PoisonToken`, an ERC20 whose `transfer` succeeds normally but is made to revert once a flag is set (attacker can flip the flag any time before the solver claims, e.g., right after the destination `_filled` event is observed for the order).
2. Attacker (order creator) builds an `Order` with `inputs = [ {USDC, 1000e6}, {PoisonToken, 1} ]`, `source` = chain A, `destination` = chain B, and calls `placeOrder`, escrowing both tokens in `IntentGateway` on chain A (this ultimately hits `_withdraw`'s counterpart escrow bookkeeping, unaffected here).
3. A solver, evaluating the 1000 USDC reward, fills the order on chain B via `fillOrder`/`_fillCrossChain`, delivering `order.output` assets to the beneficiary; `_filled[commitment]` is set on chain B and a `RedeemEscrow` `PostRequest` carrying `order.inputs` (USDC + PoisonToken) is dispatched to chain A via Hyperbridge.
4. Attacker flips the `PoisonToken` revert flag.
5. A relayer delivers the `RedeemEscrow` message to chain A; `EvmHost`/ISMP invokes `onAccept` → `_withdraw`. The loop successfully sends nothing yet, reaches the `PoisonToken` transfer, and reverts, unwinding the entire `_withdraw` call including the USDC transfer.
6. Every retry of message delivery reverts identically since `PoisonToken` permanently reverts. The solver can never claim the 1000 USDC despite having delivered the output on chain B, and the user cannot cancel/refund from source because `_filled[commitment]` is already set to the solver's address on chain B, causing `onGetResponse` to revert with `Filled()`. The escrowed USDC is permanently stuck in the gateway contract.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
