### Title
Intra-batch write/read lock race in `AccountLocks::try_lock_transaction_batch` allows simultaneous read and write locks on the same account - ([File: accounts-db/src/account_locks.rs])

### Finding Description
`try_lock_transaction_batch` processes an entire batch in two decoupled passes instead of a single interleaved check-then-lock pass per transaction: [1](#0-0) 

The first loop calls `can_lock_accounts` for **every** transaction in the batch against the *same, unmodified* `self` state (locks are not applied yet), and only the second loop calls `lock_accounts`, which unconditionally mutates `write_locks`/`readonly_locks` with no re-validation: [2](#0-1) 

Because validation for the whole batch happens before any locks are applied, two transactions in the *same batch* that reference the same key with conflicting lock types (A: read K, B: write K) both pass `can_lock_accounts` — B's check sees `self.write_locks`/`self.readonly_locks` still empty, since A's read lock hasn't been applied yet at that point. In the second pass, both `lock_readonly(K)` and `lock_write(K)` are then executed unconditionally, leaving `readonly_locks[K] == 1` and `write_locks[K] == 1` simultaneously — violating the mutual-exclusion invariant that `can_write_lock`/`can_read_lock` are supposed to enforce. A correct implementation must apply each transaction's lock immediately after validating it (or validate cumulatively against locks already granted within the same batch), which this two-phase split does not do.

An unprivileged attacker can trigger this simply by constructing two transactions in the same processing batch (e.g., within the same banking-stage batch handed to `Bank::prepare_sanitized_batch`) where one transaction declares `K` read-only and the other declares `K` writable, with no elevated privileges required — the account list, writability, and batch composition are all attacker-controlled inputs.

### Impact Explanation
This breaks the "only writable-declared accounts may be mutated; readers must not observe partial writes" invariant at the `AccountLocks` layer. If both transactions are then dispatched for execution/commit under the assumption that a granted lock guarantees exclusivity, the writer transaction can mutate `K` while the reader transaction is concurrently reading it or has its pre/post balance snapshots (`collect_pre_balances`/`collect_post_balances`, via `runtime/src/transaction_balances.rs`) taken mid-mutation, producing torn/incorrect balance data and inconsistent transaction-status output. This corresponds to an "undeclared account mutation / state corruption" class finding at the accounts-locking layer.

### Likelihood Explanation
Preconditions are minimal and fully attacker-controlled: only two ordinary transactions need to land in the same processing batch with a read/write conflict on a shared key. No validator, leader, or privileged access is required — this is a standard TPU/RPC transaction-submission scenario. The bug is deterministic given the code path shown (not a rare race window), because the two-phase design guarantees the check phase never observes locks from other batch members.

### Recommendation
Merge validation and locking into a single pass per transaction so each transaction's lock state is committed to `self` immediately after it passes `can_lock_accounts`, ensuring subsequent transactions in the same batch observe prior grants:
```rust
validated_batch_keys
    .into_iter()
    .map(|available_keys| {
        available_keys.and_then(|keys| {
            self.can_lock_accounts(keys.clone())?;
            self.lock_accounts(keys);
            Ok(())
        })
    })
    .collect()
```

### Proof of Concept
```rust
#[test]
fn test_intra_batch_read_write_conflict_both_succeed_bug() {
    let key = Pubkey::new_unique();
    let mut account_locks = AccountLocks::default();

    // Tx A: read-only lock on `key`
    let tx_a_keys = vec![(&key, false)];
    // Tx B: writable lock on `key`, in the SAME batch
    let tx_b_keys = vec![(&key, true)];

    let batch = vec![
        Ok(tx_a_keys.into_iter()),
        Ok(tx_b_keys.into_iter()),
    ];

    let results = account_locks.try_lock_transaction_batch(batch);

    // Expected (invariant): B must fail with AccountInUse since A holds a
    // read lock incompatible with a write lock.
    assert!(results[0].is_ok());
    assert_eq!(results[1], Err(TransactionError::AccountInUse)); // FAILS currently: both Ok
}
```
Running this against the current implementation shows `results[1]` is `Ok(())`, and internal state ends up with both `readonly_locks[key] == 1` and `write_locks[key] == 1` simultaneously, confirming the mutual-exclusion violation described.

```rust
    pub fn try_lock_transaction_batch<'a>(
        &mut self,
        mut validated_batch_keys: Vec<
            TransactionResult<impl Iterator<Item = (&'a Pubkey, bool)> + Clone>,
        >,
    ) -> Vec<TransactionResult<()>> {
        validated_batch_keys.iter_mut().for_each(|validated_keys| {
            if let Ok(keys) = validated_keys.as_ref()
                && let Err(e) = self.can_lock_accounts(keys.clone())
            {
                *validated_keys = Err(e);
            }
        });

        validated_batch_keys
            .into_iter()
            .map(|available_keys| available_keys.map(|keys| self.lock_accounts(keys)))
            .collect()
    }
```

```rust
    fn can_lock_accounts<'a>(
        &self,
        keys: impl Iterator<Item = (&'a Pubkey, bool)>,
    ) -> TransactionResult<()> {
        for (key, writable) in keys {
            if writable {
                if !self.can_write_lock(key) {
                    return Err(TransactionError::AccountInUse);
                }
            } else if !self.can_read_lock(key) {
                return Err(TransactionError::AccountInUse);
            }
        }

        Ok(())
    }

    fn lock_accounts<'a>(&mut self, keys: impl Iterator<Item = (&'a Pubkey, bool)>) {
        for (key, writable) in keys {
            if writable {
                self.lock_write(key);
            } else {
                self.lock_readonly(key);
            }
        }
    }
```
