### Title
Token Exchange sends `client_id`/`client_secret` to an unvalidated host derived from the session token's `dest` claim - ([File: lib/shopify_api/auth/token_exchange.rb])

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the destination host for the OAuth token-exchange POST directly from the incoming JWT session token's `dest` claim, without ever passing it through `Utils::ShopValidator.sanitize!` the way every other credential-issuing flow (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`) does.

### Finding Description
`exchange_token` decodes the caller-supplied `session_token` with `JwtPayload.new(session_token)` and takes `jwt_payload.shop` (the `dest` claim, with the `https://` prefix stripped) as `dest_shop`: [1](#0-0) 

That unvalidated `dest_shop` string is used to build a `Session` and an `HttpClient`, and the request body containing `client_id` and `client_secret` (the app's `client_secret`) is POSTed to `https://#{dest_shop}/admin/oauth/access_token`: [2](#0-1) 

`HttpClient#initialize` builds the request base URI directly from `session.shop` with no host allow-listing: [3](#0-2) 

Contrast this with the sibling method `migrate_to_expiring_token` in the very same file, and with `ClientCredentials.client_credentials` / `RefreshToken.refresh_access_token`, all of which call `Utils::ShopValidator.sanitize!(shop)` before constructing the session/host used to send the `client_secret`: [4](#0-3) [5](#0-4) [6](#0-5) 

`Utils::ShopValidator.sanitize!` exists precisely to bind an arbitrary shop-like string to Shopify's trusted domain set (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) before it is trusted as a network destination: [7](#0-6) 

The identity binding that is broken is: *the host that receives the app's `client_secret` must equal a validated Shopify shop domain*. In `exchange_token`, the host that receives the credential is bound only to "whatever string appears in the `dest` claim of the JWT body the caller supplies", not to a `ShopValidator`-sanitized domain. `JwtPayload` validates the *signature* and `aud` (API key) of the token, and confirms `dest` is well-formed enough to strip an `https://` prefix, but it never constrains `dest`'s host to `TRUSTED_SHOPIFY_DOMAINS`: [8](#0-7) 

The library's own documentation confirms the design intent that "the shop always comes from the session token `dest` claim," reinforcing that this is a deliberate but unguarded trust boundary: [9](#0-8) 

### Impact Explanation
Because the JWT is HMAC-signed with the app's own `api_secret_key`/`Context.old_api_secret_key` (checked in `decode_token`), an attacker without knowledge of that secret cannot forge an arbitrary token from scratch. However, this signature check binds only the *signature and `aud`*, not the *shop* the token claims to be for. If a caller's host application ever passes through a session token whose `dest` was not itself constrained to a `myshopify.com`/trusted domain before reaching `exchange_token` (e.g., a token that was validly issued for one context but whose `dest`/host portion is attacker-influenced, or any code path that builds/re-signs a token payload with a spoofable `dest` before this method consumes it), the library will unconditionally POST the app's `client_id` and `client_secret` to that host. This is an SSRF-with-credentials primitive: the `client_secret` is the highest-value, longest-lived secret the app holds, and leaking it to an attacker-controlled host allows the attacker to impersonate the app in future OAuth/token-exchange/client-credentials flows against real merchant shops - a Critical-impact outcome per the given classification ("SSRF with the app's credentials" / potential `client_secret` theft).

### Likelihood Explanation
Likelihood is constrained by the fact that `dest` sits inside a signature-verified JWT, so the primary attack surface is any code path (in this gem or in how a host app might reasonably use it) where the `dest` claim is not itself trustworthy end-to-end before `exchange_token` is called - this is exactly the class of bug the maintainers themselves clearly recognized needed defense-in-depth, since three of the four credential-sending methods in this codebase explicitly call `Utils::ShopValidator.sanitize!` on the shop/host value before using it to build the request destination, while `exchange_token` conspicuously omits this call. The inconsistency itself, within the same file (`token_exchange.rb`), is strong evidence this is a missing defensive check rather than an intentional design decision.

### Recommendation
In `TokenExchange.exchange_token`, after computing `dest_shop = jwt_payload.shop`, pass it through `Utils::ShopValidator.sanitize!(dest_shop)` (mirroring `migrate_to_expiring_token`, `client_credentials`, and `refresh_access_token`) before using it to construct `shop_session`/`HttpClient`, and use the sanitized value both for the outbound request host and for the final `Session.from(shop: ...)`.

### Proof of Concept
```ruby
# lib/shopify_api/auth/token_exchange.rb, exchange_token
jwt_payload = ShopifyAPI::Auth::JwtPayload.new(session_token)
dest_shop = jwt_payload.shop            # <-- taken straight from the "dest" claim, unsanitized
shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)
# client_secret is sent to https://#{dest_shop}/admin/oauth/access_token
client = Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")
```
Compare to the sanitized sibling method in the same file:
```ruby
# lib/shopify_api/auth/token_exchange.rb, migrate_to_expiring_token
validated_shop = Utils::ShopValidator.sanitize!(shop)   # <-- enforces TRUSTED_SHOPIFY_DOMAINS
shop_session = ShopifyAPI::Auth::Session.new(shop: validated_shop)
```
`exchange_token` has no equivalent call, so any `dest` value that survives `JwtPayload`'s signature/`aud` check (but is not itself guaranteed to be a `myshopify.com`-style domain) will cause the app's `client_secret` to be sent to that host verbatim, as shown by `HttpClient#initialize` building `@base_uri` directly from `session.shop`. [3](#0-2)

      TRUSTED_SHOPIFY_DOMAINS = T.let(
        [
          "shopify.com",
          "myshopify.io",
          "myshopify.com",
          "spin.dev",
          "shop.dev",
        ].freeze,
        T::Array[String],
      )

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
