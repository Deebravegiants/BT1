Found a solid analog. Here's the key code:### Title
OAuth `state` anti-CSRF nonce compared with non-constant-time `==` allows timing-based recovery and forced OAuth completion - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` compares the anti-CSRF `state` nonce (read from the `shopify_app_session` cookie) against the `state` parameter supplied in the OAuth callback request using plain Ruby string equality (`state == auth_query.state`), instead of a constant-time comparison such as `OpenSSL.secure_compare`, which the library already uses elsewhere for its HMAC checks.

### Finding Description
The identity binding this code is supposed to enforce is: `state stored in the httponly cookie set during begin_auth == state parameter returned by the OAuth provider in the callback`. This binding is the sole anti-CSRF/forced-OAuth-completion protection for the authorization code grant flow.

`begin_auth` generates a 15-character alphanumeric nonce and returns it in a `SessionCookie`: [1](#0-0) 

`validate_auth_callback` then checks the cookie-stored value against the query-string value using ordinary Ruby `String#==`: [2](#0-1) 

Ruby's `String#==` short-circuits on the first mismatched byte, so the time taken to evaluate the comparison leaks how many leading bytes of the guess are correct. This is exactly the bug class in the referenced report: a secret value is compared/derived through an operation whose output (here, timing instead of a Pedersen commitment) acts as an oracle enabling incremental recovery of a value that is supposed to remain hidden from an unauthorized party guessing it. Contrast this with the HMAC validation code in the same gem, which correctly uses a constant-time comparison for exactly this reason: [3](#0-2) 

Because the `state` value is the only artifact binding "the party that initiated `begin_auth`" to "the party completing the callback," a timing side-channel that lets an attacker reconstruct the correct `state` value byte-by-byte lets the attacker forge a valid callback URL/cookie pair without ever having legitimately initiated the flow, defeating the CSRF protection the state nonce exists to provide.

### Impact Explanation
Successfully guessing `state` allows an attacker to construct a callback request that will pass the `state == auth_query.state` check, enabling forced OAuth completion / CSRF against the app's OAuth callback endpoint — one of the explicitly listed High-severity outcomes (session fixation or forced OAuth completion). This can result in the attacker's authorization code/access token being bound into a victim's session, or a victim's session being bound to an attacker-controlled shop/token, depending on how the host application wires session storage to `validate_auth_callback`.

### Likelihood Explanation
Exploitation requires many timing measurements per byte position against a live server, over what is likely a noisy network channel (classic remote timing-attack constraints), so this is a High rather than Critical severity issue — it is not a one-shot bypass but a probabilistic timing side-channel, consistent with the "guessing" mechanism described in the source report (which itself required iterative guessing against a commitment oracle).

### Recommendation
Replace `state == auth_query.state` with a constant-time comparison, consistent with the rest of the codebase's HMAC validation:
```ruby
raise Errors::InvalidOauthError,
  "Invalid state in OAuth callback." unless state && OpenSSL.secure_compare(state, auth_query.state.to_s)
```

### Proof of Concept
1. App calls `ShopifyAPI::Auth::Oauth.begin_auth`, which sets cookie `shopify_app_session=<state>` (15 random alphanumeric chars) in the victim's browser and starts the OAuth redirect.
2. Attacker cannot read the httponly cookie directly, but can repeatedly submit callback requests to the app's OAuth callback endpoint with the victim's browser (which will automatically send the cookie) while varying a candidate `state` query parameter, timing each response from `Oauth.validate_auth_callback`.
3. Because `state == auth_query.state` in `lib/shopify_api/auth/oauth.rb:71` uses non-constant-time `String#==`, responses for candidate strings that match more leading bytes of the true cookie value take measurably longer to fail (or succeed once fully guessed).
4. By iterating this measurement per byte position (62 possible alphanumeric characters × ≤15 positions), the attacker statistically recovers the correct `state` value.
5. With the correct `state` value, the attacker can construct/replay a callback request (e.g., via CSRF against a victim who still has the matching cookie) that passes validation, completing the OAuth flow under attacker-influenced parameters — forced OAuth completion.
