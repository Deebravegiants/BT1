## Finding: Unchecked ERC20 return value in Tron `IntentGatewayV2.withdraw()` finalizes escrow before confirming the transfer succeeded

### Title
Silent transfer failure in Tron `IntentGatewayV2.withdraw()` permanently strands escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron port of `IntentGatewayV2` releases and refunds cross-chain escrow using a raw low-level `.call()` to the token's `transfer` selector and only checks that the call did not revert (`success`), never inspecting the returned `bool` that ERC20/TRC20 `transfer()` uses to signal failure. This lets a non-strictly-reverting token silently fail to move funds while the contract still finalizes accounting and emits a success event.

### Finding Description
`withdraw()` in the Tron contract is the destination-side handler for both `RedeemEscrow` (solver settlement) and `RefundEscrow` (cancellation) messages, reached permissionlessly via `onAccept()`: [1](#0-0) 

The relevant transfer path is:
```
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
_orders[body.commitment][token] -= amount;
```
`success` is only `false` if the callee reverts or the call itself fails at the EVM/TVM level; it is `true` whenever a `transfer()` implementation returns normally, *even if it returns `false`* — the common failure signature for many non-compliant or condition-gated ERC20/TRC20 tokens (pausable, blacklist-enabled, or otherwise non-strict implementations). Once `success` is `true`, the function unconditionally decrements the escrow bucket, marks `_filled[commitment] = beneficiary`, and emits `EscrowReleased`/`EscrowRefunded`, finalizing the order regardless of whether tokens actually reached the beneficiary.

This is dispatched via the same `onAccept` entrypoint used for `RedeemEscrow`/`RefundEscrow` requests reachable by any relayer delivering a legitimate settlement/cancellation message from a peer `IntentGatewayV2` instance: [2](#0-1) 

The hardened, mainline EVM implementation avoids this class of bug entirely by using OpenZeppelin's `SafeERC20.safeTransfer`, which reverts the whole transaction (including state changes) if the underlying transfer call fails or returns `false`: [3](#0-2) [4](#0-3) 

The same low-level pattern is used again for `SweepDust` in the Tron contract: [5](#0-4) 

### Impact Explanation
Because the escrow slot is decremented and the order is finalized (`_filled` set) on a `transfer()` call that merely returned `false`, the beneficiary never receives the tokens, and the contract's accounting no longer reflects any outstanding balance for that commitment. There is no retry or reclaim path once `_filled` is finalized and `_orders[...] -= amount` has already executed — the tokens remain stuck in the `IntentGatewayV2` contract's balance with no accounting entry pointing to them. This meets the "permanent freezing of funds" acceptance criterion: user-escrowed input tokens on a cross-chain order become permanently unrecoverable through the protocol's normal settlement or cancellation paths.

### Likelihood Explanation
This triggers automatically, without any attacker-crafted proof or governance compromise, whenever the escrowed/refunded token's `transfer()` can return `false` instead of reverting under any condition (paused state, blacklist, insufficient internal balance/allowance quirks common to many TRC20 tokens). Every legitimate `RedeemEscrow`/`RefundEscrow` delivery for such a token during that condition silently locks funds. Given TRC20 tokens on Tron frequently deviate from strict-revert-on-failure semantics, likelihood is Medium-to-High for any deployment integrating non-audited or pausable tokens.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` (and in the `SweepDust` branch) with OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom`, matching `IntentsBase.sol`'s `_withdraw`. This ensures any failed transfer — including one that returns `false` without reverting — reverts the entire delivery, leaving `_orders` accounting and `_filled` state untouched so the message can be safely retried instead of silently finalizing on a failed transfer.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` with a TRC20 token `T` whose `transfer()` implementation returns `false` (rather than reverting) when, e.g., the recipient is paused/blacklisted or a supply-cap condition is hit.
2. A user places a cross-chain order escrowing `T` on the source chain (Tron).
3. A solver fills the order on the destination chain; the fill dispatches a `RedeemEscrow` message back to the source chain.
4. A relayer delivers this message; `onAccept` → `withdraw()` calls `T.transfer(solver, amount)`, which returns `false` under the failing condition but does not revert, so `success == true`.
5. `withdraw()` proceeds: decrements `_orders[commitment][T]`, sets `_filled[commitment] = solver`, and emits `EscrowReleased` — yet `solver` never received the tokens, which remain permanently locked in the `IntentGatewayV2` contract's balance with no accounting path to recover them.

**Note:** I was unable to retrieve the body of `fillOrder`/`_fillCrossChain`/`_fillSameChain` in the Tron contract before the session ended, so I could not verify whether a separate reentrancy issue (the Tron file has no `nonReentrant`/`ReentrancyGuard` import, unlike the mainline EVM contract) is independently exploitable — that avenue remains unconfirmed and is not included in this report.
