# No Vulnerability found for this question

The proposed attack does not work because the `ViewFunction`'s declared parameter types are never attacker-controlled — they come from the on-chain module's own function signature, not from the request.

**Trace of the path:**

1. `ViewFunctionRequest::Bcs` deserializes a `ViewFunction { module, function, ty_args, args }` where `args: Vec<Vec<u8>>` is opaque bytes per argument, matched only by position, not by an attacker-declared type tag. [1](#0-0) 

2. `execute_view_function_in_vm` loads the actual function definition from the module (`loader.load_instantiated_function`) and derives `func.param_tys()` from that loaded, on-chain function — this is fixed code, not something the caller can substitute. [2](#0-1) 

3. `validate_view_function` / `construct_args` then walks `func.param_tys()` zipped with the supplied byte arrays and validates length equality up front (`types.len() != args.len()` → error), and for compound types recursively parses/validates bytes against the real declared type. [3](#0-2) 

4. During actual execution, `deserialize_arg` computes the `MoveTypeLayout` from the real parameter `Type` (again sourced from the loaded module, not attacker input) and calls `ValueSerDeContext::deserialize(arg.borrow(), &layout)`, which returns `None`/error on any byte-layout mismatch (e.g., 8-byte u64 payload fed against a 32-byte `address` layout), producing `FAILED_TO_DESERIALIZE_ARGUMENT` rather than silently reinterpreting the bytes as the wrong type. [4](#0-3) 

Because the parameter type used for deserialization is always the function's actual, immutable on-chain signature — never something the caller can redeclare via the BCS view request — there is no way to make the VM "interpret raw bytes as a different-typed `MoveValue`". A byte layout crafted for `u64` and pointed at a function expecting `address` will fail BCS deserialization and the whole view call errors out; it cannot corrupt a returned balance/owner value. This matches exactly the outcome the submitter's own proof idea predicts (VM rejects it), so the underlying premise of "silently returning a wrong value" is incorrect, and no custody boundary (deposit/withdraw/transfer/split/merge/burn accounting) is crossed.

// Construct arguments. Walk through the arguments and according to the signature
// construct arguments that require so.
// TODO: This needs a more solid story and a tighter integration with the VM.
pub(crate) fn construct_args(
    session: &mut SessionExt<impl AptosMoveResolver>,
    loader: &impl Loader,
    gas_meter: &mut impl GasMeter,
    traversal_context: &mut TraversalContext,
    types: &[Type],
    args: Vec<Vec<u8>>,
    ty_args: &[Type],
    allowed_structs: &ConstructorMap,
    is_view: bool,
    pack_fn_cache: &mut PackFunctionCache,
) -> Result<Vec<Vec<u8>>, VMStatus> {
    // Perhaps in a future we should do proper gas metering here
    let mut res_args = vec![];
    if types.len() != args.len() {
        return Err(invalid_signature());
    }

    let ty_builder = &loader.runtime_environment().vm_config().ty_builder;
    for (ty, arg) in types.iter().zip(args) {
        let subst_res = ty_builder.create_ty_with_subst(ty, ty_args);
        let ty = subst_res.map_err(|e| e.finish(Location::Undefined).into_vm_status())?;
        let arg = construct_arg(
            session,
            loader,
            gas_meter,
            traversal_context,
            &ty,
            allowed_structs,
            arg,
            is_view,
            pack_fn_cache,
        )?;
        res_args.push(arg);
    }
    Ok(res_args)
}

fn deserialize_arg(
    function_value_extension: &impl FunctionValueExtension,
    layout_converter: &LayoutConverter<impl Loader>,
    gas_meter: &mut impl GasMeter,
    traversal_context: &mut TraversalContext,
    ty: &Type,
    arg: impl Borrow<[u8]>,
) -> PartialVMResult<Value> {
    let deserialization_error = || -> PartialVMError {
        PartialVMError::new(StatusCode::FAILED_TO_DESERIALIZE_ARGUMENT)
            .with_message("[VM] failed to deserialize argument".to_string())
    };

    // Make sure we do not construct values which might have delayed fields inside. This should be
    // guaranteed by transaction argument validation but because it does not use layouts we better
    // double-check here.
    let layout = layout_converter
        .type_to_type_layout_with_delayed_fields(gas_meter, traversal_context, ty)
        .map_err(|err| {
            if layout_converter.is_lazy_loading_enabled() {
                err
            } else {
                // Note: for backwards compatibility, the error code is remapped to this error. We
                // no longer should do it because layout construction may return useful errors such
                // as layout being too large, running out of gas, etc.
                PartialVMError::new(StatusCode::INVALID_PARAM_TYPE_FOR_DESERIALIZATION)
                    .with_message("[VM] failed to get layout from type".to_string())
            }
        })?
        .into_layout_when_has_no_delayed_fields()
        .ok_or_else(deserialization_error)?;

    let max_value_nest_depth = function_value_extension.max_value_nest_depth();
    ValueSerDeContext::new(max_value_nest_depth)
        .with_func_args_deserialization(function_value_extension)
        .deserialize(arg.borrow(), &layout)
        .ok_or_else(deserialization_error)
}
