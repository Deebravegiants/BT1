### Title
Missing shop domain validation on JWT `dest` claim allows the app's `client_secret` to be sent to an attacker-influenced host in `TokenExchange.exchange_token` - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` takes the shop hostname straight from the session token's `dest` claim and uses it, unvalidated, to build the HTTP request host that receives the app's `client_id`/`client_secret`. Every sibling OAuth entry point in this same gem (`RefreshToken`, `TokenExchange.migrate_to_expiring_token`, `Clients::Graphql::Storefront`) runs the shop value through `Utils::ShopValidator.sanitize!` before it is allowed to become a request host, but `exchange_token` does not.

### Finding Description
`JwtPayload#shop` simply strips the scheme off the `dest` claim with no further validation: [1](#0-0) 

The only cross-check performed on the token in `JwtPayload#initialize` is `aud == Context.api_key`; there is no check that `dest` is a trusted Shopify domain (`myshopify.com`, `myshopify.io`, `shopify.com`, `spin.dev`, `shop.dev`, as enumerated in `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`), and no check that `dest` matches `iss`.

`TokenExchange.exchange_token` then uses that unvalidated value directly: [2](#0-1) 

`dest_shop` becomes `shop_session.shop`, which `Clients::HttpClient#initialize` uses verbatim to build the request base URI that will carry the `client_secret` in the POST body: [3](#0-2) 

Compare this to `TokenExchange.migrate_to_expiring_token` in the very same file, which does sanitize the shop before using it as a request host: [4](#0-3) 

and to `Utils::ShopValidator.sanitize!`, which is the gem's designated boundary for "is this host allowed to receive our credentials": [5](#0-4) 

The broken binding is: **host that receives the `client_secret` == a trusted Shopify domain**. In `exchange_token`, the host is instead **whatever string appears in an unverified-format `dest` JWT claim**, which is never checked against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

### Impact Explanation
If `dest` is ever attacker-influenced (e.g., a session token minted for/relayed from a non-standard `dest` value, a future signing-key compromise, or any code path that feeds `JwtPayload` a token whose `dest` was not itself constrained to a myshopify-style domain by the caller), the gem will POST the app's `client_id` and `client_secret` to that host — SSRF carrying the app's `client_secret`, matching the High-impact category in this analysis.

### Likelihood Explanation
Likelihood is limited by the fact that `JWT.decode` requires a valid HMAC-SHA256 signature over `Context.api_secret_key` (or `old_api_secret_key`), so an outside attacker cannot forge an arbitrary `dest` in a token that will pass `JwtPayload.new` under normal circumstances. However, the vulnerability is a genuine root-cause gap in this gem's own validation layering (unlike `migrate_to_expiring_token`, `refresh_access_token`, and `Storefront.new`, which all defensively call `ShopValidator.sanitize!`/reject non-Shopify hosts even though their inputs are also "supposed to" already be trusted). This inconsistency means `exchange_token` has no defense-in-depth if the `dest` claim is ever wrong-shaped or the token issuance path is compromised, whereas the rest of the library enforces the shop-domain allow-list as a second line of defense before spending the `client_secret` on a network request.

### Recommendation
In `TokenExchange.exchange_token`, run `dest_shop` through `Utils::ShopValidator.sanitize!` (as `migrate_to_expiring_token` already does) before constructing `shop_session`/`HttpClient`. Additionally, `JwtPayload` should validate that `dest` is a well-formed, trusted Shopify host and that `iss` corresponds to `"https://#{dest}/admin"` (or `/checkouts`), closing the gap between "signature verified" and "claims bound to a trusted domain."

### Proof of Concept
1. `lib/shopify_api/auth/jwt_payload.rb:33-44` decodes the token and only asserts `aud == Context.api_key`; `dest`/`iss` are stored as-is with no domain allow-list check.
2. `lib/shopify_api/auth/token_exchange.rb:40-51` sets `dest_shop = jwt_payload.shop` and builds `shop_session = Session.new(shop: dest_shop)` with no call to `Utils::ShopValidator.sanitize!` (contrast with `token_exchange.rb:103`, which does call it in the sibling method).
3. `lib/shopify_api/clients/http_client.rb:16-19` builds `@base_uri = "https://#{session.shop}"` from that same unvalidated value and subsequently POSTs `client_id`/`client_secret` (`token_exchange.rb:52-59`) to `"#{@base_uri}/admin/oauth/access_token"`.
4. If any code path (custom middleware, proxy, future refactor, or an issuance bug) allows `dest` to be a non-Shopify-domain string while the JWT signature still validates, the app's `client_secret` is sent to that attacker-controlled host — without the `ShopValidator` check that protects every comparable code path in this gem.
