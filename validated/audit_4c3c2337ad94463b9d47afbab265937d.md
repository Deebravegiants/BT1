This confirms the vulnerability structure. `WebhookMetadata.shop` (which the host application uses as the tenant identifier per this gem's own documented `WebhookHandler` interface) is populated directly from an unauthenticated HTTP header, while the HMAC verification performed by `Utils::HmacValidator.validate` only covers the raw body.

### Title
Webhook `shop` tenant identifier is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (and `topic`, `api_version`, `webhook_id`) attributes exclusively from HTTP headers, while `to_signable_string` — the data actually covered by the HMAC signature — returns only the raw request body. `Registry.process` validates the HMAC and then unconditionally trusts `request.shop` as the tenant identifier passed to the app's `WebhookHandler`. Because the same `api_secret_key` is used to sign webhooks for every shop installed on the app, a merchant who legitimately installs the app on their own store can capture one of their own genuine `(raw_body, hmac)` pairs and replay it to the app's public webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. The HMAC check still passes (it only verifies the body), so the forged shop attribution reaches the handler as if it were authentic.

### Finding Description
- `lib/shopify_api/webhooks/request.rb#L20-L38`: `shop`, `topic`, `api_version`, and `webhook_id` come from `shopify_header(...)`, plain HTTP headers under the caller's control. `to_signable_string` returns only `@raw_body`. [1](#0-0) 
- `lib/shopify_api/utils/hmac_validator.rb#L26-L31`: `validate_signature` computes the HMAC over `verifiable_query.to_signable_string` (the body) and compares it to the `hmac` header — it never incorporates `shop`, `topic`, or `webhook_id`. [2](#0-1) 
- `lib/shopify_api/webhooks/registry.rb#L188-L200`: `process` gates only on `Utils::HmacValidator.validate(request)`, then builds `WebhookMetadata.new(... shop: request.shop ...)` from the unauthenticated header and hands it to the app's handler. [3](#0-2) 
- `lib/shopify_api/webhooks/webhook_handler.rb#L6-L23`: `WebhookMetadata.shop` is the gem's own documented interface field host applications are expected to rely on as the tenant identifier for the event. [4](#0-3) 

The identity binding that is broken: `shop header value == shop the body/HMAC was actually generated for`. Before the attack, an honest webhook has `hmac = HMAC(secret, body_for_shop_A)` and `shop header = shop_A`, so they are consistent. After the attacker's replay, `hmac` is unchanged (`HMAC(secret, body_for_shop_A)`, still valid because the secret is shared across all shops for the same app) but `shop header = shop_B`. `HmacValidator.validate` only checks that `hmac` matches `body`, so it returns `true` for both cases — the shop field is never part of the equality it verifies.

### Impact Explanation
This enables cross-tenant confusion: an app's webhook handler (built against this gem's documented `WebhookHandler`/`WebhookMetadata` contract) will process attacker-supplied body data as if it originated from an arbitrary victim shop of the attacker's choosing. Depending on the handler's logic (e.g., updating per-shop billing/plan state, order records, `app/uninstalled` bookkeeping, GDPR mandatory topics), this can corrupt or leak another tenant's data path, satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Any user who can install the app on their own shop (an ordinary, unprivileged action available to any merchant/developer) can capture one legitimate webhook delivery for their own shop and immediately reuse it against the app's public webhook endpoint with a modified `shop-domain` header, requiring no access token, no `api_secret_key`, and no privileged account — just a normal HTTP replay.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) values in the HMAC-covered signable content, or otherwise cryptographically bind the header-derived `shop` to the signed body (e.g., require it to be embedded in the body itself, as Shopify does for the resource payload) before `Registry.process` trusts `request.shop` for dispatch to handlers.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook: body `B`, header `x-shopify-shop-domain: attacker.myshopify.com`, header `x-shopify-hmac-sha256: H` where `H = Base64(HMAC-SHA256(secret, B))`.
2. Attacker POSTs to the app's webhook endpoint with the same body `B` and same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which computes `HMAC(secret, B)` and compares to `H` — matches, since `B` is unchanged. [5](#0-4) 
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)`, even though `B` was never generated for `victim.myshopify.com`.
