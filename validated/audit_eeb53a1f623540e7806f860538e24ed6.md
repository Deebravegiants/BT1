### Title
Uncontrolled Resource Consumption via Unbounded/Uncharged `GetRequest` Key Batches - (File: `modules/pallets/state-coprocessor/src/impls.rs`)

### Summary
`GetRequest.keys` is an unbounded `Vec<Vec<u8>>` [1](#0-0) , and dispatching a GET request on an EVM source chain via `EvmHost.dispatch(DispatchGet)` has no cap on `keys.length` and no protocol-level per-key fee — the relayer `fee` field is fully optional and can be `0` for self-relaying [2](#0-1) . When the request lands on Hyperbridge, `pallet-state-coprocessor::handle_get_requests` performs full storage-proof verification (`verify_state_proof`) for *every key in every request* before any bandwidth/fee accounting occurs against that request [3](#0-2) . The bandwidth gate (`BandwidthGate::try_consume`) is only charged *after* the (potentially very expensive) proof verification completes, per response, not per request [4](#0-3) .

### Finding Description
The `IHandlerV2`/pallet-ismp message-delivery path is explicitly permissionless — "All handler methods are permissionless - anyone can call them to relay messages" [5](#0-4) , and on the Substrate side `handle_unsigned` "permits anyone execute ISMP messages for free, provided they have valid proofs" [6](#0-5) .

An attacker (any EVM contract) dispatches a `GetRequest` with an arbitrarily large `keys` array via `EvmHost.dispatch(DispatchGet)`. The struct places no bound on `keys.length`, and if the attacker sets `fee: 0` (self-relay), the request costs only source-chain gas to create [2](#0-1) , and the documented `bandwidth` model explicitly notes that per-byte protocol fees on dispatch were removed entirely from `EvmHost` [7](#0-6) .

When Hyperbridge's `pallet-state-coprocessor::handle_get_requests` processes the corresponding `GetRequestsWithProof` (submitted by a relayer/prover), it loops over every `GetRequest` and calls `dest_state_machine.verify_state_proof(&host, req.keys.clone(), ...)` — a CPU/memory-intensive trie-verification routine that scales with the number of keys — for the full request *before* the `BandwidthGate::try_consume` check for that response is ever reached [8](#0-7) . The bandwidth documentation itself confirms the gate is only "consulted on every non-purchase **POST** request" [9](#0-8)  — GET requests/responses are metered only after the expensive verification work is already done, and the metering happens per-response after the fact, not as an admission-control gate on key count before verification begins.

Additionally, off-chain relayer/prover infrastructure must fetch a storage proof for every key (e.g. via `eth_getProof`), which the codebase itself acknowledges is expensive enough to require rate-limited batching (`MAX_PROOF_KEYS_PER_BATCH = 5`, with delays between batches) purely to avoid provider rate limits [10](#0-9)  — a single request with thousands of keys forces relayers/provers to spend substantial time and RPC bandwidth fetching proofs for a request that may ultimately be self-relayed for zero fee.

This mirrors the OpenMeetings NetTest bug class (CVE-2021-27576): an unauthenticated/near-free operation whose resource cost is controlled entirely by the caller and is not bounded or paid for up front, allowing bandwidth/CPU exhaustion of the service (here, Hyperbridge's coprocessor pallet and the relayer network) with an unprivileged single transaction.

### Impact Explanation
An attacker can repeatedly dispatch `GetRequest`s with maximal `keys` arrays and `fee: 0`, forcing:
- Hyperbridge validator/collator nodes to burn CPU cycles in `verify_state_proof` per submitted batch before any bandwidth check rejects the work, since the check only fires per-response after verification completes.
- Relayers/provers to consume real bandwidth and third-party RPC quota fetching large storage proofs for requests that pay no fee, degrading relay service for legitimate requests and potentially exhausting rate-limited RPC allowances (as evidenced by the explicit rate-limit mitigation code for Pharos).

This is a resource-exhaustion / availability risk against the Hyperbridge relay path — not a fund-theft bug — but it is a route-availability degradation ("a route unable to deliver messages") reachable from a single unprivileged dispatch.

### Likelihood Explanation
Likelihood is constrained by two factors I could not fully verify within the indexed code: (1) whether block/extrinsic weight limits or `handle_unsigned`'s `#[pallet::weight(weight())]` calculation already caps the effective batch size before inclusion (the weight function itself was not located in the indexed content), and (2) whether EVM calldata gas costs for very large `keys[]` arrays already impose a practical economic bound on the attacker's own chain. Because of these unverified mitigating factors, I present this as a plausible but not fully confirmed uncontrolled-resource-consumption analog rather than a certain exploit — a background engineering review of `weight()` in `modules/pallets/ismp/src/lib.rs` and the destination-chain gas cost of a large `keys[]` calldata payload is required to confirm whether any effective bound already exists.

### Recommendation
- Charge (or fail) the bandwidth gate — or an equivalent key-count/byte cap — on the request side, before `verify_state_proof` runs, so the cost of an oversized `keys` array is assessed prior to the expensive computation, mirroring how `on_accept` gates `PostRequest` before dispatch.
- Enforce an explicit, bounded maximum on `GetRequest.keys.len()` (e.g. a `MaxGetKeys` runtime constant) at both `EvmHost.dispatch(DispatchGet)` and `pallet-state-coprocessor::handle_get_requests`, rejecting any request/response batch that exceeds it.
- Ensure a non-zero minimum fee (or a bandwidth-gate pre-check keyed off `keys.len()`) is required for self-relayed GET requests so the protocol cannot be forced to do unbounded off-chain/on-chain verification work for free.

### Proof of Concept
1. Attacker deploys/calls a contract that invokes `IDispatcher(host).dispatch(DispatchGet)` with `keys` containing, e.g., 50,000 arbitrary 52-byte entries and `fee: 0` [2](#0-1) .
2. Attacker (or any relayer) submits the resulting `GetRequestsWithProof` to Hyperbridge (`handle_unsigned` / `handle`), including a valid membership proof for the request and a state proof for the destination values.
3. `handle_get_requests` iterates `requests` and calls `verify_state_proof` over all 50,000 keys before the `BandwidthGate::try_consume` check is reached for that response [8](#0-7) , consuming disproportionate node CPU/time for a request that ultimately can be rejected or paid for at zero cost.
4. Repeating this from multiple free/cheap source-chain accounts degrades Hyperbridge coprocessor throughput and relayer/prover RPC bandwidth, analogous to the NetTest-driven bandwidth exhaustion in the reference advisory.

            path[0] = IUniswapV2Router02(uniswapV2).WETH();

            IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(

            IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), get.fee);
        }

        uint64 timeoutTimestamp = get.timeout == 0 ? 0 : uint64(block.timestamp) + uint64(get.timeout);
        GetRequest memory request = GetRequest({
            source: host(),
            dest: get.dest,
            nonce: uint64(_nextNonce()),
            from: abi.encodePacked(_msgSender()),
            timeoutTimestamp: timeoutTimestamp,
            keys: get.keys,
            height: get.height,
            context: get.context
        });

        commitment = request.hash();
        _requestCommitments[commitment] = FeeMetadata({sender: _msgSender(), fee: get.fee});

            from: request.from,

            height: request.height,
            context: request.context,
            timeoutTimestamp: request.timeoutTimestamp,
            fee: get.fee

# Bandwidth

Hyperbridge meters outbound traffic per `(source chain, app)`. Instead of paying a protocol fee on every dispatch, an app pre-pays for a tier and earns a byte allowance that drains as it sends messages. The allowance is enforced by the **bandwidth gate** on Hyperbridge — a hook the ISMP router consults on every inbound request from a source chain. When the gate is empty, the message is rejected.
