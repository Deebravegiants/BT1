### Title
Webhook shop identity is trusted from an unauthenticated header while the HMAC only signs the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, but derives the `shop` (and `topic`) attributes from HTTP headers that are never included in that signed content. `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` as the tenant identity for dispatching webhook data to the app's handler once the body HMAC validates, even though the header carrying that shop identity was never bound to the signature.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

Meanwhile `Request#shop` and `Request#topic` are read straight from HTTP headers, independent of the signed bytes: [2](#0-1) 

`Utils::HmacValidator.validate` only recomputes and compares the HMAC over `to_signable_string` (i.e. the body), and says nothing about the headers: [3](#0-2) 

`Registry.process` then unconditionally trusts `request.shop` as the tenant identity once that body-only HMAC passes, and hands it to the host application's handler: [4](#0-3) 

The identity binding that should hold is: `shop-domain header == shop bound inside the HMAC-signed payload`. In this gem it is instead: `shop-domain header != anything covered by the signature`. The library's own documentation reinforces the false guarantee, stating that calling `Registry.process` "will verify the request did indeed come from Shopify," without qualifying that the shop/topic headers are unauthenticated: [5](#0-4) 

### Impact Explanation
Because `api_secret_key` is shared across all shops that install a given app, any merchant/attacker who installs the app on their own store legitimately receives real, correctly-signed webhook deliveries (body + `X-Shopify-Hmac-Sha256`) from Shopify. Since the signature never covers the `X-Shopify-Shop-Domain` (or `X-Shopify-Topic`) header, the attacker can capture one legitimate `(body, hmac)` pair and replay it directly to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop. `HmacValidator.validate` still passes (body/HMAC pair is untouched), and `Registry.process` forwards attacker-controlled `shop` (and optionally `topic`) straight to `WebhookMetadata`/the app's handler as if it originated from the victim shop. Host applications typically use `data.shop` to look up per-tenant sessions/access tokens or to write data scoped to "the shop," so this enables cross-tenant data injection/confusion in the host app, satisfying the Critical "cross-tenant access" impact category — achieved purely through the gem's own `Webhooks::Request`/`Registry` code, without needing the app's `client_secret`/`api_secret_key` or any access token.

### Likelihood Explanation
Any unprivileged internet user who can install the target app on a shop they control (a normal, unprivileged flow for public apps) can obtain a validly-HMAC-signed webhook body/signature pair for their own store. Forging the replay only requires sending a raw HTTP POST with the captured body/HMAC and a modified shop header directly to the app's public webhook route — no interception of Shopify's own traffic or secret material is required.

### Recommendation
Bind the shop (and topic) identity into the data covered by the HMAC verification step, e.g. by requiring the webhook handler/registry to cross-check `request.shop` against an expected/registered shop for that installation before trusting it, or by re-deriving shop identity only from data that Shopify actually signs (Shopify does not sign headers, so the gem should document/enforce that host apps must independently confirm the shop exists as an installed/authorized tenant, e.g., by checking it against a stored session, before acting on `data.shop`). At minimum, update `docs/usage/webhooks.md` to explicitly state that only the body is authenticated by HMAC, and that `shop`/`topic` headers are unauthenticated and must be independently validated against known installed shops before being trusted as a tenant key.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a normal, unprivileged action).
2. Shopify sends a legitimate webhook to the app's registered endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the app's `api_secret_key`) and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures `(B, H)` and replays it directly to the same public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim-shop.myshopify.com", hmac-sha256: H})` is constructed; `to_signable_string` still returns `B`.
5. `Utils::HmacValidator.validate(request)` succeeds because it only re-checks `B` against `H`.
6. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host app to process attacker-supplied data as if it belonged to `victim-shop`.

          received_signature = verifiable_query.hmac
