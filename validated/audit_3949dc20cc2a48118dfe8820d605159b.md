### Title
Fee-on-transfer ERC20 tokens cause escrow over-crediting and cross-order fund drain in Tron IntentGatewayV2 - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron-specific `IntentGatewayV2.placeOrder()` computes escrowed amounts and the order commitment directly from the user-specified `order.inputs[i].amount`, then calls `safeTransferFrom` for that same amount without verifying how much the contract actually received. For any ERC20 with a fee-on-transfer (or otherwise non-1:1 transfer semantics), the gateway credits `_orders[commitment][token]` with more than the tokens it actually holds.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `placeOrder()` computes `reducedInputs` (post protocol-fee amounts used both for the EIP-712/keccak commitment and for escrow accounting) purely from `order.inputs[i].amount`: [1](#0-0) 

In the non-predispatch branch, tokens are pulled with `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)`, and the escrow ledger is incremented by `reducedInputs[i].amount` — both values derived from the *requested* amount, never from the balance actually received: [2](#0-1) 

This is exactly the bug class described in the external report: the pool/escrow "amount" tracked by the contract diverges from the actual token balance held, because a fee-on-transfer token silently deducts value during `transferFrom`.

Contrast this with the canonical EVM `IntentGatewayV2.sol`, which explicitly measures `balanceOf` before and after `safeTransferFrom` and mutates `order.inputs[i].amount` to the actual received amount before computing fees/commitment: [3](#0-2) 

The Tron deployment lacks this balance-before/after reconciliation entirely for the direct-transfer path.

The over-credited escrow entry is later paid out verbatim in `withdraw()`, which transfers `body.tokens[i].amount` to the beneficiary and only decrements internal accounting, with no check that the contract's real balance supports the transfer: [4](#0-3) 

Since all escrows for a given token share the same contract-wide ERC20 balance, an over-credited entry for one order can be paid out using tokens that were actually deposited by other, unrelated orders — i.e. later withdrawals can drain funds belonging to other users, or fail/revert leaving legitimate escrows permanently unable to be redeemed once the shared balance is exhausted.

### Impact Explanation
This qualifies as concrete loss/freezing of user funds: solvers or order owners redeeming escrow (`withdraw()` via `onAccept` RedeemEscrow/RefundEscrow or same-chain `cancelOrder`) can either (a) drain another user's genuinely-deposited tokens to cover the phantom balance from a fee-on-transfer order, or (b) find that once the shared pool of a token is exhausted, subsequent legitimate redemptions revert with `TransferFailed`, permanently freezing those users' funds since there is no reconciliation/repair mechanism. This directly matches the "concrete theft or permanent freezing of funds" bar.

### Likelihood Explanation
Likelihood is realistic for any deployment of this Tron gateway configured to accept an ERC20 with transfer fees (common on Tron, e.g. TRC20 tokens with configurable fees, similar to USDT's fee mechanism referenced in the original report) or any deflationary/rebasing token. No privileged role is required — any unprivileged user placing an order with such a token triggers the miscalculation, and it compounds every time such a token is used, since escrow bookkeeping for that token permanently overstates the real balance.

### Recommendation
Mirror the fix already present in the canonical EVM `IntentGatewayV2.sol`: measure `IERC20(token).balanceOf(address(this))` immediately before and after `safeTransferFrom` in the non-predispatch escrow path of the Tron contract, and use the actual delta (not the requested `order.inputs[i].amount`) both for the commitment hash and for crediting `_orders[commitment][token]`. Apply the same balance-based reconciliation pattern used in the predispatch branch (`balancesBefore` snapshot) consistently to the direct-transfer branch.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` and register a fee-on-transfer ERC20 (e.g. 1% fee) as a valid input token.
2. User A places `orderA` with `inputs[0].amount = 1000` of the fee token; gateway actually receives only 990, but `_orders[commitmentA][token]` is credited with `1000` (or `1000 - protocolFee`).
3. User B places `orderB` with a normal (non-fee) token or the same fee token, correctly depositing its full amount into the shared contract balance.
4. When `orderA` is redeemed via `withdraw()`, the contract attempts to transfer the full credited amount (`1000`-based) to the beneficiary; since actual balance for that token is less than the sum of all outstanding escrow entries, either: the transfer succeeds using tokens actually belonging to `orderB`'s deposit (fund theft), or later `orderB`'s legitimate `withdraw()` call reverts with `TransferFailed()` because insufficient balance remains (fund freeze). This mirrors the referenced Allo.sol `fundPool`/`distribute` PoC, where `poolAmount` diverges from actual balance and either blocks distribution or enables balance confusion across pools.
