## Title
Permissionless `Initialize2` allows front-running/DoS of AMM pool creation for a given OpenBook market with minimal token amounts - (File: `program/src/processor.rs`)

## Summary
`process_initialize2` (the handler for `AmmInstruction::Initialize2`) can be invoked by any signer, with any arbitrary `market_info` account and attacker-chosen `coin_mint`/`pc_mint`, as long as the deterministic PDAs derived from that market seed are still unowned and the attacker funds the vaults with a minimal amount of each token. This lets an attacker permanently claim the AMM PDA set tied to a specific market before the legitimate project/team does, blocking them from ever creating the canonical pool for that market — directly analogous to the reported `createRJLaunchEvent()` front-running griefing vector.

## Finding Description
`Initialize2`/`process_initialize2` derives all pool-related accounts (`amm_info`, `amm_target_orders`, `amm_lp_mint`, `amm_coin_vault`, `amm_pc_vault`) as PDAs seeded by the `market_info` pubkey plus fixed seed constants, via `get_associated_address_and_bump_seed`. [1](#0-0) 

The instruction documentation and code comments explicitly note that `market_info` is "Just a seed for AMM account. Can be any account," and that the market/market-program accounts are not otherwise validated against the token mints being initialized. [2](#0-1) [3](#0-2) 

There is no owner/admin gating in `process_initialize2` beyond `user_wallet_info.is_signer` — any signer can call it as long as the `amm_config` PDA check passes and the mints differ. [4](#0-3) 

The only economic barrier to creating a pool is that both vaults must have a nonzero balance, and the resulting `sqrt(x*y)` liquidity must exceed `10^lp_decimals` (otherwise `InitLpAmountTooLess`), which is a much smaller bar than a genuine pool launch: [5](#0-4) [6](#0-5) [7](#0-6) 

Because the associated-account creation helpers (`generate_amm_associated_account`, `generate_amm_associated_spl_token`, `generate_amm_associated_spl_mint`) return `AmmError::RepeatCreateAmm` once the derived PDA is no longer owned by the system program, whichever caller wins the race permanently claims that market's PDA set: [8](#0-7) [9](#0-8) 

This means any unprivileged user can submit an `Initialize2` transaction for a target `market_info` pubkey with self-chosen mints and trivial funding amounts, permanently occupying the AMM/target-orders/lp-mint/vault PDAs tied to that market and irreversibly blocking the legitimate project or Raydium itself from ever creating the intended AMM pool for that specific market — the same "create with minimal funds and block the rightful creator" bug class as the referenced `createRJLaunchEvent()` report.

## Impact Explanation
This is a griefing/denial-of-service vector rather than direct fund theft: no user/LP funds are held by the blocked (never-created) pool. The attacker permanently prevents the legitimate pool for a given OpenBook market from being created via this program, forcing the project to use a different market or find another workaround. This mirrors the accepted severity classification of the referenced report (Medium), which was also a pure availability/griefing issue rather than direct fund loss, and it directly maps onto the explicitly in-scope `Initialize2` code path and PDA/account-binding checks.

## Likelihood Explanation
Likelihood is high: the attack requires only a single transaction with a known target `market_info` pubkey, a minimal amount of two SPL tokens (enough for `sqrt(x*y) > 10^lp_decimals`), and standard fee-payer capability — no privileged signer, leaked key, or special build is needed. Any bot watching for pending Initialize2/pool-launch activity for a given market can front-run it.

## Recommendation
Restrict `Initialize2` to only be callable by a designated privileged authority (e.g., `config_feature::amm_owner`) or require an explicit allow-list/whitelist check tying a specific `market_info`/mint pair to an authorized creator before permitting PDA claiming, similar to the recommendation in the referenced report of gating pool/launch creation behind an owner check.

## Proof of Concept
1. Attacker observes (off-chain) that Project X intends to launch an AMM pool for OpenBook market `M` with mints `coin`/`pc`.
2. Attacker computes the PDAs `amm_info`, `amm_target_orders`, `amm_lp_mint`, `amm_coin_vault`, `amm_pc_vault` from seed `M` using `get_associated_address_and_bump_seed`.
3. Attacker submits `Initialize2` with `market_info = M`, `amm_coin_mint`/`amm_pc_mint` set to arbitrary tokens they control, funding the coin/pc token accounts with just enough of each token to pass the `amount == 0` checks and exceed `10^lp_decimals` liquidity threshold.
4. `process_initialize2` succeeds (no owner/authority check blocks it), claiming all PDAs seeded by `M`. [10](#0-9) 
5. When Project X later attempts `Initialize2` for the same market `M` with their real mints, the associated-account creation helpers detect the PDAs are already owned by the program and return `AmmError::RepeatCreateAmm`, permanently blocking the legitimate pool creation for market `M`. [9](#0-8)
