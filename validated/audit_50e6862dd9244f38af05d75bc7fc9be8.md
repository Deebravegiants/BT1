### Title
Webhook shop/topic/api-version/webhook-id headers are trusted by the handler dispatch without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then dispatches to the app's handler using the `shop`, `topic`, `api_version`, and `webhook_id` values taken directly from HTTP headers, none of which are part of the signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `hmac`, `topic`, `shop`, `api_version`, and `webhook_id` accessors are all read directly and unauthenticatedly from HTTP headers with no relation to the signed content: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, via `Utils::HmacValidator.validate(request)`, which computes the signature over `request.to_signable_string` (i.e. the body): [3](#0-2) [4](#0-3) 

After this check passes, `request.shop`, `request.topic`, `request.api_version`, and `request.webhook_id` — none of which were part of the signed data — are handed to the app's handler as trusted `WebhookMetadata`: [5](#0-4) 

The identity binding that should hold is: `shop authenticated by the HMAC == shop passed to the handler`. In this implementation, the HMAC only authenticates the byte content of the body; the `shop` (and `topic`/`webhook_id`/`api_version`) fields are asserted by the caller via headers and never cross-checked against anything in the signed payload. Because the same `api_secret_key` is shared across every shop that has installed a given app, any tenant that can legitimately trigger one authentic webhook delivery for their own shop (e.g., by placing a test order to trigger `orders/create`) possesses a validly-signed `(raw_body, hmac)` pair. That attacker can replay the identical body/HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header to name a different shop. `HmacValidator.validate` still returns `true` (only the body is checked), and `Registry.process` dispatches to the handler tagged with the attacker-chosen `shop`, causing the host app to process another tenant's webhook data under the wrong tenant identity — a shop-authentication/session-key binding break, matching the "field acted on but not covered by the HMAC" and "shop authenticated vs. shop used as session key" analog classes.

### Impact Explanation
An app that keys any subsequent behavior off `WebhookMetadata#shop` (session lookup, per-tenant record updates, redaction/GDPR routing, billing state changes, etc.) can be made to act on the wrong tenant by an attacker who only controls their own shop's genuine webhook traffic, with no access to the `api_secret_key` or another merchant's credentials. This is a cross-tenant confusion/cross-tenant access primitive purely through this gem's own webhook-authentication code path.

### Likelihood Explanation
Any merchant who has installed the app (an "unprivileged internet user" relative to other tenants) can trigger at least one real webhook delivery for their own store and capture the valid `(body, hmac)` pair, then replay it to the app's public webhook endpoint with a forged `shop-domain` header. No secret material, TLS interception, or social engineering is required — only the ability to intercept/replay their own outbound-from-Shopify HTTP request, which is trivial for anyone controlling a test shop.

### Recommendation
Bind the shop (and ideally topic/webhook id) identity into what is authenticated, e.g.:
- Include `shop`, `topic`, and `webhook_id` in the signed/verified string (or otherwise cryptographically bind them to the payload) instead of trusting raw headers, or
- Require the host application to independently verify that `request.shop` matches a shop for which the delivered `webhook_id`/topic was actually registered before invoking the handler, rejecting mismatches, and document this requirement/enforce it inside `Registry.process` itself rather than leaving it entirely to callers.

### Proof of Concept
1. App is installed on `victim-shop.myshopify.com` and `attacker-shop.myshopify.com`, both under the same Shopify app (shared `api_secret_key`).
2. Attacker triggers a real webhook for their own shop (e.g., creates an order to fire `orders/create`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sent.
3. Attacker resends the identical body and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` whose `to_signable_string` is unchanged (still equals the original raw body), so `Utils::HmacValidator.validate` succeeds.
5. `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: attacker's order payload, ...)`, and the app processes attacker-controlled data under the victim's shop identity.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
