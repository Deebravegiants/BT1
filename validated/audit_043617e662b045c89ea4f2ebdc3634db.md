### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity by computing an HMAC over the raw request body only, while the `shop` (tenant) identity used by the handler is read from the `shopify-shop-domain` header, which is never included in the signed material. Any HTTP request whose body+HMAC pair is valid for *some* shop will also validate successfully for *any other* `shop-domain` header value, because that header is not bound to the signature.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop` reads the tenant identity from a separate, unsigned header: [2](#0-1) 

`Utils::HmacValidator.validate` only checks the HMAC of `to_signable_string` (i.e., the raw body) against the secret — it never incorporates `shop`, `topic`, or `webhook_id`: [3](#0-2) 

`Webhooks::Registry.process` validates only that HMAC, then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The broken identity binding, stated as an equality that should hold but doesn't:
`shop_bound_by_hmac == shop_used_by_handler` is **false** — the signature only binds the body bytes, not the `shop-domain` header that the handler treats as the authoritative tenant for the event.

### Impact Explanation
Because `shop` is not part of the signed payload, a party who can obtain any one valid `(raw_body, hmac)` pair — trivially available to an unprivileged attacker who installs the app on their own store and triggers a webhook event for themselves (Shopify will deliver a correctly HMAC-signed request using the app's real secret to that installer) — can replay that exact body and HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `Registry.process` will still validate the HMAC (it only checks the body) and will hand the handler a `WebhookMetadata` claiming the data originated from the victim shop. Any host application that uses `shop` from `WebhookMetadata` to look up/act on a specific merchant's records (the intended and documented usage) can be induced to apply attacker-controlled data under another tenant's identity — a cross-tenant data integrity/spoofing issue.

### Likelihood Explanation
This requires no leaked or privileged credentials — an attacker only needs to be a legitimate, if unprivileged, installer of the app (achievable by any internet user for public apps) to obtain one valid signed body/HMAC pair, then modify a header before replaying it to the exposed webhook endpoint. The path is fully reachable through the gem's own public API (`Webhooks::Request.new` / `Webhooks::Registry.process`) with no reliance on host-app misconfiguration beyond following the documented handler pattern.

### Recommendation
Include the tenant identity (and ideally topic/webhook id) inside the HMAC-covered signable content, or otherwise cryptographically bind `shop-domain` to the signed body (e.g., require verification that the shop for which the signature was issued matches the header, using a per-shop or request-bound secret/nonce) before constructing `WebhookMetadata` in `Webhooks::Registry.process`.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers any webhook event (e.g., `orders/create`).
2. Shopify delivers a POST to the app's webhook endpoint with headers `shopify-shop-domain: attacker.myshopify.com`, `shopify-hmac-sha256: <valid HMAC over raw body>`, and the JSON body.
3. Attacker captures `raw_body` and the valid `hmac` header value.
4. Attacker sends a new POST to the same endpoint with the identical `raw_body`/`hmac`, but sets `shopify-shop-domain: victim.myshopify.com`.
5. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) passes because it only checks the body against the HMAC.
6. `Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) builds `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` from attacker-controlled body content, and the host app's handler processes attacker data as if it belongs to the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
