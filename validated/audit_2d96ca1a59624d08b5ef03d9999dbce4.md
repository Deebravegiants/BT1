### Title
Cross-Tenant Session Hijacking via Predictable, Unsigned Session Cookie Value - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
For non-embedded apps, `ShopifyAPI::Auth::Oauth.validate_auth_callback` sets the browser session cookie's `value` to the raw, unsigned `session.id`, and `ShopifyAPI::Auth::Session.from` derives that id deterministically as `"offline_#{shop}"` for offline sessions. `ShopifyAPI::Utils::SessionUtils.cookie_session_id` later trusts whatever value is present in that cookie and returns it as the session id used by the host app to look up the stored session (including the merchant's access token). Because the id contains no secret material and is a pure function of the publicly-known shop domain, any unprivileged user can set this cookie to `"offline_<victim-shop>.myshopify.com"` in their own browser and cause the host application to load and use the victim shop's stored session.

### Finding Description
In `lib/shopify_api/auth/session.rb`: [1](#0-0) 
the offline session id is computed as `"offline_#{shop}"` — a deterministic string derived solely from the shop domain, which is public information (every `*.myshopify.com` store name is discoverable/guessable).

In `lib/shopify_api/auth/oauth.rb`, after completing OAuth for a non-embedded app, this predictable id is placed directly into the cookie value that gets sent to the browser: [2](#0-1) 

`SessionCookie` is a plain value struct with no signature or MAC over its contents: [3](#0-2) 

The library's own documentation confirms host apps are only told to mark the cookie `secure`/`http_only` — not to sign or encrypt its value: [4](#0-3) 

Finally, `ShopifyAPI::Utils::SessionUtils.cookie_session_id` reads back whatever value is present in that cookie, with no validation that it was ever issued by the server or tied to any authenticated request: [5](#0-4) 

This breaks the identity binding: `session id returned to the host app for session lookup` should equal `an id previously issued by this app to *this* browser as a result of a real OAuth completion for *this* shop`. Instead it only equals `whatever bytes are present in a client-supplied cookie`, since nothing server-side pins those bytes to an actual authenticated session establishment. Because the offline id has no random/secret component, an attacker doesn't even need to observe a real cookie — they can compute it themselves for any target shop.

### Impact Explanation
An unprivileged internet user who knows (or guesses) a target merchant's `myshopify.com` domain can set their own browser's `shopify_app_session` cookie to `offline_<target-shop>.myshopify.com` and make requests to the app. If the host application follows this library's documented pattern (`SessionUtils.current_session_id` → `SessionRepository.load_session(id)`), the app will resolve and use the victim shop's stored `Session`, including its live Shopify Admin API `access_token`. This is cross-tenant access to another merchant's session/access token — a Critical impact per the classification (cross-tenant access / theft of merchant access token), achieved without any credential, TLS interception, or privileged account.

### Likelihood Explanation
Exploitation requires no secrets: `api_secret_key`/`client_secret` are never involved. The attacker needs only:
1. A target shop's domain (routinely visible — shop domains are not secret; they appear in app install URLs, storefront URLs, marketing, etc.).
2. The ability to set a cookie on their own browser targeting the app's non-embedded auth flow.

This is a low-effort, purely client-side attack against any host app built on this gem's documented non-embedded OAuth flow.

### Recommendation
- Never place the raw session id in a plaintext, unsigned cookie. Sign (HMAC) or encrypt the cookie value server-side, or store only an unguessable, high-entropy, randomly generated token in the cookie that is mapped server-side to the session id — not the session id itself.
- Make offline session ids non-deterministic, or bind them to a per-issuance secret/nonce, so they cannot be recomputed purely from public information (shop domain).
- Update `SessionUtils.cookie_session_id` / the documented integration pattern to require verification (e.g., signed cookie via Rack::Session or similar) rather than trusting the raw cookie value as an authoritative session identifier.

### Proof of Concept
1. App is a non-embedded Shopify app using `ShopifyAPI::Auth::Oauth.validate_auth_callback`, which sets `cookies[SessionCookie::SESSION_COOKIE_NAME] = session.id` (`"offline_victim-shop.myshopify.com"`) as instructed in `docs/usage/oauth.md`.
2. Attacker, in an unrelated browser session, manually sets:
   `shopify_app_session=offline_victim-shop.myshopify.com`
3. Attacker visits any authenticated route of the app.
4. Host app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)` → returns `cookie_session_id(cookies)` → `"offline_victim-shop.myshopify.com"` unchanged, since `cookie_session_id` performs no verification: [6](#0-5) 
5. Host app loads `victim-shop`'s stored `Session` (with real `access_token`) using this attacker-supplied id and performs Admin API calls on the attacker's behalf against the victim's shop.
