### Title
Unverified Operator QR-Code Bypass via Hardcoded `signup_extension()` Condition - (File: `src/plans/mod.rs`)

### Summary
`MasterPlan::verify_operator_qr_code` contains a hardcoded bypass condition analogous to the reported StakingContract flaw: instead of enforcing a configurable/validated authorization limit, it hardcodes a boolean shortcut (`qr_code.signup_extension() || self.operator_qr_code_override.is_some()`) that skips the backend operator-validation call entirely and substitutes fabricated, hardcoded location data.

### Finding Description
The function that is supposed to authenticate an operator QR-code against the backend does not always call the backend. If the scanned QR-code reports `signup_extension() == true`, the function short-circuits and returns success with fixed, hardcoded values instead of consulting `backend::operator_status::request`: [1](#0-0) 

```rust
async fn verify_operator_qr_code(
    &self,
    orb: &mut Orb,
    qr_code: &qr_scan::user::Data,
    qr_capture_start: Instant,
) -> Result<Option<(u64, backend::operator_status::LocationData)>> {
    if qr_code.signup_extension() || self.operator_qr_code_override.is_some() {
        return Ok(Some((0, backend::operator_status::LocationData {
            team_operating_country: "DEV".to_string(),
            session_coordinates: Coordinates { latitude: 0.0f64, longitude: 0.0f64 },
            stationary_location_coordinates: None,
        })));
    }
    ...
```

This mirrors the bug class in the report: rather than deriving the "is this operator/extension allowed" decision from a properly validated, upgrade-safe source (the backend, or a signed/verified flag), the code hardcodes a boolean condition (`signup_extension()`) that, if satisfied by attacker-controlled QR content, causes the system to treat *any* scanned "operator" QR-code as pre-authorized and injects hardcoded placeholder location/country data (`"DEV"`, `0.0, 0.0`) rather than real, backend-verified operator location data. Just as the StakingContract hardcodes operator index `0` and count `1`—silently disabling proper authorization enforcement—this code hardcodes a bypass path that silently disables backend operator verification whenever the QR content claims to be a "signup extension."

The `signup_extension()` flag and its associated `SignupExtensionConfig` are parsed directly from the content of the scanned QR code string (`qr_scan::user::Data::try_parse`), which is exactly the kind of attacker-influenced input this analog rule requires (QR/MECARD-style parsing feeding into an authorization decision).

### Impact Explanation
If an unprivileged individual can present a QR code to the Orb whose content is parsed such that `signup_extension()` evaluates to `true`, `verify_operator_qr_code` will:
1. Skip the backend call that verifies the operator's identity and legitimacy (`backend::operator_status::request`).
2. Accept the QR code as a valid operator immediately.
3. Attach fabricated `LocationData` (`team_operating_country: "DEV"`, coordinates `0.0/0.0`) to the signup session rather than the operator's real, verified location.

This allows an unauthorized/misattributed "operator" session to be established without legitimate backend approval, and it forges attestation data (fake operating country/location) that downstream systems (fraud checks, geofencing via `operation_country`/`operation_city`, debug reports) may rely upon as ground truth. This is consistent with the "attestation forgery" / "unauthorized signup" impact classes this analog scan accepts.

### Likelihood Explanation
Likelihood depends on whether `signup_extension()` can be set to `true` purely from unprivileged, attacker-supplied QR content, or whether it additionally requires a paired, cryptographically valid `signup_extension_config` (the operator QR parsing code at `src/plans/qr_scan/operator.rs:41-48` does filter: `d.signup_extension_config.is_some()` must also hold). This gate could not be fully confirmed from the indexed portions of `qr_scan/user.rs` (the file defining `signup_extension()` and `SignupExtensionConfig`) within the available tool budget — the field-level parsing logic and any cryptographic/backend binding for `signup_extension_config` were not fully retrieved. If `SignupExtensionConfig` is validated only client-side (e.g., simple string parsing of an embedded mode/parameter string, as suggested by `SignupMode::parse` reading a hex nibble from the QR text), likelihood is high, since any party able to present a QR code to the device could trigger the bypass. If it additionally requires a signed/backend-issued token, likelihood is lower.

### Recommendation
- Remove the hardcoded bypass; always call `backend::operator_status::request` to validate operator QR-codes, regardless of `signup_extension()`.
- If a legitimate "signup extension" test/internal-tooling path is required, gate it behind a compile-time feature flag (e.g., `internal-data-acquisition`, similar to other internal-only code paths already in the file) so it cannot be reached in production builds, and never substitute real location/country data with hardcoded placeholders in production.
- Ensure `signup_extension()` truth is derived from a backend-verified or cryptographically signed field, not solely from client-parsed QR string content.
- Apply the same remediation philosophy the external report recommends for `StakingContract`: replace hardcoded shortcut conditions with explicit, auditable, centrally-configured authorization checks rather than ad hoc boolean bypasses embedded in business logic.

### Proof of Concept
Full exploitation could not be conclusively demonstrated because the exact parsing/validation rules for `signup_extension()` / `SignupExtensionConfig` in `src/plans/qr_scan/user.rs` were not completely retrieved before the tool budget was exhausted. The reachable code path is:
1. Attacker presents a QR code to the Orb during the "Operator QR-code scanning" phase (`scan_operator_qr_code`, `src/plans/mod.rs:874-940`).
2. `qr_scan::operator::Data::try_parse` (`src/plans/qr_scan/operator.rs:40-48`) accepts it as `Data::Normal(user::Data)` if `user::Data::try_parse` succeeds and (`if d.signup_extension() { d.signup_extension_config.is_some() }`) holds.
3. `verify_operator_qr_code` (`src/plans/mod.rs:1543-1557`) is called with this data; because `qr_code.signup_extension()` is `true`, it returns success immediately with hardcoded `LocationData`, bypassing `backend::operator_status::request`.

To fully validate exploitability, a Devin session with repository access would need to inspect `src/plans/qr_scan/user.rs` in full to confirm exactly what QR-code content is required to set `signup_extension() == true` and whether `signup_extension_config` requires any signature/backend-issued value that an unprivileged party cannot forge.
