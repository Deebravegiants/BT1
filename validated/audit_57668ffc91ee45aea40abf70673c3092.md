Found a concrete analog: the webhook `shop` binding used to route/identify the tenant is **not covered by the HMAC**, so an attacker who has intercepted (or can forge) any single valid `X-Shopify-Hmac-Sha256` signature/body pair for their own shop can relabel the `X-Shopify-Shop-Domain` header to a victim shop, and the request will still validate.

### Title
Webhook shop-domain header not bound to HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body [1](#0-0) , while the tenant-identifying `shop` value is read directly from the unauthenticated `X-Shopify-Shop-Domain`/`Shopify-Shop-Domain` header [2](#0-1) . `Registry.process` validates the HMAC over the request and then dispatches the handler using `request.shop`, trusting it as the tenant identity without it ever being part of the signed payload [3](#0-2) .

### Finding Description
`HmacValidator.validate` computes the signature only from `to_signable_string`, which for webhooks is `@raw_body` [4](#0-3) [1](#0-0) . The `shop` accessor, however, is derived purely from an HTTP header that is never part of that HMAC-covered string [2](#0-1) . This breaks the intended binding: `HMAC-verified bytes == bytes used to identify the tenant`. In this gem's own dispatch path, `Registry.process` trusts `request.shop` post-HMAC-check to build `WebhookMetadata` passed to the app's `handler.handle` [3](#0-2) , so any consumer relying on this gem's validated `shop` value receives a shop identity that was never authenticated by the signature.

### Impact Explanation
Because the shop-domain header is unauthenticated, a party who has a legitimately-signed webhook payload for their own store (any store can receive its own webhooks with a valid HMAC) can replay that exact `raw_body`/`hmac-sha256` pair while substituting the `shop-domain` header with a victim shop's domain. `Registry.process` will pass HMAC validation (the body/HMAC pair is genuinely valid) and hand the handler a `WebhookMetadata` claiming the victim's shop, causing the app to attribute attacker-controlled webhook data to a different tenant — a cross-tenant confusion inside this gem's own webhook processing path.

### Likelihood Explanation
Exploitation requires only the ability to send an HTTP request to the app's webhook endpoint with a header that this gem does not verify against the signed content; no access token, `client_secret`, or privileged account is needed, satisfying the "unprivileged internet user" bar. The only prerequisite is possession of one valid signed webhook body (obtainable from the attacker's own store, which they can freely configure), making this practically reachable.

### Recommendation
Bind the shop identity to the HMAC by including `shop-domain` (and ideally `topic`, `webhook-id`) in `to_signable_string`, or independently verify the shop header against a value derived from signed content before trusting it in `Registry.process`.

### Proof of Concept
1. Register a webhook on attacker-controlled shop `attacker.myshopify.com`; capture a real inbound request with valid `X-Shopify-Hmac-Sha256` and raw body `B`.
2. Replay a request to the app's webhook endpoint with the same body `B` and same HMAC header, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `HmacValidator.validate` recomputes the HMAC only over `B` and succeeds [5](#0-4) .
4. `Registry.process` dispatches `handler.handle` with `shop: "victim.myshopify.com"` even though the payload originated from the attacker's own shop [6](#0-5) .
