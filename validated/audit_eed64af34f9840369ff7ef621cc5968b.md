## Title
Denial-of-service via unbounded gas forwarding to untrusted destination modules in batched message delivery — ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatchIncoming`/`dispatchTimeOut` forward calls to arbitrary destination application contracts using low-level `.call(...)` without any gas cap, and `HandlerV2` batches many independent requests/responses/timeouts into a single atomic transaction (`handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, `handleGetRequestTimeouts`, and `batchCall`). Any unprivileged application developer can deploy a destination module that consumes unbounded gas inside its `onAccept`/`onGetResponse`/`onPostRequestTimeout`/`onGetTimeout` callback, causing the whole relayer-submitted transaction — carrying many unrelated users' messages — to run out of gas and revert, mirroring the CVE-2021-22100 pattern where a single misbehaving, permissionlessly-deployed component causes the shared processing pipeline to fail for everyone.

### Finding Description
`EvmHost.dispatchIncoming(PostRequest)` calls the destination module with no gas stipend: [1](#0-0) 

The same unbounded forwarding pattern is repeated for GET responses and both timeout paths: [2](#0-1) 

These `dispatchIncoming`/`dispatchTimeOut` calls are invoked in a loop from `HandlerV2`, once per leaf in the batch, within a single transaction: [3](#0-2) 

`batchCall` further compounds the blast radius: it delegatecalls a sequence of handler invocations (e.g., `handleConsensus` + `handlePostRequests` for several independent applications) atomically, and any failure anywhere reverts the *entire* batch: [4](#0-3) 

The relayer's production code path submits large multi-message batches through exactly this atomic `batchCall`, explicitly to reduce per-message overhead: [5](#0-4) 

Because `.call` with no explicit gas amount forwards up to 63/64 of the remaining gas (EIP-150), a destination module's callback can consume nearly all of the gas available at that point in the transaction. While `dispatchIncoming` gracefully absorbs an outright *revert* from the destination (deleting the receipt so it can be retried later, without reverting the parent handler call), it does **not** protect against a callback that burns gas without reverting (e.g., an expensive/unbounded loop, repeated cold `SSTORE`s, or gas usage keyed to attacker-controlled public state). If the destination's callback consumes enough of the forwarded gas, the remaining 1/64 (or whatever is left) is insufficient to finish processing the remaining leaves/MMR verification/other messages in the same `handlePostRequests`/`handleGetResponses`/`batchCall` transaction, causing the entire transaction to run out of gas and revert — including all the legitimate, unrelated messages bundled alongside the malicious one.

Anyone can trigger this by simply dispatching (or arranging for another user to dispatch) a POST/GET request whose `to`/`from` field targets an attacker-deployed contract; the destination module lookup is by address, with no allow-listing or permission required to become a message recipient — this is directly analogous to a developer "pushing" an uncooperative broker/service in the CVE-2021-22100 scenario, except here the "service" is a permissionlessly reachable `IApp` contract.

### Impact Explanation
This falls under "a route unable to deliver messages." Because relayers batch many users' cross-chain messages into a single atomic `batchCall`/`handlePostRequests` transaction for gas efficiency, a single malicious or merely gas-heavy destination module can repeatedly force out-of-gas reverts of the whole batch. Legitimate requests/responses/timeouts bundled with the malicious one are perpetually blocked from delivery (their relayer fees are also at risk of being wasted on reverted or unprofitable retries), and since gas consumption can be made state-dependent (e.g., toggled right before inclusion), the attacker can adapt to defeat static gas-estimation defenses, sustaining the denial of service across retries.

### Likelihood Explanation
Any account can deploy an arbitrary `IApp` contract and become the destination (`to`) of a POST request, or the source (`from`) app receiving a GET response/timeout — no privileged role or governance action is required. Constructing a callback that burns gas unpredictably (e.g., depending on attacker-controlled storage read right before relayer submission) is straightforward Solidity. The only constraint is that the attacker's message must be included in the same batch as victim messages, which relayers do routinely to minimize gas overhead, making exploitation practical rather than theoretical.

### Recommendation
Cap the gas forwarded to destination module callbacks in `EvmHost.dispatchIncoming`/`dispatchTimeOut` (e.g., `.call{gas: FIXED_STIPEND}(...)`), so a single misbehaving module can, at most, exhaust its own capped allowance rather than starving the remainder of the batch. Additionally, consider isolating per-leaf processing (e.g., via a bounded sub-call/try-catch pattern with gas metering per request) so an OOG in one destination's callback cannot cascade into an atomic revert of unrelated messages in the same `handlePostRequests`/`batchCall` transaction.

### Proof of Concept
1. Deploy a malicious `IApp` contract whose `onAccept` reads a public storage flag it controls and, if set, executes an unbounded loop (or repeated cold `SSTORE`s) intended to consume nearly all forwarded gas without reverting.
2. Dispatch a legitimate-looking POST request (via `EvmHost.dispatch`) with `to` set to the malicious contract, paying a modest relayer fee so it gets bundled with other pending messages.
3. Wait until a relayer batches this request together with several unrelated legitimate POST requests into one `IHandlerV2.batchCall`/`handlePostRequests` transaction (`tesseract/messaging/evm/src/tx.rs::submit_batch_messages`).
4. Immediately before the relayer's transaction is mined, flip the malicious contract's public flag (front-run) so the callback burns far more gas than what was estimated at build time.
5. Observe the batch transaction revert with out-of-gas, causing all bundled legitimate messages to fail delivery and require costly retries, while the attacker's message can be resubmitted to repeat the griefing on the next batch.

    /**
     * @dev Process a batch of encoded handler calls in a single transaction.
     * Uses delegatecall to self so msg.sender is preserved and storage writes
     * happen in this contract's context. Atomic, any failure reverts the entire batch.
     * @param calls - array of ABI-encoded handler function calls
     */
    function batchCall(bytes[] memory calls) external {
        uint256 len = calls.length;
        for (uint256 i = 0; i < len; ++i) {
            (bool success, bytes memory returnData) = address(this).delegatecall(calls[i]);
            if (!success) revert BatchCallFailed(i, returnData);
        }
    }
