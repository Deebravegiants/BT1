### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `shop-domain` header to identify which merchant the payload belongs to. This is the same class of bug as the reported issue: an identifier that downstream code treats as verified (`request.shop`) is never actually included in the bytes that were HMAC-authenticated, so the binding between "authenticated bytes" and "the field acted on" is broken.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` value used by the application is read from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is a separate, unsigned channel: [2](#0-1) 

`Registry.process` validates HMAC via `Utils::HmacValidator.validate(request)`, which internally calls `to_signable_string` (i.e., verifies only the raw body against the shared `client_secret`), and then immediately trusts `request.shop` to build `WebhookMetadata`, which is handed to the host application's handler as the authoritative tenant identifier: [3](#0-2) [4](#0-3) 

`HmacValidator.validate_signature` computes `HMAC-SHA256(client_secret, to_signable_string)` and only compares that against the header-carried digest — it never binds the header-supplied `shop` (or `topic`, `api-version`, `webhook-id`) into the signed material: [5](#0-4) 

Because Shopify signs webhooks with the single, app-wide `client_secret` (not a per-shop secret), the exact same HMAC digest is valid for the exact same raw body regardless of which merchant it was actually sent for. Consequently, the equality the gem should be enforcing — `hmac == HMAC(secret, body ‖ shop)` — is actually only `hmac == HMAC(secret, body)`, i.e. the `shop` component of the identity binding is silently dropped. Any actor who can influence or replay the `shop-domain` header on a request that carries an otherwise-valid `(body, hmac)` pair (for example, a merchant capturing genuine webhook deliveries sent to their own store, or a party sitting on infrastructure that forwards webhooks to the app, e.g., a shared proxy/load balancer/webhook relay) can resubmit that identical `(body, hmac)` pair with a different `shop-domain` header value, and the gem will accept it as authentic for the spoofed tenant.

### Impact Explanation
This crosses a tenant boundary without any additional credential: the HMAC check passes, but the shop identity attached to the processed webhook (`WebhookMetadata#shop`) can be attacker-controlled independent of the signature. Any host application that uses `WebhookMetadata#shop` to select which merchant record to mutate (which is the intended and documented usage pattern of this field) can be made to apply another merchant's legitimately-signed webhook event under an attacker-chosen shop, i.e., cross-tenant data injection/spoofing purely through this gem's own verification logic. This matches the Critical "cross-tenant access" impact category, since the binding between the authenticated payload and the tenant is a security property this gem is expected to provide (it says "Invalid webhook HMAC" is the sole gate before dispatching to the handler with a shop identity it asserts is verified).

### Likelihood Explanation
Exploitability depends on an attacker being able to obtain one valid `(raw_body, hmac)` pair (e.g., by owning/operating their own store subscribed to the same webhook topic, or intercepting webhook traffic on a shared relay/proxy) and then re-delivering it to the app's webhook endpoint with a different `shop-domain` header. This requires network delivery capability to the app's webhook endpoint but no `api_secret_key`, access token, or privileged account — it only relies on the gem's own validation gap, which is squarely in scope.

### Recommendation
Include the shop-identifying header (and ideally `topic`/`webhook-id`) as part of the signable material verified against the HMAC, or otherwise cryptographically bind the header-derived `shop` to the payload before constructing `WebhookMetadata`. At minimum, document loudly that `request.shop` is unauthenticated and must not be trusted for tenant routing without additional verification (e.g., cross-checking against a known/registered shop for the delivered `webhook_id`).

### Proof of Concept
1. App has a webhook endpoint that calls `ShopifyAPI::Webhooks::Registry.process(request)`.
2. Attacker registers/owns "attacker-shop.myshopify.com" and receives a legitimate webhook delivery for topic `orders/create` with raw body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
3. Attacker resends an HTTP request to the app's webhook endpoint with the identical body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` in [4](#0-3) 
returns `true` because it only checks `B` against `H` — the shop header is irrelevant to the check.
5. `Registry.process` builds `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` and dispatches to the host app's handler, which now processes an event as belonging to `victim-shop.myshopify.com` even though it was never actually sent for that shop. [3](#0-2)
