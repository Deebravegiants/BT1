### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, then trusts the unauthenticated `shop-domain` header to identify the tenant the payload belongs to. Because the HMAC secret (`Context.api_secret_key`) is the same for every shop that has installed the app, any body+HMAC pair legitimately obtained from Shopify for one shop remains "valid" when replayed with a different `shop-domain` header, letting an attacker who controls one installed shop impersonate another shop to the host application's webhook handlers.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` values, however, are all read straight from HTTP headers and are never part of the signed material: [2](#0-1) 

`HmacValidator.validate` only recomputes and compares the signature over `to_signable_string` (the body) against the secret shared by all shops of the app: [3](#0-2) 

`Registry.process` treats that body-only HMAC check as sufficient authentication for the whole request, then forwards the header-derived, unauthenticated `request.shop` straight to the app's handler as the tenant identity: [4](#0-3) 

This breaks the identity binding `shop authenticated by HMAC == shop trusted by the handler`. Because Shopify's app-level webhook secret (`api_secret_key`) is identical across every shop that installs the same app, a valid `(body, hmac)` pair obtained from a genuine webhook delivery to *any* shop remains cryptographically valid when the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header is swapped to a different, victim shop domain — the signature check has no way to detect the substitution since the shop is not part of the signed payload.

### Impact Explanation
An unprivileged internet user who can install the app on a shop they control (or simply observe one legitimate webhook delivery to their own shop) can capture a valid `(raw_body, hmac)` pair, then replay that request to the app's webhook endpoint with the `shop-domain` header rewritten to point at a different, victim shop that also uses the app. `Registry.process` will pass HMAC validation and hand the handler a `WebhookMetadata` object whose `shop` claims to be the victim's, with attacker-chosen `body` content. Any host application that keys data storage, session lookup, or business logic off `WebhookMetadata#shop` (the documented and intended usage) will process attacker-controlled data under the victim tenant's identity — a cross-tenant data/authorization confusion.

### Likelihood Explanation
Any developer/attacker can freely create a free Shopify development store and install a public app to obtain legitimate webhook deliveries and their HMAC signatures at will, since the shared secret is per-app, not per-shop. No credential theft, TLS interception, or privileged access is required — only normal installation of the target app on an attacker-owned store, which is standard, unprivileged usage.

### Recommendation
Bind the shop identity to the authenticated request instead of trusting an unauthenticated header:
- Reject webhook processing when the header-provided `shop` does not match a shop known/expected by the receiving app for that delivery (e.g., cross-check with the currently registered/active session shop), or
- Include the `shop-domain` header value as part of the signable string used for HMAC verification (mirroring Shopify's own webhook validation guidance that treats the header set plus body as the authenticated unit within the host integration), or, at minimum,
- Document prominently that `WebhookMetadata#shop` is not covered by the HMAC and must not be trusted as tenant identity without independent verification against the app's own shop/session records.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger any subscribed webhook topic (e.g. `products/create`) to receive a legitimate delivery with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Replay the captured request to the same app's webhook endpoint, keeping body `B` and header `X-Shopify-Hmac-Sha256: H` unchanged, but set `X-Shopify-Shop-Domain: victim.myshopify.com` (a real shop that also installed the app).
3. `ShopifyAPI::Utils::HmacValidator.validate` recomputes `HMAC-SHA256(api_secret_key, B)`, which still equals `H`, since the secret is shared across shops and the shop header is not part of the signed string — validation succeeds.
4. `Registry.process` builds `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed_body_of_B, ...)` and invokes the app's handler, which now processes attacker-supplied content under the victim shop's identity.

          received_signature = verifiable_query.hmac
