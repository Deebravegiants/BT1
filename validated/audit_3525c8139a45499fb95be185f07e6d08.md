### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `Utils::HmacValidator.validate` verifies the HMAC exclusively against that body. The `shop` (from the `shopify-shop-domain`/`x-shopify-shop-domain` header) and `topic` fields are never included in the signed material, yet `Registry.process` trusts `request.shop` as the authenticated tenant identity when building `WebhookMetadata` passed to the app's handler.

### Finding Description
The identity binding that should hold is:

`shop cryptographically bound by HMAC == shop acted upon by the handler`

In this gem, that equality does not hold. `Request#to_signable_string` is defined as: [1](#0-0) 

which returns only `@raw_body`. `Request#shop` reads directly from an unauthenticated header: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string` (the body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` then relies on this body-only HMAC check as the sole authenticity gate, and forwards the unverified `request.shop` value straight into the handler's `WebhookMetadata`: [4](#0-3) 

Because the `shop` header sits entirely outside the signed bytes, any request whose **body** matches a body that Shopify has genuinely HMAC-signed (for *any* shop, including one the attacker controls) will pass HMAC validation regardless of which `shop` header value accompanies it. An unprivileged merchant who installs the app on their own store can trigger real webhook deliveries with content they fully control (e.g., create an order/product/customer with attacker-chosen field values, or use a topic whose payload is constant such as an empty `{}` mandatory webhook body), capture the genuine `body` + `hmac` pair Shopify sent them, and replay that exact pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds because it never inspected the header, and `Registry.process` hands the handler a `WebhookMetadata` claiming `shop: <victim-shop>` with attacker-controlled `body`.

### Impact Explanation
Any host application that uses `data.shop` from `WebhookMetadata` to select the tenant session/store context (the documented and expected pattern for multi-tenant embedded apps) will process attacker-controlled webhook content under the identity of a different merchant. This is a cross-tenant boundary violation reachable by any user capable of installing the app on their own shop (no `api_secret_key`, access token, or privileged access required) — matching the Critical "cross-tenant access" impact category, since the root cause (unsigned `shop` field trusted as the tenant identity) lives entirely in this gem's `Request`/`HmacValidator`/`Registry` code.

### Likelihood Explanation
Exploitation requires only: (1) the ability to install the target app on an attacker-controlled shop (standard for any public Shopify app), and (2) the ability to intercept/replay the attacker's own webhook HTTP request with a modified header, which is straightforward since the attacker owns both endpoints of the original delivery. No secrets are required. The only constraint is finding a webhook topic/body the attacker can make byte-identical to what they want attributed to the victim (mandatory/empty-body topics or topics with attacker-fully-controlled payloads make this trivial).

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`, `api_version`) header values in the HMAC-signed material, or otherwise cryptographically bind them to the signature check in `HmacValidator`/`Request`, so that `Registry.process` cannot deliver a `WebhookMetadata` whose `shop` was not itself authenticated by the HMAC. At minimum, document prominently that `request.shop` is unauthenticated and must not be used to select a tenant session without an independent verification step.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Attacker triggers a webhook whose body they fully control or which is constant (e.g., a mandatory GDPR webhook with body `{}`), causing Shopify to deliver a request with headers:
   `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over "{}">`.
3. Attacker resends this exact `body`/`hmac` pair to the app's webhook endpoint, replacing only the header:
   `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this as a normal request; `Utils::HmacValidator.validate(request)` succeeds because it only recomputes the HMAC over the unchanged body [5](#0-4) .
5. `Registry.process` builds `WebhookMetadata.new(shop: "victim.myshopify.com", body: {}, ...)` and invokes the app's handler, which believes this authenticated event originated from `victim.myshopify.com` [6](#0-5) .
