### Title
Unbounded Uniswap V2 spot-price swap in `EvmHost.dispatch()`/`fundRequest()` allows sandwich-attack fund extraction and message-delivery DoS - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` all execute `IUniswapV2Router02.swapETHForExactTokens` directly against the live Uniswap V2 pool reserves, with `deadline = block.timestamp` (no real deadline protection) and no independent slippage/price bound beyond the caller's own `msg.value`. This mirrors the reported bug class: consuming an AMM's instantaneous spot price on-chain, with no TWAP or price-sanity check, in a path reachable by any unprivileged message dispatcher paying in native token.

### Finding Description
Any unprivileged caller of `dispatch()` (POST or GET) or `fundRequest()` who pays with native token triggers this code: [1](#0-0) 

The pair path is fixed as `WETH -> feeToken()` and the swap is executed against whatever the pool's current reserves are at the moment the transaction lands — the "most recent data point" analogous to `slot0` in the original report, with no TWAP oracle or circuit breaker. The same unguarded pattern repeats in `dispatch(DispatchGet)` and `fundRequest()`: [2](#0-1) 

The project's own documentation acknowledges this exact class of risk for the companion `quote()` view function ("makes it vulnerable to sandwich attacks... Only use it off-chain"), but the actual fund-moving swap inside `dispatch()`/`fundRequest()` — the one that matters, since it spends real `msg.value` — has no such warning-driven mitigation on-chain: no `amountInMax` distinct from `msg.value`, no minimum-output/price-impact guard, and a `deadline` of `block.timestamp` that provides no protection since it always passes.

An attacker (or MEV searcher) can:
1. Observe a pending `dispatch()`/`fundRequest()` transaction with `msg.value` sized close to the fair-market cost of `post.fee` feeToken (as estimated off-chain via `quote()`).
2. Front-run it with a swap that moves the WETH/feeToken pool price against the victim.
3. Let the victim's `swapETHForExactTokens` execute, consuming close to the victim's entire `msg.value` for the same fixed `post.fee` output (worse execution price), or forcing the call to revert entirely if the required input now exceeds `msg.value`.
4. Back-run to restore the pool price and capture the sandwich profit, which is extracted at the direct expense of the fee payer's native token and/or denies the dispatch/fundRequest call outright.

Because the swap sits directly in the `notFrozen`-gated dispatch path used to move real user funds and to open/fund a cross-chain request commitment, this is not merely an "off-chain estimation" concern — it is a live, unauthenticated, on-chain oracle-manipulation surface.

### Impact Explanation
- **Value extraction:** Sandwiching lets an attacker systematically capture the spread between the fair rate and the worst rate the victim's `msg.value` permits, on every native-paid `dispatch`/`fundRequest` call, without any protocol-level protection.
- **Message-delivery denial:** If the attacker moves the price enough that the required `amountIn` exceeds the caller's `msg.value`, the whole `dispatch()`/`fundRequest()` call reverts — the ISMP request is never created/funded, i.e., "a route unable to deliver messages" for any user relying on native-token payment, which can be repeated to griefingly block native-fee dispatch across the entire host.
- This affects `EvmHost`, the core dispatcher used by every `HyperApp` (POST/GET requests) and `fundRequest()` (used to top up in-flight relayer incentives), so the blast radius spans the whole EVM-side messaging surface, not a single peripheral app.

### Likelihood Explanation
- Reachable by any unprivileged address supplying `msg.value` to `dispatch()`/`fundRequest()` — no special role required.
- WETH/feeToken Uniswap V2 pools used for host fee conversion are typically far shallower than major pairs, making price manipulation with a modest flash-loaned or self-funded position economically feasible.
- The project's own docs flag sandwich-attack risk for the *quoting* half of this exact mechanism, confirming the AMM-spot-price hazard is already recognized for this pair/path — it was simply not carried through to the on-chain swap execution.

### Recommendation
- Do not let unauthenticated callers trigger a fund-moving AMM swap with only their own `msg.value` as the only bound. Require callers to pass an explicit `amountInMax` (distinct from `msg.value`) and a real `deadline`, and refund unused native token to the original caller rather than trusting `block.timestamp`.
- Prefer collecting the relayer fee/exchange rate from a manipulation-resistant source (e.g., a TWAP oracle over the WETH/feeToken pool, or a fixed/administered conversion rate) rather than the instantaneous Uniswap V2 reserves, or bound the acceptable price deviation against a reference rate before executing the swap.
- Consider removing the implicit swap from the hot dispatch path altogether and requiring feeToken payment directly, keeping any native-to-feeToken conversion strictly off-chain/user-side (as the docs already recommend for `quote()`).

### Proof of Concept
1. Attacker monitors the WETH/feeToken Uniswap V2 pool used by `EvmHost` (`_hostParams.uniswapV2`) for pending `dispatch()`/`fundRequest()` transactions paying with native token.
2. Attacker front-runs with a large swap in the same pool that pushes the WETH→feeToken price unfavorably for the pending transaction.
3. Victim's transaction executes `swapETHForExactTokens{value: msg.value}(post.fee, [WETH, feeToken], address(this), block.timestamp)` [3](#0-2)  at the manipulated price:
   - If the now-required `amountIn` for `post.fee` output exceeds `msg.value`, the whole `dispatch()` call reverts — the ISMP request is never dispatched (DoS on message delivery).
   - Otherwise, the swap consumes materially more of the victim's ETH for the same fixed `post.fee` feeToken output, and the attacker back-runs to realize the arbitrage profit extracted from the victim's transaction.
4. Repeat for every native-paid `dispatch()`/`fundRequest()` call targeting that pool — no privileged role or governance action is needed by the attacker.
