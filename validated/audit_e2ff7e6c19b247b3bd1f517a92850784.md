### Title
Unbounded `Topics` array in web-api trigger requests enables synchronous CPU-exhaustion DoS that blocks all Gateway message processing - ([File: core/capabilities/webapi/trigger/trigger.go])

### Summary
`triggerConnectorHandler.processTrigger` iterates over every registered workflow trigger and, for each trigger, over every entry of the attacker-supplied `payload.Topics` slice, with no upper bound on the number of topics a caller may submit. Because `HandleGatewayMessage` is invoked synchronously from the Gateway connector's single-threaded `readLoop`, a request with an excessively large `Topics` array causes the loop to run for an extended time, blocking processing of all subsequent Gateway messages on that connection — the same "unbounded loop over attacker-controlled array" root cause as the referenced OpenQ finding, adapted to a Go/CPU-time DoS instead of Solidity gas exhaustion.

### Finding Description
`processTrigger` reads `topics := payload.Topics` directly from the untrusted JSON-RPC payload decoded in `HandleGatewayMessage` and immediately runs a nested loop: [1](#0-0) 

There is no check limiting `len(topics)` (only a check that it is non-empty), and the message decoding path (`ValidatedMessageFromReq`/`json.Unmarshal`) performs no bound on array length either: [2](#0-1) 

The only size restriction anywhere in the pipeline is the overall HTTP request byte size (`MaxRequestBytesLimiter`) enforced at the Gateway's HTTP server, which limits total payload bytes but not the number of elements in the `Topics` array — a payload of a few hundred KB can still contain tens of thousands of short topic strings. [3](#0-2) 

Critically, `HandleGatewayMessage` (and therefore `processTrigger`) executes synchronously in the Gateway connector's `readLoop`, which processes one message at a time per gateway connection: [4](#0-3) 

Thus a single unprivileged actor's oversized `Topics` array causes `O(registeredWorkflows × len(topics))` iterations to run inline in the shared read loop, delaying or starving delivery of legitimate trigger messages for every other workflow/user connected through that Gateway — directly mirroring the reported bug class (unbounded, attacker-influenced loop size disabling processing for all users) even though the underlying resource exhausted is CPU/wall-clock time rather than EVM gas.

### Impact Explanation
This is reachable from any unprivileged client capable of sending a `web_api_trigger` message through the internet-facing Gateway (no authentication/allowlist beyond signature validation of the message envelope is required for the DoS itself, since the cost is paid before/while processing topics). A single malicious/careless request can stall the shared connector read loop, delaying delivery of all other pending trigger events for that DON's Gateway connection — a cross-tenant availability impact affecting unrelated workflows and users, analogous to the "claims can be stopped" impact in the source report.

### Likelihood Explanation
Likelihood is high: constructing a large `Topics` array requires no special privilege, no prior registration, and no bypass of any security control — only that the JSON payload fit under the byte-size cap, which still permits very large arrays of short strings.

### Recommendation
Enforce a strict maximum on `len(payload.Topics)` (and on `len(triggers)` iteration cost) in `processTrigger` before entering the nested loop, rejecting requests that exceed the limit. Additionally, consider moving trigger processing off the synchronous `readLoop` path (e.g., dispatch to a bounded worker pool per gateway connection) so that a single expensive/malformed message cannot block delivery of unrelated messages.

### Proof of Concept
1. Register a workflow trigger with `AllowedTopics` containing at least one topic.
2. As any client, send a `web_api_trigger` JSON-RPC message through the Gateway HTTP/WS endpoint with `payload.Topics` containing a very large number (e.g. tens of thousands) of short strings, kept under the HTTP body byte-size limit.
3. Observe that `triggerConnectorHandler.processTrigger` performs `registeredWorkflows × len(topics)` map lookups synchronously inside the Gateway connector's `readLoop`, delaying processing of other queued/incoming Gateway messages for the duration of the loop.

Note: I was unable to find any code path that further parallelizes or bounds `HandleGatewayMessage` dispatch beyond what's shown in `connector.go`'s `readLoop`; if such a mechanism exists elsewhere (e.g., a wrapping goroutine dispatcher not captured by the index), the severity of the blocking effect would need to be reassessed, and a Devin session with full repository access should be used to confirm this call path end-to-end.

// ValidatedMessageFromReq validated and extracts a legacy Gateway Message
// from params field of JSON-RPC request
func ValidatedMessageFromReq(req *jsonrpc.Request[json.RawMessage]) (*api.Message, error) {
	if req.Version != "2.0" {
		return nil, errors.New("incorrect jsonrpc version")
	}
	if req.Method == "" {
		return nil, errors.New("empty method field")
	}
	if req.Params == nil {
		return nil, errors.New("missing params attribute")
	}
	var m api.Message
	err := json.Unmarshal(*req.Params, &m)
	if err != nil {
		return nil, fmt.Errorf("failed to unmarshal request params: %w", err)
	}
	m.Body.Method = req.Method
	m.Body.MessageID = req.ID
	err = m.Validate()
	if err != nil {
		return nil, err
	}
	return &m, nil
}

	defer c.closeWait.Done()
	ctx, cancel := c.shutdownCh.NewCtx()
	defer cancel()

	for {
		select {
		case <-c.shutdownCh:
			return
		case item := <-gatewayState.conn.ReadChannel():
			var req jsonrpc.Request[json.RawMessage]
			err := json.Unmarshal(item.Data, &req)
			if err != nil {
				c.lggr.Errorw("parse error when reading from Gateway", "id", gatewayState.config.ID, "err", err)
				break
			}
			c.handlersMu.RLock()
			handler, exists := c.handlers[req.Method]
			c.handlersMu.RUnlock()
			if !exists {
				c.lggr.Errorw("no handler for method", "id", gatewayState.config.ID, "method", req.Method)
				break
			}
			// do not break on error. HandleGatewayMessage handles errors
			// by sending a response back to the Gateway.
			err = handler.HandleGatewayMessage(ctx, gatewayState.config.ID, &req)
			if err != nil {
				c.lggr.Warnw("failed to handle message from Gateway", "id", gatewayState.config.ID, "method", req.Method, "err", err)
			}
		}
	}
