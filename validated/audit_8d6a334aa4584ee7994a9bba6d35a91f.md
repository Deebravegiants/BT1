Based on my research, I found a strong analog in `IntentGatewayV2.cancelOrder`'s destination-side cancellation path.

### Title
Order placer can front-run a solver's fill by cancelling from the destination chain right before `fillOrder` lands, always winning the race - ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
`_cancelFromDest` lets the order's own user (the party who benefits from cancelling) unilaterally mark an order as cancelled at any time before the deadline, with no coordination against a pending, already-broadcast `fillOrder` transaction. The two functions read and write the same `_filled[commitment]` slot with no additional synchronization, so whichever transaction lands first in a block wins — and the order's own user (or, after expiry, anyone) is the party who decides when to fire the cancellation, giving them a built-in advantage.

### Finding Description
`fillOrder` in `IntentGatewayV2.sol` checks `_filled[commitment] != address(0)` and reverts `Filled()` if the order is already taken/cancelled [1](#0-0) . Cancellation from the destination chain (`_cancelFromDest`) writes `_filled[commitment] = order.user` unconditionally, before the deadline gate even matters for the user themselves: `if (order.deadline >= _blockNumber()) { if (order.user != ... ) revert Unauthorized(); }` then `_filled[commitment] = ...` [2](#0-1) .

Both paths gate on nothing but a single storage slot read/write, and there is no reservation, pending-fill lock, or minimum-notice window between a solver broadcasting `fillOrder` and the user broadcasting `cancelOrder`. The user, who is the party who set the order's price/deadline and who is the only party allowed to cancel before expiry, is the one racing a solver's committed fill. This is structurally the same "front-runnable stale-status gate" defect as the report: a permissionless status-mutating call (`assessState`/`cancelOrder`) competes against action that depends on the pre-mutation status (`buyProtection`/`fillOrder`), and the actor who benefits from the mutation (the attacker/the order's own user) can choose the timing to always win.

### Impact Explanation
A solver that spends gas building/submitting `fillOrder` (and, for cross-chain orders, already delivering output tokens to the beneficiary before the settlement message is dispatched, per the fill flow docs) can be front-run by the order's own user cancelling in the same block, marking the order `Filled` from the cancellation path and reverting the solver's fill, or — worse for cross-chain orders — leaving the solver's output delivery irreversible while the escrow return path proceeds via `RefundEscrow`. The user loses nothing (their tokens are simply refunded) while a solver's delivered value or wasted gas cost is not covered by any protocol guarantee, and repeated exploitation drains solver profitability without recourse.

### Likelihood Explanation
The order's own user (a fully unprivileged, permissionless caller) can watch the mempool for a competing `fillOrder`/`select` transaction and submit `cancelOrder` with higher gas/priority, and nothing in the contract prevents this — there is no minimum time between order placement and eligibility to cancel, and no fill-in-progress lock.

### Recommendation
Introduce a fill-intent reservation (e.g., a short lock set when a solver is selected via `solverSelection`/`select`) that blocks `_cancelFromDest` while a fill is pending, or require the cancellation transaction to prove no fill has landed within the same block via a stricter ordering guarantee (e.g., requiring cancellation to only be processed after a minimum number of blocks following order placement, and treating a fill that lands in the same block as taking priority).

### Proof of Concept
1. User places a cross-chain order via `placeOrder`, escrowing input tokens, with `deadline = block.number + N`.
2. A solver observes the order and prepares/broadcasts a `fillOrder` transaction on the destination chain, intending to deliver output tokens and later redeem escrow.
3. Before that transaction is mined, the user (or their bot) broadcasts `cancelOrder` on the destination chain with `_cancelFromDest` targeting the same commitment, with equal or higher gas price.
4. If the cancellation lands first, `_filled[commitment]` is set to `order.user` [3](#0-2) , and the solver's subsequent `fillOrder` reverts with `Filled()` [4](#0-3) .
5. The user reclaims their escrow via the `RefundEscrow` path with no penalty, while the solver has already committed resources (gas, or in some flows, output tokens) toward a fill that can never complete.

    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
        }

        _filled[commitment] = address(uint160(uint256(order.user)));

        _post(
            order, _body(RequestKind.RefundEscrow, commitment, order.inputs, order.user), options.relayerFee, msg.value
        );
    }
