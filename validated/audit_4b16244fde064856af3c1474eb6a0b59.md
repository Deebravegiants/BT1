## Title
Webhook `shop` domain is trusted for tenant attribution without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` attribute that is read directly from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, but the HMAC signature that `HmacValidator` verifies is computed only over the raw request body. `Registry.process` validates the HMAC and then forwards `request.shop` straight to the app's webhook handler as the authoritative tenant identity, so the shop attribution is never actually authenticated.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop` is derived independently from a header that is not part of that signable string: [2](#0-1) 

`Utils::HmacValidator.validate` only proves that `@raw_body` was signed with `Context.api_secret_key`; it never checks `shop`: [3](#0-2) 

`Webhooks::Registry.process` uses this unverified field as the tenant identity passed to the handler after the HMAC check passes: [4](#0-3) 

Because a single app's `client_secret` (and thus HMAC key) is shared across every shop that installs the app, an unprivileged attacker can:
1. Install the target app on their own (attacker-controlled) Shopify store.
2. Trigger a real webhook delivery, which Shopify signs with the app's `api_secret_key` — a valid HMAC over the attacker's own body.
3. Replay that exact body + HMAC directly to the app's public webhook endpoint, but substitute the `shopify-shop-domain` header with a victim shop's domain.

The HMAC check still passes (it only covers the body), and `Registry.process` hands the handler a `WebhookMetadata` claiming the payload originated from the victim shop, i.e. `request.shop == "shop acted on"` while `verified.shop` (the shop whose secret actually signed the request) is only "the app's secret", not bound to any particular shop at all. This breaks the identity binding: **shop attributed to payload == shop that authenticated the payload** does not hold, because no per-shop credential/lookup is verified in this gem.

### Impact Explanation
This lets an unprivileged internet user (anyone who can install the app on a shop, e.g. a free dev/trial store) submit attacker-controlled webhook payloads that the app processes as if they originated from an arbitrary victim shop domain. Depending on how the host app keys per-tenant state/data off `WebhookMetadata#shop` (session lookup, data writes, redaction/compliance webhook handling, etc.), this is a cross-tenant data-integrity/impersonation vector — satisfying the "cross-tenant access" Critical/High impact bar, since the gem itself provides no protection and effectively vouches for an unauthenticated field as tenant identity.

### Likelihood Explanation
Moderate-to-high: it requires only a self-service Shopify store to install the target app (no privileged credentials, no leaked secrets), and the webhook endpoint is public by design (Shopify must be able to POST to it from the internet), so nothing in this gem prevents a direct, non-Shopify-originated POST with a forged shop header.

### Recommendation
Bind `shop` into the HMAC-verified signable content (as Shopify's newer webhook signing schemes do), or require the host application to cross-check `request.shop` against a shop that is independently known/authorized (e.g. an installed-shop registry) before trusting it. At minimum, `Webhooks::Request#to_signable_string` should incorporate the shop-domain header, and `HmacValidator`/`Registry.process` should reject any webhook whose claimed shop cannot be corroborated.

### Proof of Concept
```ruby
# Attacker has installed the target app on their own store "attacker.myshopify.com"
# and received a legitimately-signed webhook delivery.
raw_body = '{"id":123,"note":"attacker data"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_api_secret_key, raw_body)

# Attacker replays the same body+hmac to the app's public webhook endpoint,
# but swaps the shop-domain header to the victim's shop.
forged_headers = {
  "shopify-topic" => "orders/create",
  "shopify-hmac-sha256" => Base64.encode64(valid_hmac),
  "shopify-shop-domain" => "victim-shop.myshopify.com", # not covered by HMAC
  "shopify-webhook-id" => "attacker-controlled-id",
  "shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Utils::HmacValidator.validate(request) # => true, HMAC only covers raw_body
ShopifyAPI::Webhooks::Registry.process(request)
# Handler receives WebhookMetadata(shop: "victim-shop.myshopify.com", body: attacker-controlled)
# even though the request never actually came from Shopify on behalf of that shop.
```

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
