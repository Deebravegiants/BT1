### Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` Fields Are Not Covered by the HMAC Signature, Allowing Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw HTTP body via HMAC, while the `shop`, `topic`, `webhook_id`, and `api_version` values that `ShopifyAPI::Webhooks::Registry.process` uses to route and attribute the webhook to a tenant are taken straight from unauthenticated HTTP headers.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are read directly from HTTP headers that are never included in the signed content: [2](#0-1) 

`HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (i.e., the raw body) and compares it to the `hmac` header value; it never binds any header to the signature: [3](#0-2) 

`Registry.process` validates the HMAC and then dispatches the handler using the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` values: [4](#0-3) 

Because the app's webhook `api_secret_key` is shared across every shop installed on the app (it is not per-shop), any body+HMAC pair that is valid for one tenant's webhook delivery is also a valid signature for the same body delivered with a different `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, or `X-Shopify-Webhook-Id` header. The equality that should hold — "shop bound by the signed payload" == "shop used to attribute/process the webhook" — is broken, since the shop identity is carried entirely by a field outside the HMAC's coverage.

### Impact Explanation
This breaks the tenant-identity binding for webhook processing: an unprivileged holder of any one legitimate webhook delivery (body + valid HMAC, which is fully observable/replayable by any shop that installs the app) can re-submit that exact body with altered `shop-domain`/`topic`/`webhook-id` headers, causing the app's registered handler to execute business logic (e.g., data updates, deletions, entitlement changes, `app/uninstalled` handling) attributed to an arbitrary victim shop. This is a cross-tenant impact, since the handler layer built on top of this gem has no way to detect that the "shop" it is told to act on was never actually verified by the signature.

### Likelihood Explanation
Exploitation only requires the attacker to operate their own store that has the target app installed (or otherwise capture one legitimate delivery), which is trivial and requires no credentials beyond normal merchant access. No access to `api_secret_key`, access tokens, or TLS interception is needed — only observation of one's own webhook traffic and re-sending an HTTP POST with modified headers.

### Recommendation
Include the tenant-identifying headers (`shop-domain` at minimum, and ideally `topic`/`webhook-id`) in the signable content used for HMAC verification, or otherwise cryptographically bind them to the payload before `Registry.process` uses them to route/attribute the webhook. At minimum, document and enforce that consumers must not trust `request.shop`/`request.topic` for tenant attribution without independent verification (e.g., cross-checking against a known/registered shop for that specific webhook subscription).

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and lets Shopify deliver a legitimate webhook, e.g. `orders/create`, capturing:
   - raw body `B`
   - `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` using the app's shared `api_secret_key`)
2. Attacker POSTs the same raw body `B` and same `H` header to the app's webhook endpoint, but sets:
   - `X-Shopify-Shop-Domain: victim.myshopify.com`
   - (optionally) a different registered `X-Shopify-Topic`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `H` against `HMAC(B, api_secret_key)` — this still succeeds because `B` and `H` are unchanged.
4. `Registry.process` invokes the topic handler with `shop: "victim.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198`), even though Shopify never generated this webhook for `victim.myshopify.com` — the shop value was fully attacker-controlled and outside the signed content.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
