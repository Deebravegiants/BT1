### Title
Bandwidth subscriptions can expire fully unused due to strict FIFO drain order, permanently losing purchased bytes with no rollover - (File: `modules/pallets/bandwidth/src/lib.rs`)

### Summary
`pallet-bandwidth` drains a purchaser's `(app_chain, app)` subscription queue strictly in **FIFO/insertion order**, regardless of each subscription's individual expiry. A subscription whose position in the queue is never reached before its `expires_at` is silently swept and its entire prepaid byte allowance is lost forever, with no mechanism to roll the unused bytes into a future purchase — the same root-cause pattern as the referenced `StakingRewards` finding, where value accrued/allocated over a period of no consumption becomes permanently unusable.

### Finding Description
Every purchase appends a new `Subscription { tier, remaining_bytes, expires_at, purchased_at }` to the back of a `BoundedVec` FIFO list via `push_subscription`, with `expires_at = now + duration_secs` fixed at insertion time and never extended: [1](#0-0) 

The gate (`try_consume`) always drains from the **head** of the list (`list.get_mut(0)`), independent of which entry is closest to expiring, and any entry whose `expires_at <= now` is swept in place with no accounting of its lost bytes back to the payer: [2](#0-1) 

Because drain order is purely chronological-insertion rather than soonest-expiring-first, a smaller/shorter-duration tier purchased while an older, larger tier is still being drained can sit untouched at the tail of the queue until it expires — at which point its entire byte allocation (which the purchaser paid for) is permanently forfeited. This mirrors the `StakingRewards` bug class: a resource whose "unused" portion (for a period where it wasn't the active recipient of consumption) is discarded rather than rolled forward or refunded.

The pallet's own documentation and test suite confirm this is the actual, reachable behavior: [3](#0-2) [4](#0-3) 

### Impact Explanation
A bandwidth purchaser (an unprivileged, permissionless actor calling `BandwidthManager.purchase()` on any registered EVM source chain) pays real fee-token value for a tier's byte allowance. If that purchaser (or an app being sponsored) tops up with an additional tier while an existing, larger/longer subscription is still being consumed, the newly purchased allocation can be entirely swept unused once its fixed-duration clock expires — permanently freezing/destroying the purchased value with zero possibility of recovery or credit toward the next purchase. This is a direct, protocol-level loss of paid-for funds/resources, not user error, since the drain algorithm itself (strict FIFO by purchase order rather than by soonest-expiring) guarantees this outcome under normal, foreseeable usage patterns (e.g., topping up before running out, mixing tier sizes, or sponsors crediting multiple tiers).

### Likelihood Explanation
This requires no privileged access and no attacker — it occurs under ordinary bandwidth purchasing behavior any time two or more live subscriptions with different remaining durations coexist on the same `(app_chain, app)` queue and the head subscription's lifetime spans past the tail subscription's `expires_at`. This is a common and even encouraged usage pattern (buying ahead of exhaustion, sponsors granting multiple tiers), making the loss highly likely to occur in production rather than a contrived edge case.

### Recommendation
Change the gate's drain policy to prioritize subscriptions closest to expiry rather than strict FIFO insertion order (e.g., drain by soonest `expires_at` first), or alternatively track and roll over any `remaining_bytes` from a subscription about to expire into the next-purchased subscription for the same `(app_chain, app)` before sweeping it. At minimum, emit and account for the exact `lost_bytes` (as already done for `SubscriptionEvicted`) when a subscription expires unconsumed, so governance can reason about and potentially compensate the purchaser, and consider warning/reverting purchases that are provably unreachable given the current queue state.

### Proof of Concept
This is exactly reproduced by the existing test `unused_subscription_expires_independently`: [5](#0-4) 

1. Governance configures `TIER1` (1,000,000 bytes / `QUARTER_SECS` duration) and `TIER2` (500 bytes / `MONTH_SECS` duration).
2. The app buys `TIER1` then `TIER2` at `T0`. `TIER1` is inserted first (head), `TIER2` second (tail).
3. The app lightly consumes bytes (`consume(100)`), which stays entirely within `TIER1`'s large allocation — `TIER2` is never touched because it isn't at the head yet.
4. Time advances past `TIER2`'s expiry (`T0 + MONTH_SECS + 1`) while `TIER1` still has plenty of remaining bytes.
5. The next gate call (`consume(100)`) sweeps `TIER2` out of the list entirely via `list.retain(|s| s.expires_at > now)` — its full 500-byte allocation is permanently lost, with no event crediting or rolling over the loss, even though the purchaser paid for it in full.

			if list.is_empty() {
				return Err(GateError::NoAllowance);
			}

			let total: u128 = list.iter().map(|s| s.remaining_bytes).sum();
			if total < need {
				return Err(GateError::Insufficient { remaining: total, required: need });
			}

			// Drain from the front in insertion order. Once a sub is
			// fully consumed, pop it and continue with the next.
			// `get_mut` defends against a malformed list that satisfies
			// the `total >= need` precheck but is structurally empty;
			// we'd otherwise panic via `list[0]`.
			let mut left = need;
			while left > 0 {
				let Some(head) = list.get_mut(0) else {
					return Err(GateError::NoAllowance);
				};

				head.remaining_bytes = head.remaining_bytes.saturating_sub(take);
				left = left.saturating_sub(take);
				if head.remaining_bytes == 0 {

				}

/// Critical ISP-style property: a sub whose drain never starts (because
/// older subs are still being consumed) still expires on its own clock.
/// What you don't reach in time, you lose.
#[test]
fn unused_subscription_expires_independently() {
	new_test_ext().execute_with(|| {
		jump_to(T0);
		register_manager(APP_CHAIN);
		// sub#0 is fat + long: drain stays inside it the whole test.
		configure_tier(TIER1, 1_000_000, QUARTER_SECS);
		// sub#1 is thin + short: nominally available, but never reached.
		configure_tier(TIER2, 500, MONTH_SECS);
		buy(TIER1).unwrap();
		buy(TIER2).unwrap();

		// Light usage stays inside sub#0.
		assert_eq!(consume(100), Ok(()));
		assert_eq!(sub_count(APP_CHAIN), 2);

		// Cross sub#1's expiry; first gate hit after that prunes it.
		jump_to(T0 + MONTH_SECS + 1);
		assert_eq!(consume(100), Ok(()));
		assert_eq!(sub_count(APP_CHAIN), 1, "unused sub#1 expired and was swept");
		assert_eq!(sub_at(APP_CHAIN, 0).unwrap().tier, TIER1);
	});
