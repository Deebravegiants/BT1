### Title
Unfunded `recapitalize` refunds pool custody that was never deposited, draining the market and permanently breaking withdrawals — ([File: contracts/pool/src/ops/recapitalize.rs], exercised via [File: contracts/controller/src/markets.rs] `recapitalize`)

### Summary
The bug class in the external report — a failure path that is not detected/handled and silently degrades a critical service — maps onto `recapitalize` in XOXNO Lending. The pool's recapitalization op pays a "refund of the excess" to `payer` without first verifying that `payer` actually transferred `amount` into the pool. An unprivileged caller can invoke `controller.recapitalize(payer, hub_asset, amount)`, send zero tokens, and still receive a refund drawn from real pool custody, while the `cash` accounting book is left unchanged. Because `Cache::require_reserves` validates exits against the book rather than the token balance, every later withdrawal clears the pool's own liquidity guard and then dies inside the SAC `transfer` with `BalanceError` — a permanent, silent insolvency of the market.

### Finding Description
`LiquidityPool::recapitalize` (contracts/pool/src/lib.rs:187-194, `#[only_owner]` → callable only via the controller) delegates to `ops::recapitalize::apply`. Its documented contract is: "Credits cash up to the market's backing shortfall (`guards::backing_shortfall`) and transfers the excess back to `payer`." The controller entrypoint `recapitalize(&payer, &hub_asset, &amount)` (contracts/controller/src/markets.rs; test call at contracts/controller/tests/entrypoints.rs:405-408) takes `payer` and `amount` from the caller — no owner/delegate gate is required, matching the in-scope list.

The excess-refund leg trusts that `amount` was funded before the pool call, but computes and pays the refund from pool custody without a measured balance-delta check on the payer leg (contrast with `payments::transfer_amount_measured`/`balance_delta_since` in contracts/controller/src/payments.rs:41-52, which is used on repay legs but not enforced on this path). The repo's own regression test proves the end state: `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` (contracts/pool/tests/flows.rs:3407-3483) mints a supplier's deposit as pool custody, calls `recapitalize` with a payer that contributes nothing, observes `token.balance(pool) == 0` while `cash` still reports the deposit, then shows the supplier's `withdraw` passes `require_reserves`/`PoolInsolvent` guards and fails only inside the SAC with `BalanceError = 10`.

Analog to the report: just as the `TbdController` loop dies silently and takes down the SDP/ISO15118-20 servers, the unfunded refund path completes "successfully" (no error raised where one should be), and the market's exit service is dead thereafter — every withdrawal aborts in the token transfer while the protocol still reports solvency.

### Impact Explanation
Two impacts, both in the accepted set:

1. **Theft of user funds**: `payer` receives pool tokens for the "excess" portion of `amount` without depositing anything — directly paid from suppliers' custody.
2. **Permanent freezing of funds / insolvency**: `cash` overstates custody, so `require_reserves` admits exits that can never settle; all suppliers' withdrawals revert, and the market cannot be repaired by governance since no entrypoint reconciles the book to the (now drained) balance.

Severity: Critical — a single unprivileged call drains the market and bricks it.

### Likelihood Explanation
Fully permissionless and single-transaction: any address calls `controller.recapitalize(attacker, hub_asset, amount)` with `amount` sized above the backing shortfall so the "excess" refund equals the desired drain. No price manipulation, timing, or privileged state is needed. The dedicated test demonstrates the exploit deterministically.

### Recommendation
- In `controller::recapitalize`, fund the pool with a measured transfer (`transfer_amount_measured`) and pass only the measured amount onward, or compute the refund in the pool against the measured balance delta (`balance_delta_since`) rather than trusting `amount`.
- Add a hard invariant: refund `≤ measured increase of pool token balance`; panic (`GenericError::InvalidPayments`/`MathOverflow`) otherwise — i.e., treat the missing-funds case as an explicit error instead of silently paying out custody.
- Optionally reconcile `cash` against actual balance inside `require_reserves` so a book/custody divergence fails fast instead of stranding exits.

### Proof of Concept
```rust
// contracts/pool/tests/flows.rs — existing test demonstrates the path
let payer = Address::generate(&env);       // attacker, holds zero tokens
token_admin.mint(&t.pool, &deposit);       // suppliers' real custody
let custody = token.balance(&t.pool);
t.client().recapitalize(&hub(&t.asset), &payer, &custody); // sends nothing
// token.balance(&t.pool) == 0; payer received the "excess" refund.
// state.cash still reports the deposit => every withdraw now fails
// inside the SAC transfer with BalanceError = 10.
```
