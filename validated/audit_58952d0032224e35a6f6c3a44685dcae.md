### Title
Emporium arbitrary-call action can drain any ERC20 token balance held by the Emporium contract that is not declared in `circomData.erc20TokenAddresses` - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
The Astaria report describes value being moved (a lien taken / an asset bought) that falls outside the equality the protocol relies on (`collateralStateHash`), letting an attacker walk away with funds the accounting never captured. The Hinkal analog is in `EmporiumUpgradeable.runAction`, where the "stateless" op path executes an arbitrary external call from the Emporium contract's own balance, but the pre/post balance equality that is supposed to capture and account for every token movement is only computed over `circomData.erc20TokenAddresses` — a list the caller fully controls and that can omit tokens actually touched by the call.

### Finding Description
`runAction` snapshots `balancesBefore`/`balancesAfter` only for `circomData.erc20TokenAddresses` [1](#0-0) , then in the unsigned "stateless interaction" branch (`stack.signerAddress == address(0)`) directly performs `op.endpoint.call{value: op.value}(op.callData)` with attacker-supplied `endpoint`/`callData`, restricted only to blocking the `callHinkalWallet`/`doSendToRelay` selectors [2](#0-1) . `verifyWallet` performs no signature check at all in this branch — it just marks the `emporiumMessage` used and returns [3](#0-2) .

Because the Emporium contract is a single shared contract (not a per-user wallet — that role is `HinkalWallet`), any ERC20 token balance it happens to hold (e.g. dust/leftovers from a prior swap, a token that was part of a previous user's `erc20TokenAddresses` list but never fully swept by `handleOut`) is not protected. An attacker submits `transact()` with `externalActionId == HINKAL_EMPORIUM_ACTION_ID`, `circomData.erc20TokenAddresses` containing only tokens they intend to declare (e.g. none, or unrelated ones), and `stack.ops` containing a raw call such as `IERC20(otherToken).transfer(attacker, balance)` where `otherToken` is not in `circomData.erc20TokenAddresses`. This call succeeds (`onlyAllowedRecipient` only checks `msg.sender == Hinkal`, not the token/target), and:
- `balancesBefore`/`balancesAfter` never observe `otherToken`, so `handleOut` never creates/consumes a UTXO for it [4](#0-3) .
- Hinkal's top-level balance equation (`balanceDif == amountChanges[i] + utxoAmount`) is likewise only enforced per-token over `circomData.erc20TokenAddresses` [5](#0-4) , so a token entirely absent from that array is never checked and its movement is invisible to the equality the whole system relies on to conserve value.
- The ZK proof's `calldataHash`/`signedMessageHash` bind the *declared* `erc20TokenAddresses`/`amountChanges`/`externalActionMetadata`, but they do not (and cannot) constrain what `op.callData` actually does at the target contract, nor tie the call's real-world token effects back into the balance equation.

This mirrors the Astaria bug class exactly: an action (`listForSaleOnSeaport` there, `runAction`'s stateless call here) moves/exposes value while the state variable the security check relies on (`collateralStateHash` there, the `erc20TokenAddresses`-scoped balance snapshot here) is never updated/consulted for that value, letting the attacker extract funds the accounting never captured.

### Impact Explanation
This is a direct theft of protocol/relay-held funds: any ERC20 balance sitting in the Emporium contract that is not part of the caller's declared `erc20TokenAddresses` list can be transferred to an arbitrary attacker-chosen address with no signature, no proof constraint on the call's effect, and no balance check catching it. Per the rules this is at minimum High severity (theft of protocol/relay fees or funds not belonging to the caller); if such residual balances include another user's leftover shielded-then-unswept token, it rises to Critical (theft of user funds).

### Likelihood Explanation
Requires (a) the Emporium contract to be holding some ERC20 balance outside the current caller's declared token set (plausible via dust from partial swaps/rounding, previously failed sweeps, or another concurrent user's in-flight operation using the same shared contract), and (b) the attacker simply omits that token from `circomData.erc20TokenAddresses` while including a transfer of it in `stack.ops`. No special privileges or a compromised relayer are required — any unprivileged EOA calling `transact()` with `externalActionId = HINKAL_EMPORIUM_ACTION_ID` can attempt this whenever the Emporium contract's balance is non-empty.

### Recommendation
Restrict the stateless call path so that `op.endpoint` cannot be an ERC20/ERC721/ERC1155 contract not present in `circomData.erc20TokenAddresses` (or more robustly, snapshot/verify the Emporium's balance for every token actually touched during the call, not just the declared list), and/or require the Emporium to sweep to zero balance after every `runAction` and revert if any non-declared-token balance changed. Alternatively, disallow direct token-contract calls from the stateless branch entirely, forcing all token movement through the already-audited `deltaAmountChanges`/`handleOut` accounting.

### Proof of Concept
1. Assume the Emporium contract holds `X` amount of `TokenB` left over from an earlier operation (dust from a partial swap or an interrupted transaction).
2. Attacker calls `Hinkal.transact()` with `circomData.externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `circomData.erc20TokenAddresses = [TokenA]` (deliberately excluding `TokenB`), and `externalActionMetadata` encoding an `EmporiumStack` with `signerAddress = address(0)` and one `EmporiumOperation{ endpoint: TokenB, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, X)) }`.
3. `EmporiumUpgradeable.runAction` executes the stateless branch: `verifyWallet` requires no signature since `signerAddress == address(0)` [6](#0-5) ; the selector check only blocks `callHinkalWallet`/`doSendToRelay`, so `TokenB.transfer` passes through and executes, moving `X` `TokenB` from Emporium to the attacker [2](#0-1) .
4. `balancesBefore`/`balancesAfter` and Hinkal's balance-equation loop never observe `TokenB` since it's absent from `circomData.erc20TokenAddresses`, so no revert occurs and no UTXO accounting is required for the stolen amount [5](#0-4) .

Note: I was unable to independently confirm within the indexed context whether the Emporium contract is guaranteed to always hold zero residual balance after every legitimate operation (which would reduce likelihood) — this would require reviewing all callers/action integrations and off-chain sweep guarantees, which is not fully available in the indexed portion of the repo.
