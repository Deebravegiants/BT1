### Title
Webhook Shop/Topic Identity Spoofing via Headers Not Covered by HMAC - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by verifying the HMAC signature over the **raw JSON body only**, but then trusts the `shop`, `topic`, `webhook_id`, and `api_version` values taken from HTTP **headers**, which are never included in the signed payload. This breaks the identity binding `HMAC-verified data == data acted upon`: the signature proves the *body bytes* are authentic, but it proves nothing about which shop or topic that body belongs to.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from attacker-influenceable HTTP headers with no cryptographic binding to the body: [2](#0-1) [3](#0-2) 

`HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string` (i.e., the raw body): [4](#0-3) 

`Registry.process` performs exactly one check — the body HMAC — and then unconditionally forwards the header-derived `shop`/`topic`/`webhook_id`/`api_version` to the webhook handler as authoritative identity fields: [5](#0-4) 

Because the app's `api_secret_key` is shared across **every** shop that installs the app, any merchant who installs the app is a legitimate holder of `(raw_body, valid_hmac)` pairs for their own genuine webhook deliveries. Such a merchant (an unprivileged internet user with respect to any *other* tenant) can replay that exact raw body and its valid HMAC to the app's webhook endpoint while altering the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header to name a different, victim shop. The HMAC check still passes (it only checks the body), and `WebhookMetadata` is constructed with the attacker-chosen `shop`, so the handler processes/attributes the payload as if it came from the victim tenant.

This is the binding-break class called out in the prompt: a field (`shop`, the tenant/session key) is acted upon by the library but is not covered by the HMAC that is supposed to authenticate the request.

### Impact Explanation
This enables cross-tenant confusion: an app that keys any state, side effects, or data writes off `WebhookMetadata#shop` (as the gem's own doc/tests demonstrate is the intended usage — see `handler.handle(data: WebhookMetadata.new(... shop: request.shop ...))`) can be made to attribute a genuine, signature-valid webhook body to the wrong shop. Depending on what the host app does with `shop` (e.g., looking up/activating a session, writing to a shop-scoped record, triggering a shop-specific side effect), this is a cross-tenant access vector meeting the "Critical - cross-tenant access" bar, since the *identity* used to select the tenant context is unauthenticated while the *payload* is merely proven authentic-but-unattributed.

### Likelihood Explanation
Likelihood is bounded by needing a legitimate install of the app on at least one shop under attacker control (to obtain valid `(body, hmac)` pairs), which is realistic for any multi-tenant Shopify app with public/self-serve installation. No access token, `client_secret`, or privileged credential is required — only ordinary use of the gem's own public `Registry.process` API with attacker-controlled headers, which is exactly the surface exposed to "unprivileged internet user" per the scan rules.

### Recommendation
Bind the identity fields into the HMAC-verified payload rather than trusting raw headers:
- Include `shop`, `topic`, `webhook_id`, and `api_version` in the signable string alongside the body, or
- Require host applications to cross-check `request.shop` against the shop associated with the currently active/looked-up session *before* trusting it, and document this requirement explicitly, or
- At minimum, have `Registry.process` verify that the resolved shop is one for which the app holds an active session/install record before dispatching to the handler.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and on victim `victim-shop.myshopify.com`, both using the same app `api_secret_key`.
2. Shopify delivers a genuine webhook to the attacker's endpoint for `attacker-shop.myshopify.com`:
   - Headers: `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`
   - Body: `{"id": 1, ...}`
3. Attacker replays the identical body and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, only changing:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
4. `Utils::HmacValidator.validate` passes (body/HMAC pair is untouched and valid).
5. `Registry.process` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and dispatches to the handler, which now believes this data belongs to `victim-shop.myshopify.com`. [6](#0-5)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
