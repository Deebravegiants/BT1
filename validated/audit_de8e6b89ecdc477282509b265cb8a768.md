Based on my investigation, I found the analog: `placeOrder()` in `IntentGatewayV2.sol` performs a Uniswap V2 fee-token swap using `block.timestamp` as the deadline, which is functionally identical to a missing deadline check.

### Title
Missing effective deadline check in `placeOrder()` fee-token swap allows the swap to be executed at an arbitrarily delayed, manipulated price - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`placeOrder()` swaps native ETH sent by the user for the protocol fee token via `IUniswapV2Router02.swapETHForExactTokens`, passing `block.timestamp` as the `deadline` argument instead of a caller-supplied, submission-time deadline [1](#0-0) . The identical pattern also exists in the Tron variant of the contract [2](#0-1) .

### Finding Description
`block.timestamp` evaluated inside the transaction is always equal to (or effectively equal to) the timestamp of the block that mines the transaction, so the Uniswap V2 router's `ensure(deadline)` modifier can never reject the swap regardless of how long the transaction has sat in the mempool or been withheld by a block builder/validator. This nullifies the entire purpose of the deadline parameter — it should be set by the caller (e.g. `block.timestamp + X`) at the time the transaction is submitted, bounding how long the transaction can be delayed before execution. Here the router-level deadline provides no protection because it is computed by the callee (the router call, embedded inside `placeOrder`) at execution time rather than supplied by the user at signing time [1](#0-0) .

This directly mirrors the reported bug class in `SingleSidedLiquidityVault.deposit()`: a user-facing function that performs a swap on the user's behalf with no way to bound how long the transaction can be withheld before execution.

### Impact Explanation
`placeOrder` is the primary unprivileged, user-facing entrypoint of the Intent Gateway that any user calls to escrow inputs and start an order — reachable directly from a single submitted transaction with no special privileges [3](#0-2) . Because the deadline is meaningless, a validator/builder/relayer (or a searcher observing the pending transaction) can withhold the `placeOrder` transaction and choose to include it at a block where the ETH/fee-token pool price has been manipulated unfavorably (sandwich attack), before finally including the user's transaction. Since the swap is an exact-output swap bounded by `msgValue` (the ETH sent), the most direct consequence is that the swap either consumes materially more of the user's ETH than the market price at submission time warranted, or (if fully priced out) the whole `placeOrder` call reverts, forcing the user to resubmit with more gas/ETH under an again-manipulated price — a market/timing manipulation that causes users to lose ETH value on every attempted fee-token acquisition. This is the same class of unfavorable-price-execution impact called out in the source report as "unfair swap execution due to unbounded execution timing."

### Likelihood Explanation
Likelihood is fairly high in practice: any user who pays the solver fee in native token when placing an order triggers this code path [4](#0-3) , and MEV searchers/builders routinely watch mempools for exactly this pattern (an ETH→token swap with no real time bound) to sandwich for value extraction.

### Recommendation
Add an explicit `deadline` field to the `Order`/`placeOrder` call parameters (or accept a separate `swapDeadline` argument) supplied by the caller at signing time, and pass that value — not `block.timestamp` — into `swapETHForExactTokens`. Apply the same fix to the Tron variant in `evm/tron/contracts/apps/IntentGatewayV2.sol`.

### Proof of Concept
1. User calls `placeOrder` with `order.fees > 0` and `msg.value` sized to cover the current expected fee-token price plus a small buffer.
2. A validator/searcher observing the pending transaction withholds it (or sandwiches it) across N blocks/transactions, manipulating the ETH/fee-token pool price upward in the interim.
3. When finally included, `swapETHForExactTokens{value: msgValue}(order.fees, path, address(this), block.timestamp)` is evaluated with `deadline = block.timestamp` of the *inclusion* block — always satisfying the router's deadline check regardless of delay [5](#0-4) .
4. The swap executes at the manipulated price: it either consumes more of the user's ETH than intended (with only the small residual refunded via `_sendValue`) [6](#0-5) , or reverts entirely if `msgValue` is insufficient at the manipulated price, wasting the user's gas and requiring costly resubmission at the newly manipulated price.
