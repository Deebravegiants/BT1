### Title
Orb-relay client bypasses source-identity verification when handling `RequestState`, allowing an unauthorized peer to trigger replay of the last self-serve signup message - (File: `orb-relay-client/src/client.rs`)

### Summary
This mirrors the Seda `H-8` bug class: a message is acted upon (here, re-transmission of the last outgoing message) without verifying that the request actually came from the authorized counterparty. In `orb-relay-client`'s `PollerAgent::main_loop`, every other inbound message is validated with `src.id != self.config.dst_id` before being processed, but the `self_serve::app::v1::RequestState` branch skips that check entirely and unconditionally re-sends `self.last_message` the moment any payload matches `RequestState`, regardless of who the `src` on the frame actually is.

### Finding Description
In the poller's main receive loop: [1](#0-0) 

the normal path is:
- if `payload` matches `RequestState`, resend `self.last_message` — no `src` check at all.
- otherwise, only if `src.id == self.config.dst_id` is the payload handed to `handle_message`; if the source id doesn't match, the message is logged and dropped.

This is the same root-cause pattern as the Seda `Withdraw` bug: an action with a sensitive side effect (delivering the previously sent self-serve state/result payload, e.g. `SignupEnded`, `CaptureTriggerTimeout`, `CaptureStarted`, or `AnnounceOrbId` acknowledgements used to gate biometric capture) is performed for *any* sender that can format a matching payload, without validating that the sender is bound to the same session/identity (`dst_id`) that the orb is legitimately talking to. The relay server multiplexes messages by `src`/`dst` `Entity` on a session, but the client-side trust decision ("is this the entity I'm paired with for this signup session") is completely omitted for this one message type.

### Impact Explanation
`RequestState` triggers a resend of orb-side self-serve session state (the last message sent to the paired App entity, which can be signup lifecycle/result data such as `SignupEnded`, `CaptureStarted`, `CaptureTriggerTimeout`). Because the `src.id != self.config.dst_id` authorization check present everywhere else is bypassed in this branch, a peer that is not the legitimate paired App for that signup session can force retransmission of that state to the configured destination on demand, which is unpaired-session state disclosure/replay of self-serve signup lifecycle data and a break of the trust boundary between the Orb-relay client and the App it believes it is exchanging session data with.

### Likelihood Explanation
Reachable by any unprivileged client capable of connecting through orb-relay and sending a well-formed `self_serve::app::v1::RequestState` payload; the check that would normally reject an unexpected source (`src.id != self.config.dst_id`) is never evaluated for this message type, so no special privilege beyond network/relay access is required to trigger the bypass.

### Recommendation
Validate `src.id == self.config.dst_id` for the `RequestState` branch exactly as done for the general message-handling `else` branch, before resending `self.last_message`, so only the paired counterparty for the active session can request a state replay.

### Proof of Concept
1. Attacker connects to orb-relay as an `App`/`Orb` entity (or otherwise gets a message with `src.id` different from the expected `dst_id` routed on the stream).
2. Attacker sends a payload that unpacks to `self_serve::app::v1::RequestState {}` (per `PayloadMatcher` at `orb-relay-client/src/lib.rs:32-43`).
3. In `main_loop`, the branch `self_serve::app::v1::RequestState::matches(&payload).is_some()` is true, so `sender_tx.send(self.last_message.clone())` executes unconditionally — no `src.id` comparison occurs, unlike the `else if src.id != self.config.dst_id` check that gates all other messages.
4. The last self-serve state message is retransmitted without any verification that the requester is the legitimate paired entity for that signup session. [2](#0-1) [3](#0-2)
