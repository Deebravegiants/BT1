**Rationale:** `RANDOMNESS_GENERATED_EVENT_MOVE_TYPE_TAG` is a static `TypeTag` built once via `TypeTag::from_str("0x1::randomness::RandomnessGeneratedEvent")` [1](#0-0) . It is only referenced in consensus pipeline/executor code for identifying randomness-generation events (used for metrics/counting purposes), not in any resource-account freeze or custody logic [2](#0-1) .

There is no "freeze logic" in resource accounts (`aptos_framework::resource_account` or `aptos_framework::account`) that performs a string-equality or `TypeTag` comparison against this constant. Resource-account custody is instead governed by `SignerCapability` possession and the `Container` map keyed by address, e.g. `retrieve_resource_account_cap` checks `container.store.contains_key(&resource_addr)` [3](#0-2) , and account freezing/auth-key rotation is gated by the `SignerCapability` object itself, not by any event type-tag string comparison [4](#0-3) .

Since:
1. The premise (a "strict-equality custody check in a resource account's freeze logic" using the `RandomnessGeneratedEvent` type-tag string) does not correspond to any real code path in this repository, and
2. `TypeTag::FromStr`/`parse_type_tag` parsing differences (case, whitespace) would at most affect whether an event *matches* for filtering/indexing purposes — an event-level concern, not a custody boundary — this does not meet the review's requirement that unprivileged input must cross a real custody boundary affecting ownership, freeze, or transfer authority of an asset.     public fun retrieve_resource_account_cap(
        resource: &signer, source_addr: address
    ): account::SignerCapability acquires Container {
        assert!(
            exists<Container>(source_addr),
            error::not_found(ECONTAINER_NOT_PUBLISHED)
        );

        let resource_addr = signer::address_of(resource);
        let (resource_signer_cap, empty_container) = {
            let container = borrow_global_mut<Container>(source_addr);
            assert!(
                container.store.contains_key(&resource_addr),
                error::invalid_argument(EUNAUTHORIZED_NOT_OWNER)
            );
            let (_resource_addr, signer_cap) =
                container.store.remove(&resource_addr);
            (signer_cap, container.store.length() == 0)
        };

        if (empty_container) {
            let container = move_from<Container>(source_addr);
            let Container { store } = container;
            store.destroy_empty();
        };

        account::rotate_authentication_key_internal(resource, ZERO_AUTH_KEY);
        resource_signer_cap
    }

        let resource_addr = create_resource_address(&signer::address_of(source), seed);
        let resource = if (exists_at(resource_addr)) {
            if (resource_exists_at(resource_addr)) {
            let account = &Account[resource_addr];
            assert!(
                account.signer_capability_offer.for.is_none(),
                error::already_exists(ERESOURCE_ACCCOUNT_EXISTS),
            );
            };
            assert!(
                get_sequence_number(resource_addr) == 0,
                error::invalid_state(EACCOUNT_ALREADY_USED),
            );
            create_signer(resource_addr)
        } else {
            create_account_unchecked(resource_addr)
        };

        // By default, only the SignerCapability should have control over the resource account and not the auth key.
        // If the source account wants direct control via auth key, they would need to explicitly rotate the auth key
        // of the resource account using the SignerCapability.
        rotate_authentication_key_internal(&resource, ZERO_AUTH_KEY);

        let account = &mut Account[resource_addr];
        account.signer_capability_offer.for = option::some(resource_addr);
        let signer_cap = SignerCapability { account: resource_addr };
        (resource, signer_cap)
    }
