### Title
Reachable panic (Rust `unwrap`/CHECK-fail analog) in `calc_take_pnl`/`calc_x_power` from Deposit, Withdraw and WithdrawPnl — potential freezing of pool funds - (File: `program/src/processor.rs`, `program/src/math.rs`)

### Summary
The TensorFlow advisory is a classic CWE-617 "reachable assertion" bug: a `CHECK`/unwrap-style operation trusts an implicit invariant between two attacker-influenced values (`input` and `weights` shapes) instead of validating it, so a crafted call panics the process. The Raydium AMM program contains the same bug class: `Calculator::calc_x_power` performs an unchecked `checked_div(current_y).unwrap()` [1](#0-0)  that is called from `Processor::calc_take_pnl` [2](#0-1) , which in turn is invoked from `process_deposit`, `process_withdraw`, and `process_withdrawpnl` [3](#0-2) [4](#0-3) . None of these call sites validate that `total_coin_without_take_pnl` (the divisor, `y1`) is non-zero before calling into `calc_take_pnl`.

### Finding Description
`calc_total_without_take_pnl_no_orderbook` computes the pool's coin/pc balances net of pending PnL using `checked_sub(...).ok_or(...)`, so it safely rejects the case where the vault balance is *less than* `need_take_pnl_*`, but it explicitly allows the result to be exactly `0` [5](#0-4) . That `0` value is then normalized into `y1` via `normalize_decimal_v2` and passed straight into `Processor::calc_take_pnl` as `current_y` [6](#0-5) .

Inside `calc_take_pnl`, `Calculator::calc_x_power` divides by `current_y` with `.checked_div(current_y).unwrap()` [1](#0-0) , and the surrounding function chains several more `.unwrap()`s on `checked_sub`/`checked_mul`/`checked_div` that assume `x2 <= x1` and `y2 <= y1` hold by construction [7](#0-6) . None of this is guarded by an explicit "is `total_coin_without_take_pnl` zero" check like the shape check that TensorFlow's `DenseBincount` was missing for `weights`. If the pool's remaining coin balance net of pending PnL (`y1`) ever reaches `0` — for example after aggressive draining via swaps that push `amm_coin_vault.amount` down close to `amm.state_data.need_take_pnl_coin` — any subsequent call to `Deposit`, `Withdraw`, or `WithdrawPnl` triggers `checked_div(0).unwrap()` → `None.unwrap()` → panic, aborting the transaction.

### Impact Explanation
A panic in a Solana on-chain program simply fails the invoking transaction; it does not corrupt state by itself. The concern is that `calc_take_pnl` is on the *mandatory* code path of `process_withdraw` and `process_withdrawpnl` — there is no way to call these instructions successfully while the divide-by-zero condition persists. If the zero-`y1` (or symmetric zero-`x1`, via the pc side) state can be driven and then held (e.g., because the same trade activity that created it also prevents new coin/pc from re-entering the accounted `total_*_without_take_pnl`), LPs would be permanently unable to withdraw their liquidity through `Withdraw`, and pending PnL could become permanently unclaimable through `WithdrawPnl`, which matches the "permanent freezing of LP funds" impact class this scan is scoped to accept.

### Likelihood Explanation
This requires an attacker to engineer an exact edge-state (vault balance minus pending PnL reaching exactly zero on one side) purely through public, unprivileged instructions (repeated swaps, deposits/withdrawals) — no privileged signer or off-chain step is needed, but the precision required (similar to the original advisory's `AC:H` attack complexity) makes it a non-trivial, deterministic-but-narrow condition rather than trivially reachable on every pool. I was not able to fully enumerate, within the available iterations, the exact sequence of swap/withdraw amounts that forces `total_coin_without_take_pnl` (or the pc equivalent) to hit `0` given the rest of the deposit/withdraw slippage and status guards; this would need dedicated arithmetic modeling or a Devin session with test execution to confirm feasibility end-to-end.

### Recommendation
Replace the `.unwrap()` calls in `Calculator::calc_x_power` and the surrounding `checked_sub`/`checked_mul`/`checked_div` chains in `Processor::calc_take_pnl` with explicit `ok_or(AmmError::...)?` propagation, and add an explicit guard in `calc_take_pnl` (and/or in `calc_total_without_take_pnl_no_orderbook`) that returns a typed `AmmError` when `current_x`/`current_y` (i.e., `total_pc_without_take_pnl`/`total_coin_without_take_pnl`) is zero, instead of allowing execution to reach the unchecked division.

### Proof of Concept
Not independently reproduced — deriving the precise deposit/withdraw/swap sequence needed to drive `total_coin_without_take_pnl` (or `total_pc_without_take_pnl`) to exactly `0` requires stepping through `process_deposit`/`process_withdraw`/swap arithmetic with concrete numeric fixtures (similar to the existing `test_calc_take_pnl`/`test_calc_pnl_precision` unit tests at `program/src/processor.rs:3057-3212`) [8](#0-7) , which was not completed within this investigation.

```rust
        // must be use u256, because u128 may be overflow
        let x_power = last_x
            .checked_mul(last_y)
            .unwrap()
            .checked_mul(current_x)
            .unwrap()
            .checked_div(current_y)
            .unwrap();

    }
```

```rust
    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
```
