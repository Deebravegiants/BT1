### Title
Webhook `shop` (and `topic`) identity is trusted from unauthenticated HTTP headers while HMAC only covers the body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Utils::HmacValidator.validate` computes/compares the HMAC solely against that signable string [2](#0-1) . Meanwhile `Request#shop` and `Request#topic` are read directly from the `x-shopify-shop-domain`/`shopify-shop-domain` and `x-shopify-topic` HTTP headers [3](#0-2) , which are never included in the HMAC-signed content. `Registry.process` validates the HMAC and then, without any further check, hands the header-derived `shop` value straight to the app's handler as authoritative tenant identity: [4](#0-3) .

### Finding Description
The identity binding that should hold is: `shop_used_by_handler == shop_that_produced_the_HMAC-signed_payload`. In this gem that equality is never enforced — `shop` (and `topic`, `webhook_id`, `api_version`) are parsed from HTTP headers that sit entirely outside the HMAC's scope, which is limited to the raw request body [5](#0-4) .

Because `Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e., "does this body hash to a value Shopify could have produced with our secret") and then unconditionally builds `WebhookMetadata` from `request.shop`/`request.topic` [6](#0-5) , any request carrying a body+HMAC pair that is valid for *some* shop's genuine webhook delivery, but with the `x-shopify-shop-domain` header swapped to name a different shop, will pass validation and be dispatched to the handler as if it legitimately originated from the victim shop. The library's own documentation reinforces that this is treated as a proven identity: "This will verify the request did indeed come from Shopify" [7](#0-6) , and shows consuming code keying off `data.shop` directly (`perform_later(topic: data.topic, shop_domain: data.shop, ...)`) [8](#0-7) .

### Impact Explanation
This breaks the tenant boundary the HMAC check exists to enforce. An unprivileged internet user who legitimately installs the app on their own shop (no special privileges required, no `api_secret_key` needed) can capture a genuinely-signed webhook delivery for their own store (body + HMAC), then replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop. Downstream apps that use `data.shop` (as the gem's own docs instruct) to select which shop's session/access token/database row to act on will process attacker-supplied body content under the victim's identity — i.e. cross-tenant data injection/spoofing that the HMAC check was supposed to prevent.

### Likelihood Explanation
Likelihood is high for any app following the documented pattern literally: register a handler, call `Registry.process`, and trust `data.shop`. No credentials, tokens, or TLS interception are needed — only an HTTP POST with attacker-controlled headers to the app's public webhook endpoint, which is by design internet-reachable.

### Recommendation
Bind the shop/topic/webhook identity into the HMAC-verified content, or otherwise cryptographically/authoritatively establish it rather than trusting request headers. Concretely, `VerifiableQuery#to_signable_string` for webhooks should incorporate the header fields that the app relies on for tenant identity (`shop`, `topic`, `webhook_id`, `api_version`) into the signable payload before computing/comparing the HMAC, or the library should document/require that consumers independently verify `data.shop` against a shop they already have a stored session for rather than trusting it as proof of origin.

### Proof of Concept
1. Install the app on shop `attacker.myshopify.com` (unprivileged, self-service).
2. Trigger a real webhook for a topic the app is registered for; capture the raw body and the genuine `x-shopify-hmac-sha256` header Shopify sent for that delivery.
3. Replay an HTTP POST to the app's webhook endpoint with the identical body and HMAC header, but set `x-shopify-shop-domain: victim.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `@raw_body` [1](#0-0)  — validation succeeds because the body/HMAC pair is unmodified.
5. `Registry.process` dispatches `WebhookMetadata.new(..., shop: request.shop, ...)` with `shop == "victim.myshopify.com"` [9](#0-8) , and the app's handler (following the documented pattern) processes attacker-controlled body content under the victim shop's identity.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
