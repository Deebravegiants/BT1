### Title
Webhook shop-domain identity is trusted for routing/authorization but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and exposes an HMAC that only signs the raw request body, while the `shop` (and `topic`, `webhook_id`, `api_version`) values are read from unauthenticated HTTP headers and passed straight through to the app's webhook handler as trusted identity.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery` by computing an HMAC over `verifiable_query.to_signable_string` and comparing it against `verifiable_query.hmac` [1](#0-0) .

For webhooks, `to_signable_string` returns only `@raw_body` — none of the `shopify-*` headers are part of the signed material [2](#0-1) . The `shop`, `topic`, `api_version`, and `webhook_id` accessors are read straight from HTTP headers with no additional integrity check [3](#0-2) .

`Registry.process` validates only the body HMAC, then immediately constructs a `WebhookMetadata` object using `request.shop` (and the other header-derived fields) and hands it to the app-registered handler as the trusted identity of the webhook's originating shop [4](#0-3) .

The binding that should hold is:
`shop value the HMAC authenticates == shop value the handler acts on`

but in practice:
`shop value the HMAC authenticates (nothing, since HMAC covers only raw_body) != shop value handed to the handler (request.shop, an unauthenticated header)`

Because the header is outside the signed material, any party capable of obtaining one genuinely Shopify-signed webhook body+HMAC pair (e.g., by installing the app on their own store, which is a routine, unprivileged step available to anyone) can replay that exact body/HMAC pair while substituting an arbitrary `x-shopify-shop-domain` header value. The HMAC will still validate (it only checks the body), yet `WebhookMetadata#shop` will report the attacker-chosen shop domain to the handler.

### Impact Explanation
Apps built on this gem are documented to trust `WebhookMetadata#shop` (and `topic`) as the authenticated identity of which merchant/tenant the webhook event pertains to. Since this identity is not covered by the HMAC, an attacker who owns any store (a trivial, free, unprivileged action) can forge the apparent originating shop of a webhook payload while keeping a valid signature, enabling cross-tenant confusion: the handler may write/update state keyed by an incorrect `shop`, effectively impersonating another merchant's webhook traffic. This satisfies the "cross-tenant access" impact category because the shop-domain identity binding — the boundary between tenants in a multi-tenant app — can be crossed without any tenant-specific secret.

### Likelihood Explanation
Exploitation requires only: (1) installing the target public app on an attacker-owned store to receive one legitimately HMAC-signed webhook body, and (2) resending that body with a modified `shop-domain` header to the app's webhook endpoint. No access token, `client_secret`, or privileged account is required — this is achievable by any unprivileged internet user who can install a public Shopify app, which is a low bar. The likelihood is tempered somewhat by needing the JSON body shape to be one the handler expects and by the app operator's own endpoint being reachable, but the core signature-bypass technique requires no secret material.

### Recommendation
Include the `shop`, `topic`, `webhook_id`, and `api_version` header values in the HMAC-signed material (or otherwise cryptographically bind them to the body, e.g., by including them in a canonical string that gets HMAC-verified) so that `Utils::HmacValidator.validate` fails whenever any of these identity-bearing headers are altered, not just when the body changes.

### Proof of Concept
1. Attacker creates a free `attacker.myshopify.com` development store and installs the target public app (no privileged credentials needed).
2. Shopify sends the attacker a legitimately signed webhook, e.g.:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of body B>
   x-shopify-shop-domain: attacker.myshopify.com
   Body: B
   ```
3. Attacker resends the identical body `B` and identical `x-shopify-hmac-sha256` value, but changes the header:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only verifies `B` against the unchanged HMAC.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and invokes the handler, which now believes the (attacker-controlled) body `B` originated from `victim-shop.myshopify.com`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
