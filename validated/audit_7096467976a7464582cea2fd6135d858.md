## Title
Vetoing the latest EVM state-machine height resets `_latestStateMachineHeight` to a hardcoded `1` instead of the real prior height, reopening the ordering check to stale/incorrect commitments - (File: `evm/src/core/EvmHost.sol`)

### Summary
This is the same bug class as the Badger Citadel finding: a validation-invalidation action (`clearCitadelPriceFlag` / here, vetoing a state commitment) clears a guard without restoring the correct underlying value, so a later operation resumes using an incorrect/stale reference point rather than the true last-good state.

### Finding Description
When a fisherman detects a fraudulent L2 state and the Handler invokes `deleteStateMachineCommitment` → `deleteStateMachineCommitmentInternal`, the function deletes the bad commitment and, if it was the latest height, resets the height pointer to the literal constant `1` instead of the real previous legitimate height: [1](#0-0) 

Compare this with the equivalent Substrate/pallet-ismp implementation of the same operation, which correctly restores `PreviousStateMachineHeight` rather than an arbitrary constant: [2](#0-1) 

The `_latestStateMachineHeight` value is the sole ordering guard used by `HandlerV2.handleConsensus` to decide whether a newly delivered intermediate state (from a subsequent, unprivileged relayer-submitted consensus proof) may be stored as a state commitment: [3](#0-2) 

The check is simply `intermediate.height > latestHeight`. Once a veto resets `latestHeight` to `1`, this ordering guard is effectively disabled for every subsequent `handleConsensus` call on that state machine until a brand-new higher commitment is stored: any relayer can now get an intermediate state at *any* height greater than 1 accepted and persisted via `storeStateMachineCommitment`, including a stale, previously-superseded, or otherwise incorrect commitment that the ordering check would have correctly rejected had `_latestStateMachineHeight` been restored to the real prior legitimate height (as the Rust/pallet-ismp implementation does). This mirrors the Citadel bug precisely: the flag/guard is cleared, but the value that should back it (the true previous height) is not correctly restored, so a subsequent, permissionless action gets to shape state outside of the honest consensus-derived ordering.

### Impact Explanation
This breaks the ordering invariant that guarantees state commitments only move forward monotonically and only through validated consensus proofs. An attacker (or a relayer replaying old/valid-looking consensus proofs) can, after any veto of the latest height, get a stale/incorrect `StateCommitment` accepted at a height that would normally have been rejected as "not newer than latest." Because `StateCommitment`s are the basis for state membership/non-membership proofs used to process incoming requests and responses, forging or resurrecting an old, already-superseded commitment can lead to unsound state proofs being accepted, enabling forged message delivery/incorrect asset or state proofs downstream — a concrete path to unsound state commitment and consequent unauthorized message/app actions.

### Likelihood Explanation
Vetoes are a normal, expected, permissionless-adjacent operational event in Hyperbridge's fisherman design (any fisherman/collator can trigger one without heavy coordination, analogous to the Citadel policy-ops team's "nimble" flag-clearing power). Every time a veto targets the *current* latest height for an EVM destination host, the height pointer degrades to `1`, and the next `handleConsensus` call (submittable by any relayer) can then push through a commitment that should have failed the ordering check. No unusual coordination between consensus and the vetoing party is required — this is a straightforward, reachable sequence: veto → relayer submits any old/incorrect intermediate state above height 1 → `handleConsensus` accepts it.

### Recommendation
Track and restore the actual previous valid state-machine height on veto (as already done correctly in `modules/pallets/ismp/src/host.rs`'s `delete_state_commitment`, which keeps a `PreviousStateMachineHeight` mapping), instead of resetting `_latestStateMachineHeight` to the constant `1` in `deleteStateMachineCommitmentInternal`. Concretely, maintain a `_previousStateMachineHeight` mapping updated alongside `storeStateMachineCommitment`, and on veto of the latest height, roll `_latestStateMachineHeight` back to that tracked previous value rather than to `1`.

### Proof of Concept
1. Handler stores commitments at heights 100, 200, 300 for state machine `S` via successive `handleConsensus` calls; `_latestStateMachineHeight[S] = 300`.
2. A fisherman detects height 300's commitment is fraudulent and the Handler calls `deleteStateMachineCommitment({S,300}, fisherman)`.
3. Inside `deleteStateMachineCommitmentInternal`, since `_latestStateMachineHeight[S] == 300`, it is reset to `1` (not `200`, the real previous legitimate height). [4](#0-3) 
4. Any relayer now submits a consensus proof whose intermediate state includes a stale/incorrect commitment at, say, height 150 (which is less than the real previous height 200 and would have been rejected under correct bookkeeping).
5. `HandlerV2.handleConsensus`'s check `intermediate.height > latestHeight` (150 > 1) passes, so `storeStateMachineCommitment` persists this stale/incorrect commitment as authoritative state for height 150, and `_latestStateMachineHeight[S]` becomes 150 — a regression and acceptance of unvetted state. [5](#0-4)

	fn delete_state_commitment(&self, height: StateMachineHeight) -> Result<(), Error> {
		// The height's entry in the state commitment queue is deliberately left
		// behind; locating it would mean scanning the queue, which is the per-insert
		// cost the queue exists to avoid. Usually its eviction is a no-op, but when
		// the vetoed height is the latest the reset below re-opens it for honest
		// resubmission, and the resubmitted height gets a *second* queue entry. The
		// stale entry then evicts the live commitment when it reaches the head —
		// one insertion before the live entry would have, since the resubmission
		// lands directly behind its stale twin. So a veto costs that height one
		// insertion of retention and permanently burns one queue slot. Both are
		// negligible against the configured caps; making it exact would need a
		// height -> index map on the insert path.
		BoundedStateCommitments::<T>::remove(height.id, height.height);
		BoundedStateMachineUpdateTime::<T>::remove(height.id, height.height);

		// technically any state commitment can be vetoed,
		// safety check that it's the latest before resetting it.
		if let Some(latest) = LatestStateMachineHeight::<T>::get(height.id) {
			if latest == height.height {
				// Reset back to the initial height to allow for honest updates
				let prev_height =
					PreviousStateMachineHeight::<T>::get(height.id).ok_or_else(|| {
						Error::Custom("Previous state machine height should exist".to_string())
					})?;
				LatestStateMachineHeight::<T>::insert(height.id, prev_height);
			}
		}
		Ok(())
	}

        uint256 delay = block.timestamp - host.consensusUpdateTime();
        if (delay >= host.unStakingPeriod()) revert ConsensusClientExpired();

        bytes memory previousState = host.consensusState();
        (bytes memory verifiedState, IntermediateState[] memory intermediates, uint256 nextAuthoritySetId) =
            IConsensusV2(host.consensusClient()).verify(previousState, proof);

        if (keccak256(previousState) == keccak256(verifiedState)) return;
        host.storeConsensusState(verifiedState);

        uint256 intermediatesLen = intermediates.length;
        for (uint256 i = 0; i < intermediatesLen; i++) {
            IntermediateState memory intermediate = intermediates[i];
            uint256 latestHeight = host.latestStateMachineHeight(intermediate.stateMachineId);
            if (latestHeight != 0 && intermediate.height > latestHeight) {
                StateMachineHeight memory stateMachineHeight =
                    StateMachineHeight({stateMachineId: intermediate.stateMachineId, height: intermediate.height});
                host.storeStateMachineCommitment(stateMachineHeight, intermediate.commitment);
            }
        }
