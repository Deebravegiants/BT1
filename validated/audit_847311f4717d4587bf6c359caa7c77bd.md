## Title
Webhook `shop`/`topic`/`webhook-id` fields are trusted for tenant identity while excluded from HMAC verification, enabling cross-tenant webhook forgery — (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by HMAC-verifying the raw request body, then unconditionally trusts the `shop-domain`, `topic`, and `webhook-id` HTTP headers — none of which are covered by that signature — to build the `WebhookMetadata` handed to the app's handler.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery`, but its `to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from unauthenticated headers: [2](#0-1) 

`Registry.process` validates only the HMAC of that body and then immediately dispatches using the unverified `request.shop`/`request.topic`/`request.webhook_id`: [3](#0-2) 

The identity binding that should hold is: `shop that produced/HMAC-signed the body == shop the handler is told owns the data (WebhookMetadata#shop)`. Because Shopify webhook HMACs are computed with the app's single `client_secret`/`api_secret_key`, which is shared across *every* shop that installs the app (not per-tenant), any shop that has the app installed can legitimately obtain a `(body, hmac)` pair for content of its choosing. Nothing in `Request` or `Registry` binds that signature to the `shop-domain` header, so the header can be swapped to name a different (victim) shop while keeping the same, still-valid, body+HMAC pair.

### Impact Explanation
An unprivileged internet user who has installed the app on any shop they control (e.g. a free/dev store) can:
1. Trigger a webhook delivery for a topic/body they can predict or capture (or simply keep any legitimately-received `(raw_body, hmac)` pair from their own shop).
2. Replay that exact body and `X-Shopify-Hmac-Sha256`/`shopify-hmac-sha256` value directly to the app's public webhook endpoint, but with the `X-Shopify-Shop-Domain`/`shopify-shop-domain` header set to a victim shop.
3. `HmacValidator.validate` succeeds (it only checks the body bytes against the shared secret), and `Registry.process` calls the handler with `WebhookMetadata#shop` equal to the attacker-chosen victim domain.

Any host application that uses `data.shop` from the webhook handler to select/write tenant data, trigger tenant-scoped side effects, or otherwise route by shop identity is exposed to cross-tenant data injection/confusion — meeting the "cross-tenant access" bar for this analysis.

### Likelihood Explanation
Reaching this path requires no secrets, tokens, or privileged access — only that the attacker has (or can trivially obtain) the app installed on one shop, which is the normal onboarding flow for any Shopify app listed publicly. Crafting an HTTP POST with attacker-controlled headers and a captured body is trivial once a legitimate `(body, hmac)` pair from the attacker's own shop is observed.

### Recommendation
Bind the HMAC-covered signable content to the identity fields that the handler relies on: include the `shop-domain` (and ideally `topic`/`webhook-id`) header value in `to_signable_string`, or otherwise cryptographically bind the verified shop to a per-shop secret/session before trusting `request.shop` in `WebhookMetadata`. Alternatively, require host applications to cross-check `request.shop` against an authenticated, previously-established session/install record before acting on the webhook payload, and document this requirement clearly since the gem currently implies the value is trustworthy once `HmacValidator.validate` passes.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook topic the app subscribes to and capture the raw POST body `B` and its `shopify-hmac-sha256` value `H` (valid because it was computed by Shopify with the app's shared secret).
2. Send a new POST to the app's webhook endpoint with the same body `B` and header `shopify-hmac-sha256: H`, but set `shopify-shop-domain: victim.myshopify.com` (and desired `shopify-topic`/`shopify-webhook-id`).
3. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-199`) calls `Utils::HmacValidator.validate(request)`, which returns `true` because only `B` and `H` are checked.
4. The registered handler receives `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, causing the host app to process attacker-supplied data as if it belonged to `victim.myshopify.com`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
