### Title
Webhook HMAC does not bind the `shop`/`topic` headers to the signed body, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` — the fields the registry uses to decide *who* the webhook is for and *which handler* processes it — are read straight from unauthenticated HTTP headers. `Registry.process` validates only the body's HMAC and then dispatches using those unauthenticated header values, breaking the intended binding `hmac == HMAC(secret, body+shop+topic)`.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
only the raw body is included. Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled directly from headers with no signature coverage: [2](#0-1) 

`Registry.process` verifies only this body-scoped HMAC and then immediately trusts the unauthenticated header-derived fields to build the dispatched `WebhookMetadata` and select the handler: [3](#0-2) 

The identity binding that should hold is: `hmac` verifies `(body, shop, topic)` as a unit. Instead, only `hmac` verifies `body`; `request.shop` and `request.topic` are attacker-controlled HTTP headers that travel alongside a genuine, previously-observed `(body, hmac)` pair. An unprivileged internet user who has ever received one legitimate webhook from Shopify (e.g., by installing the app on their own trial/dev shop and triggering any subscribed webhook topic they registered) can capture a valid `raw_body` + `x-shopify-hmac-sha256` pair, then replay it directly to the app's webhook endpoint with a forged `x-shopify-shop-domain` (a victim shop) and/or forged `x-shopify-topic`/`x-shopify-webhook-id`. `HmacValidator.validate` in `Utils::HmacValidator` only recomputes the HMAC over `to_signable_string` (the body) and compares it — it never checks that the header-derived `shop`/`topic` match anything signed: [4](#0-3) 

This is confirmed by the registry test's `hmac` computation, which is derived from the body alone, independent of the headers set alongside it: [5](#0-4) 

### Impact Explanation
Any host application that relies on `WebhookMetadata#shop` (built from `request.shop`) to attribute incoming webhook data to a merchant/tenant — the documented and expected usage pattern of this gem's webhook API — can be tricked into processing attacker-supplied body content under a victim shop's identity, or triggering handlers for topics/webhook IDs the attacker chooses while reusing a genuinely-signed body. This is a cross-tenant confusion: data validated as "from Shopify" (via HMAC) is then attributed to an arbitrary tenant chosen by the requester, without any authentication of that attribution. This can corrupt or inject records into another merchant's tenant data, satisfying the Critical "cross-tenant access" impact criterion.

### Likelihood Explanation
Likelihood is moderate-to-high: obtaining one legitimate `(body, hmac)` pair only requires installing the target app on any shop (including the attacker's own free/dev store) and triggering a subscribed webhook — no privileged credentials, access tokens, or `api_secret_key` are needed. Replaying that pair with a different `shop`/`topic` header against the public webhook endpoint requires nothing more than a normal HTTP client.

### Recommendation
Include the `shop` (and ideally `topic`) header values in the string that is HMAC-verified, or independently authenticate the `shop` claim (e.g., cross-check it against a shop associated with the webhook subscription/session store) before using it to route or persist data. At minimum, document that `request.shop`/`request.topic` are unauthenticated and must not be trusted for tenant attribution without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and triggers a subscribed webhook topic (e.g. `orders/create`), capturing the raw POST body and the valid `x-shopify-hmac-sha256` header Shopify sent.
2. Attacker sends a POST to the app's webhook endpoint with the exact same `raw_body` and `x-shopify-hmac-sha256`, but sets:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: <any topic the app has a handler for>`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` (`lib/shopify_api/webhooks/registry.rb:190`), which succeeds because it only checks the body against the secret.
4. The handler receives `WebhookMetadata.new(topic: <attacker-chosen>, shop: "victim-shop.myshopify.com", body: <attacker's genuine body>, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the host app to act on attacker data as if it belonged to `victim-shop.myshopify.com`.
