### Title
Webhook `shop-domain` Header Not Covered by HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while the shop identity used by the application (`request.shop`) is read from the `X-Shopify-Shop-Domain` / `shopify-shop-domain` header, which is never included in the HMAC-signed material. `ShopifyAPI::Webhooks::Registry.process` validates only the body against the HMAC and then forwards the unverified `shop` header straight to the app's handler as the tenant identifier, breaking the identity binding `hmac_signed_bytes == full_request_identity(shop, topic, body)`.

### Finding Description
`Webhooks::Request#to_signable_string` is defined as: [1](#0-0) 

which returns only `@raw_body`. The `shop`, `topic`, and `webhook_id` accessors are populated straight from unauthenticated headers with no cryptographic binding to the signature: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC only over `to_signable_string` (i.e., the body) and compares it to the `hmac` header: [3](#0-2) 

`Webhooks::Registry.process` validates the HMAC and then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`) as the tenant identity passed to the host application's handler, with no additional check that the shop is the one that actually produced the signed body: [4](#0-3) 

Because only the body is bound to the HMAC, the equality that should hold — `hmac_verified(shop, topic, body) == shop_used_by_handler` — does not hold. An attacker who legitimately receives a signed webhook for their own shop (e.g., by installing the app on a store they control) possesses a byte-for-byte valid `(body, hmac)` pair. They can then replay that exact body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary victim `shopify-shop-domain` header. `HmacValidator.validate` still succeeds because it never inspects the header, and `Registry.process` hands the forged shop value to the handler as `WebhookMetadata.shop`.

### Impact Explanation
This is a cross-tenant identity binding break: data that is only proven to originate from the attacker's own shop (the signed body) gets attributed to an arbitrary victim shop identifier chosen by the attacker. Any host application logic that uses `WebhookMetadata#shop` to look up sessions, update records, or authorize per-tenant actions can be tricked into applying the attacker's payload to another merchant's tenant, i.e., cross-tenant access/data corruption — a Critical-impact class per the classification rules.

### Likelihood Explanation
Exploitation requires the attacker to (1) install the app on a store they control (or otherwise obtain one legitimately signed webhook body+HMAC pair for any topic used by the target app) and (2) send an HTTP POST to the app's public webhook endpoint with the captured body/HMAC but an attacker-chosen `shopify-shop-domain` header. Both steps are achievable by any unprivileged internet user/merchant without needing `api_secret_key`, access tokens, or TLS interception, since the webhook endpoint is a public HTTP endpoint by design and the gem performs no header-to-signature binding.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) as part of the signed material verified by `HmacValidator`, or independently verify that `request.shop` corresponds to a shop actually associated with the delivered webhook (e.g., cross-check against Shopify's per-shop webhook secrets if using per-shop rotation, or validate the header against an out-of-band trusted source) before invoking the handler with that shop value.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com`; capture a legitimately delivered webhook request, including its raw body and valid `shopify-hmac-sha256` header.
2. Replay the exact same raw body and HMAC header to the app's webhook endpoint, but change the `shopify-shop-domain` header to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate` returns `true` because it only checks the body against the HMAC: [5](#0-4) 
4. `Registry.process` invokes the handler with `shop: request.shop` set to `"victim-shop.myshopify.com"`, even though the signed body originated from the attacker's shop: [6](#0-5)
