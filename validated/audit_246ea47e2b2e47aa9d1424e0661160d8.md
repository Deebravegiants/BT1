### Title
`exchangeRate()` failure on the reserve LT permanently freezes both buy and sell — not just buy, as the documented mint-pause tradeoff assumes - (File: packages/contracts/src/Bonding.sol, packages/contracts/src/Zap.sol)

### Summary
The bonding-curve's graduation check `Bonding.canGraduate()` unconditionally calls the reserve LT's `exchangeRate()` view whenever the curve still has unsold supply. Both `Zap.buy` and, critically, `Zap.sell` call this check before executing a trade. If the LT's `exchangeRate()` ever reverts, every buy **and every sell** for tokens paired to that LT reverts too — contradicting the protocol's own documented design intent that sells stay available even when the LT is impaired.

### Finding Description
`Bonding.canGraduate()` reads the LT's live price via `exchangeRate()` on the USD trigger leg: [1](#0-0) 

This function is called unconditionally at the start of every sell in `Zap._sellInternal`, before the curve/redeem path even begins: [2](#0-1) 

It is also called (indirectly, via `Bonding.previewLtUntilGraduation`, which likewise reads `exchangeRate()`) on every curve buy in `Zap._executeBuy`: [3](#0-2) [4](#0-3) 

`IBounceLeveragedToken.exchangeRate()` is a plain external view with no staleness/failure handling anywhere in `alt.fun`'s contracts — there is no `try/catch`, cached fallback, or circuit breaker around any of these calls. The codebase explicitly documents an *accepted* asymmetric-degradation design for BounceTech's mint-pause (`Zap.sol` around `_executeBuy`), where buys DoS but sells keep working "since holders can still exit to USDC": [5](#0-4) 

That accepted tradeoff is broken by the `exchangeRate()` dependency: because `canGraduate()` is on the mandatory pre-check path of `_sellInternal`, an `exchangeRate()` failure (BounceTech pausing/bricking the rate feed, an upgrade window, or any other transient revert on that view) blocks sells too, not just buys — for any curve token whose pair still has `tokenBalance() != 0` (i.e., virtually always, except a fully sold-out curve). This is a stronger, previously-unaccounted-for freeze than the one the codebase's own comments claim is impossible ("holders can always exit via `redeem`").

### Impact Explanation
While the LT's `exchangeRate()` reverts:
- `Zap.buy` reverts for every non-graduated token on that LT (via `previewLtUntilGraduation`).
- `Zap.sell` also reverts for every non-graduated token on that LT (via `canGraduate`'s USD leg), unless the curve happens to be fully sold out (`tokenBalance() == 0`).

This traps trader funds already committed to the curve — they can neither buy nor exit to USDC — for the duration of the oracle/rate outage, directly contradicting the protocol's stated exit-guarantee ("holders can always exit via `redeem`", `Bonding.sol` graduation comments). This matches the report's impact class: a single dependency (price/rate feed) going unavailable makes a core user-facing function ("rebalance"/exit path here) permanently unusable while the outage persists, and — unlike the documented mint-pause tradeoff — leaves users with no fallback exit route at all.

### Likelihood Explanation
BounceTech LTs are explicitly documented in this codebase as capable of pausing/degrading (`mint`-pausable per `Zap.sol` comment, and "Retired LTs" freezing `exchangeRate` tracking per `docs/contracts-scope.md`). A view reverting outright (vs. returning a stale/frozen value) during an emergency pause, upgrade, or de-registration event is a realistic operational state for an external dependency the protocol has no control over, and every trade on an affected token routes through this unguarded call.

### Recommendation
Decouple the sell path from `exchangeRate()`-dependent `canGraduate()` checks — e.g., gate the "sell triggers graduation instead" branch behind a `try/catch` around `canGraduate()` (or split `canGraduate` into a supply-only check plus a separately-guarded USD check) so that an `exchangeRate()` revert falls back to allowing the ordinary `redeem`-based sell rather than blocking the trade entirely. Buys can retain the existing accepted DoS tradeoff, but sells — the user's only exit route — should not share the same unguarded external-call failure mode.

### Proof of Concept
1. Launch a token on the curve against LT `L`, buy some tokens so `tokenBalance() != 0` (curve not fully sold out).
2. Have `L.exchangeRate()` revert (e.g., BounceTech pauses the rate feed / a keeper-only checkpoint state / any operational condition on the live LT that reverts the view — mirrored in tests via `MockLeveragedToken`, though the mock currently has no revert mode).
3. Call `Zap.sell(tokenAddress, tokenAmount, minUsdcOut)` as any holder: `_sellInternal` calls `bonding_.canGraduate(tokenAddress)` at line 430, which calls `IBounceLeveragedToken(info.ltAddress).exchangeRate()` at `Bonding.sol:693` and reverts.
4. Every sell (and buy) for this token now reverts for as long as `exchangeRate()` fails, with holders unable to redeem out of the position.

    function canGraduate(
        address token_
    ) public view returns (bool) {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[token_];
        if (info.creator == address(0)) return false;
        if (info.lifecycle != Lifecycle.Curve) return false;

        address pair = info.pair;
        if (IPair(pair).tokenBalance() == 0) return true;

        (, uint256 assetReserve) = IPair(pair).getReserves();
        uint256 realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair);

        return valueUsd >= $.graduationThresholdUsd;
    }
