### Title
Webhook `shop`, `topic`, `webhook-id`, and `api-version` headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives its HMAC-signable payload solely from the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values used by the application are read directly, unauthenticated, from HTTP headers. `ShopifyAPI::Webhooks::Registry.process` only verifies the body's HMAC and then trusts these header-derived fields — most critically `shop`, which downstream applications use as the tenant identifier — breaking the binding: `shop-domain header used for tenant dispatch == shop bytes covered by HMAC`.

### Finding Description
The signable string for a webhook request is defined as: [1](#0-0) 

Only `@raw_body` is signed. All identity/routing fields are pulled straight from headers with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` validates only this body-bound HMAC, then immediately trusts `request.shop` as the tenant identity passed to the app's handler: [3](#0-2) 

Because the webhook signing secret (`Context.api_secret_key`, the app's `client_secret`) is the same for every shop that has installed the app, a merchant who installs the target app on their own store can legitimately receive a webhook with a body they influence (many webhook topics, e.g. `products/update`, `customers/update`, echo attacker-supplied field values) and a valid `x-shopify-hmac-sha256` for that exact body. Since the HMAC never covers `x-shopify-shop-domain`, the attacker can replay the identical `raw_body`/`hmac` pair to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop that also has the app installed. `HmacValidator.validate` still returns `true` because it only recomputes the signature over `to_signable_string` (the raw body): [4](#0-3) 

The application then processes the forged event as if it genuinely originated from the victim shop, since `WebhookMetadata.shop` is populated from the unauthenticated header: [5](#0-4) 

### Impact Explanation
This crosses a tenant boundary: an attacker-controlled webhook payload can be attributed to a victim merchant's shop domain purely by header manipulation, since `shop` is never part of the signed bytes. Any host application that uses `WebhookMetadata#shop` to select tenant records, refresh caches, or trigger tenant-scoped side effects (a common integration pattern with this gem) can be tricked into acting on/for the wrong tenant — i.e., cross-tenant access/confusion driven entirely by unauthenticated header data.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate merchant of the same app (a normal, unprivileged install available to any internet user who installs a public/embedded Shopify app), and that at least one accepted webhook topic includes attacker-influenceable body content or a predictable body they can capture and replay with a different shop header. No access token, `client_secret`, or privileged account is required beyond what any installer of the app already has.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the value that is HMAC-verified, or otherwise cryptographically bind the shop-domain header to the signed body before trusting it (e.g., validate that the receiving endpoint/shop context matches the header, and treat `shop`/`topic` as untrusted until independently confirmed against a known session/tenant record before dispatching to handlers).

### Proof of Concept
1. Install the target Shopify app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g., `products/update`) with attacker-chosen values.
2. Capture the resulting `raw_body` and its valid `x-shopify-hmac-sha256` (computed with the shared `api_secret_key`), as constructed in the existing test fixtures: [6](#0-5) 
3. Resend that identical body/HMAC pair to the app's webhook endpoint, but replace `x-shopify-shop-domain` with `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which still succeeds because only `raw_body` is signed: [7](#0-6)  — the handler now receives `WebhookMetadata` with `shop: "victim.myshopify.com"` even though the payload never originated from that shop.
