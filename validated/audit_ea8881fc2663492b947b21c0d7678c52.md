### Title
Fee-on-transfer / balance-skimming underlying tokens can permanently drain `WrappedHyperFungibleToken`'s escrow, freezing later bridge withdrawals - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`WrappedHyperFungibleToken.send()` dispatches a cross-chain message promising `params.amount` of the underlying token will be released on the destination side, but it only actually escrows whatever the ERC20 `safeTransferFrom` call happens to deliver. If the configured `_underlying` token takes a fee, rebases down, or otherwise delivers less than the nominal transfer amount, the contract's real balance falls below what it has cumulatively promised to unlock, and a subsequent legitimate `onAccept` unlock for a different user reverts for insufficient balance — the same failure mode as the JUSDBank/JUSDExchange report, where the app relies on a pre-funded/self-accounted balance that isn't guaranteed to match what it must pay out.

### Finding Description
In `send()`, the contract escrows tokens with `safeTransferFrom` and then unconditionally builds the cross-chain `Message` with `amount: params.amount` — it never checks the actual balance delta received: [1](#0-0) 

On the destination side (or on this same contract for a returning message), `onAccept` transfers out exactly `message.amount` of the underlying token from the contract's own balance: [2](#0-1) 

The same "transfer the full nominal amount out of contract balance" pattern is repeated for the timeout refund path: [3](#0-2) 

Because `send()` never verifies that the amount actually received equals `params.amount`, any underlying ERC20 that:
- charges a transfer fee (deflationary/fee-on-transfer tokens),
- has a rebasing/negative-yield balance mechanic, or
- is otherwise non-standard in its `transferFrom` accounting,

will cause the contract's real token balance to be strictly less than the sum of all `amount`s it has promised across dispatched `Sent` messages. This mismatch is silent — no revert occurs at send time — and accumulates with every such transfer.

Once the shortfall exceeds the contract's actual balance, the next `onAccept` (unlocking funds for some *other*, unrelated user whose funds were legitimately locked/burned on the counterpart chain) will revert in `safeTransfer` due to insufficient balance. Because ISMP relayers cannot forge a way around this — the underlying transfer genuinely fails — that user's funds are locked on the source chain (already burned/escrowed there) but can never be released here, i.e. a permanent freeze of funds for an entirely innocent party, triggered by an unrelated user's earlier `send()`.

### Impact Explanation
This is a Medium/High-severity freezing-of-funds bug: a single unprivileged `send()` call (by any user, including a griefer) using a non-standard underlying token can permanently prevent other users from redeeming their legitimately bridged funds, because the escrow contract's on-chain balance no longer backs its accounting 1:1. This mirrors the reported JUSDBank/JUSDExchange class of bug — an operation that should always succeed (paying out from what should be a fully-backed pool) reverts because the contract ran out of the token it needs to pay out, and there is no protocol-level mechanism (mint-on-demand, minting authority, or balance reconciliation) to recover.

### Likelihood Explanation
Likelihood depends on the token chosen as `_underlying` by the deploying owner. For plain, standards-compliant ERC20 tokens (the common case), this issue does not manifest, which somewhat limits likelihood. However, deploying `WrappedHyperFungibleToken` for any fee-on-transfer, deflationary, or otherwise non-strictly-conforming ERC20 (a category of tokens that does exist and is sometimes wrapped for bridging) makes this trivially and repeatedly triggerable by any user simply calling `send()`, with no special privileges required.

### Recommendation
In `send()`, measure the actual balance delta of `_underlying` before and after the `safeTransferFrom` call and use that measured amount (rather than the caller-supplied `params.amount`) when building the dispatched `Message`. Alternatively, explicitly document and enforce (e.g., via a `IERC20Metadata` allow-list check or a constructor/`configure` assertion) that only standard, non-fee-on-transfer, non-rebasing tokens may be used as `_underlying`, and consider tracking total outstanding escrowed liabilities on-chain so a shortfall can be detected/paused before it causes an unrelated user's withdrawal to revert.

### Proof of Concept
1. Owner deploys `WrappedHyperFungibleToken` and calls `configure()` with `_underlying` set to a fee-on-transfer ERC20 (e.g., a token that burns 1% on every `transfer`/`transferFrom`).
2. User A calls `send(params)` with `amount = 1000`. `safeTransferFrom` moves only 990 tokens into the contract (10 burned as fee), but the dispatched `Message.amount` is still encoded as `1000`.
3. This repeats for several other users; the contract's real underlying balance is now cumulatively short of the total amount it has promised across all in-flight/failed messages.
4. User B's earlier cross-chain transfer (burned/escrowed on the counterpart chain for `amount = X`) is delivered via a valid POST request and reaches `onAccept`. `IERC20(_underlying).safeTransfer(beneficiary, message.amount)` reverts because the contract's actual balance is now less than `message.amount`.
5. User B's funds are stuck: already consumed on the source chain, unrecoverable here since the delivery message will keep reverting on redelivery, and no protocol path exists to mint or otherwise make up the shortfall. [4](#0-3)

    function send(HyperFungibleToken.SendParams calldata params) external payable whenNotPaused {
        uint256 msgValue = msg.value;
        if (_isWeth && msgValue >= params.amount) {
            msgValue = msgValue - params.amount;
            IWETH(_underlying).deposit{value: params.amount}();
        } else {
            IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
        }

        DispatchPost memory request = _buildDispatchPost(params);
        bytes32 commitment;
        if (msgValue > 0) {
            commitment = IDispatcher(_host).dispatch{value: msgValue}(request);
        } else {
            commitment = dispatchWithFeeToken(request);
        }

        emit Sent({
            from: msg.sender,
            to: params.to,
            dest: string(params.dest),
            amount: params.amount,
            commitment: commitment
        });
    }

     * @dev Called by the ISMP host when a POST request is received. Verifies the source
     * address matches the configured contract for that chain, then transfers the underlying
     * ERC20 to the recipient. If calldata is present, executes it via the CallDispatcher.
     * @param incoming The incoming POST request containing the token transfer message

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);

        HyperFungibleToken.Message memory message = abi.decode(incoming.request.body, (HyperFungibleToken.Message));

                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(refundee, message.amount);
            }

            IERC20(_underlying).safeTransfer(refundee, message.amount);
        }
