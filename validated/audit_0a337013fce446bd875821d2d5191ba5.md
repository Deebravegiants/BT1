### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies webhooks using only the raw request body, while the `shop` (tenant) field the handler relies on to route the event is taken from an unauthenticated HTTP header, breaking the binding `hmac(signed bytes) == hmac(bytes trusted for tenant identity)`.

### Finding Description
`Registry.process` validates a webhook solely with `Utils::HmacValidator.validate(request)`, then immediately trusts `request.shop` as the tenant identifier and passes it straight into the handler: [1](#0-0) 

`HmacValidator.validate` recomputes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` field: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns **only the raw body** — the `shop`, `topic`, `webhook_id`, and `api_version` values (all sourced from HTTP headers) are excluded from the signed material entirely: [3](#0-2) 

So the cryptographic check only proves "this body was produced by Shopify using the app's `client_secret`"; it proves nothing about which shop the header claims to be from. `WebhookMetadata.shop` — the field host applications use to key session/tenant lookups — is populated directly from this unauthenticated header: [4](#0-3) [5](#0-4) 

This is structurally the same class of bug as the reported `ClaggBaseAdapter.sol` issue: a state/identity field (`shop`, analogous to the incentive-token/round state) is acted upon (routing/tenant binding) without being covered by the same integrity check (HMAC) that gates the rest of the action, letting attacker-controlled, unverified bytes drive privileged tenant-scoped behavior.

### Impact Explanation
Because the `client_secret` used to sign webhooks is shared per app across all shops that install it, any merchant who has installed the app receives genuinely Shopify-signed webhooks for their own store with a valid HMAC over the body. That merchant can replay the exact same body+HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain. The HMAC check still passes (it never looked at the header), and the host application's handler receives `WebhookMetadata` claiming the event belongs to the victim shop. If the host app uses `data.shop` to select the session/access token or to trigger tenant-scoped side effects (common pattern, e.g. `orders/create`, `app/uninstalled`), this results in cross-tenant confusion/injection of forged events attributed to another merchant's shop — a boundary the gem is expected to guarantee is authentic.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate installer of the same app (unprivileged relative to other tenants) and be able to send an HTTP POST to the app's public webhook endpoint with attacker-chosen headers — no access to `api_secret_key`, access tokens, or the victim's credentials is needed. This satisfies the "unprivileged internet user" bar and the cross-tenant impact criterion.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the signed material verified by `to_signable_string`, or otherwise cryptographically bind the shop domain to the payload before trusting it (e.g., require host apps to cross-check `request.shop` against a shop already known/authorized via a prior OAuth session, and document this requirement explicitly). At minimum, `HmacValidator` should verify the full set of fields the application will treat as authenticated, not just the body.

### Proof of Concept
1. Attacker installs the vulnerable app on `attacker-shop.myshopify.com` and triggers a real event (e.g., updates a product), causing Shopify to POST a genuinely-signed webhook to the app's endpoint:
   - Headers: `x-shopify-topic: products/update`, `x-shopify-hmac-sha256: <valid HMAC over body>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - Body: `{...attacker's product payload...}`
2. Attacker captures this raw request (body + valid `hmac-sha256` header).
3. Attacker resends the identical body and `hmac-sha256` header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `@raw_body` against the HMAC — the forged `shop-domain` header is never validated: [6](#0-5) 
5. `Registry.process` builds `WebhookMetadata.new(..., shop: request.shop, ...)` using the forged `victim-shop.myshopify.com` value and invokes the host application's handler with it as if Shopify itself attested to that shop: [7](#0-6)

          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
