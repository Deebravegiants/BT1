This confirms the vulnerability: the `Webhooks::Request#shop` value (`shop-domain` header) is trusted and passed directly into `WebhookMetadata` for handler dispatch, while the HMAC in `Utils::HmacValidator.validate` only ever covers `to_signable_string`, which returns `@raw_body` — the shop-domain header is never part of the signed material.

### Title
Webhook shop-domain header is not bound to the HMAC signature, enabling cross-tenant webhook impersonation - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` but its `to_signable_string` returns only the raw HTTP body [1](#0-0) , while the `shop` (and `topic`, `webhook_id`, `api_version`) values are read directly from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates only the body's HMAC and then forwards `request.shop` straight to the app's webhook handler as the tenant identifier [3](#0-2) .

### Finding Description
The binding that should hold is: `hmac(secret, signed_bytes) == received_hmac` where `signed_bytes` must equal the tenant-identifying bytes actually acted upon (`shop`). Here, `signed_bytes = raw_body` but `acted_on_field = shop-domain header`, so the equality `signed_bytes == acted_on_bytes` never holds — the shop identity is completely outside the cryptographic envelope.

Any body+HMAC pair that is valid for the app's shared `api_secret_key` (the same secret is used for every shop on the app, not a per-shop secret — see `HmacValidator.validate`/`Context.api_secret_key` usage in `lib/shopify_api/utils/hmac_validator.rb`) remains valid no matter what `shop-domain` header accompanies it. An attacker who can obtain one genuinely-signed `(body, hmac)` pair for the app — trivially possible by installing the app on their own store and triggering a webhook with attacker-chosen body content (e.g. renaming a product, editing an order note, or using a topic whose payload is attacker-controlled) — can then replay that exact body and HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `Request#shop` will report the victim's domain, `Utils::HmacValidator.validate(request)` will still pass because it never inspects the header, and `Registry.process` will hand the attacker-controlled body to the handler tagged as originating from the victim shop [4](#0-3) .

### Impact Explanation
This is a cross-tenant identity confusion: the host application's webhook handler will process attacker-supplied data believing it came from a different merchant's shop. Depending on how the host app uses `WebhookMetadata#shop` (e.g., to look up that shop's session/access token, to update per-shop cached data, or to trigger `shop/redact`-style flows), this can lead to cross-tenant data corruption or to the app performing actions against the wrong tenant's stored session/access token — satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
The only prerequisite is installing the app on any shop (including one the attacker controls) and capturing one legitimately-signed webhook — no leaked secrets, no privileged access, and no interaction with `api_secret_key` are required, since the app secret is never exposed to the attacker; they just reuse a signature Shopify computed for them on their own data.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook_id`) header values in the signable material verified by the HMAC, or independently cross-check the header-derived `shop` against a shop identity embedded in and covered by the signed payload (e.g., verify the resolved shop against a previously-stored, per-shop webhook secret or the shop found inside the signed JSON body) before dispatching to the handler in `Registry.process`.

### Proof of Concept
1. Install the target app on attacker-owned store `attacker.myshopify.com`; scope-permitting, trigger any webhook whose payload the attacker can influence (or capture any legitimate webhook delivered to their own endpoint).
2. Note the exact `raw_body` and the resulting `X-Shopify-Hmac-Sha256` header value — valid for the shared `api_secret_key`.
3. Send a new POST to the app's webhook endpoint with the identical `raw_body` and `X-Shopify-Hmac-Sha256`, but set `X-Shopify-Shop-Domain: victim.myshopify.com` and desired `X-Shopify-Topic`.
4. `Webhooks::Request.new` accepts it (all required headers present) [5](#0-4) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the HMAC [6](#0-5) ; the handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and attacker-controlled `body`.
