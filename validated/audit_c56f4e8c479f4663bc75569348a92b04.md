### Title
Webhook `shop-domain` Header Is Not Covered by HMAC Verification, Enabling Cross-Tenant Shop Identity Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so `Utils::HmacValidator.validate` cryptographically authenticates the webhook payload bytes but never binds that authentication to the `shop-domain` (or `topic`/`webhook-id`/`api-version`) HTTP header. `Registry.process` nevertheless takes `request.shop` straight from that unauthenticated header and hands it to the app's webhook handler as the tenant identity.

### Finding Description
The identity binding that should hold is:
`HMAC_valid(raw_body, secret) == true` should imply `shop-domain header == the shop that actually sent this exact body`.

In this gem that equality is broken:

- `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
- `Request#shop` is read from an attacker-controllable header (`shopify-shop-domain` / `x-shopify-shop-domain`) that is never included in the signable string: [2](#0-1) 
- `HmacValidator.validate`/`validate_signature` only recomputes the HMAC over `to_signable_string` (i.e., the body) and compares it to the `hmac-sha256` header: [3](#0-2) 
- `Registry.process` gates on that same body-only HMAC check and then forwards the unauthenticated `request.shop` (and `topic`/`webhook_id`/`api_version`) to the handler as trusted tenant metadata: [4](#0-3) 

Because HMAC verification only proves "this body byte-sequence was signed by Shopify with our secret at some point," it does not prove which shop the body was signed for. Any HTTP client can supply any `shop-domain` header value alongside a body+HMAC pair that was legitimately generated for a *different* shop, and `process` will accept it, since `Errors::InvalidWebhookError` is only raised when the body/HMAC pair itself doesn't match — not when the shop header is inconsistent with the signed content.

### Impact Explanation
This breaks the tenant-authentication boundary the gem is documented to provide. The doc for `Registry.process` explicitly tells integrators: "This will verify the request did indeed come from Shopify," implying the shop it attributes to the webhook is trustworthy: [5](#0-4) . Handler implementations are told `data.shop` is "The shop domain of the webhook" and commonly use it to key per-tenant lookups/DB writes/job enqueuing: [6](#0-5) . An attacker who controls (or has previously observed) any valid `(raw_body, hmac)` pair — e.g. from webhooks sent to their own shop for a topic they registered — can replay that exact body/HMAC to the app's public webhook endpoint while substituting an arbitrary victim `shop-domain` header. The gem will report the webhook as authenticated and hand the attacker-chosen body to the handler labeled as belonging to the victim shop, enabling cross-tenant data confusion/corruption in the host application (impact class: cross-tenant access).

### Likelihood Explanation
The webhook endpoint is a public, unauthenticated HTTP endpoint by design (Shopify calls it directly), so any internet user can send arbitrary headers and bodies to it — no credentials are required to attempt the spoof itself. The attacker only needs one legitimate `(raw_body, hmac)` pair, which they can obtain trivially by installing the target app on their own store and registering for any webhook topic supported by that app, then replaying the captured payload with a forged shop header. No secret key or access token needs to be leaked.

### Recommendation
Include the shop identity (and topic/webhook id, if used for handler dispatch) in the HMAC-signable material for webhooks, or otherwise cryptographically bind the `shop-domain` header to the signed body before trusting it in `Registry.process`/`WebhookMetadata`. At minimum, document that `data.shop` in the webhook handler is unauthenticated relative to the HMAC and must not be used to select tenant scope without an independent trust check (e.g., cross-referencing against the shop stored for the resource ids in the body).

### Proof of Concept
1. App registers `orders/create` webhook handling with `ShopifyAPI::Webhooks::Registry` per the documented pattern.
2. Attacker installs the same app on `attacker-shop.myshopify.com`, triggers `orders/create`, and captures the resulting `raw_body` and `shopify-hmac-sha256` header sent by Shopify (this is a legitimate signed payload for the attacker's own shop).
3. Attacker POSTs to the app's webhook endpoint reusing that exact `raw_body` and `hmac-sha256` value, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `raw_body` — [1](#0-0)  and [7](#0-6)  — and passes.
5. The handler is invoked with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker's order data>, ...)` — [8](#0-7)  — causing the app to process attacker-controlled data under the victim shop's identity.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
