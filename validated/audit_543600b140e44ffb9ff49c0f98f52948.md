### Title
Unsanitized `shop` domain from webhook headers is trusted for identity/dispatch while HMAC only signs the raw body - ([File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so the HMAC verification performed by `HmacValidator.validate` in `Registry.process` [2](#0-1)  only proves that the *body bytes* were signed by Shopify with the app's secret. The `shop` value, read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header [3](#0-2) , is never part of the signed material and is never passed through `Utils::ShopValidator.sanitize!` (the trusted-domain allowlist check used elsewhere, e.g. in `ClientCredentials`, `RefreshToken`, and `TokenExchange.migrate_to_expiring_token`) [4](#0-3) [5](#0-4) . `Registry.process` passes this unvalidated header value straight into `WebhookMetadata` and the handler as the tenant identity: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` [6](#0-5) .

### Finding Description
The binding that should hold is: `shop` identity used by the handler == `shop` that is cryptographically bound to the authenticated webhook delivery. Instead, the gem verifies `hmac(raw_body, secret) == received_hmac`, but `shop` is read from a separate, unauthenticated header and handed to the application's webhook handler unchanged, with no sanitization against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`. This is the same class of bug as the report: an "amount acted on" (or in this case, "identity acted on") that isn't covered by the same authentication check as the payload it's associated with — bytes verified (raw body) vs. bytes/fields actually used (the shop header) diverge.

Any request that carries a body/HMAC pair that legitimately validates (e.g., a topic the app handles, replayed or crafted by anyone who can produce a body Shopify would sign — including via SSRF-adjacent replay of a previously captured legitimate webhook, or more directly, any request where the attacker can influence headers independently of the signed body on a shared/misconfigured ingress) can carry an arbitrary `shop-domain` header value. Because this value is used as the tenant key passed to the app's handler without validation, a webhook whose body was legitimately signed for shop A can be delivered/re-labeled as belonging to shop B purely by changing the header, since the header is outside the HMAC's scope.

### Impact Explanation
If exploited, this allows cross-tenant confusion: a webhook payload can be attributed to a shop domain that was never cryptographically bound to that payload, letting an attacker who can influence headers (e.g., a compromised intermediary, or by capturing/replaying webhook bodies for their own shop but relabeling the domain) cause the host application to act on data under another tenant's identity. This matches the "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is moderate: the attacker needs the ability to submit an HTTP request to the app's webhook endpoint with a controlled `shop-domain` header alongside a body/HMAC pair that validates for some topic (which they can obtain, e.g., from their own shop's legitimate webhook deliveries, since HMAC only covers the body, not the shop). No access token, `api_secret_key`, or privileged account is required — only network access to the app's public webhook endpoint, which is the intended entry point for an "unprivileged internet user."

### Recommendation
Bind `shop` to the HMAC-signed material, e.g., include the `shop-domain` header value in `to_signable_string` (as part of a canonical signed string) or otherwise cryptographically bind it before use, and additionally validate `request.shop` through `Utils::ShopValidator.sanitize!` before it is passed to `WebhookMetadata`/handlers, consistent with how `ClientCredentials`, `RefreshToken`, and `TokenExchange.migrate_to_expiring_token` already validate shop domains.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` and captures a legitimate webhook delivery (raw body + valid `x-shopify-hmac-sha256`) for a topic the app handles (e.g., `orders/create`).
2. Attacker replays the exact same raw body and HMAC to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `HmacValidator.validate` succeeds because only `@raw_body` is checked [1](#0-0) .
4. `Registry.process` invokes the handler with `shop: "victim-shop.myshopify.com"` [6](#0-5) , causing the host application to process attacker-controlled order data under the victim's tenant identity.
