Based on my analysis, the webhook processing path in this gem exhibits exactly the identity-binding gap described in the rules: a field acted on (the `shop` domain used to route/attribute webhook data) but not covered by the HMAC.

### Title
Webhook Shop-Domain Header Is Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then unconditionally trusts the `shop` (and `topic`/`webhook_id`) values taken from HTTP headers when constructing `WebhookMetadata` and dispatching it to the app's handler.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` header using a secure comparison: [1](#0-0) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` — it does not include `shop`, `topic`, `webhook_id`, or `api_version`, all of which are read directly and exclusively from unauthenticated HTTP headers: [2](#0-1) 

`Registry.process` performs only this body-HMAC check, and then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`) to build `WebhookMetadata` handed to the app's registered handler: [3](#0-2) 

Because the HMAC only binds the raw body bytes and never binds them to the `shop-domain` header, an attacker who legitimately installs the app on their own shop can capture a genuinely-signed webhook (valid body + valid HMAC, since the HMAC uses the shared `client_secret` common to the whole app, not per-shop), then replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary victim `shop-domain` header. `HmacValidator.validate` will still succeed (it never inspects the header), yet `WebhookMetadata#shop` will report the attacker-chosen victim shop. This is the "field acted on but not covered by the HMAC" binding break: the equality the code implicitly assumes — `shop header == shop the signed payload actually originated from` — does not hold and is never checked.

### Impact Explanation
If the host application (as is standard practice, and as this library's own `WebhookMetadata.shop` field encourages) uses `shop` to select the tenant/session/store record to update (order status, inventory, redact/GDPR compliance flows, etc.), an attacker can inject attacker-controlled body content attributed to an arbitrary victim shop domain, achieving cross-tenant data corruption/injection without ever possessing the victim's credentials or access token. This satisfies the Critical "cross-tenant access" bar, since a party authenticated only as themselves (their own shop's valid webhook) can act as/write into any target shop.

### Likelihood Explanation
Any developer/merchant who installs the app on their own store can generate a legitimately-signed webhook payload+HMAC at will (e.g. by triggering an event on their own shop), then replay it with a forged `shop-domain` header — no secrets, tokens, or network position beyond normal internet access are required. This is a self-service, repeatable, unprivileged attack path fully within the described threat model.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) as part of the signable payload bound by the HMAC, or explicitly verify that the `shop-domain` header value matches an app-side record of the currently-authenticated/subscribed shop before constructing `WebhookMetadata`, rather than trusting the header outright once only the body signature has been checked.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook: body `B`, header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, header `X-Shopify-Hmac-Sha256: H = HMAC-SHA256(secret, B)`.
2. Attacker sends a new HTTP request to the app's webhook endpoint with the same body `B` and same `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Webhooks::Request#hmac` reads `H` from the header; `to_signable_string` returns `B`; `HmacValidator.validate` recomputes `HMAC-SHA256(secret, B)` and it matches `H` — validation passes ( [4](#0-3) ).
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: ..., ...)` and dispatches it to the app's handler, which processes attacker-controlled data as if it originated from the victim shop ( [5](#0-4) ).
