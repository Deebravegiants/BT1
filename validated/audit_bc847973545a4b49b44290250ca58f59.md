### Title
Webhook Shop-Domain Header Is Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the `shop` value pulled from an unauthenticated HTTP header when building the `WebhookMetadata` passed to the app's handler. Because the tenant-identifying `shop` field is never included in the signed material, any party who can produce (or replay) a body/HMAC pair valid for the secret can attach an arbitrary `shop-domain` header, causing the handler to process the webhook as belonging to a different merchant than the one the body was actually signed for.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` header using a constant-time comparison: [1](#0-0) 

For webhooks, `Webhooks::Request#to_signable_string` returns only the raw JSON body — nothing else: [2](#0-1) 

Meanwhile, `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from HTTP headers with no cryptographic binding to the body or to the HMAC: [3](#0-2) 

`Registry.process` only re-checks the HMAC (which, as shown, verifies the body only) before dispatching to the registered handler with the header-derived `shop`: [4](#0-3) 

The resulting `WebhookMetadata.shop` is exactly the unauthenticated header value: [5](#0-4) 

The identity binding that should hold is:
`hmac-authenticated bytes == bytes the handler uses to determine tenant (shop)`

Because `shop` is outside the signed payload, this equality does not hold. An unprivileged actor who can obtain any single valid `(raw_body, hmac)` pair for the app's secret — trivially available to them by installing the app on their own shop and receiving one genuine webhook delivery for their own tenant — can resend that exact body/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` (or `x-shopify-shop-domain`) header with any other shop domain (e.g., a victim merchant's domain). `HmacValidator.validate` will still pass because it never inspects the headers, and `Registry.process` will invoke the app's handler believing the event originated from the spoofed shop.

### Impact Explanation
This is a cross-tenant confusion primitive reachable without the app's `api_secret_key`, an access token, or any privileged account — the attacker only needs one legitimate webhook of their own. If the host application uses `WebhookMetadata#shop` to key session/credential lookups, tenant-scoped data writes, deduplication, or trust decisions (a documented, expected usage pattern per `docs/usage/webhooks.md`), the attacker can make the app attribute attacker-controlled event data to a victim shop, corrupting tenant-scoped state or triggering shop-specific side effects (e.g., uninstall/GDPR handlers) for a shop the attacker does not control. This satisfies the "cross-tenant access" Critical impact category, since the gem provides no verified tenant binding for a value the host application is directed to trust.

### Likelihood Explanation
Likelihood is high for any consumer of this gem's webhook feature: no secret material is needed beyond running one's own Shopify app instance to obtain a single genuine webhook, and the header manipulation step is trivial (a normal client library or curl replay to the app's own public webhook endpoint). The vulnerability requires no timing race, no interception of TLS, and no social engineering.

### Recommendation
Include the tenant-identifying fields (`shop`, `topic`, `webhook_id`, `api_version`) in the signed material verified against the HMAC, or otherwise cryptographically bind them to the body before dispatch — e.g., verify the HMAC over a canonical string that concatenates the header values with the body, or require the app to independently confirm the resolved `shop` against a value it already possesses for that specific delivery (idempotency key + webhook id lookup via GraphQL) before trusting `WebhookMetadata#shop`. At minimum, document prominently that `Registry.process` provides no cryptographic guarantee that the `shop` value matches the body's origin, so integrators do not rely on it as an authenticated tenant identifier.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives one genuine webhook, e.g. body `{"id":123}` with header `x-shopify-hmac-sha256: <valid_hmac_for_body>` and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker sends a POST to the victim-hosted app's webhook endpoint with the *same* raw body and *same* `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `request.to_signable_string` (the raw body) — see [2](#0-1)  and [6](#0-5) .
4. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` per [7](#0-6) , despite the payload never having been signed in association with that shop.
