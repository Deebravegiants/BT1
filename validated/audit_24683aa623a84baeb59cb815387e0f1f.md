Audit Report

## Title
Stale `PendingSwap` entry survives counterparty deregistration, allowing an attacker who re-reserves the freed `ParaId` to hijack a pending `swap` and seize the original counterparty's lease/deposit state - (File: polkadot/runtime/common/src/paras_registrar/mod.rs)

## Summary
`PendingSwap<T>` stores a one-directional mapping `PendingSwap[id] = other` when a swap is initiated but not yet reciprocated. `do_deregister` only removes the entry keyed by the deregistered id (`PendingSwap::<T>::remove(id)`), never scanning for entries where the deregistered id appears as the *value*. If A initiates `swap(A, B)` and B is later deregistered by its own manager, the stale `PendingSwap[A] = B` entry persists, and if the freed `ParaId` B is re-reserved by an unrelated attacker who then calls `swap(B, A)`, the match `PendingSwap::get(A) == Some(B)` still succeeds, triggering `T::OnSwap::on_swap`/`do_thread_and_chain_swap` and migrating A's lease/crowdloan state onto the attacker-controlled B.

## Finding Description
`swap` inserts a one-way pending entry when no reciprocal swap exists: [1](#0-0) 

The completion check only compares `ParaId` values, not manager identity or a registration/lifecycle epoch: [2](#0-1) 

`do_deregister` clears the entry keyed by the deregistered id but never checks/cleans entries where that id is the *value* of someone else's pending swap: [3](#0-2) 

`deregister` is reachable by any signed account that is the manager/owner of a parathread, via `ensure_root_para_or_owner`, requiring no special privilege: [4](#0-3) 

Exploit flow, confirmed against the code:
1. Owner1 registers para A; Owner2 registers para B (both parathreads).
2. Owner1 calls `swap(A, B)`. Since `PendingSwap::get(B) != Some(A)`, the else-branch stores `PendingSwap[A] = B`.
3. Owner2 calls `deregister(B)`. This is permitted (B is a parathread, Owner2 is its manager) and frees `ParaId` B, unreserving Owner2's deposit via `do_deregister`, but only removes `PendingSwap[B]` (which didn't exist) — `PendingSwap[A] = B` remains untouched.
4. Attacker reserves/registers the now-free `ParaId` B, becoming its manager as a parathread via `do_reserve`/`do_register`: [5](#0-4) 
5. Attacker calls `swap(B, A)`. `ensure_root_para_or_owner` succeeds (attacker legitimately manages B now). The stale-entry check `PendingSwap::get(A) == Some(B)` is true, so lifecycle logic executes and `T::OnSwap::on_swap` is invoked, migrating A's lease/crowdloan association onto B: [6](#0-5) [7](#0-6) 

No existing guard prevents this: `ensure_root_para_or_owner` only validates that the caller currently manages the id being acted upon (true for the attacker, who legitimately re-registered B), and the `PendingSwap` match is purely a `ParaId` equality check with no binding to manager identity, deposit, or a registration/lifecycle generation that would be invalidated by a deregister-then-re-reserve cycle.

## Impact Explanation
`T::OnSwap::on_swap` (implemented by the crowdloan/slots pallets in the broader runtime) migrates lease-holding/auction/crowdloan-fund association between `ParaId`s. Exploiting this stale-entry bug lets an attacker with no relationship to the original swap counterparty redirect another para's lease/crowdloan state onto a para they control, via ordinary signed calls (`reserve`, `register`, `swap`, `deregister`) — no governance or root privilege involved. This is a genuine state/logic hijack of `Registrar::swap`, matching an in-scope "unauthorized state migration via `OnSwap::on_swap`" impact class.

## Likelihood Explanation
The attack chain uses only unprivileged, ordinary extrinsics (`reserve`, `register`, `swap`, `deregister`), each independently reachable by any signed account. The main friction is opportunistic timing: the attacker must reserve/register the exact `ParaId` freed by the counterparty's deregistration before anyone else does, which is feasible for anyone monitoring on-chain events (`Deregistered`) and racing to submit `reserve`/`force`-path transactions in a subsequent block. This is a realistic, non-mocked-path scenario relying only on standard extrinsic sequencing, not on unrealistic assumptions, victim mistakes beyond an ordinary deregister, or direct storage manipulation.

## Recommendation
Make `PendingSwap` invalidation symmetric on deregistration: either maintain a reverse index (or store both directions `PendingSwap[A]=B` and `PendingSwap[B]=A`) so `do_deregister(id)` can clear all entries referencing `id` as either key or value, or bind the pending-swap check to something that changes across a deregister/re-reserve cycle (e.g., a per-`ParaId` registration/lifecycle generation counter recorded at insertion time and checked at completion time), rejecting stale matches whose generation no longer matches current state.

## Proof of Concept
1. Register para A (account 1) and para B (account 2) as parathreads.
2. `swap(1, A, B)` → verify `PendingSwap::<Test>::get(A) == Some(B)`.
3. `deregister(2, B)` → verify (bug) `PendingSwap::<Test>::get(A)` remains `Some(B)` instead of `None`.
4. `reserve`/`register` B again as account 3 (parathread).
5. `swap(3, B, A)` succeeds and emits `Swapped { para_id: B, other_id: A }`, invoking `OnSwap::on_swap(A, B)` and migrating A's state to B — despite account 3 having no relation to account 1's original swap intent, confirming the hijack.
