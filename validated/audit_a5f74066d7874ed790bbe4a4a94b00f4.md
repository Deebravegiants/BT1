### Title
`Webhooks::Registry.process` trusts the unauthenticated `shop`/`topic` headers because the HMAC only covers the raw body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The HackerOne report describes an identity-binding failure where a value trusted by a "review before you trust it" code path (`describe_transfer`) is read from a field that was never actually validated (`real_output_in_tx_index` vs. `real_output`). The analogous class in this gem is: `ShopifyAPI::Webhooks::Registry.process` HMAC-validates a webhook, then hands the handler a `shop` identity that was never covered by that HMAC at all.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` values are all read straight from HTTP headers with no cryptographic binding to the request at all: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately constructs `WebhookMetadata` using `request.shop` and `request.topic`, passing this straight to the app's registered handler as trusted, authenticated data: [3](#0-2) 

`HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest(sha256, api_secret_key, verifiable_query.to_signable_string)` and compares it to the received signature: [4](#0-3) 

Since `to_signable_string` for a webhook request is *only the raw body*, the HMAC proves "this body was produced with knowledge of `api_secret_key`" — it proves nothing about which shop, topic, or webhook the body belongs to. Those identity fields are asserted by the caller in the HTTP headers and taken at face value.

The equality that should hold but does not is:
`shop authenticated by the webhook HMAC == shop delivered to the handler as request.shop`

Because a single app (single `api_secret_key`) serves many merchant shops, and the signature is a pure function of `(secret, raw_body)` with no shop/topic binding, two different shops receiving webhooks with byte-identical bodies (trivially achievable — many webhook payloads for the same topic across shops have identical or attacker-influenceable JSON structure, and an attacker who legitimately installs the app on their own shop can capture a real `(body, hmac)` pair for their own tenant) produce identical, valid signatures. An unprivileged internet user who controls (or has installed) the app on their own shop can:
1. Trigger (or receive) a legitimate webhook for their own shop and capture the exact `(raw_body, x-shopify-hmac-sha256)` pair.
2. Replay that exact body+signature to the app's webhook endpoint over the internet, but forge the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header to name a victim shop.
3. `Utils::HmacValidator.validate` still passes, because it only checks the body against the secret, not the shop header.
4. The app's handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and processes attacker-supplied body content as if it were an authentic event from the victim tenant.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook delivery: cross-tenant data injection/spoofing. Any downstream logic that keys off `WebhookMetadata#shop` (e.g., "look up shop record and update order state from this webhook body") can be made to act on a victim shop using attacker-chosen JSON content, without ever having compromised the victim, the app's `api_secret_key`, or an access token. This matches "cross-tenant access" in the Critical impact bucket.

### Likelihood Explanation
Likelihood is not trivial but real: the attacker needs a valid `(body, hmac)` pair, which they can obtain by being any merchant who installs the app (a normal, unprivileged action for any public app) and observing their own webhook deliveries, or by finding topics/bodies that are largely fixed/predictable (e.g., `app/uninstalled` bodies, or bodies with static schema and few variable fields that the attacker can also control on their own shop to match a targeted structure). No secret material, TLS interception, or privileged account is required — only normal use of the app as an unprivileged merchant plus a forged header on a replayed HTTP request.

### Recommendation
Bind the identity headers into the signed material that `HmacValidator` checks, or otherwise verify `request.shop` against an authenticated source before trusting it:
- Either include `shop`, `topic`, and `webhook_id` in `to_signable_string` (this would require changing what's hashed, which must match Shopify's actual signing scheme — likely not possible unilaterally since Shopify signs only the body), or
- Require the caller to independently prove the shop was expected (e.g., verify `request.shop` corresponds to a shop for which the app has a known session/installation) before acting on the webhook body, and document this responsibility clearly for consumers of `Registry.process`.

### Proof of Concept
1. App is installed on attacker's own shop `attacker.myshopify.com`; attacker triggers a webhook whose body is fully attacker-controlled or predictable (e.g., a custom metafield update) and captures the resulting `x-shopify-hmac-sha256` value and raw body from the real Shopify delivery.
2. Attacker sends a POST to the app's webhook endpoint with:
   - Body: the captured raw body (byte-for-byte).
   - Header `x-shopify-hmac-sha256`: the captured signature.
   - Header `x-shopify-shop-domain`: `victim.myshopify.com`.
   - Header `x-shopify-topic`: same topic as captured.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over the raw body only and matches the forged request's signature — validation passes.
4. The registered handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and the attacker-supplied body, and processes it as an authentic event from the victim tenant.

        sig { params(request: Request).void }
        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
