### Title
Duplicate `erc20TokenAddresses` entries cause the same external-action UTXO to be committed to the Merkle tree multiple times - (File: contracts/Hinkal.sol)

### Summary
In `Hinkal.sol`'s `transact()` function, the loop that matches UTXOs returned by an external action to the token list is matched by **address equality**, not by a unique per-token index. If `circomData.erc20TokenAddresses` contains the same token address more than once, a single UTXO returned from `_externalTransact` can be matched — and committed to the Merkle tree — once for *each* occurrence of that address in the array. This mirrors the reported bug class of a value/state item being counted (pushed) more than once into a structure that a downstream invariant sums over.

### Finding Description
`transact()` builds `onChainCommitments` by iterating over `circomData.erc20TokenAddresses` and, for each index `i`, scanning the *entire* `utxoSet` for entries whose `erc20Address` equals `erc20TokenAddresses[i]`: [1](#0-0) 

There is no requirement anywhere that `erc20TokenAddresses` contains unique addresses. `dimensionsCheck` in `HinkalHelper.sol` only validates array *lengths* against `dimensions.tokenNumber`, never uniqueness of the addresses themselves: [2](#0-1) 

`CircomDataBuilder.formBasicInput` simply copies `erc20TokenAddresses` into the public/private circuit input array in order, with no de-duplication constraint expressed at the Solidity level: [3](#0-2) 

If the same token address is listed twice (e.g. `erc20TokenAddresses = [tokenA, tokenA]`) and the registered external action returns a single UTXO for `tokenA` (a normal, expected outcome of a single swap/output), the inner loop's `if (utxoSet[j].erc20Address == circomData.erc20TokenAddresses[i])` condition is true for **both** `i` values. This causes:
- `utxoAmount` to be summed twice against the (identical) `balanceDif` computed independently for each duplicated index — because `oldBalances`/`newBalances` are taken from `getBalancesForArray`, which also just re-reads the same token balance for each duplicate index, the same balance delta is checked twice, so the `require(balanceDif == amountChanges[i] + utxoAmount)` check passes trivially for both indices even though only one real balance movement occurred.
- `createOnchainCommitment(utxoSet[j], ...)` to be called **twice** for the same `utxoSet[j]`, producing an *identical* commitment hash both times, which is written into `onChainCommitments[onChainCommitmentCounter]` twice.

These duplicated commitments are then passed into `insertCommitments`, which inserts each entry as an independent leaf into the Merkle tree: [4](#0-3) 

The result is that a single, real value movement (one UTXO backed by one token balance change) produces **two identical valid leaves** in the shielded-pool Merkle tree, each independently provable via Merkle inclusion.

### Impact Explanation
If the underlying spend circuit derives a note's nullifier purely from the note's secret contents (amount, stealth address, blinding factor) rather than from its tree position, both duplicate leaves would share the same nullifier and the second spend attempt would be rejected by `insertNullifiers`'s `"Nullifier cannot be reused"` check, limiting the practical damage to at most a state/gas inefficiency rather than a double-spend. Conversely, if any code path allows deriving distinct valid spends from the two identical leaves (e.g., different leaf indices being treated as distinct notes), this becomes a direct **minting of shielded value without backing** — the attacker would obtain two spendable UTXOs of value `V` for a single deposit/action of value `V`, i.e., a Critical impact (unbacked minting / double count of collateral, directly analogous to the reported `colPools` double-count).

I was not able to fully verify, within the scope of the files reviewed, whether the nullifier/Merkle-inclusion circuit ties a nullifier to leaf position (which would fully mitigate the exploit) or purely to note secrets (which would make it exploitable). This is the key open question for confirming full exploitability, but the on-chain Solidity flaw that produces the duplicated leaf writes is concretely present and file-verified as shown above.

### Likelihood Explanation
Triggering the duplicated-commitment write requires only that a user submit a `transact()` call whose `circomData.erc20TokenAddresses` list contains a repeated address alongside a registered external action that legitimately returns a single UTXO for that token — no admin, relayer, or privileged role is required to submit the transaction. The check that would normally prevent this (uniqueness of `erc20TokenAddresses`) simply does not exist in `dimensionsCheck` or anywhere else in `HinkalHelper.sol`/`CircomDataBuilder.sol`.

### Recommendation
- Enforce uniqueness of `circomData.erc20TokenAddresses` in `dimensionsCheck` (or earlier), rejecting any `transact()` call where a token address repeats.
- Alternatively, restructure the matching loop in `Hinkal.sol` (lines 92-132) to match `utxoSet` entries to `erc20TokenAddresses` by consuming each `utxoSet[j]` at most once (e.g., mark matched entries, or match by explicit index rather than by address equality across the whole array).

### Proof of Concept
Conceptual PoC (mirrors the structure of the original report's double-`deposit(0)` PoC, adapted to this repo's data flow):
1. Register/use any external action that, given a swap of tokenA→tokenA-equivalent output, returns a `UTXO[] utxoSet` containing exactly one entry for `erc20Address = tokenA`.
2. Craft `circomData.erc20TokenAddresses = [tokenA, tokenA]` with corresponding duplicated `amountChanges`/`slippageValues` entries so both `balanceDif` checks trivially pass against the same real balance delta.
3. Call `Hinkal.transact(...)` with a proof that is valid for this `circomData` (the circuit does not reject duplicate addresses at the Solidity level, per `CircomDataBuilder.formBasicInput`).
4. Observe (via `NewCommitment` events emitted by `insertCommitments`) that the identical commitment/UTXO is emitted and inserted into the Merkle tree **twice** for a single external-action value movement, in `contracts/Hinkal.sol` lines 117-132 and `contracts/HinkalBase.sol` lines 100-131.     function insertCommitments(
        uint256[][] memory offChainCommitments,
        bytes[][] memory offChainEncryptedOutputs,
        OnChainCommitment[] memory onChainCommitments,
        bool[] memory onChainCreation
    ) internal {
        // 1) Total Length of Commitments
        uint256 length = 0;
        for (uint256 i = 0; i < offChainCommitments.length; i++) {
            for (uint256 j = 0; j < offChainCommitments[i].length; j++) {
                if (onChainCreation[i]) break;
                length += offChainCommitments[i][j] != 0 ? 1 : 0;
            }
        }
        length += onChainCommitments.length;

        if (length > 0) {
            // 2) Flattening leaves array
            uint256[] memory leaves = new uint256[](length);
            uint256 index = 0;
            for (uint256 i = 0; i < offChainCommitments.length; i++) {
                for (uint256 j = 0; j < offChainCommitments[i].length; j++) {
                    if (onChainCreation[i] == true) break;
                    if (offChainCommitments[i][j] != 0) {
                        leaves[index++] = offChainCommitments[i][j];
                    }
                }
            }
            for (uint256 i = 0; i < onChainCommitments.length; i++) {
                leaves[index++] = onChainCommitments[i].commitment;
            }

            // 3) Inserting Leaves
            uint256[] memory insertedIndexes = insertMany(leaves);

            // 4) Emitting Commitments/EncryptedOutputs
            index = 0;
            for (uint256 i = 0; i < offChainEncryptedOutputs.length; i++) {
                for (uint256 j = 0; j < offChainEncryptedOutputs[i].length; j++) {
                    if (onChainCreation[i] == true) break;
                    if (offChainCommitments[i][j] != 0) {
                        emit NewCommitment(
                            leaves[index],
                            int256(insertedIndexes[index]),
                            offChainEncryptedOutputs[i][j]
                        );
                        index++;
                    }
                }
            }
            for (uint256 i = 0; i < onChainCommitments.length; i++) {
                emit NewCommitment(
                    leaves[index],
                    -1 * int256(insertedIndexes[index++]),
                    abi.encode(
                        onChainCommitments[i].utxo,
                        onChainCommitments[i].onChainEncryptedOutput
                    )
                );
            }
        }
    }
