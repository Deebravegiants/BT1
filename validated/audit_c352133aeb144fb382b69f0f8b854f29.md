### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while the shop identity (`shopify-shop-domain` / `x-shopify-shop-domain` header) is read directly off the unauthenticated HTTP headers and later trusted as the tenant identity when dispatching the webhook to the app's handler.

### Finding Description
`Request#to_signable_string` is defined as just `@raw_body` [1](#0-0) , and `Request#shop` is parsed straight from the HTTP header with no cryptographic binding to the body or to the HMAC [2](#0-1) . `Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, which only compares the HMAC against `to_signable_string` (the raw body) [3](#0-2) [4](#0-3) . After that single check passes, `request.shop` (and `topic`, `api_version`, `webhook_id`) — none of which are part of the signed payload — are forwarded unchanged into `WebhookMetadata` and handed to the app's `WebhookHandler#handle` as the trusted tenant context [5](#0-4) .

Because the HMAC secret (`Context.api_secret_key` / the app's `client_secret`) is shared across **every** shop that has installed the app, a valid `(raw_body, hmac)` pair captured from one legitimate webhook delivery remains a cryptographically valid HMAC for that same app regardless of which shop the request claims to be from. The equality the code should be enforcing is:
`shop-identity-verified-by-HMAC == shop-identity-acted-upon-by-handler`
but instead it verifies only `body-integrity-verified-by-HMAC` and separately, unauthenticated, trusts `shop-header-value` — breaking that binding.

### Impact Explanation
An attacker who controls (or has installed) any shop using the target app can capture a legitimate webhook delivery to their own store (raw body + `X-Shopify-Hmac-Sha256` header), then replay that exact body/HMAC pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain that also has the app installed. `HmacValidator.validate` still succeeds because it never inspects the header, and `Registry.process` will invoke the app's handler with `WebhookMetadata.shop` set to the victim shop while the payload body is attacker-controlled. This is a cross-tenant data-integrity break: the app processes attacker-fabricated webhook data (e.g., order/customer/inventory events) as if it belonged to a different merchant's tenant, which can corrupt per-shop state, trigger unintended actions, or leak/mutate data across tenant boundaries — this satisfies the "cross-tenant access" Critical-impact criterion.

### Likelihood Explanation
The attacker only needs to be a legitimate (even free-trial) installer of the target app in order to receive at least one real signed webhook for their own shop, then can freely replay it against the same endpoint with a spoofed shop header — no access to `client_secret`, TLS interception, or privileged credentials is required. This is a purely gem-side gap: the HMAC verification logic in `HmacValidator`/`Request` never binds the shop header into the signed content, so the vulnerability is always reachable wherever host apps rely on this gem's `Webhooks::Registry.process` for webhook authentication (which is the gem's documented usage pattern).

### Recommendation
Include the shop-domain (and ideally topic/webhook id) in the signable content used for HMAC verification, or explicitly document that consuming apps must independently verify `request.shop` against a known/authorized shop list (e.g., an existing session) before trusting it, rather than allowing verification of body integrity alone to imply shop authenticity.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and receives a legitimate webhook: raw body `B` with header `X-Shopify-Hmac-Sha256: H` (valid for the app's shared `client_secret`) and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker sends a new HTTP POST directly to the app's webhook endpoint with the same body `B` and the same `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (a real shop that also installed the app).
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body normally [6](#0-5) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only and matches `H` successfully [7](#0-6) .
4. `Registry.process` builds `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)` and invokes the app's handler with attacker-controlled body content attributed to the victim shop [5](#0-4) , demonstrating the cross-tenant binding break.

        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
