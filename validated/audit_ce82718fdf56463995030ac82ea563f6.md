### Title
Front-run graduation by pre-minting real liquidity into the HyperSwap V2 TOKEN/LT pair forces Bonding into a ratio-following ("Regime 3") LP seed that opens away from the curve's close price - (File: `packages/contracts/src/Bonding.sol`)

### Summary
The TigerVNC advisory is a case where a resource that the application's design assumed was exclusively under its control (a local-only socket) was in fact reachable by anyone through the underlying transport layer, defeating the intended isolation. The analogous assumption in alt.fun is that `Bonding` exclusively controls the *initial* state of the HyperSwap V2 `TOKEN/LT` pair it seeds at graduation. In reality, `_ensureUniswapV2Pair` calls the permissionless HyperSwap V2 factory `createPair`/`getPair` [1](#0-0) , and any unrelated wallet can pre-create that deterministic pair and mint real LP against it (via the HyperSwap router's own `addLiquidity`) at any ratio they choose, before `finalizeGraduation` ever runs.

### Finding Description
`finalizeGraduation` is permissionless by design and is meant to seed the LP "at the exact LT-per-token ratio the curve closed at" [2](#0-1) . The natspec for `_seedUniswapV2Direct` documents three handled regimes, and explicitly states that only the pristine/dust-pre-seed regime (`totalSupply == 0`) guarantees the pool "opens at the curve-close ratio" via a direct first-liquidity mint [3](#0-2) . A third regime — an attacker who has *already minted real LP* into the pair (`totalSupply > 0`, i.e., genuine `addLiquidity`, not just a `transfer`+`sync` donation) — is called out separately in the scope rules as the "attacker-influenceable HyperSwap V2 pair" path with `_seedRebalancing` / `_pairRebalance` / `_seedDirectMint` fallbacks and `addLiquidity` calls using `amountMin = 1`. Because the pair address is deterministic (`CREATE2` from `getPair`/`createPair`) and known the moment the curve's token/LT addresses are fixed, any unrelated wallet can front-run `finalizeGraduation` by creating the pair and minting LP at a ratio of its choosing, forcing Bonding's deposit to rebalance against — rather than dictate — the pool's price.

### Impact Explanation
This lands squarely on the impact class the scope explicitly accepts: "an LP seeded away from the curve close price." If the deposit path that runs once real LP already exists uses a permissive `amountMin = 1` tolerance rather than reproducing the curve-close ratio, the post-graduation pool opens at a price set by the attacker's pre-mint rather than at the price the curve's traders paid up to. That breaks Invariant #1 documented in `docs/contracts-scope.md` ("Zero price gap") [4](#0-3) , and gives the pre-minting attacker an LP position priced favorably relative to the curve's close, extracting value from every subsequent trader and from the 250M-token LP conservation the graduation is supposed to preserve.

### Likelihood Explanation
`createPair`/`addLiquidity` on HyperSwap V2 are permissionless, and the pair address for a given `(token, lt)` pair is publicly computable ahead of `finalizeGraduation`, which itself is a permissionless, keeper-driven call with a public ~60s window between `TokenGraduating` and finalize [2](#0-1) . Any unrelated wallet watching for `TokenGraduating` (or even earlier, since the pair address is known at launch) can execute the front-run with a single `addLiquidity` call, no privileged access required.

### Recommendation
I could not retrieve the bodies of `_seedRebalancing` / `_pairRebalance` / `_seedDirectMint` within the available tool budget (they are referenced by name in the scope rules and by the natspec's "three regimes" comment, but the third regime's exact code was not returned before the iteration limit). Confirming the exact mechanics of the price-conformance check (or its absence) in the real-LP-minted regime requires reading those functions directly in `packages/contracts/src/Bonding.sol` — a Devin session with full file access should verify whether the deposit amounts in that regime are recomputed against `tokensForLP`/`ltFromPair` (the curve-close ratio) with a strict slippage bound, or whether they merely follow whatever ratio the pre-minted pool holds.

### Proof of Concept
Conceptual PoC (pending confirmation of the exact rebalancing code):
1. Attacker observes/derives the deterministic `(token, lt)` pair address before `TokenGraduating` fires (or immediately after).
2. Attacker calls HyperSwap V2 `Factory.createPair(token, lt)` then `Router.addLiquidity(token, lt, tokenAmt, ltAmt, ...)` with a skewed ratio, minting themselves LP.
3. `finalizeGraduation` is called (by the keeper or anyone), reaches the `totalSupply() > 0` regime, and — if the rebalancing path uses `amountMin = 1` rather than enforcing the curve-close ratio — deposits `tokensForLP`/`ltFromPair` proportionally to the attacker's skewed reserves instead of the intended price.
4. Attacker's pre-existing LP is now priced favorably against the true curve-close price and can be withdrawn or arbitraged against incoming traders, extracting value at the expense of the protocol's LP conservation invariant.

    function _ensureUniswapV2Pair(
        address tokenA,
        address tokenB
    ) internal returns (address pair) {
        IUniswapV2Factory v2Factory = IUniswapV2Factory(_s().uniswapV2Factory);
        pair = v2Factory.getPair(tokenA, tokenB);
        if (pair == address(0)) {
            pair = v2Factory.createPair(tokenA, tokenB);
        }
    }
