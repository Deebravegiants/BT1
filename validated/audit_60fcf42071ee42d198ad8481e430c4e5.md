## Title
Donation/inflation attack on AMM `liquidity_pool.move` — `balance()`-based reserves let attackers manipulate LP mint/burn ratios via direct `fungible_asset::deposit` - (File: `aptos-move/move-examples/swap/sources/liquidity_pool.move`)

### Summary
This is the same custody-invariant break as the QodaToken report — using a raw, externally-manipulable balance query (`balanceOf`/`fungible_asset::balance`) instead of internally-tracked accounting to compute value distribution. In Aptos's `move-examples/swap` AMM, `mint()` and `burn()` compute LP token issuance/redemption directly from `fungible_asset::balance(store_1)` / `balance(store_2)` [1](#0-0) , rather than from an internally tracked reserve variable updated only through `swap`/`mint`/`burn` logic.

### Finding Description
`fungible_asset::FungibleStore` objects support ordinary, permissionless deposits — any holder of a `FungibleAsset` can call `fungible_asset::deposit(store, fa)` (or `primary_fungible_store`-style direct transfer) to add balance to *any* store object address, including `pool_data.token_store_1`/`token_store_2`, without going through the AMM's `swap`/`mint` entrypoints. The pool's own `mint` function reads the "reserve" straight from this manipulable balance:

```
let reserve_1 = fungible_asset::balance(store_1);
let reserve_2 = fungible_asset::balance(store_2);
...
let token_1_liquidity = math64::mul_div(amount_1, (lp_token_supply as u64), reserve_1);
let token_2_liquidity = math64::mul_div(amount_2, (lp_token_supply as u64), reserve_2);
``` [2](#0-1) 

and `burn` computes redemption amounts the same way:
```
let reserve_1 = fungible_asset::balance(store_1);
let reserve_2 = fungible_asset::balance(store_2);
let amount_to_redeem_1 = math128::mul_div((amount as u128), (reserve_1 as u128), lp_token_supply);
``` [3](#0-2) 

`get_amount_out` (used for swap pricing) and `pool_reserves` also derive directly from `fungible_asset::balance` [4](#0-3) [5](#0-4) .

Because these stores are ordinary `FungibleStore` objects (created via `fungible_asset::create_store` inside `create()` [6](#0-5) ) with no dispatch/freeze hooks restricting deposits, an unprivileged attacker can directly donate tokens to `token_store_1`/`token_store_2` to inflate the on-chain "reserve" without minting any LP shares for the donation. This is the exact donation/inflation-attack class described in the external report (manipulable `balanceOf` corrupting distribution math), just expressed through Aptos's fungible-asset custody primitives instead of ERC-20 `balanceOf`.

### Impact Explanation
An attacker who front-runs the very first `mint()` call on a freshly created pool (reserves = 0, `lp_token_supply == 0` branch) can donate a large, disproportionate amount of one token directly to `store_1`/`store_2` before the first legitimate LP deposits. This skews `reserve_1`/`reserve_2` so that subsequent `mint()` calls compute `token_1_liquidity`/`token_2_liquidity` via `mul_div(amount, lp_token_supply, reserve)` against an inflated denominator, causing genuine depositors to receive far fewer LP tokens than their contribution is worth (classic share-price/inflation-attack primitive), while the attacker's own earlier minted LP tokens capture a share of the donated value. Symmetrically, at `burn()`, since the payout uses the same live `balance()` as numerator/denominator, an attacker can donate immediately before someone else's `burn()` call to shift how much of the pool's held tokens that LP receives back, or manipulate `get_amount_out`/swap pricing transiently. The result is a direct custody/value-corruption impact: value is diverted from legitimate liquidity providers to the attacker, matching the "Supply or custody accounting corruption that moves value to the wrong holder" impact category.

### Likelihood Explanation
The attack requires only: (1) holding the underlying fungible asset (or wrapped coin) of one leg of the pool, and (2) calling the ordinary, unprivileged `fungible_asset::deposit`/transfer against the pool's public store object address — no special permission, admin role, or governance action is needed. The pool store address is discoverable via `liquidity_pool_address`/`pool_reserves` view functions [7](#0-6) . This is most exploitable on pool creation (classic first-depositor inflation attack) but remains a live griefing/manipulation vector on every subsequent `mint`/`burn`/swap-quote call since reserves are always re-read live from `balance()`.

### Recommendation
Track reserves as internal state fields on `LiquidityPool` (or `FeesAccounting`) that are updated only inside `swap`, `mint`, and `burn`, mirroring the `total_coins` pattern already used correctly in `pool_u64`/`pool_u64_unbound` for share accounting [8](#0-7) . Do not use `fungible_asset::balance(store)` as the source of truth for reserve-dependent math; if direct donations must be tolerated, "sync" internal reserves explicitly via a permissioned/rate-limited function rather than implicitly on every read.

### Proof of Concept
Note: this is a Move-based analog, and a runnable Foundry-style PoC is not applicable; the following pseudo-flow demonstrates the exploit path using the module's own public API:
1. Attacker calls `liquidity_pool::create(token_1, token_2, false)` or targets an existing freshly created pool with `lp_token_supply == 0`.
2. Attacker calls `liquidity_pool::mint(attacker, small_fa_1, small_fa_2, false)` to become the first LP with minimal committed liquidity, obtaining almost all initial LP shares (`total_liquidity - MINIMUM_LIQUIDITY`), per [9](#0-8) .
3. Attacker independently calls `fungible_asset::deposit(pool_data.token_store_1, large_fa_1)` directly (bypassing `mint`) to inflate `reserve_1` without receiving any additional LP shares for it.
4. A victim then calls `mint()` with proportionate amounts; because `reserve_1` is now inflated, `math64::mul_div(amount_1, lp_token_supply, reserve_1)` at [10](#0-9)  yields a disproportionately small LP token allocation for the victim's real contribution.
5. Attacker calls `burn()` to redeem their LP shares, which pays out proportional to the now-larger `reserve_1`/`reserve_2` computed at [3](#0-2) , capturing value from the victim's donated-inflated deposit.
