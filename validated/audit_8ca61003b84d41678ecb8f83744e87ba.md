### Title
Nested `EmporiumOperation` stateless calls bypass `Hinkal._externalTransact` and let an attacker drain another allowed-recipient action's residual token balance - (File: `contracts/external-actions/swaps/LifiExternalAction.sol`, `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction`'s stateless-op branch performs an arbitrary low-level `op.endpoint.call(op.callData)` with no restriction beyond blocking two wallet selectors. If Emporium is registered as an `allowedRecipient` on another `IExternalActionV2` action (e.g. `LifiExternalAction`), an attacker can make Emporium call that action's `runAction(forgedCircomData, forgedDeltaAmounts)` directly, since `onlyAllowedRecipient` only checks `msg.sender == Emporium`, not that the call originated from `Hinkal._externalTransact`. The forged `CircomData`/`deltaAmounts` are never covered by any ZK proof, so the attacker can set `deltaAmounts[0]` to consume the target action's leftover token balance instead of funds actually transferred for that call.

### Finding Description
The intended invariant is: *tokens an external action sends out during `runAction` must equal `-deltaAmountChanges` that Hinkal actually transferred to it in `_externalTransact` right before the call* (`contracts/Hinkal.sol:244-260`):
```
deltaAmountChanges[i] = _calculateDeltaAmount(circomData, i);
if (deltaAmountChanges[i] < 0) {
    transferERC20TokenOrETH(..., externalAddress, uint256(-deltaAmountChanges[i]));
}
...
IExternalActionV2(externalAddress).runAction(circomData, deltaAmountChanges);
``` [1](#0-0) 

`ExternalActionSwap.runAction`/`swap` trusts this invariant blindly: `inputAmount = uint256(-deltaAmounts[0])` is used to pull tokens for the router swap with no check that those tokens were freshly transferred in for this call. [2](#0-1) 

`LifiExternalAction.callRouter` also only measures a balance delta on the output token and approves+calls the router with `inputAmount`, again assuming that amount genuinely arrived for this call: [3](#0-2) 

The only gate on `runAction` is `onlyAllowedRecipient`, which merely checks `msg.sender` against an allow-list, with no binding to the actual Hinkal-driven call chain or to a proof-verified `CircomData`: [4](#0-3) 

`EmporiumUpgradeable.runAction`'s stateless branch performs an unrestricted external call:
```
(success, err) = op.endpoint.call{value: op.value}(op.callData);
```
only blocking `callHinkalWallet`/`doSendToRelay` selectors - nothing prevents `op.endpoint` from being another `allowedRecipient`-gated action and `op.callData` from being an arbitrary `runAction(forgedCircomData, forgedDeltaAmounts)` payload. [5](#0-4) 

**Exploit flow (if Emporium is an `allowedRecipient` of `LifiExternalAction`):**
1. Attacker calls `Hinkal.transact` with a legitimate proof for a normal Emporium action, declaring `erc20TokenAddresses = [outputToken]`, `amountChanges[outputToken] = 0`, and includes one `EmporiumOperation` with `invokeWallet=false`, `endpoint = LifiExternalAction`, `callData = abi.encodeCall(runAction,(forgedCircomData, forgedDeltaAmounts))`, `forgedDeltaAmounts[0] = -dustAmount`.
2. `Hinkal._externalTransact` transfers **nothing** related to `inputToken` (it's not declared at all in the outer `circomData`), then calls `Emporium.runAction`.
3. Emporium's stateless branch calls `LifiExternalAction.runAction(forgedCircomData, forgedDeltaAmounts)`. `onlyAllowedRecipient` passes because `msg.sender == Emporium`.
4. `swap()` computes `inputAmount = dustAmount`, which is actually pre-existing residual `inputToken` balance left in `LifiExternalAction` from a prior, unrelated, already-completed swap (rounding/leftover approval dust) - never transferred for this call.
5. `callRouter` swaps that dust through the real router, sends `outputToken` back to `msg.sender` (which, inside this nested call, is `Emporium`), increasing Emporium's balance.
6. Back in `Emporium.runAction`, `balancesAfter - balancesBefore` for `outputToken` reflects this increase; since the outer `deltaAmountChanges[outputToken] = 0`, the whole amount is passed to `handleOut`, which forwards it to Hinkal and mints a UTXO with the attacker's `stealthAddressStructure`.
7. Hinkal's own balance-diff/slippage check (`Hinkal.sol:134-146`) is trivially satisfied because `amountChanges[outputToken]=0` and `utxoAmount == balanceDif` by construction - the check was never designed to catch value materializing from a third contract's residual balance.

No proof, nullifier, root-hash, or `dimensionsCheck` constrains the inner forged `CircomData`/`deltaAmounts` at all, since that data never flows through `performHinkalChecks`/`verifyProof` - it is pure attacker-crafted calldata inside the Emporium stateless op.

### Impact Explanation
The attacker converts an external action's stray/residual ERC-20 (or ETH) balance into a shielded UTXO credited to themselves, for free, repeatable any time dust exists on any action listed in Emporium's allow-list. This is theft of protocol/action residual funds (High) rather than a live user's in-flight funds, because Hinkal transactions are atomic per call - by the time any transaction fully completes, any leftover balance in an external action is orphaned dust, not another user's active operation. If, in some future extension, an action's balance can legitimately remain "in-flight" across transactions on behalf of a specific user, this would escalate to Critical (direct theft of another user's funds).

### Likelihood Explanation
Preconditions: (1) Emporium must be added to `allowedRecipients` of another `IExternalActionV2` action such as `LifiExternalAction` - a configuration decision, not a privileged runtime action by the attacker; (2) that action must hold a nonzero residual balance of some token (plausible over time from rounding, positive slippage, or partial fills in `callRouter`). Given those, exploitation requires only an unprivileged, self-funded `Hinkal.transact` call with an attacker-authored Emporium op - no special role, no other user's keys, fully repeatable and drains the dust each time it reappears.

### Recommendation
- Do not allow `ExternalActionBaseV2.onlyAllowedRecipient` allow-lists to include other external-action contracts as callers unless the calling contract also forwards a caller-agnostic proof of legitimate `deltaAmountChanges`.
- Have `IExternalActionV2` implementations (e.g., `ExternalActionSwap`) require and validate that `deltaAmounts` matches tokens actually received in the *current* call (e.g., pass and check a fresh balance snapshot taken by `Hinkal` immediately before invoking `runAction`, or have `Hinkal` itself pass a signed/committed value that `runAction` can verify came from `_externalTransact`).
- Alternatively/also, restrict Emporium's stateless-call `op.endpoint` to a curated set that excludes other `onlyAllowedRecipient`-gated actions, or require `EmporiumOperation.callData` selectors to be explicitly denylisted for all `runAction`-shaped calls, not just wallet-selector calls.
- Sweep/zero out residual balances after each swap (send dust back to `msg.sender`/Hinkal) so no meaningful dust can accumulate.

### Proof of Concept
Foundry fork test plan:
1. Deploy `LifiExternalAction` with `Emporium` address included in `_allowedRecipients`.
2. Simulate residual dust: directly `deal`/transfer `inputToken` to `LifiExternalAction` (representing leftover from a prior legitimate swap) without any corresponding Hinkal accounting.
3. Craft an outer `CircomData`/proof for a normal Emporium `runAction` call via `Hinkal.transact`, with `erc20TokenAddresses = [outputToken]`, `amountChanges[outputToken] = 0`, `stealthAddressStructure` = attacker's own.
4. In `EmporiumStack.ops`, include a stateless op: `endpoint = LifiExternalAction`, `callData = abi.encodeCall(IExternalActionV2.runAction, (forgedCircomData, forgedDeltaAmounts))` where `forgedDeltaAmounts[0] = -dustAmount` and `forgedCircomData` encodes a valid LI.FI router calldata swapping `dustAmount` of `inputToken` to `outputToken`.
5. Assert before/after: `LifiExternalAction`'s `inputToken` balance goes from `dustAmount` to 0 without any transfer from Hinkal to `LifiExternalAction` for `inputToken` in this transaction (equality `tokensOut(LifiExternalAction) == -deltaAmountChanges_from_Hinkal` is violated: LHS = `dustAmount`, RHS = `0`).
6. Assert a new on-chain UTXO commitment is created for the attacker's stealth address with `amount == swappedAmount`, and that this amount is not backed by any deposit/withdrawal declared in the proof-verified outer `circomData.amountChanges`.
