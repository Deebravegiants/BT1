### Title
Hardcoded 18-decimal `HyperFungibleToken` combined with unscaled `WrappedHyperFungibleToken` locking causes catastrophic mispricing/loss of value for non-18-decimal bridged tokens - (File: sdk/packages/core/contracts/apps/HyperFungibleToken.sol, sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol)

### Summary
`WrappedHyperFungibleToken` locks an arbitrary underlying ERC20 token 1:1 by raw `amount` and forwards that raw amount unchanged in the cross-chain `Message`. `HyperFungibleToken`, the mint/burn representation deployed on every remote chain, inherits OpenZeppelin's `ERC20` without overriding `decimals()`, so it is always 18 decimals regardless of what the underlying token actually uses. Any token bridger sending tokens whose real decimals differ from 18 (e.g. USDC/USDT at 6 decimals, WBTC at 8 decimals) will have their raw amount minted as if it were expressed in 18-decimal units, producing a destination-chain representation that is off by a factor of `10^(18-realDecimals)` from the intended value.

### Finding Description
`WrappedHyperFungibleToken.send()` pulls `params.amount` raw underlying-token units via `safeTransferFrom` and encodes the same raw `amount` into the `HyperFungibleToken.Message` body with no decimal normalization: [1](#0-0) 

On the destination chain, `HyperFungibleToken.onAccept()` mints exactly `message.amount` of its own token to the beneficiary: [2](#0-1) 

`HyperFungibleToken`'s constructor only sets name/symbol via the base `ERC20` constructor and never overrides `decimals()`, so it always reports 18 (OpenZeppelin's default): [3](#0-2) 

This is the exact bug class from the external report — OpenZeppelin's ERC20 defaulting to 18 decimals regardless of the represented asset's real precision — except here it is compounded because the protocol has no scaling logic anywhere in the generic `HyperFungibleToken`/`WrappedHyperFungibleToken` pair to compensate. The team's own `BridgeToken.sol` subclass acknowledges and manually works around this exact problem for the BRIDGE token (12 decimals on nexus vs. 18 on EVM), explicitly scaling by `10^6` in `pallet-hyper-fungible-token`: [4](#0-3) 

and the pallet has dedicated conversion helpers for this purpose: [5](#0-4) 

However, no equivalent scaling exists for the general `WrappedHyperFungibleToken` → `HyperFungibleToken` EVM-to-EVM path documented for arbitrary ERC20 deployments (e.g. wrapping USDC): [6](#0-5) 

### Impact Explanation
When wrapping any ERC20 token with decimals different from 18 (extremely common — USDC/USDT are 6, WBTC is 8), a user bridging tokens through the documented `HyperFungibleToken` flow will have their locked funds represented on the destination chain at the wrong scale by a fixed power-of-ten factor. If the underlying has fewer decimals than 18 (e.g., 6-decimal USDC), the destination token is effectively worthless per unit minted (the recipient must divide by 10^12 to get the "real" value they should have received, i.e. they receive a negligible fraction of intended value when interpreted at face value) — or conversely, if application/UI logic assumes 18 decimals uniformly, users/integrators will misprice amounts by orders of magnitude, and burning back through `send()` will not reflect the correct proportion of locked collateral, permanently stranding value in the escrow contract or allowing attackers to redeem disproportionate amounts of the locked underlying by manipulating decimal assumptions in any downstream integration (DEXs, price oracles, or the SDK) that trusts the destination token's `decimals()`. This constitutes unbacked/mispriced minting and potential permanent freezing/loss of bridged value, satisfying a Medium/High severity bar.

### Likelihood Explanation
Likelihood is high: `HyperFungibleToken`/`WrappedHyperFungibleToken` are the actively documented, current (non-deprecated) primitives for bridging arbitrary ERC20 tokens, replacing the old `TokenGateway`. Any deployer wrapping a common stablecoin (6 decimals) or wrapped BTC (8 decimals) — a mainstream use case — will trigger this by default, with no built-in safeguard, warning, or scaling mechanism in the generic contracts. The bug requires no privileged action; it is triggered by ordinary `send()` calls from an unprivileged token bridger.

### Recommendation
Add a `decimals()` override to `HyperFungibleToken` (and its upgradeable variant) that is set at deployment/configuration time to match the underlying token's decimals, and have `WrappedHyperFungibleToken`/`HyperFungibleToken` scale `amount` by the decimal delta between source and destination representations when constructing/decoding the `Message`, mirroring the `convert_to_erc20`/`convert_to_balance` pattern already used in `pallet-hyper-fungible-token`.

### Proof of Concept
1. Deploy `WrappedHyperFungibleToken` on Ethereum configured with `underlying = USDC` (6 decimals).
2. Deploy `HyperFungibleToken("Wrapped USDC","wUSDC", owner)` on a remote chain; `decimals()` returns 18 (OpenZeppelin default, unmodifiable).
3. User calls `WrappedHyperFungibleToken.send({amount: 1_000_000, ...})` to bridge 1 USDC (1e6 raw units, 6 decimals).
4. The `Message.amount` field carries `1_000_000` unchanged across the ISMP POST request.
5. On the remote chain, `HyperFungibleToken.onAccept()` executes `_mint(beneficiary, 1_000_000)`, minting `0.000000000001` wUSDC (interpreting `1_000_000` as an 18-decimal amount) instead of `1` wUSDC — a 10^12x undervaluation, with no on-chain safeguard or decimal reconciliation anywhere in the referenced contracts.

    function onAccept(IncomingPostRequest calldata incoming) public virtual override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}

# HyperFungibleToken

Deploy this on every **remote chain** where the token doesn't have native supply. The contract inherits from ERC20 and [HyperApp](/developers/evm/api/hyperapp), so it is both the token and the bridge in one contract.

When tokens arrive from the home chain, the contract mints new supply to the recipient. When a user bridges back, it burns their tokens and dispatches an ISMP POST request to the home chain. On timeout, tokens are re-minted to the original sender. The HFT has no initial supply — tokens are only minted when cross-chain transfers arrive.
