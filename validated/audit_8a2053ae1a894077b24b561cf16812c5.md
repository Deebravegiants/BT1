### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw webhook body, and `ShopifyAPI::Utils::HmacValidator.validate` verifies the HMAC exclusively against that body. The `shop-domain` header, which is passed unmodified into the `WebhookMetadata` given to the host application's handler as the tenant identifier, is never part of the HMAC-covered material. This breaks the equality `shop authenticated by HMAC == shop acted upon by the handler`.

### Finding Description
`ShopifyAPI::Webhooks::Request` exposes `shop` by simply reading the `shopify-shop-domain`/`x-shopify-shop-domain` header: [1](#0-0) 

The HMAC signature is verified only over the raw request body via `to_signable_string`: [2](#0-1) 

`HmacValidator.validate` computes the signature strictly from `verifiable_query.to_signable_string` (the body) and compares it to the `hmac-sha256` header value — it never incorporates the `shop-domain` header: [3](#0-2) 

`Registry.process` validates the HMAC and then forwards `request.shop` directly to the host application's handler as the trusted tenant identifier, without any additional binding check: [4](#0-3) [5](#0-4) 

Because the app's `api_secret_key` is shared across every merchant installation of the app, any merchant that installs the app (an unprivileged party with respect to other tenants) can legitimately trigger a real webhook for their own shop, capture the resulting `(raw_body, hmac-sha256)` pair — which is fully valid — and then replay it to the same webhook endpoint while substituting an arbitrary `shop-domain` header (e.g. a victim shop that also has the app installed, or any string). Since the HMAC never covers the shop header, `HmacValidator.validate` still returns `true`, and `Registry.process` calls the handler with `WebhookMetadata#shop` set to the attacker-chosen value while the body content originates from the attacker's own account. Documentation confirms `data.shop` is intended to be trusted as the definitive per-request tenant identifier for the handler: [6](#0-5) 

### Impact Explanation
Host applications built on this gem are expected to use `WebhookMetadata#shop` to determine which merchant's data record a webhook event applies to (this is the gem's documented contract). Because `shop` is not authenticated by the HMAC, a merchant who has installed the app can forge webhook deliveries attributed to a different shop while controlling the (valid, HMAC-passing) body content. This allows cross-tenant data confusion/corruption: e.g., an `orders/create` or `app/uninstalled` webhook for shop A can be delivered under shop B's identity, causing the host app to write attacker-influenced data into another tenant's records, incorrectly treat another tenant's installation state (e.g., uninstall/GDPR-redact them), or otherwise cross tenant boundaries — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is Medium-High for any deployment that: (1) uses the app's own real HMAC signing (no exploit of leaked secrets is required — the attacker only needs the ability to install the app on a shop they control, which is normal usage), and (2) trusts `data.shop` for tenant lookups as the documented usage pattern suggests. The attack requires only knowledge of the webhook endpoint URL (learned from the merchant's own installed app's registered callback path) and the ability to replay an HTTP POST with a modified header — no cryptographic secret is needed since the vulnerable component (the header) sits entirely outside the signed payload.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `api-version`, `webhook-id`) headers in the HMAC-signed material, or independently verify that the `shop-domain` header corresponds to a shop with an active, expected session/installation before trusting it in `WebhookMetadata`. At minimum, `Utils::VerifiableQuery#to_signable_string` for `Webhooks::Request` should incorporate the shop-domain header (matching Shopify's actual webhook signing scheme, which signs the raw body but the app must independently cross-check the shop header against a known/expected value) — or the gem should document and enforce that `shop` must additionally be corroborated against the app's own topic-specific expected shop set before being handed to handlers as trusted metadata.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` (fully legitimate, unprivileged action).
2. Attacker triggers a real webhook (e.g., `orders/create`) for their own shop; Shopify sends:
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - `x-shopify-hmac-sha256: <valid signature over raw_body>`
   - `raw_body: {"id": ..., attacker-controlled order fields...}`
3. Attacker replays this exact HTTP POST to the app's webhook endpoint but changes only the header:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - keeps the same `raw_body` and `x-shopify-hmac-sha256`.
4. `ShopifyAPI::Utils::HmacValidator.validate` recomputes HMAC over `raw_body` only (per `Webhooks::Request#to_signable_string`, `lib/shopify_api/webhooks/request.rb:35-38`) — the check passes.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) calls the host app's handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker-controlled body>, ...)`, causing the host application to process attacker-controlled data under the victim shop's tenant context.
