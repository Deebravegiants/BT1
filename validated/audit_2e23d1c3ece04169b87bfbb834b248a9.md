## Audit Report

## Title
Stale `PendingSwap` entry survives `deregister`, letting a re-registered `ParaId`'s new manager complete an unconsented swap - (File: polkadot/runtime/common/src/paras_registrar/mod.rs)

## Summary
`Pallet::swap` stores a one-sided pending swap request keyed only by the initiator's `ParaId` (`PendingSwap[id] = other`), and `Pallet::do_deregister` only clears the entry keyed by the para being deregistered (`PendingSwap::<T>::remove(id)`), never scanning for entries where the deregistered para is referenced as the *target* value of another para's pending swap. This allows a new, unrelated manager who later re-registers the deregistered `ParaId` to complete a stale swap request against the original initiator without consent.

## Finding Description
`swap(origin, id, other)` requires only that the caller control `id` [1](#0-0) , and if no reciprocal entry exists yet, it unconditionally stores `PendingSwap::<T>::insert(id, other)` [2](#0-1) . The confirmation path checks only `PendingSwap::<T>::get(other) == Some(id)` [3](#0-2) , a purely `ParaId`-keyed check with no binding to the manager identity or registration epoch of `other`. `do_deregister(id)` clears deposits and lifecycle for `id` but only removes `PendingSwap::<T>::remove(id)` — i.e., the entry keyed by the para being deregistered itself, not entries where `id` appears as a *value* elsewhere in the map [4](#0-3) .

Consequently, if A calls `swap(A_id, B_id)` (storing `PendingSwap[A_id] = B_id`), and B later deregisters `B_id` and a new party C re-registers the same `ParaId` value `B_id` (only possible once `paras::Pallet::<T>::lifecycle(B_id)` returns `None`, gated by `do_reserve`'s check at [5](#0-4) ), C can call `swap(B_id, A_id)`. This passes `ensure_root_para_or_owner` for C's ownership of `B_id`, and the stale `PendingSwap[A_id] = B_id` causes the reciprocal check to succeed, triggering `do_thread_and_chain_swap` or `T::OnSwap::on_swap` between A's para and C's newly-registered para [6](#0-5)  — without A's consent to swap with C's new registration.

## Impact Explanation
This is a genuine logic flaw: the `PendingSwap` map has no invalidation on deregistration of the counterparty and no manager/epoch binding, so a stale request can be "completed" against an entirely different registration of the same numeric `ParaId`. The consequence is an unauthorized transfer of lifecycle state and `OnSwap`-tracked data (deposits, lease/crowdloan bookkeeping via `T::OnSwap::on_swap`) between the original initiator and an unrelated new registrant, which the initiator never agreed to interact with.

## Likelihood Explanation
Exploitability is real but requires a specific, timing-sensitive sequence: (1) A must have an outstanding, unconfirmed `swap` request naming `other = B_id`; (2) B (owner of `B_id`) must deregister; (3) the deregistered para's lifecycle must actually reach `None` (which depends on `schedule_para_cleanup` completing, generally requiring a session boundary) before C's `reserve`/`register` can succeed against that exact `ParaId`; and (4) C must specifically target the reused `ParaId` and call `swap` before A cancels the pending request (A can call `swap(A_id, A_id)` at any time to clear it, per the self-swap-clear branch [7](#0-6) ). All of these steps use ordinary signed extrinsics reachable by unprivileged accounts, so it is not admin/governance-gated, and the vulnerable code paths behave exactly as claimed upon reading the source.

## Recommendation
When `do_deregister(id)` runs (or when a para's registration/manager changes), also clear any `PendingSwap` entry where `id` is referenced as the target value of another para's pending swap (requires either a reverse index or an iteration/cleanup pass), or redesign `PendingSwap` to bind the request to a manager identity/registration generation so a stale request cannot be confirmed against a different registration epoch of the reused `ParaId`.

## Proof of Concept
1. Register `para_1` (Parachain, manager Alice) and `para_2` (Parathread, manager Bob).
2. Alice calls `Registrar::swap(para_1, para_2)`; verify `PendingSwap::<Test>::get(para_1) == Some(para_2)`.
3. Bob calls `Registrar::deregister(para_2)`; verify `PendingSwap::<Test>::get(para_1)` remains `Some(para_2)` (the bug).
4. Advance sessions until `paras::Pallet::<Test>::lifecycle(para_2)` is `None`.
5. Carol calls `reserve()` then `register(para_2, ...)`, becoming the new manager of `para_2`.
6. Carol calls `Registrar::swap(para_2, para_1)`.
7. Observe the call succeeds and a `Swapped` event fires, executing `T::OnSwap::on_swap`/lifecycle swap between Alice's `para_1` and Carol's newly-registered `para_2`, demonstrating the unconsented swap.

	fn do_deregister(id: ParaId) -> DispatchResult {
		match paras::Pallet::<T>::lifecycle(id) {
			// Para must be a parathread (on-demand parachain), or not exist at all.
			Some(ParaLifecycle::Parathread) | None => {},
			_ => return Err(Error::<T>::NotParathread.into()),
		}
		polkadot_runtime_parachains::schedule_para_cleanup::<T>(id)
			.map_err(|_| Error::<T>::CannotDeregister)?;

		if let Some(info) = Paras::<T>::take(&id) {
			<T as Config>::Currency::unreserve(&info.manager, info.deposit);
		}

		PendingSwap::<T>::remove(id);
		Self::deposit_event(Event::<T>::Deregistered { para_id: id });
		Ok(())
	}
