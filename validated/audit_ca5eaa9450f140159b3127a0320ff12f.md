### Title
Fee-on-transfer / deflationary / rebasing underlying tokens cause unbacked minting in `WrappedHyperFungibleToken` - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`WrappedHyperFungibleToken.send()` locks the underlying ERC20 via `safeTransferFrom` but never measures the actual amount received by the contract; it dispatches the cross-chain message using the caller-supplied `params.amount`. If the underlying token takes a fee on transfer, rebases, or is a proxy/upgradable token whose transfer semantics change (the exact bug class cited in the source report for TUSD-style tokens), the wrapper receives less than `params.amount`, yet the destination `HyperFungibleToken` mints the full `params.amount` to the recipient.

### Finding Description
In `send()`:
```solidity
if (_isWeth && msgValue >= params.amount) {
    ...
} else {
    IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
}

DispatchPost memory request = _buildDispatchPost(params);
``` [1](#0-0) 

The dispatched `Message.amount` is `params.amount` unconditionally, not the actual post-transfer balance delta, unlike `IntentGatewayV2.placeOrder`, which explicitly snapshots balances before/after transfer and mutates `order.inputs[i].amount` to the real received amount for exactly this reason:
```solidity
uint256 balBefore = IERC20(token).balanceOf(address(this));
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;
``` [2](#0-1) 

`WrappedHyperFungibleToken` has no equivalent safeguard. The `HyperFungibleToken.onAccept()` on the destination chain mints exactly `message.amount` with no independent verification against locked supply:
```solidity
Message memory message = abi.decode(request.body, (Message));
address beneficiary = _toAddr(message.to);
_mint(beneficiary, message.amount);
``` [3](#0-2) 

Each send therefore mints more wrapped supply on the destination chain(s) than is actually locked in the home-chain custody contract. `WrappedHyperFungibleTokenUpgradeable.sol` mirrors this same `send()`/`_buildDispatchPost()` pattern without a balance check.

### Impact Explanation
This is a direct route to permanent freezing/loss of funds: the home-chain `WrappedHyperFungibleToken` accumulates less underlying balance than the total minted wrapped supply circulating across all remote chains. Since custody is shared across all bridge users of that token, later users who try to bridge wrapped tokens back to the home chain (`send()` on a remote `HyperFungibleToken`, then `onAccept()` unlocking on `WrappedHyperFungibleToken`) will find insufficient underlying balance to unlock, reverting their withdrawal and permanently freezing their funds. This satisfies the "unbacked mint" / "permanent freezing of funds" criteria.

### Likelihood Explanation
Reachable with a single unprivileged `send()` transaction by any user who bridges a fee-on-transfer, deflationary, or otherwise transfer-value-altering ERC20 (including upgradable/proxy tokens like TUSD whose logic can change to introduce such behavior) through a deployed `WrappedHyperFungibleToken` instance. No governance or privileged role is required to trigger the discrepancy — only that the token owner configures the wrapper with such a token as `underlying`, which is a normal deployment configuration decision, not an attack requiring a malicious admin.

### Recommendation
In `send()` (and the upgradeable variant), measure the actual balance delta on the wrapper after `safeTransferFrom` and use that value both for the dispatched `Message.amount` and any accounting, mirroring the pattern already used in `IntentGatewayV2.placeOrder`. Alternatively, document and technically restrict `underlying` tokens to standard, non-fee, non-rebasing ERC20s (e.g., a deployment-time balance-based sanity check that reverts if received amount != `params.amount`).

### Proof of Concept
1. Deploy `WrappedHyperFungibleToken` on chain A, `HyperFungibleToken` on chain B, register peers.
2. Configure the wrapper's `underlying` to a fee-on-transfer token (1% fee), simulating an upgraded/malicious TUSD-like token.
3. User calls `send({amount: 1000, to: recipient, dest: chainB, ...})`. `safeTransferFrom` moves only 990 tokens into the wrapper (fee burned), but the dispatched message still encodes `amount: 1000`.
4. On chain B, `onAccept()` mints `1000` wrapped tokens to `recipient` — 10 more than what is actually custodied on chain A (990).
5. Repeating this drains the ratio of backed to minted supply; eventually a legitimate unlock request on chain A reverts due to insufficient underlying balance, permanently freezing that user's bridged funds.
