### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook confusion - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature purely from the raw request body (`to_signable_string` returns `@raw_body`), while the `topic`, `shop-domain`, `api-version`, and `webhook-id` values are all read directly from unauthenticated HTTP headers via `shopify_header`. `Registry.process` validates the HMAC and then hands `request.shop` (and `request.topic`, `request.webhook_id`) straight to the app's `WebhookHandler`, treating the header value as the authenticated tenant identifier even though it was never part of the signed payload.

### Finding Description
The bug-class analog here is the reported "field acted on but not covered by the authentication check" pattern: the report describes IDs that are trusted/relied upon without being cryptographically bound to the operation that creates them, letting an attacker substitute a colliding/different value. In this gem, the equivalent identity binding that should hold is:

`hmac_valid(raw_body, secret) == true` should imply `(topic, shop, webhook_id, api_version)` are exactly the values Shopify sent for *this* body.

But the implementation only proves integrity of `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are pulled from headers that are never included in the signable string: [2](#0-1) 

`Registry.process` validates only the HMAC and then forwards the header-derived `shop`/`topic`/`webhook_id` to the handler without any additional binding check: [3](#0-2) 

`HmacValidator.validate` calls `verifiable_query.to_signable_string`, i.e. only the body, when computing/comparing the signature: [4](#0-3) 

Because the signature never binds `shop-domain` to the body, any entity that can capture one genuine, validly-signed webhook delivery for *its own* shop (which any merchant/dev store owner can trivially generate by installing the app and triggering an event) can replay that exact `raw_body` + `hmac-sha256` header pair while swapping the `shop-domain` (and/or `topic`/`webhook_id`) header to a victim shop's domain. `Utils::HmacValidator.validate` will still return `true` because it only recomputes/compares against `@raw_body`, and `Registry.process` will dispatch the handler with `shop: request.shop` set to the attacker-chosen victim domain.

### Impact Explanation
This breaks the tenant/authentication boundary the gem's webhook verification is documented to provide: HMAC validation is supposed to let a host app trust `request.shop` as "this event genuinely originated from this shop." Since the shop identity is not bound to the signature, an attacker-controlled shop can forge webhook deliveries that are processed as if they came from any other shop of the attacker's choosing. Any host application that relies on `WebhookMetadata#shop` (populated straight from `request.shop`) to select which tenant's session/access token/business data to update — mandatory GDPR webhooks (`customers/redact`, `shop/redact`, `customers/data_request`) being especially sensitive — would perform actions against the wrong tenant, which is a cross-tenant access/integrity violation.

### Likelihood Explanation
Medium-High. Any unprivileged actor who can install the target app on any shop (including their own free/dev store) can capture a legitimately-signed webhook (body + HMAC) for a chosen topic, then replay it to the app's webhook endpoint with a modified `shopify-shop-domain`/`x-shopify-shop-domain` header. No knowledge of `api_secret_key` or any credential belonging to the victim is required — only the ability to trigger a webhook that Shopify signs for the attacker's own shop and to make an HTTP POST with custom headers to the app's public webhook endpoint.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook_id`) header values in the material that is HMAC-verified, or otherwise cryptographically bind them to the signed body (e.g., verify a combined string of `headers + body`, or require the host app to independently confirm that `request.shop` corresponds to a shop with an active, previously-established session/installation before dispatching the handler). At minimum, document that `request.shop` is unauthenticated and must be independently checked against known installed shops before being trusted by the handler.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and triggers a webhook event (e.g. `orders/create`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sent — this HMAC is valid because Shopify signed it with the real `api_secret_key`.
2. Attacker replays the exact same body to the app's public webhook endpoint but replaces the `shop-domain` header with `victim-shop.myshopify.com`:
```
POST /webhooks HTTP/1.1
X-Shopify-Topic: orders/create
X-Shopify-Hmac-Sha256: <captured-valid-hmac>
X-Shopify-Shop-Domain: victim-shop.myshopify.com
<captured raw body>
```
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Utils::HmacValidator.validate(request)` recomputes the HMAC over `request.to_signable_string` (= raw body only) and it matches, so validation passes. [5](#0-4) 
4. `Registry.process` invokes the handler with `shop: request.shop` == `"victim-shop.myshopify.com"`, even though Shopify never actually sent this payload for that shop, allowing the host app to act on the victim's tenant using attacker-supplied data.
