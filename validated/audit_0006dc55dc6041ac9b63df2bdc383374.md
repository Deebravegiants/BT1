### Title
Unrestricted `approve` call in Emporium stateless op lets any prover steal Emporium's residual ERC20 balances - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction` executes a batch of arbitrary `(endpoint, callData, value)` operations decoded from `circomData.externalActionData.externalActionMetadata`. When the batch is unsigned (`stack.signerAddress == address(0)`, "CASE 2: Stateless Interaction"), the contract itself directly performs `op.endpoint.call{value: op.value}(op.callData)` with no restriction on the callee or calldata other than blocking two specific selectors. This mirrors the Connext Executor.sol bug class: an attacker can set `op.endpoint` to any ERC20 token and `op.callData` to `approve(attacker, type(uint256).max)`, granting themselves an unlimited allowance over any token balance the Emporium contract happens to hold.

### Finding Description
`runAction` at [1](#0-0)  loops over `stack.ops` and, for the stateless branch, only blocks the `callHinkalWallet` and `doSendToRelay` selectors before performing the raw external call:
```solidity
bytes4 selector = bytes4(op.callData);
if (selector == IHinkalWallet.callHinkalWallet.selector || selector == IHinkalWallet.doSendToRelay.selector) {
    revert UnauthorizedWalletCall();
}
(success, err) = op.endpoint.call{value: op.value}(op.callData);
```
There is no allow-list of callable `endpoint`s, and the ERC20 `approve` selector is not filtered.

The only economic safety net is the post-call balance check:
```solidity
int256 balanceChange = int256(balancesAfter[i]) - int256(balancesBefore[i]);
...
if (balanceChange < 0) revert BalanceChangeShouldBePositive();
``` [2](#0-1) 

This check only guards against a *transfer out* within the same transaction — it does nothing to stop `approve`, which changes zero balances but creates a standing allowance. The code comment itself confirms Emporium can carry a nonzero token balance **across transactions**: "the only case when balanceChange can be < 0, when there were some funds on emporium before the call" [3](#0-2) .

Note that the stateless-op batch (`op.endpoint`, `op.callData`) is committed to the ZK-proof's public input via `calldataHash`, which is derived over `circomData.externalActionData` (containing the metadata) [4](#0-3)  and checked in `performHinkalChecks` [5](#0-4) . This proves the *batch itself* is authorized by the prover, but the prover only needs to own their own (possibly dust-sized) shielded UTXO to submit a valid proof — nothing ties the callee/calldata to being restricted to assets that belong to that same prover. Any Hinkal user can therefore submit a fully valid, self-authorized transaction whose op payload targets an unrelated token/allowance to sweep whatever balance Emporium is holding for other users or transient DeFi flows.

### Impact Explanation
Once the attacker's transaction succeeds, `EmporiumUpgradeable` has granted `type(uint256).max` allowance on an arbitrary ERC20 token to the attacker. In a follow-up, ordinary `token.transferFrom(emporium, attacker, balance)` call (no Hinkal proof needed at all), the attacker can drain any current or future balance of that token sitting in the Emporium contract — including leftover funds from other users' multi-op DeFi flows, dust from partial fills/slippage, or funds deposited by other users that transiently reside in Emporium. This is theft of protocol/user funds not authorized by the affected users' provers or signers, satisfying the High-impact bar ("theft ... of protocol/relay fees, temporary freezing of user funds, executing calls or moving assets a wallet owner or prover never authorized").

### Likelihood Explanation
Likelihood is moderate-to-high: it requires only an unprivileged EOA capable of generating a valid Hinkal proof for their own (arbitrarily small) shielded UTXO and submitting a `transact` call with `externalActionId == HINKAL_EMPORIUM_ACTION_ID`, `stack.signerAddress == address(0)`, and one crafted op. No admin, relay, or other-user key is required. The main precondition is that Emporium hold a nonzero ERC20 balance at exploit time (residual balance across transactions, as acknowledged by the code's own comment), which is a normal expected state for a "Batched DeFi Execution" contract used across multi-step flows.

### Recommendation
- Restrict stateless-op `callData` to a selector allow-list appropriate for DeFi router/swap calls, or require `endpoint` to be an allow-listed router contract (similar to `ExternalActionBaseUpgradeable.onlyAllowedRecipient` pattern already used elsewhere).
- Explicitly block the ERC20 `approve`/`increaseAllowance`/`permit`-style selectors (or any selector that can grant `msg.sender`/attacker-controlled spender an allowance) in the stateless branch, not just the two `IHinkalWallet` selectors.
- Adopt the "funds left after a call are claimable by anyone" mitigation Connext ultimately used, or better, never allow a stateless/unsigned op batch to leave standing allowances at all — revoke any allowance granted by an op after the batch completes if it's not consumed by the same op.

### Proof of Concept
1. Emporium `E` holds `1000 USDC` left over from prior user flows (acknowledged possible per the balance-underflow comment).
2. Attacker (any EOA with a valid, arbitrary shielded UTXO, even 0-value/dust) builds a Hinkal `transact` call with `circomData.externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID` and `externalActionMetadata` encoding an `EmporiumStack` with `signerAddress = address(0)` and a single op:
   - `op.endpoint = USDC_ADDRESS`
   - `op.invokeWallet = false`
   - `op.callData = abi.encodeWithSelector(IERC20.approve.selector, attacker, type(uint256).max)`
   - `op.value = 0`
3. Attacker generates a valid ZK proof over their own UTXO/circomData (satisfying `calldataHash` and the circuit checks) and calls `Hinkal.transact(...)`.
4. `EmporiumUpgradeable.runAction` executes CASE 2, calling `USDC.approve(attacker, type(uint256).max)` from `E`. `balanceChange` for USDC is `0`, so `BalanceChangeShouldBePositive` does not revert.
5. Separately (outside Hinkal, with no proof needed), attacker calls `USDC.transferFrom(E, attacker, 1000e6)`, draining Emporium's residual USDC balance.
