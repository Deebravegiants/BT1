### Title
Unbounded, weight-independent `Vec<Message>` batches in `handle_unsigned` allow free computational DoS via pool-validation re-execution - (File: `modules/pallets/ismp/src/lib.rs`)

### Summary
`pallet-ismp`'s `handle_unsigned` extrinsic is a permissionless, unsigned, fee-free call that accepts an unbounded `Vec<Message>` and is charged a **fixed** weight regardless of how many messages/proofs it contains. Because `ValidateUnsigned::validate_unsigned` must fully execute the same message batch (`Self::execute(messages.clone())`) just to admit the transaction into the pool, an unprivileged submitter can force expensive consensus/state-proof verification and message dispatch to run twice per submission, for free, and can fan out many such calls concurrently. This mirrors the Superset issue: an unauthenticated/low-privilege actor triggers unbounded, uncharged, concurrent expensive work, leading to denial of service.

### Finding Description
`handle_unsigned` is declared as: [1](#0-0) 

The weight annotation `#[pallet::weight(weight())]` calls a **parameterless** function — it does not scale with `messages.len()` or with the size/complexity of the proofs inside each `Message` (state-machine height, membership proof size, number of requests per `RequestMessage`, etc.). The call itself takes `messages: Vec<Message>` with no length bound (`BoundedVec`) and no `MaxMessages` config parameter, meaning a caller can pack an arbitrarily large batch into a single extrinsic.

Because this is an **unsigned** transaction, `ValidateUnsigned::validate_unsigned` is invoked by every node's transaction pool to admit it, and this validation path itself fully executes the batch: [2](#0-1) 

This means the full cost of state-machine commitment verification, membership-proof verification (for every request/response in the batch), and dispatch-to-module callbacks is paid by the node during pool validation — before the fixed weight is ever charged, and before the extrinsic is even included in a block. The docs acknowledge the design intent ("malformed messages or those with invalid proofs are filtered out by the transaction pool validation logic preventing unnecessary processing") but that logic only rejects *invalid* proofs; it does not bound the *size* of valid-looking batches nor charge fees/weight proportional to the amount of proof-verification work performed, and the extrinsic is explicitly documented as free: [3](#0-2) 

An attacker can submit many concurrent `handle_unsigned` calls, each carrying a maximal batch of syntactically valid (state-machine-committed) requests/responses with large membership proofs, causing every node's transaction-pool validation (and later execution, if admitted) to perform large amounts of cryptographic verification work for zero fees — the same "unbounded concurrent requests with unmetered per-request cost" pattern as the Superset dashboard-export DoS.

### Impact Explanation
Nodes running `pallet-ismp` with the `unsigned` feature enabled (all Hyperbridge/coprocessor and connected-chain nodes accepting unsigned ISMP messages) can be forced to spend unbounded CPU/verification time per submitted transaction, both during gossip/pool validation and during block execution, without the submitter paying any transaction fee or weight cost proportional to the work performed. Sustained concurrent submission from a single account (no signature/authentication required at all — even weaker than Superset's "authenticated user" precondition) can degrade block production, delay legitimate message delivery, and destabilize the relayer network — a denial-of-service condition on the message-delivery path that the entire protocol depends on.

### Likelihood Explanation
Likelihood is high: `handle_unsigned` requires no signature, no fee, and no special privilege (`ensure_none(origin)`), and the batch size/proof complexity is entirely attacker-controlled. Any relayer-capable actor who can construct or replay valid-looking (state-committed) message batches can trigger this at will, and can trivially parallelize many such submissions across nodes.

### Recommendation
- Bound the number of messages/requests per `handle_unsigned` call (e.g., a `BoundedVec` with a `MaxMessagesPerBatch` config constant), and reject calls that exceed reasonable limits during `validate_unsigned` before any proof verification runs.
- Make weight (and therefore any resource accounting / pool priority) scale with the actual size of the batch (number of requests/responses, proof byte length) rather than a fixed constant.
- Consider cheap, cacheable pre-checks (e.g., structural size limits, per-account/IP rate limiting at the pool layer) that reject oversized or duplicate-heavy batches prior to running full consensus/membership verification in `validate_unsigned`.

### Proof of Concept
1. Construct a `handle_unsigned` call whose `messages: Vec<Message>` contains the maximum number of `RequestMessage`/`ResponseMessage` entries the codec/block size permits, each with a valid membership proof against a real, already-verified state-machine commitment.
2. Submit many such extrinsics concurrently from a single unsigned account (no funds/signature required) to multiple nodes.
3. Each submission forces every receiving node to run `Self::execute(messages.clone())` in full inside `validate_unsigned` (verifying all included membership proofs and dispatching to module callbacks) merely to decide pool admission — costing significant CPU with zero fee charged, and repeatable indefinitely since nothing in the code bounds batch size or scales weight with batch content.
