### Title
Forged xpub/publicKey entries synced/imported into StorageFormatLegacy are trusted without cryptographic linkage to the wallet account, enabling address substitution - ([File: features/public-key-provider/module/store/formats/storage/legacy.ts])

### Summary
`assertStorageFormatLegacy` and `StorageFormatLegacyBuilder` only perform structural/type validation (string keys, and `xpub`/`publicKey` serialization format checks), not cryptographic verification that a stored `xpub`/`publicKey` actually belongs to the claimed `walletAccountName`/`derivationPath`. Because hardware-wallet public keys are persisted via `WalletAccounts#replaceAll` from a fusion-sync channel payload and later re-validated only through this same structural check, a forged entry under an existing `walletAccountName`/`derivationPath` combination will be accepted and returned as authentic key material.

### Finding Description
`assertStorageFormatLegacy` checks only that `walletAccountName`/`derivationPath` are strings and that `publicKey`/`xpub` pass format-only checks: [1](#0-0) 

The format validators are trivial and do not verify any cryptographic relationship to the account: `xpub.validateSerialized` only checks the string prefix `xpub`, and `publicKey.validateSerialized` only checks that the value is a string: [2](#0-1) [3](#0-2) 

For hardware wallets, this storage is populated from `WalletAccounts#replaceAll`, which is the fusion sync channel handler; it directly replaces `#hardwareWalletPublicKeys` with the `accounts` field of incoming sync data without going through `assertStorageFormatLegacy`: [4](#0-3) 

That value is persisted via `#savePublicKeys` directly to `hardwareWalletPublicKeysAtom`: [5](#0-4) 

Later, `PublicKeyStore#getData` reads from `hardwareWalletPublicKeysAtom`, wraps it with `StorageFormatLegacyBuilder`, which does invoke `assertStorageFormatLegacy` — but this only enforces the same structural checks described above, not authenticity: [6](#0-5) [7](#0-6) 

Finally, `PublicKeyProvider#exportPublic` trusts the cached value for hardware wallet accounts (or dev builds) without further validation, returning it directly to the caller (a dapp/RPC request): [8](#0-7) 
The `#traversePathForXpub` fallback similarly derives child keys directly from any `xpub` found in the store for a shortened path, with no check that this xpub is legitimate: [9](#0-8) 

If an attacker can influence the fusion sync payload/import blob (per the question's stated threat model of a compromised sync payload or crafted backup import), they can construct a `StorageFormatLegacy`-shaped object with a forged, syntactically-valid `xpub` under a victim's existing `walletAccountName`/`derivationPath`. This passes `assertStorageFormatLegacy` because the checks never verify that the xpub is derived from the actual hardware device/seed for that account.

### Impact Explanation
If exploited, a dapp request for a public key/xpub for a hardware wallet account would silently return attacker-controlled key material instead of the true derived key, letting the attacker substitute receive addresses (funds sent to an attacker-controlled address) or spoof signing-related data derivation for that account. This matches a wrong-account / address-substitution class of wallet compromise.

### Likelihood Explanation
This requires the attacker to be able to inject/modify the fusion sync payload or backup/import blob that feeds `WalletAccounts#replaceAll` — this is an external precondition (compromised sync channel, malicious backup import, or MITM on sync data) that is not verified by any tool available in this codebase context; the code path itself does not perform origin/authenticity binding on `accounts` field content beyond structural typing, so once such influence exists, exploitation is straightforward and repeatable via a crafted payload.

### Recommendation
Add cryptographic verification when accepting `xpub`/`publicKey` entries from sync/import: e.g., validate `xpub` chain-code/parent-fingerprint against a value derived independently from the wallet's known master/account-level public key (already trusted via hardware device confirmation), or require an authenticated/signed attestation from the hardware device for any account-level xpub before storing/trusting it. At minimum, `assertStorageFormatLegacy` should not be the sole gatekeeper for data arriving via `WalletAccounts#replaceAll`; that path should validate xpub provenance against previously device-confirmed values and reject changes to already-established `walletAccountName`/`derivationPath` entries unless reconfirmed with the hardware wallet.

### Proof of Concept
1. Unit test in `features/wallet-accounts/src/module/__tests__/index.test.ts` style: simulate `channelOptions.processOne` with a fusion `data.accounts` payload containing a forged `xpub` (valid `xpub...` prefix, arbitrary chain code/key) under an existing hardware `walletAccountName` and `derivationPath` that already has a legitimate entry from a previous session.
2. Assert `walletAccounts.getAccounts()` / `hardwareWalletPublicKeysAtom.get()` now returns the forged entry (no rejection occurs).
3. In `features/public-key-provider/module/__tests__`, instantiate `PublicKeyProvider` with the same `hardwareWalletPublicKeysAtom`/`publicKeyStore` wired to a hardware `walletAccount`, call `getExtendedPublicKey`/`getPublicKey` for that `walletAccountName`/`derivationPath`.
4. Assert the returned `xpub`/`publicKey` equals the forged value (expected: should be rejected/flagged as untrusted, but currently is returned as authentic), demonstrating the vulnerability.
