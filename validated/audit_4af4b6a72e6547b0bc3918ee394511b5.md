### Title
`detect_fraud` unconditionally returns `Ok(false)`, disabling all Orb-side fraud detection during signup - ([File: src/plans/mod.rs])

### Summary
`MasterPlan::detect_fraud` in `src/plans/mod.rs` contains no fraud logic: whenever a `Some(pipeline)` is passed in, it immediately returns `Ok(false)` with the comment `// FOSS: WE HAVE DELETED ALL FRAUD CHECKS`. This makes `SignupReason::Fraud` unreachable through this code path for any biometric pipeline content, regardless of malformed or suspicious iris/face data.

### Finding Description
`do_signup` calls `self.detect_fraud(orb, debug_report, pipeline.as_ref()).await?` and uses the boolean result to decide `signup_reason`: [1](#0-0) 
The implementation of `detect_fraud` short-circuits to `Ok(false)` for `None`, and for `Some(_)` it falls through the empty check body straight to `Ok(false)`: [2](#0-1) 
Supporting this, the underlying `FraudChecks` plan and `Report` struct are hard-coded to zero checks (`N_FRAUD_CHECKS: usize = 0`), so even if `detect_fraud` were extended to consult a `Report`, there is currently no check implementation to consult: [3](#0-2) [4](#0-3) 
As a result, `fraud_detected` in `do_signup` is always `false` whenever `skip_fraud_checks()` is `false` (the default, non-test path), so `signup_reason` can only ever be `SignupReason::Failure` (if pipeline is `None`) or `SignupReason::Normal` (if pipeline is `Some`) — `SignupReason::Fraud` is dead code on this path.

### Impact Explanation
Any attacker who completes biometric capture (producing `Some(pipeline)`, e.g. with malformed iris codes, mismatched shares, or other anomalies detectable by a fraud pipeline) will always have their signup evaluated as `SignupReason::Normal` with respect to Orb-side fraud detection, and this reason is propagated into enrollment and backend reporting (`report_signup_reason`, `enroll_user`, PCP construction): [5](#0-4) 
This is a fail-open enforcement bug for local fraud detection: the Orb never flags a signup as fraud on the device side, so any fraud mitigation is fully offloaded (silently) to the backend, with no local defense-in-depth. This matches a liveness/fraud-bypass-class impact in the Orb bounty scope (biometric integrity control bypass).

### Likelihood Explanation
This is deterministic and unconditional, not dependent on any race, timing, or malformed input trick — every non-`skip_fraud_checks` signup with a produced pipeline hits this exact code and always returns `false`. No privileges beyond completing a normal signup session (attacker-controlled biometric presentation) are required.

### Recommendation
Restore or reintroduce real fraud-check logic in `detect_fraud` / `FraudChecks::run`, or, if fraud enforcement is intentionally delegated entirely to the backend in this FOSS build, make that explicit and ensure the backend enforces a fail-closed policy on fraud data so device-side removal of checks cannot be relied upon by an attacker as a bypass. At minimum, this should be flagged as a known limitation of the FOSS build rather than silently returning `false`.

### Proof of Concept
Unit test in `src/plans/mod.rs` (or a new test module) constructing a `MasterPlan` and a `biometric_pipeline::Pipeline` fuzzed with clearly malformed data (e.g., empty/zeroed iris code shares, mismatched left/right mask codes), then calling `detect_fraud(&mut orb, &mut debug_report, Some(&pipeline))` for many fuzzed variants and asserting the result is always `Ok(false)`:
```rust
#[tokio::test]
async fn detect_fraud_never_flags_fraud() {
    for fuzzed_pipeline in fuzzed_pipelines() { // malformed iris codes, mismatched shares, etc.
        let result = master_plan.detect_fraud(&mut orb, &mut debug_report, Some(&fuzzed_pipeline)).await;
        assert_eq!(result.unwrap(), false);
    }
}
```
Expected: assertion passes for all fuzzed inputs, proving `detect_fraud` is a no-op regardless of pipeline content.
