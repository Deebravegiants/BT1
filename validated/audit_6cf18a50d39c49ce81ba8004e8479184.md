### Title
Webhook shop-domain/topic identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authentic solely because `Utils::HmacValidator.validate(request)` returns true, but the HMAC is computed only over the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` fields — all of which are read from unauthenticated HTTP headers and handed to the app's handler as trusted identity — are never included in the signed content.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 
while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `HMAC(secret, to_signable_string)`, i.e. `HMAC(secret, raw_body)`: [3](#0-2) 

`Registry.process` only gates on this body-only HMAC before dispatching to the app's handler with `request.shop`, `request.topic`, etc. treated as verified identity: [4](#0-3) 

This is the same bug class as the referenced report: a field that is *acted upon* (here, `shop`/`topic`) is not covered by the authenticity check (here, the HMAC), so the two can be made to disagree. The equality the gem implicitly assumes is:

`hmac_valid(raw_body) == (shop_header == actual_sending_shop AND topic_header == actual_topic)`

This equality does not hold: HMAC validity only proves the body bytes were signed by the secret at some point; it says nothing about which shop or topic that signature was originally issued for.

### Impact Explanation
An attacker who controls any shop that has the target app installed (e.g., a free development store, which requires no privileged credentials of the app or of a victim merchant) can:
1. Trigger a real webhook delivery for their own shop/topic (fully legitimate, no secrets needed — they just perform an action in their own store that fires a registered webhook), capturing the genuine `raw_body` and its valid `shopify-hmac-sha256` value from Shopify's request to the app's endpoint (or via a local proxy they run in front of their own endpoint).
2. Replay that exact `(raw_body, hmac)` pair to the app's public webhook route, substituting the `shopify-shop-domain` header with a victim shop's domain, and/or the `shopify-topic`/`shopify-webhook-id` headers with a different value.
3. `HmacValidator.validate` still returns `true` because the HMAC only covers `raw_body`, which is unchanged. `Registry.process` dispatches to the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` reflecting the attacker-chosen, forged shop/topic.

Documented usage patterns pass `data.shop` directly into app business logic (e.g., queuing jobs keyed by shop, as shown in the gem's own docs), so this directly enables cross-tenant data confusion/corruption — for example, triggering `shop/redact` or `customers/redact` compliance actions against a victim shop's data, or injecting fabricated `orders/create`/`app/uninstalled` events attributed to a shop the attacker does not own. This matches the Critical "cross-tenant access" impact category, since a boundary that should isolate one merchant's webhook stream from another's is not actually enforced by the cryptographic check the gem performs.

### Likelihood Explanation
Likelihood is meaningful but not trivial: the attacker needs (a) their own store with the target app installed (freely obtainable via a Shopify Partner dev store — no privileged credentials of the app owner or victim required) and (b) a body/topic pair whose semantics are still damaging when replayed under a different shop/topic header (e.g., an empty-body or attacker-shaped-body mandatory-compliance webhook, or a webhook whose body doesn't strongly self-identify the shop). Because `shop`, `topic`, and `webhook_id` are all excluded from the signed content, any handler logic that branches on those header-derived fields (which is the officially documented pattern) is exposed. This does not require the app's `client_secret`, an access token, or any credential belonging to the victim — only the ability to run one's own store and interact with the public webhook endpoint, which is unprivileged internet access.

### Recommendation
Include `shop`, `topic`, and `webhook_id`/`api_version` in the value that is authenticated, not just the raw body — e.g., verify the raw body HMAC as Shopify computes it, but additionally cross-check the `shopify-shop-domain` header value against an app-known set of shops the app has session data for (defense in depth), and consider incorporating the delivery-specific headers into a secondary integrity check performed by the host app before trusting `WebhookMetadata#shop`/`#topic`. At minimum, document explicitly and loudly that `data.shop`/`data.topic` in `WebhookMetadata` are **not** covered by the HMAC and must not be trusted as tenant identity without an independent binding (e.g., matching against the shop for which the webhook topic was registered).

### Proof of Concept
```ruby
# Attacker owns shop "attacker-shop.myshopify.com" with the app installed,
# and captures a legitimate webhook delivery + its valid HMAC for some topic,
# e.g. an empty-body mandatory webhook like "customers/data_request":

raw_body = "{}"
valid_hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_client_secret_KNOWN_ONLY_TO_SHOPIFY_AND_APP, raw_body)
)
# ^ attacker does not compute this themselves -- Shopify computed and sent it
#   to the attacker's own registered webhook endpoint for their own shop.

# Attacker replays it against the app's public webhook endpoint,
# substituting the shop-domain header to impersonate a victim shop:
forged_headers = {
  "shopify-topic"       => "customers/data_request",
  "shopify-hmac-sha256" => valid_hmac,                       # unchanged, still valid
  "shopify-shop-domain" => "victim-shop.myshopify.com",      # attacker-controlled
  "shopify-webhook-id"  => "attacker-chosen-id",
  "shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) => true, because it only checks HMAC(secret, raw_body).
# Handler is invoked with WebhookMetadata(shop: "victim-shop.myshopify.com", topic: "customers/data_request", ...)
# even though this delivery never originated for that shop or topic.
```

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
