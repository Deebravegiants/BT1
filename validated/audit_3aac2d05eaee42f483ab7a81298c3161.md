### Title
Webhook `shop` (and `topic`/`webhook-id`) Header Fields Are Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw request body for HMAC verification, while the `shop`, `topic`, and `webhook_id` values used by the handler for tenant identification and dispatch are parsed straight from unauthenticated HTTP headers. This breaks the equality that should hold between "bytes verified by HMAC" and "bytes the handler acts on," letting any party who can obtain one validly-signed webhook body (e.g. by installing the app on their own shop) replay it with a forged `shop-domain` header to make the receiving app attribute the payload to an arbitrary victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, and `webhook_id` are read directly from HTTP headers with no cryptographic binding to the HMAC: [2](#0-1) [3](#0-2) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which internally calls `verifiable_query.to_signable_string` (i.e. only the body) and compares it against the `hmac` value, and then immediately dispatches to the handler using the unauthenticated `request.shop`: [4](#0-3) 

`HmacValidator.validate`/`validate_signature` only ever inspects `verifiable_query.to_signable_string` and `verifiable_query.hmac` — it never incorporates the `shop` header into the signed material: [5](#0-4) 

Because Shopify signs webhook bodies with the **app's single shared `client_secret`** (the same secret is used for every shop that installs the app, not a per-shop key), an unprivileged user who installs the public app on their own shop receives a validly HMAC-signed body/HMAC pair. Nothing in this library prevents that identical `(raw_body, hmac)` pair from being replayed to the same webhook endpoint with the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header rewritten to any other shop's domain: `HmacValidator.validate` will still return `true` because the signed bytes (the body) are unchanged, yet `request.shop` used by the handler will report the attacker-chosen victim domain.

The root cause is an identity-binding mismatch: **bytes verified (body only) != bytes acted upon (headers, including `shop`)**.

### Impact Explanation
Any app built on this gem that uses `WebhookMetadata#shop` to key merchant data (e.g., to look up a session/store record, disable a feature, write to a tenant-scoped table, or trigger a side effect scoped by shop) can be made to process attacker-supplied webhook data under the identity of a shop the attacker does not own — a cross-tenant access/write primitive achieved purely by replaying a legitimately-obtained signature with a forged shop header. This matches the Critical "cross-tenant access" impact bucket, since the vulnerability crosses the tenant/shop identity boundary that the HMAC is supposed to enforce.

### Likelihood Explanation
Likelihood is high for any consumer that trusts `WebhookMetadata#shop` without independently cross-checking it (e.g., against a stored session for that shop or comparing to an expected value). Obtaining a valid `(raw_body, hmac)` pair requires no privileges beyond installing the target's public app on any shop (including a free development store) and capturing one webhook delivery, which any unprivileged internet user can do.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the material that is verified, not just the raw body — e.g., have `HmacValidator`/`to_signable_string` also incorporate the shop domain header, or have `Registry.process` cross-validate `request.shop` against a shop that is independently known/authenticated by the host app (e.g., an active session) before invoking the handler. At minimum, document prominently that `request.shop` is not authenticated by the HMAC and must not be trusted as a tenant identifier without additional verification.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled shop `attacker-shop.myshopify.com` (any unprivileged user can do this for a public app).
2. Trigger any webhook event (e.g., `orders/create`) and capture the exact raw POST body and the `X-Shopify-Hmac-Sha256` header value sent by Shopify to the app's webhook endpoint — this HMAC is valid because Shopify signs it with the app's shared `client_secret`.
3. Replay the identical raw body and HMAC header to the same webhook endpoint, but replace the `X-Shopify-Shop-Domain` header with `victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` which succeeds (only body bytes are checked), then dispatches `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` to the app's handler — the app now processes attacker-controlled data attributed to a shop the attacker never authenticated against.
