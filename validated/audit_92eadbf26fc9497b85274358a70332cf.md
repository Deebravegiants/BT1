### Title
OAuth authorization-code grant sends `client_secret` to an unvalidated `shop` host, unlike every other grant flow in the gem - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` and `ShopifyAPI::Auth::Oauth.validate_auth_callback` build the OAuth target host directly from the caller-supplied `shop` string, without ever calling `ShopifyAPI::Utils::ShopValidator.sanitize!`. Every other credential-exchanging flow in this gem (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.exchange_token`) explicitly validates `shop` through `ShopValidator` before using it to build the request host. `oauth.rb` is the one path that skips this binding, and it is also the path most likely to receive `shop` straight from an unauthenticated query parameter (`?shop=`), because that is the standard way Shopify apps start an OAuth install flow.

### Finding Description
The intended invariant, enforced everywhere else in the gem, is: *host that receives `client_secret` == a validated `*.myshopify.com` (or other Shopify-trusted) domain*.

- `ClientCredentials.client_credentials`: `validated_shop = Utils::ShopValidator.sanitize!(shop)` before building the session/host. [1](#0-0) 
- `RefreshToken.refresh_access_token`: same pattern. [2](#0-1) 
- `ShopValidator` itself exists specifically to reject hosts outside `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`). [3](#0-2) 

In contrast, `Oauth.begin_auth` takes `shop:` and uses it unvalidated to build the redirect target: [4](#0-3) 

and `auth_base_uri` interpolates `shop` straight into a URL with no sanitization: [5](#0-4) 

`Oauth.validate_auth_callback` then uses `auth_query.shop` (again unvalidated by `ShopValidator`) to construct the `null_session` and POST the app's `client_secret` to `https://#{shop}/admin/oauth/access_token`: [6](#0-5) 

The only integrity check present is `Utils::HmacValidator.validate(auth_query)`, which authenticates that the *set* of query parameters (`code, host, shop, state, timestamp`) was signed with `api_secret_key` — it does not constrain `shop` to a Shopify domain: [7](#0-6) [8](#0-7) 

So the binding this gem is supposed to enforce is:
`host that receives client_secret == ShopValidator.sanitize!(shop)`

For the OAuth authorization-code flow this equality is never checked; `shop` flows straight from `begin_auth`'s untrusted input parameter through to the `client_secret`-bearing POST in `validate_auth_callback`.

### Impact Explanation
`begin_auth`'s `shop` parameter is, by the documented usage pattern of this gem (see `docs/usage/oauth.md`), taken directly from the app's initial unauthenticated request (the `?shop=` query string a merchant/attacker supplies to start install). Because it is never passed through `ShopValidator.sanitize!`, a caller can supply an arbitrary hostname as `shop`, and:
1. `begin_auth` will build an authorization URL (`auth_base_uri(shop) + "/oauth/authorize?..."`) pointing at an attacker-controlled host, sending the app's `client_id`, `scope`, and `redirect_uri` there (host-confusion/redirect issue on the front channel).
2. If a host application constructs its callback `AuthQuery` from request parameters (as documented) and does not itself re-validate `shop` against the domain it expects, `validate_auth_callback` will happily accept any `shop` value that the HMAC covers and POST the app's `client_secret` to `https://#{shop}/admin/oauth/access_token`. Since `HmacValidator` only proves the query string was signed by the shared secret (or is required to be, in the legitimate flow originating from Shopify), it does nothing to constrain the *domain* — it is possible for a caller to construct/replay a manipulated `AuthQuery` (e.g., in test/integration harnesses, or where the host app forwards raw request params without confirming `shop` is the same shop that initiated the flow) causing `client_secret` to be sent to a non-Shopify host.

This matches the report's underlying bug class: an identity-binding field (`shop`, which determines where the app's secret is sent) is authenticated as "signed" but not authenticated as "the correct/trusted domain," breaking the equality `host receiving client_secret == validated Shopify domain` that the rest of this codebase enforces via `ShopValidator`.

### Likelihood Explanation
This is reachable purely by an unprivileged caller supplying `shop` to `begin_auth` — no access token, secret, or privileged account is required, and `begin_auth` is explicitly documented as being called with unauthenticated request input. The absence of `ShopValidator` in `oauth.rb`, while present in three sibling flows (`client_credentials.rb`, `refresh_token.rb`, `token_exchange.rb`), demonstrates this is an inconsistency/omission in the gem itself, not a host-application misuse of a documented API.

### Recommendation
In `lib/shopify_api/auth/oauth.rb`, validate `shop` with `Utils::ShopValidator.sanitize!(shop)` (with the app's configured `myshopify_domain` if applicable) at the start of `begin_auth`, and validate `auth_query.shop` the same way at the start of `validate_auth_callback` before it is used to build `auth_base_uri`/POST the `client_secret`. This aligns the OAuth authorization-code grant with the same domain-binding guarantee already implemented for client credentials, refresh token, and token exchange flows.

### Proof of Concept
1. A host application built on this gem exposes an install route that calls:
   `ShopifyAPI::Auth::Oauth.begin_auth(shop: params[:shop], redirect_path: "/callback")`
   with `shop` taken verbatim from the query string, as shown in the gem's own docs example.
2. An attacker requests `install?shop=attacker-controlled-host.example` (or any string not ending in a Shopify-trusted domain).
3. `begin_auth` calls `auth_base_uri(shop)` → `"https://attacker-controlled-host.example/admin"` with no rejection, since no `ShopValidator` call exists in this path. [9](#0-8) 
4. Downstream, if the callback is completed with a `shop` value under attacker control (e.g., a host app that reflects `shop` from the request into `AuthQuery` without independently confirming it matches the shop it began auth for), `validate_auth_callback` builds `client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")` scoped to that `shop` and POSTs `client_id`/`client_secret`/`code` to it. [10](#0-9) 
5. No `ShopValidator` check exists anywhere in this file to prevent `shop` from being a non-Shopify host, unlike the equivalent code paths in `client_credentials.rb` and `refresh_token.rb`.

        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
            access_token_response: Oauth::AccessTokenResponse.from_hash(session_params))

        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
