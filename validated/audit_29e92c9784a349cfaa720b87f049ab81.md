### Title
Deterministic pool-account derivation from an unvalidated `market` account lets an attacker front-run `Initialize2` and squat the pool addresses - (File: program/src/processor.rs)

### Summary
`process_initialize2` derives every pool-related account (`amm_info`, `lp_mint`, `coin_vault`, `pc_vault`, `target_orders`) as a PDA computed solely from the `program_id` and the `market` account's pubkey plus fixed seed strings, with no validation that the supplied `market` account is a genuine, un-associated OpenBook market. This is analogous to the reported CREATE1 front-running issue: the resulting pool address is fully predictable from a single, attacker-visible input, allowing a third party to preempt legitimate pool creation at that address with attacker-chosen mints/liquidity.

### Finding Description
`generate_amm_associated_account`, `generate_amm_associated_spl_mint`, and `generate_amm_associated_spl_token` all compute the target address via `get_associated_address_and_bump_seed(program_id, &market_account.key, associated_seed, program_id)` and then allocate/assign the account with `invoke_signed` using `[program_id, market_account.key, associated_seed, bump]` as signer seeds. [1](#0-0) [2](#0-1) 

Crucially, in `process_initialize2` the `market_info` account is explicitly documented as unchecked and arbitrary: [3](#0-2) [4](#0-3) 

No comparison is ever made against real OpenBook market data (e.g., its coin/pc mint fields) — `market` is used purely as a seed to derive the pool PDAs, and the actual `coin_mint`/`pc_mint` used for the pool come from the caller-supplied `amm_coin_mint_info`/`amm_pc_mint_info` accounts, which are only checked to be distinct from one another, not tied to the market: [5](#0-4) 

Because the AMM account addresses are a deterministic function of `market` pubkey alone (a value that is public well before pool creation — e.g., an OpenBook market ID everyone can observe), any address that a legitimate pool creator's `Initialize2` transaction will occupy can be computed in advance by anyone. Once computed, an attacker can submit their own `Initialize2` for the same `market` key first (front-running), using their own mints and minimal liquidity, claiming those PDAs before the legitimate transaction lands.

Once seized, `generate_amm_associated_*` functions check `associated_token_account.owner == system_program_account.key` before initializing; if it's not still system-owned (because the attacker's tx already assigned it), the legitimate call fails with `AmmError::RepeatCreateAmm`: [6](#0-5) 

### Impact Explanation
This blocks the legitimate pool creation for that market (denial of service), and more importantly poisons the deterministic address that any off-chain tooling, aggregator, or bot may have already pre-computed and started sending deposit/swap instructions to (analogous to Bob's deposit landing in Alice's malicious vault in the referenced report). A user or integrator who computes the expected AMM/vault addresses for a market ahead of confirmation and immediately issues `Deposit`/`SwapBaseIn`/`SwapBaseOut` against those addresses can have their tokens deposited into or swapped through a pool that the attacker controls with worthless or malicious mints, since `Deposit`/`Swap` only validate the supplied `amm_info` matches the vaults recorded in the on-chain `AmmInfo` struct — not that the pool corresponds to a bona fide, unmodified market/mint pairing chosen by the real deployer.

### Likelihood Explanation
Exploitation requires only observing a pending `Initialize2` transaction (or knowing the target `market` pubkey in advance, which is generally public knowledge — e.g., markets are created and publicized before a Raydium pool is added) and submitting a competing `Initialize2` with higher priority fee. All required accounts (`amm_config`, `create_pool_fee_address`, `AUTHORITY_AMM` PDA) are public/derivable, and no signer other than the attacker's own wallet is needed. This is a single, unprivileged, attacker-crafted transaction — well within the "single submitted tx with attacker-chosen accounts and data" threat model.

### Recommendation
Bind the pool PDA derivation to more than just the market pubkey — include the `coin_mint` and `pc_mint` (and/or the creator's wallet) as part of the seed so that pool addresses cannot be squatted independent of the intended token pair, and/or require validation that `market_info` is an actual, unassociated OpenBook market (checking its `coin_mint`/`pc_mint` against the supplied mint accounts) rather than accepting "any account" as documented in the code comments. Additionally, downstream consumers should be advised to always read and verify `AmmInfo.coin_vault_mint`/`pc_vault_mint` on-chain before trusting a pre-computed pool address.

### Proof of Concept
1. Attacker observes (or already knows) a `market` pubkey `M` that a project intends to use to create an official Raydium pool via `Initialize2`.
2. Attacker computes the deterministic addresses for `amm_info`, `lp_mint`, `coin_vault`, `pc_vault`, and `target_orders` using `get_associated_address_and_bump_seed(program_id, M, seed, program_id)` — identical derivation the honest deployer will use.
3. Attacker submits `Initialize2` first (front-running via higher fee), supplying `market = M` but attacker-controlled `coin_mint`/`pc_mint` and minimal `init_coin_amount`/`init_pc_amount`.
4. The attacker's transaction succeeds, creating the pool at the deterministic addresses and setting `AmmInfo.coin_vault_mint`/`pc_vault_mint` to attacker-chosen mints.
5. The legitimate deployer's `Initialize2` (or any bot/integrator that had pre-computed the address and immediately sends `Deposit`/swap instructions to it) either fails with `AmmError::RepeatCreateAmm`, or — worse — interacts with the attacker's rogue pool, sending real tokens against fake/malicious mints.
