Audit Report

## Title
Unsynchronized concurrent map access in HTTP-Trigger workflow authorization allows crash/DoS - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

## Summary
`WorkflowMetadataHandler.Authorize` reads `h.authorizedKeys[workflowID]` at line 92 without acquiring `h.mu.RLock()`, while `syncMetadata`, invoked periodically by a background ticker (`MetadataAggregationIntervalMs`, default 60s), reassigns `h.authorizedKeys` (and related maps) under `h.mu.Lock()`. Since `Authorize` is executed on every incoming, pre-authentication HTTP-trigger request, an unauthenticated remote client sending ordinary trigger requests can race with the periodic sync and cause a Go runtime "fatal error: concurrent map read and map write," crashing the gateway process.

## Finding Description
`Authorize` (`core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go:80-108`) directly indexes `h.authorizedKeys[workflowID]` at line 92 with no lock held. `syncMetadata` (lines 114-183) builds fresh `authorizedKeys`, `workflowRefToID`, `workflowIDToRef`, and `workflowShards` maps and swaps them into the struct fields at lines 178-181 while holding `h.mu.Lock()` (acquired at line 164). This lock/reassignment runs automatically via `h.runTicker(time.Duration(h.config.MetadataAggregationIntervalMs)*time.Millisecond, h.syncMetadata)` invoked from `Start` (line 296).

Every other reader of these same struct fields — `GetWorkflowID` (lines 356-369), `GetWorkflowReference` (lines 371-376), and `WorkflowShards` (lines 271-278) — correctly wraps its map read in `h.mu.RLock()`/`RUnlock()`. `Authorize` is the sole exception, breaking the locking invariant that all other accessors of `h.authorizedKeys`/`h.workflowIDToRef`/`h.workflowRefToID`/`h.workflowShards` observe.

`Authorize` sits on the direct, pre-authentication request path: `httpTriggerHandler.authorizeRequest` (`http_trigger_handler.go:368-376`) calls `h.workflowMetadataHandler.Authorize(...)` directly, and `authorizeRequest` is called from `HandleUserTriggerRequest` (`http_trigger_handler.go:95-109`), which processes every incoming user trigger request before authorization succeeds. No existing middleware or lock protects this specific read.

## Impact Explanation
Go maps are not safe for concurrent read/write; a write (`syncMetadata`'s map field reassignment, which itself is a memory write requiring synchronization for visibility across goroutines) racing with a read (`Authorize`'s lookup) is undefined behavior that the Go runtime actively detects and can panic on ("fatal error: concurrent map read and map write"), which is unrecoverable and crashes the whole process. Since the gateway is shared infrastructure serving HTTP-triggered workflow requests for potentially many workflows/DONs, a crash constitutes a full denial-of-service, not limited to a single requester or workflow. This maps to an in-scope Chainlink gateway/node availability impact.

## Likelihood Explanation
`syncMetadata` runs unconditionally every `MetadataAggregationIntervalMs` (default 60000ms) for the lifetime of a started `WorkflowMetadataHandler`. `Authorize` is invoked on every incoming HTTP trigger request without any precondition beyond sending a request with a `workflowID` and `Auth` (JWT) field — reachable by any unauthenticated/unprivileged external caller. Under moderate to high trigger request throughput, the probability of a request's `Authorize` call overlapping with a `syncMetadata` tick's write window is non-trivial and increases with load, making this readily and repeatably triggerable, especially detectable immediately under `go test -race`.

## Recommendation
Acquire `h.mu.RLock()` at the start of `Authorize` (or immediately before the `h.authorizedKeys[workflowID]` lookup) and `defer h.mu.RUnlock()`, mirroring the pattern used in `GetWorkflowID`, `GetWorkflowReference`, and `WorkflowShards`. Since the JWT verification and JWT replay checks that precede the map access don't need the lock, the lock can be scoped to wrap only the map lookup, or acquired at function entry along with the other checks for simplicity and consistency with the codebase's other RLock-guarded readers.

## Proof of Concept
1. In a Go test file for `workflow_metadata_handler.go`, construct a `WorkflowMetadataHandler` with a valid workflow registered (populate `authorizedKeys`, `workflowIDToRef` via a direct call to `syncMetadata` or by manipulating fields, then run with `-race`).
2. Launch one goroutine looping calls to `handler.syncMetadata(ctx)` (simulating the ticker) and a second goroutine looping calls to `handler.Authorize(workflowID, validJWT, req)` with a valid signed request/token for that workflow.
3. Run `go test -race ./core/services/gateway/handlers/capabilities/v2/...` — the race detector reports a DATA RACE between the unguarded read at line 92 in `Authorize` and the guarded write at lines 178-181 in `syncMetadata`.
4. In a non-`-race` production-like load test, repeatedly send HTTP trigger requests to a running gateway node while metadata sync ticks occur in the background; reproduction of the "fatal error: concurrent map read and map write" crash is expected under sufficient concurrent load, confirming the DoS impact.
