### Title
Silent ERC20/TRC20 transfer failure in `withdraw`/`SweepDust` permanently freezes escrowed order funds - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.withdraw` and the `SweepDust` handler in `evm/tron/contracts/apps/IntentGatewayV2.sol` release escrowed tokens using a raw low-level `.call` to the token's `transfer` selector, and only check the outer `success` boolean of the call, never decoding/validating the ERC20 `bool` return value. This is exactly the ERC20 return-value-handling class of bug described in the referenced report (H01): for "type 2" tokens that return `false` on failure instead of reverting, the outer `call` reports `success = true` even though no tokens moved, so the contract proceeds to zero out escrow accounting and emit `EscrowReleased`/`EscrowRefunded`/`DustSwept` while the beneficiary receives nothing.

### Finding Description
In `withdraw`, escrowed order tokens are paid out with: [1](#0-0) 
```
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
and immediately after: [2](#0-1) 
```
_orders[body.commitment][token] -= amount;
```
The same pattern recurs for fee-token payout in `withdraw` [3](#0-2)  and for the `SweepDust` request handler in `onAccept` [4](#0-3) .

`success` here only reflects whether the low-level call reverted, not whether the encoded ERC20 `transfer` returned `true`. Any token that returns `false` on a failed transfer (per the ERC20 spec's non-mandatory throw-on-failure behavior — the same class enumerated in the H01 report) will make this call succeed at the EVM level while the ERC20 `transfer` call itself silently failed. The contract then treats the withdrawal as successful: it decrements `_orders[body.commitment][token]` (in `withdraw`) or simply emits `DustSwept` (in the `SweepDust` branch) without ever verifying the tokens actually reached the beneficiary.

This directly contradicts the codebase's own established convention elsewhere: the sibling `evm/src/apps/IntentGatewayV2.sol` version and every other bridging/vault contract (`WrappedHyperFungibleToken`, `EvmHost.fundRequest`, `IntentGatewayV2` predispatch/input paths, `UniswapV2` wrapper contracts) consistently use OpenZeppelin's `safeTransfer`/`safeTransferFrom`, e.g. [5](#0-4)  and [6](#0-5) . The Tron variant at `evm/tron/contracts/apps/IntentGatewayV2.sol` deviates from this pattern specifically on the outbound/payout leg (`withdraw`, `SweepDust`), reproducing the exact "check `success` of the call but not the ERC20 boolean" mistake called out in the report.

### Impact Explanation
`withdraw` is reached from `onAccept` for both `RedeemEscrow` and `RefundEscrow` request kinds, i.e., every time an order is filled or refunded cross-chain via a relayed ISMP message: [7](#0-6) . Once a relayer delivers a legitimate authenticated `RedeemEscrow`/`RefundEscrow` message referencing an order whose input/output token is a "type 2" ERC20/TRC20 (returns `false` rather than reverting on failure — e.g., due to a paused token, blacklist, insufficient allowance edge case, or fee/limit logic implemented via boolean return), the escrow record `_orders[commitment][token]` is decremented to zero and the contract emits a success event, even though the tokens never left the gateway and never reached the user/solver. Because the accounting entry that gates any future withdrawal is deleted, the funds become permanently un-retrievable through the normal protocol flow — a permanent freezing/loss of user (or solver) funds inside `IntentGatewayV2`, satisfying the "permanent freezing of funds" impact bar.

### Likelihood Explanation
Triggering this only requires: (1) an order using an ERC20/TRC20 token that returns `false` (rather than reverting) under some failure condition reachable at withdrawal time (e.g., a pausable/blacklistable stablecoin, or any token contract that implements soft-fail transfer semantics — common on TRC20 tokens, which this file specifically targets given the `tron/` path), and (2) a normal relayed `RedeemEscrow`/`RefundEscrow` delivery, which is the standard, expected completion path for every cross-chain intent order. No malicious relayer, governance, or admin behavior is required — a single legitimate order fill/refund against a token with these semantics is sufficient, making this a realistic, non-contrived trigger for a widely-used token category.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw` and the `SweepDust` branch of `onAccept` with OpenZeppelin's `SafeERC20.safeTransfer`, mirroring the pattern already used throughout the rest of the codebase (e.g. `evm/src/apps/IntentGatewayV2.sol`, `WrappedHyperFungibleToken.sol`). `safeTransfer` correctly reverts whenever the call fails outright, when it returns `false`, or when it returns malformed/no data, eliminating the silent-failure window before escrow state is mutated.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) with an order whose input/output token is a mock ERC20 that returns `false` on `transfer` to certain addresses/conditions instead of reverting (type-2 semantics), e.g.:
```solidity
function transfer(address to, uint256 amount) external returns (bool) {
    if (blacklisted[to]) return false; // no revert
    _transfer(msg.sender, to, amount);
    return true;
}
```
2. Place an order with this token as an output/input asset and have it filled normally, escrowing funds in `_orders[commitment][token]`.
3. Have the relayer deliver the legitimate `RedeemEscrow` message; `onAccept` calls `withdraw`.
4. Set the beneficiary address to be blacklisted in the mock token (or otherwise trigger the `false`-return branch) before delivery.
5. Observe: `token.call(...)` returns `success = true` (call didn't revert) even though the token's internal `transfer` returned `false` and moved no balance; `withdraw` proceeds to execute `_orders[body.commitment][token] -= amount;` and emits `EscrowReleased`, while `beneficiary`'s token balance is unchanged — the escrowed funds are now unrecoverable through the protocol.
