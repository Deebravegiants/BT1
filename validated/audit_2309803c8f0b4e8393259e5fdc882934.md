## Title
Webhook `shop` identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw HTTP body, while the `shop` (and `topic`/`webhook_id`) that the handler receives are read straight from unauthenticated HTTP headers. Any internet-facing attacker who can obtain one genuine `(raw_body, hmac)` pair for a shop they control can replay it to the app's webhook endpoint with a forged `x-shopify-shop-domain` header, and the request will still pass HMAC validation while `WebhookMetadata#shop` reports an arbitrary victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is derived from the `shop-domain` header, which is never part of the signed content: [2](#0-1) 

`Registry.process` validates only the HMAC over that body via `Utils::HmacValidator.validate(request)`, then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`) to build `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the received signature — for `Request` that signable string is `raw_body` only: [4](#0-3) 

The intended identity binding is: `hmac_valid(body) ⇒ shop_header authentically identifies the tenant that generated body`. The actual code only proves `hmac_valid(body) ⇒ body was produced using this app's api_secret_key` — it says nothing about which shop the header claims. Since a single app has one shared `api_secret_key` across all installed shops, the same secret produces valid HMACs for any shop's webhook body. An attacker who installs the app on their own store (a normal, unprivileged action) receives real webhook deliveries — e.g., `orders/create`, `app/uninstalled` — with a valid `(raw_body, hmac)` pair signed by the app's `api_secret_key`. They can then POST that exact `raw_body`/`hmac` pair to the app's public webhook callback URL while substituting the `x-shopify-shop-domain` header with a victim shop's domain (and/or a different `x-shopify-topic`). `Registry.process` will accept it, because the signature check never inspects the header. The documentation frames this check as proof "the request did indeed come from Shopify": [5](#0-4) 
— which is misleading regarding the `shop` field specifically, since it is never authenticated.

### Impact Explanation
This breaks the tenant/shop identity boundary the gem is expected to enforce for webhook consumers: an unprivileged attacker with their own valid app installation can make the app believe arbitrary payload data (of their own crafting/timing, subject to real event bodies they can trigger on their own store) originated from a different, victim shop. Depending on the webhook topics registered (e.g. `app/uninstalled`, GDPR `shop/redact`/`customers/redact`, `orders/create`), this can drive the app to perform actions against the wrong tenant's data/account — a cross-tenant confusion analogous to the referenced oracle-corruption bug, where data meant for one identity slot (block/epoch there, shop here) gets attributed to another because the binding key is not covered by the authenticity check.

### Likelihood Explanation
Any user can install the target app on a free/dev store to obtain legitimate `(raw_body, hmac)` pairs, and the webhook callback endpoint is by design public/unauthenticated (Shopify calls it directly). Forging the header and replaying the POST requires no secret, no credentials, and no privileged access — only network access to the app's public webhook route.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, or otherwise cryptographically tie the header claims to the signed body (e.g., include the shop domain in `to_signable_string`, or have `Registry.process`/`WebhookHandler` require the caller to supply and cross-check an expected shop from the app's own session store rather than trusting the raw header). At minimum, update `docs/usage/webhooks.md` and `WebhookMetadata` to make explicit that `shop`/`topic` are NOT covered by the HMAC and must be independently validated against the app's known installed shops before use.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and registers for `orders/create`.
2. Attacker creates an order, capturing the real webhook POST: raw body `B` and header `x-shopify-hmac-sha256: H` (valid for the app's `api_secret_key`).
3. Attacker POSTs the same body `B` and header `H` to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and matches `H` — validation succeeds.
5. `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed_body_of_B, ...)` is delivered to the app's handler, which now processes attacker-supplied data as if it belongs to `victim.myshopify.com`.
