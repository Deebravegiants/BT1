### Title
Registry.process trusts unauthenticated `X-Shopify-Topic`/`X-Shopify-Shop-Domain` headers for handler dispatch and `WebhookMetadata`, because HMAC only signs the raw body - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`Webhooks::Registry.process` validates a webhook by calling `Utils::HmacValidator.validate(request)`, but that validator only checks the HMAC over `request.to_signable_string`, which is defined to be just the raw request body. `request.topic` and `request.shop` are read straight from HTTP headers that are never part of the signed material, so a valid HMAC on a body says nothing about which topic or shop that body is being delivered for.

### Finding Description
The claimed binding is:
`(topic_signed, shop_signed) == (topic_dispatched, shop_dispatched)`

Tracing the code:
- `HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to `verifiable_query.hmac` [1](#0-0) .
- `Webhooks::Request#to_signable_string` returns only `@raw_body` [2](#0-1) . Neither `topic` nor `shop` is part of the signable string.
- `Webhooks::Request#topic` and `#shop` are read verbatim from the `X-Shopify-Topic` / `X-Shopify-Shop-Domain` headers, which are attacker-controllable, unsigned inputs [3](#0-2) .
- `Registry.process` performs exactly one guard (`raise ... unless Utils::HmacValidator.validate(request)`), then immediately uses `request.topic` to look up the handler and both `request.topic`/`request.shop` to build `WebhookMetadata` that is handed to the handler [4](#0-3) .

So the "authenticated" side of the equality (topic/shop as actually signed) is undefined — the signature never covers those fields — while the "dispatched" side is taken from plain headers. The equality is not enforced; it merely appears to hold in the honest case because Shopify normally sets consistent headers. An attacker who obtains one validly-signed body (e.g., from a webhook Shopify sends them for their own development shop) can resend that exact body to the app's webhook endpoint with a different `X-Shopify-Topic` and/or `X-Shopify-Shop-Domain` header. The HMAC still validates because it only covers `@raw_body`, but the handler dispatched and the `shop`/`topic` recorded in `WebhookMetadata` are now attacker-chosen and unrelated to what Shopify actually signed.

No other guard in the reachable path closes this gap: `HmacValidator.validate` is body-only, `Registry.process` does not call `ShopValidator.sanitize!` on `request.shop`, and there is no re-derivation of topic/shop from any signed source.

### Impact Explanation
An attacker who legitimately receives one validly-signed webhook body (trivial: create a dev shop, install the app, trigger any webhook) can relabel its topic and/or shop-domain header and replay it to the app's webhook endpoint. This lets them:
- Trigger a different handler than the one actually associated with the signed payload (e.g., feed a body meant for `orders/create` into the `shop/redact` or `customers/data_request` handler, or vice versa), corrupting the app's understanding of what data it's acting on.
- Set `WebhookMetadata#shop` to an arbitrary shop domain (including a victim's), causing the handler to act as if the (attacker-controlled) body content belongs to another tenant — a cross-tenant confusion since nothing binds the signed body to the shop it's attributed to.

This matches the "cross-tenant access" / authentication-bypass category: a value (topic/shop) that is not cryptographically authenticated is nonetheless trusted as if it were. It is repeatable against any deployed handler and any shop the attacker chooses to name in the header, without needing `api_secret_key` or any credential.

### Likelihood Explanation
Preconditions: the app must have at least one working webhook registration (near-universal for Shopify apps) and expose the standard webhook receiving endpoint using this gem's `Registry.process`. The attacker only needs their own development shop to obtain one genuine signed body/HMAC pair, then can freely vary the header values on replay since those headers are outside the signed scope. No secrets, no privileged access, no timing dependency — fully attacker-controlled and repeatable per request.

### Recommendation
Include `topic` and `shop` (and ideally `webhook_id`/`api_version`) in the signable string, or otherwise cryptographically bind them (e.g., verify HMAC over a canonical string composed of the relevant headers plus body, matching Shopify's actual signing scope if it covers them), and additionally validate `request.shop` with `ShopValidator.sanitize!` before using it for tenant-scoped dispatch in `Registry.process`.

### Proof of Concept
```ruby
# test/webhooks/registry_relabel_test.rb
require "test_helper"

class RegistryRelabelTest < Minitest::Test
  def setup
    ShopifyAPI::Webhooks::Registry.clear
  end

  def test_topic_and_shop_are_not_bound_to_hmac
    raw_body = '{"id":1}'
    secret = "secret"
    ShopifyAPI::Context.setup(api_secret_key: secret, ...)

    # HMAC computed the same way HmacValidator does - over raw_body ONLY
    valid_hmac = Base64.strict_encode64(
      OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, raw_body)
    )

    handler_a = mock("handler_a")
    handler_a.expects(:handle).once
    ShopifyAPI::Webhooks::Registry.add_registration(
      topic: "orders/create", delivery_method: :http, path: "/x", handler: handler_a
    )

    # Attacker relabels topic/shop headers; body+hmac unchanged and still "valid"
    forged_request = ShopifyAPI::Webhooks::Request.new(
      raw_body: raw_body,
      headers: {
        "x-shopify-hmac-sha256" => valid_hmac,
        "x-shopify-topic" => "orders/create",       # attacker-chosen, not signed
        "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-chosen, not signed
      },
    )

    # Assert: HmacValidator.validate succeeds purely on raw_body/secret
    assert ShopifyAPI::Utils::HmacValidator.validate(forged_request)

    # Assert: process() dispatches handler_a using attacker-supplied shop,
    # with zero cryptographic linkage between the validated body and the shop/topic used
    ShopifyAPI::Webhooks::Registry.process(forged_request)
    # handler_a.handle was called with shop: "victim-shop.myshopify.com" even though
    # that value was never part of the signed material.
  end
end
```
This demonstrates: (1) `HmacValidator.validate` returns true regardless of the `topic`/`shop` header values, and (2) `Registry.process` dispatches using those unauthenticated header values with no additional check, proving the single guard line provides no binding between "authenticated" and "acted-on" topic/shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

        end
