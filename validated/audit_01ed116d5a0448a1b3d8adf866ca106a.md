### Title
`describeWithdrawal`/`findMatchingWithdrawal` misattributes status/txHash between same-asset withdrawals in a batch - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves a `WithdrawalIdentifier` to a status by calling `findMatchingWithdrawal`, which selects the first entry in the PoA API's `withdrawals` array whose `nep141:<near_token_id>` equals `args.withdrawalParams.assetId`, ignoring destination address, amount, and the `index` field entirely. When a batch contains two or more withdrawals of the same `assetId` (e.g. two `nep141:ltc.omft.near` payouts to different addresses), both `WithdrawalIdentifier`s will match against the same (arbitrary, first-found) API entry, so one destination's completed status/txHash can be reported for the other's identifier.

### Finding Description
The broken equality is: `WithdrawalIdentifier` (bound to a specific `destinationAddress`/`amount` at a given `index`) should map 1:1 to the withdrawal record with the matching destination/amount returned by the PoA `withdrawal_status` API. Instead, `findMatchingWithdrawal` (lines 418-427) matches purely on `nep141:${w.data.near_token_id} === assetId`: [1](#0-0) 

The function's own docstring admits the limitation: "multiple withdrawals of the same token in a single transaction are not supported," and proposes a future fix by sorting on amount — but no such fix or guard exists.

`describeWithdrawal` calls this matcher directly, with a comment acknowledging the API list is unsorted and matching is done "by assetId instead of index": [2](#0-1) 

Root cause: there is no validation anywhere in `PoaBridge` (`supports`, `validateWithdrawal`, `createWithdrawalIdentifier`) that rejects or disambiguates a batch containing repeated `assetId`s. `createWithdrawalIdentifier` (lines 295-311) just carries the `index` and `withdrawalParams` through, but that `index`/destination-specific data is never used to disambiguate the API response in `describeWithdrawal`.

Exploit flow: an integrator/user submits a withdrawal batch with two `nep141:ltc.omft.near` withdrawals — one to address A, one to address B. Both get intents signed and sent. The relayer processes the two withdrawals independently. `IntentsSDK.waitForWithdrawalCompletion` calls `describeWithdrawal` for both `WithdrawalIdentifier`s; both calls invoke `getWithdrawalStatusWithRetry` (keyed by `args.tx.hash`, the NEAR tx hash shared by the whole batch) and then `findMatchingWithdrawal` with the same `assetId`. `Array.prototype.find` returns the same first match for both calls regardless of which destination actually completed, so if the API returns entries `[{near_token_id: "ltc.omft.near", status: COMPLETED, transfer_tx_hash: null}, {near_token_id: "ltc.omft.near", status: PENDING, ...}]`, both identifiers resolve to the same "completed"/`transfer_tx_hash: null` record — meaning the payout destined for B could be misreported as A's completed transfer (or vice versa) depending on array order, which the docstring explicitly states is unsorted.

None of the existing guards prevent this: `validateAddress`/`compareAddresses` operate at withdrawal creation, not at status resolution; `supports()` only filters by route/assetId type, not batch composition; there's no `assert` checking for duplicate `assetId`s across a batch in `describeWithdrawal`/`findMatchingWithdrawal`/`getWithdrawalStatusWithRetry`.

### Impact Explanation
An integrator relying on `waitForWithdrawalCompletion`/`describeWithdrawal` to determine whether a specific withdrawal (identified by destination address and amount) has completed can receive a `completed` status and a `transfer_tx_hash` that actually belongs to a different destination in the same batch. This is a status/hash misreport that could cause an integrator to credit or refund a user twice, or fail to detect that the intended payout to a specific address never landed — matching the "High" impact category (status or hash misreport making an integrator credit or refund twice).

### Likelihood Explanation
Preconditions: the attacker only needs to submit (or have an integrator submit on their behalf) a single NEAR Intents withdrawal batch containing two or more withdrawals of the same PoA token (same `assetId`, e.g. `nep141:ltc.omft.near`) to different destination addresses/amounts — an ordinary, unprivileged action fully within documented SDK capabilities (`createWithdrawalIdentifier` and `describeWithdrawal` place no restriction on repeated assetId). This is low-cost and repeatable on every batch containing duplicate-token withdrawals. The bug is deterministic given the code's reliance on `Array.prototype.find` and an "unsorted" API response, as acknowledged directly in the source comments.

### Recommendation
Disambiguate matching beyond `assetId`: sort both the API's `withdrawals` array and the batch's `WithdrawalIdentifier`s deterministically (e.g., by amount, as hinted in the docstring) before pairing them, or reject/throw when `supports`/`createWithdrawalIdentifier` detects duplicate `assetId`s within a single batch until the PoA API supports disambiguation (e.g., by `withdrawal_id`/destination address). At minimum, add a runtime guard in `findMatchingWithdrawal` that throws if more than one candidate withdrawal matches the same `assetId`, rather than silently returning the first one.

```typescript
	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}
```

```typescript
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
```
