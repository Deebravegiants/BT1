### Title
Webhook shop identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) exclusively from the unauthenticated `X-Shopify-Shop-Domain` HTTP header, while `Utils::HmacValidator` only verifies the raw request body. The `shop` field is never part of the signed material, so any caller that can produce (or replay) a body/HMAC pair valid for *some* shop can attach an arbitrary `shop` header, and `Webhooks::Registry.process` will hand that spoofed shop identity straight to the app's handler as trusted.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` header with no cryptographic tie to the signature: [2](#0-1) 

`HmacValidator.validate` computes and compares the signature against `verifiable_query.to_signable_string` only — i.e. the body — never the shop header: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` to construct the `WebhookMetadata` passed to the app's handler, with no secondary check that the shop matches what was actually signed: [4](#0-3) 

The broken identity binding, stated as an equality that should hold but doesn't:
`shop_used_by_handler (header, unauthenticated) == shop_covered_by_hmac (none, since HMAC covers body only)`.

Because Shopify's HMAC for webhooks is computed over the raw JSON body with the app's `client_secret`, and the shop domain is delivered as a sibling header, this gem does not enforce that the header matches any claim inside the signed body (e.g. `myshopify_domain`) or otherwise bind the two. Any entity that operates its own installed instance of the app (a legitimate, unprivileged action requiring no secrets) receives real, correctly-HMAC-signed webhook deliveries for its own store. That party can replay the exact same signed body to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain` for a different (victim) shop. `HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` will dispatch the payload to the app's handler tagged with the victim's shop identity.

### Impact Explanation
If the host application's webhook handler uses `WebhookMetadata#shop` to look up per-tenant session/access-token records or to authorize/attribute an action (a documented and expected usage pattern for this gem, since `shop` is the only tenant identifier `Registry.process` supplies to handlers), an attacker-controlled shop domain can be injected into another tenant's processing path. This constitutes cross-tenant access/confusion — the app is deceived into applying or accepting data under the wrong shop's identity, which is a Critical-class impact per the given classification (cross-tenant access).

### Likelihood Explanation
Moderate-to-high: obtaining a validly-signed body requires only that the attacker runs the app for their own shop (an ordinary, unprivileged flow with no leaked credentials needed), after which they can freely forge the `shop` header on replay to the app's public webhook endpoint. No access token, `api_secret_key`, or privileged account is required — only knowledge of the gem's own webhook-verification design, which this analysis confirms does not bind headers to the signature.

### Recommendation
Bind the shop identity into the HMAC-covered material, or independently verify it against a signed claim in the payload. Concretely:
- In `lib/shopify_api/webhooks/request.rb`, include `shop` (and other identity-bearing headers such as `topic`/`webhook_id`) inside `to_signable_string`, or
- Require the webhook payload to carry a shop-scoped identifier that is itself cross-checked against the header before `Registry.process` constructs `WebhookMetadata`, rejecting the request on mismatch.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers any subscribed webhook topic, causing Shopify to POST a correctly HMAC-signed body `B` with headers `X-Shopify-Hmac-Sha256: H`, `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker resends the identical body `B` and signature `H` to the app's webhook endpoint, but replaces the header with `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`; since only `B` is checked against `H`, validation succeeds. [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and processes `B` as if it originated from the victim shop. [6](#0-5)
