### Title
Dynamic resharding leaves stale `proposed_split` in the child shard's `ChunkExtra`, causing spurious `InvalidChunkHeaderShardSplit` chunk-validation failures - (File: `chain/chain/src/resharding/manager.rs`)

### Summary
When a shard is split via NEAR's dynamic resharding feature, the resharding manager builds each child shard's `ChunkExtra` by cloning the parent's `ChunkExtra` and then only overwriting `state_root` and `congestion_info`. It never resets the inherited `proposed_split` field, which still holds the `TrieSplit` value that triggered the just-completed split. This is directly analogous to the ZetaChain `UpdateSystemContract` bug: a state-migrating/"upgrade" operation copies most fields into the new state (new system contract / child shard) but omits resetting one field that downstream consensus-critical logic depends on being correctly populated, causing the next operation (`withdraw` / chunk validation) to fail.

### Finding Description
`ReshardingManager::process_memtrie_resharding_storage_update` clones the parent `ChunkExtra` for each child shard and mutates only two fields: [1](#0-0) 

The `// TODO(resharding): set all fields of ChunkExtra...` comment on this exact line documents that not every field is correctly (re)computed for the child — and the field explicitly named as missing in the accompanying architecture doc is `proposed_split`: [2](#0-1) 

The identical pattern exists in the stateless-validation replay path for the resharding transition, which also updates `state_root` and `congestion_info` but not `proposed_split`: [3](#0-2) 

This matters because `proposed_split` is a consensus-checked field: `validate_chunk_with_chunk_extra_and_receipts_root` requires the *previous* chunk extra's `proposed_split` to exactly equal the new chunk header's `proposed_split`, else the chunk is rejected as `InvalidChunkHeaderShardSplit`: [4](#0-3) 

For a freshly split child shard, the chunk producer computes a fresh `proposed_split` for its very first chunk via `compute_proposed_split`, which gates on `can_reshard` (the resharding cooldown). Because the split for this child epoch has `last_resharding` just set, `can_reshard` returns false and the freshly computed value is `None`: [5](#0-4) 

Meanwhile the *previous* chunk extra used for that validation is the child's inherited `ChunkExtra`, whose `proposed_split` still carries `Some(split)` from the parent shard (the split that was just consumed to create the child). The `DynamicReshardingConfig` doc comment for `min_epochs_between_resharding` independently confirms this exact failure mode by name: [6](#0-5) 

The `min_epochs_between_resharding` cooldown (required to be non-zero) only prevents a *second* split from being *proposed* too soon after the first — it does not clear or correctly recompute the stale `proposed_split` value copied verbatim into the freshly-created child's `ChunkExtra` at the moment of the split itself. The manager code that performs that copy has no `proposed_split` reset logic at all (confirmed by the TODO at `manager.rs:255-257` and the tracked TODO item in the architecture doc), so the mismatch described above can occur on the child's very first post-split chunk.

### Impact Explanation
If the stale `Some(split)` value is not overwritten before being compared, the first chunk produced for a newly split child shard would fail `validate_chunk_with_chunk_extra_and_receipts_root` with `InvalidChunkHeaderShardSplit`, exactly mirroring the "permanent halt" scenario NEAR's own tests are built to catch (`test-loop-tests/src/tests/resharding_missing_chunks.rs` explicitly asserts children "must produce endorsed chunks... on unfixed code they never do (permanent halt)"): [7](#0-6) 

A shard stuck unable to produce a validly-endorsed chunk is a chain-stall of that shard — no user transactions or receipts targeting that shard's accounts can execute (deposits, withdrawals, contract calls all included). Since dynamic resharding is triggered automatically and deterministically once a shard's trie memory usage crosses `memory_usage_threshold` (driven purely by ordinary account/contract activity, not by any privileged actor), this is reachable purely from unprivileged transaction volume.

### Likelihood Explanation
Dynamic resharding (`ProtocolFeature::DynamicResharding`) is documented as active at protocol version 85, i.e. active at the current stable version 86 used in this tree: [8](#0-7) 

The trigger condition (a shard's memtrie memory usage crossing a configured threshold) is a normal consequence of network growth, not an adversarial or validator-privileged action, making the path realistically reachable whenever an operator enables `ShardLayoutConfig::Dynamic` in the epoch config. The explicit TODO comments left by the NEAR team in both `manager.rs` and the architecture doc indicate this gap is known/unresolved in this snapshot rather than already fixed.

### Recommendation
When constructing the child shard's `ChunkExtra` during `process_memtrie_resharding_storage_update` (and in the equivalent stateless-validation replay path in `chunk_validation.rs`), explicitly reset `proposed_split` to `None` (or to the value the child's own fresh `compute_proposed_split` would produce) rather than leaving the value inherited from `ChunkExtra::clone(&parent_chunk_extra)`. This mirrors the ZetaChain fix of explicitly re-deriving/copying the missing state (`gasPriceByChainId`) into the new contract instead of relying on an incomplete field-by-field copy.

### Proof of Concept
1. Enable `ShardLayoutConfig::Dynamic` with a low `memory_usage_threshold` and `min_epochs_between_resharding = 1` in a test-loop environment (see `test-loop-tests/src/tests/resharding_v3.rs` / `test-loop-tests/src/utils/resharding.rs` harnesses already present in the repo).
2. Drive enough transactions against a shard to cross the threshold and trigger a dynamic split at an epoch boundary.
3. Immediately after the split, inspect the child shard's `ChunkExtra.proposed_split()` — it will equal the parent's last `Some(TrieSplit{..})` rather than `None`.
4. Observe that the child shard's first chunk (whose `chunk_header.proposed_split()` is freshly computed as `None` via `compute_proposed_split`/`can_reshard`) fails `validate_chunk_with_chunk_extra_and_receipts_root` with `Error::InvalidChunkHeaderShardSplit`, matching the "permanent halt" assertion pattern already encoded in `test-loop-tests/src/tests/resharding_missing_chunks.rs`.
