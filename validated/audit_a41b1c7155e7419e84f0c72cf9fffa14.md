I have enough confirmation to write the analog finding. The `liquidate` function in `market.clar` / `v0-4-market.clar` never checks `coll-aid != debt-aid`, and the collateral-seizure math always applies a liquidation bonus (`calc-liq-collateral-repay`) even when collateral and debt reference the identical fungible asset.

### Title
Liquidation of same-asset collateral/debt positions applies liquidator bonus with no cross-asset conversion, minting value from a fungible-token identity - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`liquidate()` never verifies that `collateral-ft` and `debt-ft` reference different underlying assets. When a borrower's position holds the same asset both as collateral and as debt (technically possible since assets like sBTC are enabled `collateral: true, debt: true` and the health check only aggregates USD values, ignoring asset identity), a self/colluding liquidation lets the liquidator redeem strictly more tokens of asset X than they repay in the same asset X, because the liquidation-bonus math (`calc-liq-collateral-repay`) is applied unconditionally regardless of whether collateral and debt are fungible-identical.

### Finding Description
`borrow()` at [1](#0-0)  only checks aggregate USD health (`is-healthy`), never that the asset being borrowed differs from assets already posted as collateral. `liquidate()` at [2](#0-1)  computes `coll-aid` and `debt-aid` independently from the caller-supplied `collateral-ft`/`debt-ft` traits with no `(asserts! (not (is-eq coll-aid debt-aid)) ...)` guard anywhere in the function.

The liquidation math then applies a bonus unconditionally: [3](#0-2) 
`coll-usd-expected` is `debt-repay-usd * (BPS + liq-penalty) / BPS`, computed in `process-collateral-asset`: [4](#0-3) 

When `coll-aid == debt-aid`, `coll-price == debt-price` and `coll-decimals == debt-decimals`, so:
`coll-final (tokens of X) = debt-to-repay (tokens of X) * (BPS + liq-penalty) / BPS > debt-to-repay`

The identity that should hold for a same-asset liquidation is `coll-final == debt-to-repay` (moving the same fungible token from a user's collateral bucket to close their own debt bucket nets to zero external value transfer), but the code instead executes: [5](#0-4) 
`vault-system-repay` credits `debt-to-repay` tokens of asset X back into the vault, while `collateral-remove` pays out `coll-final` tokens of the same asset X to the liquidator — strictly more than what was deposited back. The difference `(coll-final − debt-to-repay)` is extracted from the shared vault pool of asset X, i.e. from other depositors of that asset, with nothing posted in exchange (no different asset was ever contributed).

This is the direct analog of the reported Catalyst `localSwap` bug: a conversion function that applies a bonus/slippage-style rate meant for cross-asset trades, but fails to check `fromAsset != toAsset`, letting the caller extract free value when the two sides are actually the same fungible token.

### Impact Explanation
This breaks the vault-solvency identity for asset X: `vault_balance(X)_after == vault_balance(X)_before − (coll_final − debt_to_repay)`, permanently draining value from the shared liquidity pool of that asset to the attacker/liquidator with no corresponding value ever entering the vault. Repeated over time (the position can be pushed past `LTV-LIQ-PARTIAL` purely by natural interest accrual on the debt side without needing any price manipulation, since collateral and debt track the identical price), this results in protocol insolvency for that asset pool and theft of other depositors' principal — a Critical-severity impact.

### Likelihood Explanation
An attacker only needs to: (1) deposit asset X as collateral, (2) borrow the same asset X up to the max borrow LTV (fully permitted, since `borrow()` has no same-asset restriction), (3) let interest accrue naturally (or supply/borrow index divergence) until LTV crosses `LTV-LIQ-PARTIAL`, then (4) call `liquidate()` themselves (or via a colluding second account) passing `collateral-ft` and `debt-ft` as the same token contract. No governance, oracle manipulation, or privileged role is required — this is a fully unprivileged, permissionless call path.

### Recommendation
Add an explicit guard in `liquidate()` (and any other function computing `coll-aid`/`debt-aid` independently) rejecting `coll-aid == debt-aid`, e.g. `(asserts! (not (is-eq coll-aid debt-aid)) ERR-SAME-ASSET-LIQUIDATION)`, immediately after both asset IDs are resolved at [6](#0-5) . Alternatively (or additionally), consider disallowing a user from simultaneously holding the same asset ID as both collateral and debt when computing health/borrow eligibility.

### Proof of Concept
1. Attacker deposits `N` units of sBTC as collateral via `collateral-add`, then calls `borrow` on sBTC (same asset) for the maximum amount allowed under `LTV-BORROW`, per [7](#0-6) .
2. Time passes; borrow-index accrual increases `debt-value` in USD while collateral value (same asset, same price) stays effectively flat, pushing `current-ltv` above `LTV-LIQ-PARTIAL`.
3. Attacker (or an accomplice) calls `liquidate(borrower=attacker, collateral-ft=sBTC, debt-ft=sBTC, debt-amount=X, min-collateral-expected=0, ...)`.
4. Because `coll-aid == debt-aid`, `process-collateral-asset` computes `coll-final = debt-to-repay * (BPS + liq-penalty) / BPS` (per [4](#0-3) ), strictly greater than `debt-to-repay`.
5. `vault-system-repay` deposits `debt-to-repay` sBTC back to the vault; `collateral-remove` pays out `coll-final` sBTC to the attacker — net gain of `(coll-final − debt-to-repay)` sBTC extracted from the shared vault, funded by other sBTC depositors.
