Confirming the code paths: the gateway-side handler runs authorization *at the gateway* first, via `GatewayVaultRequestProcessor.authorizeAndStamp`, calling the same `allowListBasedAuth.AuthorizeRequest` chain shown in the report [1](#0-0) . Audit Report

## Title
Unbounded per-request allowlist scan with retry-sleep amplification enables DoS in Vault gateway/node request authorization - ([File: core/capabilities/vault/allow_list_based_auth.go])

## Summary
Every non-JWT Vault request is authorized via `allowListBasedAuth.AuthorizeRequest` → `findAllowlistedItemWithRetry`, which performs up to 11 full O(n) linear scans of the entire in-memory allowlisted-requests slice (plus unconditional debug-string formatting of every entry) and sleeps 3 seconds between failed attempts, for a worst-case ~30-second, O(11n) cost per unauthorized request [2](#0-1) . This authorization path runs at the gateway (`GatewayVaultRequestProcessor.authorizeAndStamp`) before any allowlist check succeeds, and is reachable by any unprivileged client sending a `SecretsCreate/Update/Delete/List` JSON-RPC request without a valid JWT [1](#0-0) , and there is no per-sender rate limiter guarding this expensive path in the gateway's vault `handler.go` (only a node-response-side limiter exists) [3](#0-2) .

## Finding Description
The allowlist slice `w.allowListedRequests` grows monotonically with legitimate on-chain activity across the whole network (pruned only on expiry) via `syncAllowlistedRequests` [4](#0-3) , so the per-request authorization cost scales with total network-wide allowlist size and is multiplied elevenfold by the retry loop and its accompanying sleeps. The retry design intentionally exists to tolerate on-chain-to-syncer propagation delay (per the code comment referencing the syncer's 12s poll interval), but it applies the same 10×3s worst case to requests that are simply never going to be allowlisted (e.g., garbage/unauthorized requests), which is the common case for an attacker. There is no indexed (map-based) lookup — `fetchAllowlistedItem` does a linear `for` loop — and the debug-string slice `allowedRequestsStrs` is built unconditionally on every attempt regardless of log level [5](#0-4) . Existing checks (structural JSON-RPC validation, request ID length cap) run before authorization but do not rate-limit or short-circuit repeated unauthorized authorization attempts.

## Impact Explanation
This is a genuine resource-exhaustion (CPU/goroutine/wall-clock) concern that scales with allowlist size and attacker request volume, mapping to a DoS impact category. However, its severity is more limited than the original claim suggests: the authorization loop executes primarily at the **gateway** (which already gates the fan-out to nodes), not automatically against every DON node for every rejected request — `fanOutToVaultNodes` is only reached for authorized requests [6](#0-5) . So the primary blast radius is the single gateway process handling the request, not the entire DON simultaneously (the node-side `GatewayHandler.HandleGatewayMessage` path only matters for requests forwarded by the gateway to nodes with a legacy/backward-compat flow, which per the code is exercised only after gateway-side authorization already succeeded or for messages the node receives directly). This still allows concurrent unauthorized requests to tie up gateway goroutines for up to 30 seconds each, degrading gateway responsiveness for legitimate Vault traffic — a real but moderate-severity availability issue rather than a whole-DON-wide compute exhaustion attack.

## Likelihood Explanation
Likelihood is moderate: no privilege is required — an unprivileged client can send a non-JWT Vault JSON-RPC request through the public gateway endpoint, and the expensive path is guaranteed to execute to completion for any digest not present in the allowlist. There is no per-sender rate limiter in the vault gateway handler to throttle repeated unauthorized attempts [7](#0-6) , so an attacker can open many concurrent connections to amplify the effect. The allowlist naturally grows over time in normal network operation, increasing the per-attempt scan cost without attacker action.

## Recommendation
- Avoid retry-with-sleep loops for the common "never going to match" case: consider a single fast lookup plus a short bounded retry budget independent of allowlist size, or apply retries only when there is a plausible propagation-timing signal (e.g., very recent workflow registration).
- Replace the O(n) linear scan (`fetchAllowlistedItem`) with a map keyed by request digest maintained by the syncer, making lookups O(1) regardless of allowlist size.
- Gate the debug `allowedRequestsStrs` construction behind an actual debug-log-level check, or drop it/cap its size.
- Add per-sender/per-IP rate limiting at the gateway's vault handler ahead of the authorization pipeline to bound how many concurrent expensive authorization attempts an unprivileged caller can trigger.

## Proof of Concept
1. Populate the workflow registry syncer's in-memory allowlist with a large number of entries (occurs naturally over time in normal operation).
2. As an unauthenticated client, send a `SecretsList` (or other non-JWT) JSON-RPC request to the gateway's vault endpoint with a digest that does not match any allowlisted entry.
3. Observe (via unit test on `allowListBasedAuth.findAllowlistedItemWithRetry` or integration test against `GatewayVaultRequestProcessor.ProcessRequest`) that authorization takes up to 11 × O(n) scans and up to ~30 seconds before returning `"request not allowlisted"`.
4. Send many such requests concurrently to the gateway to observe cumulative goroutine/CPU/wall-clock consumption on the gateway process, with no per-sender rate limiter in `core/services/gateway/handlers/vault/handler.go` intervening.

func (r *allowListBasedAuth) findAllowlistedItemWithRetry(ctx context.Context, req jsonrpc.Request[json.RawMessage], requestDigest string, requestDigestBytes32 [32]byte) (*workflow_registry_wrapper_v2.WorkflowRegistryOwnerAllowlistedRequest, []string, error) {
	for attempt := 0; attempt <= r.retryCount; attempt++ {
		allowedRequests := r.workflowRegistrySyncer.GetAllowlistedRequests(ctx)
		allowedRequestsStrs := make([]string, 0, len(allowedRequests))
		for _, rr := range allowedRequests {
			allowedReqStr := fmt.Sprintf("AuthorizedOwner: %s, RequestDigest: %s, ExpiryTimestamp: %d", rr.Owner.Hex(), hex.EncodeToString(rr.RequestDigest[:]), rr.ExpiryTimestamp)
			allowedRequestsStrs = append(allowedRequestsStrs, allowedReqStr)
		}
		r.lggr.Debugw("AllowListBasedAuth loaded allowlisted requests", "method", req.Method, "requestID", req.ID, "attempt", attempt+1, "allowedRequests", allowedRequestsStrs)

		allowlistedRequest := r.fetchAllowlistedItem(allowedRequests, requestDigestBytes32)
		if allowlistedRequest != nil {
			return allowlistedRequest, allowedRequestsStrs, nil
		}
		if attempt == r.retryCount {
			return nil, allowedRequestsStrs, nil
		}

		r.lggr.Debugw("AllowListBasedAuth request digest not yet allowlisted, retrying",
			"method", req.Method,
			"requestID", req.ID,
			"digestHexStr", requestDigest,
			"attempt", attempt+1,
			"maxAttempts", r.retryCount+1,
			"retryInterval", r.retryInterval)
		if err := sleepWithContext(ctx, r.retryInterval); err != nil {
			r.lggr.Debugw("AllowListBasedAuth retry canceled", "method", req.Method, "requestID", req.ID, "error", err)
			return nil, nil, err
		}
	}

	return nil, nil, nil // unreachable: loop always returns
}

func (h *handler) fanOutToVaultNodes(ctx context.Context, l logger.Logger, ar *activeRequest) error {
	var nodeErrors []error
	for _, node := range h.donConfig.Members {
		err := h.don.SendToNode(ctx, node.Address, &ar.req)
		if err != nil {
			nodeErrors = append(nodeErrors, err)
			l.Errorw("error sending request to node", "node", node.Address, "error", err)
		}
	}

	if len(nodeErrors) == len(h.donConfig.Members) && len(nodeErrors) > 0 {
		return h.sendResponse(ctx, ar, h.errorResponse(ar.req, api.FatalError, errors.New("failed to forward user request to nodes"), nil))
	}

	l.Debugw("successfully forwarded request to Vault nodes")
	return nil
}

		case <-ticker:

			if err != nil {
				w.lggr.Errorw("failed to call getAllowlistedRequests", "err", err)
				continue
			}
			w.allowListedMu.Lock()
			// Prune expired requests
			activeAllowlistedRequests := []workflow_registry_wrapper_v2.WorkflowRegistryOwnerAllowlistedRequest{}
			expiredRequestsCount := 0
			for _, request := range w.allowListedRequests {
				if int64(request.ExpiryTimestamp) > time.Now().Unix() {
					activeAllowlistedRequests = append(activeAllowlistedRequests, request)
				} else {
					expiredRequestsCount++
				}
			}

			// Add new requests
			activeAllowlistedRequests = append(activeAllowlistedRequests, newAllowListedRequests...)

				"expiredRequestsNum", expiredRequestsCount,
				"activeRequestsNum", len(w.allowListedRequests),
				"lastSeenOnchainRequestsNum", w.lastSeenAllowlistedRequestsCount,
				"blockHeight", head.Height,
			)
			w.allowListedMu.Unlock()
		}
	}
