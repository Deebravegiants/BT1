### Title
Webhook shop-domain identity is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value that is handed to the host application's webhook handler from the `shopify-shop-domain` HTTP header, but the HMAC signature validated by `Utils::HmacValidator` only covers the raw request body. The identity binding the report calls for — "the shop authenticated versus the shop stored/used" — is broken: `request.shop` is never part of `request.to_signable_string`.

### Finding Description
`Registry.process` accepts a `Webhooks::Request`, checks `Utils::HmacValidator.validate(request)` [5](#0-4) , and then builds `WebhookMetadata` using `request.shop`, `request.topic`, `request.parsed_body`, etc. [6](#0-5) . `Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against `verifiable_query.hmac` [4](#0-3) . For `Webhooks::Request`, `to_signable_string` returns `@raw_body` only [1](#0-0) , and `shop` is read straight from a header with no cryptographic tie to the signature [2](#0-1) .

Equality that should hold: `shop_verified_by_hmac == shop_delivered_to_handler`. In this code, the left side does not exist at all — the HMAC only proves "this body was signed by our api_secret_key," not "this body was signed for shop X." Any request whose body+HMAC pair was legitimately produced by Shopify for tenant A's webhook can be replayed with the `shopify-shop-domain` header changed to tenant B, and `HmacValidator.validate` will still return `true`, because it never looks at the header at all.

This is exploitable by an unprivileged actor who is a legitimate merchant/tenant of the multi-tenant app: they can install the app on their own shop (A), capture a genuine webhook Shopify sends them (raw body + valid `x-shopify-hmac-sha256`), and resend that exact body/signature pair to the app's webhook endpoint with the `shopify-shop-domain` header swapped to another tenant's shop domain (B). The gem's registry will accept it as valid and dispatch it to the handler tagged as shop B's data, since `HmacValidator.validate` only checks the body signature, never the shop header [7](#0-6) .

### Impact Explanation
This crosses a tenant boundary: an attacker who legitimately controls one tenant (shop A) can cause the app to process attacker-controlled (their own, but re-labeled) webhook data as if it belonged to a different tenant (shop B), all while the gem reports `Utils::HmacValidator.validate` as passing. Depending on how the host application keys session lookup, data storage, or de-duplication off `WebhookMetadata#shop`, this enables cross-tenant data injection/confusion — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
The attacker only needs to be a legitimate, unprivileged merchant who has installed the app (no `api_secret_key`, no leaked credentials, no privileged account required) — they already receive genuine signed webhook bodies for their own shop from Shopify and can freely choose what HTTP headers to send when replaying that body to the app's public webhook endpoint. No secret material needs to be forged, since the header being changed is entirely outside the signed content.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the HMAC-signed content, or otherwise cryptographically bind the accepted `shop` value to the signature — e.g. compute the signature over `shop + raw_body`, or independently verify that the shop header matches an expected/registered shop for the session before dispatching to the handler in `Registry.process`.

### Proof of Concept
1. App receives a legitimate webhook from Shopify for `tenant-a.myshopify.com`:
   - Headers: `x-shopify-shop-domain: tenant-a.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw_body>`
   - Body: `{"id": 123, "note": "some order data"}`
2. Attacker (who owns/administers `tenant-a.myshopify.com` and legitimately receives this webhook) resends the exact same body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: tenant-b.myshopify.com`.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `raw_body` against the HMAC — this still passes [1](#0-0) .
4. The handler receives `WebhookMetadata` with `shop: "tenant-b.myshopify.com"` and the tenant-A order data, even though Shopify never issued this webhook for tenant B [6](#0-5) .
