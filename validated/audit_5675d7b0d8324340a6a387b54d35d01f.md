### Title
Anti-Spoofing Occlusion Threshold Is Hardcoded and Cannot Be Updated Without a Firmware Release - (File: `src/consts.rs`)

### Summary
The occlusion-detection threshold that gates whether a signup attempt is treated as "eyes occluded" (a liveness/anti-spoofing control analogous to the reported hardcoded royalty-fee percentage) is baked into the binary as `THRESHOLD_OCCLUSION_30` rather than being sourced from the backend-updatable `Config`/`BackendConfig` mechanism that nearly every other tunable parameter in orb-core uses.

### Finding Description
`THRESHOLD_OCCLUSION_30` is defined as a compile-time constant in `src/consts.rs`, with an explicit acknowledgment that this is the wrong design: [1](#0-0) 

This constant directly gates the biometric-capture liveness/occlusion check used during every signup, in `update_occlusion`: [2](#0-1) 

and is also used to seed the low-pass filter state at capture start: [3](#0-2) 

By contrast, virtually every other operationally significant parameter in the system — the under-age threshold, fraud-check engine settings, face-identifier model configs, PCP tiering thresholds, QR expiration, etc. — is deliberately routed through the backend-controlled `Config`/`BackendConfig` structures so operators/the backend can adjust it without shipping new firmware: [4](#0-3) [5](#0-4) 

`THRESHOLD_OCCLUSION_30` (and its sibling constants `IRIS_SCORE_MIN` / `IRIS_SHARPNESS_MIN`, also flagged with TODOs) is not part of this configuration surface at all, so there is no owner/backend-protected way to raise or lower the occlusion sensitivity in response to newly discovered spoofing techniques or model recalibration — mirroring exactly the bug class described in the report: a security-relevant numeric parameter is hardcoded with no update mechanism.

### Impact Explanation
Because the occlusion threshold that participates in fraud/liveness enforcement for every signup is fixed in the compiled binary, if this threshold is later found to be miscalibrated (e.g., too permissive, allowing a partially-occluded, spoofed, or non-live capture to be treated as clean), the backend/operator has no way to remediate it without a full firmware build-and-deploy cycle for the Orb fleet. This directly impacts the ability to defend the liveness/fraud enforcement boundary called out as in-scope, and is a structural weakness rather than a one-off misconfiguration.

### Likelihood Explanation
This is present in the default code path of every signup (`update_occlusion` runs on every IR-Net occlusion estimate during biometric capture), so the exposure is constant; the only trigger needed is a future discovery that the fixed 0.85 threshold (or its 1.5×/1.05×/1.025×/0.975× derived comparisons) is not conservative enough for some attack, at which point there is no operational lever to fix it quickly.

### Recommendation
Move `THRESHOLD_OCCLUSION_30` (and related hardcoded fraud/liveness thresholds such as `IRIS_SCORE_MIN`, `IRIS_SHARPNESS_MIN`) into the backend-controlled `Config`/`BackendConfig` structures — following the same pattern already used for `child_threshold` and `fraud_check_engine_config` — so that the value can be safely updated remotely, ideally with sane min/max clamping as done for other numeric backend-config fields (e.g. `fan_max_speed.clamp(...)` in `src/config.rs`).

### Proof of Concept
1. Inspect `src/consts.rs:347-349`: `THRESHOLD_OCCLUSION_30` is a `pub const` with a `TODO` noting it "should be a getter function from ir_net rather than a constant."
2. Trace its usage in `src/plans/biometric_capture/mod.rs::update_occlusion` (lines 666-690): the constant directly determines `occlusion_detected`, which is surfaced to the UI and factors into whether the capture is considered valid/clean.
3. Compare with `src/config.rs`/`src/backend/config.rs`, which show that essentially all other operational knobs (including the closely related `child_threshold`) are `Option<T>` fields sourced from the backend `Config` response, confirming that occlusion/liveness thresholds are the outlier that cannot be updated through the same, already-existing mechanism.

    // TODO: include the occlusion 90 and make it request the threshold occlusion from the python directly
    fn update_occlusion(&mut self, orb: &mut Orb, estimate: &EstimateOutput) {
        let dt = self.occlusion_center_led_timer.get_dt().unwrap_or(0.0);
        let EstimateOutput { mut occlusion_30, sharpness, .. } = *estimate;
        if occlusion_30.is_nan() || sharpness.is_nan() || sharpness < IRIS_SHARPNESS_MIN {
            occlusion_30 = THRESHOLD_OCCLUSION_30 * 1.05;
        }
        let occlusion_30_low_pass =
            self.occlusion_30_filter.add(occlusion_30, dt, OCCLUSION_CENTER_LED_LOW_PASS_FILTER_RC);
        // Apply hysteresis and a minimum pulse time.
        let occlusion_detected =
            if let Some(occlusion_indicator_on_time) = self.occlusion_indicator_on_time {
                occlusion_30_low_pass < THRESHOLD_OCCLUSION_30 * 1.025
                    || occlusion_indicator_on_time.elapsed() < OCCLUSION_INDICATOR_MIN_TIME_INTERVAL
            } else {
                occlusion_30_low_pass < THRESHOLD_OCCLUSION_30 * 0.975
            };
        if occlusion_detected {
            self.occlusion_indicator_on_time.get_or_insert_with(Instant::now);
            orb.ui.biometric_capture_occlusion(true);
        } else {
            orb.ui.biometric_capture_occlusion(false);
            self.occlusion_indicator_on_time = None;
        }
    }
