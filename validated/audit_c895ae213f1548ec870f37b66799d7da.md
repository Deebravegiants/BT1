### Title
Webhook shop identity taken from unauthenticated header, not bound by HMAC - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`Utils::HmacValidator.validate` verifies the HMAC over `Request#to_signable_string`, which is exclusively the raw request body. The `shop` value that `Registry.process` passes into the app's `WebhookHandler` (via `WebhookMetadata`) is read straight from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, which is not part of the HMAC-signed bytes.

### Finding Description
`HmacValidator.validate_signature` computes the HMAC over `verifiable_query.to_signable_string`, and for `Webhooks::Request` that method returns only `@raw_body`: [2](#0-1) 
Meanwhile, `Registry.process` trusts `request.shop`, which is populated from an HTTP header that is entirely attacker-controlled and never mixed into the signed bytes: [1](#0-0) [3](#0-2) 
This breaks the identity binding `bytes verified == bytes parsed`: the gem verifies "body is authentic" but hands the host application a `shop` claim ("this webhook is for tenant X") that was never authenticated. Since a valid HMAC only proves the raw body's integrity for *some* shop sharing the app's `api_secret_key` (all installs of one app share one `client_secret`), an attacker who can obtain one legitimate webhook delivery (e.g., from their own shop's install of the same app, which they fully control) can capture a valid `(raw_body, hmac)` pair and replay it to the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` header, causing `WebhookMetadata.shop` to report a victim shop while the HMAC check still passes.

### Impact Explanation
This allows cross-tenant confusion: `Registry.process`/`WebhookHandler#handle` will act on webhook data believing it originated from `shop: <victim>` when it only ever proved the body was untampered for the attacker's own shop. Any host application that uses `WebhookMetadata#shop` to look up which tenant/session/data to mutate (a documented and expected usage pattern of this gem) can be tricked into cross-tenant writes (e.g., processing a `customers/redact` or app-uninstall style webhook body against a different shop's records), which maps to the "cross-tenant access" impact category.

### Likelihood Explanation
Requires the attacker to control one working, low-privilege install of the app (their own shop) to obtain a valid raw body + HMAC pair, then send it directly to the app's public webhook endpoint with a forged shop-domain header — no access token, `api_secret_key`, or privileged account needed. This is a realistic "unprivileged internet user" path since webhook endpoints are public HTTP endpoints and the shop header is fully attacker-supplied.

### Recommendation
Include the shop domain (and ideally topic/api-version) inside the HMAC-signed material, or otherwise cryptographically bind `shop` to the verified payload — for example, require host applications to correlate `request.shop` against a shop already known/authorized for that specific delivery, and/or change `to_signable_string` so the shop is validated against a value obtained independently of the raw header (Shopify's actual webhook HMAC is computed only over the body by design, so the real mitigation is for `Registry.process` to document/require that consumers not treat `WebhookMetadata#shop` as authenticated proof of tenant without additional binding, or for the gem to expose a method that verifies the shop against a registered session/store rather than trusting the header value used elsewhere).

### Proof of Concept
1. Install the target app on an attacker-owned development shop `attacker.myshopify.com`; trigger any webhook (e.g. `app/uninstalled`) to receive a legitimate `(raw_body, x-shopify-hmac-sha256)` pair signed with the app's shared `api_secret_key`.
2. Replay that exact `raw_body` and `x-shopify-hmac-sha256` header to the app's public webhook endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` in `lib/shopify_api/webhooks/registry.rb#L190` succeeds because it only checks `raw_body` integrity.
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)` (`lib/shopify_api/webhooks/registry.rb#L198-199`), so any host logic keyed on `shop` operates on the victim tenant using attacker-supplied body content.
