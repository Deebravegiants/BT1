### Title
Webhook tenant identity (`shop`) is not covered by the HMAC signature, letting a captured payload be replayed against a different shop - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook using `Utils::HmacValidator.validate(request)`, but the HMAC signature that is validated only covers the raw request body. The `shop` (and `topic`, `webhook_id`, `api_version`) values are read from unauthenticated HTTP headers and passed straight into the handler as the trusted tenant identity, without being part of the signed data.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`ShopifyAPI::Webhooks::Request#shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of that signable string: [2](#0-1) [3](#0-2) 

`Registry.process` validates the HMAC and, once it passes, immediately trusts `request.shop` (the unsigned header) as the tenant identity handed to the app's handler: [4](#0-3) 

The intended binding is: `shop asserted in the authenticated request == shop the app treats as the authenticated tenant`. Because `shop-domain` is excluded from the signed bytes, this equality is never actually checked — only "some Shopify-signed body arrived" is proven, not "this body belongs to shop X." Any request whose body+HMAC pair is valid for the app's shared `client_secret` will be accepted for whatever `shop-domain` header is attached to it, since the secret used to compute/verify the HMAC is the app's single `api_secret_key`, not something scoped per shop.

### Impact Explanation
If an attacker who can obtain (or reuse) any single valid `(body, hmac)` pair generated for the app (e.g., from a webhook delivered to their own installed shop, from webhook logs, from a debugging/proxy tool, or from a delivery captured on an unencrypted hop) can then submit that same body/HMAC pair directly to the app's public webhook endpoint with an arbitrary `shopify-shop-domain` header, the gem will accept it as authentic and hand it to the app's handler tagged as belonging to a different, victim shop. Because the gem's own webhook-processing API is the thing asserting "this data is from shop X," host applications that trust `WebhookMetadata#shop` for tenant routing (e.g., to select which merchant's session/data to update) can be tricked into cross-tenant data processing — an app might apply order/customer/inventory data delivered for one merchant to another merchant's records. This corresponds to the cross-tenant-access class of impact.

### Likelihood Explanation
Exploitation requires the attacker to first obtain one valid `(body, hmac)` pair tied to the app (most plausibly by installing the app on a shop they control and observing/capturing a real webhook delivery, or by intercepting an insecure delivery). It does not require knowledge of `api_secret_key` or an access token, satisfying the "unprivileged internet user" framing. This is a real, structural gap in the library (the header used as the trust anchor for tenant identity is outside the authenticated envelope), but it depends on the attacker having a legitimate delivery to replay, which somewhat limits ease of exploitation compared to a pure forgery.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the authenticated data the HMAC covers, or otherwise cryptographically tie the header-derived shop to the verified body (e.g., include the header values in the signable string, or require the caller to independently confirm the shop is one for which the app holds an active session before trusting `WebhookMetadata#shop`). At minimum, document prominently that `request.shop`/`WebhookMetadata#shop` is not authenticated by the HMAC and must not be used as a sole tenant-identity source by host applications.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers/receives (or otherwise captures) one legitimate webhook delivery, yielding a valid `(raw_body, x-shopify-hmac-sha256)` pair signed with the app's shared `client_secret`.
2. Attacker POSTs that exact `raw_body` to the app's public webhook endpoint, replaying the captured `x-shopify-hmac-sha256` header unchanged, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this successfully (all required headers present) and `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the secret [5](#0-4) .
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)` [6](#0-5) , even though the data actually originated from the attacker's own shop — demonstrating the shop claim is accepted without being authenticated.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
