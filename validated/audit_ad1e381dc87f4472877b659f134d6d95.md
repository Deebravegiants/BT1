### Title
Division-by-zero panic in `calc_take_pnl` can permanently freeze LP deposits/withdrawals - ([File: program/src/processor.rs])

### Summary
`Processor::calc_take_pnl` and the `Calculator::calc_x_power` helper it calls perform unchecked division by the normalized pool reserves (`x1`/`y1`). If either the pc-side or coin-side reserve (net of `need_take_pnl_*`) is zero, the `checked_div(...).unwrap()` calls panic, reverting the transaction. Because `calc_take_pnl` is invoked from `process_deposit`, `process_withdraw`, and `process_withdrawpnl`, a pool that reaches a zero-reserve state on one side becomes permanently unable to process deposits or withdrawals, freezing any remaining LP funds — the same "zero division causes revert / funds locked" bug class described in the reported `SolverVault::deposit`/`requestWithdraw` issue.

### Finding Description
`Calculator::calc_x_power` divides by `current_y` with no zero check: [1](#0-0) 

`calc_take_pnl` then divides by `x1` when computing `y2`, again with no zero check: [2](#0-1) 

`x1` and `y1` are derived from `total_pc_without_take_pnl` / `total_coin_without_take_pnl` via `normalize_decimal_v2`, which itself is just a `checked_mul`/`checked_div` of the raw vault balance with no minimum-value guard: [3](#0-2) 

`total_pc_without_take_pnl`/`total_coin_without_take_pnl` are computed as `vault_amount - need_take_pnl_*`, so they can legitimately become `0` when the recorded PnL owed equals (or, in edge cases with lopsided withdrawals, drains) the vault balance on one side: [4](#0-3) 

Every call path that touches LP accounting recomputes `x1`/`y1` and feeds them into `calc_take_pnl`, including the unprivileged, user-reachable `process_deposit` and `process_withdraw` entry points: [5](#0-4) [6](#0-5) 

If `x1 == 0` (pc side exhausted) or `y1 == 0` (coin side exhausted), `calc_x_power`'s `.checked_div(current_y).unwrap()` or the subsequent `y2` computation's `.checked_div(x1).unwrap()` panics, causing the instruction to abort with a runtime panic instead of a clean program error.

### Impact Explanation
Once a pool's normalized reserve for one token side becomes exactly zero (while `lp_amount > 0`, i.e., LP tokens are still outstanding), every subsequent `deposit` and `withdraw` instruction against that pool will panic and revert, since they all funnel through `calc_take_pnl`. This permanently freezes any remaining LP-held funds in the pool with no recovery path, matching the "Medium" impact class of the reported analog (transaction revert due to zero division locking user funds).

### Likelihood Explanation
Reaching an exact zero reserve on one side requires a specific, lopsided pool state — this is not trivially reachable from a single normal swap (constant-product math keeps `amount_out < total_reserve`), but can arise from the interaction of `need_take_pnl_*` accounting and skewed/rounding-heavy withdrawals over the pool's lifetime, particularly for tokens with large decimal differences or thinly-liquid pools. This makes it a plausible, if not everyday, occurrence rather than a one-transaction certainty, which is consistent with the Medium severity of the analogous report.

### Recommendation
Add explicit zero-checks before dividing in `Calculator::calc_x_power` and in the `y2` computation of `calc_take_pnl`, returning a dedicated `AmmError` (e.g. `AmmError::CalcPnlError`) instead of allowing the `unwrap()` to panic. Consider also guarding `normalize_decimal_v2`/`calc_total_without_take_pnl_no_orderbook` callers to short-circuit the PnL calculation when either normalized reserve is zero.

### Proof of Concept
1. Drive a pool into a state where `total_pc_without_take_pnl` (or `total_coin_without_take_pnl`) equals `0` after subtracting `need_take_pnl_pc`/`need_take_pnl_coin` from the vault balance, while `amm.lp_amount > 0` — e.g., via repeated swaps that accrue `need_take_pnl_*` combined with a withdrawal that rounds one side's `total_*_without_take_pnl` down to zero (`Calculator::calc_total_without_take_pnl_no_orderbook`, `program/src/math.rs:238-250`).
2. Call `deposit` or `withdraw` again; `Calculator::normalize_decimal_v2` on the zero reserve yields `x1 == 0` or `y1 == 0` (`program/src/math.rs:106-116`).
3. `Processor::calc_take_pnl` calls `Calculator::calc_x_power(..., x1, y1)`, whose `.checked_div(current_y).unwrap()` (or the later `y2 = x2.checked_mul(y1).checked_div(x1).unwrap()`) panics, aborting the transaction (`program/src/math.rs:50-60`, `program/src/processor.rs:199-209`).
4. All future `deposit`/`withdraw` calls on this pool panic identically, permanently freezing any LP tokens still outstanding.

    pub fn calc_x_power(last_x: U256, last_y: U256, current_x: U256, current_y: U256) -> U256 {
        // must be use u256, because u128 may be overflow
        let x_power = last_x
            .checked_mul(last_y)
            .unwrap()
            .checked_mul(current_x)
            .unwrap()
            .checked_div(current_y)
            .unwrap();
        x_power
    }

    }

    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
