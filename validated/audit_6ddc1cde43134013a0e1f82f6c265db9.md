### Title
Webhook shop attribution is not covered by the HMAC, allowing cross-tenant data spoofing via header replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw request body for HMAC verification, while the `shop` identifier used to attribute the webhook payload to a tenant is taken from an HTTP header that is completely outside the HMAC's coverage. Any unprivileged attacker who has the app installed on their own store (a legitimate, low-privilege action) can capture a validly-signed webhook delivery for their own shop and replay the body with a forged `shopify-shop-domain`/`x-shopify-shop-domain` header pointing at a victim shop. The gem still reports the HMAC as valid and hands the handler data labeled with the attacker-chosen `shop`.

### Finding Description
`Utils::HmacValidator.validate` computes the signature exclusively over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw JSON body: [2](#0-1) 

The `shop` value, however, is read directly from an HTTP header and is never included in the signed material: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` to build the metadata handed to the app's webhook handler, with no cross-check that the shop matches anything else about the request: [4](#0-3) 

The identity binding that should hold is:
`hmac_valid(raw_body) == true` should imply `shop_header == shop_that_actually_produced(raw_body)`.

In reality, `hmac_valid(raw_body)` only proves the body bytes were signed by *some* shop that has the app installed (including the attacker's own shop) with the app's shared secret — it says nothing about which shop the header claims. An attacker who owns a store with the app installed:
1. Triggers a webhook event on their own store, capturing the legitimate `raw_body` and its correct `hmac-sha256` header from Shopify's real delivery.
2. Replays that exact `raw_body` + `hmac-sha256` value directly to the app's public webhook endpoint, but substitutes `shopify-shop-domain` (or `x-shopify-shop-domain`) with a victim shop's domain.
3. `HmacValidator.validate` passes (body+signature match), and `WebhookMetadata.new(shop: request.shop, ...)` is built with the victim's domain while the body content actually originated from the attacker's own store.

Any app logic that uses this `shop` value to attribute/store data, look up per-tenant records, or take shop-scoped action (e.g., writing into the victim shop's stored data, or triggering behavior keyed by `shop`) can be tricked into cross-tenant data confusion driven entirely by attacker-controlled data purporting to belong to a shop the attacker doesn't control.

### Impact Explanation
This breaks tenant isolation (cross-tenant data confusion) between the `shop` label trusted by the handler and the shop that actually authenticated the request payload — matching the Critical "cross-tenant access" impact category, since consuming applications rely on this gem's `shop` field as the authenticated tenant identifier for webhook processing.

### Likelihood Explanation
Requires only that the attacker be able to install the app on a shop they control (an ordinary, unprivileged action any merchant/developer can do) and the ability to send arbitrary HTTP requests with custom headers to the app's public webhook endpoint — both trivially available to an "unprivileged internet user."

### Recommendation
Bind the shop identity into the verified signature material (e.g., include the `shop-domain` header value, together with topic/webhook-id, in the string that is HMAC-verified), or otherwise cryptographically bind the reported shop to the signed body before constructing `WebhookMetadata`, rejecting the request if headers used for tenant attribution were not covered by the signature.

### Proof of Concept
```ruby
# 1. Attacker installs the app on their own shop "attacker-shop.myshopify.com"
#    and triggers any webhook event, capturing Shopify's real delivery:
raw_body = '{"id": 1, "note": "some event on attacker shop"}'
real_hmac_b64 = "<hmac captured from legitimate Shopify webhook delivery for attacker-shop>"

# 2. Attacker replays the exact body+hmac to the app's webhook endpoint,
#    but swaps the shop-domain header:
headers = {
  "shopify-topic" => "orders/create",
  "shopify-hmac-sha256" => real_hmac_b64,       # unchanged, still valid for raw_body
  "shopify-shop-domain" => "victim-shop.myshopify.com",  # forged
  "shopify-webhook-id" => "attacker-controlled-id",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) passes because it only checks raw_body against real_hmac_b64.
# The handler receives WebhookMetadata with shop == "victim-shop.myshopify.com"
# even though the payload came from the attacker's own store.
```
