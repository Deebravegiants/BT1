### Title
Webhook `shop-domain` (and `topic`/`api-version`/`webhook-id`) headers are not covered by the HMAC signature, enabling cross-tenant payload attribution - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then trusts the `shop-domain` header verbatim as the tenant identifier passed to the app's handler. Because the header is never part of the signed content, the binding `authenticated_bytes == acted_upon_shop` does not hold, so a caller who possesses one validly-signed webhook body can relabel it to any shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` (and `topic`, `api_version`, `webhook_id`) are read straight from HTTP headers with no cryptographic tie to the body: [2](#0-1) 

`Registry.process` validates the HMAC using `HmacValidator.validate(request)` — which, per `to_signable_string`, checks only the body against the app's shared `client_secret` — and then immediately hands `request.shop` to the application handler as the trusted tenant identifier, with no further binding check: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` confirm the signature is computed purely from `verifiable_query.to_signable_string`, i.e. the body, using the app-wide secret: [4](#0-3) 

Shopify signs webhooks with the app's `client_secret`, which is identical across every merchant that installs the same public app. Any unprivileged user can install the app on their own free development shop, trigger a legitimate webhook, and capture a genuinely valid `(raw_body, hmac)` pair. Because the `shop-domain` header sits outside the signed bytes, that same pair can be replayed to the app's webhook endpoint with the `shop-domain` header swapped to a victim shop. `HmacValidator.validate` still returns `true` (the body/HMAC pair is authentic), and `Registry.process` forwards `WebhookMetadata.new(... shop: request.shop ...)` carrying the attacker-chosen shop to the handler: [5](#0-4) 

The equality that should hold is:
`hmac_signed_bytes == bytes_that_determine_the_acted-upon_shop`
but in this implementation:
`hmac_signed_bytes == raw_body` while `acted-upon_shop == header["shop-domain"]`,
i.e., the field used to select/attribute the tenant is disjoint from the field covered by the cryptographic proof.

### Impact Explanation
Any host application built on this gem that uses `WebhookMetadata#shop` (as documented/exposed by `Registry.process`) to route processing, look up per-tenant session/storage, or attribute webhook data to a merchant is exposed to cross-tenant payload injection: an attacker-controlled shop can cause its own legitimately-signed webhook payload to be processed and stored under an arbitrary victim shop's identity, since the gem gives the host application no way to know that `shop` is unauthenticated. This falls under the Critical impact category "cross-tenant access," since the gem itself supplies an unauthenticated tenant identifier as if it were authenticated.

### Likelihood Explanation
Exploitation requires only an ability to install the target public app on any shop (unprivileged, self-service, no special access, no leaked credentials, no possession of `api_secret_key`/access tokens) and the ability to send an HTTP POST with attacker-controlled headers to the app's public webhook endpoint — both are available to an ordinary unprivileged internet user/merchant. The remaining variable is whether/how the host application uses `WebhookMetadata#shop`; the gem's own API surface (`Registry.process`, `WebhookMetadata`) actively encourages using this unauthenticated value as if it were verified, which is the root cause inside this gem's scope.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`api-version`/`webhook-id`) headers in the HMAC-signable content, or otherwise cryptographically bind the header-derived shop to the signed body, in `ShopifyAPI::Webhooks::Request#to_signable_string`. At minimum, document/enforce that `WebhookMetadata#shop` must not be trusted for tenant attribution unless it is included in the signed payload, and consider validating that the `shop-domain` header matches a shop value embedded in the JSON body where the topic includes one.

### Proof of Concept
1. Install the target public app on attacker-owned shop `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) and capture the raw POST: body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
2. Replay the exact same request to the app's webhook endpoint, but change the header `X-Shopify-Shop-Domain` from `attacker.myshopify.com` to `victim.myshopify.com`, keeping `B` and `H` unchanged.
3. In `ShopifyAPI::Webhooks::Registry.process`, `Utils::HmacValidator.validate(request)` recomputes the HMAC over `request.to_signable_string` (== `B`) and it matches `H`, so validation succeeds: [6](#0-5) 
4. The handler receives `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)` even though the payload actually originated from the attacker's shop, demonstrating the shop-domain/HMAC binding break: [5](#0-4)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
