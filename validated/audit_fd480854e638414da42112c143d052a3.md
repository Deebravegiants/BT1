### Title
Webhook Shop-Domain and Topic Not Bound by HMAC, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies only that the raw request body is HMAC-signed with the app's secret. The `shop-domain`, `topic`, `api-version`, and `webhook-id` headers — which are what the handler actually uses to decide *which tenant* the payload belongs to — are read straight from unauthenticated HTTP headers and are never included in the signed material. An attacker who controls a legitimately-installed shop for the same app (a normal, unprivileged installer, not an admin of Shopify or the target victim shop) can capture one of their own validly-signed webhook deliveries and replay the identical body+HMAC to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop. The signature still validates, and the host app processes attacker-controlled data as if it originated from the victim tenant — a cross-tenant binding break with no use of `api_secret_key`, access token, or victim credentials.

### Finding Description
`ShopifyAPI::Webhooks::Request` mixes in `Utils::VerifiableQuery` and defines: [1](#0-0) 

`to_signable_string` returns only `@raw_body`. Every other field the request exposes — `topic`, `shop`, `api_version`, `webhook_id` — is pulled directly from HTTP headers with no cryptographic binding: [2](#0-1) 

`Utils::HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it against the `hmac` header value: [3](#0-2) 

`Registry.process` uses this validation as the sole gate before dispatching, and then builds tenant-identifying metadata straight from the unauthenticated `shop` header: [4](#0-3) 

The equality this breaks: the gem treats `hmac_valid(raw_body) == true` as proof that `(shop, topic, body)` as a tuple is authentic for that shop, when in fact only `raw_body` is authenticated. The `shop` value handed to the host application's handler (used as the session/tenant key in virtually every consuming app) is not bound to the signature at all.

Because a single app's `api_secret_key` is shared across *every* shop that installs the app, any unprivileged merchant who installs the app on their own store receives genuinely HMAC-signed webhook deliveries for that store. They can capture the raw body and the `x-shopify-hmac-sha256` value from one of their own deliveries (e.g. via a proxy they control, or by having their endpoint log the request) and replay that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting `x-shopify-shop-domain: victim-shop.myshopify.com`. `HmacValidator.validate` still succeeds because it never looks at the shop header, and `Registry.process` calls the handler with `shop: "victim-shop.myshopify.com"` and the attacker's own body content.

### Impact Explanation
This is a cross-tenant binding break: an unprivileged installer of the app can inject attacker-controlled webhook payloads that a host application will attribute to a different (victim) shop. Depending on how the host app's `WebhookHandler` implementation uses `data.shop` (virtually always as the row/session key for storing or acting on the payload — e.g. updating order/customer records, triggering GDPR-request-style actions, or invalidating/creating sessions keyed by shop), this can lead to data corruption or unauthorized cross-tenant actions being performed against a shop the attacker does not control, satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Likelihood is realistic: the only prerequisite is installing the target app on any shop the attacker controls — a fully unprivileged action available to any Shopify merchant — and capturing one webhook delivery's body/HMAC pair via a proxy or logging endpoint. No secrets, tokens, or victim-shop access are required, and the header manipulation is trivial with any HTTP client.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the signed/verified material, or independently verify the `shop-domain` header against a value tied to the webhook subscription (e.g. compare against the registered webhook id resolved server-side rather than trusting the header). At minimum, `Request#to_signable_string` should incorporate all fields the handler relies on for tenant attribution, mirroring how `Auth::Oauth::AuthQuery#to_signable_string` binds `shop` into its signable string.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and registers a webhook subscription (e.g. `orders/create`).
2. Attacker triggers a delivery (e.g. creates an order) and captures the raw POST body and the `x-shopify-hmac-sha256` header value sent by Shopify to the app's webhook endpoint (attacker controls the endpoint or a proxy in front of it).
3. Attacker crafts a new HTTP POST to the same webhook endpoint with:
   - Identical raw body and `x-shopify-hmac-sha256` value captured in step 2.
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (any shop that has the app installed).
   - `x-shopify-topic: orders/create` (unchanged).
4. `ShopifyAPI::Utils::HmacValidator.validate` returns `true` because it only checks `HMAC(secret, raw_body)`, which is unchanged.
5. `ShopifyAPI::Webhooks::Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled order JSON>, ...)`, i.e. the host application processes attacker-controlled data believing it belongs to `victim-shop`.
