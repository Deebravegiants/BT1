## Custody Invariant Reduction

The Chainlink bug is about **trusting stale data without validating it reflects current state** (stale `timestamp`/`answeredInRound`). The Aptos-native custody analog: **a `TombStone.original_owner` field recorded at burn-time must never be trusted to authorize an ownership change unless it is proven consistent with the object's current, legitimate ownership history.** `aptos_framework::object`'s soft-burn/unburn mechanism violates this — it trusts a stale recovery claim that was never invalidated across an intervening legitimate transfer.

### Title
Stale `TombStone.original_owner` allows a past owner to reclaim an Object after it has been legitimately re-transferred and burned by a later owner - (File: aptos-move/framework/aptos-framework/sources/object.move)

### Summary
`object::burn` performs a "soft burn": it attaches a `TombStone{original_owner}` marker but does **not** change the object's `owner` field or disable `allow_ungated_transfer`. The object can therefore continue to be freely transferred through ordinary paths (`transfer`, `transfer_call`, `transfer_to_object` → `transfer_raw` → `transfer_raw_inner`). Unlike `transfer_with_ref` (the `LinearTransferRef` path), `transfer_raw_inner` never clears an existing `TombStone`. If a later legitimate owner sends the object to `BURN_ADDRESS` via an ordinary transfer, the stale `TombStone` (still recording the *original*, no-longer-current owner) lets that original owner call `unburn` and reclaim the object from the burn address, stealing it from the party who actually burned it.

### Finding Description [1](#0-0) 

`burn` does not transfer ownership away from the caller — `ensures is_owner(object, signer::address_of(owner))` per the spec — it only writes a `TombStone{original_owner}` while leaving `allow_ungated_transfer` untouched: [2](#0-1) 

Ordinary transfers go through `transfer_raw` → `transfer_raw_inner`, which only updates `owner` and emits an event — it never inspects or clears `TombStone`: [3](#0-2) 

By contrast, the `LinearTransferRef` path explicitly clears a stale `TombStone` specifically to prevent this class of bug, per its own comment: [4](#0-3) 

`unburn` then trusts the tombstone's `original_owner` field whenever current `owner == BURN_ADDRESS`, without verifying that `original_owner` is the party who actually performed the send to `BURN_ADDRESS`: [5](#0-4) 

Exploit sequence:
1. Alice owns object `X`. She calls `burn(alice, X)` → `TombStone{original_owner: alice}` is created; `X.owner` remains `alice`; ungated transfer stays enabled.
2. Alice legitimately sells/transfers `X` to Bob via `object::transfer` (ordinary ungated transfer). `TombStone` is **not** cleared (only `transfer_with_ref` clears it).
3. Bob, the new legitimate owner, later decides to genuinely retire/burn `X` by sending it to `BURN_ADDRESS` via an ordinary `transfer`/`transfer_call` (a completely normal, unprivileged operation — `BURN_ADDRESS` is just a constant address, not specially gated).
4. `X.owner == BURN_ADDRESS`, but `TombStone.original_owner` is still `alice` (stale from step 1).
5. Alice calls `unburn(alice, X)`. Since `object_core.owner == BURN_ADDRESS` and `tomb_stone.original_owner == alice`, the function executes `transfer_raw_inner(object_addr, alice)` — Alice reclaims the object.

Alice, who no longer legitimately owns `X` (she sold it to Bob), recovers it from the burn sink instead of Bob (the actual party who chose to burn it), and Bob's real disposal/burn intent is undone in favor of an unrelated stale claimant.

### Impact Explanation
This is a direct custody-integrity break: unauthorized ownership reassignment of an `Object`-held asset. This applies to any Move object built on `aptos_framework::object`, including NFTs/token objects (`aptos_token`, `ambassador`, `guild`, etc.) and fungible-asset primary stores, since primary store custody logic is explicitly built on `object::burn`/`object::unburn` (see requirement doc): [6](#0-5) 
A past owner can hijack value away from the legitimate current chain of custody, which is theft/unauthorized owner reassignment of object-held (and potentially fungible-asset-held) value — a High severity custody violation.

### Likelihood Explanation
Both `burn` and `unburn` are `public entry` functions directly callable by any account for any object they can produce an `Object<T>` handle for; no privileged role is required. The only precondition is that the object passes through the specific but realistic sequence: soft-burn → ordinary re-transfer (a supported, common operation since soft-burn does not disable transfers) → send-to-`BURN_ADDRESS`. Existing tests (`test_burn_and_unburn_old`, `test_cannot_unburn_after_transfer_with_ref`) only cover burn-then-immediate-unburn and burn-then-`transfer_with_ref`, not the burn → ordinary-transfer-to-new-owner → new-owner-burns-to-`BURN_ADDRESS` path, indicating this gap was not covered by the mitigation added for the `LinearTransferRef` case.

### Recommendation
Clear any existing `TombStone` on every ownership-changing path, not just `transfer_with_ref`. Specifically, `transfer_raw_inner` (or `transfer_raw`) should remove a stale `TombStone` whenever the owner actually changes, mirroring the fix already applied in `transfer_with_ref`:
```move
inline fun transfer_raw_inner(object: address, to: address) {
    let object_core = borrow_global_mut<ObjectCore>(object);
    if (object_core.owner != to) {
        if (exists<TombStone>(object)) {
            let TombStone { original_owner: _ } = move_from<TombStone>(object);
        };
        event::emit(Transfer { object, from: object_core.owner, to });
        object_core.owner = to;
    };
}
```
Additionally, `unburn`'s `BURN_ADDRESS` branch should only ever succeed for a `TombStone` that was created via the same transaction/flow that sent the object to `BURN_ADDRESS`, not an arbitrary earlier tombstone from a prior owner.

### Proof of Concept
```move
#[test(alice = @0x123, bob = @0x456)]
fun test_stale_tombstone_theft(alice: &signer, bob: &signer) {
    let (_, hero) = create_hero(alice);

    // Step 1: Alice soft-burns (does not change owner, does not disable transfer).
    burn(alice, hero);
    assert!(hero.owner() == signer::address_of(alice), 0);

    // Step 2: Alice legitimately transfers to Bob via an ordinary transfer.
    transfer(alice, hero, signer::address_of(bob));
    assert!(hero.owner() == signer::address_of(bob), 1);
    // TombStone still exists with original_owner = alice (not cleared by transfer_raw_inner).

    // Step 3: Bob genuinely burns it by sending to BURN_ADDRESS via ordinary transfer.
    transfer(bob, hero, BURN_ADDRESS);
    assert!(hero.owner() == BURN_ADDRESS, 2);

    // Step 4: Alice, a past owner with no current claim, reclaims it from the burn sink.
    unburn(alice, hero);
    assert!(hero.owner() == signer::address_of(alice), 3); // Theft: Alice regains an object she sold to Bob.
}
```

    /// Allow origin owners to reclaim any objects they previous burnt.
    public entry fun unburn<T: key>(
        original_owner: &signer,
        object: Object<T>,
    ) {
        let object_addr = object.inner;
        assert!(exists<TombStone>(object_addr), error::invalid_argument(EOBJECT_NOT_BURNT));

        // The new owner of the object can always unburn it, but if it's the burn address, we go to the old functionality
        let object_core = borrow_global<ObjectCore>(object_addr);
        if (object_core.owner == signer::address_of(original_owner)) {
            let TombStone { original_owner: _ } = move_from<TombStone>(object_addr);
        } else if (object_core.owner == BURN_ADDRESS) {
            // The old functionality
            let TombStone { original_owner: original_owner_addr } = move_from<TombStone>(object_addr);
            assert!(
                original_owner_addr == signer::address_of(original_owner),
                error::permission_denied(ENOT_OBJECT_OWNER)
            );
            transfer_raw_inner(object_addr, original_owner_addr);
        } else {
            abort error::permission_denied(ENOT_OBJECT_OWNER);
        };
    }
