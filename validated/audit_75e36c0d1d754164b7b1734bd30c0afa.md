Confirmed root cause: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop` is read directly from the unsigned `x-shopify-shop-domain`/`shopify-shop-domain` header [2](#0-1) . `Registry.process` validates only the HMAC over the body and then forwards `request.shop` straight into the tenant-identifying `WebhookMetadata` passed to the app's handler [3](#0-2) .

### Title
Webhook tenant identity (`shop` header) is not covered by the HMAC, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signature over the raw body only, but the `shop` value used by `ShopifyAPI::Webhooks::Registry.process` to identify which tenant a webhook belongs to is taken from an HTTP header that is never included in the signed material.

### Finding Description
`HmacValidator.validate` verifies `OpenSSL::HMAC.hexdigest(secret, verifiable_query.to_signable_string)` against the received `hmac` [4](#0-3) . For webhooks, `to_signable_string` is defined as just `@raw_body` [1](#0-0) . Meanwhile `shop` (as well as `topic`, `api_version`, `webhook_id`) is read straight from request headers, independent of the signed body [2](#0-1) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e., body integrity/authenticity) and then trusts `request.shop` as the tenant identity passed to the handler: `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` [5](#0-4) .

The broken binding, stated as an equality that should hold but does not:
`HMAC-authenticated(raw_body, secret) == true` should imply `shop header == shop that produced raw_body`, but the gem only proves the former; the header is fully attacker-controlled and unauthenticated.

Because the same `api_secret_key` is shared across every shop/tenant installed on a given app, any party who can obtain one valid `(raw_body, hmac)` pair for the app (e.g., by installing the app on their own store and capturing a webhook Shopify sends them) can resubmit that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. `HmacValidator.validate` will still return `true` because it never looks at the header, so `Registry.process` will invoke the handler with `shop` set to the attacker-chosen value while `body` is the (still valid) captured payload.

### Impact Explanation
This is a cross-tenant identity confusion: the host application's webhook handler (which typically uses `data.shop` to look up/act on that merchant's session, data, or storage record) can be made to process a webhook attributed to a shop that never sent it. Depending on how the host app uses `data.shop` (e.g., writing merchant-scoped state, triggering fulfillment or redact/GDPR flows, updating a specific tenant's row), this can lead to cross-tenant data corruption or spoofed mandatory-compliance webhooks (`customers/redact`, `shop/redact`, `customers/data_request`) being attributed to the wrong shop. This matches the "shop authenticated versus shop trusted as identity key" analog and is High severity per the given impact categories (scope/tenant-binding bypass).

### Likelihood Explanation
Any user able to install the app on their own store (a normal, unprivileged flow for public/embedded apps) can capture one legitimate `(body, hmac)` pair from a real Shopify-delivered webhook and replay it with a forged `shop-domain` header directly to the app's public webhook endpoint. No access to `api_secret_key`, tokens, or the target shop's credentials is required — only network access to the endpoint and one captured payload from the attacker's own tenant.

### Recommendation
Include the tenant-identifying header(s) (`shop-domain`, and ideally `topic`, `webhook-id`) in the HMAC-signed material for webhook requests, or otherwise cryptographically bind the `shop` value to the signed body before trusting it as a tenant key in `WebhookMetadata`. At minimum, `Registry.process`/host apps should be instructed (and the gem should assist) to cross-check `request.shop` against a shop known to be enrolled/authorized for that specific `topic`/`webhook_id`, rather than trusting the raw header outright.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, capturing the raw POST body `B` and the `x-shopify-hmac-sha256` header value `H` (a valid HMAC of `B` under the app's shared `api_secret_key`).
2. Attacker sends a forged POST to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256: H` (unchanged, still valid since it signs only `B`)
   - Header `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
   - Header `x-shopify-topic: orders/create` (unchanged)
3. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present) [6](#0-5) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `@raw_body` only and matches `H` — validation passes [7](#0-6) .
5. The handler is invoked with `WebhookMetadata` whose `shop` is `"victim-shop.myshopify.com"`, even though the body/order data actually belongs to the attacker's own shop [8](#0-7) .

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
