### Title
i128 overflow in interest accrual permanently freezes a market — every entry point accrues first (`common/src/rates/scaling.rs`)

### Summary
The external report is a NULL pointer dereference that crashes the process (remote DoS). The XOXNO Lending analog is a `MathOverflow` panic inside `scaled_to_original` during interest accrual: once a market's `borrow_index` grows large enough that `borrowed * borrow_index` exceeds `i128::MAX`, the accrual step aborts. Because every user-facing controller verb (supply, borrow, withdraw, repay, liquidate, clean_bad_debt, flash paths) runs accrual before touching positions, and the permissionless `update_indexes` also runs it, the entire market is bricked: no repayment, no withdrawal, no liquidation, ever. User collateral and debt are permanently frozen.

### Finding Description
`accrue_step` in `common/src/rates/simulate.rs` calls `scaled_to_original(env, borrowed, borrow_index)` and `scaled_to_original(env, supplied, supply_index)` at the top of every compounding step. `scaled_to_original` is `scaled.mul(env, index)` in `common/src/rates/scaling.rs:14-16`, which panics with `GenericError::MathOverflow` on i128 overflow rather than saturating.

`update_borrow_index` (`common/src/rates/index.rs:13-19`) multiplies the index by the interest factor *before* clamping to `MAX_BORROW_INDEX_RAY`, and the unscaled-value product check happens only implicitly through the panic — there is no guard that `borrowed * borrow_index < i128::MAX` before `scaled_to_original` runs. For a large-scale market (e.g., an 18-decimal asset) at sustained high utilization, the borrow index crosses the `i128::MAX / borrowed` threshold well before reaching `MAX_BORROW_INDEX_RAY`, so the cap never engages.

The repo's own test proves the end state: `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` in `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-360` shows `update_indexes` returning `MATH_OVERFLOW`, after which `withdraw` and `repay` revert with the same error — "the market is frozen: exits and repayments accrue first and hit the same panic."

### Impact Explanation
Permanent freezing of funds and protocol insolvency mechanics for that market: suppliers cannot withdraw, borrowers cannot repay, liquidators cannot seize collateral. All positions on the affected (hub, token) book are stuck indefinitely; there is no admin path that skips accrual, so even governance intervention cannot recover the book without a contract upgrade. This matches the accepted "permanent freezing of funds" / "contract unable to operate" impact class.

### Likelihood Explanation
Reachable entirely by unprivileged addresses: `update_indexes` is permissionless, and any address can open large supply/borrow positions to raise utilization and push the borrow rate onto the steep segment of the curve. The barrier is capital and time — the market must be large (high-decimals asset, whale-scale principal) and sustained near-max utilization until the index grows past `i128::MAX / borrowed`, which the test shows occurs before the `MAX_BORROW_INDEX_RAY` cap. Not attacker-triggered on demand, so Medium likelihood; the trigger, once reached, is irreversible.

### Recommendation
Bound the accrual inputs instead of letting `scaled_to_original` panic:
- In `accrue_step`, check `borrowed.raw() <= i128::MAX / borrow_index.raw()` (and symmetrically for `supplied * supply_index`) before multiplying; on breach, clamp the index to `MAX_BORROW_INDEX_RAY` / `MAX_SUPPLY_INDEX_RAY` rather than aborting.
- Alternatively, make `update_borrow_index` saturate *before* multiplication (compute `min(factor, i128::MAX / old_index)`) so the cap always engages before any overflow.
- Add a regression test asserting that at the index ceiling, `update_indexes`, `withdraw`, and `repay` still succeed rather than reverting with `MathOverflow`.

### Proof of Concept
Existing test demonstrating the freeze (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-360`):

```rust
let principal = BILLION * 10i128.pow(18);          // whale-scale 18-decimal asset
t.supply_raw(BOB, "BIG18", principal);
t.borrow_raw(ALICE, "BIG18", principal / 100 * 98); // ~98% utilization
loop {
    t.advance_time(YEAR_SECS);
    if let Err(e) = t.try_update_indexes_for(&["BIG18"]) { break e; } // MathOverflow
}
// borrow_index < MAX_BORROW_INDEX_RAY: the cap never engaged
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

Root cause: `common/src/rates/scaling.rs:14-16` (`scaled.mul` panics on overflow), called unconditionally at `common/src/rates/simulate.rs:60-61` inside `accrue_step`, which every controller verb reaches via `ops::renewed_market` / `interest::global_sync`.
