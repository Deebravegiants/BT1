### Title
Duplicate-assetId batch withdrawal causes describeWithdrawal to misreport a failed withdrawal as completed with a stolen txHash - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` and `findMatchingWithdrawal` match POA API withdrawal records only by `assetId` (`nep141:${near_token_id}`), ignoring the `WithdrawalIdentifier.index` and any per-withdrawal amount/destination distinction. When a single signed intent contains multiple withdrawals of the same `assetId`, and one of them fails while others complete, the failed withdrawal's status lookup can match an already-"claimed" COMPLETED record belonging to a different withdrawal, returning that record's `txHash` as if it were the failed withdrawal's completion.

### Finding Description
The broken equality is: **reported status/txHash for withdrawal at `index=N`** should equal **the actual on-chain outcome of that specific withdrawal**. Because `findMatchingWithdrawal` performs a bare `Array.prototype.find` keyed solely on `assetId` [1](#0-0) , it has no way to distinguish between multiple withdrawals of the same token within one batch/tx. The code comment explicitly acknowledges this: "multiple withdrawals of the same token in a single transaction are not supported" [2](#0-1) .

Exploit flow:
1. Attacker (an ordinary user) signs one intent containing 3 withdrawals of the same `assetId`, amounts `[100, 200, 300]`, to three different destination addresses.
2. `createWithdrawalIdentifiers` assigns indices 0,1,2 for the same bridge route but the same `tx.hash` (the single signed NEAR intent tx) to all three `WithdrawalIdentifier`s [3](#0-2) .
3. `watchWithdrawal` polls `describeWithdrawal` independently for each index, each call hitting `getWithdrawalStatus({ withdrawal_hash: args.tx.hash })` — the *same* hash for all three [4](#0-3) .
4. The relayer completes withdrawals 0 and 1 but withdrawal 2 (amount 300) fails/never lands; the API returns only 2 COMPLETED records for the shared `assetId`.
5. For `index=2`, `findMatchingWithdrawal` (an `Array.find`) returns the first record whose `near_token_id` matches — one of the two COMPLETED records that already "belongs" to index 0 or 1 — yielding `{ status: "completed", txHash: <someone else's tx> }` [5](#0-4) .
6. `watchWithdrawal` treats this as a genuine completion and resolves with that stolen hash [6](#0-5) .

No existing guard prevents this: `supports()`, `validateWithdrawal`, and `createWithdrawalIntents` never check for or reject duplicate `assetId`s within a batch, and `findMatchingWithdrawal` has no uniqueness/consumption tracking (it doesn't mark a record as already matched to another index) — it can return the same record to multiple callers.

### Impact Explanation
An integrator using `watchWithdrawal`/`waitForWithdrawalCompletion` to confirm on-chain settlement will receive a `completed` status with a real (but wrong) `txHash` for a withdrawal that actually failed. This is a status/hash misreport that can cause the integrator to credit or refund the user twice (once implicitly via belief that the 300-unit withdrawal succeeded, and again if they issue manual remediation for the "failed" leg, or fail to retry a stuck withdrawal because it appears completed). This matches the **High** impact category ("a status or hash misreport making an integrator credit or refund twice"). It's repeatable any time an attacker crafts a multi-withdrawal batch with duplicate `assetId`s and one leg fails, and it doesn't require privileged access — any ordinary user can construct such a signed intent.

### Likelihood Explanation
Preconditions: a single signed intent with ≥2 withdrawals sharing the same `assetId` via the POA bridge route, where at least one succeeds and at least one fails/never completes at the relayer. This is entirely attacker-controlled (the attacker signs their own intent with their own funds) and costless to set up. The only external dependency is the relayer executing withdrawals asynchronously with partial failure, which is a normal, expected operational scenario for the POA bridge (not a "malicious relayer" assumption — ordinary transient failures suffice). No SDK-side validation currently rejects same-asset multi-withdrawal batches, so this is fully feasible and repeatable per batch.

### Recommendation
Track which withdrawal records have already been matched/claimed within a `describeWithdrawal` call chain (e.g., pass already-consumed indices/hashes and exclude them from subsequent matches), or reject/queue duplicate-`assetId` withdrawals within a single batch until the POA API supports disambiguating them by index/amount as the code comment suggests (sort by amount on both sides). At minimum, `describeWithdrawal` should refuse to return `completed` for an index if the matched record was already returned for a different index in the same batch.

```typescript
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
```

```typescript
export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
```
