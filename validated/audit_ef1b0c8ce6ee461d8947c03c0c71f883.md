### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers and are never bound to that signature. Any actor who can obtain one valid `(raw_body, hmac)` pair (trivially available to any developer who installs the app on their own free/dev store and lets Shopify deliver a webhook) can replay that pair to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header, and `HmacValidator.validate` will still report success. The app will then process attacker-controlled payload data as though it originated from a victim shop.

### Finding Description
`Webhooks::Request` mixes in `Utils::VerifiableQuery` and defines: [1](#0-0) 
```
def hmac
  Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
end
...
def shop
  T.cast(shopify_header("shop-domain"), String)
end
...
def to_signable_string
  @raw_body
end
```
`to_signable_string` — the value that `HmacValidator.compute_signature`/`validate_signature` actually hash and compare — is exclusively `@raw_body`: [2](#0-1) 
```
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
```
`shop`, `topic`, `webhook_id`, and `api_version` are simply parsed off the incoming headers with no cryptographic binding to that HMAC check: [3](#0-2) 

This is structurally the same bug class as the report's `tnsl`/reward issue: a field that downstream logic *acts on* (there: the rolled-over reward amount computed from `tnsl`; here: the `shop` used to attribute/process the webhook) is not actually protected by the check meant to guarantee its integrity (there: the epoch-bounded HMAC-independent `tnsl` math; here: the HMAC signature that only covers `raw_body`). The equality that should hold is:

`shop_that_Shopify_signed_this_payload_for == shop_header_used_by_Registry.process`

but the gem only verifies `bytes_verified(raw_body) == bytes_received(raw_body)`, leaving `shop` (and `topic`/`webhook_id`) completely unauthenticated.

### Impact Explanation
Any unprivileged internet user who can install the target app on a shop they control (a normal, free Shopify development/trial store is enough — no `api_secret_key`, access token, or privileged account of the *target* app is required) can:
1. Trigger a real webhook delivery from Shopify to the app's public webhook endpoint, capturing a genuine `(raw_body, X-Shopify-Hmac-Sha256)` pair signed with the app's real `api_secret_key` (which the attacker never needs to know).
2. Replay that exact `raw_body` + `hmac-sha256` header to the same public endpoint, but change the `shop-domain` header to a victim shop that also has the app installed.
3. `HmacValidator.validate` still returns `true`, because it only re-hashes `raw_body`; `Registry.process` then dispatches the handler with `shop` == the victim's domain and attacker-chosen `body`/`topic` content that is treated as authoritative for the victim tenant.

Depending on how the host app keys its business logic off `Webhooks::Request#shop` (session lookup, data writes, billing/inventory sync, etc.), this enables cross-tenant data confusion/spoofing — an attacker-controlled event body is processed as if it came from a victim shop. This matches the "cross-tenant access" High-severity impact category.

### Likelihood Explanation
Likelihood is realistic: the webhook receiver is by design a public, unauthenticated-by-mTLS HTTP endpoint that must accept POSTs from the internet; obtaining a valid `(body, hmac)` pair only requires installing the app on any shop the attacker controls (no secret, no privileged access, no TLS interception needed); and swapping one header on a replayed request is trivial for any HTTP client.

### Recommendation
Bind the identity fields to the HMAC-verified payload rather than trusting headers independently:
- Include `shop`, `topic`, and `webhook_id` in `to_signable_string` (or otherwise cryptographically bind them to the body before verification), OR
- After verifying the HMAC on the raw body, cross-check that the `shop-domain` header matches a shop value embedded/expected inside the verified payload, and reject mismatches, similar to how `AuthQuery#to_signable_string` in `lib/shopify_api/auth/oauth/auth_query.rb` includes `shop` as part of the signed string.

### Proof of Concept
```ruby
# Attacker controls "attacker-shop.myshopify.com" (installed the app themselves)
# and captures a real webhook delivery from Shopify with a valid HMAC:
captured_body = '{"id": 1, "note": "hi"}'
captured_hmac_header = "REAL_BASE64_HMAC_FROM_SHOPIFY"  # signs captured_body only

# Attacker now POSTs directly to the app's public webhook endpoint,
# reusing the untouched body/hmac but swapping the shop header:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => captured_hmac_header,   # unchanged, still valid for captured_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_body, headers: headers)
ShopifyAPI::Utils::HmacValidator.validate(request) # => true, because to_signable_string == captured_body only
ShopifyAPI::Webhooks::Registry.process(request)    # handler invoked with shop == "victim-shop.myshopify.com"
```
`request.shop` returns the forged victim domain while `HmacValidator.validate` still passes, confirming the shop identity is unauthenticated relative to the signature check. [4](#0-3) [5](#0-4)
