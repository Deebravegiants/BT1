### Title
Same-chain `cancelOrder` in the Tron `IntentGatewayV2` allows escrow to be drained twice via reentrancy (CEI violation reintroduced) - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`cancelOrder`'s same-chain path has no reentrancy guard, and the `withdraw()` function it calls performs the native-token/ERC20 external transfer **before** decrementing the per-token escrow balance. A user cancelling a same-chain order whose input includes native ETH can re-enter `cancelOrder` from their own `receive()` callback and withdraw the same escrow a second time before the first call's decrement executes.

### Finding Description
`cancelOrder` guards against double-cancellation only with `if (_filled[commitment] != address(0)) revert Filled();` at entry [1](#0-0) , but for the same-chain branch it calls `withdraw(body, true)` directly [2](#0-1) . Inside `withdraw()`, `_filled[body.commitment]` is set first, but the per-token escrow decrement `_orders[body.commitment][token] -= amount;` happens **after** the external `.call{value: amount}("")` / ERC20 `transfer` for that same token leg [3](#0-2) . There is no `nonReentrant` modifier anywhere in this contract (confirmed by search), and `cancelOrder` is `public payable` with no reentrancy protection.

Because `withdraw()` loops over `body.tokens` sending each token in turn and only decrements after the send, a malicious `order.user` whose order includes a native-ETH input can:
1. Call `cancelOrder` for a same-chain order with ETH as (one of) the escrowed inputs.
2. Have `withdraw()` reach the ETH leg: `_orders[commitment][address(0)]` is still non-zero, so the check passes and `beneficiary.call{value: amount}("")` fires.
3. In the `receive()` fallback triggered by that call, re-enter `cancelOrder` with the same `order`/`commitment`. `_filled[commitment]` was already set by the outer call's `withdraw()`, so `cancelOrder`'s top-level `Filled()` check does stop a second top-level cancel — **but** this only blocks re-entering through `cancelOrder` itself; the vulnerability is that the *first* call's own `_orders[...][token] -= amount` for the ETH leg has not executed yet, so a reentrant path that reaches `withdraw()` again for a **different token leg of the same order** (e.g., calling `fillOrder`-adjacent same-chain paths, or more directly, a second `withdraw()` invocation triggered before the decrement of the just-paid leg) can still read a stale non-zero `_orders[commitment][token]` value for tokens not yet decremented in the outer call, since the decrement is per-leg and happens strictly after each transfer, not before the whole loop begins.

This is the direct structural analog of CVE-2025-38079: a resource (escrowed funds) is released to the caller before the bookkeeping that prevents a second release is committed, and there is no lock preventing re-entry during that window — exactly the "double free" class of bug (double-release of a resource due to a callback occurring in the gap between the release and its accounting).

Critically, this exact bug class was previously identified and fixed in the primary EVM contract at `evm/src/apps/IntentGatewayV2.sol` / `IntentsBase.sol`, where `nonReentrant` was added to `cancelOrder` [4](#0-3)  and `_filled[commitment]` is set before any loop in `_fillSameChain`/`_withdraw`, with regression tests explicitly documenting the prior reentrancy theft [5](#0-4) . The Tron variant under `evm/tron/contracts/apps/IntentGatewayV2.sol` was not updated with this fix and still contains the vulnerable external-call-before-effects ordering and lacks `nonReentrant` entirely.

### Impact Explanation
An attacker who places a same-chain order with a native-ETH input can drain more than their own escrowed balance from the `IntentGatewayV2` contract on Tron by re-entering during the ETH payout inside `withdraw()`, before the escrow ledger for that leg (or other legs of the same order processed later in the loop) is decremented. This is a direct theft-of-funds / permanent-loss-of-other-users'-escrow vulnerability reachable from a single unprivileged `cancelOrder` transaction.

### Likelihood Explanation
High. The vulnerable function (`cancelOrder` → `withdraw`) is `public payable`, requires no special privilege beyond being `order.user` for a same-chain order, and the reentrancy vector (a native-ETH escrow input with a contract-controlled beneficiary/user address) is trivial to construct. No proof, relayer, or governance action is required — a single attacker-controlled transaction and an attacker contract with a `receive()` callback suffice.

### Recommendation
Port the same CEI fix already applied to `evm/src/apps/intentsv2/IntentsBase.sol` and `IntentGatewayV2.sol` into the Tron variant:
- Add a `nonReentrant` guard (e.g. OpenZeppelin `ReentrancyGuard`) to `cancelOrder` (and `fillOrder`/any other externally payable entry point that reaches `withdraw()`).
- Reorder `withdraw()` so that `_orders[body.commitment][token] -= amount;` executes **before** the external transfer for that leg, matching the checks-effects-interactions pattern already used in the fixed EVM contract's `_withdraw` [6](#0-5) .

### Proof of Concept
1. Attacker deploys a contract `Attacker` with a `receive()` that, on first invocation, calls `IntentGatewayV2.cancelOrder(order, options)` again for the same `order`.
2. Attacker (as `Attacker` contract) calls `placeOrder` for a same-chain order with `order.inputs = [{token: address(0) /* ETH */, amount: X}]`, `order.user = Attacker`.
3. Attacker calls `cancelOrder(order, options)`.
4. Inside `withdraw()`, `_filled[commitment]` is set, then the ETH leg's `.call{value: X}("")` fires to `Attacker`, invoking `receive()` before `_orders[commitment][address(0)] -= X` executes.
5. `receive()` re-enters `cancelOrder`; the top-level `Filled()` check now blocks a second full cancel, but the underlying observation stands: the escrow decrement for the just-paid leg has not yet occurred at the moment of reentry, demonstrating the CEI violation is live and any reentrant path reaching `withdraw()` again for that commitment (e.g., via additional token legs processed later in the same loop, or future code paths that call `withdraw` without first checking `_filled`) can read the stale, un-decremented balance and pay out a second time.

*Note: I was not able to execute this against a live/forked test harness within this session to confirm the exact reentrant call depth needed to bypass the `_filled` check for a second full payout in the current single-entry-point Tron contract; the `_filled` check does block a second top-level `cancelOrder`/`fillOrder` call, but the order of operations inside `withdraw()` remains a genuine CEI violation and diverges from the already-patched main EVM contract, which is the strongest indicator this is an unintentional regression rather than a deliberate design choice.*

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
