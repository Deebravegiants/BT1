### Title
Webhook `shop` (and `topic`/`webhook_id`) header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives its identity fields (`shop`, `topic`, `webhook_id`, `api_version`) directly from HTTP headers, but `to_signable_string` — the data actually covered by the HMAC signature check in `Utils::HmacValidator.validate` — is only the raw request body. `Registry.process` trusts the header-derived `shop` when dispatching to the registered handler, so the binding "HMAC-verified bytes" ≠ "shop attributed to the webhook" is broken.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight out of request headers with no cryptographic binding to the HMAC at all: [2](#0-1) [3](#0-2) 

`Registry.process` validates only the body's HMAC and then unconditionally trusts `request.shop` (and `request.topic`, `request.webhook_id`) to build the metadata passed to the app's handler: [4](#0-3) 

`HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string`, i.e. the raw body, using the app's single, install-wide `Context.api_secret_key`: [5](#0-4) 

Because `api_secret_key` is one shared secret for the whole app (not per-shop), *any* shop that has the app installed can capture a legitimate `(raw_body, hmac)` pair sent to their own store's webhook endpoint (e.g., by pointing a webhook receiver they control at the same body, or simply observing their own inbound webhook traffic). That same `(raw_body, hmac)` pair remains valid under `HmacValidator.validate` regardless of which shop it is replayed for, since the shop is never included in the signed payload. The attacker can then replay the request to the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` (or `shopify-shop-domain`) header naming a victim shop. `Registry.process` will validate the HMAC (it only checks the body), then call the handler with `WebhookMetadata` claiming the victim's `shop`: [6](#0-5) 

This is directly analogous to the ERC20Facet bug: the check that "authenticates" the payload (HMAC over body / name+symbol non-empty) does not cover the field actually used to make a trust decision (which shop the data belongs to / whether the contract is initialized), so an attacker can manipulate the unverified field to spoof identity.

### Impact Explanation
This breaks the binding `shop authenticated by HMAC == shop used for tenant-scoped business logic`. A merchant with the app installed on their own store (an "unprivileged" party relative to other tenants) can forge webhook events attributed to any other shop that also uses the app, since the shared `api_secret_key` makes any valid `(body, hmac)` pair reusable across tenants. Depending on the host app's webhook handlers (e.g., `orders/create`, `app/uninstalled`, `shop/redact`), this enables cross-tenant data injection or triggering of shop-specific side effects (fulfillment actions, data deletion flows, billing events) against a shop the attacker does not control — a cross-tenant access vector.

### Likelihood Explanation
Exploitation requires only: (1) the app being installed on at least one shop controllable by the attacker (a normal merchant/dev store, not privileged access), and (2) capturing one legitimate raw webhook body + its HMAC for any topic the attacker wants to spoof. Both are readily achievable by any merchant using the app (e.g., by inspecting a webhook payload sent to their own endpoint) since the secret is shared app-wide rather than shop-specific, and the shop-domain header is never included in the signed content.

### Recommendation
Bind the shop identity to the verified payload: include `shop` (and ideally `topic`, `webhook_id`) in the HMAC signable string, or otherwise cryptographically tie the header-derived shop to the signed body before trusting it in `Registry.process`. At minimum, document and/or enforce that consuming applications must independently verify the `shop` header against a known/installed shop list before acting on `WebhookMetadata#shop`, since the gem's own HMAC check does not protect that field.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` with the same `api_secret_key` used for all installs.
2. Attacker triggers/observes a webhook to their own endpoint and records `raw_body` and the `x-shopify-hmac-sha256` header (a valid pair since `HmacValidator.validate` only checks the body against the shared secret): [7](#0-6) 
3. Attacker sends this same `raw_body` and `hmac` header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and any desired `x-shopify-topic`.
4. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC successfully (body unchanged) and invokes the handler with `shop: "victim-shop.myshopify.com"`: [8](#0-7) 
5. The app's handler performs shop-scoped logic believing the event genuinely originated from `victim-shop.myshopify.com`.

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
