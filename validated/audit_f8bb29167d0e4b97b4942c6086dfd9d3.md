### Title
Webhook shop-domain and topic are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body via `Utils::HmacValidator.validate(request)` [1](#0-0) . The `Webhooks::Request#to_signable_string` method that is HMAC-verified returns only `@raw_body`, while `topic`, `shop`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers and are never part of the signed material [2](#0-1) . This breaks the intended binding: `hmac_valid(body) == true` should imply `shop == authenticated_shop`, but here `shop` and `topic` are accepted independently of the signature that is supposed to authenticate the whole message.

### Finding Description
`Utils::HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to `verifiable_query.hmac` [3](#0-2) . For the webhook case, the signed string is exactly the raw JSON body (`@raw_body`) [4](#0-3) . The `shop`, `topic`, `webhook_id`, and `api_version` fields are parsed straight out of the `x-shopify-*` / `shopify-*` headers with no cryptographic tie to the HMAC that `Registry.process` checks [5](#0-4) .

`Registry.process` then trusts these unauthenticated fields directly: it dispatches on `request.topic` to select the handler and forwards `request.shop` into `WebhookMetadata` for the handler to act on [1](#0-0) .

Because any request body with a given JSON payload produces a fixed, secret-independent-of-headers HMAC, a party who has legitimately received one webhook delivery (e.g., for their own shop, or any payload with identical body content) can present the same `(raw_body, hmac)` pair to the app's webhook endpoint with a *different* `x-shopify-shop-domain` and/or `x-shopify-topic` header. `Utils::HmacValidator.validate` will still return `true` because it only checks the body, and `Registry.process` will call the handler with an attacker-chosen `shop`/`topic` in `WebhookMetadata`, even though that shop/topic pair was never actually signed by Shopify for that combination.

This breaks the equality the report's bug class targets: the identity the HMAC authenticates (`body`) is not the identity the handler code acts on (`shop`, `topic`). `hmac_valid` only proves `secret_owner_signed(body)`, not `secret_owner_signed(shop, topic, body)`.

### Impact Explanation
If a host application's webhook handler uses `WebhookMetadata#shop` to select which merchant's tenant data to update, delete, or use for authorization decisions (a common integration pattern, e.g., "look up the access token for `data.shop` and act on that shop's data"), an attacker who can produce or replay any HMAC-valid `(body, hmac)` pair (trivial for topics/bodies they control themselves, e.g. a shop they installed the app on, or by replaying an observed webhook) can redirect the processing to a different shop identifier. Combined with a host app that stores/looks up sessions keyed by `shop`, this enables cross-tenant action/data confusion, which the rules classify as Critical (cross-tenant access).

### Likelihood Explanation
Exploitation requires the ability to send an HTTP request to the app's webhook endpoint with attacker-controlled headers and a body+hmac pair that is valid for the *shared* app secret — obtainable by any party who has ever received (or can generate, if they run their own store with the app installed) a legitimate webhook delivery, since the HMAC only binds the body, not the headers. No access token, `client_secret`, or privileged credential is required, satisfying the "unprivileged internet user" analog criteria. The actual severity in a live deployment depends on the host app trusting `WebhookMetadata#shop`/`#topic` without an additional check (e.g., cross-referencing against the shop that installed the app), which the library documentation implicitly assumes is unnecessary since Shopify itself is expected to be the only sender.

### Recommendation
Bind the `shop` and `topic` (and ideally `webhook_id`/`api_version`) to the authenticated material before they are trusted:
- Include `shop`, `topic`, and `webhook_id` in `Webhooks::Request#to_signable_string`, or
- After HMAC validation, cross-check `request.shop` against the shop associated with the currently active/looked-up session/access token before invoking the handler, and document that host applications must not treat `WebhookMetadata#shop`/`#topic` as authenticated purely because `Registry.process` succeeded.
- At minimum, update documentation to explicitly warn that the HMAC only authenticates the raw body, not the `shop-domain`/`topic` headers, so integrators do not implicitly trust those fields for tenant routing.

### Proof of Concept
```ruby
# Attacker obtains (or generates, e.g. via their own installed test shop) a valid webhook delivery:
raw_body = '{"id": 1}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# Attacker crafts a new request with the SAME body/hmac but a DIFFERENT shop domain/topic:
forged_headers = {
  "x-shopify-topic" => "shop/redact",                     # attacker-chosen topic
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),        # same valid hmac (body unchanged)
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",  # attacker-chosen shop, not the one that actually sent this body
  "x-shopify-webhook-id" => "attacker-controlled-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# This passes HMAC validation because only raw_body is checked:
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle is invoked with WebhookMetadata(shop: "victim-shop.myshopify.com", topic: "shop/redact", ...)
# even though neither "shop" nor "topic" were ever part of the signed material.
```

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

          received_signature = verifiable_query.hmac
