### Title
Unchecked ERC20 `transfer` return value in `IntentGatewayV2.withdraw` and `SweepDust` handling permanently marks escrow as settled even when the token transfer silently fails - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` escrows ERC20 tokens on order creation and releases them on `RedeemEscrow`/`RefundEscrow`/`SweepDust` delivery via `onAccept`. Unlike the rest of the contract (and the sibling `evm/src/apps/IntentGatewayV2.sol`, which consistently uses `SafeERC20.safeTransferFrom`), the payout paths in this file perform a raw low-level `.call()` to `IERC20.transfer` and only check that the call itself did not revert, never decoding the ERC20 boolean return value. Any token that returns `false` instead of reverting on a failed transfer (a well-known non-conforming ERC20 pattern) will cause funds to be considered delivered while never actually moving, permanently freezing the escrowed value.

### Finding Description
In `withdraw()`, invoked from `onAccept` for `RedeemEscrow`/`RefundEscrow` requests that are delivered by any relayer submitting a verified cross-chain message, and in the `SweepDust` branch, ERC20 payouts are done like this: [1](#0-0) 

`token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `success = true` as soon as the target contract does not revert, regardless of what boolean value (if any) the ERC20 `transfer` function actually returns. For a token that implements `transfer` to return `false` on failure (e.g. insufficient balance in some non-standard implementations, blacklists, or a paused/rugged token) rather than reverting, `success` is `true`, so `if (!success) revert TransferFailed();` never fires.

Immediately after this unchecked call, the function unconditionally updates accounting state as if the transfer succeeded: [2](#0-1) 

`_filled[body.commitment] = beneficiary;` marks the order permanently filled/refunded and `_orders[body.commitment][token] -= amount;` decrements the escrow accounting even though the beneficiary received nothing. Since `_filled` and `_orders` are now updated, the withdrawal cannot be retried or re-triggered (the incoming request is one-shot, authenticated via `authenticate(incoming.request)` and processed once), so the escrowed tokens remain stuck in the contract with no accounting path left to redeem them. The identical unchecked pattern also appears in the `SweepDust` branch and in the fee payout: [3](#0-2) 

The contract already imports and uses `SafeERC20` elsewhere (`using SafeERC20 for IERC20;`), showing the correct pattern was known but not applied consistently to these payout sites.

### Impact Explanation
This directly matches "concrete theft or permanent freezing of funds": a solver/user filling or cancelling an order whose input/output token is a non-standard ERC20 (returns `false` on failure instead of reverting) will have their escrowed funds marked as redeemed/refunded on-chain while never receiving the tokens, and there is no retry mechanism once `_filled`/`_orders` are updated. This is reachable by any relayer delivering a normally-processed `RedeemEscrow`/`RefundEscrow`/`SweepDust` message — no privileged role is required, only that the escrowed asset behaves this way (which is plausible for arbitrary ERC20s supported by the intents gateway, since token support is not restricted to strictly-conforming implementations).

### Likelihood Explanation
Likelihood is moderate-to-high: it requires the escrowed token to be a non-reverting-on-failure ERC20 (a documented and not-uncommon class of tokens), and it triggers automatically on the normal cross-chain settlement/refund/dust-sweep flow with no attacker privilege needed beyond choosing/using such a token in an order, which the IntentGateway does not appear to restrict against.

### Recommendation
Replace the raw `.call()` + `success`-only checks in `withdraw()` and the `SweepDust` branch of `onAccept` with `SafeERC20.safeTransfer` (already imported and used via `using SafeERC20 for IERC20;` elsewhere in the contract), which reverts on both call failure and a `false` boolean return, ensuring accounting state is never advanced unless the transfer genuinely succeeded.

### Proof of Concept
1. An order escrows a token `T` that implements `transfer` to return `false` (rather than revert) when the transfer cannot be completed (e.g., recipient blacklisted, contract paused, or any other conditional failure returning `false`).
2. Order is filled/cancelled and Hyperbridge delivers a `RedeemEscrow`/`RefundEscrow` `onAccept` message to `IntentGatewayV2` on the escrow chain.
3. Inside `withdraw()`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` executes `T.transfer` which returns `false` without reverting; `success` is `true` so the `TransferFailed` revert is skipped. [4](#0-3) 
4. `_filled[body.commitment]` is set and `_orders[body.commitment][token]` is decremented as if the beneficiary was paid.
5. The beneficiary's token balance never changed, but the commitment can no longer be redeemed through any other path — the escrowed `amount` of `T` is permanently stuck in the `IntentGatewayV2` contract.
