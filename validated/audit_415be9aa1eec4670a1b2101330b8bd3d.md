### Title
Owner `removeChain()` on `WrappedHyperFungibleTokenUpgradeable` can permanently freeze in-flight locked tokens (no timelock, zero-timeout messages unrecoverable) - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleTokenUpgradeable.sol`)

### Summary
`WrappedHyperFungibleTokenUpgradeable.removeChain()` lets the owner instantly delete a peer chain's `_supportedChains` mapping entry with no timelock or grace period. Any POST request already in flight (tokens locked on the source chain via `send()`) that has `timeout == 0` ("no timeout") can never be delivered after removal (because `onAccept` requires `expectedSource.length != 0` and reverts with `UnsupportedChain`), and can never be recovered via timeout either, since a zero-timeout request is defined by the protocol to never expire. This mirrors the JOJO `delistReserve` bug class: an unqualified, un-timelocked admin removal instantly invalidates user positions/messages already committed, with no way for affected users to react or recover funds.

### Finding Description
`send()` locks the underlying ERC20 (or wraps native ETH) and dispatches a `PostRequest` to the destination chain's peer contract registered in `_supportedChains[dest]`: [5](#0-4) 

The owner can call `removeChain(chainId)` at any time, deleting the mapping entry with no delay: [1](#0-0) 

On the destination chain, `onAccept()` (invoked by the ISMP host when a relayer delivers the message with a valid membership proof) checks `_supportedChains[request.source]` and reverts with `UnsupportedChain` if the source chain was removed there, or `onAccept` on the sending side's peer contract similarly requires the entry to exist: [2](#0-1) 

Crucially, if the dispatcher's `SendParams.timeout` was set to `0`, the protocol treats this as "no timeout — message never expires": [4](#0-3) [3](#0-2) 

Since a zero-timeout request never reaches its `timeout_timestamp`, `on_timeout`/`onPostRequestTimeout` (the only path that refunds locked tokens back to the sender) can never be triggered for it. If the destination-side owner calls `removeChain()` for the source chain (or the source-side owner removes the destination) after such a message has been dispatched but before it is relayed, the message becomes permanently undeliverable, and because it has no timeout, it is also permanently unrefundable. The locked tokens (in the contract's custody) are frozen forever, with no on-chain recourse for the user — the owner can only fix this by re-adding the chain (`addChain`), which is not guaranteed and is entirely subject to the owner's future choices.

Even for non-zero timeouts, the removal is instantaneous and gives users zero notice/grace period to avoid initiating transfers that will be stuck for the full timeout duration, unlike the recommended timelock pattern.

### Impact Explanation
This can cause permanent freezing of user funds locked in the wrapped-token bridge contract, triggered by a single unprivileged action (a user's own `send()` call) combined with an admin action that requires no attacker coordination — only an owner decision (which could also be a compromised or reactive key, e.g. delisting a compromised peer). Because zero-timeout messages are an explicitly supported and documented protocol feature, this is a realistic operational configuration, not a contrived edge case, and directly matches the "permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
Likelihood is moderate: it requires (1) a user dispatching a transfer with `timeout = 0` (or any timeout, for a smaller-scale liveness/freeze window), and (2) the owner calling `removeChain` for that route before relaying completes. `removeChain` is a normal, expected admin operation (e.g., decommissioning a deprecated deployment, responding to a compromised peer, or migrating module addresses) rather than a rare or malicious event, so the race condition is plausible in production usage, especially since off-chain relayer delivery latency is nondeterministic.

### Recommendation
- Do not allow `timeout = 0` ("no timeout") to be combined with a chain-removal path that has no timelock, or disallow zero-timeout dispatches altogether in this app.
- Add a timelock/grace period to `removeChain()` (and `addChain()` re-pointing to a different `moduleId`) so in-flight requests can be relayed or can time out before the mapping is cleared.
- Alternatively, provide an owner-callable recovery/refund path for messages whose destination chain entry has been removed, independent of the ISMP timeout mechanism.

### Proof of Concept
1. Owner configures chain B as supported peer via `addChain(chainB, moduleB)`.
2. User calls `send({dest: chainB, ..., timeout: 0})`, locking `amount` of the underlying ERC20 in the contract and dispatching a `PostRequest` with `timeoutTimestamp = 0`.
3. Before any relayer delivers the request to chain B, owner calls `removeChain(chainB)` on chain A (or the destination-side owner removes chain A's entry on chain B).
4. Relayer later attempts delivery; `onAccept` reverts with `UnsupportedChain` on chain B — the message can never be executed there.
5. Because `timeoutTimestamp == 0`, `post.timed_out()` (per `modules/ismp/core/src/router.rs`) never returns true (`Duration::from_secs(u64::MAX)`), so `onPostRequestTimeout` can never be triggered on chain A to refund the locked tokens.
6. The user's locked tokens remain stuck in the chain-A contract indefinitely, recoverable only if the owner unilaterally re-adds chain B later.
