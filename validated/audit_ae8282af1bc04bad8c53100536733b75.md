### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) headers are trusted for tenant identity but excluded from the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying the HMAC over the raw request body, but the `shop` value that is then handed to the app's handler (and used to decide which tenant's data to act on) is read from an HTTP header that is **not** part of the signed content. This breaks the identity binding: `hmac_valid(raw_body) == true` should imply `shop == the tenant that produced raw_body`, but the library allows `shop` to be substituted freely without invalidating the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 

`to_signable_string` returns only `@raw_body`, so the HMAC computed by `HmacValidator` never covers the `shop`, `topic`, `webhook-id`, or `api-version` values, all of which are read straight from HTTP headers: [2](#0-1) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (which hashes `raw_body` against `Context.api_secret_key`) before dispatching to the topic handler with `request.shop` as the tenant identifier: [3](#0-2) 

Because the signature only binds `raw_body`, any `(raw_body, hmac)` pair that was ever legitimately produced by Shopify for **any** shop (including a shop the attacker controls, e.g., a free/dev store they create themselves) remains a valid signature for that same body with an **arbitrary substituted `shopify-shop-domain` header**. An unprivileged internet user who operates their own Shopify dev store can trigger a real webhook delivery to capture a valid `(raw_body, hmac)` pair, then replay that exact body/HMAC to the app's public webhook endpoint while setting `shopify-shop-domain` to a victim shop's domain. `HmacValidator.validate` will still return `true` (it only compares the HMAC over `raw_body`), and `Registry.process` will call the app's handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` where `shop` is the attacker-chosen, unverified victim domain.

This is exactly the identity-binding class flagged in scope: *"a field acted on but not covered by the HMAC."* The equality that should hold is:
`shop_used_by_handler == shop_that_actually_produced(raw_body, hmac)`
but the implementation only enforces `hmac_matches(raw_body)`, decoupling the two.

### Impact Explanation
If the host application's webhook handler uses `data.shop` (as constructed in `Registry.process`) to select which tenant's records to update/delete/read (a documented, expected pattern for webhook handlers, e.g. `shop/redact`, `customers/redact`, order/product sync, etc.), an attacker can forge cross-tenant writes/deletes by supplying a self-obtained legitimate webhook body/HMAC together with a victim's shop domain. This is a cross-tenant data-integrity/exfiltration primitive achievable purely with public network access to the app's webhook endpoint plus the ability to generate at least one real webhook for a shop the attacker controls (a normal, unprivileged capability — anyone can spin up a Shopify dev/trial store and trigger webhooks like `app/uninstalled`, `shop/update`, etc.). No access token, `client_secret`, or leaked credential is required, satisfying the Critical - cross-tenant access category.

### Likelihood Explanation
Exploitability depends on the app's handler trusting `shop` from `WebhookMetadata` to scope its side effects — a normal and encouraged usage pattern (see `lib/shopify_api/webhooks/webhook_handler.rb`). The attacker needs only: (1) a Shopify store of their own to receive at least one authentic webhook delivery for a topic that also fires for other shops (most topics qualify), and (2) network access to POST to the app's public webhook route. Both are trivially available to an unprivileged internet user, making this readily exploitable wherever an app's webhook handler is shop-scoped without independently re-verifying `shop` against the signed body content.

### Recommendation
Bind `shop` (and ideally `topic`, `api-version`, `webhook-id`) into the signed content checked by `HmacValidator`, e.g. by including the relevant headers in `to_signable_string`, or by validating that the `shop` header matches an expected/allow-listed value tied to the session/install record before trusting it, similar to how `Auth::Oauth::AuthQuery#to_signable_string` binds `shop` into its HMAC:
```diff
 sig { override.returns(String) }
 def to_signable_string
-  @raw_body
+  "#{shopify_header("shop-domain")}\n#{shopify_header("topic")}\n#{@raw_body}"
 end
```
Note this changes the signature computation, so it must match how Shopify actually signs webhook payloads (Shopify's `X-Shopify-Hmac-Sha256` is computed over the raw body only per Shopify's public documentation) — if header binding cannot be added without breaking compatibility with Shopify's real signing scheme, the library should instead document/enforce that consuming applications must independently verify `request.shop` against their own known list of installed shops before trusting it as a tenant key, and this gem's `WebhookMetadata`/`Registry.process` should not present an unverified header value as if it were authenticated.

### Proof of Concept
1. Attacker creates their own Shopify development store `attacker-shop.myshopify.com` and installs the target app, causing the app to register for webhook topic `T` (e.g., `shop/update`).
2. Shopify sends a legitimate webhook to the app: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for `B` with the app's `client_secret`), header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker replays the exact same request to the app's webhook endpoint, but changes only the header:
   `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   Body `B` and `X-Shopify-Hmac-Sha256: H` are unchanged.
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` computes `HMAC(secret, B)` and compares to `H` — it matches, since `shop` was never part of the signed input (`lib/shopify_api/webhooks/request.rb:35-38`).
5. `Registry.process` invokes the topic handler with `WebhookMetadata.new(topic: T, shop: "victim-shop.myshopify.com", body: parsed(B), ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the app to apply attacker-controlled webhook content under the victim shop's identity.
