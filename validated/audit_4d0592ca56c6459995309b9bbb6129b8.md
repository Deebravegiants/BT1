### Title
Webhook `shop` (and `topic`) identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates webhook authenticity solely via `Utils::HmacValidator.validate(request)`, which signs only the raw request body. The `shop` and `topic` values used to route and attribute the webhook are read from unauthenticated HTTP headers (`x-shopify-shop-domain`, `x-shopify-topic`) that are never included in the HMAC-signable string. This breaks the identity binding: `shop`(HMAC-verified) ≠ `shop`(used for dispatch/attribution).

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` and `topic` are parsed straight from headers, independent of the signed body: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then dispatches the handler using the header-derived, unsigned `topic` and passes the header-derived, unsigned `shop` straight into `WebhookMetadata`: [3](#0-2) 

`HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` (the raw body) against the computed signature — it has no knowledge of, and does not bind, the `shop-domain` or `topic` headers: [4](#0-3) 

Because the merchant's own shop legitimately receives HMAC-signed webhook deliveries from Shopify (signed with the app's `api_secret_key` over the body only), an unprivileged internet user who *is themselves an installed/authenticated merchant* of the app can capture one of their own valid signed webhook payloads and replay it to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header (and/or `X-Shopify-Topic` header) naming a *different* tenant shop or a different webhook topic. The signature check still passes because the body — the only thing actually signed — is unchanged and genuinely valid. The gem then hands the handler a `WebhookMetadata` object whose `shop` is entirely attacker-controlled and unauthenticated, breaking the equality `shop (HMAC-bound identity) == shop (used for tenant attribution)`.

### Impact Explanation
This is a cross-tenant identity spoofing vector: the webhook processing pipeline attributes verified-body data to an attacker-chosen shop/topic. Any host application that trusts `WebhookMetadata#shop` (as documented/intended usage of this library) to determine which tenant's data record to create/update/delete will act on behalf of the wrong tenant using data an attacker fully controls in shape and timing (replay of their own legitimate payload) combined with arbitrary shop/topic headers. This matches "cross-tenant access" (Critical) since the gem's own webhook verification API provides no protection against header spoofing despite headers carrying the sole identity/routing signal.

### Likelihood Explanation
High/practical: any merchant who installs the app is, by design, a legitimate source of correctly-signed webhook bodies for their own shop. Replaying that body with modified headers requires no secret material, no privileged access, and no interception — just a normal HTTP client sending a POST to the app's public webhook endpoint with attacker-controlled headers. No compromise of `api_secret_key` or Shopify infrastructure is required.

### Recommendation
Bind the shop (and ideally topic) identity into the value that is actually authenticated. Concretely:
- Have `Webhooks::Request#to_signable_string` incorporate the `shop-domain` (and `topic`) header material into what is HMAC-verified, or
- Have `Registry.process` independently corroborate the header-derived `shop` against a value derived from the verified body (if Shopify's webhook payloads include the shop id/domain in-body), rejecting mismatches, or at minimum document/enforce that host applications must not trust `WebhookMetadata#shop`/`#topic` for tenant attribution without an out-of-band corroboration (e.g., only invoke handlers for topic/shop combinations the app itself registered for that specific shop's known session).

### Proof of Concept
1. Merchant A installs the app; Shopify sends a legitimately signed webhook to the app's endpoint with headers `X-Shopify-Shop-Domain: shop-a.myshopify.com`, `X-Shopify-Topic: orders/create`, and a body `B` whose HMAC (computed over `B` with the app's `api_secret_key`) is `H`.
2. Merchant A (or anyone who can observe this HTTP request, since they control their own shop's webhook deliveries/tunnel) captures `(headers, B, H)`.
3. Attacker resends `POST /webhooks` with body `B` and signature header unchanged (`H`), but sets `X-Shopify-Shop-Domain: shop-victim.myshopify.com` and/or `X-Shopify-Topic: customers/data_request`.
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` because it only checks `B` against `H`, per: [5](#0-4) 
5. `Registry.process` proceeds to invoke the handler registered for the spoofed topic with `WebhookMetadata.new(shop: "shop-victim.myshopify.com", body: parsed_body_of_B, ...)`, per: [3](#0-2) 
6. Any host application logic keyed on `data.shop` now processes attacker-supplied data under the identity of a shop the attacker does not control.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
