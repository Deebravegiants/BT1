### Title
Unbounded swap fee bps in `set_stable_fee`/`set_volatile_fee` lets `fee_manager` set custody-draining fee rates - (File: aptos-move/move-examples/swap/sources/liquidity_pool.move)

### Summary
`liquidity_pool.move` defines a constant `MAX_SWAP_FEES_BPS = 25` (intended cap of 0.25%) but never enforces it. The `fee_manager`-gated setters `set_stable_fee` and `set_volatile_fee` write `new_fee_bps` directly into `LiquidityPoolConfigs` with no upper-bound check, and existing pools' `swap_fee_bps` is likewise never re-validated against this cap when a pool inherits the config value at creation time.

### Finding Description
`LiquidityPoolConfigs` stores `stable_fee_bps`/`volatile_fee_bps`, initialized to 10/20 bps [1](#0-0) . The module declares `MAX_SWAP_FEES_BPS: u64 = 25` as the intended ceiling (0.25%) at declaration [2](#0-1) , but this constant is never referenced anywhere else in the file (only its declaration and the `FEE_SCALE` denominator of 10000 are used elsewhere for fee math) — the search for `MAX_SWAP_FEES_BPS` usage returns only its own definition line, confirming the check is dead/never enforced.

The setter functions are:
```
public entry fun set_stable_fee(fee_manager: &signer, new_fee_bps: u64) acquires LiquidityPoolConfigs {
    let pool_configs = fee_manager_only_mut_liquidity_pool_configs(fee_manager);
    pool_configs.stable_fee_bps = new_fee_bps;
}

public entry fun set_volatile_fee(fee_manager: &signer, new_fee_bps: u64) acquires LiquidityPoolConfigs {
    let pool_configs = fee_manager_only_mut_liquidity_pool_configs(fee_manager);
    pool_configs.volatile_fee_bps = new_fee_bps;
}
``` [3](#0-2) 

Neither function bounds `new_fee_bps` against `FEE_SCALE` (10000, i.e. 100%) or `MAX_SWAP_FEES_BPS`. The only guard is the `fee_manager_only_mut_liquidity_pool_configs` authorization check, which confirms caller identity but does not validate the value [4](#0-3) .

This value is consumed directly in the swap fee calculation:
```
let fees_amount = math64::mul_div(amount_in, pool_data.swap_fee_bps, FEE_SCALE);
let amount_in = ((amount_in - fees_amount) as u256);
``` [5](#0-4) 

New pools created after a malicious/compromised `fee_manager` sets `stable_fee_bps`/`volatile_fee_bps` above `10000` inherit that value into `LiquidityPool.swap_fee_bps` at creation time: `swap_fee_bps: if (is_stable) { configs.stable_fee_bps } else { configs.volatile_fee_bps }` [6](#0-5) . If `swap_fee_bps > FEE_SCALE` (>10000), `fees_amount` computed via `mul_div(amount_in, swap_fee_bps, FEE_SCALE)` can exceed `amount_in`, causing `amount_in - fees_amount` at line 329 to underflow (Move u64 subtraction aborts on underflow) — a straightforward DoS on swaps for any pool created under that misconfigured fee. Even without overflow-triggering underflow, any value up to 10000 (100%) is a custody-relevant fee-drain: a `fee_manager` could set the fee to 100%, causing every swapper's entire input to be extracted as "fees" (deposited into `fees_store_1`/`fees_store_2`), which are only withdrawable via `claim_fees` by LPs — a full value transfer from swappers to LP fee accounting with no cap, exceeding the documented/intended 0.25% maximum.

### Impact Explanation
This breaks the custody invariant that swap fees are bounded and predictable: an authorized-but-unbounded `fee_manager` (a single non-multisig role, set at `initialize()` to `@deployer` and transferable via `set_fee_manager`/`accept_fee_manager`) can silently redirect up to 100% of every swapper's input into the fee pool, or set a fee bps `> FEE_SCALE` and cause an underflow abort that permanently DoSes swaps on that pool. Both are custody-grade: economic value is misdirected away from the intended holder (the swap counterparty) to the fee/LP accounting, and in the overflow case, users' funds already deposited into the pool for swap (via `fungible_asset::deposit(store_1, from)` before the abort check) — though transactions abort atomically in Move so no partial deposit occurs, this is still a functional lock (DoS) on the pool's swap capability.

### Likelihood Explanation
Requires the `fee_manager` role to act maliciously or be compromised (single EOA, not a Move-example placeholder for governance/multisig by default). This is a real bug-class match to the external `_MAX_FEE` report: an unrestricted admin setter for a fee parameter with an intended-but-unenforced cap (`MAX_SWAP_FEES_BPS`), directly mirroring the exact pattern reported for `GluexRouter.setMaxFee`.

### Recommendation
Enforce the documented cap in both setters:
```move
public entry fun set_stable_fee(fee_manager: &signer, new_fee_bps: u64) acquires LiquidityPoolConfigs {
    assert!(new_fee_bps <= MAX_SWAP_FEES_BPS, EINVALID_FEE);
    let pool_configs = fee_manager_only_mut_liquidity_pool_configs(fee_manager);
    pool_configs.stable_fee_bps = new_fee_bps;
}

public entry fun set_volatile_fee(fee_manager: &signer, new_fee_bps: u64) acquires LiquidityPoolConfigs {
    assert!(new_fee_bps <= MAX_SWAP_FEES_BPS, EINVALID_FEE);
    let pool_configs = fee_manager_only_mut_liquidity_pool_configs(fee_manager);
    pool_configs.volatile_fee_bps = new_fee_bps;
}
```

### Proof of Concept
1. Deploy/initialize the `swap` package; `fee_manager` defaults to `@deployer` [7](#0-6) .
2. `fee_manager` calls `set_volatile_fee(fee_manager, 10000)` (100%) — succeeds with no bound check [8](#0-7) .
3. A new volatile pool is created via `create(token_1, token_2, false)`, inheriting `swap_fee_bps = 10000` [9](#0-8) .
4. Any user calling `swap` on this pool has `fees_amount = amount_in` computed at line 328, meaning 100% of their input is taken as "fee" and they receive `amount_out = 0` (or the swap effectively steals their entire deposit into `fees_store`), which is only claimable by LPs via `claim_fees` — an unbounded, unprivileged-caller-triggered custody drain enabled purely by the missing bound in the admin setter.

Note: I could not fully verify whether this `move-examples/swap` package is deployed as a production/mainnet contract versus purely an example/reference implementation (its directory is `aptos-move/move-examples/`), which affects whether this qualifies as "mainnet-relevant" per the custody gate. This distinction should be verified before treating the finding as in-scope.
