I have enough context. Let me verify the delegate-withdrawal path quickly.### Title
A delegated position manager can withdraw all of a delegating account's collateral to an arbitrary recipient — ([File: contracts/controller/src/positions/supply.rs])

### Summary
The bZx incident class is "one compromised EOA silently controls assets belonging to many users." XOXNO Lending reproduces that shape at the account level: `withdraw` accepts a caller-supplied `to` recipient, and `require_owner_or_delegate` admits any active, governance-listed position manager that the owner has delegated to. A single compromised or malicious delegate key can therefore call `withdraw(account_id, ..., to = attacker)` for every account that delegated to it and exfiltrate all withdrawable collateral — the same "one key drains many wallets" structure as bZx, without touching the timelock or any protocol admin path.

### Finding Description
`process_withdraw` in `contracts/controller/src/positions/supply.rs:140-157` authenticates the caller, loads the account, and calls `require_owner_or_delegate(env, account_id, caller, &account.owner)`. On success it takes `to: Option<Address>` and pays out to `to.unwrap_or_else(|| caller)` — there is no check that the recipient is the account owner.

`is_owner_or_delegate` in `contracts/controller/src/account.rs:115-127` returns true when `caller` is either the NFT owner or an address that (a) is an active `PositionManager` and (b) appears in `get_delegates(account_id, owner)`. Delegation is granted by the owner via `add_delegate` (`account.rs:229-232`), which only requires that the delegate be an active manager at grant time.

So the authority a delegate exercises is *full withdrawal authority including destination choice*: borrow, withdraw, repay_debt_with_collateral, swap_collateral, swap_debt, multiply, migrate_from_blend and liquidate (Credit mode) all gate on `require_owner_or_delegate`, and `withdraw` in particular lets the delegate name any external recipient. The test at `tests/integration/flows/production.sh` even pins `prod_delegate_withdraw` as an intended delegate action — but nothing in the code constrains `to` to the owner.

### Impact Explanation
Theft of user funds. Every account that delegates to a position manager (the intended pattern for managed/auto-compounding integrations) grants that manager's key the ability to sweep all of its collateral to the manager's own address in a single `withdraw` call per account, limited only by post-withdrawal solvency — which is vacuous once all collateral is pulled. The blast radius is identical in shape to bZx: one key, many victims, no admin privileges required. Severity is bounded by the number of delegating accounts rather than total TVL, so High rather than Critical.

### Likelihood Explanation
- Users must opt in via `add_delegate`, so the victim set is smaller than bZx's "anyone who ever approved the contract." Still, delegation is the designed integration path for third-party position managers, so the exposed population is expected to be non-trivial.
- The manager key is a hot operational key (it must sign calls regularly), making phishing/malware compromise — the exact bZx vector — realistic.
- Governance listing (`set_position_manager`) gates *who can be a delegate at grant time*, but does nothing to limit what an already-delegated manager may do afterward, including redirecting payouts.

### Recommendation
Split delegate authority by risk: when `caller != account.owner`, force the withdrawal recipient to the owner (or to a per-account owner-registered payout address), so a delegate can rebalance but cannot divert funds. Alternatively, store per-delegate permission flags (e.g., can-withdraw, can-borrow) at `add_delegate` time and enforce them in `is_owner_or_delegate` callers. At minimum, document loudly that delegation is equivalent to handing the manager the keys to the collateral.

### Proof of Concept
```rust
// Alice owns account A with 10,000 USDC supplied; MGR is an active position manager.
// Alice delegates: controller.add_delegate(alice, account_id_A, MGR)

// Attacker holding MGR's key (or a malicious manager) then:
ctrl_client.withdraw(
    &mgr_key,                                   // caller = delegate
    &account_id_A,
    &vec![&env, HubPayment { hub_asset: usdc_key, amount: 0 }], // 0 = withdraw all
    &Some(attacker_addr),                        // `to` is fully caller-controlled
);
// process_withdraw: require_owner_or_delegate passes (MGR is delegated),
// recipient = attacker_addr; settle_withdraw pays Alice's collateral to the attacker.
// enforce_post_pool_solvency trivially passes once collateral is zeroed.
```
