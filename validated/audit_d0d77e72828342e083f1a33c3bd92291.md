### Title
Webhook `shop-domain` header is not covered by HMAC verification, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the HMAC signable string exclusively from the raw request body, never from any header, including `shop-domain`/`x-shopify-shop-domain`. `Registry.process` validates only that body-derived HMAC and then hands the unauthenticated `shop` header straight to the app's webhook handler as the tenant identifier. This breaks the identity binding: `hmac_verified_bytes == raw_body` while `tenant_identity_used == request.shop`, i.e. the bytes that are cryptographically verified are not the bytes that determine which shop's data/session the host application acts on.

### Finding Description
`Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 

The `shop` accessor is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is completely outside the signed material: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the body) against the app's `api_secret_key`: [4](#0-3) 

`Registry.process` performs this HMAC check and then constructs `WebhookMetadata` using `request.shop`, which was never authenticated: [5](#0-4) 

`WebhookMetadata.shop` is documented as "The shop domain of the webhook" and the gem's own usage example dispatches background work keyed on this unauthenticated field (`shop_domain: data.shop`): [6](#0-5) [7](#0-6) 

Because a legitimate webhook is only bound to the raw body, any attacker who has ever received a genuine Shopify webhook for their own store (e.g., by installing the app on a store they control) has a body/HMAC pair that is valid for that exact body under the app's secret. Since the header carrying the shop domain is unauthenticated, the attacker can replay that exact body+HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` will still succeed because it only checks the body, and `Registry.process` will dispatch the handler with `shop` set to the victim's domain, causing the host application to act (queue jobs, update records, invalidate sessions, etc.) against the victim tenant using attacker-controlled body content.

### Impact Explanation
This crosses a tenant boundary without needing any privileged credential, matching "Critical - cross-tenant access": the identity used to route/act on a webhook (`shop`) is decoupled from the only field the gem actually authenticates (the body). Any app built on this gem's documented pattern (`data.shop` as the tenant key) inherits this cross-tenant spoofing surface.

### Likelihood Explanation
An attacker needs only the ability to trigger a legitimate webhook for their own shop (trivial — install the target app, perform an action that fires a webhook such as `orders/create`) and then replay the captured raw body/HMAC with a forged `shop-domain` header value pointed at another (target) shop. No secret material or session token is required to spoof the header since it isn't authenticated at all.

### Recommendation
Include the shop domain (and topic/webhook id) as part of the signed material, or independently verify that the `shop-domain` header value matches an expected/registered shop for the api secret in use before trusting `request.shop`/`WebhookMetadata#shop`. At minimum, update documentation to explicitly warn that `data.shop` is unauthenticated and must not be used as a sole tenant key without additional verification (e.g., cross-checking against a known list of shops that have installed the app).

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com`; trigger a webhook (e.g. `orders/create`) and capture the raw POST body and its `x-shopify-hmac-sha256` header — this HMAC is valid because it's computed by Shopify over that exact body with the app's real secret.
2. Replay that captured body and HMAC header unmodified to the app's webhook endpoint, but change `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `@raw_body` only [1](#0-0)  — validation passes since the body is unchanged.
4. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled>, ...)` [8](#0-7) , and the host app (following the gem's documented handler pattern) performs shop-scoped actions against `victim-shop.myshopify.com` using attacker-supplied body data.
