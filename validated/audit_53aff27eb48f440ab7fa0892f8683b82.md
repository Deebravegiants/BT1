### Title
Webhook shop/topic/api-version identity fields are not covered by the HMAC signature, allowing a replayed payload to be attributed to an arbitrary shop - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the `shop-domain`, `topic`, `webhook-id`, and `api-version` HTTP headers verbatim to build the `WebhookMetadata` handed to the app's handler. Those header values are never included in the HMAC-signed content, so the binding "HMAC verified ⇒ (body, shop) pair is authentic" does not hold — only "HMAC verified ⇒ body is authentic" holds.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 
`to_signable_string` returns only `@raw_body`: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature purely over `to_signable_string` (i.e. the raw body) and compares it with the `hmac` header: [3](#0-2) 

`Registry.process` uses this same validation result to authorize trust in the *whole* request, including headers that were never signed: [4](#0-3) 

`request.shop`, `request.topic`, and `request.api_version` are all read straight from HTTP headers with no cryptographic binding to the HMAC-covered body: [5](#0-4) 

The equality that should hold is:
`HMAC-verified(body) == HMAC-verified(body, shop, topic, api_version)`

But the code only proves the left side. Consequently, once an attacker obtains one legitimate `(raw_body, hmac)` pair (trivially achievable by installing the app on their own free-trial development store, an action requiring no privileged access to Shopify or the target app), they can replay that exact body/HMAC to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header (and/or `topic`/`webhook-id`/`api-version` headers) naming a different, victim shop. `Registry.process` will pass the forged `shop` value straight into `WebhookMetadata` for the handler: [6](#0-5) 

Any downstream handler that uses `data.shop` to key merchant data, invalidate a session, trigger uninstall/GDPR-redact logic, or otherwise act on behalf of "the shop that sent this webhook" is acting on an identity value the HMAC never certified.

### Impact Explanation
This breaks the tenant boundary the HMAC is meant to enforce: an unprivileged attacker (anyone who can install the app on any shop, including a free trial store they control) can forge webhook events that are misattributed to a different merchant shop while still passing HMAC validation. Depending on how the host application's webhook handlers use `data.shop` (e.g., to look up/mutate the victim's stored session or trigger the GDPR mandatory redaction/uninstall flows for `shop/redact`, `customers/redact`, `customers/data_request`), this can result in cross-tenant data corruption or forced processing of another merchant's data — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Reaching this requires no leaked credentials, TLS interception, or privileged account — only the ability to (a) receive one legitimate webhook (trivial via a self-owned trial shop) and (b) POST an HTTP request with attacker-chosen headers to the app's already-public webhook endpoint. The gem provides no header/body cross-check to prevent this, so the likelihood of exploitation is bounded only by whether the integrating app relies on `WebhookMetadata#shop`/`#topic` for security-relevant per-shop logic, which is the documented intended use of this data.

### Recommendation
Bind the shop (and ideally topic/api-version) to the HMAC-protected value. Options:
- Include Shopify's `X-Shopify-Shop-Domain` (and other identity headers) in the value that is HMAC-verified, or
- Cross-validate the header-provided `shop` against a `myshopify_domain`/shop identifier embedded in the parsed JSON body before constructing `WebhookMetadata`, or
- Have `Registry.process` require and check that any session-derived shop matches the shop implied by other body content before invoking the handler.

### Proof of Concept
1. Attacker creates a free development/trial store and installs the target app, receiving one legitimate webhook delivery, e.g.:
   - headers: `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over body>`, `x-shopify-topic: orders/create`
   - body: `{"id": 1, ...}`
2. Attacker replays the exact same request to the app's public webhook endpoint but changes only `x-shopify-shop-domain` to `victim-shop.myshopify.com` (and/or the topic header to `shop/redact`).
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers/body (`lib/shopify_api/webhooks/request.rb:45-63`), and `Utils::HmacValidator.validate` succeeds because it only checks the (unchanged) body/HMAC pair (`lib/shopify_api/utils/hmac_validator.rb:26-31`).
4. `Registry.process` proceeds to call the registered handler with `WebhookMetadata` carrying the forged `shop: "victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though Shopify never issued this webhook for that shop.
