**Analysis:** The behavior described is intentional and consistent across the entire storage stack, not a bug.

`FlatStateChanges::from_state_changes` collapsing to `changes.last()` exactly mirrors what `TrieUpdate::finalize` and `Trie::update` do with the same `RawStateChangesWithTrieKey` — both only persist the final value for a key changed multiple times within a chunk. This is documented behavior: "When the same key is written multiple times within a single block, only the final value enters the trie." [1](#0-0)  and implemented identically in `TrieUpdate::finalize` [2](#0-1) . Flat storage is required to always mirror the trie's actual persisted state, so collapsing to the last write is correct, not a metering flaw.

Separately, storage-fee metering (`storage_usage`) is tracked incrementally and correctly through each individual `storage_write` call via `current_storage_usage`, which subtracts the evicted (previous) value length and adds the new value length on every call [3](#0-2) . Because each write reads the actual current value (reflecting all prior writes within the same receipt via `TrieUpdate`'s prospective/committed maps) before overwriting, this is a telescoping sum: for N sequential writes to the same key, the net change in `current_storage_usage` always equals `final_value_len - original_value_len`, regardless of how many intermediate writes occurred. This is exactly the same net effect that ends up persisted in the trie and flat storage (only the final value). So there is no discrepancy between charged storage usage and the actually persisted state.

Gas (compute) cost is charged per `storage_write` call via `storage_write_base`/`storage_write_key_byte`/`storage_write_value_byte` [4](#0-3) , which is intentionally per-operation (to pay for the compute/DB-touch cost of each call) and is independent from the storage-usage/staking-deposit accounting, which is based on net footprint. There is no "double-charge or under-charge of storage staking deposit relative to actual final storage_usage" — the deposit accounting and the persisted flat/trie state are kept consistent by construction, and this is covered by existing unit tests such as `flat_state_changes_creation` in `core/store/src/flat/delta.rs`. [5](#0-4)

    pub fn finalize(self) -> Result<TrieUpdateResult, StorageError> {
        assert!(self.prospective.is_empty(), "Finalize cannot be called with uncommitted changes.");
        let TrieUpdate { trie, committed, contract_storage, .. } = self;
        let mut state_changes = Vec::with_capacity(committed.len());
        let trie_changes = trie.update(
            committed.into_iter().map(|(k, changes_with_trie_key)| {
                let data = changes_with_trie_key
                    .changes
                    .last()
                    .expect("Committed entry should have at least one change")
                    .data
                    .clone();
                state_changes.push(changes_with_trie_key);
                (k, data)
            }),
            AccessOptions::DEFAULT,
        )?;
        let contract_updates = contract_storage.finalize();
        Ok(TrieUpdateResult { trie, trie_changes, state_changes, contract_updates })
    }
