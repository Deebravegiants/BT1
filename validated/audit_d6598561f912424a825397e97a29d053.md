### Title
Webhook shop-domain identity is not bound by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and exposes an HMAC that only signs the raw request body, while the `shop` (from the `X-Shopify-Shop-Domain` header) is never included in the signed material. `Webhooks::Registry.process` trusts this unauthenticated `shop` value and hands it directly to the app's webhook handler, so a genuinely-signed webhook payload for one tenant can be replayed with a different `shop` header to make the app believe the event belongs to a different, victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is not part of that signable string: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC solely against `verifiable_query.to_signable_string`, i.e. the body: [3](#0-2) 

`Registry.process` checks only that HMAC and then forwards the unauthenticated `request.shop` straight into `WebhookMetadata`, which is what app code uses to determine which tenant/session the payload belongs to: [4](#0-3) 

This breaks the identity binding `shop authenticated == shop acted on`: the HMAC authenticates "this body came from an app secret holder for *some* shop," but the `shop` value that the handler actually acts on is a bare, unsigned header value.

### Impact Explanation
Any internet user who can get the app installed on their own (attacker-controlled) shop — a normal, unprivileged action available to anyone who can create a Shopify dev/trial store — will legitimately receive real webhook deliveries from Shopify for that shop, each with a correctly computed HMAC over the body. Because the `shop` header is not covered by the signature, the attacker can replay the exact same body/HMAC pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. The gem will validate the HMAC successfully and hand the app a `WebhookMetadata` claiming the event is for the victim shop, with body content fully controlled by the attacker (subject to whatever webhook topic they choose on their own shop, e.g. `customers/create`, `orders/create`, `app/uninstalled`, etc.). Any app logic keyed off `WebhookMetadata#shop` to write/update per-tenant state is exposed to cross-tenant data injection or spoofed lifecycle events (e.g., forging an `app/uninstalled` or `shop/redact` event against another tenant). This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
No secrets, tokens, or privileged access are required — only the ability to install/create a shop that has the target app installed (or subscribed to at least one webhook topic) and the ability to send arbitrary HTTP requests to the app's public webhook endpoint. Both are available to any unprivileged internet actor. Likelihood is High for apps whose webhook handlers rely on `WebhookMetadata#shop` for tenant scoping without independently re-validating it (which the gem provides no primitive to do, since `shop` is deliberately excluded from the signed payload).

### Recommendation
Bind the `shop` identity into the verified material before it is trusted: either include the shop domain in the HMAC-signable string (a gem-level breaking change requiring coordination with Shopify's webhook signing behavior), or, at minimum, have `Registry.process`/`HmacValidator` cross-check the `shop` header against an independently trusted source (e.g., the shop associated with the webhook subscription id, or an out-of-band verified session) before constructing `WebhookMetadata`, rather than passing the raw unauthenticated header value straight through to handlers.

### Proof of Concept
1. Attacker creates their own Shopify shop `attacker-shop.myshopify.com` and installs the target app; they subscribe (or the app subscribes them) to a webhook topic, e.g. `customers/create`.
2. Shopify delivers a legitimate webhook to the app's endpoint for `attacker-shop.myshopify.com`; attacker captures the raw body `B` and the valid `X-Shopify-Hmac-Sha256` header `H` (H = HMAC-SHA256(secret, B), computed by Shopify).
3. Attacker sends their own POST directly to the app's public webhook endpoint:
   ```
   POST /webhooks HTTP/1.1
   X-Shopify-Topic: customers/create
   X-Shopify-Hmac-Sha256: H
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   X-Shopify-Webhook-Id: <any>
   Content-Type: application/json

   B
   ```
4. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` whose `hmac` and `to_signable_string` (`= B`) pass `HmacValidator.validate` (see `lib/shopify_api/utils/hmac_validator.rb` lines 26-31), because only `B` is checked, not the shop header.
5. `Registry.process` (lib/shopify_api/webhooks/registry.rb lines 188-200) calls the registered handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` even though the payload body actually originated from the attacker's own shop — demonstrating that the shop identity was never cryptographically bound to the verified request.
