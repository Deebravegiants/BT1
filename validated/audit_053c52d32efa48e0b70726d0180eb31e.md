### Title
Webhook shop identity is not covered by the HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw HTTP body, while the `shop` value used by `ShopifyAPI::Webhooks::Registry.process` to build `WebhookMetadata` comes from the unsigned `X-Shopify-Shop-Domain` header. Because the same `api_secret_key` is shared across every shop installing the app, any shop that has legitimately installed the app can capture one authentic `(raw_body, hmac)` pair from Shopify and replay it to the app's webhook endpoint with a forged `shop-domain` header, causing the handler to process the event as if it came from a different, victim shop.

### Finding Description
`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to the received HMAC: [1](#0-0) 

For webhooks, `to_signable_string` returns only `@raw_body`: [2](#0-1) 

`shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is not part of the signed content at all: [3](#0-2) 

`Registry.process` validates only the HMAC of the body, then trusts `request.shop` (and `request.topic`, `request.webhook_id`, `request.api_version`, all header-derived and unsigned) to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

`WebhookMetadata.shop` is documented as "the shop domain of the webhook" and is the field apps are expected to use to know which shop/tenant the event belongs to: [5](#0-4) 

The identity binding that should hold is: `hmac(raw_body, api_secret_key)` valid ⇒ `shop header == shop that Shopify actually sent this exact body for`. Because `shop` is excluded from the signed string, this equality does not hold. Since all shops share one `api_secret_key` for signing (it's the app's client secret, not shop-specific), a shop that has itself installed the app can obtain a genuine `(raw_body, hmac)` pair from a real Shopify-delivered webhook, then resend that exact byte-identical body/HMAC pair to the app's webhook controller while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `Utils::HmacValidator.validate` still succeeds (it never inspects `shop`), and the forged shop value is handed to the app's `WebhookHandler` as trusted data.

### Impact Explanation
This breaks the tenant boundary the HMAC is meant to enforce: an attacker who is merely one (possibly malicious) merchant using the app can make the app process attacker-controlled webhook bodies "as" a different, victim shop, since `WebhookMetadata#shop` is what apps use to route/attribute the processed data (e.g., load the correct shop record, apply mandatory GDPR webhooks like `customers/redact`, or key job queues, as shown in the gem's own docs example `perform_later(topic: data.topic, shop_domain: data.shop, ...)`). This is cross-tenant data confusion caused entirely by a field that is acted upon (`shop`) but not covered by the HMAC that is supposed to authenticate the request.

### Likelihood Explanation
Exploitation requires no secrets beyond what a normal merchant already has: install the app on any shop (even a throwaway one), capture one legitimate webhook `(raw_body, hmac)` pair Shopify sends for that installation, then POST it to the app's public webhook endpoint with an altered `shop-domain` header pointing at any other shop. No `api_secret_key` or access token theft is needed. Because `HmacValidator` and `Webhooks::Request` never bind `shop` into the signed content, this holds for every app using this gem's webhook processing path as documented.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) in the value that gets HMAC-verified, or otherwise cryptographically bind them to the signed body, e.g. by having `Request#to_signable_string` combine the raw body with the shop/topic headers in a canonical form, and updating `HmacValidator`/webhook signature verification accordingly. At minimum, document that `WebhookMetadata#shop` is unauthenticated and must not be trusted for tenant identification without additional verification (e.g., cross-checking against a known/installed shop list).

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` (a shop they control) and triggers a webhook event (e.g. `orders/create`) with body `B`. Shopify signs it: `hmac = HMAC-SHA256(api_secret_key, B)`, delivered with headers `X-Shopify-Hmac-Sha256: hmac`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker captures this exact `(B, hmac)` pair.
3. Attacker POSTs to the app's webhook endpoint directly with body `B`, header `X-Shopify-Hmac-Sha256: hmac` (unchanged), but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` in `lib/shopify_api/utils/hmac_validator.rb` recomputes `HMAC-SHA256(api_secret_key, B)`, matches `hmac`, and returns `true` — because `to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`) never includes the shop header.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) calls the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: B, ...)`, and the app processes attacker-supplied data attributed to a shop the attacker does not control.
