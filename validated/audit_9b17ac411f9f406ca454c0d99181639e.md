### Title
User enumeration via distinct login error messages in local session authentication - (File: `core/sessions/localauth/orm.go`)

### Summary
The local authentication `CreateSession` implementation returns the raw database lookup error when an email address does not exist, while returning generic, hand-crafted messages (`"Invalid email"`, `"Invalid password"`) when the email exists but credentials mismatch. These differing error strings are propagated verbatim to the unauthenticated HTTP client via the `/sessions` endpoint, allowing an unprivileged remote attacker to enumerate valid Chainlink node user accounts.

### Finding Description
`orm.CreateSession` first calls `o.FindUser(ctx, sr.Email)` and, if it fails, returns the raw error directly to the caller: [1](#0-0) 

`FindUser`/`findUser` performs a direct SQL lookup and passes through whatever the driver returns (e.g. `sql.ErrNoRows`, surfaced as `"sql: no rows in result set"`) without normalization: [2](#0-1) 

In contrast, when the email *does* exist but the case-insensitive match or password check fails, the code returns fixed, generic messages: [3](#0-2) 

The HTTP layer (`SessionsController.Create`) forwards this error unmodified as the HTTP 401 body via `jsonAPIError`, which serializes `err.Error()` directly into the JSON response: [4](#0-3) [5](#0-4) 

As a result, an unauthenticated caller of `POST /sessions` receives:
- `"sql: no rows in result set"` (or similar raw DB error) for a **non-existent** email, and
- `"Invalid password"` for an **existing** email with a wrong password.

This is precisely the bug class in CVE-2025-56423 (user enumeration via login error message differences), applied here to the node's own unprivileged login endpoint rather than a peer/operator path. Notably, the LDAP (`ldapauth`) and OIDC (`oidcauth`) authenticators already normalize this via `localLoginFallback`, which uniformly returns `"invalid email"`/`"invalid password"` regardless of whether the account exists — the local-auth ORM path (`core/sessions/localauth/orm.go`) is the outlier that leaks the distinguishing raw error. [6](#0-5) 

### Impact Explanation
An unauthenticated remote attacker hitting the public `/sessions` endpoint can determine whether a given email address corresponds to a valid node operator/API user account, without any credentials or prior access. This does not directly grant access but materially aids credential-stuffing, phishing, and brute-force targeting of the Chainlink node admin API by confirming valid usernames — the login endpoint is confirmed to be internet reachable and rate limited only after failed attempts, not per-account. [7](#0-6) 

### Likelihood Explanation
High likelihood: the endpoint requires no authentication, is a normal part of node operation, and the differing error text is deterministic and trivially observable via a single unauthenticated HTTP request per email guess (only throttled after 5 requests via existing rate limiting, but the responses across different accounts across different rate-limit windows still leak the distinction).

### Recommendation
Normalize `CreateSession` in `core/sessions/localauth/orm.go` to return an opaque, identical error (e.g. `"invalid email or password"`) regardless of whether `FindUser` fails due to a missing account or the password check fails — mirroring the approach already used in `ldapauth.localLoginFallback` and `oidcauth.localLoginFallback`. Ensure `jsonAPIError`/`SessionsController.Create` never leak raw `sql.ErrNoRows` or other backend error text to the client for authentication failures.

### Proof of Concept
1. `POST /sessions` with `{"email":"nonexistent@test.com","password":"x"}` → response body contains a raw DB error such as `"sql: no rows in result set"`.
2. `POST /sessions` with `{"email":"<valid-existing-user>@test.com","password":"wrongpassword"}` → response body contains `"Invalid password"`.
3. Compare response bodies across repeated requests with different candidate emails: the two error strings differ, confirming account existence without valid credentials. [8](#0-7)

// localLoginFallback tests the credentials provided against the 'local' authentication method
// This covers the case of local CLI API calls requiring local login separate from the OIDC server
func (oi *oidcAuthenticator) localLoginFallback(ctx context.Context, sr clsessions.SessionRequest) (clsessions.User, error) {
	var user clsessions.User
	err := oi.ds.GetContext(ctx, &user, SQLSelectUserbyEmail, sr.Email)
	if err != nil {
		return user, err
	}
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		oi.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return user, errors.New("invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		oi.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return user, errors.New("invalid password")
	}

	return user, nil
}

func TestSessions_RateLimited(t *testing.T) {
	t.Parallel()

	ctx := t.Context()
	app := cltest.NewApplicationEVMDisabled(t)
	require.NoError(t, app.Start(ctx))

	router := web.Router(t, app, nil)
	ts := httptest.NewServer(router)
	defer ts.Close()

	client := clhttptest.NewTestLocalOnlyHTTPClient()
	input := `{"email":"brute@force.com", "password": "wrongpassword"}`

	for range 5 {
		request, err := http.NewRequestWithContext(ctx, http.MethodPost, ts.URL+"/sessions", bytes.NewBufferString(input))
		require.NoError(t, err)

		resp, err := client.Do(request)
		require.NoError(t, err)
		assert.Equal(t, http.StatusUnauthorized, resp.StatusCode)
	}

	request, err := http.NewRequestWithContext(ctx, http.MethodPost, ts.URL+"/sessions", bytes.NewBufferString(input))
	require.NoError(t, err)

	resp, err := client.Do(request)
	require.NoError(t, err)
	assert.Equal(t, 429, resp.StatusCode)
}
