### Title
Webhook `shop-domain` and `topic` headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its verifiable signature over the raw request body only, while the shop identity (`shop-domain` header) and event `topic` header are read separately and never bound into the HMAC. `ShopifyAPI::Webhooks::Registry.process` validates only that HMAC-over-body, then dispatches the handler using the unauthenticated `shop` and `topic` header values, breaking the identity binding `hmac(body) == hmac(body)` while trusting `shop_used_by_handler == shop_claimed_in_header` without verification.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop` and `topic` are pulled straight from HTTP headers that are not part of that signable string: [2](#0-1) 

`HmacValidator.validate` verifies the HMAC exactly against `to_signable_string`, i.e., only the body bytes: [3](#0-2) 

`Registry.process` performs this HMAC check and then immediately trusts `request.shop` and `request.topic` to build the dispatched metadata handed to the app's business logic: [4](#0-3) 

Because the signature is computed over the raw body alone, any actor who can obtain one valid `(raw_body, hmac)` pair from Shopify (e.g., by owning any development/trial store subscribed to the target app's webhook endpoint) can replay that exact body+HMAC pair to the target app's public webhook URL while substituting arbitrary `x-shopify-shop-domain` and `x-shopify-topic` header values. `HmacValidator.validate` will still return `true` because it only re-derives the HMAC from `@raw_body`, and `Registry.process` will hand the forged `shop`/`topic` straight to the app's handler as if it were an authentic event for that shop.

This breaks the identity binding that a webhook consumer implicitly relies on: `shop_header == shop_that_actually_produced_and_signed_the_payload`. The HMAC only proves "Shopify's secret produced this body," not "this body belongs to this shop/topic."

### Impact Explanation
This is a cross-tenant authenticity break (Critical): a low-privilege actor (any merchant/developer who has installed the target app on their own store) can forge webhook deliveries that appear to originate from an arbitrary other shop and/or arbitrary topic, while passing the app's own HMAC verification. Downstream app logic that keys off `WebhookMetadata#shop` (e.g., to look up a session/store record, adjust billing, sync inventory, or trigger fulfillment) can be manipulated to act on/against a shop the attacker does not own, since the library provides no protection against this at the `Registry.process` layer.

### Likelihood Explanation
Requires only: (1) attacker has (or creates) any store subscribed to the target app so it receives at least one signed webhook, and (2) the attacker can send arbitrary HTTP requests to the app's public webhook endpoint — no access to `api_secret_key`, no TLS interception, no privileged account on the victim shop needed. This is straightforward to execute with a normal HTTP client.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the value that is HMAC-verified (or require the consuming app to separately authenticate the shop against a known/expected session before trusting `WebhookMetadata#shop`), and document/enforce that `Registry.process` should reject events whose `shop` was not otherwise expected/registered by the app. At minimum, `to_signable_string` should incorporate the headers that downstream code treats as trusted identity, or `Registry.process` should cross-check `request.shop` against an allow-list/expected session store before dispatching.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and triggers any subscribed event (e.g., `orders/create`), causing Shopify to POST a legitimately-signed webhook to the app:
   - Headers: `x-shopify-topic: orders/create`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`
   - Body: `{"id": 1, ...}`
2. Attacker captures `body` and `x-shopify-hmac-sha256` value.
3. Attacker sends a new POST to the same app endpoint with the identical `body` and `x-shopify-hmac-sha256`, but headers changed to:
   - `x-shopify-topic: orders/create` (or any registered topic)
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
4. `ShopifyAPI::Utils::HmacValidator.validate` recomputes the HMAC over `@raw_body` only (`lib/shopify_api/webhooks/request.rb` L35-38, `lib/shopify_api/utils/hmac_validator.rb` L26-31) — it matches, since the body is unchanged.
5. `ShopifyAPI::Webhooks::Registry.process` (L188-200) accepts the request and invokes the app's handler with `shop: "victim-shop.myshopify.com"`, even though that shop never sent this webhook.
