### Title
Attacker-crafted HyperSwap pre-seed reserves trigger an unhandled `Math.mulDiv` overflow revert in `_noFeeSwapInput`, permanently bricking `finalizeGraduation` and freezing curve-raised LT + reserved LP tokens - ([File: packages/contracts/src/Bonding.sol])

### Summary
CVE-2019-15892 is a Varnish Cache DoS where a crafted HTTP/1 request trips an internal assert, forcing a restart. The same bug class — an attacker-crafted, protocol-reachable input tripping an unhandled hard-revert deep in an arithmetic helper — exists in `Bonding._noFeeSwapInput`, which `finalizeGraduation` calls (via `_seedUniswapV2Direct` → `_seedRebalancing` → `_pairRebalance`) with attacker-influenced HyperSwap V2 pair reserves. Unlike Varnish, which auto-restarts with a clean cache, this protocol has no recovery path: a triggered revert here permanently freezes the token in `Lifecycle.Graduating`, trapping the curve-raised LT and the 250M-token `LP_RESERVE` in `Bonding` forever.

### Finding Description
`finalizeGraduation` is permissionless and, per the protocol's own design contract, "Phase 2 must never revert under any pre-seed shape" [1](#0-0) . Any unprivileged address can pre-create the HyperSwap TOKEN/LT pair and seed it with a self-funded `pair.mint` before `finalizeGraduation` runs, which routes into the "mint pre-seed" rebalance branch [2](#0-1) .

That branch calls `_pairRebalance`, which calls `_noFeeSwapInput`:

```
uint256 product = Math.mulDiv(reserveIn * reserveOut, targetN, targetD);
uint256 newIn = Math.sqrt(product);
``` [3](#0-2) 

`reserveIn`/`reserveOut` come straight from the attacker-controlled HyperSwap `pair.getReserves()` (uint112, up to ~5.19e33 each) [4](#0-3) . `targetN`/`targetD` are `tokensForLP`/`ltFromPair` (or their inverse), which are bounded by the curve but can be pushed to a very lopsided ratio (e.g. `tokensForLP` rounds toward the low end while `ltFromPair` is large, or vice versa) [5](#0-4) . The developers explicitly acknowledge that `reserveIn * reserveOut * targetN / targetD` can exceed the uint256 range for "constructed adversarial inputs," and state the resulting behavior is to `revert` rather than truncate [6](#0-5) .

Critically, no caller in the chain (`_pairRebalance` → `_seedRebalancing` → `_seedUniswapV2Direct` → `finalizeGraduation`) wraps this call in a `try/catch` or otherwise falls back on failure — `Math.mulDiv`'s revert propagates all the way out of `finalizeGraduation`, undoing the entire transaction. This directly contradicts the documented "Phase 2 must never revert under any pre-seed shape" brick-resistance invariant [7](#0-6) , and unlike the dust/mint-pre-seed cases that are explicitly handled by falling back to `_seedDirectMint` when the rebalance swap would revert with `INSUFFICIENT_OUTPUT_AMOUNT` [8](#0-7) , there is no equivalent fallback for a `mulDiv` overflow.

Once `_enterGraduating` fires (Phase 1), the token is already stuck in `Lifecycle.Graduating`: trading is frozen, the curve-raised LT and `LP_RESERVE` (250M tokens) already sit in `Bonding` awaiting Phase 2 [9](#0-8) , and there is no cancel/rescue path back to `Curve` or any alternative claim mechanism for creator/traders. If `finalizeGraduation` can be made to always revert for that token (by re-seeding the same pre-seed shape after every attempted call, or simply by the pre-seed persisting on-chain), the token — and every trader's/creator's already-raised LT plus the reserved LP tokens — is permanently frozen.

### Impact Explanation
This is a permanent freezing-of-funds bug reachable by a single unprivileged address: it can trap the LT raised by every buyer on the curve plus the 250M `LP_RESERVE` tokens earmarked for LP for that token, indefinitely, with no recovery mechanism (`LPLock` also has no rescue path, but the funds here never even reach `LPLock` — they never leave `Bonding`). This meets the "permanent freezing of trader, creator or LP funds" bar in the validation rules.

### Likelihood Explanation
Reachable purely through public, permissionless calls: an unrelated wallet can call `HyperSwapFactory.createPair`, `transfer` TOKEN/LT to the pair, and `pair.mint` to bake an extreme reserve ratio, then let (or force, by repeating) `finalizeGraduation` hit the unhandled `Math.mulDiv` revert path that the code's own comments already flag as reachable for "constructed adversarial inputs." The main friction is acquiring enough of the launched TOKEN and/or LT to build a sufficiently skewed/large reserve pair, which varies per token/LT liquidity but is not otherwise permission-gated.

### Recommendation
Wrap the `_pairRebalance` → `_noFeeSwapInput` → `Math.mulDiv` computation in a way that cannot revert `finalizeGraduation`: either bound/clamp the inputs before calling `Math.mulDiv` (e.g., cap `reserveIn`/`reserveOut` scaling or reorder the division to avoid the overflow-prone intermediate), or wrap the rebalance attempt in a low-level call with a `try/catch`/return-bool pattern (mirroring the existing `INSUFFICIENT_OUTPUT_AMOUNT` handling) so any arithmetic failure falls back to `_seedDirectMint`, exactly as the dust/mint-preseed paths already do for other revert conditions.

### Proof of Concept
1. Creator launches a token via `Bonding.launch`/`Zap.createToken`; curve accrues buys until `canGraduate` is true and Phase 1 (`_enterGraduating`) fires, caching `(tokensForLP, ltFromPair)` in `pendingGraduation[token]`.
2. Before anyone calls `finalizeGraduation`, an unrelated attacker wallet calls `HyperSwapFactory.createPair(token, lt)`, then transfers a large, lopsided amount of TOKEN and/or LT into the pair and calls `pair.mint(attacker)`, pushing `getReserves()` toward the extreme end of the uint112 range and/or an extreme ratio relative to the cached `(tokensForLP, ltFromPair)`.
3. Anyone calls `Bonding.finalizeGraduation(token)`. Execution reaches `_seedRebalancing` → `_pairRebalance` → `_noFeeSwapInput`, where `Math.mulDiv(reserveIn * reserveOut, targetN, targetD)` overflows uint256 and reverts.
4. The revert propagates out of `finalizeGraduation`; the transaction fails. Because the pre-seed reserves persist on-chain (or can be recreated identically), every subsequent `finalizeGraduation(token)` call reverts the same way, leaving the token permanently stuck in `Lifecycle.Graduating` with the curve-raised LT and 250M `LP_RESERVE` tokens locked in `Bonding` with no recovery path.

    function _pairRebalance(
        RebalanceParams memory p
    ) internal returns (bool) {
        uint256 s = _noFeeSwapInput(p.reserveIn, p.reserveOut, p.targetN, p.targetD, p.maxSwap);
        if (s == 0) return false;

        // Quote from the pair so the output tracks its live fee; a value
        // derived from a stale fee rate would trip the pair's K-check.
        uint256 expectedOut = IUniswapV2Pair(p.pair).getAmountOut(s, p.tokenIn);
        if (expectedOut == 0) return false;

        IERC20(p.tokenIn).safeTransfer(p.pair, s);
        (uint256 amount0Out, uint256 amount1Out) = p.tokenInIs0 ? (uint256(0), expectedOut) : (expectedOut, uint256(0));
        IUniswapV2Pair(p.pair).swap(amount0Out, amount1Out, address(this), new bytes(0));
        return true;
    }

    function _noFeeSwapInput(
        uint256 reserveIn,
        uint256 reserveOut,
        uint256 targetN,
        uint256 targetD,
        uint256 maxSwap
    ) internal pure returns (uint256) {
        if (reserveIn == 0 || reserveOut == 0 || targetN == 0 || targetD == 0 || maxSwap == 0) {
            return 0;
        }
        uint256 product = Math.mulDiv(reserveIn * reserveOut, targetN, targetD);
        uint256 newIn = Math.sqrt(product);
        if (newIn <= reserveIn) return 0;
        uint256 s = newIn - reserveIn;
        return s > maxSwap ? maxSwap : s;
    }
