Based on the available context, I found a strong structural analog to the SolverVaults rounding bug in Hyperbridge's cross-chain decimal-scaling logic for `pallet-hyper-fungible-token`, though I was unable to fully read `modules/pallets/hyper-fungible-token/src/module.rs` (the receiving-side handler) due to a tool error in the final iteration — I could only confirm it calls `convert_to_balance` via `grep_search`, not view its exact call site with surrounding checks. This should be verified further, but the conversion helper itself and its floor-division design are confirmed.

### Title
Small incoming cross-chain amounts silently round to zero in `convert_to_balance`, burning source tokens with no destination credit - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`pallet-hyper-fungible-token` scales ERC20-precision amounts (18 decimals on EVM, e.g. `HyperFungibleToken`/`BridgeToken`) down to the pallet's local asset precision (e.g. 12 decimals for BRIDGE on nexus) using floor integer division in `convert_to_balance`. Any incoming amount smaller than `10^(erc_decimals - local_decimals)` truncates to zero, exactly mirroring the `SolverVaults.requestWithdraw` bug where `amount / 10 ** (18 - 6)` rounds a small solver-token amount to zero collateral.

### Finding Description
`convert_to_balance` performs unconditional floor division when scaling down precision: [1](#0-0) 

The BRIDGE token's own documentation confirms this exact decimal gap is live in production: EVM side is 18 decimals, nexus is 12 decimals, so the pallet "scales by 10^6 in both directions": [2](#0-1) 

On the EVM send path, a user burns their ERC20 balance and dispatches a POST request to nexus (`onSend`/`send` burns first, dispatches after) — this is the general HFT flow described in the docs: [3](#0-2) 

When that message is relayed and delivered to the pallet, the receiving handler in `module.rs` (confirmed via `grep_search` to call `convert_to_balance`, three call sites) must convert the raw ERC20 `U256` amount back into the pallet's native/local balance type using this same floor-division helper. If the bridged amount, expressed in 18-decimal ERC20 units, is smaller than `10^6` (i.e., less than 0.000001 in whole-token terms — a small but plausible dust amount, especially after fee deductions, rounding elsewhere, or a user simply requesting a tiny top-up), `convert_to_balance` returns `0`. The tokens were already irrevocably burned on the EVM side before the message was ever dispatched, so a `0` result on the pallet side means the user's funds are burned with nothing minted/unlocked in return — a direct structural match to the `amountInCollateralDecimals = 0` bug in the reported `SolverVaults.requestWithdraw` issue.

This is reachable by any unprivileged user who calls `send()`/bridges a small enough amount through the public `HyperFungibleToken`/`BridgeToken`/`WrappedHyperFungibleToken` contracts — no privileged role or malicious relayer is required; the relayer merely delivers the honestly-dispatched message.

### Impact Explanation
Permanent loss of user funds: burned collateral/tokens on the source chain with zero credited on the destination chain, no revert, no error — silent value destruction. This matches the "concrete theft or permanent freezing of funds" bar, functioning as a rounding-based fund loss identical in mechanism (and thus in severity, High) to the original SolverVaults report.

### Likelihood Explanation
Likelihood is moderate-to-high in principle since any user (or automated integrator) submitting a bridge transfer with a raw amount below the precision-loss threshold (`10^(erc_decimals-local_decimals)`, e.g., under 1,000,000 wei-equivalent units for the documented 18→12 decimal BRIDGE conversion) triggers this deterministically. Whether current UI/SDK tooling enforces a minimum transfer amount that prevents this in practice is not established from the code reviewed — the `TypeScript SDK` documentation mentions it "handles ... decimal scaling automatically" but does not confirm a minimum-amount guard exists at the contract or pallet level: [4](#0-3) 

No on-chain minimum-amount check was found in `impls.rs` or the EVM `HyperFungibleToken.sol`/`BridgeToken.sol` send paths reviewed.

### Recommendation
Add an explicit minimum-transferable-amount check on the EVM `send()` path (and/or the pallet's `send` extrinsic) that reverts if the computed destination-side amount after decimal conversion would be zero, analogous to enforcing `amount >= 10 ** (erc_decimals - local_decimals)` before allowing a burn/lock to proceed. This prevents any burn from occurring when it cannot be represented on the receiving side.

### Proof of Concept
Given `erc_decimals = 18` (BridgeToken/HyperFungibleToken on EVM) and `local_decimals = 12` (BRIDGE on nexus), as documented in `BridgeToken.sol`:
1. User calls `send()` with `amount = 500_000` wei (0.0000000000005 tokens, i.e. `< 10^6`).
2. `HyperFungibleToken`/`BridgeToken` burns `500_000` units of the user's ERC20 balance and dispatches a POST request carrying that raw amount.
3. On delivery, the pallet's incoming-message handler calls `convert_to_balance(U256::from(500_000), 18, 12)`, computing `500_000 / 10^6 = 0`.
4. The pallet credits/unlocks `0` to the beneficiary's local balance while the user's `500_000` units are permanently gone from the EVM side — a full loss of the bridged amount with no error surfaced. [1](#0-0) [5](#0-4)

pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
