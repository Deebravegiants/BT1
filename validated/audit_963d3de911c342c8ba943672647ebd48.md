### Title
Webhook shop identity spoofing via cross-tenant HMAC replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The `ShopifyAPI::Webhooks::Request` HMAC signature only covers the raw request body, never the `shop-domain` header. Since the same `api_secret_key` is used to validate webhooks for every shop that has the app installed, any shop owner can capture a legitimately-signed webhook delivered to their own store and replay it to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header naming a victim shop. `Utils::HmacValidator.validate` will accept it because the signature only binds to the body, not to the shop the data is attributed to.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is read directly from the (attacker-controllable) `shopify-shop-domain` / `x-shopify-shop-domain` header and is never part of the signed content: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, then trusts `request.shop` (and `request.topic`) verbatim when constructing the data passed to the app's handler: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` compute `HMAC(api_secret_key, signable_string)` and compare it to the received `hmac`, where `signable_string` is body-only: [4](#0-3) 

Because `api_secret_key` is a single app-wide secret shared across all installed shops (see `Context.setup`), the equality that should hold is:

`shop the HMAC vouches for == shop attributed to the payload by the handler`

but the actual behavior is:

`shop the HMAC vouches for == "whichever body bytes were signed" (no shop binding at all)`

An attacker who has installed the app on their own store receives real, validly-signed webhooks (e.g., `customers/redact`, `shop/redact`, `orders/create`, `app/uninstalled`) for their own store. They can replay that exact signed body to the app's public webhook endpoint while substituting the `shop-domain` header for a victim's `myshopify.com` domain. `Utils::HmacValidator.validate` still returns true (the body/HMAC pair is unchanged and valid), so `Registry.process` invokes the app's handler with `shop: <victim shop>` while the body content is fully attacker-controlled (within the constraints of whatever event they triggered on their own store).

### Impact Explanation
This breaks the tenant boundary between shops without requiring any credential, access token, or `client_secret` belonging to the victim. Depending on which webhook handler the host application registers, this can be used to inject attacker-controlled data attributed to a victim shop — e.g., triggering GDPR mandatory-topic handlers (`customers/redact`, `shop/redact`) against a victim's data, forging `app/uninstalled` to make the host app tear down/revoke a victim shop's session or access token, or injecting fabricated `orders/create`/`customers/create` payloads into the victim shop's records inside the host application. This is a cross-tenant access/impersonation vulnerability caused purely by a missing identity binding in this gem's webhook verification code.

### Likelihood Explanation
Any unprivileged internet user can install the target app on a free/dev Shopify store, capture one legitimate webhook (body + HMAC) delivered to their own store, and replay it against the app's public webhook endpoint with a forged shop-domain header. No secrets, tokens, or privileged access are required — only knowledge of the app's public webhook URL, which is normally public/discoverable.

### Recommendation
Bind the shop (and ideally the topic) into the signed material, or otherwise cryptographically tie the `shop-domain` header to the verified body before trusting it — e.g., require the host application/registry to independently confirm that the shop presented in the header actually corresponds to a session/installation that is expected to receive that topic, or include shop/topic in an app-level replay/idempotency check keyed by `webhook_id` plus a shop allow-list, since the wire-level HMAC (matching Shopify's actual webhook contract) cannot be changed to include the header.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers an event that generates a webhook the app has registered for (e.g. updates a customer to trigger `customers/redact`, or updates an order for `orders/create`).
2. Shopify delivers the webhook to the app's endpoint with headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid HMAC of raw body>`, and the raw JSON body.
3. Attacker replays the exact same raw body and `X-Shopify-Hmac-Sha256` value to the same endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `@raw_body` — the forged shop header does not affect the check, so validation succeeds:
   `lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:12-31`.
5. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker-controlled parsed body>, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the host application to process attacker-supplied data as if it originated from the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
