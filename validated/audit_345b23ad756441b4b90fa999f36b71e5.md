### Title
Accrual overflow permanently freezes an oversized high-utilization market - (File: common/src/rates/index.rs)

### Summary
High severity. Accrual converts scaled debt and supply shares back to RAY values using `i128`; once `borrowed * borrow_index / RAY` exceeds `i128::MAX`, `calculate_supplier_rewards` panics before the borrow-index ceiling can protect the market. [1](#0-0) [2](#0-1)  Every market operation that first syncs interest then repeats the panic, permanently freezing supplier and borrower positions under the deployed code. [3](#0-2) 

### Finding Description
`global_sync` calls `accrue_chunk` for each elapsed chunk, and `accrue_chunk` passes the market's scaled `borrowed`, `supplied`, and index totals into `accrue_step`. [4](#0-3)  The reward calculation computes `borrowed.mul(old_borrow_index)` and `borrowed.mul(new_borrow_index)`, while supply-index growth likewise computes `supplied.mul(old_index)`. [5](#0-4) [1](#0-0)  `Ray::mul` delegates to `mul_div_half_up`, which panics with `MathOverflow` when the mathematically correct result cannot fit in `i128`. [6](#0-5) [7](#0-6) 

This is not prevented by `MAX_BORROW_INDEX_RAY`: that ceiling bounds the index, but not the product of the index and a sufficiently large scaled position. [8](#0-7) [2](#0-1)  The failed call rolls back before `mark_accrued`, so every later call starts from the same stale `last_timestamp` and reaches the same overflowing multiplication. [9](#0-8) 

The reachable path is the permissionless `update_indexes` entrypoint, which forwards the chosen `HubAssetKey` to the pool accrual routine. [10](#0-9) [11](#0-10)  Once the state crosses the representability boundary, `withdraw`, `repay`, liquidation seizure, and `recapitalize` all load an interest-synced market and fail before performing their own accounting. [12](#0-11) [13](#0-12) [14](#0-13) [15](#0-14) 

### Impact Explanation
All suppliers in the affected `(hub_id, asset)` market lose the ability to withdraw any collateral, even when enough token liquidity remains in the pool. [12](#0-11)  Borrowers cannot partially or fully repay, liquidators cannot perform the pool repayment or seizure legs needed to reduce risk, and recapitalization cannot repair the market because it also accrues first. [13](#0-12) [16](#0-15) [17](#0-16)  This is permanent under the deployed implementation, although an owner-controlled contract upgrade could potentially deploy corrected accounting. [18](#0-17) 

### Likelihood Explanation
The attack requires a very large listed market, sustained high utilization, and enough elapsed accrual for the aggregate RAY value to exceed the `i128` domain. [4](#0-3)  A single unprivileged address can create two accounts it owns, supply the debt asset to one and collateral to the other, borrow the debt asset, and then invoke permissionless `update_indexes` until the overflow is encountered. [10](#0-9)  Governance caps do not prevent the precondition by themselves: `max_cap_for_decimals` permits values up to `i128::MAX / 10^(27-d)`, so a one-billion-token, 18-decimal market is well below the admitted cap domain. [19](#0-18)  Exploitability on a particular deployment still depends on that market's actual token supply, configured caps, rate curve, and collateral liquidity.

### Recommendation
Do not treat the index ceiling as a sufficient bound on position or market value. [8](#0-7)  Enforce a scaled-share cap that guarantees `scaled_total * MAX_INDEX / RAY` remains representable for both borrowed and supplied totals, or store aggregate values in a wider representation and redesign settlement so partial operations do not require materializing an unrepresentable total. [5](#0-4) [1](#0-0)  If dynamic index clamping is used, derive the highest index that keeps `borrowed.mul(index)` and `supplied.mul(index)` representable before calling those multiplications; clamping only after the multiplication is too late. [6](#0-5)  Add regression coverage asserting that admitted caps cannot create a market in which `update_indexes`, `withdraw`, `repay`, liquidation, or `recapitalize` becomes permanently uncallable.

    borrower,
    vec![(big18.clone(), 980_000_000 * 10i128.pow(18))],

controller.update_indexes(attacker, vec![big18.clone()]);

controller.withdraw(attacker, supplier, vec![(big18.clone(), 0)], Some(attacker));

controller.recapitalize(attacker, big18, 1);

pub fn max_cap_for_decimals(asset_decimals: u32) -> i128 {
    let Some(exp) = RAY_DECIMALS.checked_sub(asset_decimals) else {
        return 0;
    };
    let upscale = 10i128
        .checked_pow(exp)
        .expect("10^(RAY_DECIMALS - asset_decimals) fits i128 for asset_decimals <= RAY_DECIMALS");
    i128::MAX / upscale
}

    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))

    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
