### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity fields are trusted from unauthenticated headers, not covered by the HMAC - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` field from the raw HTTP header `X-Shopify-Shop-Domain` / `shopify-shop-domain`, while `to_signable_string` (the value the HMAC is computed and verified over) is only the raw request body. `Registry.process` validates the HMAC and then immediately forwards the unauthenticated `shop` header value to the app's webhook handler as trusted tenant identity, with no cross-check that the signed body actually belongs to that shop.

### Finding Description
`Request#hmac` and `Request#to_signable_string` implement `Utils::VerifiableQuery`, and the signable string is exactly `@raw_body`: [3](#0-2)  The `shop` accessor simply reads the `shopify-shop-domain`/`x-shopify-shop-domain` header with no relation to the signed bytes: [4](#0-3) 

`Registry.process` validates only `Utils::HmacValidator.validate(request)` — i.e., that `HMAC(secret, raw_body)` matches — then constructs `WebhookMetadata` directly from `request.shop` (plus `topic`, `api_version`, `webhook_id`, all likewise header-derived and unsigned) and calls the app's handler with it: [5](#0-4) 

`HmacValidator.validate`/`validate_signature` only ever operate on `verifiable_query.to_signable_string`, i.e. the body — the shop header plays no role in the signature computation or comparison: [6](#0-5) 

This is exactly the "field acted on but not covered by the HMAC" identity-binding break: the equality the code implicitly assumes is `shop_header == shop_that_produced(raw_body)`, but the HMAC only proves `raw_body` was signed with the app's shared secret — it says nothing about which shop the body came from. Because `api_secret_key` is one shared value across every shop that installs the app, any shop that installs the app (an ordinary, unprivileged Shopify merchant/attacker) can capture a genuine webhook delivery it legitimately receives (valid body + valid HMAC for that body), then replay that exact body+HMAC to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop's domain. The HMAC check still passes (it only checks the body), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop.

The gem's own docs and example handler reinforce that `data.shop` is meant to be treated as the trusted per-tenant key (e.g., used to route/enqueue per-shop jobs): [7](#0-6) 

### Impact Explanation
An attacker who is a legitimate (if unprivileged) installer of the target app — i.e., any normal internet user who can install a Shopify app on their own store — can forge the shop attribution of a webhook delivery to another tenant. Since host applications are told by this gem's docs to key their per-shop state off `data.shop`, this enables cross-tenant data injection/confusion: e.g., an attacker's own `orders/create` or `app/uninstalled` payload can be attributed to a victim shop, corrupting or spoofing that victim's data in the host app. This matches the Critical "cross-tenant access" impact category, since the tenant boundary (`shop`) is not actually authenticated by the HMAC that is meant to authenticate the whole webhook delivery.

### Likelihood Explanation
Likelihood is high for any attacker willing to install the target Shopify app on their own store (a normal, unprivileged action) — a real, publicly documented capability of Shopify's App Store model. Capturing a genuine body+HMAC pair from their own store's webhook deliveries requires no special access, and replaying it with a different shop header against the app's public webhook endpoint requires only basic HTTP tooling.

### Recommendation
Bind the shop identity into the signed payload, or otherwise verify it out-of-band before trusting it:
- Require host apps (and this gem) to validate `request.shop` against the shop associated with the specific webhook subscription/session for that delivery, not merely trust the header.
- Where possible, cross-check the `shop` header against known/registered shops for that app installation before dispatching to the handler, rejecting deliveries whose header shop does not match a shop with an active subscription for that topic/webhook id.
- Consider including `shop` in the value that `to_signable_string` returns (if Shopify's HMAC scheme is changed to support it) or otherwise verify shop-webhook_id pairing server-side.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and receives a legitimate `orders/create` webhook: body `B`, valid header `X-Shopify-Hmac-Sha256: HMAC(secret, B)`, header `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker replays an HTTP POST to the app's public webhook endpoint with the same body `B` and same valid HMAC header, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(secret, B)` against the (still valid) provided HMAC [8](#0-7) .
4. `Registry.process` calls the app's handler with `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body:, ...)` [9](#0-8) , and the host app (following the gem's documented pattern) processes/stores this data as if it genuinely belongs to `victim.myshopify.com`.
