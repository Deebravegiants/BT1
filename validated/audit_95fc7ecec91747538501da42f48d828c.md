Audit Report

## Title
CORS wildcard-origin check in Gateway HTTP server uses unanchored suffix match, allowing spoofed subdomains to bypass allowlist - (File: core/services/gateway/network/httpserver.go)

## Summary
`isAllowedOrigin` implements wildcard-origin matching for the Gateway HTTP server's CORS allowlist. For entries like `*.example.com`, it strips the `*.` prefix and compares the request's `Origin` host using `strings.HasSuffix` without requiring a `.` boundary before the matched suffix, so any origin host that merely ends with the configured suffix (e.g., `evilexample.com`) passes the check even though it is not a genuine subdomain.

## Finding Description
`isAllowedOrigin` parses the incoming `Origin` header and each configured allowed origin into scheme/host/port via `splitURL`, then for wildcard entries performs: `allowedHost = allowedHost[2:]` (stripping `*.` from e.g. `*.example.com`, leaving `example.com`), followed by `strings.HasSuffix(originHost, allowedHost)` [1](#0-0) . This returns `true` for any `originHost` ending in that literal string — including `evilexample.com` or `notexample.com` — not just genuine subdomains like `sub.example.com`. Scheme and port are correctly compared for exact equality earlier in the function [2](#0-1) , but the host wildcard branch omits an equivalent host-label boundary check (e.g., requiring `originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost)`).

## Impact Explanation
This function directly governs `Access-Control-Allow-Origin` responses in `handleRequest`, which echoes back the raw `Origin` header value and sets permissive CORS headers when `isAllowedOrigin` returns true [3](#0-2) . Since the Gateway HTTP server is internet-facing and reachable by unauthenticated browser clients, an attacker controlling a domain that ends with the configured wildcard suffix (without a preceding dot) can have the server grant it cross-origin trust it was never intended to receive, enabling browser-based cross-origin requests from an unintended domain against the Gateway.

## Likelihood Explanation
This requires the operator to configure a wildcard entry (e.g., `*.example.com`) in `CORSAllowedOrigins`, which is a documented/expected pattern for this server, combined with an attacker registering and serving content from any domain string ending in that suffix (e.g. `evilexample.com`). Since domain registration is unprivileged and cheap, and no operator or elevated access is needed by the attacker (only ordinary domain registration and hosting a webpage), this is realistically exploitable whenever wildcard CORS is configured.

## Recommendation
Anchor the suffix match to the host-label boundary: after stripping `*.`, require either an exact match or that the origin host ends with `"." + allowedHost`:
```go
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost) {
        return true
    }
}
```

## Proof of Concept
1. Configure the Gateway HTTP server with `CORSEnabled = true` and `CORSAllowedOrigins = ["https://*.example.com"]`.
2. Attacker serves a page from `https://evilexample.com` and sends a cross-origin request to the Gateway with header `Origin: https://evilexample.com`.
3. In `isAllowedOrigin`: `originHost = "evilexample.com"`, `allowedHost` after stripping `*.` = `"example.com"`; `strings.HasSuffix("evilexample.com", "example.com")` evaluates `true`, so the function returns `true` [4](#0-3) .
4. `handleRequest` sets `Access-Control-Allow-Origin: https://evilexample.com`, permitting cross-origin access despite `evilexample.com` not being a subdomain of `example.com` [5](#0-4) . This can be verified with a Go unit test calling `isAllowedOrigin("https://evilexample.com")` against a config containing `*.example.com` and asserting it returns `true`.
