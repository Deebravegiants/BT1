Unverified "overpayment" refund in `recapitalize`/`repay` pays out of pool custody — attacker can drain the pool's token balance - ([File: contracts/pool/src/ops/recapitalize.rs](contracts/pool/src/ops/recapitalize.rs))

### Summary
The external report describes a contract that refunds ether based on a caller-supplied amount without checking that the corresponding value actually arrived. XOXNO Lending's pool has the same shape: `recapitalize` and `repay` compute a refund as `declared_amount - applied` and unconditionally `transfer_out` that refund from the pool's real token custody, without verifying that `declared_amount` was ever transferred in and without debiting `cash` or passing reserve checks. The codebase's own test `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` proves a repay with **zero inbound tokens and zero debt** refunds the entire declared amount out of custody.

### Finding Description
In `contracts/pool/src/ops/recapitalize.rs`, `accounting` computes `applied = amount.min(backing_shortfall)` and `refund = amount - applied`, then `apply` calls `cache.transfer_out(&payer, refund)` — moving real tokens out of the pool — purely on the caller-declared `amount`, with no check that `amount` tokens were actually deposited [1](#0-0) [2](#0-1) . The identical pattern exists in `contracts/pool/src/ops/repay.rs`, where `overpayment = amount - net_repay` is refunded to `payer` regardless of inbound funding [3](#0-2) [4](#0-3) . The test at `contracts/pool/tests/flows.rs` documents that neither refund "debits `cash` or passes `require_reserves`," and that a repay against a market with no debt makes the full declared amount an overpayment refunded "out of real custody with the book untouched" [5](#0-4) . The pool trusts that the controller transferred exactly `amount` before invoking the op; the refund itself is never tied to a measured balance delta, so any path where the controller invokes these ops without first pulling the full declared amount into the pool (e.g., `repay_prefunded_position` resolving a debt "from funds already received by the pool," or a recapitalize where the backing shortfall is 0 so the entire declared amount becomes `refund`) pays the difference out of depositors' funds [6](#0-5) .

### Impact Explanation
If any unprivileged-reachable controller entrypoint (`repay`, `recapitalize`, liquidation, strategy repay) reaches the pool's refund leg with a declared `amount` exceeding the tokens actually transferred in, the attacker receives the difference directly from the pool's token balance — i.e., theft of supplier funds. Even absent a missing-transfer path, the design guarantees that any tokens that ever become stranded in the pool contract (direct `token.transfer` to the pool address, fee-on-transfer shortfalls, rounding dust) are claimable by anyone who can get the controller to pass a matching declared amount, mirroring the reported "steal all ether stuck in the contract" class.

### Likelihood Explanation
Pool mutators are `#[only_owner]`-gated to the controller [7](#0-6) , so the attack requires a controller path that forwards a user-declared `amount` without a verified full inbound transfer — I could not fully confirm within the available iterations whether the controller prefunds every recapitalize/repay call with a measured transfer of exactly `amount`. If it does, the residual issue is drainage of any stray tokens sent directly to the pool (unprivileged via `token.transfer`). The codebase's own regression tests assert the unfunded-refund-drains-custody property, indicating the refund trusts the declared amount rather than measured receipt [8](#0-7) .

### Recommendation
Make refunds self-accounting: before paying `refund`/`overpayment`, either (a) measure the pool's actual token-balance increase during the leg and cap the refund at `max(0, received - credited_to_cash)`, or (b) require the controller to pass a `received_amount` obtained via `payments::transfer_amount_measured` (as already done in `repay_debt_from_controller` [9](#0-8) ) and assert `refund <= received_amount - applied`. A pool-side `require_reserves`-style invariant ("token balance ≥ cash book after refund") would catch all unfunded-refund paths.

### Proof of Concept
1. Attacker (unprivileged) calls a controller entrypoint that reaches `pool.repay`/`pool.recapitalize` for a market with zero outstanding debt or zero backing shortfall, declaring `amount = B` where `B` is the pool's token balance (e.g., `recapitalize(hub_asset, amount = B)` when `backing_shortfall == 0`, or `repay` on a position with no debt).
2. Pool's `accounting` computes `applied = 0`, `refund = B` (`recapitalize.rs:52-55`) or `overpayment = B` (`repay.rs:44`).
3. `cache.transfer_out(attacker, B)` moves the pool's entire token custody to the attacker while `cash` accounting is untouched (`flows.rs:3578-3611` demonstrates the drain).
4. Suppliers can no longer withdraw — the pool's books still show cash that no longer exists.

fn test_unfunded_repay_overpayment_refund_also_pays_out_of_custody() {
    let t = TestSetup::new();
    let token = token::Client::new(&t.env, &t.asset);
    let payer = Address::generate(&t.env);

    let custody_before = token.balance(&t.pool);
    let before = t.state_snapshot();
    assert_eq!(
        before.cash, custody_before,
        "fixture guard: book and custody must start in sync"

    // Nothing transferred in, no debt to retire: the whole amount is "excess".

        .client()
        .repay(&payer, &t.ract(0, custody_before))
        .get_unchecked(0)
        .actual_amount;
    assert_eq!(credited, 0, "no debt was retired, so nothing is credited");
    assert_unfunded_refund_drained_custody(&t, &payer, custody_before, &before);
}
