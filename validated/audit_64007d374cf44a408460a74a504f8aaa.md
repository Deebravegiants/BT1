### Title
Webhook Shop/Topic/Webhook-ID Identity Is Not Covered by the HMAC, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`), the dispatch key (`topic`), and the idempotency key (`webhook_id`) purely from unauthenticated HTTP headers, while the HMAC signature that `Utils::HmacValidator` verifies only covers the raw request body. This breaks the binding `shop authenticated == shop acted on`, letting an attacker who controls their own Shopify shop replay a validly-signed webhook body under a different `shop-domain`/`topic` header and have the app process it as if it came from a victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are read straight from HTTP headers, which are never mixed into the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` verifies `HMAC(secret, verifiable_query.to_signable_string) == verifiable_query.hmac`, i.e. only the body's authenticity, not the headers': [3](#0-2) 

`Registry.process` trusts this HMAC check and then dispatches solely using the unauthenticated header-derived `topic`/`shop`, handing them to the app's handler as the tenant/event identity: [4](#0-3) 

The equality that should hold is: `shop bound by HMAC == shop delivered to the handler`. In this implementation, the HMAC binds only the raw body bytes; it says nothing about which shop, topic, or webhook id those bytes belong to. Because every shop installing the same app shares the app's single `api_secret_key`, any legitimately-signed body (which an attacker can freely obtain by triggering a real webhook from their own, attacker-controlled install of the app) remains validly signed no matter which `shop-domain`/`topic`/`webhook-id` header is attached to it.

### Impact Explanation
This is a cross-tenant identity-binding break (Critical): an attacker who has installed the app on their own store (a normal, unprivileged action) can capture the raw body + `X-Shopify-Hmac-Sha256` value of a real webhook their own store triggers, then resend that exact `(body, hmac)` pair to the app's public webhook endpoint while substituting a victim shop's domain (and/or a different topic) in the headers. `Registry.process` will validate the HMAC successfully and route the body into the handler with `shop: <victim>`, so any per-shop side effects (data writes, redaction handling, order/customer records, `shop/redact`-style logic, etc.) are attributed to the victim tenant instead of the attacker. This can corrupt another merchant's data or trigger tenant-scoped business logic using attacker-supplied content.

### Likelihood Explanation
Likelihood is realistic: webhook endpoints are internet-reachable by design, no access token or `client_secret` is needed by the attacker (only a free/self-installed test shop, which is normal app usage), and capturing one's own outbound webhook body+HMAC requires nothing more than operating a proxy/logger in front of one's own endpoint. No cryptographic secret needs to be recovered — the legitimate signature is simply replayed under attacker-chosen headers.

### Recommendation
Bind the tenant/topic identity into the signed material (or otherwise cryptographically bind headers to the body) before trusting `request.shop`/`request.topic`/`request.webhook_id` for dispatch, e.g., have `to_signable_string` incorporate the header values actually relied upon, or independently verify `shop`/`topic` against server-side registration state (e.g., confirm the shop has an active session/registration for that topic) before invoking the handler, rather than trusting header values whose authenticity was never checked by the HMAC.

### Proof of Concept
1. Attacker installs the target app on their own Shopify dev/trial store (`attacker.myshopify.com`) and registers/receives a webhook, e.g. `orders/create`.
2. Attacker places a logging proxy in front of their webhook endpoint (or otherwise intercepts the POST) and records the raw body `B` and header `X-Shopify-Hmac-Sha256: H` that Shopify legitimately computed with the shared `api_secret_key`.
3. Attacker resends an HTTP POST to the same app endpoint with:
   - body = `B` (unchanged)
   - header `X-Shopify-Hmac-Sha256` = `H` (unchanged)
   - header `X-Shopify-Shop-Domain` = `victim-shop.myshopify.com` (a real merchant using the same app)
   - header `X-Shopify-Topic` unchanged or altered to another registered topic
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb:12-31` recomputes `HMAC(secret, B)` and it matches `H`, so validation passes.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb:188-200` looks up the handler for the (unauthenticated) topic and calls it with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body `B`, causing the app to process attacker data as belonging to the victim tenant.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
