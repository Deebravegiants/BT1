### Title
Webhook `shop-domain` header is trusted for tenant identification without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then hands the caller-supplied `shop-domain` header straight to the handler as the tenant identifier, without that header ever being part of the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop` is read directly and unauthenticated from the `x-shopify-shop-domain`/`shopify-shop-domain` header [2](#0-1) . `Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, which computes `OpenSSL::HMAC.hexdigest` over `to_signable_string` (i.e. the body only) and compares it against the `hmac` header [3](#0-2) . Once that check passes, `Registry.process` builds `WebhookMetadata` using `shop: request.shop` — the unauthenticated header value — and forwards it to the app's handler [4](#0-3) .

The identity binding that should hold is: `shop` used by the handler == `shop` the HMAC actually authenticates. Because the HMAC only covers `@raw_body`, that equality does not hold — `request.shop` is fully attacker-controllable independent of the signature. A user in possession of *any* validly-signed webhook body for the configured `client_secret` (e.g. one legitimately delivered to their own shop's endpoint, since anyone can install the app on a shop they control and receive genuine webhooks with a valid HMAC) can replay that request while substituting the `shop-domain` header for an arbitrary victim shop domain. `HmacValidator.validate` still returns `true` because it never inspects the header, and `WebhookMetadata#shop` will contain the attacker-chosen victim domain [5](#0-4) .

### Impact Explanation
Any host application that trusts `WebhookMetadata#shop` to select which merchant/tenant record to update, or to look up/derive the session used for follow-up Admin API calls (e.g. via `Utils::SessionUtils.offline_session_id(shop)` style keys) [6](#0-5) , can be driven to associate attacker-supplied webhook data with a victim shop's tenant record — a cross-tenant data confusion primitive achieved without ever possessing the victim's credentials or the app's `client_secret`. This matches the "Critical - cross-tenant access" impact tier since the trust boundary broken is exactly the `shop` field never being cryptographically bound to the signature that is supposed to authenticate the message's origin and content.

### Likelihood Explanation
Exploitation only requires the ability to send an HTTP request to the app's public webhook endpoint with a body/HMAC pair that is valid for the shared `client_secret` — obtainable by any user who installs the app on a shop they control (Shopify will deliver genuinely signed webhooks to that install) and then replays the captured body/HMAC pair against the endpoint with a forged `shop-domain` header. No access token, `api_secret_key`, or privileged account is required.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the HMAC-signed material, or otherwise cryptographically bind the `shop-domain` header to the signature Shopify computes, so `Utils::HmacValidator.validate` fails if the header is altered relative to what was actually signed. Short of that, document that host applications must independently cross-check `WebhookMetadata#shop` against an out-of-band trusted source before using it as a tenant key, since this gem currently provides no such guarantee.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; Shopify delivers a webhook (e.g. `orders/create`) with a valid `x-shopify-hmac-sha256` computed over the JSON body using the app's `client_secret`.
2. Capture the raw body and `hmac-sha256` header from that delivery.
3. Replay the exact same body and HMAC header to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` in `HmacValidator#validate_signature` [3](#0-2)  succeeds because it only checks the body against the HMAC.
5. `Registry.process` calls the registered handler with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)` [7](#0-6) , causing any app logic keyed on `data.shop` to act as though the (attacker-controlled) payload originated from the victim shop.
