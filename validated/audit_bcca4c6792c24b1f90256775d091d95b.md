## Analysis

The ERC865 bug class here is: **a value is trusted/acted upon by the application while a different, incomplete value is what's actually covered by the integrity check** — the 4-byte selector didn't match the full function signature it was supposedly derived from. The closest analog in this Ruby gem is in **Shopify webhook processing**, where the HMAC only covers the raw request body, while the `shop`, `topic`, `webhook-id`, and `api-version` fields — which the library treats as authenticated identity data and hands to the app's webhook handler — come from unauthenticated HTTP headers.

### Root cause

`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from headers with **no cryptographic binding**: [2](#0-1) 

`Registry.process` validates the HMAC against the body only, then immediately trusts the header-derived `shop`/`topic`/`webhook_id` to dispatch the event to the app's handler: [3](#0-2) 

`HmacValidator.validate` simply confirms `verifiable_query.to_signable_string` (the body) matches the HMAC — it says nothing about the headers: [4](#0-3) 

### Broken identity binding (as equality)

`HMAC-verified(raw_body)` ≠ `shop/topic/webhook_id acted upon by handler`

Concretely: **shop authenticated by the HMAC (none) ≠ shop trusted and passed to the handler (`request.shop`, from an arbitrary header)**.

### Exploitability

An unprivileged internet user can:
1. Create their own (free/dev) Shopify store and install the target app, or otherwise legitimately trigger any webhook delivery for a topic the app subscribes to. Shopify will send a correctly-signed `(raw_body, x-shopify-hmac-sha256)` pair to the app's public webhook endpoint.
2. Capture that `raw_body` + valid `hmac` value.
3. Replay the identical `raw_body` and `hmac` to the same public webhook endpoint, but forge `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) to name a *different, victim* shop.
4. `Utils::HmacValidator.validate` still succeeds — it never looked at the headers — so `Registry.process` calls the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: forged_topic, body: attacker_controlled_payload, ...)`.

The receiving application (using this gem's documented API, exactly as shown in `docs/usage/webhooks.md`) has no way to detect the forgery, since the gem itself asserts these fields are authenticated by virtue of having passed `HmacValidator.validate`. This is a cross-tenant spoofing primitive: attacker-controlled webhook data can be injected and attributed to an arbitrary shop domain the attacker does not own or control, with no `api_secret_key`, access token, or privileged access required beyond the trivial step of installing the app on a store they legitimately control.

### Title
Webhook shop/topic identity spoofing via HMAC that only covers the request body, not the `shop-domain`/`topic`/`webhook-id` headers - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` binds the HMAC to the raw body only. The `shop`, `topic`, `webhook_id`, and `api_version` values that `Registry.process` passes on, unverified, to the app's webhook handler are read directly from client-supplied headers that are entirely outside the HMAC's coverage.

### Finding Description
`Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) gates dispatch solely on `Utils::HmacValidator.validate(request)`, which recomputes an HMAC over `request.to_signable_string` — the raw body (`lib/shopify_api/webhooks/request.rb:35-38`) — and compares it to `request.hmac`, itself parsed from a header (`lib/shopify_api/webhooks/request.rb:10-13`). The `shop`, `topic`, and `webhook_id` accessors (`lib/shopify_api/webhooks/request.rb:15-33`) read straight from other headers that are never mixed into the signable string. Consequently, once an attacker holds any single valid `(raw_body, hmac)` pair — trivially obtainable by having the app installed on a store they control — they can resend that exact body with an arbitrary `x-shopify-shop-domain`/`x-shopify-topic`/`x-shopify-webhook-id` and the HMAC check still passes.

### Impact Explanation
This breaks the tenant identity binding the whole webhook-authentication mechanism is supposed to provide: "the shop this event happened to" is asserted by the gem to be authentic, but it is not actually covered by any credential. A downstream app relying on `WebhookMetadata#shop` (as the gem's own documentation instructs) to key writes, billing, entitlements, or notification state per-tenant can be made to apply attacker-supplied data to an arbitrary victim shop, i.e., cross-tenant data injection/corruption.

### Likelihood Explanation
Requires no `api_secret_key`, access token, or leaked credential — only the ability to install the app once on any (even free/dev) store to harvest one valid signed body, and the ability to POST to the app's public webhook endpoint with modified headers, which is what any unprivileged internet user attacking a live install could do.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC signable string (or otherwise cryptographically bind them, e.g. re-deriving them only from a signed payload), so that spoofing any of these fields invalidates the signature, mirroring how `Auth::Oauth::AuthQuery#to_signable_string` already includes `code`, `host`, `shop`, `state`, and `timestamp` together.

### Proof of Concept
```ruby
# Step 1: attacker installs app on their own store "attacker-shop.myshopify.com"
# and captures a real webhook delivery, e.g. for topic "customers/create":
raw_body = '{"id":1,"email":"attacker@example.com"}'
valid_hmac = "<hmac value Shopify actually sent for the above body>"

# Step 2: attacker replays it against the victim app's public webhook endpoint,
# forging the shop-domain and topic headers:
headers = {
  "x-shopify-topic" => "orders/create",              # forged
  "x-shopify-hmac-sha256" => valid_hmac,              # untouched, still valid because body is unchanged
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged
  "x-shopify-webhook-id" => "forged-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate passes (body unchanged); handler is invoked with
#    shop: "victim-shop.myshopify.com", topic: "orders/create", body: attacker's data
```
