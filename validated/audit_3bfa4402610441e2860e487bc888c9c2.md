### Title
Front-runnable AMM pool initialization allows attackers to hijack pool creation and set a malicious initial price - ([File: program/src/processor.rs])

### Summary
`Processor::process_initialize2` (handling `AmmInstruction::Initialize2`) derives every pool-related account (the AMM state account, LP mint, coin/pc vaults, target-orders account) deterministically from the `market_info` account key via `get_associated_address_and_bump_seed`, and lets the caller freely choose `init_coin_amount`/`init_pc_amount` to set the pool's initial price. Because the instruction can be submitted by any signer and the resulting addresses are 100% predictable from the (public) OpenBook market key, this is directly analogous to the `delegateBtc` front-running bug class: an attacker who observes a pending "create pool for market M" transaction in the mempool can submit their own `Initialize2` for the same market first, claiming the deterministic pool address and setting an arbitrary, attacker-favorable coin/pc ratio before the legitimate creator's transaction lands.

### Finding Description
`process_initialize2` computes the pool's associated accounts purely from `market_info.key` and static seeds: [1](#0-0) 

These derived addresses (`AMM_ASSOCIATED_SEED`, `LP_MINT_ASSOCIATED_SEED`, `COIN_VAULT_ASSOCIATED_SEED`, `PC_VAULT_ASSOCIATED_SEED`, `TARGET_ASSOCIATED_SEED`) are used to create the pool's AMM account, LP mint, and vaults: [2](#0-1) 

The only signer requirement is on `user_wallet_info` — there is no check restricting who may call `Initialize2` for a given market, and the initial price is fully attacker-controlled via `init.init_coin_amount`/`init.init_pc_amount`: [3](#0-2) 

The initial LP liquidity and price ratio are derived directly from whatever amounts the caller supplies: [4](#0-3) 

If a second `Initialize2` targets the same market after the accounts already exist, account creation fails with `RepeatCreateAmm`/`AlreadyInUse`: [5](#0-4) [6](#0-5) 

Since the market account key is public (it's the OpenBook/Serum market being paired), and the resulting AMM/vault/LP-mint addresses are fully determined by that key and static seeds, any unprivileged party watching the mempool can front-run a legitimate creator's `Initialize2` for the same market with a higher priority fee, claiming the deterministic pool address first and choosing an arbitrary `init_coin_amount`/`init_pc_amount` ratio.

### Impact Explanation
The legitimate creator's `Initialize2` transaction fails after already paying the SOL `create_pool_fee` transfer (invoked before the account-creation checks) and any transaction fees, causing direct fund loss/griefing: [7](#0-6) 

More severely, the attacker — not the intended creator — sets the pool's initial coin/pc ratio, i.e., the starting market price, using minimal capital of their own choosing. All subsequent `Deposit` operations add liquidity proportionally to whatever ratio the attacker set, and swaps are priced against it, so any legitimate depositor or trader interacting with what they believe is "their" pool is instead trading against a price set unilaterally and maliciously by the attacker, and the attacker can immediately arbitrage against the skewed price they created. This is a concrete unauthorized-privileged-effect / fund-theft vector matching the CoreDAO "front-running due to no uniqueness/ownership check" bug class.

### Likelihood Explanation
Any pool creation is observable in the mempool prior to confirmation. Because the target accounts are fully deterministic from the market key and program ID (no randomness, no creator-bound seed), an attacker only needs to detect an `Initialize2` transaction referencing a market of interest and resubmit their own version with a higher priority fee — a standard, low-cost front-running technique requiring no special privileges, matching exactly the PoC structure in the referenced report.

### Recommendation
Bind the derived pool/vault/lp-mint addresses (or at minimum the AMM account) to something the legitimate creator controls exclusively, e.g., include the creator's pubkey (or a creator-supplied nonce bound to a signature) in the seed derivation, or require the AMM account to be pre-created/owned by the intended creator before `Initialize2` can populate it, so that an unrelated third party cannot claim the deterministic address for a given market. Additionally, defer/refund the `create_pool_fee` charge until after all uniqueness/ownership checks succeed so a front-run does not cost the legitimate user funds.

### Proof of Concept
1. Legitimate user Alice builds and broadcasts an `Initialize2` instruction for `market M` with `init_coin_amount = 1_000_000`, `init_pc_amount = 1_000_000` (1:1 price), computing the deterministic AMM/vault/LP addresses via `get_associated_address_and_bump_seed(program_id, &M, seed, program_id)`.
2. Attacker Bob observes Alice's pending transaction in the mempool, and independently computes the same deterministic addresses for market `M` using the public seeds in `program/src/processor.rs`.
3. Bob submits his own `Initialize2` for market `M` with a higher priority fee and a skewed ratio, e.g. `init_coin_amount = 1_000_000`, `init_pc_amount = 1` (extreme price skew), funded from his own token accounts.
4. Bob's transaction lands first: `generate_amm_associated_account`/`generate_amm_associated_spl_token`/`generate_amm_associated_spl_mint` succeed for Bob, initializing the pool at the deterministic address for market `M` with his chosen skewed price, per `process_initialize2` (`program/src/processor.rs:748-930`).
5. Alice's transaction now fails at the account-creation stage (`RepeatCreateAmm`, `program/src/processor.rs:378-381`) or at `AlreadyInUse` (`program/src/processor.rs:844-847`), after she has already paid the `create_pool_fee` SOL transfer (`program/src/processor.rs:712-740`).
6. Bob immediately swaps against the mispriced pool he created, extracting value, while Alice's intended pool parameters and fee payment are lost.
