## Title
Escrow release/refund and dust-sweep in the Tron `IntentGatewayV2` use raw low-level ERC20 `transfer` calls that ignore the returned boolean, enabling silent transfer failures to be treated as success — permanently freezing escrowed user/solver funds - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron deployment of the Intent Gateway (`evm/tron/contracts/apps/IntentGatewayV2.sol`) imports and declares `using SafeERC20 for IERC20;` [1](#0-0)  and correctly uses `safeTransferFrom` when pulling tokens into escrow, but the critical fund-release paths — `withdraw()` (escrow redemption/refund) and the `SweepDust` handler — bypass `SafeERC20` entirely and instead perform raw low-level `.call()` invocations of `IERC20.transfer`, checking only that the call didn't revert (`success`) and never inspecting the returned boolean.

A raw `address.call(...)` only reverts (`success == false`) if the callee itself reverts or the call target has no code. For ERC20 tokens that signal failure by returning `false` instead of reverting (a documented, common non-standard behavior, and precisely the class of token `SafeERC20` was built to guard against), `success` will be `true` even though the actual token transfer failed. The code treats this as a successful transfer: it unconditionally decrements the internal escrow accounting (`_orders[body.commitment][token] -= amount;`) and emits `EscrowReleased`/`EscrowRefunded`/`DustSwept`, permanently marking the funds as paid out — while the beneficiary never actually received them and there is no remaining accounting entry to retry the transfer.

This is a direct violation of the same root-cause pattern flagged in the source report ("use safeERC20 instead of raw IERC20 interface to handle tokens that don't revert on failure but return false"), and it is inconsistent with the rest of the same file (and with the canonical EVM `IntentsBase.sol._withdraw`, which correctly uses `IERC20(token).safeTransfer(beneficiary, amount);` [4](#0-3) ), showing the Tron variant regressed to an unsafe transfer pattern specifically in the value-release path.

### Impact Explanation
`withdraw()` is reachable by any relayer that delivers a valid `RedeemEscrow`/`RefundEscrow` cross-chain message (via `onAccept`) or a `GET` response confirming cancellation (via `onGetResponse`) [5](#0-4) . Once the message is delivered, `withdraw()` executes automatically and is not retriable if the underlying token silently fails — the escrow ledger (`_orders[commitment][token]`) is already decremented and `_filled[commitment]` is already set, so the funds become permanently unrecoverable by both the user and the solver. This is a permanent freezing/loss-of-funds condition for any TRC-20 token deployed on Tron that follows the "return false on failure" convention (common practice for pausable/blacklistable stablecoins), directly matching the accepted impact class (permanent freezing of funds).

### Likelihood Explanation
Likelihood is Medium-High: it requires only that one of the escrowed/output tokens used with the Intent Gateway on Tron implements ERC20 in the non-reverting, boolean-return-on-failure style (e.g., a paused or blacklist-enforcing stablecoin), and that a transfer condition transiently fails (recipient blacklisted, contract paused, or insufficient balance due to fee-on-transfer/rounding edge cases already handled elsewhere in this same contract). No privileged access or malicious actor is required — it can be triggered by ordinary protocol usage and a normal relayer delivering the settlement message.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` invocations in `withdraw()` and the `SweepDust` branch of `onAccept` with `IERC20(token).safeTransfer(...)` (the contract already imports and uses `SafeERC20` elsewhere), so that non-standard token failures revert instead of being silently swallowed and recorded as fund-release success.

### Proof of Concept
1. Deploy/list a TRC-20 token whose `transfer()` returns `false` on failure instead of reverting (e.g., due to a blacklist or pause flag) as an escrow/output token in `IntentGatewayV2` (Tron).
2. A user places a cross-chain order with this token as input; tokens are escrowed via `safeTransferFrom` (correct).
3. Before settlement, the token issuer blacklists/pauses the gateway's address or the beneficiary address so `transfer()` returns `false` without reverting.
4. A relayer delivers the `RedeemEscrow` message; `onAccept` → `withdraw()` executes `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))`. The low-level call succeeds (`success == true`) because the token contract does not revert, yet no tokens are transferred.
5. `_orders[body.commitment][token] -= amount` still executes and `EscrowReleased` is emitted, permanently closing out the escrow entry — the beneficiary never receives the tokens, and there is no remaining state to allow retry or refund.
