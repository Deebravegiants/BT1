## Analysis: Webhook HMAC Does Not Bind the Shop Identity Header

The reported CCTP bug class is "an operation trusts a value (`order.amount_in`) that isn't actually verified against the thing it's supposed to represent (custody token balance)." The closest concrete analog in this Ruby gem is in the webhook processing path, where the HMAC signature only binds the request body — never the `shop`, `topic`, or `webhook-id` headers that the gem treats as authenticated identity.

### Root cause

`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from unauthenticated HTTP headers: [2](#0-1) 

`Registry.process` validates only the HMAC-over-body, then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`) to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

The identity-binding equality the design implicitly assumes is:
`shop_header == shop_that_actually_produced_and_signed_this_body`

But the HMAC computation never covers `shop_header`, so that equality is never checked — only `HMAC(secret, body) == received_hmac` is checked, and `secret` is shared across all shops that installed the same app.

### Exploit path (no privileged access required)

1. An unprivileged attacker installs the target Shopify app on their own store (or otherwise obtains one legitimate webhook delivery for their own store — no special access needed, just being a merchant/tenant of a multi-tenant app).
2. Shopify sends the attacker's app instance a legitimate webhook: raw body `B`, and header `x-shopify-hmac-sha256 = HMAC(app_secret, B)`, plus `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. The attacker replays this exact body and HMAC header to the app's shared webhook endpoint, but substitutes `x-shopify-shop-domain: victim-shop.myshopify.com` (and/or a different `x-shopify-topic`/`x-shopify-webhook-id`).
4. `HmacValidator.validate(request)` passes because it only recomputes `HMAC(app_secret, B)` and compares — it never looks at the shop header.
5. `Registry.process` calls the app's handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: B, ...)`, so the host application processes attacker-controlled data as though it originated from the victim tenant.

This is a genuine cross-tenant identity confusion enabled entirely by this gem's own `HmacValidator`/`Webhooks::Request`/`Registry` code — it does not require the host app to misuse or ignore documented behavior; the gem's own `to_signable_string` simply never includes the header fields it later trusts as identity.

### Title
Webhook Shop/Topic/Webhook-ID Headers Are Trusted Without Being Covered by the HMAC Signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw body, while `shop`, `topic`, and `webhook_id` — used as trusted identity for routing and tenant attribution in `ShopifyAPI::Webhooks::Registry.process` — come from unauthenticated headers. Because the app-wide `client_secret` used for the HMAC is identical across all shops on a multi-tenant app, any merchant that has installed the app can capture one legitimate webhook (body + HMAC) delivered to their own store and replay it to the shared webhook endpoint with a forged `x-shopify-shop-domain` (and/or `x-shopify-topic`/`x-shopify-webhook-id`) header pointing at a different, victim shop. `HmacValidator.validate` still returns `true` since it never checks header content, and `Registry.process` forwards the forged shop identity to the app's handler.

### Finding Description
- `to_signable_string` in `lib/shopify_api/webhooks/request.rb:35-38` returns `@raw_body` only.
- `HmacValidator.validate_signature` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) computes `HMAC(secret, verifiable_query.to_signable_string)` and compares against the `hmac` header — the shop/topic/webhook-id headers never enter this computation.
- `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) trusts `request.shop`, `request.topic`, `request.webhook_id` post-validation and forwards them unmodified to the registered handler via `WebhookMetadata`.
- Because the same `client_secret` is used to sign webhooks for every shop that installs a given app, a valid `(body, hmac)` pair captured from one tenant remains valid when replayed with a different tenant's identity in the headers.

### Impact Explanation
This breaks the tenant identity binding the library is expected to enforce for incoming webhooks — an unprivileged tenant (any merchant who installed the app) can inject data that the host app will attribute to an arbitrary victim shop (e.g. forged `orders/create`, `app/uninstalled`, `customers/data_request`/GDPR webhooks, etc.), constituting cross-tenant data injection/confusion.

### Likelihood Explanation
Requires only that the attacker be a legitimate, unprivileged installer of the target app (very low bar for any public/multi-tenant Shopify app) and knowledge of the shared webhook endpoint URL, which is typically fixed and public. No secrets, tokens, or elevated access are needed.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) as part of the signable string, or otherwise cryptographically bind the header-derived identity fields to the signed payload (e.g., using per-shop registered callback verification, or requiring the caller to separately corroborate `shop` against the session/access token used to register that specific webhook subscription) before trusting `request.shop` in `Registry.process`.

### Proof of Concept
```ruby
# Attacker owns/installs the app on attacker-shop.myshopify.com and
# receives a legitimate webhook from Shopify:
body = '{"id":123,"note":"legit order for attacker-shop"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_secret, body)

# Attacker replays the same body+hmac to the shared webhook endpoint,
# only forging the shop-domain header:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged
  "x-shopify-webhook-id" => "attacker-controlled-id",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (only body is checked),
#    handler.handle receives shop: "victim-shop.myshopify.com" despite the
#    payload never having been produced for that shop.
```
