### Title
Webhook shop-domain identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented as verifying "the request did indeed come from Shopify," but the HMAC signature it checks only covers the raw request body. The `shop-domain` header — which is surfaced to the host app as the trusted tenant identifier (`WebhookMetadata#shop`) — is never included in the signed bytes, so it can be freely substituted by anyone who can produce a body+HMAC pair.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes and compares the HMAC solely against that signable string: [2](#0-1) 

`Registry.process` treats a passing HMAC check as full request authentication, then immediately trusts `request.shop` (read straight from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` header) to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) [4](#0-3) 

The identity binding that should hold is: `shop header used by the handler == shop bytes actually covered by the HMAC`. Here the HMAC only binds `secret + raw_body`; it says nothing about `shop-domain`, `topic`, `webhook-id`, or `api-version`. Because the app's `api_secret_key` is the same for every shop that installs the app, an attacker who controls their own installed shop can generate a validly-signed webhook body for any topic they can influence (e.g. by creating an order, updating a product, etc. on their own store), then replay that exact body+HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop's domain. `Utils::HmacValidator.validate` still returns `true` because it never looks at the header, and `Registry.process` hands the handler a `WebhookMetadata` claiming the (attacker-controlled) body originated from the victim shop.

The gem's own documentation reinforces that host apps are expected to treat `Registry.process`/`data.shop` as authenticated output ("This will verify the request did indeed come from Shopify" and the example handler does `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), so this is not a case of the host app ignoring documented behavior — the gem's contract itself is broken. [5](#0-4) 

### Impact Explanation
An attacker (any merchant who can install the target app on their own store) can forge webhooks that appear to originate from a different, victim shop. Depending on how the host app uses `data.shop` (e.g. looking up that shop's stored access token/session, writing to per-shop data, triggering shop-scoped actions), this enables cross-tenant data confusion or cross-tenant actions taken under the victim shop's identity — meeting the "cross-tenant access" bar, since the shop identity used to key per-tenant operations is not actually authenticated by this gem.

### Likelihood Explanation
Exploitation requires only: (1) the app being installed on an attacker-controlled shop (normal, unprivileged flow for any public Shopify app), and (2) the ability to send an arbitrary HTTP POST with a chosen `shopify-shop-domain` header to the app's public webhook endpoint — no `api_secret_key`, access token, or privileged access is needed. This is a realistic and moderately likely path for any app that trusts `data.shop` for tenant-scoped logic, which the documented example encourages.

### Recommendation
Bind the shop domain (and ideally topic/webhook id) into the HMAC-verified surface, or otherwise cross-check `request.shop` against a shop that the app has an active, previously-established session/webhook registration for before trusting it. At minimum, update `to_signable_string`/`HmacValidator` so the verified bytes include the shop-domain header, and update `docs/usage/webhooks.md` to make clear that `data.shop` is not itself signature-verified if that remains unchanged.

### Proof of Concept
1. App with `client_secret` S is installed on attacker's own shop `attacker.myshopify.com`.
2. Attacker triggers a webhook-eligible event on their own shop (e.g. creates an order), causing Shopify to POST body `B` to the app's webhook endpoint with `x-shopify-hmac-sha256 = HMAC-SHA256(S, B)` and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker captures `B` and its valid HMAC, then sends their own POST to the same endpoint with the same body `B` and the same HMAC header, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) validates successfully because it only checks `B` against `S`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) builds `WebhookMetadata` with `shop: "victim.myshopify.com"` and invokes the app's handler, which believes the event data in `B` came from the victim shop.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
