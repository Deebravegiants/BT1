### Title
Missing Chainlink `roundId`/`answeredInRound` staleness check in SimplexPaymaster's oracle price fetch - ([File: evm/src/utils/SimplexPaymaster.sol])

### Summary
`SimplexPaymaster._getOraclePrice` only validates a Chainlink `latestRoundData()` answer for a positive price and for `updatedAt` freshness, but never checks that `answeredInRound >= roundId`. This is the same bug class as the reported Notional `TradingModule` finding: a stale/carried-over round can pass the freshness check while still returning an outdated price, since `updatedAt` for a carried-over round can still be recent depending on the aggregator's phase transition behavior.

### Finding Description
`_getOraclePrice` is the sole oracle-consumption path for both the ERC-4337 gas-payment pricing (`_tokenPrice`, used in `_fetchDetails`/`_prefund`) and the treasury `swapAndDeposit` slippage bound: [1](#0-0) 

```solidity
function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
    (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

    if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
    if (block.timestamp - updatedAt > maxOracleAge) {
        revert StaleOraclePrice(address(oracle), updatedAt);
    }
    ...
}
```

The function discards `roundId` and `answeredInRound` entirely (both are left unnamed in the destructuring), so it can never detect a round whose answer was carried over from a prior round via a phase aggregator switch. This is functionally identical to the flagged `TradingModule` code, which likewise checked only freshness and sign, and is the exact bug class Sherlock flagged as Medium.

The interface itself declares all five return values, confirming the values are available but unused for validation: [2](#0-1) 

### Impact Explanation
`_getOraclePrice`'s output feeds directly into `_tokenPrice`, which determines how much ERC-20 token is pulled from every UserOp sender's permit/Permit2 signature to pay for gas: [3](#0-2) 

If a stale/carried-over round is returned for either the native/USD or token/USD feed while still passing the `updatedAt` freshness check (e.g., during an aggregator phase transition or an oracle malfunction that keeps `updatedAt` ticking without a genuinely new answer), `tokenPrice` will be computed from incorrect USD values. This can:
- Overcharge unprivileged UserOp senders in mode `0x00` (`_executePermit`/`transferFrom`), directly taking excess tokens from any address that calls this permissionless paymaster.
- Undercharge senders, silently draining the paymaster's EntryPoint deposit/treasury surplus over time, since `swapAndDeposit`'s `amountOutMin` is also derived from the same stale price: [4](#0-3) 

Both directions cause concrete loss of funds — either from arbitrary unprivileged callers (any UserOp sender) or from the treasury-owned deposit that backs bundler gas — matching the "concrete theft or permanent freezing of funds" bar.

### Likelihood Explanation
The path is reachable by any unprivileged party: `fetchDetails`/`_prefund` execute for every UserOp routed through this permissionless paymaster, requiring no special privilege, governance action, or admin misbehavior — only a Chainlink feed entering a stale-round state (a known, documented Chainlink failure mode, e.g., during aggregator/proxy phase transitions) coincides with an ordinary gas-payment transaction. The existing test suite (`SimplexPaymasterTest.t.sol`) only exercises `updatedAt`-based staleness (`testStaleOracleReverts`) and never exercises the round-carryover scenario, confirming the gap is untested and unmitigated in code.

### Recommendation
Destructure `roundId` and `answeredInRound` in `_getOraclePrice` and add `require(answeredInRound >= roundId, "Stale price")` (or an equivalent revert) alongside the existing freshness and positive-price checks, for both the native and token oracle reads used in `_tokenPrice` and `swapAndDeposit`.

### Proof of Concept
1. Deploy `SimplexPaymaster` with a native or token Chainlink feed.
2. Simulate the feed entering a phase transition where `latestRoundData()` returns a round whose `answeredInRound < roundId` (carried-over answer) but whose `updatedAt` is still within `maxOracleAge` — reproducible against the existing `MockOracle` in `SimplexPaymasterTest.t.sol` by decoupling `answeredInRound` from `roundId` (currently hardcoded equal at line 55: `return (1, answer, updatedAt, updatedAt, 1);`).
3. Call `getTokenPrice`/submit a UserOp through `fetchDetails`/`_prefund`; observe the stale answer is accepted and used to compute `tokenPrice`, over/undercharging the token amount pulled from the UserOp sender or misdirecting `swapAndDeposit`'s slippage bound.

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
