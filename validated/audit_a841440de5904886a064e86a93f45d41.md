### Title
Escrow redemption and dust sweeping in `IntentGatewayV2` (Tron) ignore ERC20 `transfer` return value, enabling silent transfer failure and fund loss - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2` finalizes escrow withdrawals (`RedeemEscrow`/`RefundEscrow`) and processes `SweepDust` messages by issuing a raw low-level `.call` with the `IERC20.transfer` selector and checking only that the call itself did not revert (`success`), without decoding/validating the returned boolean. This is exactly the unsafe-transfer pattern flagged in the referenced report, except the risk here is broader than USDT-style no-return tokens: any ERC20 that signals failure by returning `false` (rather than reverting) will be treated as a successful transfer.

### Finding Description
In `withdraw()`, which is invoked from `onAccept()` for both `RedeemEscrow` and `RefundEscrow` request kinds delivered via cross-chain ISMP messages, the escrow accounting is decremented and the order is marked filled/refunded regardless of whether the token transfer actually succeeded: [1](#0-0) 

The same unchecked pattern appears in the `SweepDust` handling branch of `onAccept()`: [2](#0-1) 

And again for transaction-fee redemption within `withdraw()`: [3](#0-2) 

In all three cases, `(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` only reflects whether the call reverted, not the ERC20's boolean return value. Because Solidity's low-level `.call` never reverts on a `false` return, any ERC20 implementation that returns `false` on failed transfer (e.g., insufficient balance edge cases, blacklisted/frozen recipient, paused token, fee-managed tokens with custom failure semantics) will report `success == true`, so `_orders[...]` is decremented and the order is marked filled/refunded even though the beneficiary received nothing.

This contrasts with the fix already applied elsewhere in the same codebase: `IntentsBase._withdraw()` uses OpenZeppelin's `SafeERC20.safeTransfer`, which correctly reverts on both false-returning and no-return tokens: [4](#0-3) 

The Tron `IntentGatewayV2.sol` contract does not use `SafeERC20`/`SafeTransferLib` for these paths despite importing `SafeERC20` for other functions, making this an inconsistent, unsafe transfer implementation reachable directly from message delivery.

### Impact Explanation
Any relayer delivering a `RedeemEscrow`, `RefundEscrow`, or `SweepDust` cross-chain message for an order that settles in a token which can return `false` on transfer failure will cause the beneficiary/solver/protocol to receive zero tokens while the contract's internal escrow ledger is permanently decremented and the order is marked as filled. This is a permanent freezing/loss of escrowed user funds with no recovery path, since `_filled[body.commitment]` is set unconditionally before/regardless of actual token receipt.

### Likelihood Explanation
Reachable by a single relayed message (an unprivileged relayer submitting a valid consensus/state proof for a `RedeemEscrow`/`RefundEscrow`/`SweepDust` request) once any input/output token used by an intent order can return `false` on failure. This does not require a malicious admin, governance, or node — it only requires the order to reference a token with non-reverting failure semantics, which is a realistic condition for arbitrary user-supplied `TokenInfo.token` addresses in the permissionless Intents flow.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` and the `SweepDust` branch of `onAccept()` with `SafeERC20.safeTransfer` (already imported via `using SafeERC20 for IERC20;` in this file), matching the pattern already used in `IntentsBase._withdraw()`, so that both no-return and false-returning ERC20 tokens revert on failure and escrow state cannot be decremented without a real transfer.

### Proof of Concept
1. Deploy/use an ERC20 whose `transfer()` returns `false` (instead of reverting) under some failure condition (e.g., custom compliance/blacklist logic).
2. Place an order via `placeOrder()` on the source chain with this token as an input, escrowing funds in `IntentGatewayV2` (Tron).
3. Trigger the failure condition for the beneficiary (e.g., blacklist the beneficiary address in the token contract) after order fulfillment/cancellation is initiated.
4. A relayer submits a valid `RedeemEscrow`/`RefundEscrow` proof; `onAccept()` calls `withdraw()`.
5. `token.call(...)` succeeds at the EVM level (`success == true`) even though `transfer` returned `false` internally; `_orders[commitment][token] -= amount` executes and `_filled[commitment]` is set, permanently marking the order settled while the beneficiary's balance never increases — escrowed funds are lost.
