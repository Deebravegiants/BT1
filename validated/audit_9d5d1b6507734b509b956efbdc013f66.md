### Title
Accrual-time `i128` value overflow permanently bricks a saturated market — any entrypoint panic-freezes supply, debt, repay, withdraw and liquidation - (File: contracts/pool/src/interest.rs)

### Summary
Every state-mutating controller/pool path accrues first via `global_sync` → `accrue_step`. `accrue_step` computes `scaled_to_original(supplied, supply_index)` and `scaled_to_original(borrowed, borrow_index)` as `i128` mul-divs that panic with `MathOverflow` once the unscaled value exceeds `i128::MAX`. A single unprivileged actor can push a market's scaled supply to the cap ceiling — which is deliberately set at exactly the largest `i128`-representable balance — and wait for the indexes to drift marginally above `RAY`. From that point `supplied * supply_index / RAY` no longer fits `i128` and every accrual panics, permanently freezing the market: no withdraw, repay, borrow, liquidate, or `update_indexes` can ever execute, and the index ceiling never engages because the panic fires before the cap is applied.

### Finding Description
The bug class is CVE-2017-12425: an arithmetic-overflow condition reachable through ordinary requests that aborts the worker — here, a panic reachable through ordinary entrypoints that aborts the transaction, mapped onto Soroban where the same trap, hit inside a shared pre-computation, wedges the market forever.

- `contracts/pool/src/interest.rs:20-33` — `global_sync` runs on every verb; `accrue_chunk` calls `accrue_step`.
- `common/src/rates/simulate.rs:60-61` — `accrue_step` calls `scaled_to_original(env, borrowed, borrow_index)` and `scaled_to_original(env, supplied, supply_index)`; both are `Ray::mul`, i.e. `mul_div_half_up`.
- `common/src/math/fp_core.rs:108-118,138-143` — the widened `I256` path returns `to_i128()`, which yields `None` when the *result* exceeds `i128`, and the caller panics with `GenericError::MathOverflow`.
- `common/src/validation.rs` (test `cap_ceiling_is_exactly_the_largest_representable_balance`, `common/tests/validation.rs:346-371`) — `max_cap_for_decimals` is exactly `i128::MAX / unit_in_ray`, so `Ray::from_asset(cap)` at a max-configured listing already sits at the `i128` boundary. Once `supply_index > RAY`, `supplied * supply_index / RAY > i128::MAX` and accrual panics.
- The failure is end-to-end demonstrated in `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-361`: after the "ray-value cliff" is reached, `update_indexes`, `withdraw`, and `repay` all revert with `MATH_OVERFLOW`, and the test notes "the index cap never engages" — the panic precedes `MAX_BORROW_INDEX_RAY`/`MAX_SUPPLY_INDEX_RAY` clamping. The test only used `lift_caps` to accelerate the setup; the same state is reachable at the real cap ceiling, just with more tokens.

### Impact Explanation
Permanent freezing of all funds in the affected (hub, token) book: suppliers can never withdraw, borrowers can never repay, liquidators can never close underwater positions on that market (every `liquidate` accrues first), and `clean_bad_debt`/`recapitalize` paths that touch the book's index math are equally wedged. No privileged recovery exists — `update_params` itself accrues under the old curve first. This matches the accepted "permanent freezing of funds / contract unable to operate" impact class.

### Likelihood Explanation
Reachable by a single unprivileged address using only `supply`, `borrow`, and `update_indexes` on a market whose listed cap approaches `max_cap_for_decimals`:

1. Supply the market up to the cap (`supply` with any amount the cap admits; the cap ceiling is defined to be the largest `Ray::from_asset`-representable value, so a saturated market's scaled supply is already ~`i128::MAX`).
2. Borrow enough to keep utilization and the indexes positive (index > 1 requires only time + any nonzero borrow rate; even `base_borrow_rate` alone grows the index).
3. Once `supply_index` ticks above `RAY` by even a few units — the very first accrual on a near-max book suffices, since the product only needs to exceed `i128::MAX` — every subsequent `accrue_step` traps.

The requirement is a cap set close to the asset-domain ceiling (a governance listing choice within in-scope normal operation) plus enough capital to saturate it; nothing privileged or off-chain is needed, and `update_indexes` is permissionless so the attacker controls accrual cadence. Markets capped far below the ceiling get correspondingly more headroom (index must reach ~170× in the test scenario), which is why this is not reachable on every listing — hence Medium rather than High/Critical.

### Recommendation
Saturate instead of panicking on the unscale step, or enforce headroom:

- In `accrue_step`, compute `borrowed_original`/`supplied_original` with the saturating variant (`mul_div_floor_saturating`) or clamp `supplied`/`borrowed` to `i128::MAX / index` before unscaling, so index clamping (`MAX_BORROW_INDEX_RAY`, `MAX_SUPPLY_INDEX_RAY`) still engages rather than a raw `MathOverflow` trap.
- Alternatively, validate supply caps against `i128::MAX / MAX_SUPPLY_INDEX_RAY` (not just `Ray::from_asset` representability) in `require_cap_within_asset_domain`, so `supplied * index` can never overflow before the index ceiling.
- Add a regression entrypoint test: saturate a max-cap market, advance time so `supply_index > RAY`, assert `update_indexes`/`withdraw`/`repay` still succeed.

### Proof of Concept
Sketched against the existing harness (`tests/test-harness`), mirroring `large_positions_and_long_horizons.rs:321-360` but at real caps:

```rust
let mut t = LendingTest::new()
    .with_market(big("BIG18", 18, xlm_curve()))
    .with_market(col())
    .with_max_utilization_disabled_all_markets()
    .build();

// Fill the market to its asset-domain cap: at the cap ceiling,
// Ray::from_asset(cap) is already ~i128::MAX.
let cap = common::validation::max_cap_for_decimals(18);
t.supply_raw(BOB, "BIG18", cap);

// Any positive debt keeps the indexes moving.
t.supply_raw(ALICE, "COL", /* enough collateral */);
t.borrow_raw(ALICE, "BIG18", /* small positive borrow */);

// First accrual window where supply_index ticks above RAY.
t.advance_time(SOME_MS);
// update_supply_index computes supplied.mul(old_index); the result of
// supplied * supply_index / RAY exceeds i128::MAX -> MathOverflow panic.
assert_contract_error(t.try_update_indexes_for(&["BIG18"]), errors::MATH_OVERFLOW);
// Market permanently frozen — every verb accrues first.
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```
