### Title
`validateStarknetAddress` accepts felt252 values ≥ Starknet's field prime, letting withdrawals be signed to unresolvable addresses - (File: packages/intents-sdk/src/lib/validateAddress.ts)

### Summary
`validateStarknetAddress` at `packages/intents-sdk/src/lib/validateAddress.ts` only checks that the address is `0x` followed by 1-64 hex characters, with no check against the Starknet field modulus (`2^251 + 17·2^192 + 1`). A destination string that is a syntactically valid 64-hex-char value but numerically exceeds the prime will pass `validateAddress(address, Chains.Starknet)`, be treated as a valid `OmniAddress` recipient (`strk:0x...`) via `CHAIN_MAPPINGS` in `packages/intents-sdk/src/bridges/omni-bridge/omni-bridge-utils.ts`, and get embedded as `recipient` in the signed `ft_withdraw` intent payload built by `createWithdrawIntentsPrimitive`.

### Finding Description
The claimed equality is: *address validated by `validateAddress(address, Chains.Starknet)` == a valid felt252 value that a Starknet contract can actually resolve as an account/contract address*.

`validateStarknetAddress` [1](#0-0)  is implemented purely as a regex `/^0x[a-fA-F0-9]{1,64}$/`, which bounds the value to 252 bits of hex digits but performs no comparison against the Starknet prime. A felt252 is only valid if its numeric value is strictly less than the prime; a 64-hex-digit value can be up to `2^256-1`, which is far larger than the ~2^251.8 prime, so many syntactically valid-looking hex strings are not valid field elements.

This address flows unchanged into `compareAddresses`'s `compareHexAddress`/`normalizeHexAddress` [2](#0-1)  (which also does no bound check, only hex-format and zero-padding normalization), and into the Omni Bridge `recipient` field via `CHAIN_MAPPINGS` mapping `Chains.Starknet` to `ChainKind.Strk` [3](#0-2)  and `createWithdrawIntentsPrimitive`, which places `recipient` directly into the `ft_withdraw` intent's `msg` JSON without any further validation [4](#0-3) .

No other guard in this repository re-validates the numeric range of the felt before the intent is signed. Because the intent is signed by the user's key and submitted to `intents.near` for settlement, an out-of-range value that Starknet's actual `ft_withdraw`/bridge contract will reject or misinterpret cannot be "fixed" after the fact — the funds are already debited on NEAR by the time the destination-side transfer fails.

### Impact Explanation
The user's funds are debited from `intents.near` via the signed intent (nonce consumed, balance reduced) while the destination-chain leg is directed at an address string that is not a valid Starknet field element and therefore cannot be resolved/deployed as an account on Starknet. This matches "funds delivered to a wrong address/chain/contract with no recovery" (Critical), since the withdrawal is irreversible once signed and settled on the NEAR side, and any bridge relayer/contract on the Starknet side has no way to correct or reroute to a valid felt. This is repeatable for every withdrawal request that supplies such a destination string, whether from a buggy integrator, a malicious counterparty supplying a `destinationAddress`, or user input error that the SDK fails to catch.

### Likelihood Explanation
The only precondition is that the attacker/integrator supply a 64-hex-character Starknet destination address whose numeric value is ≥ the field prime (`0x0800000000000011000000000000000000000000000000000000000000000001` region and above) — trivially constructable, e.g. `0xff...ff` (64 f's). No special privileges, contract state, or route-specific setup are needed; the SDK's `validateAddress` is a pure client-side regex check called before signing, so the cost to trigger it is zero and it is deterministic and repeatable on every call.

### Recommendation
In `validateStarknetAddress`, after the regex format check, parse the hex value as a `BigInt` and reject it if it is greater than or equal to the Starknet field prime `2n**251n + 17n*2n**192n + 1n` (matching the corresponding subgroup/field bound checks already implemented for other chains such as `validateAleoAddress` and `validateSuiAddress`'s stricter checks). Apply the same numeric bound in `normalizeHexAddress`/`compareHexAddress` in `compareAddresses.ts` for consistency.

### Proof of Concept
```ts
// packages/intents-sdk/src/lib/validateAddress.spec.ts
import { describe, it, expect } from "vitest";
import { validateAddress } from "./validateAddress";
import { Chains } from "./caip2";

describe("validateStarknetAddress field-element bound", () => {
  it("currently (incorrectly) accepts a 64-hex value exceeding the Starknet prime", () => {
    // Starknet field prime = 2^251 + 17*2^192 + 1
    const PRIME = 2n ** 251n + 17n * 2n ** 192n + 1n;
    const overPrime = "0x" + "f".repeat(64); // 2^256 - 1, far above PRIME
    expect(BigInt(overPrime) >= PRIME).toBe(true);

    // Left side of the claimed equality: SDK says this is a valid Starknet address
    const sdkResult = validateAddress(overPrime, Chains.Starknet);

    // Right side: it is NOT a valid felt252 that Starknet can resolve
    const isValidFelt = BigInt(overPrime) < PRIME;

    expect(sdkResult).toBe(true);      // demonstrates the bug (should be false)
    expect(isValidFelt).toBe(false);   // ground truth: not a resolvable felt
  });
});
```

/**
 * Validates Starknet addresses
 * Starknet addresses are felt252 (252-bit field elements) represented as
 * hex strings with 0x prefix (up to 64 hex characters)
 */
function validateStarknetAddress(address: string): boolean {
	return /^0x[a-fA-F0-9]{1,64}$/.test(address);
}

// Aptos/Movement/Sui/Starknet addresses are hex field elements: case is not
// significant, and both zero-padded (0x000...01) and short (0x1) forms refer
// to the same address.
function compareHexAddress(a: string, b: string): boolean {
	const normalizedA = normalizeHexAddress(a);
	const normalizedB = normalizeHexAddress(b);
	if (normalizedA === null || normalizedB === null) return false;
	return normalizedA === normalizedB;
}

function normalizeHexAddress(address: string): string | null {
	const withoutPrefix = address.toLowerCase().startsWith("0x")
		? address.slice(2)
		: address;
	if (withoutPrefix.length === 0 || !/^[0-9a-fA-F]+$/.test(withoutPrefix)) {
		return null;
	}
	const withoutLeadingZeros = withoutPrefix.replace(/^0+/, "");
	return withoutLeadingZeros.toLowerCase() || "0";
}

export function createWithdrawIntentsPrimitive({
	tokenAccountId,
	recipient,
	msg,
	externalId,
	storageDepositAccountId,
	amount,
	nativeFee,
	storageDepositAmount,
}: OmniWithdrawIntentParams): (IntentStorageDeposit | IntentFtWithdraw)[] {
	const ftWithdrawPayload: {
		recipient: OmniAddress;
		fee: string;
		native_token_fee: string;
		external_id: string;
		msg?: string;
	} = {
		recipient,
		fee: "0",
		native_token_fee: nativeFee.toString(),
		external_id: externalId,
	};
	if (msg !== "") {
		ftWithdrawPayload.msg = msg;
	}

	const intents: (IntentStorageDeposit | IntentFtWithdraw)[] = [];
	if (storageDepositAccountId !== null) {
		intents.push({
			deposit_for_account_id: storageDepositAccountId,
			amount: nativeFee.toString(),
			contract_id: OMNI_BRIDGE_CONTRACT,
			intent: "storage_deposit",
		});
	}
	intents.push({
		intent: "ft_withdraw",
		token: tokenAccountId,
		receiver_id: OMNI_BRIDGE_CONTRACT,
		amount: amount.toString(),
		storage_deposit:
			storageDepositAmount > 0n ? storageDepositAmount.toString() : undefined,
		msg: JSON.stringify(ftWithdrawPayload),
		min_gas: MIN_GAS_AMOUNT,
	});

	return intents;
}
