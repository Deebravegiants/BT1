### Title
Webhook `shop-domain` and `topic` headers are trusted for dispatch but are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request **body only**, while `ShopifyAPI::Webhooks::Registry.process` dispatches the webhook to the host app's handler using the `shop-domain` and `topic` values taken from unauthenticated **HTTP headers**. This breaks the identity binding: `bytes verified by HMAC == raw_body` ≠ `bytes acted on == headers(shop-domain, topic, webhook-id) + body`.

### Finding Description
`Request#to_signable_string` only returns `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Registry.process` validates only the HMAC of the body via `Utils::HmacValidator.validate(request)`, and then immediately trusts the header-derived `request.topic` and `request.shop` to select a handler and construct `WebhookMetadata`: [3](#0-2) 

`HmacValidator.validate` computes the HMAC purely over `verifiable_query.to_signable_string` (the raw body for webhooks) and compares it against the received `hmac` header: [4](#0-3) 

Because the `api_secret_key` is shared across all shops that install a given app (it is not per-shop), any body+HMAC pair that is valid for the app's secret remains valid **regardless of which shop or topic header accompanies it**. An unprivileged internet user who can install the app on their own store (a normal, unprivileged action) can capture one genuine `(raw_body, hmac)` pair delivered to their own webhook endpoint, then replay that exact body and HMAC to the app's public webhook endpoint while substituting the `shopify-shop-domain` (and/or `shopify-topic`) header with a victim shop's domain. `Registry.process` will accept it as valid (the HMAC still matches the unmodified body) and will invoke the host application's handler with `WebhookMetadata.shop` set to the attacker-chosen victim domain.

### Impact Explanation
This is a cross-tenant identity-binding break: data that the host application treats as authenticated per-shop input (`shop`) is not actually covered by the cryptographic proof that authenticates the request. Any application that uses `WebhookMetadata.shop` to route business logic, index/store data, trigger side effects, or make decisions per-tenant (which is the documented, expected use of this field) can be made to attribute attacker-controlled or replayed data to an arbitrary other shop known to use the same app, resulting in cross-tenant data corruption/injection. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Requires only that the attacker (1) installs the same app on any store they control (an ordinary, unprivileged action for public apps) to obtain one legitimate `(body, hmac)` sample, and (2) can send arbitrary HTTP requests to the app's public webhook endpoint with forged headers — both trivially available to an unprivileged internet user. No possession of `api_secret_key` or any victim credential is required. The only constraint is that the replayed body's semantic content must still make sense to the target handler for topic `T`, which is often true for many webhook topics whose payload schema doesn't include the shop identifier and is topic-generic (e.g., `app/uninstalled`, `shop/redact`, or handlers that only care about IDs relative to the claimed shop).

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the HMAC-verified material, or otherwise cryptographically tie header values to the signed payload (e.g., by having `to_signable_string` incorporate the relevant headers, or by requiring the host application to independently verify that `shop` in `WebhookMetadata` corresponds to a shop that actually has this app installed before trusting the payload). At minimum, document prominently that `shop`/`topic` headers are unauthenticated and must be cross-checked against the app's own installation records before being trusted.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`.
2. Shopify sends a genuine webhook, e.g. `orders/create`, to the app's endpoint with body `B` and header `shopify-hmac-sha256: H`, where `H = HMAC-SHA256(secret, B)`.
3. Attacker replays the identical raw body `B` and `H` to the same app endpoint, but sets `shopify-shop-domain: victim.myshopify.com` (and optionally a different, but still valid-body-compatible, topic).
4. `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(secret, B)`, which still equals `H`, so validation passes: [5](#0-4) 
5. `Registry.process` proceeds and invokes the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: JSON.parse(B), ...)`: [6](#0-5) 
6. The host application processes attacker-supplied payload data under the identity of `victim.myshopify.com`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
