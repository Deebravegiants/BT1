### Title
Webhook `shop`/`topic`/`webhook-id` identity headers are trusted but not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook purely by validating an HMAC over the raw request body, then trusts unauthenticated HTTP headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) to build the `WebhookMetadata` handed to the host application's handler. The tenant-identity binding `hmac_verified_bytes == data_acted_on` is broken: the signature only binds the body, not the shop/topic/webhook-id that the handler uses to decide "which tenant does this event belong to."

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over that signable string and compares it with `OpenSSL.secure_compare`: [2](#0-1) 

Meanwhile, `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read directly from HTTP headers with no cryptographic linkage to the signed body: [3](#0-2) 

`Registry.process` validates only the HMAC, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to construct the metadata delivered to the app's business-logic handler: [4](#0-3) 

Because the shop-identity header is not part of the signed payload, `hmac_valid(body) == true` does not imply `shop_header == shop_that_generated(body)`. Any party capable of producing one legitimately-signed webhook body (e.g., by triggering an event on their own store, which requires no privileged credentials — just a free Shopify dev/partner store) can replay that same body+HMAC pair to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header value. The HMAC check still passes (it only re-hashes the body), but the handler now executes under a shop identity chosen by the attacker rather than the shop that actually produced the event.

### Impact Explanation
This breaks the tenant-authentication boundary the HMAC is supposed to enforce. If the host application's webhook handler uses `data.shop` (as documented/intended, see `WebhookMetadata` fields consumed at `lib/shopify_api/webhooks/registry.rb:198`) to look up or mutate per-tenant state (e.g., updating orders/customers/subscription status for "shop X"), an attacker can cause that state to be applied to a victim shop's tenant record using event content the attacker fully controls (their own store's legitimately-signed payload), i.e., cross-tenant data corruption/injection without ever possessing `api_secret_key`, an access token, or any credential belonging to the victim. This matches the Critical "cross-tenant access" impact category, since it lets one merchant impersonate/target another merchant's tenant identity purely by controlling unauthenticated headers on an internet-reachable endpoint.

### Likelihood Explanation
Likelihood is High: exploitation requires only (1) the ability to trigger one webhook event on any attacker-owned/free-tier store to obtain a validly HMAC-signed body, and (2) the ability to send an HTTP POST to the app's public webhook receiver with attacker-chosen headers — both are unprivileged, internet-reachable actions with no secret material needed. The gem provides no built-in mitigation (no shop allow-list check, no requirement that headers be covered by the signature), so any application that relies on `Registry.process`/`Webhooks::Request` as documented inherits this gap.

### Recommendation
Include the identity-bearing headers (`shop-domain` at minimum, ideally `topic` and `webhook-id`) in the HMAC-signed material, or otherwise cryptographically bind them to the verified body (e.g., verify `shop` against an expected/allow-listed value per registration, or require the caller to pass the expected shop and compare it before dispatch). At minimum, document prominently that `request.shop`/`request.topic` are unauthenticated and must not be trusted for authorization decisions without additional verification.

### Proof of Concept
1. Attacker registers a free/dev Shopify store `attacker-shop.myshopify.com` and installs the target app, subscribing it to a webhook topic the app handles (e.g., `orders/create`).
2. Attacker triggers the event on their own store, capturing the real webhook POST: raw body `B`, and header `x-shopify-hmac-sha256: H` (valid, since Shopify signed `B` with the app's real secret) along with `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker replays the exact same body `B` and HMAC header `H` to the app's public webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com` (and/or a different `x-shopify-webhook-id`).
4. `Utils::HmacValidator.validate` in `lib/shopify_api/webhooks/registry.rb:190` recomputes the HMAC over `B` only — it succeeds, because `to_signable_string` never included the shop header. [4](#0-3) 
5. `Registry.process` calls the registered handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON>, ...)`. Any handler logic keyed on `data.shop` now operates on the victim tenant using attacker-supplied data, despite no credential of the victim ever being involved.
