## Title
Governance-updatable `_instances[stateMachineId]` gateway mapping can strand escrow and orphan fills for orders placed before a `NewDeployment`/re-registration - (File: `evm/src/apps/intentsv2/IntentsBase.sol`, `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`IntentGatewayV2`/`ExtrinsicIntents` resolves the counterparty gateway address for every cross-chain message (`RedeemEscrow`, `RefundEscrow`, and the cancellation GET-proof key) at *send time* through the mutable `_instances` mapping, rather than the address that was actually registered when the order was placed. Hyperbridge governance can update this mapping at any time via a `NewDeployment` request. If that happens while a cross-chain order is in flight, messages meant to settle that order are routed to the newly registered (different) gateway address instead of the original one that holds the order's escrow/`_filled` state, permanently orphaning the funds — the same "address changed underneath an in-flight operation" bug class as the RabbitHole report.

### Finding Description
`_instances` maps `keccak256(stateMachineId) => gateway address` and is written only by `_addDeployment`, invoked from `onAccept` when `RequestKind.NewDeployment` arrives from Hyperbridge governance: [1](#0-0) 

This mapping is read live, not snapshotted per order, whenever a message must be routed to the counterparty chain's gateway:
- `_post`, used by `_fillCrossChain` to dispatch `RedeemEscrow` back to the source chain, addresses the message with `to: abi.encodePacked(_instance(order.source))`: [2](#0-1) 
- `_cancelFromSource` builds the GET storage-proof key against `_instance(order.destination)` to check whether the order was filled on the destination chain: [3](#0-2) 
- Incoming `RedeemEscrow`/`RefundEscrow` deliveries are authenticated against `instance(request.source)` as well (see `_authenticate`/`onAccept` dispatch in `IntentsBase.sol`/`ExtrinsicIntents.sol`), i.e. the *current* registered address, not the address that was live when the order's counterpart message was originally sent.

An `Order` itself only carries chain identifiers (`order.source`, `order.destination`), never the gateway address that was authoritative at placement time. Once `NewDeployment` re-points `_instances[chain]` to a different address (e.g., a gateway migration/redeploy on that chain, which the protocol explicitly supports since deployments are not required to be CREATE2-pinned to one canonical address the way `HyperApp`/`HyperbridgeLzEndpoint` insist an app's own address must be), every order still pending settlement across that route breaks:
- A `RedeemEscrow` dispatched by `_fillCrossChain` after the source's registered address rotates is sent `to` the *new* source gateway, not the one where `_orders[commitment]` escrow actually lives. The new gateway has no record of the commitment, so the solver who already delivered output tokens on the destination chain cannot be paid, and the escrow sits unreachable in the old (now de-registered) contract.
- A `_cancelFromSource` GET-proof after the destination's registered address rotates reads `_filled` state from the *new* destination gateway's storage, which is empty for an order that was actually filled against the old gateway. This can cause the source chain to erroneously conclude the order was never filled and release escrow back to the user even though the solver already paid out — a double-spend of the same order.

### Impact Explanation
This breaks core reachable, unprivileged user paths (`placeOrder`, `fillOrder`, `cancelOrder`) of the Intent Gateway. Depending on which side of a pending order is affected: (a) solvers who honestly filled an order lose their payout permanently because the settlement message is misrouted to a contract with no knowledge of the commitment (freezing of solver funds), or (b) a user can obtain a refund of escrow that was already paid out on the destination side (double payment / unbacked release of funds). Both are concrete fund-loss outcomes reachable from a normal `fillOrder`/`cancelOrder` call, not merely a griefing/DoS. This matches Medium/High severity criteria — permanent freezing of funds or unsound settlement — for a change gated only behind a single Hyperbridge governance action (`NewDeployment`), analogous to the "admin changes a referenced contract address mid-flight" root cause in the RabbitHole finding.

### Likelihood Explanation
`NewDeployment` requests are an ordinary, expected part of gateway lifecycle management (adding/rotating a chain's gateway instance), not a rare emergency action — the protocol has dedicated pallet extrinsics (`add_deployment`/`update_params` in `modules/pallets/intents-coprocessor/src/lib.rs`) that broadcast it to all existing gateways whenever a chain's registered address changes. Any order that is placed and not yet settled at the moment such a rotation propagates is affected without any special attacker action; an attacker (or unlucky solver) does not need to do anything beyond normal fill/cancel activity that happens to straddle a legitimate governance update.

### Recommendation
Snapshot the counterparty gateway address into the order/commitment state at `placeOrder` time (or otherwise bind the settlement message's destination/authentication to the address that was registered when the order was created), rather than re-resolving `_instance(...)` against the live, governance-mutable mapping when dispatching or authenticating settlement messages. Alternatively, gate `NewDeployment`/re-registration so it can only add new chains, never replace an existing chain's live address while orders may still be outstanding for it, forcing an explicit drain/migration window analogous to what `kirk-baird` recommended for RabbitHole (resolve the dependent contract directly from the object that was created with it, not from a container that can be repointed later).

### Proof of Concept
1. User calls `placeOrder` on chain S; `IntentGatewayV2` on S is registered on chain D's `_instances[keccak256(S)]` as address `A`.
2. Solver fills the order on chain D (`fillOrder` → `_fillCrossChain`), which reads `_instance(order.source)` = `A` and dispatches `RedeemEscrow` `to: A`.
3. Before that message is relayed/delivered, Hyperbridge governance issues `NewDeployment` on chain D re-pointing `_instances[keccak256(S)]` to a new address `A'` (e.g. gateway redeployed on S).
4. Any *subsequent* order placed after step 3 will correctly route to `A'`, but the already-in-flight `RedeemEscrow` from step 2 is `to: A` regardless — however, consider the inverse timing: governance rotates the mapping on chain D *before* the solver's fill executes. `_fillCrossChain` then reads `_instance(order.source) = A'` and dispatches `RedeemEscrow` to `A'`, even though the user's escrow for this order lives in `_orders[commitment]` on contract `A` (the address that existed and was authoritative when `placeOrder` executed on chain S).
5. On chain S, `A'` receives the `RedeemEscrow` post but has no `_orders[commitment]` entry (different contract storage) — the solver is never paid, while the user's original escrow remains locked in `A` with no remaining code path to release it except a governance-only `Execute`/manual intervention, mirroring the RabbitHole "admin must manually distribute and pay fees" outcome.

     * @dev Registers a new IntentGateway deployment for a remote state machine.
     * Called when Hyperbridge governance adds support for a new chain. The gateway
     * address is stored in `_instances` keyed by the hash of the state machine ID.
     *
     * @param body The deployment info containing the state machine ID and gateway address.

    function _addDeployment(Deployment memory body) internal {
        _instances[keccak256(body.chain)] = body.gateway;
        emit DeploymentAdded({chain: string(body.chain), gateway: body.gateway});
    }
