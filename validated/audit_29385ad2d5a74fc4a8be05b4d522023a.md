### Title
Webhook shop-domain header not covered by HMAC signature enables cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The webhook signature verification in this gem binds only the raw request body to the HMAC; the `shop-domain` header that is later trusted as the tenant identifier is never included in the signed material. This breaks the intended equality `hmac_signed_bytes == bytes_used_to_attribute_the_request_to_a_shop`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from a separate, unsigned header (`shopify-shop-domain` / `x-shopify-shop-domain`): [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature strictly from `verifiable_query.to_signable_string` (i.e. the body) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` accepts the request once that body-only HMAC passes, and then forwards the **unauthenticated** `request.shop` value straight into the handler as the tenant identifier: [4](#0-3) 

Because every shop installed on the app shares the same `client_secret` (`Context.api_secret_key`) used to compute the webhook HMAC, any body+HMAC pair that is valid for one tenant's webhook delivery is *also* valid for every other tenant, since the shop identity is not part of the signed bytes. An unprivileged party who has access to any one legitimately-signed webhook delivery for the app (e.g., a merchant who installed the app and can observe/replay webhooks sent to their own endpoint, or capture one via a public tunnel/logging proxy) can resend the identical `raw_body` + `hmac-sha256` header to the app's webhook endpoint while substituting a different `shopify-shop-domain` header value. The HMAC validation in `HmacValidator.validate_signature` still succeeds — it never inspected the shop header — yet `Registry.process` and the app's handler now believe the payload originates from the victim shop, since `WebhookMetadata.shop` is populated straight from that header: [5](#0-4) 

This is the direct analog of the reported bug class: a field that is *acted on* (the shop used to attribute/process webhook data, i.e. the tenant boundary) is not *covered* by the integrity check (the HMAC) that is supposed to authenticate the whole request.

### Impact Explanation
This breaks the tenant boundary of a multi-tenant Shopify app: cross-tenant data injection/attribution is possible by any actor able to relay one previously observed, validly-signed webhook body for the app. An app that keys database writes/side effects off `WebhookMetadata#shop` (as the shipped docs/handler contract instructs) can have another merchant's webhook payload silently attributed to and applied against a victim shop's records — a cross-tenant access impact.

### Likelihood Explanation
Exploitation requires only observing (or being the recipient of) one legitimately signed webhook delivery for the app — something any merchant using a multi-tenant app already receives — plus the ability to POST to the app's public webhook endpoint with a modified `shop-domain` header. No `api_secret_key`, access token, or privileged account is required; the attacker never needs to compute a new HMAC, only replay bytes they already possess with a substituted header.

### Recommendation
Include the shop-domain (and, ideally, webhook id/topic) as part of the signed/verifiable material, or otherwise cryptographically bind the shop identity used for downstream processing to the same bytes the HMAC certifies, mirroring the register_service fix's approach of not letting a derived/administrative value (wallet list vs. wallet_count) drift out of sync with the value actually used for iteration/attribution. At minimum, document that `request.shop` is unauthenticated and must not be trusted for tenant attribution without an independent verification against the session/shop the webhook subscription was registered for.

### Proof of Concept
1. App is installed on Shop A and Shop B, both signed with the same `client_secret`.
2. Attacker (merchant of Shop A) captures a legitimately delivered webhook: `raw_body`, and header `shopify-hmac-sha256: <valid mac of raw_body>`, along with `shopify-shop-domain: shop-a.myshopify.com`.
3. Attacker POSTs the same `raw_body` and same `shopify-hmac-sha256` value to the app's webhook endpoint, but sets `shopify-shop-domain: shop-b.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `raw_body` against the HMAC header — validation passes.
5. The handler receives `WebhookMetadata.new(shop: "shop-b.myshopify.com", body: <Shop A's payload>, ...)`, causing Shop A's data to be processed under Shop B's tenant context.
