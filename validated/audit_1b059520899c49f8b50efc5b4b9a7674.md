Based on my research, this bug report describes a Solidity-specific issue in Sablier's token-streaming contracts (`SablierV2LockupLinear.sol`, `SablierV2LockupDynamic.sol`) where a `refundableAmountOf()` view function fails to check the `isCancelable` flag before computing a nonzero refundable amount for non-cancelable streams. This bug class requires: (1) a stateful "stream" object with deposit/streamed/cancelable/canceled/depleted fields, and (2) a view function computing a refund amount that omits one of these state checks.

Searching nearcore's codebase for analogous constructs turns up nothing that matches this pattern within scope:

- nearcore's refund logic operates on receipts/gas/deposits at the runtime level, not stateful "streams." Refunds for failed receipts or unused gas are generated unconditionally as system receipts, not via a view function with a cancelable/permission-based amount calculation. [1](#0-0) [2](#0-1) 
- The only "lockup/vesting" related code in-scope is the genesis CSV-to-state-record tooling, which builds one-time genesis records and calls an external `lockup_and_vesting.wasm` contract (not part of this repo) via an `init` function call; there is no `refundableAmountOf`-style view function or cancelable-stream logic present in nearcore's own runtime, transaction validation, action execution, access-key authorization, storage staking, or wasm metering code. [3](#0-2) 

Since the actual lockup/vesting contract logic lives outside this repository (in the separate `near/core-contracts` project, not indexed here) and nearcore's own refund/gas-accounting code doesn't share the relevant state-machine shape (cancelable vs. canceled vs. depleted flags feeding a refund-amount view function), there is no reachable analog within nearcore's transaction/receipt validation, action execution, access-key authorization, balance/gas accounting, storage staking, wasm metering, host functions, or trie/state accounting paths.

## Deposit Refunds

Deposit refunds are generated when an action receipt fails to execute. All attached deposit amounts are summed together and
sent as a refund to a `predecessor_id` (because only the predecessor can attach deposits).

Deposit refunds have the following fields in the `ActionReceipt`:

- `signer_id` is `system`
- `signer_public_key` is ED25519 key with data equal to 32 bytes of `0`.

Deposit refunds are free for the user and incur no refund fee.
