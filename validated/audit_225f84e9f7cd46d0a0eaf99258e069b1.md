### Title
Unchecked ERC-20 `transfer` return value in Tron `IntentGatewayV2.withdraw`/`onAccept` escrow release - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron fork of the intent-gateway settlement contract releases escrowed ERC-20 tokens with a raw low-level `.call()` encoding `IERC20.transfer.selector`, and only checks the outer call's `success` boolean. It never decodes or validates the ABI-encoded `bool` that `transfer()` itself returns, unlike the canonical EVM implementation which uses OpenZeppelin's `SafeERC20.safeTransfer` (which validates both call success and, when return data is present, that it decodes to `true`).

### Finding Description
In `withdraw()` (called from `onAccept` for `RedeemEscrow`/`RefundEscrow` requests, and from `onGetResponse` for GET-timeout refunds) and in the `SweepDust` branch of `onAccept`, token payouts are performed as:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [1](#0-0) [2](#0-1) 

This checks only that the callee did not revert; it does not verify the returned boolean payload. Any ERC-20 (or TRC-20, which is common on Tron) that signals failure by returning `false` instead of reverting will make `success == true` while the transfer silently fails. Because the code treats `success` as proof of a completed transfer, it immediately debits internal accounting (`_orders[body.commitment][token] -= amount`) and emits `EscrowReleased`/`EscrowRefunded`/`DustSwept` regardless of whether tokens actually moved.

This directly mirrors the referenced Sherlock finding's bug class: a return value from a token operation that signals success/failure is not checked, so the caller (here, `IntentsBase`/`IntentGatewayV2` withdrawal logic) proceeds as if funds were correctly moved.

Contrast with the canonical (non-Tron) EVM contract, which correctly uses `SafeERC20.safeTransfer` for the equivalent logic: [3](#0-2) 

### Impact Explanation
This code path is the core escrow-release mechanism for the intent-gateway's cross-chain and same-chain order settlement. If a token's `transfer` returns `false` on failure (a widely-existing non-standard-but-real-world token pattern, and plausible for arbitrary TRC-20 tokens users configure as order inputs on Tron), the gateway will:
- Decrement/zero-out internal escrow accounting for a commitment even though the beneficiary received nothing, permanently freezing the underlying token balance in the contract (no remaining code path can re-attempt payout for that commitment), and
- Emit `EscrowReleased`/`EscrowRefunded` events that downstream relayers/indexers treat as proof of settlement, causing a wrong contract state that can further propagate to cross-chain accounting (e.g., a source-chain `onGetResponse` refund believing the destination-side redeem/refund succeeded).

This results in permanent loss/freezing of user or protocol funds without any revert to alert callers, which is High severity given real financial impact and no recovery mechanism.

### Likelihood Explanation
Reachable by any solver or user's own escrow withdrawal (RedeemEscrow/RefundEscrow post requests processed by `onAccept`, or GET-timeout refunds via `onGetResponse`) using an ERC-20/TRC-20 token that returns `false` rather than reverting on transfer failure — a routine, unprivileged interaction with the intent gateway that requires no special conditions beyond selecting such a token as an order asset.

### Recommendation
Replace the raw `.call` + `success`-only checks with `SafeERC20.safeTransfer` (as already used in `evm/src/apps/intentsv2/IntentsBase.sol` and `evm/src/apps/IntentGatewayV2.sol`), or manually decode and require the returned boolean to be `true` when return data is present, consistent across `withdraw()` and the `SweepDust` branch in `evm/tron/contracts/apps/IntentGatewayV2.sol`.

### Proof of Concept
1. Configure an order input/output token as (or user selects for withdrawal) a TRC-20 token whose `transfer()` implementation returns `false` on insufficient balance/allowance/blacklist instead of reverting.
2. Trigger `withdraw()` via a `RedeemEscrow`/`RefundEscrow` `onAccept` call (or via `onGetResponse` refund) for a commitment where that token's contract-side balance transfer would fail.
3. Observe: `token.call(...)` returns `success = true` (since the call executed without reverting) even though `transfer` internally returned `false` and moved no tokens.
4. `_orders[body.commitment][token] -= amount` executes, `EscrowReleased`/`EscrowRefunded` is emitted, and the beneficiary never receives funds — the tokens remain permanently trapped in the gateway with no code path left to reclaim them for that commitment.
