### Title
Webhook `shop-domain` Header Is Not Bound to the HMAC Signature, Allowing Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, and `HmacValidator.validate` verifies the HMAC solely against that raw body. The `shop` value handed to the app's webhook handler is read straight from the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header, which is never included in the signed bytes. This breaks the intended binding: `hmac_signed_bytes == bytes_the_app_trusts_for_tenant_identity` does not hold, because `hmac_signed_bytes = raw_body` while `bytes_the_app_trusts_for_tenant_identity = raw_body + shop_header`.

### Finding Description
`Request#initialize` only requires that the `topic`, `hmac-sha256`, and `shop-domain` headers be present; it does not validate that the `shop-domain` value has any relation to the signed payload. `Request#to_signable_string` returns `@raw_body` verbatim, and `Registry.process` calls `Utils::HmacValidator.validate(request)`, which computes an HMAC over `verifiable_query.to_signable_string` (i.e., the body only) and compares it to the `hmac-sha256` header. The `shop` accessor is read independently from the `shop-domain` header and passed unchanged into `WebhookMetadata.shop`, which is what the app's `WebhookHandler#handle` implementation uses to identify the tenant.

Because `api_secret_key` is shared by the app across every merchant that installs it (it is not per-shop), any merchant who installs the app can receive a legitimately-signed webhook for their own shop and obtain a `(raw_body, hmac)` pair that passes `HmacValidator.validate`. That pair remains valid regardless of what `shop-domain` header value accompanies it, since the header is not part of the signed string. A malicious merchant can therefore replay that same valid `raw_body`/`hmac` pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header value naming a victim shop, and the library will report `Utils::HmacValidator.validate(request) == true` and hand the handler a `WebhookMetadata` claiming `shop: "<victim-shop>.myshopify.com"`.

### Impact Explanation
Multi-tenant apps commonly key persistence, session lookup, and business logic off `WebhookMetadata#shop` (this is the documented purpose of that field). An attacker who controls one legitimate tenant/shop can forge webhook events that the app will process as belonging to a different, victim tenant, since the gem provides no cryptographic binding between the verified body and the trusted shop identity. This crosses the tenant boundary the HMAC check is meant to enforce, satisfying the High severity category (scope/tenant check bypass via an unbound field), and depending on what the app does with `data.shop` in its handler (e.g., writing to a shop-keyed store, granting internal state changes), it can lead to cross-tenant data corruption or unauthorized actions attributed to another merchant.

### Likelihood Explanation
Any unprivileged internet user who can install the target app on their own store (i.e., become a legitimate low-privilege tenant) can trigger a real event to capture a valid `(body, hmac)` pair, then replay it with a forged shop header directly to the app's public webhook endpoint — no access to `api_secret_key`, access tokens, or any other tenant's credentials is required. The only requirement is knowledge of the gem's documented webhook verification contract, which relies solely on `Utils::HmacValidator.validate` and exposes `request.shop`/`WebhookMetadata.shop` unauthenticated.

### Recommendation
Bind the shop identity into the signed material that `HmacValidator` verifies, or independently verify that the `shop-domain` header matches an identifier embedded in the verified body (where the topic's payload includes one), before trusting `request.shop` in `WebhookMetadata`. At minimum, `Request#to_signable_string` should incorporate the `shop-domain` header (and ideally `topic`), so the HMAC comparison in `HmacValidator.validate_signature` fails if header values are altered post-signing.

### Proof of Concept
1. App installs on attacker's own shop `attacker.myshopify.com`; Shopify sends a legitimate webhook with `X-Shopify-Shop-Domain: attacker.myshopify.com`, some `raw_body`, and `X-Shopify-Hmac-Sha256` computed over `raw_body` with the app's shared `api_secret_key`.
2. Attacker captures this `(raw_body, hmac)` pair (e.g., by running a proxy in front of their own installed app, which they fully control).
3. Attacker sends a new POST to the app's webhook endpoint with the same `raw_body` and `hmac`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` at `lib/shopify_api/webhooks/registry.rb:190`, which only checks `raw_body` against `hmac` and returns `true`.
5. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed_body, ...)` and processes the attacker's body as if it originated from `victim.myshopify.com`.
