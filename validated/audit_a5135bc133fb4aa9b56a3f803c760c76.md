### Title
Webhook shop/topic identity spoofing via HMAC binding only the raw body, not the `shop`/`topic`/`webhook_id` headers - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook exclusively by checking that `HMAC(secret, raw_body)` matches the `X-Shopify-Hmac-Sha256` header, then trusts the `shop`, `topic`, and `webhook_id` values taken from unauthenticated headers when dispatching to the registered handler [1](#0-0) . The `Request#to_signable_string` used by the HMAC check returns only `@raw_body`, never the shop-domain, topic, or webhook-id headers [2](#0-1) . This breaks the identity binding `shop_claimed_in_header == shop_the_signature_actually_covers`: a valid signature only proves the body's integrity, not which shop it originated from.

### Finding Description
`Request#hmac` decodes the `hmac-sha256` header and `Request#to_signable_string` returns only `@raw_body`:
```ruby
def hmac
  Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
end

def to_signable_string
  @raw_body
end
``` [3](#0-2) 

`Utils::HmacValidator.validate` only ever compares `HMAC(secret, to_signable_string)` against the received signature [4](#0-3) , so the `shop`, `topic`, and `webhook_id` headers are never part of what is verified.

`Registry.process` then reads `request.shop`, `request.topic`, and `request.webhook_id` straight from those unauthenticated headers and hands them to the app's registered handler as trusted metadata:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [1](#0-0) 

Contrast this with `Auth::Oauth::AuthQuery`, where `shop` is explicitly part of the signed string (`to_signable_string` includes `shop:`) [5](#0-4) , showing the gem's own convention that identity fields used downstream should be covered by the signature — a convention broken for webhooks.

Because `shop` is never bound to the signature, any legitimate webhook delivery captured by an unprivileged merchant for their own store — a `hmac-sha256`/body pair they legitimately receive, including highly sensitive GDPR mandatory topics like `shop/redact`, `customers/redact`, or `customers/data_request` [6](#0-5)  — can be replayed to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to name a different (victim) shop. The signature still validates because it depends only on the unmodified body, and `Registry.process` passes the attacker-chosen `shop` value straight through to the handler as if it were authenticated.

### Impact Explanation
This equates to a scope/identity check answering permissively: the gem asserts webhook authenticity ("Invalid webhook HMAC" is the only failure condition) while silently not authenticating the shop that the data is attributed to. A host application, following the gem's documented API, reasonably treats `WebhookMetadata#shop` as trustworthy once `Registry.process` has not raised. An attacker who controls one shop (any developer/merchant account, no elevated privilege needed) can cause the app to process business-critical, tenant-identifying events (including GDPR redact/data-request webhooks) under an arbitrary victim shop's identity — a cross-tenant confusion that can corrupt per-tenant state, trigger deletion/redaction workflows for a shop the attacker doesn't own, or otherwise mix data across tenants.

### Likelihood Explanation
Exploitation only requires an unprivileged attacker to run their own app-installed shop (freely obtainable), capture one legitimate webhook delivery (any topic, since the flaw is header-independent), and resend it with a modified shop-domain header and no access token or `client_secret` needed. No cryptographic secret needs to be known or brute-forced.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the value that is HMAC-verified (e.g., include them in `to_signable_string`, or otherwise require the host app to separately confirm the claimed shop against a known/installed-shop list before trusting `WebhookMetadata#shop`), and document that `shop` in `WebhookMetadata` is not currently covered by the HMAC so callers know they must independently corroborate it.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and legitimately receives (or triggers) a webhook, e.g. `customers/data_request`, with a valid `x-shopify-hmac-sha256` for the raw body.
2. Attacker resends the exact same raw body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds because it only hashes `@raw_body` [7](#0-6) .
4. `Registry.process` dispatches to the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` [8](#0-7) , causing the host app to act on victim-shop identity using attacker-originated data.
