### Title
Fixed-nominal UTXO accounting for rebasing ERC20 tokens allows negative-rebase sandwiching to drain pooled custody and freeze other users' shielded funds - (File: contracts/Hinkal.sol)

### Summary
Hinkal has no token allow-list — any ERC20 address supplied by a caller/prover is accepted as `circomData.erc20TokenAddresses[i]` [1](#0-0)  and the contract simply reads `IERC20.balanceOf` deltas to police deposits/withdrawals [2](#0-1) . Because Hinkal is a pooled-custody shielded-balance system (all depositors of a given token share one on-chain balance while their individual holdings live only as fixed nominal amounts inside private UTXOs), depositing and later withdrawing a rebasing token such as stETH reproduces the exact Lybra bug class: the recorded UTXO amount never adjusts for a negative rebase that shrinks the pooled balance, so an attacker who withdraws promptly after a negative rebase (or before it propagates to the checked balance) can extract their full pre-rebase nominal amount from the shared pool, leaving later legitimate withdrawers unable to redeem their own recorded UTXO amounts.

### Finding Description
On deposit, Hinkal requires that the measured token-balance delta exactly equal the prover-specified `amountChanges[i]`, and that nominal amount becomes the value embedded in the private UTXO commitment [3](#0-2) . On withdrawal, the contract again transfers exactly that fixed nominal `amountChanges[i]` value out of its own token balance [4](#0-3) , and re-validates via the same balance-delta equation [5](#0-4) .

This works correctly for normal ERC20s because 1 unit deposited always equals 1 unit later held. For a rebasing token like Lido stETH, however, `balanceOf` for the *entire pooled Hinkal balance* moves for all depositors simultaneously whenever Lido applies a rebase, while every individual depositor's shielded note still records the old fixed nominal amount. There is no per-user share bookkeeping anywhere in `Hinkal.sol` / `HinkalHelper.sol` / `Transferer.sol` — the "balance equation" is purely `balanceOf(before) vs balanceOf(after)` within a single call, so it cannot detect that a negative rebase changed the aggregate backing for all outstanding UTXOs of that token.

Attack sequence:
1. Attacker deposits amount `A` of a rebasing token (e.g. stETH) into Hinkal, creating a private UTXO for nominal `A`, verified via the balance-delta check [3](#0-2) .
2. A negative rebase occurs (as in the referenced Lido/Lybra report), shrinking Hinkal's total token balance for that asset across *all* depositors, without any Hinkal-side event or accounting update.
3. Attacker immediately withdraws the same nominal `A`, which succeeds because the shrunk pool still momentarily contains enough tokens (the negative rebase hits everyone's aggregate backing, not the attacker's UTXO specifically) — the withdrawal transfer and balance-delta check both pass exactly as in the deposit case [4](#0-3) .
4. Other, honest UTXO holders of the same token, whose notes were also created pre-rebase for fixed nominal amounts, later find that the pool's actual `balanceOf` is insufficient to cover the sum of all outstanding nominal UTXOs, so their withdrawals revert (temporary/permanent freezing) once the shortfall is exhausted by earlier withdrawers.

This is precisely the equality that the external report's Lybra bug breaks: "deposited/recorded nominal amount" is treated as invariant across a rebase, when the actual custodial balance backing it is not.

### Impact Explanation
This breaks the pooled-custody balance equation without ever tripping the on-chain balance-delta check, since that check only verifies intra-transaction consistency, not cross-time backing consistency for a token whose supply floats. The result is uninsured, unbacked withdrawal of pooled funds at the expense of other depositors of the same rebasing token, and permanent/temporary freezing of the last withdrawers who can no longer redeem their full recorded UTXO value — squarely matching the "High" impact category (temporary/permanent freezing of user funds; theft of protocol-held/pooled fee/asset funds).

### Likelihood Explanation
Likelihood depends entirely on whether any Hinkal deployment enables a rebasing ERC20 (e.g. stETH) as a supported deposit/withdraw token, since there is no code-level restriction preventing it [1](#0-0) . Any unprivileged EOA can trigger the sandwich once such a token is in use; no special privileges, oracle manipulation, or admin actions are required — only timing around a real rebase event, exactly as demonstrated by the referenced Lybra PoC.

### Recommendation
Either (a) explicitly disallow rebasing/elastic-supply tokens from being used as `erc20TokenAddresses` in `Hinkal.transact` / `prooflessDeposit` (e.g., via an allow-list enforced in `HinkalHelper`), or (b) if such tokens must be supported, track pooled custody in underlying shares (e.g. wrap stETH into wstETH before crediting a UTXO, or store share-normalized amounts) so that a token's rebase cannot desynchronize a fixed nominal UTXO amount from its actual backing.

### Proof of Concept
Reasoning follows the same mechanics as the external report's Foundry PoC against Lybra: deposit `A` stETH into `Hinkal.transact` (creates UTXO recording nominal `A`) → force/await a negative Lido rebase (shrinks Hinkal's actual stETH `balanceOf`) → immediately call `Hinkal.transact` to withdraw nominal `A` again; the balance-delta check at [3](#0-2)  passes because it only checks the current call's delta, not whether `A` still reflects the attacker's true post-rebase share of the pool, allowing the attacker to extract the same nominal amount deposited pre-rebase while leaving the pool undercollateralized for other UTXO holders of that token.
