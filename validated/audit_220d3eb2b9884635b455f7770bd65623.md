### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop`, `topic`, `api_version`, and `webhook_id` values entirely from unauthenticated HTTP headers, while the HMAC signature validated by `Utils::HmacValidator` only covers the raw request body. This breaks the binding "shop attributed to the webhook == shop whose secret actually authenticated the request," letting an attacker who possesses one validly-signed webhook body (e.g., from their own shop's installation) relabel it as coming from a victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are read straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (the body only) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` validates only this body HMAC, then hands `request.shop` (an unauthenticated header value) straight to the host application's handler as the tenant identifier: [4](#0-3) 

Because the `shop-domain` header is excluded from the signed payload, an unprivileged attacker who owns a legitimate shop installation of the app can:
1. Trigger a webhook delivery to their own shop, capturing a request with a valid HMAC (computed by Shopify using the app's real `client_secret` over that specific raw body).
2. Replay that exact body/HMAC pair to the app's webhook endpoint, but substitute the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain.
3. `HmacValidator.validate` still returns `true`, because it never inspects the shop header — it only recomputes the HMAC over the untouched raw body.
4. The registry then calls `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` with `shop` set to the victim's domain and `body` containing the attacker's own (but validly-signed) data.

The equality that is broken is: `shop authenticated by HMAC == shop attributed to the processed event`. The HMAC only proves "this body was signed with the app secret"; it proves nothing about which shop the body is scoped to, yet the gem lets the caller-supplied `shop` header dictate tenant attribution downstream.

### Impact Explanation
Any host application built on this gem's webhook processing pipeline that trusts `WebhookMetadata#shop` for tenant-scoped side effects (e.g., looking up the victim's session/access token, writing to victim-tenant records, cache keys, billing, or audit logs) can be tricked into performing cross-tenant actions using attacker-supplied but validly-signed data. This is a cross-tenant confusion vulnerability stemming purely from this gem's failure to bind the `shop` field to the HMAC-covered payload, matching the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
High. Any merchant/developer who installs the app on their own store (a normal, unprivileged action) can trigger webhooks for their own shop and thus obtain arbitrarily many valid `(body, hmac)` pairs signed with the real app secret. Forging the `shop-domain` header on a replay requires no cryptographic material — it is a plain HTTP header — and the gem performs no additional check tying it to the signature.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signable string validated by `Utils::HmacValidator`, or otherwise cryptographically bind the `shop` header to the signed payload before trusting it in `WebhookMetadata`. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must be independently verified by the host application (e.g., cross-checked against a known/installed shop list) before being used for tenant-scoped operations.

### Proof of Concept
1. App has two installs: attacker's shop `attacker.myshopify.com` and victim's shop `victim.myshopify.com`.
2. Attacker triggers any webhook event on their own store, capturing the raw POST to the app's webhook endpoint, including headers `x-shopify-hmac-sha256: <valid_hmac>`, `x-shopify-shop-domain: attacker.myshopify.com`, and body `{"id": 123, ...}`.
3. Attacker resends the identical body and HMAC header, but changes `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC purely over `@raw_body` — unchanged — so validation passes: [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop == "victim.myshopify.com"` and the attacker-controlled body, even though the request was never sent by Shopify on behalf of the victim shop.
