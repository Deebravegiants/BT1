### Title
`cancelOrder()` accepts native token via `msg.value` on the same-chain path without any accounting or refund, permanently locking user funds - (File: evm/src/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.cancelOrder()` is declared `public payable` and routes to `_cancelSameChain()` when the order's source and destination chain match [1](#0-0) . Unlike `placeOrder()` and `fillOrder()`, which meticulously track `msg.value` into a local `msgValue` variable, consume it for the relevant legs, and explicitly refund any unspent amount to the caller [2](#0-1) , the same-chain cancellation path (`IntrinsicIntents._cancelSameChain`) never reads `msg.value` at all [3](#0-2) .

### Finding Description
`cancelOrder()` is marked `payable`, so any unprivileged caller can attach ETH to the call. For a same-chain order, execution flows: `cancelOrder` → `_cancelSameChain(order, commitment)` [4](#0-3) . `_cancelSameChain` only computes the remaining escrowed ERC-20/native input amounts and calls `_withdraw` to refund the order's original *escrow* back to `order.user`; it never inspects, forwards, or refunds `msg.value` from the caller of `cancelOrder` itself [3](#0-2) .

Any ETH sent by the caller when invoking `cancelOrder()` on a same-chain order is therefore silently absorbed into the contract's balance. It is:
- Not recorded anywhere in the `_orders` escrow mapping (no commitment/token entry is created for it, since `_cancelSameChain` never touches `_orders[commitment][address(0)]` for the caller's own value),
- Not refunded to the caller (contrast with `placeOrder`/`fillOrder`, both of which explicitly `_sendValue(msg.sender, msgValue)` for any leftover value) [2](#0-1) [5](#0-4) ,
- Not otherwise consumed by any dispatch fee logic, since the same-chain cancel path performs no Hyperbridge dispatch at all.

This is directly analogous to the referenced Gitcoin/Sherlock report: a `payable` entry point in a strategy/escrow-style contract accepts native tokens without validating `msg.value == 0` and without any accounting path for the received value, resulting in funds becoming permanently stuck.

### Impact Explanation
Any native token mistakenly or unnecessarily attached by a user calling `cancelOrder()` on a same-chain order becomes permanently locked in the `IntentGatewayV2` contract. There is no protocol-level accounting entry created for that value and no `SweepDust`/administrative path is documented to reference it specifically (the `SweepDust` request kind is driven by the tracked dust accounting in `_orders`, not by raw untracked contract balance from misdirected calls). Since this function is reachable by any unprivileged caller cancelling their own order (a normal, expected user action), and the UX for `fillOrder`/`placeOrder` on the very same contract normalizes sending `msg.value` with these calls, users following the same pattern with `cancelOrder` on a same-chain order will have their attached ETH permanently frozen — a concrete freezing-of-funds bug.

### Likelihood Explanation
Likelihood is non-trivial: `cancelOrder` is a normal, frequently used user-facing entry point (used whenever an order expires or the user wants to back out), and it is `payable` just like `placeOrder`/`fillOrder`, which train users/integrators to send `msg.value` for native-input orders. Any wallet, script, or aggregator that reuses the same call pattern (e.g., copy-pasting `value: nativeDispatchFee` handling from `fillOrder`/cross-chain cancel paths) when calling `cancelOrder` on a same-chain order will trigger permanent fund loss with no on-chain signal beyond a normal-looking successful transaction.

### Recommendation
Require `msg.value == 0` in the same-chain cancellation branch of `cancelOrder` (or generally whenever `_cancelSameChain` is invoked), e.g.:
```solidity
if (isSameChain) {
    if (msg.value != 0) revert InvalidInput();
    if (currentChain != orderSource) revert WrongChain();
    _cancelSameChain(order, commitment);
}
```
Alternatively, explicitly refund any `msg.value` to `msg.sender` at the end of `_cancelSameChain`, consistent with the refund pattern already used in `placeOrder` and `_fillCrossChain`/`_fillSameChain`.

### Proof of Concept
1. User places a same-chain order via `placeOrder()` with ERC-20 inputs (no native token required).
2. Before the order is filled, the user (or any integrator following the `payable` convention used elsewhere in the same contract) calls:
   `intentGateway.cancelOrder{value: 1 ether}(order, options)` where `order.source == order.destination == host chain`.
3. Execution routes to `_cancelSameChain`, which only processes the ERC-20 escrow refund via `_withdraw`; `msg.value` (1 ether) is never read, transferred, or accounted for [3](#0-2) .
4. The transaction succeeds, the ERC-20 escrow is correctly refunded, but the 1 ETH sent with the call remains stuck in `address(intentGateway).balance` with no accounting entry and no path to reclaim it, permanently locking the funds.

```text
    function cancelOrder(Order calldata order, CancelOptions calldata options) public payable nonReentrant {
        bytes32 commitment = keccak256(abi.encode(order));

        if (_filled[commitment] != address(0)) revert Filled();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        // Emitted here, once, rather than from each of the three routes below. Every check those
        // routes make — Unauthorized, NotExpired, UnknownOrder — reverts, and a revert discards
        // logs, so an early emit can never announce a cancellation that did not happen. Emitting
        // before the branch also keeps `EscrowRefunded` the last log on the same-chain route, where
        // the refund is processed in this same transaction. Three emit sites cost bytecode this
        // contract does not have: it sits within ~100 bytes of the EIP-170 limit.
        emit OrderCancelled({commitment: commitment, canceller: msg.sender});

        if (isSameChain) {
            // Checked here rather than inside `_cancelSameChain`, which used to re-read `host()`,
            // re-query the host's state machine id and re-hash `order.source` to reach the same
            // answer this function already has. Same check, one external call fewer.
            if (currentChain != orderSource) revert WrongChain();
            _cancelSameChain(order, commitment);
```

```text
    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }
```
