### Title
Non-embedded OAuth session cookie stores a predictable, unsigned session ID used directly as the session-storage lookup key, enabling session fixation / cross-tenant session hijacking - (File: `lib/shopify_api/auth/oauth.rb`, `lib/shopify_api/utils/session_utils.rb`)

### Summary
For non-embedded apps, `ShopifyAPI::Auth::Oauth.validate_auth_callback` sets the browser session cookie's value to the plaintext `session.id` (e.g. `"{shop}.myshopify.com_{user_id}"` or `"offline_{shop}.myshopify.com"`) with no HMAC/signature over the cookie value. `ShopifyAPI::Utils::SessionUtils.current_session_id` / `cookie_session_id` later trusts whatever value is present in that cookie as the key to fetch the session (and its access token) from the host app's session storage, without checking that the ID is actually bound to the current browser/user.

### Finding Description
In `lib/shopify_api/auth/oauth.rb`, after a successful OAuth callback, the returned cookie for non-embedded apps is: [1](#0-0) 
i.e. `SessionCookie.new(value: session.id, expires: ...)` — the raw session identifier, not an HMAC or opaque signed token.

The session id itself is fully deterministic and derivable from public information (shop domain + user id, or shop domain alone for offline sessions): [2](#0-1) 

This value is later read straight back out of the cookie and used as the authoritative session lookup key without any integrity check: [3](#0-2) [4](#0-3) 

The identity binding that should hold is: `cookie value == session id that was cryptographically established for *this* browser/OAuth flow`. Instead, the equality that actually holds is only `cookie value == session.id` (a bare string), with nothing tying the cookie to the specific OAuth transaction that produced it (no HMAC, no reference to the `state` nonce, no signature using `Context.api_secret_key`). Since `session.id` is a predictable format (`"#{shop}_#{user_id}"` / `"offline_#{shop}"`), any party who can write a cookie value into the victim's browser (e.g. a subdomain cookie-tossing attacker, a network attacker on a non-HTTPS cookie write path, or any app endpoint that reflects/sets cookies from attacker input) can set `shopify_app_session=offline_victim-shop.myshopify.com` and have the host application's `SessionRepository` hand back the victim shop's stored access token for that "session id" — a classic session-fixation primitive, because the "session" is not actually a proof of authentication, only a lookup key equal to guessable data.

### Impact Explanation
If the host application's session storage keys sessions purely by this ID (as the library's own documentation examples suggest — see `docs/usage/oauth.md` "Store the Session object ... using result Session object" and `MyApp::SessionRepository.store_session(auth_result[:session])`), an attacker who can inject/fixate this cookie value gains cross-tenant access: they can retrieve another merchant's stored `Session` (containing the access token) purely by knowing/guessing that merchant's shop domain, without ever completing an OAuth flow for that shop. This matches "Critical - cross-tenant access" / "High - session fixation" per the impact criteria.

### Likelihood Explanation
Exploitability depends on the attacker's ability to set the `shopify_app_session` cookie in the victim's browser for the app's domain (e.g., via a sibling subdomain, a non-`Secure`/non-`HttpOnly` misconfiguration by the host app's own cookie-setting code, or any endpoint that echoes cookie values). The gem's own example code marks the cookie `secure: true, http_only: true`, which mitigates JS-based theft but does not prevent cookie fixation/injection from a sibling subdomain or a network position that can set cookies for the parent domain. Because the ID has no cryptographic binding, no forged HMAC or knowledge of `api_secret_key` is required — only knowledge of the target `shop` domain (public) and, for online sessions, the numeric `user_id` (often guessable/enumerable). This is a directly reachable path through the gem's own `Oauth.validate_auth_callback` / `SessionUtils` code, not a host-app misuse of a documented API.

### Recommendation
Do not use the raw, predictable `session.id` as the cookie value. Instead, generate an opaque, cryptographically random session cookie value (or an HMAC of the session id keyed with `Context.api_secret_key`) and store the mapping server-side, or sign the cookie value so `cookie_session_id` can verify integrity before trusting it as a lookup key.

### Proof of Concept
1. Attacker learns/guesses a target shop's domain, e.g. `victim-shop.myshopify.com` (public information, and offline session ids are just `"offline_victim-shop.myshopify.com"`).
2. Attacker sets the victim's browser cookie `shopify_app_session=offline_victim-shop.myshopify.com` for the app's domain (via a cookie-fixation vector such as a sibling subdomain, or any app response that lets cookies be set from user-controlled input).
3. Victim (or attacker, using their own browser with the fixated cookie) visits the app; `SessionUtils.current_session_id` reads the cookie value verbatim via `cookie_session_id`: [3](#0-2) 
4. The host app's session repository (per the documented pattern in `docs/usage/oauth.md`) looks up the stored `Session` by this id and returns the victim shop's access token to the attacker's request context — no re-verification that this id was ever legitimately re-derived for the current requester.
