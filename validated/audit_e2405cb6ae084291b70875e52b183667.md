## Title
Division‑by‑zero panic in `Calculator::calc_x_power` reachable from `Processor::calc_take_pnl` can brick Deposit/Withdraw/WithdrawPnl on a fully‑drained pool - (`program/src/math.rs`, `program/src/processor.rs`)

### Summary
The go-ethereum advisory describes a crash caused by code that assumes a value can never be nil/zero and dereferences/uses it unconditionally with `.unwrap()`-style logic instead of validating it first. Raydium's PnL-accrual routine, `Calculator::calc_x_power`, has the same class of defect: it performs `checked_div(current_y).unwrap()` without ever verifying `current_y != 0`, even though `current_y` is derived from live, attacker-influenceable vault balances.

### Finding Description
`Calculator::calc_x_power` divides by `current_y` unconditionally: [1](#0-0) 

It is invoked from `Processor::calc_take_pnl`, which is itself called from `process_deposit`, `process_withdraw`, and `process_withdrawpnl` — all of which are reachable from an ordinary, unprivileged user transaction: [2](#0-1) 

`current_y` corresponds to `y1 = Calculator::normalize_decimal_v2(total_coin_without_take_pnl, ...)`, and `total_coin_without_take_pnl` is computed directly from the *live coin vault token balance* minus `amm.state_data.need_take_pnl_coin`: [3](#0-2) 

If the coin side of the pool is ever driven down to a remaining balance exactly equal to `need_take_pnl_coin` (i.e. `total_coin_without_take_pnl == 0`), `y1` becomes `0`. The guard that decides whether to enter the pnl-adjustment branch (`pool_pc_amount * pool_coin_amount >= calc_pc_amount * calc_coin_amount`) is satisfied whenever the pool side is fully drained (LHS becomes `0`), so the branch computing `calc_x_power(... , current_x, current_y=0)` executes and panics on `checked_div(current_y).unwrap()`: [4](#0-3) 

Exactly like the geth `tryGetNode`/`snap.Account` bug, none of the intermediate helper functions (`calc_total_without_take_pnl_no_orderbook`, `normalize_decimal_v2`, `calc_x_power`) verify the "impossible" zero case before it is consumed by an unconditional arithmetic operation, and the panic aborts the instruction instead of returning a structured `AmmError`.

### Impact Explanation
A Rust `panic!`/`unwrap()` inside a Solana on-chain program aborts the transaction (transaction fails), rather than crashing the validator process the way a Geth panic crashes a node. Because the trigger condition depends on the *persisted* on-chain state (`total_coin_without_take_pnl == 0`, which is a function of vault balance vs. `need_take_pnl_coin`), any state that reaches this condition will make **every subsequent** `Deposit`, `Withdraw`, and `WithdrawPnl` call on that pool panic identically, since the same computation is re-executed and the same zero-division condition persists until the state is externally corrected (which none of these three instructions can do once the panic prevents them from running). This is a durable denial-of-service on core LP operations (deposit/withdraw/pnl-withdraw) for the affected pool, which can freeze LP principal that can no longer be withdrawn through the normal instruction paths.

### Likelihood Explanation
The precise numeric preconditions (coin vault balance dropping to exactly `need_take_pnl_coin`, and pool/target-order products satisfying the `>=` branch guard) require a specific sequence of swaps/withdrawals that is plausible but non-trivial to hit exactly (division truncation from `checked_div` inside swap math makes landing on an *exact* equality harder than it looks, and swaps enforce `amount_out < total_*_without_take_pnl` so they cannot bring the balance to exactly the pnl threshold through the swap path alone). The most direct path is via `process_withdraw`, which lets an LP holder withdraw down to (or very near) full depletion of one side of the pool. This makes the bug reachable, but it depends on reaching a specific state rather than being trivially triggerable with one arbitrary instruction the way the geth bug was.

### Recommendation
- In `Calculator::calc_x_power`, replace `checked_div(current_y).unwrap()` with `checked_div(current_y).ok_or(AmmError::...)?` and propagate a proper program error instead of panicking.
- In `Processor::calc_take_pnl`, explicitly check `total_pc_without_take_pnl != 0 && total_coin_without_take_pnl != 0` (or `x1 != 0 && y1 != 0`) before calling `calc_x_power`, returning a clean `AmmError` (e.g., `CalcPnlError`) when the pool is (near-)fully drained, matching the geth fix pattern of validating "impossible" zero/nil values before use.
- Audit other `.unwrap()` calls inside `calc_take_pnl` (e.g., `x1.checked_sub(x2).unwrap()`, `y1.checked_sub(y2).unwrap()`) for the same class of unguarded panic and convert them to checked, error-returning operations.

### Proof of Concept
1. Attacker (or any LP) accumulates enough LP tokens and repeatedly calls `process_withdraw` (`program/src/processor.rs:1543`) to drain the coin side of the pool's vault down until `coin_amount - amm.state_data.need_take_pnl_coin == 0`.
2. Any subsequent call to `WithdrawPnl` (`process_withdrawpnl`, `program/src/processor.rs:1376`) or `Deposit` (`process_deposit`) recomputes `total_coin_without_take_pnl == 0` via `Calculator::calc_total_without_take_pnl_no_orderbook` (`program/src/math.rs:238`), yielding `y1 == 0`.
3. `Processor::calc_take_pnl` (`program/src/processor.rs:167`) enters the pnl branch and calls `Calculator::calc_x_power(..., current_y = 0)` (`program/src/math.rs:50`), where `checked_div(current_y).unwrap()` panics, aborting the transaction.
4. Because the same on-chain state persists, every future `Deposit`/`Withdraw`/`WithdrawPnl` transaction against this pool repeats the same computation and panics identically, permanently blocking these instructions for the pool.
