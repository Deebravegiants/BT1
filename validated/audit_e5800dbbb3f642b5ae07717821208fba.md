### Title
Webhook tenant identity (`shop-domain` header) is not covered by the HMAC, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes/verifies the webhook HMAC over the raw request body only. The `shop-domain` header — the value the gem uses to attribute the webhook to a specific merchant/tenant — is never included in the signed material. Because the app's webhook signing secret (`api_secret_key`) is shared across every shop that installs the app, any merchant who has installed the app can capture a legitimate `(raw_body, hmac)` pair delivered to their own shop and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` will report success (the body is unmodified and the HMAC is valid for that body+secret), yet `Registry.process` attributes the payload to the attacker-chosen `shop` value.

### Finding Description
The binding that should hold is:
`shop-domain header used by the app == shop that the signed bytes actually originated from`

`Request#to_signable_string` only returns `@raw_body` [1](#0-0) , and `HmacValidator.validate_signature` computes/compares the HMAC purely against that signable string [4](#0-3) . Meanwhile `Request#shop` is pulled directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is completely outside the signed payload [2](#0-1) .

`Registry.process` validates the HMAC and then constructs `WebhookMetadata` using `request.shop` as the tenant identifier passed to the app's handler, without any additional binding check between the body and the shop header [3](#0-2) .

Since Shopify webhooks for a given app are all signed with the same app-level `client_secret` regardless of which shop sent them (this is standard Shopify webhook behavior, not something this gem can control on the sender side, but the gem is the party responsible for the identity binding on receipt), an attacker who legitimately installs the app on their own shop can:
1. Trigger a webhook (e.g., `orders/create`) on their own shop and capture the raw body + valid `X-Shopify-Hmac-Sha256` header Shopify sent.
2. Replay that exact `raw_body`/HMAC pair to the app's webhook endpoint, but swap the `X-Shopify-Shop-Domain` header to a victim shop's domain.
3. `HmacValidator.validate` passes (HMAC only covers `raw_body`, unchanged), and `Registry.process` calls the handler with `shop: <victim shop>`.

This lets an unprivileged (from the victim's perspective) but authenticated (from their own shop) attacker inject data/events that the host application will process as if they came from a shop the attacker does not control — a cross-tenant identity confusion analogous to the `VaultRouter` bug's "argument overwritten/ignored, binding broken" pattern: here the `shop` binding used downstream is never checked against the bytes that were actually verified.

### Impact Explanation
This is a cross-tenant boundary break: any app that keys per-shop business logic (e.g., updating shop-specific records, triggering shop-specific side effects, GDPR/redact processing) off `WebhookMetadata#shop` as provided by this gem can be made to act on behalf of, or against, a shop the attacker does not control, purely by replaying a webhook they legitimately received for their own shop with a forged header. This matches the "Critical - cross-tenant access" impact bucket, since it lets one tenant inject data attributed to another tenant without ever compromising that tenant's credentials.

### Likelihood Explanation
Likelihood is high for any app author following the gem's documented pattern (`Registry.process`/`WebhookHandler.handle` using `data.shop`) if the receiving HTTP layer passes headers through mostly as-is (a very common integration pattern shown in the gem's own docs) — the attacker only needs to install the app themselves (a normal, unprivileged action) to obtain a valid `raw_body`+HMAC pair, then replay it with a modified header. No secrets, tokens, or privileged access are required.

### Recommendation
Bind the `shop` identity into the verified material instead of trusting an unsigned header:
- Include the `shop-domain` header (and ideally `topic`, `webhook-id`) in the HMAC's signable string (or otherwise cryptographically bind them), so that swapping the header invalidates the signature; or
- Cross-validate `request.shop` against an independently-authenticated source (e.g., a previously stored, verified association between the webhook delivery and the shop) rather than trusting the raw header value alone.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and has installed the target app.
# Step 1: Attacker's own shop triggers a webhook; attacker captures the delivery:
raw_body = '{"id": 12345, "email": "attacker@example.com"}'   # from a legit delivery to attacker's shop
valid_hmac_b64 = "<X-Shopify-Hmac-Sha256 header value captured from that legitimate delivery>"

# Step 2: Attacker replays the exact same body/HMAC to the app's webhook endpoint,
# but swaps the shop-domain header to the victim shop:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac_b64,     # unchanged, still valid for raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",  # forged
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) succeeds (HMAC only covers raw_body),
#    handler.handle is invoked with shop: "victim-shop.myshopify.com",
#    even though the payload never originated from that shop.
```
