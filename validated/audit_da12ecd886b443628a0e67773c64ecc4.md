### Title
Caller-supplied route bytes let an unallowlisted venue inject a wallet-draining `transfer` into the victim's signed auth tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
Like the gin advisory, where a client-supplied header (`X-Forwarded-For`) is trusted by one layer and interpreted inconsistently by another, the controller strategy verbs accept fully attacker-constructed `swap` XDR and forward it to the swap router without validating which contracts it names. The router invokes the pool/venue addresses encoded in the payload. A rogue "venue" contract placed on the route can call `token.transfer(victim, attacker, amount)` on any token the victim holds; in auth-recording (simulation) mode that nested call is recorded as a child of the victim's `require_auth` entry and — if the victim signs the resulting tree — executes under their authority. The controller's own guards (`RouterOverspend`, `NoSwapOutput`, post-swap risk gates) only measure the swap input/output and do not bound this side effect. Demonstrated end-to-end by `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` and acknowledged in `docs/explanation/threat-model.md`.

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs` is reached by every unprivileged router strategy entrypoint: `multiply`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral` (and the same pattern underlies `flash_position`). It:

1. reads the router address from storage (`storage::get_swap_aggregator`), [1](#0-0) 
2. authorizes exactly one `token_in.transfer(controller, router, amount_in)` via invoker auth, [2](#0-1) 
3. calls `router.execute_strategy(controller, amount_in, swap)` where `swap` is the raw `StrategySwap` bytes supplied by the caller — never decoded or venue-checked by the controller, [3](#0-2) 
4. enforces only measured input/output deltas and post-swap account risk. [4](#0-3) 

The account owner signs `swap_collateral(caller, account_id, ...)` with `caller.require_auth()` at the root. Because the route bytes can name any contract as a hop venue (the router keeps no allowlist of pool/token addresses — confirmed in `docs/explanation/threat-model.md` lines 154–165: "keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization"), an attacker who supplies the route (e.g., a malicious quote source, phishing UI, or MITM on the off-chain quote service) can make a rogue venue execute `token.transfer(victim, attacker, X)` mid-swap.

The inconsistency, analogous to gin trusting a forged `X-Forwarded-For`: Soroban's recording-mode simulation (`mock_all_auths` / `simulateTransaction`) attributes that nested `transfer` to the victim's auth entry as a child sub-invocation, and enforcing mode executes it if that tree is signed. The harness proves it:

- `RogueHopPool::swap` performs `token.transfer(victim, wallet_token, attacker, amount)` with `victim.require_auth()` satisfied through the caller's tree. [5](#0-4) 
- The test `simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry` shows the stolen transfer recorded as a sub-invocation of Alice's `swap_collateral` auth entry, after which `wallet(alice) == 0` and `wallet(attacker) == WALLET_BALANCE` while the swap itself still pays fair output and passes all controller guards. [6](#0-5) 

### Impact Explanation
Theft of user funds exceeding the routed amount. The victim's entire balance of any token (not just the swap input) can be moved to the attacker in the same transaction that otherwise settles a legitimate-looking, fair-priced `swap_collateral`/`multiply`/`swap_debt`. Neither the payload `min_out`, `RouterOverspend`/`NoSwapOutput`, nor `strategy_finalize`'s health-factor gates bound the loss — they only inspect the declared swap tokens. The threat model itself states: "The loss is then the caller's wallet, not the routed amount." [7](#0-6) 

### Likelihood Explanation
Exploitation requires the victim to sign a transaction containing the malicious `routeXdr` and the poisoned auth tree. The auth tree is visible in simulation output, so a careful wallet that decodes the route and rejects unexpected child sub-invocations blocks it — which is exactly the documented mitigation burden ("A client must decode the route it signs and refuse an authorization tree with any other child"). This mirrors the CVE's `UI:R` vector: success depends on a user/wallet that trusts the quote source and does not inspect nested auth, which is the common case for wallet UIs that render only the root invocation. No on-chain defense exists in the controller or router. Severity: Medium/High.

### Recommendation
Bound the authority placed under the caller's auth tree rather than relying on clients to decode routes:

- Prefer `require_auth_for_args`-style scoping or structure the call so venues execute under the router's invoker auth only — the router already self-authorizes venue pulls via `authorize_as_current_contract` (`venues/auth.rs`); a rogue venue should never be able to add a `victim.require_auth()` child to the signer's tree. Where the host permits, isolate venue calls so `require_auth` on the sender address outside the single authorized input transfer fails.
- Short-term, enforceable on-chain partial fix: before/after `execute_strategy`, the controller cannot prevent the nested-tree issue, but the router could restrict hop pool invocations to a governance-registered venue allowlist (pool address ↔ venue binding) so arbitrary third-party code cannot be placed below the caller's auth. This is a design change since payload-named pools are currently load-bearing for venue discovery.
- At minimum, surface the invariant to integrators: emit/route metadata so wallets can statically verify that the signed auth tree contains exactly the one expected input-transfer child.

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
