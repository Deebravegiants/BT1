### Title
Non-embedded session lookup trusts a raw, unauthenticated cookie value as the session identifier, and offline session IDs are deterministic/public, enabling cross-tenant session takeover - ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
`ShopifyAPI::Utils::SessionUtils.current_session_id` (not `http_client.rb`, which never calls this method) only raises `Errors::CookieNotFoundError` when the `shopify_app_session` cookie key is missing; any present value is returned verbatim as the session ID via `cookie_session_id`. Because offline session IDs generated by this same gem (`offline_session_id(shop) => "offline_#{shop}"`, used in `lib/shopify_api/auth/oauth.rb` as the literal cookie value for non-embedded apps) are fully deterministic and derived only from the public shop domain, an attacker who never installed the app can forge that exact cookie value in their own raw request and have the host app resolve it to a legitimate victim shop's stored session/access token.

### Finding Description
The broken binding: the app assumes `cookie_value == session.id_that_the_server_itself_issued_to_this_browser`, but the code only enforces `cookie_value.present? == true`; it never enforces `cookie_value == an_id_this_specific_client_was_ever_issued`.

Code path:
- `lib/shopify_api/utils/session_utils.rb:19-37` — `current_session_id` for the non-embedded branch (and the embedded fallback branch when `shopify_id_token` is nil) only checks `cookies && cookies[SESSION_COOKIE_NAME]` is truthy, then calls `cookie_session_id(cookies)` which does `cookies[SESSION_COOKIE_NAME]` (`lib/shopify_api/utils/session_utils.rb:68-71`) — no signature, no HMAC, no per-client binding, no ownership check.
- `lib/shopify_api/auth/oauth.rb:100-110` — after a legitimate OAuth completion for a non-embedded app, the gem sets `SessionCookie.new(value: session.id, ...)`. For offline sessions, `session.id` is produced by `offline_session_id(shop) = "offline_#{shop}"` (`lib/shopify_api/utils/session_utils.rb:63-66`) — a value with zero secret entropy, fully derivable from the public `myshopify.com` domain.
- The host app (per the gem's own documented usage in `docs/getting_started.md:47-52`) is expected to store/retrieve the real `Session` (containing `access_token`) keyed by this same ID, and to store the cookie as a plain (not Rails-signed/encrypted) cookie, per the documented example in `docs/usage/oauth.md`.

Attacker's exact request: send any HTTP request to an app endpoint that calls `current_session_id` with header `Cookie: shopify_app_session=offline_victim-shop.myshopify.com` and no `Authorization`/JWT. `Context.embedded?` being false (or true with no id token) routes into the branch that only checks for key presence, returning `"offline_victim-shop.myshopify.com"` unchanged. The host app then looks this ID up in its own session store, retrieves the victim's real persisted `access_token`, and serves the attacker's request as if it were the victim shop.

Why existing guards don't help: `HmacValidator.validate` and the OAuth `state` comparison only protect the OAuth callback step (`lib/shopify_api/auth/oauth.rb:64-71`), not this cookie-lookup path. `JwtPayload`'s `aud`/claim checks only apply when a JWT (`shopify_id_token`) is present — irrelevant here since the attacker supplies no token. `Context.embedded?`/`private?` only select which branch runs; neither branch validates the cookie's authenticity, only its presence.

### Impact Explanation
Any attacker who can guess or discover a target shop's `myshopify.com` domain (commonly discoverable via storefront metadata, canonical links, redirects, etc.) and who knows the app calls `current_session_id` for cookie-based (non-embedded) session resolution can forge the `shopify_app_session` cookie value `offline_{shop}` in their own request. If that shop previously installed the app (creating a real persisted offline session with a real `access_token`), the attacker's forged request resolves to that victim's session and access token — a cross-tenant access / authentication bypass, repeatable against any shop whose domain is known, with no interaction from the victim required.

### Likelihood Explanation
Preconditions: app is non-embedded (or embedded without token but with cookie fallback reachable), uses the gem's documented cookie-based session flow (`docs/getting_started.md`), and persists sessions keyed by the deterministic `offline_#{shop}` ID as generated by this gem. Attacker cost is trivial — one HTTP request with a crafted `Cookie` header, no secrets or prior installation required, and the target shop domain is often public or easily enumerable. This is fully repeatable against any shop domain the attacker can enumerate.

### Recommendation
Do not use a deterministic, publicly-derivable string as the sole identifier/bearer value in an unauthenticated cookie. Either (a) bind the session cookie to a cryptographically random, unguessable value distinct from the storage lookup key, or (b) require the cookie to be verified via a signed/encrypted mechanism (e.g., Rails' signed/encrypted cookie jar) so its authenticity — not just its presence — is checked, and update `current_session_id`/`cookie_session_id` and the documented usage example accordingly to avoid recommending plain, unsigned cookies for authentication-bearing values.

### Proof of Concept
```ruby
# test/utils/session_utils_test.rb (illustrative addition)
def test_forged_offline_cookie_value_is_accepted_without_ownership_check
  ShopifyAPI::Context.stubs(:embedded?).returns(false)

  forged_session_id = "offline_victim-shop.myshopify.com"
  cookies = { ShopifyAPI::Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME => forged_session_id }

  result = ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)

  # No CookieNotFoundError is raised, and the attacker-chosen value is trusted verbatim
  assert_equal(forged_session_id, result)
end
```
This confirms `current_session_id` never validates that the cookie value corresponds to a session actually issued to the requesting client — it only checks the key exists — so any host app resolving sessions by this deterministic ID is exposed to cross-tenant session takeover.         def current_session_id(shopify_id_token, cookies, online)
          if Context.embedded?
            if shopify_id_token

              session_id_from_shopify_id_token(id_token: id_token, online: online)

            raise Errors::CookieNotFoundError, "Session cookie not found for app" unless

          end
        end

```markdown
#### Cookie
Cookie based authentication is not supported for embedded apps due to browsers dropping support for third party cookies due to security concerns. Non-embedded apps are able to use cookies for session storage/retrieval.

For *non-embedded* apps, you can pass the cookies into:
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, true)` for online (user) sessions or
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)` for offline (store) sessions.
```

    auth_response = ShopifyAPI::Auth::Oauth.begin_auth(shop: domain, redirect_path: "/auth/callback")
