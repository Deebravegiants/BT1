## Finding: Webhook shop/topic identity not covered by HMAC in `ShopifyAPI::Webhooks::Request` [1](#0-0) [2](#0-1) 

### Title
Webhook shop/topic/webhook-id headers are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying the HMAC over the raw request body via `Utils::HmacValidator.validate(request)`. The signable string used for that HMAC is `Webhooks::Request#to_signable_string`, which returns only `@raw_body`. The `shop`, `topic`, `webhook_id`, and `api_version` values, however, come from HTTP headers (`x-shopify-shop-domain`, `x-shopify-topic`, `x-shopify-webhook-id`, `x-shopify-api-version`) that are never part of the HMAC-signed material. After HMAC validation succeeds, these unverified header values are forwarded verbatim into `WebhookMetadata` and handed to the app's registered handler as trusted identity fields.

### Finding Description
`Webhooks::Request#hmac` and `#to_signable_string` establish the binding that `Registry.process` relies on for authentication: [3](#0-2) 

The equality the gem needs to hold is:
`bytes verified by HMAC == bytes the shop identity is derived from`

But in reality only `@raw_body` is verified, while `shop` (line 21-23), `topic` (line 16-18), and `webhook_id` (line 31-33) are read straight from attacker-controllable headers, not from the signed payload: [4](#0-3) 

`Registry.process` then trusts these unverified fields to build the `WebhookMetadata` passed to the app's handler: [2](#0-1) 

Because the HMAC only proves "this body was produced by Shopify for *some* shop/topic pair signed with our secret," it does **not** prove which shop or topic that body belongs to. An unprivileged actor who legitimately receives one valid webhook delivery for their own store (e.g., by installing the app on a store they control) obtains a valid `(raw_body, hmac)` pair. They can then replay that exact body/HMAC pair while substituting the `x-shopify-shop-domain` header (and optionally `x-shopify-topic`) to point at a victim shop. `HmacValidator.validate` still succeeds because it only checks the body against the secret, and `Registry.process` will dispatch the handler believing the event originated from the victim's tenant.

### Impact Explanation
This breaks the tenant boundary the library is expected to enforce for webhook delivery: `shop` is meant to identify which merchant's data a webhook event applies to, but that field is never covered by the same authentication mechanism (HMAC) that is used to prove the request came from Shopify. Any host application that uses `WebhookMetadata#shop` (as returned by this gem) to select which merchant's session/records to update is exposed to cross-tenant data corruption or disclosure driven entirely by attacker-controlled headers with a replayed-but-valid HMAC. This matches the Critical category of "cross-tenant access."

### Likelihood Explanation
Likelihood is non-trivial but requires the attacker to first obtain at least one genuine `(raw_body, hmac)` pair, which is trivially available to anyone who can install the app on a store they control (a normal, unprivileged action many test/dev merchants can perform) and capture one webhook delivery. From there, replaying the body with a forged shop header requires no secret material at all, since the vulnerable check (`Utils::HmacValidator.validate`) never inspects headers.

### Recommendation
Extend `Webhooks::Request#to_signable_string` (or add a separate binding check in `Registry.process`) so that `shop`, `topic`, and `webhook_id` are cryptographically bound to the same value verified by the HMAC — for example, by rejecting/flagging any mismatch between the header-derived shop/topic and values embedded in (or derivable from) the signed body, or by requiring the caller to supply the expected shop/topic out-of-band and asserting equality before dispatch. At minimum, document loudly that `WebhookMetadata#shop`/`#topic`/`#webhook_id` are **not** authenticated by the HMAC and must not be trusted for tenant selection without an independent check (e.g., cross-referencing against the shop associated with the currently active session/install).

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and captures a legitimate webhook delivery, e.g. for `orders/create`, giving them a valid `raw_body` and its corresponding `x-shopify-hmac-sha256` value (both signed against the app's real `api_secret_key`, which the attacker never needs to know).
2. Attacker resends the exact same `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but sets:
   - `x-shopify-shop-domain: victim.myshopify.com`
   - (optionally) `x-shopify-topic` to a topic of choice, if the target handler is registered for it.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `request.to_signable_string` (`@raw_body`) — validation succeeds because the body/HMAC pair is genuinely valid.
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` using the attacker-supplied `shop` header and dispatches it to the app's handler, which believes the event pertains to `victim.myshopify.com` even though the body content actually belongs to the attacker's own store.
