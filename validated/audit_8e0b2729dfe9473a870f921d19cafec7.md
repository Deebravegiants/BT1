Based on my investigation, I found a clear analog matching the report's bug class ("field acted on but not covered by the HMAC").

### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook event forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body. The `shop` value that the gem hands to the app's `WebhookHandler` — and which the documentation explicitly tells integrators to trust as "The shop domain of the webhook" — is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never included in the signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from unauthenticated HTTP headers: [2](#0-1) 

`Registry.process` validates the request using only that signable string: [3](#0-2) 
and then passes `request.shop` straight through as the tenant identifier in `WebhookMetadata`, which the docs instruct app authors to use directly as the shop to act on (e.g., `perform_later(shop_domain: data.shop, ...)`): [4](#0-3) 

The binding that should hold is: `HMAC(raw_body, api_secret_key) valid` ⟺ `(raw_body, shop) originated together from Shopify for that shop`. In reality the equality only covers `raw_body`; `shop` is unauthenticated and freely attacker-settable per request. `Utils::HmacValidator.validate` performs a `secure_compare` purely over `verifiable_query.to_signable_string`, i.e. the body, never the shop header. [5](#0-4) 

**Exploit path**: An unprivileged internet user can install the same app on their own store (any user can create a Shopify dev store), and Shopify will deliver a genuine webhook (e.g. `orders/create`) to the app with a body they influence (order note, custom fields, etc.) and a correctly computed HMAC signed with the app's real secret. The attacker captures this valid `(raw_body, hmac)` pair and replays it directly against the app's public webhook endpoint, substituting the `x-shopify-shop-domain` header with a victim shop's domain. Because the shop header is not part of the signed content, `HmacValidator.validate` still succeeds, and `Registry.process` invokes the app's handler with `WebhookMetadata#shop` set to the victim's domain and attacker-controlled body content.

### Impact Explanation
This is a cross-tenant data injection / cross-tenant access vulnerability: an attacker with no relationship to the victim shop can cause the app to persist or act on forged data (fake orders, fake customer records, fake redact/GDPR events, etc.) as if it originated from the victim's store, because the gem's only authentication of the webhook (the HMAC) does not bind the `shop` field it exposes to callers. This satisfies the Critical bar of "cross-tenant access" since tenant isolation is broken purely through this gem's webhook processing API used exactly as documented.

### Likelihood Explanation
Likelihood is realistic: creating a Shopify dev store and installing a public app is trivial and requires no privileges; webhook endpoints are necessarily internet-reachable and unauthenticated aside from the HMAC by design; and the docs explicitly instruct developers to trust `data.shop` from `WebhookMetadata` as the tenant key, so most integrations follow this pattern per the gem's own guidance.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the value verified by the HMAC check, or have `Registry.process`/`Utils::HmacValidator` cross-check `request.shop` against the shop associated with the currently active/expected session or an app-provided allow-list before invoking the handler, rather than trusting an unauthenticated header as the tenant identifier. At minimum, the documentation and `WebhookMetadata#shop` contract should make clear that `shop` is not cryptographically bound and must be independently verified by the host app (e.g., confirmed against a known installed-shop list) before being used as a tenant key.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a real webhook (e.g. `orders/create`) with attacker-chosen order data.
2. Attacker's own endpoint (or a proxy they control) records the raw request body and the `x-shopify-hmac-sha256` header Shopify sent — this HMAC is valid because it was computed by Shopify with the app's real `api_secret_key` over that exact body.
3. Attacker POSTs that exact `raw_body` and `x-shopify-hmac-sha256` value to the target app's public webhook route, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers, `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the HMAC, and `Registry.process` invokes the handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, causing the app to write attacker-controlled data under the victim tenant's identity.           end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
