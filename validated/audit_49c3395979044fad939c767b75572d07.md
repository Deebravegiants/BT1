### Title
Unverified route venue contracts execute under the caller's authorization tree, enabling wallet drain - (File: contracts/swap-aggregator/src/venues/mod.rs)

### Summary
The reported bug class is a client that trusts a peer without authenticating it (missing `verify_ssl` → MITM). The direct analog in XOXNO Lending is the swap router's hop dispatcher: `execute_strategy` decodes pool and token addresses entirely from the caller-supplied `swap_xdr` payload and invokes whatever contract each `hop.pool` names, keeping no allowlist of legitimate venue contracts. A route can therefore substitute an attacker-deployed contract for a real Aquarius/Soroswap/Phoenix/Sushi/Comet pool, and anything that contract does below the router sits inside the swap caller's signed authorization tree — the on-chain equivalent of an unauthenticated endpoint speaking for the counterparty.

### Finding Description
`execute_strategy(sender, total_in, swap_xdr)` authenticates `sender`, pulls `total_in`, and walks the payload's hops. `dispatch_hop` in `contracts/swap-aggregator/src/venues/mod.rs` calls `invoke_contract(&ctx.hop.pool, ...)` where `hop.pool` is an arbitrary address read from the payload's address registry — there is no check that `hop.pool` is a genuine pool of the declared `SwapVenue`, or that `hop.token_in`/`hop.token_out` are real Stellar asset contracts.

Because `sender.require_auth()` covers the whole `execute_strategy` call, any `require_auth` a rogue hop contract performs on the sender (e.g., `token.transfer(sender, attacker, x)` on an unrelated token the victim holds) is recorded by the Soroban host as a child of the caller's authorization entry and executes if the caller signs that tree — which is what `simulateTransaction` records and wallets typically sign verbatim. The measured-delta checks in `dispatch_hop` only bound the *routed* `amount_in`/`token_out` flows; they do nothing to constrain what the malicious contract does with the caller's own auth.

This is demonstrated end-to-end in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`: a `RogueHopPool` named by the route performs `token::transfer(victim, attacker, WALLET_BALANCE)` during `swap_collateral`, and the test asserts the recorded auth tree contains the theft under Alice's `swap_collateral` entry and that her entire unrelated-token wallet balance (77,770 units) moves to the attacker while the swap itself pays a fair output.

The same exposure applies to the controller strategies (`multiply`, `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`), which forward caller-supplied `swap` bytes to the configured router — the controller's own grant is narrowly scoped to one input transfer, but the caller's `require_auth` on the controller entrypoint still spans the rogue hop's calls.

### Impact Explanation
Theft of user funds. A single malicious route converts a routine swap into a full drain of every token the victim holds — the loss is the caller's wallet, not merely the routed `total_in`, and neither the payload `min_out` check nor the controller's final risk gates bound it. Severity: High — the economic impact is unbounded wallet theft conditioned on the victim signing a crafted route.

### Likelihood Explanation
Medium. Exploitation requires the victim to submit a route whose authorization tree contains the malicious child — e.g., via a compromised/malicious quoting service, a doctored XDR payload, or a client that auto-signs whatever the simulation records. No privileged access, key compromise, or protocol cooperation is needed on the attacker's side: deploying the rogue pool contract and crafting the payload are both unprivileged actions. Honest routes produce no extra auth children, so a careful client can detect the tree — but the contracts place that burden entirely on the signer.

### Recommendation
Bind hop targets to verified venue deployments: maintain a governance-managed allowlist (or canonical factory/registry lookup) of pool addresses per `SwapVenue` in the swap-aggregator, and reject hops whose `pool`/`token` addresses are not registered. Alternatively or additionally, the router should invoke each hop with a scoped `authorize_as_current_contract` rather than letting venue code run beneath the caller's `require_auth`, so a hop can never add children to the sender's auth tree. Clients should also be required to reject any authorization tree containing children beyond the expected single input transfer (as the threat model already advises).

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:

1. Deploy `RogueHopPool` storing `(victim, wallet_token, attacker, amount)`.
2. Build `RoutedSwap` naming the rogue contract as `hop_pool` with fair `min_out` and legitimate `token_in`/`token_out`.
3. Victim calls `swap_collateral` (or `execute_strategy` directly) with the crafted route.
4. During the hop, `RogueHopPool::swap` calls `token::transfer(victim → attacker, WALLET_BALANCE)`; the host records it under the victim's authorization entry.
5. Assertions confirm: recorded tree contains the stolen transfer, victim's wallet token balance is `0`, attacker's is `WALLET_BALANCE`, and the swap otherwise settled "fairly" (`supply_balance_raw(ALICE, "ETH") == FAIR_OUT_ETH`).
