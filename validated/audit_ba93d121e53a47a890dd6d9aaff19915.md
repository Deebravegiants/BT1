### Title
POA Bridge Withdrawal Status Misreport for Batched Same-Asset Withdrawals - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` identifies which withdrawal record to report by matching only on `assetId`, ignoring the `index` field that uniquely distinguishes withdrawals of the same asset submitted in a single batched NEAR intent transaction. When two or more withdrawals of the same token (different amounts/destinations) are included in one batch, every `describeWithdrawal` call returns the same (first found) API record regardless of which index was requested, causing the wrong status/txHash to be reported for at least one withdrawal.

### Finding Description
The SDK explicitly supports batching multiple withdrawals in a single NEAR intent transaction (see `docs/design/rfc-batch-withdrawal-granular-control.md` and the "Batch Withdrawals" section of `packages/intents-sdk/README.md`). Each withdrawal is assigned a per-bridge-route sequence number by `createWithdrawalIdentifiers` in [1](#0-0) , which increments an `index` counter keyed by `bridge.route`. Two withdrawals routed to `PoaBridge` for the *same* `assetId` (e.g., a batch withdrawing `usdt.omft.near` to two different destination addresses) receive `index` 0 and 1 respectively, but both share the same `assetId`.

`PoaBridge.describeWithdrawal` delegates matching to `findMatchingWithdrawal`, which searches the bridge's unsorted API response by `assetId` alone and returns the **first** match, deliberately not using `index`: [2](#0-1) [3](#0-2) 

The docstring itself acknowledges the limitation ("multiple withdrawals of the same token in a single transaction are not supported... POA API doesn't currently support this case either"), but the SDK does not prevent this scenario from occurring — `PoaBridge.supports()` and `validateWithdrawal()` place no restriction preventing two withdrawal params with the same `assetId` from both being routed to `PoaBridge` in one call to `sdk.createWithdrawalIntents`/`processWithdrawal` with an array of `WithdrawalParams`.

As a result, when the caller (or `withdrawal-watcher.ts` / `createWithdrawalCompletionPromises`) later calls `describeWithdrawal({ ..., index: 0, ... })` and `describeWithdrawal({ ..., index: 1, ... })` for the two same-asset withdrawals, both calls resolve against the identical first-matching API record — i.e. the same `status` and `txHash` — even though they correspond to two physically distinct withdrawals with different destination addresses/amounts and (once the second withdrawal actually settles on-chain) different real transaction hashes.

This breaks the equality: *status/txHash reported for withdrawal index N == the actual on-chain outcome for withdrawal index N*.

### Impact Explanation
An integrator using the granular batch-completion API (`createWithdrawalCompletionPromises`/`watchWithdrawals`, per the RFC) to independently credit/refund/mark-complete per index would:
- Report withdrawal index 1 as `completed` with the txHash that actually belongs to withdrawal index 0 (misdelivery-status confusion), potentially crediting/marking-settled a withdrawal that has not actually landed, or
- Report the same `txHash` for two distinct withdrawals, leading an integrator's reconciliation logic to treat both withdrawals as fulfilled by a single destination transaction (double credit / incorrect refund decision).

This matches the explicitly in-scope High-impact category: "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
This requires no privileged access or malicious peer — it is triggered by an ordinary, SDK-supported usage pattern: submitting a batch withdrawal (`WithdrawalParams[]`) containing two entries with the same `assetId` routed to POA bridge (e.g., partial withdrawal to a primary address plus a refund/fee-split to a secondary address of the same token). The bug manifests automatically once both entries are queried via `describeWithdrawal`.

### Recommendation
Update `findMatchingWithdrawal` (and `PoaBridge.describeWithdrawal`) to disambiguate by more than `assetId` — e.g., by matching remaining unmatched withdrawal records per index/consuming matched records so each index maps to a distinct API withdrawal record (matching by amount/destination in addition to assetId, or consuming already-claimed entries), and/or explicitly reject/guard batches containing multiple same-`assetId` withdrawals routed through POA until upstream API support exists.

### Proof of Concept
1. Build a batch: `withdrawalParams = [{assetId:"nep141:usdt.omft.near", amount:1000n, destinationAddress:"addrA", feeInclusive:false}, {assetId:"nep141:usdt.omft.near", amount:2000n, destinationAddress:"addrB", feeInclusive:false}]`.
2. Call `sdk.signAndSendWithdrawalIntent({withdrawalParams})`; both entries route to `PoaBridge`, receiving `index` 0 and 1 respectively via `createWithdrawalIdentifiers`.
3. POA bridge's public withdrawal-status API returns both withdrawals for the batch's near tx hash (unsorted), both with `intents_token_id`/`near_token_id` equal to `usdt.omft.near`.
4. Call `bridge.describeWithdrawal(wid0)` and `bridge.describeWithdrawal(wid1)` — both calls invoke `findMatchingWithdrawal(response.withdrawals, "nep141:usdt.omft.near")`, which returns `withdrawals.find(...)`'s first hit for both calls regardless of `wid.index`, yielding identical `{status, txHash}` for both, even though withdrawal 1 (to `addrB`) may still be pending or have a different real destination tx hash than withdrawal 0 (to `addrA`).

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

		args: WithdrawalIdentifier & { logger?: ILogger },

		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
