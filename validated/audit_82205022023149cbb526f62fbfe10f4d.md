### Title
Permanent freezing of escrow via ERC721 tokens registered as intent-gateway input assets - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentGatewayV2`'s `placeOrder` (and the same-chain/cross-chain fill paths in `IntrinsicIntents.sol`/`ExtrinsicIntents.sol`) accept any address as `TokenInfo.token` and pull it in with `IERC20(token).safeTransferFrom(...)`, with no validation that the address is actually a standard ERC20. An ERC721 contract can be substituted, using the NFT's `tokenId` as the `amount`, which succeeds on deposit but makes the escrowed asset permanently un-withdrawable.

### Finding Description
`placeOrder` in `evm/src/apps/IntentGatewayV2.sol` (mirrored in `evm/tron/contracts/apps/IntentGatewayV2.sol`) iterates `order.inputs` and, for any non-zero address, calls: [1](#0-0) 
which pulls the token via `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)`. There is no check that `token` implements the ERC20 interface, no `decimals()`/ERC165 sanity check, and no restriction preventing `amount` from being interpreted as an NFT `tokenId`.

`SafeERC20.safeTransferFrom` (OpenZeppelin) treats any call that succeeds with empty return data as a success. ERC721's `transferFrom(address,address,uint256)` has the exact same selector/signature as ERC20's, but returns no value — so if the caller owns (or has approved) `tokenId == order.inputs[i].amount` of an ERC721 contract at `token`, the deposit call succeeds and the NFT is transferred into the `IntentGatewayV2`/`IntentsBase` contract. The escrow ledger is credited via `_orders[commitment][token] = reducedInputs[i].amount` treating the tokenId as a fungible balance.

The withdrawal path, `_withdraw` in `evm/src/apps/intentsv2/IntentsBase.sol`, unconditionally calls: [2](#0-1) 
`IERC20(token).safeTransfer(beneficiary, amount)`. ERC721 has no `transfer(address,uint256)` function (selector `0xa9059cbb`) and no fallback to catch it, so this call reverts unconditionally. Since `_withdraw` is the single code path used for cancellation, refunds, and settlement (`RedeemEscrow`/`RefundEscrow` via `onAccept`, and `onGetResponse`), every attempt to release this escrow entry — refund to the user or payout to the solver — reverts, permanently freezing the escrowed NFT (and, since the loop iterates all `body.tokens` and reverts the whole withdrawal on any single failure, it can also block release of any other legitimately-escrowed tokens bundled in the same order).

The same unchecked-token pattern also lets the *output* side of a fill (`order.output.assets`, consumed by `_fillSameChain`/`_fillCrossChain` via `safeTransferFrom`) be poisoned by a solver, though the primary freezing risk is on the input/escrow side since that's the value locked in the contract long-term.

### Impact Explanation
This causes permanent freezing of user/solver funds escrowed in `IntentGatewayV2`. A user (or a malicious actor crafting an order against another party's expected flow) can lock any ERC721 they control into the gateway with no way to ever retrieve it via `cancelOrder`, `fillOrder`-triggered settlement, or timeout/refund — every path funnels through `_withdraw`'s `safeTransfer`, which reverts for the NFT contract. This meets the "permanent freezing of funds" bar for a valid finding, matching the External Report's bug class (ERC721 registered as ERC20 collateral → unliquidatable/un-withdrawable position).

### Likelihood Explanation
Reachable directly by any unprivileged caller of `placeOrder` with a single transaction — no special privileges, governance, or auxiliary conditions are required, only that the caller own/approve an ERC721 whose `tokenId` fits in `uint256` (always true). No dispatcher/relayer/consensus proof involvement is needed to trigger the deposit-side success or the later revert.

### Recommendation
Validate that `TokenInfo.token` addresses are genuine ERC20 contracts before accepting them as escrow inputs — e.g., require a successful `balanceOf`/`decimals()` call, or explicitly check that the contract does not support `IERC721`/`IERC1155` via ERC165 (`supportsInterface`). Alternatively, harden the withdrawal path itself: wrap `_withdraw`'s external token transfer in a low-level call with try/catch (or a per-token isolation pattern) so a single malformed/non-standard token cannot brick the release of an entire withdrawal batch, and expose an escape-hatch/rescue function gated appropriately for tokens that fail standard ERC20 semantics.

### Proof of Concept
1. Attacker owns ERC721 `NFT` and holds `tokenId = 7`.
2. Attacker calls `NFT.approve(intentGateway, 7)`.
3. Attacker calls `IntentGatewayV2.placeOrder(order, graffiti)` with `order.inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(NFT)))), amount: 7})` and any valid `order.output`.
4. `placeOrder`'s deposit loop executes `IERC20(NFT).safeTransferFrom(attacker, gateway, 7)` — this matches ERC721's `transferFrom(address,address,uint256)` selector, succeeds with empty return data, and the NFT (tokenId 7) is transferred to the gateway. `_orders[commitment][NFT] = 7` is recorded as escrow.
5. Time passes past `order.deadline`; attacker (or anyone after deadline) calls `cancelOrder` to reclaim the escrow, or a solver fills the order and the settlement message calls `_withdraw`.
6. `_withdraw` executes `IERC20(NFT).safeTransfer(beneficiary, 7)`. Since `NFT` (ERC721) has no `transfer(address,uint256)` function, the low-level call reverts, and `SafeERC20` bubbles the revert. The entire withdrawal transaction reverts — the NFT (and any other tokens bundled in the same withdrawal call) remains stuck in the gateway permanently, with no code path able to move it out.
