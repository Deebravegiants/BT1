### Title
Webhook `shop` (tenant identity) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop` value that identifies which tenant/store the webhook belongs to is taken from an HTTP header that is never included in the signed payload. This breaks the intended binding `HMAC(secret, signed_bytes) == verified` should equal `shop_used_by_handler == shop_that_generated_the_signed_bytes`.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) [2](#0-1) 

`to_signable_string` returns only `@raw_body`; the `shop-domain` header is parsed independently via `shopify_header("shop-domain")` and is never folded into the bytes that get HMAC-verified. `Registry.process` verifies the HMAC and then immediately trusts `request.shop` to build the metadata handed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` only checks `verifiable_query.to_signable_string` against `verifiable_query.hmac`: [4](#0-3) 

Since the signable string is the body alone, the `hmac-sha256` header cryptographically proves only "this body was produced by Shopify for *some* legitimate webhook delivery to this app," not "this body was produced for shop X." An attacker who controls a shop that has the app installed (an ordinary, unprivileged merchant/tenant of the app — no special credentials required) receives genuine, correctly-signed webhook deliveries for their own store. They can capture a `(raw_body, hmac-sha256)` pair from their own legitimate webhook and resend it to the app's webhook endpoint with the `x-shopify-shop-domain` / `shopify-shop-domain` header changed to a victim shop's domain. `HmacValidator.validate` still succeeds (it never looked at the header), and `Registry.process` calls the handler with `shop: request.shop` set to the attacker-chosen victim domain.

### Impact Explanation
Any host application that uses the gem's documented `shop` field from `WebhookMetadata` to select which merchant's data/session to act upon (the intended and expected usage pattern per the gem's own webhook docs) can be made to process attacker-supplied webhook content under a victim shop's identity. Depending on the webhook topic and handler logic, this is a cross-tenant data/state corruption vector: e.g., a `customers/redact`, `app/uninstalled`, `orders/*`, or custom topic handler could execute victim-shop-scoped side effects (deleting data, revoking access, mutating order/customer state) triggered entirely by an attacker who only controls their own store. This satisfies the "cross-tenant access" Critical impact category, since the trust boundary between tenants is defined by exactly this `shop` binding, which the gem fails to authenticate.

### Likelihood Explanation
High. Any developer/customer of the app (an unprivileged internet user with respect to other tenants) can install the app on a shop they control, capture one legitimate webhook delivery (trivial — just log the raw body + `hmac-sha256` header, which they can observe from their own server), and replay it with a forged `shop-domain` header. No secrets, tokens, or privileged access to Shopify or the app are required, and no interaction from the victim is needed.

### Recommendation
Include the tenant-identifying header(s) (`shop-domain`, and ideally `topic`/`webhook-id`) in the bytes that are HMAC-verified, or otherwise cryptographically bind `shop` to the verified payload before it is handed to `Registry.process`'s caller. At minimum, document (and preferably enforce in `Request`/`Registry`) that `shop` must be independently corroborated against a known-installed shop record before being trusted for tenant-scoped side effects, since it is presently unauthenticated header data.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" with the app installed.
# They capture a legitimate delivery from Shopify to their own endpoint:
raw_body = '{"id":123,"note":"legit order update"}'
hmac_b64 = "<value of x-shopify-hmac-sha256 header from the real, valid delivery>"

# The HMAC was computed by Shopify only over raw_body, using the app's secret.
# Replay it, but swap the shop-domain header to the victim's shop:
forged_headers = {
  "x-shopify-topic"        => "orders/updated",
  "x-shopify-hmac-sha256"  => hmac_b64,          # unchanged, still valid for raw_body
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com", # forged
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# Passes HMAC validation because it only checks raw_body:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# Registry.process happily invokes the handler as "victim-shop.myshopify.com":
ShopifyAPI::Webhooks::Registry.process(request)
# handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...))
```
