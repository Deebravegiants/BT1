### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook replay - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates the webhook's HMAC and then dispatches the payload to the app's handler using the shop identity taken from an HTTP header (`shopify-shop-domain`) that is never included in the signed material. `ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, and `hmac` is computed over that body alone, while `shop`, `topic`, and `webhook_id` are read straight from headers with no binding to the signature.

### Finding Description
`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw request body: [2](#0-1) 

`shop`, `topic`, and `webhook_id` are pulled from headers with no cryptographic tie to the HMAC: [3](#0-2) 

`Registry.process` verifies the HMAC and then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`) to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The equality this breaks is: **shop authenticated by the HMAC (over the body) ≠ shop attributed to the request (from the unsigned header)**. Because the signature never binds `shop-domain` to the body, any request that carries a *valid* body+HMAC pair for topic T (a pair the attacker can legitimately obtain by installing the target app on their own shop and receiving a real Shopify-signed webhook delivery for that topic) can be replayed against the app's webhook endpoint with the `shop-domain` header swapped to a victim shop. `HmacValidator.validate` still passes because it never inspects the header, and the handler executes with `data.shop` set to the victim's domain — a cross-tenant identity confusion entirely internal to this gem's webhook processing path.

### Impact Explanation
An attacker who has a working installation of the target app (even a free/trial shop) can capture a legitimately signed webhook (body + `x-shopify-hmac-sha256`) for any subscribed topic, then replay it to the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` value. Since `Registry.process` only checks the HMAC of the body and blindly trusts the shop header for tenant attribution, the app will process attacker-controlled webhook content under another (victim) tenant's identity — e.g., updating state keyed by the victim shop, or triggering handler logic scoped to the victim's session/data. This is a cross-tenant access vector rooted in a broken authentication binding.

### Likelihood Explanation
Likelihood is moderate to high: the attacker only needs their own working app installation (trivially obtainable by installing on a dev/trial store) to harvest one valid signed webhook payload per topic of interest, and a way to send raw HTTP requests to the app's public webhook endpoint (which must be internet-reachable by design). No secrets, tokens, or privileged access are required.

### Recommendation
Bind the shop identity (and topic/webhook id) into the HMAC-verified material, or otherwise cross-check the header-derived `shop` against a value independently known to the app before trusting it (e.g., verify the webhook subscription/shop pairing recorded at registration time, or require the shop domain to appear inside the signed body payload as Shopify's payload itself typically includes shop-scoped identifiers). At minimum, document that `request.shop` is unauthenticated and must not be used as the sole tenant key without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook of topic `orders/create`; Shopify delivers a POST with a valid body `B` and header `x-shopify-hmac-sha256: HMAC(B)`.
2. Attacker resends the exact same body `B` and HMAC header to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)` [5](#0-4)  — this passes because it only checks `B` against the HMAC.
4. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` using `shop = "victim-shop.myshopify.com"` even though the payload actually originated from the attacker's own shop, corrupting per-tenant processing.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
