### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop` value that is subsequently handed to the app's webhook handler is read from the `X-Shopify-Shop-Domain` HTTP header, which is never included in the HMAC-signed data. This breaks the identity binding `HMAC-verified bytes == attributed tenant (shop)`: the bytes verified (body only) are not the bytes used to determine which merchant/tenant the event belongs to.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

`shop` is derived independently from the `shopify-shop-domain` / `x-shopify-shop-domain` header, a completely separate, unauthenticated channel: [2](#0-1) 

`Utils::HmacValidator.validate_signature` computes the HMAC exclusively over `to_signable_string` (i.e., the body), and compares it against the `hmac-sha256` header value: [3](#0-2) 

`Registry.process` uses this same-body HMAC check as the sole authentication gate, then trusts `request.shop` (the unsigned header) when constructing `WebhookMetadata` passed to the app's handler: [4](#0-3) 

Because the `shop-domain` header sits entirely outside the signed payload, any request with a *body* that has a valid HMAC (computed with the app's `client_secret`) will pass verification regardless of what `shop-domain` header accompanies it. A holder of one legitimately-signed webhook body/HMAC pair (e.g., an attacker who runs their own store using the same app and receives real webhooks for their own shop) can resend that exact body and HMAC while substituting an arbitrary victim shop domain in the header. `Registry.process` will accept it as authentic and dispatch it to the handler tagged with the attacker-chosen `shop`, causing the app to process/store data as if it came from the victim tenant — a cross-tenant identity confusion.

### Impact Explanation
This crosses the tenant boundary the HMAC is meant to enforce: `HmacValidator.validate` only proves "this body was sent by someone who knows `client_secret`," not "this body originated from the shop named in the header." Any app handler that keys its database writes/reads or triggers privileged actions off `WebhookMetadata#shop` (which nearly all handlers do, since that's the documented API — see `handler.handle(data: WebhookMetadata.new(... shop: request.shop ...))`) can be made to attribute attacker-controlled payload content to a shop the attacker does not own, i.e., cross-tenant access/injection.

### Likelihood Explanation
The attacker needs no privileged credential (`api_secret_key`, access token, etc.) belonging to the victim. They only need one valid signed body from any shop that legitimately uses the same app (including their own store, or a webhook body they can otherwise observe), which they can trivially obtain by triggering any webhook-emitting action in their own store. They then replay it with a forged `shop-domain` header.

### Recommendation
Include the shop domain (and ideally topic) in the HMAC-signable string for webhooks, or otherwise cryptographically bind the `shop-domain` header to the signed body before trusting it for tenant attribution in `Registry.process`/`WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw body `B` and the resulting `X-Shopify-Hmac-Sha256: H` header, which is valid because `H = HMAC(client_secret, B)`.
2. Attacker resends an HTTP POST to the app's webhook endpoint with the same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `to_signable_string` (= `B`) only, and it matches `H` — verification succeeds.
4. `request.shop` returns `"victim.myshopify.com"` (from the header), and `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: parsed(B), ...)` is dispatched to the app's handler, which processes attacker-supplied data under the victim shop's identity.
