### Title
Webhook `shop` Identity Not Bound to HMAC-Verified Payload, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the tenant identity (`shop`) used to dispatch the webhook to application handlers is read from an unauthenticated HTTP header. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then trusts `request.shop` unconditionally when building the `WebhookMetadata` passed to the app's handler, so the "which shop is this event for" binding is never covered by the cryptographic check.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shop-domain` header without any cross-check against the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` calls `verifiable_query.to_signable_string` (i.e., the raw body) and HMACs it with `Context.api_secret_key`, comparing to the `hmac` header: [3](#0-2) 

`Registry.process` validates only this body-bound HMAC, then forwards `request.shop` (the untrusted header) directly into `WebhookMetadata` used by the app's handler: [4](#0-3) 

The equality the gem actually enforces is:
`HMAC_sha256(api_secret_key, raw_body) == received_hmac`

The equality that is *not* enforced, but is required to bind the event to the correct tenant, is:
`shop_header == shop_bound_inside(raw_body_or_signature)`

Because the `shop-domain` header sits entirely outside the signed content, any two (body, hmac) pairs that are ever legitimately produced by Shopify for *any* shop the attacker controls (e.g., their own installed shop, which they can freely trigger topics/webhooks for) can be replayed verbatim against the app's public webhook endpoint with the `shop-domain` header rewritten to name a different, victim shop. `HmacValidator.validate` will still succeed, since it validates the body only, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event originates from the victim shop.

### Impact Explanation
This breaks the tenant/shop identity binding on a security boundary that application handlers rely on to scope side effects (e.g., persisting order/customer data, triggering per-shop business logic, updating stored session/webhook state keyed by `shop`) — the gem is the only guardrail apps have here since it validates the HMAC and hands `shop` to the handler as a trusted value. An attacker (an unprivileged internet user who is a merchant installing the app on their own store, hence able to generate a legitimately-signed webhook body/HMAC pair) can cause the vulnerable app to attribute attacker-controlled webhook data to an arbitrary victim shop, which matches the "cross-tenant access" class of impact.

### Likelihood Explanation
Exploitation requires only: (1) installing the target app on an attacker-owned shop to obtain a real `(raw_body, hmac)` pair for a chosen topic, and (2) sending a raw HTTP POST to the same app's public webhook endpoint with that body/HMAC and an attacker-chosen `x-shopify-shop-domain` header. No access to the app's `api_secret_key`, tokens, or any privileged account for the victim shop is required, and no TLS interception is needed since the forged request is sent directly by the attacker.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) into the value that is HMAC-verified, or otherwise require the application layer to correlate `request.shop` against session/subscription state before trusting it (e.g., verify the shop against a previously-registered subscription for that specific `webhook_id`), rather than handing the raw header value straight to `WebhookMetadata` once only the body's HMAC has been checked.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com`; trigger a webhook (e.g., `orders/create`) and capture the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header `H` that Shopify sends (`H = HMAC_SHA256(api_secret_key, B)`).
2. Send a new HTTP POST directly to the same app's webhook endpoint with:
   - Body: `B` (unchanged)
   - `X-Shopify-Hmac-Sha256: H` (unchanged)
   - `X-Shopify-Topic: orders/create` (unchanged)
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (attacker-chosen)
3. `Utils::HmacValidator.validate` succeeds because it only hashes `B`.
4. `Registry.process` dispatches to the registered handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the event body actually belongs to `attacker-shop.myshopify.com`.
