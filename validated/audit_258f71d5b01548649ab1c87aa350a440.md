### Title
PoA Bridge `describeWithdrawal` misreports withdrawal status/hash when a batch contains multiple withdrawals of the same token - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal` and the underlying `findMatchingWithdrawal` helper identify a specific withdrawal in a batch **only by `assetId`**, ignoring the caller-supplied `index`/`destinationAddress`/`amount`. When a single batched intent contains two or more withdrawals of the *same* token (e.g. two USDC withdrawals to two different destination addresses in one `processWithdrawal` batch call, which the SDK explicitly supports), both withdrawal identifiers resolve to the same (first) matching record returned by the PoA API. This breaks the equality "status/hash reported for withdrawal N == on-chain outcome of withdrawal N."

### Finding Description
The SDK supports batch withdrawals via `sdk.processWithdrawal({ withdrawalParams: [...] })`, which internally calls `createWithdrawalIdentifiers` to build one `WithdrawalIdentifier` (with per-route `index`) per withdrawal [1](#0-0) , and then polls each one independently via `watchWithdrawal` → `bridge.describeWithdrawal(wid)` [2](#0-1) .

For the PoA route, `describeWithdrawal` fetches the full withdrawal-status response and matches the correct entry using only `assetId`, explicitly commenting that the response is "unsorted" so it deliberately avoids using `index`: [3](#0-2) 

The matching function itself confirms the same-token-in-one-tx limitation is a known, accepted gap: [4](#0-3) 

`Array.prototype.find` returns only the first element whose `near_token_id` matches; if the batch contains two withdrawals of the same `assetId` (different `destinationAddress`/`amount`), `describeWithdrawal` invoked for index 0 **and** index 1 will both resolve to whichever record the PoA API happens to list first. There is no correlation by `destinationAddress`, `amount`, or `index` to disambiguate.

### Impact Explanation
Because both withdrawal slots collapse onto the same underlying record, an integrator polling per-withdrawal status (e.g., via `waitForWithdrawalCompletion` with an array of `withdrawalParams`, or `createWithdrawalCompletionPromises`) can receive:
- A `{status: "completed", txHash: X}` for withdrawal #2 where `X` is actually the destination transaction hash belonging to withdrawal #1 (a different destination address/amount), or
- Both withdrawals reported "completed" with the identical `txHash`, even though only one of the two on-chain transfers has actually settled.

This is a status/hash misreport that can cause a downstream integrator to credit or reconcile the wrong destination address/amount, or to treat a withdrawal as settled/refundable prematurely — matching the High severity category "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
This requires no malicious actor — it is triggered by a normal, SDK-supported usage pattern: a legitimate user or integrator batching two withdrawals of the same asset (same `nep141:...` assetId) to two different destinations within one `processWithdrawal`/`signAndSendWithdrawalIntent` call, which is a documented feature (`Batch Withdrawals` in the SDK README) [5](#0-4) . Nothing in `createWithdrawalIdentifiers` or `PoaBridge` prevents or warns against this input; the collision is silent.

### Recommendation
Disambiguate PoA withdrawal matching using more than `assetId`: correlate by `destinationAddress` and `amount` (and ideally an index/ordering guarantee) in `findMatchingWithdrawal` (`packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`) and in `PoaBridge.describeWithdrawal` (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`). At minimum, detect the ambiguous case (multiple same-asset withdrawals in one intent tx) and either reject/queue such batches distinctly per-destination, or require the PoA API to return an index/withdrawal-id that can be threaded through `WithdrawalIdentifier`.

### Proof of Concept
1. Call `sdk.processWithdrawal` (or `signAndSendWithdrawalIntent` + `waitForWithdrawalCompletion`) with `withdrawalParams = [ {assetId: "nep141:usdt...omft.near", amount: 100, destinationAddress: A}, {assetId: "nep141:usdt...omft.near", amount: 200, destinationAddress: B} ]`.
2. `createWithdrawalIdentifiers` assigns `index: 0` and `index: 1` to the two PoA withdrawal identifiers [6](#0-5) .
3. Once only the first (A→100) settles on the PoA bridge side, `PoaBridge.describeWithdrawal` for **both** `index: 0` and `index: 1` calls `findMatchingWithdrawal(response.withdrawals, "nep141:usdt...omft.near")`, which returns the same first-match record (A→100, `COMPLETED`) for both calls [3](#0-2) .
4. `waitForWithdrawalCompletion` resolves the withdrawal destined for `B` as `{status: "completed", txHash: <A's tx hash>}` even though B's transfer has not occurred, misreporting completion/hash for the wrong destination.

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}
