### Title
Webhook `shop-domain` header is not covered by HMAC verification, allowing shop-spoofed webhook delivery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook by validating only the HMAC of the raw request body, then trusts the `shop-domain` HTTP header verbatim to build the `WebhookMetadata` passed to the app's handler. The `shop` field is acted upon (used as the tenant identifier for the webhook) but is never included in the HMAC-signed material, breaking the intended binding `hmac(secret, signed_bytes) == hmac(secret, X-Shopify-Shop-Domain + body)`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

while `shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic tie to the signature: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature exclusively over `to_signable_string` (i.e., the body) and compares it against the `hmac-sha256` header: [3](#0-2) 

`Webhooks::Registry.process` then trusts `request.shop` for tenant attribution after this body-only check passes: [4](#0-3) 

and forwards it into `WebhookMetadata`, which is documented as "The shop domain of the webhook" and is explicitly the value host apps are expected to use to key work to a tenant (e.g., "shop_domain: data.shop" in the gem's own webhooks documentation): [5](#0-4) [6](#0-5) 

The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify" — but the verification only proves the *body* bytes are unmodified and were signed with the app's secret; it proves nothing about which shop the payload is for: [7](#0-6) 

This is exactly the "field acted on but not covered by the HMAC" identity-binding gap: for a given valid `(raw_body, hmac)` pair, the `shop-domain` header can be swapped to any other merchant's domain and `HmacValidator.validate` still returns `true`, since it never sees the header value.

### Impact Explanation
This crosses a tenant boundary within the gem's own trust decision: `Registry.process` is the gem's sanctioned mechanism for authenticating a webhook and identifying its shop before invoking the app's handler. Because `shop` is un-bound to the signature, an attacker who can capture or reconstruct one legitimate `(raw_body, hmac)` pair (e.g., via a shared or compromised webhook proxy/log, replay through a public endpoint, or any scenario where the byte content is knowable/predictable) can resubmit it with an arbitrary `shop-domain` header and have the gem hand the app a `WebhookMetadata` claiming to originate from a different shop. Any app that keys persistence, side effects, or authorization decisions off `data.shop` (as the gem's own documentation instructs) will attribute attacker-chosen data to the wrong merchant — a cross-tenant data/action confusion.

### Likelihood Explanation
Exploitation requires the attacker to already possess or be able to reconstruct a valid `(body, hmac)` combination signed with the app's `api_secret_key`, which is realistically only within reach of someone who has observed at least one legitimate webhook delivery (e.g., through a non-TLS-terminated proxy, logging misconfiguration, or a predictable/fixed-shape payload) rather than someone with no prior visibility into any webhook traffic. This limits practical likelihood, but the underlying binding failure is unconditional and 100% reproducible in the gem's own code — no host-application misuse of documented API is required, since `Registry.process` faithfully implements the documented behavior and still exposes the gap.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook_id`, `api_version`) header values in the HMAC-signed material, or otherwise cryptographically bind the shop identity to the signature check in `Utils::HmacValidator`/`Webhooks::Request#to_signable_string`, so that tampering with the `shop-domain` header invalidates the signature.

### Proof of Concept
1. Attacker captures/observes one legitimate webhook delivery for `shop-a.myshopify.com`: raw body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(secret, B)`.
2. Attacker resends the same `B` and `H` to the app's webhook endpoint but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "shop-b.myshopify.com", "x-shopify-hmac-sha256" => H, ...})` is constructed.
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(secret, B)` — identical to `H` — and passes, since `shop-domain` never enters `to_signable_string`.
5. `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "shop-b.myshopify.com", body: JSON.parse(B), ...))` is invoked, and the app processes `B`'s content as if it belongs to `shop-b`, even though it was never signed for `shop-b`.
