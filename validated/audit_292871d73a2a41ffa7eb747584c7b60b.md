## Title
Tron `IntentGatewayV2.withdraw()`/dust-sweep only check low-level call success, not the ERC20 return value, silently losing escrowed funds for non-compliant tokens - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` moves ERC20/TRC20 tokens out of escrow using a raw low-level `.call` with the `IERC20.transfer` selector, and only checks that the call itself did not revert (`success`). It never inspects/decodes the returned boolean. Non-standard tokens (most notably USDT on Tron, TRC20-USDT, which is exactly the class of token flagged in the referenced report) can return `false` on a failed transfer instead of reverting. Because `success` is `true` for such a call, the contract proceeds as if the transfer succeeded, permanently decrementing the escrow accounting and emitting success events, while the beneficiary never actually receives the tokens.

### Finding Description
In `withdraw()`, `onAccept()` (`SweepDust` branch), and the fee-redemption path, transfers are performed like this: [1](#0-0) 

```solidity
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}

_orders[body.commitment][token] -= amount;
```

and identically in the `SweepDust` handler: [2](#0-1) 

Unlike every other transfer path in the codebase, which uses OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom` (which correctly treats empty returndata as success but requires `true` when returndata is non-empty), these three sites use a bare `.call` and check only `success` — i.e., whether the call reverted — never validating the decoded boolean return value. A token whose `transfer` implementation returns `false` on failure (rather than reverting) will make `success == true` even though no tokens moved. This is exactly the token-compliance class called out in the referenced Sherlock report (non-standard `transfer`/`transferFrom` semantics causing incorrect assumptions about success), just manifesting in the opposite failure mode: instead of a revert breaking usage, a silent `false` return is misinterpreted as success.

Elsewhere in the same file (`placeOrder`), deposits correctly use `safeTransferFrom`: [3](#0-2) 

confirming that the withdrawal-path calls in `withdraw()`/`SweepDust` are an inconsistent, unsafe deviation from the rest of the contract.

### Impact Explanation
`withdraw()` is invoked from `onAccept()` for `RedeemEscrow`/`RefundEscrow` requests and from `onGetResponse()`, both callable by any relayer who submits a valid cross-chain message/proof to the ISMP host — this is the standard, unprivileged intents-fulfillment path, not an admin-only function: [4](#0-3) 

If the escrowed token misbehaves (returns `false` instead of reverting on a failed transfer — e.g. due to an allowance/balance edge case, blacklist, or pausing logic in the token), the escrow ledger (`_orders[commitment][token]`) is decremented and `EscrowReleased`/`EscrowRefunded`/`DustSwept` are emitted as if the beneficiary was paid, while the tokens remain stuck in the `IntentGatewayV2` contract. Because the escrow mapping is zeroed, there is no legitimate way to retry or reclaim the funds — this is a permanent freezing/loss of user funds, satisfying the Medium severity bar (concrete permanent freezing of escrowed funds reachable from a single relayed message).

### Likelihood Explanation
Likelihood is moderate: it requires escrowing a token on Tron whose `transfer` can return `false` without reverting under some condition. This is a real and common pattern for TRC20 tokens on Tron (mirroring the exact USDT non-standard-return concern raised in the original report), and any solver/relayer can trigger the withdrawal path with ordinary intents usage — no privileged role required.

### Recommendation
Replace the raw `.call` + `success`-only checks in `withdraw()` and the `SweepDust` handler with `SafeERC20.safeTransfer` (already imported and used via `using SafeERC20 for IERC20;` in this same file), which correctly validates both call success and the decoded boolean return value (or absence thereof for non-compliant tokens):

```solidity
IERC20(token).safeTransfer(beneficiary, amount);
```

Apply the same fix to the fee-token transfer and dust-sweep transfer in this file.

### Proof of Concept
1. Configure/escrow a TRC20 token whose `transfer(to, amount)` implementation returns `false` (instead of reverting) when, e.g., `to` is blacklisted or some internal condition fails, while still returning normally (not reverting) — a legitimate pattern for several TRC20 tokens.
2. User calls `placeOrder` with this token as input; tokens are escrowed via `safeTransferFrom` (works fine).
3. A relayer delivers a valid `RedeemEscrow` message; `onAccept` calls `withdraw()`.
4. Inside `withdraw()`, `token.call(...)` succeeds (`success == true`) even though the token's `transfer` internally returned `false` and did not move funds to `beneficiary`.
5. `_orders[commitment][token] -= amount` zeroes the escrow record, and `EscrowReleased` is emitted — the beneficiary never received the tokens, and the escrow accounting no longer reflects the outstanding balance, permanently freezing the funds inside the `IntentGatewayV2` contract with no recovery path.
