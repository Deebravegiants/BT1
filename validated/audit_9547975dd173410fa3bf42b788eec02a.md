### Title
Webhook shop identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying the HMAC of the request body, then unconditionally trusts the `shop-domain` header to identify which merchant the payload belongs to. Because the HMAC signature never covers the shop-domain value, any party who can produce one validly-signed webhook body (e.g., a malicious merchant receiving genuine webhooks for their own shop) can replay that exact body/HMAC pair while substituting a different shop's domain in the header, causing the handler to process the payload as if it originated from the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

The `shop` accessor, however, is read straight from the `shop-domain` header, which is completely outside the signed payload: [2](#0-1) 

`HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` (the body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` performs this HMAC check and then, without any further validation, builds the `WebhookMetadata` passed to the app's handler using `request.shop`: [4](#0-3) 

The identity binding that should hold is:
`shop authenticated by HMAC == shop delivered to handler as WebhookMetadata#shop`

but in this code the equality actually enforced is only:
`HMAC(body) == received hmac header`

with the `shop-domain` header entirely unauthenticated. Since `api_secret_key` is the app's single `client_secret`, shared across every merchant who installs the app (it is not a per-shop secret), a merchant who has installed the app can capture one of their own genuine, validly-HMAC-signed webhook deliveries and replay the identical `raw_body`/`hmac` pair to the app's webhook endpoint while changing only the `x-shopify-shop-domain` (or `shopify-shop-domain`) header to a victim shop's domain. The HMAC check still passes because it never inspects that header, and the handler receives a `WebhookMetadata` claiming the payload is from the victim shop.

### Impact Explanation
This breaks tenant isolation (cross-tenant access), a Critical-impact class under the assessment rules. Any app that keys internal actions off of `WebhookMetadata#shop` (order/customer data updates, redaction webhooks, entitlement or subscription changes, GDPR mandatory webhooks such as `customers/redact`, `customers/data_request`, `shop/redact`) can be made to apply attacker-chosen webhook content to an arbitrary victim shop's data/state, using nothing but the attacker's own valid webhook traffic and knowledge of the victim's shop domain (which is often public, e.g., `victim.myshopify.com`).

### Likelihood Explanation
Likelihood is high for any unprivileged party who can install the app on their own store (a normal, low-privilege action for a Shopify app) since they will naturally receive real webhooks with a valid HMAC for their own shop and can freely re-send that exact body with a modified shop header to the app's public webhook endpoint. No secret material beyond what Shopify already delivers to the merchant is needed.

### Recommendation
Bind the shop identity into the authenticated material, e.g. have the HMAC validator/signable string incorporate the `shop-domain` header (or otherwise cryptographically bind topic/shop/webhook-id to the signature) so a captured payload cannot be replayed under a different shop identity, and/or cross-check `request.shop` against an expected, session-bound value before dispatching to handlers.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Shopify sends the attacker a genuine webhook, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the shared `api_secret_key`), and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker resends the same request to the app's webhook endpoint but replaces the header with `x-shopify-shop-domain: victim-shop.myshopify.com`, keeping body `B` and HMAC `H` unchanged.
4. `Utils::HmacValidator.validate` recomputes HMAC over `B` and matches `H` — validation passes [5](#0-4) .
5. `Registry.process` builds `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)` and invokes the app's handler as if the payload legitimately came from `victim-shop.myshopify.com` [6](#0-5) .
