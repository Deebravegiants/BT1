### Title
Banned/deactivated LDAP user retains full API access via cached API token until periodic upstream sync purges it - ([File: core/sessions/ldapauth/ldap.go])

### Summary
In the LDAP authentication provider, interactive session-based login (`FindUser`) explicitly re-validates a user's "active" status against the upstream LDAP server on every request, but the API-token-based authentication path (`FindUserByAPIToken`) does not perform this check at all. It only checks whether the locally cached token row has expired based on a time-to-live, not whether the underlying account has been disabled/deactivated upstream.

### Finding Description
`FindUser` (interactive/session login path) calls `l.validateUsersActive([]string{email})` and rejects the user if the upstream LDAP "active" attribute indicates they are no longer active: [1](#0-0) 

By contrast, `FindUserByAPIToken`, which is invoked on every API-token authenticated request via `AuthenticateByToken`, only queries the locally cached `ldap_user_api_tokens` table and checks a TTL-based expiry (`created_at + duration >= now()`). It performs no upstream active/ban-state check whatsoever: [2](#0-1) 

This cached token/role is only reconciled against the true upstream user state by the asynchronous `LDAPServerStateSyncer.Work` reaper, which purges tokens for users no longer present upstream and updates cached roles — but this runs only on a configurable timer (`UpstreamSyncInterval`), not per-request: [3](#0-2) [4](#0-3) 

The path this token flows through at request time is the API auth middleware, which trusts whatever `FindUserByAPIToken` returns without any additional active-state gate: [5](#0-4) 

This mirrors the HackerOne report's bug class: a previously-valid credential (API token) continues to grant full account access after the underlying account has been banned/deactivated, because the deactivation is not synchronously enforced on the token-authenticated path — only asynchronously, on a timer, and only on the session/interactive path is it enforced immediately.

Note: the sync reaper purges tokens only for users who are entirely absent from the upstream user map (i.e., removed from all LDAP groups), and separately updates role for users still present — it is not fully clear from the available code whether an "active=false" (deactivated but still group-member) upstream user is purged from `ldap_user_api_tokens` by `Work`, versus only role-synced. This distinction affects exact severity but does not change the core finding: `FindUserByAPIToken` itself never checks the active attribute, unlike `FindUser`.

### Impact Explanation
A deactivated/banned LDAP user (e.g., removed from the org, suspended, terminated employee) whose account is disabled upstream retains full API access — including whatever role/permissions were cached (Admin/Edit/Run/View) — until the next scheduled sync cycle runs and either purges the stale token or the token's own configured TTL expires. Depending on `UpstreamSyncInterval` and `UserAPITokenDuration` configuration, this window could be extended, allowing continued unauthorized access to node operations, job data, or read/write actions matching the cached role.

### Likelihood Explanation
Likelihood is moderate: it requires (1) LDAP authentication to be enabled and configured with API token support (`UserApiTokenEnabled`), (2) a user having previously created an API token before being deactivated, and (3) the deactivation happening between sync cycles. Since this is an intentional security control gap (deliberately checked on session path but omitted on token path) rather than a race condition, exploitation is deterministic and reliable for the duration of the sync/token TTL window — the operator does not need to do anything special to trigger it.

### Recommendation
Add an upstream active-status check to `FindUserByAPIToken`, mirroring the check already performed in `FindUser` (`validateUsersActive`), or reduce the trust window by having the token authentication path revalidate against a short-lived active-status cache rather than relying solely on TTL expiry and the periodic reaper. Alternatively, shorten `UpstreamSyncInterval` defaults and ensure `Work` unconditionally purges tokens for any user found to have `active=false`, not just users absent from the upstream group map.

### Proof of Concept
1. Configure Chainlink node with LDAP auth (`ActiveAttribute` set) and `UserApiTokenEnabled = true`.
2. As a valid LDAP user, log in and generate an API token via `SetAuthToken`/`CreateAndSetAuthToken`.
3. Have an administrator deactivate the user upstream (set the LDAP active attribute to false) without removing them from their groups.
4. Attempt interactive login with the user's session credentials — `FindUser` correctly rejects due to `validateUsersActive` returning false: [6](#0-5) .
5. Instead, call any API endpoint using the previously issued `X-API-KEY`/`X-API-SECRET` headers, hitting `AuthenticateByToken` → `FindUserByAPIToken`: [7](#0-6) .
6. Observe the request succeeds because `FindUserByAPIToken` only checks token TTL, not active status: [8](#0-7) , granting full access with the user's last-cached role until the next `LDAPServerStateSyncer.Work` cycle runs.

// FindUserByAPIToken retrieves a possible stored user and role from the ldap_user_api_tokens table store
func (l *ldapAuthenticator) FindUserByAPIToken(ctx context.Context, apiToken string) (sessions.User, error) {
	if !l.config.UserApiTokenEnabled() {
		return sessions.User{}, errors.New("API token is not enabled ")
	}

	// Query the ldap user API token table for given token, user role and email are cached so
	// no further upstream LDAP query is performed, sessions and tokens are synced against the upstream server
	// via the UpstreamSyncInterval config and reaper.go sync implementation
	var foundUserToken struct {
		UserEmail string
		UserRole  sessions.UserRole
		Valid     bool
	}
	err := l.ds.GetContext(ctx, &foundUserToken,
		"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM ldap_user_api_tokens WHERE token_key = $1",
		apiToken, l.config.UserAPITokenDuration().Duration(),
	)
	if err != nil {
		return sessions.User{}, err
	}
	if !foundUserToken.Valid { // API Token expired, purge
		if _, execErr := l.ds.ExecContext(ctx, "DELETE FROM ldap_user_api_tokens WHERE token_key = $1", apiToken); execErr != nil {
			l.lggr.Errorf("error purging stale ldap API token session: %v", execErr)
		}
		return sessions.User{}, sessions.ErrUserSessionExpired
	}

	return sessions.User{
		Email: foundUserToken.UserEmail,
		Role:  foundUserToken.UserRole,
	}, nil
}

func AuthenticateByToken(c *gin.Context, authr Authenticator) error {
	ctx := c.Request.Context()
	token := &auth.Token{
		AccessKey: c.GetHeader(APIKey),
		Secret:    c.GetHeader(APISecret),
	}
	if token.AccessKey == "" {
		return auth.ErrorAuthFailed
	}

	if token.Secret == "" {
		return auth.ErrorAuthFailed
	}

	// We need to first load the user row so we can compare tokens using the stored salt
	user, err := authr.FindUserByAPIToken(ctx, token.AccessKey)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) || errors.Is(err, clsessions.ErrUserSessionExpired) {
			return auth.ErrorAuthFailed
		}
		return err
	}

	ok, err := clsessions.AuthenticateUserByToken(token, &user)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionUserKey, &user)

	return nil
}
