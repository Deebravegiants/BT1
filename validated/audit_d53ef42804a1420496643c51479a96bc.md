### Title
Webhook `shop-domain` Header Is Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body for HMAC verification, while the `shop` (and `topic`, `webhook_id`, `api_version`) values are read directly from unauthenticated HTTP headers. `Registry.process` trusts `request.shop` to identify which tenant the webhook belongs to after HMAC validation, but that field was never part of the signed payload.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes and compares an HMAC over whatever `to_signable_string` returns for the `VerifiableQuery` object passed in: [1](#0-0) 

For webhooks, `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers with no cryptographic binding to the signed body: [3](#0-2) 

`Registry.process` validates the HMAC (over the body only) and then immediately builds `WebhookMetadata` using the unauthenticated `request.shop` header as the tenant identifier that is handed to the app's handler: [4](#0-3) 

This breaks the intended identity binding: `shop` claimed in the header ≠ `shop` actually covered by the HMAC-authenticated bytes (only `raw_body` is covered). The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify" (docs/usage/webhooks.md), implying the whole request — including the shop attribution — is authenticated, when in fact only the body bytes are.

Since a single app-wide `api_secret_key` HMAC-signs webhook bodies for *every* installed shop, any entity that can obtain one validly-signed `(raw_body, hmac)` pair for its own shop (e.g., a merchant who installs the public app and captures its own webhook traffic) can replay that exact body/HMAC pair to the app's webhook endpoint while swapping the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header to name a different, victim shop. The HMAC still validates (it only checks the body), and `Registry.process` will dispatch the handler with `data.shop` set to the victim shop's domain while the body content is attacker-controlled — a classic tenant-confusion primitive.

### Impact Explanation
Any app built on this gem that uses `data.shop` from `WebhookMetadata` to select the tenant context (e.g., look up the shop's stored access token/session, or write/merge data keyed by shop) can be tricked into associating attacker-supplied webhook body content with a victim shop's identity. Depending on how the host app persists webhook data, this enables cross-tenant data injection/confusion using only unprivileged means (installing the app on an attacker-controlled shop to obtain one legitimate signed payload). This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires no leaked secrets or elevated privileges — only becoming a normal merchant/installer of the target public app (or otherwise observing one legitimate webhook delivery) and then replaying that body with a forged shop header to the app's public webhook endpoint. The gem provides no defense against this because the shop identity is never part of the signed content, and the documentation encourages developers to trust `data.shop` directly.

### Recommendation
Include the shop-identifying header (and topic/webhook id where feasible) in the HMAC-covered signable content, or otherwise cryptographically bind the header-sourced `shop` value to the signed body (e.g., derive/confirm the shop from a value embedded in the JSON payload itself, or require the host application to cross-check `request.shop` against the shop associated with the specific `webhook_id`/subscription on Shopify's side before trusting it). At minimum, update documentation to explicitly warn that `data.shop` is not authenticated by the HMAC check and must be independently verified by the host app.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and registers for a webhook topic (e.g., `customers/data_request`), receiving a legitimately signed webhook: `raw_body = B`, header `X-Shopify-Hmac-Sha256 = HMAC(secret, B)`, header `X-Shopify-Shop-Domain = attacker.myshopify.com`.
2. Attacker crafts a new HTTP request to the app's webhook endpoint using the exact same `raw_body = B` and the exact same `X-Shopify-Hmac-Sha256` value, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. The app calls `ShopifyAPI::Webhooks::Registry.process(request)`. `Utils::HmacValidator.validate(request)` succeeds because it only checks `HMAC(secret, B)` against the same `B`: [5](#0-4) 
4. The registered handler is invoked with `WebhookMetadata` where `shop == "victim.myshopify.com"` but `body` is the attacker's own webhook content, causing the host app to process/store attacker-controlled data under the victim tenant's identity.
