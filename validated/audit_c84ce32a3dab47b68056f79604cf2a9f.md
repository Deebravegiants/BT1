### Title
Unbounded chunked-accrual loop permanently bricks a dormant market - (File: contracts/pool/src/interest.rs)

### Summary
`global_sync` in `contracts/pool/src/interest.rs` advances interest from the stored `last_timestamp` to the current ledger time by looping `while remaining > 0` and accruing in chunks of at most `MAX_COMPOUND_DELTA_MS` [1](#0-0) . The loop iteration count is proportional to elapsed wall-clock time and has no other bound, so once a market's idle gap exceeds what fits in one transaction's compute budget, every state-changing call that touches that market exhausts the budget and reverts — permanently, because elapsed time only grows. This is the on-chain analog of the CVE-2017-14684 class: resource consumption that scales with attacker-influenced input (here, accrual time) rather than with a bounded work unit, causing denial of service.

### Finding Description
Every pool operation routes through the `Cache`, which calls `global_sync` before any supply, borrow, repay, withdraw, liquidation, or flash logic executes. `global_sync` computes `remaining = cache.elapsed_ms()` and iterates `accrue_chunk` once per `MAX_COMPOUND_DELTA_MS` slice until the gap is consumed [2](#0-1) . Each iteration performs full RAY fixed-point math (`accrue_step` over borrow/supply indexes and protocol fee shares) [3](#0-2) . There is no cap on iteration count, no catch-up approximation for very old timestamps, and no escape path that skips accrual — `cache.mark_accrued()` is reached only after the loop completes. Per-market `State(HubAssetKey)` and `Params(HubAssetKey)` entries are per-market, so a single stale market is bricked independently of the rest of the protocol.

An unprivileged user cannot set the ledger timestamp, but they fully control *when* a thin market is next touched. Any account can leave a dust position in a little-used market (or a market becomes dormant naturally after listing), wait until `elapsed_ms` exceeds the per-transaction chunk ceiling, and then the market is permanently frozen. Crucially, the healing path itself — permissionless `update_indexes` [4](#0-3)  — also calls into the same accrual and would hit the same budget limit, so no transaction can ever advance `last_timestamp` again once the gap is too large.

### Impact Explanation
Permanent freezing of funds. Once `elapsed_ms / MAX_COMPOUND_DELTA_MS` iterations exceeds the Soroban per-transaction CPU budget, every entrypoint for that `(hub, token)` book — `supply`, `withdraw`, `borrow`, `repay`, `liquidate`, `clean_bad_debt`, `flash_loan`, `claim_revenue`, `recapitalize`, `update_indexes` — reverts before doing any work, and no call can reduce `elapsed_ms`. All supplier principal, unclaimed revenue, and collateral backing that market is locked forever; accrued debt can never be repaid or liquidated through the pool. Because the condition is monotonic in time, this is irreversible without a contract upgrade.

### Likelihood Explanation
Medium. The trigger requires a market whose accrual timestamp goes untouched for a gap on the order of `MAX_COMPOUND_DELTA_MS` × (max chunks per transaction). Whether that gap is days or months depends on the `MAX_COMPOUND_DELTA_MS` constant and Soroban budget limits, which I could not fully verify numerically from the indexed code. The keeper renews storage TTL but is not configured to call `update_indexes` by default (`enable_index_refresh: false`), and its index loop only covers configured markets [5](#0-4) . A low-activity or newly listed spoke market with one dust position is a realistic dormant-market candidate, and any single user can guarantee dormancy is never accidentally healed by being the only participant. No privileged action or oracle manipulation is required.

### Recommendation
Bound the accrual loop: cap the number of `accrue_chunk` iterations per call (e.g., accrue at most `N` chunks and store the partially advanced `last_timestamp`), or clamp `elapsed` to a maximum catch-up window and accrue the remainder as a single non-compounded/simple-interest step. A bounded-iteration design also lets `update_indexes` make incremental progress across multiple transactions to un-stick a stale market instead of bricking on the first touch. Add a regression test that sets `last_timestamp` far in the past and asserts the entrypoint completes within budget.

### Proof of Concept
1. A market `M` is listed; an attacker supplies a dust amount so `State(M)` exists with `last_timestamp = T0`.
2. Nobody calls any pool function for `M` for a duration `D` where `D / MAX_COMPOUND_DELTA_MS` × per-chunk cost > Soroban transaction CPU budget (attacker can also simply wait for organic dormancy).
3. Attacker (or any user) calls `Controller::supply`/`withdraw`/`update_indexes` for `M`. `global_sync` enters the `while remaining > 0` loop at `contracts/pool/src/interest.rs:26` and iterates `D / MAX_COMPOUND_DELTA_MS` times, exceeding the budget; the transaction reverts.
4. Since `elapsed_ms` strictly increases and `last_timestamp` is only updated after the loop completes (`cache.mark_accrued()` at line 32), every subsequent call fails identically — the market, its supplied funds, and its unclaimed revenue are frozen permanently.

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}
```

fn accrue_chunk(env: &Env, cache: &mut Cache, delta_ms: u64) {
    let step = accrue_step(
        env,
        cache.params(),
        cache.borrowed(),
        cache.supplied(),
        cache.borrow_index(),
        cache.supply_index(),
        delta_ms,
    );

    cache.set_borrow_index(step.borrow_index);
    cache.set_supply_index(step.supply_index);
    cache.accrue_revenue(step.revenue_shares);
}
```
