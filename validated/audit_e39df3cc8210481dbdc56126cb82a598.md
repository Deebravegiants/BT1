## Title
Webhook HMAC does not bind the `shop`/`topic`/`webhook-id` headers to the signed payload, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values that the host application uses to attribute the webhook to a specific tenant are read directly from unauthenticated HTTP headers and are never included in the HMAC-signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but the identity fields consumed downstream — `shop`, `topic`, `webhook_id`, `api_version` — are pulled straight from headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Utils::HmacValidator.validate` (and `validate_signature`) only ever signs/compares `verifiable_query.to_signable_string`, i.e. the raw body: [3](#0-2) 

`Registry.process` accepts the request once this body-only HMAC check passes, then hands the *header-derived* `shop` value to the app's handler as the authoritative tenant identifier: [4](#0-3) 

Because the `api_secret_key` is shared across every shop that has installed the app, the HMAC of a given raw body is identical regardless of which shop it is claimed to originate from. This breaks the intended identity binding `hmac-authenticated bytes == shop that produced them`. Concretely: `hmac(raw_body) == hmac(raw_body)` holds true independent of the `x-shopify-shop-domain` header, so the equality the code implicitly relies on — "a validated HMAC implies the accompanying `shop` header is authentic" — does not hold.

### Impact Explanation
This is a cross-tenant identity-binding failure of exactly the kind flagged in the report (an identity/attribution value acted upon that is not covered by the integrity check). A user who has installed the app on their own store (an "unprivileged" tenant relative to other merchants) can trigger a legitimate webhook to capture a valid `(raw_body, hmac)` pair, then replay that same body/hmac pair to the app's webhook endpoint while substituting `x-shopify-shop-domain` (and/or `x-shopify-topic`) headers naming a victim shop. Because `Registry.process` never checks that the `shop` header is consistent with anything the HMAC actually covers, the forged request passes validation and the app's `WebhookMetadata` reports the victim's shop as the source. Any host application that uses `WebhookMetadata#shop` to look up per-tenant records, apply mutations, or route data (the documented and intended usage pattern) can be tricked into writing/reading data under the wrong tenant — a cross-tenant access/data-integrity break.

### Likelihood Explanation
Exploitation only requires: (1) being a legitimate installer of the target app on any shop (no special privilege, no access to `api_secret_key`), and (2) the ability to send arbitrary HTTP requests to the app's public webhook endpoint with attacker-controlled headers, which is standard and always available to an internet client. No TLS interception, credential theft, or access-token possession is needed, since the HMAC secret is never exposed to the attacker but its output over attacker-obtainable, replayable bodies is reusable.

### Recommendation
Bind the identity-critical headers (`shop`, `topic`, `webhook_id`, `api_version`) into the HMAC-signed content — e.g. concatenate them with the raw body before signing/verifying, or independently verify that the `shop` header corresponds to a shop with a session known to the app before trusting it as an attribution key. Short term, document and enforce that consumers must additionally verify `WebhookMetadata#shop` against their own session/tenant store rather than trusting the header value implied only by a body-only HMAC check.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers any webhook topic, capturing the exact `raw_body` and its `x-shopify-hmac-sha256` value from the delivered request.
2. Attacker replays this exact `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and, if desired, an arbitrary `x-shopify-webhook-id`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `raw_body` — this succeeds because the body is byte-identical to what the attacker legitimately received: [4](#0-3)  and [5](#0-4) .
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload actually originated from the attacker's own shop, allowing the attacker to inject/attribute data to a shop they do not control.
