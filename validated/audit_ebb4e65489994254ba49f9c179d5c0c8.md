### Title
Webhook shop-domain and topic headers are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop`, `topic`, and `webhook_id` values that the app uses to attribute and route that body are read from HTTP headers that are never included in the signed material.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Utils::HmacValidator.validate` computes/compares the HMAC exclusively over that signable string [2](#0-1) . Meanwhile `Request#shop`, `#topic`, and `#webhook_id` are parsed directly from the `shopify-shop-domain`, `shopify-topic`, and `shopify-webhook-id` headers with no cryptographic binding to the body they accompany [3](#0-2) .

`Registry.process` checks only `Utils::HmacValidator.validate(request)` (body HMAC) before dispatching the event to the app's handler using the unauthenticated `request.shop`/`request.topic`/`request.webhook_id` metadata: [4](#0-3) 

The binding this breaks, expressed as an equality that should hold but doesn't:
`shop_bound_by_hmac(request) == shop_used_by_handler(request)`

Before the attacker's request: for a legitimately delivered webhook, both sides equal the shop that Shopify actually generated the event for.
After the attacker's request sequence: an unprivileged internet user who owns/operates their own Shopify store can install the target app on their own store, legitimately triggering the app to receive a genuinely-signed webhook (valid HMAC, computed with the app's shared `api_secret_key`, over some body they influence or observe — e.g., `customers/data_request`, `orders/create`, etc.). Because the HMAC covers only `@raw_body`, the attacker can then replay the exact same `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header (and/or `shopify-topic`/`shopify-webhook-id` headers) with a different, victim shop's domain or a different topic. `HmacValidator.validate` still returns true because the body/HMAC pair is untouched, but `Registry.process` now dispatches the handler with `shop: request.shop` set to the attacker-chosen value [5](#0-4) .

### Impact Explanation
This qualifies as cross-tenant access: an attacker who is a legitimate but unprivileged installer of the app on their own shop can cause the app's webhook handler to process event data under the identity of any other shop (or any other topic) it chooses, purely by manipulating unauthenticated headers on an otherwise validly-signed request. Depending on how the consuming application (which relies on this gem's `Webhooks::Registry`/`Request` primitives as documented) keys its per-tenant data by `shop`, this can be leveraged to pollute, delete, or misattribute another merchant's data (e.g., forging a `customers/redact` or `shop/redact` event against a victim shop, or injecting attacker-controlled body content — such as GDPR/data request bodies — attributed to a victim's `shop-domain`).

### Likelihood Explanation
Requires only that the attacker be able to install the target app on a shop they control (a normal unprivileged action any Shopify merchant can perform) and be able to POST arbitrary HTTP headers to the app's public webhook endpoint — no access to the app's `client_secret`/`api_secret_key`, no privileged account, and no interception is required. This is a realistic, moderately easy-to-execute replay/header-substitution attack once a single genuine webhook has been captured from the attacker's own store.

### Recommendation
Bind the shop, topic, and webhook id to the HMAC-verified material instead of trusting unauthenticated headers: include `shop-domain`, `topic`, and `webhook-id` (or an app-generated canonical identifier derived from the verified body, if Shopify's payload includes shop identification) in `to_signable_string`, or otherwise cross-check the header-derived shop/topic against the shop/topic embedded in `parsed_body` before dispatching to handlers. At minimum, document prominently that `Request#shop`/`#topic`/`#webhook_id` are unauthenticated header values and must not be used by consuming apps as a tenant-scoping key without additional verification.

### Proof of Concept
1. Attacker registers/installs the target Shopify app on their own store `attacker-shop.myshopify.com`, triggering a real webhook delivery, e.g. `customers/data_request`, with headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: customers/data_request`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>` and raw body `B`.
2. Attacker captures `(B, valid-hmac-of-B)`.
3. Attacker (or attacker's automation) sends a new HTTP POST to the app's public webhook endpoint with the same body `B` and same `X-Shopify-Hmac-Sha256` header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and/or a different `X-Shopify-Topic`, e.g. `shop/redact`).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` — this returns `true` because it only hashes `@raw_body`, which is unchanged [6](#0-5) .
5. The handler is invoked with `WebhookMetadata.new(topic: "shop/redact", shop: "victim-shop.myshopify.com", body: parsed(B), ...)` [5](#0-4) , causing the app to act on `victim-shop.myshopify.com`'s tenant data using attacker-supplied body content, despite the HMAC never having authenticated that shop/topic association.
