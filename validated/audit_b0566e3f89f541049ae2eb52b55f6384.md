### Title
Webhook `shop`/`topic`/`webhook_id` identity headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then unconditionally trusts the `shop`, `topic`, `webhook_id`, and `api_version` values taken from unauthenticated HTTP headers to build the `WebhookMetadata` handed to the app's business logic. None of these identity fields are included in the signed bytes, so they can be swapped independently of a valid HMAC.

### Finding Description
`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it with the received HMAC: [1](#0-0) 

For `Webhooks::Request`, `to_signable_string` returns only the raw HTTP body: [2](#0-1) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers, which are never part of the signable string: [3](#0-2) [4](#0-3) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` and then passes the header-derived `request.shop`, `request.topic`, `request.webhook_id`, `request.api_version` straight into `WebhookMetadata`, which is delivered to the host application's handler as the trusted tenant/topic identity: [5](#0-4) 

This reproduces the same class of bug as the reference report: an equality that should hold — `bytes verified by HMAC == identity fields the code acts on` — does not hold. The HMAC only proves "this body byte-string was signed with `api_secret_key`"; it proves nothing about which shop, topic, or webhook id that body is claimed to belong to.

Because Shopify apps use a single `api_secret_key`/`client_secret` shared across every merchant that installs the app (not a per-tenant secret), any merchant who has genuinely installed the app can trigger a real webhook delivery for their own store (e.g., by creating an order), capturing a wire-valid `(raw_body, x-shopify-hmac-sha256)` pair. That merchant — an otherwise unprivileged tenant with no access to `api_secret_key` — can then directly POST that exact `(body, hmac)` pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`/`x-shopify-webhook-id`) header with a victim shop's domain. `Registry.process` will validate the HMAC successfully (it only checks the body) and hand the host application a `WebhookMetadata` claiming the payload came from the victim shop.

### Impact Explanation
Any host application that relies on `WebhookMetadata#shop` (as the library's own API and documentation direct it to) to select which tenant's data to update, will process attacker-supplied content under a victim shop's identity — a cross-tenant data-integrity/confusion issue at the trust boundary the gem is responsible for enforcing (the HMAC check is the only authentication primitive this gem exposes for webhooks).

### Likelihood Explanation
Requires only an app installation on any single (even attacker-owned) shop — no `api_secret_key`, access token, or privileged account is required, and no code changes are needed in the host app beyond using this library's documented webhook verification/registry flow as intended.

### Recommendation
Bind the identity headers into the HMAC-verified surface, e.g. include `shop`, `topic`, and `webhook_id` in the signable string (matching them against a value that only the legitimate delivery could produce), or independently verify `request.shop` against the specific `Session`/tenant the app expects the webhook for, rather than trusting the header value emitted from `Registry.process`.

### Proof of Concept
1. Install the target app on shop `attacker.myshopify.com`.
2. Trigger a real webhook (e.g., `orders/create`) from that shop; capture the raw POST body and its `x-shopify-hmac-sha256` header — this is a validly-signed `(body, hmac)` pair.
3. POST that identical body and HMAC header directly to the app's webhook endpoint, but replace `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because it only checks the body bytes: [6](#0-5) 
5. `Registry.process` dispatches the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host application to act as though the (attacker-controlled) payload originated from the victim shop.
