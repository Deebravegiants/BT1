### Title
Webhook `shop` domain and other request metadata are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signature only over the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values are read directly from unauthenticated HTTP headers and are never included in the signed payload. `Registry.process` validates the HMAC and then trusts these header-derived fields to build the `WebhookMetadata` handed to the host application's handler, so the binding "the bytes that were HMAC-verified" ≠ "the shop identity the handler acts on" is broken.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are parsed straight out of caller-supplied headers with no cryptographic binding to the body or to the HMAC: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, then immediately builds `WebhookMetadata` from these unauthenticated header fields and dispatches it to the application-provided handler: [3](#0-2) 

`HmacValidator.validate` in turn calls `verifiable_query.to_signable_string`, which for a `Request` is exactly the raw body — nothing else: [4](#0-3) 

Because the api_secret_key is shared by the app across all installed shops (it is not per-tenant), a single legitimately-obtained `(raw_body, hmac)` pair — for example one delivered to an attacker's own shop that has installed the app — remains a cryptographically valid pair regardless of which `shop-domain`/`topic`/`webhook-id` header values accompany it. An attacker who controls one merchant install can replay that valid body+HMAC pair to the app's webhook endpoint while substituting a victim shop's domain in the `x-shopify-shop-domain` header (or any topic/webhook-id value they like), and `Registry.process` will accept it as authentic and dispatch it to the handler labeled with the attacker-chosen shop.

### Impact Explanation
This directly breaks the identity binding "bytes verified == identity acted upon" for webhook shop attribution, letting an unprivileged (but installed) app user forge webhook events that the host application will attribute to any other merchant/tenant using the app — a cross-tenant confusion vector for any downstream logic that trusts `WebhookMetadata#shop` (e.g., to select which merchant record to update, credit, or mark as changed).

### Likelihood Explanation
Medium: exploitation requires the attacker to first obtain one legitimately signed `(body, hmac)` pair, which is trivially available to anyone who installs the app on their own shop and triggers any webhook delivery (e.g., an `orders/create` event on their own store). No access to `api_secret_key` or any privileged credential is required.

### Recommendation
Include the security-relevant header values (at minimum `shop-domain`, and ideally `topic`/`webhook-id`/`api-version`) in the string that is HMAC-verified, or otherwise cryptographically bind them to the body before trusting them in `Registry.process`/`WebhookMetadata`. At minimum, document/require that host applications independently verify `request.shop` against a known/installed shop list before acting on webhook data, since the gem itself does not bind that field to the signature.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook delivery with raw body `B` and header `x-shopify-hmac-sha256: H` (valid because `HMAC(secret, B) == H`).
2. Attacker POSTs the same raw body `B` and the same `x-shopify-hmac-sha256: H` header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged shop header (`lib/shopify_api/webhooks/request.rb:21-23`); `Utils::HmacValidator.validate` succeeds because it only checks `HMAC(secret, B) == H` (`lib/shopify_api/utils/hmac_validator.rb:27-31`).
4. `Registry.process` calls the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: ..., body: parsed_body)` (`lib/shopify_api/webhooks/registry.rb:188-200`), causing the host application to process attacker-controlled data as though it originated from the victim shop.
