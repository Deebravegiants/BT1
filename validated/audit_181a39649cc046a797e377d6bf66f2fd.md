This confirms the vulnerability: `Webhooks::Request#to_signable_string` returns only `@raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`), while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from HTTP headers (`lib/shopify_api/webhooks/request.rb:20-33`) and are never part of the HMAC-signed data. `Registry.process` validates only `Utils::HmacValidator.validate(request)` (body-only HMAC) then trusts `request.shop`/`request.topic` to route/attribute the webhook to a tenant and handler (`lib/shopify_api/webhooks/registry.rb:188-199`).

### Title
Webhook `shop-domain`/`topic`/`webhook-id` headers are trusted but not covered by the HMAC signature, enabling cross-tenant webhook replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body [1](#0-0) , so `HmacValidator.validate` only ever authenticates the body bytes [2](#0-1) . The `shop`, `topic`, and `webhook_id` values consumed by `Registry.process` are pulled straight from unauthenticated HTTP headers [3](#0-2)  and are passed into the handler's `WebhookMetadata` without any binding to the signed body [4](#0-3) .

### Finding Description
The identity binding that should hold is: `bytes verified by HMAC == bytes acted upon by the handler for tenant attribution`. Here that equality is broken — the HMAC only covers the JSON body, while `shop-domain`, `x-shopify-topic`, and `x-shopify-webhook-id` headers are excluded from the signed content but are exactly the fields the host application uses to decide which shop/tenant a webhook belongs to and how to route it.

An unprivileged attacker who legitimately installs the app on their own store (a normal, unprivileged action) will receive genuine Shopify-signed webhooks containing a valid `(raw_body, hmac)` pair for their own store. Because the header fields are not part of the signed content, the attacker can replay the exact same body+HMAC to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) to claim to be a different, victim shop. `HmacValidator.validate` still succeeds because it only checks the (unchanged) body against the secret, and `Registry.process` will invoke the handler with `WebhookMetadata` claiming the victim's shop [5](#0-4) .

### Impact Explanation
Any handler logic that uses `data.shop` from `WebhookMetadata` to key mutations (deleting store data on `shop/redact`, updating billing/subscription state, disabling app access, writing to a shop-scoped database record, etc.) can be tricked into acting on behalf of a shop the attacker does not control. This is a cross-tenant boundary violation: the attacker (bound to their own shop) causes state changes attributed to another tenant, purely by controlling headers that are outside the cryptographic envelope. This matches the Critical impact category "cross-tenant access."

### Likelihood Explanation
The attacker only needs to be a legitimate, unprivileged merchant/installer of the app (no `api_secret_key`, no access token, no social engineering) to obtain one authentic `(body, hmac)` pair for their own shop, then simply resend it to the public webhook endpoint with altered headers. This requires no interception of Shopify's traffic and no cryptographic secret — only a normal webhook received on any shop the attacker controls, making the exploit straightforward to reproduce.

### Recommendation
Include the tenant-identifying fields in the HMAC signable content, or otherwise cryptographically bind `shop`, `topic`, and `webhook_id` to the verified body (e.g., have `to_signable_string` incorporate the headers, or independently validate that `shop` matches a shop known to have subscribed to the specific `webhook_id`/topic via a separate Shopify API lookup) before dispatching to handlers.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B`), `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: shop/redact`.
2. Attacker sends a new POST to the app's webhook endpoint with the identical body `B` and identical `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers; `Utils::HmacValidator.validate(request)` calls `to_signable_string` (body only) and succeeds because `B`/`H` are unchanged [6](#0-5) .
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", ...)`, causing the host application to act on the victim shop's data using the attacker-controlled body [7](#0-6) .
