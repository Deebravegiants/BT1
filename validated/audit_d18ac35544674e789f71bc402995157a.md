### Title
Protocol fee (`protocolShare`) can be evaded by an unprivileged filler/order-creator using a malicious ERC-20 output token in `ExtrinsicIntents._fillCrossChain` - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`ExtrinsicIntents._fillCrossChain` collects the solver's overpayment surplus by issuing two independent `safeTransferFrom` calls from `msg.sender` (the filler) using the arbitrary output token specified in the order — one to the `beneficiary`, and a second, separate one to `address(this)` (the gateway, which later has this "dust" swept to the protocol treasury). Because the order's output token address is attacker-controllable, a malicious ERC-20 can be crafted to silently no-op (while returning `true`) only when the transfer recipient is the gateway address, letting a filler keep the `protocolShare` while still appearing to satisfy `safeTransferFrom` and while `DustCollected` is still emitted.

### Finding Description
In `_fillCrossChain`, for each ERC-20 output asset the contract does: [1](#0-0) 

```solidity
IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare);
if (protocolShare > 0) {
    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
}
if (protocolShare > 0) emit DustCollected(token, protocolShare);
```

`token` is `address(uint160(uint256(order.output.assets[i].token)))` — a value taken directly from the cross-chain order, which is attacker/user-controlled data (the order originates from an unprivileged party on the source chain and is only validated by hash/commitment, not by an allow-list of tokens). This mirrors the Allo `_fundPool` pattern exactly: two separate `transferFrom` calls against the same arbitrary ERC-20, one that goes to a normal party (`beneficiary`) and a second that goes specifically to the protocol-controlled address (`address(this)`, which accumulates fee "dust" later swept to treasury via `_sweepDust`, see `IntentsBase.sol` lines 639-656). A malicious ERC-20 contract can implement `transferFrom` to special-case `to == <gateway address>` and skip the balance movement while still returning `true`, so the `safeTransferFrom` call to `address(this)` succeeds without moving any tokens, yet the code proceeds to emit `DustCollected(token, protocolShare)` as if the fee had actually been collected.

Note the difference from `IntentGatewayV2.placeOrder`, which is *not* vulnerable to this class: there, protocol fee accounting is derived from a single `balanceOf` before/after check around one `safeTransferFrom` call (see `evm/src/apps/IntentGatewayV2.sol` lines 320-323, and the `FeeOnTransferToken` tests confirming this design defends against fee-on-transfer/malicious tokens). `_fillCrossChain`, however, performs two independent transfers with no balance verification, reproducing exactly the flaw described in the external report.

### Impact Explanation
Because the "protocol" portion of the surplus never actually lands in the gateway contract for that malicious token, the emitted `DustCollected` event and any offchain/governance accounting of accrued protocol fees becomes false. When governance later attempts `_sweepDust` for that token/amount, it will either revert (insufficient balance) or, more dangerously in a shared-balance contract, be settled against balances actually belonging to other legitimate escrows of the same token, since the sweep is driven by an accounting figure (`req.outputs[i].amount`) rather than a verified per-order balance delta. At minimum this is a direct, repeatable loss of protocol fee revenue matching the original report's severity class ("large loss of protocol revenue"), and at worst can corrupt shared-token accounting used by `_sweepDust`.

### Likelihood Explanation
Any user can create a cross-chain intent order with a custom ERC-20 as the output token (no allow-list is enforced on `order.output.assets[i].token`), and any address (including the order creator itself, self-filling) can act as the filler who calls `fillOrder`/`_fillCrossChain`. Crafting an ERC-20 that special-cases a known, public gateway address is trivial and gas-cheap, and the exploit requires only a single order placement + fill transaction with a surplus configured (`solverAmount > totalRequired`). This makes the likelihood high for any deployment that does not vet output tokens.

### Recommendation
- Verify actual token receipt via balance-delta checks (`balanceOf` before/after) around fee/dust-relevant transfers, as already done for input tokens in `IntentGatewayV2.placeOrder`, rather than trusting the boolean return of `safeTransferFrom`.
- Alternatively, collect `protocolShare` using a single `transferFrom` to one destination and let the beneficiary internally forward, or restrict output tokens to a governance-curated list of trusted assets.
- Do not emit `DustCollected` (or credit sweep-able balances) based on the intended `protocolShare` value; instead emit/store the amount actually observed to have moved into the contract.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC-20 whose `transferFrom(from, to, amount)` behaves normally for any `to` except a hardcoded `GATEWAY` address, for which it updates no balances but still returns `true`.
2. Attacker (as `user`) creates a cross-chain `Order` with `order.output.assets[0].token = EvilToken` and `order.output.assets[0].amount` set below the amount the attacker will supply as filler, so that `solverAmount - totalRequired = surplus > 0` and, via `_splitSurplus`, `protocolShare > 0`.
3. Attacker (as `solver`/filler) calls the destination gateway's fill entrypoint that invokes `_fillCrossChain` with `options.outputs[0].amount = solverAmount`.
4. Inside `_fillCrossChain`:
   - `IERC20(EvilToken).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare)` succeeds and moves real tokens to `beneficiary` (attacker-controlled or a colluding party).
   - `IERC20(EvilToken).safeTransferFrom(msg.sender, address(this), protocolShare)` returns `true` but moves zero tokens because `to == address(this)` matches the gateway's special-cased address.
5. `DustCollected(EvilToken, protocolShare)` is emitted despite the gateway holding zero `EvilToken` balance corresponding to that fee.
6. When governance later calls `_sweepDust` expecting to collect the recorded `protocolShare` of `EvilToken`, the sweep either reverts for insufficient balance or, if batched with other escrowed `EvilToken` balances, sweeps funds that belong to unrelated orders — confirming the fee was never actually collected while the on-chain event log claims otherwise.
