### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity by HMAC-signing only the raw JSON body, while the `shop`, `topic`, `webhook_id`, and `api_version` values used by the app's business logic are taken from unauthenticated HTTP headers. Because the HMAC secret (`api_secret_key`) is shared across every shop that installs the app, any unprivileged merchant who legitimately installs the app can obtain a validly-signed `(body, hmac)` pair for their own store, then resend that exact pair to the app's public webhook endpoint with a forged `shop-domain` header naming a victim shop. The signature check still passes because the shop identity was never part of the signed material, so the app processes attacker-controlled event data as if it originated from the victim tenant — an identity-binding break directly analogous to the PPS oracle's missing binding between the signed payload and the entity it is applied to.

### Finding Description
`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac-sha256` header: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw body — none of the identifying headers are included in the signed bytes: [2](#0-1) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read directly from HTTP headers with no cryptographic tie to the HMAC: [3](#0-2) 

`Registry.process` validates only the HMAC of the body, then immediately trusts `request.shop` (and other headers) as the tenant identity passed to the app's handler: [4](#0-3) 

Equality that should hold but doesn't: `shop bound by signature == shop used by handler`. In practice: `shop_signed (∅, not part of HMAC input) != shop_trusted (request.shop header, used verbatim in WebhookMetadata)`. Since `api_secret_key` is the same across all shops installing a given app, an attacker who is a legitimate installer on their own store can capture any `(body, x-shopify-hmac-sha256)` pair Shopify generates for their own account's events, then replay that exact pair to the app's public webhook endpoint while substituting a victim shop's domain in `x-shopify-shop-domain`. The signature still validates because it never covered the shop header, so `Registry.process` dispatches the (attacker-controlled) payload to the handler labeled as belonging to the victim shop.

### Impact Explanation
This breaks the tenant boundary the webhook mechanism is supposed to enforce: the handler receives `WebhookMetadata` claiming to be from shop X while the content/signature actually originates from attacker's own shop Y. Any application logic that trusts `data.shop` to scope database writes, cache invalidation, order/customer sync, or other per-tenant side effects can be manipulated by an unprivileged attacker into performing cross-tenant data injection/corruption against a shop they do not control — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is high: no privileged credentials, access tokens, or the app's `client_secret` are required. The attacker only needs to be an ordinary merchant who installs the target app (a normal, unprivileged action), trigger any webhook-eligible event, capture the body/HMAC header pair from the request their own server receives, and replay it to the app's public webhook URL with a different `shop-domain` header. No signature forgery is needed since the shop field was never protected.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-signed material, or otherwise cryptographically bind the header-derived identity to the verified body — e.g., verify that `request.shop` matches an expected/known installed shop for the api key/session context before dispatching to handlers, and/or extend `to_signable_string` (or add a secondary check) so `shop-domain` cannot vary independently of a valid signature.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` (a normal unprivileged action).
2. Attacker triggers a real event (e.g., `orders/create`) causing Shopify to POST a webhook to the app's endpoint with body `B` and header `x-shopify-hmac-sha256: H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker's own server (or a proxy they control) intercepts/logs this `(B, H)` pair.
4. Attacker crafts a new HTTP request to the same public webhook endpoint with the identical body `B` and header `H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
5. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb#L26-L31` succeeds because it only checks `HMAC(B) == H`, which is unaffected by the shop header.
6. `Registry.process` in `lib/shopify_api/webhooks/registry.rb#L188-L200` calls `handler.handle` with `shop: "victim.myshopify.com"` and the attacker-controlled body `B`, causing the app to process/store data as if it came from the victim tenant.
