Based on the analysis, this maps cleanly to the report's bug class: a field that is *acted on* by the application (`shop`) is not covered by the cryptographic binding (`hmac`) that is supposed to authenticate the request.

### Title
Webhook `shop-domain` header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC signature that `Registry.process` validates covers exclusively the request body. The `shop`, `topic`, `webhook_id`, and `api_version` values are all read straight from HTTP headers that sit entirely outside the signed content, yet `shop` is the value handed to the host application's handler as the tenant identifier.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the HMAC using `verifiable_query.to_signable_string`, which for webhooks is defined as just the raw body: [1](#0-0) 

Meanwhile `shop` is derived from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header: [2](#0-1) 

`Registry.process` only checks the HMAC before forwarding `request.shop` into `WebhookMetadata` and thus into the app's handler as the trusted tenant identifier: [3](#0-2) 

The identity binding the gem should be enforcing is: `hmac == HMAC(secret, body ‖ shop ‖ topic)`. What it actually enforces is: `hmac == HMAC(secret, body)`, independent of `shop`. Because a shop owner running their own store legitimately receives genuine Shopify webhooks (valid body + valid HMAC) for their own tenant, they can capture such a webhook and replay it to the app's public webhook endpoint with the `shop-domain` header rewritten to a victim's `myshopify.com` domain. The HMAC still validates (it only ever checked the body), so `Registry.process` calls the app's handler believing the event originated from the victim shop.

### Impact Explanation
This is a cross-tenant identity confusion: an unprivileged shop owner (attacker) can make the merchant application process attacker-controlled webhook data (topic + body they legitimately received) while it's attributed to a shop they don't own. Any app logic keyed off `data.shop`/`data.topic` (e.g., updating per-shop billing state, GDPR mandatory topics like `customers/data_request`/`shop/redact`, inventory/order records, or any state keyed by shop domain) can be corrupted or triggered for a shop the attacker doesn't control — a cross-tenant access/write primitive achieved without ever possessing the app's `client_secret`.

### Likelihood Explanation
Any merchant/developer who can install the app on their own store (a normal, unprivileged action) can receive at least one legitimate webhook and thus obtain one valid `(body, hmac)` pair. Replaying it against the app's public webhook URL with a modified `shop-domain` header requires no secret knowledge and no elevated access — only knowledge of the target's `myshopify.com` domain, which is public.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signable content used for HMAC verification (or otherwise cryptographically bind the header-derived `shop` value to the signed payload), rather than trusting `shopify-shop-domain` unconditionally once only the body's HMAC passes.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com` and registers for a webhook topic (e.g. `orders/create`).
2. Shopify sends a legitimate webhook: body `B`, header `x-shopify-shop-domain: attacker.myshopify.com`, and `x-shopify-hmac-sha256: HMAC(secret, B)`.
3. Attacker replays the exact same body `B` and HMAC header to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request#to_signable_string` returns unchanged body `B`; `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` and it matches — validation passes.
5. `Registry.process` invokes the app's handler with `WebhookMetadata(shop: "victim.myshopify.com", topic: ..., body: B, ...)`, causing the app to act on attacker-supplied data as if it came from the victim's shop.
