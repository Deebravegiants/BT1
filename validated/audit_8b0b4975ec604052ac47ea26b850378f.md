### Title
`DeleteKey`/`DeleteAccount` actions bypass per-receipt storage-proof-size enforcement pre-`EnforceStorageProofLimitForAllActions` - (`runtime/runtime/src/lib.rs`)

### Summary
The per-receipt storage witness/proof size limit introduced by `ProtocolFeature::EnforcePerReceiptStorageProofLimit` is enforced two different ways: for `FunctionCall` actions via the in-VM `RecordedStorageCounter::observe_size` (checked after every host-level trie op), and for *all* actions via an outer per-action check in `apply_action_receipt` — but the outer check is itself gated behind a *second*, later-activating feature, `ProtocolFeature::EnforceStorageProofLimitForAllActions`. Until that second feature activates, non-`FunctionCall` actions such as `DeleteKey` and `DeleteAccount` (which remove access keys directly via `TrieUpdate::remove`) have no proof-size enforcement at all within the action loop, letting an attacker accumulate an unbounded storage proof/witness for a receipt using only native actions.

### Finding Description
`apply_action_receipt` (`runtime/runtime/src/lib.rs:773`) snapshots `recorded_storage_size_upper_bound()` before executing a receipt's actions only `if ProtocolFeature::EnforcePerReceiptStorageProofLimit.enabled(...)` [1](#0-0) . It then computes `storage_proof_limit_for_all_actions`, which is `Some(limit)` **only** `if ProtocolFeature::EnforceStorageProofLimitForAllActions.enabled(...)` [2](#0-1) . After each action, the accumulated proof delta is compared against the limit and the receipt is failed with `ActionErrorKind::ReceiptStorageProofSizeExceeded` **only when that `Option` is `Some`** [3](#0-2) .

The doc comment on `EnforceStorageProofLimitForAllActions` in `version.rs` explicitly states the root cause: "The `RecordedStorageCounter` only runs inside the VM, so it bounds `FunctionCall` actions alone; other actions in the same receipt could record proof past the limit" [4](#0-3) . `RecordedStorageCounter::observe_size` (`runtime/near-vm-runner/src/logic/recorded_storage_counter.rs:19`) is only invoked from VM host functions like `storage_read`/`storage_remove`/`storage_write` in `logic.rs` and the wasmtime runner [5](#0-4) , i.e. it is wired exclusively into `FunctionCall` execution.

Native (non-`FunctionCall`) actions such as `DeleteKey`/`DeleteAccount` go through `access_keys.rs::action_delete_key` → `remove_access_key` → `TrieUpdate::remove(TrieKey::AccessKey{...})`, entirely outside the VM and its `RecordedStorageCounter`. In `TrieUpdate::remove` (`core/store/src/trie/update.rs:169`), the extra "2000-bytes-per-removal" charge in `TrieRecorder::record_key_removal` is applied **only** for `TrieKey::ContractData` keys: `if matches!(trie_key, TrieKey::ContractData { .. }) { recorder.record_key_removal(); }` [6](#0-5) . Access-key removals get no such margin, and — more importantly — they get **no enforcement checkpoint at all** unless `EnforceStorageProofLimitForAllActions` is active, since that is the only mechanism checking non-`FunctionCall` actions' proof growth.

`STABLE_PROTOCOL_VERSION` for this codebase's pinned release is 86 (per `protocol-model/spec/state-storage.md:3,108`), while `EnforcePerReceiptStorageProofLimit.protocol_version() == 86` and `EnforceStorageProofLimitForAllActions.protocol_version() == 87` [7](#0-6) . This means at the currently-stable/pinned protocol version, the precondition described in the question (limit enforcement partially active but not yet extended to all actions) is satisfied: `DeleteKey`/`DeleteAccount`-only receipts are not covered by any proof-size cap.

An attacker (ordinary account holder) can create an account with a very large number of access keys (via many `AddKey` actions/transactions, which are unprivileged and permitted), then submit a single `DeleteAccount` receipt (which internally iterates and removes every access key of the account) or a batch of `DeleteKey` actions in one receipt. Each removal causes normal trie-node reads/writes to be recorded into `PartialStorage` (the proof), and because there is no outer per-action check active pre-v87, the total recorded proof for that single receipt can grow far beyond `per_receipt_storage_proof_size_limit` without the runtime ever rejecting it — bounded only by gas/compute limits and any hard cap on the number of access keys/actions, not by the proof-size mechanism the protocol depends on for stateless-validation witness size guarantees.

### Impact Explanation
This falls under "unbounded recorded witness size / validator resource exhaustion" — the state witness produced for stateless validation can exceed the size the whole witness-distribution/size-limit machinery assumes, increasing bandwidth, memory, and CPU cost for chunk producers and validators, and potentially exceeding hard witness-size ceilings enforced elsewhere in the pipeline (denial-of-service / node resource exhaustion risk), matching NEAR's "unbounded resource use" bounty class. It does not directly cause fund loss but is a metering/limit-bypass defect in a security-relevant control (per-receipt storage proof cap) that the protocol explicitly tracks and intends to close via `EnforceStorageProofLimitForAllActions`.

### Likelihood Explanation
- Fully reachable by an unprivileged account: creating thousands of access keys and issuing a `DeleteAccount`/batch `DeleteKey` receipt requires only ordinary transactions through public RPC.
- The precondition (feature `EnforcePerReceiptStorageProofLimit` active, `EnforceStorageProofLimitForAllActions` not yet active) matches the currently pinned stable protocol version (86) in this repository snapshot, i.e. this is not a purely hypothetical/future-only window — it is the present production configuration for the pinned release documented in `protocol-model/spec/state-storage.md`.
- The gap is explicitly acknowledged by the codebase's own doc comments (`version.rs:451-457`), indicating the developers are aware of and are in the process of closing it, which corroborates that it is currently exploitable pre-v87.
- Practical limits (max access keys per account, max actions per receipt, gas costs of `AddKey`) bound how large a single exploit receipt can get, but nothing in the code ties those bounds to the storage-proof-size limit, so the attack is repeatable across many receipts/accounts to keep pushing witness sizes up in aggregate as well.

### Recommendation
- Do not gate the outer per-action proof-size check behind a separate feature flag from the initial per-receipt limit; enable enforcement for all action kinds as soon as `EnforcePerReceiptStorageProofLimit` activates (i.e., merge/align `EnforceStorageProofLimitForAllActions` into the same activation version as `EnforcePerReceiptStorageProofLimit`, or ship them together).
- Alternatively, apply the outer `recorded_storage_size_upper_bound()` check unconditionally (not gated by `storage_proof_limit_for_all_actions.is_some()`) whenever `storage_proof_size_before_receipt` is `Some`, so any receipt (VM or non-VM actions) is bounded from the moment the base feature is enabled.
- Extend `record_key_removal`'s conservative extra-margin accounting to all removal-triggering `TrieKey` variants (not just `ContractData`), or otherwise justify with a caching-argument comment why native/runtime-driven removals are provably safe from the same abuse — since access keys are attacker-controlled data (number of keys is chosen by the account owner, not "the runtime"), the "removals performed by the runtime are non-malicious" rationale in `update.rs:170-174` does not hold for user-triggered `DeleteKey`/`DeleteAccount` actions.

### Proof of Concept
Integration test modeled on `runtime/runtime/src/tests/apply.rs::test_per_receipt_storage_proof_size_limit` / `test_add_keys_after_large_read_exceed_receipt_storage_proof_limit`:
1. Set `apply_state.current_protocol_version` to a value where `EnforcePerReceiptStorageProofLimit` is enabled but `EnforceStorageProofLimitForAllActions` is not (e.g. `EnforceStorageProofLimitForAllActions.protocol_version() - 1`, which for this repo is protocol version 86).
2. Set up an account and issue enough `AddKey` transactions/receipts to give it thousands of access keys (large enough that the trie subtree holding these keys, once fully touched during `DeleteAccount`, would record a `PartialStorage` far larger than `per_receipt_storage_proof_size_limit`).
3. Commit state, then apply a single receipt containing one `DeleteAccount` action (or a batch of `DeleteKey` actions covering all the keys) against a trie built with `recording_reads_new_recorder()`.
4. Assert:
   - The receipt succeeds (`ExecutionStatus::SuccessValue`/no `ReceiptStorageProofSizeExceeded` error) at the pre-`EnforceStorageProofLimitForAllActions` protocol version, even though `state_update.trie.recorded_storage_size_upper_bound()` measured after the receipt minus before exceeds `per_receipt_storage_proof_size_limit`.
   - Re-running the identical scenario at `EnforceStorageProofLimitForAllActions.protocol_version()` (87) causes the receipt to fail with `ActionErrorKind::ReceiptStorageProofSizeExceeded`, demonstrating the enforcement gap is closed only starting at that version and confirming the vulnerability window at the currently pinned stable version (86).

        // We count removals performed by the contracts and charge extra for them.
        // A malicious contract could generate a lot of storage proof by a removal,

                recorder.record_key_removal();
            }
        }
