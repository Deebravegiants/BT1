### Title
TOCTOU in keychain `signBuffer` allows a frozen-but-getter-based `KeyIdentifier`-like object to sign for a derivation path different from the one validated - ([File: features/keychain/module/crypto/ed25519.js], [File: features/keychain/module/keychain.js])

### Summary
`ed25519.js#signBuffer` forwards the caller-supplied `keyId` unchanged into `Keychain#getPrivateHDKey`, unlike `exportKey`/`getPublicKey` which first normalize it via `new KeyIdentifier(keyId)`. Because `throwIfInvalidKeyIdentifier` validates the raw object by constructing a *temporary*, discarded `KeyIdentifier` (reading `keyId.derivationPath` once) and only checks `Object.isFrozen(keyId)`, an attacker can supply a frozen object whose `derivationPath` is a getter that returns a different path on the second read — the one destructured for the actual `master.derive(derivationPath)` call.

### Finding Description
`Keychain#getPrivateHDKey` (`features/keychain/module/keychain.js:223-246`) is the single choke point used by `ed25519.create(...).signBuffer` (`features/keychain/module/crypto/ed25519.js:7-11`, which just calls `getPrivateHDKey({ seedId, keyId })`): [1](#0-0) 

Inside `#getPrivateHDKey`, `throwIfInvalidKeyIdentifier(keyId)` is called (line 228) before `const { derivationAlgorithm, derivationPath, keyType } = keyId` (line 234) is used in `master.derive(derivationPath)` (line 245): [2](#0-1) 

`throwIfInvalidKeyIdentifier` requires `Object.isFrozen(potentialKeyIdentifier)` and `KeyIdentifier.validate(potentialKeyIdentifier)`: [3](#0-2) 

`KeyIdentifier.validate` only performs `new KeyIdentifier(potentialKeyIdentifier)` in a try/catch and discards the constructed instance — it reads `derivationPath` exactly once to build a throwaway object, it does not persist or reuse that read value: [4](#0-3) 

`Object.freeze()` only makes an object's own property descriptors non-configurable/non-writable; it does not make an accessor (`get`) property return a deterministic value. A getter already defined on a frozen object can still execute arbitrary logic and return different values on each invocation. Therefore an attacker-controlled, frozen plain object such as:
```js
Object.freeze({
  keyType: 'nacl',
  derivationAlgorithm: 'SLIP10',
  assetName: undefined,
  get derivationPath() { return firstCall ? "m/44'/0'/0'" : "m/44'/999'/0'" },
})
```
passes `throwIfInvalidKeyIdentifier` (the getter is invoked once during `KeyIdentifier.validate`'s internal construction, returning a valid-looking path P1, and `Object.isFrozen` is true), but the actual `derivationPath` used moments later in `#getPrivateHDKey`'s destructuring (line 234) invokes the getter a second time, returning P2, which is what actually gets passed to `master.derive(derivationPath)`.

Contrast this with `exportKey` and `getPublicKey`, which explicitly call `keyId = new KeyIdentifier(keyId)` before invoking `#getPrivateHDKey`, converting `derivationPath` into a fixed, non-getter data property (see `KeyIdentifier` constructor, lines 40-51 of `key-identifier.js`) and closing this gap for those code paths: [5](#0-4) [6](#0-5) 

`Keychain#signBuffer`, however, does not do this normalization before dispatching to `this.ed25519.signBuffer({ seedId, keyId, data })`: [7](#0-6) 

### Impact Explanation
An unprivileged origin/dapp/RPC caller able to supply an object (instead of a real `KeyIdentifier` instance) as `keyId` to `keychain.signBuffer`/`ed25519.signBuffer` can cause the wallet to derive and sign with a private key at a derivation path different from the one that any upstream code path used to display/validate/log/approve the signing request (since that upstream code and the internal validation both only see the getter's first-read value P1, while the actual signing key comes from a second read P2). This is a wrong-account signing / consent-bypass primitive: the user (or any approval UI) believes they approved signing for account/path P1, but the wallet actually signs with the key at path P2.

### Likelihood Explanation
Feasibility depends entirely on whether attacker-controlled, non-`KeyIdentifier`-instance objects can reach `signBuffer` as `keyId` — e.g., through a loosely-typed RPC/IPC deserialization boundary that reconstructs `keyId` as a plain object (possibly with defined getters) rather than instantiating the real `KeyIdentifier` class. This repository (keychain module) does not itself enforce that `keyId` is a `KeyIdentifier` instance for the `signBuffer` path (only `Object.isFrozen` + structural `validate`), so the vulnerability is real and reproducible purely from the keychain module's code, though its ultimate exploitability is gated by whatever caller/RPC layer constructs `keyId` before invoking `signBuffer`.

### Recommendation
In `Keychain#signBuffer` (and anywhere else `keyId` is accepted from external input), normalize the identifier once via `keyId = new KeyIdentifier(keyId)` before any further use — mirroring `exportKey`/`getPublicKey` — so that `derivationPath` becomes a fixed data property rather than a re-invokable getter. Additionally, `throwIfInvalidKeyIdentifier` should reject `keyId` unless it is `instanceof KeyIdentifier` (rather than merely frozen + structurally valid), since `Object.isFrozen` does not guarantee getter-return determinism.

### Proof of Concept
```js
// features/keychain/module/__tests__/toctou-derivation-path.test.js
import { Keychain } from '../keychain.js'

test('signBuffer must reject a keyId whose derivationPath getter returns a different value on each read', async () => {
  const keychain = new Keychain({})
  const seedId = await keychain.addSeed(/* 64-byte seed */ someSeed)
  await keychain.unlockPrivateKeys([someSeed])

  let reads = 0
  const maliciousKeyId = Object.freeze({
    keyType: 'nacl',
    derivationAlgorithm: 'SLIP10',
    assetName: undefined,
    get derivationPath() {
      reads += 1
      return reads === 1 ? "m/44'/0'/0'/0'/0'" : "m/44'/60'/0'/0'/0'"
    },
  })

  // Expected: the wallet must reject this object outright (not a real KeyIdentifier instance),
  // because it cannot guarantee the path used for validation equals the path used for signing.
  await expect(
    keychain.signBuffer({
      seedId,
      keyId: maliciousKeyId,
      data: new Uint8Array(32),
      signatureType: 'ed25519',
    })
  ).rejects.toThrow()

  // If this instead resolves successfully, assert the actual derived key does NOT correspond
  // to a second, different read of derivationPath, proving the TOCTOU:
  // (in current code this assertion FAILS, showing reads === 2 and P2 was used for derivation)
  expect(reads).toBeLessThanOrEqual(1)
})
```
