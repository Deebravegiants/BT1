### Title
Webhook `shop` (and `topic`/`webhook-id`) attribution is not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying an HMAC over the raw request body, then dispatches the handler using a `shop` value that is read from an HTTP header that is never included in that HMAC computation. This breaks the identity binding `verified_bytes == attributed_shop`, allowing a request whose body+HMAC pair is valid for one shop to be re-attributed to an arbitrary victim shop merely by changing the `shopify-shop-domain` header.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

Meanwhile `shop` (the tenant identifier the gem hands to the application) is parsed straight out of the `shopify-shop-domain` / `x-shopify-shop-domain` header, with no cryptographic relationship to the signed bytes: [2](#0-1) 

`Registry.process` validates only the HMAC over that signable string (the body), and — once it passes — trusts `request.shop` (and `request.topic`, `request.webhook_id`) to build the `WebhookMetadata` passed to the application's handler: [3](#0-2) 

`HmacValidator.validate` itself is generic and only signs/compares whatever `to_signable_string` returns — it has no knowledge of `shop`: [4](#0-3) 

The identity binding that should hold is:
`hmac_verified(raw_body) == true` **and** `shop == the shop whose secret actually produced that HMAC`.

Because the app's `api_secret_key` (the HMAC key) is the same for **every** shop that installs the app (it is not a per-tenant key), any shop that legitimately installs the app can obtain a validly-signed `(body, hmac)` pair for events it controls (e.g. by creating a product/customer/order with attacker-chosen field values in its own store, which Shopify will sign with the app's shared secret and deliver as a real webhook). Since `shop` is excluded from the signed bytes, that same valid `(body, hmac)` pair can be replayed to the app's webhook endpoint with the `shopify-shop-domain` header swapped to a victim shop's domain. `HmacValidator.validate` still passes (it never looked at the shop header), and `Registry.process` forwards `WebhookMetadata.new(... shop: request.shop ...)` — i.e. the victim's domain — down to the application's `WebhookHandler#handle`.

### Impact Explanation
Any application built on this gem that uses `WebhookMetadata#shop` to key tenant-scoped state (session lookup, per-shop database records, triggering per-shop business logic) can be made to process attacker-supplied payloads as if they originated from a different, victim tenant. This is a cross-tenant access primitive: an unprivileged attacker who merely installs the app on their own store can forge webhook deliveries attributed to another merchant's shop, without ever needing that merchant's or the app's credentials.

### Likelihood Explanation
Requires only: (1) the attacker's own (real, unprivileged) shop installs the target app so it receives genuine, correctly-signed webhooks, and (2) the ability to make an arbitrary HTTP POST to the app's public webhook endpoint with modified headers — both trivial for any internet user who can install/use the app. No secrets, tokens, or privileged access are needed.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the signed material, or otherwise cryptographically verify that the `shopify-shop-domain` header matches the shop the HMAC was actually generated for (e.g., include the header value in `to_signable_string`, or require the caller to supply/verify the expected shop out of band and compare it against a value derived from verified data, not from an untrusted header).

### Proof of Concept
1. Attacker installs the target app on their own (fully legitimate, unprivileged) Shopify dev store `attacker.myshopify.com`.
2. Attacker creates a resource (e.g., a customer) with attacker-controlled field values, triggering Shopify to send a real webhook to the app's endpoint: body `B`, header `shopify-hmac-sha256: HMAC(secret, B)`, header `shopify-shop-domain: attacker.myshopify.com`.
3. Attacker intercepts/replays this exact request but rewrites the `shopify-shop-domain` header to `victim.myshopify.com`, keeping `B` and the HMAC unchanged.
4. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` (via `to_signable_string` returning only `B`) — this still matches, since the shop header was never part of the signed string: [5](#0-4) 
5. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker-controlled B>, ...)`, and any application logic keyed on `shop` now acts on the victim tenant using attacker-controlled data.
