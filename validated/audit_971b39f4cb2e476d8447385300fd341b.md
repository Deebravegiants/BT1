Confirmed the vulnerability: `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb`) validates the HMAC via `Utils::HmacValidator.validate(request)`, but `Request#to_signable_string` returns only `@raw_body`, meaning the `shop`, `topic`, `api_version`, and `webhook_id` fields—read straight from unauthenticated HTTP headers (`shopify-shop-domain`/`x-shopify-shop-domain`, etc.)—are never covered by the HMAC signature (`lib/shopify_api/webhooks/request.rb`).

### Title
Webhook shop/topic identity spoofing via HMAC-uncovered headers - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant (`shop`), `topic`, `api_version`, and `webhook_id` used to route and process a webhook entirely from raw, unauthenticated HTTP headers, while the HMAC signature that `Registry.process` checks only covers the raw request body [1](#0-0) . This breaks the intended identity binding: `hmac_valid(body) == true` is treated as proof that `(shop, topic, body)` as a tuple is authentic, when in fact only `body` is authenticated.

### Finding Description
`Registry.process` does:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
handler = @registry[request.topic]&.handler
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))
``` [2](#0-1) 

`HmacValidator.validate` recomputes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` header using `OpenSSL.secure_compare` [3](#0-2) . For webhooks, `to_signable_string` is defined as simply `@raw_body` [4](#0-3) , while `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from headers with no cryptographic linkage to the signed bytes [5](#0-4) .

Compare this to the OAuth callback path, where `AuthQuery#to_signable_string` explicitly includes `shop`, `host`, `code`, `state`, and `timestamp` in the signed content [6](#0-5)  — the webhook path lacks this equivalent binding for `shop`/`topic`.

Because Shopify signs webhooks per-app with the single shared `api_secret_key` (not per-shop), any shop that has the app installed receives webhooks with a valid `(raw_body, hmac)` pair for that same shared secret. An attacker who owns/controls a store with the app installed can capture one of their own legitimate webhook deliveries (raw body + `X-Shopify-Hmac-Sha256` value), then resend that exact `(body, hmac)` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain (and/or a different `X-Shopify-Topic`). `Utils::HmacValidator.validate` will still return `true` because it only checks the body bytes, and `Registry.process` will dispatch the attacker-supplied body to the handler tagged with `shop: <victim-shop>`.

### Impact Explanation
This is a broken authentication binding: `shop_verified_by_hmac == shop_used_for_processing` does not hold, since only the body is verified while `shop` (and `topic`) come from unauthenticated headers. Any host application that trusts `WebhookMetadata#shop` to attribute or persist webhook data per-tenant (a documented, expected usage pattern per `docs/usage/webhooks.md`) can have attacker-controlled event data cross-tenant misattributed to an arbitrary shop domain, satisfying the "cross-tenant access" Critical impact criterion.

### Likelihood Explanation
Any unprivileged internet user who can install the app on their own development/trial store (a normal, unprivileged action for public or even private Shopify apps) can obtain a valid `(raw_body, hmac)` pair signed with the app's shared `api_secret_key`, then replay it against the app's public webhook endpoint with a forged `shop-domain` header — no access token, leaked credential, or privileged access is required.

### Recommendation
Bind the `shop` (and ideally `topic`, `webhook_id`) to the HMAC-verified content, e.g. by including them in `to_signable_string`, or by cross-checking `request.shop` against a shop known to have registered that specific webhook subscription (e.g., verifying `webhook_id` against records created during registration for a specific session/shop) before dispatching to the handler.

### Proof of Concept
```ruby
# Attacker owns shop "attacker.myshopify.com" with the app installed.
# Shopify sends a legitimate webhook:
raw_body = '{"id": 1, "note": "hello"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_SECRET, raw_body)
hmac_b64 = Base64.encode64(hmac)

# Attacker replays the same body+hmac but swaps the shop-domain header:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => hmac_b64,       # unchanged, still valid for raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged
  "x-shopify-webhook-id" => "attacker-controlled",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) => true (only checks raw_body)
# handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "orders/create", body: {...}))
```
`Registry.process` accepts this forged request because the HMAC check in `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) never inspects `request.shop` or `request.topic`, both sourced from attacker-controlled headers in `lib/shopify_api/webhooks/request.rb`.
