This confirms the pattern: `Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are all read from unauthenticated headers [2](#0-1)  and are forwarded verbatim into `WebhookMetadata` that the app's `WebhookHandler#handle` acts on [3](#0-2) [4](#0-3) . `HmacValidator.validate` only checks the HMAC over `to_signable_string` (the raw body) against the app's single `api_secret_key` [5](#0-4) .

Because Shopify signs webhooks per-app (not per-shop) using the app's `client_secret`, any shop that has installed the app can obtain a validly HMAC-signed body/signature pair from Shopify for its own webhook deliveries. Since the `shop-domain` header is never included in the signed content, that same valid `(raw_body, hmac)` pair can be resent with an arbitrary `X-Shopify-Shop-Domain` header pointing at a victim shop, and `Registry.process` will accept it as authentic and hand the attacker-controlled body to the handler labeled with the victim's shop domain.

### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature validated by `Utils::HmacValidator` never covers the `shop`, `topic`, `webhook_id`, or `api_version` values. These fields are read straight from unauthenticated headers and passed through to the app's webhook handler as if they were verified.

### Finding Description
`Request#hmac` and `#to_signable_string` bind the signature check only to `@raw_body` [6](#0-5) . Meanwhile `#shop`, `#topic`, `#webhook_id`, and `#api_version` are pulled from HTTP headers with no cryptographic tie to the body [2](#0-1) . `Registry.process` validates only the HMAC and then trusts `request.shop`, `request.topic`, etc., to build `WebhookMetadata`, which is handed directly to the registered `WebhookHandler` [7](#0-6) .

Shopify computes the webhook HMAC using the app's single `client_secret`, shared across every shop that installs the app — it is not per-shop. That means the equality the gem implicitly relies on — "HMAC-authenticated payload" == "payload legitimately destined for the shop named in the header" — does not hold. An attacker who installs the target app on their own (attacker-controlled) shop receives genuinely-signed `(raw_body, hmac)` pairs from Shopify. Because the header is outside the signed content, the attacker can replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the victim's shop domain in the `X-Shopify-Shop-Domain` header. `HmacValidator.validate` still succeeds (it only checks the body), and the handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's own webhook body>, ...)`.

### Impact Explanation
If a host application's webhook handler uses `data.shop` to key session/state lookups or writes body content into per-tenant storage (the intended usage pattern shown in this gem's own tests and docs, e.g. `WebhookMetadata` carrying `shop` for routing) [8](#0-7) , an attacker can inject attacker-chosen, validly-"authenticated" webhook data into a victim shop's context — a cross-tenant data-confusion/injection primitive carried entirely by this gem's trust decision.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the target app on any shop they control (a normal, unprivileged action for a public app) and be able to POST to the app's registered webhook endpoint with a modified header — no access to `api_secret_key` or any victim credential is needed.

### Recommendation
Bind the shop identity to the verification: include the `shop-domain` (and ideally `topic`/`webhook-id`) header value in the signed string checked by `HmacValidator`, or otherwise reject processing when the shop advertised in the header cannot be corroborated (e.g., cross-check against the shop associated with the session/access token used to register that specific webhook subscription) before constructing `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, receiving a legitimate webhook POST with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(api_secret_key, B)`).
2. Attacker resends the identical body `B` and header `H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `B` and succeeds [9](#0-8) .
4. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's body>, ...)`, and the app processes attacker-controlled data under the victim shop's identity.
