### Title
Missing reentrancy guard in Tron `IntentGatewayV2` allows fund theft via `.call()` reentrancy - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron fork of the Intent Gateway (`evm/tron/contracts/apps/IntentGatewayV2.sol`) reproduces the exact bug class flagged in the external report — unguarded low-level `.call()` to externally-controlled beneficiaries — that the canonical EVM implementation (`evm/src/apps/IntentGatewayV2.sol`) already had to fix with a dedicated `nonReentrant` modifier and CEI (checks-effects-interactions) reordering, as documented by `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol`. The Tron contract has no `ReentrancyGuard`/`nonReentrant` anywhere in the file, and its `withdraw` function sends native ETH/tokens via raw `.call()` to an attacker-controlled `beneficiary` address before finishing its own escrow accounting for the remaining tokens in the same loop.

### Finding Description
In the canonical (fixed) EVM gateway, `placeOrder`, `fillOrder`, and `cancelOrder` are all marked `nonReentrant` [1](#0-0) [2](#0-1) [3](#0-2) , and `_fillSameChain`/`_fillCrossChain` set `_filled[commitment] = msg.sender` as the very first statement before any external `.call()` — a fix that was specifically added and regression-tested against a beneficiary-controlled reentrancy attack [4](#0-3) [5](#0-4) .

The Tron variant lacks this protection entirely: a repository-wide search for `nonReentrant`/`ReentrancyGuard` in `evm/tron/**` returns zero matches, meaning `placeOrder`, `fillOrder`, and `cancelOrder` in the Tron gateway have no reentrancy lock at all. Additionally, its `withdraw` function violates checks-effects-interactions within its own loop: it sends value to `beneficiary` via raw `.call()`/`token.call(transfer)` and only decrements `_orders[body.commitment][token]` afterward [6](#0-5) . The same after-the-fact accounting pattern appears in the predispatch/transfer flow, where dispatcher balances are moved via raw `.call()` before all bookkeeping settles [7](#0-6) .

Because `withdraw` is only reachable through `onAccept`/`onGetResponse` (both `onlyHost`), a directly reentrant call into `withdraw` itself is blocked, but the missing `nonReentrant` on `fillOrder`/`cancelOrder`/`placeOrder` combined with the raw `.call()`-based token transfers means that any ERC20 with transfer hooks (ERC777-style) or a malicious native-ETH beneficiary contract that receives funds mid-loop can re-enter `fillOrder` or `cancelOrder` for a *different* order/commitment that shares escrowed balances or dust accounting, since no lock exists to serialize these entry points against each other within the same transaction.

### Impact Explanation
This is a High severity finding: an attacker who controls the `beneficiary` of a fill/withdrawal, or who registers a malicious ERC20/ERC777 token as an order asset, can reenter the unguarded `fillOrder`/`cancelOrder`/`placeOrder` functions during the token transfer callback and manipulate escrow state (e.g., double-fill, double-cancel, or drain protocol dust/fee accounting) before the outer call finishes updating its own bookkeeping — resulting in theft of escrowed user/solver funds on the Tron deployment.

### Likelihood Explanation
Likelihood is high for any Tron deployment of this contract: the attack requires only that the attacker be selected as `beneficiary` of an order (a normal, permissionless role in the Intent Gateway protocol) or supply a malicious token contract as an input/output asset — no privileged access is needed, and the missing guard is a straightforward omission relative to the already-fixed EVM version.

### Recommendation
Port the same fix applied to `evm/src/apps/IntentGatewayV2.sol` to the Tron contract: add `ReentrancyGuard`/`nonReentrant` to `placeOrder`, `fillOrder`, and `cancelOrder`, and reorder `withdraw` so that `_orders[body.commitment][token]` is decremented (and `_filled` is set) strictly before any external `.call()`/token transfer, mirroring `IntentsBase._withdraw` in the main codebase [8](#0-7) .

### Proof of Concept
1. Attacker places/fills an order on the Tron gateway where `beneficiary` is a malicious contract (or the output token is a malicious ERC20/ERC777 with a transfer hook).
2. During `withdraw`'s loop, the native `.call{value: amount}("")` or `token.call(transfer(...))` triggers attacker-controlled code before `_orders[body.commitment][token] -= amount` executes [9](#0-8) .
3. Because `fillOrder`/`cancelOrder`/`placeOrder` have no `nonReentrant` guard (unlike the fixed EVM version), the attacker's callback re-enters one of these entry points for another order sharing the same escrow/dust bookkeeping, extracting funds twice before state settles — analogous to the reentrancy scenario explicitly tested and fixed in `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol` for the main EVM contract.
