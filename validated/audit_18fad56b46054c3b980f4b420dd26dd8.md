### Title
Emporium `erc20TokenAddresses=[]` (emporium-min proof) lets attacker execute arbitrary unaccounted token movements out of Emporium, freezing/stealing other users' Emporium-held funds - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
When `circomData.erc20TokenAddresses.length == 0`, `formInputForCircom` routes proof verification to `formInputEmporiumMin`, which is backed by `MainEVMCircuitMin` — a circuit that constrains nothing except `messageSeed`, `outTimeStamp`, `calldataHash`. `EmporiumUpgradeable.runAction` then runs its balance-accounting loop over the (empty) `erc20TokenAddresses` array, so any token balance change caused by the attacker-supplied `ops` is never measured, never turned into a UTXO, and never checked against slippage. Combined with the fact that `stack.signerAddress == address(0)` bypasses the EIP712 signature check in `verifyWallet` and CASE-2 permits an arbitrary `op.endpoint.call{value: op.value}(op.callData)` from Emporium's own context, any unprivileged EOA can generate a trivial min-circuit proof and cause Emporium to move/transfer tokens it holds (deposited earlier by legitimate users) with zero accounting.

### Finding Description
Broken equality: the code assumes `Σ balanceChange[i]` over `circomData.erc20TokenAddresses` equals all token movement caused by `stack.ops` inside `runAction`. When the attacker sets `erc20TokenAddresses = []`, the loop bounds are `0`, so the left side of that equality is vacuously `[]` while the right side (actual token flows produced by `op.endpoint.call`) can be arbitrary: [1](#0-0) 

The min-mode path is selected purely based on array length, independent of any privileged check: [2](#0-1) 

The backing circuit for this mode constrains nothing about tokens, balances, nullifiers or amounts: [3](#0-2) 

`dimensionsCheck`/`checkOnchainCreation` also pass trivially because the attacker controls `dimensions.tokenNumber = 0` to match their own empty arrays: [4](#0-3) 

Inside `runAction`, an attacker sets `stack.signerAddress = address(0)`, which makes `verifyWallet` skip the EIP712 signature check entirely (only `usedMessages` replay-protection remains): [5](#0-4) 

With `signerAddress == address(0)`, every op falls into CASE 2, which performs an arbitrary low-level call to any attacker-chosen `endpoint`/`callData` (only `callHinkalWallet`/`doSendToRelay` selectors are blocked), executed with `msg.sender == Emporium`: [6](#0-5) 

Attacker exploit: call `Hinkal.transact()` with `externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `erc20TokenAddresses = []`, `dimensions.tokenNumber = 0`, and `externalActionMetadata` decoding to an `EmporiumStack{ signerAddress: address(0), ops: [{endpoint: <tokenB or router>, invokeWallet:false, value:0, callData: swap-or-transfer-calldata}] }`. Generate a valid `MainEVMCircuitMin` proof (only requires the attacker's own freely-chosen `messageSeed`), submit the minimal proof — no shielded UTXO ownership, nullifier, or balance knowledge is required. `runAction` executes the op, produces zero balance checks, mints zero UTXOs, and returns `utxoSet.length == 0`. Any tokens moved (e.g. token A swapped into token B inside Emporium, or token B/ETH directly transferred out via `transfer(attacker, amount)`) are fully outside the accounting loop.

Why existing guards fail:
- `onlyAllowedRecipient` only restricts which *contract* (Hinkal.sol) can call `runAction`, not which EOA can drive that call via `transact()` — reachable by any unprivileged attacker.
- `dimensionsCheck`/`checkOnchainCreation` validate internal array-length consistency, not that arrays are non-empty or that all tokens touched by `ops` are listed.
- `verifyWallet`'s signature check is entirely skippable via `signerAddress == address(0)`.
- The balance/slippage/UTXO-minting logic in `runAction` (lines 122–151) is scoped strictly to `circomData.erc20TokenAddresses`, so it structurally cannot see or constrain any token not in that (attacker-chosen, here empty) list.

### Impact Explanation
Prior legitimate depositors have off-chain UTXO notes representing claims on tokens held inside Emporium (created via ordinary non-min `transact()` calls). An attacker's unaccounted emporium-min op can (a) swap that reserve token into a different, unlisted token, permanently breaking the 1:1 backing so the legitimate owner's later withdrawal (a normal proof for the original token) reverts on `BalanceChangeShouldBePositive`/slippage checks — **permanent freezing of user funds**; and/or (b) directly `transfer` any ERC20 (or ETH via `value`) currently held by Emporium to the attacker via CASE-2's arbitrary call — **direct theft of protocol/user funds held in Emporium**. Both fall under Critical: permanent freezing of user funds and/or theft of shielded/backing value with no UTXO ever accounted for the movement. The attack is repeatable per unique `emporiumMessage`/token pair and costs only gas plus generation of a trivial min-circuit proof.

### Likelihood Explanation
Preconditions: Emporium must hold a non-zero balance of some token (true whenever any user has previously deposited via the Emporium action, which is the intended/expected steady state of the contract) and a reachable router/token contract to call. No privileged role, signature, or shielded-fund knowledge is needed — the attacker only needs to construct their own `CircomData`/`Dimensions`/`EmporiumStack` and generate a valid `MainEVMCircuitMin` proof (which only encodes a self-chosen `messageSeed`). This is fully within an unprivileged EOA's capability and is repeatable against any token balance sitting in Emporium.

### Recommendation
Reject/disallow the emporium-min (`erc20TokenAddresses.length == 0`) path whenever `stack.ops` is non-empty, or require that every token address touched by `stack.ops.endpoint`/decoded call effects be explicitly present in `circomData.erc20TokenAddresses` and accounted for by the existing balance/UTXO loop. Additionally, require `stack.signerAddress != address(0)` (i.e., a real signed wallet) for any CASE-2 call to be permitted, or restrict CASE-2 `op.endpoint` to a pre-approved allowlist of routers rather than arbitrary addresses/calldata.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`, mock ERC20 tokens A and B, and a mock swap router.
2. Preload Emporium with token A (simulate a legitimate prior deposit) and set an allowance from Emporium to the mock router (via a legitimate prior emporium action or direct `deal`+`vm.prank` setup for test purposes).
3. Craft `CircomData` with `erc20TokenAddresses = []`, `dimensions.tokenNumber = 0`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, and `externalActionMetadata` encoding `EmporiumStack{signerAddress: address(0), ops: [{endpoint: router, invokeWallet:false, value:0, callData: swap(A->B, amount)}]}`.
4. Generate a valid `MainEVMCircuitMin` proof for a self-chosen `messageSeed`/`emporiumMessage`, satisfying `calldataHash`/`timeStamp` matching.
5. Call `Hinkal.transact()` with this proof/circomData.
6. Assert: (a) `token B.balanceOf(Emporium) > 0` after the call; (b) no UTXO/commitment was inserted for token B (`utxoSet.length == 0`, no `insertCommitments` entry); (c) `deltaAmountChanges` returned to `runAction` has length 0 so it cannot represent the A→B movement; (d) a subsequent call by any address using another emporium-min op (`token B.transfer(attacker, balance)`, `signerAddress = address(0)`) succeeds and drains B to the attacker with no reverts and no balance/slippage checks triggered.

    function formInputForCircom(
        uint256 chainId,
        address verifyingContract,
        CircomData calldata circomData
    ) internal pure returns (uint256[] memory) {
        if (
            circomData.externalActionData.externalActionId ==
            HINKAL_EMPORIUM_ACTION_ID &&
            circomData.erc20TokenAddresses.length == 0
        ) {
            return formInputEmporiumMin(circomData);
        } else {
            return formInputNormal(chainId, verifyingContract, circomData);
        }
    }

    function formInputEmporiumMin(
        CircomData calldata circomData
    ) internal pure returns (uint256[] memory input) {
        input = new uint256[](circomData.publicSignalCount);

        uint16 index = 0;

        input[index++] = circomData.emporiumMessage;

        input[index++] = circomData.timeStamp;
        input[index++] = circomData.calldataHash;
    }

template MainEVMCircuitMin() {
  // Public inputs:
  signal input outTimeStamp;
  signal input calldataHash;

  // Private inputs:
  signal input messageSeed;
