Audit Report

## Title
Deregistering a parathread does not clear stale `assigned_slots::PermanentSlots`/`TemporarySlots` entries, leaving `PermanentSlotCount`/`TemporarySlotCount` overcounted - ([File: polkadot/runtime/common/src/paras_registrar/mod.rs])

## Summary
`Registrar::do_deregister` only checks `paras::Pallet::lifecycle(id)` before purging a para's registrar/lifecycle state and refunding its deposit; it has no awareness of the `assigned_slots` pallet's `PermanentSlots`/`TemporarySlots` maps or `PermanentSlotCount`/`TemporarySlotCount` counters. Because the only code paths that clear those entries and decrement the counters are `assign_perm_parachain_slot`/`assign_temp_parachain_slot` (insert/increment) and the privileged `unassign_parachain_slot` (remove/decrement), a para whose slot lease naturally expires (reverting it to `ParaLifecycle::Parathread`) can be deregistered by its unprivileged manager via the ordinary `deregister` extrinsic while leaving a stale, uncorrectable `PermanentSlots`/`TemporarySlots` entry and an inflated count behind.

## Finding Description
`do_deregister` at [1](#0-0)  only matches on `paras::Pallet::lifecycle(id)` being `Parathread` or `None`, then calls `schedule_para_cleanup`, removes the `Paras` registrar entry, and unreserves the deposit — it never reads or writes `assigned_slots` storage. `deregister` is reachable by a signed manager via `ensure_root_para_or_owner`, which permits the para's own manager as long as it is unlocked, per [2](#0-1) .

On the `assigned_slots` side, `assign_perm_parachain_slot` inserts into `PermanentSlots::<T>` and increments `PermanentSlotCount::<T>` [3](#0-2) , and `assign_temp_parachain_slot` does the analogous insert/increment into `TemporarySlots`/`TemporarySlotCount` [4](#0-3) . The only place these entries/counts are removed/decremented is the privileged `unassign_parachain_slot`, gated by `T::AssignSlotOrigin` [5](#0-4) . There is no hook tying registrar deregistration to `assigned_slots` cleanup, so this is confirmed to be a genuine one-way accounting gap in the code as claimed.

## Impact Explanation
Once a slot lease naturally expires and lifecycle reverts to `Parathread`, an unprivileged manager can call `deregister`, fully removing the para while `PermanentSlots`/`TemporarySlots` and their counts remain stale. Since new assignments are gated by `PermanentSlotCount::<T>::get() < MaxPermanentSlots::<T>::get()` [6](#0-5)  (and the analogous check for temporary slots at lines 347-350), this stale count permanently occupies a slot in the finite pool until a privileged `AssignSlotOrigin` account notices and calls `unassign_parachain_slot`.

However, the `assigned_slots` pallet's own module documentation explicitly states: *"This pallet should not be used on a production relay chain, only on a test relay chain (e.g. Rococo)"* [7](#0-6) . This materially limits the real-world severity: the affected pallet is not part of Polkadot/Kusama production runtimes, and the "resource-seizure" impact is a temporary-network/administrative bookkeeping inconvenience (correctable at any time by a governance/root call to `unassign_parachain_slot`) rather than a loss of funds, chain halt, or unrecoverable state. There is no accompanying loss of user funds, no double-spend, and no privilege escalation — the deposit refund to the manager on deregistration is legitimate and expected behavior for a parathread.

## Likelihood Explanation
The mechanics described are accurate and reproducible: an admin grants a permanent/temporary slot, the lease naturally expires per `PermanentSlotLeasePeriodLength`/`TemporarySlotLeasePeriodLength`, and the manager then calls the unprivileged `deregister` instead of waiting for/prompting `unassign_parachain_slot`. This requires no race condition or protocol violation and is deterministic. That said, it requires a preceding privileged action (an `AssignSlotOrigin` account choosing to grant a slot) and only manifests on test networks where this pallet is actually deployed, reducing real-world attacker incentive and blast radius considerably.

## Recommendation
`do_deregister` (or `schedule_para_cleanup`) should either query and clear `assigned_slots::PermanentSlots`/`TemporarySlots` and decrement the corresponding counters as part of para cleanup, or expose a hook/trait (e.g., `OnDeregister`) that `AssignedSlots` implements, keeping the counts in sync with the registrar's source of truth. Alternatively, `do_deregister` could refuse to deregister a para that still has an active `PermanentSlots`/`TemporarySlots` entry, requiring `unassign_parachain_slot` to run first.

## Proof of Concept
The PoC described in the submission (assign a permanent slot, run chain forward past `PermanentSlotLeasePeriodLength` so lifecycle reverts to `Parathread`, then call `Registrar::deregister` as the manager and observe `PermanentSlotCount`/`PermanentSlots` remain stale, blocking a new assignment via `MaxPermanentSlotsExceeded`) is consistent with the code paths reviewed and would be an appropriate unit test to add to `polkadot/runtime/common/src/assigned_slots/mod.rs`'s test module. This was not independently executed in this review, but the storage read/write logic and the described lease-expiry test (`assign_perm_slot_succeeds_for_parathread`) exist in the codebase and support the claimed reproduction path.

	fn do_deregister(id: ParaId) -> DispatchResult {
		match paras::Pallet::<T>::lifecycle(id) {
			// Para must be a parathread (on-demand parachain), or not exist at all.
			Some(ParaLifecycle::Parathread) | None => {},
			_ => return Err(Error::<T>::NotParathread.into()),
		}
		polkadot_runtime_parachains::schedule_para_cleanup::<T>(id)
			.map_err(|_| Error::<T>::CannotDeregister)?;

		if let Some(info) = Paras::<T>::take(&id) {
			<T as Config>::Currency::unreserve(&info.manager, info.deposit);
		}

		PendingSwap::<T>::remove(id);
		Self::deposit_event(Event::<T>::Deregistered { para_id: id });
		Ok(())
	}
