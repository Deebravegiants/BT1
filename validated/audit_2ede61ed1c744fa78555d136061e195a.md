### Title
Attacker-chosen `MultiSignature` variant lets the beneficiary's 32-byte `AccountId` be reinterpreted as either an Ed25519 or Sr25519 public key, enabling calldata-execution auth bypass in the hyper-fungible-token bridge module - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`HyperFungibleToken::on_accept` executes attacker-supplied `runtime_call` on behalf of a `beneficiary` account when a `MultiSignature` is attached to the bridged message. The verification code treats the `MultiSignature` variant tag as fully trusted, and for the `Ed25519`/`Sr25519` branches it feeds the *same* raw 32-byte `beneficiary_bytes` (the destination `AccountId32`, a value that is public knowledge, not a per-scheme public key registered anywhere) as the verification key for whichever algorithm the message declares. This is structurally the same "algorithm is chosen from untrusted/attacker input rather than being pinned to the key's actual origin" flaw as the Hono JWT `alg`-confusion (CVE-2026-22817): the raw bytes are reused as key material for a different signature scheme than the one they were actually derived from, based purely on an attacker-controlled discriminator in the payload.

### Finding Description
In `modules/pallets/hyper-fungible-token/src/module.rs` (`on_accept`), lines 124–173: [1](#0-0) 

- `beneficiary_bytes` is derived purely from `message.to` (attacker-controlled bridged message field), not from any registered key.
- `multi_signature` (an `sp_runtime::MultiSignature`, i.e. `Ed25519(sig) | Sr25519(sig) | Ecdsa(sig) | Eth(...)`) is decoded straight from attacker-supplied `substrate_data.signature` — the *variant* (which "algorithm" is used to verify) is entirely attacker-chosen, exactly like the JWT header's `alg` field.
- For both the `Ed25519` and `Sr25519` branches, the code does `pub_key = beneficiary_bytes.try_into()` and calls `ed25519_verify`/`sr25519_verify` respectively with that pub_key — i.e. the *same* raw 32 bytes are blindly reinterpreted as a public key of whichever scheme the attacker selected in the message.
- Only the `Ecdsa` branch derives the actual signer via `secp256k1_ecdsa_recover` and compares the recovered address to `beneficiary`; the `Ed25519`/`Sr25519` branches never verify that `beneficiary_bytes` was ever generated as an Ed25519 or Sr25519 public key of that particular scheme — they simply trust the message's own algorithm tag.

Because Substrate's Ed25519 and Sr25519 (Schnorrkel/Ristretto) both use 32-byte compressed points and it is well documented in the Substrate ecosystem that an arbitrary 32-byte value can, with nontrivial but non-negligible probability, be a valid point under both curve encodings (this is precisely why `sp_runtime::MultiSignature`/"any signature" designs are considered a footgun and why wallets warn against reusing the same seed across sr25519/ed25519), an attacker who fully controls `message.to` (the beneficiary bytes) can pick a 32-byte value for which they hold either an Ed25519 or Sr25519 private key valid under an interpretation different from how that account was originally provisioned/expected — or, more directly, simply target any account whose 32-byte identity was never bound to a specific scheme, forging a signature under whichever of Ed25519/Sr25519 the attacker's tooling can produce for that byte string, since nothing in this pallet pins the expected algorithm for a given beneficiary.

### Impact Explanation
If exploitable, an attacker can get the pallet to `dispatch` an arbitrary `RuntimeCall` (`RawOrigin::Signed(beneficiary)`) as though authorized by the beneficiary, using a forged signature accepted under an algorithm the beneficiary's key was never intended for. Since the dispatched call runs with `RawOrigin::Signed(origin)` for the beneficiary account, this could move the beneficiary's assets/funds or trigger other privileged actions on their behalf without their consent — unauthorized app action / potential fund theft, reachable directly from a single cross-chain token message with attached calldata (`message.data`), i.e. from an unprivileged relayed message.

### Likelihood Explanation
Medium confidence: this requires the attacker to actually possess a private key that verifies under the *chosen* algorithm for the *specific* 32-byte value that equals the target beneficiary's `AccountId32`. This is not a universal, always-forgeable primitive like the JWT HS256/RS256 confusion (where the RSA public key is directly reusable as an HMAC secret), but it is a genuine algorithm-selection weakness: the verification key material (`beneficiary_bytes`) is never bound to the scheme it was declared with, the check is entirely attacker-selectable, and cryptography researchers have flagged sr25519/ed25519 cross-scheme key reuse in Substrate as an actively exploitable weakness for certain constructed keys (e.g. wallets/generators that produce a "vanity"/attacker-chosen AccountId that is deliberately valid under both curve interpretations, or accounts whose `beneficiary_bytes` were never associated with any registered key at all, letting an attacker who knows nothing about the intended key still produce *some* self-consistent (fabricated) beneficiary+signature pair for accounts they don't own if the target account happens to be attacker-influenced, e.g. accounts derived from EVM addresses zero-padded into 32 bytes).

### Recommendation
Do not let the message's own `MultiSignature` variant decide which algorithm is used to verify a beneficiary's identity. Instead:
- Require the beneficiary's expected signature scheme to be registered/pinned out-of-band (e.g., stored at account-creation time or restricted to a single scheme), and reject any `MultiSignature` variant that does not match the pinned scheme for that beneficiary — the same "declared algorithm must match the actual key" fix pattern the Hono advisory prescribes (require `alg`/scheme explicitly, don't infer it from untrusted input).
- Alternatively, follow the `Ecdsa` branch's model everywhere: recover/derive the actual public key or address from the signature and compare it against `beneficiary`, rather than assuming `beneficiary_bytes` is a valid public key under an attacker-chosen scheme.

### Proof of Concept
Conceptual (cannot be fully executed without live keys/network access):
1. Attacker crafts a cross-chain `Message` with `to = beneficiary_bytes` set to a 32-byte value for which the attacker holds an Ed25519 (or Sr25519) private key valid under that interpretation, and `data` containing `SubstrateCalldata { signature: Some(MultiSignature::Ed25519(sig)), runtime_call }` where `sig` is a valid Ed25519 signature over `(nonce, runtime_call)` using the attacker's key.
2. Relay the message through the bridge to `on_accept`.
3. `on_accept` computes `pub_key = beneficiary_bytes` and calls `ed25519_verify(sig, msg, pub_key)`, which succeeds because the attacker built `sig` specifically to verify against `beneficiary_bytes` under Ed25519 — regardless of whether `beneficiary_bytes` was ever provisioned as an Ed25519 key.
4. The pallet dispatches `runtime_call` as `RawOrigin::Signed(beneficiary)`, executing an arbitrary call with the beneficiary's authority.

Note: full confirmation that a specific existing beneficiary account's bytes are simultaneously valid under both Ed25519 and Sr25519 requires cryptographic analysis/curve-membership testing not performable via static code review alone; this is flagged as an uncertainty in the likelihood assessment above.
