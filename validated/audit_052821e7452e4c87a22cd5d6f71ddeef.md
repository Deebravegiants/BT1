### Title
Emporium allows unauthenticated arbitrary calls draining un-tracked ETH/token balances via `erc20TokenAddresses.length == 0` "Min" proof path - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
When `circomData.externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `circomData.erc20TokenAddresses.length == 0`, `CircomDataBuilder.formInputForCircom` routes proof generation to `formInputEmporiumMin`, which produces only `[emporiumMessage, timeStamp, calldataHash]` as public input, matching the trivial `MainEVMCircuitMin` template that performs **no note-ownership, no signature, and no balance/root-hash checks** at all — it merely verifies knowledge of `messageSeed` such that `message = Poseidon(messageSeed)`. [1](#0-0) [2](#0-1) 

Because `dimensions.tokenNumber` is set to 0 in this case, `dimensionsCheck` passes trivially and no root-hash/nullifier verification whatsoever is performed for the transaction. [3](#0-2) 

An unprivileged caller can then submit this trivial proof with an attacker-crafted `EmporiumStack` (`stack.signerAddress = address(0)`, arbitrary `ops`). Because `erc20TokenAddresses` is empty, `_externalTransact`'s loop and `EmporiumUpgradeable.runAction`'s pre/post balance-tracking loop over `circomData.erc20TokenAddresses` never execute (both loops are bounded by `circomData.erc20TokenAddresses.length == 0`), so there is no invariant enforcing that funds moved by the `ops` calls came from this transaction's own deposit. [4](#0-3) [5](#0-4) 

`verifyWallet` also returns immediately (after marking `emporiumMessage` used) when `stack.signerAddress == address(0)`, performing zero signature or authorization checks: [6](#0-5) 

The attacker's `ops` are then executed via the "Case 2: Stateless Interaction" branch, which performs a fully attacker-controlled low-level call from the Emporium contract's own address/identity, restricted only from calling `callHinkalWallet`/`doSendToRelay` selectors: [7](#0-6) 

This is the same bug class as the Chainlink report: an unprivileged actor crafts a request whose "callback" (here, `op.endpoint` + `op.callData` + `op.value`) is fully attacker-defined and executed by a contract that may be holding value (ETH sent via `receive()`, or ERC20 tokens/dust left over from prior interactions that are not part of the current tx's `erc20TokenAddresses` set, hence untracked by the balance-delta invariant). [8](#0-7) 

### Finding Description
The Emporium's core safety invariant — "balance moved out must not exceed balance moved in for this tx" — is enforced only over the set of tokens listed in `circomData.erc20TokenAddresses` for that specific transaction, via the before/after balance loop in `runAction`. When a transaction declares zero tokens (`erc20TokenAddresses.length == 0`), which the "Emporium-min" circuit path explicitly supports and which requires no proof of UTXO ownership, no signature, and no root-hash check at all, an attacker can still supply an arbitrary `EmporiumStack` (with `signerAddress = address(0)` to skip the EIP-712 check too) whose `ops` array performs any external call (`op.endpoint.call{value: op.value}(op.callData)`) from the Emporium contract. Any ETH held by Emporium (accepted unconditionally via its `receive()`), or any ERC20 balance the contract holds that is not enumerated in that transaction's `erc20TokenAddresses`, can be moved out with no ownership check whatsoever.

### Impact Explanation
This breaks the balance-preservation invariant of the Emporium/Hinkal external-action system: value held by the Emporium contract that is not "backed" by the current transaction's declared token set can be extracted by any unprivileged caller without proving ownership of any shielded note, without any relayer/EIP-712 signature, and without any nullifier/root-hash check. This is a direct, unauthorized asset movement / theft of protocol-held funds (Critical/High depending on residual balance), matching the Chainlink report's "malicious callback drains oracle-held tokens" pattern exactly, but here the vector is the min-circuit bypass plus the untracked-token gap in the balance loop.

### Likelihood Explanation
Likelihood depends on the Emporium contract actually holding a residual ETH/token balance at the time of attack (e.g., leftover ETH from `receive()`, or dust left from swaps/refunds not swept in the same tx as their deposit). Any unprivileged EOA can trigger the exploit path itself (crafting the trivial min-circuit proof and calling `Hinkal.transact` directly, since `originalSender == sender` and `relay == address(0)` is permitted) — no privileged role, relayer cooperation, or victim action is required.

### Recommendation
- Require `circomData.erc20TokenAddresses.length > 0` (or otherwise disallow the Emporium-min zero-dimension path) whenever `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `stack.ops.length > 0`, so that any value-moving operation is always covered by the balance-delta invariant.
- In `verifyWallet`, never fully skip authorization when `stack.ops` is non-empty; require `stack.signerAddress != address(0)` (and a valid signature) whenever `ops` contains calls with `op.value > 0` or targets not present in `erc20TokenAddresses`.
- Sweep/zero-out or disallow the contract from holding idle ETH/ERC20 balances between transactions, or track *all* token balances (not just the ones declared in `erc20TokenAddresses`) in the pre/post invariant check.

### Proof of Concept
1. Ensure the Emporium contract holds ETH balance (e.g., someone/some prior partial refund sends ETH via the unconditional `receive()` at `EmporiumUpgradeable.sol:369`).
2. Attacker builds a `CircomData` with `erc20TokenAddresses = []`, `amountChanges = []`, `inputNullifiers = []`, `outCommitments = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionData.externalAddress = <Emporium address>`, and `externalActionData.externalActionMetadata = abi.encode(EmporiumStack({v,r,s: 0, signerAddress: address(0), ops: [EmporiumOperation({endpoint: attacker, invokeWallet: false, value: <Emporium's ETH balance>, callData: ""})], maxFee: 0, deadline: 0}))`.
3. Attacker computes `calldataHash` per `CircomDataBuilder.getHashedCalldata`, generates a trivial `MainEVMCircuitMin` proof (attacker just picks any `messageSeed`), and calls `Hinkal.transact` directly as `originalSender == msg.sender` with `relay == address(0)`.
4. `performHinkalChecks` passes (calldata hash matches, dimensions all zero so `dimensionsCheck` is vacuous, no root-hash requirement is hit because `tokenNumber == 0`), proof verifies trivially.
5. `_externalTransact` executes with an empty token loop, then calls `EmporiumUpgradeable.runAction`; `verifyWallet` returns immediately (signerAddress == 0); the ops loop executes `op.endpoint.call{value: op.value}(op.callData)`, sending Emporium's ETH balance to the attacker's address, with `balancesBefore`/`balancesAfter` arrays empty so no revert occurs.

Note: I could not fully verify from the indexed code whether any additional runtime guard elsewhere (e.g., in a `HinkalHelperManager`, deployment configuration, or `ExternalActionBaseUpgradeable`/`ExternalActionBaseV2` not fully retrieved) restricts `stack.signerAddress == address(0)` combined with zero-dimension transactions specifically for the Emporium action; the excerpt of `ExternalActionBaseUpgradeable.sol` was not read in full. If such a repo-wide guard exists, the practical exploitability is reduced to cases where the Emporium contract accumulates un-swept balance.
