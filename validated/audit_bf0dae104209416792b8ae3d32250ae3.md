### Title
Webhook `shop-domain` and `topic` headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the `shop`, `topic`, `api_version`, and `webhook_id` values used by `ShopifyAPI::Webhooks::Registry.process` to route and attribute the webhook to a tenant are taken directly from unauthenticated HTTP headers that are never part of the HMAC-signed content.

### Finding Description
`Registry.process` validates the webhook solely via `Utils::HmacValidator.validate(request)`, which in turn calls `request.to_signable_string`: [1](#0-0) [1](#0-0) 

That method returns only `@raw_body`: [1](#0-0) 

The HMAC is verified with `OpenSSL.secure_compare(computed_signature, received_signature)` where `computed_signature` is derived solely from `verifiable_query.to_signable_string` (i.e., the raw body): [2](#0-1) 

Meanwhile, `Registry.process` trusts `request.shop`, `request.topic`, `request.api_version`, and `request.webhook_id` — all read straight from HTTP headers — to build the `WebhookMetadata` object dispatched to the app's handler: [3](#0-2) 

And `Request#shop`/`#topic`/etc. are simple header lookups with no cryptographic binding to the HMAC: [4](#0-3) 

The identity binding broken is: `HMAC-verified bytes (raw_body)` ≠ `bytes acted upon for tenant identification (shop header)`. Since a single app has one `api_secret_key` shared across every merchant installation, any user who installs the app on their own store legitimately receives valid `(raw_body, x-shopify-hmac-sha256)` pairs computed with that same shared secret. Because the `shop-domain` header is excluded from the signed content, that attacker can replay the same body and HMAC value to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (and/or `x-shopify-topic`) header. `HmacValidator.validate` will still return `true`, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload originated from the victim shop, even though it did not.

### Impact Explanation
This is a cross-tenant identity-binding bypass: an attacker with a legitimate installation of the app (an unprivileged relationship to other tenants) can forge webhook events that the host application will process as if they came from a different, victim shop. Depending on how the host app's registered handler uses `WebhookMetadata#shop` (e.g., to look up per-shop settings, write orders/customers data, or trigger shop-specific side effects), this enables cross-tenant data corruption or disclosure — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation only requires the attacker to be an app user (install the app on any shop, which is normal, low-privilege access) and the ability to POST an HTTP request with attacker-chosen headers to the app's public webhook endpoint (which by design must accept unauthenticated inbound HTTP calls). No access token, `client_secret`, or privileged account is required — only reuse of a webhook payload/HMAC pair that the attacker legitimately received for their own shop.

### Recommendation
Include the shop domain, topic, and any other value used for tenant identification or business logic in the signable content verified by HMAC (or otherwise cryptographically bind the header values to the payload), instead of computing the signature over the raw body alone. At minimum, `Registry.process` should not trust `request.shop`/`request.topic` for authorization or routing decisions unless those values are covered by the verified signature.

### Proof of Concept
1. Attacker installs the app normally on `attacker-shop.myshopify.com`; the app is configured with a single shared `api_secret_key` for all merchants.
2. Shopify delivers a real webhook to the attacker's shop with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker captures `(B, H)` and sends a forged POST to the app's webhook endpoint:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: H
   x-shopify-shop-domain: victim-shop.myshopify.com
   x-shopify-webhook-id: <any>
   Body: B
   ```
4. `Utils::HmacValidator.validate` recomputes the HMAC over `B` only (per `to_signable_string`) and it matches `H`, so validation succeeds: [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload never originated from that shop.
