The `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `Utils::HmacValidator.validate` only proves that the raw body bytes match an HMAC computed over the body with the app's secret [2](#0-1) . The `shop` value returned by `Request#shop` comes straight from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header [3](#0-2) , and `Registry.process` passes that unverified value directly into `WebhookMetadata` used by the app's handler to attribute the event to a tenant [4](#0-3) .

### Title
Webhook shop-domain header is not covered by the HMAC digest, allowing cross-tenant event spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw HTTP body when validating a webhook's authenticity, but hands the caller-supplied `shop-domain` header to the app's webhook handler as the trusted tenant identifier. Because that header is never part of the signed material, an attacker who has captured any single genuine webhook delivery for the app (body + valid `hmac-sha256` value) can replay it with an arbitrary `shop-domain` header and the library will still report `Utils::HmacValidator.validate` as successful, attributing the (unchanged) payload to a shop the attacker chooses.

### Finding Description
`Request#to_signable_string` is defined as simply `@raw_body` [1](#0-0) . `Utils::HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest` over exactly that signable string and compares it to the `hmac-sha256` header using `OpenSSL.secure_compare` [2](#0-1) . The `shop`, `topic`, `api_version`, and `webhook_id` values are all read straight from HTTP headers with no cryptographic binding to the HMAC [5](#0-4) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching to the app's registered handler, then constructs `WebhookMetadata` using `request.shop` (the unauthenticated header value) as the shop identity passed to application code [4](#0-3) . Documentation explicitly tells integrators that `data.shop` is "The shop domain of the webhook" and encourages using it directly for shop-scoped work, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` [6](#0-5) .

This breaks the intended identity binding: `hmac-sha256(raw_body, api_secret_key) == received_hmac` should imply `shop-domain header == the shop that Shopify actually generated this delivery for`, but the header is never part of the signed bytes, so the equality does not hold. Any request with a body/HMAC pair captured from one legitimate delivery (e.g. from logs, a proxy, or a shared testing webhook subscribed to multiple shops during development) can be re-submitted with a different `shop-domain` header and will still pass `process`.

### Impact Explanation
This allows cross-tenant confusion at the trust boundary the gem is responsible for: an app relying on this library's webhook verification to safely key persisted data, jobs, or side effects by `data.shop` can be made to process a genuine, HMAC-valid payload under an attacker-chosen shop identity. Depending on how the host app uses `data.shop` (e.g., to look up per-shop credentials/records, as documented), this can lead to writing or acting on data under the wrong tenant — a cross-tenant access issue.

### Likelihood Explanation
Exploitation requires the attacker to have previously obtained one valid `(raw_body, hmac-sha256)` pair, which is plausible in several realistic non-privileged scenarios (webhook logs, non-TLS-terminated proxies, browser dev tools during testing, or shared api_secret_key across a multi-shop app since the same app secret signs every shop's webhook body). No possession of `api_secret_key` is required to exploit the header substitution itself — only a previously observed delivery.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the material verified against the HMAC (or, at minimum, require the host application to independently authenticate the shop before trusting `data.shop`), so header values cannot be substituted independently of the signed body.

### Proof of Concept
1. Register a webhook handler that trusts `data.shop`, per the documented pattern in `docs/usage/webhooks.md` (e.g. persists/keys data by `data.shop`).
2. Capture one legitimate webhook delivery to the app: raw body `B` and its `shopify-hmac-sha256` header `H` (computed by Shopify over `B` with the app's secret) for shop `victim.myshopify.com`.
3. Replay a request to the app's webhook endpoint with the same body `B` and header `H`, but set `shopify-shop-domain: attacker-controlled-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC only over `B` and succeeds [7](#0-6) ; the handler is invoked with `WebhookMetadata.shop == "attacker-controlled-shop.myshopify.com"` even though the payload `B` was never issued for that shop [8](#0-7) .
