### Title
Non-embedded session cookie stores a predictable, unsigned session ID that lets an attacker hijack another shop's session - (File: lib/shopify_api/utils/session_utils.rb, lib/shopify_api/auth/oauth/session_cookie.rb)

### Summary
For non-embedded (and cookie-fallback embedded) apps, `ShopifyAPI::Auth::Oauth::SessionCookie` stores the raw session ID as its cookie value with no signature or encryption binding it to the browser/session that completed OAuth. `Utils::SessionUtils.cookie_session_id` trusts that cookie value directly as the session lookup key, and `Auth::Session.from` computes that key deterministically as `"offline_#{shop}"` or `"#{shop}_#{associated_user.id}"`. Because the ID is derived from public, guessable inputs (myshopify domain, numeric user id) rather than a random unguessable token, and the cookie itself carries no HMAC/signature, an attacker can forge the cookie value for a victim shop and have the host application (which trusts `SessionUtils`) load and use the victim's stored session/access token.

### Finding Description
The identity binding that should hold is:
`cookie.value (bytes an unprivileged client can set) == session_id that was actually issued to *this* browser after a verified OAuth/HMAC flow for *this* shop`

Looking at the code:

- `Auth::Oauth::SessionCookie` is a plain `T::Struct` with `name`, `value`, `expires` — the `value` is stored verbatim, with no signature/HMAC/encryption over it: [1](#0-0) 
- After a successful OAuth callback, the cookie's `value` is simply set to `session.id`: [2](#0-1) 
- `session.id` is *not* random — it's deterministically derived from `shop` (and user id for online tokens): [3](#0-2) 
- Later, when the app needs to look up "the current session," `Utils::SessionUtils.current_session_id` — for non-embedded apps, or as a fallback for embedded apps without a JWT — reads the session id straight out of the cookie with no verification that it matches anything previously issued to this browser: [4](#0-3)  and [5](#0-4) 

Because `session.id` for an offline session is just `"offline_#{shop}"` (fully predictable from the public myshopify domain) and for an online session is `"#{shop}_#{associated_user.id}"` (shop domain + a small sequential numeric Shopify user id, both easily enumerable/guessable), any client can construct a cookie value naming a *different* shop's session ID. Since `SessionUtils` performs no cryptographic check that the cookie was actually set by this gem's OAuth flow for the current visitor, an attacker who sets `shopify_app_session=offline_victim-shop.myshopify.com` in their own browser and calls into an app that uses `SessionUtils.current_session_id` will have that value returned as "the current session id," which the host application then uses to look up the stored `Session` (containing the victim shop's live access token) from its session storage.

### Impact Explanation
If exploited, this results in cross-tenant access: an attacker session belonging to one browser ends up bound to a stored session (and access token) that was issued to a completely different, unrelated shop, purely because the session-identification scheme relies on unauthenticated, guessable cookie bytes rather than a value cryptographically bound to the OAuth flow that created it. This matches the Critical bar of cross-tenant access to a merchant's stored access token via the application's own session store, reachable purely through gem-provided APIs (`SessionCookie`, `SessionUtils.current_session_id`) without needing the `api_secret_key`, a leaked token, or social engineering.

### Likelihood Explanation
Exploitability depends entirely on the host application calling `ShopifyAPI::Utils::SessionUtils.current_session_id`/`cookie_session_id` as documented, and using its return value to fetch a session from storage — the intended and documented usage pattern of this gem for non-embedded/cookie-based session retrieval. No secrets are required to compute a target session ID: for offline (the default and by far most common) sessions it's simply `"offline_" + <public myshopify domain>`. This is a low-effort, no-credential attack path.

### Recommendation
Do not use a deterministic, guessable value as the session-cookie value/lookup key. Instead:
- Generate a random, unguessable session identifier (e.g., `SecureRandom.uuid`) for the cookie value, independent of `shop`/user id, and store the mapping `random_cookie_id -> real session.id` server-side, or
- Sign/HMAC the cookie value (binding it to `shop`, session id, and an expiry) using `Context.api_secret_key`, and verify that signature in `SessionUtils` before trusting the cookie's session id.
- At minimum, document prominently that host applications must not treat the cookie's session id as authenticated and must independently verify shop ownership before using the resulting session.

### Proof of Concept
1. App is configured non-embedded (or embedded with the cookie fallback path in `SessionUtils.current_session_id`).
2. Victim shop `victim-shop.myshopify.com` installs the app and completes OAuth; app persists a session with id `"offline_victim-shop.myshopify.com"` and a real access token, via [3](#0-2) .
3. Attacker, in their own unauthenticated browser, sets a cookie:
   `shopify_app_session=offline_victim-shop.myshopify.com`
4. Attacker visits any app route that calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`; per [4](#0-3) , this returns `"offline_victim-shop.myshopify.com"` — the attacker never went through OAuth for that shop.
5. The host application (following the gem's intended pattern) looks up the session by that id in its storage, retrieves the victim shop's `Auth::Session` (including its live access token), and the attacker's request is now served in the victim's tenant context.
