### Title
Webhook shop-domain identity is not covered by HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` by signing only the raw HTTP body [1](#0-0) , while `shop` (the tenant identifier used to route/handle the webhook) is read straight from an attacker-controlled HTTP header, `shopify-shop-domain`/`x-shopify-shop-domain`, without being part of the signed content [2](#0-1) . `HmacValidator.validate` only proves the raw body matches the HMAC computed with the app's shared `api_secret_key`; it says nothing about which shop the body belongs to [3](#0-2) . `Registry.process` trusts `request.shop` after only checking `Utils::HmacValidator.validate(request)` and passes it straight to the handler as the tenant identity [4](#0-3) .

### Finding Description
The binding that should hold is: `hmac == HMAC(secret, body || shop)` (or equivalent, cryptographically tying the tenant identity to the payload). Instead the code only enforces `hmac == HMAC(secret, body)`, i.e. `to_signable_string` returns just `@raw_body` [1](#0-0) , and `shop` is parsed independently from the header and never checked against anything cryptographic [2](#0-1) .

Because an app's `api_secret_key` is shared across every shop that installs that app, any tenant that has legitimately installed the app can generate an arbitrary `(body, hmac)` pair that is valid under the shared secret (e.g., by triggering webhook-eligible events in their own store, or via any endpoint of the app that echoes attacker-controlled JSON signed with the app secret). That attacker can then replay the same `body`/`hmac` pair to the app's webhook endpoint while swapping the `x-shopify-shop-domain` header to point at a victim shop. `HmacValidator.validate` still returns `true` since it only checks the body bytes [5](#0-4) , and `Registry.process` will hand the handler a `WebhookMetadata` claiming `shop: request.shop` for the spoofed victim domain [6](#0-5) .

This is exactly the class of bug described in the report: a value (the shop/tenant identity) that is trusted by the consuming logic is not actually constrained by the cryptographic check that is supposed to bind it.

### Impact Explanation
Any host application that keys per-shop state, credentials, or business logic off `WebhookMetadata#shop` (as the gem's own documentation instructs) is exposed to cross-tenant data confusion or corruption: an attacker who controls one shop that installed the app can forge webhooks purporting to originate from any other shop that also installed the same app, without ever needing that shop's own secret. This crosses the tenant-isolation boundary that the HMAC signature is meant to enforce.

### Likelihood Explanation
Exploitation only requires the attacker to install the app on their own shop (or otherwise obtain one valid `(body, hmac)` pair for content they control) and the ability to send an HTTP request with a spoofed `x-shopify-shop-domain` header to the app's public webhook endpoint — no access token, `client_secret`, or privileged account is needed.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers (or otherwise obtains) a webhook whose body they control, computing `hmac = HMAC-SHA256(api_secret_key, body)` legitimately delivered by Shopify.
2. Attacker replays that exact `body` and `hmac` to the app's webhook endpoint, but sets the header `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present) [7](#0-6) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only re-hashes `@raw_body` [8](#0-7) .
4. The handler receives `WebhookMetadata.new(... shop: request.shop ...)` with `shop == "victim-shop.myshopify.com"`, even though the payload was never produced by or for that shop [9](#0-8) .

### Recommendation
Include the shop domain (and ideally topic/api-version) in the signed content used for verification, or otherwise cryptographically bind `request.shop` to the HMAC before trusting it — e.g., compute/verify the signature over `shop + raw_body` instead of `raw_body` alone, so a payload signed for one tenant cannot be replayed under a different tenant's identity.
