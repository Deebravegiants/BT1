### Title
Webhook shop identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, but the `shop` (and `topic`/`webhook_id`/`api_version`) identity that the app actually acts on is taken from unauthenticated HTTP headers that are never included in the signed payload. This breaks the binding "shop that produced a valid HMAC == shop the handler executes logic for."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors all read from HTTP headers that are outside the signed material: [2](#0-1) 

`HmacValidator.validate` only verifies `verifiable_query.hmac` against `to_signable_string` (i.e., the raw body) using the app's single `api_secret_key`: [3](#0-2) 

`Registry.process` treats a passing HMAC check as sufficient proof of authenticity for the whole request, then dispatches to the handler using the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id`: [4](#0-3) 

Because `api_secret_key` is shared by the app across every shop that has installed it (not shop-specific), any unprivileged user who installs the app on their own shop can trigger a real webhook, capture the legitimate `(raw_body, hmac)` pair Shopify sends for their own shop, and then replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header value. The HMAC check still passes because it only verifies the body bytes, not the headers. The handler then executes with `shop:` set to an attacker-chosen value — potentially a victim shop's domain — even though Shopify never generated that body for that shop.

**Equality that should hold but doesn't:** `shop bound by HMAC == shop the handler acts on`. In reality, HMAC only binds `raw_body`, while `shop` (the tenant key used by `WebhookMetadata`/handlers) is taken from an independent, unauthenticated header.

### Impact Explanation
This is a cross-tenant identity confusion: an attacker with a legitimate (but unprivileged) installation of the app on their own shop can produce validly-HMAC'd requests and relabel them as belonging to any other shop the attacker names in the header. Any app logic keyed on `WebhookMetadata#shop` (e.g., writing data to a per-shop record, triggering fulfillment/order actions, invalidating tokens, or other tenant-scoped side effects) can be executed against a victim tenant using attacker-supplied body content that Shopify never issued for that tenant. This matches "cross-tenant access," a Critical-impact category per the rules.

### Likelihood Explanation
Likelihood is credible but requires two unprivileged capabilities the attacker controls: (1) installing the same public app on a shop they control to obtain at least one legitimate `(raw_body, hmac)` pair, and (2) being able to send arbitrary headers to the app's public webhook endpoint (standard for any HTTP client — this gem does not require TLS client certs or IP allowlisting to reach the endpoint). No access token, `api_secret_key`, or privileged account is needed. The main constraint is that the attacker can only replay bodies they themselves generated (their own shop's data), not arbitrary attacker-chosen JSON for a victim — but if any handler in the host app only checks `topic`/`shop` and processes the body generically (e.g., a generic "resync this shop" or "shop uninstalled" handler where body content is mostly irrelevant, only the topic+shop matter), the impact is immediately exploitable to cross-tenant effect.

### Recommendation
Bind the shop/topic identity into the HMAC-verified material, or otherwise ensure the same request's headers are validated against the source, e.g.:
- Include `topic`, `shop`, and `api_version` in the string that is HMAC-verified (this would require coordinating with Shopify's signing scheme, since Shopify currently signs only the body — so at minimum the gem should not assume `shop`/`topic` are trustworthy once the body-only HMAC passes).
- At minimum, document/enforce that consuming applications must cross-check `request.shop` against an independently known list of currently-installed shops (session store) before trusting it, and that the library should expose this as a required step rather than implying the HMAC check alone authenticates the full `WebhookMetadata`.
- Consider deriving `shop` from a value that Shopify actually signs (if available in a newer webhook delivery format) rather than the `X-Shopify-Shop-Domain` header alone.

### Proof of Concept
1. Install the target app (a normal, public flow available to any merchant) on `attacker-shop.myshopify.com`.
2. Trigger any registered webhook topic (e.g., `orders/create`) on that shop; capture the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sends to the app's webhook endpoint — this HMAC is valid because `HmacValidator.validate` only checks the body against `Context.api_secret_key`, shared across all shops on the app. [5](#0-4) 
3. Replay the exact same body and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and keep/alter `X-Shopify-Topic` as desired.
4. `Registry.process` accepts the request because `HmacValidator.validate(request)` only checks the (unchanged) body/HMAC pair: [6](#0-5) 
5. The registered handler executes with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though Shopify never issued this webhook for that shop.

Note: Due to index size limits, some webhook-handler or `WebhookMetadata` file contents were only partially retrievable — I was unable to confirm downstream handler code the host application typically writes, but the library-level authentication gap in `lib/shopify_api/webhooks/request.rb` and `lib/shopify_api/webhooks/registry.rb` is clearly established from the available source.
