### Title
RAY value multiplication overflows before the borrow-index cap, permanently freezing a market - ([File: contracts/pool/src/cache/scale.rs](contracts/pool/src/cache/scale.rs))

### Summary
The Namada advisory is an integer-overflow panic reachable by a crafted unprivileged message. The analog on XOXNO Lending is an `i128` overflow inside interest accrual: `scaled_to_original(borrowed_scaled_ray, borrow_index)` computes `scaled * index` as a RAY product, and that product exceeds `i128::MAX` before the `MAX_BORROW_INDEX_RAY` index cap can clamp the index. Because every pool verb calls `global_sync` first, once the product overflows the market can never accrue again and is permanently frozen.

### Finding Description
- `Cache::calculate_utilization` computes `scaled_to_original(&self.env, self.borrowed, self.borrow_index)` and `scaled_to_original(&self.env, self.supplied, self.supply_index)` on every accrual (`contracts/pool/src/cache/scale.rs:19-27`).
- `scaled_to_original` is a `Ray` multiply (`shares_ray * index_ray`), i.e. `scaled * index / RAY` via `mul_ceil`/`mul_div_ceil`. The intermediate `scaled * index` product can reach ~`scaled * index` where both operands are RAY-scaled; the panic path raises `GenericError::MathOverflow` (`common/src/math/fp.rs:13-16`, `common/src/math/fp_core.rs:164-175`).
- `global_sync` runs `accrue_chunk` unconditionally whenever time elapsed, and every mutating op accrues first (`contracts/pool/src/interest.rs:20-33`).
- The borrow-index cap `MAX_BORROW_INDEX_RAY` is applied inside `accrue_step` to the index, but the overflow happens on `borrowed_scaled * borrow_index`, which grows with total debt size — so for a sufficiently large book the value product overflows while the index is still far below its cap.
- The repo's own integration test proves the end state: `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` reaches `MATH_OVERFLOW` in accrual with `last.borrow_index < MAX_BORROW_INDEX_RAY`, and afterwards `try_withdraw_raw` and `try_repay` both revert with `MATH_OVERFLOW` — "the market is frozen: exits and repayments accrue first and hit the same panic" (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-361`). The test also notes the documented bound in `docs/reference/formulas.md` is wrong, so this is not a correctly documented safety limit.

### Impact Explanation
Permanent freezing of funds. Once `borrowed_scaled * borrow_index` (or `supplied_scaled * supply_index`) exceeds `i128::MAX`, `global_sync` panics on every call. `supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, `claim_revenue`, and `recapitalize` all accrue before acting, so suppliers can never withdraw and borrowers can never repay. There is no rescue path: even a permissionless `update_indexes` call hits the same panic, and the panic is inside pool math, not something governance can patch without an upgrade.

### Likelihood Explanation
Reaching the ceiling requires a very large book (on the order of 10^27 RAY-scaled shares, e.g. ~10^9 whole units of an 18-decimal asset) at sustained high utilization over many accrual periods, as the test demonstrates with a 98% utilized billion-unit market. An unprivileged attacker can set this up via ordinary `supply`/`borrow` calls — caps can be lifted by governance configuration and the attacker only needs capital, not privileges — but the capital requirement and the accrual horizon make it an expensive, slow-to-mount attack rather than a single-transaction exploit. Medium.

### Recommendation
Apply the index cap to the *value* bound, not just the index: before accrual, clamp `borrowed_scaled`/`supplied_scaled` or compute `scaled_to_original` via a saturating/`I256` path and cap the resulting RAY value at `i128::MAX`, mirroring the `mul_div_floor_saturating` primitive already in `common/src/math/fp_core.rs:180-201`. Alternatively, check `scaled * index` for overflow inside `accrue_step` and clamp the index to the largest value that keeps the product in `i128`, so the cap that currently never engages actually bounds the growth. Update `docs/reference/formulas.md` so the documented bound matches the enforced one.

### Proof of Concept
Existing test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361`):

1. Attacker supplies `10^9 * 10^18` units of an 18-decimal market (`t.supply_raw(BOB, "BIG18", principal)`) and borrows 98% of it (`t.borrow_raw(ALICE, "BIG18", debt)`) — all unprivileged `supply`/`borrow` calls.
2. As time advances, `update_indexes` → `global_sync` → `accrue_chunk` recomputes utilization via `scaled_to_original(borrowed, borrow_index)`; the product overflows `i128` and panics with `MathOverflow` while `borrow_index < MAX_BORROW_INDEX_RAY` (asserted at lines 348-353).
3. Subsequent `try_withdraw_raw(BOB, "BIG18", 1)` and `try_repay(ALICE, "BIG18", 1.0)` both revert with `MATH_OVERFLOW` (lines 355-356): all funds in the market are permanently frozen.

Note: I could not read `common/src/rates.rs` (`scaled_to_original`/`accrue_step`) directly to confirm the exact multiply site, but the scale.rs wrappers, the `mul_ceil` semantics in `fp.rs`, and the test's panic-in-`scaled_to_original` comment establish the root cause.
