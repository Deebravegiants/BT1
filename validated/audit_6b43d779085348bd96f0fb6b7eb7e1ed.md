### Title
Webhook shop-domain identity spoofing via HMAC that only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value that a handler acts on directly from the unauthenticated `x-shopify-shop-domain` HTTP header, while `ShopifyAPI::Utils::HmacValidator` only verifies the raw request body against the app's shared secret. The `shop-domain` header is never part of the signed bytes, so the identity binding "shop the handler processes" == "shop implied by the verified bytes" is broken.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook exclusively by checking the HMAC over the request: [1](#0-0) [1](#0-0) 

The HMAC check calls `Utils::HmacValidator.validate`, which computes the signature over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`; none of the Shopify headers (topic, shop-domain, api-version, webhook-id) are included in the signed material: [3](#0-2) 

Yet `shop` — the field that identifies which merchant/tenant the payload belongs to — is read straight from the unauthenticated header and passed unmodified into the handler: [4](#0-3) [5](#0-4) 

Because the app's `client_secret`/`api_secret_key` is shared across every shop that installs the same app (it is not per-tenant), any merchant who installs the app can legitimately receive real `(body, hmac)` pairs for their own shop's webhooks. That attacker-controlled shop can then replay the exact same body+HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the (unmodified) body, so `Registry.process` calls the handler with `WebhookMetadata` claiming the payload came from the victim shop: [6](#0-5) 

If the host application uses `data.shop` to key database writes, cache invalidation, or business logic per tenant (which is the documented purpose of the `shop` field in `WebhookMetadata`), this lets one merchant's attacker-controlled webhook content be attributed to and processed under a different, victim merchant's tenant.

### Impact Explanation
This breaks the equality "identity the HMAC-verified bytes belong to" == "identity the handler is told the data belongs to," resulting in cross-tenant data injection: an attacker-controlled webhook body can be attributed to an arbitrary victim shop, letting one tenant inject or corrupt data belonging to another tenant of the same app. This matches the Critical impact category of cross-tenant access.

### Likelihood Explanation
Requires the attacker to be an unprivileged but legitimate installer of the target app (a normal, unprivileged merchant/internet user of the app), no `api_secret_key`, no leaked credentials, and no privileged account. They only need to capture one genuine webhook delivered to their own store and resend it to the app's public webhook endpoint with a modified shop header — both trivially available via a normal app install and any HTTP client.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header in the HMAC-signed material, or otherwise cryptographically bind the claimed shop to the verified payload, so that `to_signable_string` cannot be satisfied by replaying a genuine payload under a different tenant's identity. At minimum, cross-check the `shop` header against a shop the caller is actually authorized/registered for before dispatching to handlers.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`. Trigger a subscribed webhook topic (e.g. `orders/create`) and capture the raw POST body and its `x-shopify-hmac-sha256` header — both are validly signed with the app's shared `api_secret_key`.
2. Resend the identical raw body and HMAC header to the app's webhook endpoint, but replace `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks `@raw_body`, which is unchanged.
4. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` (line 198-199) invokes the handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON> ...)`, causing the host application to process attacker-supplied content as belonging to the victim tenant.
