Audit Report

## Title
CORS allowlist bypass via improper subdomain suffix matching in gateway HTTP server - (File: core/services/gateway/network/httpserver.go)

## Summary
The gateway's HTTP server implements a wildcard-origin CORS allowlist check (`*.example.com`) using a plain `strings.HasSuffix` comparison without verifying a label/dot boundary. This lets an attacker-controlled domain that merely ends with the allowed suffix (e.g. `evilethereum.org` matching an allowlisted `*.ethereum.org`) be treated as a trusted CORS origin, causing the server to reflect `Access-Control-Allow-Origin` for that attacker origin.

## Finding Description
`isAllowedOrigin` compares an incoming `Origin` header host against configured `CORSAllowedOrigins`. For wildcard entries it strips the `*.` prefix and does a raw suffix check: [1](#0-0) 
This has no `.`-boundary enforcement: `strings.HasSuffix("evilethereum.org", "ethereum.org")` returns `true`, so any operator-configured wildcard allowlist entry (e.g. `https://*.ethereum.org`) can be bypassed by registering an unrelated domain sharing the suffix, without any real subdomain relationship.

The result is consumed directly in `handleRequest`, which reflects the untrusted `Origin` back verbatim if `isAllowedOrigin` returns true: [2](#0-1) 
There is no additional origin-boundary validation elsewhere in the flow — the scheme/port checks preceding this logic do not mitigate the flawed host suffix comparison.

## Impact Explanation
Any browser-based client that visits a page hosted on an attacker-registered domain sharing the allowlisted suffix will have its cross-origin requests to the gateway's HTTP endpoint accepted as if from a trusted origin. The server sets `Access-Control-Allow-Origin` to the attacker's origin, allowing the attacker's page to read the JSON-RPC response returned by `s.handler.ProcessRequest` via the victim's browser. This maps to the in-scope "allowlist bypass / cross-origin response corruption" impact category for the gateway.

## Likelihood Explanation
Exploitation only requires that the operator configure a wildcard CORS entry — a supported, documented configuration pattern (used in `core/scripts/gateway/sample_config.toml`) — and that the attacker register a domain sharing the suffix, which is trivial and requires no privileged access to Chainlink infrastructure. This is reachable by any unprivileged external actor capable of luring a victim's browser to their domain; no operator/admin credentials on the gateway itself are needed.

## Recommendation
Fix `isAllowedOrigin` to require a proper label boundary when matching wildcard hosts, e.g.:
```go
if strings.HasSuffix(originHost, "."+allowedHost) || originHost == allowedHost {
    return true
}
```
instead of a bare `strings.HasSuffix`, so that `evilethereum.org` cannot match `*.ethereum.org`.

## Proof of Concept
1. Configure the gateway with `CORSEnabled: true` and `CORSAllowedOrigins: []string{"https://*.ethereum.org"}`.
2. From a browser page hosted at `https://evilethereum.org`, send `fetch("https://gateway-host/path", {method: "POST", headers: {"Content-Type": "application/json"}, body: "..."})`.
3. Observe the server responds with `Access-Control-Allow-Origin: https://evilethereum.org`, because `isAllowedOrigin` returns `true` due to `strings.HasSuffix("evilethereum.org", "ethereum.org")`, even though `evilethereum.org` is not a subdomain of `ethereum.org`.
4. A Go unit test calling `isAllowedOrigin("https://evilethereum.org")` against config `CORSAllowedOrigins: []string{"https://*.ethereum.org"}` and asserting it returns `false` (currently returns `true`) would directly prove the bug.
