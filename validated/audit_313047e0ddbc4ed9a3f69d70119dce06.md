Analysis confirms a genuine identity-binding break in the webhook processing path that matches the rule's "field acted on but not covered by the HMAC" pattern.

### Title
Webhook `shop` domain is trusted for tenant routing but is not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then dispatches the payload to the registered handler using the `shop` value read from an unauthenticated HTTP header. Because the shop identity is never part of the signed content, the binding `shop asserted in header == shop that produced the signed body` is never enforced.

### Finding Description
`Webhooks::Registry.process` validates the request like this: [1](#0-0) 

The only cryptographic check is `Utils::HmacValidator.validate(request)`, which computes/compares the HMAC using `request.to_signable_string`: [2](#0-1) 

`Webhooks::Request#to_signable_string` returns **only** the raw HTTP body — it excludes every header, including the shop domain: [3](#0-2) [4](#0-3) 

Yet `request.shop` (parsed straight from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header) is exactly the tenant identifier handed to the app's handler for further action: [5](#0-4) 

This is the same class of bug called out in the analog rules: a field that is *acted on* (the shop, used to key tenant data/handler logic) is not covered by the cryptographic proof (`hmac`) that is supposed to authenticate the request. Contrast this with the OAuth callback path, where `AuthQuery#to_signable_string` deliberately includes `shop` in the signed content precisely to bind the shop identity to the HMAC: [6](#0-5) 

The webhook path has no equivalent binding for `shop`.

### Impact Explanation
Any attacker who can obtain one validly-signed webhook body/HMAC pair for the app (trivially available to them by installing the app on a store they control, or from any webhook they can observe, since the signing secret is the *app's* `client_secret` and is identical across all shops that installed the app) can replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary victim shop domain in the `shop-domain` header. `HmacValidator.validate` still succeeds (it never looks at the header), and `Registry.process` will hand the (attacker-controlled) `shop` value plus the replayed body to the app's handler as if it were a genuine event for the victim tenant. Depending on how the host app's handler uses `WebhookMetadata#shop` (e.g., to look up/update per-shop records, or to fulfill mandatory GDPR webhooks like `shop/redact`, `customers/redact`, `customers/data_request`), this enables cross-tenant data confusion/corruption without needing the victim's access token, refresh token, or `client_secret`.

### Likelihood Explanation
Exploitation requires only: (1) obtaining any single legitimately-signed webhook payload for the app (achievable by any unprivileged user who installs the app on their own store, since app-level webhooks are signed with the shared `client_secret`, not a per-shop secret), and (2) sending an HTTP POST to the app's public webhook endpoint with a forged `shop-domain` header. No admin session, access token, or leaked secret is required — this is squarely an "unprivileged internet user" attack path through the gem's own `Webhooks::Request`/`Registry` code.

### Recommendation
Bind the shop identity to the signed content, mirroring what `AuthQuery` already does for OAuth: either include the `shop-domain` header value in `Webhooks::Request#to_signable_string`, or require host applications to pass the expected/registered shop domain into `Registry.process` and reject the request if it doesn't match the value later derived from an authenticated source (e.g., a shop that is already known to have this app installed, tied to the actual signed payload content rather than an arbitrary header).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a store they legitimately control) and triggers a webhook (e.g., `orders/create`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header sent by Shopify — this HMAC is valid because it is computed with the app's shared `client_secret`, not a shop-specific secret.
2. Attacker sends a new HTTP POST to the same app's webhook endpoint with:
   - Body: identical to the captured raw body.
   - Header `X-Shopify-Hmac-Sha256`: identical (unchanged) valid HMAC.
   - Header `X-Shopify-Shop-Domain`: replaced with `victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (the untouched raw body) and finds it matches — validation passes.
4. `Registry.process` builds `WebhookMetadata.new(topic:, shop: request.shop, ...)` with `shop == "victim-shop.myshopify.com"`, taken straight from the attacker-controlled header, and invokes the app's handler as if the event genuinely originated from the victim shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
