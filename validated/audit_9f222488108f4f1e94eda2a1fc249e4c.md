### Title
Tron `IntentGatewayV2.setParams` accepts an unbounded `protocolFeeBps`, allowing user input tokens to be fully or over-fully seized as protocol fee - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment of `IntentGatewayV2` stores gateway configuration (`Params`, including `protocolFeeBps`) via `setParams` without any bounds validation, unlike the canonical EVM implementation which enforces `protocolFeeBps < 10_000` (i.e. < 100%) before accepting it. Because `placeOrder` deducts `protocolFeeBps` directly from every user's escrowed input amount, an out-of-range value (e.g. `>= 10000`) causes users to lose their entire input, or causes an arithmetic underflow revert that denies service, depending on the exact value.

### Finding Description
In the canonical implementation, parameters are only ever written through paths that call `_validateParams(p)`, which the test suite confirms rejects `protocolFeeBps >= 10000` and `destinationFeeBps >= 10000`: [1](#0-0) [2](#0-1) 

In the Tron port, however, `setParams` performs no such validation — it simply checks the caller is `_admin`, clears `_admin`, and stores the raw struct verbatim: [3](#0-2) 

This `_params.protocolFeeBps` (and the per-destination override `_destinationProtocolFees`) is then used unguarded inside `placeOrder`, on the path any unprivileged user reaches by submitting an order with token inputs: [4](#0-3) 

`protocolFee = (originalAmount * protocolFeeBps) / 10_000` and `reducedAmount = originalAmount - protocolFee` are computed with no upper-bound guard on `protocolFeeBps`. If `protocolFeeBps` is ever configured at or above `10000`, `reducedAmount` becomes zero (100% fee, exact match to the reported bug class) or the subtraction underflows and reverts (>100%), bricking order placement for that destination. This is the exact root cause identified in the external report — `feeRate`/fee-percentage state used in a fee calculation with no upstream cap — reproduced here because the Tron variant of the contract omits the validation that its sibling implementation on canonical EVM already performs.

### Impact Explanation
Because the fee percentage is consumed directly against user-escrowed `order.inputs` amounts in `placeOrder`, a misconfigured (or unbounded) `protocolFeeBps` directly and irreversibly confiscates user deposited funds (up to 100%) with no code-level ceiling to prevent it, or permanently denies order placement to a given destination via underflow revert — a fund-loss/freezing outcome matching the target categories (concrete theft / permanent freezing of funds via an unbounded fee applied to a core unprivileged user-facing entry point).

### Likelihood Explanation
The only barrier is that `_params`/`_destinationProtocolFees` are set once via the admin-only `setParams` (and subsequently through cross-chain `UpdateParams` governance messages), so triggering requires a configuration value at or above 10000 bps to be applied. However, unlike the canonical implementation, there is no code-level safeguard preventing this from ever happening by mistake or by any future/careless value chosen for this parameter on Tron, whereas the equivalent EVM contract explicitly guards against it. The absence of validation is a genuine deviation between the two deployed variants of the same contract for identical logic.

### Recommendation
Add the same bound check used in the canonical implementation's `_validateParams` to Tron's `setParams` (and to its `UpdateParams` handler, if a separate one exists in this file), e.g.:
```solidity
if (p.protocolFeeBps >= 10_000) revert InvalidInput();
```
Additionally, defensively bound-check `protocolFeeBps` at the point of use in `placeOrder` before computing `protocolFee`/`reducedAmount`, so that even if a mis-set value slips through configuration, in-flight order placement cannot zero out or underflow user escrow.

### Proof of Concept
1. Deploy Tron `IntentGatewayV2` with `constructor(admin)`.
2. Admin calls `setParams(Params{ ..., protocolFeeBps: 10000, ... })` — succeeds with no revert (contrast with the canonical EVM `initialize`, which reverts per `testRevert_SetParams_ProtocolFeeBpsTooHigh`). [5](#0-4) 
3. A user calls `placeOrder` with `order.inputs = [{token: X, amount: 1000}]`.
4. Inside `placeOrder`, `protocolFee = (1000 * 10000) / 10000 = 1000` and `reducedAmount = 1000 - 1000 = 0` — the user's entire escrowed input is attributed to the protocol fee (`DustCollected` emits the full amount), and the order commitment records `0` as the escrowed amount for the filler, i.e. the user pays 100% in fees. [6](#0-5)
