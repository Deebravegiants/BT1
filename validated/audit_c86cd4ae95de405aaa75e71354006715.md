### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing on replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop` from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but `to_signable_string` (the data actually covered by the HMAC check) is only the raw request body. `ShopifyAPI::Utils::HmacValidator.validate` verifies `hmac(raw_body, api_secret_key)` and never binds the `shop` header (or `topic`, `webhook-id`, `api-version`) into that signature.

### Finding Description
`Utils::VerifiableQuery#to_signable_string` is the only thing `HmacValidator.validate` signs/checks: [1](#0-0) 

For webhooks, `to_signable_string` returns only `@raw_body`, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from unauthenticated headers: [2](#0-1) 

`Registry.process` accepts the request purely based on `Utils::HmacValidator.validate(request)` succeeding, then forwards `request.shop` (the unverified header value) straight to the handler as the tenant identifier: [3](#0-2) 

Because the HMAC only authenticates the byte-identical body, not the shop header, the equality the app implicitly relies on — "shop the payload's signature was produced for" == "shop passed to the handler" — is never checked. Any request whose body matches a body that was legitimately signed by Shopify for the app (e.g., a webhook the attacker's own store received, since the merchant/attacker controls the endpoint receiving their own shop's webhooks) can be replayed with the `x-shopify-shop-domain` header rewritten to a victim shop, and it will still pass `HmacValidator.validate`.

### Impact Explanation
This breaks the tenant boundary the gem promises: `data.shop` handed to the app's `WebhookHandler` is trusted to identify which merchant/tenant a webhook belongs to, but it is attacker-controllable while the signature still validates. An app that uses `data.shop` (from `WebhookMetadata`, built in `Registry.process`) to select which tenant's session/DB record to act on can be tricked into applying a legitimately-signed payload under a different tenant's identity — a cross-tenant confusion. This falls under the "Critical – cross-tenant access" impact bucket since the shop identity binding used for authorization/routing decisions is unauthenticated.

### Likelihood Explanation
Exploitation only requires an attacker who is a normal merchant that has installed the app (an "unprivileged internet user" from the app's perspective, no `api_secret_key`, no access token, no privileged account needed): they legitimately receive HMAC-valid webhooks for their own shop, then resend that exact body to the app's public webhook endpoint with a forged `shop-domain` header naming a different, victim shop. No secret material needs to be recovered because the signature check does not depend on the header at all — it is unconditionally satisfied by any valid `(body, hmac)` pair regardless of header content.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the value that is actually verified — e.g., include `shop-domain` in `to_signable_string`, or require the caller to independently verify `request.shop` against the session/tenant the webhook route expects before trusting `WebhookMetadata#shop`, and document this expectation clearly. At minimum, `Registry.process` should not treat the header-derived `shop` as authenticated data merely because the body's HMAC checked out.

### Proof of Concept
1. App merchant M installs the app on `m.myshopify.com`; the app registers an HTTP webhook.
2. Shopify sends a legitimate webhook to the app: body `{"id":123}`, header `x-shopify-shop-domain: m.myshopify.com`, header `x-shopify-hmac-sha256: <valid HMAC of body>`.
3. M captures this exact request (they control the endpoint or can sniff it), then re-POSTs the identical body and identical `hmac-sha256` header to the same webhook endpoint, but changes `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` recomputes `HMAC(raw_body, api_secret_key)` — unchanged since `to_signable_string` ignores the header — so validation succeeds. [4](#0-3) 
5. `Registry.process` invokes the handler with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop` is now `victim.myshopify.com`, even though the payload was never produced by/for that shop. [5](#0-4)

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
