### Title
Webhook `shop`, `topic`, `webhook-id` and `api-version` are not covered by the HMAC signature, allowing tenant-header spoofing on a validly-signed webhook body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` verifies nothing but the JSON body bytes. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values are read straight from HTTP headers and handed to the app's handler as trusted metadata, without ever being part of the signed payload.

### Finding Description
`Registry.process` accepts a `Request`, checks only `Utils::HmacValidator.validate(request)`, and then builds `WebhookMetadata` from `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version`, which the host app's `WebhookHandler#handle` implementation treats as the authenticated tenant/topic identity: [1](#0-0) 

The HMAC itself is computed only over the raw body: [2](#0-1) 

And `HmacValidator.validate`/`validate_signature` only ever authenticate `to_signable_string`, i.e. the body — never the headers: [3](#0-2) 

The exposed identity binding that should hold is:
`request.shop` (used to build `WebhookMetadata.shop`, the tenant key the host app keys its data/session lookups on) == `shop that Shopify actually signed/authorized this delivery for`.

Because the HMAC covers only `@raw_body`, this equality is never checked — the `shop-domain` (and `topic`/`webhook-id`/`api-version`) headers are attacker-controlled relative to the signature. Any party that has ever observed one genuine, validly-signed webhook body+HMAC pair for the app (e.g., the operator of their own shop that has the app installed, who legitimately receives their own webhooks) can resend that same body/HMAC pair to the app's webhook endpoint while substituting a different `x-shopify-shop-domain` (and/or `x-shopify-topic`/`x-shopify-webhook-id`) header. `HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` will happily dispatch it to the handler tagged with the attacker-chosen `shop`.

### Impact Explanation
This breaks the tenant boundary the gem is documented to enforce for webhook processing: `WebhookMetadata.shop` is meant to unambiguously identify which merchant's data/event this is, but that field is not part of what Shopify's HMAC actually authenticates. Host applications built on this gem's contract (`process` returning "verified" webhooks) will act on `data.shop` as an authenticated tenant identifier — e.g., updating stored per-shop state, dispatching GDPR/`shop/redact`-style logic, or writing merchant-scoped records — for a shop the attacker does not control, using a body they can only replay (not arbitrarily forge, since they don't know `api_secret_key`). This is a cross-tenant integrity/spoofing issue: it lets an unprivileged holder of one valid signed webhook cause the receiving app to attribute that event to any other shop.

### Likelihood Explanation
Requires the attacker to possess at least one genuine, validly-signed webhook delivery for the app (trivially available to any merchant who installs the app on their own store and receives their own webhooks), then replay it against the app's public webhook endpoint with a modified `shop-domain`/`topic`/`webhook-id` header. No knowledge of `api_secret_key` or the target shop's access token is needed. This is a realistic and low-effort attack path for any app that keys per-shop side effects off `WebhookMetadata.shop` as returned by this gem.

### Recommendation
Include the `shop-domain`, `topic`, `webhook-id`, and `api-version` header values in the HMAC-signed payload (`to_signable_string`) the same way Shopify does not intend headers to be trusted independently of the body, or otherwise cryptographically bind them (e.g., require the host app to additionally verify `shop` against a known/registered shop list before trusting `WebhookMetadata.shop`). At minimum, document clearly that `Registry.process`'s HMAC check does not authenticate the `shop`, `topic`, `webhook_id`, or `api_version` fields of `WebhookMetadata`, since these come from unauthenticated headers.

### Proof of Concept
1. App has the gem installed and processes webhooks via `ShopifyAPI::Webhooks::Registry.process`.
2. Attacker installs the app on their own shop `attacker.myshopify.com` and receives a legitimate webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid for `B` under the app's shared `api_secret_key`), `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker resends the exact same `B` and `H` to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim.myshopify.com` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`).
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:13-22`) returns `true` because it only checks `B` against `H`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-200`) builds `WebhookMetadata` with `shop: "victim.myshopify.com"` and dispatches it to the host app's handler as if Shopify had verified this event for `victim.myshopify.com`.

          received_signature = verifiable_query.hmac
