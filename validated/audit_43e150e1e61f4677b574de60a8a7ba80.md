Found the critical finding: the webhook `Request` class binds its HMAC signature only to the raw request body, while the `shop` field used for tenant identification comes from an unauthenticated header that is never covered by that signature.

### Title
Webhook shop-domain header not covered by HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` to authenticate incoming webhook requests via HMAC, but the signable string used for HMAC verification is only the raw request body [1](#0-0) . The `shop` attribute, which host applications use as the tenant key to look up which merchant/session a webhook belongs to, is read directly from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header [2](#0-1)  and is never included in the HMAC-signed data.

### Finding Description
`HmacValidator.validate` verifies the HMAC by computing a signature over `verifiable_query.to_signable_string` and comparing it to `verifiable_query.hmac` [3](#0-2) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [1](#0-0) , and `hmac` is read from the `hmac-sha256` header [4](#0-3) . This mirrors the correct real Shopify webhook verification scheme (body-only HMAC), so the HMAC itself is legitimately body-bound by design.

However, the `shop` accessor used by host applications to identify *which tenant* the webhook body belongs to is derived purely from the `shop-domain` header [2](#0-1) , which is completely outside the HMAC-covered data. The class only validates that the three required headers (`topic`, `hmac-sha256`, `shop-domain`) are *present* [5](#0-4) ; it never verifies that the value of the `shop-domain` header actually matches the shop that generated the signed body/HMAC.

This breaks the intended identity binding: `shop-domain header == shop that produced this HMAC-signed payload`. Since the `hmac-sha256` value depends only on the body content and the shared `api_secret_key`, an attacker who has legitimately received one valid signed webhook body from Shopify for **their own shop** (which is trivial to obtain — any developer can install their own app and receive a legitimately signed webhook for their own store) can replay that exact `(raw_body, hmac-sha256)` pair while substituting an arbitrary victim shop's domain into the `shop-domain` header. Because `to_signable_string` never depends on `shop-domain`, `HmacValidator.validate` will still report success, since it only checks that the payload is properly signed — not that the claimed shop matches the signer.

### Impact Explanation
If the host application (following this gem's documented pattern) uses `Webhooks::Request#shop` to select which merchant's stored session/data the webhook payload should be applied to — which is the exact intended usage pattern for this class, since it exists specifically to expose `shop` alongside HMAC validation — an attacker can trigger cross-tenant data corruption or cross-tenant impersonation: a webhook payload that was legitimately generated for the attacker's own shop, replayed under an arbitrary victim shop identifier, passes signature validation and is then processed as if it originated from the victim's store. This is a cross-tenant boundary violation, since one merchant's HMAC-authenticated event is misattributed to another merchant.

### Likelihood Explanation
Likelihood is high for any application that trusts `shop` on a validated `Request` without independently cross-checking it against a shop the app expects for that specific topic/resource, since the gem does not provide or enforce any additional binding between `shop-domain` and the signed content. Any developer with a Shopify store and app installed can generate arbitrarily many legitimately-signed `(body, hmac)` pairs for known/controlled payload topics (e.g., `orders/create` with attacker-controlled order data) and then splice in a victim's shop domain header when replaying the request to the app's webhook endpoint.

### Recommendation
Include the shop domain in `to_signable_string`, or otherwise cryptographically bind the shop identity to the payload, so that`HmacValidator.validate` fails when the `shop-domain` header doesn't match the shop under which the payload was actually signed. At minimum, document explicitly and enforce that `shop` must never be trusted independently from a signature that doesn't cover it, or change the verification flow so the shop is derived only from a value that is part of the signed content.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a legitimate webhook, e.g. `POST /webhooks` with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid: `HMAC-SHA256(api_secret_key, B) == H`), plus `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker replays the exact same request to the victim app's webhook endpoint, but replaces the header to `X-Shopify-Shop-Domain: victim.myshopify.com` (leaving `B` and `H` unchanged).
3. The app calls `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-hmac-sha256" => H, "x-shopify-shop-domain" => "victim.myshopify.com", ...})` then `ShopifyAPI::Utils::HmacValidator.validate(request)`.
4. `to_signable_string` returns `B` (unchanged), so `HMAC-SHA256(api_secret_key, B) == H` still holds — validation succeeds [1](#0-0) [6](#0-5) .
5. The host app reads `request.shop` and gets `"victim.myshopify.com"` [2](#0-1) , processing the attacker-controlled body `B` as if it were the victim's own data.
