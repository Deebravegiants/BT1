### Title
Withdrawal status misreported when batching multiple same-asset withdrawals — POA bridge matches by `assetId` only, ignoring destination address/index - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal` and the shared `waitForWithdrawalCompletion` helper resolve a withdrawal's on-chain completion status by looking up the POA bridge's response list and matching **only on `assetId`** (`nep141:${near_token_id}`), never on destination address, amount, or withdrawal index. The SDK explicitly supports batching multiple withdrawals into one NEAR transaction (`signAndSendWithdrawalIntent`/`processWithdrawal` batch API). If two withdrawals of the *same* `assetId` (potentially with different destination addresses) are included in the same NEAR transaction, `findMatchingWithdrawal` in both `poa-bridge.ts` and `waitForWithdrawalCompletion.ts` will always return the first list entry whose `near_token_id` matches — this can be the wrong withdrawal from the batch.

### Finding Description
The equality that should hold is: *the withdrawal record returned by the POA indexer for a given `assetId`+`index`+`destinationAddress` in a batch is the withdrawal the caller actually requested.* The code instead breaks this down to `assetId` equality alone: [1](#0-0) [2](#0-1) 

The `index` field is deliberately ignored ("Response list is unsorted, so we match by assetId instead of index"), and there is no tie-breaking by `destinationAddress` or `amount` when multiple withdrawals share an `assetId`. The same limitation is documented and reproduced in the generic `waitForWithdrawalCompletion` helper used elsewhere in `internal-utils`: [3](#0-2) 

Both implementations carry a code comment acknowledging that "multiple withdrawals of the same token in a single transaction are not supported," but nothing in `createWithdrawalIntents`/batch composition (`intent-executer.ts`, `sdk.ts`) actually prevents an integrator from submitting two withdrawals of the same `assetId` to two different destination addresses within one atomic batch (the SDK's batch withdrawal feature is generic and only demonstrated with distinct assets in the README, not enforced to be distinct).

### Impact Explanation
If a batch contains two withdrawals of the same token to two different addresses/amounts, `describeWithdrawal`/`waitForWithdrawalCompletion` can report the wrong `txHash`/`chain`/`status` for a given withdrawal index — i.e., an integrator polling per-withdrawal status could see withdrawal #2 reported as `completed` with the destination tx hash that actually belongs to withdrawal #1 (or vice versa). This is a status/hash misreport that can cause an integrator to credit or refund the wrong leg, or to prematurely mark one withdrawal complete while the other is still pending — matching the "status or hash misreport making an integrator credit or refund twice" impact class.

### Likelihood Explanation
Requires only an ordinary user/integrator action — submitting a batch with two withdrawals of the same asset to different addresses — no malicious relayer, admin, or third party behavior is needed. Likelihood depends on how commonly integrators batch same-asset withdrawals; the SDK's public batch API does not disallow this, so it is a reachable, unprivileged path, though its use may be uncommon in practice since documented examples use distinct assets.

### Recommendation
- Enforce (or document/validate) that batched POA-bridge withdrawals must have unique `assetId`s, or
- Extend `findMatchingWithdrawal` to disambiguate by destination address and amount (not just `assetId`) when multiple candidates match, consistent with the code's own suggested mitigation ("matching could be done by sorting both API results and withdrawal params by amount").
- Apply the same fix to `waitForWithdrawalCompletion`'s `findMatchingWithdrawal` in `internal-utils`.

### Proof of Concept
1. Build a batch of two withdrawal intents in one NEAR transaction, both with `assetId: "nep141:usdc.omft.near"`, but `destinationAddress: A` (index 0) and `destinationAddress: B` (index 1).
2. Publish and confirm the transaction via `signAndSendIntent`/batch withdrawal flow.
3. Call `bridge.describeWithdrawal` for `index: 1` (destination B). Since matching ignores `index`, if the POA bridge indexer returns withdrawal A first in its (unsorted) list, `findMatchingWithdrawal` returns A's `transfer_tx_hash`/status for the query about B.
4. The integrator, trusting `describeWithdrawal({index:1,...})` to describe B's withdrawal, records A's destination tx hash against B, or marks B "completed" using A's completion, producing a mismatched settlement record — as anticipated by the code's own comment at [4](#0-3) .

function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}
