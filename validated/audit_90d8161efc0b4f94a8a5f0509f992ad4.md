### Title
`CallDispatcher.dispatch` has no access control and executes attacker-controlled calls with arbitrary value from its own balance - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher.dispatch` mirrors the vulnerable pattern in the XProvider report: an external entry point takes attacker-controlled `(to, value, data)` and performs a low-level `.call` on it, with the call executing "as" the dispatcher contract. Unlike `EvmHost.dispatchIncoming`, which gates the `IApp.onAccept` low-level call behind `restrict(_hostParams.handler)`, `CallDispatcher.dispatch` is `external` with no caller restriction at all — anyone, not just the token apps (`HyperFungibleToken`/`WrappedHyperFungibleToken`) that are supposed to be the only legitimate callers via a verified ISMP message, can invoke it directly.

### Finding Description
`CallDispatcher.dispatch` decodes an arbitrary `Call[]` and does:
```solidity
(bool success, bytes memory result) = to.call{value: call.value}(call.data);
``` [1](#0-0) 

It has a `receive() external payable {}` to accept ETH transfers, meaning `CallDispatcher` is designed to hold a native-token balance at times. [2](#0-1) 

The `dispatch` function has no `onlyApp`/`onlyHost`/allow-list modifier, so the intended callers (`HyperFungibleToken.onAccept`, `WrappedHyperFungibleToken.onAccept`, and their upgradeable variants) that invoke `ICallDispatcher(_dispatcher).dispatch(message.data)` after verifying an ISMP-sourced message are not the only path to it — anyone can call `dispatch` directly with `Call[]` specifying any `to`, any `value`, and any `data`. [3](#0-2) [4](#0-3) 

Because the low-level call is made from `CallDispatcher`'s own address (`address(this)` is `CallDispatcher`, not the caller), the `msg.sender` on the sub-call is `CallDispatcher`, and `call.value` is drawn from `CallDispatcher`'s own native balance. Any ETH that accumulates in `CallDispatcher` (from the `receive()` fallback, dust, or a partially-failed/looped multicall pattern) is fully drainable by an unprivileged caller who directly calls `dispatch()` with `Call[{to: attacker, value: <balance>, data: ""}]`, since `dispatch` performs no source/authorization check comparable to `EvmHost.dispatchIncoming`'s `restrict(_hostParams.handler)` gate. [5](#0-4) 

This is structurally the same root cause flagged in the external report: an unrestricted low-level `.call` with attacker-controlled target/calldata/value, reachable without going through the verified ISMP delivery path that the rest of the protocol relies on for authorization.

### Impact Explanation
Any native token balance held by `CallDispatcher` (via its `receive()` function) can be drained by any unprivileged address, since `dispatch()` is callable directly, bypassing the ISMP `onlyHost`/source-verification checks that `HyperFungibleToken.onAccept` and `WrappedHyperFungibleToken.onAccept` apply before invoking the dispatcher. This is a concrete theft-of-funds vector for any value that transiently or persistently sits in `CallDispatcher`.

### Likelihood Explanation
Likelihood depends on whether `CallDispatcher` is expected to hold meaningful ETH balances in production. The `receive()` function's presence, with the comment "to accept ETH transfers," indicates the developers anticipated it holding native value at some point, but the reachable call sites I found (`HyperFungibleToken`/`WrappedHyperFungibleToken` `onAccept`) invoke `dispatch()` without forwarding `msg.value`, so no ETH normally passes through this path. If any future or existing integration sends native value to `CallDispatcher` (directly or through a `Call` with `value>0` inside a dispatched batch that leaves change), that balance is unconditionally exposed. I was unable to fully trace whether `IntentGatewayV2`/`IntentsBase.sol` route value through `CallDispatcher` within the available index — this should be verified in a live session.

### Recommendation
Restrict `CallDispatcher.dispatch` to only be callable by an authorized/allow-listed app contract (e.g., a per-app modifier or a caller registry set at deployment), analogous to `EvmHost.dispatchIncoming`'s `restrict(_hostParams.handler)` gate. Alternatively, ensure `CallDispatcher` never retains a nonzero balance between calls (e.g., revert if `address(this).balance` is unexpectedly nonzero after execution, or forbid the `receive()` fallback and require value to be passed through in the same transaction only).

### Proof of Concept
1. Assume `CallDispatcher` at address `D` holds `X` ETH (via its unrestricted `receive()`).
2. Attacker calls `D.dispatch(abi.encode([Call{to: attacker, value: X, data: ""}]))` directly — no ISMP message, no host authorization, no app-level check is required since `dispatch` has no modifier.
3. `D`'s low-level call `attacker.call{value: X}("")` succeeds, transferring all of `D`'s ETH balance to the attacker. [6](#0-5)

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
```

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
