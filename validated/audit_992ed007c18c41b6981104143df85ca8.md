### Title
Retroactive extension of an already-elapsed inactivity window lets `PassphraseCache` return an expired cached passphrase after `changeLockTimer` is called - ([File: features/application/src/modules/passphrase-cache.ts])

### Summary
`PassphraseCache.get()` decides whether to still hand back a cached passphrase (i.e., auto-unlock the wallet) by comparing a *stored checkpoint* (`inactiveAt`) against a *stored TTL* (`ttl`) that can be updated independently and later than the checkpoint. Because `changeTtl()` only rewrites `TTL_KEY` in storage and never touches `INACTIVE_AT_KEY`, increasing the auto-lock timer after the wallet went inactive retroactively re-validates an inactivity period that had already exceeded the TTL that was actually in force while the wallet was backgrounded. This mirrors the referenced Arbitrum BOLD finding: a security-relevant amount ("required stake" there, "lock TTL" here) is changed after a checkpoint was recorded ("last staked assertion" there, `inactiveAt` here), and the code never re-validates or invalidates the stale checkpoint against the new value, producing an inconsistent, exploitable state.

### Finding Description
`PassphraseCache` persists four keys: `passphrase`, `addedAt`, `inactiveAt`, `ttl` [1](#0-0) .

`scheduleClear()` is called on background/inactivity events and stamps `inactiveAt = Date.now()`, using whatever `ttl` happens to already be stored — it does not read or store a fresh `ttl` snapshot at that moment [2](#0-1) .

`get()` later decides validity purely by comparing the *current* `inactiveAt` and `ttl` values read from storage:
```
if (inactiveAt) {
  if (inactiveAt + ttl > Date.now()) {
    return passphrase
  }
}
``` [3](#0-2) 

`changeTtl()` is exposed publicly via `Application.changeLockTimer` → `exodus.application.changeLockTimer({ ttl })` [4](#0-3) [5](#0-4) . When invoked, it overwrites `TTL_KEY` with the new value but never re-checks or re-stamps `inactiveAt`:
```
async changeTtl(ttl: number) {
  const newTtl = Math.min(this.#maxTtl, ttl)
  await this.#autoLockTimerAtom.set(newTtl)
  const passphrase = await this.#storage.get(PASSPHRASE_KEY)
  if (passphrase) {
    await this.#storage.set(TTL_KEY, newTtl)
    void this.#scheduleClear()
  }
}
``` [6](#0-5) 

Because `inactiveAt` is never adjusted or invalidated when `ttl` changes, the check in `get()` is evaluated against a TTL value that did not exist during the elapsed inactivity window. If the TTL is increased any time before the (lazy, on-demand) expiry check in `get()` fires, an inactivity period that had already exceeded the *original* TTL is retroactively treated as still "in activity period," and the cached passphrase is returned, silently auto-unlocking the wallet.

This is the direct structural analog of H-01: a security-relevant configuration value (`requiredStake` in the rollup / `ttl` here) is mutable after the fact, and the code path that decides pass/fail (staker "inactive" check / passphrase "still valid" check) uses a stale checkpoint (`lastStakedAssertion` / `inactiveAt`) combined with the *new* value instead of the value that was actually in effect when the checkpoint was recorded.

### Impact Explanation
An attacker/process able to invoke `changeLockTimer` (e.g., a compromised or malicious dApp/background script with access to the `application` API, or a subsequent legitimate settings change by the user without realizing the side effect) can cause a wallet that should already be considered locked-out-of-cache to still yield its cached passphrase, resulting in unauthorized retrieval of wallet unlock material and effectively bypassing the auto-lock security control. This is a concrete auth-bypass / secret-disclosure impact on the wallet's session/lock trust boundary.

### Likelihood Explanation
Requires the attacker to trigger a `changeLockTimer` call while the app is backgrounded/inactive and after the previously configured TTL window has elapsed but before anything calls `get()` to lazily expire the entry. `changeLockTimer` is a normal, low-privilege API surface (settings), reachable from the SDK's `application.changeLockTimer` without requiring the wallet to already be unlocked or `#applicationStarted` gating (unlike `lock`/`unlock`/`changePassphrase`) [4](#0-3) , making the precondition plausible in normal usage flows (e.g., a settings UI persisting a new timer value on resume).

### Recommendation
- When `changeTtl` is called, re-evaluate the currently stored `inactiveAt`/`ttl` pair against the *old* TTL before applying the new one; if the session would already be expired under the old TTL, clear the passphrase cache instead of silently extending it.
- Alternatively, store a fixed "expiresAt" timestamp computed once at the moment `inactiveAt` is stamped (using the TTL in force at that time), and never allow `changeTtl` to retroactively affect timestamps already committed to storage.

### Proof of Concept
1. User backgrounds wallet with `autoLockTimer = 5m`; `scheduleClear()` runs and stores `inactiveAt = T0`, `ttl = 5m`.
2. Time passes to `T0 + 10m` (session should already be expired, but `get()` has not yet been called to lazily clear it).
3. `exodus.application.changeLockTimer({ ttl: 30m })` is invoked (e.g., by any code path/dApp with access to the `application` API) — `changeTtl` rewrites `TTL_KEY = 30m` in storage, leaving `inactiveAt = T0` untouched.
4. `exodus.application.unlock()`/auto-unlock flow calls `passphraseCache.get()`: `inactiveAt(T0) + ttl(30m) > Date.now()(T0+10m)` evaluates true, so the cached passphrase is returned and the wallet is auto-unlocked, even though the original 5-minute policy had already expired 5 minutes earlier.
