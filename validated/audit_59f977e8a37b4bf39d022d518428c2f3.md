### Title
Webhook `shop` (and `topic`) identity is not covered by the HMAC signature, enabling cross-tenant impersonation - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) and event `topic` from HTTP headers that are never included in the HMAC-signed payload, while `ShopifyAPI::Webhooks::Registry.process` trusts these header-derived values to route and label webhook data as belonging to a specific shop.

### Finding Description
`Request#to_signable_string` returns only the raw request body: [1](#0-0) 

`Utils::HmacValidator.validate` computes/validates the signature exclusively against this signable string using the app's shared `api_secret_key`: [2](#0-1) 

However, `Request#shop`, `Request#topic`, and `Request#webhook_id` are all pulled straight from HTTP headers (`x-shopify-shop-domain`, `x-shopify-topic`, `x-shopify-webhook-id`), which are **not** part of the signed bytes: [3](#0-2) 

`Registry.process` validates only the HMAC (i.e., only that `raw_body` was signed by the app secret at some point) and then unconditionally trusts `request.shop` and `request.topic` when dispatching to the handler: [4](#0-3) 

This breaks the intended identity binding `hmac_valid(raw_body) == shop_is_authentic`. Because the `api_secret_key` (`client_secret`) is shared across all shops that have installed a given app, an attacker who has legitimately installed the app on their own store (an unprivileged tenant with no access to any other merchant's data) can capture a genuinely-signed webhook delivery from their own shop and then freely rewrite the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header before replaying it to the host application's webhook endpoint. The HMAC check still passes because it only re-verifies `raw_body`, but `Registry.process` will hand the handler a `WebhookMetadata`/callback stamped with the attacker-chosen `shop` value, not the shop the body actually came from.

### Impact Explanation
This is a cross-tenant boundary violation: an app built on this gem that keys any per-tenant logic (e.g., "look up shop X's session/token", "update shop X's data", data-deletion/redaction handlers) off `request.shop`/`WebhookMetadata#shop` can be tricked into acting on behalf of, or against, a shop the attacker doesn't control, using only a legitimately-signed payload from the attacker's own store. This matches the Critical-tier "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any host application that relies on `request.shop` from a processed webhook without independently cross-checking it (which is exactly the intended usage pattern of `Registry.process`/`WebhookMetadata`). The attacker needs only their own paid/free installation of the target app and the ability to POST an HTTP request with custom headers to the app's public webhook endpoint — no leaked secrets, tokens, or privileged access required.

### Recommendation
Include the tenant-identifying and event-identifying fields (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed payload verification — e.g., verify against a canonical string that binds these header values together with the body, or independently corroborate `request.shop` against a value derived from signed data before trusting it in `Registry.process`.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; the app is configured with a shared `client_secret`.
2. Trigger any registered webhook topic (e.g. `orders/create`) on `attacker.myshopify.com`; capture the raw POST: headers include `x-shopify-hmac-sha256: <valid-hmac-of-body>`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`.
3. Replay the exact same request to the host app's webhook endpoint, but change `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` still succeeds because it only hashes `@raw_body`, which is unchanged.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb`) invokes `handler.handle` with `shop: "victim.myshopify.com"`, causing the host app to act as if the (attacker-controlled) body originated from the victim shop.
