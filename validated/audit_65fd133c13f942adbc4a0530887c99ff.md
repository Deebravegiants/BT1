Confirmed: `Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are all pulled from unauthenticated headers via `shopify_header` [2](#0-1) . `Registry.process` validates the HMAC over that raw body only, then trusts `request.shop`/`request.topic` to dispatch the handler [3](#0-2) .

### Title
Webhook shop-domain and topic headers are not covered by the HMAC, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable string as the raw HTTP body alone [1](#0-0) , but `Registry.process` acts on `request.shop` and `request.topic`, which come from HTTP headers that are never included in that signed material [3](#0-2) . This breaks the intended binding `hmac(raw_body) == hmac(raw_body, shop, topic)`: the gem verifies bytes that do not include the shop/topic, yet uses the shop/topic bytes to route data.

### Finding Description
`Utils::HmacValidator.validate` recomputes an HMAC-SHA256 over `verifiable_query.to_signable_string` using `Context.api_secret_key` (shared for the whole app across all installed shops) and compares it to the header-supplied `hmac` [4](#0-3) . For webhooks, `to_signable_string` is exactly `@raw_body` — none of `shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, or `shopify-api-version` are part of the signed payload [5](#0-4) .

Because the app's secret is shared across every shop that installs the app, any body+HMAC pair that is valid for one shop's webhook is also a valid HMAC for that same body when replayed with a different `shop-domain` header — the signature check in `Registry.process` (`Utils::HmacValidator.validate(request)`) has no way to detect the substitution, since it never looks at the shop header at all [3](#0-2) . An attacker who legitimately installs the app on their own shop (or otherwise obtains a valid raw_body/hmac pair, e.g. for topics like `app/uninstalled` or mandatory GDPR topics where body shape is predictable/shop-agnostic) can resend that exact body and signature to the app's webhook endpoint while forging the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header to name a victim shop. `WebhookMetadata` is then built directly from that unverified `request.shop`/`request.topic` and handed to the registered handler [6](#0-5) , so any host application that keys per-tenant behavior (e.g. uninstall/redact processing, data updates) off `data.shop` will act on the wrong tenant despite HMAC validation "passing."

This matches the report's bug class: a field that is acted upon (`shop`) is not covered by the HMAC that is supposed to authenticate the request, i.e. the equality `hmac_verified_bytes == acted_upon_bytes` does not hold.

### Impact Explanation
This allows cross-tenant impersonation: a party who can obtain any one valid webhook body/HMAC pair for the shared app secret can make the host application process arbitrary data under an arbitrary victim shop's identity, without ever possessing that shop's access token or the app's `client_secret`. This falls under the "cross-tenant access" Critical impact category.

### Likelihood Explanation
High for apps that install this gem's webhook handling as documented: `Registry.process` is the only integration point offered, and the shop/topic fields are unconditionally taken from headers regardless of body contents [3](#0-2) . The attacker only needs to be able to trigger at least one legitimate webhook delivery for the app (trivial via installing the app on a shop they control) to obtain a valid raw_body/hmac pair to replay.

### Recommendation
Bind the shop (and ideally topic) into the value that is authenticated, or otherwise verify that `request.shop` matches an expected/known shop for the session/installation being acted upon before dispatching to handlers. At minimum, `to_signable_string` should not be the sole source of truth for authorization decisions — the gem should not expose `request.shop`/`request.topic` as trusted values purely because `HmacValidator.validate(request)` returned true.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, receiving a legitimate webhook delivery for topic `app/uninstalled` with raw body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(client_secret, B)`, and `client_secret` is shared for the app across all shops).
2. Attacker sends a POST to the app's webhook endpoint with the same raw body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com` and (if desired) a different `x-shopify-topic`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers, and `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(client_secret, B)` and finds it equals `H` — validation passes because the shop header was never part of the signed content [1](#0-0) .
4. The handler is invoked with `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim.myshopify.com", ...)` [6](#0-5) , causing the host app to perform uninstall/redact/other tenant-scoped processing against `victim.myshopify.com` even though no data actually originated from that shop.
