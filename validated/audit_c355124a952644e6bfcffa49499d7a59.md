### Title
Legacy WebAPI Trigger Handler Overwrites In-Flight Callback on Duplicate MessageID, Causing Cross-Requester Response Hijack/DoS - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The external report's bug class is "missing reentrancy/duplicate-invocation guard leading to state corruption during an in-flight operation." The closest concrete, unprivileged-reachable analog in this codebase is in the gateway's legacy WebAPI trigger handler: `handler.HandleLegacyUserMessage` stores a pending callback keyed only by the caller-supplied `MessageID`, with no check that an identical, still in-flight `MessageID` already exists — unlike the newer v2 HTTP trigger handler which explicitly guards against this.

### Finding Description
`handler.HandleLegacyUserMessage` in [1](#0-0)  unconditionally does:
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageID] = &savedCallback{id: msg.Body.MessageID, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()
```
There is no existence check before overwriting `h.savedCallbacks[msg.Body.MessageID]`. `MessageID` is fully attacker-controlled — it is a field on the client-supplied `MessageBody` [2](#0-1) , and `Message.Validate()` only checks length/format, not uniqueness or ownership [3](#0-2) . This message flows in from `gateway.ProcessRequest`, an unauthenticated, internet-facing entry point that dispatches to `HandleLegacyUserMessage` for any decoded legacy request [4](#0-3) .

By contrast, the newer v2 `httpTriggerHandler.setupCallback` explicitly rejects a second request using an in-flight `requestID`:
```go
if _, found := h.callbacks[requestID]; found {
    h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, ... "requestID has already been used" ..., callback)
    return nil, fmt.Errorf("in-flight request ID: %s", requestID)
}
``` [5](#0-4)  — confirming that the legacy path's lack of an equivalent guard is a real gap rather than intended design.

Because the legacy path lacks this guard, a second `HandleLegacyUserMessage` call using the same `MessageID` (either from the same attacker re-sending quickly, or coincidentally/maliciously from two different legitimate callers who happen to pick the same ID) silently replaces the first caller's saved callback in the map before the first request's node round-trip completes. When `HandleNodeMessage` → `handleWebAPITriggerMessage` later receives the node's response keyed by that `MessageID`, it looks up and deletes the map entry and sends the response to *whichever* callback is currently stored [6](#0-5) :
```go
h.mu.Lock()
savedCb, found := h.savedCallbacks[msg.Body.MessageID]
delete(h.savedCallbacks, msg.Body.MessageID)
h.mu.Unlock()
if found {
    return savedCb.SendResponse(...)
}
```
The original requester's HTTP connection will hang (until any client-side timeout) and never receive its result, while the second/attacker request's callback receives the response instead — a cross-requester response mix-up triggered purely by an unprivileged client choosing a colliding `MessageID`.

### Impact Explanation
This does not directly enable fund movement or full authentication bypass, but it does allow an unprivileged, unauthenticated caller of the gateway's legacy endpoint to:
- Cause denial of service for another concurrent legacy request sharing the same `MessageID` (that request's HTTP client never gets a response and its callback is dropped from the map without being invoked).
- Potentially intercept a response meant for a different in-flight request if that response is delivered to the callback that currently occupies the slot, resulting in cross-requester response confusion — directly matching one of the explicitly accepted impact categories ("cross-user response confusion").

The severity is bounded because it is scoped to the legacy WebAPI trigger surface (comment at line 384 already flags it as `// TODO: apply allowlist and rate-limiting here`), and typical `MessageID`s are expected to be unique per legitimate client, making accidental collisions unlikely; however, since the field is fully attacker-controlled and unchecked, deliberate collision by a malicious client targeting a known/predictable `MessageID` of another request is feasible.

### Likelihood Explanation
Likelihood is moderate: exploitation requires an attacker to know or guess another in-flight request's `MessageID` (or to race their own duplicate submissions), and requires two requests to be genuinely in-flight (bounded by node response latency, not an arbitrarily long window). It is not gated by any privileged role — any client that can reach the gateway's legacy `web_api_trigger` message path can attempt it, and the endpoint's own code comments confirm the missing allowlist/rate-limiting is a known gap.

### Recommendation
Mirror the v2 `setupCallback` pattern in the legacy handler: before storing a new callback, check whether `msg.Body.MessageID` already exists in `h.savedCallbacks`, and if so, reject the new request with a conflict error rather than silently overwriting the existing entry. Additionally, consider deriving/validating `MessageID` uniqueness per-sender (e.g., scoping the map key by `(Sender, MessageID)`) so that unrelated callers cannot collide with each other's identifiers at all.

### Proof of Concept
1. Attacker (or two concurrent legitimate clients) send two `HandleLegacyUserMessage` requests using the identical `MessageID` value M, differing signatures/senders otherwise valid.
2. First call stores `savedCallbacks[M] = callbackA` and dispatches to DON nodes; second call overwrites `savedCallbacks[M] = callbackB` before the first node response arrives (see [1](#0-0) ).
3. When the node responds with `MessageID = M`, `handleWebAPITriggerMessage` looks up `savedCallbacks[M]`, finds `callbackB`, and sends the (potentially request-A-originated) response to caller B, while caller A's HTTP connection hangs until timeout/prune (`pruneCallbacks`, `defaultCallbackMaxAgeSec` = 120s) [6](#0-5) .

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
	delete(h.savedCallbacks, msg.Body.MessageID)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JSONRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}

		return errors.New("method name ending with null bytes")

		return errors.New("invalid DON ID length")
