Based on my research, I found a custody-relevant analog in Aptos' **multisig_account.move** timelock feature — a mutable security parameter (`override_threshold`) that silently degrades whenever the owner set shrinks, mirroring the external bug's core flaw: a value that gates a safety window can be manipulated *during* that same window to effectively cancel the protection.

### Title
Multisig Timelock `override_threshold` Silently Clamps Down on Owner Removal, Allowing a Coalition to Retroactively Bypass the Timelock Delay - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
The multisig account module supports an optional `MultisigAccountTimeLock` with an `override_threshold`: transactions that gather at least `override_threshold` approvals can skip the timelock waiting period, while transactions with fewer approvals (but ≥ `num_signatures_required`) must wait `timelock_period`. `update_owner_schema` — invoked whenever owners are added/removed or the signature threshold changes — auto-clamps `override_threshold` down to the new owner count whenever owners are removed and that count drops below the configured `override_threshold`. [1](#0-0) 

### Finding Description
`override_threshold` is meant to represent a supermajority of the account's owners that can bypass the timelock. But its only invariant enforced is a *relative* one — `override_threshold > num_signatures_required` — not any invariant tied to the number of approvals a specific pending transaction already has. Whenever an owner-removal transaction executes (via the normal `remove_owners`/`swap_owners` multisig flow, itself just another multisig transaction subject to `num_signatures_required`), `update_owner_schema` recomputes `num_owners` and, if `override_threshold > num_owners`, silently rewrites `override_threshold = num_owners` and emits `TimelockUpdated`. [2](#0-1) 

This creates the same pattern as the Wheel `joinGame` bug: a value that determines whether a privileged/urgent action can proceed (win probability / timelock bypass) can be pushed toward the attacker-favorable extreme by a state-mutating call (`joinGame` deposits / `remove_owners`) made *while* the safety window (60s cooldown / `timelock_period`) is still open, using only the ordinary permissions already available to the caller (any player / a `num_signatures_required`-sized owner coalition).

Concretely: suppose owners = 10, `num_signatures_required` = 3, `override_threshold` = 10 (i.e., only unanimous consent may bypass the delay). A coalition of exactly 3 owners proposes a sensitive transaction (e.g., changing the multisig's auth key, transferring a resource-account/code-object it controls, or an entry function that moves custodied assets) and gets exactly 3 approvals — enough to eventually execute, but only after `timelock_period`. That same 3-owner coalition then creates and executes a **second**, ordinary `remove_owners` transaction (also needing only 3 approvals) that removes the other 7 owners. `update_owner_schema` recomputes `num_owners = 3` and clamps `override_threshold` down to 3. The original pending transaction now already has exactly 3 approvals, which now equals the (freshly lowered) `override_threshold`, so it becomes immediately eligible for bypass execution — collapsing what was supposed to be a mandatory unanimous-consent delay into a 3-of-3 vote with no delay at all.

### Impact Explanation
This corrupts the custody control field intended to protect the multisig-owned resource account/asset custody: `override_threshold` is a security parameter gating unauthorized-in-time execution, and it can be devalued by the very minority that is trying to exploit the timelock, using only ordinary owner-removal privileges. Because a multisig account in Aptos is itself a resource account that may hold APT, fungible assets, or code-object/upgrade authority, an unprivileged minority coalition (holding only `num_signatures_required` seats, not the intended supermajority) can execute high-impact operations (asset transfers, auth-key rotation, upgrade authority changes) before the community/other owners have the reaction time the timelock was designed to guarantee — a direct custody/control bypass of a live asset-holding account.

### Likelihood Explanation
Likelihood is moderate to high in any deployment that combines the multisig timelock feature with an `override_threshold` set below the full owner count and that also allows the minority-approval coalition to independently execute owner-removal transactions with the same or lower approval threshold. The clamp logic executes unconditionally on every `remove_owners`/`swap_owners` call with no dependency on which transaction is pending, so no special preconditions beyond controlling `num_signatures_required` owners are needed.

**Important caveat**: I was not able to fully trace, within the available tool budget, the exact `execute_transaction`/`can_be_executed` logic that consumes `override_threshold` to actually perform the bypass, nor confirm whether owner-removal transactions themselves are subject to the same timelock delay (which, if true, would require the attacker to also wait out a timelock for the owner-removal transaction, weakening — but not eliminating — the attack, since the two pending transactions' delays could still be raced/overlapped). This should be verified against `execute_transaction`, `can_be_executed`, and the exact timelock-check code path in `multisig_account.move` before treating this as fully confirmed.

### Recommendation
- Do not allow `override_threshold` to be silently lowered as a side effect of unrelated owner-management transactions; instead, either (a) recompute eligibility per-transaction based on the owner count captured at transaction-creation time, or (b) require owner-removal transactions that would reduce `override_threshold` to themselves be subject to the full timelock period with no override path.
- Snapshot the effective override threshold (and approval count) at the time a transaction is created, and require re-validation against the *current* full owner set rather than an already-clamped value, closing the "shrink-then-bypass" race.

### Proof of Concept
1. Configure a `MultisigAccountTimeLock` on a 10-owner multisig with `num_signatures_required = 3` and `override_threshold = 10`.
2. A coalition of 3 owners creates transaction A (e.g., an entry function draining a fungible asset store owned by the multisig / resource account) and each of the 3 approves it — reaches `num_signatures_required` but not `override_threshold`; A must wait `timelock_period`.
3. The same 3 owners create and execute transaction B = `remove_owners(other 7 addresses)`, itself needing only their 3 approvals.
4. `update_owner_schema` runs: `num_owners` becomes 3, `override_threshold` (10) > `num_owners` (3), so it clamps `override_threshold` to 3 and emits `TimelockUpdated`. [3](#0-2) 
5. Transaction A's existing 3 approvals now meet the newly-clamped `override_threshold = 3`, allowing immediate execution without waiting for `timelock_period` — bypassing the intended safety delay using only ordinary owner permissions.
