Confirmed: `Clients::HttpClient#initialize` builds `@base_uri = "https://#{api_host || session.shop}"` (line 18) and, when `Context.api_host` is set, sends the `Host` header from `session.shop` while POSTing to `api_host` — but in the default case (`Context.api_host` nil, the normal deployment), the actual TCP/TLS destination is `session.shop` itself. This means whichever code path constructs `Auth::Session.new(shop: <value>)` controls the network destination that receives `client_id`/`client_secret` in the OAuth token-exchange POST body.

### Title
Unvalidated `shop` parameter in `Auth::Oauth.begin_auth` enables OAuth redirect/session-fixation to attacker-controlled domain - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` accepts a caller-supplied `shop:` string and uses it, unsanitized, to build the OAuth authorization redirect URL (`auth_base_uri(shop)`), while sibling flows in the same gem (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`) all call `Utils::ShopValidator.sanitize!(shop)` before using a caller-supplied shop to construct a session/request target.

### Finding Description
`begin_auth` in [1](#0-0)  takes `shop:` directly from the caller and passes it straight into `auth_base_uri(shop)` ( [2](#0-1) ), which returns `"https://#{shop}/admin"` with no validation that `shop` is a trusted `*.myshopify.com`/`myshopify.io`/`spin.dev` domain. The resulting `auth_route` (containing the app's `client_id`, `scope`, and `redirect_uri`) is then handed back to the host application to redirect the user's browser to.

By contrast, every other place in this gem that accepts a raw, non-cryptographically-authenticated `shop` string and turns it into a network destination explicitly binds it through `Utils::ShopValidator.sanitize!` first:
- `ClientCredentials.client_credentials` [3](#0-2) 
- `RefreshToken.refresh_access_token` [4](#0-3) 
- `TokenExchange.migrate_to_expiring_token` [5](#0-4) 

The equality that should hold is: `shop` used to build any outbound request/redirect target == a value proven to be a trusted Shopify domain (either by `ShopValidator.sanitize!` or by cryptographic binding, e.g. HMAC in `validate_auth_callback` or JWT signature in `TokenExchange.exchange_token`). `begin_auth`'s `shop` satisfies neither: it is neither passed through `ShopValidator.sanitize!` nor derived from a signed Shopify payload — it is the raw caller input.

I was only able to confirm the `begin_auth` code path itself and the sibling validated call sites; I could not find any call-site enforcement (e.g., in a Rails engine/controller helper within this gem) that sanitizes `shop` before it reaches `begin_auth`, and the docs snippet examined does not show such validation either (`docs/usage/oauth.md`).

### Impact Explanation
If a host application built on this gem passes a user-supplied `shop` (e.g., from a query string on a login route, a common integration pattern shown in `docs/usage/oauth.md`) straight into `begin_auth`, an unprivileged internet user can supply an arbitrary non-Shopify domain and cause the app to redirect a victim's browser to that attacker-controlled host with the app's real `client_id` and callback `redirect_uri` in the query string. Combined with the session cookie set for the OAuth `state` nonce (`cookie = SessionCookie.new(value: state, expires: Time.now + 60)`), this enables a forced/attacker-initiated OAuth flow against a domain the attacker controls, which can be leveraged to fixate or hijack the subsequent OAuth completion once the victim is redirected back — matching the "session fixation or forced OAuth completion" High-impact category. This does not by itself leak `client_secret` (that value is only sent in `validate_auth_callback`'s POST, which uses `auth_query.shop` that IS bound by HMAC verification), so the impact is bounded to the forced-OAuth/redirect class rather than direct credential theft.

### Likelihood Explanation
Likelihood depends entirely on whether the integrating application passes attacker-controlled input into `begin_auth`'s `shop` parameter without its own validation — this gem provides `Utils::ShopValidator` for exactly this purpose but does not apply it internally in `begin_auth`, unlike its sibling OAuth-adjacent methods. Given that `ShopValidator.sanitize!` is already used defensively at three other call sites in this same gem for the exact same class of input, the omission in `begin_auth` is inconsistent with the gem's own established security pattern for this bug class.

### Recommendation
In `lib/shopify_api/auth/oauth.rb`, validate `shop` in `begin_auth` the same way the other flows do:
```ruby
validated_shop = Utils::ShopValidator.sanitize!(shop)
...
auth_route = auth_base_uri(validated_shop) + "/oauth/authorize?#{query_string}"
```
This enforces the same binding equality (`shop used in redirect == validated trusted Shopify domain`) that the gem already applies in `client_credentials.rb`, `refresh_token.rb`, and `token_exchange.rb`'s `migrate_to_expiring_token`.

### Proof of Concept
1. Host application exposes a login route that calls `ShopifyAPI::Auth::Oauth.begin_auth(shop: params[:shop], redirect_path: "/callback")`, a pattern shown in `docs/usage/oauth.md` step 3.
2. Attacker sends a victim a link to that login route with `shop=attacker-controlled-domain.example`.
3. `begin_auth` builds `auth_route = "https://attacker-controlled-domain.example/admin/oauth/authorize?client_id=<real client_id>&scope=<real scope>&redirect_uri=<real redirect_uri>&state=<nonce>"` ( [6](#0-5) ) and sets the state cookie, then the host app redirects the victim's browser there.
4. The attacker's server now controls what happens next in the flow (e.g., it can immediately bounce the victim to the real `redirect_uri` with an attacker-obtained `code`/`state` pair from a shop the attacker controls), enabling forced OAuth completion against a session the attacker set up, without the app ever detecting that `shop` was not a genuine Shopify domain.
