## Analysis Result

I traced the report's bug class ("field acted on but not bound by the authentication check") to the closest analog in this gem: webhook processing in `lib/shopify_api/webhooks/request.rb` and `lib/shopify_api/webhooks/registry.rb`.

### Title
Webhook `shop` identity is trusted from an HTTP header that is not covered by the HMAC, enabling cross-tenant webhook shop-spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC signature verified by `Utils::HmacValidator.validate` proves nothing about which shop the request claims to be from — it only proves the body bytes were signed with the app's (single, shop-independent) `client_secret`. The `shop` value used downstream by `Registry.process` to build `WebhookMetadata` is read straight from an unauthenticated header, so any two shops of the same app can trade valid `(body, hmac)` pairs and relabel them with an arbitrary shop identity.

### Finding Description
`Request#hmac` and `Request#to_signable_string` bind the signature check exclusively to the raw request body: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Registry.process` validates only the body HMAC and then forwards the header-derived `shop` straight into the metadata passed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` verifies `verifiable_query.hmac` against `verifiable_query.to_signable_string` using `Context.api_secret_key`, which is the same secret for **every** shop installed on the app (it is the app's `client_secret`, not a per-shop secret): [4](#0-3) 

The identity equality the code implicitly assumes is:
```
shop header value == shop that the HMAC-signed body actually originated from
```
But because the HMAC only signs the body (not the `shop-domain`/`hmac-sha256` topic/shop tuple), this equality is never checked. Any attacker who installs the app on their own shop can:
1. Receive a genuine webhook delivery for their own shop (a real `(raw_body, hmac)` pair correctly signed by Shopify with the app's shared secret).
2. Replay that exact `raw_body` and `hmac-sha256` header to the app's webhook endpoint, but substitute the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with a victim shop's domain.
3. `Utils::HmacValidator.validate` still passes because it only checks `raw_body` against the shared `api_secret_key`. `Registry.process` then invokes the app's handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker's own body content>, ...)`.

This is the same class of bug as the reported `Ticket._beforeTokenTransfer()` issue: a value that participates in identity-critical logic (`from`/`to` in the ticket case, `shop` here) is trusted and acted upon without being covered by the mechanism (`SortitionSumTree` bookkeeping vs. HMAC) meant to bind it to the correct entity.

### Impact Explanation
Any handler that uses `WebhookMetadata#shop` to key persisted state, dispatch per-tenant side effects, or make authorization decisions (a common and expected pattern per this gem's own documentation) can be tricked into applying attacker-supplied webhook content under a victim shop's identity — a cross-tenant confusion crossing an unprivileged-merchant-to-victim-merchant boundary, using only the app's own single shared secret which the attacker already legitimately possesses access to indirectly (via their own shop's deliveries).

### Likelihood Explanation
Any merchant who installs the target app (a normal, unprivileged action) can capture real `(body, hmac)` pairs for their own shop's webhooks and replay them with a forged shop header against the app's own webhook endpoint; no access token, `client_secret`, or privileged access is required. The only requirement is calling `ShopifyAPI::Webhooks::Registry.process` as documented — no misuse of the gem's API by the host application is needed.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the value that is HMAC-verified, or otherwise cryptographically bind the header-derived `shop` to the signed payload before it is trusted, e.g. by having `to_signable_string` incorporate the shop header, or by validating the header `shop` against session/registration state before constructing `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook delivery: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the app's shared secret), header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker POSTs to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` unchanged, but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body successfully ( [5](#0-4) ), `Utils::HmacValidator.validate(request)` returns `true` (only `B` is checked), and `Registry.process` invokes the handler with `shop: "victim-shop.myshopify.com"` and attacker-controlled body content.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end
