### Title
PoA batch withdrawals of the same token collapse to one status/txHash, misreporting completion for the other destination - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal` resolves each `WithdrawalIdentifier` by calling `findMatchingWithdrawal` which matches purely on `nep141:<near_token_id> === assetId`, ignoring destination address, amount, and index. When a batch intent contains two withdrawals of the same PoA token (e.g. two `nep141:dash.omft.near` withdrawals to different destination addresses), both independently-polled identifiers query the exact same `getWithdrawalStatus({ withdrawal_hash })` response and both `.find()` calls return the same single matching entry, so both are reported as `completed` with the same `txHash` even though only one on-chain payout matches that hash/destination.

### Finding Description
`describeWithdrawal` in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` computes the result as: [1](#0-0) 

It fetches the withdrawal list keyed only by the intent transaction hash via `getWithdrawalStatusWithRetry`, then calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`: [2](#0-1) 

The function's own doc comment admits the limitation: "multiple withdrawals of the same token in a single transaction are not supported... When support is added, matching could be done by sorting both API results and withdrawal params by amount." Despite this known gap, the SDK offers first-class batch APIs (`sdk.processWithdrawal`, `sdk.waitForWithdrawalCompletion`, `sdk.createWithdrawalCompletionPromises`) that accept arrays of `WithdrawalParams` with no validation rejecting duplicate `assetId` entries.

`createWithdrawalIdentifiers` in `packages/intents-sdk/src/core/withdrawal-watcher.ts` builds one `WithdrawalIdentifier` per withdrawal param, tracking only a per-bridge-route running `index` counter, and does not encode destination address or amount into any matching key used later by `describeWithdrawal`: [3](#0-2) 

Each `WithdrawalIdentifier` is polled independently in `watchWithdrawal`, invoking `bridge.describeWithdrawal({...args.wid, ...})` on every poll cycle: [4](#0-3) 

The broken equality: the SDK implicitly claims `WithdrawalIdentifier[i].result.txHash` corresponds to the on-chain payout that used `WithdrawalIdentifier[i].withdrawalParams.destinationAddress`/`amount`. In reality, for two same-`assetId` identifiers `i` and `j` in the same intent tx, `findMatchingWithdrawal` returns the identical array element for both (whichever the POA API lists first for that `near_token_id`), because it filters only by `nep141:<near_token_id> === assetId` with no disambiguation by destination or amount. So `result[i].txHash === result[j].txHash` even when the two withdrawals paid out to different addresses/amounts on-chain - i.e., the equality "each `WithdrawalIdentifier` resolves to the withdrawal with the same destination address and amount" is violated whenever a batch repeats an assetId.

The analogous helper `findMatchingWithdrawal` in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts` (used by a different `waitForWithdrawalCompletion` path with a `WithdrawalCriteria { assetId }`) has the identical limitation and the identical doc comment: [5](#0-4) 

No existing guard prevents this: there is no `assert` on uniqueness of `assetId` across a batch, no validation function found rejecting duplicate-token batches, and the repo's own test suite explicitly documents matching "by assetId, not by index" as intended behavior for the single-withdrawal-per-token case: [6](#0-5) 

### Impact Explanation
An integrator that batches multiple withdrawals of the same PoA token (e.g., paying out `dash.omft.near` to customer A's address and customer B's address in one intent) will have the SDK report the identical `status: "completed"` and identical `txHash` for both `WithdrawalIdentifier`s, even though only one destination transaction actually matches that hash. This is a status/hash misreport that could cause an integrator to credit two different customers/ledger entries against a single on-chain payout, or credit a customer for a payout that in fact went to a different address - matching the "status or hash misreport making an integrator credit or refund twice" High-severity category. The misreport is repeatable for every batch containing repeated same-token withdrawals, at zero attacker cost, since it requires no adversarial input beyond ordinary batch composition (attacker controls `withdrawalParams` array construction only in the sense that any integrator/counterparty routing user requests can trigger this by combining two users' payouts of the same token in one call).

### Likelihood Explanation
Preconditions: the integrator (or a counterparty-controlled request path that an integrator forwards) must construct a batch (`withdrawalParams: WithdrawalParams[]`) containing two or more entries with the same `assetId` on the PoA route (e.g., `nep141:dash.omft.near`), then call `sdk.processWithdrawal`, `sdk.waitForWithdrawalCompletion`, or `sdk.createWithdrawalCompletionPromises`. No special token/route state is required beyond the token being a PoA-bridged NEP-141 asset. The SDK's public API imposes no restriction against this and the code comments confirm this is a known, unhandled case, making this readily reproducible by any ordinary user/integrator of the SDK without needing to exploit any escape hatch or external component.

### Recommendation
In `findMatchingWithdrawal` (both in `poa-bridge.ts` and `internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`), disambiguate same-`assetId` withdrawals within a batch — e.g., by additionally matching on `address`/`amount`, or by explicitly detecting duplicate `assetId` withdrawals in the batch (at `createWithdrawalIdentifiers` or at `processWithdrawal`/`estimateWithdrawalFee` validation time) and either rejecting such batches with a clear error, or implementing the amount-sorted matching strategy the code comment describes, tracking consumption of matched entries so the same POA withdrawal record cannot be attributed to two different `WithdrawalIdentifier`s.

		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
