### Title
Order/timing-dependent stake-delegation adjustment during partitioned reward distribution allows a direct-transfer "donation" to skew rewards between stakers - (File: runtime/src/bank/partitioned_epoch_rewards/distribution.rs)

### Summary
Solana's partitioned epoch-rewards system splits reward *calculation* and reward *distribution* across multiple blocks/slots. Stake reward calculation snapshots delegation state at one point, but the actual crediting (`build_updated_stake_reward`) reads the *live* stake account lamport balance and delegation at distribution time, several blocks later. Because arbitrary lamports can be transferred directly to a stake account via the System Program at any time (analogous to a "deflationary token donate to vault" style direct transfer), a staker's post-reward delegation/stake amount can be recomputed differently depending on when in the multi-block distribution window the deposit lands, relative to when that particular stake account's partition is processed.

### Finding Description
`build_updated_stake_reward` in `runtime/src/bank/partitioned_epoch_rewards/distribution.rs` reads the stake account's *current* lamports (`account.lamports()`) from the live `StakesCache` at the time its partition is processed, not from a snapshot taken during the calculation phase: [1](#0-0) 

When `adjust_delegations_for_rent` (the `relax_post_exec_min_balance_check` feature) is active, `adjust_delegation_for_rent` uses this live `account.lamports()` to decide the final delegation size: [2](#0-1) 

The existing test `test_delegation_adjustment_at_distribution` explicitly demonstrates that lamports transferred into the stake account *after* calculation but *before* distribution ("But we transfer in more lamports before distribution time") change the outcome of the distribution step: [3](#0-2) 

Since reward distribution across the whole validator set happens over `REWARD_CALCULATION_NUM_BLOCKS`+ multiple partitioned blocks (`num_partitions`), and each partition is only settled when its specific block is processed, two stakers who deposited/staked identically and whose `PartitionedStakeReward` entries were computed identically at the calculation phase can end up with different final `Stake.delegation.stake` / final balances purely based on (a) which partition index they land in (i.e., processing order) and (b) whether a large, unrelated lamport transfer hits their specific stake account in the window between calculation and their partition's distribution slot. This mirrors the reported bug class: state used by a proportional/shared calculation (`total_active_stake`, account lamport balance) is mutable and externally fundable between the "deposit"/calculation snapshot and the "withdraw"/settlement step, so whoever is processed relative to the donation gets an inconsistent, order-dependent outcome. A related instance of the same root cause is called out explicitly in code comments for `calculate_block_reward`, which also warns that recalculation can make `stake > total_active_stake` and clamps only per-individual reward, not against a true remaining-pool invariant: [4](#0-3) 

### Impact Explanation
This does not directly let an attacker steal counterparty funds outright the way an ERC-4626 first-depositor attack does (Solana core stake/reward accounting is not a share-price vault), but it does produce order/timing-dependent divergence in how much stake/lamports a validator's staker ends up with after an epoch's rewards are distributed, purely as a function of transaction/slot timing of unrelated lamport transfers versus partition-block ordering. This is a state-consistency/fairness bug in the bank's commit path (`distribution.rs` runs during block production/reward distribution, which is part of core, unprivileged-reachable bank commit logic), not merely a theoretical concern, since `test_delegation_adjustment_at_distribution` was written specifically to cover this scenario.

### Likelihood Explanation
Triggering it does not require validator/operator privilege — any account holder can transfer lamports to any stake account via a normal System Program transfer, which is an ordinary unprivileged transaction. The distribution window naturally spans multiple blocks whenever `num_partitions > 1` (large validator sets), giving an attacker/normal user ample opportunity, within the same epoch boundary, to time a transfer to land between the calculation snapshot and a specific stake account's distribution slot.

### Recommendation
Snapshot the relevant stake-account lamport balance (or otherwise make the rent/delegation adjustment deterministic and independent of live account mutations) at calculation time rather than re-reading live `StakesCache` balances during the later distribution phase, so a given epoch's reward outcome for every stake account is fixed once calculated and cannot be perturbed by external transfers landing in the multi-block gap between calculation and per-partition distribution.

### Proof of Concept
The codebase's own test demonstrates the underlying mechanism: [5](#0-4) 
It shows: (1) a `PartitionedStakeReward` is calculated for a stake account with `reward_lamports = 1`; (2) before the distribution call, `1_000_000_000` lamports are transferred directly into the stake account (`stake_account.checked_add_lamports(1_000_000_000)`); (3) `distribute_epoch_rewards_in_partition` is then invoked, and the final on-chain delegation/state depends on the account's balance *at distribution time*, not at calculation time — confirming that a direct, unrelated lamport transfer landing in this window changes the reward-distribution outcome for that specific stake account relative to others processed earlier/without such a transfer.

I was unable to fully verify (due to running out of tool iterations) the exact body of `adjust_delegation_for_rent` / `delegation_may_need_adjustment` in `runtime/src/inflation_rewards/mod.rs`, so I cannot state with certainty the precise numeric magnitude of stake/lamport divergence this produces in a live multi-partition scenario, or whether downstream invariant checks (e.g., capitalization assertions) would catch or bound the discrepancy. A Devin session with full repository access would be needed to trace `adjust_delegation_for_rent` in detail and construct a concrete numeric PoC across multiple partitions.

    fn test_delegation_adjustment_at_distribution() {
        let (mut genesis_config, _mint_keypair) =
            create_genesis_config(1_000_000 * LAMPORTS_PER_SOL);
        genesis_config.epoch_schedule = EpochSchedule::custom(432000, 432000, false);
        let bank = Bank::new_for_tests(&genesis_config);

        // Set up epoch_rewards sysvar with rewards with 10e9 lamports to distribute.
        let total_rewards = 10 * LAMPORTS_PER_SOL;
        let block_rewards = 0;
        let num_partitions = 2; // num_partitions is arbitrary and unimportant for this test
        let total_points = (total_rewards * 42) as u128; // total_points is arbitrary for the purposes of this test
        bank.create_epoch_rewards_sysvar(
            0,
            42,
            num_partitions,
            &PointValue {
                rewards: total_rewards,
                points: total_points,
            },
            block_rewards,
        );
        let pre_epoch_rewards_account = bank.get_account(&sysvar::epoch_rewards::id()).unwrap();
        let expected_balance =
            bank.get_minimum_balance_for_rent_exemption(pre_epoch_rewards_account.data().len());
        // Expected balance is the sysvar rent-exempt balance
        assert_eq!(pre_epoch_rewards_account.lamports(), expected_balance);

        // Use lower lamports per byte for creating, bank has higher amount
        let mut lower_rent = bank.rent_collector.rent.clone();
        lower_rent.lamports_per_byte /= 10;

        // Below new minimum, small reward, should normally be destaked
        let reward_lamports = 1;
        let reward = PartitionedStakeReward::new_with_lamport_amounts(reward_lamports, 0, 1);
        let rewards_to_distribute = reward.inflation.stake_reward;
        let stake_pubkey = reward.stake_pubkey;
        let stake_rewards = [reward];
        populate_starting_stake_accounts_from_stake_rewards(&bank, &lower_rent, &stake_rewards);
        let mut stake_account = bank.get_account(&stake_pubkey).unwrap();

        let expected_num = 1;

        let partitioned_rewards = StartBlockHeightAndPartitionedRewards {
            distribution_starting_block_height: bank.block_height() + REWARD_CALCULATION_NUM_BLOCKS,
            all_stake_rewards: Arc::new(stake_rewards.into_iter().collect()),
            partition_indices: vec![(0..expected_num).collect::<Vec<_>>()],
        };

        // But we transfer in more lamports before distribution time
        stake_account.checked_add_lamports(1_000_000_000).unwrap();
        bank.store_account(&stake_pubkey, &stake_account);

        // Distribute rewards
        let pre_cap = bank.capitalization();
        bank.distribute_epoch_rewards_in_partition(&partitioned_rewards, 0);
        let post_cap = bank.capitalization();
        let post_epoch_rewards_account = bank.get_account(&sysvar::epoch_rewards::id()).unwrap();

        assert_eq!(post_epoch_rewards_account.lamports(), expected_balance);

        let epoch_rewards: sysvar::epoch_rewards::EpochRewards =
            from_account(&post_epoch_rewards_account).unwrap();
        assert_eq!(epoch_rewards.total_rewards, total_rewards);
        assert_eq!(epoch_rewards.distributed_rewards, rewards_to_distribute,);

        // Assert that the bank total capital changed by the amount of rewards
        // distributed
        assert_eq!(pre_cap + rewards_to_distribute, post_cap);

        // Check that delegation just gets rewards
        let post_account = bank.get_account(&stake_pubkey).unwrap();
        let post_stake_state: StakeStateV2 = post_account.state().unwrap();
        let pre_stake_state: StakeStateV2 = stake_account.state().unwrap();
        assert_eq!(
            post_stake_state.delegation().unwrap().stake,
            pre_stake_state.delegation().unwrap().stake + reward_lamports
        );
