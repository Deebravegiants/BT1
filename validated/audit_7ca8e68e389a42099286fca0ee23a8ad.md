### Title
Webhook Shop-Domain Header Is Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` field directly from the unauthenticated `X-Shopify-Shop-Domain` header, but `Utils::HmacValidator` only verifies the HMAC over the raw request body. The tenant-identifying header is never part of the signed bytes, so it can be forged independently of a valid HMAC.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` with `to_signable_string` returning only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not included in that signable string: [2](#0-1) 

`Registry.process` validates the request using `Utils::HmacValidator.validate(request)`, which computes `HMAC(secret, request.to_signable_string)` and compares it to the `hmac` field — i.e., it only proves the body bytes are untampered, not that the shop header is authentic: [3](#0-2) [4](#0-3) 

After the HMAC check passes, `request.shop` is passed unmodified into `WebhookMetadata` and handed to the app's handler as the authoritative tenant identifier: [5](#0-4) [6](#0-5) 

The binding that should hold is: `shop-domain-header == shop bound inside the HMAC-signed payload`. In this implementation that equality is never checked — the HMAC only proves `raw_body` integrity, `shop` is a completely independent, attacker-controllable channel (any HTTP header). Any party capable of triggering a genuine webhook delivery to the app for a shop they control (e.g., a merchant who installs the app on their own store, or anyone able to capture one legitimate webhook body+HMAC pair — which is not secret) can replay that exact `raw_body`/`hmac` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for any other shop's domain (a competitor's store, a victim tenant, etc.). The signature remains valid because it never covered the shop header, and `Registry.process` will accept it and invoke the handler with `shop: <attacker-chosen-domain>`.

This is documented in `docs/usage/webhooks.md` as the expected trust boundary: apps are told the `data.shop` field is safe to use for tenant lookups after `Registry.process` "will verify the request did indeed come from Shopify": [7](#0-6) 

That guarantee is false for the `shop` field specifically.

### Impact Explanation
This breaks the tenant/shop identity binding that host applications are told they can rely on after HMAC validation. Depending on how the host app's handler uses `data.shop` (e.g., looking up a stored access token/session by shop domain and then performing writes, or persisting webhook payloads keyed by shop), an attacker can cause the app to process attacker-supplied webhook content under another tenant's identity — cross-tenant data confusion. This satisfies the "cross-tenant access" criterion for High/Critical impact, since it lets one tenant inject data that is processed as if it belonged to a different merchant's shop, entirely within the gem's own webhook verification contract (`Request`/`HmacValidator`/`Registry`), independent of how any particular host app is built.

### Likelihood Explanation
Likelihood is significant: the attacker only needs (a) the ability to trigger one legitimate webhook to their own store (trivial — install any app subscribing to the topic and perform the triggering action, e.g. create an order) to obtain a valid `raw_body`+`hmac` pair, and (b) the ability to POST to the app's public webhook endpoint with a modified shop header — no secret material, access token, or privileged access is required. The gem provides no cross-check between the header value and the signed payload, so this is not a theoretical gap but a direct exploitable byte-verified-vs-byte-parsed mismatch matching the reported bug class.

### Recommendation
Bind the shop identity into the verified signature computation, or otherwise cryptographically tie `X-Shopify-Shop-Domain` to the signed request:
- At minimum, document/enforce that `shop` must be cross-checked by the host application against a shop it already has an active session/install record for (defense in depth), but the gem itself should not present `request.shop` as verified by `HmacValidator.validate`.
- Preferably, include the shop domain (and other identifying headers) as part of `to_signable_string`, or verify the header against a separately known-good identifier (e.g., matching topic/api-version validated combination) instead of trusting it standalone.
- Update `docs/usage/webhooks.md` to explicitly state that `data.shop` is not covered by HMAC verification, and require explicit shop allow-listing by the host application before this field is trusted for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and subscribes to a webhook topic (e.g., `orders/create`).
2. Attacker triggers the webhook (e.g., creates an order), capturing the raw POST body and the valid `X-Shopify-Hmac-Sha256` header Shopify sent — both computed from the app's `client_secret`, which the attacker does not need to know.
3. Attacker replays the exact same `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's registered webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses `shop` from the forged header:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
```
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (`@raw_body` only) — this matches, since the body/HMAC pair is untouched — and the request is accepted.
6. `Registry.process` invokes the host app's handler with `WebhookMetadata.new(... shop: request.shop ...)`, i.e., `shop: "victim-shop.myshopify.com"`, even though the payload actually originated from and pertains to `attacker-shop.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
