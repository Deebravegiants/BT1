### Title
Incorrect one-directional decimals-scaling assumption in `hyper-fungible-token`'s balance↔ERC20 conversion causes unbacked mint / value loss across the bridge - (`modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
The Pendle report's root cause is a hard-coded assumption ("1 SY == 1 Yield Token") that only holds in one direction and silently breaks when the real relationship diverges, inflating a computed value. The `hyper-fungible-token` pallet's decimal-conversion helpers, `convert_to_balance` and `convert_to_erc20`, make the analogous one-directional assumption about the relationship between an ERC-20 token's decimals and the local (Substrate) asset's decimals: they only implement the "ERC-20 decimals ≥ local decimals" case. When the real relationship is the opposite (local decimals greater than the paired ERC-20's decimals — a very ordinary configuration, e.g. a 12-decimal native/local asset bridged against a 6-decimal ERC-20 like USDC), the scaling silently collapses to a no-op instead of the required inverse scaling, corrupting amounts by an integer power of ten in the mint/credit path.

### Finding Description
Both conversion helpers use `saturating_sub` to compute the scaling exponent, which can only express one direction of decimal difference: [1](#0-0) 

```rust
pub fn convert_to_balance<B: core::str::FromStr>(
    value: U256,
    erc_decimals: u8,
    local_decimals: u8,
) -> Result<B, B::Err> {
    let dec_str = (value /
        U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
    .to_string();
    dec_str.parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
```

- `convert_to_erc20`'s own doc comment states the assumption explicitly: "Multiplies by `10^(erc_decimals - local_decimals)` to scale up to ERC20 precision" — i.e. it is written under the assumption that `erc_decimals >= local_decimals` always holds.
- When `local_decimals > erc_decimals` (e.g. local asset has 12 decimals, paired ERC-20 has 6), `erc_decimals.saturating_sub(local_decimals)` clamps to `0`, so the exponent becomes `10^0 = 1` — no scaling is applied in either function, even though a real scale factor of `10^(local_decimals - erc_decimals)` is required.
- This mirrors the Pendle bug precisely: an implicit "this relationship always points one way" assumption which is not always true, and the code has no fallback or explicit check for the opposite case.

`convert_to_balance` is used on `on_accept` (incoming mint/transfer path) and `on_timeout` (refund path): [2](#0-1) 

The inverse helper, `convert_to_erc20`, is documented and implemented purely for the "scale up" direction, implying it is used on the outbound path (converting a local balance amount into the ERC-20-denominated amount embedded in the outgoing cross-chain `Message` before dispatch). Its docstring assumption never accounts for `local_decimals > erc_decimals`.

### Impact Explanation
If any configured asset pair has `local_decimals > erc_decimals` (an entirely plausible, non-malicious configuration — Substrate pallets commonly default to higher-precision balances than many ERC-20 tokens use), then:
- On the outbound direction, `convert_to_erc20` fails to scale the amount down, so the ERC-20 amount encoded in the dispatched message is `10^(local_decimals - erc_decimals)` times larger than the real value corresponding to the locked/burned local balance. This is an unbacked-mint bug: the destination chain's `on_accept` handler will credit/mint an ERC-20 amount vastly exceeding what backs it, directly causing bad debt / theft of protocol funds once redeemed.
- On the inbound direction, the same clamped-exponent bug in `convert_to_balance` causes the opposite failure: incoming ERC-20 value is credited at a fraction of its true value, permanently under-crediting depositors (fund loss for the user, though not insolvency for the protocol).

Both outcomes satisfy the "concrete theft/unbacked mint or permanent fund loss" bar, reachable by any ordinary user simply bridging a token pair with this decimal relationship — no privileged action is required to trigger it, only a decimals configuration in the normal range of possibilities.

### Likelihood Explanation
The trigger condition (`local_decimals > erc_decimals`) is common in practice — many ERC-20s use 6 or 8 decimals while Substrate balances frequently use 10–12 decimals. This is not an adversarial admin/governance action; it is a foreseeable configuration outcome that the code fails to handle correctly. However, I was not able to fully trace the exact extrinsic/call site in `lib.rs` that invokes `convert_to_erc20` before dispatch within the available context, so the precise end-to-end call path from an unprivileged user's bridge-out action to the vulnerable conversion could not be fully confirmed with citations — this is noted as an open verification item for a deeper code walk of `modules/pallets/hyper-fungible-token/src/lib.rs`.

### Recommendation
Replace the `saturating_sub`-based one-directional exponent computation in both `convert_to_balance` and `convert_to_erc20` with logic that handles both directions explicitly (multiply when the target has more decimals, divide when it has fewer), and add unit tests covering `local_decimals > erc_decimals` for both helpers, mirroring the fix pattern already applied elsewhere in this codebase (e.g. `VWAPOracle::_normalizeAmount`, which correctly branches on `<`, `==`, and `>` cases) rather than assuming a single fixed ordering of decimals.

### Proof of Concept
Not independently reproduced in this analysis (no test harness was run); the vulnerability is demonstrated analytically from the source: for `erc_decimals = 6`, `local_decimals = 12`, `convert_to_erc20(value=1, erc_decimals=6, local_decimals=12)` returns `1` instead of the correct `1` (already equal since asset amounts are typically ≥1 unit)... concretely, for a locked local balance of `1_000_000_000_000` (1 whole token at 12 decimals), the correct ERC-20 amount at 6 decimals should be `1_000_000` (scaled down by `10^6`), but `convert_to_erc20` returns `1_000_000_000_000` unchanged — a `10^6`-fold over-mint on the destination chain relative to what was actually locked.
