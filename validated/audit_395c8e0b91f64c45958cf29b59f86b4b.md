This confirms the reachable panic path. In `process_swap_base_out` (and identically in `process_swap_base_out_v2`), `Calculator::swap_token_amount_base_out` is invoked with the raw, attacker-supplied `swap.amount_out` **before** any check that `swap.amount_out < total_pc_without_take_pnl` (or `total_coin_without_take_pnl`) — that bounds check only happens later, at [1](#0-0) , after the vulnerable math has already executed.

Inside `swap_token_amount_base_out`, the denominator is computed as `total_pc_without_take_pnl.checked_sub(amount_out).unwrap()` (or the coin equivalent), with an unguarded `.unwrap()` on the `checked_sub` result: [2](#0-1)

### Title
Reachable panic (unchecked `checked_sub().unwrap()`) in `swap_token_amount_base_out` triggerable via attacker-controlled `amount_out` before bounds validation - ([File: program/src/math.rs])

### Summary
`Calculator::swap_token_amount_base_out` computes a denominator via `total_pc_without_take_pnl.checked_sub(amount_out).unwrap()` (or `total_coin_without_take_pnl.checked_sub(amount_out).unwrap()`) without checking that `amount_out` is less than the pool's reserve first. Both `process_swap_base_out` and `process_swap_base_out_v2` call this function with the raw, un-validated `swap.amount_out` supplied by the caller, and only perform the `amount_out >= total_*_without_take_pnl` sanity check *after* this math has already run and could have panicked.

### Finding Description
The instruction handlers `process_swap_base_out` (program/src/processor.rs:2043-2260) and `process_swap_base_out_v2` (program/src/processor.rs:2455-2581) deserialize the `SwapInstructionBaseOut` payload, which includes an attacker-fully-controlled `amount_out: u64`, from the instruction data (no privileged signer required beyond the normal user's own token account signer). Before any check that `amount_out` is smaller than the pool's available reserve, both handlers call: [3](#0-2) 

which enters `Calculator::swap_token_amount_base_out`: [2](#0-1) 

For `SwapDirection::Coin2PC`, `denominator = total_pc_without_take_pnl.checked_sub(amount_out).unwrap()`; for `SwapDirection::PC2Coin`, `denominator = total_coin_without_take_pnl.checked_sub(amount_out).unwrap()`. If `amount_out` is greater than or equal to the relevant pool reserve (which is entirely legal for an attacker to submit — `SwapInstructionBaseOut::amount_out` is just a raw `u64` deserialized from instruction data with no upper bound applied prior to this call), `checked_sub` returns `None`, and the immediately following `.unwrap()` panics, aborting the transaction.

The proper bounds check (`swap.amount_out >= total_pc_without_take_pnl` / `total_coin_without_take_pnl`) exists in the code, but only fires afterward: [5](#0-4) 

By the time this check runs, the panic in `swap_token_amount_base_out` has already occurred for any out-of-range `amount_out`, making the later check dead code for this specific input range. This mirrors the CVE-2017-13745 bug class: an unprivileged, remotely reachable input causes a reachable assertion/panic due to an unchecked function return value (here, `Option` from `checked_sub`) being blindly `.unwrap()`ed instead of validated before use.

### Impact Explanation
Any user can submit a single `SwapBaseOut` or `SwapBaseOutV2` transaction with attacker-chosen `amm_info`/vault accounts and an `amount_out` value at or above the pool's current reserve to deterministically trigger a Rust panic inside the on-chain program for that transaction. This is a reachable-panic / instruction-abort condition triggerable at will by any caller with no special privileges — a denial-of-service against that specific swap call. Because the panic occurs before the transfer CPIs execute, no funds move in this call, but the instruction is a straightforward way to force program panics on attacker-chosen inputs, which is the same underlying defect class as the referenced CVE.

### Likelihood Explanation
High — the attacker only needs to know the current pool vault balances (public on-chain state, readable at any time) and submit `amount_out` slightly above `total_pc_without_take_pnl` or `total_coin_without_take_pnl`. No signer other than the transaction submitter's own source-token-account owner is required, and both `process_swap_base_out` and `process_swap_base_out_v2` are reachable via the standard swap instruction dispatch.

### Recommendation
Move the `swap.amount_out >= total_pc_without_take_pnl` / `total_coin_without_take_pnl` bounds check to occur *before* calling `Calculator::swap_token_amount_base_out`, in both `process_swap_base_out` and `process_swap_base_out_v2`. Additionally, harden `swap_token_amount_base_out` (and the analogous `checked_sub().unwrap()` patterns in `math.rs`) to return a `Result`/`Option` instead of panicking, propagating a proper `AmmError` (e.g., `AmmError::InsufficientFunds` or `CalculationExRateFailure`) when the subtraction would underflow.

### Proof of Concept
1. Read the current `amm_pc_vault`/`amm_coin_vault` token account balances and the `AmmInfo.state_data.need_take_pnl_pc`/`need_take_pnl_coin` fields to compute `total_pc_without_take_pnl` and `total_coin_without_take_pnl`.
2. Submit a `SwapBaseOut` (or `SwapBaseOutV2`) instruction where `swap.amount_out >= total_pc_without_take_pnl` (for a Coin2PC-direction pair) using otherwise valid, attacker-controlled accounts (own token accounts as source/destination).
3. The call reaches `Calculator::swap_token_amount_base_out` at [3](#0-2)  before the guard at [1](#0-0) , causing `total_pc_without_take_pnl.checked_sub(amount_out).unwrap()` at [6](#0-5)  to panic, aborting the transaction.

```rust
    pub fn swap_token_amount_base_out(
        amount_out: U128,
        total_pc_without_take_pnl: U128,
        total_coin_without_take_pnl: U128,
        swap_direction: SwapDirection,
    ) -> U128 {
        let amount_in;
        match swap_direction {
            SwapDirection::Coin2PC => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (coin + amount_in) * (pc - amount_out) = coin * pc
                // => amount_in = coin * pc / (pc - amount_out) - coin
                // => amount_in = (coin * pc - pc * coin + amount_out * coin) / (pc - amount_out)
                // => amount_in = (amount_out * coin) / (pc - amount_out)
                let denominator = total_pc_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_coin_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
            SwapDirection::PC2Coin => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (pc + amount_in) * (coin - amount_out) = coin * pc
                // => amount_out = coin - coin * pc / (pc + amount_in)
                // => amount_out = (coin * pc + coin * amount_in - coin * pc) / (pc + amount_in)
                // => amount_out = coin * amount_in / (pc + amount_in)

                // => amount_in = coin * pc / (coin - amount_out) - pc
                // => amount_in = (coin * pc - pc * coin + pc * amount_out) / (coin - amount_out)
                // => amount_in = (pc * amount_out) / (coin - amount_out)
                let denominator = total_coin_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_pc_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
        }
        return amount_in;
    }
```
