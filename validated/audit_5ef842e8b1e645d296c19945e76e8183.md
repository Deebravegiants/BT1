### Title
Webhook shop identity spoofing via HMAC not covering `shop-domain` header, enabling cross-tenant webhook impersonation - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking the HMAC signature over the raw request body [3](#0-2) . The `Request#to_signable_string` method used for that HMAC computation returns only `@raw_body` [4](#0-3) . The `shop` value that is subsequently handed to the app's handler as the tenant identifier is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is never included in the signed content [5](#0-4) . This breaks the intended binding `authenticated_bytes == identity_used_for_authorization`: the HMAC authenticates the body, but the body-independent `shop` header is what the app trusts to know "which shop" the webhook is for.

### Finding Description
`HmacValidator.validate` computes `HMAC(api_secret_key, verifiable_query.to_signable_string)` and compares it to the `hmac` field of the query object [6](#0-5) . For webhook requests, `to_signable_string` is defined as just the raw JSON body [4](#0-3) , and `hmac` is read from the `hmac-sha256` header [7](#0-6) .

`Registry.process` only calls this HMAC check, then immediately forwards `request.shop` — pulled straight from the unauthenticated `shop-domain` header — into `WebhookMetadata`, which is passed to the app's handler as the shop the event belongs to [3](#0-2) .

Because the signature never covers the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers, any two requests with the same body will produce the same valid HMAC regardless of which shop's headers are attached. An unprivileged attacker who legitimately receives one genuine webhook delivery for their own shop (e.g., by installing the app on their own store, or by capturing any publicly observable webhook body/HMAC pair for a given topic and payload shape) can replay that exact body and HMAC to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value naming a *different* merchant's shop. `Registry.process` will validate successfully (the body/HMAC pair is legitimate) and will invoke the handler with `WebhookMetadata.shop` set to the attacker-chosen shop domain [8](#0-7) .

This exactly matches the documented gem contract: `docs/usage/webhooks.md` tells implementers that `Registry.process` "will verify the request did indeed come from Shopify" and that `data.shop` is "The shop domain of the webhook" [1](#0-0) [2](#0-1) . An app author following this documentation and using `data.shop` to select which shop's session/access token to act on (a normal, encouraged pattern, e.g. `perform_later(shop_domain: data.shop, ...)` shown in the docs) will act on the wrong tenant's data because the gem's own webhook verification never authenticates that field.

### Impact Explanation
This is a cross-tenant access vector: an attacker can make the host application execute shop-scoped side effects (queue jobs, cache invalidation, order/customer processing, data writes) attributed to a victim merchant's shop using only a body/HMAC pair the attacker legitimately has for their own installation, without needing the app's `client_secret` or any victim credentials. Given the gem's documented API explicitly delegates `shop` identity to `data.shop` post-`process`, this crosses the tenant boundary this gem is responsible for establishing.

### Likelihood Explanation
Requires the attacker to install the target app on a shop they control (widely available for public apps) to obtain at least one valid body+HMAC pair, and requires the app to use `data.shop` from the webhook handler to select tenant context (the documented, expected usage pattern). No secrets or privileged access are needed beyond that.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) headers in the signed/verified content for webhook requests, or independently verify that the `shop-domain` header matches an out-of-band-trusted value (e.g., cross-check against the shop tied to the webhook subscription/registration) before handing it to the handler. At minimum, document prominently that `data.shop` is not cryptographically authenticated and must not be trusted for authorization decisions.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header value `H` that Shopify sent to the app's webhook endpoint.
2. Attacker sends a new POST to the same webhook endpoint with body `B` unchanged, header `X-Shopify-Hmac-Sha256: H` unchanged, but `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and `X-Shopify-Topic`/`X-Shopify-Webhook-Id` set arbitrarily.
3. `ShopifyAPI::Webhooks::Request.new` parses these headers [9](#0-8) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` successfully [10](#0-9) .
4. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` [8](#0-7) , causing the app to act as if this event belongs to `victim-shop.myshopify.com`.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
