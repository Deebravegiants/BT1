### Title
Unchecked UTF-8 Conversion of Untrusted Cross-Chain Message Body Causes Undefined Behavior - (File: modules/pallets/demo/src/lib.rs)

### Summary
`pallet-demo`'s `IsmpModule::on_accept` handler calls `String::from_utf8_unchecked` on the raw `body` of an incoming ISMP `PostRequest` whenever the request's `source` is `StateMachine::Evm(_)`, without validating that the bytes are well-formed UTF-8. This mirrors the `xcb` advisory's soundness violation, where `from_utf8_unchecked()` was invoked on unvalidated bytes originating from an untrusted remote peer (an X server there; a remote EVM-side message sender here).

### Finding Description
The relevant code is:
```rust
StateMachine::Evm(_) => Pallet::<T>::deposit_event(Event::Request {
    source: source_chain,
    data: unsafe { String::from_utf8_unchecked(request.body) },
}),
``` [1](#0-0) 

`request.body` is attacker-controlled: it is the payload of a `PostRequest` dispatched from an arbitrary EVM-side `StateMachine`, delivered through Hyperbridge's message pipeline (relayed proof → `HandlerV2`/`EvmHost` delivery → ISMP router → this module's `on_accept` callback). Nothing upstream of `on_accept` validates that the request body is valid UTF-8 — proof/consensus verification only guarantees the message was included/committed on the source chain, not that its contents are well-formed text.

`std::str::from_utf8_unchecked` (used internally by `String::from_utf8_unchecked`) is documented as unsafe precisely because it skips UTF-8 validation; if the caller cannot guarantee validity, the produced `String` violates Rust's invariant that `str`/`String` are UTF-8-encoded. Any bytes are accepted as a valid body since a `PostRequest` body is an arbitrary byte vector — an attacker can trivially post a request with a body containing invalid UTF-8 sequences (e.g., a lone continuation byte, an overlong encoding, or a byte ≥ 0x80 that doesn't form a valid multi-byte sequence).

This is the direct analog of the xcb advisory: `xcb::xproto::GetAtomNameReply::name()` called `from_utf8_unchecked()` on unvalidated bytes from an X server; here, the pallet calls the equivalent unchecked conversion on unvalidated bytes from a remote chain's dispatched message, reachable by any account able to trigger a cross-chain `PostRequest` to this module (i.e., a relayer delivering a message from any EVM source, or in some deployments an unprivileged actor triggering a message send on the EVM side that gets relayed).

### Impact Explanation
Producing a `String` that is not valid UTF-8 is undefined behavior in Rust: any subsequent safe code that treats the value as valid UTF-8 (string slicing at non-char boundaries, iteration over `.chars()`, comparisons, further FFI, on-chain storage, or in this case emitting/decoding this string as event data downstream by indexers/tesseract relayer tooling) invokes UB. Concretely this can produce corrupted state (Substrate node process/consensus divergence), a node panic/crash (denial of service against the collator/validator producing the block, or indexers/tooling parsing chain events), or, since the value is emitted as an `Event`, potential for miscompilation/optimizer-exploiting behavior in any downstream code path that relies on the string being valid UTF-8. Because the event is emitted from consensus-critical runtime execution, a malformed value could cause divergent behavior across nodes if any client-side logic branches differently on the (formally invalid) string content, which in the worst case threatens chain liveness/consensus, and at minimum crashes off-chain indexers/relayer software consuming the event feed — a route/tooling denial that can block message delivery.

### Likelihood Explanation
High. Reaching this code path requires only dispatching a single `PostRequest` from an EVM-side `StateMachine` targeting the demo pallet's module id (`PALLET_ID = b"ismp-ast"`) with an arbitrary, attacker-chosen body, then having it relayed with a valid proof — the standard, permissionless Hyperbridge relaying flow. `pallet-demo` is wired into the production runtimes (`parachain/runtimes/gargantua` and `parachain/runtimes/nexus` reference it) via the ISMP router, so it is reachable in deployed chain configurations, not merely in isolated tests.

### Recommendation
Replace the unsafe unchecked conversion with a checked one that returns/handles an error instead of assuming validity, e.g.:
```rust
data: String::from_utf8(request.body)
    .map_err(|_| IsmpError::Custom("invalid utf8 in request body".to_string()))?,
```
or use `String::from_utf8_lossy` if invalid bytes should be tolerated with replacement characters rather than rejecting the message. This is the same fix pattern used elsewhere in the codebase (e.g., `modules/consensus/pharos/verifier/src/state_proof.rs` already validates untrusted bytes via `String::from_utf8(...).map_err(...)` rather than the unchecked variant). ### Proof of Concept
1. From an EVM-side source `StateMachine`, dispatch an ISMP `PostRequest` whose `body` contains an invalid UTF-8 byte sequence, e.g. `body = vec![0xC0, 0x80]` (an overlong/invalid two-byte sequence) or `body = vec![0xFF]` (never valid in UTF-8), targeting the demo pallet's destination module (`ModuleId::Pallet(PalletId(*b"ismp-ast"))`).
2. Relay the request with a valid inclusion/consensus proof through the normal Hyperbridge relaying flow so it reaches `pallet_ismp`'s dispatch, which routes it to `IsmpModuleCallback::on_accept`.
3. Execution reaches:
```rust
StateMachine::Evm(_) => Pallet::<T>::deposit_event(Event::Request {
    source: source_chain,
    data: unsafe { String::from_utf8_unchecked(request.body) },
}),
``` [1](#0-0) 
producing a `String` backed by invalid UTF-8 bytes, which is emitted as chain event data — undefined behavior per Rust's `str`/`String` invariants, and a crash vector for any consumer (indexer, RPC client, or further runtime logic) that assumes the emitted string is valid UTF-8.
