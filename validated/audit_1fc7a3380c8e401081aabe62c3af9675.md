## Analysis

The report's bug class — "a field is trusted/acted upon but not actually covered by the integrity check" — maps directly onto how `ShopifyAPI::Webhooks::Request` and `ShopifyAPI::Utils::HmacValidator` process incoming webhooks.

`Request#to_signable_string` returns **only the raw JSON body** — the HMAC signature covers just that body, nothing else: [1](#0-0) 

But the `shop`, `topic`, `webhook_id`, and `api_version` values that the registry acts on are all pulled straight from **unauthenticated HTTP headers**, never included in the signed bytes: [2](#0-1) 

`HmacValidator.validate` confirms this — it only recomputes and compares the signature over `verifiable_query.to_signable_string` (the body): [3](#0-2) 

`Registry.process` validates the HMAC, then hands `request.shop` and `request.topic` (unauthenticated header values) directly to the app's registered handler as the identity of the event: [4](#0-3) 

### Title
Webhook `shop`/`topic`/`webhook_id`/`api_version` headers are not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`HmacValidator.validate` only authenticates the raw webhook body. The `shop-domain`, `topic`, `webhook-id`, and `api-version` fields — which `Registry.process` uses to attribute the event and dispatch to the correct handler — come from plain HTTP headers that are entirely outside the signed bytes. Anyone able to obtain one genuine `(body, hmac)` pair signed by the app's secret can replay it to the app's public webhook endpoint with arbitrary header values, and the signature check will still pass.

### Finding Description
The identity binding that should hold is:
`bytes verified by HMAC == bytes the registry treats as authoritative`

In this gem it does not: `to_signable_string` returns `@raw_body` alone [5](#0-4)  , while `shop`, `topic`, `webhook_id`, and `api_version` are read from headers [2](#0-1)  that are never fed into the HMAC computation. `HmacValidator.validate_signature` computes the digest strictly over `verifiable_query.to_signable_string` [6](#0-5) , so the header values can be modified freely without invalidating the signature.

Any unprivileged internet user can obtain a legitimate `(body, hmac)` pair simply by installing the public app on their own shop and observing a real webhook delivered to their own endpoint — no access to `api_secret_key` is required. That valid body+hmac pair can then be resent to the target app's webhook endpoint with the `x-shopify-shop-domain` header (and/or `x-shopify-topic`) changed to reference a **different, victim** shop. `Registry.process` still accepts it, since `Utils::HmacValidator.validate(request)` only checks the body [7](#0-6) , and then dispatches to the handler with the attacker-chosen `shop`/`topic` metadata [8](#0-7) .

### Impact Explanation
This breaks the tenant boundary the app relies on: the handler is invoked believing the event genuinely originates from the shop named in `data.shop`, when that value was attacker-controlled and never cryptographically bound to the signed body. Depending on how the host app's webhook handlers use `shop` (e.g., updating that shop's local record, processing `app/uninstalled` or GDPR-type payloads, invalidating sessions, etc.), this enables cross-tenant data corruption/access attributed to a shop the attacker does not control — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Requires only: (1) installing the same public app on an attacker-controlled shop to receive one genuine webhook (no privileged credentials needed), and (2) replaying that request to the app's public webhook endpoint with a modified header. No knowledge of `api_secret_key` or any access token is needed, since the signature check never covers the headers being forged.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable string, or otherwise cryptographically bind them to the verified body (e.g., verify shop domain against session/store state maintained by the host app, or extend the HMAC input to cover the full header set) so that no field the registry acts upon can be altered without invalidating the signature.

### Proof of Concept
1. Install the target app on shop `attacker.myshopify.com` (any unprivileged party can do this for a public app).
2. Capture one genuine webhook delivery to the app's endpoint: headers include `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and some `raw_body`.
3. Resend the exact same `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but replace `x-shopify-shop-domain` with `victim.myshopify.com` (and/or change `x-shopify-topic`).
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` still returns `true` because only the body is checked; `Registry.process` in `lib/shopify_api/webhooks/registry.rb` dispatches the handler with `shop: "victim.myshopify.com"`, as confirmed by the request accessors in `lib/shopify_api/webhooks/request.rb`.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
