### Title
Webhook `shop-domain`, `topic`, `webhook-id` headers are not covered by the HMAC signature, enabling cross-tenant webhook data attribution - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `HmacValidator.validate` verifies the HMAC exclusively against that body. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values, which are taken directly from HTTP headers and used to attribute the webhook payload to a specific merchant/tenant, are never included in the signed material.

### Finding Description
`Request#hmac` and `Request#to_signable_string` establish the value that `HmacValidator` checks: [1](#0-0) [2](#0-1) 

`to_signable_string` returns `@raw_body` only, meaning the HMAC computed by `HmacValidator.validate_signature` binds solely to the request body: [3](#0-2) 

Meanwhile, `shop`, `topic`, and `webhook_id` are read straight from unauthenticated headers: [4](#0-3) 

`Registry.process` validates the HMAC and then dispatches to the handler using the header-derived `shop`, `topic`, and `webhook_id`, none of which were part of the signed bytes: [5](#0-4) 

This breaks the binding: `hmac == HMAC(secret, body)` should equal `hmac == HMAC(secret, body + shop + topic + webhook_id)`, but the gem verifies only the former while trusting the latter for tenant attribution. `WebhookMetadata.shop` — the value app code uses to know which merchant the payload belongs to — is filled from the unauthenticated header: [6](#0-5) 

### Impact Explanation
An unprivileged attacker who operates their own shop with the app installed will legitimately receive real webhooks from Shopify with a valid HMAC computed over the body of *their own* shop's event. Because the signature never covers the `shop-domain` header, the attacker can replay that same body/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` (or `x-shopify-shop-domain`) header with a victim merchant's domain. `HmacValidator.validate` will still pass (it only checks the body), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload belongs to the victim shop. Any app logic that trusts `data.shop` to select/update per-tenant data (e.g., writing order/product records keyed by shop) can be corrupted with attacker-controlled data attributed to a different tenant — a cross-tenant data injection.

### Likelihood Explanation
Likelihood is high once an attacker has any shop with the app installed (a standard, unprivileged self-service action for public Shopify apps): they can capture their own valid webhook deliveries (their own server receives them) and freely replay them with modified `shop-domain`/`topic`/`webhook-id` headers against the same public webhook endpoint, since HTTP headers are entirely attacker-controlled on a replayed request and the check never inspects them.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed/verified material, or otherwise cryptographically bind them to the request (e.g., verify the delivery via Shopify's webhook UUID against a per-shop record established at subscription time) rather than trusting header values that fall outside the HMAC's coverage. At minimum, `to_signable_string` should incorporate all header fields that downstream handlers use for tenant attribution.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Attacker triggers/receives a legitimate webhook delivery, e.g. `orders/create`, with a body `B` and a valid `shopify-hmac-sha256` header `H = HMAC(secret, B)` and `shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker resends the exact same body `B` and hmac header `H` to the app's public webhook endpoint, but changes `shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes `HMAC(secret, B)` (body-only) and it matches `H`, so validation passes.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and dispatches to the app's handler, which processes attacker-supplied data as if it originated from the victim tenant.
