### Title
Webhook `shop-domain` header is not covered by HMAC verification, enabling cross-tenant webhook spoofing via signature reuse - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `api_version`, and `webhook_id` are all read from unauthenticated HTTP headers and forwarded untouched into `WebhookMetadata` passed to the app's handler. The identity binding "HMAC signature == the shop this payload is for" does not hold: the HMAC only proves "the body is byte-for-byte what the app's secret signed," it says nothing about which shop header may legitimately accompany that body.

### Finding Description
`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` header using `OpenSSL.secure_compare`: [1](#0-0) 

For webhooks, `to_signable_string` is defined to be only the raw body: [2](#0-1) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers with no relation to the signed bytes: [3](#0-2) 

`Registry.process` validates only the HMAC of the body, then immediately trusts `request.shop` (and `request.topic`) as the tenant identity for dispatch, with no secondary check that the header value corresponds to the shop that actually produced the signed body: [4](#0-3) 

That value flows unchanged into the `WebhookMetadata` struct delivered to the host app's handler: [5](#0-4) 

**Equality that should hold but doesn't:** `hmac_signer_identity(raw_body) == shop_header_claimed_identity`. Because the HMAC only binds the *body bytes* to the app's secret, and the `shop-domain` header is outside that binding, any two payloads with identical bodies (e.g., identical JSON, which is common for many webhook topics with sparse/templated content, or bodies an attacker fully controls by triggering webhooks to their own store) will carry a valid HMAC regardless of which shop-domain header is attached.

### Impact Explanation
An attacker who operates their own Shopify store with the app installed (an unprivileged action available to anyone able to install/dev a Shopify app, no theft of credentials or `api_secret_key` required) can:
1. Trigger a legitimate webhook delivery to their own store, capturing a validly-signed `(raw_body, hmac)` pair from Shopify.
2. Replay that exact `(raw_body, hmac)` to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and, since it's equally uncovered, `x-shopify-topic`) header to claim it originates from a different shop.
3. `HmacValidator.validate` still succeeds because it only ever re-derives the signature from `raw_body`, which is unchanged.
4. The app's handler receives `WebhookMetadata` claiming to be for shop B while it is fully attacker-controlled data, causing the app to write/act on data under a different tenant's identity (session key, DB row, business logic keyed by `shop`) than the one that actually produced it — a cross-tenant identity confusion inside a boundary the gem is supposed to enforce.

This satisfies the High-impact bar in scope ("cross-tenant access") since the attacker crosses a tenant boundary without possessing any secret belonging to the victim shop or the app.

### Likelihood Explanation
Medium. It requires the attacker to control at least one shop where the app is installed (self-serviceable via any Partner/dev store) and to find a webhook topic/body combination that is either attacker-fully-controlled or has content overlap useful across shops (many webhook bodies — e.g., `app/uninstalled`, `shop/redact`, or templated compliance topics — contain little or no shop-specific data, making forged bodies trivial to reuse across "victim" shop claims). The gem does nothing to make this harder; it is a property of the signing scheme as implemented here, not something the host app can compensate for except by independently re-verifying shop identity from a source outside the HMAC (which is not documented as required, and the gem provides no helper to do so).

### Recommendation
Bind the `shop`, `topic`, `api_version`, and `webhook_id` header values into the signable string used for HMAC verification in `lib/shopify_api/webhooks/request.rb` (e.g., include a canonical representation of these headers alongside the body before computing/comparing the signature), or provide/document an explicit secondary check that ties the verified body to the claimed `shop` header before constructing `WebhookMetadata`. At minimum, the library should not present `request.shop` to consumers as if it were part of the same trust boundary the HMAC check just established.

### Proof of Concept
1. As an app-installing "attacker" shop (`attacker.myshopify.com`), trigger a webhook whose body is attacker-fully-controlled or content-independent of shop identity (e.g. a compliance/uninstall topic with an empty or templated body `{}` as used in the test fixtures): [6](#0-5) 
2. Capture the resulting `x-shopify-hmac-sha256` value Shopify computed over that body using the app's real secret.
3. Replay the same raw body and HMAC to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` returns `true` because it only checks `raw_body` against the HMAC: [7](#0-6) 
5. `Registry.process` dispatches to the app's handler with `WebhookMetadata#shop == "victim.myshopify.com"`, even though the payload was never produced by or for that shop.
