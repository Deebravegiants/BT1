### Title
Webhook Shop Identity Not Bound to HMAC — Cross-Tenant Shop Spoofing via `ShopifyAPI::Webhooks::Request#shop` - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, but the `shop` (and `topic`/`webhook_id`) values delivered to the app's handler are read from HTTP headers that are never covered by that HMAC. This breaks the equality binding: `shop passed to handler == shop the HMAC-signed body actually originated from`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes/verifies the signature exclusively against `verifiable_query.to_signable_string`, i.e. only the body bytes: [2](#0-1) 

`Registry.process` gates on that same HMAC check, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id`, all sourced from raw headers, to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

`Request#shop`, `#topic`, and `#webhook_id` are parsed straight from `shopify-shop-domain`/`x-shopify-shop-domain` and sibling headers with no cross-check against the HMAC-covered body: [4](#0-3) 

Because the HMAC only binds the body bytes, any tenant of a multi-tenant app who can trigger a legitimate webhook for their **own** shop (e.g. update a product) can capture the genuine `(raw_body, hmac)` pair Shopify sent to the app's endpoint, and independently replay that exact body+HMAC to the same endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`/`x-shopify-webhook-id`) header with a different, victim shop's domain. `Utils::HmacValidator.validate` still succeeds (body and HMAC are untouched), and `Registry.process` forwards the attacker-chosen `shop` value straight to the app's handler as if it were authenticated.

### Impact Explanation
Any host application that uses `WebhookMetadata#shop` (or `#topic`/`#webhook_id`) to select which tenant's records to create/update/delete — a very common and reasonable use of this API, since the gem explicitly hands `shop` to the handler as the request's shop identity — can be tricked into attributing attacker-supplied webhook data to a shop the attacker does not control. This is a cross-tenant data-integrity break driven purely by the gem's own identity-binding gap (shop not covered by HMAC), not by the host ignoring documented behavior; the docs present `Registry.process`/`WebhookMetadata#shop` as the mechanism for identifying "the request did indeed come from Shopify" and for which shop.

### Likelihood Explanation
Reachable by any unprivileged existing merchant/tenant of the target app (no `api_secret_key`, access token, or privileged role needed) — they only need a store that already has the app installed, which is the normal, low-privilege state for any app user. They trigger one of their own webhooks to obtain a valid `(body, hmac)` pair, then directly POST a forged HTTP request to the app's public webhook endpoint with a different `shop` header value. No credential theft or TLS interception is required, and no host-application misuse is needed beyond using the field the gem hands it.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the value verified by the HMAC check, e.g. by including the `x-shopify-shop-domain`, `x-shopify-topic`, and `x-shopify-webhook-id` header values (or the merchant/shop the app registered the token for) as part of the signable string, or by requiring/validating that `request.shop` matches an expected, already-known shop for the given webhook registration before invoking the handler. At minimum, document explicitly that `WebhookMetadata#shop`/`#topic`/`#webhook_id` are unauthenticated inputs that must not be trusted for tenant-scoping decisions without independent verification (e.g. cross-checking against a known set of subscribed shops).

### Proof of Concept
1. Attacker (owner of `attacker-shop.myshopify.com`, a legitimate installed instance of the target app) performs an action that triggers a webhook (e.g. product update). The app's endpoint receives:
   - `raw_body = B`
   - Header `x-shopify-hmac-sha256 = HMAC(secret, B)` (valid)
   - Header `x-shopify-shop-domain = attacker-shop.myshopify.com`
2. Attacker captures `B` and the HMAC value from their own webhook delivery (visible to them as the account owner, e.g. via a proxy/logging tool they control on their own webhook receiver, or by using ngrok to observe it — no secrets required since they're only observing traffic addressed to their own listener).
3. Attacker independently sends an HTTP POST directly to the app's public webhook route with the *same* `raw_body = B` and *same* `x-shopify-hmac-sha256` header, but with `x-shopify-shop-domain` header changed to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` recomputes `HMAC(secret, B)`, which matches, so validation passes: [5](#0-4) 
5. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` using the attacker-controlled `shop` header value and calls the app's handler, which processes body `B` as if it belongs to `victim-shop.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
