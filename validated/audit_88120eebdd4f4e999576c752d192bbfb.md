The bug-class hint ("Method 1" — using unauthenticated/unbound values to double-dip on an identity-scoped payout) maps in this gem to a structural gap in `ShopifyAPI::Webhooks::Request`: the shop/topic/webhook identity fields used to route and attribute a webhook are not covered by the HMAC that is verified.

### Title
Webhook `shop`, `topic`, and `webhook_id` fields are trusted from unsigned HTTP headers while only the raw body is HMAC-verified, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary

### Finding Description
`ShopifyAPI::Webhooks::Request` implements the `Utils::VerifiableQuery` interface with `to_signable_string` returning only `@raw_body`: [1](#0-0) . The `shop`, `topic`, and `webhook_id` accessors are read straight from HTTP headers, entirely outside the signed content: [2](#0-1) .

`Utils::HmacValidator.validate` only recomputes and compares the HMAC over `verifiable_query.to_signable_string`, i.e. the raw body: [3](#0-2) .

`Webhooks::Registry.process` then uses `request.shop` and `request.topic` — both unauthenticated header values — to decide the handler and identify the tenant, after only confirming the body's HMAC is valid: [4](#0-3) .

The equality this design fails to enforce is: `shop-header == shop bound inside the signed payload`. Contrast this with the OAuth flow's `AuthQuery`, where `shop`, `host`, `code`, `state`, and `timestamp` are all explicitly included in `to_signable_string` and therefore bound to the HMAC: [5](#0-4) . The webhook path omits this binding entirely — the HMAC secret (the app's `client_secret`) is shared across every shop that has installed the app, so a valid `(raw_body, hmac)` pair proves only "signed by Shopify for this app," not "for this specific shop/topic."

### Impact Explanation
Any merchant who has installed the app (an unprivileged actor with respect to other tenants of the same multi-tenant app) can trigger legitimate webhook deliveries for their own store and observe the raw `(body, hmac)` pair on infrastructure they control (e.g., their own webhook receiver/dev tunnel). Because `shop`, `topic`, and `webhook_id` are not part of the signed content, they can resend the identical body+HMAC to the app's shared webhook endpoint while altering the `shop-domain` (and/or `topic`/`webhook-id`) header to impersonate a different, victim shop. `Registry.process` will accept the HMAC as valid and dispatch the payload to the handler tagged with the attacker-chosen `shop`, achieving cross-tenant data injection/spoofing (e.g., forging `app/uninstalled`, `customers/redact`, or `orders/*` events attributed to a shop the attacker does not control). This meets the Critical - cross-tenant access bar.

### Likelihood Explanation
Requires only capabilities every installed merchant already has (their own installation triggers legitimate webhooks with a valid HMAC under the shared app secret) plus the ability to replay an HTTP request with modified headers to the app's public webhook endpoint — no access to `api_secret_key`, access tokens, or TLS interception is needed.

### Recommendation
Bind the identity fields into the signed content, mirroring what `AuthQuery` already does: extend `Webhooks::Request#to_signable_string` (or the validation call site) to include `shop`, `topic`, and `webhook_id` in the value that is HMAC-verified, or otherwise cryptographically bind these header values to the signed body (e.g., verify HMAC over a canonical string combining headers + body) so that changing any of them invalidates the signature.

### Proof of Concept
1. Merchant A installs the app and triggers an action (e.g., updates an order) causing Shopify to deliver a webhook to the app's shared `/webhooks` endpoint with headers `X-Shopify-Shop-Domain: shop-a.myshopify.com`, `X-Shopify-Topic: orders/updated`, `X-Shopify-Hmac-Sha256: <valid hmac over raw_body>`, and some `raw_body`.
2. Merchant A observes this exact request via infrastructure they control (their own tunnel/receiver used during development, or by momentarily pointing the webhook subscription to a host they own).
3. Merchant A resends the identical `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's shared webhook endpoint, but sets `X-Shopify-Shop-Domain: shop-b.myshopify.com` (victim shop) and/or a different `X-Shopify-Topic`.
4. `Utils::HmacValidator.validate(request)` returns `true` because it only checks the raw body's HMAC ( [6](#0-5) ), and `Registry.process` dispatches the handler using the attacker-controlled `request.shop`/`request.topic` ( [4](#0-3) ), causing the app to process shop A's data as if it belonged to shop B.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
