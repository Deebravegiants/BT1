### Title
Webhook `shop` identity is trusted from an unauthenticated header while HMAC only covers the raw body, enabling cross-tenant webhook confusion - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identifier (`shop`) used by webhook handlers from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature computed by `Utils::HmacValidator` only covers the raw request body (`to_signable_string` returns `@raw_body`). The `shop` header is never included in the signed content, so the binding `shop_header == shop_that_produced_this_signed_body` is never enforced.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop` is read straight from the `shop-domain`/`x-shopify-shop-domain` header without any cryptographic binding to the body or HMAC: [2](#0-1) 

`Registry.process` validates the HMAC over the request (i.e., only over the body) and then forwards `request.shop` directly to the app's handler as the trusted tenant identity, alongside the parsed body: [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature exclusively from `verifiable_query.to_signable_string` (the raw body for webhooks) and compares it against the header-supplied HMAC using `Context.api_secret_key`, which is the same secret for *every shop* that installs the app: [4](#0-3) 

The resulting `WebhookMetadata.shop` field, which host applications use to determine which tenant a webhook payload belongs to, is populated from this unauthenticated header: [5](#0-4) 

**Root cause as an equality that is broken:** the gem verifies `HMAC(api_secret_key, raw_body) == received_hmac`, but the caller (and downstream handler) treats `request.shop` as if it satisfied `shop_header == shop_that_generated(raw_body, hmac)`. Since `api_secret_key` is shared across all shops of a given app (it's the app's `client_secret`, not a per-shop secret) and the header is outside the signed payload, any `(raw_body, hmac)` pair that is valid for shop A remains a valid HMAC pair regardless of which `X-Shopify-Shop-Domain` header accompanies it.

An unprivileged actor who can obtain (or generate, e.g. by triggering webhook-eligible events in their own installed shop) one valid `(raw_body, hmac)` pair for the app can replay that exact body/HMAC to the app's public webhook endpoint while substituting an arbitrary victim shop domain in the `X-Shopify-Shop-Domain` header. `Utils::HmacValidator.validate` will still return `true` because it never inspects the shop header, and `Registry.process` will invoke the handler with `WebhookMetadata.new(shop: <attacker-controlled victim domain>, body: <replayed body>, ...)`. This crosses the tenant boundary the gem is expected to enforce.

### Impact Explanation
This satisfies the "Cross-tenant access" criterion: an app built on this gem that keys any tenant-scoped side effect (e.g., updating data, deleting resources, revoking access, storing state) off `WebhookMetadata#shop` can be tricked into applying attacker-supplied webhook data under a different shop's identity, purely because the gem's webhook authentication does not bind the claimed shop to the HMAC-protected bytes.

### Likelihood Explanation
High reachability: webhook endpoints are public HTTP endpoints by design (Shopify posts to them over the internet), so any internet client can POST directly to them. The attacker needs one legitimate `(body, hmac)` pair signed with the app's shared `api_secret_key` — trivially obtainable by installing the app on their own store and triggering any registered webhook topic (e.g. `app/uninstalled`), since Shopify signs with the same app-level secret for every shop.

### Recommendation
Bind the shop identity into the verified signature material, or otherwise cryptographically/logically tie the `X-Shopify-Shop-Domain` header to the specific shop session/installation before trusting it: e.g., only accept the header value if it matches a shop associated with the session used to look up the app's stored access token/state for that webhook, or require the app to independently confirm the shop exists among its installed shops and that the raw body's own shop-identifying fields (if present) agree with the header. At minimum, document loudly that `Request#shop` is unauthenticated and must not be used as the sole tenant key.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and triggers a webhook topic the app has registered for (e.g. by updating a product), causing Shopify to POST a legitimately signed webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for `HMAC(api_secret_key, B)`), and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker captures `B` and `H`.
3. Attacker POSTs directly to the app's public webhook endpoint with the identical body `B` and `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Utils::HmacValidator.validate` recomputes `HMAC(api_secret_key, B)` and compares to `H` — it matches (body unchanged), so validation succeeds: [6](#0-5) 
5. `Registry.process` calls the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to act on the attacker's payload attributed to the victim tenant.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
