### Title
Webhook `shop` identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating an HMAC over the raw request body only, but then trusts the `shop` (and `topic`/`webhook_id`/`api_version`) values taken from unauthenticated HTTP headers to identify which merchant/tenant the payload belongs to. This breaks the intended identity binding `HMAC-authenticated-body == shop-that-owns-the-body`, letting anyone who can obtain one valid `(raw_body, hmac)` pair replay it with a forged `shop-domain` header to make the app process attacker-supplied data under a victim tenant's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from request headers with no cryptographic binding to that body: [2](#0-1) 

`Registry.process` validates the HMAC of the body and, if it matches, immediately trusts `request.shop` (and the other header-derived fields) as the tenant identity to hand to the app's webhook handler: [3](#0-2) 

`HmacValidator.validate` only proves that *some* body was signed with the app's secret — it says nothing about which shop that body was signed for, because the signable string never included `shop`: [4](#0-3) 

This is exactly the reported bug class transposed into this codebase: a field that is *acted on* (`shop`, used as the tenant/session key passed to the handler) is not covered by the value that is *cryptographically verified* (the HMAC, which only covers `raw_body`). The equality that should hold — `shop-bound-by-signature == shop-trusted-by-handler` — does not hold, because the signature never binds `shop` at all.

### Impact Explanation
Any entity capable of installing the app on their own store (an ordinary, unprivileged merchant/internet user) can legitimately trigger a webhook for their own shop and thereby obtain a valid `(raw_body, hmac)` pair signed with the app's shared `client_secret` — without ever learning the secret itself. That same attacker can then send a forged HTTP request directly to the app's webhook endpoint, reusing the observed `raw_body` and `hmac-sha256` header verbatim, but substituting the `shop-domain` (and/or `topic`/`webhook-id`) header with a victim merchant's domain. `Registry.process` will validate successfully (the body's HMAC still matches) and will invoke the registered handler with `WebhookMetadata#shop` set to the victim's domain and attacker-controlled `body`. Any app logic that uses `data.shop` as a tenant key (e.g., to look up or update per-shop records, apply the payload to the "current shop," or route notifications) will apply attacker-controlled data to a different tenant's context — a cross-tenant data-integrity/confusion issue.

### Likelihood Explanation
Exploitation requires only: (1) the ability to install the target app on an attacker-controlled shop (routine, unprivileged, free), (2) triggering an action that fires a webhook the attacker can observe, and (3) sending an HTTP request with edited headers to the app's public webhook endpoint. No knowledge of `api_secret_key`, access tokens, or any privileged credential is required — this is achievable by any ordinary internet user/merchant.

### Recommendation
Bind the tenant identity to the signed payload instead of trusting header values independently of the HMAC:
- Reject or independently corroborate the `shop` header before trusting it (e.g., only accept webhooks for shops with an active, previously-established session/install record, and correlate against the `webhook_id`/subscription that was registered for that specific shop via the GraphQL API), or
- If the current design intentionally relies on TLS + endpoint secrecy for the shop binding (as Shopify's own webhook delivery does, since deliveries originate only from Shopify's IPs to a known callback URL), document this trust boundary explicitly in the library so integrators know `data.shop` is not itself authenticated by the HMAC and must not be used as a sole tenant key without additional verification (e.g., checking it matches a shop with a valid stored session/access token).

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and performs an action that triggers a registered webhook topic (e.g. `orders/create`).
2. Attacker's server captures the real inbound request: `raw_body` and the `X-Shopify-Hmac-Sha256` header value (both valid, since they were legitimately signed by Shopify using the app's `client_secret` for the attacker's own shop).
3. Attacker crafts a new HTTP POST to the app's webhook endpoint using the identical `raw_body` and `hmac-sha256` header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this into `shop == "victim-shop.myshopify.com"`, `hmac` matching the body.
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `raw_body` and succeeds: [5](#0-4) 
6. The registered handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: <attacker's data> ...)`, processing attacker-controlled data as if it belonged to `victim-shop.myshopify.com`.

          received_signature = verifiable_query.hmac
