## Title
Emporium output token/destination (`erc20TokenAddresses`, `stealthAddressStructure`) is never bound to the signed `EmporiumStack`, letting any caller redirect swap proceeds authorized by a victim's wallet signature - (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.verifyWallet` recovers `stack.signerAddress` over `EMPORIUM_SIGNATURE_TYPEHASH`, which only commits to `emporiumMessage`, the ops array hash, `maxFee`, and `deadline`. The `circomData.erc20TokenAddresses` and `circomData.stealthAddressStructure` that `runAction`/`handleOut` actually use to compute and route the post-op balance change into a new shielded UTXO are outside that signed hash and are instead constrained only by the calling transaction's own ZK proof, which the attacker (the `transact` caller) generates themselves.

### Finding Description
The equality that should hold: *the `(erc20TokenAddresses, stealthAddressStructure)` pair that `handleOut` uses to create the output UTXO should be the pair the wallet owner (`stack.signerAddress`) implicitly authorized when signing the `EmporiumOperation[]`.* In reality these are two disjoint values:

- Signed side: `EMPORIUM_SIGNATURE_TYPEHASH` covers only `emporiumMessage`, `_hashEmporiumOps(stack.ops)`, `maxFee`, `deadline`. [1](#0-0) 
- Used side: `runAction` executes `stack.ops` via `IHinkalWallet(stack.signerAddress).callHinkalWallet(...)` (spending the signer's real wallet balance), then measures `balanceChange` and calls `handleOut(balanceChange, circomData, i)`, which builds the output `UTXO` from `circomData.erc20TokenAddresses[i]` and `circomData.stealthAddressStructure` and sends the token to `msg.sender` (the Hinkal contract). [2](#0-1) 

`circomData.erc20TokenAddresses` and `circomData.stealthAddressStructure` are validated only by the ZK proof of the *caller of `transact`* — they are public inputs the caller's own proof must be consistent with (`formBasicInput` embeds `stealthAddressStructure.H1x/H1y/stealthAddress`, `H0x/H0y`, and `erc20TokenAddresses` directly as circuit public inputs). [3](#0-2) [4](#0-3)  Nothing ties this proof, or these fields, to `stack.signerAddress`'s signature — `performHinkalChecks` only requires that `circomData.originalSender` match the actual transaction sender (or be zero with a relay set), not that it match `stack.signerAddress`. [5](#0-4) 

Exploit flow: an attacker who obtains any validly signed `EmporiumStack` (e.g. one the victim intended for a self-custodied swap) can call `Hinkal.transact` themselves, supplying that same `stack` inside `circomData.externalActionData.externalActionMetadata`, but generating their own proof over `circomData` with `erc20TokenAddresses`/`stealthAddressStructure` of their choosing. `verifyWallet` still validates fine because the signature only checks `ops`/`maxFee`/`deadline`/`emporiumMessage`, all unchanged. `runAction` executes the victim wallet's authorized ops (spending the victim's real balance through `invokeWallet`), and `handleOut` then mints the resulting output value into a UTXO under the attacker's own `stealthAddressStructure`, transferring the actual tokens to the Hinkal contract in a note only the attacker can spend.

`usedMessages[circomData.emporiumMessage]` is indeed set to `true` before signature verification, but this ordering alone is not separately exploitable since a revert (e.g., on bad signature) unwinds the storage write too; the real issue is that a single, otherwise-legitimate first use is already sufficient to redirect funds because the destination/token fields were never part of what was signed. [6](#0-5) 

None of the existing guards close this gap: `performHinkalChecks`'s `calldataHash` check binds `circomData` internally consistent with itself, not with the `EmporiumStack` signature; `dimensionsCheck`/`checkOnchainCreation` don't reference `stack`; and the circuit's `inTotal + amountChanges === outTotal` only enforces the attacker's own proof is internally consistent, not that it matches the signer's intended token/destination. [7](#0-6) 

### Impact Explanation
Critical — direct theft of value spent from the signer's wallet balance (via authorized `invokeWallet` operations) into a shielded UTXO controlled by an unrelated attacker, since the destination `stealthAddressStructure` and accounted `erc20TokenAddresses` are entirely attacker-chosen and never bound to the signature the wallet owner produced. This is repeatable for every captured `EmporiumStack` with `invokeWallet` operations that move real wallet balance.

### Likelihood Explanation
Requires the attacker to obtain a validly-signed `EmporiumStack` for a target wallet performing a value-moving `invokeWallet` operation (e.g. a swap) and to be able to submit their own `transact` call with a self-generated proof — both are within the stated attacker capabilities (deploy contracts, craft `CircomData`, generate proofs for their own UTXOs, pick ordering). No privileged role is needed; the only precondition is exposure of a signed stack (e.g. via a relay/mempool/off-chain channel), which is the normal way these signatures are meant to be relayed.

### Recommendation
Include `circomData.erc20TokenAddresses` and `circomData.stealthAddressStructure` (and ideally `circomData.originalSender`/`relay`) in the EIP-712 typehash the signer approves (`EMPORIUM_SIGNATURE_TYPEHASH`), or otherwise cryptographically bind the executed op's resulting token/destination to the same signature that authorizes `stack.ops`, so a captured signature cannot be paired with an arbitrary output configuration.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`/`EmporiumUpgradeable` stack with a mock `IHinkalWallet` for `signerAddress` that performs a real token swap when `callHinkalWallet` is invoked.
2. Have `signerAddress` sign an `EmporiumStack` (`ops`, `maxFee`, `deadline`, fixed `emporiumMessage`) authorizing a swap op via `invokeWallet`.
3. Craft `circomData` A with `erc20TokenAddresses = [tokenOut]`, `stealthAddressStructure = victimStealth`, generate a valid proof, and confirm `handleOut` would route proceeds to `victimStealth`.
4. As the attacker, craft `circomData` B with the same signed `stack` embedded, but `erc20TokenAddresses` unchanged (must match actual swap output to be credited) and `stealthAddressStructure = attackerStealth`, with attacker's own self-consistent proof; call `Hinkal.transact` with B.
5. Assert: `handleOut`'s emitted `UTXO.stealthAddressStructure` equals `attackerStealth`, not `victimStealth`, while the tokens spent originate from `signerAddress`'s wallet balance via `callHinkalWallet` — demonstrating the equality "(erc20TokenAddresses, stealthAddressStructure) used == pair implied by signer's authorization" is broken on the very first (non-replay) use.

    function verifyWallet(
        EmporiumStack memory stack,
        CircomData calldata circomData
    ) internal {
        EmporiumStorageVars storage $ = _getEmporiumStorage();

        if ($.usedMessages[circomData.emporiumMessage]) {
            revert UsedMessage();
        }

        $.usedMessages[circomData.emporiumMessage] = true;

        if (stack.signerAddress == address(0)) {
            return;
        }

        bytes32 hashedMessage = _hashTypedDataV4(
            keccak256(
                abi.encode(
                    EMPORIUM_SIGNATURE_TYPEHASH,
                    circomData.emporiumMessage,
                    _hashEmporiumOps(stack.ops),
                    stack.maxFee,
                    stack.deadline
                )
            )
        );

        (address recoveredAddress, ECDSA.RecoverError err) = ECDSA.tryRecover(
            hashedMessage,
            stack.v,
            stack.r,
            stack.s
        );
        bool verified = err == ECDSA.RecoverError.NoError &&
            recoveredAddress == stack.signerAddress;
        if (!verified) {
            revert InvalidSignature();
        }

        if (block.timestamp > stack.deadline) {
            revert SignatureExpired();
        }

        if (circomData.feeStructure.flatFee > stack.maxFee) {
            revert FeeExceedsSignedMax();
        }
    }

    function performHinkalChecks(
        CircomData calldata circomData,
        Dimensions calldata dimensions,
        address sender
    ) external view returns (uint256[] memory) {
        require(
            (circomData.originalSender == address(0) &&
                circomData.relay != address(0)) ||
                (circomData.originalSender == sender &&
                    circomData.relay == address(0)),
            "invalid value for originalSender"
        );

        require(
            CircomDataBuilder.getHashedCalldata(circomData) ==
                circomData.calldataHash,
            "Calldata Hash Integrity Check Failed"
        );
        relayerIsValid(circomData.relay);
        dimensionsCheck(circomData, dimensions);
        checkOnchainCreation(circomData);

        return
            CircomDataBuilder.formInputForCircom(
                block.chainid,
                hinkalAddress,
                circomData
            );
    }
