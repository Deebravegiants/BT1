### Title
Webhook `shop` identity is not bound to the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC only over the raw request body [1](#0-0) , while the `shop` domain used by `Registry.process` to identify the tenant is read directly from an attacker-controllable HTTP header and is never included in the signed data [2](#0-1) . Because the same `api_secret_key` is shared by every shop that has the app installed, any merchant that controls one legitimate install can capture a genuine `(body, hmac)` pair from their own store and replay it against the app's webhook endpoint with the `shop-domain` header swapped for a victim shop, and `Utils::HmacValidator.validate` will still accept it [3](#0-2) .

### Finding Description
The bug-class pattern from the report ("checked balance vs. actually-created pair") maps here to: "a field acted on but not covered by the HMAC" — specifically, `shop` is acted upon by the webhook handler but is not covered by the signature.

- `Webhooks::Request#hmac` and `#to_signable_string` derive the signature solely from `@raw_body` (the JSON payload bytes) [4](#0-3) .
- `Webhooks::Request#shop` simply reads the `shopify-shop-domain` / `x-shopify-shop-domain` header with no cross-check against the signed payload [2](#0-1) .
- `Registry.process` validates only the HMAC, then hands `request.shop` straight to the app's handler as the trusted tenant identifier: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [5](#0-4) .
- `Utils::HmacValidator.validate_signature` verifies `HMAC(api_secret_key, raw_body)` against the received signature, with no reference to `shop` at all [6](#0-5) .

The equality that should hold is: `shop authenticated by HMAC == shop consumed by handler.handle`. In reality, HMAC only authenticates "the holder of `api_secret_key`" (i.e., that some genuine webhook was produced by Shopify for the app), while `shop` is an independent, unauthenticated header value. Since `api_secret_key` is identical for all shops that install the same app, any one merchant install is enough to mint valid `(body, hmac)` pairs that can be relayed with a forged `shop` header claiming to be a different, victim tenant.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce for webhook processing. An attacker who runs their own store with the target app installed can:
- Trigger a real webhook to their own shop with content they substantially influence (e.g. `orders/create`, `products/update` — order notes, line item properties, product titles/tags, etc.).
- Capture the resulting raw body and its valid `X-Shopify-Hmac-Sha256`.
- Replay that exact body/HMAC pair to the app's webhook endpoint with `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) rewritten to a victim shop's domain.
- `HmacValidator.validate` passes because it never inspected `shop` [3](#0-2) , and the app's registered handler executes business logic (session lookups, database writes, state changes) believing the event legitimately originated from the victim shop.

This qualifies as cross-tenant access: data/state attributed to shop A can be injected as if belonging to shop B purely by an unprivileged merchant of the app on their own store, with no access to B's credentials.

### Likelihood Explanation
Likelihood is significant for any app supporting multiple merchant installs (the standard Shopify app model): a single normal, non-privileged app install is a sufficient attacker foothold, no secrets from the victim are required, and forging HTTP headers on a POST to the app's own public webhook endpoint requires no special access.

### Recommendation
Bind the tenant identity into the verification step rather than trusting it as a bare header:
- Have `VerifiableQuery#to_signable_string` (or a webhook-specific equivalent) fold the `shop` value into the signed material, or
- After HMAC validation, cross-check `request.shop` against the set of shops actually authorized/installed for this app (e.g., verify a stored session exists for that shop) before invoking `handler.handle`, so a replay with a swapped `shop-domain` header can be rejected even though the body/HMAC pair is technically valid for some shop.

### Proof of Concept
1. App is installed on attacker's own shop `attacker.myshopify.com` and on victim's shop `victim.myshopify.com` (both using the same app `api_secret_key`).
2. Attacker triggers a legitimate webhook (e.g., `orders/create`) on their own store with attacker-influenced content, and captures the raw POST body plus `X-Shopify-Hmac-Sha256` header that Shopify sends to the app's endpoint.
3. Attacker replays that exact request to the app's webhook endpoint, only changing `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Webhooks::Request.new` accepts the headers/body [7](#0-6) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, raw_body)` and compares to the (still-valid) captured signature — it passes [8](#0-7) .
5. The registered handler runs with `shop: "victim.myshopify.com"` and attacker-controlled `body`, even though the data never came from victim's store.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

          received_signature = verifiable_query.hmac
