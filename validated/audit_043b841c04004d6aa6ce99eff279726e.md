### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) header values are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while `shop`, `topic`, `api_version`, and `webhook_id` are read straight from unauthenticated HTTP headers. `Webhooks::Registry.process` validates only the body HMAC and then blindly trusts the header-derived `shop` value when constructing `WebhookMetadata` passed to the app's handler. This breaks the intended binding `authenticated(body) == attributed(shop)`, letting anyone who possesses one valid `(body, hmac)` pair (e.g. from installing the app on their own store) replay it against the app's public webhook endpoint with an arbitrary `x-shopify-shop-domain` header, causing the app to process the payload as if it belongs to a different tenant.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are pulled directly from HTTP headers with no cryptographic binding to the signed body: [2](#0-1) 

`HmacValidator.validate` verifies only `verifiable_query.to_signable_string` (i.e., the raw body) against the computed HMAC: [3](#0-2) 

`Webhooks::Registry.process` performs this body-only HMAC check and then constructs `WebhookMetadata` using the unauthenticated `request.shop`, handing it to the host application's webhook handler as the tenant identifier: [4](#0-3) 

Because the HMAC never covers the `shop-domain` header, the equality the library implicitly promises — "HMAC-verified bytes == the shop this data is attributed to" — does not hold. Any party that obtains one legitimate `(raw_body, x-shopify-hmac-sha256)` pair signed with the app's shared `api_secret_key` (trivially available to an unprivileged attacker who installs the app for free on their own development/trial store and captures the resulting webhook delivery) can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting a different `x-shopify-shop-domain` header value. The HMAC check still passes (body unchanged), and the handler receives `WebhookMetadata` claiming the payload originated from the victim shop.

### Impact Explanation
This is a cross-tenant identity confusion vulnerability: the gem hands the host application attacker-controlled tenant attribution (`shop`) alongside genuinely-signed, but tenant-mismatched, body content. Any app that uses `data.shop` from `WebhookMetadata` to route/store the webhook payload (the documented and expected usage pattern) can be made to apply one merchant's webhook data under a different merchant's identity — a cross-tenant access/data-integrity break, which maps to the "Critical — cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high: the attacker does not need any privileged credential of the app operator. They only need to be able to install the app themselves (any Shopify merchant/developer can do this for free) to receive a legitimate webhook and its valid HMAC, and then send a forged HTTP POST to the app's public webhook endpoint with a substituted `shop-domain` header — both trivially achievable by an unprivileged internet user.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the HMAC-signable representation (or otherwise cryptographically bind them to the body, e.g. by validating the shop against the session/store that installed the app, or requiring the host application to independently confirm the shop is a known, installed merchant) before constructing `WebhookMetadata`. At minimum, document clearly that `request.shop` is unauthenticated and must not be trusted for authorization without an independent installed-shop lookup.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and captures a real webhook delivery, e.g. body `B` with header `x-shopify-hmac-sha256: H` (valid since `H = HMAC-SHA256(api_secret_key, B)`), and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker sends a new POST request to the app's public webhook endpoint with the exact same body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(api_secret_key, B)` and finds it matches `H` — validation passes since the shop header is never part of the signed string: [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: parsed_body_of_B, ...)`, causing the host app to process attacker-supplied data as belonging to the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
