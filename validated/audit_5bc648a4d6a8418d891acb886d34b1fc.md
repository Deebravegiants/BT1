### Title
Webhook `shop` (tenant) identity is not covered by the HMAC, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then dispatches the (already-parsed) body to the app's handler tagged with a `shop` value that is read from an unauthenticated header. Because the app's `client_secret` (used as the HMAC key) is identical for every shop that installs the app, any actor who can obtain one genuine `(body, hmac)` pair — trivially, by installing the app on their own store — can replay that pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain`/`shopify-shop-domain` header for an arbitrary victim shop domain. The signature still validates because it never covered the shop identity, and the handler receives attacker-controlled data attributed to the victim tenant.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string`, and for webhook requests that string is just the raw HTTP body: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight out of HTTP headers, none of which participate in the signable string: [2](#0-1) 

`Registry.process` performs only the body HMAC check, then immediately trusts `request.shop` as the tenant identity passed to the app's handler: [3](#0-2) 

The equality this code implicitly assumes is: `shop authenticated by the request == shop delivered to the handler`. In reality, the HMAC only proves `body == HMAC_verify(body, client_secret)`; it proves nothing about which shop header accompanied that body. Since the HMAC secret (`client_secret`) is shared across every shop that installs a given app (not shop-specific), an unprivileged internet user can:
1. Install the app for free on their own (attacker-controlled) development/test store — a normal, unprivileged action requiring no special access to the victim.
2. Receive a genuine webhook from Shopify for their own store, capturing a valid `(raw_body, x-shopify-hmac-sha256)` pair signed with the app's `client_secret`.
3. Replay that exact `(raw_body, hmac)` pair directly to the app's public webhook endpoint, but with `x-shopify-shop-domain` changed to the victim's `myshopify.com` domain.
4. `HmacValidator.validate` passes (body+hmac are still consistent), and `Registry.process` calls the handler with `WebhookMetadata.shop == "victim.myshopify.com"` while `body` is fully attacker-controlled content from the attacker's own store.

This breaks the tenant identity binding the gem's own documentation assumes handlers can rely on ("`shop` — The shop domain of the webhook"), letting an attacker inject falsified data (fake orders, fake customer records, fake app/uninstall or GDPR redact events, etc.) attributed to a shop they do not control.

### Impact Explanation
This is a cross-tenant data-injection vector: an attacker with no relationship to the victim shop can cause an app to process arbitrary, attacker-chosen webhook payloads as if they originated from the victim tenant, because the gem exposes and the host app is expected to trust `request.shop`/`WebhookMetadata#shop` without it being bound to the HMAC that authenticates the request. Depending on how the host app keys its per-shop state off `data.shop` (queue jobs, database writes, GDPR/redact processing, order sync, uninstall handling), this can lead to cross-tenant data corruption or state confusion for the victim shop.

### Likelihood Explanation
Likelihood is real but has a precondition: the attacker needs at least one genuine `(body, hmac)` pair signed with the target app's `client_secret`. This is trivially obtainable for any app distributed on the Shopify App Store or any dev app, since an attacker can just install the app on their own store and receive real webhooks for it (this requires no compromise of the victim, the merchant's token, or the app's secret — only the shared, install-time HMAC key common to that app).

### Recommendation
Do not treat the `shop` header as authenticated tenant identity on its own. Options: bind the shop domain (and ideally webhook id / topic) into the HMAC-verified payload check by cross-referencing it against the shop that was actually granted the specific webhook subscription id server-side (e.g., verifying `webhook_id` against Shopify's API for that shop before trusting `shop`), or otherwise document/require that host apps must not use the unauthenticated `shop` header as a sole tenant key without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, granting it webhook subscription for topic `orders/create`.
2. Shopify delivers a genuine webhook to the app: `raw_body = attacker_json`, header `x-shopify-hmac-sha256 = HMAC(client_secret, attacker_json)`, header `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker replays the identical `raw_body` and `x-shopify-hmac-sha256` to the same webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds successfully; `Utils::HmacValidator.validate` succeeds because it only re-hashes `raw_body`: [4](#0-3) 
5. `Registry.process` invokes the app's handler with `shop: "victim.myshopify.com"` and `body: attacker_json`, as demonstrated by the test harness pattern: [5](#0-4)
