### Title
Webhook `shop` (and `topic`) identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` field from an unauthenticated HTTP header, while the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` validates only covers the raw request body. This breaks the identity binding `shop asserted-to-handler == shop that produced the signed bytes`, letting any party who can obtain a validly-signed webhook (signed with the app's single shared `client_secret`) relabel it as belonging to a different merchant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile, `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from HTTP headers that are never mixed into the signable string: [2](#0-1) 

`HmacValidator.validate` computes the HMAC purely over `to_signable_string` (i.e., the raw body) and compares it against the `shopify-hmac-sha256` header: [3](#0-2) 

`Webhooks::Registry.process` performs exactly this check and then forwards the *unauthenticated* `request.shop` value straight to the app's handler as the tenant identifier, alongside the verified body: [4](#0-3) 

This is precisely the reported bug class: a field (`shop`) that is *acted on* (passed to the handler as the source-of-truth tenant identity) is not covered by the cryptographic check that the code performs. The gem's own documentation reinforces the false expectation that `process` "will verify the request did indeed come from Shopify" as a whole, when in fact only the body bytes are verified — not which shop the webhook is claimed to be for: [5](#0-4) 

Critically, Shopify signs webhooks for *all* shops that installed a given app using that **single shared `client_secret`** for the app. Therefore, a webhook that is genuinely and validly signed for Shop A's install is signed with the exact same secret that signs Shop B's webhooks. Any party who receives a legitimate webhook for their own shop (e.g., an attacker who installs the same public app) can capture that signed body+HMAC pair and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` (and `x-shopify-topic`) header rewritten to name a victim shop. Because `HmacValidator.validate` never looks at these headers, `Registry.process` will accept the payload as if it authentically originated for the spoofed shop and dispatch it to the handler with the attacker-chosen `shop`.

### Impact Explanation
Host applications built on this gem are documented to trust `data.shop` from `WebhookMetadata` as the authoritative tenant key (see the documented handler example that uses `data.shop` to route/store per-merchant data): [6](#0-5) 

An attacker who can obtain any validly-HMAC'd webhook body from the same app (trivial: install the app on a shop they control and trigger the target topic) can forge a webhook attributed to an arbitrary victim shop domain. Depending on how the host app persists webhook payloads (order data, customer data, GDPR/compliance topics, uninstall notifications, etc.) keyed by `data.shop`, this enables cross-tenant data injection/corruption — data belonging to the attacker's shop gets written into or triggers side effects for a victim's tenant record. This satisfies the "cross-tenant access" Critical impact criterion, since the identity boundary between merchants collapses.

### Likelihood Explanation
Any user of the app (i.e., any merchant who installs it — which for public apps is any unprivileged internet user) can generate a validly-signed webhook body for their own store and then freely control the `shop-domain`/`topic` headers, since these are never part of the signed payload. No access to `client_secret`, tokens, or the victim's credentials is required — only a legitimate installation of the same app by the attacker.

### Recommendation
Bind the `shop` (and `topic`, `webhook_id`, `api_version`) identity headers into the value that is cryptographically verified, or otherwise fail closed when they can't be tied to the signed body. Concretely:
- Include the `shop-domain` (and `topic`) header values in `Request#to_signable_string` so the HMAC covers them, rejecting any mismatch between the header and what Shopify actually signed, or
- Document explicitly (and enforce in the gem) that `process` only authenticates the body, and require host apps to separately verify `shop` against a known/installed-shop list before trusting it — but since this is a gem-level identity binding gap, the safer fix is to make `HmacValidator` reject webhooks whose `shop` header cannot be validated against the signed content.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and receives a legitimate webhook (e.g., `orders/create`) with body `B`, and headers including `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's shared `client_secret`) and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker replays the exact same body `B` and HMAC `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim.myshopify.com", hmac-sha256: H...})` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H`.
4. The handler is invoked with `WebhookMetadata(shop: "victim.myshopify.com", body: B, ...)`, causing the host app to process/store attacker-controlled data under the victim's tenant identity.
