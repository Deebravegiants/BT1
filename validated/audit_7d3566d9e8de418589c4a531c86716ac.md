Audit Report

## Title
Vault request replay guard is in-memory only, allowing an already-consumed, single-use gateway authorization to be reused after a node restart - ([File: core/capabilities/vault/request_replay_guard.go])

## Summary
`RequestReplayGuard` is the sole mechanism converting the inherently reusable `AllowListBasedAuth`/JWT authorization into a single-use guarantee, but it stores "already seen" digests only in a process-local `map[string]int64` with no persistence. Any node restart resets this state while the underlying on-chain allowlist entry (or JWT) can still be unexpired, letting a client resend a previously consumed, authorized request and have it executed again by `Authorizer.AuthorizeRequest`.

## Finding Description
`RequestReplayGuard.CheckAndRecord` is a pure in-memory map guarded by a mutex, with no database or durable backing store [1](#0-0) . `NewAuthorizer` constructs a fresh `RequestReplayGuard` on every instantiation, and `AuthorizeRequest` relies exclusively on this guard to reject a digest that was already authorized [2](#0-1) . The underlying `AllowListBasedAuth.AuthorizeRequest` is explicitly designed to re-authorize the same digest as many times as requested so long as the on-chain allowlist entry's `ExpiryTimestamp` has not passed — this is confirmed both by the code and by the test comment stating replay protection is delegated to the generic `Authorizer`. Because the guard's state does not survive process restarts, an authorized digest that has already been consumed becomes authorizable again after any deploy, crash, or node rotation, as long as the allowlist/JWT expiry window has not elapsed. This is reachable from `GatewayHandler.HandleGatewayMessage`, which routes `SecretsCreate/Update/Delete/List` through `Authorizer.AuthorizeRequest` as the sole replay defense.

## Impact Explanation
This breaks the documented single-use invariant of vault gateway authorizations ("a given request digest is only accepted once"). Because the allowlist entry is meant to authorize exactly one action, a client that retains a copy of its own previously-submitted, already-executed request can resend it and obtain a second execution of that authorized action (e.g., a duplicate `SecretsCreate`/`SecretsUpdate`) whenever a node restart happens to occur within the expiry window — this is a duplicate/replay-driven bypass of the allowlist's single-use semantics, which is an in-scope "allowlist bypass" / duplicate-effect class of impact. Notably, this does not require network interception: the legitimate requester itself, holding its own already-sent request, can attempt replay purely by waiting for or repeatedly probing across a routine node restart.

## Likelihood Explanation
No privileged access is required — a normal, previously-authorized client can trigger this simply by resending a request it authored itself. The primary constraint is timing: the underlying process must restart (a routine operational event — deploy, crash, rolling upgrade, node rotation) while the allowlist/JWT expiry window is still open. Since expiry windows are configurable and can be relatively long (e.g., an hour in test scenarios), and restarts are a normal part of node operations, the exposure window is realistic, though it is not fully attacker-controlled.

## Recommendation
Persist replay-guard state (e.g., in the node's database) so that consumed digests remain "seen" across process restarts, or bind allowlist/JWT expiry windows tightly to expected request-completion time so a restart cannot reopen a meaningful replay window. At minimum, do not treat the in-memory `RequestReplayGuard` alone as sufficient for the single-use guarantee across restarts.

## Proof of Concept
1. Allowlist a `SecretsCreate` request digest on-chain with a 1-hour expiry.
2. Send the request through the gateway; `GatewayHandler.HandleGatewayMessage` → `Authorizer.AuthorizeRequest` authorizes and records the digest in the in-memory `RequestReplayGuard`, and `SecretsCreate` executes.
3. Restart the node process before the allowlist expiry elapses; a new `Authorizer`/`RequestReplayGuard` is constructed with an empty `seen` map [3](#0-2) .
4. Resend the identical request; `AllowListBasedAuth.AuthorizeRequest` re-authorizes it (still unexpired) and the fresh `RequestReplayGuard.CheckAndRecord` has no record of it, so `SecretsCreate` executes a second time [4](#0-3) .
   A deterministic Go unit test can simulate this without an actual process restart: authorize/record a digest via one `RequestReplayGuard` instance, then construct a second fresh `RequestReplayGuard` instance (simulating restart) and show `CheckAndRecord` succeeds again for the same digest/expiry.

type RequestReplayGuard struct {
	mu      sync.Mutex
	seen    map[string]int64 // digest → unix expiry timestamp
	nowFunc func() time.Time // injectable for testing
}

// NewRequestReplayGuard creates a replay guard for authorized Vault requests.
func NewRequestReplayGuard() *RequestReplayGuard {
	return &RequestReplayGuard{
		seen:    make(map[string]int64),
		nowFunc: time.Now,
	}
}

// CheckAndRecord returns ErrRequestAlreadySeen if the digest was previously
// recorded and has not yet expired. Otherwise it records the digest with
// the given expiry timestamp (unix seconds, UTC).
//
// Expired entries are cleaned up on every call.
func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}

func NewAuthorizer(allowListBasedAuth Authorizer, jwtBasedAuth Authorizer, lggr logger.Logger) Authorizer {
	return &authorizer{

func (a *authorizer) AuthorizeRequest(ctx context.Context, req jsonrpc.Request[json.RawMessage]) (*AuthResult, error) {
	authResult, err := a.authorizeRequest(ctx, req)
	if err != nil {
		return nil, err
	}
	if authResult == nil {
		err = errors.New("auth mechanism returned nil auth result")
		a.lggr.Errorw("auth mechanism returned nil auth result", "method", req.Method, "requestID", req.ID, "hasAuth", req.Auth != "")

	}
	if err := a.replayGuard.CheckAndRecord(authResult.Digest(), authResult.ExpiresAt()); err != nil {
