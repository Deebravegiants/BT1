### Title
Webhook shop/topic identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes/verifies the HMAC over the raw HTTP body only, while the `shop`, `topic`, `webhook_id`, and `api_version` fields that identify *which tenant* the webhook belongs to are read directly from unauthenticated HTTP headers. `Registry.process` validates only the body HMAC and then dispatches to the handler using these unverified header values as the tenant identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `Request#shop`, `#topic`, `#api_version`, `#webhook_id` are all pulled straight from HTTP headers with no cryptographic binding: [2](#0-1) 

`HmacValidator.validate` (and the underlying `validate_signature`) verifies exactly what `to_signable_string` returns, i.e. only the body bytes, against the app's single shared `api_secret_key`: [3](#0-2) 

`Registry.process` performs this body-only HMAC check and then immediately trusts `request.shop`, `request.topic`, `request.webhook_id`, `request.api_version` — all header-derived, unauthenticated values — to build the `WebhookMetadata` passed into the app's handler: [4](#0-3) 

The identity binding that should hold is: `hmac(secret, signable_string) == received_hmac` implies `signable_string` (and everything the app subsequently treats as authenticated, including tenant identity) was produced by Shopify for *this specific request*. Here the equality only covers the body bytes:
`hmac_verified_bytes == raw_body ≠ (raw_body, shop, topic, webhook_id, api_version)` — the header fields that the handler uses to decide "which merchant/tenant does this data belong to" are outside the signed material.

Because the API secret (`Context.api_secret_key`) is a single value shared by the app across *all* installed shops (not shop-specific), any shop that has installed the app can trigger a webhook event on their own store (e.g., `customers/data_request`, `orders/create`, etc.), capture the genuinely Shopify-signed `(raw_body, hmac)` pair for their own shop, and then replay that exact body+HMAC to the app's webhook endpoint while forging the `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) headers to name a different, victim shop. `HmacValidator.validate` will still pass because it only checks the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload is `shop: victim-shop.myshopify.com` even though the actual signer/originator was the attacker's own shop.

### Impact Explanation
This is a cross-tenant identity confusion at the boundary between "cryptographically verified" and "acted upon." Any app whose webhook handlers key persistence, authorization, or business logic off `WebhookMetadata#shop` (which is exactly the documented/intended usage pattern of this gem) can be made to apply attacker-supplied webhook body data to a victim shop's tenant record, since the HMAC only proves the body came from Shopify for *some* shop — not that it came from Shopify *for the claimed shop*. This falls into "cross-tenant access," which the rules classify as Critical impact.

### Likelihood Explanation
The attacker only needs their own legitimate installation of the target app (any merchant can install most public apps) and the ability to POST arbitrary headers/body to the app's public webhook endpoint (which by design must be reachable by "Shopify," i.e. by anyone claiming to be Shopify, since the endpoint has no other authentication than this HMAC check). No access to `api_secret_key`, tokens, or any privileged account is required beyond ordinary self-service app installation, so this is exploitable by an unprivileged internet user/merchant.

### Recommendation
Include the tenant-identifying headers (`shop`, `topic`, `webhook_id`, `api_version`) in the material that is verified, not just the raw body — e.g. by having the host application independently corroborate `request.shop` against the shop that was expected/registered for that webhook subscription, or by requiring the webhook consumer to cross-check the `shop` header against a known, previously-established relationship (session/store record) before trusting it, rather than treating any header value that arrives alongside a validly-HMACed body as authoritative tenant identity. At minimum, the gem's documentation and `WebhookMetadata` should make explicit that `shop`/`topic`/`webhook_id` are **not** covered by `HmacValidator.validate` and must not be trusted as tenant identity without additional verification by the host application.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and configures a webhook subscription (or reuses a mandatory one such as `customers/data_request`).
2. Shopify sends a legitimately signed webhook to the app: body `B`, headers including `X-Shopify-Hmac-Sha256: H`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: customers/data_request`.
3. Attacker captures `(B, H)` and replays a new HTTP POST to the same webhook endpoint with the same body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` in `Registry.process` recomputes HMAC over `B` only and it matches `H`, so validation passes (`lib/shopify_api/webhooks/registry.rb:190`).
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the app to process attacker-controlled data as if it belonged to `victim-shop.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
