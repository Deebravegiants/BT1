### Title
Theft of NFTs/ERC721/ERC1155 tokens held by the shared `EmporiumUpgradeable` contract via unrestricted CASE 2 stateless calls - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Finding Description
The claimed equality is: *"every asset created by a user's ops is owned by that user's wallet or stealth address, never by Emporium."* This equality is broken because `EmporiumUpgradeable` is a single shared contract used by every `transact` caller (guarded only by `onlyAllowedRecipient`, which just checks `msg.sender == Hinkal`, see [1](#0-0) ), yet its post-op accounting only iterates the caller's own `circomData.erc20TokenAddresses` array [2](#0-1) .

`Transferer.getERC20OrETHBalance`/`getBalancesForArray`, used to compute `balancesBefore`/`balancesAfter`, only support ERC20 `balanceOf`/ETH balance semantics [3](#0-2) . `Transferer` explicitly implements `onERC721Received`/`onERC1155Received`, so Emporium (which inherits `Transferer`) can and does receive NFTs from any user's CASE 2 op [4](#0-3) , but nothing in `runAction` ever represents such an NFT as a UTXO for the depositing user — only tokens present in the caller's own `erc20TokenAddresses` array are turned into `UTXO` via `handleOut` [5](#0-4) .

CASE 2 ("Stateless Interaction") lets any caller specify an arbitrary `op.endpoint` and `op.callData`, executed as `op.endpoint.call{value: op.value}(op.callData)` — the only restriction is a selector blacklist against `callHinkalWallet`/`doSendToRelay` [6](#0-5) . If `stack.signerAddress == address(0)`, `verifyWallet` returns immediately with no signature check at all [7](#0-6) , so an attacker needs no wallet/relay authorization to invoke an op — only a valid ZK proof for their own (potentially trivial, zero-value) `circomData`.

Exploit flow: Emporium ends up holding an NFT (e.g. a victim's protocol-position NFT minted to Emporium via a prior CASE 2 op, or any other externally-minted NFT). An unrelated attacker calls `Hinkal.transact` with `externalActionId` pointed at Emporium and an `EmporiumStack` containing a single CASE 2 op: `endpoint = nftContract`, `callData = abi.encodeWithSelector(IERC721.safeTransferFrom.selector, emporium, attacker, victimTokenId)`. Since `msg.sender` as seen by the NFT contract is Emporium (the actual token owner), `safeTransferFrom` succeeds unconditionally. The attacker's own `circomData.erc20TokenAddresses` never includes `nftContract`, so the balance-diff loop at lines 132-151 never observes or constrains this transfer, `deltaAmountChanges` never reflects it, and no nullifier/UTXO accounting for that asset is touched. `payloadHash`/`calldataHash` commitments only prevent tampering by a relay with the attacker's own submitted data — they do not restrict what the attacker (the author of the payload) is allowed to target.

### Impact Explanation
Any asset (NFT, or any token type the caller chooses to omit from their own `erc20TokenAddresses` list) sitting in the shared `EmporiumUpgradeable` contract can be moved out by an unrelated, unprivileged attacker with a single, cheap, arbitrary `transact` call, with zero effect on the balance/UTXO accounting invariants that are supposed to guarantee "value moved equals value counted." This is direct theft of another user's (or the protocol's) asset from a shared contract, permanently and irrecoverably, matching Critical severity ("direct theft of shielded or in-flight user funds"/"executing calls or moving assets a wallet owner or prover never authorised"). It is fully repeatable for every asset stranded at Emporium.

### Likelihood Explanation
Precondition is only that some ERC721/ERC1155 (or any token) ends up held by Emporium — a state Emporium's own `onERC721Received`/`onERC1155Received` implementation explicitly supports and even a legitimate CASE 2 interaction (e.g. minting an LP-position NFT) can create. The attacker needs no privileged role, no victim key, and no signature (since `signerAddress == address(0)` skips `verifyWallet`'s signature branch); they only need to submit their own valid, otherwise-trivial ZK proof to pass `verifyProof`/`performHinkalChecks`. Cost is one transaction; feasibility is high given the code as written.

### Recommendation
Restrict CASE 2 stateless calls so `op.endpoint` cannot be used to move out tokens/NFTs that were not deposited/owned by the calling user in the same operation (e.g., maintain explicit per-depositor NFT/token accounting rather than relying purely on a self-declared ERC20 address array, or disallow direct external calls to arbitrary token contracts from Emporium's own context entirely, funneling all such calls exclusively through the signed, wallet-scoped CASE 1 path with strict authorization).

### Proof of Concept
Foundry test: (1) Deploy `EmporiumUpgradeable`, an `ERC721` mock, and `Hinkal`. (2) As "victim," call `Hinkal.transact` with `externalActionId` for Emporium and a CASE 2 op whose `callData` mints/transfers `victimTokenId` to `emporium`; assert Emporium now owns the token and no UTXO/commitment event referencing this token was emitted (the `UTXO[]` returned by `runAction` has no entry for the NFT). (3) As unrelated "attacker," call `Hinkal.transact` with their own minimal valid proof/`circomData` (excluding the NFT contract from `erc20TokenAddresses`) and a CASE 2 op with `callData = abi.encodeWithSelector(IERC721.safeTransferFrom.selector, emporium, attacker, victimTokenId)`. Assert the call succeeds, `nftMock.ownerOf(victimTokenId) == attacker`, and that `deltaAmountChanges`/`balancesBefore`/`balancesAfter`/`utxoSet` computed inside `runAction` never referenced the NFT contract — i.e., the balance equation before/after is unaffected by the stolen asset.
