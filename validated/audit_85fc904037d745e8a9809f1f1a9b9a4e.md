### Title
Unsynchronized concurrent read of `authorizedKeys` map in `WorkflowMetadataHandler.Authorize` races with periodic `syncMetadata` writes - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

### Summary
The Olympus governance bug (M-10) is a class of "stale snapshot compared against mutated shared state" defect: a value read/decided at one point in time (a user's cast vote) is later invalidated by concurrent, unsynchronized mutation of the underlying collection it depends on (vote supply), producing an inconsistent authorization/accounting result. The closest reachable analog in this codebase is in the internet-facing gateway's `WorkflowMetadataHandler`, where the `authorizedKeys` map used to authorize unprivileged HTTP-trigger requests is read without holding the handler's mutex, while a periodic background goroutine mutates (replaces) that same map under the mutex.

### Finding Description
`WorkflowMetadataHandler.Authorize` is the function that authorizes incoming, unprivileged JSON-RPC/HTTP trigger requests against a workflow's registered signer keys: [1](#0-0) 

Note that at line 92 it reads `h.authorizedKeys[workflowID]` directly, with **no `h.mu.RLock()`**: [2](#0-1) 

Meanwhile, `syncMetadata` — run periodically via a background ticker (`h.runTicker(time.Duration(h.config.MetadataAggregationIntervalMs)*time.Millisecond, h.syncMetadata)`) — replaces the entire `h.authorizedKeys` map (and related maps) while holding `h.mu.Lock()`: [3](#0-2) [4](#0-3) 

Every other accessor of the same handler state (`WorkflowShards`, `GetWorkflowID`, `GetWorkflowReference`) correctly acquires `h.mu.RLock()` before reading, showing that `Authorize` is the outlier that was missed: [5](#0-4) [6](#0-5) 

This mirrors the Olympus root cause exactly: the outcome of an unprivileged action (a vote / here, an authorization decision) is checked against shared mutable state (vote supply / here, the `authorizedKeys` map) that a separate, independently-triggered process (admin `issueVotesTo`/`revokeVotesFrom` / here, the periodic `syncMetadata` sync) can mutate concurrently without any coordination with the in-flight check, because the read path bypassed the lock that protects consistency.

The earlier broader search did show `Authorize` is called from `core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go` (1 match reported), which is consistent with the HTTP Trigger Handler description that "Authentication: Verifies JWT token (ECDSA signature) and checks authorized keys" for inbound trigger requests from unprivileged workflow requesters: [7](#0-6) 

I could not confirm the exact line/receiver at which `HandleUserTriggerRequest` calls `.Authorize(...)`, so the precise request-handling code path should be verified directly in `http_trigger_handler.go`.

### Impact Explanation
In Go, concurrent unsynchronized read/write access to the same map from different goroutines is undefined behavior and, when detected by the runtime, causes an immediate `fatal error: concurrent map read and map write`, crashing the process. Because:
- `Authorize` is invoked on every unprivileged HTTP-trigger request (attacker-controlled request rate), and
- `syncMetadata` runs unconditionally on a fixed period once the handler is started,

any attacker who can send trigger requests to the gateway can race this window repeatedly, making the crash reliably triggerable — a remote, unauthenticated Denial of Service against the gateway node process. Even short of a hard crash, a torn/partial read of the map during the map's internal rehash (as `h.authorizedKeys = authorizedKeys` swap occurs) can yield inconsistent authorization decisions, analogous to the Olympus report's "unreliable results on whether the proposal can be executed."

### Likelihood Explanation
Likelihood is high: no privileged access is required, only the ability to send HTTP trigger requests to the gateway (the stated in-scope unprivileged path), and the racing writer (`syncMetadata`) runs on every gateway node by design at a fixed interval (`MetadataAggregationIntervalMs`, default 1 minute per the constant `defaultMetadataAggregationIntervalMs`). Sustained request traffic during that periodic window will eventually hit the race.

### Recommendation
Acquire `h.mu.RLock()`/`RUnlock()` around the read of `h.authorizedKeys[workflowID]` (and the subsequent `keys[key]` lookup) inside `Authorize`, consistent with the locking pattern already used in `WorkflowShards`, `GetWorkflowID`, and `GetWorkflowReference`. Consider also snapshotting the specific per-workflow key set under the lock (e.g., copy just the `map[gateway.AuthorizedKey]struct{}` for `workflowID`) to minimize lock hold time while eliminating the race.

### Proof of Concept
1. Start a `WorkflowMetadataHandler` with `Start(ctx)`, which schedules the `syncMetadata` ticker per `MetadataAggregationIntervalMs`.
2. Register at least one workflow's authorized keys via metadata sync (as done in `TestSyncMetadata`) so `h.authorizedKeys` is non-empty.
3. From one goroutine, continuously call `handler.Authorize(workflowID, validJWT, req)` in a tight loop (simulating unprivileged HTTP trigger traffic).
4. From another goroutine (or by letting the real ticker fire), continuously invoke `handler.syncMetadata(ctx)` to repeatedly replace `h.authorizedKeys`.
5. Run under Go's race detector (`go test -race`) or long enough under load: the concurrent unsynchronized map read in `Authorize` at line 92 versus the locked write in `syncMetadata` at lines 164–178 will be flagged by the race detector, and under sufficient contention can produce `fatal error: concurrent map read and map write`, crashing the gateway node. func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (h *WorkflowMetadataHandler) WorkflowShards(workflowID string) []*shardEndpoint {
	h.mu.RLock()
	defer h.mu.RUnlock()

func (h *WorkflowMetadataHandler) GetWorkflowID(workflowOwner, workflowName, workflowTag string) (string, bool) {
	h.mu.RLock()
	defer h.mu.RUnlock()
	workflowRef := workflowReference{
		workflowOwner: workflowOwner,
		workflowName:  workflowName,
		workflowTag:   workflowTag,
	}
	workflowID, exists := h.workflowRefToID[workflowRef]
	if !exists {
		return "", false
	}
	return workflowID, true
}
