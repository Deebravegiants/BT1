## Title
Webhook HMAC validation covers only the raw body, not the `shop`, `topic`, `webhook-id`, or `api-version` headers, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read from HTTP headers that are never included in the HMAC computation. `Registry.process` trusts `request.shop` unconditionally once the HMAC check passes, so an attacker who can obtain one valid `(body, HMAC)` pair (e.g., by installing the app on their own store and capturing a real webhook delivery) can replay that same body/HMAC pair while forging the `x-shopify-shop-domain` (and `x-shopify-topic`/`x-shopify-webhook-id`) headers to impersonate a different shop.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

only the raw body (`@raw_body`) is signed. However, `shop`, `topic`, `webhook_id`, and `api_version` are derived purely from headers: [2](#0-1) 

`Registry.process` validates the HMAC and then trusts these header-derived fields when dispatching to the handler: [3](#0-2) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`, i.e. only the body, using `OpenSSL.secure_compare`: [4](#0-3) 

The identity binding broken is:
`HMAC-verified bytes (raw_body)` ≠ `bytes acted upon (shop, topic, webhook_id, api_version headers)`

Since the shop attribution used by the webhook handler is not part of what's cryptographically verified, any entity capable of producing one valid `(raw_body, HMAC)` pair for the app's shared secret — trivially available to any merchant who installs the app on their own store, since Shopify signs and delivers genuine webhooks to them — can resend that exact body with the HMAC header intact, but with the `shop-domain` (and/or `topic`/`webhook-id`) header rewritten to name a completely different (victim) shop. `HmacValidator.validate` will still pass because it only checks the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the (forged) victim `shop`.

### Impact Explanation
This breaks the tenant isolation boundary: a webhook event that is cryptographically only proven to have originated from the app's Shopify integration (not tied to any specific shop) is delivered to the app's handler as if it belongs to an arbitrary shop of the attacker's choosing. Depending on how the app uses `WebhookMetadata#shop` (e.g., looking up sessions/access tokens, triggering data deletion for GDPR webhooks like `customers/redact` or `shop/redact`, updating billing/subscription state, or writing data under that shop's tenant record), this enables cross-tenant data corruption, spoofed compliance/redaction actions against a victim shop, or injection of forged business events attributed to a shop the attacker does not control.

### Likelihood Explanation
Exploitation only requires the attacker to install the app on a shop they control (a normal unprivileged action) and capture one legitimate webhook delivery to obtain a valid `(body, HMAC)` pair for a topic of interest, then send a normal HTTP POST to the app's registered webhook endpoint with the captured body/HMAC and a forged `shop-domain`/`topic` header. No access token, `client_secret`, or privileged credential is needed.

### Recommendation
Include all fields relied upon for authorization/attribution — `shop-domain`, `topic`, `webhook-id`, `api-version` — in the value that is HMAC-verified, or otherwise cryptographically bind them (e.g., verify `shop` against the session/shop the webhook was registered for, not solely trust the header). At minimum, `to_signable_string` should incorporate the shop/topic headers so `HmacValidator.validate` fails if they are altered independently of the body.

### Proof of Concept
1. Install the vulnerable app on an attacker-controlled shop `attacker.myshopify.com`. Wait for (or trigger) a genuine webhook delivery for topic `customers/redact` (or any topic the app handles) — Shopify sends:
   - Headers: `x-shopify-topic: customers/redact`, `x-shopify-hmac-sha256: <valid_hmac_for_body>`, `x-shopify-shop-domain: attacker.myshopify.com`
   - Body: `{"shop_id":..., "customer": {...}}`
2. Attacker replays this exact request to the app's webhook endpoint, keeping the body and `x-shopify-hmac-sha256` unchanged, but rewrites `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate(request)` succeeds because it only hashes `@raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
4. `Registry.process` dispatches to the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: "customers/redact", body: <attacker's body>, ...)`, causing the app to perform the redaction/action against the victim shop's tenant data instead of the attacker's own.
