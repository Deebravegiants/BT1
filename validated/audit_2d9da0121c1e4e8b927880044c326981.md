### Title
Webhook `shop`, `topic`, `webhook_id` and `api_version` identity fields are trusted from unauthenticated HTTP headers while only the raw body is covered by the HMAC - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body. The `shop` (tenant identity), `topic`, `webhook_id`, and `api_version` values that are handed to the app's `WebhookHandler#handle` as `WebhookMetadata` are read verbatim from HTTP headers that are **not** part of the signed material. Any actor who can obtain one validly-signed webhook body/HMAC pair (trivially available to any merchant that installs the app, since the signing secret is the single app-wide `client_secret`, not a per-shop secret) can replay that body with an arbitrary `shop`, `topic`, `webhook_id`, or `api_version` header and still pass `HmacValidator.validate`.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`: for `Webhooks::Request` this is defined as the raw body alone. [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors used by the registry/handler pipeline are read directly from headers, which are never included in the signable string: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `verifiable_query.to_signable_string` (i.e. only the body): [3](#0-2) 

`Registry.process` raises only if the HMAC (body) check fails, then immediately trusts `request.shop`/`request.topic`/`request.webhook_id`/`request.api_version` as the identity fields passed into `WebhookMetadata`, which is the only tenant/topic identifier delivered to the app's handler: [4](#0-3) [5](#0-4) 

This exactly matches the "field acted on but not covered by the HMAC" bug class from the report: the binding that should hold is `hmac == HMAC(secret, body ∥ shop ∥ topic)`, but the actual check enforced is only `hmac == HMAC(secret, body)`. Because Shopify's HMAC secret is the app's single `client_secret` (shared across every shop that installs the app, per `Context.api_secret_key`/`old_api_secret_key` used identically for every tenant in `HmacValidator.validate`), any tenant that receives a legitimately signed webhook for itself possesses a valid `(body, hmac)` pair that remains valid when re-sent to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header claiming to be a different shop.

### Impact Explanation
This breaks the tenant-identity binding the gem is supposed to guarantee to the host application: `WebhookMetadata#shop` is the *only* per-tenant identifier the library exposes to `WebhookHandler#handle`, and host apps universally use it to select the tenant's DB row/settings/API session and persist or act on the delivered `body`. Because `shop` is unauthenticated, an attacker who controls (or has installed the app on) any single shop can forge webhook deliveries that are attributed by this library to an arbitrary victim shop domain, letting them inject attacker-controlled data (order/customer/product payloads, etc.) into another tenant's records — a cross-tenant data-integrity/confusion vulnerability that Critical/High severity classes described in scope (cross-tenant access) directly cover.

### Likelihood Explanation
Likelihood is high for any consumer relying on this gem's webhook pipeline as its trust boundary: obtaining a valid `(body, hmac)` pair requires nothing more than installing the app on any shop (or triggering any webhook-eligible event on one's own shop) and capturing the delivered request — no access token, `client_secret`, or privileged access is needed. The attacker then only needs to replay the HTTP POST to the app's public webhook endpoint with a modified `shop` (and/or `topic`/`webhook_id`) header.

### Recommendation
Bind the tenant/topic identity to the signed payload instead of trusting headers outright:
- Include `shop`, `topic`, and `webhook_id` in the HMAC-signed material (or verify them against Shopify's known-shop registry/session store for that specific webhook subscription) before constructing `WebhookMetadata`.
- At minimum, require host applications to cross-check `WebhookMetadata#shop` against an already-established, authenticated session/shop record for the specific `webhook_id` that was registered via `Registry.register`, rather than trusting the header value as an authenticated identity by itself, and document this requirement prominently since the current API surface (`WebhookMetadata`) implies these fields are trustworthy.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger any subscribed webhook topic (e.g. `orders/create`) to receive a legitimately Shopify-signed request:
   ```
   POST /webhook
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid HMAC of body using app's client_secret>
   X-Shopify-Shop-Domain: attacker.myshopify.com
   Body: {"id": 1, "note": "malicious payload"}
   ```
2. Replay the identical body and HMAC header to the same app endpoint, but replace only the domain header:
   ```
   POST /webhook
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <same valid HMAC — body unchanged>
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   Body: {"id": 1, "note": "malicious payload"}
   ```
3. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over the (unchanged) raw body and succeeds. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) dispatches to the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host app to attribute the attacker's forged payload to `victim-shop.myshopify.com`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
