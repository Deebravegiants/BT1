## Title
Webhook HMAC Does Not Cover `shop`/`topic`/`webhook-id` Headers, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The reported bug class is "a value that controls trade/settlement outcome is not bound by the authentication check that gates the action" (slippage not covered by the trade's authorization). The direct analog in this gem is `ShopifyAPI::Webhooks::Request`: the HMAC signature validated by `Utils::HmacValidator` only covers the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` — the values used to route and attribute the webhook to a tenant — are read straight from unauthenticated HTTP headers.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all pulled from HTTP headers that are never fed into the signable string: [2](#0-1) 

`Registry.process` validates only the HMAC and then dispatches using the unauthenticated `request.shop`/`request.topic`/`request.webhook_id`: [3](#0-2) 

`HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the received `hmac`; for webhooks this is `HMAC(secret, raw_body)` only: [4](#0-3) 

The broken identity binding, stated as an equality that the code fails to enforce:
`HMAC_secret(raw_body) == received_hmac` is verified, but `shop_header == shop_that_generated(raw_body, hmac)` is never checked.

Because a single app's `client_secret` is shared across every shop that installs it, any merchant who has the app installed (an unprivileged holder of a legitimate, but low-privilege, installation) legitimately receives real `(raw_body, hmac)` pairs from Shopify for their own shop. Nothing in this library prevents that same attacker from replaying that valid `(raw_body, hmac)` pair to the target app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) header with a victim shop's domain. `HmacValidator.validate` still succeeds because it never inspected those headers, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop.

### Impact Explanation
This is a cross-tenant boundary break: an attacker who legitimately controls one tenant (their own shop with the app installed) can make the app process attacker-chosen webhook content as if it came from a different, victim tenant, because the header that determines tenant attribution is not bound to the payload's HMAC. Depending on how the host application keys its data store off `WebhookMetadata#shop`, this can lead to data being written into, or actions being taken against, the wrong merchant's tenant — matching the "cross-tenant access" critical-impact category.

### Likelihood Explanation
Reachable by any party who can (a) install the app on any shop (even a shop they control) to legitimately observe a real `(body, hmac)` pair, and (b) send an HTTP request to the target app's public webhook endpoint. No access token, `api_secret_key`, or privileged credential is required — only header manipulation, which is trivial for any unprivileged client making raw HTTP requests to the app's webhook route.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable content used by `HmacValidator`, or otherwise cryptographically bind them to the payload (e.g., verify `shop` against the session/tenant the app expects for that webhook subscription id, and reject webhooks whose header-derived `shop` was not the one that registered the corresponding `webhook_id`). At minimum, document that host applications must independently verify `request.shop` against the app's own installation registry before trusting it, since the gem does not perform this binding.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook delivery, e.g. `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H` (a valid HMAC of `B` under the shared app `client_secret`).
2. Attacker crafts `B` in advance (they control their own shop's data, e.g. create an order with attacker-chosen field values) so `H = HMAC(client_secret, B)` is known-valid for that exact body.
3. Attacker sends a new HTTP request directly to the target app's webhook endpoint with the same body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `HMAC(client_secret, B) == H` — the substituted `shop` header is never part of the check: `lib/shopify_api/webhooks/registry.rb` line 190, `lib/shopify_api/webhooks/request.rb` lines 36-38.
5. The registered handler receives `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host app to process attacker-controlled data as belonging to the victim tenant.
