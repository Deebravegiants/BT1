### Title
Webhook Shop Identity Not Bound by HMAC, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and exposes an HMAC that is verified only against the raw request body, while the `shop` (and `topic`/`webhook_id`) values that the app's handler treats as the authenticated tenant identity are taken from unauthenticated HTTP headers. This is the same class of bug described in the external report: a value used to make a trust/accounting decision (there: Bank balance vs. `VaultNAV`; here: the `shop` field vs. the HMAC-signed body) is not bound to the value that was actually integrity-checked.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`, and `Utils::HmacValidator.validate` computes/verifies the HMAC solely over that string: [1](#0-0) [2](#0-1) 

However, `Registry.process` uses `request.shop` — read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic binding to the signature — as the tenant identity passed to the app's handler: [3](#0-2) [4](#0-3) 

The identity binding that should hold is:
`HMAC-verified bytes == bytes used to attribute the webhook to a shop`

but in this implementation:
`HMAC-verified bytes (raw_body only) ≠ bytes used to attribute the webhook to a shop (shop-domain header, unauthenticated)`

The gem's own documentation instructs developers to trust `data.shop` from `WebhookMetadata` as "The shop domain of the webhook" once `Registry.process` has "verif[ied] the request did indeed come from Shopify": [5](#0-4) [6](#0-5) [7](#0-6) 

That documented guarantee is broken: `process` only guarantees the body's integrity, not the shop attribution, yet the API surface (`WebhookMetadata#shop`) presents it as trusted, verified data.

### Impact Explanation
Because the HMAC is a keyed function of the body alone, any party who legitimately receives one correctly-signed webhook for a shop they control (e.g., after installing the app on their own store — an "unprivileged" tenant relative to other merchants) can replay the exact same body+signature to the victim app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value. The signature still validates (since it never covered that header), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload belongs to a different shop of the attacker's choosing. Any host application that follows this gem's documented contract and uses `data.shop` to route/attribute webhook data (e.g., writing order/customer data, invalidating caches, or triggering shop-scoped side effects) can be made to attribute attacker-controlled body content to an arbitrary victim shop — a cross-tenant data-integrity/confusion vulnerability reachable without an access token, `client_secret`, or `api_secret_key`.

### Likelihood Explanation
Requires only that the attacker be able to receive at least one signed webhook from Shopify for a shop under their own control (any merchant/developer can install a public app or point their own store's webhook to an endpoint they observe) and replay the raw body with a modified shop header to the target app's public webhook endpoint. No secret, credential, or privileged access is needed — only network access and one legitimately-received webhook body.

### Recommendation
Bind the shop identity into the value that is HMAC-verified, or otherwise cryptographically tie the `shop-domain` header to the signed body:
- Include the shop domain (and ideally topic/webhook-id) in the signable string used by `to_signable_string`, matching it against a canonical value derived independently (e.g., looked up via the registered webhook `webhook_id` against Shopify), or
- After HMAC validation succeeds, cross-check `request.shop` against an out-of-band source of truth (e.g., confirm the shop is one the app has an active session/installation for) before handing it to the handler as trusted, and update the documentation to clarify that `shop` is not itself covered by the HMAC and must not be treated as authenticated on its own.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a shop they control) and triggers a webhook (e.g. `orders/create`) for that shop, capturing the raw POST body and the `x-shopify-hmac-sha256` header sent by Shopify.
2. Attacker resends that exact same raw body and HMAC header to the app's public webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (the raw body only) — this matches the original signature, so validation passes: [8](#0-7) 
4. `process` then builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the attacker-supplied `shop-domain` header and invokes the app's handler, which per this gem's own documentation is entitled to treat `data.shop` as "the shop domain of the webhook": [9](#0-8) 
5. The host application processes attacker-controlled webhook content under the identity of `victim-shop.myshopify.com`, despite the signature never having covered that claim.
