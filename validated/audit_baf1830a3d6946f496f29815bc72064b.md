### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC-signable content solely from the raw request body (`to_signable_string` returns `@raw_body`), while `shop`, `topic`, `webhook_id`, and `api_version` are parsed directly from HTTP headers that are never included in the signed bytes. `Registry.process` validates the HMAC and then forwards the header-derived `shop` value to the host application's webhook handler as if it were an authenticated tenant identifier, without binding it to the signature.

### Finding Description
The security-relevant invariant that should hold is: `shop conveyed to the handler == shop the HMAC signature actually vouches for`. Because `HmacValidator.validate` only verifies `verifiable_query.to_signable_string` (the raw body) against `Context.api_secret_key` [5](#0-4) , and `Request#to_signable_string` never incorporates the `shop-domain` (or `topic`/`webhook-id`) header [1](#0-0) , a valid HMAC only proves that Shopify (the true secret holder) produced this exact body at some point — it says nothing about which shop or topic the header claims to be. `Registry.process` nonetheless treats the header's `shop` as trustworthy and forwards it verbatim into `WebhookMetadata` for the app's handler to act on [3](#0-2) . This is directly analogous to the reported bug class: a field that is *acted on* (`shop`, used as the tenant-identity bound by the request) is not covered by the HMAC that is supposed to authenticate the request.

An attacker who can obtain any single genuine `(raw_body, hmac)` pair generated by Shopify with the app's real secret — for example by installing the same public app on their own store and capturing one of the webhooks Shopify sends to the app's endpoint — can replay that exact body and HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim merchant's domain. `HmacValidator.validate` will still pass because it only checks the (unmodified) body, and the app's handler will receive `WebhookMetadata#shop` equal to the victim's shop domain, causing it to process attacker-controlled payload content as if it originated from the victim tenant.

### Impact Explanation
This breaks the tenant/shop authentication boundary the gem is supposed to enforce for webhook delivery: the `shop` value handed to application code is not actually authenticated by the HMAC, enabling cross-tenant confusion where one merchant's webhook traffic can be attributed to another merchant. Any host application that uses `WebhookMetadata#shop` to select which tenant's session/data to mutate (a documented and expected usage pattern for this field) can be made to apply attacker-influenced webhook data to a different shop's context.

### Likelihood Explanation
High: any user who can install the target public app on any store (a normal, unprivileged action) can capture a legitimately-signed `(body, hmac)` pair and replay it against the app's shared webhook endpoint with a forged shop-domain header. No access token, `api_secret_key`, or privileged account is required.

### Recommendation
Bind the shop identity to the HMAC-verified payload rather than trusting the `X-Shopify-Shop-Domain` header independently. This can be done by requiring host applications (or the gem itself) to cross-check the header `shop` against a shop value embedded/expected in the verified body, or by rejecting webhook requests whose `shop-domain` header cannot otherwise be correlated to a known, previously-registered shop for that specific webhook subscription/topic before dispatching to the handler.

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) so Shopify sends `raw_body` + `X-Shopify-Hmac-Sha256: H` to the app's webhook endpoint, where `H = HMAC-SHA256(api_secret_key, raw_body)`.
2. Capture this exact `raw_body` and `H`.
3. Send a new HTTP request to the same webhook endpoint with the identical `raw_body`/`H`, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses `shop` as `victim.myshopify.com` [6](#0-5) ; `Registry.process` calls `HmacValidator.validate(request)`, which passes because it only checks `raw_body` against `H` [7](#0-6) ; the handler is invoked with `WebhookMetadata.new(... shop: "victim.myshopify.com", body: <attacker's body> ...)` [8](#0-7) .
