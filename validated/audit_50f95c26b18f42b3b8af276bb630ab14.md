## Analysis

The reported bug class (a signature that authorizes an action but omits a disambiguating field that downstream code branches on, letting the un-signed field be manipulated to defraud the counterparty) has a concrete analog in `EmporiumUpgradeable.sol`'s wallet-authorization flow.

### Title
Emporium wallet signature does not bind the shielded output recipient or settlement amounts, allowing a relay to steal swap proceeds - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable` lets a smart-contract-wallet owner pre-authorize a batch of operations (`EmporiumOperation[] ops`) via an EIP-712 signature that is meant to be submitted by an untrusted relay together with a Hinkal ZK proof. The EIP-712 struct only commits to `message`, the hash of `ops` (endpoint/invokeWallet/value/callData), `maxFee` and `deadline`. It never binds the `CircomData` fields that determine *where the resulting shielded value goes and how much of it is settled* — `circomData.stealthAddressStructure`, `circomData.erc20TokenAddresses`, and `circomData.amountChanges` (passed into `runAction` as `deltaAmountChanges`). Because the party assembling `circomData` and the accompanying ZK proof is the same party submitting `Hinkal.transact` (an unprivileged relay), that party can freely choose the shielded output's recipient key while reusing a legitimately-signed `EmporiumSignature`.

### Finding Description
`EMPORIUM_SIGNATURE_TYPEHASH` is: [1](#0-0) 

`verifyWallet` only checks this signature against `emporiumMessage`, the ops hash, `maxFee`, and `deadline`: [2](#0-1) 

Once the signed ops execute (Case 1, `invokeWallet=true`, driving `IHinkalWallet(stack.signerAddress).callHinkalWallet(...)`), the actual token proceeds are measured purely from the wallet's balance delta and handed to `handleOut`, which mints a new shielded UTXO addressed to `circomData.stealthAddressStructure` — a field that is *not* part of the signed struct: [3](#0-2) 

`circomData.stealthAddressStructure` is only constrained inside the ZK circuit to be internally consistent with whatever `spendingPublicKey`/`nullifyingPrivateKey` the prover supplies (`StealthAddressCalculator` in `circuits/MainEVMCircuit.circom`): [4](#0-3) 

There is no external check anywhere that ties this recipient key to the `EmporiumSignature` signer or to the wallet owner. `Hinkal.transact`'s post-action balance equation only verifies that the *amount* is fully accounted for (`balanceDif == amountChanges[i] + utxoAmount`); it never validates *who* the note belongs to: [5](#0-4) 

Since a fresh output UTXO with zero real spent inputs requires no ownership proof over existing shielded funds (the EdDSA check in `SignatureVerifier`/`MainEVMCircuit` is only meaningfully constrained when `inAmounts[i][j] != 0` via `calcEqual[i][j].enabled <== inAmounts[i][j]`), any relay can generate a self-consistent proof using its own arbitrary keypair and route the wallet's swap proceeds to itself, while satisfying every on-chain check (signature valid, balances valid, slippage valid).

This is the structural analog of H-29: a signature intended to authorize a specific, bounded operation omits a field that a downstream contract branches on to decide value ownership, so an operator who is not supposed to control that field (here, the relay/prover instead of the strategist/wallet owner) can substitute their own value and defraud the legitimate party.

### Impact Explanation
Critical — this allows direct theft of shielded user funds: the actual value moved out of a user's smart wallet (via operations the user did authorize) can be permanently redirected to an attacker-controlled shielded balance, an asset movement never authorized by the wallet owner's signature.

### Likelihood Explanation
Emporium's whole design assumes signed meta-transactions get carried by third-party relays (`stack.signerAddress`, `relay` fields), so an adversarial or compromised relay is squarely within the threat model. No admin/owner/relay-privilege is required beyond acting as the ordinary, permissionless caller of `Hinkal.transact`, which any EOA can be.

### Recommendation
Extend `EMPORIUM_SIGNATURE_TYPEHASH` (and its hashing in `verifyWallet`) to bind the fields that determine settlement: `circomData.stealthAddressStructure` (or a commitment to it), `circomData.erc20TokenAddresses`, and the declared `amountChanges`/`deltaAmountChanges`. Recompute and check this extended hash in `verifyWallet` before executing any `invokeWallet` operations, so a relay cannot resubmit a valid signature with a different value-recipient or settlement amount.

### Proof of Concept
1. Wallet owner signs an `EmporiumSignature` authorizing `ops = [approve(router, amountIn), swap(amountIn, minOut)]` intending the resulting `amountOut` to be deposited into their own shielded balance, and hands the signature + ops to a relay to submit.
2. The relay calls `Hinkal.transact` with the exact signed `ops`/`maxFee`/`deadline` (so `verifyWallet` passes), but crafts its own `circomData.stealthAddressStructure` (and matching ZK proof, self-signed with an arbitrary key since no real inputs are spent) pointing at the relay's own shielded key.
3. `EmporiumUpgradeable.runAction` executes the wallet's approved swap exactly as signed, measures the resulting `balanceChange`, and calls `handleOut`, which transfers the proceeds to the `Hinkal` contract and mints a UTXO under the relay's `stealthAddressStructure`.
4. `Hinkal.transact`'s balance-equation checks pass (amounts reconcile), the proof verifies, and the new commitment is inserted into the tree — the wallet owner's swap proceeds are now shielded value controlled by the relay, not the wallet owner.
