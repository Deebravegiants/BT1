### Title
Webhook shop identity spoofing via unauthenticated `shop-domain` header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value used to route/attribute an incoming webhook entirely from an HTTP header, while the HMAC signature that authenticates the request only covers the raw request body. Because the app's webhook HMAC secret (`api_secret_key`) is shared across every shop that installs the app, a valid HMAC only proves "some install of this app produced/received this exact body from Shopify" — it does **not** bind the payload to the specific shop named in the `shop-domain` header. This breaks the identity binding: `shop authenticated by HMAC` ≠ `shop used as the tenant key by the handler`.

### Finding Description
`ShopifyAPI::Webhooks::Request#shop` reads the tenant identifier straight from the header, with no coverage by the signature check: [1](#0-0) 

`to_signable_string`, which is what `HmacValidator` actually verifies, returns only `@raw_body`: [2](#0-1) 

`HmacValidator.validate` computes the HMAC over `to_signable_string` (the raw body) using the app's single, per-app `api_secret_key`/`old_api_secret_key` — the same secret is valid for every shop that has this app installed: [3](#0-2) 

`Webhooks::Registry.process` trusts `request.shop` unconditionally once the (body-only) HMAC passes, and hands it to the app's handler as the authoritative tenant identifier for the payload: [4](#0-3) 

Because the `shop-domain` header is never part of the signed bytes, and the signing secret is identical across all shops of the same app, any party that can obtain one genuine `(raw_body, hmac)` pair from Shopify for this app — e.g. by being a merchant who installed the app and can observe their own store's webhook traffic — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (or `shopify-shop-domain`) header value. `HmacValidator.validate` will still return `true` because it only re-computes the HMAC over the untouched raw body, and `Registry.process` will dispatch the handler with `shop` set to the attacker-chosen value instead of the shop that actually produced the payload.

### Impact Explanation
This is a cross-tenant identity-binding break: the equality the gem is supposed to enforce — `shop that produced the signed payload == shop value the handler will treat as the tenant key` — does not hold, because only the body is signed and the shop identifier travels unauthenticated in a header. Host applications typically use `WebhookMetadata#shop` to look up/update per-tenant records (e.g., "which merchant does this order/customer belong to"), so an attacker-controlled shop value lets one tenant's webhook data be attributed to (and potentially written into) another tenant's records — a cross-tenant access/data-integrity violation stemming directly from this gem's request-verification logic.

### Likelihood Explanation
Exploitation requires the attacker to be a legitimate merchant/installer of the same app (so they can capture one genuine `(body, hmac)` pair from their own store's webhook deliveries) and the ability to POST to the app's public webhook endpoint with a modified header — both are realistic for any external, unprivileged user of a multi-tenant Shopify app, and no `api_secret_key` or access-token theft is required, since the secret is only used to *validate* signatures, never revealed to the attacker.

### Recommendation
Include the shop identity in the material that is cryptographically bound to the request, or otherwise cross-check `request.shop` against an independently trusted source (e.g., verify the shop is one that is actually registered/subscribed to receive this specific webhook topic/id, and reject if the `(shop, webhook_id)` pair does not match Shopify's registration) before dispatching to the handler in `Registry.process`. At minimum, document prominently that `WebhookMetadata#shop` is not authenticated by the HMAC and must not be trusted as a tenant key without additional verification.

### Proof of Concept
1. App is installed on `shop-a.myshopify.com` and `shop-b.myshopify.com` (same `api_secret_key` for both, per `HmacValidator.validate`, `lib/shopify_api/utils/hmac_validator.rb:12-22`).
2. Attacker controls `shop-b.myshopify.com` and receives a legitimate Shopify webhook: raw body `B` with header `x-shopify-hmac-sha256: H` (valid since `H = HMAC(api_secret_key, B)`) and `x-shopify-shop-domain: shop-b.myshopify.com`.
3. Attacker resends the exact same body `B` and HMAC header `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: shop-a.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this into a request whose `to_signable_string` is still just `B` (`lib/shopify_api/webhooks/request.rb:35-38`); `HmacValidator.validate` recomputes `HMAC(api_secret_key, B)` and it matches `H`, returning `true` (`lib/shopify_api/utils/hmac_validator.rb:12-22`).
5. `Registry.process` calls the registered handler with `shop: "shop-a.myshopify.com"` even though the payload actually originated from `shop-b`'s data (`lib/shopify_api/webhooks/registry.rb:188-200`), causing the host app to process/store shop-b's webhook content under shop-a's tenant identity.
