## Analysis

I traced the exact equality this question is asking about: **tokens leaving `ExternalActionSwap` in a tx must equal `-deltaAmountChanges` Hinkal sent it that tx.**

The code path: `Hinkal.transact` → `Hinkal._externalTransact` transfers exactly `uint256(-deltaAmountChanges[0])` of the input token to the action [1](#0-0) , then calls `runAction` → `ExternalActionSwap.swap`, which computes `inputAmount = uint256(-deltaAmounts[0])` [2](#0-1)  and passes it to `callRouter`.

The critical finding is in `LifiExternalAction.callRouter`: the `inputAmount` parameter is **never used** to constrain the router call for ERC20 inputs — the function only calls `approveUnlimited(inputToken, router)` and then blindly executes `router.call(externalActionMetadata)`, an attacker-fully-controlled calldata blob [3](#0-2) . Because `approveUnlimited` grants the router an allowance of `type(uint256).max` [4](#0-3) , the router can pull **any balance of `inputToken` the action contract currently holds**, not just the `inputAmount` Hinkal just funded it with in this tx. The only measurement of "swap output" is a balance-before/after snapshot around the router call [5](#0-4) , so any pre-existing/stranded `inputToken` balance sitting in the action gets swept into `swappedAmount` and ultimately into `amountToSendToHinkal`, which becomes the attacker's own output UTXO via `circomData.stealthAddressStructure` [6](#0-5) .

Critically, `Hinkal.transact`'s balance-diff invariant check does **not** catch this, because it only checks Hinkal's own balance change against `amountChanges[i] + utxoAmount`, and `utxoAmount` is derived from the very same self-reported UTXO amount that already includes the swept residual [7](#0-6) . The check is self-consistent from Hinkal's perspective, but it never validates that the amount consumed by the router equals `-deltaAmountChanges[0]` on the action side — that invariant exists nowhere in the code.

This is a real, exploitable gap: since the action contract's address is a public, unrestricted destination (anyone can `transfer` tokens to it, or tokens can be stranded there from dust/partial-fill LI.FI swaps from other users' prior transactions), an attacker can seed or wait for residual balance and then craft `externalActionMetadata` that instructs the router to pull the full balance rather than just their legitimately funded `inputAmount`, capturing the excess as their own shielded output. This is squarely in-scope (this repo's `ExternalActionSwap`/`LifiExternalAction.sol`, not a router or oracle defect) and matches the Critical impact category: direct theft of shielded/in-flight funds (other users' stranded dust) via an unconstrained input-side balance in an unprivileged transaction.

### Title
Unbounded router pull via `approveUnlimited` lets attacker sweep stranded/residual input-token balance from `ExternalActionSwap` into their own output UTXO - (File: contracts/external-actions/swaps/LifiExternalAction.sol)

### Summary
`LifiExternalAction.callRouter` grants the LI.FI router an unlimited (`type(uint256).max`) allowance via `approveUnlimited` and then executes fully attacker-controlled `externalActionMetadata` without ever constraining the amount pulled to the `inputAmount` Hinkal actually sent to the action in that transaction. Any `inputToken` balance already resident in the action contract (from dust, partial fills, direct transfers, or other users' stranded funds) can therefore be pulled by the router and swapped, with the resulting output credited entirely to the calling attacker's own UTXO.

### Finding Description
The invariant that should hold is: *tokens consumed from `ExternalActionSwap` for the input leg of a swap == `uint256(-deltaAmountChanges[0])` that `Hinkal._externalTransact` just transferred to the action* [8](#0-7) .

In `ExternalActionSwap.swap`, `inputAmount` is computed from `deltaAmounts[0]` [2](#0-1)  and passed into `callRouter`. However `LifiExternalAction.callRouter` never uses `inputAmount` to bound or verify the ERC20 branch — it only checks the router call succeeded, then measures `swappedAmount` purely from the **output** token's balance delta [9](#0-8) . Because `approveUnlimited` sets the router's allowance to `type(uint256).max` [4](#0-3) , and `externalActionMetadata` is fully attacker-supplied calldata forwarded verbatim to the router [10](#0-9) , the attacker can encode a swap instruction that transfers **more** than `inputAmount` of `inputToken` from the action to the router, as long as the action's actual token balance covers it. Any extra amount comes from tokens already parked in the action (stranded dust from a previous imperfect swap, or simply sent there directly by anyone, since the contract has no access control on incoming transfers).

The resulting larger `swappedAmount` flows straight through into `amountToSendToHinkal` and the single output `UTXO` created with the attacker's own `stealthAddressStructure` [11](#0-10) . `Hinkal.transact`'s balance-diff/UTXO equality check does not catch this because it derives `utxoAmount` from the same self-reported UTXO the action just created, so the check is tautologically satisfied regardless of where the extra input tokens came from [12](#0-11) . No code path anywhere validates `balanceOf(inputToken, action)` before vs. after the router call against `inputAmount`.

### Impact Explanation
An attacker gains any residual/stranded `inputToken` balance sitting in the `ExternalActionSwap`/`LifiExternalAction` contract, swapped and converted into their own shielded output UTXO, at the cost of only their own legitimate (potentially minimal) swap. This is theft of value that does not belong to the attacker — whether it originated from another user's incomplete/partial-fill swap dust or was otherwise parked in the action — and is repeatable every time residual balance accumulates or is seeded. This matches the Critical category: direct theft of shielded or in-flight user funds.

### Likelihood Explanation
Preconditions: some non-zero balance of `inputToken` must exist in the `LifiExternalAction` contract beyond what Hinkal transferred for the current tx (achievable passively via dust from partial-fill swaps over time, or actively — the attacker can simply `IERC20(token).transfer(actionAddress, X)` themselves before calling `Hinkal.transact`, since the action contract has no restriction on who can send it tokens). The attacker needs to craft `externalActionMetadata` (valid LI.FI router calldata) that pulls the full balance rather than just `inputAmount` — this is fully within attacker control per the threat model. Attacker cost is just gas plus (optionally) the seed amount, which they immediately recover plus any pre-existing residual. This is practical and repeatable.

### Recommendation
In `LifiExternalAction.callRouter`, snapshot `IERC20(inputToken).balanceOf(address(this))` before and after the router call and require the consumed amount to equal exactly `inputAmount` (revert otherwise), instead of trusting the router calldata unconditionally. Additionally, avoid `approveUnlimited`; approve only `inputAmount` per call (reset to 0 afterward) so the router cannot pull more than intended even if the balance check is bypassed in a future refactor.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `LifiExternalAction` (with a mock router mimicking LI.FI behavior: pulls `amountOut of calldata` via `transferFrom` and sends back a configurable output amount), and a mock ERC20 `inputToken`/`outputToken`.
2. Seed residual: directly `inputToken.transfer(address(lifiAction), RESIDUAL_AMOUNT)` from an unrelated address (simulating stranded dust), with no corresponding Hinkal accounting.
3. Attacker performs a legitimate small deposit/UTXO for `LEGIT_AMOUNT` of `inputToken` and generates a valid proof for a swap transaction where `deltaAmountChanges[0] = -LEGIT_AMOUNT`.
4. Craft `externalActionMetadata` for the mock router to pull `LEGIT_AMOUNT + RESIDUAL_AMOUNT` (using the unlimited allowance) and return `outputToken` proportionally.
5. Call `Hinkal.transact` with this data.
6. Assert: `outputToken` UTXO amount credited to attacker's stealth address > amount corresponding to `LEGIT_AMOUNT` alone (i.e., attacker's output UTXO includes value derived from `RESIDUAL_AMOUNT`, which was never debited from Hinkal via `deltaAmountChanges` in this transaction) — proving the equality "tokens leaving the action == `-deltaAmountChanges` Hinkal sent it" is broken while the transaction still succeeds.

    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
