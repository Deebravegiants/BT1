### Title
Webhook shop-domain identity is not bound by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the unauthenticated `X-Shopify-Shop-Domain` header, while `Utils::HmacValidator.validate` only verifies `@raw_body` via `to_signable_string`. The header is never included in the signed bytes, so the value used by the host application to route/attribute a webhook to a merchant is unauthenticated relative to the HMAC that supposedly "proves" the webhook is genuine.

### Finding Description
`HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest` over `verifiable_query.to_signable_string` and compares it to the `hmac` field using `OpenSSL.secure_compare`. [3](#0-2) 

For `Webhooks::Request`, `hmac` is read from the `hmac-sha256` header and `to_signable_string` returns only `@raw_body`. [4](#0-3) [2](#0-1) 

However `shop`, `topic`, `api_version`, and `webhook_id` — the identity fields a host app uses to route the webhook to the correct merchant/tenant record and process handler — are all pulled straight from HTTP headers that are never fed into `to_signable_string`: [5](#0-4) 

This breaks the intended binding `hmac-verified-bytes == bytes-used-for-tenant-attribution`. The equality that should hold is:
`HMAC(secret, signed_bytes) == received_hmac` AND `shop used by app == shop covered by signed_bytes`.
In this gem, only the first half holds; the `shop` (and `topic`) values are asserted by the caller-controlled header and are never covered by the signature.

An unprivileged internet user who can reach the app's webhook endpoint (webhook endpoints are typically public HTTP endpoints, not behind session auth) can replay or forge a POST with a *legitimately-signed* raw body/HMAC pair (e.g., captured from any webhook they can trigger on their own store, since the HMAC only signs the body, not the shop) together with an arbitrary `X-Shopify-Shop-Domain` header naming a victim shop. `Webhooks::Request.new` will pass HMAC validation (the body/HMAC pair is genuinely valid) while `request.shop` returns the attacker-chosen victim domain.

### Impact Explanation
Host applications built on this gem are expected to trust `request.shop` (post-`HmacValidator.validate`) as the authenticated tenant identity for the webhook, since that's the entire purpose of running HMAC verification before processing. Because `shop` is not cryptographically bound to the signed bytes, an attacker who controls one legitimately-webhook-capable shop (any developer/partner sandbox store, trivially obtainable) can cause the gem to report an arbitrary victim `shop` value alongside a validated HMAC, enabling cross-tenant data confusion/injection into whichever shop-keyed store, queue, or side effect the host app performs based on `request.shop`. This matches the Critical bucket "cross-tenant access."

### Likelihood Explanation
High/practical: webhook endpoints are internet-reachable by design (Shopify calls them without any session), the attacker only needs a body/HMAC pair they legitimately received on their own low-privilege store, and simply substitutes the shop-domain header value before replaying to the target app's webhook URL. No access token, `client_secret`, or privileged account is required — only the gem's public verification contract, which host apps rely on directly.

### Recommendation
Include `shop`, `topic`, and other identity-bearing headers in the HMAC-signed material (or otherwise cryptographically bind them, e.g., via a signed digest that covers the full header set Shopify controls), or clearly document that `shop`/`topic` are unauthenticated hints and must be independently re-verified by the host app against a known/allow-listed store record before being trusted for tenant attribution.

### Proof of Concept
1. Register/own a low-privilege development store `attacker.myshopify.com` and subscribe it to any webhook topic.
2. Capture a legitimate webhook delivery: raw body `B`, and the `X-Shopify-Hmac-Sha256` header `H`, where `H == HMAC-SHA256(client_secret, B)`.
3. Send a new POST to the victim host application's webhook endpoint with the same body `B` and header `H` (both untouched, so HMAC validation succeeds), but replace `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
4. `HmacValidator.validate(request)` returns `true` because it only checks `B` against `H`; the constructed `Webhooks::Request#shop` returns `"victim-shop.myshopify.com"`.
5. The host application, trusting the gem's "hmac validated ⇒ shop is authentic" contract, processes/attributes the payload to `victim-shop.myshopify.com`, achieving cross-tenant confusion.

          received_signature = verifiable_query.hmac
