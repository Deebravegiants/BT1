### Title
Webhook HMAC only signs the request body, letting the `shop`/`topic` metadata be forged for cross-tenant webhook injection - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` but its `to_signable_string` returns only the raw HTTP body, never the `shop-domain`, `topic`, or `webhook-id` headers. `Utils::HmacValidator.validate` therefore authenticates only the body bytes, while `Webhooks::Registry.process` still trusts the unauthenticated `shop` header to build the `WebhookMetadata` handed to the app's handler. This breaks the intended identity binding: `hmac == HMAC(body)` is verified, but `shop_acted_on == shop_covered_by_hmac` is not.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

and `shop`/`topic`/`webhook_id` are read straight from request headers without any cryptographic binding to the signed content: [2](#0-1) 

`Utils::HmacValidator` computes the HMAC purely from `to_signable_string`, i.e. the body: [3](#0-2) 

`Webhooks::Registry.process` accepts the request once this body-only HMAC check passes, then forwards the caller-supplied `shop` value straight to the handler as trusted metadata: [4](#0-3) 

Because the app's shared `api_secret_key` is the same for every shop that installs the app, any body+HMAC pair that is valid for one shop is byte-for-byte valid for any other shop's webhook, since the shop identity is never part of the signed payload. An attacker who can obtain one genuine `(body, hmac)` pair for a shop under their own control (e.g., a free/dev store, or any shop where they can trigger a webhook-eligible event) can replay that exact body+hmac to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop. The signature check in `HmacValidator.validate_signature` still passes because it never inspects the header, and `Registry.process` dispatches to the handler with the forged `shop` value trusted as fact.

### Impact Explanation
This breaks the `shop` binding that host applications rely on to route webhook data. `Registry.process` is the gem's own trusted primitive for authenticating and dispatching webhooks, and it hands `request.shop` to the handler as an authenticated fact even though it never entered the HMAC computation. Any application that keys off `WebhookMetadata#shop` (as recommended in the gem's own webhook usage docs) to select which tenant's state to update can be made to apply data under the wrong shop, i.e., cross-tenant access/injection, without possession of the victim's own secrets — only the app's single shared `api_secret_key`-produced signature (from any shop) is needed.

### Likelihood Explanation
Exploitation requires obtaining one legitimately signed webhook body from any shop that has the target app installed. Because installing a Shopify app on a low-privilege/dev store and triggering an eligible event (e.g., a state change producing the desired topic/body) is something any internet user can do without elevated access to the victim, and because the HMAC/shop binding gap is unconditional in `Request`/`HmacValidator`/`Registry`, the path is directly reachable through the gem's own documented `Registry.process` entry point.

### Recommendation
Bind the header-derived identity fields into the value that is HMAC-verified, not just the body. Concretely, extend `Request#to_signable_string` (and `VerifiableQuery` consumers in `HmacValidator`) to incorporate `shop-domain` (and ideally `topic`/`webhook-id`) into the signed material, or have `Registry.process` cross-check `request.shop`/`request.webhook_id` against the shop the caller is expecting to receive on that specific endpoint/registration before invoking the handler, instead of trusting the header value as-is.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a store they fully control) and triggers a webhook-eligible event, capturing the genuine POST: headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <H>`, raw body `B` (`<H>` = `HMAC-SHA256(app_secret, B)`).
2. Attacker replays the exact same request to the app's webhook route, but changes only `x-shopify-shop-domain` (and if desired `x-shopify-topic`) to `victim-shop.myshopify.com`, leaving body `B` and hmac `<H>` untouched.
3. `ShopifyAPI::Webhooks::Request.new` parses this into a request whose `hmac` is `<H>` and `shop` is `victim-shop.myshopify.com` (`lib/shopify_api/webhooks/request.rb:12-23`).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(app_secret, B)` from `to_signable_string` (still just `B`) and finds it equals `<H>` — validation succeeds (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: ..., ...)` (`lib/shopify_api/webhooks/registry.rb:189-199`), even though no data from `victim-shop.myshopify.com` was ever actually involved — the app now processes attacker-controlled data under the victim's tenant identity.
