### Title
Cross-tenant session hijack via unauthenticated cookie fallback in `SessionUtils.current_session_id` — ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
When `Context.embedded?` is true and a request arrives without an `X-Shopify-Id-Token`/`Authorization` header, `SessionUtils.current_session_id` falls back to trusting the raw `shopify_app_session` cookie value as the session storage key with zero cryptographic verification. Because offline session IDs are deterministic (`offline_#{shop}`), an attacker who knows or guesses a victim shop's domain can forge this cookie in a direct backend request and have the host app load and use the victim's stored offline session (including its access token).

### Finding Description
The broken binding, stated as an equality that the code implicitly assumes but never enforces:
`session_id used by the app == an identity proven by a Shopify-issued, cryptographically-verified credential`

In the JWT path this holds: `session_id_from_shopify_id_token` (`lib/shopify_api/utils/session_utils.rb:45-56`) derives `shop` from `Auth::JwtPayload.new(id_token)`, whose claims (`aud`, `iss`, `exp`, signature) are verified before `shop` is trusted.

In the cookie fallback path this equality is **never checked at all**: [1](#0-0) 
`cookie_session_id` simply returns the cookie's value verbatim as the session ID with no HMAC, no signature, and no correlation to any server-issued token: [2](#0-1) 

Offline session IDs are deterministic and derived only from the shop domain: [3](#0-2) 

The cookie the gem originally sets for a legitimate non-embedded flow is exactly this session id, with no signing: [4](#0-3) 

Attack: after any victim shop has completed OAuth once (a normal, unavoidable precondition for any installed app), its offline session is stored under key `"offline_#{victim_shop}"`. The attacker — who has never authenticated, never held an id token or access token — sends a raw HTTP request directly to the app backend with:
- No `Authorization` / id-token header (forces the "no id token" branch).
- `Cookie: shopify_app_session=offline_victim-shop.myshopify.com`.

`current_session_id` returns `"offline_victim-shop.myshopify.com"` unchanged. The host app then calls its `SessionStorage.load_session(id)` with this attacker-supplied string, retrieves the victim's real offline session (including `access_token`), and processes the request as an authenticated request for the victim's shop.

None of the existing guards apply to this path:
- `HmacValidator.validate` and the OAuth `state` check only run during the OAuth callback (`Oauth.validate_auth_callback`), not on ongoing app requests.
- `JwtPayload`'s `aud`/`iss`/`exp` checks are entirely skipped because no id token is presented.
- `ShopValidator.sanitize!` is not invoked anywhere in this call path.
- `Context.embedded?`/`Context.setup?`/`Context.private?` only gate *which* branch runs; they do not validate the cookie's authenticity.

### Impact Explanation
An unprivileged attacker who knows (or enumerates) a victim shop's `myshopify.com` domain can obtain that shop's stored offline session and its access token by simply setting a predictable cookie value on a direct request — no XSS, no browser interaction, no secret required. This is cross-tenant access / access-token theft, repeatable against any shop that has installed the app, satisfying the Critical bar ("theft ... of a merchant access token ... or cross-tenant access").

### Likelihood Explanation
Preconditions: app is embedded (`Context.embedded?` true, the default and recommended mode for Shopify embedded apps), and the victim shop has previously completed installation (normal state for any real merchant). Attacker cost is trivial — one HTTP request with a forged `Cookie` header and no `Authorization` header; shop domains are frequently public/guessable (storefront URLs, App Store listings, marketing pages). The attack is fully repeatable against arbitrary victim shops with no rate limiting consideration needed to demonstrate the primitive.

### Recommendation
Do not treat an unauthenticated `Cookie` value as an authoritative session identifier. At minimum:
- Sign/HMAC the session cookie value (e.g., using `Context.api_secret_key`) when it is set in `Oauth.validate_auth_callback`, and verify that signature in `SessionUtils.cookie_session_id` before returning it.
- Alternatively, bind the cookie to a per-browser random session token that is opaque and unpredictable, rather than the raw `session.id`, and never fall back to trusting cookies for embedded apps without additional verification of shop identity (e.g., re-validating against a JWT or signed state).

### Proof of Concept
```ruby
# test/utils/session_utils_test.rb (new test)
def test_cookie_fallback_allows_cross_tenant_session_hijack_when_embedded
  ShopifyAPI::Context.setup(
    api_key: "key", api_secret_key: "secret", host_name: "host",
    scope: "scope", is_embedded: true, api_version: "unstable",
    is_private: false,
  )

  victim_shop = "victim-shop.myshopify.com"
  forged_session_id = "offline_#{victim_shop}" # attacker guesses this format

  # Simulate that the victim already has a stored offline session
  # under this exact deterministic id (established by a real install).
  ShopifyAPI::Utils::SessionUtils.expects(:cookie_session_id)
    .with({ ShopifyAPI::Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME => forged_session_id })
    .returns(forged_session_id)

  # Attacker sends no id token (Authorization header absent) but supplies
  # a forged Cookie header with a guessed victim session id.
  result = ShopifyAPI::Utils::SessionUtils.current_session_id(
    nil, # shopify_id_token
    { ShopifyAPI::Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME => forged_session_id },
    false,
  )

  # Assert both sides of the binding: the returned "authenticated" id
  # equals the victim's real session id, despite zero cryptographic
  # proof of identity being presented by the attacker.
  assert_equal forged_session_id, result
end
```
This demonstrates that `current_session_id` returns an attacker-chosen, unverified string identical to a real victim session key whenever the embedded/no-id-token branch is hit, with no signature check anywhere in `cookie_session_id`.
