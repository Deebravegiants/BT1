### Title
Webhook shop-domain (and topic/webhook_id/api_version) header spoofing bypasses HMAC binding, enabling cross-tenant webhook impersonation - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body; the `shop-domain`, `topic`, `webhook_id`, and `api_version` headers are parsed but never included in the value that the HMAC is computed over. Because the app's `client_secret`/`api_secret_key` is shared across every shop that installs the app, any unprivileged merchant who installs the app on their own store can capture a validly-signed webhook body from their own shop and replay it with a forged `X-Shopify-Shop-Domain` header pointing at a different (victim) shop. `HmacValidator.validate` accepts the request because it only checks the body/signature pair, and `Registry.process` then passes the attacker-controlled `shop` value straight into `WebhookMetadata`, which host applications use as the tenant identifier for looking up sessions, access tokens, or writing per-shop data.

### Finding Description
The signature contract is defined by `VerifiableQuery`, which requires only `hmac` and `to_signable_string`, per [4](#0-3) . For webhooks, `to_signable_string` is implemented to return just `@raw_body`, per [1](#0-0) , while `shop`, `topic`, `webhook_id` and `api_version` are simple header lookups with no cryptographic binding to the signature, per [2](#0-1) .

`HmacValidator.validate` recomputes the HMAC solely over `to_signable_string` and compares it to the `hmac` header value, per [5](#0-4) . It never verifies that the `shop` (or `topic`/`webhook_id`) the caller claims matches anything cryptographically tied to that shop. Since a single `api_secret_key` is used for HMAC computation across *all* shops that install the app (there is no per-shop signing key in this gem), a signature that is valid for shop A's body is equally "valid" when replayed with a header claiming to be shop B — the signature check only proves "the app's secret produced this signature for this body," not "this body came from shop X."

`Registry.process` treats HMAC success as full authentication and forwards the untrusted `shop` header value directly into the `WebhookMetadata` struct delivered to the host app's handler: [3](#0-2) . Documented usage patterns show host apps trusting `data.shop` for identification and further asynchronous processing (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), which is exactly the kind of per-tenant routing/state update that this spoofed field can corrupt.

The equality this breaks is:
`shop authenticated by HMAC` (there is none — the HMAC covers body bytes only) `≠` `shop attributed to the event` (taken verbatim from an unauthenticated header and handed to the host application as ground truth).

### Impact Explanation
This is a cross-tenant identity-binding break: an attacker who legitimately controls one Shopify store (trivial to obtain — anyone can create a Shopify dev/trial store and install a test app) can produce arbitrarily many validly-HMAC'd webhook bodies for their own shop, then relabel each one with any other shop domain string when delivering it to the target app's webhook endpoint. Any host application that uses `data.shop` from `WebhookMetadata` to select the tenant record to update, revoke, act on billing, or store data (as the gem's own documentation instructs developers to do) will attribute the attacker's payload to the impersonated shop, corrupting cross-tenant state or triggering shop-scoped side effects without ever needing that shop's access token or credentials.

### Likelihood Explanation
Likelihood is high for any app that lets an unprivileged user self-serve install (which is the norm for Shopify apps): the attacker only needs to install the app once on a store they control to get an arbitrarily reusable, validly-signed webhook body/HMAC pair, then can freely swap the `shop-domain` (and `topic`/`webhook_id`) headers when POSTing to the app's public webhook endpoint. No secrets, tokens, or privileged access to the target tenant are required.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the signed material, or independently authenticate the header value against the signature-verified body, e.g., by including `shop-domain` in `to_signable_string` for webhook requests, or by requiring the host app to check that `request.shop` matches a shop that the app actually has an active, previously-verified installation/session for before trusting `WebhookMetadata#shop`. At minimum, document explicitly that `shop` on `WebhookMetadata` is not authenticated by the HMAC and must be cross-checked by the caller against known installed shops.

### Proof of Concept
```ruby
# 1. Attacker installs the target app on their own shop "attacker.myshopify.com"
#    and receives a legitimate webhook delivery for it, e.g. via a stubbed capture harness:

raw_body = '{"id":1}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

legit_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "attacker.myshopify.com",
}

# 2. Attacker replays the SAME body+hmac but swaps the shop-domain header
#    to a victim shop's domain — the signature (computed over body only) still validates.
spoofed_headers = legit_headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: spoofed_headers)

# 3. HmacValidator.validate(request) returns true because it only checks raw_body against the hmac.
ShopifyAPI::Webhooks::Registry.process(request)
# => The host app's handler receives WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
#    even though the payload actually originated from the attacker's own shop.
```
