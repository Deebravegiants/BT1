### Title
Webhook `shop-domain` and `topic` headers are trusted for tenant/handler dispatch without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `api_version`, and `webhook_id` purely from unauthenticated HTTP headers, while `Utils::HmacValidator` (invoked from `Registry.process`) only verifies the HMAC over the raw request body. This breaks the identity binding: **shop authenticated by HMAC ≠ shop acted upon (`request.shop`) passed to the host application's handler**.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Yet `shop`, `topic`, `api_version`, and `webhook_id` are read straight from headers that are never included in the signed data: [2](#0-1) 

`Registry.process` validates the HMAC only against the body, then blindly trusts `request.topic` for handler dispatch and forwards `request.shop` (and `request.topic`) into the app-facing `WebhookMetadata` used for tenant attribution: [3](#0-2) 

`WebhookMetadata` treats `shop` and `topic` as trusted fields handed to the app's `WebhookHandler#handle`: [4](#0-3) 

Because the HMAC only binds `secret ↔ raw_body`, and never `secret ↔ (shop, topic, raw_body)`, any valid `(body, hmac)` pair — which an unprivileged internet user can legitimately obtain by installing the same public app on their own free/dev store and receiving a real webhook for it — can be replayed to the target app's webhook endpoint with the `shop-domain` header rewritten to a victim shop's domain (and/or the `topic` header rewritten to a different registered topic). `HmacValidator.validate` will report success because it only checks the body/hmac pair, and `Registry.process` will happily hand the forged `shop` value to the handler as if it belonged to the request's real, HMAC-verified tenant: [5](#0-4) 

This is exactly the "field acted on but not covered by the HMAC" identity-binding break called out in scope: the equality that should hold is `hmac_signed(shop, topic, body) == (shop, topic, body)_used_by_handler`, but the actual gem behavior is `hmac_signed(body) == body_used_by_handler` while `shop`/`topic` are taken from unauthenticated bytes.

### Impact Explanation
Any host application that uses `request.shop` (or `request.topic`) coming out of this gem to key data writes, tenant-scoped lookups, or access-control decisions (e.g., "store this order's data under `data.shop`", or "grant refund because `data.topic == 'refunds/create'`") can be made to attribute a legitimately-signed webhook body to an attacker-chosen shop or process it under an attacker-chosen topic. This is a cross-tenant data/identity confusion at the point where the app's business logic trusts this gem's parsed request, satisfying the "cross-tenant access" impact bucket — it requires no possession of the target's `client_secret`, access token, or any credential belonging to the app or the victim shop; it only requires the ability to send an HTTP request with attacker-controlled headers and a genuine `(body, hmac)` pair obtainable from the attacker's own store.

### Likelihood Explanation
High. Obtaining a valid `(body, hmac)` pair requires nothing more than installing the target's app (if public) on a store the attacker controls, or capturing any of their own store's webhook deliveries — no secret key or privileged access is needed. Rewriting `X-Shopify-Shop-Domain` / `X-Shopify-Topic` headers on replay is trivial for anyone who can reach the app's public webhook endpoint.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the HMAC-covered signable string (or otherwise cryptographically bind them, e.g. via a signed envelope), so `Utils::HmacValidator.validate` fails if any of these fields are altered relative to what Shopify actually signed. At minimum, `Registry.process` should not use `request.shop`/`request.topic` for any authorization- or tenant-scoping decision without an independent verification path (e.g., cross-checking against the registered webhook's expected topic/shop via the `webhook_id`).

### Proof of Concept
1. Attacker installs the target's (public) Shopify app on their own store `attacker-shop.myshopify.com` and triggers any webhook (e.g. `orders/create`), capturing the raw POST body `B` and the resulting `X-Shopify-Hmac-Sha256: H` header — a fully valid, Shopify-issued `(B, H)` pair.
2. Attacker resends the same `(B, H)` to the target app's public webhook endpoint, but sets:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   - `X-Shopify-Topic: <a topic registered by the app, possibly different from the original>`
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` builds successfully (all required headers present).
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and compares it to `H` — this passes because `B` and `H` are unmodified and genuinely matching: [6](#0-5) 
5. The registered handler is invoked with `WebhookMetadata.new(topic: "<attacker-chosen>", shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, causing the host application to process legitimate Shopify-signed content under the wrong shop and/or wrong topic.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
