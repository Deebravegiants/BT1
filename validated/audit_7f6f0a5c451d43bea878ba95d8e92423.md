Audit Report

## Title
LDAP Bind with Empty/Unvalidated Password Enables Unauthenticated ("Passwordless") LDAP Bind Login - ([File: core/sessions/ldapauth/ldap.go])

## Summary
`ldapAuthenticator.CreateSession` and `TestPassword` pass the client-supplied `SessionRequest.Password` (or raw `password` parameter) directly to `conn.Bind(searchBaseDN, password)` with no check that the password is non-empty. [1](#0-0) [2](#0-1)  The `SessionRequest` struct and its JSON binding path apply no minimum-length or non-empty validation on `Password`. [3](#0-2) 

## Finding Description
The public, unauthenticated `/sessions` route accepts an arbitrary `{email, password}` JSON payload and routes it to `CreateSession`. [4](#0-3)  Inside `CreateSession`, the DN is constructed from the (attacker-controlled but escaped) email, and `conn.Bind(searchBaseDN, sr.Password)` is invoked with no guard rejecting an empty `sr.Password`; if `err` is `nil`, `returnErr` stays `nil`, `FindUser` resolves the real role for that DN, and a fully privileged `ldap_sessions` row plus session cookie is created for that account. [5](#0-4)  The same unguarded pass-through exists in `TestPassword`, used by API-token flows. [6](#0-5)  No code in the file performs an empty/whitespace check on the password before calling `Bind`.

This is a genuine defense-in-depth gap: RFC 4513 §5.1.2 defines a simple bind with non-empty DN and empty password as an "unauthenticated bind," and it is well documented that many LDAP servers/directories can be configured to accept such binds as successful without validating a credential. The application performs no compensating check, so its security posture for this path is entirely dependent on the specific external LDAP directory's configuration (e.g., OpenLDAP's `disallow bind_anon` on by default in modern releases, Active Directory's default behavior rejecting simple binds with empty password since it is generally treated as an anonymous bind unless anonymous bind is explicitly enabled). The vulnerability requires the LDAP backend to be misconfigured or non-default in a specific way (accepting unauthenticated bind as authentication success) for exploitation to actually occur; the Chainlink codebase's own code does not by itself grant access — success or failure hinges entirely on the connected external LDAP server's behavior, which is out of this repository's control and constitutes a configuration/environment dependency rather than a self-contained application bug.

## Impact Explanation
If the connected LDAP server treats an empty-password simple bind as successful (non-default in most modern LDAP/AD deployments, but possible under specific configurations), this could grant an attacker a fully authenticated session for any account whose email/DN they can guess, including admin — a legitimate CWE-285/CWE-287 authentication-bypass class impact. However, this requires a specific external misconfiguration (LDAP server permitting unauthenticated binds to resolve as success) that is not controlled by, or a direct consequence of, the Chainlink codebase itself.

## Likelihood Explanation
Low, and not attributable to the application alone. Exploitation requires (1) the operator to have opted into and deployed the optional LDAP authentication feature, (2) the backing LDAP/AD server to be configured (or misconfigured) to treat simple binds with empty passwords as successful unauthenticated binds rather than rejecting them — which is not the default behavior for the common directory implementations (OpenLDAP disallows anonymous/unauthenticated bind success by default in recent versions; Active Directory rejects simple bind with empty password by default). The application code provides no compensating control, but the actual exploitability is gated entirely by third-party server configuration outside the scope of this codebase.

## Recommendation
Add an explicit guard in `ldapAuthenticator.CreateSession` and `TestPassword` to reject empty/whitespace-only passwords before calling `conn.Bind`, e.g., `if strings.TrimSpace(sr.Password) == "" { return "", errors.New("password is required") }`. This removes any reliance on external LDAP server semantics regarding RFC 4513 unauthenticated binds and closes this defense-in-depth gap regardless of directory configuration.

## Proof of Concept
1. Deploy a Chainlink node with LDAP authentication enabled, backed by an LDAP server explicitly configured to accept unauthenticated/anonymous-style simple binds as successful (a non-default configuration for most directories).
2. Send `POST /sessions` with `{"email":"victim@example.com","password":""}`.
3. Observe `conn.Bind(searchBaseDN, "")` at `core/sessions/ldapauth/ldap.go:408` returning `nil`, resulting in a valid session being issued for `victim@example.com` without a correct password — reproducible only when the backing LDAP server is configured to permit this bind behavior.
