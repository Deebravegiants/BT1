### Title
Webhook HMAC signature covers only the raw body, not the `shop-domain` header, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop` is read from an unauthenticated header. `Registry.process` validates the HMAC over the body only, then forwards the unauthenticated `shop` value straight to the app's webhook handler as the tenant identifier.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` with: [1](#0-0) 

```ruby
def hmac
  Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
end
...
def shop
  T.cast(shopify_header("shop-domain"), String)
end
...
def to_signable_string
  @raw_body
end
```

The `to_signable_string` used by `Utils::HmacValidator.validate` is `@raw_body` alone [2](#0-1) , which mirrors Shopify's real webhook signing scheme (the HMAC is computed by Shopify only over the request body). The `shop` accessor, however, is read from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, which is not part of the signed material at all [3](#0-2) .

`Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant for the handler call: [4](#0-3) 

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
```

The identity-binding broken here is: `HMAC(raw_body) valid` is treated as equivalent to `shop header == originating shop`, but the `shop` header is never covered by the signature. This is directly analogous to the report's bug class: code (here, tenant-authorization logic in `process`) relies on a value (`shop`) that is not actually bound by the security mechanism that is assumed to cover it (the HMAC), just as a proxy's logic contract wrongly assumes constructor state is present when only the initializer path is actually executed.

### Impact Explanation
Because `shop` is unauthenticated, an attacker who can obtain any single valid `(raw_body, hmac)` pair — e.g., by installing the target app on their own Shopify development store and capturing a legitimate webhook delivery — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary victim `shop-domain` header value. `Utils::HmacValidator.validate` will pass (it only checks the body against the secret), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload originated from the victim shop. Any app logic that uses `WebhookMetadata#shop` to select which merchant's data to read/write/redact (the entire purpose of exposing `shop` on the metadata, including for the mandatory `shop/redact`, `customers/redact`, `customers/data_request` topics) can be tricked into acting on the wrong tenant — a cross-tenant access/write vulnerability.

### Likelihood Explanation
Any developer/attacker can register the app on their own store, trigger any webhook topic, capture the raw body and `X-Shopify-Hmac-Sha256` value, and replay it to the app's public webhook endpoint with a forged `X-Shopify-Shop-Domain` header. No access token, `client_secret`, or privileged credential is required — only the gem's own public verification logic is used, which explicitly ignores the shop header when computing the signature.

### Recommendation
Bind `shop` (and ideally `topic`, `webhook_id`) into the signed material, or otherwise cryptographically tie the header values to the payload before trusting them. If Shopify's real HMAC scheme genuinely does not sign the shop header, the gem should document this loudly and require host apps to separately re-verify that the `shop` in the webhook belongs to a shop that currently has this app installed (i.e., cross-check `request.shop` against stored, previously-authenticated sessions) before acting on `WebhookMetadata`, rather than presenting `request.shop`/`WebhookMetadata#shop` as though it were already authenticated by `Utils::HmacValidator.validate`.

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker.myshopify.com`; trigger a webhook (e.g. `customers/data_request`) and capture the raw POST body `B` and header `X-Shopify-Hmac-Sha256: H` sent to the app's webhook endpoint.
2. Replay a POST to the same app endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` unchanged, but `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "shop-domain" => "victim.myshopify.com", "hmac-sha256" => H})` is constructed; `Utils::HmacValidator.validate(request)` succeeds because it only re-derives the HMAC from `B` [5](#0-4) .
4. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(..., shop: "victim.myshopify.com", ...))`, causing the app's handler to run business logic under the victim's tenant identity despite the payload/HMAC actually having originated from the attacker's shop.
