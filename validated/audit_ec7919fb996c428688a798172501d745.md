### Title
Token exchange sends `client_secret` to an unvalidated JWT `dest` host - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`TokenExchange.exchange_token` derives the destination shop purely from the session token's `dest` claim and uses it, unsanitized, as the host that receives the app's `client_id`/`client_secret` via `HttpClient`. Unlike the sibling method `migrate_to_expiring_token`, which calls `Utils::ShopValidator.sanitize!(shop)` before building the session, `exchange_token` never runs `dest_shop` through `ShopValidator`, breaking the intended binding "host that receives the client_secret == a domain in `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`".

### Finding Description
`JwtPayload#shop` simply strips `"https://"` from the raw `dest` claim with no format/domain check: [2](#0-1) 

`JwtPayload.new` only validates `aud == Context.api_key`; it does not check that `dest` is a `myshopify.com`/`myshopify.io`/`spin.dev`/`shop.dev` host, nor that `dest` is consistent with `iss`: [3](#0-2) 

`exchange_token` takes this unvalidated `dest_shop` and builds a `Session` with it directly, then issues the OAuth token-exchange POST (containing `client_id` and `client_secret`) to that host: [4](#0-3) 

`HttpClient#initialize` takes `session.shop` at face value to build `@base_uri`, with no `ShopValidator` call anywhere in this path: [1](#0-0) 

Contrast this with `migrate_to_expiring_token`, in the very same file, which does validate the shop before it is used to build the request: [5](#0-4) 

This is the exact bug class named in scope: "a JWT claim trusted without being bound" — here the `dest` claim is trusted as a request host without being bound to the `TRUSTED_SHOPIFY_DOMAINS` allow-list that every other shop-consuming entry point (`ShopValidator.sanitize!`, used in `migrate_to_expiring_token`, `RefreshToken`, `ClientCredentials`, and the Storefront GraphQL client) enforces.

### Impact Explanation
If the equality that should hold — "host receiving `client_secret` == validated Shopify domain" — is broken, the app's `client_secret` (a Critical-impact credential per the given scope: "theft or exfiltration of ... the app's `client_secret`") can be sent to a host controlled by whoever can influence the `dest` claim value that ends up decoded here. Because `JwtPayload` verifies the token's HMAC signature with `Context.api_secret_key` before trusting any claim, exploitation strictly requires a token that verifies under the app's own secret; this analysis cannot demonstrate a path for an unprivileged internet user to forge such a token without already possessing that secret or an equivalent trusted issuance channel, so I can't fully confirm end-to-end exploitability from an external, credential-less attacker position.

### Likelihood Explanation
Low/uncertain from a purely code-review perspective: the missing validation is real and demonstrably inconsistent with the sibling method in the same file, but turning it into an actual credential-exfiltration primitive depends on how `dest` values are produced/verified upstream (by Shopify's signing process), which is outside this gem and which I could not verify further within the given scope.

### Recommendation
Validate `dest_shop` with `Utils::ShopValidator.sanitize!` (as already done in `migrate_to_expiring_token`) before constructing the `Session`/`HttpClient` in `TokenExchange.exchange_token`, and/or add domain validation of the `dest` claim inside `JwtPayload` itself so no caller can bypass it.

### Proof of Concept
Not able to construct a concrete unprivileged PoC: exploitation requires a `session_token` whose `dest` claim decodes successfully under `Context.api_secret_key` (or `old_api_secret_key`) — i.e., a value already trusted as coming from Shopify — with a non-`myshopify` `dest`. I could not verify within this gem's scope whether such a token can be produced by an unprivileged actor.
