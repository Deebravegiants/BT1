### Title
Position NFT `transfer`/`transfer_from` performs no recipient-capability check — a position transferred to a contract that cannot produce auth is permanently frozen, locking all collateral and debt — ([File: contracts/position-nft/src/contract.rs])

### Summary
The external report describes an ERC-721 `safeTransferFrom` that skips the `onERC721Received` recipient check, so a token sent to a contract unaware of the standard is locked forever. The same bug class exists in XOXNO Lending's position NFT: `transfer` and `transfer_from` (inherited unchanged from the OpenZeppelin `NonFungibleToken` trait) update the `Owner(token_id)` record and never verify that `to` can actually exercise ownership. Because the token *is* the lending account — `token_id == account_id` and the controller resolves authority by reading `owner_of` live — sending the token to a contract address that cannot produce `require_auth` permanently freezes every asset and debt in that account.

### Finding Description
`PositionNft` implements `transfer(e, from, to, token_id)` and `transfer_from(e, spender, from, to, token_id)` purely as the stock OZ trait exports. The only authorization is on the sender side: `transfer` calls `from.require_auth()` and `transfer_from` requires `spender` to be the owner, an approved spender, or an operator. Nothing inspects `to`.

The controller keys all authority on live ownership: every owner-gated entrypoint (`supply`, `borrow`, `withdraw`, `repay`, `claim_revenue`, `update_account_threshold`, `add_delegate`, etc.) resolves the caller by reading `owner_of(account_id)` and requiring that address's auth, and `burn` is controller-only precisely because the holder may never sign (contract.rs lines 88–95). If `to` is a contract that has no code path which calls `transfer`/`transfer_from`/`approve` on the NFT or `require_auth`s itself before invoking the controller — e.g. a multisig wrapper, an exchange deposit contract, a SAC, or any contract that simply never calls these entrypoints — the position becomes a black hole:

- `withdraw`, `borrow`, `repay`, `supply` for that `account_id` all fail with `NOT_AUTHORIZED` because the stored owner never authorizes.
- `transfer`/`transfer_from`/`approve` on the NFT likewise require the current owner's auth, so the token cannot be rescued.
- The controller cannot intervene: there is no admin transfer or recovery function for the NFT; the only owner-bypassing verb is `burn`, which requires the account to be empty first — and emptying it requires owner auth. Circular lock.
- Interest keeps accruing on trapped debt; liquidation can still seize the collateral legs, but any residual/supply value the account holds stays unreachable forever.

The README itself documents that the only safety model is sender-side auth and enumerates no recipient check (contracts/position-nft/README.md lines 62–63, 141–166). No `data`/callback or receiver-introspection step exists anywhere in the transfer path.

### Impact Explanation
Permanent freezing of user funds. All collateral held by the transferred account is unrecoverable — potentially the user's entire supplied balance — and the position's debt becomes stranded bad-debt-adjacent state that can only be worked down via liquidation, not repaid normally. A single `transfer` call by the token owner to the wrong contract address irreversibly destroys the position's value. Unlike a plain collectible NFT, this token carries the whole margin account, so the freeze extends to real pooled assets.

### Likelihood Explanation
Medium-low but realistic. Users interacting through smart wallets, multisig contracts, custodial/exchange deposit contracts, or scripted runners are the natural population to set `to` to a contract address. The harness itself demonstrates contract-held positions are normal (the flash receiver and script runner legitimately hold NFTs), so the distinguishing factor is only whether the receiving contract happens to implement the owner verbs — a property the sender has no way to verify on-chain because the NFT never checks it. Any holder can trigger the loss with one unprivileged `transfer` call; no privileged role, no economic setup required.

### Recommendation
Add a recipient-capability check to the transfer path, mirroring the ERC-721 fix: when `to` is a contract address, invoke a receiver hook (e.g. a Soroban `on_position_received`-style interface or a declared capability) and abort the transfer if the recipient does not acknowledge. Short of a hook, document and enforce a policy — e.g. restrict `to` or expose a two-step transfer-claim — so a holder cannot silently commit the account to an address that can never authorize. At minimum the risk should be called out wherever `transfer`/`transfer_from` are surfaced to integrators.

### Proof of Concept
1. Alice supplies collateral via `controller::supply` (account id `N` minted to Alice by `position_nft::mint`).
2. Alice calls `position_nft::transfer(from=alice, to=C, token_id=N)` where `C` is a contract that never calls `transfer`/`transfer_from`/`approve` on the NFT and never `require_auth`s before controller calls — e.g. a generic custody contract.
3. `transfer` succeeds: only `alice.require_auth()` is checked; `C` is written into `Owner(N)`.
4. Any subsequent `controller::withdraw(caller=C, account_id=N, ...)` fails `NOT_AUTHORIZED` because `C` cannot produce the owner auth; `C` cannot return the token for the same reason.
5. Alice's collateral is permanently locked; the controller has no recovery path (`burn` needs an empty account, which needs owner auth).
