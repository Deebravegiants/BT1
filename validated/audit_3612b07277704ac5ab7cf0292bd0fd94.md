### Title
Webhook `shop-domain` Header Is Not Covered by the HMAC Signature, Enabling Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers. `Registry.process` validates the HMAC and then forwards `request.shop` straight into the `WebhookMetadata` passed to the app's handler, so the tenant identity (`shop`) is never bound to the cryptographic signature that authenticates the request.

### Finding Description
`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`, and for webhook requests that string is just `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are pulled straight from HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e., that *some* body was signed with the app's shared `api_secret_key`), then immediately trusts `request.shop` as the tenant identifier passed to the handler: [3](#0-2) 

The identity binding broken is: `shop_authenticated_by_hmac == shop_delivered_to_handler` is assumed but never enforced — the HMAC only proves `secret == HMAC_key(raw_body)`, it says nothing about which shop the body belongs to.

Because `api_secret_key` (the app's `client_secret`) is shared across *every* shop that installs the app, and this is a **public app** by definition, an unprivileged attacker can install the same app on a shop they control, receive a legitimately-signed webhook (valid `hmac-sha256` header for a given raw body), then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header with a victim shop's domain. `HmacValidator.validate` still passes because it never inspects headers, and the handler receives `WebhookMetadata` with `shop` set to the forged victim domain, plus whatever `topic`/`body` the attacker chooses (bounded by what topics they can generate signed bodies for from their own installed instance).

### Impact Explanation
This lets an attacker who has installed the app on their own shop forge webhook events that the host app will process as if they originated from a different, victim shop — a cross-tenant data-integrity/authentication issue. Depending on how the host app's handler uses `data.shop` (e.g., to look up records, fulfill orders, update local state), this can lead to cross-tenant data corruption or unauthorized actions being attributed to another merchant's account, which falls under "cross-tenant access."

### Likelihood Explanation
Exploitation requires only: (1) the ability to install the target app on an attacker-controlled shop (typical for any public Shopify app), and (2) network access to POST directly to the app's public webhook endpoint with attacker-chosen headers — both are available to an ordinary unprivileged internet user/merchant, with no need for the app's `client_secret`, an access token, or any privileged account.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the value that is verified, not just trusted from headers, e.g.:
- Incorporate `shop-domain` (and `topic`) into the signed payload check, or
- Cross-validate the `shop-domain` header against an out-of-band trusted source (e.g., confirm the shop has an active session/install record) before dispatching to the handler, rather than trusting the raw header value implicitly.

### Proof of Concept
1. Attacker installs the public app on `attacker-shop.myshopify.com`, triggering a real Shopify webhook delivery with a valid `x-shopify-hmac-sha256` for some raw body `B`.
2. Attacker captures `B` and its valid HMAC (e.g., via a proxy they run at the registered callback path).
3. Attacker sends a POST directly to the same app's public webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256`: unchanged, valid signature
   - Header `x-shopify-shop-domain`: `victim-shop.myshopify.com` (forged)
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` which passes because only `B` is signed.
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: B, ...)` and processes it as a legitimate event for the victim shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
