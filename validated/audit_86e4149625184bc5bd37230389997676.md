### Title
FXFiller prices exotic-token legs from a manipulable Uniswap V4 spot price with the overfill clamp disabled, allowing an attacker to drain filler inventory - (File: `sdk/packages/simplex/src/strategies/fx.ts`)

### Summary
`FXFiller.calculateProfitability` prices venue-priced legs (pairs with no static curves) off the live Uniswap V4 pool spot price (`sqrtPriceX96` from `slot0`) with no TWAP, and the per-leg overfill clamp that previously bounded the loss from a manipulated venue price has been explicitly disabled. The only remaining defense — the `priceGuard` reference-price band — is optional and unguarded by default. This mirrors the Panoptic `PanopticFactory.deployNewPool` finding: spot price consumed for a fund-moving computation with no manipulation resistance.

### Finding Description
Venue-priced pairs (curve-less pairs anchored on a USD stable) derive their fill rate from `getVenueUsdPrice` → `UniswapV4FundingPlanner.getExoticTokenPrice` → `computeDirectPoolPriceUsd`, which reads the pool's current tick/price via `sdkPool.token0Price`/`token1Price`, itself built directly from a live `getSlot0` read [1](#0-0) . This is the on-chain instantaneous spot price with no TWAP, exactly the class of price the Panoptic report warns about.

The only mitigation is `checkPriceGuard`, which compares the venue quote to a static `referencePrice` within `maxDeviationBps` — but it is optional: "The two fields must be set together; omit both to leave the chain unguarded" [2](#0-1) . In code, `checkPriceGuard` returns `true` (pass) whenever no guard map entry exists for the chain [3](#0-2) .

Critically, the per-leg overfill clamp that used to bound the damage from a bad/manipulated price has been deliberately disabled, and the code comment states this explicitly:

```
// Overfill detection is warn-only: the clamp is DISABLED, so the filler
// fills the full computed amount even when it exceeds
// (1 + maxOverfillBps) × user-requested — including venue-priced legs
// (e.g. Uniswap V4). NOTE: this removes the per-leg loss bound that
// previously protected against a bug / stale cache / manipulated venue
// price. Output is no longer capped; we only emit a warning.
``` [4](#0-3) 

The venue-pricing flow itself documents the same shape of weakness: `checkPriceGuard` is "the only defense on this path, and it checks deviation from a static reference, not execution cost" [5](#0-4) .

### Impact Explanation
An attacker who flashloan-manipulates the configured Uniswap V4 pool's spot price (e.g., pushes the exotic token's implied USD price far above its true value) and then submits/relays an intent order that the filler fills through `FXFiller` on the venue-priced pair will have that leg priced from `computeLegPolicyOutput` using the manipulated `rate` [6](#0-5) . Because the overfill clamp is disabled, the resulting `policyMaxOutput`/`targetOutput` is paid out unclamped [7](#0-6) [8](#0-7) , funded first from wallet balance and then from the Uniswap V4 LP position withdrawal (`planWithdrawalForToken`) [9](#0-8) . This can cause the filler to pay out far more of the exotic token (or funding-venue LP inventory) than the true market rate justifies — direct theft of solver/filler funds, unless the operator has manually configured a `priceGuard` band for that chain (an opt-in mitigation, not a default protection).

### Likelihood Explanation
Reachable by any unprivileged intent submitter/order relayer: an attacker only needs (1) enough capital/flashloan access to move the configured V4 pool's spot price, and (2) to submit an order matching a venue-priced pair on that chain. No governance or privileged role is required. Likelihood is reduced only for operators who have manually set `referencePrice`/`maxDeviationBps` for every venue-priced chain; per the docs this is optional and off by default, and even when configured it bounds only a static deviation, not a moving/legitimate reference, so a manipulator staying within `maxDeviationBps` of a stale reference still passes. Given the fee-tier/impact costs are also otherwise unaccounted for on this path (per the flow doc), the practical cost of manipulation for shallow pools/positions can be low.

### Recommendation
- Re-enable and enforce the overfill clamp for venue-priced legs (or a dedicated tighter clamp), rather than warn-only, so a single bad quote cannot pay out unbounded excess.
- Make the Uniswap V4 price guard mandatory (not optional) for any venue-priced pair, and prefer a TWAP/observation-based price over the raw `slot0` spot price for `computeDirectPoolPriceUsd`.
- Bound the size of any single leg fillable off venue pricing so the manipulation cost scales with the potential loss (an economic floor, not just a static deviation band).

### Proof of Concept
Conceptual attack path (concrete on-chain PoC would require deployment addresses and cannot be fully constructed from static analysis alone):
1. Operator runs `FXFiller` with a venue-priced pair (USDC/EXOTIC) funded via `[vault.uniswapV4]`, without configuring `priceGuard` for the target chain (or with a stale `referencePrice`).
2. Attacker flashloan-swaps against the configured Uniswap V4 pool to move `slot0.sqrtPriceX96` so EXOTIC's USD price appears inflated.
3. Attacker submits/relays an intent order requesting the filler swap the attacker's stablecoin input for an outsized amount of EXOTIC, matching the manipulated rate returned by `getExoticTokenPrice`/`computeDirectPoolPriceUsd` [10](#0-9) .
4. `calculateProfitability` computes `policyMaxOutput` from this manipulated rate; the overfill clamp is disabled so the amount is not capped, and `checkPriceGuard` passes (no guard configured / within stale band) [4](#0-3) .
5. Filler executes the fill, withdrawing from its wallet and/or Uniswap V4 LP position to pay the inflated `finalOutputAmount`, at the attacker's benefit.
6. Attacker reverses the flashloan manipulation, keeping the excess EXOTIC/stablecoin extracted from the filler.

	async getExoticTokenPrice(chain: string, exoticToken: string): Promise<Decimal | null> {
		const state = this.stateByChain.get(chain)
		if (!state || !state.isHydrated()) return null

		try {
			await state.refresh()
		} catch (err) {
			this.logger.error({ err, chain }, "Failed to refresh state for price query")
			return null
		}

		const tokenLower = exoticToken.toLowerCase()
		let bestPrice: Decimal | null = null
		let bestLiquidity = 0n

		for (const pos of state.allPositions()) {
			if (pos.currency0.toLowerCase() !== tokenLower && pos.currency1.toLowerCase() !== tokenLower) continue
			const sdkPool = state.getSdkPool(pos.tokenId)
			if (!sdkPool) continue

			const result = this.computeDirectPoolPriceUsd(pos, sdkPool, chain)
			if (result && result.exoticToken.toLowerCase() === tokenLower) {
				const poolLiquidity = state.getPoolLiquidity(pos.tokenId)
				if (poolLiquidity > bestLiquidity) {
					bestPrice = result.priceUsd
					bestLiquidity = poolLiquidity
				}
			}
		}

		if (bestPrice) {
			this.logger.debug({ chain, token: tokenLower, priceUsd: bestPrice.toString() }, "Exotic token price computed")
		}
		return bestPrice
	}

```text
## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.

	/**
	 * Validates a live venue quote against the static reference price for the chain.
	 * Returns true (pass) when no guard is configured, or no reference exists for the
	 * chain. Returns false when the quote (token1 per USD) deviates from the reference
	 * by more than `maxDeviationBps`, in which case the order must not be filled.
	 */
	private checkPriceGuard(orderId: string | undefined, chain: string, venueToken1PerUsd: Decimal): boolean {
		const guard = this.priceGuard?.get(chain)
		if (!guard || guard.reference.lte(0)) return true

		const deviationBps = venueToken1PerUsd.minus(guard.reference).abs().div(guard.reference).mul(10000)
		if (deviationBps.gt(guard.maxDeviationBps)) {
			this.logger.warn(
				{
					orderId,
					chain,
					venuePrice: venueToken1PerUsd.toString(),
					referencePrice: guard.reference.toString(),
					deviationBps: deviationBps.toFixed(2),
					maxDeviationBps: guard.maxDeviationBps,
				},
				"Rejecting order: Uniswap venue quote outside price-guard band",
			)
			return false
		}
		return true
	}

`computeDirectPoolPriceUsd` returns the **raw pool mid** derived from `sqrtPriceX96`. The pool's
fee tier is read and stored on the hydrated position (`pos.fee`) but never applied to the price,
and there is no size or impact term — `computeLegPolicyOutput` extends the mid linearly across the
whole priced quantity. `checkPriceGuard` is the only defense on this path, and it checks deviation
from a static reference, not execution cost. A venue-priced pair that has to swap through its own
pool to source inventory pays a fee tier it never quoted against.
