### Title
Unauthorized auto-approve self-escalation via `ConnectedOrigins#setAutoApprove` lacking trust check - ([File: features/connected-origins/module/connections.js])

### Finding Description
`setAutoApprove` delegates directly to `#setAttributes`, which only verifies that a record exists for the origin via `#getOrigin` — it never calls `isTrusted` before allowing the `autoApprove` flag to be flipped to `true`: [1](#0-0) . Compare this with `getConnectedAccounts`, which explicitly gates on `isTrusted` before returning sensitive data: [2](#0-1) . Because `add({ origin, trusted })` allows `trusted` to remain falsy/undefined for a new record (it's only set if the caller passes it), and `#getOrigin` only checks for record *existence*, any code path that can call `add` followed by `setAutoApprove` for the same origin can set `autoApprove: true` on an untrusted record: [3](#0-2) . `isAutoApprove` later returns this raw flag with no cross-check against `isTrusted`: [4](#0-3) .

However, both `setAutoApprove` and `add` are exposed only through `connectedOriginsApi`, which is registered as an internal `type: 'api'` module [5](#0-4) , consumed via the extension's UI↔background RPC channel (`@exodus/browser-extension-rpc`'s `createUiRpc`/`createBackgroundRpc`), not the dapp-facing content-script/provider bridge (`content.js`) that injects `window.ethereum`/`window.exodus.*` into web pages [6](#0-5) . I could not find any code path in the Ethereum/Bitcoin/Cardano provider bridges (`docs/web3-providers/*`, provider RPC handlers) that forwards a `connectedOrigins.setAutoApprove` call from an untrusted origin/dapp through to this API — the provider surface only exposes chain-specific RPC methods (e.g., `eth_sendTransaction`, `wallet_switchEthereumChain`), not direct calls into `connectedOriginsApi`.

### Impact Explanation
While the internal logic gap is real (`setAutoApprove` doesn't call `isTrusted`), I found no reachable attacker path from an untrusted dapp/origin to invoke `connectedOriginsApi.setAutoApprove` directly. The API is only wired into the internal extension UI↔background RPC surface, not the content-script/provider bridge that web pages can reach. Without evidence of a provider handler or content-script route forwarding arbitrary origin-controlled RPC calls into `connectedOriginsApi.setAutoApprove`, this does not constitute an attacker-controlled-origin exploit reachable "via ordinary dapp/origin requests" as required by the audit scope.

### Likelihood Explanation
Low/unconfirmed — the vulnerable code exists, but the required reachability (an untrusted web origin calling `connectedOriginsApi.setAutoApprove` for itself) is not demonstrated in the indexed codebase. This may be due to index coverage limits on the provider/RPC-handler wiring code, which I could not fully trace.

### Recommendation
Regardless of current reachability, harden `setAutoApprove` defensively: require `isTrusted({ origin })` to be true before allowing `attributes.autoApprove = true`, mirroring the pattern used in `getConnectedAccounts` and `untrust`.

### Proof of Concept
Unit test in `features/connected-origins/module/__tests__/connections.test.js`:
```js
test('setAutoApprove should not enable auto-approve for untrusted origin', async () => {
  await connectedOriginsAtom.set([{ origin: 'evil.com', trusted: false, autoApprove: false }])
  await connectedOrigins.setAutoApprove({ origin: 'evil.com', value: true })
  const result = await connectedOrigins.isAutoApprove({ origin: 'evil.com' })
  expect(result).toBe(false) // currently fails: returns true
})
```
This confirms the internal logic gap exists in isolation, but note that a full exploit PoC would additionally need to demonstrate a reachable RPC/provider path from an untrusted dapp into `connectedOriginsApi.setAutoApprove`, which was not found in this codebase during this investigation. I recommend a Devin session with full filesystem access to trace all provider/RPC handler registrations exhaustively before treating this as a confirmed exploitable vulnerability.

export const createRPCProxy = ({ extensionName, channelName }) => {
  if (typeof extensionName !== 'string' || typeof channelName !== 'string') {
    throw new TypeError(`Unable to create RPC because channelName or extensionName are missing`)
  }

  const channel = channels[channelName]
  const transport = createWindowRpcTransport({
    name: `${extensionName}-${channelName}`,
    target: `${extensionName}-${channelName}-window`,
  })

  transport.on('data', async (event) => {
    const isResponse = !JSON.parse(event).method
    const senderMetadata = await metadata
    const options = { senderMetadata }

    if (isResponse) {
      channel.sendMessage(event, options)
    } else {
      channel.call(event, options).then(transport.write)
    }
  })

  channel.onMessage((message, sender) => {
    if (sender.tab) return
    transport.write(message)
  })
}
