### Title
Attacker-crafted swap route executes arbitrary contract calls under the victim's authorization tree, draining wallet tokens - (contracts/swap-aggregator/src/venues/mod.rs)

### Summary
`execute_strategy` deserializes an untrusted `swap_xdr` payload — supplied verbatim by the caller/counterparty — into a `StrategyPayload` whose `assets` registry names the `pool` addresses each hop invokes. The router keeps no allowlist of pools or tokens and self-authorizes venue calls with `env.authorize_as_current_contract`, so a pool address in the payload is arbitrary attacker-deployed code placed on the call stack *inside* the user's authorized invocation. That code can call `token.transfer(victim, attacker, amount)` on any token; the transfer joins the victim's auth tree as a child entry, and if the victim signs the simulated tree it executes — the same bug class as `serialize-to-js` evaluating an IIFE inside attacker-controlled serialized data. This is reachable from controller `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, and `flash_position` (all of which take a `StrategySwap` payload) and from direct `execute_strategy` calls.

### Finding Description
The router decodes `swap_xdr` with `StrategyPayload::from_xdr` and runs the instruction stream, dispatching each `Opcode::Swap` to `venues::dispatch_hop`, which calls `ctx.hop.pool` — an address taken straight from the payload's `assets` registry with no allowlist [1](#0-0) [2](#0-1) . The venue adapters only self-authorize the router's own input pull; nothing constrains what the invoked pool contract does next.

The threat-model doc states the exposure directly: "a route can put third-party code on the call stack below the caller's authorization. A token transfer that such code makes from the caller is recorded by an honest simulation as a child of the caller's authorization entry, and it executes if the caller signs that tree. The loss is then the caller's wallet, not the routed amount" [3](#0-2) .

The harness test proves execution: `RogueHopPool::swap` calls `token::Client::transfer(victim, attacker, amount)`; when the victim signs the tree simulation produced, the transfer succeeds and Alice's unrelated wallet token is fully drained [4](#0-3) [5](#0-4) .

On the controller side, `swap_tokens` passes the caller-supplied `StrategySwap` bytes straight into `router.execute_strategy`, so every strategy entrypoint inherits the exposure [6](#0-5) .

### Impact Explanation
Theft of user funds: any token in the victim's wallet (not just the routed input) can be transferred to the attacker inside the victim's own signed authorization. The routed amount, the payload `min_out`, and the controller's final risk gate do not bound the loss — a poisoned route can still deliver fair-looking swap output while the rogue pool sweeps the wallet. Severity: High.

### Likelihood Explanation
Exploitation requires the victim to sign an authorization tree that contains the malicious child transfer. Wallets and SDK flows typically sign the simulated tree wholesale; the repo's own guidance treats decoding-and-inspecting the auth tree as a mitigation clients "must" perform, which is not enforced by any contract and not performed by default. An attacker can distribute malicious `routeXdr` through phishing quote responses or malicious frontends. Single-transaction, no privilege required to deploy the rogue pool or craft the payload.

### Recommendation
- Enforce a venue/pool allowlist or verified-pool registry on-chain rather than trusting payload-supplied `pool` addresses; alternatively pin pools per (venue, pair) in router storage.
- Run each hop inside a scope that cannot reach the sender's auth (e.g., isolate the venue call so it cannot `require_auth` on the sender) if the host supports it.
- Enforce in SDKs/wallets: refuse to sign an `execute_strategy` or controller-strategy auth tree containing any child entry other than the single input `transfer`.

### Proof of Concept
`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` is the working PoC:

1. Attacker deploys `RogueHopPool` whose `swap()` does `token.transfer(alice → attacker, WALLET_BALANCE)` on an unrelated wallet token (`PLAN` set in `__constructor`, lines 56–71).
2. Attacker crafts route XDR naming that contract as the hop pool (`route_through_pool_stealing`, lines 111–125).
3. Victim calls `swap_collateral` (or `execute_strategy` directly) with the route. Simulation returns an auth tree containing the rogue `transfer` as a child of her root authorization.
4. Signing that tree executes the theft: `assert_eq!(s.wallet(&s.alice), 0); assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);` (lines 265–269). The honest tree without the child correctly fails with `Unauthorized function call for address` (lines 240–254).
