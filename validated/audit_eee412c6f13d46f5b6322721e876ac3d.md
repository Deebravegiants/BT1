### Title
Webhook `topic` and `shop` headers are unauthenticated and unbound to the HMAC signature, allowing tenant-identity forgery in `Registry.process` - (File: `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies only that the raw request body was signed with the app's shared secret; it never binds the `topic` or `shop-domain` headers to that signature. Because `Webhooks::Request#to_signable_string` returns only `@raw_body`, and `topic`/`shop` are read straight from unsigned HTTP headers, an attacker who has ever obtained one valid `(body, hmac)` pair from the app (e.g., by installing it on their own development shop) can replay that same body/HMAC to the app's public webhook endpoint while substituting arbitrary `topic` and `shop-domain` header values. `HmacValidator.validate` will still pass, and `WebhookMetadata#shop`/`#topic` — the values host apps are documented to trust for routing and per-shop record access — will contain attacker-chosen data.

### Finding Description
The broken binding is:
`HMAC_valid(request) == true` is claimed to imply `request.shop == victim_owns_this_webhook AND request.topic == actual_event_type`, but in reality `HMAC_valid(request)` only certifies `HMAC(api_secret_key, request.raw_body) == request.hmac`. `shop` and `topic` are excluded from the signable string.

Evidence:
- `Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 
- `topic` and `shop` are pulled directly from unauthenticated headers with no cross-check against the signed payload: [2](#0-1) 
- `Registry.process` validates the HMAC, then immediately uses the *unverified* `request.topic` to select a handler and passes the *unverified* `request.shop` straight into `WebhookMetadata`, which host apps use to decide "whose records to touch": [3](#0-2) 
- `WebhookMetadata#shop` is a plain `T::Struct` field with no provenance/authentication semantics: [4](#0-3) 
- Documentation confirms host apps are expected to key off `data.shop`/`data.topic` directly (e.g., to route jobs "shop_domain: data.shop"): [5](#0-4) 

Exploit flow: the attacker (an unprivileged party who can install the same app on their own development shop, per the threat model) receives a legitimate webhook delivery with body `B` and a valid `hmac-sha256` header `H = HMAC(secret, B)`. Because `secret` is shared across all shops using this app installation, `(B, H)` remains a valid pair regardless of which shop it is attributed to. The attacker then sends their own HTTP POST directly to the app's public webhook route (this route has no other authentication — it is "the entry point of every app's public webhook route") with:
- `raw_body = B`
- `x-shopify-hmac-sha256 = H` (unchanged, still valid for body `B`)
- `x-shopify-topic = <attacker-chosen topic, e.g. "customers/redact" or "app/uninstalled">`
- `x-shopify-shop-domain = <victim-shop.myshopify.com>`

`HmacValidator.validate` passes because it only checks `HMAC(secret, B) == H`. `Registry.process` then selects the handler solely by the forged topic and constructs `WebhookMetadata` with the forged shop, which the host app's handler treats as the authenticated tenant for record mutation, exactly as documented.

None of the existing guards catch this: `HmacValidator.validate` doesn't cover headers; there is no `ShopValidator.sanitize!` call in this path; there is no JWT/session-token check in the webhook flow at all (webhooks don't carry JWTs); `Context.setup?`/`private?`/`embedded?` are unrelated to webhook payload authenticity. Sorbet typing only enforces `String` types, not provenance.

### Impact Explanation
This breaks the SINGLE IDENTITY invariant: the `shop` value used to select which tenant's data a webhook handler touches is not derived from any authenticated source — it is copied verbatim from an attacker-controllable header once *any* valid signed body is available. This enables cross-tenant impact: an attacker can cause a host application to execute arbitrary registered webhook handlers (e.g., GDPR redaction endpoints, uninstall cleanup, order/customer sync) against a victim merchant's shop identity, using only a body/HMAC pair the attacker legitimately obtained for their own shop. This is repeatable against any shop domain the attacker chooses to type into the forged header, for as long as the attacker retains one valid `(body, hmac)` pair (which they can obtain repeatedly by triggering webhooks on their own dev shop). This matches the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Preconditions: the host app must expose the standard public webhook route as documented (no extra app-level authentication is expected or provided by this gem), and the attacker must be able to install the same app (or otherwise trigger a webhook delivery) on a shop they control to harvest one valid `(body, hmac)` pair — both are explicitly within the stated attacker capabilities. No `api_secret_key`, tokens, or victim credentials are required. Cost is a single webhook capture plus one crafted HTTP POST; the attack is fully repeatable and scriptable.

### Recommendation
Do not treat `topic` or `shop` from `Webhooks::Request` as trusted merely because the HMAC validates. At minimum:
1. Include `topic` and `shop-domain` in the signable string used for HMAC verification (if compatible with Shopify's actual webhook signing scheme), or
2. Require the host app to independently verify that `request.shop` corresponds to a shop with an active, known installation/session before invoking the handler, and reject topics that don't match the destination route's registered topic, and
3. Document/enforce that `Registry.process` must only be reachable via routes bound 1:1 to a specific topic (so the header-derived topic cannot be used to pick an arbitrary handler), and validate `shop` against the app's own installed-shops store rather than trusting the header outright.

### Proof of Concept
Minitest + WebMock/Mocha plan (no live shop):
```ruby
def test_shop_and_topic_are_not_bound_to_hmac
  secret = ShopifyAPI::Context.api_secret_key
  body = '{"id":1}'
  valid_hmac = Base64.encode64(OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, body))

  legit_headers = {
    "x-shopify-topic" => "orders/create",
    "x-shopify-hmac-sha256" => valid_hmac,
    "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
  }

  forged_headers = {
    "x-shopify-topic" => "customers/redact", # attacker picks handler
    "x-shopify-hmac-sha256" => valid_hmac,    # same body+hmac, unchanged
    "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged tenant
  }

  received_shop = nil
  handler = TestHelpers::FakeWebhookHandler.new(->(data) { received_shop = data.shop })
  ShopifyAPI::Webhooks::Registry.add_registration(
    topic: "customers/redact", path: "path", delivery_method: :http, handler: handler,
  )

  # Assert: HMAC computed over body only, unaffected by topic/shop change
  legit_request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: legit_headers)
  forged_request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)
  assert_equal(legit_request.hmac, forged_request.hmac) # binding is broken: shop/topic don't affect hmac

  ShopifyAPI::Webhooks::Registry.process(forged_request)
  assert_equal("victim-shop.myshopify.com", received_shop) # attacker-controlled shop accepted as authentic
end
```
This demonstrates the equality `HMAC(body)_legit == HMAC(body)_forged` holds despite `shop`/`topic` differing, proving `Registry.process` treats the forged, attacker-chosen `shop` as authenticated tenant identity.
