Confirming the AuthQuery HMAC covers `code`, `host`, `shop`, `state`, `timestamp` — all bound. The webhook path is where the identity binding actually breaks: `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) trusts `request.shop`, `request.topic`, and `request.webhook_id` (all read from unauthenticated HTTP headers via `shopify_header` in `lib/shopify_api/webhooks/request.rb:20-33`) while `Utils::HmacValidator.validate` only verifies `to_signable_string`, which returns solely `@raw_body` (`lib/shopify_api/webhooks/request.rb:36-38`). The header values used to route/attribute the webhook (especially `shop`) are never part of the signed material.

### Title
Webhook `shop`/`topic`/`webhook_id` headers are not covered by HMAC verification, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, and `webhook_id` are read directly from HTTP headers that are excluded from the HMAC computation. `Registry.process` verifies only the body's HMAC and then unconditionally trusts these unauthenticated headers to build `WebhookMetadata`, breaking the intended binding `hmac(secret, signed_material) == hmac_header` against the equality that should hold: `shop_used_by_handler == shop_the_hmac_actually_authenticates`.

### Finding Description
`Registry.process` is:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
end
``` [1](#0-0) 

`Utils::HmacValidator.validate` only checks `verifiable_query.to_signable_string` against the HMAC header: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns just `@raw_body`, while `shop`, `topic`, and `webhook_id` come from headers that are never included in the signed content: [3](#0-2) 

Because a Shopify app's `api_secret_key` is shared across every shop that installs the app (it is the app's client secret, not per-tenant), any merchant who installs the app can receive a genuine, validly-signed webhook (raw body + matching `X-Shopify-Hmac-SHA256`) addressed to their own shop. That merchant — an otherwise unprivileged internet user with respect to any other tenant of the same app — can replay that exact `raw_body`/HMAC pair directly to the app's public webhook endpoint while substituting the `shop-domain`, `topic`, and/or `webhook_id` headers with a different (victim) shop's domain or an arbitrary topic/id. `HmacValidator.validate` still succeeds because it never inspects those headers, and `Registry.process` dispatches the handler with the forged `shop` value, causing the host application's handler logic (which typically loads store/session data keyed by `request.shop`) to run against the wrong tenant.

This is exactly the reported bug class translated into this gem's own code: a field (`shop`, and also `topic`/`webhook_id`) is acted upon by `process`/`WebhookMetadata` but is not covered by the HMAC that is supposed to authenticate the whole payload.

### Impact Explanation
This breaks the equality `shop bound by signature == shop acted on by handler`, letting an app-installing attacker (unprivileged relative to other tenants) make the app process forged webhook events attributed to an arbitrary victim shop — cross-tenant confusion/access via the webhook processing path. This satisfies the Critical bar of cross-tenant access, since any handler logic keyed off `data.shop` (loading sessions, updating records, mutating that shop's data) executes for a shop the request never actually came from.

### Likelihood Explanation
Medium-to-High: it requires the attacker to be (or become) a merchant who has installed the target app once, to obtain one genuinely signed webhook body/HMAC pair for their own shop, then replay it against the app's public webhook endpoint with edited headers — no access token, `api_secret_key`, or TLS interception is needed, and the request travels over the normal internet path to the app's exposed endpoint.

### Recommendation
Include the security-relevant identity fields (`shop-domain`, `topic`, `webhook_id`, `api-version`) in the material that is HMAC-verified, or otherwise cryptographically bind them to the raw body (e.g., require the host app to separately validate that `shop` matches an installed, expected shop for the delivered `topic`/`webhook_id` combination, or have `Registry.process` reject requests where the shop is not one with an active, previously-established session before dispatching the handler).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering a real webhook delivery; attacker's own endpoint captures the exact `raw_body` and its `x-shopify-hmac-sha256` value (both legitimately signed by Shopify using the app's shared `api_secret_key`).
2. Attacker sends a new HTTP POST directly to the app's public webhook endpoint with:
   - the exact same `raw_body` and `x-shopify-hmac-sha256` from step 1,
   - `x-shopify-shop-domain: victim-shop.myshopify.com`,
   - optionally a different `x-shopify-topic`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (`@raw_body` only) and finds it matches — validation passes. [4](#0-3) 
4. `Registry.process` builds `WebhookMetadata` using `request.shop` (`victim-shop.myshopify.com`, taken straight from the attacker-controlled header) and `request.topic`, then invokes the registered handler. [5](#0-4) [6](#0-5) 
5. The host application's handler executes business logic (e.g., data sync, session lookups, order processing) attributing it to `victim-shop.myshopify.com`, despite the payload never having been sent by or signed for that shop.
