## Title
Webhook shop identity spoofing via HMAC that only covers the raw body, not the `shop-domain` header — cross-tenant webhook impersonation - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the `shop` value used to identify the tenant for the webhook is read from an unauthenticated HTTP header. Because a single app secret (`api_secret_key`) is shared across every shop that installs the app, any merchant who can trigger a webhook to themselves can capture a body+HMAC pair that is valid for that api key, then replay it to the app's public webhook endpoint with a forged `X-Shopify-Shop-Domain` header naming a different (victim) shop. `Registry.process` accepts the request as valid and hands the handler a `WebhookMetadata` object whose `shop` field is the attacker-chosen value, breaking the binding `authenticated_shop == shop_the_data_is_processed_for`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop` is parsed straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the signature: [2](#0-1) 

`Utils::HmacValidator.validate` only ever verifies `verifiable_query.to_signable_string` (the body) against `verifiable_query.hmac`: [3](#0-2) 

`Registry.process` performs exactly this body-only check and then trusts `request.shop` (and `request.topic`) unconditionally to build the metadata delivered to the app's handler: [4](#0-3) 

Since `api_secret_key` is a single per-app secret shared across all installed shops (as seen throughout `HmacValidator`, `JwtPayload`, and OAuth code, which all key off `Context.api_secret_key`), any shop that has installed the app can generate a genuinely-signed webhook body/HMAC pair. Because the `shop-domain` header is outside the signed content, that same valid `(body, hmac)` pair can be replayed against the app's public webhook endpoint with an arbitrary `shop-domain` header value, and it will pass `HmacValidator.validate` even though the body did not originate from, and has no relation to, the shop named in the header.

### Impact Explanation
This breaks the tenant-identity binding the gem is responsible for enforcing when it hands verified webhook data to the host application: "the shop that authenticated the request" must equal "the shop the payload is attributed to." A malicious merchant (any shop owner able to install the app) can impersonate an arbitrary victim shop by relabeling a self-generated, validly-signed webhook payload. Any host application that trusts `WebhookMetadata#shop` (returned by `Registry.process`/passed to `handler.handle`) to scope writes/updates (e.g., "look up or create the local shop record named `data.shop` and apply `data.body`") is exposed to cross-tenant data injection/corruption — attacker-controlled content is delivered under a victim shop's identity. This matches the Critical "cross-tenant access" impact category: no credentials, access tokens, or `api_secret_key` knowledge are needed beyond running the app on the attacker's own shop, which is normal, unprivileged merchant capability.

### Likelihood Explanation
High. The webhook endpoint is by design internet-reachable (Shopify posts to it over the open internet), and any attacker with a free/legitimate installation of the target app on their own store can generate valid signed webhook traffic at will (e.g., by editing a product, updating an order note, etc., all of which allow attacker-controlled body content). Forging the `shop-domain` header requires nothing more than crafting an HTTP request with a different header value — no cryptographic material is needed since that field is unauthenticated.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-signable content, or otherwise cryptographically bind the claimed shop to the verified payload before constructing `WebhookMetadata`. At minimum, `Registry.process` should cross-check the `shop-domain` header against a value that is authenticated out-of-band (e.g., only accept webhooks for shops with an existing, matching offline session/access token on file) rather than trusting the header verbatim once body HMAC succeeds.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`.
2. Attacker performs an action that causes Shopify to send a webhook (e.g. `products/update`) with a body they fully control (product title/body_html), producing a request with header `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over that body computed with the app's api_secret_key>`.
3. Attacker replays that exact `(raw_body, hmac header)` pair directly to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` which only checks `raw_body` against the HMAC — validation succeeds.
5. The registered handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON>, ...)`, i.e., attacker-controlled data is processed under the victim's tenant identity. [5](#0-4) [6](#0-5)
