### Title
Missing shop domain validation in `TokenExchange.exchange_token` allows the app's `client_secret` to be sent to an attacker-controlled host - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the request host for the Shopify OAuth token endpoint directly from the `dest` claim of the caller-supplied session token, without ever passing it through `Utils::ShopValidator.sanitize!`. Every other credential-sending method in this module and its sibling files (`migrate_to_expiring_token`, `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`) explicitly validate the `shop` value against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` before using it to build the session/host that will receive `client_id`/`client_secret`. This asymmetry breaks the intended binding: *"the host validated" should equal "the host that receives the `client_secret`."*

### Finding Description
`exchange_token` decodes the caller-supplied `session_token` via `JwtPayload.new(session_token)` and takes the shop straight from the token: [1](#0-0) 

`JwtPayload#shop` performs no domain allow-listing — it just strips the `https://` prefix from the raw `dest` claim: [2](#0-1) 

`dest_shop` is then used, unsanitized, to build the session whose `shop` attribute determines the target host for the token-exchange HTTP request that carries the app's `client_id`/`client_secret`: [3](#0-2) 

Contrast this with the three sibling flows in the same module/area, which all call `Utils::ShopValidator.sanitize!(shop)` before constructing the session/host that will receive the same secret: [4](#0-3) [5](#0-4) [6](#0-5) 

`ShopValidator` exists specifically to enforce that any string used as a request host must resolve to a domain under the small allow-list (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`, or a configured `myshopify_domain`): [7](#0-6) 

`exchange_token` is the one code path in this family that skips this check entirely, so whatever string is present in the token's `dest` claim (after only a naive `.gsub("https://", "")`) becomes the literal host contacted with the app's `client_secret` in the POST body.

### Impact Explanation
This maps to the analog rule "a host validated versus the host that receives the access token or `client_secret`" — the equality that should hold is:
`ShopValidator.sanitize!(host_used_for_request) == host_that_actually_receives_client_secret`.
For every sibling method this equality is enforced; for `exchange_token` it is not — the unsanitized `dest_shop` is both used and trusted with no allow-list check. If the `dest` claim can ever contain a value outside the trusted domain suffixes (docs confirm `dest` is not restricted to a single canonical format — it can be `myshopify.io`, `spin.dev`, etc., i.e., it is a free-form string interpreted by this method), the app's confidential `client_secret` would be sent verbatim to that host — an SSRF-with-credentials scenario (Critical/High per the rules: "SSRF with the app's credentials" / credential exfiltration).

### Likelihood Explanation
The primary safeguard is that `session_token` must pass `JwtPayload`'s HMAC/JWT signature check against `Context.api_secret_key` before its `dest` is trusted, so in the fully-correct/expected deployment this should only ever contain a legitimate Shopify-issued value. However, this method is the codebase's *own* recommended, primary flow (per `docs/usage/oauth.md`, "we strongly recommend ... token exchange"), and it is the only one of four analogous credential-sending call sites that omits the `ShopValidator` defense-in-depth check that its siblings apply uniformly to the exact same class of input (a string ultimately used to build the request host). This is a genuine, verifiable inconsistency in the library's own trust model rather than a hypothetical scenario, and it removes a validation layer that the codebase itself considers necessary elsewhere for the same operation (sending `client_secret` to a shop-derived host).

### Recommendation
Route `dest_shop` through `Utils::ShopValidator.sanitize!` before constructing `shop_session` in `TokenExchange.exchange_token`, consistent with `migrate_to_expiring_token`, `ClientCredentials.client_credentials`, and `RefreshToken.refresh_access_token`:
```ruby
dest_shop = Utils::ShopValidator.sanitize!(jwt_payload.shop)
```

### Proof of Concept
1. Obtain/construct a `session_token` whose `dest` claim, once validated by `JwtPayload`, is a string that does not resolt to a `ShopValidator`-trusted domain (e.g., a `spin.dev`-style or otherwise permissively-formatted domain string that the deployment's `Context` configuration does not add to the allow-list).
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. Observe that `dest_shop` is used unvalidated to build `shop_session`, and the subsequent `Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")` request — carrying `client_id`/`client_secret` in its body — is sent to a host derived from that unsanitized value, whereas the sibling `migrate_to_expiring_token`/`client_credentials`/`refresh_access_token` paths would have rejected such a value via `ShopValidator.sanitize!` raising `Errors::InvalidShopError`.

*Note:* Full confirmation of exactly how `Clients::HttpClient` resolves `session.shop` into the outbound HTTP host was not independently re-verified in this final pass (index limits); the pattern is inferred from the identical `Clients::HttpClient.new(session: ..., base_path: "/admin/oauth")` usage shared with `oauth.rb`'s `validate_auth_callback`, where `session.shop` is documented/used as the request host. A Devin session with full repo access could confirm `HttpClient`'s host-resolution logic directly.
