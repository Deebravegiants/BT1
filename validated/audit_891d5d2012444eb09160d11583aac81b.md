### Title
Vetoed-and-resubmitted state height creates a duplicate queue entry that evicts the live state commitment one insertion early - (File: modules/pallets/ismp/src/host.rs)

### Summary
`delete_state_commitment` (invoked by fraud-proof handling in `pallet-ismp`) deliberately does not remove the corresponding entry from `StateCommitmentQueue`, and when the vetoed height is the current latest height it rolls `LatestStateMachineHeight` back to the previous height, re-opening that height number for a fresh consensus update. This is a documented, intentional trade-off (see the comment in [1](#0-0) ), but it produces two live-looking queue slots pointing at the same height — a stale one and a fresh one — with only the FIFO head/tail bookkeeping in `CommitmentQueueState` tracking retention.

### Finding Description
`StateCommitmentQueue`/`CommitmentQueueStates` implement a bounded FIFO free-list: `head`/`tail` indices bound the "live" window of a per-chain queue, and `insert_bounded_state_commitment` evicts entries at `head` to enforce `StateMachineCommitmentCap` (default `MAX_STATE_MACHINE_COMMITMENTS`), as documented at [2](#0-1)  and the `CommitmentQueueState` struct in [3](#0-2) .

When a fraud/veto proof is processed by an unprivileged relayer (via `handle_unsigned` dispatching a consensus fault-proof message, which calls into `delete_state_commitment`), and the vetoed height happens to be the chain's current latest height, `LatestStateMachineHeight` is rolled back to `PreviousStateMachineHeight`, re-opening that exact height for honest resubmission — [4](#0-3) . Because the queue entry for the vetoed height is deliberately left in place ("locating it would mean scanning the queue"), the honest resubmission of that same height inserts a **second** queue entry immediately behind the stale one. This is exactly the free-list/queue race-class described in the CVE: the eviction accounting (analogous to Xen's maptrack free list) becomes desynchronized from the actual live entries, so when the stale index reaches `head` it evicts the *live* commitment for that height one insertion earlier than the configured cap intends, permanently burning one queue slot per veto-and-resubmit cycle — confirmed by the regression test at [5](#0-4) .

### Impact Explanation
This does not directly enable theft or forged messages, but it corrupts the retention guarantee `StateCommitmentQueue`/`BoundedStateCommitments` exist to provide: a state commitment that should still be retained (within the configured cap) is silently deleted from `BoundedStateCommitments`/`BoundedStateMachineUpdateTime` one insertion too early, whenever any legitimate veto of the latest height (a normal, permissionless fraud-proof event) is followed by honest resubmission and further consensus updates. Any pending message/state-proof verification depending on the prematurely evicted height would then fail with `StateCommitmentNotFound`, denying relayers the ability to deliver requests/responses that were relying on that height — a "route unable to deliver messages" outcome for anyone who submitted a request expecting to be proven against that height. Each occurrence also permanently shrinks the effective retention window by one slot, an accumulating degradation under repeated veto/resubmit cycles on a chain with adversarial or faulty consensus relayers.

### Likelihood Explanation
Reaching this path requires only an unprivileged relayer submitting (a) a legitimate fraud/veto proof against the current latest height for some counterparty state machine, followed by (b) an honest consensus update resubmitting that same height, and (c) enough further consensus updates to advance `head` up to the stale index — all through the permissionless `handle_unsigned` extrinsic. No admin/governance action is required, and fraud-proof vetoes of the latest height are an expected, not just theoretical, occurrence in the protocol's fault-handling design. However, the codebase's own comments explicitly document this as a known, accepted "wart" with negligible practical cost against the configured caps, which somewhat tempers the severity from the maintainers' perspective.

### Recommendation
Track the queue index alongside each state commitment (e.g., a `StateMachineId -> height -> queue_index` map, or store the index in `BoundedStateCommitments`/`BoundedStateMachineUpdateTime` metadata) so `delete_state_commitment` can invalidate the specific stale queue entry rather than leaving a duplicate behind, or mark resubmitted heights so the eviction logic recognizes and skips a stale twin instead of deleting the live entry it precedes.

### Proof of Concept
The exact reproduction sequence is already codified in the test suite: [6](#0-5)  stores height 10 and 11, vetoes height 11 (the latest), asserts the latest pointer rolls back to 10, resubmits height 11 (creating a second queue entry pointing at 11), then stores height 12 and demonstrates the live commitment for height 11 is deleted (`state_machine_commitment(...11).is_err()`) one insertion earlier than the cap of 2 would allow, with `CommitmentQueueStates` showing the queue has burned one slot (`head: 2, tail: 4` instead of the expected retention window).

I was not able to fully trace whether `delete_state_commitment` is reachable purely by an unprivileged relayer with no additional trust assumptions (i.e., the exact fraud-proof consensus-client message flow invoking it) within the given context — this would need to be verified in `modules/ismp/core` consensus client fraud-proof handling code, which wasn't part of what I retrieved.

	fn delete_state_commitment(&self, height: StateMachineHeight) -> Result<(), Error> {
		// The height's entry in the state commitment queue is deliberately left
		// behind; locating it would mean scanning the queue, which is the per-insert
		// cost the queue exists to avoid. Usually its eviction is a no-op, but when
		// the vetoed height is the latest the reset below re-opens it for honest
		// resubmission, and the resubmitted height gets a *second* queue entry. The
		// stale entry then evicts the live commitment when it reaches the head —
		// one insertion before the live entry would have, since the resubmission
		// lands directly behind its stale twin. So a veto costs that height one
		// insertion of retention and permanently burns one queue slot. Both are
		// negligible against the configured caps; making it exact would need a
		// height -> index map on the insert path.
		BoundedStateCommitments::<T>::remove(height.id, height.height);
		BoundedStateMachineUpdateTime::<T>::remove(height.id, height.height);

		// technically any state commitment can be vetoed,
		// safety check that it's the latest before resetting it.
		if let Some(latest) = LatestStateMachineHeight::<T>::get(height.id) {
			if latest == height.height {
				// Reset back to the initial height to allow for honest updates
				let prev_height =
					PreviousStateMachineHeight::<T>::get(height.id).ok_or_else(|| {
						Error::Custom("Previous state machine height should exist".to_string())
					})?;
				LatestStateMachineHeight::<T>::insert(height.id, prev_height);
			}
		}
		Ok(())
	}

	/// Per-chain FIFO queue of heights retained in [`BoundedStateCommitments`]
	/// and [`BoundedStateMachineUpdateTime`], keyed by a monotonically
	/// increasing insertion index. Insertion order matches height order because
	/// consensus updates only ever advance a state machine, so evicting at the
	/// head removes the oldest height. Entries whose height was vetoed via
	/// `delete_state_commitment` are left in place and become harmless no-ops
	/// when their index is evicted.
	///
	/// Each insertion touches O(1) small storage items, so the per-chain cap
	/// can grow without adding I/O or PoV weight to the insert path.
	#[pallet::storage]
	pub type StateCommitmentQueue<T: Config> = StorageDoubleMap<
		_,
		Blake2_128Concat,
		StateMachineId,
		Twox64Concat,
		u64,
		u64,
		OptionQuery,
	>;

	/// Head/tail indices for [`StateCommitmentQueue`], per chain.
	#[pallet::storage]
	pub type CommitmentQueueStates<T: Config> =
		StorageMap<_, Blake2_128Concat, StateMachineId, CommitmentQueueState, ValueQuery>;

// Vetoing the *latest* height resets the latest pointer, which re-opens that height
// for honest resubmission. The resubmission gets a second queue entry, and the stale
// twin ahead of it evicts the live commitment one insertion early. This pins that
// wart: it costs the height one insertion of retention and burns one queue slot,
// which is negligible against the configured caps but is not a no-op.
#[test]
fn vetoed_latest_height_that_is_resubmitted_evicts_one_insertion_early() {
	let mut ext = new_test_ext();
	ext.execute_with(|| {
		let host = Ismp::default();
		let id = queue_test_state_machine();
		let store = |height: u64| {
			host.store_state_machine_commitment(
				StateMachineHeight { id, height },
				queue_test_commitment(),
			)
			.unwrap();
			host.store_latest_commitment_height(StateMachineHeight { id, height }).unwrap();
		};

		pallet_ismp::Pallet::<Test>::update_commitment_caps(
			RuntimeOrigin::root(),
			BTreeMap::from([(id, 2)]),
		)
		.unwrap();

		store(10);
		store(11);

		// Vetoing the latest height rolls the latest pointer back to 10, so the
		// consensus handler would accept 11 again: it is not below the latest and
		// its commitment is now absent.
		host.delete_state_commitment(StateMachineHeight { id, height: 11 }).unwrap();
		assert_eq!(host.latest_commitment_height(id).unwrap(), 10);

		store(11);
		assert!(host.state_machine_commitment(StateMachineHeight { id, height: 11 }).is_ok());
		// Two queue entries now point at height 11: the stale one and the live one.
		assert_eq!(StateCommitmentQueue::<Test>::get(id, 1), Some(11));
		assert_eq!(StateCommitmentQueue::<Test>::get(id, 2), Some(11));

		// Evicting the stale entry at index 1 deletes the live commitment for 11,
		// one insertion before the entry at index 2 would have.
		store(12);
		assert!(host.state_machine_commitment(StateMachineHeight { id, height: 11 }).is_err());
		assert!(host.state_machine_commitment(StateMachineHeight { id, height: 12 }).is_ok());
		// The queue still counts index 2 as live, so the burnt slot leaves this
		// chain retaining one fewer commitment than its cap of 2.
		assert_eq!(
			CommitmentQueueStates::<Test>::get(id),
			CommitmentQueueState { head: 2, tail: 4 }
		);
		assert_eq!(StateCommitmentQueue::<Test>::get(id, 2), Some(11));
	})
}
