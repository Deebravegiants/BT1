Audit Report

## Title
CORS wildcard allowlist bypass via missing domain-boundary check in Gateway HTTP server - (File: core/services/gateway/network/httpserver.go)

## Summary
The Gateway HTTP server's `isAllowedOrigin` function implements wildcard CORS origin matching (`*.example.com`) using a raw `strings.HasSuffix` check with no requirement that the match be preceded by a `.` boundary. As a result, an attacker-controlled domain that merely ends with the same characters as the configured suffix (e.g. `fakeethereum.org` for an allowlist entry of `*.ethereum.org`) is incorrectly treated as a legitimate subdomain.

## Finding Description
In `isAllowedOrigin`, when an allowlist entry has the `*.` prefix, the code strips it and performs `strings.HasSuffix(originHost, allowedHost)` with no boundary check: [1](#0-0)  This means any origin host string ending with the literal suffix `ethereum.org` — including a completely unrelated, attacker-registrable domain like `fakeethereum.org` — satisfies the match, since Go's `strings.HasSuffix` performs no semantic subdomain check. `handleRequest` then directly reflects the attacker's `Origin` header into `Access-Control-Allow-Origin` based on this flawed result: [2](#0-1)  The existing test suite only validates true subdomain matches and a non-suffix-colliding negative case (`ethereum.remix.org`, which doesn't even end in the target string), and never tests a domain that shares the literal suffix without a dot boundary, so this gap is unguarded: [3](#0-2) 

## Impact Explanation
This is an internet-facing CORS scoping bypass on the Gateway's HTTP endpoint. Any operator who legitimately uses the wildcard-origin feature (a normal, documented configuration option, not misuse) to restrict access to their own subdomains inadvertently also grants trust to any attacker who registers a domain sharing the literal suffix. This allows an arbitrary, unprivileged web origin to have its cross-origin requests reflected with `Access-Control-Allow-Origin`, letting a browser-based attacker read `ProcessRequest` responses cross-origin — an allowlist/CORS bypass, which maps to the in-scope "allowlist or subscription bypass" / gateway impersonation impact category.

## Likelihood Explanation
Exploitation requires no credentials, no privileged role, and no interaction with the node operator — only registering or controlling a domain string with the matching suffix, then getting a victim browser to visit an attacker page that issues a cross-origin request to the Gateway. This is a standard, low-cost, and fully repeatable attack precondition.

## Recommendation
Require that the suffix match be preceded by a `.` boundary (or be an exact match), e.g.: `originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost)`, so only genuine subdomains satisfy the wildcard rule.

## Proof of Concept
1. Start the Gateway HTTP server with `CORSEnabled: true` and `CORSAllowedOrigins: []string{"https://*.ethereum.org"}` (as in `startNewServer` from `httpserver_test.go`).
2. Send a POST request to the gateway path with header `Origin: https://fakeethereum.org`.
3. Observe that `isAllowedOrigin` returns `true` because `strings.HasSuffix("fakeethereum.org", "ethereum.org")` is `true`.
4. Observe the response contains `Access-Control-Allow-Origin: https://fakeethereum.org`, confirming the bypass — this can be added as a Go test analogous to `TestHTTPServer_HandleRequest_CORSEnabled_FromAllowedOriginWildcards` but asserting the header should be empty and currently is not.
