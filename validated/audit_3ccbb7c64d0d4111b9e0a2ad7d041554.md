### Title
Webhook shop attribution bypass via unsigned `X-Shopify-Shop-Domain` header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw request body only, while the `shop` (merchant) attribution is read from a separate, unsigned HTTP header. `Registry.process` validates the HMAC and then trusts `request.shop` as the tenant identity passed to the host app's handler, without that value ever being covered by the signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is never part of the signable string: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` — which, per `HmacValidator`, only recomputes the signature over `to_signable_string` (i.e., the body) — and then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) [4](#0-3) 

The identity binding that should hold is:
`shop_bound_by_hmac == shop_used_for_tenant_attribution`

But because `to_signable_string` covers only the body, and `hmac-sha256` is computed with the app's single shared `api_secret_key` (identical for every shop that installs the app, not shop-specific), the equality breaks: the HMAC only proves "this body+secret pair is authentic for *some* shop that installed this app," not "this body belongs to the shop named in this header."

### Impact Explanation
A malicious/curious merchant who has legitimately installed the app receives real webhook deliveries containing a valid `body` + `hmac-sha256` pair (both computed with the app's shared `client_secret`). Because the header is not covered by the signature, that same `(body, hmac)` pair can be replayed to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a different (victim) shop's domain. `Utils::HmacValidator.validate(request)` will still pass, since it only checks the raw body against the shared secret, and `Registry.process` will hand the forged `WebhookMetadata` (with the victim's `shop` but the attacker's `body`) straight to the app's handler. This is a cross-tenant identity-binding break: an attacker can inject falsified webhook events (order data, customer data, etc.) attributed to a shop they do not own/operate, using only their own legitimate webhook traffic and no possession of the `client_secret` or victim credentials. Any app relying on `WebhookMetadata#shop` for tenant scoping (e.g., looking up the corresponding session/DB record by shop to act on the payload) is affected — Impact: Critical, cross-tenant access.

### Likelihood Explanation
High. The `client_secret`/`api_secret_key` for a Shopify app is shared across every shop that has installed it — it is not per-shop. Any merchant that installs the app can capture (or trigger, e.g. via `orders/create`) a webhook of their own, then simply POST the identical body/HMAC to the endpoint again with a different `shop-domain` header. No special privileges, no secret leakage, and no interaction with Shopify's own signing process are required beyond being one authorized installer of the app.

### Recommendation
Bind the shop (and other identity-relevant fields such as `topic`/`api-version`/`webhook-id`) into the signed material, or otherwise verify server-side that the `shop-domain` header matches an entity actually authorized to send that specific signed body (e.g., look up the expected shop for the HMAC/webhook subscription rather than trusting the header verbatim). At minimum, `Registry.process`/`WebhookMetadata` construction should not treat `request.shop` as trusted purely because `Utils::HmacValidator.validate(request)` passed, since that validation says nothing about header authenticity.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com`; Shopify sends a legitimate webhook (e.g. `orders/create`) to the app's endpoint with:
   - Body: `{"id":1,"total_price":"1.00", ...}`
   - Headers: `X-Shopify-Hmac-Sha256: <valid hmac of body with shared client_secret>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`
2. Attacker captures this exact `(body, hmac)` pair (they can trivially do so since it was delivered to their own endpoint/logs).
3. Attacker POSTs the same body and the same `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint again, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` recomputes HMAC over `@raw_body` only — matches, validation passes.
5. `Registry.process` builds `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)` and invokes the app's handler, which now processes attacker-controlled data as if it belongs to `victim-shop.myshopify.com`. [3](#0-2) [5](#0-4)
