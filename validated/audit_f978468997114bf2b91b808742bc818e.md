### Title
`withdraw()` in the Tron IntentGatewayV2 finalizes escrow release without validating ERC20 transfer success, allowing silent-fail tokens to cause permanent freezing of escrowed funds - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2` releases escrowed intent tokens using a raw low-level `.call()` to the token's `transfer` selector and only checks that the call itself did not revert (`success`), without decoding or validating the returned boolean. This mirrors the Cooler audit finding: contracts that assume ERC20 `transfer`/`transferFrom` revert on failure will mishandle tokens that instead return `false`.

### Finding Description
In `withdraw()`, escrow release for ERC20 tokens is implemented as: [1](#0-0) 
```solidity
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}
```
and the same pattern is used for fee release: [2](#0-1) 

This check only verifies that the external call did not revert. For an ERC20 implementation that returns `false` on failure instead of reverting (the exact class of token cited in the original Cooler report, e.g. ZRX-style tokens, and common among non-standard TRC20 tokens on Tron), `success` will be `true` even though no tokens were actually moved. Immediately before this call, the function has already finalized state: [3](#0-2) 
```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;

    // redeem escrowed tokens
    uint256 len = body.tokens.length;
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();
```
`_filled[body.commitment]` is set unconditionally and `_orders[body.commitment][token] -= amount` executes regardless of whether the token transfer actually delivered funds, because the raw call "succeeds" even on a logical-failure `transfer(...) returns (false)`.

This is a direct analog of the Cooler bug: the surrounding EVM-mainline version of the same contract (`evm/src/apps/intentsv2/IntentsBase.sol`) correctly uses OpenZeppelin's `SafeERC20.safeTransfer`, which decodes and validates the boolean return value: [4](#0-3) 
```solidity
if (token == address(0)) {
    _sendValue(beneficiary, amount);
} else {
    IERC20(token).safeTransfer(beneficiary, amount);
}
```
The Tron fork diverges from this safe pattern and reintroduces the exact unchecked-transfer class of bug the rest of the codebase avoids.

### Impact Explanation
Once `withdraw()` is invoked (reached via `onAccept` handling a `RedeemEscrow`/`RefundEscrow` message, or via `onGetResponse` after a GET-response proof), the order commitment is marked filled and the escrow accounting is decremented irrespective of whether tokens actually left the contract. If the escrowed token silently fails the transfer (returns `false`), the intended beneficiary (solver or user, depending on `isRefund`) receives nothing, yet the order is marked as settled — permanently freezing the escrowed value inside the contract with no remaining code path to retrieve it (the order is already `_filled`, and there is no re-withdrawal or sweep mechanism for this token/commitment pair). This is a concrete, permanent loss/freezing of user or solver funds for any input/output token that does not strictly follow the revert-on-failure ERC20 convention — a realistic condition on Tron, where many TRC20 tokens (including USDT-TRC20 historically) have non-standard `transfer` semantics.

### Likelihood Explanation
Likelihood is Medium-High specifically on the Tron deployment: any order placed with a token whose `transfer` can return `false` without reverting (insufficient balance edge cases, blacklist/pause logic, or non-standard TRC20 tokens) will trigger this on the very first settlement attempt. No malicious actor is required — a single unprivileged user placing/filling an order with such a token is sufficient to trigger permanent fund freezing, satisfying the "single submitted transaction" reachability bar.

### Recommendation
Replace the raw `.call()` + `success`-only check in `withdraw()` (both the ERC20 escrow release and the fee-token release branches) with `SafeERC20.safeTransfer`, exactly as done in the EVM mainline `IntentsBase._withdraw`. If Tron-specific token quirks (e.g., tokens without a return value) motivated the low-level call, use OpenZeppelin's `SafeERC20` which already tolerates missing return data while still decoding and reverting on an explicit `false` return, rather than ignoring return data entirely.

### Proof of Concept
1. Deploy a TRC20/ERC20 token whose `transfer(to, amount)` returns `false` (rather than reverting) when, e.g., the contract enforces an internal check that fails (mirrors the ZRX-style implementation cited in the original report).
2. User calls `placeOrder` on `IntentGatewayV2` (Tron), escrowing this token — accepted normally since `placeOrder`'s inbound leg uses `safeTransferFrom`.
3. Solver fills the order cross-chain; the source chain host delivers the `RedeemEscrow` message, invoking `onAccept` → `withdraw(body, false)`.
4. Inside `withdraw`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `success = true` even though the token internally returned `false` and moved no funds.
5. `_filled[body.commitment]` is set and `_orders[body.commitment][token] -= amount` is applied — the order is considered settled, but the beneficiary's balance never increased. The escrowed tokens remain stuck in the `IntentGatewayV2` contract with no code path left to reclaim them.
