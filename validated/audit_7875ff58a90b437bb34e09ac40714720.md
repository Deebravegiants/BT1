### Title
Live re-fetch of mutable `pallet-assets` decimals in `HyperFungibleToken::send` allows unbacked minting via decimals metadata drift - ([File: modules/pallets/hyper-fungible-token/src/lib.rs])

### Summary
`pallet-hyper-fungible-token` validates an asset's local decimals only once, at `register_token`/`update_token` time, against the destination chain's `Precisions` entry (`config.decimals >= local_decimals`). However, `send()` does not use a cached/committed decimals value — it re-reads the local decimals live from `fungibles::metadata::Inspect::decimals()` every time a transfer is dispatched. Because `pallet-assets` metadata (including `decimals`) is a display-only field that the asset's `Owner` can change at any time via `set_metadata`, and changing it does not rescale the actual raw balance, an asset owner can lower their asset's recorded decimals after registration to force `send()` to compute a hugely inflated destination-chain mint amount for the same locally-burned/escrowed raw balance. This is directly analogous to the reported `L2StandardERC20.reinitializeToken` issue where overwriting the `decimals` field after the fact breaks invariants that other code silently depends on.

### Finding Description
In `register_token` and `update_token`, decimals are validated once: [1](#0-0) 

But the destination-side conversion factor is computed in `send()` using a **live** lookup of the local asset's decimals metadata, not any value fixed/verified at registration: [2](#0-1) 

`Precisions` only records the remote/EVM-side decimals (`erc_decimals`); there is no stored/committed local decimals value that `send()` checks against: [3](#0-2) 

The scaling helper multiplies the raw balance by `10^(erc_decimals - local_decimals)`: [4](#0-3) 

`pallet-assets` decimals are purely metadata (`set_metadata`), independent of the actual raw balance representation; the asset's `Owner` (a normal, non-privileged account relative to the pallet's `CreateOrigin`/governance) can update decimals at will after the pallet's `CreateOrigin` has registered the asset for bridging. There is no mechanism in `pallet-hyper-fungible-token` to freeze, snapshot, or re-validate the local decimals after registration.

### Impact Explanation
An asset owner can register an asset (e.g. 6 decimals) that a governance/`CreateOrigin` account subsequently approves for the HFT bridge with `erc_decimals = 18` on the destination chain (satisfying `18 >= 6` at registration time). After registration, the owner calls `pallet_assets::set_metadata` to change the asset's decimals to a smaller value (e.g. `0`). The next `send()` call burns/escrows the same raw local balance but computes `erc20_amount = amount * 10^(18-0)` instead of `amount * 10^(18-6)`, inflating the minted amount on the destination chain by orders of magnitude (in this example, 1,000,000x) relative to what was actually removed from local circulation. This is an unbacked mint on the destination chain / direct theft of bridge-custodied value, reachable from a single unprivileged `send` extrinsic plus a single unprivileged `pallet_assets::set_metadata` call by the asset owner.

### Likelihood Explanation
Likelihood is high wherever the bridge registers assets whose `Owner` (per `pallet-assets`) is not locked/burned or otherwise still controlled by an untrusted party after registration — a common situation for permissionlessly created assets later approved for cross-chain bridging by governance. No collusion with `CreateOrigin`/governance is required beyond the one-time registration approval; all subsequent exploitation steps (`set_metadata`, `send`) are executable by an ordinary token owner.

### Recommendation
Snapshot and store the local decimals at `register_token`/`update_token` time (alongside `Precisions`) instead of re-reading `fungibles::metadata::Inspect::decimals()` live in `send()`/`on_accept`. Alternatively, re-validate at every `send()` call that the live decimals still satisfy `erc_decimals >= decimals` and match the value recorded at registration, rejecting the transfer (or requiring a governance-gated `update_token` call) if the asset's decimals metadata has drifted since registration.

### Proof of Concept
1. Attacker creates a `pallet-assets` asset `X` with `decimals = 6`, becoming its `Owner`.
2. Governance/`CreateOrigin` calls `register_token` for asset `X`, with `chains[Evm(1)].decimals = 18` (passes the `18 >= 6` check in `modules/pallets/hyper-fungible-token/src/lib.rs:352-355`).
3. Attacker calls `pallet_assets::set_metadata(X, decimals = 0)` — permitted since the attacker is the asset `Owner`; this does not touch or rescale any account balances.
4. Attacker calls `HyperFungibleToken::send` with `asset_id = X`, `amount = 1_000000` (raw units, i.e. "1.000000" token at the original 6-decimal display). `send()` burns exactly `1_000000` raw units from the attacker (`modules/pallets/hyper-fungible-token/src/lib.rs:278-286`), then computes `decimals = Inspect::decimals(X) = 0` (line 287-289) and `erc20_amount = convert_to_erc20(1_000000, 18, 0) = 1_000000 * 10^18` (`modules/pallets/hyper-fungible-token/src/impls.rs:57-59`) — instead of the correct `1_000000 * 10^12`.
5. The destination `HyperFungibleToken`/`WrappedHyperFungibleToken` EVM contract mints `erc20_amount` to the recipient upon message delivery, resulting in a mint 1,000,000x larger than the value actually burned on the source chain.

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
