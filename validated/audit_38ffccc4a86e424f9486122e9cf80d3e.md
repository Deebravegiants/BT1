This confirms the claim exactly as described. There is no dedup/uniqueness check anywhere in `ProcessRequest` (`core/services/gateway/gateway.go`) or `HandleLegacyUserMessage` before writing to `h.savedCallbacks`, and `MessageID` is entirely attacker-controlled (only length and null-byte suffix are validated in `Message.Validate()`). The signature binds `MessageID` to the sender's identity for authenticity of that particular message, but does nothing to prevent two different senders from independently choosing the same `MessageID` string, since there is no cross-request uniqueness enforcement.

Audit Report

## Title
Global `savedCallbacks` map keyed only by client-supplied `MessageID` allows one user to overwrite/hijack another user's pending gateway callback - ([File: core/services/gateway/handlers/capabilities/handler.go])

## Summary
The legacy WebAPI gateway `handler` stores pending user callbacks in a single, DON-wide map `savedCallbacks map[string]*savedCallback` keyed purely by the caller-supplied `MessageID`. `HandleLegacyUserMessage` writes into this map unconditionally with no uniqueness or ownership check, so a colliding `MessageID` from a different, unprivileged caller silently overwrites another in-flight caller's saved callback, causing that caller's response to be dropped or misdelivered.

## Finding Description
`HandleLegacyUserMessage` stores the callback with `h.savedCallbacks[msg.Body.MessageID] = &savedCallback{...}` with no existence check beforehand: [1](#0-0) . `Message.Validate()` only checks length bounds and a trailing null byte on `MessageID`, never per-sender or global uniqueness: [2](#0-1) . The signature computed over `MessageID`/`Method`/`DonID`/`Receiver`/`Payload` in `GetRawMessageBody` authenticates that a specific sender authored that specific message, but it does nothing to prevent a second, independent sender from choosing (or by chance colliding with) the exact same `MessageID` value while an earlier request is still in flight [3](#0-2) .

The gateway's top-level dispatcher, `ProcessRequest` in `core/services/gateway/gateway.go`, performs no request-ID deduplication before calling `HandleLegacyUserMessage`; it only validates the message and routes it to the handler for the specified DON: [4](#0-3) .

When a node later responds, `handleWebAPITriggerMessage` looks up and deletes `h.savedCallbacks[msg.Body.MessageID]` unconditionally and delivers the response to whichever callback is currently registered under that key: [5](#0-4) . If that key was overwritten by a second request between submission and response, the original caller's callback is silently discarded and never resolved (until the 120-second `CallbackMaxAgeSec` timeout expires the caller's HTTP request), while the second caller's callback receives the (first) node's response for the wrong request.

This is a real behavioral gap relative to the newer, hardened handlers in the same package tree, which explicitly detect and reject a duplicate/in-flight request ID rather than silently overwriting — e.g. the v2 HTTP trigger handler's `"in-flight request"`/`ErrConflict` rejection, the vault handler's `"request was already authorized previously"` rejection, and the confidential relay handler's `"request ID already exists"` rejection. No equivalent check exists in the legacy `capabilities` handler for `MethodWebAPITrigger`/`MethodWebAPITarget`/`MethodComputeAction`/`MethodWorkflowSyncer`.

## Impact Explanation
This is an in-scope gateway request/response impersonation and cross-user response corruption issue. An unprivileged client can cause another legitimate concurrent user's in-flight legacy WebAPI trigger request to be silently orphaned (denial of service on a per-request basis, resolved only via the callback timeout), or — in a race — cause the DON node's response intended for one user to be delivered to a different user's callback. This does not leak secrets (unlike the vault handler, which correctly scopes IDs), but it does break the assumption that a caller's own submitted request will receive its own response.

## Likelihood Explanation
Exploitation only requires submitting two legacy gateway messages with the same `MessageID` while the first is still within the 120-second default `CallbackMaxAgeSec` window [6](#0-5) . Since `MessageID` is fully attacker-chosen and unauthenticated against uniqueness, this is trivial to trigger deliberately, and plausible as an accidental self-inflicted collision for clients using low-entropy or sequential ID schemes. No special role or credential beyond normal unprivileged access to the gateway's user-facing HTTP endpoint is required.

## Recommendation
Scope `savedCallbacks` keys by sender identity in addition to `MessageID` (e.g., `sender + "/" + MessageID`), and/or have `HandleLegacyUserMessage` reject requests whose `MessageID` already has a live, non-expired entry, mirroring the duplicate-ID rejection already implemented in the v2 HTTP trigger handler, vault handler, and confidential relay handler.

## Proof of Concept
1. Send a legacy gateway JSON-RPC request to `ProcessRequest` with `method = "web_api_trigger"`, `don_id = <target-don>`, and `message_id = "X"`, signed by key A. This registers `savedCallbacks["X"]` with caller A's callback via `HandleLegacyUserMessage`.
2. Before the DON responds, send a second legacy request with `message_id = "X"` signed by a different key B for the same `don_id`. This overwrites `savedCallbacks["X"]` with caller B's callback, per `handler.go` line 412.
3. When the DON node eventually responds for `MessageID = "X"`, `handleWebAPITriggerMessage` looks up and deletes `savedCallbacks["X"]`, finding only B's callback, and delivers the response to B — A's HTTP request is left hanging until the callback/context times out. A unit test extending `handler_test.go` that calls `HandleLegacyUserMessage` twice with the same `MessageID` from two different callbacks, then triggers `HandleNodeMessage` once, and asserts that only one callback receives a response while the other times out, would demonstrate this concretely.
