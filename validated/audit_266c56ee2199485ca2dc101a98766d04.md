The documentation explicitly states that `Registry.process` "will verify the request did indeed come from Shopify" [1](#0-0)  and that the `shop` field on `WebhookMetadata` is "The shop domain of the webhook" [2](#0-1) , implying it is a verified/trusted identity value returned by this gem's own verification step, not raw unauthenticated input.

This confirms the finding is a genuine analog to the report's bug class: a field acted upon (`shop`) is not covered by the cryptographic binding (HMAC), while the gem claims/implies the request has been verified as authentic.

### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's authenticity solely via `Utils::HmacValidator.validate(request)`, which HMACs only the raw body bytes [3](#0-2) . The `shop`, `topic`, `webhook_id`, and `api_version` values used downstream by application handlers are read directly from HTTP headers and are never included in the signed content [4](#0-3) . `Registry.process` then dispatches the handler using these unauthenticated header values as if they were verified [5](#0-4) .

### Finding Description
`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string`, and for webhook `Request` objects, `to_signable_string` returns only `@raw_body` [3](#0-2) . Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from the `shopify-*`/`x-shopify-*` HTTP headers with no cryptographic binding to the signature [4](#0-3) .

`Registry.process` performs exactly one authenticity check — the body HMAC — then immediately trusts `request.topic` (for handler routing) and `request.shop` (forwarded into `WebhookMetadata` given to the app's handler) without any further verification [5](#0-4) . This is the binding equality that breaks: the gem implies `verified_hmac_body == authentic_from_shop_X`, but in reality only `verified_hmac_body == authentic_body_bytes`; the `shop` claim is a separate, unauthenticated identity field asserted by the header alone.

Because a merchant who has legitimately installed the app can trigger real webhooks for their own store (e.g., by creating an order with attacker-controlled content), they possess a body + valid HMAC pair signed with the app's shared `api_secret_key`. Since the secret is shared across all shops for a given app (not shop-specific), this same valid `(body, hmac)` pair remains valid regardless of which `shop-domain` header accompanies it. An attacker who controls the raw HTTP request to the app's webhook endpoint (e.g., via a proxy, replay tooling, or a modified webhook forwarder) can therefore submit the legitimately-signed body together with a forged `x-shopify-shop-domain` header naming a different, victim shop. `HmacValidator.validate` will still pass, because it never looks at the header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event is `from` the victim shop [6](#0-5) .

### Impact Explanation
This breaks the tenant isolation the documentation promises ("verify the request did indeed come from Shopify" [1](#0-0)  and `shop` being "the shop domain of the webhook" [2](#0-1) ). A host application that reasonably relies on `data.shop` from a `handle` callback as an authenticated tenant identifier (as shown in the gem's own documented example, which forwards `data.shop` directly into job processing [7](#0-6) ) can be made to attribute attacker-supplied webhook data (order contents, product data, etc.) to an arbitrary victim shop, resulting in cross-tenant data injection/confusion — data intended for one merchant's records ends up processed under another merchant's identity.

### Likelihood Explanation
Exploitation requires only: (1) the attacker be a legitimate but unprivileged user of the app on their own shop, able to trigger webhook deliveries with content they control, and (2) the attacker being able to submit a raw HTTP request to the app's public webhook endpoint with a modified `shop-domain` header while keeping the original signed body (this only requires network-level request manipulation, not any secret material). No access token, `client_secret`, or privileged credential is required — the gem's own signature-checking logic simply never binds `shop` to the signature.

### Recommendation
`HmacValidator`/`Request#to_signable_string` should include the identity-bearing header values (`shop`, `topic`, `webhook_id`, `api_version`) in the signed content, or `Registry.process` should independently verify that the `shop-domain` header corresponds to a shop the app has an active registration/session for that specific webhook subscription, rather than trusting the header value implicitly once the body-only HMAC succeeds.

### Proof of Concept
1. App merchant A installs the app on `shop-a.myshopify.com` and configures a webhook (e.g., `orders/create`).
2. Merchant A creates an order with attacker-chosen content, causing Shopify to deliver a webhook: body `B` with header `x-shopify-shop-domain: shop-a.myshopify.com` and a valid `x-shopify-hmac-sha256` computed over `B` using the app's shared `api_secret_key`.
3. Attacker (also merchant A, or an intermediary who can manipulate the request en route to the app's endpoint) resubmits the exact same body `B` and HMAC header to the app's webhook endpoint, but replaces `x-shopify-shop-domain` with `shop-victim.myshopify.com`.
4. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over `B` only, which matches — validation succeeds.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` builds `WebhookMetadata` with `shop: "shop-victim.myshopify.com"` and calls the app's handler, which processes attacker-controlled order data as though it originated from `shop-victim`, per the documented handler contract in `docs/usage/webhooks.md`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
