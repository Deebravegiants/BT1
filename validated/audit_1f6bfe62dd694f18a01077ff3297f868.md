## Title
Webhook shop/topic identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw request body alone, while the `shop`, `topic`, `webhook_id`, and `api_version` fields are read directly from unauthenticated HTTP headers. `Registry.process` trusts these header-derived values and forwards them to the app's handler as if they were verified, breaking the binding `shop authenticated == shop attributed to the webhook`.

### Finding Description
`Request#hmac` and `Request#to_signable_string` only cover `@raw_body`: [1](#0-0) [2](#0-1) [3](#0-2) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from headers with no cryptographic binding to the signed body: [4](#0-3) 

`Utils::HmacValidator.validate` verifies only `verifiable_query.to_signable_string` (i.e., the body) against `verifiable_query.hmac`: [5](#0-4) 

`Registry.process` treats the HMAC check as authenticating the whole request, then forwards the *unverified* `request.shop` and `request.topic` to the app's handler as trusted identity metadata: [6](#0-5) 

Because a Shopify app's `api_secret_key` (the HMAC key) is a single per-app client secret shared across every shop that installs the app — not a per-shop secret — any unprivileged user can install the public app on their own store and thereby obtain a body+HMAC pair that is valid under the app's global secret. Nothing in `Request` or `HmacValidator` binds that HMAC to the specific shop or topic that produced it, so the pair can be replayed against the app's webhook endpoint with the `X-Shopify-Shop-Domain` / `X-Shopify-Topic` headers changed to claim any other tenant or event type, and `HmacValidator.validate` will still return `true`.

**Binding broken:** `shop authenticated by HMAC == shop the app attributes the webhook to`. Before the attack these are equal (Shopify sets both consistently); after a forged replay, the HMAC still validates for the attacker's captured body while the `shop`/`topic` header values are attacker-controlled and unequal to the shop/topic that actually produced that body.

### Impact Explanation
This crosses the tenant boundary the gem is responsible for: `WebhookMetadata#shop` is the value application code uses to decide *which merchant's* data the webhook event refers to (see `RegistryTest`, which asserts `data.shop` equals the header value). An attacker who legitimately installs the app on their own store can produce a validly-signed webhook body and relabel it as belonging to a victim shop, or relabel a benign topic's body as a security-sensitive topic (e.g., `shop/redact`, `customers/data_request`), causing the host app to act on the wrong tenant's data under an apparently-authenticated event. This matches the High-severity category "credential leakage / cross-tenant access" carried purely through this gem's own verification primitive.

### Likelihood Explanation
Any user can become an "unprivileged internet user" with respect to this boundary simply by installing the target app on a store they control (a normal, unprivileged action for any public Shopify app), which lets them harvest one or more legitimately-signed `(raw_body, hmac)` pairs under the app's shared secret. No access token, `client_secret`, or privileged account is required — only the ability to trigger or receive a webhook on their own shop and replay it with modified headers.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, and ideally `webhook_id`/`api_version`) in the signed material, or independently verify that `request.shop` matches a shop the app has an active session/installation for and that `request.topic` is consistent with the payload shape, before dispatching to `WebhookMetadata`/handlers. At minimum, document that `shop`/`topic` are unauthenticated and must not be used as sole tenant-routing keys.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a normal, unprivileged install).
2. Shopify sends the attacker a legitimate webhook: body `B`, headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: customers/data_request`, `X-Shopify-Hmac-Sha256: H` (computed over `B` using the app's single, shared `api_secret_key`).
3. Attacker replays `POST` to the app's webhook endpoint with the same body `B` and `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds successfully; `Utils::HmacValidator.validate` recomputes HMAC over `B` only and it matches `H` [7](#0-6) .
5. `Registry.process` calls the handler with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: ..., ...)` [8](#0-7) , causing the app to process an attacker-fabricated event as if it originated from `victim-shop.myshopify.com`.
