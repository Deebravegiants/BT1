I found this: `place_bid` in `pallet-intents-coprocessor` is a permissionless extrinsic, callable by anyone with a signed origin, and it stores a bid marker in the `Bids` double-map keyed by `(commitment, filler)` with no cap on the number of distinct fillers (accounts) that can bid on a single commitment.

### Title
Unbounded `Bids` StorageDoubleMap per commitment lets an attacker degrade order/price discovery for a commitment via mass `place_bid` spam - (File: modules/pallets/intents-coprocessor/src/lib.rs)

### Summary
`pallet_intents_coprocessor::place_bid` [1](#0-0)  lets any signed account place a bid on any commitment (including one it made up) by reserving a small, governance-set deposit. There is no limit on how many distinct filler accounts can bid on the same commitment, and no requirement that the commitment correspond to a real order. This differs from the reported Factory pool-array pattern only in shape (growth is per-`(commitment, filler)` map entries rather than a single array), but the underlying bug class — unbounded, permissionlessly-grown state keyed by attacker-controlled input, later enumerated by downstream consumers — is the same.

### Finding Description
`place_bid` validates only that `user_op` is non-empty and that the caller can reserve the (governance-configured) `StorageDepositFee`; it does not check that `commitment` refers to a real, still-open order except in the phantom-order branch, which only tightens rules for `CurrentPhantomOrder` entries and is a no-op check for any commitment that isn't the active phantom order [2](#0-1) . An attacker can therefore create unlimited distinct signer accounts and call `place_bid` with the same (possibly bogus) commitment from each one, each such call inserting a new `(commitment, filler)` entry into the `Bids` StorageDoubleMap [3](#0-2) , with the deposit amount coming from `StorageDepositFee`, which is a governance-tunable value that can be arbitrarily low.

Every place that needs "the bids for a commitment" enumerates this map without a bound: the RPC handler `get_bids_for_order` iterates raw storage keys under the commitment's prefix and caps only the *on-chain* portion at `MAX_ON_CHAIN_BIDS = 30` [4](#0-3) , but that cap only limits how many of the (potentially huge) key set the RPC will *read into the response* — it still calls `storage_keys` unbounded and pays that iteration cost. More importantly, the SDK's `getBidsViaStorage` fallback path calls `api.query.intentsCoprocessor.bids.entries(commitment)` and then issues one offchain-storage lookup per entry with `Promise.all` [5](#0-4) , so a bidder-count blow-up on one commitment directly inflates the work (and dies slowly instead of failing fast) for anyone — an intent user, a solver's `BidManager.selectAndExecuteBest` [6](#0-5) , or the indexer's `aggregatePhantomBids` pipeline that fetches every bid for a commitment during phantom price-snapshot processing [7](#0-6)  — trying to resolve bids for that commitment.

### Impact Explanation
This does not directly cause theft or forged delivery, but it is a route-availability degradation: an unprivileged attacker can make bid discovery for a specific order commitment arbitrarily expensive/slow for solvers and users (and for the indexer's price-snapshot pipeline), which can cause a real order's genuine bids to be effectively undiscoverable within its fill/auction window (`auctionTimeMs`), functionally freezing that order's ability to be filled by anyone using the standard SDK path. Given the low, governance-set deposit floor and no per-commitment or per-account rate limit, the cost of mounting this is cheap relative to the damage to a specific victim order.

### Likelihood Explanation
Likelihood is limited by the need to pay `StorageDepositFee` per bid and per signer account, and by governance's ability to raise that fee; however, since the fee is explicitly described as adjustable and no cap exists on distinct fillers per commitment, a well-resourced attacker (or one targeting a specific high-value order) can trivially mount this at low cost. The `place_bid` extrinsic is fully permissionless and requires no relayer, proof, or governance action — the weakest possible reachability bar.

### Recommendation
Add an explicit cap on the number of distinct fillers/bids allowed per commitment in `pallet_intents_coprocessor::place_bid` (mirroring the `MAX_SUBSCRIPTIONS`/eviction pattern already used in `pallet-bandwidth`), and/or require the commitment to correspond to a currently-open, known order (not just the active phantom order) before accepting a bid. Additionally, make the RPC's `storage_keys` prefix scan itself bounded (not just the response), and make the SDK's `getBidsViaStorage` fallback bound how many entries it will resolve per commitment rather than issuing unbounded parallel offchain lookups.

### Proof of Concept
1. Generate N signer accounts, each funded with at least `StorageDepositFee`.
2. From each account, call `intentsCoprocessor.placeBid(commitment, userOp)` with the same target `commitment` (an arbitrary or real order's commitment) and arbitrary non-empty `userOp` bytes — this passes validation since only the phantom-order branch requires the commitment to be a real, currently-active phantom order [2](#0-1) .
3. Each call inserts a distinct `(commitment, filler)` entry into `Bids` with no upper bound [8](#0-7) .
4. Any caller resolving bids for that commitment via `getBidsForOrder`/`getBidsViaStorage` now pays O(N) offchain-storage round trips [5](#0-4) , or the RPC pays an unbounded `storage_keys` prefix scan [4](#0-3) , degrading or starving legitimate bid discovery for that specific order within its auction window.

		#[pallet::call_index(0)]
		#[pallet::weight(T::WeightInfo::place_bid())]
		pub fn place_bid(
			origin: OriginFor<T>,
			commitment: H256,
			user_op: BoundedVec<u8, ConstU32<1_048_576>>,
		) -> DispatchResult {
			let filler = ensure_signed(origin)?;

			// Validate user_op is not empty
			ensure!(!user_op.is_empty(), Error::<T>::InvalidUserOp);

			// Phantom orders have stricter rules: one bid per filler, no updates, and only
			// within the configured acceptance window after the order was registered. Every
			// chain's active order is checked, not just the most recently generated one.
			if let Some(active) = CurrentPhantomOrder::<T>::get() {
				if let Some((_, info)) = active.iter().find(|(c, _)| *c == commitment) {
					let window: BlockNumberFor<T> = Self::phantom_bid_window().into();
					ensure!(
						frame_system::Pallet::<T>::block_number() <= info.created_at_block + window,
						Error::<T>::PhantomOrderBidWindowClosed
					);
					ensure!(
						!Bids::<T>::contains_key(&commitment, &filler),
						Error::<T>::DuplicatePhantomBid
					);
				}
			}

			// If a bid already exists, unreserve the old deposit first
			if let Some(old_deposit) = Bids::<T>::get(&commitment, &filler) {
				<T as Config>::Currency::unreserve(&filler, old_deposit);
			}

			let deposit = Self::storage_deposit_fee();

			// Reserve the new deposit
			<T as Config>::Currency::reserve(&filler, deposit)
				.map_err(|_| Error::<T>::InsufficientBalance)?;

			// Store the bid in offchain storage
			let bid = Bid { filler: filler.clone(), user_op: user_op.to_vec() };
			let offchain_key = Self::offchain_bid_key(&commitment, &filler);
			offchain_index::set(&offchain_key, &bid.encode());

			// Store deposit amount in onchain storage for discoverability and accurate refunds
			Bids::<T>::insert(&commitment, &filler, deposit);

			Self::deposit_event(Event::BidPlaced { filler, commitment, deposit });

			Ok(())
		}

	private async getBidsViaStorage(commitment: HexString): Promise<FillerBid[]> {
		const api = await this.http()
		// eslint-disable-next-line @typescript-eslint/no-explicit-any
		const entries = await (api.query.intentsCoprocessor.bids as any).entries(commitment)

		if (entries.length === 0) return []

		const bidPromises = entries.map(async ([storageKey, depositValue]: [any, any]) => {
			try {
				const filler = storageKey.args[1].toString()
				const deposit = BigInt(depositValue.toString())

				const offchainKey = this.buildOffchainBidKey(commitment, filler)
				const offchainKeyHex = u8aToHex(offchainKey)

				const offchainResult = await api.rpc.offchain.localStorageGet("PERSISTENT", offchainKeyHex)

				if (!offchainResult || offchainResult.isNone) return null

				const bidData = offchainResult.unwrap().toHex() as HexString
				const decoded = this.decodeBid(bidData)

				return { filler: decoded.filler, userOp: decoded.userOp, deposit }
			} catch {
				return null
			}
		})

		const results = await Promise.all(bidPromises)
		return results.filter((b): b is FillerBid => b !== null)
