### Title
Excess native ETH sent to `EvmHost.dispatch()` / `fundRequest()` is refunded to the Host contract instead of the caller and becomes permanently stuck - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all forward `msg.value` directly to `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)` without ever capturing the router's returned `amounts[0]` (actual ETH spent) or reconciling/refunding the difference to the original caller.

### Finding Description
In `evm/src/core/EvmHost.sol`, all three payable entry points that accept native-token payment for dispatch fees follow the same pattern: [1](#0-0) [2](#0-1) [3](#0-2) 

The standard `UniswapV2Router02.swapETHForExactTokens` implementation only requires `amounts[0] <= msg.value` and refunds any unspent ETH (`msg.value - amounts[0]`) via `TransferHelper.safeTransferETH(msg.sender, ...)`. Since `EvmHost` itself is the direct caller of the router (not the original transaction sender), that refund lands back on the `EvmHost` contract's own balance — not on `_msgSender()` who actually paid the overpaid `msg.value`. `EvmHost` never checks the router's return value or forwards any surplus back to the caller.

This is the exact bug class described in the report: `totalFee`-equivalent (here, the token amount needed for the swap) is computed/consumed, but any ETH sent beyond what's strictly required remains trapped in the contract with no path back to the user.

Notably, other parts of the same codebase correctly handle this pattern by capturing the swap's spent amount and refunding the difference to `msg.sender`, e.g. `IntentGatewayV2.placeOrder` and `ExtrinsicIntents`: [4](#0-3) 

This shows the fix pattern is known and used elsewhere in the same repo, but is missing from `EvmHost.sol`'s three dispatch-fee-paying functions.

### Impact Explanation
Any unprivileged user or application calling `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, or `fundRequest()` with native ETH slightly in excess of the exact swap cost — which is the normal, expected usage pattern since exact fee amounts fluctuate with AMM price and are estimated off-chain (the docs explicitly warn against on-chain `quote()` calls and recommend a buffer, e.g. the LZ endpoint code applies a 2x buffer) — will permanently lose the excess ETH. It becomes locked in `EvmHost`'s native balance. I was unable to fully confirm during this review whether `EvmHost.sol` contains any function capable of sweeping raw native ETH balance (a `function withdraw` grep hit 4 matches in the file that I did not get to inspect in detail before the session ended); however, even if such a function exists, it is governance-only and intended for protocol fee-token revenue withdrawal per the `hostManager` documentation, not a mechanism to return the specific overpaid amount to the specific affected user. In either case, the individual user's excess funds are not recoverable by that user.

Given that `dispatch`/`fundRequest` are the core message-dispatch entry points used across essentially every app built on Hyperbridge (documented as the standard "Native Token Payment" pattern for POST/GET requests), this is a broadly reachable, unprivileged loss-of-funds bug affecting any caller who overpays even slightly.

### Likelihood Explanation
High. Native-fee overpayment is the documented, encouraged usage pattern (fee estimation is explicitly stated to be approximate/off-chain and buffered), so essentially every native-fee dispatch transaction with any margin above the exact AMM-determined cost triggers fund loss. No special conditions, privileges, or attacker action are required — a normal user transaction is sufficient.

### Recommendation
In `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, capture the `amounts` array returned by `swapETHForExactTokens` and refund any unspent native ETH back to `_msgSender()`, mirroring the pattern already used in `IntentGatewayV2.placeOrder`:

```solidity
uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
if (msg.value > amounts[0]) {
    (bool sent, ) = _msgSender().call{value: msg.value - amounts[0]}("");
    if (!sent) revert FailedToSendETH(msg.value - amounts[0]);
}
```

### Proof of Concept
1. User calls `EvmHost.dispatch{value: X}(post)` where `X` is intentionally padded above the exact ETH needed to swap for `post.fee` in `feeToken` (as recommended by the protocol's own documentation, which advises buffering estimates since on-chain quoting is unsafe).
2. `EvmHost.dispatch` forwards the full `X` to `swapETHForExactTokens{value: X}(post.fee, path, address(this), block.timestamp)`.
3. The Uniswap router spends only `amounts[0] < X` and refunds `X - amounts[0]` via `safeTransferETH(msg.sender, ...)`, where `msg.sender` from the router's perspective is `EvmHost` itself.
4. `EvmHost.dispatch` returns normally; the surplus ETH now sits in `EvmHost`'s balance, and the calling user has no recorded claim or refund path for it. [1](#0-0)
