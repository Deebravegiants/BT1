## Title
Webhook Cross-Tenant Shop Spoofing via HMAC Scope Gap (Shop Header Not Covered by Signature) - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then trusts the `shop` value taken from the `x-shopify-shop-domain` HTTP header — a field that is never included in the HMAC-signed payload — when dispatching the event to the app's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are all derived from HTTP headers that sit entirely outside the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e., the raw body only) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` gates on that HMAC check and then immediately forwards `request.shop` — unverified — to the app's webhook handler as the tenant identity for the event: [4](#0-3) 

The identity binding that is broken:
`HMAC-verified bytes (raw body)` ≠ `shop identity acted upon (x-shopify-shop-domain header)`.

The library validates "the bytes are unmodified" but silently substitutes that guarantee for "the shop is authentic," even though the shop domain header is never part of what was actually verified.

### Impact Explanation
Any actor who can legitimately trigger a webhook delivery for **their own shop** (e.g., a merchant installing the app on a store they control and performing an action that fires a webhook, such as creating an order) obtains a `(raw_body, hmac-sha256)` pair that Shopify has validly signed with the app's shared `client_secret`. Because the shop-domain header is not part of the signed material, that attacker can replay the exact same body/HMAC pair to the app's webhook endpoint while substituting a different `x-shopify-shop-domain` header pointing at a victim merchant's shop.

Downstream, `Registry.process` builds `WebhookMetadata.new(shop: request.shop, ...)` and hands it to the app's handler with the attacker-controlled shop value now treated as authentic. Any app logic that looks up sessions, tenant-scoped data, or store state keyed by this `shop` value will act on the victim's tenant using attacker-supplied content — a cross-tenant data/action confusion driven purely by an unauthenticated header value riding along with a validly-signed body.

This satisfies the Critical criterion of cross-tenant access: the shop identity boundary that the rest of the library (and app authors) rely on the HMAC to guarantee is not actually enforced for the field that matters (`shop`).

### Likelihood Explanation
Any user able to install the app on a store (a standard, unprivileged capability for anyone who can create a development/test store or become a merchant using the app) can generate valid `(body, hmac)` pairs for their own shop at will and then relay them with a forged shop header to the app's public webhook endpoint. No access to `api_secret_key`, tokens, or any privileged credential is required — only the ability to receive one's own legitimate webhook and resend it with a modified header, which is trivial HTTP tooling.

### Recommendation
Bind the shop identity into the material that is actually verified. At minimum, include the `x-shopify-shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) header values in the signable string alongside the raw body inside `ShopifyAPI::Webhooks::Request#to_signable_string`/`HmacValidator`, or have `Registry.process` independently cross-check that the shop asserted by the header corresponds to a session/store this specific webhook subscription was registered for, rather than trusting the header outright once the body-only HMAC passes.

### Proof of Concept
1. Install/operate the app on `attacker-shop.myshopify.com` and trigger a real webhook (e.g., `orders/create`) so Shopify sends a validly HMAC-signed request:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid-hmac-of-body>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   Body: {"id": 1, "note": "malicious payload"}
   ```
2. Capture the raw body and the `x-shopify-hmac-sha256` value.
3. Replay the identical body and HMAC header to the app's webhook endpoint, but replace the shop header:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <same-valid-hmac-of-body>
   x-shopify-shop-domain: victim-shop.myshopify.com
   Body: {"id": 1, "note": "malicious payload"}
   ```
4. `Utils::HmacValidator.validate` passes because it only checks the (unchanged) body against the (unchanged) HMAC, per `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/utils/hmac_validator.rb:26-31`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the app's handler with `shop: "victim-shop.myshopify.com"`, causing the app to process attacker-controlled data under the victim tenant's identity.
