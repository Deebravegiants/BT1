### Title
Webhook `shop`, `topic`, and `webhook_id` fields are trusted by the app handler without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw HTTP body alone, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers that are never part of the signed material. [1](#0-0)  `Registry.process` validates only that the body's HMAC matches, then hands `request.shop`, `request.topic`, and `request.webhook_id` straight to the app's handler as trusted tenant/routing identifiers. [2](#0-1)  This breaks the intended binding: `HMAC-verified bytes == raw_body` but the values the handler actually acts on (`shop`, `topic`, `webhook_id`) are *not* the verified bytes.

### Finding Description
`Request#hmac` and `#to_signable_string` are defined as:

```ruby
def hmac
  Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
end

def to_signable_string
  @raw_body
end
``` [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read from headers via `shopify_header`, completely outside the signed payload:
```ruby
def topic
  T.cast(shopify_header("topic"), String)
end

def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [3](#0-2) 

`Utils::HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (i.e. the raw body) and compares it to the `hmac-sha256` header value:
```ruby
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [4](#0-3) 

`Registry.process` gates on this HMAC check and then forwards the *header-derived* `shop`/`topic`/`webhook_id`/`api_version` to the app-supplied handler, unauthenticated:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [2](#0-1) 

The gem's own documentation confirms apps are expected to use `data.shop` as the tenant key for downstream logic (e.g. enqueueing per-shop jobs), i.e. `shop` is treated as an authenticated tenant identifier:
```ruby
def handle(data:)
  puts "... shop: #{data.shop} ..."
  perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
end
``` [5](#0-4) 

**The binding that should hold:** `HMAC-verified(secret, bytes) == bytes-that-determine-shop/topic-attribution`. Instead, the gem enforces `HMAC-verified(secret, raw_body) == raw_body`, while `shop`/`topic`/`webhook_id`/`api_version` are taken from unauthenticated headers — an equality gap identical in shape to the referenced report, where the amount that was validated (`flashloanRepayAmount <= balance`) was not the same value that was actually transferred (the full balance).

**Exploit path (unprivileged internet user):** Any user can install the target Shopify app as a merchant (this is the normal, unprivileged app-installation flow) and thereby legitimately receive webhooks for their own store, each containing a genuine `raw_body` + valid `hmac-sha256` value signed with the app's real secret. Because the signature never covers the headers, that attacker can capture one such valid `(raw_body, hmac)` pair and replay it against the app's webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a victim shop, and/or the `X-Shopify-Topic` / `X-Shopify-Webhook-Id` headers changed arbitrarily. `Utils::HmacValidator.validate` still passes (it only checks the body), so `Registry.process` dispatches the handler with attacker-chosen `shop`/`topic`/`webhook_id` values that the app will treat as authenticated Shopify-originated data for a tenant the attacker does not control.

### Impact Explanation
This qualifies as **High** severity per the rubric ("a scope or expiry check that answers permissively" / identity-binding bypass): it allows a `Critical`-adjacent cross-tenant confusion — an app that keys any state, deduplication, authorization, or side effects off `data.shop`/`data.topic`/`data.webhook_id` (exactly as the gem's own documentation recommends) can be made to attribute attacker-controlled webhook content to an arbitrary victim shop domain, or to falsely believe a benign topic's payload is actually a sensitive topic (e.g. `app/uninstalled`, `shop/redact`) using a body that was really signed for a different topic. Depending on how the host app dispatches on `topic`/`shop`, this can lead to cross-tenant data corruption, spoofed lifecycle events, or logic bypass — all without any credential leak, purely by observing one legitimately-received webhook.

### Likelihood Explanation
Likelihood is **moderate**: it requires the attacker to have received at least one genuine webhook (trivial for a self-service merchant installing a public app, or via captured logs/network traces) and requires the target endpoint to accept arbitrary headers from the replaying client (true by default for any HTTP endpoint unless the host framework strips/overwrites `X-Shopify-*` headers, which this gem does not require or document). The gem provides no mitigation, nonce/timestamp binding, or documentation warning that `shop`/`topic`/`webhook_id` are unauthenticated, so most integrators relying on the documented usage pattern are exposed.

### Recommendation
Bind the header-derived identifiers into the HMAC-signed material, or otherwise cryptographically/structurally tie them to the verified body:
- Include `shop`, `topic`, and `webhook_id` in the string that is HMAC-verified (this would require Shopify to sign over them too, which isn't currently how Shopify webhooks work — so at minimum the gem should not present these fields as "verified" without a caveat), and/or
- Cross-check `shop` against the body's own shop-identifying content (e.g. `admin_graphql_api_id` / `shop_id` present in most webhook payloads) before trusting it for tenant dispatch, and
- Document explicitly in `docs/usage/webhooks.md` that `data.shop`, `data.topic`, and `data.webhook_id` are **not covered by HMAC verification** and must not be used as sole tenant/authorization keys without additional server-side correlation (e.g. comparing against the shop stored for the currently active session/lookup, replay/nonce tracking of `webhook_id`).

### Proof of Concept
```ruby
# 1. Attacker installs the app for their own store "attacker.myshopify.com"
#    and captures a genuine webhook delivery, e.g. for topic "orders/create":
raw_body = '{"id":123,...}'   # exact bytes Shopify sent
hmac_header = "base64-hmac-signed-with-real-api_secret_key"

# 2. Attacker replays the exact same body/hmac to the same webhook endpoint,
#    but swaps the shop/topic/webhook-id headers:
headers = {
  "x-shopify-topic"        => "app/uninstalled",       # attacker-chosen
  "x-shopify-hmac-sha256"  => hmac_header,              # unchanged, still valid for raw_body
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com", # attacker-chosen
  "x-shopify-webhook-id"   => "attacker-chosen-id",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) succeeds (body untouched),
#    handler.handle is invoked with shop: "victim-shop.myshopify.com",
#    topic: "app/uninstalled", despite none of that being authenticated by Shopify.
