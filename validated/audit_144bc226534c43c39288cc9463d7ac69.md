## Title
Webhook shop attribution is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

## Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop` (tenant) attribute is read directly from an unauthenticated HTTP header. `Registry.process` validates only that signature, then hands the unauthenticated `shop` value straight to the app's webhook handler as the tenant identifier. This breaks the identity binding: `shop authenticated by HMAC == shop the handler acts on`.

## Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`, and `hmac` is read from the `hmac-sha256` header: [1](#0-0) 

`shop` is a plain header value that is never part of the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC (which only covers the body) and then trusts `request.shop`, `request.topic`, etc. wholesale when constructing the metadata passed to the app's handler: [3](#0-2) 

Because Shopify signs webhooks with the app's `client_secret`, which is identical across every shop that has the app installed, a valid HMAC only proves "this body was produced/authorized under this app's secret" — it does **not** prove which shop it came from. An attacker who legitimately installs the target app on their own shop can trigger a real webhook delivery (e.g. via a resource they control), capture the resulting `(raw_body, hmac)` pair signed with the shared secret, and replay it to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header with an arbitrary victim shop domain. `Registry.process` still validates successfully (the body/HMAC pair is genuine), but `request.shop` now reports the attacker-chosen victim domain to the handler.

The gem's own documentation reinforces that host apps are expected to treat a passing `Registry.process` call as proof the request "did indeed come from Shopify" for the shop indicated: [4](#0-3) [5](#0-4) 

This is exactly the "field acted on but not covered by the HMAC" identity-binding gap: `shop` is consumed by the handler but is outside the cryptographically verified scope.

## Impact Explanation
Host applications built on this gem receive `WebhookMetadata` with a `shop` field they are told is authenticated. Many webhook-driven flows key off `data.shop` to select or mutate per-tenant state (e.g. `app/uninstalled` deleting a shop's session, `shop/redact` / `customers/redact` compliance flows, order/product sync writing into the wrong tenant's records). Since `shop` is fully attacker-controllable while the HMAC still verifies, an attacker with nothing more than their own (possibly free/dev) shop installation of the target app can forge webhook events attributed to any victim shop domain they choose, causing cross-tenant data corruption, spurious deletions, or state confusion in the host app. This matches the Critical/High class of "cross-tenant access" via a broken authentication binding.

## Likelihood Explanation
Likelihood is moderate-to-high for any app that: (a) is installable by low-privilege/public users (most public apps), and (b) trusts `data.shop` from `WebhookMetadata` for tenant-scoped side effects, which is exactly the pattern demonstrated in the gem's own usage docs. No special credentials beyond installing the app on an attacker-owned shop are required; the attacker never needs the app's `client_secret` because the HMAC is computed by Shopify's own webhook delivery for the attacker's real installation, and the header substitution happens purely on the replayed HTTP request the attacker sends to the target app's endpoint.

## Recommendation
Include the shop domain (and other identity-relevant headers such as `webhook-id`/`api-version`) in the signed payload verified by `HmacValidator`, or otherwise cross-check `request.shop` against a shop known to have a currently registered webhook subscription/session before dispatching to the handler, rather than trusting the header verbatim once the body HMAC passes.

## Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker.myshopify.com`, obtaining legitimate webhook deliveries signed with the app's shared `client_secret`.
2. Attacker triggers/captures a real webhook delivery, e.g. `POST /callback/orders/create` with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` under `client_secret`), `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker resends the exact same body `B` and `X-Shopify-Hmac-Sha256: H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers, `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only recomputes/compares the HMAC over `@raw_body` — see `to_signable_string` returning `@raw_body`: [6](#0-5) .
5. The handler receives `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: B, ...)` and performs shop-scoped side effects against `victim.myshopify.com`, even though nothing was ever confirmed to originate from that shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
