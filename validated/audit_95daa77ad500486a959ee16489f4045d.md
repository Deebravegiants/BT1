### Title
Unconstrained `op.value` lets any user drain EmporiumUpgradeable's stranded ETH when `address(0)` is omitted from `erc20TokenAddresses` - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction` only enforces ETH balance conservation for token indices that appear in `circomData.erc20TokenAddresses`. Because an attacker fully controls `circomData.erc20TokenAddresses` (it is not required to include `address(0)`), and because the "stateless" op branch requires no signature at all (`verifyWallet` returns immediately when `stack.signerAddress == address(0)`), an attacker can submit a self-funded, otherwise legitimate transact call whose `erc20TokenAddresses` list never mentions ETH, while embedding an `EmporiumOperation` with `op.value` equal to the contract's entire ETH balance and `op.endpoint` pointing at an attacker-controlled sink. The reconciliation loop in `runAction` never touches index `address(0)` in this case, so the drain is never checked and never reverts.

### Finding Description
The equality the contract is supposed to enforce, per token index `i` in `circomData.erc20TokenAddresses`, is:

`balancesAfter[i] - balancesBefore[i] (+ |deltaAmountChanges[i]| if deposit) >= 0` [1](#0-0) 

This check is computed **only** for indices present in `circomData.erc20TokenAddresses`, which is attacker-supplied data decoded straight from `circomData` with no requirement that `address(0)` be included when ETH is present on the contract: [2](#0-1) 

The stateless op branch executes an arbitrary low-level call with attacker-chosen `value` before any of that reconciliation happens: [3](#0-2) 

Crucially, this stateless branch requires no wallet signature — `verifyWallet` only checks/marks `usedMessages` and returns early when `stack.signerAddress == address(0)`: [4](#0-3) 

`EmporiumUpgradeable` also has an unrestricted `receive()` that lets anyone top up its ETH balance (dust from prior partial/rounding operations, refunds from swap routers, or simply accidental/deliberate sends), which becomes the stranded balance `D`: [5](#0-4) 

**Attacker call:** Craft a valid Hinkal `transact` proof for the attacker's own real UTXOs (e.g. depositing/moving some ERC20 token `X`, nothing to do with ETH) with `circomData.erc20TokenAddresses = [X]` (no `address(0)` entry) and `externalActionData.externalActionMetadata` encoding an `EmporiumStack` with `signerAddress = address(0)`, one `EmporiumOperation{ endpoint: attackerContract, invokeWallet: false, value: address(EmporiumUpgradeable).balance, callData: "" }`.

Because `circomData.erc20TokenAddresses` never contains `address(0)`, the reconciliation `for` loop in `runAction` (lines 132–151) never computes `balancesBefore`/`balancesAfter` for ETH, so the entire ETH balance transferred out via `op.endpoint.call{value: op.value}("")` is unchecked and un-reverted. `_calculateDeltaAmount`/`_externalTransact` in `Hinkal.sol` likewise only iterate over the same attacker-controlled `erc20TokenAddresses` array, so no ETH deposit/­accounting entry is ever created or checked for this call either: [6](#0-5) 

Existing guards do not stop this: `performHinkalChecks`/`dimensionsCheck` validate proof/dimension shapes but do not force `address(0)` to be present whenever the Emporium contract holds ETH; the circuit constraints (`inTotal + amountChanges === outTotal`) only bind the declared `erc20TokenAddresses`/`amountChanges`, and `externalActionMetadata` (the `EmporiumStack`/`op.value`/`op.endpoint`) is not constrained by the proof at all — it is free-form calldata decoded on-chain. `BalanceChangeShouldBePositive` can only fire for indices actually iterated, so an omitted index is a silent bypass, not a guarded path.

### Impact Explanation
Any unprivileged user can permanently steal all ETH balance sitting in `EmporiumUpgradeable` at the time of their call — this is protocol/relay/other-users' stranded ETH, not the attacker's own funds. This qualifies as High severity ("theft or permanent freezing of protocol/relay fees" / theft of funds not backed by the attacker's own deposit) since the attacker moves value out of Hinkal's external-action contract that was never accounted to them. The attack is fully repeatable any time `address(this).balance > 0` on `EmporiumUpgradeable`, and costs only gas plus the cost of a trivial, self-owned proof for an unrelated token.

### Likelihood Explanation
Preconditions: `EmporiumUpgradeable` must hold nonzero ETH (trivial to create — the attacker or any third party can send ETH directly via `receive()`, or dust can accumulate from normal swap/rounding operations). No special role, signer, or victim cooperation is required; `stack.signerAddress = address(0)` deliberately skips signature verification for the "no wallet" stateless path, and `usedMessages` only prevents replay of the exact same `emporiumMessage`, not different messages. The attacker needs only a single valid proof for their own UTXOs on an unrelated token, which is fully within an unprivileged user's capability. This makes the exploit highly feasible and repeatable across every block where Emporium holds residual ETH.

### Recommendation
Do not rely on the caller-supplied `erc20TokenAddresses` array to decide which tokens get balance-conservation checks. Instead, either (a) always additionally snapshot and verify `address(0)` balance in `EmporiumUpgradeable.runAction` regardless of whether it appears in `circomData.erc20TokenAddresses`, ensuring `address(this).balance` never decreases below its pre-call value unless justified by a declared negative `deltaAmountChanges` entry for ETH; or (b) require `circomData.erc20TokenAddresses` to include `address(0)` whenever any `EmporiumOperation.value > 0` is present, enforced on-chain before executing ops; or (c) bound the sum of all `op.value` in the stack to `sum(|deltaAmountChanges[i]| for erc20TokenAddresses[i] == address(0))` before executing any op, reverting otherwise.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable` (as a registered external action, `allowedRecipients` including Hinkal), and a minimal ERC20 `X`.
2. Send ETH directly to `EmporiumUpgradeable` via `receive()` (or run one legitimate Emporium swap op that leaves rounding dust) to establish `D = address(emporium).balance > 0`.
3. Assert `address(emporium).balance == D`.
4. Deploy `AttackerSink` contract with a `receive()`.
5. Generate a valid Hinkal proof/`CircomData` for the attacker's own UTXO of token `X` only (`erc20TokenAddresses = [address(X)]`), with `externalActionData.externalActionMetadata` ABI-encoding an `EmporiumStack{ signerAddress: address(0), ops: [EmporiumOperation{ endpoint: address(attackerSink), invokeWallet: false, value: D, callData: "" }] }`.
6. Call `Hinkal.transact(...)`.
7. Assert: `address(emporium).balance == 0` and `address(attackerSink).balance == D`, while the `transact` call does **not** revert (no `BalanceChangeShouldBePositive`), proving `D` was drained without any accounting entry, i.e. `balanceChange` for `address(0)` was never computed/checked (`balancesBefore`/`balancesAfter` for ETH is undefined in this call because `address(0) ∉ erc20TokenAddresses`).
