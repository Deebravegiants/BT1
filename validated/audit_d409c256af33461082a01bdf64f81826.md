Based on my review, the core claim is confirmed by the actual code, though the test citation used to support it is from a different file than the vulnerable one.

The `HandleGatewayMessage` function in `core/capabilities/vault/gw_handler.go` does log the entire raw `*jsonrpc.Request[json.RawMessage]` struct at Debug level before any authorization/redaction occurs, and the raw `*jsonrpc.Response[json.RawMessage]` at Info level afterward: [1](#0-0) [2](#0-1) 

The `req` object here is a `jsonrpc.Request[json.RawMessage]`, and other code in the same package treats `req.Auth` as the caller-supplied JWT bearer token used for authorization, e.g. in `authorizer.go` and `jwt_based_auth.go`, both of which deliberately log only `req.Auth != ""` (a boolean) rather than the raw value — demonstrating that the maintainers are aware `Auth` is sensitive and take care to avoid logging it directly elsewhere in the same package: [3](#0-2) [4](#0-3) 

By contrast, `Debugw("received message from gateway", "req", req)` and `Infow("Sent message to gateway", "resp", response)` log the entire struct, and there is no evidence in this codebase of a custom `MarshalJSON`/`String()`/logger-hook redaction mechanism on `jsonrpc.Request`/`jsonrpc.Response` (these types are defined in the external `chainlink-common` module, not vendored into this repo, so I could not directly inspect their marshal behavior, but nothing in the vault package compensates for this).

One caveat: the test cited in the report, `TestVaultHandler_InvalidParamsDoesNotLogRawParams` in `core/services/gateway/handlers/vault/handler_test.go`, belongs to a **different package** — the Gateway-side handler (`core/services/gateway/handlers/vault/handler.go`), not the node-side `core/capabilities/vault/gw_handler.go` that is the actual subject of this claim. That test's comment about "the pre-existing whole-request Debug log" refers to a similar-looking Debug log in the *gateway-side* handler, not the one in `gw_handler.go`. This doesn't invalidate the underlying claim about `gw_handler.go` (which independently and clearly logs the raw request/response, confirmed by direct code read), but the citation linking the test as evidence for maintainer awareness of this specific line is not accurate — it's evidence of the same *pattern* existing in a sibling file, not proof that this exact line was acknowledged.

The core vulnerability claim holds: an unprivileged client sends a normal JWT-authenticated request through the Gateway, and the node's `GatewayHandler.HandleGatewayMessage` will log the full request struct (including `Auth`) at Debug level unconditionally, and the response at Info level. No authorization or redaction step happens before this log line executes. This is a credential-disclosure issue reachable by any caller who can send Gateway/Vault traffic, with impact scoped to node logs — a legitimate, in-scope finding under "key/secret exfiltration" via node log exposure of a bearer credential, contingent on debug logging being enabled (which is a common operational configuration, not an admin-only setting) for the request-side log, though the response-side `Infow` log also exposes result data at default level (though the response itself may not carry `Auth` unless it's echoed back — this is worth noting as a limitation: the `Infow` "Sent message to gateway" logs the *response*, not necessarily the incoming `Auth`, unless jsonrpc.Response also embeds an Auth-carrying request/echo, which I could not confirm from available code).

Audit Report

## Title
Vault Gateway node handler logs full JSON-RPC request/response including the raw JWT bearer `Auth` token at Debug/Info level - (File: core/capabilities/vault/gw_handler.go)

## Summary
`GatewayHandler.HandleGatewayMessage` logs the entire inbound `jsonrpc.Request[json.RawMessage]` (which carries the caller's `Auth` JWT bearer token) via `reqLggr.Debugw("received message from gateway", "req", req)` before any redaction, and logs the full response via `reqLggr.Infow("Sent message to gateway", "resp", response)` afterward. This exposes live bearer credentials in node logs to anyone with log access.

## Finding Description
The Vault capability's node-side gateway handler receives `*jsonrpc.Request[json.RawMessage]` objects forwarded from the Gateway, where the `Auth` field carries the caller's JWT used for authorization (as consumed by `authorizer.go` and `jwt_based_auth.go`). `HandleGatewayMessage` logs this entire struct wholesale at Debug level immediately upon receipt, with no field-level redaction, unlike the careful `hasAuth` boolean pattern used elsewhere in the same package's authorization code. [1](#0-0) [3](#0-2) 

## Impact Explanation
If the log level includes Debug (common in troubleshooting/managed deployments), the full JWT bearer token used to authorize Vault secrets operations (create/update/delete/list) is written to node logs in plaintext. Anyone with log read access (operators, log aggregation pipelines) can extract and replay the token to impersonate the caller for Vault operations, subject to token validity and any replay-guard binding.

## Likelihood Explanation
Triggered by any normal JWT-authenticated Vault request through the Gateway — no malicious input required. Exposure depends on Debug-level logging being enabled for the request-side log line; the response-side Infow logs unconditionally but its exposure of `Auth` specifically is unconfirmed.

## Recommendation
Replace wholesale struct logging with structured, redacted fields (method, requestID, gatewayID, `hasAuth` boolean, response size) — following the existing `hasAuth` pattern already used in `authorizer.go` in the same package.

## Proof of Concept
1. Send a JWT-authenticated `vault.secrets.list` request through the Gateway to a node running the Vault capability with debug logging enabled.
2. Observe `GatewayHandler.HandleGatewayMessage`'s `Debugw("received message from gateway", "req", req)` line emit the full request struct, including `Auth`, to node logs.
3. Extract the JWT from logs and replay it against the Gateway within its validity window.
