### Title
Missing existence-check on `DeleteAccountAction::beneficiary_id` permits unrecoverable burn of an account's balance - (File: `runtime/runtime/src/actions.rs`)

### Summary
`DeleteAccountAction` lets any account owner attach a `beneficiary_id` that receives the deleted account's remaining balance. The action is only validated for well-formed `AccountId` syntax, never for whether the account actually exists. Because the payout is implemented as a refund receipt, and refund receipts are explicitly barred from creating new accounts, pointing `beneficiary_id` at a non-existent (or otherwise inert) account causes the entire balance to be permanently burned instead of transferred — the direct analog of the reported "treasury set to zero address" bug class, but here the loss is baked into protocol-level fund routing rather than a contract initializer.

### Finding Description
Validation of the action only checks that `beneficiary_id` parses as a syntactically valid `AccountId`; it never checks that the account exists: [1](#0-0) 

At execution time, `action_delete_account` unconditionally creates a `Receipt::new_balance_refund` addressed to `beneficiary_id` for the account's full balance, with no existence check on the target: [2](#0-1) 

The comment in `check_transfer_to_nonexisting_account` documents, by design, that this refund receipt will *not* create the target account even if it doesn't exist, unlike a normal `Transfer` action to an implicit account: [3](#0-2) 

Per the refund semantics documented in the runtime spec, refund receipts are free (no gas) and, critically, **if execution of a refund fails, the refund amount is burnt**: [4](#0-3) 

This is confirmed in code: for any receipt with `predecessor_id().is_system()` (i.e., a refund), a failed result routes the deposit into `other_burnt_amount` rather than reattempting delivery or refunding elsewhere: [5](#0-4) 

So the full causal chain is: user (or contract acting on a user's behalf via `promise_batch_action_delete_account`) submits `DeleteAccount{beneficiary_id}` → `beneficiary_id` passes syntax-only validation → balance is packaged into a system-refund `Transfer` receipt to `beneficiary_id` → if `beneficiary_id` does not exist as an account, that transfer fails with `AccountDoesNotExist` → because it's a refund, the amount is irreversibly burned instead of returned to anyone.

### Impact Explanation
Any account holder can lose their entire remaining NEAR balance with no recovery path by supplying a `beneficiary_id` that does not correspond to a live account (typo, already-deleted account, or an account that is deleted in the same/an earlier action of a batch). This is functionally identical in effect to routing funds to the "zero address" in the referenced Solidity finding: value is destroyed/unrecoverable due to the absence of a target-existence check on a security-critical destination parameter. Unlike a normal `Transfer` action, which can implicitly create eligible target accounts, this specific code path (refunds) intentionally will not, so the design itself guarantees burn-on-mistake for this one action type.

### Likelihood Explanation
Reachable by any unprivileged account via a plain signed transaction (`DeleteAccount` action) or via a contract calling `promise_batch_action_delete_account` from the host function API — no validator/node privilege required. The action-level validation gives a false sense of safety (it does validate account-ID *syntax*), which makes an accidental typo or stale-beneficiary bug in a wallet/contract integration plausible; it does not require any adversarial third party, matching the "confirmed, Medium severity" characterization in the source report (loss of funds, no easy fix once the account is deleted).

### Recommendation
Before generating the balance-refund receipt in `action_delete_account`, verify that `beneficiary_id` corresponds to an existing account in state (or explicitly document/require this as a client-side responsibility and add a warning at the RPC/wallet layer). If backward compatibility must be preserved for missing accounts, consider allowing this specific refund-receipt class to implicitly create eligible (e.g., NEAR-implicit) accounts rather than silently burning the balance, or reroute unresolvable balances to a well-defined fallback (e.g., back to the deleting account's predecessor) instead of burning.

### Proof of Concept
1. Create account `alice.near` with balance `B`.
2. Submit `DeleteAccount { beneficiary_id: "nonexistent123.near" }` (an account never created) as the sole/final action for `alice.near`.
3. `action_delete_account` (`runtime/runtime/src/actions.rs:364-371`) enqueues `Receipt::new_balance_refund("nonexistent123.near", B)`.
4. Runtime processes this receipt with `predecessor_id == "system"`; `apply_action` sees `is_refund = true` and `implicit_account_creation_eligible` logic in `check_transfer_to_nonexisting_account` returns `AccountDoesNotExist` because it is a refund.
5. Because the receipt is a refund and failed, `lib.rs:993-1000` adds `B` to `other_burnt_amount` — the balance is permanently destroyed, matching the integration test comment/behavior pattern seen in `pytest/tests/sanity/rosetta.py` and `integration-tests/src/tests/features/delegate_action.rs:574-619` (where a *valid* beneficiary receives funds — contrast with an invalid one, which burns them per the documented refund-failure rule). # Refunds

When execution of a receipt fails or there is some unused amount of prepaid gas left after a function call, the Runtime generates refund receipts.

The are 2 types of refunds:

- Refunds for the failed receipt for attached deposits. Let's call them **deposit refunds**.
- Refunds for the unused gas and fees. Let's call them **gas refunds**.

Refund receipts are identified by having `predecessor_id == "system"`. They are also special because they don't cost any gas to generate or execute. As a result, they also do not contribute to the block gas limit.

If the execution of a refund fails, the refund amount is burnt.
The refund receipt is an `ActionReceipt` that consists of a single action `Transfer` with the `deposit` amount of the refund.
