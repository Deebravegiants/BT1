### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing shop/tenant spoofing on otherwise-valid webhook requests - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from unauthenticated HTTP headers [2](#0-1) . `ShopifyAPI::Utils::HmacValidator.validate` only checks the HMAC against `to_signable_string`, i.e. the body [3](#0-2) . `Registry.process` validates the HMAC and then forwards `request.shop` (and `topic`) straight to the app's handler as trusted tenant-identifying data [4](#0-3) . This mirrors the report's bug class: a field ("shop") that is acted upon (used as the tenant key passed to the handler) is not covered by the cryptographic binding (HMAC only covers body bytes), so an attacker can vary that field independently of the signed content — exactly like Alice varying her staked amount independently of the quorum snapshot.

### Finding Description
The documented/expected binding is: `HMAC(body, client_secret) == received_hmac` implies "this body legitimately originated from Shopify for the shop identified in this request." In reality the equality only proves the body is authentic; it says nothing about the `shop-domain` header, because that header is excluded from `to_signable_string`.

Because a Shopify app's `client_secret` is a single app-level secret shared across every shop that installs the app (not a per-shop credential), any shop that installs the app can generate a body + HMAC pair that is valid according to `HmacValidator.validate`. That party can then replay the exact same `(raw_body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary value in the `X-Shopify-Shop-Domain` / `shopify-shop-domain` header. `HmacValidator.validate` still returns `true` because it never inspects the header, and `Registry.process` proceeds to call the handler with `WebhookMetadata.new(shop: request.shop, ...)` using the attacker-controlled shop string [5](#0-4) .

The documentation confirms host apps are expected to use `data.shop` as the tenant key for looking up/queuing per-shop work (`perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [6](#0-5) , i.e. this is the gem's documented API surface, not host-app misuse.

Equality that should hold but doesn't:
`shop authenticated by HMAC == shop delivered to the handler as WebhookMetadata#shop`

Before attack: legitimate webhook for Shop A arrives with body B, header `shop-domain=A`, `hmac=HMAC(B)`. Validation passes, handler receives `shop: "A"`.

Attack: attacker (who has installed the same app on their own shop, an unprivileged/self-serve action) captures a valid `(B, HMAC(B))` pair from their own legitimate webhook traffic, then POSTs it to the same endpoint with `shop-domain=VictimShop`. `HmacValidator.validate` still returns true (only checks `B`), so `Registry.process` calls the handler with `shop: "VictimShop"` even though the body content and signature never authenticated anything about `VictimShop`.

### Impact Explanation
This crosses a tenant boundary: an app using this gem as documented will process attacker-supplied data attributed to a shop the attacker does not control, because the gem's own signature check does not bind the `shop` (or `topic`/`webhook_id`) field to the signed bytes. Depending on the handler logic (queuing background jobs keyed by `shop_domain`, updating per-shop records, redact/data-request workflows, etc.), this enables cross-tenant data confusion/corruption driven entirely from the webhook ingestion endpoint, matching the "Critical - cross-tenant access" impact category, since the root cause is entirely inside this gem's `Request`/`HmacValidator`/`Registry` code path rather than host-app misuse of an undocumented API.

### Likelihood Explanation
Moderate-to-high: the only prerequisite is that the attacker be able to install the target app on any shop they control (a normal, unprivileged Shopify merchant/developer action, not requiring the app's `client_secret`, an access token, or any privileged account) in order to legitimately receive `(body, hmac)` pairs signed with the shared app secret, and then replay them with a forged header value at the public webhook endpoint. No TLS interception or credential theft is required — only observation of the app's own legitimate webhook traffic to itself.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` (all Shopify-controlled header values used for downstream tenant/topic identification) in the HMAC-signed material, or otherwise cryptographically bind them to the body (e.g., verify shop against a separately-authenticated channel such as mTLS/IP allowlists is not sufficient alone). At minimum, `to_signable_string` in `lib/shopify_api/webhooks/request.rb` should incorporate the header fields that `WebhookMetadata` exposes to the handler, and `HmacValidator` should verify the resulting composite string, so that no header value trusted by the handler can vary independently of what Shopify actually signed.

### Proof of Concept
1. App `X` is installed by an attacker on their own store `attacker.myshopify.com` (self-serve, no special privilege).
2. Shopify sends a legitimate webhook to app `X`'s endpoint: body `B`, headers `shopify-shop-domain: attacker.myshopify.com`, `shopify-hmac-sha256: HMAC(B)`.
3. Attacker captures `(B, HMAC(B))` (e.g., from their own server logs/proxy — this is their own traffic, no interception of anyone else's data required).
4. Attacker replays: `POST /webhooks` with body `B`, `shopify-shop-domain: victim.myshopify.com`, `shopify-hmac-sha256: HMAC(B)` (unchanged).
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`; validation succeeds because `to_signable_string` returns only `B`, per `lib/shopify_api/webhooks/request.rb` lines 35-38.
6. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: ..., body: request.parsed_body, ...)`, per `lib/shopify_api/webhooks/registry.rb` lines 196-200 — the app now processes attacker-controlled data under the victim shop's tenant identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
