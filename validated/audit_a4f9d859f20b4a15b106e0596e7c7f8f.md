### Title
Deposit/Withdraw/Swap pricing relies on the live SPL Token vault balance, letting anyone "donate" tokens directly to `coin_vault`/`pc_vault` to corrupt LP-mint/redeem math and PNL accounting - ([File: program/src/math.rs], [File: program/src/processor.rs])

### Summary
Like the Fei `GenesisGroup` bug, which used `address(this).balance` (attacker-manipulable via `selfdestruct`) instead of tracked accounting to gate minting/launch logic, this AMM computes its core reserve figures directly from the live SPL Token account balances of `amm.coin_vault` and `amm.pc_vault` rather than from an internally-tracked, program-controlled reserve. Because SPL Token transfers only require the *source* owner's signature — the *destination* token account can be any account, including the AMM's vaults — any unprivileged actor can submit a bare `spl_token::instruction::transfer` (or `transfer_checked`) CPI to send tokens straight into `coin_vault`/`pc_vault` without ever calling `Deposit`, `Swap`, or any other instruction of this program. This silently inflates the balances that `Deposit`, `Withdraw`, `SwapBaseIn/Out` and the PNL-taking logic use as ground truth.

### Finding Description
`Calculator::calc_total_without_take_pnl_no_orderbook` derives the AMM's authoritative reserves purely from the live vault token-account balances passed in: [1](#0-0) 

Every state-changing instruction that prices deposits, withdrawals, and swaps calls this function with the *actual* unpacked vault balances, not any internally tracked counter:

- `process_deposit` — `amm_pc_vault.amount` / `amm_coin_vault.amount`: [2](#0-1) 
- `process_withdraw` — same pattern: [3](#0-2) 
- `process_swap_base_in` / `process_swap_base_in_v2` / `process_swap_base_out` / `process_swap_base_out_v2` — same pattern repeated at each swap entry point: [4](#0-3) [5](#0-4) [6](#0-5) 

None of these paths verify that the vault balance only changed via the program's own `Invokers::token_transfer` CPIs, e.g. in `process_deposit`: [7](#0-6) 

An attacker only needs the vault's public key (readable on-chain from the `AmmInfo` account) and any funded token account of the matching mint; no signer authority over the vault or any AMM-defined instruction is required to change the value the math relies on — precisely analogous to `selfdestruct` forcing ETH into `GenesisGroup` to corrupt `address(this).balance`-based accounting.

### Impact Explanation
Because the LP-mint ratio in `Deposit` (`invariant_coin.exchange_token_to_pool(amm.lp_amount, ...)`) and the redemption ratio in `Withdraw` (`invariant.exchange_pool_to_token(...)`) both use `total_coin_without_take_pnl` / `total_pc_without_take_pnl` sourced straight from the vault balance, an attacker who already holds LP tokens can:
1. Front-run a victim's incoming `Deposit` transaction with a direct token transfer ("donation") into `coin_vault`/`pc_vault`, inflating the apparent reserves.
2. The victim's `Deposit` then mints an LP amount computed against the inflated reserve, so the victim receives fewer LP tokens than the fair share of the value they actually contributed (rounding/ratio math in `mint_lp_amount = invariant_coin.exchange_token_to_pool(amm.lp_amount, RoundDirection::Floor)`), while their real tokens still land in the vault as part of total pool value.
3. The attacker (holding a fixed LP amount that did not change) then withdraws, extracting a share of the pool that now includes the recovered donation plus a slice of the victim's under-priced contribution.

This is a concrete theft-of-LP-funds vector, not merely a self-inflicted loss: value is transferred from the victim depositor to the pre-positioned attacker. It also corrupts `calc_take_pnl`'s unrealized-profit computation (`target.calc_pnl_x`/`calc_pnl_y` vs. live `x1`/`y1`), letting externally donated (or removed-in-the-future accounting) balances be mis-attributed as trading profit and skimmed via `process_withdrawpnl`: [8](#0-7) 

### Likelihood Explanation
The precondition (attacker owning some LP of the target pool and being able to observe/front-run a pending `Deposit`) is realistic for any actively traded pool; sending an SPL token transfer to a known, publicly-readable vault address requires no special privilege and is a single ordinary transaction.

### Recommendation
Track `total_pc`/`total_coin` (or equivalent reserve counters) as part of `AmmInfo` state, updated exclusively inside the program's own transfer CPIs (`Invokers::token_transfer`, `token_transfer_with_authority`), instead of re-reading the live SPL Token account balance in `calc_total_without_take_pnl_no_orderbook`. If vault balance must be read for reconciliation, cap its use to detecting/rejecting unexpected surplus rather than feeding it directly into LP-mint/redeem/swap pricing.

### Proof of Concept
1. Attacker acquires LP tokens for pool `P` (any amount).
2. Attacker observes a pending `Deposit` transaction from victim `V` for pool `P`.
3. Attacker submits, ahead of `V`'s transaction, a plain `spl_token::instruction::transfer` moving `D` coin tokens from an attacker-owned token account into `P.coin_vault` (no signature from the AMM authority or program is needed since only the *source* owner must sign).
4. `V`'s `Deposit` executes; `calc_total_without_take_pnl_no_orderbook` now returns `total_coin_without_take_pnl` inflated by `D`, so `mint_lp_amount` computed in `process_deposit` (program/src/processor.rs:1244-1250) is smaller than it would be absent the donation, for the same `deduct_coin_amount`/`deduct_pc_amount` contributed by `V`.
5. Attacker calls `Withdraw` for their unchanged LP balance; `coin_amount`/`pc_amount` in `process_withdraw` (program/src/processor.rs:1756-1761) are computed against the now-larger `total_coin_without_take_pnl`/`total_pc_without_take_pnl` (which include both the attacker's donation and `V`'s under-priced contribution), letting the attacker recover more value than they donated, at `V`'s expense.

    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
