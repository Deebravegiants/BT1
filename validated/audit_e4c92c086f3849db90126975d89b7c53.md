## Title
Non-constant-time Bearer token comparison on Prometheus metrics endpoint enables timing side-channel token recovery - ([File: core/web/router.go])

## Summary
The `prometheusHandler` middleware protecting the `/metrics` endpoint compares the client-supplied `Authorization` header against `"Bearer " + token` using Go's native `!=` string operator, which is not constant-time. This deviates from every other credential-comparison path in the codebase (bcrypt for passwords, `subtle.ConstantTimeCompare` for API/external-initiator tokens), creating a genuine timing side-channel against an unauthenticated, network-reachable secret check.

## Finding Description
`prometheusUse` registers `prometheusHandler(p.Token, h)` as the gin handler for `p.MetricsPath` [1](#0-0) . Inside `prometheusHandler`, when a token is configured, the code builds `bearer := "Bearer " + token` and compares it against the request header with a plain `!=`: [2](#0-1) . Go's `!=` on strings performs byte-by-byte comparison and returns as soon as a mismatch is found, so rejection latency is correlated with the number of correct leading bytes an attacker supplies — a textbook timing side-channel (same bug class as CVE-2021-33880). This is inconsistent with the rest of the codebase's authentication paths, which deliberately use timing-safe comparisons (`subtle.ConstantTimeCompare` for tokens, bcrypt for passwords), confirming this specific path was overlooked rather than intentionally designed this way.

## Impact Explanation
If exploited, an attacker could recover the `Prometheus.AuthToken` secret without prior credentials, then gain access to the node's `/metrics` endpoint, which exposes internal operational telemetry. This is a legitimate confidentiality/secret-disclosure class issue matching the "secret exfiltration" category, but the exposed asset (metrics data) is lower-sensitivity than credentials, funds, or job execution control — it does not directly enable job manipulation or fund movement.

## Likelihood Explanation
Exploitability requires an attacker to have network access to the metrics endpoint and to perform a large number of precisely-timed requests to statistically distinguish microsecond-scale latency differences per byte guessed. This is realistic on a low-jitter LAN path but significantly harder over the public internet due to network jitter, and the `/metrics` endpoint may not be internet-exposed in typical deployments (often bound to internal networks/scrape targets only). The vulnerability is real and root-caused in the code, but requires a sophisticated, patient attacker and favorable network conditions — consistent with a Medium/Low-likelihood, root-caused, in-scope finding rather than a trivial exploit.

## Recommendation
Replace the direct string comparison with `crypto/subtle.ConstantTimeCompare([]byte(header), []byte(bearer)) == 1` (after confirming equal length, or by hashing both sides with HMAC/SHA-256 to normalize length before comparison), matching the pattern already used in `AuthenticateUserByToken` [3](#0-2)  and `AuthenticateExternalInitiator` [4](#0-3) .

## Proof of Concept
1. Configure a node with `[Prometheus] AuthToken = "<secret>"`.
2. Send repeated GET requests to `/metrics` with `Authorization: Bearer <guess>`, incrementally varying one byte at a time from a known-correct prefix.
3. Measure response latency for each guess over many samples (to average out network jitter); requests with a longer correct prefix take measurably longer to reject due to `!=`'s byte-by-byte short-circuit behavior.
4. Statistically distinguish latency deltas byte-by-byte to reconstruct the full `AuthToken` without ever supplying a valid credential.
5. A Go benchmark/unit test comparing `!=` timing for strings with 0 vs. N correct leading bytes can also demonstrate the underlying non-constant-time behavior directly (without requiring network jitter mitigation).

func prometheusUse(p *ginprom.Prometheus, e *gin.Engine, handlerOpts promhttp.HandlerOpts) {
	var (
		r prometheus.Registerer = p.Registry
		g prometheus.Gatherer   = p.Registry
	)
	if p.Registry == nil {
		r = prometheus.DefaultRegisterer
		g = prometheus.DefaultGatherer
	}
	h := promhttp.InstrumentMetricHandler(r, promhttp.HandlerFor(g, handlerOpts))
	e.GET(p.MetricsPath, prometheusHandler(p.Token, h))
	p.Engine = e
}

// use is adapted from ginprom.prometheusHandler to add support for custom http.Handler
func prometheusHandler(token string, h http.Handler) gin.HandlerFunc {
	return func(c *gin.Context) {
		if token == "" {
			h.ServeHTTP(c.Writer, c.Request)
			return
		}

		header := c.Request.Header.Get("Authorization")

		if header == "" {
			c.String(http.StatusUnauthorized, ginprom.ErrInvalidToken.Error())
			return
		}

		bearer := "Bearer " + token

		if header != bearer {
			c.String(http.StatusUnauthorized, ginprom.ErrInvalidToken.Error())
			return
		}

		h.ServeHTTP(c.Writer, c.Request)
	}
}

// AuthenticateUserByToken returns true on successful authentication of the
// user against the given Authentication Token.
func AuthenticateUserByToken(token *auth.Token, user *User) (bool, error) {
	hashedSecret, err := auth.HashedSecret(token, user.TokenSalt.ValueOrZero())
	if err != nil {
		return false, err
	}
	return subtle.ConstantTimeCompare([]byte(hashedSecret), []byte(user.TokenHashedSecret.ValueOrZero())) == 1, nil
}
