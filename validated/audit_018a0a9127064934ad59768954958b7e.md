### Title
Webhook `shop`, `topic`, and `webhook_id` fields are trusted from HTTP headers that are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` by defining `to_signable_string` as only the raw HTTP body [2](#0-1) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers [3](#0-2) . `Utils::HmacValidator.validate` only verifies that the raw body matches the HMAC signature [4](#0-3) ; it never binds the header-derived `shop` value into the signed bytes. `Registry.process` then trusts this unauthenticated `shop` value as the tenant identity passed to the app's handler [1](#0-0) .

### Finding Description
This is the "field acted on but not covered by the HMAC" identity-binding break. The equality that should hold is:

`shop used by HmacValidator to authenticate the request == shop used by Registry.process/WebhookHandler to identify the tenant`

In reality:
- The bytes verified by `OpenSSL.secure_compare(computed_signature, received_signature)` are exclusively `@raw_body` [2](#0-1) .
- The `shop` (and `topic`/`webhook_id`) values acted on by the handler come from `shopify-shop-domain` / `x-shopify-shop-domain` headers, which are never part of the signed payload [5](#0-4) .

Because only the body bytes are HMAC-bound, any correctly-signed `(body, hmac)` pair remains valid under `Utils::HmacValidator.validate` no matter what `shop-domain` header accompanies it [6](#0-5) . An unprivileged internet user who legitimately installs the target app on their own store will receive genuinely-signed webhooks (body + valid HMAC) for their own shop. They can then replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header value. `Registry.process` will validate the HMAC successfully (since it only checks the body) and will construct `WebhookMetadata` using the attacker-supplied `shop` value, handing the app's `WebhookHandler#handle` a payload it will treat as coming from a different, victim tenant [7](#0-6) .

### Impact Explanation
This breaks the tenant boundary this gem is supposed to enforce for webhook delivery: an attacker-controlled shop identifier reaches the app's business logic carrying data that was never bound to that shop by any cryptographic check. Any app that keys per-merchant state, access tokens, or database records off `WebhookMetadata#shop` (the documented, expected pattern per `docs/usage/webhooks.md`) can have another merchant's records overwritten, deleted, or polluted with attacker-supplied (but validly-signed-for-a-different-shop) payloads — a cross-tenant access/injection condition, consistent with the report's core bug class (breaking an identity binding that is checked in one place but relied upon in another).

### Likelihood Explanation
The prerequisite is only that the attacker is able to install the target app on a shop they control (any unprivileged Shopify merchant/developer can do this) and can freely craft the HTTP request to the app's own webhook endpoint (headers are fully attacker-controlled at the HTTP layer; the gem does no header authentication). No access token, `client_secret`, or privileged account is required — this exactly satisfies the "unprivileged internet user" scope of this exercise.

### Recommendation
Bind the `shop-domain` (and ideally `topic`/`webhook-id`) header values into the HMAC-verified material, e.g. by including them in `to_signable_string`, or by requiring the caller to supply the `shop` out-of-band from a previously authenticated session and rejecting the request if the header value does not match. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be trusted for tenant routing without independent verification (e.g., cross-checking against a known/registered shop list).

### Proof of Concept
1. Attacker installs the app on their own shop `attacker-shop.myshopify.com` and receives a real webhook: body `B`, header `shopify-hmac-sha256: H` (valid HMAC of `B` under the app's `client_secret`), and `shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker replays the identical `B` and `H` to the app's webhook endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. The app calls `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: { "shopify-hmac-sha256" => H, "shopify-shop-domain" => "victim-shop.myshopify.com", "shopify-topic" => ... })` then `ShopifyAPI::Webhooks::Registry.process(request)`.
4. `Utils::HmacValidator.validate(request)` returns `true` (only `B` and `H` matter) [8](#0-7) .
5. `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...))` executes with attacker-chosen `shop`, even though that shop never actually sent or signed this webhook [7](#0-6) .
