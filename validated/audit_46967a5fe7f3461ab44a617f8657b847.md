### Title
Webhook shop-domain (and topic/webhook-id) header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while the `shop`, `topic`, and `webhook_id` fields used downstream by `ShopifyAPI::Webhooks::Registry.process` are read from unauthenticated HTTP headers. Because the app's `client_secret`/`api_secret_key` is shared across every shop that has the app installed, any merchant who installs the app on their own store can obtain genuinely-signed `(body, hmac)` pairs and replay them to the app's webhook endpoint with a forged `shopify-shop-domain` header pointing at a victim shop. `Utils::HmacValidator.validate` only re-computes the HMAC over the body and never checks that the claimed shop is bound to that signature, so the forged request passes validation and the handler is invoked as if the data belongs to the victim tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, and `#webhook_id` are parsed straight from headers with no cryptographic tie to the signed body: [2](#0-1) 

`HmacValidator.validate`/`validate_signature` verify only `verifiable_query.to_signable_string` (the raw body) against `verifiable_query.hmac`, with no involvement of `shop`, `topic`, or `webhook_id`: [3](#0-2) 

`Registry.process` trusts `request.shop` (and `request.topic`, `request.webhook_id`) directly once the HMAC check passes, and hands them to the app's handler as authenticated tenant identity: [4](#0-3) 

The identity binding this breaks is: `shop header claimed by request == shop bound by HMAC(secret, message)`. In this implementation, `message = raw_body` only, so `shop` is never an input to the HMAC. Since `api_secret_key` is a single per-app secret shared by all shops that install the app (not shop-specific), an unprivileged attacker who installs the app on their own store receives real, validly-signed webhook deliveries. They can capture a `(raw_body, hmac)` pair from their own shop and POST it directly to the app's public webhook endpoint with the `shopify-shop-domain` (and/or `shopify-topic`, `shopify-webhook-id`) header rewritten to name a different, victim shop. `HmacValidator.validate` recomputes the HMAC over the (attacker-supplied) body only, which still matches, so `Registry.process` calls the app's handler with `shop: <victim shop>` even though that value was never signed.

### Impact Explanation
This lets an unprivileged, merely-app-installed attacker forge webhook events attributed to an arbitrary other tenant (shop) known to the attacker, without stealing any credential. Depending on how the host application keys its data/session store by `shop` (which the library's own README/example usage assumes is authenticated, e.g., used to fetch/store sessions or trigger shop-scoped side effects such as `app/uninstalled`, `customers/redact`, `shop/redact`), this enables cross-tenant data corruption or unauthorized actions being taken against a victim's tenant records — a cross-tenant access impact.

### Likelihood Explanation
Likelihood is moderate-to-high in realistic deployments: any Shopify merchant can install a public app for free/trial, giving them a legitimate, validly-HMAC-signed webhook they fully control the body of, and the shared per-app secret means that signature is valid for every installation of the same app. Forging headers on a direct HTTP POST to a public webhook endpoint requires no special access beyond knowledge of a victim's shop domain (which is generally public, e.g. `victim.myshopify.com`).

### Recommendation
Bind the shop (and ideally topic/webhook-id) to the HMAC verification, not just the raw body — e.g. include `shop`, `topic`, and `webhook_id` header values in the signable message alongside the body, or otherwise require the caller/handler to cross-check `request.shop` against a shop the app has legitimately provisioned/installed for before trusting it for tenant-scoped operations. At minimum, document prominently that `Request#shop`/`#topic`/`#webhook_id` are NOT covered by the HMAC and must not be trusted as authenticated tenant identifiers on their own.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, obtaining the app's shared `api_secret_key` behavior via genuine webhook deliveries (e.g. triggers an `orders/create` webhook by placing a test order).
2. Attacker captures the delivered request: raw body `B` and header `shopify-hmac-sha256: H` (a valid HMAC of `B` under the shared secret).
3. Attacker crafts a new HTTP POST to the same app's webhook endpoint with:
   - Body: `B` (unchanged, so HMAC stays valid)
   - `shopify-hmac-sha256: H` (unchanged)
   - `shopify-shop-domain: victim.myshopify.com` (forged)
   - `shopify-topic`/`shopify-webhook-id` optionally forged as well
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and succeeds.
5. The app's registered handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, causing the app to process/act as if the (attacker-controlled) payload originated from the victim shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
