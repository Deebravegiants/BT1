This confirms the vulnerability: `WebhookMetadata.shop` is populated directly from `request.shop` (the `x-shopify-shop-domain` / `shopify-shop-domain` header) and passed to app handlers as the tenant identity, while `Registry.process` only checks `Utils::HmacValidator.validate(request)`, which verifies the HMAC solely against `to_signable_string` (the raw body) per `Webhooks::Request#to_signable_string`.

### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body [1](#0-0) . The `shop` value that is subsequently trusted and forwarded to the host application's handler as the tenant identity is read from an HTTP header (`shopify-shop-domain` / `x-shopify-shop-domain`) that is never included in the signed bytes [2](#0-1) .

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery`, whose contract requires `hmac` and `to_signable_string` [3](#0-2) . For webhook requests, `to_signable_string` returns only `@raw_body`, and `hmac` is read from the header sent by the caller [4](#0-3) . `Utils::HmacValidator.validate_signature` computes `HMAC-SHA256(secret, to_signable_string)` and compares it to the supplied HMAC with a constant-time comparison [5](#0-4) . This means the identity binding actually enforced is:

`HMAC(client_secret, body) == received_hmac`

but the binding that the application logic relies on for tenant scoping is:

`shop == request.shop` (i.e., "the shop this webhook is delivered for"),

and `request.shop` is never an input to the HMAC computation. Since the app's `client_secret` is shared across every shop/tenant that has installed the app (it's the same secret Shopify uses to sign every merchant's webhooks for that app), a party who controls (or has compromised) one legitimate shop can capture a valid `(body, hmac)` pair from a real webhook delivery for their own shop, then replay that exact `body`/`hmac` to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop. `Registry.process` only checks the HMAC over the body [6](#0-5) ; it performs no check that `request.shop` corresponds to the shop that actually produced the signature (there is no per-shop key or nonce binding shop to signature). The unauthenticated `shop` value is then packaged directly into `WebhookMetadata` and handed to the application's registered handler as ground truth for which tenant the event belongs to [7](#0-6)  and [8](#0-7) .

This mirrors the report's bug class exactly: an identity/weight field (there, the signatory address; here, the `shop` field) is used to make an authorization/attribution decision but is not itself covered by the verification the code relies on to establish trust.

### Impact Explanation
An attacker who has (or creates) a legitimate installation of the target app on any shop can forge webhook deliveries that the gem will accept as coming from an arbitrary victim shop, because the `shop` attribution is not bound to the signature. Any host application that keys its data store, session lookup, or business logic off `WebhookMetadata#shop` (which is the gem's documented, intended usage pattern per `docs/usage/webhooks.md`) can be tricked into writing/reading data under, or triggering shop-scoped actions for, a tenant the attacker does not control — a cross-tenant confusion within the trust boundary this gem is responsible for establishing.

### Likelihood Explanation
Exploitation requires only that the attacker control one shop with the app installed (a routine, low-privilege state — installing a public/free app is not a privileged credential) and be able to replay an HTTP POST to the app's own publicly reachable webhook endpoint with a modified header; no access to `api_secret_key`, tokens, or Shopify infrastructure is needed. This is a realistic, low-effort attack path.

### Recommendation
Bind the shop identity into the verified bytes, e.g., include `shop-domain` (and ideally `topic`/`webhook-id`) in `to_signable_string`, or independently verify that the `shop` header matches an expected/allow-listed shop associated with the delivery (e.g., cross-check against a per-shop webhook secret or a registered subscription record) before trusting `request.shop` in `Registry.process`/`WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers a real webhook event (e.g., `orders/create`), capturing the raw POST body `B` and the legitimate `X-Shopify-Hmac-Sha256` header value `H` computed by Shopify using the app's shared `client_secret`.
2. Attacker crafts a POST to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid because it only signs `B`), but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Webhooks::Request.new` parses the request; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(client_secret, B)` and matches `H` — validation passes [9](#0-8) .
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body(B), ...)` and processes attacker-supplied data as if it originated from `victim-shop.myshopify.com` [7](#0-6) .
