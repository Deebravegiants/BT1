### Title
Webhook tenant identity (`shop`) is not bound to the HMAC, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` authenticates a webhook solely by HMAC-verifying the raw request body against the app's `client_secret`. The `shop` (and `topic`, `api_version`, `webhook_id`) values that the host application uses to determine *which merchant* the webhook belongs to are read straight from unauthenticated HTTP headers and are never included in the HMAC computation. Since a single app's `client_secret` is shared across every shop that has installed the app, any merchant who has installed the app can capture a validly-signed webhook body from their own store and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a different (victim) merchant that has also installed the app. The signature check still passes because the signature never covered the shop header, breaking the equality `shop authenticated by HMAC == shop used as tenant key`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) . `Utils::HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest` over exactly that signable string using `Context.api_secret_key` and compares it to the `hmac` derived from the `X-Shopify-Hmac-Sha256` header [4](#0-3) . None of `topic`, `shop`, `api_version`, or `webhook_id` — all sourced from attacker-controllable HTTP headers via `shopify_header` [5](#0-4) [6](#0-5)  — are covered by that signature.

`Registry.process` uses this HMAC check as its sole authentication gate, then immediately forwards `request.shop` (an unauthenticated header value) to the app's handler as the tenant identity: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [3](#0-2) .

Because Shopify signs webhooks with the app-wide `client_secret` (identical for every shop that installs the app), the HMAC alone cannot distinguish which shop a request came from — the signature only proves "some install of this app produced this body," not "this specific shop produced this body." This is directly analogous to the report's bug class: a field that is acted upon (`shop`, used as the tenant/session key by the handler) is not covered by the authentication mechanism (the HMAC), so it can be substituted freely by anyone able to obtain one validly-signed payload.

### Impact Explanation
An unprivileged user who has installed the target app on their own store (a normal, low-privilege action available to any merchant) can capture one legitimately HMAC-signed webhook body from their shop, then resend it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to any other shop that has installed the same app. The HMAC check in `Utils::HmacValidator.validate` still passes since it never inspected the shop header. If the host application looks up per-shop state (access tokens, settings, order records) keyed by `data.shop` from `WebhookMetadata`, the attacker can inject spoofed data, trigger unauthorized processing, or exfiltrate/overwrite another merchant's data — a cross-tenant boundary break, matching the Critical "cross-tenant access" impact criterion.

### Likelihood Explanation
Likelihood is high for any app using this gem's webhook processing exactly as documented: the attacker requires nothing more than a normal app installation on one shop (freely obtainable for any public app) and the ability to send arbitrary HTTP requests with custom headers to the app's public webhook endpoint. No access token, `client_secret`, or privileged account is needed — only observation of one legitimately delivered webhook payload plus header manipulation.

### Recommendation
Bind the tenant-identifying fields into the authenticated material, or otherwise independently verify `shop` against server-side state before trusting it:
- Include `shop`, `topic`, `api_version`, and `webhook_id` in the HMAC-signed payload used by `to_signable_string` (or verify them against an out-of-band record of the shop's own signing context), rather than signing the body alone.
- Alternatively/additionally, require the caller to look up and validate that `request.shop` corresponds to a shop with a currently valid, stored session/access token for this app before dispatching to `handler.handle`, and reject the webhook if the shop domain cannot be corroborated independently of the header.
- Document to consumers of the gem that `WebhookMetadata#shop` is not authenticated by the HMAC and must be cross-checked against the app's own installed-shop records before being used as a tenant key.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a normal, unprivileged action).
2. Shopify delivers a legitimate webhook, e.g. `orders/create`, to the app's endpoint with headers:
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - `X-Shopify-Hmac-Sha256: <valid HMAC of raw body using the app's client_secret>`
   - body: `{"id": 1, ...}`
3. Attacker captures this raw body and HMAC header value (they can read their own webhook deliveries, e.g., via a reverse proxy they control in front of their own store's webhook receiver, or by re-registering the webhook URL to their own logger).
4. Attacker resends the exact same raw body and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (a shop that also has the app installed).
5. `Utils::HmacValidator.validate` recomputes the HMAC over `@raw_body` only [1](#0-0)  using the same app-wide `Context.api_secret_key`, so it matches and validation succeeds.
6. `Registry.process` calls the registered handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)` [7](#0-6) , causing the app to process attacker-controlled webhook content under the victim shop's tenant context.
