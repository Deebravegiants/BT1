### Title
Cross-chain token refunds are blocked by `whenNotPaused` on `onPostRequestTimeout()`, permanently freezing burned/locked user funds while the contract is paused - (File: `sdk/packages/core/contracts/apps/HyperFungibleToken.sol`, `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`HyperFungibleToken` and `WrappedHyperFungibleToken` (and their upgradeable variants) let the contract owner pause all cross-chain operations via `pause()`/`_pause()`. The `onPostRequestTimeout()` function — the sole mechanism that refunds a user's already-burned or already-locked tokens when a cross-chain `send()` message times out — is gated by the same `whenNotPaused` modifier as `send()` and `onAccept()`. If the contract is paused after a user has called `send()` (funds already burned/locked) but before the message's timeout is delivered, the user's refund cannot be processed until the owner unpauses, freezing funds that rightfully belong to the user regardless of protocol state.

### Finding Description
In `HyperFungibleToken.sol`, `send()` immediately burns the caller's tokens and dispatches a cross-chain POST request: [1](#0-0) 

If that POST request times out (destination never delivers), the ISMP host calls `onPostRequestTimeout()` to re-mint the burned tokens back to the sender. This function is restricted by `onlyHost` and, critically, also by `whenNotPaused`: [2](#0-1) 

The same pattern exists in `WrappedHyperFungibleToken.sol`, where `send()` locks the underlying ERC20 (or wraps native ETH) and `onPostRequestTimeout()` — guarded by `whenNotPaused` — is the only path that unlocks/returns those tokens to the original sender: [3](#0-2) [4](#0-3) 

Both `pause()` functions are `onlyOwner`-callable, intended as an emergency stop for `send`/`onAccept`, but the modifier is reused verbatim on the refund/timeout handler: [5](#0-4) 

There is no separate, always-available path for a user to reclaim funds committed prior to the pause. As soon as the owner pauses the contract — for any reason, at any time — every pending timed-out transfer becomes unrefundable until the owner unpauses. This is the exact class of bug identified in the external report: an emergency pause switch that blocks the fund-recovery/refund flow instead of only blocking new activity.

### Impact Explanation
Users who have already burned tokens (HyperFungibleToken) or locked underlying assets/ETH (WrappedHyperFungibleToken) via `send()` depend entirely on `onPostRequestTimeout()` to recover their funds if the cross-chain message is not delivered before its timeout. If the contract is paused during that window, their funds are frozen and cannot be recovered through any other function until the owner calls `unpause()`. This is a High-impact freezing-of-funds condition since the amount at risk is unbounded and tied directly to user-initiated transfers, and the trigger (owner pausing while messages are in-flight) is plausible during any incident response.

### Likelihood Explanation
Low-to-moderate likelihood: it requires that (1) a user has an in-flight `send()` whose message ultimately times out, and (2) the owner pauses the contract during that window — a scenario that is realistically expected during exactly the kind of security incident that `pause()` is meant to address (e.g., pausing in response to a bridge exploit while an unrelated user's honest transfer is stuck in-flight).

### Recommendation
Remove the `whenNotPaused` modifier from `onPostRequestTimeout()` in `HyperFungibleToken.sol`, `WrappedHyperFungibleToken.sol`, and their upgradeable counterparts (`HyperFungibleTokenUpgradeable.sol`, `WrappedHyperFungibleTokenUpgradeable.sol`), so that refunds of already-committed user funds remain available regardless of the pause state. Pausing should only prevent new outbound `send()` calls and/or new inbound `onAccept()` deliveries, not the return of funds already owed to users.

### Proof of Concept
1. User calls `send()` on `WrappedHyperFungibleToken`, locking `amount` of the underlying ERC20 (or wrapping ETH) and dispatching a POST request with a finite `timeout`.
2. Before the destination chain delivers the message, the contract owner calls `pause()` (e.g., in response to an unrelated incident).
3. The POST request times out on-chain; a relayer submits the timeout proof and the ISMP host invokes `onPostRequestTimeout()`.
4. The call reverts due to `whenNotPaused`, so the user's locked tokens are not returned.
5. The user's funds remain frozen in the contract until the owner calls `unpause()`, with no alternative recovery path available.

    function onPostRequestTimeout(PostRequestTimeout calldata incoming) external override onlyHost whenNotPaused {
        HyperFungibleToken.Message memory message = abi.decode(incoming.request.body, (HyperFungibleToken.Message));
        address refundee = _toAddr(message.from);

        if (_isWeth) {
            // Try a native-ETH push first; if the refundee cannot accept native value
            // (e.g. the caller used the ERC-20 deposit path in `send()` from a
            // non-payable contract), re-wrap the withdrawn ETH and deliver the
            // underlying WETH as an ERC-20 transfer so the timeout still settles and
            // funds are not permanently locked.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = refundee.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(refundee, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(refundee, message.amount);
        }

        emit Refunded({to: refundee, amount: message.amount});
    }
