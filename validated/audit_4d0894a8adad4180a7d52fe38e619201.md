This confirms the finding. The gem's own documentation explicitly states `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" (`docs/usage/webhooks.md:125`), and hands the handler a `data.shop` field described as "The shop domain of the webhook" (`docs/usage/webhooks.md:14`), implying it is part of what's verified. In reality, `Utils::HmacValidator.validate` only ever checks `to_signable_string`, which for `Webhooks::Request` is just `@raw_body` — the `shop-domain` header is never covered by the signature.

### Title
Webhook `shop` identity is not bound to the HMAC, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authenticated once `Utils::HmacValidator.validate(request)` passes, then forwards `request.shop` to the app's handler as the tenant identifier. But `Webhooks::Request#to_signable_string` only returns the raw body, never the `shop-domain` header, so the HMAC never binds the shop to the payload. Anyone who possesses one valid `(body, hmac)` pair — trivially available to any merchant who has installed the app, since Shopify sends them real webhooks for their own shop — can replay that exact body+hmac to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header, and `Registry.process` will accept it as an authentic webhook "for" the spoofed shop.

### Finding Description
`Registry.process` performs exactly one authentication check before dispatching to the app's handler: [1](#0-0) 

The check is `Utils::HmacValidator.validate(request)`, which computes the signature purely from `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` is defined as just the raw body, and `shop` is read straight from an unauthenticated header: [3](#0-2) 

That unauthenticated `shop` value is then handed to the handler as the trusted tenant identifier in `WebhookMetadata`: [4](#0-3) [5](#0-4) 

The binding that is broken is: `shop` authenticated by the HMAC (what the API documents) ≠ `shop` actually read by the handler (an arbitrary, attacker-controlled header). The gem's own docs describe `process` as verifying "the request did indeed come from Shopify" and describe `data.shop` as "The shop domain of the webhook" — implying the shop is part of what was verified: [6](#0-5) [7](#0-6) 

Because `Context.api_secret_key` is shared by all shops that install the same app, and the HMAC is only ever computed over the body, an unprivileged user who is themselves a merchant/installer of the target app can obtain a genuine `(raw_body, hmac)` pair from Shopify (their own real webhook deliveries for topics like `app/uninstalled`, `orders/create`, etc.), and resend that exact pair to the app's public webhook endpoint with a forged `X-Shopify-Shop-Domain` header naming a different shop. `HmacValidator.validate` still succeeds (it never looks at the header), and the app's own handler — built exactly as this gem documents — will process data intended to represent another tenant's shop, e.g., triggering "shop uninstalled" cleanup, resource deletion, or state changes scoped by `data.shop` for a shop the attacker does not control.

### Impact Explanation
This crosses a tenant boundary using only a signature that was never meant to authenticate that boundary: the shop identity handed to app logic is fully attacker-controlled while still passing the gem's only authenticity check. Depending on how host apps key their data/side effects off `WebhookMetadata#shop` (which is exactly what this gem instructs them to do), this can cause cross-tenant state corruption, spurious uninstall/cleanup actions against another merchant's data, or other cross-tenant effects — all without needing any of the target shop's credentials.

### Likelihood Explanation
Exploitability only requires being a legitimate (if unprivileged) installer of the target app on some shop, which is the minimum bar for "unprivileged internet user" against a public app. Capturing one's own genuine webhook body/HMAC and replaying it against the same public endpoint with a different `shop-domain` header is trivial and requires no secret material, no access token, and no interaction with Shopify's servers beyond normal app installation.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the signed material that `HmacValidator` checks, or independently verify that `request.shop` corresponds to a shop with an active, known installation/session before trusting it in `WebhookMetadata`. At minimum, document prominently that `data.shop` is unauthenticated header data and must be independently validated by the host app against its own session/shop registry before being used for any tenant-scoped action.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a legitimate, unprivileged install).
2. Shopify sends a real webhook, e.g. `orders/create`, to the app's endpoint with headers including `X-Shopify-Hmac-Sha256: <hmac>` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, and some raw body `B`.
3. Attacker captures `B` and the `hmac` value (trivial — it's their own traffic to their own endpoint, or observable via any request logging they control).
4. Attacker replays a POST to the same public webhook endpoint with the same `raw_body: B`, the same `X-Shopify-Hmac-Sha256` header, but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches — validation passes.
6. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and performs whatever tenant-scoped action the app implements for that topic, now against data/logic keyed to `victim-shop.myshopify.com` while under attacker control of the payload contents.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`.
