Based on the investigation, this scenario is not exploitable because the codebase already enforces global (post-ALT-resolution) uniqueness of account keys before any account loading or rent verification occurs.

### Key findings

Duplicate account keys — whether both static, both ALT-resolved, or one static/one ALT-resolved — are rejected by `validate_account_locks`, which is explicitly documented and tested to run **after** ALT resolution specifically to catch this class of issue: `has_duplicates` is checked over the fully resolved `AccountKeys` (static + ALT writable + ALT readonly) and returns `TransactionError::AccountLoadedTwice` on any repeat, regardless of writable/readonly position. [1](#0-0) [2](#0-1) 

This same check is used in the account-locking path that all transactions traverse before loading/execution (`Accounts::lock_accounts`), and a dedicated regression test (`test_duplicate_account_key` in `runtime/src/bank/tests.rs`) confirms that a hand-crafted duplicate-key transaction is rejected with `AccountLoadedTwice` at `bank.process_transaction`. [3](#0-2) [4](#0-3) 

Because of this guard, by the time `load_transaction_accounts`/`load_transaction_account` (in `svm/src/account_loader.rs`) or `TransactionAccountStateInfo::new_pre_exec`/`new_post_exec`/`verify_changes` (in `svm/src/transaction_account_state_info.rs`) run, every pubkey in `message.account_keys()` is guaranteed unique across all positions (static and ALT-resolved). Both `inspect_account`'s `is_writable` argument (derived via `message.is_writable(account_index)` in `load_transaction_account` at `svm/src/account_loader.rs:629`) and `verify_changes`'s per-index rent-state check (via `iter_writable_accounts` iterating `0..message.account_keys().len()` and calling `message.is_writable(i)` in `svm/src/transaction_account_state_info.rs:145-164`) operate on the same message-level indices, using the same `is_writable` derivation, for a key set that cannot contain the same pubkey at two positions with different writability. There is therefore no way to construct a message where the same account key appears simultaneously as writable in one position and read-only in an ALT-resolved duplicate index — such a transaction is rejected during account-lock validation before it ever reaches `inspect_account` or `verify_changes`.
