### Title

Aggregate-debt overflow permanently freezes market before borrow-index cap - ([File: common/src/rates/index.rs])

### Summary

A sufficiently large, heavily borrowed market can permanently freeze because accrual computes `borrowed * borrow_index` in RAY units and panics when the resulting aggregate debt exceeds `i128::MAX`, before the configured borrow-index ceiling can bound the index. [1](#0-0) 

Severity: Medium. [2](#0-1) 

### Finding Description

The permissionless `Controller::update_indexes` entrypoint forwards the selected `HubAssetKey` values to the pool’s index-accrual path. [3](#0-2)  The pool loads each market, calls `interest::global_sync`, and then commits the resulting state. [4](#0-3) 

`global_sync` splits elapsed time into bounded chunks and calls `accrue_chunk`, which computes the accrual step from the aggregate scaled debt and both indexes. [5](#0-4)  During interest distribution, `calculate_supplier_rewards` multiplies the same scaled debt total by both the old and new borrow indexes. [1](#0-0) 

The borrow index itself is capped only after `old_index.mul(interest_factor)` returns, but that cap does not constrain the separate `borrowed * index` product. [6](#0-5)  Fixed-point multiplication widens only the intermediate product to `I256` and panics if the quotient does not fit back into `i128`. [7](#0-6) 

After the aggregate debt crosses that representable-value boundary, every later accrual panics before `last_timestamp` advances. [8](#0-7)  Withdrawal and repayment both load the market through the synchronized path before resolving their positions, and recapitalization also synchronizes the market before computing the shortfall. [9](#0-8) [10](#0-9) [11](#0-10) 

### Impact Explanation

This permanently freezes the affected market’s funds: suppliers cannot withdraw, borrowers cannot repay, liquidations cannot settle accrued debt, and recapitalization cannot run because each path retries the overflowing accrual. [12](#0-11) 

The failure is not a temporary transaction limit because the persisted `last_timestamp` remains in the past, so every subsequent call accumulates a nonzero elapsed interval and reaches the same multiplication. [13](#0-12) 

### Likelihood Explanation

Triggering the final revert is permissionless through `update_indexes`, but reaching the vulnerable aggregate-value domain requires an extremely large market and sustained high utilization over an extended period. [14](#0-13) [15](#0-14) 

The indexed test uses one-billion whole tokens with 18 decimals, approximately 98% utilization, repeated yearly accruals, and shows that the panic occurs while `borrow_index` is still below `MAX_BORROW_INDEX_RAY`. [16](#0-15) 

### Recommendation

Bound the aggregate RAY-denominated debt value, not just the borrow index. [6](#0-5) 

Before multiplying `borrowed` by an updated index, compute the largest index satisfying `floor(borrowed * index / RAY) <= i128::MAX`, clamp the new index to that bound, and leave the market in a state that can still process repayments and withdrawals. [2](#0-1)  The same bound must cover `supplied * supply_index`, bad-debt valuation, and every other aggregate share-to-value multiplication so that no common accrual branch can permanently trap the market. [17](#0-16) [18](#0-17) 

### Proof of Concept

The repository’s long-horizon harness creates an 18-decimal market, deposits `1_000_000_000 * 10^18` base units, borrows 98% of that amount against other collateral, advances ledger time in yearly increments, and repeatedly calls `update_indexes`. [15](#0-14) 

```rust
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);
let debt = principal / 100 * 98;
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);

loop {
    t.advance_time(YEAR_SECS);
    if t.try_update_indexes_for(&["BIG18"]).is_err() {
        break;
    }
}
```

The resulting error is `MathOverflow`, while the stored borrow index remains below `MAX_BORROW_INDEX_RAY`, proving that the aggregate-value multiplication fails before the index ceiling protects the market. [19](#0-18)  The same test then demonstrates that both withdrawal and repayment revert with `MathOverflow`, leaving the market’s funds stuck. [20](#0-19)

pub fn update_supply_index(env: &Env, supplied: Ray, old_index: Ray, rewards_increase: Ray) -> Ray {
    if supplied == Ray::ZERO || rewards_increase == Ray::ZERO {
        return old_index;
    }

    let total_supplied_value = supplied.mul(env, old_index);

    if total_supplied_value == Ray::ZERO {
        return old_index;
    }

    let new_value = total_supplied_value.checked_add(env, rewards_increase);
    let grown = fp_core::mul_div_floor_saturating(env, new_value.raw(), RAY, supplied.raw());

    Ray::from(grown.min(MAX_SUPPLY_INDEX_RAY).max(bounded_old))

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())

    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
