### Title
`EvmHost.dispatch(DispatchPost/DispatchGet)` charges the fee to `msg.sender` instead of the caller-supplied `payer` address, decoupling who pays from who is credited on refund - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch()` accepts a `DispatchPost`/`DispatchGet` struct that carries an explicit `payer` field — documented as "the account responsible for paying the fees" and "who receives a refund of the relayer fees if the request times out" [1](#0-0) . However, the actual fee-token collection in `dispatch()` pulls funds from `_msgSender()`, not from `post.payer`/`get.payer`, while the commitment metadata used for the timeout refund records `post.payer` (for POST) as the beneficiary: [2](#0-1) . This is the same bug class as JOJO's `Funding.requestWithdraw`: a function takes an explicit account parameter meant to designate who is charged/paid, but the money-moving line uses `msg.sender` (or the reverse asymmetry) instead of that parameter, decoupling the party who pays from the party who is credited.

### Finding Description
In `EvmHost.dispatch(DispatchPost memory post)`:
- Fee-token payment path: `IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);` — funds are pulled from `_msgSender()` [3](#0-2) .
- The commitment that records who should be refunded on timeout is written as `_requestCommitments[commitment] = FeeMetadata({sender: post.payer, fee: post.fee});` — i.e., it stores the caller-supplied `payer`, not `_msgSender()` [4](#0-3) .
- On timeout, the protocol refunds `meta.sender` (i.e., the stored `payer`): `IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);` [5](#0-4) .
- For `dispatch(DispatchGet memory get)`, the same fee-collection-from-`_msgSender()` pattern exists [6](#0-5) , but curiously the recorded metadata there uses `_msgSender()` consistently (`FeeMetadata({sender: _msgSender(), fee: get.fee})` [7](#0-6) ), which is internally consistent for GET but inconsistent with the documented semantics of the `payer` field and with the POST path's behavior.

This is directly analogous to `Funding.requestWithdraw` in the referenced report: an explicit address argument (`from`/`payer`) is meant to identify the account that funds move to/from, but the state-changing operation is keyed to `msg.sender` in one place and to the parameter in another, so the two diverge whenever `msg.sender != payer`.

Any application built on `HyperApp` that calls `host.dispatch()` directly (rather than through the safe `dispatchWithFeeToken()` helper, which does correctly `safeTransferFrom(request.payer, ...)` before calling `dispatch` [8](#0-7) ) and sets `payer` to an address other than itself will have its own fee-token balance debited by `EvmHost`, while the refund-on-timeout entitlement is recorded against the unrelated `payer` address it supplied. Because nothing in `dispatch()` validates any relationship between `_msgSender()` and `post.payer` (no approval check, no equality check), any caller can set `payer` to an arbitrary third-party address.

### Impact Explanation
This breaks the invariant that "the account that pays the request's dispatch fee is the account that gets refunded if the request times out." Concretely:
- An app contract (or any direct caller of `EvmHost.dispatch`) that pays fees out of its own pooled balance but sets `payer` to an arbitrary address (attacker-controlled or otherwise) permanently loses those fee tokens to that address once the request times out, since the refund goes to `meta.sender = post.payer`, not to the party whose balance was actually debited.
- Conversely, integrators relying on the documented contract ("payer pays, payer is refunded on timeout") can be tricked or can accidentally misconfigure `payer`, causing relayer-fee refunds to be misdirected away from the entity that actually funded the request — a permanent loss of the fee-token principal for whoever gets `transferFrom`'d, with the credited party gaining assets they never contributed.
- This satisfies the "concrete theft or permanent freezing of funds" bar: fee-token balances are moved from `_msgSender()` and, on timeout, credited to an unrelated `payer` address chosen entirely by the caller.

### Likelihood Explanation
The vulnerability is trivially reachable by any single transaction: any address can call `EvmHost.dispatch(DispatchPost)` or `dispatch(DispatchGet)` directly and pass an arbitrary `payer` value, since `IDispatcher.dispatch` is a public/external entry point with no relationship check between `msg.sender` and `payer` [9](#0-8) . The severity of the exploit depends on integration patterns: applications that call `dispatch()` directly (bypassing `HyperApp.dispatchWithFeeToken`), or that let user input influence the `payer` field without also constraining who actually funds the fee token allowance, are directly exposed. Given `payer` is a first-class, documented field intended for exactly this delegation pattern, it is reasonable to expect real integrations use it this way.

### Recommendation
Make fee collection and refund crediting consistent and tied to the same account:
- In `dispatch(DispatchPost)` and `dispatch(DispatchGet)`, collect the fee-token payment from `post.payer` / `get.payer` (via `safeTransferFrom(post.payer, address(this), post.fee)`), not from `_msgSender()`, mirroring what `HyperApp.dispatchWithFeeToken` already does; if `payer == address(this)`/`payer == _msgSender()`, keep the current behavior as an optimization.
- Alternatively, if the design intent is that `_msgSender()` is always the one who pays, then store `sender: _msgSender()` (not `post.payer`) in `_requestCommitments` for the POST path, exactly as already done for the GET path, so refunds always go to whoever actually paid.
- Add an explicit invariant check (e.g., revert unless `payer == _msgSender()` or `payer` has approved/pre-funded the exact fee) so third parties cannot silently redirect refund entitlements away from whoever is charged.

### Proof of Concept
1. Attacker (or a misconfigured app contract `App`) holds fee tokens and has approved `EvmHost` to spend them.
2. `App` calls `EvmHost.dispatch(DispatchPost({ ..., fee: X, payer: victimOrAttackerControlledAddress, ... }))` directly (not via `dispatchWithFeeToken`).
3. `EvmHost.dispatch` executes `IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), X)` — debiting `App`'s balance for `X` fee tokens [3](#0-2) .
4. `EvmHost.dispatch` stores `_requestCommitments[commitment] = FeeMetadata({sender: payer, fee: X})` [4](#0-3)  — crediting the unrelated `payer` address, not `App`.
5. If the request later times out, `handlePostRequestTimeout`/equivalent path refunds `meta.sender` (the `payer` address) the full fee `X` [5](#0-4)  — `App` never recovers the `X` fee tokens it was actually debited, and `payer` receives tokens it never contributed.

Note: I could not fully verify `fundRequest` (which also lets an existing request's fee be topped up) or whether any other guard elsewhere in the contract restricts `payer` to equal `_msgSender()`, since the file read for that section did not complete before the tool budget ran out. This should be double-checked in a full review of `evm/src/core/EvmHost.sol` (particularly the `fundRequest` function and any `_msgSender()`/`payer` equality checks that may exist elsewhere in the file) before treating this as fully confirmed.

    function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
        if (msg.value > 0) {
            address[] memory path = new address[](2);
            address uniswapV2 = _hostParams.uniswapV2;
            path[0] = IUniswapV2Router02(uniswapV2).WETH();
            path[1] = feeToken();
            IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
                post.fee, path, address(this), block.timestamp
            );
        } else if (post.fee > 0) {
            IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
        }

        // adjust the timeout
        uint64 timeoutTimestamp = post.timeout == 0 ? 0 : uint64(block.timestamp) + uint64(post.timeout);
        PostRequest memory request = PostRequest({
            source: host(),
            dest: post.dest,
            nonce: uint64(_nextNonce()),
            from: abi.encodePacked(_msgSender()),
            to: post.to,
            timeoutTimestamp: timeoutTimestamp,
            body: post.body
        });

        // make the commitment
        commitment = request.hash();
        _requestCommitments[commitment] = FeeMetadata({sender: post.payer, fee: post.fee});
        emit PostRequestEvent({
            source: string(request.source),
            dest: string(request.dest),
            from: _msgSender(),
            to: abi.encodePacked(request.to),
            nonce: request.nonce,
            timeoutTimestamp: request.timeoutTimestamp,
            body: request.body,
            fee: post.fee
        });

    function dispatchWithFeeToken(DispatchPost memory request) internal returns (bytes32) {
        address hostAddr = host();
        address feeToken = IDispatcher(hostAddr).feeToken();
        if (request.payer != address(this)) IERC20(feeToken).safeTransferFrom(request.payer, address(this), request.fee);
