## Analysis

This CVE is an internal-invariant/assertion failure: JerryScript re-derives the same timezone-adjustment value at two points and asserts they must match, but a mutation between the two computations breaks that assumption, crashing the interpreter. The alt.fun analog to "an invariant the code treats as an assertion, but which an attacker can actually break" lives in `Router._computeBuy`'s overflow-cap branch, which is explicitly documented as depending on an invariant that can be violated by a direct token donation to the `Pair`.

`Router._computeBuy` computes the capped state like this: [1](#0-0) 

The cap branch subtracts the live, donation-inflatable `pair.tokenBalance()` from the *virtual* stored `reserveToken`:

```
uint256 realBalance = pair.tokenBalance();
if (tokensOut > realBalance) {
    tokensOut = realBalance;
    uint256 cappedReserveToken = reserveToken - tokensOut;   // <-- underflow if realBalance > reserveToken
    if (cappedReserveToken == 0) revert OverflowCapDegenerate();
    ...
}
```

The project's own test suite documents this as an invariant, not a guaranteed on-chain property: [2](#0-1) 

The comment states plainly: *"if it ever ceased to hold, that branch would revert with `OverflowCapDegenerate` rather than over-pay."* But the invariant only holds when `tokenBalance()` tracks `reserveToken` through curve swaps alone. Any unrelated ERC20 transfer of the launched `Token` directly into the `Pair` (a donation an unprivileged trader can always send, since `Token` is a plain ERC20) increases `pair.tokenBalance()` without moving `reserveToken`. `Pair.sol` never resyncs `_pool.tokenReserve` against live balance except through `swap`/`mint`, both gated to `onlyRouter`: [3](#0-2) 

The launch-time gap between virtual `reserveToken` and real `tokenBalance` is a fixed 250M-token constant (`LP_RESERVE`) that shrinks 1:1 with every wei donated directly to the pair: [4](#0-3) 

Once cumulative donations reach that 250M-token gap, `tokenBalance() >= reserveToken`. From that point, any buy whose uncapped `tokensOut` exceeds the (now donation-inflated) `realBalance` enters the cap branch and computes `cappedReserveToken = reserveToken - tokensOut`, where `tokensOut` was just set to `realBalance ≥ reserveToken` — this **underflows** and reverts with Solidity's raw arithmetic-underflow panic instead of the intended `OverflowCapDegenerate` custom error, permanently DoS-ing the finishing buy on that curve. Since the supply-side graduation trigger (`IPair.tokenBalance() == 0`) can never be satisfied once real balance is inflated by donations either, the curve can become permanently un-completable via the supply leg, and any large buy near the tail of the curve reverts unexpectedly — a freeze of trader funds/curve completion, not merely a cosmetic revert-message change.

### Title
Direct token donations to the curve `Pair` can invert the virtual/real reserve gap and brick `Router._computeBuy`'s overflow cap - ([File: packages/contracts/src/Router.sol])

### Summary
`Router._computeBuy`'s overflow-cap branch assumes `pair.tokenBalance() < pair.tokenReserve()` always holds (a 250M-token gap fixed at launch). This assumption is only true absent donations. An unprivileged holder of the launched `Token` can `transfer` tokens directly into the `Pair` address, inflating `tokenBalance()` without moving the stored `tokenReserve`. Once cumulative donations close the 250M gap, the cap-branch subtraction `reserveToken - tokensOut` underflows and reverts with a raw Solidity panic instead of behaving as designed.

### Finding Description
`_computeBuy` in [1](#0-0)  caps `tokensOut` at `pair.tokenBalance()` when the uncapped constant-product output would exceed the real sellable balance, then back-solves `amountInUsed` via `cappedReserveToken = reserveToken - tokensOut`. This is only safe while `reserveToken - realBalance` stays positive — an invariant the project's own graduation-invariant test explicitly calls out as load-bearing but not enforced on-chain: [5](#0-4) .

`Token.sol` is a standard ERC20 clone with no transfer restriction to the pair address, so any address holding launched tokens (e.g. an earlier curve buyer) can shrink the gap by simply transferring tokens into the `Pair`. `Pair.sol`'s reserves are only ever mutated by `mint`/`swap` under `onlyRouter` [6](#0-5) , so a raw ERC20 `transfer` silently inflates `tokenBalance()` while `tokenReserve` (and hence the assumed 250M gap) stays frozen. Once enough tokens are donated to close that gap, the next buy attempting to hit the overflow-cap path underflows in `cappedReserveToken = reserveToken - tokensOut` (Solidity 0.8 panics rather than reaching the intended `OverflowCapDegenerate` guard), reverting the transaction.

### Impact Explanation
This freezes the bonding curve's completion path for that token: any buy sized to finish the curve (the intended "overflow-capped" trade) reverts unconditionally once the gap is closed, and the supply-side graduation trigger (`tokenBalance() == 0`) can never fire because the donated tokens permanently keep the real balance above zero. Legitimate traders attempting to buy out the remaining curve supply have their transactions revert, and the token can be stuck in `Lifecycle.Curve` unless it separately clears the USD-value graduation trigger. This is a freezing-of-funds/DoS impact reachable by any unprivileged token holder.

### Likelihood Explanation
The attack requires only holding/acquiring ~250M of the launched token's 750M curve-sellable supply and sending a plain ERC20 `transfer` to the `Pair` address — no privileged role, no reentrancy, and no interaction with `BONDING_ROLE`-gated functions is needed. It is capital-intensive (must own a large fraction of curve supply) but fully permissionless and requires only ordinary trading + one `transfer` call.

### Recommendation
Do not rely on the fixed launch-time gap between `reserveToken` and `tokenBalance()` as an unenforced invariant. In `Router._computeBuy`, clamp/guard the subtraction (`reserveToken - tokensOut`) so a donation-driven inversion cannot underflow — e.g., explicitly check `realBalance >= reserveToken` and handle it as a defined degenerate case (revert with `OverflowCapDegenerate` or otherwise short-circuit) rather than letting a raw panic occur, and/or have `_prepareGraduationLiquidity`/an anytime-callable sweep burn donated excess before it can close the gap, rather than only at graduation time.

### Proof of Concept
1. Launch a token via `Zap.createToken`, letting `curveSupply = 750M` real tokens sit in the `Pair` and `reserveToken` (virtual) start at `1e9`.
2. Buy a modest amount so the caller now holds launched `Token`s.
3. Repeatedly (or via multiple colluding/independent holders) `Token.transfer(pairAddr, amount)` directly to the `Pair`, donating tokens without going through `Router`/`Bonding`, until cumulative donations reach the 250M-token launch-time gap (`reserveToken - tokenBalance() ≈ 0`).
4. Call `Zap.buy`/`Bonding.buy` with an `amountIn` large enough that `_computeBuy`'s uncapped `tokensOut` exceeds the now-inflated `realBalance` — the transaction reverts with a raw arithmetic-underflow panic instead of completing or reverting with `OverflowCapDegenerate`, and the curve can no longer be driven to `tokenBalance() == 0` for the supply-side graduation trigger.

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }

        uint256 tokenReserve,

    ) external onlyRouter returns (bool) {
        if (_pool.k != 0) revert AlreadyMinted();
        _pool = Pool({tokenReserve: tokenReserve, assetReserve: assetReserve, k: tokenReserve * assetReserve});
        emit Mint(tokenReserve, assetReserve);
        return true;
    }

    function swap(
        uint256 tokenIn,
        uint256 tokenOut,
        uint256 assetIn,
        uint256 assetOut
    ) external onlyRouter returns (bool) {
        uint256 newTokenReserve = (_pool.tokenReserve + tokenIn) - tokenOut;
        uint256 newAssetReserve = (_pool.assetReserve + assetIn) - assetOut;
        if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated();

        _pool.assetReserve = newAssetReserve;
        emit Swap(tokenIn, tokenOut, assetIn, assetOut);
