### Title
`Bonding.transferCreator` Permanently Reassigns Fee-Attribution Rights With No Confirmation Step, Unlike Every Other Sensitive Role-Transfer in the Protocol - (File: `packages/contracts/src/Bonding.sol`)

### Summary
`Bonding.transferCreator` reassigns a token's `creator` role — and with it, all future 0.25% creator-fee attribution — in a single, single-signature transaction with no second-party confirmation, timelock, or reversal mechanism. This is the same bug class as the referenced CVE: a permanent, high-value account/role change is executed on session-level authorization alone, with no secondary confirmation step to catch a hijacked session, a phished signature, or a fat-fingered address. Notably, the same codebase already recognizes this exact risk class and mitigates it everywhere else with `Ownable2StepUpgradeable` (`Bonding`, `Zap`, `FeeVault` owner transfers all require a two-step propose/accept), but `transferCreator` — which controls an economically identical "who gets paid" right — was left single-step.

### Finding Description
`transferCreator` is reachable by any address currently recorded as `info.creator` for a token, and performs the reassignment unconditionally in one call: [1](#0-0) 

```
function transferCreator(address tokenAddress, address newCreator) external {
    if (newCreator == address(0)) revert ZeroAddress();
    TokenInfo storage info = _s().tokenInfo[tokenAddress];
    if (msg.sender != info.creator) revert NotCreator();
    if (newCreator == info.creator) revert InvalidInput();
    info.creator = newCreator;
    emit CreatorTransferred(tokenAddress, msg.sender, newCreator);
}
```

`info.creator` is the sole source of truth `Zap` reads to attribute every future fee accrual on that token: [2](#0-1)  — "Creator attribution comes from `Bonding.tokenInfo(token).creator` (set at launch, updatable via `transferCreator`)." Every subsequent buy/sell on that token — curve or post-graduation — routes its 0.25% creator cut to whatever address is currently in `info.creator` via `FeeVault.accrue`, which credits `creatorBalance[creator]` by that address, not by the original launcher: [3](#0-2) .

By contrast, every other role/ownership transfer in this codebase deliberately uses a two-step pattern precisely to prevent an irreversible mistake or a single compromised signature from causing permanent loss — see `FeeVault`'s own doc comment: [4](#0-3)  ("Uses `Ownable2StepUpgradeable` so a bad `transferOwnership` can be cancelled ... before it takes effect — single-step transfer to a fat-fingered or contract-incompatible address would otherwise brick every owner-only path"), and confirmed for `Bonding`/`Zap` in the ownership-transfer test suite: [5](#0-4) . `transferCreator` grants no such safety net despite controlling an economically live, perpetual revenue stream (creator fees accrue for as long as the token trades, including post-graduation on HyperSwap).

The unprivileged test confirms the single-step, unconditional nature of the transfer: [6](#0-5) .

### Impact Explanation
Any temporary compromise of the creator's signing capability — a shared/public device, a malicious dApp popup, a phished signature, session-key leakage, or simple key-management error — allows a single `transferCreator(tokenAddress, attacker)` call to permanently and silently redirect **all future** 0.25%-of-volume creator fees for that token to the attacker's address. Because there is no accept/confirm step, no timelock, and no way to detect-and-cancel before it takes effect (unlike `Ownable2Step`'s pending-owner window), the legitimate creator has no recourse once the transaction lands — this is a permanent freezing/theft of an ongoing revenue stream, directly analogous to the referenced report's "irreversible account action taken without re-confirmation." For actively-traded tokens this can represent a substantial, continuously-accruing loss with no on-chain remediation path (the original creator would have to convince the new holder to call `transferCreator` back, or ask the protocol owner — who has no override for this field).

### Likelihood Explanation
The call requires only that `msg.sender == info.creator`, i.e. exactly the session/key an attacker would obtain via the same access-sharing/session-hijack scenario described in the source report. No special timing, no race condition, and no privileged role are needed — this is a single, permissionless-to-the-legitimate-caller transaction. The primary friction is the same as the CVE's precondition (temporary access to an authenticated session/key), which the rest of the codebase explicitly treats as a real threat model worth defending against via two-step transfers.

### Recommendation
Convert `transferCreator` to a two-step propose/accept pattern (mirroring the existing `Ownable2StepUpgradeable` usage elsewhere in the protocol): store a `pendingCreator[token]` on the first call, and require the new address to call an `acceptCreator(token)` function before `info.creator` is updated. Optionally add a cancellation path and/or a minimum delay, consistent with the safeguards already applied to `Bonding`/`Zap`/`FeeVault` ownership transfers.

### Proof of Concept
1. Creator `C` launches `Token T` via `Zap.createToken`, becoming `Bonding.tokenInfo(T).creator == C`.
2. `T` trades over time, accruing creator fees to `C` in `FeeVault`.
3. `C`'s session/key is temporarily exposed (shared machine, phished signature, leaked session — same precondition as CVE-2025-47272).
4. Attacker, using that session, submits `bonding.transferCreator(T, attacker)`. The call succeeds in one transaction with no confirmation, per the code at `packages/contracts/src/Bonding.sol:738-748`.
5. From that block forward, every `Zap.buy`/`Zap.sell` on `T` accrues its 0.25% creator fee to `attacker` via `FeeVault.accrue`, permanently and irreversibly, as shown by `test_transferCreator` at `packages/contracts/test/Bonding.t.sol:604-611` demonstrating the unconditional, single-call state change.

```text
    function accrue(
        address token,
        address creator,
        uint256 creatorAmount,
        uint256 protocolAmount,
        bool isBuy
    ) external onlyDepositor {
        FeeVaultStorage storage $ = _s();
        if (creatorAmount > 0) {
            if (creator == address(0)) revert ZeroAddress();
            $.creatorBalance[creator] += creatorAmount;
            $.totalAccruedCreator += creatorAmount;
            $.lifetimeCreatorEarned[creator] += creatorAmount;
        }
        if (protocolAmount > 0) {
            $.protocolBalance += protocolAmount;
            $.lifetimeProtocolEarned += protocolAmount;
        }
        if ($.usdc.balanceOf(address(this)) < $.totalAccruedCreator + $.protocolBalance) {
            revert UnderfundedAccrual();
        }
        emit FeeAccrued(token, creator, creatorAmount, protocolAmount, isBuy);
    }
```
