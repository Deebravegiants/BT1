## Finding: Webhook `shop` field is not covered by the HMAC signature, enabling cross-tenant webhook spoofing

The webhook processing pipeline validates only the raw request body against the HMAC signature, while the `shop` (tenant identifier) is read from an unauthenticated header and passed straight through to the app's handler.

### Root cause

`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, and `#hmac` reads the `X-Shopify-Hmac-SHA256` header: [1](#0-0) [2](#0-1) 

The `shop` attribute is read from the `x-shopify-shop-domain`/`shopify-shop-domain` header, entirely independent of the signed bytes: [3](#0-2) 

`HmacValidator.validate` only checks `hmac` against `to_signable_string` (the raw body) — it never touches `shop`, `topic`, or `webhook_id`: [4](#0-3) 

`Registry.process` validates the HMAC, then immediately trusts `request.shop` to build the `WebhookMetadata` handed to the app's handler, with no additional binding check between the shop header and the signed body: [5](#0-4) 

### The broken binding

The identity binding that should hold is:
`hmac == HMAC(secret, body || shop)`, i.e. the tenant identifier should be cryptographically bound to the signed payload.

What is actually implemented is:
`hmac == HMAC(secret, body)` while `shop` is taken from an untrusted header, so:
`shop_verified (header) ≠ shop_bound_by_hmac (nothing)`.

### Why this is exploitable by an unprivileged party

The webhook HMAC secret is the app's single `api_secret_key`/`client_secret`, shared across **every** shop that installs the app — it is not per-tenant. Any attacker can:
1. Install the target app on their own (attacker-controlled) development/trial shop — this requires no special privilege, just being any Shopify merchant.
2. Trigger any webhook topic the app subscribes to (e.g. `orders/create`, `customers/data_request`, `app/uninstalled`) on their own shop, capturing a legitimate `(raw_body, X-Shopify-Hmac-SHA256)` pair signed by the app's real secret.
3. Replay that exact body+HMAC to the app's webhook endpoint, but substitute `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` passes (only the body is checked), and `Registry.process` hands the handler a `WebhookMetadata` claiming `shop: "victim-shop.myshopify.com"` with attacker-controlled `body`.

Because `data.shop` is the field host applications use to select the tenant's DB record/session to act on (as shown in the gem's own webhook documentation example), this allows an attacker to inject forged webhook events attributed to a victim shop — a cross-tenant confusion/spoofing primitive stemming directly from this gem's failure to bind the tenant identity to the authenticated bytes. [6](#0-5) 

### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs/verifies only the raw JSON body via HMAC, while `shop`, `topic`, and `webhook_id` are read from unauthenticated HTTP headers and passed unmodified to the app's `WebhookHandler`. Since the webhook signing secret (`api_secret_key`) is shared across all shops that install a given app, any attacker who installs the app on their own shop can capture a validly-signed `(body, hmac)` pair and replay it with a forged `shop-domain` header pointing at a victim tenant, causing the handler to process attacker-controlled data as if it belonged to the victim shop.

### Finding Description
`Utils::HmacValidator.validate` computes/compares the HMAC solely over `verifiable_query.to_signable_string`, which for `Webhooks::Request` returns only `@raw_body`. The `shop` header used downstream (`WebhookMetadata.shop`) is never included in this signable string, so it carries no cryptographic guarantee of authenticity or binding to the signed body.

### Impact Explanation
This breaks tenant isolation (cross-tenant access), classified as Critical per the given impact categories, because any app relying on `data.shop` from this library to select which merchant's session/data to act on can be tricked into operating on the wrong tenant using attacker-supplied body content, using only a body+HMAC pair the attacker legitimately obtained for their own shop.

### Likelihood Explanation
High likelihood: no special privilege or leaked credential is needed — only signing up as any Shopify merchant/dev store, installing the target app, and triggering one webhook event on their own store to obtain a valid `(body, hmac)` pair, then replaying it with a modified header.

### Recommendation
Bind the tenant identity to the authenticated bytes: include `shop`, `topic`, and `webhook_id` in the signable string used for HMAC verification (matching how Shopify's actual outbound webhook signature is computed, or otherwise require the consuming application to cross-check `data.shop` against a shop it already trusts, e.g. an existing stored session) rather than trusting the header value on its own.

### Proof of Concept
1. Attacker installs target app on `attacker-shop.myshopify.com`.
2. Attacker triggers `orders/create` webhook; captures raw body `B` and header `X-Shopify-Hmac-SHA256: H` (both legitimately generated by Shopify using the app's real secret).
3. Attacker sends a new POST to the app's webhook endpoint:
   - `X-Shopify-Hmac-SHA256: H`
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   - `X-Shopify-Topic: orders/create`
   - Body: `B` (or any content attacker can get validly signed for their own shop)
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H`.
5. The registered handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: ..., ...)`, causing the app to act on `victim-shop`'s data using attacker-influenced content. [5](#0-4)
