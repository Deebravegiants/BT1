## Title
Infinite loop / DoS in `AncestryChain::ancestry` via crafted cyclic `parent_hash` pointers in an unprivileged GRANDPA consensus proof - (File: `modules/consensus/grandpa/primitives/src/justification.rs`)

### Summary
The GRANDPA consensus client's `ConsensusClient::verify_consensus` path builds an `AncestryChain` map directly from the attacker-supplied, unverified `unknown_headers` field of a submitted `FinalityProof`, and walks it with a `while` loop that has no bound on iteration count or cycle detection. A relayer can submit a consensus update whose `unknown_headers` contain headers with mutually pointing `parent_hash` fields, creating a cycle that the walk can never escape, causing the runtime to hang.

### Finding Description
`AncestryChain::ancestry` walks a hash-keyed map from a target block back toward a base block: [1](#0-0) 

The map itself is constructed straight from the proof's `unknown_headers`, with no validation that they form an acyclic, connected chain: [2](#0-1) 

Because each `H` (SubstrateHeader) is an attacker-controlled struct, its `parent_hash` field is not constrained to correspond to any real chain relation — the header's own hash is derived from its fields, but nothing stops the prover from setting header `A.parent_hash = hash(B)` and header `B.parent_hash = hash(A)`, producing a 2-node (or larger) cycle in the `BTreeMap<Hash, Header>`.

Critically, `verify_grandpa_finality_proof` invokes this unbounded walk **before** the justification's cryptographic signatures are checked: [3](#0-2) 

`headers.ancestry(from, target.hash())` at line 88 runs before `justification.verify(...)` at line 91. So an attacker does not need a valid GRANDPA authority signature at all — only a self-consistent cyclic set of headers that decode successfully. Once `current_hash` enters the cycle, `while current_hash != base` never becomes false (assuming `base`/`from` is not part of the cycle), and the loop runs forever, with no depth counter, weight metering escape, or timeout — directly analogous to the `TNEFFillMapi` infinite-loop bug class in CVE-2017-6299 (unbounded loop over attacker-supplied structured data with no cycle/size guard).

This is reachable via `GrandpaConsensusClient::verify_consensus`, which decodes an untrusted `ConsensusMessage`/`FinalityProof` supplied as the `proof` argument of a consensus-update dispatch — the standard, unprivileged relayer-submitted path into `pallet-ismp`'s consensus update mechanism: [4](#0-3) 

The same `AncestryChain::ancestry` call is also used inside `GrandpaJustification::verify_with_voter_set` for each precommit's ancestry route, another unprivileged-reachable invocation: [5](#0-4) 

### Impact Explanation
This is a message-dispatch-reachable infinite loop in consensus-state verification: any unprivileged relayer can submit a GRANDPA consensus update whose `unknown_headers` decode successfully (basic SCALE decoding, no cryptographic pre-check) but contain a `parent_hash` cycle. Execution of that consensus update then hangs the runtime call indefinitely inside `ancestry()`, with no upper bound on loop iterations, no cycle guard, and the hang occurs before any signature/finality validation rejects the proof. On a Substrate-based chain, an unbounded native loop inside runtime execution can stall/DoS block production for the extrinsic executing it (denial of service on the state-machine finality-verification pipeline used by Hyperbridge's GRANDPA client), preventing new consensus/message proofs from being processed — i.e., "a route unable to deliver messages."

### Likelihood Explanation
Likelihood is moderate: the attacker must craft two or more `unknown_headers` whose `parent_hash` fields point to each other, which is trivial (no cryptographic constraint links `parent_hash` to the referenced header's real content — the attacker fully controls all header fields). The proof must still decode via SCALE (`FinalityProof<SubstrateHeader>::decode_all`) and pass the `envelope_matches_state_machine` check, both easily satisfiable with a syntactically valid but semantically fabricated message. No valid GRANDPA signature is required because the ancestry walk executes before `justification.verify(...)`.

### Recommendation
Bound the `ancestry()` walk with an explicit maximum number of iterations (e.g., equal to `self.ancestry.len() + 1`) and return `finality_grandpa::Error::NotDescendent` (or a similar bounded error) once that bound is exceeded, rather than relying solely on reaching `base`. Additionally, consider validating that `unknown_headers` form a strictly increasing, non-repeating chain by block number before constructing the `AncestryChain`, and moving any expensive ancestry computation after cheap validity checks (e.g., after or alongside justification signature verification) so malformed/cyclic input is rejected before doing unbounded work.

### Proof of Concept
1. Construct header `B` with an arbitrary `parent_hash = H_A` (to be set) and other fields.
2. Compute `hash(B)`.
3. Construct header `A` with `parent_hash = hash(B)`.
4. Compute `hash(A) = H_A`, then set/confirm `B.parent_hash = H_A` (headers can be constructed in either order since `parent_hash` is just a field value, not a Merkle-verified reference).
5. Set `finality_proof.unknown_headers = [A, B, ...]`, with `target = A` (highest number) and `base = B` (lowest number), and any `from` (consensus state's `latest_hash`) that is not equal to `A`, `B`, or reachable from them.
6. Submit this as the `proof` bytes for a `ConsensusMessage::Polkadot`/`Relaychain` update via the GRANDPA `ConsensusClient::verify_consensus` entry point (reachable through pallet-ismp's unsigned/relayer consensus-update dispatch).
7. Execution enters `AncestryChain::ancestry(from, target.hash())` at `verify_grandpa_finality_proof` (line 88), which loops indefinitely between `A` and `B` because `current_hash` never equals `base`/`from`, hanging before signature verification ever runs.

impl<H: HeaderT> finality_grandpa::Chain<H::Hash, H::Number> for AncestryChain<H>
where
	H::Number: finality_grandpa::BlockNumberOps,
{
	fn ancestry(
		&self,
		base: H::Hash,
		block: H::Hash,
	) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
		let mut route = vec![block];
		let mut current_hash = block;
		while current_hash != base {
			match self.ancestry.get(&current_hash) {
				Some(current_header) => {
					current_hash = *current_header.parent_hash();
					route.push(current_hash);
				},
				_ => return Err(finality_grandpa::Error::NotDescendent),
			};
		}
		Ok(route)
	}
}
