### Title
LP share-price manipulation via unprivileged direct `FungibleAsset` deposit into pool reserves - (File: `aptos-move/move-examples/swap/sources/liquidity_pool.move`)

### Summary
The AMM `liquidity_pool::mint` function computes the number of LP tokens minted to a depositor using the pool's raw fungible-asset *balances* (`fungible_asset::balance(store_1/store_2)`) as the reserve figures, rather than an internally-tracked, deposit-gated accounting value. Because `fungible_asset::deposit` is a permissionless operation (any holder of a `FungibleAsset` can deposit it into any known `FungibleStore` address, not just via the pool's `mint`/`swap` entrypoints), an attacker can inflate the reserves of a thinly-liquid pool without minting LP tokens for that inflation, corrupting the ratio calculation that determines how many LP shares a subsequent depositor receives. This is the same "attacker seeds an unprivileged input to a balance-based ratio check/formula, causing another user's legitimate action to compute a corrupted, disadvantageous result" pattern as the TribeRedeemer `balance != 0` / `amountIn * balance / base` bug.

### Finding Description
In `liquidity_pool::mint` (`aptos-move/move-examples/swap/sources/liquidity_pool.move:387-439`):

```
let reserve_1 = fungible_asset::balance(store_1);
let reserve_2 = fungible_asset::balance(store_2);
let lp_token_supply = option::destroy_some(fungible_asset::supply(pool));
...
let token_1_liquidity = math64::mul_div(amount_1, (lp_token_supply as u64), reserve_1);
let token_2_liquidity = math64::mul_div(amount_2, (lp_token_supply as u64), reserve_2);
math64::min(token_1_liquidity, token_2_liquidity)
```

`reserve_1`/`reserve_2` are read directly from the pool's underlying `FungibleStore` balances (`pool_data.token_store_1`/`token_store_2`), the same store addresses used by `get_amount_out` at lines 321-322. These stores are ordinary `FungibleStore` objects; deposits into a `FungibleStore` via `fungible_asset::deposit` do not require pool-module involvement or a signer check tying the caller to the pool — any address holding the underlying asset can transfer tokens straight into `store_1`/`store_2`.

Because the LP-token amount minted for a non-first depositor is `amount * lp_token_supply / reserve`, an attacker who (a) becomes the pool's initial LP with a minimal amount (bypassing `MINIMUM_LIQUIDITY` protection, which only guards the *first* mint from being zero) and (b) then donates a large amount of the underlying assets directly into `store_1`/`store_2` (outside of `mint`), inflates `reserve_1`/`reserve_2` without any corresponding increase to `lp_token_supply`. A subsequent legitimate LP's deposit is then divided by this inflated denominator, causing `token_1_liquidity`/`token_2_liquidity` to round down toward zero — either aborting via `EINSUFFICIENT_LIQUIDITY_MINTED` (`liquidity_pool.move:425`) or minting the victim a disproportionately small number of LP shares for a large deposit. The attacker, holding effectively all LP supply, then withdraws the pool's true reserves (including the victim's freshly-deposited liquidity) via LP-token burn/withdraw, extracting the victim's assets.

This directly parallels the reported bug's custody invariant: a value-distribution calculation trusts a balance the attacker can freely inflate through means outside the "intended" deposit path, corrupting share/exchange-rate math and diverting value to the attacker.

### Impact Explanation
This is a custody-accounting corruption of the pool's core value pointer: `lp_token_supply` no longer reflects claim rights over `reserve_1`/`reserve_2`. A victim LP's deposited fungible assets (real, mainnet value) can be captured almost entirely by the attacker who controls the LP-token supply, i.e., theft of fungible-asset custody via manipulated share issuance — a classic "vault/AMM donation" attack, high severity because it is a direct and irreversible transfer of victim funds to an attacker.

### Likelihood Explanation
Requires the attacker to front-run or otherwise be the first (or an early, low-liquidity) LP of a given `(token_1, token_2, is_stable)` pool — pools are permissionlessly creatable (`create_lp_token`/pool registration logic elsewhere in the file), so an attacker can create a pool, become sole LP with minimal liquidity, then wait for/target a victim's deposit. Both `store_1`/`store_2` addresses are discoverable on-chain (stored in `LiquidityPool` resource, emitted in `CreatePool`/`Swap` events), so no privileged information is needed. This mirrors the external report's judged severity (Medium/High): external preconditions exist (attacker must seed the pool and donate), but no privileged access or governance assumption is required — it is a standard, well-documented AMM/ERC-4626-style donation attack.

### Recommendation
- Track pool reserves via internal accounting (updated only through `mint`/`swap`/`burn`) instead of querying `fungible_asset::balance(store)` directly, or reconcile "unexpected" balance excess by crediting it fairly/rejecting it.
- Increase/enforce a meaningful `MINIMUM_LIQUIDITY` burn relative to expected pool sizes, and/or require a minimum first-deposit size.
- Consider virtual/offset reserves (as used in some AMMs) to make donation-based reserve inflation economically infeasible.

### Proof of Concept
1. Attacker creates a new liquidity pool for `(TokenA, TokenB)` and calls `mint` with `amount_1 = amount_2 = 1`, becoming the sole LP (subject to `MINIMUM_LIQUIDITY`, `liquidity_pool.move:413-417`).
2. Attacker directly calls `fungible_asset::deposit(store_1, huge_amount_of_TokenA)` and `fungible_asset::deposit(store_2, huge_amount_of_TokenB)` using the pool's known store addresses — bypassing `mint` entirely, so `lp_token_supply` stays unchanged while `reserve_1`/`reserve_2` balloon.
3. Victim calls `mint` with a reasonable deposit (`amount_1`, `amount_2`); `math64::mul_div(amount_1, lp_token_supply, reserve_1)` rounds to 0 or a negligible value due to the inflated `reserve_1` (`liquidity_pool.move:421-423`), so the victim either gets reverted (`EINSUFFICIENT_LIQUIDITY_MINTED`) after their deposit is already added to the pool via subsequent code paths, or receives a tiny LP share.
4. Attacker, holding all/most LP supply, burns LP tokens to withdraw the pool's full reserves, capturing the victim's deposited assets.
