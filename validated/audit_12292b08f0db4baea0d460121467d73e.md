### Title
Webhook `shop` (and `topic`/`api-version`/`webhook-id`) headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw body for HMAC verification, but `Registry.process` trusts the unauthenticated `shop` header to identify which merchant/tenant the event belongs to. An attacker who can obtain one legitimate `(body, hmac)` pair (trivially, by installing the app on their own store and receiving a webhook) can replay that exact body/HMAC while substituting the `x-shopify-shop-domain` header to impersonate a different, victim tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` (and `topic`, `api_version`, `webhook_id`) are read straight from HTTP headers with no cryptographic binding to the signed payload: [2](#0-1) 

`HmacValidator.validate` only verifies `verifiable_query.to_signable_string`, i.e., only the body bytes, never the headers: [3](#0-2) 

`Registry.process` validates the HMAC (body-only) and then hands the handler the **unauthenticated** `request.shop` value as the tenant identifier: [4](#0-3) 

This reproduces the report's root cause exactly: an identity/binding value (`requestId` in the report, `shop` here) is used to route/act on a request but is generated/consumed **outside** the value that is actually authenticated (the nonce/oracle response in the report, the HMAC-signed body here). The equality that should hold is:

```
authenticated_bytes (HMAC-covered body) == identity_used_by_handler (shop header)
```

but the gem only guarantees `authenticated_bytes == body`, while `identity_used_by_handler = shop_header`, which is never included in the signable string. These two are independent, so an attacker fully controls the identity binding while reusing a validly-signed body.

### Impact Explanation
This is a cross-tenant access vector (Critical, per the report categories): a merchant/attacker who is a genuine, unprivileged installer of the app (no special privileges, no leaked secret, no TLS interception) can:
1. Install the app on their own store, or otherwise cause the app to deliver/receive one legitimate webhook for a given topic — capturing a valid `(raw_body, x-shopify-hmac-sha256)` pair.
2. Replay that exact body and HMAC to the app's webhook endpoint, but with `x-shopify-shop-domain` (and/or `x-shopify-topic`/`x-shopify-webhook-id`) rewritten to point at a victim shop.
3. `Utils::HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: <victim-shop>, body: <attacker-chosen-but-previously-signed-body>, ...)`, causing the host application to process/attribute the event to the wrong tenant.

Depending on the handler's use of `shop`, this can lead to state corruption, data written under the wrong shop record, or triggering actions/side effects tied to the victim tenant using attacker-controlled body content (bounded to whatever body was originally validly signed for some topic).

### Likelihood Explanation
Likelihood is Low/Moderate: exploitation requires the attacker to first obtain a legitimately signed `(body, hmac)` pair, which is realistic for any attacker who can install the target app on their own development/trial store (a normal, unprivileged action for any Shopify app) and capture the webhook delivery. No `api_secret_key`, access token, or privileged account is needed to mount the spoof itself — only the header value needs to be forged, which any unprivileged internet user with network access to the app's webhook endpoint can do directly.

### Recommendation
Bind the tenant/topic identity into the signed material, mirroring the report's fix of mixing `orderId` into `requestId`:
- Include `shop`, `topic`, `api_version`, and `webhook_id` in `Request#to_signable_string` (or otherwise cryptographically bind them, e.g., by having `HmacValidator`/`Registry.process` re-derive/verify these fields against a signed value rather than trusting raw headers), so a valid HMAC can only be produced for the specific header set it was issued for.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives (or causes) delivery of a real webhook, capturing:
   - `raw_body = "{...attacker order data...}"`
   - `x-shopify-hmac-sha256 = HMAC(api_secret_key, raw_body)` (valid, since body-only signing per [1](#0-0) )
2. Attacker POSTs to the victim app's webhook endpoint with the **same** `raw_body` and `x-shopify-hmac-sha256`, but sets:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the HMAC: [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload was never generated for, or authorized by, that shop — a cross-tenant identity-binding break.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
