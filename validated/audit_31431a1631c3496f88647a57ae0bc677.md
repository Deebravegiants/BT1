### Title
Webhook shop identity spoofing via HMAC that only covers the request body - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` only validates the HMAC over the raw webhook body, but the `shop`, `topic`, and `webhook_id` values consumed and forwarded to the app's handler come from unauthenticated headers that are never included in the signed payload. An attacker who has legitimately received one valid `(body, hmac)` pair for the app (e.g. by installing the app on their own shop, which is unprivileged) can replay that exact body/HMAC to the app's real webhook endpoint while forging the `X-Shopify-Shop-Domain` header to name a different, victim shop. Because the shop identifier is never bound to the HMAC, `Registry.process` will accept the forged request and hand the handler a `WebhookMetadata` claiming to belong to the victim shop, breaking the tenant boundary the handler relies on.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to the presented `hmac`: [1](#0-0) 

For webhooks, `to_signable_string` is defined to be only the raw body: [2](#0-1) 

But `shop`, `topic`, and `webhook_id` are pulled straight from HTTP headers that are not part of the signable string at all: [3](#0-2) 

`Registry.process` validates only the HMAC, then immediately trusts `request.shop` (together with `request.topic` and `request.webhook_id`) to construct the `WebhookMetadata` passed to the app-registered handler — with no secondary check that the shop matches the one the HMAC/body actually originated from: [4](#0-3) 

The identity binding that should hold is: `shop authenticated by the app’s webhook trust boundary == shop bytes covered by the verified HMAC`. In this implementation that equality does not hold — the HMAC verifies only the body bytes, while `shop` (the tenant identifier acted upon by the handler) is taken from unsigned bytes. This is the equivalent of the `LineOfCredit` bug class in the report: a value acted upon (there, accrued interest; here, the shop/tenant binding) is not actually covered by the mechanism (there, the accounting update; here, the HMAC) that is supposed to guarantee its correctness.

### Impact Explanation
Because the shop domain is not bound to the HMAC, any unprivileged actor who can install the target app on their own store (a completely unprivileged, self-service action for any public Shopify app) can obtain a valid `(raw_body, hmac)` pair signed with the app's shared `api_secret_key`. They can then replay that exact pair to the app's real webhook endpoint while substituting the `X-Shopify-Shop-Domain` header (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) to reference an arbitrary victim shop. `Registry.process` will accept this as fully authenticated and dispatch the handler believing the event is for the victim's shop, causing the host application to act on/against the wrong tenant's data (e.g. update state, sync data, or issue Admin API calls scoped to the wrong shop's session). This satisfies the Critical "cross-tenant access" impact category, since it crosses the fundamental multi-tenant boundary this gem is meant to enforce for webhook processing.

### Likelihood Explanation
Likelihood is high for any app that:
1. Registers at least one webhook topic, and
2. Allows unrelated third parties to install the app (typical for any listed/public Shopify app).

No access token, `client_secret`, or privileged account is required — only the ability to install the app once on an attacker-controlled store to harvest a valid `(body, hmac)` pair, then a single forged HTTP POST to the app's public webhook callback URL.

### Recommendation
Bind the shop identity to the HMAC verification, not just the raw body:
- Include the shop domain (and ideally topic/webhook id) in the signable string used for HMAC computation, or
- After HMAC validation, cross-check `request.shop` against the shop associated with the session/store that installed the app (e.g., verify it is a known, previously-onboarded shop) before dispatching to the handler, or
- Document and enforce that handlers must independently re-validate `data.shop` against their own store of installed shops before trusting it, and make `Registry.process` fail closed if no such shop registry is configured.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and registers/receives any webhook (e.g. `orders/create`), capturing the exact raw body and the `X-Shopify-Hmac-Sha256` value Shopify sent.
2. Attacker crafts a new HTTP POST to the app's public webhook endpoint using the exact same raw body and HMAC header, but replaces:
   - `X-Shopify-Shop-Domain: victim.myshopify.com`
3. The app calls `ShopifyAPI::Webhooks::Registry.process(ShopifyAPI::Webhooks::Request.new(raw_body:, headers:))`.
4. `Utils::HmacValidator.validate` succeeds because it only re-hashes `raw_body`, which is unchanged: [5](#0-4) 
5. The handler is invoked with `WebhookMetadata` whose `shop` is `"victim.myshopify.com"`, even though the payload never originated from Shopify for that shop: [6](#0-5) 
6. Any host-application logic keyed on `data.shop` (e.g., updating stored order data, triggering side effects scoped to "victim.myshopify.com") now executes against the wrong tenant.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
