### Title
Webhook Shop-Tenant Identity Not Covered by HMAC Signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identifier (`shop`) from an HTTP header that is never included in the HMAC-signed material. `HmacValidator.validate` only proves the integrity of the raw request body; it says nothing about which shop the request claims to be from. Any component (`shop-domain` header) trusted to route or scope a webhook to a merchant/tenant can be swapped without invalidating the signature. This is the same bug class as the report's "field acted on but not covered by the guarding check" — here the binding broken is `HMAC-verified bytes == bytes used to identify the shop`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` computes the signature strictly over `to_signable_string` and compares it to the `hmac-sha256`/`x-shopify-hmac-sha256` header: [2](#0-1) 

However, `Request#shop` (used by host apps to identify which merchant/tenant the webhook belongs to) is read straight from the `shop-domain`/`x-shopify-shop-domain` HTTP header, completely outside the signed content: [3](#0-2) 

The same is true for `topic`, `api_version`, and `webhook_id`, all pulled from unauthenticated headers: [4](#0-3) 

The equality that should hold is: `shop used to route/persist the webhook == shop authenticated by the HMAC`. Because the HMAC only covers `@raw_body`, that equality does not hold — `Request#shop` is attacker-controllable metadata riding alongside a validly-signed body.

### Impact Explanation
Any consumer of this gem that follows the documented pattern of "validate HMAC, then trust `request.shop` to identify the tenant" (the `shop` accessor exists specifically for that purpose) can be tricked into associating a genuinely-signed payload with the wrong merchant. Since a webhook body originating from Shop A is HMAC-valid for Shop A's own `client_secret`-independent check (the check only proves "these bytes weren't tampered with"), an attacker who can influence or replay delivery with a different `shop-domain` header — e.g., a malicious app-store merchant replaying their own legitimately received webhook against the app's endpoint with a forged `shop-domain` header — causes the host application to process/store the payload under a different tenant's record. This is a cross-tenant data-integrity break stemming directly from this gem's API surface (`Request#shop`), not from host misuse of an undocumented feature.

### Likelihood Explanation
Exploitation requires only the ability to send an HTTP request to the app's public webhook endpoint with attacker-chosen headers and a body/HMAC pair the attacker already legitimately possesses (e.g., from their own shop's webhook deliveries, which any merchant with the app installed can capture). No access token, `client_secret`, or privileged account is required — this is reachable by any unprivileged internet user who has installed the app on at least one shop and can replay their own captured webhook body with a modified `shop-domain` header.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, `topic`, `api_version`, `webhook_id`) in the HMAC-signed material, or otherwise cryptographically bind them to the payload before exposing `Request#shop`/`#topic` to callers. At minimum, document prominently that these accessors are unauthenticated and must not be used for tenant routing/authorization decisions without an independent verification step (e.g., cross-checking against a shop already known from OAuth for the given webhook subscription id).

### Proof of Concept
1. Merchant M installs the app; the app registers a webhook subscription and receives a webhook delivery `POST /webhooks` with:
   - `X-Shopify-Shop-Domain: shop-m.myshopify.com`
   - `X-Shopify-Hmac-Sha256: <valid hmac over raw_body>`
   - body: `raw_body`
2. Merchant M (attacker) captures this exact `raw_body` + `hmac` pair (their own legitimate webhook).
3. Attacker resends the identical `raw_body` and `hmac` to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: shop-victim.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` because it only checks `raw_body` against the HMAC — see [5](#0-4)  and [6](#0-5) .
5. `request.shop` now returns `"shop-victim.myshopify.com"`, and the app processes/stores the attacker's data under the victim's tenant record, despite the payload never having been signed on behalf of that shop.
