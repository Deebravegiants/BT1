This confirms the vulnerability. The gem's own documentation instructs developers to trust `data.shop` as the tenant identifier (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), and `ShopifyAPI::Webhooks::Registry.process` claims to "verify the request did indeed come from Shopify" as its only authentication step before invoking the handler with that `shop` value.

### Title
Cross-tenant webhook spoofing via unauthenticated `shop-domain` header not covered by HMAC - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` (and `topic`, `webhook_id`, `api_version`) from HTTP headers that are never included in the HMAC signature computation, while `ShopifyAPI::Webhooks::Registry.process` treats successful HMAC validation as proof the entire request — including the shop identity — is authentic.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`. For webhook requests, `to_signable_string` returns only the raw request body: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` values are pulled directly from HTTP headers, none of which are included in the signed content: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, then immediately trusts `request.shop` as the identity of the tenant the payload belongs to, passing it straight into `WebhookMetadata` and to the app's handler: [3](#0-2) 

Since the HMAC secret (`Context.api_secret_key`) is the app's single `client_secret`, shared across every shop that has installed the app, any recipient of a genuine webhook from *any* installed shop possesses a payload whose HMAC will validate for every other shop of the same app. The `shop-domain` header is attacker-controllable and completely unauthenticated — it is not part of the value verified by `OpenSSL.secure_compare` in `HmacValidator.validate_signature`: [4](#0-3) 

This breaks the intended identity binding: `shop header used by the handler == shop that produced the HMAC-signed body`. An attacker who controls (or has previously received) a validly-signed webhook body for their own shop can replay it to the app's public webhook endpoint while substituting the `shopify-shop-domain` / `x-shopify-shop-domain` header with a victim shop's domain. The HMAC still validates (same app secret), so `Registry.process` calls the developer's handler with `WebhookMetadata#shop` set to the victim's domain and the attacker-supplied body.

The gem's own documentation instructs developers to key their persisted/queued state off `data.shop` without saying it needs independent verification, reinforcing that this field is treated as a trusted tenant identifier by design: [5](#0-4) 

### Impact Explanation
This is a cross-tenant confusion primitive: an attacker who is a legitimate merchant/tenant of the app can cause the app to process attacker-controlled webhook data (order/customer/product payloads, GDPR-mandatory topics, etc.) as if it belonged to a victim shop. Depending on how the host app keys its downstream processing off `data.shop` (job queues, database writes, cache invalidation, per-shop feature toggles), this can lead to cross-tenant data corruption, incorrect authorization decisions, or injection of attacker data into another merchant's records — satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Requires the attacker to install the app on their own shop (or otherwise obtain one genuinely-signed webhook payload/body) and to be able to POST to the app's public webhook callback endpoint with custom headers — both of which are actions available to an ordinary unprivileged internet user/merchant. No access token, `client_secret`, or privileged account is needed since the attacker only reuses their own legitimately-received HMAC/body pair.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, and ideally `topic`/`webhook_id`) in the HMAC-signed content, or otherwise cryptographically bind them to the body before verification, so that `HmacValidator.validate` fails if any of these headers are altered relative to what Shopify actually sent. At minimum, document prominently that `data.shop` must not be trusted as authenticated tenant identity by itself.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering a legitimate webhook, e.g. `orders/create`, to the app's callback URL with body `B` and header `shopify-hmac-sha256: H` (valid HMAC of `B` under the app's shared `client_secret`).
2. Attacker replays the exact same request to the same callback endpoint, keeping body `B` and header `shopify-hmac-sha256: H` unchanged, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into a request object; `HmacValidator.validate` recomputes HMAC over `B` only, matches `H`, and returns `true` per [6](#0-5) .
4. `Registry.process` invokes the developer's handler with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: B, ...)`, causing the app to process attacker-controlled data attributed to the victim tenant.
