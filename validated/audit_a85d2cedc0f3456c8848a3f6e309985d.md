### Title
Emporium relay fee bypass: attacker-signed `signerAddress` skips the variable-rate fee - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumStack.signerAddress` is fully attacker-controlled and is only validated by a plain ECDSA signature check [1](#0-0) , exactly like the 0x delegated-stake bug where a party can construct a self-controlled entity to escape the "reduced weight" default path. Here, any caller can self-sign a message with an EOA they own and pass that EOA as `signerAddress`, which flips `payRelayFees` into the "wallet" branch that charges only the flat fee and skips the percentage-based (`variableRate`) relay fee entirely.

### Finding Description
In `payRelayFees`, the relay fee computed for each withdrawn/swapped token depends solely on whether `signerAddress == address(0)`: [2](#0-1) 
- If `signerAddress == address(0)`, the fee is `hinkalHelper.calculateRelayFee(sumAbs, flatFee, variableRate)` — flat fee **plus** a percentage of the withdrawn amount.
- If `signerAddress != address(0)`, the fee is just `flatFee` — the percentage-based component is skipped entirely.

`signerAddress` is a field the caller supplies inside `EmporiumStack`, decoded from `circomData.externalActionData.externalActionMetadata` [3](#0-2)  and validated only by `verifyWallet`, which recovers the signer of an EIP-712 message via plain `ECDSA.tryRecover` and checks it equals `stack.signerAddress` [4](#0-3) . Because this is raw ECDSA (not EIP-1271/`SignatureChecker`), `signerAddress` just needs to be an EOA the caller controls the private key for — the caller can trivially self-sign the exact `EmporiumOperation[]`/`maxFee`/`deadline` payload they intend to submit.

Crucially, whether the "stateful" wallet-invocation path (`IHinkalWallet(signerAddress).callHinkalWallet(...)`) is even used is gated per-operation by `op.invokeWallet` [5](#0-4) . A caller can set every `op.invokeWallet = false` (so all calls execute as ordinary low-level calls from Emporium itself, not routed through any wallet contract) while still supplying a non-zero, self-signed `signerAddress`. This decouples the fee-bypass condition (`signerAddress != address(0)`) from any actual use of a `HinkalWallet` contract, letting an attacker keep 100% of the value that should have gone to the relay as the variable-rate fee, while paying only the flat fee — mirroring the reported pattern of using an external/self-controlled entity to escape the intended (lower) treatment and capture a strictly better outcome than the honest default path.

### Impact Explanation
This is a direct underpayment/theft of protocol/relay fees: for every Emporium withdrawal/swap, the attacker can strip out the `variableRate` percentage fee that `HinkalHelper.calculateRelayFee` would otherwise apply [6](#0-5) , paying only the flat fee regardless of transaction size. Given the accepted severity taxonomy, this matches "High — theft or permanent freezing of protocol/relay fees."

### Likelihood Explanation
High. No privileged role, admin key, or relayer cooperation is needed — the caller only needs to sign an EIP-712 message with an EOA they control, matching the exact `EmporiumOperation[]`, `maxFee`, and `deadline` they submit. This can be done for every Emporium call.

### Proof of Concept
1. Attacker generates a fresh EOA `E` and its private key (or reuses an existing one they control).
2. Attacker builds `EmporiumStack.ops` with all `invokeWallet = false`, pointing to whatever endpoint/swap they want to perform (stateless call path) [7](#0-6) .
3. Attacker signs the EIP-712 `EmporiumSignature` hash (`emporiumMessage`, ops hash, `maxFee`, `deadline`) with `E`'s key, producing `(v, r, s)`, and sets `signerAddress = E`.
4. Attacker submits the Hinkal transaction with this `circomData`. `verifyWallet` recovers `E` from the signature and it matches `stack.signerAddress`, so validation passes [8](#0-7) .
5. `payRelayFees` sees `signerAddress != address(0)` and charges only `flatFee`, skipping the `variableRate`-based relay fee that would otherwise apply to the withdrawn amount [9](#0-8) .
6. The attacker repeats this for arbitrarily large withdrawals/swaps, always paying only the fixed flat fee instead of the intended percentage-based relay fee.

    function verifyWallet(
        EmporiumStack memory stack,
        CircomData calldata circomData
    ) internal {
        EmporiumStorageVars storage $ = _getEmporiumStorage();

        if ($.usedMessages[circomData.emporiumMessage]) {
            revert UsedMessage();
        }

        $.usedMessages[circomData.emporiumMessage] = true;

        if (stack.signerAddress == address(0)) {
            return;
        }

        bytes32 hashedMessage = _hashTypedDataV4(
            keccak256(
                abi.encode(
                    EMPORIUM_SIGNATURE_TYPEHASH,
                    circomData.emporiumMessage,
                    _hashEmporiumOps(stack.ops),
                    stack.maxFee,
                    stack.deadline
                )
            )
        );

        (address recoveredAddress, ECDSA.RecoverError err) = ECDSA.tryRecover(
            hashedMessage,
            stack.v,
            stack.r,
            stack.s
        );
        bool verified = err == ECDSA.RecoverError.NoError &&
            recoveredAddress == stack.signerAddress;
        if (!verified) {
            revert InvalidSignature();
        }

    function calculateRelayFee(
        uint256 balance,
        uint256 flatFee,
        uint256 variableRate
    ) public pure returns (uint256 relayFee) {
        require(balance >= flatFee, "Relay Fee is over withdraw amount");
        uint256 recipientAmount = ((10000 - variableRate) *
            (balance - flatFee)) / 10000;
        relayFee = balance - recipientAmount;
    }
