Confirmed root cause: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so the HMAC (computed via `HmacValidator.validate`) only authenticates the body bytes, never the `shopify-shop-domain` header [2](#0-1) . Yet `Registry.process` passes `request.shop` — read straight from that unauthenticated header — into `WebhookMetadata` as the tenant identifier delivered to the app's handler [3](#0-2) [4](#0-3) . This is exactly the documented `data.shop` field the gem tells developers to trust for tenant routing/dispatch [5](#0-4) .

Contrast this with `Auth::Oauth::AuthQuery`, where `shop` **is** included inside `to_signable_string` and thus is bound by the HMAC [6](#0-5) . The webhook path breaks the same binding that the OAuth path correctly enforces.

### Title
Webhook shop-domain identity spoofing via HMAC binding gap - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes/validates the webhook HMAC over the raw body only, never over the `shopify-shop-domain` header, yet `Registry.process` forwards that same unauthenticated header value as the trusted `shop` field of `WebhookMetadata` passed to the app's webhook handler.

### Finding Description
The identity binding that should hold is: `shop_bytes_covered_by_hmac == shop_value_delivered_to_handler`. In this gem that equality is false. `to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` signs/verifies exactly that string [7](#0-6) . Meanwhile `Request#shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic tie to the signature [4](#0-3) . `Registry.process` passes this header-derived value straight through to the handler as `shop:` [8](#0-7) .

Any tenant who can legitimately install the app on their own store can capture a genuine, validly-signed webhook (body + HMAC) addressed to their own shop, then resend that exact `(raw_body, hmac)` pair to the shared webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. `HmacValidator.validate` will still pass because it never inspects the header, and the app-side handler (following the gem's documented pattern of trusting `data.shop` for tenant dispatch, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` [9](#0-8) ) will process the attacker's body content as if it originated from the victim shop.

This is a direct analog of the ValueTokenFacet bug class: the "amount" bound by cryptographic proof (raw body/HMAC) is decoupled from the "identity" (shop) the calling code acts on, letting an attacker substitute a cheaper/attacker-controlled identity for a victim's, causing cross-tenant misattribution.

### Impact Explanation
This yields cross-tenant data confusion: an attacker-controlled webhook body (from their own shop) gets attributed to and processed against a different merchant's tenant records, since the gem provides no way for a handler to detect the mismatch — the shop value it receives is never verified. Depending on the handler logic downstream (queued jobs, order/inventory sync, GDPR/mandatory webhook handling keyed by `data.shop`), this can corrupt or leak state across tenants, satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Likelihood is meaningful: the attacker precondition is only that they operate any shop with the app installed (no leaked secrets, no TLS interception, no privileged access) — they legitimately receive real signed webhooks for their own store and can freely replay them to the shared public webhook endpoint with a modified header, since the endpoint is reachable by any internet client and the header is not authenticated in any way.

### Recommendation
Bind the shop identity to the HMAC signature (or otherwise authoritatively resolve tenant identity), analogous to how `Auth::Oauth::AuthQuery#to_signable_string` includes `shop` in the signed payload [6](#0-5) . For webhooks, since Shopify's HMAC only covers the body, the gem should document/require that `shop-domain` be cross-checked against the shop associated with the resolved webhook subscription/session rather than trusted as-is, or the gem could expose a helper that validates the header-derived shop against session storage before constructing `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and registers for a webhook topic (e.g. `orders/create`).
2. Attacker triggers the event on their own store and captures the real inbound request: raw body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC(secret, B)` — valid per `HmacValidator.validate` [2](#0-1) .
3. Attacker crafts a new POST to the app's shared webhook endpoint with the same body `B` and same `hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts it (all required headers present) [10](#0-9) ; `Registry.process` validates HMAC successfully (only body is checked) and dispatches `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)` to the app's handler [8](#0-7) .
5. The handler processes attacker-controlled body content believing it is legitimate data for `victim.myshopify.com`.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
