### Title
Webhook HMAC validation covers only the raw body, not the `shop-domain`/`topic`/`webhook-id` headers, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values that are handed to the app's webhook handler as trusted, tenant-identifying data come from unauthenticated HTTP headers that are never included in the HMAC computation. This breaks the identity binding `HMAC-authenticated data == data trusted by the handler`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are all parsed straight out of caller-supplied headers with no cryptographic protection: [2](#0-1) 

`Registry.process` validates the HMAC using the generic `HmacValidator`, which only ever verifies `verifiable_query.to_signable_string` (i.e. the body) against the secret: [3](#0-2) 

After the HMAC check passes, `Registry.process` forwards the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` verbatim into `WebhookMetadata`, which the host application's handler treats as the trusted tenant/topic identity: [4](#0-3) 

The gem's own documentation reinforces that `process` is expected to fully authenticate the request ("This will verify the request did indeed come from Shopify") and instructs handlers to treat `data.shop` as the shop domain of the webhook, so app authors reasonably rely on it for tenant scoping (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), per the documented handler example.

Because a single `api_secret_key` is shared across every shop that has installed a given app (this is a multi-tenant credential, not a per-shop secret), any shop that has installed the app can receive a legitimate webhook delivery with a body+HMAC pair valid under that shared secret. Since headers are excluded from the signed content, that captured `(raw_body, hmac)` pair remains valid regardless of which `shop-domain`/`topic`/`webhook-id` headers accompany it. A malicious merchant (an unprivileged actor relative to other tenants of the app) can therefore replay their own genuine webhook body/HMAC to the app's webhook endpoint while substituting a different shop's domain in the `shop-domain` header, causing the app to process and attribute that (possibly attacker-crafted, since the merchant controls what data triggers their own store's webhooks, e.g. order/product content) payload as belonging to the victim shop.

### Impact Explanation
This is a cross-tenant identity/data confusion: the equality the app relies on, `HMAC-authenticated request == the shop/topic asserted to the handler`, does not hold, because the shop and topic are never part of the signed content. This lets one tenant impersonate another tenant's webhook delivery, corrupting per-shop data pipelines, job queues, or state keyed by `data.shop`/`data.topic` in the host application — a cross-tenant access impact.

### Likelihood Explanation
Any app built on this gem that uses multiple shops (the standard multi-tenant SaaS model) shares one `api_secret_key` across tenants. Any merchant who installs the app automatically receives legitimate webhook deliveries (valid body+HMAC) for their own store, which is all an attacker needs; no additional credential, secret leakage, or privileged access is required beyond normal app installation. The webhook endpoint is a public HTTP route by design.

### Recommendation
Include the identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-covered content (or otherwise cryptographically bind them, e.g. via a domain-separated signable string), and reject requests where headers were altered after signing. Short term, document clearly that `process`/`HmacValidator` only authenticates the body, and instruct host applications to independently verify `data.shop` against the shop for which the webhook was registered before trusting it for tenant-scoped operations.

### Proof of Concept
1. App is installed by attacker's shop `attacker.myshopify.com` and by victim shop `victim.myshopify.com`, both using the same app (`api_secret_key`).
2. Shopify sends a legitimate webhook to the app for `attacker.myshopify.com` with body `B` and header `x-shopify-hmac-sha256: HMAC(B, secret)`.
3. Attacker captures `(B, HMAC(B, secret))` from their own webhook delivery.
4. Attacker POSTs to the app's webhook endpoint with the same body `B` and same HMAC header, but sets `x-shopify-shop-domain: victim.myshopify.com` (and optionally a different `topic`/`webhook-id`).
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC only over `B` and succeeds, since headers are irrelevant to `to_signable_string`.
6. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: <attacker-chosen>, body: <attacker-controlled body content>, ...)`, and the host app processes it as authentic data for the victim shop.
