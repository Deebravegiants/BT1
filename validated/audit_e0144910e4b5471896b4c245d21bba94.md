### Title
Attacker-chosen `req.ID` collision in Vault gateway handler enables DoS on a victim's request before authorization runs - ([File: core/services/gateway/handlers/vault/handler.go])

### Summary
The Sherlock report describes a DoS where an attacker front-runs a state-changing admin call (`LibTWAPOracle::setPool`) by manipulating shared state (pool balances) that the call strictly compares for equality, causing the legitimate call to revert. The analogous bug class here is a strict "already exists" keying check on attacker-influenced, globally-shared state — the `activeRequests` map in the Vault gateway handler, keyed purely by the client-supplied `req.ID` — which is checked before authorization/ownership is verified.

### Finding Description
`HandleJSONRPCUserMessage` accepts a JSON-RPC request with a client-supplied `req.ID` (only length-bounded, 1–200 chars, no other constraint) [1](#0-0) . Before ownership/authorization is even resolved (for `MethodPublicKeyGet` this branch happens immediately; for other methods it happens right after `ProcessRequest` succeeds), the handler calls `newActiveRequest`, which stores the pending request keyed only by `req.ID` in a single shared map `h.activeRequests`, with no per-sender or per-owner namespacing: [2](#0-1) 

If an entry with the same `req.ID` already exists, the call fails outright with `"request ID already exists: " + req.ID"` rather than treating it as a new, independent request: [3](#0-2) 

Because `req.ID` is fully attacker-controlled and the map is process-wide (not partitioned by sender, workflow owner, or DON), any unprivileged client that can reach this JSON-RPC gateway endpoint can pre-register an `activeRequest` under a specific ID and hold the entry alive for the duration of `requestTimeout` (or until a node fully responds and the aggregator completes/cancels it), preventing any other legitimate caller from using that same `req.ID` until the entry is cleaned up. This mirrors the reported bug class: a state check with strict equality/exclusivity, keyed on a value the admin/legit caller does not fully control, that an unprivileged attacker can pre-empt to cause the victim's otherwise-valid call to fail.

The likelihood of a real, cross-user collision depends on how request IDs are chosen by legitimate node/workflow callers (e.g., if they are deterministic per workflow/execution rather than fully random UUIDs, an attacker could predict and squat on them). I could not fully verify from the available index whether workflow-side callers use unpredictable random IDs (e.g., UUIDv4) for every request or something derivable/predictable by third parties; this would need to be confirmed by inspecting the caller side (e.g., `core/services/workflows` vault client code) to assess exploitability precisely.

### Impact Explanation
If an attacker can predict or brute-force a victim's `req.ID` (or if IDs are otherwise not namespaced per caller), the attacker can occupy that ID first, causing the victim's legitimate `SecretsCreate`/`SecretsUpdate`/`SecretsDelete`/`SecretsList`/`PublicKeyGet` request to be rejected with an "already exists" error — a denial-of-service on Vault secret operations for the affected caller until the entry times out. This does not directly leak secrets or bypass authorization, but it can disrupt availability of a security-sensitive capability (vault operations) for targeted users/workflows.

### Likelihood Explanation
Likelihood depends on: (1) whether `req.ID` values used by legitimate callers are unpredictable/random enough to prevent guessing, and (2) whether the gateway is reachable by unprivileged/untrusted parties before per-request authorization gates it (as is the case for `MethodPublicKeyGet`, and for other methods the ID slot is claimed right after authorization succeeds but keyed globally regardless of owner). Since the map has no per-owner segregation and the check happens on a purely attacker-suppliable string, exploitability is plausible but bounded by ID predictability, which I was unable to fully confirm from available context.

### Recommendation
- Namespace `activeRequests` by a caller identity in addition to `req.ID` (e.g., key on `(authorizedOwner, req.ID)` or `(senderAddress, req.ID)`), so the exclusivity check cannot be triggered by unrelated third parties.
- Move the ID-uniqueness/state registration to occur only after authorization succeeds and is bound to the resolved owner, not before.
- Consider generating/validating `req.ID` server-side (or requiring a signed nonce tied to the authorized owner) rather than trusting an arbitrary client-chosen string for a shared map key.

### Proof of Concept
Conceptual PoC (exploitability contingent on real caller IDs being predictable, which needs separate confirmation):
1. Attacker (or any client permitted to submit `MethodPublicKeyGet`, which requires no authorization) sends a JSON-RPC request to the Vault gateway handler with `req.ID = "victim-known-id"`.
2. This claims the slot in `h.activeRequests["victim-known-id"]` via `newActiveRequest` [4](#0-3) .
3. Victim's legitimate call using the same `req.ID` (e.g., a deterministic ID for a given workflow execution) then hits `newActiveRequest` and receives `"request ID already exists: victim-known-id"` [5](#0-4) , denying the victim's Vault operation until the attacker's entry expires/times out.

func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	ar := &activeRequest{
		Callback:  callback,
		req:       req,
		createdAt: h.clock.Now(),
		responses: map[string]*jsonrpc.Response[json.RawMessage]{},
	}
	h.activeRequests[req.ID] = ar
	return ar, nil
}
