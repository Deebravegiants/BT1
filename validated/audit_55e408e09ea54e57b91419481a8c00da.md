### Title
POA Bridge withdrawal status/hash misattribution in batch withdrawals of the same asset - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal()` matches an on-chain withdrawal to a `WithdrawalIdentifier` using only `assetId`, ignoring the `index` field that is supposed to disambiguate multiple withdrawals of the same token created in the same NEAR transaction (a feature explicitly supported by the SDK — see "Batch Withdrawals" in `packages/intents-sdk/README.md`).

### Finding Description
`findMatchingWithdrawal()` returns the *first* withdrawal in the POA API response whose `near_token_id` matches the requested `assetId`: [1](#0-0) 

`describeWithdrawal()` calls this matcher without ever consulting `args.index` (the value produced by `createWithdrawalIdentifier` to distinguish multiple withdrawals of the same asset in one transaction): [2](#0-1) 

If a single NEAR transaction contains two or more POA-bridge withdrawal intents for the same `assetId` (e.g., withdraw 100 USDT to address A and 500 USDT to address B in one batch, a use case the SDK explicitly advertises as "Batch Processing"), then `watchWithdrawal()`/`describeWithdrawal()` for **both** `WithdrawalIdentifier`s (index 0 and index 1) will resolve to the **same** matched withdrawal record — whichever the POA API happens to return first. This breaks the equality "status/txHash reported == actual on-chain outcome for *this* withdrawal": one withdrawal's real completion (with its real `transfer_tx_hash` and real destination) gets reported as the completion of a *different* withdrawal identifier that has a different destination address and amount, while the true status of the second withdrawal is not tracked at all.

This is not a trust-in-external-API issue in the sense excluded by scope — the API is behaving correctly (it doesn't guarantee ordering and only exposes `near_token_id`), but the SDK's own matching logic silently drops the disambiguating `index` it created for exactly this purpose, causing itself to attribute a completed transfer to the wrong withdrawal identifier.

### Impact Explanation
This is a status/hash misreport: an integrator calling `sdk.processWithdrawal`/`watchWithdrawal` for a batch containing two same-asset POA withdrawals can be told "withdrawal B completed with txHash X" where X actually corresponds to withdrawal A's transfer to a *different* destination address and amount. An integrator relying on this to credit/release funds, mark an order as fulfilled, or refund a user could act on the wrong transfer, effectively causing a double-credit or a credit against the wrong destination/amount. This matches the "status or hash misreport making an integrator credit or refund twice" High-impact category.

### Likelihood Explanation
This is reachable through completely normal, unprivileged SDK usage: any integrator or user who batches multiple withdrawals of the same token to different destinations within a single NEAR transaction (a documented, supported feature) will trigger this ambiguous matching. No malicious behavior from the relayer, bridge, or a third party is required — the bug is self-triggered by the SDK's own logic even under benign batch usage. The code comment in `findMatchingWithdrawal` confirms this was a known, accepted limitation ("multiple withdrawals of the same token in a single transaction are not supported"), but that limitation is not surfaced to the caller (no rejection/guard), so `processWithdrawal`/`createWithdrawalIntents` silently allow the unsafe batch and then misreport status.

### Recommendation
- In `createWithdrawalIntents` / the batch withdrawal path, detect when a single NEAR transaction would contain multiple POA-bridge withdrawal intents for the same `assetId` and either reject it explicitly (throw a clear error) or ensure `describeWithdrawal` can disambiguate.
- If POA API ordering is stable relative to intent submission order, extend `findMatchingWithdrawal` to also correlate by `amount`/`destinationAddress` (sorted comparison, as suggested in the existing code comment) instead of `assetId` alone, and only fall back to first-match when no other same-asset withdrawal is pending.
- At minimum, throw immediately from `PoaBridge.supports`/`validateWithdrawal`/`createWithdrawalIdentifier` when it can detect duplicate assetIds within the same batch, so silent misattribution cannot occur.

### Proof of Concept
1. Call `sdk.createWithdrawalIntents` (or the batch-withdrawal API) with two withdrawal params using the same `assetId` (e.g., `nep141:usdt.tether-token.near`), one with `destinationAddress: A, amount: 100`, another with `destinationAddress: B, amount: 500`, in the same NEAR transaction/intent.
2. Call `bridge.createWithdrawalIdentifier` for `index: 0` and `index: 1` respectively, then `describeWithdrawal` for both.
3. Mock/observe the POA bridge withdrawal-status API to return withdrawal records for the two transfers in any order (the API does not guarantee submission order per `findMatchingWithdrawal`'s own comment).
4. Observe that both `describeWithdrawal` calls resolve using `findMatchingWithdrawal`, which returns the same first `nep141:usdt.tether-token.near` record for both `index: 0` and `index: 1` — i.e., the withdrawal to `A` may be reported as completed for the identifier associated with `B` (and vice versa), confirmed at: [3](#0-2)

	createWithdrawalIdentifier(args: {
		withdrawalParams: WithdrawalParams;
		index: number;
		tx: NearTxInfo;
	}): WithdrawalIdentifier {
		const assetInfo = this.parseAssetId(args.withdrawalParams.assetId);
		assert(assetInfo != null, "Asset is not supported");

		const landingChain = assetInfo.blockchain;

		return {
			landingChain,
			index: args.index,
			withdrawalParams: args.withdrawalParams,
			tx: args.tx,
		};
	}

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
