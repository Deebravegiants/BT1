### Title
Unprivileged borrow positions can permanently freeze a pool market via i128 overflow during interest accrual - (File: common/src/rates/scaling.rs)

### Summary
Analogous to CVE-2020-14150 (input-driven crash/DoS), the pool's interest accrual performs an unchecked-guard `i128` multiply (`scaled × borrow_index`) inside `scaled_to_original`, which panics with `MathOverflow` once the debt value exceeds the `i128` domain. Because every market-mutating entrypoint runs `interest::global_sync` before doing anything else, once accrual overflows the panic is permanent: no repay, withdraw, borrow, liquidation settlement, flash loan, or `update_indexes` on that market can ever succeed again. The `MAX_BORROW_INDEX_RAY` cap is applied to the *index* only, so it cannot prevent the *value* product `borrowed × index` from overflowing first.

### Finding Description
`accrue_step` computes utilization by unscaling totals before anything else: [1](#0-0) 

`scaled_to_original` is a plain `mul` on `Ray`, which panics with `GenericError::MathOverflow` on `i128` overflow: [2](#0-1) 

The pool calls this unconditionally on every mutation via `global_sync`, which loops over chunked windows and calls `accrue_chunk` → `accrue_step` before the operation's own logic: [3](#0-2) 

The documented flow confirms accrual precedes every guard and mutation: [4](#0-3) 

The index ceiling does not help: `update_borrow_index` clamps `borrow_index` at `10^36`, but the panic happens in `borrowed × borrow_index / RAY` while the index is still well below the cap, because `borrowed` in RAY terms can approach `i128::MAX / 10^(27-d)` per the admitted cap bound. `docs/reference/formulas.md` acknowledges the cliff: "Value overflow can occur before the index ceiling and block repayment/withdrawal because those operations accrue first" — but acknowledgment does not neutralize the freeze. [5](#0-4) 

The end-to-end harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` demonstrates the exact scenario on the shipped XLM curve: after enough elapsed time at ~98% utilization, `update_indexes`, `withdraw`, and `repay` all revert with `MATH_OVERFLOW`, and `borrow_index < MAX_BORROW_INDEX_RAY` at the freeze point. [6](#0-5) 

### Impact Explanation
Permanent freezing of funds and permanent protocol incapacitation for the affected `(hub, token)` book. Once `borrowed_scaled × borrow_index` exceeds `i128::MAX`:
- Suppliers cannot `withdraw` a single unit — `withdraw` accrues first and panics.
- Borrowers cannot `repay` — `repay` accrues first and panics.
- Liquidators cannot settle bad positions touching this market — any `seize_positions`/repay leg on it panics, so liquidation plans involving the asset revert.
- `update_indexes` itself panics, so `last_timestamp` never advances; there is no recovery path that skips accrual. `recapitalize` also accrues first.
- The market is bricked forever with all deposited cash, debt accounting, and revenue shares locked.

This is not a fail-closed price outage or a flag policy — it is a latent arithmetic trap reachable entirely through normal user operations.

### Likelihood Explanation
Reachable by unprivileged addresses through `supply` and `borrow` only:
1. In a high-cap market (caps admit up to ~170B whole tokens of `i128::MAX / 10^(27-d)`), supply a large amount of the asset.
2. Supply collateral in another market and `borrow` the target market to high utilization (near `max_utilization`, or unbounded when `max_utilization >= RAY`).
3. Wait: at sustained high utilization the borrow index grows multiplicatively; the harness test shows the cliff occurs within tens of years on the shipped XLM curve, earlier for larger books and steeper curve segments.

No privileged action, oracle manipulation, or special input is needed — only a large position and elapsed time. Any large organic market drifts toward the same cliff even without an attacker, and an attacker holding a large borrow can accelerate it deliberately. Severity is bounded by the capital required, matching the report's Medium class.

### Recommendation
Bound the accrual-domain product rather than only the index:
- In `accrue_step`, compute `borrowed_original`/`supplied_original` through a saturating or `I256`-widened path (the `fp_core` helpers already widen to `I256` for `mul_div`), and cap `new_borrow_index` at the largest index for which `borrowed × index` stays in domain, so accrual saturates instead of panicking — mirroring the existing `calculate_scaled_cap` saturation approach.
- Alternatively, enforce at `borrow`/`mint_debt` time a `max_borrowed` such that `borrowed × MAX_BORROW_INDEX_RAY` cannot overflow, making the freeze state unreachable.
- Add a regression test asserting `withdraw`/`repay` still succeed when the index cap has engaged at maximum utilization.

### Proof of Concept
The repository's own harness test demonstrates the freeze; reduced to controller calls:

1. `supply(BOB, BIG18_market, 1_000_000_000 * 10^18)` — whale liquidity.
2. `supply(ALICE, COL_market, collateral)` + `borrow(ALICE, BIG18, 0.98 * supplied)` — unprivileged borrow at 98% utilization on the XLM rate curve.
3. Advance ledger time; call `update_indexes` each year. After the debt value crosses `i128::MAX`, `update_indexes` reverts with `MathOverflow` (33) inside `scaled_to_original` while `borrow_index < 10^36`.
4. Subsequently `withdraw(BOB, BIG18, 1)` and `repay(ALICE, BIG18, any)` both revert with `MathOverflow`, permanently — confirmed by `assert_contract_error(t.try_withdraw_raw(...), errors::MATH_OVERFLOW)` and the matching repay assertion in `large_positions_and_long_horizons.rs`.

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}
```

```rust
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
    std::println!(
        "ray-value cliff reached after {years} years at 98 percent utilization on the XLM curve; last index x{:.1}",
        last.borrow_index as f64 / RAY as f64
    );
```
