### Title
Webhook shop-domain header is not covered by HMAC, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies webhook authenticity using `Utils::HmacValidator.validate(request)`, which signs and checks only the raw request body via `Request#to_signable_string`. The `shop` (tenant identity) is read from the `x-shopify-shop-domain` HTTP header, which is never included in the signed content, so the HMAC does not bind the shop identity to the payload it authenticates.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` attribute used for tenant attribution is pulled from a header, entirely outside the signed material: [2](#0-1) 

`Registry.process` validates the HMAC (over the body only) and then dispatches to the app's handler using `request.shop` as the tenant key, with no additional cross-check that the header matches the shop the body actually belongs to: [3](#0-2) 

The identity binding that should hold is: `HMAC-verified content == content used to attribute the event to a shop`. Here that equality fails — `hmac` covers `raw_body` only, while `shop` (the value consumed by `WebhookMetadata` and forwarded to the app's handler) is sourced from an unauthenticated header: [4](#0-3) 

Because Shopify signs all webhooks for a given app with the same `client_secret` regardless of which merchant/shop triggered the event, any party that can obtain one validly-signed webhook body for their own shop (e.g., by installing the app on their own store — an "unprivileged" action requiring no app secret) can replay that exact body to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header value for a victim shop's domain. `HmacValidator.validate` will still pass, because it only checks the (unchanged) body against the (unchanged, correctly-computed) signature — it never inspects the header. The app's handler then receives `WebhookMetadata` attributing forged/attacker-controlled event data to the victim shop, corrupting per-tenant data or triggering shop-scoped side effects (e.g., `shop/redact`, `customers/data_request`, inventory or order updates) under the wrong tenant.

### Impact Explanation
This breaks a tenant boundary: an attacker who legitimately holds valid webhook material for their own installation can inject data attributed to a different merchant's `shop` value into the host application, without ever needing the app's `client_secret`, an access token, or any privileged credential. This is a cross-tenant data-confusion/spoofing vector consistent with the "cross-tenant access" High/Critical impact category, since the shop identity — the primary tenant key most Shopify apps use to route/store webhook data — is fully attacker-controllable independent of the cryptographically verified payload.

### Likelihood Explanation
Exploitation only requires: (1) the attacker's own shop has the target app installed (any merchant can install a public app), (2) the attacker captures one webhook delivery for their shop (trivial, they control the receiving endpoint or can proxy it), and (3) the attacker resends that exact body to the app's public webhook endpoint with a modified `x-shopify-shop-domain` header. No secrets, tokens, or privileged access are needed — this is squarely within the "unprivileged internet user" threat model, though it does require the app to expose its webhook endpoint publicly (true by design) and depends on the host app trusting `WebhookMetadata#shop` for tenant routing, which is the gem's documented usage pattern.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-signable content, or otherwise cryptographically bind the `shop` value to the verified payload before exposing it via `WebhookMetadata`. At minimum, document that host applications must independently validate `request.shop` against their own shop/token registry (e.g., confirm they hold an active session for that shop) before trusting the value, since the gem itself does not perform that binding.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, receiving a legitimately-signed webhook for topic `orders/create` with a raw body `B` and a valid `hmac` computed over `B` using the app's shared `client_secret`.
2. Attacker resends the identical raw body `B` and identical `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "shopify-shop-domain" => "victim.myshopify.com", "shopify-hmac-sha256" => hmac})` is constructed.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (== `B`) and compares to the received `hmac` — this passes because the body and signature are untouched.
5. `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: JSON.parse(B), ...))` is invoked, causing the host app to process attacker-controlled order/data content as if it belonged to `victim.myshopify.com`.
