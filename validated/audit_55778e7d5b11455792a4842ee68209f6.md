Audit Report

## Title
Bridge `outgoingToken` is returned unmasked in read-only API/GraphQL responses to any authenticated user with the lowest "view" role - (File: core/web/presenters/bridges.go, core/web/resolver/bridge.go)

## Summary
`BridgeType.OutgoingToken` is stored as plaintext and is returned in full on every `Show`/`Index` REST call and every `bridge`/`bridges` GraphQL query, unlike `IncomingToken`, which is hashed at rest and only surfaced once at creation via `omitempty`. Critically, `GET /v2/bridge_types` and `GET /v2/bridge_types/:BridgeName` require no elevated role beyond authentication — the router wires them without any `auth.RequiresEditRole`/`auth.RequiresAdminRole` wrapper, and this is intentionally documented in the RBAC test matrix as `viewOnlyAllowed: true`.

However, I was unable to confirm within the available index that `OutgoingToken` is actually still wired into the outbound HTTP request to the external adapter. A search of `core/services/pipeline/task.bridge.go` (the code that builds and sends bridge requests, including header construction via `reqHeaders`/`makeHTTPRequest`) shows no reference to `OutgoingToken` at all, and a repo-wide search for `OutgoingToken` usage outside of presenters/resolvers/CLI/tests/generated SDK code turned up nothing in `core/services/**`. This means the field may be a legacy/vestigial column that is no longer used to authenticate outbound bridge calls, which would significantly undercut the claimed impact ("replay or forge requests that the adapter will treat as legitimate"). I could not fully verify this within the available tool budget, and the index does not show the field being consumed anywhere in the live request path.

## Impact Explanation
Assuming `OutgoingToken` is still functionally used to authenticate the node's outbound calls to an external adapter (unconfirmed in this codebase), disclosure to any "view"-role user would allow that user to potentially replay/forge requests trusted by the adapter — a legitimate secret-exfiltration concern. However:
- This requires an authenticated node account (at minimum "view" role), which is provisioned by a node admin — it is not exploitable by a fully anonymous/unauthenticated actor.
- The behavior (view-role access to `GET /v2/bridge_types*`) is explicitly codified as intended in the RBAC test suite, suggesting this is a known, accepted design point rather than an overlooked authorization gap — the routes are not merely "unprotected by accident," they are deliberately open to all authenticated roles including view.
- I could not confirm the token is still live/functional in the outbound request path, which is central to the claimed impact of "credential misuse against the external adapter."

## Likelihood Explanation
Exploitability requires a legitimate, admin-provisioned account with at least the "view" role — the lowest tier of authenticated access, but still a credentialed, admin-granted role, not a fully unprivileged/anonymous actor. Within that constraint, exploitation is trivial and repeatable (one GET request). The severity of impact is contingent on the unconfirmed question of whether `OutgoingToken` is still functionally consumed by the bridge task execution path.

## Recommendation
- Confirm whether `BridgeType.OutgoingToken` is still consumed anywhere in the live bridge-execution/HTTP-request path (`core/services/pipeline/task.bridge.go` and related bridge connection manager code). If it is dead/legacy, this finding has no meaningful security impact and should be closed as informational (remove the unused field instead).
- If it is still live, mask/redact `OutgoingToken` on `Show`/`Index` REST responses and `bridge`/`bridges` GraphQL queries, exposing it only at creation/rotation time, and consider gating any full-value exposure behind a stricter role than plain "view".

## Proof of Concept
1. Provision a node account with `UserRoleView` (the lowest authenticated role).
2. `GET /v2/bridge_types/<bridge-name>` — response includes `"outgoingToken": "<value>"` per `core/web/presenters/bridges_test.go` and `TestRBAC_Routemap_ViewOnly` in `core/web/auth/auth_test.go`.
3. To fully substantiate the security impact, an additional step is needed beyond what was verified here: trace `core/services/pipeline/task.bridge.go`'s outbound HTTP request construction (`makeHTTPRequest`, `reqHeaders`) to confirm whether `bridge.OutgoingToken` is actually attached to requests sent to the external adapter today. This could not be confirmed in this investigation and materially affects whether disclosure has any exploitable downstream consequence.
