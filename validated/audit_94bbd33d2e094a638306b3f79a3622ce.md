I found a clear identity-binding gap: the webhook `shop` field is delivered to the app's handler but is never covered by the HMAC signature, which is computed over the raw body alone.### Title
Webhook `shop` domain is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` computes the signature input from `@raw_body` alone, while `Request#shop` (parsed from the `x-shopify-shop-domain`/`shopify-shop-domain` header) is never part of that signed material. `Registry.process` still forwards this unauthenticated `shop` value straight into the app's handler as an identity field.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` verifies a request by recomputing the HMAC over `verifiable_query.to_signable_string` and comparing it to `verifiable_query.hmac`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw body: [2](#0-1) 

Meanwhile `shop` is read from a separate, unsigned header: [3](#0-2) 

After `Registry.process` validates the HMAC, it passes `request.shop` unchanged into `WebhookMetadata`, which the host app's handler uses to identify which tenant the event belongs to: [4](#0-3) [5](#0-4) 

The identity binding that should hold is:
`HMAC(api_secret_key, signed_bytes) == received_hmac` **and** `shop ∈ signed_bytes`.

In this implementation, `signed_bytes == raw_body` only, so `shop` is entirely outside the authenticated envelope. Because the app-level `api_secret_key` is shared across every shop that installs the same app (it is not per-shop), any actor able to obtain one validly-signed webhook body+HMAC pair (e.g., by installing the app on their own store and capturing an inbound webhook) can replay that exact `raw_body`/`hmac` pair while substituting the `x-shopify-shop-domain` header for a different, victim shop's domain. `HmacValidator.validate` will still succeed because it only checks the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload originated from the victim shop.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce for webhook consumers: an unprivileged installer of the app can inject data or trigger side effects (e.g., `orders/create`, `app/uninstalled` handling) that the host application will attribute to a shop they do not control, since `data.shop` is trusted without being covered by the signature. This is a cross-tenant identity confusion enabled directly by this gem's `Request`/`Registry` implementation, matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Exploitation requires only: (1) the attacker being an installed user/merchant of the target app (to obtain one legitimately signed body+HMAC pair from their own webhook feed), and (2) sending a forged HTTP request to the app's public webhook endpoint with the captured body/HMAC and a victim shop domain header. No access token, `client_secret`, or privileged access is needed — this is reachable by any internet user who can install the app on a store they control.

### Recommendation
Include the shop domain (and topic/webhook id) in the signable material for webhook requests, or otherwise cryptographically bind `shop` to the verified payload before it is handed to `WebhookHandler#handle`. At minimum, `Registry.process` should cross-check that the shop asserted in the header corresponds to a shop that actually has this specific `webhook_id`/subscription registered, rather than trusting the header value outright.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and registers for `orders/create`.
2. Shopify sends a legitimate webhook: `raw_body = B`, header `x-shopify-hmac-sha256 = HMAC(secret, B)`, header `x-shopify-shop-domain = attacker.myshopify.com`.
3. Attacker resends the identical `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which only checks `HMAC(secret, raw_body)` — this still matches, so validation passes.
5. The app's handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: B, ...)` and processes attacker-controlled data as if it came from the victim tenant.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
