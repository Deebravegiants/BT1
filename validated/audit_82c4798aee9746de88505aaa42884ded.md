### Title
`IntentExecuter.signAndSendIntent` lets caller-supplied `verifying_contract` in `intentParams` silently override the SDK's env-derived contract id - (File: packages/intents-sdk/src/intents/intent-executer-impl/intent-executer.ts)

### Summary
`signAndSendIntent` builds the intent payload with `{ verifying_contract: verifyingContract, ...intentParams }`, but because `intentParams` is spread after the explicit key, any `verifying_contract` field present in the caller-supplied `intentParams` object silently overwrites the SDK's own `envConfig.contractID`. This value flows unvalidated through `defaultIntentPayloadFactory` straight into the signed `IntentPayload`/`MultiPayload`.

### Finding Description
The broken equality: `signedPayload.verifying_contract === this.envConfig.contractID` is expected to always hold for intents signed by this SDK, since `verifying_contract` identifies the contract the signature authorizes to move the user's funds.

In `signAndSendIntent`: [1](#0-0) 
`verifyingContract` is computed correctly from `this.envConfig.contractID`, but the object literal passed to `defaultIntentPayloadFactory` spreads `...intentParams` *after* the `verifying_contract: verifyingContract` key. JavaScript object literal semantics mean the later key wins, so if `intentParams` (which is `Partial<Parameters<IntentPayloadFactory>[0]>`, i.e. any field of the intent payload including `verifying_contract`) contains its own `verifying_contract`, it silently replaces the SDK-computed one.

`defaultIntentPayloadFactory` performs no validation of `verifying_contract` — it destructures it and passes it straight into the returned payload: [2](#0-1) 

That payload is then signed as-is by `this.intentSigner.signIntent(intentPayload)`: [3](#0-2) 

No code path validates or asserts that the final `intentPayload.verifying_contract` equals `this.envConfig.contractID` before signing. There is no `assert`, no whitelist check, no re-derivation after the merge. `mergeIntentPayloads` (used only when a custom `intentPayloadFactory` is configured) does not restore or protect `verifying_contract` either — it merges `customPayload` over `basePayload`, so a compromised custom factory or the same spread pattern could reintroduce the issue, but the core flaw is already present without any custom factory, purely via the type-permitted `intentParams` spread.

Since `Partial<Parameters<IntentPayloadFactory>[0]>` includes `verifying_contract` in its type, any caller of `IntentExecuter.signAndSendIntent` (and, transitively, any integrator code in `sdk.ts` that forwards a user/route-editable object into this call) can override it with an arbitrary string like `"attacker-contract.near"`.

### Impact Explanation
This is exactly the scenario described: an intent gets **signed** and bound to a `verifying_contract` value that is not `envConfig.contractID`. Once signed and published, the resulting `MultiPayload` authorizes execution against a different (potentially attacker-controlled or non-existent) contract id, which is either rejected downstream (best case — DoS on that specific call, not in scope) or, if a valid alternate contract accepts the payload/nonce format, could allow funds/authorization to be bound to a contract the integrator did not intend — matching "a signature bound to the wrong contract" (High) up to "funds moved the user did not authorise" (Critical) depending on what that contract does with a validly-signed NEP-413-style payload. This is repeatable on every call where `intentParams.verifying_contract` is attacker/caller supplied.

### Likelihood Explanation
Preconditions: the caller (or an integrator's naive pass-through code) must include a `verifying_contract` key in the object passed to `signAndSendIntent`. Since the public method's type signature (`Partial<Parameters<IntentPayloadFactory>[0]>`) explicitly permits this field, there is no special access required — it's a directly reachable, type-legal call. No RPC/relayer/contract-side vulnerability is required to trigger the override; the divergence exists purely in this SDK function before anything is sent over the wire.

### Recommendation
Do not allow `verifying_contract` to be overridden by caller-supplied `intentParams`. Destructure and discard `verifying_contract` from `intentParams` before spreading, e.g.:
```ts
const { verifying_contract: _ignored, ...safeIntentParams } = intentParams;
let intentPayload = defaultIntentPayloadFactory(salt, {
  ...safeIntentParams,
  verifying_contract: verifyingContract,
});
```
placing the trusted value last so it cannot be shadowed, and/or add an explicit assertion right before signing: `assert(intentPayload.verifying_contract === this.envConfig.contractID)`.

```ts
import { describe, it, expect, vi } from "vitest";
import { IntentExecuter } from "./intent-executer";

describe("verifying_contract override", () => {
  it("intentParams.verifying_contract should NOT override envConfig.contractID", async () => {
    const signIntent = vi.fn().mockResolvedValue({ standard: "nep413", payload: {}, signature: "", public_key: "" });
    const publishIntent = vi.fn().mockResolvedValue("ticket-1");

    const exec = new IntentExecuter({
      envConfig: { contractID: "intents.near" } as any,
      intentRelayer: { publishIntent, publishIntents: vi.fn(), waitForSettlement: vi.fn() } as any,
      intentSigner: { signIntent } as any,
    });

    await exec.signAndSendIntent({
      intents: [],
      salt: /* valid Salt */ ({} as any),
      verifying_contract: "attacker-contract.near", // attacker/integrator-forwarded field
    } as any);

    const signedPayload = signIntent.mock.calls[0][0];
    // Broken equality demonstrated:
    expect(signedPayload.verifying_contract).not.toBe("intents.near"); // actual (vulnerable) behavior
    // Expected/secure behavior (currently fails):
    // expect(signedPayload.verifying_contract).toBe("intents.near");
  });
});
```

```typescript
export function defaultIntentPayloadFactory(
	salt: Salt,
	{
		intents,
		verifying_contract,
		...params
	}: Partial<IntentPayload> & Pick<IntentPayload, "verifying_contract">,
): IntentPayload {
	// remove `undefined` properties
	params = Object.fromEntries(
		Object.entries(params).filter(([, value]) => value !== undefined),
	);

	const deadline =
		params.deadline != null
			? new Date(params.deadline)
			: new Date(Date.now() + DEFAULT_DEADLINE_MS);
	const nonceDeadline = new Date(
		deadline.getTime() + DEFAULT_NONCE_DEADLINE_OFFSET_MS,
	);

	return {
		verifying_contract,
		deadline: deadline.toISOString(),
		nonce: VersionedNonceBuilder.encodeNonce(salt, nonceDeadline),
		intents: intents == null ? [] : intents,
		signer_id: undefined, // or you can specify intent user id
		...params,
	};
```
