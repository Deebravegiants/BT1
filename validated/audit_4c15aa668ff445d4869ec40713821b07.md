Audit Report

## Title
View-role authenticated users can read all External Initiators' `AccessKey`/`OutgoingToken` request-impersonation credentials via `GET /v2/external_initiators` - (File: core/web/external_initiators_controller.go)

## Summary
`GET /v2/external_initiators` is registered on the authenticated `/v2` route group with no role restriction, unlike its sibling `Create`/`Destroy` handlers on the same resource which require `auth.RequiresEditRole`. The `Index` handler returns every External Initiator record in the node's database, and the list presenter serializes each initiator's `AccessKey` and `OutgoingToken` in cleartext, exposing secret material to any authenticated user regardless of role, including the lowest-privilege `view` role.

## Finding Description
The router wires `eia.Index` directly behind `paginatedRequest` with no `auth.RequiresEditRole`/`auth.RequiresAdminRole` wrapper, while `Create` and `Destroy` on the same `ExternalInitiatorsController` are explicitly wrapped with `auth.RequiresEditRole`. This asymmetry means any user who can authenticate at all — including `UserRoleView` — passes the `auth.Authenticate` middleware and reaches `Index` unimpeded.

Inside `Index`, the handler calls `eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)`, which returns all initiators in the node (paginated, but not filtered by ownership or role), and maps each one through `presenters.NewExternalInitiatorResource`. That presenter's `ExternalInitiatorResource` struct includes `AccessKey` and `OutgoingToken` as plain, non-`omitempty` JSON fields, so they are always serialized in the response.

This is a real inconsistency compared to the deliberate design elsewhere in the same file: the `Create` handler's one-time response (`ExternalInitiatorAuthentication`) uses `omitempty` for secret fields and is only returned once at creation, and `Secret`/`OutgoingSecret` are never persisted/exposed again. The list endpoint bypasses that intended one-time-disclosure model by re-exposing `AccessKey` and `OutgoingToken` (though not `Secret`) on every subsequent `GET`, to any authenticated caller.

`AccessKey` is one of two credentials (`AccessKey` + `Secret`) checked by `AuthenticateExternalInitiator` to authenticate inbound requests that trigger job runs under the elevated `UserRoleRun` role. `OutgoingToken` is the secret the node itself uses when calling out to the initiator's webhook. Disclosing these to a `view`-role user breaks the intended boundary that only initiator owners/admins should see this material, and it is one half of what's needed to impersonate an External Initiator's inbound request (the `Secret` itself is not stored in plaintext/returned, only its salted hash, so full impersonation additionally requires learning/brute-forcing `Secret`).

The project's own RBAC test suite (`auth_test.go`) explicitly marks this route `viewOnlyAllowed: true` and asserts `view` role gets non-403/401 responses, and the controller test directly asserts that `AccessKey` and `OutgoingToken` come back in the list response — confirming the described behavior is real and not a hypothetical misreading of the code.

## Impact Explanation
This is a credential/secret disclosure that violates the intended per-initiator confidentiality boundary and node RBAC model: a `view`-role user (the lowest privilege API role, intended to be read-only/non-sensitive) can enumerate `AccessKey` and `OutgoingToken` for every External Initiator on the node, not just ones relevant to them. `OutgoingToken` disclosure alone is a direct secret leak (it's the credential the node presents to the initiator's webhook). `AccessKey` disclosure is a partial step toward inbound request impersonation (still requires the `Secret`). This maps to the "key/secret exfiltration" and "node API authentication/role bypass" in-scope impact categories, since the `Index` route effectively lacks the role gate its sibling routes enforce.

## Likelihood Explanation
Exploitation requires only an authenticated API user with any role (including `view`) — no privilege escalation, no host/DB access, no admin cooperation beyond the initial provisioning of that low-privilege account (which is a normal, expected operational scenario, not a misconfiguration). Once such a session/API token exists, a single unauthenticated-role-gated `GET` request discloses the data deterministically and repeatably; this matches a low-complexity, low-privilege-required exploit profile.

## Recommendation
Wrap `authv2.GET("/external_initiators", ...)` with `auth.RequiresEditRole` (or `auth.RequiresAdminRole`) to match `Create`/`Destroy` on the same resource. Alternatively/additionally, strip `AccessKey` and `OutgoingToken` from `ExternalInitiatorResource` (the list/`Index` presenter) and only return them once, at creation time, via the existing `ExternalInitiatorAuthentication` presenter, consistent with how `Secret`/`OutgoingSecret` are already handled.

## Proof of Concept
1. Start a local node with `ExternalInitiatorsEnabled` and create at least one External Initiator via an edit/admin-role session (`POST /v2/external_initiators`), noting its `AccessKey`/`OutgoingToken`.
2. Provision a second API user with `Role: sessions.UserRoleView` and authenticate as that user.
3. Issue `GET /v2/external_initiators?size=100` as the `view`-role user.
4. Observe the JSON:API response body contains `accessKey` and `outgoingToken` attributes for the initiator created in step 1, as confirmed by the existing test assertions in `core/web/external_initiators_controller_test.go` (lines 104-126) and the RBAC route table entry `{"GET", "/v2/external_initiators", true, true, true}` in `core/web/auth/auth_test.go` (line 224), which encodes `viewOnlyAllowed: true` for this route. func (eic *ExternalInitiatorsController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	externalInitiators, count, err := eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)
	resources := make([]presenters.ExternalInitiatorResource, 0, len(externalInitiators))
	for _, initiator := range externalInitiators {
		resources = append(resources, presenters.NewExternalInitiatorResource(initiator))
	}

	paginatedResponse(c, "externalInitiators", size, page, resources, count, err)
}

type ExternalInitiatorAuthentication struct {
	Name           string        `json:"name,omitempty"`
	URL            models.WebURL `json:"url"`
	AccessKey      string        `json:"incomingAccessKey,omitempty"`
	Secret         string        `json:"incomingSecret,omitempty"`
	OutgoingToken  string        `json:"outgoingToken,omitempty"`
	OutgoingSecret string        `json:"outgoingSecret,omitempty"`
}

// NewExternalInitiatorAuthentication creates an instance of ExternalInitiatorAuthentication.
func NewExternalInitiatorAuthentication(
	ei bridges.ExternalInitiator,
	eia auth.Token,
) *ExternalInitiatorAuthentication {
	var result = &ExternalInitiatorAuthentication{
		Name:           ei.Name,
		AccessKey:      ei.AccessKey,
		Secret:         eia.Secret,
		OutgoingToken:  ei.OutgoingToken,
		OutgoingSecret: ei.OutgoingSecret,
	}
	if ei.URL != nil {
		result.URL = *ei.URL
	}
	return result
}
