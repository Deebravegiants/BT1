### Title
`_deployAndSeed` accepts a degenerate zero `virtualLtReserve` when the paired LT's `exchangeRate()` is high, zeroing `Pair.k` and letting the seed buy drain the entire curve for near-zero LT — ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding._deployAndSeed` derives the curve's launch-time virtual LT reserve as `virtualLtReserve = (VIRTUAL_LIQUIDITY_USD * 1e18) / exchangeRate` and only bounds it from above (`revert ExchangeRateTooLow()` if it exceeds `uint112.max/4`). There is no lower-bound / zero check other than `exchangeRate == 0` itself. If the paired BounceTech LT's `exchangeRate()` is large enough that `VIRTUAL_LIQUIDITY_USD * 1e18 / exchangeRate` floors to `0`, the curve is seeded with `reserveAsset = 0`, which is the exact "degenerate/zero public key" analog of CVE-2017-1000168: an all-zero input that the code should reject is silently accepted and produces a deterministic degenerate output (`Pair.k() = totalSupply * 0 = 0`) regardless of any legitimate counter-value. [1](#0-0) 

### Finding Description
In `Bonding._deployAndSeed`:
```
uint256 exchangeRate = IBounceLeveragedToken(ltAddress).exchangeRate();
if (exchangeRate == 0) revert ZeroExchangeRate();
uint256 virtualLtReserve = (VIRTUAL_LIQUIDITY_USD * 1e18) / exchangeRate;
if (virtualLtReserve > type(uint112).max / 4) revert ExchangeRateTooLow();
...
$.router.addInitialLiquidity(tokenAddr, totalSupply, curveSupply, virtualLtReserve);
``` [2](#0-1) 

Only an upper bound on `virtualLtReserve` is enforced; there is no check that `virtualLtReserve > 0`. Because Solidity integer division floors, any LT whose `exchangeRate()` (18-dp, USDC per LT) is `>= VIRTUAL_LIQUIDITY_USD * 1e18` produces `virtualLtReserve == 0`. `VIRTUAL_LIQUIDITY_USD` is the fixed dollar target (documented at ~$3K) that is supposed to seed every curve's launch-time depth — the same role the "public key" plays in the ECDH analog: it must be nonzero/well-formed for the downstream cryptographic (here, AMM) computation to be sound.

`Router.addInitialLiquidity` then calls `Pair.mint(virtualReserveToken, 0)`: [3](#0-2) 

`Pair.mint` sets `_pool.k = tokenReserve_init * assetReserve_init = totalSupply * 0 = 0`, a value that — per the protocol's own documentation — is "locked in at `Pair.mint` and never modified by swaps." [4](#0-3) 

With `k == 0`, every subsequent buy computation in `Router._computeBuy` becomes degenerate — exactly analogous to a zero shared-secret that no longer depends on the "private" input (here, the LT amount actually paid in):
```
uint256 newReserveAsset = reserveAsset + amountInUsed;
tokensOut = reserveToken - (k / newReserveAsset); // k == 0 → tokensOut == reserveToken (full reserve) for ANY amountInUsed > 0
``` [5](#0-4) 

This routes into the overflow-cap branch (`tokensOut > realBalance`), where the back-calculated LT price is also degenerate:
```
uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken; // k == 0 → floors toward 0
amountInUsed = cappedReserveAsset - reserveAsset;
``` [6](#0-5) 

Because `k = 0`, `cappedReserveAsset` rounds to essentially the smallest value satisfying the ceil-division, so `amountInUsed` is driven to near-zero regardless of `reserveToken` size. The `Pair.swap` K-invariant check is likewise defeated:
```
if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated();
```
With `_pool.k == 0`, this check can never fail — the AMM's core solvency invariant is void for this pair for its entire life. [7](#0-6) 

The net effect: any trader (including the token's own creator on the very first seed buy, or a later buyer) can acquire the *entire* 750M curve-token supply for a vanishingly small amount of LT, because the curve's constant-product invariant was seeded at `k=0` — the AMM equivalent of accepting an all-zero public key that always yields a zero (attacker-controlled/degenerate) shared secret.

### Impact Explanation
This is a direct, permanent freezing/theft-of-funds condition for any token launched against an LT whose `exchangeRate()` is high enough to floor `virtualLtReserve` to zero:
- The bonding curve for that token is permanently broken (`k = 0` for its whole life — `Pair.k` is immutable post-mint).
- Any buyer can drain essentially the full 750M real token supply from the curve for near-zero LT, effectively stealing the token's entire tradable supply and any LT subsequently deposited by other legitimate buyers before them.
- Because the supply-exhaustion graduation trigger (`tokenBalance() == 0`) fires immediately, the token graduates on the first buy, permanently locking in a worthless/degenerate LP price (near-zero LT for 750M tokens), which corrupts `_prepareGraduationLiquidity`'s "zero price gap" invariant and permanently damages the token's post-graduation market.
- This satisfies the Validate criteria: concrete theft of curve-raised value and an LP seeded at a price wildly divorced from any legitimate curve, i.e., unbacked token payout and value extraction from any USDC/LT contributed to that curve.

### Likelihood Explanation
Reachable by any unprivileged party performing `Zap.createToken`, which is exactly the permissionless entry point the rules require. The only precondition is pairing against an existing, `ltExists()`-registered BounceTech LT whose `exchangeRate()` has appreciated to/above `VIRTUAL_LIQUIDITY_USD` (documented ~$3,000, 18dp). Leveraged tokens are explicitly designed to appreciate (2x/3x long or short exposure), so over time any actively-traded LT that has grown enough naturally crosses this threshold — no privileged action, upgrade, or off-chain component is needed; the launch call itself (`Bonding.launch` → `_deployAndSeed`) contains no lower-bound guard against this. `_launchTimeVirtualLtReserve`'s only defensive check in the codebase is the *upper* bound (`ExchangeRateTooLow` on overflow); the zero/near-zero regime at the other end of the range is unguarded.

### Recommendation
Add an explicit lower bound in `Bonding._deployAndSeed` immediately after computing `virtualLtReserve`:
```solidity
if (virtualLtReserve == 0) revert ExchangeRateTooHigh();
```
Ideally also enforce a meaningful minimum (e.g., large enough that the curve's virtual depth remains within the expected precision), not just `> 0`, since a `virtualLtReserve` of `1` wei is equally degenerate. Mirror the same defensive posture already present for the overflow-cap side (`OverflowCapDegenerate`) by treating a zero/near-zero seed identically: reject the launch rather than silently minting a broken pair.

### Proof of Concept
1. BounceTech LT `L` exists (`ltExists(L) == true`) with `L.exchangeRate() >= VIRTUAL_LIQUIDITY_USD * 1e18` (e.g., a long-running 3x leveraged token that has appreciated past the $3,000 mark).
2. Any address calls `Zap.createToken(name, ticker, ..., ltAddress: L, seedUsdc, ...)`, which internally calls `Bonding.launch` → `_deployAndSeed`.
3. `virtualLtReserve = (VIRTUAL_LIQUIDITY_USD * 1e18) / L.exchangeRate()` floors to `0`; the only guard (`virtualLtReserve > type(uint112).max/4`) does not fire.
4. `Router.addInitialLiquidity(token, totalSupply, curveSupply, 0)` → `Pair.mint(totalSupply, 0)` sets `_pool.k = 0`.
5. The mandatory seed buy (or any subsequent public buy once the anti-snipe delay elapses) computes, in `Router._computeBuy`: `tokensOut = reserveToken - (0 / newReserveAsset) = reserveToken`, capped to `realBalance = 750,000,000e18`, with `amountInUsed` computed from `k=0` and rounding to near-zero.
6. The caller receives the full 750M curve-token supply for a fraction-of-a-cent worth of LT, and the token immediately supply-graduates with a near-worthless HyperSwap LP seeded at the same degenerate ratio.

(Existing repo tests such as `test_launch_allowsLowButViableExchangeRate` in `packages/contracts/test/Bonding.t.sol` confirm the *low*-rate side is tested and accepted without an upper-reserve issue, but no test in `Bonding.t.sol` or `GraduationInvariants.t.sol` exercises the high-exchange-rate / zero-`virtualLtReserve` boundary, confirming the gap is untested and unguarded.) [8](#0-7)

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }

        uint256 tokenIn,

        uint256 assetIn,
        uint256 assetOut
    ) external onlyRouter returns (bool) {
        uint256 newTokenReserve = (_pool.tokenReserve + tokenIn) - tokenOut;
        uint256 newAssetReserve = (_pool.assetReserve + assetIn) - assetOut;
        if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated();

        _pool.tokenReserve = newTokenReserve;
        _pool.assetReserve = newAssetReserve;
        emit Swap(tokenIn, tokenOut, assetIn, assetOut);
        return true;
    }
