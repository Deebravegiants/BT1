### Title
Locally-Determined Enrollment Success Bypasses Backend Signup Verification for User-Centric Signups - (File: `src/plans/mod.rs`)

### Summary
For `user_centric_signup` flows, the orb's main signup plan sets the enrollment outcome to `Success` purely from a locally-computed `signup_reason` value, without ever invoking the actual backend enrollment call (`enroll_user`, which POSTs to the signup backend and polls for confirmation). This mirrors the GMX bug class: a state transition that should be gated by an external, revertible operation (a real network call to the backend that can fail on duplicate detection, backend-side fraud checks, or connectivity issues) is instead performed via a purely local "accounting" shortcut that cannot fail the same way.

### Finding Description
In the non-user-centric path, signup success is only recorded after a real round trip to the backend: `enroll_user::Plan::run` calls `signup_post::request` and then polls `signup_poll::request`, and only returns `Status::Success` when the backend explicitly reports `success: true` and `status: Completed`. [1](#0-0) [2](#0-1) 

However, in `src/plans/mod.rs`, when `user_centric_signup` is true and the orb is not configured to `ignore_user_centric_signups`, the code skips this entire backend round trip and instead sets `debug_report.enrollment_status` directly from the *locally computed* `signup_reason` (itself derived only from local pipeline output and local, now-empty fraud checks): [3](#0-2) 

`signup_reason` is computed purely from local state — whether the local biometric pipeline produced output and whether local `detect_fraud` flagged fraud: [4](#0-3) 

Notably, the local fraud-check engine has had all actual checks removed (`N_FRAUD_CHECKS = 0`), so `detect_fraud` unconditionally returns `false`/no fraud detected: [5](#0-4) [6](#0-5) 

This is structurally identical to the GMX bug: the "transfer" (the real backend enrollment call that can revert/fail due to duplicate signups, backend-detected fraud, or network/service problems) is bypassed, and the outcome is instead derived from an internal, always-optimistic local computation, analogous to `getLiquidationValues()` updating internal accounting instead of doing an actual token transfer that could revert.

### Impact Explanation
For the user-centric signup path, a signup can be marked `enroll_user::Status::Success` — and thus `result.success = true`, driving `debug_report.signup_successful()` and the UI's success flow — without the backend ever confirming or being asked to confirm the signup. This can lead to:
- Misattributed/unauthorized signup success: an identity credential/signup can be treated as finalized locally while the backend's own verification (duplicate-signup detection, backend fraud detection) is never consulted, since `enroll_user` (the function that performs `signup_post::request`/`signup_poll::request`) is never called on this path.
- Loss of the backend's ability to veto a fraudulent or duplicate signup for user-centric signups, since the "gate" that could fail (the real HTTP call) is replaced by data that is optimistic by construction (local fraud detection is a no-op).

### Likelihood Explanation
This path is reachable whenever the user's QR code data sets `user_centric_signup: true` and the orb's config does not set `ignore_user_centric_signups`. It requires no special privilege beyond a normal signup attempt and is not gated by attacker-controlled corrupt input — it is a structural bypass in the main signup control flow, triggered under ordinary conditions whenever this signup mode is active.

### Recommendation
For `user_centric_signup`, still perform the real backend confirmation call (`enroll_user`/`signup_post` + `signup_poll`) before recording `Success`, rather than deriving the enrollment result solely from local pipeline/fraud state. If the intent is to avoid double confirmation, the backend interaction should be the authoritative source of truth for success/failure, with local `signup_reason` only used to select which reason to report, not to bypass backend confirmation entirely.

### Proof of Concept
1. Trigger a signup where `user_data.user_centric_signup == true` and orb config `ignore_user_centric_signups == false`.
2. Ensure the local biometric pipeline produces output (`pipeline.is_some()`), which is trivial since only pipeline crashes cause `None`.
3. Because `fraud_check::Report::fraud_detected_with_config`/`detect_fraud` always resolves to "no fraud" (0 checks compiled in), `signup_reason` resolves to `SignupReason::Normal`.
4. Code path in `src/plans/mod.rs:639-645` sets `debug_report.enrollment_status(enroll_user::Status::Success)` directly — the real `enroll_user::Plan::run` (which posts to `/api/v2/signups/{id}` and polls for backend completion) is never invoked, so no backend-side duplicate/fraud check ever occurs for this signup.
5. `result.success` becomes `true` purely from this local determination.

Note: I was unable to fully trace how `enrollment_status`/`result.success` is consumed further downstream (e.g., whether a credential is minted or persisted as a result) due to indexing/context limits; a full Devin session with complete repository access would be needed to confirm the ultimate downstream consequence of this bypass.
