### Title
ERC777/callback-token reentrancy amplifies escrowed order amount in `placeOrder` via balance-diff accounting - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.placeOrder` measures the actual amount received for each ERC20 input by diffing `balanceOf(address(this))` before and after `safeTransferFrom`, exactly the pattern described in the ERC777 reentrancy report. Because the "actual received" amount computed from this diff feeds directly into `order.inputs[i].amount`, the order commitment, and the escrow accounting, a token with a pre-transfer hook (ERC777 `tokensToSend`, or any ERC-1363/ERC-777-style callback token) lets an attacker re-enter `placeOrder`/related paths during the `safeTransferFrom` call and inflate the recorded escrow amount relative to what was actually pulled from them, the same amplification mechanic as the original PolygonZkEvmBridge bug.

### Finding Description
In the non-predispatch escrow branch of `placeOrder`: [1](#0-0) 
the amount actually escrowed for a token input is computed as `balanceOf(this) after − balanceOf(this) before` around `safeTransferFrom`, mirroring the vulnerable PolygonZkEvmBridge code quoted in the external report almost verbatim. This value then becomes part of `order.inputs[i].amount`, which is used both to compute the order `commitment` (`keccak256(abi.encode(order))`) in Phase 2 and to size the escrow recorded for that commitment: [2](#0-1) 

If the input token exercises a pre-transfer callback into the caller (ERC777 `tokensToSend`, or any custom token registered via ERC1820, since the gateway accepts arbitrary attacker-supplied ERC20 addresses as `order.inputs[i].token`), the attacker can re-enter the escrow-transfer loop (or a sibling deposit path) while `balanceOf(this)` has not yet reflected the outer transfer, causing the "received amount" to be double- or multiply counted across nested calls — precisely the `LEVEL * amount` amplification described in the external report. Unlike the Tron variant of this contract (`evm/tron/contracts/apps/IntentGatewayV2.sol:450-469`), which stores a fixed pre-computed `reducedInputs[i].amount` into escrow rather than a balance-diff value, this EVM/core version ties the escrowed/commitment amount directly to the manipulable balance measurement.

The contract does declare `ReentrancyGuardTransient` at the top level: [3](#0-2) 
and a dedicated regression suite exists proving `fillOrder`'s CEI ordering blocks reentrancy on the *fill* side: [4](#0-3) 
However, no equivalent reentrancy test or `nonReentrant` guard was found scoped specifically to `placeOrder`'s balance-diff escrow loop, and the fee-on-transfer test suite only validates the honest-token diff behavior, not adversarial reentrant tokens: [5](#0-4) 

### Impact Explanation
Because the diffed amount becomes part of the order commitment and the per-token escrow ledger `_orders[commitment][token]`, an attacker who supplies a malicious ERC777-style token as an order input can record an escrow/commitment amount larger than what they actually transferred into the gateway. When solvers or cross-chain redemption logic later settle against `_orders[commitment][token]`, the attacker can extract more value than deposited, draining shared token liquidity belonging to other users/solvers of the same token pool — a concrete theft-of-funds outcome matching the accepted impact criteria (unauthorized withdrawal / freezing of others' escrowed balances).

### Likelihood Explanation
The `placeOrder` entry point is fully unprivileged: any address can call it with an attacker-controlled token contract as `order.inputs[i].token` and arbitrary calldata/hooks in that token. No allow-list of input tokens was found restricting this to vetted ERC20s. The only friction is registering an ERC1820 interface implementer (trivial, one transaction) and deploying a custom token with a `tokensToSend`-style hook — well within reach of a single attacker transaction, matching the original report's "one transaction" exploitation model.

### Recommendation
- Apply `nonReentrant` (the existing `ReentrancyGuardTransient`) directly to `placeOrder` (and any other function performing balance-diff accounting around external token calls), not just to the fill/withdraw paths.
- Alternatively/additionally, follow the Checks-Effects-Interactions pattern already used to fix `fillOrder`: finalize/lock the order's nonce or commitment slot before performing external `safeTransferFrom` calls, so a reentrant `placeOrder` cannot observe a stale `balanceOf` snapshot.
- Consider capping supported input tokens to a vetted allow-list, or measuring balance diffs per logical transfer with an explicit reentrancy lock around the whole escrow loop rather than relying solely on contract-level guards that may not be wired to every state-mutating entry point.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC20 that also registers as its own ERC777 `tokensSender` implementer in `_ERC1820_REGISTRY`, with `tokensToSend()` calling back into `IntentGatewayV2.placeOrder` (or the relevant escrow function) with a fresh order using the same `EvilToken` as input, amount = 1 (bypassing the `amount == 0` check).
2. Attacker calls `placeOrder(order, graffiti)` with `order.inputs[0] = {token: EvilToken, amount: X}` and approves the gateway for `X`.
3. During `IERC20(EvilToken).safeTransferFrom(msg.sender, address(this), X)`
   ( [6](#0-5) ), `tokensToSend` fires before the balance actually changes, re-entering `placeOrder` N times with small/zero-net amounts.
4. Each nested call captures `balBefore = 0` (pre-transfer) and, once the outermost transfer finally lands, every nested frame's `balanceOf(this) - balBefore` diff resolves to the full transferred amount `X`, so N nested commitments are minted, each recording escrow of `X`, while only `X` tokens were actually deposited once.
5. Attacker (or colluding solver) redeems/cancels each of the N inflated commitments, draining `(N-1) * X` in shared token liquidity that was never actually deposited.
