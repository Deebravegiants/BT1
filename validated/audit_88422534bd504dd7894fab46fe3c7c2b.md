### Title
Unchecked BEEFY vote-signature length causes a panic (chain-halting DoS) when decoding the Naive/ECDSA consensus proof — (File: `evm/rust/src/conversions.rs`)

### Summary
`impl From<Vote> for SignatureWithAuthorityIndex` copies an attacker-controlled, arbitrary-length ABI `bytes` field into a fixed 65-byte array with `copy_from_slice` and no length check, so a malformed length panics instead of erroring. [1](#0-0) 

### Finding Description
The BEEFY `Vote` type (`signature: bytes`, from Solidity ABI) is decoded via `abi_decode_params` with no length constraint — `bytes` in ABI encoding can be any length. The `From<Vote>` conversion then does:
```rust
let sig_bytes = value.signature.to_vec();
let mut signature: TSignature = [0u8; 65];
signature.copy_from_slice(&sig_bytes);
``` [2](#0-1) 
`copy_from_slice` panics whenever `sig_bytes.len() != 65`. This conversion is reached from `From<RelayChainProof> for MmrProof`, which maps every `votes` entry through `Into::into()` unconditionally:
```rust
signatures: value.signedCommitment.votes.into_iter().map(Into::into).collect(),
``` [3](#0-2) 
and that in turn is reached from `From<BeefyConsensusProof> for ConsensusMessage`: [4](#0-3) 

This whole chain is designed to be the ABI-decode boundary for a Naive/ECDSA BEEFY consensus proof submitted on-chain by any relayer/submitter (an unprivileged, signed extrinsic per the pallet's own documentation: "Proofs are submitted via **signed** extrinsics"), analogous to `PROOF_TYPE_NAIVE`/`BeefyConsensusProof` handling seen elsewhere in the beefy client (`modules/ismp/clients/beefy/src/consensus.rs`) which ABI-decodes an untrusted `proof` payload before any signature/authority verification takes place. [5](#0-4) 

This is the same bug class as the LibreDWG CVE cited in the report: an attacker-supplied length field drives an unchecked, fixed-size buffer copy past its bounds — here in safe Rust that manifests as a deterministic runtime panic rather than heap corruption, but the underlying flaw (trusting an untrusted length before bounding a fixed-size copy) is identical. Elsewhere in this same codebase, the pattern is explicitly recognized and fixed with an `if sig.len() != 65 { return None; }` guard before the analogous copy in `modules/consensus/beefy/prover/src/lib.rs`: [6](#0-5) 
— but the guard is missing in `evm/rust/src/conversions.rs`'s `From<Vote>`.

### Impact Explanation
A runtime panic triggered deterministically by the same submitted extrinsic on every validator/collator executing the block is a consensus-halting fault: block execution traps for all nodes applying the same state transition, which can stall block production/finalization for the chain that hosts this pallet (denial of service on the BEEFY consensus-update path). This directly maps to "a route unable to deliver messages" since the BEEFY light client is the mechanism by which cross-chain messages get their consensus/state proofs verified; if the consensus-update extrinsic path panics, new consensus updates (and therefore all downstream ISMP message delivery gated on this consensus client) cannot proceed.

### Likelihood Explanation
High: `Vote.signature` is a plain ABI `bytes` field with no length assertion anywhere before this conversion, decoded straight from proof bytes an ordinary signed extrinsic submitter controls. Producing a `Vote` with a signature of any length other than 65 bytes is trivial and costs only the submitter's own transaction fee (their proof will fail cryptographic verification anyway, but the panic happens during the unconditional type conversion, before verification runs).

### Recommendation
Validate `value.signature.len() == 65` in `From<Vote> for SignatureWithAuthorityIndex` and return a `Result`/typed error instead of using an infallible `From` with an unchecked `copy_from_slice`, mirroring the guard already present in `beefy/prover/src/lib.rs` (`if sig.len() != 65 { return None; }`). Since `From` cannot fail, convert this to `TryFrom` and propagate the error through `RelayChainProof -> MmrProof` and `BeefyConsensusProof -> ConsensusMessage` conversions (which will also need to become fallible) so malformed proofs are rejected with a normal dispatch error rather than panicking.

### Proof of Concept
1. Submit a signed extrinsic that invokes the BEEFY consensus-proof entry point (`verify_and_apply` / the pallet call wrapping `BeefyConsensusProof`/`RelayChainProof`, PROOF_TYPE_NAIVE) with an ABI-encoded `RelayChainProof` whose `signedCommitment.votes[i].signature` is any length other than 65 bytes (e.g., 64 or 66 bytes) — trivially constructible since `bytes` accepts arbitrary length in ABI encoding.
2. On processing, `<ismp_abi::...>::abi_decode_params` succeeds (no length constraint on `bytes`), and the `.into(): ConsensusMessage` conversion chain reaches `From<Vote> for SignatureWithAuthorityIndex`.
3. `signature.copy_from_slice(&sig_bytes)` panics because `sig_bytes.len() != 65`, aborting the extrinsic's execution abnormally instead of returning a `DispatchError`, deterministically for every node executing the block.
