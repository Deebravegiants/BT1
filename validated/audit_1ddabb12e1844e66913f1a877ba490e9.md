### Title
Webhook `shop-domain` (and `topic`/`api_version`/`webhook_id`) are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while the shop identity (`shop-domain` header) used by the webhook dispatcher to attribute the event to a tenant is taken from an unsigned header. Any party in possession of one valid `(raw_body, hmac)` pair signed with the app's `client_secret` — trivially obtainable by installing the app on an attacker-controlled shop — can replay that pair with a forged `shop-domain` header and have it accepted as an authentic webhook for an arbitrary victim shop.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

but `Request#shop` (as well as `topic`, `api_version`, `webhook_id`) is read directly from HTTP headers, which are entirely attacker-controlled on the wire: [2](#0-1) 

`Registry.process` validates only the HMAC-over-body via `Utils::HmacValidator.validate(request)`, then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (i.e. the raw body for webhooks) and the app's single, global `Context.api_secret_key` (shared across every shop that installs the app): [4](#0-3) 

Because the same `client_secret` signs webhooks for *all* shops that install a given app, and the `shop-domain` header is excluded from what is signed, the binding `hmac-authenticated payload == shop the handler believes it came from` does not hold. This is the same root cause pattern as the referenced report: a field that participates in downstream logic (there, `feePct`; here, `shop`) is excluded from the calculation/verification that is supposed to bind it (there, precision truncation; here, HMAC coverage), so an attacker can manipulate that field independent of the verified value.

### Impact Explanation
An unprivileged internet user who installs the target Shopify app on their own (attacker-controlled) shop receives genuine webhooks, each a valid `(body, hmac)` pair signed with the app's `client_secret`. Nothing prevents that user from POSTing the exact same body/HMAC to the app's webhook endpoint again while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain. `Utils::HmacValidator.validate` will accept it (it never inspects `shop`), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event is `shop: <victim>`. Any app logic that trusts `data.shop` for tenant-scoped effects (e.g., looking up/mutating the victim shop's stored session or data, triggering shop-scoped side effects, or bypassing per-shop authorization checks) is cross-tenant compromised — this matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Requires only (a) the ability to install the target app on any shop (an ordinary, unprivileged Shopify merchant action — no special credential beyond a free dev/partner store) and (b) the ability to send arbitrary HTTP requests to the app's public webhook endpoint. No access token, `api_secret_key`, or privileged account of the *victim* is needed. This is realistic and low-effort for a determined attacker.

### Recommendation
Include the tenant-identifying and semantic fields (`shop`, `topic`, `api_version`, `webhook_id`) in the HMAC-signable string, or otherwise cryptographically bind the shop domain to the signed payload, so that a signature computed over one shop's data cannot be replayed with a different shop's identity. At minimum, document that consumers of `WebhookMetadata#shop` must independently confirm that the resolved shop has an active installation/session before trusting it for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering a legitimate webhook, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(client_secret, B)`), and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the identical request to the app's webhook endpoint but replaces the header with `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`: [5](#0-4) 
   which only checks `HMAC(client_secret, B) == H` — still true, since `B` and `H` are unchanged.
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: B, ...)`, believing the event originated from the victim shop, even though it never did.
