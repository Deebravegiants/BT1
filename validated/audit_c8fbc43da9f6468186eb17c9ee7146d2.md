### Title
Zero-amount output legs allow a solver to claim escrowed input tokens for free — (File: evm/src/apps/intentsv2/IntrinsicIntents.sol)

### Summary
`IntentGatewayV2.placeOrder()` rigorously validates that every **input** leg has a non-zero amount (`if (order.inputs[i].amount == 0) revert InvalidInput();`) [1](#0-0) [2](#0-1) , but it performs **no equivalent check on `order.output.assets[i].amount`**. Nothing in `placeOrder` rejects an order whose declared output requirement is zero, mirroring the reported "zero leverage cycles" class of bug: a degenerate, economically meaningless value is silently accepted at creation time and produces broken/exploitable downstream behavior.

### Finding Description
In `IntrinsicIntents.sol`'s fill logic, each output leg is processed as:

```solidity
uint256 totalRequired = order.output.assets[i].amount;
uint256 solverAmount = options.outputs[i].amount;
uint256 alreadyFilled = _partialFills[commitment][outputToken];
uint256 remaining = totalRequired - alreadyFilled;
if (remaining == 0 || solverAmount == 0) {
    if (solverAmount == 0 && remaining > 0) isFullyFilled = false;
    continue;
}
``` [3](#0-2) 

If `order.output.assets[i].amount == 0` (`totalRequired == 0`), then `remaining` is `0` on the very first fill attempt, so the leg is treated as already satisfied (`continue`) and `isFullyFilled` is never set to `false` for that leg, since the branch only flips it false when `solverAmount == 0 && remaining > 0`. Later, `if (totalRequired > amountFilled) isFullyFilled = false;` is likewise never triggered because `totalRequired` is `0` [4](#0-3) . Consequently the order is reported fully filled and the escrowed input tokens for that leg are released to whichever address calls `fillOrder` — even though that caller supplied zero value in return.

This is not a hypothetical edge case: the SDK's own filler strategy explicitly documents that this is a real, live behavior of the gateway, not a theoretical corner case:

```
// A zero requested output is degenerate on the fill path: the gateway
// releases no escrow for it (remaining == 0), yet the leg would still be
// sized and could feed the profit gate. Never bid on such an order.
if (order.output.assets.some((a) => a.amount === 0n)) {
``` [5](#0-4) 

The escrow amount for that input leg is still non-zero (it was validated `!= 0` at `placeOrder`), so once `isFullyFilled` incorrectly evaluates true, `_withdraw(..., finalize=true)` transfers the full escrowed input balance to the caller with zero compensation supplied for that leg — analogous to the reported "opening a 0-leverage position": a degenerate, unvalidated zero-value field on entry (there: leverage cycles; here: output amount) that the contract logic subsequently mishandles, resulting in loss of the user's escrowed value.

### Impact Explanation
Any user who submits (or is tricked/griefed into submitting, e.g. via a front-end bug, malformed intent, or malicious dApp) an order with a zero-amount output leg has that leg's escrowed input tokens claimable by literally any address calling `fillOrder` with a matching zero `solverAmount`, at no cost. This is a direct, unbacked transfer of escrowed user funds to an attacker/solver — concrete theft of funds, matching the required "concrete theft ... of funds" bar. It also matches the report's freezing angle: for multi-leg orders where only some legs are zero, the trivially-satisfied zero leg can distort `isFullyFilled` bookkeeping in `_partialFills` state used elsewhere in escrow accounting.

### Likelihood Explanation
Requires a user (or intent-encoding pallet/relayer/SDK) to submit an order with `output.assets[i].amount == 0` for at least one leg — plausible via UI/input error or a malformed intent from an integrating protocol, exactly as the source report characterizes likelihood as low but impact meaningful. Unlike governance/admin-triggered bugs, this path is reachable by any unprivileged order submitter through the normal `placeOrder` → `fillOrder` flow, satisfying the reachable-by-unprivileged-transaction requirement.

### Recommendation
In `placeOrder` (and its Tron/EVM variants), reject orders where any `order.output.assets[i].amount == 0`, mirroring the existing input-amount validation. Additionally, harden `IntrinsicIntents.sol`'s fill loop so a `totalRequired == 0` leg cannot be counted toward `isFullyFilled` at all, independent of the `placeOrder` fix (defense in depth).

### Proof of Concept
1. User calls `placeOrder` with two output legs: leg A with a legitimate non-zero amount, leg B with `amount = 0` (input tokens escrowed are non-zero and pass the existing `inputs[i].amount == 0` check).
2. Any solver calls `fillOrder` providing `options.outputs[B].amount = 0` (and satisfying leg A normally).
3. In the fill loop, leg B hits `remaining == 0` and is skipped without decrementing `isFullyFilled`; combined with leg A being genuinely filled, `isFullyFilled` evaluates `true`.
4. `_withdraw(..., finalize=true)` releases the **full escrowed input amount for leg B's corresponding input** to the solver's beneficiary, even though the solver provided nothing for that leg — net theft of the user's escrowed tokens for that leg.
