## Title
Webhook shop/topic identity spoofing — HMAC only covers the request body, not the `shop-domain`/`topic`/`webhook-id` headers - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC of the raw request **body**. The `shop`, `topic`, `webhook_id`, and `api_version` values that the app's handler subsequently trusts are all pulled from HTTP **headers**, which are never included in the signed payload. Anyone who can obtain one genuinely-signed webhook body (trivially, by installing the app on their own store) can replay that exact body to the app's webhook endpoint while freely rewriting the `shop-domain`, `topic`, and `webhook-id` headers, and the gem will accept it as authentic and hand it to the app's handler under the attacker-chosen shop/topic identity.

### Finding Description
The binding that should hold is:
`shop header value used by the app == shop that the HMAC-signed bytes actually originated from`

But `Webhooks::Request#to_signable_string` only returns the raw body: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from client-controlled headers with no cryptographic tie to the body: [2](#0-1) 

`Registry.process` verifies only that body against the shared secret via `Utils::HmacValidator.validate`, then immediately constructs `WebhookMetadata` using the unauthenticated header fields and dispatches it to the registered handler: [3](#0-2) 

`HmacValidator.validate` computes the HMAC purely from `to_signable_string` (i.e., the body) and the app's `api_secret_key` — it never incorporates headers: [4](#0-3) 

Because the signature covers only the body, an attacker who legitimately installs the app on their own store `attacker-shop.myshopify.com` will receive real webhook deliveries with a valid `X-Shopify-Hmac-Sha256` computed over that body using the app's real secret (Shopify signs with the shared secret regardless of which merchant triggered it). The attacker can capture such a delivery (body + valid HMAC header) and re-POST it to the app's public webhook endpoint, substituting:
- `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
- `X-Shopify-Topic: shop/redact` (or `customers/redact`, `app/uninstalled`, etc.)
- `X-Shopify-Webhook-Id: <arbitrary>`

The HMAC check still passes (body unchanged), and `Registry.process` calls the handler with `shop: "victim-shop.myshopify.com"` and the attacker-chosen topic, even though that body never actually originated from, nor was ever authorized for, that shop or topic.

### Impact Explanation
This breaks the tenant-isolation guarantee the gem is expected to provide to host applications: HMAC validation is the *only* authentication mechanism for inbound webhooks, and host apps are expected to trust `WebhookMetadata#shop`/`#topic` as coming from Shopify for that specific shop. Since these identity fields are unauthenticated, an attacker (an ordinary merchant who installs the app) can impersonate an arbitrary victim shop for any registered webhook topic — e.g., forcing processing of a spoofed `shop/redact`/`customers/redact` mandatory compliance webhook or `app/uninstalled` against a victim shop, or feeding attacker-controlled but victim-attributed data into any handler keyed by `data.shop`. This is a cross-tenant identity-confusion vulnerability reachable by an unprivileged internet user with no special credentials beyond installing the app once on a shop they control.

### Likelihood Explanation
High. No secrets or privileged access are required — only the ability to install the app on any store (including a free/dev store) to obtain one genuinely HMAC-signed webhook body, and the ability to send arbitrary HTTP requests with custom headers to the app's public webhook endpoint.

### Recommendation
Bind the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) into the signed material verified by `Utils::HmacValidator`, or otherwise cryptographically tie them to the body (e.g., verify `shop`/`topic` also appear inside the parsed, HMAC-covered JSON body where Shopify includes them), so that a body signed for one shop/topic cannot be replayed under a different shop/topic combination.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com` and trigger a webhook the app subscribes to (e.g. `orders/create`). Shopify delivers:
   - Body: `B`
   - Header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` using the app's `api_secret_key`)
   - Header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - Header `X-Shopify-Topic: orders/create`
2. Capture `B` and `H` (e.g., via a proxy on the attacker's own server that observed the delivery).
3. POST to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` unchanged, but `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and, if desired, `X-Shopify-Topic: shop/redact`.
4. `Webhooks::Request.new` builds successfully (all required headers present); `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `@raw_body` only and matches `H` — validation passes.
5. `Registry.process` dispatches `WebhookMetadata.new(topic: "shop/redact", shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)` to the app's handler, which now executes shop-redaction (or whatever topic-specific) logic against `victim-shop.myshopify.com`, a shop the attacker never installed on nor was ever authorized to act on behalf of.
