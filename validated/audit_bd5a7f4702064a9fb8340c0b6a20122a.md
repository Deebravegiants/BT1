## Front-running/sandwich manipulation of the Uniswap V2 fee swap causes permanent loss of native-token overpayment in `EvmHost` - (File: `evm/src/core/EvmHost.sol`)

### Summary
The Havven `IssuanceController` report describes front-running an on-chain price used to convert a user's payment into tokens, to the user's disadvantage. The Hyperbridge analog is in `EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()`: whenever a message dispatcher pays the relayer fee with native token, the host performs an on-chain, sandwichable Uniswap V2 spot-price swap (`swapETHForExactTokens`) and any refunded "dust" ETH from that swap is sent to `address(this)` (the Host) instead of back to the original caller, permanently trapping the user's overpayment.

### Finding Description
`dispatch(DispatchPost)` and `dispatch(DispatchGet)` both execute: [1](#0-0) [2](#0-1) 

and `fundRequest()` does the same: [3](#0-2) 

`swapETHForExactTokens(amountOut, path, to, deadline)` on Uniswap V2's router computes `amounts[0] = getAmountsIn(amountOut, path)` against the pool's live spot reserves, requires `amounts[0] <= msg.value`, and refunds `msg.value - amounts[0]` in ETH to `msg.sender` — which in this call is the `EvmHost` contract, not the original dispatcher who supplied `msg.value`. Because `getAmountsIn` is a spot-price read with no TWAP or oracle protection, it is directly manipulable by front-running/sandwiching: an attacker who observes a pending `dispatch()`/`fundRequest()` transaction in the mempool can trade against the pool beforehand to shift the effective price at execution time.

Callers must supply `msg.value` before knowing the exact spot price at execution, so SDK helpers deliberately overestimate and attach a buffer (1–2%) above the quoted cost, e.g.: [4](#0-3) [5](#0-4) 

The docs themselves warn this on-chain quote is "vulnerable to sandwich attacks": [6](#0-5) 

Whenever `amounts[0] < msg.value` (i.e., any time the buffer is not fully consumed, which is the normal, expected case, and is exacerbated whenever an attacker manipulates the pool price down between quote-time and execution-time to widen the residual), the router refunds the difference to the `EvmHost` contract itself. `EvmHost` never forwards this refund back to `_msgSender()`/`post.payer`, so the ETH is permanently absorbed by the Host with no accounting path back to the user who paid it.

### Impact Explanation
Every unprivileged message dispatcher who pays Hyperbridge dispatch/fund-request fees with native ETH (the "Native Token" payment path documented for both `dispatch(DispatchPost)` and `dispatch(DispatchGet)`) permanently loses any overpayment above the router's realized swap cost — a guaranteed, protocol-wide fund loss on the primary native-fee payment path, not merely a griefing/DoS issue. This loss is amplified by an attacker who front-runs the pending dispatch transaction to move the AMM spot price, either forcing the transaction to revert (wasted gas/DoS) or widening the gap between the quoted price and the realized swap price so more of the user's buffer/dust is captured by the Host instead of refunded to them. This is a Medium/High severity permanent loss-of-funds bug reachable from a single unprivileged dispatch transaction.

### Likelihood Explanation
Every native-token dispatch is affected because SDK tooling always attaches a price buffer (seen throughout `hyperFungibleToken.ts`, `tokenGateway.ts`, and `EvmHost.ABI`-based fee estimation) to guard against exactly this kind of spot-price slippage, guaranteeing dust ETH accrues on essentially every native-fee dispatch; the loss is deterministic, not merely theoretical, and requires no special privileges — any user calling `dispatch{value: ...}(...)` or `fundRequest{value: ...}(...)` is affected, and any onlooker can amplify the loss via ordinary mempool front-running of the Uniswap V2 pool used as `_hostParams.uniswapV2`.

### Recommendation
Track the router's actual native-token balance before and after the swap call (or use `swapExactETHForTokens`-style accounting) and refund any residual ETH to `_msgSender()`/`post.payer` rather than leaving it in `EvmHost`. Consider exposing a `minAmountOut`/`maxAmountIn` parameter under caller control, and prefer the fee-token payment path (or a TWAP-based fee oracle) for any state-changing dispatch calls, consistent with the docs' own warning against using spot Uniswap quotes for on-chain execution.

### Proof of Concept
1. Dispatcher calls `EvmHost.dispatch{value: v}(DispatchPost{fee: F, ...})` where `v` includes a small buffer above the quoted native cost for `F` fee-token units (as recommended/implemented by the SDK).
2. `EvmHost` calls `IUniswapV2Router02.swapETHForExactTokens{value: v}(F, [WETH, feeToken], address(this), block.timestamp)`.
3. Uniswap V2 computes `amountIn = getAmountsIn(F, path) < v`, executes the swap, and calls `TransferHelper.safeTransferETH(msg.sender, v - amountIn)` — refunding the difference to `EvmHost` (the caller of the router), not to the original dispatcher.
4. `EvmHost.dispatch()` never reads or forwards this refund; the surplus ETH remains permanently in the `EvmHost` contract's balance, unrecoverable by the original payer.
5. An attacker observing step 1 in the mempool can front-run a trade against the `WETH/feeToken` pool to either push `amountIn` above `v` (causing the whole dispatch to revert) or to shrink `amountIn` relative to the quote used to size `v` (increasing the trapped dust), demonstrating the front-running/sandwich amplification of the underlying loss-of-funds bug.
