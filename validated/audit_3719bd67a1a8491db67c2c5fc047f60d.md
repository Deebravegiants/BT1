### Title
First authority-set rotation reward is permanently unrecordable due to a zero-default epoch sentinel - ([File: evm/src/core/HandlerV2.sol])

### Summary
`EvmHost` uses `_currentEpoch == 0` both as the genesis default ("no epoch recorded yet") and as a legitimate epoch value (the genesis authority set, epoch 0, whose rotation is what `nextAuthoritySetId == 1` represents). `HandlerV2.handleConsensus` gates the call to `recordEpoch` with `epoch > host.currentEpoch()`, which is structurally identical to the Derby `require(user.withdrawalRequestPeriod == 0)` bug: a strict ordering check against a field whose default value collides with a real, in-range value.

### Finding Description
In `evm/src/core/HandlerV2.sol`, `handleConsensus` computes the epoch to credit from the consensus proof's `nextAuthoritySetId`: [1](#0-0) 

and only calls `host.recordEpoch(epoch, _msgSender())` when `epoch > host.currentEpoch()`. `EvmHost.recordEpoch` re-applies the same strict check: [2](#0-1) 

`_currentEpoch` initializes to `0` (Solidity default) and is never explicitly seeded. The very first mandatory rotation that a relayer can ever prove is `nextAuthoritySetId == 1`, i.e. `epoch = 0` — the genesis authority set. At that point `host.currentEpoch()` is also `0`, so `epoch > host.currentEpoch()` evaluates `0 > 0 == false`, and `recordEpoch` is never invoked. `_epochs[0]` (queried via `relayerOf(0)`) permanently stays `address(0)`, and `_currentEpoch` remains `0`. Once a later proof legitimately advances the epoch (e.g. `nextAuthoritySetId == 2`, `epoch = 1`), the check `1 > 0` passes and all subsequent epochs are recorded correctly — but epoch 0 can never be revisited or backfilled, because the same monotonic guard (`authoritySetId <= _currentEpoch`) in `recordEpoch` would now reject any attempt to write epoch 0 after `_currentEpoch` has advanced past it.

This is exactly the Derby class of bug: a "not yet set" guard implemented as `field == 0` (or here, `newValue > storedValue` against a zero-initialized field) that cannot distinguish "genuinely at value 0" from "never initialized," causing the zero-valued instance of the legitimate state transition to be silently dropped rather than recorded. In Derby it caused share-burning/allowance overwrite; here it causes the reward-attribution write for epoch 0 to be permanently skipped.

The relayer reward pallet (`modules/pallets/relayer/src/outbound_consensus.rs`) explicitly depends on `EvmHost._epochs[set_id]` being populated by `HandlerV2.handleConsensus` → `EvmHost.recordEpoch` in order to prove, via storage proof, which relayer address to pay the `OutboundConsensusDeliveryReward` to: [3](#0-2) 

Since `_epochs[0]` can never be non-zero, no relayer can ever construct a valid storage proof + signature to claim the reward for the genesis rotation (set_id 0) on any newly deployed `EvmHost`. This is corroborated by the test suite: every existing test that exercises reward recording deliberately starts one rotation ahead (`_makeConsensusProof(2000, 1, 2)`, crediting epoch 1) rather than the true first case (`nextAuthoritySetId == 1`, epoch 0), so the gap is untested. [4](#0-3) 

### Impact Explanation
Every relayer that is first to submit the genesis authority-set rotation proof to a given `EvmHost` deployment permanently loses eligibility for that host's `OutboundConsensusDeliveryReward` for epoch 0 — the funds allocated for that reward become permanently unclaimable/frozen for that (destination, set_id=0) pair, since `OutboundConsensusRotationsClaimed`/`_epochs[0]` can never resolve to a real relayer address. This falls under "permanent freezing of funds" / broken relayer reward accounting, which is explicitly in scope. The loss is deterministic and occurs on the normal, unprivileged happy path (any permissionless relayer submitting the first mandatory consensus update reachable via `HandlerV2.handleConsensus`), not requiring any malicious actor.

### Likelihood Explanation
High likelihood of occurrence (it happens on every single `EvmHost` deployment's first authority-set rotation, unconditionally, with no attacker required), though the value at risk is bounded to a single epoch's reward per host rather than unbounded funds — this keeps it in the Medium severity range.

### Recommendation
Track "has any epoch been recorded" explicitly rather than relying on `_currentEpoch == 0` as a sentinel — e.g., add an `_epochInitialized` boolean, or initialize `_currentEpoch` to `type(uint256).max` sentinel with a dedicated "first write" branch, or change the comparison to `>=` combined with an explicit initialized flag so that `epoch == 0` can be recorded exactly once. Mirror the fix pattern from the Derby report: require the guard to distinguish "never set" from "legitimately zero," and add a regression test that exercises `nextAuthoritySetId == 1` (epoch 0) specifically.

### Proof of Concept
1. Deploy a fresh `EvmHost`; `_currentEpoch` defaults to `0`, `_epochs[0]` is `address(0)`.
2. A relayer submits a valid consensus proof via `HandlerV2.handleConsensus(host, proof)` where the consensus client returns `nextAuthoritySetId = 1` (the genesine authority set just rotated) — analogous to `evm/tests/foundry/HandlerV2Test.sol`'s `_makeConsensusProof(2000, 1, 1)` pattern but using `1` instead of the tested `2`.
3. Inside `handleConsensus`: `epoch = nextAuthoritySetId - 1 = 0`; check `epoch > host.currentEpoch()` → `0 > 0` → `false`; `recordEpoch` is never called.
4. `host.relayerOf(0)` still returns `address(0)`; `host.currentEpoch()` still returns `0`.
5. The relayer pallet's `claim_outbound_consensus_delivery_reward` for `(destination, set_id=0)` can never produce a valid storage-proof + signature pair (the proven slot value is `address(0)`, no signature can recover to it), so the reward for epoch 0 is permanently unclaimable.
6. Any later proof with `nextAuthoritySetId = 2` (`epoch = 1`) passes `1 > 0` and is recorded normally — confirming only epoch 0 is permanently lost, exactly mirroring how the Derby vault's `rebalancingPeriod == 0` window was the only period where the guard misbehaved.

    function recordEpoch(uint256 authoritySetId, address relayer) external restrict(_hostParams.handler) {
        if (authoritySetId <= _currentEpoch) return;
        _currentEpoch = authoritySetId;
        _epochs[authoritySetId] = relayer;
        emit NewEpoch({authoritySetId: authoritySetId, relayer: relayer});
    }
