### Title
Webhook shop/topic identity not bound to HMAC signature enables cross-tenant webhook forgery - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw HTTP body, while `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from unauthenticated HTTP headers. `Utils::HmacValidator.validate` only proves that the *body* was signed by the app's `client_secret`; it proves nothing about which shop or topic the body belongs to. Since a single `client_secret` signs webhook bodies for every shop that has the app installed, an attacker who controls one tenant (their own dev/test store with the app installed) can capture a legitimate `(body, hmac)` pair and replay it to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain`/`X-Shopify-Topic` header pointing at a different shop, and the gem will accept it as authentic.

### Finding Description
`Request#to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`) is defined as: [1](#0-0) 
which is just `@raw_body`. Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are pulled from headers with no cryptographic binding at all: [2](#0-1) 

`Registry.process` trusts these header-derived values to route and execute the handler, using only the body-only HMAC as its authenticity gate: [3](#0-2) 

`HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) verifies `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)` — for webhook requests this signable string is the raw body only, never the shop or topic: [4](#0-3) 

The identity binding that should hold is:
`(shop acted on by the handler) == (shop that the HMAC-signed content actually originated from)`

Because `shop` and `topic` are excluded from the signed content, this equality is not enforced. All shops that install the same app share the same `client_secret`, so any tenant of the app (including an attacker who installs the app on their own shop, a capability available to any unprivileged internet user through normal app installation) can legitimately obtain valid `(body, hmac)` pairs. That attacker can then submit an HTTP request to the app's webhook endpoint with the genuine body/HMAC but with the `X-Shopify-Shop-Domain` header changed to a victim shop's domain (and/or `X-Shopify-Topic` changed to any topic), and `Registry.process` will accept it as an authentic webhook for the victim shop.

### Impact Explanation
This breaks the tenant isolation the webhook subsystem is expected to provide: the shop identifier the handler code acts on (`WebhookMetadata.shop`) is not the shop that the verified bytes actually came from. Depending on how the host application's webhook handler uses `shop` (e.g., looking up the shop's stored access token/session, updating billing state, processing `app/uninstalled`, GDPR mandatory webhooks, or writing merchant records), this allows a malicious app tenant to inject attacker-controlled webhook events "as" any other shop that has installed the same app — a cross-tenant confused-deputy condition. This matches the Critical "cross-tenant access" impact bucket.

### Likelihood Explanation
Exploitation requires no privileged credentials beyond what any developer/merchant can obtain by simply installing the target app on their own store (a standard, unprivileged install), then replaying a captured legitimate webhook to the endpoint with modified headers. No access token, `client_secret`, or victim credentials are needed — only network access to the app's public webhook endpoint and one genuine `(body, hmac)` pair generated on the attacker's own tenant.

### Recommendation
Bind the routing metadata into the verified signature material, or otherwise cryptographically tie `shop`/`topic` to the verified request instead of trusting them from headers:
- Prefer verifying the shop against server-side state (e.g., confirm the `shop` header matches a shop for which the app currently holds a valid access token/session record, rather than trusting the header value implicitly), and/or
- Where possible, incorporate `shop`/`topic`/`webhook_id` into the value passed to `HmacValidator` (if Shopify webhook signing is extended/able to support this) or add an application-level secondary check requiring that the `shop` header corresponds to an installed, known tenant before dispatching to `handler.handle`.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger a real webhook (e.g., `orders/create`) and capture the raw POST body and the `X-Shopify-Hmac-Sha256` header — both are valid and pass `HmacValidator.validate` since they were genuinely signed by the app's shared `client_secret`.
2. Replay this exact `(raw_body, hmac)` pair to the app's public webhook endpoint, but replace `X-Shopify-Shop-Domain` with `victim.myshopify.com` (optionally also change `X-Shopify-Topic`).
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers (`lib/shopify_api/webhooks/request.rb:45-63`), `Registry.process` calls `Utils::HmacValidator.validate(request)` which passes because it only checks the raw body (`lib/shopify_api/webhooks/registry.rb:190`), and the handler executes with `shop: "victim.myshopify.com"` even though the payload never originated from that shop (`lib/shopify_api/webhooks/registry.rb:198-199`).

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
