## Finding

### Title
Webhook signature only binds the raw body — `shop`/`topic`/`webhook_id` headers are trusted unauthenticated, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's HMAC and then dispatches to the registered handler using `request.shop` and `request.topic`, but the HMAC computation only ever covers the raw request body — never the `shop`, `topic`, or `webhook_id` header values that the handler trusts for tenant identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers, entirely outside the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC against `to_signable_string` (i.e. body-only) and then immediately trusts `request.shop`/`request.topic` to build `WebhookMetadata` and dispatch to the handler: [3](#0-2) 

`HmacValidator.validate` performs a straightforward `OpenSSL.secure_compare` over `compute_signature(verifiable_query.to_signable_string, secret)`, so its guarantee is strictly "this body was HMAC'd with our secret" — it says nothing about which shop or topic the body was meant for: [4](#0-3) 

The identity binding that should hold is: `HMAC-verified bytes == (shop, topic, body)` used by the dispatched handler. In fact only `HMAC-verified bytes == body` holds; `shop` and `topic` are accepted from unauthenticated header bytes and forwarded to `WebhookMetadata` unchanged.

### Impact Explanation
Because Shopify's own webhook signature is computed purely over the JSON body, any body+HMAC pair that a caller can legitimately obtain (e.g., a webhook delivered to their own installed shop, whose body content is attacker-influenced or generic — such as `app/uninstalled`, `shop/redact`, or other structurally simple GDPR/lifecycle payloads) remains a *valid* HMAC for that exact byte sequence regardless of which `shop-domain`/`topic` header accompanies it. An attacker controlling their own shop/app installation can capture such a valid `(body, hmac)` pair and replay it against the same webhook endpoint with a different `x-shopify-shop-domain` header, and `Registry.process` will accept it and hand the handler a `WebhookMetadata` claiming to be for the victim shop. If the host application's handler acts on `data.shop` for lifecycle/GDPR/tenant-scoped state changes (as `WebhookMetadata` is designed to be used), this crosses a tenant boundary using only credentials the attacker legitimately possesses for their own tenant.

### Likelihood Explanation
Requires only that the attacker have their own working relationship with the same app (their own shop, i.e. any real merchant installer), and that some webhook topic exists whose signed body is fixed/predictable/attacker-influenced. No `api_secret_key`, access token, or privileged access is needed. This is a moderate-likelihood path since it depends on finding a topic/body combination useful for the attacker's target action, but the structural weakness (headers unauthenticated) is unconditionally present for every webhook processed by this gem.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable string used for HMAC verification (or otherwise cryptographically bind them, e.g., by validating that the HMAC-covered body itself embeds/echoes the shop and topic), so that `Registry.process` cannot be tricked into associating a validly-signed body with a different shop or topic than the one it was actually signed for.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook delivery for topic `T` with a simple/fixed body `B` (HMAC `H` computed by Shopify over `B` with the app's real `api_secret_key`).
2. Attacker replays a POST to the app's webhook endpoint with headers `x-shopify-shop-domain: victim.myshopify.com`, `x-shopify-topic: T`, `x-shopify-hmac-sha256: H`, and body `B`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` builds successfully; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `B` and matches `H` — validation succeeds.
4. `handler.handle(data: WebhookMetadata.new(topic: T, shop: "victim.myshopify.com", body: parsed(B), ...))` is invoked, and the host application processes the webhook as if it legitimately originated from `victim.myshopify.com`.

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
