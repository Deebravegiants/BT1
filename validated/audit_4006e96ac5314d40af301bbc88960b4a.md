### Title
Same-asset batched withdrawals are matched only by `assetId`, causing a completion status/tx-hash to be misreported for the wrong withdrawal - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves the completion status of a specific withdrawal by matching entries returned from the POA bridge indexer using only the `assetId` (`near_token_id`), not the withdrawal's index, destination address, or amount.

### Finding Description
`findMatchingWithdrawal` in [1](#0-0)  is invoked from `describeWithdrawal`, which is the function the SDK uses to report per-withdrawal completion status/tx hash back to callers of `sdk.waitForWithdrawalCompletion` (supporting arrays of `WithdrawalParams`, see [2](#0-1) ). The matching function itself is documented as limited: it explicitly matches "by assetId, not by index" and the code comment states "This means multiple withdrawals of the same token in a single transaction are not supported," as seen in the analogous `internal-utils` implementation [3](#0-2) , and mirrored in the `poa-bridge.ts` matching logic used by `describeWithdrawal`.

Concretely: when an integrator batches two or more withdrawals of the same `assetId` (e.g., withdrawing the same token to two different destination addresses) in one intent transaction, `describeWithdrawal` for withdrawal-at-index-0 and withdrawal-at-index-1 both call `findMatchingWithdrawal` with the same `assetId` criteria. The function returns the *first* withdrawal in the (unsorted) API response array that matches the assetId, regardless of which index/destination/amount the caller actually asked about. This breaks the equality "status/tx hash reported == the on-chain outcome for *this* withdrawal": if withdrawal-0 (say, to attacker-controlled address A) completes on-chain while withdrawal-1 (to address B) is still pending or has a different transfer tx hash, `describeWithdrawal` can report the same `COMPLETED` status and `transfer_tx_hash` for both withdrawals.

### Impact Explanation
An integrator that relies on `sdk.waitForWithdrawalCompletion`/`processWithdrawal` for batched same-asset withdrawals could be told that withdrawal-to-address-B is `completed` with a transfer hash that actually corresponds to withdrawal-to-address-A. This is a status/hash misreport that can cause an integrator to credit/confirm a withdrawal that never actually reached its intended destination — matching the "status or hash misreport making an integrator credit or refund twice" impact category (High). It could also cause the reverse: a completed withdrawal is left permanently "pending" because the matched entry always resolves to the other batched item, leading to funds appearing stuck from the integrator's perspective (though the actual on-chain transfer succeeded to the correct chain, the destination/reporting association is wrong).

### Likelihood Explanation
This requires no malicious relayer or bridge action — it is triggered purely by an integrator (a permitted, unprivileged, ordinary user of the public SDK API) submitting a batch withdrawal (`WithdrawalParams[]`) with two or more entries sharing the same `assetId` via the POA bridge route. The code path and the array-based `waitForWithdrawalCompletion`/`processWithdrawal` API explicitly support this usage, and the bug is self-acknowledged in a code comment, indicating it is a known, reachable gap rather than a theoretical one.

### Recommendation
Extend `findMatchingWithdrawal` (and the analogous `internal-utils` `waitForWithdrawalCompletion`) to disambiguate between multiple same-asset withdrawals within a batch — e.g., by matching on `amount` and `address` (destination) in addition to `assetId`, or by requiring/using an index-stable ordering contract from the bridge indexer API. Until fixed, the SDK should explicitly reject or warn when multiple `WithdrawalParams` entries share the same `assetId` in a single batched POA-bridge withdrawal, to prevent silent misattribution of completion status.

### Proof of Concept
1. Caller submits `sdk.processWithdrawal({ withdrawalParams: [ {assetId:"nep141:x.near", amount:100, destinationAddress:"A"}, {assetId:"nep141:x.near", amount:100, destinationAddress:"B"} ] })` using the POA bridge route.
2. Both withdrawals are included in one intent transaction, producing one `near_tx_hash`.
3. `waitForWithdrawalCompletion` calls `describeWithdrawal` for each entry with `index: 0` and `index: 1` respectively, both with `assetId: "nep141:x.near"`.
4. The POA bridge indexer returns both withdrawal records under the same `near_token_id`. `findMatchingWithdrawal(withdrawals, "nep141:x.near")` returns `.find(...)`, i.e., the *first* entry in the array, for **both** index-0 and index-1 lookups.
5. If only the withdrawal to "A" has settled (`COMPLETED`, `transfer_tx_hash: "0xA"`) while the withdrawal to "B" is still `PENDING`, `describeWithdrawal` for the index-1 (destined for "B") request returns `{status: "completed", txHash: "0xA"}` — a tx hash belonging to a transfer to a different address — instead of correctly reporting "pending" for B.

**Uncertainty:** I was not able to load `sdk.createWithdrawalCompletionPromises.test.ts` or the `createWithdrawalCompletionPromises` implementation in `sdk.ts` before running out of tool calls, so I could not fully confirm whether an index-aware disambiguation guard exists elsewhere in the orchestration layer that might mitigate this specific batching scenario (e.g., rejecting same-asset batches or sorting matches by amount as the code comment suggests as a future fix). This should be verified with a Devin session that can read `packages/intents-sdk/src/sdk.ts` (`createWithdrawalCompletionPromises`) in full and the associated test file to determine if any such safeguard is already present.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}
