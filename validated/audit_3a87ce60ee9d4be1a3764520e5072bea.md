### Title
Webhook shop-domain and topic headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `HmacValidator.validate` authenticates nothing but the body bytes. The `shop-domain`, `topic`, `webhook-id`, and `api-version` headers — which `Registry.process` passes straight into the app's handler as trusted, tenant-identifying data — are completely outside the HMAC's coverage. This is the "field acted on but not covered by the HMAC" bug class from the report, applied to the shop identity binding instead of a vote/chain-id binding.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` verifies authenticity with: [1](#0-0) 

The HMAC check calls `Utils::HmacValidator.validate(request)`, which signs/verifies `request.to_signable_string`: [2](#0-1) 

But `Request#to_signable_string` is defined to be just the raw body, not the headers: [3](#0-2) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from unauthenticated headers and forwarded verbatim to the app-supplied handler as trusted tenant/routing data: [4](#0-3) [5](#0-4) 

Because the HMAC only binds the body bytes to the app's `api_secret_key`, an attacker who is a legitimate merchant of the app (or who otherwise obtains one genuine, validly-signed webhook delivery for their own shop) can replay that exact body+HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header value for a different, victim shop. `HmacValidator.validate` still returns `true` because the signature only covers `@raw_body`, which is unchanged. `Registry.process` then hands `data.shop` (the attacker-controlled victim shop id) to the app's handler as if it were an authentic message about that tenant. Documentation explicitly tells integrators to use `data.shop` as the tenant key for downstream processing (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), so this is the intended, documented use of the field — the equality `shop-authenticated-by-HMAC == shop-header-trusted-by-handler` does not hold.

### Impact Explanation
This breaks the tenant binding of a message: `shop` value verified (none) vs. `shop` value consumed by the handler (attacker-controlled header). An app that keys any tenant-scoped side effect (order/product sync, database row lookups keyed by shop, job dispatch) off `data.shop` can be made to apply another merchant's or attacker-chosen shop's identity to an actually-attacker-supplied payload, i.e. cross-tenant data confusion/injection driven entirely by an unprivileged internet user's own legitimate app installation. This matches the report's "Critical - cross-tenant access" impact category, since the trust boundary between tenants is defined by this gem's webhook processing API and is crossed without needing any of the app's own credentials.

### Likelihood Explanation
Low-to-Medium likelihood: exploitation requires the attacker to actually possess one genuine (body, HMAC) pair, which they can obtain simply by installing the app on their own store (any attacker can become a merchant of the target app) and receiving one webhook for their own shop. No secret key, token, or privileged access is needed beyond normal app installation available to any internet user, and the header substitution + replay is trivial once a genuine pair is captured. The severity of impact depends on whether the app's handler trusts `data.shop` for tenant lookups (a documented, encouraged pattern), which is common.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, and ideally `topic`/`webhook-id`) in the HMAC-verified payload, or cryptographically bind them another way (e.g., require the app to independently confirm the shop domain against its own session store before trusting `data.shop`, or extend `to_signable_string` to canonicalize and include these headers so tampering invalidates the signature). At minimum, update documentation to explicitly warn that `data.shop`, `data.topic`, and `data.webhook_id` are unauthenticated header values not covered by the HMAC and must not be trusted for tenant-scoped authorization decisions without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`, triggers a webhook (e.g. `orders/create`), and captures the raw POST from Shopify, including the genuine `X-Shopify-Hmac-Sha256` header (computed by Shopify using the app's real `api_secret_key`) and the raw body.
2. Attacker replays this exact HTTP request to the app's webhook endpoint, keeping `raw_body` and `X-Shopify-Hmac-Sha256` unchanged, but rewrites `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the tampered headers; `HmacValidator.validate` recomputes HMAC over `@raw_body` only (per `to_signable_string`) and it still matches, so validation passes.
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: attacker's payload, ...)`, causing the app to process attacker-supplied data under the victim shop's identity.
