## Finding: Webhook `shop` identity not covered by HMAC signature - allows cross-tenant webhook forgery

### Title
Webhook Shop-Domain Header Is Not Covered by HMAC Validation, Enabling Cross-Tenant Webhook Replay - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body, while the `shop` (tenant identity) is read from an entirely separate, unsigned HTTP header. `Registry.process` validates only the body HMAC and then hands `request.shop` straight to the host application's webhook handler as the authoritative tenant identifier. Because the app's `client_secret` is shared across every shop that installs the app, any merchant who installs the app on their own store can capture a legitimately-signed webhook (body + valid HMAC) and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header swapped to a victim shop, producing a request that passes HMAC validation but is misattributed to another tenant.

### Finding Description
The identity binding that should hold is:
`shop asserted to the handler == shop whose secret produced the verified HMAC`

In this gem, that equality is broken:

- `Request#hmac` decodes the signature strictly from the `hmac-sha256` header, and `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) 

- `Request#shop` is read from a separate, unauthenticated header (`shop-domain` / `x-shopify-shop-domain`) that plays no part in the signable string: [3](#0-2) 

- `Registry.process` validates the HMAC (over the body only) and then trusts `request.shop` as the tenant identity passed to the handler: [4](#0-3) 

Since every shop that installs a given app shares the same `client_secret`, the HMAC only proves "this body was signed with this app's secret" — it says nothing about which shop the body actually pertains to. A merchant who installs the app on their own store (an unprivileged, ordinary action) receives real webhooks from Shopify with a valid `hmac-sha256` for bodies they fully control (e.g., by creating orders/products with attacker-chosen field values in their own store). They can then replay that exact body+HMAC pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a different, victim shop that also uses the app. `HmacValidator.validate` still succeeds because it never looks at the shop header, and `Registry.process` forwards `WebhookMetadata.new(shop: request.shop, body: request.parsed_body, ...)` to the handler as if the payload genuinely originated from the victim shop.

### Impact Explanation
This is a cross-tenant identity confusion: an attacker-controlled body, generated and signed under the attacker's own tenant, can be relabeled and delivered to any app-integrated host application as if it belonged to another tenant. Host applications built on this gem's webhook API rely on `WebhookMetadata#shop` to select which tenant's records to update/delete/create in response to the webhook — this is the gem's documented API contract. Forged cross-tenant webhooks can trigger unauthorized data mutation, false state transitions (e.g., fake `orders/create`/`app/uninstalled` handling), or record/tenant confusion in the host application's persistence layer, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Any user can install the target app on a store they control (no special privilege, access token, or `client_secret` knowledge required), capture the legitimate webhook Shopify sends them, and replay it with a modified `shop` header to the app's public webhook receiver endpoint. No secrets need to be forged, guessed, or leaked — only the unsigned header needs to be changed. This requires nothing beyond ordinary internet access and normal app-installation privileges.

### Recommendation
Bind the shop identity into the verified signature space, for example:
- Verify the HMAC using the specific shop's known/expected secret when multiple shops or secrets are relevant, or
- Additionally validate the `shop` header against an independently-obtained record (e.g. an active, previously-established `Session` for that shop before honoring the webhook), so a replayed body cannot be attributed to a shop that never actually sent it.
- At minimum, document/require that host apps must not treat `WebhookMetadata#shop` as a trust anchor without confirming an existing app installation/session for that shop, and provide gem-level support for that check.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` (ordinary, unprivileged action) and registers for a webhook topic the app subscribes to (e.g. `orders/create`).
2. Attacker creates an order/product in their own store with attacker-chosen field values, triggering Shopify to POST a webhook to the app's callback URL with:
   - `X-Shopify-Hmac-Sha256: <valid HMAC over body>`
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - Body: attacker-controlled JSON
3. Attacker captures this request and replays it to the same webhook endpoint, changing only `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` (a shop known to have the app installed).
4. `Utils::HmacValidator.validate(request)` succeeds because it only checks the body against the HMAC [5](#0-4) ; `Registry.process` invokes the handler with `shop: "victim-shop.myshopify.com"` and the attacker's forged body [6](#0-5) , causing the host app to process attacker-controlled data as if it belonged to the victim tenant.
