### Title
Webhook `shop` and `topic` are trusted without being covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw body, then unconditionally trusts the `shop`, `topic`, `webhook_id`, and `api_version` values taken from HTTP headers to build the `WebhookMetadata` handed to the app's handler. Those header values are never included in the HMAC-signed content, so they are not bound to the authenticated payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are read directly from attacker-controllable HTTP headers and are not part of the signed string: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, then immediately trusts `request.shop` (and `request.topic`) to build `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` only compares the HMAC against `to_signable_string`, i.e. the raw body — it has no knowledge of `shop`: [4](#0-3) 

Because Shopify's webhook HMAC covers only the JSON body (this is by design, matching Shopify's real signing scheme), the `shop`-domain header is orthogonal to the signature. The binding that should hold is:

`shop header used by the handler == shop that legitimately owns/produced the signed body`

but nothing in this gem enforces that equality. An unprivileged internet user who owns or controls any store (even a free development store) can trigger genuine Shopify webhooks for their own shop, capturing a validly-signed `(raw_body, hmac)` pair. Because the HMAC only authenticates the body bytes and not the shop identity, that same signed body can be replayed to the victim application's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to name an arbitrary target shop. `HmacValidator.validate` still returns `true` (the body and HMAC are unchanged and valid), and `Registry.process` will dispatch the handler believing the data originated from the spoofed `shop`.

### Impact Explanation
Any downstream logic in the host application that uses `WebhookMetadata#shop` as a tenant key (e.g., to look up which merchant's session/access token to act on, or to attribute/store data against a shop record) can be tricked into processing attacker-supplied data under an arbitrary shop identity. This is a cross-tenant confusion: the gem provides no guarantee that the `shop` value it hands to application code is authentic, only that the request contains *some* body that was validly signed for *some* topic/shop by the app's secret. This satisfies the "cross-tenant access" impact class since the shop identifier consumed by the handler is not bound to the authenticated content.

### Likelihood Explanation
Exploitation requires only that the attacker be able to generate one legitimately signed webhook (trivial: install the target app on any shop they control, including a free development store, and trigger a webhook event) and then send a forged HTTP request with the captured `raw_body`/`hmac-sha256` header pair but a different `shop-domain` header to the app's public webhook endpoint. No knowledge of `api_secret_key` or any privileged credential is required — only knowledge of the gem's documented webhook processing behavior (HMAC over body only).

### Recommendation
Include `shop` (and ideally `topic`) as part of the value the HMAC is computed over, or otherwise cryptographically bind the header-derived `shop` to the signed payload before trusting it. At minimum, document clearly that `shop` is unauthenticated header data and require host applications to cross-check it against an out-of-band trusted source (e.g., matching against a known/installed shop record) before using it as a tenant key, and/or add a built-in check in `Registry.process` that ensures the `shop` header corresponds to a shop with a currently valid session/installation state managed by this library.

### Proof of Concept
1. Install/trigger any real webhook (e.g., `orders/create`) for a shop the attacker controls, capturing the raw request body and the legitimate `X-Shopify-Hmac-Sha256` header value computed by Shopify using the target app's shared secret.
2. Replay this exact `(raw_body, hmac header)` pair to the victim application's public webhook endpoint, but override `X-Shopify-Shop-Domain` to the victim's shop domain (and optionally the topic header, if the target handler is registered for multiple topics).
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers, and `Registry.process` -> `HmacValidator.validate` succeeds because it only checks `raw_body` against the HMAC: [3](#0-2) 
4. The registered handler is invoked with `WebhookMetadata.shop` set to the attacker-chosen victim shop domain, despite the payload never having been produced by or for that shop.
