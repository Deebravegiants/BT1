### Title
Stale delegate grant resurrects on NFT round-trip, restoring spending authority without re-authorization - ([File: contracts/controller/src/storage/account.rs])

### Summary
The controller stores delegate grants as a single `DelegateGrant { granted_by, delegates }` record keyed by `ControllerKey::Delegates(account_id)`. Read-path filtering (`get_delegates` keeps only grants where `granted_by == current_owner`) makes a previous owner's grant *invisible* while someone else owns the NFT, but the record is **not deleted**. It is purged only if the *new* owner explicitly calls `remove_delegate` (or overwrites it via `add_delegate`). If the intermediate owner never touches delegates and the NFT returns to the original grantor, `granted_by == owner` is true again and the orphaned grant silently regains full spending authority — borrow and withdraw to arbitrary recipients — with no fresh authorization. This mirrors the report's bug class: an orphaned authorization record surviving a state transition and bypassing the approval requirement that should have been re-established.

### Finding Description
In `contracts/controller/src/storage/account.rs:176-181`, `get_delegates` returns `Vec::new` for any owner other than `granted_by`, but leaves the entry in persistent storage. `remove_delegate` (`storage/account.rs:226-247`) is the only path that deletes a foreign-owned grant (`grant.granted_by != *owner` → `persistent().remove`), and only the current NFT owner can invoke it through `require_account_owner` (`account.rs:143-148`). The unit test `remove_delegate_purges_stale_grant_preventing_resurrection` (`contracts/controller/tests/storage/account.rs:180-225`) explicitly acknowledges resurrection as the failure mode and shows the purge occurs only when the new owner calls `remove_delegate`. Nothing else cleans the record on transfer: the position NFT (`contracts/position-nft/src/contract.rs`) has no controller hook on transfer, and `is_owner_or_delegate` (`account.rs:115-127`) re-arms any stored grant whose `granted_by` matches the current owner once the delegate is an active position manager.

Attack path (all unprivileged entrypoints): `position_nft.transfer` Alice→Bob, Bob does nothing with delegates, `position_nft.transfer` Bob→Alice (sale round-trip, buyback, or Bob cooperating), then the delegate calls `controller.withdraw` / `controller.borrow` with `to = <delegate-controlled address>` on `account_id`.

### Impact Explanation
Theft of user funds. Delegates can `borrow` and `withdraw` to arbitrary recipients (`docs`/`abi.md`: "Delegates may borrow or withdraw to arbitrary recipients"), so a resurrected grant lets the manager drain Alice's collateral or draw debt against it, up to the solvency limits of the account. Alice reasonably believes transferring the position revoked her grant — the read path returns an empty list for every other owner and the codebase's own test frames non-purged grants as a resurrection hazard — yet her stale authorization reactivates the moment she reacquires the account, without any `add_delegate` call or signature from her in the new ownership epoch.

### Likelihood Explanation
Medium. Requires (1) Alice previously delegating to a position manager that remains active, (2) an NFT transfer chain that returns the token to Alice while no intermediate owner ever calls `remove_delegate` or `add_delegate` (a passive holder or direct resale triggers nothing), and (3) the delegate being able to act — either a malicious/compromised shared manager contract, or any already-active public manager the attacker can route calls through. All steps use unprivileged paths (`transfer`, `borrow`, `withdraw`); no privileged or timing-sensitive action is needed. The economic precondition (a valuable account changing hands twice) limits frequency but not feasibility.

### Recommendation
Delete the `Delegates(account_id)` entry eagerly on ownership change rather than relying on the new owner to purge it. Since the NFT cannot callback into the controller on transfer, do it lazily but deterministically: on every account load that resolves the owner (`storage::get_account` / `account_owner`), or at minimum inside `require_owner_or_delegate` and `require_account_owner`, compare `DelegateGrant.granted_by` to the resolved owner and `persistent().remove` the key when they differ — the same purge `remove_delegate` already performs, applied on read instead of only on an explicit revoke. Alternatively, stamp grants with an ownership epoch/token-generation counter so a grant can never match a later ownership epoch even for the same address.

### Proof of Concept
The existing test `remove_delegate_purges_stale_grant_preventing_resurrection` (`contracts/controller/tests/storage/account.rs:180-225`) demonstrates the purge path; the vulnerability is the complementary case where `remove_delegate` is never called:

```rust
// Alice owns account_id and delegates to active manager M.
add_delegate(&env, account_id, &alice, &manager);          // grant stamped by alice

// Alice sells/transfers the position NFT to Bob.
nft.transfer(&alice, &bob, &token_id);
// Bob never calls remove_delegate or add_delegate; the
// DelegateGrant { granted_by: alice, delegates: [M] } record
// remains in persistent storage, merely filtered out by get_delegates.

// Bob transfers the NFT back to Alice (resale / buyback).
nft.transfer(&bob, &alice, &token_id);

// granted_by == owner again: the orphaned grant is live.
assert!(is_owner_or_delegate(&env, account_id, &manager, &alice));
// M now calls controller.withdraw(account_id, ..., to = M_address)
// or controller.borrow(...) and drains Alice's position,
// despite Alice never re-authorizing the delegate.
```

Key uncertainty I could not fully verify within the iteration limit: whether any other account-loading path (e.g., `adopt_account` bookkeeping or liquidation `Credit` account adoption) incidentally clears `Delegates` on transfer — the code and docs show none, and `remove_account_entry` is the only other site that removes the key, reached only on account deletion.
