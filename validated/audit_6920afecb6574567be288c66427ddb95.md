### Title
`Oauth.begin_auth` builds the OAuth authorization redirect from an unsanitized `shop` host, unlike every other grant-type helper in the gem - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` takes the caller-supplied `shop:` string and feeds it straight into `auth_base_uri(shop)` to build the Shopify authorization redirect URL, without ever validating that `shop` is a trusted `*.myshopify.com`/`myshopify.io`/etc. domain. Every sibling credential-exchange helper in this same gem (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`) explicitly calls `Utils::ShopValidator.sanitize!(shop)` before using the shop value to build the host that will receive the app's `client_id`/`client_secret`. `Oauth.begin_auth` (and its counterpart `validate_auth_callback`, which reuses the unsanitized value) is the one path in the gem that skips this check.

### Finding Description
`Utils::ShopValidator` exists specifically to enforce the invariant `validated_shop_host == host_that_receives_client_secret`, restricting `shop` to `TRUSTED_SHOPIFY_DOMAINS` [1](#0-0) . This validator is consistently applied before constructing an `Auth::Session`/`Clients::HttpClient` in:
- `ClientCredentials.client_credentials` [2](#0-1) 
- `RefreshToken.refresh_access_token` [3](#0-2) 
- `TokenExchange.migrate_to_expiring_token` [4](#0-3) 

In contrast, `Oauth.begin_auth` takes `shop:` directly and passes it unchecked to `auth_base_uri(shop)`, which builds `"https://#{shop}/admin"` and appends the authorize path with the app's `client_id` and a fresh `state` nonce: [5](#0-4)  and [6](#0-5) . There is no HMAC to check at this stage (that only exists later on the callback), so this is the one point where the gem itself is responsible for the shop/host binding, and it is the one place that binding is missing.

The gem's own documentation shows this `shop` value being taken straight from a request header (`shop = request.headers["Shop"]`) and passed into `begin_auth` [7](#0-6) , i.e. this is the gem's own recommended usage pattern, not a case of the host app ignoring documented API.

`validate_auth_callback` reuses `auth_query.shop` (a value covered by the callback HMAC signed by Shopify) to build the session and to POST the app's `client_id`/`client_secret` to `https://#{auth_query.shop}/admin/oauth/access_token` [8](#0-7) , again without ever routing it through `ShopValidator`, unlike every other credential-exchange helper in the gem.

### Impact Explanation
`begin_auth` is the entry point of the entire authorization-code OAuth flow and is called before any signature exists to bind `shop` to Shopify. If the host application follows the gem's own documented pattern of sourcing `shop` from user-controllable input (query/header) and forwarding it unchanged into `begin_auth` — exactly as shown in `docs/usage/oauth.md` — the gem itself will redirect the merchant's browser, with the app's `client_id` and a fresh authorization `state` nonce, to an arbitrary attacker-chosen host of the form `https://{attacker-controlled-shop}/admin/oauth/authorize?...`. This is a forced-OAuth-completion / session-fixation primitive: the gem sets the anti-CSRF `state` cookie for a flow whose target authorization host was never validated as a genuine Shopify domain, undermining the security purpose of `ShopValidator`, which the gem's own maintainers built and applied to the exact three sibling flows above but omitted here.

### Likelihood Explanation
High for apps that follow the documented pattern (`docs/usage/oauth.md`) of deriving `shop` from request input and calling `begin_auth` directly, since the gem performs no internal sanitation at all in this code path — a stark asymmetry compared to the other three grant flows in the same file tree that all call `Utils::ShopValidator.sanitize!` first.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) at the top of `Oauth.begin_auth` before constructing `auth_base_uri(shop)`, mirroring `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and `TokenExchange.migrate_to_expiring_token`. Apply the same validation to `auth_query.shop` inside `validate_auth_callback` before it is used to build `null_session`/`Clients::HttpClient` and before it is returned as the session's `shop`.

### Proof of Concept
1. Host app follows the gem's documented pattern: `shop = request.headers["Shop"]` (unsanitized) and calls `ShopifyAPI::Auth::Oauth.begin_auth(shop: shop, redirect_path: "/auth/callback")`.
2. Attacker sends: `GET /login` with header `Shop: evil-host.attacker.com`.
3. `begin_auth` computes `auth_base_uri("evil-host.attacker.com")` → `"https://evil-host.attacker.com/admin"` [6](#0-5) , and returns `auth_route = "https://evil-host.attacker.com/admin/oauth/authorize?client_id=...&state=...&redirect_uri=..."` together with a `state` cookie [9](#0-8) .
4. The application redirects the victim's browser there, leaking the app's `client_id` and setting up an OAuth flow whose authorization host was never checked against `Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS`, unlike the equivalent checks performed for client-credentials, refresh-token, and token-exchange migration flows in the same gem.

        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
            access_token_response: Oauth::AccessTokenResponse.from_hash(session_params))

        sig { params(shop: String).returns(String) }
        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end

  def login
    shop = request.headers["Shop"]

    # Builds the authorization URL route to redirect the user to
    auth_response = ShopifyAPI::Auth::Oauth.begin_auth(shop: domain, redirect_path: "/auth/callback")

    # Store the authorization cookie
    cookies[auth_response[:cookie].name] = {
      expires: auth_response[:cookie].expires,
      secure: true,
      http_only: true,
      value: auth_response[:cookie].value
    }

    # Redirect the user to "auth_response[:auth_route]" to allow user to grant the app permission
    # This will lead the user to the Shopify Authorization page
    head 307
    response.set_header("Location", auth_response[:auth_route])
  end
