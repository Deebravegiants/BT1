### Title
Webhook tenant attribution (`shop`) is not covered by the HMAC signature, allowing cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by checking `Utils::HmacValidator.validate(request)`, then immediately trusts `request.shop` (read from the `X-Shopify-Shop-Domain` header) as the tenant identity for the event, without that header ever being part of the HMAC-signed material.

### Finding Description
`Utils::HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the received HMAC. [1](#0-0) 
For webhooks, the signable string is the raw request body only — confirmed by the test fixture, which computes the HMAC over `"{}"` (the body) while the shop domain, topic, and webhook id are supplied as separate, unsigned headers: [2](#0-1) 

`Registry.process` validates that HMAC and then builds `WebhookMetadata` using `request.shop`, `request.topic`, and `request.webhook_id` — all values that come from those unsigned headers, not from the signed body: [3](#0-2) 

The equality that should hold is:
`shop_bound_by_signature == shop_used_for_tenant_attribution`

What actually holds is:
`hmac_valid == HMAC(secret, raw_body)` while `shop_used_for_tenant_attribution == unauthenticated_header("X-Shopify-Shop-Domain")`

Because the header is never mixed into the signed material, any request whose **body** carries a valid HMAC (i.e., a body that was genuinely signed and delivered to the app for *some* shop, e.g. the attacker's own installed shop) can be replayed with the `X-Shopify-Shop-Domain` header rewritten to a different, victim shop domain that also has the app installed. `HmacValidator.validate` still returns `true` because it only re-derives the signature from the untouched body bytes; `Registry.process` then dispatches the handler with `shop: request.shop` pointing at the victim tenant.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook consumers: an attacker who has legitimately received one authentic (body, HMAC) pair from Shopify (trivial — they just install the app on their own shop and wait for any webhook) can cause the host application to process that payload as if it originated from an arbitrary other shop of their choosing, as long as that shop also has the app installed. Any handler logic keyed off `WebhookMetadata#shop` (e.g., syncing order/customer data, revoking access on `app/uninstalled`, refreshing per-shop caches) will act on the wrong tenant with attacker-controlled body content — a cross-tenant data/action injection, matching the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
No secrets, tokens, or privileged access are required beyond what any developer/merchant naturally has by installing the app once (a normal, unprivileged step for any public or custom app). The only requirement is that the header this gem trusts for attribution (`X-Shopify-Shop-Domain`) is not bound into the signature it verifies — a static property of `Webhooks::Registry.process` and `Utils::HmacValidator`, always reachable whenever webhooks are processed through this gem.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-covered signable string for webhook validation, or otherwise cryptographically bind the header values Shopify sends (e.g., derive/verify `shop` from a signed claim rather than from `X-Shopify-Shop-Domain` alone) before using it for tenant attribution in `Webhooks::Registry.process`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and lets Shopify deliver any webhook (e.g. `orders/create`) to the app's endpoint — this arrives with a genuine body `B` and a valid `X-Shopify-Hmac-Sha256` header computed as `HMAC(secret, B)`, alongside `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker replays the identical HTTP request to the app's webhook endpoint, changing only `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` (also an app installer), leaving body `B` and the HMAC header untouched.
3. `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)`, matches the untouched header, and returns `true`. [4](#0-3) 
4. `Registry.process` proceeds and invokes the registered handler with `WebhookMetadata` reporting `shop: "victim-shop.myshopify.com"` and the attacker's body `B`, even though Shopify never sent this event for that shop. [3](#0-2)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
