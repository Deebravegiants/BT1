### Title
Emporium `EmporiumStack` signature does not bind `circomData.stealthAddressStructure` (or `relay`/`feeToken`), letting a front-runner redirect a signed wallet-owner's asset movement to their own shielded UTXO - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
The EIP-712 hash verified in `verifyWallet` only commits to `emporiumMessage`, the hashed `ops`, `maxFee` and `deadline`; it never covers `circomData.stealthAddressStructure`, `erc20TokenAddresses`, `feeStructure`/`relay`, or `rootHashHinkal`. Because `runAction` turns any positive Emporium-contract balance change produced by executing the signed `ops` into a new shielded UTXO addressed to whatever `circomData.stealthAddressStructure` the *caller* of `Hinkal.transact` supplies, an attacker who observes a signed-but-unconsumed `EmporiumStack` can front-run its intended submission with their own `circomData`/proof and steal the resulting output.

### Finding Description
Broken equality: "(assets leaving/entering via the signed `ops`, their eventual destination UTXO) == what `stack.signerAddress` authorised via EIP-712" is violated, because the destination is not part of the signed payload.

- `verifyWallet` computes the signed hash from only `circomData.emporiumMessage`, `_hashEmporiumOps(stack.ops)`, `stack.maxFee`, `stack.deadline`: [1](#0-0) 
- Replay protection is a single global flag keyed only by `circomData.emporiumMessage`, set before any content-specific validation, and it is silent about which `circomData` was allowed to consume the message: [2](#0-1) 
- `runAction` executes the signed `ops` (which can invoke the owner's `IHinkalWallet` via `callHinkalWallet`), measures the Emporium contract's own balance delta, and converts any positive delta into a UTXO addressed to `circomData.stealthAddressStructure` supplied entirely by the caller, not the signer: [3](#0-2) [4](#0-3) 
- Stealth addresses require only the recipient's public key material to construct (`H0x/H0y/H1x/H1y/stealthAddress`), and these fields are simply public inputs formed by the caller-controlled `circomData`, not tied to `stack.signerAddress` in any way: [5](#0-4) [6](#0-5) 

Exploit flow: The wallet owner (or their designated relay) signs an `EmporiumStack` intended to run `ops` that pull the owner's externally-held assets (e.g., via `invokeWallet` calls to the owner's `HinkalWallet`) into the Emporium contract, expecting the resulting balance increase to become a shielded UTXO for themselves. An attacker who sees this signed stack before it is consumed (e.g. via mempool/relay-network observation) submits their own `Hinkal.transact` call reusing the identical `(v, r, s, ops, maxFee, deadline, emporiumMessage)`, but with a `circomData` whose `stealthAddressStructure` encodes the attacker's own public key, and their own locally-generated valid proof (nothing in `formInputEmporiumMin`/`formInputNormal` requires the caller to be the signer). If the attacker's transaction lands first, `verifyWallet` accepts the (still valid) signature, marks `usedMessages[emporiumMessage] = true`, runs the same `ops` against the owner's wallet, and mints the resulting UTXO to the attacker's stealth address. The legitimate submission subsequently reverts with `UsedMessage()`.

Existing guards fail to prevent this: `performHinkalChecks`/`dimensionsCheck`/`checkOnchainCreation`, `verifyProof`, and the `Hinkal.transact` balance/slippage equalities only check internal self-consistency of whatever `circomData` is submitted — none of them constrain `stealthAddressStructure` (or `relay`/`feeToken`) to match anything the signer of the `EmporiumStack` committed to. `relayerIsValid` does block an unprivileged attacker from redirecting protocol/relay fees via `circomData.relay` (it must be `address(0)` or a whitelisted address equal to `tx.origin`), so the fee-recipient leg of this question does not hold for an unprivileged attacker — but the UTXO-destination leg does, since nothing gates `stealthAddressStructure`.

### Impact Explanation
An unprivileged attacker can permanently divert to themselves the shielded value produced by executing a wallet owner's explicitly signed `EmporiumStack` operations (e.g., DeFi position unwinds, transfers routed back into the Emporium contract) — this is "executing calls or moving assets a wallet owner ... never authorised," matching the High severity category. The action is a one-shot theft per intercepted signed stack (the global `usedMessages` flag prevents reuse after either party consumes it), but it is repeatable across every signed `EmporiumStack` the attacker can observe before it is mined.

### Likelihood Explanation
Preconditions: (1) a wallet owner has produced (and is about to submit, or has handed to a relay) a signed `EmporiumStack` whose `ops` cause a positive balance change to land in the Emporium contract; (2) the attacker observes this signed payload before the legitimate transaction is confirmed (mempool visibility or relay-network leakage) and wins the race to be mined first. Both `EmporiumStack` fields and a full transact call (including a locally generated valid proof for the attacker's own circumData) are entirely within the stated attacker capabilities — no privileged role, no other user's keys, and no compromise of dependencies is required. This is a standard front-running/signature-scope gap, feasible for any chain with a public mempool or leaky relay path.

### Recommendation
Include `circomData.stealthAddressStructure`, `circomData.erc20TokenAddresses`, and ideally `circomData.relay`/`feeStructure.feeToken` in the EIP-712 typed hash signed by the wallet owner (extend `EMPORIUM_SIGNATURE_TYPEHASH` and the corresponding `abi.encode` in `verifyWallet`), so that a signed `EmporiumStack` can only be executed with the exact `circomData` context the signer authorised, closing the front-running window entirely.

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable`, a mock `IHinkalWallet`, and wire up `Hinkal`/`HinkalHelper` with a minimal mock verifier that accepts any proof matching the computed public inputs (bypass real snark generation, but keep `formInputForCircom`/`formBasicInput` logic intact to preserve realism).
2. Have "owner" sign an `EmporiumStack` with `ops = [invokeWallet call that transfers ERC20 X from owner's wallet into the Emporium contract]`, `maxFee`, `deadline = far future`, `emporiumMessage = M`.
3. Craft `circomDataOwner` with `stealthAddressStructure = ownerStealthAddr` and a valid mock proof; assert this WOULD create `UTXO(amount, tokenX, ownerStealthAddr)` if submitted.
4. Instead, as "attacker" (never given owner's keys), craft `circomDataAttacker` reusing the same `(v,r,s, ops, maxFee, deadline, emporiumMessage=M)` but with `stealthAddressStructure = attackerStealthAddr`, and submit it first via `Hinkal.transact`.
5. Assert: (a) the call succeeds and emits a UTXO/commitment tied to `attackerStealthAddr`, not `ownerStealthAddr`; (b) `owner`'s wallet balance decreased by the `ops`-transferred amount; (c) a subsequent submission of `circomDataOwner` with the same `emporiumMessage` reverts with `UsedMessage()`. This demonstrates `(assets leaving the wallet via ops, destination UTXO owner)` diverges from what the owner's EIP-712 signature authorised.
