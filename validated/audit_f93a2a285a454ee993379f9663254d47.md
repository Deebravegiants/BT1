### Title
Duplicated, independently-maintained `FunctionCall` access-key permission enforcement between transactions and `DelegateAction`s risks silent security-check divergence - ([File: runtime/runtime/src/actions.rs])

### Summary
The report describes a class of bug where an invariant (a permission/restriction list) is enforced in one place but must be manually kept in sync with a separate, independent enforcement point elsewhere in the system; because the sync is implicit and not structurally guaranteed, the two can drift and produce a fatal inconsistency. Nearcore has this exact pattern in access-key `FunctionCall` permission enforcement: the same security invariant ("this key may only call one specific method, on one specific receiver, with zero deposit") is implemented twice, independently, in two different files.

### Finding Description
The canonical, shared implementation of the `FunctionCall` access-key permission check lives in `verify_function_call_permission` [1](#0-0)  and is reused by both the regular transaction path and the gas-key transaction path [2](#0-1) [3](#0-2) .

However, `DelegateAction` (meta-transaction) processing does **not** call this shared function. Instead, `actions.rs` reimplements the same invariant from scratch in a separate, hand-written block that checks action count, deposit-with-function-call, receiver match, and method-name match in its own control flow [4](#0-3) .

This is precisely the "implicit restriction duplicated across modules" pattern from the report: the invariant enforced by `verify_function_call_permission` must be mirrored by hand in the `DelegateAction` validator, with no shared code or compiler-enforced coupling between them. The code already carries evidence that this duplication caused a real divergence in the past: a comment notes that the `DepositWithFunctionCall` branch was missing an early `return`, so execution "fell through to the receiver_id and method_name checks, which could overwrite this error with a different one" [5](#0-4) . The fix was implemented not by unifying the two enforcement paths, but by adding a protocol-feature-gated early return, `ProtocolFeature::FixDelegateActionDepositWithFunctionCallError` [6](#0-5) , meaning the duplicated, independently-maintained implementation remains in place going forward.

### Impact Explanation
Because the `DelegateAction` permission check is a separate reimplementation rather than a shared call to `verify_function_call_permission`, any future change or fix applied to the canonical function-call-permission logic in `verifier.rs` (e.g., a new restriction field, a new error precedence rule, or a bug fix) is not automatically reflected in the `actions.rs` `DelegateAction` path. As demonstrated by the historical `DepositWithFunctionCall` fall-through bug, this class of divergence can let a `FunctionCall`-restricted access key be used to execute unintended actions (e.g., bypass the receiver/method restriction or attach a deposit that should have been rejected) via meta-transactions, which is a direct authorization bypass on a real transaction path (`apply_delegate_action`).

### Likelihood Explanation
This is a maintenance-driven latent risk rather than an immediately exploitable bug in the current code state as read: the specific fall-through issue already identified is guarded by `ProtocolFeature::FixDelegateActionDepositWithFunctionCallError`. I was not able to confirm, within the available tool budget, whether this feature is unconditionally active at all currently supported protocol versions (`MIN_SUPPORTED_PROTOCOL_VERSION`) or still conditionally gated, so I cannot assert this specific historical variant is exploitable today. What is confirmed is the underlying structural weakness: the duplicated/unshared implementation pattern itself, which is the direct root cause the historical bug and remains present in the codebase, making recurrence of similar divergences likely on future changes to either path.

### Recommendation
Refactor `DelegateAction` permission validation in `runtime/runtime/src/actions.rs` to call the shared `verify_function_call_permission` (or an equivalent single source of truth) instead of maintaining a separate hand-written reimplementation of the same invariant. This removes the implicit synchronization requirement between the two code paths and eliminates the class of bug that already manifested once (the `DepositWithFunctionCall` fall-through).

### Proof of Concept
Not applicable as a standalone runnable PoC — the concrete historical manifestation of this exact divergence is preserved in-repo as a fixed bug: prior to `ProtocolFeature::FixDelegateActionDepositWithFunctionCallError`, a `FunctionCall` access key used to sign a `DelegateAction` with `deposit > 0` would trigger the `DepositWithFunctionCall` check but fail to `return`, letting subsequent `receiver_id`/`method_name` checks silently overwrite the correct error [7](#0-6) . This confirms the duplicated-enforcement design is a proven source of security-relevant inconsistency, matching the reported "too flexible/implicit configuration across modules" bug class.

/// Validates FunctionCall permission constraints:
/// - Transaction must have exactly one action
/// - Action must be FunctionCall with zero deposit
/// - Receiver must match permission's receiver
/// - Method name must be in allowed list (if list is non-empty)
fn verify_function_call_permission(
    function_call_permission: &FunctionCallPermission,
    tx: &Transaction,
) -> Result<(), InvalidTxError> {
    if tx.actions().len() != 1 {
        return Err(InvalidTxError::InvalidAccessKeyError(
            InvalidAccessKeyError::RequiresFullAccess,
        ));
    }
    let Some(Action::FunctionCall(function_call)) = tx.actions().get(0) else {
        return Err(InvalidTxError::InvalidAccessKeyError(
            InvalidAccessKeyError::RequiresFullAccess,
        ));
    };
    if function_call.deposit > Balance::ZERO {
        return Err(InvalidTxError::InvalidAccessKeyError(
            InvalidAccessKeyError::DepositWithFunctionCall,
        ));
    }
    let tx_receiver = tx.receiver_id();
    let ak_receiver = &function_call_permission.receiver_id;
    if tx_receiver != ak_receiver {
        return Err(InvalidTxError::InvalidAccessKeyError(
            InvalidAccessKeyError::ReceiverMismatch {
                tx_receiver: tx_receiver.clone(),
                ak_receiver: ak_receiver.clone(),
            },
        ));
    }
    if !function_call_permission.method_names.is_empty()
        && function_call_permission
            .method_names
            .iter()
            .all(|method_name| &function_call.method_name != method_name)
    {
        return Err(InvalidTxError::InvalidAccessKeyError(
            InvalidAccessKeyError::MethodNameMismatch {
                method_name: function_call.method_name.clone(),
            },
        ));
    }
    Ok(())
}
