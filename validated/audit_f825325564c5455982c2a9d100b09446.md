### Title
POA Bridge withdrawal status matched only by `assetId`, causing wrong destination tx hash reported for batched same-token withdrawals - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` and the equivalent `waitForWithdrawalCompletion` helper resolve the on-chain outcome of a withdrawal by matching the POA Bridge API response *only* on `assetId` (`near_token_id`), completely ignoring the withdrawal `index`, destination address, or amount. When a single intent batches two or more POA-bridge withdrawals of the **same token** to **different destinations**, every index resolves to the same matched record, so the SDK reports the same `transfer_tx_hash`/`status` for withdrawals that are actually distinct, unrelated on-chain transfers.

### Finding Description
`findMatchingWithdrawal` in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` searches the withdrawal list for the first entry whose `near_token_id` matches the requested `assetId`: [1](#0-0) 

This function is called from `describeWithdrawal`, which uses whatever it returns as the ground truth for the withdrawal's status and destination tx hash: [2](#0-1) 

The identical pattern (and identical caveat comment) exists in the lower-level `waitForWithdrawalCompletion` helper used by `internal-utils`: [3](#0-2) 

The SDK explicitly supports batch withdrawals with multiple `withdrawalParams` entries settled in one NEAR intent/transaction, and each entry keeps its own `index` used to build a `WithdrawalIdentifier`: [4](#0-3) 

Nothing in `sdk.ts`'s batch orchestration (`createWithdrawalIntents`, `signAndSendWithdrawalIntent`, `waitForWithdrawalCompletion`) rejects or deduplicates two withdrawal entries that share the same `assetId` but have different `destinationAddress`/`amount`: [5](#0-4) 

Because `findMatchingWithdrawal` keys only on `assetId`, if the batch contains two POA withdrawals of e.g. `nep141:usdt.tether-token.near` — one to address A and one to address B — the POA Bridge API returns two independent withdrawal records (one per real transfer), but `Array.prototype.find` will return the *first* matching record for **both** `index=0` and `index=1` calls to `describeWithdrawal`. Both indices therefore report the exact same `status`/`transfer_tx_hash`, even though only one of the two real destination transfers is actually reflected by that hash.

### Impact Explanation
This breaks the equality "status/hash reported == actual on-chain outcome for that specific withdrawal." An integrator relying on `sdk.waitForWithdrawalCompletion` / `createWithdrawalCompletionPromises` / `processWithdrawal` for a batch containing repeated same-token withdrawals to different destinations will:
- Mark the withdrawal to destination B as "completed" using the tx hash that actually only proves delivery to destination A, and
- Potentially credit/release funds for both legs based on a single real transfer, i.e., an integrator could credit the user twice (or believe two distinct deliveries occurred when only one did).

This matches the "High" impact category: a status/hash misreport that could make an integrator credit or refund twice.

### Likelihood Explanation
The condition requires only that a caller submit a batch withdrawal with two or more entries whose `assetId` is identical but destination/amount differ — a normal, unprivileged usage pattern the SDK's public API does not prevent (batch withdrawals are a first-class documented feature). No malicious relayer/bridge/RPC behavior is required; the bug reproduces with entirely honest POA Bridge API responses, purely from the SDK's own matching logic.

### Recommendation
Match withdrawal records by a discriminator that uniquely identifies each batch item — e.g., include withdrawal amount and/or destination address (and mark matched records as consumed so subsequent lookups in the same batch cannot reuse them), or request the POA Bridge API return correlation identifiers per withdrawal index. At minimum, apply the fix suggested in the existing code comment (sort both API results and `withdrawalParams` by amount for the same token to preserve relative ordering) and remove already-matched entries from the candidate pool before matching the next index.

### Proof of Concept
1. Build a batch withdrawal via `sdk.processWithdrawal({ withdrawalParams: [ { assetId: "nep141:usdt.tether-token.near", amount: 1000000n, destinationAddress: "0xAAA…", feeInclusive: false }, { assetId: "nep141:usdt.tether-token.near", amount: 2000000n, destinationAddress: "0xBBB…", feeInclusive: false } ] })`.
2. After NEAR settlement, the POA Bridge indexer eventually returns two `COMPLETED` withdrawal records for the same `near_token_id`, each with its own distinct `transfer_tx_hash` (one to 0xAAA, one to 0xBBB).
3. Call `bridge.describeWithdrawal` for `index: 0` and `index: 1` (as done inside `waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises`): both calls invoke `findMatchingWithdrawal(response.withdrawals, "nep141:usdt.tether-token.near")`, which returns the same first match for both indices.
4. Both `destinationTx` results reported by the SDK carry the identical `transfer_tx_hash`, even though the actual on-chain deliveries to 0xAAA and 0xBBB are two distinct transactions — the reported status for one of the withdrawals does not correspond to its actual on-chain outcome.

			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",

		};

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}
