### Title
Webhook shop-domain and topic spoofing due to HMAC covering only the raw body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `api_version`, and `webhook_id` are read straight from unauthenticated HTTP headers. `ShopifyAPI::Utils::HmacValidator.validate` only ever checks that HMAC against the body bytes, so any request whose body+HMAC pair is valid (for *any* shop's webhook, including the attacker's own shop) will pass validation no matter what shop-domain or topic header is attached. This lets an unprivileged internet user who legitimately installs the app on their own store capture a valid `(body, hmac)` pair and replay it against the app's public webhook endpoint with an arbitrary victim `shop-domain` header, causing the host application's webhook handler to process attacker-controlled data as if it came from a different, victim tenant.

### Finding Description
The HMAC binding is defined here: [1](#0-0) 

```ruby
def hmac
  Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
end
...
def shop
  T.cast(shopify_header("shop-domain"), String)
end
...
def to_signable_string
  @raw_body
end
```

The validator computes the signature only over `to_signable_string` (i.e. the raw body): [2](#0-1) 

And `Registry.process` trusts `request.shop` (parsed from the header, not the HMAC-covered payload) once the HMAC check on the body passes: [3](#0-2) 

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
end
```

This breaks the identity binding: `shop attributed to the handled event == shop that actually generated (and cryptographically bound) the payload`. In reality, `shop` (and `topic`) are *parsed but not verified* — only the raw body bytes are verified. Because Shopify signs webhook bodies with the app's single shared `api_secret_key` for every installed shop, a valid `(raw_body, hmac)` pair generated for shop A's install will also satisfy `HmacValidator.validate` when replayed with a `shop-domain` header claiming shop B (or any topic claiming a different event type), since none of those fields are part of the signed content.

### Impact Explanation
This is a cross-tenant integrity/spoofing issue: an attacker who is merely an ordinary internet user (they only need to install the target public app on their own free/dev store — no `api_secret_key`, access token, or privileged access is required) can:
1. Trigger a real webhook to their own store, capturing a genuinely valid `(body, hmac)` pair.
2. Replay that exact HTTP request to the app's public webhook endpoint, substituting the `x-shopify-shop-domain` header with a victim shop's domain (and/or a different `x-shopify-topic`).
3. The gem accepts it as authentic because HMAC validation never covers `shop`/`topic`, causing the host app's webhook handler to execute attacker-influenced logic while believing it originates from the victim shop.

Because host applications typically use `shop` from webhook metadata to look up sessions, access tokens, or drive per-tenant business logic (uninstall, orders, customer data requests, GDPR redaction, etc.), this enables cross-tenant data confusion/spoofing — matching the "cross-tenant access" class of impact.

### Likelihood Explanation
Likelihood is high: the webhook endpoint is a public HTTP endpoint by design; capturing a valid signed payload only requires the attacker to install the app once on a shop they control (a normal, unprivileged action any developer can perform), and replaying it with modified headers requires no cryptographic secret at all.

### Recommendation
Include `shop`, `topic`, and any other header-derived fields that influence handler dispatch or tenant attribution in the HMAC-signed content (`to_signable_string`), or otherwise cryptographically bind them to the payload (e.g., verify `shop` against Shopify's per-shop webhook secret if available, or require the raw body to embed/validate the shop domain). At minimum, do not treat `request.shop`/`request.topic` as trusted simply because the body HMAC validated.

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker.myshopify.com`; trigger any subscribed webhook (e.g. `orders/create`) to receive a real request with headers `x-shopify-hmac-sha256: <H>` and body `B`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Craft a new HTTP POST to the app's webhook endpoint with the same body `B` and same `x-shopify-hmac-sha256: <H>`, but set `x-shopify-shop-domain: victim.myshopify.com` (and/or a different `x-shopify-topic`).
3. `ShopifyAPI::Webhooks::Request.new` parses `shop`/`topic` from the attacker-supplied headers; `HmacValidator.validate` only checks `B` against `H`, which still matches: [4](#0-3) 
4. `Registry.process` dispatches the handler with `WebhookMetadata.new(topic: <attacker-chosen>, shop: "victim.myshopify.com", body: parsed_body, ...)`, despite the payload never having been produced by or for `victim.myshopify.com`. [3](#0-2)
