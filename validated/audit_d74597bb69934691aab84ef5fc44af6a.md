### Title
Webhook Shop Identity Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (tenant identity) is read from an HTTP header that is never included in that signature. `ShopifyAPI::Webhooks::Registry.process` trusts this unauthenticated `shop` value and forwards it to the app's webhook handler as the tenant identifier. Anyone who can obtain one valid `(raw_body, hmac)` pair for the shared app secret — which any merchant installing the app can trivially generate by triggering a webhook on their own store — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header, and HMAC validation will still succeed.

### Finding Description
The identity binding that should hold is:
`shop asserted by the HMAC-signed payload == shop used by the app to attribute/act on the webhook`

In this gem it does not hold:

- `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

- `Request#shop` is derived purely from an HTTP header, independent of the signed payload: [2](#0-1) 

- `HmacValidator.validate_signature` verifies `computed_signature` (over `to_signable_string`, i.e. body only) against the received `hmac`; it never touches `shop`: [3](#0-2) 

- `Registry.process` only calls `Utils::HmacValidator.validate(request)` and then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

Because the app's per-installation webhook shared secret (`Context.api_secret_key`) is the same for every shop that has the app installed, a legitimate but unprivileged merchant can:
1. Install the app on their own shop and trigger any webhook topic, capturing the genuine `raw_body` and its valid `x-shopify-hmac-sha256` value.
2. Resend that identical `raw_body` + `hmac` header to the app's webhook endpoint, but with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header changed to a victim shop's domain.
3. `HmacValidator.validate` recomputes the HMAC over `raw_body` only, finds it matches, and returns `true` — the forged `shop` header is never checked.
4. `Registry.process` hands the handler a `WebhookMetadata` claiming `shop: "victim-shop.myshopify.com"` with attacker-chosen body content, even though the payload was never actually signed for that shop.

This breaks the tenant boundary the HMAC is supposed to enforce: the gem verifies "this body came from an app-secret holder" but not "this body is scoped to this shop", yet it exposes `request.shop` as if it were an authenticated field.

### Impact Explanation
Any app relying on `ShopifyAPI::Webhooks::Registry`/`Request` to attribute incoming webhook data to the correct shop (which is the documented, expected usage pattern) can be made to process attacker-supplied data under another tenant's identity — a cross-tenant access/data-integrity issue. Depending on the handler logic (e.g., updating local records keyed by `shop`, triggering GDPR mandatory webhook flows, syncing state), this can corrupt or leak per-tenant state across tenants, which maps to the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is high given the low bar to exploit: any actor with a normal, low-privilege merchant/dev-store install of the app (an "unprivileged internet user" from the perspective of other tenants) can generate a valid `(body, hmac)` pair themselves, since they only need to trigger a webhook on their own shop — they never need the app's `client_secret`. The only thing they alter is an unauthenticated header value, and the gem's own `HmacValidator`/`Registry.process` code offers no additional protection against that.

### Recommendation
Bind the shop identity to the signed payload before trusting it:
- Include `shop` (and ideally `topic`/`webhook_id`) in the HMAC-signable string, or
- Cross-check the `shop-domain` header against an out-of-band trusted value (e.g., look up the expected shop for the webhook subscription/session before processing), and
- Document/enforce that `Registry.process` should not expose `request.shop` to handlers as trusted data unless it has been bound to the signature.

### Proof of Concept
```ruby
# Step 1: attacker installs the app on their own shop and captures a real webhook delivery
raw_body = '{"id":1,"note":"hello"}'
real_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# Step 2: attacker replays the identical body/hmac but swaps the shop-domain header
forged_headers = {
  "shopify-topic" => "orders/create",
  "shopify-hmac-sha256" => Base64.encode64(real_hmac),
  "shopify-shop-domain" => "victim-shop.myshopify.com", # arbitrary, unauthenticated
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# Step 3: HMAC validation succeeds because it only checks raw_body, not shop
ShopifyAPI::Utils::HmacValidator.validate(request) #=> true

# Step 4: Registry.process forwards attacker-chosen body attributed to victim-shop.myshopify.com
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: {...}, ...))
``` [4](#0-3)
