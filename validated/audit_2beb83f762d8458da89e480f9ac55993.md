### Title
Webhook shop identity not covered by HMAC signature allows cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates only the request *body* via HMAC, then trusts the `shop-domain` (and `topic`/`webhook-id`) HTTP headers — which are never part of the signed material — to decide which tenant the payload belongs to.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, and `#hmac` is derived solely from the `hmac-sha256` header: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC over `to_signable_string` (i.e. the body only) and compares it to the received signature: [2](#0-1) 

`Registry.process` calls this validator, and — once it passes — unconditionally trusts `request.shop`, `request.topic`, and `request.webhook_id`, which are read directly from unauthenticated headers, to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) [4](#0-3) 

The identity binding that should hold is: `shop-domain header == shop whose data the signed body actually represents`. Because the header is not part of the signed bytes, that equality is never enforced by this gem — it is enforced only by trusting that the header travels unmodified from Shopify to the app, which is not something an HMAC-over-body-only scheme guarantees. The gem's own documentation encourages apps to key business logic (e.g., enqueuing jobs "per shop_domain") directly off `data.shop` without any additional verification step: [5](#0-4) 

### Impact Explanation
An actor who can obtain one legitimately-signed `(raw_body, hmac)` pair for any topic (e.g. by installing the app on a shop they control, which is the normal, unprivileged onboarding path for any merchant) can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. `HmacValidator.validate` still succeeds because the header is not covered by the signature, and the app's handler receives `WebhookMetadata` claiming the payload originated from a different (victim) shop. Depending on how the host app keys per-tenant state on `data.shop`, this can lead to cross-tenant data confusion/injection — data or events attributed to another merchant's store.

### Likelihood Explanation
Exploitation requires only: (1) ability to install the app on an attacker-controlled shop (normal, unprivileged merchant capability, not a credential leak), and (2) the ability to send arbitrary HTTP requests to the app's public webhook callback URL. No access token, `client_secret`, or privileged account is needed to perform the header substitution itself — only a genuine body+HMAC pair from any topic delivery, which the attacker can generate at will using their own shop's own real webhook traffic.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed material used for HMAC verification, or otherwise cryptographically bind them to the body before trusting them (e.g., validate `shop-domain` against a previously known, installed shop record for the app, independent of the header value) before constructing `WebhookMetadata` and dispatching to handlers.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; trigger any webhook (e.g. `orders/create`) and capture the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sends.
2. Replay this exact `raw_body` and `hmac-sha256` value to the same app's webhook endpoint, but replace `X-Shopify-Shop-Domain` with `victim.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate` (called from `Registry.process`) succeeds because it only checks the body against the HMAC — it never inspects the shop header.
4. `Registry.process` invokes the registered handler with `WebhookMetadata#shop == "victim.myshopify.com"`, even though the payload actually originated from the attacker's own shop, corresponding to the code path at [6](#0-5) .

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
