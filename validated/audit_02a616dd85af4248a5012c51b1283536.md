### Title
Webhook `shop` field is trusted by the registry/handler pipeline without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC signature that `ShopifyAPI::Utils::HmacValidator.validate` checks in `ShopifyAPI::Webhooks::Registry.process` authenticates the body bytes only. The `shop` (and `topic`, `webhook_id`, `api_version`) values are read straight from unauthenticated HTTP headers and forwarded into `ShopifyAPI::Webhooks::WebhookMetadata`, which the gem's own documentation instructs handler authors to trust as "the shop domain of the webhook."

### Finding Description
The binding that should hold is: `shop value bound by HMAC == shop value delivered to the handler`. In this gem that equality fails.

- `ShopifyAPI::Webhooks::Request#shop` reads `shopify-shop-domain`/`x-shopify-shop-domain` header directly: [1](#0-0) 
- `ShopifyAPI::Webhooks::Request#to_signable_string` only signs the raw body, excluding the shop header entirely: [2](#0-1) 
- `ShopifyAPI::Webhooks::Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` and then, on success, immediately constructs `WebhookMetadata` using `request.shop`, `request.topic`, etc. — none of which the HMAC covers: [3](#0-2) 
- `HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string`, so it never touches headers: [4](#0-3) 

Because every shop that installs the app shares the same `Context.api_secret_key` used to sign all webhooks for that app, a merchant (an unprivileged actor from the app operator's perspective) can install the app on their own store, capture a genuinely-signed `(body, hmac)` pair for their own webhook deliveries, and then POST that exact `(body, hmac)` pair to the app's shared webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header pointing at a victim shop. `HmacValidator.validate` will still succeed because it only checks the body against the secret, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the (attacker-controlled) body belongs to the victim shop.

### Impact Explanation
This breaks the shop/tenant identity binding the gem documents as guaranteed ("This will verify the request did indeed come from Shopify" per `docs/usage/webhooks.md` line 125, and `shop` is documented as trustworthy per lines 12-14). Any host application that uses `data.shop` from `WebhookMetadata` to key persistence, authorization, or business logic (the exact pattern shown in the gem's own usage example) can have attacker-controlled webhook bodies attributed to a victim shop it does not control — a cross-tenant data/identity confusion inside the trust boundary this gem is responsible for establishing.

### Likelihood Explanation
Any user able to install the app on a store they control (a normal, unprivileged merchant action for any public/installable app) can obtain a validly-HMAC-signed body for themselves and replay it with a forged shop header, with no access to `api_secret_key`, access tokens, or any privileged account required.

### Recommendation
Do not treat `Request#shop` (or `topic`/`webhook_id`/`api_version`) as authenticated. At minimum, document clearly that `HmacValidator` only proves the body was signed with the app secret and does not bind the shop header, or better, require the host application to cross-check `shop` against a known/registered shop for that webhook subscription before trusting it, and/or extend the signable content to include the shop header where feasible.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggers a webhook (e.g. `orders/create`), and captures the raw body `B` and the `X-Shopify-Hmac-Sha256` header `H` that Shopify sends (valid because it's HMAC’d with the app’s real `api_secret_key`).
2. Attacker POSTs to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged), but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into `shop = "victim-shop.myshopify.com"`, `hmac` from header `H`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `to_signable_string` (`= B`) only — matches `H`, validation passes: [3](#0-2) 
5. Handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and body `B` (attacker-controlled content from their own shop's webhook), even though this data has nothing to do with the victim shop.
