Based on the investigation, I found a valid analog vulnerability class in the webhook processing path.### Title
Webhook topic and shop identity spoofing via HMAC that only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body alone, while `topic` and `shop` are read straight from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` then uses those unauthenticated header values to select the handler and to populate `WebhookMetadata` (tenant identity) passed to the app, without binding them to the HMAC. This breaks the identity binding: `HMAC(body) == HMAC(body)` while `topic_signed ≠ topic_used` and `shop_signed ≠ shop_used`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`topic`, `shop`, `webhook_id`, and `api_version` are all read from HTTP headers that are never part of the signed content: [2](#0-1) 

`Registry.process` verifies the HMAC over the request (i.e., over the body only) and then dispatches on `request.topic`, passing `request.shop` into `WebhookMetadata` as the trusted tenant identifier for the handler: [3](#0-2) 

Because the headers `shopify-topic`/`x-shopify-topic` and `shopify-shop-domain`/`x-shopify-shop-domain` are not part of `to_signable_string`, any request that reproduces a `(raw_body, hmac)` pair that is valid for the app's `client_secret` will pass `Utils::HmacValidator.validate` regardless of what topic or shop header is attached to it: [4](#0-3) 

An attacker who legitimately installs the same app on a shop they control will receive genuine webhooks (valid `raw_body` + `hmac` computed with the app's real `client_secret`) for events they themselves trigger. They can then replay that exact `raw_body`/`hmac` pair directly to the app's public webhook endpoint while substituting a different `shopify-topic` header (to invoke a different, possibly more sensitive, registered handler) and/or a different `shopify-shop-domain` header (to make the payload appear to originate from another, victim, shop). `HmacValidator.validate` will still succeed because it only checks the body bytes, not the headers.

### Impact Explanation
This is a cross-tenant identity-binding break: the byte range verified by HMAC (`raw_body`) does not equal the byte range acted upon (`topic` + `shop` headers used for handler dispatch and for the `WebhookMetadata#shop`/`#topic` passed to the application). Any host application that uses `WebhookMetadata#shop` from a successfully-`process`-ed webhook as an authenticated tenant identifier (a documented, expected usage per `docs/usage/webhooks.md`) can be made to associate attacker-controlled webhook content with a different (victim) shop, or to trigger a handler for a topic the payload was never actually signed for. This matches "cross-tenant access" (Critical) since it lets one authenticated app-installer spoof another tenant's identity to the app's own webhook-processing logic while presenting a validly-HMAC'd payload.

### Likelihood Explanation
Exploitation requires only that the attacker be an app installer (or otherwise obtain one valid `raw_body`/`hmac` pair for the target app, e.g., from their own store's webhook traffic) and be able to POST to the app's public webhook endpoint with custom headers — both are within reach of an unprivileged internet user/app installer, with no need for the app's `client_secret`, an access token, or any other privileged credential.

### Recommendation
Include the identity-relevant headers (`topic`, `shop-domain`, and ideally `webhook_id`/`api_version`) in the HMAC-signable content, or otherwise cryptographically bind them to the payload before use, so `to_signable_string` cannot be satisfied by a body-only signature while headers are swapped. At minimum, `Registry.process` should not trust `request.topic`/`request.shop` for dispatch or tenant identification unless those values are covered by the same HMAC that authenticates the body.

### Proof of Concept
1. App developer's app has `client_secret = S` and is installed on `shop-a.myshopify.com` (attacker-controlled) and `shop-b.myshopify.com` (victim), both with a webhook subscription for topics `orders/create` and `customers/create`.
2. Attacker triggers an `orders/create` event on `shop-a`, capturing the legitimate webhook POST: headers `x-shopify-topic: orders/create`, `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw_body with S>`, and `raw_body`.
3. Attacker resends the exact same `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but sets `x-shopify-shop-domain: shop-b.myshopify.com` (victim) and/or `x-shopify-topic: customers/create` (a different registered topic).
4. `Utils::HmacValidator.validate(request)` recomputes `HMAC(raw_body, S)`, which still matches the attacker-supplied `hmac`, because headers are excluded from `to_signable_string`. `Registry.process` proceeds, looks up the handler for the spoofed topic, and calls it with `WebhookMetadata` whose `shop` is `shop-b.myshopify.com` — even though the payload content actually originated from and was signed only in the context of `shop-a`.
