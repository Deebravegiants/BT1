### Title
Missing hash-length validation in `secp256k1.js:signBuffer` allows signing over attacker-controlled non-32-byte data via directly exposed `keychain.secp256k1.signBuffer` API - ([File: features/keychain/module/crypto/secp256k1.js])

### Summary
`features/keychain/module/crypto/secp256k1.js`'s `signBuffer` passes `data` straight to `secp256k1.ecdsaSignHash({ hash: data, ... })` with no length assertion [1](#0-0) . The only 32-byte length check for the `'ecdsa'` signature type lives in the higher-level dispatcher `keychain.js:signBuffer`, at `assert(data.length === 32, ...)` [2](#0-1) . Critically, `features/keychain/api/index.js` exposes `keychain.secp256k1.signBuffer` directly (bound to the low-level, unvalidated instance) as part of the wallet's public keychain API, bypassing `keychain.js`'s dispatcher and its length assertion entirely [3](#0-2) .

### Finding Description
The dispatcher `keychain.js:signBuffer` is the only place enforcing "only accept 32 byte buffers for ecdsa" before delegating to `this.secp256k1.signBuffer` [4](#0-3) . However `features/keychain/api/index.js` wires up a separate, parallel API surface: `keychain.secp256k1.signBuffer: keychain.secp256k1.signBuffer` — i.e., a direct reference to the low-level ECDSA signer instance, not routed through `keychain.js`'s `signBuffer` method [3](#0-2) . Any caller reaching this API entry point (e.g. via the public keychain API surface consumed by other features/plugins) can call `api.keychain.secp256k1.signBuffer({ seedId, keyId, data })` with `data` of arbitrary length, and `secp256k1.js` will forward it unchecked to `ecdsaSignHash({ hash: data, ... })` [5](#0-4) . This is confirmed by existing test usage showing `secp256k1.signBuffer` accepting non-hash raw buffers without length checks, e.g. `ethsign.test.js` signs a 32-byte hex fixture directly via `create({ getPrivateHDKey }).signBuffer` with no assertion on data shape beyond what the fixture happens to be [6](#0-5) . Production code paths that route through `SeedBasedTransactionSigner` (`tx-signer`) correctly funnel all signing through `this.#keychain.signBuffer(...)`, which does enforce the 32-byte check [7](#0-6) , so that path is safe. The exploitable gap is specifically the `api/index.js` exposure of `keychain.secp256k1.signBuffer` as a standalone, unguarded entry point.

### Impact Explanation
If a plugin, extension bridge, or dapp-facing RPC method is wired to this `keychain.secp256k1.signBuffer` API entry (rather than `keychain.signBuffer`), an attacker-controlled caller could submit oversized or otherwise unintended byte sequences (e.g., raw unhashed transaction bytes) to be signed with a valid ECDSA signature over content that never went through the 32-byte hash-length invariant enforced elsewhere in the codebase. This breaks the "signed content matches expected hash shape" invariant and could enable a forged-signature/approval-scoping issue if any downstream consumer relies on that invariant holding by construction rather than re-validating.

### Likelihood Explanation
Exploitability depends entirely on whether any actual RPC/dapp/plugin-facing consumer calls `api.keychain.secp256k1.signBuffer` directly instead of `api.keychain.signBuffer`. From the code searched, all identified production signing entry points (`tx-signer`'s `seed-signer.ts`) go through `keychain.signBuffer`, which does enforce the length check [7](#0-6) . I could not find, within the indexed codebase, a concrete attacker-reachable caller (dapp origin, RPC handler, deeplink) that invokes `api.keychain.secp256k1.signBuffer` directly with untrusted data — only tests and README examples do so. Without such a reachable caller, this is a latent defense-in-depth gap in the API surface rather than a demonstrated exploitable path from an ordinary dapp/origin request today.

### Recommendation
Add an explicit `assert(data.length === 32, ...)` check inside `secp256k1.js:signBuffer` before calling `ecdsaSignHash` for the ECDSA (non-Schnorr) path, so the invariant is enforced at the lowest layer regardless of caller, rather than relying solely on the `keychain.js` dispatcher. Additionally, reconsider whether `features/keychain/api/index.js` should expose `secp256k1.signBuffer`/`signSchnorr`/`signSchnorrZ` directly at all, or should route all signing through `keychain.signBuffer` with `signatureType` to guarantee the top-level validation always applies.

```js
import { create } from '../crypto/secp256k1.js'
import KeyIdentifier from '@exodus/key-identifier'

test('secp256k1.js signBuffer should reject non-32-byte data for ECDSA', async () => {
  const getPrivateHDKey = () => ({
    privateKey: Buffer.from('164122e5d39e9814ca723a749253663bafb07f6af91704d9754c361eb315f0c1', 'hex'),
  })
  const signer = create({ getPrivateHDKey })
  const keyId = new KeyIdentifier({
    keyType: 'secp256k1',
    derivationPath: 'm/0',
    derivationAlgorithm: 'BIP32',
  })

  // Oversized / non-hash payload (e.g. raw unhashed tx bytes)
  const oversizedData = Buffer.alloc(1000, 0x41)

  await expect(
    signer.signBuffer({ keyId, data: oversizedData })
  ).rejects.toThrow(/32/) // currently this does NOT throw, demonstrating the gap
})
```
This test currently passes (i.e., signs successfully) against `secp256k1.js`, demonstrating the absence of the length check at that layer. It should be updated to assert a throw once the fix is applied.
