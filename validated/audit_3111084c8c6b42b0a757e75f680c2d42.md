Found a strong structural analog to the `setNonceTrue` bug class in Hyperbridge's core message-delivery path.

### Title
Front-runnable `DuplicateMessage` revert lets a malicious relayer permanently grief batched `handlePostRequests`/`handleGetResponses` deliveries - (File: `evm/src/core/HandlerV2.sol`)

### Summary
`HandlerV2.handlePostRequests` and `HandlerV2.handleGetResponses` are fully permissionless entry points that accept a batch of proven requests/responses and deliver them atomically. Both functions revert the **entire batch** the instant a single element in the batch is found to already have a receipt, instead of skipping that one element and delivering the rest. Because delivery of any individual request/response is itself permissionless (self-relaying is explicitly supported), an attacker can watch the mempool for an honest relayer's multi-item batch, front-run it with a cheap single-item delivery of one of the requests contained in that batch, and force the entire batch transaction to revert with `DuplicateMessage()` — exactly the same "consume a shared, permissionlessly-writable check ahead of a batched operation" pattern as the `setNonceTrue` bug in the source report.

### Finding Description
`HandlerV2.handlePostRequests` first verifies the MMR/state-proof for the whole batch of `leaf.request`s, then loops a second time and, for each leaf, reverts the whole call if `host.requestReceipts(leaf.request.hash())` is already non-zero: [1](#0-0) 

The same pattern exists for GET responses: [2](#0-1) 

`requestReceipts`/`responseReceipts` are written by `EvmHost.dispatchIncoming`, which is only callable by the configured handler, but the handler functions themselves (`handlePostRequests`, `handleGetResponses`, `batchCall`) are explicitly documented as permissionless — "anyone can call them to relay messages": [3](#0-2) 

Self-relaying a single request via the same handler is an explicitly supported, documented flow: [4](#0-3) 

Request bodies, their destinations, and their commitments are all public (via `PostRequestEvent`/indexers), so an attacker can compute the exact commitment of any request inside a pending relayer batch and pre-deliver just that one request with a trivial single-element `PostRequestMessage`. If that transaction is mined first (trivial via higher gas), the original batch's second loop hits `requestReceipts(leaf.request.hash()) != address(0)` for that leaf and reverts `DuplicateMessage()` for the **entire** batch — including all the other, still-undelivered requests bundled with it — wasting the honest relayer's gas and delaying delivery of every request in that batch. Because this attack can be repeated indefinitely on the next resubmission (the attacker just needs to grab one commitment out of the new batch each time), it recreates the "malicious front-run of a permissionless nonce/receipt write makes batched execution always fail" bug class from the reference report, just with `requestReceipts`/`responseReceipts` playing the role of `nonces[trader][nonce]`.

### Impact Explanation
This is a griefing/DoS vector against Hyperbridge's core cross-chain delivery path rather than a fund-theft bug: it does not corrupt state or forge deliveries, but it lets any unprivileged actor perpetually force honest relayers' batched deliveries to revert, wasting their gas and materially degrading/delaying message delivery on the affected route ("a route unable to deliver messages" in the accepted-impact list), since relayers must fall back to per-message delivery (defeating the purpose and gas savings of `batchCall`/batched handler submission) whenever an attacker chooses to interfere.

### Likelihood Explanation
Likelihood is high for a determined griefer: request/response data and their target commitments are public before finalization (emitted in `PostRequestEvent`/indexer feeds), delivering an individual request is fully permissionless and cheap, and front-running a pending relayer transaction with a higher gas price is a standard, low-cost MEV technique. No special privileges, secrets, or races beyond ordinary transaction-ordering control are required.

### Recommendation
In `handlePostRequests` and `handleGetResponses`, do not revert the whole batch when an individual leaf's receipt already exists. Instead, skip that leaf (continue) while still delivering the remaining, not-yet-delivered leaves in the same call — mirroring how `EvmHost.dispatchIncoming` already avoids reverting the whole batch on a destination-call failure (`evm/src/core/EvmHost.sol:800-803`). Alternatively, exclude already-delivered leaves from the MMR-membership check up front so a race against a benign concurrent relayer, or a malicious front-run, degrades gracefully to "deliver everything not yet delivered" rather than "deliver nothing."

### Proof of Concept
1. Relayer A observes `N` pending POST requests (e.g., commitments `c1..cN`) finalized on Hyperbridge and prepares `handlePostRequests(host, {requests: [c1..cN], proof})`.
2. Attacker, watching the mempool, extracts `c1`'s `PostRequestLeaf` and submits `handlePostRequests(host, {requests: [c1], proof: proof_for_c1})` with a higher gas price, or self-relays it via `batchCall`.
3. Attacker's transaction lands first; `EvmHost.dispatchIncoming` sets `requestReceipts[c1] != address(0)`.
4. Relayer A's batch transaction executes its second loop, reaches `c1`, and hits `if (host.requestReceipts(leaf.request.hash()) != address(0)) revert DuplicateMessage();` — the entire transaction (covering `c1..cN`) reverts.
5. Relayer A must resubmit without `c1`; the attacker repeats the same front-run against any future batch, indefinitely delaying batched delivery on this route.

## Self Relayed Requests

Self-relaying allows you to deliver POST requests to the destination chain yourself, instead of relying on the Hyperbridge relayer network. This is useful when you want full control over delivery timing, need to save on relayer fees, or want to guarantee delivery for critical requests.

The `@hyperbridge/sdk` provides tools to track POST requests and automatically generates the calldata needed to execute [`handlePostRequests()`](/developers/evm/api/ihandler#handlepostrequests) on the destination chain's [`IHandler`](/developers/evm/api/ihandler) contract.

To learn how to self-relay requests:

1. **[Get Started with the SDK](/developers/sdk/getting-started)** - Install and set up the Hyperbridge SDK
2. **[Track POST Requests](/developers/sdk/tracking/post-requests)** - Monitor request status and extract delivery calldata
3. **[IsmpClient API](/developers/sdk/api/ismp-client)** - Use the [`postRequestStatusStream()`](/developers/sdk/api/ismp-client#postrequeststatusstream) method to get calldata when `HYPERBRIDGE_FINALIZED` status is reached

The SDK automatically generates the [`PostRequestMessage`](/developers/evm/api/ihandler#postrequestmessage) proof and calldata you need to call the [`IHandler.handlePostRequests()`](/developers/evm/api/ihandler#handlepostrequests) function on the destination chain. You can make your users self-relay requests or run a server which can relay requests on behalf of users.
