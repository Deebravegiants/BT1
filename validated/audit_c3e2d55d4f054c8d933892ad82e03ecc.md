### Title
Webhook `shop`/`topic`/`webhook_id` fields are trusted by the dispatch handler while only the raw body is covered by the HMAC, enabling cross-tenant webhook data injection - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then dispatches to the app's handler using `shop`, `topic`, `webhook_id`, and `api_version` values pulled directly from HTTP headers that are never included in that HMAC computation. This is the same bug class as the referenced report: a value that the code *acts on* (here, tenant identity `shop`, and routing/versioning metadata) is not bound by the same integrity check (HMAC) used to authenticate the request, so it can be substituted independently of the signed payload.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from attacker-controllable headers, independent of that signed body: [2](#0-1) [3](#0-2) 

`Registry.process` validates only the HMAC (i.e., only the body) and then forwards the unauthenticated header-derived `shop`/`topic`/`webhook_id`/`api_version` straight into `WebhookMetadata`, which the app's `WebhookHandler#handle` uses to decide which merchant/tenant the payload belongs to: [4](#0-3) 

`WebhookMetadata` binds `shop` as a plain, unauthenticated string field consumed by host application handler logic: [5](#0-4) 

The identity binding equality that should hold is:
`shop_authenticated_by_hmac == shop_used_by_handler`

In this gem, the left side is always `nil`/undefined because the HMAC only ever covers `@raw_body`, so the equality can never be enforced — `shop_used_by_handler` is taken entirely from an unauthenticated header. Because HMAC-SHA256 with the app's shared `api_secret_key` is identical across every shop that installs the app, any actor able to obtain one valid `(raw_body, hmac)` pair for the app (e.g., by installing the app on their own test/dev store and capturing a real delivered webhook, since Shopify signs webhooks with the same per-app secret for all merchants) can replay that exact body+hmac pair to the app's webhook endpoint while substituting the `shopify-shop-domain`, `shopify-topic`, and `shopify-webhook-id` headers with values naming a different, victim shop. `HmacValidator.validate` will pass (body untouched), and `Registry.process` will hand the app's handler a `WebhookMetadata` claiming the payload originated from the victim shop.

### Impact Explanation
This breaks the tenant-isolation guarantee that host applications rely on `ShopifyAPI::Webhooks::Registry.process`/`WebhookMetadata#shop` to provide: it enables cross-tenant data injection — an attacker can make an app process forged data (with an actor-chosen body they legitimately obtained a valid signature for) as if it came from a shop they do not control. Depending on how the host app's handler uses `data.shop` (e.g., to look up per-shop state, trigger per-shop side effects, or mark data as belonging to that store), this is a cross-tenant access vector, matching the "cross-tenant access" impact tier.

### Likelihood Explanation
Likelihood is constrained: the attacker needs at least one valid `(raw_body, hmac)` pair produced by Shopify for the target app (most straightforwardly obtainable by installing the app on any shop the attacker controls and capturing one delivered webhook, since the same `api_secret_key` signs webhooks for every install of the app). No secrets, tokens, or privileged access to the *victim* shop are required — only a normal, self-service app install and a replay against the exposed webhook endpoint. This matches the "unprivileged internet user" threat model in scope.

### Recommendation
Bind `shop`, `topic`, `webhook_id`, and `api_version` into the HMAC-signable representation (or otherwise cryptographically/contextually verify them, e.g. cross-check `request.shop` against the shop associated with the session/store that registered the webhook) instead of trusting header values that fall outside the HMAC's coverage. At minimum, document and require callers of `Registry.process` to independently verify `request.shop` against a known/expected tenant before acting on `WebhookMetadata`.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g., `orders/create`) and capture the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header value `H` that Shopify computed for it (valid because it's signed with the app's real `api_secret_key`).
2. Replay a new HTTP request to the app's webhook endpoint with:
   - Body = `B` (unchanged, so `H` still validates)
   - `X-Shopify-Hmac-Sha256: H`
   - `X-Shopify-Shop-Domain: victim.myshopify.com` (forged)
   - `X-Shopify-Topic`, `X-Shopify-Webhook-Id` optionally forged as well
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `@raw_body` — validation succeeds: [6](#0-5) 
4. `process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the forged `shop` header value and dispatches to the app's registered handler, which now processes body `B` attributed to `victim.myshopify.com`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
