### Title
All-or-nothing multi-token escrow release permanently freezes unrelated assets when one token's transfer to the beneficiary reverts - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentsBase._withdraw()` iterates over every escrowed token in an order and transfers each to a single beneficiary in one atomic loop. If any single token in that list reverts on transfer to the beneficiary (e.g. a USDC-style blacklist, or any ERC-20 with transfer-blocking hooks), the entire function reverts, which blocks release of *every other* (non-problematic) token escrowed for that same order commitment — with no way to redeem just the unaffected tokens.

### Finding Description
`_withdraw` is the single settlement path for releasing escrowed order inputs, whether on a successful fill (`RedeemEscrow`) or a refund (`RefundEscrow`/cancel): [1](#0-0) 

```
function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    if (finalize) _filled[body.commitment] = beneficiary;

    uint256 len = body.tokens.length;
    for (uint256 i; i < len; i++) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (amount == 0) continue;

        uint256 escrowed = _orders[body.commitment][token];
        if (escrowed == 0) revert UnknownOrder();

        _orders[body.commitment][token] = escrowed - amount;
        if (token == address(0)) {
            _sendValue(beneficiary, amount);
        } else {
            IERC20(token).safeTransfer(beneficiary, amount);
        }
    }
    ...
```

The `tokens` list comes directly from `order.inputs` (set by the order creator in `placeOrder`), and can legitimately include multiple asset types — e.g., native ETH, DAI, and USDC — in a single order. `_withdraw` is invoked from two entry points:

- `onAccept` for `RequestKind.RedeemEscrow`/`RequestKind.RefundEscrow`, which is the ISMP delivery path for the cross-chain settlement message. This is reachable by any relayer delivering a `PostRequest` (or the sole authorized relayer if `_relayer` is set) — a permissionless, unprivileged trigger: [2](#0-1) 
- `onGetResponse`, the cancellation-confirmation path that also calls `_withdraw(body, true, true)`: [3](#0-2) 

`safeTransfer` bubbles up any revert from the ERC-20 `transfer` call (e.g. a blacklist check reverting inside the token contract). Because `_withdraw` processes *all* tokens for the commitment inside a single loop with no isolation, per-token try/catch, or partial retry, a revert on any one token aborts the whole withdrawal — including the release of ETH or other perfectly-transferable tokens escrowed in the same order.

`EvmHost.dispatchIncoming` swallows a failing `onAccept` call and deletes the receipt so the message "stays deliverable" (retryable), but a retry replays the exact same `WithdrawalRequest`/`_withdraw` call with the exact same token list and beneficiary — so if the beneficiary is permanently blacklisted for one token in that list, every retry fails identically and the escrow (all tokens, not just the blacklisted one) is frozen forever. There is no code path to redeem a subset of an order's escrowed tokens, or to sweep the non-blocked tokens while leaving the blocked one pending.

This mirrors the reported OpenQ `ClaimManagerV1._claimAtomicBounty` bug class: a loop over multiple token addresses to a single recipient, where a blacklist/revert on one token DOSes delivery of the rest.

### Impact Explanation
Funds are permanently frozen: any order whose `inputs` include a token that can later block the eventual beneficiary (order creator on refund, or solver on redeem) from receiving it — deliberately (a griefing solver who is itself/associate-controlled and gets blacklisted, or a user who becomes sanctioned/blacklisted after placing the order but before cancellation resolves) — locks up *all* co-escrowed assets for that order, not just the problematic token. Since `_orders[commitment][token]` accounting and `_filled[commitment]` state are only updated/finalized within the same atomic call, there is no partial-success state to recover from; the entire escrowed balance for the order (potentially large amounts of ETH/DAI/etc.) becomes unrecoverable. This satisfies "permanent freezing of funds."

### Likelihood Explanation
Any user constructing a multi-asset order via the permissionless `placeOrder` (no restriction against mixing a blacklist-capable ERC-20 like USDC with other assets) can create this condition, and the failure is triggered purely by normal delivery of the settlement message via `onAccept`/`onGetResponse` — both permissionless, unprivileged-relayer-reachable paths, requiring no admin/governance compromise. The only external dependency is that the beneficiary becomes non-transferable for one listed token (a realistic, externally-controlled event, e.g. Circle blacklisting a USDC address), which is outside the protocol's control but well within scope of "attackers can DOS claims of blacklisted claimers," matching the referenced report's own likelihood framing.

### Recommendation
Make token release resilient to a single failing transfer:
- Wrap each per-token transfer in `_withdraw` in a try/catch (or use a low-level `call` and check success without reverting the loop), and on failure leave that token's escrow balance intact while still releasing all other tokens and finalizing what can be finalized.
- Track and allow a separate, permissionless "claim remaining stuck token" flow (e.g., let the beneficiary specify an alternate recipient for that specific token) so a blacklist on one token cannot hold hostage the rest of the escrow.
- Ensure `_filled`/escrow bookkeeping updates only for tokens that were actually transferred, so partial withdrawal remains consistent and retryable independently per token.

### Proof of Concept
1. User A calls `placeOrder` on chain X with `order.inputs = [{token: USDC, amount: 1000e6}, {token: address(0) /*native ETH*/, amount: 1 ether}]`, targeting a cross-chain fill on chain Y.
   - `evm/src/apps/IntentGatewayV2.sol` `placeOrder` (lines 194-329) escrows both assets under the same `commitment`.
2. Suppose USDC later blacklists user A's address (a real-world event outside the protocol, or triggered by a griefer that gets the user reported/sanctioned) before the order is cancelled or filled.
3. Order expires; user A calls `cancelOrder` → dispatches `RefundEscrow`/GET flow back to source chain, ultimately invoking `_withdraw(body, true, true)` in `IntentsBase.sol` with `body.tokens = [USDC, ETH]`, `body.beneficiary = user A`.
4. Inside `_withdraw`'s loop (`evm/src/apps/intentsv2/IntentsBase.sol:456-470`), the USDC `safeTransfer(beneficiary, 1000e6)` reverts because A is blacklisted.
5. The whole `_withdraw` call reverts — the escrowed 1 ether of ETH, which would have transferred successfully, is never released. `_filled[commitment]` is never set. Every relayer retry of the same `RefundEscrow`/GET-response message reproduces the same revert (`EvmHost.dispatchIncoming` deletes the receipt and lets it be resubmitted, but the outcome is deterministic), permanently freezing the entire escrow.
