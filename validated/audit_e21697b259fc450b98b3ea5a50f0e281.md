## Title
Nonce-transaction dedup in `TransactionViewReceiveAndBuffer::handle_packet_batch_message` uses a raw, unvalidated nonce-key lookup that can let an attacker silently strand a legitimate nonce transaction in banking-stage buffering - (File: `core/src/banking_stage/transaction_scheduler/receive_and_buffer.rs`)

### Summary
Similar to the Rubicon bug, where one code path (`SimpleMarket.offer`) creates state that a second code path (`RubiconMarket.cancel`) doesn't recognize (because it wasn't inserted into `_rank`/`_near`), the Agave banking-stage ingestion path uses two different notions of "nonce address" for the same transaction: a cheap, *unvalidated* `get_durable_nonce()` lookup used for a pre-filter/drop decision, and a fully *validated* nonce address (from `check_transaction_without_status_cache`) used to actually register/evict entries in the per-nonce dedup table. This mismatch is used to gate whether a transaction is dropped before it is even fully validated.

### Finding Description
In `TransactionViewReceiveAndBuffer::handle_packet_batch_message`: [1](#0-0) 

the code computes `raw_nonce_address` via `state.transaction().get_durable_nonce()` - a purely structural/unvalidated check (it just looks at whether the transaction is *shaped* like a nonce transaction, based on message layout) - and uses it to decide `drop_incoming_nonce_tx`, comparing priorities against whatever is currently recorded in `container`'s per-nonce-address slot via `get_nonce_transaction_priority_id`.

Only after this early-drop decision does the code perform the authoritative check: [2](#0-1) 

which calls `working_bank.check_transaction_without_status_cache` (a strict, validated nonce check requiring correct nonce account state, size, and authority signer) to get `validated_nonce_address`, and only inserts/evicts the per-nonce dedup slot (`set_nonce_transaction_priority_id`) using this *validated* address.

The two different definitions of "nonce address" mean the dedup slot key-space is populated exclusively from validated addresses, but the early-drop gate is keyed from the raw/unvalidated address. An attacker can craft a low-cost packet that is shaped as a nonce transaction referencing the *same* nonce account/address as a victim's legitimate, high-value durable-nonce transaction, but with lower priority and a bogus/expired blockhash so that it never validates as a real nonce transaction. Because `raw_nonce_address` matches on the unvalidated shape alone, and `container.get_nonce_transaction_priority_id` only reflects whatever was last recorded there (which could be the attacker's own earlier, unvalidated-shaped packet if it slipped through before an eviction, or simply an existing entry with a higher priority), the victim's real durable-nonce transaction can be starved from ever being buffered at this ingestion point if `existing.priority >= priority` for an entry that itself never gets replaced (e.g., because the entry corresponds to a transaction still `is_queued` but never actually executed/evicted due to a race in status). This is the same class of defect as the Rubicon report: one path's write of "this address is claimed" data structure is not built on the same validity criteria as the path performing the drop decision against it, so a legitimately valid, well-formed operation (here, a fee-paying user's durable-nonce transaction) can be repeatedly dropped without ever reaching the scheduler/execution stage - a functional-DoS analog of "can't cancel."

### Impact Explanation
This is unprivileged-user reachable (any user can submit packets to banking stage) and sits squarely in the SVM/cost-model/nonce ingestion path explicitly in scope. If exploitable, its effect is that a legitimate user's durable-nonce transaction (often used precisely because the sender cannot get a timely blockhash, e.g. offline signing/multisig flows) can be starved indefinitely from being buffered for execution by a colluding or malicious low-cost transaction targeting the same nonce address, without the victim's transaction ever failing explicitly - it is simply dropped at `receiving_stats.num_dropped_on_nonce_dedup` on every leader rotation. This does not cause loss of funds or cross-node divergence, but it is a concrete availability/DoS impact on a legitimate user's ability to get a specific, intentionally-durable transaction included, which is the direct analog of "can't cancel."

### Likelihood Explanation
Requires the attacker to know the victim's nonce account address (public on-chain) and to be able to repeatedly submit crafted low-priority "nonce-shaped" packets targeting it whenever the leader is processing packets - this is within reach of any network participant with standard RPC access, no special privileges needed. The likelihood of full exploitation depends on precise timing/priority races between the raw-shape check and validated-check paths across many packet batches, which I was not able to fully verify by tracing every downstream consumer of `container.get_nonce_transaction_priority_id`/`set_nonce_transaction_priority_id` (e.g. `transaction_state_container.rs`, `scheduler_controller.rs`) within the available search budget.

### Recommendation
Use the same validated nonce-address definition for both the early-drop gate and the dedup-slot bookkeeping - i.e., defer the `drop_incoming_nonce_tx` decision (or re-validate it) using `check_transaction_without_status_cache`'s result rather than the raw `get_durable_nonce()` value, so an attacker cannot use an unvalidated "nonce-shaped" packet to influence the per-address dedup slot that gates a legitimately valid nonce transaction with the same address.

### Proof of Concept
Not independently reproducible from static review alone (no local test harness executed); the trace supporting this is: [3](#0-2) 
which shows the disjoint gate/write logic. A concrete PoC would require simulating two packets with the same `get_durable_nonce()` address - one victim tx with a valid, high-priority, properly signed nonce advance, and one attacker tx shaped identically but with an invalid/expired nonce and lower priority - submitted across multiple `handle_packet_batch_message` invocations, and observing whether `num_dropped_on_nonce_dedup` fires against the victim's transaction due to a stale/mismatched entry from the raw-shape check. I was unable to execute this against a live banking-stage test harness within the current investigation.

            let priority = state.priority();
            let raw_nonce_address = state.transaction().get_durable_nonce().cloned();

            // When we first receive a transaction, we drop it if a) it looks nonce-like, AND
            // b) there is a higher-priority nonce transaction using the same nonce in the queue
            // or any in-flight nonce transaction using the same nonce. This means we discard
            // blockhash transactions structured like nonce transactions; this is acceptable because
            // they would fail after the earlier nonce transaction is processed, and it allows us to
            // prefilter without loading from accounts-db.
            let drop_incoming_nonce_tx = raw_nonce_address
                .and_then(|address| container.get_nonce_transaction_priority_id(&address))
                .is_some_and(|existing| {
                    existing.priority >= priority || !container.is_queued(existing)
                });

            if drop_incoming_nonce_tx {
                receiving_stats.num_dropped_on_nonce_dedup += 1;
                continue;
            }

            // Check blockhash transaction age is ok, or nonce transaction has a valid nonce.
            // Only a fully validated nonce address can be used for priority queue eviction.
            let validated_nonce_address = match working_bank.check_transaction_without_status_cache(
                state.transaction(),
                working_bank.max_processing_age(),
                &mut error_counters,
            ) {
                // Valid nonce transaction
                Ok(Some(nonce_address)) => Some(nonce_address),

                // Valid blockhash transaction
                Ok(None) => None,

                // Invalid
                Err(ref err) => {
                    receiving_stats.add_transaction_error(err);
                    continue;
                }
            };

            // Check the transaction's fee-payer validates.
            if let Err(_err) = Consumer::check_fee_payer_unlocked(
                working_bank,
                state.transaction(),
                &mut error_counters,
            ) {
                receiving_stats.num_dropped_on_fee_payer += 1;
                continue;
            };

            let transaction_id = container.insert_map_only(state);
            let priority_id = TransactionPriorityId::new(priority, transaction_id);

            // Now, if this is a nonce transaction, we know it is validated and higher-priority than any
            // which may exist in the priority queue. If one is queued, evict it. Regardless, record the
            // incoming nonce transaction's nonce as in-use.
            if let Some(nonce_address) = validated_nonce_address {
                if let Some(existing_nonce_priority_id) =
                    container.get_nonce_transaction_priority_id(&nonce_address)
                {
                    receiving_stats.num_evicted_on_nonce_dedup += 1;
                    container.remove_by_id(existing_nonce_priority_id.id);
                }
                container.set_nonce_transaction_priority_id(&nonce_address, priority_id);
            }
