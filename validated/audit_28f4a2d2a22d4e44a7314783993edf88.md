### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and exposes an HMAC that authenticates only the raw request body. The `shop` (tenant identity) is read directly from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` header and is never included in the signed material. Any party that can obtain one genuine `(body, hmac)` pair signed with the app's secret - e.g. a merchant who has installed the app on their own store and receives real webhooks - can replay that exact body/hmac pair while substituting an arbitrary `shop-domain` header, and `Utils::HmacValidator.validate` will report the forged request as authentic for the victim shop.

### Finding Description
The identity binding the webhook pipeline is supposed to enforce is:
`hmac_valid(body) == true` should imply `shop_header == shop_that_actually_sent_this_body`.

In practice this equality does not hold, because the two are computed from disjoint inputs:

- `hmac` is derived only from the signature header itself, and is checked against `to_signable_string`, which returns `@raw_body` exclusively: [1](#0-0) [2](#0-1) 
- `shop` is parsed straight from the `shop-domain` header with no cryptographic tie to the body or the hmac: [3](#0-2) 
- `HmacValidator.validate`/`validate_signature` only ever compares `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)` - i.e. purely a function of the body bytes, never of `shop`: [4](#0-3) 

Because a single app secret (`api_secret_key`) is shared across every shop that installs the app, any merchant who legitimately installs the app can capture a real, validly-signed webhook `(raw_body, hmac)` pair delivered to their own shop. That merchant can then send the identical body and hmac to the app's webhook endpoint while setting the `shop-domain` header to a different (victim) shop's domain. `Webhooks::Request#hmac` and `#to_signable_string` are unchanged (they don't read `shop`), so `HmacValidator.validate` still returns `true`; `Webhooks::Registry.process` dispatches to the registered handler with `request.shop` equal to the attacker-chosen victim domain, as demonstrated by the handler contract itself (`data.shop`): [5](#0-4) 

This is exactly the "field acted on but not covered by the HMAC" class: `shop` is acted upon (used as the tenant key for whatever the host app's handler does - session lookup, data writes, uninstall processing, GDPR deletion, etc.) but is not part of the signed payload.

### Impact Explanation
This breaks the tenant isolation boundary the HMAC is meant to enforce. An unprivileged internet user who can install the app on any shop (including a free/trial shop) - a normal, unprivileged action - gains the ability to forge webhook events that the host app will attribute to any other merchant shop it also serves, since `Webhooks::Registry.process` treats a validated request's `shop` as trustworthy. Depending on how the host app's handlers use `shop`/`topic`/`body` (which is exactly the intended and documented usage pattern of this API), this enables cross-tenant state corruption, forged `app/uninstalled` or `shop/redact` events against a victim shop, or injection of forged order/customer data attributed to a shop the attacker does not control - a cross-tenant access impact.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the app on a shop of their own (an ordinary act available to any internet user for public/embedded apps) in order to obtain one genuine `(raw_body, hmac)` pair, plus the ability to send an arbitrary HTTP request with a spoofed `shop-domain` header to the app's public webhook endpoint. No access token, `client_secret`, or privileged credential is required - only a replayed body/hmac pair and header manipulation, both fully attacker-controlled.

### Recommendation
Bind the claimed `shop` (and ideally `topic`/`webhook_id`) into the value that is cryptographically verified, or independently authenticate the shop before trusting it:
- Preferred: verify that the shop in the header corresponds to a shop for which the app holds an active session/access-token record before honoring the webhook, rather than trusting the header outright.
- Alternatively, include the `shop-domain` (and `topic`) in `to_signable_string` so the HMAC covers the full identity tuple rather than only the raw body, matching Shopify's guidance that webhook shop identity should not be trusted independent of signature verification.
- At minimum, document prominently (and enforce in this gem, since it is the single place the invariant can live) that consumers of `Webhooks::Request#shop` must not treat it as authenticated by `HmacValidator.validate` alone.

### Proof of Concept
1. Install the target app (as any user) on `attacker-shop.myshopify.com`. Trigger any webhook topic the app subscribes to (e.g. `orders/create`); Shopify delivers a request with headers `x-shopify-hmac-sha256: <H>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, and body `B`. Capture `B` and `H`.
2. Send a new POST to the app's webhook endpoint with the same body `B` and header `x-shopify-hmac-sha256: H`, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. The app calls `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...with victim shop...})` then `ShopifyAPI::Webhooks::Registry.process(request)`.
4. `HmacValidator.validate(request)` succeeds because `to_signable_string` returns `B` (unchanged) and the hmac header matches - see: [1](#0-0) 
5. The registered handler is invoked with `data.shop == "victim-shop.myshopify.com"`, even though `victim-shop` never sent this webhook - matching the handler-shape shown in the existing test suite: [6](#0-5)
