## Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating an HMAC that covers **only the raw request body**, then hands the handler a `WebhookMetadata` object whose `shop` field is read straight from the unauthenticated `X-Shopify-Shop-Domain` header. The HMAC never binds the body to the shop header, so the value the host application uses to identify *which tenant* the webhook is about is never cryptographically verified.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is parsed independently from a header that plays no role in the signature: [2](#0-1) 

`HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest` over `verifiable_query.to_signable_string` (the body only) and compares it to `verifiable_query.hmac`, with no reference to the shop header anywhere in the computation: [3](#0-2) 

`Registry.process` gates on that body-only HMAC, then forwards `request.shop` (unauthenticated) directly into the metadata passed to the registered handler: [4](#0-3) 

The equality the gem implicitly claims to guarantee is:
`shop used by handler (request.shop from header) == shop that produced the signed body`

But the gem only proves:
`HMAC(client_secret, raw_body) == received_hmac`

These are independent facts. Because the app's `client_secret` is shared across every shop that has the app installed, an unprivileged party can install the app on their own store, capture a validly-signed `(raw_body, hmac)` pair for a webhook topic whose body content is fixed/predictable (e.g. `{}` bodies, or GDPR mandatory webhooks with attacker-influenced-but-known JSON), and replay those exact bytes to the app's public webhook endpoint while substituting an arbitrary victim shop domain in `X-Shopify-Shop-Domain`. The HMAC check still passes (it only checks the body), and `Registry.process` delivers the forged shop identity to the handler as if it were authentic.

### Impact Explanation
This is a direct analog of the reported bug class: an identity field (`shop`, akin to `owner`/`msg.sender` in the Staking example) is *acted upon* by downstream logic without being *covered by the authentication check* (HMAC), while a different, unrelated piece of data (the raw body) is what's actually verified. Any host application that trusts `WebhookMetadata#shop` (returned by this gem) to key session lookups, scope data writes, or route work per-tenant can be made to process/attribute data under the wrong merchant's identity — a cross-tenant confusion primitive rooted entirely in this gem's webhook verification contract, not in host-app misuse of an undocumented API (the gem's own `Registry.process`/`WebhookMetadata` explicitly exposes `shop` as the trusted identifier of the sender, sourced from this unauthenticated header).

### Likelihood Explanation
The header/body split is intrinsic to Shopify's webhook design (HMAC only ever signs the body), but this gem does nothing to compensate — it doesn't cross-check the header against a shop the app expects, doesn't rely on the delivery URL/topic-scoped webhook ID, and directly surfaces the raw header value as `shop` in the public `WebhookMetadata` API. Any actor able to install the app once (a normal, unprivileged developer action, not requiring any victim credentials) can obtain valid `(body, hmac)` pairs and replay them with a forged shop header against the app's public webhook endpoint.

### Recommendation
Do not treat `request.shop` as authenticated. At minimum, cross-validate the incoming `shop-domain` header against the shop that was used to register the specific `webhook_id` (via a lookup keyed by `webhook_id`, or by verifying the delivery came through a per-shop, opaque callback path) before dispatching to the handler; alternatively/additionally, include the shop domain in the signable string used for HMAC verification so the header itself becomes bound to the signature.

### Proof of Concept
1. Attacker installs the target app on their own dev store `attacker.myshopify.com`, obtaining the app's shared `client_secret`-signed webhook traffic for a topic with fixed body content (e.g. many mandatory/compliance topics send `{}` or a small deterministic JSON payload).
2. Attacker captures the legitimate `X-Shopify-Hmac-Sha256` value Shopify computed over that raw body.
3. Attacker sends that exact raw body and HMAC header to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the body bytes: [5](#0-4) 
5. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)`, believing the event genuinely originated from the victim shop, even though it never did.

          received_signature = verifiable_query.hmac
