This confirms the exact documented flow: the gem's own doc explicitly states `Registry.process` "will verify the request did indeed come from Shopify" based solely on the `ShopifyAPI::Webhooks::Request` object built from `raw_body` and `headers` [1](#0-0) , yet the HMAC only signs `@raw_body` while `shop`, `topic`, `webhook_id`, and `api_version` come from unauthenticated headers [2](#0-1) .

### Title
Webhook shop/topic/id attribution is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body [3](#0-2) . The `shop`, `topic`, `webhook_id`, and `api_version` values that are handed to the application's handler and used as the tenant/event identity are read straight from HTTP headers and are never included in the signed bytes, so they are not bound to the HMAC at all [4](#0-3) .

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [5](#0-4) , and `Utils::HmacValidator.validate_signature` computes/compares the HMAC exclusively against that string [6](#0-5) . Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are parsed out of headers that are completely outside the signed payload [7](#0-6) . `Registry.process` trusts these header-derived values directly when constructing `WebhookMetadata` passed to the app's handler: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))` [3](#0-2) .

Because the app's `client_secret`/`api_secret_key` is shared across every shop that installs the app, any party who can trigger one legitimate webhook delivery for their own shop (e.g. by installing the app and performing an action that fires a subscribed topic) obtains a valid `(raw_body, hmac)` pair signed with that same shared secret. Since the signature never covers the `shop`, `topic`, `webhook_id`, or `api_version` headers, that same `raw_body`+`hmac` pair can be replayed to the app's public webhook endpoint with a forged `x-shopify-shop-domain` (and/or `x-shopify-topic`) header pointing at a victim shop. `HmacValidator.validate` will still return `true` because it only re-derives the HMAC from the body [8](#0-7) , and `Registry.process` will dispatch the forged `shop`/`topic` straight to the handler as if Shopify itself had asserted that identity.

This is the same class of bug as the reported front-running issue: the report's `Whitelist`/`InvestmentPoolCore` bug is about an identity/state field (an address) being actionable without being properly bound to the authorization check that is supposed to gate the action. Here, the identity field that gates cross-tenant dispatch (`shop`) is likewise never bound to the cryptographic check (`HMAC`) that is supposed to prove authenticity of the whole webhook, breaking the equality `shop_verified_by_hmac == shop_used_by_handler` (the left side is actually undefined/empty, since HMAC never inspects `shop` at all).

### Impact Explanation
This breaks the tenant-authentication boundary the gem's `Registry.process`/HMAC check is documented to provide ("verify the request did indeed come from Shopify") [9](#0-8) . A host app that (as documented) trusts `data.shop` from the handler to scope work to a tenant (job queues, per-shop data writes, `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` per the gem's own example) [10](#0-9)  can be made to process attacker-supplied webhook bodies under an arbitrary victim shop's identity. This is a cross-tenant data-integrity/attribution bypass in the gem's authenticity check.

### Likelihood Explanation
Medium. It requires the attacker to (a) be or become a merchant who installs the target app (or otherwise obtain any single valid `(body, hmac)` pair for a subscribed topic — trivial once installed), and (b) send a crafted HTTP POST directly to the app's public webhook endpoint with the real `hmac` header but a forged `shop-domain`/`topic` header. No secret material is required; the endpoint is public by design.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable/verified payload — e.g. compute/verify the HMAC over a canonical string that binds `raw_body` together with these header values — instead of signing `raw_body` alone in `ShopifyAPI::Webhooks::Request#to_signable_string`. At minimum, document loudly that `Registry.process`'s HMAC check does not authenticate `shop`/`topic`/`webhook_id`, and warn integrators against trusting those fields for tenant scoping without additional verification (e.g., cross-checking against the shop's known/subscribed webhook IDs).

### Proof of Concept
```ruby
require "openssl"
require "base64"
require "digest"

secret = "shared_api_secret_key" # same for every shop of this app

# 1. Attacker owns "attacker-shop.myshopify.com" and installs the app.
#    They trigger a subscribed topic (e.g. "orders/create") and capture the
#    genuine webhook Shopify sends them:
raw_body = '{"id":1,"note":"hello"}'
hmac_digest = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, raw_body)
hmac_header = Base64.encode64(hmac_digest) # this is what Shopify would have sent

# 2. Attacker replays the SAME body+hmac to the app's public webhook endpoint,
#    but forges the shop-domain header to point at a victim shop:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => hmac_header,     # unchanged, still valid!
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged
  "x-shopify-webhook-id" => "forged-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# 3. HmacValidator.validate only checks the body against the shared secret,
#    so this passes even though shop/topic/webhook_id were never signed:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# 4. Registry.process dispatches to the handler believing this is a
#    legitimate webhook for "victim-shop.myshopify.com":
ShopifyAPI::Webhooks::Registry.process(request)
# handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
```
