### Title
Unrestricted arbitrary calls in `EmporiumUpgradeable.runAction` CASE 2 allow theft of any asset custodied by the shared Emporium contract - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction` executes fully attacker-controlled `op.endpoint.call(op.callData)` with `msg.sender == Emporium` whenever `stack.signerAddress == address(0)` (CASE 2, "Stateless Interaction"), and the only economic guard (`getBalancesForArray`/`balanceChange` check) covers exclusively the ERC20/ETH addresses the *caller themselves* lists in `circomData.erc20TokenAddresses` for that specific call. Any asset that ends up owned/held by the shared Emporium contract — most severely an ERC721/ERC1155 position that a prior CASE 2 interaction caused to be minted to `msg.sender` (i.e. to Emporium), or ERC20 dust simply not declared in the attacker's own token array — is completely invisible to this accounting and can be pulled out by any unrelated, unprivileged caller in a later transaction.

### Finding Description
Broken equality: `asset_owner(NFT_at_Emporium_after_victim_tx1) == victim.stealthAddress` is false; the true state is `asset_owner == address(EmporiumUpgradeable)`, a shared contract, so `claimable_by(NFT) != creator(NFT)`.

- CASE 2 in `runAction` performs a raw low-level call to any `op.endpoint` with any `op.callData` chosen by whoever supplies `circomData.externalActionData.externalActionMetadata`, with the only restriction being a check against `IHinkalWallet.callHinkalWallet`/`doSendToRelay` selectors: [1](#0-0) .
- The only value-conservation guard is built from `getBalancesForArray(circomData.erc20TokenAddresses)` taken before/after the ops loop, applied only to the caller-supplied `erc20TokenAddresses` array: [2](#0-1)  and [3](#0-2) . `getERC20OrETHBalance` only calls `balanceOf(address(this))`/`address(this).balance`, so it can never represent NFT ownership at all: [4](#0-3) .
- Anyone (an unprivileged EOA holding their own valid Hinkal UTXOs, or no funds at all) can drive this path: `Hinkal.transact()` → `_externalTransact` → `runAction`, where `runAction` is only gated by `onlyAllowedRecipient` (i.e. it must be invoked by the registered `Hinkal` contract), not by any check on the operation contents: [5](#0-4) , [6](#0-5) .
- Critically, the Emporium action can be driven by `MainEVMCircuitMin`, which only constrains `emporiumMessage`, `outTimeStamp`, `calldataHash` — no token or amount signals — and this circuit is selected precisely when `circomData.erc20TokenAddresses.length == 0`: [7](#0-6) , [8](#0-7) . With an empty `erc20TokenAddresses`, the balance-diff loop in `runAction` (and the mirrored loop in `Hinkal.transact()`) never executes, so **zero economic constraints** apply to the ops — an attacker doesn't even need real Hinkal balances to drain Emporium.
- `verifyWallet` provides no protection here either: when `stack.signerAddress == address(0)` it returns immediately without any signature check, only marking the attacker's own chosen `emporiumMessage` nonce as used: [9](#0-8) .

Exploit flow: victim's own (or any integrator's) CASE-2 interaction causes an external vault to mint/transfer an NFT position to `msg.sender`, which resolves to the shared `EmporiumUpgradeable` address (since Transferer implements `onERC721Received`, the NFT is accepted): [10](#0-9) . In a fully independent transaction, the attacker calls `Hinkal.transact()` with their own proof/nullifiers (optionally using the token-count-0 `MainEVMCircuitMin` path to bypass all balance checks) and `externalActionMetadata` ops = `[{endpoint: NFTVault, invokeWallet:false, callData: transferFrom(Emporium, attacker, tokenId)}]`. Since Emporium is the actual on-chain owner of the token, this call succeeds and the NFT/position moves to the attacker.

### Impact Explanation
Direct theft of a victim's in-flight/created position or any other asset (ERC20 dust, ERC721/1155 positions) sitting in the shared `EmporiumUpgradeable` contract, by any unprivileged third party who never held that asset. This is repeatable against every asset that transiently or persistently resides at the Emporium address, and is worsened by the zero-token `MainEVMCircuitMin` path, which removes all balance-conservation constraints from the call. This matches Critical: direct theft of shielded/in-flight user funds and execution of calls/movement of assets never authorized by the asset's actual owner.

### Likelihood Explanation
Preconditions: some asset must be resident at the `EmporiumUpgradeable` address — achievable whenever a CASE 2 ("Stateless Interaction") op interacts with any protocol that mints/transfers a position to `msg.sender` (a normal pattern for vault/LP/NFT-position contracts), or simply from ERC20 remainders not included in a given transaction's `erc20TokenAddresses`. The attacker needs no special privilege, no capital (can use the 0-token min circuit), and only needs to craft `EmporiumOperation.callData` targeting the known vault/token contract and known `tokenId`/amount. This is fully within reach of the defined "unprivileged attacker" and is trivially repeatable once identified.

### Recommendation
- Remove or heavily restrict CASE 2 arbitrary calls: require an allowlist of `op.endpoint` addresses (and ideally selectors) that `EmporiumUpgradeable` is permitted to call directly as itself, separate from the wallet-based CASE 1 flow.
- Never allow position-creating/receiving calls (anything that can leave an asset owned by `address(this)`, e.g., `onERC721Received`/`onERC1155Received` acceptance, or unaccounted ERC20 balances) to execute in "stateless" mode; force such interactions through per-user `HinkalWallet` instances (CASE 1) so custody is scoped to the individual user, not the shared Emporium.
- Track and constrain any non-ERC20 assets transferred as part of an Emporium action (e.g., require an explicit NFT/asset manifest in `circomData` and verify pre/post ownership deltas match declared recipients), and disallow using the zero-token `MainEVMCircuitMin` verifier for any action that performs `op.endpoint.call` with arbitrary calldata.

### Proof of Concept
Foundry fork test:
1. Deploy `EmporiumUpgradeable`, `Hinkal`, a mock ERC721 "vault" with `depositFor(address recipient, uint256 tokenId)` (mints/transfers `tokenId` to `recipient`) and `transferFrom`.
2. Victim runs `transact()` with `externalActionId = HINKAL_EMPORIUM_ACTION_ID`, ops = `[{endpoint: vault, invokeWallet:false, callData: depositFor(address(this) /* i.e. Emporium, resolved as msg.sender inside the vault call */, tokenId)}]`, `stack.signerAddress = address(0)`. Assert `vault.ownerOf(tokenId) == address(emporium)` after the call (confirms broken equality: NFT owner is Emporium, not the victim).
3. Attacker (different EOA, own nullifiers/proof, `circomData.erc20TokenAddresses = []` using the `MainEVMCircuitMin` verifier) calls `transact()` with ops = `[{endpoint: vault, invokeWallet:false, callData: transferFrom(address(emporium), attacker, tokenId)}]`.
4. Assert the call succeeds and `vault.ownerOf(tokenId) == attacker` afterward, while the victim never signed/authorized any transfer of `tokenId` to the attacker — proving theft.
