## Finding

### Title
Webhook shop identity not bound to HMAC signature enables cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw body only, while the `shop` (and `topic`/`webhook_id`) values used to attribute the webhook to a tenant come from unauthenticated HTTP headers. Because Shopify webhook HMACs are computed with the app's single `api_secret_key` (shared across every shop that installs the app), a body+HMAC pair legitimately obtained from one shop's webhook delivery remains valid when replayed with the `shopify-shop-domain` header rewritten to a different shop, letting an unprivileged merchant (or anyone who intercepts one of their own webhook deliveries) impersonate another tenant to the app.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Request#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header without any cross-check against the signed payload [2](#0-1) . `Utils::HmacValidator.validate` verifies only that `computed_signature` (HMAC of `to_signable_string`, i.e. the body) matches the received signature [3](#0-2) . `Webhooks::Registry.process` then trusts `request.shop` unconditionally after this body-only HMAC check passes and forwards it to the handler as the shop of record: [4](#0-3) .

The binding that should hold is: `shop-domain header == shop whose secret produced the HMAC over this body`. In fact only `hmac == HMAC(api_secret_key, body)` is checked; the header is never part of the signed material. Since Shopify signs app webhooks with the app's `client_secret`, which is identical for every shop that installs the app (not a per-shop secret), a valid `(body, hmac)` pair generated for shop A's webhook delivery still verifies successfully when the `shopify-shop-domain` header is swapped to shop B — the equality the code should be enforcing (header shop == signing shop) is broken while the equality it actually enforces (hmac == HMAC(secret, body)) still holds.

### Impact Explanation
An unprivileged internet user who merely installs the target app on their own store (a normal, unprivileged action) receives legitimate webhook deliveries with valid `(body, hmac)` pairs signed under the app's shared secret. By replaying that body with the HMAC unchanged but the `shopify-shop-domain` header rewritten to a victim shop's domain, they can make the app's webhook handler process their attacker-controlled body while attributing it to the victim's tenant (per `WebhookMetadata.new(topic:, shop: request.shop, body: request.parsed_body, ...)`). Any app logic keyed off `data.shop` (e.g., updating tenant records, triggering tenant-scoped side effects) is exposed to cross-tenant data injection/confusion — matching the "Critical: cross-tenant access" category.

### Likelihood Explanation
Exploitation requires no privileged credential, no `api_secret_key`, no stolen access token, and no TLS interception: the attacker only needs to be a legitimate (even free) merchant of the app to obtain one authentic `(body, hmac)` pair, then POST it to the app's own public webhook endpoint with a modified shop header — a capability available to any unprivileged internet user who installs the app.

### Recommendation
Bind the shop identity to the same authenticated material as the HMAC, e.g. include the shop domain (and topic) in the signed payload, verify `shop-domain` against a value already associated with that HMAC-verified body server-side, or use per-shop verification (compare against the shop associated with the webhook subscription id) rather than trusting the raw header directly in `Request#shop`.

### Proof of Concept
1. Attacker installs the vulnerable app on their own shop `attacker.myshopify.com` and captures a real webhook delivery: body `B` with header `x-shopify-hmac-sha256: HMAC(secret, B)` and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker sends the same body `B` and the same (still-valid) HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` (which only checks `HMAC(secret, B)`) succeeds [5](#0-4) .
4. `Registry.process` invokes the handler with `WebhookMetadata.new(... shop: "victim.myshopify.com", body: parsed(B) ...)` [4](#0-3) , causing the app to process attacker-controlled data under the victim's tenant identity.
