## Title
CORS wildcard-origin check uses unanchored suffix match, allowing origin spoofing via lookalike domains - (File: core/services/gateway/network/httpserver.go)

## Summary
`isAllowedOrigin` implements wildcard CORS-origin matching (`*.example.com`) by stripping the `*.` prefix and checking `strings.HasSuffix(originHost, allowedHost)` with no verification that the character preceding the matched suffix is a `.` label separator. This allows any hostname that merely ends with the configured suffix — including unrelated domains such as `evilethereum.org` matching an allowlist entry `*.ethereum.org` — to be treated as an allowed CORS origin, which the gateway then echoes back in `Access-Control-Allow-Origin`.

The vulnerable logic is confirmed exactly as described in `core/services/gateway/network/httpserver.go`: [1](#0-0)

`strings.HasSuffix("evilethereum.org", "ethereum.org")` returns `true` because there is no check that the preceding character is a `.`, so a fully unrelated domain that happens to end with the allowlisted suffix passes the wildcard check. The existing test suite only covers a non-subdomain case that doesn't share the suffix at all (`ethereum.remix.org` vs `*.ethereum.org`), which does not exercise this boundary-less-suffix scenario: [3](#0-2) 

No other validation (auth middleware, role checks, additional origin normalization) intervenes before this check; the `splitURL` helper only parses scheme/host/port and does not affect the suffix-matching flaw.

## Impact Explanation
This maps to an in-scope "cross-user response corruption / CORS bypass" style impact: an attacker-controlled origin, if accepted, is echoed into `Access-Control-Allow-Origin`, letting a page on the attacker's domain make cross-origin browser requests to the gateway and read JSON responses that should be restricted to the legitimate allowlisted subdomains. This is a real logic bug in the gateway's own code, not a misconfiguration by the operator — the wildcard feature is an intended, documented configuration mechanism (`CORSAllowedOrigins` supports `*.` prefix and is used exactly this way in `core/scripts/gateway/sample_config.toml`), and the flaw breaks the security guarantee that wildcard means "any subdomain of X," not "anything ending in X."

## Likelihood Explanation
Exploitability requires only that the operator has enabled CORS with at least one wildcard entry — a supported, intended configuration, not a misconfiguration — and that an attacker registers/controls a domain sharing the suffix without the dot boundary (cheap, since attacker fully controls domain registration). No authentication, node privilege, or special network position is needed; the trigger is a normal unauthenticated browser page setting a crafted `Origin` header.

## Recommendation
After stripping the `*.` prefix, require a proper label boundary: `originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost)` instead of a bare `strings.HasSuffix` check.

## Proof of Concept
1. Configure gateway with `CORSEnabled = true` and `CORSAllowedOrigins = ["https://*.ethereum.org"]`.
2. Attacker registers `evilethereum.org` and serves a page there.
3. Browser on that page sends `fetch(gatewayURL, {headers: {Origin: "https://evilethereum.org"}})`.
4. `isAllowedOrigin` strips the wildcard to `ethereum.org`; `strings.HasSuffix("evilethereum.org", "ethereum.org")` returns `true`, so the gateway responds with `Access-Control-Allow-Origin: https://evilethereum.org`, letting the attacker page read the gateway's response cross-origin — verifiable via a Go unit test analogous to the existing `TestHTTPServer_HandleRequest_CORSEnabled_FromNotAllowedOriginWildcards` but asserting the header IS set for `https://evilethereum.org`.
