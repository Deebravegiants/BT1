This confirms the finding: the gem's own documentation instructs developers to trust `data.shop` from `WebhookMetadata` as "The shop domain of the webhook" (`docs/usage/webhooks.md` line 14) after only calling `ShopifyAPI::Webhooks::Registry.process`, which the docs claim "will verify the request did indeed come from Shopify" (`docs/usage/webhooks.md` line 125). This is misleading: the verification only covers the body, not the shop-domain header.

### Title
Webhook shop-domain identity is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while the tenant-identifying `shop-domain` header is read separately and is never included in the signed payload. `ShopifyAPI::Webhooks::Registry.process` verifies the HMAC and then trusts `request.shop` as the tenant identity passed to the app's handler, so the equality "authenticated shop == HMAC-covered shop" never actually holds: the HMAC binds only the body, not the shop.

### Finding Description
`Request#to_signable_string` returns just `@raw_body`: [1](#0-0) . The `shop` accessor is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header without any cryptographic binding: [2](#0-1) .

`HmacValidator.validate` computes/compares the signature strictly against `verifiable_query.to_signable_string`, i.e., the body: [3](#0-2) .

`Registry.process` performs this HMAC check and then immediately forwards `request.shop` (the unauthenticated header) to the app's handler as the tenant identity: [4](#0-3) .

The gem's own documentation instructs integrators that `Registry.process` "will verify the request did indeed come from Shopify" and that `data.shop` is simply "The shop domain of the webhook": [5](#0-4)  and [6](#0-5) . This is precisely the bug class from the external report: a field (`shop`) that is acted upon downstream is not covered by the integrity check (`hmac`), so the equality `hmac-authenticated bytes == bytes the app trusts for tenant identity` is broken.

Because the API secret (`client_secret`) used to sign webhook payloads is shared across every shop that installs the app, a valid `(raw_body, hmac)` pair captured from a webhook legitimately delivered to an attacker's own store (an unprivileged merchant who installed the app) remains cryptographically valid when replayed to the app's public webhook endpoint with the `shopify-shop-domain` header changed to a victim shop. `HmacValidator.validate` still succeeds because it never inspects the header, and `Registry.process` hands `WebhookMetadata` with the attacker-chosen `shop` value to the handler.

### Impact Explanation
This crosses a tenant boundary: an attacker who is a legitimate but unprivileged installer of the app on their own shop can inject attacker-controlled webhook payloads (topic, body) that are processed by the app under a victim shop's identity. Depending on the handler (persisting orders, customers, fulfillment updates, GDPR data, etc. keyed by `data.shop`), this enables cross-tenant data corruption/injection — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
The attacker only needs (1) their own valid app installation to receive at least one genuine webhook delivery (trivial — any merchant using the app receives them, and dev/staging environments routinely proxy/log these), and (2) the ability to POST the captured `(raw_body, hmac)` pair to the app's known/shared webhook endpoint with a modified `shop-domain` header — an unauthenticated HTTP action requiring no secret, session, or token.

### Recommendation
Include the tenant-identifying headers (`shopify-shop-domain`, `shopify-webhook-id`, `shopify-topic`) in the HMAC-signable string, or otherwise cryptographically bind the shop to the signed payload (e.g. verify `shop` against a value derived from the payload itself, or require that `Registry.process` re-validate `shop` against an out-of-band trusted session/webhook-subscription record) before dispatching to handlers.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a normal event (e.g. creates an order), causing Shopify to deliver a legitimate webhook to the app's shared endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and some JSON `raw_body`.
2. Attacker captures this exact `raw_body` and `x-shopify-hmac-sha256` value (e.g., via a debugging proxy they control on their own endpoint).
3. Attacker sends a new POST to the same app webhook endpoint, keeping `raw_body` and `x-shopify-hmac-sha256` identical, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body successfully; `Utils::HmacValidator.validate` recomputes the HMAC over `raw_body` only and it matches, so `Registry.process` does not raise `Errors::InvalidWebhookError`.
5. The registered handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's JSON>, ...)` and processes attacker-controlled data as if it originated from `victim-shop.myshopify.com`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
