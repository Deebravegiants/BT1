### Title
System-originated cross-chain dispatches set zero relayer fee, so hyperbridge-originated requests are never delivered - (File: `modules/pallets/host-executive/src/lib.rs`)

### Summary
Analogous to the reported `xcall` issue (no relayer fee configured, so no relayer has an economic incentive to complete the cross-chain transaction), several Hyperbridge system pallets dispatch outgoing ISMP `PostRequest`s via `IsmpDispatcher::dispatch_request` with `FeeMetadata { payer: [0u8; 32].into(), fee: Default::default() }` — i.e., zero relayer fee and a null payer. This means no unprivileged relayer/tesseract operator is economically compensated for delivering these messages to their destination.

### Finding Description
`pallet-ismp`'s dispatcher escrows `fee.fee` from `fee.payer` into `RELAYER_FEE_ACCOUNT` at dispatch time; that escrow is what a delivering relayer later claims via the fee-accumulation flow [1](#0-0) . Several pallets that originate cross-chain requests bypass any real fee funding and dispatch with a zero-value, zero-payer `FeeMetadata`:

- `pallet-host-executive::update_host_params`, which propagates critical host parameter updates (e.g. manager rotation) to destination EVM hosts, dispatches with `FeeMetadata { payer: [0u8; 32].into(), fee: Default::default() }` [2](#0-1) .
- The same zero-fee/zero-payer pattern is used in `modules/pallets/intents-coprocessor/src/lib.rs`, `modules/pallets/relayer/src/withdrawal.rs`, and `modules/pallets/state-coprocessor/src/impls.rs` [2](#0-1) .

This is explicitly documented as a known, unresolved gap: "these all dispatch with `FeeMetadata { payer: [0u8; 32].into(), fee: Default::default() }` ... Zero fee, zero payer. So relayers have no economic reason to pick them up, and the only thing that keeps them flowing today is altruism." [3](#0-2) 

Because delivery is entirely dependent on `Tesseract` relayers voluntarily fetching and submitting these unrewarded messages, and the outbound relaying economic model is explicitly fee-driven ("Outbound delivery is funded by the user... The relayer that delivers the message to its destination claims the user-posted fee"), messages dispatched with zero fee have no guaranteed delivery path [4](#0-3) .

### Impact Explanation
`update_host_params` is used to propagate host manager rotations and other critical host parameter changes to destination EVM hosts [5](#0-4) . If no altruistic relayer delivers this message, the destination `EvmHost`'s parameters (including manager address) never get updated, leaving destination chains with stale/incorrect host configuration — a route unable to deliver critical protocol-governance messages. Similarly, `pallet-relayer`'s withdrawal dispatch instructs a destination host manager to disburse accumulated relayer fees to a beneficiary [6](#0-5) ; if that withdrawal request is never relayed (no incentive), relayers' earned fees become permanently stuck/undeliverable, freezing funds that are otherwise accounted for as claimable. Both cases represent liveness failures of a core, unprivileged messaging path (relayer fee/reward accounting and host-parameter propagation).

### Likelihood Explanation
Likelihood is high in the absence of goodwill relaying: any operator running Tesseract has no reason to pick up a zero-fee message over fee-bearing user traffic, especially under load or on chains where they aren't already relaying for other reasons. This is acknowledged directly in the project's own documentation as an open problem, tracked upstream (`polytope-labs/hyperbridge#532`) [7](#0-6) , indicating the maintainers already recognize the current state as broken/unreliable, not merely theoretical.

### Recommendation
Implement the reward mechanism already scoped in `docs/outbound-request-incentivization.md`: introduce a `pallet-relayer` module-keyed reward (e.g. `OutboundRequestDeliveryReward`) paid from the treasury when a relayer proves delivery of a hyperbridge-originated request, mirroring the existing `claim_outbound_consensus_delivery_reward` flow [8](#0-7) , rather than leaving `host-executive`, `intents-coprocessor`, `relayer::withdrawal`, and `state-coprocessor` dispatch sites with zero fee/zero payer.

### Proof of Concept
1. Governance calls `pallet_host_executive::update_host_params` to rotate the manager on a destination EVM host.
2. The call dispatches `DispatchRequest::Post(post)` with `FeeMetadata { payer: [0u8; 32].into(), fee: Default::default() }` [2](#0-1) .
3. `pallet-ismp`'s dispatcher skips the fee-escrow branch because `fee.fee == Zero::zero()` [9](#0-8) , so no funds are escrowed for a relayer.
4. No Tesseract relayer has an economic incentive to include this message in an outbound batch, since outbound delivery rewards are funded strictly from the user-attached fee claimed on the source chain [4](#0-3) .
5. The request commitment sits undelivered indefinitely (or until an altruistic operator relays it), leaving the destination host's parameters stale.

```rust
		&self,
		request: DispatchRequest,
		fee: FeeMetadata<T>,

		// collect payment for the request
		if fee.fee != Zero::zero() {
			T::Currency::transfer(

				&RELAYER_FEE_ACCOUNT.into_account_truncating(),
				fee.fee,
				Preservation::Expendable,
			)
			.map_err(|err| IsmpError::Custom(format!("Error withdrawing request fees: {err:?}")))?;
		}
```

```rust
				dest: state_machine,
				from: PALLET_ID.to_bytes(),
				to: current_manager.0.to_vec(),

			};
```

```markdown
# Outbound Request Delivery Incentivization

How relayers that deliver a hyperbridge-originated request to a destination chain get paid in BRIDGE from the Hyperbridge treasury.

Tracking issue: [polytope-labs/hyperbridge#532](https://github.com/polytope-labs/hyperbridge/issues/532).

## The problem

A regular cross-chain message that flows *through* hyperbridge has a fee attached at origin (the source chain transfers `fee.payer → RELAYER_FEE_ACCOUNT` and records `RequestPayments[commitment]` in pallet-hyperbridge's child trie). When a relayer delivers and the destination receipt lands back on hyperbridge, the existing `accumulate_fees` flow credits that fee to the relayer. That whole pipeline assumes a *user* paid at origin.

But hyperbridge itself originates requests too: host parameter propagation, host-executive updates, intents-coprocessor responses, token-governor messages, the relayer pallet's withdrawal request. Today these all dispatch with `FeeMetadata { payer: [0u8; 32].into(), fee: Default::default() }` (see `modules/pallets/host-executive/src/lib.rs:228`, `modules/pallets/intents-coprocessor/src/lib.rs:486`, `modules/pallets/relayer/src/lib.rs:638`, and `modules/pallets/token-governor/src/impls.rs`). Zero fee, zero payer. So relayers have no economic reason to pick them up, and the only thing that keeps them flowing today is altruism.
```

```markdown
The issue creator's preferred shape ([comment 4428807013](https://github.com/polytope-labs/hyperbridge/issues/532#issuecomment-4428807013)): use `pallet-relayer` to pay BRIDGE to whoever proves they delivered a hyperbridge-originated request. The messaging task in the tesseract relayer submits the claim.

Not every pallet on hyperbridge that dispatches a request is in scope. `pallet_ismp::child_trie::RequestCommitments` ends up holding commitments for every successful dispatch via `IsmpDispatcher`, which includes both the system messages we want to incentivize (host-executive, intents-coprocessor, token-governor, the relayer pallet's withdrawal path, future modules like bandwidth) and any other pallet that ends up dispatching from hyperbridge. The reward storage is therefore keyed by `source_module_id` and only modules with a non-zero reward are eligible. The `module_id` is the `from` field on the `PostRequest`, which each pallet sets to its unique module identifier. A module with zero reward is treated as not on the allowlist and rejected before any state proof verification runs.

This is structurally identical to the existing `claim_outbound_consensus_delivery_reward` (see `modules/pallets/relayer/src/outbound_consensus.rs`) on the consensus side. The request claim lives in its own `modules/pallets/relayer/src/outbound_request.rs` module that mirrors it: swap "consensus rotation delivered" for "request delivered," key the reward storage by `module_id`, and have the relayer ship the full `PostRequest` in the claim so the pallet can hash it on chain.

No changes to pallet-hyperbridge or to any of the system-message dispatch sites. The reward is decoupled from the dispatch path and paid out at claim time against a destination state proof.
```

```text
### Economic model

Outbound delivery is funded by the user, not the protocol. When
dispatching a request, the user attaches a fee on the **source chain**
in an ERC-20 stablecoin chosen per host at deployment time. `DAI` is
the typical choice on EVM hosts for its decentralized properties,
though the host stores a configurable `feeToken` address that
governance can update without a redeploy.

The relayer that delivers the message to its destination claims the
user-posted fee on the source chain. Concretely, after a successful
destination submission the tesseract process submits a delivery proof
to Hyperbridge, which credits the relayer's unclaimed balance.
```

```rust
//! Once fees have been accumulated into [`crate::pallet::Fees`] by

//! The flow:

//! 3. The `Fees` entry is zeroed so the same balance cannot be withdrawn twice.
//!
//! The on-chain effect is just dispatching the message; the destination chain settles the
```
