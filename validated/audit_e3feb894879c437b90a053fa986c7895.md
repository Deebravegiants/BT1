### Title
Unvalidated dApp/WalletConnect-supplied strings stored via `personalNotes.upsert` and rendered/exported without sanitization - (File: features/personal-notes/module/index.js)

### Summary
`personalNotes.upsert` accepts free-form strings (`message`, `username`, `dapp`, `providerData.origin`, `walletConnect.dappName/dappUrl`) that originate from external, untrusted dApps connecting to the wallet (e.g., via WalletConnect or an injected provider), stores them with no format/length/character validation, syncs them across the user's devices via fusion, and later surfaces them verbatim in the activity feed UI and in CSV transaction exports. This mirrors the Rocketpool analog: untrusted external strings are persisted with only trivial checks and consumed downstream without sanitization, creating an injection surface in rendered/exported output.

### Finding Description
The `personalNotes` API definition declares `upsert` accepting `message`, `username`, `dapp: Record<string, any>`, `providerData: { origin, network }`, and `walletConnect: { dappName, dappUrl }` as free-form inputs [1](#0-0) . These fields are explicitly documented as being populated by "platforms features" i.e., data coming from connected dApps [2](#0-1) .

The module's `upsert` implementation passes these values straight into the `PersonalNote` model with no validation beyond truthiness checks, and merges/updates them without any sanitization: [3](#0-2) 

The underlying `PersonalNote` model only asserts that `txId` is a string; `message` and all other custom props (`username`, `dapp`, `providerData`, `walletConnect`) are accepted as-is via `Object.assign(this, props)`, with no length limit, no character allowlist, and no stripping of control characters: [4](#0-3) 

This is a direct analog of the Rocketpool `setTimezoneLocation`/email issue, where a minimally-validated field can carry arbitrary attacker-controlled content through the storage layer into presentation layers.

Downstream, these notes are:
1. Synced across the user's own devices via a `fusion` channel (`personalNoteSet`), so any device receiving synced data renders it [5](#0-4) .
2. Joined directly into activity items and displayed in the transaction feed via selectors such as `createWithConnectionsActivity`, which reads `personalNote?.providerData?.origin` directly from the untrusted payload [6](#0-5) .
3. Concatenated into CSV export rows in `formatTransactionOutput`, where `personalNote?.getMessage()` values are joined with `' | '` and placed into a `personalNote` field of the exported row with no escaping or CSV-injection mitigation (e.g., no neutralizing of leading `=`, `+`, `-`, `@` characters that trigger formula execution in spreadsheet applications): [7](#0-6) 

I was unable to fully confirm the exact serialization library used to write the final CSV/export file (`features/export-transactions/module/utils.js` only builds the row object; the writer itself was not located in the indexed files), so it is uncertain whether any escaping happens at the final serialization step. This should be verified directly in the `features/export-transactions` package.

### Impact Explanation
A malicious or compromised dApp that a user connects to (via WalletConnect or an injected provider) can supply arbitrary strings as `username`, `dapp.*`, `providerData.origin`, or `walletConnect.dappName/dappUrl`. Because these are stored without sanitization and later:
- Rendered in the wallet's transaction/activity UI (spoofing risk — e.g., displaying a fake "origin"/dApp name next to a transaction to mislead the user about what they interacted with), and
- Exported into CSV files without apparent formula/control-character sanitization (CSV/formula injection risk when the exported file is opened in spreadsheet software, and potential terminal/control-character injection if the export is later `cat`'d or processed by another tool),

this can be used for social engineering (displaying misleading transaction context to trick a user into approving future signing requests) and for injection into downstream consumer applications (spreadsheet formula injection, or corrupting log/terminal output). This does not directly yield unauthorized signing or key compromise on its own, but it materially weakens the trust boundary between untrusted dApp input and rendered/exported wallet data — directly matching the reported bug class (lax validation of untrusted strings that get persisted and later displayed/exported).

### Likelihood Explanation
Likelihood is moderate-to-high: any dApp a user connects to via WalletConnect can trigger `personalNotes.upsert` with attacker-controlled `dappName`, `dappUrl`, `username`, or `providerData.origin`, since the API imposes no format or length constraints (confirmed by the model and module code cited above). No special privilege is required beyond a normal dApp connection, which is a standard, low-friction interaction for wallet users.

### Recommendation
- Enforce strict validation/sanitization on all dApp-controlled fields (`username`, `dapp`, `providerData.origin`, `walletConnect.dappName`, `walletConnect.dappUrl`, `message`) at the `PersonalNote` model level and in `personalNotes.upsert`: cap lengths, strip/reject non-printable and control characters, and validate `origin`/`dappUrl` as well-formed URLs.
- Sanitize/escape all personal-note-derived fields before CSV export in `features/export-transactions/module/utils.js` (neutralize leading `=`, `+`, `-`, `@` to prevent formula injection, and strip control characters).
- Clearly label in the UI that `username`/`dapp`/`providerData` fields are attacker-controlled/unverified metadata, and avoid using them to make trust-implying UI decisions.

### Proof of Concept
1. Connect a malicious dApp to the wallet via WalletConnect.
2. Have the dApp trigger a call equivalent to:
```js
exodus.personalNotes.upsert({
  txId: '<victim-tx-id>',
  walletConnect: { dappName: '=cmd|\' /C calc\'!A0', dappUrl: 'javascript:alert(1)' },
  providerData: { origin: 'Balance: 1000 RPL\nStatus: Trusted' },
})
```
3. Observe that `PersonalNote` stores these values unmodified [4](#0-3) .
4. Export transaction history; the injected content flows unescaped into `formatTransactionOutput`'s `personalNote` field [7](#0-6) , and opening the resulting file in a spreadsheet application may trigger formula execution if the export writer does not separately escape it (unverified — see note above).

  upsert = async ({
    txId,
    message = '',
    username,
    address,
    dapp,
    providerData,
    walletConnect,
    xmrInputs,
  }) => {
    const personalNotes = await this.#personalNotesAtom.get()
    if (!txId) {
      throw new Error('provide txId to set personal note')
    }

    const prevPersonalNote = personalNotes.get(txId)
    let personalNote =
      prevPersonalNote ||
      PersonalNote.fromJSON(
        pickBy(
          {
            txId,
            message: '',
            dapp,
            username,
            providerData,
            walletConnect,
            xmrInputs,
          },
          identity
        )
      )
    if (prevPersonalNote?.dapp || dapp) {
      personalNote = personalNote.update({ dapp: merge({}, personalNote.dapp, dapp) })
    }

    if (prevPersonalNote?.username || username) {
      personalNote = personalNote.update({ username })
    }

    if (prevPersonalNote?.providerData || providerData) {
      personalNote = personalNote.update({ providerData })
    }

    if (prevPersonalNote?.walletConnect || walletConnect) {
      personalNote = personalNote.update({ walletConnect })
    }

    if (prevPersonalNote?.xmrInputs || xmrInputs) {
      personalNote = personalNote.update({ xmrInputs })
    }

    personalNote = personalNote.setMessage({ to: address, message })
    await this.#update([personalNote])
  }
