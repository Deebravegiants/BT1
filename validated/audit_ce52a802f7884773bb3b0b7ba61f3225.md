### Title
Webhook `shop` and `topic` fields are trusted for routing/handler dispatch without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity by HMAC-validating only the raw request body, while the `shop` and `topic` values used to route the webhook to a handler and to identify the tenant are taken from HTTP headers that are never included in the signed material. This breaks the intended binding "HMAC-verified bytes == the shop/topic the handler acts on."

### Finding Description
`Webhooks::Registry.process` validates a webhook using `Utils::HmacValidator.validate(request)`: [1](#0-0) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` — the raw JSON payload: [3](#0-2) 

But `shop`, `topic`, `api_version`, and `webhook_id`, which are used by `Registry.process` to dispatch to a handler and are handed to application code via `WebhookMetadata`, are parsed straight from attacker-controllable HTTP headers with no cryptographic binding to the signed body: [4](#0-3) [5](#0-4) 

This is structurally the same class of bug as the reported issue: a value that is *acted upon* (here, `shop`/`topic` used for tenant identification and handler routing) is not actually covered by the cryptographic check that is supposed to guarantee its authenticity (here, the HMAC only covers the body). In the Shopify webhook protocol, the HMAC header itself is computed by Shopify only over the body — this is documented/expected on Shopify's side, but it means this library's `shop` field (surfaced to consuming application code as an authenticated tenant identifier) is not actually authenticated by the signature check performed here.

### Impact Explanation
If an attacker can reach the app's webhook endpoint (a public HTTP endpoint by design) and forge a POST with a body that happens to match a previously-observed valid `(body, hmac)` pair for a real webhook from the merchant's shop, or more directly, if the host application (per this gem's documented `WebhookMetadata#shop` contract) trusts `data.shop` as a verified tenant identifier for tenant-scoped writes/lookups, an attacker can send an arbitrary `x-shopify-shop-domain` / `shopify-shop-domain` header alongside a validly-signed body (e.g., replaying a webhook whose body is generic or attacker-influenceable) and cause the handler to process data under a different tenant identity than the one Shopify actually sent it for. This crosses the tenant boundary this gem is documented to certify via `WebhookMetadata`, potentially causing cross-tenant data confusion in the host app (e.g., a "customers/redact" or "shop/redact" webhook processed under the wrong shop). This maps to the Critical "cross-tenant access" category, contingent on how strongly host apps rely on `WebhookMetadata#shop` as an authenticated value — which this gem's API surface (`WebhookMetadata.new(shop: request.shop, ...)`) explicitly presents as trustworthy output of `Registry.process`, a method whose whole purpose is verification.

### Likelihood Explanation
Exploitability requires the attacker to produce a request whose raw body/HMAC pair is valid (e.g., by capturing/replaying a real webhook delivery, which is possible for an unprivileged network attacker with visibility into webhook traffic, or for topics with attacker-influenced/static bodies) while freely varying the `shop-domain` header, since that header is completely outside the signed scope. This does not require the `api_secret_key` or any credential — only the ability to send an HTTP request to the app's public webhook endpoint and knowledge/possession of one valid `(body, hmac)` pair, which is realistic given webhook payloads are often somewhat predictable or replayable across shops using the same webhook secret setup pattern.

### Recommendation
Include the `shop` (and ideally `topic`) values in the signed/verified material, or otherwise cryptographically bind them to the verified body before they are surfaced through `WebhookMetadata`. At minimum, document clearly that `WebhookMetadata#shop`/`#topic` are unauthenticated header values and must be independently cross-checked by the host application against a known/registered shop before being used for tenant-scoped operations.

### Proof of Concept
1. Capture one legitimate webhook delivery for shop `victim-shop.myshopify.com` — record `raw_body` and its `x-shopify-hmac-sha256` value (computed by Shopify over the body only).
2. Replay the exact same `raw_body` and `hmac` header, but set `x-shopify-shop-domain: attacker-shop.myshopify.com` (or any other shop domain).
3. Send this crafted request to the app's public webhook endpoint that calls `ShopifyAPI::Webhooks::Registry.process(request)`.
4. `Utils::HmacValidator.validate(request)` succeeds because it only checks `raw_body`/`hmac` — the tampered `shop-domain` header is never checked.
5. `Registry.process` calls the registered handler with `WebhookMetadata.new(topic:, shop: request.shop, body:, ...)`, i.e., `shop` is `attacker-shop.myshopify.com`, even though the payload actually originated (per HMAC) from `victim-shop.myshopify.com`'s webhook subscription — demonstrating shop/tenant field is unauthenticated relative to the HMAC check performed by this gem.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
