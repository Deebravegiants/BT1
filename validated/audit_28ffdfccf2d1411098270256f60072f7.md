### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook forgery via replay - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [1](#0-0) , while the tenant-identifying value used by the handler, `shop` (`x-shopify-shop-domain` header), is read directly from an unauthenticated header [2](#0-1) . `Registry.process` only checks `Utils::HmacValidator.validate(request)` (which verifies the body against the HMAC) and then forwards `request.shop` straight into the handler without any additional binding check [3](#0-2) . This is the same bug class as the referenced report: "a field acted on but not covered by the HMAC."

### Finding Description
The equality that should hold is:
`bytes_covered_by_hmac == bytes_the_handler_trusts_for_tenant_identity`

Here that is false: `HmacValidator.validate_signature` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it only to the received `hmac` [4](#0-3) . For `Webhooks::Request`, `to_signable_string` is `@raw_body` only [1](#0-0)  — none of `topic`, `shop`, `api_version`, or `webhook_id` (all read from headers) are part of the signed material [5](#0-4) .

`Registry.process` validates the HMAC, then dispatches `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` to the app-provided handler, without verifying that `shop` corresponds to a shop the app actually expects for this signed payload [3](#0-2) .

Because `secure_compare` only binds the request to the body bytes, an attacker who can obtain one legitimate `(raw_body, hmac)` pair — e.g., by installing the app on a shop they control and capturing a real webhook delivery for their own store — can replay that exact body+hmac pair to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. `HmacValidator.validate` will pass (body and hmac are unchanged and valid), yet `request.shop` will resolve to the attacker-chosen value, letting the forged event be processed and attributed to a different, victim tenant.

### Impact Explanation
This crosses a tenant boundary defined by `shop`: the HMAC only authenticates "this body came from Shopify for some shop that had this exact payload," not "this body belongs to shop X." Any app whose webhook handler uses `WebhookMetadata#shop` to select a tenant record, credentials, or perform a write keyed by shop (a normal and expected usage pattern) can be made to perform actions or persist attacker-controlled webhook data against another merchant's tenant. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Requires only: (1) the attacker be able to install the target app on a shop they control (a normal/legitimate merchant action, not a privileged one), (2) the attacker be able to trigger a webhook event with a body of their choosing/knowledge, and (3) the attacker be able to send an arbitrary HTTP POST with custom headers to the app's public webhook endpoint (which is inherently internet-reachable, since Shopify itself must be able to reach it). No secret material, no TLS interception, and no social engineering are required — the attack is a straightforward header substitution on a replayed, still-validly-signed body. This is realistic and does not depend on the host app ignoring documented behavior, since the gem's own `to_signable_string` implementation is what excludes the header fields from the signature.

### Recommendation
Include the tenant-identifying header fields (`shop`, and ideally `topic`) in the signable string used by `Webhooks::Request`, or otherwise cryptographically bind them to the signed payload, so that `HmacValidator.validate` fails if `shop`/`topic` are altered independently of the body. At minimum, document and/or enforce in `Registry.process` that `request.shop` must be cross-checked against an expected/registered shop before invoking the handler, rather than trusting the header value unconditionally once only the body has been HMAC-verified.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers a webhook event with body `B` (e.g. `orders/create` with `{"id":1}`).
2. Attacker captures the resulting legitimate request: headers `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, body `B`.
3. Attacker sends a new POST to the app's webhook endpoint with the same body `B` and same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and compares to `H` — this succeeds because `B` is unchanged [6](#0-5) .
5. `handler.handle` is invoked with `shop: "victim-shop.myshopify.com"` [7](#0-6) , causing the app to process attacker-controlled webhook content under the victim's tenant context.
