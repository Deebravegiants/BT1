### Title
Panic-on-untrusted-consensus-data via `.expect()` unwraps in BEEFY U256→primitive conversions - ([File: evm/rust/src/conversions.rs])

### Summary
CVE-2015-8776 is a class of bug where an out-of-range/attacker-influenced time or numeric value that should be validated is instead fed into a conversion routine that aborts the process instead of returning an error. The Hyperbridge analog is in `evm/rust/src/conversions.rs`, where every `U256` field coming out of the Solidity BEEFY/SP1-BEEFY ABI types (`Commitment`, `BeefyConsensusState`, `BeefyMmrLeaf`, `PartialBeefyMmrLeaf`, `ParachainProof`, `Vote`, and the `IntermediateState.commitment.timestamp` conversion) is converted with `.try_into().expect("... out of bounds")` rather than a fallible/error-returning path.

### Finding Description
The BEEFY/SP1-BEEFY numeric fields (`blockNumber`, `validatorSetId`, authority-set `id`/`len`, MMR `leafIndex`/`parentNumber`, `leafCount`, vote `authorityIndex`, parachain `id`/`index`, and the state-commitment `timestamp`) are declared as `uint256` on the Solidity side [1](#0-0)  and are populated from data that a relayer/prover submits and that is only partially bounds-checked by the contract (e.g. the timestamp is decoded straight from the parachain header's ISMP digest with `ScaleCodec.decodeUint256`, with only a "nonzero" sanity check) [2](#0-1) .

When this same proof/state data is processed on the Rust side (used by the SP1 zk-prover pipeline and other off-chain tooling built on this crate) via `evm/rust/src/conversions.rs`, every one of these values is narrowed with `try_into().expect(...)` instead of being propagated as an error: [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

Since these conversions run over data that is under the control of whoever supplies the "proof"/parachain header being converted (block numbers, validator set ids, MMR leaf indices, and the timestamp digest are all attacker-influenced inputs prior to full on-chain verification, exactly like the untrusted `time_t` value handed to `strftime`), a value that does not fit into the target primitive (`u32`/`u64`/`u8`) triggers a Rust panic rather than a handled error. This mirrors CVE-2015-8776's root cause: an out-of-range externally-supplied value reaching an unchecked conversion routine and crashing the process instead of being rejected gracefully.

### Impact Explanation
A panic in this conversion path aborts the executing process. Because this crate underlies the BEEFY/SP1-BEEFY off-chain proof-generation and message-processing pipeline (any component that decodes `IntermediateState`, `Commitment`, `BeefyMmrLeaf`, etc. from submitted proof bytes before or during zk-proof generation), a single crafted proof/header with a `uint256` field exceeding `u32::MAX`/`u64::MAX`/`u8::MAX` can crash that component. If it runs as a long-lived service (prover/relayer), this is a denial-of-service on the consensus-update/message-relay pipeline for that route, i.e. "a route unable to deliver messages" until manually restarted — the same crash-class impact class as the glibc `strftime` bug.

### Likelihood Explanation
Reachability requires only submitting a BEEFY/SP1-BEEFY consensus proof (or parachain header bytes feeding `IntermediateState`) with one numeric field larger than what the target native type allows — no privileged role is needed, any unprivileged relayer/prover-submitter can supply such data because the values (block number, validator set id, leaf index, timestamp, vote index, parachain id) are attacker/relayer-controlled before this Rust-side conversion runs. The Solidity contracts themselves treat these as plain `uint256` with no upper-bound check before this data is handed off to the Rust conversion layer.

### Recommendation
Replace every `.try_into().expect("... out of bounds")` in `evm/rust/src/conversions.rs` with fallible conversions that propagate a typed error (`TryFrom` returning `Result`, or explicit range checks) instead of panicking, so malformed/oversized proof data is rejected rather than crashing the process.

### Proof of Concept
1. Craft a `BeefyConsensusProof`/`IntermediateState` (or any of the affected structs) where a numeric field normally expected to fit `u32`/`u64`/`u8` (e.g., `Commitment.blockNumber`, `BeefyMmrLeaf.leafIndex`, `ParachainProof.leafCount`, `Vote.authorityIndex`, or `IntermediateState.commitment.timestamp`) is set to a value `> u64::MAX` (or `> u32::MAX`/`u8::MAX` as appropriate for the target field).
2. Submit this data through the path that invokes the Rust-side `From`/`TryFrom` conversions in `evm/rust/src/conversions.rs` (e.g., during SP1 proof generation/verification tooling that decodes the on-chain ABI structs into the local `beefy_verifier_primitives`/`local::IntermediateState` types).
3. Observe the process panics at the corresponding `.expect("... out of bounds")` call site, aborting the service instead of returning a decode error.

    /// @dev Extracts the ISMP MMR root, child trie root, and timestamp from the header
    /// digests and returns them as a StateCommitment. Reverts if no timestamp digest is found.
    function stateCommitment(Header memory self) internal pure returns (StateCommitment memory) {
        bytes32 mmrRoot;
        bytes32 childTrieRoot;
        uint256 timestamp;

        for (uint256 j = 0; j < self.digests.length; j++) {
            if (self.digests[j].isConsensus && self.digests[j].consensus.consensusId == ISMP_CONSENSUS_ID) {
                mmrRoot = Bytes.toBytes32(Bytes.substr(self.digests[j].consensus.data, 0, 32));
                childTrieRoot = Bytes.toBytes32(Bytes.substr(self.digests[j].consensus.data, 32));
            }

            if (self.digests[j].isConsensus && self.digests[j].consensus.consensusId == ISMP_TIMESTAMP_ID) {
                timestamp = ScaleCodec.decodeUint256(self.digests[j].consensus.data);
            }
        }

        // sanity check
        if (timestamp == 0) revert TimestampNotFound();

        return StateCommitment({timestamp: timestamp, overlayRoot: mmrRoot, stateRoot: childTrieRoot});
    }

	impl From<Commitment> for SpCommitment {
		/// BEEFY commitment reconstruction. Reassembles the `Payload` from its
		/// `(id, data)` entries, starting with the first entry and pushing the rest via
		/// `push_raw` (which re-sorts by id to keep the invariant `Payload` expects).
		fn from(value: Commitment) -> Self {
			let mut iter = value.payload.into_iter();
			let first = iter.next().expect("commitment has at least one payload entry");
			let mut payload = BeefyPayload::from_single_entry(first.id.0, first.data.to_vec());
			for p in iter {
				payload = payload.push_raw(p.id.0, p.data.to_vec());
			}
			sp_consensus_beefy::Commitment {
				payload,
				block_number: value.blockNumber.try_into().expect("block number out of bounds"),
				validator_set_id: value
					.validatorSetId
					.try_into()
					.expect("validator set id out of bounds"),
			}
