### Title
Deposit-side seize unconditionally reclassifies supply shares as protocol revenue without distinguishing SeizeMode, corrupting `supplied`/`revenue`/`cash` accounting - (File: contracts/pool/src/ops/seize.rs)

### Summary
The pool's `seize` entry point treats every deposit-side seizure identically: it calls `Cache::absorb_supply_as_revenue`, which only increases `revenue` and leaves `supplied` and `cash` untouched. This is correct only for the internal share-credit path. For the liquidation `SeizeMode::Transfer` path — where the controller moves the seized collateral's underlying tokens out of the pool to the liquidator — the pool still only reclassifies the shares and never debits `cash` or burns the shares from `supplied`. The result mirrors the reported bug class: a state-changing path records claims (revenue shares) without updating the tracked asset side, so the book keeps tokens that have physically left and double-counts shares that were already claimed.

### Finding Description
`seize::apply` dispatches purely on `entry.side` [1](#0-0) . For `AccountPositionType::Deposit` it always executes `cache.absorb_supply_as_revenue(position)`, which does `revenue += shares` while `supplied` is unchanged and no cash is moved [2](#0-1) . The doc comment confirms the intent: "Reclassifying seized collateral as revenue leaves total supply unchanged" and "no cash moves" [3](#0-2) .

The controller, however, supports two seizure outcomes during liquidation: `SeizeMode::Credit` (collateral shares credited to the liquidator's position inside `supplied`) and `SeizeMode::Transfer` (underlying tokens paid out to the liquidator). The `PoolSeizeEntry` wire type carries no mode field — only `hub_asset`, `position`, and `side` — so the pool cannot distinguish them and applies the same revenue reclassification in both cases.

Two distinct corruptions follow:

- **Credit mode:** the liquidator's supply position is credited with the seized shares while `absorb_supply_as_revenue` simultaneously assigns those same shares to `revenue`. `revenue <= supplied` still passes [4](#0-3) , but the same shares are now owned by two claimants — the classic "shares minted without updating totals" defect from the reference report. When either claimant redeems, other suppliers' withdrawals compute against an overstated `supplied` and hit `require_reserves`/`debit_cash` failures [5](#0-4) .
- **Transfer mode:** tokens leave via `transfer_out`, which explicitly does not adjust accounting cash [6](#0-5) . Since `seize` performs no `debit_cash` and no `burn_supply`, tracked `cash` and `supplied` both overstate reality — the book claims tokens and shares that no longer exist. Contrast with `withdraw::accounting`, which burns supply shares and debits cash for the net transfer [7](#0-6) , and `borrow::accounting`, which pairs every debt mint with a cash debit [8](#0-7) . `seize` is the only value-moving op that performs neither burn nor cash debit.

Any unprivileged address can reach this via `liquidate` on an account whose health factor is below threshold, whenever the liquidation planner selects the Transfer seizure leg for a collateral market.

### Impact Explanation
Protocol insolvency and freezing of user funds. Each Transfer-mode deposit seizure leaves `cash` and `supplied` inflated by the seized leg: `backing_shortfall` (`floor(supply_value) - (cash + ceil(debt_value))` [9](#0-8) ) stays at zero while real reserves fell, so `require_backed_market` keeps admitting new suppliers into an under-backed book. Each Credit-mode seizure double-assigns shares, inflating claims beyond backing. In both cases, honest suppliers later find withdrawals reverting on `InsufficientLiquidity` or paying out less than their floor-valued claim — i.e., tokens were extracted by liquidators while the accounting layer pretended nothing left, exactly the redemption-miscalculation impact described in the reference report.

### Likelihood Explanation
Triggering requires only a standard liquidation: an unprivileged liquidator calls `liquidate` on an under-water account, and the seize leg executes through `seize::apply`. No privileged role, no oracle manipulation, no timing condition is needed — the defect is in the unconditional accounting, so every deposit-side seize in the affected mode corrupts state. Frequency is bounded by liquidation volume on deposit-collateral markets, but each occurrence is deterministic and cumulative.

### Recommendation
Extend `PoolSeizeEntry` (or the controller's use of it) so the pool can distinguish the two modes, then account for each correctly:

- **Credit mode:** reassign the shares to the liquidator's position and do *not* absorb them into `revenue` (the shares already sit in `supplied`; only ownership changes).
- **Transfer mode:** burn the seized supply shares (`burn_supply`) and `debit_cash` for the asset value paid out, mirroring `withdraw::gate_and_debit` [10](#0-9) .

Reserve `absorb_supply_as_revenue` strictly for the case where neither shares nor cash move — i.e., a pure ownership reclassification to the protocol with no external payout.

### Proof of Concept
1. Supplier deposits X of asset A into a hub market: `supplied = s_X`, `cash = X`, `revenue = 0`.
2. Borrower opens a position collateralized by A and backed by debt in another asset; prices move so `HF < 1`.
3. Liquidator calls `liquidate`; the plan contains a deposit-side seize of `s_k` shares of A in `SeizeMode::Transfer`, paying `v` tokens of A to the liquidator.
4. `seize::apply` runs `absorb_supply_as_revenue(s_k)`: `revenue = s_k`, `supplied` still `s_X`, `cash` still `X` — while `transfer_out`-equivalent payout already moved `v` tokens out.
5. Pool's real balance is now `X - v` but `cash = X`. The next `withdraw`/`borrow`/`claim_revenue` sized against `cash` either reverts on `InsufficientLiquidity` mid-batch or transfers tokens belonging to other suppliers' claims. `get_supplied_amount` for remaining suppliers still reports the pre-seize index valuation, so redemption math is wrong until insolvency surfaces — the same symptom (shares issued/transferred without the tracked asset totals being updated) as the `mint`/`withdraw` defects in the reference report.

Note: the pool-side evidence is definitive — `seize.rs` has no mode input and unconditionally absorbs deposit-side shares as revenue while performing no `burn_supply`/`debit_cash`. The precise wiring of `SeizeMode` inside `contracts/controller/src/positions/liquidation/apply.rs` (which legs emit `PoolSeizeEntry` under each mode) was not fully verifiable within available iterations; if the controller never emits a deposit seize under Transfer mode, the residual bug is the Credit-mode double-assignment in step 4, which stands on the same code.
