This confirms the finding: `HttpClient#initialize` builds `@base_uri = "https://#{api_host || session.shop}"` directly from `session.shop` with no domain validation performed inside `HttpClient` itself [1](#0-0) . Validation must happen upstream by the caller before constructing the `Session`.

### Title
`TokenExchange.exchange_token` sends the app's `client_secret` to a host derived from an unvalidated JWT `dest` claim, unlike sibling OAuth flows - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` builds the shop-scoped `Session` used to POST `client_id`/`client_secret` to `/admin/oauth/access_token` directly from the session token's `dest` claim, without ever passing it through `Utils::ShopValidator.sanitize!`. This is inconsistent with the two other credential-bearing OAuth flows in the same file/module family (`TokenExchange.migrate_to_expiring_token` and `ClientCredentials.client_credentials`), both of which call `Utils::ShopValidator.sanitize!(shop)` before constructing the session used for the token request.

### Finding Description
In `exchange_token`, the shop used to build the outbound request host is taken verbatim from the JWT payload: [2](#0-1) 

That `dest_shop` value is passed straight into `Auth::Session.new(shop: dest_shop)`, and `Clients::HttpClient` uses `session.shop` verbatim to build `@base_uri` — `"https://#{api_host || session.shop}"` — with no further host allow-listing at that layer [1](#0-0) . The POST body sent to that host includes `client_secret: Context.api_secret_key` [3](#0-2) .

Contrast this with the two sibling flows that build an identical request shape:
- `ClientCredentials.client_credentials` sanitizes the shop first: [4](#0-3) 
- `TokenExchange.migrate_to_expiring_token` sanitizes the shop first: [5](#0-4) 

`Utils::ShopValidator.sanitize!` enforces that the host is one of `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) or a configured custom `myshopify_domain` [6](#0-5) . `exchange_token` performs none of this — it derives the host directly from `JwtPayload#shop`, which is nothing more than `@dest.gsub("https://", "")`, an unvalidated string field, only integrity-protected by JWT/HMAC and checked for `aud == Context.api_key`, but never checked against `TRUSTED_SHOPIFY_DOMAINS` [7](#0-6) .

The broken identity binding, as an equality: `host validated by ShopValidator against TRUSTED_SHOPIFY_DOMAINS` **should equal** `host that receives the app's client_secret in exchange_token`, but in this path it does not — the host receiving the secret is only bound to "whatever string decoded out of the `dest` JWT claim," with domain-suffix trust delegated to nothing.

### Impact Explanation
If any code path in an integrating application allows a session token to be decoded/accepted whose `dest` claim is not itself already constrained to a genuine `*.myshopify.com`/trusted domain (e.g., a token minted for a different, non-standard `iss`/`dest` pair, a relayed/replayed token from a differently configured environment, or any host-app logic that forwards a session token without first confirming the originating shop against its own domain allow-list), `exchange_token` will POST the app's `client_secret` — a High-severity credential per the rules (SSRF carrying the app's credentials / credential leakage) — to a host chosen entirely by the `dest` field's contents, with no defense-in-depth check inside this gem. This is exactly the "host validated vs. host that receives the client_secret" identity-binding break called out in the task rules, and it is present asymmetrically only in this one function of an otherwise-consistent module.

### Likelihood Explanation
Likelihood is bounded by the fact that `JwtPayload` verifies the JWT's HMAC signature against `Context.api_secret_key` (or `old_api_secret_key`) before trusting any claim, so an outside attacker with no knowledge of the app's secret cannot forge a `dest` value outright. However, this gem provides no independent verification that `dest_shop` is a trusted Shopify domain, breaking the "defense in depth" pattern the maintainers deliberately built into the two structurally identical sibling functions in the same files. Any weakness in how the host application sources/passes the `session_token` to `exchange_token` (a boundary this gem cannot control) is the only thing standing between that gap and credential exfiltration.

### Recommendation
Route `dest_shop` through `Utils::ShopValidator.sanitize!` (mirroring `migrate_to_expiring_token` and `client_credentials`) before constructing `shop_session` in `exchange_token`, so all three OAuth credential-bearing HTTP calls in this module share the same trusted-domain enforcement.

### Proof of Concept
1. In `lib/shopify_api/auth/token_exchange.rb`, observe that `exchange_token` never calls `Utils::ShopValidator.sanitize!` on `dest_shop`, unlike `migrate_to_expiring_token` (same file) and `client_credentials` (`lib/shopify_api/auth/client_credentials.rb`), which both call it explicitly before building the request session.
2. Confirm `Clients::HttpClient#initialize` performs no host validation of its own — it interpolates `session.shop` straight into the request base URI: `lib/shopify_api/clients/http_client.rb` lines 16-19.
3. Confirm `JwtPayload` only checks `aud == Context.api_key`; it performs no `TRUSTED_SHOPIFY_DOMAINS`/`ShopValidator` check on `iss`/`dest`: `lib/shopify_api/auth/jwt_payload.rb` lines 33-51.
4. Any caller path that supplies `exchange_token` a `session_token` whose `dest` is not already independently constrained to a trusted domain results in `client_secret` being POSTed to that unvalidated host — the same request shape/body as `client_credentials`, but without its `sanitize!` guard.

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
