### Title
Webhook `shop-domain`, `topic` and `webhook-id` headers are not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw HTTP body when validating webhook authenticity, while the `shop`, `topic`, `api_version` and `webhook_id` values used to route and process the webhook are taken from unauthenticated HTTP headers. Any party able to obtain one genuine, HMAC-valid webhook delivery for the app (e.g. a merchant who has installed the app on their own store) can replay that exact body/HMAC pair while substituting the `X-Shopify-Shop-Domain` (and/or topic) header to impersonate a different, victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate`/`validate_signature` compute and compare the HMAC exclusively against `verifiable_query.to_signable_string`, i.e. the raw body — the `shop`, `topic`, `webhook_id`, and `api_version` are never part of the signed material: [2](#0-1) 

Yet `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are read straight from headers with no cryptographic binding to the body they accompany: [3](#0-2) 

`Registry.process` validates only the body HMAC and then trusts these header-derived fields to build the `WebhookMetadata` object that is handed to the app's webhook handler as the identity of the shop/tenant that triggered the event: [4](#0-3) 

This is the exact bug class described in the report: a field that is *acted on* (the `shop` used by the handler to attribute/store the event) is not *covered by the HMAC* (which only signs the body). The binding that should hold is:
`hmac == HMAC(secret, body || shop || topic || webhook_id)`
but the implementation only enforces:
`hmac == HMAC(secret, body)`

Because a single app `client_secret` is shared across every shop that installs the app, any merchant who installs the app is a legitimate, unprivileged recipient of real webhooks signed with that same secret. Such a merchant can capture a genuine `body` + `X-Shopify-Hmac-Sha256` pair from their own shop's webhook deliveries (and, for many topics, can influence the body content itself, e.g. via product/order/customer fields that get echoed into webhook payloads), then resend the identical body and HMAC to the app's webhook endpoint while changing only the `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`) headers to name an arbitrary victim shop. `HmacValidator.validate` still succeeds because it never inspects those headers, and `Registry.process` dispatches the forged event to the handler labeled with the victim's shop.

### Impact Explanation
This breaks tenant isolation (cross-tenant access), a Critical-impact category: an attacker-controlled webhook body can be injected into the app's processing pipeline under a victim shop's identity. Depending on how the host application uses `WebhookMetadata#shop`/`#topic` (common patterns include looking up the victim's stored session/access token to react to the event, updating per-shop billing/state, or triggering `app/uninstalled`-style cleanup), this can lead to unauthorized cross-tenant data manipulation or state corruption for shops the attacker does not control.

### Likelihood Explanation
Any user who can install the target app on a shop they control (a low bar — many Shopify apps offer free installs/trials) can capture real, validly-signed webhook deliveries and replay them with a forged shop/topic header, since replaying an HTTP request with modified headers requires no special access, credentials, or the app's `client_secret`.

### Recommendation
Bind the routing headers to the signed content instead of validating the body alone: include `shop-domain`, `topic`, and `webhook-id` (at minimum `shop-domain`) in the string that `Request#to_signable_string` returns, matching however Shopify's own doc guidance specifies the HMAC should be verified, or otherwise cryptographically bind them (e.g. verify header values against the shop association fetched independently, or require them to be echoed inside the signed JSON body if the upstream sender includes them). At minimum, document that consuming applications must not use header-derived `shop`/`topic` values for authorization decisions unless additionally corroborated.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and registers a webhook (e.g. `orders/create`).
2. Shopify delivers a genuine webhook to the app with headers:
   `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid hmac of body>`, plus a JSON `body`.
3. Attacker captures `body` and the valid `X-Shopify-Hmac-Sha256` value.
4. Attacker resends the same `body` and `X-Shopify-Hmac-Sha256` to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, body) == received_hmac` — this passes because `body` is unchanged.
6. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: ..., ...)`, processing attacker-controlled data as an event belonging to `victim.myshopify.com`.
