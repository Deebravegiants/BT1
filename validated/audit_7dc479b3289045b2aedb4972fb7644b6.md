### Title
Fee-token TOCTOU: relayer fees and refunds paid via a live `feeToken()` lookup that can differ from the token actually escrowed at dispatch time - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)` / `dispatch(DispatchGet)` collect the relayer fee in whatever ERC-20 `feeToken()` currently points to and store only `{payer, fee}` in `_requestCommitments[commitment]` — the fee-token address itself is never captured per-request. Delivery (`dispatchIncoming(GetResponse,...)`) and timeout handling (`dispatchTimeOut(...)`) later pay that stored `fee` out by re-reading `feeToken()` at that later moment. If governance rotates the host's fee token between dispatch and delivery/timeout — an explicitly supported, documented operation ("the host stores a configurable `feeToken` address that governance can update without a redeploy") — every request still in flight has its fee metadata checked against a stale token identity but paid out against the current one, exactly mirroring the exec() ToCToU pattern of checking permission/metadata once and consuming a possibly-changed value later.

### Finding Description
`dispatch(DispatchPost memory post)` collects the fee in the fee token live at call time and stores only the numeric amount and payer: [1](#0-0) 

`FeeMetadata` carries no token identifier, so once stored, the commitment's fee is permanently ambiguous as to denomination: [2](#0-1) 
(the same shape — `{sender, fee}`, no token id — is used on the EVM side via `FeeMetadata{sender, fee}` in `EvmHost.sol`).

At delivery time, `dispatchIncoming(GetResponse memory response, address relayer)` pays the relayer using a fresh call to `feeToken()`, not the token that was actually collected when the request was dispatched: [3](#0-2) 

Likewise, `dispatchTimeOut` (both `GetRequestTimeout` and `PostRequestTimeout` overloads) refunds the payer via a live `feeToken()` read at time of timeout, not the token in effect when the fee was escrowed: [4](#0-3) 

The host does gate fee-token changes with a dedicated error, `CannotChangeFeeToken` ("Cannot change the fee token without sweeping all funds from previous one"), which shows the protocol authors are aware that a stale-balance/stale-token problem exists around this parameter: [5](#0-4) 
However, this guard operates on the host's aggregate token *balance*, not on the identity bound to any individual already-dispatched, not-yet-delivered request's `FeeMetadata`. Sweeping the old token's balance to zero before flipping `feeToken()` (which is what the error's own description implies is required to unblock the change) actively removes the exact funds that in-flight requests' `fee` figures are denominated in and depend on, while every later `dispatchIncoming`/`dispatchTimeOut` call for those requests will re-resolve `feeToken()` to the new token and attempt to pay from it instead.

I was not able to fully read `updateHostParamsInternal()`'s fee-token branch in this pass to confirm exactly how/whether it accounts for in-flight commitments; that remains unverified and should be checked directly in the repository.

### Impact Explanation
Any request dispatched before a fee-token rotation and delivered or timed-out after it hits one of two outcomes, both reachable by an ordinary, unprivileged relayer simply submitting a normal proof:
- The `safeTransfer` in the new fee token reverts (host has no allocation there for that commitment, especially right after the "sweep all funds" step the `CannotChangeFeeToken` guard implies), which per `dispatchIncoming`/`dispatchTimeOut`'s "so it can be retried" pattern leaves the receipt around and could permanently strand delivery/timeout of that specific message — a route unable to deliver messages, and a permanent freeze of the escrowed relayer fee and, for timeouts, the payer's refund.
- Or the transfer succeeds against whatever balance the host holds of the new token, paying the relayer (or refunding the payer) an amount denominated in a completely different asset from what the user actually escrowed — an accounting/value mismatch that either shortchanges the relayer/payer or drains host-held balances of the new token that were not backing that commitment.

This reaches "concrete theft or permanent freezing of funds" and "a route unable to deliver messages" from the validation rules, triggered by a single relayed delivery/timeout transaction from any relayer, with no need for a malicious admin — a legitimate, documented fee-token rotation is enough to create the window.

### Likelihood Explanation
Fee-token rotation is presented as a normal governance/operations action ("governance can update without a redeploy"), and Hyperbridge's cross-chain delivery pipeline routinely has requests sitting in flight for the duration of a challenge period plus relayer scheduling — a realistic window for a rotation to land in between dispatch and delivery/timeout. The bug requires no attacker privilege at all: any relayer's ordinary delivery or timeout call after a fee-token change triggers the mismatch.

### Recommendation
Bind the fee-token address into `FeeMetadata` at dispatch time (store the token alongside `sender`/`fee`) and use that stored token — not a live `feeToken()` read — in every downstream payout (`dispatchIncoming` relayer reward, `dispatchTimeOut` refund/reward paths). Alternatively, block `feeToken()` rotation while any un-delivered/un-timed-out commitment still references the old token, rather than gating purely on the aggregate token balance.

### Proof of Concept
1. User/app calls `dispatch(DispatchGet)` (or `DispatchPost`) while `feeToken() == TokenA`; `fee` is collected in `TokenA` and `_requestCommitments[commitment] = {payer, fee}` is stored with no token reference: [1](#0-0) .
2. Before the request is delivered, governance rotates the fee token: sweeps `TokenA` balance and calls the host-params update path so `feeToken()` now returns `TokenB` (guarded only by `CannotChangeFeeToken`'s balance-sweep check): [5](#0-4) .
3. A relayer submits the GET response proof; `dispatchIncoming(GetResponse,...)` calls `IERC20(feeToken()).safeTransfer(relayer, fee)`, which now resolves to `TokenB`: [6](#0-5) . Because the host's `TokenA` balance for this commitment was already swept and no `TokenB` was ever escrowed for it, the transfer either reverts (stalling delivery of this specific message forever under the "retry" branch) or drains unrelated `TokenB` balance held by the host, mispaying the relayer relative to what the user actually escrowed.

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);

     * @dev Dispatch an incoming GET timeout to the source module.
     * @notice Does not refund any protocol fees.
     * @param timeout - timed-out get request bundled with the relayer that submitted the timeout proof
     * @param meta - fee metadata for the original request
     * @param commitment - request commitment
     */
    function dispatchTimeOut(
        GetRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onGetTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit GetRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }
