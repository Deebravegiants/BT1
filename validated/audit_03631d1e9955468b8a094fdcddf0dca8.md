### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) identity fields are not covered by the HMAC signature, allowing tenant-spoofed webhook delivery - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying an HMAC over the raw request body, then unconditionally trusts the `shop`, `topic`, `api_version`, and `webhook_id` values taken from HTTP headers — none of which are included in the signed content — when building the `WebhookMetadata` passed to the app's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body: [1](#0-0) 

`HmacValidator.validate` computes the HMAC exclusively over that signable string: [2](#0-1) 

`Registry.process` treats a passing HMAC check as sufficient authentication, then immediately hands unauthenticated header-derived fields to the handler as trusted metadata: [3](#0-2) 

The `shop`, `topic`, `api_version`, and `webhook_id` values are all read directly from HTTP headers with no cryptographic binding to the HMAC: [4](#0-3) 

The identity binding that should hold is: `hmac == HMAC(secret, body)` should imply `(body, shop, topic)` were all authentically produced together by Shopify for that specific shop/topic. Instead the equality actually enforced is only `hmac == HMAC(secret, body)`, while `shop`, `topic`, `webhook_id`, and `api_version` are unauthenticated and freely attacker-controllable in the request, since they are ordinary HTTP headers.

Because HMAC(secret, body) is deterministic and independent of the headers, any request bearing a **previously observed valid `(body, hmac)` pair** (e.g., a webhook delivery the attacker's own shop received, or one captured via any other channel) can be replayed with an arbitrary `x-shopify-shop-domain` (and `x-shopify-topic`) header, and `Utils::HmacValidator.validate` will still return `true`. `Registry.process` will then invoke the registered handler with `WebhookMetadata` claiming the payload originated from the attacker-chosen shop: [5](#0-4) 

For a multi-tenant host application that uses this gem's webhook processing and trusts `data.shop`/`data.topic` from `WebhookMetadata` to select which tenant's records to update (a very natural and documented use of this API — see `WebhookMetadata` fields consumed in handlers), an attacker who can reach the app's webhook endpoint can inject data attributed to a shop they do not own, i.e. a cross-tenant data-integrity/confusion bypass, using only a body/HMAC pair they already legitimately possess (e.g., from their own shop's webhooks).

### Impact Explanation
This breaks the tenant identity binding that HMAC validation is meant to provide: passing HMAC validation is treated by callers as proof "this webhook body belongs to shop X, topic Y," but the gem never binds X or Y into the signature. This enables cross-tenant confusion/injection in any host app that dispatches or scopes work per-tenant based on `WebhookMetadata#shop`/`#topic`, without requiring any credentials, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only network access to the application's webhook endpoint and a previously valid `(body, hmac)` pair — obtainable trivially by any user who is themselves a legitimate merchant/tenant of the app (since every merchant receives correctly-signed webhooks for their own shop) or by any observer of an unencrypted/leaked webhook delivery. No access to `api_secret_key`, tokens, or the app's infrastructure is needed, so likelihood is high for any multi-tenant deployment.

### Recommendation
Include the tenant/topic identity fields (`shop`, `topic`, `api_version`, `webhook_id`) in the HMAC-verified content, or otherwise cryptographically bind them, before exposing them via `WebhookMetadata`. At minimum, `Request#to_signable_string` should incorporate the shop domain and topic (in a canonical, unambiguous encoding) so `HmacValidator.validate` cannot pass unless those fields are exactly what Shopify signed for.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker-shop.myshopify.com` and receives a legitimate webhook, capturing `raw_body` and the valid `x-shopify-hmac-sha256` header (both computed only from `raw_body`, per `to_signable_string`).
2. Attacker sends a new HTTP request to the app's webhook endpoint with the identical `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes `HMAC(secret, raw_body)`, which matches, and returns `true` (see `lib/shopify_api/utils/hmac_validator.rb:26-31`).
4. `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)` (see `lib/shopify_api/webhooks/registry.rb:198-199`), causing the host app to process attacker-controlled data as belonging to `victim-shop.myshopify.com`.
