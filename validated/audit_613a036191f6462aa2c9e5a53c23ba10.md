### Title
Permanent inability to establish the first state-machine commitment for a new destination chain due to a flawed zero-height guard - ([File: evm/src/core/HandlerV2.sol])

### Summary
`HandlerV2.handleConsensus` stores each intermediate state-machine commitment produced by a consensus-client proof only if the destination's previously recorded height is non-zero *and* the new height is greater than it. For any state machine that has never had a height recorded (`latestStateMachineHeight == 0`), this guard permanently prevents the very first commitment from ever being written, because the only way `latestHeight` becomes non-zero is through the same code path that the guard blocks. This silently drops legitimate consensus data without reverting or otherwise signaling failure — the same bug-class as the Terrapin report: a message (here, a state commitment) that should be authenticated/accepted is silently stripped because a counter/height comparison is evaluated against an unset baseline.

### Finding Description
`HandlerV2.handleConsensus` iterates the `intermediates` array returned by the consensus client and only calls `host.storeStateMachineCommitment` when:

```solidity
if (latestHeight != 0 && intermediate.height > latestHeight) {
    ...
    host.storeStateMachineCommitment(stateMachineHeight, intermediate.commitment);
}
``` [1](#0-0) 

`latestHeight` is read via `host.latestStateMachineHeight(intermediate.stateMachineId)` [2](#0-1) , which is the on-chain `_latestStateMachineHeight` mapping updated exclusively by `storeStateMachineCommitment` in `EvmHost.sol` [3](#0-2) . For any state machine ID that has never been committed on this host (a brand-new destination/counterparty chain onboarded after deployment, or any ID whose mapping slot defaults to `0`), `latestHeight` is `0`. The guard `latestHeight != 0` then evaluates false regardless of how valid or how large `intermediate.height` is, so the commitment is dropped — no revert, no event, no error. Because the mapping is never updated, every subsequent consensus proof for that state machine hits the exact same `latestHeight == 0` state and is dropped again, forever. There is no other write path to `_latestStateMachineHeight`, so the state machine can never receive its first commitment through the normal consensus-update flow.

This is directly reachable by any permissionless caller submitting a consensus proof through `handleConsensus` (no admin/governance role required) [4](#0-3) . It is not a malicious-relayer or malicious-admin issue — it is a logic defect that fires on entirely honest, correctly verified consensus proofs for any state machine whose height happens to start at the natural "unset" sentinel value of `0`.

### Impact Explanation
Both `handlePostRequests` and `handleGetResponses` require a non-zero `stateMachineCommitment(...).overlayRoot` (or a populated `StateCommitment`) at the referenced height before any membership proof can be verified [5](#0-4) [6](#0-5) . If the very first commitment for a given `stateMachineId` can never be stored because of the guard above, then no request or response destined to/from that chain can ever be delivered through this host — a permanent freeze of message delivery for that route, satisfying the "route unable to deliver messages" impact criterion. This is not a resource-exhaustion or availability nuisance; it is a permanent, silent correctness failure in the core consensus/commitment pipeline that every downstream dispatch (token bridge messages, intents, relayer rewards tied to that state machine) depends on.

### Likelihood Explanation
Likelihood is high for any state machine ID whose commitment mapping starts at the default `0` — which is the normal initial condition for any newly added destination chain, since Solidity mappings default to zero and there is no bootstrap/initialization call elsewhere in the reviewed code that pre-seeds `_latestStateMachineHeight` for a state machine before its first `handleConsensus` proof. Triggering the bug requires nothing more than a single, entirely valid, permissionless `handleConsensus` call — no attacker capability beyond ordinary relaying is needed; the condition is hit by design on the first legitimate consensus update for that state machine.

### Recommendation
Remove the `latestHeight != 0` sentinel check and instead track "has this state machine ID ever been committed" explicitly (e.g., via a separate boolean/existence flag, or by allowing height `0` to be a valid recorded height distinguishable from "unset"), so the first commitment for any state machine is always stored when `intermediate.height` is greater than the recorded height (treating "never set" as `-1`/negative infinity rather than `0`). Add a regression test that submits a consensus proof for a brand-new `stateMachineId` and asserts that `stateMachineCommitment` and `latestStateMachineHeight` are populated after a single `handleConsensus` call.

### Proof of Concept
1. Deploy `EvmHost`/`HandlerV2` and register a consensus client for a new counterparty chain whose `stateMachineId` has never appeared in `_latestStateMachineHeight` (mapping defaults to `0`).
2. Have the consensus client return one `IntermediateState` for that `stateMachineId` at any valid height `H > 0` from a legitimately verified proof.
3. Call `handleConsensus(host, proof)`. Inside the loop, `latestHeight = host.latestStateMachineHeight(stateMachineId) == 0`, so the `if` condition is false and `storeStateMachineCommitment` is never invoked [7](#0-6) .
4. Query `host.stateMachineCommitment(StateMachineHeight{stateMachineId, height: H})` — it returns the zero-value struct (`overlayRoot == bytes32(0)`).
5. Attempt `handlePostRequests`/`handleGetResponses` against that height — both revert with `StateCommitmentNotFound()` [8](#0-7) , and re-submitting the same or later consensus proofs for that `stateMachineId` reproduces step 3 indefinitely since `latestHeight` never advances past `0`.
