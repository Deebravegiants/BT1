### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) headers are not covered by the HMAC signature, allowing cross-tenant spoofing of webhook identity - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely via `Utils::HmacValidator.validate(request)`, which recomputes an HMAC over `request.to_signable_string`. For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`; none of the identity-carrying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) are included in the signed material, yet `shop` is later trusted and handed to the host app's handler as the tenant identifier.

### Finding Description
`Webhooks::Request#to_signable_string` is defined as: [1](#0-0) 

while `shop` is read straight from an unauthenticated header: [2](#0-1) 

`Registry.process` verifies the request via `HmacValidator.validate`, which internally calls `validate_signature`, comparing `verifiable_query.hmac` against an HMAC computed on `to_signable_string` (the raw body only) using `Context.api_secret_key`: [3](#0-2) [4](#0-3) 

After this check passes, `request.shop` (the raw header value) is forwarded unchecked into `WebhookMetadata` and dispatched to the app's handler: [5](#0-4) 

The identity binding that should hold is: `hmac == HMAC(secret, body || shop || topic || webhook_id)`. Instead the gem only enforces `hmac == HMAC(secret, body)`, i.e. `shop` (the field the host application acts on to select a tenant) is disjoint from the signed material. Since Shopify computes the webhook HMAC using the app-wide `client_secret` (identical for every shop/tenant that installed the app, not a per-shop secret), any account holder who has legitimately installed the app receives their own correctly-signed webhook bodies. Because the signature never binds to the `shop-domain` header, that same `(body, hmac)` pair validates successfully no matter which `shop-domain` value is presented alongside it. An attacker who controls a webhook endpoint replay (e.g., a malicious tenant capturing their own legitimate webhook deliveries and replaying the identical body/hmac pair with a different `shop-domain` header value to the shared app webhook endpoint) causes `HmacValidator.validate` to still return `true`, and the handler executes with an attacker-chosen `shop` value instead of the value actually authenticated.

### Impact Explanation
This breaks tenant isolation: the `shop` value trusted by downstream handler logic (`WebhookMetadata#shop`) is not the value the cryptographic signature actually authenticates. Any app built on this gem that uses `data.shop` to scope database writes, trigger per-tenant side effects, or select which merchant's records to update is exposed to cross-tenant data injection/corruption using data that was only ever validly signed for the attacker's own tenant. This matches the "cross-tenant access" Critical-impact category, since the gem's own webhook verification API provides no guarantee that the `shop` header is authentic, despite exposing it via `WebhookMetadata` as if it were validated alongside the payload.

### Likelihood Explanation
Requires only that the attacker be a legitimate (even free/trial) merchant who has installed the target app — no leaked secrets, TLS interception, or privileged access is needed. The attacker only needs one genuine webhook delivery to their own shop (trivially obtainable by taking any action that triggers a webhook) and the ability to send an HTTP POST to the app's public webhook endpoint with a modified `shop-domain` header while keeping the original raw body and HMAC header unchanged.

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, `webhook_id`, `api_version`) in the material that is authenticated, or otherwise cryptographically bind them to the body before dispatch. Concretely, change `Webhooks::Request#to_signable_string` to incorporate these headers (matching however Shopify actually signs webhooks) or, at minimum, have `Registry.process`/`WebhookMetadata` treat `shop` as untrusted unless it can be independently corroborated (e.g., against a previously known/allow-listed shop for that specific webhook body), so `hmac` validation cannot succeed while `shop` is substituted.

### Proof of Concept
1. Install the target Shopify app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook (e.g., `orders/create`) to receive a legitimately Shopify-signed delivery: headers `x-shopify-hmac-sha256: <H>`, `x-shopify-shop-domain: attacker.myshopify.com`, body `B`.
2. Replay the exact same body `B` and `x-shopify-hmac-sha256: <H>` to the app's webhook endpoint, but replace the header with `x-shopify-shop-domain: victim.myshopify.com`.
3. `Webhooks::Registry.process` builds a `Webhooks::Request` from these headers/body and calls `Utils::HmacValidator.validate(request)`, which only hashes `@raw_body` (`B`) — validation succeeds because the body and HMAC are unchanged. [3](#0-2) 
4. The registered handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` even though the cryptographic proof only ever covered the attacker's own payload, letting the attacker inject data attributed to a shop they do not control.
