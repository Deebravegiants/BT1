### Title
Webhook `shop-domain` and `topic` Headers Are Trusted Without Being Covered by the HMAC, Enabling Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the identity fields `shop`, `topic`, `webhook_id`, and `api_version` directly from HTTP headers, but the HMAC signature verified by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body [1](#0-0) . Because the same `api_secret_key` is used to sign webhooks for every shop that has installed the app, any merchant (an unprivileged actor relative to other tenants of the same app) can capture a legitimate, validly-signed webhook delivered to their own store and replay it against the app's webhook endpoint with a forged `shop-domain` header pointing at a different (victim) shop. The signature still validates because it only checks the body bytes, not the header claiming which shop the event belongs to.

### Finding Description
`HmacValidator.validate` computes the expected signature from `verifiable_query.to_signable_string` and compares it with `verifiable_query.hmac` using `OpenSSL.secure_compare` [2](#0-1) .

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`, while `hmac`, `shop`, `topic`, `webhook_id`, and `api_version` are all pulled independently from HTTP headers that are not part of the signed payload: [3](#0-2) 

`Webhooks::Registry.process` validates the HMAC and then unconditionally trusts `request.shop` (and `request.topic`) to build the metadata passed to the app's handler: [4](#0-3) 

The binding that should hold is:
`shop asserted in the HMAC-signed payload == shop the handler acts on`

But the actual binding enforced is only:
`HMAC(raw_body, api_secret_key) == received_hmac`

with `shop` supplied out-of-band via an unauthenticated header. Since `api_secret_key` (the app's client secret) is shared across every shop installation of the app, any tenant that legitimately receives one authentic webhook can capture that raw body + valid `hmac-sha256` header and resend it with an arbitrary `shop-domain` header value. The signature check passes because it never inspects the shop header, so the forged shop identity is passed straight through to the handler as if it were authentic.

### Impact Explanation
This breaks the tenant isolation the HMAC is meant to guarantee: an unprivileged merchant using the app can cause the app to process arbitrary webhook events (of a topic/body they control, replayed from their own legitimately-received webhooks) attributed to a shop they do not own or operate. Depending on how the host application's webhook handlers key state, storage lookups, or side effects off `WebhookMetadata#shop`, this can result in cross-tenant data corruption, unauthorized state changes, or information disclosure scoped to a shop the attacker does not control — a cross-tenant access impact.

### Likelihood Explanation
Any merchant who installs the app (a normal, unprivileged position) automatically receives real webhooks with valid HMACs for their own store. Forging the `shop-domain` (and `topic`) header requires no cryptographic material beyond replaying an already-valid webhook and editing an unsigned header, making this trivially reproducible by any existing customer/tenant of the app without needing the app's `client_secret` or any credential belonging to the victim shop.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signed payload verified by the HMAC (or otherwise cryptographically bind them to the body), and/or require the host application to cross-check the header-derived shop domain against the shop that is actually expected to receive that webhook (e.g., an installed/known-shops list) before invoking handlers. At minimum, document prominently that `WebhookMetadata#shop` is not authenticated by the HMAC and must be independently verified against the app's known tenant list before being trusted.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. topic `orders/create`, with headers:
   - `x-shopify-hmac-sha256: <valid-hmac-of-raw-body>`
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - `x-shopify-topic: orders/create`
   - raw body `{"id": 1, ...}`
2. Attacker resends the identical raw body and `x-shopify-hmac-sha256` header to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into a request object; `hmac` and `to_signable_string` (`@raw_body`) are unchanged from the original legitimate delivery [5](#0-4) .
4. `Utils::HmacValidator.validate(request)` succeeds because the signature only covers `@raw_body`, which was not tampered with [6](#0-5) .
5. `Webhooks::Registry.process` calls the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "orders/create", body: ..., ...)` [7](#0-6) , causing the host application to process attacker-controlled data as if it originated from the victim shop.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
