### Title
Position-map entries can expire while account metadata is renewed, silently deleting user collateral/debt claims — (File: contracts/controller/src/storage/account.rs)

### Summary
`write_side_map` persists `ControllerKey::SupplyPositions` / `ControllerKey::BorrowPositions` via `persistent.set` but never extends their TTL, while `set_account_meta` and `renew_user_account` do renew sibling keys. An account's position entries can therefore be evicted (archived) while `AccountMeta` and the NFT remain live — a dangling reference of the same class as CVE-2019-19770 (use-after-remove of a resource still referenced by its registry). Reads then silently default to empty maps.

### Finding Description
The bug class is "remove a registry-backed object while consumers still reference it." Here the registry is the account's metadata + NFT ownership, and the referenced objects are the two position maps.

- `set_supply_positions` / `set_debt_positions` route through `write_side_map`, which calls `persistent.set(key, map)` with **no TTL renewal** [1](#0-0) .
- `set_account_meta` uses `set_user`, which renews TTL, and the module doc states "position-map writes do not" renew [2](#0-1) .
- On read, a missing/expired position map is indistinguishable from an empty one: `get_supply_positions` and `get_debt_positions` return `Map::new(env)` on miss [3](#0-2) .
- `get_account` / `try_get_account` only require metadata and NFT ownership — expired position maps are not detected [4](#0-3) .
- Renewal exists only via the explicit owner-authenticated `renew_account` entrypoint, which renews all four keys [5](#0-4) . Routine supply/withdraw/borrow/repay calls renew `AccountMeta` but not the position maps, so an actively-used account's position entries still expire at their original write TTL.

Consequences once a `SupplyPositions` entry expires while the account is live:

- `withdraw` sees an empty supply map: the user's collateral claim vanishes; `cleanup_account_if_empty` can then delete the account and burn the NFT via `remove_account_and_burn_nft` [6](#0-5) , destroying the last reference to the still-on-pool-book shares — funds are stranded in the pool with no account that can claim them.
- `get_account_borrow_only` similarly loads a defaulted-empty debt map for paths that only check debt [7](#0-6) .

### Impact Explanation
Expired/archived persistent entries can be restored on Soroban, so this is a temporary freezing of funds rather than permanent loss in the base case: the user's collateral becomes unreachable (all position reads default to empty) until the archived entry is restored. The worse outcome is if `cleanup_account_if_empty` runs after the supply map expired but before restore — the NFT is burned and meta deleted, permanently severing ownership of pool shares whose totals (`supplied`, `cash` in `PoolStateRaw`) remain on the pool's books [8](#0-7) . Any unprivileged user can call `liquidate`/`clean_bad_debt`-adjacent flows on the affected account, and the owner cannot prevent eviction during normal use because no non-renewal entrypoint bumps the position-map TTL.

### Likelihood Explanation
Triggering does not require an attacker action — it requires only that the user not call `renew_account` within the TTL window of the initial position write, even if they actively transact (writes do not renew). Soroban persistent archival makes expiry a routine event rather than an edge case. Impact severity is bounded by archival restorability in the common case, but the burn-on-empty path upgrades it to permanent loss of the collateral claim. Medium severity.

### Recommendation
Extend the user TTL inside `write_side_map` (call `renew_user_key` on `SupplyPositions`/`BorrowPositions` whenever the map is written), matching the renewal done for `AccountMeta`/`Delegates`. Additionally, make `cleanup_account_if_empty` defensive: before burning, verify the position-map keys are genuinely absent-vs-archived, or require the owner/NFT holder auth for the burn so a third party cannot finalize an account whose positions merely expired.

### Proof of Concept
1. User supplies collateral via `supply`; `SupplyPositions(account_id)` is written with default TTL; `AccountMeta` written with renewed TTL.
2. User continues to interact (borrow/repay) — each `set` rewrites the map without extending TTL.
3. TTL lapses on `SupplyPositions`; entry archives. `get_supply_positions` returns `Map::new`.
4. `withdraw` finds no position (reverts) — collateral temporarily frozen. If any flow invokes `cleanup_account_if_empty` (e.g., full debt repayment path or liquidation leaving zero borrows), the NFT is burned and meta removed while the pool still credits `supplied`/`cash` for the vanished shares.

*Uncertainty note: I could not confirm within the available iterations whether `set_user`/`get_user` in `storage/protocol.rs` also renew position-map keys on read — the module comment says successful reads renew user TTL, which would mitigate expiry for actively-read accounts; if so, the residual risk concentrates on idle accounts, reducing likelihood but not the dangling-reference flaw.*

fn write_side_map<V: TryFromVal<Env, Val> + IntoVal<Env, Val>>(
    env: &Env,
    key: &ControllerKey,
    map: &Map<HubAssetKey, V>,
) {
    let persistent = env.storage().persistent();
    if map.is_empty() {
        persistent.remove(key);
    } else {
        persistent.set(key, map);
    }
}

    let owner = try_account_owner(env, account_id)?;
    Some(account_from_parts(
        owner,
        meta,
