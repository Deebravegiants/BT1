### Title
Division by zero panic in `calc_take_pnl` due to attacker-drivable zero pool reserve - (File: `program/src/processor.rs`)

### Summary
`Processor::calc_take_pnl` divides by `x1` (the normalized `total_pc_without_take_pnl`) without any zero-check. `x1` is derived from live vault balances minus the accumulated `amm.state_data.need_take_pnl_pc` debt, a value that grows monotonically with every `Deposit`/`Withdraw` call and is only reset by the privileged `WithdrawPnl` instruction. An unprivileged user can drive `total_pc_without_take_pnl` (or the coin-side equivalent) to exactly zero through repeated permissionless swaps and deposits/withdraws, causing a division-by-zero panic that aborts the transaction and can permanently block further `Deposit`/`Withdraw` calls on the pool.

### Finding Description
`calc_take_pnl` computes: [1](#0-0) 

```rust
let x2_power = Calculator::calc_x_power(target.calc_pnl_x.into(), target.calc_pnl_y.into(), x1, y1);
let x2 = x2_power.integer_sqrt();
let y2 = x2.checked_mul(y1).unwrap().checked_div(x1).unwrap();
```
`x1` here is the normalized `total_pc_without_take_pnl` passed in by the caller, computed as: [2](#0-1) 

`total_pc_without_take_pnl = pc_amount - amm.state_data.need_take_pnl_pc`, guarded only against underflow (`checked_sub`), not against reaching exactly zero. If it equals zero, `normalize_decimal_v2` also yields zero, so `x1 == 0` is passed straight into `calc_take_pnl`, and `checked_div(x1).unwrap()` panics.

`calc_take_pnl` is invoked unconditionally from `process_deposit`: [3](#0-2) 

and conditionally from `process_withdraw` (skipped only when the pool is in `WithdrawOnly` status): [4](#0-3) 

`need_take_pnl_pc`/`need_take_pnl_coin` are increased every time `calc_take_pnl` observes that the pool invariant (`k`) has grown due to accumulated trading fees: [5](#0-4) 

Both `Deposit` and `Withdraw` are freely callable by any unprivileged liquidity provider, and price movement (via `SwapBaseIn`/`SwapBaseOut`, also unprivileged) increases `k` between calls. Because these debts are only ever cleared by the privileged `WithdrawPnl` instruction, a determined attacker can, through a sequence of swaps and deposits/withdraws they fully control, push `need_take_pnl_pc` (or `need_take_pnl_coin`) arbitrarily close to the vault balance, until `total_pc_without_take_pnl` (or the coin-side equivalent, `x1`/`y1` — note `y1` is also used as a divisor via `checked_ceil_div`/`checked_div` patterns in the broader pnl and swap math) equals zero.

### Impact Explanation
Once the state is reached, every subsequent `Deposit` and `Withdraw` transaction that must run `calc_take_pnl` will panic with a division-by-zero error and abort. Since Solana aborts revert all account state changes from within that instruction, this does not corrupt state directly, but it permanently freezes normal LP deposit/withdraw functionality for the pool until the privileged pool owner calls `WithdrawPnl` to reduce the debt below the vault balance — an action outside the control of the affected LPs. This constitutes a freezing-of-funds condition (CWE-369 class) reachable purely through unprivileged transactions (`Deposit`, `Withdraw`, `SwapBaseIn`/`SwapBaseOut`).

### Likelihood Explanation
The attacker needs no special privileges — only the ability to submit `Deposit`, `Withdraw`, and swap instructions with attacker-chosen amounts, which is exactly the intended permissionless usage of the AMM. Precisely hitting `x1 == 0` requires careful control of trade/deposit sizes across multiple transactions, which is feasible off-chain since all relevant state (`need_take_pnl_pc`, vault balances, `calc_pnl_x/y`) is readable, and amounts are fully attacker-controlled integers.

### Recommendation
In `calc_take_pnl` (`program/src/processor.rs`), validate that `x1` and `y1` are non-zero before performing the ratio calculations, and return `AmmError::CalcPnlError` (or a new dedicated error) instead of relying on `unwrap()` on `checked_div`. Additionally, consider bounding `need_take_pnl_pc`/`need_take_pnl_coin` so they can never approach the full vault balance, or fail gracefully with a typed error when doing so instead of panicking.

### Proof of Concept
1. Attacker creates a pool via `Initialize2` (or targets an existing pool) and provides/observes initial liquidity so `target_orders.calc_pnl_x`/`calc_pnl_y` are set to the initial reserves via `process_initialize2`.
2. Attacker repeatedly performs `SwapBaseIn`/`SwapBaseOut` (no `calc_take_pnl` involvement, purely constant-product swaps, each collecting a trading fee that increases `k`), interleaved with minimal `Deposit` calls that trigger `calc_take_pnl` and accrue amounts into `amm.state_data.need_take_pnl_pc`/`need_take_pnl_coin`.
3. Because `need_take_pnl_pc`/`need_take_pnl_coin` only grow (cleared solely by the privileged `WithdrawPnl` instruction), the attacker precisely sizes swaps/deposits (fully attacker-controlled integers, computable off-chain) so that `pc_amount - need_take_pnl_pc == 0` (or equivalently for the coin side) exactly, as computed in `Calculator::calc_total_without_take_pnl_no_orderbook`.
4. Any subsequent `Deposit` or `Withdraw` call now passes `x1 == 0` (or `y1 == 0`) into `calc_take_pnl`, triggering `checked_div(x1).unwrap()` to panic, aborting the transaction and preventing any user from depositing to or withdrawing from the pool until the pool owner manually calls `WithdrawPnl`.

```rust
    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
```
