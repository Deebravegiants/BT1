### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing tenant spoofing in `Webhooks::Registry.process` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` but its `to_signable_string` returns only the raw JSON body [1](#0-0) . The `shop` accessor, which is derived from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, is never included in the signable string and therefore is not bound to the HMAC [2](#0-1) . `Registry.process` validates only that the HMAC matches the raw body (`Utils::HmacValidator.validate(request)`), then forwards `request.shop` unchanged to the app's handler as the tenant identifier [3](#0-2) .

### Finding Description
This is the same bug class as the reported "debt ceiling can be exceeded" issue: the code that authorizes/binds an action (`HmacValidator.validate`, analogous to the debt-ceiling check on `bond.totalSupply()`) does not cover a field that is later trusted for a security-relevant decision (`depositUnderlying()` minting hTokens without the ceiling check, analogous to `request.shop` being used for tenant routing without being HMAC-bound).

Concretely:
- `HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to `verifiable_query.hmac` [4](#0-3) .
- For `Webhooks::Request`, `to_signable_string` is exactly `@raw_body` — nothing else [1](#0-0) .
- `shop` is read straight from the `shopify-shop-domain` header with no cross-check against the body or HMAC [2](#0-1) .
- `Registry.process` uses that unverified `shop` value directly to build the `WebhookMetadata` passed to the host application's handler, after only checking the HMAC of the body [3](#0-2) .

The broken identity binding, stated as an equality that should hold but doesn't:
`shop-header-used-for-tenant-routing == shop-that-the-app's-secret-actually-signed-for`

Before the attack: a legitimate webhook for shop A arrives with body B, a valid HMAC over B computed with the app's `api_secret_key`, and header `shopify-shop-domain: shop-a.myshopify.com`.

Attack: any party who can present an HTTP request to the app's webhook endpoint (this includes the app developer's own additional store, or anyone who can capture/replay one legitimate webhook delivery for any shop that installed the same app) submits the same body B and the same valid HMAC, but with `shopify-shop-domain` changed to `shop-b.myshopify.com` (a different merchant/tenant).

After: `HmacValidator.validate` still succeeds because it only re-hashes `@raw_body`, which is unchanged [1](#0-0) . `Registry.process` passes `shop: "shop-b.myshopify.com"` to the handler even though the payload was never actually signed for shop B [5](#0-4) . If the host app uses `data.shop` (as most Shopify apps do, per the gem's own `WebhookMetadata` contract) to look up per-tenant session/access-token records or to scope data writes, this yields cross-tenant data confusion/access using the target's own valid signature material for someone else's tenant identity.

### Impact Explanation
This matches the **Critical: cross-tenant access** category. The gem's webhook verification API is documented and relied upon by host apps specifically to assert "this payload was authentically sent by Shopify for shop X." Because `shop` is excluded from the signed content, the gem's own `process`/`HmacValidator.validate` combination hands the host app a shop identifier that carries no cryptographic guarantee, enabling tenant impersonation without requiring the attacker to know `api_secret_key`, an access token, or any other credential of the impersonated tenant.

### Likelihood Explanation
Any user who has installed the app on their own store receives their own genuinely HMAC-valid webhook deliveries (bodies + HMACs signed with the shared app secret, since HMAC signing here does not vary per-shop content beyond the body). Replaying such a delivery to the app's public webhook endpoint with a different `shopify-shop-domain` header requires only basic HTTP tooling — no credential theft, no TLS interception, no social engineering. This is fully reachable by an "unprivileged internet user" who is simply a legitimate (even trial) merchant of the same app.

### Recommendation
Bind the `shop` (and ideally `topic`/`api_version`) header values into the signed content that `HmacValidator` verifies, or otherwise cryptographically tie the header-derived shop to the payload before trusting it for tenant-scoped operations. At minimum, `Webhooks::Request#to_signable_string` should incorporate the `shop-domain` header (or the gem should document/enforce that host apps must independently verify shop-webhook binding via Shopify's registered webhook subscription topic/address, and should not use `request.shop` as an assumed-authenticated tenant key without doing so).

### Proof of Concept
1. App installs on `shop-a.myshopify.com`; Shopify delivers a legitimate webhook to the endpoint with body `B`, header `x-shopify-hmac-sha256: H` (valid for `B` with `api_secret_key`), and header `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Attacker (who owns `shop-b.myshopify.com`, also an installer of the same app, or who can capture the above request) resends the exact same body `B` and the exact same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: shop-a.myshopify.com` while their handler-side session context expects `shop-b`, or more directly crafts a request with a shop-domain of a *different, victim* tenant they do not control, reusing any body/HMAC pair they've legitimately received before (e.g., a common webhook topic like `app/uninstalled` whose body content may be predictable/empty, as shown in `test/webhooks/registry_test.rb`: `raw_body: "{}"`) [6](#0-5) .
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because the signature only covers `@raw_body` ("{}"), then invokes the app handler with `shop: "<victim-shop>.myshopify.com"` [7](#0-6) .
4. The host application processes the event as if it authentically originated from the victim shop, despite the HMAC never having covered that claim.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end
