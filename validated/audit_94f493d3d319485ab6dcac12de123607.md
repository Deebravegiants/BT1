### Title
Unsigned subtraction `assetReserve - virtualLtReserve` in `canGraduate`/`_prepareGraduationLiquidity`/`previewLtUntilGraduation` can underflow-revert, permanently bricking a curve token's buy/sell path - (File: packages/contracts/src/Bonding.sol)

### Summary
`Bonding.sol` recovers the launch-time virtual LT reserve as `Pair.k() / Token.TOTAL_SUPPLY()` and then computes the curve's "real" raised LT with a plain unsigned subtraction, `assetReserve - virtualLtReserve`, in three places: `canGraduate` [1](#0-0) , `previewLtUntilGraduation` [2](#0-1) , and `_prepareGraduationLiquidity` [3](#0-2) . This code implicitly assumes `assetReserve >= virtualLtReserve` always holds. Just like the FlatMoney report's `marginDepositedTotal < -fundingFees` comparison assumed a relationship between a signed and unsigned quantity that isn't actually guaranteed in the worst case, this codebase assumes the pair's stored `assetReserve` can never fall below the immutable, launch-time-derived `virtualLtReserve`. Solidity 0.8's automatic underflow-revert on `uint256 - uint256` turns any violation of that assumption into a hard revert (panic 0x11) in a function that every single buy and sell must pass through.

### Finding Description
At mint, `Pair.mint(tokenReserve, assetReserve)` sets `_pool.k = tokenReserve * assetReserve = TOTAL_SUPPLY * virtualLtReserve` [4](#0-3) , and `assetReserve` starts out exactly equal to `virtualLtReserve`. `Pair.swap` enforces the constant-product floor with a `+1` slack on both sides: `(newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k` reverts [5](#0-4) . This `+1` slack is exactly the "K slack" the assignment calls out as a known bug-class hotspot in `Pair.swap`.

Because a sell can bring `tokenReserve` back up toward its original virtual value (`TOTAL_SUPPLY`) while only needing `(TOTAL_SUPPLY+1) * (newAssetReserve+1) >= TOTAL_SUPPLY * virtualLtReserve`, the K-floor's `+1` slack allows `newAssetReserve` to land 1–2 wei *below* `virtualLtReserve` on a round trip (buy tokens, then sell them all back) — the pool is allowed to give up a hair more asset than it took in, because the check only needs the product to clear `k`, not each reserve individually. `Router`'s buy/sell math (`_computeBuy`/`_computeSell`, floor-rounded like `getAmountOut`'s `reserveAsset - k/newReserveToken`) does not special-case or defensively clamp `assetReserve` at `virtualLtReserve`; nothing in `Router.sol` or `Pair.sol` prevents `assetReserve` from settling marginally below the launch-time `virtualLtReserve` after ordinary buy/sell activity.

Once that happens, `_launchTimeVirtualLtReserve(token_, pair) = k() / TOTAL_SUPPLY()` still returns the *original* `virtualLtReserve` exactly (since `k` is immutable and `k = TOTAL_SUPPLY * virtualLtReserve` divides evenly), while the live `assetReserve` is now smaller. The next call to `assetReserve - _launchTimeVirtualLtReserve(...)` underflows and reverts.

`canGraduate` is invoked unconditionally at the end of `Bonding._executeBuy` for every single buy (per `docs/contracts-scope.md`: "`Bonding.canGraduate()` is checked at the end of every buy inside `_executeBuy`") and by `Zap._sellInternal` before every curve sell (`if (bonding_.canGraduate(tokenAddress)) { ... }`) [6](#0-5) . Once the underflow condition is hit, both the buy path and the sell path for that token revert unconditionally and permanently — there is no recovery: the same K-floor mechanics that produced the below-`virtualLtReserve` state will keep reproducing or worsening it (any further sell only pushes `assetReserve` further away from recovery unless a sufficiently large buy pushes it back above the threshold, but that buy itself cannot land because `canGraduate` is evaluated at the end of `_executeBuy`, and the underflow happens on the *post-swap* reserves, so the very buy meant to fix it will itself revert).

### Impact Explanation
This breaks the same class of invariant as the FlatMoney finding: an unsigned subtraction between a "total" quantity and a component assumed to always be smaller, without accounting for the true worst case, crashes the entire feature. Here the consequence is a permanent denial-of-service specific to a launched token:
- Every future `Zap.buy` and `Zap.sell` (curve leg) on the affected token reverts, since both paths route through `canGraduate` in `Bonding`.
- The token can never reach graduation (no LP is ever seeded, `LPLock.recordLock` never fires), and it can never sell back down.
- All LT and tokens already deposited into that `Pair` (creator's seed buy, all trader buys) become permanently stuck — no rescue/withdraw path exists for curve-stage funds outside of the buy/sell/graduate flow, all of which are bricked.

This satisfies "permanent freezing of trader, creator, or LP funds," reachable purely from `Zap.buy`/`Zap.sell` calls made by unprivileged traders — no privileged role is required.

### Likelihood Explanation
The triggering condition — `assetReserve` dipping 1–2 wei below the launch-time `virtualLtReserve` via ordinary buy-then-sell round trips exploiting `Pair.swap`'s `+1` K-invariant slack — is reachable by any trader submitting only `Zap.buy` and `Zap.sell` transactions with attacker-chosen amounts, with no special timing or privileged access needed. It does not require an adversarial LT or extreme market conditions; it only requires enough buy/sell round trips (or one round trip on a token with a small `virtualLtReserve`, e.g. paired with a high-priced LT) for the accumulated flooring/slack to close the tiny gap. I was not able to execute a fuzz/PoC run against the deployed test suite to pin the exact minimal sequence of trade sizes, so the precise number of round trips needed for a given `virtualLtReserve` magnitude is unconfirmed from static review alone — this should be validated by a concrete Foundry PoC before treating the exact reproduction steps as final.

### Recommendation
Replace the plain subtraction with a saturating/guarded version everywhere `assetReserve - _launchTimeVirtualLtReserve(...)` is computed (`canGraduate`, `previewLtUntilGraduation`, `_prepareGraduationLiquidity`):
```solidity
uint256 virtualLt = _launchTimeVirtualLtReserve(token_, pair);
uint256 realLtRaised = assetReserve > virtualLt ? assetReserve - virtualLt : 0;
```
This mirrors the FlatMoney fix's intent (never let an assumed-nonnegative accounting delta revert the whole system; clamp to the true worst-case value, here `0`, instead of underflowing). Separately, consider hardening `Pair.swap`'s `+1` slack so it cannot let `assetReserve` drop below the pair's initial virtual reserve at all, since that slack is the root cause enabling the underflow.

### Proof of Concept
Conceptual reproduction (exact trade sizes require a Foundry fuzz/PoC run to pin down precisely, given the tiny wei-level margin involved):
1. `Zap.createToken(...)` launches a token with a given `ltAddress`/`exchangeRate`, fixing `virtualLtReserve = VIRTUAL_LIQUIDITY_USD * 1e18 / exchangeRate` and `k = TOTAL_SUPPLY * virtualLtReserve` in the `Pair` [7](#0-6) .
2. Attacker (or any trader) calls `Zap.buy(tokenAddress, usdcAmount, 0, referrer)` to buy some tokens on the curve.
3. Attacker calls `Zap.sell(tokenAddress, tokensJustBought, 0)` to sell the entire position back, repeating buy/sell round trips as needed so that `Pair`'s K-floor `+1` slack lets `assetReserve` settle 1–2 wei below the immutable `virtualLtReserve`.
4. The next `Zap.buy` or `Zap.sell` on this token triggers `Bonding.canGraduate` (called inline from `_executeBuy` / from `Zap._sellInternal`), which executes `assetReserve - _launchTimeVirtualLtReserve(token_, pair)` with `assetReserve < virtualLtReserve`, causing a panic 0x11 (arithmetic underflow) revert.
5. From this point, every `Zap.buy` and `Zap.sell` call against this token permanently reverts, freezing all creator/trader funds already deposited in the `Pair` with no path to graduation or exit.
