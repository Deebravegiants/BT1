### Title
`Oauth.begin_auth` fails to validate the `shop` parameter against a trusted-domain allowlist before using it to build the OAuth redirect URI, unlike every other credential-issuing flow in the gem - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` accepts a caller-supplied `shop:` string and passes it directly to `auth_base_uri(shop)` to build the URL the merchant's browser is redirected to for authorization, without ever validating that `shop` is a legitimate `*.myshopify.com` (or other trusted) domain.

### Finding Description
The equality this gem is supposed to enforce is: **the domain the app trusts as "the shop" == a domain actually issued by Shopify** (`*.myshopify.com`/`myshopify.io`/etc., as enumerated in `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`).

Every other entry point in this gem that turns a caller-supplied `shop` string into an outbound request enforces that equality with `Utils::ShopValidator.sanitize!(shop)` before constructing the session/request:

- `ClientCredentials.client_credentials`: `validated_shop = Utils::ShopValidator.sanitize!(shop)` [1](#0-0) 
- `RefreshToken.refresh_access_token`: `validated_shop = Utils::ShopValidator.sanitize!(shop)` [2](#0-1) 
- `TokenExchange.migrate_to_expiring_token`: `validated_shop = Utils::ShopValidator.sanitize!(shop)` [3](#0-2) 
- `TokenExchange.exchange_token` deliberately ignores any caller-passed `shop` and instead derives it from the HMAC-signed session token's `dest` claim [4](#0-3) 

`Oauth.begin_auth`, however, takes the raw `shop:` argument and feeds it straight into `auth_base_uri(shop)` with no call to `ShopValidator` anywhere in the method: [5](#0-4) 

```ruby
def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
  ...
  query_string = URI.encode_www_form(query)
  auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"
  { auth_route: auth_route, cookie: cookie }
end
```
and
```ruby
def auth_base_uri(shop)
  return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")
  ...
end
``` [6](#0-5) 

`begin_auth` is documented as the very first step of the OAuth flow — the gem's own docs describe `shop` as coming from the initial, pre-authentication "Add a route to start OAuth" request, i.e. before any HMAC or session has been established [7](#0-6) . Because this is the one function in the gem explicitly designed to accept an *unauthenticated, untrusted* `shop` value, and because the gem itself provides and consistently uses `ShopValidator.sanitize!` for exactly this purpose in every sibling function, its absence here is a genuine bug in this gem's own code, not a misuse of a documented contract by the host app.

The resulting `auth_route` is `https://#{attacker-controlled-host}/admin/oauth/authorize?client_id=<APP_CLIENT_ID>&scope=<SCOPES>&redirect_uri=<APP_REAL_CALLBACK>&state=<NONCE>`. If the host application follows the documented contract (redirect the browser to `auth_route` and set the returned `cookie`), the merchant's browser is sent to an attacker-chosen host carrying the app's `client_id`, requested `scope`, and the CSRF `state` nonce that is simultaneously stored in the `SessionCookie` on the victim's browser.

### Impact Explanation
This matches the report's "High — session fixation or forced OAuth completion" category. An attacker who controls the `shop` value used in `begin_auth` (e.g., because the host app passes through an unauthenticated query parameter, which the documented flow implies is the normal source of this value at install time) can:
- Force the merchant's browser to a domain of the attacker's choosing while a legitimate `state` nonce/cookie pair is being established for the app, setting up session fixation / forced OAuth completion once the attacker relays a crafted callback.
- Leak the app's `client_id` and configured `scope` to an arbitrary host.

No `client_secret` is transmitted at this step, so this does not rise to token/secret exfiltration, but it does break the domain-trust binding this gem is otherwise careful to enforce everywhere else in the credential-issuing surface.

### Likelihood Explanation
Because `shop` is exactly the field described in the docs as being the untrusted, caller-provided identifier at the very start of the flow (before any Shopify-issued HMAC exists to protect it), and because this gem elsewhere assumes callers may pass unsanitized values (hence `ShopValidator.sanitize!` calls in `client_credentials.rb` / `refresh_token.rb` / `migrate_to_expiring_token`), the missing check in `begin_auth` is reachable by design, not merely by host-app misuse.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) at the top of `Oauth.begin_auth`, exactly as done in `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and `TokenExchange.migrate_to_expiring_token`, and raise `Errors::InvalidShopError` for any shop that isn't a trusted Shopify domain, before it is used in `auth_base_uri`.

### Proof of Concept
```ruby
ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", ...)

result = ShopifyAPI::Auth::Oauth.begin_auth(
  shop: "attacker.example",              # not sanitized anywhere
  redirect_path: "/auth/callback",
)

result[:auth_route]
# => "https://attacker.example/admin/oauth/authorize?client_id=key&scope=...&redirect_uri=https://app.example.com/auth/callback&state=<nonce>"
```
Compare with the equivalent flow in `ClientCredentials.client_credentials("attacker.example")`, which raises `ShopifyAPI::Errors::InvalidShopError` via `Utils::ShopValidator.sanitize!` [8](#0-7)  — demonstrating the inconsistency is a gem-level omission rather than intended behavior.

        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end

#### 1. Add a route to start OAuth
Add a route to your app to start the OAuth process.

```ruby
class ShopifyAuthController < ApplicationController
  def login
    # This method will trigger the start of the OAuth process
  end
end
```

#### 2. Add an OAuth callback route
After the app is authenticated with Shopify, the Shopify platform will send a request back to your app using this route
(which you will provide as the `redirect_path` parameter to `begin_auth` method, in [step 3 - Begin OAuth](#3-begin-oauth)).
```ruby
class ShopifyCallbackController < ApplicationController
  def callback
    # This callback method will be called once user grants permission to this app from Shopify Admin.
  end
```

#### 3. Begin OAuth
To request access scopes from the shop during authorization code grant OAuth flow, 
configure access scopes needed by adding the `scope` parameter to the `ShopifyAPI::Context.setup` method in your configuration.

```ruby
ShopifyAPI::Context.setup(
  api_key: <SHOPIFY_API_KEY>,
  api_secret_key: <SHOPIFY_API_SECRET>,
  api_version: <SHOPIFY_API_VERSION>,
  scope: <SHOPIFY_API_SCOPES>, # Accepts array or string: "read_orders, write_products" or ["read_orders", "write_products"]
  ...
  )
```

Use [`ShopifyAPI::Auth::Oauth.begin_auth`](https://github.com/Shopify/shopify-api-ruby/blob/main/lib/shopify_api/auth/oauth.rb#L22) method to start OAuth process for your app.

#### Input
| Parameter      | Type                   | Required? | Default Value | Notes                                                                                                       |
| -------------- | ---------------------- | :-------: | :-----------: | ----------------------------------------------------------------------------------------------------------- |
| `shop`          | `String`               |    Yes    |       -       | A Shopify domain name in the form `{exampleshop}.myshopify.com`.                                            |
| `redirect_path` | `String`               |    Yes    |       -       | The redirect path used for callback with a leading `/`. The route should be allowed under the app settings. |
| `is_online`     | `Boolean`              |    No     |    `true`     | `true` if the session is online and `false` otherwise.                                                      |
