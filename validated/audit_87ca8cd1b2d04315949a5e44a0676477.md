### Title
Webhook `shop` (tenant identifier) is not covered by HMAC signature verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` authenticates an incoming webhook using an HMAC that is computed **only over the raw request body**, while the `shop` value that is later trusted and dispatched to the app's handler code comes from the unsigned `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header. This breaks the identity binding: `hmac_verified_bytes == bytes_the_app_acts_on_as_tenant_identifier`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, however, is read straight from a header that is never included in that signable string: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC exclusively against `verifiable_query.to_signable_string`: [3](#0-2) 

`Registry.process` accepts the request purely on that HMAC check and then forwards `request.shop` directly into the handler's `WebhookMetadata`, without any additional binding to a known/expected shop: [4](#0-3) 

Because the app's `client_secret` (`Context.api_secret_key`) is shared across every shop that installs the app, the HMAC over the body only proves "this body was sent by Shopify for *some* installation of this app" — it does not prove which shop it came from. The `shop` field that host applications rely on to scope data/tenant lookups (`data.shop` in the handler) is therefore an unauthenticated field acted upon as if it were verified, exactly the identity-binding gap called out in the report's bug class (a field acted on but not covered by the HMAC).

### Impact Explanation
A merchant who has installed the app on their own store (an "unprivileged internet user" with respect to every other tenant) can capture a legitimate webhook delivery for their own shop — which they can trigger themselves (e.g., placing an order to fire `orders/create`) — and replay it to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to point at a victim shop. The HMAC still validates because it never covered the shop header. If the host application's webhook handler uses `WebhookMetadata#shop` to look up the corresponding session/access token or to write data attributed to that shop (the documented and expected usage pattern of this gem), the attacker can inject cross-tenant data or trigger shop-scoped side effects for a shop they do not control — a cross-tenant access impact.

### Likelihood Explanation
Likely: no privileged credentials are required beyond a normal, self-serviceable app installation; capturing and replaying one's own webhook payload with a modified header is trivial, and the gem performs no secondary check tying the header-derived `shop` to the HMAC-covered bytes or to a known session.

### Recommendation
Include the shop domain (and topic/webhook id) inside the HMAC-signed payload verification, or require callers of `Registry.process` to cross-check `request.shop` against an independently established session/shop record before trusting it for tenant-scoped operations. At minimum, document prominently that `WebhookMetadata#shop` is not cryptographically bound by the HMAC and must not be used as a sole tenant-authentication signal.

### Proof of Concept
1. App installs on `attacker.myshopify.com`; attacker places an order, triggering Shopify to send a legitimate `orders/create` webhook with a valid `x-shopify-hmac-sha256` computed over the JSON body using the shared `client_secret`.
2. Attacker captures the raw body and HMAC header value.
3. Attacker POSTs the same raw body and same HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) succeeds because it only hashes `@raw_body`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) dispatches the handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, causing the host app to act as if the (attacker-controlled) payload originated from the victim shop.

          received_signature = verifiable_query.hmac
