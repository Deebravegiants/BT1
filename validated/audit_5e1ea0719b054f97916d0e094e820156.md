### Title
`CallDispatcher.dispatch()` has no access control, letting anyone drain transient balances/approvals it holds during `placeOrder`/`_execute`/`onAccept` composable-call flows - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch()` is a fully public function with zero caller restriction, invoked by `IntentGatewayV2.placeOrder`, `IntentsBase._execute` (fill path) and `HyperFungibleToken`/`WrappedHyperFungibleToken.onAccept` to run attacker/solver/user-supplied `Call[]` batches while tokens or ETH are sitting on the dispatcher. This is the same bug class as the Nexus `fallback()` finding: a function reachable only through a specific privileged flow in the happy path is in fact callable directly by anyone, with no check that the caller is the orchestrating contract, so any value the dispatcher happens to be holding (or approvals it grants mid-sequence) can be seized out-of-band.

### Finding Description
`CallDispatcher.dispatch(bytes memory encoded)` decodes an arbitrary `Call[]` and executes each element with `to.call{value: call.value}(call.data)` from the dispatcher's own context, with no `onlyX` modifier, no allow-list, and no `msg.sender` check whatsoever: [1](#0-0) 

Several core contracts rely on this contract holding tokens/ETH *between* separate `dispatch()` calls, not atomically within one:

- `IntentGatewayV2.placeOrder` sends predispatch assets to the dispatcher, then calls `dispatch(order.predispatch.call)`, and only afterwards issues a *second, separate* `dispatch()` call to sweep the resulting balances back to the gateway: [2](#0-1) 

- `IntentsBase._execute` (used on the fill/output side) similarly calls `dispatch(order.output.call)` first, then measures `dispatcher.balance` / `IERC20(token).balanceOf(dispatcher)` afterward and issues a *second* `dispatch()` call to sweep the residue: [3](#0-2) 

- `HyperFungibleToken`/`WrappedHyperFungibleToken.onAccept` mint/unlock tokens directly to the dispatcher's address and then call `dispatch(message.data)`, with the documentation itself acknowledging the dispatcher "holds tokens temporarily during execution": [4](#0-3) [5](#0-4) 

Because `dispatch()` has no restriction, the window between "assets/tokens arrive at the dispatcher" and "the sweep/second `dispatch()` call runs" — and any leftover dust from slippage, partial output-call execution, or an unlimited approval left outstanding by a `Call[]` — is directly reachable by an unprivileged third party. An attacker only needs to submit their own transaction calling `CallDispatcher.dispatch()` with a `Call[]` such as `[{to: token, data: transfer(attacker, dispatcher_balance)}]` (or `transferFrom` against any outstanding allowance the dispatcher granted to a spender that the attacker also controls/can trigger) before the legitimate second `dispatch()`/sweep call lands. This mirrors the report's root cause precisely: "the problem is that the function is unrestricted so it can also be called by anyone directly... This alternate call path does not check if the [orchestrating contract] is the caller... the account might have given large approvals of funds to the handler... the attacker gets to misuse the approvals."

### Impact Explanation
Any value transiently parked on the shared, permissionless `CallDispatcher` singleton — dust from slippage/partial fills in `IntentGatewayV2`/`IntentsBase._execute`, the full `order.predispatch.assets` amount sitting there between the two `dispatch()` calls in `placeOrder`, or minted/unlocked HFT/WHFT tokens sitting there before their `dispatch(message.data)` call resolves in the same call frame but leaves dust afterward — is stealable by any address, since `dispatch()` performs no authentication of the caller. This is concrete theft of user/protocol funds reachable from a single unprivileged transaction, matching the required "concrete theft ... unauthorized app action" bar, and is amplified by the protocol's own documentation admitting the dispatcher is expected to hold balances/approvals mid-flow.

### Likelihood Explanation
High: `dispatch()` requires no special permission, no proof, and no ISMP message — an attacker simply needs to observe (or predict) that value is sitting at the known `CallDispatcher` address (a single canonical, documented, publicly-listed address per chain) and race a call to `dispatch()` ahead of, or interleaved with, the legitimate follow-up sweep. Every `placeOrder` with `predispatch.call` set, every `_execute` fill with `order.output.call` set, and every HFT/WHFT `onAccept` with non-empty `data` creates such a window.

### Recommendation
Restrict `CallDispatcher.dispatch()` to only the orchestrating application contracts (an allow-list of registered callers, or an `onlyCaller`/per-invocation authorization scheme), analogous to the report's recommendation for `fallback()`: either gate the entrypoint itself, or ensure the dispatcher never persists exploitable balances/approvals across transaction boundaries (e.g., use per-call, single-use dispatcher instances via `CREATE2`/minimal proxy, or require dispatch to be invoked exclusively via a trusted caller check `require(msg.sender == authorizedCaller)`), and enforce exact (non-unlimited) approvals as already advised in the docs.

### Proof of Concept
1. A user calls `IntentGatewayV2.placeOrder` with `predispatch.call` set. The gateway `safeTransferFrom`s the predispatch assets to `_params.dispatcher`, then calls `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` [6](#0-5) .
2. Before the gateway's second `dispatch()` sweep call executes (or in a case where the predispatch call itself under-consumes the transferred assets, leaving a residual token balance on the dispatcher), an attacker submits a separate transaction directly calling `CallDispatcher.dispatch(abi.encode([Call({to: token, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, IERC20(token).balanceOf(dispatcher))})]))`.
3. `CallDispatcher.dispatch` performs no caller check [7](#0-6)  and executes the attacker's call from its own context, transferring the dispatcher's token balance to the attacker instead of back to the gateway.

contract CallDispatcher is ICallDispatcher {
    /**
     * @dev error thrown when the target is not a contract.
     */
    error NotContract(address target);

    /**
     * @dev error thrown when a call fails.
     */
    error CallFailed(address target, bytes result);

    /**
     * @dev Receive function to accept ETH transfers
     */
    receive() external payable {}

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

        PostRequest calldata request = incoming.request;

            from: message.from,
            to: beneficiary,
            source: string(request.source),

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

Existing `CallDispatcher` deployments are listed on the [contract addresses](/developers/evm/contract-addresses/mainnet) page.
