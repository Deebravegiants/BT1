### Title
Webhook `shop` identity is not bound by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its verifiable signature only over the raw webhook body, while the `shop` (tenant) identifier is read from an HTTP header that is never included in that signed string. `Utils::HmacValidator` only verifies the raw body against the app's shared `client_secret`; it never binds the `shop-domain` header to the signature. Since the HMAC secret is shared across every store that installs the app, any merchant who has legitimately installed the app can capture a valid `(raw_body, hmac)` pair from their own webhook deliveries and replay it against the app's public webhook endpoint with an arbitrary `x-shopify-shop-domain` header, causing the gem to accept and process the payload as if it came from a different (victim) shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop` is parsed straight from the `shop-domain`/`x-shopify-shop-domain` header, which is completely outside that signable string: [2](#0-1) 

`Utils::HmacValidator.validate` only recomputes and compares the HMAC over `to_signable_string`, i.e. the body, using `Context.api_secret_key`: [3](#0-2) 

`Webhooks::Registry.process` validates the HMAC and then trusts `request.shop` as the tenant identifier that is handed to the app's webhook handler: [4](#0-3) 

Compare this to the OAuth callback path, where `AuthQuery#to_signable_string` explicitly includes `shop` in the signed parameters, correctly binding the shop identity to the HMAC: [5](#0-4) 

The webhook path lacks this binding. The `client_secret` used to sign webhooks is a single app-level secret shared by all shops that install the app, not a per-shop secret, so any authenticated merchant (an "unprivileged internet user" with respect to any other tenant) can obtain a valid `(body, hmac)` pair for their own shop and then present that exact pair to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header. The check `Utils::HmacValidator.validate(request)` passes because it never looks at the header, and the forged `shop` value flows straight into `WebhookMetadata` for the handler to act on.

This breaks the identity binding: `shop asserted-by-header == shop covered-by-hmac` is false — the header is trusted for tenant attribution while the signature only covers the body.

### Impact Explanation
This is a cross-tenant access vulnerability: an app built on this gem can be made to attribute attacker-controlled webhook data (order/customer/etc. payloads under the attacker's control, since they own the body they captured) to a shop domain of the attacker's choosing, including shops they do not own or control. Any downstream logic that uses `WebhookMetadata#shop` (or `request.shop`) as a per-tenant key — updating records, revoking data, triggering GDPR mandatory webhook flows, etc. — can be poisoned for a victim tenant without the attacker ever needing the app's `client_secret`, an access token, or any credential belonging to the victim.

### Likelihood Explanation
Likelihood is realistic for any app author who installs on their own store (a normal, unprivileged action): they automatically receive real webhook deliveries with a valid `hmac` for the shared secret, capture the raw body/hmac header pair from their own traffic, and can replay it to the app's public webhook endpoint with a modified `shop-domain` header. No secret material or elevated privilege is required, only a standard app installation and the ability to send an HTTP request to the app's webhook receiver.

### Recommendation
Include the `shop` header (and ideally `topic`/`webhook-id`) in the value that is HMAC-verified for webhooks, or otherwise cryptographically bind the asserted shop to the signed payload, so that `Utils::HmacValidator.validate` fails if the `shop-domain` header does not match the shop the signature was actually generated for.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H` (valid since `H = HMAC(B, client_secret)`).
2. Attacker sends a POST request directly to the app's webhook endpoint with the same raw body `B` and same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(B, client_secret) == H` — true — and never inspects the `shop-domain` header: [6](#0-5) 
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, and any tenant-scoped side effect the app performs is executed against the victim shop's tenant using attacker-supplied data.
