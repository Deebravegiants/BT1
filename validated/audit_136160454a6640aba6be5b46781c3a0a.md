### Title
Queued governance operations remain permissionlessly executable after an emergency halt - (contracts/governance/src/timelock/mod.rs)

### Summary
XOXNO's halt analogue is controller pause plus per-listing `paused`/`frozen`/`no_seize` flags, but timelock execution does not re-check that emergency state before running a ready operation. `Governance::execute` and `execute_self` allow `executor: None`, meaning any address can drive a scheduled operation once delay and grace checks pass. [1](#0-0) [2](#0-1) 

### Finding Description
Guardian pause is immediate and role-gated, while reopening is a scheduled `AdminOperation::Unpause` resolved to controller `unpause`. [3](#0-2) [4](#0-3)  `prepare_execute` only authorizes an optional executor and checks operation expiry; it does not check whether the controller is paused or whether guardian flags were raised after scheduling. [5](#0-4)  The controller exposes owner-only `unpause`, `upgrade_pool`, `upgrade_position_nft`, and `upgrade`, with controller `upgrade` pausing before replacing Wasm rather than making the halted state irreversible. [6](#0-5) [7](#0-6)  The freeze runbook admits the gap: stale relaxations are epoch-blocked, but “Other pending operations, such as `Unpause`, still execute as proposed,” and operators are told to cancel every Waiting/Ready op manually. [8](#0-7) 

### Impact Explanation
A single unprivileged caller can execute a previously scheduled ready `Unpause`, `RelaxSpokeAssetFlags` that still names the current epoch, or upgrade operation during an incident, reopening guarded entry or replacing code while operators believe the market is halted. Reopened `paused` listings also expose borrowers to immediate liquidation because docs state there is no liquidation grace after unpause. [9](#0-8)  This is a temporary-freeze / halt-integrity failure and can become insolvency or fund theft if the queued operation is an upgrade or reopening that re-enables the attacked path. [10](#0-9) 

### Likelihood Explanation
Exploitation does not require a role if the operation was scheduled with `executor = None` semantics at call time; the attacker only supplies the ready `Operation` fields to `execute`. [11](#0-10)  The precondition is an operational one: a sensitive op must already be Waiting/Ready and not cancelled before or during the emergency, which the runbook treats as a required manual cleanup step rather than an invariant. [12](#0-11) 

### Recommendation
Make emergency state part of execution validity: reject `execute`/`execute_self` for reopening or upgrade operations while the controller is paused or relevant flags epochs changed, or automatically invalidate all non-recovery scheduled ops on guardian pause/flag ratchet. At minimum, bind `Unpause`, flag relaxation, and upgrades to an explicit emergency epoch that guardian actions bump.

### Proof of Concept
1. Proposer schedules `AdminOperation::Unpause` or `UpgradePool`; it becomes Ready.
2. Guardian calls `pause` or `set_spoke_asset_flags` to halt the incident.
3. Unprivileged attacker calls `execute(None, controller, "unpause", [], predecessor, salt)` with the scheduled operation fields.
4. `prepare_execute` performs no auth for `executor=None` and only checks expiry; `execute_operation` invokes controller `unpause`, ending the halt while guardian flags/emergency context are not consulted. [13](#0-12) [14](#0-13)

pub(crate) fn execute(
    env: &Env,
    executor: Option<Address>,
    target: Address,
    function: Symbol,
    args: Vec<Val>,
    predecessor: BytesN<32>,
    salt: BytesN<32>,
) -> Val {
    assert_with_error!(
        env,
        target != env.current_contract_address(),
        GenericError::InternalError
    );
    let operation = Operation {
        target,
        function,
        args,
        predecessor,
        salt,
    };
    let operation_id = prepare_execute(env, executor.as_ref(), &operation);
    let result = execute_operation(env, &operation);
    finish_execute(env, &operation_id);
    result
