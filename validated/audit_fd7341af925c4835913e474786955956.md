### Title
POA Bridge withdrawal status matched only by `assetId`, causing wrong-withdrawal status/hash to be reported for batched same-token withdrawals - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal()` and the standalone `waitForWithdrawalCompletion()` helper both resolve which on-chain withdrawal record corresponds to a given `WithdrawalIdentifier`/index using `findMatchingWithdrawal()`, which matches purely by `assetId` (via `near_token_id`) and ignores the `index`/per-record amount or destination. When a single NEAR transaction contains two or more withdrawals of the same token (e.g., splitting a payout to two different destination addresses), both entries resolve to the *same* (first-matched) record returned by the POA API, so the reported completion status and destination `txHash` for one withdrawal is actually the outcome of the other withdrawal.

### Finding Description
In `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`: [1](#0-0) 

`describeWithdrawal` calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which is implemented as: [2](#0-1) 

`.find()` returns the *first* array element whose `near_token_id` matches `assetId` — it never looks at `args.index`, `withdrawalParams.amount`, or `withdrawalParams.destinationAddress`. The comment in the code explicitly acknowledges: "multiple withdrawals of the same token in a single transaction are not supported." The same pattern (and same limitation) exists in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`: [3](#0-2) 

Callers such as `createWithdrawalIdentifiers` assign a distinct, per-route `index` to each withdrawal in a batch specifically so each one can be tracked independently: [4](#0-3) 

and `sdk.waitForWithdrawalCompletion` calls `describeWithdrawal` once per index expecting independent results: [5](#0-4) 

Because `findMatchingWithdrawal` disregards `index`, if a batch contains two withdrawals of the same `assetId` (e.g., 100 USDT to address A at index 0 and 100 USDT to address B at index 1), both `describeWithdrawal({index:0, ...})` and `describeWithdrawal({index:1, ...})` calls will match the **same** first record in `response.withdrawals` and return the **same** `status`/`txHash`. This breaks the equality "status/txHash reported for withdrawal N == actual on-chain outcome of withdrawal N": the SDK reports completion (and a destination transaction hash) for a withdrawal that has not actually happened yet, using another withdrawal's already-completed transaction as if it were this one's.

### Impact Explanation
An integrator relying on `describeWithdrawal`/`waitForWithdrawalCompletion` to confirm each individual withdrawal in a batch (e.g., to release custody, mark an invoice paid, or credit an off-chain ledger) can be made to believe withdrawal index 1 (destined for address B) is "completed" using a tx hash that actually sent funds to address A. This is a status/hash misreport that can cause an integrator to credit or consider settled a transfer that never reached its intended destination — matching the High-impact category ("a status or hash misreport making an integrator credit or refund twice"). It requires no privileged action; any normal user/integrator batching two same-token withdrawals to different destinations triggers it.

### Likelihood Explanation
This is reachable through completely normal, documented SDK usage (batch withdrawals of the same asset to different destinations), not an adversarial edge case requiring a malicious actor. The code comment itself acknowledges the limitation exists today and is unresolved, which corroborates that this is a live, unaddressed condition in the current codebase.

### Recommendation
Extend `findMatchingWithdrawal` (in both `poa-bridge.ts` and `waitForWithdrawalCompletion.ts`) to disambiguate multiple same-asset withdrawals within a single transaction — e.g., by consuming matched records so each is only returned once per polling pass, or by sorting both the API response and the requested `withdrawalParams` deterministically (e.g., by amount/destination) and pairing them positionally, as the existing code comment already suggests. At minimum, `describeWithdrawal` should never return the same underlying withdrawal record for two different indices.

### Proof of Concept
1. Submit a batch withdrawal transaction with two `WithdrawalParams` entries for the same `assetId` (e.g., `nep141:btc.omft.near`), amount 100000, destined to two different addresses A and B; the SDK assigns index 0 and 1 respectively via `createWithdrawalIdentifiers`.
2. The POA bridge indexer completes the withdrawal to address A first (data has `near_token_id: "btc.omft.near"`, `transfer_tx_hash: "hash-A"`), while the withdrawal to address B is still pending.
3. Call `describeWithdrawal({index:0, withdrawalParams:{assetId:"nep141:btc.omft.near",...}})` and `describeWithdrawal({index:1, withdrawalParams:{assetId:"nep141:btc.omft.near",...}})`.
4. Both calls invoke `findMatchingWithdrawal(withdrawals, "nep141:btc.omft.near")`, which `.find()`s the same single record (`hash-A`) for both, so index 1 (destined to B) is incorrectly reported `{status:"completed", txHash:"hash-A"}` even though that transfer went to A and B's transfer hasn't executed — as reproduced by the existing test `it("matches withdrawal by assetId, not by index", ...)` at [6](#0-5)  which demonstrates the same-`assetId`-collision resolution path.

		args: WithdrawalIdentifier & { logger?: ILogger },

		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index

			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
