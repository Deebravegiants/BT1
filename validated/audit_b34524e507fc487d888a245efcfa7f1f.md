### Title
Webhook tenant identity (`shop-domain`, `topic`, `webhook-id`) is not covered by the HMAC signature, allowing cross-tenant data attribution - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw request body only, while the shop identity (`shop-domain` header) that the application uses to attribute the webhook to a specific merchant/tenant is taken from an unsigned header. This breaks the intended binding `hmac == HMAC(secret, body + shop)` down to `hmac == HMAC(secret, body)`, letting an attacker who controls one legitimate, validly-signed webhook body (e.g., from their own store) relabel it as belonging to a different shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `#shop`, `#topic`, and `#webhook_id` are pulled straight from HTTP headers that are never mixed into the signed string: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` confirm that the check is purely `computed_signature(to_signable_string) == received_signature`, with `to_signable_string` never including the shop: [4](#0-3) 

`WebhookMetadata.shop` is a plain, unauthenticated field the gem forwards to the developer's `WebhookHandler#handle`: [5](#0-4) 

**Identity binding broken (as an equality):**
Intended: `shop_used_by_handler == shop_the_HMAC_secret_actually_authenticated_for`
Actual: `shop_used_by_handler == shop_header_value` (attacker-controlled, unauthenticated), independent of what the HMAC covers.

Because Shopify computes each shop's webhook HMAC over the JSON body with the app's shared secret, and the body content for many topics is attacker-influenceable (an attacker owns a development store, can trigger webhooks such as `orders/create`, `app/uninstalled`, `customers/data_request`, etc., with content they control), a merchant with access to only their own store can:
1. Trigger a webhook from their own shop, capturing a `(raw_body, hmac)` pair that is legitimately signed by Shopify with the app's secret.
2. Replay that exact `(raw_body, hmac)` to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header with a different shop's domain.
3. `HmacValidator.validate` still succeeds — it never inspects the shop header — so `Registry.process` dispatches the (attacker-controlled) body to the handler while asserting `data.shop` is the victim shop.

This is exactly the "field acted on but not covered by the HMAC" analog: the shop identity that downstream code trusts for tenant scoping is not part of the authenticated bytes.

### Impact Explanation
Any application that uses `data.shop` from `WebhookMetadata` to select which tenant's records to create/update/delete (a standard and expected usage pattern encouraged by this gem's own docs) can be tricked into writing attacker-supplied webhook payloads into another shop's tenant data store, or into believing GDPR/mandatory webhooks (`customers/redact`, `shop/redact`, `customers/data_request`) originated from a different shop than they actually did. This crosses a tenant boundary using only a legitimate, non-privileged Shopify development-store account and no access to the app's `client_secret`/access tokens — matching the "cross-tenant access" Critical-impact category.

### Likelihood Explanation
Exploitation requires only: (a) a free/registered development store capable of receiving webhooks for the same app (any merchant who installs the app can do this), and (b) the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with modified headers, both of which are trivial for any unprivileged internet user/merchant. No credential theft, TLS interception, or social engineering is needed.

### Recommendation
Include the tenant/shop identity (and ideally topic and webhook id) in the signed payload, or validate the shop header against an independently trusted source (e.g., the shop associated with the currently installed access token/session, cross-checked via a separate authenticated API call) before dispatching to the handler. At minimum, document prominently that `WebhookMetadata.shop` is not authenticated by HMAC and must not be trusted for tenant scoping without additional verification (e.g., confirming the shop has an active, matching session/installation record) in `lib/shopify_api/webhooks/registry.rb` and `lib/shopify_api/webhooks/request.rb`.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and the target app is installed there.
# Step 1: Attacker triggers any webhook (e.g. orders/create) on their own shop and
# captures the raw body + the valid HMAC Shopify computed with the app's secret:
raw_body = '{"id":1,"note":"payload attacker controls"}'
hmac     = Base64.encode64(OpenSSL::HMAC.digest("sha256", app_secret, raw_body))
# (app_secret unknown to attacker; this hmac/body pair is legitimately produced
#  by Shopify for attacker-shop.myshopify.com)

# Step 2: Attacker replays the exact same body+hmac to the app's webhook endpoint,
# but swaps the shop-domain header to the victim shop:
headers = {
  "x-shopify-topic"       => "orders/create",
  "x-shopify-hmac-sha256" => hmac,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # spoofed
  "x-shopify-webhook-id"  => "any-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (HMAC only covers raw_body),
#    and the handler receives WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
#    even though the payload actually originated from attacker-shop.
```
This demonstrates the app can be made to process attacker-controlled webhook content under a victim shop's identity, purely because `Request#to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`) and `HmacValidator` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) never bind the shop header into the signature check.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
