### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing a validly-signed webhook to be replayed under a spoofed tenant identity - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body [1](#0-0) . The `shop` value that is then handed to the host application's handler as the tenant identifier is read from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is never included in the signed bytes [2](#0-1) [3](#0-2) . This breaks the equality `bytes_verified (raw_body) == identity_used_for_tenant_attribution (shop header)`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [3](#0-2) , and `HmacValidator.validate_signature` computes/compares the HMAC exclusively against that string [4](#0-3) . Meanwhile `Request#shop` is parsed straight out of the `shopify-shop-domain` header with no cryptographic binding to the signed payload [2](#0-1) . `Registry.process` checks only `Utils::HmacValidator.validate(request)` and then immediately trusts `request.shop` to build the `WebhookMetadata` that is passed to the app's handler [5](#0-4) .

Because the HMAC in this gem is computed with the app's single, shared `api_secret_key` for every shop that installs the app (not a per-shop secret), any shop that installs the app can obtain a genuinely-signed webhook body/HMAC pair for its own shop (Shopify signs and delivers these webhooks automatically on ordinary events like `orders/create`). That attacker-controlled tenant can then replay the exact same `raw_body` + `hmac` to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. `HmacValidator.validate` still returns `true` because the header is outside the signed bytes, and the handler receives `shop: "victim-shop.myshopify.com"` (or any other value) attached to the attacker's payload.

### Impact Explanation
This crosses the tenant boundary the gem is responsible for establishing: the shop identity that host applications rely on to attribute webhook data (order/customer data, redact requests, etc.) to the correct merchant is not authenticated by this library at all — only the body content is. A malicious merchant/app-installer can therefore inject data attributed to a different shop into any handler that trusts `WebhookMetadata#shop` (e.g., to look up/store per-shop records, or to satisfy `customers/redact`/`shop/redact` mandatory webhook flows), which is a cross-tenant data-integrity/spoofing issue stemming directly from a gem-level identity-binding gap.

### Likelihood Explanation
No access token, `client_secret`, or privileged account is required beyond becoming a normal (even free) installer of the target app — which is the "unprivileged internet user" position described by the bug-class hint. The attacker only needs to capture one legitimately delivered webhook for their own shop (trivial, since Shopify sends these automatically) and replay it with a modified header, which is a standard HTTP replay requiring no cryptographic secret.

### Recommendation
Include the shop domain (and topic) inside the HMAC-signed material, or otherwise cryptographically bind the header value to the verified body — e.g., have `Request#to_signable_string` incorporate `shop`/`topic`/`webhook_id` alongside the raw body, or independently verify the `shop-domain` header against a value obtained from an authenticated source (such as the registered session for the topic) rather than trusting the raw header. At minimum, document that `WebhookMetadata#shop` is unauthenticated and must not be used by host applications as the sole tenant key without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (no special privilege required).
2. Shopify delivers a legitimate webhook (e.g., `orders/create`) to the app's endpoint with headers `shopify-hmac-sha256: <valid-hmac-of-body>`, `shopify-shop-domain: attacker-shop.myshopify.com`, and some JSON body `B`.
3. Attacker captures `B` and the valid `hmac`, then re-POSTs the same body/hmac to the app's webhook endpoint but sets `shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `hmac_of(B)` [1](#0-0) .
5. `handler.handle` is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` [6](#0-5) , causing the host application to process attacker-supplied data under the victim shop's identity.
