### Title
Permanent, unrecoverable loss of encrypted biometric custody data on client-error upload failure in `data-uploader` agent - (File: src/agents/data_uploader.rs)

### Summary
The referenced bug class (force deployment loop that keeps advancing while the failed sub-operation's associated resource is neither refunded nor retried, silently stranding funds) has a direct analog in the `data-uploader` agent, which permanently discards a user's personal-custody package (PCP) tier-1/tier-2 biometric data when the upload fails with a client error, while still marking the item as "committed"/done.

### Finding Description
The `Agent::upload_pcp` loop in `src/agents/data_uploader.rs` retries the personal-custody-package upload indefinitely, but on a client HTTP error it simply `break`s out of the retry loop and returns `(tier, id)` as if the operation had produced a valid, final outcome: [1](#0-0) 

Back in the agent's main event loop, that returned `(tier, id)` unconditionally triggers `queues[...].commit(id)`, which removes the item from the queue (and, for the persistent variant, deletes the on-disk `meta.json`/`data.bin` for that entry): [2](#0-1) [3](#0-2) 

There is no distinction in the returned value between "successfully uploaded" and "gave up after a client error"; both paths feed into the same `commit()` call, which is the sole bookkeeping mechanism tracking whether the PCP has been durably delivered to the backend. Just as `ContractDeployer.forceDeployOnAddresses` compares the aggregated `msg.value` against a running total rather than tracking per-item success/failure and leaves ETH stuck in the contract when one sub-deployment fails, this loop tracks completion by queue/id bookkeeping rather than by verified backend acknowledgment, and permanently drops (rather than recovering or re-queuing) the biometric package when the sub-operation fails.

### Impact Explanation
The dropped item is the encrypted personal-custody package (tier-1 and/or tier-2), which contains the user's iris/face biometric commitments and the only mechanism for later self-custody/retrieval of that biometric data (`src/plans/personal_custody_package.rs`, `src/plans/mod.rs::do_signup` enqueues tier1/tier2 to `data_uploader::Input::Pcp` for pcp_version >= 3, at [4](#0-3) ). If the upload agent hits a client error (e.g. transient auth/validation issue) once, the package is deleted from the local queue/disk and never retried, uploaded, or reported as failed to the calling signup plan — there is no callback, error propagation, or notification back into the signup flow. This is a silent, permanent loss of biometric custody data tied to a specific signup with no recovery path, directly mirroring the "loss of funds" impact structure of the referenced report (resource consumed/marked-done on failure, with no sweep/retry/notification).

### Likelihood Explanation
This path is reachable in every normal PCP v3 signup (no privileged access, malicious peer, or hardware access required) — it triggers whenever the backend `upload_personal_custody_package` endpoint returns any 4xx-class response during tier-1/tier-2 upload, which the reporter class explicitly notes is "not low probability" (network/backend validation errors are a normal occurrence, not an edge case).

### Recommendation
Distinguish "uploaded" from "permanently failed" outcomes in `upload_pcp`'s return value, and do not call `commit()` (which deletes the persisted/queued data) on failure. On unrecoverable failure, either keep the item queued for a bounded number of retries with backoff, or explicitly surface the failure to the signup flow (e.g., via a status callback / dbus signal) so the failure can be logged, retried later, or the user re-signed-up, instead of silently discarding the biometric custody package.

### Proof of Concept
1. A signup with `pcp_version >= 3` completes tier-0 upload successfully and enqueues tier-1/tier-2 packages via `data_uploader::Input::Pcp` (`src/plans/mod.rs:613-636`).
2. `Agent::upload_pcp` (`src/agents/data_uploader.rs:170-217`) calls `backend::upload_personal_custody_package::request`; assume the backend returns a 4xx (client error) response for this request.
3. The `Err` branch downcast succeeds, `status.is_client_error()` is true, and the loop `break`s, returning `(tier, id)` exactly as the success path would.
4. The main agent loop receives `(tier, id)` from `uploaders.next()` and calls `queues[tier-1].commit(id).await`, which removes/deletes the queued/persisted PCP data (`src/agents/data_uploader.rs:119-121`, `321-341`).
5. The tier-1/tier-2 biometric custody package for that signup is now permanently gone; no retry occurs and no error is reported anywhere upstream — an unrecoverable data loss with no sweep/notification path, analogous to ETH being stranded when a `forceDeployOnAddresses` sub-call reverts.

                *in_progress = in_progress.checked_sub(1).expect("shouldn't go negative");
