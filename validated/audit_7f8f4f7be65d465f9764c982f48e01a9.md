### Title
Inverted `drop_oldest()` in Personal-Custody Package Upload Queue Deletes Newest Biometric Data Instead of Oldest - (File: src/agents/data_uploader.rs)

### Summary
The `data_uploader` agent maintains per-tier FIFO queues of `Pcp` (Personal-Custody Package) structures containing biometric signup data (`signup_id`, `user_id`, encrypted image/data payload, checksum) awaiting upload to the backend. When a queue reaches its configured "dropping threshold," the code is supposed to evict the oldest item to make room for new captures, but the eviction function actually removes the newest item due to using the wrong end of the underlying `VecDeque`. This mirrors the reported analog bug class: a data structure is pushed at one end and consumed at the other (FIFO semantics), but the "remove specific/intended element" operation silently operates on the wrong element, causing unintended loss of legitimate, non-targeted data.

### Finding Description
Items are always inserted at the back of the queue: [1](#0-0) 
and normal consumption (`pop`) removes from the front, i.e., FIFO — the front is the oldest item, the back is the most recently pushed item: [2](#0-1) 

However, `drop_oldest()`, which is explicitly meant to evict the oldest queued package once the per-tier dropping threshold is reached, calls `pop_back()` on both the in-memory and persistent variants of the queue — removing the most recently pushed (newest) package instead of the oldest one: [3](#0-2) 

This function is invoked from the main agent loop exactly when a tier's queue length equals `dropping_thresholds[i]`, immediately before pushing the new incoming `Pcp`: [4](#0-3) 

Because `drop_oldest()` pops from the back (the newest previously-queued entry, i.e., the entry that was pushed just before the current one) rather than the front (the oldest, longest-waiting entry), the queue's intended "drop oldest to bound backlog" policy is inverted: the stalest entries are never purged, while entries that were queued moments earlier are discarded to make room for whatever arrives next. As with the reported `_removeOrder()` bug — where `_addOrder()` appends to one end of a linked list while `_removeOrder()` blindly pops from the other end without validating identity — here `push()` appends to the back while `drop_oldest()` blindly pops from the back as well (instead of the front where the true "oldest" element resides), producing a structural mismatch between insertion order and the intended eviction target.

### Impact Explanation
The `Pcp` queue carries personal-custody biometric upload packages tied to a specific `signup_id`/`user_id`. If the oldest backlog entry is problematic (e.g., consistently failing to upload, or the queue is persistently near-full), this bug causes freshly captured biometric packages to be silently and permanently discarded (their on-disk directory removed in the persistent variant) while the stale, non-representative backlog entry is retained indefinitely. This is a data-retention correctness defect for locally custodied biometric data: the enforcement of "evict stalest / retain most recent" backlog behavior is inverted, risking unintended, non-deterministic loss of legitimate biometric upload data rather than the intended stale data.

### Likelihood Explanation
This path executes automatically, without any special user action, whenever the tier1/tier2 dropping threshold is reached during normal operation (i.e., uploads falling behind ingestion rate). It requires no attacker interaction — it is a latent logic defect that triggers under ordinary backlog conditions, making it moderately likely to manifest during periods of degraded network connectivity or backend slowness where custody-package upload lags behind capture.

### Recommendation
Fix `drop_oldest()` to evict from the front of the queue (matching `pop()`/FIFO semantics) instead of the back, for both `Queue::Memory` and `Queue::Persistent` variants:
```rust
async fn drop_oldest(&mut self) {
    match self {
        Self::Memory { queue } => {
            queue.pop_front();
        }
        Self::Persistent { path, queue, .. } => {
            let Some(id) = queue.pop_front() else { return };
            // ... remove path.join(id.to_string())
        }
    }
}
```
Add a regression test asserting that, after pushing N+1 items past the dropping threshold, the surviving items are the most recently pushed ones and the very first (oldest) push is the one removed.

### Proof of Concept
Given `dropping_threshold = 2`:
1. Push `Pcp{id=A}` → queue: `[A]` (A pushed at t0).
2. Push `Pcp{id=B}` → queue: `[A, B]` (queue length now equals threshold).
3. Next incoming `Pcp{id=C}` triggers `drop_oldest()` before pushing C:
   - Expected: oldest (`A`) is evicted → queue becomes `[B]`, then C pushed → `[B, C]`.
   - Actual (per code at [5](#0-4) ): `pop_back()` removes `B` (the newest queued item) → queue becomes `[A]`, then C pushed → `[A, C]`.
4. Result: package `B`'s biometric custody data is permanently lost (persistent variant deletes its on-disk directory), while stale package `A` remains stuck in the backlog — the opposite of the intended retention policy.
