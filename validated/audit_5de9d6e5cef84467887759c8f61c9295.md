### Title
First-ever state machine commitment for a state machine is silently dropped due to an `latestHeight != 0` guard, permanently blocking that route - (File: `evm/src/core/HandlerV2.sol`)

### Summary
`HandlerV2.handleConsensus` only persists a new `IntermediateState` commitment when the state machine already has a non-zero recorded `latestStateMachineHeight`. A state machine whose height has never been initialized (the default/unset value is `0`) can never have its first commitment stored, because the guard `latestHeight != 0 && intermediate.height > latestHeight` fails on the very first legitimate update. This is analogous to the CVE-2021-47284 bug class: state (`card->irq` / here, `latestStateMachineHeight`) is treated as "already correctly initialized" by a later code path, when in fact the zero value is indistinguishable from "never set", causing the handling logic to behave incorrectly on the very first pass.

### Finding Description
In `evm/src/core/HandlerV2.sol`, `handleConsensus` iterates the `intermediates` returned by the consensus client's `verify()` call: [1](#0-0) 

```solidity
for (uint256 i = 0; i < intermediatesLen; i++) {
    IntermediateState memory intermediate = intermediates[i];
    uint256 latestHeight = host.latestStateMachineHeight(intermediate.stateMachineId);
    if (latestHeight != 0 && intermediate.height > latestHeight) {
        StateMachineHeight memory stateMachineHeight =
            StateMachineHeight({stateMachineId: intermediate.stateMachineId, height: intermediate.height});
        host.storeStateMachineCommitment(stateMachineHeight, intermediate.commitment);
    }
}
```

`latestStateMachineHeight(id)` reads `_latestStateMachineHeight[id]`, a `mapping(uint256 => uint256)` whose default value for any state machine ID that has never had a commitment stored is `0`. The only other place `_latestStateMachineHeight` is written is in the admin-only, one-shot bootstrap function `setConsensusState`: [2](#0-1) 

For any state machine that the consensus client (BEEFY, SP1, sync-committee, GRANDPA, etc.) begins reporting intermediate states for *without* having been seeded via `setConsensusState` (e.g., a new parachain/state machine added to the connected relay chain after genesis, or one whose first proof simply predates any admin seeding), `latestHeight` is `0` on the first `handleConsensus` call that includes it. Because the guard requires `latestHeight != 0`, the very first, legitimately verified commitment for that state machine is silently discarded — `storeStateMachineCommitment` is never invoked, and `_latestStateMachineHeight` is never advanced past `0` for that ID by this path. Every subsequent `handleConsensus` call for that state machine hits the exact same `latestHeight == 0` condition, so the state machine can never receive a first commitment through the normal consensus-update path at all. This is a straightforward "zero used as sentinel for unset, but zero is also a valid/possible state" ordering bug, in the same spirit as `card->irq` being read as "already requested" in the Linux CVE, when it was in fact never validly set.

### Impact Explanation
Once a state machine is caught in this state, no proof (`handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, etc.) referencing any height of that destination/source state machine can ever be verified, since `EvmHost.stateMachineCommitment(height)` will always be empty (`overlayRoot == 0`), causing `StateCommitmentNotFound` reverts in every message-handling path in `HandlerV2.sol`. This permanently freezes message delivery for that state machine — a "route unable to deliver messages" condition — reachable from a completely unprivileged relayer simply submitting a valid consensus proof through `handleConsensus`, with no admin or governance action needed to trigger the bug (only to avoid it, by pre-seeding via `setConsensusState`).

### Likelihood Explanation
This triggers deterministically, not probabilistically, whenever a new state machine's first `IntermediateState` arrives without prior admin seeding via `setConsensusState`. Any relayer (fully unprivileged, since `handleConsensus` has no access restriction beyond `notFrozen`) can trigger the code path by submitting the first valid consensus proof; no malicious behavior is required — this is a correctness bug in the mainline path.

### Recommendation
Do not use `latestHeight != 0` as a proxy for "state machine previously initialized." Track initialization explicitly (e.g., via a separate `mapping(uint256 => bool) initializedStateMachine`, or by checking `stateMachineCommitment` existence) so that the first ever commitment for a state machine is always stored when `intermediate.height` is greater than or equal to whatever the true "unset" sentinel should be, rather than being unconditionally skipped when the recorded height happens to equal the zero default.

### Proof of Concept
1. Deploy `EvmHost` and configure a consensus client (e.g., BEEFY) for a state machine ID `X` that has never been passed to `setConsensusState`.
2. As any relayer, call `HandlerV2.handleConsensus(host, proof)` with a valid consensus proof whose `IConsensusV2.verify()` output includes an `IntermediateState` for state machine `X` at height `H`.
3. Observe: `host.latestStateMachineHeight(X)` returns `0` (never seeded), so `latestHeight != 0` is `false`; `storeStateMachineCommitment` is never called for `X`.
4. Any subsequent `handlePostRequests`/`handleGetResponses` call referencing a proof height for state machine `X` reverts with `StateCommitmentNotFound` because `host.stateMachineCommitment(height).overlayRoot == bytes32(0)`.
5. Repeat step 2 with further valid consensus proofs for `X`: `latestStateMachineHeight(X)` remains `0` forever through this path, so the condition never becomes true and `X` can never receive a commitment via `handleConsensus`.
