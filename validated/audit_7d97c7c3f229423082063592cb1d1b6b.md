### Title
`Oauth.begin_auth` builds the OAuth authorization redirect from an unvalidated `shop` string, leaking the CSRF `state` nonce to attacker-controlled hosts and enabling forced OAuth / session-fixation - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` accepts a caller-supplied `shop` and builds the OAuth authorization URL with `auth_base_uri(shop)`, which is simply `"https://#{shop}/admin"` [1](#0-0) . Unlike other entry points in this same gem that accept a `shop` string (e.g. `TokenExchange.migrate_to_expiring_token` and `Clients::Graphql::Storefront.new`, both of which call `Utils::ShopValidator.sanitize!`), `begin_auth` performs **no host validation at all** on `shop` before using it to construct the redirect target and embed the anti-CSRF `state` value in that URL's query string [2](#0-1) . The documented, intended usage is for `shop` to come straight from the initial (pre-auth, unauthenticated) request, e.g. `shop = request.headers["Shop"]` [3](#0-2) , so the gem is squarely responsible for sanitizing it, exactly as it already does for other similar inputs (`Utils::ShopValidator`) [4](#0-3) .

### Finding Description
The binding that should hold is: **host that receives the CSRF `state` nonce == a trusted Shopify domain** (as enforced elsewhere by `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`). Instead, in `begin_auth`, that equality is never checked:

```ruby
def auth_base_uri(shop)
  return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")
  ...
end
``` [5](#0-4) 

`begin_auth` interpolates this attacker-influenceable `shop` value directly into `auth_route`, which also carries the freshly-generated CSRF `state` nonce and the app's `redirect_uri`:

```ruby
state = SecureRandom.alphanumeric(NONCE_LENGTH)
cookie = SessionCookie.new(value: state, expires: Time.now + 60)
query = {
  client_id: ShopifyAPI::Context.api_key,
  scope: scope.to_s,
  redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
  state: state,
  "grant_options[]": is_online ? "per-user" : "",
}
query_string = URI.encode_www_form(query)
auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"
``` [6](#0-5) 

If a merchant/browser is directed into the flow with an attacker-supplied `shop` (e.g. `shop=attacker.example`), `auth_route` becomes `https://attacker.example/admin/oauth/authorize?...&state=<NONCE>...`, and the merchant's browser is redirected there while the `SessionCookie` containing the same `NONCE` is set on the app's domain. The `state` value is thereby disclosed to the attacker's server via the redirect, purely from an unauthenticated request — no secret, token, or privileged access is required to trigger `begin_auth` with a hostile `shop`.

Once the attacker knows the victim's `state` nonce, they can complete `validate_auth_callback` on the victim's behalf using a *legitimately Shopify-signed* callback for a shop the attacker controls (e.g. their own `evil.myshopify.com` install), because `validate_auth_callback` only checks `state == auth_query.state` and the HMAC of the (real) Shopify-issued query — it never verifies that the `shop` in the callback matches the `shop` the victim originally started with:

```ruby
state = cookies[SessionCookie::SESSION_COOKIE_NAME]
raise Errors::NoSessionCookieError unless state
raise Errors::InvalidOauthError,
  "Invalid state in OAuth callback." unless state == auth_query.state
null_session = Auth::Session.new(shop: auth_query.shop)
``` [7](#0-6) 

Since the attacker knows and controls both the leaked `state` and their own real, Shopify-signed `code`/`hmac` (obtained by simply installing the app on their own shop), they can get the victim's browser to complete the callback bound to the attacker's shop, fixing the victim's app session to the attacker's Shopify store. This is a textbook forced-OAuth-completion / session-fixation primitive, explicitly called out as a High-severity impact category in scope.

### Impact Explanation
This breaks the intended trust boundary that ties a merchant's OAuth session/state to the shop *they* intended to authenticate. An attacker can:
- Leak/predict a specific victim's CSRF `state` nonce by forcing them through `begin_auth` with an attacker-chosen `shop`.
- Complete the callback with their own legitimately-signed OAuth grant, causing the victim's browser/session to be fixated on the attacker's shop/session (session fixation / forced OAuth completion).

This matches the "High - session fixation or forced OAuth completion" impact category.

### Likelihood Explanation
The `shop` parameter used to start OAuth is, per the gem's own documentation, taken directly from an unauthenticated pre-auth request (header, query param, subdomain, etc.) with no server-side trust established yet [3](#0-2) . Any host application that follows the gem's documented usage pattern and does not itself re-implement host validation before calling `begin_auth` is exposed. Given that the gem exposes `Utils::ShopValidator` and uses it in other, less security-critical call sites (`TokenExchange.migrate_to_expiring_token`, `Clients::Graphql::Storefront.new`) but conspicuously omits it here, this is a straightforward, no-secret, unauthenticated-attacker-triggerable condition.

### Recommendation
Validate/sanitize `shop` in `Oauth.begin_auth` using the same `Utils::ShopValidator.sanitize!` mechanism already used elsewhere in the gem before it is used to build `auth_base_uri`/`auth_route`, raising `Errors::InvalidShopError` for any shop that isn't a trusted Shopify domain. Additionally, `validate_auth_callback` should assert that `auth_query.shop` matches the shop the flow was originally started for (e.g., store the expected shop alongside the `state` cookie and compare it during callback validation), not just that `state` matches.

### Proof of Concept
1. A vulnerable host app's login route does: `ShopifyAPI::Auth::Oauth.begin_auth(shop: params[:shop], redirect_path: "/auth/callback")`, following the gem's documented pattern of taking `shop` from the initial unauthenticated request.
2. Attacker sends a victim a link to that login route with `shop=attacker.example`.
3. `begin_auth` returns `auth_route = "https://attacker.example/admin/oauth/authorize?...&state=<NONCE>..."` and a `SessionCookie` with `value: <NONCE>` set in the victim's browser for the app's domain.
4. Victim's browser is redirected to `https://attacker.example/...`, which the attacker controls, so the attacker's server logs `<NONCE>` from the query string.
5. Attacker separately performs a legitimate OAuth install of the target app on their own real Shopify shop (`evil.myshopify.com`), obtaining a Shopify-issued, correctly HMAC-signed `code`/`hmac` for `shop=evil.myshopify.com`.
6. Attacker lures the victim (still holding the `state` cookie from step 3) to visit `https://app.example.com/auth/callback?shop=evil.myshopify.com&code=<attacker_code>&hmac=<valid_hmac>&timestamp=...&state=<NONCE>`.
7. `validate_auth_callback` passes: HMAC is valid (genuinely signed by Shopify for `evil.myshopify.com`), and `state == auth_query.state` matches because it's the same nonce leaked in step 4. The victim's session/cookie becomes bound to `evil.myshopify.com` — a session-fixation / forced OAuth completion against the victim, achieved without ever knowing the app's `api_secret_key`.

        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings

        end
