Found it. The bug is in `evm/rust/src/conversions.rs`, in the `From<Vote> for SignatureWithAuthorityIndex` conversion, which is reachable from a naive BEEFY consensus proof submitted through `submit_proof` on `pallet-beefy-consensus-proofs`.

### Title
Unchecked `copy_from_slice` from ABI-decoded `Vote.signature` panics on any length ≠ 65, allowing an unprivileged submitter to DoS BEEFY consensus proof processing - ([File: evm/rust/src/conversions.rs])

### Summary
`evm/rust/src/conversions.rs` converts a Solidity-ABI-decoded `Vote` (from `BeefyConsensusProof.relay.signedCommitment.votes`) into `SignatureWithAuthorityIndex` by copying `value.signature.to_vec()` into a fixed `[u8; 65]` buffer with `copy_from_slice`, without validating the length first: [1](#0-0) 

`Vote.signature` is an ABI `bytes` field with no length constraint enforced by the Solidity ABI decoder, so `abi_decode_params` accepts a `Vote` whose `signature` is any length. `copy_from_slice` panics if `sig_bytes.len() != 65`.

### Finding Description
This is the same bug class as the CVE: writing attacker-controlled, variable-length data into a fixed-size buffer without validating the length first (in libspf2, `sprintf` overflowed a 4-byte buffer; here, `copy_from_slice` overruns/panics on a mismatched-length write into `[u8; 65]`). Rust's memory safety converts what would be a heap overflow/RCE in C into a guaranteed panic — but the panic is fully attacker-triggerable from untrusted, unsigned/relayer-submitted proof bytes and reachable through the pallet's public dispatch path.

The call chain:
1. `pallet-beefy-consensus-proofs::submit_proof` (any signed account can call it) hands the raw proof bytes to `do_submit_proof` → `verify_and_apply`. [2](#0-1) 
2. For `PROOF_TYPE_NAIVE`, `verify_and_apply` ABI-decodes the caller-supplied bytes into `ismp_abi::ecdsa_beefy::BeefyConsensusProof`, then calls `.into()`, which routes through the `From<RelayChainProof> for MmrProof` and `From<Vote> for SignatureWithAuthorityIndex` impls in `evm/rust/src/conversions.rs`. [3](#0-2) 
3. `From<RelayChainProof> for MmrProof` maps every entry of `value.signedCommitment.votes` through `Into::into`, i.e. through the vulnerable `From<Vote>`: [4](#0-3) 
4. The vulnerable conversion itself: [1](#0-0) 

Nothing between ABI-decoding the caller's `proof` bytes and this conversion validates that each `Vote.signature` is exactly 65 bytes — the length is only implicitly assumed by the buffer size. This is squarely the pattern the repository has otherwise hardened against elsewhere (e.g. `modules/utils/serde/src/lib.rs`'s `as_utf8_string`/`StateMachineId` fixes, and the pharos SPV `MAX_PROOF_DEPTH`/`nibble_at_depth` bounds-checking fixes, both explicitly documented as "must not panic on untrusted input" regressions), but this particular conversion path was missed. [5](#0-4) 

### Impact Explanation
Any account (the pallet only requires `ensure_signed`, no permissioning) can submit a malformed naive BEEFY proof with a `Vote.signature` field of any length other than 65 bytes and crash/panic the runtime call. In a Substrate/FRAME runtime, an unhandled panic inside pallet dispatch logic is typically caught by the executive's panic handler and turned into a failed extrinsic, but if this conversion is exercised in a context without panic-unwind safety (e.g. inside `on_initialize`/off-chain worker paths, or if `panic = "abort"` is configured for the runtime, or via `beefy_verifier::error` propagation paths that assume `Result`, not panics) it can abort block execution, effectively halting BEEFY consensus updates or crashing the node process. At minimum this is a reliable, cheap, single-extrinsic denial-of-service against the BEEFY consensus proof pathway, blocking the route that carries parachain state commitments into Hyperbridge (a "route unable to deliver messages" condition), justifying High severity.

### Likelihood Explanation
High likelihood: the path is reachable by a single unsigned/permissionless account submitting one extrinsic (`submit_proof`) with an intentionally malformed `Vote.signature` length; no privileged role, no state precondition, and no complex proof construction beyond a valid ABI encoding with an incorrect one byte-array length is required.

### Recommendation
In `evm/rust/src/conversions.rs`, replace the unchecked `copy_from_slice` with a fallible conversion (e.g. `TSignature::try_from(sig_bytes.as_slice())`) and propagate an error (or reject the proof) when `sig_bytes.len() != 65`, mirroring the pattern already used elsewhere in the codebase (`WithdrawalParamsError::InvalidBeneficiaryAddressLength`, the `as_utf8_string` length-checked deserializer) instead of panicking on untrusted proof input.

### Proof of Concept
1. Construct a `BeefyConsensusProof` (ABI struct matching `evm/src/consensus/Types.sol`'s `Vote`/`RelayChainProof`/`BeefyConsensusProof`) where `relay.signedCommitment.votes[0].signature` is, e.g., 64 or 66 bytes instead of 65.
2. ABI-encode it, prefix with `PROOF_TYPE_NAIVE`, and submit via `BeefyConsensusProofs::submit_proof(proof)` from any signed account.
3. `verify_and_apply` ABI-decodes successfully (ABI places no constraint on `bytes` length) and calls `.into()`, which reaches `From<Vote> for SignatureWithAuthorityIndex`'s `signature.copy_from_slice(&sig_bytes)` with `sig_bytes.len() != 65`, panicking instead of returning `Error::<T>::AbiDecodeFailed` or similar.
