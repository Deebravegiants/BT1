## Title
`ShopifyAPI::Auth::Oauth.validate_auth_callback` sends the app's `client_secret` to an unvalidated `shop` host - ([File: lib/shopify_api/auth/oauth.rb])

## Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the access-token request host directly from the caller-supplied `auth_query.shop` value, without ever passing it through `Utils::ShopValidator.sanitize!`, unlike every other credential-exchange flow in the gem (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`) which all validate `shop` against `TRUSTED_SHOPIFY_DOMAINS` before using it to build the request host.

## Finding Description
`validate_auth_callback` in `lib/shopify_api/auth/oauth.rb` builds `null_session = Auth::Session.new(shop: auth_query.shop)` directly from `auth_query.shop`, then creates `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")` and POSTs `client_id` + `client_secret` to `https://#{auth_query.shop}/admin/oauth/access_token`: [1](#0-0) 

Compare this to the sibling credential-exchange flows in the same gem, all of which call `Utils::ShopValidator.sanitize!(shop)` before constructing the session/host used to send `client_secret`: [2](#0-1) [3](#0-2) [4](#0-3) 

`Utils::ShopValidator` exists specifically to prevent an arbitrary/attacker-influenced string from being used as the request host, restricting it to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`): [5](#0-4) 

The only check the `shop` field goes through in `validate_auth_callback` is HMAC verification via `Utils::HmacValidator.validate(auth_query)`, which validates that `code`, `host`, `shop`, `state`, `timestamp` were signed together with the app's `api_secret_key`: [6](#0-5) 

The binding that should hold is: `host that receives the client_secret == a Shopify-trusted domain`. Because there is no `ShopValidator` check, that binding is not enforced by domain allow-listing at all — it relies entirely on the HMAC being unforgeable, and unlike the other flows in this gem, there is no defense-in-depth domain check.

## Impact Explanation
If HMAC validation is ever bypassed or weakened (e.g., a future regression, a misconfigured/rotated secret, or reliance on `old_api_secret_key` fallback), or if the calling application constructs an `AuthQuery` from unauthenticated input (a realistic misuse given the documented pattern of building `AuthQuery` directly from `request.parameters`), the `shop` field flows unchecked into the URI used to transmit the app's `client_id`/`client_secret` (`SSRF carrying the app's credentials`). This is the exact defense the gem's own `ShopValidator` module exists to provide, and it is applied everywhere else credentials are sent except here.

## Likelihood Explanation
Under normal operation, HMAC validation is the sole barrier and should block spoofed `shop` values, so this is not directly triggerable by an unprivileged attacker without also defeating the HMAC check. However, the missing defense-in-depth is inconsistent with the rest of the codebase and is the same class of "check that answers permissively / missing state validation" issue as the cited analog report — an important safety check (`ShopValidator.sanitize!`) present in every sibling method is simply absent here.

## Recommendation
Add `validated_shop = Utils::ShopValidator.sanitize!(auth_query.shop)` in `validate_auth_callback` and use `validated_shop` (not `auth_query.shop`) to construct `null_session` and the final `Session.from(shop: ...)`, matching the pattern used in `ClientCredentials`, `RefreshToken`, and `TokenExchange`.

## Proof of Concept
Not independently reproducible as a standalone exploit without also defeating HMAC verification (which requires the app's `api_secret_key`), because `Utils::HmacValidator.validate(auth_query)` currently gates the call before the host is used. This report is submitted as a defense-in-depth/consistency gap: `lib/shopify_api/auth/oauth.rb`'s `validate_auth_callback` is the only credential-exchange path in the gem that omits the `Utils::ShopValidator.sanitize!` call applied everywhere else, contrary to the codebase's own established invariant that any `shop` string used to build the host receiving `client_secret` must be validated against `TRUSTED_SHOPIFY_DOMAINS`.

```ruby
        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end
```
