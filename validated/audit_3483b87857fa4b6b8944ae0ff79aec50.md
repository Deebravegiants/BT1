Webhook `shop` (and `topic`) header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` fields are read directly and unauthenticated from HTTP headers. `Registry.process` validates only the body HMAC and then forwards the header-derived `shop` value to the app's `WebhookHandler` as trusted tenant identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `Request#shop` is pulled straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the HMAC: [2](#0-1) 

`HmacValidator.validate` verifies `hmac == HMAC(secret, to_signable_string)`, i.e. it authenticates the body bytes only, not the shop header: [3](#0-2) 

`Registry.process` checks this body-only HMAC, then immediately trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` delivered to the host app's handler: [4](#0-3) [5](#0-4) 

Shopify webhook HMACs are computed with the app's single `client_secret` (`api_secret_key`), which is identical for every shop that installs the app. This means an attacker who controls their own shop (e.g., installs the app on a free/dev store they own) can generate a validly-signed webhook body/HMAC pair for *any* topic and body content, then replay the request to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. Because the shop field is never part of the signed content, `Utils::HmacValidator.validate` still returns `true`, and the forged `shop` value is passed on to `WebhookHandler#handle` as if it authentically originated from the victim tenant.

This breaks the identity binding: `shop authenticated by HMAC == shop delivered to the handler`. In reality the HMAC only authenticates `(secret, body)`; the `shop` claim is unauthenticated attacker-controlled input.

### Impact Explanation
If a host application uses `WebhookMetadata#shop` to select which merchant's session/access-token/data to act on (a documented and expected usage pattern for this gem, since `shop` is the only tenant identifier exposed on the webhook object), an attacker can spoof webhooks as coming from an arbitrary victim shop. Depending on how the host app processes the webhook (e.g., updating stored data keyed by shop, triggering shop-scoped actions using the shop's stored access token), this enables cross-tenant data manipulation/confusion — matching the "cross-tenant access" impact category, since the gem itself hands the host an unauthenticated tenant identifier under the guise of "this passed HMAC verification."

### Likelihood Explanation
Exploitability requires only that the attacker be able to install the app on any shop they control (a standard, low-privilege, unprivileged-internet-user action for public Shopify apps) and be able to send a normal HTTP request to the app's webhook endpoint with a crafted header — no access token, `client_secret`, or victim credentials are needed. The vulnerability is a direct root-cause defect in this gem's `to_signable_string` design (body-only signing, header-only shop), not a misuse of documented API by the host, since `shop` is exposed and intended for use as the trusted tenant identifier from a "verified" webhook.

### Recommendation
Include the shop-identifying header(s) (and ideally topic/webhook id) in the HMAC-signed content, or otherwise cryptographically bind `shop` to the verified payload, before exposing it via `WebhookMetadata`. At minimum, document clearly that `Request#shop`/`#topic` are unauthenticated header values and must not be trusted for tenant selection without additional verification (e.g., cross-checking against a known/registered shop for that webhook subscription).

### Proof of Concept
1. Attacker installs the target app on their own Shopify store `attacker.myshopify.com`, obtaining the ability to trigger real webhook deliveries signed with the app's shared `api_secret_key`.
2. Attacker captures one such webhook: valid `x-shopify-hmac-sha256` for a chosen raw body (e.g., `{}`), plus headers `x-shopify-topic`, `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker resends this exact HTTP request to the app's webhook endpoint, replacing only `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes `HMAC(api_secret_key, raw_body)` — unaffected by the header change — and returns `true`: [6](#0-5) 
5. `Registry.process` proceeds and calls the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, even though the request body/topic never originated from that shop: [7](#0-6)
