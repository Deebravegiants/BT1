### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing tenant spoofing in `WebhookMetadata` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook by validating an HMAC, then hands the caller a `WebhookMetadata` struct whose `shop` field is taken directly from the unauthenticated `x-shopify-shop-domain` / `shopify-shop-domain` header, not from any value covered by that HMAC.

### Finding Description
`Registry.process` gates handling on HMAC validation only: [1](#0-0) 

The HMAC check is `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` to build the signed payload: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only the raw request body — `@raw_body` — and nothing else: [3](#0-2) 

Meanwhile, `request.shop` is read straight from the `shopify-shop-domain` (or `x-shopify-shop-domain`) HTTP header, which is not part of the signed bytes at all: [4](#0-3) [5](#0-4) 

That unauthenticated value is then propagated verbatim into `WebhookMetadata.shop`, which is the only shop/tenant identifier passed to the consuming application's `handle` callback: [6](#0-5) [7](#0-6) 

This is exactly the identity-binding break described in the rules: "a field acted on but not covered by the HMAC." The equality that should hold — `shop authenticated by HMAC == shop attributed to the tenant in WebhookMetadata` — does not hold, because the HMAC covers only the body bytes, while `shop` is sourced from a completely separate, unsigned header.

### Impact Explanation
Any party who can produce one *valid* HMAC/body pair for their own store (trivial — they own a store, install the app, and receive a legitimately-signed webhook whose HMAC is `HMAC(client_secret, body)`) can replay that same body+HMAC pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value. Because the header is outside the signed bytes, the HMAC still validates. The application's webhook handler receives `WebhookMetadata` claiming the event belongs to a different (victim) shop, even though it was neither generated by nor authorized on behalf of that shop. Any host application that uses `data.shop` (the only tenant identifier exposed by this gem) to determine whose data to look up, modify, or key application state by — a documented and expected usage pattern in `docs/usage/webhooks.md` — can be tricked into acting on/for the wrong tenant. This is a cross-tenant identity confusion rooted entirely in this gem's `Webhooks::Request`/`Registry` implementation, not merely a downstream misuse, since the gem provides no authenticated shop value at all.

### Likelihood Explanation
Exploitation only requires the attacker to install the target app on their own shop (or otherwise obtain one legitimately-signed webhook body+HMAC pair) and then send a forged HTTP request to the merchant app's public webhook endpoint with a spoofed `shop-domain` header. No access token, `client_secret`, or privileged access is required — only the app's public webhook URL and a genuine webhook the attacker legitimately received for their own store. This is a low-effort, unprivileged-internet-user attack path.

### Recommendation
Include the shop domain (and ideally topic/api-version) inside the HMAC-signed bytes verified by `Webhooks::Request#to_signable_string`, or otherwise cryptographically bind `shop` to the payload before exposing it via `WebhookMetadata`. At minimum, document prominently that `data.shop` is unauthenticated and must not be trusted for tenant selection without independent verification (e.g., cross-checking against a shop that has a valid stored session/access token).

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and receives a legitimate webhook: body `B`, header `x-shopify-hmac-sha256: HMAC(client_secret, B)`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the identical body `B` and identical HMAC header to the merchant's public webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `Webhooks::Request.new` accepts the headers (only presence, not authenticity, of the required headers is checked) — see `lib/shopify_api/webhooks/request.rb:45-63`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`; since the signable string is body-only, the previously-valid HMAC still matches, so `process` proceeds — `lib/shopify_api/webhooks/registry.rb:188-190`.
5. `WebhookMetadata.new(topic:, shop: request.shop, ...)` is built with `shop == "victim-shop.myshopify.com"`, and the app's `handle` callback executes application logic believing this event originated from the victim shop — `lib/shopify_api/webhooks/registry.rb:198-199`.
