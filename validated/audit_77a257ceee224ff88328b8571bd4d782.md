Based on the code, the premise of this finding does not hold. [1](#0-0) 

The call to `verify_relay_parent_descendants` in `set_validation_data` is explicitly gated by `if expected_rp_descendants_num > 0 && !v3_enabled`, i.e. it is only invoked when `V3_SCHEDULING_ENABLED` is `false`. When `V3_SCHEDULING_ENABLED = true` (one of the question's stated preconditions), `verify_relay_parent_descendants` is skipped entirely — the comment even states "When V3 scheduling is enabled: skip this validation, V3 scheduling validation happens in validate_block with header chain from PVF params." [2](#0-1) 

Separately, the `V3_SCHEDULING_ENABLED`-gated logic referenced in the question (`CumulusDigestItem::core_info_exists_at_max_once` and `max_claim_queue_offset`) is an unrelated check on the `CumulusDigestItem::CoreInfo` digest item and `claim_queue_offset`, not on BABE authority/epoch data from `relay_parent_descendants`. [3](#0-2)  Under V3 scheduling, authority verification is instead performed via `VerifySchedulingSignature::verify` against parachain Aura authorities (e.g. `AuraSchedulingVerifier`), which is entirely independent of the BABE relay-chain descendant/epoch validation logic in `descendant_validation.rs`. [4](#0-3)  There is therefore no code path by which a manipulated `relay_parent_descendants` vector feeds into the `max_claim_queue_offset`/`core_info_exists_at_max_once` check — these are two mutually exclusive, unrelated mechanisms.

Even setting aside the precondition conflict, and considering the non-V3 case where `verify_relay_parent_descendants` does run: the function enforces a strict chain-linking invariant — each descendant's `parent_hash` must equal the hash of the previous verified (and correctly-sealed/signed) header [5](#0-4) , and every header's BABE seal must verify against the authority set derived from the on-chain state proof (`read_authorities`/`read_next_authorities`), not attacker-supplied data [6](#0-5) [7](#0-6) . Since these headers are actual relay chain block headers with real BABE signatures produced by relay chain validators, a collator cannot fabricate a shorter chain that both (a) matches the exact expected length and (b) satisfies the hash-chain linkage to the real relay parent state root, while omitting a genuine epoch-change header — doing so would break the `parent_hash` continuity check and be rejected with `InvalidChainSequence`, or fail signature verification. The existing rstest suite explicitly covers epoch-change-at-various-positions scenarios and confirms rejection/rotation behaves correctly (`test_verify_relay_parent_with_epoch_change_at_positions`, `test_verify_relay_parent_descendants_missing_next_authorities_with_epoch_change`).
