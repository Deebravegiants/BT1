Audit Report

## Title
Nil pointer dereference panic on Vault `PublicKeyGet` requests with missing `params` crashes the node-side gateway handler - ([File: core/capabilities/vault/gw_handler.go])

## Summary
`GatewayHandler.HandleGatewayMessage` routes `vaulttypes.MethodPublicKeyGet` requests directly to `handlePublicKeyGet` without any pre-check of `req.Params`, and `handlePublicKeyGet` immediately dereferences `*req.Params` in `json.Unmarshal(*req.Params, r)`. Since `req.Params` is a `*json.RawMessage` that can legitimately be nil (as shown by the explicit nil-check pattern used elsewhere in `ValidatedMessageFromReq`), a request with a missing/null `params` field causes a nil-pointer dereference panic on every node that receives the forwarded request.

## Finding Description
`HandleGatewayMessage` dispatches `MethodPublicKeyGet` unconditionally to `handlePublicKeyGet`: [1](#0-0) . `handlePublicKeyGet` then dereferences `req.Params` without a nil guard: [2](#0-1) . The same unguarded pattern exists in `handleSecretsCreate`, `handleSecretsUpdate`, `handleSecretsDelete`, and `handleSecretsList` [3](#0-2) [4](#0-3) , but those methods first pass through `h.requestProcessor.ProcessRequest`, whereas `PublicKeyGet` skips authorization/validation entirely per the code path in `HandleGatewayMessage`.

On the gateway side, `handler.HandleJSONRPCUserMessage` explicitly treats `MethodPublicKeyGet` as not requiring authorization, and on a cache miss it forwards the request unchanged via `handlePublicKeyGet` → `fanOutToVaultNodes` → `don.SendToNode` to every DON member node, with no validation of `req.Params` anywhere in that path: [5](#0-4) [6](#0-5) .

Elsewhere in the same package, the legacy message-parsing helper `ValidatedMessageFromReq` explicitly checks `req.Params == nil` before dereferencing, confirming that `Params` is a nilable pointer type that the codebase's own conventions require guarding: [7](#0-6) . No equivalent guard exists in the node-side `handlePublicKeyGet` or its sibling handlers in `gw_handler.go`.

I was unable to fully verify (index/tooling limits) whether a `recover()` exists in the gateway connector's inbound message-processing goroutine that dispatches to `GatewayHandler.HandleGatewayMessage`, which would determine whether the blast radius is a single goroutine crash or a full node crash. No recover pattern was found in `core/services/gateway/**`, which is consistent with the claim's own caveat.

## Impact Explanation
This is a genuine, code-confirmed nil-pointer dereference reachable from the unauthenticated `PublicKeyGet` path. At minimum, it panics the goroutine handling that gateway message on every DON member node the fanned-out request reaches, since `fanOutToVaultNodes` forwards the same unvalidated request to `h.donConfig.Members` in a loop. This maps to an in-scope denial-of-service class of impact against the Vault DON's message-processing path, triggerable without authentication or any privileged role, satisfying the "in-scope impact" bar for availability disruption in a security-critical subsystem (Vault key/secrets management).

## Likelihood Explanation
High, matching the claim's analysis. `PublicKeyGet` is designed to skip authorization by intent (per the comment "Public key requests don't require authorization"), so no bypass of allowlist/JWT logic is needed — any client that can reach the gateway's Vault JSON-RPC endpoint can trigger this. The only condition is a cache miss on `h.getCachedPublicKey()`, which is guaranteed at startup or after cache invalidation, making the attack reliably reproducible.

## Recommendation
Add an explicit `req.Params == nil` check at the top of `handlePublicKeyGet` (and consistently in `handleSecretsCreate`, `handleSecretsUpdate`, `handleSecretsDelete`, `handleSecretsList` in `core/capabilities/vault/gw_handler.go`), returning an `api.UserMessageParseError`/`InvalidParamsError` response instead of allowing the nil dereference — mirroring the existing pattern in `ValidatedMessageFromReq` at `core/services/gateway/handlers/common/message_util.go:43-45`. Additionally, consider validating `Params` on the gateway side (`handler.HandleJSONRPCUserMessage` in `core/services/gateway/handlers/vault/handler.go`) before fanning out to nodes, to avoid propagating a malformed request to the entire DON.

## Proof of Concept
1. Send a JSON-RPC request to the gateway's Vault endpoint with `"method": "vault.publicKey.get"` and `"params"` omitted or `null`, before the gateway's public-key cache is populated (e.g., immediately after gateway/node startup, or after forcing a cache miss).
2. `HandleJSONRPCUserMessage` (`core/services/gateway/handlers/vault/handler.go:404-419`) sees `cachedPublicKey == nil` and calls `handlePublicKeyGet` → `fanOutToVaultNodes`, forwarding the request with nil `Params` unchanged to every DON node via `don.SendToNode`.
3. Each node's `GatewayHandler.HandleGatewayMessage` (`core/capabilities/vault/gw_handler.go:207-208`) routes to `handlePublicKeyGet`, which executes `json.Unmarshal(*req.Params, r)` (`core/capabilities/vault/gw_handler.go:366`); since `req.Params` is nil, this panics with a nil-pointer dereference.
4. A minimal Go unit test constructing `&jsonrpc.Request[json.RawMessage]{Method: vaulttypes.MethodPublicKeyGet, Params: nil}` and calling `GatewayHandler.handlePublicKeyGet` directly would reproduce the panic deterministically.

	var nodeErrors []error
