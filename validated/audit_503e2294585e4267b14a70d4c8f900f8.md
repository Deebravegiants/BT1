Audit Report

## Title
Reward-per-token griefing via block-by-block resets causes permanent loss of `pallet-asset-rewards` rewards - (File: `substrate/frame/asset-rewards/src/lib.rs`)

## Summary
`pallet-asset-rewards`'s `reward_per_token` function computes a reward-per-share increment as `reward_rate_per_block * elapsed_blocks * PRECISION_SCALING_FACTOR / total_tokens_staked`, using a fixed `PRECISION_SCALING_FACTOR` of only `4096`. Because `update_pool_rewards` unconditionally resets `last_update_block` to the current block on every invocation regardless of whether the computed increment was non-zero, and because `stake`, `unstake`, and `harvest_rewards` are permissionless self-actions callable with zero amounts, any signed account that has interacted with a pool can call one of these extrinsics every block to keep `rewardable_blocks_elapsed` pinned at `1`, causing the integer division to truncate to zero whenever `reward_rate_per_block * 4096 < total_tokens_staked`. This permanently freezes `reward_per_token_stored` for the entire pool, with no mechanism to recover the un-accrued rewards once `expiry_block` passes.

## Finding Description
The vulnerable computation is in `reward_per_token`: [1](#0-0) , using the scaling constant defined at [2](#0-1) .

`update_pool_rewards` unconditionally advances `last_update_block` to the current block on every call, irrespective of whether the increment computed was zero: [3](#0-2) .

Both `stake` and `unstake` accept caller-chosen amounts with no minimum-stake enforcement — `unstake` only checks `staker_info.amount >= amount`, which is trivially satisfied by `amount = 0`: [4](#0-3) . `stake` similarly has no non-zero amount requirement and creates a `PoolStakers` entry via `unwrap_or_default()`: [5](#0-4) . `harvest_rewards` is likewise callable by the staker themselves with no additional permission check prior to expiry: [6](#0-5) .

Since `reward_per_token_stored` is a single pool-wide accumulator (not per-staker), an attacker calling any of these extrinsics with a zero (or minimal) amount every block resets the elapsed-block window to `1` before it can accumulate to a value large enough for `reward_rate_per_block * elapsed * 4096` to reach `total_tokens_staked`. No existing check prevents `last_update_block` from advancing when the computed increment is zero, so the freeze is total and affects every staker in the pool, not just the attacker.

## Impact Explanation
While the attacker's calls keep `reward_per_token_stored` pinned, no staker accrues any reward share for that window, even honest stakers who take no action at all. `last_block_reward_applicable` caps the elapsed-block computation at `expiry_block`, so once expiry passes, the reward accounting for the griefed window is permanently lost — there is no remainder-carrying or retroactive recomputation mechanism. This is a concrete, in-scope loss-of-funds impact for an unbounded number of legitimate stakers in any pool where `total_tokens_staked` is large relative to `reward_rate_per_block * 4096`, a condition that becomes more likely as pool TVL grows.

## Likelihood Explanation
The attack requires only an ordinary signed account, which can call `stake(pool_id, 0)` once to register in `PoolStakers`, then repeatedly call `unstake(pool_id, 0, None)`, `stake(pool_id, 0)`, or `harvest_rewards(pool_id, None)` every block — all permissionless, low-cost self-actions with no special origin or minimum-amount requirement. On any parachain with low per-block extrinsic fees, this is economically feasible and becomes easier to sustain as pool TVL grows relative to the reward emission rate.

## Recommendation
- Use a higher-precision accumulator (e.g., `FixedU128` or a wider integer type) instead of the fixed `u16` `PRECISION_SCALING_FACTOR = 4096`, following the pattern used in `pallet-nomination-pools`'s `RewardCounter`.
- Only advance `last_update_block` when a non-zero reward increment is actually recorded, or accumulate a fractional remainder across calls so that frequent successive calls cannot indefinitely zero out accrual.
- Consider disallowing zero-amount `stake`/`unstake` calls and/or rate-limiting reward-updating calls per account per pool.

## Proof of Concept
1. Admin creates a pool via `create_pool` with `reward_rate_per_block = R` and `expiry_block`.
2. Legitimate stakers deposit tokens such that `total_tokens_staked = S > R * 4096`.
3. Attacker calls `stake(pool_id, 0)` once to register in `PoolStakers`.
4. Every subsequent block, attacker calls `harvest_rewards(pool_id, None)` (or `unstake(pool_id, 0, None)` / `stake(pool_id, 0)`).
5. Each call invokes `reward_per_token` with `rewardable_blocks_elapsed = 1`; since `R * 1 * 4096 < S`, `ensure_div(S)` truncates to `0`, so `reward_per_token_stored` never increases while `last_update_block` resets to the current block: [7](#0-6) .
6. Repeat until `expiry_block`; since `last_block_reward_applicable` caps accrual at `expiry_block`, `reward_per_token_stored` never advances for the entire window, and no staker (including honest ones who took no action) can ever claim rewards for that period — the loss is permanent and unrecoverable via `cleanup_pool` for stakers.

		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}
