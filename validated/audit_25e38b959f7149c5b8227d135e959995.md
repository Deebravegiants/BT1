### Title
Chain-unbound outbound-delivery reward claims allow cross-deployment replay to drain sibling Hyperbridge treasuries - ([File: modules/pallets/relayer/src/outbound_consensus.rs])

### Summary
The signed payloads used to attribute and pay out `pallet-relayer`'s outbound consensus- and request-delivery rewards omit any identifier of the Hyperbridge chain instance that verifies them (no genesis hash, parachain ID, or `consensus_state_id`). Because the extrinsics that consume these payloads are unsigned/permissionless (`ensure_none`), and the state proofs they carry are proofs of the *destination* chain's own state (not of the originating Hyperbridge instance), an entire claim — including its embedded signature — can be copied verbatim from one Hyperbridge deployment and resubmitted to any other deployment that independently tracks the same destination chain, draining that sibling deployment's treasury for a delivery event it never independently rewarded.

### Finding Description
Both reward-claim messages are constructed with no data that ties them to a specific Hyperbridge chain: [1](#0-0) [2](#0-1) 

Both `outbound_consensus_delivery_message(set_id, destination, payee)` and `outbound_request_delivery_message(commitment, destination, payee)` hash only fields describing the *destination* chain and the payee — never anything identifying which Hyperbridge instance is meant to pay the reward.

The extrinsics that process these claims accept them from `OriginFor::None` (fully permissionless, spam-gated only by `validate_unsigned`): [3](#0-2) 

Replay protection is documented as purely local to the on-chain idempotency tag: [4](#0-3) 

That tag (`OutboundRequestsClaimed[commitment]` / `OutboundConsensusRotationsClaimed[destination][set_id]`) only prevents replay *within the same chain's storage*. It does nothing to stop the identical claim being submitted to a different Hyperbridge deployment that independently maintains its own consensus client and state commitments for the same destination `StateMachine`.

Verification of the claim relies entirely on data intrinsic to the destination chain: the state proof is checked against "Hyperbridge's stored commitment for the destination" — which any sibling deployment that also tracks that destination will independently possess via its own light client: [5](#0-4) 

Because the signature only proves "the private key belonging to the address recorded in the destination's `RequestReceipts`/`EvmHost._epochs` slot approves paying `payee`," and that recorded address/slot value is identical regardless of which Hyperbridge chain reads it, the exact same `(request/state_proof/payee/signature)` tuple verifies successfully against any deployment tracking that destination — with no per-instance binding to reject it.

This is the direct analog of the reported issue: a signed structure omits the chain-scoping data (there, EIP-712's `chainId`; here, any Hyperbridge-instance identifier) that would make the signature/claim meaningful to exactly one verifying chain, enabling the same payload to be replayed wherever an equivalent verifying context exists.

### Impact Explanation
Hyperbridge is explicitly designed to be deployed on multiple parachains (production "Nexus" plus test networks such as "Gargantua", referenced in the repo's simnode tooling), several of which are expected to track the same popular destination chains (Ethereum mainnet/Sepolia, BSC, etc.) and to configure non-zero `OutboundConsensusDeliveryReward` / `OutboundRequestDeliveryReward` for the same modules/destinations. In that overlap, anyone who observes a successful claim on one deployment (block explorers, public mempools — the extrinsic is unsigned and its whole payload including the signature is public) can resubmit the identical extrinsic to a sibling deployment. If that deployment has a reward configured and the `(destination, set_id)`/`commitment` has not yet been claimed there, the transfer in step 11 of `process_outbound_consensus_delivery_claim` / `process_outbound_request_delivery_claim` fires and drains that deployment's treasury PalletId account, paying the (correct, but not necessarily consenting to the second payout) `payee` a second time for one physical relay action. This is a genuine loss of protocol treasury funds on the affected deployment, satisfying the "theft/drain of funds" bar, and requires nothing more privileged than observing a public extrinsic and resubmitting it (no signing key needed by the attacker at all).

### Likelihood Explanation
The precondition — multiple Hyperbridge deployments independently tracking the same destination chain with rewards configured for the same module/set — is a normal, expected operational pattern for this codebase (mainnet + testnets tracking the same major EVM chains), not a contrived edge case. The claim extrinsics are unsigned and thus copyable by anyone without needing the original relayer's cooperation or key. The only gating factor is governance independently enabling a reward for the overlapping destination/module on more than one deployment, which is plausible during coordinated rollouts, staging mirrors of production consensus state, or testnets configured to mirror mainnet rewards for testing/demo purposes.

### Recommendation
Include a Hyperbridge-instance-specific identifier in both signed payloads (e.g., the paying chain's own `host_state_machine()`/genesis hash, or a configured `consensus_state_id`/deployment salt), analogous to adding `chainId` to an EIP-712 domain:
```rust
pub fn outbound_consensus_delivery_message(
    set_id: u64,
    dest_chain: StateMachine,
    payee: [u8; 32],
    local_state_machine: StateMachine, // NEW: binds message to this Hyperbridge instance
) -> [u8; 32] {
    sp_io::hashing::keccak_256(&(set_id, dest_chain, payee, local_state_machine).encode())
}
```
Apply the same change to `outbound_request_delivery_message`, and verify `local_state_machine == IsmpHost::host_state_machine()` inside `process_outbound_consensus_delivery_claim` / `process_outbound_request_delivery_claim` before accepting the claim.

### Proof of Concept
1. Deployment A ("Nexus") and Deployment B ("Gargantua-testnet-mirror") both run `pallet-ismp-relayer`, both track destination `StateMachine::Evm(11155111)`, and both governance-set a non-zero `OutboundConsensusDeliveryReward` for that destination (a realistic staging/testnet mirroring setup).
2. A relayer legitimately delivers a mandatory rotation to the EVM destination and submits `claim_outbound_consensus_delivery_reward` to Deployment A with `signature = sign(outbound_consensus_delivery_message(set_id, dest, payee))`; Deployment A pays the reward and sets `OutboundConsensusRotationsClaimed::<A>[dest][set_id]`.
3. An observer copies the entire extrinsic (unsigned, fully public) and submits it verbatim to Deployment B.
4. Deployment B independently already has its own state commitment for the same `dest` (from its own consensus-client tracking of Ethereum), so `verify_withdrawal_proof` succeeds using the same proof bytes; `OutboundConsensusRotationsClaimed::<B>[dest][set_id]` is unset, so the idempotency check passes; the recovered signer still matches `EvmHost._epochs[set_id]` on the shared destination chain, so `OutboundSignerMismatch` does not trigger.
5. Deployment B's treasury pays `payee` the reward a second time for the same physical relay action — draining B's treasury without any corresponding delivery work performed for B specifically.

/// Signed payload for [`OutboundConsensusDeliveryClaim`]. Replay protection
/// comes from the on-chain `(destination, set_id)` idempotency tag in
/// [`crate::pallet::OutboundConsensusRotationsClaimed`], not from a per-relayer

}
