### Title
SSRF with client_secret exfiltration via unvalidated `dest` claim in `TokenExchange.exchange_token` - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`TokenExchange.exchange_token` derives the shop host used for the OAuth token-exchange request directly from the JWT `dest` claim without passing it through `Utils::ShopValidator.sanitize!`, unlike the parallel `migrate_to_expiring_token` method which does validate. `Auth::JwtPayload` only checks the `aud` claim against `Context.api_key`; `dest` (and `iss`) are never checked against `TRUSTED_SHOPIFY_DOMAINS`. Since the JWT is decoded with `Context.api_secret_key`/`old_api_secret_key`, forging an arbitrary `dest` value normally requires the app secret. However, the equality being broken is: **host validated (none) ≠ host that receives `client_secret`** — `HttpClient` builds `@base_uri = "https://#{session.shop}"` verbatim from the string produced by `jwt_payload.shop` (`dest` claim value), and that URI is where the outgoing POST containing `client_id`/`client_secret` is sent.

### Finding Description
`exchange_token` computes `dest_shop = jwt_payload.shop`, builds `shop_session = Session.new(shop: dest_shop)`, and instantiates `Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")`. `HttpClient#initialize` sets `@base_uri_and_path = "https://#{api_host || session.shop}#{base_path}"` and then `client.request(...)` sends a POST to `#{@base_uri_and_path}/access_token` with a JSON body containing `client_id` and `client_secret`. There is no call to `Utils::ShopValidator.sanitize!` (or any domain allow-list check) on `dest_shop` anywhere in this path, whereas `migrate_to_expiring_token` in the same file explicitly validates the `shop` argument with `Utils::ShopValidator.sanitize!(shop)` before doing the identical HTTP construction. `JwtPayload#initialize` only asserts `@aud == Context.api_key`; it performs no validation of `dest` against a trusted-domain list.

### Impact Explanation
If an attacker can influence the `dest` claim of a token presented to `exchange_token` (e.g., by controlling what session token gets passed to the host app's token-exchange call, or if a future/alternate JWT issuance path fails to bind `dest` to a real myshopify host), the resulting request — carrying the app's `client_id` and `client_secret` — is sent to an attacker-chosen host. This matches the "High - SSRF with the app's credentials" impact class, since the destination host is derived entirely from unvalidated `dest` bytes rather than a sanitized/allow-listed shop domain.

### Likelihood Explanation
Exploitability is constrained: today, a valid JWT can only be produced by someone holding `Context.api_secret_key`, since `decode_token` verifies the HS256 signature with that secret. Under the normal protocol, only genuine Shopify-issued session tokens should reach this code path, and Shopify is expected to always populate `dest` with the real shop's myshopify domain. The defect is that the library performs no independent verification of that host itself — it trusts `dest` unconditionally — which is inconsistent with the defense-in-depth check the library already applies in `migrate_to_expiring_token`. This is a missing binding/validation defect rather than a demonstrated no-credential remote exploit against the current protocol.

### Recommendation
Add `Utils::ShopValidator.sanitize!(dest_shop)` (or equivalent trusted-domain validation) in `TokenExchange.exchange_token` immediately after extracting `dest_shop = jwt_payload.shop`, mirroring the validation already performed in `migrate_to_expiring_token`, so the token-exchange endpoint host is always constrained to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` before any request carrying `client_secret` is issued.

### Proof of Concept
1. Compare the two methods in `lib/shopify_api/auth/token_exchange.rb`: `exchange_token` (lines 29–89) uses `dest_shop = jwt_payload.shop` unsanitized to build `shop_session`, while `migrate_to_expiring_token` (lines 97–136) calls `Utils::ShopValidator.sanitize!(shop)` first.
2. `Auth::JwtPayload#shop` (`lib/shopify_api/auth/jwt_payload.rb:47-50`) returns `@dest.gsub("https://", "")` verbatim — no domain allow-list check exists anywhere in `JwtPayload`.
3. `Clients::HttpClient#initialize` (`lib/shopify_api/clients/http_client.rb:11-19`) sets `@base_uri = "https://#{api_host || session.shop}"`, and `exchange_token` then POSTs `{client_id, client_secret, ...}` to `#{base_uri}/admin/oauth/access_token` — i.e., whatever host `dest_shop` resolves to receives the app's `client_secret`.
4. This confirms the missing binding: `dest_shop` is trusted for constructing the credential-carrying request target without being checked against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`, unlike the sibling method in the same file.
