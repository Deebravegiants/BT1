### Title
Webhook tenant identity (`shop`) is trusted from an unauthenticated header while only the body is HMAC-verified - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by HMAC-verifying the raw request body via `Utils::HmacValidator.validate(request)`, where `Request#to_signable_string` returns only `@raw_body`. The `shop` (tenant identifier), `topic`, `webhook_id`, and `api_version` are all read from HTTP headers that are never included in the signed bytes. `process` then forwards `request.shop` — an unauthenticated header value — directly into the `WebhookMetadata` passed to the host application's handler, which typically uses it as the tenant key for persisting/acting on the payload.

### Finding Description
The identity binding that should hold is: `shop value acted on by handler.handle` == `shop value cryptographically bound to the signed payload`. In this gem that equality does not hold — the HMAC in `lib/shopify_api/utils/hmac_validator.rb` is computed with `OpenSSL::HMAC.hexdigest(sha256, secret, signable_string)` where `signable_string` is exactly `@raw_body` (`request.rb:36-38`). The `shop-domain` header (`request.rb:20-23`) is read independently via `shopify_header`, entirely outside the signed bytes, and is a header the client fully controls when constructing the HTTP request to the app's webhook endpoint.

Because a public/custom Shopify app uses one shared `api_secret_key` (the app's `client_secret`) to sign webhook bodies for every shop that has installed the app, any body+HMAC pair valid for one installed shop (Shop A) is also a valid HMAC for the identical body regardless of which `shop-domain` header accompanies it. `process` (`registry.rb:189-199`) never verifies that the `shop-domain` header actually corresponds to the shop the payload was generated for — it only checks that the body's HMAC matches *some* valid signature under the shared secret, then unconditionally trusts the header for tenant attribution.

### Impact Explanation
This breaks the cross-tenant boundary: an attacker who is a legitimate merchant/installer of the app on Shop A can capture a genuine webhook (raw body + `x-shopify-hmac-sha256` value) sent to the app for their own shop, then replay that exact body/HMAC pair to the app's webhook endpoint while substituting `shop-domain: victim-shop.myshopify.com`. `Registry.process` will accept it (HMAC still validates against the unmodified body) and hand the host application a `WebhookMetadata` claiming the payload belongs to the victim shop. Any host application that uses `WebhookMetadata#shop` to look up or write per-tenant records (e.g., updating orders/products/customers keyed by shop domain, as the documented usage pattern in `docs/usage/webhooks.md` and the `shopify_app` gem reference implementation does) will process attacker-supplied data under the wrong tenant's identity — a cross-tenant data injection / confusion vulnerability.

### Likelihood Explanation
Likelihood is realistic for any app author who installs (or has legitimate access to) the app on at least one shop: no `api_secret_key`, access token, or other privileged secret is required beyond what any installer already has visibility into (their own webhook deliveries). The `shop-domain` header is fully attacker-controlled on the HTTP request to the app's public webhook endpoint, and the gem provides no additional binding (no per-shop signing key, no cross-check between header and body content) to prevent the substitution.

### Recommendation
Bind the `shop` value into the authenticated computation rather than trusting it purely from an unauthenticated header. Concretely:
- Incorporate the `shop-domain` (and `topic`) header into `to_signable_string` construction verified against a secret keyed per-shop, or independently verify that the JSON body's own shop-identifying content (if present) matches the header, or
- At minimum, document and enforce in `Registry.process` that host apps must independently verify `request.shop` is a shop currently known/installed with an active session before trusting `WebhookMetadata#shop`, and consider exposing a helper that cross-checks header-derived `shop` against session storage before dispatch.

### Proof of Concept
1. App is installed on `shop-a.myshopify.com`. Attacker (installer of Shop A) receives a legitimate webhook delivery, capturing:
   - Raw body: `{"id":123,"...":"..."}`
   - Header `x-shopify-hmac-sha256: <valid-hmac-for-body>`
2. Attacker sends a new POST to the app's webhook endpoint with:
   - Same raw body and same `x-shopify-hmac-sha256` value
   - `x-shopify-shop-domain: victim-shop.myshopify.com` instead of `shop-a.myshopify.com`
   - `x-shopify-topic`, `x-shopify-webhook-id` set arbitrarily as needed
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses the forged headers (`request.rb:45-63`).
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `@raw_body` against the shared secret (`registry.rb:190`, `request.rb:36-38`, `hmac_validator.rb:26-31`).
5. `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...))` is invoked (`registry.rb:198-199`), causing the host application to process/store attacker-supplied webhook data under the victim shop's tenant identity. [1](#0-0) [2](#0-1) [3](#0-2)
