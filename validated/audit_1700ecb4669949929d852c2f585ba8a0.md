### Title
Permanent freezing of escrowed intent funds if `order.user` (or beneficiary) is blacklisted by an input/output ERC20 - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._withdraw`, the single function used by every escrow-release path in the Intents module (same-chain cancel, cross-chain `RedeemEscrow`, cross-chain `RefundEscrow`, and the `onGetResponse` cancel-from-source path), transfers each escrowed token directly to `beneficiary` with an unguarded `IERC20.safeTransfer`. If `beneficiary` (which for refunds is always `order.user`, the same account that deposited the funds) becomes blacklisted by that token's issuer (e.g. USDC), the transfer permanently reverts, and there is no fallback claim mechanism to recover the escrow.

### Finding Description
`_withdraw` iterates the withdrawal request's token list and unconditionally calls `IERC20(token).safeTransfer(beneficiary, amount)` (and the same pattern for the accumulated fee-token amount): [1](#0-0) 

This function is reached by:
- `_cancelSameChain` in `IntrinsicIntents.sol`, refunding the order creator directly, `beneficiary = order.user`. [2](#0-1) 
- `onAccept` on `RequestKind.RefundEscrow`/`RedeemEscrow`, dispatched via Hyperbridge from the destination chain (permissionless relayer delivery), which decodes a `WithdrawalRequest` whose `beneficiary` is `order.user` for refunds. [3](#0-2) 
- `onGetResponse`, the source-chain cancellation path that also calls `_withdraw(body, true, true)` with `order.user` as beneficiary. [4](#0-3) 

None of these paths wrap the transfer in try/catch or maintain a claims-style fallback ledger — this was confirmed by inspecting `IntentsBase.sol`, `ExtrinsicIntents.sol`, and `IntrinsicIntents.sol` for any such mechanism, none exists.

When `onAccept` reverts because the inner `safeTransfer` reverts, `EvmHost.dispatchIncoming` catches the failure at the low level, deletes the request receipt, and returns without reverting the whole batch so the message "stays deliverable" and can be retried: [5](#0-4) 

This retry mechanism is meant to allow transient failures to self-heal, but a blacklist condition is not transient — every retry will fail identically, forever. The escrowed input tokens (and, for cross-chain orders, the destination-side `RefundEscrow` acknowledgement) can never be settled: the tokens are permanently stuck in `IntentGatewayV2`'s escrow with no recovery path for the protocol, LPs, or any other party, and (for `_cancelFromDest`) the order is already marked filled/cancelled on the destination side (`_filled[commitment] = beneficiary`) before the source-side refund is attempted, so the order can't be re-filled or re-cancelled through any other route either. [6](#0-5) 

This is the same root-cause pattern as the referenced report: a refund/payout to a self-custodied address that can enter a token blacklist, with no fallback claim path, causing indefinite fund lock — except here the destination-chain state has already been finalized as cancelled, so there isn't even a "liquidator can zero out the swap" mitigation available as in the original report; the order is unrecoverable end-to-end once the user is blacklisted for any escrowed token.

### Impact Explanation
Any input token (or the protocol fee token used for `TRANSACTION_FEES`) escrowed by a user placing an intent order becomes permanently unrecoverable the moment that user's address is blacklisted by the token issuer while the order is outstanding — whether via same-chain cancel, cross-chain cancel-from-destination, or cross-chain cancel-from-source. This is a genuine permanent freezing of user/protocol funds inside the `IntentGatewayV2` contracts, satisfying the "permanent freezing of funds" criterion for the escrow path explicitly in scope.

### Likelihood Explanation
Requires the specific but realistic precondition that a user with an outstanding intent order becomes blacklisted on a widely-blacklist-capable token (USDC, USDT, etc.) before their order is filled or cancelled. This is outside attacker/protocol control but is a foreseeable and recurring event given regulatory/compliance blacklisting activity on major stablecoins, matching the acknowledged (but "rare occurrence") likelihood in the original report.

### Recommendation
Add a pull-based claim mechanism: when a `safeTransfer` to `beneficiary` in `_withdraw` fails (wrap in try/catch, or use a low-level call and check success), credit the amount to a `claims[beneficiary][token]` mapping instead of reverting the whole withdrawal, still finalize/mark the order as settled, and expose a separate `claim(token)` function that lets `beneficiary` (or a designated recovery address) withdraw once unblacklisted, or lets governance redirect stuck funds to an alternate address after a timelock.

### Proof of Concept
1. User places a cross-chain order via `IntentGatewayV2.placeOrder`, escrowing USDC as `order.inputs`.
2. Before the order is filled, Circle blacklists the user's address for USDC.
3. User (or anyone, post-deadline) calls `cancelOrder` on the destination chain: `_cancelFromDest` marks `_filled[commitment] = user` and dispatches a `RefundEscrow` request via Hyperbridge. [6](#0-5) 
4. A relayer delivers the message on the source chain; `onAccept` calls `_withdraw(body, true, true)`, which calls `IERC20(USDC).safeTransfer(user, amount)` — this reverts because `user` is blacklisted.
5. `EvmHost.dispatchIncoming` swallows the revert, deletes the receipt, and the message remains "retryable" — but every future retry hits the identical blacklist revert.
6. The USDC remains permanently escrowed in `IntentGatewayV2` on the source chain; the order is already irreversibly marked cancelled on the destination chain, so no other path (fill, re-cancel) can recover the funds.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        if (finalize) {
            uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
            if (fees > 0) {
                delete _orders[body.commitment][TRANSACTION_FEES];
                IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }

    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
        }

        _filled[commitment] = address(uint160(uint256(order.user)));

        _post(
            order, _body(RequestKind.RefundEscrow, commitment, order.inputs, order.user), options.relayerFee, msg.value
        );
    }
