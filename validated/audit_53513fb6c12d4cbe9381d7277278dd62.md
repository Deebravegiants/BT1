## Finding

The webhook processing pipeline authenticates only the request body, but derives the tenant identity (`shop`) and other event metadata from unauthenticated HTTP headers. This mirrors the reported bug class: a downstream consumer (`ExitAdministrator`/here, `Registry.process`) trusts data supplied by a component that itself performed no binding validation.

### Title
Webhook shop identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC computed by `Utils::HmacValidator` authenticates the byte payload but not the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. `Registry.process` nonetheless uses these unauthenticated header values (particularly `request.shop`) to build the `WebhookMetadata` handed to the host application's handler.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

and `HmacValidator.validate`/`validate_signature` compute/compare the HMAC exclusively over that signable string: [2](#0-1) 

Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers with no cryptographic binding to the body/HMAC: [3](#0-2) 

`Registry.process` validates only the body HMAC, then immediately trusts these header-derived, unauthenticated fields to build the metadata dispatched to the app's webhook handler: [4](#0-3) 

The identity binding that should hold is: `shop asserted by hmac-signed payload == shop used to route/process the event`. Instead the gem enforces only `bytes verified (raw_body) == bytes the HMAC covers`, while `shop` (and `topic`/`webhook_id`) are taken from a completely separate, unsigned channel (headers). Because any user can install a public app on their own store and legitimately receive a validly-HMAC'd `(raw_body, hmac)` pair from Shopify for that shop, that pair can be resubmitted to the same app's webhook endpoint with a forged `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header claiming a different shop. `Registry.process` will pass HMAC validation (the body/HMAC pair is genuinely valid) and will hand the handler a `WebhookMetadata` claiming to be from the spoofed shop, while the body content actually belongs to the attacker's own shop.

### Impact Explanation
Any host application whose webhook handlers key persistence, queuing, or side effects (e.g. inventory sync, order processing, data deletion, GDPR compliance actions) off `WebhookMetadata#shop` is exposed to cross-tenant data confusion: an attacker can inject events that are processed under an arbitrary victim shop's identity using only a `(raw_body, hmac)` pair obtained from their own, legitimately-installed copy of the same app. This satisfies the "cross-tenant access" criterion for Critical impact, since tenant isolation guaranteed by the gem's webhook verification is broken.

### Likelihood Explanation
Exploitation requires no privileged access, TLS interception, or leaked credentials — only installing the target app (or observing a public webhook payload it emits, e.g., app/uninstalled) on an attacker-controlled store, which is available to any unprivileged internet user, and sending a crafted POST with a spoofed `shop-domain` header to the app's public webhook endpoint.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header values in `to_signable_string` so they are covered by the HMAC, or otherwise cryptographically bind them to the verified body before they are trusted by `Registry.process`/`WebhookMetadata`.

### Proof of Concept
1. Install the target Shopify app on an attacker-owned store `attacker.myshopify.com`. Shopify sends a legitimate webhook to the app's endpoint with a valid `X-Shopify-Hmac-Sha256` computed over the request body using the app's `api_secret_key`.
2. Capture the raw request body and its `X-Shopify-Hmac-Sha256` value from that legitimate call.
3. Re-POST the same body and HMAC header to the app's webhook endpoint, but replace `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` passes because it only checks the raw body against the HMAC (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
5. `Registry.process` dispatches `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` to the handler (`lib/shopify_api/webhooks/registry.rb:188-200`), causing the host app to process attacker-controlled data under the victim tenant's identity.
