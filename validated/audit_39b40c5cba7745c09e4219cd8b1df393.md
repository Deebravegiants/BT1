Based on my investigation, I found a genuine custody-analog vulnerability in `multisig_account.move`'s newly added timelock feature — a broken invariant between the timelock override threshold and the ordinary signature threshold, directly paralleling the external report's "two independently-configured thresholds whose drift silently defeats the intended protection" bug class.

### Title
Timelock override_threshold invariant is validated only at set-time, allowing a later increase to `num_signatures_required` to silently and permanently disable the multisig timelock - (File: aptos-move/framework/aptos-framework/sources/multisig_account.move)

### Summary
`upsert_timelock_internal` enforces `override_threshold > num_signatures_required` only at the moment the timelock is configured [1](#0-0) . However, `num_signatures_required` can be changed afterward via `update_signatures_required` / `swap_owners_and_update_signatures_required` through the normal multisig transaction flow, with no re-validation against the existing `MultisigAccountTimeLock.override_threshold` [2](#0-1) . If `num_signatures_required` is raised to meet or exceed `override_threshold`, the timelock's bypass check becomes trivially true every time the normal approval threshold is met, because `can_execute_with_timelock` only checks `num_approvals >= override_threshold` OR `elapsed >= timelock` [3](#0-2) .

### Finding Description
The timelock feature is meant to give a custody-relevant guarantee: transactions require either (a) waiting `timelock_period` seconds, or (b) reaching a stricter `override_threshold` of approvals that is documented and enforced to be *strictly greater* than the ordinary `num_signatures_required` [4](#0-3) .

That invariant (`override_threshold > num_signatures_required`) is checked only inside `upsert_timelock_internal`, at the time the timelock is created or updated [5](#0-4) . It is never re-checked when `num_signatures_required` subsequently changes through `update_signatures_required` (or the `swap_owners_and_update_signatures_required` variant), which routes through `update_owner_schema` — a function which (based on the module's stated purpose) only validates that the new required-signature count is in `(0, owners.length()]`, with no interaction with `MultisigAccountTimeLock` at all.

Once `num_signatures_required` is raised to be `>= override_threshold`, `can_execute_with_timelock`'s override branch (`num_approvals >= override_threshold`) becomes automatically satisfied any time the ordinary execution branch (`num_approvals >= num_signatures_required`) in `can_execute`/`can_be_executed` is satisfied [6](#0-5) . This silently and permanently nullifies the timelock delay for every future transaction — no `TimelockRemoved` event is emitted, and `timelock_period(multisig_account)`/`timelock_override_threshold` view functions will keep reporting a seemingly-active configuration, masking the fact that the delay no longer applies in practice.

### Impact Explanation
This corrupts a documented custody control: the timelock is a governance/custody safeguard meant to give other owners or monitoring infrastructure a window to detect and react to a malicious or compromised-owner transaction before it executes against the multisig-controlled resource account (which may hold APT, fungible assets, or other object-controlled value, as evidenced by the resource-account creation in `create_multisig_account` and its AptosCoin registration [7](#0-6) ). A quorum equal to `num_signatures_required` that raises that value up to `override_threshold` effectively deletes the timelock's protective guarantee without any visible signal, allowing subsequent transactions (fund transfers, capability grants, owner changes) to execute at ordinary quorum speed instead of the operator-configured delay. This is a permanent, silent loss of a custody-relevant safety control on multisig-held assets.

### Likelihood Explanation
Exploitation requires the acting quorum to already hold `num_signatures_required` approvals (i.e., it is not exploitable by a fully unprivileged outside party), which somewhat limits severity. However, it does not require any owners beyond the ordinary/lower quorum — specifically it does not require the honest majority that configured a *stricter* override threshold to protect against a *smaller* malicious/compromised subset. That smaller subset (meeting only the base, lower threshold) can, through this gap, defeat a safeguard explicitly designed to require more signatures than they have. This is a realistic insider/compromised-owner-subset scenario rather than a fully permissionless one, and I was not able to fully confirm `update_owner_schema`'s internal validation logic (the file was truncated before I could read its body), so I cannot rule out an existing but undiscovered cross-check there.

### Recommendation
In `update_owner_schema` (and any other code path that mutates `num_signatures_required` or `owners.length()`), re-validate the existing `MultisigAccountTimeLock.override_threshold`, if present, against the new values — aborting or auto-adjusting (e.g., clearing/raising `override_threshold`) whenever `override_threshold <= new_num_signatures_required`, mirroring the check already done in `upsert_timelock_internal`.

### Proof of Concept
1. Create a multisig account with `num_signatures_required = 2`, `owners.length() = 5`.
2. Call `upsert_timelock(timelock_period = 7 days, override_threshold = Some(3))` — passes validation since `3 > 2` and `3 <= 5` [8](#0-7) .
3. A 2-of-5 quorum (the ordinary threshold) creates and approves a transaction calling `update_signatures_required(new_num_signatures_required = 3)`. This executes normally (no timelock check applies to owner-schema self-update transactions beyond the standard `can_execute_with_timelock` gate, which at this point still uses the old config and is satisfied either by elapsed time or by reaching override_threshold=3 — but if 2-of-5 also includes a 3rd approver opportunistically, or simply waits out the timelock once, this update transaction itself executes).
4. Now `num_signatures_required = 3 == override_threshold`.
5. Any future transaction that reaches 3 approvals (the new ordinary threshold) automatically satisfies `num_approvals >= override_threshold` in `can_execute_with_timelock`, bypassing the `elapsed >= timelock` requirement entirely — the 7-day delay is permanently gone, silently, with no `TimelockRemoved` event.

Note: step 3 still requires passing through the timelock once for the `update_signatures_required` transaction itself; a fully non-privileged bypass was not confirmed. This finding should be treated as likely but not fully verified without inspecting `update_owner_schema`'s complete implementation, which was cut off by file-size truncation.

    inline fun can_execute_with_timelock(multisig_account: address, sequence_number: u64, num_approvals: u64): bool {
        if (exists<MultisigAccountTimeLock>(multisig_account)) {
            let multisig_account_resource = &MultisigAccountTimeLock[multisig_account];
            let timelock = multisig_account_resource.timelock_period;
            let override_threshold = multisig_account_resource.override_threshold;

            // Get the pending transaction to check if the timelock has expired
            // Assume that the transaction has already been checked to exist and is valid
            let pending_transaction = get_transaction(multisig_account, sequence_number);

            // Use subtraction to avoid overflow (now_seconds() >= creation_time_secs is always true)
            let elapsed = now_seconds() - pending_transaction.creation_time_secs;

            // If the number of approvals meets the override threshold, or the timelock has expired, allow execution
            (override_threshold.is_some() && &num_approvals >= override_threshold.borrow()) || elapsed >= timelock
        } else {
            true
        }
    }

    fun upsert_timelock_internal(
        multisig_account: &signer,
        timelock_period: u64,
        override_threshold: Option<u64>,
    ) {
        let multisig_address = address_of(multisig_account);
        assert_multisig_account_exists(multisig_address);

        assert!(
            timelock_period >= MIN_TIMELOCK_PERIOD && timelock_period <= MAX_TIMELOCK_PERIOD,
            error::invalid_argument(EINVALID_TIMELOCK_DURATION)
        );

        let multisig_account_resource = &MultisigAccount[multisig_address];
        assert!(
            override_threshold.is_none() || *override_threshold.borrow() > multisig_account_resource.num_signatures_required,
            error::invalid_argument(EINVALID_TIMELOCK_OVERRIDE_THRESHOLD)
        );
        assert!(
            override_threshold.is_none() || *override_threshold.borrow() <= multisig_account_resource.owners.length(),
            error::invalid_argument(EINVALID_TIMELOCK_OVERRIDE_THRESHOLD)
        );
