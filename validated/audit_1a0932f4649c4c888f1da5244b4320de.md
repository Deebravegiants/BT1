Confirmed: `Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `VerifiableQuery` only requires `hmac` and `to_signable_string` [2](#0-1) . The `shop` accessor is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never part of the signed bytes [3](#0-2) . `Registry.process` validates only the HMAC over the body, then forwards `request.shop` unmodified into `WebhookMetadata` passed to the app's handler [4](#0-3) .

### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating the HMAC of the raw request body only. The `shop` field returned by `Request#shop` — which is taken directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header — is never included in the HMAC-signed bytes (`to_signable_string` returns just `@raw_body`). The `shop` value is nonetheless trusted and passed into `WebhookMetadata` given to the app's webhook handler as the identity of the tenant that produced the event.

### Finding Description
`HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against the `hmac` field [5](#0-4) . For `Webhooks::Request`, `to_signable_string` is defined as simply the raw body [1](#0-0) , while `shop` is read from a header that is entirely outside that signed string [3](#0-2) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching to the handler with `shop: request.shop` [4](#0-3) . Because the same `api_secret_key` is shared across every shop that installs the app, any unprivileged user who installs the app on their own store legitimately receives valid `(body, hmac)` pairs for their own shop's webhooks. That attacker can then replay the exact same body/HMAC to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value. The HMAC check still passes (it only verifies the body was produced with the correct secret, not which shop it belongs to), so the handler receives `WebhookMetadata` claiming the event came from a shop the attacker does not own.

This breaks the intended binding: **the shop identity delivered to the handler == the shop the signature actually vouches for**. Instead, the gem only guarantees **the body bytes were signed with the app's secret**, with no binding between that signature and the `shop` header value. This directly parallels the smart-contract bug class cited in the report: a value that is trusted and acted upon (`epochRevenues[token]` / here `request.shop`) is not actually covered by the mechanism assumed to authenticate it (poolAdapter accounting / here the HMAC), leading to attribution to the wrong tenant.

### Impact Explanation
Any app handler that uses `WebhookMetadata#shop` to key persistence, authorization, or business logic (the documented/intended use, since `Registry.process` passes it as the trusted tenant identifier) can be made to write, delete, or act on data under a shop identity chosen by the attacker rather than the shop that actually generated the event. This is a cross-tenant boundary break rooted entirely in this gem's `Webhooks::Request`/`Registry` code, not in any assumption the host app must additionally verify — the gem presents `shop` as an already-authenticated field once `Registry.process` succeeds.

### Likelihood Explanation
Exploitation only requires an attacker to be an installer of the target app on any shop (unprivileged, no `api_secret_key` or access token needed) — they can capture their own legitimate webhook deliveries and replay them with a modified `shop` header to the app's public webhook endpoint.

### Recommendation
Include the `shop`/`shop-domain` header (and ideally `topic`, `webhook-id`) in the HMAC-signed material, or independently verify the `shop` header against an out-of-band source (e.g., cross-check against the shop associated with the webhook subscription/session) before constructing `WebhookMetadata`, so that the value acted upon by handlers is provably the same value the signature authenticates.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com`; capture a legitimate webhook POST, e.g. body `{"id":1}` with header `x-shopify-hmac-sha256: <valid-hmac-for-body>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Replay the identical body and HMAC header to the app's webhook endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` returns `true` (it only checks the body signature) [6](#0-5) , so `Registry.process` invokes the handler with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body:, ...)` [7](#0-6) , causing the attacker-controlled event body to be processed as if it belonged to `victim-shop`.
