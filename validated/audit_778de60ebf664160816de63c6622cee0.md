## Title
Webhook `shop`/`topic` identity is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC that `Utils::HmacValidator` verifies binds nothing but the request body. The tenant identity (`shop`) and dispatch key (`topic`) that `Webhooks::Registry.process` uses to route and attribute the webhook are read straight from HTTP headers and are never part of the signed bytes.

### Finding Description
`to_signable_string` in `lib/shopify_api/webhooks/request.rb:35-38` only returns `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all derived purely from headers, independent of the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e. `raw_body` only) and compares it against the `hmac` header — it never mixes in `shop`, `topic`, or any other header: [3](#0-2) 

`Webhooks::Registry.process` then trusts `request.topic` to select the handler and passes `request.shop` straight through as the tenant identity to the handler, with no re-validation that this `shop` is actually the one the payload originated from: [4](#0-3) 

The equality this breaks is:
`shop used to authenticate/identify the tenant in HMAC-signed bytes` ≠ `shop used to attribute and act on the webhook in Registry.process`.

Because the app's webhook HMAC secret (`Context.api_secret_key`) is shared across **all** shops that install the app (it is not per-shop), any party who can obtain one valid `(raw_body, hmac)` pair — e.g. by installing the app on their own test/dev store and capturing a webhook their store legitimately receives — holds a signature that Shopify itself would also accept for a *different* `shop-domain` and `topic` header, because those headers are outside the signed scope. Replaying the same body+hmac with `x-shopify-shop-domain` set to a victim shop (and, if desired, a different registered `x-shopify-topic`) passes `HmacValidator.validate` unchanged, yet `Registry.process` will dispatch to a handler and construct `WebhookMetadata` claiming the event is for the victim shop: [5](#0-4) 

### Impact Explanation
This is a cross-tenant integrity issue: an attacker who can produce or capture one valid webhook signature for their own shop can spoof the tenant identity (`shop`) and/or event type (`topic`) processed by the app's webhook handlers for any other merchant on the same app, without ever possessing that merchant's data or the app's `client_secret` directly. Depending on the handler logic (e.g. `shop/redact`, `customers/data_request`, order/product sync handlers), this can drive the host application to perform destructive or data-disclosing actions attributed to a victim shop it never actually occurred for — a cross-tenant access/integrity break as defined in scope.

### Likelihood Explanation
Exploitability requires only: (1) the attacker be able to install the same app on at least one shop they control (or otherwise observe one legitimate webhook delivery, which any app-installing merchant naturally can), and (2) the ability to POST directly to the app's public webhook endpoint with attacker-controlled headers — both of which are available to any unprivileged internet user/merchant interacting with a Shopify app built on this gem, with no reliance on leaked credentials or the `client_secret`.

### Recommendation
Include the identity-bearing fields (`shop`, `topic`, and ideally `webhook_id`/`api_version`) in the value that is HMAC-verified, or otherwise cryptographically bind them to the payload before trusting them in `Registry.process`. At minimum, `Webhooks::Registry.process` should independently verify that `request.shop` corresponds to a shop with an active, legitimately-installed session for this app before dispatching the handler, rather than trusting the header value implicitly once the body-only HMAC check passes.

### Proof of Concept
1. Install the vulnerable app on an attacker-controlled shop `attacker.myshopify.com`; trigger a mandatory/registered webhook topic (e.g. `orders/create`) so Shopify delivers a legitimate `(raw_body, x-shopify-hmac-sha256)` pair to the app's webhook endpoint.
2. Capture that exact `raw_body` and `hmac` header value.
3. Replay an HTTP POST to the same app webhook endpoint with:
   - `x-shopify-hmac-sha256`: unchanged (still valid, since it only ever signed `raw_body`)
   - `x-shopify-shop-domain`: `victim.myshopify.com`
   - `x-shopify-topic`: unchanged or any other topic registered in `Registry`
   - body: unchanged `raw_body`
4. `Utils::HmacValidator.validate` returns `true` (per `lib/shopify_api/utils/hmac_validator.rb:12-31`) because it only checks `raw_body` against the hmac.
5. `Webhooks::Registry.process` (per `lib/shopify_api/webhooks/registry.rb:188-200`) dispatches the handler with `shop: "victim.myshopify.com"`, causing the app to perform tenant-scoped side effects attributed to a shop the attacker never controlled.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
