### Title
Receipts can be created above `max_receipt_size` after validation, undermining the protocol's hard size limit and requiring runtime-wide "pretend" workarounds - (File: `runtime/runtime/src/verifier.rs`, `runtime/runtime/src/congestion_control.rs`)

### Summary
`validate_receipt` enforces `max_receipt_size` only at the moment a receipt is first constructed [1](#0-0) , but subsequent mutations to that same receipt — e.g., appending an `output_data_receivers` entry during `promise_return`, or attaching a large returned value — happen after this check and can push the receipt's serialized size above `max_receipt_size`. This is an acknowledged, still-open bug tracked as [near/nearcore#12606](https://github.com/near/nearcore/issues/12606), documented directly in `ValidateReceiptMode::ExistingReceipt` [2](#0-1)  and reproduced by tests `test_max_receipt_size_promise_return` and `test_max_receipt_size_value_return` [3](#0-2) .

### Finding Description
This is the direct protocol-level analog of the Lido `MAX_STETH_WITHDRAWAL_AMOUNT` bug: a hard, documented ceiling (`max_receipt_size`, analogous to `MAX_STETH_WITHDRAWAL_AMOUNT`) is supposed to gate an operation (receipt creation/forwarding, analogous to `unstake()`/`requestWithdrawals`), but a code path exists that lets the quantity exceed the ceiling after the check has already passed, risking the item becoming permanently stuck downstream.

Concretely:
- `validate_receipt` in `NewReceipt` mode checks `borsh::object_length(receipt) <= limit_config.max_receipt_size` [1](#0-0) .
- After this validation, the receipt can still be mutated (e.g., `output_data_receivers` populated when a later promise in the DAG returns/points back to it via `promise_return`), growing its serialized size beyond `max_receipt_size` before it is persisted/forwarded.
- Because the size ceiling can be silently violated, the rest of the pipeline — `ReceiptSinkV2::try_forward` and `generate_bandwidth_request` in `runtime/runtime/src/congestion_control.rs` — has to explicitly "pretend" oversized receipts are only `max_receipt_size` bytes to avoid them getting permanently wedged in outgoing buffers [4](#0-3) [5](#0-4) .
- The comment in the code explicitly states this workaround exists only because "there is a bug which allows to create receipts that are above the size limit" [6](#0-5) , and `ValidateReceiptMode::ExistingReceipt` exists specifically to "tolerate" already-oversized receipts that were let through this gap [7](#0-6) .

This mirrors the report's root cause exactly: the check happens at one step (stake/receipt-creation time), but the actual value used later (unstake/forward-and-bandwidth-request time) can exceed the checked bound due to state added afterward, and only a size-clamping workaround — not a real fix — currently prevents indefinite stalls.

### Impact Explanation
Reachable directly from an unprivileged account: any user can deploy a contract and submit a function-call transaction whose cross-contract promise chain (via `promise_return`, chained `then`, or a large return value) produces a receipt whose final size exceeds `max_receipt_size` after the validation check has already passed, as demonstrated by `test_max_receipt_size_promise_return` and `test_max_receipt_size_value_return` [8](#0-7) . While the current mitigations (clamping size to `max_receipt_size` in `try_forward` and `generate_bandwidth_request`) prevent the oversized receipt from being permanently wedged (the analog of "tokens locked forever"), the underlying invariant — "no receipt exceeds `max_receipt_size`" — that downstream systems (`ChunkStateWitness` sizing, bandwidth requests, congestion accounting) rely on is violated. The `docs/misc/state_witness_size_limits.md` design explicitly assumes `max_receipt_size` is a hard limit that bounds total witness size to ~21 MiB [9](#0-8) ; a receipt actually exceeding this limit undermines that bound and the size-accounting invariants the whole congestion-control/bandwidth-scheduler subsystem depends on.

### Likelihood Explanation
High — this is not a hypothetical; it is a known, reproducible, currently-open issue (nearcore#12606) with dedicated regression tests in the codebase demonstrating oversized receipts being created via ordinary promise chaining, and it is triggerable by any unprivileged account submitting a function call.

### Recommendation
Re-validate the receipt's size (and other `NewReceipt`-mode invariants) after all mutations are finalized — e.g., after `output_data_receivers` are appended during DAG resolution/`promise_return` — rather than only at initial creation, so that `max_receipt_size` is a true hard limit enforced before persistence/forwarding rather than a limit that is "pretended" to hold. This removes the need for the `ValidateReceiptMode::ExistingReceipt` tolerance path and the clamping workarounds in `try_forward`/`generate_bandwidth_request`.

### Proof of Concept
Use the existing regression tests as the PoC: `test_max_receipt_size_promise_return` constructs a promise DAG `A -then-> B` where `A` creates promise `C` and calls `promise_return`; `C`'s receipt is built at exactly `max_receipt_size`, and appending `output_data_receivers` to point `C` back at `B` pushes it over the limit without being re-validated [10](#0-9) . `test_max_receipt_size_value_return` similarly returns a value of exactly `max_receipt_size` bytes, which is then wrapped in a `Data` receipt that becomes larger than `max_receipt_size` [11](#0-10) . Both tests assert `assert_oversized_receipt_occurred`, confirming the oversized-receipt condition is reached in practice via normal, unprivileged contract calls.
