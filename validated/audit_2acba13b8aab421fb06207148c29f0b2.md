## Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing a merchant to relabel their own signed webhook as belonging to another shop - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable content from the raw request body only, while the `shop`, `topic`, `webhook-id`, and `api-version` values are read straight from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then unconditionally trusts `request.shop` as the tenant identifier passed to the host application's handler. This is the same class of bug as the referenced IBC middleware issue: the code checks that *some* bytes are validly signed (the memo/payload in the Sherlock report, the body here) but acts on a separate, unauthenticated field (the sender in the report, the `shop-domain` header here) to make a trust decision — breaking the binding `verified_bytes == acted_upon_identity`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic tie to the body or to the HMAC: [2](#0-1) 

`HmacValidator.validate` computes the HMAC over `to_signable_string` (the body) only: [3](#0-2) 

`Registry.process` validates that HMAC, then hands `request.shop` straight to the handler as the authenticated tenant identity, with no separate check binding the header to the signed payload: [4](#0-3) 

Equality that should hold but doesn't: `shop_used_for_tenant_routing == shop_covered_by_hmac`. In reality, `shop_covered_by_hmac` is undefined — the HMAC only proves "this body was signed by our secret for some webhook," not "this body belongs to shop X."

### Impact Explanation
A merchant who has the app installed on their own store legitimately receives real webhook deliveries containing a valid `body` + `x-shopify-hmac-sha256` pair for their own shop. Because the header carrying the shop identity is outside the signed content, that same unprivileged actor can replay the identical `(body, hmac)` pair to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header value. `Registry.process` will pass HMAC validation (since the body/HMAC pair is genuinely valid) and will deliver `WebhookMetadata` claiming the payload came from a different, victim shop. Any host application that uses `data.shop` from this metadata to route/apply the webhook body (e.g., update records, sync order/product data) can be tricked into applying one tenant's data to another tenant's namespace — a cross-tenant integrity/confidentiality violation, achieved without an access token, `client_secret`, or TLS interception.

### Likelihood Explanation
Any merchant who can install the app (a normal, unprivileged onboarding step) can trigger legitimate webhook events for their own shop and capture the `(body, hmac)` values via any tool that inspects outgoing/incoming HTTP traffic they control (e.g., their own reverse proxy, a debug logger, or simply configuring the app's webhook URL to a shop they operate). No secret material is needed — they only need a body+HMAC pair valid for *any* shop. This makes exploitation straightforward for any tenant of a multi-tenant app built on this gem.

### Recommendation
Bind the tenant identity into the signed content, mirroring the fix pattern from the referenced report (reintroduce the missing identity check before trusting the derived value). Concretely, `HmacValidator`/`Request#to_signable_string` should incorporate the shop-domain (and ideally topic/webhook-id) into the signable string, or `Registry.process` should independently verify that `request.shop` corresponds to a shop with an active, previously-established registration/session before invoking the handler, rather than trusting the header outright.

### Proof of Concept
1. Attacker's own shop `attacker.myshopify.com` has the app installed and receives a legitimate webhook:
   - `raw_body = '{"id":123,...}'`
   - `x-shopify-hmac-sha256 = HMAC(raw_body, api_secret_key)` (captured via attacker's own infrastructure/logging).
2. Attacker crafts a new HTTP request to the app's public webhook endpoint using the identical `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses `shop` as `"victim.myshopify.com"` [2](#0-1) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the body signature [5](#0-4) .
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` even though the payload actually originated from, and was signed for, the attacker's own shop.
