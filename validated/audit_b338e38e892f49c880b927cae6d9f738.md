## Title
Webhook shop domain and topic are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
The reported bug class is: a piece of data that is *acted upon* by trusted-looking logic is not actually covered by the cryptographic binding that is supposed to authenticate the whole message (bundled transactions accepted as standalone because they aren't bound to the auction tx by signature/inclusion). The exact analog exists in `ShopifyAPI::Webhooks` processing: the HMAC signature only covers the raw request body, while the `shop` domain and `topic` — the values the library uses to route and to identify the tenant — are taken from unauthenticated HTTP headers.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the signature strictly over `to_signable_string` and compares it to the `hmac` header: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read from separate, unsigned headers: [3](#0-2) 

`Registry.process` validates only the HMAC over the body, then trusts `request.shop` and `request.topic` (both unauthenticated) to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The broken identity binding, stated as an equality that the gem fails to enforce:
`HMAC-authenticated bytes (raw_body)` ≠ `shop/topic values the handler acts on (unauthenticated headers)`.

Because only the body is bound by the signature, an attacker who has ever legitimately received one Shopify webhook (e.g., by installing the app on their own development/test shop and triggering any topic) possesses a valid `(raw_body, hmac)` pair signed with the real `api_secret_key`. They can then replay that exact body and HMAC to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` and `x-shopify-topic` headers with values of their choosing (e.g., a victim shop's domain, or a sensitive topic such as `app/uninstalled`, `shop/redact`, or `customers/data_request`). `HmacValidator.validate` still returns `true` because it never inspects those headers, and `Registry.process` dispatches the handler believing the event legitimately originates from the spoofed shop/topic.

### Impact Explanation
This is a cross-tenant identity confusion at the library level: the gem hands the host application attacker-controlled `shop` and `topic` values under the guise of "HMAC verified," when in fact only the body bytes were verified. Any app whose webhook handlers key state, deletion, or authorization decisions off `WebhookMetadata#shop`/`#topic` (the documented, intended usage per `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))`) can be tricked into acting on behalf of a shop it never actually received an event for — including GDPR/mandatory topics that trigger data deletion (`shop/redact`, `customers/redact`) or uninstall cleanup (`app/uninstalled`) for a victim tenant. This matches the Critical "cross-tenant access" bar, since the tenant boundary (`shop`) is not actually authenticated by the mechanism the library advertises as its integrity check.

### Likelihood Explanation
The prerequisite is low: the attacker only needs the ability to receive one legitimate webhook themselves (trivial — install the app on any shop, including a free/dev store, and trigger any webhook topic) and the ability to POST to the app's public webhook endpoint (by definition internet-reachable, since Shopify itself must reach it). No access token, `api_secret_key`, or privileged account is required.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signable payload (or otherwise cryptographically bind the header values to the signed body) before trusting them in `Registry.process`, or require callers to independently re-verify that `request.shop` matches an already-known, provisioned shop before dispatching handlers.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook topic and capture the raw POST body plus the `x-shopify-hmac-sha256` header (this is a genuinely Shopify-signed request).
2. Replay that exact body/HMAC pair to the app's webhook endpoint, replacing only `x-shopify-shop-domain` with `victim.myshopify.com` (and optionally `x-shopify-topic` with a sensitive topic).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the body against the HMAC: [5](#0-4) 
   Validation passes, and the handler executes believing the event is authentically from `victim.myshopify.com`.
