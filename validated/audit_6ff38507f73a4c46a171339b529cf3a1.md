### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the `shop`, `topic`, `api_version`, and `webhook_id` fields are read directly from unauthenticated HTTP headers. `Webhooks::Registry.process` validates only the body's HMAC and then forwards the header-derived `shop` value, unverified, to the host app's handler. Any party able to reach the app's public webhook endpoint can therefore replay a genuine, validly-signed webhook body while substituting an arbitrary `x-shopify-shop-domain` header, causing the app to process the payload as if it belonged to a different merchant.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

but `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers with no cryptographic binding to the HMAC: [2](#0-1) 

`HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` (the body) against `verifiable_query.hmac`, so it never binds the shop header to the signature: [3](#0-2) 

`Registry.process` validates only that body-level HMAC and then trusts `request.shop` (a raw header value) when constructing the data handed to the app's business logic: [4](#0-3) 

This breaks the identity binding that the equality `shop verified by HMAC == shop attributed to the processed payload` should enforce: the HMAC only proves "this body was produced with the app's `client_secret`", not "this body belongs to shop X". Since the same `api_secret_key` (the app's shared client secret) signs webhooks for *every* installed shop, a valid `(body, hmac)` pair from one tenant remains valid when replayed with a different `shop-domain` header.

### Impact Explanation
Any unprivileged party who can obtain one legitimately-signed webhook delivery for their own shop (e.g., a merchant who installs the app, or anyone who can capture a webhook the app receives on a reachable endpoint) can resubmit that exact body/HMAC pair to the app's public webhook endpoint while swapping the `x-shopify-shop-domain` header to a victim shop's domain. `Registry.process` will accept it as authentic and deliver `WebhookMetadata` attributing the payload to the victim shop, letting the attacker inject/replay data or trigger tenant-scoped side effects (e.g., data updates, cache/state keyed by shop, uninstall/GDPR handling) under another merchant's identity. This is a cross-tenant authentication/identity-binding failure rooted entirely in this gem's `Request`/`HmacValidator`/`Registry` code, not in host-app misuse.

### Likelihood Explanation
The webhook endpoint is, by design, a public unauthenticated HTTP endpoint that must accept POSTs from Shopify's IPs but has no network-level restriction preventing replay from any internet client. Obtaining a valid `(body, hmac)` pair only requires being (or briefly being) a legitimate installed merchant of the target app, which is a low bar for a SaaS app with self-serve installs. Constructing the forged request is trivial (copy body + hmac header, change one header).

### Recommendation
Bind the shop (and ideally topic/webhook id) into the value that is HMAC-verified, or independently authenticate the `shop-domain` header against a known/installed shop record before trusting it, e.g.:
- Include `shop-domain` (and `topic`) in the signable string used for the HMAC comparison (mirroring how Shopify's own signature scheme could be extended), or
- After HMAC success, cross-check `request.shop` against the shop associated with the webhook subscription being delivered (Shopify does send a consistent shop per subscription topic/id) and reject processing if the app cannot independently confirm the header is authoritative for this delivery.
At minimum, document clearly that `Request#shop` is unauthenticated header data not covered by `hmac`, so host apps do not rely on it as a trusted tenant identifier without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own dev/test shop `attacker-shop.myshopify.com`, triggering a legitimate webhook delivery to the app's public webhook endpoint, e.g.:
```
POST /webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <valid HMAC of body computed with app's api_secret_key>
x-shopify-shop-domain: attacker-shop.myshopify.com
x-shopify-webhook-id: b1234-...

{"id": 1, ...}
```
2. Attacker captures this exact body and `x-shopify-hmac-sha256` value (e.g., via a proxy they control in front of their own dev endpoint, or by momentarily pointing the webhook subscription at infrastructure they own before capturing).
3. Attacker replays the identical body/HMAC to the app's real webhook endpoint but changes only the shop header:
```
POST /webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <same valid HMAC as step 1>
x-shopify-shop-domain: victim-shop.myshopify.com
x-shopify-webhook-id: b1234-...

{"id": 1, ...}
```
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the (unchanged) body against the (unchanged) HMAC — see [5](#0-4) . The handler then executes with `data.shop == "victim-shop.myshopify.com"`, even though the payload actually originated from `attacker-shop.myshopify.com`.
