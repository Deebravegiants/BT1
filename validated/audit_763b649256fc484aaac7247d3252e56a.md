### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop` (tenant identity) is taken from an unauthenticated HTTP header that is never included in the signed material. `Registry.process` accepts the request as long as the body signature validates, then hands the unauthenticated `shop` value to the app's webhook handler. This breaks the binding `hmac_covers(shop) == shop_used_for_tenant_attribution`.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic tie to the HMAC: [2](#0-1) 

`HmacValidator.validate` calls `validate_signature`, which only compares `compute_signature(verifiable_query.to_signable_string, secret)` against the received HMAC — i.e., it only authenticates the body bytes, never the `shop` field: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler, without ever re-checking that the shop is bound to the signature: [4](#0-3) 

Because the HMAC secret (`api_secret_key`) is the same across every shop/tenant that has installed a given app, any webhook body+HMAC pair that is valid for one tenant is valid for every tenant sharing that app's client secret. An attacker who can obtain one legitimate `(raw_body, hmac)` pair (e.g. from their own installed dev/test store, or from a public/replayable webhook body) can resend that exact body and signature to the app's webhook endpoint while substituting the `shopify-shop-domain` header with any victim shop domain. `HmacValidator.validate` will still return `true` because it only checks the body, and `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop.

This is exactly the "field acted on but not covered by the HMAC" pattern: the identity binding `verified_bytes == attributed_tenant` does not hold — `verified_bytes` is the raw body only, while `attributed_tenant` (`shop`) is unauthenticated header data.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` (as documented/intended, see `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))`) to select which merchant's session/access token/data to act on, an attacker can forge a cross-tenant event: causing the app to process a payload as if it originated from a shop the attacker does not have access to. This satisfies the Critical impact category "cross-tenant access," since the tenant boundary (`shop`) is the exact value that is spoofable despite HMAC "verification" passing.

### Likelihood Explanation
Exploitability requires only one legitimate `(body, hmac)` pair for any shop using the same app installation (trivial to obtain — an attacker can install the app on their own free/dev store and capture a real webhook delivery), plus the ability to send an arbitrary HTTP POST with custom headers to the app's public webhook endpoint. No access token, `api_secret_key`, or privileged access is needed. This is a purely unprivileged-internet-user attack against the gem's own webhook validation code path.

### Recommendation
Include the shop domain (and other tenant-identifying headers, e.g. topic, webhook id) in the signed material that `HmacValidator` verifies, or explicitly bind them via a MAC that covers `raw_body + shop + topic`. At minimum, `Registry.process`/`WebhookMetadata` should not treat `request.shop` as authenticated unless it has been cryptographically bound to the signature validated by `HmacValidator.validate`.

### Proof of Concept
1. Install the vulnerable app on an attacker-controlled shop `attacker-shop.myshopify.com`; trigger any webhook topic the app subscribes to and capture the raw POST: headers (`x-shopify-hmac-sha256: <hmac>`, `x-shopify-topic: <topic>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`) and raw body `B`.
2. Resend the identical body `B` and the identical `x-shopify-hmac-sha256` value to the same webhook endpoint, but change `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (== `B`, unchanged) and matches the received HMAC — validation succeeds: [5](#0-4) 
4. The handler is invoked with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the request never legitimately originated for that shop.
