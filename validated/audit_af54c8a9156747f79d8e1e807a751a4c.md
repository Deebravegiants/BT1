Confirmed: the Tron variant of `IntentGatewayV2` (`evm/tron/contracts/apps/IntentGatewayV2.sol`) contains exactly the CEI-violation pattern the report describes, and unlike the mainline EVM contract, it lacks a `nonReentrant` guard on the entry points that reach it.

### Title
Reentrancy in Tron `IntentGatewayV2.withdraw()` via unguarded native/ERC20 transfer before escrow-accounting update enables theft/lock of other users' escrow - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron fork's internal `withdraw()` function transfers tokens/native currency to the beneficiary **before** decrementing `_orders[commitment][token]`, and neither `withdraw()` nor its callers (`cancelOrder`, `onAccept`, `onGetResponse`) are protected by a reentrancy guard, unlike the mainline `evm/src` contracts which apply `nonReentrant` on `cancelOrder`/`fillOrder` and perform the CEI-correct ordering (decrement `_orders` before transferring) in `IntentsBase._withdraw`.

### Finding Description
`withdraw()` in the Tron contract: [1](#0-0) 
transfers native ETH via a raw `.call{value: amount}("")` or ERC20 via a low-level `.call` **before** updating `_orders[body.commitment][token] -= amount`. This is the same Checks-Effects-Interactions violation as the referenced BvB report: state that gates future entitlement (`_orders[...]`) is written *after* an external call that can hand control to attacker-controlled code (a native transfer to a contract beneficiary, or a malicious/ERC-777-like token).

Compare this to the fixed mainline contract `evm/src/apps/intentsv2/IntentsBase.sol`, where `_withdraw()` decrements `_orders[body.commitment][token]` **before** calling `_sendValue`/`safeTransfer`: [2](#0-1) 

Critically, the mainline contract's `cancelOrder` is `nonReentrant`: [3](#0-2) 
but the Tron variant's `cancelOrder` has **no reentrancy guard at all**: [4](#0-3) 
A `grep` for `nonReentrant`/`ReentrancyGuard` across `evm/tron/**` returned zero matches, confirming the entire Tron app is unguarded.

Attack path: a beneficiary that is a contract calls `cancelOrder()` for a same-chain order it created, which invokes `withdraw(body, true)` for that commitment. Native-ETH escrow triggers `beneficiary.call{value: amount}("")` before `_orders[commitment][token]` is decremented, so beneficiary's `receive()`/fallback can re-enter the same commitment while `_orders[commitment][token]` still reflects the full pre-withdrawal balance. Re-entrant calls can reach `withdraw` again through `onAccept`/`onGetResponse` (if the attacker also controls the corresponding cross-chain flow) or, more directly, drain the not-yet-zeroed per-token escrow slot multiple times within the loop over `body.tokens`/fee slot before the top-level call returns and finally sets the accounting straight — resulting in double payout from `_orders`/`TRANSACTION_FEES` and permanent shortfall or lock for any other legitimate order sharing gateway-held liquidity for that token/commitment path.

### Impact Explanation
An attacker-controlled beneficiary can re-enter the withdrawal path before `_orders[...]` accounting is updated, enabling double-withdrawal of escrowed input tokens and/or transaction fees for the same order commitment — a direct theft of escrowed user funds from the gateway. This is a concrete loss-of-funds/insolvency vector for the Tron `IntentGatewayV2`, matching the Medium-severity classification of the cited analog (funds theft/other users' funds becoming inaccessible due to a CEI violation on withdrawal).

### Likelihood Explanation
Reachable from a single unprivileged `cancelOrder` (or the cross-chain `onAccept`/`onGetResponse` withdrawal path) call where the beneficiary is attacker-supplied/attacker-deployed, which is the normal, permissionless path for order creators. No privileged role, governance, or off-chain cooperation is required, and there is no reentrancy guard anywhere in the Tron app to block it.

### Recommendation
Apply Checks-Effects-Interactions in `withdraw()`: decrement `_orders[body.commitment][token]` (and delete the `TRANSACTION_FEES` slot) *before* performing the native/ERC20 transfer, mirroring the fixed ordering already used in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`. Additionally, add a `nonReentrant` modifier (or a transient-storage-based reentrancy lock, as elsewhere in the codebase) to `cancelOrder`, `onAccept`, and `onGetResponse` in `evm/tron/contracts/apps/IntentGatewayV2.sol` to bring it in line with the mainline EVM contract's protections.

### Proof of Concept
1. Attacker deploys a malicious beneficiary contract with a `receive()` that calls `cancelOrder`/or triggers the withdrawal path again for the same `commitment`.
2. Attacker places a same-chain order with native-ETH input and itself (the malicious contract) as `order.user`/beneficiary.
3. Attacker calls `cancelOrder(order, options)`, routing to `withdraw(body, true)`: [5](#0-4) 
4. Inside `withdraw`, the native transfer `beneficiary.call{value: amount}("")` fires before `_orders[body.commitment][token] -= amount` executes: [6](#0-5) 
5. The malicious `receive()` re-enters (e.g., re-triggers the withdrawal for the same still-nonzero `_orders[commitment][token]` slot), draining escrow beyond the amount actually owed, since no `nonReentrant` guard exists anywhere in this file to stop it.
