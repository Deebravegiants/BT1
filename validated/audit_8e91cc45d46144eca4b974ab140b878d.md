### Title
Webhook shop identity is unauthenticated: `shop-domain` header is not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (and `topic`/`webhook_id`) values from raw HTTP headers, while `HmacValidator` only authenticates the request body. `Registry.process` treats a passing HMAC check as proof that the whole webhook—including which shop it came from—is legitimate, then hands `request.shop` straight to the host application's handler via `WebhookMetadata`. This breaks the intended identity binding: `shop-domain claimed == shop-domain cryptographically authenticated`.

### Finding Description
`HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns just the raw request body: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from HTTP headers that are entirely outside the signed content: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant identifier passed to the handler: [4](#0-3) 

Because the HMAC secret (`Context.api_secret_key`, the app's client secret from the Partner Dashboard) is the same for *every* shop that has installed the app, any unprivileged merchant who has installed the app can obtain a genuinely-signed `(body, hmac)` pair for their own shop (e.g. by triggering a webhook event on their own store, using attacker-controlled body content such as product/customer fields). Because the header block (`shop-domain`, `topic`, `webhook-id`) is not covered by the signature, that same `(body, hmac)` pair remains valid when replayed to the app's webhook endpoint with a forged `x-shopify-shop-domain` header naming a different (victim) shop. `Registry.process` will accept it, and `WebhookMetadata.shop` will report the victim's domain even though the payload actually originated from the attacker's own store.

### Impact Explanation
This is a cross-tenant identity-confusion vulnerability at Critical/High severity: the app's webhook handler is given attacker-controlled data tagged with an arbitrary shop identity that passed "signature verification." Any host application that uses `WebhookMetadata#shop` to select the merchant record to update (the documented, intended pattern for webhook consumption) can be tricked into writing attacker-supplied data into another tenant's record — a cross-tenant data-integrity/confusion attack achieved purely by an unprivileged, arbitrarily-registered merchant of the app, requiring no leaked secrets or privileged access.

### Likelihood Explanation
Likelihood is high for any app that has more than one shop installed (the normal case for any public/multi-tenant Shopify app). The only prerequisite is that the attacker installs the target app on their own store (a normal, unprivileged, self-service action) and can trigger at least one webhook event with attacker-influenced body content (e.g. product update, customer update). No access to `api_secret_key`, tokens, or the victim's environment is required.

### Recommendation
Bind the shop (and topic/webhook id) identity to the cryptographic signature instead of trusting raw headers separately from the HMAC check:
- Include the `shop-domain` (and ideally `topic`, `webhook-id`) in the signed material that `HmacValidator` verifies, or
- Independently verify that `request.shop` matches an app-known, previously authenticated shop/session before allowing `Registry.process` to hand it to the handler, or
- At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be trusted for tenant selection without an additional check against the caller's own session/install records.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook event with attacker-controlled body content (e.g. edits a product to embed malicious JSON fields), causing Shopify to POST to the app's webhook endpoint with a body `B` and a valid `x-shopify-hmac-sha256` header computed over `B` using the app's shared `api_secret_key`.
3. Attacker captures `(B, HMAC(B))`.
4. Attacker (or a script) re-sends `(B, HMAC(B))` to the same app webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and any topic of choice).
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(B)` against `B` — it never inspects the `shop-domain` header.
6. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)` and, following the intended/documented usage pattern, applies attacker-controlled data `B` to the victim shop's record. [4](#0-3) [5](#0-4)
