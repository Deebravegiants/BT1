### Title
Unconditional relayer fee payout before verifying underlying transfer succeeds in `inner_rlp_execute()` - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
In the NEAR Wallet Contract, `inner_rlp_execute()` dispatches a relayer fee `Transfer` promise as an independent, unchained receipt immediately upon parsing an `EOABaseTokenTransfer` or `ERC20Transfer`, before the underlying base-token transfer or NEP-141 `ft_transfer` action is known to succeed. This is analogous to the reported ERC20 issue where a value-transfer's success is assumed rather than verified before downstream accounting/actions proceed, leading to funds being disbursed on the basis of an unconfirmed outcome.

### Finding Description
`inner_rlp_execute()` computes `tx_fee` and, for `EOABaseTokenTransfer`/`ERC20Transfer` transaction kinds, immediately creates a *separate* promise batch and calls `env::promise_batch_action_transfer` to pay the relayer — independent of, and not chained (`.then`) to, the promise that performs the actual transfer/`ft_transfer` action: [1](#0-0) 

The actual value-moving action is dispatched afterward as its own, independently-resolved promise chain — e.g. for `ERC20Transfer` it is a chain of `storage_balance_of` → (`storage_deposit` +) `ft_transfer` → `rlp_execute_callback`: [2](#0-1) [3](#0-2) 

Both promises are created as sibling receipts of the same host-function execution and resolve asynchronously and independently; there is no dependency (`.then`) making the fee-transfer conditional on the outcome of the `ft_transfer`/base-token transfer. The callback (`rlp_execute_callback`) does correctly check `env::promise_result(0)` for the *action* promise and issues a *caller*-deposit refund on failure via `caller_deposit`: [4](#0-3) 

However, this refund logic only covers `caller_deposit` (the attached NEAR deposit of the calling transaction), not the relayer fee, which was already unconditionally sent out at the top of `inner_rlp_execute()`. So if the wrapped `ft_transfer` fails (e.g., the token contract panics because the account has insufficient token balance, is not registered per NEP-141/NEP-145, or the token contract itself is paused/reverts), the relayer still receives `tx_fee`, taken from the wallet owner's NEAR balance, for a token transfer that never happened.

### Impact Explanation
This causes direct loss of funds for the wallet owner (an unprivileged account): the owner pays a relayer fee in NEAR for a service (moving ERC-20-emulated / NEP-141 tokens or base tokens) that was never actually delivered, because success of the wrapped action was never checked before compensating the relayer. This mirrors the referenced Visor bug class — value disbursed on the unverified assumption that a preceding transfer succeeded — but manifests here as fund loss to the transaction's signer/owner rather than an intended recipient.

### Likelihood Explanation
Reachable directly by any unprivileged relayer/user calling `rlp_execute` on a deployed Wallet Contract with an RLP-encoded ERC-20 `transfer` or an EOA base-token transfer whose `to` fails to receive tokens (e.g., insufficient token balance in the wallet, unregistered receiver combined with a `storage_deposit` that fails, or the token contract reverting the `ft_transfer`). No validator or malicious-node capability is required; only a standard relayer/user flow through the wallet contract's public `rlp_execute` entrypoint.

### Recommendation
Chain the relayer fee transfer to depend on (or be issued after confirming) the success of the primary action promise — e.g., move the fee `Transfer` into the success branch of `rlp_execute_callback` (or an equivalent callback) instead of dispatching it unconditionally in `inner_rlp_execute()`, so the relayer is only compensated when the wrapped `ft_transfer`/base-token transfer actually succeeds.

### Proof of Concept
1. User's wallet contract holds NEAR but zero/insufficient balance of NEP-141 token `tokenA`.
2. A relayer submits an RLP-encoded Ethereum-style ERC-20 `transfer(to, 100)` transaction for `tokenA`, with `max_fee_per_gas`/`gas_limit` implying a non-zero `tx_fee`.
3. `inner_rlp_execute()` parses the tx as `ERC20Transfer`, and — before any check that the `ft_transfer` call will succeed — creates and dispatches the fee-refund promise to the relayer at [5](#0-4) .
4. Separately, the `storage_balance_of` → `ft_transfer` chain is dispatched; `ft_transfer` fails because the wallet has insufficient `tokenA` balance (the NEP-141 contract panics).
5. `rlp_execute_callback` observes `PromiseResult::Failed` and refunds only `caller_deposit` (attached NEAR), not the already-paid relayer fee: [6](#0-5) .
6. Result: the relayer keeps `tx_fee` in NEAR even though no `tokenA` was transferred — direct fund loss for the wallet owner.

    #[private]
    pub fn nep_141_storage_balance_callback(
        &mut self,
        token_id: AccountId,
        receiver_id: AccountId,
        action: near_action::Action,
        caller_deposit: Option<CallerDeposit>,
    ) -> PromiseOrValue<ExecuteResponse> {
        self.has_in_flight_tx = false;
        let maybe_storage_balance: Option<StorageBalance> = match env::promise_result(0) {
            PromiseResult::Failed => {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some(format!("Call to NEP-141 {token_id}::storage_balance_of failed")),
                });
            }
            PromiseResult::Successful(value) => match serde_json::from_slice(&value) {
                Ok(x) => x,
                Err(_) => {
                    return PromiseOrValue::Value(ExecuteResponse {
                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from NEP-141 storage_balance_of".into()),
                    });
                }
            },
        };
        let current_account_id = env::current_account_id();
        let ext = WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
        let promise = match maybe_storage_balance {
            Some(_) => {
                // receiver_id is registered so we can send the transfer
                // without additional actions. Note: in the standard NEP-141
                // implementation it is impossible to have `Some` storage balance,
                // but have it be insufficient to transact.
                match action_to_promise(token_id, action)
                    .map(|p| p.then(ext.rlp_execute_callback(caller_deposit)))
                {
                    Ok(p) => p,
                    Err(e) => {
                        return PromiseOrValue::Value(e.into());
                    }
                }
            }
            None => {
                // receiver_id is not registered so we must call `storage_deposit` first.
                let storage_deposit_args =
                    format!(r#"{{"account_id": "{receiver_id}"}}"#).into_bytes();
                let transfer_function_call = match action {
                    near_action::Action::FunctionCall(x) => x,
                    _ => {
                        return PromiseOrValue::Value(ExecuteResponse {
                            success: false,
                            success_value: None,
                            error: Some(
                                "Expected function call action to perform NEP-141 transfer".into(),
                            ),
                        });
                    }
                };
                Promise::new(token_id)
                    .function_call(
                        "storage_deposit".into(),
                        storage_deposit_args,
                        NEP_141_STORAGE_DEPOSIT_AMOUNT,
                        NEP_141_STORAGE_DEPOSIT_GAS,
                    )
                    .function_call(
                        transfer_function_call.method_name,
                        transfer_function_call.args,
                        transfer_function_call.deposit,
                        transfer_function_call.gas,
                    )
                    .then(ext.rlp_execute_callback(caller_deposit))
            }
        };
        self.has_in_flight_tx = true;
        PromiseOrValue::Promise(promise)
    }
