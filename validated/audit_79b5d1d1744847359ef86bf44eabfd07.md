Webhook `shop-domain` header is authenticated by TLS/possession-of-secret only, not bound to the HMAC-verified body, enabling cross-tenant shop-identity spoofing in `ShopifyAPI::Webhooks::Registry.process` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `Utils::HmacValidator.validate` verifies the HMAC over that body alone. [1](#0-0) [2](#0-1)  The `shop-domain` header, however, is read unauthenticated and passed straight through to the application's webhook handler as the tenant identity, with no cryptographic binding to the HMAC-verified payload. [3](#0-2) [4](#0-3)  This breaks the identity binding `shop-domain header == shop that produced the HMAC-verified body`, which is exactly the class of "field acted on but not covered by the HMAC" flaw the analog rules call out.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process(request)` performs a single check — `Utils::HmacValidator.validate(request)` — before dispatching to the app's `WebhookHandler#handle`. [4](#0-3)  That validator recomputes an HMAC-SHA256 over `request.to_signable_string`, which is defined as just `@raw_body`. [1](#0-0)  None of the HTTP headers — `topic`, `shop-domain`, `webhook-id`, `api-version` — are included in the signed material; they are parsed directly from attacker-influenceable request headers via `shopify_header`. [5](#0-4) [6](#0-5) 

Once HMAC validation succeeds, `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` and hands it to the handler. [7](#0-6)  `WebhookMetadata#shop` is a plain `String` field with no further validation. [8](#0-7)  The library's own documentation instructs integrators to treat `data.shop` as "The shop domain of the webhook" and use it directly as the tenant key (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`). [9](#0-8) 

Because the client_secret used to compute the HMAC is shared across every shop that has installed the app (it is the app's single `api_secret_key`, not a per-shop secret), a valid HMAC only proves "produced by someone in possession of the app's secret for this exact body" — it says nothing about which shop the body pertains to. An unprivileged party who has installed the app on their own shop (or who can otherwise intercept/replay one legitimate webhook delivery for a body they control) can take a genuine `(raw_body, hmac)` pair that is valid for their own shop, and resend the identical body/HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop domain also using the same app. `HmacValidator.validate` still passes because it only checks the body, and `Registry.process` will then hand the handler a `WebhookMetadata` whose `shop` field is the victim's domain paired with attacker-chosen body content — a cross-tenant identity/data confusion at the library's trust boundary.

### Impact Explanation
This breaks the equality that a security-conscious integrator relies on: `verified(body) == attributed(shop)`. The library documents `data.shop` as reliable and recommends using it as the tenant/shop key for downstream processing (queueing jobs, looking up the session, updating shop-scoped records), so any host app following the documented pattern inherits a cross-tenant data-injection vector — attacker-controlled body content processed under a victim shop's identity — without needing the victim's access token, session, or the app's `client_secret`. This matches the "cross-tenant access" impact category.

### Likelihood Explanation
Requires only: (1) the attacker to be a legitimate (unprivileged) installer of the app on their own shop, allowing them to receive at least one genuine, validly-signed webhook body they can replay; and (2) knowledge of a target shop's domain (public information, often the store's storefront URL). No secret, token, or privileged access is required — only header manipulation on a replayed HTTP request, which any internet-capable client can perform against the app's public webhook endpoint.

### Recommendation
Bind the `shop-domain` (and ideally `topic`/`webhook-id`) header into the value that is HMAC-verified, or otherwise cryptographically/contextually tie the claimed shop to the verified payload — e.g., include the header values in `to_signable_string`, or cross-check `request.shop` against a shop the app has an active, previously-established session/install for before dispatching to the handler. At minimum, document prominently that `data.shop` is not covered by the webhook HMAC and must not be trusted as an unauthenticated tenant identifier without additional server-side verification (e.g., matching against known installed-shop records).

### Proof of Concept
1. App is installed by attacker on `attacker-shop.myshopify.com` and also by victim on `victim-shop.myshopify.com`, both using the same app (`api_secret_key`).
2. Shopify delivers a genuine webhook to the app's endpoint for the attacker's shop:
   - Headers: `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of body B>`, body `B`.
3. Attacker captures `(B, HMAC(B))` and replays a forged request to the same endpoint:
   - Headers: `x-shopify-shop-domain: victim-shop.myshopify.com`, `x-shopify-hmac-sha256: <same HMAC of body B>`, body `B` (attacker chooses `B`'s content within whatever topic schema they registered a handler for).
4. `ShopifyAPI::Webhooks::Request.new` parses headers, `HmacValidator.validate` recomputes HMAC over `B` only and passes (per `to_signable_string` / `validate_signature`), and `Registry.process` calls the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: B, ...)`, causing the host app to process attacker-controlled content as if it originated from the victim's shop.
