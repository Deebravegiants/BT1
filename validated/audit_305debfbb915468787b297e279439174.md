### Title
Webhook HMAC covers only the raw body, not the `shop` header used for tenant identity - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC signature Shopify sends only authenticates the JSON body content. The `shop`, `topic`, `api_version`, and `webhook_id` values are read straight from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) and are never included in the signed payload, yet `Registry.process` passes them unmodified into `WebhookMetadata`, which apps use as the authoritative tenant/shop identifier for processing the event.

### Finding Description
`Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-22`) computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to `verifiable_query.hmac`. For `Webhooks::Request`, `hmac` decodes the `shopify-hmac-sha256` header and `to_signable_string` returns `@raw_body` only [1](#0-0) . Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all sourced from unauthenticated headers via `shopify_header` [2](#0-1) . `Registry.process` validates the HMAC and then forwards these header-derived values directly to the handler as trusted metadata [3](#0-2) . The equality the gem implicitly (and incorrectly) guarantees is: `shop header value == shop for which the signed body was generated`. In reality the HMAC only proves `raw_body == body signed by Shopify with the app secret`; it says nothing about which shop that body belongs to. Any request with a body/HMAC pair that was genuinely issued for shop A can be replayed with the `shop-domain` header changed to shop B, and it will still pass `Registry.process`'s HMAC check.

### Impact Explanation
An attacker who legitimately installs the app on their own store (an unprivileged action requiring no secrets) continuously receives genuine webhook deliveries to the app's public webhook endpoint, each with a valid body + `X-Shopify-Hmac-Sha256` pair signed with the app's shared secret. By capturing one such delivery and re-sending it to the same endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop's domain, the attacker gets the app to process attacker-controlled/attacker-supplied event content (e.g., `orders/create`, `app/uninstalled`, `customers/data_request`) as if it originated from the victim shop. Depending on what the host application's `WebhookHandler.handle` does with `data.shop` (e.g., writing state keyed by shop, triggering data exports, honoring `shop/redact` or `customers/redact` mandatory topics), this is a cross-tenant data integrity/confidentiality break driven entirely by trusting an unsigned header as the tenant identity.

### Likelihood Explanation
Reaching this requires no possession of `api_secret_key`, no TLS interception, and no privileged account — only the ability to install the app on any shop (which is the normal, expected way to obtain access to the app) and to observe/replay one legitimate webhook HTTP request, which is fully attacker-visible since it is delivered to the app's own endpoint. The only constraint is that the attacker must reuse an actual previously-signed body rather than forging arbitrary content, which narrows but does not eliminate impact for topics whose body content is attacker-influenced or where the mere shop-identity confusion (e.g., redact/uninstall topics) is itself damaging.

### Recommendation
Bind the header-derived identity to the signed payload: include `shop`, `topic`, and `webhook_id` in the HMAC-signed string (mirroring Shopify's newer per-field signing patterns), or independently verify that the `shop-domain` header corresponds to a session/shop the app has actually installed for the specific webhook subscription id before dispatching to the handler, rather than trusting the header outright once the body-only HMAC passes.

### Proof of Concept
1. Register a webhook handler and endpoint as in `docs/usage/webhooks.md` (`ShopifyAPI::Webhooks::Registry.process(ShopifyAPI::Webhooks::Request.new(raw_body:, headers:))`).
2. Install the app on `attacker-shop.myshopify.com`; capture a genuine incoming webhook POST, e.g. body `{"id":123}` with header `X-Shopify-Hmac-Sha256: <valid-for-body>` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Replay the identical body and `X-Shopify-Hmac-Sha256` value to the same endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes the HMAC over `@raw_body` only, which still matches, so `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: {"id":123}, ...)` — the app processes an event under the victim's identity despite it never having sent that request.           received_signature = verifiable_query.hmac
