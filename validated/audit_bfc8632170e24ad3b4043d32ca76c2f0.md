## Title
Escrowed native-token funds permanently frozen if a cross-chain order's beneficiary is a contract without a payable `receive`/`fallback` — (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`, `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentGatewayV2.withdraw()` and `IntentsBase._withdraw()` unconditionally push native ETH to a `beneficiary` address decoded from a cross-chain `WithdrawalRequest` (populated from `order.user` on refund or `msg.sender`/solver on redeem) via a low-level `.call{value: amount}("")`, and `revert` the entire `onAccept` transaction if the push fails. This is the same bug class as the reported Footium issue: a contract beneficiary without a payable fallback makes the native-token transfer permanently un-deliverable.

### Finding Description
When a cross-chain intent order settles, the source-chain gateway's `onAccept` is invoked by the ISMP host with a `RedeemEscrow` or `RefundEscrow` request, decoding a `WithdrawalRequest{commitment, tokens, beneficiary}` and calling `withdraw()`: [1](#0-0) 

Inside `withdraw()`, for native-token entries (`token == address(0)`), funds are force-pushed to `beneficiary` and the call reverts on failure: [2](#0-1) 

The same unconditional native push/`revert`-on-failure pattern exists in the shared base logic used by the EVM IntentGatewayV2 implementations (`_withdraw`, called from `onAccept` for `RedeemEscrow`/`RefundEscrow`): [3](#0-2) 

The `beneficiary` here is attacker/user-controlled cross-chain data: for a `RefundEscrow` it is `order.user` (set by whoever placed the order), and for `RedeemEscrow` it is the filling solver's address (`msg.sender` at fill time), both encoded in the message body dispatched from the other chain — see the `WithdrawalRequest` construction in the cancel/fill flow: [4](#0-3) 

If either of these addresses is a smart contract without a `receive()`/payable `fallback()`, the `.call{value: amount}("")` fails, and the entire `onAccept` handler reverts. There is no ERC20-wrapping fallback here (unlike `WrappedHyperFungibleToken.onAccept`, which explicitly re-wraps ETH to WETH and does an ERC20 `safeTransfer` if the native push fails — showing the team is aware of and has fixed this exact class of bug elsewhere): [5](#0-4) 

Because `IntentGatewayV2`/`IntentsBase` lack this fallback, a relayer's submission of the settlement proof for that commitment will keep reverting forever. No governance or user action can change the already-committed `beneficiary` in the dispatched message (it is fixed in the order/commitment at placement/fill time), and no retry with a different address is possible without redeploying/rebuilding the commitment.

### Impact Explanation
The escrowed input tokens (native ETH) tied to that order commitment become permanently frozen in the `IntentGatewayV2` contract on the source chain: any relayer attempting to deliver the `RedeemEscrow` (successful fill settlement) or `RefundEscrow` (cancellation refund) message will have their transaction revert indefinitely, since the beneficiary contract can never accept the push. This is a concrete permanent freezing-of-funds bug reachable purely by a user placing an order whose `order.user` (refund beneficiary) is a non-payable contract, or a solver filling with a non-payable contract as `msg.sender`.

### Likelihood Explanation
Any user can trigger this unintentionally (multisig/contract wallets without payable fallback are common) or an attacker could deliberately craft this to grief a solver's fills or lock protocol escrow. No privileged role is required — a single order placement + fill/cancel + relay of the resulting message is sufficient.

### Recommendation
Mirror the pattern already used in `WrappedHyperFungibleToken.onAccept`/`onPostRequestTimeout`: on native-push failure, fall back to wrapping the native asset (e.g. WETH) and delivering it as an ERC-20 transfer to the beneficiary instead of reverting the whole settlement. Alternatively, adopt a pull-based withdrawal pattern (credit an internal balance mapping that the beneficiary can withdraw later) so that a failed push never blocks message delivery/settlement finality.

### Proof of Concept
1. User places a cross-chain order with `order.user` set to a contract address `C` that has no `receive()`/payable `fallback()` and native-ETH input escrowed.
2. Order expires; anyone calls `cancelOrder`, which dispatches a `RefundEscrow` request back to the source chain with `beneficiary = order.user = C`. [6](#0-5) 
3. A relayer submits the ISMP proof to deliver the request; `onAccept` decodes the body and calls `withdraw()`.
4. `withdraw()` attempts `C.call{value: amount}("")`, which fails since `C` rejects native ETH; the `if (!sent) revert InsufficientNativeToken();` check reverts the whole transaction. [7](#0-6) 
5. Every subsequent relay attempt for the same commitment reverts identically — the escrowed native ETH is permanently locked in the gateway contract.

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();

                if (!success) revert TransferFailed();

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
