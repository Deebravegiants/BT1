## Analysis: Permissionless `CallDispatcher.dispatch()` enables theft of any funds it custodies

### Title
Unauthenticated `CallDispatcher.dispatch()` allows theft of any ETH/token balance transiently held by the shared dispatcher contract - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher` is a single, shared, permissionless utility contract reused across `HyperFungibleToken`, `WrappedHyperFungibleToken`, `IntentGatewayV2` and `ExtrinsicIntents` to execute arbitrary post-mint/post-fill calldata (swap-then-forward patterns) [1](#0-0) . Its `dispatch(bytes)` function has **no caller restriction whatsoever** and its `receive()` accepts ETH from anyone [2](#0-1) . Any address on-chain — an unprivileged message dispatcher, relayer, or ordinary EOA — can call `dispatch()` directly and force the `CallDispatcher` to execute an arbitrary `Call[]` moving out any ETH or ERC20 balance it happens to be holding at that moment.

### Finding Description
Multiple ISMP apps route mint/unlock/fill proceeds through this shared `CallDispatcher` before sweeping them back to the app contract:
- `HyperFungibleToken.onAccept` mints tokens to a beneficiary (which can be the `CallDispatcher` itself) and then calls `ICallDispatcher(_dispatcher).dispatch(message.data)` [3](#0-2) .
- `IntentsBase._execute` transfers order output tokens through the dispatcher, runs `order.output.call`, then attempts to sweep only the *known* `order.output.assets` back to the gateway [4](#0-3) .
- `IntentGatewayV2` and its Tron variant route `predispatch` assets through the same dispatcher [5](#0-4) .

Because the sweep logic in `_execute` only recovers balances for tokens explicitly listed in `order.output.assets` [6](#0-5) , any token produced as an unlisted intermediate/byproduct of the executed `Call[]` (e.g., an intermediate swap-path token, rounding remainder, or airdrop/dust sent to the dispatcher) is left un-swept inside `CallDispatcher`. Likewise, if any downstream call in a multi-call batch reverts before completing a transfer-out (though `HyperFungibleToken`/`IntentsBase` require the whole batch to succeed, partial successes within the `Call[]` sequence prior to the failing call are not rolled back independently — only the whole transaction is), residual balances can persist in the dispatcher's storage across blocks.

Since `dispatch()` has no `onlyHost`, `onlyGateway`, or any allow-list check, **any external account can subsequently call `CallDispatcher.dispatch()` directly** with a `Call[]` of its own choosing (e.g., `IERC20.transfer` to itself for any token balance, or a plain value-transfer `Call` to drain native ETH) and extract whatever the contract is holding — funds that belong to whichever app/user last routed assets through it.

This is the same bug class flagged by the DAFI/ChainSwap report referenced by the external report: a bridge-adjacent contract exposes a function that moves assets under attacker-controlled instructions without verifying the caller is an authorized bridge component, letting anyone trigger unauthorized asset movement out of a contract that is supposed to be a trusted intermediary.

### Impact Explanation
Any ETH or ERC20 balance that transiently or persistently sits in the shared `CallDispatcher` — across `HyperFungibleToken`, `WrappedHyperFungibleToken`, and both `IntentGatewayV2`/`ExtrinsicIntents` intents flows on every chain that reuses the same deployment [7](#0-6)  — can be permanently stolen by any unprivileged address. Given the dispatcher is explicitly a **shared singleton** ("Existing `CallDispatcher` deployments are listed on the contract addresses page"), the blast radius spans every app that references it, not a single deployment.

### Likelihood Explanation
Exploitation requires only a single unauthenticated transaction to `CallDispatcher.dispatch()` — no proof, no consensus verification, no relayer privilege — as soon as any residual balance (dust from an unlisted output token, ETH sent via `receive()`, or a stuck partial execution) is observable on-chain. This is directly reachable by any address, matching the "unprivileged... token bridger" reachability requirement.

### Recommendation
Restrict `CallDispatcher.dispatch()` to only the authorized calling contract(s) for a given invocation (e.g., pass/verify an authorized caller allow-list, or make each app deploy/own its own dispatcher instance rather than sharing one globally), and ensure `_execute`/`onAccept` sweep logic accounts for *all* balances the dispatcher could plausibly hold (not just the explicitly listed output assets) before returning control, so no exploitable residual balance can remain.

### Proof of Concept
1. A user bridges tokens via `HyperFungibleToken.send()` with `to = CALL_DISPATCHER` and `data` encoding a `Call[]` that performs a Uniswap swap through an intermediate token not accounted for in the destination logic.
2. `onAccept` mints tokens to the dispatcher and calls `dispatch()`, which performs the swap; the intermediate/output token from the swap is not fully forwarded and remains held by `CallDispatcher`.
3. Any third party observes the residual balance (e.g., via `IERC20.balanceOf(dispatcher)`) and calls `CallDispatcher.dispatch(abi.encode([Call({to: token, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, balance)})]))` directly — no access control blocks this — draining the balance to themselves.

     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

Existing `CallDispatcher` deployments are listed on the [contract addresses](/developers/evm/contract-addresses/mainnet) page.
