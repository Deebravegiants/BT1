### Title
GRANDPA justification verification performs unbounded work on attacker-supplied ancestry headers before any signature/authority check succeeds, enabling a free-transaction CPU-exhaustion DoS - (File: `modules/consensus/grandpa/primitives/src/justification.rs`)

### Summary
`GrandpaJustification::verify_with_voter_set` (`modules/consensus/grandpa/primitives/src/justification.rs:66-146`) builds an `AncestryChain` from the fully attacker-controlled `votes_ancestries: Vec<H>` field of a GRANDPA consensus proof, then, for every precommit, walks that chain and finally hashes every supplied header to build a `BTreeSet` for a final equality check. This proof is submitted via the free, unsigned `pallet-ismp::handle_unsigned` extrinsic (`modules/pallets/ismp/src/lib.rs:373-382`), whose `validate_unsigned` implementation actually *executes* the message (`modules/pallets/ismp/src/lib.rs:614-625`) — i.e., this expensive verification runs on every node's transaction-pool validation path, before any fee is charged and before the proof is known to be valid.

### Finding Description
`verify_with_voter_set` (lines 66-146) does the following with attacker-supplied data:
1. Constructs `AncestryChain::new(&self.votes_ancestries)` — a `BTreeMap` built from every header the submitter chooses to include, with no upper bound on `Vec<H>` length or on each header's own encoded size (a Substrate `Header`'s `digest: Vec<DigestItem>` is itself unbounded).
2. For each precommit in `self.commit.precommits` (bounded by the real GRANDPA voter set, but this can still be hundreds of entries), it calls `ancestry_chain.ancestry(base_hash, target_hash)` (`AncestryChain::ancestry`, lines 180-197), which walks parent-hash links through the header map. This is `O(votes_ancestries.len())` per iteration in the worst case (crafted long, disconnected, or maximal chains), giving up to `O(precommits.len() * votes_ancestries.len())` total.
3. It then computes `h.hash()` for **every** header in `votes_ancestries` (line 137) to build `ancestry_hashes`, forcing a full hash pass over the whole attacker-controlled blob regardless of whether the walk above rejected early.

Crucially, none of this is gated behind the actual GRANDPA signature check succeeding for the ancestry data itself — the walk and the final hash-comparison happen unconditionally on `votes_ancestries`, and `finality_grandpa::validate_commit` (line 75) only validates the *commit/precommit signatures*, not the size or shape of the supplied ancestry vector. There is no visible cap (`MaxEncodedLen`, explicit length check, or similar) on `votes_ancestries` before this cost is paid.

This is delivered through `pallet_ismp::Call::handle_unsigned` (`modules/pallets/ismp/src/lib.rs:373-382`), which is `ensure_none` (unsigned, free) and whose `ValidateUnsigned::validate_unsigned` (lines 614-625) calls `Self::execute(messages.clone())` — meaning the entire (potentially adversarial) verification workload runs on **every node's mempool validation** of the submitted extrinsic, at zero cost to the submitter, and can be resubmitted repeatedly with trivial per-submission variation.

This is the same bug class as the reported Rack multipart-parser CVE (CWE-400): an untrusted, attacker-shaped input structure drives a verification/parsing routine into a CPU cost disproportionate to the "useful" size of the request, because the routine does unbounded work on attacker-controlled auxiliary data before the cheap, bounding checks (signature validity, structural caps) are enforced.

### Impact Explanation
Because `handle_unsigned` messages are validated for free by every collator/full node's transaction pool (per the documented design in `docs/content/developers/polkadot/pallet-ismp/overview.mdx:258`, "all cross-chain messages received are executed for free as unsigned transactions"), an attacker who can grow `votes_ancestries` to be large (bounded only by the chain's max extrinsic/block length, typically several MB) forces disproportionate CPU work (`BTreeMap` construction + repeated ancestry walks + hashing every header) on every node that must validate the extrinsic before it can even determine the proof is invalid. Repeated submission of such payloads (with cheap per-submission mutation to avoid `provides`-tag dedup) can degrade validator/relayer node responsiveness and mempool throughput — a network-wide availability degradation for the GRANDPA-consensus route, which can delay or block legitimate message delivery (a "route unable to deliver messages" condition) network-wide, not just for a single submitter.

### Likelihood Explanation
This requires only a normal, unprivileged actor able to submit an unsigned extrinsic (any relayer/user, no special permission) with a decodeable but ultimately-invalid `ConsensusMessage::StandaloneChain`/`Relaychain`/`Polkadot` proof containing an oversized `votes_ancestries` vector. No signature forgery or consensus compromise is needed — the cost is paid regardless of whether the proof ultimately verifies. The barrier is only the general extrinsic/block size limit, not any dedicated guard on this specific field, making this straightforward and repeatable to trigger.

### Recommendation
Add an explicit, low upper bound on `votes_ancestries.len()` (and ideally on cumulative header size) before constructing `AncestryChain` or performing the `ancestry()` walk, rejecting proofs that exceed the bound as `InvalidJustification`/`ProofTooLarge` immediately after decode. Consider also capping `commit.precommits.len()` and enforcing it before this loop, and short-circuiting the final `ancestry_hashes` computation to only the headers actually visited (`visited_hashes`) rather than hashing the entire input, so that unused/unvisited attacker padding never gets paid for by an honest verifier.

### Proof of Concept
Not directly executable from a static index review — this finding is based on tracing the reachable call path (`pallet_ismp::handle_unsigned` → `validate_unsigned` → `Self::execute` → `GrandpaConsensusClient::verify_consensus` → `verify_grandpa_finality_proof`/`verify_parachain_headers_with_grandpa_finality_proof` → `GrandpaJustification::verify` → `verify_with_voter_set`) and the absence of any length guard on `votes_ancestries` prior to the `AncestryChain` construction and walk in `modules/consensus/grandpa/primitives/src/justification.rs:66-146`. A concrete PoC would submit a `Message::Consensus` extrinsic whose `ConsensusMessage::StandaloneChain` proof decodes successfully, has legitimate-looking `commit.precommits` (or a set sized to the real voter set) but a `votes_ancestries` vector padded to the maximum allowed extrinsic size with maximal-digest headers, and measure per-node validation time versus a minimal-size equivalent proof. 	pub fn verify_with_voter_set(
		&self,
		set_id: u64,
		voters: &VoterSet<AuthorityId>,
	) -> Result<(), anyhow::Error> {
		use finality_grandpa::Chain;

		let ancestry_chain = AncestryChain::<H>::new(&self.votes_ancestries);

		match finality_grandpa::validate_commit(&self.commit, voters, &ancestry_chain) {
			Ok(ref result) if result.is_valid() => {
				if result.num_duplicated_precommits() > 0 ||
					result.num_invalid_voters() > 0 ||
					result.num_equivocations() > 0
				{
					Err(anyhow!("Invalid commit, found one of `duplicate precommits`, `invalid voters`, or `equivocations` {result:?}"))?
				}
			},
			err => {
				let result = err.map_err(|_| {
					anyhow!("[verify_with_voter_set] Invalid ancestry while validating commit!")
				})?;
				Err(anyhow!("invalid commit in grandpa justification: {result:?}"))?
			},
		}

		// we pick the precommit for the lowest block as the base that
		// should serve as the root block for populating ancestry (i.e.
		// collect all headers from all precommit blocks to the base)
		let base_hash = self
			.commit
			.precommits
			.iter()
			.map(|signed| &signed.precommit)
			.min_by_key(|precommit| precommit.target_number)
			.map(|precommit| precommit.target_hash.clone())
			.expect(
				"can only fail if precommits is empty; \
				 commit has been validated above; \
				 valid commits must include precommits; \
				 qed.",
			);

		let mut visited_hashes = BTreeSet::new();
		for signed in self.commit.precommits.iter() {
			let message = finality_grandpa::Message::Precommit(signed.precommit.clone());

			check_message_signature::<_, _>(
				&message,
				&signed.id,
				&signed.signature,
				self.round,
				set_id,
			)?;

			if base_hash == signed.precommit.target_hash {
				continue;
			}

			let route = ancestry_chain
				.ancestry(base_hash, signed.precommit.target_hash)
				.map_err(|_| anyhow!("[verify_with_voter_set] Invalid ancestry!"))?;
			// ancestry starts from parent hash but the precommit target hash has been
			// visited
			visited_hashes.insert(signed.precommit.target_hash);
			for hash in route {
				visited_hashes.insert(hash);
			}
		}

		let ancestry_hashes: BTreeSet<_> =
			self.votes_ancestries.iter().map(|h: &H| h.hash()).collect();

		if visited_hashes != ancestry_hashes {
			Err(anyhow!(
				"invalid precommit ancestries in grandpa justification with unused headers",
			))?
		}

		Ok(())
	}

impl<H: HeaderT> finality_grandpa::Chain<H::Hash, H::Number> for AncestryChain<H>
where
	H::Number: finality_grandpa::BlockNumberOps,
{
	fn ancestry(
		&self,
		base: H::Hash,
		block: H::Hash,
	) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
		let mut route = vec![block];
		let mut current_hash = block;
		while current_hash != base {
			match self.ancestry.get(&current_hash) {
				Some(current_header) => {
					current_hash = *current_header.parent_hash();
					route.push(current_hash);
				},
				_ => return Err(finality_grandpa::Error::NotDescendent),
			};
		}
		Ok(route)
	}
