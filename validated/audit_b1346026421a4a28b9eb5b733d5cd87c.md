## Title
Webhook Shop/Topic Identity Spoofing via HMAC Scope Mismatch - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` fields that `ShopifyAPI::Webhooks::Registry.process` uses to route and attribute the webhook are read directly from unauthenticated HTTP headers. Any attacker who can obtain one genuine `(raw_body, hmac)` pair signed by the app's `client_secret` (trivially available to anyone who installs the app on their own store and captures their own webhook deliveries) can replay that exact body/HMAC pair while substituting the `shopify-shop-domain`, `shopify-topic`, or `shopify-webhook-id` headers with arbitrary values, and the request will still pass HMAC validation.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` verifies a `VerifiableQuery`'s `hmac` against a signature computed over `to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw HTTP body: [2](#0-1) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are parsed straight from the incoming headers with no cryptographic binding to the signed content: [3](#0-2) 

`Registry.process` validates only the HMAC of the body and then dispatches the handler using the unauthenticated header-derived `topic` and `shop`: [4](#0-3) 

The identity binding that should hold is: **shop/topic authenticated == shop/topic acted upon**. Here, the bytes verified by HMAC (the body) are disjoint from the bytes actually parsed and trusted for tenant/topic attribution (the headers). This is the same class of bug as the report's root cause — a value that participates in a security-relevant decision (`_owner`/tier state in the MEME404 case; `shop`/`topic` here) is not covered by the integrity mechanism relied upon to prevent forgery (a callback race in the original; the HMAC signable-string scope here).

Because an attacker can freely install the target app on a shop they control, they legitimately receive `(body, hmac)` pairs signed with the real `client_secret` for topics they subscribed to. They can then replay that same body+hmac to the host application's webhook endpoint while forging the `shopify-shop-domain` header to name a *different*, victim shop, and/or forging the `shopify-topic` header to a topic they never actually triggered. `Registry.process` will accept it as valid because HMAC validation never inspects those headers.

### Impact Explanation
This breaks the shop-authenticated == shop-acted-upon binding, allowing cross-tenant webhook spoofing: a handler written against `WebhookMetadata#shop` (built from the forged header) will process attacker-chosen body content as if it came from the victim's shop. Depending on what the host application's `WebhookHandler#handle` implementations do with `shop` (e.g. lookups, cache invalidation, triggering shop-specific side effects, mandatory `shop/redact`/`customers/redact` compliance handlers), this enables cross-tenant data confusion/actions — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only an unprivileged attacker with a legitimate app installation on any single shop (a free, developer-store install suffices for most public apps) to harvest one valid `(body, hmac)` pair per topic of interest, then replay it with forged headers against the app's webhook endpoint. No secret, token, or privileged access is required beyond what any installer already has.

### Recommendation
Bind the shop/topic/webhook_id metadata into the signed content, or otherwise cryptographically tie the header values to the HMAC. Concretely, include the `shopify-shop-domain`, `shopify-topic`, and `shopify-webhook-id` header values in `to_signable_string` (or independently verify them against a value embedded in the signed body/JWT), so that changing any of these headers invalidates the HMAC.

### Proof of Concept
```ruby
# Attacker installs the target app on their own controlled shop "attacker.myshopify.com"
# and captures a genuine webhook delivery for topic "orders/create":
raw_body = '{"id":1,"note":"legit order"}'
hmac     = Base64.encode64(OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), api_secret_key, raw_body))

# Attacker replays the exact same body+hmac but forges the shop-domain and topic headers:
forged_headers = {
  "shopify-topic"       => "orders/create",       # unchanged, or swapped to any registered topic
  "shopify-hmac-sha256" => hmac,                   # untouched, still valid because body is unchanged
  "shopify-shop-domain" => "victim-shop.myshopify.com", # forged - not covered by HMAC
  "shopify-webhook-id"  => "forged-id",
  "shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Utils::HmacValidator.validate(request) # => true, because only raw_body is checked
ShopifyAPI::Webhooks::Registry.process(request)
# Handler receives WebhookMetadata(shop: "victim-shop.myshopify.com", ...) despite the
# webhook never actually originating from that shop.
```

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
