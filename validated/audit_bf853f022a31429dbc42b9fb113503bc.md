Webhook `shop` domain is trusted from an unauthenticated HTTP header not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) solely from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, while the HMAC signature validated by `Utils::HmacValidator.validate` is computed only over the raw request body (`to_signable_string` returns `@raw_body`). The `shop` header is never part of the signed bytes, so it can be swapped freely without invalidating the HMAC check.

### Finding Description
`Registry.process` validates the webhook solely via `Utils::HmacValidator.validate(request)` and then immediately trusts `request.shop` to build `WebhookMetadata`: [1](#0-0) 

The HMAC is computed exclusively over `@raw_body`: [2](#0-1) 

But the `shop` accessor used downstream is read from a header that is completely outside that signed content: [3](#0-2) 

The identity binding this breaks is: `shop used for tenant attribution (header) != shop covered by the HMAC (none — only body bytes are signed)`. Since the same `client_secret`/`api_secret_key` is shared across every shop that installs a given app (it is not per-shop), any attacker who installs the app on their own store can generate a genuinely HMAC-valid webhook (correct signature over an attacker-chosen body), then replay that exact raw body + valid HMAC signature to the app's webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. `HmacValidator.validate` will still pass because it never inspects the `shop` header, and the resulting `WebhookMetadata` handed to the app's handler will report `shop: <victim-domain>` with attacker-controlled body content.

This contrasts with the OAuth callback path, where `shop` is explicitly included inside `to_signable_string` and therefore is bound by the HMAC: [4](#0-3) 

The webhook path has no equivalent binding.

### Impact Explanation
An app built on this gem processes every registered webhook by trusting `WebhookMetadata#shop` (sourced from `request.shop`) as the tenant identifier, e.g. to look up which shop's session/data to mutate. An attacker who has legitimate access to the app on any one shop (including a shop they control themselves) can forge webhook deliveries that are cryptographically valid (per this gem's own verification) but falsely attributed to a different, victim tenant. This is a cross-tenant identity confusion at the authentication-boundary layer this gem is responsible for (`Utils::HmacValidator` / `Webhooks::Request` / `Webhooks::Registry`), directly matching the "Critical - cross-tenant access" impact category, since the gem asserts the webhook is verified and safe to act on for the shop it reports, when in fact the shop attribution is unauthenticated.

### Likelihood Explanation
Exploitation requires only: (1) the ability to install/observe the target app on an attacker-controlled shop to obtain one genuinely signed webhook payload (any app installable by the public, e.g. via the Shopify App Store, satisfies this — no privileged credentials of the victim are needed), and (2) the ability to send an HTTP request to the app's public webhook endpoint with a modified `shop-domain` header, which is a standard unauthenticated-internet-user action. No access token, `client_secret`, or victim credentials are required, satisfying the scope constraints.

### Recommendation
Include the `shop` domain (and ideally `topic`/`webhook_id`) inside the signed material verified against the HMAC, or independently authenticate the `shop` header against a value derived from the app's own trusted session/installation store before constructing `WebhookMetadata`. At minimum, `Webhooks::Registry.process` should not accept the header-derived `shop` as authoritative without cross-checking it against the shop the app actually expects to receive this specific webhook payload for.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw POST body `B` and the genuine `shopify-hmac-sha256` header value `H` (valid because `H = HMAC-SHA256(api_secret_key, B)` and `api_secret_key` is shared across all installs of the app).
2. Attacker sends a new HTTP request to the app's webhook endpoint with:
   - Body: exactly `B` (unchanged)
   - Header `x-shopify-hmac-sha256`: exactly `H` (unchanged)
   - Header `x-shopify-shop-domain`: `victim.myshopify.com` (forged)
   - Header `x-shopify-topic`: unchanged
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`= B`) and finds it matches `H` — validation passes. [5](#0-4) 
4. `handler.handle` is invoked with `WebhookMetadata` reporting `shop: "victim.myshopify.com"` even though the payload originated from and was signed for the attacker's own shop. [6](#0-5)
