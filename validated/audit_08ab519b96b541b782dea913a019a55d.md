### Title
`promise_yield_create_with_id` yield-ID namespace is scoped only by contract account, not by caller — allowing front-run-and-grief of pending cross-contract callbacks - ([File: runtime/runtime/src/ext.rs])

### Summary
NEP-compliant meta/callback tooling in nearcore exposes a host function, `promise_yield_create_with_id`, that lets any function call register a user-provided 32-byte `yield_id` for the *currently executing contract account*, with duplicate detection keyed only by `(receiver_id, yield_id)` where `receiver_id` is the contract's own account id — not the predecessor/caller who triggered the call. This mirrors the reported Solidity bug class: an identifier used to guard against duplicate/competing operations omits the actor ("proposer"/caller) from its uniqueness key, letting any unprivileged party front-run and block a legitimate operation that would otherwise use the same identifier.

### Finding Description
`promise_yield_create_with_id` is implemented in `runtime/near-vm-runner/src/logic/logic.rs` (and the wasmtime mirror in `runtime/near-vm-runner/src/wasmtime_runner/logic.rs`). It forwards to: [1](#0-0) 

which performs duplicate detection via `has_yield_id_mapping(self.trie_update, &receiver_id, user_yield_id)`. Here `receiver_id` is not the caller/predecessor of the function call — it is `self.context.current_account_id`, i.e. the contract account under which the yield is being created: [2](#0-1) 

The trie key used for this bookkeeping, `TrieKey::YieldIdToDataId`, is likewise scoped only by `receiver_id` and `yield_id`, with no binding to the transaction signer or predecessor account that invoked the host call: [3](#0-2) 

Consequently, for any contract that is shared by multiple unrelated end users (e.g. an exchange, marketplace, or escrow contract where each user's function call internally derives or accepts a `yield_id` — such as an order id, request id, or any value an attacker can predict or also control), the yield-id namespace is a single flat space per contract account. An unprivileged attacker can submit an ordinary transaction to the very same contract, calling the same (or another) method that triggers `promise_yield_create_with_id` with a colliding `yield_id`, before the victim's transaction lands. Since duplicate detection only checks `(receiver_id, yield_id)` and not the caller, the victim's subsequent legitimate call receives the `u64::MAX` sentinel instead of successfully registering its own pending yield: [4](#0-3) 

This is the direct protocol-level analog of the reported bug class: an identifier meant to disambiguate a pending operation is not bound to the actor who is supposed to own it, so any other unprivileged actor can pre-empt/collide with it and block the legitimate flow — exactly as VeloGovernor's `proposalHash()` omitted `proposer`, letting a griefer front-run and cancel a targeted proposal.

### Impact Explanation
The griefed call does not create its intended `PromiseYield` receipt and callback chain; the calling contract only learns of the collision via the `u64::MAX` return value and must have been written defensively to detect and recover from it (as the doc comment itself acknowledges: "Contracts can branch on this to recover from duplicates without aborting execution"). Any contract logic that assumes uniqueness of its own `yield_id` scheme across its user base (rather than being aware that the namespace is shared and un-authenticated) can have specific user-initiated operations silently denied by a third party, producing application-level denial-of-service / stuck-callback conditions for the targeted account without requiring any privilege beyond submitting an ordinary transaction to the shared contract. This matches the reported class's classification as griefing/DoS (Medium severity), not direct fund theft, since gas/deposit deduction for the new receipt happens only after the duplicate check succeeds (`Some` branch), so the attacker does not directly steal the victim's deposit, but the victim's expected asynchronous callback path can be blocked.

### Likelihood Explanation
Exploitation requires no special privileges: any account with enough gas to submit a `FunctionCall` action to the same contract as the victim, guessing or replicating the target `yield_id` (which is often application-defined, e.g., deterministic per order/request), before the victim's transaction is applied. This is fully reachable from ordinary transaction/receipt processing paths and does not require validator, network, or mocked-only access.

### Recommendation
Bind the yield-id uniqueness key to the calling context as well as the receiver, e.g. incorporate the predecessor account id (or another authenticated component under the contract's control, not attacker-suppliable) into the `TrieKey::YieldIdToDataId` / `DataIdToYieldId` keys, or document explicitly and prominently that `yield_id` uniqueness is scoped per-contract-account only and that contracts MUST derive `yield_id` values that cannot be predicted or replayed by third parties (e.g., by hashing in the predecessor id and a contract-internal counter) before relying on this API for access control or ordering guarantees.

### Proof of Concept
1. Deploy/target a shared contract `C` that, on receiving a `FunctionCall` from any user, derives a `yield_id` from application-visible data (e.g. `sha256(order_id)`), and calls `promise_yield_create_with_id` with it, per `runtime/near-test-contracts/estimator-contract/src/lib.rs` and the `call_promise` test dispatcher pattern in `integration-tests/src/tests/runtime/test_yield_resume.rs`.
2. Attacker learns/predicts the `order_id`/`yield_id` the victim's imminent transaction will use for account `C`.
3. Attacker submits their own `FunctionCall` transaction to `C` using the same `yield_id`, and gets it included first.
4. Victim's transaction to `C` executes `promise_yield_create_with_id` with the identical `yield_id`; because `has_yield_id_mapping` only checks `(C, yield_id)` (see `runtime/runtime/src/ext.rs:378`), it returns `None`, and the host call returns the `u64::MAX` sentinel to the victim's contract execution instead of creating the intended pending callback — exactly reproducing the "duplicate create with same id returns sentinel" behavior asserted in `integration-tests/src/tests/runtime/test_yield_resume.rs:361-386`, but triggered by an unrelated third-party transaction rather than the same caller.
