### Title
Attacker-minimized `ltFromPair` + hostile HyperSwap pre-seed causes an unrecoverable `Math.mulDiv` overflow revert in `Bonding._noFeeSwapInput`, permanently bricking `finalizeGraduation` and freezing the parked curve-raised LT and 250M LP tokens - ([File: packages/contracts/src/Bonding.sol])

### Summary
CVE-2023-23009 is a DoS where a crafted length field triggers an unconditional assert failure that permanently kills the daemon. The analog here is a crafted-ratio input (an attacker-chosen, near-zero `ltFromPair`/`tokensForLP` denominator combined with an attacker-controlled HyperSwap V2 pre-seed) that drives `Bonding._noFeeSwapInput`'s `Math.mulDiv` call past uint256 capacity, causing an unconditional revert. Because `finalizeGraduation` takes no caller-supplied parameters and the underlying cached values (`pendingGraduation`) can never be recomputed once a token enters `Lifecycle.Graduating`, the revert is permanent: the token can never leave the `Graduating` state, and all curve-raised LT plus up to 250M tokens parked on `Bonding` are frozen forever.

### Finding Description
`_deployAndSeed` only upper-bounds the launch-time virtual LT reserve — it rejects an exchange rate that is *too low* (`ExchangeRateTooLow`) but places no lower bound on `virtualLtReserve` for a *high* exchange rate: [1](#0-0) 

A creator can pick a BounceTech LT with a very high `exchangeRate()`, which drives `virtualLtReserve` (and therefore `K = TOTAL_SUPPLY * virtualLtReserve`) down to a tiny value. On such a curve, the supply-exhaustion graduation trigger (`tokenBalance() == 0`) can fire after real buyers have deposited only a minuscule amount of LT, making the eventual `ltFromPair` computed in `_prepareGraduationLiquidity` arbitrarily small: [2](#0-1) [3](#0-2) 

Once phase 1 fires and the token is `Graduating`, anyone (including the same attacker) can pre-mint a HyperSwap V2 `TOKEN/LT` pair with an extreme reserve skew before calling the permissionless `finalizeGraduation`. This routes `_seedUniswapV2Direct` into the "Regime 3" rebalance branch (`_seedRebalancing`), which selects a rebalance direction whose `targetD` is the attacker-minimized `ltFromPair` (or `tokensForLP`, similarly manipulable): [4](#0-3) 

`_pairRebalance` then calls `_noFeeSwapInput`, which computes:
```
product = Math.mulDiv(reserveIn * reserveOut, targetN, targetD)
```
with `reserveIn`/`reserveOut` up to `uint112.max` (attacker-set HyperSwap reserves) and `targetD` driven arbitrarily close to zero. The code's own comment acknowledges this is unguarded and will revert rather than truncate: [5](#0-4) 

`Math.mulDiv` in OpenZeppelin reverts (`MathOverflowedMulDiv`) when the true product cannot be represented in 256 bits after the division — exactly what an attacker-controlled combination of huge `reserveIn*reserveOut` and near-zero `targetD` produces.

This revert propagates all the way up through `_pairRebalance` → `_seedRebalancing` → `_seedUniswapV2Direct` → `finalizeGraduation`: [6](#0-5) 

`finalizeGraduation` has no arguments and derives everything from `pendingGraduation[token]` (frozen at phase 1) plus the live, attacker-controlled HyperSwap pair state — there is no way to call it with different values or repair the computation. As long as the attacker (or anyone) does not remove/rebalance their own pre-seeded LP — which they have no incentive to do — every future call to `finalizeGraduation(token)` reverts identically forever.

### Impact Explanation
The token becomes permanently stuck in `Lifecycle.Graduating`:
- All real curve-raised LT (`ltFromPair`, already pulled out of the curve `Pair` via `Router.graduate` inside `_prepareGraduationLiquidity`) sits in `Bonding` with no withdrawal path.
- Up to `LP_RESERVE` (250,000,000 tokens, 25% of supply) minted to `Bonding` for LP seeding is permanently stranded.
- Trading is frozen (`buy`/`sell` both reject non-`Curve` lifecycle), and `LPLock.recordLock` — the one-shot call that `finalizeGraduation` cannot skip — never fires, so the token can never legitimately open a V2 market.

This is a permanent freezing of creator/trader/LP funds reachable purely through unprivileged transactions (`launch`, curve `buy`s, and a HyperSwap V2 `mint`/pre-seed), matching the CVE's "denial of service" bug class mapped onto alt.fun's real two-phase-graduation and pre-seedable-LP-pair shape.

### Likelihood Explanation
Medium. The attack requires: (1) finding or deploying a BounceTech LT with a sufficiently high `exchangeRate()` (feasible — LT creation/rate is outside `Bonding`'s control and no lower bound is enforced), (2) driving the curve to the supply-exhaustion trigger cheaply, and (3) pre-seeding the HyperSwap pool with an extreme, self-funded ratio skew. All steps are executable by a single unprivileged address with ordinary transactions; no privileged role or off-chain component is needed. The natspec throughout `Bonding.sol` shows the authors deliberately hardened most bricking vectors (saturating subtracts, `_swapBudget` 1% reserve, direct-mint fallback for "too small" swaps) but explicitly left `_noFeeSwapInput`'s overflow path as "the correct failure mode" — i.e., an acknowledged but unmitigated revert path.

### Recommendation
- Enforce a sane lower bound on `virtualLtReserve` in `_deployAndSeed` (mirroring the existing `ExchangeRateTooLow` upper-bound check) so `ltFromPair` cannot be driven to a value that makes downstream ratio math degenerate.
- In `_noFeeSwapInput`, clamp/guard the `Math.mulDiv` call (e.g., detect when the result would overflow and fall back to the existing direct-mint path) instead of letting the arithmetic revert propagate up through `finalizeGraduation`.
- More generally, ensure `finalizeGraduation` always has a guaranteed-successful fallback path (as already exists for the "seed too small" case) for *every* possible attacker-chosen combination of cached `(tokensForLP, ltFromPair)` and live, attacker-influenceable HyperSwap reserves.

### Proof of Concept
1. Attacker deploys/selects a BounceTech LT whose `exchangeRate()` is very high, so `virtualLtReserve = VIRTUAL_LIQUIDITY_USD * 1e18 / exchangeRate` is minimal (just above the `ExchangeRateTooLow` floor check) — see `Bonding._deployAndSeed`, `packages/contracts/src/Bonding.sol:477-484`.
2. Attacker calls `Zap.createToken`/`launch` with this LT, then buys through the curve until `IPair.tokenBalance() == 0` (supply-exhaustion trigger), paying only a tiny amount of real LT — `ltFromPair` computed in `_prepareGraduationLiquidity` (`packages/contracts/src/Bonding.sol:1084-1096`) ends up near-dust.
3. Phase 1 fires automatically (`_enterGraduating`), caching the tiny `ltFromPair`/`tokensForLP` in `pendingGraduation`.
4. Before anyone calls `finalizeGraduation`, attacker creates the HyperSwap V2 `TOKEN/LT` pair and calls `mint()` directly with an extreme, self-funded reserve skew (e.g., very large `reserveToken`, tiny `reserveLT`, or vice versa) to land in Regime 3 of `_seedUniswapV2Direct`.
5. Anyone calls `Bonding.finalizeGraduation(token)`. `_seedRebalancing` selects the branch whose `targetD` equals the near-dust `ltFromPair` (or `tokensForLP`), and `_noFeeSwapInput`'s `Math.mulDiv(reserveIn * reserveOut, targetN, targetD)` overflows uint256, causing `Math.mulDiv` to revert — see `packages/contracts/src/Bonding.sol:1507-1522`.
6. Every subsequent call to `finalizeGraduation(token)` reverts identically (no arguments to vary, cached state unchanged), permanently stranding the curve-raised LT and the 250M LP-reserve tokens in `Bonding`.

        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[tokenAddress];
        if (info.lifecycle != Lifecycle.Graduating) revert NotGraduating();

        address lt = info.ltAddress;
        PendingGraduation memory p = $.pendingGraduation[tokenAddress];

        // Anything in this contract beyond `p.ltFromPair` belongs to a
        // concurrent graduation on the same LT (Phase 1 transferred it
        // via `Router.graduate`) or to stray dust. Either way it is
        // off-limits to this graduation's deposit and sweep — see
        // `_routerDepositAndDispose` and `_sweepLTToOwner`.
        // Saturating subtract: a balance below `p.ltFromPair` shouldn't
        // be reachable in normal operation, but we keep finalize from
        // bricking on a Panic if any future code path or non-canonical
        // LT briefly violates the invariant.
        uint256 ltBalance = IERC20(lt).balanceOf(address(this));
        uint256 protectedLT = ltBalance > p.ltFromPair ? ltBalance - p.ltFromPair : 0;

        address lpPair = _ensureUniswapV2Pair(tokenAddress, lt);
        uint256 liquidity = _seedUniswapV2Direct(tokenAddress, lt, lpPair, p.tokensForLP, p.ltFromPair, protectedLT);

        _sweepLTToOwner(lt, protectedLT);

        info.lifecycle = Lifecycle.Graduated;
        $.graduatedPair[tokenAddress] = lpPair;
        delete $.pendingGraduation[tokenAddress];

        LPLock($.lpLock).recordLock(tokenAddress, lpPair, liquidity);

        emit TokenGraduated(tokenAddress, lpPair, liquidity, p.tokensForLP, p.lpBurned, p.unsoldBurned);
    }

    /// @dev Smallest swap input that drives the pool's reserve ratio
    ///      `(reserveIn + s) / (reserveOut - out)` to `targetN/targetD`
    ///      under the no-fee constant-product model:
    ///        `(reserveIn + s)² = reserveIn * reserveOut * targetN/targetD`
    ///      ⇒ `s = sqrt(reserveIn * reserveOut * targetN/targetD) - reserveIn`,
    ///      capped at `maxSwap`. The actual swap is fee-charging (the pair's
    ///      live fee), so the post-swap ratio drifts from the target by the
    ///      fee; the balanced-subset deposit absorbs the residual without
    ///      donating.
    ///
    ///      `Math.mulDiv` keeps the intermediate product
    ///      `reserveIn * reserveOut * targetN` inside its 512-bit working
    ///      space, but the final result `... / targetD` must still fit in
    ///      uint256. Call sites must keep that invariant — in practice
    ///      both the V2 uint112 reserve cap and the bound that
    ///      `tokensForLP` ≤ `LP_RESERVE` and `ltFromPair` ≤ raised LT
    ///      are well inside the safe envelope. Constructed adversarial
    ///      inputs that violate this would `revert` rather than silently
    ///      truncate, which is the correct failure mode.
    function _noFeeSwapInput(
        uint256 reserveIn,
        uint256 reserveOut,
        uint256 targetN,
        uint256 targetD,
        uint256 maxSwap
    ) internal pure returns (uint256) {
        if (reserveIn == 0 || reserveOut == 0 || targetN == 0 || targetD == 0 || maxSwap == 0) {
            return 0;
        }
        uint256 product = Math.mulDiv(reserveIn * reserveOut, targetN, targetD);
        uint256 newIn = Math.sqrt(product);
        if (newIn <= reserveIn) return 0;
        uint256 s = newIn - reserveIn;
        return s > maxSwap ? maxSwap : s;
    }
