### Title
Primary `exact_amount_out` quote branch in `getFeeQuote` accepts unbounded `amount_in` from a solver, allowing fee overcharge - ([File: packages/intents-sdk/src/lib/estimate-fee.ts])

### Summary
`getFeeQuote`'s primary branch requests a quote with `exact_amount_out: feeAmount` and returns whatever `solverRelay.getQuote` resolves to without any check on `amount_in`. `matchesRequest` in the relay layer only validates that `quote.amount_out === exact_amount_out`; it never bounds `quote.amount_in`, so a solver can charge an arbitrarily large `amount_in` for the fixed `feeAmount` output, and that number is embedded directly as the debit in the `token_diff` intent.

### Finding Description
The claimed equality is: **(value user pays as fee, i.e. `token_diff.amount_in`) == (fee actually owed, `feeAmount`)**. In the exact-out primary path, only `amount_out` is fixed/verified; `amount_in` is left to "solver competition" with no relay-side or SDK-side sanity check.

- `getFeeQuote` sends `exact_amount_out: feeAmount.toString()` and returns the resolved `solverRelay.getQuote` result directly, with no post-hoc check on `amount_in` in the primary branch (unlike the fallback `exact_amount_in` branch, which does compute a 1.5x ratio guard on `amount_out` vs `feeAmount`). [1](#0-0) 
- `matchesRequest` in the relay client only checks token identifiers and, for the exact-out case, `BigInt(quote.amount_out) === BigInt(quoteParams.exact_amount_out)`. It explicitly documents: "Only the side fixed by the request is verified; the other side is what the solver competes on... min amount_in for exact_out." [2](#0-1) 
- `sortQuotes` picks the lowest `amount_in` among *matching* quotes for exact-out — but if only one (attacker-controlled) solver responds, or if all responding solvers are colluding/self-serving, the "lowest" is still the inflated value; there is no absolute ceiling. [3](#0-2) 
- The returned `quote.amount_in` then flows unmodified into `FeeEstimation.amount` and into the `token_diff` intent's debit (`-quote.amount_in`) in every bridge's `createWithdrawalIntents` (omni-bridge, hot-bridge, direct-bridge, aurora-engine-bridge). [4](#0-3) [5](#0-4) [6](#0-5) 

The only partial mitigation found is `FeeExceedsAmountError`, thrown from `sdk.ts`, which compares `feeEstimation.amount` against the user's withdrawal `amount`. This bounds the overcharge only by the size of the withdrawal itself — a solver can still inflate `amount_in` up to just under the full withdrawal amount before this check trips, which still constitutes draining a material (up to ~100%) share of the funds. I was not able to fully verify the exact numeric threshold/comparison logic of `FeeExceedsAmountError` in `sdk.ts` due to incomplete retrieval of that code block in this session, but its existence and reference to `feeEstimation.amount` were confirmed via `grep_search`. This is worth explicit verification (e.g., via a Devin session) if precise bound behavior matters.

### Impact Explanation
The `token_diff` intent debit for the fee-swap leg is directly attacker (solver)-controlled up to the withdrawal amount ceiling enforced elsewhere. Since the user signs the `IntentPrimitive[]` returned by `createWithdrawalIntents` (which embeds `quote.amount_in`), a self-serving/malicious solver can cause the user's signed intent to debit far more than the true `feeAmount` for the same fixed fee-token payout, draining a material share of the withdrawal. This matches the "fee overcharge... draining a material share of the amount" Critical category. It is repeatable on every withdrawal that goes through the primary (non-fallback) exact-out quote path with a malicious/colluding solver willing to answer with an inflated `amount_in`.

### Likelihood Explanation
Preconditions: the withdrawal route must use `getFeeQuote`'s exact-out primary branch (i.e. no `QuoteError` triggering fallback), and a permissionless solver responding to the relay's quote request must offer the highest `amount_in` while other solvers don't undercut it (or there is only one responder, or several colluding solvers). Because the relay itself picks the *minimum* `amount_in` among valid quotes for exact-out, a single attacker-controlled solver cannot force selection of an inflated `amount_in` when honest competing solvers submit tighter quotes — the attack requires either being the sole quoting solver for the pair, or colluding with/being all responding solvers. This lowers likelihood somewhat versus a "always exploitable" bug, but it is not prevented by any SDK-level code; the SDK relies entirely on solver market competition for this constraint, with no ceiling check on `amount_in` for exact-out at all (unlike the fallback exact-in branch's explicit 1.5x ratio guard).

### Recommendation
Add an explicit upper-bound sanity check on the primary exact-out quote's `amount_in` in `getFeeQuote`, similar to the ratio guard already present in the fallback branch, using price-derived expected `amount_in` (with a bounded multiplier, e.g., 1.5x) before returning/accepting the quote, rather than relying solely on relay-side solver competition.

### Proof of Concept
```ts
// packages/intents-sdk/src/lib/estimate-fee.test.ts (new)
import { describe, it, expect, vi } from "vitest";
import * as solverRelay from "@defuse-protocol/internal-utils"; // adjust import path
import { getFeeQuote } from "./estimate-fee";

describe("getFeeQuote exact_amount_out overcharge", () => {
  it("accepts a quote with amount_out==feeAmount but grossly inflated amount_in", async () => {
    const feeAmount = 1_000_000n;
    const maliciousQuote = {
      amount_in: "999999999999999999", // grossly inflated, unrelated to feeAmount
      amount_out: feeAmount.toString(), // exact match required by matchesRequest
      defuse_asset_identifier_in: "nep141:token.near",
      defuse_asset_identifier_out: "nep141:wrap.near",
      expiration_time: "2099-01-01T00:00:00.000Z",
      quote_hash: "attacker-hash",
    };

    // Mock only the HTTP-level quote fetch used inside solverRelay.getQuote
    vi.spyOn(solverRelay, "getQuote").mockResolvedValueOnce(maliciousQuote);

    const result = await getFeeQuote({
      feeAmount,
      feeAssetId: "nep141:wrap.near",
      tokenAssetId: "nep141:token.near",
      envConfig: /* test env config */ {} as any,
    });

    // Left side: fee actually owed
    // Right side: value the user is asked to pay (amount_in charged)
    expect(BigInt(result.amount_out)).toBe(feeAmount); // matchesRequest guarantee holds
    expect(BigInt(result.amount_in)).toBe(
      BigInt(maliciousQuote.amount_in),
    ); // amount_in accepted with NO upper bound relative to feeAmount

    // Downstream: token_diff intent embeds the inflated amount_in as the debit
    // (verified separately in omni-bridge.createWithdrawalIntents / hot-bridge.createWithdrawalIntents,
    // which copy `feeEstimation.quote.amount_in` verbatim into the signed intent diff).
  });
});
```
This demonstrates that the equality `(amount_in charged) == (feeAmount owed)` is not enforced by `getFeeQuote`/`matchesRequest` in the primary exact-out branch — only `amount_out == feeAmount` is guaranteed, while `amount_in` is unconstrained short of the relay's own solver-competition minimum-selection behavior and the caller-side `FeeExceedsAmountError` ceiling equal to the full withdrawal amount.

```typescript
function sortQuotes(
	quotes: Quote[],
	quoteKind: "exact_in" | "exact_out",
): Quote[] {
	return quotes.slice().sort((a, b) => {
		if (quoteKind === "exact_in") {
			// For exact_in, sort by `amount_out` in descending order
			if (BigInt(a.amount_out) > BigInt(b.amount_out)) return -1;
			if (BigInt(a.amount_out) < BigInt(b.amount_out)) return 1;
			return 0;
		}

		// For exact_out, sort by `amount_in` in ascending order
		if (BigInt(a.amount_in) < BigInt(b.amount_in)) return -1;
		if (BigInt(a.amount_in) > BigInt(b.amount_in)) return 1;
		return 0;
	});
}
```

```typescript
function matchesRequest(
	quote: Quote,
	quoteParams: GetQuoteParams["quoteParams"],
): boolean {
	if (
		quote.defuse_asset_identifier_in !==
			quoteParams.defuse_asset_identifier_in ||
		quote.defuse_asset_identifier_out !==
			quoteParams.defuse_asset_identifier_out
	) {
		return false;
	}

	// Only the side fixed by the request is verified; the other side is what the
	// solver competes on (max amount_out for exact_in, min amount_in for
	// exact_out). Compare as BigInt so formatting differences don't matter.
	if (quoteParams.exact_amount_in != null) {
		return BigInt(quote.amount_in) === BigInt(quoteParams.exact_amount_in);
	}
	return BigInt(quote.amount_out) === BigInt(quoteParams.exact_amount_out);
}
```
