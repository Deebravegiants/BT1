### Title
Divergent account-ownership sources let a stale owner or delegate act after NFT transfer - (File: contracts/controller/src/account.rs)

### Summary
The controller maintains two different notions of "who owns an account": the stored `Account.owner` field written at creation, and the position-nft's current `owner_of(token_id)`. Different entrypoints authenticate against different sources — an ambiguity of subject identity analogous to CVE-2021-44533, where a single identifier was interpreted inconsistently between components.

### Finding Description
`create_account` writes `owner` into `Account` at mint time [1](#0-0) . Two authorization paths then disagree on the subject:

- `is_owner_or_delegate` / `require_owner_or_delegate` compare `caller` against the stored `account.owner` and check `get_delegates(env, account_id, owner)` keyed by that stored owner [2](#0-1) .
- `require_account_owner` instead reads `storage::account_owner` (the live NFT owner) [3](#0-2) .

`load_or_create_account` routes `AccountGuard::Migrate` and `AccountGuard::Multiply` through the stored-owner check [4](#0-3) , while ownership-critical paths elsewhere use the NFT-based check. If the account NFT is transferred via the position-nft `transfer`/`approve` entrypoints and `Account.owner` is not resynchronized, the previous owner (or a delegate grant keyed to the previous owner, which `set_account_delegate` stores under `caller`) retains authority on `migrate_from_blend` / `multiply` flows while the NFT holder is treated as owner elsewhere. A stale delegate is worse: `add_delegate` grants are keyed by the grantor address [5](#0-4) , so a delegate approved by the old owner could keep acting on an account the old owner no longer holds.

**Caveat:** I could not fully verify whether the position-nft `transfer` path synchronizes `Account.owner` or clears delegates — the position-nft source was not read in the available iterations. If a hook updates the stored owner on transfer, this collapses to a non-issue; the vulnerability exists only if the two identity sources can diverge, which the code structure permits.

### Impact Explanation
If divergence is reachable, a former owner or their still-authorized delegate can drive `multiply` (which mints debt and swaps collateral) or `migrate_from_blend` against an account whose NFT was sold/transferred — imposing debt on the new owner's collateral, i.e., theft of user funds. Conversely the new NFT owner could be partially locked out of delegate/migrate flows.

### Likelihood Explanation
Reachable by a single unprivileged address: call position-nft `transfer` to move an account NFT, then invoke controller entrypoints that consult the stored owner. Likelihood is gated entirely on whether the transfer path resyncs `Account.owner`/delegates; nothing in the snippets shown performs that resync (`set_account_delegate` and `remove_account_and_burn_nft` are the only owner-touching code seen).

### Recommendation
Use `storage::account_owner` (the NFT owner) as the single identity source everywhere `require_owner_or_delegate` / `is_owner_or_delegate` is called, or update `Account.owner` and clear `get_delegates` entries inside the NFT transfer hook so the two interpretations can never diverge.

### Proof of Concept
1. Alice owns `account_id` with collateral; she delegates to manager M via `add_delegate`.
2. Alice transfers the account NFT to Bob via position-nft `transfer`.
3. If `Account.owner` remains Alice, M calls `multiply`/`migrate_from_blend` with `account_id`: `is_owner_or_delegate` resolves `owner = account.owner = Alice`, finds M in `get_delegates(account_id, Alice)`, and passes — minting debt against Bob's collateral.

```rust
pub(crate) fn is_owner_or_delegate(
    env: &Env,
    account_id: u64,
    caller: &Address,
    owner: &Address,
) -> bool {
    if caller == owner {
        return true;
    }
    let active_manager =
        storage::get_position_manager(env, caller).is_some_and(|config| config.is_active);
    active_manager && storage::get_delegates(env, account_id, owner).contains(caller)
}
```
