Webhook shop-tenant attribution not covered by HMAC, enabling cross-tenant event injection - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating the HMAC over the raw request body only, then trusts the `shop` (and `topic`/`webhook_id`) values taken from HTTP headers — which are never included in the signed content — to attribute the event to a tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop`, `topic`, `api_version`, and `webhook_id` are all read from HTTP headers that are completely outside the HMAC's scope: [2](#0-1) 

`Registry.process` verifies the HMAC using `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` (the body) against the app's shared `api_secret_key`, and then immediately builds `WebhookMetadata` from the unauthenticated `request.shop`/`request.topic`/`request.webhook_id` headers and dispatches it to the app's handler: [3](#0-2) 

The identity binding that is broken is:
`HMAC_valid(secret, raw_body) == true` is treated as proving `shop_header == originating_tenant`, but the equality that is actually verified is only `HMAC(secret, raw_body) == received_hmac`; there is no cryptographic link between the signed body and the `shop`/`topic`/`webhook_id` headers.

Since `api_secret_key` is the app's single, `client_secret`-derived signing key shared across **every** shop that installs the app (not a per-shop secret), any tenant that has legitimately installed the app can obtain a genuinely-signed webhook body from their own store (e.g. by triggering an `orders/create` event). Because the signature covers only the body, that same signed body/HMAC pair remains valid if replayed to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header rewritten to name a different, victim shop that also uses the app. `HmacValidator.validate` will still return `true` (the body/HMAC pair is unchanged and correct), and `Registry.process` will hand the attacker-controlled body to the handler labeled as coming from the victim shop.

### Impact Explanation
This is a cross-tenant confused-deputy condition: an attacker who legitimately controls one tenant (their own install of the app) can inject arbitrary, HMAC-“verified” webhook payloads that the host application will process as belonging to another merchant’s shop. Any host application that uses the trusted `shop` field from `WebhookMetadata` to select which tenant’s data/session to update (the documented and intended usage — see `docs/usage/webhooks.md`, where `data.shop` is used directly as `shop_domain`) will write or act on data under the wrong tenant, i.e., cross-tenant access/data corruption purely from the gem's own webhook processing API, satisfying the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is realistic for any attacker capable of installing the app on a shop they control (a normal, unprivileged flow for any public Shopify app) and capturing/replaying one genuine webhook delivery with a modified `Shop-Domain` header pointed at the endpoint. No `api_secret_key`, access token, or privileged access is required — only a legitimately-obtained, correctly-signed webhook body from the attacker's own install, which is trivial to acquire.

### Recommendation
Bind the tenant-identifying fields (`shop`, `topic`, `webhook_id`) into the HMAC-signable content, or otherwise cryptographically tie the `shop` header to the signed body (e.g., include it as part of the signable string, or cross-check it against a shop known to be currently registered for that specific webhook subscription/`webhook_id`) before constructing `WebhookMetadata` in `Registry.process`.

### Proof of Concept
1. Install the target app on an attacker-owned development store; trigger any subscribed webhook (e.g. `orders/create`) to receive a request with a correct `X-Shopify-Hmac-Sha256` header computed over the raw body using the app's shared `api_secret_key`.
2. Capture the raw body and HMAC header exactly as delivered.
3. Replay the same raw body + HMAC header to the app's webhook endpoint, but change `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`) to the victim shop's domain.
4. `Utils::HmacValidator.validate` in `HmacValidator#validate` still succeeds because it only checks the body against the HMAC (`lib/shopify_api/utils/hmac_validator.rb:26-31`), and `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) dispatches the handler with `shop: request.shop` set to the victim's domain, causing the host app to process attacker data as belonging to the victim tenant.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
