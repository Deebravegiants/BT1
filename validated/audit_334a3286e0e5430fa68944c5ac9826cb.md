## Analysis: Valid analog found

The external report's core bug class — an imprecise/insufficient rebalancing formula that fails to bring a pool to the correct price, especially under extreme skew — maps directly onto alt.fun's HyperSwap V2 LP-seeding rebalance in `Bonding.sol`. The codebase itself explicitly documents and tests this exact residual (labeled "M-02" in comments/tests), confirming the root-cause mapping, though the LP-price-deviation impact itself is not fully closed.

### Title
Budget-capped rebalance swap in `Bonding._seedRebalancing`/`_pairRebalance` permanently seeds the locked HyperSwap LP away from curve-close price under extreme hostile pre-seeds - (File: `packages/contracts/src/Bonding.sol`)

### Summary
`Bonding._pairRebalance` computes the no-fee constant-product swap input needed to bring a pre-seeded HyperSwap V2 pair back to the cached curve-close ratio, but caps it at 99% of the available inventory via `_swapBudget`. For sufficiently lopsided hostile mint pre-seeds, the mathematically required swap exceeds this budget, so the swap only partially corrects the ratio. `_routerDepositAndDispose` then deposits the remaining inventory into the pool at this still-skewed ratio and `LPLock.recordLock` locks the resulting LP permanently, with no withdraw path in v1.

### Finding Description
`_seedRebalancing` branches into `_pairRebalance` when the pre-seed reserves lie above the `DIRECT_MINT_PRESEED_BPS` band on either side [1](#0-0) . `_pairRebalance` uses `_noFeeSwapInput(...)` capped by `maxSwap = _swapBudget(inventory)`, where `_swapBudget` caps the swap at 99% of the available token/LT balance so the subsequent `addLiquidity` call always has non-zero inventory on both sides [2](#0-1) . When the true no-fee-optimal swap needed to reach the curve-close ratio exceeds this budget (an extreme LT-rich or token-rich pre-seed), the cap binds, the swap only partially rebalances the pool, and `_routerDepositAndDispose` deposits the remaining inventory at the still-skewed post-swap ratio into the router's `addLiquidity(min0=1, min1=1, ...)` call [3](#0-2) . The resulting LP tokens are minted to `LPLock`, which has no rescue/withdraw path in v1, per the code's own natspec [4](#0-3) .

This is precisely the bug class in the external report: a rebalancing formula/limit that fails to correctly account for the true price-correction requirement, leaving the pool priced incorrectly relative to its intended peg (here, curve-close price rather than an external oracle peg).

### Impact Explanation
The protocol's own regression test, `test_hostilePreSeed_budgetCappedSwap_isNotProfitable`, constructs exactly this scenario (`reserveToken = tokensForLP/100`, `reserveLt = ltFromPair*200`) and asserts as an "accepted residual" that the pool opens materially off curve-close — the assertion explicitly checks the final pool price is >20% (documented as ~2x) off the intended curve-close ratio [5](#0-4) . While the test proves the *attacker's own* P&L is non-positive (the over-funded side is swept to the protocol owner, and the attacker's residual LP claim, valued at curve-close, is worth less than their deposit) [6](#0-5) , this does not protect the protocol-owned locked LP itself. The LP is permanently minted and locked at a price up to ~2x away from the fair curve-close price. Any third-party arbitrageur (not the original pre-seeder) can immediately trade against the newly-opened, mispriced pool and extract the price-gap value from the LP's reserves — a real and permanent transfer of value out of the protocol's locked liquidity position, which per `LPLock`'s v1 design can never be withdrawn or corrected. This matches the explicitly accepted impact category "an LP seeded away from the curve close price."

### Likelihood Explanation
Fully reachable by any unprivileged wallet: `factory.createPair` is permissionless, and an attacker can `transfer` an extremely lopsided token/LT ratio to the pair and call `pair.mint(attacker)` before `finalizeGraduation` runs, exactly as the existing hostile-pre-seed test suite already exercises. No special privilege, timing race beyond front-running phase 2, or unusual capital is required — a cheap, deliberately skewed dust-scale deposit is sufficient to make the required correction swap exceed the 99%-of-inventory budget cap. The codebase's own test explicitly reproduces and names this regime ("M-02"), confirming the condition is realistically triggerable, not a theoretical edge case.

### Recommendation
Reconsider the fixed 99%-of-inventory swap budget cap. Options include: (a) scaling `maxSwap` dynamically based on how far off-ratio the pre-seed is so more of the correction can be executed while still guaranteeing a non-zero deposit remainder, (b) iterating/splitting the rebalance across multiple bounded swaps rather than a single capped swap, or (c) enforcing a maximum acceptable price-deviation threshold post-rebalance and reverting/queueing remediation (e.g., a follow-up permissionless "top-up rebalance" call) rather than unconditionally proceeding to lock LP at a materially off-ratio price. At minimum, document and monitor this residual as a live economic risk to locked LP value, not merely an attacker-profitability question.

### Proof of Concept
Directly reproducible via the existing repository test `test_hostilePreSeed_budgetCappedSwap_isNotProfitable` [7](#0-6) :
1. Launch and graduate-trigger a token so `_enterGraduating` caches `tokensForLP` / `ltFromPair`.
2. Front-run `finalizeGraduation`: `factory.createPair(token, lt)`, `transfer(pair, tokensForLP/100)` token, `transfer(pair, ltFromPair*200)` LT, `pair.mint(attacker)`.
3. Call `finalizeGraduation(token)` (permissionless). `_pairRebalance`'s swap is capped at 99% of `tokensForLP` and cannot fully correct the 200x LT-rich skew.
4. Resulting pool price is >20% (up to ~2x) off curve-close, and this LP is permanently locked in `LPLock` with no v1 withdraw path.

    /// @dev Cap the rebalance swap at 99% of the available side's budget,
    ///      so the subsequent `addLiquidity` always has a non-zero amount
    ///      of BOTH sides to deposit. Without this, an extreme hostile
    ///      pre-seed (massively imbalanced reserves) drives the
    ///      unconstrained `_noFeeSwapInput` past our per-side budget,
    ///      `_pairRebalance` clamps to the full budget, and the swap
    ///      consumes 100% of one side. `_routerDepositAndDispose` then
    ///      skips `addLiquidity` (`remToken == 0` or `remLT == 0`),
    ///      `finalizeGraduation` returns `liquidity = 0`, and
    ///      `LPLock.recordLock(...)` records a zero-sized lock — the
    ///      attacker's pre-existing LP becomes 100% of the pool. Reserving
    ///      1% guarantees the deposit leg always lands AND mints non-zero
    ///      LP at the post-swap ratio. The 1% comes off the swap, not the
    ///      deposit — for any realistic pre-seed `s_unconstrained` is
    ///      orders of magnitude below `maxSwap`, so the cap doesn't bind
    ///      and behaviour is unchanged. It only kicks in for catastrophic
    ///      pre-seeds beyond our budget capacity, where the alternative
    ///      is bricking.
    function _swapBudget(
        uint256 budget
    ) internal pure returns (uint256) {
        return (budget * 99) / 100;
    }

    function test_hostilePreSeed_budgetCappedSwap_isNotProfitable() public {
        (address tokenAddr,) = _launchToken();
        _enterGraduating(tokenAddr);

        (uint256 tokensForLP, uint256 ltFromPair,,) = bonding.pendingGraduation(tokenAddr);

        // Extreme LT-rich shape: TOKEN side at 1% of target, LT side at 200x.
        // The optimal TOKEN-in swap to reach the cached ratio is ~1.4x
        // `tokensForLP`, so the 99%-of-`tokensForLP` budget cap binds and the
        // pool stays ~2x off curve-close after the swap.
        uint256 reserveToken = tokensForLP / 100;
        uint256 reserveLt = ltFromPair * 200;

        // M-02 precondition: the optimal swap exceeds the budget (this is the
        // budget-capped regime, distinct from the swap-rounds-to-zero fallback
        // covered by the dust tests above).
        assertGt(
            _noFeeSwapInputUncapped(reserveToken, reserveLt, tokensForLP, ltFromPair),
            (tokensForLP * 99) / 100,
            "setup: optimal rebalance swap must exceed the per-side budget (M-02 regime)"
        );

        deal(tokenAddr, griefer, reserveToken);
        address hyperPair = _grieferMintPreSeed(tokenAddr, reserveToken, reserveLt);
        uint256 grieferLp = MockHyperswapPair(hyperPair).balanceOf(griefer);
        uint256 ownerLtBefore = lt.balanceOf(bonding.owner());

        bonding.finalizeGraduation(tokenAddr);
        assertTrue(bonding.isGraduated(tokenAddr), "finalize must succeed despite an unrecoverable pre-seed");

        // The accepted residual: no bounded swap can correct a 200x LT-rich
        // pre-seed, so the pool opens materially off curve-close.
        assertGt(
            _poolPriceLtPerToken(hyperPair, tokenAddr),
            (((ltFromPair * 1e18) / tokensForLP) * 12) / 10,
            "M-02 regime: pool opens materially off curve-close"
        );

        // The over-funded LT side is arbed out by the rebalance swap and swept
        // to the owner — the pre-seeder cannot recover it.
        assertGt(
            lt.balanceOf(bonding.owner()) - ownerLtBefore,
            reserveLt / 2,
            "the over-funded LT side must be confiscated to the owner"
        );

        // P&L: the pre-seeder's residual LP, valued at the fair (curve-close)
        // price, is worth a fraction of what they deposited — the attack is
        // cost-negative.
        uint256 claimValue = _lpValueAtCurveClose(hyperPair, tokenAddr, grieferLp, tokensForLP, ltFromPair);
        uint256 depositValue = _depositValueAtCurveClose(reserveToken, reserveLt, tokensForLP, ltFromPair);
        assertLe(claimValue, depositValue, "pre-seeder must not profit (P&L <= 0)");
        assertLt(claimValue * 2, depositValue, "pre-seeder must lose materially, not merely break even");
    }
