## Analysis Result [1](#0-0) 

The same vulnerability class (reward-per-token integer-division truncation triggered by attacker-controlled, permissionless "update" calls) has a valid analog in `pallet-asset-rewards`.

### Title
Permissionless frequent `stake`/`unstake` calls truncate `reward_per_token` to zero via low-precision integer division - (File: `substrate/frame/asset-rewards/src/lib.rs`)

### Summary
`pallet-asset-rewards` implements a generic Synthetix-style staking-rewards pool where any account can call the permissionless `stake` or `unstake` extrinsics, both of which trigger a pool-wide reward-per-token recalculation via `update_pool_and_staker_rewards`. That calculation uses a fixed, small `PRECISION_SCALING_FACTOR` of `4096` (2^12) rather than a large fixed-point base like `1e18`, and performs `ensure_div` truncating integer division. Exactly like the Kwenta `StakingRewardsV2` bug, if the interval between updates is kept small enough (by spamming `stake`/`unstake`), the per-call reward increment rounds down to zero and is permanently lost — because `reward_rate_per_block * blocks_elapsed * PRECISION_SCALING_FACTOR` can be smaller than `total_tokens_staked`.

### Finding Description
`reward_per_token` computes:
```
reward_per_token_stored + reward_rate_per_block * blocks_elapsed * PRECISION_SCALING_FACTOR / total_tokens_staked
``` [2](#0-1) 

`PRECISION_SCALING_FACTOR` is only `4096`, far lower precision than the `1e18` scaling Kwenta's fix (and Substrate's own `pallet-nomination-pools`, which uses `FixedU128` with `10^18` base) uses to guard against this exact rounding-to-zero problem. [3](#0-2) 

Both `stake` and `unstake` are permissionless (`ensure_signed`), and both unconditionally call `update_pool_and_staker_rewards` before mutating balances — meaning any account, including one staking a trivial/minimal amount, can force the pool's `reward_per_token_stored` to be recomputed on every block: [4](#0-3) [5](#0-4) 

If an attacker calls `stake` (or `unstake`) every block, `rewardable_blocks_elapsed` is always `1`, so the increment each time is:
```
reward_rate_per_block * 1 * 4096 / total_tokens_staked
```
Whenever `reward_rate_per_block * 4096 < total_tokens_staked`, `ensure_div` truncates this to `0` every single block, permanently. The lost portion is not recovered elsewhere — `derive_rewards` only ever adds `reward_per_token_stored` deltas to a staker's `rewards`, with no dust-tracking mechanism: [6](#0-5) 

This is structurally the same root cause as the Kwenta finding: a reward-per-token accumulator using low-precision scaling combined with attacker-triggerable frequent updates causes permanent zeroing of rewards instead of temporary rounding dust.

### Impact Explanation
All stakers in an affected pool (any pool where `reward_rate_per_block * PRECISION_SCALING_FACTOR` is small relative to `total_tokens_staked` — plausible for pools pairing a low-decimal/low-rate reward asset against a large amount of staked tokens) permanently lose their share of rewards for every block the attack is sustained. Reward tokens remain stuck in the pool account and can only be recovered by the pool admin via `cleanup_pool`, which additionally requires the pool to have zero stakers — meaning legitimate stakers cannot retrieve the lost rewards themselves. [7](#0-6) 

### Likelihood Explanation
Any signed account can call `stake`/`unstake` with no minimum-amount restriction and no rate limiting beyond normal transaction fees, so the attack is fully permissionless and repeatable every block, matching the Kwenta PoC pattern. Because `PRECISION_SCALING_FACTOR` (4096) is drastically smaller than the `1e18` precision used elsewhere in the runtime (e.g., `pallet-nomination-pools`'s `FixedU128` reward counter), the threshold at which truncation occurs is reached far more easily here, making this pallet's design more susceptible than the fixed Kwenta contract or Substrate's own nomination-pools reward accounting.

### Recommendation
Increase `PRECISION_SCALING_FACTOR` to a much larger fixed-point base (e.g. `FixedU128`-style `10^18`, as used in `pallet-nomination-pools`'s `current_reward_counter`) so that per-block increments do not truncate to zero under realistic `reward_rate_per_block`/`total_tokens_staked` ratios, and/or accumulate/store fractional remainder dust across updates so no reward is permanently lost regardless of update frequency.

### Proof of Concept
1. Admin creates a pool via `create_pool` with `reward_asset_id` set to a low-decimal reward token and a `reward_rate_per_block` such that `reward_rate_per_block * 4096 < total_tokens_staked` once enough is staked (analogous to Kwenta's USDC-vs-KWENTA decimal mismatch).
2. A legitimate staker stakes a large amount via `stake`, establishing `total_tokens_staked` high enough to satisfy the inequality above.
3. An attacker (any signed account already having a stake, even a minimal one) calls `stake(pool_id, 0)` or `unstake(pool_id, 0, None)` (or stakes/unstakes trivial dust amounts) every block.
4. Each call invokes `update_pool_and_staker_rewards` → `reward_per_token`, where `blocks_elapsed == 1` each time, causing `reward_rate_per_block * 1 * 4096 / total_tokens_staked` to evaluate to `0` via integer truncation in `ensure_div`.
5. `reward_per_token_stored` never advances; all legitimate stakers accrue `0` rewards for the duration of the attack, exactly mirroring the `test_rewardPerTokenUSDC` scenario in the Kwenta report. [8](#0-7)

		pub fn unstake(
			origin: OriginFor<T>,
			pool_id: PoolId,
			amount: T::Balance,
			staker: Option<T::AccountId>,
		) -> DispatchResult {
			let caller = ensure_signed(origin)?;
			let staker = staker.unwrap_or(caller.clone());

			// Always start by updating the pool rewards.
			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			let now = T::BlockNumberProvider::current_block_number();
			ensure!(now > pool_info.expiry_block || caller == staker, BadOrigin);

			let staker_info = PoolStakers::<T>::get(pool_id, &staker).unwrap_or_default();
			let (mut pool_info, mut staker_info) =
				Self::update_pool_and_staker_rewards(&pool_info, &staker_info)?;

			// Check the staker has enough staked tokens.
			ensure!(staker_info.amount >= amount, Error::<T>::NotEnoughTokens);

			// Unfreeze staker assets.
			T::AssetsFreezer::decrease_frozen(
				pool_info.staked_asset_id.clone(),
				&FreezeReason::Staked.into(),
				&staker,
				amount,
			)?;

			// Update Pools.
			pool_info.total_tokens_staked.ensure_sub_assign(amount)?;
			Pools::<T>::insert(pool_id, pool_info);

			// Update PoolStakers.
			staker_info.amount.ensure_sub_assign(amount)?;

			if staker_info.amount.is_zero() && staker_info.rewards.is_zero() {
				PoolStakers::<T>::remove(&pool_id, &staker);
			} else {
				PoolStakers::<T>::insert(&pool_id, &staker, staker_info);
			}

			// Emit event.
			Self::deposit_event(Event::Unstaked { caller, staker, pool_id, amount });

			Ok(())
		}

		#[pallet::call_index(8)]
		pub fn cleanup_pool(origin: OriginFor<T>, pool_id: PoolId) -> DispatchResult {
			let who = ensure_signed(origin)?;

			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			ensure!(pool_info.admin == who, BadOrigin);

			let stakers = PoolStakers::<T>::iter_key_prefix(pool_id).next();
			ensure!(stakers.is_none(), Error::<T>::NonEmptyPool);

			let pool_balance = T::Assets::reducible_balance(
				pool_info.reward_asset_id.clone(),
				&pool_info.account,
				Preservation::Expendable,
				Fortitude::Polite,
			);
			T::Assets::transfer(
				pool_info.reward_asset_id,
				&pool_info.account,
				&pool_info.admin,
				pool_balance,
				Preservation::Expendable,
			)?;

			if let Some((who, cost)) = PoolCost::<T>::take(pool_id) {
				T::Consideration::drop(cost, &who)?;
			}

			Pools::<T>::remove(pool_id);

			Self::deposit_event(Event::PoolCleanedUp { pool_id });

			Ok(())
		}

			return Ok((pool_info, new_staker_info));

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}
