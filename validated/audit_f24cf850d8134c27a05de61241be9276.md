### Title
Permanent freezing of escrowed native ETH when a beneficiary/order-user contract has no payable fallback - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._withdraw`, and the equivalent inline logic in `IntrinsicIntents._fillSameChain` / the Tron `IntentGatewayV2.withdraw`, release escrowed native ETH with a raw `call{value: amount}("")` and unconditionally `revert` if that call fails. Because the beneficiary address is embedded, immutable data inside the order/commitment (it cannot be changed after order placement), a beneficiary that is a contract without a payable `receive`/`fallback` permanently blocks that escrow's release path, with no alternative recovery mechanism for the escrowed funds.

### Finding Description
`_withdraw` transfers escrowed native ETH via `_sendValue`, which reverts the whole request-handling call on failure: [1](#0-0) 

`_withdraw` is reached from three flows that all encode the beneficiary at order-creation/fill time and never allow it to be substituted later:
- `_cancelSameChain` (same-chain refund to `order.user`): [2](#0-1) 
- `_cancelFromDest` (cross-chain refund to `order.user`, dispatched via ISMP `RefundEscrow`): [3](#0-2) 
- `onAccept` invoking `_withdraw` for `RedeemEscrow`/`RefundEscrow`: [4](#0-3) 

The actual token release, with the same non-recoverable pattern, is in `_withdraw`: [5](#0-4) 

Same-chain fills use an inline copy of the same unconditional-revert pattern: [6](#0-5) 

The Tron variant of the gateway has an identical structural issue: [7](#0-6) 

Once `order.user` (chosen at `placeOrder` time and hashed into the order `commitment`) is a contract with no payable fallback, every code path that would release its escrowed native ETH — same-chain cancel, cross-chain refund via `RefundEscrow`, and cross-chain redemption via `RedeemEscrow` where a solver sets `beneficiary` — reverts. There is no admin/governance sweep for a specific order's escrow (the only sweep, `SweepDust`, only moves protocol-owned dust collected via `_splitSurplus`/`DustCollected`, not a user's escrowed input tokens), and the order's beneficiary field cannot be updated post-creation. The escrowed ETH is therefore permanently locked in the gateway contract.

### Impact Explanation
This is a permanent freezing-of-funds bug: any order that escrows native ETH (`token == address(0)` in `order.inputs`) and whose `order.user` (or, for a filled cross-chain order, the solver-designated `beneficiary` in the `RedeemEscrow` request) is a contract without a receive/fallback function can never have its escrow released — not on cancellation, not on fill, and not through any privileged recovery path in the contract. Meets the Medium bar for concrete permanent freezing of funds.

### Likelihood Explanation
Reachable via ordinary, unprivileged usage: any account can call `placeOrder`/`cancelOrder` on `IntentGatewayV2` with a smart-contract address (e.g., a multisig, proxy, or vault without a payable fallback) as `order.user`/beneficiary, and any solver can set a non-payable contract as the fill `msg.sender`/beneficiary in a cross-chain redemption. No relayer, governance, or admin action is required to trigger the freeze — a single `placeOrder` + `cancelOrder`/`fillOrder` sequence suffices.

### Recommendation
Do not let a failed native-ETH push permanently strand escrowed funds. Options:
- On `_sendValue` failure, fall back to a pull-based withdrawal (credit an internal balance the beneficiary/anyone can later claim) instead of reverting the whole request.
- Wrap native ETH into the host's WETH and deliver it as an ERC-20 transfer on failure (the pattern already used for send/refund paths in `WrappedHyperFungibleTokenUpgradeable.onAccept`/`onPostRequestTimeout`, e.g. lines 338-350 and 373-384), so a non-payable beneficiary still receives a claimable asset.

### Proof of Concept
1. Deploy a beneficiary contract `Bad` with no `receive()`/`fallback()`.
2. Call `IntentGatewayV2.placeOrder` with `order.user = address(Bad)` (or, for a same-chain order, `order.output.beneficiary` irrelevant here — use `Bad` as `order.user`) and `order.inputs` containing a native-ETH `TokenInfo` (`token == bytes32(0)`), sending the ETH with the call.
3. After `order.deadline` passes with no fill, call `cancelOrder` (same-chain path hits `_cancelSameChain` → `_withdraw`; cross-chain path hits `_cancelFromDest` → `RefundEscrow` → `onAccept` → `_withdraw`).
4. `_withdraw`'s `_sendValue(beneficiary, amount)` (`IntentsBase.sol:466`) attempts `Bad.call{value: amount}("")`, which fails and reverts with `InsufficientNativeToken`.
5. Every subsequent retry of the same commitment produces the identical revert — the escrowed ETH is permanently stuck in the gateway with no alternative code path to extract it.

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }
