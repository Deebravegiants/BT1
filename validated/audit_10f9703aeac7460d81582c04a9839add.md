## Analysis

The keeper-gauge bug's root cause — a governance action that swaps out a component reference while it is still relied upon by in-flight, unprivileged-user-initiated messages, with no on-chain check and no recovery path — maps to `pallet-bandwidth`'s manager-rotation flow.

### Title
Bandwidth-purchase fee tokens are permanently stranded when governance rotates `BandwidthManager` mid-flight - (File: `evm/src/apps/BandwidthManager.sol`, `modules/pallets/bandwidth/src/lib.rs`)

### Summary
A bandwidth purchaser calls `BandwidthManager.purchase()`, which immediately pulls the fee token into the manager contract and dispatches a POST request to `pallet-bandwidth` naming that manager as `request.from`. If governance calls `set_manager` to rotate the registered manager for that source chain before the request is delivered, `pallet-bandwidth`'s `on_accept` will permanently reject the message because `request.from` no longer matches the (now different) registered manager. The buyer's fee tokens are left in the old, now-orphaned `BandwidthManager` contract with no code path to move them out.

### Finding Description
`BandwidthManager.purchase()` transfers the fee token into itself and dispatches the purchase message before any confirmation that the message will actually be honored: [1](#0-0) 

On the pallet side, `on_accept` authenticates inbound purchases solely by checking that `request.from` equals the manager address currently stored in `BandwidthManager::<T>` for that source chain, returning `UnauthorizedManager` otherwise: [2](#0-1) 

`set_manager` allows unconditional overwrite of that registration with no check for in-flight purchases: [3](#0-2) 

The documentation itself confirms the race is expected to occur and that it fails silently: *"Overwriting an existing registration is allowed (useful for redeployments); in-flight purchases from the old contract will fail after the swap."* [4](#0-3) 

Unlike the keeper-gauge case, where the delivery could eventually succeed once governance repointed `TopUpActionFeeHandler`, here the failure is **permanent by construction**: `request.from` is baked into the already-dispatched request and can never again equal the currently registered manager once rotation has happened. `BandwidthManager.sol` exposes no owner-only emergency withdrawal — the only fund-exit path is `onAccept`, gated by `onlyHost` and reachable only via a `Withdraw` governance message that the pallet addresses to `BandwidthManager::<T>::get(target)` (the *current* manager), never the orphaned old one: [5](#0-4) [6](#0-5) 

Because the ISMP router deletes the request receipt on a failed `on_accept` (making the message notionally "retryable"), a relayer can resubmit — but resubmission is futile since `request.from` never changes and the registered manager never reverts back: [7](#0-6) 

### Impact Explanation
Fee tokens paid by an unprivileged bandwidth purchaser become permanently frozen in an orphaned contract with no on-chain recovery mechanism, satisfying the "permanent freezing of funds" bar. This directly parallels the keeper-gauge finding: a routine, non-malicious governance action (rotating/redeploying a downstream component) silently and irreversibly strands user funds because the protocol never checks whether the outgoing component still has messages in flight before the swap takes effect.

### Likelihood Explanation
`set_manager` overwrite is explicitly documented as the supported redeployment procedure ("useful for redeployments"), so it is expected to be exercised in normal chain operations. Any buyer whose `purchase()` transaction is pending (mempool delay, block reorg, or slow relayer delivery) at the moment of a redeployment is affected — no attacker coordination is required, only ordinary transaction-propagation timing on a live, purchasable chain.

### Recommendation
Before allowing `set_manager` to overwrite an existing registration, either (a) require draining/pausing the old manager and confirming no purchase is in flight (e.g., a timelock plus an explicit sweep of the old manager's balance back to buyers or treasury), or (b) have `pallet-bandwidth` retain the previous manager address for a grace/challenge window and accept purchases from either the current or the immediately-prior manager during that window, refunding rather than silently discarding requests that fail authentication. Additionally, give `BandwidthManager.sol` an owner-gated (or governance-gated via a dedicated `Withdraw`-style message addressed by contract address rather than by current-registration lookup) emergency recovery function so orphaned balances are not unconditionally unrecoverable.

### Proof of Concept
1. Buyer calls `BandwidthManager.purchase()` on chain A; the manager (`address M1`) pulls the fee token and dispatches a `BandwidthPurchaseMsg` with `request.from = M1` to `pallet-bandwidth` (evm/src/apps/BandwidthManager.sol:153-188).
2. Before a relayer delivers the request, governance calls `set_manager(source=A, manager=M2)` to redeploy the storefront (modules/pallets/bandwidth/src/lib.rs:216-225).
3. Relayer delivers the purchase request; `on_accept` compares `request.from (M1)` against `BandwidthManager::<T>::get(A) (M2)`, they differ, and the pallet returns `UnauthorizedManager` (modules/pallets/bandwidth/src/lib.rs:192-196).
4. The request receipt is deleted, so the message can be resubmitted, but `request.from` is immutably `M1` and `BandwidthManager::<T>::get(A)` will never again equal `M1` post-rotation — delivery can never succeed.
5. The buyer's fee tokens remain locked in `M1`. `M1` has no owner-only withdrawal function, and the pallet's `dispatch_withdraw` can only target the currently registered manager (`M2`), never `M1`, so the funds are permanently stranded.

        external
        returns (bytes32 commitment)
    {
        if (app.length == 0 || app.length > MAX_APP_LENGTH || chain.length == 0 || months == 0) {
            revert InvalidPurchase();
        }
        uint256 price18d = tierPrice[tier];
        if (price18d == 0) revert UnknownTier();

        uint256 total18d = price18d * months;
        address feeToken = IDispatcher(_host).feeToken();
        uint8 dec = IERC20Metadata(feeToken).decimals();
        uint256 scale = 10 ** (18 - dec);
        if (total18d % scale != 0) revert PriceNotRepresentable();
        uint256 amount = total18d / scale;

        IERC20(feeToken).safeTransferFrom(msg.sender, address(this), amount);

            app: app,
            tier: tier,
            months: months,
            chain: chain
        });

                dest: IDispatcher(_host).hyperbridge(),
                to: PALLET_BANDWIDTH_MODULE_ID,
                body: abi.encode(body),
                timeout: 0,
                fee: 0,
                payer: address(this)
            })
        );

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        PostRequest calldata request = incoming.request;

        if (!request.source.equals(IDispatcher(_host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.SetTiers) {
            Tier[] memory updates = abi.decode(request.body[1:], (Tier[]));
            for (uint256 i = 0; i < updates.length; i++) {
                tierPrice[updates[i].tier] = updates[i].price;
                emit TierSet(updates[i].tier, updates[i].price);
            }
        } else if (action == OnAcceptActions.Withdraw) {
            Withdrawal memory w = abi.decode(request.body[1:], (Withdrawal));
            if (w.token != address(0)) {
                IERC20(w.token).safeTransfer(w.beneficiary, w.amount);
            } else {
                (bool sent,) = w.beneficiary.call{value: w.amount}("");
                if (!sent) revert InsufficientNativeToken();
            }
            emit Withdrawn(w.token, w.beneficiary, w.amount);
        } else {
            revert UnauthorizedAction();
        }
    }
