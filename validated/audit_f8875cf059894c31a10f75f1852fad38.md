### Title
Webhook shop/topic identity headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing via signature replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes/exposes the HMAC-verifiable bytes as only the raw request body, while the shop identity (`shop-domain`), `topic`, `api-version`, and `webhook-id` are read straight from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` accepts any request whose body HMAC validates, then dispatches to the handler using `request.shop` taken from the header — a value the HMAC never protected.

`VerifiableQuery#to_signable_string` for a webhook request is defined as: [2](#0-1) 

This means the HMAC covers `@raw_body` only. Meanwhile, the shop, topic, webhook id, and API version are all pulled from headers that are never part of the signed bytes: [3](#0-2) 

`Registry.process` validates the HMAC and then trusts `request.shop`/`request.topic` (unauthenticated header values) to build the metadata handed to the app's webhook handler: [4](#0-3) 

This is exactly the class of bug in the external report: a field the code *acts on* (`shop`, used as the tenant/session key for the handler) is not bound by the cryptographic check (HMAC only covers `raw_body`). The equality that should hold — `hmac-authenticated shop == shop the handler processes` — does not, because the "shop" side of that equality is read from a header the HMAC never touches.

Because the HMAC is computed only from the JSON body, any actor who has ever legitimately received one webhook delivery (e.g., by installing the app on their own store and capturing a real `(raw_body, hmac)` pair for a generic/empty-body topic) can replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary victim `x-shopify-shop-domain` (and `x-shopify-topic`) header. `HmacValidator.validate` will still succeed because it only re-derives the signature over `raw_body`, which is unchanged. `Registry.process` will then invoke the registered handler with `WebhookMetadata` claiming the victim shop, per: [5](#0-4) 

Any app that uses `data.shop` from the handled webhook to select which merchant's session/data to act on (the intended and documented use of this field) will act on behalf of a different, victim tenant using attacker-controlled/replayed content.

### Impact Explanation
This breaks the tenant binding between the cryptographically authenticated bytes (body) and the identity value the library hands to the app (shop). An attacker who is merely an unprivileged (but real) merchant using the same app can forge webhook deliveries that are accepted as authentic for a shop they do not control, letting them inject/replay data attributed to an arbitrary other tenant into the host app's webhook handling pipeline. This is a cross-tenant access vector consistent with the "Critical - cross-tenant access" impact bucket, since it requires no access token, no `api_secret_key`, and no interception of Shopify's own traffic — only reuse of a webhook payload the attacker legitimately received once.

### Likelihood Explanation
Likelihood is moderate-to-high for any internet-reachable webhook endpoint: the attacker needs only (1) to install the target app on their own store to legitimately receive one webhook with a benign/predictable body (many Shopify webhook topics have very small or template-like bodies), and (2) knowledge of the app's public webhook URL, which is required to exist for the app to function at all. No secret material, TLS interception, or privileged access is required — only an unprivileged, arms-length HTTP replay with a modified header.

### Recommendation
Bind the shop identity (and ideally topic) into what is HMAC-verified rather than trusting header values that ride outside the signature. Practically:
- Do not use `request.shop`/`request.topic` from headers as the sole tenant key for downstream processing without independently confirming the shop against the session/store the app already has on file for the delivery, and/or
- Include the relevant headers (`shop-domain`, `topic`, `webhook-id`) in the signable string used for verification (this would require a corresponding change in how the signature is computed/verified, consistent with how Shopify signs deliveries), and/or
- At minimum, document prominently that `WebhookMetadata#shop`/`#topic` are NOT covered by HMAC verification, and require host applications to treat webhook idempotency/tenant binding via the `webhook_id` plus a freshness/replay check, rather than trusting the header-derived `shop`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and receives (via their own publicly reachable webhook endpoint clone, or by simply observing wire traffic to their own server) one legitimate webhook delivery for a topic with a static/predictable body, e.g. `{}` or a template payload, along with its `x-shopify-hmac-sha256` header — this `(raw_body, hmac)` pair is valid under the app's `api_secret_key` for that exact body.
2. Attacker sends a POST to the app's webhook endpoint with the same `raw_body` and the same `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim.myshopify.com` (and optionally a topic of their choosing that the app has registered a handler for with a compatible body shape).
3. `ShopifyAPI::Utils::HmacValidator.validate` recomputes the HMAC over `@raw_body` only (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`) — it matches, so the request is accepted.
4. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the app's handler with `shop: request.shop`, i.e. `"victim.myshopify.com"`, even though nothing about that value was authenticated — resulting in the app processing attacker-supplied data as if `victim.myshopify.com` initiated it.
