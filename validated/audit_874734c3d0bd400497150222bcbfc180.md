### Title
Webhook HMAC does not authenticate the `shop`, `topic`, or `webhook_id` fields, enabling cross-tenant webhook spoofing/replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC verification performed in `Registry.process` proves only that the *body bytes* were signed with the app secret — it says nothing about which shop, topic, or webhook id that signed body is associated with. `Registry.process` nonetheless trusts the unauthenticated `shop`, `topic`, and `webhook_id` header values to route and label the event to a handler.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 

`to_signable_string` returns `@raw_body` only. `shop`, `topic`, and `webhook_id` are read straight from HTTP headers with no cryptographic binding to the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `to_signable_string` (i.e. `@raw_body`): [3](#0-2) 

`Registry.process` uses this HMAC check as the sole authentication gate, then immediately trusts the unauthenticated header-derived `request.shop` and `request.topic` to dispatch to a handler and construct `WebhookMetadata`: [4](#0-3) 

The identity binding that should hold is:
`HMAC-verified(raw_body) == HMAC-verified(raw_body, shop, topic, webhook_id)`

but the actual behavior is:
`HMAC-verified(raw_body) ⇒ trusted(shop, topic, webhook_id)` — i.e., the shop/topic/webhook_id are accepted with no proof they were ever signed alongside that body.

Because only the body is signed, any two requests with the same body and a validly-signed HMAC (for the same shared app secret) will pass verification regardless of what `shop-domain`, `topic`, or `webhook-id` header values accompany them. An entity that has legitimately received one authentic webhook (e.g., a merchant who has installed the app on their own store, which is an unprivileged, self-service action) can capture a `(raw_body, hmac)` pair from their own genuine webhook delivery and replay it to the app's public webhook endpoint with a different `shop-domain` header (naming a victim shop) and/or a different `topic` header. `Registry.process` will accept the HMAC (it only checks the body) and hand the handler a `WebhookMetadata` claiming the event belongs to the victim shop/topic, even though the body content is really the attacker's own data.

### Impact Explanation
This breaks the tenant boundary the webhook subsystem is supposed to enforce: an app that uses `data.shop` from `WebhookMetadata` to select which merchant's record to update (the intended and documented use of this API) can be tricked into applying attacker-supplied body content to another shop's account, or into invoking a different handler than the one the payload was actually signed for by mislabeling `topic`. This is a cross-tenant access primitive (High/Critical depending on what handlers do with `data.shop`/`data.body`), achieved without possessing the app's `client_secret`, an access token, or any elevated privilege — only the ability to install the app on one's own store and send arbitrary HTTP requests to the app's public webhook endpoint.

### Likelihood Explanation
Likelihood is moderate-to-high in any app that: (1) allows self-service installation (standard for public/embedded Shopify apps), and (2) exposes a webhook endpoint reachable from the internet (required for Shopify webhooks). Obtaining one legitimate `(body, hmac)` pair only requires triggering an event on one's own installed shop and observing the outgoing webhook request (e.g., via a debug proxy the attacker controls in front of their own endpoint, or logs in their own infrastructure). No secret material is needed.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` cryptographically to the signed content, or otherwise authenticate them independently of headers — e.g., include the canonicalized header values in `to_signable_string` (if compatible with Shopify's signing scheme), or cross-check `shop`/`topic` against server-side webhook registration state (the subscription id returned by Shopify at registration time) before dispatching to a handler, rather than trusting the caller-supplied headers as-is.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers an event (e.g., `orders/create`) to receive one legitimate webhook delivery: headers include `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, and body `B`.
2. Attacker replays the exact same body `B` and HMAC `H` to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`).
3. `Utils::HmacValidator.validate` recomputes HMAC over `B` only and it matches `H`, so validation passes: [5](#0-4) 
4. `Registry.process` dispatches the handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, causing the app to process attacker-controlled data under the victim shop's identity: [6](#0-5)

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
