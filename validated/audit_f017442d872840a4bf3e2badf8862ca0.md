### Title
Empty BEEFY commitment payload causes an unconditional panic during untrusted proof conversion - ([File: evm/rust/src/conversions.rs])

### Summary
The `From<Commitment> for SpCommitment` conversion in `evm/rust/src/conversions.rs` unconditionally calls `.expect()` on the first element of an attacker-controlled `payload` vector when reconstructing a BEEFY `Commitment` from ABI-decoded proof data. A commitment with a zero-length `payload` array — a structurally valid Solidity ABI encoding — causes an unrecoverable Rust panic instead of a typed verification error.

### Finding Description
`evm/rust/src/conversions.rs` defines the conversion used to turn the Solidity-ABI `Commitment` struct (submitted as part of a BEEFY/SP1 relay-chain proof) into the Substrate `sp_consensus_beefy::Commitment` type consumed by the consensus verifier: [1](#0-0) 

```rust
fn from(value: Commitment) -> Self {
    let mut iter = value.payload.into_iter();
    let first = iter.next().expect("commitment has at least one payload entry");
    ...
```

`value.payload` is a Solidity dynamic array (`Payload[]`) decoded straight from calldata supplied by whoever submits the proof — a relayer, prover, or any account calling `submit_proof` (see `modules/pallets/beefy-consensus-proofs/src/lib.rs`, which is the on-chain entry point that ultimately builds this `RelayChainProof`/`Commitment` structure)  and `evm/rust/src/conversions.rs` lines 368-389, where `RelayChainProof::into::<MmrProof>()` drives `value.signedCommitment.commitment.into()` into this same conversion [2](#0-1) . An empty `Payload[]` array is a perfectly valid ABI encoding (dynamic array of length 0), so it passes ABI decoding cleanly — the existing regression test only checks that a *malformed* (non-decodable) proof is rejected with `AbiDecodeFailed` [3](#0-2) , not that a well-formed-but-empty payload is rejected.

This mirrors the CVE-2023-1945 bug class: "unexpected data" that is syntactically well-formed but semantically unexpected triggers a crash in code that assumed a data invariant (there, memory corruption in a browser process handling attacker-influenced Safe Browsing responses; here, a `.expect()` panic in Rust code handling attacker-supplied consensus proof data).

### Impact Explanation
A panic triggered while processing a submitted consensus proof aborts execution mid-verification. Because Substrate/host runtimes trap on Rust panics, this is not a graceful `Result::Err` — it is an unhandled trap in a function on the direct path of BEEFY consensus-proof submission/verification. Any account (an unprivileged relayer or prover) can submit a proof with an empty payload array and reliably trigger this crash, denying availability of the BEEFY consensus update path used to advance/verify relay-chain state for Hyperbridge. This blocks the delivery of any dependent cross-chain messages that rely on this consensus client being updated — a "route unable to deliver messages" condition.

### Likelihood Explanation
High. No signature check, membership proof, or other validation gates the code before this conversion runs — it only requires an ABI-decodable `Commitment` with a zero-length `payload` field, which is trivial for any submitter to construct.

### Recommendation
Replace the `.expect()` in `From<Commitment> for SpCommitment` with a proper fallible conversion (`TryFrom`) that returns a typed error when `payload` is empty, and propagate that error through `From<RelayChainProof> for MmrProof` and any pallet call sites so malformed proofs are rejected with a `DispatchError`/`Err` instead of panicking. Add a regression test analogous to `empty_hp_prefix_returns_error_not_panic` (`modules/trees/ethereum/src/tests.rs`) that submits a `Commitment` with an empty `payload` array and asserts a clean error.

### Proof of Concept
1. Craft an ABI-encoded `RelayChainProof`/`SP1BeefyProof` whose `signedCommitment.commitment.payload` is an empty `Payload[]` array (valid ABI encoding, length prefix `0`).
2. Submit it via the `submit_proof` extrinsic path in `modules/pallets/beefy-consensus-proofs` (or the corresponding SP1 proof verification entry point) as an unprivileged account.
3. ABI decoding succeeds (the array is well-formed); execution reaches `evm/rust/src/conversions.rs:340` (`iter.next().expect(...)`), which panics because `payload` is empty, aborting proof verification.

Note: I was unable to fully trace whether the SP1-zkVM guest program itself (vs. the pallet extrinsic path) is what directly invokes this specific `From<Commitment> for SpCommitment` conversion at runtime, since the guest binary entry point (`fn main`) wiring for `tesseract/consensus/beefy/zk` wasn't located in the indexed content. This does not change the fact that the conversion function is reachable from proof-verification code operating on attacker-supplied data, but confirming the exact call chain (pallet extrinsic vs. zk guest) would benefit from a full-repository session.

	impl From<Commitment> for SpCommitment {
		/// BEEFY commitment reconstruction. Reassembles the `Payload` from its
		/// `(id, data)` entries, starting with the first entry and pushing the rest via
		/// `push_raw` (which re-sorts by id to keep the invariant `Payload` expects).
		fn from(value: Commitment) -> Self {
			let mut iter = value.payload.into_iter();
			let first = iter.next().expect("commitment has at least one payload entry");
			let mut payload = BeefyPayload::from_single_entry(first.id.0, first.data.to_vec());
			for p in iter {
				payload = payload.push_raw(p.id.0, p.data.to_vec());
			}
			sp_consensus_beefy::Commitment {
				payload,
				block_number: value.blockNumber.try_into().expect("block number out of bounds"),
				validator_set_id: value
					.validatorSetId
					.try_into()
					.expect("validator set id out of bounds"),
			}
		}
	}
