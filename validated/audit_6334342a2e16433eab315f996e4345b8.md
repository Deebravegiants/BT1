### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body when computing/verifying the webhook HMAC, while `Registry.process` uses `request.shop` (taken from the unauthenticated `shopify-shop-domain` header) as the tenant identifier passed to the host application's webhook handler. An attacker who legitimately owns one shop under the same app can capture a valid `(body, hmac)` pair for their own tenant and replay it to the app's webhook endpoint while substituting the `shop-domain` header value for a *different* merchant, and the signature will still validate — because that header is never part of what is HMAC'd.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` verifies `verifiable_query.hmac` against `HMAC(secret, verifiable_query.to_signable_string)`: [1](#0-0) 

For webhooks, `to_signable_string` is defined to be only the raw HTTP body: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers, which are completely outside of the signed content: [3](#0-2) 

`Registry.process` validates only the HMAC of the body, then dispatches to the handler using the unauthenticated `request.shop` and `request.topic` values as the tenant/topic identity: [4](#0-3) 

This is the identity-binding break called out in the rules: a field (`shop`) that is *acted on* (used as the tenant key for handler dispatch/storage) is not covered by the HMAC that is supposed to authenticate the request as genuinely originating from Shopify for that shop. The equality that should hold is:
`shop authenticated-by-HMAC == shop used as tenant key`
but in this implementation the left side is empty — no shop value is bound into the signature at all, so any `shop-domain` header value passes as long as the body+hmac pair was ever valid for *some* shop under the same app secret.

### Impact Explanation
Any merchant using an app built on this gem can, for their own store, trigger a real webhook delivery (e.g. by performing an action that fires `orders/create`), capture the resulting `(raw_body, x-shopify-hmac-sha256)` pair using a proxy under their control, and then POST that same body/HMAC pair to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to another merchant's shop domain. `Utils::HmacValidator.validate` will still accept it because the signature was never bound to a shop, and the app's registered handler will process/store the attacker-supplied payload as if it belonged to the victim shop. Depending on how the host app implements its handler (most apps use `WebhookMetadata#shop` as the row key to update local state, subscriptions, inventory, order status, etc.), this allows cross-tenant data injection/corruption — a High-impact cross-tenant issue.

### Likelihood Explanation
Any user of the app (a normal, unprivileged merchant with a real install) can obtain a valid `(body, hmac)` pair for themselves trivially, since the shared secret is the app's `client_secret`, identical across every installed shop. No access to another merchant's credentials, access token, or the app's `client_secret` is required — only the ability to receive one webhook for your own shop and resend it with a modified header. This is a realistically reachable, low-effort attack path.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook_id`, `api_version`) header values in the signed/verified content, or otherwise cryptographically bind the shop to the HMAC before using `request.shop` as a tenant key in `Registry.process`. At minimum, `to_signable_string` should incorporate the `shop-domain` header alongside the body so that spoofing the header invalidates the signature.

### Proof of Concept
1. App is installed on `victim-shop.myshopify.com` and `attacker-shop.myshopify.com` (same app, same `api_secret_key`).
2. Attacker triggers a webhook delivery to their own controlled endpoint for `attacker-shop.myshopify.com`, capturing `raw_body` and the `x-shopify-hmac-sha256` value Shopify computed over that body.
3. Attacker POSTs to the real app's webhook endpoint with:
   - Body: the captured `raw_body`
   - `x-shopify-hmac-sha256`: the captured (still-valid) hmac
   - `x-shopify-shop-domain`: `victim-shop.myshopify.com`
   - `x-shopify-topic`: unchanged
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the body against the hmac and passes: [5](#0-4) 
5. The handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON>)`, causing the host app to process attacker-controlled data under the victim's tenant identity.
