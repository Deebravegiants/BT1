## Finding [1](#0-0) 

### Title
Meta-transaction (NEP-366) balance refunds are returned to the delegate action's `sender_id`, not the relayer who actually funded the deposit — ([File: runtime/runtime/src/actions.rs])

### Summary
When a relayer submits a `DelegateAction` (meta transaction) on behalf of a signer, the relayer pays all gas and attached deposits for the inner actions, but if execution of those inner actions fails on the destination shard, the refunded deposit is sent to the delegate action's `sender_id` (the party who signed the inner actions), not to the relayer who actually supplied the funds. This is the exact "unexpected refund recipient" bug class from the report: the entity that economically funded an operation is not the entity that receives the refund when the "true" payer is hidden behind a layer of indirection (in zkEVM: the bootloader hides the real `tx.origin`; in NEAR: the relayer's payment is hidden behind the `predecessor_id`-based refund heuristic).

### Finding Description
NEAR's balance-refund logic always resolves the refund recipient from the receipt's `predecessor_id` (or an explicit `refund_to` override), never from whoever actually funded the deposit: [2](#0-1) 

When `apply_delegate_action` unpacks a `SignedDelegateAction`, it creates the inner receipt with `predecessor_id: sender_id.clone()` — i.e., the delegate action's signer (Alice), even though the relayer paid for the attached deposit and gas of that receipt: [3](#0-2) 

The refund path (`refund_unspent_gas_and_deposits`) then routes any deposit refund to `receipt.balance_refund_receiver()`, which falls back to `predecessor_id` when no explicit `refund_to` is set: [4](#0-3) 

This is explicitly documented as a known, unresolved trade-off: [1](#0-0) 

The parallel to the reported `GnosisSafeZk` bug is precise: on the EVM/zkEVM report, refunds fall back to `tx.origin`, which is correct for EOA-initiated calls but incorrect once a layer of indirection (bootloader in zkSync's account-abstraction model) hides the true initiator. In NEAR, refunds fall back to `predecessor_id`, which is correct for direct transactions but incorrect once a layer of indirection (a relayer paying on behalf of a signer via `DelegateAction`) hides the true economic payer.

### Impact Explanation
A malicious `sender_id` (Alice) can craft a `DelegateAction` whose inner actions carry a large attached deposit but are engineered to fail once forwarded and executed on the receiver's shard (e.g., calling a non-existent method, a method that will predictably abort, or a receiver with insufficient state). The relayer, having no visibility into whether the receiver-side execution will fail, pays and forwards the deposit. On failure, the deposit refund is credited back to Alice's account (`predecessor_id`), not the relayer who funded it — a direct, protocol-level transfer of relayer funds to the malicious signer. This is concrete theft of relayer funds enabled purely by submitting a transaction (the wrapped `DelegateAction`), reachable by any account with no special privileges.

### Likelihood Explanation
This requires no validator collusion, no P2P manipulation, and no special access — any account can construct a `DelegateAction` with a deposit-bearing inner action designed to fail on a chosen receiver, then have it signed and handed to a relayer for submission (the normal, intended meta-transaction flow). The docs themselves acknowledge the attack surface ("there is a financial incentive for Alice to submit meta transactions that have high balances attached but will fail on Bob's shard"), meaning the runtime code path is proven reachable and the only defense currently is relayer-side trust/vetting rather than a protocol-level guarantee.

### Recommendation
When constructing the inner receipt in `apply_delegate_action`, set `refund_to` (via `ActionReceiptV2`) to the relayer's account (the outer transaction's `signer_id`/`action_receipt.signer_id()`) rather than leaving it unset so the fallback resolves to `sender_id`. This mirrors the report's suggested fix of "always specify a refundRecipient when the initiator is [effectively hidden]" — here, always specify `refund_to` as the relayer when the receipt is generated by unpacking a delegate action, so deposit refunds return to whoever actually funded them.

### Proof of Concept
1. Alice (any account, no special privileges) signs a `DelegateAction` with `receiver_id = "victim.near"`, containing a `FunctionCall` action with a large attached `deposit` calling a method Alice knows will fail (e.g., wrong argument encoding or a nonexistent method) on `victim.near`.
2. A relayer, unaware execution will fail, wraps the `SignedDelegateAction` in a transaction it signs and pays gas/deposit for, per the documented flow in `apply_delegate_action` ( [3](#0-2) ).
3. Execution proceeds: the delegate action is unpacked on Alice's shard, producing a new receipt with `predecessor_id = Alice` sent to `victim.near`; the relayer's balance was already debited to cover this deposit.
4. The `FunctionCall` fails on `victim.near`; `refund_unspent_gas_and_deposits` refunds the full deposit to `receipt.balance_refund_receiver()`, which resolves to `predecessor_id = Alice` ( [5](#0-4) , [4](#0-3) ).
5. Alice receives the deposit refund despite never having paid it — the relayer's funds are effectively transferred to Alice.

```markdown
## Balance refunds in meta transactions

Unlike gas refunds, the protocol sends balance refunds to the predecessor
(a.k.a. sender) of the receipt. This makes sense, as we deposit the attached
balance to the receiver, who has to explicitly reattach a new balance to new
receipts they might spawn.

In the world of meta transactions, this assumption is also challenged. If an
inner action requires an attached balance (for example a transfer action) then
this balance is taken from the relayer.

The relayer can see what the cost will be before submitting the meta transaction
and agrees to pay for it, so nothing wrong so far. But what if the transaction
fails execution on Bob's shard? At this point, the predecessor is `Alice` and
therefore she receives the token balance refunded, not the relayer. This is
something relayer implementations must be aware of since there is a financial
incentive for Alice to submit meta transactions that have high balances attached
but will fail on Bob's shard.
```

```rust
    pub fn refund_to(&self) -> &Option<AccountId> {
        match self.receipt() {
            ReceiptEnum::Action(_)
            | ReceiptEnum::Data(_)
            | ReceiptEnum::PromiseYield(_)
            | ReceiptEnum::PromiseResume(_)
            | ReceiptEnum::GlobalContractDistribution(_) => &None,
            ReceiptEnum::ActionV2(action_receipt_v2)
            | ReceiptEnum::PromiseYieldV2(action_receipt_v2) => &action_receipt_v2.refund_to,
        }
    }

    pub fn balance_refund_receiver(&self) -> &AccountId {
        self.refund_to().as_ref().unwrap_or_else(|| self.predecessor_id())
    }
```
