### Title
Silent ERC20/TRC20 `transfer` failure treated as success in `IntentGatewayV2.withdraw()` permanently freezes escrowed funds - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron-targeted `IntentGatewayV2.withdraw()` function releases escrowed order/fee tokens using a raw low-level `.call()` to the token's `transfer` selector, checking only that the external call did not revert (`success`), never decoding/verifying the returned boolean. Tokens that follow the LDO-style behavior — returning `false` on a failed transfer instead of reverting — will cause `withdraw()` to treat a failed transfer as a full success.

### Finding Description
In `withdraw()`, both the per-input escrow release and the fee release use this pattern: [1](#0-0) 

Only `success` (i.e., the external call itself did not revert due to an EVM-level failure) is checked; the returned `bool` payload from `transfer()` is discarded. Per the LDO incident referenced in the report, some ERC20/TRC20-standard tokens intentionally return `false` rather than reverting when a transfer cannot be completed (e.g., insufficient contract balance, a blacklisted/paused recipient, or any other application-level rejection). For such tokens, `token.call(...)` returns `success = true` with `abi.decode(data, (bool)) == false`, so the `if (!success) revert TransferFailed();` guard never fires.

Because this happens before the accounting bookkeeping is skipped, the function still unconditionally proceeds to: [2](#0-1) 

`_filled[body.commitment] = beneficiary` is set and `_orders[body.commitment][token] -= amount` is decremented as though the beneficiary was paid, even though the token silently rejected the transfer and the beneficiary received nothing.

This is a direct analog of the LDO false-top-up bug class: the caller (this contract) misinterprets a token's non-reverting failure signal as a successful transfer, and — because this state update is irreversible (`_filled` gates re-entry via `Filled()` checks elsewhere, e.g. `onGetResponse`) — the escrowed tokens become permanently stuck in the contract with no path to reclaim them for the intended beneficiary.

Notably, the equivalent function in the canonical (non-Tron) codebase, `IntentsBase._withdraw()`, uses OpenZeppelin's `safeTransfer`, which correctly reverts on a `false` return: [3](#0-2) 

confirming that the Tron variant's raw `.call()` pattern is a regression/deviation from the safe pattern used elsewhere in the same protocol, and not an intentional design choice.

The same unchecked pattern also appears in the `SweepDust` handling path in the same file: [4](#0-3) 

### Impact Explanation
Any input/output token or fee token configured for use with this Tron `IntentGatewayV2` deployment that implements the LDO-style non-reverting-`false`-on-failure transfer semantics (a documented, real-world ERC20/TRC20 pattern) will cause escrowed solver/user funds to be permanently frozen: the order is marked filled/refunded and escrow decremented, but the beneficiary never receives the tokens, with no recovery mechanism. This satisfies "permanent freezing of funds" / "unauthorized app action" (fills recorded as successful without actual value transfer) under a single relayer-submitted proof-driven `withdraw()` call path (reachable via `onGetResponse` or the fill/refund entrypoints that call `withdraw`).

### Likelihood Explanation
Likelihood is moderate-to-high: it does not require an attacker exploit — it triggers deterministically whenever the configured token (input token, output token, or protocol fee token) is one that returns `false` rather than reverting on failure (e.g., blacklist/pause-style tokens, or Tron TRC20 tokens known for this non-standard behavior), combined with any legitimate condition causing the transfer to be rejected (blacklisted beneficiary, paused token, insufficient balance from unexpected accounting drift, etc.). Given this is Tron-specific code (TRC20 tokens have well-documented divergent implementations from strict ERC20 semantics), the exposure is realistic for any Tron deployment listing such tokens.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` (and the `SweepDust` handler) with OpenZeppelin's `SafeERC20.safeTransfer`, mirroring `IntentsBase._withdraw()` in the canonical codebase, so that a `false` return value reverts the transaction instead of being silently accepted as success.

### Proof of Concept
1. Deploy/configure `IntentGatewayV2` (Tron variant) with an escrow token `T` whose `transfer()` implementation returns `false` (does not revert) when the recipient is blacklisted or the transfer otherwise fails at the application level (LDO-style semantics).
2. A solver fills an order and escrow is recorded for `beneficiary` in token `T` via the normal `placeOrder`/fill flow.
3. Trigger `withdraw()` for that commitment (e.g., via the GET-response refund path `onGetResponse` at [5](#0-4) ) while `beneficiary` is in a state where `T.transfer(beneficiary, amount)` returns `false` (e.g., blacklisted).
4. Observe: `token.call(...)` returns `success = true` (no revert), so `if (!success) revert TransferFailed();` does not trigger; `_orders[body.commitment][token] -= amount` executes and `_filled[body.commitment] = beneficiary` is set, permanently marking the order as filled/refunded.
5. Beneficiary's on-chain balance of `T` is unchanged (transfer silently failed), while the contract's internal escrow accounting shows the funds as released — tokens remain locked in the contract with no code path to retry or reclaim them for the beneficiary.
