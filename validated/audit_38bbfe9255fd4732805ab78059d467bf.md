### Title
Webhook shop-domain identity is not covered by the HMAC signature, allowing tenant-attribution spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then hands the caller a `shop` identity taken verbatim from an unauthenticated HTTP header. The `shop` value is never included in the signed material, so it can be freely substituted while the HMAC check still passes.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` header, independent of that signed body: [2](#0-1) 

`Registry.process` validates the HMAC and then forwards `request.shop` (header-derived, unsigned) straight to the app's handler as the tenant identity for the event: [3](#0-2) 

Crucially, the HMAC secret (`Context.api_secret_key`) is the **app's** secret, shared across every shop that installs the app — it is not shop-specific: [4](#0-3) 

Because of this, the binding the gem should enforce — "the shop the event is attributed to" == "the shop the signature actually proves the event came from" — does not hold. An attacker who legitimately installs the same public app on their own shop can trigger any subscribed webhook event on their shop (e.g. `orders/create`, `app/uninstalled`, `shop/update`) and capture a genuine `(raw_body, x-shopify-hmac-sha256)` pair signed by Shopify with the app's secret. Because the HMAC never covers the `shop-domain` header, the attacker can replay that exact body+signature to the app's webhook endpoint while altering only the `x-shopify-shop-domain` header to name a victim shop that also has the app installed. `Utils::HmacValidator.validate` still succeeds (it only recomputes the HMAC over the body), and the handler receives `WebhookMetadata` claiming the event is for the victim shop.

This is the same bug class as the reference report (a privileged, one-time action — here, "this webhook event belongs to shop X" — being accepted a second time / for a different context because the guard that should make it exclusive doesn't cover all the state that is acted upon).

### Impact Explanation
This breaks the tenant boundary the gem is meant to provide: `shop` is documented as the field host applications should use to route work to per-tenant state ("shop, `String` - The shop domain of the webhook"). Depending on how the host app trusts `data.shop` (which is exactly the gem's documented contract), an attacker can:
- Forge lifecycle events (e.g. `app/uninstalled`, `shop/redact`) attributed to a victim shop, causing the app to delete/disable data for a tenant the attacker doesn't control.
- Inject attacker-controlled body content (crafted via their own shop's resource state) that the host app persists keyed by the spoofed victim shop, corrupting or overwriting another tenant's data — i.e., cross-tenant access/write.

This matches the "Critical – cross-tenant access" impact category, since the identity used to select which tenant's data is mutated is attacker-controllable despite HMAC verification passing.

### Likelihood Explanation
Requires no leaked credentials, access tokens, or `api_secret_key`. The only prerequisite is that the attacker be a normal, unprivileged Shopify merchant who installs the same app that the victim shop also has installed (trivial for any public/embedded app), then triggers an event on their own store and replays the HTTP request with a modified shop header. This is entirely reachable through the gem's public, documented webhook-processing API (`Registry.process`) without any assumption that the host app "misuses" the gem — the gem itself asserts the request "did indeed come from Shopify" based only on the body HMAC while exposing an unauthenticated `shop` field as if it were verified.

### Recommendation
Do not treat `request.shop` as authenticated by `Registry.process`. At minimum:
- Document explicitly (and ideally enforce) that `shop` from `WebhookMetadata` must be cross-checked by the host application against a shop for which the app itself registered/owns an active webhook subscription (e.g., via the `webhook_id`, which is unique per subscription per shop), not trusted as attacker-supplied.
- Preferably, extend the signable content (or provide a companion check) that binds the `shop-domain` header value into the verification, e.g., by validating the webhook_id/shop pair against Shopify (GraphQL lookup) before invoking the handler, so `Registry.process` cannot be tricked into reporting an event for a shop other than the one that actually produced the signed body.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and subscribes it to webhooks (or the app auto-subscribes on install) for a topic such as `app/uninstalled`.
2. Attacker performs the action on their own shop that triggers the webhook, and captures Shopify's genuine POST request, including body `B` and header `x-shopify-hmac-sha256: H` (computed over `B` using the shared app secret).
3. Attacker constructs a new POST request to the same webhook endpoint with the same body `B` and same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses these headers; `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and succeeds because `B` and `H` are unchanged: [5](#0-4) 
5. The handler is invoked with `WebhookMetadata` whose `shop` is `victim-shop.myshopify.com`, even though the event body and signature genuinely originated from the attacker's own shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
