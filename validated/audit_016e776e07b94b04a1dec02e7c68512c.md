### Title
Webhook `shop-domain` Identity Not Bound by HMAC, Enabling Cross-Tenant Webhook Forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates its HMAC signature over the raw request body only, while the `shop` identity used to route the webhook to a merchant's tenant data is taken from a separate, unsigned HTTP header. Any party who can obtain one valid `(body, hmac)` pair signed with the app's shared secret — for example, by installing the app on their own store and receiving a legitimate webhook — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header with a victim shop's domain. The gem's `HmacValidator` reports this as a valid, authentic webhook, and the tenant identifier passed to the app's handler is the attacker-controlled header, not something cryptographically bound to the payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read straight from an HTTP header that is not part of that signable string: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC purely against `verifiable_query.to_signable_string` (i.e., the raw body), with no reference to `shop`: [3](#0-2) 

`Registry.process` then trusts the passed-in `request.shop` value directly (post-HMAC-validation) to build the `WebhookMetadata` handed to the app's handler code, which apps typically use to select the tenant/store record to act on: [4](#0-3) 

The equality that should hold is: `shop bound in HMAC-signed bytes == shop acted upon by the handler`. Instead, the gem verifies `HMAC(raw_body) == received_hmac` but then acts on `shop` parsed from an independent, unauthenticated header — breaking the binding between "bytes verified" and "identity acted on," exactly the class of bug described in the report (a field used for accounting/routing decisions that isn't covered by the integrity check).

Since the same `api_secret_key` is shared across every shop that has the app installed, any unprivileged merchant who installs the app on their own store can legitimately trigger a webhook, capture the valid `(raw_body, hmac)` pair Shopify sent them, and then directly POST that same body/HMAC to the app's public webhook endpoint while changing only the `shop-domain` header to a victim shop. `HmacValidator.validate` will still pass because it never looks at the header, and `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the victim's domain.

### Impact Explanation
This allows cross-tenant data manipulation: an attacker can make a merchant's app process arbitrary (previously legitimate, replayable) webhook payloads under a victim shop's identity, causing writes/updates to be attributed to, or performed against, the wrong tenant. This matches the Critical "cross-tenant access" impact category, since the trust boundary between shops sharing one app installation is broken.

### Likelihood Explanation
Likelihood is realistic but requires the attacker to have their own legitimate install of the target app (to obtain one valid HMAC-signed body) and the ability to reach the app's public webhook endpoint directly (which is normally internet-reachable, since that's how Shopify delivers webhooks). No access token, `client_secret`, or privileged account is required — only ordinary use of the app as an unprivileged merchant.

### Recommendation
Bind the shop identity into the value that is HMAC-verified. Either include `shop-domain` (and other routing headers) in `to_signable_string` so `HmacValidator` verifies them together with the body, or have `Registry.process` cross-check `request.shop` against an independently trusted source (e.g., look up the topic/webhook via Shopify's API using the id, rather than trusting the header) before dispatching to the handler.

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker.myshopify.com`; trigger any webhook topic the app registers for (e.g., `orders/create`) and capture the raw POST: body `B` and header `X-Shopify-Hmac-Sha256: H` (valid since signed with the shared `api_secret_key`).
2. Replay the exact same request to the app's public webhook endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com` instead of `attacker.myshopify.com`.
3. In the gem, `ShopifyAPI::Webhooks::Request.new` parses `shop` from the (attacker-controlled) header while `hmac` is computed only from the untouched body [5](#0-4) .
4. `Utils::HmacValidator.validate` succeeds because it only checks `HMAC(body)` [6](#0-5) .
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(... shop: request.shop ...)` set to `victim.myshopify.com` [7](#0-6) , causing the app to act as though the victim shop sent this webhook.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
