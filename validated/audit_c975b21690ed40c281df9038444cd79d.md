### Title
Webhook shop/topic identity is not bound to the HMAC signature, enabling cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from unauthenticated HTTP headers and are handed to application handlers as if they were verified. This mirrors the YAXIS-style bug class of "a field acted on but not covered by the signature": the value used downstream (`shop`) is not the value the cryptographic check actually covers.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are pulled directly from HTTP headers with no participation in the signed payload: [2](#0-1) 

`Registry.process` validates only the body's HMAC and then dispatches the handler using the unauthenticated `request.shop` and `request.topic` values: [3](#0-2) 

Because the HMAC binds `hmac == HMAC(secret, body)` but the host application actually keys tenant/topic dispatch on `shop == header["x-shopify-shop-domain"]` and `topic == header["x-shopify-topic"]`, the two "shop" identities diverge: the HMAC proves the body came from Shopify for *some* delivery, but it proves nothing about which shop or topic that body is attributed to by this gem.

### Impact Explanation
Any entity that can obtain one legitimate `(raw_body, hmac)` pair — e.g., a malicious merchant capturing their own shop's webhook delivery from their own app/logs, or any party who can observe one delivery to a shared/public webhook endpoint — can replay that exact body to the app's webhook endpoint while substituting `x-shopify-shop-domain` (and/or `x-shopify-topic`) headers to impersonate a different tenant. Since `Registry.process` forwards `request.shop`/`request.topic` unchecked to `WebhookMetadata` and the registered handler, the host application will process/attribute the payload to the spoofed shop, breaking the `shop-authenticated == shop-acted-on` identity binding and enabling cross-tenant data confusion. This does not require the app's `api_secret_key`, an access token, or any privileged credential — only possession of one prior valid delivery.

### Likelihood Explanation
Medium-to-high: exploitation does not require breaking the HMAC itself, only reusing a legitimate `(body, hmac)` pair with attacker-chosen headers, which any unprivileged party who owns/controls a shop that installs the app (and can view their own webhook deliveries) can obtain trivially and then target another tenant's identifier on the shared endpoint.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the signed material used for verification (or otherwise cryptographically tie the header values to the payload before using them for dispatch), so `to_signable_string` cannot be satisfied by a body whose accompanying identity headers have been altered. At minimum, cross-check `request.shop` against the shop associated with the session/registration expected to receive that topic before invoking the handler.

### Proof of Concept
1. Attacker owns "attacker-shop.myshopify.com" and installs the vulnerable app, receiving legitimate webhook deliveries (raw body + `x-shopify-hmac-sha256` + `x-shopify-shop-domain: attacker-shop.myshopify.com`).
2. Attacker resends the exact same raw body and HMAC header to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds because it only checks the body against the HMAC — it never inspects `shop`.
4. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host application to act as though the data belongs to `victim-shop`.
