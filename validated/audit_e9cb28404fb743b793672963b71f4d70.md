Confirmed. The `shop` field delivered to webhook handlers is sourced purely from an HTTP header and is never included in the HMAC-signed payload.

### Title
Webhook `shop` identity is not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the `shop` (and `topic`/`api_version`/`webhook_id`) values taken from unauthenticated HTTP headers when constructing the `WebhookMetadata` passed to the app's handler.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0)  None of the Shopify headers—including `shop`, which is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header—are part of the signed string: [2](#0-1) 

`Registry.process` validates the request using only this HMAC-over-body check, then immediately trusts `request.shop` to build the metadata object handed to the app's business logic: [3](#0-2) 

The HMAC secret (`api_secret_key`/`client_secret`) used to sign webhooks is shared by the app across every shop that installs it—Shopify does not use a per-shop signing key. This means the equality the gem should enforce, `shop_bound_by_hmac == shop_acted_on`, never actually holds: the `shop` field acted upon by `Registry.process` (and forwarded to the handler as `WebhookMetadata.shop`, [4](#0-3) ) is completely disjoint from the set of bytes (`raw_body`) actually covered by the HMAC.

### Impact Explanation
Any unprivileged internet user who installs the target app on their own Shopify store (a normal, unprivileged action) will legitimately receive real webhooks from Shopify, signed with the app's shared secret, for topics/bodies they can influence by acting in their own store (e.g., updating their own product/order data to embed attacker-chosen values in the body JSON). Because the header (`shop`) is not part of the signed material, the attacker can replay that valid `(body, hmac)` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `Utils::HmacValidator.validate` still succeeds (it only checks `raw_body` against the secret), and `Registry.process` dispatches to the handler with `WebhookMetadata.shop` set to the victim's domain and attacker-controlled `body`. Any host application that uses `data.shop` to determine which merchant record to update (the standard, expected usage pattern for Shopify webhook handlers) will apply attacker-controlled data under another tenant's identity—resulting in cross-tenant data corruption/injection, which qualifies as cross-tenant access.

### Likelihood Explanation
High. Becoming an "attacker" only requires being any developer/merchant who can install the app once (no special privilege, access token, or leaked credential needed) and being able to send an arbitrary HTTP POST with custom headers to the app's public webhook endpoint. No knowledge of `api_secret_key` is required—the attacker only needs one valid `(body, hmac)` pair, which Shopify hands them for free on any topic they can trigger in their own store.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the material that is cryptographically bound to the request—Shopify's own guidance is to treat `X-Shopify-Shop-Domain` as authenticated only in combination with a per-shop check (e.g., verifying the domain against the shop's own stored session/access token, or otherwise correlating with topic/webhook subscription records) rather than trusting it purely because the shared-secret HMAC over the body validated. At minimum, `Registry.process` should require the caller to supply/verify the expected shop (e.g., from session storage) rather than propagating the raw unauthenticated header value as the source of truth for tenant identity.

### Proof of Concept
1. Attacker signs up for the target Shopify app on their own store `attacker.myshopify.com`, completing OAuth normally.
2. Attacker triggers a webhook-eligible event in their own store with attacker-controlled content in the resource (e.g., set a product title to `"body": {"malicious":"payload"}`-equivalent JSON), causing Shopify to POST a webhook to the app's endpoint with:
   - `X-Shopify-Hmac-Sha256: <valid HMAC of raw_body computed with the app's shared api_secret_key>`
   - `X-Shopify-Shop-Domain: attacker.myshopify.com`
3. Attacker intercepts/replays this exact `(raw_body, hmac)` pair via their own HTTP client, but rewrites the header to `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) succeeds because it only checks `raw_body` against the shared secret.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) dispatches `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker JSON>, ...)` to the app's handler, which updates data believing it originated from the victim shop.
