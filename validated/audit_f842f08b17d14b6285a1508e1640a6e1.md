### Title
Webhook HMAC signature does not bind the `shop` field, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies its HMAC over the raw request body only, while the `shop` (tenant identifier) is taken from an unauthenticated header and passed straight through to the webhook handler. This breaks the intended binding `hmac_verified_bytes == data_acted_on`, allowing a legitimately-signed webhook payload from one shop to be replayed against a victim shop's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` with: [1](#0-0) 
`hmac` is derived from the `hmac-sha256` header, and `shop` is derived from the `shop-domain` header — a completely separate, unauthenticated header.

`to_signable_string` only returns the raw body: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC exclusively over `to_signable_string` (i.e., only the body): [3](#0-2) 

`Webhooks::Registry.process` then trusts `request.shop` — the unauthenticated header — as the tenant identity for dispatching to the handler, without any additional check that the `shop` matches the body or the signature: [4](#0-3) 

The broken identity binding, stated as an equality:
`shop_authenticated_by_hmac (∅, not covered by signature) != shop_used_for_tenant_dispatch (request.shop header, attacker-controlled)`

Because the signature covers only the JSON body, any request with a *valid* body+HMAC pair — regardless of which shop it originated from — will pass `HmacValidator.validate` no matter what value is placed in the `shop-domain` header. An unprivileged actor who has access to any one legitimately-signed webhook delivery (e.g., a merchant who installed the app themselves and can observe/capture webhooks delivered to their own endpoint, since Shopify does deliver real signed webhooks to the app's registered endpoint for every shop that installs it) can resubmit that exact body with the `shop-domain` header changed to a different (victim) shop's domain. The gem will accept it as valid and hand the handler a `WebhookMetadata` claiming to be from the victim shop: [5](#0-4) 

### Impact Explanation
This breaks the tenant isolation boundary the gem is expected to enforce for multi-tenant apps: any downstream logic that trusts `WebhookMetadata#shop` for tenant-scoped writes/reads (e.g., "save this order data for shop X", "update this shop's settings") can be tricked into attributing attacker-supplied, replayed data to a different shop than the one it actually came from. This meets the Critical "cross-tenant access" bar, since the app's per-shop data can be cross-contaminated using only a webhook payload the attacker legitimately received for their own shop.

### Likelihood Explanation
Moderate-to-high: no secret, access token, or privileged account is required. Any merchant who installs the app on their own store — an "unprivileged" party with respect to other tenants — automatically receives legitimately HMAC-signed webhooks and can replay them with a forged `shop-domain` header against the app's public webhook endpoint. The only requirement is that the app dispatches on `request.shop`/`WebhookMetadata#shop` without independently corroborating it (which the gem does nothing to prevent or even warn about).

### Recommendation
Bind `shop` (and other identity-bearing fields such as `topic`/`webhook_id`) into the HMAC-verified surface, or otherwise cryptographically bind them to the signed body — Shopify already includes the shop in other signed contexts (e.g., OAuth `AuthQuery`). At minimum, `Webhooks::Registry.process` should not trust `request.shop` as an authenticated tenant identifier; document clearly that `shop` is unauthenticated header data and require callers to corroborate it against known installed-shop records before using it for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw body `B` and the resulting valid `x-shopify-hmac-sha256` header `H` (a legitimate signature over `B` with the app's shared secret).
2. Attacker sends a new POST to the app's webhook endpoint with the *same* body `B` and *same* header `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into `hmac = H`, `shop = "victim-shop.myshopify.com"`.
4. `Utils::HmacValidator.validate` recomputes HMAC over `B` only, matches `H`, and returns `true` (see `lib/shopify_api/utils/hmac_validator.rb` lines 26-31).
5. `Registry.process` calls the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` (`lib/shopify_api/webhooks/registry.rb` lines 190-199), causing the app to process attacker-supplied data under the victim shop's identity.
