Found a strong, concrete analog in the system program's `CreateAccount` instruction handling — the same "front-run a must-be-empty precondition to grief a critical state-transition" bug class as the MakerDAO `Vow.flop()` finding.

### Title
Unprivileged "account pre-funding" front-run blocks `SystemInstruction::CreateAccount` (and any downstream PDA/account creation flow) - (File: `programs/system/src/system_processor.rs`)

### Summary
`SystemInstruction::CreateAccount` (and `CreateAccountWithSeed`) require the destination account to have exactly zero lamports before creation is allowed. Because the System program's `Transfer` instruction lets *any* unprivileged signer send lamports to *any* address (including addresses that don't yet exist), an attacker who can predict a target address (a PDA, an Associated Token Account, a vote/stake account, or any deterministically derived account) can send a trivial amount of lamports to it before the legitimate `CreateAccount` transaction lands. This causes the legitimate creation to permanently fail with `SystemError::AccountAlreadyInUse`, exactly mirroring the Vow `flop()`/`vat.dai(this)==0` DoS pattern from the report: an unprivileged party griefs a "must be empty" precondition by racing in a trivial value transfer.

### Finding Description
The vulnerable check is in `create_account`: [1](#0-0) 

```rust
fn create_account(...) -> Result<(), InstructionError> {
    // if it looks like the `to` account is already in use, bail
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        if to.get_lamports() > 0 {
            ic_msg!(invoke_context, "Create Account: account {:?} already in use", to_address);
            return Err(SystemError::AccountAlreadyInUse.into());
        }
        allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
    }
    transfer(from_account_index, to_account_index, lamports, invoke_context, instruction_context)
}
``` [2](#0-1) 

The precondition `to.get_lamports() > 0 => fail` is exactly analogous to the Dai `Vow.flop()`'s `require(vat.dai(address(this)) == 0)`. Just as `Vat.move()` lets any unprivileged party push a trivial Dai balance into the Vow, the System program's ordinary lamport `transfer`/`transfer_verified` path lets any unprivileged signer send lamports into an arbitrary, not-yet-existent System-owned account with no signature required from the recipient: [3](#0-2) 

This is the well-known "address/account pre-funding" (a.k.a. dust/poisoning) griefing pattern on Solana: since PDAs and derived addresses (e.g., Associated Token Accounts, program-derived vote/stake/config accounts, escrow accounts) are deterministically computable off-chain before creation, an attacker watching the mempool/gossip for a soon-to-be-submitted `CreateAccount` transaction can front-run it (or simply pre-emptively fund the address ahead of time, since address derivation requires no permission) with as little as 1 lamport, permanently blocking creation until someone/some privileged path drains or reclaims the funds.

Notably, the codebase's own `CreateAccountAllowPrefund` instruction and `create_account_allow_prefund` function were added specifically to work around this exact defect by explicitly not requiring zero lamports: [4](#0-3) 

This confirms the underlying "must have zero lamports" precondition in the classic `CreateAccount`/`CreateAccountWithSeed` path is a recognized foot-gun; however, `CreateAccount` (the default, still used by nearly every program/CLI/SDK path, e.g., `system_instruction::create_account`) still enforces the vulnerable check and is not deprecated, so the DoS surface remains live for any caller that hasn't migrated to `CreateAccountAllowPrefund`.

### Impact Explanation
An unprivileged attacker can permanently block creation of any address they can predict in advance (PDAs, ATAs, vote/stake accounts created via `create_account`/`create_account_with_seed`, escrow/vault accounts, etc.) at negligible cost (rent for 0-byte account, reclaimable later). This is a genuine denial-of-service against unprivileged/protocol-level SVM execution paths: legitimate transactions relying on `CreateAccount` will deterministically fail with `AccountAlreadyInUse` until the account is manually reclaimed (which itself requires the account's authority/owner to sweep it, an operation the victim may not know to perform). This matches the report's "obstruct legitimate protocol operation via front-running a zero-balance precondition" bug class, causing loss of availability / griefing rather than direct fund loss.

### Likelihood Explanation
High. No special privileges, cluster access, or validator control are required — this only needs a plain `SystemInstruction::Transfer` to the target address, which any wallet can construct given knowledge of the seed/PDA derivation (which is by design public/derivable). This is a widely known and previously observed real-world nuisance/attack on Solana ("account funding griefing"), and its root cause — `create_account`'s hard requirement that the destination start at exactly zero lamports — is still present and reachable by any unprivileged transaction sender.

### Recommendation
Short term: encourage/migrate callers (SDKs, CLIs, common programs like SPL Token/ATA) to use `CreateAccountAllowPrefund` instead of `CreateAccount` wherever the account address is derivable/predictable, since that path already tolerates pre-funded lamports.
Long term: consider making `CreateAccount`/`CreateAccountWithSeed` tolerant of pre-existing lamports as long as the account has no data and is owned by the System program (mirroring `create_account_allow_prefund`'s behavior), removing the `AccountAlreadyInUse` trap for the zero-lamports case entirely, matching the report's recommendation to eliminate the exact-value precondition rather than requiring exact state.

### Proof of Concept
1. Attacker computes the deterministic destination address a victim's client is about to create — e.g., an Associated Token Account address via `get_associated_token_address`, or a PDA `Pubkey::create_with_seed`/`find_program_address` result.
2. Attacker submits `SystemInstruction::Transfer { lamports: 1 }` from any funded, unprivileged wallet to that address (no recipient signature required, per `transfer_verified` at `programs/system/src/system_processor.rs:216-243`).
3. Victim's subsequent `SystemInstruction::CreateAccount` (or `CreateAccountWithSeed`) transaction targeting the same address now sees `to.get_lamports() > 0` at `programs/system/src/system_processor.rs:164`, and fails with `SystemError::AccountAlreadyInUse`.
4. Victim's operation (ATA creation, PDA initialization, vote/stake account setup, etc.) is blocked until they detect the poisoned account and take separate remedial action (if even possible), reproducing the Vow `flop()` DoS pattern.

fn transfer_verified(
    from_account_index: IndexOfAccount,
    to_account_index: IndexOfAccount,
    lamports: u64,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    let mut from = instruction_context.try_borrow_instruction_account(from_account_index)?;
    if !from.get_data().is_empty() {
        ic_msg!(invoke_context, "Transfer: `from` must not carry data");
        return Err(InstructionError::InvalidArgument);
    }
    if lamports > from.get_lamports() {
        ic_msg!(
            invoke_context,
            "Transfer: insufficient lamports {}, need {}",
            from.get_lamports(),
            lamports
        );
        return Err(SystemError::ResultWithNegativeLamports.into());
    }

    from.checked_sub_lamports(lamports)?;
    drop(from);
    let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
    to.checked_add_lamports(lamports)?;
    Ok(())
}
