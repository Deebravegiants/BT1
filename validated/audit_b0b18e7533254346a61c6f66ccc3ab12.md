Confirmed: `ShopValidator` is never called anywhere in the webhook processing path — it's only used in OAuth-related flows (`token_exchange.rb`, `client_credentials.rb`, `refresh_token.rb`, `storefront.rb`), never in `registry.rb` or `request.rb`.

### Title
Webhook shop attribution is not bound to the HMAC signature, enabling cross-tenant webhook forgery - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` proves nothing about the `shopify-shop-domain`/`x-shopify-shop-domain` header — it only proves the body was signed by *some* shop under the app's shared `api_secret_key`. `Registry.process` then reads `request.shop` directly from that unauthenticated header and hands it to the handler as trusted tenant identity, with no call to `ShopValidator.sanitize!` or any other shop cross-check.

### Finding Description
The broken binding: `HMAC-signed bytes (raw_body) != bytes acted on (raw_body + shop header)`, equivalently `shop authenticated by signature != shop attributed to handler`.

- `Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 
- `Request#shop` reads the header value verbatim with no validation: [2](#0-1) 
- `HmacValidator.validate_signature` computes the HMAC solely over `verifiable_query.to_signable_string` (the raw body) and compares against the received `X-Shopify-Hmac-Sha256`, never touching the shop header: [3](#0-2) 
- `Registry.process` validates the HMAC, then passes `request.shop` straight into `WebhookMetadata.new(...)` without any `ShopValidator.sanitize!` or equivalent check: [4](#0-3) 
- `ShopValidator` exists in this gem but is used only in OAuth/token-exchange flows (`lib/shopify_api/auth/token_exchange.rb`, `client_credentials.rb`, `refresh_token.rb`, `clients/graphql/storefront.rb`), never in the webhook path.

Because `api_secret_key` is a single shared app secret (not per-shop), any body/HMAC pair that is valid for one shop's webhook is valid for every shop's webhook delivered to the same app. An attacker installs the app on their own development shop `attacker.myshopify.com`, receives a legitimately signed webhook (raw body `B`, `X-Shopify-Hmac-Sha256: H`), then sends their own HTTP POST directly to the target app's webhook endpoint with the same `B` and `H` but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`. `HmacValidator.validate` recomputes the HMAC over `B` only, matches `H`, and returns `true`. `Registry.process` then invokes the handler with `WebhookMetadata` claiming `shop: "victim-shop.myshopify.com"`, `body: parsed(B)`, letting attacker-chosen data be attributed to and processed under the victim's tenant identity.

### Impact Explanation
Any handler that trusts `WebhookMetadata#shop` to key per-tenant state (e.g., updating victim shop's local records, billing, inventory, orders) can be made to write or act on attacker-controlled data under the victim's tenant. This is a cross-tenant authentication bypass: an unauthenticated value (the shop header) is treated as authenticated because the signature check silently omits it. The attack is repeatable against arbitrary victim shop domains once the attacker has one valid signed payload from their own dev shop, since only the header (not the signed content) needs to change per victim.

### Likelihood Explanation
Preconditions are minimal and fully within an unprivileged attacker's control: create a free development shop, install the target app, register one webhook, capture one legitimately delivered body+HMAC pair, then replay it directly to the app's public webhook endpoint with a forged shop header. No secrets, tokens, or privileged access are required. The relevant gem code path (`Request`, `HmacValidator`, `Registry.process`) is exactly what the documented usage exercises, so this is not dependent on unusual host-app misconfiguration.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signable bytes, or otherwise bind the header's shop value to the signature — e.g., append the raw shop header to `to_signable_string`, or require host apps to independently validate `request.shop` against session/tenant records before trusting it. At minimum, call `ShopValidator.sanitize!` in `Registry.process` before constructing `WebhookMetadata`, and document to consumers that `request.shop` must be treated as provisional even after `HmacValidator.validate` passes, since the signature does not cover the shop header.

### Proof of Concept
minitest + WebMock:
1. Build `raw_body = '{"id":1}'`; compute `H = OpenSSL::HMAC.hexdigest(SHA256, api_secret_key, raw_body)` (base64-encode per real header format as `hmac()` expects `Base64.decode64`).
2. Construct `request_a = Request.new(raw_body: raw_body, headers: {"x-shopify-hmac-sha256" => H_b64, "x-shopify-topic" => "orders/create", "x-shopify-shop-domain" => "attacker.myshopify.com"})`.
3. Construct `request_b` identically except `"x-shopify-shop-domain" => "victim-shop.myshopify.com"`.
4. Assert `Utils::HmacValidator.validate(request_a) == true` and `Utils::HmacValidator.validate(request_b) == true` (same body/HMAC, different shop).
5. Assert `request_a.shop != request_b.shop` (`"attacker.myshopify.com"` vs `"victim-shop.myshopify.com"`), demonstrating the signature validates identically regardless of the claimed shop, i.e., the equality `signed shop == attributed shop` fails while `HmacValidator.validate` returns `true` for both.
6. Optionally call `Registry.process(request_b)` with a stub handler registered for the topic and assert the handler receives `WebhookMetadata#shop == "victim-shop.myshopify.com"` despite the payload/signature having been produced under the attacker's own shop context.
