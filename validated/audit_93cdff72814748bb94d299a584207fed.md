### Title
Webhook HMAC signature does not bind the `X-Shopify-Shop-Domain` header, allowing shop-identity spoofing on otherwise valid webhook deliveries - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) purely from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, while the HMAC signature validated by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body. This breaks the identity binding: `shop == HMAC-authenticated shop` does not hold, because the header carrying the shop is never part of the signed content passed to the app's webhook handler.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop` accessor, however, is read directly and unauthenticated from a header: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then hands `request.shop` straight to the app's handler as the trusted tenant identity, with no cross-check that the header matches anything covered by the signature: [3](#0-2) 

`HmacValidator.validate` computes/compares the signature strictly against `verifiable_query.to_signable_string`, which for webhooks is `@raw_body` — the `shop-domain` header is never included: [4](#0-3) 

Because the HMAC key (`api_secret_key`) is shared by the app across all of its installed shops, any merchant who has installed the app receives a legitimately-HMAC-signed webhook body for their own shop. Since the signature doesn't cover the `shop-domain` header at all, that same valid `(body, hmac)` pair can be resent to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header changed to reference a *different* shop that also has the app installed. `Registry.process` will report `Utils::HmacValidator.validate(request)` as `true` (the body/HMAC pair is genuinely valid), and will pass the attacker-chosen `shop` value into `WebhookMetadata` as if it were an authenticated fact about which tenant the payload belongs to.

This is the direct analog of the reported bug class: a field that is *acted upon* (the tenant/shop identity used by the handler to select per-tenant session/access-token/data) is not the field that was actually *cryptographically verified* (only the body was verified) — i.e., `shop_verified != shop_used`.

### Impact Explanation
If a host application uses `WebhookMetadata#shop` (as documented/intended by this gem) to select which shop's session, access token, or per-tenant datastore record to operate on, an attacker who controls one installed shop can forge webhook deliveries that are accepted as valid for a *different* tenant shop, leading to cross-tenant data confusion/access — matching the "cross-tenant access" Critical impact category defined in scope.

### Likelihood Explanation
High: the attacker only needs to have the target app installed on any shop they control (a normal, unprivileged usage of the app) to legitimately receive a validly-signed webhook body+HMAC pair, then can freely resend it with an arbitrary `X-Shopify-Shop-Domain` header value. No secret material, TLS interception, or elevated privilege is required — only a normal HTTP client capable of replaying a captured request with a modified header.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the HMAC-signable content, or otherwise cryptographically tie the header-derived identity fields to the verified payload before handing them to `WebhookMetadata`/the app's handler, so that `Registry.process` cannot be satisfied by a signature that never covered the tenant-identifying header.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Shopify sends a legitimate webhook: body `B`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`, header `x-shopify-hmac-sha256: H` where `H = HMAC(api_secret_key, B)` — this is valid per `HmacValidator.validate`.
3. Attacker resends the exact same `raw_body: B` and `x-shopify-hmac-sha256: H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (a shop the same app is installed on).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` — using only `request.to_signable_string` (i.e. `B`) — which returns `true` because `H` is a valid HMAC of `B`, regardless of the shop header. [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload originated from, and was signed for, `attacker-shop.myshopify.com`.

          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
