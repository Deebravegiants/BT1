### Title
Hostile mint pre-seed with an extreme reserve ratio caps the rebalance swap and seeds HyperSwap LP at an off-curve-close price - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding._seedRebalancing` / `_pairRebalance` / `_swapBudget` defend `finalizeGraduation` against a front-run `pair.mint` hostile pre-seed by computing a no-fee rebalance swap and depositing the remainder via the router. The rebalance swap input is capped at 99% of Bonding's *own* graduation inventory (`tokensForLP` / `ltFromPair`), not at whatever size is needed to fully correct the pre-seed ratio. An attacker who mints a sufficiently large, sufficiently skewed pre-seed can force the required rebalance input to exceed this cap, so the swap only partially corrects the ratio, and the subsequent `_routerDepositAndDispose` deposits at the still-skewed post-swap ratio (via `addLiquidity(min0=1, min1=1)`), permanently seeding the graduated LP away from the true curve-close price.

### Finding Description
`_seedRebalancing` (`Bonding.sol`, ~1279-1354) branches into the mint-pre-seed rebalance path when reserves are non-trivial relative to `(tokensForLP, ltFromPair)`. It calls `_pairRebalance` with `maxSwap: _swapBudget(_ltSwapInventory(lt, protectedLT))` or `_swapBudget(IERC20(tokenAddress).balanceOf(address(this)))` [1](#0-0) . `_swapBudget` caps this at 99% of Bonding's own inventory for that side, explicitly to guarantee the deposit leg still has a non-zero amount of both sides after the swap [2](#0-1) .

`_pairRebalance` computes the theoretically-correct no-fee swap input via `_noFeeSwapInput(reserveIn, reserveOut, targetN, targetD, maxSwap)` and clamps it to `maxSwap` [3](#0-2) . If the pre-seed's reserve skew is large enough that the mathematically-required swap `s = sqrt(reserveIn·reserveOut·targetN/targetD) − reserveIn` exceeds `maxSwap`, the actual swap executed is only `maxSwap`, which is strictly less than what's needed to move the pool back to the `tokensForLP/ltFromPair` ratio.

After this partial rebalance, `_routerDepositAndDispose` deposits the remaining inventory into the still-skewed pool using the router's `quote()`-based optimal split with `min0=1, min1=1` [4](#0-3) . Because the router deposits at the *current* (still off-target) pool ratio rather than the cached curve-close ratio, the resulting LP — locked permanently in `LPLock` via `finalizeGraduation`'s `LPLock.recordLock` call, which cannot be skipped — opens at a price that deviates from the last curve price, violating the "zero price gap" invariant the whole `_seedUniswapV2Direct` subsystem exists to guarantee.

The code comments in `_swapBudget` acknowledge only the brick-avoidance property ("the deposit leg always lands AND mints non-zero LP") [2](#0-1) , but do not address correctness of the resulting price when the cap actually binds — the natspec states the cap "doesn't bind" for "any realistic pre-seed" but does not exclude a large-budget attacker capable of funding a big enough pre-seed. The developers themselves flag that the dedicated end-to-end hostile-pre-seed regression suite (`test/HostilePreSeed.t.sol`) covering "the wrong-opening-price / LP-capture scenarios, attacker-no-profit ... properties" was removed and "no longer enforced by automated tests" [5](#0-4) .

### Impact Explanation
A hostile pre-seed sized so the required corrective swap exceeds the graduation's own inventory budget results in an LP that opens away from the curve-close price. This lets the attacker (who holds the pre-existing skewed-ratio LP) capture value at graduation time through the wasted-side donation/arbitrage that `_seedUniswapV2Direct` was built to eliminate, transferring value out of the protocol's curve-raised LT/token reserves and permanently mispricing the LP that `LPLock` locks (no withdraw path in v1). This matches the explicitly in-scope impact: "an LP seeded away from the curve close price."

### Likelihood Explanation
This requires the pre-seed to be large enough, on the reserve-imbalance side, that the rebalance swap needed to correct the ratio exceeds 99% of Bonding's own `tokensForLP`/`ltFromPair` inventory for that graduation — i.e., a well-funded attacker (funding both the token supply, via `Zap.buy`/curve activity or direct transfer, and a large LT amount) rather than a "$1 dust" attacker. It is reachable by any unprivileged address front-running `finalizeGraduation` with `factory.createPair` + `transfer` + `pair.mint`, all callable by any wallet. The size of budget needed scales with the token's `LP_RESERVE`/curve-raised LT, which is bounded but non-trivial (up to 250M tokens / the curve's raised LT), so likelihood depends on the attacker's capital relative to a given token's post-graduation LP size — plausible for large or blue-chip launches.

### Recommendation
Do not silently deposit at the post-swap ratio when the swap was clamped by `maxSwap` and the ratio is not actually restored. Either (a) increase/uncap the rebalance budget so the swap can always fully correct the ratio regardless of pre-seed size (accepting the deposit-side dust risk this was designed to avoid, but bounding it safely), or (b) after the clamped swap, re-check whether the resulting ratio is within an acceptable tolerance of `tokensForLP/ltFromPair`; if not, fall back to a mechanism that doesn't donate value to the pre-existing hostile LP (e.g., a bounded direct-mint fallback proportional to the *actual* achievable post-swap ratio, or explicitly reverting/queuing recovery for operator intervention rather than silently locking a mispriced LP). Restore/add the removed end-to-end hostile-pre-seed regression tests (previously in `test/HostilePreSeed.t.sol`) specifically covering pre-seeds large enough to hit the `_swapBudget` cap.

### Proof of Concept
1. Creator launches a token via `Zap.createToken`; trading proceeds until the curve nears graduation (large `tokensForLP`/`ltFromPair` inventory accrues, e.g., near the 250M `LP_RESERVE` cap for a heavily-traded token).
2. Before `finalizeGraduation` is called (racing the keeper, or immediately after the threshold-crossing buy that fires `_enterGraduating`), an attacker:
   - Calls `factory.createPair(token, lt)` (permissionless).
   - Transfers a very large, heavily skewed amount of `lt` (or `token`) to the pair — sized so that the amount needed to rebalance back to `tokensForLP/ltFromPair` would exceed 99% of Bonding's own `ltFromPair` (or `tokensForLP`) inventory for this graduation.
   - Calls `pair.mint(attacker)` to receive LP against this hostile ratio.
3. Anyone calls `finalizeGraduation(tokenAddress)`. `_seedRebalancing` detects the mint pre-seed, computes `_noFeeSwapInput`, which exceeds `maxSwap`, and `_pairRebalance` clamps the swap to `maxSwap` — insufficient to restore the target ratio.
4. `_routerDepositAndDispose` deposits the remaining inventory at the still-skewed ratio via `addLiquidity(min0=1, min1=1)`, minting LP to `LPLock` at a price that deviates materially from the last curve price.
5. `LPLock.recordLock` finalizes the lock — the mispriced LP is now permanent and unrecoverable in v1, and the attacker's pre-existing LP share captures value from the pool at the true market price via arbitrage.

*(Note: I was unable to fully trace `_noFeeSwapInput`'s exact closed-form implementation and `DIRECT_MINT_PRESEED_BPS`/`_prepareGraduationLiquidity` bounds within the remaining tool budget to precisely quantify the minimum attacker capital required to trigger the `maxSwap` clamp for a given token size; this would need to be verified against `test/NoFeeSwapInput.t.sol` and `_prepareGraduationLiquidity` in a follow-up review.)*

    /// @dev Cap the rebalance swap at 99% of the available side's budget,
    ///      so the subsequent `addLiquidity` always has a non-zero amount
    ///      of BOTH sides to deposit. Without this, an extreme hostile
    ///      pre-seed (massively imbalanced reserves) drives the
    ///      unconstrained `_noFeeSwapInput` past our per-side budget,
    ///      `_pairRebalance` clamps to the full budget, and the swap
    ///      consumes 100% of one side. `_routerDepositAndDispose` then
    ///      skips `addLiquidity` (`remToken == 0` or `remLT == 0`),
    ///      `finalizeGraduation` returns `liquidity = 0`, and
    ///      `LPLock.recordLock(...)` records a zero-sized lock — the
    ///      attacker's pre-existing LP becomes 100% of the pool. Reserving
    ///      1% guarantees the deposit leg always lands AND mints non-zero
    ///      LP at the post-swap ratio. The 1% comes off the swap, not the
    ///      deposit — for any realistic pre-seed `s_unconstrained` is
    ///      orders of magnitude below `maxSwap`, so the cap doesn't bind
    ///      and behaviour is unchanged. It only kicks in for catastrophic
    ///      pre-seeds beyond our budget capacity, where the alternative
    ///      is bricking.
    function _swapBudget(
        uint256 budget
    ) internal pure returns (uint256) {
        return (budget * 99) / 100;
    }

    function _pairRebalance(
        RebalanceParams memory p
    ) internal returns (bool) {
        uint256 s = _noFeeSwapInput(p.reserveIn, p.reserveOut, p.targetN, p.targetD, p.maxSwap);
        if (s == 0) return false;

        // Quote from the pair so the output tracks its live fee; a value
        // derived from a stale fee rate would trip the pair's K-check.
        uint256 expectedOut = IUniswapV2Pair(p.pair).getAmountOut(s, p.tokenIn);
        if (expectedOut == 0) return false;

        IERC20(p.tokenIn).safeTransfer(p.pair, s);
        (uint256 amount0Out, uint256 amount1Out) = p.tokenInIs0 ? (uint256(0), expectedOut) : (expectedOut, uint256(0));
        IUniswapV2Pair(p.pair).swap(amount0Out, amount1Out, address(this), new bytes(0));
        return true;
    }
