## Title
`process_deposit` mints LP tokens with no user-specified minimum, exposing depositors to reserve-manipulation slippage - (File: `program/src/processor.rs`)

### Summary
The Raydium AMM `Deposit` instruction lets a liquidity provider bound the input token amounts (`max_coin_amount`, `max_pc_amount`) and optionally bound the "other side" input via `other_amount_min`, but it never lets the caller specify a minimum number of LP tokens (`mint_lp_amount`) to receive. Because `mint_lp_amount` is computed as a share of the *current* pool reserves (`total_coin_without_take_pnl` / `total_pc_without_take_pnl`), which a same-block/adjacent transaction can shift via ordinary swaps, an attacker can sandwich a deposit to dilute the LP tokens minted to the depositor while still satisfying the depositor's coin/pc-ratio slippage bounds. This mirrors the Code4rena Vader finding [M-01] `VaderPoolV2.mintFungible` exposes users to unlimited slippage, where the missing control is specifically the minimum LP-output check, not the input-ratio check.

### Finding Description
`DepositInstruction` only carries `max_coin_amount`, `max_pc_amount`, `base_side`, and an optional `other_amount_min`: [1](#0-0) 

In `Processor::process_deposit`, the pool's current reserves (net of PnL) are used to build an `InvariantToken`/`InvariantPool` and compute both the "deduct" amounts and the LP amount to mint: [2](#0-1) 

For `base_side == 0` (base coin), `deduct_coin_amount` is fixed to `deposit.max_coin_amount`, and `deduct_pc_amount` is computed from the *current* invariant, then checked only against `max_pc_amount` and, if provided, `other_amount_min`: [3](#0-2) 

Crucially, `mint_lp_amount` is derived independently as `deduct_coin_amount / total_coin_without_take_pnl * amm.lp_amount` (floored), with **no lower bound enforced anywhere**: [4](#0-3) [5](#0-4) 

The only guard on `mint_lp_amount` is that it must not be zero: [6](#0-5) 

Because `total_coin_without_take_pnl`/`total_pc_without_take_pnl` reflect the pool's live reserves at execution time (see `Calculator::calc_total_without_take_pnl_no_orderbook`), an attacker can submit a swap transaction immediately before the victim's `Deposit` to shift the coin/pc reserve balance. This changes the exchange rate used to compute `deduct_pc_amount`/`deduct_coin_amount` (which can still land within the victim's `max_pc_amount`/`other_amount_min` bounds, since those bounds are typically set loosely by wallets/UI, or the attacker calibrates the shift precisely to stay inside them) while simultaneously inflating the reserve base (`total_coin_without_take_pnl`) that determines the victim's *proportional* LP share. The attacker then reverses the swap after the victim's deposit lands, restoring the pool to its prior price and pocketing the difference between the LP share the victim should have received and the diminished share actually minted.

This is the exact bug class from the external report: input-side (price) slippage protection exists, but **output-side (LP share) slippage protection does not**, so the LP receives fewer pool tokens than the fair value of their deposit while all program-level checks pass.

### Impact Explanation
A successful sandwich lets the attacker capture value that rightfully belongs to the depositor — a direct, silent value transfer from LPs to frontrunners on every deposit, with no cap other than the loose `max_coin_amount`/`max_pc_amount`/`other_amount_min` bounds the depositor happens to set. Because `Deposit` is reachable by any unprivileged account with attacker-controlled adjacent transactions (a swap before and after), and the loss is real token value permanently transferred out of the depositor's intended contribution, this is a legitimate Medium-severity finding consistent with the judged severity of the original report.

### Likelihood Explanation
Every `Deposit` call is susceptible whenever a depositor does not pass tight bounds for `max_coin_amount`/`max_pc_amount`/`other_amount_min` (common in practice, since UIs often compute these with a percentage-based slippage tolerance around the *value* transferred, not around the resulting LP-share). Any searcher/MEV bot monitoring the mempool for `Deposit` instructions can execute the swap-sandwich atomically within a single block, making this readily and repeatedly exploitable without any privileged access.

### Recommendation
Add a caller-supplied `min_lp_amount` (or equivalent) field to `DepositInstruction`, and after computing `mint_lp_amount` in `process_deposit`, enforce `mint_lp_amount >= min_lp_amount` (returning `AmmError::ExceededSlippage` otherwise), mirroring the existing `other_amount_min` pattern already used for the exchange-rate check.

### Proof of Concept
1. Attacker observes a pending `Deposit` (`base_side = 0`) transaction with `max_coin_amount = C`, `max_pc_amount = P_max` (loose bound), and no tight `other_amount_min`.
2. Attacker front-runs with a `SwapBaseIn`/`SwapBaseOut` that sells coin into the pool, increasing `amm_coin_vault.amount` (hence `total_coin_without_take_pnl`) and decreasing `total_pc_without_take_pnl`, calibrated so the resulting `deduct_pc_amount` for the victim's `C` stays `<= P_max` (and, if set, `>= other_amount_min`).
3. Victim's `Deposit` executes: `deduct_coin_amount = C`; `mint_lp_amount = C / total_coin_without_take_pnl_inflated * amm.lp_amount` — smaller than it would have been against the pre-swap reserves — see `program/src/processor.rs` lines 1243-1250, 1341-1350.
4. Attacker back-runs with the inverse swap, restoring the pool price and net-capturing (minus fees) the LP-share differential that the victim should have received.
5. No check in `process_deposit` (lines 988-1374) rejects this because `mint_lp_amount` has no user-specified floor — only a non-zero check at line 1323.
