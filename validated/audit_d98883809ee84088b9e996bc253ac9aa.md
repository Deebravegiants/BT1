### Title
Webhook `shop-domain` is trusted for tenant routing but is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook's authenticity by calling `Utils::HmacValidator.validate(request)`, which computes the HMAC only over `request.to_signable_string` — the raw request body. The `shop` (from the `X-Shopify-Shop-Domain` header) is never included in the signed material, yet it is the value handed to the app's handler as the tenant identifier for the webhook.

### Finding Description
`HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the received HMAC [1](#0-0) . For webhooks, `Webhooks::Request#to_signable_string` returns only `@raw_body`, while `Webhooks::Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header and is not part of the signed string [2](#0-1) .

`Registry.process` validates the HMAC and then dispatches to the app's handler using `request.shop` as the tenant identifier, without any additional binding between the verified body and the claimed shop:
```
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
``` [3](#0-2) 

The identity binding that should hold is: `shop-domain header == shop that produced the HMAC-signed body`. Because `shop` is excluded from `to_signable_string`, this equality is never checked — the gem only proves "this body was HMAC'd with the app's `client_secret`," not "this body came from shop X." Since a single app-level `client_secret` is shared across every merchant install of the app (it is not per-shop), any unprivileged user who installs the app on their own store receives genuine webhooks with valid HMACs computed with that same shared secret. That user can then replay the body+HMAC pair while substituting the `X-Shopify-Shop-Domain` header for a victim shop's domain, and `Registry.process` will accept it as authentic and route it to the handler tagged with the victim's shop.

### Impact Explanation
This breaks the tenant boundary the gem is relied upon to enforce for webhook processing: `HmacValidator.validate` proves body integrity/authenticity, but the host application uses `request.shop` (unverified) to select the tenant session/data. An attacker who is merely another merchant using the same app can forge webhooks that are attributed to a different shop, which is a cross-tenant access primitive (Critical impact category: cross-tenant access) — e.g., causing an app to process attacker-controlled data (order/cart/customer payloads it fully controls) under a victim shop's identity, potentially triggering shop-scoped side effects (data writes, notifications, automated actions) keyed to the wrong tenant.

### Likelihood Explanation
Reachable by any unprivileged internet user: no access token, `client_secret`, or privileged account is required beyond installing the app themselves (a normal, unprivileged action), which yields legitimate signed webhook bodies. The only additional step is sending a POST to the app's webhook endpoint with the captured raw body/HMAC and a modified shop-domain header. No cryptographic secret needs to be recovered; the gap is structural (field excluded from the signed payload).

### Recommendation
Extend `VerifiableQuery`/`HmacValidator` usage for webhooks so that `shop` (and ideally `topic`/`webhook_id`) is included in the material that binds to the verified secret, or require the host application to cross-check `request.shop` against the shop associated with the session/subscription that registered the webhook before trusting it as the tenant identifier in `Registry.process`. At minimum, document and enforce that `request.shop` must be reconciled with a known, registered shop for the given webhook subscription rather than trusted at face value.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, completing OAuth normally (unprivileged, self-service).
2. The app registers a webhook subscription; Shopify sends a real webhook to the app's endpoint with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid HMAC over raw body B>`.
3. Attacker captures raw body `B` and its valid HMAC.
4. Attacker POSTs the same body `B` and HMAC to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `B` against the HMAC using the app's shared `client_secret` [4](#0-3)  — validation succeeds because `shop` is not part of the signed content [5](#0-4) .
6. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and attacker-controlled body content `B`, believing this is legitimate victim-shop data [6](#0-5) .

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
