### Title
Livestream GPU texture state is not cleared on `Event::Closed`, allowing stale biometric frames from a prior signup session to bleed into a new session view - ([File: src/agents/livestream/mod.rs])

### Summary
The livestream `Agent::run` event loop only clears GPU texture state (`gpu.clear_textures()` / `gpu.app.clear()`) when an explicit `Input::Clear` message is processed, not when `Event::Closed` fires. Consequently, when a connection is closed after signup A pushed frames into the shared `Gpu` state and a new connection is later accepted (`Event::Connected`) for an unrelated signup B, the render loop will immediately render and push signup A's still-resident IR/RGB/thermal/depth textures to the new viewer until signup B's own frames happen to overwrite them.

### Finding Description
In `src/agents/livestream/mod.rs`, the `Agent::run` loop maintains a single long-lived `gpu: Gpu` instance across the whole agent lifetime [1](#0-0) . Texture/app state is only reset inside the `Input::Clear` branch: [2](#0-1) 

The `Event::Closed` branch, by contrast, only drops the `Downstream` socket/pipeline reference and does nothing to the `gpu` state: [3](#0-2) 

Camera frame inputs (`Input::IrEyeFrame`, `Input::RgbFrame`, etc.) unconditionally update GPU textures regardless of whether a downstream is currently connected [4](#0-3) , meaning these textures are the last frames observed from whichever signup happened to be running when the previous connection closed.

On the next `Event::Connected(addr)`, a fresh `Downstream` is created and, at the bottom of the same loop iteration (and on every subsequent iteration before the next camera frame input arrives), `gpu.render(events, ...)` is called and its output is pushed to the newly attached downstream using whatever textures are currently loaded in `gpu`: [5](#0-4) 

Because `Input::Clear` is a distinct, separately-dispatched message (sent from orchestration code, e.g. `src/plans/mod.rs`) and is not guaranteed to be processed strictly between `Event::Closed` and the next `Event::Connected` on this same single-threaded port loop, a race/ordering window exists where a second unrelated signup's viewer connects and receives rendered frames sourced from the first signup's stale `camera_ir_eye_frame`/`camera_rgb_frame`/etc. textures before any `Clear` or new frame for the second signup has been applied.

### Impact Explanation
This is a cross-signup biometric data disclosure: an observer connected to the livestream downstream port for signup B can be shown IR-eye/IR-face/RGB/thermal/depth camera frames that actually belong to a different, unrelated signup A, because the shared GPU texture cache is not deterministically reset on connection teardown/re-establishment, only on an explicit and separately-ordered `Input::Clear` message. This violates the session-isolation invariant that no biometric frame from one signup should ever be observable during another signup's session.

### Likelihood Explanation
The precondition is two sequential signups where the orchestration code's `Input::Clear` is not guaranteed (by the type system or the agent loop) to be applied before the next `Event::Connected`/frame update — it is only guaranteed at agent startup (`gpu.clear_textures()` in `Agent::run` initialization) and whenever explicitly sent as a separate port message. Since `Input::Clear` is delivered through the same single `port::Inner<Self>` channel as all other inputs and interleaved with `Event`s from a completely separate `Upstream` source, there is no cross-source ordering guarantee enforced by the loop itself between "signup ended/cleared" and "new viewer connected." This makes the bleed timing-dependent but structurally real, not merely theoretical.

### Recommendation
Clear GPU texture/app state synchronously inside the `Event::Closed` handler (and/or on `Event::Connected`) in `src/agents/livestream/mod.rs`, rather than relying solely on a separately dispatched `Input::Clear` message, e.g.:
```rust
Either::Right(Some(Ok(Event::Closed))) => {
    downstream = None;
    gpu.clear_textures();
    gpu.app.clear();
}
```
and/or clear again when accepting a new connection, so that no render pushes stale textures to a newly connected viewer before that session's own frames arrive.

### Proof of Concept
Integration test plan for `src/agents/livestream/mod.rs`:
1. Start the `Agent` thread with a mock `Upstream`/`Downstream` harness.
2. Feed `Input::RgbFrame`/`Input::IrEyeFrame` with a distinguishable marker pattern ("signup A" pixels) into the port.
3. Emit `Event::Connected(addr_A)`, capture at least one rendered frame from `Downstream::push`, assert it contains "signup A" pixels.
4. Emit `Event::Closed` (simulate client disconnect) without sending `Input::Clear`.
5. Emit `Event::Connected(addr_B)` for a new, unrelated viewer.
6. Assert that the very first frame pushed to `addr_B`'s downstream does NOT contain "signup A" pixel data — expected to currently FAIL, proving the bleed, until `gpu.clear_textures()`/`gpu.app.clear()` is invoked synchronously on `Event::Closed`.
7. After the fix, re-run and assert the first frame rendered for `addr_B` is blank/cleared rather than showing signup A's stale texture.
