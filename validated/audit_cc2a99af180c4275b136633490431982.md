### Title
XRPL X-address with embedded destination tag paired with a separate `destinationMemo` causes tag divergence between validated address and sent memo - ([File: packages/intents-sdk/src/lib/validateAddress.ts])

### Summary
`validateXrpAddress` accepts XRPL X-addresses via `xrp_isValidXAddress`, which embed a destination tag inside the address encoding itself. `createWithdrawMemo` in `poa-bridge-utils.ts` builds `WITHDRAW_TO:<address>:<xrpMemo>` using the raw X-address string plus the separately-supplied `destinationMemo`/`xrpMemo`, without ever decoding the X-address to extract or reconcile its embedded tag.

### Finding Description
The broken equality: (validated destination = address + embedded tag from `isValidXAddress`) should equal (paid destination = address string + explicit `xrpMemo` sent to relayer via `WITHDRAW_TO:...` memo). They do not necessarily match.

- `validateXrpAddress` at [1](#0-0)  returns true for both classic `r...` addresses and X-addresses (`xrp_isValidXAddress`). X-addresses encode a destination tag (0 to 2^32-1, or "no tag") inside their base58 payload.
- `createWithdrawMemo` at [2](#0-1)  takes `receiverAddress` (the raw, possibly-X-address string) and `xrpMemo` (`destinationMemo`), and simply concatenates them as `WITHDRAW_TO:<receiverAddress>:<xrpMemo>` if `xrpMemo` is non-empty — it never calls `xAddressToClassicAddress` (or similar) to decode the embedded tag, and never checks whether the X-address's embedded tag conflicts with the externally supplied `destinationMemo`.
- `createWithdrawIntentPrimitive` at [3](#0-2)  is the caller that wires `destinationAddress`/`destinationMemo` straight through to `createWithdrawMemo`.

Attacker/caller input: `destinationAddress` = a valid XRPL X-address encoding tag `999` (e.g. `X7AcgcsY...` derived from classic address + tag 999), `destinationMemo` = `"111"`.
- `validateAddress(address, Chains.XRPL)` returns `true` (valid X-address format).
- The relayer/PoA bridge receives memo `WITHDRAW_TO:<X-address raw string>:111`. The relayer's actual XRP payment logic uses whichever tag it derives — if it decodes the X-address itself, it uses `999`; the memo passed also literally contains `111`. Either way, two different tag values are embedded/transmitted for the same destination with no reconciliation or rejection at the SDK layer.
- No code path in `validateAddress.ts` or `poa-bridge-utils.ts` decodes the X-address to compare its internal tag against `destinationMemo`, so validation never flags the conflict.

### Impact Explanation
If an exchange or wallet decodes the X-address's embedded tag (`999`) while a downstream system uses the literal memo string (`111`) — or vice versa depending on how the receiving system parses the `WITHDRAW_TO` memo — funds can be credited under the wrong destination tag at the receiving custodian, which is typically unrecoverable on XRPL (tag-based routing at custodians has no on-chain recourse). This matches "funds delivered to a wrong address/chain/contract with no recovery" — Critical severity. It is repeatable on every withdrawal call where a caller supplies an X-address together with a non-empty `destinationMemo`.

### Likelihood Explanation
Preconditions: caller (an ordinary SDK user/integrator forwarding a `destinationAddress`) must supply an XRPL X-address (a legitimate, standard, self-describing address format that is valid per `isValidXAddress`) plus a non-empty `destinationMemo`. No privileged access is needed — this is a normal public call to the withdrawal-creation function with a well-formed X-address, which the SDK explicitly accepts as valid. The attacker cost is zero (constructing a well-formed X-address with an arbitrary tag is trivial via `ripple-address-codec`), and the divergence is triggered on every such call.

### Recommendation
When the address is XRPL and is an X-address, decode it (e.g., `xAddressToClassicAddress`) to extract its embedded tag. If a `destinationMemo` is also supplied and differs from the decoded tag, reject with an explicit error rather than silently proceeding with an ambiguous input. If only the X-address's tag should be authoritative, convert the X-address to its classic form + tag internally and use that tag for the memo, discarding a conflicting caller-supplied `destinationMemo`. At minimum, `createWithdrawMemo`/`validateXrpAddress` should never let two contradictory tag values reach the relayer without an explicit, hard failure.

### Proof of Concept
```ts
import { describe, it, expect } from "vitest";
import { xAddressToClassicAddress, classicAddressToXAddress } from "ripple-address-codec";
import { validateAddress } from "../src/lib/validateAddress";
import { Chains } from "../src/lib/caip2";
// createWithdrawMemo is not exported; test via createWithdrawIntentPrimitive
import { createWithdrawIntentPrimitive } from "../src/bridges/poa-bridge/poa-bridge-utils";

describe("XRPL X-address tag divergence", () => {
  it("accepts X-address with embedded tag 999 but sends memo with tag 111 with no conflict error", () => {
    const classicAddress = "rDsbeomae4FXwgQTJp9Rs64Qg9vDiTCdBv";
    const xAddress = classicAddressToXAddress(classicAddress, 999, false); // encodes tag=999

    // Side A: validated destination truth (address + embedded tag)
    expect(validateAddress(xAddress, Chains.XRPL)).toBe(true);
    const decoded = xAddressToClassicAddress(xAddress);
    expect(decoded.tag).toBe(999);

    // Side B: what actually gets paid — memo built from raw X-address + explicit destinationMemo
    const intent = createWithdrawIntentPrimitive({
      assetId: "nep141:xrp.omft.near", // XRP asset id placeholder
      destinationAddress: xAddress,
      destinationMemo: "111",
      amount: 1000n,
    });

    // BUG: memo carries tag "111" while the X-address itself encodes tag 999 —
    // no error is thrown, and the two tag values diverge silently.
    expect(intent.memo).toBe(`WITHDRAW_TO:${xAddress}:111`);
    expect(intent.memo).not.toContain("999"); // embedded tag is dropped entirely
  });
});
```

function createWithdrawMemo({
	receiverAddress,
	xrpMemo,
}: {
	receiverAddress: string;
	xrpMemo: string | undefined;
}) {
	// Strip "bitcoincash:" prefix from BCH CashAddr addresses
	const normalizedAddress = receiverAddress
		.toLowerCase()
		.startsWith("bitcoincash:")
		? receiverAddress.slice("bitcoincash:".length)
		: receiverAddress;

	const memo = ["WITHDRAW_TO", normalizedAddress];

	if (xrpMemo != null && xrpMemo !== "") {
		memo.push(xrpMemo);
	}

	return memo.join(":");
}
