Confirmed: `CallDispatcher.dispatch()` has zero access control — it's `external` with no caller restriction whatsoever [1](#0-0)  and `ICallDispatcher.dispatch` is declared explicitly as dispatching "untrusted calls" [2](#0-1) . This is deployed as a single shared singleton reused across `IntentGatewayV2`, `HyperFungibleToken`, `WrappedHyperFungibleToken`, etc. [3](#0-2) , and multiple legitimate flows transiently route real ETH/ERC20 value through it before sweeping it back in the same transaction [4](#0-3) [5](#0-4) .

### Title
Unauthenticated `CallDispatcher.dispatch()` lets anyone drain any ETH/ERC20 balance temporarily held by the shared dispatcher - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher` is a shared, singleton utility contract used by `IntentGatewayV2`, `HyperFungibleToken`, `WrappedHyperFungibleToken` and their upgradeable variants to execute arbitrary attacker/solver-supplied `Call[]` batches during predispatch/postdispatch swap flows and calldata-bearing bridge transfers. Its `dispatch(bytes memory encoded)` function is `external` with no access-control modifier, no caller allowlist, and no `onlyGateway`/`onlyHost` check of any kind.

### Finding Description
`dispatch` decodes an arbitrary `Call[]` from `encoded` and, for each entry, executes `to.call{value: call.value}(call.data)` from the `CallDispatcher`'s own context (using its own ETH and, implicitly, whatever ERC20 approvals/balances it happens to hold) [1](#0-0) . There is no restriction on who may call `dispatch` — any EOA or contract can call it directly, bypassing `IntentGatewayV2`/`HyperFungibleToken` entirely.

The contract is designed to hold real value, at least transiently: it has a `receive() external payable {}` explicitly to accept ETH [6](#0-5) , and legitimate flows deliberately push funds into it mid-transaction — e.g. `IntentGatewayV2.placeOrder` transfers `order.predispatch.assets` (native or ERC20) to the dispatcher before invoking `dispatch(order.predispatch.call)` [4](#0-3) , and `IntentsBase._execute` runs `order.output.call` through the dispatcher and only afterward sweeps whatever balance remains on it back to the gateway [5](#0-4) . `HyperFungibleToken`/`WrappedHyperFungibleToken` similarly forward minted/unlocked tokens through the same dispatcher when calldata is attached [7](#0-6) .

Because `dispatch` performs no accounting of "whose" funds are currently sitting in the contract and imposes no caller check, any adversary can, at any moment the dispatcher holds a nonzero ETH or ERC20 balance (from a stray direct transfer, a race between two flows, or any transaction that reverted/partially failed after moving funds in but before the sweep-back completed), call `dispatch()` directly with a crafted `Call[]` such as `{to: attacker, value: address(dispatcher).balance, data: ""}` or `{to: token, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, balance)}` to move that value to themselves. This is architecturally identical to the reported `RollerPeriphery` bug: a shared, unauthenticated contract that is documented/expected to briefly custody funds (`receive() external payable {}` "required for refunds" in `RollerPeriphery` vs. "Receive function to accept ETH transfers" in `CallDispatcher`), with a public function reachable by any unprivileged caller that lets them redirect that custodied value to themselves.

### Impact Explanation
Any ETH or ERC20 balance transiently or accidentally held by the shared `CallDispatcher` (used across every `IntentGatewayV2`, `HyperFungibleToken`, and `WrappedHyperFungibleToken` deployment on a chain) can be stolen by an unprivileged third party with a single unpermissioned call, with no signature, proof, or relayer involvement required — concrete theft of funds.

### Likelihood Explanation
`dispatch` requires zero privilege and is directly callable by any address; the only precondition is a nonzero balance on the dispatcher at call time, which is a normal and recurring condition given that multiple in-repo flows intentionally park funds there mid-transaction, and the contract explicitly accepts unsolicited ETH via `receive()`.

### Recommendation
Restrict `CallDispatcher.dispatch` to a known, trusted set of callers (e.g., an `onlyAuthorizedCaller` allowlist of the registered `IntentGatewayV2`/`HyperFungibleToken` instances configured at deployment), or make the dispatcher single-use/per-caller (e.g., deploy a fresh minimal-proxy dispatcher per transaction/call, or track and gate against the caller that funded it in the same call) so that an unrelated address can never redirect value that another flow deposited into the shared instance.

### Proof of Concept
1. Deploy `CallDispatcher` as shared by `IntentGatewayV2` on a chain (as in production configuration referenced by the docs).
2. Wait for/observe any transaction that transfers ETH or an ERC20 to the dispatcher address and has not yet executed its sweep-back call in the same transaction (e.g., a `placeOrder` with predispatch assets, or any direct/accidental transfer to the dispatcher's `receive()`).
3. As an unrelated attacker, call `CallDispatcher.dispatch(abi.encode(Call[]))` directly with `to = attacker`, `value = address(dispatcher).balance` for native ETH, or `to = token, data = abi.encodeWithSelector(IERC20.transfer.selector, attacker, IERC20(token).balanceOf(dispatcher))` for an ERC20 held by the dispatcher.
4. The call succeeds because `dispatch` performs no caller check — funds are redirected to the attacker.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.
