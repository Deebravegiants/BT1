### Title
`makeInnerSwapMessage` silently drops the app-fee `transfer` intent when net token deltas sum to zero - (File: `packages/internal-utils/src/utils/messageFactory.ts`)

### Summary
`makeInnerSwapMessage` builds a `transfer` intent for `appFee` and pushes it into a local `intents` array before computing `tokenDiff` from `tokenDeltas` [1](#0-0) . If the summed `tokenDiff` across all tokens ends up empty (all deltas net to zero), the function unconditionally returns `intents: []`, discarding the already-built app-fee `transfer` intent [2](#0-1) . This is confirmed purely by reading the function; the code path is exactly as described in the question.

### Finding Description
Broken equality: intents actually returned (`[]`, i.e., zero debits) ≠ intents that should be signed (`token_diff` + `transfer` for `appFee`, i.e., a non-zero fee debit to `appFeeRecipient`).

Code path: `intents` is initialized with the `token_diff` intent, then the `appFee`-derived `transfer` intent is conditionally pushed if `appFee.length` is non-zero [3](#0-2) . Afterward, `tokenDeltas` are aggregated into `tokenDiff`/`tokenDiffNum` [4](#0-3) . If every token's net delta cancels out to leave `tokenDiff` with zero keys (e.g., equal `+X`/`-X` on the same token, or deltas that mutually cancel across tokens), the function takes the early-exit branch and returns a fresh object with `intents: []`, completely ignoring the local `intents` array that already contains the fee `transfer` intent [2](#0-1) .

There is no guard inside this function that checks `appFee.length` before taking the early-return branch, and no caller-side validation was found in this repo's indexed code that prevents `tokenDeltas` from netting to zero while `appFee` is non-empty — `makeInnerSwapMessage` performs no cross-check between `appFee` and `tokenDiff`.

### Impact Explanation
If reached with a non-empty `appFee`, the caller ends up signing a completely empty intents message (`intents: []`), which the intents contract would presumably reject or treat as a no-op transaction, rather than a message that pays the computed `appFee` to `appFeeRecipient`. This means a solver/fee-recipient that was owed a fee gets nothing from that signed message — a fee that "should be collected" is silently dropped from what the user signs. This matches the "fee overcharge or a solver overpaid" / underpaid category the audit treats as High severity, since a party relying on the fee being included in the signed payload is left uncompensated with no indication of failure (the returned object is a "valid-looking" `Nep413DefuseMessageFor_DefuseIntents`).

### Likelihood Explanation
The defect itself is unconditionally present and trivially triggered by calling `makeInnerSwapMessage` directly with `tokenDeltas` that net to zero (e.g. `[["foo.near", 100n], ["foo.near", -100n]]`) and non-empty `appFee` — this is confirmed by static code reading with no external dependency. However, I could not locate, within this repo's indexed source, a production call site of `makeInnerSwapMessage` other than its own unit tests; every other reference is in `messageFactory.test.ts` and `prepareBroadcastRequest.test.ts` [5](#0-4) . This means I cannot confirm from the indexed code whether any real, attacker-reachable swap flow constructs `tokenDeltas` that can net to exactly zero while simultaneously computing a non-zero `appFee` (a normal swap has `token_in ≠ token_out`, so a net-zero diff would require a same-token/self-swap quote or a specific aggregation edge case not visible in this search). This is a genuine limitation of index coverage/reachability analysis, not evidence that the path is unreachable. A full reachability confirmation (e.g., in the higher-level swap-building code that calls this function with real quote data) would require a Devin session with full repo access to trace all call sites, including any code outside the indexed portion.

### Recommendation
In `makeInnerSwapMessage`, when `Object.keys(tokenDiff).length === 0`, do not blindly return `intents: []`. Instead, filter out only the `token_diff` intent (or omit it) while preserving any already-constructed `appFee` transfer intent, e.g., return `intents: appFee.length ? intents.filter(i => i.intent !== "token_diff") : []`, or restructure the function to decide inclusion of the `token_diff` intent independently from the app-fee `transfer` intent, ensuring the fee intent is never dropped when `appFee.length > 0`.

### Proof of Concept
```ts
// packages/internal-utils/src/utils/messageFactory.test.ts
it("BUG: drops app fee transfer when net token deltas sum to zero", () => {
  const innerMessage = makeInnerSwapMessage({
    tokenDeltas: [
      ["foo.near", 100n],
      ["foo.near", -100n], // wash trade: nets to zero
    ],
    signerId: authHandleToIntentsUserId("user.near", "near"),
    deadlineTimestamp: 1704110400000,
    appFee: [["baz.near", 30n]],
    appFeeRecipient: "app_fee_mock.near",
  });

  // Equality that should hold: debits signed for appFeeRecipient === appFee amount (30n baz.near)
  const feeIntent = innerMessage.intents.find(
    (i) => i.intent === "transfer" && i.receiver_id === "app_fee_mock.near",
  );

  // Currently: innerMessage.intents === [] and feeIntent === undefined,
  // even though appFee (30n baz.near) was computed and should have been signed.
  expect(innerMessage.intents).toEqual([]); // demonstrates the bug
  expect(feeIntent).toBeUndefined(); // fee intent silently dropped
});
```
No HTTP mocking is required since `makeInnerSwapMessage` is a pure function; the test directly demonstrates that a non-empty `appFee` is silently omitted from the returned `intents` whenever `tokenDeltas` net to zero.
