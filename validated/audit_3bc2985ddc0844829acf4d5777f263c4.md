This confirms the vulnerability: `Registry.process` in `lib/shopify_api/webhooks/registry.rb` only validates the raw body against the HMAC signature, and separately trusts the `shop-domain`, `topic`, and `webhook-id` headers verbatim when constructing `WebhookMetadata` for the handler.This confirms the finding: the docs explicitly claim `Registry.process` "will verify the request did indeed come from Shopify," but only the raw body is HMAC-verified, and the `shop` field handed to the handler is trusted straight from an unauthenticated header — this is exactly the "field acted on but not covered by the HMAC" identity-binding break.

### Title
Webhook `shop` domain is trusted from an unauthenticated header while only the raw body is HMAC-verified, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking the HMAC signature over the raw HTTP body [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` values that are forwarded to the app's handler come from HTTP headers that are never included in the signed content — `Request#to_signable_string` returns only `@raw_body` [2](#0-1) , and `HmacValidator.validate` computes/compares the signature purely against that signable string [3](#0-2) . The `shop`, `topic`, and `webhook_id` accessors simply read directly from attacker-controllable headers [4](#0-3) .

### Finding Description
The binding that should hold is: **shop authenticated by the HMAC == shop attributed to the webhook payload delivered to the app's handler**. In this gem that binding does not exist, because the HMAC is computed with the app's single, shop-independent `client_secret` (`Context.api_secret_key`) over the raw body only, and `shop`/`topic`/`webhook_id`/`api_version` are read verbatim from headers that are outside the signed content:

- `Request#hmac`, `#topic`, `#shop`, `#webhook_id`, `#api_version` all read from `@headers`, not from anything covered by the signature [5](#0-4) .
- `Registry.process` validates only the HMAC over the body, then immediately hands the header-derived `request.shop`, `request.topic`, etc. to the handler as trusted `WebhookMetadata` [6](#0-5) .
- `WebhookMetadata` is a typed struct that simply carries these fields through to the app's business logic unchanged [7](#0-6) .
- The gem's own documentation instructs developers to trust this process, stating it "will verify the request did indeed come from Shopify," implying the entire tuple (shop, topic, body) is authenticated, when only the body byte-string is [8](#0-7) .

Because `Context.api_secret_key` is the single app-level secret shared across every shop that has installed the app (the same secret used for all HMAC computations, as seen in `HmacValidator.validate` and in OAuth token exchange) [9](#0-8) , any user who installs the app for their own shop can receive a genuine, validly-HMAC-signed webhook body from Shopify. That user can then replay the identical raw body and HMAC header to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) header to name a different, victim shop that also uses the same app. `HmacValidator.validate` still succeeds (it only checks the body bytes against the shared secret), and `Registry.process` dispatches the forged `shop` value straight to the app's handler as if it were authenticated [6](#0-5) .

### Impact Explanation
Host applications are documented to key their per-tenant logic off `data.shop` (e.g., looking up the stored access token/session for that shop, or writing shop-scoped records) exactly as shown in the gem's own usage example (`shop_domain: data.shop`) [10](#0-9) . Because the gem asserts (and developers reasonably rely on) that `Registry.process` fully authenticates the webhook, an attacker who is merely an installed/trial merchant of the same app can inject attacker-controlled webhook bodies attributed to an arbitrary victim shop, achieving cross-tenant data injection into another merchant's webhook-processing pipeline — an authentication/tenant-binding bypass consistent with the Critical "cross-tenant access" category, since the identity check the gem is documented to perform ("verify the request did indeed come from Shopify" for *this* shop) does not actually bind the shop identity to the signed content.

### Likelihood Explanation
Likelihood is high for any app built on this gem that (a) allows self-serve or trial installation (an "unprivileged internet user" can install the app for a shop they control) and (b) trusts `WebhookMetadata#shop` as gem-authenticated, which is exactly what the gem's own documentation encourages. No access token, leaked credential, or privileged account is required — only the ability to install the app on one's own shop and capture/replay one legitimate webhook delivery while altering headers.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-signed content, or independently bind `request.shop` to a per-shop secret/session known to the app before trusting it, rather than relying on an unauthenticated header. At minimum, update `Request#to_signable_string` and `HmacValidator` so identity-relevant headers are covered by the signature, and update the documentation to no longer claim the shop is verified when it is not.

### Proof of Concept
1. Attacker installs the target app for `attacker-shop.myshopify.com` (a normal, unprivileged install).
2. Shopify sends a legitimate webhook to the app: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` using the app's shared `client_secret`), `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker replays the exact same body `B` and header `X-Shopify-Hmac-Sha256: H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim-shop.myshopify.com", hmac: H...})` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and succeeds (same body, same secret) [1](#0-0) .
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` [11](#0-10)  and processes attacker-supplied data as if it legitimately originated from `victim-shop.myshopify.com`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
