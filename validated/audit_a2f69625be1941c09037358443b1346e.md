### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signature only over the raw HTTP body, while the `shop`, `topic`, `webhook_id`, and `api_version` fields used to route and identify the tenant are read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates only that the body's HMAC is correct, then hands the handler a `WebhookMetadata` object whose `shop` field is taken verbatim from the (unsigned) `x-shopify-shop-domain` header. This breaks the identity binding `bytes verified == bytes trusted`: the bytes covered by the HMAC (body) are not the bytes the host application uses to identify the tenant (`shop` header).

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` (and `topic`, `webhook_id`, `api_version`) are pulled straight from headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate`, which calls `verifiable_query.to_signable_string` (i.e., body-only) and compares against `verifiable_query.hmac`: [3](#0-2) 

After this body-only check passes, `Registry.process` immediately constructs `WebhookMetadata` using `request.shop` — the unauthenticated header value — and passes it to the app's handler: [4](#0-3) 

`WebhookMetadata#shop` is a plain `String` field with no further validation: [5](#0-4) 

**Why this is exploitable, not just theoretical:** the HMAC secret (`Context.api_secret_key`) is the app's `client_secret`, which is identical for every shop that installs the app — it is not tenant-specific. Any unprivileged internet user who can install (or already has) the app on their own shop receives genuine webhooks from Shopify, each with a valid HMAC computed with that shared secret over the raw body. Because the `shop-domain` header is excluded from the signed bytes, that same attacker can capture one such genuine `(raw_body, hmac)` pair and replay it against the app's webhook endpoint while substituting the `x-shopify-shop-domain` header (and/or `x-shopify-webhook-id`/`x-shopify-topic`) to name a different, victim shop. `HmacValidator.validate` will report the signature as valid (it only checks the body), and `Registry.process` will dispatch the handler with `WebhookMetadata.shop` set to the victim's domain while `body` actually contains the attacker's own shop's data.

This is the same class of bug as the reported issue: an identity/tenant-selector field (`asset_mint` in the PDA / here, `shop` in `WebhookMetadata`) is not bound by the authenticator (PDA seeds / here, the HMAC) that is supposed to enforce per-tenant isolation, letting one tenant's authenticated artifact be relabeled to another tenant.

### Impact Explanation
Any Rails/host application built on this gem's documented `Webhooks::Registry.process` flow (as shown in `docs/usage/webhooks.md`) trusts `WebhookMetadata#shop` to select the correct shop's session/store record for persisting webhook data (order updates, uninstall events, GDPR events, etc.). Because `shop` is not bound to the signed payload, an attacker who has legitimate access to any single shop that installs the app can forge webhook deliveries that appear to originate from an arbitrary victim shop domain, injecting attacker-controlled body content under the victim's tenant identity. This is a cross-tenant data-integrity/spoofing vulnerability directly reachable through this gem's own webhook-processing API, matching the "cross-tenant access" impact category.

### Likelihood Explanation
High likelihood for any app that follows the gem's documented webhook-processing pattern (`docs/usage/webhooks.md`, `Registry.process`). The only prerequisite is that the attacker has (or creates) one shop where the app is installed so they can observe a valid `(body, hmac)` pair signed with the app's shared `client_secret`-derived key — no access to the victim's credentials, TLS interception, or the app's `client_secret` itself is required. The attacker merely replays a signed body while altering the `x-shopify-shop-domain`/`x-shopify-webhook-id` headers, which the gem never authenticates.

### Recommendation
Bind the tenant/identity headers into the HMAC-verified surface, or otherwise cryptographically or contextually validate `shop`/`webhook_id`/`topic` before trusting them:
- Include `shop-domain` (and ideally `topic`, `webhook-id`) in `to_signable_string`, matching how Shopify's own webhook signature scheme could be extended, or
- Require host applications to cross-check `request.shop` against an independently known, previously-registered shop for the given `webhook_id`/subscription before processing, and document this requirement prominently since the current docs (`docs/usage/webhooks.md`) do not mention that `shop` is unauthenticated.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`. Shopify delivers a legitimate webhook to the app's endpoint with headers:
   - `x-shopify-shop-domain: attacker.myshopify.com`
   - `x-shopify-hmac-sha256: <valid HMAC of raw_body>`
   - `x-shopify-topic: orders/create`
2. Capture the raw POST body and the `x-shopify-hmac-sha256` value.
3. Replay the identical request to the same endpoint, but replace the header:
   - `x-shopify-shop-domain: victim.myshopify.com`
   Leave the body and HMAC header unchanged.
4. Server-side, `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `request.to_signable_string` (the raw body) — this succeeds because the body wasn't modified: [6](#0-5) 
5. `Registry.process` then builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` with `shop == "victim.myshopify.com"`, and invokes the app's handler as if the (attacker-supplied) body data belongs to the victim shop: [4](#0-3) 

This confirms the identity binding `HMAC-verified bytes == trusted shop identity` does not hold, allowing cross-tenant webhook spoofing without any credential leak or access to the app's `client_secret`.
