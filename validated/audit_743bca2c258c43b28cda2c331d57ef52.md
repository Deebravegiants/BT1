### Title
Unfilled zero-amount output transfer in `_fillCrossChain` can permanently block order fills for tokens that revert on zero-value transfers - (File: evm/src/apps/intentsv2/ExtrinsicIntents.sol)

### Summary
`ExtrinsicIntents._fillCrossChain` unconditionally calls `safeTransferFrom` for the "required + beneficiary surplus" portion of every output asset in an order, without checking that the amount is non-zero. Because the output asset list (`order.output.assets`) is defined by the (unprivileged) order creator when the order is placed, and can name an arbitrary ERC20 token including one whose `totalRequired` is `0` and which reverts on zero-value transfers, the fill call for that order can be made to always revert, exactly the bug class described in the external report for `ExtraRewardStashV2.stashRewards()`.

### Finding Description
In `_fillCrossChain` (evm/src/apps/intentsv2/ExtrinsicIntents.sol, lines 164-220), each entry of `order.output.assets` is processed in a loop: [1](#0-0) 

For a non-native token, `IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare)` is executed with no guard on the transferred amount being greater than zero — unlike the immediately following `protocolShare` transfer, which is explicitly gated by `if (protocolShare > 0)`. `totalRequired` comes straight from `order.output.assets[i].amount`, a value fully controlled by whoever placed the order (any unprivileged caller of `placeOrder`), and `token` is likewise an arbitrary externally-controlled ERC20 address, not vetted by the protocol.

If an order includes an output asset with `totalRequired == 0` (e.g., a placeholder/optional output slot) and the solver correspondingly supplies `solverAmount == 0` for that asset (which is not rejected, since the check `solverAmount < totalRequired` only reverts when the solver under-supplies), then `beneficiaryShare` also resolves to `0` via `_splitSurplus`, and the code calls `safeTransferFrom(..., ..., 0)` unconditionally. If `token` is a "weird" ERC20 that reverts on zero-value transfers, this call — and therefore the entire `_fillCrossChain` transaction — reverts every time, for every solver, for that specific order.

This is structurally identical to the reported bug: an externally-controlled token list feeding an un-guarded, potentially-zero token transfer that can be made to always revert, permanently disabling a piece of base functionality (order fulfillment) for the affected order.

### Impact Explanation
Because `_filled[commitment] = msg.sender` is only committed to storage after the loop completes without reverting, a cross-chain order carrying such a poisoned zero-amount output asset can never be filled by any solver. The order's escrowed input tokens (`order.inputs`) remain locked in the source-chain gateway's `_orders` mapping until the order's deadline passes and cancellation is separately triggered via `_cancelFromSource`/`_cancelFromDest`. Until then, funds are effectively frozen and the base "fill" functionality of the IntentGateway is unusable for that order — matching the medium-severity characterization in the original report ("reward/base functionality gathering... availability... affected").

### Likelihood Explanation
Triggering this requires only that an order creator (any unprivileged user calling `placeOrder`) construct an order with an output asset entry of amount `0` denominated in a real-world token that reverts on zero-value ERC20 transfers (a documented weird-ERC20 behavior class, see https://github.com/d-xo/weird-erc20#revert-on-zero-value-transfers). No special privileges, governance, or malicious relayer/operator involvement is needed — the path is reachable directly from a single `fillOrder`/`_fillCrossChain` call driven by data the placer of the order fully controls.

### Recommendation
Guard the primary output transfer the same way the protocol-share transfer is already guarded:
```solidity
uint256 beneficiaryTotal = totalRequired + beneficiaryShare;
if (beneficiaryTotal > 0) {
    IERC20(token).safeTransferFrom(msg.sender, beneficiary, beneficiaryTotal);
}
if (protocolShare > 0) {
    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
}
```
Consider applying the same zero-amount skip pattern already used in `_fillSameChain` (`if (remaining == 0 || solverAmount == 0) continue;`) and in `IntentsBase._withdraw` (`if (amount == 0) continue;`) consistently across all token-moving loops in the intents module.

### Proof of Concept
1. Order creator calls `placeOrder` with an `output.assets` array containing at least one entry where `token` is a "revert-on-zero-transfer" ERC20 and `amount == 0` (a legitimate zero-value placeholder output entry alongside other non-zero outputs). [2](#0-1) 
2. A solver calls the fill entrypoint leading to `_fillCrossChain`, supplying `options.outputs[i].amount == 0` for that asset (satisfies `solverAmount < totalRequired` check since both are `0`).
3. `totalRequired + beneficiaryShare` evaluates to `0`; `IERC20(token).safeTransferFrom(msg.sender, beneficiary, 0)` is called unconditionally and reverts because the token disallows zero-value transfers.
4. The whole `_fillCrossChain` transaction reverts. Every solver attempting to fill this order hits the same revert, so the order can never be filled and its escrowed inputs stay frozen until deadline-based cancellation.
