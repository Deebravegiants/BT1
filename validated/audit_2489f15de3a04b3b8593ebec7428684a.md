Confirmed: the webhook HMAC only covers the raw body, while `shop` (and `topic`, `webhook_id`) are taken from unauthenticated headers and passed downstream to handlers as trusted tenant identity.### Title
Webhook shop identity is not covered by the HMAC signature, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signature over the raw body only, while the `shop` (tenant identity), `topic`, and `webhook_id` are taken from unauthenticated HTTP headers. `Registry.process` validates only the body's HMAC and then forwards the header-derived `shop` value to the app's webhook handler as trusted tenant identity, breaking the binding `shop authenticated == shop the payload is attributed to`.

### Finding Description
`Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 

`Request#shop` (and `topic`, `webhook_id`) are read straight from request headers, which are attacker-controllable when a request is forwarded/replayed to the app's webhook endpoint: [2](#0-1) 

`HmacValidator.validate` computes the signature purely from `to_signable_string` (i.e., the body) and the app's shared `api_secret_key`: [3](#0-2) 

`Registry.process` accepts the request once this body-only HMAC check passes, then constructs `WebhookMetadata` using the unauthenticated `request.shop` value and hands it to the registered handler as the trusted tenant identifier: [4](#0-3) 

Because the api_secret_key is a single shared secret for the whole app (not per-shop), and the signature never binds to the shop, any body+HMAC pair that was legitimately generated for one shop (e.g., a merchant who installed the app and triggered their own webhook, receiving a validly-signed payload) remains a fully valid signature when replayed with a different `X-Shopify-Shop-Domain` / `shopify-shop-domain` header. The gem has no mechanism to detect this substitution, since the shop is never part of the signed material.

This is exactly the class of bug in the report generalized to this codebase: a field that the code acts on (`shop`, used as the tenant key by `WebhookMetadata`/handlers) is not covered by the integrity check (the HMAC), so the verified bytes (body) and the trusted bytes (headers) diverge — `verified(body) != trusted(shop)`.

### Impact Explanation
If a host application uses `WebhookMetadata#shop` to decide which merchant's data the webhook event applies to (the intended and documented use, per `docs/usage/webhooks.md`), an attacker who has legitimate access to any shop that installed the app can capture their own real, validly-signed webhook and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop. `Registry.process` will accept the payload as authentic (HMAC checks out) and dispatch it as if it originated from the victim shop. This is a cross-tenant identity confusion: an unprivileged, un-victim-related actor can inject data/events attributed to another tenant, satisfying the "cross-tenant access" impact bar.

### Likelihood Explanation
Requires the attacker to be an installed user of the target app (no special privilege, no access to `api_secret_key`, no TLS interception) — they simply need one authentic webhook delivery for their own shop, which is trivial to obtain by performing an action in their own store (e.g., creating an order). Replaying it with a modified header is a normal HTTP request. Likelihood is moderate-to-high for any app that keys tenant logic off `WebhookMetadata#shop` rather than an independently-verified value.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the material that is authenticated, or independently verify `request.shop` against a known/expected shop before trusting it (e.g., cross-check against an existing session's shop, or require the caller to also pass shop out-of-band via a route parameter tied to session lookup) rather than trusting the raw header value once the body-only HMAC succeeds. At minimum, document prominently that `Request#shop` is unauthenticated and must not be used as a sole tenant-identity source by consuming applications.

### Proof of Concept
1. App installs on `shop-a.myshopify.com`; attacker controls this shop and triggers a webhook event (e.g., `orders/create`), receiving a legitimate delivery with body `B` and header `shopify-hmac-sha256: H` (H = HMAC-SHA256(api_secret_key, B)), plus `shopify-shop-domain: shop-a.myshopify.com`.
2. Attacker resends the exact same body `B` and `H` to the app's webhook endpoint but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim-shop.myshopify.com"...})` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` — validation succeeds [5](#0-4) .
4. `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: ..., ...)` is passed to the handler, which the host app treats as an authentic event for `victim-shop.myshopify.com` [6](#0-5) .
