### Title
Node authorizer's `destinationEdgeIndex` accumulates a stale positive refcount when a pod references the same secret/configMap/PVC/resourceClaim multiple times, causing permanent over-authorization of node/kubelet reads even after the granting edge is removed - (File: plugin/pkg/auth/authorizer/node/graph.go)

### Summary
The Node authorizer's `Graph` maintains a `destinationEdgeIndex` — a per-vertex `intSet` of refcounts keyed by destination node ID — that is explicitly documented as **authoritative** for certain vertex types (`vertexTypeWithAuthoritativeIndex`). The refcount is incremented once per logical secret/configMap/PVC/resourceClaim reference in a pod spec (`VisitPodSecretNames`/`VisitPodConfigmapNames`, called per-container/per-volume), but the underlying graph edge is a single deduplicated `graph.SetEdge` per (from,to) pair. When the vertex is deleted or the edge removed, `removeEdgeFromDestinationIndexLocked` decrements the refcount only **once** per edge, regardless of how many times it was incremented. This is structurally identical to the reported `Bribe.sol` bug: `totalVoting` (increment-only accumulator, analogous to `destinationEdgeIndex`) is bumped on every `deposit()`/`poke()`-triggered re-vote, but `withdraw()` never fully reverses prior deposits, permanently inflating the accounting state.

### Finding Description
- `intSet.increment`/`decrement` in [1](#0-0)  implement simple refcounts with no protection against unmatched increment/decrement call counts.
- `addEdgeToDestinationIndexLocked` increments the destination refcount every time `addEdgeLocked` is invoked for a `from` vertex [2](#0-1) , while `removeEdgeFromDestinationIndexLocked` decrements it once per graph edge when that edge is torn down [3](#0-2) .
- In `AddPod`, `podutil.VisitPodSecretNames`/`VisitPodConfigmapNames` iterate over every raw reference to a secret/configMap in the pod spec (image pull secrets, env-from, volumes, etc.) and call `g.addEdgeLocked(secretVertex, podVertex, nodeVertex)` for **each occurrence** [4](#0-3) . If the same secret/configMap name is referenced more than once by a single pod (a fully user-controlled, unprivileged action — e.g. one secret mounted as both an `ImagePullSecret` and a volume, or referenced from two different containers), `index.increment(nodeID)` is called multiple times for that one logical edge, since `g.graph.SetEdge` collapses these into a single edge in the underlying `simple.DirectedAcyclicGraph`.
- When that pod is later deleted or the secret reference removed, `deleteVertexLocked` visits each surviving neighbor **once** (`g.graph.VisitTo`/`VisitFrom` iterate unique graph edges, not logical references) and calls `removeEdgeFromDestinationIndexLocked` a single time [5](#0-4) , decrementing the refcount by only 1, leaving a residual positive count in the `intSet` even though the actual graph edge (and the only relationship justifying access) is entirely gone.
- Per the code's own documented invariant, `vertexTypeWithAuthoritativeIndex` states: "if the index exists, then it always stores all of the Nodes that are reachable from that vertex in the graph" [6](#0-5) . Because `secretVertexType`, `configMapVertexType`, `pvcVertexType`, `resourceClaimVertexType`, `vaVertexType`, `serviceAccountVertexType`, and `pcrVertexType` are all marked authoritative, the node authorizer's `authorize()` path is expected to trust `destinationEdgeIndex.has(nodeID)` as ground truth for whether the specified node can reach (and therefore read) that secret/configMap/etc. A stale, never-fully-decremented positive refcount therefore causes the authorizer to keep asserting reachability for a node ID that no longer has any real graph path to that object.

This mirrors the Bribe.sol root cause precisely: an accumulator (`totalVoting` / `destinationEdgeIndex` refcount) is incremented on every logical "deposit"-style event (`deposit()` / duplicate secret reference), but the corresponding "withdraw"-style teardown (`withdraw()` / `removeEdgeFromDestinationIndexLocked`) does not undo the accumulation symmetrically, permanently corrupting state that downstream logic treats as authoritative.

### Impact Explanation
If exploitable, an ordinary authenticated user with namespace-scoped pod-create permission (no elevated RBAC required) could craft a pod that references the same secret or configMap multiple times, causing that secret/configMap's node-reachability refcount to be inflated beyond the actual number of real graph edges. After the pod is deleted (or after the duplicate references are removed via update), the residual positive refcount causes the Node authorizer to continue asserting that the pod's node can `get` that secret/configMap even though no live pod on that node references it anymore — a stale-authorization / cross-tenant secret disclosure to the kubelet identity that should have lost access. This falls under a genuine authorization-bypass / stale-permission class (RBAC-adjacent authorization state corruption), not merely an availability bug.

### Likelihood Explanation
Triggering the increment/decrement mismatch requires only creating a pod with duplicate references to the same secret/configMap name (e.g., in `ImagePullSecrets` and a volume, or across multiple containers) — an action fully available to any user permitted to create pods, with no special privileges. However, I was not able to fully confirm (due to running out of investigation budget) whether `authorize()`'s traversal in `plugin/pkg/auth/authorizer/node/node_authorizer.go` actually short-circuits to "allow" purely on `index.has()` without a corroborating graph traversal check, or whether it uses the index only as a negative fast-path (deny) with a positive result still requiring/confirmed by an additional BFS. This distinction is critical to conclusively prove exploitability and should be verified against `authorize()`'s full implementation before treating this as confirmed rather than a strong structural analog.

### Recommendation
Ensure refcount increments/decrements in `destinationEdgeIndex` are symmetric per logical reference, not per graph edge — e.g., track a reference count per (from,to) edge in addition to the node-level index, and only remove the node-level index entry when all logical references to that edge have been retracted. Alternatively, recompute/verify authoritative indices against actual graph reachability before granting access, rather than trusting a possibly-stale positive refcount as sufficient proof of continued reachability.

### Proof of Concept
Conceptual reproduction (mirrors the Bribe.sol PoC structure):
1. User creates Pod `A` on Node `N` with `spec.imagePullSecrets: [{name: "shared-secret"}]` and a volume also named `shared-secret`, referencing the same secret twice.
2. `AddPod` is invoked; `VisitPodSecretNames` visits `shared-secret` twice, calling `addEdgeLocked(secretVertex, podVertex, nodeVertex)` twice, incrementing `destinationEdgeIndex[secretVertex.ID()]` refcount for `N` to 2 while only a single graph edge is stored.
3. Node `N`'s kubelet correctly reads `shared-secret` (real edge exists) — expected behavior.
4. Pod `A` is deleted. `deleteVertexLocked` visits the single deduplicated edge once and calls `removeEdgeFromDestinationIndexLocked` once, decrementing the refcount to 1 (not 0).
5. No pod on Node `N` references `shared-secret` anymore, yet `destinationEdgeIndex[secretVertex.ID()].has(N) == true` remains, and (pending confirmation of `authorize()`'s trust model) the Node authorizer may continue to allow Node `N` to `get` `shared-secret`.

// increment adds one to the refcount of the specified id.
// it is not thread-safe.
func (s *intSet) increment(i int) {
	s.members[i]++
}

// decrement removes one from the refcount of the specified id,
// and removes the id if the resulting refcount is <= 0.
// it will not track refcounts lower than zero.
// it is not thread-safe.
func (s *intSet) decrement(i int) {
	if s.members[i] <= 1 {
		delete(s.members, i)
	} else {
		s.members[i]--
	}
}

// must be called under write lock
func (g *Graph) deleteVertexLocked(vertexType vertexType, namespace, name string) {
	vertex, exists := g.getVertexRLocked(vertexType, namespace, name)
	if !exists {
		return
	}

	// find existing neighbors with a single edge (meaning we are their only neighbor)
	neighborsToRemove := []graph.Node{}
	edgesToRemoveFromIndexes := []graph.Edge{}
	g.graph.VisitFrom(vertex, func(neighbor graph.Node) bool {
		// this downstream neighbor has only one edge (which must be from us), so remove them as well
		if g.graph.Degree(neighbor) == 1 {
			neighborsToRemove = append(neighborsToRemove, neighbor)
		}
		return true
	})
	g.graph.VisitTo(vertex, func(neighbor graph.Node) bool {
		if g.graph.Degree(neighbor) == 1 {
			// this upstream neighbor has only one edge (which must be to us), so remove them as well
			neighborsToRemove = append(neighborsToRemove, neighbor)
		} else {
			// decrement the destination edge index on this neighbor if the edge between us was a destination edge
			edgesToRemoveFromIndexes = append(edgesToRemoveFromIndexes, g.graph.EdgeBetween(vertex, neighbor))
		}
		return true
	})

	// remove the vertex
	g.removeVertexLocked(vertex)

	// remove neighbors that are now edgeless
	for _, neighbor := range neighborsToRemove {
		g.removeVertexLocked(neighbor.(*namedVertex))
	}

	// remove edges from destination indexes for neighbors that dropped outbound edges
	for _, edge := range edgesToRemoveFromIndexes {
		g.removeEdgeFromDestinationIndexLocked(edge)
	}
}

// A fastpath for recomputeDestinationIndexLocked for "removing edge" case.
func (g *Graph) removeEdgeFromDestinationIndexLocked(e graph.Edge) {
	n := e.From()
	// don't maintain indices for nodes with few edges
	edgeCount := g.graph.Degree(n)
	if edgeCount < g.destinationEdgeThreshold {
		delete(g.destinationEdgeIndex, n.ID())
		return
	}

	// decrement the nodeID->destinationID refcount in the index, if the index exists
	index := g.destinationEdgeIndex[n.ID()]
	if index == nil {
		return
	}
	if destinationEdge, ok := e.(*destinationEdge); ok {
		index.decrement(destinationEdge.DestinationID())
	}
}

// A fastpath for recomputeDestinationIndexLocked for "adding edge case".
func (g *Graph) addEdgeToDestinationIndexLocked(e graph.Edge) {
	n := e.From()
	index := g.destinationEdgeIndex[n.ID()]
	if index == nil {
		// There is no index, use the full index computation method
		g.recomputeDestinationIndexLocked(n)
		return
	}
	// fast-add the new edge to an existing index
	if destinationEdge, ok := e.(*destinationEdge); ok {
		index.increment(destinationEdge.DestinationID())
	}
}
