### Title
Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook by validating only the raw request body against the `X-Shopify-Hmac-Sha256` header, but the `shop` value that the host application uses to attribute the event to a tenant is taken from a separate, unsigned header and is never bound to that signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `#shop` is read independently from the `shopify-shop-domain`/`x-shopify-shop-domain` header [2](#0-1) . `Registry.process` validates the HMAC over that same request object and, once it passes, builds `WebhookMetadata` using `request.shop` verbatim, then invokes the app's handler with it [3](#0-2) . Because `HmacValidator.validate` only checks `verifiable_query.to_signable_string` (the body) against the shared secret [4](#0-3) , the `shop` header is never part of what is authenticated — the equality the code implicitly (and incorrectly) assumes is:

`shop used for tenant attribution == shop cryptographically bound by HMAC`

but in reality:

`shop used for tenant attribution (header) ≠ any byte covered by the HMAC (body only)`

This is the same defect class as the reported bug (a value acted upon that isn't covered by the integrity check that is supposed to protect it), applied to the tenant-identifying field of the webhook pipeline instead of the borrow accounting field of the original report.

Any external actor who is a valid webhook sender for a shop they control (e.g., a developer with any real or free/dev Shopify store subscribed to the app) can capture one legitimately-signed webhook request generated by Shopify for their own shop, then replay it to the app's webhook endpoint with only the `shop-domain` header rewritten to a victim shop's domain. The HMAC — computed and verified only over the raw JSON body — remains valid, so `Registry.process` accepts the request and calls the host app's handler with `data.shop` set to the victim's domain while `data.body` is the attacker's own (or a captured) legitimate payload.

### Impact Explanation
Applications built on this gem's documented webhook API (as shown in `docs/usage/webhooks.md`) key their tenant-scoped side effects — enqueuing jobs, updating merchant-specific state, or making Admin API calls on behalf of "the shop" — directly on `data.shop`. Because this gem hands the handler an unauthenticated shop value, a spoofed webhook can make the host app perform actions attributed to a shop the attacker doesn't control, i.e., cross-tenant confusion/spoofing of the identity binding this gem is expected to guarantee once `HmacValidator.validate` returns true.

### Likelihood Explanation
Exploitation requires only: (1) the ability to send arbitrary HTTP requests to the app's public webhook endpoint (unprivileged internet access), and (2) possession of one validly-signed webhook body/HMAC pair, which is trivially obtainable by installing the target app on any store the attacker controls (including a free development store) and capturing Shopify's own webhook delivery. No access token, `client_secret`, or privileged account is needed — the same shared secret already used for all merchants signs the body regardless of which shop header accompanies it.

### Recommendation
Bind the shop identity to the authenticated payload instead of trusting the header value at face value: include `shop` (and ideally `topic`/`webhook_id`) as part of the signable content that `HmacValidator` verifies, or independently verify header-derived tenant identifiers against a value embedded in the signed body/JWT-equivalent construct before constructing `WebhookMetadata`. At minimum, document prominently that `data.shop` is unauthenticated and must not be trusted for tenant-scoped authorization decisions without additional verification by the host app.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a store they control) and triggers a webhook event (e.g., `orders/create`), capturing the exact `raw_body` and the `x-shopify-hmac-sha256` value Shopify sends.
2. Attacker replays this exact HTTP request to the same public webhook endpoint, keeping `raw_body` and the HMAC header unchanged, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `HmacValidator.validate` recomputes the HMAC over `raw_body` only [5](#0-4)  — it matches, since the body wasn't changed.
4. `Registry.process` proceeds and calls the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` [6](#0-5) , causing the host app to act as if the event genuinely originated from the victim shop.
