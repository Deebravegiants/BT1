### Title
Request-level headers can override `x-exodus-*` identity headers set by `setDefaultExodusIdentifierHeaders` - ([File: adapters/fetch-factory/src/fetch-factory.js])

### Summary
`FetchFactory#buildHeaders` applies headers in the order GLOBAL_HOST → matched domain (which includes the `x-exodus-app-id`/`x-exodus-version`/`x-requested-with` values set by `setDefaultExodusIdentifierHeaders`) → caller-supplied `existingHeaders`, using `Headers.set()`, which always overwrites the previous value for the same key. Since the caller-supplied headers (`opts.headers` for string/URL URLs, and both `Request.headers` and `opts.headers` for `Request` inputs) are applied last with no exclusion list, any code invoking the fetch function returned by `create()` can freely overwrite the exodus identity headers for requests to `exodus.io`.

### Finding Description
In `#buildHeaders` [1](#0-0) , the identifier headers set via `setDefaultExodusIdentifierHeaders` [2](#0-1)  are stored under `this.headerConfigs[EXODUS_HOST]` and applied to the `Headers` object before `existingHeaders` is applied. The final block:
```js
if (existingHeaders) {
  new Headers(existingHeaders).forEach((value, key) => {
    headers.set(key, value)
  })
}
```
overwrites any previously-set header with the same (case-insensitive) name, including `x-exodus-app-id`, `x-exodus-version`, and `x-requested-with`. The same overwrite-last pattern also applies in the `Request` branch of `create()` [3](#0-2) , where `urlOrRequest.headers` are applied after the built-in headers, and `opts.headers` are applied last on top of that. There is no allowlist/denylist preventing `opts.headers` or `Request.headers` from touching the exodus identifier keys — unlike `setHeaders`, which enforces a whitelist for globally-set default headers [4](#0-3) , no such protection exists for per-request overrides in `#buildHeaders`/`create()`.

The existing test suite in fact documents and asserts this override-friendly behavior for arbitrary custom headers (`'options headers take precedence over Request headers'`) [5](#0-4) , but there is no test verifying the exodus identifier headers specifically resist request-level override — and based on the code, they would not.

### Impact Explanation
If a caller of the fetch function returned by `create()` is influenced by attacker-controlled input (e.g., a dapp-facing RPC layer, or any code path that forwards attacker-supplied headers into `opts.headers` for a request to `exodus.io`), the attacker can overwrite `x-exodus-app-id`, `x-exodus-version`, and `x-requested-with` with arbitrary values. If backend services key trust decisions, feature-flag eligibility, or verification levels off these headers, this allows spoofing of client identity/version, potentially unlocking behavior gated behind a specific app build. This is scoped strictly to the `FetchFactory` header-merging logic itself; it does not by itself demonstrate wallet key compromise, but it does demonstrate a forgeable identity signal for any backend that trusts these headers.

### Likelihood Explanation
Exploitability depends entirely on whether any concrete call site in the codebase passes attacker-influenced values into `opts.headers` (or as a `Request`'s headers) for requests going to `exodus.io` through a `FetchFactory` instance that has called `setDefaultExodusIdentifierHeaders`. I was unable to locate, within the indexed codebase, an actual production call site where `FetchFactory.create()` is invoked with headers derived from untrusted/dapp-controlled input for `exodus.io` requests — the only located usages are in tests [6](#0-5)  and in `sdks/headless/__tests__/adapters/fetch.js`. The parallel "shim" implementations in `apps/sdk-playground` and `apps/sdk-minimal-demo` [7](#0-6) [8](#0-7)  exhibit the identical overwrite pattern (`{ ...DEFAULT_FETCH_HEADERS, ...opts.headers }`), confirming this is a consistent design pattern across the codebase rather than an isolated bug, but I could not confirm from the index whether `opts.headers` in these call paths is ever attacker-reachable (vs. only internally set by trusted app code). Without a confirmed reachable path from unprivileged dapp/RPC/deeplink input into these `opts.headers`, the "attacker-influenced" precondition required by the question cannot be verified from available context.

### Recommendation
In `#buildHeaders` (and in the `Request` branch of `create()`), after merging `existingHeaders`, re-apply the `EXODUS_HOST`-scoped identifier headers (`x-exodus-app-id`, `x-exodus-version`, `x-requested-with`) as a final, non-overridable step for hosts matching `EXODUS_HOST`, or explicitly strip these keys from `existingHeaders`/`Request.headers` before merging, mirroring the whitelist-enforcement approach already used in `setHeaders`.

### Proof of Concept
```js
// adapters/fetch-factory/__tests__/exodus-identifier-override.test.js
import { FetchFactory, hosts } from '../src/index.js'

test('request-level headers cannot override exodus identifier headers', async () => {
  const fetchFn = async (url, opts) => Object.fromEntries(opts.headers)
  const fetchFactory = new FetchFactory(fetchFn)

  fetchFactory.setDefaultExodusIdentifierHeaders({
    appId: 'real-id',
    appVersion: '1.0.0',
    appBuild: 'real-build',
  })

  const result = await fetchFactory.create()('https://exodus.io/api', {
    headers: { 'x-exodus-version': 'spoofed-version', 'x-exodus-app-id': 'spoofed-id' },
  })

  // Expected (fails today): identifier headers remain the ones set via
  // setDefaultExodusIdentifierHeaders regardless of request-level headers.
  expect(result['x-exodus-version']).toBe('1.0.0')
  expect(result['x-exodus-app-id']).toBe('real-id')
})
```
Given the current implementation, this test would fail because `result['x-exodus-version']` would be `'spoofed-version'`, confirming the override is possible.

  setDefaultExodusIdentifierHeaders({ appId, appVersion, appBuild }) {
    if (!this.headerConfigs[EXODUS_HOST]) {
      this.headerConfigs[EXODUS_HOST] = Object.create(null)
    }

    this.headerConfigs[EXODUS_HOST] = {
      ...this.headerConfigs[EXODUS_HOST],
      'x-exodus-app-id': appId,
      'x-exodus-version': appVersion,
      'x-requested-with': `${appId} ${appVersion} ${appBuild}`,
    }

    return this
  }

  #buildHeaders(url, existingHeaders) {
    const headers = new Headers(Object.create(null))

    Object.entries(this.headerConfigs[GLOBAL_HOST]).forEach(([key, value]) => {
      headers.set(key, value)
    })

    const hostname = getUrlHostname(url)
    if (hostname) {
      const matchedDomain = Object.keys(this.headerConfigs).find((key) => {
        return hostname === key || hostname.endsWith(`.${key}`)
      })

      if (matchedDomain) {
        Object.entries(this.headerConfigs[matchedDomain]).forEach(([key, value]) => {
          headers.set(key, value)
        })
      }
    }

    if (existingHeaders) {
      new Headers(existingHeaders).forEach((value, key) => {
        headers.set(key, value)
      })
    }

    return headers
  }
