Audit Report

## Title
CORS wildcard origin allowlist bypass via unanchored suffix match - ([File: core/services/gateway/network/httpserver.go])

## Summary
The Gateway HTTP server's CORS origin check treats a wildcard allow-entry like `*.remix.com` as "any host that ends with `remix.com`" instead of "any host that is a subdomain of `remix.com`," because the wildcard match at [3](#0-2)  uses `strings.HasSuffix` without a boundary check on the preceding character. This allows an attacker controlling a domain like `evil-remix.com` to have their `Origin` reflected into `Access-Control-Allow-Origin` by `handleRequest`.

## Finding Description
`isAllowedOrigin` strips the `*.` prefix from a configured wildcard entry and performs `strings.HasSuffix(originHost, allowedHost)` with no check that the character immediately preceding the match is a `.` (i.e., no label-boundary enforcement). Given `CORSAllowedOrigins = ["https://*.remix.com"]`, `allowedHost` becomes `"remix.com"`; `strings.HasSuffix("evil-remix.com", "remix.com")` evaluates to `true` even though `evil-remix.com` is not a subdomain of `remix.com`. This bypass then feeds directly into `handleRequest`, which reflects the raw `Origin` header value into the `Access-Control-Allow-Origin` response header once `isAllowedOrigin` returns true, per [4](#0-3) . No other check (scheme/port matching at lines 172-179, or exact-match at 180-183) mitigates this, since those checks pass normally for a legitimately-formed but suffix-colliding origin.

## Impact Explanation
Any browser-based attacker who can serve a page from a domain merely ending with the configured wildcard suffix (trivial and cheap to register, e.g. `evil-remix.com` vs. intended `*.remix.com`) can get their origin reflected as CORS-allowed on the Gateway's HTTP endpoint. This permits a victim's browser to make cross-origin `fetch`/XHR requests to the Gateway from the attacker's page and have the JS read the JSON-RPC response bodies, constituting a cross-origin response corruption / allowlist bypass — an impact class explicitly listed as in-scope.

## Likelihood Explanation
Exploitability requires only that the operator configure any wildcard entry in `CORSAllowedOrigins` (e.g., `*.example.com`), which is a legitimate, documented feature of the code (not a misconfiguration/mistake) — once that feature is used, exploitation is straightforward and repeatable by an unprivileged remote attacker who registers a suffix-colliding domain and lures/gets a victim's browser to issue a request with that origin.

## Recommendation
Anchor the suffix match on a full-label boundary:
```go
if strings.HasPrefix(allowedHost, "*.") {
    suffix := allowedHost[1:] // ".remix.com" (keep the dot)
    if originHost == allowedHost[2:] || strings.HasSuffix(originHost, suffix) {
        return true
    }
}
```
This ensures `evil-remix.com` no longer matches `*.remix.com`, while `foo.remix.com` still matches correctly.

## Proof of Concept
1. Configure Gateway with `CORSEnabled = true` and `CORSAllowedOrigins = ["https://*.remix.com"]`.
2. From a page served at `https://evil-remix.com`, issue `fetch("https://<gateway-host>/<path>", {headers: {Origin: "https://evil-remix.com"}})` (or rely on the browser's automatic `Origin` header for cross-origin requests).
3. Server-side, `isAllowedOrigin` computes `allowedHost = "remix.com"` and `strings.HasSuffix("evil-remix.com", "remix.com")` returns `true`.
4. `handleRequest` sets `Access-Control-Allow-Origin: https://evil-remix.com` in the response.
5. The attacker's page JavaScript can now read the Gateway's JSON-RPC response body cross-origin, confirmed via a Go unit test calling `isAllowedOrigin("https://evil-remix.com")` against a config with `CORSAllowedOrigins = []string{"https://*.remix.com"}` and asserting it returns `true` (bug) versus the expected `false`.
