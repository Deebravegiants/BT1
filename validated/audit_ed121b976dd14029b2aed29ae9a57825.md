### Title
`TokenExchange.exchange_token` accepts any signed session token regardless of issuer context, allowing a checkout-extension token to be escalated into a full merchant access token - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` builds the outbound `client_secret`-bearing request using the shop taken from a session token's `dest` claim, but it never checks the token's `iss` (issuer) claim, i.e. it never verifies that the token was actually intended for the admin/embedded-app context that is allowed to perform token exchange for an access token.

### Finding Description
`JwtPayload` decodes and verifies a session token's signature and `aud`, but exposes both "admin" tokens (`iss` ending in `/admin`) and "checkout" tokens (`iss` ending in `/checkouts`) through the same `JwtPayload` object: [1](#0-0) 

The only place `admin_session_token?` is consulted is when deriving `shopify_user_id`: [2](#0-1) [3](#0-2) 

The test fixtures confirm both token "flavors" are valid, HS256-signed inputs to `JwtPayload`: an admin session token with `iss: "https://test-shop.myshopify.io/admin"` and a checkout UI extension token with `iss: "https://test-shop.myshopify.io/checkouts"`: [4](#0-3) [5](#0-4) 

`TokenExchange.exchange_token` takes any `session_token` that passes `JwtPayload.new`, reads `dest_shop = jwt_payload.shop`, and immediately forwards it — with the app's `client_id`/`client_secret` — to Shopify's `/admin/oauth/access_token` endpoint to obtain a full online/offline **merchant access token** for that shop: [6](#0-5) 

At no point does `exchange_token` check `jwt_payload.iss` (or otherwise assert `admin_session_token?`). Compare this to the sibling flows `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and `TokenExchange.migrate_to_expiring_token`, all of which pass the shop through `Utils::ShopValidator.sanitize!` before it is bound to the outbound request host/session: [7](#0-6) [8](#0-7) [9](#0-8) 

`exchange_token` has no equivalent binding check for the *token's issuing context*: the identity equality that should hold is `jwt_payload.iss corresponds to an admin/embedded-app session context` but the code only asserts `jwt_payload.aud == Context.api_key` and `jwt_payload.dest == <shop used in request>`. A token minted by Shopify for a lower-trust context (checkout UI extension, which per Shopify's docs can be issued to buyer-facing/anonymous checkout sessions) satisfies both of those checks equally well, since `aud` is still the app's `api_key` and `dest` is still the shop domain — only `iss` differs (`/checkouts` vs `/admin`).

### Impact Explanation
If an app uses checkout UI extensions and also calls `TokenExchange.exchange_token` (the officially recommended token-exchange flow, per `docs/usage/oauth.md`), a session token minted for the checkout-extension context can be replayed against the admin token-exchange path to mint a full online or offline merchant access token for the shop, i.e., theft of a merchant access token via context/issuer confusion. This meets the Critical bar ("theft or exfiltration of a merchant access token").

### Likelihood Explanation
Exploitability depends on an attacker (e.g., an unauthenticated/low-trust buyer in a checkout extension context) being able to obtain a checkout-scoped session token and getting the host app to run that token through `exchange_token` (e.g., because the app's authentication middleware calls `exchange_token` on whatever bearer/id-token it receives without first checking the token's `iss`). The signature/`aud` checks are legitimately satisfied by such a token because it was actually signed by Shopify with the real `api_secret_key`, so no secret-guessing or brute force is required — only a valid, unmodified token from a different (lower-trust) context.

### Recommendation
In `TokenExchange.exchange_token`, explicitly verify that `jwt_payload` is an admin/embedded-app session token (e.g., expose and require `jwt_payload.admin_session_token?` to be true) before proceeding to request an access token, mirroring the explicit `ShopValidator.sanitize!` binding already used for `shop` in the sibling grant flows.

### Proof of Concept
1. App uses checkout UI extensions and also implements token exchange per `docs/usage/oauth.md`'s recommended flow.
2. A buyer's checkout UI extension is issued a valid session token with `iss: "https://shop.myshopify.io/checkouts"`, `aud: <app api_key>`, `dest: "https://shop.myshopify.io"` (as modeled in `test/auth/jwt_payload_test.rb:23-32`).
3. That token is submitted to the app's endpoint that calls:
   ```ruby
   ShopifyAPI::Auth::TokenExchange.exchange_token(
     session_token: checkout_extension_token,
     requested_token_type: ShopifyAPI::Auth::TokenExchange::RequestedTokenType::OFFLINE_ACCESS_TOKEN,
   )
   ```
4. `JwtPayload.new` succeeds (signature and `aud` are valid — see `lib/shopify_api/auth/jwt_payload.rb:33-44`), `dest_shop` is extracted, and `exchange_token` (`lib/shopify_api/auth/token_exchange.rb:39-65`) proceeds to request and return a full offline merchant `Session` with a real `access_token` for `shop.myshopify.io`, without ever checking that the token came from an admin context rather than checkout.
