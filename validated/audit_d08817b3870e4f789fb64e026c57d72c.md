### Title
Webhook shop identity spoofable because `X-Shopify-Shop-Domain` header is not covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) for an incoming webhook from the `X-Shopify-Shop-Domain`/`Shopify-Shop-Domain` HTTP header, but the HMAC signature that `Registry.process` validates only covers the raw request body, never the shop header. This breaks the identity binding `hmac_signed_bytes == bytes_acted_on`: the bytes verified (raw body) are not the bytes used to determine which merchant/tenant the payload belongs to.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `Request#shop` is read straight from an attacker-controllable HTTP header with no cryptographic binding to the body: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` (i.e., only the body) against `Context.api_secret_key`, and then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) [4](#0-3) 

Because a single app's `client_secret` (`Context.api_secret_key`) is shared across **all** merchants/shops installed on that app, a valid `(raw_body, hmac)` pair legitimately produced by Shopify for shop A's webhook remains cryptographically valid when replayed with the `Shopify-Shop-Domain` header changed to shop B. The library performs no check that the header value corresponds to a shop that actually has an active installation/session, nor does it bind the header into the signed payload before dispatching to `handler.handle`.

### Impact Explanation
This is a High-severity scope/identity-binding bypass: it lets an unprivileged internet user who has observed (or can otherwise obtain) one valid `(body, hmac)` pair for the app forge the tenant attribution of that webhook to any other shop, causing the app's webhook handler to execute merchant-specific business logic (e.g., data sync, order fulfillment, uninstall/redact processing) under a `WebhookMetadata.shop` value that does not match the shop that actually generated the event — a cross-tenant confusion that the gem's own signature check does nothing to prevent, since the equality it verifies (`hmac == HMAC(body)`) is disjoint from the equality the application logic actually relies on (`declared shop == originating shop`).

### Likelihood Explanation
Exploitation requires the attacker to know a valid `(raw_body, hmac)` pair for the target app (e.g., from their own shop's webhook traffic, which any merchant installing the app can observe) and then POST it directly to the app's webhook endpoint with a forged `Shopify-Shop-Domain` header — no access to `client_secret`, tokens, or TLS interception is required. This makes it fully unprivileged-internet-user reachable, though it does require the app owner to also install the app on at least one shop the attacker controls to first obtain a valid signed sample.

### Recommendation
Bind the shop identity into the verified material: either include the shop-domain header value in the HMAC-signed string (matching whatever Shopify actually signs), or — more robustly — after HMAC validation, cross-check `request.shop` against the set of shops with an active session/installation known to the host app before invoking the handler. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated header data and must be independently verified by the consuming application before being trusted for tenant-scoped operations.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`; attacker captures a legitimate webhook delivery: raw body `B` and header `Shopify-Hmac-Sha256: H` (valid because `H = HMAC-SHA256(client_secret, B)`).
2. Attacker POSTs the same body `B` and header `Shopify-Hmac-Sha256: H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` recomputes `HMAC(client_secret, B)` — unchanged, since `to_signable_string` only returns `B` — and the check passes: [1](#0-0) 
4. `Registry.process` proceeds to call `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` with `shop == "victim-shop.myshopify.com"`, even though the payload actually originated from `attacker-shop.myshopify.com`: [3](#0-2)
