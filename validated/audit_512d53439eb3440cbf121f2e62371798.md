### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity via `Utils::HmacValidator`, but the HMAC only signs the raw request body — the `shop` identity (from the `X-Shopify-Shop-Domain` header) is never part of the signed material. An attacker who obtains any single genuine `(raw_body, hmac)` pair — trivially available by installing the target app on their own shop, since apps are freely installable — can replay that exact body+HMAC to the app's webhook endpoint while swapping the shop-domain header to a victim shop. The signature still validates, and the gem hands the forged shop identity straight to the app's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from an unauthenticated header and is never included in the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` computes/compares the signature purely over `to_signable_string`, so it only proves the body wasn't tampered with — it says nothing about which shop the body belongs to: [3](#0-2) 

`Registry.process` treats a passing HMAC check as proof the whole request "did indeed come from Shopify" for the claimed shop, then forwards `request.shop` unchanged to the app's handler: [4](#0-3) 

The documentation reinforces this false guarantee, telling integrators that calling `Registry.process` "will verify the request did indeed come from Shopify" and that `data.shop` is simply "The shop domain of the webhook" — with no caveat that it is unauthenticated: [5](#0-4) [6](#0-5) 

This is exactly the WooFi-report bug class translated to an identity binding: the code implicitly assumes `hmac_valid(body) == shop_is_authentic`, but the equality does not hold because `shop` is not part of the signed input. `hmac_valid(body, hmac)` only proves `body` is unmodified relative to *some* valid signature Shopify generated for *some* delivery — not that the accompanying `shop` header matches the shop Shopify actually sent that body to.

### Impact Explanation
Because the app's client_secret is shared across all merchants that install the app (it is not shop-specific), any unprivileged actor who installs the app on their own store receives genuine `(body, hmac)` pairs from Shopify for their own webhook deliveries. They can then replay the identical body and hmac to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` header changed to an arbitrary victim shop. `Registry.process` will accept it as authentic and invoke the app's handler with `WebhookMetadata#shop` set to the victim shop, causing the app to process attacker-controlled data as if it were authoritative data from the victim tenant — a cross-tenant data-integrity/confusion breach for any app whose webhook handlers key state, records, or authorization decisions off `data.shop` (which the gem's own documentation instructs handlers to do, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`).

### Likelihood Explanation
Requires no privileged credentials, no `api_secret_key`, and no access token — only the ability to install the target app on any shop (unprivileged, normal usage) and send one crafted HTTP POST to the app's public webhook route with a modified header. Reliable and repeatable.

### Recommendation
Bind the `shop` claim to the signed material, e.g. include the `X-Shopify-Shop-Domain` value in `to_signable_string` (matching how `Auth::Oauth::AuthQuery#to_signable_string` already includes `shop`), or otherwise cryptographically verify that the delivered `shop` corresponds to a shop actually registered/installed for this app before dispatching to handlers. At minimum, update the documentation so integrators do not treat `data.shop` as authenticated.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and registers for `orders/create`.
2. Shopify delivers a genuine webhook to the app's endpoint with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid HMAC over raw body>`, and some `raw_body`.
3. Attacker captures this exact `raw_body` and `X-Shopify-Hmac-Sha256` value (they own this shop, so they can see the payload, e.g. via their own logging or by causing the event themselves).
4. Attacker replays a POST to the same webhook endpoint with the identical `raw_body` and `X-Shopify-Hmac-Sha256`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses this successfully; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the HMAC.
6. The app's handler executes with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON>, ...)`, causing the app to act on forged data under the victim's tenant identity.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
