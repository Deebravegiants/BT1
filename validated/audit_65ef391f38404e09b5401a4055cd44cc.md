Based on this, the analysis confirms the vulnerability. The HMAC verification only covers `@raw_body` (via `to_signable_string`), while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from unsigned HTTP headers and passed downstream unverified.

### Title
Webhook Shop-Domain Header Is Not Bound to HMAC Signature, Enabling Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (and `topic`, `webhook_id`, `api_version`) values used by `ShopifyAPI::Webhooks::Registry.process` are read straight from attacker-controllable HTTP headers that are never included in the signed payload. This breaks the identity binding `shop authenticated == shop acted upon`, allowing a party who possesses one validly-signed webhook body (e.g., obtained by installing the app on their own store) to replay that body against the app's webhook endpoint while relabeling it as belonging to a different, victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all pulled from HTTP headers, none of which are part of the signable string: [2](#0-1) 

`HmacValidator.validate_signature` computes the HMAC over `verifiable_query.to_signable_string` (i.e., body only) and compares it with `OpenSSL.secure_compare`: [3](#0-2) 

`Registry.process` validates the HMAC and then trusts `request.shop` (and `request.topic`) directly to dispatch the handler and build `WebhookMetadata`, with no cross-check that the shop matches the body content or any registered/expected shop: [4](#0-3) 

Since the same app-level `Context.api_secret_key` is used to sign webhooks for *every* merchant that installs the app (it is not shop-specific), any party can:
1. Install the app on their own (free/trial) store, receiving a legitimately HMAC-signed webhook whose body and signature they fully control/observe.
2. Replay that exact `raw_body` + `hmac-sha256` header to the app's webhook endpoint, but substitute the `shopify-shop-domain` (and optionally `shopify-topic`) header with a victim shop's domain / a different topic.
3. `HmacValidator.validate` still returns `true`, because it only re-derives the HMAC from `raw_body`, which is unchanged. `Registry.process` then invokes the handler with `WebhookMetadata` claiming the victim's shop, dispatching the attacker-chosen body content as if it originated from — and pertains to — the victim tenant.

This is precisely the class of bug the reported "unchecked decode/trust" issue generalizes to: a value (`shop`) that downstream code treats as authenticated is never actually covered by the authentication primitive (the HMAC).

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: `shop verified via HMAC` != `shop the handler acts on`. A host application's webhook handler (built using `WebhookMetadata#shop`) typically uses this value to look up/update per-tenant records (e.g., mark data deleted, update order/product state, trigger side effects) keyed by shop domain. An attacker can inject spoofed data attributed to an arbitrary victim shop domain that is a customer of the same app, resulting in cross-tenant data corruption/injection — this matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitability requires only that the attacker install the target app on any shop they control (trivial and requires no privileged credentials, matching the "unprivileged internet user" threat model) to obtain one legitimately signed webhook body/HMAC pair, then send a crafted HTTP request with a substituted `shop-domain` header to the app's public webhook endpoint. No access token, `client_secret`, or other secret is needed by the attacker.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, and ideally `api-version`/`webhook-id`) in the value that is HMAC-verified, or otherwise cryptographically bind them to the signed body (e.g., by requiring the host application to independently confirm that `request.shop` corresponds to a shop with an active, stored session/installation before invoking the handler). At minimum, document prominently that `Request#shop`/`#topic` are **not** authenticated by the HMAC check and must be independently validated by the consuming application before being trusted.

### Proof of Concept
```ruby
require "shopify_api"

# Attacker legitimately installs the app on their own shop "attacker.myshopify.com"
# and captures a real webhook fired by Shopify for that shop:
raw_body = '{"id": 12345, "note": "malicious payload"}'
valid_hmac = OpenSSL::HMAC.digest(
  OpenSSL::Digest.new("sha256"),
  ShopifyAPI::Context.api_secret_key, # shared across all merchants of this app
  raw_body,
)

# Attacker now replays the SAME body+hmac but swaps the shop header to a victim shop
forged_headers = {
  "x-shopify-topic" => "orders/updated",
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not covered by HMAC
}

forged_request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# Passes validation because only raw_body is signed:
ShopifyAPI::Utils::HmacValidator.validate(forged_request) # => true

# Registry.process dispatches the handler with shop == "victim-shop.myshopify.com"
ShopifyAPI::Webhooks::Registry.process(forged_request)
```
