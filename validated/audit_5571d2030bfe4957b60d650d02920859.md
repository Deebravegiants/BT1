### Title
Webhook HMAC does not bind the `shop`/`topic` headers, allowing a replayed webhook to be re-attributed to a different shop - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying the HMAC over the raw request body, then trusts the `shop`, `topic`, and `webhook_id` values taken directly from unauthenticated HTTP headers when constructing the `WebhookMetadata` passed to the app's handler.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC signature Shopify computes and sends in `x-shopify-hmac-sha256` covers *only the JSON body*: [1](#0-0) 

`Registry.process` validates that HMAC and, once it passes, unconditionally trusts `request.shop`, `request.topic`, and `request.webhook_id` — all of which are parsed straight from headers with no cryptographic binding: [2](#0-1) [3](#0-2) 

This breaks the intended identity binding: `hmac_valid(raw_body) == true` is treated as proof that `(shop, topic, webhook_id, raw_body)` as a whole originated from Shopify for that shop, when in fact only `raw_body` is authenticated. Concretely: `HMAC(secret, raw_body) == received_hmac` does **not** imply `shop_header == shop_that_shopify_actually_sent_this_for`.

Compare this with the OAuth callback path, where the equivalent `AuthQuery#to_signable_string` explicitly includes `shop` in the signed string, so `shop` is bound to the HMAC there: [4](#0-3) 

No such binding exists for webhooks. Any party who has ever obtained one valid `(raw_body, hmac)` pair for a given shop/topic — for example a merchant who has installed the app and can observe webhooks delivered to their own configured endpoint, or otherwise capture a legitimately-signed webhook payload — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting a different `shopify-shop-domain` (and/or `shopify-topic`) header. `Utils::HmacValidator.validate` will still return `true` because it only recomputes the signature over the body, and `Registry.process` will hand the attacker-chosen `shop` value to the registered `WebhookHandler`, letting data intended for/about shop A be processed and applied as if it belonged to shop B.

### Impact Explanation
This is a cross-tenant data integrity issue: the gem's public contract for webhook handlers (`data.shop` in `WebhookMetadata`) is presented as an authenticated attribute of the webhook, but it is not bound to the HMAC that supposedly authenticates the message. Any app whose webhook handler uses `data.shop` to select which tenant's records to create/update/delete (the documented and expected usage pattern) can have another tenant's data processed under the wrong shop, i.e., cross-tenant access/mutation — matching the "cross-tenant access" Critical impact category, achieved without needing the app's `client_secret` or an access token, only a previously-observed valid (body, hmac) pair.

### Likelihood Explanation
Exploitation requires obtaining at least one legitimately signed `(raw_body, hmac)` pair, which is realistic for any merchant/tenant that has installed the app (they naturally receive webhooks addressed to their own shop, signed with the shared `api_secret_key`) and can then replay that pair against the shared webhook endpoint with a forged `shopify-shop-domain` header. No secret material or privileged access is needed beyond normal use of the app by a regular customer — this keeps it within the "unprivileged internet user" threat model, since the attacker doesn't need the app owner's `client_secret`, just a webhook they were legitimately sent.

### Recommendation
Include the identity-relevant headers (`shop`, `topic`, and ideally `webhook_id`/`api_version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the payload before trusting them in `Registry.process`/`WebhookMetadata`. At minimum, `Webhooks::Request#to_signable_string` should not be limited to `@raw_body` alone if downstream consumers (like `data.shop`) are treated as authenticated.

### Proof of Concept
1. Attacker merchant installs the app on `attacker-shop.myshopify.com` and triggers a webhook event (e.g., `orders/create`) which Shopify delivers to the app's webhook endpoint with a valid `raw_body` and `x-shopify-hmac-sha256` signed with the app's `api_secret_key`.
2. Attacker captures this `(raw_body, hmac)` pair from their own endpoint logs.
3. Attacker resends the identical `raw_body` and `x-shopify-hmac-sha256` to the same app endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-webhook-id`).
4. `Utils::HmacValidator.validate(request)` (`lib/shopify_api/utils/hmac_validator.rb`) returns `true` because it recomputes the HMAC over `raw_body` only, which is unchanged.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) proceeds and calls the registered handler with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: request.parsed_body, ...)`, causing the app's handler to apply attacker-controlled order/data content to the victim shop's tenant context.
