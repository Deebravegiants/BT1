### Title
Attacker-crafted CASE 2 Emporium operation can grant a Permit2 allowance from Emporium's shared balance, letting the attacker later drain other depositors' pooled funds outside of Hinkal's accounting - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction`'s CASE 2 ("Stateless Interaction") branch executes `op.endpoint.call{value: op.value}(op.callData)` directly from the Emporium contract's own context, with the only restriction being a selector blocklist for `callHinkalWallet`/`doSendToRelay`. An attacker can use their own valid deposit/proof to craft an op that calls a Permit2-style `approve`/`permit` function, creating an allowance keyed to `(owner=Emporium, token, spender=attacker)`. Because Permit2 allowance state lives entirely outside Hinkal's `amountChanges`/`balanceChange`/nullifier accounting, the attacker can later call `Permit2.transferFrom` directly, bypassing Hinkal entirely, to pull tokens out of Emporium's shared balance that back other depositors' UTXOs.

### Finding Description
The broken equality: **"tokens the attacker is authorized to move from Emporium equals the `deltaAmountChanges`/UTXO amounts constrained by the attacker's own ZK proof for that single `transact()` call."** After a CASE 2 op sets a Permit2 allowance, this equality breaks — the attacker gains a standing, unbounded pull-right over Emporium's aggregate token balance that was never bounded by any `amountChanges` or `balanceChange` check.

Code path:
- `EmporiumUpgradeable.runAction` (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:91-118`) iterates `stack.ops`. For CASE 2 (`op.invokeWallet == false` or `stack.signerAddress == address(0)`), it does `op.endpoint.call{value: op.value}(op.callData)` with `msg.sender == Emporium`, blocking only two specific selectors: [1](#0-0) 
- `verifyWallet` only requires an EIP-712 signature over the ops when `stack.signerAddress != address(0)` (CASE 1). For CASE 2, it just marks `emporiumMessage` used and returns — no additional gate on `op.callData` content: [2](#0-1) 
- The only accounting performed afterwards is a per-token `balanceChange` check comparing Emporium's own balance before/after the call, and `handleOut` only creates a UTXO if `balanceChange > 0`: [3](#0-2) 
Calling `approve`/`permit` on Permit2 produces `balanceChange == 0`, so this passes trivially and no UTXO is created or consumed — the malicious op is invisible to Hinkal's balance/UTXO invariants.

Root cause: `op.callData`'s effect (setting third-party contract storage such as a Permit2 allowance) is unconstrained by, and has no relationship to, any of the values actually hashed into `calldataHash`/`signedMessageHash` in a way that bounds *future* asset movement. `CircomDataBuilder.getSignedMessageHash` and `getHashedCalldata1` do bind `externalActionData` (hence `externalActionMetadata`, hence the `EmporiumStack`/ops) into the proof's public input, but that only proves the attacker's own EdDSA key authorized *this op for this transaction* — it says nothing about the token custody implications of executing that op against Emporium's pooled balance, which backs *other* users' UTXOs. Since Emporium is a shared vault (`getBalancesForArray` reads the contract's own aggregate ERC20 balance, used to satisfy all depositors' UTXOs), and CASE 2 lets any depositor make Emporium itself the token-approving party for an arbitrary spender, the attacker converts a legitimate small self-authorized action into a persistent, unbounded external claim on the shared pool.

Exploit flow:
1. Attacker deposits a small amount into Emporium (or otherwise obtains a valid UTXO/proof usable in `transact()`).
2. Attacker crafts `CircomData.externalActionData.externalActionMetadata` as an `EmporiumStack` with `signerAddress = address(0)` and one CASE 2 op: `endpoint = Permit2`, `callData = approve(token, attackerAddr, type(uint160).max, type(uint48).max)` (or `permit` with the same effect).
3. Attacker generates their own valid proof (self-authorized, no privileged role needed) and calls `Hinkal.transact()`. `runAction` executes the approve call with `msg.sender = Emporium`; `balanceChange == 0` so all Hinkal checks pass.
4. Other users deposit into Emporium normally, growing its aggregate ERC20 balance.
5. Attacker calls `Permit2.transferFrom(Emporium, attacker, token, amount)` directly — completely outside `Hinkal.transact()`, with no proof, no nullifier, no balance-diff check — draining tokens backing other users' UTXOs.

### Impact Explanation
This is theft of shielded/pooled user funds (Critical): the attacker can drain any amount up to the granted Permit2 allowance from Emporium's aggregate balance, which backs UTXOs of users unrelated to the attacker's own deposit. The attack is repeatable (can be re-armed with fresh `approve` calls as allowances get consumed or reset) and costs only the price of one small deposit plus gas. No existing guard (`performHinkalChecks`, `dimensionsCheck`, `checkOnchainCreation`, `verifyProof`, `verifyWallet`, the `balanceChange` requires) constrains third-party contract state changes caused by CASE 2 `op.callData`, since none of these check anything about token-approval side effects — only direct balance deltas within the single call.

### Likelihood Explanation
Preconditions are minimal: the attacker needs only their own funds, their own valid proof, and the ability to choose `externalActionMetadata` freely (explicitly allowed to an unprivileged attacker per scope). CASE 2 requires no signature at all beyond the attacker's own ZK proof over their own transaction. The only requirement is that Emporium hold (or later come to hold) meaningful balances of the target token from other depositors, which is the normal operating condition of a shared-custody Emporium vault. This is highly feasible and fully repeatable.

### Recommendation
Restrict CASE 2 stateless calls so that Emporium cannot become the approving/owner party for value-authorization primitives on arbitrary spender addresses. Concretely: maintain an explicit allowlist of endpoints permitted in CASE 2 stateless ops (rather than a denylist of two selectors), or block any selector matching common `approve`/`permit`/`increaseAllowance`/Permit2 `approve`/`permit` signatures for `op.endpoint` when acting with `msg.sender == address(this)` (Emporium). Alternatively, require CASE 2 ops to only be executable when they are proven to have zero and only zero lasting state effects outside the balance delta already checked (e.g., disallow `approve`-like calls to any token/Permit2 contract entirely), and audit all allowed endpoints on `onlyAllowedRecipient`/CASE 2 execution surfaces for standing-allowance side effects.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable`, and a Permit2 mock (canonical `Permit2` or a minimal mock implementing `approve(token, spender, amount, expiration)` and `transferFrom(from, to, token, amount)`).
2. Attacker deposits a small amount of `TokenA` into Emporium via `transact()` with `externalActionId` pointing to Emporium, `externalActionMetadata` encoding an `EmporiumStack{ signerAddress: address(0), ops: [{ endpoint: permit2, invokeWallet: false, value: 0, callData: abi.encodeCall(Permit2.approve, (TokenA, attacker, type(uint160).max, type(uint48).max)) }] }`. Generate a locally-built valid proof for this attacker-owned UTXO/deposit.
3. Assert: `transact()` succeeds; assert `Permit2.allowance(address(emporium), address(TokenA), attacker) == type(uint160).max`; assert Emporium's `TokenA` balance is unchanged by this call (`balanceChange == 0` accepted by `runAction`).
4. Second depositor calls `transact()` depositing a large amount of `TokenA` into Emporium (legitimate shielded deposit, separate proof).
5. Attacker (no Hinkal call, no proof) calls `Permit2.transferFrom(emporium, attacker, TokenA, largeAmount)` directly.
6. Assert `TokenA.balanceOf(attacker)` increased by `largeAmount` and `TokenA.balanceOf(emporium)` decreased accordingly, while the second depositor's UTXO/leaf in the Hinkal tree still claims to be backed by that balance (i.e., aggregate Emporium balance is now insufficient to redeem outstanding UTXOs) — demonstrating funds moved and were "not counted" by any depositor's proof.
