### Title
Webhook `shop-domain` header is not covered by HMAC verification, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` verifies the body's integrity but never binds the `shop-domain` (or `topic`/`webhook-id`) header to that signature. This breaks the identity binding `shop authenticated == shop acted upon`: any actor who possesses one valid `(body, hmac)` pair for the shared app secret can resubmit the same body/HMAC to the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` header, and the gem will treat the request as belonging to that spoofed shop.

### Finding Description
`Registry.process` only checks:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
``` [1](#0-0) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` header value: [2](#0-1) 

But for `Webhooks::Request`, `to_signable_string` returns only `@raw_body`, deliberately excluding all headers: [3](#0-2) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from unauthenticated headers: [4](#0-3) 

and are handed directly to the host application's handler as trusted tenant-identifying data: [5](#0-4) 

Because a single `api_secret_key` is shared by the app across every installed shop, a `(raw_body, hmac)` pair that is valid for one tenant's webhook is also a syntactically valid HMAC for the exact same bytes regardless of which shop header accompanies it — the signature says nothing about `shop`. An attacker who can obtain one legitimately-signed webhook (e.g., by installing the app on their own shop and capturing/replaying their own webhook traffic to the app's public webhook endpoint) can therefore change only the `x-shopify-shop-domain` header, keep body and hmac unchanged, and have `Registry.process` accept it and invoke the handler with an attacker-chosen `data.shop` value. This is the exact bug class described in the report — a check (here, HMAC integrity) that answers permissively for a field it never actually covers — applied to the shop-binding boundary instead of a liquidation ratio.

### Impact Explanation
This crosses the tenant boundary the HMAC check is supposed to enforce: the webhook handler is invoked with `shop:` fully attacker-controlled while `hmac`-validation still reports "valid." Any host application that uses `WebhookMetadata#shop` to route side effects, look up which merchant's session/store to update, or make trust decisions (which is the documented, expected use per `docs/usage/webhooks.md`) can be made to perform actions against, or attribute data to, a different shop than actually sent the webhook — a cross-tenant confusion/access issue that maps to the Critical impact category (cross-tenant access) defined in scope.

### Likelihood Explanation
Webhook endpoints are public HTTP endpoints on the host app (that is the entire point of webhooks), so no privileged credentials are needed to reach them. The only prerequisite is possession of one legitimately-signed `(body, hmac)` pair for the shared app secret — trivially obtainable by any user who installs the target app on their own shop (a normal, unprivileged action) and observes their own inbound webhook traffic. No access to `api_secret_key`, access tokens, or the app's `client_secret` is required, satisfying the "unprivileged internet user" constraint.

### Recommendation
Include the identity-bearing headers (`shop-domain`, and ideally `topic`) in the signable content the HMAC binds to, or otherwise cryptographically bind the shop value to the verified body (e.g., require the host application to independently confirm `shop` against a known/authorized shop list before trusting `data.shop`, and document this gap clearly). At minimum, `Registry.process` / `WebhookMetadata` documentation should explicitly warn that `shop` is not authenticated by the current HMAC check so implementers do not treat it as a verified tenant identifier.

### Proof of Concept
```ruby
require "openssl"
require "base64"

secret = ShopifyAPI::Context.api_secret_key
body   = '{"id":1,"note":"legit order from attacker-owned-shop"}'

# Attacker legitimately receives this webhook for their own shop and captures it
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, body)

# Original legitimate headers (attacker's own shop)
original_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "attacker-owned-shop.myshopify.com",
}
ShopifyAPI::Webhooks::Registry.process(
  ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: original_headers)
) # -> handler invoked with data.shop == "attacker-owned-shop.myshopify.com" (expected)

# Replay with same body/hmac but spoofed shop header
spoofed_headers = original_headers.merge(
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",
)
ShopifyAPI::Webhooks::Registry.process(
  ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: spoofed_headers)
)
# HmacValidator.validate still returns true (only `body` is signed),
# so the handler is invoked with data.shop == "victim-shop.myshopify.com"
# even though this webhook never originated from that shop.
``` [6](#0-5) [7](#0-6)
