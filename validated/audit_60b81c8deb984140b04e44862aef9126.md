### Title
Flash-loan users can be charged more than expected because `flash_loan` lacks a maximum-fee bound - ([File: contracts/controller/src/strategies/flash_loan.rs](contracts/controller/src/strategies/flash_loan.rs))

### Summary

`Controller::flash_loan` accepts only the asset, amount, receiver and callback data; it does not let the initiator specify a maximum acceptable fee. The pool computes the actual repayment from the market's current `flashloan_fee` when the transaction executes and then pulls `amount + fee` from the receiver. A ready governance operation that changes the market model can therefore alter the fee between transaction construction and inclusion. A receiver that has approved principal plus a sufficiently large fee can be forced to pay more than intended.

### Finding Description

The controller entrypoint exposes no `max_fee`, `max_total_repayment`, deadline or comparable execution-condition parameter. [1](#0-0) 

The controller forwards the request directly to the pool and merely publishes the fee returned by the pool after execution. [2](#0-1) 

Inside `pool::ops::flash::apply`, the fee is read from live market parameters immediately before the principal is transferred. [3](#0-2) 

`terms` calculates `fee = amount * flashloan_fee / 10_000` and sets `total_repayment = amount + fee`. [4](#0-3) 

After the callback, the pool requires receiver allowance for that dynamically calculated total and pulls it with `transfer_from`. [5](#0-4) 

Consequently, the signed request does not bind the fee observed by the user to the fee charged at execution. The same variable-cost pattern also exists in strategy borrows because `multiply` and `swap_debt` call `borrow_into_controller` with `charge_fee = true`, and the pool deducts `flashloan_fee` from the borrowed amount while minting debt for the full gross amount. [6](#0-5) [7](#0-6) 

### Impact Explanation

A flash-loan receiver can lose the difference between the expected fee and the newly configured fee. The loss is direct user-fund loss because `transfer_from` collects the larger repayment from the receiver. For a large loan, even a modest basis-point increase can be material.

In `multiply` and `swap_debt`, an increased strategy fee reduces the amount delivered to the router while leaving the account with debt for the full requested gross amount. Although a well-formed route should revert through its encoded minimum-output check, the contract itself provides no maximum-fee guard independent of route quality.

### Likelihood Explanation

The fee can only change through an authorized market-parameter update, so an arbitrary user cannot directly raise it. However, governance execution of an already-ready operation is an unprivileged path in the stated threat model. If such an operation is waiting while a user's flash-loan or strategy transaction is pending, execution ordering determines which fee applies. The vulnerable transaction does not need to be maliciously constructed; a stale fee assumption and broad token allowance are sufficient.

### Recommendation

Add an explicit fee bound to `flash_loan`, for example `max_fee` or `max_total_repayment`, and revert when the computed `terms.fee` or `terms.total_repayment` exceeds that bound.

Apply the same protection to strategy entrypoints that charge a fee through `create_strategy`, either by adding `max_fee` to `multiply` and `swap_debt` or by adding a maximum acceptable net-receipt parameter. Pass the bound through the controller-to-pool call so it is enforced against the live `flashloan_fee`, not merely documented off-chain.

A receiver-side fee check inside `execute_flash_loan` is useful defense in depth, but it does not replace an on-chain bound on the user-signed lending request.

### Proof of Concept

1. A market has `flashloan_fee = 10` BPS.
2. A user submits `Controller::flash_loan(caller, hub_asset, 1_000_000, receiver, data)`, expecting a 1,000-unit fee and a 1,001,000-unit repayment.
3. Before that transaction is included, a permissionless caller executes an already-ready governance operation that calls the controller owner path `upgrade_liquidity_pool_params`, replacing the market model with `flashloan_fee = 50` BPS.
4. The user's transaction executes afterward. `pool::ops::flash::terms` computes a 5,000-unit fee and a 1,005,000-unit repayment.
5. The receiver had approved at least 1,005,000 units, so `collect_repayment` succeeds.
6. The receiver pays 4,000 more units than expected for the same principal.

The same state transition can be applied to `multiply` or `swap_debt`: the account still mints debt for the requested gross amount, but `create_strategy` delivers `gross - increased_fee` to the strategy.

```rust
pub(crate) fn terms(env: &Env, amount: i128, fee_bps: u32, pre_balance: i128) -> FlashTerms {
    let fee = Bps::from(i128::from(fee_bps)).flash_loan_fee_on(env, amount);
    FlashTerms {
        fee,
        total_repayment: amount
            .checked_add(fee)
            .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow)),
        balance_after_payout: pre_balance
            .checked_sub(amount)
            .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow)),
        balance_after_repayment: pre_balance
            .checked_add(fee)
            .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow)),
    }
```

```rust
/// Pulls principal + fee via `transfer_from` after verifying allowance.
fn collect_repayment(
    env: &Env,
    asset: &token::Client,
    pool: &Address,
    receiver: &Address,
    terms: &FlashTerms,
) {
    assert_with_error!(
        env,
        asset.allowance(receiver, pool) >= terms.total_repayment,
        FlashLoanError::InvalidFlashloanRepay
    );
    asset.transfer_from(pool, receiver, pool, &terms.total_repayment);
    require_balance(env, asset, pool, terms.balance_after_repayment);
}
```

```rust
/// Computes the fee, mints debt for `action.amount`, and debits cash for
/// `amount - fee`.
///
/// The fee stays in the pool as protocol revenue via
/// [`interest::add_protocol_revenue`].
pub(crate) fn accounting(env: &Env, action: PoolAction, charge_fee: bool) -> StrategyOutcome {
    let PoolAction {
        position,
        amount,
        hub_asset,
    } = action;
    require_nonneg_amount(env, amount);

    let mut cache = ops::renewed_market(env, &hub_asset);
    let fee = compute_fee(env, &cache, amount, charge_fee);

    let mut position = Ray::from(position.scaled_amount);
    borrow::mint_debt(env, &mut cache, &mut position, amount);

    let protocol_fee = Ray::from_asset(env, fee, cache.params().asset_decimals);
    interest::add_protocol_revenue(&mut cache, protocol_fee);

    let amount_to_send = amount
        .checked_sub(fee)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow));
```
