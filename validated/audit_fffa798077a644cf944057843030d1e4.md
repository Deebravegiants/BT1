### Title
Unrestricted method-name dispatch in cross-process `assetsApi` RPC bridge allows invoking any `keys`/`api`/`address`/`blockExplorer` method on an asset, bypassing the intended allowlist - (File: `libraries/domain-serialization/src/assets-serialization.js`)

### Summary
The `assetsApi` dispatcher, which is the background-process handler for the UI↔background RPC bridge (`@exodus/browser-extension-rpc`), resolves and invokes an arbitrary method on a privileged asset object using a caller-supplied string, with no check that the method is one of the methods the wallet intends to expose to the UI process. This mirrors the root cause of the reported `PrivatePool.execute` bug: a generic "call this named operation with these arguments" primitive that is trusted to only be used for a benign purpose (claiming airdrops / proxying safe UI calls), but which actually allows the caller to reach any method on the privileged target.

### Finding Description
`assetsApi(asset, functionName, ...args)` splits the caller-provided `functionName` into `apiName`/`name`, looks up `asset[apiName][name]`, and calls it directly with deserialized args: [1](#0-0) 

This function is wired as the background-side implementation of the `assetsApi` RPC method, invoked from the UI process via `rpc.assetsApi(...)`: [2](#0-1) 

Separately, the codebase defines an explicit allowlist of which methods on `address`, `api`, `blockExplorer`, and `keys` are meant to be proxy-callable from the UI (`serializeApis`), which only picks a small, safe subset (e.g. `validate`, `resolvePurpose`, `getFee`, `hasFeature`, `validateAssetId`, `addressUrl`, `txUrl`, `encodePublic`, `encodePrivate`): [3](#0-2) 

However, this allowlist is only enforced on the *serialization* side (i.e., which stub functions get attached to the object handed to the UI's own generated proxies) — it is **not** re-checked inside `assetsApi` itself, which is the actual privileged dispatcher reachable via the RPC transport: [4](#0-3) 

Just like `PrivatePool.execute(target, data)` trusted that only "airdrop claim" calldata would ever be sent by the owner, `assetsApi(asset, functionName, ...args)` trusts that only allowlisted `apiName.name` values will ever be sent by the UI RPC client — but the dispatcher performs no validation of `apiName`/`name` against `serializeApis`'s picked list, so any caller capable of issuing an `assetsApi` RPC request (e.g., a compromised/malicious UI-side script, or malicious rendered content within the UI process) can invoke **any** method under `asset.address`, `asset.api`, `asset.blockExplorer`, or `asset.keys` — not just the intended ones — with attacker-controlled arguments.

### Impact Explanation
If any method beyond the intended allowlist exists on these privileged asset sub-APIs (e.g. anything under `keys` beyond `encodePublic`/`encodePrivate`, or any signing/derivation helper on `api`), a compromised or malicious UI-side context can call it directly through the RPC bridge, bypassing whatever UI-level gating (confirmation dialogs, permission checks) normally wraps those operations. This is the same class of "trusted caller can execute an unbounded surface of privileged operations" bug as the PrivatePool finding, and in a wallet, that surface directly touches key-encoding/derivation logic (`keys` namespace) — i.e., it sits on the boundary the report calls out (unauthorized signing / secret disclosure).

### Likelihood Explanation
Exploitability depends on the trust level of the UI process relative to the background process and on what additional (non-allowlisted) methods actually exist on `asset.keys`/`asset.api` at runtime — this could not be fully confirmed from the indexed code, since the concrete `keys`/`api` implementations for each asset were not available for review. If the UI process can be influenced by less-trusted content (e.g., rendered dApp/browser content within the extension UI, or any other injection into the UI-side JS), likelihood is high, since no server-side or IPC-side authorization or allowlist check exists at all in `assetsApi`; the only thing standing between "safe proxy call" and "arbitrary call" is what the UI's own generated stubs choose to expose, and `assetsApi` does not re-derive or check against that.

### Recommendation
Mirror the PrivatePool fix pattern: enforce the allowlist check inside the actual privileged dispatcher, not just at serialization time. Concretely, `assetsApi` in `libraries/domain-serialization/src/assets-serialization.js` should validate `apiName`/`name` against the same allowlist used by `serializeApis` before invoking `api[name](...)`, e.g.:

```js
const ALLOWED = { address: ['validate','resolvePurpose'], api: ['features','getFee','hasFeature','validateAssetId'], blockExplorer: ['addressUrl','txUrl'], keys: ['encodePublic','encodePrivate'] }
assert(ALLOWED[apiName]?.includes(name), `method ${apiName}.${name} is not allowed via assetsApi`)
```

This ensures the RPC dispatcher itself — the actual trust boundary — cannot be used to reach unintended privileged methods, regardless of what the UI-side proxy code chooses to expose.

### Proof of Concept
Conceptual PoC (cannot be executed against this indexed snapshot, but demonstrates the reachable code path):

```js
// From the UI-process RPC client (or any code able to issue RPC calls to background):
await rpc.assetsApi('bitcoin', 'keys.someInternalOrUnintendedMethod', ...attackerArgs)

// This reaches, unchecked:
// assetsApi(asset, 'keys.someInternalOrUnintendedMethod', ...attackerArgs)
//   -> apiName = 'keys', name = 'someInternalOrUnintendedMethod'
//   -> api = asset.keys
//   -> api[name](...deserializedArgs)   // no allowlist check performed here
```

Because `assetsApi` (libraries/domain-serialization/src/assets-serialization.js:43-53) never checks `name` against the `serializeApis` picked list (lines 80-96), any method that exists on `asset.keys`/`asset.api`/`asset.address`/`asset.blockExplorer` beyond the intentionally-exposed ones is reachable through this single generic dispatcher — the same "generic arbitrary-execution primitive trusted to only be used safely" pattern as `PrivatePool.execute`.

// called on the background process
export const assetsApi = async (asset, functionName, ...args) => {
  assert(asset, `missing asset in assetProxy`)
  const assetName = asset.name
  assert(assetName && functionName, 'missing args in assetProxy')
  const parts = functionName.split('.')
  assert(parts[0], `missing function name in assetProxy for ${assetName}`)
  const [apiName, name] = parts[1] ? parts : ['api', parts[0]]
  const api = asset[apiName]
  assert(api && api[name], `invalid member in assetProxy for ${assetName}`)
  const deserializedArgs = args.map((arg) => deserializeArg(arg))
  const result = await api[name](...deserializedArgs)
  return serializeArg(result)
}
