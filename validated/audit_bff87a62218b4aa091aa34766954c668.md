### Title
Webhook shop/topic/id identity headers are not covered by the HMAC signature, allowing cross-tenant impersonation - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then trusts the `shop-domain`, `topic`, `webhook-id`, and `api-version` HTTP headers — none of which are covered by that signature — to build the `WebhookMetadata` passed to the app's handler.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `Request#hmac` reads the `hmac-sha256` header: [1](#0-0) [2](#0-1) 

`Registry.process` verifies only that HMAC-over-body via `Utils::HmacValidator.validate(request)`, and then hands the handler a `WebhookMetadata` struct built from `request.shop`, `request.topic`, and `request.webhook_id` — fields taken straight from headers that were never part of the signed material: [3](#0-2) [4](#0-3) 

`HmacValidator.validate`/`validate_signature` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` header, confirming the signature binds body bytes only, never `shop`, `topic`, or `webhook_id`: [5](#0-4) 

The identity binding that should hold is: `shop header == the tenant whose events this HMAC authenticates`. Since the HMAC only certifies the body bytes, that equality never holds — `shop`, `topic`, and `webhook_id` are unauthenticated request headers that any caller reaching the app's public webhook endpoint controls, independent of the signature check.

Because a webhook endpoint is a plain public HTTP endpoint, any unprivileged internet user who has ever installed the app on a shop they control receives one or more genuinely Shopify-signed webhooks (valid `raw_body` + valid `hmac-sha256`, computed by Shopify with the app's `client_secret`, which the attacker never needs to know). That attacker can replay the exact same `raw_body`/`hmac-sha256` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop and/or a different `x-shopify-topic`/`webhook-id`. `Utils::HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` dispatches the handler with `WebhookMetadata` claiming the event belongs to the victim shop/topic.

### Impact Explanation
This breaks the tenant boundary the app relies on: `Registry.process` and the resulting `WebhookMetadata.shop` are the only tenant-attribution mechanism the gem provides for webhook processing, and it is not authenticated. Any app logic that keys off `data.shop`/`data.topic` (e.g., updating shop state, redact handling, mandatory-topic handlers like `shop/redact`, `customers/redact`, `customers/data_request`) can be made to act on a different shop's identity while presenting attacker-supplied body content, i.e., cross-tenant data manipulation using a replayed-but-valid signature. This matches the Critical "cross-tenant access" category.

### Likelihood Explanation
Any user who installs the target app on their own store (a normal, unprivileged action available to any merchant) obtains legitimate `raw_body` + `hmac-sha256` pairs from real Shopify webhook deliveries at will. Sending a POST directly to the app's public webhook URL with modified headers is trivial and requires no secret material, no privileged access, and no interaction with the victim. The gem performs no header binding to close this gap.

### Recommendation
Extend `Utils::VerifiableQuery#to_signable_string` (or add a separate check in `Registry.process`) so the signed material — or a secondary integrity check — covers the identity-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`), not just the raw body. At minimum, `Registry.process` should refuse to trust `request.shop`/`request.topic` for authorization decisions unless they are cryptographically bound to the signature, e.g. by validating them against the topic/handler that was registered and cross-checking `shop` against an independently known session/shop record rather than trusting the header verbatim.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, and the app is subscribed to some webhook topic (e.g. `orders/create`).
2. Shopify delivers a legitimately signed webhook to the app: body `B`, header `x-shopify-hmac-sha256: H = HMAC(client_secret, B)`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`.
3. Attacker captures `B` and `H` (both fully known to them, since they are the recipient) and issues their own POST directly to the app's public webhook endpoint with the same `B` and `H`, but sets `x-shopify-shop-domain: victim.myshopify.com` (and/or a different `x-shopify-topic`).
4. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request`; `Utils::HmacValidator.validate` recomputes `HMAC(client_secret, B)` and finds it equals `H` — validation succeeds because the shop header was never part of the signed input.
5. `Registry.process` dispatches the registered handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-controlled body content attributed to `victim.myshopify.com`.
