### Title
Missing `return` after failed email-claim extraction and after failed session DB insert allows creation of an authenticated session with an empty/incorrect email - (File: core/sessions/oidcauth/oidc.go)

### Summary
In `oidcAuthenticator.handleTokenExchange`, two error-handling branches write an HTTP error response but omit the `return` statement, so execution continues into the session-creation logic even though a required value could not be obtained.

### Finding Description
When the OIDC ID token's claims do not contain a string `email` field, the type assertion at [1](#0-0)  fails, `oi.lggr.Errorf` and `c.String(http.StatusInternalServerError, ...)` are called, but there is no `return`. Execution falls through to role mapping and then to session creation at [2](#0-1) , which inserts a new row into `oidc_sessions` using the empty/invalid `email` value together with the `role` derived independently from group claims via `IDClaimsToUserRole`. The function then sets the session cookie and, if `ginSession.Save()` succeeds, returns `200 OK` with `{"success": true}` at [3](#0-2) , granting the caller a valid, cookie-backed authenticated session tied to an empty-string `user_email`.

A second, related instance exists right after the DB insert: if `oi.ds.ExecContext` fails while inserting the session row, the error is logged and `c.String(http.StatusInternalServerError, ...)` is written, again without a `return`, at [4](#0-3) . Execution proceeds to audit-log a "successful" login, set the session cookie, call `ginSession.Save()`, and respond `200 OK` even though no session row exists in `oidc_sessions` for that session ID (or a stale/incorrect row from a previous failed attempt could be picked up). This is directly analogous to the audit report's pattern: unchecked/ignored failure of an external call step (here, the claim extraction / DB write) silently continues execution and produces an outcome that harms trust in the intended access-control decision, rather than the caller-visible error being enforced.

Downstream, `AuthorizedUserWithSession` (used by every authenticated request) trusts whatever row is present in `oidc_sessions` for the given session ID, as seen at [5](#0-4) ; it does not re-validate that `user_email` is non-empty or consistent with the OIDC identity that was supposed to be attested.

### Impact Explanation
Any two OIDC-authenticated principals whose ID token responses trigger the missing-email branch would each get a `oidc_sessions` row keyed with `user_email = ""` but with independently-derived roles (from group claims). This causes cross-user response confusion: multiple distinct external identities collapse onto the same empty-email identity, breaking per-user audit trails, `FindUser`/email-based lookups, and potentially allowing a session created under one flawed OIDC response to be functionally indistinguishable from another. Combined with the second bug (DB insert failure not aborting the request), a client can receive `200 OK`/`success: true` and a working session cookie even when the server-side session record was never durably created or is stale, undermining the integrity of the authentication state the rest of the node relies on for role-gated access (`RequiresRunRole`/`authenticateUserIsAdmin` etc. in [6](#0-5) ).

### Likelihood Explanation
This path is reached by any client completing the standard, unprivileged OIDC login flow (`POST` to the token-exchange endpoint) whenever the configured OIDC provider omits/mistypes the `email` claim, or whenever the local DB insert transiently fails (e.g., load, connection blips). No special privileges are required to trigger the missing-email branch; a caller only needs an OIDC provider/session response lacking a proper `email` claim, and normal DB error handling makes the second branch reachable by ordinary error/retry conditions.

### Recommendation
Add `return` immediately after both error responses:
- After `c.String(http.StatusInternalServerError, "Failed to get email from claims")` at [1](#0-0) .
- After `c.String(http.StatusInternalServerError, "Error creating session")` at [7](#0-6) .

Additionally, validate that `email` is non-empty before proceeding to session creation/audit logging, and ensure the audit log at [8](#0-7)  only fires on a confirmed successful session insert.

### Proof of Concept
1. Configure an OIDC provider (or a compromised/misconfigured one) whose UserInfo/ID token claims omit the `email` field but include valid group claims mapping to a role via `IDClaimsToUserRole`.
2. Complete the standard OAuth2 authorization code flow and `POST` the resulting `code`/`state` to the token-exchange endpoint handled by `handleTokenExchange`.
3. Observe that despite the `email` type-assertion failure (`ok == false`) and the `500` body written by `c.String`, the handler continues, inserts an `oidc_sessions` row with `user_email = ''`, sets the session cookie, and ultimately responds `200 OK` with `{"success": true}` — the client now holds a working, cookie-authenticated session mapped to an empty email.
4. Separately, force `oi.ds.ExecContext` to fail (e.g., via a DB error injection or connection interruption) during a valid login; observe the same 200-with-cookie result even though the session row was never inserted, at [9](#0-8) .

// AuthorizedUserWithSession will return the API user associated with the Session ID if it
// exists and hasn't expired
func (oi *oidcAuthenticator) AuthorizedUserWithSession(ctx context.Context, sessionID string) (clsessions.User, error) {
	if len(sessionID) == 0 {
		return clsessions.User{}, errors.New("session ID cannot be empty")
	}
	var foundUser clsessions.User
	err := sqlutil.TransactDataSource(ctx, oi.ds, nil, func(tx sqlutil.DataSource) error {
		// Query the oidc_sessions table for given session ID, user role and email are saved after the id claims is provided and validated
		var foundSession struct {
			UserEmail string
			UserRole  clsessions.UserRole
			Valid     bool
		}
		if err := tx.GetContext(ctx, &foundSession,
			"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM oidc_sessions WHERE id = $1",
			sessionID, oi.config.SessionTimeout().Duration(),
		); err != nil {
			if errors.Is(err, sql.ErrNoRows) {
				return clsessions.ErrUserSessionExpired
			}
			return err
		}
		if !foundSession.Valid {
			// Sessions expired, purge
			return clsessions.ErrUserSessionExpired
		}
		foundUser = clsessions.User{
			Email: foundSession.UserEmail,
			Role:  foundSession.UserRole,
		}
		return nil
	})
	if err != nil {
		if errors.Is(err, clsessions.ErrUserSessionExpired) {
			if _, execErr := oi.ds.ExecContext(ctx, "DELETE FROM oidc_sessions WHERE id = $1", sessionID); execErr != nil {
				oi.lggr.Errorf("error purging stale OIDC session: %v", execErr)
			}
		}
		return clsessions.User{}, err
	}
	return foundUser, nil
}

// Authenticates the user from the session cookie and asserts at least 'run' role.
func authenticateUserCanRun(ctx context.Context) error {
	session, ok := auth.GetGQLAuthenticatedSession(ctx)
	if !ok {
		return unauthorizedError{}
	}
	if session.User.Role == sessions.UserRoleView {
		return RoleNotPermittedError{session.User.Role}
	}
	return nil
}

// Authenticates the user from the session cookie and asserts at least 'edit' role.
func authenticateUserCanEdit(ctx context.Context) error {
	session, ok := auth.GetGQLAuthenticatedSession(ctx)
	if !ok {
		return unauthorizedError{}
	}
	switch session.User.Role {
	case sessions.UserRoleView, sessions.UserRoleRun:
		return RoleNotPermittedError{session.User.Role}
	default:
	}
	return nil
}

// Authenticates the user from the session cookie and asserts has 'admin' role
func authenticateUserIsAdmin(ctx context.Context) error {
	session, ok := auth.GetGQLAuthenticatedSession(ctx)
	if !ok {
		return unauthorizedError{}
	}
	if session.User.Role != sessions.UserRoleAdmin {
		return RoleNotPermittedError{session.User.Role}
	}
	return nil
}
