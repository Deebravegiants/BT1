### Title
Permanent DoS of legitimate pool creation via unvalidated `market` account squatting in `Initialize2` - (File: `program/src/processor.rs`)

### Summary
`process_initialize2` derives every account slot for a new AMM pool (target orders, LP mint, coin/pc vaults, and the `AmmInfo` account itself) from the `market_info` account key as a seed, but never validates that `market_info` is an actual, correctly-owned OpenBook/Serum market account. Any unprivileged user can call `Initialize2` first with an arbitrary market pubkey (including one that a legitimate project intends to use) paired with throwaway mints/vaults, permanently occupying the PDA slots for that market and blocking the real pool from ever being created there.

### Finding Description
In `process_initialize2`, the accounts are created deterministically from `market_info.key` via `generate_amm_associated_account` / `generate_amm_associated_spl_token` / `generate_amm_associated_spl_mint`, using seeds like `TARGET_ASSOCIATED_SEED`, `LP_MINT_ASSOCIATED_SEED`, `COIN_VAULT_ASSOCIATED_SEED`, `PC_VAULT_ASSOCIATED_SEED`, and `AMM_ASSOCIATED_SEED` combined with `market_info.key`: [1](#0-0) 

The only checks performed are that `amm_coin_mint_info.key != amm_pc_mint_info.key`, that the user is a signer, and that `amm_config_info` is the correct PDA — there is no check that `market_info` is owned by, or is a valid state account of, the OpenBook/Serum market program, nor that it corresponds to the `coin`/`pc` mints being supplied: [2](#0-1) 

Each helper that creates an associated account checks only that the target address is still owned by the System Program; if it is not (i.e., someone already created it), it returns a permanent `RepeatCreateAmm` error: [3](#0-2) 

Because the PDA addresses are keyed purely off the caller-supplied `market_info.key`, and that key is never validated to be a genuine, unique OpenBook market, an attacker can:
1. Observe/predict a market pubkey that a legitimate team intends to use for their pool (e.g., a freshly created OpenBook market, whose pubkey is public before the Raydium pool-creation transaction lands).
2. Call `Initialize2` themselves first, supplying that market pubkey as `market_info`, along with attacker-controlled coin/pc mints, vault accounts, and a minimal (e.g., 1 lamport) `init_coin_amount`/`init_pc_amount` that still satisfies `amm_coin_vault.amount != 0` and clears `InitLpAmountTooLess`.
3. The instruction succeeds, permanently creating (and initializing, `status != Uninitialized`) the target-orders, LP-mint, vault, and `AmmInfo` accounts derived from that specific market key.
4. When the legitimate project later calls `Initialize2` with the same market pubkey and their real mints/vaults, every `generate_amm_associated_*` call hits the "account already exists / not system-owned" branch and returns `AmmError::RepeatCreateAmm`, permanently blocking creation of the real pool for that market.

This is directly analogous to the Aloe `enrollCourier` issue: a bounded/deterministic identifier space (there, a `uint32 id`; here, the PDA space keyed by `market` pubkey) can be permissionlessly claimed by any unprivileged caller with no restriction on reuse, and the contract's "already exists" check (meant to prevent double-initialization) becomes the permanent-DoS primitive once an attacker claims the slot first.

### Impact Explanation
The intended pool for that market can never be created through this program — a permanent, unrecoverable denial of service against pool creation (not merely griefing gas). Since AMM pool creation is a core, unprivileged, user-facing operation (`Initialize2` is explicitly documented as reachable by any wallet with the right token accounts), this blocks legitimate LPs/pool creators from ever launching a pool tied to that specific market account, and there is no governance/admin recovery path shown in the code to reclaim or reset these PDAs.

### Likelihood Explanation
Likelihood is significant in any environment where market pubkeys are predictable or observable ahead of the real pool-creation transaction (e.g., a market is created in one transaction/block and the pool-creation transaction follows shortly after, or transactions are visible in the mempool/RPC before landing). The attack requires no special privileges — only a signer wallet, two throwaway mints, and minimal token balances — well within reach of a single unprivileged attacker transaction with attacker-chosen accounts and data.

### Recommendation
- Validate that `market_info` is genuinely owned by the expected OpenBook/Serum market program and represents a real, distinct market (as intended by the "Just a seed... can be any account" comment being overly permissive).
- Consider binding the PDA derivation to a combination that a griefer cannot cheaply front-run and squat on 1:1 with the legitimate mints (e.g., derive using `(market, coin_mint, pc_mint)` rather than `market` alone, and/or require the caller to have created/own the market), or restrict pool creation for a given market to be re-attemptable/cancelable if the first Initialize2 was not backed by a legitimate market state.
- Add a recovery mechanism (e.g., governance-gated) to reclaim or invalidate squatted `AmmInfo`/vault/mint PDAs tied to a market that never received a legitimate initialization.

### Proof of Concept
1. Attacker observes a soon-to-be-used OpenBook market pubkey `M` (or any account they can predict will be used as `market_info` for a legitimate pool).
2. Attacker creates two throwaway SPL mints `mintA`, `mintB` and matching vault/LP accounts they control.
3. Attacker submits `Initialize2` with `market_info = M`, `amm_coin_mint_info = mintA`, `amm_pc_mint_info = mintB`, `init_coin_amount = 1`, `init_pc_amount = 1`, following the account layout in `initialize2()`: [4](#0-3) 
4. The transaction succeeds; PDAs for target orders / LP mint / coin vault / pc vault / `AmmInfo`, all seeded by `M`, are now system-owned no longer and `AmmInfo.status` is set to `WaitingTrade`/`SwapOnly`: [5](#0-4) 
5. The legitimate team later calls `Initialize2` with `market_info = M` and their real mints; every associated-account creation call now hits the already-owned branch and returns `AmmError::RepeatCreateAmm`, permanently preventing the legitimate pool from ever being created for market `M`.

        associated_token_account: &'a AccountInfo<'b>,

        _rent_sysvar_account: &'a AccountInfo<'b>,
        associated_seed: &[u8],
        data_size: usize,
    ) -> ProgramResult {
        let (associated_token_address, bump_seed) = get_associated_address_and_bump_seed(
            &program_id,
            &market_account.key,
            associated_seed,
            program_id,
        );
        if associated_token_address != *associated_token_account.key {
            msg!("Error: Associated token address does not match seed derivation");
            return Err(AmmError::ExpectedAccount.into());
        }
        if associated_token_account.owner == system_program_account.key {
            let associated_account_signer_seeds: &[&[_]] = &[
                &program_id.to_bytes(),
                &market_account.key.to_bytes(),
                associated_seed,
                &[bump_seed],
            ];
            let rent = Rent::get()?;
            let required_lamports = rent
                .minimum_balance(data_size)
                .max(1)
                .saturating_sub(associated_token_account.lamports());
            if required_lamports > 0 {
                invoke(
                    &system_instruction::transfer(
                        user_wallet_account.key,
                        associated_token_account.key,
                        required_lamports,
                    ),
                    &[
                        user_wallet_account.clone(),
                        associated_token_account.clone(),
                        system_program_account.clone(),
                    ],
                )?;
            }
            invoke_signed(
                &system_instruction::allocate(associated_token_account.key, data_size as u64),
                &[
                    associated_token_account.clone(),
                    system_program_account.clone(),
                ],
                &[&associated_account_signer_seeds],
            )?;
            invoke_signed(
                &system_instruction::assign(associated_token_account.key, assign_to),
                &[
                    associated_token_account.clone(),
                    system_program_account.clone(),
                ],
                &[&associated_account_signer_seeds],
            )?;
        } else {
            associated_token_address.log();
            return Err(AmmError::RepeatCreateAmm.into());
        }
        Ok(())
    }
