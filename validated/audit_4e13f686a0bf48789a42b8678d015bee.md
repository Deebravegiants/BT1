### Title
ERC20 `transfer` success only checks call success, not the return value, in Tron `IntentGatewayV2.withdraw()` and `SweepDust` handling - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.withdraw()` and the `SweepDust` request handler on the Tron variant of the Intent Gateway release escrowed ERC20 tokens using a raw low-level `.call()` to the token's `transfer` selector, checking only that the call itself did not revert (`success`). They never decode and validate the returned boolean. Tokens that signal failure by returning `false` (instead of reverting) — the exact "no-revert-on-failure" ERC20 class from the referenced report — will cause the transfer to silently fail while the contract still deducts the escrow accounting and marks the order filled/refunded, permanently losing the user's or solver's funds.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `withdraw()` releases escrowed tokens like this: [1](#0-0) 


The same pattern is used for transaction-fee payout in the same function and for `SweepDust`: [2](#0-1) [3](#0-2) 

`success` from a low-level `.call` only reflects whether the callee's code executed without reverting — it says nothing about the ABI-encoded return value. Per the "no-revert-on-failure" ERC20 class documented in the referenced report (and in `d-xo/weird-erc20`), some tokens return `false` from `transfer()` on failure (e.g., due to a blacklist, pause, or internal balance check) instead of reverting. In that case `success == true` even though no tokens moved, so `if (!success) revert TransferFailed();` never triggers.

Contrast this with the rest of the codebase (including the canonical `IntentGatewayV2.sol` and `IntentsBase.sol` used on standard EVM chains), which consistently uses OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom` — importing `SafeERC20` for exactly this reason: [4](#0-3) 

The Tron contract also imports `SafeERC20` and declares `using SafeERC20 for IERC20;` but does not apply it in `withdraw()` / `SweepDust`, using the unchecked-return raw call instead.

### Impact Explanation
After `withdraw()` runs, `_orders[body.commitment][token] -= amount` unconditionally decrements escrow accounting and `_filled[body.commitment]` is set, marking the order as settled — regardless of whether the token transfer actually moved funds. If the underlying token silently returns `false`, the beneficiary (solver on a fill, or user on a refund/cancel) never receives their tokens, yet the protocol's internal bookkeeping treats the order as resolved. The escrowed tokens remain stuck in the contract with no accounting path left to reclaim them, resulting in a permanent loss of user/solver funds. This is reachable on the standard settlement path: any relayer delivering a `RedeemEscrow`/`RefundEscrow` POST request via `onAccept`, or any account triggering the `onGetResponse` refund path, invokes `withdraw()`.

### Likelihood Explanation
Likelihood is moderate to high in production: it only requires a single input/output token configured for an order to be a token from the "no-revert-on-failure" class (some stablecoins and several deployed ERC20 tokens behave this way under blacklist/pause conditions). Since the Intent Gateway is a permissionless token-swap venue, users and solvers choose the tokens used per order, and the contract does not restrict which tokens can be escrowed/settled — a single order created with such a token is enough to trigger the loss on settlement.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` (both the token loop and the tx-fee payout) and in the `SweepDust` handler with `IERC20(token).safeTransfer(beneficiary, amount)` (or `SafeERC20.safeTransfer`), consistent with the rest of the codebase (`IntentsBase.sol`, `EvmHost.sol`). This ensures the ABI-encoded return value is properly checked (and reverts for tokens with no return data are handled), preventing escrow accounting from advancing when a transfer did not actually succeed.

### Proof of Concept
1. Deploy (or use) an ERC20 token whose `transfer()` returns `false` on failure instead of reverting (e.g., recipient blacklisted, contract paused, or insufficient internal balance check that returns `false`).
2. A user places a cross-chain order on the source chain with this token as an input, and a solver fills it on the destination chain.
3. The settlement `RedeemEscrow` POST request is delivered by any relayer to the source chain's `IntentGatewayV2.onAccept()`, which calls `withdraw()`.
4. Inside `withdraw()`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `success = true` (the call didn't revert) but the token internally returned `false` and did not transfer any balance.
5. `if (!success) revert TransferFailed();` does not trigger; `_orders[body.commitment][token] -= amount` proceeds and `EscrowReleased` is emitted, even though the solver received nothing.
6. The escrowed tokens remain locked in the `IntentGatewayV2` contract with no remaining accounting path to withdraw them — permanent fund loss for the solver (or user, on the refund path).
