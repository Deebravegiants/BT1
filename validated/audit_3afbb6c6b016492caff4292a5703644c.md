### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant attribution of webhook payloads - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating an HMAC computed over the raw body only, but then trusts the `shop-domain` header — which is *not* part of the signed material — to attribute the request to a tenant when building `WebhookMetadata` passed to the app's handler.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the signature from `verifiable_query.to_signable_string` and compares it against the `hmac` header using the app's single, shop-independent `Context.api_secret_key`: [1](#0-0) 

For webhooks, `Request#to_signable_string` returns only `@raw_body`; none of the identifying headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, `shopify-api-version`) are included in the signed payload: [2](#0-1) 

`Registry.process` validates only that HMAC, then unconditionally reads `request.shop` (sourced from the unauthenticated `shop-domain` header) and forwards it to the app's handler as the tenant identity: [3](#0-2) 

Because a single Shopify app uses one `api_secret_key` shared across every shop that installs it, any merchant/tenant that has installed the app can generate an HTTP request whose HMAC validates (using a body they legitimately received a webhook for, or one they can trigger themselves), then modify only the `shop-domain` header to name a different, victim shop before delivering it to the app's webhook endpoint. The HMAC check in `HmacValidator.validate` (binds body ↔ secret) still passes because it never looks at the header, so `Registry.process` proceeds to call the handler with `shop: <attacker-chosen shop>` alongside the (attacker-influenced) body. This breaks the identity binding `shop authenticated by HMAC == shop attributed to the payload`: the HMAC only proves "some installer of this app sent this body," not "this specific shop sent this body."

The gem's own documentation instructs host apps to trust `data.shop` directly (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), so this is not merely a downstream misuse — the documented API surface itself hands out an unauthenticated tenant identifier as if it were verified.

### Impact Explanation
This is a cross-tenant confusion vulnerability: an unprivileged internet user who is merely a legitimate installer of the target app (no elevated privileges, no leaked secrets) can cause the app's webhook processing pipeline to attribute attacker-controlled webhook data to an arbitrary victim `shop` domain that also uses the same app. Depending on how the host app uses `data.shop` (e.g., to look up a merchant's session/store record to write data, queue jobs, or update state), this can lead to cross-tenant data corruption or unauthorized actions performed against a shop the attacker doesn't control — satisfying the "cross-tenant access" impact class.

### Likelihood Explanation
High feasibility for the entity performing the forgery: no secrets need to be leaked, only that the attacker is a real (if malicious) installer of the app, which is the normal "unprivileged internet user" position for a multi-tenant Shopify app. The only requirement is producing a request whose body has a valid HMAC under the shared app secret and then swapping the `shop-domain` header value, both of which are within an attacker's control at the HTTP layer since the header is not covered by the signature.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signed material, or independently verify that the `shop-domain` header corresponds to a shop actually authorized/registered for that specific webhook subscription (e.g., cross-check against the webhook_id's registered shop via the Admin API) before handing it to the handler. At minimum, document prominently that `data.shop` from `WebhookMetadata` is unauthenticated and must not be trusted without additional verification, and consider having `HmacValidator`/`Request#to_signable_string` incorporate the relevant headers into the signable string if compatible with Shopify's webhook signing scheme.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store (`attacker.myshopify.com`), a normal unprivileged action.
2. Attacker triggers/receives a legitimate webhook delivery for their own store, capturing the `raw_body` and its valid `X-Shopify-Hmac-Sha256` header (computed with the app's single shared secret).
3. Attacker (or any actor able to POST to the app's public webhook endpoint) replays the same raw body/HMAC but changes the `X-Shopify-Shop-Domain` header to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`; validation passes because only the body (unchanged) is signed: [4](#0-3) 
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and attacker-controlled `body`, and — per the gem's documented usage pattern — acts on behalf of the victim shop.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
