### Title
Accumulated rounding drift between `Pair`'s frozen `k` and its real reserves triggers an unrecoverable arithmetic-underflow revert, permanently bricking a curve token's trading and graduation - (File: `packages/contracts/src/Router.sol`, `packages/contracts/src/Pair.sol`)

### Summary
The NimBLE advisory is a reachable-assertion class bug: a value accepted by a parser without full validation lets a later internal invariant check fail, causing an unconditional `assert`/panic that DoSes the affected component. alt.fun's bonding-curve AMM has the same class of bug: `Pair.swap` enforces the K-invariant with a `+1` grace band [1](#0-0)  while `Router._computeBuy` / `_computeSell` compute trade outputs by dividing the pair's *original, frozen* `k` by the *live* reserve [2](#0-1) [3](#0-2) . Because `k` is set once in `Pair.mint` and never recomputed [4](#0-3) , repeated ordinary buy/sell round-trips accumulate integer-division drift between the frozen `k` and the true `tokenReserve * assetReserve` product. Once the drift is large enough, `Router._computeBuy`'s `reserveToken - (k / newReserveAsset)` (or the symmetric `_computeSell` subtraction) underflows and panics (`0x11`), permanently reverting every subsequent buy and sell for that token.

### Finding Description
`Pair.mint` fixes `k = tokenReserve * assetReserve` exactly once at launch and it is never updated afterward [4](#0-3) . Every trade instead mutates only `tokenReserve`/`assetReserve`, gated by a *weakened* invariant check that allows the post-trade product to fall below the stored `k` by up to `tokenReserve + assetReserve + 1` (the "+1" on each side of the check) [5](#0-4) .

`Router._computeBuy` derives `tokensOut` from `reserveToken - (k / newReserveAsset)`, where `k` is the pool's fixed, never-updated constant, and `reserveToken`/`newReserveAsset` are the *live*, already-drifted reserves [2](#0-1) . Each floor-division in `_computeBuy`/`_computeSell` rounds the trade output slightly in the trader's favor, which is equivalent to shrinking the real reserve product below `k` a little more with every trade — while `k` itself stays static. Because `Pair.swap`'s `+1` grace band only checks that the *post-trade* product doesn't fall too far below `k` in that single step, it does nothing to stop this drift from *accumulating* across many trades.

Once enough ordinary buy/sell round-trips have executed on a given token's curve, the accumulated drift makes `k` large relative to the actual `reserveToken`/`reserveAsset` state. On the next buy, `k / newReserveAsset` (computed against the stale, oversized `k`) can exceed the live `reserveToken`, so `reserveToken - (k / newReserveAsset)` underflows and the call reverts with an arithmetic panic. The identical shape exists in `_computeSell`'s `reserveAsset - (k / newReserveToken)` [3](#0-2) . Unlike `Bonding.finalizeGraduation`'s deliberately saturating subtractions that were added specifically to avoid exactly this Panic-bricking failure mode [6](#0-5) , `Router._computeBuy`/`_computeSell` have no such guard — every buy and sell on the curve routes through these unprotected subtractions [7](#0-6) [8](#0-7) .

Once this state is reached, both `Bonding.buy` and `Bonding.sell` revert unconditionally for that token (they call straight through to `Router.buy`/`Router.sell` → `_computeBuy`/`_computeSell` [9](#0-8) [10](#0-9) ). The only path off `Lifecycle.Curve` besides trading is `triggerGraduation`, which is gated by `canGraduate` reading `assetReserve` against the USD threshold or `tokenBalance()==0` [11](#0-10)  — if the token has not yet crossed that threshold when the panic state is reached, it can neither trade nor graduate, permanently locking every trader's LT and every holder's tokens inside the `Pair`.

### Impact Explanation
This permanently freezes trader and creator funds held in the affected `Pair`: LT deposited by buyers and tokens held by sellers/creators become unrecoverable once the curve is bricked, since neither `buy` nor `sell` can execute and `triggerGraduation`/`finalizeGraduation` require `canGraduate` to already be true. This satisfies the "permanent freezing of trader, creator … funds" bar. Because any unprivileged trader can drive the accumulation simply by repeatedly buying and selling through `Zap.buy`/`Zap.sell` (no privileged role required), the vulnerability is reachable by a single unrelated wallet.

### Likelihood Explanation
Reachability requires only ordinary, permissionless `Zap.buy` / `Zap.sell` calls (or direct `Bonding.buy`/`sell` via an allowlisted router path already used by every user) — no special LT behavior, no pre-seeding, and no privileged access. The exact number of round-trips needed to accumulate enough drift depends on reserve magnitudes and rounding at each step, but the drift is monotonic and one-directional (each trade can only push the real product further below the frozen `k`, never back toward it), so the failure state is deterministically reachable given enough trade volume on a single token, which is plausible for any actively-traded low/mid-cap curve token, especially one traded by bots doing many small round-trips.

### Recommendation
Bound `Router._computeBuy`/`_computeSell`'s subtractions the same way `Bonding.finalizeGraduation` already treats analogous subtractions elsewhere in the codebase: saturate at zero (or explicitly cap `k / newReserve` at the live opposing reserve) instead of allowing an unchecked panic, and/or periodically resynchronize `k` to the actual `tokenReserve * assetReserve` product on each successful swap rather than freezing it permanently at mint-time, closing the accumulating drift entirely.

### Proof of Concept
1. Launch a token via `Zap.createToken`, seeding `Pair.mint` with `k = totalSupply * virtualLtReserve` [12](#0-11) .
2. Repeatedly call `Zap.buy` followed by `Zap.sell` on the same token with amounts sized so each round-trip's floor-division in `Router._computeBuy`/`_computeSell` shaves the real `tokenReserve * assetReserve` product further below the pool's frozen `k`, while `Pair.swap`'s `(x+1)(y+1) ≥ k` check keeps admitting each individual step [1](#0-0) .
3. After sufficient rounds, submit one more `Zap.buy`; `Router._computeBuy`'s `tokensOut = reserveToken - (k / newReserveAsset)` underflows because `k / newReserveAsset` (using the stale oversized `k`) now exceeds the drifted-down `reserveToken`, reverting with a Solidity arithmetic panic [13](#0-12) .
4. Confirm every subsequent `Zap.buy`/`Zap.sell` for that token now reverts identically, and that `Bonding.canGraduate` remains false, leaving the token's curve permanently stuck with LT/tokens locked in the `Pair`.

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }

    function canGraduate(
        address token_
    ) public view returns (bool) {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[token_];
        if (info.creator == address(0)) return false;
        if (info.lifecycle != Lifecycle.Curve) return false;

        address pair = info.pair;
        if (IPair(pair).tokenBalance() == 0) return true;

        (, uint256 assetReserve) = IPair(pair).getReserves();
        uint256 realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair);
        uint256 valueUsd = (realLtRaised * IBounceLeveragedToken(info.ltAddress).exchangeRate()) / 1e18;
        return valueUsd >= $.graduationThresholdUsd;
    }
