### Title
Missing swap deadline in `EvmHost.dispatch()` allows delayed/sandwiched fee-swap execution - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)` swap native tokens for the fee token via `IUniswapV2Router02.swapETHForExactTokens`, but pass `block.timestamp` as the swap `deadline`. This is the same anti-pattern as the referenced report: a deadline resolved to the *execution-time* timestamp provides no protection at all, because it is impossible for `block.timestamp` to ever be less than itself when the transaction is finally mined.

### Finding Description
Both dispatch entry points build the swap deadline inline from `block.timestamp` at the moment the transaction executes, not at submission time: [1](#0-0) [2](#0-1) 

Because `deadline = block.timestamp` is evaluated by the EVM inside the very transaction being validated, the Uniswap V2 router's `ensure(deadline)` check (`require(deadline >= block.timestamp)`) is always trivially satisfied regardless of how long the transaction sat in the mempool before inclusion. This means a block producer, sequencer, or any actor with transaction-ordering power over these public, unprivileged `dispatch()` calls can hold a submitted `dispatch()` transaction (or reorder it) and execute it later, at an arbitrary point where the ETH/feeToken price has moved unfavorably, then sandwich it for MEV extraction. There is no way for the caller to bound the staleness window of their own transaction, unlike the wrapper contracts in this same codebase (`UniV3UniswapV2Wrapper`, `UniV4UniswapV2Wrapper`), which correctly accept an explicit `deadline` parameter from the caller.

### Impact Explanation
`dispatch()` is the primary unprivileged entry point any user or relayer uses to submit POST/GET requests to Hyperbridge while paying protocol fees in native token. Because the swap has no real staleness bound, a delayed or sandwiched execution can force the caller's ETH to be swapped for the fee token at a worse-than-expected rate, directly causing a fund loss for the dispatcher on every native-fee dispatch. Since this affects the core message-dispatch path (reachable from any submitted transaction) rather than an admin-only function, and results in concrete value extraction from users, this is a Medium severity issue.

### Likelihood Explanation
Likelihood is high on any chain with private mempools, MEV-aware block builders/sequencers, or high native-token payment volume through `dispatch()`, since exploitation requires no special privilege beyond ordinary block-production/ordering influence and can be triggered on essentially every native-fee dispatch call.

### Recommendation
Allow callers to supply their own `deadline` (and ideally an `amountInMaximum`/slippage bound distinct from `msg.value`) for the `DispatchPost`/`DispatchGet` structs, and pass that caller-supplied deadline to `swapETHForExactTokens`, mirroring the pattern already used correctly in `UniV3UniswapV2Wrapper.swapETHForExactTokens`/`swapExactTokensForETH`.

### Proof of Concept
1. A dispatcher calls `EvmHost.dispatch(DispatchPost)` with `msg.value` sized against the current WETH/feeToken price to cover `post.fee`.
2. The transaction sits in the mempool; a block builder/validator with ordering control delays or reorders inclusion of this transaction until the price has moved unfavorably (or sandwiches it with front/back-run trades on the local Uniswap V2 pool).
3. When finally included, `deadline = block.timestamp` is set to the current block's timestamp at inclusion, so `swapETHForExactTokens`'s `ensure(deadline)` check always passes — there is no revert protecting the caller from the staleness/price movement.
4. The dispatcher's ETH is swapped at the worse price (up to the full `msg.value`), realizing a loss compared to the rate they expected when submitting the transaction.
