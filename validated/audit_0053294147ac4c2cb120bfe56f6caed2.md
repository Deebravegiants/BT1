### Title
Webhook `shop` (and `topic`) attribution is not covered by the HMAC signature, allowing replay of a genuine webhook under a forged tenant identity - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authentic for whatever `shop` value is in the `x-shopify-shop-domain` header once `Utils::HmacValidator.validate` succeeds. However, the HMAC signature only covers the raw request body, not the `shop` (or `topic`) header. This is the same class of bug as the reported issue: a value that is *acted on* (here, the tenant/shop identity used to route and attribute webhook data) is not *covered by the cryptographic check* that is supposed to authenticate the request (here, the HMAC), so the two can be made to disagree.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `shop`, `topic`, `api_version`, and `webhook_id` are read straight from HTTP headers, independent of the signed payload: [2](#0-1) 

`Registry.process` validates only that `hmac` matches `to_signable_string` (i.e., the body) using the app's shared `api_secret_key`, and then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the host app's handler: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` only ever hashes `verifiable_query.to_signable_string`, so for a `Webhooks::Request` this is exclusively the body: [4](#0-3) 

The identity binding the gem should guarantee is: `hmac_valid(body, secret) == true` implies `shop == the shop for which Shopify actually generated this request`. In reality it only proves `body` integrity; `shop` is an unauthenticated header value passed through unchanged.

Because a single app has one `client_secret`/`api_secret_key` shared across every merchant that installs it, an unprivileged user can:
1. Install the target app on their own (attacker-controlled) Shopify store — a normal, unprivileged action for any public app.
2. Receive a legitimate webhook from Shopify for their own shop; it carries a valid `x-shopify-hmac-sha256` computed with the app's shared secret over the body they fully control (webhook bodies for topics like `orders/create`, `customers/create`, etc. contain data the attacker can influence by creating/editing records in their own store).
3. Replay that exact HTTP POST to the target app's public webhook endpoint, changing only the `x-shopify-shop-domain` header to the victim shop's domain.
4. `HmacValidator.validate` still succeeds, because it only checks the body, and `Registry.process` calls the handler with `shop: <victim-shop>` and attacker-controlled `body`.

### Impact Explanation
This crosses a tenant boundary: data that Shopify never actually associated with the victim shop is delivered to the host application labeled as belonging to that shop. Any handler that uses `WebhookMetadata#shop` to look up the corresponding session/tenant and perform actions (store order data, update customer records, trigger app-side side effects tied to that merchant) can be made to act on forged, attacker-chosen content under another merchant's identity — a cross-tenant data-integrity/authentication issue, consistent with the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires: (a) the ability to install the target public app on any Shopify store (available to any store owner, no special privilege), and (b) the ability to POST arbitrary headers/body to the app's public webhook endpoint (trivial, since it's an internet-reachable, unauthenticated route by design — its only defense is the HMAC check). No access token, `api_secret_key`, or privileged account is required. This is realistically exploitable by any unprivileged internet user who can install a public app.

### Recommendation
Bind the tenant identity to the authenticated payload instead of trusting an unauthenticated header:
- Include `shop` (and ideally `topic`) inside `to_signable_string` for `ShopifyAPI::Webhooks::Request`, matching how `Auth::Oauth::AuthQuery#to_signable_string` already includes `shop` in its signed parameters, or
- Have `Registry.process` cross-check `request.shop` against an independently-known/authorized set of shop domains for the app before dispatching to the handler, and document that host apps must not treat `WebhookMetadata#shop` as authenticated unless it is bound to the signature.

### Proof of Concept
1. Attacker installs the target public app on their own store `attacker.myshopify.com`, obtaining a legitimate webhook delivery for `orders/create` with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker crafts request:
```
POST /callback/orders/create HTTP/1.1
x-shopify-topic: orders/create
x-shopify-hmac-sha256: H
x-shopify-shop-domain: victim-shop.myshopify.com
x-shopify-webhook-id: <reused-or-arbitrary>
x-shopify-api-version: 2024-01

B
```
3. Host app calls:
```ruby
ShopifyAPI::Webhooks::Registry.process(
  ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)
)
```
4. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:13-22`) recomputes HMAC over `B` only and it matches `H`, so validation passes.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-199`) invokes the registered handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, even though Shopify never sent this webhook for `victim-shop.myshopify.com`.

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
