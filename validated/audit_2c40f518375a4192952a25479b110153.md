### Title
Unauthenticated cross-chain source in `pallet-ismp-demo::on_accept` allows unbacked minting via forged Polkadot/Kusama messages - (File: `modules/pallets/demo/src/lib.rs`)

### Summary
`IsmpModuleCallback::on_accept` in `pallet-ismp-demo`, which is wired directly into the production `gargantua` runtime's ISMP router, mints native currency to an arbitrary account decoded from an incoming POST request body whenever the request's `source` is any `StateMachine::Polkadot(_)` or `StateMachine::Kusama(_)`, with **no check that the request came from the expected peer module/pallet on that chain**. This mirrors the root cause of the Evmos `GHSA-5jgq-x857-p8xw` advisory: trusting an unauthenticated sender/recipient field from any connected chain to move/mint value to an attacker-chosen address.

### Finding Description
The router `ProxyModule::on_accept` in `parachain/runtimes/gargantua/src/ismp.rs` dispatches any inbound POST request addressed to `pallet_ismp_demo::PALLET_ID` straight to `pallet_ismp_demo::IsmpModuleCallback::<Runtime>::default().on_accept(request)`: [1](#0-0) 

Inside that callback, for any `source_chain` matching `StateMachine::Polkadot(_)` or `StateMachine::Kusama(_)` — i.e. **any** parachain id, not just a registered/authorized peer — the request body is decoded into a `Payload { to, from, amount }` and the `amount` is minted directly into `payload.to` via `NativeCurrency::mint_into`: [2](#0-1) 

There is no verification of `request.from` (the sending module/pallet id on the source chain) against a registered/expected pallet id, and no check that `source_chain`'s specific para-id is an authorized counterparty. Contrast this with every other production app in this codebase, which enforces exactly this kind of check before minting or releasing value:
- `HyperFungibleToken.onAccept` verifies `_supportedChains[request.source]` matches `request.from` before minting: [3](#0-2) 
- `ExtrinsicIntents._authenticate` verifies `request.from` against the registered gateway instance for `request.source` before releasing escrow: [4](#0-3) 
- The Substrate `pallet-hyper-fungible-token` has an explicit test asserting unknown source contracts/pallets are rejected: [5](#0-4) 

`pallet-ismp-demo` has none of this. Any state machine that ISMP considers connected as `Polkadot(x)` or `Kusama(x)` for any `x` can send a POST to `PALLET_ID` (`b"ismp-ast"`) with an arbitrary `Payload{to: <attacker-controlled AccountId>, from: <anything>, amount: <arbitrary>}` and the pallet will mint that `amount` of native currency to `to`, with no economic backing (no corresponding burn/escrow on any real source chain, since the "source chain" is only checked by state-machine type, not identity).

This satisfies the ISMP handler's guarantee that the request is provably from the claimed chain (membership proof against that chain's state, per `modules/ismp/core/src/handlers/request.rs`), but the vulnerability is that `on_accept` accepts messages from *any* module on *any* chain of the right family, rather than only from an authorized/registered peer pallet — exactly the class of bug in the Evmos report (accepting IBC transfers from any connected chain that impersonates the expected sender, instead of restricting to authorized channels/modules).

### Impact Explanation
Any actor who can stand up or control a chain that is connected to this Hyperbridge deployment as a `Polkadot(_)` or `Kusama(_)` state machine (e.g., a permissionless/canary parachain, or any chain whose consensus client has been onboarded) can dispatch a forged POST request to `PALLET_ID` (`ismp-ast`) and mint unlimited native currency to any account on the Hyperbridge/Gargantua runtime. This is an unbacked mint of the native token — a direct, permanent value-creation/theft vector with no corresponding burn, matching the report's "unbacked mint" impact category.

### Likelihood Explanation
Reachability requires only a single relayed ISMP POST request from a connected (or newly connected) Polkadot/Kusama-family state machine with a valid membership proof for a message the attacker's own chain authored — the attacker fully controls the message contents (`to`, `from`, `amount`) on their own chain, so no privileged Hyperbridge action or governance compromise is needed. The chain identity check is only by `StateMachine` variant/para-id, not by module authorization, so no cross-chain trust relationship needs to be broken — only that some Polkadot/Kusama-family chain is connected to the network, which is a standard, permissionless-by-design operational state for Hyperbridge.

### Recommendation
Add source-module authentication to `IsmpModuleCallback::on_accept` (and `on_timeout`) analogous to the checks already present in `HyperFungibleToken`/`ExtrinsicIntents`: maintain a registry of authorized peer pallet ids per `StateMachine`/para-id, and reject (`Err`) any request whose `request.from` does not match the expected peer for `request.source`. If `pallet-ismp-demo` is intended purely as a demonstration/testing pallet, it should not be wired into the production `gargantua` runtime's live ISMP router without this authorization, or it should be feature-gated out of production builds.

### Proof of Concept
1. Attacker operates or gains connection of a chain onboarded to Hyperbridge as `StateMachine::Polkadot(9999)` (or any para id not specifically the legitimate demo-pallet counterparty).
2. From that chain, the attacker's own pallet dispatches an ISMP POST request with `to = PALLET_ID.to_bytes()` (`b"ismp-ast"`), and body = SCALE-encoded `Payload { to: <attacker AccountId>, from: <arbitrary>, amount: <large value> }`.
3. A relayer submits the `RequestMessage` with a valid membership proof (this proof only proves the message exists on the attacker's own chain, which the attacker fully controls) to `pallet-ismp`'s `handle` on Gargantua: [6](#0-5) 
4. The router dispatches to `pallet_ismp_demo::IsmpModuleCallback::on_accept`, which matches `StateMachine::Polkadot(_)`, decodes the payload, and mints `amount` into the attacker's account with no check on which module/chain sent it: [7](#0-6) 
5. The attacker now holds newly minted, unbacked native currency on Gargantua, repeatable for any amount and any number of times.

impl<T: Config> IsmpModule for IsmpModuleCallback<T> {
	fn on_accept(&self, request: PostRequest) -> Result<Weight, anyhow::Error> {
		let source_chain = request.source;

		match source_chain {
			StateMachine::Evm(_) => Pallet::<T>::deposit_event(Event::Request {
				source: source_chain,
				data: unsafe { String::from_utf8_unchecked(request.body) },
			}),
			StateMachine::Polkadot(_) | StateMachine::Kusama(_) => {
				let payload =
					<Payload<T::AccountId, <T as Config>::Balance> as codec::Decode>::decode(
						&mut &*request.body,
					)
					.map_err(|_| IsmpError::Custom("Failed to decode request data".to_string()))?;
				<T::NativeCurrency as Mutate<T::AccountId>>::mint_into(
					&payload.to,
					payload.amount.into(),
				)
				.map_err(|_| IsmpError::Custom("Failed to mint funds".to_string()))?;
				Pallet::<T>::deposit_event(Event::<T>::BalanceReceived {
					from: payload.from,
					to: payload.to,
					amount: payload.amount,
					source_chain,
				});
			},
			source => Err(IsmpError::Custom(format!("Unsupported source {source:?}")))?,
		}

		Ok(weight())
	}
