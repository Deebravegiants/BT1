Audit Report

## Title
Missing `return` after failed email-claim extraction lets OIDC login continue and create a valid session even when the client is told the request failed - ([File: core/sessions/oidcauth/oidc.go])

## Summary
In `handleTokenExchange`, the `email, ok := claims["email"].(string)` check at [1](#0-0)  writes a `500` response via `c.String(...)` when the assertion fails but does not `return`, unlike every other error branch in the same function (e.g. [2](#0-1) , [3](#0-2) , [4](#0-3) , [5](#0-4) ). Execution falls through and still inserts an `oidc_sessions` row, audits a successful login, and sets the session cookie, so a session is created and returned to the client even though the HTTP response signaled failure.

## Finding Description
After ID token verification and claim extraction, the code performs:
```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims. error: %v", err)
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
}
```
at [1](#0-0) . There is no `return` statement, so the function proceeds to compute `role` from `IDClaimsToUserRole` at [6](#0-5) , insert the new session row via `oi.ds.ExecContext(... INSERT INTO oidc_sessions ...)` using the empty `email` at [7](#0-6) , call `oi.auditLogger.Audit(audit.AuthLoginSuccessNo2FA, ...)` at [8](#0-7) , and finally set the session cookie and write a superfluous `200 OK` response at [9](#0-8) . All sibling error paths in this exact function correctly `return` after writing their error response, confirming this is an isolated omission rather than intended behavior.

The role assigned to the session is derived from cryptographically verified group claims (`idClaims`, from the signed ID token), not from `email`, so this bug does not by itself let an unauthorized party forge a role — it requires the user to already have successfully completed real OIDC/IdP authentication with valid group claims. The break is specifically that the client-visible `500` response does not correspond to "no session was created": a working, persisted session and `Set-Cookie` are issued regardless of the email-extraction outcome.

## Impact Explanation
This breaks the invariant that a `500` response from `/oidc-login` means no session exists, resulting in a persisted `oidc_sessions` row (with `user_email = ''`) and a valid `Session-ID` cookie for a role-mapped session that `AuthorizedUserWithSession`/`AuthenticateBySession` will accept on subsequent requests. This is a real logic defect matching the "checked-but-ignored return value" bug class and falls under node API authentication/session-management correctness.

## Likelihood Explanation
Triggering it requires the upstream OIDC IdP's ID-token claims to omit or malform the `email` field while still supplying valid group claims — an edge case dependent on IdP configuration/behavior rather than something an unprivileged remote attacker can freely manufacture through the node's public endpoint alone, since the group/role claims must still be legitimately signed by the IdP. It does not enable privilege escalation beyond what the IdP already granted; it only causes an inconsistent HTTP-response-vs-session-state outcome for that already-authenticating user.

## Recommendation
Add `return` immediately after the `c.String(http.StatusInternalServerError, "Failed to get email from claims")` call in the `!ok` branch at [1](#0-0) , matching the pattern used by every other error branch in `handleTokenExchange`. The similar missing `return` after the `oidc_sessions` INSERT error at [10](#0-9)  should also be fixed for consistency.

## Proof of Concept
1. Stand up or proxy an OIDC provider whose token exchange returns valid, signed group/role claims but an ID token lacking the `email` field (or with `email` as a non-string type).
2. Complete the OIDC redirect flow to `/oidc-login/callback`, driving `handleTokenExchange`.
3. Observe: response is `500 "Failed to get email from claims"`, but the response also carries `Set-Cookie` for `webauth.SessionIDKey`, and a new `oidc_sessions` row is created with `user_email = ''` and a role mapped from the verified group claims — confirmed by reading [11](#0-10) .
4. Replay the returned session cookie against an authenticated endpoint to show it is accepted despite the client having received a failure response.
