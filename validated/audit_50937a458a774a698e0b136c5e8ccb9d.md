### Title
Webhook shop/topic fields trusted from unauthenticated headers while HMAC signs only the raw body, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then dispatches to a handler using the `shop` and `topic` values taken directly from HTTP headers, which are never covered by that HMAC. Anyone who possesses one validly-signed webhook body/HMAC pair (e.g. a legitimate webhook delivered to their own installed app) can replay that same body+HMAC to the app's webhook endpoint while freely rewriting the `x-shopify-shop-domain` and `x-shopify-topic` headers, causing the app to process the payload as if it originated from a different shop/topic.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` and `topic` are read straight from request headers with no cryptographic binding to the body: [2](#0-1) 

`Utils::HmacValidator.validate_signature` computes the HMAC over exactly that signable string (the body only) and compares it to the `hmac` header value: [3](#0-2) 

`Registry.process` performs the HMAC check and then trusts `request.topic`/`request.shop` (unauthenticated headers) to select the handler and populate the `WebhookMetadata` passed into application code: [4](#0-3) 

This is exactly the bug class from the reference report: a field that is acted upon (`shop`, used as the tenant identity for the delivered webhook) is not covered by the integrity check (`HMAC` only signs `@raw_body`). Formally the binding the gem should enforce is:
`HMAC_valid(body, shop, topic) == HMAC_valid(body)`
but the implementation only checks the right-hand side, so `shop`/`topic` can be freely substituted post-hoc without invalidating the signature.

Exploit path: an unprivileged internet user who installs the app on their own (attacker-controlled) shop receives genuine outbound webhooks from Shopify — each is a valid `(body, hmac)` pair signed with the app's real `client_secret` (the attacker never needs to know the secret). The attacker then POSTs that same `body`/`hmac` to the app's public webhook endpoint, but swaps the `x-shopify-shop-domain` header to a victim shop's domain (and optionally the `x-shopify-topic` header to any topic the app has registered a handler for, as long as the JSON body shape satisfies that handler). Because `Utils::HmacValidator.validate` only re-derives the HMAC from the body, the forged headers pass verification unchanged, and the handler executes believing the event is authentic for the victim shop/topic.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook delivery: an attacker can make the app process attacker-chosen `shop`/`topic` metadata alongside a genuinely-signed body, without ever needing the app's `client_secret`, an access token, or the victim's credentials. Any app logic that keys off `WebhookMetadata#shop` (e.g. looking up that shop's stored session/access token to act on its behalf, or writing to that shop's records) can be tricked into acting under an attacker-chosen tenant identity — a cross-tenant access primitive, matching the Critical impact bucket in scope.

### Likelihood Explanation
The only prerequisite is that the attacker be able to install the target app on any shop they control (or otherwise obtain one legitimately-signed webhook delivery), which is available to any unprivileged internet user for a self-serve Shopify app. No secret material, TLS interception, or privileged account is required — only a normal HTTP POST to the app's public webhook route with edited headers.

### Recommendation
Include `shop`, `topic`, and `webhook_id`/`api_version` in the signable string that the HMAC is computed over (or otherwise cryptographically bind them to the body), so that `Utils::HmacValidator.validate` fails if any of these header-derived fields are altered relative to what Shopify actually signed. At minimum, update `Webhooks::Request#to_signable_string` to include the shop domain and topic, and have `HmacValidator` verify against that composite string instead of the raw body alone.

### Proof of Concept
```ruby
# 1. Attacker installs the app on their own shop "attacker.myshopify.com"
#    and receives a real webhook delivery from Shopify:
raw_body = '{"id": 123, "note": "hello"}'
real_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_CLIENT_SECRET, raw_body)
# headers as delivered by Shopify:
# x-shopify-topic: orders/create
# x-shopify-hmac-sha256: Base64.encode64(real_hmac)
# x-shopify-shop-domain: attacker.myshopify.com

# 2. Attacker replays the identical body+hmac to the app's webhook endpoint,
#    but rewrites the shop header to a victim shop:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(real_hmac), # unchanged, still valid
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => Utils::HmacValidator.validate(request) returns true (body unchanged),
#    handler executes with data.shop == "victim-shop.myshopify.com"
```
