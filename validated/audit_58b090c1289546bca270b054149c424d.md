### Title
Webhook `shop`, `topic`, and `webhook_id` fields are trusted from unauthenticated HTTP headers, not bound by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#hmac` and `Registry.process` verify only the raw request body against the HMAC signature. The `shop`, `topic`, `webhook_id`, and `api_version` values consumed by the handler are all pulled from HTTP headers that are never covered by that signature, so an attacker who can produce one valid `(body, hmac)` pair can freely swap in a different `shop-domain` header and have it processed as if it came from that other shop.

### Finding Description
`Utils::HmacValidator.validate` computes the expected signature from `verifiable_query.to_signable_string` and compares it to `verifiable_query.hmac`: [1](#0-0) 

For webhooks, `Webhooks::Request` implements `VerifiableQuery` by making `to_signable_string` return only `@raw_body`: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from attacker-supplied HTTP headers (`x-shopify-shop-domain`, `x-shopify-topic`, etc.), independent of the signed body: [3](#0-2) 

`Registry.process` validates only the HMAC of the body, then dispatches the handler using `request.shop` from the unauthenticated header, alongside `request.parsed_body` and `request.webhook_id`: [4](#0-3) 

The identity binding broken is: **shop authenticated by the HMAC (none — HMAC only covers `raw_body`) vs. shop trusted and handed to the host application as the tenant key** (`request.shop` inside `WebhookMetadata`). The signature proves the body wasn't tampered with and that the sender knows the app's secret key (or a valid signed payload), but it proves nothing about which shop the body belongs to.

### Impact Explanation
Any unprivileged internet user can install the merchant's Shopify app on their own store (a normal, unprivileged action) and thereby obtain a validly HMAC-signed webhook payload for a topic/body of their choosing (e.g., `customers/data_request`, `shop/update`, or any topic whose body they can shape via their own store's data). They can then replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) header with a victim shop's domain. `Registry.process` only checks `Utils::HmacValidator.validate(request)` — which passes because the body/hmac pair is valid — and then invokes the handler with `shop: request.shop` set to the victim's domain. If the host application uses `data.shop` to load the victim's session/access token (the documented and expected usage pattern for webhook handlers), the attacker causes the app to process attacker-controlled data under the victim shop's identity, i.e., cross-tenant confusion/access using the victim's stored credentials.

### Likelihood Explanation
Requires only a store the attacker controls with the target app installed (to legitimately obtain one valid signed payload) and the ability to send arbitrary HTTP requests to the app's public webhook endpoint with custom headers — no access token, `api_secret_key`, or other privileged credential is needed, and no host-application misuse beyond following the gem's own documented `shop:` field is required.

### Recommendation
Bind the identity-relevant metadata into the signed payload before verifying it — e.g., include `shop`, `topic`, and `webhook_id` in `to_signable_string` (or verify them against a second HMAC/signature Shopify provides), or require the caller to additionally confirm the shop has an active session/installation before trusting `request.shop` for any privileged lookup, and treat `topic`/`webhook_id` similarly.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, obtaining a legitimate webhook delivery (`raw_body`, `x-shopify-hmac-sha256`) for topic `customers/data_request` (or any topic with attacker-influenceable content).
2. Attacker replays the exact `raw_body` and `x-shopify-hmac-sha256` header to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `raw_body` against the signature and succeeds.
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and `body` fully attacker-controlled, and if it loads the victim's session/access token keyed by `shop`, the attacker's payload is processed under the victim's tenant identity.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

        end
