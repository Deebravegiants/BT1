Confirmed. `CallDispatcher.sol` is a stateless, permissionless proxy contract shared by every order across `IntentGatewayV2`, `HyperFungibleToken`, and `WrappedHyperFungibleToken` deployments on a chain [1](#0-0) . It executes arbitrary attacker/solver-supplied `Call[]` in its own context via `to.call{value: call.value}(call.data)` [2](#0-1) , and postdispatch calldata is documented to route received tokens "through a DeFi protocol before reaching the beneficiary" — explicitly including deposits into lending protocols [3](#0-2) . After execution, `IntentsBase._execute` only sweeps the balances of the order's declared `output.assets` tokens back to the gateway; it has no knowledge of, and does not sweep, any ERC-4626 vault shares or other tokens the postdispatch calldata acquired [4](#0-3) . This is exactly the `VaultRouter` bug pattern: a single shared contract acts as `msg.sender`/depositor to a third-party vault on behalf of many unrelated end users, and any vault gating deposits on `balanceOf(msg.sender)` (the reported root cause, and a documented ERC-4626 pattern the codebase itself works around elsewhere via `maxDeposit` checks in `VaultFundingPlanner.ts`) permanently blocks that shared caller once its balance/share holding crosses the cap.

### Title
Permanent DoS of postdispatch/predispatch composability for *any* order routing through a per-depositor-capped vault via the shared `CallDispatcher` - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher` is a single, chain-wide, stateless relay contract shared by every `IntentGatewayV2` order (and every `HyperFungibleToken`/`WrappedHyperFungibleToken` message) that carries postdispatch/predispatch calldata. Any order can instruct it to deposit received output tokens into an ERC-4626-style vault (a documented, supported use case). If that vault enforces a per-depositor deposit cap keyed on `balanceOf(msg.sender)` — the exact anti-pattern from the referenced BakerFi finding — the cap accrues against `CallDispatcher`'s own address across *every unrelated order and every unrelated user* that ever deposits into that vault through it, because the gateway's sweep step only returns the order's declared output-asset token balances, never the vault shares the dispatcher received.

### Finding Description
- `CallDispatcher.dispatch` executes attacker/solver-supplied calls in its own context: `(bool success, bytes memory result) = to.call{value: call.value}(call.data);` [5](#0-4) . It has no owner, no per-order state, and is reused for every order on the chain.
- `IntentsBase._execute` dispatches `order.output.call` through this shared dispatcher and then sweeps only the tokens named in `order.output.assets` back to the gateway (`IERC20(token).balanceOf(dispatcher)` for each declared output token) [6](#0-5) . Vault shares minted to `CallDispatcher` by a `deposit()` call embedded in `order.output.call` are not among the declared output assets and are therefore never swept — they remain permanently held by `CallDispatcher`.
- `IntentGatewayV2._placeOrder`'s predispatch path follows the identical shape: assets are pushed to `dispatcher`, `dispatcher.dispatch(order.predispatch.call)` runs attacker-controlled calls, and only the declared `order.inputs` tokens are pulled back [7](#0-6) .
- Documentation confirms this "transfer-and-deposit into a lending protocol" pattern is an intended, advertised composability feature, not an edge case [8](#0-7)  and [3](#0-2) .
- Because `CallDispatcher` is the `msg.sender`/depositor to any such vault for every order that routes through it, any vault whose deposit limit is enforced against `balanceOf(msg.sender)` (rather than the true beneficiary) treats all unrelated users' orders as a single depositor. An unprivileged user places one order whose postdispatch calldata deposits into a capped vault, permanently (or until the vault manually adjusts the cap) filling `CallDispatcher`'s share of that vault's deposit limit. Every subsequent order — from any other user, for any other purpose — that includes a postdispatch call depositing into the same vault will revert at the vault's cap check, since it is still checking the same shared `CallDispatcher` address.

### Impact Explanation
This is a permanent denial-of-service on the intent-gateway's documented composable execution feature for any capped-deposit vault reachable from a single, chain-wide, immutable `CallDispatcher` instance. Once poisoned, the affected vault path is unusable by any of the gateway's future orders/users, not just the attacker's own order — matching the "DoS of the router's deposit functionality" impact class from the referenced report, but with a strictly broader blast radius (every user of the intent gateway on that chain, rather than one router's own users).

### Likelihood Explanation
Any unprivileged party can place a single, ordinary `placeOrder`/`fillOrder` with `output.call` (or `predispatch.call`) targeting an ERC-4626 vault's `deposit()`, requiring no special privilege, no cooperation from other actors, and no unusual capital beyond a minimal deposit sized to reach the target vault's cap. The precondition is simply that some vault reachable via the shared `CallDispatcher` implements a per-`msg.sender` deposit cap — a common and documented ERC-4626 extension pattern, and the exact one the codebase itself defensively checks for elsewhere (`maxDeposit` handling in `VaultFundingPlanner.sweepChain`) [9](#0-8) .

### Recommendation
Do not let a single stateless, permanently-address-fixed `CallDispatcher` accumulate residual non-declared-asset balances (e.g., vault shares) across unrelated orders. Options: (1) deploy or route through a fresh, ephemeral per-order dispatcher/proxy (e.g., a minimal-proxy clone created per `placeOrder`/`fillOrder` call and self-destructed or abandoned after use) so no shared address ever accrues cross-user vault balance/deposit-limit state; (2) require postdispatch/predispatch calldata to end by sweeping *any* token balance the dispatcher holds (not just the declared input/output assets) back to the gateway or beneficiary, closing the residual-balance gap that lets vault shares accumulate; (3) document and warn integrators that any vault reachable through `CallDispatcher` composability must not gate deposits on `balanceOf(msg.sender)`/per-depositor caps, since `CallDispatcher` is a shared, unbounded-lifetime caller.

### Proof of Concept
1. Deploy (or identify) an ERC-4626-style vault `V` on a chain where `IntentGatewayV2`'s `CallDispatcher` address is `D`, where `V.deposit()` reverts once `V.balanceOf(msg.sender)` (post-deposit) exceeds `V.getMaxDeposit()` — mirroring the referenced BakerFi `VaultBase._depositInternal` check [10](#0-9)  (dispatch call site) — i.e., a vault whose cap logic checks the caller's balance rather than the ultimate order beneficiary's.
2. Attacker places an order whose `output.call` is a `Call[]` of: `V.approve(V, x)` then `V.deposit(x, D)` (dispatcher approves itself and deposits, receiving `x` vault shares to `D`), sized so `V.balanceOf(D)` lands at or above `V.getMaxDeposit()`.
3. `fillOrder` executes; `_execute` dispatches the calls, `D` receives vault shares; the sweep loop in `_execute` iterates only `order.output.assets` (the underlying token, whose balance in `D` is now zero because it was deposited) and finds nothing to sweep — the vault shares stay in `D` permanently [11](#0-10) .
4. A second, unrelated user places an order whose `output.call` also deposits into `V` via the same `D`. `V.deposit()` now reverts because `V.balanceOf(D)` is already at/above the cap — the second user's fill reverts and cannot use that composable path, even though they have no relation to the attacker's order.

## Calldata Execution

Both contracts support optional calldata execution on the destination chain via the `CallDispatcher`. By passing a non-empty `data` field in `SendParams`, the sender can trigger arbitrary contract calls on the destination chain immediately after tokens are minted or unlocked. This enables composable cross-chain workflows like transfer-and-swap (e.g., bridge USDC then swap to WETH via UniswapV2), transfer-and-stake, or transfer-and-deposit into a lending protocol — all in a single cross-chain operation.

The `data` field is an ABI-encoded `Call[]` array, where each `Call` specifies a target contract, a native value to forward, and the calldata to execute. On the destination chain, the HFT contract mints or unlocks tokens to the `to` address, then forwards the entire `data` payload to the `CallDispatcher`, which executes each call sequentially. If the calls need to spend the bridged tokens (e.g., approve then swap), set `to` to the `CallDispatcher` address so tokens are delivered directly to it.
