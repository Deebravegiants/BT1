### Title
Webhook `shop` (and `topic`) identity is not covered by the HMAC signature, enabling cross-tenant webhook forgery — ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, then hands the caller-supplied `shop`, `topic`, `webhook_id`, and `api_version` HTTP headers straight through to the app's handler as trusted identity fields — even though none of those headers are covered by the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` accessors instead read directly from HTTP headers that are never mixed into the signable string: [2](#0-1) .

`Utils::HmacValidator.validate` computes `HMAC-SHA256(Context.api_secret_key, verifiable_query.to_signable_string)` and compares it to the `hmac` header using `OpenSSL.secure_compare`: [3](#0-2) . Since `to_signable_string` is only the raw body, this check proves nothing about which shop, topic, or webhook id the payload is "for" — it only proves the body bytes were signed at some point with `Context.api_secret_key`, which is the single `client_secret` shared by an app across *all* installed shops (there is no per-shop signing key in this gem).

`Registry.process` then trusts the unauthenticated `shop` header as the tenant identity and forwards it to the app's handler: [4](#0-3) .

This breaks the intended identity binding: **`shop` used by the handler == `shop` the HMAC actually authenticates**. In reality, the HMAC authenticates only the body bytes; the `shop` (and `topic`/`webhook_id`) fields are attacker-controlled HTTP headers that ride along unauthenticated. The documentation confirms host apps are expected to trust `data.shop` from the handler payload as the webhook's shop identity without any additional binding: [5](#0-4) , and the "Process a Webhook" section states that `Registry.process` "will verify the request did indeed come from Shopify" — implying the whole request, including `shop`, is authenticated, which it is not: [6](#0-5) .

### Impact Explanation
Because `Context.api_secret_key` is a single app-wide secret (not per-shop), any attacker who controls one shop with the app installed can generate a real Shopify webhook delivery for their own shop (a resource fully under their control, e.g. an order or customer they create), capturing a genuinely-signed `(raw_body, hmac)` pair. They can then replay that exact body and HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header to point at a *different, victim* shop that also has the app installed. `HmacValidator.validate` will still pass because it only checks the body bytes against the shared secret, and `Registry.process` will invoke the app's handler with `shop: "<victim-shop>.myshopify.com"` and attacker-crafted body content. This is a cross-tenant identity/data injection: the attacker forges webhook events "from" a shop they do not own, potentially triggering data writes, notifications, fulfillment actions, GDPR/redact-topic side effects, or any tenant-scoped business logic keyed on `data.shop` in the host app. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any app that (a) has more than one shop install (typical for any real Shopify app) and (b) uses the webhook `shop` field from `WebhookMetadata` to select tenant context (the documented, intended usage pattern shown in `docs/usage/webhooks.md`). No credentials, TLS interception, or privileged access are required — only having installed the app to one's own store, which any merchant can do, and the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with modified headers.

### Recommendation
Bind the values the handler relies on to the signature: include `shop`, `topic`, and `webhook_id` in the signed content that `HmacValidator` verifies (e.g., have `Webhooks::Request#to_signable_string` incorporate the shop/topic headers alongside the body, consistent with how `Oauth::AuthQuery#to_signable_string` binds `shop`/`host`/`state` for OAuth), or otherwise cryptographically bind the header-derived shop to the request before it is exposed via `WebhookMetadata`. At minimum, the library should document explicitly and loudly that `data.shop`/`data.topic` are **not** authenticated by the HMAC and that host applications must independently verify the shop against a known/installed-shop list before acting on webhook data.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" with the target app installed.
# They trigger a real Shopify webhook for their own shop (e.g., orders/create)
# and capture the raw body + genuine "X-Shopify-Hmac-Sha256" header Shopify sent them.

captured_body = '{"id":1,"note":"forged payload attacker fully controls"}'
captured_hmac = "<valid Base64 HMAC Shopify computed with the app's shared client_secret>"

# Attacker replays it to the app's webhook endpoint, swapping only the shop header:
headers = {
  "X-Shopify-Topic"        => "orders/create",
  "X-Shopify-Hmac-Sha256"  => captured_hmac,       # still valid: HMAC only covers the body
  "X-Shopify-Shop-Domain"  => "victim-shop.myshopify.com", # forged tenant identity
  "X-Shopify-Webhook-Id"   => "attacker-chosen-id",
  "X-Shopify-Api-Version"  => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => Utils::HmacValidator.validate(request) returns true, because
#    to_signable_string == captured_body and Context.api_secret_key is the same
#    secret used to sign the attacker's own genuine webhook.
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
#    is invoked with attacker-controlled body, impersonating victim-shop.
```

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
