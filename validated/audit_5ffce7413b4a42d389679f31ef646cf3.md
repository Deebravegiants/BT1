The re-org bug in the external report hinges on a permissionless, incrementing ID scheme (`numMarkets` → `targetMarketID`) that lets a later transaction silently rebind an old identifier to a new, attacker-controlled resource after a chain re-org. Raydium AMM's on-chain reachable surface (`Initialize2`, `Deposit`, `Withdraw`, and the swap instructions) has no analogous indirection: every instruction that touches a pool requires the caller to supply the actual `AmmInfo` account pubkey directly as an account, and the program cryptographically validates the accompanying `$authority` PDA (`authority_id` derived from `AUTHORITY_AMM` seed and `nonce`) and the `AmmConfig` PDA on every call rather than resolving an integer counter to a market [1](#0-0) [2](#0-1) . The `AmmInfo` account itself, its `market`, and related fields are set once at `Initialize2` and are tied to the specific account address supplied at creation, not an incrementing index that a re-org could let an attacker "reuse" for a different pool [3](#0-2) [4](#0-3) . Since there is no `targetMarketID`-style numeric handle that offers/instructions reference indirectly, there is no reachable path in Deposit/Withdraw/swap/Initialize2 where a re-org could let an attacker inject a different, malicious pool under the same reference that a user's prior transaction depended on.
