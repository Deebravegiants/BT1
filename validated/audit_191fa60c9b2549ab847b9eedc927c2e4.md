### Title
Malicious swap route can inject a token transfer into the caller’s signed authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
Controller strategy entrypoints accept caller-supplied opaque route bytes and execute them through the configured router. Because route-selected third-party code runs below the caller’s authorized controller invocation, that code can add arbitrary `token.transfer(caller, attacker, amount)` calls to the simulated authorization tree. If the caller signs the poisoned tree, the attacker can steal wallet tokens unrelated to the lending position while the strategy still produces valid output and passes final risk checks. [1](#0-0) 

### Finding Description
`swap_collateral(caller, account_id, current, amount, new, swap)` authenticates `caller`, verifies account ownership or delegation, and forwards the caller-controlled `swap` bytes into the strategy swap path. [2](#0-1) 

`swap_tokens` invokes the configured router with those bytes and bounds only the controller’s own `token_in` grant: it authorizes exactly `token_in.transfer(controller, router, amount_in)`, checks measured spend, and requires positive measured output. [3](#0-2) 

That control does not bound what route-selected code asks the original `caller` to authorize. The route can name an attacker-controlled pool/venue; during simulation, a transfer from the caller to the attacker is recorded as a child of the caller’s `swap_collateral` authorization. If that returned tree is signed, enforcing auth accepts the injected transfer and the strategy completes. [4](#0-3) 

This is analogous to CVE-2015-8325: attacker-controlled input—the route payload rather than `LD_PRELOAD`—causes privileged execution context—the caller’s authorization tree rather than `/bin/login`—to perform an unintended privileged action.

### Impact Explanation
An attacker can steal any token balance held by the victim’s wallet, including assets never supplied to or listed by the protocol. In the regression proof, Alice holds `77_770_000_000` units of an unrelated token; a rogue hop transfers the full balance to the attacker while the requested collateral swap still succeeds. [5](#0-4) 

The loss is not limited to the swap input or the user’s lending collateral. Any caller-signed child invocation can move wallet funds, while controller-side output and solvency checks remain satisfied because they measure only the strategy’s controller balances and resulting account risk. [6](#0-5) 

Affected reachable entrypoints include `multiply`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral`; the demonstrated path is `swap_collateral`. [7](#0-6) 

### Likelihood Explanation
Exploitation requires the victim to submit a malicious route and sign the authorization tree containing the extra child transfer. The injected call cannot execute under an honest root-only signature; enforcing auth rejects it when the child is absent. [8](#0-7) 

This is nevertheless a realistic authorization-boundary failure because route bytes are opaque to the controller, route-selected contracts are not constrained by the controller, and ordinary simulation records the malicious child beneath the strategy invocation. The protocol’s own threat model places the burden on clients to detect unexpected children rather than enforcing the boundary in the strategy path. [1](#0-0) 

### Recommendation
Constrain route execution so route-selected contracts cannot attach caller-authorization children during lending strategies. Prefer a design where the router is invoked by the controller without inheriting any user-auth context, or enforce a route/venue allowlist for strategy execution.

At minimum, reject nested authorization expansion at the integration boundary and make the canonical controller/SDK path fail simulation or submission when the returned tree contains children beyond the expected input pull. The protocol should not rely solely on every wallet/client manually identifying malicious authorization children. [1](#0-0) 

### Proof of Concept
The repository contains a focused proof in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:

1. Alice supplies USDC and holds `77_770_000_000` units of an unrelated `wallet_token`.
2. The test configures a router whose caller-supplied route names `hop_pool`.
3. `RogueHopPool.swap` calls `wallet_token.transfer(alice, attacker, WALLET_BALANCE)`.
4. Alice invokes:
   `swap_collateral(alice, account_id, USDC_hub_asset, 50_000_000_000, ETH_hub_asset, malicious_route)`.
5. Simulation records the malicious token transfer as a child of Alice’s `swap_collateral` authorization.
6. Signing that poisoned tree allows the transfer: Alice’s wallet balance becomes zero and the attacker receives `WALLET_BALANCE`, while Alice receives the expected ETH collateral output. [9](#0-8)

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
