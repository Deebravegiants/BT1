### Title
Webhook `shop` identity field is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The reward-accounting bug in `Rewards.sol` is a class of "field trusted for accounting/identity purposes that is not actually bound by the verification mechanism protecting the transaction." The equivalent pattern in this gem is the webhook `shop` (tenant) field: `ShopifyAPI::Webhooks::Request` computes its HMAC only over the raw body, while the `shop` domain used for tenant attribution is read directly from an HTTP header that is never included in the signed bytes.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` verifies a `VerifiableQuery` by recomputing an HMAC over `verifiable_query.to_signable_string` and comparing it to the supplied `hmac`: [1](#0-0) 

For webhook requests, `to_signable_string` returns only `@raw_body` — the shop domain is *not* part of the signed content: [2](#0-1) 

The `shop` accessor is instead parsed straight from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` header: [3](#0-2) 

`Registry.process` validates the HMAC (over the body only) and then forwards `request.shop` — taken from the unauthenticated header — straight into the handler as the tenant identity, with no cross-check that the signed body actually corresponds to that shop: [4](#0-3) 

The equality that should hold is:
`shop used for tenant attribution (request.shop, from header) == shop bound inside the HMAC-signed bytes (to_signable_string)`

This equality does not hold: `to_signable_string` only contains `@raw_body`, so the header-derived `shop` is fully attacker-controlled and independent of the signature check. Because the HMAC secret (`api_secret_key`/`client_secret`) is a single per-app secret shared across every installed shop (not a per-shop secret), any unprivileged user who has legitimately installed the app on their own store can obtain a genuine `(raw_body, hmac)` pair for their own shop's webhook event, then replay it to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (it never looks at the header), and `WebhookMetadata` is constructed with the attacker-chosen `shop` value: [5](#0-4) 

Any host application that uses `WebhookMetadata#shop` to key persistence, look up a session/access token, or attribute the event to a merchant (which is the gem's documented usage pattern) will process a forged event as if it originated from the victim's shop.

### Impact Explanation
This breaks the tenant/shop identity binding that the HMAC is supposed to protect, letting an unprivileged attacker (any developer who installs the app on their own store) inject webhook events falsely attributed to a different shop into the app's processing pipeline. Depending on how the host app consumes `WebhookMetadata#shop` (e.g., updating merchant records, triggering data mutations, or resolving which session/access token to act with), this constitutes cross-tenant access/confusion — Critical impact per the classification of "cross-tenant access."

### Likelihood Explanation
Likelihood is High for an attacker who is capable of installing the target app on their own shop (a normal, unprivileged flow for any Shopify app). No access token, `api_secret_key`, or privileged account for the *victim* shop is required — only a genuine webhook fired for the attacker's own shop, whose signature the attacker can capture and replay with a modified shop header. The described request/response asymmetry (verified bytes vs. parsed identity field) is directly analogous to the reported "funds distributed based on unaccounted state" pattern in `Rewards.sol`.

### Recommendation
Bind the shop identity into the signed material, or otherwise cross-verify it out-of-band:
- Include the `shop` domain (and ideally `topic`/`webhook-id`) in the string that is HMAC-verified, or
- After successful body HMAC validation, independently verify that the header-supplied `shop` corresponds to a shop that has an active, previously-stored session/installation for this app (i.e., treat the header value as untrusted input to be checked against known state, not as a verified identity), and reject/flag mismatches.
- Document explicitly that `WebhookMetadata#shop` is unauthenticated and must not be used as an identity key without further verification by the host application.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` (normal unprivileged app installation).
2. Attacker triggers any webhook event on their own store (e.g., `orders/create`) and captures the raw POST body and the genuine `x-shopify-hmac-sha256` header Shopify computed with the app's single `api_secret_key`.
3. Attacker replays this exact `(raw_body, hmac)` pair to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the shared secret: [6](#0-5) 
5. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: ...)`, and any downstream logic keyed on `shop` now operates as if this event genuinely came from the victim shop.
