### Title
Webhook `shop-domain` header is trusted for tenant identification without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw request body only, while the `shop` value used downstream to attribute the webhook to a tenant comes from an HTTP header that is completely outside the signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook using `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` to compute the expected signature [1](#0-0) . `to_signable_string` returns only `@raw_body` [2](#0-1) . Meanwhile, `shop` (the tenant identifier passed to the handler) is read directly from the `X-Shopify-Shop-Domain` / `shopify-shop-domain` header [3](#0-2) , which is never included in the HMAC-signed bytes.

After HMAC validation succeeds, `Registry.process` builds `WebhookMetadata` using `request.shop` straight from that unauthenticated header and passes it to the app's handler as the source-of-truth tenant identifier: [4](#0-3) .

This breaks the intended identity binding: `shop-header-value == authenticated-tenant`. Since all webhooks for every shop that installs a given app are signed with the same app `client_secret` (the HMAC secret is per-app, not per-shop), the signature (body, hmac) pair generated for one merchant's shop is equally "valid" when replayed with a different `shop-domain` header value, because the header is never part of the signed content. A merchant who legitimately receives real, correctly-signed webhooks for their own shop (e.g., by installing the app) can capture `(raw_body, hmac)` and resend it to the app's webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header pointing at a different, victim shop. `HmacValidator.validate` will still pass because it only checks the body signature [5](#0-4) , and the handler will process data it believes belongs to the victim shop.

### Impact Explanation
This is a cross-tenant data confusion / spoofing primitive: it lets a shop that has legitimate access to the app's webhook signing secret pathway (i.e., any installed shop) forge webhook events attributed to any other shop known to the app. Depending on the host application's handler logic (documented in `docs/usage/webhooks.md` to key work off `data.shop`) [6](#0-5) , this can be used to inject fake `orders/create`, `app/uninstalled`, GDPR, or other events for a shop the attacker does not own, corrupting per-tenant queues, state, or triggering unauthorized actions keyed by a spoofed `shop` value — a cross-tenant integrity violation.

### Likelihood Explanation
Exploitation requires the attacker to have installed the app on at least one real shop (to receive genuine signed webhooks) and to know or guess a target shop's `myshopify.com` domain (often discoverable/public). No secret key or token theft is required beyond what any legitimate merchant already has access to. This is a design gap in the gem's own `Request`/`Registry` classes rather than a host-application misuse, since the gem itself defines what is and is not covered by `to_signable_string` and what field is exposed as `WebhookMetadata#shop`.

### Recommendation
Bind the shop identity into what is authenticated. Options:
- Include the `shop-domain` header in the HMAC-signed content check (Shopify's exact webhook HMAC only covers body per the platform's design, so this specific mitigation may not be directly compatible — but at minimum the gem should not present `request.shop` as an implicitly-trusted value without documentation that consuming code must independently verify it belongs to a shop with an active, stored session/installation for this app before acting on it).
- Update `docs/usage/webhooks.md` to explicitly warn that `data.shop` from webhook processing is not covered by the HMAC signature and must be cross-checked against a known, previously-authenticated shop/session record before being trusted for any privileged or tenant-scoped action.
- Consider exposing a stricter verification helper that ties `shop` to the registered webhook subscription id (`webhook_id`) fetched via an authenticated GraphQL call, rather than trusting the header value at face value.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com`; Shopify sends a legitimately signed webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for `B` with the app's `client_secret`), header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker replays the exact same body `B` and hmac `H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`= B`) only, matches `H`, and returns `true` [2](#0-1) [5](#0-4) .
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes payload `B` as if it originated from the victim's shop [7](#0-6) .

**Note on confidence:** I was not able to fully confirm how downstream consumers (outside this gem, e.g., `shopify_app`) use `data.shop` in practice, since that logic lives in host applications, not in this gem. The finding is scoped strictly to the gem's own `Request`/`Registry`/`HmacValidator` code, where the identity-binding gap (`shop` header unauthenticated vs. HMAC-signed body) is concretely verifiable.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
