## Title
Single global `maxOracleAge` staleness bound applied uniformly to Chainlink feeds with drastically different heartbeats can let stale/halted prices be used for gas fee pricing - ([File: evm/src/utils/SimplexPaymaster.sol])

### Summary
`SimplexPaymaster` enforces exactly one governance-configured `maxOracleAge` value against **every** Chainlink feed it consults — both the native-asset/USD oracle and every registered token/USD oracle — even though the contract's own documentation acknowledges these feeds have very different heartbeats (e.g. BSC stablecoins ~27s vs Ethereum/Base stablecoins up to 24h). This is the same class of bug as the referenced report: a staleness bound that is not matched to the actual freshness guarantee of the specific feed it is applied to, letting a feed be treated as "fresh" long after it has genuinely gone stale (or been halted/manipulated), rather than the report's reverse failure mode (module too strict vs. too lenient). Here the mismatch runs in the dangerous direction — too lenient for fast-heartbeat feeds — directly affecting how much ERC-20 token is pulled from a UserOperation sender to pay for gas.

### Finding Description
`Params.maxOracleAge` / the stored `maxOracleAge` state variable is a single value used by `_getOraclePrice` for **all** oracle reads: [1](#0-0) 

It is invoked identically for the `nativeOracle` and for every per-token `cfg.tokenOracle` inside `_tokenPrice`: [2](#0-1) 

The contract's own NatSpec documents that heartbeats vary drastically per chain/token, yet only one bound is stored and enforced: [3](#0-2) 

The deployment script default further confirms the bound is deliberately sized for the *slowest* feed (24h Ethereum/Base heartbeat) with a buffer, i.e. ~25 hours: [4](#0-3) 

There is no per-oracle staleness configuration in `TokenConfig`: [5](#0-4) 

so any token registered with a fast-heartbeat feed (e.g. ~27s on BSC) is checked against the same ~25h bound used for slow feeds. If that specific token feed stalls, is deprecated, or is otherwise halted (a not-uncommon occurrence for smaller/less-liquid Chainlink feeds), its `latestRoundData().updatedAt` can be up to ~25 hours old and still pass `_getOraclePrice`'s staleness check, because the check only compares against the global `maxOracleAge`, not against that feed's actual expected heartbeat.

### Impact Explanation
`_tokenPrice`/`_getOraclePrice` is on the direct, permissionless path every UserOperation sender exercises: `_fetchDetails` (called by `PaymasterERC20._validatePaymasterUserOp` during EntryPoint processing of any UserOperation) computes `tokenPrice` from these oracle reads and that price directly determines how much ERC-20 token is pulled from the sender to cover gas: [6](#0-5) 

If a token's real market price moves substantially while its feed is halted (still within the global `maxOracleAge` window), the paymaster will keep computing costs off the last (now-wrong) reported price:
- If the token has since depreciated relative to native gas cost, users are overcharged (loss of funds for permissionless UserOp senders).
- If the token has since appreciated, the paymaster undercharges, effectively subsidizing gas from its own deposit/treasury (loss of protocol funds), draining value that legitimate solvers/users would otherwise have kept.

This is a fund-safety issue reachable by any ordinary UserOperation sender with no special privilege, matching the "unfair"/incorrect-fee-accounting class called out in the source report.

### Likelihood Explanation
Likelihood is elevated because:
- The staleness bound is explicitly configured to be large (default ~90,000s / 25h) specifically to avoid reverts from the *slowest* feeds, per the deployment script comment.
- Governance can register arbitrary ERC-20/oracle pairs (`RegisterToken`) with heartbeats far shorter than that bound, and the contract provides no mechanism to tighten staleness per token.
- Chainlink feed halts/deprecations for lower-liquidity tokens are a known, recurring occurrence, so the precondition (a fast-heartbeat feed silently stalling for hours) is realistic rather than purely theoretical.

### Recommendation
Store and check a per-oracle (or at minimum per-token) staleness bound derived from that specific feed's actual heartbeat, instead of one global `maxOracleAge` applied to both the native oracle and all token oracles. `TokenConfig` (and the native oracle config) should carry their own `maxAge`, set at `RegisterToken`/`UpdateParams` time, and `_getOraclePrice` should accept and enforce that oracle-specific bound rather than the single global `maxOracleAge`.

### Proof of Concept
1. Governance registers `TokenX` with a Chainlink feed whose heartbeat is 27 seconds (e.g., a BSC stablecoin), while `maxOracleAge` is set to the deployment default of 90,000 seconds (25h) to accommodate Ethereum/Base 24h-heartbeat feeds.
2. `TokenX`'s feed stalls (deprecated aggregator, sequencer/keeper failure, or feed migration) at a stale price for several hours; `latestRoundData().updatedAt` is, say, 5 hours old.
3. Any user submits a `UserOperation` paying gas in `TokenX`. `_fetchDetails` → `_tokenPrice` → `_getOraclePrice(cfg.tokenOracle, ...)` computes `block.timestamp - updatedAt = 18000s`, which is well under `maxOracleAge = 90000s`, so the stale-check passes and the stale price is used.
4. If `TokenX`'s real price has since fallen (or the market moved against the stale quote), the sender is charged the wrong amount of `TokenX` for the same gas cost — either overpaying (user loss) or the paymaster undercharging (protocol treasury loss) — despite the feed having been genuinely stale by that token's own 27-second heartbeat standard for the entire multi-hour window.

    function _tokenPrice(TokenConfig memory cfg) internal view returns (uint256) {
        uint256 nativeUsd = _getOraclePrice(nativeOracle, nativeOracleDecimals);
        uint256 tokenUsd = _getOraclePrice(cfg.tokenOracle, cfg.tokenOracleDecimals);

        return (nativeUsd * (10 ** cfg.tokenDecimals) * (10_000 + markupBps)) / (tokenUsd * 10_000);
    }

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
