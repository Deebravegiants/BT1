### Title
Webhook HMAC only signs the request body, not the `shop-domain` header, allowing shop-identity spoofing via webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body. The `shop` (and `topic`/`api_version`/`webhook_id`) values that the handler subsequently trusts to route/attribute the webhook are read from HTTP headers that are **not** included in the signed payload. Any party who legitimately receives one valid webhook for their own shop (which is the case for any merchant who installs the app) can replay that exact body to the app's webhook endpoint while substituting a different `X-Shopify-Shop-Domain` header, and the signature will still validate — because the signature never covered the shop header in the first place.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes and compares the HMAC using `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [2](#0-1) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers, none of which are part of the signed string: [3](#0-2) 

`ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then immediately trusts `request.shop` (and other header-derived fields) to build the `WebhookMetadata` object handed to the application's webhook handler: [4](#0-3) 

This is the exact "field acted on but not covered by the HMAC" binding break: the equality the app relies on is `shop-in-HMAC == shop-used-for-routing`, but in reality `shop-used-for-routing` (the header) is never part of the HMAC input, so the two can diverge. Since a single `api_secret_key` is shared across all shops installed on the app (it is an app-level secret, not per-shop), any unprivileged merchant who has installed the app can capture a webhook body that Shopify legitimately signed for their own shop (e.g. `orders/create`), and replay that identical body to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header naming a victim shop. `HmacValidator.validate` will report success because the body — the only signed input — is unchanged, and the application's handler will process/store the data under the attacker-chosen `shop` value.

### Impact Explanation
This breaks the tenant boundary the webhook signature is supposed to enforce: an app that keys any behavior (data storage, cache invalidation, triggering actions, billing events, etc.) off `WebhookMetadata#shop` can be made to attribute attacker-supplied webhook data to a different, victim shop, all while passing HMAC verification. That is cross-tenant data injection/impersonation through a documented "verified" webhook, which maps to the Critical "cross-tenant access" bucket under the given impact criteria.

### Likelihood Explanation
Any unprivileged internet user who is a legitimate merchant of the app (no special privileges, no leaked secrets, no access token needed) can trigger a real webhook for their own shop by performing an ordinary storefront action (e.g., placing an order), capture the exact raw body and valid signature Shopify sent them, and replay it to the app's public webhook endpoint with a modified shop header. No cryptographic secret needs to be known to the attacker — they only reuse a signature that was legitimately produced by Shopify for their own account.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the material that is actually authenticated, rather than trusting header values that live outside the HMAC:
- Include the `X-Shopify-Shop-Domain` (and other relied-upon headers) in `to_signable_string`, or
- Cross-check the header-derived `shop` against an independently-verified identifier (e.g., the shop tied to the specific `webhook_id`/subscription looked up via the Admin API) before dispatching to the handler, or
- At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated header data and must not be trusted for authorization decisions, and provide a supported API to validate it.

### Proof of Concept
1. App has installed shop `attacker.myshopify.com`; Shopify sends a legitimate webhook:
   ```
   POST /webhooks HTTP/1.1
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid-hmac-of-body>
   X-Shopify-Shop-Domain: attacker.myshopify.com

   {"id": 1, "note": "hello"}
   ```
2. Attacker (who legitimately received this webhook to their own server/tunnel) replays the identical body/HMAC to the app's webhook endpoint, only changing the shop header:
   ```
   POST /webhooks HTTP/1.1
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <same-valid-hmac-of-body>
   X-Shopify-Shop-Domain: victim.myshopify.com

   {"id": 1, "note": "hello"}
   ```
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `@raw_body` only — unchanged — so validation succeeds.
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` and processes/stores the attacker's payload as if it came from `victim.myshopify.com`. [4](#0-3) [5](#0-4)
