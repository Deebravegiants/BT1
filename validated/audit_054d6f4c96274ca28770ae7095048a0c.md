## Analysis

I traced every identity-binding surface in this gem (OAuth callback HMAC, JWT session token signature/`aud` check, shop-domain sanitization used before sending `client_secret`, session-id derivation) and most are correctly bound to their cryptographic proof. However, the webhook processing path breaks exactly the binding described by the report's bug class: **a field that is acted upon by the application is not covered by the HMAC**.

`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body: [1](#0-0) 

and `Utils::HmacValidator.validate` verifies the HMAC solely against that signable string (the raw body): [2](#0-1) 

But `Registry.process` takes the unauthenticated `shop-domain` header and forwards it directly into the handler's trust boundary without any additional binding to the signed body: [3](#0-2) 

And `Request#shop` is read straight from the header with no relation to the signed payload: [4](#0-3) 

### Title
Webhook `shop` identity is not bound to the HMAC-verified payload, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating the HMAC of the raw body only (`Utils::HmacValidator.validate`), then attributes that verified body to whatever shop is named in the `shop-domain`/`x-shopify-shop-domain` header, which is never included in the signed content. This breaks the equality that the report's bug class targets: `shop that is HMAC-authenticated == shop that data is attributed to`. Any actor who can obtain one valid `(body, hmac)` pair signed with the app's shared secret — trivially available to them by installing the app on their own store and triggering a webhook for a topic they control — can replay that exact body+HMAC to the app's public webhook endpoint while substituting an arbitrary victim shop's domain in the `shop-domain` header, and the handler will process it as authentic data for the victim shop.

### Finding Description
- `Request#to_signable_string` (`lib/shopify_api/webhooks/request.rb:36-38`) returns `@raw_body` exclusively; none of `topic`, `shop`, `api_version`, or `webhook_id` are part of the signed content.
- `HmacValidator.validate_signature` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) computes the HMAC over `verifiable_query.to_signable_string` (i.e., the raw body) and does a constant-time compare against the received signature — this only proves the body's integrity/authenticity, not the shop or topic.
- `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) gates only on this body-level HMAC check, then builds `WebhookMetadata` using `request.shop`, `request.topic`, and `request.webhook_id` — all header-derived and completely unauthenticated — and dispatches it to the app's registered `handler.handle`.
- Because the app's `client_secret`/webhook secret (`Context.api_secret_key`) is shared across every shop that installs the app (it's the app's secret, not a per-shop secret), a self-registered attacker-merchant can generate a legitimately signed `(body, hmac)` pair for their own shop, then submit it directly to the app's public webhook URL with a forged `shop-domain` header pointing at a different, victim shop.

### Impact Explanation
This is a cross-tenant identity confusion: the receiving application will believe attacker-chosen JSON body content originated from a shop it never actually came from, and will run this data through any per-shop business logic (order/customer processing, data reconciliation, triggering per-shop side effects, updating per-shop state, etc.) keyed by `request.shop`. Depending on the handler, this can corrupt or exfiltrate victim-shop-scoped data, or trigger unauthorized actions attributed to the victim tenant — matching the "Critical - cross-tenant access" impact bucket.

### Likelihood Explanation
The prerequisites are within reach of an unprivileged internet user: (1) install the target app on any dev/free store to legitimately trigger a webhook and capture a genuinely valid `(body, hmac)` pair for a topic used by the app, and (2) POST that exact pair to the app's public webhook endpoint with the `shop-domain` header changed to the victim shop. No access token, `client_secret`, leaked credential, or TLS interception is required — only normal, permitted use of the app as a merchant plus a forged header on a public HTTP endpoint.

### Recommendation
- **Short term:** Document/require that consuming applications independently verify `shop` domain identity (e.g., cross-check the reported `shop` against the shop that owns the currently active session/installation, or maintain a per-shop webhook secret if supported) before trusting webhook payload attribution — do not treat `request.shop` as authenticated by `HmacValidator.validate`.
- **Long term:** Extend `VerifiableQuery`/`HmacValidator` (or add a companion check in `Registry.process`) to bind the `shop`, `topic`, and `webhook_id` header values into the value that's cryptographically verified, or otherwise require callers to explicitly re-authenticate the shop identity (e.g., via a stored per-shop webhook id/shop mapping fetched independently of the header) before dispatching to handlers.

### Proof of Concept
1. Attacker installs the target Shopify app on their own dev store `attacker.myshopify.com` and triggers a subscribed webhook topic (e.g. `orders/create`) so Shopify sends the app a legitimately-signed webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` where `H = HMAC-SHA256(secret, B)`, and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker (having full control of the raw bytes they send from their own webhook-processing tooling, or by simply reusing values observed in their own store's webhook deliveries) issues their own HTTP POST directly to the app's public webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid for body `B`)
   - Header `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (forged)
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B) == H` — this passes.
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: parsed(B), ...)` and invokes the app's handler as if `victim-shop.myshopify.com` sent body `B`, even though `victim-shop` never sent this webhook and the attacker's shop is not `victim-shop`.         def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
