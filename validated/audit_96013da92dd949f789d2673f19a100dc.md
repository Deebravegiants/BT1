### Title
Receipt size limit bypass via `promise_return` after `output_data_receivers` extension - (runtime/runtime/src/lib.rs)

### Summary
An unprivileged attacker can deploy a contract that builds a promise DAG (`A -then-> B`), where callback `A` creates a new promise `C` sized exactly at `max_receipt_size` and calls `promise_return(C)`. The runtime validates `C`'s size *before* appending `A`'s `output_data_receivers` onto it, so the final receipt exceeds `max_receipt_size` yet is accepted as an outgoing/incoming receipt, undermining size-based congestion/bandwidth accounting. This is the already-tracked bug referenced in the code as issue #12606.

### Finding Description
When an `ActionReceipt` (here, promise `A`) finishes execution and returns `ReturnData::ReceiptIndex` (the effect of `promise_return`), the runtime does not re-route the caller's `output_data_receivers` as separate `DataReceipt`s; instead it appends them directly onto the *already-created* new receipt (`C`) referenced by that index: [1](#0-0) 

This append happens **after** the per-action new-receipt validation loop that calls `validate_receipt(..., ValidateReceiptMode::NewReceipt)` on each newly created receipt: [2](#0-1) 

`validate_receipt` enforces `max_receipt_size` via a borsh-size check: [3](#0-2) 

Because receipt `C` was already sized exactly at `max_receipt_size` when it was created (and passed the check), the later `output_data_receivers.extend_from_slice(...)` pushes it over the limit *without any subsequent validation pass*. The `ValidateReceiptMode::ExistingReceipt` doc comment explicitly acknowledges this: "There is a bug which allows to create receipts that are above the size limit. Runtime has to handle them gracefully until the receipt size limit bug is fixed. See https://github.com/near/nearcore/issues/12606 for details." [4](#0-3) 

Attack path is fully reachable from an unprivileged account: deploy any contract, call a method that (1) creates promise `A` then-chained to `B` via standard host functions (`promise_batch_create`/`promise_then`/`promise_batch_action_function_call_weight`), and (2) inside `A`'s callback, creates promise `C` sized to exactly `max_receipt_size` and calls `promise_return(C)`. Since `A`'s receipt has `output_data_receivers` pointing at `B`, those get appended onto `C` after validation. All of these are standard promise-API host functions available to any deployed WASM contract, not special test-only code — the codebase's own reference contract (`test-contract-rs`) implements exactly this pattern and is exercised by `max_receipt_size_promise_return_method1`/`_method2`. [5](#0-4) 

The nearcore test suite already reproduces and asserts this exact bug in `test_max_receipt_size_promise_return`, which explicitly checks that an oversized receipt does occur (`assert_oversized_receipt_occurred`) rather than that it is rejected: [6](#0-5) [7](#0-6) 

Bandwidth-scheduler / congestion-control code paths that rely on `max_receipt_size` as a hard bound (e.g., `try_forward` clamping) explicitly reference this same issue #12606 as a "bug workaround for oversized receipts," confirming that downstream size-based accounting logic (`outgoing_receipts_usual_size_limit`, congestion bookkeeping) is built assuming this class of oversized receipt should not exist but currently can.

### Impact Explanation
This falls into the "receipt/congestion accounting failure" impact class: a receipt above the protocol's hard `max_receipt_size` limit (4 MiB) can be produced and forwarded as an outgoing/incoming/delayed receipt, and can end up embedded in `ChunkStateWitness`. Downstream code paths (bandwidth scheduler admission math, `ChunkStateWitness` size budgeting documented in `docs/misc/state_witness_size_limits.md`) assume this cannot happen; an oversized receipt evading these checks can inflate witness size beyond the ~21 MiB budget, break size-based congestion bookkeeping, or otherwise perturb receipt delivery guarantees the size limit was designed to preserve.

### Likelihood Explanation
Fully reachable by any unprivileged account: deploy a contract, submit one function-call transaction constructing the promise DAG and one `promise_return` call, no elevated privileges, no consensus/node assumptions. Repeatable deterministically (the receipt size is fully attacker-controlled via `args_size`). This is already independently reproduced by nearcore's own `test_max_receipt_size_promise_return` test, confirming exploitability with 100% reliability under current code.

### Recommendation
Re-validate the final (post-`output_data_receivers`-extension) receipt with `validate_receipt(..., ValidateReceiptMode::NewReceipt)` after the extension step in `runtime/runtime/src/lib.rs` (around lines 1098-1116), rather than only validating receipts before this mutation. Alternatively, reserve headroom for `output_data_receivers` size when validating candidate receipts created via `promise_return`, or reject such extensions if they would push the total size above `max_receipt_size`.

### Proof of Concept
Extend the existing `test_max_receipt_size_promise_return` test in `test-loop-tests/src/tests/max_receipt_size.rs` to additionally assert the *negative* invariant (currently it asserts the bug's presence via `assert_oversized_receipt_occurred`): after fix, replace/augment with an assertion that walks all blocks' incoming receipt proofs and `ChunkStateWitness`-relevant receipt data, asserting `receipt_size <= max_receipt_size` for every receipt (i.e., invert `assert_oversized_receipt_occurred` into `assert_no_oversized_receipt`), and confirm the transaction instead fails with `ReceiptValidationError::ReceiptSizeExceeded`.

// Runtime shouldn't die when it encounters a receipt with size above `max_receipt_size`.
#[test]
fn test_max_receipt_size_promise_return() {
    init_test_logger();

    let account = create_account_id("account0");
    let account_signer = create_user_test_signer(&account);
    let mut env = TestLoopBuilder::new()
        .enable_rpc()
        .add_user_account(&account, Balance::from_near(10_000))
        .build();

    // Deploy the test contract
    let deploy_contract_tx = SignedTransaction::deploy_contract(
        101,
        &account,

        &account_signer,

    env.rpc_runner().run_tx(deploy_contract_tx, Duration::seconds(5));

    // User calls a contract method

    // When promise A is executed, it creates a third promise - `C` and does a `promise_return`.
    // The DAG changes to: [C ->then-> B]
    // The receipt for promise C is a maximum size receipt.
    // Adding the `output_data_receivers` to C's receipt makes it go over the size limit.
    let base_receipt_template = Receipt::V0(ReceiptV0 {
        predecessor_id: account.clone(),
        receiver_id: account.clone(),
        receipt_id: CryptoHash::default(),
        receipt: ReceiptEnum::Action(ActionReceipt {
            signer_id: account.clone(),
            signer_public_key: account_signer.public_key().into(),
            gas_price: Balance::ZERO,
            output_data_receivers: vec![],
            input_data_ids: vec![],
            actions: vec![Action::FunctionCall(Box::new(FunctionCallAction {
                method_name: "noop".into(),
                args: vec![],
                gas: Gas::ZERO,
                deposit: Balance::ZERO,
            }))],
        }),
    });
    let base_receipt_template = action_receipt_v1_to_latest(&base_receipt_template);
    let base_receipt_size = borsh::object_length(&base_receipt_template).unwrap();

    let args_size = max_receipt_size - base_receipt_size;

    // Call the contract
    let large_receipt_tx = SignedTransaction::call(
        102,
        account.clone(),
        account.clone(),
        &account_signer,
        Balance::ZERO,
        "max_receipt_size_promise_return_method1".into(),

        account.clone(),
        account,
        &account_signer,

        "".into(),
        Gas::from_teragas(300),

    );
    env.rpc_runner().run_tx(assert_test_completed, Duration::seconds(5));

}

/// Assert that there was an incoming receipt with size above max_receipt_size
fn assert_oversized_receipt_occurred(node: &TestLoopNode<'_>) {
    let client = node.client();
    let chain = &client.chain;
    let epoch_manager = &*client.epoch_manager;

    let tip = chain.head().unwrap();
    let epoch_id = epoch_manager.get_epoch_id(&tip.last_block_hash).unwrap();
    let protocol_version = epoch_manager.get_epoch_protocol_version(&epoch_id).unwrap();
    let runtime_config = client.runtime_adapter.get_runtime_config(protocol_version);
    let max_receipt_size = runtime_config.wasm_config.limit_config.max_receipt_size;

    let mut block = chain.get_block(&tip.last_block_hash).unwrap();

    // Go over all blocks down to genesis looking for a receipt above max_receipt_size.
    loop {
        if block.header().is_genesis() {
            panic!("Didn't find receipt with size above max_receipt_size!");
        }
        let prev_block = chain.get_block(block.header().prev_hash()).unwrap();

        let shard_layout = epoch_manager
            .get_shard_layout(&epoch_manager.get_epoch_id(block.hash()).unwrap())
            .unwrap();

        let oversized = if ProtocolFeature::Spice.enabled(protocol_version) {
            // With spice chunks are executed asynchronously and their produced receipts are
            // persisted as receipt proofs keyed by the block in which the chunk was applied,
            // rather than as incoming receipts on the following block.
            shard_layout.shard_ids().any(|shard_id| {
                chain
                    .chain_store()
                    .iter_receipt_proofs_for_shard(block.hash(), shard_id)
                    .iter()
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        } else {
            block.chunks().iter_new().any(|new_chunk| {
                let shard_id = new_chunk.shard_id();
                let prev_shard_index = epoch_manager
                    .get_prev_shard_id_from_prev_hash(block.header().prev_hash(), shard_id)
                    .unwrap()
                    .2;
                let prev_height_included =
                    prev_block.chunks().get(prev_shard_index).unwrap().height_included();
                let incoming_receipts_proofs = get_incoming_receipts_for_shard(
                    &chain.chain_store,
                    epoch_manager,
                    shard_id,
                    &shard_layout,
                    *block.hash(),
                    prev_height_included,
                    ReceiptFilter::TargetShard,
                )
                .unwrap();
                incoming_receipts_proofs
                    .iter()
                    .flat_map(|response| response.1.iter())
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        };

        if oversized {
            return;
        }

        block = prev_block;
    }
}

fn receipt_is_oversized(receipt: &Receipt, max_receipt_size: u64) -> bool {
    let receipt_size: u64 = borsh::object_length(receipt).unwrap().try_into().unwrap();
    if receipt_size > max_receipt_size {
        tracing::info!(%receipt_size, %max_receipt_size, "found receipt above max size");
        return true;
    }
    false
}
