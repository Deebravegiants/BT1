This confirms the finding is well-supported by the code. The webhook signature (`Utils::HmacValidator.validate`) only covers `request.to_signable_string`, which returns `@raw_body` — never the `shop-domain`, `topic`, or `webhook-id` headers. This means the tenant-identifying `shop` field is never authenticated by the HMAC, even though `Registry.process` trusts it and hands it directly to the app's handler as the tenant context.

### Title
Webhook Shop-Domain Header Not Covered by HMAC Allows Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , while `shop`, `topic`, and `webhook_id` are read straight from HTTP headers that are never part of the signed content [2](#0-1) . `Registry.process` verifies only the HMAC over the body and then passes `request.shop` unchecked to the handler as the authoritative tenant identifier [3](#0-2) .

### Finding Description
The equality that should hold is: `shop authenticated by HMAC == shop used by the handler as the tenant key`. Instead, `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) computes `HMAC(secret, to_signable_string)` and compares it to the `hmac-sha256` header, where `to_signable_string` is just `@raw_body`. The `shop-domain` header consumed via `request.shop` [4](#0-3)  is never included in `to_signable_string`, so it is authenticated by nothing.

Since `Context.api_secret_key` is the app's single `client_secret` shared across every shop that installs the app (not a per-shop secret), any shop that has installed the app can trigger a legitimately-signed webhook for itself (e.g., by creating an order, if `orders/create` is subscribed), capture the raw body + valid `hmac-sha256` header, then replay that exact body/signature to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to a victim shop that also uses the app. `HmacValidator.validate` still succeeds because it only checks the body bytes, and `Registry.process` forwards the attacker-controlled `shop` value to the handler as if it were verified [5](#0-4) .

### Impact Explanation
This breaks the tenant isolation the HMAC is meant to provide. A host application that uses `WebhookMetadata#shop` to route webhook data into per-tenant storage (the documented/expected pattern) can be made to attribute a hostile-but-authentic payload to a different merchant's tenant, i.e., cross-tenant data injection/spoofing without ever compromising the app's `client_secret`. This matches the Critical "cross-tenant access" impact class, since the attacker (any merchant who installed the app) can cause the app to act on data under an arbitrary other shop's identity.

### Likelihood Explanation
Any user who installs the app on a real Shopify store can generate genuine webhooks for their own shop on demand (e.g., triggering `orders/create`), intercept the raw body and `hmac-sha256` value client-side is not needed — they simply need to control the HTTP request delivered to their own webhook receiver, or more directly, replay a body-signature pair from their own tenant against the shared endpoint while altering only the `shopify-shop-domain` header, which requires no secret material at all.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signed content used for HMAC verification, or independently verify that the `shop-domain` header value matches an expected/registered shop for the delivery before trusting it, rather than relying solely on a body-only signature.

#    body: raw_body

# 2. Attacker replays the identical body + hmac header to the same endpoint,
#    only changing the shop-domain header:

ShopifyAPI::Webhooks::Registry.process(request)
