### Title
Signup continues (biometric capture, fraud checks, PCP build/upload) despite OS-version block signal not being enforced on `stage` builds - (File: `src/plans/mod.rs`)

### Summary
`orb-core` implements a backend "kill-switch" for signups: the backend can mark an orb's software version as not `Allowed` (e.g. `Blocked`, `Unknown`, `Error`) to disable signups, analogous to GMX's protocol-level feature-disable flags for deposits/withdrawals. The check is implemented correctly and evaluated on every signup, but the branch that is supposed to halt execution when the check fails only does so on non-`stage` builds. On `stage` builds, the disable signal is *acknowledged* (a UI failure notification is fired) but execution is **not aborted**, and the signup pipeline (biometric capture, fraud checks, personal-custody-package build/upload, enrollment attempt) proceeds anyway — exactly the "feature disabled but the failure/cancellation path doesn't enforce it" pattern described in the GMX report.

### Finding Description
The gatekeeping function is `is_orb_os_version_allowed`, which returns `true` only when the backend explicitly reports `OrbOsVersionStatus::Allowed`; any other outcome (`Blocked`, `Deprecated`→handled elsewhere, `Unknown`, `Error`, or a failed HTTP request) causes it to return `false`: [1](#0-0) 

The caller, `do_signup`, is supposed to stop the signup flow entirely when this check fails: [2](#0-1) 

```rust
if !self.is_orb_os_version_allowed(debug_report).await {
    #[cfg(feature = "stage")]
    notify_failed_signup(orb, Some(SignupFailReason::SoftwareVersionBlocked));
    #[cfg(not(feature = "stage"))]
    return Ok(result);
}
```

On a production build (`stage` feature disabled), the `return Ok(result)` executes and the signup is correctly aborted. On a `stage` build, only `notify_failed_signup` is called — there is no `return` — so control falls through into the rest of `do_signup`, which runs `scan_remaining_qr_codes`, `biometric_capture`, `biometric_pipeline`, `detect_fraud`, `build_pcp`, and `upload_pcp_tier_0`, and finally attempts `enroll_user`: [3](#0-2) [4](#0-3) 

Only much later, inside the actual `enroll_user::Plan::run` call to the backend, is the version block re-checked and enforced server-side: [5](#0-4) 

By that point the orb has already: captured the user's iris/face biometric images, run them through the biometric pipeline, built the personal-custody-package (PCP) bundle, and started uploading tier-0/1/2 PCP data to the backend — all despite the orb having already been signaled (locally, before capture even started) that its software version is not authorized to perform signups. This mirrors the GMX root cause precisely: a disable/feature check exists and is correctly computed, but the code path taken on failure does not enforce the disablement, so downstream state-changing/resource-consuming operations proceed anyway.

### Impact Explanation
An orb whose OS version has been `Blocked`/marked `Unknown`/erroring is meant to be prevented from signing anyone up at all — this is the backend's mechanism to disable signups on non-compliant or maintenance-flagged hardware (identity-binding/signup-authorization enforcement). With the `stage` build's fall-through, the orb still runs a full biometric capture and processing cycle and pushes iris/face-derived PCP data toward the backend before the authoritative rejection is applied. This causes: (1) unnecessary collection and local/pipeline processing of a real user's sensitive biometric data under a state that should have blocked the signup outright, and (2) wasted PCP tier-0/1/2 uploads that the backend will ultimately discard, i.e. resources spent and biometric data exposed to processing/upload despite the operation being disabled — the same "disabled operation still executes, incurring cost/exposure before it is cancelled" pattern flagged in the source report.

### Likelihood Explanation
This requires the orb binary to be compiled with the `stage` Cargo feature and for the backend orb-os-version-check endpoint to return anything other than `Allowed` (block/maintenance/unknown/network error) while the orb is actively used for signups — a state fully controlled by the backend/operations team, not requiring any attacker action, and used across other parts of the codebase (`src/config.rs`, `src/backend/endpoints.rs`, `src/consts.rs`, `src/plans/enroll_user.rs`, etc.), indicating `stage` denotes a real deployed configuration (pointed at the staging backend/environment) rather than a throwaway unit-test path. Since I could not fully confirm from the index whether `stage`-feature orbs are ever used to process real end-user signups in the field versus purely internal staging fleets, the exact deployment likelihood carries some uncertainty; a Devin session with full repo/build access would be needed to confirm how `stage` binaries are distributed.

### Recommendation
Remove the `#[cfg(feature = "stage")]` / `#[cfg(not(feature = "stage"))]` split around the version-block check in `do_signup`, and unconditionally `return Ok(result)` (after firing the appropriate UI/telemetry notification) whenever `is_orb_os_version_allowed` returns `false`, regardless of build feature. This ensures the local "feature disabled" signal is enforced identically to the production path, rather than only being surfaced as a notification while the biometric capture/enrollment pipeline continues to run.

### Proof of Concept
1. Build/run `orb-core` with the `stage` Cargo feature enabled, pointed at a backend whose `orb_os_status::request()` endpoint returns `OrbOsVersionStatus::Blocked` (or `Unknown`/`Error`) for the orb's current version — a state the backend uses to disable signups fleet-wide (maintenance, security incident, etc.).
2. Trigger a signup: `is_orb_os_version_allowed` (`src/plans/mod.rs:1625-1641`) returns `false`.
3. In `do_signup` (`src/plans/mod.rs:520-525`), because `stage` is enabled, only `notify_failed_signup` fires; there is no early return.
4. Execution continues into `scan_remaining_qr_codes`, `biometric_capture`, `biometric_pipeline`, `detect_fraud`, `build_pcp`, `upload_pcp_tier_0` (`src/plans/mod.rs:550-636`), capturing and uploading the user's biometric data.
5. Only when `enroll_user::Plan::run` calls the backend signup endpoint does the block finally get enforced (`src/plans/enroll_user.rs:246-254`, returning `Status::SoftwareVersionOutdated`), by which time biometric capture and PCP upload have already occurred despite the signup being disabled from the start.

    /// Checks if Orb OS is in an allowed version range.
    async fn is_orb_os_version_allowed(&self, debug_report: &mut debug_report::Builder) -> bool {
        match backend::orb_os_status::request().await {
            Ok(orb_os_status::OrbOsVersionCheckResponse {
                status: OrbOsVersionStatus::Allowed,
                ..
            }) => return true,
            Ok(orb_os_status::OrbOsVersionCheckResponse { status, error }) => {
                dd_incr!("main.count.signup.result.failure.orb_os_version");
                tracing::error!("Orb OS version check failed. Status: {status:?} Error: {error:?}");
                debug_report.signup_server_failure();
                debug_report.enrollment_status(enroll_user::Status::SoftwareVersionOutdated);
            }
            Err(e) => tracing::error!("Orb OS version check request failed: {e:?}"),
        }
        false
    }
