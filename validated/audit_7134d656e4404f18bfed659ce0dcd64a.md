### Title
Webhook shop-domain identity is not covered by HMAC, allowing cross-tenant impersonation - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` trusts the `shop` value extracted from the `X-Shopify-Shop-Domain` header to identify which merchant/tenant a webhook belongs to, but the HMAC signature that `HmacValidator.validate` checks is computed only over the raw request body, never over the shop-domain header. This breaks the identity binding `hmac_signed_bytes == bytes_used_for_tenant_identification`, letting an attacker who can deliver (or replay) a validly-signed webhook body substitute an arbitrary `shop` value.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, completely independent of the signed bytes: [2](#0-1) 

`Registry.process` validates the HMAC against the body only, then dispatches the handler using `request.shop` as the tenant identifier, without any cross-check that the shop matches the body/HMAC: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` verifies `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e., it only ever proves the integrity of `to_signable_string` (the body for webhooks) — the shop-domain header is outside the HMAC's scope entirely: [4](#0-3) 

Because the header carrying the tenant identity is not part of the signed payload, `hmac_valid(body) == true` does not imply `shop_header == shop_that_actually_sent_this_body`. Any party who obtains one legitimately-signed webhook body/HMAC pair (e.g., their own shop's webhook, or a captured/replayed one) can resubmit it to the app's webhook endpoint with a different `X-Shopify-Shop-Domain` header value, and `Registry.process` will accept it as authentic and route it to the handler tagged with the attacker-chosen shop.

### Impact Explanation
This is a cross-tenant identity-binding bypass: the "authenticated" shop (via HMAC) and the shop used by the application to select the tenant record are not the same equality the code assumes. Shopify's own webhook signing scheme, as consumed by this gem, does not bind the sender's shop domain to the signature, so a host application that (as documented in the README and by design) relies on `WebhookMetadata#shop` from `Registry.process`'s handler callback to identify which merchant a webhook payload/body pertains to can be made to apply data believed to belong to a different tenant. This matches the "Critical - cross-tenant access" category, since it lets an attacker cause the app to process webhook data (customer/order/shop payloads) under an arbitrary shop identity while HMAC validation still reports success.

### Likelihood Explanation
Exploitation requires the attacker to control (or replay) a validly HMAC-signed body — most plausibly their own shop's outbound webhook traffic, which any merchant/app-installer can trivially generate from their own store, or a captured webhook that is then replayed with a modified shop header pointed at a victim. No secrets are required to forge headers, since the shop header sits outside the signed data; only a legitimately-signed body is needed, which is attacker-obtainable through their own shop.

### Recommendation
Include the shop-domain header (and ideally webhook ID/topic) inside the signed data validated for webhooks, or independently verify that `request.shop` corresponds to a shop the app has actually installed/registered before trusting it as the tenant key. Concretely, extend `Utils::VerifiableQuery`/`HmacValidator` usage for webhooks so `to_signable_string` binds shop and topic, not just the raw body, closing the gap between the header used for tenant routing and the bytes actually covered by the HMAC.

### Proof of Concept
1. Attacker (or their own test shop) receives a legitimately signed webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` where `H = HMAC(api_secret_key, B)`.
2. Attacker resends the identical `B`/`H` pair to the target app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` instead of their own shop domain.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, B)` and matches `H` — validation succeeds because the header is never part of `to_signable_string`. [5](#0-4) 
4. The handler is invoked with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the payload actually originated from the attacker's own shop, achieving tenant-identity spoofing.

          received_signature = verifiable_query.hmac
