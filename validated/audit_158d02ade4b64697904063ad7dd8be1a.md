### Title
Webhook shop-domain spoofing via HMAC that covers only the raw body, not the `shop-domain` header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by verifying an HMAC over the raw request body, then trusts the unauthenticated `shop-domain` header to attribute the event to a tenant. This mirrors the reported bug class: a field that is acted upon (`shop`) is not cryptographically bound to the signature that gates trust (`hmac`).

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers without any cryptographic binding: [2](#0-1) 

`Registry.process` validates the request using only `Utils::HmacValidator.validate(request)`, which in turn calls `to_signable_string` (raw body only) against `Context.api_secret_key`: [3](#0-2) [4](#0-3) 

Once the HMAC check passes, `request.shop` (from the unauthenticated header) is handed directly to the handler via `WebhookMetadata.new(... shop: request.shop ...)`: [5](#0-4) 

Since a single `api_secret_key` (the app's client secret) is shared across **every** shop that has installed the app, any unprivileged internet user who installs the app on their own store can:
1. Receive a legitimate, correctly-HMAC-signed webhook from Shopify for their own store (they control the HTTP endpoint and can capture the raw request, headers included).
2. Replay that exact `raw_body` + `hmac` to the app's webhook endpoint, but substitute the `x-shopify-shop-domain` header with a victim shop's domain.
3. Because `to_signable_string` never includes the shop header, `HmacValidator.validate` still succeeds — the equality being broken is: `shop authenticated by HMAC == shop acted upon by the handler`, which does not hold.
4. `Registry.process` dispatches the (attacker-authored) payload to the handler labeled as coming from the victim shop.

### Impact Explanation
This breaks the tenant/shop authentication boundary of the webhook processing pipeline: an attacker who legitimately installed the app on their own store can forge webhook events attributed to any other shop's domain, without ever needing that shop's credentials. Depending on how the host app's handler acts on `WebhookMetadata#shop` (e.g., updating per-shop database records, triggering `app/uninstalled` cleanup, mandatory compliance webhooks like `customers/redact`), this can result in cross-tenant data corruption or forged compliance actions attributed to another merchant. This qualifies as Critical — cross-tenant access, since the shop identity binding used throughout the webhook-processing API of this gem is not authenticated.

### Likelihood Explanation
Moderate-to-high: the only prerequisite is that the attacker be able to install the target app on any shop they control (a normal, unprivileged action for any merchant/developer), and observe/replay HTTP traffic to their own publicly reachable webhook endpoint. No secrets, tokens, or privileged access to the victim shop are required — only the app's single shared `api_secret_key`, which by design is common to every installation, is used to compute the accepted HMAC.

### Recommendation
- Include the `shop-domain` (and ideally `topic`, `webhook_id`) header values as part of the signed material verified by `HmacValidator`, or independently verify that the `shop` header corresponds to a shop actually known/installed by the app before trusting it.
- At minimum, document/require host applications to independently authenticate the `shop` value returned in `WebhookMetadata` against their own installed-shop registry before acting on webhook contents, since this gem does not bind `shop` into the HMAC.
- Consider maintaining per-shop webhook secrets/binding if stronger tenant isolation guarantees are desired (long-term fix, analogous to binding `_status` into the signature in the original report).

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, obtaining the app's shared `api_secret_key` implicitly (they never see it, but Shopify computes valid HMACs with it for their store's webhooks).
2. Shopify sends attacker a legitimate webhook, e.g.:
```
POST /webhooks HTTP/1.1
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <valid-hmac-of-raw-body>
x-shopify-shop-domain: attacker-shop.myshopify.com
x-shopify-webhook-id: ...
Body: {"id": 1, ...attacker-controlled order data...}
```
3. Attacker replays this exact body and HMAC to the app's webhook endpoint, changing only the header:
```
x-shopify-shop-domain: victim-shop.myshopify.com
```
4. `ShopifyAPI::Utils::HmacValidator.validate` succeeds (it only checks `raw_body` against the HMAC) — see [1](#0-0)  and [6](#0-5) .
5. `Registry.process` invokes the registered handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker-controlled>, topic: "orders/create", ...)`, and the host app acts on this data believing it originates from `victim-shop.myshopify.com`.

**Uncertainty note:** I was not able to inspect every downstream consumer of `WebhookMetadata#shop` in host applications (out of scope, and dependent on the integrating app), so real-world impact severity depends on what the host app does with the `shop` field in its webhook handler. The root cause within this gem — `shop` not being bound to the HMAC in `Webhooks::Request`/`Registry` — is verified directly from the cited source.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
