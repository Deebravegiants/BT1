### Title
Cross-Tenant Session Hijacking via Unsigned, Predictable `shopify_app_session` Cookie — ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
`ShopifyAPI::Utils::SessionUtils.current_session_id` derives the session-lookup identifier directly from the raw `shopify_app_session` cookie value with no cryptographic verification, while `ShopifyAPI::Auth::Oauth.validate_auth_callback` sets that same cookie to a fully deterministic, publicly-guessable string (`offline_#{shop}` or `#{shop}_#{user_id}`). Any unauthenticated party who knows (or guesses) a target shop's domain can set this cookie value themselves and cause the host app to resolve/authenticate as that shop's stored session.

### Finding Description
During OAuth completion, `Oauth.validate_auth_callback` builds the browser cookie from the newly created session's `id`, which is not a random token but a deterministic function of the shop domain (and user id for online tokens): [1](#0-0) 

The identifiers themselves are generated as plain, non-random strings: [2](#0-1) 

When the app later needs to identify which session to use for a request, `SessionUtils.current_session_id` reads this cookie back and returns it verbatim, with no signature, HMAC, or any other binding to the original authenticated OAuth flow that created it: [3](#0-2) [4](#0-3) 

The equality the library should enforce is:
`bytes read from the session cookie` == `an identifier cryptographically bound to a specific, previously-authenticated OAuth/session-token exchange for that browser`

Instead, the library accepts:
`bytes read from the session cookie` == `bytes an unauthenticated caller can compute themselves from the public shop domain`

This is exactly the "session id derived from unauthenticated bytes" class of bug: the cookie carries no MAC/signature over its value, and the derivation formula (`offline_<shop>` / `<shop>_<user_id>`) is deterministic and public (it is even documented and directly loggable/visible in `docs/usage/oauth.md`'s example flow). The gem's own documented integration pattern is to use `session.id` verbatim as the cookie value and to use `SessionUtils.current_session_id`/`cookie_session_id` verbatim as the storage lookup key, so this is not a case of an app ignoring the documented API — it is the API's documented behavior.

### Impact Explanation
If a host application follows the documented pattern (store sessions keyed by `session.id`, and use `SessionUtils.current_session_id` to resolve the current session from the cookie), an attacker who knows a target shop's `myshopify.com` domain (public information, or discoverable) can:
1. Set their own browser's `shopify_app_session` cookie to `offline_<target-shop>.myshopify.com` (or `<target-shop>.myshopify.com_<uid>` for online tokens, where UIDs are often small sequential integers).
2. Send a request to the app.
3. Have the app resolve and use the victim shop's stored session — including its Shopify access token — for API calls made on the attacker's behalf.

This is cross-tenant access and potential theft/misuse of another merchant's access token, satisfying the Critical impact bar (cross-tenant access / access token exfiltration path).

### Likelihood Explanation
Exploitation requires no credentials, no TLS interception, and no social engineering — only knowledge of the target's shop domain (which is frequently public, e.g., visible in storefront URLs) and, for online sessions, a small integer user id. Setting an arbitrary cookie value on one's own browser session against the target app is trivial for any unprivileged internet user.

### Recommendation
Do not use a deterministic, attacker-computable string as the bare cookie value used for session lookup. Instead:
- Sign/HMAC the cookie value (or the session id it encodes) with `Context.api_secret_key` so `SessionUtils.cookie_session_id` can verify integrity/authenticity before using it as a lookup key, rejecting unsigned or tampered values.
- Alternatively, use a random, unguessable session cookie value (opaque token) that is separately mapped to the deterministic session id server-side, rather than exposing the deterministic id directly in the cookie.
- Ensure `SessionUtils.current_session_id`/`cookie_session_id` fail closed unless the signature/binding check passes.

### Proof of Concept
```ruby
# Attacker knows target shop domain: "victim-shop.myshopify.com"
# For an offline session, the app's stored session id (and thus the cookie
# ShopifyAPI::Auth::Oauth.validate_auth_callback previously set for the real merchant) is:
predicted_id = ShopifyAPI::Utils::SessionUtils.offline_session_id("victim-shop.myshopify.com")
# => "offline_victim-shop.myshopify.com"

# Attacker sets this as their own browser cookie:
#   Cookie: shopify_app_session=offline_victim-shop.myshopify.com

# Host app resolves current session per documented usage:
session_id = ShopifyAPI::Utils::SessionUtils.current_session_id(
  nil,                                   # no id token supplied
  { "shopify_app_session" => "offline_victim-shop.myshopify.com" },
  false,
)
# => "offline_victim-shop.myshopify.com"
# Host app then loads the *victim's* stored Session (with victim's access_token)
# from its session repository using this attacker-supplied, unverified id.
```
