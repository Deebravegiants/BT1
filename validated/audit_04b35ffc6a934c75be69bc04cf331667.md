### Title
Webhook Shop-Domain Header Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable content from the raw body only, while the `shop` (and `topic`/`webhook-id`) values used for tenant identification are taken from unauthenticated HTTP headers.

### Finding Description
`Registry.process` gates webhook processing on `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` to compute the signature. `Request#to_signable_string` returns only `@raw_body` [1](#0-0) . The `shop` accessor, however, is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header without any cryptographic binding to that HMAC [2](#0-1) . `Registry.process` then forwards this unauthenticated `shop` value straight into `WebhookMetadata`, which is the sole tenant identifier handed to the app's handler [3](#0-2) [4](#0-3) .

This is the same class of bug as the vesting report: a value the code acts on (`shop`, the tenant key) is not covered by the integrity check (the HMAC), while a different, structurally identical value (`raw_body`) is. The identity binding that should hold — `hmac(raw_body, secret) ⇒ shop == authenticated_shop` — is never established; only `hmac(raw_body, secret) ⇒ valid` is checked.

Because every shop installed on a given app shares the same `api_secret_key`, a merchant who owns/controls their own shop can capture a legitimate webhook (valid body + valid HMAC signed by the app's shared secret) delivered to their own endpoint, then replay that exact body/HMAC pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the body's signature, and the gem hands the handler a `WebhookMetadata` claiming the (forged) victim shop.

### Impact Explanation
This maps to the Critical "cross-tenant access" bucket: the gem-documented processing flow (`docs/usage/webhooks.md`, "Process a Webhook") explicitly tells integrators to key downstream tenant-scoped actions off `data.shop`, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`. An attacker who is an authenticated user of the app for their own shop (unprivileged relative to other tenants) can inject attacker-chosen body content into another tenant's webhook processing pipeline, since the gem provides no verification that the `shop` header actually corresponds to the shop whose data produced the signed body.

### Likelihood Explanation
Requires the attacker to install the app on their own shop (a normal, unprivileged action any merchant can take) and to have HTTP access to send arbitrary requests to the app's public webhook endpoint — both are within an unprivileged internet user's reach. No secret material needs to be obtained beyond the webhook body/HMAC pair generated for the attacker's own shop.

### Recommendation
Bind the shop identity into the verified data: either include the `shop-domain` (and `topic`/`webhook-id`) header values in the HMAC-signed content used by `to_signable_string`, or independently authenticate `request.shop` against a known/expected value (e.g., cross-check with the shop tied to the session that originally requested webhook registration) before constructing `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`), receiving `raw_body = B` with header `x-shopify-hmac-sha256 = HMAC(B, secret)`.
2. Attacker POSTs to the app's webhook endpoint with the same `raw_body = B` and same HMAC header, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes `HMAC(B, secret)` and it matches, so `Registry.process` proceeds [3](#0-2) .
4. The handler receives `WebhookMetadata(shop: "victim.myshopify.com", body: <attacker-controlled B>, ...)` and performs tenant-scoped work under the victim's identity, per the documented pattern in `docs/usage/webhooks.md`.
