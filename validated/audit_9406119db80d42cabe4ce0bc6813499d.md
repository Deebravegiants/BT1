## Title
Webhook shop identity is not bound to the HMAC signature, enabling cross‑tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by verifying an HMAC computed only over the raw request body, then dispatches the handler using the `shop` value taken from an **unauthenticated** header. The identity binding "authenticated shop == shop the handler acts on" does not hold: the HMAC never covers the `shopify-shop-domain` header, so the shop identity delivered to app code is not cryptographically tied to the signature that proves the payload is genuine.

### Finding Description
`Utils::HmacValidator.validate` computes the signature exclusively from `verifiable_query.to_signable_string`. For webhooks, `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` fields are all pulled straight from HTTP headers, none of which are included in the signed material: [2](#0-1) 

`Registry.process` verifies only the body HMAC, then immediately forwards `request.shop` (the unauthenticated header value) to the app's handler as the tenant identity for the event: [3](#0-2) 

The equality that should hold is:
`shop authenticated by HMAC == shop delivered to WebhookMetadata`

What actually holds is:
`shop authenticated by HMAC == nothing` (HMAC covers body bytes only) while `shop delivered to WebhookMetadata == unauthenticated header value`

Because the app's own `api_secret_key` is shared across **all** shops that install the app (it is not per‑tenant), any two webhook deliveries for two different shops of the same app are signed with the identical secret. A merchant who has installed the app on their own shop can legitimately receive a webhook (body + valid `x-shopify-hmac-sha256`), then resend that exact body/HMAC pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header for a different, victim shop that also uses the app. `Utils::HmacValidator.validate` still succeeds (it never looks at the header), and `Registry.process` calls the registered handler with `shop: <victim-shop>`.

### Impact Explanation
This breaks the tenant boundary: a malicious but otherwise unprivileged app-installing merchant can cause the app's webhook handler to execute under the identity of a different merchant/shop (cross-tenant access), e.g. triggering data updates, cache invalidation, session/session-token side effects, or any shop-scoped business logic keyed off `WebhookMetadata#shop`, without ever compromising the victim or obtaining their credentials.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate (if low-privilege) install of the app on their own shop — no leaked secrets, no TLS interception, and no special access to the victim's tenant are needed, satisfying the "unprivileged internet user" bar. The replay is a simple HTTP POST with a copied body/HMAC and a modified header.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-signed material, or otherwise cryptographically bind the header-derived `shop` to the verified payload before it is handed to `WebhookMetadata`/handlers, so the identity used by application logic cannot diverge from the one Shopify actually signed for.

### Proof of Concept
1. App is installed on `shop-a.myshopify.com` and `shop-b.myshopify.com` (both configured with the same `ShopifyAPI::Context.api_secret_key`).
2. Attacker controls `shop-a` and receives a legitimate webhook: `raw_body = "{...}"`, `x-shopify-hmac-sha256 = HMAC(api_secret_key, raw_body)`, `x-shopify-shop-domain: shop-a.myshopify.com`.
3. Attacker POSTs the same `raw_body` and same `x-shopify-hmac-sha256` to the app's webhook endpoint, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
4. `Utils::HmacValidator.validate` (in `lib/shopify_api/utils/hmac_validator.rb`) returns `true` because it only checks the body bytes.
5. `Registry.process` invokes the handler with `WebhookMetadata.new(..., shop: "shop-b.myshopify.com", body: <shop-a's data>, ...)`, causing shop-a's webhook content to be processed under shop-b's identity.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
