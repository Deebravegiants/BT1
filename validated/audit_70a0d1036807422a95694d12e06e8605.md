## Analysis

`Bonding.transferCreator` reassigns the `creator` role for a launched token in a single, unrecoverable step, unlike every privileged owner role in the same codebase (`Bonding` and `FeeVault` both explicitly use `Ownable2StepUpgradeable` for their owner, with code comments citing exactly this class of bug as the reason). The `creator` role, however, is transferred with a plain single-step assignment and has no equivalent two-step safety net, even though it directly controls where all future protocol-fee revenue for that token is paid.

### Title
Single-step `Bonding.transferCreator` permanently misroutes future creator fees on a fat-fingered call - (`packages/contracts/src/Bonding.sol`)

### Summary
`Bonding.transferCreator` lets the current creator of a launched token reassign the `creator` field for that token in one transaction, with no acceptance step by the new address. `FeeVault.accrue` attributes every subsequent buy/sell's 0.25% creator fee to whatever address is currently stored as `tokenInfo[token].creator`. A single mistaken call — a typo'd address, a copy-paste error, or an unreachable/incompatible contract address — instantly and irreversibly redirects all future fee accrual for that token to an address the real creator does not control, with no recovery path.

### Finding Description
`transferCreator` performs the ownership change directly, with only a zero-address and same-address check, and no `pendingCreator`/`acceptCreator` step: [1](#0-0) 

Contrast this with the pattern the project itself deliberately applies to `owner()` on both `Bonding` and `FeeVault`, precisely to avoid this failure mode: [2](#0-1) [3](#0-2) 

The `creator` value set by `transferCreator` is the sole source of fee attribution in `FeeVault.accrue`, which is called on every buy/sell: [4](#0-3) 

Once `accrue` is called with the wrong `creator`, the USDC is credited to `creatorBalance[wrongAddress]` and is claimable only by that address via `FeeVault.claim()`: [5](#0-4) 

There is no mechanism in `Bonding` or `FeeVault` to reverse an accrual once it has been paid to the wrong `creatorBalance` slot, and `transferCreator` provides no confirmation/acceptance step to catch the mistake before it takes effect.

### Impact Explanation
Any creator-role holder that calls `transferCreator` with an incorrect address (typo, wrong checksum, an address they don't control, or a non-interactive contract) permanently loses all their token's future creator fee stream — 0.25% of every subsequent buy and sell, both pre- and post-graduation, for the life of the token — to an address that cannot be recovered. This is a permanent loss of creator funds, matching the accepted impact class (permanent freezing/loss of creator funds), and it happens with a single transaction from the legitimate, unprivileged creator account — no admin or attacker action required.

### Likelihood Explanation
`transferCreator` is a normal, expected user-facing function (the project's own docs describe it as the mechanism for creators to hand off tokens), so it will be called in ordinary usage, and a single address typo — the exact failure mode this bug class targets — silently and irrevocably redirects all future revenue. The one-step nature of the call removes any chance to catch the mistake before real funds start flowing to the wrong address.

### Recommendation
Convert `transferCreator` to a two-step pattern mirroring the existing `Ownable2StepUpgradeable` convention already used for `owner()` in `Bonding`/`FeeVault`: add a `pendingCreator` mapping, have `transferCreator` only set the pending value, and require the new address to call `acceptCreator(tokenAddress)` (`msg.sender == pendingCreator[tokenAddress]`) before `tokenInfo[token].creator` is actually updated and fee attribution changes.

### Proof of Concept
1. Creator `C` launches token `T` via `Zap.createToken`, making `Bonding.tokenInfo(T).creator == C`.
2. Traders buy/sell `T`; `Zap` forwards 0.25% of each trade to `FeeVault` and calls `FeeVault.accrue(T, C, ...)`, crediting `creatorBalance[C]`.
3. `C` calls `bonding.transferCreator(T, X)` intending to set `X` as a co-founder's wallet but mistypes the address (or pastes an address they don't control).
4. `tokenInfo[T].creator` is now `X` with no confirmation step — see [1](#0-0) .
5. All subsequent trades on `T` call `FeeVault.accrue(T, X, ...)`, crediting `creatorBalance[X]` — see [6](#0-5) .
6. `C` can never claim these fees again; only `X` can call `FeeVault.claim()` to withdraw them — see [5](#0-4) . There is no `Bonding` or `FeeVault` function that lets `C` reclaim the misdirected fee stream.

    function transferCreator(
        address tokenAddress,
        address newCreator
    ) external {
        if (newCreator == address(0)) revert ZeroAddress();
        TokenInfo storage info = _s().tokenInfo[tokenAddress];
        if (msg.sender != info.creator) revert NotCreator();
        if (newCreator == info.creator) revert InvalidInput();
        info.creator = newCreator;
        emit CreatorTransferred(tokenAddress, msg.sender, newCreator);
    }
```

    function accrue(
        address token,
        address creator,
        uint256 creatorAmount,
        uint256 protocolAmount,
        bool isBuy
    ) external onlyDepositor {
        FeeVaultStorage storage $ = _s();
        if (creatorAmount > 0) {
            if (creator == address(0)) revert ZeroAddress();
            $.creatorBalance[creator] += creatorAmount;
            $.totalAccruedCreator += creatorAmount;
            $.lifetimeCreatorEarned[creator] += creatorAmount;
        }
        if (protocolAmount > 0) {
            $.protocolBalance += protocolAmount;
            $.lifetimeProtocolEarned += protocolAmount;
        }
        if ($.usdc.balanceOf(address(this)) < $.totalAccruedCreator + $.protocolBalance) {
            revert UnderfundedAccrual();
        }
        emit FeeAccrued(token, creator, creatorAmount, protocolAmount, isBuy);
    }
```
