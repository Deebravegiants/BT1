### Title
Cross-account address disclosure via `getConnectedAccounts` in connected-origins module - (File: features/connected-origins/module/connections.js)

### Summary
The external report's bug class is a trust-boundary/authorization signature defect: a caller-facing function omits information the underlying logic needs to correctly scope its behavior, so the operation silently applies to the wrong scope (in the C4 report, the wrong/absent pool). Searching for an unprivileged-user analog in Hydra's own cross-origin trust boundary (the "connected origins" web3-dApp permission system), the same class of defect appears: `getConnectedAccounts({ origin })` is only scoped by `origin`, not by which specific wallet account(s) the user actually consented to share with that origin, so it discloses addresses for *every* enabled wallet account rather than only the account(s) connected to that origin.

### Finding Description
`ConnectedOrigins#connect({ id, origin })` only records a connection id under `activeConnections`; it does not record which wallet account the user approved for that origin. [1](#0-0) 

`getConnectedAccounts({ origin })` checks only that the origin is `isTrusted`, then returns **addresses for every account in `#connectedAccountsAtom`** (which is populated from *all* enabled wallet accounts via `#getAccounts`/`#setData`, not from the specific account(s) the origin was granted access to): [2](#0-1) [3](#0-2) 

This is confirmed by the module's own test: a site trusted only for `solana`/`exodus.com` and never connected to `exodus_1` still receives `exodus_1`'s Solana address in the response (merely sorted after the active account): [4](#0-3) 

`getConnectedAccounts` is exposed verbatim through the public API surface consumed by the extension/RPC bridge that untrusted web pages talk to (the same kind of RPC-bridge boundary highlighted in the rules): [5](#0-4) 

Root cause: the function's signature/authorization scope (`{ origin }` only, "is this origin trusted at all") does not match the semantics the caller expects ("give me only the account(s) this origin is permitted to see"), exactly mirroring the C4 finding where the exposed function's signature dropped the parameter (`pool`, here effectively "which account(s)") needed to correctly scope the privileged operation.

### Impact Explanation
Any dApp that a user has trusted/connected for even a single wallet account (e.g., to see one Solana address) is handed the addresses of **all other enabled wallet accounts** in the user's wallet for the connected asset(s), including accounts the user never intended to expose to that origin. This is a cross-account privacy/privilege bleed across the origin-isolation boundary that the connected-origins feature exists to enforce — an unprivileged web page gains information about accounts it was never granted access to.

### Likelihood Explanation
This triggers on every call from a trusted, multi-account wallet setup — no attacker action beyond normal dApp connection flow is required, and the behavior is deterministic and reproduced by the project's own unit test, so likelihood is high whenever a user has more than one enabled wallet account and has connected at least one site.

### Recommendation
Track which specific wallet account name(s) were approved per origin/connection (e.g., store the account name in `activeConnections` or a dedicated per-origin account list at `connect` time), and have `getConnectedAccounts` filter `#connectedAccountsAtom` down to only those approved accounts for the given `origin`, instead of returning every enabled wallet account's addresses.

### Proof of Concept
1. Enable two wallet accounts, `exodus_0` and `exodus_1`.
2. Trust `exodus.com` and connect only `exodus_0` (or whichever is active) for `solana`, as in the existing test: [6](#0-5) 
3. Call `connectedOrigins.getConnectedAccounts({ origin: 'exodus.com' })`.
4. Observe the response includes `exodus_1`'s Solana address as well, even though `exodus_1` was never connected to `exodus.com`: [7](#0-6) 

Note: I was unable to fully trace how `activeConnections`/`connect` is invoked from the actual web3 provider (`window.exodus.solana`/`window.ethereum`) content-script bridge in this pass, so I cannot definitively confirm whether the UI layer further filters this result before it reaches the page; this would need to be verified in a live session to confirm end-to-end exploitability versus mitigation elsewhere in the stack.

```javascript
    const newConnection = { id, createdAt: Date.now() }
```

```javascript
  /**
   * Returns the connected accounts for a given origin with the active wallet account sorted first. Can be used while
   * the wallet is locked
   */
  getConnectedAccounts = async ({ origin }) => {
    const isTrusted = await this.isTrusted({ origin })
    if (!isTrusted) return []

    const value = await this.#getOrigin({ origin })
    const assetNames = [value.connectedAssetName, ...(value.assetNames ?? [])].filter(
      (name, index, ary) => Boolean(name) && ary.indexOf(name) === index
    )

    const activeWalletAccount = await this.#activeWalletAccountAtom.get()
    const accounts = await this.#connectedAccountsAtom.get()

    const connectedAccounts = []
    for (const name of Object.keys(accounts)) {
      if (name === activeWalletAccount) continue
      connectedAccounts.push({ name, addresses: pick(accounts[name].addresses, assetNames) })
    }

    connectedAccounts.unshift({
      name: activeWalletAccount,
      addresses: pick(accounts[activeWalletAccount].addresses, assetNames),
    })

    return connectedAccounts
  }
```
