## Analysis Result

### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) Header Is Not Covered by the HMAC, Allowing Cross-Tenant Shop Impersonation - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The gem's webhook `Request` object signs only the raw HTTP body for HMAC verification, while the `shop-domain` header — the sole tenant identifier passed to webhook handlers — is read directly from unauthenticated headers and never included in the signed payload. Any user who can obtain one genuinely-signed webhook body (e.g., by installing the same app on their own store) can replay that body with a forged `shop-domain` header for a different shop, and `Registry.process` will accept it as valid and dispatch it under the impersonated shop's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, whose contract is `hmac` + `to_signable_string`. Its `to_signable_string` only returns the raw body: [1](#0-0) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers, which are not part of the signed string: [2](#0-1) 

`Registry.process` validates only the HMAC-over-body, then trusts `request.shop` (from the unsigned header) as the tenant key passed into the handler: [3](#0-2) 

The `HmacValidator` itself is generic and correctly compares HMAC over whatever `to_signable_string` returns — the problem is that `Request#to_signable_string` never binds the tenant-identifying header into that string: [4](#0-3) 

**Binding that is broken:** the app's trust equality should be `shop asserted by the signed webhook == shop the handler acts on`. Instead, the code enforces only `hmac == HMAC(body)`, and separately trusts `shop = header["x-shopify-shop-domain"]` with no cryptographic tie between the two. Before the attack: legitimate webhook for shop A arrives with header `shop-domain: A` and a valid HMAC over its body. After the attack: the attacker resends the identical body (and thus identical valid HMAC) but with `shop-domain: B` — validation still passes because the header was never part of what's signed, and the handler now processes shop A's payload as if it belongs to shop B (or vice versa).

### Impact Explanation
This breaks the tenant isolation the library is supposed to provide to host applications: `WebhookMetadata#shop`, the only per-tenant identifier surfaced to `handler.handle`, can be forged independently of the signed content. A host app that uses `data.shop` to select which merchant's records to update (the documented, intended usage pattern) can be made to write/attribute another shop's webhook data under an attacker-chosen shop, or vice versa — a cross-tenant data confusion/access issue driven entirely by this gem's verification logic.

### Likelihood Explanation
The attacker only needs to be able to install the same public app on their own store (a normal, unprivileged action — no leaked credentials, no TLS interception, no access token required) to receive one legitimately HMAC-signed webhook body for their own shop, and then replay that same body against the app's webhook endpoint with a different `shop-domain` header value. Because the app secret is shared across all installs of the app, the reused HMAC remains valid for any header combination, making this reachable by any ordinary merchant/attacker.

### Recommendation
Include the tenant-identifying headers (`shop-domain` at minimum, ideally `topic`, `api-version`, and `webhook-id`) as part of the signed material verified against the HMAC, or otherwise cryptographically bind them to the body (e.g., re-verify the shop domain against session/installation records keyed by webhook subscription id rather than trusting the header value that arrives with the request). At minimum, document that `Request#shop` is not authenticated by the HMAC and must not be used as a sole tenant boundary without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers/receives a legitimate webhook, capturing:
   - Body: `{"id": 1, ...}`
   - Header `x-shopify-hmac-sha256: <valid-for-body>`
   - Header `x-shopify-shop-domain: attacker-shop.myshopify.com`
2. Attacker resends the exact same request to the app's webhook endpoint, changing only:
   - Header `x-shopify-shop-domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (the unchanged raw body) and finds it matches — validation succeeds.
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)`, i.e., attacker-controlled body data is now attributed to `victim-shop.myshopify.com` inside the host application.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end
