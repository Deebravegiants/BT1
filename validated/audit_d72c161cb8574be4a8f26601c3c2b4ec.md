### Title
Unbounded GRANDPA `unknown_headers` vector in unsigned consensus messages allows fee-less resource-exhaustion DoS - (File: `modules/consensus/grandpa/verifier/src/lib.rs`)

### Summary
`pallet-ismp`'s `handle_unsigned` extrinsic executes ISMP consensus messages for free, as an unsigned transaction, and every full node must run this execution during transaction-pool validation before deciding whether to accept/propagate the transaction. For the GRANDPA consensus client, the submitted `FinalityProof::unknown_headers` (a caller-controlled `Vec<Header>`) is decoded and processed with no upper bound on its length before the actual cryptographic justification is verified, similar in spirit to the Apache `mod_md` OCSP issue where externally supplied response data was processed without any allocation/throttling limit.

### Finding Description
`pallet_ismp::Pallet::execute` is reachable via the unsigned call `Call::handle_unsigned { messages }`, and is invoked both in `Pallet::validate_unsigned` (mempool validation, run by every node for free, no fee charged) and on dispatch: [1](#0-0) 

For a `Message::Consensus` targeting the GRANDPA client, this flows into `GrandpaConsensusClient::verify_consensus`, which decodes the attacker-supplied `ConsensusMessage` (containing a `FinalityProof<H>` with an `unknown_headers: Vec<H>` field) directly from the untrusted proof bytes, with no length check: [2](#0-1) [3](#0-2) 

`verify_grandpa_finality_proof` then unconditionally builds an `AncestryChain` (a `BTreeMap` over every submitted header), scans for max/min headers, and walks a parent-hash ancestry chain across all of them — all *before* the actual GRANDPA justification signature verification runs: [4](#0-3) 

`AncestryChain::new` performs an unconditional `O(n log n)` map build over the full header set: [5](#0-4) 

There is no `MAX_HEADERS`-style bound anywhere in the GRANDPA verifier or the `ismp-grandpa` client wrapper on the number of headers a single consensus message may carry (confirmed by searching the codebase for any such cap). By contrast, the codebase demonstrably has developer awareness of and precedent for adding such bounds elsewhere (e.g. `MAX_PROOF_DEPTH` in the Pharos SPV verifier, and the `ONE_MB`/`MaxCallSize` bound recently added in `pallet-call-decompressor` specifically to stop an unsigned, fee-less "zstd bomb" from expanding unboundedly during mempool validation): [6](#0-5) 

Because `handle_unsigned` messages incur no transaction fee and this pallet documents that "all cross-chain messages received are executed for free as unsigned transactions," an attacker can gossip repeated unsigned `handle_unsigned` extrinsics packed with a very large `unknown_headers` vector (each entry a full valid-looking Substrate header struct) up to the runtime's max extrinsic/block-length limit. Every node on the network that receives the extrinsic must decode and process the entire header set (map construction + ancestry traversal) during `validate_unsigned`, before the (comparatively cheap early-reject) justification check can fail it, at zero cost to the attacker and at CPU/memory cost to every honest node.

### Impact Explanation
This is a network-wide, unauthenticated resource-exhaustion vector reachable from a single unsigned, fee-less extrinsic — it does not require any privileged role (submitter can be any peer relaying/broadcasting messages). Repeated submission can degrade transaction-pool validation throughput and node CPU/memory across the Hyperbridge relay network, delaying legitimate consensus/message delivery and effectively creating "a route unable to deliver messages" during sustained attack, which aligns with the Medium/High severity floor for this class of finding.

### Likelihood Explanation
Likelihood is high: submitting an unsigned extrinsic requires no fee, no signature, and no special privilege — only that the header vector decode successfully (headers are simple, well-known SCALE-encodable structs, trivial to mass-produce), and the extrinsic must simply fit inside the node's configured max block/extrinsic length, which is normally on the order of megabytes — enough to carry many thousands of headers.

### Recommendation
Enforce an explicit upper bound on `finality_proof.unknown_headers.len()` (and similarly on `votes_ancestries` size inside `GrandpaJustification::verify`) at the earliest possible point — ideally before `AncestryChain::new` is invoked — analogous to the `MAX_PROOF_DEPTH` guard already used in the Pharos SPV verifier and the `MaxCallSize` guard added to `pallet-call-decompressor`. The bound should be small enough to cover realistic relay-chain finality gaps under the configured `max_block_range`, and any consensus message exceeding it should be rejected immediately during `validate_unsigned`.

### Proof of Concept
1. Construct a `ConsensusMessage::Relaychain`/`Standalone` (or the underlying `FinalityProof<H>`) whose `unknown_headers` vector contains as many synthetic (non-finalizing) `SubstrateHeader` entries as fit within the runtime's max extrinsic size.
2. Wrap it as `pallet_ismp::Call::handle_unsigned { messages: vec![Message::Consensus(msg)] }` and broadcast it as an unsigned transaction to the network — no signing key, balance, or fee is required.
3. Every receiving node calls `ValidateUnsigned::validate_unsigned`, which executes `Pallet::execute` → `GrandpaConsensusClient::verify_consensus` → `verify_grandpa_finality_proof`, which decodes and processes the entire oversized header vector (building the `BTreeMap` ancestry chain and walking it) before the justification check ultimately rejects it.
4. Repeating and parallelizing this submission from many peers amplifies CPU/memory load network-wide at zero cost to the attacker, since the transaction is never included on-chain (thus never charged) but still forces full processing on every node during pool validation.
