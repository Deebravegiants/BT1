### Title
Reentrancy in escrow `withdraw()` allows draining more tokens than were ever escrowed for a commitment - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The `withdraw()` function in the Tron `IntentGatewayV2` contract performs the external token/native transfer **before** decrementing the per-commitment escrow accounting (`_orders[commitment][token]`), and only guards against a fully-zeroed balance rather than validating that the transfer amount does not exceed the recorded escrow. This is the same class of bug as the referenced report — a withdrawal path that fails to verify the amount being paid out against the actual backing balance before/while performing the transfer — except here the missing "amount ≤ balance" invariant is exploitable via reentrancy rather than raw underflow (Solidity 0.8.24 has built-in overflow/underflow reverts, so the literal underflow described in the report cannot occur, but the check-effects-interactions violation reproduces the same impact: a withdrawal that outruns its backing collateral).

### Finding Description
`withdraw()` is invoked from `onAccept()` (restricted to `onlyHost`, but reachable by any relayer that has forwarded a valid `RedeemEscrow`/`RefundEscrow` cross-chain message) and from `onGetResponse()` for cancellations: [1](#0-0) 

Inside `withdraw()`, for each token in the withdrawal request, the code only checks that the escrow entry is non-zero, then performs the external transfer, and only afterwards decrements the escrow balance: [2](#0-1) 

Because `token` and `amount` originate from `order.inputs`/`order.tokens`, which are attacker-controllable when the order was originally created (a user can specify any contract address as the "token" for their order's inputs), an attacker can supply a malicious ERC-20-like contract as `token`. When `withdraw()` calls `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))`, the malicious token's `transfer` implementation can re-enter the gateway (e.g. by having the host re-deliver, or by re-triggering another code path that also calls into the same commitment's escrow) before `_orders[body.commitment][token] -= amount;` executes. Because the escrow entry has not yet been decremented, the guard `if (_orders[body.commitment][token] == 0) revert UnknownOrder();` still passes, letting the transfer be issued again against the same, still-unreduced balance.

This lets an attacker extract more tokens out of the contract's pooled balance than were ever escrowed for that specific commitment — draining funds that belong to other unrelated orders/escrows sharing the same token, mirroring the underlying flaw in the referenced report: a withdrawal is allowed to proceed for more than the actual backing balance because the balance check is evaluated against stale/insufficiently-validated state.

### Impact Explanation
This breaks a core invariant of the intents escrow: that a commitment can never release more of a token than was deposited for it. A successful exploit results in direct theft of pooled escrow funds from the `IntentGatewayV2` contract, at the expense of other users' orders — a concrete, unbounded loss of funds reachable from a single crafted order plus its "redeem"/"refund" message relay, satisfying the High severity bar (theft of funds via unauthorized/duplicated withdrawal).

### Likelihood Explanation
The path is reachable by any unprivileged user who can (1) create an order specifying a malicious contract as one of the input "tokens," and (2) have that order's `RedeemEscrow`/`RefundEscrow` message relayed through the normal cross-chain flow (a permissionless relayer can deliver any correctly-proven message). No admin or governance privilege is required; the `onlyHost` check only restricts who calls `onAccept`, not who controls the content or token addresses inside the escrowed order, and reentrancy via attacker-supplied token contracts is a common, well-understood exploitation technique.

### Recommendation
Apply checks-effects-interactions in `withdraw()`: decrement `_orders[body.commitment][token]` (and validate `amount <= escrowed` explicitly, reverting otherwise) *before* performing the external `token.call`/native transfer. Additionally, add a `nonReentrant` guard on `onAccept`/`onGetResponse` (or the internal `withdraw` function) as defense in depth, consistent with the safer pattern already used in the mainline `IntentsBase.sol`, where the escrow value is decremented prior to the transfer: [3](#0-2) 

### Proof of Concept
1. Attacker creates a cross-chain order whose `inputs` list includes a malicious contract `Evil` (deployed by the attacker) as the `token`, escrowing some `amount` of "Evil tokens" (which need not have any real value) alongside genuine tokens/native value the attacker wants to steal, if pooled in the same contract balance. Attacker sets `beneficiary` to their own address.
2. Attacker gets the order filled or triggers a refund/cancel flow, causing a `RedeemEscrow`/`RefundEscrow` message to be relayed to the source chain and delivered via `onAccept()` -> `withdraw()`.
3. Inside the loop for the `Evil` token entry, `withdraw()` checks `_orders[commitment][Evil] != 0` (true), then calls `Evil.call(transfer(beneficiary, amount))`.
4. `Evil.transfer()` re-enters the gateway (e.g., by re-invoking `onAccept` with a resend of the same or another crafted request referencing the same commitment/token, or via any other reentrant path that reaches `withdraw` for the same commitment before the pending decrement executes).
5. The reentrant call passes the `_orders[commitment][token] == 0` check again (since the first call hasn't decremented it yet), performing another payout for the same, already-consumed escrow balance without a corresponding deposit, draining the contract's pooled token/native balance.
6. Execution unwinds back to the first call, which now decrements `_orders[commitment][token] -= amount`, completing normally while the attacker has received `2x` (or more, with deeper reentrancy) the escrowed amount.
