This confirms the finding. The gem's webhook HMAC validation (`ShopifyAPI::Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb`) is computed only over `Webhooks::Request#to_signable_string`, which returns just `@raw_body`. The `shop` (and `topic`, `webhook_id`, `api_version`) values come from separate, unsigned HTTP headers parsed by `shopify_header` in `lib/shopify_api/webhooks/request.rb`, and are passed unchecked into `WebhookMetadata` by `Registry.process` in `lib/shopify_api/webhooks/registry.rb`, which app handlers use as the tenant identifier for the webhook.

### Title
Webhook `shop-domain` header is not covered by HMAC verification, allowing shop/tenant spoofing in webhook processing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook purely by validating the HMAC over the raw request body, then trusts the unsigned `shop-domain` (and `topic`/`webhook_id`/`api_version`) headers to construct `WebhookMetadata` for the handler. Because the shop identity is never bound to the signature, any body+HMAC pair that is valid for one shop can be replayed with a different `shop-domain` header to make the app process attacker-controlled webhook content as if it belonged to a different (victim) shop/tenant.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled from HTTP headers, entirely separate from the signed content: [2](#0-1) 

`HmacValidator.validate` computes and compares the signature only against `verifiable_query.to_signable_string` (i.e., the raw body), never touching `shop`: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` to build `WebhookMetadata`, which is handed to the app's handler as the tenant identity for the event: [4](#0-3) 

The binding that is broken: **the shop that is cryptographically authenticated (none — only the body is authenticated) versus the shop that is acted upon (`request.shop`, taken from an attacker-controllable, unsigned header)**. Since the `api_secret_key` is shared across every shop that installs a given app, any attacker can:
1. Install the target app on their own shop (an ordinary, unprivileged action requiring no special credentials).
2. Trigger any webhook topic for their own shop and capture the exact `(raw_body, X-Shopify-Hmac-Sha256)` pair that Shopify legitimately sends — this pair is validly signed with the shared `api_secret_key`.
3. Replay that identical `raw_body` and `X-Shopify-Hmac-Sha256` header to the app's webhook endpoint, but substitute the `X-Shopify-Shop-Domain` header with the victim shop's domain.
4. `HmacValidator.validate` still succeeds because it only checks the body against the signature — the `shop-domain` header is not part of what's signed — so `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(shop: <victim-shop>, body: <attacker-controlled-body>, ...)`.

The gem's own documentation instructs apps to use `data.shop` directly to key their business logic (e.g., enqueue background jobs, look up/write the shop's stored records), reflecting the intended contract that `shop` is an authenticated field: [5](#0-4) 

### Impact Explanation
This breaks the tenant-isolation boundary the webhook signing mechanism is meant to enforce. An attacker with no more privilege than the ability to install the app on their own store can make an app process attacker-chosen webhook payloads under the identity of any other (victim) shop that also uses the app — since `shop-domain` and `webhook_id`/`topic` aren't authenticated, the app cannot distinguish a legitimate victim-shop event from a spoofed one. Depending on how the host application consumes `data.shop`/`data.body` (a documented, standard usage pattern per this gem's own docs, e.g. writing/updating shop-keyed state, triggering data mutations, or acting on the victim's stored access token), this enables cross-tenant data corruption or unauthorized actions performed against a shop the attacker does not control — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Reaching this requires only: (a) installing the app on an attacker-controlled shop (no privileged credential, no access to `api_secret_key` needed — this is exactly the trust boundary the HMAC is supposed to enforce), and (b) capturing and replaying one legitimate webhook delivery with a modified header. No token, secret, or victim interaction is required.

### Recommendation
Bind the shop domain (and ideally the topic/webhook id) into the value that is verified, e.g., by including `shop-domain` in the signed string, or independently verifying that the shop in the header matches an app-tracked, previously-established relationship (a registered webhook subscription id/shop pair) before trusting `request.shop` in `WebhookMetadata`. At minimum, document clearly that `data.shop` is *not* authenticated by the HMAC and must not be trusted as an unspoofable tenant identifier without additional verification.

### Proof of Concept
```ruby
require "openssl"
require "shopify_api"

secret = ShopifyAPI::Context.api_secret_key # shared across all shops of this app

# Step 1-2: attacker installs the app on shop "attacker-shop.myshopify.com"
# and receives a legitimate webhook, e.g. orders/create, with this raw body:
raw_body = '{"id":123,"note":"hello"}'

hmac_digest = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, raw_body)
valid_hmac_b64 = Base64.encode64(hmac_digest) # exactly what Shopify would send for attacker's own shop

# Step 3: attacker replays body+hmac but swaps shop-domain header to the victim shop
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac_b64,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # <-- spoofed, not covered by HMAC
  "x-shopify-webhook-id" => "attacker-controlled-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)

# Step 4: HMAC validation succeeds (only checks raw_body), handler is invoked
# with data.shop == "victim-shop.myshopify.com" even though the body/webhook
# was never actually sent by Shopify for that shop.
ShopifyAPI::Webhooks::Registry.process(request)
```
