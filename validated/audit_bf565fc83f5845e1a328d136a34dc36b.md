This confirms the vulnerability. The gem's own documentation states `process` "will verify the request did indeed come from Shopify" [1](#0-0) , and presents `data.shop` as trustworthy shop identity data [2](#0-1) , yet `shop` is never included in the HMAC-signed content.

### Title
Webhook shop-domain identity spoofing due to `shop` field not covered by HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, while `shop` is read directly from an unauthenticated header. `Registry.process` accepts the request once the body HMAC validates, then forwards the unauthenticated `shop` value to the app's handler as trusted tenant identity, breaking the intended binding `HMAC(secret, signed_bytes) == received_hmac` where `signed_bytes` should include `shop`.

### Finding Description
`Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)`, which computes the signature over `verifiable_query.to_signable_string`: [3](#0-2) 

`Request#to_signable_string` returns `@raw_body` only: [4](#0-3) 

`shop` is parsed from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never part of the HMAC-signed bytes: [5](#0-4) 

`HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` against the HMAC, so it cannot detect tampering of `shop`: [6](#0-5) 

After successful (body-only) HMAC validation, the unauthenticated `shop` is passed straight to the app's webhook handler as authoritative tenant identity: [3](#0-2) 

This is the same class of bug as the reference report: a field that downstream logic treats as verified/bound (`shop`, analogous to the nominee's epoch eligibility) is not covered by the authenticity check that gates the rest of the flow (HMAC, analogous to the epoch-weight snapshot), producing incorrect identity for the action taken. Notably, the same gem gets this right elsewhere: `Auth::Oauth::AuthQuery#to_signable_string` explicitly includes `shop` in the signed parameter set: [7](#0-6)  — showing the webhook path is the outlier that omits this binding.

Because Shopify signs webhooks with the app's `client_secret`, which is identical for every shop that installs the app, any unprivileged internet user can install the target app on their own store, capture one legitimate `(raw_body, hmac)` pair for their own shop, then replay that same body/HMAC pair to the app's public webhook endpoint with the `shopify-shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` still returns `true` (only `raw_body` is checked), and `WebhookMetadata#shop` is populated with the attacker-chosen victim domain and delivered to the app's `handle` method as if Shopify itself asserted it.

### Impact Explanation
This breaks the identity binding `shop_that_signed_the_webhook == shop_delivered_to_handler`, letting an attacker inject arbitrary-shop-attributed webhook events into any app built on this gem's documented API surface (`Registry.process` + `WebhookMetadata#shop`), enabling cross-tenant data corruption/spoofing (e.g., orders/customers/app-uninstalled events falsely attributed to a victim shop) without needing the victim's or the app's access token or `client_secret`.

### Likelihood Explanation
Requires only: (1) attacker can install the target app on any shop they control (a normal, unprivileged action for public/listed apps), (2) knowledge of the app's public webhook callback path (commonly discoverable/predictable), and (3) ability to replay an HTTP POST with modified headers. No secrets or elevated access are required, making this practically reachable by any internet user targeting apps that key business logic off `WebhookMetadata#shop`, exactly as this gem's own documentation instructs (`docs/usage/webhooks.md`).

### Recommendation
Bind `shop` (and `topic`/`webhook_id`) into the authenticity check instead of trusting it as a bare header: e.g., require the caller to supply the expected/authenticated shop (from an existing stored session or install record) and compare it against `request.shop` before dispatch, or otherwise make `HmacValidator`/`to_signable_string` incorporate the shop-domain header so tampering invalidates the signature, and document clearly that `shop` in `WebhookMetadata` is not currently covered by the HMAC and must be independently corroborated by the host app.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (legitimate, unprivileged install).
2. Attacker triggers an event (e.g., creates an order) and captures the resulting webhook POST: raw body `B`, header `shopify-hmac-sha256: H` (valid, since `H = HMAC(client_secret, B)` and `client_secret` is shared across all shops using the app), and `shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker replays an HTTP POST to the app's public webhook endpoint with the same body `B` and header `shopify-hmac-sha256: H`, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {... "shop-domain" => "victim-shop.myshopify.com", "hmac-sha256" => H})` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(client_secret, B) == H` — this still passes because `B` and `H` are untouched: [8](#0-7) 
5. The app's handler receives `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body:, ...)` and processes/stores the attacker's data under the victim shop's identity.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
