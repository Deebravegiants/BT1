### Title
Deterministic account IDs use a 160-bit truncated hash, permitting `CREATE2`-style collision attacks that let an attacker capture pre-funded accounts - (File: `core/primitives/src/utils.rs`)

### Summary
NEP-616 "deterministic accounts" derive their `AccountId` from `keccak256(borsh(DeterministicAccountStateInit))` truncated to 20 bytes (160 bits), exactly mirroring the address-space size and derivation style of an EVM `CREATE2` clone address that is the subject of the external report. Because (1) the derivation truncates to 160 bits, (2) both the `code` and `data` fields that feed the hash are entirely attacker-controlled, and (3) `DeterministicStateInitAction` is a permissionless, first-writer-wins action that anyone can submit for any target account id, an attacker who finds a hash collision between their own malicious `state_init` and a victim application's (not-yet-initialized) deterministic account can front-run the legitimate initialization and seize control of any balance already sent/pre-funded to that address.

### Finding Description
`derive_near_deterministic_account_id` computes the account id as: [1](#0-0) 

This is structurally identical to the `CREATE2` collision primitive described in the external report: a 160-bit, attacker-influenceable hash determines an address before the "contract" (here, the deterministic account's code+data) is actually installed.

Two protocol properties make the collision exploitable:

1. **Pre-funding before initialization is explicitly supported.** A `Transfer` action can fund a deterministic account id before the corresponding `DeterministicStateInitAction` executes, and initialization can happen later without additional balance: [2](#0-1) 

2. **State-init is first-writer-wins and not bound to a specific submitter.** `action_deterministic_state_init` only checks whether the account already has a contract installed (`account.contract().is_none()`); if not, it deploys whatever `state_init` is presented in *this* action, regardless of who signed the transaction: [3](#0-2) 

Because `code` (a `GlobalContractIdentifier`, which can reference an attacker's own permissionlessly-deployed global contract) and `data` (an arbitrary `BTreeMap<Vec<u8>, Vec<u8>>`) are both hashed to produce the account id, an attacker has a large, freely searchable space to mount the same "meet-in-the-middle" collision search described in the external report (there, salt values for `CREATE2`; here, `(code, data)` pairs for `DeterministicAccountStateInit`). Given a known/observable target derivation (e.g. a dApp's `spread()`-style factory that publishes `derive_near_deterministic_account_id` inputs, as in `runtime/near-test-contracts/sharded-contract/src/lib.rs`), an attacker can search for a colliding `state_init` whose derived id matches the victim's future account, then submit their own `DeterministicStateInitAction` first. Because the account's code/data are locked in on first init, the attacker permanently claims that account for their malicious global contract and can withdraw any balance sitting there (from pre-funding transfers or later transfers directed to that presumed-safe address) via their own contract's logic (e.g., a `transfer`-to-attacker method).

Note that this is a genuinely new/distinct attack surface from the already-patched `FixDelegatedDeterministicStateInit` bug (which addressed a receiver-id mismatch in meta-transactions): [4](#0-3) 
That fix does not address hash-collision front-running of independently-derived `state_init` values, which remains structurally possible given the 160-bit truncation.

### Impact Explanation
A successful collision lets an attacker permanently seize a deterministic account address intended for a legitimate application/user, redirecting all current and future funds sent to that address into an attacker-controlled global contract - i.e., unauthorized state/balance capture and theft of funds, matching the "concrete token inflation or theft, unauthorized state or balance change" impact bucket. As with the original report, the severity scales with how much value ends up pre-funded/directed at the address before the legitimate owner performs `DeterministicStateInitAction`.

### Likelihood Explanation
This requires an attacker to perform an off-chain hash-collision search over `keccak256` truncated to 160 bits - computationally comparable in cost/feasibility to the `CREATE2`/EOA collision search cited in the original report (their own estimate: on the order of `2^80` operations with a meet-in-the-middle strategy, achievable within reasonable time using significant but attainable hashing hardware). It does not require any validator/node compromise, any privileged account, or any network-layer capability - purely a transaction-submission-level attack, consistent with the required "unprivileged-account" analog. Likelihood is Medium: it requires sustained off-chain compute investment and a target with enough expected/observable pre-funding to make the attack worthwhile, mirroring the judge's rationale in the original report ("attacker could target any pool ... and can wait for enough deposits").

### Recommendation
- Do not truncate the deterministic-account-id hash to 160 bits; use the full 256-bit `keccak256`/SHA3-256 digest (or otherwise widen the collision-resistant portion) so brute-force collision search becomes computationally infeasible, consistent with the mitigation suggested in the original report (avoid attacker-searchable narrow hash spaces).
- Alternatively/additionally, disallow "first-writer-wins" `DeterministicStateInitAction` for accounts that already hold a nonzero balance from an unrelated predecessor unless some out-of-band binding proof is supplied, or require the `DeterministicStateInitAction` to be co-submitted with the funding transfer (as is already enforced for `Transfer`+`CreateAccount`/`AddKey` on implicit accounts) to close the pre-fund/front-run window.
- Consider incorporating additional entropy that is hard for an attacker to search over freely (e.g., binding a portion of the id to the funding transaction/predecessor) so that a valid collision cannot be freely re-targeted at a specific victim's future account.

### Proof of Concept
Conceptual PoC (based on reachable, already-present test scaffolding in `test-loop-tests/src/tests/deterministic_account_id.rs`):
1. Off-chain: Iterate over candidate `DeterministicAccountStateInitV1 { code: GlobalContractIdentifier::AccountId(attacker_global_contract), data }` values, computing `derive_near_deterministic_account_id` for each (see `core/primitives/src/utils.rs:468-477`), until a produced 20-byte truncated hash equals the id independently computed by a target application's own `derive_near_deterministic_account_id` call over its `(code, data)` (e.g., as done by `runtime/near-test-contracts/sharded-contract/src/lib.rs`'s `spread()`).
2. Deploy `attacker_global_contract` as a permissionless global contract (`GlobalContractDeployMode::AccountId`), giving it a method that transfers the account's balance to the attacker.
3. Wait for/observe a `Transfer` funding the target deterministic account id (legitimately expected to later run `DeterministicStateInitAction` with the victim's `state_init`), as demonstrated feasible in `test_deterministic_state_init_prepay_for_storage` (`test-loop-tests/src/tests/deterministic_account_id.rs:466-507`).
4. Before the victim submits their `DeterministicStateInitAction`, submit the attacker's own `DeterministicStateInitAction` with the colliding `state_init` to the same account id; `action_deterministic_state_init` (`runtime/runtime/src/deterministic_account_id.rs:15-48`) installs the attacker's contract since `account.contract().is_none()` is still true.
5. Call the attacker's method on the now-owned account to drain the pre-funded balance.

The full 160-bit collision search itself was not executed (as with the original report, this is infeasible to demonstrate directly within this review), but every on-chain step (permissionless global contract deployment, pre-funding via `Transfer`, and first-writer-wins `DeterministicStateInitAction`) is confirmed reachable and unauthenticated in the current code and test suite cited above.

/// Returns a NEP-616 compliant deterministic account id.
/// This is a NEAR-implicit account ID which is fully defined by its initial state.
pub fn derive_near_deterministic_account_id(
    state_init: &DeterministicAccountStateInit,
) -> AccountId {
    use sha3::Digest;
    let data = borsh::to_vec(&state_init).expect("borsh must not fail");
    let hash = sha3::Keccak256::digest(&data);
    format!("0s{}", hex::encode(&hash[12..32])).parse().unwrap()
}

/// Ensure we can pre-pay the balance for a deterministic account.
///
/// It is a required feature that one can send a Transfer to a non-existing
/// deterministic account first and later initialize it without adding balance,
/// even if more storage than the ZBA limit is used.
#[test]
fn test_deterministic_state_init_prepay_for_storage() {
    let mut env = TestEnv::setup(Balance::from_near(100));
    env.deploy_global_contract(GlobalContractDeployMode::AccountId);

    let data = BTreeMap::from_iter([(b"key".to_vec(), vec![0u8; 100_000])]);
    let (state_init, det_account) = env.new_deterministic_account_with_data(data.clone());

    // Try once without pre-paying, must fail.
    let outcome = env
        .try_deploy_deterministic_account_with_data(data.clone(), Balance::ZERO)
        .expect("should be able to send transaction");
    assert_matches!(
        outcome.status,
        FinalExecutionStatus::Failure(TxExecutionError::ActionError(ActionError {
            kind: ActionErrorKind::LackBalanceForState { .. },
            index: _
        }))
    );

    // Prepay
    let required_for_storage = env.balance_for_storage(state_init);
    env.fund_with_near_balance(det_account.clone(), required_for_storage);
    assert_eq!(
        required_for_storage,
        env.get_account_state(det_account.clone()).amount,
        "account should have been created and funded now"
    );

    // Contract can't be called, yet.
    env.assert_test_contract_not_usable_on_account(det_account.clone());

    // Try creating again, with zero balance again. Must succeed this time.
    env.try_deploy_deterministic_account_with_data(data, Balance::ZERO)
        .expect("should be able to send transaction")
        .assert_success();
    env.assert_test_contract_usable_on_account(det_account);

pub(crate) fn action_deterministic_state_init(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    maybe_account: &mut Option<Account>,
    account_id: &AccountId,
    receipt: &Receipt,
    action: &DeterministicStateInitAction,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    // See https://github.com/near/NEPs/blob/master/neps/nep-0616.md#account-state
    // for the detailed description around deterministic account state.
    let storage_usage_config = &apply_state.config.fees.storage_usage_config;
    let account = match maybe_account {
        Some(account) => account,
        None => {
            // cspell:ignore nonexist
            // `nonexist` -> `uninit` account state transition
            // Create with zero balance now and check later how much of the
            // provided deposit is needed.
            let new_account = create_deterministic_account(Balance::ZERO, storage_usage_config);
            maybe_account.insert(new_account)
        }
    };
    if account.contract().is_none() {
        // `uninit` -> `active` account state transition
        deploy_deterministic_account(
            state_update,
            account,
            account_id,
            &action.state_init,
            result,
            storage_usage_config,
        )?;
    }
