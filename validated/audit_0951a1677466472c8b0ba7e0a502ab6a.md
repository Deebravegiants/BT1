Audit Report

## Title
Unauthenticated panic (DoS) via negative-count `strings.Repeat` in HTTP-trigger workflow ID/owner normalization - ([File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go])

## Summary
`validateHexInput` only bounds the *raw* length of `workflowID`/`workflowOwner` (`len(input) <= expectedLength`) without requiring the `"0x"` prefix to be present, so a full-length lowercase hex string with no prefix passes validation. `normalizeHex` then computes `expectedHexLength - len(hexStr)` and feeds it directly into `strings.Repeat` with no bounds check; when the prefix is omitted, this subtraction goes negative and `strings.Repeat` panics (`"strings: negative Repeat count"`).

## Finding Description
`validateHexInput` at [1](#0-0)  checks `len(input) > expectedLength` and calls `hex.DecodeString` on `strings.TrimPrefix(input, "0x")`, but never enforces that the `"0x"` prefix is actually present nor that the length is *exactly* the expected length after stripping. A 66-character (workflowID) or 42-character (workflowOwner) string of lowercase hex digits with no `"0x"` prefix satisfies both checks.

`normalizeHex` at [2](#0-1)  strips an optional `"0x"` prefix (no-op if absent), computes `expectedHexLength := length - 2`, and calls `strings.Repeat("0", expectedHexLength-len(hexStr))`. For a 66-character workflowID with no prefix, `hexStr` stays 66 chars, `expectedHexLength` is 64, and `strings.Repeat("0", 64-66)` panics with a negative count — this is real, verified Go behavior (`strings.Repeat` panics on negative `count`).

This is reachable pre-authentication: `HandleUserTriggerRequest` calls `h.validatedTriggerRequest` (which runs `validateWorkflowFields` → `validateWorkflowID`/`validateWorkflowOwner`, i.e. `validateHexInput`) and then `h.resolveWorkflowID` (which calls `normalizeHex`) *before* `h.authorizeRequest` [3](#0-2) . No signature, key, or registered workflow is required to reach the panic.

The call chain from the outer gateway handler confirms there is no `recover()` wrapping the request-handling path: `HandleJSONRPCUserMessage` directly invokes `h.triggerHandler.HandleUserTriggerRequest` synchronously with no `defer recover()` [4](#0-3) . A `grep` for `recover()` under `core/services/gateway/**` found only a match in a test file (`response_cache_test.go`), confirming no production `recover()` guards this call path.

## Impact Explanation
This maps to CWE-400 (Denial of Service). Because the panic occurs synchronously inside `HandleJSONRPCUserMessage` with no `recover()` in the call chain shown, an unrecovered panic here will propagate up through whatever goroutine is servicing the JSON-RPC request. Whether that crashes only the single request-handling goroutine or brings down the whole gateway process depends on code outside the reviewed files (the outer transport/dispatcher that ultimately invokes `HandleJSONRPCUserMessage`), which was not located in the available index. At minimum, this is a reliable, unauthenticated way to cause an ungraceful failure of a `workflows.execute` request via an unrecovered panic; at worst, it is a full gateway process crash — the severity boundary could not be fully confirmed from the code reachable here.

## Likelihood Explanation
High. A single, unauthenticated JSON-RPC `workflows.execute` POST with `workflowID` set to exactly 66 lowercase hex characters (or `workflowOwner` set to exactly 42) and no `"0x"` prefix triggers the panic deterministically, with no rate limiting, authentication, or registered-workflow precondition, since the crash point (`resolveWorkflowID` → `normalizeHex`) executes before `authorizeRequest` and `checkRateLimit`.

## Recommendation
1. In `normalizeHex`, guard against a negative repeat count: only pad if `expectedHexLength > len(hexStr)`, otherwise treat as invalid/truncate-reject.
2. In `validateHexInput`, require the `"0x"` prefix to be present and validate the *exact* expected length after stripping it, rejecting oversized or prefix-less inputs before they reach `normalizeHex`.
3. Add a `recover()` around the JSON-RPC request dispatch path (e.g., in `HandleJSONRPCUserMessage` or its caller) so any single malformed request cannot crash the gateway process.

## Proof of Concept
Send to the gateway's HTTP-trigger JSON-RPC endpoint:
```json
{
  "jsonrpc": "2.0",
  "id": "poc-1",
  "method": "workflows.execute",
  "params": {
    "workflow": {
      "workflowID": "abcdefabcdefabcdefabcdefabcdefabcdefabcdefabcdefabcdefabcdefabcd"
    },
    "params": {}
  }
}
```
This 66-character, prefix-less, lowercase-hex `workflowID` passes `validateHexInput(workflowID, 66)` and then panics in `normalizeHex` via `strings.Repeat("0", 64-66)` inside `resolveWorkflowID`, called from `HandleUserTriggerRequest` before `authorizeRequest`. A Go unit test calling `normalizeHex("abcdef...abcd" /*66 chars, no 0x*/, workflowIDLength)` directly reproduces the panic without any mocks or network setup.

```go
func validateHexInput(input string, expectedLength int) error {
	if input != strings.ToLower(input) {
		return errors.New("must be lowercase")
	}

	if len(input) > expectedLength {
		return fmt.Errorf("hex string too long: expected at most %d characters, got %d", expectedLength, len(input))
	}

	hexStr := strings.TrimPrefix(input, "0x")
	_, err := hex.DecodeString(hexStr)
	if err != nil {
		return errors.New("must be a valid hex string")
	}

	return nil
}
```

```go
// normalizeHex normalizes a hex string by stripping 0x prefix, padding with leading zeros, and adding 0x prefix back
func normalizeHex(input string, length int) string {
	hexStr := strings.TrimPrefix(input, "0x")
	// length-2 because we'll add "0x" prefix
	expectedHexLength := length - 2
	paddedHex := strings.Repeat("0", expectedHexLength-len(hexStr)) + hexStr
	return "0x" + paddedHex
}
```
