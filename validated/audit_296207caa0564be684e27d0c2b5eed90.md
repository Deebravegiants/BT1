### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant shop spoofing via header replay - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` derives the merchant identity (`shop`, `topic`, `webhook_id`, `api_version`) entirely from HTTP headers, but the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` verifies only covers the raw request body. This breaks the intended equality `shop_verified_by_HMAC == shop_used_by_handler`, exactly analogous to the reported class of bug where a value acted upon is not the value actually covered by the authenticity check.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop` (and `topic`, `webhook_id`, `api_version`) are read straight from attacker-controllable HTTP headers, unauthenticated by the HMAC: [2](#0-1) 

`Registry.process` only calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, raw_body)` and compares it to the `hmac` header — it never binds the verified body to the `shop` header before dispatching to the handler: [3](#0-2) 

Because the app's `api_secret_key` is shared across every shop/tenant that has the app installed, any merchant who has legitimately installed the app (an unprivileged actor with respect to *other* tenants) receives genuine webhooks with a valid `hmac-sha256` header for their own shop. Since the HMAC never covers the `shop-domain` header, that same attacker can capture one authentic `(raw_body, hmac)` pair from their own store and replay it to the app's webhook endpoint while substituting the `x-shopify-shop-domain` / `shopify-shop-domain` header with a victim merchant's domain. `HmacValidator.validate` still passes (it only checks the body bytes against the secret), and `Registry.process` forwards `request.shop` — now the attacker-chosen victim domain — straight into `WebhookMetadata`, which host applications use as the authoritative tenant identifier for handling the event: [4](#0-3) 

This is a direct instance of "bytes verified versus bytes/fields parsed and acted on" — the signature proves the body is genuine, but the code (and any host app trusting `WebhookMetadata#shop`) treats the unauthenticated header as if it were equally trustworthy proof of tenant origin.

### Impact Explanation
This crosses a tenant boundary without any credential of the victim shop: a single unprivileged app installer can cause the library (and any consuming application relying on `request.shop`/`WebhookMetadata#shop`) to process a webhook event under another merchant's identity. Depending on how the host app uses `shop` (e.g., to select which tenant's data to mutate, or which cached session/token to act on), this can lead to cross-tenant data confusion or unauthorized actions attributed to a victim shop — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Any developer/merchant who can install the app for their own store can trivially capture a legitimate `(raw_body, hmac)` webhook and replay it with a modified shop header — no access to `api_secret_key`, access tokens, or TLS interception is required. The only prerequisite is that the gem's own `process` method never checks shop/body binding, which is a code-level, always-reachable condition.

### Recommendation
Either include the `shop` (and ideally `topic`/`webhook_id`) values in the signed material used for verification, or require host applications/`Registry.process` to independently confirm that the `shop` header corresponds to a shop for which that specific webhook body/topic combination is expected (e.g., cross-check against a per-shop secret or a stored expected shop for the webhook subscription) before dispatching to handlers.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a real webhook, e.g. body `{"id":1}` with header `x-shopify-hmac-sha256: <valid-for-body>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the exact same body and `hmac-sha256` header to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged shop header: [5](#0-4) 
4. `Registry.process` validates the HMAC (passes, since only body bytes matter) and calls the handler with `shop: request.shop` set to `victim-shop.myshopify.com`: [6](#0-5) 
5. The handler/host app processes the event as belonging to `victim-shop`, even though the payload originated from the attacker's own shop.
