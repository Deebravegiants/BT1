## Title
Webhook shop/topic identity spoofing via HMAC that only covers the raw body — (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw JSON body. The `shop`, `topic`, `webhook_id`, and `api_version` values that the handler subsequently trusts and acts on are taken from unauthenticated HTTP headers that are never included in the signed material. An unprivileged attacker who can obtain one genuine, HMAC-signed webhook delivery for their own shop (e.g. by installing the app on a dev/trial store they control) can replay that exact body+HMAC pair to the app's webhook endpoint while substituting the `shop-domain` (and/or `topic`) header for a victim shop, and the signature still validates.

### Finding Description
`Utils::HmacValidator.validate` computes the expected signature over `verifiable_query.to_signable_string` and compares it to the supplied HMAC: [1](#0-0) 

For webhooks, `to_signable_string` is defined to return only the raw request body — it never mixes in the `shop`, `topic`, `webhook_id`, or `api_version` headers: [2](#0-1) 

`Registry.process` then trusts `request.shop` and `request.topic` (pulled straight from headers) to route and label the payload, without any cross-check that they were part of what was signed: [3](#0-2) 

This breaks the intended identity binding:
`shop authenticated (bytes actually covered by HMAC) == shop acted on (request.shop passed to the handler)`

Because the equality does not hold — the HMAC only binds the body bytes, not the shop/topic headers — any valid `(raw_body, hmac)` pair obtained for shop A can be replayed with the `shop-domain` header rewritten to shop B, and `Utils::HmacValidator.validate` will still return `true`, since it never looks at the shop header at all.

### Impact Explanation
This crosses a tenant boundary: an attacker who legitimately owns a webhook delivery for their own store (trivial to obtain by installing any public app on a store they control, or capturing their own store's webhook traffic) can forge webhook deliveries that the host application will process as if they came from an arbitrary victim shop. Depending on how the host app uses `WebhookMetadata#shop` (e.g. deleting session data on `app/uninstalled`, updating per-tenant records on `orders/*`/`customers/*` topics), this enables cross-tenant data corruption or destructive actions against a shop the attacker does not control, using only a body they crafted/received for their own tenant. This matches the "cross-tenant access" critical impact category, since the tenant (shop) identity is not actually authenticated by this gem despite being handed to application code as if it were.

### Likelihood Explanation
Likelihood is high for any app relying on this gem's webhook processing without adding its own shop-binding check: the attacker needs no special privileges — only the ability to install the app / receive one webhook on a shop they control — and needs no knowledge of `api_secret_key`. The signature check in `HmacValidator.validate_signature` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) is satisfied for any header combination, so the replay is a simple HTTP request with a modified header, no cryptographic work required.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the signable material used by `Webhooks::Request#to_signable_string`, or otherwise cryptographically bind the header to the request (e.g., separately verify the shop against a per-shop stored webhook secret/session rather than trusting the header). At minimum, document and enforce that `WebhookMetadata#shop` is untrusted unless the consuming application independently verifies the shop is one it has an active session/installation for, and reject requests where the header-derived shop cannot be reconciled with any authenticated signal.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a store they control) and receives a legitimate webhook delivery, e.g. topic `app/uninstalled`, with headers:
   - `x-shopify-topic: app/uninstalled`
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - `x-shopify-hmac-sha256: <valid-hmac-of-body>`
   - body: `{}` (or whatever Shopify sends)
2. Attacker resends the exact same body and `x-shopify-hmac-sha256` value to the app's public webhook endpoint, but replaces the header:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present), and `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because `to_signable_string` only checks the body — identical to what was signed originally: [4](#0-3) 
4. The registered `app/uninstalled` handler is invoked with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, causing the host application to perform uninstall-cleanup (or any other topic-specific tenant action) against the victim shop's data, even though the victim never sent this webhook and the attacker never possessed `api_secret_key`.
