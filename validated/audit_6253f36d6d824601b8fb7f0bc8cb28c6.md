## Custody invariant reduction

The PaymentProcessor bug reduces to one invariant: **a security-critical authorization decision must be derived from verified on-chain state, not from a value supplied by the calling/executing party.** In the Solidity case, `sellerAcceptedOffer` was a caller-controlled boolean substituting for a real state check.

## Candidate paths considered

1. `dispatchable_fungible_asset`/`fungible_asset` withdraw/deposit sanity checks — these correctly derive authorization from `object::owns`/`FungibleStore.frozen`, not from caller flags. Rejected.
2. `object::transfer_raw`/`verify_ungated_and_descendant` — ownership and `allow_ungated_transfer` are read from `ObjectCore` state, not parameters. Rejected.
3. `object_code_deployment::upgrade`/`freeze_code_object` — authority derived from `object::is_owner(code_object, publisher_address)`, a real state check. Rejected.
4. `multisig_account::validate_multisig_transaction` — the equality check between the payload actually being executed and the payload the owners voted on is **feature-flag-gated and skippable via an empty parameter**, unlike the unconditional hash-based path. This is the strongest analog.

## Title
Multisig transaction payload-match check is executor-controllable and feature-flag-gated, allowing execution of an unapproved payload - (File: aptos-move/framework/aptos-framework/sources/multisig_account.move)

### Summary
`validate_multisig_transaction` verifies that the payload about to be executed matches what owners approved only when a runtime feature (`abort_if_multisig_payload_mismatch_enabled`) is enabled *and* the caller-supplied `payload` argument is non-empty. When the full transaction payload was stored on-chain (the common `create_transaction` flow, as opposed to `create_transaction_with_hash`), an executor can pass an empty `payload` to skip the comparison entirely — mirroring the PaymentProcessor pattern of trusting a caller-supplied value instead of enforcing a state-derived invariant.

### Finding Description
`validate_multisig_transaction` [1](#0-0)  is invoked by the VM as part of the multisig prologue, taking an executor-supplied `payload: vector<u8>`.

For transactions created via `create_transaction_with_hash` (only a hash stored), the match check is unconditional: [2](#0-1) 

For transactions created via `create_transaction` (the full payload stored on-chain, `transaction.payload.is_some()`), the equivalent check is guarded by both a feature flag and a non-emptiness condition on the caller-supplied `payload`: [3](#0-2) 

If `features::abort_if_multisig_payload_mismatch_enabled()` is false, or the executor simply submits an empty `payload` vector, this block is skipped unconditionally — no assertion ties the executed transaction back to `transaction.payload`, the value the owners actually approved and voted on via `approve_transaction`/`vote_transanction` [4](#0-3) . The existence of a dedicated, separately-toggleable feature flag whose name (`abort_if_multisig_payload_mismatch_enabled`) implies "abort if mismatch" strongly suggests that in the default/disabled state, a payload mismatch does **not** abort — i.e., the check is opt-in rather than an unconditional invariant, structurally identical to `sellerAcceptedOffer` being a spoofable flag instead of a real state check.

### Impact Explanation
If the actual entry function dispatched by the VM for a multisig execution is derived from the executor-supplied `payload` bytes (rather than always re-reading `transaction.payload` from storage), then any executing owner could submit a transaction body different from the one that the required quorum of owners approved, once quorum/timelock conditions are otherwise satisfied. Since a multisig account is a resource account that can hold and control APT, fungible assets, objects, and code-object upgrade authority, this would let a single executing owner redirect withdrawals, mint/burn calls, or upgrade payloads away from what was voted on — a direct custody-control break for multisig-held assets.

### Likelihood Explanation
Likelihood depends entirely on how the VM wires the caller-supplied `payload` bytes into actual execution versus the stored `transaction.payload` — I was not able to trace this final link (in `aptos-move/aptos-vm/src/aptos_vm.rs` / `transaction_validation.rs`) within the available tool budget. If the VM always executes the on-chain stored payload regardless of what is passed for validation, this finding degrades to at most an event/log inconsistency (informational), not a custody break. I flag this explicitly as an unresolved and necessary verification step before treating this as a confirmed critical/high-severity custody bypass.

### Recommendation
Make the payload-match assertion for the on-chain-stored-payload path unconditional (remove the feature-flag gate and the `!payload.is_empty()` escape), analogous to how the hash-based path is already unconditionally enforced, so that the executed payload can never diverge from the owner-approved payload regardless of feature-flag state or executor-supplied emptiness.

### Proof of Concept
Conceptual (unverified against VM execution wiring):
1. Owner A creates a multisig transaction via `create_transaction` with payload `P1` (e.g., transfer 100 APT to A). Enough owners approve.
2. Owner A (the executor) submits the execution transaction with an empty `payload` argument (or the network has `abort_if_multisig_payload_mismatch_enabled` disabled).
3. `validate_multisig_transaction` skips the payload-match assertion at lines 1373-1384 since `payload.is_empty()` is true.
4. If VM execution then dispatches based on the submitted (different) payload bytes rather than `transaction.payload`, funds/authority intended for `P1` are instead redirected per the unapproved payload.

**Note:** Step 4 is the unverified link; confirming it requires reading `aptos-move/aptos-vm/src/aptos_vm.rs` multisig execution handling, which I could not complete before the tool budget was exhausted. Given the index size limits, a Devin session with full repo access would be needed to trace this precisely and confirm actual exploitability.
