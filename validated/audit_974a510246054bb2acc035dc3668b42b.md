### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [1](#0-0) , while `shop` (and `topic`, `webhook_id`, `api_version`) are read directly from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates only that the body's HMAC matches, then forwards `request.shop` straight into the handler as trusted, verified tenant data [3](#0-2) .

### Finding Description
The identity binding that should hold is:
`HMAC-verified(bytes) == bytes that determine the shop attributed to this webhook`

In `HmacValidator.validate`, `verifiable_query.to_signable_string` is the only input covered by the signature check [4](#0-3) . For `Webhooks::Request`, `to_signable_string` returns `@raw_body` exclusively [1](#0-0) . The `shop` accessor, however, is derived purely from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is never included in the signed bytes [2](#0-1) .

`Registry.process` raises only if the HMAC of the body fails, then immediately builds `WebhookMetadata` using `request.shop` as the tenant identifier passed to the caller's handler [3](#0-2) . The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify" and that `data.shop` is "The shop domain of the webhook" [5](#0-4) [6](#0-5) , i.e. the gem contractually presents `shop` as authenticated, verified data — so any host app that attributes the payload to `data.shop` (exactly as the shipped example does [7](#0-6) ) is following the documented API, not misusing it.

Because only the body — not the shop header — is bound by the signature, a party who possesses one legitimately Shopify-signed webhook body (e.g. from their own store's installation of the app, which uses the same `client_secret` for every shop) can replay that exact body to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. The HMAC check still passes because it only checks the body bytes, and the tampered `shop` value flows into `WebhookMetadata.shop` as if it were verified.

### Impact Explanation
This breaks the tenant/session boundary: an unprivileged app user (already receiving genuine signed webhooks for their own shop) can forge the shop attribution on that payload to make the receiving application ingest, store, or act on data under a different shop's identity — a cross-tenant data-integrity/confusion issue, since the app has no gem-provided way to distinguish this from a legitimate webhook for the claimed shop.

### Likelihood Explanation
Likelihood is moderate: the attacker needs at least one genuinely Shopify-signed webhook body (trivially available by installing the app on their own store and triggering any subscribed event) and the ability to send an HTTP POST to the app's public webhook endpoint with a modified header — both require no privileged credentials, access tokens, or `client_secret`.

### Recommendation
Include the shop domain (and ideally topic/webhook-id/api-version) in the bytes that are HMAC-verified for webhook requests, or otherwise cryptographically bind the header-derived `shop` value to the signed body before exposing it via `WebhookMetadata`, so `Registry.process` cannot report an unverified shop as authenticated.

### Proof of Concept
1. Install the target app on shop `attacker.myshopify.com`; trigger any webhook (e.g. `orders/create`). Capture the raw POST body and the valid `x-shopify-hmac-sha256` value Shopify computed for it.
2. Replay this exact HTTP request to the app's webhook endpoint, keeping the body and HMAC header unchanged, but replacing `x-shopify-shop-domain` with `victim.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` (only the body is checked) [4](#0-3) , and `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` [8](#0-7) , causing the app to process attacker-controlled data as belonging to `victim.myshopify.com`.
