### Title
Predictable, unauthenticated offline session ID used as the non-embedded session cookie value enables session fixation / cross-tenant hijacking - (File: `lib/shopify_api/auth/session.rb`, `lib/shopify_api/auth/oauth.rb`)

### Summary
For non-embedded apps, `ShopifyAPI::Auth::Oauth.validate_auth_callback` sets a browser cookie whose value is the session's `id`. That `id` is generated deterministically from public, unauthenticated data — `"offline_#{shop}"` for offline sessions (and `"#{shop}_#{associated_user.id}"` for online sessions) — with no HMAC, nonce, or secret binding it to the OAuth exchange that produced it.

### Finding Description
`ShopifyAPI::Auth::Session.from` computes the session identifier purely from the `shop` domain (and, for online sessions, the numeric Shopify user id): [1](#0-0) 

This `id` is exactly the value placed into the `shopify_app_session` cookie that is handed back to the browser after a successful OAuth callback for non-embedded apps: [2](#0-1) 

The library documents this cookie/session-id as the sole artifact host applications should use to retrieve the stored `Session` (and thus the access token) for subsequent requests: [3](#0-2) [4](#0-3) 

The identity binding that is broken here is: **the bytes stored in the session cookie (used as the lookup key for a merchant's stored access token) should be bound to the authenticated OAuth exchange, but instead equal `"offline_" + shop`, i.e., they are fully derivable by anyone who knows the target's `.myshopify.com` domain — no server-side secret, HMAC, or random nonce is mixed in.** Compare this with the OAuth callback's own `state` cookie, which correctly uses a `SecureRandom.alphanumeric(NONCE_LENGTH)` nonce: [5](#0-4) 

Shop domains are not secrets — they are visible in storefront URLs, install links, marketing pages, App Store listings, etc. Any unprivileged internet user who knows (or enumerates) a target shop's domain can compute the exact session id/cookie value the gem will produce and set for that shop after it completes OAuth.

### Impact Explanation
Per the documented usage pattern, host applications look up the stored `Session` (containing the merchant's access token) keyed by this cookie value with no additional server-side proof of authenticity: [6](#0-5) 

Because the cookie value is a predictable function of public data, an attacker can:
1. Pre-set (fixate) their own browser's `shopify_app_session` cookie to `offline_<target-shop>.myshopify.com` before the real merchant authorizes the app, or
2. Simply set that cookie value in their own browser at any time after the target shop has completed OAuth once (since the id is stable/deterministic and doesn't rotate), and have the host app resolve it to the victim shop's stored session/access token when the attacker calls into `SessionUtils.current_session_id` / the app's session repository.

This crosses a tenant boundary using bytes that were never authenticated by Shopify or by this gem — the classic "session id derived from unauthenticated bytes" defect — leading to cross-tenant access to another merchant's session/access token via the app, which meets the Critical bar ("cross-tenant access") in this program's rules.

### Likelihood Explanation
High. No credentials, TLS interception, or privileged access are required — only knowledge of a target's `myshopify.com`/`myshopify.io` domain, which is routinely public (storefront URL, marketing site, App Store reviews, etc.). The only prerequisite is that the host application follows the gem's own documented pattern of trusting the cookie value as the session lookup key (which is exactly what the library's official usage docs instruct developers to do), so this is not a case of the host app ignoring the gem's API — it is a direct consequence of following it.

### Recommendation
- Do not derive the session id (or the cookie value used to retrieve it) solely from the shop domain and/or Shopify user id.
- Bind the cookie value to an unguessable, per-authorization secret (e.g., a `SecureRandom` token generated at session-creation time, stored server-side and mapped internally to the deterministic session id), so the cookie itself cannot be forged/guessed by an unprivileged party.
- Alternatively, mark the id as an internal storage key only, and issue a separate signed/opaque cookie value (e.g., HMAC-signed with `api_secret_key` or a random token) that must be validated before session lookup.

### Proof of Concept
1. Attacker learns (or guesses) a target shop's domain, e.g. `target-shop.myshopify.com` (publicly visible on the shop's storefront).
2. Attacker computes the offline session id exactly as the gem would: `offline_target-shop.myshopify.com`, per [7](#0-6) .
3. In their own (or a victim's) browser, attacker sets the cookie `shopify_app_session=offline_target-shop.myshopify.com` for the app's domain (either via pre-authorization fixation, or, after the real merchant has installed the app and this deterministic id/session record exists in the host app's session store).
4. Attacker requests an app page/API route; the host app calls `SessionUtils.current_session_id(nil, cookies, false)`, which simply returns the raw cookie value with no verification: [8](#0-7) .
5. The host app looks up the `Session` for `offline_target-shop.myshopify.com` in its session store (following the documented `SessionRepository.store_session`/load pattern) and finds the real merchant's stored access token, since that is the exact id the gem generated and persisted for that shop during the merchant's legitimate OAuth flow.
6. The app now serves the attacker's request as if it were an authenticated request from `target-shop`, exposing that shop's data/access token usage to the attacker — a cross-tenant compromise achieved purely by guessing a public shop domain, with no secret, token, or credential in the attacker's possession.
