### Title
Transaction/message signing paths accept caller-supplied `keyId`/`txMeta.keyId` validated only for structural well-formedness, bypassing per-asset key-derivation policy restrictions - ([File: features/tx-signer/src/module/seed-signer.ts])

### Summary
`OracleUniGeoDistribution`'s bug class is: a value is computed and *policy-validated* (bounded to a safe range) only in one call path (`isValidParams`), while other call paths that consume the same underlying computation (`query`, `computeSwap`, `cumulativeAmount0/1`) skip that validation and only rely on a much weaker/no check, letting execution proceed with out-of-range values. The same structural pattern exists in Hydra's transaction/message signing stack: `KeyIdentifier` objects are supposed to be constrained by asset-specific policy rules (`assertKeyIdentifierParameters` / `createGetKeyIdentifier` — allowed purposes, allowed chain indices, whether multiple addresses/arbitrary address indices are permitted, whether raw XPUB-level derivation is permitted), but the actual signing call paths (`SeedBasedTransactionSigner#sign`, `createSigner` in `features/keychain/module/create-signer.js`) only check `KeyIdentifier.validate(keyId)`, which merely verifies that the object is *structurally* a valid `KeyIdentifier` (valid `derivationAlgorithm`, `keyType`, parseable `derivationPath`) — not that it conforms to the asset's allowed policy.

### Finding Description
`libraries/key-identifier/src/key-identifier.js` defines: [1](#0-0) 
`KeyIdentifier.validate` simply attempts to construct a `KeyIdentifier` and returns whether construction succeeded — it enforces only structural constraints (algorithm/keyType/path parse-ability), not any asset-specific derivation policy.

Separately, `libraries/key-utils/src/key-identifier.js` (`assertKeyIdentifierParameters`, used by `createGetKeyIdentifier`) enforces the actual security policy: allowed `purpose`s, allowed `chainIndex` values, whether `addressIndex` may be non-zero (multi-address mode), and whether XPUB-level (unbounded) derivation is permitted: [2](#0-1) 
This stricter policy validation is applied only when a `KeyIdentifier` is minted via `baseAsset.api.getKeyIdentifier(...)` (i.e., `createGetKeyIdentifier`'s returned function).

In `features/tx-signer/src/module/seed-signer.ts`, `signTransaction` accepts an externally-supplied `unsignedTx.txMeta.keyId` and, if present, uses it directly for signing after only the weak structural check: [3](#0-2) 
and the underlying `sign()` closure repeats the same weak check: [4](#0-3) 
The same pattern recurs in `features/keychain/module/create-signer.js`: [5](#0-4) 
and in `features/tx-signer/README.md`, confirming `txMeta.keyId` is treated as ordinary, externally-suppliable transaction metadata reaching `exodus.transactionSigner.signTransaction`: [6](#0-5) 

Because `seedId` is taken from `walletAccount.seedId` (a trusted, resolved value), the immediate blast radius is scoped to keys derivable under that seed. However, unlike the code paths that mint `KeyIdentifier`s via `baseAsset.api.getKeyIdentifier`, this path performs **no check** that:
- `derivationPath`'s `purpose`/`chainIndex`/`addressIndex` fall within the asset's `allowedPurposes`/`allowedChainIndices`,
- `addressIndex` is zero when `allowMultipleAddresses` is false,
- the account index matches `walletAccount.index` (there is no assertion tying `keyId`'s account index to `unsignedTx.txMeta.accountIndex`, which itself is only checked to be *an integer*, not that it matches the wallet account being confirmed to the user),
- XPUB-level (unbounded) derivation is disallowed where the asset's policy requires bounded derivation.

This is directly analogous to `LibOracleUniGeoDistribution`: the "safe" validation function exists and is invoked in one legitimate path, but a second path reaching the same privileged sink (here: keychain private-key signing; there: the LDF tick range used for swap execution) only performs a superficial/no-op check.

### Impact Explanation
If a caller (a dApp/malicious website via an injected web3 provider, or a compromised/lower-trust feature module in the same process) can influence `unsignedTx.txMeta.keyId` or `unsignedTx.txMeta.accountIndex` when requesting a "confirm and sign" transaction for a given `walletAccount`, the wallet's UI would show the user the transaction they intend to authorize, while the *actual private key used to produce the signature* is determined by the attacker-supplied `keyId`/`accountIndex`, not the account the user believes they are signing with. Because only structural validation is performed, an attacker can supply any well-formed derivation path (any purpose/chainIndex/addressIndex/account index) reachable under the same seed, producing an unauthorized signature — potentially exposing an address/private-key-derived signature for a different account under the same seed than the one the user consented to interact with. This maps to the "unauthorized signing" / "cross-account privilege bleed" impact category.

### Likelihood Explanation
Exploitability depends on whether an unprivileged caller (dApp/provider bridge or another feature) can actually populate `unsignedTx.txMeta.keyId`/`accountIndex` before it reaches `SeedBasedTransactionSigner#signTransaction`. I was not able to fully trace, within the available index, whether the `txMeta` object passed by web3 providers documented in `docs/web3-providers/*` is sanitized/stripped of a `keyId` field before reaching `exodus.transactionSigner.signTransaction`, or whether `txMeta` is asset-plugin generated. This is the key open question determining real-world reachability from an untrusted origin; it should be confirmed by tracing each asset plugin's transaction-building code and the RPC/provider bridge layer, which are outside what the current index exposes.

### Recommendation
- Enforce the same policy validation (`assertKeyIdentifierParameters`/asset-specific `allowedPurposes`/`allowedChainIndices`/`allowMultipleAddresses`) inside `SeedBasedTransactionSigner#signTransaction` and `create-signer.js`'s `sign`/`getPublicKey`, not just `KeyIdentifier.validate`, whenever a caller-supplied `keyId` is accepted.
- Assert that any caller-supplied `keyId`'s account index matches `walletAccount.index`/`unsignedTx.txMeta.accountIndex`, and that `unsignedTx.txMeta.accountIndex` itself matches `walletAccount.index` unless an explicit, audited override path is required.
- Audit every asset-plugin/provider-bridge code path that constructs `unsignedTx.txMeta` to confirm `keyId` cannot be influenced by content originating from an unprivileged dApp/origin.

### Proof of Concept
Not independently reproducible from the indexed code alone (requires confirming that `unsignedTx.txMeta.keyId`/`accountIndex` is reachable end-to-end from an untrusted dApp/provider call into `exodus.transactionSigner.signTransaction` without sanitization). Conceptually:
1. A caller invokes `exodus.transactionSigner.signTransaction({ baseAssetName, unsignedTx: { txData, txMeta: { keyId: <arbitrary well-formed KeyIdentifier for a different account/asset under the same seed>, accountIndex: <arbitrary> } }, walletAccount })`.
2. `SeedBasedTransactionSigner#signTransaction` (`features/tx-signer/src/module/seed-signer.ts:136-151`) only checks `KeyIdentifier.validate(keyId)` (structural) and proceeds to derive/sign with that `keyId` under `walletAccount.seedId`, bypassing the asset's `allowedPurposes`/`allowedChainIndices`/`allowMultipleAddresses` policy that would otherwise be enforced via `baseAsset.api.getKeyIdentifier`. import KeyIdentifier from '@exodus/key-identifier'
import assert from 'minimalistic-assert'

export async function createSigner({ keychain, seedId }) {
  const getPublicKey = async ({ keyId }) => {
    assert(KeyIdentifier.validate(keyId), 'getPublicKey: invalid `keyId`')
    return keychain.getPublicKey({ seedId, keyId })
  }

  const sign = ({ data, keyId, signatureType, enc, tweak, extraEntropy }) => {
    assert(KeyIdentifier.validate(keyId), 'sign: invalid `keyId`')

    return keychain.signBuffer({
      seedId,
      keyId,
      data,
      signatureType,
      enc,
      tweak,
      extraEntropy,
    })
  }

  return { sign, getPublicKey }
}
