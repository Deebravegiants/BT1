### Title
Webhook `shop` identity is taken from an unauthenticated header while the HMAC only covers the request body, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, but the `shop` value that identifies which tenant the webhook belongs to is read from an HTTP header that is **not** part of the signed material. This breaks the binding `shop-authenticated == shop-that-the-HMAC-actually-covers`, the same class of defect as the external report (a value used for accounting/identification is excluded from the verification that is supposed to authenticate it).

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop` is read from the `x-shopify-shop-domain` / `shopify-shop-domain` header, which is completely outside the HMAC input: [2](#0-1) 

`Registry.process` validates the HMAC over the request (i.e., over the body only) and then dispatches to the handler using the unauthenticated `request.shop`: [3](#0-2) 

The HMAC validator itself only ever signs/verifies whatever `to_signable_string` returns: [4](#0-3) 

Because the `x-shopify-shop-domain` header sits outside the signed bytes, `WebhookMetadata.shop` handed to the host application's handler is **not cryptographically bound to the body whose HMAC was just verified**. Any unprivileged user who is a legitimate merchant of the app (and therefore automatically receives real, Shopify-signed webhook payloads for their own store, without ever seeing `api_secret_key`) can:
1. Capture one legitimate webhook call Shopify sends to the app's public webhook URL for their own shop `A.myshopify.com` (raw body `B`, valid `x-shopify-hmac-sha256`).
2. Replay `B` with the *same, still-valid* HMAC to the same public webhook endpoint, but with the `x-shopify-shop-domain` header changed to any other shop domain `B.myshopify.com`.
3. `Utils::HmacValidator.validate` still returns `true` (it never looked at the shop header), so `Registry.process` accepts the request and invokes the handler with `shop: "B.myshopify.com"`.

If the host application (as documented for this gem) uses `WebhookMetadata#shop` to select the tenant's stored access token, update tenant records, or otherwise scope the action, this yields cross-tenant data manipulation/disclosure without ever touching `api_secret_key` or any credential belonging to the victim shop.

### Impact Explanation
This satisfies the "Critical - cross-tenant access" bar: a merchant with no special privileges can cause an app to process a webhook body against a tenant identity it never authenticated, letting them write/read data under another shop's identity that the host app associates via `WebhookMetadata.shop`. No leaked credentials, TLS interception, or `api_secret_key` access is required — only ordinary receipt of a webhook the attacker's own shop legitimately triggers, and the ability to POST to the app's public webhook endpoint (which is not secret).

### Likelihood Explanation
Likely to be reachable: webhook endpoints are public HTTP routes (no bearer/session auth), any app subscriber can generate a validly-signed body for their own shop by performing a normal action (e.g., updating an order), and replaying with a different `shop` header requires no special tooling.

### Recommendation
Bind the tenant identity into the verified material, mirroring the Morpho fix pattern of including the previously-ignored value in what is checked: either (a) include `shop`, `topic`, and `webhook_id` in the HMAC signable string on both the sending and verifying sides (this would require changing the wire format Shopify sends, which this gem cannot unilaterally alter), or, more practically, (b) require the host application to cross-check `request.shop` against the tenant that owns the URL/subscription the request arrived on (e.g., match `webhook_id` to a stored subscription record for the tenant) rather than trusting the header value alone, and document this requirement prominently since `Registry.process` currently implies the shop field is trustworthy once `HmacValidator.validate` passes.

### Proof of Concept
```ruby
# Attacker owns shop "attacker-shop.myshopify.com" and receives a legitimate
# Shopify-signed webhook for it, e.g. via a normal order update:
raw_body = '{"id":123,...}'                      # legitimate body from Shopify
hmac      = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"),
                                  APP_API_SECRET, raw_body)  # computed by Shopify, not attacker

# Attacker replays the exact same body+hmac to the app's public webhook URL,
# only changing the shop-domain header:
forged_headers = {
  "x-shopify-topic"        => "orders/updated",
  "x-shopify-hmac-sha256"  => Base64.encode64(hmac),      # still valid, body unchanged
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com", # attacker-controlled, unsigned
  "x-shopify-webhook-id"   => "any-id",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) is true (only raw_body is checked)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
```
`lib/shopify_api/webhooks/registry.rb#L190` and `#L198-199` show the validation and the unauthenticated `shop` being forwarded together.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
