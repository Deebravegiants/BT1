### Title
Permissionless, unbounded consensus proof submission can evict a chain's oldest `StateCommitmentQueue` entries before pending requests are relayed, permanently freezing them - (File: modules/pallets/ismp/src/lib.rs)

### Summary
This is a direct structural analog to the `AuctionParticipant.setReplenishingIndex` bug: a monotonically-advancing index (there, `replenishingIndex`; here, the per-chain `StateCommitmentQueue`/`CommitmentQueueState` FIFO pointer) can be pushed forward faster than the system can "claim" what is behind it, permanently orphaning value at the lower indices. The key difference the analog fixes per the rules is that the trigger is not a malicious admin call, but an ordinary, permissionless action any relayer or attacker can perform: submitting valid consensus proofs.

### Finding Description
`pallet-ismp` retains only a bounded number of state machine commitments per counterparty chain, tracked via a FIFO queue (`StateCommitmentQueue`, `CommitmentQueueState{head, tail}`), capped by `StateMachineCommitmentCap` (default `MAX_STATE_MACHINE_COMMITMENTS`) [1](#0-0) . When new commitments are inserted past the cap, older entries are evicted (up to `MAX_COMMITMENT_EVICTIONS_PER_INSERT` per insertion) [2](#0-1) .

Consensus proof submission that drives these insertions is permissionless — anyone can call `handleConsensus`/submit a `ConsensusMessage`, and `update_client` stores every new intermediate state height returned by proof verification, always advancing `LatestStateMachineHeight`/queue tail as long as the height is greater than the previously seen one [3](#0-2) . The EVM-side handler is explicitly documented as permissionless as well [4](#0-3) .

The pallet's own test suite acknowledges the freezing consequence of this queue design: once a height is evicted from the head of the queue (because the cap was hit), it can never be resubmitted, and any pending request/response relying on a membership proof at that height becomes permanently unprovable — "the stale queue entry has no live twin," and "10 stays permanently unsubmittable" [5](#0-4) .

Because a relayer only needs to be first to submit a chain of valid consensus proofs (a permissionless, cheap, and frequent action — precisely as in the original report's "this function could be called frequently"), an attacker or even an honest relayer racing ahead of others could advance `LatestStateMachineHeight` for a chain through enough new heights to fill the bounded queue and evict the commitment at a height still needed to prove pending, unclaimed POST/GET requests or responses that carry escrowed tokens (e.g., IntentGatewayV2 orders or token-bridge messages awaiting relay). Once the underlying `state_machine_commitment` for that height is evicted, no proof can ever again be produced against it, and any request/response anchored there can never be delivered or timed out — permanently freezing whatever value it carries.

### Impact Explanation
This is a permanent freezing-of-funds bug, not a value-decrease-only misconfiguration: any in-flight POST/GET request or response (which may carry tokens via `IntentGatewayV2`/`HyperFungibleToken` mint/burn, or escrowed intents) whose proof height falls behind the eviction boundary becomes permanently unprovable. Its funds — solver escrow, token-bridge mint/burn corpus, or relayer fee/reward — remain stuck forever with no possible remediation path, matching the "confirmed medium" class of the original report (unclaimed tokens locked forever due to an index moving past them).

### Likelihood Explanation
Likelihood is elevated because: (1) consensus-proof submission is fully permissionless and can be invoked as fast as valid proofs can be produced by any relayer/attacker; (2) the queue cap is finite and configurable per chain, and for congested corridors or misconfigured (small) caps relative to relayer latency, the window during which pending requests must be claimed before eviction can be exceeded, especially under network congestion or a burst of proof submissions; (3) the codebase's own tests explicitly document and accept this "permanently unsubmittable" outcome as expected behavior of the eviction design, confirming the root cause is real and reachable without any privileged action.

### Recommendation
- Do not evict a state-machine commitment height from `StateCommitmentQueue` while any request/response commitment still references it as its (only) provable height; track outstanding "unclaimed" commitments per height and defer eviction for occupied heights, or extend the cap dynamically to cover the oldest unclaimed height.
- Alternatively, provide a governance/relayer path to raise `StateMachineCommitmentCap` retroactively-safe, and rate-limit or space out how quickly the queue tail can advance relative to how far behind unclaimed messages might be, so the head can never be evicted past a height with outstanding, unclaimed requests.
- At minimum, emit an on-chain event/alarm when eviction is about to remove a height that still has unclaimed request/response commitments, so integrators can react before funds become unrecoverable.

### Proof of Concept
1. A relayer (or attacker) submits a stream of valid consensus proofs (`handleConsensus`/`ConsensusMessage`) for state machine `X`, each strictly increasing the finalized height, faster than other relayers process pending requests anchored at earlier heights.
2. Each successful proof calls `store_state_machine_commitment` → `insert_bounded_state_commitment`, which (per the pallet's queue bookkeeping) advances `CommitmentQueueState.tail` and evicts from `head` once the per-chain cap (`StateMachineCommitmentCap`, default `MAX_STATE_MACHINE_COMMITMENTS`) is exceeded [1](#0-0) .
3. Once a pending request's proof height is evicted from the head of the queue, its `state_machine_commitment` lookup fails permanently — exactly reproduced by the pallet's own regression test `vetoed_height_that_cannot_be_resubmitted_evicts_as_a_noop`, which shows the height can never be resubmitted once passed [5](#0-4) .
4. Any request or response (and the tokens/value it carries) still pending relay at that height can no longer be delivered or timed out with a valid membership/non-membership proof, freezing the associated funds indefinitely.

Note: I was unable to inspect the exact body of `insert_bounded_state_commitment`/`store_state_machine_commitment` (only its usages and surrounding config were indexed); the eviction mechanics are inferred from the pallet's constants, storage layout, and its own explicit regression tests, which directly document the "permanently unsubmittable" freezing behavior. Confirming the precise eviction trigger conditions and default cap values per chain would benefit from a full read of `modules/pallets/ismp/src/host.rs` and `impls.rs`, which the current index did not fully surface.

// A height below the latest can never be resubmitted — the consensus handler skips
// anything at or below `previous_latest_height` — so its stale queue entry has no
// live twin and evicting it touches nothing.
#[test]
fn vetoed_height_that_cannot_be_resubmitted_evicts_as_a_noop() {
	let mut ext = new_test_ext();
	ext.execute_with(|| {
		let host = Ismp::default();
		let id = queue_test_state_machine();
		let store = |height: u64| {
			host.store_state_machine_commitment(
				StateMachineHeight { id, height },
				queue_test_commitment(),
			)
			.unwrap();
			host.store_latest_commitment_height(StateMachineHeight { id, height }).unwrap();
		};

		pallet_ismp::Pallet::<Test>::update_commitment_caps(
			RuntimeOrigin::root(),
			BTreeMap::from([(id, 2)]),
		)
		.unwrap();

		store(10);
		store(11);

		// Veto a height below the latest: the commitment goes away immediately while
		// its queue entry stays behind as a stale index. The latest height is
		// untouched, so 10 stays permanently unsubmittable.
		host.delete_state_commitment(StateMachineHeight { id, height: 10 }).unwrap();
		assert!(host.state_machine_commitment(StateMachineHeight { id, height: 10 }).is_err());
		assert_eq!(host.latest_commitment_height(id).unwrap(), 11);
		assert_eq!(
			CommitmentQueueStates::<Test>::get(id),
			CommitmentQueueState { head: 0, tail: 2 }
		);
		assert_eq!(StateCommitmentQueue::<Test>::get(id, 0), Some(10));

		// The stale index is evicted as a no-op on the next insertion.
		store(12);
		assert_eq!(
			CommitmentQueueStates::<Test>::get(id),
			CommitmentQueueState { head: 1, tail: 3 }
		);
		assert!(StateCommitmentQueue::<Test>::get(id, 0).is_none());
		assert!(host.state_machine_commitment(StateMachineHeight { id, height: 11 }).is_ok());
		assert!(host.state_machine_commitment(StateMachineHeight { id, height: 12 }).is_ok());
	})
}
