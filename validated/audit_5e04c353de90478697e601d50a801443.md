Audit Report

## Title
Check-then-act TOCTOU race in JWT replay-guard allows a single-use HTTP trigger token to authorize two concurrent workflow executions - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

## Summary
`WorkflowMetadataHandler.Authorize` checks JWT replay status via `jwtCache.isReplay(claims.ID)` under a read lock, then performs signer/authorization lookups, and only afterward calls `jwtCache.recordUsage(claims.ID)` under a separate write lock. Because the check and the record are not one atomic critical section, two concurrent requests presenting the identical externally-supplied JWT can both pass the replay check before either records usage, allowing a nominally single-use trigger token to authorize two concurrent workflow executions.

## Finding Description
`Authorize` verifies the JWT, extracts `claims.ID` (the `jti`), and calls `h.jwtCache.isReplay(claims.ID)`, which takes only a read lock (`cache.mu.RLock()`) and releases it immediately. Execution then proceeds through workflow/signer authorization logic, and only calls `h.jwtCache.recordUsage(claims.ID)` (a separate `cache.mu.Lock()`) near the end of the function. There is no lock held across the "check → authorize → record" sequence. The `httpTriggerHandler.HandleUserTriggerRequest` entry point calls `authorizeRequest` → `Authorize` for each incoming request with no serialization by `jti`, so concurrent identical requests can race through `isReplay` (both `false`) before either calls `recordUsage`, resulting in both being treated as valid and both being forwarded toward `SendToNode`/DON execution. This mirrors the exact race-condition bug class that the codebase has already fixed elsewhere: `core/capabilities/vault/request_replay_guard.go`'s `CheckAndRecord` performs the existence check and map write atomically under one mutex acquisition, and is explicitly tested for correctness under 100 concurrent goroutines. That pattern was not applied to `jwtReplayCache`.

## Impact Explanation
A single-use workflow-execution JWT can be replayed exactly once under a race window, causing the DON to receive and process a duplicate `MethodWorkflowExecute` trigger for what is intended to be a single authenticated request. This undermines the single-use guarantee that the code explicitly implements and tests for sequentially, and constitutes limited request duplication for an already-authenticated caller (not a bypass to a different identity or workflow). It maps to the in-scope "gateway request impersonation"/duplicate-execution impact category, but is capped at duplicate processing rather than full authentication bypass since signer/authorization checks succeed independently and correctly for both racing requests.

## Likelihood Explanation
No privileged or host-level access is required; an unprivileged client who already holds one valid JWT for a single trigger can attempt to fire two near-simultaneous requests carrying that same token to win the narrow race window between `isReplay`'s lock release and `recordUsage`'s lock acquisition. Winning the race is not guaranteed on every attempt but is straightforward to attempt repeatedly and reliably feasible under normal goroutine/network scheduling, making likelihood moderate.

## Recommendation
Combine `isReplay` and `recordUsage` into a single atomic method that takes the write lock once, checks for the `jti`'s existence, inserts it if absent, and returns an error if it was already present — matching the pattern in `core/capabilities/vault/request_replay_guard.go`'s `CheckAndRecord`. Update `WorkflowMetadataHandler.Authorize` to call this atomic method in place of the separate `isReplay`/`recordUsage` calls, and add a concurrent-goroutine unit test analogous to `TestRequestReplayGuard_ConcurrentAccess` to verify exactly one winner per `jti`.

## Proof of Concept
1. Register a workflow and its authorized signer key (as in `TestWorkflowMetadataHandler_Authorize`).
2. Create one valid `MethodWorkflowExecute` request signed with a JWT (`jti = X`).
3. Launch two goroutines concurrently, each calling `handler.Authorize(workflowID, tokenString, req)` with the identical token.
4. Under the current implementation, both goroutines can observe `isReplay(X) == false` before either calls `recordUsage(X)`, so both return success, whereas the existing test `TestWorkflowMetadataHandler_Authorize/"JWT replay protection"` only verifies correct rejection for strictly sequential (non-concurrent) calls and does not cover this race, leaving the concurrent path unverified and exploitable.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {

		return nil, err

		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())

	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (cache *jwtReplayCache) isReplay(jti string) bool {

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
