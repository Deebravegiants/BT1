### Title
Webhook shop-domain/topic headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from unauthenticated HTTP headers [2](#0-1) . `Utils::HmacValidator.validate` only checks the raw body against the app secret [3](#0-2) , yet `Registry.process` trusts `request.shop` and `request.topic` as authenticated tenant/topic identity when dispatching to the handler [4](#0-3) .

### Finding Description
The binding that should hold is: **shop-domain header == shop bound to the HMAC signature**. In this gem it does not — the equality actually enforced is only `HMAC-SHA256(secret, raw_body) == received_hmac`, with `shop-domain`, `topic`, `webhook-id`, and `api-version` completely excluded from the signed material.

Since the webhook signing secret (`Context.api_secret_key`) is identical for every shop that has the app installed, any merchant who has legitimately installed the app (an "unprivileged" tenant, not a privileged operator of the app) can obtain a validly-signed `(raw_body, hmac)` pair for their own store by triggering any webhook event. That pair can then be POSTed to the app's public webhook endpoint with the `shop-domain` and/or `topic` headers rewritten to any value the attacker chooses (e.g. a victim shop's domain, or a different topic such as `customers/data_request`). `HmacValidator.validate(request)` still succeeds because it only re-derives the HMAC from `raw_body` [5](#0-4) , and `Registry.process` then dispatches the handler with the attacker-controlled `shop` and `topic` values [4](#0-3) .

### Impact Explanation
This breaks the cross-tenant boundary: an app built on this gem receives a cryptographically "valid" webhook that is falsely attributed to a shop the attacker does not control. Depending on how the host app's `WebhookHandler` uses `data.shop` (typically to look up/act on that tenant's session or data — the gem's own docs and `WebhookMetadata` are built specifically to key handler logic off `topic`/`shop`), this enables cross-tenant data injection/corruption, forged mandatory-compliance webhooks (`shop/redact`, `customers/redact`, `customers/data_request`) against a victim shop, or topic confusion (relabeling a benign event as a different, more privileged topic) — all without ever needing the app's secret, an access token, or any credential belonging to the victim. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Reachable by any unprivileged internet user who can install the target app on their own (even free/dev) store — no privileged access, leaked secret, or victim credentials are required. The webhook endpoint is by design internet-facing (it must receive Shopify's callbacks), so replaying a captured, validly-signed body with modified headers is trivial and requires no more than basic HTTP tooling.

### Recommendation
Bind the identity headers into the signed material verified by `HmacValidator`, or otherwise independently authenticate them before trusting them for tenant dispatch:
- Extend `Webhooks::Request#to_signable_string` to include `shop`, `topic`, and `webhook_id` (or otherwise validate that the shop/topic delivered are consistent with a value obtained through an independently-trusted channel, e.g. the webhook subscription id looked up via the Admin API for the session under which the app expects the event), or
- Have `Registry.process` cross-check `request.shop` against an installed/known-shop registry (offline session store) before dispatching, and reject unknown or mismatched shops, and
- Add webhook replay protection (e.g., dedupe by `webhook_id` within a time window) so a captured `(body, hmac)` pair cannot be resubmitted with different headers.

### Proof of Concept
1. Attacker installs the vulnerable app on their own store `attacker.myshopify.com` and lets Shopify deliver any real webhook (e.g. `orders/create`) to the app's endpoint, capturing the raw body `B` and the `X-Shopify-Hmac-Sha256` header `H` (both valid for the shared app secret).
2. Attacker resends the exact same body `B` and header `H` to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` and/or `X-Shopify-Topic: customers/data_request`.
3. `Webhooks::Request.new(raw_body: B, headers: {...spoofed...})` builds successfully [6](#0-5) .
4. `Utils::HmacValidator.validate(request)` recomputes HMAC over `B` only and it matches `H`, so validation passes [7](#0-6) .
5. `Registry.process` looks up the handler for the spoofed topic and invokes it with `shop: "victim.myshopify.com"`, `topic: "customers/data_request"`, and the attacker's body content [8](#0-7)  — a webhook event forged for a tenant the attacker does not control, passing HMAC validation.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
