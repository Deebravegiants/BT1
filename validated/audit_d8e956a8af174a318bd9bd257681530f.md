### Title
Webhook tenant identity (`shop-domain`) is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identifier (`shop`) from the `shop-domain`/`x-shopify-shop-domain` HTTP header, but `Utils::HmacValidator` only authenticates the raw request body, not this header. The `shop` value that `Registry.process` hands to the host app's `WebhookHandler` is therefore never bound to the HMAC signature, breaking the equality `authenticated_bytes == bytes_the_app_acts_on_as_tenant_id`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` and compares it to the supplied `hmac`: [2](#0-1) 

Meanwhile, `shop` is read straight from an attacker-controllable header with no cryptographic binding to the body or the HMAC: [3](#0-2) 

`Webhooks::Registry.process` validates only the HMAC of the body, then passes `request.shop` (the unauthenticated header value) directly into `WebhookMetadata`, which the host app's handler uses to identify which tenant/shop the payload belongs to: [4](#0-3) [5](#0-4) 

Because Shopify computes the webhook HMAC the same way (over body only, using the shared `api_secret_key`), a raw_body + hmac pair that was legitimately generated for one shop (e.g., a merchant who owns Shop B and can observe/capture their own inbound webhook traffic, or intercept it on a non-TLS-terminating hop) remains a **valid, verifiable** pair when replayed with any other `shop-domain` header value, since the header plays no role in `to_signable_string`. `Registry.process` will accept it (`HmacValidator.validate` returns `true`) and dispatch it to the handler tagged with an attacker-chosen `shop`, i.e., `authenticated(shop_actually_signed) != shop_the_handler_believes(shop_header)`.

### Impact Explanation
This is a cross-tenant integrity break at the identity-binding layer this gem is responsible for: a webhook payload cryptographically proven only to have originated "from Shopify for *some* shop" gets attributed to a caller-chosen `shop` value that the app uses as its per-tenant key (session lookup, data isolation, mandatory `shop/redact`/`customers/redact` compliance flows, etc.). Any host app that trusts `WebhookMetadata#shop` for tenant scoping — which is exactly the value this gem hands it — can have data or actions misattributed across shops, matching the "cross-tenant access" impact class.

### Likelihood Explanation
Requires that the caller obtain a valid `raw_body`+`hmac` pair (e.g., from a webhook delivered to their own shop, or a network position that can observe an app's inbound webhook traffic) and can then send arbitrary HTTP requests to the app's public webhook endpoint with a forged `shop-domain` header — no possession of `api_secret_key` is needed, only knowledge of one legitimately-signed body/hmac pair for any shop. This is more constrained than a fully unauthenticated attack but does not require any Shopify-side compromise, matching the analog class of "shop authenticated vs. shop used as the identity key."

### Recommendation
Include the `shop-domain` (and ideally `topic`/`api-version`) header values in the signed payload used for HMAC verification, or otherwise cryptographically bind the tenant identifier to the signature, instead of trusting an unauthenticated header for tenant attribution in `WebhookMetadata`.

### Proof of Concept
Conceptually (illustrating the missing binding, based on `test/webhooks/registry_test.rb` and `hmac_validator_test.rb` patterns):
```ruby
raw_body = "{}"
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# Legitimately captured for "victim-shop.myshopify.com"
headers_victim = {
  "x-shopify-topic" => "customers/redact",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",
}

# Replayed unchanged except for the shop header -- HMAC still validates
headers_attacker = headers_victim.merge("x-shopify-shop-domain" => "attacker-shop.myshopify.com")

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers_attacker)
ShopifyAPI::Utils::HmacValidator.validate(request) # => true, even though shop was swapped
``` [6](#0-5)
