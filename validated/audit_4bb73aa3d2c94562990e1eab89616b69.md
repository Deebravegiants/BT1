### Title
Excess native ETH sent to `EvmHost.dispatch()` / `fundRequest()` is not refunded to the caller and is silently captured by the Host contract - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all forward `msg.value` directly into `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(...)` to buy an exact amount of fee token, but never measure or forward back any leftover native ETH to the original transaction sender. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`swapETHForExactTokens` on a standard UniswapV2 router computes the exact ETH input required for `post.fee`/`get.fee`/`amount` tokens out, performs the swap, and refunds any unspent ETH — but that refund is sent to `msg.sender` of the router call. Since `EvmHost` itself calls the router (`IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(...)`), `msg.sender` from the router's perspective is `EvmHost`, not the original dispatcher of the request (`_msgSender()`). Any ETH sent by a user/app above what the swap actually consumes is refunded back into `EvmHost`'s own balance rather than being sent back to the caller who is entitled to it.

This is the exact same bug class as the referenced report: a downstream call is made with `{value: msg.value}` where the recipient's excess-refund logic returns the residual native token to the *intermediate contract* (the wrapper/host) instead of the true depositor, because the intermediate contract never captures a before/after balance delta of its own and forwards the difference onward.

Docs for this codebase even acknowledge the swap is "Approximate (subject to slippage)" for native payments, meaning callers routinely cannot supply the exact wei amount and are expected to overpay slightly and rely on a refund that never happens here. [4](#0-3) 

Contrast this with every other native-payment path in the same codebase, which correctly measures before/after balances or captures the router's refund and forwards it to the true payer: [5](#0-4) [6](#0-5) 

`EvmHost.dispatch`/`fundRequest`, however, has no such logic — it does not check `address(this).balance` before/after the swap, nor does it forward any leftover value to `_msgSender()`. [1](#0-0) 

### Impact Explanation
Any unprivileged dispatcher — an ordinary app or user calling `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, or `fundRequest` with native ETH — permanently loses any ETH sent in excess of what the Uniswap swap actually consumes. Because callers can only estimate the required native amount off-chain via `quote()` (explicitly documented as approximate/subject to slippage), overpayment is a normal, expected occurrence, not an edge case. The excess ETH accumulates in `EvmHost`, and unless there is a privileged sweep mechanism (which, if present, would only benefit the protocol admin, not the paying user), it constitutes a direct, permanent loss of user/app funds. Given `dispatch`/`fundRequest` are core, high-traffic entry points used by every Hyperbridge app paying fees in native token, this is a systemic loss-of-funds condition on the primary message-dispatch path.

### Likelihood Explanation
High likelihood: this triggers on every native-token-fee dispatch or fund-request call where the caller's supplied `msg.value` doesn't exactly match the swap's consumed amount — which, per the router's slippage-based pricing and the protocol's own documentation, is the expected common case rather than a rare edge case. No malicious actor is required; any normal user following the documented native-payment flow will trigger the loss.

### Recommendation
In `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, snapshot `address(this).balance` (excluding the inbound `msg.value`) before calling `swapETHForExactTokens`, and after the call compute the delta and forward any residual native ETH back to `_msgSender()` (the same pattern already used correctly in `UniV4UniswapV2Wrapper.swapETHForExactTokens` and `IntentGatewayV2`'s fee-swap refund logic).

### Proof of Concept
1. An app calls `EvmHost.dispatch(DispatchPost)` with `msg.value = X` intending to pay `post.fee` in fee-token via the native swap path. [1](#0-0) 
2. `swapETHForExactTokens{value: X}(post.fee, path, address(this), ...)` only consumes `Y < X` ETH (the exact amount needed for `post.fee` tokens); the UniswapV2 router refunds `X - Y` ETH to `msg.sender`, which is `EvmHost`.
3. `EvmHost` never reads its balance delta nor forwards `X - Y` back to the app/user who called `dispatch`.
4. The residual `X - Y` ETH remains stuck in `EvmHost`'s balance, unreachable by the paying app/user, for every dispatch/fundRequest call made with native token overpayment — the same "residual native token left in the intermediary contract instead of returned to the depositor" bug pattern as the referenced H-2 report.
