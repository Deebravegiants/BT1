### Title
Webhook `shop-domain` (and `topic`/`webhook_id`/`api_version`) headers are trusted for tenant identification but are not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw HTTP body only, while the `shop` (and `topic`, `webhook_id`, `api_version`) values used to identify the tenant for a webhook are taken from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` treats a request as fully authenticated once the body HMAC matches, then forwards the header-derived `shop` value to the handler as trusted tenant data — breaking the intended binding `shop-domain header == shop that produced the signed body`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `HmacValidator.validate` computes/compares the HMAC purely over that signable string: [2](#0-1) 

Meanwhile `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read straight from HTTP headers, none of which participate in the signature: [3](#0-2) 

`Registry.process` gates on the HMAC check and then immediately builds `WebhookMetadata` using the unauthenticated `request.shop`, `request.topic`, `request.webhook_id`, `request.api_version`, passing it straight to the app's handler as if it were verified: [4](#0-3) 

The intended identity binding is: `shop-domain header == shop associated with the HMAC-signed body`. Because the signature only covers the body, this binding does not actually hold. An unprivileged internet user who can obtain any one legitimate `(raw_body, hmac)` pair — trivially available to them by installing the app on their own store and receiving one real webhook, since installing an app and registering for its own webhooks requires no privilege over other tenants — can resend that exact body and HMAC to the app's public webhook endpoint while substituting an arbitrary value for `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`). `HmacValidator.validate` will still succeed because it never inspects the headers, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload originated from the spoofed shop/topic.

### Impact Explanation
Any host application that uses `WebhookMetadata#shop` (or `#topic`) returned by this gem to route/attribute incoming webhook data to a specific merchant/tenant record — the intended and documented use per `docs/usage/webhooks.md` — can be made to process a legitimately-signed payload from the attacker's own shop under a victim shop's identity, since the gem asserts the request is verified after only checking the body HMAC. This is a cross-tenant identity confusion: data change/deletion events, or mandatory GDPR topics processed via this metadata (e.g., `shop/redact`, `customers/redact`, `customers/data_request`) can be triggered for a shop the attacker does not own, without ever needing the app's `client_secret`.

### Likelihood Explanation
Exploitation requires only: (1) installing the app on any shop the attacker controls (or reusing a webhook they legitimately received) to obtain one valid `(raw_body, hmac)` pair, and (2) sending an HTTP request to the app's public webhook endpoint with that body/hmac but forged shop/topic headers. No access to the app's `api_secret_key`, access tokens, or the victim's account is required, making this reachable by any unprivileged internet user who can install the target app.

### Recommendation
Do not treat header-derived `shop`, `topic`, `webhook_id`, or `api_version` as authenticated by the body HMAC. Either:
- Include these header values in the signed payload used for HMAC comparison (matching what Shopify actually includes, if anything), or
- Explicitly document that `Registry.process` only authenticates the raw body, and require host applications to independently verify `request.shop` against a shop they have an existing, previously-established session/webhook registration for before trusting it as the tenant identity.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and registers an HTTP webhook (e.g., `orders/create`).
2. Shopify sends the app a legitimately-signed webhook: raw body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for `B`), `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker replays the exact same `(B, H)` to the app's public webhook endpoint but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and/or a different `X-Shopify-Topic`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC solely from `B` and matches `H` — validation succeeds.
5. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` reports `shop: "victim-shop.myshopify.com"` to the handler, even though the payload was never produced by or for that shop.
