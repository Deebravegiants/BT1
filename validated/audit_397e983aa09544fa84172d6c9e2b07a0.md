### Title
Webhook `shop` field is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , while `shop` (from the `X-Shopify-Shop-Domain` header) is read independently and is not part of the signed content [2](#0-1) . `Registry.process` validates the HMAC against the body only, then constructs `WebhookMetadata` using the unverified `request.shop` value and passes it straight to the app's handler [3](#0-2) . This mirrors the report's bug class: a field (`shop`) is acted upon but is not covered by the same authenticator (HMAC) that is used to establish trust in the message, breaking the binding `hmac ⇒ (shop, body)` down to `hmac ⇒ body`.

### Finding Description
Shopify webhook authenticity is verified with a single shared secret — the app's `api_secret_key` — applied identically for every shop that installs the app [4](#0-3) . The signature is computed purely over `verifiable_query.to_signable_string`, which for `Webhooks::Request` is `@raw_body` [1](#0-0)  — the `shop-domain` header is excluded.

Because the same `api_secret_key` is used across all shops using a given app, any user who has legitimately installed the app on their own shop receives real webhook deliveries with a valid `(raw_body, hmac)` pair for their own tenant. Since the shop identity is carried out-of-band in a header that is not bound by that HMAC, this attacker can replay the exact same body+HMAC to the app's webhook endpoint while substituting an arbitrary victim shop's domain in the `shopify-shop-domain` / `x-shopify-shop-domain` header. `HmacValidator.validate` will still pass (`OpenSSL.secure_compare` only checks body-derived signature) [5](#0-4) , and `Registry.process` will hand the forged `shop` value straight to the host app's handler as trusted metadata [3](#0-2) .

The equality that should hold is: `hmac_valid(body) ⇒ (shop, body) authentically originated together`. In reality it only proves: `hmac_valid(body) ⇒ body was signed by some shop using this app`. The `shop` half of the tuple is attacker-controlled.

### Impact Explanation
If a host application uses `WebhookMetadata#shop` (as delivered by this gem) to select which tenant's data/session to act on — a documented and expected usage pattern for multi-tenant Shopify apps — an attacker who is merely a legitimate installer of the app on their own store can forge webhook events attributed to any other shop that also uses the app, since the shop identifier is never bound to the HMAC. This is a cross-tenant integrity/authentication issue: the app trusts the HMAC as a proof of "this event is genuinely from shop X," but the gem's design only proves "this body was HMAC-signed by our shared secret," not which shop it belongs to.

### Likelihood Explanation
Any user of a Shopify app who installs it on their own store obtains valid `(body, hmac)` pairs for arbitrary event types they can trigger themselves (e.g., `orders/create`). Replaying that pair against the app's public webhook endpoint with a modified `shop-domain` header requires no secret knowledge and no privileged access — only knowledge of the app's public webhook URL, which is unprivileged-internet-user reachable.

### Recommendation
Bind the `shop` (and ideally `webhook_id`/`api_version`) into the signable content that is HMAC-validated, or independently verify that `request.shop` matches a shop this specific webhook subscription was registered for (e.g., cross-check against the stored session/shop associated with the subscription id) before dispatching to the handler. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be trusted for tenant selection without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and triggers a real event (e.g., creates an order), receiving a genuine webhook delivery:
   - Headers: `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over body>`
   - Body: `{"id": 123, ...}`
2. Attacker resends the identical body and HMAC header to the app's webhook endpoint, only replacing the header:
   - `x-shopify-shop-domain: victim.myshopify.com`
3. `Webhooks::Request.new` parses this successfully [6](#0-5) ; `Registry.process` calls `HmacValidator.validate(request)`, which passes because it only checks the body against the shared secret [7](#0-6) .
4. `WebhookMetadata.new(topic:, shop: request.shop, ...)` is built with `shop = "victim.myshopify.com"` and dispatched to the app's handler as an authenticated victim-shop event [8](#0-7) , despite originating entirely from the attacker's own tenant data.

        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
