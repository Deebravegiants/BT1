### Title
Webhook HMAC only covers the request body, allowing `shop-domain` header spoofing / cross-tenant webhook injection - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC verified by `Utils::HmacValidator.validate` in `ShopifyAPI::Webhooks::Registry.process` binds only the request body's bytes. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values are read directly from unauthenticated HTTP headers and passed downstream to the app's webhook handler as `WebhookMetadata#shop`, which the app treats as the authenticated tenant identity for the incoming webhook.

### Finding Description
`Request#to_signable_string` is defined as:
```ruby
def to_signable_string
  @raw_body
end
``` [4](#0-3) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all pulled straight from HTTP headers with no HMAC coverage:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [5](#0-4) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant identity handed to the app:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
end
``` [2](#0-1) 

The binding the code implicitly claims to establish is: `shop header == tenant that produced/authorized this HMAC-signed body`. In reality, the equality that actually holds is only: `HMAC(api_secret_key, raw_body) == received_signature`. Because the app's `api_secret_key` is identical for every shop that installs the app, any request bearing a body/HMAC pair that was validly generated for **one** shop remains HMAC-valid regardless of which `shop-domain` header value is attached to it. An unprivileged holder of one legitimately-delivered webhook (e.g., a merchant who installed the app and can observe webhooks sent to their own shop, or anyone who can capture one such delivery) can replay that body+HMAC pair to the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` header (e.g., a victim shop) and the gem will report the webhook as valid, handing the app a `WebhookMetadata` claiming to be from the victim shop.

This directly matches the report's bug class: "a field acted on but not covered by the HMAC" and "a shop authenticated versus the shop stored as a session key" — here the shop identity forwarded to the app is a header value that is never part of the signed material, while the app is documented to rely on the gem to "verify the request did indeed come from Shopify" (`docs/usage/webhooks.md:125`).

### Impact Explanation
This allows cross-tenant data injection: an attacker (any merchant with the app installed, i.e., an unprivileged multi-tenant user of the platform, or anyone who intercepts one webhook delivery) can cause the host application to process attacker-controlled webhook bodies under a victim shop's identity. Depending on how the host app uses `data.shop` (e.g., to look up the shop's session/access token, update shop-scoped records, or trigger shop-scoped side effects), this can lead to cross-tenant data corruption or the app performing actions/queries against the wrong tenant. This satisfies the "cross-tenant access" Critical impact category.

### Likelihood Explanation
The HMAC validation, `topic` dispatch, and `shop` propagation are entirely within this gem's own code (`Utils::HmacValidator`, `Webhooks::Request`, `Webhooks::Registry`), requiring no `api_secret_key`, access token, or privileged access from the attacker — only a single previously-observed valid webhook body+HMAC pair (obtainable by any merchant using the app for their own shop, or via capture of one delivery over the wire before TLS, or from app-side logs) and the ability to POST to the app's public webhook endpoint.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `api-version`, `webhook-id`) header values in the material that is HMAC-verified, or otherwise cryptographically bind them to the signed body before trusting `request.shop` as tenant identity — e.g., compute the signature over a canonical string combining these headers and the raw body, matching the fix pattern described in the report (binding all security-relevant identity fields into the verified hash rather than trusting unauthenticated fields).

### Proof of Concept
1. App has two installed shops: `victim-shop.myshopify.com` and `attacker-shop.myshopify.com`, both under the same app `client_secret`.
2. Attacker triggers/receives a legitimate webhook delivery to their own shop, capturing the raw body `B` and its valid `X-Shopify-Hmac-Sha256` header `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker POSTs to the app's webhook endpoint with:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   - `X-Shopify-Hmac-Sha256: H`
   - `X-Shopify-Topic: <same topic>`
   - body `B`
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed; `Utils::HmacValidator.validate` succeeds because `to_signable_string` returns only `B`, and `H` matches `HMAC(api_secret_key, B)`.
5. `Registry.process` calls the app handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the body/content actually originated from/for the attacker's own shop.
