### Title
Missing validation that decoded backend/self-custody `PublicKey`s are non-degenerate (zero) - ([File: src/backend/user_status.rs])

### Summary
`decode_public_key` in `src/backend/user_status.rs` only validates that a base64-decoded key is exactly 32 bytes; it never checks that the value is not the all-zero (or otherwise degenerate/low-order) Curve25519 point before it is used as a `sodiumoxide` `PublicKey` for `sealedbox::seal` encryption of biometric data. [1](#0-0) 

### Finding Description
`decode_public_key` decodes a base64 string into exactly `[u8; 32]` and wraps it into a `sodiumoxide::crypto::box_::PublicKey` with no further validation: [1](#0-0) 

This function is used to build the `backend_iris_public_key`, `backend_normalized_iris_public_key`, `backend_face_public_key`, `backend_tier2_public_key`, and `self_custody_user_public_key` fields of `UserData` returned from `request()`: [2](#0-1) 

Notably, `self_custody_public_key` originates from `orb_qr_link::UserData`, which is app/user-supplied data whose authenticity is only checked against a QR-embedded hash (`user_data.verify(user_data_hash)`) — i.e., the *value* of the key itself is chosen by the app/user, not by the trusted backend, and is never checked for being the zero point or another low-order Curve25519 point: [3](#0-2) 

These decoded public keys are subsequently used directly as recipients for `sodiumoxide::crypto::sealedbox::seal`, which encrypts sensitive biometric artifacts (iris/face images, normalized iris data) for "self-custody" and backend delivery in the Personal Custody Package (PCP) build pipeline: [4](#0-3) 

X25519/Curve25519 has a small number of known low-order points (including the all-zero point) for which the Diffie-Hellman shared secret is a fixed, publicly known value **regardless of the other party's private key**. If a zero (or other degenerate) public key reaches `sealedbox::seal`, the resulting ciphertext's shared secret is predictable/known, defeating the confidentiality guarantee of the sealed box — analogous to the "zero address" input-validation defect class flagged in the external report (unchecked degenerate/zero input parameter accepted and used in a security-critical operation).

### Impact Explanation
If a crafted or malfunctioning app supplies a degenerate `self_custody_public_key` (e.g., all-zero bytes) that still passes the 32-byte length check and QR hash verification (since the app itself computes the hash over its own chosen key), the orb will proceed to encrypt the user's iris/face biometric package to that key via `sealedbox::seal`. Because the shared secret for such degenerate points is fixed and computable without the private key, any party capturing the encrypted PCP tier data could decrypt the user's biometric images — a direct biometric data disclosure impact, tied specifically to the trust boundary between the orb and the signing/self-custody app during signup.

### Likelihood Explanation
Exploitation requires the party supplying the QR-embedded `self_custody_public_key` (the app side) to submit a degenerate key value; this is plausible for a malicious or compromised client app performing an unprivileged-user signup flow, without needing to compromise the orb, the backend, or any operator/hardware trust boundary. The likelihood is moderate: it depends on an attacker controlling the signup-app-side QR payload, which is within the "unprivileged signup/identity binding" trust boundary explicitly in scope.

### Recommendation
In `decode_public_key` (`src/backend/user_status.rs`), after successful length validation, reject keys that are the all-zero point or otherwise known low-order Curve25519 points before constructing the `PublicKey`. At minimum, add an explicit check `if bytes == [0u8; 32] { return Err(...) }`, and consider validating against the full list of known low-order X25519 points before use in `sealedbox::seal`.

### Proof of Concept
1. A malicious/compromised signup app generates a QR payload whose `authenticated_app_data.self_custody_public_key` is base64-encoded `[0u8; 32]` and computes `user_data_hash` over this same payload (so `verify()` succeeds).
2. Orb-core scans this QR code, calls `backend::user_status::request`, which decodes and accepts the zero key via `decode_public_key` (no zero-check), storing it as `self_custody_user_public_key`.
3. During `build_pcp`, this key is used with `sealedbox::seal` to encrypt biometric package tiers.
4. Because the DH shared secret for the zero/low-order point is a fixed, publicly derivable value, any observer of the resulting ciphertext (e.g., during data upload) can decrypt the sealed box without possessing any legitimate private key, disclosing biometric data.

Note: I could not fully trace, within the available index, whether any downstream check elsewhere in the biometric-pipeline/upload path independently rejects degenerate public keys before `sealedbox::seal` is invoked — this could not be conclusively ruled out or confirmed from the visible code, and would benefit from a full-repository review (e.g., via a Devin session) to verify there is no compensating validation in the `personal_custody_package::Credentials` construction path.

fn decode_public_key(payload: &str) -> Result<PublicKey> {
    let bytes = BASE64.decode(payload.as_bytes())?;
    let bytes = <[u8; 32]>::try_from(bytes)
        .map_err(|x| eyre!("incompatible public key length: {}", x.len()))?;
    Ok(PublicKey(bytes))
}
