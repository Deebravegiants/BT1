## Analysis

The Morpho bug's core custody invariant is: **authorization/accounting state can silently become stale relative to the real underlying state, and that staleness can be weaponized by bundling state-changing transactions** (there, `lostAssets` lagging behind an actual near-total loss; a liquidator exploits the lag to make depositors believe a vault is healthy). Reducing this to Aptos-native terms: *"a piece of state that is supposed to represent current, freshly-granted authority over custody must not silently persist and be reactivated after the underlying grant was revoked."*

I traced this into Aptos's `multisig_account` module, which is Aptos's canonical mechanism for shared custody of resource accounts (and, through them, APT, fungible assets, and code-object upgrade authority).

### The stale-vote resurrection bug

- Votes on a pending `MultisigTransaction` are stored in a `SimpleMap<address, bool>` keyed by owner address, set by `vote_transanction`: [1](#0-0) 
- Removing an owner (`remove_owners` → `update_owner_schema`) only mutates the `owners` vector of `MultisigAccount`; it never touches the `votes` map of any pending `MultisigTransaction`: [2](#0-1) 
- Approval/rejection counts are recomputed dynamically by iterating the *current* owners list and checking whether that address key exists in the transaction's `votes` map: [3](#0-2) 

This dynamic recomputation is what makes `test_validate_transaction_should_not_consider_removed_owners` pass — a removed owner's stale approval stops counting *while they're out*: [4](#0-3) 

However, the vote entry is never purged from the `votes` map. If that same address is later swapped back in via `swap_owner`/`swap_owners`/`add_owners` (a common operational action — e.g., "clear" a suspected-compromised owner and later reinstate them, or churn owners for other reasons) while the original transaction is *still pending* (not yet executed or evicted), `num_approvals_and_rejections_internal` will silently count their old, pre-revocation vote again — without that owner ever re-approving the transaction after being reinstated. This can push a stale/potentially malicious transaction over the `num_signatures_required` threshold based on an authorization grant that was supposed to have been revoked when the owner was removed.

Because the multisig account is itself a resource account that can hold `AptosCoin`/fungible-asset stores or control code-object upgrade authority, execution of such a resurrected transaction is a direct custody violation: unprivileged/former-owner-derived approval state is leaking transfer or upgrade authority.

### Title
Stale multisig transaction votes are silently resurrected when a removed owner is re-added, enabling unauthorized execution of custody-controlling transactions - (File: aptos-move/framework/aptos-framework/sources/multisig_account.move)

### Summary
`multisig_account`'s per-transaction `votes: SimpleMap<address, bool>` is never cleared when an owner is removed via `remove_owners`/`swap_owner`/`update_owner_schema`. Approval counts are recomputed by scanning the *current* owner list against this map, so a compromised or since-revoked owner's original approval automatically reactivates the moment that same address is re-added as an owner, without any new act of approval. This lets a stale (and possibly malicious) pending transaction reach quorum and execute against the multisig's resource-account-controlled assets/authority.

### Finding Description
`vote_transanction` records votes keyed only by owner address in the transaction's `votes` map [5](#0-4) . `update_owner_schema`, used by `remove_owners`/`swap_owner`/`swap_owners`/`add_owners`, only edits `MultisigAccount.owners`; it performs no cleanup of any `MultisigTransaction.votes` map for pending transactions [6](#0-5) . Quorum is computed on demand by `num_approvals_and_rejections_internal`, which iterates the live `owners` vector and checks map membership [3](#0-2) . There is no "owner epoch"/generation concept attached to a vote, so a vote cast under a past owner-set membership is indistinguishable from a vote cast under the current one. Consequently, removing then re-adding the same address (a normal remediation/rotation operation) silently restores that address's old approval on every transaction still pending at the time of removal.

### Impact Explanation
Multisig accounts are resource accounts and are the standard Aptos custody primitive for shared control over APT, fungible assets, and code-object/package upgrade authority. If a transaction proposing a fund transfer or upgrade was approved by an owner who is later found compromised and removed, remaining owners may reasonably assume that transaction's approval count has been invalidated (as the module's own test explicitly asserts `!can_be_executed(...)` right after removal). But if that owner's address is ever reinstated for any reason before the stale transaction is evicted/rejected, the old approval resurfaces without a new signature, potentially reaching `num_signatures_required` and executing the transaction — moving custody-held assets or altering control (owner list, upgrade authority) to an unintended holder. This is a direct violation of the "multisig-owned assets/resource accounts must not leak transfer or upgrade authority to unprivileged/former callers" custody invariant.

### Likelihood Explanation
Requires: (1) a malicious/compromised owner creates or approves a transaction, (2) that owner is removed while the transaction remains pending, (3) the same address is later re-added as an owner before the transaction is executed or explicitly evicted/rejected. Owner rotation and "innocent until further review" reinstatement are realistic operational patterns for multisig treasuries, and the pending-transaction queue can persist (subject to `MAX_PENDING_TRANSACTIONS`) across such rotations, making this a plausible, non-contrived scenario rather than a purely theoretical edge case.

### Recommendation
Invalidate an owner's votes across all pending transactions when that owner is removed (e.g., iterate pending transactions and remove the entry for the removed address in `update_owner_schema`), or bind each vote to an owner-set version/epoch counter incremented on every owner-list change, so that `num_approvals_and_rejections_internal` only counts votes cast under the current epoch.

### Proof of Concept
Extending the existing test harness pattern from `test_validate_transaction_should_not_consider_removed_owners` [4](#0-3) :
```move
// 2-of-3 multisig: owner_1, owner_2, owner_3
create_with_owners(owner_1, vector[owner_2_addr, owner_3_addr], 2, vector[], vector[]);

// owner_1 creates tx (auto-approves), owner_2 approves -> 2 approvals, executable
create_transaction(owner_1, multisig_account, PAYLOAD);
approve_transaction(owner_2, multisig_account, 1);
assert!(can_be_executed(multisig_account, 1), 0);

// owner_1 is suspected compromised and removed -> approvals drop below threshold
let multisig_signer = &create_signer(multisig_account);
remove_owners(multisig_signer, vector[owner_1_addr]);
assert!(!can_be_executed(multisig_account, 1), 1);

// owner_1 is later cleared/reinstated (routine ops action, unaware of stale vote)
add_owners(multisig_signer, vector[owner_1_addr]);

// owner_1's original stale approval silently counts again -> tx executable
// WITHOUT owner_1 ever re-approving after reinstatement
assert!(can_be_executed(multisig_account, 1), 2);
```
This demonstrates that `num_approvals_and_rejections_internal`/`can_be_executed` resurrect a previously-invalidated approval solely because the address reappears in the owner list, letting a stale transaction (which may transfer custody-held assets or change control) reach quorum without fresh consent.

    inline fun num_approvals_and_rejections_internal(owners: &vector<address>, transaction: &MultisigTransaction): (u64, u64) {
        let num_approvals = 0;
        let num_rejections = 0;

        let votes = &transaction.votes;
        owners.for_each_ref(|owner| {
            if (simple_map::contains_key(votes, owner)) {
                if (*simple_map::borrow(votes, owner)) {
                    num_approvals += 1;
                } else {
                    num_rejections += 1;
                };
            }
        });

        (num_approvals, num_rejections)
    }

    /// Add new owners, remove owners to remove, update signatures required.
    fun update_owner_schema(
        multisig_address: address,
        new_owners: vector<address>,
        owners_to_remove: vector<address>,
        optional_new_num_signatures_required: Option<u64>,
    ) {
        assert_multisig_account_exists(multisig_address);
        let multisig_account_ref_mut =
            borrow_global_mut<MultisigAccount>(multisig_address);
        // Verify no overlap between new owners and owners to remove.
        new_owners.for_each_ref(|new_owner_ref| {
            assert!(
                !vector::contains(&owners_to_remove, new_owner_ref),
                error::invalid_argument(EOWNERS_TO_REMOVE_NEW_OWNERS_OVERLAP)
            )
        });
        // If new owners provided, try to add them and emit an event.
        if (new_owners.length() > 0) {
            multisig_account_ref_mut.owners.append(new_owners);
            validate_owners(
                &multisig_account_ref_mut.owners,
                multisig_address
            );
            emit(AddOwners { multisig_account: multisig_address, owners_added: new_owners });
        };
        // If owners to remove provided, try to remove them.
        if (owners_to_remove.length() > 0) {
            let owners_ref_mut = &mut multisig_account_ref_mut.owners;
            let owners_removed = vector[];
            owners_to_remove.for_each_ref(|owner_to_remove_ref| {
                let (found, index) =
                    vector::index_of(owners_ref_mut, owner_to_remove_ref);
                if (found) {
                    vector::push_back(
                        &mut owners_removed,
                        vector::swap_remove(owners_ref_mut, index)
                    );
                }
            });
            // Only emit event if owner(s) actually removed.
            if (owners_removed.length() > 0) {
                emit(
                    RemoveOwners { multisig_account: multisig_address, owners_removed }
                );
            }
        };
