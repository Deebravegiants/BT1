### Title
TIMELOCK_SENSITIVE_MIN_DELAY_LEDGERS is set to 12 instead of 120_960, letting any address execute sensitive-tier operations ~1 minute after proposal instead of after the intended 7-day delay - (File: contracts/governance/src/constants.rs)

### Summary
The governance timelock assigns every `AdminOperation` to a delay tier in `resolve_op`, and `operation_delay` raises the configured `min_delay` to a per-tier floor for `Sensitive` and `Recovery` operations [1](#0-0) . The sensitive-tier floor constant is `TIMELOCK_SENSITIVE_MIN_DELAY_LEDGERS: u32 = 12`, with an in-code comment stating the target is `120_960` (about 7 days) and that the current value is an "audit-period value" [2](#0-1) . This is the same bug class as `LOCK_DURATION = 0` in the reference report: a delay constant mis-set so low that the intended restriction is effectively absent.

### Finding Description
Sensitive-tier operations include `UpgradeGov`, `UpgradeController`, `UpgradePool`, `UpgradePositionNft`, `UpgradePriceAggregator`, `TransferGovOwnership`, `TransferCtrlOwnership`, `GrantGovRole`, `RevokeGovRole`, `SetPriceAggregator`, `SetSwapAggregator`, `SetPositionManager`, and `ForceSocializeBadDebt` [3](#0-2) . When such an op is proposed, `propose` computes `delay = operation_delay(env, DelayTier::Sensitive) = min_delay.max(12)` and calls `schedule_operation` [4](#0-3) . On a deployment whose `min_delay` is below 12 (permitted — the constructor only rejects zero [5](#0-4) ), a sensitive op becomes `Ready` after 12 ledgers (~60 seconds at ~5s/ledger) instead of the documented 7-day floor. Once ready, `execute`/`execute_self` with `executor: None` performs no auth or role check — "anyone may drive execution of a ready op" [6](#0-5)  — so a completely unprivileged address can trigger the scheduled upgrade, ownership transfer, role grant, aggregator swap-in, or forced bad-debt socialization almost immediately.

### Impact Explanation
The 7-day sensitive floor exists so guardians/cancellers and users have a review window before high-risk changes (contract upgrades, ownership transfers, role grants, swapping the price-aggregator/swap-aggregator addresses, `force_socialize_bad_debt`). With the floor at 12 ledgers that window collapses to about a minute: a scheduled sensitive operation can be permissionlessly executed before any canceller can react, and the epoch-check/`cancel` protections are useless if execution lands in the same minute as the proposal. Depending on the scheduled op, this enables theft or freezing of user funds (e.g., a controller upgrade or `set_swap_aggregator` executed before review), matching the "operator bypasses an intended restriction" impact of the reference issue.

### Likelihood Explanation
Triggering requires a sensitive op to be proposed while `min_delay < 12` (or relies on the floor itself being the only protection). Proposal needs `PROPOSER_ROLE` (and owner for the most dangerous variants), so likelihood depends on privileged scheduling; however the bypassed delay floor and the permissionless `execute` path mean no further privilege is needed to land the op the moment it is scheduled. The constant is hardcoded, so the weakness exists on every deployment until a governance `UpgradeGov` fixes it.

### Recommendation
Set `TIMELOCK_SENSITIVE_MIN_DELAY_LEDGERS` to its documented target `120_960` before deployment, and add a deploy-time assertion (e.g., in `__constructor` or via `require_nonzero_delay`-style validation) that the sensitive floor meets the intended minimum so a future constant regression cannot silently weaken the tier.

### Proof of Concept
Mirror of the existing test `sensitive_operations_are_not_ready_at_a_min_delay_below_the_floor` (tests/test-harness/tests/governance/stale_edit_and_sensitive_floor.rs:333), which already demonstrates the flaw:

1. Deploy `Governance` with `min_delay = 3` (`LOW_MIN_DELAY`), which the constructor accepts.
2. `propose(AdminOperation::TransferCtrlOwnership{...})` (or `GrantGovRole`, `SetSwapAggregator`, `ForceSocializeBadDebt`) — `get_operation_ledger(id)` returns `proposed_at + 12` (the test asserts `SENSITIVE_FLOOR`, i.e., 12).
3. Advance the ledger by 12 and call `execute(None, target, function, args, predecessor, salt)` as an arbitrary unprivileged address — `authorize_executor` performs no check for `executor: None` — and the sensitive operation executes ~1 minute after proposal instead of after the intended 7-day delay.

pub(crate) fn operation_delay(env: &Env, tier: DelayTier) -> u32 {
    let min = get_min_delay(env);
    match tier {
        DelayTier::Standard => min,
        DelayTier::Sensitive => min.max(constants::TIMELOCK_SENSITIVE_MIN_DELAY_LEDGERS),
        DelayTier::Recovery => min.max(constants::TIMELOCK_RECOVERY_MIN_DELAY_LEDGERS),
    }
}
