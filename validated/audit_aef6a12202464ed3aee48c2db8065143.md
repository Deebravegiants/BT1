### Title
Batch withdrawals of the same assetId cause `findMatchingWithdrawal` to report the wrong (status, txHash) for one of the withdrawal indices - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal` resolves a withdrawal's on-chain outcome purely by matching `assetId` against the POA bridge's status-list response, ignoring `WithdrawalIdentifier.index`. When a single NEAR transaction contains two withdrawals of the same token (a supported batch-withdrawal pattern), both `describeWithdrawal({index:0,...})` and `describeWithdrawal({index:1,...})` resolve to the same array element via `Array.prototype.find`, so both indices report identical `(status, txHash)` even though the POA API returned two distinct entries corresponding to two different on-chain transfers.

### Finding Description
The equality that must hold is: for withdrawal `i` in a batch, `describeWithdrawal({index:i,...})` must report the `(status, txHash)` of the on-chain execution of withdrawal `i`. The code breaks this because `findMatchingWithdrawal` never looks at `index`: [1](#0-0) [2](#0-1) 

The `NOTE` comment on `findMatchingWithdrawal` explicitly acknowledges: *"Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported."* Because `withdrawals.find(...)` always returns the first array element whose `near_token_id` matches, calling `describeWithdrawal` twice with `index: 0` and `index: 1` (but the same `assetId`) both resolve to `response.withdrawals[0]`, regardless of which physical withdrawal is being queried, since the response array order is unspecified by the API and there is no per-entry correlation (e.g., amount, per-withdrawal sub-index) used to disambiguate.

An unprivileged NEAR Intents user (or a counterparty whose withdrawal params an integrator forwards) triggers this simply by submitting a NEAR intents transaction with two withdrawal instructions for the same `assetId` (e.g., a batch of "send 100 USDC to A" + "refund 5 USDC to B" both denominated as `nep141:usdc...near`). This is exactly the batch-withdrawal capability the SDK documents and builds tooling around (see `docs/design/rfc-batch-withdrawal-granular-control.md` and `createWithdrawalIdentifiers`/`watchWithdrawal` in `withdrawal-watcher.ts`, which call `describeWithdrawal` once per index): [3](#0-2) [4](#0-3) 

No existing guard prevents this: `supports()`, `validateWithdrawal`, `compareAddresses`, and `assert` sanity checks all operate on a single withdrawal's parameters and never enforce distinctness of `assetId` across a batch, nor validate that per-index status responses are actually distinct. The intents contract's own signature/nonce verification is unrelated — it verifies the batch was authorized, not that the SDK correctly reports per-item outcomes afterward.

### Impact Explanation
Two different on-chain withdrawal executions (potentially to different `destinationAddress`/amounts, since only `assetId` need match) collapse into a single reported `(status, txHash)` for both indices. An integrator using `watchWithdrawal`/`createWithdrawalCompletionPromises` per-index (the documented pattern in the RFC) will see the same `txHash` for both withdrawal 0 and withdrawal 1, risking crediting/refunding the same destination transaction twice for two logically separate withdrawals, or silently missing the real status/hash of the second withdrawal. This matches the High severity category: "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
Preconditions: the attacker (any ordinary NEAR Intents user) must submit a single NEAR transaction with ≥2 withdrawal intents sharing the same `assetId` routed through the POA bridge — a supported, permissionless action requiring no special privilege, just their own funds/keys. This is entirely attacker-controlled and repeatable on every batch withdrawal of same-token entries; no dependency on relayer/RPC misbehavior.

### Recommendation
Extend `findMatchingWithdrawal` to disambiguate entries with the same `assetId` by an additional stable correlator (e.g., amount plus deterministic sort, or a per-withdrawal identifier from the POA API if available), and until the POA API supports index-aware lookup, either: (a) throw/flag a "not supported" error when a batch contains duplicate `assetId`s so callers don't get silently wrong results, or (b) sort both the local per-index withdrawal params and the API response deterministically (e.g., by amount, as the code's own comment suggests) and match by relative order.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
