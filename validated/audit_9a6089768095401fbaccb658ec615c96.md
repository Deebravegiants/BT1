Audit Report

## Title
Gateway CORS wildcard allowlist bypass via missing subdomain boundary check - ([File: core/services/gateway/network/httpserver.go])

## Summary
`httpServer.isAllowedOrigin` implements wildcard CORS matching (`*.example.com`) using `strings.HasSuffix(originHost, allowedHost)` after stripping the `*.` prefix, without requiring a `.` boundary immediately before the match. This allows an attacker-controlled `Origin` header like `evilexample.com` to be incorrectly treated as a subdomain of an allowlisted `*.example.com` entry.

## Finding Description
The vulnerable logic strips the `*.` prefix from the allowlist entry and does a raw suffix comparison: [1](#0-0)  Because `allowedHost[2:]` becomes `"example.com"` and `strings.HasSuffix` has no boundary check, any origin ending in the literal characters `example.com` — including `evilexample.com`, `notexample.com`, or an attacker-registered `attacker-example.com` — is accepted, even though these are not subdomains of `example.com`. This is reachable directly from `handleRequest`, which reads the client-supplied `Origin` header on every incoming gateway request with no other validation or trusted intermediary: [2](#0-1)  When the check passes, the attacker's exact `Origin` value is reflected into `Access-Control-Allow-Origin`, enabling a browser on the attacker's domain to make authenticated cross-origin requests against the gateway API that CORS was meant to restrict to the operator's trusted domain family. The existing test suite (`core/services/gateway/network/httpserver_test.go`) only verifies non-matching-suffix rejection (e.g., `ethereum.remix.org` vs `*.ethereum.org`) and does not cover the suffix-without-boundary case (e.g., `evilethereum.org` vs `*.ethereum.org`), confirming the gap is untested and unmitigated.

## Impact Explanation
This is a concrete CORS allowlist bypass (CWE-183/CWE-193 boundary error) falling into the "allowlist bypass" impact category. It allows a fully unprivileged web attacker who registers a domain sharing the allowlisted suffix to have their origin reflected in `Access-Control-Allow-Origin`, enabling cross-origin browser requests against the gateway's user-facing HTTP API that the operator intended to restrict to genuine subdomains of a trusted domain.

## Likelihood Explanation
Exploitation requires only that an operator use the documented wildcard CORS pattern (`*.example.com`) — a supported configuration shown in `core/scripts/gateway/sample_config.toml` — and that an attacker registers or controls any domain ending in the same suffix (trivial and low-cost, e.g., `evil-example.com`). No credentials, insider access, or victim-side vulnerability are needed; the flawed check runs on every request's `Origin` header.

## Recommendation
Require a subdomain boundary when matching the wildcard suffix, e.g., compare against `"."+allowedHost` (or verify the character preceding the suffix match is a `.`), so that `originHost` must equal the base domain or end with `.example.com` exactly, not merely share trailing characters.

## Proof of Concept
1. Start the gateway HTTP server with `CORSEnabled: true` and `CORSAllowedOrigins: []string{"https://*.example.com"}` (as done in `startNewServer` in `core/services/gateway/network/httpserver_test.go`).
2. Send a POST request to the gateway path with header `Origin: https://evilexample.com`.
3. Observe the response includes `Access-Control-Allow-Origin: https://evilexample.com`, confirming `isAllowedOrigin` incorrectly returned `true` via `strings.HasSuffix("evilexample.com", "example.com")`, matching the pattern of the existing `TestHTTPServer_HandleRequest_CORSEnabled_FromAllowedOriginWildcards` test but with a non-subdomain attacker origin.

func (s *httpServer) handleRequest(w http.ResponseWriter, r *http.Request) {
	if s.config.CORSEnabled {
		origin := r.Header.Get("Origin")
		if s.isAllowedOrigin(origin) {
			w.Header().Set("Access-Control-Allow-Origin", origin)
			w.Header().Set("Access-Control-Allow-Methods", "GET, POST, OPTIONS")
