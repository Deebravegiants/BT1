## Title
Webhook shop/topic identity not bound to HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used by the registry/handler dispatch are read straight from unauthenticated HTTP headers. This breaks the identity binding `shop authenticated == shop acted upon`, letting a merchant who legitimately triggers one webhook for their own shop replay that valid body+signature pair while forging the shop-domain header to impersonate a different tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0)  and `HmacValidator.validate` / `validate_signature` verify exactly that string against the computed HMAC: [2](#0-1) . Meanwhile `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are parsed directly from HTTP headers with no cryptographic tie to the verified bytes: [3](#0-2) .

`Registry.process` verifies only the body HMAC and then dispatches the handler using the unauthenticated `request.shop` and `request.topic`: [4](#0-3) .

The result is: bytes verified (raw body) != bytes/fields acted upon (shop, topic, webhook_id, api_version headers). Any party who can obtain one validly-signed webhook body (e.g., by installing the app on their own shop and triggering a webhook) can resend that exact body+HMAC to the app's public webhook endpoint with an arbitrary `shopify-shop-domain` header (and arbitrary `shopify-topic`), and `Registry.process` will accept it as authentic and hand `WebhookMetadata` with the forged `shop` value to the app's handler.

### Impact Explanation
This lets an unprivileged (but app-installed) attacker who owns a valid signed body forge which tenant a webhook payload is attributed to, since the shop identity used for dispatch is not part of the signed payload. Host applications that use `request.shop` (per this gem's documented API) to select which merchant's record to update would apply the attacker's payload to the impersonated victim shop, resulting in cross-tenant data corruption/access — this maps to the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Requires the attacker to be able to obtain at least one genuinely signed webhook body (trivial for any merchant who installs the app on their own store and triggers any webhook topic) and to submit an HTTP request directly to the app's public webhook endpoint with a modified `shopify-shop-domain`/`shopify-topic` header pair reusing the captured body and its unchanged HMAC. No access token, `client_secret`, or privileged credential is required — only crafting an HTTP request, which is squarely reachable by an unprivileged internet user.

### Recommendation
Bind the `shop`, `topic`, and `webhook_id` values into the material verified by the HMAC (or otherwise cryptographically tie them to the signed body), or explicitly document that `request.shop`/`request.topic` are unauthenticated header values that host applications must not trust for tenant identification without additional verification (e.g., cross-checking against a known/registered shop for that webhook_id).

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook, capturing the real request: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` with the app's `api_secret_key`), `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`.
2. Attacker sends a new POST directly to the app's public webhook endpoint with the same body `B` and same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H`: [5](#0-4) .
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body `B`, even though `victim-shop` never sent this webhook.
