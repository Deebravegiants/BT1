## Finding [1](#0-0) 

### Title
Unbounded `handle_unsigned` message batch charged a fixed static weight enables free block-production slowdown - (File: modules/pallets/ismp/src/lib.rs)

### Summary
`pallet_ismp::Call::handle_unsigned` accepts an unbounded `Vec<Message>` and is billed at a single hard-coded `Weight::from_parts(300_000_000, 0)` regardless of how many messages, consensus proofs, or state proofs the batch contains. Since this is an unsigned, fee-free extrinsic, anyone can submit a batch whose real verification cost vastly exceeds the weight the runtime accounts for it, letting them occupy disproportionate block-authoring and validation time for free — the same "malicious message causes computation the metering doesn't reflect, slowing block production" class as CWA-2025-002/wasmvm.

### Finding Description
`handle_unsigned` is declared as:
```rust
#[pallet::weight(weight())]
#[pallet::call_index(0)]
#[frame_support::transactional]
pub fn handle_unsigned(
    origin: OriginFor<T>,
    messages: Vec<Message>,
) -> DispatchResultWithPostInfo {
    ensure_none(origin)?;
    Self::execute(messages.clone())?;
    Ok(().into())
}
``` [2](#0-1) 

with:
```rust
fn weight() -> Weight {
    Weight::from_parts(300_000_000, 0)
}
``` [3](#0-2) 

`messages` is a plain `Vec<Message>` with no `BoundedVec` cap and no per-item/size-scaled weight component, while the comment above the function explicitly states "Static weights because these should get overridden by the FeeHandler" — but `FeeHandler::on_executed` only affects *fee* accounting (`actual_weight`/`pays_fee` for the transaction-payment pallet), not the pre-dispatch `#[pallet::weight]` figure Substrate's block-authoring/`CheckWeight` logic uses to decide how many extrinsics fit in a block and how much execution time an extrinsic is allowed to consume.

Each `Message` in the batch can carry an arbitrarily expensive consensus or state proof — BEEFY/SP1 Groth16 verification, GRANDPA fraud-proof ancestry walks, sync-committee BLS aggregate verification, Pharos SPV trie walks, or Patricia/Merkle state proofs with many keys — all of which are real, non-trivial CPU costs that scale with the number of messages and proof size, yet are metered as a single flat 300M weight unit regardless of batch contents. `Self::execute` iterates and fully verifies every message via `handle_incoming_message`. [4](#0-3) 

Compounding this, `ValidateUnsigned::validate_unsigned` for the same call *also* runs the full `Self::execute(messages.clone())` during transaction-pool validation, before the extrinsic is even included in a block:
```rust
fn validate_unsigned(_source: TransactionSource, call: &Self::Call) -> TransactionValidity {
    ...
    let messages = match call {
        Call::handle_unsigned { messages } => messages,
        ...
    };
    let events = Self::execute(messages.clone()).map_err(|_| InvalidTransaction::BadProof)?;
    ...
}
``` [5](#0-4) 

So the expensive verification work is performed twice per submission — once for free in every node's mempool validation, and again at block-execution/dispatch time — with the runtime's weight accounting believing the whole operation cost a fixed, small amount of time. This directly mirrors the wasmvm CWA-2025-002 pattern: a permissionless message crafted by an attacker (no special privilege required — `ensure_none(origin)` just requires an unsigned transaction) causes real computation that the metering system fails to reflect, letting the attacker consume disproportionate block-production and network-wide validation time cheaply and repeatably.

### Impact Explanation
Because `handle_unsigned` messages are unsigned and fee-free by design (documented as: "all cross-chain messages received are executed for free as unsigned transactions"), an attacker pays nothing to submit a batch of many messages each carrying maximal-cost, cryptographically valid proofs (e.g., dozens of BEEFY/GRANDPA/sync-committee consensus updates or large state-proof request/response batches). The fixed 300M weight means the runtime's block-weight limit does not throttle in proportion to actual CPU/verification cost, so a single extrinsic (or a burst of them) can consume block-authoring time and mempool-validation time across every collator/validator far beyond what the weight system permits for other extrinsics, degrading block production throughput network-wide — a Medium-severity availability/DoS impact consistent with the referenced advisory's classification.

### Likelihood Explanation
High likelihood of feasibility: the attack requires no special privilege, no signature, and no fee (`ensure_none(origin)`), just crafting a batch of otherwise-valid ISMP messages/proofs (e.g., replaying real consensus proofs, or legitimate but maximally-sized request/response batches with large state proofs) inside one `Vec<Message>` payload and submitting it as an unsigned transaction. The only friction is the extrinsic byte-size limit of the chain (`BlockLength`), not a computational weight limit, so an attacker is bounded only by how much serialized proof data fits in a block, not by how much CPU time it costs to verify — which for consensus/state proofs can be substantially higher per byte than ordinary extrinsics.

### Recommendation
Scale `handle_unsigned`'s declared weight by the actual number and type of messages in the batch (e.g., a per-message-type weight function similar to `add_state_machines(n)`/`remove_state_machines(n)` in `modules/ismp/clients/grandpa/src/weights.rs`), and/or bound `messages: Vec<Message>` with a `BoundedVec<Message, MaxMessagesPerBatch>` so batch size and thus worst-case proof-verification cost cannot grow unbounded. Ensure the weight figure used for block-inclusion accounting (not just the `FeeHandler`-computed `actual_weight`) reflects the true worst-case cost of consensus/state proof verification for the message mix supplied, and consider making `validate_unsigned`'s dry-run cheaper than a full `execute` (or capping how much validation work per unsigned tx the pool performs) to avoid double-paying the same unmetered cost.

### Proof of Concept
1. Construct a `Vec<Message>` containing N `Message::Consensus`/`Message::Request` entries, each with a real, individually-valid but computationally heavy consensus/state proof (e.g., large BEEFY MMR + parachain header batches, or GRANDPA fraud-proof-sized ancestry chains, or many Get-response storage-proof keys).
2. Submit as `pallet_ismp::Call::handle_unsigned { messages }` via an unsigned transaction; `ensure_none(origin)` accepts it with no fee.
3. Observe `validate_unsigned` executes `Self::execute(messages.clone())`, fully verifying every proof in the mempool-validation path, then the same full verification repeats in the dispatched `handle_unsigned` — all charged the fixed `Weight::from_parts(300_000_000, 0)` — while wall-clock verification time scales with N and proof complexity, independent of the declared weight, letting the batch occupy disproportionate block-production time relative to what the runtime's weight limit accounts for.

impl<T: Config> Pallet<T> {
	/// Execute the provided ISMP datagrams, this will short circuit if any messages are invalid.
	/// This also charges fee on valid message delivery
	pub fn execute(messages: Vec<Message>) -> Result<Vec<events::Event>, Error<T>> {
		let host = Pallet::<T>::default();

		let message_results = messages
			.iter()
			.map(|msg| handle_incoming_message(&host, msg.clone()))
			.collect::<Result<Vec<_>, _>>()
			.map_err(|err| {
				log::debug!(target: "ismp", "Handling Error {:#?}", err);
				Pallet::<T>::deposit_event(Event::<T>::Errors { errors: vec![err.into()] });
				Error::<T>::InvalidMessage
			})?;
```
