## Analog Found

Raydium's classic AMM v4 program exhibits the same missing-mandatory-slippage-check pattern described in the referenced Olympus finding: the withdrawal path allows the caller to submit a transaction **without any minimum-output protection at all**, leaving LPs exposed to price manipulation/sandwiching between transaction submission and execution.

### Title
Optional (skippable) minimum-output enforcement in `process_withdraw` exposes LPs to slippage/sandwich attacks - (File: `program/src/processor.rs`)

### Summary
`WithdrawInstruction` carries `min_coin_amount: Option<u64>` and `min_pc_amount: Option<u64>` [1](#0-0) . The instruction unpacker only populates these fields when the caller supplies 16 extra bytes; otherwise both are silently set to `None` [2](#0-1) . In `process_withdraw`, the slippage check is only performed when `withdraw.min_coin_amount.is_some() && withdraw.min_pc_amount.is_some()` — meaning an all-or-nothing, entirely optional guard [3](#0-2) . The CLI even demonstrates this "no slippage limit" mode explicitly via `slippage_limit: false` [4](#0-3) .

### Finding Description
When a user withdraws LP tokens, `coin_amount`/`pc_amount` are computed at execution time from the pool's live vault balances and the LP-to-token invariant [5](#0-4) . If the withdraw instruction omits `min_coin_amount`/`min_pc_amount` (or a wallet/integration builds the instruction without them, as the CLI's `false` slippage-limit example encourages), there is **no on-chain enforcement whatsoever** of a minimum acceptable output. Unlike the swap instructions, where `minimum_amount_out` is a mandatory (non-`Option`) field always checked [6](#0-5) , the withdraw path treats slippage protection as fully optional.

Because the pool state (vault balances / target-orders PnL) can be altered by any other transaction landing before the withdraw (e.g., an attacker's swap that skews the coin/pc ratio, or PnL take logic in `calc_take_pnl`), a withdraw submitted without min-amounts can be sandwiched: an attacker swaps to shift the ratio unfavorably immediately before the victim's withdraw executes, then reverses the swap afterward, extracting value at the victim's expense.

### Impact Explanation
An LP who withdraws without setting min-amounts (either because their integration doesn't populate them, or because they rely on the "optional" nature of the field) can receive materially fewer `coin`/`pc` tokens than the fair-value redemption of their LP position, directly transferring value to the attacker performing the sandwich. This is a direct, concrete loss of LP funds during market turbulence or targeted MEV, matching the impact class of the referenced report.

### Likelihood Explanation
Any unprivileged party can trigger this: the attacker only needs to observe a pending withdraw transaction in the mempool (or via Jito bundles) and insert bracketing swap transactions using the four permissionless swap instructions on the same pool. No privileged accounts, special build, or off-chain component is required — everything routes through the standard `Withdraw` and `SwapBaseIn`/`SwapBaseOut` instructions reachable by any signer with the right token accounts. The likelihood is amplified by the fact that the min-amount fields are optional and the reference client tooling explicitly demonstrates disabling them.

### Recommendation
Make `min_coin_amount` and `min_pc_amount` mandatory (non-`Option`) fields on `WithdrawInstruction`, always enforced in `process_withdraw`, mirroring the mandatory `minimum_amount_out` design already used for swaps. Reject the instruction if the caller passes 0 as a way to bypass protection unless explicitly intended, and update `amm-cli`/client helpers to always populate these values by default rather than exposing a "no slippage limit" toggle.

### Proof of Concept
1. Attacker observes an in-flight `Withdraw` instruction (built via `amm-cli` with `slippage_limit: false`, or any client that omits the 16 trailing bytes) targeting `AmmInfo` pool `P`.
2. Attacker submits (or bundles) a `SwapBaseIn`/`SwapBaseOut` against pool `P` right before the withdraw lands, shifting `amm_coin_vault`/`amm_pc_vault` balances so that `Calculator::calc_total_without_take_pnl_no_orderbook` yields a worse ratio for the withdrawing LP.
3. The victim's `Withdraw` executes: because `withdraw.min_coin_amount`/`min_pc_amount` are `None`, the check at `program/src/processor.rs` lines 1779-1786 is skipped entirely, and the LP receives `coin_amount`/`pc_amount` computed off the manipulated vault state — no error is raised regardless of how unfavorable the output is.
4. Attacker reverses their swap afterward, pocketing the difference extracted from the victim's withdrawal.
