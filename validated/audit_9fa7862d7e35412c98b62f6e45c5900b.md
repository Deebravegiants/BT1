This confirms the root cause: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` (`lib/shopify_api/webhooks/request.rb:36-38`), and `shop` is read straight from the `shop-domain` header (`lib/shopify_api/webhooks/request.rb:20-23`) with no cross-check against the HMAC-signed content. `Registry.process` validates only `Utils::HmacValidator.validate(request)` (which hashes `to_signable_string`, i.e., body only) then passes `request.shop` — the unauthenticated header value — straight into the handler.

### Title
Webhook shop identity spoofing via HMAC that only covers the request body, not the `shop-domain` header - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body alone, while the `shop` attribute that host applications use to key tenant data comes from the unsigned `X-Shopify-Shop-Domain` header. `Registry.process` only checks that the body's HMAC is valid; it never verifies the header claiming which shop the event belongs to actually matches the same webhook delivery.

### Finding Description
`to_signable_string` in `lib/shopify_api/webhooks/request.rb:35-38` returns `@raw_body` only:
```ruby
def to_signable_string
  @raw_body
end
```
`shop` is derived independently from a header that is not part of that signable string:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
```
`Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) recomputes the HMAC over `verifiable_query.to_signable_string` (the body) and compares it to the `hmac` header. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) only gates on this body HMAC:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
```
Because `shop` is never covered by the HMAC, the identity binding the report describes — "the field a decision is made on" (`shop`, used by host applications to scope per-tenant data) versus "the field actually authenticated" (only the raw body) — is broken. Any merchant who has legitimately installed the app receives real, validly-HMAC-signed webhook deliveries for their own store. Since the same app `client_secret` is used to sign webhooks for every shop that installs the app, that merchant can capture one of their own genuine `(body, hmac)` pairs and replay it to the app's public webhook endpoint while substituting an arbitrary value in the `X-Shopify-Shop-Domain` header (e.g., another victim shop's domain). The HMAC check still passes because it only validates the body, and `Registry.process` hands the handler a `WebhookMetadata` whose `shop` is the attacker-chosen, unauthenticated value.

### Impact Explanation
This is a cross-tenant authentication-boundary break: an unprivileged but legitimately-installed merchant can forge webhook events (e.g. `app/uninstalled`, `customers/data_request`, `shop/redact`, order/customer webhooks) that appear to originate from a different shop, because the only cryptographic guarantee (`hmac` over body) says nothing about which tenant the event is for. Host applications built against this gem's documented API reasonably rely on `WebhookMetadata#shop` as an authenticated tenant identifier once `Registry.process` has not raised `InvalidWebhookError`. This can lead to cross-tenant data corruption, unauthorized session/token deletion, or triggering GDPR-mandated data actions against the wrong merchant's data store.

### Likelihood Explanation
Requires only that the attacker be a legitimate app-installing merchant (any unprivileged internet user who installs the app) who can receive at least one real webhook for their own shop and replay it with a modified header at the app's public webhook receiving endpoint. No access token, `client_secret`, or privileged credentials are needed — only a captured valid `(body, hmac)` pair from their own tenant.

### Recommendation
- Short term: Include the shop domain (and other identity-relevant headers such as `webhook-id`, `api-version`) in the HMAC-signable string, or independently verify `request.shop` against session/tenant records the app already trusts before dispatching to handlers.
- Long term: Add tests that specifically simulate cross-tenant replay (valid HMAC over body, mismatched `shop-domain` header) to ensure `Registry.process` rejects or the resulting `WebhookMetadata#shop` cannot be trusted without additional binding.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a legitimate webhook delivery, e.g. an `app/uninstalled` event, with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because both are generated by Shopify with the app's `client_secret`).
2. Attacker replays the exact same `POST` to the app's webhook endpoint, keeping body `B` and header `H` unchanged, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "victim.myshopify.com", "x-shopify-hmac-sha256" => H})` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and succeeds.
4. The registered handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the host application to act on `victim.myshopify.com`'s tenant data using content that was never actually sent by Shopify for that shop. [1](#0-0) [2](#0-1) [3](#0-2)
