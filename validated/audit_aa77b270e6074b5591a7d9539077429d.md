### Title
Webhook shop-domain header is trusted for tenant routing while only the raw body is HMAC-covered - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by HMAC-verifying the raw request body [1](#0-0) . The `shop` (and `topic`/`webhook_id`) values used to build the `WebhookMetadata` passed to the app's handler come from HTTP headers (`shopify-shop-domain` / `x-shopify-shop-domain`) that are **not** part of the signed content — `to_signable_string` returns only `@raw_body` [2](#0-1) . This breaks the intended binding `hmac == HMAC(secret, body + shop)`; in reality it is only `hmac == HMAC(secret, body)`.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` with `to_signable_string` returning just `@raw_body` [3](#0-2) , while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from unauthenticated headers [4](#0-3) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e., that the body's HMAC matches the app's shared `api_secret_key`) before dispatching to the topic handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` [5](#0-4) . Because `api_secret_key` is a single app-level secret shared across every shop that installs the app (not a per-shop secret), any merchant who installs the app on their own store legitimately receives correctly signed `(raw_body, hmac)` pairs from Shopify. That merchant — an otherwise unprivileged actor with respect to any other tenant — can replay that exact `raw_body` + `hmac` to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. Because the header is never covered by the signature, `Utils::HmacValidator.validate` still returns `true`, and the handler receives a `WebhookMetadata` claiming to originate from a victim shop.

The gem's own documentation reinforces the false guarantee: it states that `Registry.process` "will verify the request did indeed come from Shopify" [6](#0-5) , without noting that the `shop` field returned in the metadata is unauthenticated. This is a `field acted on but not covered by the HMAC` binding failure directly in the gem's own webhook-verification code (`Utils::HmacValidator` + `Webhooks::Request`), not something that requires the host app to misuse an API — the gem itself hands out an unverified `shop` value as part of the "verified" result.

### Impact Explanation
This allows cross-tenant impersonation of webhook events: an attacker who has legitimate access to their own shop's webhook deliveries can forge events (e.g., `app/uninstalled`, `customers/data_request`, `shop/update`, or any topic-specific body they can get signed via their own install) that the host app will treat as coming from a different, victim merchant's shop, since the gem exposes `shop` inside the "verified" `WebhookMetadata` without it being bound to the signature. Any app logic that keys off `data.shop` for authorization or state changes (a common, encouraged pattern per the docs, e.g. "register to receive webhooks for that shop") is exposed to cross-tenant data corruption or unauthorized state changes. This matches the Critical-severity "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only that the attacker have legitimate access to at least one installation of the target app (any developer/merchant can install a public app on their own store) in order to obtain a validly-signed `(body, hmac)` pair, then replay it with a spoofed `shop-domain` header at the app's webhook endpoint. No access to `api_secret_key`, access tokens, or any other credential belonging to the victim shop is required — only the ability to send an HTTP request with a rewritten header, which is fully within reach of an unprivileged internet user who is a legitimate customer of the SaaS app.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header value into the signed content checked by `Utils::HmacValidator`, or, at minimum, do not present `request.shop` as part of a "verified" result — require host apps to independently authenticate the shop (e.g., by confirming a session/install record exists in their own store, and by cross-checking that `shop` matches session data obtained through OAuth/token exchange) before trusting it as `WebhookMetadata.shop`. At the least, `docs/usage/webhooks.md` and `Registry.process` should be updated to state clearly that `shop` is not covered by the HMAC and must not be relied upon alone for tenant identification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`, receiving legitimate webhook deliveries signed with the app's shared `api_secret_key`.
2. Attacker captures one such delivery's `raw_body` and its valid `X-Shopify-Hmac-Sha256` header.
3. Attacker resends that exact `raw_body` and `hmac` header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and any topic they want.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds successfully (all required headers present) [7](#0-6) ; `Utils::HmacValidator.validate(request)` returns `true` because it only checks `raw_body` against the shared secret [8](#0-7) .
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` [5](#0-4) , causing the host app to act on data attributed to a shop the attacker never controls.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

        end

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
