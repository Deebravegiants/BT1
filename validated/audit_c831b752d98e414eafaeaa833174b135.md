This confirms the vulnerability analysis. `emporiumMessage` is a public field visible in `CircomData`, part of `calldataHash` and included as a public circuit input [1](#0-0) , but the `usedMessages` mapping that tracks whether it has been consumed is keyed *only* by the raw `emporiumMessage` value with no binding to the original signer's identity [2](#0-1) .

### Title
Anyone can front-run and permanently burn another user's pending Emporium operation via `cancelEmporiumMessage` - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`cancelEmporiumMessage` is meant to let a signer "burn `emporiumMessage` before it's used, via a fresh signature recovering to msg.sender (so no one else can cancel it for them)" [3](#0-2) . However, the function only checks that the ECDSA signature over `EmporiumCancel(uint256 message)` recovers to `msg.sender` — it never checks that `msg.sender`/the recovered signer is the same party (`stack.signerAddress`) that originally created the pending `EmporiumSignature` for that `emporiumMessage`. Since `emporiumMessage` is an arbitrary value chosen by the original order's creator and is visible on-chain (it is part of `CircomData.calldataHash` inputs and a public circuit signal) [4](#0-3) , any unrelated attacker can sign an `EmporiumCancel` message for that exact `emporiumMessage` value with their *own* private key and call `cancelEmporiumMessage`. Because `usedMessages` is a single global mapping keyed only by the numeric message, not by signer [2](#0-1) , this marks the victim's not-yet-executed `emporiumMessage` as used, causing the legitimate `runAction` call that later references it to revert with `UsedMessage` in `verifyWallet` [5](#0-4) .

### Finding Description
The equality that should hold is: *"a message can only be cancelled/burned by the same signer who created the corresponding `EmporiumSignature`."* Instead, `cancelEmporiumMessage` verifies `recoveredAddress == msg.sender` — an always-true statement for whoever calls it with a signature over their own address, regardless of whose `emporiumMessage` value they choose to target:

```solidity
function cancelEmporiumMessage(uint256 emporiumMessage, uint8 v, bytes32 r, bytes32 s) external {
    EmporiumStorageVars storage $ = _getEmporiumStorage();
    bytes32 hashedMessage = _hashTypedDataV4(
        keccak256(abi.encode(EMPORIUM_CANCEL_TYPEHASH, emporiumMessage))
    );
    (address recoveredAddress, ECDSA.RecoverError err) = ECDSA.tryRecover(hashedMessage, v, r, s);
    bool verified = err == ECDSA.RecoverError.NoError && recoveredAddress == msg.sender;
    if (!verified) revert InvalidSignature();
    $.usedMessages[emporiumMessage] = true;
}
``` [6](#0-5) 

Any attacker A can:
1. Observe (in mempool, or knowing it beforehand off-chain) victim B's pending `circomData.emporiumMessage` value that B intends to submit via `Hinkal.transact` → `EmporiumUpgradeable.runAction`.
2. Sign `EmporiumCancel(emporiumMessage)` with A's own wallet key (a trivial, valid self-signature).
3. Call `cancelEmporiumMessage(emporiumMessage, vA, rA, sA)` with higher gas to land first.
4. `$.usedMessages[emporiumMessage]` is now `true`, and B's `runAction` call reverts at `verifyWallet` with `UsedMessage()` — even though A never had any authorization over B's order and the ZK-proof/EIP-712 signature that actually authorized B's operation was never touched.

This breaks the intended per-signer isolation invariant of `usedMessages`, which is a single shared global mapping across all users of the `EmporiumUpgradeable` contract [2](#0-1) , with no namespacing by `stack.signerAddress`.

### Impact Explanation
This is a griefing/DoS primitive that maps to "temporary freezing of user funds": a victim's Emporium operation (e.g., a time-bound swap/withdrawal governed by `stack.deadline`) can be repeatedly and permanently blocked by any unprivileged attacker without needing the victim's signature, ZK proof knowledge, or relay privileges. Since operations carry a `deadline` [7](#0-6) , an attacker can continuously invalidate the victim's chosen `emporiumMessage` before the deadline, effectively causing loss of funds if the operation was, e.g., a time-sensitive swap that cannot be re-submitted profitably, or causing indefinite freezing if the attacker monitors the mempool and always front-runs new attempts.

### Likelihood Explanation
High likelihood: exploitation requires no privileged role, no knowledge of the victim's private key, and no proof generation — only observing a public `emporiumMessage` value and submitting a cheap self-signed cancel transaction with higher gas. This is directly analogous to, but more severe than, the referenced Putty finding: instead of merely being unable to cancel one's *own* order, an attacker can maliciously cancel *anyone's* pending order.

### Recommendation
Bind `usedMessages` (and the cancel authorization check) to the original signer, e.g. `mapping(address => mapping(uint256 => bool)) usedMessages`, and require in `cancelEmporiumMessage` that the recovered signer matches the `signerAddress` that was bound to `emporiumMessage` when it was created (or require the caller to supply/prove the same `signerAddress` used in the corresponding `EmporiumSignature`, and verify equality before marking used).

### Proof of Concept
1. Victim B constructs an `EmporiumStack` with `emporiumMessage = M`, signs `EmporiumSignature` with `signerAddress = B`, and broadcasts a `Hinkal.transact` call referencing `circomData.emporiumMessage = M`.
2. Attacker A sees `M` in the pending transaction calldata (public mempool) or otherwise learns it.
3. A computes `EmporiumCancel(M)` typed-data hash and signs it with A's own key, producing `(v, r, s)`.
4. A calls `cancelEmporiumMessage(M, v, r, s)` with a higher gas price so it mines before B's transaction.
5. `verified` is `true` because `recoveredAddress == msg.sender == A`; `$.usedMessages[M] = true` is set.
6. B's `runAction` call subsequently reverts with `UsedMessage()` in `verifyWallet`, even though A had no relation to B's order [8](#0-7) .
