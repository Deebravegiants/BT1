### Title
Disabled overfill clamp plus optional `maxOrderSize` lets a manipulated pool price drain a solver's escrowed output with no upper bound - ([File: sdk/packages/simplex/src/strategies/fx.ts])

### Summary
The reported bug is a lending market that has no cap on how much of a price-pegged asset (Note) can be borrowed against manipulable TWAP-derived collateral pricing, letting an attacker manipulate the oracle and extract unbounded value. The closest reachable analog in Hyperbridge is the intents filler (`FXFiller`) in `sdk/packages/simplex/src/strategies/fx.ts`, which sizes and pays out `IntrinsicIntents.sol` / `IntentGatewayV2.sol` fills using a curve/rate that can be influenced by a spot/venue price (e.g. a Uniswap V4 pool), while both of the guardrails that used to bound the payout — the per-pair `maxOrderSize` and the `maxOverfillBps` overfill ceiling — have been made non-binding.

### Finding Description
`FXFiller.calculateProfitability` in `sdk/packages/simplex/src/strategies/fx.ts` computes `targetOutput = policyMaxOutput` "unconditionally" — the curve amount is paid out even when it exceeds what the order actually asked for, per the documented rationale that `IntrinsicIntents.sol` splits any solver overpay between the beneficiary and protocol (`surplusShareBps`) [1](#0-0) .

Two separate protections that would previously have bounded this payout are both non-functional:

1. `maxOrderSize` is now optional per trading pair — "absent means uncapped, and the pair fills every order at its full notional" — so a pair configured (or manipulated into) an unbounded budget imposes no ceiling on the curve evaluation point at all [2](#0-1) .

2. The `maxOverfillBps` clamp — the mechanism that was designed to reject/limit a fill when the curve output diverges too far above `(1 + maxOverfillBps) * userRequested` — is explicitly disabled. The code only logs a warning and still fills the "unclamped amount": *"Overfill detection is warn-only: the clamp is DISABLED, so the filler fills the full computed amount even when it exceeds (1 + maxOverfillBps) × user-requested... This removes the per-leg loss bound that previously protected against a bug / stale cache / manipulated venue price."* [3](#0-2) 

The design decision record acknowledges the disabled ceiling is "dormant config" left deliberately unarmed rather than removed, explicitly framing this as a known open trade-off [4](#0-3) .

The rate/curve driving `policyMaxOutput` is sourced in part from venue prices (Uniswap V4 pool state read via `UniswapV4LiquidityState`/`UniswapV4FundingPlanner`), the same class of on-chain spot price the original report warns is manipulable to distort the amount a lending/fill mechanism will release. With both the per-pair notional cap and the overfill ceiling disabled/optional, there is no remaining bound on how much output the on-chain fill (`IntrinsicIntents.sol`'s `solverAmount > totalRequired` surplus branch) will be sized to pay, other than the solver's own wallet balance and funding-venue liquidity.

### Impact Explanation
An attacker who can move the venue price feeding the curve (e.g. via a flash-loan-assisted swap against the referenced Uniswap V4 pool, mirroring the original report's TWAP-manipulation vector) can cause `policyMaxOutput`/`targetOutput` to be computed far above the fair value of the order. Because:
- `maxOrderSize` may be unset (uncapped) for the pair, and
- the `maxOverfillBps` ceiling that would otherwise reject or cap an anomalously large computed output is disabled (warn-only),

the filler will size and submit a fill that pays out an unbounded amount of its escrowed/held tokens relative to what the counterparty's order actually required, extracting value from the solver's balance sheet and, transitively, from any liquidity it draws from funding venues (vault, Uniswap V4 positions) to cover the shortfall. This mirrors the reported Medium-severity impact: no cap plus a manipulable price feed makes the extractable value effectively unbounded, and the cost/benefit of the manipulation attack cannot be safely evaluated because there's no ceiling on the resulting loss.

### Likelihood Explanation
This requires an attacker to be able to manipulate the reference/venue price feeding the pair's curve (analogous cost to the original report's TWAP manipulation) and to submit or steer an order that the filler will evaluate against a pair with no `maxOrderSize` configured (or one large enough not to bind), while `maxOverfillBps` remains disabled by default in this codebase. Both preconditions — an unset/loose `maxOrderSize` and the disabled overfill clamp — are current, non-exceptional configuration/behavior of the shipped filler rather than a rare misconfiguration, which raises likelihood relative to the "requires oracle manipulation" caveat the original judge applied when downgrading severity to Medium.

### Recommendation
- Re-arm the `maxOverfillBps` ceiling as a hard cap (not warn-only) on `policyMaxOutput`/`targetOutput`, or reject the fill outright when the computed output exceeds the configured tolerance above `output.amount`.
- Do not allow `maxOrderSize` to be fully unbounded for pairs whose rate depends on a manipulable on-chain venue price; require an explicit, sane maximum notional per pair regardless of configuration, mirroring the original report's recommendation of an enforced borrow/mint-style cap.
- Where venue prices (e.g., Uniswap V4 spot price) feed the curve, prefer TWAP-averaged or multi-block-resistant price sources, and sanity-check the resulting rate against an independent reference before sizing a fill.

### Proof of Concept
1. Configure (or find in production) a `TradingPair` whose `maxOrderSize` is unset (uncapped) and whose rate is derived, even partially, from a Uniswap V4 pool's spot state, as read by `UniswapV4LiquidityState`/`UniswapV4FundingPlanner`.
2. Flash-loan-manipulate that pool's price momentarily (the same class of attack described in the source report against a lending market's TWAP) so that `computeLegPolicyOutput`'s resulting `policyMaxOutput` for the leg is far above the order's fair value.
3. Submit (or wait for) an order matching that pair; `FXFiller.calculateProfitability`/`executeOrder` computes `targetOutput = policyMaxOutput` unconditionally [5](#0-4) , logs (but does not block on) the overfill-ceiling breach [6](#0-5) , and proceeds to source the inflated amount from wallet balance plus funding venues before calling `IntentGatewayV2`/`IntrinsicIntents.sol`'s `fillOrder`, which pays the surplus out per `surplusShareBps` with no protocol-side ceiling on `solverAmount`.
4. Restore the pool price after the fill lands, having extracted the manipulated surplus from the solver's escrowed funds.
