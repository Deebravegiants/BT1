Audit Report

## Title
LDAP Authentication Bypass via Empty Password Triggering Unauthenticated Bind - (File: core/sessions/ldapauth/ldap.go)

## Summary
`ldapAuthenticator.CreateSession` and `ldapAuthenticator.TestPassword` in `core/sessions/ldapauth/ldap.go` forward the client-supplied `sr.Password` / `password` directly into `conn.Bind(dn, password)` without ever checking that the password is non-empty. `SessionRequest.Password` has no validation tag or empty-string guard anywhere in the JSON binding path, so an unauthenticated `POST /sessions` request with an empty password string reaches the LDAP bind call unmodified.

## Finding Description
`CreateSession` builds a DN from the attacker-supplied email and calls `conn.Bind(searchBaseDN, sr.Password)` with no precondition on `sr.Password` being non-empty: [1](#0-0) . The same unguarded pattern exists in `TestPassword`: [2](#0-1) . The `sessions.SessionRequest` struct that carries the password from the JSON body has no `binding:"required"` tag or other validation preventing an empty string from reaching this code path: [3](#0-2) . The HTTP path from an unauthenticated client is `POST /sessions` → `SessionsController.Create` → `sc.App.AuthenticationProvider().CreateSession(ctx, sr)`, with only a JSON-bind check (`c.ShouldBindJSON`) that does not enforce non-empty password: [4](#0-3) . Per RFC 4513 §5.1.2, a `Bind` with a non-empty DN and an empty password is defined as an "unauthenticated bind," which many LDAP servers will complete successfully without validating the DN/password pair at all — this is the same root-cause class as CVE-2018-11407 in Symfony's LDAP authentication component.

## Impact Explanation
If the operator's LDAP server permits unauthenticated binds for non-empty DN + empty password (a documented default per RFC 4513, and the exact condition Symfony's advisory addressed), an attacker who knows or guesses a valid LDAP `uid`/email could get `conn.Bind` to return success without any password check, causing `CreateSession` to call `FindUser`, create an `ldap_sessions` row, and issue a valid session cookie for that user — assuming their full RBAC role, potentially Admin. This maps to the in-scope "node API authentication or role bypass" impact category and would be Critical severity if the precondition holds.

## Likelihood Explanation
The vulnerability is reachable by a fully unprivileged, unauthenticated client (`POST /sessions` requires no prior credential), which satisfies the "no operator/admin access needed" bar. However, actual exploitability is entirely gated by LDAP server-side behavior: it only manifests if the configured LDAP server accepts unauthenticated/anonymous binds for a non-empty DN and empty password rather than rejecting per RFC 4513 §5.1.2 default recommendation (many hardened directory servers, including modern OpenLDAP/AD defaults, explicitly disable this). This is precisely the kind of "misconfiguration-dependent" precondition that the validation rules direct me to treat with caution, but it is also the identical, well-established defense-in-depth failure that Symfony's CVE-2018-11407 fix addressed by adding the check regardless of server config — the application should not rely on server-side behavior for a security-critical guarantee it controls locally (verifying non-empty password before bind).

## Recommendation
Add an explicit check in both `CreateSession` and `TestPassword` in `core/sessions/ldapauth/ldap.go` to reject any request where `sr.Password` (or `password`) is empty or whitespace-only, failing authentication before ever calling `conn.Bind`, mirroring Symfony's fix for CVE-2018-11407.

## Proof of Concept
1. Identify or guess a valid LDAP `uid`/email for a node user (e.g., an admin's email).
2. Send `POST /sessions` with body `{"email":"admin@example.com","password":""}`.
3. If the configured LDAP backend allows unauthenticated binds for the given DN, `conn.Bind(searchBaseDN, "")` at `core/sessions/ldapauth/ldap.go:408` returns success, `FindUser` resolves the role, and a valid session is created and returned — without any correct password.
4. As a Go unit test: mock `LDAPConn.Bind` to return `nil` when called with an empty password argument (to simulate a real unauthenticated-bind-permissive server) and assert that `CreateSession` returns a valid session ID for an empty-password `SessionRequest`.

func (sc *SessionsController) Create(c *gin.Context) {
	defer sc.App.WakeSessionReaper()
	ctx := c.Request.Context()
	sc.App.GetLogger().Debugf("TRACE: Starting Session Creation")

	session := sessions.Default(c)
	var sr clsessions.SessionRequest
	if err := c.ShouldBindJSON(&sr); err != nil {
		jsonAPIError(c, http.StatusBadRequest, fmt.Errorf("error binding json %w", err))
		return
	}

	// Does this user have 2FA enabled?
	userWebAuthnTokens, err := sc.App.AuthenticationProvider().GetUserWebAuthn(ctx, sr.Email)
	if err != nil {
		sc.App.GetLogger().Errorf("Error loading user WebAuthn data: %s", err)
		jsonAPIError(c, http.StatusInternalServerError, errors.New("internal Server Error"))
		return
	}

	// If the user has registered MFA tokens, then populate our session store and context
	// required for successful WebAuthn authentication
	if len(userWebAuthnTokens) > 0 {
		sr.SessionStore = sc.sessions
		sr.WebAuthnConfig = sc.App.GetWebAuthnConfiguration()
	}

	sid, err := sc.App.AuthenticationProvider().CreateSession(ctx, sr)
	if err != nil {
		jsonAPIError(c, http.StatusUnauthorized, err)
		return
	}
