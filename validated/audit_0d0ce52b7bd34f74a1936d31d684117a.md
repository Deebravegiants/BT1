### Title
Vetoing the latest state-machine height causes a stale bounded-commitment-queue entry to prematurely delete a live, unvetoed commitment — ([File: modules/pallets/ismp/src/lib.rs])

### Summary
`pallet-ismp`'s bounded state-commitment cache (`BoundedStateCommitments` / `StateCommitmentQueue`) can end up with two queue entries pointing at the same height after a fisherman vetoes the *latest* stored height and the height is honestly resubmitted. When the queue subsequently evicts oldest-first, the stale (already-consumed) queue entry is dequeued first and deletes the now-live commitment for that height — one insertion before the legitimate queue entry for the same height would have retired it naturally. This is a stale-reference-triggers-premature-free bug: a resource (`BoundedStateCommitments[height]`) that is still "live" and referenced by relayers/handlers gets deleted because of a dangling index left behind by the veto path, analogous to a use-after-free where a freed/stale handle is later dereferenced/acted upon to corrupt a still-live object.

### Finding Description
`insert_bounded_state_commitment` appends every newly stored height to a FIFO `StateCommitmentQueue` and evicts from the head once the per-chain cap is exceeded [1](#0-0) . `delete_state_commitment` (invoked by the fisherman veto path) removes the `BoundedStateCommitments` entry immediately but deliberately leaves the corresponding queue slot behind rather than scanning the queue to find it [2](#0-1) . If the vetoed height is the *latest* one, `LatestStateMachineHeight` is rolled back to the previous height, which re-opens that same height number for an honest consensus resubmission [3](#0-2) . The resubmission inserts a *second* queue entry for the same height, directly behind the stale one. When the queue later evicts at the head, the stale entry fires first and calls `BoundedStateCommitments::remove` / `BoundedStateMachineUpdateTime::remove` for that height — deleting the live, still-referenced commitment one insertion earlier than it should have been retired, and permanently burning one queue slot (the chain retains one fewer commitment than its configured cap) [4](#0-3) .

This exact behavior is confirmed and explicitly documented as a known "wart" in the pallet's own regression test, `vetoed_latest_height_that_is_resubmitted_evicts_one_insertion_early`, which asserts that after the stale eviction, `host.state_machine_commitment(... height: 11)` — the resubmitted, live commitment — returns an error [5](#0-4) .

Once `BoundedStateCommitments` for a height is gone, any handler that depends on `state_machine_commitment(height)` — e.g. `validate_state_machine` / `verify_delay_passed` in the core message-handling path — will fail to locate the state root for that height [6](#0-5) , and `verify_membership` for post-request/response delivery against that height's overlay root becomes unusable [7](#0-6) . Because state-machine heights only move forward and the same height number will not be re-issued, any request or response whose relayer proof targets that specific height is permanently undeliverable through that height once it is prematurely evicted.

### Impact Explanation
This is a state-invalidation bug reachable through the protocol's normal, intended fisherman-veto mechanism rather than any admin/governance compromise: an honest fisherman correctly vetoes a genuinely bad `StateMachineHeight` (the designed use of `delete_state_commitment`), and the very next honest consensus update at that same height (the designed recovery path) triggers collateral damage — deletion of the just-restored, valid commitment. The result is a route that cannot deliver messages for that height: relayers holding valid membership/non-membership proofs against the destroyed commitment can no longer get `handlePostRequests`/`handlePostRequestTimeouts`-equivalent verification through `verify_membership`/`verify_state_proof`, effectively freezing any in-flight cross-chain request or response anchored to that height until a later height supersedes it (and any request whose timeout window elapses before that happens is permanently lost). This qualifies as "unsound state commitment" / "a route unable to deliver messages" under the given impact taxonomy.

### Likelihood Explanation
The precondition is narrow but plausible under adversarial network conditions Hyperbridge is explicitly built to tolerate: a fisherman vetoes the *latest* height (a routine, expected veto scenario — vetoing older heights is far more common but vetoing the newest height happens whenever a bad update is caught immediately), followed by the very next honest state-machine update landing at that same height number, which is the ordinary next step in ISMP consensus progression. No malicious relayer, collator, or governance action is required — only the standard veto-then-resubmit sequence that the fishermen system is designed to support, combined with the queue reaching its (configurable, potentially small) per-chain cap so eviction actually fires on the next few insertions.

### Recommendation
When `delete_state_commitment` vetoes the latest height and rolls `LatestStateMachineHeight` back, also mark/skip the corresponding stale `StateCommitmentQueue` entry (e.g., by storing a tombstone value or the actual height→index mapping the code comment mentions) so that the eviction path does not remove a commitment that was live-relaid at the same height number. Alternatively, on resubmission of a previously-vetoed-and-reopened height, detect the pre-existing stale queue slot for that height and reuse/overwrite it in place instead of appending a second entry.

### Proof of Concept
The existing test `vetoed_latest_height_that_is_resubmitted_evicts_one_insertion_early` in the testsuite is a working PoC: it stores heights 10 and 11 with cap 2, vetoes height 11 (the latest), resubmits height 11, and shows two queue entries now reference height 11; after one more legitimate insertion (height 12), the stale queue entry evicts the live commitment for 11, and `host.state_machine_commitment(... height: 11)` returns an error while it should be a valid, retained commitment [8](#0-7) .

		/// Insert a state commitment into the bounded map. ISMP does not allow
		/// duplicate state updates so we don't have an overwrite path.
		///
		/// Appends the height to the per-chain [`StateCommitmentQueue`] and, once
		/// the chain's cap is exceeded, evicts oldest-first from the queue head.
		/// Evictions are limited to [`MAX_COMMITMENT_EVICTIONS_PER_INSERT`] per
		/// call so a lowered cap drains over many insertions rather than in one.
		pub fn insert_bounded_state_commitment(
			height: StateMachineHeight,
			commitment: StateCommitment,
		) {
			let cap = Self::state_machine_commitment_cap(height.id).max(1) as u64;
			let mut state = CommitmentQueueStates::<T>::get(height.id);

			StateCommitmentQueue::<T>::insert(height.id, state.tail, height.height);
			state.tail += 1;

			let excess = (state.tail - state.head)
				.saturating_sub(cap)
				.min(MAX_COMMITMENT_EVICTIONS_PER_INSERT as u64);
			for _ in 0..excess {
				if let Some(old) = StateCommitmentQueue::<T>::take(height.id, state.head) {
					BoundedStateCommitments::<T>::remove(height.id, old);
					BoundedStateMachineUpdateTime::<T>::remove(height.id, old);
				}
				state.head += 1;
			}

			CommitmentQueueStates::<T>::insert(height.id, state);
			BoundedStateCommitments::<T>::insert(height.id, height.height, commitment);
		}

	fn delete_state_commitment(&self, height: StateMachineHeight) -> Result<(), Error> {
		// The height's entry in the state commitment queue is deliberately left
		// behind; locating it would mean scanning the queue, which is the per-insert
		// cost the queue exists to avoid. Usually its eviction is a no-op, but when
		// the vetoed height is the latest the reset below re-opens it for honest
		// resubmission, and the resubmitted height gets a *second* queue entry. The
		// stale entry then evicts the live commitment when it reaches the head —
		// one insertion before the live entry would have, since the resubmission
		// lands directly behind its stale twin. So a veto costs that height one
		// insertion of retention and permanently burns one queue slot. Both are
		// negligible against the configured caps; making it exact would need a
		// height -> index map on the insert path.
		BoundedStateCommitments::<T>::remove(height.id, height.height);
		BoundedStateMachineUpdateTime::<T>::remove(height.id, height.height);

		// technically any state commitment can be vetoed,
		// safety check that it's the latest before resetting it.
		if let Some(latest) = LatestStateMachineHeight::<T>::get(height.id) {
			if latest == height.height {
				// Reset back to the initial height to allow for honest updates
				let prev_height =
					PreviousStateMachineHeight::<T>::get(height.id).ok_or_else(|| {
						Error::Custom("Previous state machine height should exist".to_string())
					})?;
				LatestStateMachineHeight::<T>::insert(height.id, prev_height);
			}
		}
		Ok(())
	}

	ext.execute_with(|| {
		let host = Ismp::default();
		let id = queue_test_state_machine();

			host.store_state_machine_commitment(
				StateMachineHeight { id, height },
				queue_test_commitment(),
			)
			.unwrap();
			host.store_latest_commitment_height(StateMachineHeight { id, height }).unwrap();
		};

		pallet_ismp::Pallet::<Test>::update_commitment_caps(
			RuntimeOrigin::root(),
			BTreeMap::from([(id, 2)]),
		)
		.unwrap();

		store(10);
		store(11);

		// Vetoing the latest height rolls the latest pointer back to 10, so the
		// consensus handler would accept 11 again: it is not below the latest and
		// its commitment is now absent.
		host.delete_state_commitment(StateMachineHeight { id, height: 11 }).unwrap();
		assert_eq!(host.latest_commitment_height(id).unwrap(), 10);

		store(11);
		assert!(host.state_machine_commitment(StateMachineHeight { id, height: 11 }).is_ok());
		// Two queue entries now point at height 11: the stale one and the live one.
		assert_eq!(StateCommitmentQueue::<Test>::get(id, 1), Some(11));
		assert_eq!(StateCommitmentQueue::<Test>::get(id, 2), Some(11));

		// Evicting the stale entry at index 1 deletes the live commitment for 11,
		// one insertion before the entry at index 2 would have.
		store(12);
		assert!(host.state_machine_commitment(StateMachineHeight { id, height: 11 }).is_err());
		assert!(host.state_machine_commitment(StateMachineHeight { id, height: 12 }).is_ok());
		// The queue still counts index 2 as live, so the burnt slot leaves this
		// chain retaining one fewer commitment than its cap of 2.
		assert_eq!(
			CommitmentQueueStates::<Test>::get(id),
			CommitmentQueueState { head: 2, tail: 4 }
		);
		assert_eq!(StateCommitmentQueue::<Test>::get(id, 2), Some(11));

where
	H: IsmpHost,
{
	let update_time = host.state_machine_update_time(*proof_height)?;
	let delay_period = host
		.challenge_period(proof_height.id)
		.ok_or(Error::ChallengePeriodNotConfigured { state_machine: proof_height.id })?;
	let current_timestamp = host.timestamp();
	Ok(delay_period.as_secs() == 0 || current_timestamp.saturating_sub(update_time) > delay_period)
}
