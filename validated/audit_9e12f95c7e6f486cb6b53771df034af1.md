### Title
Non-embedded/offline session cookie value is an unauthenticated, deterministic session ID with no cryptographic binding to shop identity - (File: `lib/shopify_api/utils/session_utils.rb`)

### Summary
For embedded apps, this gem derives the session lookup key from a Shopify-signed JWT whose HMAC and claims (`aud`, `exp`, `nbf`) are verified before the shop/user identity is trusted. For non-embedded apps (and the non-embedded fallback path for embedded apps), the session lookup key is instead the raw, unsigned `shopify_app_session` cookie value, which the gem sets to a **deterministic** string (`"offline_#{shop}"` or `"#{shop}_#{user_id}"`) with no HMAC or other cryptographic proof binding it to a genuine, completed OAuth flow.

### Finding Description
`SessionUtils.current_session_id` branches on `Context.embedded?`: for embedded apps with an `id_token`, it calls `session_id_from_shopify_id_token`, which constructs `Auth::JwtPayload.new(id_token)` — a class that verifies the JWT's HMAC signature against `Context.api_secret_key` and validates the `aud` claim before any shop/user value is trusted [1](#0-0) . Only after this verification does it derive `jwt_session_id(shop, user_id)` or `offline_session_id(shop)` [2](#0-1) .

In every other branch (non-embedded apps, or embedded apps falling back to the cookie), the session id is taken directly and unconditionally from the cookie with **no signature check at all**: [3](#0-2) [4](#0-3) 

Critically, the value that this cookie *legitimately* takes after a real OAuth flow is fully deterministic and derivable from public information: for offline access it is `"offline_#{shop}"`, and for online access it is `"#{shop}_#{associated_user.id}"` — both computed in `Auth::Session.from` [5](#0-4)  and mirrored by `SessionUtils.offline_session_id`/`jwt_session_id` [6](#0-5) . The `SessionCookie` struct that carries this value is a plain, unsigned value/expiry pair with no MAC or nonce [7](#0-6) , and `Oauth.validate_auth_callback` sets the cookie's value to exactly `session.id` for non-embedded apps [8](#0-7) .

This breaks the binding that should hold: *`session_id used to fetch a stored access token` == `session_id that could only be produced by a party who actually completed OAuth for that shop`*. Because the ID is a deterministic function of public data (the shop domain, and often-enumerable numeric user IDs), any unprivileged party who merely knows or guesses a target shop's domain (and, for online sessions, a staff user ID) can construct the exact cookie value that will be used to key a legitimate, already-installed session in the host application's session store — without ever having gone through the OAuth handshake themselves. This is precisely the "session id derived from unauthenticated bytes" failure mode: the gem hands the host application a value that *looks like* an authenticated session identifier but carries no proof of authentication, in contrast to the JWT path where the analogous derivation is preceded by HMAC/claims verification.

### Impact Explanation
If the host application relies on `ShopifyAPI::Utils::SessionUtils.current_session_id`/`cookie_session_id` as the sole key into its session/token store (as the gem's documented cookie-based flow encourages for non-embedded apps), an attacker who supplies a forged `shopify_app_session` cookie with a guessed/known deterministic value can retrieve or activate another tenant's session — including the merchant's stored offline access token — without any credential of their own. That is cross-tenant access to another merchant's access token, matching the Critical impact bar (theft of a merchant access token / cross-tenant access). It is also a session-fixation vector: because the value is deterministic, an attacker can pre-compute and plant the exact cookie value that will "become valid" once a victim merchant completes OAuth, satisfying the High "session fixation" impact category even where an out-of-band step is needed to inject the cookie.

### Likelihood Explanation
The offline session ID requires only knowledge of the target's `myshopify.com` domain, which is public. The online session ID additionally requires the numeric Shopify staff user id, which is commonly low-cardinality/sequential and frequently observable via other Admin API responses (`associated_user.id`), making it realistically guessable in many deployments. No secret material, TLS interception, or prior privileged access is needed to compute the value — only the ability to place it into a cookie header on a request to the app (e.g., via any host-app behavior that reflects or sets cookies from user-controlled cookie state, standard in non-embedded browser session flows).

### Recommendation
Do not use a raw, predictable string as the trust-bearing session identifier for the cookie-based (non-embedded) path. Bind the cookie value to an unguessable, high-entropy, ideally signed/HMAC'd token (as is already done for the embedded JWT path via `Auth::JwtPayload`), so that presenting the cookie itself constitutes proof of having completed the OAuth handshake, not just knowledge of the shop's domain. At minimum, generate `session.id` from `SecureRandom` for the cookie value and store the deterministic `shop`/`user`-derived key only server-side, decoupling the externally-presented cookie bytes from the internal lookup key.

### Proof of Concept
1. Merchant `victim-shop.myshopify.com` installs the app and completes OAuth; the host app stores an offline session keyed by `"offline_victim-shop.myshopify.com"` with a real access token, as produced by `Auth::Session.from` [5](#0-4) .
2. An attacker, with no access to the app or Shopify credentials, sends a request to the host application with `Cookie: shopify_app_session=offline_victim-shop.myshopify.com` (a value computable purely from the public shop domain).
3. The host app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which returns `cookie_session_id(cookies)` — the raw attacker-supplied string, unverified [4](#0-3) .
4. The host app looks up this ID in its session store and retrieves `victim-shop`'s real offline access token, which it then uses on the attacker's behalf — a full cross-tenant compromise achieved with zero credentials, contingent only on the host app trusting the gem's session-id derivation as proof of authentication for the cookie path (unlike the JWT path, where `Auth::JwtPayload` enforces this proof).

        def session_id_from_shopify_id_token(id_token:, online:)
          raise Errors::MissingJwtTokenError, "Missing Shopify ID Token" if id_token.nil? || id_token.empty?

          payload = Auth::JwtPayload.new(id_token)
          shop = payload.shop

          if online
            jwt_session_id(shop, T.must(payload.sub))
          else
            offline_session_id(shop)
          end
        end

      class SessionCookie < T::Struct
        extend T::Sig

        SESSION_COOKIE_NAME = "shopify_app_session"

        const :name, String, default: SESSION_COOKIE_NAME
        const :value, String
        const :expires, T.nilable(Time)

        alias_method :eql?, :==
        sig { params(other: T.nilable(SessionCookie)).returns(T::Boolean) }
        def ==(other)
          return false unless other

          name == other.name &&
            value == other.value &&
            expires == other.expires
        end
      end
