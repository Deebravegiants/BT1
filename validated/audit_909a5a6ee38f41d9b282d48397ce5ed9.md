This confirms a strong, gem-consistent pattern: `ShopValidator.sanitize!` is deliberately used in `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and `TokenExchange` to constrain the `shop` value to a trusted Shopify domain *before* it is used to build the URL that receives `client_id`/`client_secret`, but `Auth::Oauth.begin_auth` and `Auth::Oauth.validate_auth_callback` never call it.

### Title
OAuth authorization-code flow never validates `shop` against trusted Shopify domains, enabling forced OAuth completion / host-binding bypass - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` and `validate_auth_callback` build the OAuth authorize URL and the access-token exchange host directly from the caller-supplied `shop` string, with no validation that it is a trusted `*.myshopify.com`/`myshopify.io`/`spin.dev` domain, unlike every other credential-exchange path in the gem.

### Finding Description
The equality that should hold is: *the domain that receives the app's redirect (`client_id`, `state` nonce) and later the domain that receives `client_id`/`client_secret` during code exchange* **==** *a domain independently proven to be a genuine Shopify shop*.

`begin_auth` builds the redirect target purely from the input `shop`: [1](#0-0) 
and `auth_base_uri` turns that unsanitized `shop` directly into a host: [2](#0-1) 

`validate_auth_callback` only checks the HMAC over the query bytes and the CSRF `state` cookie — it never checks that `auth_query.shop` is a real Shopify domain before using it to build the session that talks to the token endpoint: [3](#0-2) 

Every other credential-exchange path in the gem enforces `Utils::ShopValidator.sanitize!(shop)` before constructing the `HttpClient`/session that will carry `client_id`/`client_secret`: [4](#0-3) [5](#0-4) 

`Clients::HttpClient` derives the request host directly from `session.shop` when no `api_host` is configured: [6](#0-5) 

The gem's own documented usage feeds an unauthenticated, user-supplied value straight into `begin_auth(shop: ...)`: [7](#0-6) 

`Utils::ShopValidator` exists specifically to close this gap and is invoked everywhere except `oauth.rb`: [8](#0-7) 

### Impact Explanation
Because `begin_auth` never sanitizes `shop`, an attacker who supplies a non-Shopify `shop` value (e.g. a domain they control) causes the app to redirect the victim's browser to `https://<attacker-domain>/admin/oauth/authorize?client_id=...&state=<nonce>&redirect_uri=...`, leaking the app's `client_id` and the CSRF `state` nonce to the attacker's server while the nonce is simultaneously stored in the victim's session cookie by the app. The attacker can then complete a real OAuth grant with their own (attacker-owned) Shopify shop, and redirect the victim's browser back to the app's legitimate callback URL using the leaked `state` and a genuine Shopify-issued `code`/`hmac` for the attacker's shop. `validate_auth_callback` will accept this because the HMAC is valid (Shopify signed it) and `state` matches the victim's cookie — completing "forced OAuth" and binding the victim's application session/account to the attacker's shop. This lands squarely in the High-impact bucket: "session fixation or forced OAuth completion." It does not require the attacker to know `api_secret_key` or any merchant token.

### Likelihood Explanation
The vulnerable pattern (`shop` taken from an unauthenticated request field and passed straight into `begin_auth`) is exactly what the gem's own documentation instructs developers to do, so this is not a case of a host application misusing the library outside its documented contract — it is the sanctioned pattern combined with a gap in the library's own validation that every sibling grant flow (`ClientCredentials`, `RefreshToken`, `TokenExchange`) already closes.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) inside `Oauth.begin_auth` before constructing `auth_base_uri`, and apply the same validation to `auth_query.shop` inside `Oauth.validate_auth_callback` before it is used to build the `null_session`/`HttpClient` and before it is persisted into the resulting `Session`.

### Proof of Concept
1. App exposes `/login?shop=<value>` and calls `ShopifyAPI::Auth::Oauth.begin_auth(shop: value, redirect_path: "/auth/callback")` per the documented pattern [9](#0-8) .
2. Attacker sends victim a link to `/login?shop=attacker-controlled.example.com`.
3. `begin_auth` builds `auth_route = "https://attacker-controlled.example.com/admin/oauth/authorize?client_id=...&state=<nonce>&..."` via `auth_base_uri` [2](#0-1) , and the app sets the `state` nonce cookie in the victim's browser.
4. Victim's browser is redirected to the attacker's server, leaking `client_id` and `state`.
5. Attacker performs a genuine OAuth grant with their own Shopify shop, obtaining a real Shopify-signed `code`/`hmac` for `shop=attacker.myshopify.com`, and constructs a callback URL to the victim app using the leaked `state`.
6. Victim's browser (still holding the matching `state` cookie from step 3) is redirected to the app's real `/auth/callback?...&state=<nonce>&shop=attacker.myshopify.com&hmac=...`.
7. `validate_auth_callback` passes HMAC validation (genuinely signed by Shopify) and state-match validation [10](#0-9) , completing OAuth and binding the victim's app session to the attacker's shop.

    module ShopValidator
      TRUSTED_SHOPIFY_DOMAINS = T.let(
        [
          "shopify.com",
          "myshopify.io",
          "myshopify.com",
          "spin.dev",
          "shop.dev",
        ].freeze,
        T::Array[String],
      )

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
