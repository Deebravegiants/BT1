### Title
Webhook Shop Identity Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the `shop` value that is handed to application webhook handlers is taken from an unauthenticated HTTP header. Because a single app-level `api_secret_key` is shared across every shop that has installed the app, any merchant (including a low-privilege attacker who installs the app on their own store) can obtain one validly HMAC-signed webhook and replay it with a forged `shop` header to make `ShopifyAPI::Webhooks::Registry.process` accept and dispatch an event that appears to originate from a different (victim) shop.

### Finding Description
`Utils::HmacValidator.validate` computes the expected signature from `verifiable_query.to_signable_string` and compares it to the `hmac` value on the object: [1](#0-0) 

For webhook requests, `to_signable_string` returns only the raw request body: [2](#0-1) 

The `shop` accessor, however, is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is **not** part of the signed content: [3](#0-2) 

`Registry.process` validates the HMAC of the request and then trusts `request.shop` to construct `WebhookMetadata` that is handed to the app's registered handler, with no additional check that the shop matches the tenant the HMAC secret is scoped to: [4](#0-3) 

Because `Context.api_secret_key` is a single, app-wide secret shared by every shop that installs the app (it is not per-shop), a genuine webhook delivery to a shop the attacker legitimately controls (or has otherwise obtained) yields a body + HMAC pair that is valid for **any** shop value. Replaying that same body/HMAC pair with a different `X-Shopify-Shop-Domain` header value passes `HmacValidator.validate` unchanged, because the header is never part of `to_signable_string`. This breaks the intended identity binding: `shop that produced the valid signature == shop asserted to the handler`, and instead only proves `body signed by the app's shared secret == body received`, with the tenant identity left completely attacker-controlled.

### Impact Explanation
This is a cross-tenant access vulnerability (Critical, per the provided impact classes). Any application that uses `request.shop` from `WebhookMetadata` to select which tenant's records to update, credit, cancel orders for, sync inventory, deactivate subscriptions, etc., can be made to apply a legitimately-signed payload to an arbitrary victim shop. An attacker who installs the app on their own store (a normal, unprivileged action for any public Shopify app) can trigger events on their own shop, capture the resulting webhook body/HMAC, and replay it against the app's public webhook endpoint with a spoofed `shop` header pointing at any other installed shop, causing the handler to act as if the victim shop generated the event.

### Likelihood Explanation
Likelihood is high for any app that: (1) is public / installable by arbitrary merchants (so the attacker can generate a legitimately signed webhook for a shop they control), and (2) has a webhook endpoint reachable over the internet, which is required for Shopify webhook delivery in the first place. No access token, `client_secret`, or privileged account is required — only the ability to install the app on one's own store or otherwise capture a single legitimate webhook delivery.

### Recommendation
Bind the shop identity into the HMAC-verified content, or otherwise cryptographically tie the header-derived `shop` to the validated payload before trusting it. Concretely:
- Include `shop` (and ideally `topic`/`webhook_id`) inside `to_signable_string` for `Webhooks::Request` so a replayed body cannot be paired with a different shop header, or
- Independently corroborate `request.shop` against a per-shop secret/registration (e.g., verify the shop is an installed session with an active access token) before invoking the handler, rather than trusting the header value directly.

### Proof of Concept
1. Attacker installs the target public app on their own store `attacker.myshopify.com`, triggering any webhook topic the app subscribes to (e.g. `orders/create`).
2. Shopify sends the webhook to the app's endpoint with headers including:
   - `X-Shopify-Hmac-Sha256: <hmac over raw body, using the app's shared api_secret_key>`
   - `X-Shopify-Shop-Domain: attacker.myshopify.com`
   - raw JSON body `B`
3. Attacker captures `B` and the valid `X-Shopify-Hmac-Sha256` value.
4. Attacker resends the exact same body `B` and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `@raw_body` (identical to the legitimate delivery) — see `to_signable_string` at `lib/shopify_api/webhooks/request.rb:35-38`.
6. `Registry.process` builds `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: ..., ...)` and invokes the app's handler as though the event came from `victim.myshopify.com`, per `lib/shopify_api/webhooks/registry.rb:188-200`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
