### Title
Unrestricted `EmporiumOperation.endpoint`/`callData` lets an attacker plant a persistent ERC20 approval and drain the Emporium's stranded/in-flight token balance outside Hinkal's invariant checks - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction` executes attacker-supplied `EmporiumOperation.endpoint`/`callData` (`op.endpoint.call{value: op.value}(op.callData)`) against **any** target with **no allowlist**, and the only safety net (`balanceChange`/`BalanceChangeShouldBePositive`) only covers tokens the attacker chooses to list in `circomData.erc20TokenAddresses`. An attacker can use one legitimate `Hinkal.transact` call to make the Emporium contract `approve()` an attacker-controlled address for an unlisted token, then later drain any balance the Emporium happens to hold of that token (dust, slippage overage, another user's in-flight/parked funds) with a plain `transferFrom`, entirely outside `Hinkal.transact` and its balance/UTXO accounting.

### Finding Description
The invariant the question requires is: *tokens leaving an action in a tx == -deltaAmountChanges Hinkal sent it that tx*. This is enforced only for the tokens present in `circomData.erc20TokenAddresses`, via: [1](#0-0) 

But the `ops` loop that actually performs external calls is unconstrained — `op.endpoint` and `op.callData` come straight from `externalActionMetadata`, which is attacker-controlled, and the only guard is against `callHinkalWallet`/`doSendToRelay` selectors, not against the target address or the function being called: [2](#0-1) 

There is no requirement that a token touched by an op appear in `circomData.erc20TokenAddresses`. An attacker can:

1. Submit a valid `Hinkal.transact` call to Emporium with `erc20TokenAddresses` containing only a dummy/zero-amount token (or none related to the target token), and `stack.ops = [{ endpoint: victimToken, callData: abi.encodeCall(IERC20.approve, (attackerAddr, type(uint256).max)) }]`. Since `msg.sender` for that call is the Emporium contract itself, this sets `victimToken.allowance(Emporium, attackerAddr) = max`. This approval is never reset/cleared and outlives the transaction.
2. Because `victimToken` is not in `erc20TokenAddresses`, the `balancesBefore`/`balancesAfter` diff and `BalanceChangeShouldBePositive` check never look at it — the approve-planting transaction passes with no balance-diff constraint on that token at all.
3. At any later time the Emporium contract holds any balance of `victimToken` — which the code's own comment acknowledges is an expected, standing condition ("the only case when balanceChange can be < 0, when there were some funds on emporium before the call"), i.e., the contract is designed to park/carry balances across transactions (dust, slippage residue, partially-consumed deposits, other users' in-flight funds) — the attacker calls `victimToken.transferFrom(Emporium, attackerAddr, balance)` directly on the token contract. This bypasses `Hinkal.transact` entirely (no proof, no nullifier, no root check, no `balanceDif == amountChanges + utxoAmount` equation), so none of the guards listed in the question (`performHinkalChecks`, `verifyProof`, `rootHashExists`, the balance/slippage requires, `insertNullifiers`) are even invoked for the theft transaction.

The "many batches old root" detail in the question does not add a blocking constraint: `MerkleBase.rootHashExists` accepts any historically-recorded root indefinitely, with no expiry/pruning, so the attacker's setup transaction can use a fresh or old-but-valid root — it does not change the exploit and is not what prevents it. [3](#0-2) 

### Impact Explanation
Any balance the Emporium contract holds for a token that an attacker previously targeted with a planted `approve()` op can be permanently stolen by that attacker at will. Since Emporium is explicitly designed to park protocol/user funds mid-flight between the `deltaAmountChanges` transfer-in and the ops' consumption (per the contract's own `BalanceChangeShouldBePositive` comment), this is direct theft of shielded/in-flight user funds — Critical impact. The attack is repeatable for every ERC20 token the Emporium ever touches and requires only one cheap setup transaction per token/spender pair.

### Likelihood Explanation
- Precondition: the attacker must get one `Hinkal.transact` call to Emporium accepted with an `approve()` op on the target token — this requires no special role, just a valid proof for the attacker's own (even zero-value) UTXO.
- No allowlist restricts `EmporiumOperation.endpoint`, so any ERC20 (or any contract) can be targeted.
- Any residual/parked balance appearing later (which the code explicitly anticipates can exist) is then drainable with a single, ungated `transferFrom` call.
- Cost to the attacker is minimal (gas + one small deposit/proof); the attack is fully repeatable and can be pre-staged against every token the Emporium might ever hold.

### Recommendation
- Restrict `EmporiumOperation.endpoint` to a governance-maintained allowlist of trusted routers/protocols, and/or forbid `approve`/`increaseAllowance`-style selectors to arbitrary spenders.
- Require any approval granted during an op to be revoked (reset to 0) by the end of `runAction`, or use one-shot `permit`/exact-amount patterns instead of persistent unlimited approvals.
- Extend the balance-diff safety check to cover every token touched by any op (not just `circomData.erc20TokenAddresses`), or disallow ops from interacting with tokens outside that list.
- Ensure Emporium never carries a standing balance across transactions that isn't cryptographically tied to a specific pending claim (e.g., escrow accounting keyed by commitment, not raw `balanceOf`).

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable`, a mock ERC20 `victimToken`, and mint/transfer some `victimToken` balance directly to the Emporium contract to simulate residual/parked funds (e.g., from a prior legitimate swap's slippage overage).
2. As attacker EOA, construct a valid `CircomData`/proof for a `Hinkal.transact` call to Emporium with `erc20TokenAddresses` = `[dummyToken]` (unrelated to `victimToken`), `amountChanges = [0]`, and `externalActionMetadata` encoding an `EmporiumStack` with one stateless op: `{ endpoint: victimToken, callData: abi.encodeCall(IERC20.approve, (attacker, type(uint256).max)), value: 0 }`.
3. Call `Hinkal.transact` with this data; assert it succeeds and `victimToken.allowance(address(emporium), attacker) == type(uint256).max`.
4. As attacker, directly call `victimToken.transferFrom(address(emporium), attacker, victimToken.balanceOf(address(emporium)))` (no interaction with `Hinkal.transact`).
5. Assert: before step 4, `victimToken.balanceOf(address(emporium)) == residualAmount` and `deltaAmountChanges` for that transaction never referenced `victimToken`; after step 4, `victimToken.balanceOf(attacker) == residualAmount` while `-deltaAmountChanges` Hinkal ever sent the attacker for `victimToken` == 0 — proving tokens left the Emporium action uncounted by any `-deltaAmountChanges`/`amountChanges` equation.
