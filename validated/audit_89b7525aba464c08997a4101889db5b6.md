### Title
Legacy (pre-`validUntil`) `IntentGatewayV2` deployments have no expiry on signed solver `fillOrder` bids, enabling stale-price fund extraction from solvers - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
The current `IntentGatewayV2.fillOrder` enforces `options.validUntil` so a solver's signed bid cannot be executed after it goes stale [1](#0-0) . That protection does not exist in the legacy implementation still live on numerous chains today (`0x976b268b06f545c4a2bf44866aa2465bd8b3c67d`), whose `FillOptions` shape has no `validUntil` field at all [2](#0-1) . Any unprivileged relayer/bundler holding a previously signed solver bid can submit `fillOrder` for that bid at an arbitrary later block once market rates have moved, extracting value from the solver's escrowed outputs with no bound.

### Finding Description
`fillOrder` on the current implementation checks the fill's own validity window and reverts `FillExpired` once passed [1](#0-0) , and the `FillExpired` error/rationale is documented as protecting against exactly this scenario [3](#0-2) .

This check was added specifically because a solver's signed bid, once broadcast to the coprocessor/bid pool, cannot be retracted and stays executable indefinitely until this field was introduced [4](#0-3) .

However, the fix only exists in the *new* selector/shape (`0xa5470064`); the pre-existing implementation (selector `0x5cfb1ea5`) has `FillOptions` = `{relayerFee, nativeDispatchFee, outputs}` with no `validUntil` member and no corresponding revert path [5](#0-4) . The SDK explicitly tracks that this legacy implementation is still the live bytecode behind the ERC-1967 proxy on many chains [6](#0-5) , and lists chains whose gateway has not been redeployed at all [7](#0-6) . Because these are real proxy implementations (not test mocks), the missing field/check is a property of the deployed bytecode on those chains, not merely an SDK encoding detail.

The upgrade path off this implementation requires a host-gated governance `Execute`/`UpgradeContract` action dispatched from the intents-coprocessor pallet [8](#0-7)  — an operational migration, not an automatic fix, so the exposure persists until each chain is individually migrated.

### Impact Explanation
`fillOrder` is fully permissionless — anyone holding the ABI-encoded calldata for a previously-signed bid can submit it [9](#0-8) . On a chain still running the legacy implementation, a solver's price quote (encoded as calldata, signed once, and handed to a relayer/bundler as part of normal solving) remains executable forever with no on-chain mechanism to expire it. An unprivileged holder of that calldata can withhold it and later submit it once the market has moved against the solver, forcing the solver's committed output tokens to be paid out at a stale, unfavorable rate — exactly the fund-safety gap the `validUntil`/`FillExpired` mechanism was built to close on the upgraded implementation. This is a concrete, reachable loss of solver funds on every chain not yet migrated off the legacy implementation, matching the report's structure of a defect confined to the "v1" deployment that persists until users/operators move off it.

### Likelihood Explanation
Medium-High. No special privilege is required: capturing a solver's signed bid is a normal part of the coprocessor/bidding flow (bids are broadcast for aggregation), and resubmitting stale calldata is a single unprivileged `fillOrder` transaction. The only precondition is that the target chain's `IntentGatewayV2` proxy still resolves to the legacy implementation, which the SDK's own tracked lists confirm is the case for a substantial set of chains as of the current codebase [10](#0-9) .

### Recommendation
Complete the governance `Execute`/`UpgradeContract` migration on every remaining chain still resolving to the legacy implementation, removing each chain only from `LEGACY_FILL_OPTIONS_IMPLEMENTATIONS`/`CHAINS_WITHOUT_VALID_UNTIL` once migrated [10](#0-9) . Until migrated, solvers/integrators should treat bids destined for a legacy-implementation chain as having unbounded validity and price that risk explicitly, since the contract itself provides no bound.

### Proof of Concept
1. A solver signs an ERC-7821 batch containing a `fillOrder` call for order `O` against a proxy whose ERC-1967 implementation slot resolves to `0x976b268b06f545c4a2bf44866aa2465bd8b3c67d` [11](#0-10) , quoting a fair rate at signing time, using the v1 `FillOptions` shape with no expiry field [2](#0-1) .
2. A relayer/bundler receiving this calldata withholds submission instead of relaying it promptly.
3. Blocks later, the output asset's market rate moves against the solver.
4. The relayer submits the unchanged calldata to `intentGateway.fillOrder(order, options)`. On the legacy implementation there is no `validUntil`/`FillExpired` check to reject it (unlike the fixed behavior demonstrated by `testFillOptions_ValidUntil_RevertsOnceElapsed` on the current implementation [12](#0-11) ), so the fill executes at the stale price, extracting value from the solver.

    function fillOrder(Order calldata order, FillOptions calldata options) public payable nonReentrant {
        uint256 blockNumber = _blockNumber();
        if (order.deadline < blockNumber) revert Expired();
        // The solver's own bound on how long its quoted price stands. Zero means unbounded,
        // which is the right default for a solver filling directly — it is only at risk from
        // its own staleness. It matters for a bid signed through the coprocessor, where the
        // order placer chooses the moment of execution and nothing else caps the wait.
        if (options.validUntil != 0 && blockNumber > options.validUntil) revert FillExpired();
        bytes32 commitment = keccak256(abi.encode(order));

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain && orderSource != currentChain) revert WrongChain();
        if (!isSameChain && orderDest != currentChain) revert WrongChain();

        if (_filled[commitment] != address(0)) revert Filled();

        if (_params.solverSelection) {
            bytes32 storedSelectionHash;
            assembly {
                storedSelectionHash := tload(commitment)
            }

            bytes32 expectedSelectionHash = keccak256(abi.encode(msg.sender, order.session));
            if (storedSelectionHash != expectedSelectionHash) revert Unauthorized();
        }

        uint256 outputsLen = order.output.assets.length;
        if (options.outputs.length != outputsLen) revert InvalidInput();
        if (order.inputs.length != outputsLen) revert InvalidInput();

        if (isSameChain) {
            _fillSameChain(order, options, commitment);
        } else {
            _fillCrossChain(order, options, commitment);
        }
    }

    function testFillOptions_ValidUntil_RevertsOnceElapsed() public {
        uint256 inputAmount = 1000 * 1e6;
        uint256 outputAmount = 900 * 1e18;
        Order memory order = _placeSameChainOrder(inputAmount, outputAmount, 0);

        uint256 validUntil = block.number + 10;
        vm.roll(validUntil + 1);

        vm.startPrank(solver);
        dai.approve(address(intentGateway), outputAmount);

        solverOutputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: outputAmount});

        // The order itself is still well inside its deadline — only the quote has gone stale.
        vm.expectRevert(IntentsBase.FillExpired.selector);
        intentGateway.fillOrder(
            order, FillOptions({relayerFee: 0, nativeDispatchFee: 0, validUntil: validUntil, outputs: solverOutputs})
        );
        vm.stopPrank();
