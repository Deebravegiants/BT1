### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying an HMAC over the raw request body, then trusts the `shop-domain` header — which is *not* covered by that HMAC — as the tenant identity for the whole request. This is the same class of bug as the LSP0 report: a pre-check ("HMAC verifies the request") is treated as authorizing an action (processing data as belonging to shop X) even though the acted-upon field (`shop`) was never bound into what was verified.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC exclusively over that signable string (the body) and compares it to the `hmac-sha256` header: [2](#0-1) 

The `shop` attribute consumed by application code, however, is read straight from an independent, unauthenticated header, with no cryptographic tie to the HMAC: [3](#0-2) 

`Registry.process` validates only the body HMAC and then forwards `request.shop` (and `request.topic`) directly to the app's handler as trusted tenant identity, without any check binding `shop` to the verified bytes: [4](#0-3) 

Because the HMAC is computed with the app's single `api_secret_key`, which is identical for every shop that has installed the app, any body that was legitimately signed for **one** installation (e.g., a webhook the attacker's own shop received after installing the same public app) carries a valid HMAC regardless of which shop it was originally destined for. An attacker who controls a shop that has the app installed can:
1. Trigger any webhook event on their own shop and capture the resulting `(raw_body, hmac-sha256)` pair — a valid signature under the shared `api_secret_key`.
2. Replay that exact body/HMAC to the app's webhook endpoint, but substitute the `X-Shopify-Shop-Domain` header with a **victim** shop's domain.
3. `HmacValidator.validate` still succeeds (it never looked at the shop header), so `Registry.process` invokes the handler with `WebhookMetadata.new(..., shop: <victim shop>, body: <attacker-influenced body>, ...)`.

This breaks the intended identity equality `verified_signer(raw_body) == shop_the_handler_believes_sent_it`; the HMAC proves "Shopify signed this body for *some* install of this app," not "Shopify signed this body *for this shop*."

### Impact Explanation
This is a cross-tenant data-integrity/confusion issue: a merchant/tenant using the app can cause the app to process fabricated events *as if* they belong to a different merchant. Depending on how the host application's webhook handlers act on `data.shop` (e.g., updating that shop's local records, billing state, inventory sync, deletion flows for `shop/redact` topics, etc.), this can lead to cross-tenant data corruption or unauthorized state changes attributed to a shop the attacker does not control — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitability only requires the attacker to be able to install the target app on a shop they control (trivial for any public app) and to control the exposed webhook HTTP endpoint's headers, which any unprivileged internet client can freely set when POSTing to the app's public webhook route. No access token, `api_secret_key`, or privileged account is required.

### Recommendation
Bind the shop identity into the verified material: include the `shop-domain` (and ideally `topic`/`webhook-id`) value in the HMAC-signed content the library checks (Shopify already sends the same body for `X-Shopify-Hmac-Sha256`, but the library should separately record/verify that the shop asserted in the header matches a shop known to be associated with this app instance/session before dispatching), or otherwise document/enforce that `WebhookMetadata#shop` must not be trusted as tenant-scoping without an out-of-band check against the caller's own session/shop registry.

### Proof of Concept
```ruby
# Attacker controls "attacker-shop.myshopify.com" (a real install of the target app)
raw_body = '{"id": 123, "note": "attacker-controlled"}'
hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
)
# ^ Attacker cannot compute this themselves, but Shopify legitimately sends it for
#   any real event on the attacker's own installed shop, so the attacker captures it.

forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => hmac,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # <-- swapped, not covered by hmac
  "x-shopify-webhook-id" => "forged-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) returns true (only raw_body is checked),
# and the registered handler is invoked with shop: "victim-shop.myshopify.com".
```

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
