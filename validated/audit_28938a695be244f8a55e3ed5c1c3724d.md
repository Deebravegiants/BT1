### Title
Emporium output funds routed to attacker-chosen `stealthAddressStructure` never authorized by wallet owner's signature - (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction`/`handleOut` wraps whatever ERC20/ETH balance appears on the Emporium contract after executing a wallet owner's signed `EmporiumStack` ops into a brand-new `UTXO` using `circomData.stealthAddressStructure` verbatim [1](#0-0) . `verifyWallet`'s EIP-712 digest (`EMPORIUM_SIGNATURE_TYPEHASH`) only commits to `message`, `ops`, `maxFee`, `deadline` — never to `stealthAddressStructure` — so anyone who obtains a validly-signed `EmporiumStack` (which is designed to be relayed by an arbitrary submitter) can submit it themselves via `Hinkal.transact()` with their own ZK proof and their own recipient key material, redirecting the resulting output UTXO to themselves.

### Finding Description
The claimed broken equality is: `recipient(outUtxo.stealthAddressStructure) == recipient the wallet owner's ops[] intended to receive balanceChange`. Tracing the code shows nothing enforces this.

- `EmporiumUpgradeable.runAction` executes `stack.ops` (signed by `stack.signerAddress` per `verifyWallet`) and computes `balanceChange` from the Emporium contract's before/after balances [2](#0-1) .
- `handleOut` then builds the new `UTXO` directly from `circomData.stealthAddressStructure` — a field supplied by whoever calls `Hinkal.transact()`, not derived from `stack.signerAddress` or any recipient the owner named [1](#0-0) .
- `verifyWallet`'s signed payload is `EMPORIUM_SIGNATURE_TYPEHASH(message, ops, maxFee, deadline)` — `stealthAddressStructure` is absent from both the EIP-712 typehash and the encoded struct [3](#0-2) .
- The ZK circuit's per-transaction stealth-address block (`StealthAddressCalculator` in `MainEVMCircuit.circom`) derives `outStealthAddress` purely from the *prover's own* `spendingPublicKey`/`nullifyingPrivateKey` and an externally supplied `H0Ax`/`H0Ay` [4](#0-3) ; the same `spendingPublicKey` also authenticates the EdDSA signature over `signedMessageHash` [5](#0-4) . Since the prover freely picks their own keypair, this proves nothing about the *intended recipient of the Emporium output* — it only proves the prover controls whatever key they plugged in, which can be their own.
- `CircomDataBuilder.formBasicInput` feeds `circomData.stealthAddressStructure.{H1x,H1y,stealthAddress,H0x,H0y}` straight into the public input vector [6](#0-5)  and lines 236-237, so `verifyProof` only checks internal consistency of the caller's own chosen values — never that they match the wallet owner's expected recipient.
- `Hinkal.transact()` allows any EOA to submit directly: `performHinkalChecks` accepts `originalSender == msg.sender && relay == address(0)` [7](#0-6) , and `relayerIsValid` is a no-op when `relay == address(0)` [8](#0-7) . `verifyWallet` never checks that `msg.sender`/`circomData.originalSender` equals `stack.signerAddress` — it only recovers the ECDSA signer of the ops payload [9](#0-8) .
- The one balance-conservation check performed in `Hinkal.sol` (`balanceDif == (onChainCreation? 0 : amountChanges[i]) + utxoAmount`) only checks totals, never the recipient field of the UTXO [10](#0-9) .

Attack flow: the wallet owner signs an `EmporiumStack` (e.g., authorizing a swap/DeFi op sequence) intending resulting funds to return to their own shielded balance. The attacker, an unprivileged EOA holding this signed stack (it's designed for permissionless relaying — no restriction ties `msg.sender` to `stack.signerAddress`), calls `Hinkal.transact()` directly (`relay = address(0)`, `originalSender = attacker`), submitting a self-generated valid ZK proof over a fresh keypair, and sets `circomData.stealthAddressStructure` to values derived from their own `spendingPublicKey`/`nullifyingPrivateKey`. The owner's ops execute exactly as signed (the ops themselves are unaffected), but the resulting `balanceChange` UTXO is created under the attacker's stealth address instead of the owner's, and the attacker later opens/spends it with their own `nullifyingPrivateKey`.

### Impact Explanation
This is theft of funds resulting from a wallet owner's own authorized on-chain actions (swaps, DeFi calls) executed through Emporium — the wallet owner's assets/output value are diverted to an address the owner never approved, matching "Critical - direct theft of shielded ... user funds" / "executing calls or moving assets a wallet owner ... never authorised." It is repeatable for every `EmporiumStack` submission the attacker can intercept or is given to relay, and the attacker only needs to be the party who calls `transact()` — no privileged role required.

### Likelihood Explanation
Preconditions: a signed `EmporiumStack` must exist that results in a positive `balanceChange` at Emporium (e.g., a swap or wallet call that leaves proceeds on the Emporium contract) — this is the normal, expected use case for Emporium, not an edge case. The attacker needs to be able to submit the `transact()` call (feasible since no relay-whitelisting is required when `circomData.relay == address(0)` and `originalSender == msg.sender`), and needs to be the entity who has access to the signed stack — which, by design, is meant to be broadcastable/relayable, since `verifyWallet` never binds `msg.sender` to `stack.signerAddress`. Attacker cost is a single proof generation with a self-chosen keypair, easily reproducible.

### Recommendation
Bind the destination of Emporium-generated output UTXOs to the wallet owner's authorization: include a wallet-owner-approved recipient/stealth-address commitment (or the `stack.signerAddress`'s designated public spending key) inside `EMPORIUM_SIGNATURE_TYPEHASH`, and have `verifyWallet`/`handleOut` enforce that `circomData.stealthAddressStructure` matches that signed value before constructing `outUtxo`. Alternatively, require the caller of `transact()` for Emporium-external actions to equal `stack.signerAddress` (or a value it explicitly delegates), removing the ability of a third-party submitter to redirect proceeds.

### Proof of Concept
Foundry fork test outline:
1. Deploy `Hinkal`, `EmporiumUpgradeable`, register it as external action, deploy a mock DEX/target for ops.
2. As "owner", sign an `EmporiumStack` (`ops` = swap call moving owner's Emporium-held tokens into an output token, `maxFee`, `deadline`) via `_hashTypedDataV4(EMPORIUM_SIGNATURE_TYPEHASH,...)`.
3. As "attacker" (different EOA, no privileged role), generate a fresh EdDSA keypair and a local ZK proof for `MainEVMCircuit`/Emporium's verifier circuit, setting `circomData.stealthAddressStructure` derived from the attacker's own keys (`H0x/H0y` chosen, `H1x/H1y/stealthAddress` computed via `StealthAddressCalculator` with attacker's `spendingPublicKey`/`nullifyingPrivateKey`), `circomData.externalActionData.externalActionMetadata = abi.encode(stack)` (owner's signed stack), `relay = address(0)`, `originalSender = attacker`.
4. Call `Hinkal.transact(a,b,c,dimensions,circomData)` from the attacker address.
5. Assert: (a) `stack.ops` executed successfully using the owner's authorization; (b) the resulting `UTXO`/on-chain commitment inserted into the tree carries `circomData.stealthAddressStructure` equal to the attacker's, not any value derivable from the owner; (c) attacker can later call `transact()` again presenting a valid nullifier/proof using their own `nullifyingPrivateKey` to spend this UTXO and withdraw the funds, while the owner has no nullifying key matching it — proving `recipient(outUtxo) != owner`, i.e., the equality claimed in the question is indeed broken.

        int256 balanceChange,

    function verifyWallet(
        EmporiumStack memory stack,
        CircomData calldata circomData
    ) internal {
        EmporiumStorageVars storage $ = _getEmporiumStorage();

        if ($.usedMessages[circomData.emporiumMessage]) {
            revert UsedMessage();
        }

        $.usedMessages[circomData.emporiumMessage] = true;

        if (stack.signerAddress == address(0)) {
            return;
        }

        bytes32 hashedMessage = _hashTypedDataV4(
            keccak256(
                abi.encode(
                    EMPORIUM_SIGNATURE_TYPEHASH,
                    circomData.emporiumMessage,
                    _hashEmporiumOps(stack.ops),
                    stack.maxFee,
                    stack.deadline
                )
            )
        );

        (address recoveredAddress, ECDSA.RecoverError err) = ECDSA.tryRecover(
            hashedMessage,
            stack.v,
            stack.r,
            stack.s
        );
        bool verified = err == ECDSA.RecoverError.NoError &&
            recoveredAddress == stack.signerAddress;
        if (!verified) {
            revert InvalidSignature();
        }

        if (block.timestamp > stack.deadline) {
            revert SignatureExpired();
        }

        if (circomData.feeStructure.flatFee > stack.maxFee) {
            revert FeeExceedsSignedMax();
        }
    }
