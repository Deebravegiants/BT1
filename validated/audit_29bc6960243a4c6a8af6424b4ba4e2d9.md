## Title
Missing shop-domain validation in `exchange_token` allows SSRF with the app's `client_id`/`client_secret` - ([File: lib/shopify_api/auth/token_exchange.rb])

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the destination host it will send the app's `client_id`/`client_secret` to directly from the unvalidated `dest` claim of a caller-supplied JWT `session_token`, unlike every sibling credential-issuing method in the same module (`migrate_to_expiring_token`) and in `client_credentials.rb`/`refresh_token.rb`, which all call `Utils::ShopValidator.sanitize!` on the shop before using it to build the outbound host.

### Finding Description
This mirrors the report's "evergrowing array" bug class in spirit: a value is used for one purpose (building request/host state) but is not subjected to the same validation/consistency check that the rest of the code path applies elsewhere — an identity binding is broken. Here the binding that should hold is:

`host used to receive client_secret == host validated as a trusted Shopify domain`

In `exchange_token`, `dest_shop = jwt_payload.shop` is taken straight from `JwtPayload#shop`, which is just `@dest.gsub("https://", "")` [1](#0-0) . `JwtPayload#initialize` only checks `aud == Context.api_key` and standard JWT exp/nbf checks; it performs no validation that `dest` is a real `*.myshopify.com` (or otherwise trusted) domain [2](#0-1) . `dest_shop` is then used unsanitized to build `shop_session` and, through `Clients::HttpClient`, the request host that will carry `client_id`/`client_secret` in the POST body [3](#0-2) . `Clients::HttpClient#initialize` builds `@base_uri` from `session.shop` verbatim (`"https://#{api_host || session.shop}"`), with no domain restriction of its own [4](#0-3) .

Contrast this with the sibling method in the very same file, `migrate_to_expiring_token`, which explicitly calls `validated_shop = Utils::ShopValidator.sanitize!(shop)` before constructing the session and sending the credentialed request [5](#0-4) , and with `refresh_access_token` and `client_credentials`, which do the same [6](#0-5) [7](#0-6) . `ShopValidator.sanitize!` restricts the resulting host to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) or an app-declared `myshopify_domain` [8](#0-7) ; `exchange_token` skips this check entirely.

Because `JwtPayload` decodes the token with `HS256` and the app's own `api_secret_key`/`old_api_secret_key` [9](#0-8) , this specific gap is only reachable by a party that can produce a validly-signed session token bound to this app's `aud` — i.e. it requires knowledge of the shared secret or a genuine Shopify-issued token whose `dest` claim value the host application does not otherwise constrain. The gem's own comment at line 39 states "use the shop from the token's `dest` claim" with no accompanying sanity check, so any caller integration that passes through a session token without additional shop pinning inherits an outbound-request host that isn't confirmed to be a Shopify-controlled domain.

### Impact Explanation
If `dest` can be influenced to a non-Shopify host, the library will `POST` a JSON body containing the app's `client_id` and `client_secret` to that attacker-controlled host — an SSRF that exfiltrates the app's `client_secret`, matching the High/Critical impact bar (SSRF with the app's credentials / credential theft). This is a straightforward missing-invariant bug, exactly analogous to the report's core lesson: a security-relevant identity check applied in the rest of the code path around a construct is dropped in one execution branch.

### Likelihood Explanation
Likelihood is constrained by the fact that `JwtPayload` requires a validly HS256-signed token with the correct `aud`, which normally means it originates from Shopify. However, this is the only outbound-credentialed-request path in `lib/shopify_api/auth/*` that omits the `ShopValidator.sanitize!` call that all of its siblings apply, making it an inconsistent, latent trust boundary that is easy to overlook when the token's origin/validation assumptions change (e.g., leeway/old-secret fallback paths, or host apps that construct/relay tokens).

### Recommendation
Apply `Utils::ShopValidator.sanitize!(dest_shop)` (or equivalent) to the `dest` claim in `exchange_token` before constructing `shop_session`/`Session.from`, mirroring `migrate_to_expiring_token`, `refresh_access_token`, and `client_credentials`, so the host that receives `client_id`/`client_secret` is always constrained to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

### Proof of Concept
1. Obtain/construct a JWT `session_token` correctly signed with the app's `api_secret_key`/`old_api_secret_key` and with `aud == Context.api_key`, but with `dest` set to `https://attacker.example.com` [2](#0-1) .
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. `dest_shop` resolves to `attacker.example.com` unchecked [10](#0-9) .
4. `Clients::HttpClient` sends the POST containing `client_id`/`client_secret` to `https://attacker.example.com/admin/oauth/access_token` [4](#0-3) , leaking the app's credentials to the attacker's server.
