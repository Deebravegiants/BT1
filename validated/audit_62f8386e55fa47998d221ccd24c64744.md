### Title
Reuse of previously-validated operator QR code/session without re-checking operator active status before signup - (File: src/plans/mod.rs)

### Summary
`scan_remaining_qr_codes` reuses a cached `operator_data` from an earlier `verify_operator_qr_code()` call across multiple signup iterations as long as it hasn't expired by a wall-clock timer, without re-verifying with the backend that the operator is still active/valid at the time the signup actually proceeds. This mirrors the reported `StakingManager._distributeStake()` bug class: an action is authorized against a previously-fetched status flag ("delegation target"/"operator valid") instead of confirming the current, live state before committing user data/resources.

### Finding Description
The `MasterPlan::scan_remaining_qr_codes` function only calls the backend `verify_operator_qr_code` (which hits `backend::operator_status::request`) when the cached `operator_data.timestamp` has expired according to `operator_qr_expiration_time`: [1](#0-0) 

If the timestamp is still within the expiration window, the branch short-circuits straight to `ResolvedQrCodes` without any additional backend call to confirm the operator is still valid/active: [2](#0-1) 

The actual validity check that sets `valid: true`/`false` for the operator happens only once, in `verify_operator_qr_code`, which calls `backend::operator_status::request`: [3](#0-2) [4](#0-3) 

This is structurally identical to the `StakingManager` bug: a resource-authorizing check (`validatorManager.getDelegation()`/operator `valid` flag) is fetched once and then reused for a subsequent privileged action (fund delegation / signup completion) without confirming the checked entity is still in the same state at the time of use. Here, if the operator is deactivated/revoked on the backend (e.g., distributor suspended, fraud detected on operator side) after the initial QR verification but before `operator_qr_expiration_time` elapses, the orb will still treat the operator as authorized to run further signups tied to that operator, because `scan_remaining_qr_codes` and `scan_initial_qr_codes` gate re-verification purely on a local `Instant` timer rather than live backend state.

### Impact Explanation
If an operator's authorization is revoked mid-session (fraud, suspension, distributor account issue), signups can continue to be attributed to and processed under that now-invalid operator identity until the local expiration timer lapses. This can result in misattributed signups being recorded against a de-authorized operator, undermining the operator-authorization control that gates who is allowed to run signups on an orb — directly analogous to the "funds delegated to an inactive validator" impact of unauthorized/misattributed action against a party that is no longer in good standing. Impact is bounded by the length of `operator_qr_expiration_time`, and does not itself leak biometric data or forge attestations — it is an authorization state staleness issue.

### Likelihood Explanation
Likelihood depends on how long `operator_qr_expiration_time` is configured and how quickly backend-side operator deactivation is expected to take effect; I could not fully confirm the configured default value for `operator_qr_expiration_time` since `src/config.rs` (shown to be a documentation-only stub in the excerpts I could load) did not expose it, and I was not able to inspect the concrete default in the time available. This should be verified directly against `src/config.rs`/`src/backend/config.rs` before treating this as high likelihood.

### Recommendation
Before finalizing/using a cached `OperatorData` for a signup (particularly at the start of `do_signup`/`scan_remaining_qr_codes`), re-validate operator status against the backend rather than relying solely on the local timestamp-based expiration check, or shorten the reuse window so it cannot outlive realistic backend revocation propagation.

### Proof of Concept
1. Operator scans an operator QR code; `verify_operator_qr_code` confirms `valid: true` and `OperatorData { timestamp: Instant::now(), .. }` is cached.
2. Within `operator_qr_expiration_time`, the operator's backend status is changed to invalid/suspended (e.g., due to detected fraud).
3. A subsequent signup request reaches `scan_remaining_qr_codes`; because `operator_data.timestamp.elapsed() < operator_qr_expiration_time`, the branch at [5](#0-4)  is taken and no fresh `verify_operator_qr_code`/backend call occurs.
4. The signup proceeds and is recorded/attributed to the now-invalid operator, without the orb ever re-confirming the operator's active status for this signup.

/// Makes a validation request.
pub async fn request(qr_code: &qr_scan::user::Data) -> Result<Status> {
    let request = super::client()?
        .get(format!(
            "{}/api/v1/distributor/{}/orb/{}/status",
            *SIGNUP_BACKEND_URL, qr_code.user_id, *ORB_ID
        ))
        .basic_auth(&*ORB_ID, Some(get_orb_token()?));
    let status: Status = match request.send().await?.error_for_status() {
        Ok(response) => response.json().await?,
        Err(err) => {
            tracing::error!("Received error response {err:?}");
            return Err(err.into());
        }
    };
    if !status.valid {
        tracing::info!(
            "Operator QR-code invalid: {qr_code:?}, reason: {:?}",
            status.reason.as_deref().unwrap_or("<empty>")
        );
        return Ok(status);
    }
