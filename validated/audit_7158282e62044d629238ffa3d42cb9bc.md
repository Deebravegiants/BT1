### Title
Webhook shop attribution bypasses HMAC binding, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then hands the handler a `shop` value that is read from an HTTP header never included in that HMAC computation. Any party who can obtain one genuinely signed webhook (i.e. any merchant who has installed the app) can replay that signed body while substituting an arbitrary `X-Shopify-Shop-Domain` header, and the library will report the request as valid and pass the attacker-chosen shop identity straight through to the handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is populated directly from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic relationship to the HMAC: [2](#0-1) 

`Registry.process` validates the request using only this body-only HMAC, and then immediately forwards `request.shop` — the unauthenticated header value — to the handler as the trusted tenant identifier: [3](#0-2) 

The equality the code implicitly (and incorrectly) assumes is:
`shop_bound_by_hmac == shop_delivered_to_handler`

but in fact:
`shop_bound_by_hmac ∈ {} (nothing — HMAC covers only @raw_body)`
`shop_delivered_to_handler == request.shop (header value, attacker-controlled)`

Because the `shop` field is never part of `to_signable_string`, `Utils::HmacValidator.validate(request)` returning `true` proves only that `@raw_body` was produced with the app's secret at some point — it proves nothing about which shop that body belongs to. A merchant who has legitimately installed the app receives real webhook deliveries with valid HMACs computed over their own event bodies. That merchant can capture one such delivery and re-POST it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to name a different, victim shop that also uses the same app. `HmacValidator.validate` still succeeds (the body/secret pair is genuine), and `Registry.process` calls the handler with `WebhookMetadata.new(shop: request.shop, ...)` reporting the victim's shop as the source of the event.

### Impact Explanation
This breaks the tenant-identity binding the webhook subsystem is supposed to provide: `Registry.process` is the library's canonical authentication boundary for webhooks, and downstream apps are expected to trust `data.shop` from `WebhookMetadata` because the request "passed HMAC validation." Any app logic that keys off `data.shop` to select which merchant's records to mutate, credit, or notify can be made to act on behalf of a different tenant than the one that actually authored the payload — a cross-tenant integrity violation reachable by any user who is a legitimate, unprivileged merchant of the app (no `api_secret_key`, access token, or privileged account required).

### Likelihood Explanation
Likelihood is bounded by the need to first receive one genuine webhook delivery (trivial — any installed merchant continuously receives them) and then replay it with a modified header to the app's public webhook endpoint. No secret material, session, or elevated access is required; the only barrier is the host app's own webhook route being reachable, which is the same reachability the library assumes for the legitimate case.

### Recommendation
1. Never treat the `shopify-shop-domain` header as an authenticated tenant identifier. Bind `shop` into the signable content the HMAC actually covers, e.g. by including the header value in the digest input (mirroring how `Oauth::AuthQuery#to_signable_string` binds `shop` into its own signable string) or by deriving/cross-checking the shop from a field inside the signed JSON body itself.
2. At minimum, document and enforce in `Registry.process` that `request.shop` must be cross-validated by the caller against the specific shop session/registration the webhook was registered for (e.g. via `webhook_id` correlated to a stored registration), rather than trusted as-is.
3. Add a regression test asserting that mutating the shop-domain header on an otherwise valid signed request either fails validation or is not exposed as a trusted value to handlers.

### Proof of Concept
1. App installs webhooks for shop A and shop B (both tenants of the same app, same `api_secret_key`).
2. Shopify delivers a legitimate webhook to the app for shop A: body `B`, header `X-Shopify-Hmac-Sha256: HMAC(secret, B)`, header `X-Shopify-Shop-Domain: shop-a.myshopify.com`.
3. Merchant A (attacker) intercepts/replays this exact request to the app's webhook endpoint, only changing `X-Shopify-Shop-Domain` to `shop-b.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request#hmac` and `#to_signable_string` are computed purely from the untouched body `B`, so `Utils::HmacValidator.validate(request)` returns `true`.
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "shop-b.myshopify.com", body: <shop A's event data>, ...)` — the app now believes shop A's event belongs to shop B.
