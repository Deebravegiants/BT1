Confirmed. The vulnerability is a `hmac(body)` verification vs `shop`/`topic` header parsing binding gap in the webhook processing path.

### Title
Webhook HMAC binds only the request body, not the `shop-domain`/`topic` headers, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC that `ShopifyAPI::Webhooks::Registry.process` validates covers exclusively the JSON body bytes. The `shop`, `topic`, `webhook_id`, and `api_version` values that are subsequently trusted and handed to the app's webhook handler are read straight from unauthenticated HTTP headers, with no cryptographic binding to the signed body.

### Finding Description
`Utils::HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest(sha256, api_secret_key, verifiable_query.to_signable_string)` and compares it to the received signature using `OpenSSL.secure_compare`. [1](#0-0) 
For `Webhooks::Request`, `to_signable_string` is simply the raw body: [2](#0-1) 
Meanwhile `shop`, `topic`, `webhook_id` are all read from headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`) that play no part in the signable string: [3](#0-2) 
`Registry.process` validates the HMAC and then immediately trusts `request.shop`/`request.topic` to route and label the payload for the handler: [4](#0-3) 

The identity binding that should hold is: `hmac_verified_bytes == identity_bytes_used_by_handler`. Here, `hmac` is computed over `body` only, while `shop`/`topic` used to build `WebhookMetadata` (and thus to key any per-tenant lookup/storage the host app performs) are unauthenticated header values — an equality the gem never enforces. This is the same bug class as the C4 finding: a value trusted by downstream logic (`interim_usdc_in`) is not actually equal to the value that was verified (`interim_usdc_out`); here the value trusted by the handler (`shop`) is not covered at all by the value that was verified (`raw_body`'s HMAC).

Because the app's webhook HMAC secret (`api_secret_key`/client secret) is shared across every shop that has the app installed — it is not a per-shop credential — any shop that has legitimately installed the app can:
1. Trigger a real webhook from Shopify to obtain a valid `(raw_body, hmac)` pair (computed with the app's shared secret) for a body they crafted or influenced (e.g., via `orders/create`, `customers/create` payload content they control on their own store).
2. Replay that exact `raw_body` + `hmac-sha256` header directly to the app's public webhook endpoint, but substitute the `X-Shopify-Shop-Domain` header (and optionally `X-Shopify-Topic`) with a victim shop's domain.
3. `HmacValidator.validate` succeeds because it only checks the body bytes against the shared secret, which are unchanged and were legitimately signed by Shopify.
4. `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: attacker_controlled_body, ...)`, i.e., attacker-controlled content now impersonates the victim tenant.

### Impact Explanation
This crosses a tenant boundary using only unprivileged, self-service capability (installing the app on one's own store, or even any external actor holding a single previously-observed valid webhook body/HMAC pair for that app, since the secret is shared and not shop-specific). Any host application that uses `WebhookMetadata#shop` to key per-tenant records (the exact intended usage pattern per `docs/usage/webhooks.md` and `test/webhooks/registry_test.rb`) will process attacker-controlled data under an arbitrary victim shop identity — cross-tenant data injection/confusion.

### Likelihood Explanation
Moderate-to-high: exploitation requires no secrets beyond what any app-installing merchant already legitimately possesses (the ability to generate real webhook deliveries containing attacker-influenced body content), plus the trivial ability to send an arbitrary HTTP POST with forged headers directly to the app's public webhook endpoint (webhook endpoints are internet-reachable by design and this gem provides no origin/IP restriction).

### Recommendation
Bind the header-derived identity fields into the HMAC-verified signable string, or otherwise cryptographically bind `shop`/`topic` to the payload before trusting them (e.g., verify the callback/webhook against Shopify's IP allowlist, or require the host app to independently confirm `shop` is an actually-installed, session-bound tenant before using webhook data) — the header values must not be trusted as tenant identity unless they are covered by the same integrity check as the body.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and registers an `orders/create` webhook.
2. Attacker creates an order with attacker-chosen note/customer fields, causing Shopify to POST a webhook with `X-Shopify-Hmac-Sha256: H` computed over `raw_body B` using the app's shared secret.
3. Attacker captures `B` and `H`, then sends a POST directly to the app's webhook endpoint with headers:
   `X-Shopify-Topic: orders/create`, `X-Shopify-Hmac-Sha256: H`, `X-Shopify-Shop-Domain: victim-shop.myshopify.com`, body `B`.
4. `ShopifyAPI::Webhooks::Registry.process` at [4](#0-3)  validates the HMAC (passes, since it only checks `B`/`H`) and invokes the handler with `shop: "victim-shop.myshopify.com"` and the attacker's `B` as `body`, even though this data never originated from `victim-shop`.
