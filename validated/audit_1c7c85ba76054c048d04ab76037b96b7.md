### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` only validates the HMAC over the raw request **body**, never over the identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`). Those header values are handed to the app's webhook handler unauthenticated, breaking the intended binding `hmac_verified_bytes == data_the_handler_trusts_as_the_tenant_identity`.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string`, and for webhooks that string is defined as the raw body only: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors instead read directly from unauthenticated HTTP headers: [2](#0-1) 

`Registry.process` checks the HMAC (over the body only) and then, on success, builds `WebhookMetadata` straight from those header-derived, unauthenticated fields and dispatches it to the registered handler: [3](#0-2) 

Because Shopify signs webhooks with the app's single `client_secret` (the same secret across all shops/tenants that installed the app), any shop that can trigger a real webhook delivery for itself (e.g. by performing an action on its own store, or via any topic whose payload content an attacker who runs their own installed store can influence) obtains a request with a **valid** HMAC over the body. Nothing stops that same attacker from replaying that request to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a victim shop's domain (and/or a different `X-Shopify-Topic`): `Utils::HmacValidator.validate` still passes because it only checks the body, and `Registry.process` will hand the handler `WebhookMetadata` claiming the data came from the victim's shop. This breaks the equality that should hold — `request.shop` (what the handler trusts as the tenant) must equal `shop_bound_by_hmac` (what Shopify actually attested) — and it does not.

This is the direct analog of the reported bug class: a field that is *acted upon* (the shop identity used to route/attribute webhook data) is not *covered by the authentication check* (the HMAC), exactly mirroring "field acted on but not covered by the HMAC."

### Impact Explanation
An attacker with a legitimate but unprivileged relationship to the app (their own installed shop) can forge webhook deliveries that the app processes as if they originated from a different, victim tenant. Any app logic keyed off `WebhookMetadata#shop` (e.g., updating billing state, provisioning/deprovisioning resources, marking `app/uninstalled`, writing merchant-scoped data) can be triggered for a shop the attacker does not control — this is cross-tenant access/data corruption performed without needing the target's or the app's credentials, matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Moderate-to-high: the attacker only needs their own store to receive one legitimately signed webhook from Shopify (any topic, since the vulnerability is header-based, not content-based) and the ability to POST directly to the app's public webhook endpoint with modified headers — no secrets, tokens, or victim interaction required. The only friction is obtaining one validly-HMAC'd body, which any app-installing merchant can do trivially by triggering events in their own store.

### Recommendation
Bind the identifying headers into the signed material, or otherwise verify them independently of the raw HMAC check:
- Include `shop-domain` (and ideally `topic`/`webhook-id`) in `to_signable_string`, or
- After HMAC validation, independently confirm that the `shop-domain` header corresponds to a shop session/install actually known to the app for a webhook delivery context that is expected for that shop, and reject mismatches, or
- At minimum, document/require host applications to cross-check `shop` against their own installed-shop registry before trusting `WebhookMetadata#shop`, and add that check in `Registry.process` itself so all consumers of this library get consistent protection by default.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers any webhook topic the app subscribes to (e.g. `products/update`), causing Shopify to POST a validly-HMAC-signed body B with headers `X-Shopify-Hmac-Sha256: H(B)`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: products/update`.
2. Attacker captures this request and replays it to the app's public webhook endpoint, changing only `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` (body B and its HMAC header are left untouched).
3. `ShopifyAPI::Webhooks::Request.new` accepts it (all required headers present), `Utils::HmacValidator.validate` succeeds because it only checks `H(B)` against `B`, which is unchanged. [4](#0-3) 
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)`, causing the app to act on victim-shop data/state using attacker-supplied content.
