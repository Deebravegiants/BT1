### Title
EIP-2612 permit front-running griefs `SimplexPaymaster` PERMIT-mode (0x00) UserOps, including the delegation bootstrap - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster` supports a PERMIT mode (byte `0x00`) that executes an EIP-2612 `permit()` call during ERC-4337 paymaster validation, exactly mirroring the `supplyWithPermit()`/`repayWithPermit()` pattern described in the external report. An unprivileged attacker who observes a pending UserOp carrying this mode can extract the `(owner, token, amount, deadline, v, r, s)` fields from `paymasterData` and submit the same permit signature to the token directly, consuming the signer's EIP-2612 nonce before the UserOp lands. This causes `_executePermit` to revert, invalidating the victim's sponsored UserOp.

### Finding Description
`_validatePaymasterUserOp` unconditionally calls `_executePermit(userOp)` whenever `paymasterData[0] == 0x00`: [1](#0-0) 

`_executePermit` parses the mode-0x00 payload and calls `IERC20Permit(tokenAddr).permit(owner, address(this), permitAmount, deadline, v, r, s)`, reverting with `PermitFailed` if the call fails: [2](#0-1) 

The permit's `(v, r, s)` are fully visible in `paymasterData`, which is public calldata once the UserOp is broadcast to a bundler mempool or otherwise observable before inclusion. Because `permit()` uses a single sequential nonce per owner (standard EIP-2612 semantics, same primitive exploited in the original report), anyone can call `token.permit(owner, address(paymaster), permitAmount, deadline, v, r, s)` directly, consuming the nonce. When the original UserOp is subsequently processed, `_executePermit`'s `try` block fails and the whole `_validatePaymasterUserOp` call reverts, so the sponsored UserOp cannot be included.

The SDK's changelog confirms mode `0x00` is deliberately kept as the *sole* zero-native bootstrap mechanism for a solver's *first-time delegation on a chain* — the one op that installs the standing Permit2 allowance every later sponsored op depends on: [3](#0-2) [4](#0-3) 

Repeated front-running of this specific bootstrap op denies a solver's only zero-native path to establish the Permit2 allowance needed for every subsequent sponsored fill/bid/vault-sweep on that chain, exactly matching the griefing pattern in the report: no attacker profit, but real damage (wasted signer gas/attempts, delayed onboarding) to the victim and reliance on the contract's designated bootstrap flow. The contract itself remains "permissionless" and mode `0x00` is documented as usable by any integrator, not only the SDK's scoped flag, so the surface is broader than just the SDK's own usage: [5](#0-4) 

### Impact Explanation
Any unprivileged party monitoring the mempool/bundler for pending UserOps using PERMIT mode `0x00` can invalidate them at will by resubmitting the exposed permit signature directly to the token. Applied against the delegation-bootstrap op, this denies a solver its only no-native path to install the Permit2 allowance required for every later sponsored fill, bid, or token send on that chain — degrading or stalling the solver's participation in intent filling until it funds native gas manually. This is a griefing/DoS on a specific gas-sponsorship code path in `SimplexPaymaster`, not a direct theft of funds (the base `PaymasterERC20`/EntryPoint flow does not charge the sender when paymaster validation reverts), but it can be repeated indefinitely at negligible attacker cost to keep a target solver from bootstrapping a chain.

### Likelihood Explanation
High likelihood of triggerability given a target: the attack requires no special privileges, only observing the `paymasterData` of a pending UserOp (public once submitted to a bundler) and issuing a standard `permit()` call ahead of it — the same mechanics as the referenced Manta report. It is bounded to whichever counterparty chooses to grief a specific solver/chain-bootstrap event, since it must be timed against a specific pending UserOp.

### Recommendation
Before calling `permit()` in `_executePermit`, check the existing allowance and skip the permit call if it already covers `permitAmount`, mirroring the recommendation in the referenced report:
```solidity
if (IERC20(tokenAddr).allowance(owner, address(this)) < permitAmount) {
    try IERC20Permit(tokenAddr).permit(owner, address(this), permitAmount, deadline, v, r, s) {
        emit PermitExecuted(tokenAddr, owner, permitAmount);
    } catch {
        revert PermitFailed(tokenAddr);
    }
}
```
This makes a front-run harmless: if the attacker's `permit()` call already grants the allowance, the victim's UserOp proceeds using the existing allowance rather than reverting.

### Proof of Concept
1. Solver signs an EIP-2612 permit and submits a `PackedUserOperation` to a bundler with `paymasterData = 0x00 || token || permitAmount || deadline || v || r || s` (per `buildPermitMode`, `sdk/packages/simplex/src/services/paymaster/provider/simplex.ts:354-388`).
2. Attacker observes the pending UserOp (bundler mempool or public UserOp relay) and extracts `(owner=userOp.sender, token, permitAmount, deadline, v, r, s)`.
3. Attacker calls `IERC20Permit(token).permit(owner, address(SimplexPaymaster), permitAmount, deadline, v, r, s)` directly, in a transaction that lands before the solver's UserOp.
4. When the bundler includes the original UserOp, `EntryPoint.handleOps` calls `_validatePaymasterUserOp` → `_executePermit`, whose `IERC20Permit.permit` call now reverts (nonce already consumed) → `PermitFailed(tokenAddr)` is thrown, and the sponsored UserOp fails to validate, matching the invalidation demonstrated in the original report's Foundry PoC against `supplyWithPermit`.

    ///      Layout: mode(1) + token(20) + permitAmount(32) + deadline(32) + v(1) + r(32) + s(32) = 150 bytes
    function _executePermit(PackedUserOperation calldata userOp) internal {
        bytes calldata data = userOp.paymasterData();
        if (data.length != 150) revert InvalidPaymasterData(data.length);

        address tokenAddr = address(bytes20(data[1:21]));
        uint256 permitAmount = uint256(bytes32(data[21:53]));
        uint256 deadline = uint256(bytes32(data[53:85]));
        uint8 v = uint8(data[85]);
        bytes32 r = bytes32(data[86:118]);
        bytes32 s = bytes32(data[118:150]);

        address owner = userOp.sender;

        try IERC20Permit(tokenAddr).permit(owner, address(this), permitAmount, deadline, v, r, s) {
            emit PermitExecuted(tokenAddr, owner, permitAmount);
        } catch {
            revert PermitFailed(tokenAddr);
        }
    }

Why the scoping is the whole design. The objection to 2612 is its nonce: one sequential
counter per owner, so two permits signed for the same solver carry the same value and only
one lands. That is fatal for fills, which are the ops that actually run concurrently. It is
free for the delegation, which happens once per chain and provably has no concurrent
sibling — the account is not even delegated yet. Confining the permit to that op keeps the
serialization hazard away from everything that could hit it.

Dropping it outright lost more than it looked. The permit is the only authorization that
needs no prior on-chain state, so it is the only way an account with stablecoins and zero
native can pay for anything. Requiring native dust per chain sounds minor until it is the
operator's first run on a new chain and the failure is "send ETH here" rather than "it
worked".
