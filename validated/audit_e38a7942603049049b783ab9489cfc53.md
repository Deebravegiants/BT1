### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing shop-identity spoofing on otherwise-valid webhook requests - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw request body only, while the `shop` identity used by the registry/handler dispatch comes from an HTTP header that is never included in that signed payload.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, which is not part of `to_signable_string`: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC purely against `verifiable_query.to_signable_string` (i.e. the body) using `Context.api_secret_key`: [3](#0-2) 

`Registry.process` accepts the request once `HmacValidator.validate` passes, and then dispatches to the app's handler using `request.shop` — the unauthenticated header value — as the tenant identity: [4](#0-3) 

The identity binding that should hold is: `hmac == HMAC(secret, raw_body || shop || topic || ...)`, i.e. the shop the handler believes it is processing for should be cryptographically bound to the signature. In this implementation the binding actually enforced is only `hmac == HMAC(secret, raw_body)`; `shop` (and `topic`) are unauthenticated and can be substituted freely by anyone able to produce a request with a validly-signed body for *any* tenant.

Because a merchant/developer who has the app installed on their own store can legitimately receive (or trigger, e.g. via a `shop/redact` GDPR webhook or any subscribed topic) a raw body + valid HMAC pair for their own shop, they can replay that exact body/HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (it never looks at the header), and `Registry.process` calls the handler with `WebhookMetadata.new(..., shop: request.shop, ...)` pointing at the victim shop.

### Impact Explanation
This breaks the tenant/shop identity boundary the HMAC is meant to guarantee. Any app that uses `request.shop` from `WebhookMetadata` to key data access, cache invalidation, session lookups, redaction, or any per-tenant action (which is the documented purpose of this field) can be made to perform that per-tenant action against an attacker-chosen shop while presenting a signature that appears fully valid. Depending on the webhook topic reused (e.g. `shop/redact`, `app/uninstalled`, `customers/data_request`), this can result in cross-tenant data deletion/redaction or state corruption for a shop the attacker does not control — a cross-tenant integrity/availability impact driven purely by a gap in the identity binding enforced by this gem, without needing the app's `client_secret` or any access token.

### Likelihood Explanation
The attacker only needs: (1) the ability to install the app on any store they control (or otherwise legitimately trigger/observe one webhook delivery for a shop, since webhook bodies/HMACs are not secret to the receiving party), and (2) the ability to send an arbitrary HTTP POST with custom headers to the app's public webhook endpoint. No access token, `api_secret_key`, or privileged account is required — this is exploitable by any unprivileged internet user who can install/interact with a single test store and reach the target app's webhook URL.

### Recommendation
Bind `shop` (and `topic`/`api_version`/`webhook_id` if they influence handler behavior) into the value that is HMAC-verified, or independently authenticate the header-derived shop against the shop that Shopify's servers are actually configured/whitelisted to send for that specific webhook subscription, rather than trusting the header value once the body-only HMAC passes.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com` and capture one legitimate webhook delivery (raw body `B` and header `X-Shopify-Hmac-Sha256: H`), e.g. by observing the delivery to the app's registered endpoint.
2. Replay the exact same request to the app's webhook endpoint, keeping `raw_body = B` and `X-Shopify-Hmac-Sha256 = H`, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B) == H` — this still succeeds: [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)`, causing the app to perform the webhook's associated action attributed to `victim-shop.myshopify.com` even though Shopify never sent this event for that shop.
