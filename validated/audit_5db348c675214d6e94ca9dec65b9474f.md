### Title
Webhook `shop-domain` and `topic` headers are not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` implements the `Utils::VerifiableQuery` interface used by `HmacValidator.validate`. Its `to_signable_string` returns only `@raw_body` [2](#0-1) , while `shop`, `topic`, `api_version`, and `webhook_id` are all read from unauthenticated HTTP headers [3](#0-2) . `Registry.process` verifies the HMAC of the body and then immediately trusts these header-derived fields to build `WebhookMetadata`, which is passed to the app's handler as the shop/tenant identity for the event [1](#0-0) .

### Finding Description
The identity binding the gem is supposed to enforce is: `hmac_signed_bytes == bytes_that_determine_shop_identity`. Instead, the equality that actually holds is `hmac_signed_bytes == raw_body_only`, while `data.shop` (the value the host application uses to attribute the webhook to a tenant) comes from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is completely outside the signed payload, per `to_signable_string` [4](#0-3)  and `HmacValidator.validate_signature` [5](#0-4) .

Because a single app installation shares one `Context.api_secret_key` across every merchant shop that installs it, any merchant who legitimately receives a validly-signed webhook (body `B`, hmac `H` computed over `B` with the shared secret) can replay that exact `(B, H)` pair to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value for a different, victim shop. `HmacValidator.validate` will accept it because it only re-computes the HMAC over `B` [6](#0-5) , and `Registry.process` will hand the handler a `WebhookMetadata` claiming the victim shop's identity [7](#0-6) .

### Impact Explanation
This breaks the tenant boundary the HMAC check is meant to enforce: a host application built on this gem's documented API (`Registry.process`) has no way to distinguish an authentic webhook for shop A from a replayed body forged to claim shop B, since the shop field it receives is unauthenticated. Applications that key per-tenant state, orders, or credentials off `WebhookMetadata#shop` can have data written or read under the wrong tenant — a cross-tenant access condition.

### Likelihood Explanation
Exploitation only requires possession of one legitimately-delivered webhook body/HMAC pair for any shop under the same app installation (something any merchant who installs a multi-tenant app naturally receives) and the ability to POST to the app's public webhook route — no `api_secret_key`, access token, or other privileged credential is required.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signed/verified payload (or otherwise cryptographically bind them to the body before verification), so `HmacValidator.validate` fails if any of these header values are altered from what was originally signed by Shopify.

### Proof of Concept
1. App installs on Shop A (attacker-controlled) and Shop B (victim), sharing one `api_secret_key`.
2. Shopify delivers a genuine webhook to the app for Shop A: body `B`, headers including `x-shopify-hmac-sha256: H` (valid HMAC of `B`) and `x-shopify-shop-domain: shop-a.myshopify.com`.
3. Attacker replays `POST` to the same webhook endpoint with the identical body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers, `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H` [8](#0-7) .
5. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "shop-b.myshopify.com", ...)` even though the payload was never signed for Shop B [9](#0-8) .
