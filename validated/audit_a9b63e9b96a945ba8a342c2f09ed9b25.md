### Title
Webhook shop attribution is unauthenticated because `to_signable_string` excludes the `X-Shopify-Shop-Domain` header, letting HMAC-valid webhooks be replayed with an arbitrary `shop` value - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` never verifies the `shop-domain` header. `Webhooks::Registry.process` passes `request.shop` straight into `WebhookMetadata` without ever calling `Utils::ShopValidator.sanitize!`, so the shop attribution handed to the app's webhook handler is fully attacker-controlled while only the body is cryptographically bound.

### Finding Description
The broken binding is: **bytes verified by `HmacValidator.validate` (`request.to_signable_string` == `@raw_body`) != bytes acted on by the handler as the tenant identifier (`request.shop`, from the `shopify-shop-domain`/`x-shopify-shop-domain` header)**.

Trace:
- `to_signable_string` returns `@raw_body` only: [1](#0-0) 
- `shop` is read from `@headers["shopify-shop-domain"] || @headers["x-shopify-shop-domain"]` with a plain `T.cast`, no validation: [2](#0-1) [3](#0-2) 
- `HmacValidator.validate_signature` computes the HMAC over `verifiable_query.to_signable_string` (i.e. the body) and compares against the `hmac-sha256` header — the shop header never enters this computation: [4](#0-3) 
- `Registry.process` validates the HMAC, then hands `request.shop` unsanitized directly into `WebhookMetadata`, which is passed to the app's `handler.handle`: [5](#0-4) 
- `Utils::ShopValidator.sanitize!` exists elsewhere in the gem (used for OAuth-side shop validation) but is never invoked anywhere in the webhook path: [6](#0-5) 

Because Shopify's app `client_secret` is shared across every install of the app, an attacker who installs their own app instance / operates their own development store can legitimately receive genuinely HMAC-signed webhook deliveries for their own store. Since the signature covers only the body, the attacker can resend that exact body to the app's webhook endpoint while substituting an arbitrary value (their own shop, a victim's shop domain, or a bogus string) into `X-Shopify-Shop-Domain`. `HmacValidator.validate` still succeeds because the signable string (the body) is unchanged, and `Registry.process` forwards the attacker-chosen shop value straight to the handler as `WebhookMetadata#shop`.

The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify" and shows the handler trusting `data.shop` directly (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), so the documented contract implies `shop` is authenticated along with the body — it is not. None of the existing guards (`HmacValidator.validate`, `Context.setup?`/`private?`, Sorbet runtime typing) check that `shop` corresponds to the signed payload, and `ShopValidator.sanitize!` is simply never called in this path.

### Impact Explanation
Any host application that uses `request.shop` / `WebhookMetadata#shop` to select which tenant's data to update, which access token/session to reuse, or which merchant record to write into, can be made to attribute attacker-supplied (still validly-signed-by-secret) webhook bodies to an arbitrary shop domain, including another real merchant's domain. This is a cross-tenant data integrity issue: the attacker cannot read another tenant's secrets, but they can cause the application to process their own controlled payload under a victim shop's identity, repeatable for every webhook topic the app subscribes to and for any shop domain string the attacker chooses (subject to how the host app keys off `shop`).

### Likelihood Explanation
Exploitation requires only: (1) the attacker install the target app on their own store to legitimately receive a signed webhook, or otherwise obtain one valid signed body/HMAC pair for the shared `client_secret`, and (2) replay that raw body to the app's webhook endpoint with a modified `X-Shopify-Shop-Domain` header. No credentials, access tokens, or `api_secret_key` are needed beyond what any unprivileged developer/attacker can obtain by installing the app themselves. This is a low-cost, repeatable attack against any app built on this gem's default `Webhooks::Registry.process` flow.

### Recommendation
Bind the shop domain into the signed material or independently validate it before trusting it:
- Have the host app (or the gem, if it retains a mapping) validate `request.shop` against a known/expected value (e.g. the shop tied to the session that registered the webhook) before use, and/or route `request.shop` through `Utils::ShopValidator.sanitize!` to at least ensure it is a well-formed Shopify domain — noting this only rejects malformed strings, not cross-tenant replay.
- More fundamentally, document (and ideally enforce) that consumers of `WebhookMetadata#shop` must not treat it as authenticated for authorization decisions without corroborating it against their own session/tenant records, since the HMAC only certifies the body came from a holder of the shared secret, not which shop it belongs to.

### Proof of Concept
```ruby
# test/webhooks/shop_attribution_test.rb
require "test_helper"

class ShopAttributionForgeryTest < Test::Unit::TestCase
  def setup
    ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", ...)
  end

  def test_shop_header_is_not_covered_by_hmac
    body = '{"id":1}'
    hmac = OpenSSL::HMAC.base64digest(OpenSSL::Digest.new("sha256"), "secret", body)

    legit = ShopifyAPI::Webhooks::Request.new(
      raw_body: body,
      headers: { "x-shopify-topic" => "orders/create",
                 "x-shopify-hmac-sha256" => hmac,
                 "x-shopify-shop-domain" => "attacker.myshopify.com" },
    )
    forged = ShopifyAPI::Webhooks::Request.new(
      raw_body: body,
      headers: { "x-shopify-topic" => "orders/create",
                 "x-shopify-hmac-sha256" => hmac,
                 "x-shopify-shop-domain" => "not-a-shop" },
    )

    # Both produce the identical signable string -> identical HMAC validity
    assert_equal legit.to_signable_string, forged.to_signable_string
    assert ShopifyAPI::Utils::HmacValidator.validate(forged)

    # Yet the attacker-controlled shop value survives unchanged
    assert_equal "not-a-shop", forged.shop
  end

  def test_shop_validator_never_invoked_in_webhook_path
    ShopifyAPI::Utils::ShopValidator.expects(:sanitize!).never
    ShopifyAPI::Utils::ShopValidator.expects(:sanitize_shop_domain).never

    handler = mock("handler")
    handler.expects(:handle).with(has_entry(shop: "not-a-shop"))
    ShopifyAPI::Webhooks::Registry.add_registration(topic: "orders/create", delivery_method: :http,
      handler: handler, path: "cb")

    body = '{"id":1}'
    hmac = OpenSSL::HMAC.base64digest(OpenSSL::Digest.new("sha256"), "secret", body)
    forged = ShopifyAPI::Webhooks::Request.new(
      raw_body: body,
      headers: { "x-shopify-topic" => "orders/create",
                 "x-shopify-hmac-sha256" => hmac,
                 "x-shopify-shop-domain" => "not-a-shop" },
    )
    ShopifyAPI::Webhooks::Registry.process(forged)
  end
end
```
This demonstrates both sides of the binding diverging: the verified bytes (`to_signable_string`) are shop-independent, while the acted-upon `shop` value passed to the handler is fully attacker-controlled and never passes through `ShopValidator`.
