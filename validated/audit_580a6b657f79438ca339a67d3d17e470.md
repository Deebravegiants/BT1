Audit Report

## Title
Unbounded per-request memory allocation in the internet-facing Confidential Relay gateway handler via unauthenticated `HandleJSONRPCUserMessage` - (File: core/services/gateway/handlers/confidentialrelay/handler.go)

## Summary
`HandleJSONRPCUserMessage` in the Confidential Relay handler accepts any caller-supplied `req.ID` (validated only for non-empty and ≤200 chars) and unconditionally inserts a new `*activeRequest` into `h.activeRequests` via `newActiveRequest`, with no rate limiter or authorization gate applied to this inbound path. [1](#0-0) [2](#0-1)  The `globalNodeRateLimiter`/`perNodeRateLimiters` fields exist on the handler but are only consulted in `HandleNodeMessage` (DON node responses), not on the user-facing entry point. [3](#0-2)  Reclamation relies solely on a 1-second ticker sweeping entries older than `requestTimeout` (default 30s), a time-based, not count-based, eviction mechanism. [4](#0-3) [5](#0-4) 

## Finding Description
The gateway's HTTP entry point enforces a global per-request body size cap (`MaxRequestBytesLimiter`) at the transport layer, and `gateway.ProcessRequest` enforces only a 200-character ID length check before dispatching to the handler — no per-caller/global request-rate limiting exists at that layer either. [6](#0-5) [7](#0-6)  Once dispatched, `HandleJSONRPCUserMessage` performs no authentication or authorization before calling `newActiveRequest`, which locks the handler mutex and inserts an entry keyed by the caller-controlled `req.ID` unless that exact ID string is already in the map. [2](#0-1)  Each request also triggers a `fanOutToNodes` call, spawning a goroutine per DON member bounded by `nodeSendTimeout` (default 10s), and holds the map entry for up to `requestTimeout` (30s). [8](#0-7) 

Notably, this is inconsistent with sibling handlers in the same codebase. The `vault` handler routes mutation methods (`MethodSecretsCreate`/`Update`/`Delete`/`List`) through `h.requestProcessor.ProcessRequest`, which performs authorization (via `AllowListBasedAuth.AuthorizeRequest`, requiring a signed/allowlisted JWT-style authorization) *before* `newActiveRequest` is called. [9](#0-8)  The `capabilities` HTTP-trigger-adjacent `handler.go` additionally implements a count-based `pruneCallbacks` eviction (trimming to `maxSize/2` when the map grows beyond `MaxSavedCallbacks`), in addition to time-based expiry. [10](#0-9)  The confidential relay handler has neither of these protections: no pre-insertion authorization and no count-based cap on `activeRequests`.

## Impact Explanation
This maps to a legitimate in-scope DoS / availability impact class: an unauthenticated client of the gateway (any caller able to reach the HTTP endpoint routed to the Confidential Relay handler, which requires no signature, JWT, or allowlist check unlike the vault handler) can submit a sustained stream of distinct-ID JSON-RPC requests to grow `h.activeRequests` and spawn concurrent per-request goroutines, exhausting gateway memory/CPU. This is a real asymmetry compared to the vault and capabilities handlers in the same package, which each impose either pre-allocation authorization or count-based eviction — evidence that this is a specific gap in this handler rather than a general limitation shared identically by all gateway handlers.

## Likelihood Explanation
The attack requires only unprivileged HTTP access to the gateway's public endpoint, ordinary JSON-RPC requests with unique `id` values ≤200 characters, and a method the handler serves (`MethodSecretsGet`/`MethodCapabilityExec`). [11](#0-10)  No credential, signature, or role is needed to reach `newActiveRequest`. The only mitigating factor is the transport-level `MaxRequestBytesLimiter` (bounds per-request payload size, not request rate or count) and the 1-second cleanup ticker, neither of which caps concurrent in-flight request count. [12](#0-11) 

## Recommendation
Add a per-caller and/or global rate limiter (reusing `limits.RateLimiter`/`limits.Factory` already used elsewhere in this package) or a bounded semaphore on `len(h.activeRequests)` inside `HandleJSONRPCUserMessage` before calling `newActiveRequest`, mirroring the `userRateLimiter` pattern used in `httpTriggerHandler` and the count-based `pruneCallbacks` eviction used in the capabilities handler. Reject or backpressure new requests once an in-flight ceiling is reached.

## Proof of Concept
1. Deploy a gateway configured with the Confidential Relay handler for a DON (`core/services/gateway/handlers/confidentialrelay/handler.go`).
2. From an unauthenticated client, send a sustained stream of HTTP POST requests to the gateway's JSON-RPC endpoint, each with a unique `id` (≤200 chars), `method: "confidentialrelay.secretsGet"` (or `capabilityExec`), each under the `MaxRequestBytes` size limit.
3. Observe `h.activeRequests` (and per-request `fanOutToNodes` goroutines) growing unboundedly as long as the request rate exceeds what the 1-second/30-second sweep can reclaim; measure gateway process memory/goroutine growth as PoC of resource exhaustion. A Go integration test can instantiate the handler directly (as in `handler_test.go`) and call `HandleJSONRPCUserMessage` in a tight loop with unique IDs while asserting `len(h.activeRequests)` grows without bound and no rejection occurs prior to a configured ceiling.

func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], labels requestLabels, callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID, "executionID", labels.ExecutionID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	ar := &activeRequest{
		Callback:  callback,
		req:       req,
		labels:    labels,
		createdAt: h.clock.Now(),
		responses: map[string]*jsonrpc.Response[json.RawMessage]{},
	}
	h.activeRequests[req.ID] = ar
	return ar, nil
}

		return nil
	}

		l.Debug("global relay rate limit exceeded")
		return nil

func (h *handler) fanOutToNodes(ctx context.Context, l logger.Logger, ar *activeRequest) error {
	var (
		group      errgroup.Group
		nodeErrors atomic.Uint32
	)

	// Each send is bounded independently. A node whose websocket accepts no writes blocks
	// until its context is cancelled, and because the caller only reads the response callback
	// after this function returns, an unbounded send would hold the request open until the
	// client gives up, discarding a bundle that already reached quorum.
	sendCtx, cancel := context.WithTimeout(ctx, h.nodeSendTimeout)
	defer cancel()

	for _, node := range h.donConfig.Members {
		group.Go(func() error {
			err := h.don.SendToNode(sendCtx, node.Address, &ar.req)
			if err != nil {
				nodeErrors.Add(1)
				l.Errorw("error sending request to node", "node", node.Address, "error", err)
			}
			return nil
		})
	}

	_ = group.Wait()

func (h *handler) pruneCallbacks() {
	h.mu.Lock()
	defer h.mu.Unlock()

	// First, remove expired callbacks.
	maxAge := time.Duration(h.config.CallbackMaxAgeSec) * time.Second
	now := time.Now()
	var expired int
	for id, cb := range h.savedCallbacks {
		if now.Sub(cb.createdAt) > maxAge {
			delete(h.savedCallbacks, id)
			expired++
		}
	}

	// If there are still too many callbacks, sort them by creation time and remove the oldest ones.
	maxSize := h.config.MaxSavedCallbacks
	var evicted int
	if len(h.savedCallbacks) > maxSize {
		type entry struct {
			id        string
			createdAt time.Time
		}
		entries := make([]entry, 0, len(h.savedCallbacks))
		for id, cb := range h.savedCallbacks {
			entries = append(entries, entry{id, cb.createdAt})
		}
		sort.Slice(entries, func(i, j int) bool {
			return entries[i].createdAt.Before(entries[j].createdAt)
		})
		// Trim to maxSize/2 to avoid sorting the list too frequently.
		for _, e := range entries[:len(entries)-maxSize/2] {
			delete(h.savedCallbacks, e.id)
			evicted++
		}
	}
