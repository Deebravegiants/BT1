### Title
Emporium Min-circuit path lets an attacker drain any token Emporium holds with zero balance accounting - (File: contracts/CircomDataBuilder.sol / contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
When `circomData.externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `circomData.erc20TokenAddresses.length == 0`, `formInputForCircom` routes to `formInputEmporiumMin`, which only constrains `message == Poseidon(messageSeed)` [1](#0-0) [2](#0-1) . This proof is trivially self-generated by any unprivileged attacker (they pick their own `messageSeed`) and carries no relation to any real UTXO, root, or fund ownership. `EmporiumUpgradeable.runAction` decodes an attacker-supplied `EmporiumStack` and, when `signerAddress == address(0)`, executes arbitrary `op.endpoint.call{value: op.value}(op.callData)` from Emporium's own address with no signature check [3](#0-2) [4](#0-3) , while the only balance accounting (`balancesBefore`/`balancesAfter`/the `balanceChange` loop) is computed strictly over `circomData.erc20TokenAddresses`, which is empty in this path, so nothing constrains or reverts on funds moved through arbitrary op calls to tokens/ETH not in that (empty) list [5](#0-4) .

### Finding Description
**Broken equality:** "assets Emporium can move in a tx" must equal "assets accounted in `balancesBefore`/`balancesAfter`". With `erc20TokenAddresses.length == 0`, the accounted side is the empty set, while the movable side is unrestricted (any `op.endpoint.call` the attacker encodes).

**Path:**
1. Attacker calls `Hinkal.transact` with `dimensions.tokenNumber == 0`, `circomData.externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID`, `circomData.erc20TokenAddresses == []`.
2. `performHinkalChecks` calls `formInputForCircom`, which — because `erc20TokenAddresses.length == 0` and the action id matches — returns `formInputEmporiumMin(circomData)`, an input vector of only `{emporiumMessage, timeStamp, calldataHash}` [1](#0-0) .
3. `Hinkal.transact` calls `verifyProof` against the verifier keyed by `buildVerifierId(dimensions, externalActionId)`, which for `tokenNumber == 0` resolves to the dedicated `mainEVMCircuitMin0v4` verifier for `MainEVMCircuitMin`, whose only constraint is `message <== Poseidon(1)([messageSeed])` [2](#0-1) [6](#0-5) . The attacker generates this proof themselves — it proves nothing about ownership of funds, nullifiers, or the Merkle tree.
4. `rootHashExists` only checks that `circomData.rootHashHinkal` is some previously-inserted root — a value completely decoupled from the Min circuit's public signals, so it is trivially satisfied with any historical root [7](#0-6) .
5. `_externalTransact` builds `deltaAmountChanges` of length 0 (since `erc20TokenAddresses.length == 0`) and calls `EmporiumUpgradeable.runAction` [8](#0-7) .
6. Inside `runAction`, `balancesBefore`/`balancesAfter` are computed over the empty `erc20TokenAddresses` array [9](#0-8) . `verifyWallet` is a no-op check beyond `usedMessages` when `stack.signerAddress == address(0)` [4](#0-3) . The op loop then executes `op.endpoint.call{value: op.value}(op.callData)` directly from Emporium's own address (CASE 2, since `invokeWallet && signerAddress != 0` is false) [3](#0-2) . The attacker sets `op.endpoint` to any ERC20 token Emporium holds and `op.callData = transfer(attacker, balance)`, or sets `op.value` to drain Emporium's ETH.
7. The final balance-difference loop iterates zero times (`circomData.erc20TokenAddresses.length == 0`), so no `BalanceChangeShouldBePositive` check or UTXO minting/accounting occurs for the moved funds [10](#0-9) .

**Root cause:** the "Min" fast-path for Emporium (intended presumably for signature-only/no-fund-movement Emporium calls) does not constrain `EmporiumStack.ops` to be no-ops when `tokenNumber == 0`; nothing ties the executed `op.endpoint.call` payloads to the declared (empty) token dimension, so an attacker can move any asset Emporium custodies while the accounting loop that would normally catch the imbalance is skipped entirely because it is scoped to the (attacker-chosen, empty) `erc20TokenAddresses` array.

**Why guards fail:** `performHinkalChecks`'s `dimensionsCheck` only checks internal array-length consistency (all zero-length, so it passes), `checkOnchainCreation` loops zero times, `verifyProof` succeeds because the Min circuit imposes no meaningful constraint, and `rootHashExists` is unrelated to fund ownership. None of these guards inspect or bound the contents of `externalActionMetadata` (the `EmporiumStack`/`ops`).

**Note on prooflessDeposit:** `Hinkal.prooflessDeposit` is a separate, unrelated entrypoint that only pulls tokens from `msg.sender` and creates on-chain UTXO commitments; it never touches `externalActionData`, never calls `runAction`, and never calls `verifyProof` [11](#0-10) . It cannot be used to reach `EmporiumUpgradeable.runAction`, so the "no-proof mint path via prooflessDeposit" framing in the question is not supported by the code. The real, reachable exploit is via `Hinkal.transact` using the genuine-but-trivially-satisfiable Min circuit proof, exactly as scoped by the stated entrypoint "Hinkal.transact (Emporium min path)".

### Impact Explanation
Any unprivileged attacker can steal any ERC20 tokens or ETH balance held by the Emporium contract (e.g., protocol/relay fees in flight, or residual balances left mid multi-step Emporium sequences) with a self-generated trivial proof and no signature. This is direct theft of protocol/relay funds (or in-flight user funds sitting in Emporium at the time of the attack) — matching Critical: direct theft of shielded or in-flight user funds. The attack is fully repeatable as long as Emporium holds a drainable balance.

### Likelihood Explanation
Preconditions: Emporium must hold a nonzero balance of some token/ETH at attack time (e.g., relay fees pending, or funds mid-flight during a legitimate multi-op sequence). No tree state, deposit, or victim UTXO is required. Attacker cost is one `transact` call plus a self-generated Groth16 proof for the trivial `MainEVMCircuitMin` circuit (cheap, no special knowledge). This is fully feasible for any EOA with proof-generation tooling and is repeatable every time Emporium holds funds.

### Recommendation
Do not allow the Emporium `tokenNumber == 0` / Min-circuit path to execute arbitrary `EmporiumOperation` calls without accounting. Either: (1) restrict the Min-path `EmporiumStack.ops` to a safelisted no-value, no-transfer operation set (e.g., signature/cancel-only), or (2) require `runAction`'s balance accounting to cover every token that could conceivably be touched by `op.endpoint`/`op.callData` regardless of the declared `erc20TokenAddresses` dimension (e.g., disallow the Min circuit whenever `stack.ops` contains any endpoint call capable of moving value, or require `tokenNumber > 0` whenever `ops.length > 0`).

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable` (as allowed recipient), register `mainEVMCircuitMin0v4` verifier for `buildVerifierId({tokenNumber:0,...}, HINKAL_EMPORIUM_ACTION_ID)`.
2. Fund Emporium directly with an ERC20 token (simulate leftover/in-flight relay fee balance): `token.transfer(address(emporium), 1000e18)`. Record `emporiumBalanceBefore = token.balanceOf(emporium)`.
3. As attacker (no special role), generate a valid `MainEVMCircuitMin` proof for a self-chosen `messageSeed` (`message = Poseidon(messageSeed)`), and craft `circomData` with `erc20TokenAddresses = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionData.externalActionMetadata = abi.encode(EmporiumStack{signerAddress: address(0), ops: [EmporiumOperation{endpoint: address(token), invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, 1000e18))}], maxFee: 0, deadline: type(uint256).max})`, `rootHashHinkal` set to any existing root, `calldataHash` computed to match.
4. Call `Hinkal.transact(a, b, c, dimensions, circomData)` from attacker.
5. Assert `token.balanceOf(attacker) == 1000e18` and `token.balanceOf(emporium) == 0`, i.e., `emporiumBalanceAfter != emporiumBalanceBefore - accountedChange (0)`, proving the equality "assets moved == assets accounted" is broken.
