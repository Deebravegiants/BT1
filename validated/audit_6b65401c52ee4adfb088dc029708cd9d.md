### Title
Webhook shop-domain identity spoofing due to HMAC covering only the body, not the shop binding - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw request body, while the `shop` (and `topic`) values are read from unauthenticated HTTP headers that are never part of the signed content. `Registry.process` validates the HMAC and then unconditionally trusts `request.shop` to route the payload to the app's handler, so the "which shop does this event belong to" binding is never actually checked by the library.

### Finding Description
`Utils::HmacValidator.validate` is generic and calls `verifiable_query.to_signable_string` to compute the expected signature [1](#0-0) . For webhooks, `to_signable_string` returns only `@raw_body` [2](#0-1) , while `shop` and `topic` are pulled straight from the `shopify-shop-domain` / `x-shopify-shop-domain` headers with no cryptographic binding to that body [3](#0-2) .

`Registry.process` validates only that the body's HMAC is correct, then immediately hands `request.shop` (and `request.topic`) to the registered handler with no further check that this shop is the one that actually produced/owns the signed body: [4](#0-3) 

`WebhookMetadata` is built directly from `request.shop`, so any downstream handler that keys behavior/state off `data.shop` (e.g. looking up a session/store record and applying the webhook body to it) is trusting an attacker-controllable field.

The identity binding broken is:
`shop authenticated by HMAC` ≠ `shop used by the handler to attribute the event`

Since the HMAC only proves "this body was produced by holder of the api_secret_key for *some* shop that fired *some* webhook", but not "this body belongs to shop X", an internet-reachable actor who legitimately owns a Shopify development/trial store (no privileged access to the target app or its secrets required) can generate a real webhook (valid signature over a body they fully control, e.g. by editing their own store's product/order data) and then replay that exact `body` + `hmac-sha256` header to the target app's webhook endpoint while substituting the `shop-domain` header with the victim's shop domain. `Registry.process` will accept it as valid and dispatch it to the handler labelled as coming from the victim shop.

### Impact Explanation
This lets an unprivileged internet user with any Shopify store forge webhook events that the app processes as if they originated from a different (victim) shop, since the shop attribution is not covered by the cryptographic signature. Depending on how the host app's `WebhookHandler` uses `data.shop` (e.g., to look up and mutate a specific merchant's persisted data, trigger app-side account changes, or issue merchant-scoped actions), this can enable cross-tenant data corruption/injection against a shop the attacker does not control. This falls under the report's category of a "field acted on but not covered by HMAC" identity break.

### Likelihood Explanation
Exploitation requires only the ability to (a) operate any real Shopify store to obtain a validly signed webhook body/HMAC pair, and (b) send an HTTP POST to the target app's public webhook endpoint with a spoofed `shopify-shop-domain` header — no access to the app's `client_secret`, access tokens, or any privileged account on the victim shop is needed. This is a moderate-to-high likelihood issue for any app whose webhook handler trusts `WebhookMetadata#shop` for anything beyond logging.

### Recommendation
Bind the shop domain into the signed content, or otherwise verify it out-of-band:
- Have `Registry.process` (or an app-level check) confirm that `request.shop` corresponds to a shop that has an active/expected session before invoking the handler, rather than trusting the header outright.
- Where possible, include the `shop` value as part of the value verified for consistency (e.g., cross-check against a known/authorized list of installed shops before dispatch), since HMAC coverage is dictated by Shopify's platform and can't be changed client-side.
- Document explicitly (more strongly than currently) that `WebhookMetadata#shop` is unauthenticated header data and must be cross-checked by the app against its own installed-shop records before being trusted for any state-changing action.

### Proof of Concept
1. Attacker creates/uses their own Shopify development store `attacker.myshopify.com` and installs the target app, registering for a webhook topic (e.g. `products/update`).
2. Attacker triggers the webhook on their own store (e.g., updates a product), capturing the raw POST body `B` and the valid `x-shopify-hmac-sha256` header `H` that Shopify computed using the app's real secret.
3. Attacker POSTs the same body `B` and header `H` directly to the target app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "victim-shop.myshopify.com", "x-shopify-hmac-sha256" => H})` is constructed; `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H` [5](#0-4) .
5. `Registry.process` dispatches to the handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)`, so the app processes attacker-controlled content as belonging to `victim-shop.myshopify.com`.
