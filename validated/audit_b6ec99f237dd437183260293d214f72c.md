### Title
Snowbridge V2 `CallContract` command lets the caller supply an arbitrary `gas` value that is used unvalidated as the Ethereum dispatch gas — ([File: bridges/snowbridge/primitives/outbound-queue/src/v2/message.rs])

### Summary
The Snowbridge V2 outbound-queue `Command::CallContract` variant lets the message originator (any XCM sender able to reach the Snowbridge V2 exporter) supply a raw `gas: u64` field that becomes the `max_dispatch_gas` shipped to the Ethereum Gateway contract with no lower-bound sanity check, analogous to the ZetaChain `gasFromCCTX()` bug where a caller-chosen EVM gas limit below the intrinsic minimum led to permanently unexecutable outbound messages.

### Finding Description
`Command::CallContract` carries a caller-supplied `gas: u64` field [1](#0-0) . The `GasMeter` implementation for V2 commands simply passes this value straight through as the dispatch gas budget for every other command type it computes a fixed, hard-coded constant, but for `CallContract` it does `Command::CallContract { gas: gas_limit, .. } => *gas_limit` — i.e. it trusts the caller's number verbatim instead of enforcing any floor: [2](#0-1) .

This gas value is written into the committed `OutboundCommandWrapper.gas` field during `do_process_message`, which is what ultimately becomes the `CommandWrapper.gas` (the on-chain committed Ethereum "gas" ABI field) delivered to the Gateway contract on Ethereum: [3](#0-2) . There is no check anywhere in this flow (`validate`/`deliver` in `send_message_impl.rs`, nor `do_process_message`) that the requested `gas` is above Ethereum's intrinsic minimum (~21,000, more for calldata) or any protocol-defined floor — unlike other commands whose gas is a fixed, safe constant chosen by the runtime (e.g. `UnlockNativeToken` → 200,000, `MintForeignToken` → 100,000).

This mirrors the ZetaChain M-27 root cause precisely: a per-message/per-transaction "gas limit" field that is fully attacker/user controlled and used directly without a minimum-bound check, where too-low a value causes the outbound EVM call to fail at (or below) the EVM intrinsic gas floor.

### Impact Explanation
In the ZetaChain report, the analogous effect was a stuck outbound queue because the broadcast itself failed (RPC rejection) and the TSS nonce was never consumed, permanently blocking all subsequent nonces. In Snowbridge's design this exact "stuck nonce forever" outcome does **not** reproduce identically: the committed message (with nonce) is written to `Messages`/`MessageLeaves` and merkle-committed to the header regardless of the `gas` value [4](#0-3) ; nonce assignment happens on the Substrate side unconditionally, not after successful Ethereum broadcast, so subsequent nonces are not blocked at the Substrate layer. The concrete failure mode would instead be Ethereum-side: the relayer's `submit` transaction to the Gateway contract could either revert entirely (griefing relayers/wasting their gas, since the relayer pays L1 gas to attempt execution) or, depending on the Solidity Gateway's `call{gas: cmd.gas}(...)` semantics, silently swallow the too-low-gas `CallContract` sub-call as a failed inner call while the outer relayer transaction still succeeds — in which case the message would be marked delivered/rewarded despite the intended contract call never executing correctly. I cannot verify the exact Gateway Solidity behavior since the EVM-side Solidity contracts are not part of this repository/index, so I cannot confirm whether this is a queue-blocking DoS or a "silently dropped effect" issue, nor confirm the exact revert/proceed semantics.

### Likelihood Explanation
Reaching `Command::CallContract` requires the caller to be able to originate an XCM message that the Snowbridge V2 `EthereumBlobExporter`/system pallet accepts and converts into this command (governance/agent-controlled contract-call functionality), so this is likely restricted to privileged/governance origins or specific agent-owner accounts rather than an arbitrary unprivileged user. I was not able to fully trace the full authorization chain from XCM origin to `Command::CallContract` construction (e.g., `bridges/snowbridge/primitives/outbound-queue/src/v2/converter/convert.rs`) within the available search budget, so the exact privilege level required to trigger this path is unconfirmed.

### Recommendation
Regardless of the exact privilege level, add a sanity/minimum-gas check for `CallContract.gas` in `ConstantGasMeter::maximum_dispatch_gas_used_at_most` (or at message `validate` time), rejecting or clamping values below a safe floor (covering Ethereum intrinsic gas + calldata cost + any Gateway dispatch overhead), consistent with how ZetaChain's fix re-added the minimum gas-limit check in `gasFromCCTX()`.

### Proof of Concept
Not executed against a live Gateway contract (Solidity side unavailable in this index). Conceptually: submit/trigger a `Command::CallContract { gas: 1, .. }` message through the Snowbridge V2 exporter; observe that `ConstantGasMeter::maximum_dispatch_gas_used_at_most` returns `1` unmodified [5](#0-4) , that this value is committed as `OutboundCommandWrapper.gas` in `do_process_message` [6](#0-5) , and is delivered to Ethereum without any runtime-side rejection.

impl GasMeter for ConstantGasMeter {
	fn maximum_dispatch_gas_used_at_most(command: &Command) -> u64 {
		match command {
			Command::SetOperatingMode { .. } => 40_000,
			Command::Upgrade { initializer, .. } => {
				// total maximum gas must also include the gas used for updating the proxy before
				// the the initializer is called.
				50_000 + initializer.maximum_required_gas
			},
			Command::UnlockNativeToken { .. } => 200_000,
			Command::RegisterForeignToken { .. } => 1_200_000,
			Command::MintForeignToken { .. } => 100_000,
			Command::CallContract { gas: gas_limit, .. } => *gas_limit,
		}
	}
}
