### Title
Webhook `shop` (tenant identifier) is not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body [1](#0-0) . However, the `shop` value that is handed to the app's `WebhookHandler` as the authoritative tenant identifier is read from the `X-Shopify-Shop-Domain`/`Shopify-Shop-Domain` header [2](#0-1) , and that header is not part of the signed content — `to_signable_string` returns only `@raw_body` [3](#0-2) .

### Finding Description
The binding that should hold is: `hmac == HMAC(secret, body || shop || topic || webhook_id)`, i.e., the authenticated bytes should bind the tenant claim to the payload. Instead the gem only enforces `hmac == HMAC(secret, body)` [4](#0-3) , while `shop`, `topic`, `webhook_id`, and `api_version` are taken verbatim from unauthenticated headers [5](#0-4)  and passed straight through to `WebhookMetadata`, which the host application treats as the trusted tenant/topic identity [6](#0-5) .

Because the app's `client_secret`/`api_secret_key` is shared across every shop that installs the app (it is not per-tenant), any merchant that legitimately receives a correctly-signed webhook for their own shop can capture a valid `(raw_body, hmac)` pair and resubmit it to the app's webhook endpoint with the `shop-domain` header rewritten to name a different, victim shop. `Registry.process` calls `Utils::HmacValidator.validate(request)` which only recomputes the HMAC over `raw_body` [7](#0-6) ; since the body's HMAC is unaffected by the header rewrite, validation still succeeds, and the handler receives `WebhookMetadata` claiming the forged `shop`.

### Impact Explanation
This breaks a tenant boundary: an unprivileged (but legitimately-onboarded) merchant of a multi-tenant app can inject attacker-controlled webhook payloads that the app attributes to a different shop it did not choose to send them from, because the identity binding `shop ↔ signed bytes` does not hold. Depending on how the host app's `WebhookHandler` implementation uses `data.shop` (e.g., to key data stores, update records, or trigger `customers/redact`/`shop/redact` compliance flows), this enables cross-tenant data poisoning or spoofed compliance/administrative events attributed to a victim shop.

### Likelihood Explanation
Any actual installer of the app already possesses a valid `(body, hmac)` pair for their own shop from normal webhook delivery, so no secret material needs to be obtained — only header manipulation on replay, which is fully within reach of an "unprivileged internet user" who is a legitimate customer of the app.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signed content checked by `to_signable_string`, or otherwise cryptographically bind them (e.g., verify `shop` against a value looked up from a trusted, per-installation record rather than trusting the header), before handing `WebhookMetadata` to the handler.

### Proof of Concept
1. App installs on `victim-shop.myshopify.com` sends the attacker-installer webhooks signed with the app's single, shared `api_secret_key`.
2. Attacker (installer of the same app on `attacker-shop.myshopify.com`) receives a legitimate webhook: `raw_body = B`, header `Shopify-Hmac-Sha256 = HMAC(secret, B)`, header `Shopify-Shop-Domain = attacker-shop.myshopify.com`.
3. Attacker resends the identical `raw_body` and `hmac` header to the app's webhook endpoint, but sets `Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged header [8](#0-7) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` only and matches [1](#0-0) .
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic:, body:, ...)` [9](#0-8) , and processes attacker-supplied data as if it originated from the victim tenant.
