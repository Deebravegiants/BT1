## Analysis

The reported bug class—an unrestricted `receive()` function that can permanently trap native assets in a contract with no way to sweep them out—has a direct analog in Hyperbridge's Uniswap V2 router wrapper family.

Two of the sibling wrapper contracts explicitly guard their `receive()` against unsolicited ETH:

- `UniV3UniswapV2Wrapper.sol` only accepts ETH from its configured WETH address [1](#0-0) 
- `UniV4UniswapV2Wrapper.sol` only accepts ETH from its configured `universalRouter` [2](#0-1) 

But `GnosisUniswapV2Wrapper.sol`, part of the same interchangeable `IUniswapV2Router02` wrapper set used by `EvmHost` to swap native tokens into the fee token, has a completely unprotected `receive()`:

```solidity
/// @notice Accepts native xDAI from WXDAI during withdraw.
receive() external payable {}
``` [3](#0-2) 

This wrapper is stateless per-call: `swapExactTokensForETH` pulls WXDAI from the caller, calls `IWETH.withdraw`, and forwards the resulting native balance to `to` [4](#0-3) . It holds no persistent balance by design and has no admin, sweep, or rescue function anywhere in the file. Because `receive()` places no restriction on `msg.sender` (unlike its `UniV3`/`UniV4` siblings), **anyone** who sends native xDAI directly to this contract (a mistaken transfer, a wallet auto-forward, or a malicious griefer targeting router funds mid-swap) will have those funds permanently stuck—there is no function in the contract capable of withdrawing an accidental native balance.

### Title
Unrestricted `receive()` in GnosisUniswapV2Wrapper permanently locks stray native tokens - (File: evm/src/utils/uniswapv2/GnosisUniswapV2Wrapper.sol)

### Summary
`GnosisUniswapV2Wrapper.receive()` accepts native xDAI from any sender with no `msg.sender` check and no function exists anywhere in the contract to withdraw an unexpected native balance, unlike its sibling wrappers (`UniV3UniswapV2Wrapper`, `UniV4UniswapV2Wrapper`) which restrict `receive()` to their trusted counterpart.

### Finding Description
The wrapper is designed to be stateless: `swapExactTokensForETH` withdraws WXDAI and immediately forwards the native proceeds to the caller-specified `to` address [4](#0-3) . The comment on `receive()` states it is intended only to "accept native xDAI from WXDAI during withdraw," implying the sender should be restricted to the WXDAI contract, exactly as `UniV3UniswapV2Wrapper` and `UniV4UniswapV2Wrapper` do for their respective counterparties [1](#0-0) [2](#0-1) . However `GnosisUniswapV2Wrapper.receive()` has no such guard, so it silently accepts value from any caller. Since the contract holds no state and defines no owner/admin/withdraw method, any native tokens deposited outside of the `swapExactTokensForETH`/`swapETHForExactTokens` flows become permanently unrecoverable.

### Impact Explanation
This wrapper is configured as the `uniswapV2` router target used by `EvmHost.dispatch`/`fundRequest`/GET-dispatch paths whenever fee payments include native value [5](#0-4) . Any leftover dust, mis-estimated swap output, or a directly sent transfer targeting this address results in a permanent freeze of funds with no admin recovery mechanism—medium-severity permanent loss of native assets.

### Likelihood Explanation
Reachable by any unprivileged account with a single plain ETH/xDAI transfer to the wrapper address; no special conditions or privileged role required.

### Recommendation
Restrict `receive()` to the WXDAI contract only, matching the pattern used in `UniV3UniswapV2Wrapper`/`UniV4UniswapV2Wrapper`:
```solidity
receive() external payable {
    if (msg.sender != WETH()) revert Unauthorized();
}
```
Alternatively, add a permissioned sweep function to recover any stray native balance.

### Proof of Concept
1. Any external account sends native xDAI directly to `GnosisUniswapV2Wrapper` via a plain transfer (no calldata), which is accepted by the unguarded `receive()`.
2. The wrapper has no function referencing `address(this).balance` other than the transient balance consumed inside `swapExactTokensForETH`'s single call flow.
3. Because that balance is not tied to any pending swap accounting, the deposited value remains in the contract indefinitely with no path to reclaim it.
