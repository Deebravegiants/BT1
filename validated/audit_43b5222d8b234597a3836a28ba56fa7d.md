### Title
No vulnerability - Secret `.type` is enforced immutable on update - ([File: pkg/apis/core/validation/validation.go])

### Summary
`ValidateSecretUpdate` explicitly calls `ValidateImmutableField(newSecret.Type, oldSecret.Type, field.NewPath("type"))`, which rejects any update request that changes a Secret's `.type` from its original value, including the Opaque → `kubernetes.io/service-account-token` transition described in the question. This is also confirmed by dedicated declarative-validation test cases covering "type: changed", "type: set from unset", and "type: unset from set", all of which expect an immutability validation error.

### Finding Description
The relevant code path is `pkg/registry/core/secret/strategy.go` `strategy.ValidateUpdate`, which calls `validation.ValidateSecretUpdate(newSecret, oldSecret)` [1](#0-0) . That function immediately checks type immutability: `allErrs = append(allErrs, ValidateImmutableField(newSecret.Type, oldSecret.Type, field.NewPath("type")).WithOrigin("immutable").MarkCoveredByDeclarative()...)` [2](#0-1) . `PrepareForUpdate` in the strategy only fills in `newSecret.Type` when the incoming request leaves it empty (`len(newSecret.Type) == 0`); it does not allow an attacker to overwrite an existing type with a different non-empty one and bypass validation [3](#0-2) . Any PUT/PATCH request attempting to flip `.type` from `Opaque` to `kubernetes.io/service-account-token` (or vice versa) is rejected with a "field is immutable" error before it reaches storage, as confirmed by the table tests in `test/declarative_validation/core/secret/declarative_validation_test.go` (`"type: changed"`, `"type: set from unset"`, `"type: unset from set"`) [4](#0-3) . Thus the token controller can never see an existing Opaque secret retroactively reclassified as a service-account-token secret via update.

### Impact Explanation
No exploitable impact exists — the described identity-confusion / forged-token scenario cannot occur because the update path is rejected by validation before any controller reconciliation logic is reached.

### Likelihood Explanation
Not applicable; the precondition (successful update changing `.type`) cannot be satisfied given the immutability check.

### Recommendation
No fix needed; existing behavior already enforces immutability of Secret `.type` on update.

### Proof of Concept
Not applicable — the existing test `TestDeclarativeValidateUpdate` in `test/declarative_validation/core/secret/declarative_validation_test.go` already serves as the proof that changing `.type` on update produces a validation error rather than being persisted.
