### Title
Borrow-rate curve loses precision via division before multiplication, mis-pricing interest for all borrowers and suppliers - (File: common/src/rates/curve.rs)

### Summary
`calculate_annual_borrow_rate` interpolates each slope contribution as `excess.mul(slope).div(range)`, i.e. `half_up(half_up(excess * slope / RAY) * RAY / range)`. The inner fixed-point `mul` already divides by `RAY`, and the outer `div` multiplies back by `RAY` before dividing by `range`. The mathematically correct single-step form is `half_up(excess * slope / range)`. Splitting the operation introduces an intermediate rounding step — division before multiplication — the same bug class as the reported `CurveMath6.linearInterpolation` precision loss.

### Finding Description
In `common/src/rates/curve.rs` (lines 28–51), all three segments of the borrow-rate curve compute the slope contribution with two chained fixed-point operations:

```rust
let contribution = utilization
    .mul(env, params.slope1)      // half_up(u * slope1 / RAY)  ← division first
    .div(env, params.mid_utilization); // half_up(prev * RAY / mid)
```

`Ray::mul` is `mul_div_half_up(a, b, RAY)` and `Ray::div` is `mul_div_half_up(a, RAY, b)` (per `docs/reference/formulas.md`, which documents each slope contribution as "half-up multiplication followed by half-up division"). The inner step truncates `u * slope1` to RAY precision before the outer step rescales, whereas a single `mul_div_half_up(u, slope1, mid)` would carry the full product into one division. The result can differ from the exact rate by roughly half a RAY ulp in the intermediate term, and the error propagates identically through `calculate_borrow_rate` into `accrue_step` (`common/src/rates/simulate.rs`), which drives `update_borrow_index`, `calculate_supplier_rewards`, `update_supply_index`, and `protocol_fee_shares` on every interest accrual.

Because utilization is recomputed at every accrual chunk, any unprivileged caller of `supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `flash_loan`, `update_indexes`, etc. hits this path — no privilege or edge-case parameter is required.

### Impact Explanation
The borrow APR used for every index update is slightly mis-rounded relative to the intended interpolation. Depending on the sign of the intermediate rounding, borrowers are charged marginally less (or more) interest than the curve parameters specify, so suppliers and the protocol receive a slightly misallocated share of borrower payments — funding does not accurately reflect the intended redistribution, matching the reported impact. The magnitude per accrual is small (sub-ulp of the slope contribution), but it is systematic, applies to all interest accrued on the market, and compounds through the borrow index over the market's lifetime.

### Likelihood Explanation
Certain to occur: every borrow-rate evaluation on every market in segments below/above kinks uses the two-step form. It requires no special timing or state — any accrual where `u * slope` is not exactly representable in RAY loses precision.

### Recommendation
Collapse each contribution into a single multiply-divide so the full product reaches one division: `mul_div_half_up(excess, slope, range)` (equivalently `excess.mul_div(env, slope.raw(), range)`), rather than `excess.mul(slope).div(range)`. Apply to all three segments in `calculate_annual_borrow_rate`.

### Proof of Concept
Mirroring the report's PoC shape in Rust terms: with `mid = 0.60 RAY`, `slope1 = 0.03 RAY`, `u = 0.57 RAY`:

- Current: `inner = half_up(0.57e27 * 0.03e27 / 1e27) = 17_100_000_000_000_000_000_000_000` (exact here, but for e.g. `u = 0.5757575757…` non-terminating products the inner half-up rounds before rescaling); `contribution = half_up(inner * 1e27 / 0.6e27)`.
- Correct: `contribution = half_up(u * slope1 / mid)` in one `mul_div`.

For any `u * slope1 mod RAY ≠ 0`, `half_up(half_up(u*s/R) * R/m)` can differ from `half_up(u*s/m)` by 1 RAY, which then shifts `borrow_index'` and all derived supplier/protocol rewards. Verified behaviorally via `tests/test-harness/tests/pool/math_rates.rs::test_deposit_rate_with_reserve_factor` style harness comparing the two forms across non-terminating inputs.

Note: I was unable to open `common/src/math/fp.rs` to confirm the exact `mul`/`div` implementations in the final iteration; the claim that `mul` performs a `…/RAY` division and `div` performs a `…*RAY/…` rescale is supported by `docs/reference/formulas.md` and `skills/xoxno-lending/math.md`, which describe the slope contributions exactly as `half_up(half_up(u × slope1 / RAY) × RAY / mid)`.
