### Title
Webhook `shop-domain` header is not covered by the HMAC, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop` value handed to the application's webhook handler is read from the unauthenticated `x-shopify-shop-domain` header, which is never included in the signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Registry.process` validates the HMAC of the request (which covers only that raw body) and then immediately constructs `WebhookMetadata` using `request.shop`, which is read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header without any cryptographic binding to the signed body: [2](#0-1) [3](#0-2) 

The `shop` header is read via `shopify_header`, entirely independent of `hmac`/`to_signable_string`: [4](#0-3) 

This breaks the intended identity binding: `hmac_valid(body) == true` should imply `shop == the tenant that produced this signed body`, but the code only proves `hmac_valid(body) == true`; the `shop` field is attacker-controlled independent of that proof. An unprivileged internet user who can obtain any single genuine `(body, hmac)` pair signed by the app's shared secret — for example, by installing the target app on their own free/dev store and observing a real webhook delivery for a body they can predict or reuse (e.g., an empty/minimal body event, or any deterministic payload) — can replay that exact body and HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with an arbitrary victim shop's domain. `HmacValidator.validate` will still pass (it only checks `verifiable_query.hmac` against `to_signable_string`, i.e. the body), and the handler will be invoked with `data.shop` set to the attacker-chosen victim domain.

### Impact Explanation
This crosses a tenant boundary: the gem asserts to the host application that a webhook event is authentically associated with a specific shop, but that association is not verified. Depending on how the host application's webhook handlers use `shop` (e.g., `app/uninstalled`, `shop/redact`, `customers/redact`, or business-logic handlers keyed by shop), an attacker can inject events attributed to a shop they do not control, triggering account/session teardown, data deletion, or state corruption for another merchant — a cross-tenant access impact.

### Likelihood Explanation
Exploitation requires only an internet-reachable webhook endpoint and knowledge of one valid `(body, hmac)` pair for some topic — attainable by any developer who installs the app on their own shop (a merchant, not the app owner) and captures a legitimate delivery. No access token, `client_secret`, or privileged account is required; the `api_secret_key` never needs to be known to the attacker.

### Recommendation
Include the shop domain (and other identifying headers routed to the handler, e.g. topic/webhook-id) in the value covered by the HMAC verification, or otherwise cryptographically bind the `shop` header to the signed body before it is trusted and forwarded to `WebhookMetadata`. At minimum, document that `shop` in `WebhookMetadata` is not verified beyond formatting, and encourage host applications to cross-check it against records of Shopify webhook subscriptions for that endpoint/topic.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a webhook event whose body is deterministic/known (e.g., an app-defined webhook with an empty or predictable JSON body).
2. Attacker's server captures the legitimate `x-shopify-hmac-sha256` value Shopify sent for that exact body.
3. Attacker sends a forged POST to the app's webhook endpoint with:
   - Body: the exact same raw bytes captured in step 1
   - `x-shopify-hmac-sha256`: the same HMAC value captured in step 1
   - `x-shopify-shop-domain`: `victim-shop.myshopify.com`
   - `x-shopify-topic`: any registered topic
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the (unchanged) body against the (unchanged) HMAC.
5. The registered handler is invoked with `WebhookMetadata` where `shop == "victim-shop.myshopify.com"`, even though the request never originated from Shopify on behalf of that shop.
