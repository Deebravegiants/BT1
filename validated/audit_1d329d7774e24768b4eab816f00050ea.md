## Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

## Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload solely from the raw request body, while the `shop` (and `topic`/`webhook-id`/`api-version`) values used to attribute and process the webhook are read from unauthenticated HTTP headers. `Registry.process` validates only that `(secret, raw_body)` produces the received HMAC, then dispatches the handler using the header-derived `shop`, `topic`, and `webhook_id` without those fields ever being part of the signed material. This breaks the identity binding `HMAC(api_secret_key, raw_body) == received_hmac` ⇒ "this event genuinely originated from `shop`" — the equality only proves the body/secret pair, not the shop attribution.

## Finding Description
`Request#to_signable_string` returns just `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all pulled from HTTP headers independent of the signature: [2](#0-1) 

`Registry.process` validates the HMAC over the request (i.e., over `raw_body` only) and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to route and hand off the event to the registered handler: [3](#0-2) 

`HmacValidator.validate` confirms only that the computed signature over `verifiable_query.to_signable_string` (the raw body) matches the received HMAC — it never incorporates the shop domain: [4](#0-3) 

Because the same app's HMAC secret is shared across all shops that install it, any merchant/attacker who installs the app on their own store can trigger a webhook event with body content of their choosing (e.g., by creating an order, updating a product, etc.), capture the valid `(raw_body, x-shopify-hmac-sha256)` pair emitted to their app endpoint, and then replay that exact body+HMAC directly to the app's webhook endpoint while substituting `x-shopify-shop-domain` (and, if desired, `x-shopify-topic`/`x-shopify-webhook-id`) with an arbitrary victim shop's domain. `HmacValidator.validate` still succeeds (it only checks body+secret), and `Registry.process` calls the handler with `shop: <attacker-chosen victim shop>`, `body: request.parsed_body` (attacker-controlled), causing the host application to process attacker-controlled webhook data attributed to a shop the attacker does not control.

## Impact Explanation
This crosses a tenant boundary: any application that keys business logic (e.g., data updates, uninstall handling, entitlement changes) off `WebhookMetadata#shop` as returned by this gem will act on injected/forged data as if it came from a different, victim tenant. This matches "Critical - cross-tenant access" since the attacker never needs the victim's credentials — only knowledge of the victim's `*.myshopify.com` domain (often public) and the ability to legitimately trigger one webhook on their own installation to obtain a validly-signed body/HMAC pair.

## Likelihood Explanation
Any developer/customer of the app (a normal, unprivileged merchant) can install the app on their own store to generate arbitrary signed webhook bodies, then send a crafted HTTP POST directly to the app's public webhook endpoint with a forged `shop-domain` header. No secrets or elevated access are required beyond having the app installed on any store, which is by design available to any merchant.

## Recommendation
Include the shop domain (and ideally topic/webhook id) as part of the signed material verified against Shopify, or independently verify that the `shop` header corresponds to a shop for which the app holds an active session/install record before dispatching to handlers. At minimum, document and enforce that consumers of `WebhookMetadata#shop` must cross-check it against their own installed-shop registry rather than trusting it as authenticated by the HMAC check.

## Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers any webhook (e.g., `orders/create`) with a body of their choosing.
2. Attacker captures the raw body and the resulting `x-shopify-hmac-sha256` value from the legitimate request Shopify sends to the app.
3. Attacker sends a POST to the app's webhook endpoint with the same raw body and HMAC header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` at [5](#0-4)  validates the HMAC successfully (it only checks body+secret) and invokes the registered handler with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body, even though the event never originated from that shop.

          received_signature = verifiable_query.hmac
