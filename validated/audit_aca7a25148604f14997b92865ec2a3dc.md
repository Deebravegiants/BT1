### Title
`ShopifyAPI::Auth::Oauth.begin_auth` fails to validate `shop` before redirecting, enabling CSRF-state leak / forced OAuth completion - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` builds the OAuth `authorize` redirect URL directly from a caller-supplied `shop:` string, with **no validation that it is a trusted Shopify domain**, unlike every other flow in this gem that talks to `/admin/oauth/*` (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`), all of which call `Utils::ShopValidator.sanitize!(shop)` first.

### Finding Description
`begin_auth` generates the anti-CSRF `state` nonce, stores it in a cookie scoped to the app's own domain, then builds the redirect target purely from the unvalidated `shop` argument: [1](#0-0) 

```ruby
state = SecureRandom.alphanumeric(NONCE_LENGTH)
cookie = SessionCookie.new(value: state, expires: Time.now + 60)
query = {
  client_id: ShopifyAPI::Context.api_key,
  scope: scope.to_s,
  redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
  state: state,
  "grant_options[]": is_online ? "per-user" : "",
}
query_string = URI.encode_www_form(query)
auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"
```

`auth_base_uri` performs no domain check at all: [2](#0-1) 

```ruby
def auth_base_uri(shop)
  return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")
  ...
end
```

Compare this with the sibling flows in the same gem that construct nearly identical requests to `/admin/oauth/access_token` and *do* validate the shop first: [3](#0-2) [4](#0-3) 

The identity binding that should hold is: **shop string acted upon to build a redirect target == a value proven to be a genuine `*.myshopify.com`/trusted Shopify domain** (as enforced by `Utils::ShopValidator.sanitize!`, see `TRUSTED_SHOPIFY_DOMAINS`): [5](#0-4) 

`begin_auth` breaks this binding: the `shop` value is typically taken straight from unauthenticated request input (this is exactly what the gem's own documentation instructs consuming apps to do): [6](#0-5) 

```ruby
def login
  shop = request.headers["Shop"]
  auth_response = ShopifyAPI::Auth::Oauth.begin_auth(shop: domain, redirect_path: "/auth/callback")
```

Because `begin_auth` neither calls `ShopValidator.sanitize!` nor otherwise restricts `shop` to a Shopify domain, an attacker who controls this input can set `shop=evil.example.com`. The resulting `auth_route` is `https://evil.example.com/admin/oauth/authorize?client_id=...&scope=...&redirect_uri=<app_callback>&state=<nonce>`, and the victim's browser is redirected to a fully attacker-controlled server, carrying the CSRF `state` value that was simultaneously placed in a cookie on the legitimate app's own domain.

### Impact Explanation
Leaking the CSRF `state` nonce to an attacker-controlled origin defeats the entire purpose of the state binding performed later in `validate_auth_callback`: [7](#0-6) 

```ruby
state = cookies[SessionCookie::SESSION_COOKIE_NAME]
raise Errors::NoSessionCookieError unless state
raise Errors::InvalidOauthError, "Invalid state in OAuth callback." unless state == auth_query.state
```

Because the HMAC on the callback (`AuthQuery#to_signable_string`) is computed over `code, host, shop, state, timestamp` using the app's real `api_secret_key`, and Shopify's own OAuth server will sign whatever `state` value the attacker chooses to pass when initiating a *separate, legitimate* OAuth flow against a shop the attacker controls, an attacker can:
1. Trigger the victim's browser to hit `begin_auth`, harvesting the app-issued `state` nonce (now known to the attacker via the leaked redirect) while the matching cookie is set in the victim's browser.
2. Start their own real OAuth authorization against a shop they own, supplying the stolen `state` value as the `state` parameter.
3. Receive back a Shopify-signed callback URL (valid HMAC, since Shopify itself signs it) containing that same `state`.
4. Deliver that URL to the victim, whose browser still carries the matching state cookie — `validate_auth_callback` accepts it as a match and completes the OAuth flow, effectively **force-completing OAuth** on the attacker's chosen terms.

This matches the "session fixation or forced OAuth completion" High-impact category, since the identity binding between the CSRF `state` cookie and a trusted redirect target is broken solely due to missing shop validation in this gem's own `begin_auth` implementation, not due to host-app misuse of the documented API (the documented usage pattern is itself the trigger).

### Likelihood Explanation
Any app built per this gem's own documented usage pattern (taking `shop` from request headers/params and calling `begin_auth`) is affected without any additional developer mistake — the gem's public API provides no built-in protection here, whereas it does provide (and use) this exact protection (`ShopValidator.sanitize!`) in its other OAuth-adjacent flows.

### Recommendation
In `lib/shopify_api/auth/oauth.rb#begin_auth`, validate `shop` with `Utils::ShopValidator.sanitize!(shop)` (as done in `client_credentials.rb` and `refresh_token.rb`) before it is used in `auth_base_uri`, raising `Errors::InvalidShopError` for any non-Shopify domain.

### Proof of Concept
1. Host app implements `login` exactly as shown in `docs/usage/oauth.md`:
   ```ruby
   def login
     shop = request.headers["Shop"] # or params[:shop]
     auth_response = ShopifyAPI::Auth::Oauth.begin_auth(shop: shop, redirect_path: "/auth/callback")
     cookies[auth_response[:cookie].name] = { value: auth_response[:cookie].value, ... }
     redirect_to auth_response[:auth_route]
   end
   ```
2. Attacker lures victim to `GET /login` with header/param `shop=evil.example.com`.
3. `ShopifyAPI::Auth::Oauth.begin_auth` returns `auth_route = "https://evil.example.com/admin/oauth/authorize?client_id=...&scope=...&redirect_uri=https://app.example.com/auth/callback&state=<nonce>"` — no exception raised, no domain check performed, per `lib/shopify_api/auth/oauth.rb` lines 22-52 and 117-128.
4. Victim's browser is redirected to `evil.example.com`, which logs the leaked `state` (and sets a matching `state` cookie on `app.example.com` in the victim's browser).
5. Attacker performs a real OAuth authorization for a Shopify shop they control, injecting the captured `state` as the `state` query parameter to Shopify's `/admin/oauth/authorize`.
6. Shopify signs and redirects back to `https://app.example.com/auth/callback?code=...&shop=<attacker_shop>&state=<victim's leaked nonce>&hmac=<valid>`; attacker sends this URL to the victim.
7. Victim's browser (still holding the matching `state` cookie) completes `validate_auth_callback`, which accepts the request as legitimate, per `lib/shopify_api/auth/oauth.rb` lines 64-71 — forcing OAuth completion under attacker-controlled parameters.
