### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` extracts the shop identity that a webhook handler will act on (`shop-domain` header) separately from the bytes that the HMAC actually signs. The HMAC computed by `HmacValidator` only covers the raw request body, not the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers, so the shop that ends up in `WebhookMetadata` is never bound to the signature that authenticates the request.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, independent of the body: [2](#0-1) 

`Utils::HmacValidator.validate` verifies `verifiable_query.hmac` against `verifiable_query.to_signable_string` only: [3](#0-2) 

`Registry.process` validates the HMAC and then trusts `request.shop` — a value that was never part of the signed bytes — to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

This breaks the identity binding `shop authenticated == shop trusted by handler`: the HMAC proves "this body was signed with the app's secret," but it proves nothing about which shop the body/header combination is claimed to originate from. Since the app's `api_secret_key` is shared across all shops installing the app (it is not per-shop), any party who can obtain one valid `(raw_body, hmac)` pair — for instance, from a legitimate webhook fired to their own shop, or from any webhook topic whose body is identical/predictable across shops — can replay that exact body+hmac to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. `HmacValidator.validate` will still succeed because it only checks the body, and `Registry.process` will hand the attacker-chosen shop domain to the handler as if it were authenticated.

### Impact Explanation
This is a cross-tenant identity confusion: an unprivileged party (anyone who can trigger or capture one valid webhook delivery for any shop) can cause the app's webhook handler to process attacker-controlled `shop` values with a body that passes HMAC verification. Depending on how the host application uses `WebhookMetadata#shop` (e.g., looking up per-shop session/tokens, updating per-shop state), this can lead to cross-tenant data manipulation or acting on behalf of a shop the attacker does not own — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Requires the attacker to first obtain one valid `(body, hmac)` pair, which is available to them for any shop where the app is installed and reachable (e.g., their own development/trial store, or any webhook topic with static/predictable payloads such as `shop/redact` or app-uninstalled events with minimal body content). No access token, secret key, or privileged account is needed — only the ability to receive or trigger a webhook and then replay it with a modified `shop-domain` header to the app's public endpoint.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signed material, or have `Registry.process` derive/verify the shop independently of the untrusted header — e.g., cross-check `request.shop` against the shop associated with the session/store used to register the webhook, or bind the header value into `to_signable_string` before HMAC validation.

### Proof of Concept
1. App has any webhook registered and reachable at a public URL, using a single shared `api_secret_key`.
2. Attacker installs the app on their own shop (or otherwise triggers/observes one legitimate webhook delivery), capturing a valid `(raw_body, X-Shopify-Hmac-Sha256)` pair for topic `T`.
3. Attacker resends the exact same `raw_body` and `hmac` header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `HmacValidator.validate(request)`, which only checks `raw_body` against the hmac — this passes. [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the shop was never authenticated, letting the attacker inject data attributed to a shop they do not control.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
