## Analog Found

### Title
Simplex solver prices intent fills off Uniswap V4 `slot0` spot tick instead of a TWAP, exposing escrowed funds to flash-loan price manipulation - (File: sdk/packages/simplex/src/funding/uniswapV4/UniswapV4LiquidityState.ts)

### Summary
The Simplex intent-filler reference implementation prices "venue" pairs (pairs with no static curve) directly from a Uniswap V4 pool's current `slot0` tick/`sqrtPriceX96`, the same manipulable "instantaneous price" primitive flagged in the source report, rather than a time-weighted average. The only defense is a static `referencePrice`/`maxDeviationBps` guard, which bounds deviation from a fixed reference but does not protect against short-lived, in-block manipulation of the live pool feeding a fill.

### Finding Description
`UniswapV4LiquidityState.refresh()` reads a pool's live state via `getSlot0` and stores `sqrtPriceX96`/`currentTick` directly on the hydrated position, which is then fed straight into an SDK `V4Pool` used for pricing: [1](#0-0) [2](#0-1) 

The pricing flow documentation confirms this pool mid is used verbatim to price and fill cross-asset orders, with no execution-cost or size-impact adjustment, and that the only safeguard is a static-reference deviation check: [3](#0-2) 

The developer docs for this feature independently acknowledge the exact risk class from the source report — that "pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote" — and mitigate it only with a static reference/deviation bound, not a TWAP: [4](#0-3) 

This mirrors the reported bug class precisely: `LimitOrderRegistry.sol` used `slot0().tick` (the instantaneous, easily-moved value) to gate an economically consequential decision instead of `observe()`'s TWAP. Here, `getSlot0`'s instantaneous `sqrtPriceX96`/tick is used to compute the exact fill rate (`computeDirectPoolPriceUsd`) for orders that move the solver's escrowed inventory, gated only by a fixed reference band rather than a robust time-weighted price.

### Impact Explanation
An attacker who can move a thinly-liquid or flash-loanable Uniswap V4 pool backing a venue-priced pair within the same block can shift the pool's spot tick to the edge of (or within) the configured `maxDeviationBps` band just before the solver quotes/fills an intent order against that pool. Because the fill price is the raw pool mid with "no size or impact term" and the guard checks only static deviation (not execution cost or manipulation resistance), the solver can be induced to deliver output tokens at a rate worse than the pool's true equilibrium price, transferring value from the solver's funded inventory to the order placer/attacker. This is a direct funds-loss vector for the party funding intent fills, analogous to the audit's OTM order-cancellation manipulation via `slot0`.

### Likelihood Explanation
Exploitability depends on the liquidity depth of the specific Uniswap V4 pool configured for a given exotic-token pair and on how tightly `maxDeviationBps`/`referencePrice` are configured by the operator. Thin pools or freshly-configured pairs with a wide deviation tolerance are realistically flash-loan-manipulable within a single block, matching the "low liquidity" precondition called out in the original report. Because this component is operator-configured off-chain solver logic (not core Hyperbridge consensus/dispatch/escrow contracts), likelihood is bounded by operator pool/parameter choices rather than being universally exploitable across all deployments.

### Recommendation
Replace or supplement the `slot0`-derived spot price with a Uniswap V4 TWAP (time-weighted average tick) oracle for venue-priced pairs, and factor in trade size/impact rather than treating the raw mid as executable at any size. Tighten `maxDeviationBps` defaults and consider requiring a minimum observation window before a newly-manipulated price is trusted, consistent with the original report's recommendation to use `observe()`-style TWAP data instead of instantaneous `slot0` reads.

### Proof of Concept
1. Operator configures a venue-priced pair (`[vault.uniswapV4]`) against a Uniswap V4 pool with moderate liquidity and a permissive `maxDeviationBps`.
2. Attacker takes a flash loan and swaps against the pool to move `sqrtPriceX96`/tick to the edge of the allowed deviation band (per `checkPriceGuard`, checked only against a static `referencePrice`).
3. Attacker submits (or times) an intent order sized so `resolveLegRates`/`getVenueUsdPrice` in `sdk/packages/simplex/src/strategies/fx.ts` reads the manipulated `slot0` state via `UniswapV4LiquidityState.refresh()` [5](#0-4)  before the pool reverts to its equilibrium price.
4. The solver fills at the manipulated mid price, losing the difference between the manipulated and equilibrium rate from its funded inventory; attacker reverses the initial swap and repays the flash loan, netting the difference.

## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.

```toml lineNumbers
[vault.uniswapV4]
# referencePrice is the expected cNGN per USD;
# reject if the quote is more than 2% off.
# The two go together — one without the other is rejected.
[[vault.uniswapV4.positions]]
chain           = "EVM-8453"
tokenId         = "2087350"
referencePrice  = "1575"
maxDeviationBps = 200
```
