### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, while the `shop` (and `topic`) values used to route and label the event are taken from unauthenticated HTTP headers that are never included in the signed payload. Any party who can obtain one validly-signed webhook body/HMAC pair for a shop that has installed the app (which any merchant can do simply by generating an event on their own store) can replay that exact body+HMAC to the app's shared webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value, causing the handler to process attacker-controlled data as if it originated from a different, victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read directly from HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Registry.process` validates only the body's HMAC via `Utils::HmacValidator.validate(request)`, and then immediately dispatches the handler using the unauthenticated `request.shop` field: [3](#0-2) 

`HmacValidator.validate_signature` computes the HMAC purely over `verifiable_query.to_signable_string`, i.e., only the body: [4](#0-3) 

Because the app registers a single, shared webhook callback URL per app (not per shop) and every shop's webhooks are signed with the same global `api_secret_key`, the identity binding the app relies on is: `HMAC(secret, body)` ⇒ implies `shop == header["shopify-shop-domain"]`. This equality does not hold: the HMAC only proves "this body was produced with knowledge of the app's secret for *some* installed shop," not "this body belongs to the shop named in this header." An unprivileged merchant who has legitimately installed the app can trigger a real webhook for their own store (e.g., `customers/create` with attacker-chosen name/email fields, or any other webhook whose JSON body content they influence), capture the genuine `x-shopify-hmac-sha256` value Shopify computed for that body, and resend that exact body + HMAC to the app's public webhook endpoint with the `x-shopify-shop-domain` header rewritten to a different, victim shop domain. `HmacValidator.validate` passes because the body and signature are untouched, and `Registry.process` invokes the topic handler with `WebhookMetadata` carrying the forged `shop` value.

### Impact Explanation
This breaks the tenant boundary the library is expected to enforce for webhook processing (`shop` acted on but not covered by the HMAC). A host application that uses `request.shop`/`WebhookMetadata#shop` to route processing (persist orders, update local records, trigger emails, look up the correct merchant's stored access token, etc.) will attribute attacker-controlled data to an arbitrary victim shop, i.e., cross-tenant data injection/confusion sourced entirely from this gem's webhook verification design. This matches the allowed impact category of cross-tenant access.

### Likelihood Explanation
Exploitation requires only: (1) the attacker's own legitimate, unprivileged installation of the target app on a shop they control (the normal, unprivileged path any merchant can take), and (2) the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with modified headers, which is straightforward and requires no secret, token, or network interception. No `api_secret_key`, access token, or privileged account is needed beyond what any ordinary merchant already has by installing the app once.

### Recommendation
Bind the identifying fields into the signed payload verification instead of trusting raw headers:
- Include `shop`/`shop-domain` (and ideally `topic`) as part of the HMAC-verified material, or
- Cross-check `request.shop` against the shop associated with the specific webhook subscription/session that was registered for that topic before invoking the handler, and
- Document/require host applications to validate that the `shop` header corresponds to a shop with an active, known session/installation before trusting event data as belonging to that shop.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` (fully legitimate, unprivileged action).
2. Attacker triggers an event (e.g., creates a customer with a crafted name field) causing Shopify to send a real webhook to the app's shared callback URL, with headers:
   - `x-shopify-topic: customers/create`
   - `x-shopify-hmac-sha256: <valid HMAC over the JSON body, using the app's secret>`
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
3. Attacker captures this exact raw JSON body and HMAC value (visible to them since it's their own request/response cycle, or replays their own genuine webhook delivery).
4. Attacker resends an HTTP POST to the app's webhook endpoint with the identical body and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the (unmodified) body against the (unmodified) HMAC — see `lib/shopify_api/utils/hmac_validator.rb` lines 26-31 and `lib/shopify_api/webhooks/request.rb` lines 35-38.
6. The registered handler is invoked with `WebhookMetadata.new(topic: "customers/create", shop: "victim-shop.myshopify.com", body: <attacker JSON>, ...)` (`lib/shopify_api/webhooks/registry.rb` lines 198-199), causing the host app to process attacker-controlled data under the victim shop's identity.

          unless handler
