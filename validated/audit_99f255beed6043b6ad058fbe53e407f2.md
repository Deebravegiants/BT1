Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from an HTTP header that is never part of the HMAC-signed payload. `Registry.process` validates only that the HMAC matches the raw body, then forwards the caller-supplied `shop` header value unmodified into `WebhookMetadata`. An attacker who owns any shop that installed the app can obtain a validly-signed webhook body from Shopify for their own shop, then replay that same body/HMAC pair to the app's webhook endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header rewritten to point at a victim shop. The signature still validates because the shop value is outside the signable string.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from an attacker-controlled header with no cryptographic binding to the body or the HMAC: [2](#0-1) 

`HmacValidator.validate`/`validate_signature` compute the HMAC solely over `verifiable_query.to_signable_string`, i.e., the raw body — the shop domain is never included in the digest: [3](#0-2) 

`Registry.process` performs exactly one check — `Utils::HmacValidator.validate(request)` — and, once it passes, constructs `WebhookMetadata` directly from `request.shop` (the unauthenticated header) and hands it to the app's handler: [4](#0-3) 

This breaks the intended identity binding: `shop authenticated by HMAC == shop stored/acted upon`. In reality the HMAC only authenticates *that this body was produced by Shopify for some shop*, not *that the accompanying shop-domain header is the shop the body belongs to*. The gem's own documentation instructs consumers to trust `data.shop` directly (e.g., to look up records or enqueue jobs keyed by shop) without any further verification, since the gem states that `process` "will verify the request did indeed come from Shopify": [5](#0-4) [6](#0-5) 

### Impact Explanation
Any merchant/attacker who has installed the app (a normal, unprivileged install) can generate arbitrarily many legitimately-HMAC'd webhook bodies for their own store (Shopify sends these directly to the app's endpoint, and they are also visible/reproducible by the shop owner). By replaying such a body with a forged `shop-domain` header, the attacker can make the app process webhook data purportedly belonging to a different, victim shop. Because the library treats `request.shop` as the trusted tenant identifier and passes it straight to `WebhookMetadata` for host applications to key off of (e.g., record updates, mandatory GDPR topics such as `customers/redact`, `shop/redact`), this is a **cross-tenant boundary bypass** rooted entirely in this gem's webhook verification logic, not merely a downstream host mistake — the gem itself supplies no guarantee that `shop` is authenticated.

### Likelihood Explanation
High/practical: no secrets are required beyond running/owning a shop that has the target app installed (which any of the app's own customers can do), and forging an HTTP header is trivial. The only "special" data needed (a validly HMAC'd body) is routinely delivered to the attacker's own endpoint by Shopify itself.

### Recommendation
Bind the shop identity into the HMAC-verified material, or independently authenticate the shop domain against server-side state (e.g., cross-check `request.shop` against the topic/webhook_id/session record obtained via a separate trusted lookup, or include the shop header in the signable string if Shopify's webhook signing scheme supports it). At minimum, the gem should document/enforce that `data.shop` must not be treated as authenticated on its own, or perform its own verification (e.g., only accept shops the app has confirmed still have an active session/webhook registration matching the delivered `webhook_id`).

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and registers for topic `customers/redact` (or any topic).
2. Shopify sends a legitimately signed webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid hmac of body>`.
3. Attacker (who controls network calls / can replay HTTP requests to the app's public webhook endpoint) resends the identical raw body and HMAC header, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers; `HmacValidator.validate` succeeds because it only checks the raw body against the secret — the shop header plays no role: [7](#0-6) [1](#0-0) 
5. `Registry.process` calls the app's handler with `WebhookMetadata` containing `shop: "victim.myshopify.com"`, causing the app to act as though the (attacker-controlled) payload came from the victim tenant: [4](#0-3)

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
