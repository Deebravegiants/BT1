### Title
`numberToBigEndian` in `computeTonConnectHash` mis-encodes 64-bit `timestamp` values ≥ 2^31 due to JS 32-bit signed bitwise operators, causing local intent-hash divergence from the relayer's `intent_hash` - (File: `packages/intents-sdk/src/intents/intent-hashes/ton-connect.ts`)

### Summary
`numberToBigEndian` (packages/intents-sdk/src/intents/intent-hashes/ton-connect.ts, lines 13-20) uses `num & 0xff` and `num >>= 8`, both of which coerce `num` via `ToInt32` in JavaScript. For `timestamp` values ≥ 2^31 this causes the shifted value to become negative and arithmetic-shift-preserve its sign bits forever, so bytes beyond the low 32 bits are incorrectly filled with `0xFF` instead of `0x00`. This breaks `computeTonConnectHash(multiPayload) === <relayer-computed intent_hash>` for any correctly-implemented 64-bit big-endian reference encoder used server-side.

### Finding Description
The equality under test is:
`computeIntentHash(multiPayload)` (client-side, via `computeTonConnectHash`) `==` `intent_hash` returned by `intentRelayer.publishIntent` (server-side, presumably a correct 64-bit big-endian packer per the TON Connect sign-data spec comment at lines 30-45).

Tracing `numberToBigEndian(Number(timestamp), 8)` at line 72:
- For `timestamp = 2**32 - 1` (4294967295), the loop runs `i = 7 downto 0`.
- At `i=7`: `num & 0xff` → JS applies `ToInt32(4294967295)` = `-1` (since 4294967295 ≥ 2^31, it wraps to a 32-bit signed value of `-1`). `-1 & 0xff = 255`. Correct LSB.
- `num >>= 8`: `ToInt32(num) >> 8` = `-1 >> 8` = `-1` (arithmetic shift preserves sign, all bits remain `1`). `num` stays `-1` forever.
- Every subsequent iteration (`i=6..0`) computes `-1 & 0xff = 255`, filling **all 8 bytes with `0xFF`**.
- The correct 8-byte big-endian encoding of `4294967295` is `00 00 00 00 FF FF FF FF` (high 4 bytes zero, low 4 bytes `FF`), but the buggy code produces `FF FF FF FF FF FF FF FF`.

This diverges from any spec-correct 64-bit encoder (e.g., using `BigInt` shifts or `DataView.setBigUint64`) that a relayer would use to independently recompute `intent_hash`. None of the codebase's existing guards (`validateAddress`, `compareAddresses`, `validateWithdrawal`, `FeeExceedsAmountError`, contract-level signature/nonce checks) touch this hashing logic — they operate on address/fee/nonce validation, not on TON Connect byte-packing, so nothing intercepts or corrects the divergence before `computeIntentHash` is compared against the relayer's returned hash.

### Impact Explanation
When `computeIntentHash(multiPayload)` disagrees with the relayer's authoritative `intent_hash`, `waitForSettlement` (or equivalent status-polling logic) tracks the wrong ticket/hash. The already-signed and already-submitted intent is reported as "not found"/unsettled even though it was accepted by the relayer, leading an integrator or caller to resubmit or treat the withdrawal as failed — a status/hash misreport that can cause double-crediting/refund logic to fire incorrectly. This matches the **High** severity category ("a status or hash misreport making an integrator credit or refund twice").

### Likelihood Explanation
Preconditions: the `timestamp` field in the `ton_connect` `MultiPayload` must reach ≥ 2^31 (2147483648). If, per the TON Connect spec referenced in the file's own comment, `timestamp` is a Unix time in **seconds**, ordinary current timestamps (~1.79×10^9 in 2026) remain below 2^31 and won't trigger this until on the order of 2038 (`2^31` seconds ≈ Jan 19 2038), reducing near-term exploitability under normal SDK-generated timestamps. However, if the timestamp field is caller-supplied (as the question's threat model asserts — an ordinary user building their own signed payload can pick an arbitrary timestamp value), a user can trivially set `timestamp = 2**32 - 1` (or any value ≥ 2^31) themselves at zero cost and reproduce the divergence deterministically and repeatably on every such call.

### Recommendation
Rewrite `numberToBigEndian` to avoid JS's 32-bit signed bitwise coercion entirely, e.g. use `BigInt`-based shifting/masking or `DataView`/`Buffer` with `setBigUint64`/`writeUInt32BE` pairs for the high/low 32-bit halves:
```ts
function numberToBigEndian(num: number | bigint, bytes: number): Uint8Array {
  let n = BigInt(num);
  const result = new Uint8Array(bytes);
  for (let i = bytes - 1; i >= 0; i--) {
    result[i] = Number(n & 0xffn);
    n >>= 8n;
  }
  return result;
}
```
and update the call site at line 72 to pass `BigInt(timestamp)` so the encoding is correct for the full 64-bit range.

### Proof of Concept
```ts
import { describe, it, expect } from "vitest";
import { computeTonConnectHash } from "../ton-connect";
import { sha256 } from "@noble/hashes/sha2";

function correctBigEndian(num: bigint, bytes: number): Uint8Array {
  const result = new Uint8Array(bytes);
  for (let i = bytes - 1; i >= 0; i--) {
    result[i] = Number(num & 0xffn);
    num >>= 8n;
  }
  return result;
}

it("diverges from correct 64-bit big-endian packing for timestamp >= 2^31", () => {
  const basePayload = {
    standard: "ton_connect" as const,
    address: "<valid ton address>",
    domain: "example.com",
    timestamp: 2 ** 32 - 1,
    payload: { type: "text" as const, text: "hello" },
  };

  const actual = computeTonConnectHash(basePayload);

  // Reference: hand-build the same message using correct 64-bit packing
  const parts = [
    new Uint8Array([0xff, 0xff]),
    new TextEncoder().encode("ton-connect/sign-data/"),
    /* workchainId 4 bytes */ correctBigEndian(0n, 4),
    /* address bytes */ new Uint8Array(32),
    correctBigEndian(BigInt("example.com".length), 4),
    new TextEncoder().encode("example.com"),
    correctBigEndian(BigInt(2 ** 32 - 1), 8), // 00 00 00 00 FF FF FF FF
    new TextEncoder().encode("txt"),
    correctBigEndian(BigInt("hello".length), 4),
    new TextEncoder().encode("hello"),
  ];
  const totalLength = parts.reduce((s, p) => s + p.length, 0);
  const message = new Uint8Array(totalLength);
  let offset = 0;
  for (const p of parts) { message.set(p, offset); offset += p.length; }
  const expected = sha256(message);

  expect(actual).not.toEqual(expected); // equality broken: computeTonConnectHash != correct 64-bit reference hash
});
```
This test directly demonstrates that `computeTonConnectHash(multiPayload)` (left side of the equality) diverges from the spec-correct hash a compliant relayer would compute (right side), confirming the `intent_hash` mismatch described in the question.
