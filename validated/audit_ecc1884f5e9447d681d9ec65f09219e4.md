### Title
Retroactive challenge-period reduction lets a relayer bypass the fraud-proof review window for already-pending state commitments - ([File: modules/ismp/core/src/handlers.rs])

### Summary
Hyperbridge's delay-period check compares the *current* configured challenge period against the timestamp a state commitment was stored, rather than the challenge period that was in effect at the time the commitment was created. Any lowering of the challenge period (a routine, non-malicious risk parameter, analogous to Apollon's `setCollTokenSupportedCollateralRatio`) instantly and retroactively shortens (or eliminates) the review window for commitments that are already pending, letting a relayer immediately push through previously-unripe requests/responses.

### Finding Description
`verify_delay_passed` in [1](#0-0)  computes:

```
delay_period = host.challenge_period(proof_height.id)   // read at call time
current_timestamp.saturating_sub(update_time) > delay_period
```

`update_time` is fixed at the moment the state machine commitment was stored (via `create_client`/consensus update), but `delay_period` is read live via `host.challenge_period(...)`, which is simply a stored value that can be changed at any time by an `UpdateConsensusState` message, see [2](#0-1)  and the storage map [3](#0-2) . There is no per-commitment snapshot of the challenge period that applied when the commitment was created — only a single mutable global/per-state-machine value is consulted.

The same pattern is mirrored on the EVM side in `HandlerV2.handlePostRequests`, which reads `host.challengePeriod()` (a single mutable value on `IHost`) and compares it against `block.timestamp - host.stateMachineCommitmentUpdateTime(...)`: [4](#0-3) . `challengePeriod` is one of the fields of `EvmHostParam` that can be updated wholesale via a cross-chain `EvmHostParamUpdate` message routed through the host manager, with no timelock or buffer applied to in-flight/pending commitments: [5](#0-4) . The test `test_host_manager_set_host_params` shows the challenge period is fully replaceable in a single message: [6](#0-5) .

This mirrors exactly the "no buffer to prevent a step-wise change" risk flagged in the Apollon report about `setCollTokenSupportedCollateralRatio`: the mechanism for enacting the parameter change (here, the challenge-period update) doesn't verify or preserve the invariant (fraud-proof review time) that other in-flight state depends on.

### Impact Explanation
The challenge period exists specifically to give fishermen time to submit a `FraudProof` against a byzantine/incorrect consensus update before requests/responses proven against it are honored (`Message::FraudProof` handling in `consensus::freeze_client`, referenced in [7](#0-6) ). If the challenge period is reduced (or set to 0) while a state commitment is still within its original review window, that commitment's requests become immediately deliverable, denying fishermen the promised time to detect and freeze a bad consensus update. A relayer who front-runs the parameter change (or simply is positioned to submit immediately after it lands) can force acceptance of a message proven against a commitment that has not yet completed the fraud-proof review it was entitled to — this is a forged/unsound-state-commitment delivery vector, matching the "Accept only concrete... forged message delivery, unsound state commitment" bar.

### Likelihood Explanation
This requires only a legitimate governance parameter update (reducing `challenge_period`/`challengePeriod`), which is a normal, expected operational action (analogous to routine risk-parameter tuning in Apollon) — not a malicious-governance assumption. The exploitation step itself (submitting `handlePostRequests`/dispatching the now-"matured" request) is performed by an ordinary, unprivileged relayer using the standard dispatch path, satisfying the "reachable by a single relayed proof" requirement.

### Recommendation
Snapshot the challenge period at the time each state machine commitment/height is stored (store it alongside `state_machine_update_time`/`stateMachineCommitmentUpdateTime`), and use that snapshotted value in `verify_delay_passed`/`handlePostRequests` rather than re-reading the live, mutable configuration value. Alternatively, enforce that a challenge-period reduction only applies to commitments created after the update, preserving the originally-promised review window for already-pending commitments.

### Proof of Concept
1. Hyperbridge governance (via `UpdateConsensusState`/`EvmHostParamUpdate`) sets `challenge_period` = 1 hour for state machine X.
2. A consensus update stores a new `StateCommitment` for X at `update_time = T` (via `create_client`/consensus handler, `modules/ismp/core/src/handlers/consensus.rs`).
3. At `T + 5 minutes`, governance legitimately reduces `challenge_period` to 0 (or a few seconds) for unrelated operational reasons.
4. A relayer immediately calls `handle_incoming_message`/`HandlerV2.handlePostRequests` with a `PostRequestMessage` proven against the height stored at step 2. `verify_delay_passed` now reads the new, reduced `challenge_period`, computes `T+5min - T = 5min > 0`, and returns `true`, allowing the request to be dispatched to its destination module — 55 minutes before fishermen were originally guaranteed to be able to submit a fraud proof against that commitment.

```rust
pub fn verify_delay_passed<H>(host: &H, proof_height: &StateMachineHeight) -> Result<bool, Error>
where
	H: IsmpHost,
{
	let update_time = host.state_machine_update_time(*proof_height)?;
	let delay_period = host
		.challenge_period(proof_height.id)
		.ok_or(Error::ChallengePeriodNotConfigured { state_machine: proof_height.id })?;
	let current_timestamp = host.timestamp();
	Ok(delay_period.as_secs() == 0 || current_timestamp.saturating_sub(update_time) > delay_period)
}
```
