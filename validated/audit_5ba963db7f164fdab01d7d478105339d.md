Audit Report

## Title
ERC20 Asset Transactor blindly trusts declared transfer amount instead of verifying actual balance delta, breaking accounting for fee-on-transfer/rebasing ERC20 tokens - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` credits `AssetsInHolding` with the nominal `amount` requested rather than the amount actually received by the checking account, and `deposit_asset_with_surplus` instructs a transfer of the nominal `amount` out of the checking account without verifying its real balance. [1](#0-0) [2](#0-1)  Combined with the unrestricted `ERC20Matcher`/`IsLocalAccountKey20`, which accepts any `AccountKey20` location with no registration or allow-list gate, an unprivileged user can deploy a fee-on-transfer or rebasing ERC20 contract via `pallet-revive` and desynchronize the shared checking account's real balance from the XCM-tracked credit. [3](#0-2) 

## Finding Description
`withdraw_asset_with_surplus` calls the ERC20 `transfer(checking_address, amount)` and, on a successful (non-reverted, `true`-returning) call, unconditionally constructs `Erc20Credit(amount)` using the caller-declared `amount` — it never reads `balanceOf(checking_address)` before/after the call to derive the actual amount received. [4](#0-3)  Symmetrically, `deposit_asset_with_surplus` transfers the nominal `amount` from the checking account to the beneficiary based purely on the amount extracted from the `AssetsInHolding` argument, again without any balance-delta verification. [5](#0-4)  The `Erc20Credit` imbalance type's own doc comment states that "actual balance constraints are enforced by the ERC20 smart contract itself rather than the runtime," confirming the code never re-derives credited amounts from a real balance check. [6](#0-5) 

Critically, there is no gatekeeping on which ERC20 contracts are eligible for this transactor: `ERC20Matcher` is built from `IsLocalAccountKey20`, which matches *any* local `AccountKey20` location unconditionally, unlike the `ForeignAssets`/`PoolAssets` transactors that require a non-zero-issuance/registration check via `NonZeroIssuance`. [3](#0-2) [7](#0-6)  This means any address that resolves to a deployed `pallet-revive` contract implementing the `IERC20` interface can be used through `WithdrawAsset`/`DepositAsset` XCM instructions without any registration, permission, or vetting step.

## Impact Explanation
Because the `TransfersCheckingAccount` is shared across all users of a given ERC20 contract, a user who deploys a fee-on-transfer/rebasing ERC20 and moves value through `withdraw_asset_with_surplus` causes the checking account's real balance to increase by less than the nominal amount, while the XCM holding register is credited with the full nominal amount. That inflated credit can subsequently be deposited elsewhere via `deposit_asset_with_surplus`, which withdraws the full nominal amount from the checking account — either failing (denial of service for legitimate depositors of the same asset) once accumulated shortfall exceeds actual balance, or succeeding by consuming balance that should have backed other users' claims (fund loss for other holders of that asset). This is a genuine accounting break in an in-scope Polkadot SDK component (the XCM asset transactor used on Asset Hub), reachable without any special privilege.

## Likelihood Explanation
The precondition (deploying an arbitrary contract via `pallet-revive` and referencing it in an XCM `WithdrawAsset`/`DepositAsset` program) requires no privilege beyond normal user access to `pallet-revive` contract deployment and XCM execution, both of which are exposed to ordinary users. The matcher performs no allow-listing or registration check, so the attack path is fully self-serve. [8](#0-7)  This is repeatable and does not depend on victim mistakes, governance actions, or unrealistic assumptions — it depends only on the attacker controlling the ERC20 contract's transfer logic, which is standard when deploying arbitrary bytecode.

## Recommendation
Modify `withdraw_asset_with_surplus` and `deposit_asset_with_surplus` in `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs` to read `balanceOf` of the relevant account (checking account or beneficiary) before and after the `transfer` call, and credit/debit `AssetsInHolding` using the observed balance delta rather than the caller-declared `amount`. Alternatively, restrict `ERC20Matcher`/`IsLocalAccountKey20` to an explicit allow-list of vetted, standard-compliant (non-rebasing, non-fee-on-transfer) ERC20 contracts before they can be used as XCM fungible assets.

## Proof of Concept
1. Deploy an ERC20 contract via `pallet-revive` whose `transfer(to, amount)` deducts a fee (e.g., sends `0.95 * amount` to `to`, discarding the remainder) while still returning `true`.
2. Submit an XCM program with `WithdrawAsset` for `{ parents: 0, interior: [AccountKey20 { key: <contract address> }] }`, amount `X`, from the attacker's own account — matched unconditionally by `ERC20Matcher`/`IsLocalAccountKey20`.
3. `withdraw_asset_with_surplus` transfers nominal `X` to `TransfersCheckingAccount`; the real balance only increases by `0.95X`, but `Erc20Credit(X)` is minted into the XCM holding register (`erc20_transactor.rs:168-203`).
4. Follow with `DepositAsset` targeting a second beneficiary for amount `X`; `deposit_asset_with_surplus` instructs the checking account to send out the full nominal `X` (`erc20_transactor.rs:253-266`), which either fails once shortfall accumulates across users of the asset (DoS) or succeeds by spending balance backing other users' deposits (fund loss), demonstrating the state/accounting mismatch caused by the non-standard ERC20 transfer semantics and the absence of any balance-delta verification or registration gate.

/// `Contains<Location>` implementation that matches locations with no parents,
/// a `PalletInstance` and an `AccountKey20` junction.
pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}
