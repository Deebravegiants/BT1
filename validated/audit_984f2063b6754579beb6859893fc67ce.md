## Title
Webhook `shop` Tenant Identity Not Covered by HMAC Signature, Enabling Cross-Tenant Webhook Replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The library's webhook HMAC validation only authenticates the raw request body. The `shop` field that identifies *which tenant* a webhook belongs to is read straight from an unauthenticated HTTP header and handed to the app's handler as trusted tenant identity, even though that header is never part of the signed bytes.

### Finding Description
`ShopifyAPI::Webhooks::Request` exposes `shop` by reading the `shopify-shop-domain`/`x-shopify-shop-domain` header directly: [1](#0-0) 

Its HMAC, however, is computed only over the raw body (`to_signable_string` returns `@raw_body`), and the `hmac` accessor reads the signature from the `hmac-sha256` header: [2](#0-1) [3](#0-2) 

`Utils::HmacValidator.validate` verifies the HMAC by recomputing it from `verifiable_query.to_signable_string` (i.e., the body only) and comparing to the received signature — the `shop` header is never fed into this computation: [4](#0-3) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant identity passed into the handler's `WebhookMetadata`: [5](#0-4) 

The equality the design implicitly claims is: *`shop` bound to the signature == `shop` used for tenant dispatch*. In reality, only `body` is bound to the signature; `shop` is an independent, unauthenticated header value. Any payload/signature pair that is valid for one shop's body remains cryptographically valid if replayed with a different `shop-domain` header, because that header was never part of `to_signable_string`.

### Impact Explanation
This breaks the tenant boundary the HMAC is supposed to enforce: an attacker who obtains one legitimate `(body, hmac)` pair (e.g., from their own shop's webhook delivery logs, which merchants/developers can view in the Partner Dashboard or via CLI webhook-trigger tooling) can replay that exact body/HMAC to the app's webhook endpoint while substituting a different `x-shopify-shop-domain` value. `Utils::HmacValidator.validate` will still return `true` (the body is unchanged), and `Registry.process` will dispatch the handler with the attacker-chosen `shop`, causing the app to process webhook data under another tenant's identity — a cross-tenant confusion in a multi-tenant app.

### Likelihood Explanation
Requires no `api_secret_key`, no TLS interception, and no elevated privileges — only the ability to install/operate the app as an ordinary merchant/developer and to send an HTTP request to the app's public webhook endpoint with a header changed. Capturing one's own valid `(body, hmac)` sample is routine (webhook delivery logs, test triggers).

### Recommendation
Include the tenant-identifying header (`shop-domain`) in the signed/verified material, or otherwise cross-check it out-of-band (e.g., verify the shop against a known, registered shop for that webhook subscription/topic) before trusting `request.shop` for dispatch, rather than deriving tenant identity solely from an unauthenticated header while only the body is HMAC-covered.

### Proof of Concept
1. App has two tenants installed: `victim.myshopify.com` and `attacker.myshopify.com`.
2. Attacker, as an ordinary merchant, triggers a legitimate webhook for their own shop (e.g., via Shopify CLI `webhook trigger` or by viewing delivery details in the Partner Dashboard) and captures the exact `raw_body` and `x-shopify-hmac-sha256` value Shopify sent.
3. Attacker POSTs to the app's webhook endpoint reusing that identical `raw_body` and `hmac-sha256` value, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes the HMAC over `raw_body` only (per `lib/shopify_api/webhooks/request.rb`'s `to_signable_string`) — it matches, since `shop` was never part of the signed content.
5. `Registry.process` dispatches the handler with `shop: "victim.myshopify.com"`, causing the app to process attacker-controlled webhook data under the victim tenant's identity.
