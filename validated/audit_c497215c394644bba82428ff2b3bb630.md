### Title
Locked/unseeded `MemoizedKeychain` clone discloses cached public key data (xpub/publicKey) via `exportKey` without requiring `addSeed` - ([File: features/keychain/module/memoized-keychain.js])

### Summary
`MemoizedKeychain.exportKey` checks its persisted public-key cache (`#getCachedKey`) before invoking the base `Keychain.exportKey`, which is the only place that validates the seed actually exists on that instance. Because `clone()` returns `new MemoizedKeychain(this.#cloneOpts)` sharing the same `storage`, a freshly cloned instance loads the same persisted cache and can serve `exportKey` results for a `seedId`/`keyId` pair it has never received via `addSeed`.

### Finding Description
In [1](#0-0) , `exportKey` calls `#getCachedKey(keyId)` (where the passed argument is actually the `{seedId, keyId}` object) and returns the cached value immediately if present, **before** ever calling `super.exportKey()`. The base `Keychain.exportKey` in [2](#0-1)  is the only code path that asserts the seed is unlocked/present via `#getPrivateHDKey`, which enforces `assert(this.#masters[seedId], ...)` at [3](#0-2) . Since the memoized cache-hit path skips this call entirely, no ownership/lock check is performed for cached entries.

The cache itself is persisted to shared `storage` via `#setCachedKey` at [4](#0-3) , and `clone()` at [5](#0-4)  constructs a new instance with the same `storage` reference from `#cloneOpts` (set in the constructor at [6](#0-5) ). The constructor asynchronously reloads `#publicKeys` from that shared storage on every instantiation, including for clones, independent of whether `addSeed` is ever called on the clone.

As a result, calling `clone.exportKey({ seedId, keyId }, { exportPrivate: false })` on a clone that has never had `addSeed` invoked can return the same `{ xpub, publicKey }` data that was cached by the original, fully-seeded instance — bypassing the seed-existence/lock invariant that the base class otherwise enforces uniformly for all key operations (as demonstrated by the lock/unlock test suite in [7](#0-6) , which shows the base class does enforce these checks when the memoized cache doesn't short-circuit them).

### Impact Explanation
An unprivileged holder of a cloned/locked `MemoizedKeychain` instance (one which has not had `addSeed` called and holds no private master keys) can retrieve real wallet address material (xpub/public key) for accounts belonging to the original seeded instance, purely because both instances share the same persisted cache storage. This violates the intended AUTH_BOUNDARY where a locked/unseeded keychain instance should expose no account-bound key material — matching an address/xpub disclosure impact class.

### Likelihood Explanation
This requires: (1) the original keychain to have previously called `exportKey` for a given `seedId`/`keyId` (populating the shared persisted cache), and (2) a `clone()` call, and (3) the caller of `clone.exportKey` to know the `seedId`/`keyId` pair it wants to query (both are derivable/predictable — `seedId` is a deterministic hash of the seed, and `keyId` follows well-known derivation-path conventions used throughout the codebase). Given `clone()` is a first-class supported method sharing storage by design, and the exploit requires no privileged state or malicious peer, this is straightforward to reproduce in a unit test.

### Recommendation
In `MemoizedKeychain.exportKey`, before serving a cache hit, verify that the seed corresponding to `seedId` actually exists/is unlocked on the current instance (e.g., delegate a lightweight existence/lock check to the base class, or track known seed IDs per-instance and only serve cache entries for seed IDs added via `addSeed`/`unlockPrivateKeys` on that instance). Alternatively, do not share the raw public-key cache across clones without also validating instance-level seed ownership on read.

### Proof of Concept
```js
// integration test in features/keychain/module/__tests__/memoized-keychain.test.js
import { mnemonicToSeed } from '@exodus/bip39'
import KeyIdentifier from '@exodus/key-identifier'
import memoizedKeychainDefinition from '../memoized-keychain.js'
import { getSeedId } from '../crypto/seed-id.js'

test('locked/unseeded clone must not disclose cached public key data', async () => {
  const storage = createInMemoryStorage() // simple get/set/delete impl
  const keychain = memoizedKeychainDefinition.factory({ storage, legacyPrivToPub: {} })

  const seed = await mnemonicToSeed({ mnemonic: '...' })
  const seedId = await getSeedId(seed)
  const keyId = new KeyIdentifier({
    derivationAlgorithm: 'SLIP10',
    derivationPath: "m/0'/2'/0'",
    keyType: 'nacl',
  })

  await keychain.addSeed(seed)
  await keychain.exportKey({ seedId, keyId }) // caches entry in shared storage

  const clone = keychain.clone() // NOT seeded

  // Give the async storage.get(CACHE_KEY).then(...) in constructor a chance to resolve
  await new Promise((r) => setTimeout(r, 0))

  await expect(
    clone.exportKey({ seedId, keyId }, { exportPrivate: false })
  ).rejects.toThrow() // EXPECTED to throw ("seed ... is not initialized" or similar)
  // Currently FAILS: clone.exportKey resolves with cached { xpub, publicKey } instead of throwing.
})
```
Expected (fixed) behavior: the assertion rejects because the clone has no knowledge of `seedId`. Current behavior: the promise resolves with the cached public key data, confirming the disclosure.

    assert(typeof seedId === 'string', 'seedId must be a string')

    if (exportPrivate) {
      this.#assertPrivateKeysUnlocked([seedId])
    }

    keyId = new KeyIdentifier(keyId)

    const hdkey = this.#getPrivateHDKey({
      seedId,
      keyId,
      getPrivateHDKeySymbol: this.#getPrivateHDKeySymbol,

    const privateKey = hdkey.privateKey
    let publicKey = null

    if (exportPublic) {
      publicKey = await this.#getPublicKeyFromHDKey({ hdkey, keyId })

    const { xpriv, xpub } = hdkey.toJSON()
    return {
      xpub: exportPublic ? xpub : null,
      xpriv: exportPrivate ? xpriv : null,
      publicKey,
