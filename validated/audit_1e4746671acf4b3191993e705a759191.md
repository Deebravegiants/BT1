### Title
Webhook `shop` field is not covered by HMAC, allowing cross-tenant shop-attribution spoofing via replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns `@raw_body`, so the HMAC signature verified by `Utils::HmacValidator.validate` binds solely to the JSON body. The `shop` accessor, which is used as the tenant identity for dispatching the webhook payload to the app's handler, is read directly from the `x-shopify-shop-domain` header and is never included in the signed bytes.

### Finding Description
`Webhooks::Registry.process` gates processing on `Utils::HmacValidator.validate(request)` [5](#0-4) , which recomputes the HMAC over `verifiable_query.to_signable_string` [6](#0-5) . For `Webhooks::Request`, `to_signable_string` is simply `@raw_body` [1](#0-0) . Meanwhile `shop` is parsed straight out of an HTTP header with no cryptographic binding to the signature [2](#0-1) . The equality the HMAC is supposed to guarantee — "the `shop` acted on == the `shop` Shopify actually sent this webhook for" — is never checked; only "the `body` acted on == the `body` Shopify signed" is checked. `Registry.process` then trusts `request.shop` and threads it straight into `WebhookMetadata.shop`, delivered to the host app's `handle` implementation [7](#0-6) , which typically uses `shop` as the tenant key to look up sessions/data for that merchant (per `docs/usage/webhooks.md` handler examples).

### Impact Explanation
An attacker who obtains one legitimately-signed webhook delivery (raw body + HMAC pair — e.g., from a low-value/publicly-observable topic, or a previous delivery to the app's endpoint) can replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a different merchant's shop domain. Because the signature check never covers the `shop` header, `Utils::HmacValidator.validate` still returns `true`, and `Registry.process` will hand the payload to the handler tagged as belonging to the attacker-chosen shop. If the host application uses `WebhookMetadata#shop` (as documented) to select which tenant's data/session the payload is applied to, this causes cross-tenant data injection/corruption — the app processes and attributes attacker-controlled data to a shop the attacker does not control.

### Likelihood Explanation
Requires only network access to the app's public webhook receiving endpoint and possession of any one valid `(raw_body, hmac)` pair previously delivered by Shopify (replay), no `api_secret_key` or access token needed. This is a realistic condition since webhook endpoints are internet-facing by design.

### Recommendation
Include the `shop` (and ideally `topic`, `api-version`, `webhook-id`) header values in the signable string used for HMAC verification, or otherwise cryptographically bind `shop` to the signature check in `Webhooks::Request#to_signable_string` / `Utils::HmacValidator`, so a body cannot be replayed under a different shop's identity.

### Proof of Concept
1. Capture a legitimately Shopify-signed webhook delivery to the app: raw body `B` and header `x-shopify-hmac-sha256: H` (valid because `HMAC(secret, B) == H`).
2. Replay a POST to the app's webhook endpoint with the same body `B` and same `x-shopify-hmac-sha256: H`, but set `x-shopify-shop-domain: victim-shop.myshopify.com` (a different shop than the one that originally triggered the webhook).
3. `Webhooks::Request.new` accepts it (all required headers present) [8](#0-7) ; `Utils::HmacValidator.validate` recomputes HMAC over `B` only and it matches `H`, returning `true` [6](#0-5) .
4. `Registry.process` dispatches to the handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"` even though Shopify never sent that webhook for that shop [3](#0-2) .
