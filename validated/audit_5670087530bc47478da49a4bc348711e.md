### Title
Webhook shop-domain/topic headers are not covered by HMAC, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read from separate, unsigned HTTP headers. `Webhooks::Registry.process` validates only the body HMAC and then trusts these headers to route the payload and to populate `WebhookMetadata#shop`/`#topic` passed to the app's handler. Because a single `api_secret_key` is shared across every shop that installs a public app, any shop that can trigger a legitimate webhook to the app (by acting on its own store) obtains a body + valid HMAC pair that remains valid no matter what `shop-domain`/`topic`/`webhook-id` headers are attached to a replayed request.

### Finding Description
`HmacValidator.validate` calls `validate_signature`, which computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the supplied `hmac` [3](#0-2) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` values are derived from headers (`shopify-shop-domain`, `shopify-topic`, etc.) that are never included in the signed material [4](#0-3) .

`Registry.process` performs `Utils::HmacValidator.validate(request)` — verifying only that the body was HMAC-signed by *some* installation of the app using the shared `api_secret_key` — and then unconditionally uses `request.topic` for handler dispatch and `request.shop` to build `WebhookMetadata` delivered to the app's business logic [2](#0-1) .

The equality this construction implicitly (and incorrectly) assumes is:
`shop_header == shop_that_the_HMAC-signed_body_actually_originated_from`

But the HMAC only proves `body == body_signed_by_shopify_with_this_app's_secret`; it says nothing about which shop's event produced that body. An unprivileged internet user who owns/installs the target app on their **own** shop can trigger any webhook topic they control (e.g., `products/update`) to get Shopify to send a genuinely HMAC-signed `(raw_body, hmac)` pair to the app's public webhook endpoint. They can then replay that exact body and HMAC while substituting the `X-Shopify-Shop-Domain` header (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) to name a victim shop. `HmacValidator.validate` still succeeds because it never inspected those headers, and `Registry.process` will hand the attacker-crafted `shop`/`topic`/`body` combination to the handler as if Shopify itself vouched for that specific shop and topic.

### Impact Explanation
This breaks the tenant-identity binding that app developers reasonably assume the gem enforces (`HMAC valid` ⇒ `shop/topic header is trustworthy`). Depending on how the host application's webhook handler uses `WebhookMetadata#shop` (e.g., to select which shop's database record to update, deactivate, or process an "app/uninstalled" event for), this enables cross-tenant data corruption or spoofed lifecycle events (e.g., forging an `app/uninstalled` or `shop/redact` webhook against a victim shop's stored session/data) — a cross-tenant access impact.

### Likelihood Explanation
The prerequisite is only that the attacker can install/operate the public app on a shop they control (an ordinary, unprivileged action available to any internet user who can install a Shopify app) and capture/replay one legitimately delivered webhook request while forging headers to the app's own webhook endpoint. No access to `api_secret_key`, access tokens, or TLS interception is required.

### Recommendation
Include the shop domain, topic, and webhook id in the signed/verified material (or independently verify `shop` against a known/expected value, e.g., cross-check it against sessions the app has actually issued a token for) before trusting `request.shop`/`request.topic` in `Registry.process`. At minimum, document and enforce that `WebhookMetadata#shop` must be re-validated by the host app against its own installed-shop list before being used for any tenant-scoped operation.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers a `products/update` webhook (e.g., by editing a product), causing Shopify to POST a body `B` with header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` under the app's `api_secret_key`) and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com` to the app's webhook endpoint.
2. Attacker captures `(B, H)` and replays a new HTTP request to the same webhook endpoint with the same body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and, if desired, a different `X-Shopify-Topic`, e.g. `app/uninstalled`).
3. `ShopifyAPI::Webhooks::Request.new` parses these headers; `Utils::HmacValidator.validate(request)` succeeds because it only checks `H` against `B`, ignoring the shop/topic headers.
4. `Registry.process` dispatches to the handler registered for the forged topic with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though Shopify never sent an event for that shop — demonstrating the cross-tenant identity confusion.
