### Title
Webhook `shop` identity is trusted from an HTTP header not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook by checking the HMAC over the raw request body only, then trusts the `shop` (and `topic`/`webhook_id`/`api_version`) values taken straight from HTTP headers to build the `WebhookMetadata` passed to the host app's handler. Because the HMAC signature never covers the `shop-domain` header, the binding "authenticated body == claimed shop" does not hold, and a shop identity can be forged while keeping a cryptographically valid signature.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery` and defines `to_signable_string` to return only `@raw_body`: [1](#0-0) 
The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all read directly from HTTP headers with no cryptographic binding: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (i.e., the body) and compares it to the `hmac` header, using the app's single shared `Context.api_secret_key`: [3](#0-2) 

`Registry.process` uses this same secret-based check, and then — after validation succeeds — builds `WebhookMetadata` using `request.shop`, which was never part of the signed material: [4](#0-3) [5](#0-4) 

The identity equality that should hold is: `hmac-signed bytes == bytes that determine the tenant (shop) the event is attributed to`. Here it is broken: the HMAC only proves "this body+secret pair is valid for *some* installation of this app" (the secret, `Context.api_secret_key`, is the app's single client secret shared across all merchants who install it — not a per-shop secret). It does **not** prove which shop the event belongs to; that comes from an unsigned header.

### Impact Explanation
This is a cross-tenant identity-binding break, matching the "shop authenticated versus the shop stored/acted upon" pattern called out in the rules. Any unprivileged party who can install the app on their own store (a normal, free merchant action) receives genuinely HMAC-valid webhook deliveries signed with the app's shared secret. That attacker can capture a `(raw_body, hmac)` pair from their own store's webhook and replay it to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim merchant's shop domain. `HmacValidator.validate` will still pass, because the signature never depended on the shop header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event is `for` the victim shop. Any host application that uses `data.shop` from `WebhookMetadata` to look up per-tenant state, associated access tokens, or trigger tenant-scoped side effects (the documented purpose of this field) can be made to act on the wrong tenant — i.e., cross-tenant access/confusion driven entirely by this gem's own trust decision.

### Likelihood Explanation
Exploitability only requires: (1) the ability to install the app on an attacker-controlled shop (ordinary, unprivileged action for any public/embedded Shopify app), (2) capturing one legitimately delivered webhook (trivial — just observe your own store's webhook traffic), and (3) resending it to the same public webhook endpoint with a modified `shop-domain` header. No access token, no `client_secret`, and no privileged account are required — only participation as a normal merchant of the target app, which the threat rules classify as "unprivileged internet user."

### Recommendation
The gem should not expose an unauthenticated `shop` value as trustworthy metadata from `Webhooks::Request`. Either:
- Include the shop domain (and other identifying headers) in the signed material verified by `HmacValidator`, or
- Document/enforce that host applications must cross-check `WebhookMetadata#shop` against the shop that is expected to own the referenced resource (e.g., verify the `shop` implied by data in the signed body itself, not the header), and
- Consider deriving the trusted shop from data actually inside the signed JSON body where Shopify includes it, rather than solely from the `x-shopify-shop-domain` header, when performing tenant-sensitive lookups in `Registry.process`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, unprivileged onboarding flow).
2. Attacker triggers/receives a real webhook, capturing `raw_body` and the corresponding `x-shopify-hmac-sha256` value computed with the app's shared `api_secret_key`.
3. Attacker resends the identical `raw_body` and `hmac` header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the signature from `raw_body` only and finds it valid.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` builds `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)` and invokes the host handler with this forged shop attribution, even though the event content and signature originated from the attacker's own store.
