### Title
Webhook `shop-domain` header is excluded from the HMAC signature, allowing cross-tenant shop spoofing via replay of a validly-signed webhook body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identifier (`shop`) from an HTTP header that is never included in the HMAC-signed payload. `Utils::HmacValidator.validate` only verifies `to_signable_string`, which for a webhook request is the raw body alone [1](#0-0) . The `shop` accessor is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the body or to the HMAC [2](#0-1) . `Registry.process` validates only the HMAC and then hands the unverified `request.shop` straight to the handler as the tenant identity [3](#0-2) .

### Finding Description
The equality that should hold is: `shop bound by HMAC == shop acted upon by the handler`. Here that equality is broken: the HMAC only authenticates the raw request body (`to_signable_string` returns `@raw_body`), while the `shop` field that `WebhookMetadata` passes to the handler for tenant-scoped processing is taken from an unauthenticated header [4](#0-3) .

Because the HMAC secret (`Context.api_secret_key`) is the app-level `client_secret`, it is identical for every shop that installs the app — it is not shop-specific. An attacker who controls any shop that has the app installed (e.g., their own development/trial store) will receive genuinely Shopify-signed webhook deliveries whose body+HMAC pair is valid under the same app secret used for all merchants. The attacker can capture such a `(raw_body, hmac)` pair and replay it to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop's domain. `HmacValidator.validate` will still pass, because it only recomputes the HMAC over the body [5](#0-4) , and `Registry.process` will dispatch the (attacker-supplied) body to the handler tagged with the victim's shop domain [3](#0-2) .

### Impact Explanation
Applications built on this gem typically use the `shop` value from `WebhookMetadata` to select the tenant's session/database record and perform actions on their behalf (e.g., updating order/inventory records, triggering `shop/redact` or `customers/data_request` compliance flows). Because `shop` is not bound to the signature, an attacker can cause the host application to process attacker-controlled webhook content under a victim shop's identity — a cross-tenant confusion. Depending on how the host app uses the topic/body/shop combination, this can range from data corruption for another tenant to triggering compliance/data-erasure workflows against the wrong shop.

### Likelihood Explanation
Exploitation only requires the attacker to operate (or install the app on) any single shop to obtain one legitimately HMAC-signed webhook body, since the signing secret is shared across all shops of the app. No access to `api_secret_key`, access tokens, or the victim's credentials is needed — only interception/replay of the attacker's own traffic to the app's public webhook endpoint with a modified header. This is a realistic "unprivileged internet user" scenario within the library's own webhook-processing code path.

### Recommendation
Bind the shop (and other routing headers like `topic`) into the value that is cryptographically verified, or independently verify that the shop in the header matches the shop the payload actually pertains to (e.g., include shop/topic in the signable string, or cross-check against session/tenant state stored by the host application before trusting `request.shop`). At minimum, document prominently that `shop`, `topic`, and `webhook_id` are unauthenticated header values distinct from the HMAC-verified body, so implementers do not use `request.shop` as an authoritative tenant identifier.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook event (e.g., updates a product), receiving a real Shopify webhook POST with headers `shopify-shop-domain: attacker-shop.myshopify.com`, `shopify-hmac-sha256: <valid HMAC over raw body>`, and body `B`.
2. Attacker replays this exact body `B` and HMAC to the same endpoint but changes the header to `shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body normally [6](#0-5) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC only over `B` and succeeds because `B` and the secret are unchanged [7](#0-6) .
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)` and processes attacker-controlled data attributed to the victim shop [8](#0-7) .

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
