## Finding: Webhook shop identity not covered by HMAC signature, allowing cross-tenant data confusion - (`lib/shopify_api/webhooks/request.rb`)

### Summary
The webhook HMAC verification in this gem only authenticates the raw request body. The `shop-domain` header, which the library exposes to app handlers as the authoritative tenant identifier, is never included in the signed payload. An attacker who legitimately receives one valid `(body, HMAC)` pair for their own shop (e.g., by installing the target app on a shop they control) can replay that exact body/HMAC to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header value, and the library will accept it as an authentic webhook "from" that other shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers and are never part of the signed string: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, then immediately trusts `request.shop` as the tenant identity for dispatch, with no cross-check that the shop is one that actually owns this specific webhook payload: [3](#0-2) 

`HmacValidator.validate` computes/compares the signature purely against `verifiable_query.to_signable_string` (i.e., the body for webhooks), never against the shop header: [4](#0-3) 

The identity binding broken here is:
```
shop the HMAC-covered body was actually generated for  ≠  shop the library reports to the handler (WebhookMetadata#shop)
```
Because the second value is taken from an unauthenticated header, an attacker who can obtain any one valid `(body, hmac)` pair for a shop they control can freely re-target that authenticated body to any other shop, from the handler's point of view.

### Impact Explanation
Webhook handler code is documented and expected to key business logic off `data.shop` (see `docs/usage/webhooks.md`'s example handler using `data.shop`) while trusting `data.body` as validated Shopify data: [5](#0-4) 

Because the shop identity is not bound to the HMAC-authenticated body, an attacker can cause the library to hand the app attacker-chosen body content that is misattributed to an arbitrary victim shop domain. Depending on how the host app persists/acts on webhook data (a very common pattern per the gem's own guidance is to key records by `data.shop`), this enables cross-tenant data corruption/injection — writing or triggering actions against a victim merchant's records using data that was never actually sent by Shopify for that merchant. This matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
No possession of `api_secret_key`, access tokens, or any privileged credential is required. Any unprivileged internet user can:
1. Install the target app on a shop they control (or otherwise obtain any single legitimate webhook delivery, which is trivial for anyone using the app), capturing a real `(raw_body, HMAC)` pair.
2. Send that identical body and HMAC directly to the app's public webhook receiver endpoint (webhook endpoints are unauthenticated-by-design HTTP endpoints; the library relies solely on HMAC, not on network origin/mTLS), replacing only the `shop-domain` header value with the target's domain.
3. `HmacValidator.validate` passes (body unchanged), and `Registry.process` dispatches the handler with `shop` set to the attacker-chosen value.

This is straightforward to execute and requires no special access, matching the "unprivileged internet user" threat model.

### Recommendation
Verify that the `shop` header is bound to the caller-registered shop before dispatch — e.g., bind the shop into the signable content (as Shopify's own delivery signs are consistent per-webhook), or require the host application to confirm the reporting shop is one it has an active session/install for the specific webhook topic/id, and document explicitly that `data.shop` is not itself HMAC-verified. At minimum, the library should not present `shop` as a trusted field in `WebhookMetadata` without an accompanying integrity guarantee equivalent to the body's.

### Proof of Concept
```ruby
require "openssl"
require "base64"

secret = ShopifyAPI::Context.api_secret_key
body   = '{"id":1,"note":"legit order from attacker-shop"}'
hmac   = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, body)

# Attacker legitimately captured this (body, hmac) pair from a real webhook
# delivered to their own shop ("attacker-shop.myshopify.com").

headers = {
  "x-shopify-topic"       => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # spoofed, not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: headers)

# Passes: HMAC only verifies `body`, not `shop-domain`.
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker's body>, ...))
```
