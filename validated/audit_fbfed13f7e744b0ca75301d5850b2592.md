### Title
Hardcoded, immutable Uniswap V3 pool fee in `UniV3UniswapV2Wrapper` breaks the EvmHost native-fee dispatch route - (File: `evm/src/utils/uniswapv2/UniV3UniswapV2Wrapper.sol`)

### Summary
`EvmHost.dispatch()`, `dispatch(DispatchGet)` and `fundRequest()` allow any unprivileged caller to pay for message dispatch in native token, which is internally swapped to `feeToken()` through the configured `_hostParams.uniswapV2` router. On chains where this router is the `UniV3UniswapV2Wrapper`, every swap and every quote is forced through a single, immutable Uniswap V3 fee tier (`_params.maxFee`) that is fixed once at `init()` and can never be changed. This is the same bug class as Peapods' Zapper `_swapV3Single()`, where the pool fee used for the V3 swap is hardcoded rather than derived per-pool, causing swaps to revert or be mispriced when the real liquidity sits in a different fee tier.

### Finding Description
`UniV3UniswapV2Wrapper` exposes a V2-router-compatible interface (`swapETHForExactTokens`, `getAmountsIn`, `getAmountsOut`) that `EvmHost` and `HyperApp` treat as a generic Uniswap V2 router: [1](#0-0) [2](#0-1) 

Every swap route (`swapETHForExactTokens`, `swapExactTokensForETH`) and every quote route (`getAmountsIn`, `getAmountsOut`) hardcodes `_params.maxFee` as the pool fee tier for the underlying Uniswap V3 `exactOutputSingle`/`exactInputSingle`/`quoteExactOutputSingle`/`quoteExactInputSingle` calls: [3](#0-2) [4](#0-3) [5](#0-4) 

`maxFee` is set exactly once by the deployer through `init()` and there is no setter, no per-call fee parameter, and no fallback to other fee tiers if the configured tier has no pool or insufficient liquidity: [6](#0-5) 

This is functionally identical to the reported Zapper root cause: "the pool fee is forced to be `10000` ... this may not be the case for other tokens. We should simply use `_fee` instead." Here the equivalent flaw is that the wrapper never queries which fee tier actually holds liquidity for the WETH/feeToken pair, nor does it allow updating the fee tier if liquidity migrates — unlike the SDK's own V3 swap helper, which iterates `COMMON_FEE_TIERS` to find the correct/most-liquid pool (`sdk/packages/sdk/src/utils/swap.ts`), this on-chain wrapper commits to one fee tier forever.

Both `EvmHost.dispatch()`/`dispatch(get)`/`fundRequest()` and every `HyperApp`-based application's `quote()` function route through this exact same hardcoded-fee wrapper when `_hostParams.uniswapV2` points to it: [7](#0-6) 

### Impact Explanation
- If the actual deep-liquidity Uniswap V3 pool for WETH/feeToken is not at the exact `maxFee` tier configured at deployment (a routine occurrence as liquidity migrates between 0.05%/0.3%/1% tiers over time, or if the tier was misconfigured/never had a pool), `exactOutputSingle`/`quoteExactOutputSingle` calls revert unconditionally. This makes `EvmHost.dispatch{value: ...}()`, `dispatch(DispatchGet)` and `fundRequest()` permanently unable to accept native-token payment on that chain — an unprivileged dispatcher's message dispatch route becomes unusable, directly matching the "route unable to deliver messages" criterion.
- Even where a pool exists at `maxFee` but is thinly traded relative to the pool at another tier, the sole-source quote/swap can be manipulated or simply mispriced, forcing native-fee-paying users to overpay (excess native token consumed by `swapETHForExactTokens`) relative to the true market rate, with no on-chain fallback or slippage-tier comparison to protect them.
- Because `_params` is immutable post-`init()`, recovery requires a full contract redeployment and a governance `updateHostParams()` call — meaning the DoS persists until then, unlike the mutable, per-call fee handling that other wrappers in the same family use (e.g. `UniV4UniswapV2Wrapper`'s `defaultFee`, also fixed, or `GnosisUniswapV2Wrapper`'s hardcoded-but-correct 1:1 native/fee-token assumption specific to Gnosis).

### Likelihood Explanation
Any unprivileged user calling `EvmHost.dispatch()` with `msg.value > 0` triggers this path — no special privileges are required. Uniswap V3 liquidity distribution across fee tiers is well known to shift over time and differs per chain/token pair, so misconfiguration or later drift away from the originally chosen `maxFee` tier is a realistic operational condition, not a contrived edge case.

### Recommendation
Do not hardcode a single, permanent fee tier inside `UniV3UniswapV2Wrapper`. Either (a) query the Uniswap V3 factory across the standard fee tiers (500/3000/10000) at swap/quote time and select the pool with the deepest liquidity, mirroring the approach already used by the off-chain SDK (`getBestV3Pool`/`getV3QuoteWithAmountIn`), or (b) allow the configured fee tier to be updated via the existing `HostManager`/governance flow without redeploying the wrapper, and add a callable admin function to react to liquidity migration between tiers.

### Proof of Concept
Not applicable — this is a design/configuration flaw (immutable pool-fee selection), not exploitable via a single crafted transaction. The failure condition is triggered whenever the configured `maxFee` no longer corresponds to a pool with sufficient liquidity for the WETH/feeToken pair on the deployed chain, which can be demonstrated by pointing the wrapper (as in `evm/tests/foundry/UniV3UniswapV2WrapperTest.sol`) at a fee tier with no pool and observing that `dispatch()`/`quote()` revert.
