### Title
Fee-rounding underflow lets a floor-bumped `Zap.buy()` fully bypass the protocol buy fee - (`packages/contracts/src/Zap.sol`)

### Summary
`Zap._executeBuy()`'s floor-bump branch mirrors the Cooler `collateralFor()` bug class: a division whose numerator is dominated by a tiny value truncates to zero, decoupling the fee actually charged from the value actually delivered. Here, a graduation-cap-binding buy can be engineered so the curve-consumed LT slice (`amountInUsed`) is dust relative to the LT minted at the fixed floor (`ltMinted`), causing `effectiveBaseSpent = (amountInUsed * baseToConvert) / ltMinted` to floor to `0`. That zeroes `actualFee`, and the entire pre-collected `feeOnGross` is then refunded to the caller, fully bypassing Alt Fun's 0.75% buy fee while the caller still receives real curve tokens and keeps almost all the minted LT back as a refund.

### Finding Description
`Zap._executeBuy` (packages/contracts/src/Zap.sol, floor-bump branch, ~lines 330-410): [1](#0-0) 

collects the fee up front on the gross submitted amount: [2](#0-1) 

When the remaining curve capacity until graduation (`ltUntilGraduation`, from `Bonding.previewLtUntilGraduation`) is tiny but the implied `baseToConvert` would fall under `minUsdcAmount()`, the code force-bumps the mint up to the floor and refunds the LT the curve doesn't consume back to the caller as raw LT: [3](#0-2) 

It then prorates the fee against the curve-consumed slice using floor division: [4](#0-3) 

If `amountInUsed` (the dust the curve actually consumed) is small enough that `amountInUsed * baseToConvert < ltMinted`, `effectiveBaseSpent` truncates to `0`, so `actualFee` (computed via `Math.mulDiv(..., Ceil)` on a zero numerator) is also `0`. The full `feeOnGross` is then refunded: [5](#0-4) 

This is structurally identical to the Cooler `collateralFor()` issue: a fixed-scale numerator combined with a much larger denominator rounds a required, proportional charge down to zero, decoupling "value received" from "value paid for." In Cooler, the decoupled value was collateral; here it is the protocol/creator fee.

The scenario is fully attacker-reachable and unprivileged:
1. Use ordinary `Zap.buy` calls (any EOA) to stage a token's curve so that `Bonding.previewLtUntilGraduation(token)` (a public view) reports a residual capacity of just a few wei of LT — i.e., land the curve just short of the graduation threshold.
2. Call `Zap.buy(token, usdcAmount, 0, referrer)` with any `usdcAmount` whose `netUsdc >= minUsdcAmount()`. Because `ltUntilGraduation` is dust, the code computes `baseToConvert` from `ltToBaseAmount(ltUntilGraduation)`, finds it below the floor, and bumps `baseToConvert` to `minUsdcAmount()` (the fixed floor).
3. `ltMinted = mint(baseToConvert)` is a normal-sized LT amount; `amountInUsed` (what the curve actually consumes to hit the cap) is the dust residual from step 1 — many orders of magnitude smaller than `ltMinted`.
4. `effectiveBaseSpent = amountInUsed * baseToConvert / ltMinted` floors to `0` because the numerator product is smaller than `ltMinted`.
5. `actualFee = 0`, so `feeRefund = feeOnGross`, and the whole fee collected on `usdcAmount` is refunded to the caller in the same transaction, alongside the LT overshoot refund (`ltExcess = ltMinted - amountInUsed`) and the unused-principal refund (`usdcLeft`).

The caller nets: real graduating/curve-consuming tokens, essentially all their principal back (LT excess + USDC leftover), and a complete refund of the protocol fee that was supposed to be charged on the trade.

### Impact Explanation
This directly causes FeeVault insolvency relative to expected revenue: the 0.75% Alt Fun buy fee — split 0.5% protocol / 0.25% creator per `docs/contracts-scope.md` — can be reduced to `0` on an arbitrary-size submitted `usdcAmount` by an unprivileged trader who times the buy to land in the floor-bump branch with a dust `amountInUsed`. This is repeatable on any token approaching graduation (an attacker can even engineer their own launched token's curve state to guarantee the dust gap), so it is not a one-off dust artifact but a controllable fee-avoidance primitive. Given the explicit design intent that "every buy" pays the fee (`AGENTS.md`/`Zap._executeBuy` natspec: "Fee is charged on EVERY buy... This is intentional"), this breaks a core revenue invariant of the protocol.

### Likelihood Explanation
Reachable with only standard user-facing calls (`Zap.buy`, repeated to stage the curve, using `Bonding.previewLtUntilGraduation` as a public view to precisely target the dust gap). No privileged role, no upgrade, no oracle manipulation, and no cooperation from BounceTech LT or HyperSwap is required — only careful sizing of a sequence of ordinary buys. The existing test suite already demonstrates the floor-bump branch and dust `amountInUsed` scenario (`test_buy_capPath_floorBump_refundsLtToCaller`, `test_buy_floorBump_emitsConsumedSliceExcludingLtRefund`), confirming the mechanics are exercised in practice; those tests just don't assert on `actualFee` reaching exactly `0`, which is the missing check that would have caught this.

### Recommendation
Do not let the prorated fee floor to zero when real value was extracted from the curve. Either:
- Charge the fee against `baseToConvert` (what was actually minted/spent by the floor-bump) rather than `amountInUsed`/`ltMinted` proration when the floor-bump path is taken, or
- Round `effectiveBaseSpent`/`actualFee` up with a minimum floor (e.g., `Math.max(actualFee, 1)` is insufficient by itself — instead ensure the proration numerator scale can't collapse to zero relative to `ltMinted`, e.g. by computing fee proportionally to `baseToConvert` capped at `feeOnGross` rather than truncating through `amountInUsed`), or
- Explicitly special-case the floor-bump branch to always charge the full `feeOnGross` on `baseToConvert`'s worth of the trade, refunding only the unconverted `usdcLeft`, never `feeRefund`, whenever `ltExcess > 0` (i.e., whenever the floor-bump path fired).

### Proof of Concept
Extend `Zap.t.sol` analogous to `test_buy_capPath_floorBump_refundsLtToCaller`:
```solidity
function test_floorBump_zeroesFeeViaRoundingDown() public {
    address tokenAddr = _createToken(0);

    // Drain the curve so only ~1 wei of LT remains until graduation.
    _drainCurveDirectly(tokenAddr, _drainAmountForCapHeadroom(tokenAddr, 1));
    lt.setMinTransactionSize(zap.minUsdcAmount());

    uint256 buyAmount = bonding.graduationThresholdUsd() * 2;
    usdc.mint(trader, buyAmount);

    uint256 vaultBefore = usdc.balanceOf(address(feeVault));

    vm.startPrank(trader);
    usdc.approve(address(zap), buyAmount);
    zap.buy(tokenAddr, buyAmount, 0, address(0));
    vm.stopPrank();

    uint256 actualFee = usdc.balanceOf(address(feeVault)) - vaultBefore;
    // Bug: with a dust amountInUsed relative to ltMinted, actualFee floors to 0,
    // meaning the entire feeOnGross was refunded to the trader.
    assertEq(actualFee, 0, "Protocol fee fully bypassed via rounding");
}
```
Note: exact drain amount needed to force `amountInUsed * baseToConvert < ltMinted` depends on the LT's decimals and current `exchangeRate()`; use `previewLtUntilGraduation` to compute the precise residual before the final buy.

        // For non-cap and dust-cap buys `amountInUsed ≈ ltMinted` so
        // `effectiveBaseSpent ≈ baseToConvert` and behaviour matches the
        // pre-floor-bump formula. The floor-bump branch overshoots the
