### Title
Misattributed signup success bypasses backend verification for `user_centric_signup` - (File: src/plans/mod.rs)

### Summary
In `MasterPlan::do_signup`, two different code paths determine whether a signup counts as successful, and they diverge in exactly the same "special case vs. general case" pattern as the `ERC4626Cloned` `deposit`/`mint` bug: one path performs the "real"/authoritative check, the other reimplements it locally with different (weaker) logic, allowing an outcome that the authoritative path would not have allowed.

### Finding Description
In the normal signup flow, success is determined by actually running the backend enrollment plan `enroll_user::Plan::run`, which repeatedly calls the backend via `signup_post::request`/`signup_poll::request` and only returns `Status::Success` once the backend has confirmed the signup (this backend confirmation is explicitly documented to cover backend-side duplicate detection, in-flight match detection, and backend fraud detection): [1](#0-0) 

However, when `qr_codes.user_data.user_centric_signup` is set (and the orb is not configured to ignore it), `do_signup` takes a completely different branch that never calls the backend enrollment plan at all. Instead, it derives `success` purely from the on-device `signup_reason` (which itself only reflects local pipeline/fraud results, since `detect_fraud` in this build has no actual fraud checks): [2](#0-1) [3](#0-2) 

This exactly mirrors the reported bug class: `previewMint`/`mint` implemented a special "first supply" rule (`10e18`) meant to protect against manipulation, while `deposit`/`previewDeposit` silently omitted that special-case protection, letting an attacker mint shares through the unprotected path. Here, the "protected"/authoritative path (`enroll_user::Plan::run`, which is gated by the backend) has server-side dedupe/fraud logic, while the "unprotected" path (`user_centric_signup == true`) reimplements the enrollment-success decision locally and skips the backend round-trip entirely — the two paths that should produce equivalent enrollment decisions diverge, and one of them structurally cannot detect what the other is designed to catch (duplicate iris codes, backend-side fraud, in-flight matches).

Additionally, `detect_fraud` in this codebase is fully stubbed out ("FOSS: WE HAVE DELETED ALL FRAUD CHECKS"), so for `user_centric_signup` requests, `signup_reason` will essentially always resolve to `SignupReason::Normal` whenever the local biometric pipeline succeeds, with no fraud or duplicate check performed anywhere, on-device or backend: [4](#0-3) 

### Impact Explanation
This produces a misattributed/unauthorized signup impact: a user (or app) that supplies `user_data.orb_relay_app_id` and sets `user_centric_signup = true` in the QR-derived `UserData` can obtain a `Status::Success`/`result.success = true` enrollment outcome, and have `debug_report.enrollment_status` marked `Success`, purely from local pipeline output — without the backend ever confirming uniqueness (no duplicate check), without in-flight-match detection, and without any working fraud detection. This is a strictly weaker acceptance path than the standard enrollment path for functionally the same "enroll this iris" operation, matching the report's "attacker can still mint/enroll through the unguarded path" impact category (misattributed/duplicate signup bypassing intended anti-fraud logic).

### Likelihood Explanation
Likelihood depends on whether `user_centric_signup` and `ignore_user_centric_signups` are populated/controlled by backend-issued QR/app data versus attacker-controlled input; from the code alone, `user_centric_signup` originates from `qr_codes.user_data.user_centric_signup`, which is part of the QR-code-derived `UserData` returned via `backend::user_status`. I could not fully verify from available context whether this flag is cryptographically bound/verified server-side or can be influenced by a malicious app/user QR flow, nor could I locate the exact documentation/intent behind `ignore_user_centric_signups` in `config.rs` before running out of search budget — this needs further verification in a full checkout of `src/config.rs` and `src/backend/user_status.rs`.

### Recommendation
Ensure the `user_centric_signup` path performs the same backend-verified duplicate/fraud checks (or an equivalent authoritative check) as the standard `enroll_user` path before marking `result.success`/`enrollment_status` as `Success`, rather than deriving success solely from locally computed `signup_reason`. At minimum, require a backend round-trip (akin to `signup_post`/`signup_poll`) for `user_centric_signup` before finalizing success.

### Proof of Concept
Not independently reproducible from static analysis alone — full confirmation requires tracing how `user_data.user_centric_signup` is populated from `backend::user_status::request` / QR-code parsing to confirm attacker control, which the index did not fully expose. Given the index size limits, some file contents (e.g. full `src/config.rs`, `src/backend/user_status.rs`) may not be completely available; a Devin session with full repository access is recommended to confirm the origin/trust level of the `user_centric_signup` flag before treating this as conclusively exploitable.
