### Title
Webhook `shop-domain` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` value taken directly from the `x-shopify-shop-domain`/`shopify-shop-domain` header, but the HMAC signature validated by `Utils::HmacValidator` is computed only over the raw request body (`to_signable_string` returns `@raw_body`). The shop identity that the host application relies on (`WebhookMetadata#shop`, passed to the app's handler) is never part of the authenticated bytes.

### Finding Description
`Webhooks::Registry.process` validates a webhook exclusively via: [1](#0-0) 

The HMAC check itself only compares a signature computed from `verifiable_query.to_signable_string`: [2](#0-1) 

And for `Request`, `to_signable_string` is defined as just the raw body — it does not include the shop header, topic, webhook-id, or api-version: [3](#0-2) 

Meanwhile `shop` is read straight from an unauthenticated header: [4](#0-3) 

and it is this same unauthenticated value that ultimately gets handed to the handler as the tenant identity for the webhook: [5](#0-4) 

The identity binding that should hold is: `shop used by the app's webhook handler == shop that the HMAC-secret owner actually sent the request for`. Because `to_signable_string` only covers the body, this equality is not enforced by the gem — the HMAC is valid for *any* `shop-domain` header value as long as the body and the shared `api_secret_key` match. Since a single app's `api_secret_key` is shared across all shops that install it, any shop that has legitimately received an authentic webhook (with a given body) can capture the `body + hmac` pair and replay it against the same public webhook endpoint with a different `shop-domain` header, causing the host application to process the webhook as if it came from a different, victim shop.

### Impact Explanation
This breaks the shop/tenant authentication boundary that host applications are expected to rely on when they branch behavior (e.g., which merchant's data to update, which session/store record to look up) based on `WebhookMetadata#shop`. A malicious app-installing merchant (an "unprivileged" party relative to other tenants of the same app, requiring no access token, secret, or elevated privilege) can forge webhooks that appear to originate from a different shop, provided they can obtain (or guess/replay) a body that produces a useful outcome. This is a cross-tenant identity confusion at the library layer, matching the "Critical – cross-tenant access" impact class in the rules, since the SDK is the enforcement point host apps trust for authenticating webhook shop attribution and it fails to bind the field it hands to callers.

### Likelihood Explanation
Exploitation requires an attacker to have (a) their own valid shop installation of the target app so they can capture legitimate `body`/`hmac` pairs from webhooks Shopify sends them, and (b) knowledge of, or ability to construct, a body whose content is harmful if attributed to another shop (e.g., generic/templated payloads, or topics like `app/uninstalled`, `shop/redact` where body content is shop-agnostic or predictable). Because many webhook topics carry little or no shop-specific data in the body (the association is normally established purely via the header), this is often straightforward, and the endpoint is a public HTTP endpoint reachable by anyone, not requiring the merchant's or the app's secrets to forge the header, only capture-and-replay of one legitimately-received message.

### Recommendation
Include the shop-domain (and ideally topic/webhook-id) in the HMAC-covered content, or otherwise cryptographically bind the `shop` value that `WebhookMetadata` exposes to the same bytes verified by `HmacValidator`. At minimum, document/enforce that host apps must not trust `request.shop` as an authenticated tenant identifier unless it is independently corroborated (e.g., against a known list of installed shops), and consider computing the HMAC over `body + shop-domain header` rather than the body alone.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`.
2. Shopify sends the attacker a legitimate webhook, e.g. `topic: app/uninstalled`, with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over body>`, and some generic/empty body `{}`.
3. Attacker replays the exact same body and HMAC to the app's public webhook endpoint, but substitutes the header `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because `to_signable_string` (the body) and the HMAC still match — the shop header played no part in verification: [6](#0-5) 
5. `Registry.process` dispatches to the handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, causing the app to act (e.g., de-provision access, purge data, or perform redaction) against the victim shop's tenant record on the attacker's forged behalf.
