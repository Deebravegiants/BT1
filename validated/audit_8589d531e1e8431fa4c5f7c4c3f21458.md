Webhook `shop` (tenant) identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) purely from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, while `to_signable_string` — the data actually covered by the HMAC signature — only returns the raw request body. `Registry.process` validates the HMAC and then trusts `request.shop` to build the `WebhookMetadata` handed to the app's handler, creating a broken binding: `HMAC-verified-bytes == raw_body` but `identity-acted-on == shop header (unverified)`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read straight from an attacker-controllable HTTP header with no cryptographic binding to the HMAC: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` (i.e. only the body) and compares it against `request.hmac`. Once that check passes, the code immediately trusts `request.shop` — the unauthenticated header — to construct `WebhookMetadata`, which is the object host applications use to determine which merchant/tenant the webhook belongs to: [3](#0-2) [4](#0-3) [5](#0-4) 

The broken identity binding, stated as an equality that should hold but doesn't:
`bytes_verified_by_HMAC (raw_body only)` ≠ `bytes_relied_upon_for_tenant_identity (shop header + body)`

Because the webhook HMAC secret (`Context.api_secret_key`, the app's `client_secret`) is the **same secret for every shop/tenant** that has installed the app, any tenant that has legitimately installed the app can generate a request with a cryptographically valid HMAC over an arbitrary body of their choosing. Since the `shop-domain` header is not part of the signed material, that same valid `(body, hmac)` pair can be replayed to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to name a **different, victim** shop. `Registry.process` will pass HMAC validation (because it only checks the body) and will hand the host application a `WebhookMetadata` claiming the payload originated from the victim shop.

### Impact Explanation
This breaks the tenant/authentication boundary the gem is supposed to enforce for inbound webhooks. Any attacker who controls one shop that has the app installed can forge a webhook that the app framework will attribute to an arbitrary other shop (a shop domain string is completely attacker-supplied and has no format restriction enforced here). Depending on how the host app's `WebhookHandler#handle` implementation uses `data.shop` (e.g. to look up/update per-tenant local state, provision/deprovision resources, or trigger `shop/redact`/`customers/redact` compliance flows), this enables cross-tenant data injection or corruption — data attributed to a merchant who never sent it. This matches the "cross-tenant access" class of Critical impact defined in scope, since the gem itself misattributes an inbound, seemingly-authenticated event to the wrong tenant.

### Likelihood Explanation
Likelihood is high for any attacker who can install the app on their own store (a normal, unprivileged action for public/embedded Shopify apps) — no privileged credentials, leaked secrets, or access tokens are required. They only need to trigger any webhook topic from their own shop (e.g. by performing the underlying action, such as creating an order) to get Shopify to send them a validly-HMAC'd request, then replay it to the app's public webhook endpoint with a modified `x-shopify-shop-domain` header.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`) values in the data covered by `to_signable_string`, or otherwise cryptographically bind the header-derived shop domain to the signature before it is trusted by `Registry.process`/`WebhookMetadata`. At minimum, document and enforce that host applications must independently verify `shop-domain` against a known/installed-shop list rather than trusting it as authenticated purely because HMAC validation passed.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com`, completing OAuth normally (no special privilege required).
2. Attacker performs an action that triggers a webhook (e.g. `orders/create`) from their shop; Shopify sends the app's webhook endpoint a request with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and some JSON body.
3. Attacker intercepts/replays this request to the same endpoint, changing only `x-shopify-shop-domain` to `victim-shop.myshopify.com`. The `x-shopify-hmac-sha256` header and body are left untouched.
4. In `ShopifyAPI::Webhooks::Registry.process`, `Utils::HmacValidator.validate(request)` calls `request.to_signable_string`, which returns only `@raw_body` — unchanged — so validation succeeds: [6](#0-5) 
5. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built with `shop == "victim-shop.myshopify.com"`, taken from the forged header, and passed to the app's `handler.handle(data:)`: [7](#0-6) 
6. The host application processes attacker-controlled data believing it originated from `victim-shop.myshopify.com`.
