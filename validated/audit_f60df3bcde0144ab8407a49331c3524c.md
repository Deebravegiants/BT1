### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so the HMAC verification performed in `ShopifyAPI::Webhooks::Registry.process` authenticates the *body bytes* but never binds the `shop-domain`, `topic`, `api-version`, or `webhook-id` headers to that signature. Because a public app's webhook HMAC secret (`client_secret`) is the same across every shop that installs it, an unprivileged attacker who installs the app on their own store can capture one legitimately-signed webhook and replay it with a forged `shop-domain` header pointing at a victim shop, and the signature will still validate.

### Finding Description
The relevant identity binding that should hold is:

`hmac_signed_bytes == bytes_that_determine_the_tenant_the_event_is_attributed_to`

but in this gem:

- `Request#to_signable_string` returns only `@raw_body` [1](#0-0) .
- `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cross-check against the signed payload [2](#0-1) .
- `Registry.process` validates the HMAC over the request (i.e., over `to_signable_string`, the body only) and then immediately trusts `request.shop`, `request.topic`, `request.webhook_id`, `request.api_version` to build the `WebhookMetadata` handed to the host application's handler [3](#0-2) .
- `HmacValidator.validate` / `validate_signature` compute the HMAC using `Context.api_secret_key` (the app's `client_secret`), which is identical for every shop that installs the same app [4](#0-3) .

Because the secret is shared across all tenants of a given app, and the header that identifies *which* tenant the event belongs to is excluded from the signed bytes, any party that can obtain one valid `(body, hmac)` pair — trivially achievable by installing the (public) app on a store they control and triggering any webhook topic — can resend that exact body/HMAC pair to the app's webhook endpoint with the `shop-domain` header rewritten to a different, victim shop domain. `Utils::HmacValidator.validate` will report success because it only checks the body bytes, and `Registry.process` will hand the host application a `WebhookMetadata` claiming the event came from the victim shop [5](#0-4) .

### Impact Explanation
Host applications built on this gem are expected to trust `WebhookMetadata#shop` to determine which tenant/session the event data applies to (e.g., looking up the shop's session, updating shop-scoped records, or triggering shop-scoped side effects). Since the shop attribution is not part of the cryptographically verified content, an attacker with a legitimate (self-owned) app installation can forge webhook deliveries "from" any other shop that has the same app installed, causing the host application to process attacker-controlled data under a foreign tenant's identity. This is a cross-tenant identity-binding break stemming directly from this gem's webhook verification logic.

### Likelihood Explanation
The only prerequisite is that the attacker be able to install the target public app on a shop they control (a normal, unprivileged action for a Shopify merchant) and be able to reach the app's public webhook endpoint — both of which are ordinary capabilities of an unprivileged internet user in the app-install flow. No access to the victim's credentials, access tokens, or `client_secret` is required.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed content, or otherwise cryptographically bind `request.shop` to the verified payload (e.g., have `to_signable_string` incorporate the raw header values Shopify actually signs for, and reject requests where the header-derived shop cannot be independently corroborated, such as checking it against a known/installed shop list before dispatching to handlers).

### Proof of Concept
1. Attacker installs the target public app on `attacker-shop.myshopify.com` (a store they control) and lets Shopify deliver a legitimate webhook (e.g. `orders/create`) with a valid `x-shopify-hmac-sha256` header computed over the raw JSON body using the app's shared `client_secret`.
2. Attacker captures the raw body and the valid HMAC value.
3. Attacker crafts a new HTTP request to the app's webhook endpoint using the same raw body and same HMAC header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `@raw_body` [1](#0-0) .
5. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)` [6](#0-5) , causing the host application to process attacker-controlled data as if it originated from the victim shop.
