This confirms the mechanism is deterministic and immune to the described attack.

The `rollback_accounts` field of `LoadedTransaction` is computed once, before execution, inside `validate_transaction_fee_payer` in `svm/src/transaction_processor.rs`. There, `fee_payer_loaded_rent_epoch` is captured from the account as loaded (`loaded_fee_payer.account.rent_epoch()`) prior to any instruction execution, and `RollbackAccounts::new` immediately snapshots the fee-subtracted account with that rent epoch reset applied for the non-nonce case.<br>

The claimed attack path does not exist in this codebase's control flow.

**Why the invariant already holds deterministically:**

1. `fee_payer_loaded_rent_epoch` is captured in `validate_transaction_fee_payer` *before* any instruction executes, directly from the loaded account: `loaded_fee_payer.account.rent_epoch()`, immediately followed by `RollbackAccounts::new(...)` which stores the fee-subtracted account with `fee_payer_account.set_rent_epoch(fee_payer_loaded_rent_epoch)` baked in for the non-nonce case. [1](#0-0) [2](#0-1) 

2. This `rollback_accounts` value becomes a fixed field of `LoadedTransaction` at load time, prior to `execute_loaded_transaction` ever running. Inside `execute_loaded_transaction`, only the `accounts` field is taken via `std::mem::take` and handed to `TransactionContext` for VM execution; `rollback_accounts` is untouched by anything that happens during instruction/CPI execution. [3](#0-2) 

3. On failure, the pre-computed, execution-independent `rollback_accounts` snapshot — not any post-execution/mutated state — is what gets committed via `update_accounts_for_failed_tx` and later read in `create_commit_results`/`rollback_accounts.fee_payer()`. [4](#0-3) [5](#0-4) [6](#0-5) 

Because the fee-payer rollback account (including its rent_epoch reset) is computed once, deterministically, from pre-execution state and is structurally decoupled from whatever a later-failing instruction or an earlier CPI does to the in-flight `TransactionContext` copy of the account, there is no way for an attacker-controlled instruction sequence to make the committed rollback rent_epoch depend on execution order or any validator-specific optimization. Every validator executes the identical deterministic sequence: load → capture `fee_payer_loaded_rent_epoch` → compute `rollback_accounts` → execute (on a *copy* of accounts) → on failure, commit the untouched precomputed `rollback_accounts`. Existing unit tests (`test_new_fee_payer_only`, `test_validate_transaction_fee_payer_exact_balance`) already assert this exact reset behavior. [7](#0-6)
