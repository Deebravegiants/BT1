### Title
Disabled overfill clamp lets a user manipulate a Uniswap V4 venue price to drain filler funds - (File: `sdk/packages/simplex/src/strategies/fx.ts`)

### Summary
The `FXFiller` order-filling loop in `fx.ts` computes a `policyMaxOutput` for each leg, and previously enforced a hard ceiling (`(1 + maxOverfillBps) × user-requested`) to bound the amount the filler would pay out per leg. That ceiling has been disabled: the code now only logs a warning when `policyMaxOutput` exceeds the ceiling and pays out the full, unclamped amount regardless [1](#0-0) .

### Finding Description
For venue-priced legs (e.g. Uniswap V4 pairs with no static bid/ask policy), `policyMaxOutput` is derived from a live pool price. The code comment explicitly acknowledges the removed protection: "this removes the per-leg loss bound that previously protected against a bug / stale cache / manipulated venue price" [2](#0-1) . The `targetOutput` used to actually source and pay funds is set directly to `policyMaxOutput`, with no ceiling applied — `desiredOutput`/`overfillCeiling` are only used for logging/gating short-fills, never to cap the payout [3](#0-2) . This is structurally the same bug class as the referenced Vault.vy report: a price feed consulted at fill-time (the on-chain venue pool) can be manipulated with a flash loan by the order placer, an unprivileged intent-solver counterparty, immediately before/within the same transaction context that triggers the filler's `fillOrder` call, so the filler computes and pays out an inflated `policyMaxOutput` against a temporarily distorted price with no independent bound to prevent it.

### Impact Explanation
Because the fill amount is unbounded relative to what the user actually requested and relative to the pair's own (undistorted) price, an attacker who transiently manipulates the referenced Uniswap V4 pool can force the Simplex filler to source and pay out funds worth substantially more than the escrowed input it receives in return — directly analogous to the "bad debt" scenario in the report, except here it manifests as the solver overpaying against a manipulated on-chain price with no clamp. This is a direct loss of the filler's escrow/vault capital, reachable by any user submitting an intent order the filler competes to fill.

### Likelihood Explanation
The Intent Gateway auction/fill flow is fully permissionless — any user can place an order specifying legs priced from a Uniswap V4 venue, and any attacker with flash-loan capital can move that pool's price within the same block the filler evaluates and fills the order. Since the overfill clamp is deliberately disabled (warn-only), no additional privilege or race condition is needed beyond ordinary flash-loan price manipulation, which is a well-established, cheap technique.

### Recommendation
Re-enable the overfill ceiling as a hard cap rather than a warning: reject or clamp `policyMaxOutput`/`targetOutput` to `(1 + maxOverfillBps) × output.amount` before sourcing/paying funds, particularly for venue-priced (`priceSource === "venue"`) legs where the price is read from a manipulable on-chain pool at fill time. Alternatively, gate venue-priced fills on a TWAP or sanity-check against a secondary price source before disbursing.

### Proof of Concept
1. Attacker identifies a Simplex filler configured with a Uniswap V4-venue-priced pair (no static bid/ask curve) per `TradingPair` docs [4](#0-3) .
2. Attacker takes a flash loan and swaps against the referenced Uniswap V4 pool to skew its price so that `venueUsdPrice`/`rates.rate` used by `resolveLegRates` is temporarily inflated in the attacker's favor.
3. Attacker places (or has already placed) an intent order whose output leg resolves to that pair.
4. When the filler evaluates the order in the same or an adjacent block, `computeLegPolicyOutput` returns an inflated `rawPolicyMaxOutput`; the code detects `rawPolicyMaxOutput > overfillCeiling`, logs a warning, but still sets `targetOutput = policyMaxOutput` and pays it out in full [5](#0-4) .
5. Attacker reverses the flash-loan swap, restoring the pool price and repaying the loan, having extracted the inflated payout from the filler for the escrowed input amount.
