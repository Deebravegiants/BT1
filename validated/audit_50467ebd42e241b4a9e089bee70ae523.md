## Finding: Stale Owner Votes Persist Across Owner Removal/Re-addition in `multisig_account.move`, Allowing Unauthorized Reactivation of Approval Authority

### Title
Removed-and-reinstated multisig owner's stale vote silently regains counting power for pending transactions - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
This is a custody analog of the ERC-721 "stale per-token approval survives operator revocation" bug class. In Aptos's `multisig_account` module, a multisig-owned resource account (which may hold APT, fungible assets, or object ownership) is controlled by k-of-n owner votes on pending `MultisigTransaction`s. Votes are stored in a `SimpleMap<address, bool>` keyed by owner address [1](#0-0) , but this vote map is never purged or invalidated when the corresponding address is removed from the owners list via `remove_owners`/`update_owner_schema` [2](#0-1) .

### Finding Description
Approval counting (`num_approvals_and_rejections_internal`) iterates the **current** `owners` vector and, for each currently-listed owner, checks whether that address has an entry in `transaction.votes`: [3](#0-2) 

This design correctly excludes a removed owner's vote while they are absent from `owners` — confirmed by `test_validate_transaction_should_not_consider_removed_owners` [4](#0-3) . However, the fix is only masking, not revoking: the stale `(owner_addr -> true)` entry is **never deleted** from `transaction.votes`. `update_owner_schema` only mutates the `owners` vector; it never touches any pending `MultisigTransaction.votes` map [5](#0-4) .

Consequently, if the same address is later reinstated as an owner (e.g., via `add_owners`, `swap_owner`/`swap_owners`, which have no check preventing re-adding a previously-removed address) while the original transaction is still pending, `num_approvals_and_rejections_internal` will again find their old vote entry and silently count it as a live "approve", with **no new signature or vote action from that owner**. This is the direct custody analog of Bob's stale `DelegateToken.approve` surviving `setApprovalForAll(false)` — here, an owner's stale approval survives `remove_owners` and is reactivated by any subsequent `add_owners`/`swap_owner` that restores their address, without the owner explicitly re-approving that specific still-pending transaction.

### Impact Explanation
The multisig account is a resource account that can hold and control APT, fungible assets, and object ownership, and its transactions are executed once `num_signatures_required` genuine approvals are met (`validate_multisig_transaction` at [6](#0-5) ). Because a stale vote can silently re-enter the quorum count without the owner's current consent, a previously-approved but never-executed malicious/stale transaction payload (e.g., a transfer of the multisig's APT/FA balance, an object-ownership reassignment, or an authority-changing payload) can reach quorum and be executed at a time when the reinstated owner never re-affirmed that specific transaction. This breaks the custody invariant that "each currently-recognized owner's consent for a specific pending transaction reflects their present intent," and can move value to unintended recipients or grant control changes without expected authorization.

### Likelihood Explanation
This requires a specific operational sequence — an owner address is removed while a transaction is pending and is later re-added (or swapped back in) before that transaction resolves — mirroring the "Medium" severity judged for the original DelegateToken finding (plausible under normal owner rotation but not a one-step trivial attack). Owner churn (rotating away and back a key holder, or accidentally reusing an address in `swap_owner`) is a realistic administrative pattern, especially for multisigs used as long-lived treasury/resource accounts, making this a credible though conditional vector.

### Recommendation
When an owner is removed via `update_owner_schema`/`remove_owners`, iterate all pending transactions and clear (or mark stale) any vote entries belonging to the removed owner address(es), so that if the address is ever reinstated, it must cast a fresh vote for any still-pending transaction rather than silently inheriting its prior vote.

### Proof of Concept
1. Create multisig account with owners `[A, B, C]`, `num_signatures_required = 2`.
2. `C` calls `create_transaction` with a malicious payload (implicit self-approve) [7](#0-6) .
3. `B` calls `approve_transaction` (now `B`, `C` approved — 2/3, meets quorum).
4. Owners' quorum removes `B` (e.g., legitimately suspecting key compromise) via `remove_owners` — `can_be_executed` now correctly returns false since `B` is not in current owners (per existing test at line 2268-2289).
5. Later, owners' quorum re-adds `B` via `add_owners` (e.g., after resolving the key issue) — no check prevents reusing `B`'s address, and `B`'s vote entry in `transaction.votes` was never cleared.
6. `num_approvals_and_rejections_internal` now again counts `B`'s stale `true` vote plus `C`'s, reaching quorum (2/3) and allowing execution of `C`'s original payload — without `B` ever re-approving it after being reinstated. [3](#0-2)

    inline fun num_approvals_and_rejections_internal(owners: &vector<address>, transaction: &MultisigTransaction): (u64, u64) {
        let num_approvals = 0;
        let num_rejections = 0;

        let votes = &transaction.votes;
        owners.for_each_ref(|owner| {
            if (simple_map::contains_key(votes, owner)) {
                if (*simple_map::borrow(votes, owner)) {
                    num_approvals += 1;
                } else {
                    num_rejections += 1;
                };
            }
        });

        (num_approvals, num_rejections)
    }

    /// Add new owners, remove owners to remove, update signatures required.
    fun update_owner_schema(
        multisig_address: address,
        new_owners: vector<address>,
        owners_to_remove: vector<address>,
        optional_new_num_signatures_required: Option<u64>,
    ) {
        assert_multisig_account_exists(multisig_address);
        let multisig_account_ref_mut =
            borrow_global_mut<MultisigAccount>(multisig_address);
        // Verify no overlap between new owners and owners to remove.
        new_owners.for_each_ref(|new_owner_ref| {
            assert!(
                !vector::contains(&owners_to_remove, new_owner_ref),
                error::invalid_argument(EOWNERS_TO_REMOVE_NEW_OWNERS_OVERLAP)
            )
        });
        // If new owners provided, try to add them and emit an event.
        if (new_owners.length() > 0) {
            multisig_account_ref_mut.owners.append(new_owners);
            validate_owners(
                &multisig_account_ref_mut.owners,
                multisig_address
            );
            emit(AddOwners { multisig_account: multisig_address, owners_added: new_owners });
        };
        // If owners to remove provided, try to remove them.
        if (owners_to_remove.length() > 0) {
            let owners_ref_mut = &mut multisig_account_ref_mut.owners;
            let owners_removed = vector[];
            owners_to_remove.for_each_ref(|owner_to_remove_ref| {
                let (found, index) =
                    vector::index_of(owners_ref_mut, owner_to_remove_ref);
                if (found) {
                    vector::push_back(
                        &mut owners_removed,
                        vector::swap_remove(owners_ref_mut, index)
                    );
                }
            });
            // Only emit event if owner(s) actually removed.
            if (owners_removed.length() > 0) {
                emit(
                    RemoveOwners { multisig_account: multisig_address, owners_removed }
                );
            }
        };
