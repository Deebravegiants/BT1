## Title
Webhook shop-domain (and topic/webhook_id/api_version) header spoofing enables cross-tenant webhook injection - (File: `lib/shopify_api/webhooks/request.rb`)

## Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used downstream to identify and route the webhook are read from unauthenticated HTTP headers. Any tenant that can obtain one genuinely-signed webhook (i.e., any merchant who installs the app, since all shops share the same `api_secret_key`) can replay that exact body+HMAC pair while swapping the `x-shopify-shop-domain` header to point at a different shop, and `ShopifyAPI::Webhooks::Registry.process` will accept it as authentic and hand the forged shop identity to the host application's handler.

## Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

but the object also exposes `shop`, `topic`, `webhook_id`, and `api_version`, all sourced from headers that are never included in the signed content: [2](#0-1) 

`Registry.process` validates only the HMAC over the body via `Utils::HmacValidator.validate(request)`, and then constructs `WebhookMetadata` directly from the unauthenticated header-derived fields, including `shop: request.shop`: [3](#0-2) 

`Utils::HmacValidator.validate` in turn only checks `verifiable_query.to_signable_string` (the raw body) against the HMAC, never binding it to `shop`: [4](#0-3) 

The `Shopify` app secret (`api_secret_key`) used to sign webhooks is a single, shared secret across all shops that install the app — it is not per-shop. Consequently, the identity binding the gem's design implicitly relies on is:

`HMAC(raw_body, api_secret_key)` valid  ⇒  `request.shop` is the true origin shop

but the actual binding enforced is only:

`HMAC(raw_body, api_secret_key)` valid  ⇒  `raw_body` was produced/authorized by Shopify for *some* shop using this app

Nothing ties the specific `shop` header to the signature. The gem's own documentation confirms this field is meant to be trusted directly by host applications as the tenant identifier: [5](#0-4) [6](#0-5) 

## Impact Explanation
A malicious merchant who has legitimately installed the app on their own store (an unprivileged tenant relative to other merchants of the same app) will receive real, correctly-signed webhook deliveries from Shopify for their own shop. Because the HMAC covers only the body, the attacker can capture one such (body, HMAC) pair and resubmit it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain (and `topic`/`webhook_id` freely modified too). `Registry.process` will accept the forged request as valid and invoke the host handler with `WebhookMetadata#shop` set to the victim's domain, per the gem's documented contract. Any host application that uses `data.shop` to select the tenant record to update (exactly as the gem's own example code does: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) will apply attacker-controlled data to another merchant's tenant — a cross-tenant data injection/corruption impacting a shop the attacker does not control.

## Likelihood Explanation
Any developer/tester can freely create a Shopify development store and install an app built on this gem, which is enough to obtain a validly-signed webhook body/HMAC pair for replay, since all shops share one `api_secret_key`. No access to the app's `client_secret`/access tokens beyond what a normal merchant installation grants is required, and no TLS interception or social engineering is needed — only issuing a normal HTTP POST to the app's public webhook endpoint with modified headers.

## Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`/`api_version`) to the HMAC-verifiable content, e.g. by including these header values in `to_signable_string`, or by requiring/encouraging the host application to cross-check `request.shop` against an out-of-band expected shop (such as the path segment used at webhook registration time) before trusting it, and documenting this requirement clearly.

## Proof of Concept
1. Install the app (built on this gem) on attacker-controlled shop `attacker.myshopify.com`; capture one legitimate webhook POST, including its raw body `B` and the `x-shopify-hmac-sha256` header value `H` (valid because `H = HMAC-SHA256(api_secret_key, B)`).
2. Craft a new HTTP POST to the same webhook endpoint URL with body `B` and header `x-shopify-hmac-sha256: H` unchanged, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` builds a `Request`, calls `Utils::HmacValidator.validate(request)` which succeeds because it only checks `B` against `H` — see: [3](#0-2) 
4. The handler is invoked with `WebhookMetadata.new(... shop: "victim.myshopify.com", body: <attacker-controlled parsed body>)`, and any host application following the gem's documented pattern applies this data to `victim.myshopify.com`'s tenant record.

          received_signature = verifiable_query.hmac
