### Title
Missing length validation before offset-based `Bytes.substr` reads on attacker-controlled BEEFY digest payload can read past buffer bounds - ([File: evm/src/consensus/Types.sol])

### Summary
`HeaderImpl.stateCommitment` extracts the ISMP MMR root and child-trie root from a BEEFY header's `ISMP_CONSENSUS_ID` digest by slicing `digest.consensus.data` at fixed offsets 0 and 32 without ever checking that `data.length >= 64`. The digest bytes themselves are decoded from an attacker-supplied, SCALE length-prefixed field (`Codec.decodeDigestItem`), so a relayer can submit a consensus update whose consensus digest declares any length it wants for `data`. This is analogous to the Apache Fory bug class: a length/offset used to read a buffer is taken from untrusted input and never validated against the buffer's actual bounds before the read is performed.

### Finding Description
The BEEFY header decode path is:
- `Codec.decodeDigestItem` (evm/src/consensus/Codec.sol:104-110) reads a 4-byte digest id, then a SCALE compact `length`, then reads exactly `length` bytes into `data` via `Bytes.read`. `length` is fully attacker-controlled (a relayer crafts the header bytes submitted to `DecodeHeader`). [1](#0-0) 

- `HeaderImpl.stateCommitment` then unconditionally does:
```solidity
mmrRoot = Bytes.toBytes32(Bytes.substr(self.digests[j].consensus.data, 0, 32));
childTrieRoot = Bytes.toBytes32(Bytes.substr(self.digests[j].consensus.data, 32));
```
with no check that `self.digests[j].consensus.data.length >= 64` before slicing at offset 32 for 32 more bytes. [2](#0-1) 

Because `Bytes.substr` comes from the vendored `@polytope-labs/solidity-merkle-trees` package and its source was not present in the indexed files, I could not directly confirm at what exact byte its internal bounds check (if any) trips. However, the root cause defect is squarely in Hyperbridge's own code: `stateCommitment` never validates the length invariant it depends on (`data.length == 64`) before performing offset+length reads that the calling code assumes are always in-bounds. This is the same bug class as `readAlignedVarUint()` in Fory: a size/offset derived from an untrusted length field is used to index into a buffer without validating that the buffer actually contains that many bytes.

This function is reached from the BEEFY consensus-update entrypoints, which are invoked by any relayer submitting a consensus proof: [3](#0-2) [4](#0-3) 

### Impact Explanation
`mmrRoot` and `childTrieRoot` feed directly into the `StateCommitment` that `EvmHost` stores and later uses for all state/non-membership proof verification for that state machine height. If a relayer can submit a BEEFY header whose `ISMP` consensus digest has fewer than 64 bytes, the two fields end up populated from memory outside the intended `data` slice (whatever `Bytes.substr`'s underlying behavior turns out to be — either a revert, or reading adjacent memory words). If it silently returns unintended memory content rather than reverting, the resulting corrupted/incorrect `mmrRoot`/`childTrieRoot` gets accepted and stored as a valid state commitment, which can desynchronize or corrupt the trusted state root used for all subsequent ISMP request/response proof verification on that route — a state-commitment-soundness break reachable from a single relayed consensus proof.

### Likelihood Explanation
Reaching this code path requires only submitting a BEEFY consensus update — an action any relayer is expected and permitted to perform, with no special privileges. Crafting a header whose consensus digest declares `length < 64` is a matter of encoding the SCALE compact length prefix accordingly in `Codec.decodeDigestItem`; nothing else in `DecodeHeader` or `stateCommitment` prevents it.

### Recommendation
In `HeaderImpl.stateCommitment`, before slicing, require `self.digests[j].consensus.data.length >= 64` (revert with a descriptive error such as `InvalidConsensusDigestLength`) whenever `consensusId == ISMP_CONSENSUS_ID`, mirroring the existing `TimestampNotFound` sanity check pattern already present for the timestamp digest.

### Proof of Concept
1. Craft a BEEFY header where a digest item has `kind = DIGEST_ITEM_CONSENSUS`, `id = "ISMP"`, and a SCALE compact length prefix declaring `data.length` to be, e.g., 10 bytes (instead of the expected 64).
2. Submit this header through the standard consensus-update path (`EcdsaBeefy`/`SP1Beefy` → `Codec.DecodeHeader` → `HeaderImpl.stateCommitment`).
3. Observe that `Bytes.substr(data, 32)` is invoked on a 10-byte array requesting bytes `[32, 64)`, a read past the end of the intended buffer, with no length guard in `stateCommitment` to reject the malformed digest beforehand.

Note: I was unable to inspect the vendored `Bytes.substr` implementation (external `@polytope-labs/solidity-merkle-trees` dependency, not present in the indexed repository contents) to confirm its exact runtime behavior on out-of-bounds offsets (revert vs. silent OOB memory read). The root-cause defect — Hyperbridge's own `stateCommitment` never validating the length invariant before relying on it — is confirmed directly in the repository.

    /// @dev Decodes a SCALE-encoded digest item (4-byte consensus id + length-prefixed data).
    function decodeDigestItem(ByteSlice memory slice) internal pure returns (DigestItem memory) {
        bytes4 id = Bytes.toBytes4(read(slice, 4), 0);
        uint256 length = ScaleCodec.decodeUintCompact(slice);
        bytes memory data = Bytes.read(slice, length);
        return DigestItem(id, data);
    }
