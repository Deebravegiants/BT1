### Title
Accrual overflow permanently freezes an oversized market - ([File: common/src/rates/simulate.rs](common/src/rates/simulate.rs))

### Summary
`update_indexes` and every pool mutation synchronize interest before changing state. Accrual converts scaled debt and supply to original values with `borrowed * borrow_index` and `supplied * supply_index`, but those products are fixed-width `i128` operations. Once either product exceeds `i128::MAX`, accrual panics with `MathOverflow`. Because the stored scaled totals cannot be reduced without first completing accrual, repayment, withdrawal, liquidation, and later index updates all hit the same panic. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
The public controller `update_indexes(caller, assets)` path reaches `ops::market::accrue`, which loads each listed market and calls `interest::global_sync`. [4](#0-3)  `global_sync` processes all elapsed time in bounded chunks before stamping the market accrued. [5](#0-4)  Each chunk calls `accrue_step`; its first operations unscale both aggregate books through `scaled_to_original`, and `scaled_to_original` delegates to `Ray::mul`. [6](#0-5)  `Ray::mul` performs fixed-point multiplication and returns an `i128` result, so an oversized scaled book times its index exceeds representable RAY value before the borrow-index ceiling can engage. [7](#0-6) [8](#0-7) 

The production sequence is reachable with only unprivileged calls:

1. An attacker controls two addresses/accounts.
2. One supplies a very large amount of an 18-decimal market asset through `supply`.
3. The other supplies sufficient collateral and calls `borrow`, creating a large scaled debt book.
4. Time elapses at sustained high utilization.
5. The attacker calls `update_indexes(caller, [hub_asset])`.
6. Accrual panics while converting `borrowed` or `supplied` to its original value.
7. Subsequent `repay`, `withdraw`, `liquidate`, borrowing, supplying, and `update_indexes` calls invoke `synced_market` or `accrue` first and panic at the same multiplication.

This is not a resource-limit or malformed-transaction failure: the accepted market state itself grows into an arithmetic state that no subsequent market operation can process. [9](#0-8) 

### Impact Explanation
The market becomes permanently frozen unless out-of-scope privileged recovery or an upgrade is available. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot reduce risk, and permissionless accrual cannot advance the market. Pool administration that synchronizes before updating parameters also cannot repair the state through the ordinary `update_params`/rate-model path because it accrues under the existing state first. [10](#0-9) 

The harness reproduces the end state directly: after the accrual attempt returns `MathOverflow`, both a withdrawal and a repayment fail with `MathOverflow`. [11](#0-10)  This satisfies permanent freezing of user funds and leaves an insolvency risk unmanaged because liquidation also must pass the same accrual barrier.

### Likelihood Explanation
The trigger requires a market whose configured caps, token supply, and decimals permit a scaled book close to the RAY/`i128` ceiling, then sustained high utilization long enough for index growth to push `book * index` past `i128::MAX`. Those are deployment and capital requirements rather than privileges: an attacker can split the supplier and borrower roles across accounts they control.

The included harness uses a one-billion-token, 18-decimal market at approximately 98% utilization and demonstrates that the RAY-value ceiling is reached before `MAX_BORROW_INDEX_RAY`. [12](#0-11)  Smaller or lower-decimal markets have proportionally more headroom, so exploitability depends on the deployed market scale and rate configuration.

### Recommendation
Represent aggregate scaled-value multiplication with a wider intermediate type throughout `accrue_step`, especially the `scaled_to_original` calls and subsequent debt/reward calculations. If i128 value capacity is intentionally treated as an economic ceiling, enforce it at market entry by capping scaled supply/debt and index growth below the overflow boundary, and make the failure recoverable rather than allowing the first sync after the boundary to brick repayment and withdrawal. Add a regression test proving that a market at the configured maximum scale can still accrue, repay, withdraw, and liquidate after reaching the highest permitted index.

### Proof of Concept
The repository already contains a deterministic reproduction in `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs`:

```rust
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);
let debt = principal / 100 * 98;
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);

// Advance time and attempt permissionless accrual.
t.advance_time(YEAR_SECS);
t.try_update_indexes_for(&["BIG18"]); // -> MathOverflow

// Every path that must accrue first is then blocked.
t.try_withdraw_raw(BOB, "BIG18", 1);  // -> MathOverflow
t.try_repay(ALICE, "BIG18", 1.0);     // -> MathOverflow
```

The test documents that a billion 18-decimal-token book corresponds to `1e36` raw RAY while `i128::MAX` is only about 170 times larger, so index growth past roughly 170x overflows before the borrow-index cap engages. [11](#0-10)

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
```

```rust
/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```
