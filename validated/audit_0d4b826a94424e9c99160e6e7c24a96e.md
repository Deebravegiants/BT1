### Title
Webhook `shop`, `topic`, `api_version`, and `webhook_id` fields are trusted by handlers without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook exclusively via `Utils::HmacValidator.validate(request)`, whose signable content is `Request#to_signable_string`, which returns only `@raw_body`. However, the tenant-identifying `shop` field (and `topic`, `api_version`, `webhook_id`) are read straight from HTTP headers and passed unverified into `WebhookMetadata`, which is handed to the app's `WebhookHandler#handle`. These header fields are never part of the HMAC-signed bytes.

### Finding Description
`lib/shopify_api/webhooks/request.rb` implements `Utils::VerifiableQuery`: [1](#0-0) 
`to_signable_string` returns only the raw body, while `shop`, `topic`, `api_version`, and `webhook_id` are pulled from headers via `shopify_header`: [2](#0-1) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (which HMACs `to_signable_string`, i.e., the body) before dispatching to the handler with the header-derived `shop`: [3](#0-2) 

`Utils::HmacValidator.validate_signature` computes the HMAC over `verifiable_query.to_signable_string` only: [4](#0-3) 

`WebhookMetadata.shop` is a plain, unauthenticated field that the handler receives as the tenant identity for the event: [5](#0-4) 

This breaks the intended binding: `HMAC-verified-bytes == raw_body` but `data acted on == raw_body + shop-domain header (unverified)`. Since one Shopify app's `client_secret` is shared across every merchant that installs the app, any legitimate merchant of that same app receives genuinely-signed webhook deliveries (valid HMAC over their own body) for their own shop. Because the signature never covers the `shop-domain` header, that merchant (or anyone who can capture one such delivery) can replay the exact `raw_body` + valid `hmac` to the app's webhook endpoint while substituting a different `shop-domain` (and/or `topic`/`webhook_id`/`api_version`) header. `Registry.process` will still validate the HMAC successfully (it only checks the body) and will invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop domain.

### Impact Explanation
If the host application's webhook handler uses `data.shop` to key any per-tenant action (e.g., writing to that shop's `Session`, deleting or mutating that shop's data, invalidating access, processing GDPR redact/data-request flows, etc. — exactly the kind of mandatory topics registered via this gem, `shop/redact`, `customers/redact`, `customers/data_request`, see `MANDATORY_TOPICS`), an attacker who is a merchant on the same app can forge webhook events that are processed under another shop's identity while the request passes HMAC validation. This is a cross-tenant identity-binding bypass: Critical impact per the rubric (cross-tenant access), reachable without needing the app's `client_secret`, an access token, or any privileged credential — only a legitimate installation on the same shared-secret app plus the ability to capture one genuine webhook body+HMAC pair (visible to that merchant's own endpoint by design).

### Likelihood Explanation
Any merchant that installs a multi-tenant Shopify app automatically receives real webhook deliveries with valid HMAC signatures for their own shop. Capturing raw_body + hmac header from one's own legitimate webhook requires no special access. Replaying it to the same app's public webhook endpoint with a modified `shop-domain` header requires only an HTTP client. No secret material, token, or elevated privilege is needed — likelihood is high wherever the host app trusts `WebhookMetadata#shop`/`topic`/`webhook_id` for authorization or data-scoping decisions.

### Recommendation
Include the identifying headers (`shop-domain`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed material, or otherwise cryptographically bind them (e.g., verify `shop-domain` against a server-side registry of the topic/webhook_id via a trusted lookup) before constructing `WebhookMetadata`. At minimum, document prominently that `WebhookMetadata#shop` is not authenticated by the HMAC check and must not be trusted as a tenant boundary without independent verification (e.g., cross-checking against the shop stored for the `webhook_id` from `GET /webhooks/{id}.json` or an app-side webhook_id-to-shop mapping recorded at registration time).

### Proof of Concept
1. App A is installed on `shop-a.myshopify.com` and `shop-b.myshopify.com`, sharing one `client_secret`.
2. Shopify delivers a genuine webhook to the app for `shop-a`: headers include `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, body `{}`.
3. A merchant/operator controlling `shop-a`'s endpoint captures `raw_body="{}"` and the valid `hmac` header.
4. Attacker POSTs to the app's webhook route with the same `raw_body` and same `hmac` header, but `x-shopify-shop-domain: shop-b.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` which only checks `raw_body` against `hmac` — validation succeeds: [6](#0-5) 
6. The handler is invoked with `WebhookMetadata(shop: "shop-b.myshopify.com", ...)`, even though the request never actually came from Shopify on behalf of `shop-b`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
