## Title
Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (and `topic`, `webhook_id`, `api_version`) values from HTTP headers, but the HMAC signature that `Utils::HmacValidator` verifies is computed **only over the raw request body**. Because the shop identity is never part of the signed material, anyone who can obtain one valid `(raw_body, hmac)` pair from Shopify (e.g. by triggering a webhook on their own, attacker-controlled shop that has the app installed) can replay that exact body/HMAC pair to the app's public webhook endpoint while swapping the `X-Shopify-Shop-Domain` header to a victim shop. The HMAC check still passes, and the registry hands the forged `shop` value straight to the app's webhook handler as if it were authentic.

### Finding Description
`lib/shopify_api/webhooks/request.rb` implements `VerifiableQuery`: [1](#0-0) 

`shop` is read from the `shop-domain` header, completely independent of `to_signable_string`, which returns only `@raw_body`.

`Utils::HmacValidator.validate` computes and compares the signature using exclusively `verifiable_query.to_signable_string`: [2](#0-1) 

`Webhooks::Registry.process` trusts `request.shop` after only checking the HMAC of the body: [3](#0-2) 

Because the app's `client_secret`/`api_secret_key` is shared across every shop that installs the app, `HMAC(secret, raw_body)` is identical no matter which shop actually triggered the event. This breaks the intended binding `shop == authenticated_source_of(raw_body)`: an attacker who legitimately controls Shop A (a normal, unprivileged merchant) can capture a real webhook delivery for Shop A (body + valid `hmac-sha256`), then re-POST the identical body and HMAC directly to the app's webhook endpoint with the `shop-domain` header replaced by Shop B's (victim) domain. `Utils::HmacValidator.validate` still succeeds (it never inspects the header), and `Registry.process` invokes the app's handler with `shop: "shop-b.myshopify.com"`, even though none of the data actually originated from Shop B.

### Impact Explanation
This is a cross-tenant spoofing vulnerability (High, potentially Critical depending on handler logic): a malicious merchant/app-installer can forge webhook events (e.g. `orders/create`, `customers/update`, or `app/uninstalled`) that appear to belong to a different, victim tenant of the same app. Depending on how the host app's webhook handlers act on `WebhookMetadata#shop` (e.g. syncing data, revoking access, writing to per-shop storage keyed by `shop`), this can lead to data corruption, spoofed business events, or state confusion across tenants — directly crossing the tenant isolation boundary that `shop` is meant to enforce.

### Likelihood Explanation
Any user who can install the app on at least one shop (a normal, unprivileged action available to any merchant) can trigger a real webhook to obtain a valid `(body, hmac)` pair, then simply resend it with a different `shop-domain`/`x-shopify-shop-domain` header value to the app's public webhook endpoint. No access to `api_secret_key`, tokens, or the victim's data is required — only knowledge of the victim's shop domain, which is not secret.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the value that gets HMAC-verified, or otherwise cross-check `request.shop` against an independently trusted source (e.g. an installed/known shop list, or validate it against `Utils::ShopValidator` combined with a signed value) before trusting it in `Registry.process`. At minimum, `to_signable_string` in `lib/shopify_api/webhooks/request.rb` should incorporate the shop domain header so a captured payload cannot be replayed against a different shop.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` and triggers a webhook event (e.g. updates a product), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header value that Shopify computed and sent to the app's webhook URL.
2. Attacker sends a new HTTP POST to the same app webhook URL, with:
   - Identical raw body (from step 1)
   - Identical `X-Shopify-Hmac-Sha256` header (from step 1)
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (or any other shop domain of an app installer)
3. `ShopifyAPI::Webhooks::Request.new` parses this request; `Utils::HmacValidator.validate` succeeds because it only validates `raw_body` against the shared `api_secret_key`.
4. `ShopifyAPI::Webhooks::Registry.process` invokes the app's handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)`, causing the app to act on forged data attributed to the victim shop.
