This confirms the vulnerability: `Registry.process` calls `Utils::HmacValidator.validate(request)`, which verifies the HMAC only over `request.to_signable_string` (the raw body). The `request.shop` value (from the `X-Shopify-Shop-Domain` header) is never included in the signed bytes, yet it is trusted and passed straight into `WebhookMetadata.new(... shop: request.shop ...)` which app handlers use to determine which merchant/tenant the webhook data belongs to.

### Title
Webhook `shop` header is trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw request body only [1](#0-0) , while the `shop` value used downstream to identify the tenant is read from the unauthenticated `shopify-shop-domain` HTTP header [2](#0-1) . `Registry.process` validates only that HMAC before dispatching the handler with the attacker-controlled `shop` value [3](#0-2) .

### Finding Description
`Utils::HmacValidator.validate` recomputes the signature strictly from `verifiable_query.to_signable_string` and compares it to `verifiable_query.hmac` [4](#0-3) . For webhooks, `to_signable_string` returns only `@raw_body` [1](#0-0) . None of `topic`, `shop-domain`, `api-version`, or `webhook-id` headers are part of the signed bytes; they are parsed straight from attacker-reachable HTTP headers [5](#0-4) .

This breaks the equality the app relies on: `shop (verified by HMAC) == shop (acted upon by handler)`. In reality, `shop (HMAC-covered) = raw_body only`, while `shop (acted upon) = shopify-shop-domain header`, an entirely separate, unauthenticated channel. Because a webhook body containing tenant identifiers is typically shop-specific data anyway, and Shopify's own webhook payloads always pair a correct body with a correct header, this class of bug specifically enables an attacker who receives (or replays) one legitimately-signed webhook delivery (e.g., their own store's outgoing webhook, which they can freely trigger and capture since they control that store and its HMAC key is the same shared `client_secret` used for the app's webhook subscriptions) to resend the exact same signed body while substituting a victim shop's domain in the header. `Registry.process` will pass HMAC validation (since only the body is checked) and hand the handler a `WebhookMetadata` claiming the data belongs to the victim's shop [6](#0-5) .

### Impact Explanation
This is a cross-tenant data/identity confusion vulnerability: the app-level webhook handler receives forged tenant attribution (`shop`) for otherwise-genuinely-signed data. Any app logic that keys persistence, authorization, or side effects (e.g., updating merchant records, revoking access, processing `shop/redact`) off `WebhookMetadata#shop` can be tricked into acting on behalf of, or against, a shop that did not send the request. This matches the Critical "cross-tenant access" impact category since the tenant boundary (shop identity) is not authenticated by the HMAC that the gem itself validates.

### Likelihood Explanation
Exploitation requires only the ability to send crafted HTTP requests with attacker-controlled headers, which any unprivileged internet user can do to the app's public webhook endpoint. The attacker needs one validly HMAC-signed body (trivially obtainable by owning any Shopify store that installs the same app, since the webhook HMAC secret is the app's shared `client_secret`, common to all shops using that app) and simply swaps the `shop-domain` header value before replaying the request.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signable bytes that are HMAC-verified, or otherwise cryptographically bind the `shop` header to the signed body before trusting it in `Registry.process`/`WebhookMetadata`. At minimum, document and enforce that consuming apps must independently verify `request.shop` against a known/allow-listed shop record rather than trusting the header value implicitly.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`. Trigger any webhook topic the app subscribes to (e.g. `orders/create`) to receive a body + genuine `X-Shopify-Hmac-Sha256` signature computed with the app's shared `client_secret`.
2. Capture the raw POST: headers `X-Shopify-Topic`, `X-Shopify-Hmac-Sha256: <valid-hmac>`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, and the JSON body.
3. Replay the exact same body and HMAC header to the app's webhook endpoint, but change `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the (unchanged) body signature and passes [7](#0-6) .
5. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, causing the app to process attacker-supplied data under the victim's identity [6](#0-5) .
