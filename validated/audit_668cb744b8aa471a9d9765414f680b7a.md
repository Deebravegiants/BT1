## Title
Webhook `shop` and `topic` identity fields are not covered by the HMAC signature, allowing tenant-spoofed webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then trusts the `shop-domain` and `topic` HTTP headers — which are never included in the signed material — to determine which tenant/topic the payload belongs to.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `shop` and `topic` (and `webhook_id`) are pulled straight out of unauthenticated headers: [2](#0-1) 

`Registry.process` validates the HMAC of the body, then immediately hands `request.topic` and `request.shop` — neither of which is covered by that HMAC — to the host application's handler as trusted tenant-identifying metadata: [3](#0-2) 

The `Utils::HmacValidator.validate` call verifies `computed_signature == received_signature` where `computed_signature = HMAC(secret, verifiable_query.to_signable_string)`: [4](#0-3) 

This produces the exact binding break the analog rule targets: `bytes_verified (raw_body)` ≠ `identity_fields_acted_on (shop, topic headers)`. Since `shop-domain`/`topic` are outside the signed scope, any request with a body+HMAC pair that is valid for the app's secret (obtainable by an unprivileged user simply by installing the app on their own trial/dev shop and capturing one of their own genuine webhooks) can be replayed to the webhook endpoint with the `shop-domain` header rewritten to a victim shop's domain and/or a different `topic` header, while the HMAC check still passes because it only re-validates the unchanged body bytes.

### Impact Explanation
`WebhookMetadata.shop` is constructed directly from the forged header and passed to the host application's `WebhookHandler#handle`: [5](#0-4) 

Any host application that uses this trusted-but-unverified `shop` field to key session/store lookups (a documented, expected usage pattern of this gem) will apply the attacker's own webhook payload under a victim tenant's identity — a cross-tenant data/action confusion achieved without possessing the victim's access token, refresh token, or the app's `client_secret`.

### Likelihood Explanation
Any user who can install the app on a shop they control (unprivileged relative to other merchants) can obtain a genuine `(raw_body, hmac)` pair signed with the app's real secret, then replay it with modified `shop-domain`/`topic` headers against the webhook endpoint. No access to `api_secret_key`, tokens, or TLS interception is required — only a legitimate HMAC generated for the attacker's own tenant.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable string (or otherwise cryptographically bind them, e.g., verify the `shop-domain` header against the shop tied to the caller's own credentials/session before dispatching) so the HMAC covers every field the host application is expected to trust for tenant routing, not just the raw body.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a genuine webhook: headers include `X-Shopify-Hmac-Sha256: <valid-hmac>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`, and some `raw_body`.
2. Attacker resends the exact same `raw_body` (and therefore the same valid `hmac`) to the app's webhook endpoint, but replaces the header `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`= raw_body`, unchanged) and it matches — validation passes: [6](#0-5) 
4. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` now carries `shop: "victim-shop.myshopify.com"` even though the payload actually originated from the attacker's shop, and is passed to the host app's handler as authenticated data.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
