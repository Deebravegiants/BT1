### Title
Webhook shop/topic identity spoofing via HMAC that only covers the raw body - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `topic`, `shop`, `webhook-id`, and `api-version` fields are taken from unauthenticated HTTP headers and passed straight through to the application's webhook handler as trusted tenant-identification data.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are read from separate, unsigned headers: [2](#0-1) 

`Registry.process` validates only the body-derived HMAC and then dispatches the handler using the unauthenticated `request.shop`/`request.topic` values as the tenant identity for the event: [3](#0-2) 

`HmacValidator.validate_signature` confirms this: it signs/verifies `verifiable_query.to_signable_string` (the raw body for webhooks) against the single, app-wide `Context.api_secret_key` — the same secret is shared across every shop that has installed the app, it is not shop-specific: [4](#0-3) 

The identity binding this breaks is: `hmac == HMAC(secret, body)` should imply `shop_header == shop_that_produced(body, hmac)`, but the gem only proves `hmac == HMAC(secret, body)`; it never binds `shop`/`topic`/`webhook_id` into that signature. Because the HMAC secret is shared by the whole app across all merchants, any shop that has legitimately installed the app can capture one of its own genuine webhook deliveries (`raw_body` + valid `x-shopify-hmac-sha256`) and replay that exact body to the app's public webhook endpoint with a forged `x-shopify-shop-domain` (and/or `x-shopify-topic`) header claiming to be a different, victim shop. `Utils::HmacValidator.validate` will accept it because it never inspects those headers, and `Registry.process` will hand the forged shop/topic to the application's handler as if Shopify itself had sent it for that shop.

The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify," which overstates what is actually verified — only the body bytes are authenticated, not the shop/topic identity that handlers rely on: [5](#0-4) 

### Impact Explanation
This is a cross-tenant integrity issue: a party with a legitimate installation for their own shop can forge webhook events that the host application will process under a different shop's identity, since `WebhookMetadata#shop`/`#topic` are unauthenticated. Any downstream logic keyed on `data.shop` (e.g., order/customer processing, billing triggers, data sync) can be corrupted or spoofed for a shop the attacker does not control, meeting the "cross-tenant access" bar.

### Likelihood Explanation
Requires only a legitimate (even single) installation of the target app somewhere, ability to capture one raw webhook body + its HMAC header for one's own shop, and the ability to POST that captured pair to the app's public webhook endpoint with a different `x-shopify-shop-domain`/`x-shopify-topic`. No access token, `client_secret`, or privileged account is required — the shared `api_secret_key` used for HMAC verification is by design common to all installs of the app.

### Recommendation
Bind the shop/topic identity into the verified signature (or otherwise cryptographically tie `Request#shop`/`#topic`/`#webhook_id` to the validated payload) rather than trusting header values whose provenance the HMAC does not cover. At minimum, document clearly that `shop`/`topic` are not part of the HMAC-protected content so host applications know they must independently corroborate the shop (e.g., against a known/registered shop list) before trusting `WebhookMetadata#shop`.

### Proof of Concept
1. Attacker installs the target app for their own shop `attacker.myshopify.com` and receives a genuine webhook: raw body `B`, header `x-shopify-hmac-sha256: H` (computed as `HMAC-SHA256(api_secret_key, B)`), `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`.
2. Attacker POSTs the same body `B` and header `H` to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers, `Utils::HmacValidator.validate` succeeds because it only recomputes `HMAC(api_secret_key, B)` and never checks the shop header (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the host app to process forged data under the victim shop's identity.
