### Title
Webhook shop/topic/webhook-id identity headers are not covered by the HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `shop-domain`, `topic`, and `webhook-id` headers to build the `WebhookMetadata` handed to the app's handler. Because the signature never covers these header values, an attacker who possesses any one valid `(body, hmac)` pair signed with the app's shared secret can replay that pair with a forged `shop-domain` header for a different merchant, and the library will accept it as an authentic webhook for that victim shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC purely from `to_signable_string`, i.e. only the body, never the headers: [3](#0-2) 

`Webhooks::Registry.process` gates on that same body-only HMAC check, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` — all sourced from unauthenticated headers — to construct the metadata passed to the registered handler: [4](#0-3) 

The identity binding that should hold is: `hmac == HMAC(secret, body ‖ shop ‖ topic ‖ webhook_id)`. In this implementation the actual equality enforced is only `hmac == HMAC(secret, body)`, while `shop`, `topic`, and `webhook_id` — the very fields the handler uses to decide *which tenant's* data to act on — are read straight from `request.shop` / `request.topic` / `request.webhook_id` without any cryptographic tie to the signature. Since the app's `api_secret_key` is shared across all shops that install the app, any attacker who can install the app on their own store (an ordinary, unprivileged action) will receive real webhooks with valid HMACs computed over bodies they control the timing/topic of. They can then send the exact same `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header (and/or `x-shopify-topic`/`x-shopify-webhook-id`) with a victim shop's domain. `HmacValidator.validate` still succeeds because it never looks at the headers, and `Registry.process` dispatches the payload to the handler labeled as coming from the victim shop.

### Impact Explanation
This breaks the tenant boundary the gem is meant to enforce for webhook authenticity: the handler receives content it believes was verified as sent by Shopify *for a specific shop*, when in fact only the body's authenticity (from *some* shop) is verified, not the shop attribution. Any host application that uses `WebhookMetadata#shop` to select which merchant's records to create/update/delete (the intended and documented use of that field) can be made to write attacker-supplied webhook content into a different, victim tenant's data — a cross-tenant access primitive achieved with no access token, no leaked credential, and no privileged account.

### Likelihood Explanation
Requires only: (1) the attacker installs the target app on their own shop (self-service, unprivileged), (2) they receive one legitimate webhook delivery with a valid HMAC, and (3) they replay it to the app's webhook endpoint with a modified `shop-domain` (and optionally `topic`/`webhook-id`) header. No secret material, no bypass of TLS, and no interaction with a privileged account is needed.

### Recommendation
Include the identity headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the signed payload, so that `HmacValidator.validate` fails if any of these fields are altered after Shopify computed the signature.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook topic, capturing the raw POST body `B` and the resulting `X-Shopify-Hmac-Sha256` header `H` (valid since it is computed only from `B`).
2. Send a new POST to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged), but `X-Shopify-Shop-Domain: victim.myshopify.com` (and any desired `X-Shopify-Topic`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H`.
4. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: <attacker-chosen>, body: <attacker-controlled>, ...)`, causing the host application to act on attacker-controlled data attributed to the victim shop.
