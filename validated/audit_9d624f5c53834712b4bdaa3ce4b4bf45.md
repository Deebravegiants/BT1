## Title
Session-token `dest` claim used as tenant identity without cross-checking `iss`, and `shop` used to derive `client_secret`-carrying request host without domain sanitization - (File: lib/shopify_api/auth/jwt_payload.rb, lib/shopify_api/auth/token_exchange.rb)

### Summary
`ShopifyAPI::Auth::JwtPayload` verifies the JWT's HMAC signature and `aud` claim, but never checks that the `dest` claim (the tenant identity used everywhere downstream) is consistent with the `iss` claim. [1](#0-0)  `TokenExchange.exchange_token` then takes `jwt_payload.shop` (derived solely from `dest`) and uses it, unsanitized, as the HTTP host of the token-exchange request that carries the app's `client_id`/`client_secret` in the POST body. [2](#0-1)  `Clients::HttpClient` builds the request's base URI directly from `session.shop`. [3](#0-2) 

### Finding Description
The equality that should hold is: **the shop the session token was issued for (`iss`) == the shop the caller is granted access to (`dest`) == the host that receives the app's `client_secret`**.

`JwtPayload#initialize` only validates:
1. The JWT signature (HS256 with `Context.api_secret_key`, with fallback to `old_api_secret_key`).
2. That `aud == Context.api_key`.

It never asserts `dest == iss` (stripped of scheme/path), unlike the equivalent check present in Shopify's other official SDKs, which reject a token when `dest` and `iss` disagree. Because `shop` (used as `jwt_session_id`/`offline_session_id` and as the request host for token exchange) is taken purely from `dest`, any signed token where `dest` differs from `iss` would be accepted and its `dest` value trusted as the tenant identity, with no domain sanitization (unlike `ClientCredentials.client_credentials` and `TokenExchange.migrate_to_expiring_token`, which both call `Utils::ShopValidator.sanitize!(shop)` before use). [4](#0-3) [5](#0-4) 

In `exchange_token`, `dest_shop` is passed straight into `Session.new(shop: dest_shop)` and then into `HttpClient.new(session: shop_session, ...)`, whose constructor sets `@base_uri = "https://#{api_host || session.shop}"` — i.e., `dest_shop` becomes the literal HTTPS host that receives a POST body containing `client_id` and `client_secret`. [6](#0-5) [3](#0-2)  There is no call to `ShopValidator.sanitize!` on `dest_shop` in `exchange_token`, in contrast to the sibling method `migrate_to_expiring_token`, which does sanitize its `shop` argument. [7](#0-6) 

### Impact Explanation
If an attacker can produce (or obtain) a validly-signed session token whose `dest` claim points to an arbitrary/attacker-controlled host while `iss`/`aud` otherwise look legitimate, the gem would issue an outbound request to that host containing the app's `client_id` and `client_secret` — an SSRF carrying the app's OAuth client credentials (matches the in-scope "SSRF with the app's credentials" / "credential leakage" category). Additionally, because `dest` is trusted without being cross-verified against `iss`, and no sanitization against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` is performed in `exchange_token`, an unbound `dest` value could route a subsequent session/token to an unintended tenant host.

### Likelihood Explanation
This finding is **partially unverified**: producing a token with a mismatched `dest`/`iss` requires either (a) a legitimate Shopify-issued token where these claims genuinely diverge (which the library should still reject if Shopify's own token-issuance guarantees this invariant, making it defense-in-depth only), or (b) an attacker with access to `api_secret_key` to forge such a token — which is explicitly out of scope per the rules ("anything requiring... leaked credentials"). Without a concrete way for an *unprivileged* internet user to produce a signature-valid token with an attacker-chosen `dest`, this cannot be escalated past a defense-in-depth gap; I could not find a code path in-scope that lets an untrusted party control `dest` independent of possessing the app secret. I flag this as the strongest analog structurally (identity binding between `iss`/`dest`, and `shop`→request-host binding lacking sanitization in `exchange_token` specifically, unlike its sibling method), but I am not confident it clears the bar of a concretely exploitable vulnerability without secret compromise.

### Recommendation
- In `JwtPayload#initialize`, add a check that the shop derived from `dest` matches the shop encoded in `iss` (mirroring the `admin_session_token?` style check), raising `InvalidJwtTokenError` on mismatch.
- In `TokenExchange.exchange_token`, sanitize `dest_shop` through `Utils::ShopValidator.sanitize!` before constructing `shop_session`, for parity with `client_credentials.rb` and `migrate_to_expiring_token`.

### Proof of Concept
Not reproducible as a concrete unprivileged-attacker exploit with the tools available: constructing a signature-valid JWT with a mismatched `dest` requires possession of `Context.api_secret_key`, which is out of scope per the rules. No PoC is provided because the only in-scope observation is a structural/defense-in-depth gap (missing `iss`/`dest` cross-check, missing `sanitize!` call in `exchange_token`), not a demonstrated cross-tenant/SSRF exploit reachable by an unprivileged internet user.
