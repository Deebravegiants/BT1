### Title
Unvalidated strategy routes can inject wallet-token theft into the caller’s authorization tree - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary

The controller accepts opaque route bytes for `multiply`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral`, authenticates the account caller, and forwards those bytes to the configured router without restricting the external contracts reached by the route. [1](#0-0) [2](#0-1) 

A crafted route can therefore place attacker-controlled code below the victim’s authorized controller call and make that code execute a token `transfer` from the victim to the attacker. [3](#0-2) 

### Finding Description

`StrategySwap` is an opaque `Bytes` value, so the controller does not inspect or constrain the route’s referenced venue, token, or pool addresses. [1](#0-0) 

`swap_collateral` first requires the victim’s authorization, then withdraws the selected collateral and calls `swap_tokens_or_passthrough` with the supplied route. [4](#0-3) 

`swap_debt` and `repay_debt_with_collateral` expose the same route-controlled swap mechanism, while `multiply` passes both `swap` and optional `convert_swap` payloads through the same helper. [5](#0-4) [6](#0-5) [7](#0-6) [8](#0-7) 

`swap_tokens` checks only that the payload is nonempty, authorizes the controller’s exact input transfer to the configured router, invokes `execute_strategy`, and later validates controller-side balance deltas. [9](#0-8) 

Those settlement checks bound only the controller’s input spend and require positive output; they do not prevent payload-selected downstream code from requesting a separate `token.transfer` authorized by the caller. [10](#0-9) [11](#0-10) 

### Impact Explanation

An attacker can steal any spendable token held in the victim’s wallet, including tokens unrelated to the lending markets and tokens that were never routed through the protocol. [12](#0-11) [13](#0-12) 

The route can still return a fair output, so the lending operation can complete with healthy account risk while the unrelated wallet transfer succeeds. [14](#0-13) [13](#0-12) 

### Likelihood Explanation

No privileged protocol role, leaked key, compromised router, or protocol parameter is required once the normal router accepts routes containing attacker-chosen venue addresses. [15](#0-14) 

Exploitation does require the victim to sign the poisoned authorization tree produced by simulation, which makes the issue comparable to a signed-authorization phishing path rather than a fully passive drain. [16](#0-15) 

The impact is nevertheless severe because the extra transfer may target a different token, recipient, and amount than the visible lending action, and the protocol’s own minimum-output and final-risk checks do not bound that transfer. [17](#0-16) 

### Recommendation

Constrain strategy routes to a protocol-approved set of venue, pool, and token contract addresses and reject payload-selected arbitrary contracts before executing them. [18](#0-17) 

Additionally require clients and transaction builders to verify the complete simulated authorization tree and reject any child invocation outside the expected input-token transfer. [19](#0-18) 

### Proof of Concept

The repository’s focused test models the vulnerable authorization flow by encoding a route whose `hop_pool` is an attacker-deployed `RogueHopPool`. [20](#0-19) 

That contract stores the victim, an unrelated wallet token, the attacker recipient, and the amount to steal, then calls `transfer(victim, attacker, amount)` during the route hop. [21](#0-20) 

The victim invokes `swap_collateral` with the crafted route, and simulation records the rogue token transfer as a child of the victim’s controller authorization. [22](#0-21) [23](#0-22) 

Signing the simulated tree executes the unrelated transfer and leaves the victim’s wallet-token balance at zero while the attacker receives the full balance. [16](#0-15)

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);
