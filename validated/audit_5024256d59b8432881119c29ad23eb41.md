### Title
`IntentGatewayV2` order `deadline` is never enforced on fill, letting solvers fill "expired" orders at stale terms — ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
`Order.deadline` is documented and used to gate when an order becomes cancellable, but the actual fill path (`_fillCrossChain`, reachable via `IntentGatewayV2.fillOrder`) contains no check that `block.number <= order.deadline` before executing the fill. This is the same bug class as the Cooler `ClearingHouse.maxDuration` finding: a temporal restriction is enforced only in a secondary code path (there: `roll`; here: `cancelOrder`) while the primary action path (there: subsequent loan extension; here: order fill) is left completely unguarded, defeating the intended limit.

### Finding Description
`_fillCrossChain` in `evm/src/apps/intentsv2/ExtrinsicIntents.sol` sets `_filled[commitment] = msg.sender`, transfers output tokens, and dispatches the `RedeemEscrow` message — with no reference to `order.deadline` anywhere in the function: [1](#0-0) 

By contrast, `order.deadline` is explicitly checked in both cancellation paths, but only to decide who may call `cancelOrder` and when:
- Source-side cancellation requires the caller to prove a destination height *strictly after* the deadline: `if (options.height <= order.deadline) revert NotExpired();` [2](#0-1) 
- Destination-side cancellation restricts who may call it before the deadline, but explicitly allows *anyone* to cancel once `order.deadline < _blockNumber()`: [3](#0-2) 

Nowhere in `IntentGatewayV2.fillOrder` → `_fillCrossChain` (nor is there evidence of it in the same-chain fill path, which the docs confirm has no deadline restriction at all: "there is no cross-chain messaging required and there is no deadline restriction") is a check that the order has not yet passed its `deadline`. [4](#0-3) 

The user-facing documentation frames `deadline` as the point after which an order is expected to be recoverable/unfillable ("Only after a destination proof height is strictly greater than order.deadline", "this ensures the proof is taken from a block after the order has expired"), implying the deadline is meant to bound the window in which a solver can execute the trade: [5](#0-4) 

Because `fillOrder` never reads `order.deadline`, a solver can always fill an order — at any block, arbitrarily long after the "expiry" the placer selected — as long as the destination-side `cancelOrder` (which is the only function that marks `_filled[commitment]` to block fills) has not already been called for that commitment. This exactly mirrors the audited Cooler bug: the intended cap (`maxDuration`/`deadline`) is checked only in the "escape hatch" function (`roll`/`cancelOrder`), while the primary action (`borrow`/`fillOrder`) is left unbounded, letting the counterparty unilaterally override the placer's chosen risk window.

### Impact Explanation
An order placer sets `deadline` expecting the order to become void/unfillable and refundable after that block, bounding their exposure to stale quoted rates (this exact risk — a counterparty holding an unbounded option on a stale price — is called out repeatedly in the codebase's own design docs for the analogous solver-bid `validUntil` fix). Because `fillOrder` does not enforce `order.deadline`, a solver can wait past the deadline (e.g., for the market to move against the placer) and then fill the order at the original, now-unfavorable terms, racing any destination-side cancellation the placer or a relayer might submit. This is a permanent loss of the price-protection the deadline was meant to provide and a direct value-extraction vector against order placers using an unprivileged, single-transaction call (`fillOrder`).

### Likelihood Explanation
High reachability: `fillOrder` is a public, permissionless entry point reachable by any solver in one transaction, requiring no special privilege — the same threat model as the required "unprivileged message dispatcher/intent solver" class. The race only requires the solver to submit the fill before a `cancelOrder` transaction from the destination chain lands; since cancellation is not automatic and requires an additional user/relayer transaction (and, for the source-side route, a full cross-chain GET-proof round trip), there is a practically exploitable window after expiry in which the order remains fillable.

### Recommendation
Add an explicit deadline check in `_fillCrossChain` (and the same-chain fill path, if a deadline is intended to apply there too) that reverts if `block.number > order.deadline`, mirroring the approach `fillOrder`'s v2 codec later added via `FillOptions.validUntil` for solver bid staleness. This closes the gap symmetrically with the `Cooler.roll`-style recommendation of gating the "extension"/action path with the same restriction enforced elsewhere.

### Proof of Concept
1. User places a cross-chain order with `order.deadline = D` via `IntentGatewayV2.placeOrder`.
2. Block height advances past `D` without the user or a relayer calling `cancelOrder` on either chain.
3. A solver calls `IntentGatewayV2.fillOrder(order, options)` on the destination chain at block `> D`. `_fillCrossChain` executes normally — no code path reverts on the stale deadline — transferring output tokens to the beneficiary and dispatching `RedeemEscrow` to release the source-chain escrow to the solver, exactly as if the order were still live.
4. The user's attempt to reclaim the escrow via `cancelOrder` from the destination chain now reverts with `Filled()` since `_filled[commitment]` was already set by the fill in step 3. [1](#0-0) [6](#0-5)

    function _fillCrossChain(Order calldata order, FillOptions calldata options, bytes32 commitment) internal {
        uint256 outputsLen = order.output.assets.length;

        _filled[commitment] = msg.sender;

        uint256 msgValue = msg.value;
        address beneficiary = address(uint160(uint256(order.output.beneficiary)));
        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {
            bytes32 outputToken = order.output.assets[i].token;
            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            if (solverAmount < totalRequired) revert InvalidInput();

            (uint256 protocolShare, uint256 beneficiaryShare) =
                _splitSurplus(solverAmount - totalRequired, order.output.call.length > 0);

            if (token == address(0)) {
                if (msgValue < solverAmount) revert InsufficientNativeToken();
                uint256 beneficiaryTotal = totalRequired + beneficiaryShare;
                _sendValue(beneficiary, beneficiaryTotal);
                msgValue -= (beneficiaryTotal + protocolShare);
            } else {
                IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare);
                if (protocolShare > 0) {
                    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
                }
            }
            if (protocolShare > 0) emit DustCollected(token, protocolShare);
            outputFills[i] = TokenInfo({token: outputToken, amount: totalRequired});
        }

        _execute(order, outputsLen);

        // Native dispatch fee only if the solver sent enough to cover it; else the fee token.
        uint256 nativeFee = options.nativeDispatchFee;
        if (nativeFee > msgValue) nativeFee = 0;
        msgValue -= nativeFee;
        _post(
            order,
            _body(RequestKind.RedeemEscrow, commitment, order.inputs, bytes32(uint256(uint160(msg.sender)))),
            options.relayerFee,
            nativeFee
        );

        // Refund any unspent native tokens to the solver.
        if (msgValue > 0) {
            _sendValue(msg.sender, msgValue);
        }

        emit OrderFilled({commitment: commitment, filler: msg.sender, outputs: outputFills, inputs: order.inputs});
    }

    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
        }

        _filled[commitment] = address(uint160(uint256(order.user)));

        _post(
            order, _body(RequestKind.RefundEscrow, commitment, order.inputs, order.user), options.relayerFee, msg.value
        );
    }

For same-chain orders, the contract verifies the caller is the original order creator and that tokens remain in escrow, then returns them directly. No cross-chain messaging is required and there is no deadline restriction. The order creator can cancel at any time before the order is filled.

    function cancelOrder(Order calldata order, CancelOptions calldata options) public payable nonReentrant {
        bytes32 commitment = keccak256(abi.encode(order));

        if (_filled[commitment] != address(0)) revert Filled();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        // Emitted here, once, rather than from each of the three routes below. Every check those
        // routes make — Unauthorized, NotExpired, UnknownOrder — reverts, and a revert discards
        // logs, so an early emit can never announce a cancellation that did not happen. Emitting
        // before the branch also keeps `EscrowRefunded` the last log on the same-chain route, where
        // the refund is processed in this same transaction. Three emit sites cost bytecode this
        // contract does not have: it sits within ~100 bytes of the EIP-170 limit.
        emit OrderCancelled({commitment: commitment, canceller: msg.sender});

        if (isSameChain) {
            // Checked here rather than inside `_cancelSameChain`, which used to re-read `host()`,
            // re-query the host's state machine id and re-hash `order.source` to reach the same
            // answer this function already has. Same check, one external call fewer.
            if (currentChain != orderSource) revert WrongChain();
            _cancelSameChain(order, commitment);
        } else if (currentChain == orderSource) {
            _cancelFromSource(order, options, commitment);
        } else if (currentChain == orderDest) {
            _cancelFromDest(order, options, commitment);
        } else {
            revert WrongChain();
        }
    }
