### Title
User authorization can be poisoned by arbitrary swap-route contracts to steal unrelated wallet tokens - (File: contracts/controller/src/strategies/swap_collateral.rs)

### Summary
`swap_collateral` combines a broad `caller.require_auth()` invocation with a caller-supplied route that can invoke an arbitrary pool contract. A malicious pool can add an unrelated `token.transfer(victim, attacker, amount)` beneath the caller's recorded authorization tree, so a wallet signature for the intended collateral swap can also authorize theft of unrelated wallet assets. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
The controller authenticates `caller` before executing `swap_collateral`, then loads the victim account and permits the route bytes supplied in `swap` to convert the withdrawn collateral. [4](#0-3) [5](#0-4) 

`require_authorized_caller` performs a top-level `caller.require_auth()` without limiting the authorization to the controller's own token movements or excluding hostile descendants from the recorded invocation tree. [6](#0-5) 

The swap helper invokes the configured router with the caller-provided route while inside that user-authorized call tree. [7](#0-6) 

The router decodes each swap instruction's `pool`, `token_in`, and `token_out` addresses directly from the payload's address registry. [8](#0-7) [9](#0-8) 

The Soroswap adapter invokes caller-selected `pool` code through `get_reserves` and `swap`, allowing malicious pool code to execute beneath the same transaction and request the victim's authorization. [10](#0-9) [11](#0-10) 

The regression test demonstrates the concrete behavior: transaction simulation records a rogue pool's `token.transfer(alice, attacker, WALLET_BALANCE)` as a child of Alice's `swap_collateral` authorization, and enforcement succeeds when the poisoned child is included in the signed tree. [12](#0-11) [3](#0-2) 

The same test also proves the behavior is not limited to signature entries: a transaction using source-account credentials binds the rogue transfer to the supplied invocation tree and moves the wallet token once the malicious child is included. [13](#0-12) 

### Impact Explanation
A malicious route can transfer unrelated tokens held directly by the victim, rather than only the listed collateral being swapped. [14](#0-13) [15](#0-14) 

The victim's supplied collateral is still converted and deposited normally, so the transaction can appear economically successful while draining a separate wallet token to the attacker. [16](#0-15) 

The amount stolen is bounded only by the victim's balance and by what the signed authorization tree contains, and a malicious payload can encode the victim's entire observed wallet balance. [17](#0-16) [18](#0-17) 

### Likelihood Explanation
An attacker cannot submit the theft transaction unilaterally; they must convince the victim to request or sign a poisoned route. [19](#0-18) [20](#0-19) 

That precondition is realistic because route bytes are opaque XDR supplied by an off-chain route builder, while transaction simulation produces the nested authorization tree that the wallet must accurately present and the victim must inspect. [21](#0-20) [22](#0-21) 

No privileged protocol role, leaked key, oracle manipulation, or invalid token behavior is required; the malicious component is an unprivileged pool contract reachable through a valid route payload. [2](#0-1) [10](#0-9) 

### Recommendation
Do not execute arbitrary, caller-selected contracts inside a user-authorized invocation tree. [6](#0-5) [23](#0-22) 

Restrict each venue's `pool` address to an on-chain registry or verified pool-code hash rather than accepting it as arbitrary route input, or split user authorization/intent recording from untrusted route execution so a pool cannot append victim-authorizing calls beneath the signed invocation. [9](#0-8) [24](#0-23) 

The client-side mitigation alone is insufficient because the malicious transfer is mechanically embedded in the simulation-produced authorization tree. [22](#0-21) 

### Proof of Concept
1. Victim creates a Normal account and supplies collateral such as USDC. [25](#0-24) 

2. The attacker deploys a malicious pool contract configured with `(victim, unrelated_wallet_token, attacker, amount)` and implements the pool functions used by the selected venue adapter. [26](#0-25) 

3. The attacker or malicious route builder constructs a `swap_collateral` call whose route names the malicious contract as the hop pool while still promising a valid output token amount. [17](#0-16) [27](#0-26) 

4. During simulation, the malicious pool calls `unrelated_wallet_token.transfer(victim, attacker, amount)`, and the host records that token transfer as a child under the victim's `swap_collateral` authorization. [22](#0-21) 

5. If the wallet submits the poisoned signed tree, the collateral swap succeeds, the unrelated token balance moves to the attacker, and the victim receives the expected swapped collateral. [3](#0-2)
