### Title
Webhook `shop` and `topic` Identity Fields Are Not Bound by the HMAC Signature, Enabling Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates the HMAC signature only over the raw request body, while the `shop`, `topic`, and `webhook_id` fields that the registry uses to attribute and dispatch the event are read from unauthenticated HTTP headers that are never included in the signed content.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` computes/compares the HMAC strictly against that signable string using the app's shared `api_secret_key` [2](#0-1) . However, `Request#shop`, `Request#topic`, and `Request#webhook_id` are all parsed directly from HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`) that are completely outside the HMAC's coverage [3](#0-2) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e., body integrity) before dispatching to the topic handler and constructing `WebhookMetadata` with `request.shop` and `request.topic` taken straight from those unauthenticated headers [4](#0-3) . The equality the code implicitly assumes is: `shop header == shop that legitimately produced this exact signed body`. That equality is never checked — the HMAC only proves "this body was signed with the app's secret at some point," not "this body was signed for this shop/topic."

Because the app's `api_secret_key` (client secret) is shared across every merchant install of the app, any merchant who has legitimately installed the app can capture one of their own real, validly-signed webhook deliveries (body + HMAC), and then replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `shopify-shop-domain` (and/or `shopify-topic`) header with a victim shop's domain or a different topic. `Utils::HmacValidator.validate` will still return `true` since it only re-derives the HMAC from the (unchanged) body, and `Registry.process` will happily hand the handler a `WebhookMetadata` claiming the event belongs to the victim shop/topic [5](#0-4) .

### Impact Explanation
This breaks the tenant-identity binding relied on by any app that trusts `WebhookMetadata#shop` to select which merchant's data/session to act on (e.g., mandatory topics like `customers/redact`, `shop/redact`, `app/uninstalled`, or business-logic topics like `orders/paid`). An attacker who is merely one of the app's many installed merchants can forge webhook deliveries that the host app will process as if they came from a different, victim shop — i.e., cross-tenant access/injection of events attributed to a shop the attacker does not control, using only their own legitimately-received webhook traffic and no leaked secret.

### Likelihood Explanation
Likelihood is bounded by the fact that the attacker must first be (or become) a genuine merchant installer of the target app in order to receive at least one validly HMAC-signed webhook body to replay with a substituted shop header — this requires no credential theft, TLS interception, or privileged account, only normal app installation, which satisfies the "unprivileged internet user" bar in this gem's threat model.

### Recommendation
Bind the shop (and ideally topic) into the signed content the gem verifies, or explicitly cross-check `request.shop` against an independently-authenticated value (e.g., the shop associated with the session/store record the webhook is meant to update) before trusting `WebhookMetadata#shop` in `Registry.process`. At minimum, document that `request.shop`/`request.topic` are unauthenticated and must be independently verified by the host app against known installed shops before being used for any tenant-scoped action.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, and triggers a real webhook event (e.g. `orders/create`) so Shopify sends a POST with body `B` and header `shopify-hmac-sha256: H` computed over `B` using the app's shared `api_secret_key`.
2. Attacker captures `(B, H)` from their own inbox/proxy.
3. Attacker crafts a new POST to the app's webhook endpoint with the *same* body `B` and *same* `shopify-hmac-sha256: H`, but sets `shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `shopify-topic`).
4. `Utils::HmacValidator.validate(request)` recomputes the HMAC over `B` only and returns `true` [6](#0-5) .
5. `Registry.process` dispatches the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` where `shop` is `"victim-shop.myshopify.com"` [7](#0-6) , causing the host app to act on the victim tenant using attacker-controlled, replayed data.
