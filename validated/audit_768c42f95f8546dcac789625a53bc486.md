### Title
Webhook shop-domain identity is not bound to the HMAC-verified bytes, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signature only over the raw request body, while the shop identity (`shop-domain` header) that gets handed to app handlers is taken from an HTTP header that is completely outside the HMAC's coverage. Anyone who possesses one validly-signed webhook body/HMAC pair (e.g. delivered to their own store's endpoint) can replay it with an attacker-chosen `x-shopify-shop-domain` header and still pass `HmacValidator.validate`, causing the gem to hand the host application a `WebhookMetadata` object whose `shop` field does not match the tenant that actually produced the signed bytes.

### Finding Description
`to_signable_string` for a webhook request returns only the raw body: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all read straight from HTTP headers, none of which participate in the signable string: [2](#0-1) 

`HmacValidator.validate` computes `HMAC(secret, request.to_signable_string)` and compares it to the `hmac-sha256` header — i.e. it verifies only the body bytes: [3](#0-2) 

`Webhooks::Registry.process` validates the HMAC and then immediately trusts `request.shop` (the unauthenticated header) as the tenant identity forwarded to the host application's handler: [4](#0-3) 

The identity binding that should hold is:
```
shop_identity_used_by_handler == shop_that_produced_the_HMAC-signed_bytes
```
In reality the gem only proves `body == HMAC_valid(body)`; it never proves `shop-domain header == shop that Shopify actually generated this signature for`. Because the shop header is disjoint from the signed payload, an attacker who can obtain any one valid `(body, hmac)` pair — trivially available to them for their own store, since Shopify delivers real signed webhooks to every merchant's registered endpoint — can substitute an arbitrary `x-shopify-shop-domain` value and the request still passes `Utils::HmacValidator.validate`. The gem then reports that spoofed shop value as authoritative in `WebhookMetadata#shop`, which most host applications use directly as the tenant key to look up sessions/access tokens or to write/attribute data.

### Impact Explanation
This breaks the tenant boundary between shops: an unprivileged internet user who controls or observes a legitimately-signed webhook body for shop A can cause the app's webhook handler to process that body as if it belonged to shop B, purely by rewriting an unauthenticated header. Because host applications (as documented and expected by this gem, see `WebhookMetadata` usage in `Webhooks::Registry.process`) route storage/business logic keyed off `data.shop`, this enables cross-tenant data injection/confusion — data intended for/verified against one merchant can be attributed to a different merchant's session/store. This matches the "Critical – cross-tenant access" impact category, since the shop identity that the gem asserts as authenticated is not actually bound to the HMAC-verified bytes.

### Likelihood Explanation
Likelihood is high for any attacker who runs (or has run) their own Shopify store using the same app, or who can otherwise capture one valid signed webhook delivery — no access token, `api_secret_key`, or privileged account is required, since obtaining a legitimate webhook only requires triggering an event on a store one owns and controls the receiving endpoint for. The replay only requires changing one plain HTTP header (`x-shopify-shop-domain`); the HMAC check in `HmacValidator.validate` is unaffected because it never inspects headers.

### Recommendation
Include the shop-domain (and ideally topic/webhook-id) in the signed material that is verified, or independently authenticate the shop header against a source that is cryptographically bound to the request (e.g., require the signature to cover a canonical string containing shop + body, matching Shopify's actual webhook HMAC contract if it does bind shop-domain). At minimum, document loudly that `WebhookMetadata#shop` is unauthenticated and must be cross-checked by the host application against a shop the app already trusts (e.g., an existing session) before being used as a tenant key, and consider raising `InvalidWebhookError` if the shop header does not correspond to a shop with an active, previously-established session/registration in cases where the gem has that context.

### Proof of Concept
1. Attacker owns/operates `attacker-shop.myshopify.com` with the same app installed, and the app registers an HTTP webhook (e.g. `orders/create`).
2. Attacker triggers the event; Shopify delivers a real webhook request to the attacker's endpoint with body `B`, and header `x-shopify-hmac-sha256: HMAC(secret, B)`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker forges a new HTTP request to the same app's webhook route, keeping the exact same raw body `B` and `x-shopify-hmac-sha256` header, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. The app calls `ShopifyAPI::Webhooks::Registry.process(Request.new(raw_body: B, headers: forged_headers))`.
5. `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` — unaffected by the header change — and passes.
6. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed_body_of_B, ...)`, even though `victim-shop.myshopify.com` never produced this signature. Any host application that uses `data.shop` to select a tenant/session will act on `B`'s content under the wrong merchant's identity.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
