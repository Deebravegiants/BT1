This confirms the vulnerability: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `Utils::HmacValidator.validate` only proves the HTTP body bytes match the secret [2](#0-1) . But `shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never part of the HMAC-signed material [3](#0-2) . `Registry.process` validates the HMAC and then forwards `request.shop` unchanged straight to the app's `handler.handle` as the authoritative shop identity [4](#0-3) , and the docs explicitly tell integrators to trust `data.shop` as "The shop domain of the webhook" and use it to route/attribute work (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) [5](#0-4) .

### Title
Webhook `shop` identity is taken from an HMAC-unauthenticated header, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the merchant identity (`shop`) from the `shopify-shop-domain` HTTP header, while the HMAC signature computed by `Utils::HmacValidator` only covers the raw request body (`to_signable_string` returns `@raw_body`). Because the header is outside the signed payload, its value can be freely set by whoever sends the HTTP request to the app's webhook endpoint, while the HMAC still validates successfully as long as the body bytes match a secret the attacker can obtain (e.g. by replaying/reusing a real webhook body from their own shop, since the same `client_secret`/`api_secret_key` is shared across all shops using the app).

### Finding Description
The identity binding that should hold is: `hmac == HMAC(secret, bytes_that_include_shop)`. In this gem, the actual binding is `hmac == HMAC(secret, raw_body)` while `shop` is read independently from a header [6](#0-5) . `HmacValidator.validate_signature` recomputes the digest over `to_signable_string` and compares it with `OpenSSL.secure_compare` [2](#0-1) , so it proves only that the body bytes are authentic for *some* shop under this app's shared secret — not that the accompanying `shop` header is authentic. `Registry.process` performs the HMAC check and then immediately constructs `WebhookMetadata` using `request.shop` taken from the unauthenticated header, handing it to the application handler as ground truth [4](#0-3) .

Because Shopify's webhook HMAC secret is the app's single `client_secret`/`api_secret_key` shared across every installed shop, any merchant that has installed the app can capture a legitimate webhook delivery (body + valid HMAC) sent to their own endpoint, then replay the exact same body/HMAC pair to the target app's webhook URL while substituting the `shopify-shop-domain` header with an arbitrary victim shop domain. The HMAC check still passes because it never inspected the header, and the handler will act as if the payload legitimately originated from the victim shop.

### Impact Explanation
This breaks the shop-authenticated-by-HMAC = shop-acted-upon binding, letting one tenant impersonate another tenant to the app's webhook processing pipeline — a cross-tenant identity confusion. Depending on how the host application uses `data.shop` (attributing orders/customers, looking up sessions, triggering shop-scoped side effects, invoking the Admin API with the session tied to `data.shop`), this can lead to cross-tenant data corruption or unauthorized actions performed under another merchant's identity, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires the attacker to be an unprivileged but genuine installer of the app (to capture one authentic body+HMAC pair from their own shop) and network access to the app's public webhook endpoint — no access token, `client_secret`, or privileged account is required. Because the shared secret's HMAC never binds to the shop header, replay-with-substituted-header is straightforward and repeatable for any topic/body the attacker can trigger on their own shop.

### Recommendation
Include the shop domain (and other trust-critical headers such as topic/api-version) in the signed material, or independently cross-check `shopify-shop-domain` against a value embedded in the verified body/JWT, or bind the header value into the HMAC computation before calling `Utils::HmacValidator.validate`. At minimum, `ShopifyAPI::Webhooks::Request#to_signable_string` should incorporate the shop header so `HmacValidator` proves the shop identity, not just the body bytes.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. body `{"id":1}` with header `x-shopify-hmac-sha256: <valid-hmac-for-body>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker POSTs the identical body and HMAC header to the app's webhook endpoint but replaces the shop header: `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers, `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `@raw_body` only [1](#0-0)  — validation succeeds since the body is unmodified.
4. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` with `shop == "victim-shop.myshopify.com"` [7](#0-6) , so the app processes attacker-controlled data believing it originated from the victim shop.
