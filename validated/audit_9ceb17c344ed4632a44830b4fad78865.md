### Title
Webhook shop-domain identity is not covered by the HMAC, allowing cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by verifying the HMAC over the raw request body, but the `shop` (and `topic`/`api_version`/`webhook_id`) values that are handed to the app's handler as the tenant identifier come from HTTP headers that are never included in the signed material. This breaks the binding "shop verified by HMAC == shop delivered to handler," letting an attacker who owns/controls one shop replay their own validly-signed webhook body while relabeling it as belonging to a victim shop.

### Finding Description
`Webhooks::Request` implements `VerifiableQuery` with: [1](#0-0) [2](#0-1) 

`to_signable_string` returns only `@raw_body`; `shop`, `topic`, `api_version`, and `webhook_id` are read from headers and are not part of the signable string: [3](#0-2) 

`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (the body only) and compares it to the `hmac` header: [4](#0-3) 

`Registry.process` uses this same HMAC check to authenticate the whole request, then trusts `request.shop` (an unauthenticated header) to build the tenant-identifying `WebhookMetadata` handed to the app's handler: [5](#0-4) 

The equality that should hold is:
`shop bound by HMAC == shop delivered to WebhookMetadata.shop`

In reality:
`shop delivered to WebhookMetadata.shop` comes from `x-shopify-shop-domain` / `shopify-shop-domain`, a header that is completely outside the HMAC-covered bytes (`@raw_body` only). Before the attacker's request: a legitimate webhook for shop A has a body `B`, a valid HMAC `H = HMAC(secret, B)`, and header `shop-domain: A`. After the attacker's request: the attacker resends the same `(B, H)` pair (which they legitimately received for their own shop A, since they can install the app on their own store and receive real signed webhooks) but sets `shop-domain: victim-shop.myshopify.com`. `HmacValidator.validate` still returns `true` because it only checks `B` against `H`; `Registry.process` proceeds to call the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, `topic`, and other header-derived fields, none of which were authenticated.

### Impact Explanation
This is a cross-tenant identity-binding bypass: the app is given attacker-controlled tenant identity (`shop`) alongside a body that only proves it came from *some* Shopify-initiated webhook, not that it belongs to the claimed shop. Any app that uses `WebhookMetadata#shop` (as demonstrated by the library's own tests and documented usage pattern) to route/attribute webhook data to a specific merchant's records is exposed to cross-tenant data injection — an attacker-controlled shop can inject webhook payloads (with attacker-chosen JSON body content, since they generated it) attributed to a victim shop's tenant. This matches the Critical class "cross-tenant access" since it lets one merchant impersonate another merchant's identity within the app's data model using only the ability to install the app on their own store (no credential of the victim, no leaked secret required).

### Likelihood Explanation
Likelihood is high for any consumer of this gem that trusts `WebhookMetadata#topic`/`#shop`/`#api_version`/`#webhook_id` as authenticated fields — which is the natural reading of the API surface, since the whole point of `Registry.process` raising `Errors::InvalidWebhookError` on bad HMAC is to assure the caller the request is trustworthy. An attacker needs only: (1) to install the target app on a shop they control to receive a legitimately-signed webhook (trivial for any public/free app), and (2) the ability to POST arbitrary headers to the app's webhook endpoint (trivial, unauthenticated HTTP). No access token, `client_secret`, or victim credentials are required.

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, `api_version`, `webhook_id`) in the HMAC-signed material, or otherwise cryptographically bind them to the body before trusting them, e.g., by having `to_signable_string` return a canonical concatenation of the raw body and the relevant headers, and updating `HmacValidator`/`Registry.process` to validate against that combined string instead of the body alone. At minimum, document prominently that `WebhookMetadata#shop`/`#topic` are NOT authenticated by `Registry.process` and must not be used to resolve tenant/session state without independent verification (e.g., cross-checking against a shop already known to be installed, or against session data established via OAuth).

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`), receiving:
   - Body `B` (attacker fully controls its JSON content since it's data from their own store, e.g. order details)
   - Header `x-shopify-hmac-sha256: H` where `H = Base64(HMAC-SHA256(secret, B))`
   - Header `x-shopify-shop-domain: attacker-shop.myshopify.com`
2. Attacker resends the exact same body `B` and `x-shopify-hmac-sha256: H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `@raw_body` (`B`), matching `H`: [5](#0-4) 
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` and, if the host app uses `shop` to attribute/store the payload, victim-shop's tenant data is polluted with attacker-controlled content — a cross-tenant write achieved without any victim credential.
