### Title
Missing allowlist/rate-limit authorization in gateway's legacy WebAPI trigger path allows unauthorized job triggering - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
This is the same bug class as the `OptimismPortal`/`L2ToL1MessagePasser` `receive()` issue: one entry point into a piece of functionality enforces the necessary access-control check, while a functionally-equivalent alternate entry point does not, so the protection is bypassable through the unprotected path. In chainlink's gateway, the "internet-facing" WebAPI capability handler exposes two paths that ultimately forward a user's request to all DON nodes: `HandleLegacyUserMessage` (legacy `DonID`-addressed messages) and the JSON-RPC/service-name path. The legacy path explicitly skips the allowlist/rate-limiting checks that are supposed to gate which callers may trigger a workflow.

### Finding Description
`HandleLegacyUserMessage` in `core/services/gateway/handlers/capabilities/handler.go` validates payload decoding, a non-zero timestamp, and message staleness, but contains an explicit TODO acknowledging that authorization is missing: [1](#0-0) 
Right after that TODO, the only remaining check is that the method equals `MethodWebAPITrigger`; there is no allowlist check, no per-user/per-workflow rate limiting, and no ownership/authorization check on the caller before the message is broadcast to every DON member: [2](#0-1) 

This is invoked from the internet-facing gateway's `ProcessRequest`, which routes any incoming HTTP request carrying a legacy `DonID` in the message envelope directly to this handler via `HandleLegacyUserMessage`: [3](#0-2) 

By contrast, the newer v2 HTTP capability handler (`core/services/gateway/handlers/capabilities/v2/http_handler.go`) is built with a dedicated `HTTPTriggerHandler`, a per-user `userRateLimiter` (`cresettings.Default.PerWorkflow.HTTPTrigger.RateLimit`), global/per-node rate limiters, and an `orgresolver.OrgResolver`/`WorkflowMetadataHandler` used "for authorization for HTTP trigger requests": [4](#0-3) 

The legacy handler's `nodeRateLimiter` only throttles messages coming *from* DON nodes (`handleWebAPIOutgoingMessage`), not the initial inbound user trigger: [5](#0-4) 

So the legacy code path (still wired into the gateway's request routing and still present/compiled) lacks the equivalent access-control gate that the newer path has, mirroring the report's pattern where one entry function (`OptimismPortal.depositTransaction` via the explicit call) had a modifier while the equivalent `receive()` fallback path did not.

### Impact Explanation
If the legacy `DonID`-addressed message path is still reachable in production configuration (i.e., a DON is still configured with `serviceNameToDonID` mapping and legacy handlers registered in `g.handlers`), any caller able to reach the gateway's HTTP endpoint can submit a `web_api_trigger` message that gets broadcast to every member of the target DON without going through the allowlist/rate-limit/authorization logic that the v2 path enforces. This could let an unprivileged/unallowlisted actor trigger workflow executions on a DON they are not authorized to invoke, which is an unauthorized-job-run analog to the fund-loss impact in the original report.

### Likelihood Explanation
Likelihood depends on whether any DON is still configured to use the legacy `DonID` addressing / legacy handler registration (`g.handlers[donID]`) rather than exclusively the newer `serviceToMultiHandler`/v2 path. The code explicitly keeps this fallback alive in `gateway.go`, and the handler code still marks the missing check with an active TODO rather than a removed/dead code comment, indicating the gap is a known, currently-present limitation rather than disproven dead code. Full confirmation of exploitability requires checking the current deployment/config (whether `serviceNameToDonID`/legacy `handlers` map is populated for any active DON), which could not be verified from the indexed code alone.

### Recommendation
Add the same allowlist and rate-limiting checks used in the v2 `HTTPTriggerHandler` (or equivalent authorization based on `OrgResolver`/workflow ownership) to `HandleLegacyUserMessage` before forwarding to `don.SendToNode`, or remove/disable the legacy `DonID` routing path entirely if it is meant to be deprecated, so both entry points enforce equivalent authorization.

### Proof of Concept
1. Configure a DON reachable via the legacy `DonID`-based routing in `gateway.go` (`serviceNameToDonID` present, handler in `g.handlers`).
2. Send an HTTP POST to the gateway with a JSON-RPC request containing a legacy `DonID` and `Method: "web_api_trigger"` payload with a valid (non-zero, non-stale) `Timestamp`, without being on any allowlist.
3. `gateway.ProcessRequest` routes this to `HandleLegacyUserMessage`, which — per the code path shown above — only checks payload decoding, timestamp validity, and method name, then forwards the request to every DON member, without ever calling an allowlist or rate-limit check. [6](#0-5)

		h.lggr.Errorw(ErrDecodingPayload, "err", err)
		return callback.SendResponse(handlers.UserCallbackPayload{
			RawResponse: codec.EncodeNewErrorResponse(
				msg.Body.MessageID,
				api.ToJSONRPCErrorCode(api.UserMessageParseError),
				ErrDecodingPayload+" "+err.Error(),
				nil,
			),
			ErrorCode: api.UserMessageParseError,
		})
	}

	if payload.Timestamp == 0 {
		h.lggr.Errorw(ErrDecodingPayload)
		return callback.SendResponse(handlers.UserCallbackPayload{
			RawResponse: codec.EncodeNewErrorResponse(
				msg.Body.MessageID,
				api.ToJSONRPCErrorCode(api.UserMessageParseError),
				ErrDecodingPayload,
				nil,
			),
			ErrorCode: api.UserMessageParseError,
		})
	}

	if uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp) { //nolint:gosec // G115: comparing unix timestamps, both fit within uint
		h.lggr.Errorw("stale message")
		return callback.SendResponse(handlers.UserCallbackPayload{
			RawResponse: codec.EncodeNewErrorResponse(
				msg.Body.MessageID,
				api.ToJSONRPCErrorCode(api.HandlerError),
