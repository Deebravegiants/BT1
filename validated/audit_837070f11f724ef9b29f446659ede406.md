This is a synthesized bug-class analog based on the reNFT "stale Guard policy" report, applied to the orb-core signup flow.

### Title
Signup flow trusts a one-time user-authorization result for the entire biometric-enrollment session without re-validating it against the backend before submission - (File: `src/plans/mod.rs`)

### Summary
In the reNFT report, a rental safe keeps trusting an outdated `Guard.sol` reference because `checkTransaction()` never re-confirms with the authoritative source (`Kernel.sol`) that the guard it is pointing to is still active; the safe simply keeps calling view functions on stale state. The analogous pattern in orb-core is that a user's QR-code/session authorization is validated exactly once via `backend::user_status::request` in `verify_user_qr_code`, and the resulting `UserData` is then cached and carried, unmodified, through the entire remainder of the signup pipeline (biometric capture, fraud checks, PCP building, and final enrollment submission) without ever re-checking with the backend that the authorization is still valid at the moment the sensitive action (biometric data upload / enrollment) is performed.

### Finding Description
`verify_user_qr_code` calls `backend::user_status::request(...)` a single time and returns a `backend::user_status::UserData` value. [1](#0-0) 

That `UserData` is stored inside the `QrCodes::Both` / `ResolvedQrCodes` structures and threaded through `do_signup` unchanged. [2](#0-1) [3](#0-2) 

`do_signup` then proceeds through biometric capture, the biometric pipeline, fraud detection, PCP-package construction, and enrollment, all using the originally cached `qr_codes.user_data` (e.g. `user_centric_signup`, `orb_relay_app_id`, encryption keys) without a second call to `backend::user_status::request` or any other authority check to confirm the user session/authorization is still valid at submission time. [4](#0-3) 

The final network calls that actually commit the enrollment (`signup_post::request` / `enroll_user::Plan::run`) only send `operator_qr_code`, `user_qr_code`, `capture`, and `pipeline` data — they do not re-invoke `user_status` to reconfirm authorization, and the local orb-core code path leading up to it never does either. [5](#0-4) 

This mirrors the Guard.sol root cause: an authorization decision is fetched once from an authoritative source and then trusted indefinitely (for the whole remaining flow) via locally cached state, with no re-validation gate before the sensitive/state-changing action.

### Impact Explanation
If backend-side authorization state for a given user/session changes between the initial QR validation and the final enrollment submission (e.g., the session is invalidated, the QR is revoked, or per the report's fairness concern, different sessions end up receiving different levels of restriction depending on when they were validated), the orb-core client has no local mechanism to detect and abort on this change — it will proceed to capture and upload biometric data and attempt enrollment using the stale authorization snapshot. This does not appear to lead to direct loss of funds/assets (there are none in this domain), but — consistent with the Medium severity assigned in the original report — it could allow inconsistent enforcement of signup authorization state and misattributed submission of biometric data for a session the backend no longer considers valid, which affects fraud/authorization enforcement integrity of the protocol rather than causing an in-app monetary loss.

### Likelihood Explanation
Likelihood is low-to-moderate. Exploiting this requires the backend to actually revoke/alter user authorization mid-flow (a race condition inherent to any check-once-use-later design), which is a normal operational occurrence (QR expiration, backend-side revocation) rather than something an unprivileged attacker directly controls from the orb side. There's no local attacker action that forces re-use of stale state beyond the natural timing of the existing flow; the window is bounded by the length of a single signup attempt (QR scan → capture → pipeline → enroll), not by an indefinite/attacker-chosen duration as in the original Guard.sol report.

### Recommendation
Before performing the enrollment-committing action (immediately before `enroll_user`/`signup_post`, and ideally also before uploading biometric data via `build_pcp`), re-validate the cached `UserData`/session against the backend (or query for an authorization-still-valid signal) rather than relying solely on the snapshot captured during the initial QR scan. This closes the gap between "checked once" and "trusted for the whole flow," matching the mitigation recommended in the original report (query the authoritative source right before executing the sensitive action instead of relying on stale cached state).

### Proof of Concept
Conceptual trace (not independently exploited, since no live backend/hardware access is available in this ask-only investigation):
1. Orb scans the user QR-code and calls `verify_user_qr_code` → `backend::user_status::request`, backend returns `valid: true` and `UserData`. [6](#0-5) 
2. Between this point and the final enrollment call, the backend revokes/invalidates that user's session (e.g., operator-side action, fraud flag, QR expiry on the backend).
3. orb-core continues through `biometric_capture` → `biometric_pipeline` → `detect_fraud` → `build_pcp` → `enroll_user`/`signup_post`, all keyed off the same, now-stale `qr_codes.user_data` captured in step 1, with no intervening call back to `backend::user_status::request` to reconfirm validity. [4](#0-3) 
4. The signup request is submitted to `/api/v2/signups/{signup_id}` carrying the original (now stale) authorization assumption. [7](#0-6) 

Note: I could not verify server-side behavior (whether the backend independently re-checks authorization on the `/signups` endpoint), since that logic is outside this repository's index. This limits certainty about actual exploitability — the backend may well perform its own authoritative re-check at submission time, which would neutralize this client-side gap.
