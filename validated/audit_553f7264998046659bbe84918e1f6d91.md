### Title
Permanent inability to revoke a connected/trusted dApp origin when address resolution for one of its stored asset names fails - (File: `features/connected-origins/module/connections.js`)

### Summary
This is the closest analog in the hydra codebase to the Karak `NativeVault._decreaseBalance()` bug: a state-reducing/privilege-revoking operation (`untrust`) is gated behind an unrelated computation that can throw, and because that computation is on the *only* code path shared by every mutator, a single bad precondition permanently blocks the revocation of trust for a connected origin (dApp/website), exactly mirroring the "decrease can never commit, so the entity keeps its privileges forever" pattern from the report.

### Finding Description
`ConnectedOrigins#setData` [1](#0-0)  is the single choke point used by every mutating method on the class (`add`, `untrust`, `setFavorite`, `setAutoApprove`, `connect`, `disconnect`, `updateConnection`, `clearConnections` — all via `#setAttributes` or directly). Before persisting the new origins array, `#setData` recomputes address bindings for **every asset referenced by every stored connected origin**, not just the one being mutated: [2](#0-1) 

`#getWalletAccountAddresses` calls `this.#addressProvider.getDefaultAddress({ assetName, walletAccount })` for any asset name lacking a cached address [3](#0-2) . If any `assetName` stored on any origin's `connectedAssetName`/`assetNames` (both attacker/dApp-controlled inputs via the public `add()` API, see `features/connected-origins/api/index.js`) is or later becomes unresolvable (asset removed/disabled, unsupported name, etc.), `getDefaultAddress` throws, causing `#getAccounts` — and therefore `#setData` — to reject **before `connectedOriginsAtom.set(data)` is ever called**.

Because `untrust()` and `disconnect()` also funnel through this same `#setData` [4](#0-3) [5](#0-4) , once any stored origin references a "poisoned" asset name, **every subsequent call to any mutator — including the user's own `untrust()`** — throws and cannot persist. This is structurally identical to the Karak bug: a security-reducing operation (`_decreaseBalance` / `untrust`) is coupled to a computation (`previewWithdraw`/burn amount check / `getDefaultAddress` resolution) whose failure mode causes the entire transaction/state update to revert, leaving the subject (staker / dApp origin) with privileges it should have lost, permanently, since nothing else in the code repairs the poisoned precondition.

### Impact Explanation
A connected origin (dApp/website) that has obtained `trusted`/`autoApprove` status and/or `activeConnections` cannot be revoked by the user once one of its associated asset names becomes unresolvable by `addressProvider.getDefaultAddress`. This is a persistent cross-origin trust/privilege bleed: the origin keeps whatever wallet access it was granted (trusted status, auto-approval, active connection) indefinitely, and the user has no way through the exposed `connectedOrigins` API (`untrust`, `disconnect`, `clearConnections`) to remove it, since all of those calls hit the same failing code path.

### Likelihood Explanation
This requires an origin's `connectedAssetName`/`assetNames` (attacker-influenceable via the public `add()` call, which accepts arbitrary `assetNames` strings from the dApp) to end up referencing an asset that `addressProvider.getDefaultAddress` cannot resolve — e.g., an asset later disabled/removed, or one intentionally supplied that isn't a genuine registered asset. This is a "with stated assumptions, but external requirements" scenario similar to the judged Karak finding (Medium severity): plausible but not trivially guaranteed to reproduce without confirming `getDefaultAddress`'s exact throwing behavior for unknown/disabled assets, which I was not able to fully verify from the indexed code.

### Recommendation
- Do not gate trust-revoking mutations (`untrust`, `disconnect`, `clearConnections`) behind the full `#getAccounts` recomputation; persist the security-relevant `connectedOriginsAtom` update independently of `connectedAccountsAtom` refresh, or make address resolution best-effort (catch/skip unresolved asset names rather than throwing) so one bad asset name cannot block unrelated critical operations.
- Validate `assetNames`/`connectedAssetName` passed into `add()`/`setFavorite()` against the actual known asset registry before persisting them.
- Ensure `untrust()` always succeeds in removing the origin from `connectedOriginsAtom` even if refreshing `connectedAccountsAtom` fails.

### Proof of Concept
1. A dApp calls `exodus.connectedOrigins.add({ origin: 'site.com', connectedAssetName: 'someAsset', assetNames: ['someAsset'], trusted: true })` while `someAsset` is a valid, resolvable asset — the origin is stored as trusted.
2. At a later time, `someAsset` becomes unsupported/disabled/removed (asset toggled off via feature flags, or removed from `available-assets`), such that `addressProvider.getDefaultAddress({ assetName: 'someAsset', walletAccount })` now throws for that asset.
3. The user attempts `exodus.connectedOrigins.untrust({ origin: 'site.com' })`. This calls `#setData` → `#getAccounts(['someAsset', ...])` → `#getWalletAccountAddresses` → `getDefaultAddress` throws, so `#setData` rejects before `connectedOriginsAtom.set(...)` runs.
4. `site.com` remains permanently `trusted`, and every future `untrust()`/`disconnect()`/`clearConnections()` call throws identically, leaving the user unable to revoke the origin's wallet access.

    const walletAccounts = Object.values(await this.#enabledWalletAccountsAtom.get())

    const entries = await Promise.all(
      walletAccounts.map(async (walletAccount) => [
        walletAccount.toString(),
        {
          addresses: await this.#getWalletAccountAddresses(walletAccount, assetNames),
        },
      ])
    )

    return Object.fromEntries(entries)
  }

  #getWalletAccountAddresses = async (walletAccount, assetNames) => {
    const connectedAccounts = await this.#connectedAccountsAtom.get()
    const entries = await Promise.all(
      assetNames.map(async (assetName) => {
        const existingAddress = connectedAccounts[walletAccount]?.addresses[assetName]
        if (existingAddress) {
          return [assetName, existingAddress]
        }

        const address = await this.#addressProvider.getDefaultAddress({ assetName, walletAccount })
        return [assetName, address.toString()]
      })
    )

    return Object.fromEntries(entries)
  }

  untrust = async ({ origin }) => {
    const isTrusted = await this.isTrusted({ origin })

    if (!isTrusted) return

    const data = await this.#getData()
    const newData = data.filter((connection) => connection.origin !== origin)

    await this.#setData(newData)
  }

    const newConnections = activeConnections.filter((connection) => connection.id !== id)
