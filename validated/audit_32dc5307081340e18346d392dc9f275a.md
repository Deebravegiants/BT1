This confirms the asymmetry: for `AuthQuery` (OAuth callback), the `shop` value is explicitly part of the HMAC-signed `to_signable_string`, but for `Webhooks::Request`, the `shop` header (`x-shopify-shop-domain`) is entirely excluded from `to_signable_string`, which is only the raw body.

### Title
Webhook shop-domain header is not covered by HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` authenticates incoming webhooks by validating an HMAC over the raw request body only. The `shop` (tenant identifier), `topic`, `api_version`, and `webhook_id` values are all taken from unauthenticated HTTP headers and are never included in the signed payload, so the binding "HMAC-verified bytes == bytes the application trusts as the webhook's tenant/topic" does not hold.

### Finding Description
`Webhooks::Registry.process` accepts a `Request` and validates it via `Utils::HmacValidator.validate(request)`, which in turn calls `request.to_signable_string` and compares its HMAC-SHA256 (keyed with `Context.api_secret_key`) against the `hmac` header [1](#0-0) . `Request#to_signable_string` returns only `@raw_body` [2](#0-1) , while `Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are read directly from HTTP headers that are never part of the signed string [3](#0-2) . `HmacValidator.validate_signature` only ever recomputes the signature from `to_signable_string`, so it can never detect tampering with these header fields [4](#0-3) .

This is by design a per-app secret (`Context.api_secret_key`), not a per-shop secret — the same `api_secret_key` signs webhooks for every shop that has the app installed [5](#0-4) . Once the HMAC passes, `Registry.process` forwards `request.shop` verbatim into `WebhookMetadata`, which is delivered to the app's handler as the authoritative tenant identity for that webhook payload [1](#0-0) .

This breaks the expected binding: `hmac-verified bytes == bytes the app trusts to select the shop`. Concretely, `hmac` is computed over `raw_body` only, while `shop` (and `topic`/`api_version`/`webhook_id`) are trusted headers outside that signed scope. Compare this to `Auth::Oauth::AuthQuery`, where `shop` is explicitly included inside `to_signable_string` and therefore is bound by the HMAC [6](#0-5) .

### Impact Explanation
An attacker who has installed the app on their own shop (a normal, unprivileged flow) will legitimately receive genuine webhook deliveries with valid `hmac`, `body`, `topic`, and `webhook_id` values, all signed with the app's single shared `api_secret_key`. Because `shop` is not part of the signed bytes, the attacker can replay that exact `(body, hmac)` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with any victim shop domain. `HmacValidator.validate` will still return true (it only checks `raw_body` against `hmac`), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload originated from the victim shop [7](#0-6) . Any host application that uses `WebhookMetadata#shop` to select which merchant's data/session/store to mutate (e.g., updating settings, deleting data, crediting/debiting a subscription, processing `orders/create` payloads) can be made to act on an attacker-controlled payload while attributing it to a shop the attacker does not control — a cross-tenant integrity violation.

### Likelihood Explanation
The only prerequisite is installing the app once on an attacker-controlled or trial shop, which is normal, unprivileged usage of any public Shopify app — no leaked secrets, no privileged account, and no interception of TLS is required. Triggering a real webhook (e.g., `orders/create`) on their own shop gives the attacker a valid `(body, hmac)` pair whose `hmac` remains valid for a modified `shop` header. This is a low-effort, low-skill scenario since it only reuses the gem's documented processing path in `Webhooks::Registry.process`.

### Recommendation
Bind the shop (and topic, if used for routing) into the value that is HMAC-verified. Options: (1) include the `x-shopify-shop-domain` (and topic) header value inside `to_signable_string` alongside the body, mirroring how `AuthQuery` includes `shop` in its signable string, or (2) cross-check any shop value used to route/act on the webhook against an independently established relationship (e.g., a known/active session for that shop plus the webhook body's own `shop_id`/`myshopify_domain` field, if present), rather than trusting the unauthenticated `shop-domain` header alone.

### Proof of Concept
1. Install the target app on shop `attacker.myshopify.com`. Trigger a real webhook, e.g. `orders/create`. Capture the raw POST: headers `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid-hmac>`, `x-shopify-shop-domain: attacker.myshopify.com`, and raw JSON body `B`. The HMAC is `HMAC-SHA256(api_secret_key, B)` — note it does not depend on the shop-domain header at all [2](#0-1) .
2. Replay the identical body `B` and `x-shopify-hmac-sha256` header to the app's webhook endpoint, but change `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses these headers unchanged [8](#0-7) ; `Utils::HmacValidator.validate` recomputes the HMAC over `B` only and it still matches, so validation passes [4](#0-3) .
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, letting the attacker-controlled webhook body be processed as if it belonged to `victim.myshopify.com` [7](#0-6) .
