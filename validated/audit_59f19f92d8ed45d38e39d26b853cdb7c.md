### Title
`Webhooks::Request#to_signable_string` signs only `@raw_body`, leaving `shop`, `topic`, `webhook-id`, `api-version` headers unauthenticated - cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`Utils::VerifiableQuery` places no requirement that `to_signable_string` cover every value a consumer later trusts. `Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `Registry.process` reads `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` from HTTP headers and dispatches them, unauthenticated, to the app's business logic after `Utils::HmacValidator.validate(request)` passes [2](#0-1) . Because the shared app `client_secret` (`Context.api_secret_key`) is used to sign webhooks for every merchant that installs the app, an attacker who owns their own dev shop can capture a validly-signed webhook and replay the identical body/HMAC pair with forged `X-Shopify-Shop-Domain`/`X-Shopify-Topic`/`X-Shopify-Webhook-Id` headers, and the app will accept it as an authentic webhook from a different shop/topic.

### Finding Description
The broken binding, stated explicitly: the invariant the code should uphold is
`{shop, topic, webhook_id, api_version, body}` (everything `Registry.process` reads from `request`) `⊆ to_signable_string(request)`.
In this codebase it instead holds only that `{body} ⊆ to_signable_string(request)`, while `shop`, `topic`, `webhook_id`, `api_version` are entirely outside the signed string.

Code path:
- `Utils::VerifiableQuery` is a bare interface requiring only `hmac` and `to_signable_string`, with no contract that the signable string must include every field consumers subsequently trust [3](#0-2) .
- `Webhooks::Request#hmac` reads the `hmac-sha256` header, and `#shop`, `#topic`, `#webhook_id`, `#api_version` read other `X-Shopify-*` headers, none of which are HMAC-signed by Shopify — only the request body is signed [4](#0-3) .
- `to_signable_string` returns only `@raw_body` [5](#0-4) .
- `Utils::HmacValidator.validate_signature` computes `HMAC(secret, to_signable_string)` and compares it against `verifiable_query.hmac`, which is exactly `HMAC(secret, raw_body)` vs. the `hmac-sha256` header — completely independent of the header values used for routing [6](#0-5) .
- `Registry.process` calls `Utils::HmacValidator.validate(request)`, and — once it returns true — trusts `request.topic` to select the handler, and forwards `request.shop`, `request.topic`, `request.webhook_id`, `request.api_version` into `WebhookMetadata` passed to the app's handler, with no independent verification of those header values [2](#0-1) .

Attacker's exact request: the attacker creates their own development shop, installs the app, and registers their own endpoint/webhook so that Shopify sends them a validly-signed webhook `(body B, header hmac-sha256 = H)` where `H = HMAC(client_secret, B)`. Because `client_secret` (`Context.api_secret_key`) is the same secret for every shop that installs this app (it's the app's own OAuth client secret, not a per-shop value), `H` remains valid for `B` under that same shared secret. The attacker then sends this exact `(B, H)` pair directly to the app's public webhook endpoint, substituting `X-Shopify-Shop-Domain: victim-shop.myshopify.com`, and/or a different `X-Shopify-Topic`/`X-Shopify-Webhook-Id`/`X-Shopify-Api-Version`. `Utils::HmacValidator.validate` still returns `true` because it only checks `HMAC(client_secret, B) == H`, which is unaffected by header changes. `Registry.process` then dispatches the handler for the forged topic with `shop: "victim-shop.myshopify.com"` and the attacker's chosen `body`, `webhook_id`, and `api_version`, all trusted as authentic by the app.

Existing guards do not stop this: `HmacValidator.validate` only checks body integrity, not header authenticity [7](#0-6) ; there is no `ShopValidator.sanitize!` call on `request.shop` in this flow; there's no state/nonce/replay check comparable to `AuthQuery`'s cookie-`state` comparison for webhooks; and Sorbet's `T::Sig`/`interface!` on `VerifiableQuery` only enforces the *types* of `hmac`/`to_signable_string`, not their semantic completeness.

### Impact Explanation
An attacker can make the app process a webhook for `WebhookMetadata.shop` set to an arbitrary victim merchant's domain, with an arbitrary body and topic, while the app treats it as an authentic, HMAC-verified Shopify webhook. If the app's webhook handler performs any shop-scoped side effect keyed off `WebhookMetadata.shop` (e.g., writing data, updating billing/entitlement state, processing `orders/paid`, `app/uninstalled`, GDPR topics `shop/redact`/`customers/redact`/`customers/data_request`, etc. for that shop), the attacker can trigger it for a shop they do not control, purely by replaying one webhook they legitimately received to their own dev shop. This is a cross-tenant authentication bypass: the "authenticity" the app relies on (HMAC-validated request ⇒ genuinely came from Shopify for shop X, topic Y) is false, and it is trivially repeatable against any victim shop's domain the attacker chooses, for any topic, indefinitely, as long as the attacker retains one valid `(body, hmac)` pair for that app.

### Likelihood Explanation
Preconditions: the app must use `Webhooks::Registry.process`/`Webhooks::Request` as documented (the standard integration path in this gem) and expose an HTTP webhook endpoint reachable by the attacker — both are the default, expected usage. The attacker needs only to install the app on their own development shop (freely obtainable) to receive one legitimately signed webhook, then replay it with modified headers to the same public endpoint. No secrets, no privileged access, and no interaction with the victim are required. This is low-cost, fully unprivileged, and repeatable at will.

### Recommendation
Bind the headers that are trusted downstream into the signed material, or otherwise cryptographically tie them to the signature. Concretely: change `Webhooks::Request#to_signable_string` to include `shop`, `topic`, `webhook_id`, and `api_version` (canonically encoded, e.g. via `URI.encode_www_form` on a fixed-order hash) concatenated with `@raw_body`, and require `Registry.process` (and any other `VerifiableQuery` consumer) to only trust fields that are part of `to_signable_string`. More generally, strengthen the `VerifiableQuery` interface contract (via documentation and/or a shared test) so every field read from an implementer by its consumers must be reflected in `to_signable_string`, preventing this category of omission across both `AuthQuery` and `Webhooks::Request`.

### Proof of Concept
```ruby
# test/webhooks/registry_spoof_test.rb
require "test_helper"

class RegistrySpoofTest < Test::Unit::TestCase
  def setup
    ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", ...)
    @handler = FakeWebhookHandler.new
    ShopifyAPI::Webhooks::Registry.add_registration(
      topic: "orders/paid", delivery_method: :http, path: "/webhooks", handler: @handler,
    )
  end

  def test_hmac_ignores_shop_and_topic_headers
    body = '{"id":1,"note":"legit-for-attacker-shop"}'
    secret = "secret"
    signature = Base64.strict_encode64(
      OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, body)
    )

    # Genuine request as received by the attacker's own dev shop:
    genuine = ShopifyAPI::Webhooks::Request.new(
      raw_body: body,
      headers: {
        "x-shopify-topic" => "orders/paid",
        "x-shopify-hmac-sha256" => signature,
        "x-shopify-shop-domain" => "attacker-dev-shop.myshopify.com",
        "x-shopify-webhook-id" => "wh-1",
        "x-shopify-api-version" => "2024-01",
      },
    )
    assert ShopifyAPI::Utils::HmacValidator.validate(genuine)

    # Forged replay with the SAME body+hmac, spoofed shop/topic/id headers:
    forged = ShopifyAPI::Webhooks::Request.new(
      raw_body: body,
      headers: {
        "x-shopify-topic" => "orders/paid",
        "x-shopify-hmac-sha256" => signature,           # unchanged
        "x-shopify-shop-domain" => "victim-shop.myshopify.com", # spoofed
        "x-shopify-webhook-id" => "wh-forged",
        "x-shopify-api-version" => "2024-01",
      },
    )

    # BROKEN BINDING: signature covers only body, so this still validates
    # even though shop/webhook_id differ from the genuinely-signed request.
    assert ShopifyAPI::Utils::HmacValidator.validate(forged)
    assert_equal "victim-shop.myshopify.com", forged.shop

    # Registry.process would now hand WebhookMetadata(shop: "victim-shop...")
    # to the handler as if it were an authentic webhook for that shop.
    ShopifyAPI::Webhooks::Registry.process(forged)
    assert_equal "victim-shop.myshopify.com", @handler.last_data.shop
  end
end
```
This demonstrates the equality that should hold — `to_signable_string(request)` must uniquely determine `(shop, topic, webhook_id, api_version, body)` — is false: two `Request` objects with different `shop`/`webhook_id` produce the identical signable string and identical valid HMAC.
