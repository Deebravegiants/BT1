### Title
Rebasing-token escrow accounting mismatch in IntentGatewayV2 causes withdrawals to revert - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentGatewayV2`/`IntentsBase` escrows ERC20 input tokens per order commitment in the `_orders[commitment][token]` mapping, recording the amount actually received at `placeOrder` time. Withdrawals (`fillOrder`, `cancelOrder`/`_withdraw`) later transfer out the exact amount stored in that mapping, decrementing it by the transferred amount, rather than re-deriving the transferable amount from the contract's live token balance. If the escrowed token is a rebasing token (supply/balance adjusts after transfer, independent of internal bookkeeping), the sum of amounts recorded across all outstanding orders for that token can drift from the gateway's actual balance. A negative rebase after orders are placed leaves the contract under-collateralized relative to its own ledger, and later withdrawals will revert on `safeTransfer` once the real balance is exhausted, exactly mirroring the FraxSwap `UniV2TWAMMPair` issue described in the report.

### Finding Description
In `placeOrder`, the escrowed amount is fixed based on the balance delta measured once, at deposit time [1](#0-0) . This amount is stored in `_orders[commitment][token]` (see the Tron variant, structurally identical to the base) and never adjusted afterward [2](#0-1) .

When the order is later filled, cancelled, or refunded, `_withdraw` reads the stored escrow amount, decrements it, and calls `safeTransfer` for the literal `amount` requested in the withdrawal body — it never checks or reconciles against `IERC20(token).balanceOf(address(this))`: [3](#0-2) 

Because the escrow ledger (`_orders`) is an accounting abstraction that assumes 1:1 correspondence with the contract's real token balance, any post-deposit rebase (positive or negative) breaks that invariant:
- On a negative rebase, the aggregate `_orders[...][token]` liabilities across all pending orders for that token can exceed the gateway's actual balance. Whichever orders are withdrawn first still receive their full recorded amount, exhausting the real balance before later legitimate withdrawers can be paid, causing their `safeTransfer` calls to revert (funds effectively frozen/stuck for the last-to-withdraw users, requiring an external donation to the contract to unstick them — the same remediation-by-donation situation flagged in the source report).
- Same-chain cancellation (`_cancelSameChain`) and cross-chain refund/redeem paths (via `withdraw`/`onAccept` `RequestKind.RedeemEscrow`/`RefundEscrow`) are all reachable by an ordinary, unprivileged user simply placing and later cancelling/filling an intent order with a rebasing ERC20 as input — no special privileges are required.

### Impact Explanation
This is a permanent freezing-of-funds bug class: legitimate order owners or solvers can be unable to withdraw their rightfully escrowed tokens because the contract's internal accounting no longer matches its real balance, and the only recovery is an ad-hoc external top-up of the contract's balance. Because escrow bookkeeping is shared per-token across all orders in the gateway (not per-order-isolated custody), a single rebasing input token affects every order using that token, and reverts cascade to whichever users are queued last, which is a High severity availability/funds-freezing issue for an unprivileged, single-transaction-reachable path (`placeOrder` → later `fillOrder`/`cancelOrder`).

### Likelihood Explanation
Likelihood depends entirely on whether a rebasing ERC20 (or any token with elastic supply / balance realignment such as stETH-style rebasing tokens, or synthetic assets with negative rebases) is accepted as an order input, which the gateway does not restrict — `placeOrder` already anticipates non-standard token transfer semantics (it explicitly handles fee-on-transfer tokens by measuring balance deltas), but only at deposit time, not on an ongoing basis. Any deployer/integrator that allowlists such a token, or any permissionless deployment that accepts arbitrary ERC20 inputs, exposes this path with only a single normal `placeOrder` + wait-for-rebase + `cancelOrder`/`fillOrder`/`withdraw` sequence.

### Recommendation
- Document that rebasing/elastic-supply tokens are unsupported as order inputs/outputs in `IntentGatewayV2`, consistent with the existing fee-on-transfer handling pattern.
- Where possible, reconcile escrow releases against `IERC20(token).balanceOf(address(this))` at withdrawal time (e.g., cap the transferred amount to `min(storedEscrow, actualBalance)` and track any shortfall), or explicitly disallow tokens with `balanceOf` behavior that can diverge from transferred amounts, similar to how `placeOrder` already measures actual received amounts for fee-on-transfer tokens.
- Long term, audit every ERC20 integration point in the intents/escrow flow (`_withdraw`, `withdraw`, `_execute`, `_cancelSameChain`) for the same balance-vs-ledger divergence risk.

### Proof of Concept
1. Deploy `IntentGatewayV2` and register a mock rebasing ERC20 (balances can be reduced externally, e.g. via an `elasticity`/`rebase` admin call as in real rebasing tokens like Ampleforth-style tokens) as a supported input token.
2. Alice calls `placeOrder` with the rebasing token as input amount `A`; `_orders[commitment][token] = A` is recorded per `IntentGatewayV2.placeOrder` (`evm/src/apps/IntentGatewayV2.sol:312-323`).
3. Bob independently places a second order also using the same rebasing token as input, escrowing amount `B`; total gateway balance is now `A + B`.
4. The rebasing token undergoes a negative rebase, reducing the gateway's actual `balanceOf(gateway)` to less than `A + B` (e.g., to `A + B - Δ`), while `_orders` still records `A` and `B` separately, unaware of `Δ`.
5. Alice cancels her order via `cancelOrder`/`_cancelSameChain`, which calls `_withdraw` and transfers her full recorded `A` out (`evm/src/apps/intentsv2/IntentsBase.sol:451-469`), leaving the contract with `B - Δ` for Bob.
6. Bob attempts to cancel or the order is filled/refunded for amount `B`; `safeTransfer(beneficiary, B)` reverts because the gateway's actual balance is only `B - Δ`, permanently blocking Bob's withdrawal until someone externally donates `Δ` tokens to the contract.
