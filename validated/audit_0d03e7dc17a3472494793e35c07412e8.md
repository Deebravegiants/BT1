### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw body only, while the `shop` (tenant) identifier is taken from an unauthenticated HTTP header and passed straight through to the host application's webhook handler as the trusted tenant identity.

### Finding Description
The reported bug class is a broken identity binding: a value that is *used* to make a security decision is not the same value that was *verified*. In the audited protocol this was "receiver validated" vs. "jetton wallet actually used." In this gem, the analogous binding is "shop that the HMAC actually authenticates" vs. "shop that `Registry.process` hands to the app as the tenant."

`Utils::HmacValidator.validate` verifies the request by calling `verifiable_query.to_signable_string`, and for `Webhooks::Request` this method returns only the raw body: [1](#0-0) 

The `shop` value, by contrast, is read directly from the `x-shopify-shop-domain`/`shopify-shop-domain` header with no cryptographic binding to the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate_signature` only proves that `secret` (the app's shared `api_secret_key`, identical for every shop installed on the app) produced a valid HMAC over the raw body — it says nothing about which shop the header claims to be from: [3](#0-2) 

`Webhooks::Registry.process` validates the HMAC and then forwards the unauthenticated `request.shop` value straight to the app's handler as the tenant identity, with no cross-check against anything the HMAC covers: [4](#0-3) [5](#0-4) 

Because the same `api_secret_key` is shared across every shop that installs the app, and only the body (not the shop header) is signed, a valid `(body, hmac)` pair legitimately produced for one shop remains valid when replayed with a different `shop-domain` header value — the equality that should hold, `shop_claimed_in_header == shop_that_HMAC_authenticates`, does not, because the HMAC never binds the shop at all.

### Impact Explanation
Any merchant/tenant of a host app built on this gem can register a webhook subscription for their own store and thereby legitimately receive `(raw_body, valid HMAC)` pairs signed with the app's shared secret. By replaying that exact body/HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain, the attacker's request still passes `Utils::HmacValidator.validate` (body signature is unchanged) and `Registry.process` will hand the host application a `WebhookMetadata` claiming to originate from the victim shop. Host applications that use `data.shop` as the multi-tenant partition key (a documented and expected usage pattern for this gem, e.g. persisting/looking up data per shop) will attribute attacker-controlled data to another tenant, i.e. cross-tenant data injection. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires the attacker to be a legitimate but unprivileged customer of the app who can install it and register/receive at least one webhook for a topic with a body they control or can predict (e.g. `orders/create`, `app/uninstalled`, or any topic whose payload content the attacker can influence, such as by placing an order in their own shop). No access to the `api_secret_key` or another merchant's access token is needed — only the ability to capture one's own valid webhook delivery and resend it with a modified header, which any unprivileged internet-facing HTTP client can do.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) in the value that is HMAC-verified, or otherwise cryptographically bind them, rather than trusting header-derived fields that sit outside `to_signable_string`. At minimum, document/require that host applications independently verify `request.shop` against a known, registered shop list before trusting it as a tenant key, and consider verifying it inside `Registry.process` itself so all consumers of this gem get the protection automatically.

### Proof of Concept
1. App is installed on Shop A (attacker-controlled) and Shop B (victim), sharing one `api_secret_key`.
2. Attacker triggers a webhook delivery to their own endpoint for topic `orders/create` on Shop A, capturing the raw JSON body and the `x-shopify-hmac-sha256` header Shopify computed for it.
3. Attacker resends this exact `(raw_body, hmac)` pair to the app's public webhook endpoint but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers, `Utils::HmacValidator.validate` succeeds (only `raw_body` and the shared secret were ever checked — see `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/utils/hmac_validator.rb:26-31`).
5. `Registry.process` invokes the app's handler with `WebhookMetadata(shop: "shop-b.myshopify.com", ...)`, causing the host application to process attacker-supplied data under Shop B's identity.
