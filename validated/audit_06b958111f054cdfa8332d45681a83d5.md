### Title
Webhook Shop-Domain Spoofing via HMAC That Only Covers the Raw Body, Not the Shop Header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, and `webhook_id` are read straight from unauthenticated HTTP headers and are never included in the signed material. `Webhooks::Registry.process` validates the HMAC over the body only and then forwards the untrusted `shop` header value directly to the app's handler as the tenant identifier, breaking the intended binding of `hmac_valid == (shop, body)` down to `hmac_valid == body only`.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the signature using `verifiable_query.to_signable_string`. For webhooks, that string is defined as: [1](#0-0) 

Only `@raw_body` is signed. The `shop`, `topic`, and `webhook_id` accessors are pulled from headers that are not part of the signed data: [2](#0-1) 

`Registry.process` validates the HMAC (over the body) and then immediately trusts the header-derived `request.shop` as the tenant identity passed to the app's webhook handler: [3](#0-2) 

Because a single public webhook endpoint receives deliveries for every shop that installs the app (differentiated only by the `X-Shopify-Shop-Domain` / `shopify-shop-domain` header), and because that header is not part of the signed bytes, any request whose body+HMAC pair is valid for *some* shop will also validate successfully with the `shop` header rewritten to name a *different* shop. `Registry.process` cannot distinguish this from a legitimate delivery for the claimed shop — it hands `WebhookMetadata.new(shop: request.shop, ...)` straight to the handler.

This is the same identity-binding defect pattern as the report's hardcoded exchange rate: the mechanism that is supposed to prove authenticity of the acted-upon field (`shop`) does not actually cover that field.

### Impact Explanation
An attacker who legitimately operates their own shop with the app installed will legitimately receive validly-signed webhook deliveries (Shopify signs them with the app's secret on the attacker's behalf). The attacker can capture one such delivery (body + `X-Shopify-Hmac-SHA256`) and replay it to the same public endpoint with the `shop-domain` header rewritten to a victim shop's domain. `Utils::HmacValidator.validate` returns `true` because only the body is checked, and the handler is invoked believing the event/data belongs to the victim shop. Depending on how the host app's handler uses `data.shop` (e.g., to look up/store per-tenant records, attribute orders, trigger notifications, or select which access token/session to act with), this enables cross-tenant data injection/misattribution — a Critical-impact cross-tenant access issue per the injected identity binding being entirely attacker-controlled.

### Likelihood Explanation
The attacker only needs their own shop with the app installed (unprivileged, ordinary merchant capability) and the ability to send an HTTP request with a custom header to the app's public webhook URL — no access to `api_secret_key`, tokens, or privileged accounts is required. The webhook endpoint is public by design (Shopify must be able to reach it from the internet), so likelihood of exploitation is high wherever the host app trusts `WebhookMetadata#shop` for tenant-sensitive logic without independent verification (e.g., cross-referencing `webhook_id`/topic against records tied to a specific shop).

### Recommendation
Bind the shop identity into the verified material, or otherwise avoid trusting an unauthenticated header as tenant identity:
- Include `shop`, `topic`, and `webhook_id` in the HMAC-covered signable string (this would require coordinating with Shopify's signing scheme, which is unlikely to be app-side changeable), or
- At minimum, document/enforce that `WebhookMetadata#shop` must never be used as the sole tenant identifier for security-sensitive actions; require the host app to independently correlate the webhook against a shop-scoped record (e.g., session/store lookup keyed by `webhook_id` obtained via an authenticated API call), and add validation in `Registry.process` that the `shop` header matches an expected/registered shop context before dispatching the handler.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and captures a real Shopify-signed webhook delivery to the app's public endpoint:
   ```
   POST /webhooks
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid-signature-for-body>
   X-Shopify-Shop-Domain: attacker-shop.myshopify.com
   Body: {"id": 123, ...attacker-controlled order data...}
   ```
2. Attacker replays the identical body and `X-Shopify-Hmac-Sha256` value to the same endpoint, only changing the shop header:
   ```
   POST /webhooks
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <same-valid-signature-for-body>
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   Body: {"id": 123, ...same attacker-controlled data...}
   ```
3. `Utils::HmacValidator.validate` recomputes the HMAC over `@raw_body` only [4](#0-3)  — it matches, since the body is unchanged.
4. `Registry.process` invokes the handler with `shop: request.shop` == `"victim-shop.myshopify.com"` [5](#0-4) , causing the host application to process attacker-supplied data as if it originated from the victim shop.
