### Title
Unchecked zero-length `request.body` index causes permanent revert-on-delivery for a valid ISMP message - ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
`ExtrinsicIntents.onAccept` reads `incoming.request.body[0]` to determine the `RequestKind` of an inbound ISMP POST request without first checking `body.length > 0`. [1](#0-0) 

### Finding Description
`onAccept` is only callable by the host (`onlyHost`), but the host itself does not sanitize the *content* of the request body — it only validates the merkle proof, destination, timeout and duplicate-delivery status of the request before calling `host.dispatchIncoming(leaf.request, _msgSender())`, which in turn calls the destination module's `onAccept`. Anywhere along the ISMP dispatch path the `body` bytes are fully attacker/source-application controlled: any application on a source chain can dispatch a POST request whose `to` field targets this `ExtrinsicIntents` contract, with an arbitrary (including zero-length) `body`. [2](#0-1) 

Solidity `bytes calldata` indexing (`body[0]`) on an empty array reverts with a `Panic(0x32)` (array index out-of-bounds) rather than returning a safe default — this is directly analogous to the CVE-2025-50361 buffer-overflow class where an unbounded/unchecked index read on attacker-controlled input causes a crash. Because the request/message is bound to a specific commitment computed from its exact bytes (including the empty body), the message can never be resubmitted with different content — the destination call will revert identically on every future delivery attempt.

### Impact Explanation
Since `handlePostRequests` calls `host.dispatchIncoming` for every leaf in the batch and there is no `try/catch` isolating one leaf's destination call from the rest, a single request in a relayed batch whose body is empty (or otherwise malformed at index 0) causes the entire relaying transaction to revert. Because the underlying request commitment is already fixed and verified against the finalized source-chain state (it cannot be re-encoded with a non-empty body), the message becomes permanently undeliverable to `ExtrinsicIntents` — a "route unable to deliver messages" condition, and any other legitimate requests batched alongside it are also blocked from delivery in that transaction, forcing relayers to identify and exclude the poisoned leaf.

### Likelihood Explanation
Any account on any chain that can dispatch an ISMP POST request with `to = ExtrinsicIntents` address can trigger this by publishing a request whose body is empty — this requires no special privilege, just triggering the ordinary dispatch/relay flow reachable by an unprivileged message dispatcher or relayer. This is Medium severity because it results in a DoS on message delivery for a specific crafted commitment rather than fund theft, matching the CVSS 5.1/Medium class of the underlying report.

### Recommendation
Add an explicit length check before indexing the body, e.g.:
```solidity
if (incoming.request.body.length == 0) revert InvalidRequestBody();
RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
```
Additionally, consider wrapping the per-leaf dispatch inside `HandlerV2.handlePostRequests`/`host.dispatchIncoming` with a try/catch (or equivalent low-level call) so that one poisoned request cannot block delivery of the rest of the batch, and so failed deliveries can be reported/handled without reverting the whole transaction.

### Proof of Concept
1. On a source chain, dispatch an ISMP POST request with `dest` = the EVM chain hosting `ExtrinsicIntents`, `to` = the `ExtrinsicIntents` contract address, and `body = ""` (zero bytes).
2. Let Hyperbridge finalize consensus and generate the corresponding MMR/state proof for this request.
3. A relayer calls `HandlerV2.handlePostRequests` with this request included in `request.requests`; the proof passes (`InvalidProof` check succeeds since the commitment matches exactly what was dispatched).
4. `host.dispatchIncoming` invokes `ExtrinsicIntents.onAccept`, which executes `uint8(incoming.request.body[0])` on an empty `calldata bytes` array, reverting with `Panic(0x32)`.
5. Because there is no isolation/try-catch, the whole `handlePostRequests` transaction reverts; the request cannot be delivered on any subsequent relay attempt since its commitment (and thus its empty body) is immutable — the message is permanently stuck. [3](#0-2) [4](#0-3)

    function handlePostRequests(IHost host, PostRequestMessage calldata request) external notFrozen(host) {
        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(request.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 requestsLen = request.requests.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](requestsLen);

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // check destination
            if (!leaf.request.dest.equals(host.host())) revert InvalidMessageDestination();
            // check time-out
            if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.request.hash());
        }

        bytes32 root = host.stateMachineCommitment(request.proof.height).overlayRoot;
        if (root == bytes32(0)) revert StateCommitmentNotFound();
        bool valid = MerkleMountainRange.VerifyProof(root, request.proof.multiproof, leaves, request.proof.leafCount);
        if (!valid) revert InvalidProof();

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // duplicate request?
            if (host.requestReceipts(leaf.request.hash()) != address(0)) revert DuplicateMessage();
            host.dispatchIncoming(leaf.request, _msgSender());
        }
    }
