### Title
Webhook shop/topic identity is trusted from unauthenticated headers while HMAC only covers the raw body - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw HTTP body for HMAC verification, but the `shop`, `topic`, `webhook_id`, and `api_version` values that `Registry.process` trusts and hands to the app's webhook handler are read from HTTP headers that are never included in the signed payload. Any party who can obtain one validly-signed webhook body/HMAC pair (e.g. by installing the app on their own store and receiving a legitimate webhook) can replay that exact body+HMAC to the app's webhook endpoint with arbitrary `shop-domain`/`topic`/`webhook-id` headers, causing the app to process attacker-chosen content under the identity of a different, victim shop and/or a different topic.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors read directly from HTTP headers, none of which participate in the signable string: [2](#0-1) 

`Registry.process` verifies the HMAC (which only proves the body wasn't tampered with) and then unconditionally trusts the header-derived `topic`/`shop`/`webhook_id` to dispatch the event to the registered handler: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string`, i.e. the raw body, using the app-wide `Context.api_secret_key` (the same secret is used to sign webhooks for every shop that installed the app): [4](#0-3) 

This breaks the intended identity binding: `shop_verified_by_hmac == shop_used_by_handler`. In reality, `shop_verified_by_hmac` is undefined (the signature says nothing about `shop`), while `shop_used_by_handler` comes straight from an attacker-controllable header.

### Impact Explanation
Because the webhook signing secret (`Context.api_secret_key`) is shared across all shops that installed the app, any user who can install the app on their own shop (a low-privilege, self-service action available to any merchant/internet user) can capture one legitimately HMAC-signed `raw_body`. That exact `raw_body` + HMAC pair remains valid regardless of the `x-shopify-shop-domain`, `x-shopify-topic`, or `x-shopify-webhook-id` headers sent alongside it, since those are not part of `to_signable_string`. The attacker can therefore submit a forged webhook request directly to the app's public webhook endpoint claiming to originate from an arbitrary victim shop (cross-tenant impersonation) and/or an arbitrary topic (e.g. `app/uninstalled`, `shop/redact`), with body content the attacker fully controls (from their own real delivery). Depending on the handler logic registered by the host app, this can trigger tenant-scoped side effects (data deletion, deauthorization, state changes) attributed to a shop the attacker does not control - a cross-tenant impact.

### Likelihood Explanation
The only precondition is the ability to install the target app once (as any merchant) to obtain one valid `(raw_body, hmac)` pair, and the ability to send a raw HTTP POST to the app's public webhook endpoint with custom headers - both are available to an ordinary, unprivileged internet user/merchant. No access token, `client_secret`, or credential leak is required. The gem itself performs no binding between the signed content and the shop/topic used for dispatch, so exploitation success depends only on the host app registering a handler that has some observable side effect keyed by `shop`/`topic`, which is the gem's entire stated purpose (`Registry.add_registration`/`process`).

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or at minimum `shop`) in the HMAC-signed material used by `to_signable_string`, or otherwise cryptographically bind the header values to the signed body so that `HmacValidator.validate` fails whenever any of these header fields are altered relative to what Shopify actually signed. If binding all headers into the signature isn't feasible with the currently available Shopify signing scheme, the gem should document this limitation prominently and encourage/allow host apps to cross-check `shop` against known installed shops before acting on `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and triggers a webhook delivery whose body content they control (e.g. update an order's note to arbitrary attacker-chosen JSON), capturing the raw body `B` and Shopify-computed header `x-shopify-hmac-sha256: H`.
2. Attacker sends a POST directly to the app's public webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256: H` (unchanged, still valid because HMAC only covers body)
   - Header `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
   - Header `x-shopify-topic: app/uninstalled` (forged, if this topic's expected body happens to match `B`, or any topic whose handler only inspects `shop`)
3. `Utils::HmacValidator.validate(request)` returns `true` because the raw body's HMAC is unchanged (lib/shopify_api/utils/hmac_validator.rb:13-22).
4. `Registry.process` looks up the handler for the forged `topic` and invokes it with `shop: "victim-shop.myshopify.com"` and attacker-controlled `body`, even though nothing about `victim-shop.myshopify.com` was ever cryptographically verified (lib/shopify_api/webhooks/registry.rb:188-200).

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
