### Title
Webhook shop-domain spoofing due to HMAC signature covering only the raw body, not the `shop-domain` header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` attribute directly from the untrusted `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, while `to_signable_string` — the value that `HmacValidator` actually authenticates — is only the raw request body. Because the shop identity is never part of the HMAC-signed material, an attacker who possesses one valid `(body, hmac)` pair for the app's shared `api_secret_key` (e.g., from webhooks delivered to their own, legitimately-installed shop) can replay that request against the app's webhook endpoint with the `shop-domain` header swapped to a victim shop. `Registry.process` accepts it as authentic and dispatches it to the app's handler tagged with the attacker-chosen shop, breaking the binding between "bytes verified" and "shop attributed."

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`#shop` is read straight from a caller-supplied header with no cryptographic tie to the signed body: [2](#0-1) 

`HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the received HMAC — since `to_signable_string` never includes `shop`, the signature is unaffected by which shop the header claims: [3](#0-2) 

`Registry.process` gates purely on this HMAC check and then forwards `request.shop` unchecked into the handler payload: [4](#0-3) 

The identity-binding equality that should hold is: `hmac_signed_bytes == bytes_that_determine(shop)`. Here it does not — `hmac_signed_bytes = raw_body` while `shop = header["shop-domain"]`, an entirely separate, unauthenticated channel. Any consumer of this gem that trusts `WebhookMetadata#shop` (as the library's own docs instruct via `ShopifyAPI::Webhooks::Registry.process`) is exposed to cross-tenant webhook forgery, since `api_secret_key` is a single value shared by the app across all installed shops, not shop-specific.

### Impact Explanation
This crosses a tenant boundary: an attacker controlling any shop where the app is installed (an "unprivileged internet user" relative to other tenants) can produce webhook payloads that the app will process as belonging to a different, victim shop, because the app can't detect the header was changed after the HMAC was computed by Shopify. Depending on what the host application's webhook handlers do (e.g., update local per-shop billing/entitlement state, disable app access, sync data) this enables cross-tenant data corruption or access — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Requires the attacker to (a) have their own legitimate shop install the app so they receive real, Shopify-signed webhook bodies for that shop, and (b) know or guess a victim shop's `.myshopify.com` domain (public information) to replay the captured request with a modified `shop-domain` header at the app's public webhook endpoint. No access to `api_secret_key`, tokens, or the victim's credentials is needed — only the gem's own documented processing path is used to reach the mismatch.

### Recommendation
Bind the shop domain into the material verified by the HMAC signature (e.g., verify a scheme where the shop is derived from the app's per-shop mapping validated after HMAC, or require the raw body's own payload — most Shopify webhook JSON bodies already include identifying fields — to be cross-checked against the header), or otherwise document/enforce that `request.shop` must never be trusted for authorization decisions without additional binding (such as validating the request originated from a URL that already encodes the shop, or maintaining an allowlist of `(webhook_id, shop)` pairs fetched from Shopify's Admin API before trusting the header).

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com`. Shopify sends a legitimate webhook with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)` and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker replays the identical `B` and identical HMAC header to the app's webhook endpoint but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `HmacValidator.validate` recomputes `HMAC(secret, B)` — matches, since `B` is unchanged — via [5](#0-4) .
4. `Registry.process` invokes the handler with `WebhookMetadata.new(..., shop: request.shop, ...)` where `request.shop == "victim.myshopify.com"`, per [6](#0-5) , even though the payload never originated from or was intended for that shop.
