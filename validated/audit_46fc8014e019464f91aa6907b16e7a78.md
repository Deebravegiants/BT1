### Title
Webhook shop identity is not covered by the HMAC signature, enabling cross-tenant shop spoofing via replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
The library validates incoming webhook requests by computing an HMAC over the raw request body only. The `shop` (and `topic`, `api_version`, `webhook_id`) values are taken from HTTP headers that are never included in the signed payload. This means the cryptographic check binds "the body has not been tampered with" but does **not** bind "this body belongs to this shop" — the exact class of bug described in the source report, where a value used in downstream accounting/attribution logic is not covered by the integrity check that is supposed to authenticate it.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 

`to_signable_string` returns only `@raw_body`, while `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from HTTP headers via `shopify_header`, completely outside the signed string: [2](#0-1) 

`Utils::HmacValidator.validate` only recomputes the HMAC over `verifiable_query.to_signable_string` (i.e., the body) and compares it to the received `hmac`: [3](#0-2) 

`Webhooks::Registry.process` performs this HMAC check and, if it passes, immediately trusts `request.shop` to build the `WebhookMetadata` struct passed to the host app's handler: [4](#0-3) 

`WebhookMetadata#shop` is a plain `String` field with no further validation, and the interface contract (`WebhookHandler#handle`) hands this struct directly to the app's business logic: [5](#0-4) 

**Identity binding broken (as an equality):**
`shop_header == request.shop` is enforced by nothing — the code should assert `HMAC(secret, raw_body ++ shop) == received_hmac`, but instead only asserts `HMAC(secret, raw_body) == received_hmac`, and separately reads `shop` unauthenticated from the header.

Because the app's `api_secret_key` is shared across **all** shops that install the app (it's an app-level credential, not per-tenant), any merchant who installs the app can legitimately receive a validly-HMAC'd webhook body for their own shop. That same `(raw_body, hmac)` pair remains cryptographically valid regardless of which `shop-domain` header accompanies it, because the header is not part of the signed content. An attacker (an unprivileged internet user acting as a legitimate installer of the app on their own store) can:

1. Trigger any webhook topic on their own shop to obtain a valid `(raw_body, hmac)` pair signed with the app's shared secret.
2. Replay that exact body/HMAC to the app's webhook endpoint while substituting `x-shopify-shop-domain` (or `shopify-shop-domain`) with a victim shop's domain.
3. `HmacValidator.validate` still succeeds, because only the body is checked.
4. `Registry.process` constructs `WebhookMetadata.new(shop: <victim shop>, body: <attacker-controlled>, ...)` and forwards it to the host app's handler as if it were an authentic event for the victim shop.

### Impact Explanation
This crosses a tenant boundary: it allows one merchant's webhook traffic (with attacker-influenced ordering/timing/content, since the attacker controls their own shop's data that generates the body) to be attributed to a different, victim shop inside the host application's webhook handler. Any app logic that trusts `data.shop` from `WebhookMetadata` to key database writes, trigger fulfillment actions, update billing state, or otherwise mutate per-tenant data can be manipulated cross-tenant without ever compromising the victim's access token or the app's `client_secret`. This matches the report's "Impact" tier for cross-tenant access.

### Likelihood Explanation
Any developer/merchant who can install the target app (a completely unprivileged action) can generate valid signed webhook bodies for their own store, then trivially replay them with a modified `shop-domain` header value using any HTTP client — no possession of the app's `client_secret` or any victim credential is required. The only prerequisite is that the host application relies on `WebhookMetadata#shop` (as documented/intended by this gem) to determine which tenant a webhook event belongs to, which is exactly how the gem's own `docs/usage/webhooks.md` and `WebhookHandler` interface direct consumers to use it.

### Recommendation
Include the shop-identifying header (and ideally topic/webhook id) inside the HMAC-signed material, or otherwise cryptographically bind the header values to the body before trusting them — e.g., validate that the `shop` value is a shop the app has an active session/install for, and/or extend `to_signable_string` (or a companion check in `Registry.process`) to verify shop-domain against a value derived from an authenticated source (such as the associated session) rather than trusting the raw header outright. At minimum, document that `data.shop` is unauthenticated by the HMAC and must be cross-checked against known/installed shop records before being used for any tenant-scoped action.

### Proof of Concept
```ruby
# 1. Attacker installs the app on their own shop and captures a legitimate
#    webhook delivery, e.g. body = '{"id":123}', hmac = "<valid-hmac-for-body>"
#    signed with the app's shared api_secret_key.

raw_body = '{"id":123}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_SECRET, raw_body)

# 2. Attacker replays it, claiming to be "victim-shop.myshopify.com"
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac), # still valid! body unchanged
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, not covered by HMAC
  "x-shopify-webhook-id" => "attacker-chosen-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)

# 3. HMAC validation passes because it only checks raw_body:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# 4. Registry.process forwards attacker-controlled body attributed to victim-shop:
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: {"id"=>123}, ...))
```
