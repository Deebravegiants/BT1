## Analysis

The `describeWithdrawal` method in `OmniBridge` reports a withdrawal as `"completed"` for chains it does not explicitly recognize, without ever checking whether a destination transfer actually happened. [1](#0-0) 

### Finding Description

`CHAIN_MAPPINGS` currently lists `ChainKind.Eth, Base, Arb, Sol, Bnb, Btc, Abs, Strk, Fogo, Pol, Aptos, HlEvm, Zcash` as the supported chain kinds for Omni Bridge withdrawals [2](#0-1) . `describeWithdrawal` branches on the *destination chain kind derived from the transfer response* (`getChain(transfer.recipient)`), not from the withdrawal's own asset/chain. It only assigns a real `txHash` when the chain is EVM, `Sol`, `Fogo`, `Strk`, or `Aptos` (via `transfer.finalised?.transaction_hash`) or a UTXO chain (`Btc`/`Zcash`, via `pending_sign_id`/`finalised`). For every other `ChainKind` value returned by the Omni bridge indexer (e.g. `Bnb`... wait Bnb is EVM; but any newly added or edge-case chain kind not covered by `isEvmChain`/`Sol`/`Fogo`/`Strk`/`Aptos`/`isUtxoChain`, such as `ChainKind.Near` itself or any future chain the Omni protocol adds), the code falls into the `else` branch and unconditionally returns `{ status: "completed", txHash: null }` — without confirming any transfer occurred on that destination chain [3](#0-2) .

This breaks the equality that `WithdrawalStatus.status` must reflect the actual on-chain outcome, as documented in the type itself: `"failed"` means "I checked, and the withdrawal failed," implying `"completed"` should mean "I checked, and it landed" [4](#0-3) . Here, `"completed"` is reported purely because the chain-kind switch ran out of known cases — not because a transfer was confirmed.

### Impact Explanation

Callers of `sdk.waitForWithdrawalCompletion` / `describeWithdrawal` (integrators, backends, exchanges) treat `status: "completed"` as the signal to credit a user, release custody, or stop retrying. A false-positive "completed" for a chain kind that isn't yet mapped/handled would cause an integrator to mark a withdrawal as delivered when funds have not actually arrived — the "status misreport" impact class called out in scope (potential double-credit/incorrect settlement, since the real transfer might still be pending or could fail separately).

### Likelihood Explanation

This is reachable whenever the Omni Bridge indexer returns a `transfer.recipient` whose chain (via `getChain`) is not one of the five explicitly-checked EVM/Sol/Fogo/Strk/Aptos kinds nor a UTXO chain — this is a defensive-gap in an exhaustive-looking but not-exhaustive switch (no `default: never` check the way `validateAddress` in the same package uses `blockchain satisfies never`). Given `@omni-bridge/core`'s `ChainKind` enum is externally versioned and the SDK's own `CHAIN_MAPPINGS` is already known to lag (new chains are added over time, per the CHANGELOG history of adding chains one by one), any chain added on the Omni side before this switch is updated — or any bridge/relayer edge case producing a different `getChain` value — hits this fallback silently and by design (no error, no log), rather than throwing or staying pending.

### Recommendation

Change the final `else` branch to return `{ status: "pending" }` (matching the "unknown/no evidence yet" semantics used elsewhere in the file, e.g. `omni-bridge.ts` lines 700-701 and 726-728) or throw/log an explicit "unhandled chain kind" error, instead of asserting completion. Add a `chainKind satisfies never`-style exhaustiveness check (as already used in `validateAddress.ts`) so future additions to `ChainKind` fail to compile/loudly fail rather than silently defaulting to "completed."

### Proof of Concept

1. An Omni Bridge withdrawal targets a chain kind not in `{isEvmChain, Sol, Fogo, Strk, Aptos}` and not in `isUtxoChain` (e.g., a chain the Omni protocol has added since this switch was last updated, or any indexer-reported chain that doesn't map cleanly).
2. `bridge.describeWithdrawal({...})` is called; `transfer` is non-null with a valid `recipient`, so line 700's early return is skipped.
3. `getChain(transfer.recipient)` yields a `ChainKind` that fails every condition in lines 706-714.
4. Execution reaches the `else` at line 722 and returns `{ status: "completed", txHash: null }` unconditionally — even though no destination-chain confirmation was ever inspected for this chain.
5. A caller relying on this status (e.g., via `sdk.waitForWithdrawalCompletion`) treats the withdrawal as settled and finalizes downstream accounting despite no verified on-chain delivery.

 * - **`failed` status**: Job-level failure reported by the bridge.

export type WithdrawalStatus =
	| { status: "pending" }
	| { status: "completed"; txHash: string | null }
