## Title
Webhook shop identity spoofing via unsigned `shop-domain` header enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating only the HMAC over the raw request body, then trusts the `shop-domain` header as the tenant identity when dispatching to the app's handler. Because the shop is never part of the signed material, any party who can produce one valid signature for the shared app secret can attach that signature to an arbitrary `shop-domain` value.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string`, and for webhooks that method returns only the raw JSON body: [1](#0-0) [2](#0-1) 

`Registry.process` validates the HMAC and then immediately reads `request.shop` (from the `x-shopify-shop-domain`/`shopify-shop-domain` header) to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

The identity binding broken is: `HMAC(secret, raw_body) == received_hmac` is treated as proof that `shop-domain header == originating shop`, when in fact `shop-domain` is never included in the signed bytes. Since a single app-wide `api_secret_key` (not a per-shop secret) is used for every installation of the app, an unprivileged user who has installed the app on their own store (a normal, unprivileged tenant relative to any other merchant) can capture a legitimately signed webhook delivered to their own shop, then replay it with the `x-shopify-shop-domain` header changed to a victim shop's domain. The signature still validates because it only covers `@raw_body`, and the low-privilege attacker's own shop is never checked against the header value anywhere in `Request` or `Registry`.

### Impact Explanation
This crosses a tenant boundary: the host application's webhook handler receives `WebhookMetadata#shop` claiming to be an arbitrary victim shop, backed by a cryptographically "valid" signature, even though the payload actually originated from (and was legitimately signed for) the attacker's own tenant. Any host application logic keyed on `shop` (e.g., updating tenant records, triggering GDPR/mandatory webhook flows, mutating per-shop state) can be manipulated to act on behalf of another merchant's identity — this is cross-tenant access, matching the Critical impact bar.

### Likelihood Explanation
Any merchant/developer who installs the app (a normal unprivileged action, not requiring the app's `client_secret` or any Shopify-side credential) can capture one authentic webhook delivery to their own store and immediately reuse its signature with a forged `shop-domain` header. No brute-forcing or secret knowledge is required — only observing one legitimate webhook body/signature pair, which is trivially available to any app installer.

### Recommendation
Bind the shop identity into the verified material for webhooks — e.g., include the `shop-domain` (and ideally `webhook-id`/`api-version`) header value in the signable string used to compute/verify the HMAC, or independently confirm the shop against a value obtained through an already-authenticated channel (such as looking up a previously stored session/access token for that shop) before trusting `request.shop` in `Registry.process`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (unprivileged, self-service).
2. Shopify delivers a legitimate webhook to the attacker's endpoint (or attacker triggers one), with headers:
   - `x-shopify-hmac-sha256: <valid signature over the raw body>`
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
3. Attacker replays the exact same body and HMAC value to the app's webhook endpoint, but changes the header to:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
4. `Utils::HmacValidator.validate` succeeds because it only checks `@raw_body` (`lib/shopify_api/webhooks/request.rb` lines 35-38), and `Registry.process` (`lib/shopify_api/webhooks/registry.rb` lines 188-199) dispatches to the handler with `shop: "victim-shop.myshopify.com"`, even though the payload/signature pair actually belongs to the attacker's own shop.
