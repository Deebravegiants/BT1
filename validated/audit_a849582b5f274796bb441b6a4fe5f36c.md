### Title
Emporium `verifyWallet` binds op-set replay only to an attacker-chosen nonce, not to any authorization, enabling repeated draining of Emporium-held balances - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`verifyWallet` gates every Emporium action solely on `usedMessages[circomData.emporiumMessage]`, but when `stack.signerAddress == address(0)` it returns immediately without binding `stack.ops` to anything [1](#0-0) . Since `emporiumMessage` is just `Poseidon(messageSeed)` with `messageSeed` a private witness freely chosen by the caller [2](#0-1) , and the Min circuit constrains nothing about `ops`/`externalActionMetadata`, an attacker can submit the identical `ops` payload under an unlimited sequence of fresh, valid `(message, proof)` pairs.

### Finding Description
Broken equality: SINGLE_SPEND intends `usedMessages[emporiumMessage] == true` to permanently retire one specific authorized action set (`ops`). In practice, `emporiumMessage` and `ops` are two independent, uncorrelated values — nothing forces `emporiumMessage = f(ops)`.

Trace:
- `Hinkal.transact` → `performHinkalChecks` verifies `calldataHash` matches `getHashedCalldata(circomData)`, which *does* include `externalActionData` (hence `ops`) [3](#0-2) , and builds `inputForCircom` via `formInputForCircom` [4](#0-3) .
- When `erc20TokenAddresses.length == 0` and the action is the Emporium action, `formInputEmporiumMin` is used, producing only `[emporiumMessage, timeStamp, calldataHash]` as public inputs [5](#0-4) , matched against `MainEVMCircuitMin`, whose only real constraint is `message <== Poseidon(1)([messageSeed])` [6](#0-5) . There is no root-hash/nullifier/UTXO check in this circuit at all, and no constraint tying `message`/`emporiumMessage` to `calldataHash` or `ops`.
- `EmporiumUpgradeable.runAction` decodes `stack` from `externalActionMetadata`, then calls `verifyWallet(stack, circomData)`, which only checks/sets `usedMessages[circomData.emporiumMessage]`; if `stack.signerAddress == address(0)` it returns before ever hashing or checking `stack.ops` [7](#0-6) .
- The stateless branch (`signerAddress == 0`) then executes `op.endpoint.call{value: op.value}(op.callData)` directly as Emporium [8](#0-7) .

Because `messageSeed` is a private witness the attacker picks per proof, they can generate an unlimited number of distinct, valid `(a,b,c, emporiumMessage)` tuples, each passing `verifyProof` and `usedMessages` uniqueness, while keeping `stack.ops` (and thus `externalActionMetadata`/`calldataHash`) bit-identical. Root-hash/nullifier checks provide no additional friction in this code path since `erc20TokenAddresses.length == 0` means no UTXOs are spent and `dimensionsCheck` only requires the various per-token arrays to match `dimensions.tokenNumber == 0`. The balance-accounting loop in `runAction` (`balancesBefore`/`balancesAfter`/`BalanceChangeShouldBePositive`) iterates only over `circomData.erc20TokenAddresses`, which is empty in this exact configuration — so any token/ETH balance change caused by `ops` is entirely unchecked and unaccounted for.

### Impact Explanation
This is a genuine authorization/replay-binding gap: each call is "new" only by nonce, not by intent. Combined with the empty `erc20TokenAddresses` path bypassing all balance accounting, an attacker can repeatedly invoke the identical `ops` (e.g., calling an approved spender/token/DEX endpoint that sweeps Emporium's ETH/ERC20 balance to an attacker-controlled address) at zero marginal cost each time Emporium re-accumulates any balance (from unrelated deposits, dust, fee remnants, or partially-settled prior actions). This matches the Critical category: direct theft of value the protocol/other users have parked in Emporium, executed via calls the "SINGLE_SPEND" nonce was supposed to make single-use.

### Likelihood Explanation
Preconditions: Emporium must hold or periodically re-accumulate some balance/approval reachable by the crafted `ops` (plausible any time deposits, fee remnants, or partial swaps route through Emporium). Attacker cost is minimal — generating a new Groth16 proof for `MainEVMCircuitMin` requires only picking a new `messageSeed` and running the prover locally; no real UTXO ownership or signature is needed since `signerAddress == 0` skips it entirely. This is fully repeatable and requires no privileged role, matching the stated threat model.

### Recommendation
Bind `emporiumMessage` cryptographically to `stack.ops` (and other authorization-relevant stack fields) even in the `signerAddress == address(0)` path — e.g., require `emporiumMessage == uint256(keccak256(abi.encode(_hashEmporiumOps(stack.ops), stack.maxFee, stack.deadline))) % CIRCOM_P` (or otherwise derive/verify the message from the op-set), so a given `ops` payload can only ever be paired with one message. Additionally, when `erc20TokenAddresses.length == 0`, still enforce balance-neutrality/accounting for any ETH or token transfers performed by `ops`, rather than skipping the check entirely.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`, and the `mainEVMCircuitMin0v4` verifier; fund Emporium with a token balance representing "re-accumulated" funds (e.g., transfer tokens directly to the Emporium proxy, simulating leftover balance from unrelated flows).
2. Craft a single `EmporiumStack` with `signerAddress = address(0)` and `ops` containing one operation that calls `token.transfer(attacker, token.balanceOf(address(Emporium)))`.
3. Locally generate two Groth16 proofs for `MainEVMCircuitMin` with two different `messageSeed` values (`seed1`, `seed2`), yielding `emporiumMessage1 = Poseidon(seed1)`, `emporiumMessage2 = Poseidon(seed2)`.
4. Build two `CircomData` structs identical except for `emporiumMessage`/proof, both with `erc20TokenAddresses.length == 0` and identical `externalActionData.externalActionMetadata` (the encoded stack).
5. Re-fund Emporium between calls (simulate re-accumulation) and call `Hinkal.transact` twice.
6. Assert: both calls succeed (`usedMessages[emporiumMessage1]` and `usedMessages[emporiumMessage2]` both become `true`, no revert), and cumulative tokens received by `attacker` equal 2x the per-call drained amount — i.e., `usedMessages[m1] != usedMessages[m2]` (nonce equality broken as "different") while `stack.ops` are byte-identical both times, demonstrating the (ops, message) pairing is not single-use.
