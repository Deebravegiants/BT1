### Title
Intents escrow release uses stored escrow amounts instead of live token balances, causing permanent message-delivery failure for negatively-rebasing tokens - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentsBase._withdraw` releases escrowed intent-order tokens by transferring the amount recorded in the `_orders` mapping at order-placement time, rather than checking what the contract actually holds at release time. If the escrowed token can negatively rebase (balance of all holders, including the gateway contract, decreases without a transfer — e.g. a slashed liquid-staking token), the contract's live balance can fall below the recorded escrow amount by the time the cross-chain `RedeemEscrow`/`RefundEscrow` message is delivered, causing `safeTransfer` to revert deterministically and permanently.

### Finding Description
`_orders[commitment][token]` is populated at `placeOrder` time with the amount actually escrowed (accounting for fee-on-transfer tokens at that instant) [1](#0-0) . Later, when a cross-chain fill is settled, `onAccept` on the source chain decodes the `WithdrawalRequest` and calls `_withdraw`, which unconditionally transfers the *stored* `amount` value via `SafeERC20.safeTransfer`: [2](#0-1) 

This mirrors the reported Superform bug class exactly: a strict comparison/transfer against a value snapshotted at an earlier point in time, with no tolerance for the underlying asset's balance shrinking between snapshot and settlement. For intents, the analogous two-step, time-delayed process is: (1) `placeOrder` escrows and records `amount` on the source chain, and (2) `onAccept`/`_withdraw` releases that exact `amount` on the source chain only after the fill happens on the destination chain and the `RedeemEscrow` message round-trips back through Hyperbridge — a process that is not atomic and can span a meaningful time window (order deadline, proof generation, relay delay).

If the escrowed asset is a negatively-rebasing token (analogous to Pods' `stETHvv`/Lido-slashing scenario cited in the source report), the actual `balanceOf(gateway)` for that token decreases for every holder, including the gateway contract, without any outgoing transfer. Because `_orders[commitment][token]` is never adjusted for this externally-caused balance decrease, `_withdraw`'s `safeTransfer(beneficiary, amount)` call attempts to move more tokens than the contract actually holds, and reverts.

### Impact Explanation
Because `_withdraw` is invoked from `onAccept`, which is itself invoked by the ISMP host when delivering the `RedeemEscrow`/`RefundEscrow` message [3](#0-2) , a revert here means the incoming settlement message can never be successfully delivered. Since the deficit between recorded and actual balance is deterministic (it does not change with retries), every future delivery attempt for that commitment fails identically. This permanently locks:
- The solver's rightful payment for having filled the order on the destination chain (no route exists to ever deliver `RedeemEscrow`), and
- The user's principal on cancellation (`RefundEscrow` fails the same way), since both paths funnel through the same `_withdraw` and the same fixed `_orders[commitment][token]` amount.

This satisfies the "route unable to deliver messages" / "permanent freezing of funds" criteria, and is a High-severity issue for any intents-escrow deployment that lists a rebasing or slashing-capable token as an input asset.

### Likelihood Explanation
Likelihood depends on integrators listing a negatively-rebasing token (e.g., liquid-staking derivatives subject to slashing) as a supported input asset for the Intent Gateway. Unlike the Superform vault case where any ERC4626 vault wrapping a rebasing asset is instantly exposed, here the trigger requires (a) a rebasing token being configured as an intent input, and (b) a negative rebase event occurring within the window between order placement and cross-chain settlement. This is plausible but not guaranteed for every deployment — it is conditional on token choice, similar to the original report's framing ("if the vault's asset suffers a negative rebase").

### Recommendation
In `_withdraw`, clamp the amount actually transferred to `min(recorded amount, IERC20(token).balanceOf(address(this)))`, or better, track and decrement escrow using the live balance delta captured at deposit and re-validate against current balance before transfer, allowing partial settlement or a defined shortfall-accounting path rather than an unconditional revert. Alternatively, expose a per-order "tolerable shortfall" parameter (mirroring the original recommendation) so that a negative rebase reduces the amount delivered rather than blocking delivery of the entire message permanently.

### Proof of Concept
1. A rebasing/slashable ERC20 (e.g., an LST subject to negative rebase) is configured as a valid input token for `IntentGatewayV2`.
2. User calls `placeOrder` on the source chain, escrowing `1000` units; `_orders[commitment][token] = 1000` is recorded based on the balance actually received [1](#0-0) .
3. Solver fills the order cross-chain on the destination chain via `_fillCrossChain`, dispatching a `RedeemEscrow` post request back to the source chain.
4. Before the `RedeemEscrow` message is relayed and delivered, the input token undergoes a 1% negative rebase; the gateway's `balanceOf` for that token drops to `990`.
5. When the relayer delivers the `RedeemEscrow` message, `onAccept` calls `_withdraw`, which attempts `IERC20(token).safeTransfer(solver, 1000)` — this reverts because the contract only holds `990`.
6. Every subsequent delivery attempt for this commitment reverts identically, permanently freezing the solver's payment and blocking settlement of that order.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
