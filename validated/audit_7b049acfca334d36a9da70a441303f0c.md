### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) header is not covered by the HMAC signature, allowing cross-tenant webhook misattribution - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw HTTP body. The `shop-domain`, `topic`, `webhook-id`, and `api-version` fields are read from unauthenticated HTTP headers and are never included in the signed bytes, so the tenant identity handed to the app's webhook handler is not cryptographically bound to the verified payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are all derived from raw, unauthenticated headers instead: [2](#0-1) [3](#0-2) 

`Registry.process` verifies only the HMAC over this body via `HmacValidator.validate`, which computes the signature over `verifiable_query.to_signable_string` (i.e., the body alone): [4](#0-3) [5](#0-4) 

After this check passes, the handler is invoked with `WebhookMetadata` built directly from the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` values: [6](#0-5) 

This breaks the identity binding: `HMAC(body) == valid` is treated as proof that `(body, shop, topic, webhook_id)` as a whole originated from Shopify for that specific shop, when in fact only `body` is authenticated. Concretely: `verified(body) != verified(body, shop)`. Any actor who possesses one valid `(body, hmac)` pair signed with the app's secret (e.g., generated by triggering a webhook on their own development/test store, which they fully control) can resend that exact body and HMAC to the app's webhook endpoint while substituting an arbitrary `shop-domain` header. The HMAC check still passes because it only checks the body bytes, but `Registry.process` now attributes that (attacker-originated) webhook body to a shop the attacker does not own.

### Impact Explanation
This is a cross-tenant identity-binding bypass: the app's webhook handler receives `WebhookMetadata#shop` for one tenant while the actual signed content originated from a different (attacker-controlled) tenant. Depending on how the host app's handler uses `data.shop` (e.g., writing order/customer records, invoking `shop/redact`/`customers/redact` mandatory-topic logic, updating billing or entitlement state keyed by shop), this allows an attacker to inject content into another merchant's tenant data path, or trigger tenant-scoped side effects for a shop they do not control — a cross-tenant access impact, without needing the app's `api_secret_key`, an access token, or any privileged account on the victim shop.

### Likelihood Explanation
Exploitation requires only a genuine `(body, hmac)` pair, which the attacker can trivially obtain by having their own webhook subscription fire on their own store (any developer can create a store and receive real Shopify webhook deliveries signed for their content), then replaying that body+HMAC to the target app's public webhook endpoint with a forged `shop-domain`/`topic`/`webhook-id` header set. No secret key, token, or MITM access is required — only the ability to send an HTTP request to the app's publicly reachable webhook receiver, which is unprivileged-internet-user-reachable by design.

### Recommendation
Include the identity-relevant header values (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable string used for HMAC computation, or otherwise cryptographically bind the shop/topic/webhook-id to the signed payload (e.g., validate them against a signed field inside the body, or require the shop to be corroborated by session/tenant context already known to the app) before dispatching to the handler in `Registry.process`.

### Proof of Concept
1. As an attacker, create a personal Shopify development store and register the app's webhook endpoint for topic `orders/create` (or any topic) to receive a legitimate webhook: this yields a real request with headers `x-shopify-hmac-sha256: <HMAC1>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, and body `B`, where `HMAC1 = HMAC-SHA256(api_secret_key, B)`.
2. Capture `B` and `HMAC1`.
3. Send a new HTTP request to the same app webhook endpoint with the identical body `B` and identical `x-shopify-hmac-sha256: HMAC1`, but change `x-shopify-shop-domain` to `victim-shop.myshopify.com` (and optionally alter `x-shopify-topic`/`x-shopify-webhook-id`).
4. `ShopifyAPI::Utils::HmacValidator.validate` recomputes the HMAC over `B` only (per `Request#to_signable_string`) and it matches `HMAC1`, so `Registry.process` proceeds and calls `handler.handle` with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: parsed(B), ...)` — i.e., attacker-originated content is processed as if it belonged to `victim-shop.myshopify.com`.
