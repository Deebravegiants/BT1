### Title
Potential permanent DoS of bandwidth purchases from decimals underflow in `BandwidthManager.purchase()` - (File: evm/src/apps/BandwidthManager.sol)

### Summary
`BandwidthManager.purchase()` computes a decimal-scaling factor for the host's fee token using a hardcoded assumption that the fee token has at most 18 decimals, exactly mirroring the reported "_marginDecMultiplier" underflow pattern (`18 - decimals`).

### Finding Description
In `purchase()`, the manager reads the fee token from the host and scales the 18-decimal tier price down to the token's native decimals: [1](#0-0) 

`scale = 10 ** (18 - dec)` assumes `dec <= 18`. If `IDispatcher(_host).feeToken()` is ever configured to (or migrated to) a token whose `decimals()` returns a value greater than 18, `18 - dec` underflows a `uint8` subtraction and reverts unconditionally on every call. This is the same root cause as the reported issue: a hardcoded assumption that ERC20 decimals are `<= 18` used directly in a subtraction that feeds an exponent, rather than handling the `> 18` branch (as is done correctly elsewhere in the same file's sibling contract — see `VWAPOracle._normalizeAmount`, which branches on `_decimals > 18` and divides instead of multiplying): [2](#0-1) 

The project's own documentation acknowledges this exact limitation for `BandwidthManager` and treats it as accepted risk rather than a fixed code path: [3](#0-2) 

### Impact Explanation
If the fee token configured on the `IsmpHost` for a given chain has more than 18 decimals, `purchase()` reverts for every caller, permanently freezing the bandwidth-purchase flow for that `BandwidthManager` deployment (an unprivileged user simply calling `purchase()` triggers the revert deterministically). Any app relying on that manager to top up its `pallet-bandwidth` allowance becomes unable to pay for bandwidth via this contract, which can, in turn, cause the app's dispatch gate to block outbound ISMP messages once existing allowance is exhausted — a route rendered unable to deliver messages.

### Likelihood Explanation
Reachability requires the host's `feeToken()` to be a token with `decimals() > 18`. This is not attacker-controlled per-call (it is fixed by the host configuration), so the bug only manifests if/when such a fee token is configured. However, unlike a purely hypothetical admin-misuse scenario, real ERC20 tokens with >18 decimals exist and are exercised elsewhere in this very codebase's test suite (e.g., a 24-decimal token in `VWAPOracleTest.sol`), so the assumption is not universally safe, and the underflow is a pure function-of-state condition triggerable by any ordinary `purchase()` call once such a token is in place — no special privilege is needed to trigger the revert itself.

### Recommendation
Replace the hardcoded `10 ** (18 - dec)` scaling with a branch that handles `dec > 18` by dividing instead of multiplying (mirroring `VWAPOracle._normalizeAmount`), so a high-decimals fee token degrades gracefully (rounding) instead of bricking `purchase()` entirely.

### Proof of Concept
1. Host governance configures (or migrates to) a fee token whose `decimals()` returns `19` or greater.
2. Any user calls `BandwidthManager.purchase(app, tier, months, chain)`.
3. `uint8 dec = IERC20Metadata(feeToken).decimals();` returns `>18`.
4. `10 ** (18 - dec)` underflows the `uint8`/`uint256` subtraction and reverts, making `purchase()` permanently unusable for that manager/fee-token combination, consistent with the underflow pattern described in the external report. [1](#0-0)

```text
    function _normalizeAmount(uint256 amount, uint8 _decimals) private pure returns (uint256 normalized) {
        if (_decimals == 18) {
            return amount;
        } else if (_decimals < 18) {
            return amount * (10 ** (18 - _decimals));
        } else {
            return amount / (10 ** (_decimals - 18));
        }
    }
```

Two implications:

1. **Fee tokens with `decimals > 18` would underflow `(18 - dec)`.** This is not a concern in practice — the supported fee tokens are all `≤ 18` decimals.
2. **Tier prices must be representable at the local fee-token's decimals after multiplication by `months`.** A tier priced at `10**12` (a hypothetical sub-penny SKU) and a 6-decimal fee token would revert with `PriceNotRepresentable()` because the 18-decimal value doesn't divide cleanly. Set tier prices to multiples of `10**12` to keep them clean on 6-decimal fee tokens.
