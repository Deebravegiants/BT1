### Title
Escrow/fee withdrawals in `IntentGatewayV2` (Tron) do not verify the ERC20 `transfer` return value - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2` moves escrowed tokens to beneficiaries and sweeps dust using a raw low-level `.call()` to the ERC20 `transfer` selector, but only checks that the call itself did not revert (`success`). It never decodes/inspects the returned boolean payload. Non-compliant ERC20/TRC20 tokens that return `false` on failure instead of reverting will make the transfer silently fail while the contract still updates escrow accounting and emits success events, permanently locking user funds.

### Finding Description
In `withdraw()` (invoked from `onAccept` for `RedeemEscrow`/`RefundEscrow` requests) and in the `SweepDust` branch of `onAccept`, token payouts use:

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [1](#0-0) 

and the fee redemption uses the same pattern: [2](#0-1) 

and the dust sweep uses the same pattern: [3](#0-2) 

`success` from a low-level `.call()` only reflects whether the callee reverted — it does not validate the ABI-encoded boolean the ERC20 `transfer` function is supposed to return. Many real-world tokens (including the classic BAT/HT/CHSB/cUSDC examples from the referenced report, and numerous TRC20 tokens on Tron that mimic Ethereum's non-standard USDT-style semantics) return `false` on failure instead of reverting. For such tokens, `success` is `true` even though no tokens moved.

Despite the payout failing, the code proceeds to decrement internal accounting and emit success events unconditionally:
```solidity
_orders[body.commitment][token] -= amount;
...
emit EscrowReleased({commitment: body.commitment});
``` [4](#0-3) 

This is the exact bug class from the report: raw ERC20 `transfer` is invoked without checking the returned success flag encoded in the call's return data, matching the original `receiveByEthereumAssetAddress`/`shutDownAndMigrate` weakness. Notably, elsewhere in the same codebase (the standard EVM `IntentGatewayV2.sol` and `IntentsBase.sol`) `safeTransferFrom`/`SafeERC20` is correctly used for inbound transfers, and `safeTransfer` is used in the `WrappedHyperFungibleToken*` contracts, confirming that the Tron variant's raw-call payout path is an inconsistent, unguarded deviation. [5](#0-4) 

### Impact Explanation
This is reachable on the token-bridge/intents settlement path: escrow redemption and refund (`RedeemEscrow`/`RefundEscrow`) are triggered by relayed cross-chain messages that any relayer can deliver once authenticated, and `SweepDust` is dispatched from Hyperbridge governance messages that a relayer still delivers on-chain. When the escrowed token has non-compliant `transfer` semantics, the beneficiary never receives funds, yet the contract deletes/decrements the escrow entry and emits `EscrowReleased`/`EscrowRefunded`/`DustSwept`. The tokens remain stuck in the `IntentGatewayV2` contract with no accounting record left to reclaim them — a permanent freezing of user funds masked as a successful settlement.

### Likelihood Explanation
Likelihood is tied to whether a given escrowed/fee token on Tron has non-standard `transfer` semantics (returns `false` instead of reverting). This is a known, non-rare category of TRC20/ERC20 tokens (the original report identified 4 live examples on Ethereum out of 55 surveyed), so any solver, LP, or user routing an order through such a token via `IntentGatewayV2` on Tron triggers the bug automatically during normal escrow settlement, with no attacker privilege required beyond using/relaying an ordinary order.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` payout patterns in `withdraw()` and the `SweepDust` handler with OpenZeppelin's `SafeERC20.safeTransfer`, which is already imported and used elsewhere in this file (`using SafeERC20 for IERC20;`). This correctly reverts when the call reverts, when it returns `false`, and when a non-standard token returns no data but the call fails logically.

### Proof of Concept
1. Deploy an ERC20-like token on Tron whose `transfer` function returns `false` on failure instead of reverting (e.g., set an internal condition that always returns `false` for a specific `to` address, matching real-world non-compliant tokens like BAT/HT/CHSB/cUSDC on Ethereum).
2. Create and fill an order through `IntentGatewayV2` using this token, resulting in an escrow entry under `_orders[commitment][token]`.
3. Trigger `RedeemEscrow` via `onAccept` so `withdraw()` executes `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))`.
4. Observe: `success == true` (call did not revert) even though `transfer` internally returned `false` and moved no tokens; `_orders[commitment][token] -= amount` executes and `EscrowReleased` is emitted, while `beneficiary`'s token balance is unchanged and the tokens remain stuck in the `IntentGatewayV2` contract with no escrow record left to recover them.
