Based on the code I found, the strongest reachable analog in this gem is in the webhook processing path, where the `shop` identity is trusted from an HTTP header that is not covered by the HMAC signature.

### Title
Webhook shop identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing via replay - ([File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then dispatches the handler using the `shop` value taken from the `X-Shopify-Shop-Domain` header — a field that is never included in the signed material. This breaks the identity binding: `verified(hmac) == body` but `trusted(shop) == header`, and `header ⊄ signed_bytes`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) 

`shop` is parsed independently from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic tie to the body or the HMAC: [3](#0-2) 

`HmacValidator.validate` only calls `to_signable_string`, so it verifies the body bytes, not the shop header: [4](#0-3) 

`Registry.process` checks the HMAC of the body, then immediately trusts `request.shop` as the tenant identity passed to the app's handler: [5](#0-4) 

Because the `shop` field that identifies the tenant is disjoint from the bytes actually covered by the HMAC, any party who legitimately receives one valid signed webhook (e.g., for their own installed shop, using the same app-wide secret for all merchants) can replay that same body+HMAC pair to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header. `HmacValidator.validate` will still pass because the header is not part of `to_signable_string`, and `Registry.process` will hand the attacker-chosen `shop` value straight to the app's `WebhookMetadata`/handler as if it were an authenticated tenant identity.

### Impact Explanation
This is a cross-tenant identity confusion: the library-level API guarantees "this webhook body was signed by Shopify" but does not guarantee "this webhook is scoped to the shop named in the WebhookMetadata." An app that (reasonably, given the gem's contract) trusts `WebhookMetadata#shop` to select which merchant's data/session to update can be made to apply data or trigger side effects under another merchant's identity, without ever needing that merchant's credentials — matching the "cross-tenant access" High/Critical impact category.

### Likelihood Explanation
Any developer/merchant with a legitimate app installation receives real HMAC-signed webhook deliveries for their own shop and fully controls replaying that HTTP request to the app's exposed webhook endpoint with modified headers. No secret, token, or privileged access is required beyond having the app installed on one's own store — an ordinary unprivileged capability.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is authenticated, e.g. include the shop-domain header in `to_signable_string`/the HMAC computation, or independently verify that `request.shop` corresponds to a shop with an active, matching webhook registration/session before invoking the handler, rather than trusting the unauthenticated header value outright.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a legitimate webhook POST with body `B` and valid `X-Shopify-Hmac-Sha256` header `H` (computed by Shopify over `B` with the shared app secret).
2. Attacker resends the same request to the app's public webhook endpoint, keeping body `B` and header `H`, but changes `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and succeeds (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
4. The handler is invoked with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the app to process attacker-controlled data as if it originated from the victim shop.
