### Title
Webhook HMAC only covers the request body, not the `shop-domain`/`topic`/`webhook-id` headers, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`. `HmacValidator.validate` verifies the HMAC solely against this string. But `Registry.process` trusts `request.shop`, `request.topic`, and `request.webhook_id`, which are pulled straight from the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, and `X-Shopify-Webhook-Id` HTTP headers, none of which are part of the signed material. The binding the gem is supposed to enforce — `hmac(secret, payload) → (shop, topic)` — is broken because `shop` is not an input to the HMAC.

### Finding Description
- `to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`) signs `@raw_body` exclusively.
- `shop`, `topic`, `webhook_id`, and `api_version` (`lib/shopify_api/webhooks/request.rb:15-33`) are read from headers via `shopify_header`, entirely outside HMAC coverage.
- `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-22`) only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)` — i.e., the body-derived signature.
- `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) accepts the request once the body HMAC checks out, then builds `WebhookMetadata` using the unauthenticated `request.shop`/`request.topic`/`request.webhook_id`, and dispatches it to the handler as if it came from that shop. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

An unprivileged internet user who can obtain one legitimate `(raw_body, hmac)` pair for any shop — trivially achievable by installing the app on their own free/dev shop and capturing a webhook their own store legitimately triggers — can then POST that exact `raw_body` with the same `hmac` value to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` will hand the handler `WebhookMetadata` claiming this data originated from the victim shop, even though the app's `api_secret_key` was never known to the attacker and the actual webhook never touched that shop's data.

### Impact Explanation
This breaks the identity binding "shop authenticated == shop the app believes it received data for," which is a cross-tenant confusion: an attacker can make the host application process attacker-supplied (or replayed) content under a false shop identity. Depending on what the host `WebhookHandler` does with `data.shop` (e.g., writing to a per-shop database record keyed by `WebhookMetadata#shop`, triggering shop-scoped side effects, or invalidating/mutating another tenant's cached data), this can result in cross-tenant data corruption or information disclosure — matching the High-severity "cross-tenant access" criterion, since no access token, `api_secret_key`, or privileged credential of the target shop is required.

### Likelihood Explanation
Likelihood is realistic: obtaining a legitimate `(body, hmac)` pair only requires installing the app on any shop the attacker controls (free to do, no special privilege), and HTTP header spoofing to an app's public webhook endpoint requires no authentication at all. The only constraint is that the replayed body's content must make sense to the target handler; many webhook payloads (e.g., generic app/uninstall or product topics with attacker-controlled shop data) are usable as-is.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed material used for verification, or otherwise cryptographically bind them to the payload before dispatching to `WebhookHandler#handle`. At minimum, `to_signable_string` should incorporate the shop domain so `HmacValidator.validate` fails when the header is altered relative to what Shopify actually signed.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker-shop.myshopify.com` and receives a legitimate webhook delivery with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker sends a POST request to the app's webhook endpoint with the same body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` whose `hmac` returns the decoded `H` and whose `shop` returns `"victim-shop.myshopify.com"`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only compares `H` against `HMAC-SHA256(api_secret_key, B)` — unaffected by the spoofed shop header.
5. `Registry.process` builds `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)` and calls the registered handler, which now processes attacker-supplied content believing it is authoritative data from `victim-shop.myshopify.com`.
