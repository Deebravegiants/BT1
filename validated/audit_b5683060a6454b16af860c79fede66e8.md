### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signature exclusively over the raw request body (`to_signable_string` returns `@raw_body`), while the tenant identifier (`shop`) used downstream is read from the `x-shopify-shop-domain` / `shopify-shop-domain` header, which participates in no cryptographic binding whatsoever.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking `Utils::HmacValidator.validate(request)`, which recomputes an HMAC over `request.to_signable_string` (the raw JSON body) and compares it to the `hmac` extracted from the `x-shopify-hmac-sha256` header: [4](#0-3) 

The `shop` accessor, however, is derived purely from a separate, unsigned header: [5](#0-4) 

Once HMAC validation passes, `Registry.process` builds `WebhookMetadata` using this unauthenticated `request.shop` value and calls the app's registered handler with it: [6](#0-5) 

This breaks the intended identity binding: `shop-value-verified-by-HMAC == shop-value-delivered-to-handler`. In reality, the HMAC only proves "this body was signed with the app's client secret at some point for some shop"; it says nothing about which shop the body belongs to. Because the app's `client_secret` is shared across all shops that install the app (it is not shop-specific — only the value put into the signed payload differs), any two webhook deliveries signed for the same app (e.g., one for the attacker's own trial/dev shop and one destined for a victim shop) use the same secret. Documentation confirms `shop` is treated as the authoritative shop identity passed to host applications for tenant-scoped work: [7](#0-6) 

An attacker who controls their own Shopify store and has the target app installed on it can capture a legitimately-signed webhook delivery for their own shop (raw body + valid HMAC), then replay that exact body/HMAC pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. Because the header is not part of the signed content, the HMAC check still succeeds, and the host application's handler receives `data.shop` equal to the victim's domain alongside attacker-controlled `data.body`. Any host logic that uses `data.shop` to select the tenant record, database row, or session to act on (exactly as shown in the gem's own documented usage pattern) will attribute/act on the wrong shop's data — a cross-tenant boundary break driven entirely by gem-level logic, not a misuse of an undocumented API.

### Impact Explanation
This qualifies as cross-tenant access (Critical): a request cryptographically proven only to have originated from *some* installation of the app can be relabeled to impersonate *any other* shop that has the app installed, as long as the attacker controls the `shop-domain` header value sent to the app's endpoint. Depending on the webhook topic (e.g., `customers/redact`, `shop/redact`, `app/uninstalled`, `orders/create`), this can lead to unauthorized data deletion, data injection, or state changes attributed to a shop the attacker does not control.

### Likelihood Explanation
The attacker only needs a development/trial store with the target app installed (a normal, unprivileged step available to any internet user through the Shopify App Store install flow) to obtain a validly-HMAC'd body for at least one topic. No access to `api_secret_key`, tokens, or the victim's credentials is required — only the ability to observe one legitimate webhook delivery for their own shop and replay it with a modified header to the public webhook endpoint.

### Recommendation
Bind the shop identity to the signed payload: either include the shop domain (and other identifying headers) in `to_signable_string` so it is covered by the HMAC, or independently verify that `request.shop` corresponds to a shop with an existing, valid session/access token before invoking the handler. Shopify's own guidance is to treat the webhook body's HMAC as validating the pairing of body-and-declared-shop together, not the body alone.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives (or triggers) a webhook, e.g. `orders/create`, with body `B` and headers including `x-shopify-hmac-sha256: H` (valid for `B` under the app's `client_secret`) and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker POSTs to the app's webhook endpoint with the same body `B`, the same `x-shopify-hmac-sha256: H`, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over `B` only and it matches `H`, so validation succeeds.
4. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) invokes the app's handler with `WebhookMetadata` where `shop == "victim-shop.myshopify.com"` and `body` is attacker-controlled, despite the victim never having sent this webhook.
