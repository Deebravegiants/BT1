## Finding: Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing

### Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` metadata are trusted without being bound to the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw HTTP body via HMAC, while `shop`, `topic`, `webhook_id`, and `api_version` are read from unauthenticated headers and passed straight through to the app's webhook handler. Because these fields are not covered by the signature, an attacker who legitimately owns one Shopify store can capture their own genuinely-signed webhook (valid body + HMAC) and replay it to the app's webhook endpoint with a forged `shopify-shop-domain` header pointing at a victim shop. The signature check still passes because it only validates the body, letting the attacker impersonate the victim tenant to the handler.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

All the tenant-identifying metadata (`shop`, `topic`, `webhook_id`, `api_version`) is pulled from headers that are never mixed into the signable string: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which calls `to_signable_string` (body-only) and compares against the secret-derived signature: [3](#0-2) 

After the HMAC check succeeds, `Registry.process` forwards the unauthenticated `request.shop` value directly into `WebhookMetadata`, which the host app's handler uses to decide which tenant's data to act on: [4](#0-3) 

The equality the code implicitly assumes is: `hmac_valid(body) == request_is_authentically_from(shop_header)`. This is false — `hmac_valid(body)` only proves the body bytes were signed by the shared secret at some point (for some webhook, for any shop the attacker controls), it says nothing about which shop the current request headers claim.

### Impact Explanation
For webhook topics whose payload is generic/shop-independent (e.g. `app/uninstalled` which is `{}` as shown in this repo's own tests, `shop/redact`, etc.), the body content is identical across all shops. This means a legitimate, validly-signed webhook captured by an attacker who owns/installs the app on their own store (which they can freely do) can be replayed against the app's webhook endpoint with the `shopify-shop-domain` header rewritten to a victim's shop domain. `Utils::HmacValidator.validate` still returns `true` because it never inspects the header. The host app's handler — which trusts `WebhookMetadata#shop` to select the tenant to act on (uninstall cleanup, data redaction, deprovisioning, etc.) — will act on the victim's tenant data instead of the attacker's own. This is a cross-tenant action performed without the victim's authorization, i.e., cross-tenant access/tenant impersonation triggered purely by an unprivileged internet user who controls only their own store and can send arbitrary HTTP requests.

### Likelihood Explanation
Reaching this requires no privileged credentials, no access token, and no knowledge of the app's `client_secret`: the attacker only needs to install the target app on a store they control (a normal, unprivileged action) to receive one genuinely-signed webhook with a shop-independent payload, then replay it with a different `shopify-shop-domain` header value. The code path (`Registry.process` → `HmacValidator.validate` → handler) makes no additional check that ties the signed body to the shop header, so the replay succeeds deterministically for any topic with shop-independent bodies.

### Recommendation
Bind the tenant-identifying headers into the signed material, or independently verify that the `shop` header corresponds to a shop with an active installation/session before dispatching to the handler. At minimum, `Registry.process` should cross-check `request.shop` against a known/authorized shop list (e.g., an existing stored session for that shop) rather than trusting the header solely because the body's HMAC is valid.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering Shopify to send a real `app/uninstalled` webhook: body `{}`, with a valid `x-shopify-hmac-sha256` computed by Shopify over that body, as reflected in this repo's test fixtures: [5](#0-4) 
2. Attacker captures that request and re-sends the same raw body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` recomputes the HMAC over the (unchanged) body and it matches, so validation passes.
4. `Registry.process` invokes the app's registered handler with `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim-shop.myshopify.com", ...)`, causing the host app to perform uninstall/cleanup logic against the victim shop's tenant data — data the attacker never had access to and never authorized.
