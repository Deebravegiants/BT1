Audit Report

## Title
Cross-Workflow HTTP Response Cache Collision Due to Missing WorkflowID in Cache Key - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

## Summary
The gateway's outbound HTTP action response cache (`responseCache.Fetch`/`Set`) keys cached responses solely by `OutboundHTTPRequest.Hash()`, which excludes `WorkflowID` from the hash computation while including `WorkflowOwner`, `Method`, `URL`, `Headers`, and `Body`. This contradicts the package's own README, which explicitly documents "Cache Key: Generated from workflow ID and request hash" and "Workflow Isolation: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage," allowing two different workflows under the same owner to collide on cache entries and receive each other's cached HTTP responses.

## Finding Description
`responseCache.Fetch` and `Set` in `core/services/gateway/handlers/capabilities/v2/response_cache.go` use `req.Hash()` as the sole cache key: <cite repo="Alyssadaypin/chainlink--019" path="core/services/gateway/handlers/capabilities/v2/response_cache.go" start="66-67" end="66-67" />, and [1](#0-0) . The struct comment itself states the hash is derived from "method, URL, headers, body, workflowOwner" — `WorkflowID` is absent: [2](#0-1) .

The package's own test suite explicitly confirms this behavior: identical requests differing only by `WorkflowID` produce the same hash, while identical requests differing only by `WorkflowOwner` produce different hashes: [3](#0-2) [4](#0-3) .

This directly contradicts the documented invariant in the handler's README, which states the cache key is "Generated from workflow ID and request hash" and that cache entries are "scoped by workflow ID to prevent cross-workflow data leakage": [5](#0-4) .

The cache is populated/consumed in `gatewayHandler.makeOutgoingRequest`, invoked for every outbound-HTTP-action request originating from a workflow node, using attacker/workflow-controlled `Method`, `URL`, `Headers`/`MultiHeaders`, and `Body` fields, with caching enabled whenever `CacheSettings.MaxAgeMs > 0` or `Store: true`: [6](#0-5) . No code path re-introduces `WorkflowID` binding before the cache lookup/store, so two distinct workflows belonging to the same `WorkflowOwner` that issue HTTP action requests with identical method/URL/headers/body but different `WorkflowID` will collide on the same cache entry and receive each other's previously fetched response instead of a fresh, workflow-scoped result.

## Impact Explanation
This breaks the documented workflow-isolation guarantee of the response cache, causing cross-workflow response corruption: one workflow's fetched HTTP data (which may be execution-specific, environment-specific, or contain differing parameters intended per-workflow) can be silently served to a different workflow under the same owner, or vice versa. Since HTTP action outputs can feed subsequent workflow logic and on-chain execution, this is a concrete "cross-user/cross-workflow response corruption" issue in the sense used by the bounty scope, even though it is scoped to workflows sharing the same owner (the isolation boundary the code and docs both claim to provide but the code fails to enforce).

## Likelihood Explanation
The flaw is triggerable via the normal, unprivileged outbound-HTTP-action request path (`gatewayHandler.HandleNodeMessage` → `makeOutgoingRequest`) with no privilege escalation, malicious node, or host access required — only that two workflows under the same owner issue outbound HTTP requests with matching method/URL/headers/body and `CacheSettings.MaxAgeMs > 0` or `Store: true`, both of which are ordinary, expected configuration for HTTP action caching. This is easily reproducible and repeatable, as confirmed directly by the existing unit test `TestRequestHash`'s "having different workflowID results in same Hash" subtest.

## Recommendation
Include `WorkflowID` in `OutboundHTTPRequest.Hash()` (in the `chainlink-common` package where `Hash()` is implemented) so cache entries are correctly scoped per workflow as documented. Add a regression test asserting different `WorkflowID` values produce different hashes (inverse of the current assertion in `response_cache_test.go`), and audit any other cache/dedup logic relying on `Hash()` for the same gap.

## Proof of Concept
1. Workflow A (owner `0xabc`, `WorkflowID = wf-A`) issues an outbound HTTP action: `GET https://api.example.com/data`, `CacheSettings{MaxAgeMs: 60000, Store: true}`. The gateway fetches and caches the response keyed by `req.Hash()` (method+URL+headers+body+workflowOwner, no workflowID).
2. Workflow B (same owner `0xabc`, `WorkflowID = wf-B`) issues an identical request (`GET https://api.example.com/data`, same headers/body, `CacheSettings.MaxAgeMs > 0`).
3. `responseCache.Fetch` for Workflow B computes the same `cacheKey` as Workflow A's stored entry (per `response_cache_test.go`'s "having different workflowID results in same Hash" test) and returns Workflow A's cached response to Workflow B without executing a fresh HTTP call — directly demonstrating the cross-workflow cache collision described in `core/services/gateway/handlers/capabilities/v2/response_cache_test.go` lines 139-149.

	requestID := resp.ID
	h.lggr.Debugw("handling outgoing message", "requestID", requestID, "nodeAddr", nodeAddr)
	var req gateway_common.OutboundHTTPRequest
	err := json.Unmarshal(*resp.Result, &req)
	if err != nil {
		return fmt.Errorf("failed to unmarshal HTTP request from node %s: %w", nodeAddr, err)
	}
	timeout := time.Duration(req.TimeoutMs) * time.Millisecond
	httpReq := network.HTTPRequest{
		Method:           req.Method,
		URL:              req.URL,
		Headers:          req.Headers, //nolint:staticcheck // forward deprecated Headers for backward compatibility; request uses MultiHeaders when set
		MultiHeaders:     req.MultiHeaders,
		Body:             req.Body,
		MaxResponseBytes: req.MaxResponseBytes,
		Timeout:          timeout,
	}

	sendResponseTimeout := time.Duration(defaultSendResponseTimeoutMs) * time.Millisecond

	// send response to node async
	h.wg.Go(func() {
		// not cancelled when parent is cancelled to ensure the goroutine can finish
		baseCtx := context.WithoutCancel(ctx)
		httpCtx, httpCancel := context.WithTimeout(baseCtx, timeout)
		defer httpCancel()
		l := logger.With(h.lggr, "requestID", requestID, "method", req.Method, "timeout", req.TimeoutMs)
		var outboundResp gateway_common.OutboundHTTPResponse
		callback := h.createHTTPRequestCallback(httpCtx, requestID, httpReq, req)
		if req.CacheSettings.MaxAgeMs > 0 {
			h.metrics.IncrementCacheReadCount(ctx, h.lggr)
			outboundResp = h.responseCache.Fetch(httpCtx, req, callback, req.CacheSettings.Store)
		} else {
			outboundResp = callback()
			if req.CacheSettings.Store {
				h.responseCache.Set(req, outboundResp)
			}
		}
