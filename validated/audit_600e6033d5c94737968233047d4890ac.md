### Title
Webhook HMAC only signs the request body, not the `shop-domain` header, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` but its `to_signable_string` returns only `@raw_body`, while the identity fields `shop`, `topic`, `webhook_id`, and `api_version` are read straight from unauthenticated HTTP headers. `Registry.process` validates only the body-derived HMAC and then dispatches the handler using the unauthenticated `shop` value as the tenant identifier, breaking the binding `shop_verified_by_hmac == shop_used_for_tenant_scoping`.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

and `hmac` / `shop` are pulled from separate headers that are never mixed into that signable string: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC purely over `to_signable_string` (i.e., the raw body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` uses this same validation and then forwards the **unauthenticated** `request.shop` value straight to the app's handler as the tenant identifier: [4](#0-3) 

Because the signature only binds the body bytes, the `shop-domain` header (and `topic`/`webhook_id`) can be freely modified by anyone who can produce one authentic `(body, hmac)` pair — which any merchant with the app installed on their own store legitimately receives from Shopify. Swapping the `shop-domain` header on a byte-for-byte-identical body/HMAC pair keeps the signature valid while causing the receiving app to attribute the webhook payload to a different, attacker-chosen shop.

This mirrors the reported bug class: a field that is acted upon by application logic (`shop`, used as the tenant key) is not covered by the same integrity check that guards the rest of the payload (the HMAC), so trust in one implies unwarranted trust in the other.

### Impact Explanation
An attacker who controls a legitimate installation of the app (their own store) can obtain a valid `(raw_body, hmac)` pair from Shopify's genuine webhook delivery, then replay that exact body/HMAC to the app's webhook endpoint with a forged `x-shopify-shop-domain` (or `shopify-shop-domain`) header naming a victim shop. `Registry.process` accepts the request as authentic and calls the handler with `shop: <victim shop>`, causing the host application to process attacker-controlled data under another tenant's identity — a cross-tenant confusion/injection that can corrupt or leak per-shop data depending on how the handler uses `data.shop`.

### Likelihood Explanation
Likelihood is high for any attacker who can install the app on their own store (a normal, unprivileged action), since no secret material beyond a routine webhook delivery is required, and no other check in the gem cross-validates `shop` against the signed body or against a known/registered session for that shop.

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signable content that the HMAC validates, or otherwise cryptographically bind them to the payload, instead of trusting them as independent, unauthenticated inputs to `Registry.process`.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`; Shopify sends a legitimate webhook:
   - Headers: `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid hmac of body>`
   - Body: attacker-controlled order JSON (attacker can shape this by creating orders in their own store).
2. Attacker resends this exact `(body, hmac)` pair to the app's webhook endpoint, but replaces the header with `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` in `Registry.process` (`lib/shopify_api/webhooks/registry.rb:190`) succeeds because the HMAC only covers `@raw_body`, which is unchanged.
4. The handler executes with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON>, ...)`, causing the host app to treat attacker-controlled data as belonging to the victim tenant.
