## Title
Webhook HMAC only covers the raw body, allowing the `shop`, `topic`, `api_version`, and `webhook_id` metadata to be forged — cross-tenant webhook spoofing (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the `X-Shopify-Hmac-Sha256` signature authenticates the payload bytes but never binds the `shop`, `topic`, `api-version`, or `webhook-id` values that `Registry.process` extracts from unauthenticated HTTP headers and hands to the app's handler. This is the same defect class as the reported "Register Same Operators" issue: a value the code trusts and acts on (here, the shop/topic identity of a webhook) is not covered by the integrity check that is supposed to bind it (the HMAC), so an attacker can present that value freely while keeping the signature valid.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it against the `hmac` field: [1](#0-0) 

For webhooks, `Request#to_signable_string` is defined as just the raw body: [2](#0-1) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers that are outside the signed content: [3](#0-2) 

`Registry.process` validates the HMAC and then dispatches to the handler using these unauthenticated header values as the identity of the event: [4](#0-3) 

The binding the code assumes is:
`shop attested by HMAC == shop used to route/process the webhook`

but in reality:
`shop attested by HMAC == "" (HMAC covers only raw_body)` while `shop used to route/process the webhook == unauthenticated X-Shopify-Shop-Domain header`.

Shopify signs webhooks with the app's single shared `client_secret`, not a per-shop secret, so any (body, hmac) pair that is valid for one shop installing this app is valid for every shop the app is installed on. An attacker who controls their own store with the same app installed can capture a legitimate `(raw_body, hmac)` pair from their own webhook deliveries, then replay that exact body/hmac to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, `X-Shopify-Webhook-Id`, or `X-Shopify-Api-Version` headers with attacker-chosen values. `HmacValidator.validate` still passes because the signature check never inspects these headers.

### Impact Explanation
This breaks the tenant boundary the HMAC is meant to enforce: an attacker can make the host application believe a webhook body originated from any shop, on any topic, of their choosing, while the HMAC still validates. Depending on how the host application's handler uses `WebhookMetadata#shop`/`#topic` (e.g., to look up per-shop state, fulfil orders, update inventory, or trigger data sync), this enables cross-tenant data injection/confusion — attacker-controlled webhook content is attributed to and processed against a victim shop's context. This matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation only requires the attacker to have the app installed on their own store (a normal, unprivileged action for any merchant who can install a public/embedded app) so they can capture genuine `(body, hmac)` pairs signed with the app's shared `client_secret`, then replay them with modified headers to the same public webhook endpoint. No access token, `api_secret_key`, or privileged account is required.

### Recommendation
Include the identity fields (`shop-domain`, `topic`, `api-version`, `webhook-id`) in the HMAC-covered signable string, or otherwise cryptographically bind them (e.g., compute the signature over a canonical string built from these headers plus the raw body) so that `HmacValidator.validate` fails if any of those headers are altered relative to what Shopify actually sent.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook delivery with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(client_secret, B)`).
2. Attacker replays a request to the app's webhook endpoint with the same body `B` and same header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and/or `X-Shopify-Topic: <different-topic>`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` builds a request object; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(client_secret, B)` — identical to `H` — and returns `true`. [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker-chosen `topic`, even though neither value was ever verified by the signature.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
