### Title
Hardcoded single-fee-tier Uniswap V3 pool in `UniV3UniswapV2Wrapper` used as `EvmHost`'s fee-swap router causes suboptimal/failing native-fee-to-feeToken swaps on every dispatch - (File: evm/src/utils/uniswapv2/UniV3UniswapV2Wrapper.sol)

### Summary
`EvmHost.dispatch()`/`fundRequest()`/`HyperApp.quote()` swap native token for the ISMP `feeToken` through whatever address `_hostParams.uniswapV2` points to. On chains where a real Uniswap V2 pool for the fee token isn't available, Hyperbridge deploys `UniV3UniswapV2Wrapper`, which adapts the `IUniswapV2Router02` interface onto Uniswap V3 by hardcoding a single, immutable `maxFee` pool tier (`evm/script/DeployUniV3Wrapper.s.sol:20-28`) for *every* WETH↔feeToken swap and quote, mirroring the exact bug class described in the external report (single hardcoded `poolFee` for all swaps).

### Finding Description
`UniV3UniswapV2Wrapper.Params.maxFee` is a single `uint24` fee tier set once at `init()` and used unconditionally for both `exactOutputSingle`/`exactInputSingle` swap calls and for `getAmountsIn`/`getAmountsOut` quotes: [1](#0-0) [2](#0-1) 

This wrapper is deployed specifically to be registered as the host's `uniswapV2Router` config value: [3](#0-2) 

Every unprivileged caller who dispatches a POST/GET request or funds a pending request with native `msg.value` on `EvmHost` triggers a swap through this fixed pool: [4](#0-3) [5](#0-4) 

`HyperApp.quote()`, used by every app built on the SDK to estimate the native fee for a dispatch, also unconditionally routes through this same single-tier pool: [6](#0-5) 

As in the referenced report, liquidity for a given token pair is frequently concentrated in a different Uniswap V3 fee tier than whichever one was picked at deployment time (and can migrate over time as liquidity providers rebalance). Because `maxFee` is immutable per-wrapper-instance and there is no fallback or on-chain check of which tier is actually liquid, every dispatch/fund/quote call is forced through a single, potentially illiquid or nonexistent pool.

### Impact Explanation
- If the hardcoded fee tier's pool has thin liquidity relative to other tiers, every native-fee payer suffers excess slippage on `dispatch()`/`fundRequest()`, directly losing funds compared to routing through the most liquid tier — an unprivileged, unavoidable value leak on the base message-dispatch path.
- If the hardcoded tier's pool does not exist on that chain (e.g., liquidity later migrates entirely to another tier, or was never deployed for that tier), `exactOutputSingle`/`exactInputSingle` calls revert unconditionally, meaning `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest` all become permanently unusable for native-token fee payers on that host — a denial of the core dispatch functionality for an entire class of unprivileged callers, since there is no governance path in this contract to add a fallback tier without a full redeploy and reconfiguration of `_hostParams.uniswapV2`.
- `HyperApp.quote()` inherits the same single-tier dependency, so third-party apps built with the SDK also mis-price or fail to quote the native cost of dispatching messages.

### Likelihood Explanation
Any user calling `dispatch()`/`fundRequest()` with `msg.value > 0` on a host configured with `UniV3UniswapV2Wrapper` triggers this path — no privileged role is required. Fee-tier liquidity distribution shifting away from the deployed `maxFee` value is a normal, expected market condition (as demonstrated by the referenced report's real-world examples), making the suboptimal-routing case highly likely over time, and the total pool-drain/removal case plausible on lower-liquidity chains.

### Recommendation
Do not hardcode a single fee tier for the wrapper's lifetime. Either (a) query the Uniswap V3 factory for all standard fee tiers (100/500/3000/10000) and select the pool with the greatest on-chain liquidity/reported price at swap time (as already done correctly for off-chain price/quote helpers elsewhere in the repo, e.g. `sdk/packages/sdk/src/utils/swap.ts`'s `getBestV3Pool`), or (b) allow governance to update/add supported fee tiers on the wrapper without requiring a full host reconfiguration, with a safe fallback path if the primary tier's pool disappears.

### Proof of Concept
1. Deploy `UniV3UniswapV2Wrapper` with `maxFee = 3000` (0.3%) for a WETH/feeToken pair per `DeployUniV3Wrapper.s.sol`, and register it as `EvmHost`'s `uniswapV2` config.
2. Over time, liquidity providers migrate liquidity for that pair predominantly into the `500` (0.05%) tier, leaving the `3000` tier with materially less liquidity (directly analogous to the WETH/USDC vs. WETH/wBTC tier examples in the source report).
3. Any user calling `EvmHost.dispatch(DispatchPost)` with `msg.value` now executes `swapETHForExactTokens` against the increasingly illiquid `3000` tier, paying materially more ETH than necessary for the same `post.fee` output — or, if liquidity is fully withdrawn from that tier, the `multicall`/`exactOutputSingle` call reverts, making native-fee dispatch permanently impossible until the wrapper is redeployed and reconfigured.

    function deploy() internal override {
        address swapRouter = config.get("SWAP_ROUTER").toAddress();
        address quoter = config.get("QUOTER").toAddress();
        uint24 maxFee = uint24(config.get("MAX_FEE").toUint256());
        address uniswapV2 = IDispatcher(HOST_ADDRESS).uniswapV2Router();

        UniV3UniswapV2Wrapper wrapper = new UniV3UniswapV2Wrapper{salt: salt}(admin);
        wrapper.init(
            UniV3UniswapV2Wrapper.Params({
                WETH: IUniswapV2Router02(uniswapV2).WETH(), swapRouter: swapRouter, quoter: quoter, maxFee: maxFee
            })
        );
        vm.stopBroadcast();
        console.log("UniV3UniswapV2Wrapper deployed at:", address(wrapper));
        console.log("UniV3UniswapV2Wrapper initialized");
        // Persist the deployed wrapper address into the UNISWAP_V2 config field.
        config.set("UNISWAP_V2", address(wrapper));
    }
