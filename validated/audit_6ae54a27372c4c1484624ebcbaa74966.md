This confirms a real, already-known-and-labeled ("M-02") bug class that is a direct analog to the report's core pattern: **an attacker pre-creates/pre-seeds a resource before the legitimate process finalizes it, and the legitimate process is forced to trust/consume whatever was pre-placed there**, exactly mirroring the `managed-settings.json` pre-creation issue.

### Title
Budget-capped hostile mint pre-seed forces `finalizeGraduation` to lock protocol LP materially off curve-close price - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.finalizeGraduation` is permissionless and must create/seed the HyperSwap V2 `TOKEN/LT` pair for a graduating token [1](#0-0) . Any unprivileged address can front-run this by calling the HyperSwap factory's permissionless `createPair`, transferring an extreme, skewed `(TOKEN, LT)` ratio to the pair, and calling `pair.mint(attacker)` before `finalizeGraduation` runs, exactly as demonstrated in the repo's own `test_brick_resistance_frontRun_dust_seed` and `_grieferMintPreSeed` helpers [2](#0-1) . The protocol's rebalance defense (`_seedRebalancing` / `_pairRebalance`) caps the corrective swap at `_swapBudget`, i.e. ~99% of `tokensForLP` or `ltFromPair` [3](#0-2) . For a sufficiently lopsided pre-seed (e.g. LT-rich by ~200x), the swap needed to restore the curve-close ratio exceeds this budget, so the corrective swap cannot fully rebalance the pool before `_routerDepositAndDispose` deposits the remaining inventory.

### Finding Description
`finalizeGraduation` must never revert ("brick resistance ranks above price integrity" per the protocol's own design docs) [4](#0-3) . This means that when an attacker pre-seeds the HyperSwap pair with a ratio extreme enough to exceed the swap budget, `finalizeGraduation` proceeds anyway and permanently locks the resulting mispriced LP into `LPLock` via `LPLock.recordLock`, a one-shot call `finalizeGraduation` cannot skip [5](#0-4) . The repository's own regression test `test_hostilePreSeed_budgetCappedSwap_isNotProfitable` (referred to internally as "M-02") confirms the pool opens at more than 20% off the curve-close price for a 200x LT-rich seed [6](#0-5) .

This is a structural analog of CWE-426 (Untrusted Search Path): just as Claude Code trusted a config file placed in a shared, unprivileged-writable location before the legitimate process created it, `Bonding.finalizeGraduation` trusts (i.e. builds its permissionless canonical liquidity pool on top of) whatever pre-existing reserve ratio an unprivileged attacker manages to place in the permissionless, pre-creatable HyperSwap pair — with only a bounded corrective mechanism that a sufficiently large pre-seed can defeat.

### Impact Explanation
While the pre-seeding attacker's own residual LP position is proven net-negative by the test suite (P&L ≤ 0, per `_lpValueAtCurveClose` vs `_depositValueAtCurveClose` assertions), the rule set explicitly scopes "an LP seeded away from the curve close price" as a standalone valid impact independent of attacker profitability. The protocol-owned, permanently-locked LP (held in `LPLock` with no withdraw path in v1) opens materially mispriced, meaning:
- Every subsequent trader/holder of the launched token trades against a pool priced away from the true curve-close value until arbitrage closes the gap, transferring value out of the protocol-locked LP position to arbitrageurs.
- Because `LPLock.recordLock` is one-shot and `LPLock` has no rescue mechanism, this mispricing (and the value bled to arbitrageurs during convergence) cannot be corrected or recovered by the protocol post-hoc.

### Likelihood Explanation
The precondition is cheap and fully permissionless: `factory.createPair`, an ERC20 `transfer` of a skewed ratio, and `pair.mint(attacker)` — all reachable from a single unprivileged wallet with no special role, timed to land between phase 1 (`_enterGraduating`) and phase 2 (`finalizeGraduation`) of any graduating token. The repo's own test confirms a 200x-skewed seed is sufficient to exceed the swap budget and produce a >20% price gap.

### Recommendation
Given brick-resistance is treated as the higher-priority invariant by design, consider widening the per-side swap budget (or making it iterative/multi-pass) so it can correct larger pre-seed ratios before falling back to a fixed cap, or add a secondary post-deposit arbitrage-in-same-tx step so the locked LP always opens within a tight bound of curve-close regardless of the initial hostile ratio's magnitude.

### Proof of Concept
See `test_hostilePreSeed_budgetCappedSwap_isNotProfitable` in `packages/contracts/test/TwoPhaseGraduation.t.sol` (lines 864-917), which reproduces the exact scenario: griefer pre-seeds a 1%/200x skewed ratio, `finalizeGraduation` succeeds but the pool opens at >1.2x the curve-close price, confirmed by the assertion `assertGt(_poolPriceLtPerToken(...), (((ltFromPair * 1e18) / tokensForLP) * 12) / 10, "M-02 regime: pool opens materially off curve-close")` [7](#0-6) .
