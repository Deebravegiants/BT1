### Title
Floor-rounded `Router._computeSell` overpays LT to sellers with no real-balance cap, risking pair insolvency and DoS - ([File: packages/contracts/src/Router.sol])

### Summary
`Router._computeSell` derives `assetOut` by floor division (`k / newReserveToken`), which systematically rounds the LT payout to the seller *up*, not down, unlike `Router._computeBuy`'s cap logic (which explicitly ceil-rounds `amountInUsed` "in favour of the protocol"). Unlike `buy()`, which caps `tokensOut` against the pair's real token balance before paying out, `sell()` has no analogous check against the pair's real LT (`assetToken`) balance before calling `transferAsset`. Because the pair's `assetReserve` is partly virtual (seeded with zero real LT at `mint`, per `Router.addInitialLiquidity`), a floor-rounding-driven overpayment can exceed the LT actually held by the pair, causing `transferAsset`'s `safeTransfer` to revert and DoS the trade — the same failure mode the external report describes for Eggs Finance.

### Finding Description
In `packages/contracts/src/Router.sol`:

```solidity
function _computeSell(
    address pairAddr,
    uint256 amountIn
) internal view returns (uint256 assetOut) {
    IPair pair = IPair(pairAddr);
    (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
    uint256 k = pair.k();

    uint256 newReserveToken = reserveToken + amountIn;
    assetOut = reserveAsset - (k / newReserveToken);
}
``` [1](#0-0) 

`k / newReserveToken` floors, so the subtracted term is smaller than the exact value, meaning `assetOut` is rounded **up** — the seller is paid slightly more LT than the constant-product curve would exactly yield. Compare this to `_computeBuy`'s cap branch, which explicitly documents "rounded up so the curve never under-charges" and computes `cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken` — a deliberate ceil-div used only to make sure the *protocol* is never shortchanged on the input side: [2](#0-1) 

Critically, `Router.sell` never checks the pair's real LT holdings before paying out:
```solidity
function sell(uint256 amountIn, address token, address to) external onlyRole(BONDING_ROLE) returns (uint256 tokensIn, uint256 assetOut) {
    ...
    IERC20(token).safeTransferFrom(to, pairAddr, amountIn);
    assetOut = _computeSell(pairAddr, amountIn);
    IPair(pairAddr).transferAsset(to, assetOut);
    IPair(pairAddr).swap(amountIn, 0, 0, assetOut);
}
``` [3](#0-2) 

This is asymmetric with the buy path, which explicitly caps `tokensOut` at `pair.tokenBalance()` — the real, transferable token supply — specifically because "the virtual token reserve runs above the sellable balance" [4](#0-3) . No equivalent cap exists for `assetOut` against `pair.assetBalance()`.

The root cause of the asymmetry is that the LT-side reserve is *also* virtual at launch: `Router.addInitialLiquidity` calls `IPair(pairAddr).mint(virtualReserveToken, reserveAsset)` while only transferring `realTokenAmount` of the launched token into the pair — no LT is transferred in at mint time, so `reserveAsset` starts as a purely virtual figure: [5](#0-4) 

`Pair.swap`'s K-invariant check only guards against decreasing `K` beyond a `+1` slack; it does not enforce that `assetOut` stays within the pair's real LT balance:
```solidity
function swap(uint256 tokenIn, uint256 tokenOut, uint256 assetIn, uint256 assetOut) external onlyRouter returns (bool) {
    uint256 newTokenReserve = (_pool.tokenReserve + tokenIn) - tokenOut;
    uint256 newAssetReserve = (_pool.assetReserve + assetIn) - assetOut;
    if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated();
    ...
}
``` [6](#0-5) 

`Pair.transferAsset` is a plain `safeTransfer`, which will revert if the pair doesn't actually hold `assetOut` in real LT: [7](#0-6) 

So every sell rounds the LT payout up by up to 1 wei relative to the exact curve inverse of the corresponding buy, and this happens with no floor check against real balance. Because the virtual LT component of `reserveAsset` was never actually deposited, the *only* real LT the pair ever holds is what buyers deposited via `Router.buy`'s `amountInUsed`. Repeated buy/sell round trips (or a single large drain-to-zero sell by the last remaining holder) can push the cumulative rounding-up overpayment on the sell side past the real LT the pair actually holds, because nothing in `sell()`/`_computeSell()`/`Pair.swap` checks `assetOut <= pair.assetBalance()`.

### Impact Explanation
If the accumulated rounding-up overpayment on sells exceeds the real LT balance remaining in the pair (which shrinks to a thin margin as the curve is drained toward graduation, or in adversarial sequences of tiny buys/sells designed to accumulate rounding drift), the final seller's `Router.sell` call reverts inside `Pair.transferAsset`'s `safeTransfer` due to insufficient balance. This locks that holder's tokens (already `safeTransferFrom`'d into the pair before the revert would need to be checked, though the whole tx reverts atomically so tokens aren't lost) but permanently DoSes their ability to exit the curve — mirroring the underlying report's "last user attempts to close their position ... insufficient sonic in the system ... causing a DoS." This affects any unprivileged trader attempting `Bonding.sell` / `Zap.sell` on an under-collateralized pair.

### Likelihood Explanation
The rounding drift per trade is bounded at 1 wei of LT (18-decimals), so triggering a meaningful, exploitable shortfall requires either an extremely large number of round trips or specific edge-of-drain conditions where the real LT margin is already thin. This is a low-magnitude-per-trade issue, and I could not fully verify, within the scope of this pass, whether the pair's real LT margin ever gets thin enough in practice (e.g., near `previewLtUntilGraduation`'s cap-binding buys, which are carefully ceil-rounded per the code comments) for a 1-wei-per-trade drift to actually surface as a reachable revert. The codebase shows deliberate, extensive ceil-rounding "in favor of the protocol" everywhere else (`Router._computeBuy`'s cap branch, `Bonding.previewLtUntilGraduation`'s USD-leg and supply-leg ceil-divs, `Zap._executeBuy`'s `Math.mulDiv(..., Math.Rounding.Ceil)` fee calc), strongly suggesting the team is aware of and has systematically hardened against this exact bug class — `_computeSell` appears to be the one remaining unhardened conversion, but I cannot confirm from static analysis alone that the accumulated drift is large enough, under realistic trade volumes, to actually cause an observed insolvency revert in production before a token graduates.

### Recommendation
Round `assetOut` in `_computeSell` down (floor) in favor of the pair, mirroring the report's core recommendation ("if we're computing an amount for a user to receive, we should round down"), e.g. via `Math.mulDiv(k, 1, newReserveToken, Math.Rounding.Ceil)` on the subtracted term so `assetOut` is never more generous than the exact curve value. Additionally, cap `assetOut` at `pair.assetBalance()` in `Router.sell`, symmetric to the existing `tokensOut` cap against `pair.tokenBalance()` in `_computeBuy`, so a sell can never attempt to pay out more real LT than the pair holds.

### Proof of Concept
Conceptual sequence (cannot be executed without terminal/test access in this pass):
1. Launch a token via `Bonding` with the standard virtual-LT-seeded pair (`Router.addInitialLiquidity` with `reserveAsset` fully virtual, no real LT transferred in).
2. Have trader A `buy` a token amount, depositing real LT `amountInUsed` into the pair (rounded up in `_computeBuy`, so the pair is very slightly under-collateralized relative to the reserves it tracks even at this step).
3. Have trader A immediately `sell` the same token amount back. `_computeSell` floors `k/newReserveToken`, rounding `assetOut` up, paying trader A very slightly more real LT than was deposited in step 2.
4. Repeat steps 2–3 (or perform a single large drain-to-zero sell as the last holder) enough times, or structure amounts so that the floor/ceil interplay compounds, until the pair's real `assetBalance()` is smaller than the `assetOut` computed by `_computeSell` for the next sell.
5. That sell's `Pair.transferAsset` call reverts due to insufficient LT balance, DoSing the seller. [1](#0-0) [3](#0-2) [8](#0-7)

    /// @dev Capped: `amountInUsed` is back-calculated from the K invariant
    ///      (rounded up so the curve never under-charges).
    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }
