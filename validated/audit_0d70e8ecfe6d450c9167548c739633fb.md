### Title
`DeleteAccount`'s `beneficiary_id` is not verified to reference an existing account, causing balance-refund receipts to be silently burned - ([File: runtime/runtime/src/actions.rs])

### Summary
The external report describes `SingleStrategyController.migrate()` moving funds to a new strategy without verifying the new strategy is compatible, so funds become permanently unaccounted for. The closest reachable analog in nearcore is the `DeleteAccountAction`: an unprivileged account can delete itself and redirect its remaining balance to an arbitrary `beneficiary_id`, but the protocol only validates that `beneficiary_id` is a syntactically well-formed `AccountId` — it never checks that the target account actually exists. If it doesn't, the balance-refund receipt fails and the tokens are burned instead of being credited anywhere.

### Finding Description
`action_delete_account` unconditionally queues a refund receipt for the account's remaining balance to `delete_account.beneficiary_id`, with no existence check on that account: [1](#0-0) 

The only validation performed on `DeleteAccountAction` at admission time is that `beneficiary_id` parses as a valid `AccountId` (per `docs/RuntimeSpec/Actions.md`), not that the account exists on chain: [2](#0-1) 

The generated refund is a `Receipt::new_balance_refund`, which is executed later as a system-predecessor ("refund") receipt. When that receipt's `Transfer` action targets a non-existent, non-implicit account, `check_account_existence`/`check_transfer_to_nonexisting_account` rejects it, because implicit-account creation is explicitly disabled for refund receipts ("Refunds don't automatically create accounts, because refunds are free and we don't want some type of abuse"): [3](#0-2) 

Critically, when any receipt with `predecessor_id == "system"` (i.e., a refund receipt) fails, the runtime does **not** re-refund or bounce the funds anywhere — it burns them: [4](#0-3) 

This is the direct structural analog of the reported bug: an action that moves a balance to a second party (`beneficiary_id` / new strategy) without validating that the destination can actually receive/track it, resulting in permanent loss of the transferred value.

### Impact Explanation
Any account holder can lose their own remaining NEAR balance by submitting a `DeleteAccount` action with a `beneficiary_id` that is syntactically valid but does not correspond to an existing account (e.g., a typo, a account that was itself deleted between transaction construction and execution, or one that was never created). Instead of the transaction being rejected or the funds returned to the sender, the balance silently vanishes from total supply via `other_burnt_amount`. This is a concrete, unrecoverable token-loss bug reachable purely from a normal user transaction — no validator or node-operator privilege is required — though the loss is generally self-inflicted (own balance) rather than theft from a third party, similar to how the original report frames it as an owner/operator mistake rather than an attacker-controlled exploit.

### Likelihood Explanation
Reachability is trivial: `DeleteAccount` is a standard, unprivileged action available to any signer with full-access permission on their own account, and `beneficiary_id` is fully attacker/user-controlled with only a format check. The scenario of specifying a nonexistent beneficiary is easy to trigger accidentally (typo, race condition where the beneficiary account is deleted concurrently, or intentionally to grief oneself), making this readily reachable, though the "victim" is normally the same account performing the deletion.

### Recommendation
Before generating the balance-refund receipt in `action_delete_account`, verify that `beneficiary_id` currently exists (or is a valid implicit-account id capable of auto-creation), and reject the `DeleteAccount` action (returning an execution error rather than proceeding) if it does not. Alternatively, allow refund receipts targeting nonexistent-but-syntactically-valid named accounts to bounce back to the original account owner (or a well-defined fallback) instead of unconditionally burning the balance on refund failure.

### Proof of Concept
1. Create account `alice.near` with a nonzero balance and a full-access key.
2. Submit a transaction from `alice.near` containing a single `DeleteAccount { beneficiary_id: "nonexistent123456789.near" }` action, where `nonexistent123456789.near` is a syntactically valid but never-created account id.
3. Observe execution: `action_delete_account` removes `alice.near` and queues `Receipt::new_balance_refund(beneficiary_id, account_balance)` [1](#0-0) .
4. The refund receipt executes with `predecessor_id = "system"`; because it targets a nonexistent, non-implicit account and implicit-account creation is disabled for refunds, the receipt's `Transfer` action fails with `AccountDoesNotExist`.
5. Because the failing receipt has a system predecessor, its deposit is added to `other_burnt_amount` rather than refunded anywhere [4](#0-3) , permanently removing `account_balance` from circulation.

This test pattern is directly comparable to the existing test `test_refund_on_send_money_to_non_existent_account`, which demonstrates a normal `Transfer` to a nonexistent account is safely refunded to the sender — but the `DeleteAccount` beneficiary path lacks the equivalent safety net, since it is itself already the refund mechanism. [5](#0-4)
