### Title
Vetoing the latest EVM state-machine height resets the height tracker to `1` instead of the real previous height, reopening the monotonic-height gate to stale/lower state commitments - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.deleteStateMachineCommitmentInternal` resets `_latestStateMachineHeight[stateMachineId]` to the constant `1` whenever the vetoed height equals the currently recorded latest height, instead of restoring it to the actual previously-verified height (as the Substrate `pallet-ismp` implementation correctly does via `PreviousStateMachineHeight`). This desynchronizes the height "accounting" from the real verified state, exactly analogous to the referenced Xen CVE's root cause: an unmapping/removal operation is performed while the surrounding accounting (page-table/latest-height bookkeeping) is not kept in sync with what is actually valid.

### Finding Description
`EvmHost.sol` tracks, per counterparty state machine, the latest height for which a state commitment has been accepted: [1](#0-0) 

`HandlerV2.setConsensusState`/consensus update path only ever stores a new intermediate state commitment when its height is strictly greater than the currently recorded latest height: [2](#0-1) 

`storeStateMachineCommitment` (called only by the handler) always advances `_latestStateMachineHeight` to whatever height was just stored, assuming monotonicity: [3](#0-2) 

The veto/delete path, restricted to the handler and invoked when a fisherman/collator veto message is relayed from Hyperbridge, does the following: [4](#0-3) 

When the vetoed height is the currently recorded latest height, `_latestStateMachineHeight` is reset to the *literal constant* `1`, not to the actual prior verified height. Contrast this with the equivalent Substrate-side logic in `pallet-ismp`, which correctly restores `LatestStateMachineHeight` to a tracked `PreviousStateMachineHeight`: [5](#0-4) 

Because `HandlerV2`'s only gate against re-accepting stale/rolled-back state is `intermediate.height > latestHeight`, resetting `latestHeight` to `1` means that after any veto of the latest height, the very next consensus/message-relay transaction from *any unprivileged relayer* can re-introduce a state commitment for **any height greater than 1** — including heights that are lower than, or different from, the legitimately superseded height, and including stale/forked/previously-invalidated state roots that a correct "previous height" restoration would have continued to reject. This breaks the intended monotonic-height invariant that `state_machine_commitment`/membership-proof verification relies on to guarantee freshness and non-replay of state roots used for message delivery, receipt verification, and fund-release checks (`stateMachineCommitment`, `HandlerV2.handlePostRequests`, outbound-claim receipt proofs, etc., all key off `_stateCommitments[id][height]` and `latestStateMachineHeight`).

### Impact Explanation
Any relayer message that triggers `EvmHost.deleteStateMachineCommitmentInternal` for the currently-latest height (a legitimate, protocol-sanctioned veto forwarded from Hyperbridge's `pallet-fishermen`) leaves the EVM host's height accounting permanently desynchronized from truth (pinned at `1` rather than the real prior height). This is reachable purely through the normal message-relaying path (`HandlerV2`/`EvmHost.dispatchIncoming`) by any unprivileged relayer forwarding the veto message — no admin/governance/malicious-collator action is required beyond the ordinary, protocol-supported veto flow. Once the height is pinned at `1`, the monotonicity check in `HandlerV2.setConsensusState` (`intermediate.height > latestHeight`) becomes trivially satisfiable by almost any height, letting a relayer resubmit or accept out-of-order/stale state commitments for the affected chain. Downstream, `handlePostRequests`, `handleGetResponses`, and the outbound-request-claim receipt-proof verification all trust `stateMachineCommitment(height)`/`latestStateMachineHeight` to reflect a monotonically advancing, non-replayable view of the counterparty chain — so an attacker able to also influence which state roots get accepted (e.g., timing another consensus update around a veto, or exploiting a chain reorg on the counterparty) could get a stale or otherwise invalid state root re-admitted, enabling forged message delivery, incorrect receipt/membership proofs, or unsound acceptance of an already-superseded state commitment. This qualifies as unsound state commitment handling / a potential forged message delivery vector.

### Likelihood Explanation
Vetoing the latest height is a supported, expected part of Hyperbridge's fisherman/collator safety mechanism (any single collator can veto, and any relayer forwards this veto to the EVM host) — it is not a rare or attacker-controlled-only precondition. The desync happens automatically and silently every time this ordinary flow vetoes the current latest height; no privileged or malicious actor needs to intentionally trigger the bug, only the ordinary veto path needs to run once. The remaining exploitation step (getting an attacker-favorable stale/rolled-back commitment accepted afterward) depends on additional conditions on the counterparty chain and relayer submission timing, which lowers full-exploit likelihood but the state corruption itself is high-likelihood and automatic.

### Recommendation
Track the previous verified height per state machine on `EvmHost` (mirroring `pallet-ismp`'s `PreviousStateMachineHeight`) and restore `_latestStateMachineHeight[id]` to that value in `deleteStateMachineCommitmentInternal` instead of hardcoding `1`, so the monotonic-height invariant consumed by `HandlerV2` remains sound after a veto of the latest height.

### Proof of Concept
1. Handler stores state commitments for heights `H1 < H2` on `EvmHost` for state machine `S` (via `HandlerV2.setConsensusState`), so `latestStateMachineHeight(S) == H2`.
2. Hyperbridge's `pallet-fishermen::veto_state_commitment` vetoes height `H2` (a single collator call, no proof required) — this is forwarded and delivered to the EVM host as a `deleteStateMachineCommitment(height=H2, fisherman)` call via the handler.
3. `EvmHost.latestStateMachineHeight(S)` is now `1` (not `H1`).
4. Any relayer submits a subsequent consensus update containing an intermediate state for height `H1' `where `1 < H1' <= H1` (a height that should have been rejected as stale/already-superseded/potentially rolled back) — `HandlerV2`'s check `intermediate.height > latestHeight` (`1`) passes, and `EvmHost.storeStateMachineCommitment` accepts and overwrites the tracked "latest" state for `S` with this stale height, corrupting the monotonic state-commitment ordering that downstream message/receipt verification depends on.     /**
     * @dev Delete the state commitment at given state height.
     */
    function deleteStateMachineCommitmentInternal(StateMachineHeight memory height, address fisherman) internal {
        StateCommitment memory stateCommitment = _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitmentsUpdateTime[height.stateMachineId][height.height];
        // technically any state commitment can be vetoed, safety check that it's the latest before resetting it.
        if (_latestStateMachineHeight[height.stateMachineId] == height.height) {
            _latestStateMachineHeight[height.stateMachineId] = 1;
        }

        // track the fisherman responsible for rewards on hyperbridge through state proofs
        _vetoes[height.stateMachineId][height.height] = fisherman;

        emit StateCommitmentVetoed({
            stateMachineId: this.stateMachineId(_hostParams.hyperbridge, height.stateMachineId),
            stateCommitment: stateCommitment,
            height: height.height,
            fisherman: fisherman
        });
    }

	fn delete_state_commitment(&self, height: StateMachineHeight) -> Result<(), Error> {
		// The height's entry in the state commitment queue is deliberately left
		// behind; locating it would mean scanning the queue, which is the per-insert
		// cost the queue exists to avoid. Usually its eviction is a no-op, but when
		// the vetoed height is the latest the reset below re-opens it for honest
		// resubmission, and the resubmitted height gets a *second* queue entry. The
		// stale entry then evicts the live commitment when it reaches the head —
		// one insertion before the live entry would have, since the resubmission
		// lands directly behind its stale twin. So a veto costs that height one
		// insertion of retention and permanently burns one queue slot. Both are
		// negligible against the configured caps; making it exact would need a
		// height -> index map on the insert path.
		BoundedStateCommitments::<T>::remove(height.id, height.height);
		BoundedStateMachineUpdateTime::<T>::remove(height.id, height.height);

		// technically any state commitment can be vetoed,
		// safety check that it's the latest before resetting it.
		if let Some(latest) = LatestStateMachineHeight::<T>::get(height.id) {
			if latest == height.height {
				// Reset back to the initial height to allow for honest updates
				let prev_height =
					PreviousStateMachineHeight::<T>::get(height.id).ok_or_else(|| {
						Error::Custom("Previous state machine height should exist".to_string())
					})?;
				LatestStateMachineHeight::<T>::insert(height.id, prev_height);
			}
		}
		Ok(())
	}
