## Finding [1](#0-0) 

### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value that gets forwarded to app webhook handlers from the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) HTTP header, but the HMAC signature that `Registry.process` verifies is computed only over the raw request body. The `shop`, `topic`, `webhook-id`, and `api-version` headers are never part of the signed material, so any request with a valid `(body, hmac)` pair — which any shop that has installed the app can legitimately generate, since the API secret is shared across all shops for a given app — can be replayed with an arbitrary `shop` header value and will still pass validation.

### Finding Description
`Registry.process` gates handler execution solely on `Utils::HmacValidator.validate(request)`: [2](#0-1) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`: [3](#0-2) 

For `Webhooks::Request`, `to_signable_string` is defined as just the raw body: [1](#0-0) 

Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from unauthenticated headers: [4](#0-3) 

After the HMAC check passes, `shop` is handed to the app's handler as trusted tenant identity: [5](#0-4) 

The binding that should hold is: *the shop the HMAC was computed for* == *the shop the handler acts on*. Because the header is outside the signed bytes, this equality is never enforced — the HMAC only proves "this body was created with the app's secret," not "this body/topic came from shop X." Since the API secret key is the same for every shop that installs a given app, an attacker who controls (or has previously installed the app on) *any* shop can capture one legitimate `(raw_body, hmac)` pair from their own store's webhook delivery and resend it with the `shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` will still succeed (it never looks at the header), and the handler will receive `WebhookMetadata` claiming to be from the victim shop.

### Impact Explanation
This breaks the tenant boundary between shops sharing one app installation: a handler that looks up per-shop session/access-token records keyed by `data.shop` (the normal integration pattern documented for `WebhookMetadata`) can be tricked into acting on behalf of, or writing attacker-controlled data into, a different merchant's records — a cross-tenant access/data-integrity issue reachable by any user who can get one webhook delivered to their own store.

### Likelihood Explanation
Any developer/merchant account that can install the app on their own shop can trigger a real webhook (e.g. by placing an order, editing a product) and capture the resulting `(body, X-Shopify-Hmac-Sha256)` pair from their own endpoint logs/replay tooling, then resend it with a modified `X-Shopify-Shop-Domain` header. No access token, client secret, or privileged access to the victim shop is required.

### Recommendation
Bind the trusted shop identity to something that is part of the verified data, not an unauthenticated header:
- Prefer deriving shop identity from a per-shop session/lookup keyed by the mandatory webhook topic + a value that Shopify signs (Shopify does not sign headers for HTTP webhook delivery, so apps must not treat `shop`/`topic` headers as authenticated on their own).
- At minimum, document/require that `WebhookMetadata#shop` must be cross-checked against an app-side registry of installed shops before being trusted for authorization decisions, and consider including topic/shop in an app-level secondary integrity check (e.g., verifying the webhook id against Shopify's Admin API for the claimed shop) before acting on high-impact data.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers any webhook (e.g. `orders/create`), capturing the delivered `raw_body` and `X-Shopify-Hmac-Sha256` header — both valid under the app's shared `api_secret_key`.
2. Attacker resends the exact same `raw_body`/HMAC to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `raw_body` against the HMAC — it succeeds.
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)` and processes it as if it genuinely originated from `victim-shop`, even though `victim-shop` never sent it. [2](#0-1)
