Confirmed. The withdraw() function in the Tron IntentGatewayV2 does exactly the pattern described in the report: it checks that the low-level `.call` did not revert, but never inspects the ABI-decoded boolean return value of `transfer()`. Combined with escrow accounting being decremented before the transfer attempt (and deleted for fees), a token that returns `false` on failure without reverting causes the protocol to believe the payout succeeded while the underlying asset stays trapped in the contract with `_orders[commitment][token]` already zeroed — permanently freezing the beneficiary's escrowed funds since the same commitment can never be withdrawn again (`revert UnknownOrder()` guard on the next attempt).

### Title
Unchecked ERC20 boolean return value in `IntentGatewayV2.withdraw()` permanently freezes escrowed/fee funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`withdraw()`, reached from `onAccept` (cross-chain `RedeemEscrow`/`RefundEscrow` settlement) and `onGetResponse` (cancellation-from-source settlement), pays out escrowed tokens using a raw low-level `.call` to `IERC20.transfer` and only checks that the external call did not revert, never decoding/asserting the boolean success value the ERC20 standard returns.

### Finding Description
`withdraw()` performs token payouts like this: [1](#0-0) 
and for the transaction-fee payout: [2](#0-1) 

`token.call(...)` only reports whether the external call itself reverted; it does not decode the `(bool)` return data that `IERC20.transfer` is supposed to return. Any ERC20/TRC20 implementation that returns `false` on failure instead of reverting (a well-known non-standard-but-common token behavior, especially relevant on the Tron/TRC20 ecosystem this file targets) will make `success == true` even though no tokens moved. Notably, the contract *does* import and alias `SafeERC20` (`using SafeERC20 for IERC20;`) and uses `safeTransferFrom`/proper checks elsewhere in the same contract for escrow deposits, but deliberately reverts to unchecked raw calls specifically in the payout path (`withdraw`) and in `SweepDust`: [3](#0-2) 

Critically, the escrow accounting is mutated regardless of whether the transfer actually delivered value: [4](#0-3) 
`_orders[commitment][token]` is decremented (and `TRANSACTION_FEES` deleted) unconditionally after the unchecked call "succeeds" at the call level. Since the next attempt to withdraw the same commitment/token reverts with `UnknownOrder()` once the balance hits zero, there is no retry path — the tokens remain stuck inside `IntentGatewayV2` forever if the underlying token silently failed.

### Impact Explanation
This is reachable by any relayer delivering a legitimate settlement message (`RedeemEscrow`/`RefundEscrow` via `onAccept`, or a cancellation GET response via `onGetResponse`) — no privileged role is required to trigger the payout path; the only requirement is that one of the escrowed input tokens (or the configured fee token) is a non-standard ERC20 that returns `false` on failure. Under that condition, the beneficiary (user or solver) loses their entire escrowed amount or accrued fee permanently, since the accounting is already zeroed and cannot be re-claimed — a classic freezing-of-funds bug matching the reported bug class.

### Likelihood Explanation
Likelihood depends on whether any escrowed input token or the configured `feeToken` behaves non-standardly (return false instead of revert). This is a realistic condition on Tron, where TRC20 tokens (e.g., historically USDT-TRC20 style contracts) are known to deviate from strict ERC20 semantics, and the gateway accepts arbitrary tokens specified by users in `Order.inputs`/`Order.output.assets`. Given the contract already uses `SafeERC20` elsewhere in the same file, this looks like an inconsistency introduced specifically in the payout path.

### Recommendation
Replace the manual low-level `.call` + `TransferFailed()` pattern in `withdraw()` (lines 702-708, 716-723) and in `SweepDust` (lines 670-676) with `IERC20(token).safeTransfer(beneficiary, amount)` (the contract already has `using SafeERC20 for IERC20;` in scope), which correctly reverts both on a failed call and on a `false` boolean return, and does so *before* any escrow-accounting mutation is finalized.

### Proof of Concept
1. User places a cross-chain order with an input token `T` that implements `transfer` to return `false` on failure (e.g., insufficient contract balance, blacklist, or paused state) instead of reverting — this is legal per the actual EIP-20 spec's return value, only non-standard in that most tokens choose to revert instead.
2. Solver fills the order on the destination chain and dispatches `RedeemEscrow`.
3. On the source chain, Hyperbridge delivers the settlement to `onAccept`, which calls `withdraw(body, false)`.
4. Inside `withdraw`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `success = true` (the call did not revert) even though token `T`'s internal logic returned `false` and moved no balance.
5. `_orders[commitment][token] -= amount` proceeds, zeroing the escrow record.
6. The beneficiary never received the tokens, and any retry of `withdraw` for the same commitment/token now reverts with `UnknownOrder()` — the escrowed tokens are permanently stuck in `IntentGatewayV2`.
