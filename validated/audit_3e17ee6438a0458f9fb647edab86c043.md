### Title
Webhook `shop-domain` and `topic` headers are trusted for tenant routing without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then hands the caller (`handler.handle`) a `WebhookMetadata` struct built from the `shop-domain`, `topic`, and `webhook-id` HTTP headers — none of which are included in the signed payload.

### Finding Description
`Registry.process` performs identity/authenticity checks like this: [1](#0-0) 

The only authenticity check is `Utils::HmacValidator.validate(request)`, which computes the HMAC over `request.to_signable_string`: [2](#0-1) 

`to_signable_string` returns only `@raw_body`, never the headers. Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` — the very fields the handler uses to identify *which tenant/topic* the event belongs to — are pulled directly and unauthenticated from headers: [3](#0-2) 

The equality the gem should enforce is: `shop header used for tenant dispatch == shop cryptographically bound to the signed payload`. Instead the gem enforces only `HMAC(body, secret) == received_hmac`, with `shop` (and `topic`/`webhook_id`) verified against nothing. Anyone who can obtain one legitimate `(body, hmac)` pair for the app (e.g., a merchant who installs the app on their own store and receives a real webhook) can replay that exact body+hmac to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. `HmacValidator.validate` still returns `true` (it never looks at the header), and `Registry.process` forwards a `WebhookMetadata` claiming to be from that arbitrary shop: [4](#0-3) 

This is the exact bug class from the analog report (M-3): a value used downstream in place of an authenticated one is not covered by the same integrity check that legitimizes the request.

### Impact Explanation
Any host application that uses `WebhookMetadata#shop` for tenant-scoped operations (looking up the correct merchant's session/store record, updating per-shop data, honoring `shop/redact`/`customers/redact` compliance webhooks, etc.) can be tricked into performing that action against a different shop than the one that produced the signed body — cross-tenant data confusion/access, driven entirely by attacker-controlled headers with a replayed, unrelated signed body. This satisfies the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Requires only that the attacker has legitimately received (or can otherwise obtain) one valid `(raw_body, hmac)` pair issued by the target app to any account (their own store, or a public/predictable webhook payload) — no possession of `api_secret_key` or any credential of the app is needed. HTTP headers are trivially attacker-controlled on an unauthenticated public webhook endpoint. Exploitability is bounded by whether the host application relies on `WebhookMetadata#shop`/`#topic` for authorization decisions, which is the documented, expected usage pattern of this method.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the value that is HMAC-verified (e.g., include them in `to_signable_string`, or require the host application to independently verify that `request.shop` corresponds to a shop with an active installation/session before trusting it), so that a replayed body cannot be paired with attacker-chosen header values.

### Proof of Concept
1. App receives a legitimate webhook for `attacker-shop.myshopify.com` with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC_SHA256(secret, B)`.
2. Attacker resends the same `B`/`H` to the app's webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` and finds it equals `H` — validation passes, since header values are never part of the signable string.
4. `Registry.process` dispatches to the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: parsed(B), ...)`, causing the host app to act as if the event legitimately originated from `victim-shop`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
