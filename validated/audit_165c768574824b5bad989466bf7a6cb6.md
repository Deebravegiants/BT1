### Title
Webhook shop/topic identity is not covered by the HMAC signature, allowing cross-tenant webhook impersonation - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw request body against the app's `api_secret_key`. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values — which `ShopifyAPI::Webhooks::Registry.process` uses to identify *which tenant* the event belongs to and which handler to invoke — are taken straight from unauthenticated HTTP headers and are never included in the signed string. Any unprivileged actor who can obtain one valid (body, HMAC) pair signed with the app's shared secret (e.g. by installing the app on their own free/dev store and capturing a genuine webhook) can replay that body with a forged `shop-domain`/`topic` header claiming to be any other merchant, and the HMAC check will still pass.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The tenant/topic identity fields are pulled from headers that are excluded from that signed string: [2](#0-1) 

`HmacValidator.validate` only ever checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e. against the raw body alone for `Request` objects: [3](#0-2) 

`Registry.process` performs exactly that body-only check and then unconditionally trusts `request.shop`/`request.topic`/`request.webhook_id` to build `WebhookMetadata` and dispatch to the app's handler: [4](#0-3) 

Because the app's `api_secret_key` is shared across *all* shops that install the app, and only the body bytes are bound to the signature, the "shop this event is for" and "topic acted on" values are effectively unauthenticated attacker-controlled input once a single valid signed body is obtained. This is the exact bug class flagged by the report: a field that is acted upon (`shop`, used to select which tenant's stored session/access token and business logic to run) is not covered by the integrity check (HMAC), so the code's internal bookkeeping ("this webhook is from shop X") silently diverges from reality ("the signed bytes only prove *some* installer of this app sent this body").

### Impact Explanation
This breaks the identity binding `shop authenticated (by valid HMAC) == shop the handler acts on (header value)`. An attacker who legitimately installs the app on a shop they control receives real, validly-signed webhook bodies for that shop. They can then submit that exact body to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) header changed to name a different merchant. `Registry.process` will accept it (body HMAC still matches) and hand `WebhookMetadata` with the forged `shop`/`topic` to the app's handler. Any handler logic that looks up the victim shop's stored session/access token or performs shop-scoped side effects (e.g. GDPR/compliance webhooks, order/customer sync, app-uninstalled cleanup) keyed off `data.shop` will now execute using attacker-controlled event content but the victim's tenant context — a cross-tenant identity confusion.

### Likelihood Explanation
Exploitability only requires the ability to install the target app on any shop (trivial via a free Shopify dev/partner store) to obtain one valid (body, HMAC) pair, plus the ability to send an arbitrary HTTP POST with custom headers to the app's public webhook endpoint. No access token, `client_secret`, or privileged account is required. This is a straightforward analog to the report's "count says one thing, ground truth says another" bug class, mapped onto this gem's own webhook verification code rather than the host app's business logic.

### Recommendation
Bind the tenant-identifying fields into the verified signature surface, or otherwise cryptographically/contractually tie `shop`, `topic`, and `webhook_id` to the signed payload before they are exposed to handler code:
- At minimum, document and/or enforce in `Registry.process` that `request.shop` must be cross-checked against the caller's own session store of installed shops before dispatch (fail closed if unknown).
- Prefer including the shop domain and topic in the signable string used by `HmacValidator`, matching upstream Shopify's guidance that consuming apps should independently verify the shop identity of inbound webhooks rather than trusting headers implicitly.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (free dev store), triggering Shopify to send a legitimate webhook, e.g. `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(app_secret, B)`.
2. Attacker captures `(B, H)`.
3. Attacker POSTs to the victim app's webhook endpoint with:
   - Body: `B` (unchanged, so the signature remains valid)
   - Header `X-Shopify-Hmac-Sha256: H` (unchanged)
   - Header `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (forged)
   - Header `X-Shopify-Topic: orders/create` (attacker's choice)
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `HMAC(app_secret, B) == H`, per [5](#0-4) .
5. The registered handler for `orders/create` is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, per [6](#0-5) , even though the event never originated from `victim-shop.myshopify.com`.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
