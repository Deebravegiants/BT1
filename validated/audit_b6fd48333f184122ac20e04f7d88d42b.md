### Title
Cross-tenant webhook impersonation via unauthenticated `shop-domain` header not bound to HMAC - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates only the raw request body via HMAC, but then trusts the `shop-domain` header — a value that is never included in the HMAC computation — to identify which merchant/tenant the webhook belongs to. Because the app's `client_secret` (and therefore the HMAC key) is shared across every shop that installs the app, anyone who installs the app on their own store can capture a genuinely valid `(body, hmac)` pair and replay it to the app's webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header, causing the host application to process the payload as if it originated from a victim shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` (and `topic`, `webhook_id`, `api_version`) is read straight from an HTTP header and is never fed into the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC solely over `verifiable_query.to_signable_string`, i.e. only the body, using `OpenSSL.secure_compare`: [3](#0-2) 

`Registry.process` checks that HMAC and then immediately forwards the unauthenticated `request.shop` header value to the host application's handler as the authoritative tenant identifier, with no cross-check that the shop matches the entity that actually produced the signed body: [4](#0-3) 

The identity binding that should hold is:
`shop-domain header == shop that produced the HMAC-signed body`

but the gem only proves:
`HMAC(body, client_secret) == received_hmac`

Because `client_secret` is a single, app-wide secret shared by every store that installs the app (not a per-shop secret), the HMAC does not bind the body to a specific shop. An unprivileged internet user can:
1. Install the target app on a store they control (e.g. a free development store), which is a normal, unprivileged action available to any developer/merchant.
2. Trigger or passively receive a legitimate webhook delivery to their own endpoint — its body and `X-Shopify-Hmac-Sha256` header are valid because they were generated by Shopify using the app's real `client_secret`.
3. Replay that exact `(raw_body, hmac header)` pair to the target application's webhook endpoint, but substitute the `X-Shopify-Shop-Domain` header with the victim's shop domain.
4. `HmacValidator.validate` succeeds because the body/HMAC pair is genuinely valid; `Registry.process` then calls `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` with `shop` set to the victim's domain, even though the payload content actually originated from the attacker's own store.

This lets the attacker inject content under the identity of a shop they do not own — e.g. a forged `shop/redact`, `customers/data_request`, `app/uninstalled`, or `orders/create` webhook attributed to a victim shop — breaking the tenant isolation the host application relies on `WebhookMetadata#shop` to enforce.

### Impact Explanation
This is a cross-tenant identity/data-binding bypass: the gem hands the host application a `shop` value that was never cryptographically tied to the signed payload, allowing an unprivileged user (any app installer) to make webhook data appear as though it belongs to a different, victim shop. Depending on how the host application uses `WebhookMetadata#shop` (compliance actions like data erasure, billing/plan updates, uninstall handling, order/customer record writes keyed by shop), this can lead to cross-tenant data corruption, spoofed compliance actions against a shop the attacker doesn't control, or state confusion between tenants — matching the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is realistic but requires two preconditions that are still within the "unprivileged internet user" threat model: (1) the attacker installs the app on a store they control — apps are typically installable by anyone in Shopify's app ecosystem, and (2) the attacker can send arbitrary HTTP requests to the app's publicly reachable webhook endpoint with custom headers, which is trivial. No access token, `api_secret_key`, or privileged credential of the victim is required — only a body/HMAC pair the attacker legitimately received for their own tenant.

### Recommendation
Bind the shop identity to the HMAC-verified content rather than trusting an unauthenticated header:
- Include the shop domain (and ideally topic/webhook id) inside the signable string that `HmacValidator` verifies, or
- Cross-validate `request.shop` against the shop embedded in the webhook body payload (Shopify webhook bodies typically include the resource/shop context), rejecting the request if they disagree, and
- Document to consuming applications that `WebhookMetadata#shop` must not be treated as cryptographically authenticated on its own.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a store they control).
2. Shopify sends a legitimate webhook to the app's endpoint:
   - Headers: `X-Shopify-Topic: customers/data_request`, `X-Shopify-Hmac-Sha256: <valid-hmac>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - Body: `{"customer": {...}}`
3. Attacker captures this raw body and its valid `X-Shopify-Hmac-Sha256` value.
4. Attacker sends a new POST to the same endpoint reusing the identical body and `X-Shopify-Hmac-Sha256` header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) succeeds because it only checks the body against the shared `client_secret`.
6. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the host app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, even though the actual data originated from the attacker's own store.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
