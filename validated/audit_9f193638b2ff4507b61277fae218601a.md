### Title
`transferCreator()` is a single-step, irreversible role transfer with no confirmation step - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.transferCreator()` lets the current creator of a launched token reassign the `creator` role for that token to any address in a single call, with no acceptance/confirmation step from the new address.

### Finding Description
`transferCreator` only checks that `newCreator` is non-zero and differs from the current creator before overwriting `info.creator` in storage:

```solidity
function transferCreator(address tokenAddress, address newCreator) external {
    if (newCreator == address(0)) revert ZeroAddress();
    TokenInfo storage info = _s().tokenInfo[tokenAddress];
    if (msg.sender != info.creator) revert NotCreator();
    if (newCreator == info.creator) revert InvalidInput();
    info.creator = newCreator;
    emit CreatorTransferred(tokenAddress, msg.sender, newCreator);
}
``` [1](#0-0) 

This is precisely the bug class in the source report: a critical, ownership-like role is changed atomically with a single transaction and no way for the new party to accept, and no way for the old party to cancel before it takes effect. `info.creator` is the value read by `Zap`/`FeeVault` for all future fee attribution via `Bonding.tokenInfo(token).creator`, as documented: "Creator attribution comes from `Bonding.tokenInfo(token).creator` (set at launch, updatable via `transferCreator`)." [2](#0-1) 

Notably, the codebase's own top-level Bonding contract comment shows the developers are aware of exactly this risk class for the *owner* role and mitigated it there by using `Ownable2StepUpgradeable` specifically so that "a bad `transferOwnership` can be cancelled ... before it takes effect — single-step transfer to a fat-fingered or contract-incompatible address would otherwise brick every owner-only path." [3](#0-2)  No equivalent two-step protection was applied to `transferCreator`, even though it is a comparably consequential, irreversible role assignment.

### Impact Explanation
If the creator mistypes the new address, submits the wrong address, or the intended recipient's address is later found to be a contract that cannot handle received value (e.g., cannot call `FeeVault.claim()`), the token's `creator` role — and therefore all *future* creator-side trading fees (0.25% of every buy/sell on that token, both on the curve and post-graduation) accrued into `FeeVault` and attributed via `FeeVault.accrue(token, creator, ...)` — become permanently misdirected. There is no path back: the old creator can no longer call `transferCreator` (since `msg.sender != info.creator` now reverts), so the fee stream is permanently lost/frozen for the legitimate creator with no recovery mechanism.

### Likelihood Explanation
This requires only a normal creator-initiated transaction with a typo'd or otherwise wrong address — an ordinary user-error scenario, not an attack requiring privileged access to protocol admin keys. Given creators are unprivileged/token-scoped actors performing normal token-management actions, and the transfer takes effect instantly and permanently, the likelihood of an unrecoverable mistake here is realistic.

### Recommendation
Convert `transferCreator` to a two-step pattern mirroring `Ownable2StepUpgradeable`'s pending-owner mechanism already used elsewhere in this contract: store a `pendingCreator[tokenAddress]` on the first call, and require the new address to call an `acceptCreator(tokenAddress)` function (or have the current creator's transaction include a matching accept from `newCreator`) before `info.creator` is actually updated. This closes the same class of irreversible-typo risk that the contract already guards against for the owner role.

### Proof of Concept
1. `creator` launches a token via `Bonding` and it begins trading/accruing fees.
2. `creator` calls `bonding.transferCreator(tokenAddress, newCreator)` with a mistyped `newCreator` address (any valid, non-zero address that isn't the intended one) — see `test_transferCreator` for the call shape. [4](#0-3) 
3. `info.creator` is immediately overwritten; `msg.sender` (original creator) can never call `transferCreator` again for this token since `NotCreator` now reverts for them.
4. All subsequent `FeeVault.accrue` calls for this token attribute the 0.25% creator fee share to the wrong address permanently, with no recovery path.
