### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `shopify-shop-domain` header to identify which tenant the payload belongs to. Because the shop identity is never bound to the signed bytes, an attacker who legitimately receives one valid webhook (e.g. by installing the app on their own store) can replay that exact body/HMAC pair while substituting an arbitrary `shopify-shop-domain` header, causing the app to process attacker-controlled data as if it originated from a victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` extracts the shop from a header that is completely independent of the signed payload: [1](#0-0) 

The signable string used for HMAC verification is only the raw body, never the headers: [2](#0-1) 

`Utils::HmacValidator.validate` verifies `to_signable_string` (the raw body) against the shared app `client_secret`, with no reference to `shop`: [3](#0-2) 

`Registry.process` uses this HMAC result as the sole authenticity check, then forwards the unauthenticated `request.shop` straight into the app's handler as trusted tenant identity: [4](#0-3) 

The gem's own documentation states that `process` "will verify the request did indeed come from Shopify," implying the whole request (including the shop it's attributed to) is authenticated: [5](#0-4) 

This is the same identity-binding gap described in the analog report: the parameter that authorization/attribution decisions are made on (`sender`/`account` in the Compound report; `shop` here) is not covered by the cryptographic check that is supposed to authenticate the whole operation (the `require(sender == address(this))` check in the report; the raw-body-only HMAC here). Any unprivileged internet user who can obtain one legitimately-signed webhook body (trivially available to any merchant/attacker who installs the app on their own store, since the same `client_secret` signs webhooks for every shop that installs the app) can replay that body with a forged `shop` header to the app's public webhook endpoint, and `ShopifyAPI::Webhooks::Registry.process` will pass HMAC validation and hand the handler a `WebhookMetadata` claiming the data belongs to a different, victim shop: [6](#0-5) 

### Impact Explanation
Host applications are expected (per the gem's own docs) to key persisted data by `data.shop` after calling `process`. Since `shop` is not authenticated, an attacker can inject or corrupt data attributed to another tenant (cross-tenant data injection), satisfying the report's "cross-tenant access" criterion — the app cannot distinguish a genuine webhook for shop A from an attacker-forged claim that the same bytes belong to shop B.

### Likelihood Explanation
Exploitation requires only: (1) installing the app on an attacker-controlled store to obtain one valid signed webhook (a routine, unprivileged action any developer/merchant can perform), and (2) sending an HTTP POST to the app's public webhook endpoint with the captured body/HMAC and a modified `shopify-shop-domain` header. No access token, `client_secret`, or privileged account is needed beyond what any external developer can already obtain by installing the app once.

### Recommendation
Bind the shop domain (and other trust-sensitive headers such as `topic`/`webhook-id`) into the signed material that `Utils::HmacValidator` verifies, or otherwise cryptographically tie the header-derived `shop` to the signed body (e.g., require the shop to also be present and covered by the signed payload, or independently verify header authenticity). At minimum, document this trust gap prominently so host apps cross-check `data.shop` against an already-known, provisioned shop before trusting the webhook payload.

### Proof of Concept
1. Attacker installs the target app on their own dev store `attacker.myshopify.com`, obtaining a valid webhook POST with body `B` and header `shopify-hmac-sha256: H` (valid because `H = HMAC(client_secret, B)`), plus `shopify-shop-domain: attacker.myshopify.com`.
2. Attacker sends a new POST to the app's public webhook endpoint with the same raw body `B` and same `shopify-hmac-sha256: H`, but sets `shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses `shop` from the (now forged) header [1](#0-0) ; `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H` [7](#0-6) .
4. `Registry.process` calls the handler with `WebhookMetadata.new(... shop: "victim.myshopify.com", body: parsed B ...)` [8](#0-7) , causing the host app to act on attacker-controlled data as though it belongs to the victim tenant.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
