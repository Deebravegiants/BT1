### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook request's HMAC over the raw request body only, but then trusts the unauthenticated `shop-domain` header when constructing the metadata passed to the app's handler. Because the HMAC never binds the `shop` value, anyone who can obtain one legitimate `(body, hmac)` pair signed with the app's shared `client_secret` (e.g. an attacker who is themselves a genuine installer/merchant of the app, or who otherwise captures one Shopify-delivered webhook) can replay that exact body/HMAC pair to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop, and the library will accept it as authentic and hand `shop: <victim shop>` to the host application's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `HmacValidator.validate` computes/verifies the HMAC over that signable string alone: [1](#0-0) [2](#0-1) 

The `shop` accessor, however, is read straight from the `shop-domain` header with no cryptographic binding to the signed body: [3](#0-2) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e. body authenticity) before forwarding `request.shop` straight into `WebhookMetadata`, which is what the host application's handler is documented to trust as "The shop domain of the webhook": [4](#0-3) [5](#0-4) 

The identity binding that is broken is: `hmac_verified(body) == true` is treated as if it implied `shop_header == shop_that_generated(body)`, but the HMAC secret (`Context.api_secret_key`) is the app-level `client_secret`, shared across every shop that installs the app — it is not shop-specific. Any party who legitimately receives one signed webhook for their own shop (by installing the app themselves, a fully unprivileged action) possesses a valid `(raw_body, hmac)` pair that remains valid for **any** shop-domain header, since the header plays no role in the signature. The gem provides no mechanism (nonce/timestamp binding of shop, or shop-domain inclusion in the signed payload) to prevent this substitution, and neither `webhook_id` uniqueness/idempotency nor delivery timestamp is verified by the library either.

### Impact Explanation
An attacker (a normal, unprivileged app installer) can forge webhook deliveries that the host application will believe originate from an arbitrary victim shop, while providing a payload of their own choosing (reused from their own store's traffic, or from any other prior legitimate delivery). Depending on how the host app trusts `data.shop` (e.g. to update per-shop billing/subscription state, trigger `app/uninstalled` cleanup, process `shop/redact` GDPR deletion, or update per-shop cached settings), this results in cross-tenant state corruption/impersonation of a shop the attacker does not control — matching the "cross-tenant access" impact category, since the gem's own request-processing API is what supplies the (falsely) trusted shop identity to the app.

### Likelihood Explanation
Exploitation requires only: (1) being able to install the app on any shop (which is the normal, unprivileged onboarding flow for any Shopify app), (2) capturing one legitimate webhook body+HMAC pair delivered to that shop, and (3) POSTing it to the app's public webhook endpoint with a different `shop-domain` header. No access to `client_secret`, access tokens, or any other shop's credentials is required. This is a low-effort, reliably-reproducible attack against any app using this gem's `Webhooks::Registry.process`/`Request` as documented.

### Recommendation
Do not derive shop identity for webhook processing solely from the unauthenticated `shop-domain` header. Either (a) include the `shop-domain` (and `topic`/`webhook-id`) in the HMAC-signed material so header tampering invalidates the signature, or (b) require callers to independently correlate `webhook_id`/`shop` against a shop that has an active, previously-established session/webhook registration before acting on the payload, and document this requirement prominently since the library currently implies (via `WebhookMetadata`/docs) that `shop` can be trusted once `HmacValidator.validate` passes.

### Proof of Concept
1. App is installed on attacker's own shop `attacker.myshopify.com`; Shopify delivers a legitimate webhook, e.g. `orders/create`, to the app with headers:
   `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over raw body B>`.
2. Attacker captures raw body `B` and its valid `hmac`.
3. Attacker re-POSTs the same raw body `B` and same `hmac` header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: ...)` builds `shop == "victim.myshopify.com"`; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only — it succeeds because `B` and the secret are unchanged. [6](#0-5) 
5. The host app's handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: B, ...)` and acts on it as if it were a genuine event from `victim.myshopify.com`.
