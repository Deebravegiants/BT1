### Title
Webhook `shop` (and `topic`/`webhook-id`) attribution is not covered by the HMAC, allowing cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authorizes an inbound webhook solely by validating the HMAC over the raw body, then unconditionally trusts the `shop-domain` (and `topic`/`webhook-id`) header to attribute the payload to a tenant. The signature never binds the `shop` field, so a genuine, previously-observed HMAC/body pair can be replayed with a different `shop-domain` header and will still validate, breaking the equality `authenticated_shop == attributed_shop`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all read from HTTP headers that are outside the signed content: [2](#0-1) 

`Registry.process` validates only the HMAC computed over `to_signable_string` (i.e. the body) and then immediately hands `request.shop` to the app's handler as the authenticated tenant identifier, with no further check that this shop was the one Shopify actually generated the signature for: [3](#0-2) 

`WebhookMetadata.shop` is a plain `String` field the handler is expected to trust for tenant routing: [4](#0-3) 

Because the HMAC only binds the body bytes, not the header set, the equality the gem should enforce — `hmac_signed_shop == request.shop used for handler dispatch` — does not hold. Any body+HMAC pair the attacker has legitimately observed (e.g. from a webhook delivered to their own shop, since a merchant fully controls their own store's webhook traffic and can trigger/observe deliveries) remains valid under a replayed request that swaps the `shopify-shop-domain` header to a different shop. `HmacValidator.validate` will still return `true`, because it never inspects `request.shop`: [5](#0-4) 

### Impact Explanation
In a multi-tenant app that uses this SDK's webhook handling to key data or trigger side effects by `WebhookMetadata.shop`, an attacker who controls one installed shop (an unprivileged tenant relative to other merchants on the same app) can replay their own genuine webhook body/HMAC pair while relabeling the `shop-domain` header to point at a victim shop. The handler will process attacker-controlled data as if it originated from, and belongs to, the victim tenant — this is a cross-tenant data-integrity/confusion issue meeting the "cross-tenant access" bar, since the receiving app has no way, within this gem, to distinguish a legitimately-attributed webhook from a relabeled one.

### Likelihood Explanation
Likelihood is bounded by the fact that the attacker needs a valid body+HMAC pair, which they can only obtain by being a legitimate merchant with an active app installation (i.e., they can trigger and capture Shopify-signed webhooks for their own shop) or by finding a body they can predict/control that is also meaningful for another tenant (harder). This still fits the unprivileged-internet-user framing: any merchant installing the app is "unprivileged" with respect to other merchants' tenant data, and no `api_secret_key`, access token, or privileged account is required to mount the replay — only a previously delivered, unmodified webhook body and its associated HMAC.

### Recommendation
Bind the tenant-identifying and routing metadata (`shop-domain`, `topic`, `webhook-id`, `api-version`) into the signed content, or otherwise cryptographically bind them to the HMAC verification step, rather than trusting them as free-standing headers once only the body has been authenticated. At minimum, `Registry.process` should cross-check `request.shop` against an out-of-band, previously-established tenant record (e.g., the shop for which the webhook subscription with `request.webhook_id` was registered) before dispatching to the handler.

### Proof of Concept
1. App installs on `shop-a.myshopify.com` and registers a webhook; Shopify delivers a request with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)` plus `x-shopify-shop-domain: shop-a.myshopify.com`.
2. The merchant who controls `shop-a` (or anyone able to capture this exact delivery, e.g. via their own logging proxy) records `(B, HMAC)`.
3. Attacker sends a new request to the app's webhook endpoint with the same body `B` and same `x-shopify-hmac-sha256` header, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body normally; `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` from `to_signable_string` (body only) and it matches, so `Registry.process` proceeds and calls `handler.handle` with `WebhookMetadata.new(..., shop: "shop-b.myshopify.com", ...)`, exactly as shown in: [3](#0-2) 
5. The app processes attacker-supplied data as belonging to `shop-b`, demonstrating the missing binding between the authenticated bytes (body) and the trusted attribution field (`shop`).

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

        end
