### Title
Reentrant Escrow Drain via Transfer-Before-Effects in `IntentGatewayV2.withdraw` (Tron) - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2` releases escrowed order funds to an attacker-controlled `beneficiary` via a raw `.call` (native ETH) or unchecked `token.call` (ERC-20 `transfer`) **before** decrementing the corresponding `_orders[commitment][token]` escrow balance, and the contract has no reentrancy guard anywhere. This is the same class of bug the external DODO report describes — a state-mutating safety check/update that must gate a fund-moving action is instead performed only *after* it — and it is the exact multi-output escrow-theft pattern that was already found and fixed in the sibling mainline EVM contract but never ported here.

### Finding Description
`withdraw()` ( [1](#0-0) ) loops over `body.tokens`, and for each token performs the external transfer to `beneficiary` first, then subtracts `amount` from `_orders[body.commitment][token]` afterward:
```solidity
if (_orders[body.commitment][token] == 0) revert UnknownOrder();
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    ...
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    ...
}
_orders[body.commitment][token] -= amount;   // effect happens AFTER the external interaction
```
`withdraw` is reachable from `onAccept` (RedeemEscrow/RefundEscrow, gated `onlyHost` but driven by any relayer delivering a valid cross-chain settlement proof) and from `onGetResponse`/`cancelOrder`'s same-chain path — both attacker-triggerable by placing an order whose beneficiary is a malicious contract and then having a solver fill it or by self-cancelling a same-chain order. When an order has multiple escrowed input tokens (e.g., native ETH plus an ERC-20), the native-ETH leg's `.call` hands control to the attacker's contract fallback while the ERC-20 leg's `_orders[commitment][token]` balance is still non-zero (not yet decremented). The mainline (non-Tron) `IntentsBase._withdraw` decrements `_orders` before performing the transfer specifically to close this window ( [2](#0-1) ), and `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol` documents this exact exploit as previously live: "the malicious beneficiary could re-enter during the ETH transfer, self-fill the ERC-20 output ... and steal the entire input[1] escrow" ( [3](#0-2) ). The Tron contract still has no `nonReentrant` modifier anywhere in the file and never received this fix.

### Impact Explanation
A malicious beneficiary contract can re-enter the gateway during the native-token leg of `withdraw` and drain the not-yet-decremented escrow of a second (or further) token in the same order, or interfere with `placeOrder`/`cancelOrder` state for the same commitment, resulting in concrete theft of escrowed user/protocol funds — permanent loss of funds for the legitimate order participants and a broken settlement invariant for the Tron deployment of the Intent Gateway.

### Likelihood Explanation
High: exploitation only requires placing (or being selected to fill) an order with a beneficiary contract and a multi-token input/output set including a native-token leg — no special privilege, consensus manipulation, or governance action is needed, and the attack is a single-transaction reentrant call during ordinary settlement delivery.

### Recommendation
Port the checks-effects-interactions fix already applied to `IntentsBase._withdraw` into the Tron `withdraw()`: decrement `_orders[body.commitment][token]` (and clear `_orders[...][TRANSACTION_FEES]`) before performing any external `.call`/token transfer, and/or add a `nonReentrant` guard to `withdraw`, `onAccept`, `onGetResponse`, and `cancelOrder`.

### Proof of Concept
1. User places a same-chain order via `placeOrder` with two inputs: native ETH and an ERC-20 token, beneficiary set to an attacker-deployed contract with a malicious `receive()`.
2. Order is cancelled/filled such that `withdraw(body, ...)` is invoked with `body.tokens = [ETH, ERC20]`.
3. In the loop, the ETH leg executes `beneficiary.call{value: amount}("")`; the attacker's `receive()` fires before `_orders[commitment][ERC20]` has been decremented.
4. The attacker's fallback re-enters a path that reads/uses `_orders[commitment][ERC20]` (e.g., re-triggering `cancelOrder`/`withdraw` for the same commitment through a still-valid state, since `_filled` is set but the per-token accounting is not), extracting the ERC-20 escrow a second time before the original call's decrement executes, exactly as demonstrated by `testReentrancy_EscrowTheft_MultiOutput` against the (now-fixed) mainline contract ( [4](#0-3) ).
