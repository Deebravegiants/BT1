### Title
Phantom order price snapshots weight solver bids by an unpinned, momentary on-chain balance, letting a flash-loaned balance dictate the published exchange rate - ([File: sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts])

### Summary
The Intent Gateway's off-chain price-discovery mechanism ("phantom orders") selects the published exchange rate for a token pair as the bid from whichever solver holds the largest momentary balance of the leg's output token. That balance is read at the chain's current head with no block pinning, so it reflects whatever a caller's address holds at the instant the RPC call executes rather than a balance that was ever actually committed to backing the quote. This mirrors the APE incident's root cause: eligibility/weight is determined by transient, atomically-manipulable state rather than a durable, escrowed position.

### Finding Description
`aggregatePhantomBids` → `runAggregation` in `sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts` weights every verified solver quote for a leg by `getBalance`, described in the docstring as "the solver's balance of that leg's OUTPUT token on the destination chain — the inventory that actually backs the leg" [1](#0-0) . That reader defaults to `memoizedSolverBalance(yieldVaults)` with no `blockTags`, i.e. an unpinned "latest" read [2](#0-1) .

The indexer's own documentation confirms this is by design for the phantom price path specifically: "Only this chain is read... The phantom sweep pins nothing and reads every chain at its head" [3](#0-2) , in contrast to every other liquidity-refresh consumer, which was deliberately changed to pin reads to a specific historical block precisely because head-reads are "not replayable" and can be trivially stamped with a different balance than what genuinely backed an event [4](#0-3) .

The weighting scheme then makes this balance decisive, not just influential: `weightedMedian` "returns one bidder's exact integer, so a solver holding over half the leg's weight sets the published price verbatim, and the result can never be a value nobody quoted" [5](#0-4) . Any address can become a "solver" for this purpose by delegating itself to the deployed `SolverAccount` via EIP-7702 and producing a userOp whose signature and nonce key satisfy `isVerifiedSolverBid` [6](#0-5)  — there is no economic barrier or escrow requirement to bid, only signature validity and the momentary balance read at aggregation time.

Because the balance is read at the chain head asynchronously (whenever the indexer's event handler happens to execute after `PhantomBidWindowExhausted`), an attacker can transiently hold an outsized balance of the output token (e.g., via a flash loan, a large temporary deposit/withdrawal cycle, or simply borrowing/holding tokens for the short window until the read fires) to outweigh every genuine solver, causing their submitted quote to become the published `medianPrice`/`lowestPrice`/`highestPrice` for that pool leg with no requirement that the balance persist afterward.

### Impact Explanation
The published snapshot is not merely informational telemetry — it is consumed directly by `PhantomSnapshotIntentQuoteStrategy.quoteSnapshot`, which computes `amountOut = netAmountIn * snapshot.medianPrice / snapshot.standardAmount` (and the inverse for exact-output) to quote real users placing intents [7](#0-6) . An attacker who transiently inflates their weight to dominate the median can set an arbitrarily favorable-to-solver (unfavorable-to-user) rate, causing real users' FX intents to be quoted and ultimately filled at a manipulated price, and can repeat this cheaply every bid window since no capital needs to remain committed once the balance is read. This directly parallels the APE flash-loan class of vulnerability: an unbacked, momentary state check is trusted as if it represented genuine, durable backing.

### Likelihood Explanation
The unpinned read is deliberate and documented as a conscious design choice specific to the phantom price path [3](#0-2) , and bidding requires only a valid EIP-7702 delegation plus a correctly-signed userOp — no staking, no escrow, no minimum track record. Any address holding or able to transiently acquire (via lending markets, DEX flash swaps, or simply moving funds through the address) a large balance of a leg's output token around the time the indexer processes `PhantomBidWindowExhausted` can attempt this. The main friction is timing the balance to be present when the asynchronous indexer read fires, which is a solvable, repeatable engineering problem rather than a fundamental blocker.

### Recommendation
Pin the phantom-aggregation balance read (`memoizedSolverBalance` inside `runAggregation`) to a specific, deterministic block — e.g., the destination chain's finalized block closest to the bid-window close, the same way `blockReaders`/`inventoryReadContext` already pin every other liquidity-refresh consumer — and/or require solvers to actually escrow or lock the balance being measured (or use a time-weighted/multi-block average balance) so a momentary, unbacked balance cannot single-handedly set the published exchange rate.

### Proof of Concept
1. Attacker deploys/uses an EOA and self-delegates to a configured `SolverAccount` via EIP-7702.
2. Attacker crafts a valid `PackedUserOperation` bid for an active phantom order leg, quoting an extreme (attacker-favorable) output price, satisfying `isVerifiedSolverBid`'s signature/nonce checks [8](#0-7) .
3. Shortly before/around the time `PhantomBidWindowExhausted` fires and the indexer's `handlePhantomOrderPrices` runs `aggregatePhantomBids` (unpinned, head-block read) [9](#0-8) , attacker temporarily acquires (e.g., flash-loans) a balance of the leg's output token exceeding the combined balance of all genuine solvers.
4. `weightedMedian` selects the attacker's quote verbatim as the leg's `medianPrice` because the attacker holds over half the weight.
5. Attacker returns/dissolves the borrowed balance; the snapshot persists with the manipulated price, which `PhantomSnapshotIntentQuoteStrategy` then uses to quote real users' intents.

	commitment: string

	bidNonceKey: BidNonceKeyFn
	/** Cached per aggregation, so duplicate fillers and retries do not re-read the same answer. */
	isDelegated: DelegationReader
	logger?: AggregationLogger
}): Promise<boolean> {
	const {
		userOp,
		commitment,
		sessionKey,
		chainId,
		solverAccounts,
		evmRpcUrl,
		recoverSigner,
		bidNonceKey,
		isDelegated,
		logger,
	} = params
	const solver = userOp.sender

	const parsed = splitBidSignature(userOp.signature)
	if (!parsed) {
		logger?.warn({ solver, commitment }, "Rejecting phantom bid: malformed userOp signature")
		return false
	}

	// Cheap early-out ONLY. The prefix sits inside userOp.signature, which userOpHash excludes, so it
	// is attacker-mutable and must never be what binds a bid to an order — the nonce key below is.
	if (parsed.commitment.toLowerCase() !== commitment.toLowerCase()) {
		logger?.warn(
			{ solver, commitment, signedFor: parsed.commitment },
			"Rejecting phantom bid: signed for another order",
		)
		return false
	}

	// The authoritative binding, mirroring SolverAccount.validateUserOp on-chain. The nonce IS
	// covered by userOpHash, so a solver signature stays valid only for the (order, sessionKey) pair
	// its nonce key was derived from. `sessionKey` is read from the bid's own calldata, which is also
	// covered by userOpHash — so every operand here is signed, leaving nothing for a replay to swap.
	if (BigInt(userOp.nonce) >> 64n !== bidNonceKey(commitment as HexString, sessionKey)) {
		logger?.warn({ solver, commitment }, "Rejecting phantom bid: nonce does not bind order and session key")
		return false
	}

	// SolverAccount._rawSignatureValidation recovers over the bare userOpHash and requires the signer
	// to be the account itself, which under EIP-7702 is the sender EOA.
	const signer = await recoverSigner(userOp, ENTRY_POINT_V08_ADDRESS, chainId, parsed.solverSignature)
	if (!signer || signer.toLowerCase() !== solver.toLowerCase()) {
		logger?.warn({ solver, commitment, signer }, "Rejecting phantom bid: signature does not recover to the sender")
		return false
	}

	if (!(await isDelegated(evmRpcUrl, solver, solverAccounts))) {
		logger?.warn({ solver, commitment, solverAccounts }, "Rejecting phantom bid: sender is not a delegated solver")
		return false
	}

	return true

	private quoteSnapshot(
		params: QuoteIntentParams,
		protocolFeeBps: bigint,
		snapshot: PhantomOrderPriceSnapshot,
	): PhantomSnapshotQuoteIntentResult {
		if (params.amountIn !== undefined) {
			const netAmountIn = deductProtocolFee(params.amountIn, protocolFeeBps)
			const amountOut = (netAmountIn * snapshot.medianPrice) / snapshot.standardAmount
			if (amountOut <= 0n) {
				throw new InvalidPhantomSnapshotError(snapshot.commitment, "quote rounds down to zero output")
			}
			return this.buildResult("EXACT_INPUT", params.amountIn, amountOut, protocolFeeBps, snapshot)
		}

		if (params.amountOut === undefined) throw new Error("Quote amount is missing after validation")
		const netAmountIn = divCeil(params.amountOut * snapshot.standardAmount, snapshot.medianPrice)
		const amountIn = grossUpForProtocolFee(netAmountIn, protocolFeeBps)
		return this.buildResult("EXACT_OUTPUT", amountIn, params.amountOut, protocolFeeBps, snapshot)
