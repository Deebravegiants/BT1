It's a documented-but-only-partially-fixed griefing bug: `SimplexPaymaster.addStake` is permissionless and lets anyone extend the EntryPoint unstake delay and lock native funds, mirroring the "roll" pattern of repeated permissionless calls that lock funds for an attacker-chosen duration.### Title
Permissionless `SimplexPaymaster.addStake` lets anyone lock native funds and extend the unstake delay indefinitely - ([File: evm/src/utils/SimplexPaymaster.sol])

### Summary
`SimplexPaymaster` (an unprivileged-reachable EVM contract that pays gas for solver `UserOperation`s in the Hyperbridge intents pipeline) inherits `addStake(uint32 unstakeDelaySec)` from the ERC-4337 `PaymasterCore`/EntryPoint stack. In the version fixed by commit referenced in `sdk/packages/simplex/docs/ai/changelog/2026-08-19-security-review-fixes-stake-recovery-postop-gas-band-1071.md`, `addStake` was callable by anyone, while `unlockStake`/`withdrawStake` unconditionally revert through `_authorizeWithdraw()` and no governance `RequestKind` existed to recover the stake. This is structurally the same bug class as the Cooler `roll()` report: a permissionless function that any address can call repeatedly, each call extending a lock/expiry parameter that the protocol cannot bypass, letting an attacker lock protocol funds for an attacker-chosen (effectively unbounded) duration at negligible cost.

### Finding Description
`addStake` forwards to the ERC-4337 `EntryPoint`, which enforces the invariant that `unstakeDelaySec` **only ever grows** and any pending unlock is reset on every call to `addStake`. Because the paymaster's override had no `msg.sender` gate, this meant:

- Anyone could call `paymaster.addStake{value: 1 wei}(type(uint32).max)`.
- This stretched the delay from the intended ~1 day to ~136 years, and reset any unlock the treasury had started.
- Since `unlockStake`/`withdrawStake` both route through `_authorizeWithdraw()`, which reverts unconditionally in this contract, and no `RequestKind` existed for stake recovery, the staked native (and any newly added value) became **permanently unrecoverable** by governance.

This mirrors the reported Cooler `roll()` bug exactly: a single unauthenticated function, callable an unlimited number of times by any address, that monotonically extends a lock/expiry the honest party cannot override, turning a bounded delay into a functionally permanent freeze of protocol-owned funds, and the attacker can force the extension at trivial cost (`1 wei` + gas, versus the Cooler exploit's compounding collateral cost). ### Impact Explanation
This is a Medium/High severity permanent-freezing-of-funds bug class: any staked native value on the paymaster (required by ERC-4337 bundlers for storage access) is locked forever with no recovery path, and an unprivileged griefer can trivially force the maximum lock (136-year delay) for the cost of a few wei and gas — an even cheaper attack than the original Cooler `roll()` report, which at least required compounding collateral. Live-fork tests in the repository confirm real staked funds (0.1 native each on Ethereum, BSC, Arbitrum) were affected before the fix. [3](#0-2) 

### Likelihood Explanation
The finding notes this was already discovered and fixed via a security review (`#1071`) — `addStake` is now gated to `msg.sender == treasury`, and `RequestKind.UnlockStake`/`RequestKind.WithdrawStake` were added as governance recovery paths. [4](#0-3) [5](#0-4) 

Because the repository already contains the treasury-gated `addStake` and the `UnlockStake`/`WithdrawStake` governance kinds, the currently deployed/reviewed version of `SimplexPaymaster.sol` in this repo state is **not vulnerable** to the analog described. This is documented as a fixed historical issue, not a currently live one.

### Recommendation
No further action is required in this repo state: the fix (treasury-gating `addStake`, adding `UnlockStake`/`WithdrawStake` `RequestKind`s routed through governance `onAccept`) already implements the correct mitigation pattern from the original report (restrict who can extend the lock, and/or provide a bounded, privileged recovery path). Confirm this fix is deployed on all live chains (Ethereum, BSC, Arbitrum) referenced in `SimplexPaymasterStakeLockForkTest.t.sol`, since the fork tests indicate mainnet-deployed instances predating the patch were affected.

# 2026-08-19 — Stake gets a governance recovery path, and `addStake` is treasury-only (#1071)

Chosen: two new empty-payload request kinds (`UnlockStake` = 5, `WithdrawStake` = 6, always paying out to the treasury) and an `addStake` override gated to the treasury.

The alternative — leave stake unrecoverable and simply never stake — is not available: bundlers require a staked paymaster for the storage access this contract performs, so staking is effectively mandatory and was already done on three chains. Two kinds rather than one because the EntryPoint requires `unlockStake()` and then a wait of `unstakeDelaySec` before `withdrawStake()` will succeed; a single request could not span that delay.

Gating `addStake` is the half that cannot be deferred. The EntryPoint only ever lets `unstakeDelaySec` grow and resets any pending unlock on every `addStake`, so while the function is open an unprivileged caller can push the delay to 136 years and cancel unlocks indefinitely — which would defeat the recovery path being added here.

    /// @notice Stakes native with the EntryPoint, which bundlers require before they will
    ///         relay operations from this paymaster.
    /// @dev Treasury-gated. The EntryPoint only ever lets `unstakeDelaySec` grow and resets
    ///      any pending unlock, so leaving this open would let anyone stretch the delay far
    ///      beyond the point where governance could recover the stake.
    function addStake(uint32 unstakeDelaySec) public payable override {
        if (msg.sender != treasury) revert UnauthorizedCall();
        super.addStake(unstakeDelaySec);
    }
