### Title
Webhook `shop` field is trusted from an HMAC-unprotected header, allowing tenant-identity spoofing in `WebhookMetadata` - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#shop` reads the shop domain directly from the `x-shopify-shop-domain` (or `shopify-shop-domain`) HTTP header, but that header is never included in the HMAC signature that `HmacValidator` verifies. The gem verifies only the raw request body, then hands the caller-supplied, unauthenticated `shop` value on to the app's webhook handler as if it were verified.

### Finding Description
`Registry.process` validates the webhook using `Utils::HmacValidator.validate(request)`, which relies on `VerifiableQuery#to_signable_string`. [1](#0-0) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` — headers are never part of the signable/signed material: [2](#0-1) 

Yet `shop` is derived purely from the `shop-domain` header, and is passed straight into `WebhookMetadata` that the app's handler consumes as the tenant identifier: [3](#0-2) [4](#0-3) [5](#0-4) 

The identity binding broken is: `bytes verified (HMAC over raw_body) != bytes trusted for tenant routing (shop-domain header)`. Anyone who can produce a request whose HMAC matches an already-known valid `(secret, raw_body)` pair — e.g. by replaying a previously captured, genuine webhook payload/HMAC for shop A while swapping only the `x-shopify-shop-domain` header to shop B — passes `HmacValidator.validate` unchanged (it only checks the body) while `request.shop` and thus `WebhookMetadata#shop` report shop B. The documented usage pattern (`docs/usage/webhooks.md`) shows apps dispatching background jobs keyed by `data.shop` without any additional secondary check, since the gem's own contract implies `process` fully "verif[ies] the request did indeed come from Shopify" before invoking the handler. [6](#0-5) 

### Impact Explanation
This is a cross-tenant identity confusion: the gem lets an attacker who obtains one valid (body, HMAC) pair attribute that payload's processing to an arbitrary different shop domain by only changing an unauthenticated header, while the library's HMAC check still reports success. Applications that trust `WebhookMetadata#shop` (as the gem's own documentation instructs) to select/scope tenant data, credentials, or storage records can be made to write or act on data under the wrong tenant/shop record — a cross-tenant access condition rooted entirely in this gem's verification logic, not application misuse.

### Likelihood Explanation
Obtaining a valid `(raw_body, hmac)` pair is straightforward for an app that has installed the same app on any shop (or observed one legitimate webhook delivery, e.g. via a public endpoint/log leak, replay, or a shop the attacker themselves owns and installed the app on) since HMAC-SHA256 is computed with the app's single shared `client_secret` across all shops the app is installed on. Because Shopify uses the same per-app secret for every merchant install, an attacker who controls one shop's install can freely forge webhooks that this gem will validate as authentic for any other shop simply by changing the `shop-domain` header — no secret needs to be known or broken.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header values as part of the signed/verified material for webhook requests, or independently cross-check that the shop reported in the payload/header matches a shop with an active, registered subscription for that specific webhook id/topic before dispatching to the handler. At minimum, document prominently that `WebhookMetadata#shop` is not verified by the HMAC and must not be trusted for tenant-scoping decisions without an additional authoritative lookup (e.g., confirming an existing session/install record for that shop).

### Proof of Concept
```ruby
# Attacker has legitimately installed the app on "attacker-shop.myshopify.com"
# and captured one authentic webhook delivery (raw_body + valid HMAC),
# since the client_secret is shared across all shop installs of the same app.

raw_body = '{"id":123}'
valid_hmac_header = "shopify-hmac-sha256-value-for-raw_body-with-shared-secret"

headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac_header,   # computed only from raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # swapped, NOT covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)

# HmacValidator.validate only checks raw_body, so this still returns true
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...))
# The app's handler now processes/attributes this webhook to "victim-shop.myshopify.com"
# even though the payload was never sent by Shopify for that shop.
```

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
