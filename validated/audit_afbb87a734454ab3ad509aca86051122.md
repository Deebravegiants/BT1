## Title
Webhook shop/topic/webhook_id identity fields are not covered by HMAC verification, enabling cross-tenant webhook spoofing - (`File: lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Utils::HmacValidator.validate` verifies the HMAC exclusively against that body. The `shop`, `topic`, `webhook_id`, and `api_version` values are read straight from HTTP headers and are never included in the signed material. `ShopifyAPI::Webhooks::Registry.process` trusts these header-derived fields (in particular `request.shop`) after only confirming the body's HMAC, so the identity binding "shop whose secret authenticated this HMAC" ≠ "shop the payload is dispatched under" can be broken by anyone who can obtain one legitimately-signed body/HMAC pair for the app's shared `client_secret`.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
and `shop`/`topic`/`webhook_id`/`api_version` are pulled from headers with no cryptographic binding to the body: [2](#0-1) 

`HmacValidator.validate`/`validate_signature` compute and compare the HMAC solely over `verifiable_query.to_signable_string`, i.e., the raw body: [3](#0-2) 

`Registry.process` gates everything on that body-only HMAC check and then forwards the unauthenticated header values (including `request.shop`) straight to the app's webhook handler: [4](#0-3) 

Because Shopify apps use a single, shared `client_secret` (`Context.api_secret_key`) across every shop that installs the app, any shop that installs the app (including one an attacker controls, e.g. a free development store) can trigger a real webhook and thus obtain a genuinely-signed `(raw_body, HMAC)` pair. Since the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, and `X-Shopify-Webhook-Id` headers are excluded from the signed payload, that attacker can replay the exact same body+HMAC to the app's webhook endpoint while substituting any victim shop domain (or topic/webhook id) in the headers. `HmacValidator.validate` still returns `true` because it only re-derives the HMAC from the body, and `Registry.process` dispatches the handler with `WebhookMetadata` carrying the forged `shop`.

This breaks the equality the HMAC is meant to enforce: **shop whose secret validated this webhook == shop the handler is told the webhook came from**. Instead, the gem lets: `shop authenticated (implicitly, by the shared secret) != shop passed to the handler as the tenant identity`.

### Impact Explanation
Downstream host applications (following this gem's own documented pattern, e.g. `usage/webhooks.md`) key their tenant/session lookups off `WebhookMetadata#shop`. An attacker who forges the `shop` header can make the gem hand a handler attacker-originated event data tagged with a victim shop's domain, causing the host app to:
- Perform tenant-scoped writes/updates (e.g. order/customer sync, inventory updates, uninstall/GDPR handling) against the victim shop's stored records/access token using attacker-supplied body content.
- Trigger topic-specific privileged flows (e.g. `app/uninstalled`, `shop/redact`) for a shop the attacker does not own, since `topic` is likewise unauthenticated.

This is a cross-tenant boundary violation reachable by any unprivileged internet user who can install the app on a store they control (a normal, unprivileged action) — no access token, `client_secret`, or privileged account is required.

### Likelihood Explanation
Likelihood is high: obtaining a genuine `(body, HMAC)` pair only requires installing the target app on any store (including a free development store) and triggering any webhook topic the app subscribes to. Replaying that payload against the app's public webhook endpoint with modified `X-Shopify-Shop-Domain`/`X-Shopify-Topic` headers is trivial once the pair is captured, and the gem performs no header-to-signature binding to reject it.

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signable material verified by `HmacValidator`, or otherwise cryptographically bind them to the body (e.g., verify a canonical string of `shop|topic|webhook_id|api_version|body` against the HMAC) before `Registry.process` trusts `request.shop`/`request.topic` and constructs `WebhookMetadata`. At minimum, document prominently that `request.shop`/`request.topic` are not covered by the HMAC so host apps do not use them as an authenticated tenant key.

### Proof of Concept
1. Attacker creates/uses a Shopify development store and installs the target app (no privilege required).
2. Attacker triggers any subscribed webhook topic on their own store, capturing the raw request body `B` and the valid `X-Shopify-Hmac-Sha256` header `H` that Shopify computed with the app's shared `client_secret`.
3. Attacker sends a POST to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged), but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and/or a different `X-Shopify-Topic`).
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `HmacValidator.validate` recomputes the HMAC over `B` only (`to_signable_string` returns just `@raw_body`) and it matches `H`, so `validate` returns `true`:
```ruby
# lib/shopify_api/webhooks/request.rb
def to_signable_string
  @raw_body
end
```
5. `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)`, where `shop` is `"victim-shop.myshopify.com"` even though the signed body actually originated from the attacker's own shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
