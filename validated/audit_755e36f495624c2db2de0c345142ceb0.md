### Title
Webhook Shop-Domain Spoofing via HMAC Verification Covering Only the Raw Body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` extracts `shop`, `topic`, `webhook_id`, and `api_version` from HTTP headers that are never covered by HMAC verification. `ShopifyAPI::Webhooks::Registry.process` validates only the raw request body against the HMAC, then hands the caller-supplied `shop` header straight to the app's webhook handler. An unprivileged internet user who can obtain any single valid `(body, HMAC)` pair signed with the app's `client_secret` (trivially available to them by installing the app on their own free/dev store and capturing one of their own legitimate webhook deliveries) can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. The app will process the payload as if it originated from the victim shop of the attacker's choosing, since nothing binds the `shop` field to the cryptographically verified bytes.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, and `webhook_id` are read directly from attacker-reachable HTTP headers without any cryptographic protection: [2](#0-1) 

`Registry.process` verifies only the HMAC (which — per the above — covers `raw_body` alone) and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the data passed to the app's handler: [3](#0-2) 

The identity binding that should hold is:
`shop verified by HMAC == shop acted upon by the handler`

but the actual binding enforced by this code is only:
`bytes verified by HMAC (raw_body) == bytes parsed for shop (HTTP header, unauthenticated)`

Because the webhook HTTP endpoint is a public internet-facing route (this is explicitly how the gem's own documentation instructs apps to wire it up), any unauthenticated party who can produce a single legitimate `(raw_body, hmac-sha256)` pair — which any merchant/attacker with their own store installing the app can do by simply triggering one of their own webhooks — can replay that identical body and HMAC value to the same endpoint while forging the `shopify-shop-domain` (and `shopify-topic`/`shopify-webhook-id`) header to any value they choose. `Utils::HmacValidator.validate` will still succeed because it only recomputes the HMAC over `@raw_body`, and `Registry.process` will dispatch the handler with the attacker-chosen `shop`: [4](#0-3) 

### Impact Explanation
Apps built on this gem key persisted data, feature flags, order/customer processing, and business logic to the `shop` field of `WebhookMetadata` supplied by `Registry.process`. Since that field is not bound to the verified bytes, an attacker can inject data attributed to a shop they do not own/control (cross-tenant data injection), trigger app-side actions (e.g., re-processing GDPR/redact webhooks, order or product state changes, cache invalidation, deletion flows) against a victim shop's tenant record, or spoof mandatory compliance webhooks (`shop/redact`, `customers/redact`, `customers/data_request`) for a shop they have no relationship with. This crosses a tenant boundary using only the app's own shared `client_secret`-derived HMAC (which the attacker never needs to know directly — they only need one valid sample), qualifying as Critical (cross-tenant access).

### Likelihood Explanation
Any user who can install the app on their own shop (a normal, unprivileged flow) can capture one legitimate webhook body+HMAC pair for their own store by simply generating a qualifying event (e.g., updating a product). Replaying that exact byte-for-byte body with a forged `shop`-domain header is trivial and requires no cryptographic secret, no access token, and no privileged account — matching the "unprivileged internet user" threat model.

### Recommendation
Include the tenant-identifying headers (`shop`, `topic`, `webhook_id`) in the signable string that is HMAC-verified, or otherwise cryptographically bind the shop to the verified payload before it is handed to the handler. At minimum, `Registry.process` should require that the `shop` extracted from headers match a shop for which the app holds an active, expected session/registration before dispatching to the handler, rather than trusting the header outright.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (any free/dev store) and receives one legitimate webhook, e.g.:
   - `raw_body = '{"id":123,...}'`
   - `shopify-hmac-sha256: <valid HMAC of raw_body using the app's client_secret>`
   - `shopify-shop-domain: attacker-shop.myshopify.com`
2. Attacker replays the exact same request to the app's public webhook endpoint, unmodified except:
   - `shopify-shop-domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` only — it matches, since `raw_body` is unchanged.
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: ..., topic: ...)` and processes attacker-controlled data as if it came from the victim shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
