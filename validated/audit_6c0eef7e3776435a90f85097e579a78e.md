## Finding

### Title
Webhook shop-domain (and topic/id) header is trusted for tenant attribution without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values are read from unauthenticated HTTP headers and passed straight through to the application's webhook handler. This breaks the same class of binding described in HAL-08: a value that is *acted on* (the shop the webhook is attributed to) is not covered by the cryptographic check that is supposed to authenticate the message.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Registry.process` validates the HMAC over that signable string and, on success, immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` — all sourced from headers that are never part of the signed material — to build the metadata handed to the app's handler: [2](#0-1) 

The header accessors themselves confirm these fields come from `shopify-shop-domain`/`x-shopify-shop-domain` etc., independent of the body: [3](#0-2) 

The equality that should hold is: **shop the HMAC authenticates == shop the handler acts on**. Because the HMAC is computed only over the JSON body, that equality is never enforced — an attacker who possesses one valid `(raw_body, hmac)` pair signed with the app's `client_secret` for *their own* shop (e.g. from a legitimate webhook delivery to their own installed app, which they can trigger themselves by performing actions in their own store) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value. `HmacValidator.validate` only checks the body against the secret, so the forged request passes validation, and `Registry.process` invokes the handler with `shop: <victim-shop>` even though the payload was never generated for that shop.

### Impact Explanation
This lets an authenticated app-installer (a "shop" tenant, i.e. not privileged with respect to *other* tenants) inject fabricated webhook events attributed to a different, arbitrary shop domain into the host application, since `WebhookMetadata.shop` is unauthenticated relative to the signed payload. Depending on how the host app uses `WebhookMetadata#shop` (typically as the tenant key to look up/update per-shop records, e.g. mark app as uninstalled, alter order data, etc. for a shop the attacker does not own), this constitutes cross-tenant data injection/corruption — matching the Critical "cross-tenant access" impact category. No access token, `api_secret_key`, or session compromise is required by the attacker beyond a valid HMAC/body pair they can obtain from their own legitimate webhook traffic.

### Likelihood Explanation
Moderate: the attacker must be able to obtain at least one legitimate `(raw_body, hmac)` pair for the shared app `client_secret` (trivial for anyone who has installed the app on their own store and can trigger/receive a webhook), and must be able to send arbitrary HTTP requests with custom headers to the app's public webhook endpoint (also trivial). No brute-forcing or secret knowledge is needed since the header is simply unauthenticated and swappable.

### Recommendation
Include the `shop`, `topic`, and `webhook_id`/`api_version` header values in the HMAC-signable string (or otherwise cryptographically bind them to the body), so `Registry.process` cannot attribute a validly-signed payload to an arbitrary, attacker-chosen shop. At minimum, the library should expose a way for host applications to assert that `request.shop` matches an expected/known shop before invoking the handler, and document this binding gap clearly if it cannot be fixed at the library level.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and captures one legitimate webhook delivery: raw JSON body `B` and header `shopify-hmac-sha256: H` (valid HMAC of `B` under the app's shared `client_secret`).
2. Attacker sends a new HTTP POST to the app's webhook endpoint with the exact same body `B` and `shopify-hmac-sha256: H`, but sets `shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `shopify-topic`/`shopify-webhook-id`).
3. `ShopifyAPI::Webhooks::Request.new` parses these headers; `Utils::HmacValidator.validate(request)` succeeds because it only checks `H` against `B`, per: [4](#0-3) 
4. `Registry.process` calls the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)`, so the host application processes attacker-supplied data as if it originated from the victim shop.
