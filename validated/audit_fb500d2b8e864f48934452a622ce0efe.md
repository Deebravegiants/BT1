Webhook topic (and shop) headers are unauthenticated and can be freely spoofed for a validly-signed body - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`Webhooks::Request#topic` (and `#shop`, `#api_version`, `#webhook_id`) is read straight from an HTTP header, but `HmacValidator.validate` only verifies `to_signable_string`, which returns `@raw_body`. `Registry.process` dispatches the handler using `request.topic` (and passes `request.shop` into `WebhookMetadata`) without those values ever being covered by the HMAC, so an attacker who owns any legitimate, validly-signed webhook body (from their own shop's real installation, since the app's `client_secret`/`api_secret_key` is shared across all installs) can relabel it with any topic and shop-domain header of their choosing.

### Finding Description
The claimed binding is: `hmac == HMAC(secret, raw_body)` should imply `topic (used for dispatch) is authenticated together with raw_body`. Tracing the code shows this is false:

- `to_signable_string` returns only `@raw_body`: [1](#0-0) 
- `topic`, `shop`, `api_version`, `webhook_id` are all read from unauthenticated headers with no cross-check against the body: [2](#0-1) 
- `HmacValidator.validate_signature` computes the HMAC exclusively over `verifiable_query.to_signable_string` (i.e., the raw body) and compares it to `verifiable_query.hmac`; it never reads `topic` or `shop`: [3](#0-2) 
- `Registry.process` validates the HMAC once, then keys handler dispatch off `request.topic`, and forwards `request.shop`/`request.topic` straight into `WebhookMetadata` used by the handler: [4](#0-3) 

Because the app's `api_secret_key` (the app's `client_secret`) is the same across every shop that installs the app, an attacker who installs the app on their own development shop legitimately receives real, correctly-signed webhook deliveries. Nothing stops them from replaying that exact `raw_body`+`hmac` pair to the app's webhook endpoint while substituting `X-Shopify-Topic: app/uninstalled` and/or `X-Shopify-Shop-Domain: victim-shop.myshopify.com`. `HmacValidator.validate` still returns `true` because it only checks the body bytes against the secret, and `Registry.process` will happily invoke whatever handler is registered for the attacker-chosen topic, passing along the attacker-chosen shop domain as if it were an authentic message about that shop.

Existing guards do not close this gap: there is no `ShopValidator.sanitize!` call in this path, no topic/body content matching, and no per-shop-domain HMAC secret (the secret is app-wide, not shop-specific), so the divergence between the signed bytes and the acted-upon topic/shop is real and reachable purely with attacker-controlled HTTP headers.

### Impact Explanation
Any handler dispatch and any per-shop metadata handed to the handler (`topic`, `shop`) is trivially forgeable while still passing HMAC validation. A host app that (as documented) relies on `Registry.process` to route to the correct handler and trusts `WebhookMetadata#shop` as the shop the event pertains to is exposed to:
- Triggering sensitive handlers (e.g., `app/uninstalled`, `shop/redact`, `customers/redact`) using an unrelated, attacker-supplied body.
- Attributing the action to an arbitrary victim shop domain, since `shop` is equally unauthenticated — enabling cross-tenant effects (e.g., forcing deletion/cleanup logic meant for the victim's session/data) without ever compromising that victim or holding any of the app's secrets.

This is repeatable indefinitely against any shop domain the attacker chooses, using only their own legitimately-signed webhook traffic as raw material. This matches the Critical bucket (cross-tenant access / authentication bypass of topic-based dispatch).

### Likelihood Explanation
Preconditions are exactly the attacker capabilities given: install the app on their own shop (no privilege needed), capture one real signed webhook delivery, then POST a crafted request to the app's public webhook endpoint with the same body/HMAC but forged `X-Shopify-Topic`/`X-Shopify-Shop-Domain` headers. No secret material, no elevated access, no other app misconfiguration is required beyond using the gem's `Webhooks::Registry.process` as documented. Cost is a single HTTP request; the attack is trivially repeatable.

### Recommendation
Do not trust unauthenticated headers for security-relevant dispatch or attribution:
- Include `topic` and `shop` (and any other header used for dispatch/metadata) in the signable string that is HMAC-verified, or otherwise bind them cryptographically to the body/delivery (Shopify's actual `X-Shopify-Webhook-Id` combined with idempotency/topic-body content checks can help, but the safest fix is signing the header values along with the body).
- At minimum, cross-validate that `topic` is consistent with expected data present in the parsed body when the handler is dispatched, and require callers to confirm `shop` matches the shop context the handler expects (e.g., an active session for that shop) before acting on destructive topics like `app/uninstalled`, `shop/redact`, `customers/redact`.

### Proof of Concept
```ruby
# test/webhooks/registry_topic_spoof_test.rb
require_relative "../test_helper"

module ShopifyAPITest
  module Webhooks
    class RegistryTopicSpoofTest < Minitest::Test
      def setup
        ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", ...)
        ShopifyAPI::Webhooks::Registry.clear
      end

      def test_hmac_validation_unaffected_by_topic_or_shop_header
        raw_body = '{"id":1,"note":"benign order created on attacker shop"}'
        hmac = Base64.encode64(
          OpenSSL::HMAC.digest("sha256", ShopifyAPI::Context.api_secret_key, raw_body)
        )

        original_request = ShopifyAPI::Webhooks::Request.new(
          raw_body: raw_body,
          headers: {
            "x-shopify-topic" => "orders/create",
            "x-shopify-hmac-sha256" => hmac,
            "x-shopify-shop-domain" => "attacker.myshopify.com",
          },
        )

        spoofed_request = ShopifyAPI::Webhooks::Request.new(
          raw_body: raw_body, # identical bytes, identical valid hmac
          headers: {
            "x-shopify-topic" => "app/uninstalled",         # forged topic
            "x-shopify-hmac-sha256" => hmac,                # same signature
            "x-shopify-shop-domain" => "victim.myshopify.com", # forged tenant
          },
        )

        assert(ShopifyAPI::Utils::HmacValidator.validate(original_request))
        assert(ShopifyAPI::Utils::HmacValidator.validate(spoofed_request),
          "HMAC validation must not depend on topic/shop headers")

        # Demonstrate dispatch is driven purely by the forged, unauthenticated topic
        uninstall_handler = Minitest::Mock.new
        uninstall_handler.expect(:handle, nil) do |data:|
          data.shop == "victim.myshopify.com" && data.topic == "app/uninstalled"
        end

        ShopifyAPI::Webhooks::Registry.add_registration(
          topic: "app/uninstalled", delivery_method: :http, path: "/webhooks",
          handler: uninstall_handler,
        )

        ShopifyAPI::Webhooks::Registry.process(spoofed_request)
        uninstall_handler.verify
      end
    end
  end
end
```
This proves the equality `computed_hmac(raw_body) == received_hmac` holds identically whether `topic`/`shop` are `orders/create`/`attacker.myshopify.com` or `app/uninstalled`/`victim.myshopify.com`, and that `Registry.process` dispatches solely based on the unauthenticated `topic` header, invoking the `app/uninstalled` handler with an attacker-chosen victim shop.
