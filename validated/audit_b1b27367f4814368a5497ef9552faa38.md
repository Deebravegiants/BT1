This confirms the docs explicitly document `data.shop` as the authoritative "shop domain of the webhook," which the sample handler code uses directly (`data.shop`) for routing tenant-specific work (`shop_domain: data.shop`), while the gem's `Registry.process` states it "will verify the request did indeed come from Shopify" — but the verification only covers the raw body, not the shop header this documentation encourages developers to trust.

### Title
Webhook `shop` (and `topic`/`webhook_id`) header fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `HmacValidator.validate` computes the HMAC exclusively over that raw body string. The `shop`, `topic`, `api_version`, and `webhook_id` values are all read straight from unauthenticated HTTP headers and are never included in the signable string, yet `Registry.process` passes `request.shop` (and `request.topic`) directly into `WebhookMetadata`, which is handed to the app's handler as trusted tenant-identifying data.

### Finding Description
The intended identity binding is: `hmac == HMAC(client_secret, signable_string)` should authenticate *all* fields the application acts on, in particular the `shop` that the webhook claims to originate from. In this gem: [1](#0-0) 

- `Request#shop` is parsed from the `shopify-shop-domain`/`x-shopify-shop-domain` header: `T.cast(shopify_header("shop-domain"), String)` [2](#0-1) 
- `Request#to_signable_string` returns only `@raw_body`, excluding all headers: [3](#0-2) 
- `HmacValidator.validate`/`validate_signature` computes and compares the HMAC solely against `verifiable_query.to_signable_string`, i.e., the body: [4](#0-3) 
- `Registry.process` checks only `Utils::HmacValidator.validate(request)` and then forwards `request.shop` unchecked into `WebhookMetadata`, which is delivered to the app handler as the authoritative tenant: [5](#0-4) 

Because Shopify signs webhooks with the single **app-level `client_secret`** (shared across every shop that installs the app), any merchant that installs the app can obtain valid `(body, hmac)` pairs for their *own* shop's webhook deliveries (e.g., by controlling order/product content to shape the body, or simply replaying any webhook they legitimately receive). Since `shop-domain` is excluded from the signed content, that same attacker can resend the identical body and HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still returns `true` because it never inspected the header, and `Registry.process` calls the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", ...)`, breaking the binding `authenticated_shop == acted_upon_shop`.

### Impact Explanation
The library's own documentation instructs integrators to trust `data.shop` from the handler as the shop the webhook pertains to (`docs/usage/webhooks.md`), and the sample handler dispatches shop-scoped work keyed on it. Any downstream consumer that uses `data.shop` to select which merchant's stored session/access token to use, or which tenant's records to create/update/delete, can be made to perform cross-tenant actions using data supplied by an unrelated, unprivileged attacker-controlled shop — a cross-tenant access impact reachable purely through this gem's `Registry.process`/`Request` contract, with no access token, secret, or privileged account required beyond installing the app as an ordinary merchant.

### Likelihood Explanation
High feasibility: obtaining a valid `(body, hmac)` pair requires nothing more than installing the app (or observing any webhook delivery to one's own store) and inspecting the HTTP request; no cryptographic material needs to be recovered because the signature never binds to the shop. The only additional step is resending the request with a modified `shopify-shop-domain` header, which is trivial for any HTTP client.

### Recommendation
Include the claimed `shop` (and ideally `topic`/`webhook_id`) in the signable content, or independently verify `request.shop` against a list of shops with an active, known installation/session before trusting it in `WebhookMetadata`. At minimum, document prominently that `data.shop` is unauthenticated and must be cross-checked by the host application against its own installed-shop/session store before being used for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`; app subscribes to `orders/create`.
2. Attacker triggers an `orders/create` webhook (e.g., places an order), capturing the raw body `B` and the `x-shopify-hmac-sha256` header `H` that Shopify computed with the shared `client_secret`.
3. Attacker POSTs to the app's webhook endpoint with the same body `B` and header `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(client_secret, B) == H` — this passes. [6](#0-5) 
5. The handler receives `WebhookMetadata(shop: "victim-shop.myshopify.com", body: B, ...)` and performs tenant-scoped work under the victim's identity, even though the payload never originated from or pertained to that shop.
