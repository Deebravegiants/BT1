### Title
Arithmetic-underflow panic in `calc_take_pnl` due to decimal-rounding mismatch between the pnl-eligibility guard and the pnl computation - ([File: program/src/processor.rs])

### Summary
`Processor::calc_take_pnl` gates its pnl-extraction math on a "current k ≥ last k" check that is evaluated in **restored (native, floor-rounded) units**, while the actual sqrt/diff computation that follows is performed on the **raw normalized values** stored in `TargetOrders.calc_pnl_x/calc_pnl_y` without ever restoring them. Because `restore_decimal` truncates (floors), the guard is systematically more permissive than the invariant the downstream math actually needs (`x1 ≥ x2` and `y1 ≥ y2`). An attacker able to steer the pool into a boundary state where the floor-rounded guard passes but the true normalized inequality fails will hit an unguarded `.unwrap()` on a `checked_sub` that returns `None`, panicking the transaction. Since this function runs on every `Deposit` and `Withdraw`, a pool that reaches this boundary state becomes permanently unable to process further deposits or withdrawals, freezing all LP funds in the pool.

### Finding Description
The guard is: [1](#0-0) 

`calc_pc_amount`/`calc_coin_amount` are obtained via `Calculator::restore_decimal`, which performs an **integer (floor) division**: [2](#0-1) 

so `calc_pc_amount * calc_coin_amount <= true_unrounded_value`. This makes the guard `pool_pc_amount * pool_coin_amount >= calc_pc_amount * calc_coin_amount` strictly weaker (more likely to pass) than the precise, unrounded comparison `x1 * y1 >= calc_pnl_x * calc_pnl_y` that the subsequent computation actually assumes.

Once inside the branch, the code computes: [3](#0-2) 

`calc_x_power` multiplies the *raw* (non-restored) `target.calc_pnl_x`/`calc_pnl_y` directly against the normalized `x1`/`y1`: [4](#0-3) 

If the floor-rounded native guard passes while the true normalized relation `x1*y1 ≥ calc_pnl_x*calc_pnl_y` does not (which is possible exactly because of the rounding gap introduced by `restore_decimal`), then `x2 = sqrt(x2_power)` can exceed `x1` (or the derived `y2` can exceed `y1`), and `x1.checked_sub(x2).unwrap()` / `y1.checked_sub(y2).unwrap()` panics.

`calc_take_pnl` is invoked from the permissionless `Deposit` and `Withdraw` instructions: [5](#0-4) [6](#0-5) 

Because `target_orders.calc_pnl_x`/`calc_pnl_y` are re-derived from `x1`/`y1` and persisted at the end of every successful Deposit/Withdraw: [7](#0-6) 

any unprivileged LP whose deposit/withdraw amounts drive the pool into this rounding-boundary state can leave `calc_pnl_x`/`calc_pnl_y` "pinned" such that the very next Deposit/Withdraw by *any* user re-triggers the same underflow and reverts — with no instruction path available to un-pin the state through the AMM program itself (Deposit/Withdraw/WithdrawPnl all route through `calc_take_pnl`).

### Impact Explanation
If the pool state settles at this rounding boundary, every subsequent `Deposit` and `Withdraw` transaction against that pool panics and reverts, permanently freezing LPs' ability to withdraw their liquidity or add new liquidity through the AMM program. This is a pool-wide, permanent denial-of-service on LP funds — analogous to the CVE's "hang or repeatable crash" bug class, mapped here onto the swap/LP-math and pnl-accounting surface reachable from `Initialize2`/`Deposit`/`Withdraw`.

### Likelihood Explanation
Triggering the exact rounding coincidence requires precise engineering of vault balances and `calc_pnl_x/calc_pnl_y` state via a sequence of self-chosen Deposit/Withdraw amounts (an unprivileged LP fully controls the amounts in these instructions and can observe/replay pool state to search for the boundary condition, since all inputs — vault balances, fees, decimals — are public). No signer privilege beyond a normal token holder is required, and the arithmetic is on-chain and deterministic, making offline search for a triggering input set feasible, though it is a narrow numerical condition rather than a trivially reachable one on every input.

### Recommendation
Make the eligibility guard and the pnl-extraction math consistent in the same unit space (normalize before comparing, not restore-then-compare against raw normalized values), and replace the unchecked `.unwrap()` calls in `calc_take_pnl` (`x1.checked_sub(x2).unwrap()`, `y1.checked_sub(y2).unwrap()`, and the surrounding `checked_mul`/`checked_div().unwrap()` calls) with `ok_or(AmmError::CalcPnlError)?` (or equivalent saturating/checked handling) so that a boundary miscalculation returns a normal program error instead of panicking, and additionally clamp `x2`/`y2` to `min(x2, x1)`/`min(y2, y1)` before taking the difference.

### Proof of Concept
A concrete failing input requires solving for `(x1, y1, calc_pnl_x, calc_pnl_y, pc_decimals, coin_decimals, sys_decimal_value)` such that:
1. `floor(pool_pc*pool_coin) >= floor(calc_pnl_x*10^pc_decimals/sys) * floor(calc_pnl_y*10^coin_decimals/sys)` (guard passes), and
2. `x1*y1 < calc_pnl_x*calc_pnl_y` (true normalized invariant fails), which forces `sqrt(calc_pnl_x*calc_pnl_y*x1/y1) > x1`.

Because `restore_decimal` always floors, case (2) is reachable whenever the fractional part discarded by the two `restore_decimal` calls is large enough relative to `pool_pc*pool_coin`'s margin over the (mis-scaled) true product — this margin can be driven arbitrarily small by an attacker issuing a sequence of Deposit/Withdraw calls that leave `total_pc_without_take_pnl`/`total_coin_without_take_pnl` and `calc_pnl_x`/`calc_pnl_y` at a near-equal boundary (e.g., immediately after a Deposit/Withdraw that re-pins `calc_pnl_x = x1 - delta_x`, `calc_pnl_y = y1 - delta_y` with `delta_x`/`delta_y` computed from the same rounding-lossy path). A background engineer should reproduce this with the existing `test_swap_base_in`/withdraw unit-test harness in `program/src/processor.rs` (lines ~3122-3243) by iterating small `pc_decimals`/`coin_decimals` combinations and deposit/withdraw amount sequences to numerically confirm a case where `x2_power.integer_sqrt() > x1`.

    pub fn calc_x_power(last_x: U256, last_y: U256, current_x: U256, current_y: U256) -> U256 {
        // must be use u256, because u128 may be overflow
        let x_power = last_x
            .checked_mul(last_y)
            .unwrap()
            .checked_mul(current_x)
            .unwrap()
            .checked_div(current_y)
            .unwrap();
        x_power
    }

    pub fn restore_decimal(val: U128, native_decimal: u64, sys_decimal_value: u64) -> U128 {
        // e.g., amm.sys_decimal_value is 10**6, native_decimal is 10**9, price is 1.23, this function will convert (1.23*10**6) -> (1.23*10**9)
        // let ret:u64 = val.checked_mul((10 as u64).pow(native_decimal.into())).unwrap().checked_div(amm.sys_decimal_value).unwrap();
        let ret_mut = val
            .checked_mul(U128::from(10).checked_pow(native_decimal.into()).unwrap())
            .unwrap();
        let ret = ret_mut.checked_div(sys_decimal_value.into()).unwrap();
        ret
    }
