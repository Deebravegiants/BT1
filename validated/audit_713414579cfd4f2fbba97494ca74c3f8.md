### Title
Fee-on-transfer/deflationary tokens allow escrow-accounting desync and cross-order fund drain in `IntentGatewayV2.placeOrder` (Tron) - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` computes the order commitment and credits the internal `_orders[commitment][token]` escrow ledger using the *nominal* `order.inputs[i].amount` (reduced only by the protocol fee), before any token transfer occurs, instead of measuring the amount the contract actually received. This is the same bug class as the Sanshu Inu/KEANU incident, where a deflationary token's on-transfer burn caused the Memestake contract's reward accounting to diverge from its real token balance.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `placeOrder` first computes `reducedInputs` and the `commitment` hash directly from `order.inputs[i].amount` [1](#0-0) , and only afterward performs the token transfer:

- Non-predispatch path: `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);` followed unconditionally by `_orders[commitment][token] += reducedInputs[i].amount;` with no balance-delta check [2](#0-1) .
- Predispatch path: dust is computed as `balance - requiredAmount` against `requiredAmount = order.inputs[i].amount` (the nominal amount), and the escrow is still credited with `reducedInputs[i].amount` (nominal, fee-reduced) rather than the actually swept balance [3](#0-2) .

This is a regression relative to the mainline EVM `IntentGatewayV2.sol`, which explicitly snapshots `balanceOf` before and after every transfer, mutates `order.inputs[i].amount` to the actual received amount, and only computes the commitment/protocol fee/escrow credit from that actual amount [4](#0-3) . The project's own test suite (`FeeOnTransferToken`) demonstrates this is a recognized, previously-fixed attack surface for the mainline contract [5](#0-4) , confirming the fix was never ported to the Tron deployment.

Any ERC-20 with a transfer fee, rebase-down, or burn-on-transfer mechanism (analogous to KEANU in the Sanshu Inu incident) placed as an order input on the Tron gateway will cause the contract to record more tokens in `_orders[commitment][token]` than it actually holds for that token, because the credited amount is derived from the pre-transfer nominal amount rather than the post-transfer balance delta.

### Impact Explanation
Because `_orders[commitment][token]` is a shared per-token accounting ledger used to authorize escrow release/refund to fillers and users, over-crediting it for one order using a deflationary token inflates the pool's claimed balance beyond the actual token balance held by the contract. Every subsequent legitimate order or filler settlement for that token draws from the same underfunded pool, so once the shortfall is exploited (e.g., an attacker deliberately places many small deflationary-token orders, or the disparity accumulates over normal usage), later filler withdrawals or user refunds for genuine, correctly-collateralized orders can fail or be paid out of value effectively contributed by other users — a direct case of insolvency/fund drain analogous to the 56 ETH loss in the Sanshu Inu incident, where reward payouts also diverged from actual token receipts.

### Likelihood Explanation
Reachable by any unprivileged user submitting a single `placeOrder` transaction with a fee-on-transfer/deflationary token as an input asset — no special privileges, governance, or multi-step setup required. The Tron IntentGateway does not restrict which ERC-20 tokens may be used as order inputs, and the accounting flaw triggers deterministically whenever `balanceOf(this)` after `transferFrom` is less than the amount used for escrow crediting.

### Recommendation
Port the mainline `evm/src/apps/IntentGatewayV2.sol` fix to the Tron contract: snapshot `balanceOf` (or native balance) before and after every token movement, derive `order.inputs[i].amount` (and consequently `reducedInputs`, the commitment, and the escrow credit in `_orders[commitment][token]`) from the actually-received delta, not the pre-transfer nominal amount, for both the predispatch and non-predispatch code paths.

### Proof of Concept
1. Deploy a fee-on-transfer ERC-20 (e.g., 1% burn on `transfer`/`transferFrom`), analogous to KEANU.
2. Call `IntentGatewayV2.placeOrder` (Tron) with this token as `order.inputs[0].token`, `amount = 1000e18`.
3. The commitment/escrow logic computes `reducedInputs[0].amount` from the nominal `1000e18` (minus protocol fee) at line 362-370, then `safeTransferFrom` at line 459 actually delivers only `990e18` to the contract.
4. `_orders[commitment][token] += reducedInputs[0].amount` credits ~`997e18` (fee-adjusted nominal) into escrow, while the contract's real `balanceOf(this)` increased by only `990e18` — a persistent 7e18 shortfall recorded against the shared per-token ledger, verified by comparing `IntentGatewayV2._orders(commitment, token)` to `IERC20(token).balanceOf(address(intentGateway))` after the call.

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
