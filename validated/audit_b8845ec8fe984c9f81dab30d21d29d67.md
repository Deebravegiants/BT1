### Title
Timeout refunds in HyperFungibleToken/WrappedHyperFungibleToken are blocked by `whenNotPaused`, trapping bridged funds until the privileged pauser acts - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`onPostRequestTimeout` in the Hyper Fungible Token apps (`HyperFungibleToken.sol`, `HyperFungibleTokenUpgradeable.sol`, `WrappedHyperFungibleToken.sol`, `WrappedHyperFungibleTokenUpgradeable.sol`) is the sole mechanism that refunds a user's escrowed/burned funds after a cross-chain `send()` request times out, yet it is gated by `whenNotPaused` in addition to `onlyHost`. This mirrors the C4 finding: a "pause" state that is meant to stop *new* risky actions instead also blocks the *exit/refund* path that users rely on to recover funds already committed to the protocol, making fund recovery dependent on a privileged actor lifting the pause.

### Finding Description
When a user calls `send()` on `HyperFungibleToken`/`WrappedHyperFungibleToken`, funds are escrowed or burned and a cross-chain `PostRequest` is dispatched through the ISMP host. If the destination never delivers the message before `timeoutTimestamp`, the source-chain host (via `HandlerV2.handlePostRequestTimeouts` → `EvmHost.dispatchTimeOut`) calls back into the app's `onPostRequestTimeout`, whose entire job is to return the user's funds: [1](#0-0) 

That function is restricted with `onlyHost whenNotPaused`, so if the contract is in the `paused` state, the timeout callback reverts. Per the documented `EvmHost.dispatchTimeOut` semantics, if the callback reverts the commitment metadata is restored so it "can be retried", but no refund occurs until it eventually succeeds: [2](#0-1) 

The same pattern exists in the upgradeable variant: [3](#0-2) 

This is structurally identical to the Reserve Protocol issue: `RToken.redeem` was gated by `notFrozen` (should work while merely "paused") but transitively depended on `BasketHandler.refreshBasket`, which required the OWNER/governance to act while paused. Here, the refund of already-escrowed/burned user funds is gated by `whenNotPaused`, so it transitively depends on the pauser (an EOA/multisig with pausing rights) unpausing the contract before a user can reclaim funds from a request that already failed to deliver. A pause is meant to stop new inbound/outbound risk exposure, not to block users from recovering funds tied to requests that have already timed out — exactly the "should be exempted from pause but isn't" design flaw identified in the report.

### Impact Explanation
Any user (an unprivileged token bridger) who dispatches a cross-chain transfer via `send()` and whose request subsequently times out cannot reclaim escrowed/burned tokens if the app happens to be paused at relay-time — even though the underlying ISMP request has already legitimately timed out and the refund is otherwise fully computed and ready. Funds remain stuck in the contract (or permanently burned with no compensating mint) for the duration of the pause, which is entirely at the discretion of the pauser. This is a freezing-of-funds condition reachable by a normal user transaction with no governance/consensus compromise required — it only requires the ordinary, expected event of the contract being paused (e.g., for an incident response) while a user's request is in-flight and subsequently times out.

### Likelihood Explanation
Likelihood is moderate to high in practice: pausing is an expected, non-malicious operational lever (used for incident response, e.g., after a fraud-proof freeze or bug discovery), and any user with a request in-flight during that window is affected purely by chance. No attacker action is needed — this is a routine liveness bug that surfaces whenever pause and timeout windows overlap, which will happen regularly given normal ISMP timeout durations (often much longer than incident response windows).

### Recommendation
Exempt the refund/exit path from the pause check, mirroring the recommended Reserve Protocol fix (only gate genuinely risky *new* actions like `send()`/mint behind `whenNotPaused`, and let recovery/refund paths like `onPostRequestTimeout` execute regardless of pause state, subject only to `onlyHost`). Concretely, remove `whenNotPaused` from `onPostRequestTimeout` (and the equivalent `onPostRequestTimeout`/refund handlers) across `HyperFungibleToken.sol`, `HyperFungibleTokenUpgradeable.sol`, `WrappedHyperFungibleToken.sol`, and `WrappedHyperFungibleTokenUpgradeable.sol`, so that a paused state can never block users from recovering funds from a request that has already been confirmed as timed-out by the host.

### Proof of Concept
1. Alice calls `send()` on `WrappedHyperFungibleToken`, wrapping/escrowing `SEND_AMOUNT` and dispatching a `PostRequest` with a `timeout` of e.g. 3600s.
2. Before the destination processes the message, the contract owner calls `pause()` (a normal incident-response action, not malicious governance).
3. The request's `timeoutTimestamp` elapses; a relayer submits the timeout proof, and `EvmHost.dispatchTimeOut` (`evm/src/core/EvmHost.sol:885-906`) calls `onPostRequestTimeout` on the app.
4. Because the app is paused, `onPostRequestTimeout`'s `whenNotPaused` modifier reverts; `EvmHost.dispatchTimeOut` restores the commitment for retry but Alice receives no refund.
5. Alice's funds remain locked until the owner chooses to unpause — there is no permissionless path for her to reclaim them in the interim, unlike the underlying ISMP host, which is designed to let `handlePostRequestTimeouts` be called "permissionlessly" by anyone at any time. [4](#0-3)

    function onPostRequestTimeout(PostRequestTimeout calldata incoming) external override onlyHost whenNotPaused {
        HyperFungibleToken.Message memory message = abi.decode(incoming.request.body, (HyperFungibleToken.Message));
        address refundee = _toAddr(message.from);

        if (_isWeth) {
            // Try a native-ETH push first; if the refundee cannot accept native value
            // (e.g. the caller used the ERC-20 deposit path in `send()` from a
            // non-payable contract), re-wrap the withdrawn ETH and deliver the
            // underlying WETH as an ERC-20 transfer so the timeout still settles and
            // funds are not permanently locked.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = refundee.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(refundee, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(refundee, message.amount);
        }

        emit Refunded({to: refundee, amount: message.amount});
    }

    function dispatchTimeOut(
        PostRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onPostRequestTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit PostRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }

### handlePostRequestTimeouts()

Processes timed-out POST requests and triggers refunds.

```solidity lineNumbers
function handlePostRequestTimeouts(
    IHost host,
    PostRequestTimeoutMessage calldata message
) external
```

| Parameter | Type | Description |
|-----------|------|-------------|
| `host` | `IHost` | The IHost contract |
| `message` | `PostRequestTimeoutMessage` | Struct containing timeout proof and requests |

**Access:** Permissionless (can be called by anyone)

**Process:**
1. Verifies timeout proof
2. For each request:
   - Validates timeout timestamp has passed
   - Calls `onPostRequestTimeout()` on source application
   - Refunds relayer fee to payer (only if callback succeeds)

**Important:**
- Application timeout callback is called **before** refund
- If callback reverts, no refund occurs
- Timeout can be resubmitted until callback succeeds
