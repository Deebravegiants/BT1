This confirms the vulnerability structure. The `Utils::VerifiableQuery` interface only requires `hmac` and `to_signable_string` [1](#0-0) , and for webhooks, `to_signable_string` returns only `@raw_body`, excluding the `shop`, `topic`, `webhook_id`, and `api_version` headers from the signed content [2](#0-1) . `Registry.process` trusts `request.shop` for tenant attribution when dispatching to the handler without that field being part of the HMAC-covered data [3](#0-2) .

### Title
Webhook shop-domain header not bound to HMAC signature enables cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Utils::HmacValidator.validate` verifies the HMAC exclusively against that body using the app-wide `api_secret_key`. The `shop` (from the `x-shopify-shop-domain`/`shopify-shop-domain` header) is never included in the signed material, yet `ShopifyAPI::Webhooks::Registry.process` passes this unauthenticated `shop` value straight into the `WebhookMetadata` object delivered to the app's handler as the tenant identifier.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are the two methods required by the `Utils::VerifiableQuery` interface [4](#0-3) . In the webhook implementation:
- `hmac` decodes the `hmac-sha256` header [5](#0-4) .
- `to_signable_string` returns `@raw_body` only [2](#0-1) .
- `shop` is read directly from the `shop-domain` header with no cryptographic binding [6](#0-5) .

`HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it to the received signature [7](#0-6) . Because `to_signable_string` is body-only, the signature is valid for *any* value of the `shop-domain` header as long as the body and app secret match.

Critically, `api_secret_key` is a single, app-wide secret shared across every merchant/shop that installs the app — it is not per-tenant [8](#0-7) . This means any shop that has legitimately installed the app can trigger a real Shopify event, capture the genuine `(raw_body, hmac)` pair Shopify sends for their own store, and replay that exact body/HMAC pair to the app's webhook endpoint while substituting a different `x-shopify-shop-domain` header naming a victim shop. `HmacValidator.validate` will still pass because it only checks the body against the shared secret. `Registry.process` then raises no error and dispatches to the handler with the attacker-chosen `shop` [9](#0-8) , breaking the intended binding: `shop_header == shop_that_actually_produced_and_authorized_this_event_body`.

### Impact Explanation
This is a cross-tenant integrity issue: an unprivileged but legitimately-installed merchant (attacker) can cause the app's webhook handler to process attacker-controlled body content under an arbitrary victim shop's identity. Depending on how the consuming application uses `WebhookMetadata#shop` (e.g., to look up the merchant's session/access token, update per-shop database rows, or trigger per-shop side effects), this can lead to cross-tenant data corruption or actions being taken against a shop that never sent the event — satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Requires the attacker to (a) install the app on their own shop (unprivileged, self-service), (b) trigger any webhook event to obtain a valid `(body, hmac)` pair signed with the shared app secret, and (c) replay it with a forged `shop-domain` header. No access token, `api_secret_key`, or privileged account is required — only ordinary app installation, which any internet user with a Shopify store can do.

### Recommendation
Bind the `shop` domain (and ideally `topic`/`webhook_id`) into the HMAC-covered signable string, or otherwise independently authenticate the shop identity out-of-band (e.g., cross-check against a known/registered shop record) before trusting `request.shop` for tenant-scoped processing in `ShopifyAPI::Webhooks::Registry.process`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook: body `{"id":123}"`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`, valid `x-shopify-hmac-sha256` computed with the app's shared secret.
2. Attacker POSTs the identical body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `HmacValidator.validate` succeeds (body unchanged, same shared secret) [10](#0-9) .
4. `Registry.process` dispatches to the handler with `shop: "victim-shop.myshopify.com"` [11](#0-10) , causing the app to act on attacker-controlled data as if it originated from the victim shop.
