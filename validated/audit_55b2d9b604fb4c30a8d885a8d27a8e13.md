Based on my research, I found a genuine analog to this bug class in orb-core.

### Title
Orb Trusts App-Supplied `user_centric_signup` Flag to Bypass Backend-Verified Enrollment - (File: src/plans/mod.rs)

### Summary
Similar to how the MetaMask `displayMessage` flag lets a dapp control whether a signing operation's critical data is shown before the user approves it, orb-core lets the mobile "World App" (an external, less-trusted party relative to the backend/Orb security boundary) set a `user_centric_signup` flag that determines whether the Orb performs its authoritative, backend-confirmed enrollment (`enroll_user`, which signs the iris code with the secure element and posts/polls the signup backend) or simply trusts a locally computed result. This lets the app-side toggle skip the step that is supposed to consistently confirm and record signup outcomes with the backend, the equivalent of the "message to be displayed/verified" being made optional by an external caller.

### Finding Description
`user_centric_signup` originates from `orb_qr_link::UserData`, decoded from the app-provided QR/backend response and stored on `UserData` returned by `backend::user_status` [1](#0-0) . It is threaded into the signup flow as `qr_codes.user_data.user_centric_signup` [2](#0-1) .

Later, this flag directly decides which code path determines signup success:

```rust
let success = if user_centric_signup && !orb.config.lock().await.ignore_user_centric_signups {
    debug_report.enrollment_status(match signup_reason {
        SignupReason::Normal => enroll_user::Status::Success,
        _ => enroll_user::Status::Error,
    });
    signup_reason == SignupReason::Normal
} else {
    Box::pin(self.enroll_user(orb, debug_report, &capture, pipeline.as_ref(), signup_reason))
        .await
        .is_success()
};
``` [3](#0-2) 

When `user_centric_signup` is `true` (the default-honored behavior, since `ignore_user_centric_signups` defaults to `false`, see [4](#0-3)  and [5](#0-4) ), the Orb never calls `enroll_user::Plan::run`, which is the function that actually performs the secure-element signature over the iris code and posts/polls the backend `signup_post`/`signup_poll` endpoints to authoritatively confirm the signup [6](#0-5) [7](#0-6) . Instead, `success` is derived purely from the orb-local `signup_reason` (a purely on-device fraud/pipeline determination), with no independent backend confirmation of the enrollment outcome — analogous to the dapp being able to toggle off the step that is supposed to consistently be enforced (there, "display the message"; here, "confirm enrollment with the backend of record").

Because `user_centric_signup` comes from data attributable to the app/session rather than the Orb's own authoritative decision process, and the toggle is honored by default, the Orb's report of signup success/failure for a given signup ID may not correspond to what the backend would have independently confirmed via `signup_post`/`signup_poll`, mirroring the report's core complaint that toggles controlled by a less-trusted party should not be allowed to bypass consistently-enforced verification steps.

### Impact Explanation
If the app-centric path is taken, the debug report and downstream success/failure state (and hence which UI feedback the user sees, and what is recorded as a "successful" signup) is decided without the backend ever confirming the signup via `signup_post`/`signup_poll`, and without ever exercising the secure-element signature step in `enroll_user`. This diverges from the "backend as source of truth" enrollment model that all other paths rely on, creating an inconsistency channel where the Orb-reported signup outcome for a given `signup_id` may not match backend-verified state — a misattribution risk in the signup completion record, comparable in class to the dapp being able to suppress the verification/confirmation step that is meant to be non-optional.

### Likelihood Explanation
This path is reachable whenever an app-driven flow sets `user_centric_signup = true` in `authenticated_app_data`, which is the default-honored behavior unless an operator explicitly sets `ignore_user_centric_signups = true` in the Orb's config. Because `ignore_user_centric_signups` defaults to `false`, any deployment that hasn't explicitly overridden it will honor the app's flag, making this reachable under normal operating conditions rather than requiring privileged access.

### Recommendation
Do not let the app-supplied `user_centric_signup` flag alone determine enrollment success without an authoritative backend-confirmed check. Either always execute the full `enroll_user` backend-confirmation flow (signature + `signup_post`/`signup_poll`) regardless of `user_centric_signup`, or require server-side confirmation of the “app-centric” outcome (e.g., have the Orb still poll/report to the backend for confirmation even when skipping user-visible enrollment UI), so that the reported success/failure state is never solely determined by app-supplied, unauthenticated-at-decision-time flags.

### Proof of Concept
1. Provision a QR/backend response where `authenticated_app_data.user_centric_signup = true` (and `user_data_hash` validation passes as designed).
2. Ensure Orb config leaves `ignore_user_centric_signups` at its default (`false`) — see [5](#0-4) .
3. Complete a biometric capture/pipeline run so `signup_reason` is computed locally.
4. Observe that `do_signup` takes the `user_centric_signup` branch at [8](#0-7) , setting `enroll_user::Status::Success`/`Error` purely from the local `signup_reason`, without ever invoking `enroll_user::Plan::run` (i.e., without the secure-element signing step or the `signup_post`/`signup_poll` backend round trip in [6](#0-5) ).
5. The final signup outcome reported by the Orb for that `signup_id` is therefore not corroborated by the backend record, demonstrating the bypass.

fn make_signature(user_qr_code: &qr_scan::user::Data, pipeline: &Pipeline) -> Result<String> {
    let mut ctx = Context::new(&SHA256);
    ctx.update(ORB_ID.as_str().as_bytes());
    ctx.update(user_qr_code.user_id.as_bytes());
    ctx.update(pipeline.v2.ir_net_version.as_bytes());
    ctx.update(pipeline.v2.iris_version.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code_version.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code_version.as_bytes());
    let signed = secure_element::sign(ctx.finish())?;
    Ok(BASE64.encode(&signed))
}
