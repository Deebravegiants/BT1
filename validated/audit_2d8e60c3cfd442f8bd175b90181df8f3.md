### Title
Coalescing logic in `execute_postponed_deposits` conflates deposits of a re-instantiated contract with a prior `Terminated` marker at the same address, cancelling required charges - (File: substrate/frame/revive/src/metering/storage.rs)

### Summary
`execute_postponed_deposits` sorts `self.charges` by contract account and coalesces adjacent entries for the same account, treating any `Alive{amount}`/`Terminated` pair as "undo all deposits made by a terminated contract" regardless of whether the `Alive` entry occurred *before* the termination (correct, should be undone) or *after* re-instantiation at the same address (should be charged for real). Because Rust's `sort_by` is stable, chronological order within the same contract key is preserved, so a sequence `Terminated -> Alive{amount}` (terminate then redeploy at same address in one call stack) is merged into a single `Terminated` entry and `amount` is subtracted from `total_deposit`, and the deposit is never charged via `E::charge` in the final charge/refund loops.

### Finding Description
`execute_postponed_deposits` (substrate/frame/revive/src/metering/storage.rs:385-444) builds `self.charges: Vec<Charge<T>>` from nested `absorb` calls (line 300, 305-308) and explicit `terminate` calls (line 450-452), which push `Charge{contract, state: Terminated}` plus a refund into `total_deposit`. It then sorts by `contract` (line 397, stable sort preserves relative chronological order for equal keys) and coalesces adjacent same-contract entries (lines 398-429).

The merge rule at lines 410-415 handles `(Alive{amount}, Terminated)` and `(Terminated, Alive{amount})` identically: it subtracts `amount` from `total_deposit` and forces the coalesced state to `Terminated`. This is correct for pre-termination charges belonging to the *same* contract instance (their deposit must be voided because the contract no longer exists), but it is applied without regard to *instance* identity - only the account address is used as the coalescing key. If within the same call stack a contract at address `A` is terminated and then a *new* contract is instantiated/redeployed at the same address `A` (address reuse via deterministic address derivation/salt, or terminate+reinstantiate sequences reachable from `bare_call`'s nested sub-call handling), the resulting `charges` vector contains, in chronological (and therefore post-sort) order: `Terminated` (from the first instance's termination) followed by `Alive{amount}` (from the second instance's real storage deposit, pushed via `absorb` at line 305-308).

When coalesced, this `(Terminated, Alive{amount})` pair triggers the same "undo" branch: `total_deposit -= amount` and the merged entry becomes `Terminated`. Consequently:
- The second instance's real storage deposit `amount` is never charged to the origin in the `Deposit::Charge` loop (lines 437-441), because the coalesced entry's state is `Terminated`, not `Alive{Charge(_)}`.
- Meanwhile, `absorb` had already called `absorbed.own_contribution.update_contract(info)` (line 295) which mutates the live `ContractInfo` (`storage_byte_deposit`, `storage_item_deposit`, `storage_bytes`, `storage_items`) for the *new* contract instance as if the deposit had been paid.

The result: the new contract instance persists on-chain with storage-deposit bookkeping fields set as though backed by a reserved hold, but the origin's `HoldReason::StorageDepositReserve` hold is never increased for that amount, and `total_deposit` (used for reporting/other accounting) is also decremented incorrectly. Existing checks (`check_limit`, balance checks in `E::charge`) never trigger because the offending charge entry is silently dropped from the charge/refund execution loops before those checks would run.

### Impact Explanation
The origin obtains free storage backing for a contract redeployed at a previously-terminated address within the same call stack: it can accumulate contract storage without ever paying (or having reserved) the corresponding `StorageDepositReserve` hold, while the on-chain `ContractInfo` deposit bookkeeping believes it is paid. This breaks the deposit-conservation invariant (sum of all `Charge`/`Refund` entries actually executed via `E::charge` no longer matches the net storage deposit implied by the final `ContractInfo` state), and can be leveraged to keep storage permanently unbacked by a hold, i.e., storage rent/deposit is effectively stolen. This matches the "temporary/permanent balance extraction via storage deposit accounting bug" scoped impact, though the root cause is coalescing-by-account-only (an instance-identity confusion), not a refund-before-charge ordering flaw per se — the refund-before-charge ordering itself is comment-documented, intentional design and does not by itself leak more than net-owed value.

### Likelihood Explanation
Requires: (1) a call stack (reachable via `bare_call`/contract cross-calls) that terminates a contract and then instantiates a new contract at the exact same address within the same top-level extrinsic/call stack before `execute_postponed_deposits` runs at the root; (2) the new instance must accrue a non-zero storage charge that gets absorbed into `self.charges` after the `Terminated` marker for that address. Address reuse at the same account within one transaction depends on `revive`'s address-derivation scheme (deterministic salt-based addressing) permitting an attacker-chosen salt/nonce to produce a collision with a just-terminated address in the same call stack — this is plausible for contract-controlled address derivation (e.g. CREATE2-style) but was not fully confirmed in the available code (address-derivation details for instantiate were not retrieved before the tool budget ran out). This is the key remaining uncertainty: if same-call-stack address reuse is not actually reachable by the code (e.g., termination blocks re-instantiation at that address until a later block/nonce advances), the bug is latent/theoretical rather than practically triggerable in a single extrinsic.

### Recommendation
Coalesce charges by `(contract, instance-generation)` rather than by `contract` account alone — e.g., tag each `Charge` with an instance/generation identifier (incremented on each successful `instantiate` at a given address) so that a `Terminated` marker only cancels `Alive` entries belonging to the same instance generation, never a subsequently-instantiated one. Alternatively, insert a hard boundary/flush in the coalescing loop: when a `Terminated` entry is encountered, immediately finalize (drop) all prior same-contract entries as before, but start a *new* independent coalescing group for any entries after it for the same address rather than continuing to merge across the boundary.

### Proof of Concept
Rust unit test in `substrate/frame/revive/src/metering/storage/tests.rs` (extending the existing `TestExt`/`TestMeter` harness):
1. Construct a root `TestMeter`.
2. Simulate: nested meter charges `amount1` for contract `C` via `absorb` (charge deposit added to `C`'s `ContractInfo`).
3. Call `meter.terminate(C, refunded)` to push `Terminated` for `C`.
4. Simulate a second nested meter charging `amount2` for the *same* contract account `C` (representing re-instantiation), and `absorb` it into the root meter, pushing a fresh `Alive{Charge(amount2)}` for `C`.
5. Call `meter.execute_postponed_deposits(&origin, &exec_config)`.
6. Assert: `TestExtTestValue`'s recorded charges include an actual `Deposit::Charge(amount2)` charge call for `C` (expected, since the second instance's deposit must be collected) — and show the current implementation fails this assertion because the coalesced entry ends up `Terminated` and no charge for `amount2` is ever issued.
7. Cross-check: assert `total_deposit` returned equals `refunded`-driven net minus `amount1` only, not further reduced by `amount2`, to pin down the accounting mismatch versus the actual `ContractInfo` deposit fields that were mutated as if `amount2` was paid.
