### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing shop-domain spoofing in `ShopifyAPI::Webhooks::Request` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#hmac` validation only covers the raw request body, while the shop-identifying header (`shopify-shop-domain` / `x-shopify-shop-domain`) is read separately and is never part of the signed material. An attacker who controls any Shopify store with the target app installed can capture one genuinely-signed webhook (valid body + HMAC) and replay it against the app's webhook endpoint with a forged `shopify-shop-domain` header pointing at a victim shop. `Utils::HmacValidator.validate` still succeeds because it only checks `to_signable_string` (the raw body) against the HMAC, so the tenant-identifying field is trusted without being bound to the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

`to_signable_string` returns only `@raw_body`, while `shop` is derived independently from the `shopify-shop-domain`/`x-shopify-shop-domain` header: [2](#0-1) 

`Utils::HmacValidator.validate` computes/verifies the signature purely against `verifiable_query.to_signable_string`: [3](#0-2) 

`Webhooks::Registry.process` then dispatches the handler using `request.shop`, taken straight from the unauthenticated header, once the HMAC check on the body passes: [4](#0-3) 

The binding broken is: `shop authenticated (i.e., covered/verified by HMAC) == shop acted upon (used as the tenant key passed to the handler)`. Before the request: `HMAC covers {raw_body}`; `shop used downstream = header value`. After an attacker's replay with a rewritten `shopify-shop-domain` header but the same (still valid) body+HMAC: `HMAC verification still succeeds` while `shop used downstream = attacker-chosen value`, i.e. the two sides of the equality diverge and the tenant boundary is broken.

### Impact Explanation
An unprivileged internet user who can install the target app on their own (attacker-controlled) shop can obtain a legitimately-signed webhook payload/HMAC pair for arbitrary `raw_body` content simply by triggering that event in their own store. They can then POST that same body+HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` header with any victim shop's domain. `Webhooks::Registry.process` will accept it as authentic (HMAC only checks the body) and hand the host application a `WebhookMetadata` claiming the data originated from the victim shop. Any host application that uses `request.shop` (or `WebhookMetadata#shop`) to key merchant state, look up sessions, or gate per-tenant processing will process attacker-controlled data under the wrong tenant identity — a cross-tenant integrity/confidentiality break rooted entirely in this gem's verification logic, matching the "Critical – cross-tenant access" category.

### Likelihood Explanation
Likelihood is high for any attacker capable of installing the app (a normal, unprivileged flow for public apps): no access token, `client_secret`, or privileged account is required — only the ability to receive one legitimate webhook from their own store and replay it with a modified header, which is a standard HTTP capability.

### Recommendation
Include the tenant-identifying header (`shopify-shop-domain`) — along with `topic`, `api-version`, and `webhook-id` if they are relied upon by handlers — in the value that is HMAC-verified, or otherwise cryptographically bind the shop domain to the signed body (e.g., by validating it against a signature that covers headers+body, as Shopify's newer webhook verification schemes do). At minimum, document that `WebhookMetadata#shop` is unauthenticated header data and must not be trusted for tenant identification without independent verification (e.g., cross-checking against a known installed-shop record).

### Proof of Concept
```ruby
raw_body = '{"id":1}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# Attacker legitimately obtains this body+hmac pair from their OWN shop's webhook delivery.
legit_headers = {
  "shopify-topic" => "orders/create",
  "shopify-hmac-sha256" => Base64.encode64(hmac),
  "shopify-shop-domain" => "attacker-shop.myshopify.com",
}

# Attacker replays identical body+hmac but swaps the shop-domain header to the victim shop.
forged_headers = legit_headers.merge("shopify-shop-domain" => "victim-shop.myshopify.com")

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

ShopifyAPI::Utils::HmacValidator.validate(request) # => true, HMAC only covers raw_body
request.shop                                        # => "victim-shop.myshopify.com" (forged, unverified)

ShopifyAPI::Webhooks::Registry.process(request)
# Handler receives WebhookMetadata with shop: "victim-shop.myshopify.com" despite the
# payload actually being signed for/by attacker-shop.myshopify.com.
```
