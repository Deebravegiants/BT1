## Title
Unbounded ancestry walk in `AncestryChain::ancestry` can loop indefinitely on an attacker-supplied cyclic header set - (File: `modules/consensus/grandpa/primitives/src/justification.rs`)

## Summary
GRANDPA finality-proof verification (`GrandpaJustification::verify_with_voter_set`) walks a relayer-supplied `votes_ancestries: Vec<H>` by following `parent_hash` pointers until it reaches a target `base` hash, with no bound on iteration count or cycle detection, structurally similar to the BIND RPZ bug where an unbounded rule-processing loop hung `named` on a crafted query.

## Finding Description
`AncestryChain::ancestry` walks parent-hash pointers with no depth bound or visited-set check: [1](#0-0) 

```rust
fn ancestry(&self, base: H::Hash, block: H::Hash) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
    let mut route = vec![block];
    let mut current_hash = block;
    while current_hash != base {
        match self.ancestry.get(&current_hash) {
            Some(current_header) => {
                current_hash = *current_header.parent_hash();
                route.push(current_hash);
            },
            _ => return Err(finality_grandpa::Error::NotDescendent),
        };
    }
    Ok(route)
}
```

This is invoked both by `finality_grandpa::validate_commit` (via the `Chain` trait) and directly in `verify_with_voter_set`: [2](#0-1) [3](#0-2) 

`votes_ancestries` is an entirely relayer-controlled `Vec<H>` decoded from an unsigned `handle_unsigned`/consensus extrinsic; `self.ancestry` is a `BTreeMap<H::Hash, H>` built from that vector, keyed by each header's own computed hash. If the ancestry set contains a cycle of headers whose `parent_hash` fields point back to each other and never reach `base`, the `while current_hash != base` loop never terminates — every lookup in the map succeeds because all cycle members are present, so it never hits the `NotDescendent` error path that would otherwise break out.

Unlike the BIND RPZ analog, this loop's non-termination is gated by finding a hash cycle: an attacker would need header contents `A`, `B` with `hash(A) == B.parent_hash` and `hash(B) == A.parent_hash` simultaneously — effectively a 2-cycle fixed point of the header hash function. With a 256-bit cryptographic hash this is not feasible to construct (birthday-bound search on the order of 2^128), so while the code path itself has no explicit bound (in contrast to the Pharos SPV code in `modules/consensus/pharos/primitives/src/spv.rs`, which was hardened with an explicit `MAX_PROOF_DEPTH` check after a similar unbounded-walk issue), practical exploitation is blocked by hash preimage resistance rather than by application-level bounds.

## Impact Explanation
If exploitable, an infinite loop inside GRANDPA justification verification, reached from a single relayed consensus message via `pallet_ismp::Call::handle_unsigned`, would hang block execution indefinitely for any node processing that extrinsic — a route unable to deliver messages / consensus-halting condition. This would qualify as Medium-to-High under the "route unable to deliver messages" acceptance criterion.

## Likelihood Explanation
Low-to-negligible. Unlike the BIND CVE (a straightforward protocol/state-machine bug independent of cryptography), triggering the loop here requires producing a genuine hash cycle across two or more headers, which is computationally infeasible against a standard 256-bit collision-resistant hash. No other loop discovered during this scan (Pharos SPV walk, MMR proof reconstruction, sync-committee ancestor-block loop, EVM `HandlerV2` batch loops) lacked an explicit bound or was reachable without a similarly infeasible precondition — the Pharos code and several others already carry `MAX_PROOF_DEPTH`/length checks specifically to close this class of issue, and no equivalent unbounded loop was found unguarded in the reachable message-dispatch, MMR, or state-machine-proof paths within index coverage.

## Recommendation
Add an explicit iteration cap (e.g., bounded by `votes_ancestries.len()` or a protocol-defined `MAX_ANCESTRY_DEPTH`) and/or a visited-set check in `AncestryChain::ancestry`, mirroring the `MAX_PROOF_DEPTH` guard already applied to the Pharos SPV trie walk in `modules/consensus/pharos/primitives/src/spv.rs`, so the function fails closed with a typed error instead of looping when the supplied ancestry set does not form a simple acyclic chain to `base`.

## Proof of Concept
Not constructible with available tooling: a triggering input requires finding two (or more) headers `A`, `B` such that `hash(A) == B.parent_hash()` and `hash(B) == A.parent_hash()`, which requires inverting/cycling a cryptographic hash function and is computationally infeasible. No working PoC exists; this is noted explicitly as an unverified, likely-impractical exploitation path rather than a demonstrated vulnerability.
