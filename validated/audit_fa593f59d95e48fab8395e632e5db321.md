### Title
Webhook `shop` (tenant identity) field is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook request's authenticity solely via `Utils::HmacValidator.validate(request)`, which computes the HMAC exclusively over the raw request body (`request.to_signable_string` returns `@raw_body`). The `shop` value — read from the `x-shopify-shop-domain` HTTP header — is never included in the signable string and is therefore never authenticated, yet it is passed straight into the handler as the tenant identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `shop` is derived from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header [2](#0-1) . `Registry.process` validates the request using `Utils::HmacValidator.validate(request)`, which in turn calls `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against the received HMAC [3](#0-2) . Since `to_signable_string` never incorporates the shop header, the HMAC check only proves the *body* bytes are intact/authentic; it says nothing about which shop the header claims to be from. Immediately after this check passes, `Registry.process` forwards `request.shop` unchanged into `WebhookMetadata` and the app-supplied handler as the identity of the tenant that generated the event [4](#0-3) .

This breaks the binding: `verified_bytes (raw body) != identity_bytes (shop header)`. The equality that the gem's own documentation promises — "This will verify the request did indeed come from Shopify" and hand the host app an authenticated `data.shop` [5](#0-4)  and [6](#0-5)  — does not actually hold, because `shop` is outside the cryptographically verified scope.

Because the app's `client_secret` (HMAC key) is a single, static value shared across every shop that has the app installed, any merchant who has installed the app (an unprivileged internet user relative to other tenants of the same app) can capture one legitimately-signed webhook delivered to their own store (raw body + `x-shopify-hmac-sha256`), then replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value for a different shop that also uses the app. The HMAC check still succeeds (it only checks the body), so `Registry.process` calls the handler with the attacker-chosen `shop` value attached to the attacker's own webhook body.

### Impact Explanation
This is a cross-tenant identity confusion: an app built on this gem cannot distinguish which shop actually produced a webhook payload beyond trusting the header value that ships unauthenticated in every HTTP request. A host application that keys its tenant-scoped side effects (order sync, inventory writes, notification dispatch, per-shop data storage) off `data.shop` as the docs instruct can be made to attribute a replayed/attacker-supplied body to a victim shop, achieving cross-tenant data injection/confusion strictly through the credential-bearing HMAC path this gem exposes as its verification primitive.

### Likelihood Explanation
Requires only that the attacker legitimately installs (or otherwise has) the app on any shop, receive one real webhook (trivial - trigger any subscribed event on their own store), and replay it with a modified header to the app's shared webhook endpoint. No access to `api_secret_key`, access tokens, or the target shop's credentials is needed — the attacker only reuses a signature that was validly issued to them for their own tenant.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, and ideally `topic`, `webhook-id`, `api-version`) in the signable string used for HMAC computation, or otherwise cryptographically bind the shop identity to the verified payload before trusting `request.shop`/`data.shop`. Shopify's HMAC design only covers the body; the gem (and its documentation) should not represent `data.shop` as verified/authenticated unless it independently confirms this value against a source of truth (e.g., cross-checking the header shop against a known/registered shop for that webhook subscription, or requiring apps to validate `webhook_id` against their own webhook registration records per shop).

### Proof of Concept
1. App developer subscribes to `orders/create` via `ShopifyAPI::Webhooks::Registry.add_registration` and registers the webhook for both `victim-shop.myshopify.com` and `attacker-shop.myshopify.com` (both install the same app) [7](#0-6) .
2. Attacker triggers an `orders/create` event on their own store, capturing the legitimate raw POST body and the `x-shopify-hmac-sha256` header Shopify sent for `attacker-shop.myshopify.com`.
3. Attacker resends that identical body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body normally [8](#0-7) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `@raw_body` [9](#0-8) .
5. The handler is invoked with `WebhookMetadata` carrying `shop: "victim-shop.myshopify.com"` and the attacker's order body, even though `victim-shop.myshopify.com` never sent this event [10](#0-9) .

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
