## Analysis

The reported Sense bug is: a contract computes a "refund" from its **entire current balance** rather than tracking the actual surplus from the operation just performed, so unrelated funds sitting in the contract get swept out. In Hyperbridge, the closest reachable analog is the **inverse failure mode of the same root cause** — native-token overpayment handling around Uniswap V2 fee swaps in `EvmHost` — where the excess ETH refunded by the router is *not* tracked/forwarded back to the original caller at all, permanently trapping user funds in the host contract.

`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest` all convert `msg.value` into fee tokens via: [1](#0-0) [2](#0-1) [3](#0-2) 

In all three, `swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)` is called directly on the router. Uniswap V2's `swapETHForExactTokens` only spends what's needed for the exact output and refunds the *unspent* ETH to `msg.sender` of that call — which is `EvmHost` itself (the router only knows `EvmHost` as caller, not the original transaction sender `_msgSender()`). None of these three functions captures that returned ETH and forwards it back to `_msgSender()`/`post.payer`/`get.context` sender. There is no accounting variable (unlike, e.g., `IntentGatewayV2.placeOrder`, which correctly tracks `msgValue` locally and calls `_sendValue(msg.sender, msgValue)` for the remainder — see [4](#0-3)  for the correct pattern used elsewhere in the same codebase).

Any user who overpays `msg.value` relative to `post.fee`/`get.fee`/`amount` when calling `dispatch()` or `fundRequest()` on `EvmHost` has the difference permanently stranded as native ETH balance on the host contract, with no code path shown that sweeps or refunds stray native ETH back to users (the governance `Withdraw` action operates on the fee-token treasury via `IHostManager.withdraw`, not raw native balance — I was not able to fully verify the internals of that withdraw function before running out of investigation budget, so I cannot confirm whether admin/governance could later reclaim this stuck ETH; but there is no user-facing recovery path in `dispatch`/`fundRequest` themselves).

### Title
Unrefunded excess native-token payment is permanently stuck in `EvmHost` on `dispatch`/`fundRequest` - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest` swap `msg.value` for the exact fee-token amount needed via Uniswap V2's `swapETHForExactTokens`, but never capture or forward the router's ETH refund (unspent `msg.value`) back to the caller.

### Finding Description
Uniswap V2 Router's `swapETHForExactTokens(amountOut, path, to, deadline)` only consumes the ETH required to produce `amountOut` tokens and refunds the remainder to whichever address invoked the router — here, `EvmHost` itself, since `EvmHost` calls the router directly with `{value: msg.value}`. The three call sites: [1](#0-0) [2](#0-1) [3](#0-2) 

do not record the router's return value, do not compute `msg.value - amountSpent`, and never call anything analogous to `_sendValue(_msgSender(), leftover)`. The refunded ETH simply accumulates as native balance on `EvmHost`. This is structurally the same defect class as the reported Periphery bug: a fee-refund computation that fails to correctly account for what was actually spent versus what is held by the contract — except here the omission traps user funds instead of over-paying them.

Contrast with the correct pattern used elsewhere in this same codebase, `IntentGatewayV2.placeOrder`, which tracks `msgValue` as a local running balance through the swap and explicitly refunds the remainder to `msg.sender`: [4](#0-3) 

### Impact Explanation
Any unprivileged user who submits a `dispatch()`/`fundRequest()` transaction with `msg.value` even slightly above the exact ETH cost of the target `fee`/`amount` (which is normal — callers typically cannot predict the exact router output-to-input ratio at submission time and must send a buffer) permanently loses the difference. There is no code path in `dispatch`/`fundRequest` that returns this ETH to the payer, and no evidence of a user-facing sweep function for stray native balance on `EvmHost`. This is a permanent freezing/loss of user funds, reachable from a single unprivileged dispatched request or relayer-fee top-up — satisfying the "permanent freezing of funds" acceptance bar.

### Likelihood Explanation
High likelihood of occurrence in normal operation: because the exact ETH needed for `swapETHForExactTokens` depends on live pool reserves, virtually any caller not perfectly timing/pricing their `msg.value` will overpay by some margin, and 100% of that margin is lost every time. No malicious actor is required — this triggers under ordinary usage by any user of `dispatch()` or `fundRequest()` who pays in native ETH.

### Recommendation
In `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, capture the `amounts` array returned by `swapETHForExactTokens` (as `IntentGatewayV2.placeOrder` already does), compute the unspent `msg.value - amounts[0]`, and forward it back to `_msgSender()` (or the designated `payer`) via a safe ETH transfer, mirroring the `_sendValue` refund pattern already used in `IntentGatewayV2`.

### Proof of Concept
1. User calls `EvmHost.dispatch(post)` where `post.fee = 10` fee-token units, sending `msg.value = 1 ether` (a reasonable buffer since the exact ETH/feeToken price is not known precisely at call time).
2. `EvmHost` calls `router.swapETHForExactTokens{value: 1 ether}(10, [WETH, feeToken], address(this), deadline)`.
3. Suppose only `0.01 ether` was needed; the router sends the remaining `0.99 ether` back to `EvmHost` (the caller of the swap).
4. `dispatch()` proceeds to build/emit the request and returns, without ever moving that `0.99 ether` back to the user.
5. The `0.99 ether` is now stuck as native balance on `EvmHost` with no path shown to return it to the user.
