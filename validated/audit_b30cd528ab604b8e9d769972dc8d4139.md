## Title
Webhook shop-domain and topic headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The reported bug class is "value acted on is not the value that was authenticated" (Uniswap `getPoolPrice()` computing on unchecked/overflowing bits). The closest concrete analog in this Ruby gem is in the webhook-processing path: `ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request **body only**, while the `shop`, `topic`, `webhook_id`, and `api_version` values that `Registry.process` actually acts on (and hands to app handler code) come from unauthenticated HTTP headers that are never included in the signed bytes.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are read straight from headers with no cryptographic binding to them at all: [2](#0-1) 

`Registry.process` validates only the HMAC (over the body) via `HmacValidator.validate`, then immediately trusts `request.topic` and `request.shop` to look up the handler and build the metadata delivered to app code: [3](#0-2) 

The equality the design is supposed to guarantee is:
`bytes verified by HMAC == bytes the handler treats as the authenticated tenant identity (shop) and event (topic)`

In this implementation that equality does not hold — the HMAC only proves "this body was signed with `Context.api_secret_key`" (a secret shared by *all* shops installed on the app), it proves nothing about which shop or topic the body belongs to.

### Impact Explanation
Because the API secret is shared across every merchant using the same app, any merchant who legitimately receives one valid webhook (body + `x-shopify-hmac-sha256` pair) for their own store can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header to impersonate a different, victim shop. `HmacValidator.validate` still succeeds (it only checks the body), so `Registry.process` will invoke the registered handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` attributing the replayed/forged body to the victim's shop. Any host application that trusts `WebhookMetadata#shop` to select or mutate per-tenant data (which is the documented intended use, per `docs`) can thereby have cross-tenant data written under the wrong shop — this is a cross-tenant access issue.

### Likelihood Explanation
This requires only capturing one genuine webhook delivery for an attacker's own (legitimately installed) store — no `api_secret_key`, access token, or TLS interception is required, since the attacker legitimately possesses one valid signed body from their own store's webhook traffic. Constructing bodies that are useful across shops (e.g., topics whose payload is mostly static or attacker-influenced, such as `app/uninstalled` variants or webhooks with predictable/attacker-controlled JSON content) makes exploitation practical, though not universally trivial for every topic.

### Recommendation
Include the tenant/event-identifying fields in the signed material, or otherwise cryptographically bind them: e.g., require the app to independently verify `shop` against a known/registered store list before trusting `WebhookMetadata#shop`, or extend `to_signable_string` / a secondary check to include `shop-domain`, `topic`, and `webhook-id` so a body cannot be replayed under a different identity. At minimum, update documentation to explicitly warn that `WebhookMetadata#shop`/`#topic` are **not** authenticated by the HMAC and must not be trusted for authorization decisions without an additional binding check.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g.:
   - Headers: `x-shopify-topic: app/uninstalled`, `x-shopify-hmac-sha256: <valid HMAC of body>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - Body: `{}`
2. Attacker resends the identical body and HMAC to the app's webhook endpoint, changing only:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `OpenSSL::HMAC.hexdigest(sha256, api_secret_key, raw_body)` — it succeeds because the body and secret are unchanged. [4](#0-3) 
4. The handler registered for `app/uninstalled` is invoked with `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim-shop.myshopify.com", body: {}, ...)`, causing the host app to process an uninstall/reset action for `victim-shop.myshopify.com` that never actually happened.
