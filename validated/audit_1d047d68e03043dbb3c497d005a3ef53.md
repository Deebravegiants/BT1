### Title
Webhook shop/topic identity not covered by HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` fields — which are what `Registry.process` uses to dispatch and attribute the webhook — come from unauthenticated HTTP headers that are never included in the signature. This breaks the binding `hmac_authenticated_shop == shop_the_handler_acts_on`.

### Finding Description
`Utils::HmacValidator.validate` verifies a webhook by recomputing the HMAC over `verifiable_query.to_signable_string` and comparing it to the `hmac` field [1](#0-0) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`: [2](#0-1) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are all parsed straight from HTTP headers with no cryptographic binding to that signature: [3](#0-2) [4](#0-3) 

`Webhooks::Registry.process` validates only the HMAC against the body, then uses the unauthenticated `request.topic` to select the handler and the unauthenticated `request.shop` to build the metadata handed to the host application's handler: [5](#0-4) 

Because the signature only proves "this body was produced with the app's secret for *some* legitimate webhook," and says nothing about which shop or topic it was for, any party who is able to obtain one genuine webhook (e.g., by installing the app on a shop they control, or observing a body whose HMAC they already have) can resend that exact `raw_body` with a forged `shopify-shop-domain` header (any registered shop) and/or forged `shopify-topic` header. `HmacValidator.validate` will report the request as valid because it only checks the body bytes, and `Registry.process` will happily route it as if it came from the victim shop.

This is the same class of bug as the report: a field that is *acted on* (here, the shop identity used for tenant attribution and the topic used for handler dispatch) is not covered by the authenticating HMAC, so the value trusted downstream is disconnected from the value that was actually authenticated.

### Impact Explanation
This crosses a tenant boundary: an attacker-controlled or replayed webhook payload can be attributed to an arbitrary target shop domain, causing the host application's webhook handler to act on the wrong tenant's behalf (e.g., processing a `shop/redact` or `app/uninstalled` body under a victim shop's identity, or replaying any body under a different topic than it was actually signed for). This matches the Critical "cross-tenant access" impact category, since the shop/tenant that consumed the signed bytes is not the shop/tenant the code trusts for the resulting action.

### Likelihood Explanation
Exploitation requires only network access to the app's webhook endpoint plus knowledge of one valid `(raw_body, hmac)` pair — attainable by any developer who installs the app on their own store and receives a legitimate webhook, or by anyone who can observe one such delivery. No access token, `client_secret`, or privileged account is needed; the gem's own `Webhooks::Registry.process`/`Request` API is used exactly as documented.

### Recommendation
Bind the `shop`, `topic`, and other dispatch-relevant fields into the HMAC computation (or otherwise cryptographically tie them to the signed payload), so `to_signable_string` cannot be satisfied by a body whose associated shop/topic were forged via headers. At minimum, the gem should not expose `shop`/`topic` from `Webhooks::Request` as trusted values for host applications without documenting that they are unauthenticated header data, and the HMAC verification should incorporate them.

### Proof of Concept
1. Attacker installs the target app on their own development shop `attacker.myshopify.com` and receives a genuine webhook delivery for topic `T` with body `B`, header `shopify-hmac-sha256: H` valid for `B` under the app's `client_secret`.
2. Attacker crafts a new HTTP POST to the app's webhook endpoint with the same body `B` and header `shopify-hmac-sha256: H`, but sets `shopify-shop-domain: victim-shop.myshopify.com` (and, if desired, `shopify-topic` to any topic registered by the host app).
3. The host app calls `ShopifyAPI::Webhooks::Registry.process(request)`; `Utils::HmacValidator.validate(request)` succeeds because it only checks `raw_body` against `H` [6](#0-5) .
4. `Registry.process` invokes the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)`, so the host app's business logic executes as though `victim-shop.myshopify.com` sent this webhook, even though nothing about the shop or topic was ever authenticated [7](#0-6) .

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
