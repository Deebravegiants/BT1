### Title
Webhook shop-domain identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` value used by consumers of this gem as the tenant/session identifier is read from an unauthenticated HTTP header. This breaks the equality that should hold: `shop_bound_by_hmac == shop_used_for_tenant_identity`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and this is the exact string `Utils::HmacValidator.validate` hashes with the app's `api_secret_key` and compares to the `hmac` header via `OpenSSL.secure_compare` [2](#0-1) . However, `Request#shop` — the value the host application is expected to use to route the webhook to the correct tenant/session — is pulled directly from the `X-Shopify-Shop-Domain` header, which is never included in the signed bytes [3](#0-2) .

Because the HMAC only certifies the body bytes and not the `shop-domain`, `topic`, `api-version`, or `webhook-id` headers, a valid `(body, hmac)` pair generated for one shop remains cryptographically valid no matter which `shop-domain` header value accompanies it. This is the exact pattern the rules flag: "a shop authenticated versus the shop stored as a session key" and "bytes verified versus bytes parsed" — here the verified bytes (raw body) and the parsed tenant identity (header) are disjoint.

An unprivileged internet user who can install the app on their own store (or otherwise obtain one legitimately-signed webhook body/HMAC pair, since HMAC verification only requires knowledge of the `client_secret`-derived signature which Shopify computes and delivers, not something the attacker needs to know) can resend that exact `(body, hmac)` pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` will still report the request as authentic, because the header is outside the signed scope, causing the host application (which relies on this gem's `request.shop` to select the tenant/session, per the documented pattern) to process attacker-controlled webhook content attributed to a different merchant's session.

### Impact Explanation
This crosses the tenant boundary the gem is responsible for asserting: shop-domain identity claimed in `Request#shop` is not cryptographically tied to the HMAC-authenticated payload, enabling cross-tenant webhook injection/spoofing against apps that follow the gem's intended verify-then-trust-`shop` pattern.

### Likelihood Explanation
Likelihood is high given webhook endpoints are internet-reachable by design and replay only requires capturing one legitimately-signed body from the attacker's own installed shop, then modifying only the request headers before resubmission — no access to `api_secret_key` or any victim credential is needed.

### Recommendation
Extend `Request#to_signable_string` (or add a companion binding check) so the `shop-domain`/tenant identity is included in, or otherwise cryptographically bound to, the material verified by `HmacValidator`, so that `hmac_verified_shop == shop_used_for_session_lookup` holds by construction rather than by convention.

### Proof of Concept
1. Attacker installs the app on their own development/test shop `attacker.myshopify.com` and receives a legitimate webhook: body `B` with header `X-Shopify-Hmac-Sha256: H` (valid signature of `B`) and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker resends an HTTP POST to the app's webhook endpoint with the same body `B` and same `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. The host app calls `Request.new(raw_body: B, headers: {...})` then `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (`@raw_body` only) [4](#0-3) [5](#0-4)  — validation succeeds.
4. The app then reads `request.shop` → `"victim.myshopify.com"` [3](#0-2)  and processes attacker-controlled body content against the victim's tenant/session, despite the request never having been authenticated for that shop.
