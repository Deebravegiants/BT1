## Title
Missing Shop Domain Validation in OAuth Authorization Code Grant Leaks `client_secret` to Attacker-Controlled Host - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` and `ShopifyAPI::Auth::Oauth.begin_auth` use the caller-supplied `shop` value to build the destination host for OAuth requests without ever passing it through `ShopifyAPI::Utils::ShopValidator.sanitize!`, unlike every other OAuth flow in this gem (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange`). This breaks the intended equality binding: `host that receives the app's client_secret == a validated *.myshopify.com/trusted domain`. In practice, `client_secret` is only ever sent to whatever host the `shop` string encodes.

### Finding Description
`begin_auth` computes `auth_base_uri(shop)` directly from the raw `shop:` argument with no domain validation: [1](#0-0) 

`validate_auth_callback` is worse: it takes `auth_query.shop` — a value that arrives back at the app's callback endpoint as an ordinary, attacker-visible query parameter reflected in the browser redirect — and uses it unsanitized to build the session/host that receives the request containing `client_id`, `client_secret`, and the authorization `code`: [2](#0-1) 

```ruby
null_session = Auth::Session.new(shop: auth_query.shop)
body = {
  client_id: Context.api_key,
  client_secret: Context.api_secret_key,
  code: auth_query.code,
  ...
}
client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
```

The only gate before this POST is `Utils::HmacValidator.validate(auth_query)`, and `AuthQuery#to_signable_string` does include `shop` in the signed string: [3](#0-2) 

So the HMAC does bind `shop` — but only against the app's own `api_secret_key`. Compare this to the sibling flows that all call `Utils::ShopValidator.sanitize!(shop)` before using `shop` to build the request host: [4](#0-3) [5](#0-4) 

`ShopValidator` exists specifically to enforce that the host receiving OAuth credentials is a trusted Shopify domain (`myshopify.com`, `myshopify.io`, `shopify.com`, `spin.dev`, `shop.dev`, or a custom `myshopify_domain`): [6](#0-5) 

`Oauth.begin_auth` and `Oauth.validate_auth_callback` are the two OAuth entry points that never call it — they are the exception, not the rule, in this codebase.

I was unable to fully verify one thing within the available iterations: whether real-world hosting frameworks (e.g. `shopify_app`) additionally validate `shop` before calling `begin_auth`/`validate_auth_callback`. The rules for this exercise state analogs that depend entirely on "the host application ignoring this gem's documented API" are out of scope. However, this gem's own documentation for the authorization-code flow (`docs/usage/oauth.md`) shows constructing `AuthQuery` directly from raw `request.parameters` with no shop sanitization step, and shows `begin_auth` being called with `shop = request.headers["Shop"]` directly: [7](#0-6) [8](#0-7) 

This means the gem's *own documented usage pattern* does not sanitize `shop` before calling these methods — the gem itself is expected to be the enforcement point, exactly as it is for `ClientCredentials`/`RefreshToken`. This is consistent with the vulnerability being in-scope: the gem fails to apply its own `ShopValidator` protection uniformly.

### Impact Explanation
If an app author follows the documented flow literally (`shop = request.headers["Shop"]`, or constructing `AuthQuery` from raw request parameters as shown in the docs) without adding their own shop-domain validation — which the presence of `ShopValidator` in other flows implies should not be necessary — a user-supplied non-Shopify `shop` value flows unsanitized into `auth_base_uri` and into the POST target host in `validate_auth_callback`. This can cause the app's `client_id`/`client_secret`/authorization `code` to be POSTed to an attacker-chosen host (SSRF carrying the app's `client_secret`), matching the "High — SSRF with the app's credentials" impact category. In the `begin_auth` case it enables the app to redirect a merchant into an attacker-controlled `oauth/authorize` flow.

### Likelihood Explanation
Likelihood is constrained by the fact that in `validate_auth_callback` the request must still carry a valid HMAC computed with the app's real `api_secret_key`, which an external attacker does not possess for arbitrary `shop`/`code` combinations. The most direct path to exploitation is that `begin_auth` accepts and uses an arbitrary `shop` string with zero domain checking before any HMAC involvement — this is reachable purely from unauthenticated input if the host app passes user input into `shop`, and it exactly mirrors the fix already applied to `ClientCredentials`/`RefreshToken`/`TokenExchange` but omitted here, indicating this is a gap in this gem's own defense-in-depth rather than solely a host-app mistake.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) at the top of both `Oauth.begin_auth` and `Oauth.validate_auth_callback`, exactly as done in `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`, and use the validated/sanitized shop value everywhere downstream (`auth_base_uri`, `Auth::Session.new`, `Session.from`).

### Proof of Concept
1. Host app follows the gem's own documented pattern (`docs/usage/oauth.md`) and calls:
   `ShopifyAPI::Auth::Oauth.begin_auth(shop: request.headers["Shop"], redirect_path: "/auth/callback")`
2. Attacker sets the `Shop` header/value to `evil.attacker.com` instead of a `*.myshopify.com` domain.
3. `auth_base_uri("evil.attacker.com")` in `lib/shopify_api/auth/oauth.rb:117-119` returns `https://evil.attacker.com/admin`, and the resulting `auth_route` (containing `client_id` and `redirect_uri`) is returned to the caller for redirection — no `InvalidShopError` is raised, unlike calling `ClientCredentials.client_credentials(shop: "evil.attacker.com")` which raises `ShopifyAPI::Errors::InvalidShopError` per `test_client_credentials_rejects_non_shopify_domain`: [9](#0-8) 
4. No equivalent test exists for `Oauth.begin_auth`/`validate_auth_callback` rejecting a non-Shopify `shop`, confirming the missing check.

```ruby
        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end
```
