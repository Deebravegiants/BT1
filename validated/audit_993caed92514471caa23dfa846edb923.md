### Title
i128 overflow in accrual math permanently freezes a market before the borrow-index cap engages - (File: common/src/rates/index.rs)

### Summary
CVE-2021-26945's class — an integer overflow that crashes the application — maps onto XOXNO Lending as an `i128` overflow in RAY-scaled value arithmetic during interest accrual. On a large market at sustained high utilization, the product `borrowed × borrow_index` (both RAY-scaled) exceeds `i128::MAX` while `borrow_index` is still below `MAX_BORROW_INDEX_RAY`. The panic happens inside accrual, which every state-changing entrypoint runs first via `global_sync`, so the entire market freezes permanently: no supply, borrow, withdraw, repay, liquidate, or `update_indexes` can ever succeed again. The codebase's own test harness demonstrates exactly this cliff.

### Finding Description
Accrual flows through `accrue_step` (`common/src/rates/simulate.rs`), invoked per chunk by `accrue_chunk` in `contracts/pool/src/interest.rs:39-53`, which is run first by `global_sync` (`contracts/pool/src/interest.rs:20-33`) before any mutation. Inside the step, `update_borrow_index` multiplies `old_index × interest_factor` and only *afterwards* clamps to `MAX_BORROW_INDEX_RAY` (`common/src/rates/index.rs:13-19`). Then `calculate_supplier_rewards` computes `borrowed.mul(env, new_borrow_index)` (`common/src/rates/index.rs:80-81`), and `update_supply_index` computes `supplied.mul(env, old_index)` (`common/src/rates/index.rs:34`) — all via `Ray::mul`, which panics with `MathOverflow` when the RAY×RAY/ray result does not fit `i128` (`common/src/rates/scaling.rs:14-16`, `common/src/math/fp_core.rs`).

The mismatch: the index cap is `MAX_BORROW_INDEX_RAY = 10^36` (170× RAY), but the *value* ceiling is `i128::MAX ≈ 1.7e38`. With `borrowed` scaled shares of ~1e27 RAY (≈1 whole token's worth of shares is `amount·RAY/index`; a billion-token 18-decimal market yields `borrowed ≈ 1e36`-scale RAY values), `borrowed × borrow_index / RAY` overflows `i128` at a borrow index far below `10^36`. The cap therefore never engages, because the panic fires in the same step.

The in-repo test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361`) proves the sequence end-to-end: `try_update_indexes_for` fails with `MATH_OVERFLOW`, `borrow_index < MAX_BORROW_INDEX_RAY`, and both `try_withdraw_raw` and `try_repay` fail with the same error.

Reachable path for an unprivileged address: `controller.supply(hub, token, amount)` then `controller.borrow(...)` to push utilization high, after which *any* caller's routine `update_indexes` call once the index crosses the overflow point permanently bricks the market — or the market bricks itself on the next organic interaction. No admin action is required at the freeze point; `update_indexes` is permissionless.

### Impact Explanation
Permanent freezing of funds. Once `borrowed × borrow_index` exceeds `i128::MAX`, every controller verb (`supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, `flash_loan`, `multiply`, etc.) calls `global_sync` first and panics identically. Suppliers cannot withdraw principal or accrued interest, borrowers cannot repay or be liquidated, and the position-NFT collateral backing positions on this spoke is unrecoverable. There is no recovery path in code: indexes and scaled balances in storage are already past the point where the accrual math is representable, and `update_borrow_index`'s cap is unreachable because the multiplication that would produce the capped index panics earlier in the same step.

### Likelihood Explanation
Medium. The trigger needs a very large market (the demonstrated case is ~10^9 whole tokens at 18 decimals on the steep XLM-style rate curve, ~98% utilization, sustained for on the order of years) — well beyond current supply/borrow caps, which `lift_caps` disables in the test. However: (a) caps are governance-set parameters that can be raised for liquid markets; (b) the threshold scales down with token decimals and curve steepness — lower-decimal high-rate markets hit the cliff with less principal; (c) no mitigation bounds `borrowed × index` below `i128::MAX`, so any market whose book grows large enough relative to its index trajectory reaches it deterministically. It is a slow but certain structural limit, not an exploit that pays the attacker; the damage falls on every supplier and borrower in the market.

### Recommendation
Enforce the value ceiling before the index cap can be skipped:

- In `accrue_step`/`update_borrow_index` (`common/src/rates/index.rs`), clamp `new_borrow_index` to `min(computed, MAX_BORROW_INDEX_RAY, i128::MAX / borrowed.max(1) * RAY)` — i.e., cap the index at the largest value that keeps `borrowed × index` inside `i128`. Compute the bound via `mul_div_floor_saturating` or `I256` to avoid introducing a new overflow site.
- Apply the symmetric bound to `update_supply_index` so `supplied × supply_index` stays representable.
- Alternatively, use `mul_div_floor_saturating` for the debt-valuation products in `calculate_supplier_rewards` and `update_supply_index`, accepting a saturated (conservative) valuation rather than a panic — accrual then degrades gracefully at the ceiling instead of bricking the market.
- Add a regression test asserting that markets at cap-adjacent size reach `MAX_BORROW_INDEX_RAY` and stop accruing rather than panicking.

### Proof of Concept
The repository already contains a runnable PoC at `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361`. Sketch:

```rust
let mut t = LendingTest::new()
    .with_market(big("BIG18", 18, xlm_curve()))
    .with_market(col())
    .with_max_utilization_disabled_all_markets()
    .build();
lift_caps(&t, "BIG18", 18);
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);          // unprivileged supply
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", principal * 98 / 100); // unprivileged borrow

loop {
    t.advance_time(YEAR_SECS);
    if let Err(e) = t.try_update_indexes_for(&["BIG18"]) { break e; } // -> MATH_OVERFLOW
}
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW); // frozen
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);    // frozen
```

The panic originates at `borrowed.mul(env, new_borrow_index)` in `calculate_supplier_rewards` (`common/src/rates/index.rs:81`) while `borrow_index < MAX_BORROW_INDEX_RAY`, and propagates through `global_sync` (`contracts/pool/src/interest.rs:39-53`), which fronts every mutating entrypoint — permanently freezing all funds in the market.
