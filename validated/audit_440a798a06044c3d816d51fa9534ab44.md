## Title
Webhook Shop-Domain Spoofing — HMAC Signature Does Not Cover the `shop` (Tenant) Identity — ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) exclusively from the unauthenticated `X-Shopify-Shop-Domain` / `shopify-shop-domain` HTTP header, while the HMAC signature that `Utils::HmacValidator` verifies is computed over the raw request body only. `Registry.process` accepts any request whose body-HMAC is valid and then dispatches the webhook handler using the header-derived `shop`, without that value ever being covered by the signature. This breaks the identity binding: `shop authenticated by HMAC == shop used as the tenant key delivered to the handler`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate_signature` signs/verifies exactly that string with the app's shared `api_secret_key`: [2](#0-1) 

The `shop` (tenant identity) is read straight from a header that is never included in the signed material: [3](#0-2) 

`Registry.process` validates the HMAC (over body only) and then forwards `request.shop` unchecked to the application's handler as the tenant key: [4](#0-3) 

Because the `api_secret_key` used to compute the HMAC is shared across *all* shops that install a given app (it is per-app, not per-shop), any actor who can obtain one valid `(raw_body, hmac)` pair for their own shop installation — e.g., by installing the target app on their own store and capturing a webhook delivery — can replay that exact body/HMAC pair while substituting an arbitrary `X-Shopify-Shop-Domain` header. `HmacValidator.validate` will still return `true` because it never inspects the shop header, and `Registry.process` will hand the forged `shop` value to the app's webhook handler as if it originated from that shop.

### Impact Explanation
This is a cross-tenant identity-binding break: the equality that should hold is `shop bound by HMAC == shop delivered to handler`, but instead `shop delivered to handler` is taken from an attacker-controlled, unauthenticated header. Any host application that uses `WebhookMetadata#shop` (populated directly from `request.shop`) as the tenant/lookup key — a documented and expected usage pattern for this library — can be made to act on another merchant's behalf: e.g., an attacker can trigger `app/uninstalled`-style side effects, inject fabricated order/product data, or otherwise mutate state attributed to a victim shop, using only their own (attacker-owned) app installation's secret-signed traffic. This is a cross-tenant access vulnerability arising directly from this gem's webhook verification and dispatch logic.

### Likelihood Explanation
Likelihood is Medium-High for any consumer of the library's documented webhook flow: obtaining a signed `(body, hmac)` pair only requires installing the target app on an attacker-controlled development/trial store (something any unprivileged internet user can do for public apps), then replaying the captured body with a forged shop-domain header to the app's real webhook endpoint. No access to `api_secret_key` or any privileged credential is needed beyond what an ordinary installer already legitimately receives.

### Recommendation
Bind the shop identity into the authenticated material, or otherwise cryptographically verify that the `shop` domain in the header matches the shop that installed/is associated with the delivered payload before dispatching to handlers. Concretely:
- Include the `shop-domain` (and ideally `topic`, `webhook-id`) header values as part of the string signed/verified by `HmacValidator` (i.e., extend `to_signable_string` to incorporate these headers), or
- Cross-check `request.shop` against the shop of an already-established, authenticated session/subscription before invoking `handler.handle`, rejecting any mismatch.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and registers for a webhook topic (e.g., `orders/create`).
2. Shopify delivers a webhook to the app with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`. Attacker captures `(B, H)`.
3. Attacker crafts a new HTTP request to the same app endpoint with:
   - Body: `B` (unchanged)
   - Header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid since HMAC only covers `B`)
   - Header `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (forged)
   - Header `X-Shopify-Topic`, `X-Shopify-Webhook-Id` as desired.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H`.
5. The registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes `B` as though it were legitimately sent by the victim shop.
