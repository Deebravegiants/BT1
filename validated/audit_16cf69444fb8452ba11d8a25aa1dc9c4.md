### Title
Stale Operator Location Snapshot Reused for User QR-Code Location Validation for up to 23 Hours - (File: `src/plans/mod.rs`)

### Summary
The reported bug describes `CrvDepositorWrapper` trusting a rarely-updated TWAP oracle for a security-critical decision (slippage bound), so decisions are made on stale state that no longer reflects reality. `orb-core` has a structurally analogous pattern: the operator's location is captured once when the operator QR code is scanned, cached in `OperatorData`, and then reused as the ground truth for location-based signup authorization for up to `operator_qr_expiration_time` (23 hours by default) without ever re-verifying that the Orb (and operator) are still at that location.

### Finding Description
When an operator QR code is scanned, `verify_operator_qr_code` fetches `operator_status::LocationData` (team country, session coordinates, stationary coordinates) from the backend and stores it inside `OperatorData` together with a `timestamp: Instant::now()`. [1](#0-0) 

In `scan_remaining_qr_codes`, if the previously cached `OperatorData` is still within `operator_qr_expiration_time` of its scan timestamp, the orb skips re-scanning/re-verifying the operator QR code entirely and reuses the stale `operator_data` (including its `location_data`) directly for the next user signup: [2](#0-1) 

`operator_qr_expiration_time` defaults to 23 hours: [3](#0-2) 

This same stale `operator_data` is then passed into `verify_user_qr_code`, which — because `user_qr_validation_use_only_operator_location` defaults to `true` — sends the *cached* `session_coordinates` (not a freshly captured location) to the backend as the sole location proof for validating the user QR code / signup: [4](#0-3) [5](#0-4) 

The self-serve idle loop (`idle_scan_user_qr_code`) exhibits the same pattern: it reuses `operator_data` across an entire idle-scanning session bounded only by `operator_qr_expiration_time`. [6](#0-5) 

Just as the DeFi bug relies on an oracle price snapshot that is stale relative to the current true asset price, this code relies on a location snapshot that is stale relative to the Orb's true current location, for a window an order of magnitude larger (up to 23 hours) than what a location-based access-control mechanism should tolerate.

### Impact Explanation
Location validation is meant to restrict signups to the location(s) where an operator is authorized to operate (`team_operating_country`, `stationary_location_coordinates`, `session_coordinates`). Because the coordinates used for this check are a single snapshot cached for up to 23 hours, an Orb (or a physically mobile operator) can be relocated to a different, unauthorized location after scanning the operator QR code, and subsequent user signups occurring at the new location will still be authorized using the old, stale coordinates. This allows unauthorized or misattributed signup authorization: signups can be validated as occurring at a location the Orb is no longer physically at, undermining the operator/location-based access control that gates who is allowed to complete a biometric signup.

### Likelihood Explanation
The behavior is deterministic and driven entirely by default configuration values (`operator_qr_expiration_time = 23h`, `user_qr_validation_use_only_operator_location = true`), not by an edge case. Any Orb operating in self-serve mode, or any operator who does not immediately re-scan their operator QR code between signups, exercises this stale-cache path by design, since `scan_remaining_qr_codes` is explicitly written to short-circuit re-verification while within the expiration window.

### Recommendation
Bind the freshness of the location proof used for a signup decision much more tightly to the actual time/place of that specific signup instead of a day-long cache:
- Reduce `operator_qr_expiration_time` to a duration commensurate with realistic operator/Orb dwell time, or
- Re-verify/re-fetch operator location data (or require a fresh GPS/IP-based cross-check) at the time each user QR code is validated rather than solely relying on the cached `OperatorData.location_data`, and
- Cross-check the cached `session_coordinates` against a freshly obtained location signal (e.g., current IP-geo info, as already collected elsewhere in `LocationData::new` via `ip_geo_info`) before accepting it as authoritative for `use_only_operator_location` validation.

### Proof of Concept
1. Operator scans their operator QR code at an authorized location; the Orb stores `OperatorData { location_data, timestamp: Instant::now() }` via `scan_initial_qr_codes`/`scan_remaining_qr_codes`.
2. Within the next `operator_qr_expiration_time` window (up to 23 hours), the Orb is moved to an unauthorized location — `scan_remaining_qr_codes` still matches the `operator_data.timestamp.elapsed() < operator_qr_expiration_time` branch and reuses the original `operator_data` without re-verifying it. [7](#0-6) 
3. A user scans their QR code at the new, unauthorized location; `verify_user_qr_code` calls `backend::user_status::request` with `use_only_operator_location = true`, sending the stale `operator_data.location_data.session_coordinates` from step 1 to the backend. [8](#0-7) 
4. The backend authorizes the signup based on the stale (authorized) coordinates even though the Orb is now physically at a different, unauthorized location — completing an unauthorized/misattributed signup.

                    }
                }

                idle::Value::ButtonPress => unreachable!(),
            }
