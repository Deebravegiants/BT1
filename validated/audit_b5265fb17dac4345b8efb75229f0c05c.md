### Title
Webhook HMAC signature does not cover the `shop-domain` (or `topic`/`webhook-id`) header, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and `ShopifyAPI::Utils::HmacValidator.validate` checks the HMAC exclusively against that raw body. The `shop-domain`, `topic`, `api-version`, and `webhook-id` headers are never part of the signed material, yet `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` (parsed straight from the unauthenticated header) as the tenant identity passed into the app's webhook handler.

### Finding Description
`Request#hmac`/`#to_signable_string` binds the signature to the body only: [1](#0-0) 

`HmacValidator.validate` recomputes the HMAC solely from `to_signable_string` (the body) and compares it to the `hmac` header: [2](#0-1) 

`Registry.process` validates the request this way, then hands the caller's `handler.handle` the `shop` value taken straight from `request.shop` (the `shopify-shop-domain` header), with no separate binding check between the verified body and the header claiming which shop it came from: [3](#0-2) 

Because the app's `api_secret_key` (used to compute the webhook HMAC) is shared across *every* shop that installs the app — it is not per-shop — any legitimate webhook delivery an attacker can obtain for their own shop (e.g., a merchant who has installed the app and receives one authentic webhook, or anyone who can capture one) yields a `(raw_body, hmac)` pair that remains cryptographically valid **regardless of the `shopify-shop-domain`, `shopify-topic`, or `shopify-webhook-id` header values sent alongside it**. Re-POSTing that same body/HMAC pair to the app's public webhook endpoint with a different `shopify-shop-domain` header passes `HmacValidator.validate` unchanged, and the registry then dispatches the handler believing the payload originated from the spoofed shop.

This is the "field acted on but not covered by the HMAC" case: the equality the app relies on is
`verified_shop (derived from a validly-HMACed request) == shop_used_for_tenant_routing (request.shop header)`,
but the gem never enforces this equality — the header is fully attacker-controlled while only the body is authenticated.

### Impact Explanation
This breaks the tenant boundary the webhook signature is supposed to guarantee. A user who can obtain one valid webhook body+HMAC (e.g., from their own shop's installation) can cause the host application to process that payload as if it belongs to an arbitrary other shop that has installed the same app, since the shop identity used for data attribution/routing is taken from an unauthenticated header. Depending on how the host app uses `WebhookMetadata#shop` (e.g., to look up/update per-shop records, mark `app/uninstalled`, trigger GDPR data-erasure workflows, etc.), this enables cross-tenant data corruption or disclosure — a Critical-impact cross-tenant access issue per the rules.

### Likelihood Explanation
Exploitation requires only:
1. Obtaining one legitimately-signed webhook body/HMAC pair (trivial for any merchant who installs the app, since they receive real webhooks for their own shop), and
2. Sending an HTTP POST to the app's public webhook endpoint with the same body/HMAC but a different `shopify-shop-domain` (and/or `shopify-topic`) header — no cryptographic secret is needed for this step.

No credentials, tokens, or privileged access beyond "being able to install the app once, or capture one webhook delivery" are required, which is consistent with an "unprivileged internet user" threat model.

### Recommendation
Include the identity-relevant headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, `shopify-api-version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the request (e.g., HMAC over `headers + body` rather than body alone), so that a valid signature is tied to a specific shop/topic and cannot be replayed with altered header values.

### Proof of Concept
1. App merchant "Attacker Shop" installs the app and receives a legitimate webhook, e.g.:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of BODY signed with app's api_secret_key>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   x-shopify-webhook-id: <id>
   Body: BODY
   ```
2. Attacker replays the exact same request to the app's webhook endpoint, only changing the shop header:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <same valid HMAC of BODY, unchanged>
   x-shopify-shop-domain: victim-shop.myshopify.com
   x-shopify-webhook-id: <id>
   Body: BODY
   ```
3. `ShopifyAPI::Webhooks::Request.new(raw_body: BODY, headers: ...)` and `HmacValidator.validate(request)` succeed because `to_signable_string` only ever returns `BODY`, unaffected by the header change: [4](#0-3) 
4. `Registry.process` invokes the app's handler with `shop: "victim-shop.myshopify.com"` even though the payload was never actually generated for/by that shop: [3](#0-2)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
