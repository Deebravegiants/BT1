### Title
Reentrancy in `IntentGatewayV2.withdraw()` sends tokens before decrementing escrow, reachable via `cancelOrder` for multi-asset orders - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron fork of `IntentGatewayV2` implements `withdraw()` with the same unsafe ordering as the Joe Agent bug: it sends native/ERC20 funds to `beneficiary` via a low-level `.call` *before* decrementing the corresponding `_orders[commitment][token]` escrow entry for that specific token index. `withdraw()` is directly reachable from the public, unprivileged `cancelOrder()` entry point for same-chain orders (`isSameChain == true`), where the caller only needs `order.user == msg.sender`.

### Finding Description
In `withdraw()` [1](#0-0) , for every token in `body.tokens`, the contract performs the external transfer (`beneficiary.call{value: amount}("")` for native token, or a low-level `token.call(...transfer...)` for ERC20) and only afterwards executes `_orders[body.commitment][token] -= amount;`. This is the Checks-Effects-Interactions violation matching the Joe Agent report pattern (external transfer performed before the corresponding balance/escrow accounting is updated).

`withdraw()` is called directly, without any reentrancy guard, from the public `cancelOrder()` function when the order is same-chain and the caller is the order owner [2](#0-1) . `_filled[commitment]` is set at the very top of `withdraw()` [3](#0-2) , so a naive re-entry into `cancelOrder`/`onAccept` for the *same* commitment is blocked by the `if (_filled[commitment] != address(0)) revert Filled();` guard at the top of `cancelOrder` [4](#0-3) . However, for a multi-asset order (e.g. inputs = [native ETH/TRX, ERC20 token]), the loop in `withdraw()` still transfers token[0] to the (attacker-controlled) beneficiary *before* decrementing `_orders[commitment][token[0]]`, and before the loop even reaches token[1]. This differs from the mainline EVM contracts (`evm/src/apps/intentsv2/IntrinsicIntents.sol`/`ExtrinsicIntents.sol`), which received an explicit CEI fix verified by `IntrinsicIntentsReentrancyTest.sol` [5](#0-4)  — the Tron fork of `IntentGatewayV2` does not appear to carry the equivalent per-token escrow-decrement-before-transfer ordering, nor a `nonReentrant` modifier (no `ReentrancyGuard`/`nonReentrant` usage was found anywhere under `evm/tron/contracts/`).

### Impact Explanation
An attacker who places a same-chain order with multiple input assets and designates a malicious contract as `order.user`/beneficiary can call `cancelOrder()` themselves. During the native-token leg of the escrow refund, the malicious beneficiary's `receive()`/fallback executes while the escrow for the *other, not-yet-processed* token index is still fully intact (`_orders[commitment][token]` unchanged). If any externally reachable function (validated against `_filled`, or an ERC20 transfer hook, or another order/commitment combination sharing state) can be triggered from that fallback without hitting the `_filled` guard, escrow can be drained beyond what was legitimately deposited. Even absent a second escape hatch, this is a genuine CEI violation in unprivileged, permissionless code handling user funds, which is the exact bug class described in the report (loss of escrowed funds via reentrant low-level call preceding balance update).

### Likelihood Explanation
Medium. The `_filled` flag blocks the most direct same-commitment double-withdrawal, but the vulnerable ordering (transfer-then-decrement per token) remains in a public, unauthenticated code path (`cancelOrder`) that any user can trigger on their own order with an attacker-chosen beneficiary/token combination, satisfying the "single submitted transaction" threat model in the validation criteria.

### Recommendation
Apply the same CEI pattern already used in the mainline `IntrinsicIntents.sol`/`ExtrinsicIntents.sol`: decrement `_orders[body.commitment][token]` for each token *before* performing the external transfer (native `.call` or ERC20 `transfer`), and add a `nonReentrant` guard to `withdraw()`/`cancelOrder()`/`onAccept()` as defense in depth.

### Proof of Concept
Not independently reproducible from the available index snippets alone — the exact `fillOrder()` implementation of the Tron contract could not be located in this pass (search for `function fillOrder` in `evm/tron/contracts/apps/IntentGatewayV2.sol` returned no matches, suggesting it may be inherited/split across files not covered by the index). Given index size limits, some file contents (e.g., the full Tron `IntentGatewayV2.sol` and any base/inherited contracts defining `fillOrder`) may not be fully available; a Devin session with full repository access should be used to confirm whether a second reachable function reads/writes `_orders[commitment][token]` without checking `_filled`, which would be required to demonstrate concrete fund theft beyond the CEI-ordering violation itself.

        bytes32 commitment = keccak256(abi.encode(order));

        // order has already been filled
        if (_filled[commitment] != address(0)) revert Filled();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain) {
            // Same-chain: validate locally and refund immediately
            // only owner can cancel

            if (orderSource != currentChain) revert WrongChain();

                WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user});

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;

                ++i;
            }
        }
