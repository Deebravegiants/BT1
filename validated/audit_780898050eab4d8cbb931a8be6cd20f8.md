Webhook `shop` (and `topic`/`webhook-id`) identity is trusted from unsigned headers, not bound by the HMAC - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
The gem's webhook HMAC verification only signs the raw request body, while the `shop`, `topic`, and `webhook_id` values that the app uses to route and process the event are read from HTTP headers that are never covered by the signature. This breaks the intended identity binding: `HMAC(secret, signed_bytes) == received_hmac` should imply `signed_bytes == (shop, topic, body)`, but here `signed_bytes == body_only`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers with no cryptographic tie to the body: [2](#0-1) 

`Registry.process` validates only the body/HMAC pair via `Utils::HmacValidator.validate(request)`, then immediately trusts the header-derived `shop`/`topic`/`webhook_id` to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

`HmacValidator.validate` confirms the signature only against `verifiable_query.to_signable_string` (the body), using the app-wide `Context.api_secret_key`, which is shared across every shop that has installed the app — it is not shop-specific: [4](#0-3) 

Because the secret is shared per-app (not per-shop) and the signature covers only the body, any valid `(raw_body, hmac)` pair legitimately produced for one tenant's webhook event can be replayed to the app's public webhook endpoint with the `shopify-shop-domain` (and `shopify-topic`/`shopify-webhook-id`) headers swapped to name a different shop. The signature still validates because it never covered those fields, and the handler receives forged tenant identity: `data.shop` no longer matches which tenant actually produced `data.body`.

### Impact Explanation
This is a cross-tenant identity confusion: the app-level handler is invoked believing an event body belongs to shop B when the header/topic could be substituted to any value chosen by whoever holds one valid signed body (e.g., a merchant who installed the app on their own shop, since Shopify signs their webhooks with the same app secret used for all shops). Depending on how the host app's `WebhookHandler#handle` implementation uses `data.shop` (e.g. `shop_domain: data.shop` per the gem's own documented example), this can let an attacker's legitimately-signed webhook body be attributed to a victim shop, corrupting per-tenant state, queues, or data-request/redact processing keyed by `shop`.

### Likelihood Explanation
Exploitability only requires (1) direct network access to the app's public webhook endpoint — normal internet reachability, no credentials needed — and (2) possession of one valid `(raw_body, hmac)` pair, which any shop that installs the app legitimately receives from Shopify for its own events. No `api_secret_key`, access token, or privileged account is required by the attacker.

### Recommendation
Include the tenant-identifying and routing fields (`shop`, `topic`, `webhook_id`) in the HMAC-signed material, or otherwise cryptographically bind them to the body (e.g., validate that the header-derived shop matches a shop field embedded/verified inside the signed body), so that `to_signable_string` covers every field the handler subsequently trusts.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers any webhook (e.g. `orders/create`), letting Shopify legitimately POST body `B` with header `shopify-shop-domain: attacker.myshopify.com` and a valid `shopify-hmac-sha256` computed over `B` using the app's shared `api_secret_key`.
2. Attacker captures `B` and its accompanying HMAC value (trivial — it's their own webhook traffic to their own server, or any endpoint they control).
3. Attacker POSTs the identical body `B` and identical HMAC to the app's public webhook endpoint but replaces the header `shopify-shop-domain` with `victim.myshopify.com` (and optionally `shopify-topic`/`shopify-webhook-id`).
4. `ShopifyAPI::Webhooks::Request#hmac` reads the unchanged HMAC header; `to_signable_string` returns unchanged `B`; `Utils::HmacValidator.validate` succeeds because it never inspected the `shop` header.
5. `Registry.process` builds `WebhookMetadata.new(shop: "victim.myshopify.com", topic: ..., body: B, ...)` and invokes the app handler, which now believes body `B` originated from `victim.myshopify.com`.
