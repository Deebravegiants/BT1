The Tron variant of the Intent Gateway (`evm/tron/contracts/apps/IntentGatewayV2.sol`) reproduces exactly the fee-on-transfer accounting bug from the report, while the primary EVM contracts (`evm/src/apps/IntentGatewayV2.sol`, `evm/src/apps/intentsv2/IntrinsicIntents.sol`) have already been hardened against it with balance-diff measurement (see the `testPlaceOrder_FeeOnTransferToken_*` tests in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`).

### Title
Fee-on-transfer tokens cause escrow over-accounting and stuck/insolvent withdrawals in Tron IntentGatewayV2 - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`placeOrder` in the Tron `IntentGatewayV2` credits the per-commitment escrow ledger (`_orders[commitment][token]`) using the user-declared `order.inputs[i].amount` (minus protocol fee), instead of the amount the contract actually received via `safeTransferFrom`. For fee-on-transfer (or otherwise deflationary) ERC20 tokens, this causes the escrow ledger to record more tokens than the contract physically holds.

### Finding Description
In the non-predispatch path of `placeOrder`: [1](#0-0) 
the contract calls `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then unconditionally credits `_orders[commitment][token] += reducedInputs[i].amount`, where `reducedInputs[i].amount` is derived purely from the user-supplied `order.inputs[i].amount` minus the protocol fee — never from an actual balance check. [2](#0-1) 

The predispatch branch has a partial mitigation (it checks `balance < requiredAmount` before sweeping from the dispatcher, and computes `dust = balance - requiredAmount`), but it still escrows `reducedInputs[i].amount` (the nominal, fee-free amount) rather than what was actually swept into the gateway: [3](#0-2) 

This contrasts with the fixed EVM implementation, which measures the real balance delta after each transfer and mutates `order.inputs[i].amount` to the actual received amount before computing the commitment and escrow: [4](#0-3) 

When settlement or refund later occurs, `withdraw()` transfers the escrowed amount out via a raw `token.call(transfer...)` with a success check: [5](#0-4) 
Because the ledger recorded more than the contract actually holds for that token, this transfer reverts with `TransferFailed()`, or — in a multi-tenant pool where the same token backs multiple commitments — succeeds by draining balance that rightfully belongs to a different commitment's escrow, leaving that other order's later withdrawal to fail instead.

### Impact Explanation
This is a fund-freezing / accounting-insolvency bug reachable by any single user calling `placeOrder` with a fee-on-transfer (or any deflationary/rebasing) token as input:
1. The escrow ledger becomes permanently over-stated relative to the contract's actual token balance for that token.
2. Cross-chain settlement (`RedeemEscrow`) or refund (`RefundEscrow`) delivered via `onAccept` → `withdraw()` will revert due to insufficient balance, permanently freezing the solver's or user's funds for that order.
3. If other orders share escrow of the same token, their legitimate `withdraw()` calls can be starved by an earlier over-credited order draining the shared pool, effectively socializing the loss across unrelated commitments (a form of fund freezing/theft for uninvolved users).

### Likelihood Explanation
Any attacker or unaware user can trigger this simply by placing an order (`placeOrder`) with a fee-on-transfer ERC20 as an input asset — no privileged access is required. Fee-on-transfer tokens are common enough in production DeFi that this is a realistic single-transaction trigger, not a contrived edge case, and the EVM sibling contract's extensive dedicated test suite (`testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`, etc.) confirms the project explicitly recognizes and defends against this exact class of bug elsewhere — it was simply not ported to the Tron variant.

### Recommendation
Mirror the fix already present in `evm/src/apps/IntentGatewayV2.sol`: after each `safeTransferFrom` (and after each predispatch sweep), measure `balanceOf(address(this))` before and after the transfer and use the actual delta as the amount escrowed and included in the commitment hash, rather than trusting the caller-supplied `order.inputs[i].amount`.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 (e.g., 1% transfer fee) and mint 10,000 tokens to `user`.
2. `user` approves the Tron `IntentGatewayV2` for `1000` tokens and calls `placeOrder` with `order.inputs[0].amount = 1000e18`.
3. `safeTransferFrom` delivers only `990e18` tokens to the gateway (1% fee burned/redirected), but `_orders[commitment][token]` is credited with `reducedInputs[0].amount` computed from `1000e18` (minus protocol fee, if any) — i.e., ~`1000e18` or `997e18`, not `990e18`.
4. When the order is later filled and settlement is delivered cross-chain, `withdraw()` attempts to `token.call(transfer.selector, beneficiary, amount)` for the over-stated escrowed amount, which reverts with `TransferFailed()` because the gateway's actual token balance is short by the fee amount — permanently blocking withdrawal of that escrow (and endangering other commitments sharing the same token's pooled balance).
