### Title
Out-of-sync precision (decimals) between send-time and timeout-refund/delivery time in `pallet-hyper-fungible-token` allows amount inflation - (File: `modules/pallets/hyper-fungible-token/src/lib.rs`, `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`pallet-hyper-fungible-token` bakes the ERC20-side decimal precision into the cross-chain `Message.amount` at `send()` time, but re-reads the *current* `Precisions` storage entry to rescale that same fixed amount back to local balance on `on_timeout()` (refund) and `on_accept()` (delivery). Because `Precisions` is a governance/`CreateOrigin`-mutable value that can legitimately change while a message is still in flight or pending timeout, a user can exploit the window between dispatch and settlement to have their refund/receipt computed with a different decimal scale than the one used to compute the originally encoded amount — inflating the tokens they recover, exactly analogous to the ECO L1/L2 inflation-multiplier bug.

### Finding Description
In `send()`, the pallet reads `Precisions::<T>::get(params.asset_id, params.destination)` at the moment of dispatch and uses it to pre-scale the outgoing amount into the fixed-width `Message.amount` field that is embedded in the ISMP POST body: [1](#0-0) 

That `erc20_amount` is computed via `convert_to_erc20`, which multiplies by `10^(erc_decimals - local_decimals)`: [2](#0-1) 

On timeout, `on_timeout()` decodes that same fixed `message.amount` and rescales it back to a local balance, but it looks up `Precisions` **again, at the time the timeout is processed**, not the value that was in effect when `send()` ran: [3](#0-2) 

The same re-lookup pattern exists for successful deliveries in `on_accept()`: [4](#0-3) 

`Precisions` is not immutable per route — it can be freely overwritten for an already-registered chain via `update_token`, which inserts into `Precisions` unconditionally for any chain in `add_chains` regardless of whether that chain was previously configured: [5](#0-4) 

Because `convert_to_balance` divides the fixed, already-scaled amount by `10^(erc_decimals - local_decimals)` using whatever `erc_decimals` is current at settlement time, a decrease in the configured `erc_decimals` between the time a `send()` dispatch is created and the time its timeout (or delivery) is processed causes the divisor to shrink, inflating the resulting local balance by a full power of 10 relative to what was actually locked/burned.

This is the same root cause as the ECO L1/L2 inflation-multiplier bug: a scaling parameter used to convert an amount for a cross-chain settlement is captured once at dispatch time but re-applied at a later, different value during finalization/refund, and a user with control over the timing (e.g., choosing a short timeout so the message naturally expires, or waiting for a scheduled precision update) can profit from the mismatch.

### Impact Explanation
An unprivileged user who calls `send()` can:
1. Dispatch a transfer for a given `(asset_id, destination)` pair while `Precisions[asset_id][destination] = D1`.
2. Wait for (or otherwise cause) the ISMP request to time out before `D1` changes to `D2` via a routine `update_token` precision correction.
3. When `on_timeout` runs, `convert_to_balance` divides by `10^(D2 - local_decimals)` instead of `10^(D1 - local_decimals)`. If `D2 < D1`, the refunded local balance is inflated by `10^(D1-D2)`, minting/unlocking far more than was originally escrowed or burned — a direct unbacked mint / theft of pooled/escrowed funds from the pallet's custody account or asset supply.

Because decimal-precision differences are typically whole powers of ten (unlike the small percentage swing in the ECO inflation multiplier), the potential amplification per exploit is much larger, making this a critical fund-drain vector against the pallet's escrow account or the local asset's supply invariant.

### Likelihood Explanation
Precision updates via `update_token` are an expected, routine administrative operation (correcting a misconfigured token's decimals, adding new EVM peers with a different decimal count, etc.), not a malicious act, so the precondition (a precision change occurring) is realistic in day-to-day pallet operation. A user only needs to time an outbound `send()` with a short timeout (or simply wait) around a scheduled/likely precision correction to exploit the mismatch, and the pallet provides no defense (e.g. embedding the precision used, or the originally-converted local amount, in the message) against this.

### Recommendation
Do not re-derive the local-balance amount from the ERC20-scaled `message.amount` using the *current* `Precisions` value at refund/settlement time. Instead:
- Embed the local-denomination amount (or the precision value used at `send()` time) directly in the outbound `Message`/request context so `on_timeout` can refund the exact original amount without re-conversion, or
- Snapshot the precision used for a given in-flight commitment (e.g., store `(commitment -> erc_decimals)` at `send()` time) and use that snapshot for the corresponding timeout refund instead of the live `Precisions` map.

### Proof of Concept
1. Governance/`CreateOrigin` registers `asset_id=X` for `destination=EVM-1` with `Precisions[X][EVM-1] = 18` (`local_decimals = 12`).
2. User calls `send(asset_id=X, destination=EVM-1, amount=1_000, timeout=short)`. `convert_to_erc20(1_000, 18, 12) = 1_000 * 10^6 = 1_000_000_000` gets embedded as `message.amount` and 1,000 local units are burned/escrowed: [6](#0-5) 
3. Before the request is relayed, `CreateOrigin` runs `update_token` to correct `Precisions[X][EVM-1]` to `15` (still `>= local_decimals`, passes the `ErcDecimalsBelowLocal` check).
4. The request times out (short timeout, or relayer delay). `on_timeout` runs `convert_to_balance(1_000_000_000, erc_decimals=15, local_decimals=12) = 1_000_000_000 / 10^3 = 1_000_000` local units, refunding **1,000,000** instead of the original **1,000** — a 1000x inflation minted/unlocked to the user: [7](#0-6)

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
