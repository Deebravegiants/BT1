### Title
Missing monotonicity/staleness check on `finalized_height` in Arbitrum and Optimism consensus clients allows rollback of trusted consensus state - ([File: modules/ismp/clients/ismp-arbitrum/src/lib.rs], [File: modules/ismp/clients/ismp-optimism/src/lib.rs])

### Summary
`ArbitrumConsensusClient::verify_consensus` and `OptimismConsensusClient::verify_consensus` unconditionally overwrite `consensus_state.finalized_height` with the height proven by a submitted membership proof, with no check that this height is greater than the previously trusted `finalized_height`. Every other consensus client in the codebase enforces this invariant explicitly (BSC's `ExpiredUpdate`, Pharos's `StaleUpdate`/`EpochRegressed`, BEEFY's `StaleHeight`, sync-committee's period/slot ordering checks, GRANDPA's ancestry-based check), which is exactly the class of defect described in the go-tuf advisory: a client accepts and persists new "version" state without validating it against the previously trusted state.

### Finding Description
In `modules/ismp/clients/ismp-arbitrum/src/lib.rs::verify_consensus` (both `ArbitrumOrbit` and `ArbitrumBold` arms) and `modules/ismp/clients/ismp-optimism/src/lib.rs::verify_consensus` (both `OpL2Oracle` and `OpFaultProofGames` arms), the code does: [1](#0-0) [2](#0-1) 

There is no comparison of `state.height.height` against `consensus_state.finalized_height` before the assignment `consensus_state.finalized_height = state.height.height;`. Since Arbitrum's confirmed rollup nodes and Optimism's proposed output roots / resolved dispute games remain permanently present in their respective contracts' storage (nodes/outputs are not deleted once superseded), a submitter can construct a fresh, cryptographically valid membership proof for an *old*, already-superseded node/output and submit it at any later point, driving `consensus_state.finalized_height` backwards in the persisted `ConsensusState` blob.

This contrasts with the codebase's other consensus clients, which all enforce a strict "must be newer" invariant on their own trusted height field before mutating it, e.g. BSC: [3](#0-2) 
Pharos: [4](#0-3) 
BEEFY: [5](#0-4) 

The generic `update_client` handler in `modules/ismp/core/src/handlers/consensus.rs` does separately guard the `StateMachineHeight` → `StateCommitment` map (`latest_commitment_height`) from being overwritten by lower heights: [6](#0-5) 
That protects the externally-consumed state-membership commitments used by apps for message verification. However, it does **not** protect the consensus-client-internal `ConsensusState.finalized_height` field returned by `verify_consensus` and persisted verbatim via `host.store_consensus_state`, because that field is opaque to the generic handler — it is entirely the consensus client's own responsibility to keep it monotonic, and for Arbitrum/Optimism this responsibility is not honored.

### Impact Explanation
Rolling back `ConsensusState.finalized_height` corrupts the persisted trust anchor for these two consensus clients. Concretely:
- It desynchronizes the on-chain trusted state from reality, degrading the security guarantee that the stored consensus state always reflects forward progress — the same class of guarantee CVE-2022-29173 protects for TUF metadata versions.
- Because this field is part of the `ConsensusState` returned to and re-stored by `update_client`, any future logic (current or added later, e.g. auditing, incentive accounting, or freshness gating built on this field, as is done for other clients like BSC/Pharos/BEEFY) that trusts `finalized_height` as a monotonic "last known good" checkpoint can be fooled into believing the light client is behind or that certain heights have not yet been proven, even though higher, valid state commitments already exist in `StateCommitment` storage.
- At minimum this is an unsound consensus-state invariant reachable by any account able to submit a `ConsensusMessage` for these consensus IDs (an unprivileged relayer), which is exactly the pattern this scan is meant to flag; the lack of symmetry with every other consensus client in the repo indicates this is a real gap rather than an intentional design choice.

I was not able to conclusively find a downstream security-critical decision (e.g., challenge-period gating, incentive payout, or freeze logic) in the currently indexed code that reads `ConsensusState.finalized_height` for Arbitrum/Optimism specifically to produce a directly provable fund-theft or freeze scenario — a `grep` for `finalized_height` usage within the arbitrum/optimism client crates returned no matches beyond the definition and assignment sites shown above. This means the full exploitation chain (whether some other part of the codebase, not visible to the index, relies on this field for a security decision) could not be fully verified with the tools available.

### Likelihood Explanation
Likelihood is high for triggering the state corruption itself: any relayer can replay an old, still-provable Arbitrum/Optimism finality proof through the standard `ConsensusMessage` path with no privilege required, and the missing check makes it trivially exploitable to roll back `finalized_height`. Likelihood of using this specifically to steal or freeze funds is uncertain given the current view of the codebase, since no confirmed reader of this field performs a security-relevant comparison.

### Recommendation
Add an explicit staleness/monotonicity check, mirroring BSC's `ExpiredUpdate` / Pharos's `StaleUpdate`, before assigning `consensus_state.finalized_height` in both `ArbitrumConsensusClient::verify_consensus` and `OptimismConsensusClient::verify_consensus`: reject (or treat as a no-op) any proof whose proven height is `<=` the currently trusted `consensus_state.finalized_height`.

### Proof of Concept
1. Submit a valid `ConsensusMessage` for the Arbitrum (or Optimism) consensus client proving a node/output at height `H2` (advances `finalized_height` to `H2`).
2. Later, submit a second valid `ConsensusMessage` containing a membership proof for an older, already-superseded node/output at height `H1 < H2` (still provable because Arbitrum's `_nodes` mapping / Optimism's `l2Outputs` array retain historical entries).
3. `verify_consensus` accepts this proof (all cryptographic/storage checks pass) and unconditionally sets `consensus_state.finalized_height = H1`, rolling back the persisted consensus state despite `H2` already having been recorded as finalized.
