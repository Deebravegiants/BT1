Based on the investigation, I found a structurally analogous pattern in Hyperbridge's OP-Stack fault-dispute-game consensus verification, though I was unable to fully rule out mitigating controls given the exhausted tool budget (noted below).

### Title
Optimism fault-dispute-game verification accepts a state commitment from a still-live (unresolved) dispute game instead of requiring it be finalized - (File: `modules/ismp/clients/optimism/src/lib.rs`)

### Summary
Hyperbridge's `ismp-optimism` consensus client accepts an OP-Stack `OpFaultProofGames` consensus update as soon as the referenced `FaultDisputeGame`/`AggregateVerifier` proxy shows no counter-move at the moment of proof submission, rather than requiring the game to actually be resolved/finalized. This mirrors the Merkl `Distributor.getMerkleRoot` bug class: a state that is still "live" and subject to change is treated as final because only a point-in-time absence-of-dispute signal is checked, not the true finality condition.

### Finding Description
`verify_optimism_dispute_game_proof` in `modules/ismp/clients/optimism/src/lib.rs` (lines 279-386) accepts an L2 output root as a valid `IntermediateState` once it proves: (a) the game is registered in the `DisputeGameFactory`, (b) the `gameImpls[game_type]` matches the expected implementation, and (c) `verify_not_challenged` succeeds. [1](#0-0) 

`verify_not_challenged` (lines 410-499) determines "not challenged" purely from the current value of `claimData.length` (must equal 1) for `FaultDisputeGame`, or `counteredByIntermediateRootIndexPlusOne == 0` for `AggregateVerifier`: [2](#0-1) 

This is exactly the same category of bug as the Merkl `Distributor` finding: it checks a **mutable, live flag/counter at proof time** ("has anyone moved against this claim yet?") rather than the actual finality condition used on L1 itself — a `FaultDisputeGame` is only truly final once its chess clocks expire and `status()`/`resolvedAt` show `DEFENDER_WINS`/`CHALLENGER_WINS`. Nothing in `verify_optimism_dispute_game_proof` or `verify_not_challenged` reads `status` or `resolvedAt`; the code comments explicitly acknowledge this is a "claimData.length == 1" heuristic, not a resolution check.

The remediation path that exists for a dispute discovered *after* acceptance is `pallet_fishermen::blacklist_dispute_game`, which only prevents **future** consensus proofs referencing that same proxy — it does not retroactively invalidate the `StateCommitment` already stored from the earlier `OpFaultProofGames` proof: [3](#0-2) 

That is structurally identical to the Merkl root-cause: detecting the dispute does not retroactively un-trust data already accepted from the disputed state. The generic `veto_state_commitment` extrinsic can still be used to delete that specific `StateMachineHeight` commitment, but this is a separate, discretionary fisherman action distinct from `blacklist_dispute_game`, so a fisherman who blacklists the proxy (the natural first response) does not automatically clear the tainted commitment.

### Impact Explanation
A relayer can submit an `OpFaultProofGames` consensus proof the instant a dispute game is created (before any honest challenger has had a chance to move against it, and long before the OP Stack's real challenge window elapses). If accepted, the resulting `StateCommitment` is stored and — after only the generic ISMP `challenge_period` (which is chain-configured and can be far shorter than OP Stack's actual dispute-game clock) — becomes usable by `HandlerV2.handlePostRequests`/`handleGetResponses` to admit arbitrary Merkle-Mountain-Range-proven requests/responses against that state root: [4](#0-3) 

If the underlying L2 output root is later proven wrong (game resolves `CHALLENGER_WINS`), messages already dispatched/settled against the bogus state root cannot be undone — this is unauthorized state commitment / forged message delivery risk, i.e. potential unbacked minting or fund loss on the destination chain, matching the accepted impact classes.

### Likelihood Explanation
Exploitation requires a byzantine actor able to create or influence a dispute game with a malicious root claim, and to relay the corresponding consensus proof to Hyperbridge before genuine challengers intervene and before the fisherman/blacklist tooling reacts — the same "race the response time of governance/fishermen" pattern the original Merkl report exploited, and the same one the off-chain `op-host`/fisherman watcher (`tesseract/consensus/op-host`, `pallet_fishermen`) is designed to counter reactively rather than by construction. Likelihood is credible but non-trivial since it depends on relayer/fisherman response latency, similar to the original finding's dependency on governor/guardian latency.

### Recommendation
Require actual game finality in `verify_optimism_dispute_game_proof`/`verify_not_challenged`: prove `resolvedAt != 0` and `status` equals the expected winning outcome (or that the configured `maxClockDuration`/finalization delay has elapsed with the game undisputed), instead of accepting "no counter-move yet" as sufficient. Additionally, make `blacklist_dispute_game` also invalidate (or trigger deletion of) any `StateCommitment` already recorded from the blacklisted proxy, closing the same gap the Merkl mitigation closed by tying the "disputed" flag directly into the trust decision rather than leaving stale accepted state as authoritative.

### Proof of Concept
1. Attacker creates a `FaultDisputeGame` on L1 for chain configured in `state_machines_dispute_game_factories_types` with a malicious `rootClaim` encoding a forged L2 state root.
2. Immediately (before `claimData.length` grows past 1, i.e. before any challenger `move()`s), attacker relays an `OpFaultProofGames` consensus message to Hyperbridge.
3. `verify_optimism_dispute_game_proof` → `verify_not_challenged` passes because no counter-move exists yet; the forged `StateCommitment` is stored via `update_client`.
4. After the ISMP `challenge_period` for that state machine elapses (independent of, and potentially shorter than, OP's real dispute window), `HandlerV2.handlePostRequests` accepts MMR proofs rooted in the forged commitment, dispatching arbitrary requests to destination modules.
5. Later, the dispute game legitimately resolves `CHALLENGER_WINS` on L1; a fisherman calls `blacklist_dispute_game` to stop future abuse of that proxy, but the already-processed requests/state commitment from step 3-4 are unaffected unless a fisherman separately and additionally calls `veto_state_commitment` in time.

**Note on confidence**: I could not, within the available tool budget, fully confirm whether an additional, out-of-band finalization/time check exists elsewhere (e.g. enforced off-chain only by the `op-host` relayer before it even submits a proof, per `challenge_slot_keys`/`game_is_challenged` filtering in `tesseract/consensus/op-host/src/lib.rs`). If the protocol relies on honest relayers voluntarily waiting for game resolution before submitting proofs (rather than enforcing it on-chain in the consensus client itself), that would still leave the on-chain verifier exploitable by any relayer who skips that wait — which is the core of this finding.
