Based on the code, there's a genuine identity-binding gap in the webhook processing path: the HMAC signature only covers the JSON body, not the `shop-domain` header, yet the shop value derived from that unauthenticated header is passed straight through to the webhook handler as trusted tenant context.

### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant shop spoofing on webhook delivery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` cryptographically authenticates the body bytes but never binds the `shop` value taken from the `X-Shopify-Shop-Domain` / `shopify-shop-domain` header. `Registry.process` treats a passing HMAC check as proof the entire request (including the shop attribution) is legitimate, and forwards the unauthenticated header value to the app's handler as `data.shop`.

### Finding Description
The webhook request object exposes `shop` purely from a header: [1](#0-0) 

but the signable string used for HMAC verification is only the raw body: [2](#0-1) 

`Registry.process` validates the HMAC and, upon success, immediately constructs the handler payload using `request.shop` without any further binding check between the verified body and the shop header: [3](#0-2) 

The equality that should hold is: `shop attributed to this webhook == shop that produced the signed body`. Because the HMAC (`OpenSSL::HMAC.hexdigest(sha256, api_secret_key, raw_body)`) is computed only over `raw_body`, that equality is never enforced — the header is fully attacker-controllable independent of the signature.

### Impact Explanation
Any entity that can install the app on a shop it controls (an ordinary, unprivileged merchant/developer — no special access, no leaked credentials) receives genuinely-signed webhook deliveries for its own shop. Because the signature covers only the body, that same valid `(body, hmac)` pair remains valid no matter what `shop-domain` header accompanies it. Replaying the captured body/HMAC pair to the app's webhook endpoint with a different, victim shop's domain in the header causes `WebhookHandler.handle` to receive `data.shop = <victim-shop>` attached to the attacker's own webhook body. If the host application (as documented, treating `data.shop` as the authoritative tenant identifier per `docs/usage/webhooks.md`) uses this value to route or persist data per-shop, the attacker can inject their own data under another tenant's identity — a cross-tenant data integrity/confusion issue.

### Likelihood Explanation
Likelihood is high for any app that relies on this gem's webhook shop attribution as-is, since: (1) no secret material beyond having received one legitimate webhook (from the attacker's own shop) is required, (2) the header is fully independent of the signed payload, and (3) the documented `WebhookMetadata#shop` field gives no indication that this value requires separate verification beyond the HMAC check that already occurred.

### Recommendation
Bind the shop identity to the signed payload — e.g., include the shop domain (and ideally the topic) in the signable string used for HMAC verification, or require the app to cross-check `request.shop` against the destination host address registered for the delivered `topic`/subscription id rather than trusting the header directly. At minimum, document prominently that `data.shop` is NOT covered by the HMAC and must not be treated as authenticated without additional verification against known installed shops.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) so Shopify sends a legitimately HMAC-signed request: body `B`, header `X-Shopify-Shop-Domain: attacker.myshopify.com`, header `X-Shopify-Hmac-Sha256: H` where `H = HMAC-SHA256(secret, B)`.
2. Capture `B` and `H`.
3. Send a new POST to the app's webhook endpoint with the exact same body `B` and header `X-Shopify-Hmac-Sha256: H`, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` in [4](#0-3) 
recomputes the HMAC over `B` only, which still matches `H`, so validation passes.
5. `Registry.process` invokes the handler with `shop: "victim-shop.myshopify.com"` even though the body content was generated for `attacker.myshopify.com`.
