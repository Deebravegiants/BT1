### Title
Missing shop-domain validation before sending `client_secret` in OAuth callback - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the HTTP client that submits the app's `client_secret` using the raw, unsanitized `auth_query.shop` value, while every other OAuth grant helper in the same library (`ClientCredentials`, `RefreshToken`, `TokenExchange.migrate_to_expiring_token`) first passes `shop` through `Utils::ShopValidator.sanitize!` to enforce that it belongs to `TRUSTED_SHOPIFY_DOMAINS` before it is used to construct the destination host.

### Finding Description
In `lib/shopify_api/auth/oauth.rb`, `validate_auth_callback` does: [1](#0-0) 
It constructs `null_session = Auth::Session.new(shop: auth_query.shop)` directly and hands it to `Clients::HttpClient`, which derives the destination host as `"https://#{api_host || session.shop}"`: [2](#0-1) 
Compare this to the sibling grant flows, which all validate `shop` before it can influence the request host that receives `client_id`/`client_secret`: [3](#0-2) [4](#0-3) [5](#0-4) 

`Utils::ShopValidator` exists precisely to enforce the binding "host that receives the client_secret == a myshopify.com/trusted domain": [6](#0-5) 

`validate_auth_callback` is the one place in this library that skips this validator entirely, even though `AuthQuery#shop` is a plain attribute populated straight from caller-supplied request parameters: [7](#0-6) 

The identity binding that should hold is: `host_that_receives(client_secret) == ShopValidator.sanitize!(shop)`. In `validate_auth_callback` this becomes `host_that_receives(client_secret) == auth_query.shop` (unsanitized), breaking that equality relative to every other credential-issuing code path in the gem.

### Impact Explanation
If `auth_query.shop` is not constrained to a trusted Shopify domain, `client.request` in `validate_auth_callback` will POST a body containing `client_id` and the app's `client_secret` to `https://#{auth_query.shop}/admin/oauth/access_token` — i.e., an attacker/host-controlled destination. This is the exact "host validated versus host that receives client_secret" pattern called out as a critical binding: leaking the app's `client_secret` is equivalent to full compromise of the app's OAuth identity (an attacker holding it can mint/forge subsequent OAuth and token-exchange requests for any shop).

### Likelihood Explanation
`HmacValidator.validate` does sign over the `shop` field via `AuthQuery#to_signable_string`, which is the intended safeguard for this path: [8](#0-7) 
This reduces likelihood versus a fully open injection, since forging a valid HMAC normally requires the app's `api_secret_key`. However, the missing `ShopValidator.sanitize!` call means this method relies solely on HMAC-over-untrusted-input as its only domain check, unlike every sibling grant method, which layers explicit allow-list validation in addition to (or instead of) HMAC. This is a defense-in-depth gap and an inconsistency that leaves `validate_auth_callback` as the single credential-issuing code path in the library without the domain allow-list enforcement that `ShopValidator` was built to provide.

### Recommendation
Call `Utils::ShopValidator.sanitize!(auth_query.shop)` in `validate_auth_callback` before constructing `null_session`/`HttpClient`, mirroring `ClientCredentials`, `RefreshToken`, and `TokenExchange.migrate_to_expiring_token`, so the host that ultimately receives `client_secret` is always independently constrained to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` rather than relying only on the HMAC check over caller-supplied parameters.

### Proof of Concept
Not independently reproducible from this gem's code alone, since exploitation depends on whether Shopify's authorization server can be induced to echo/sign a non-`myshopify.com` `shop` value in the callback. The concrete, verifiable defect is the structural inconsistency shown above: `validate_auth_callback` in `lib/shopify_api/auth/oauth.rb` (lines 60-113) omits the `Utils::ShopValidator.sanitize!` call that is present in `lib/shopify_api/auth/client_credentials.rb` (line 25), `lib/shopify_api/auth/refresh_token.rb` (line 24), and `lib/shopify_api/auth/token_exchange.rb` (line 103) before the shop value is used to derive the HTTP destination for a request carrying `client_secret`.
