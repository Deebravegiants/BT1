### Title
Opaque swap routes can execute unrelated caller-authorized token transfers - (File: contracts/controller/src/strategies/swap.rs)

### Summary

The router strategy accepts an opaque `Bytes` route and forwards it to the configured swap aggregator, while the controller only constrains the single `token_in` transfer it authorizes for the aggregator. [1](#0-0) [2](#0-1)  Consequently, a route can cause a nested venue contract to request additional authorization from the account owner, such as transferring an unrelated wallet token, while still returning a valid swap output. This is a Medium-severity confused-authorization issue affecting `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply`. [3](#0-2) [4](#0-3) 

### Finding Description

`StrategySwap` is defined only as raw `Bytes`; the controller does not decode a route schema, enumerate its venues, or verify which contracts the router may invoke. [1](#0-0)  The aggregator interface similarly accepts the untyped `swap_xdr` payload. [5](#0-4) 

For `swap_collateral`, the caller supplies `swap` directly and must be the account owner or an approved delegate. [6](#0-5) [7](#0-6)  The withdrawn collateral is then forwarded to `swap_tokens_or_passthrough` together with the unchanged route bytes. [8](#0-7) 

Inside `swap_tokens`, the controller snapshots only its `token_in` and `token_out` balances, authorizes one exact `token_in -> router` transfer for `amount_in`, invokes `execute_strategy`, and later checks only the controller's input spend and output receipt. [9](#0-8) [10](#0-9)  No code limits the route to known venues or asserts that nested contracts do not request additional authorization from `caller`. [2](#0-1) 

A nested venue can therefore include a call such as `unrelated_token.transfer(caller, attacker, balance)`. That call is outside the intended swap operation, but it occurs beneath the caller's authorized strategy invocation and can be included in the authorization tree produced by transaction simulation. The subsequent strategy checks remain satisfied because the controller sees no `token_in` overspend and receives positive `token_out`. [10](#0-9) 

### Impact Explanation

An attacker can steal unrelated tokens held by a user who submits an attacker-constructed route. The stolen assets need not be listed by the lending markets, deposited in the pool, or referenced by the strategy's `token_in` and `token_out` arguments. The protocol's measured-input and measured-output checks do not detect this theft because they only observe the controller's two token balances. [9](#0-8) [11](#0-10) 

### Likelihood Explanation

Exploitation requires the victim to execute a route-bearing strategy using a malicious opaque payload and sign the authorization tree generated for that transaction. This is plausible when route bytes are constructed by an application, keeper, or route provider rather than manually authored by the user, and no privileged controller state or leaked key is required. [6](#0-5) [1](#0-0) 

The controller's balance-delta checks constrain router spending and output, but they do not reduce the route's authorization surface or prevent unrelated nested calls. [10](#0-9) 

### Recommendation

Replace opaque route bytes with a structured route representation whose venue contracts are explicitly allowlisted, or make the aggregator enforce a fixed set of audited venues and reject arbitrary nested contract invocations. The route should bind the expected input token, output token, venues, and permitted token movements so simulation cannot add an unexpected caller-authorized transfer as an implementation detail of an opaque payload. [2](#0-1) [5](#0-4) 

### Proof of Concept

1. Alice supplies USDC and holds an unrelated token `X` in her wallet.
2. An attacker deploys a venue contract whose swap callback calls `X.transfer(alice, attacker, alice_balance)`.
3. The attacker constructs router-specific `swap` bytes that send the legitimate USDC input through that venue and return enough ETH for the strategy's output check.
4. Alice submits:
   ```text
   swap_collateral(
       caller = alice,
       account_id = alice_account,
       current = USDC hub asset,
       amount = supplied USDC amount,
       new = ETH hub asset,
       swap = malicious route bytes
   )
   ```
   The entry point accepts the bytes without decoding or restricting the nested venue. [6](#0-5) [1](#0-0) 
5. The controller withdraws USDC, authorizes only the exact USDC transfer to the configured router, and invokes `execute_strategy(controller, amount_in, swap)`. [9](#0-8) 
6. The router follows the route to the attacker venue, which requests `X.transfer(alice, attacker, alice_balance)` beneath Alice's strategy invocation; simulation includes that child authorization in the signed tree.
7. The router returns ETH to the controller, so the input-spend and positive-output checks pass and Alice's ETH collateral is deposited even though `X` was transferred to the attacker. [10](#0-9) [12](#0-11)
