### Title
Webhook `shop` identity is not bound to the HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating only the raw request body against the HMAC signature, but the `shop-domain` header — which is used to attribute the event to a specific merchant — is never covered by that signature. Any request bearing a validly-signed body can be replayed with an arbitrary `shop-domain` header, causing the app to process the event as if it belongs to a different tenant.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `Webhooks::Request#to_signable_string`, which is defined as `@raw_body` only: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` values are all read directly from HTTP headers, none of which are included in the signable string: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` handed to the app's handler, with no independent check that the header value is consistent with anything cryptographically bound to the signed body: [3](#0-2) 

The equality that should hold is:
`shop_bound_by_signature == shop_used_to_attribute_the_event`

In this gem, the left side does not exist at all — only `raw_body` is bound by the HMAC — so the equality is trivially and always false whenever the header disagrees with the body's true origin.

Because `api_secret_key` is a single shared secret for the whole app (not per-shop), any party who can obtain one validly-HMAC-signed webhook body (e.g., by installing the app on their own store — a free, unauthenticated action any internet user can take — and observing the exact bytes and HMAC value Shopify sends for an event they triggered on their own shop) can resend that same body/HMAC pair to the app's webhook endpoint while swapping the `shop-domain` header to any other merchant's domain. The documented processing pattern shown in `docs/usage/webhooks.md` passes `request.shop` straight through to the handler and instructs apps to use it to key their own shop-scoped logic (e.g., `perform_later(topic:, shop_domain: data.shop, ...)`), so this is not a misuse of an undocumented API — it is the gem's own documented contract that is broken.

### Impact Explanation
This breaks the tenant boundary the webhook signature is meant to guarantee. An attacker who legitimately installs the app on a shop they control can forge webhooks that other merchants' data was affected on a victim shop, or that a victim shop performed an action it did not (e.g., `orders/create`, `app/uninstalled`, `customers/redact`), while carrying the attacker's own controlled payload. This can lead to cross-tenant data corruption, false state transitions (e.g., faking a shop's uninstall/redaction, faking billing/order events), or being used as a building block for further attacks against victim merchants — all without needing the app's `client_secret`, an access token, or any privileged account. This matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is moderate-to-high: it only requires the attacker to install the target app on any Shopify store they control (a normal, unauthenticated action available to any developer), trigger one webhook event, capture the raw bytes and the corresponding `X-Shopify-Hmac-Sha256` value, and replay it against the app's public webhook endpoint with a different `shop-domain` header. No cryptographic secret needs to be recovered — the gem's own verification logic never checks that the header is consistent with the signed payload.

### Recommendation
Bind the shop (and, ideally, topic/webhook_id) into the data that is authenticated, or require the caller/host application to independently verify that `request.shop` corresponds to a shop for which this app holds an active session/installation before trusting it in `WebhookMetadata`. At minimum, document prominently (and ideally enforce in code) that `data.shop` from `WebhookMetadata` must be cross-checked against a known/installed-shop list before being used for any shop-scoped side effects, since it is not part of the cryptographically verified payload.

### Proof of Concept
```ruby
# Attacker installs the target app on their own shop (attacker-shop.myshopify.com)
# and triggers a webhook, e.g. "orders/create". Shopify sends:
#
#   body = '{"id":1,...attacker-controlled order json...}'
#   X-Shopify-Hmac-Sha256 = Base64(HMAC-SHA256(api_secret_key, body))
#   X-Shopify-Shop-Domain: attacker-shop.myshopify.com
#
# Attacker captures the exact raw body + hmac header (they legitimately received it),
# then replays the SAME body + hmac to the app's public webhook endpoint,
# only changing the shop header to a victim shop they do not own:

headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => captured_hmac,          # still valid: body unchanged
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, unauthenticated
  "x-shopify-webhook-id" => "any-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate succeeds (only raw_body is checked),
#    handler.handle receives data.shop == "victim-shop.myshopify.com"
#    with attacker-controlled body, even though victim-shop never sent this event.
```

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
