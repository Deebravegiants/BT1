### Title
OAuth callback resolves the `client_secret`-bearing token request to an unsanitized `shop` host - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the POST target for the access-token exchange (which carries `client_id`/`client_secret`) directly from `auth_query.shop`, with no call to `Utils::ShopValidator.sanitize!`, unlike every other credential-exchanging path in this gem (`ClientCredentials#client_credentials`, `RefreshToken#refresh_access_token`, `TokenExchange#exchange_token`) which all explicitly sanitize/derive `shop` through a trusted-domain check before using it as a request host.

### Finding Description
`validate_auth_callback` only requires that the HMAC over the query (`code`, `host`, `shop`, `state`, `timestamp`) validate against the app's own secret [1](#0-0)  and then immediately uses `auth_query.shop` unsanitized as the host for the token exchange request that carries `client_secret`: [2](#0-1) 

Contrast this with `ClientCredentials#client_credentials` and `RefreshToken#refresh_access_token`, which both call `Utils::ShopValidator.sanitize!(shop)` before constructing the `shop_session` used as the request host, explicitly to guard against `shop` being an attacker-controlled/non-Shopify host: [3](#0-2) [4](#0-3) 

`ShopValidator.sanitize!` exists specifically to reject non-`myshopify.com`/trusted-domain hosts (`evil.com`, `attacker.example`, `myshopify.com.evil.com`, etc.) before a host is trusted as a request target: [5](#0-4) 

The binding equality this bug class targets is: *the host that receives the `client_secret` should equal a validated Shopify-owned domain*. In `validate_auth_callback`, that equality is never checked -- the host is taken verbatim from `auth_query.shop`, whose only protection is HMAC validity against the app's own `api_secret_key`. `AuthQuery#to_signable_string` does include `shop` in the signed payload [6](#0-5) , so in the intended flow (Shopify redirecting a merchant's browser back to the app with a callback query it signed) the `shop` value is authentic. However, this control depends entirely on the assumption that only Shopify (or someone possessing `api_secret_key`) can ever produce a request that reaches `validate_auth_callback` with a matching HMAC. Because `validate_auth_callback` is a library method invoked by the app's controller directly on whatever `AuthQuery` object the app constructs from the incoming HTTP request/params (see the documented usage pattern) [7](#0-6) , there is no additional independent verification inside the gem that `shop` is a `*.myshopify.com`/trusted domain -- the check that every other credential-bearing code path in this codebase performs is simply absent here.

### Impact Explanation
If `validate_auth_callback` is ever reached with a query whose HMAC validates but whose `shop` value is not constrained to a genuine Shopify domain, the gem will issue an HTTP POST containing the app's `client_id` and `client_secret` to `https://#{shop}/admin/oauth/access_token`, i.e., SSRF carrying the app's credentials to an attacker-influenced host. This matches the "High - SSRF with the app's credentials" impact category, and mirrors the root cause pattern in the report: a security-relevant field (`shop`, analogous to `_newSC`) that is nominally covered by a signature check is trusted for a sensitive action (sending `client_secret`) without the same defense-in-depth (`ShopValidator.sanitize!`) applied uniformly across all credential-exchange call sites in the gem.

### Likelihood Explanation
Medium-low. Exploitation requires a way to get an `AuthQuery` accepted by `validate_auth_callback` whose HMAC validates yet whose `shop` field is not a genuine Shopify domain, which in the pure library boundary requires possession of, or an HMAC-validity bypass on, `api_secret_key` — something excluded from scope per the rules. The concrete, in-scope, reachable code-level fact is the missing `ShopValidator.sanitize!` call, which is inconsistent with the rest of the gem's own defense-in-depth pattern for this exact category (host receiving `client_secret`), and any future/host-app misuse or additional relaxation of the HMAC check would immediately turn this into an exploitable SSRF-with-credentials.

### Recommendation
Apply `Utils::ShopValidator.sanitize!` to `auth_query.shop` (and to `shop` in `begin_auth`/`auth_base_uri`) in `lib/shopify_api/auth/oauth.rb` before it is used to build any request host, consistent with `ClientCredentials`, `RefreshToken`, and `TokenExchange`, so that the host receiving the `client_secret` is independently constrained to a trusted Shopify domain rather than relying solely on HMAC validity.

### Proof of Concept
1. Construct/obtain an `AuthQuery` whose HMAC is valid for `Context.api_secret_key` (in the exploitable scenario, an entity capable of computing this signature, or a downstream defect that relaxes HMAC enforcement) with `shop` set to an attacker-controlled host, e.g. `evil.attacker.com`.
2. Call `ShopifyAPI::Auth::Oauth.validate_auth_callback(cookies: cookies, auth_query: auth_query)`.
3. The gem POSTs `{client_id, client_secret, code, expiring}` to `https://evil.attacker.com/admin/oauth/access_token` [8](#0-7) , exfiltrating the app's `client_secret` to the attacker's host — no `ShopValidator.sanitize!` call intervenes, unlike in `ClientCredentials#client_credentials` [9](#0-8)  or `RefreshToken#refresh_access_token` [10](#0-9) .

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state
