## Confirmation

`Bonding.sell` calls `canGraduate(tokenAddress)` unconditionally on every sell [1](#0-0) , and `canGraduate` performs `assetReserve - _launchTimeVirtualLtReserve(token_, pair)` with no underflow guard [2](#0-1) . `Pair.swap`'s K-check permits a 1-wei slack (`(newTokenReserve+1)*(newAssetReserve+1) < _pool.k`) [3](#0-2) , which can let `assetReserve` round below the launch-time virtual reserve on a full round-trip sell, matching the report's unguarded-subtraction bug class.

### Title
Unguarded `assetReserve - virtualLtReserve` Subtraction in `canGraduate`/`previewLtUntilGraduation`/`_prepareGraduationLiquidity` Can Underflow and Permanently Brick a Curve - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.canGraduate`, `Bonding.previewLtUntilGraduation`, and `Bonding._prepareGraduationLiquidity` all compute `realLtRaised`/`ltFromPair` as `assetReserve - _launchTimeVirtualLtReserve(token_, pair)` [4](#0-3) [5](#0-4) , with no check that `assetReserve >= virtualLtReserve` first. This is the same unchecked-subtraction pattern as the external report's `recoverERC20`: `balanceOf - (locked + unclaimed)`.

### Finding Description
`Pair.swap` enforces the constant-product invariant with a +1 slack on both sides: `(newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k` reverts [6](#0-5) . This intentionally loosened check (mirrored from the Virtuals `FPair.sol` fork) allows a sell that returns 1 wei more asset than an exact round trip would, because the checked product only has to clear `k`, not exceed it exactly. On a token whose curve has been fully round-tripped (a buy immediately followed by an equal-and-opposite sell, pushing `tokenReserve` back to essentially its virtual maximum), this slack can let `newAssetReserve` land one wei below the launch-time `virtualLtReserve` that was baked into `Pair.k()` at mint (`k = TOTAL_SUPPLY * virtualLtReserve_init`, recovered via `_launchTimeVirtualLtReserve`) [7](#0-6) .

Because the contracts compile under Solidity 0.8.24 with default checked arithmetic (no `unchecked` block wraps this subtraction), `assetReserve - virtualLtReserve` reverts with a Panic(0x11) arithmetic-underflow error rather than silently wrapping. Since `Bonding.sell` calls `canGraduate(tokenAddress)` unconditionally as a pre-check on every sell [1](#0-0) , and `Bonding.buy` → `_executeBuy` is documented to check `canGraduate()` at the end of every buy [8](#0-7) , once this underflow condition is hit on a given pair, **every subsequent buy and sell on that token's curve reverts permanently** — the curve is bricked. `previewLtUntilGraduation` (a public view used by the frontend/keepers) is affected identically [9](#0-8) , and `_prepareGraduationLiquidity`, called from `_enterGraduating` during the threshold-crossing buy, has the exact same unguarded subtraction, so if this state is instead reached from the buy side, the graduation-triggering buy itself reverts, freezing the token in `Lifecycle.Curve` forever with no way to reach `Graduating`.

### Impact Explanation
This is a permanent freeze-of-funds condition, not a value-miscalculation like the original `recoverERC20` report — but it is the closer, checked-arithmetic analog of the same unguarded-subtraction bug class in this Solidity-0.8 codebase (where wraparound becomes a revert instead of silent corruption). Any unprivileged trader can push a token's curve into this reverting state via an ordinary buy immediately followed by a full-size sell (both permissionless `Zap.buy`/`Zap.sell` calls), after which:
- No further buys or sells are possible on that curve (`canGraduate` reverts inside both `buy` and `sell`).
- The token can never graduate (both `triggerGraduation` and the inline buy-side trigger revert on the same underflow).
- All LT and tokens already raised in the `Pair` (curve-raised reserve, the 250M `lpReserve` held in `Bonding`) become permanently stranded, since there is no admin rescue path for a `Lifecycle.Curve` token stuck in this state.

This satisfies "permanent freezing of trader, creator or LP funds."

### Likelihood Explanation
Likelihood depends on whether the 1-wei `+1` K-slack in `Pair.swap` can actually be steered to produce `newAssetReserve == virtualLtReserve - 1` (rather than `>= virtualLtReserve`) on a realistic buy/sell round trip, combined with `newTokenReserve` landing at exactly the virtual max so no other headroom absorbs the 1-wei slack. I was not able to fully derive or numerically simulate this edge case with the tools available (no execution environment) — the `test_roundTrip_lossless` test only asserts the trader "never profits" within rounding, it does not assert the reserves can't dip 1 wei below the virtual seed [10](#0-9) . This should be treated as a plausible-but-unconfirmed rounding edge case requiring a Foundry fuzz/PoC run to nail down the exact input sequence (buy size, sell size, exchange-rate value) that triggers the underflow — I could not execute Solidity code to confirm the precise trigger conditions.

### Recommendation
Guard every occurrence of `assetReserve - _launchTimeVirtualLtReserve(...)` (in `canGraduate`, `previewLtUntilGraduation`, and `_prepareGraduationLiquidity`) with an explicit `assetReserve >= virtualLtReserve` check, treating any shortfall as `realLtRaised = 0` rather than letting the subtraction revert. This turns a potential permanent DoS into a benign `0`-valued read, consistent with how `FeeVault.sweepDonations` already guards its analogous `balance - backed` subtraction with an explicit `balance <= backed` early return [11](#0-10) .

### Proof of Concept
Not independently reproduced with a running Foundry harness in this session. A concrete PoC would need to: (1) launch a token with a seed buy, (2) have the seed's trader sell back the exact token amount received, (3) assert whether `IPair(pair).getReserves()` ever returns `assetReserve < k/TOTAL_SUPPLY` afterward, and (4) confirm that a subsequent call to `Bonding.canGraduate`/`Bonding.sell`/`Bonding.buy` reverts with a Panic(0x11). This is flagged as unconfirmed and should be verified with an actual test run before treating it as a proven finding.
