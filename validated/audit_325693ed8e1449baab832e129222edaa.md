### Title
Webhook shop-domain header is trusted for tenant attribution without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then forwards the `shop` value taken from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` header to the app's webhook handler as trusted tenant identity.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the signature only over `request.to_signable_string`, which for `Webhooks::Request` is `@raw_body` [1](#0-0)  and [2](#0-1) . The `shop` accessor, however, is read directly from the `shop-domain` header and is never included in the signed payload [3](#0-2) .

`Registry.process` validates the HMAC and then immediately constructs `WebhookMetadata` using `request.shop` (the unauthenticated header value) and hands it to the registered handler: [4](#0-3) . `WebhookMetadata` declares `shop` as a trusted field of the callback contract given to host apps [5](#0-4) , and the gem's own documentation instructs developers to use `data.shop` to identify which tenant a webhook body belongs to [6](#0-5) .

The identity binding that should hold is:
`HMAC-authenticated content == content the app attributes to a specific shop`

In this implementation the equality is broken: the byte range verified by `OpenSSL.secure_compare` (raw body only) is not equal to the byte range the library hands to the app as the shop identity (the `shop-domain` header). Because the HMAC key (`Context.api_secret_key` / `Context.old_api_secret_key`) is a single app-wide secret shared by Shopify across every shop that installs the app — not a per-shop key — any entity capable of producing a genuinely-signed webhook body (e.g., an app-installing shop owner who receives real signed webhook traffic to their own endpoint, or anyone who can capture a `(raw_body, hmac)` pair delivered by Shopify) can replay that same body/HMAC pair while substituting an arbitrary `shopify-shop-domain` header value. `HmacValidator.validate` still returns `true` because it never inspects the header, and `Registry.process` will invoke the handler claiming the payload belongs to the attacker-chosen shop.

### Impact Explanation
This crosses a tenant boundary in exactly the pattern the review rubric calls out (a field acted on — tenant attribution — not covered by the HMAC). Because `data.shop` is the documented mechanism by which host applications determine which merchant's stored access token/session or database row to associate a webhook payload with, an attacker who can obtain any one valid `(body, hmac)` pair for the shared app secret can cause the library to hand off attacker-controlled body content under the identity of a different shop, leading to cross-tenant data confusion/corruption in any downstream application that trusts `data.shop` without independent verification (which is exactly what the shipped documentation and example handler encourage).

### Likelihood Explanation
Reachable by any unprivileged actor who has, or can obtain, one legitimately-signed webhook delivery for the app (trivial for a malicious merchant who installs the app themselves, since Shopify will deliver real signed webhooks to their configured endpoint). No knowledge of `api_secret_key` is required — only replay of already-observed signed bytes with a modified unauthenticated header, which this gem performs no additional validation to prevent.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the material verified by the HMAC check, or have `Registry.process` cross-check the header-derived shop against an independent, cryptographically verifiable source (e.g., look up the registered webhook/session for that shop and confirm the delivery was actually expected/registered for it) before dispatching to the handler. At minimum, update documentation to explicitly warn that `data.shop` is not authenticated by the HMAC and must not be used as sole tenant identification without additional verification.

### Proof of Concept
1. App is installed on `shop-a.myshopify.com`; Shopify signs webhook `raw_body` with the app's shared `client_secret` and delivers it to the app's endpoint with header `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Attacker (who controls `shop-a`, e.g. as its owner/employee) captures this `(raw_body, hmac)` pair from their own delivered webhook (trivial, they receive it directly).
3. Attacker resends the identical `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: shop-b.myshopify.com` (a different tenant).
4. `Utils::HmacValidator.validate` recomputes HMAC over `raw_body` only, matches the supplied HMAC, and returns `true` [7](#0-6) .
5. `Registry.process` builds `WebhookMetadata` with `shop: "shop-b.myshopify.com"` and the attacker-controlled body, and invokes the app's handler as if the data legitimately originated from shop B [8](#0-7) .

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

        end

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
```
