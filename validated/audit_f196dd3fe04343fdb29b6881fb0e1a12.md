### Title
Webhook `shop-domain` header is trusted for tenant dispatch but is not covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking the HMAC over the raw request body, then dispatches the handler using `request.shop`, which is read from the `X-Shopify-Shop-Domain` header — a value that is never part of the HMAC-signed material.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `Webhooks::Request#shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header independently of the HMAC computation [2](#0-1) . `Utils::HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (the body) and compares it to the `hmac` value [3](#0-2) . `Registry.process` treats a passing HMAC check as sufficient authorization, then immediately trusts `request.shop` to build `WebhookMetadata` and invoke the app's handler for that shop [4](#0-3) .

The identity binding that should hold is: `shop header used for tenant dispatch == shop bound by the HMAC signature`. Because the header is excluded from the signable string, this equality is never enforced. Any party that possesses one validly-signed webhook body/HMAC pair (e.g., their own shop's mandatory `shop/redact` webhook, or any webhook delivered to their own store) can replay that exact body+HMAC while substituting an arbitrary `X-Shopify-Shop-Domain` header value. The HMAC will still validate (it only checks the body), and `Registry.process` will hand the handler a `WebhookMetadata` claiming to be from the attacker-chosen shop.

### Impact Explanation
This breaks the tenant boundary that `Registry.process`/`WebhookMetadata` is relied upon to provide to the host application: the shop that HMAC-authenticated the payload is not necessarily the shop reported to the handler. A host app that uses `WebhookMetadata#shop` to key writes/deletes (as is standard practice, and required for the mandatory `shop/redact`/`customers/redact`/`customers/data_request` topics) can be tricked into applying an attacker-forged body under a victim shop's identity — i.e., cross-tenant data corruption/impersonation through this gem's own webhook-processing API, without any credential belonging to the victim.

### Likelihood Explanation
Exploitation requires possession of any one legitimately HMAC-signed webhook body (trivially obtainable by any merchant who installs the app, since Shopify sends every merchant real webhooks with a valid HMAC computed from the shared `client_secret`), then replaying it to the app's public webhook endpoint with a modified shop header. No access to the app's `client_secret`, access tokens, or the victim's credentials is needed — only network access to the app's webhook endpoint, which is an unauthenticated, internet-reachable endpoint by design.

### Recommendation
Include the `X-Shopify-Shop-Domain` (and ideally `X-Shopify-Webhook-Id`/topic) header value in the HMAC-covered signable string, or otherwise cryptographically bind the shop to the payload before `Registry.process` uses it for dispatch, so that `request.shop` cannot be varied independently of the authenticated body.

### Proof of Concept
1. Attacker's own shop `attacker.myshopify.com` triggers a webhook (e.g. `shop/redact`), producing `raw_body` B and a valid `hmac` H = HMAC(client_secret, B).
2. Attacker resends `POST /webhooks` with the same body B, same `X-Shopify-Hmac-Sha256` header (decoded to H), but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Webhooks::Request.new` accepts the request (all required headers present) [5](#0-4) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over B only and succeeds [6](#0-5) .
5. `Registry.process` builds `WebhookMetadata.new(... shop: request.shop ...)` with `shop == "victim.myshopify.com"` and invokes the app's handler, which now processes attacker-controlled body B under the victim shop's identity [7](#0-6) .

```ruby
      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
```
