### Title
User-controlled swap routes can inject malicious pool code beneath the caller authorization - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary

Controller strategy operations accept route bytes from the caller and forward them to the configured swap router without validating the route’s pool or token addresses. [1](#0-0)  The router decodes those bytes into an arbitrary address registry and invokes whichever pool address each hop selects. [2](#0-1)  A malicious route can therefore place attacker-controlled code below the caller’s `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, or `multiply` authorization and request unrelated token transfers from that caller. [3](#0-2) 

### Finding Description

`swap_tokens` treats `StrategySwap` as opaque route data, checks only that it is non-empty for a cross-token operation, snapshots balances, grants the router one exact input transfer, and calls `execute_strategy`. [4](#0-3)  The router payload contains an unconstrained `assets` registry whose entries are used as both token and pool addresses. [5](#0-4)  Program validation range-checks those indices but does not establish that a pool address belongs to an approved venue deployment. [6](#0-5)  During execution, the selected registry entry becomes `SwapHop.pool` and is dispatched to a venue adapter. [2](#0-1)  Those adapters invoke the supplied address as a contract. [7](#0-6) 

### Impact Explanation

A malicious pool can ask an unrelated token contract to transfer assets from the caller to the attacker while the strategy invocation is active. [8](#0-7)  Soroban simulation records that attempted transfer as a child of the caller’s strategy authorization; if the wallet signs the expanded tree, the transfer succeeds. [3](#0-2)  The regression test demonstrates complete theft of an unrelated wallet token while the malicious route still returns the expected strategy output. [9](#0-8)  This is theft of user funds beyond the swap input and is not bounded by `min_out`, measured output, or the final account risk check. [10](#0-9) 

### Likelihood Explanation

Any unprivileged user can supply route bytes to the affected controller strategy entrypoints, and the route format permits arbitrary pool contract IDs. [11](#0-10)  An attacker can deploy a contract implementing the expected venue call, embed its address in a route offered to a victim, and cause simulation to request the extra transfer. [12](#0-11)  Exploitation depends on the victim or their wallet accepting the poisoned authorization tree; an honest tree without the extra child causes the unauthorized transfer and transaction to fail. [13](#0-12)  The practical likelihood is therefore moderate where routes are sourced from an off-chain service, another user, or an UI that does not reject unexpected authorization children. [14](#0-13) 

### Recommendation

Restrict route pool addresses to governance-approved venue deployments rather than accepting arbitrary entries from the payload. [15](#0-14)  If that is intentionally unsupported, enforce it in a venue registry checked during strategy decoding or dispatch, before any external `invoke_contract` occurs. [2](#0-1)  Clients should also decode the simulated authorization tree and reject any child invocation other than the single expected input transfer, but client validation alone does not remove the contract-level injection surface. [14](#0-13) 

### Proof of Concept

1. The attacker deploys a contract exposing the venue function expected by the selected opcode, such as Soroswap’s `swap`. [16](#0-15) 
2. That contract additionally calls `token.transfer(victim, attacker, victim_wallet_balance)` for a token unrelated to the lending markets. [17](#0-16) 
3. The attacker constructs route bytes whose `assets` registry contains the malicious pool and whose swap instruction selects that pool through `idx_a`. [5](#0-4) 
4. The victim calls `swap_collateral(caller, account_id, current, from_amount, new, swap)` using that route. [11](#0-10) 
5. `swap_tokens` forwards the route to `execute_strategy`, which decodes the selected pool and invokes it. [18](#0-17) 
6. Simulation adds the malicious wallet transfer as a child of the victim’s authorization. [19](#0-18) 
7. If the victim signs that tree, the malicious transfer and the economically valid swap both execute; the test ends with the victim’s unrelated wallet balance at zero and the attacker holding the full amount. [20](#0-19)

That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
