## Analysis

I found a directly analogous vulnerability in this codebase. The root cause of the original Sentiment bug — an all-or-nothing loop of token transfers where one failing transfer (blacklist, pause, zero-balance revert, etc.) blocks the entire operation and permanently freezes user funds — maps to `Processor::process_withdraw` in `processor.rs`.

### Title
Withdraw is permanently blocked and LP funds are frozen if either underlying asset's transfer reverts - (File: `program/src/processor.rs`)

### Summary
`process_withdraw` performs two mandatory, sequential SPL token transfers (coin and PC) followed by an LP burn, all within a single atomic instruction. If either transfer reverts for any external reason (frozen/blacklisted destination account, paused token mint, or an upgraded token implementation with new revert conditions), the whole instruction fails and the LP holder's tokens can never be redeemed for that pool, since there is no fallback, retry, or partial-withdraw path.

### Finding Description
In `process_withdraw`, after computing `coin_amount` and `pc_amount`, the program unconditionally calls both transfer CPIs before burning the user's LP tokens: [1](#0-0) 

Both `Invokers::token_transfer_with_authority` calls invoke the SPL token program's `Transfer` instruction directly: [2](#0-1) 

Because Solana transactions are atomic, if the coin-side transfer to `user_dest_coin_info` succeeds but the PC-side transfer to `user_dest_pc_info` fails (e.g., the PC mint is a token like USDC and the user's destination account has been frozen/blacklisted, or the mint is paused), the entire `process_withdraw` instruction reverts. The `token_burn` of the LP tokens never executes, so the user's LP position remains intact but they possess no way to construct a withdraw transaction that avoids the frozen asset — the instruction requires both `user_dest_coin_info` and `user_dest_pc_info` to be valid, non-frozen accounts for the mint. This is the same root cause pattern as the original report: a rigid "all transfers must succeed or the whole operation aborts" design with no mechanism to skip/retry the failing leg.

### Impact Explanation
Any LP holder whose destination token account for either the coin or PC side of a pool becomes frozen, blacklisted, or otherwise reverts on transfer permanently loses the ability to withdraw their liquidity from that pool. Since `amm.lp_amount` is only decremented and LP tokens only burned after both transfers succeed, there is no partial-withdrawal fallback — the user's entire LP position for that pool becomes permanently locked, a direct freezing of LP funds.

### Likelihood Explanation
This is reachable by any unprivileged liquidity provider through a single, ordinary `Withdraw` instruction call. It requires no attacker sophistication beyond submitting a withdraw with a destination account for the affected mint. Real-world triggers include Circle freezing/blacklisting a USDC associated token account, a token mint entering a paused state, or an upgradeable token changing its transfer logic — all plausible for common quote tokens (e.g., USDC) used as `pc_vault_mint` in Raydium pools.

### Recommendation
Avoid coupling both asset transfers and the LP burn into a single unconditional path. Options include: allowing the withdrawal to proceed and burn LP proportionally per-asset even if one transfer fails (crediting the failed leg to an escrow/claimable balance for later retry), or exposing a single-asset withdrawal path so users can redeem the non-frozen asset independently, similar to the "catch reversion and skip/allow retry" recommendation adopted by the Sentiment team in the referenced fix.

### Proof of Concept
1. A liquidity provider deposits into a pool where `pc_vault_mint` is USDC and receives LP tokens.
2. The provider's USDC associated token account is later frozen by the USDC freeze authority (or the account otherwise reverts on `Transfer`, e.g., a paused/upgraded token).
3. The provider calls `Withdraw` (`process_withdraw`, `program/src/processor.rs:1787-1811`) with their LP tokens and their (now frozen) `user_dest_pc_info` account.
4. The `Invokers::token_transfer_with_authority` CPI for the PC leg reverts inside the SPL token program because the destination account is frozen.
5. Because Solana transaction execution is atomic, the entire instruction fails: the coin transfer that would have succeeded is rolled back, and `token_burn` of LP never executes.
6. The provider has no alternative instruction to redeem only the coin side or to skip the frozen PC leg — their LP position is permanently unredeemable as long as the freeze/pause persists (which can be indefinite for a blacklist).

    /// Issue a spl_token `Transfer` instruction.
    pub fn token_transfer_with_authority<'a>(
        token_program: AccountInfo<'a>,
        source: AccountInfo<'a>,
        destination: AccountInfo<'a>,
        authority: AccountInfo<'a>,
        amm_seed: &[u8],
        nonce: u8,
        amount: u64,
    ) -> Result<(), ProgramError> {
        let authority_signature_seeds = [amm_seed, &[nonce]];
        let signers = &[&authority_signature_seeds[..]];
        let ix = spl_token::instruction::transfer(
            token_program.key,
            source.key,
            destination.key,
            authority.key,
            &[],
            amount,
        )?;
        solana_program::program::invoke_signed(
            &ix,
            &[source, destination, authority, token_program],
            signers,
        )
    }
