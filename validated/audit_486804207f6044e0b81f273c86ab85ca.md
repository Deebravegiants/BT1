## Title
On-Chain Uniswap V4 Pool Price Used as Unguarded Order-Filling Oracle in Simplex FXFiller - (File: `sdk/packages/simplex/src/strategies/fx.ts`)

### Summary
This report describes the same bug class as the external `SwapperUniV3._getBestFee`/`_swap` finding: computing a fill/slippage price directly from live on-chain AMM state and trusting it without accounting for size, execution cost, or manipulation. The Hyperbridge analog is Simplex's `FXFiller`, an intent solver that prices "venue-priced" cross-asset pairs directly from a Uniswap V4 pool's spot price (`sqrtPriceX96`/tick) rather than a curve, and pays that price out unconditionally to fill Hyperbridge `IntentGateway` orders.

### Finding Description
When a pair has no static bid/ask curves, `resolveLegRates` in `sdk/packages/simplex/src/strategies/fx.ts` prices the leg from `venueUsdPrice`, which is backed by `UniswapV4FundingPlanner.getExoticTokenPrice` → `computeDirectPoolPriceUsd`, itself derived from the pool's raw `sqrtPriceX96`/current tick read via `UniswapV4LiquidityState.refresh` (`getSlot0`). [1](#0-0) [2](#0-1) [3](#0-2) 

The internal engineering notes explicitly confirm this is the raw pool mid with no size/impact modeling, and that the only defense is a deviation check against a static reference, not an execution-cost check: [4](#0-3) 

The guard (`checkPriceGuard`) is optional per-chain config, compares the live quote only against a static `referencePrice` within `maxDeviationBps`, and — like the original report's slippage tolerance — does nothing to prevent a price that has been pushed to the edge of the allowed band via a flash-loan/sandwich manipulation of the pool immediately before the fill: [5](#0-4) 

Once the (possibly manipulated) rate is obtained, `computeLegPolicyOutput` extrapolates it **linearly across the whole order notional** with no depth/impact term, and the filler pays out the full computed amount — the previous overfill-clamp safety net has been deliberately disabled, leaving payout unconditionally equal to the (possibly manipulated) quoted amount: [6](#0-5) [7](#0-6) 

### Impact Explanation
An attacker can flash-loan-sandwich the referenced Uniswap V4 pool immediately before submitting (or racing) an intent order into `IntentGatewayV2`, moving the pool's spot price up to `maxDeviationBps` away from the configured reference (or arbitrarily far if no guard is configured for that chain, which the config explicitly allows — "omit both to leave the chain unguarded"). The solver's `FXFiller` then reads that manipulated price as the fill rate, computes `policyMaxOutput` linearly off it with no size-impact discount, and — because overfill clamping is disabled — pays the attacker's order in full at the manipulated rate. This directly transfers value out of the solver's inventory to the attacker, i.e. theft of solver funds through a manipulated on-chain price oracle used for a fund-moving decision, the same fund-loss class the original report flagged (accepted risk there was tolerated because it only affected slippage on a foreclosure swap the protocol itself controlled; here it directly and unconditionally sets the payout of a third-party-reachable order fill).

### Likelihood Explanation
- Reachable by any unprivileged actor who can place an `IntentGatewayV2` order and interact with the referenced public Uniswap V4 pool (no special privilege needed).
- The price guard is optional per chain/position (`referencePrice`/`maxDeviationBps` must be set together or the chain is "unguarded"), so any operator running a venue-priced pair without both fields configured has zero manipulation resistance.
- Even when the guard is set, it only bounds deviation from a static reference, not manipulation within that band, and the linear extrapolation means the effective loss scales with order size — larger orders extract proportionally more value for the same amount of price manipulation.
- The overfill ceiling that used to bound the blast radius of a bad/manipulated price has been explicitly disabled in code, per the comment at `fx.ts:678-684`, removing what used to be a mitigating control.

### Recommendation
- Never rely on a single spot read of `sqrtPriceX96`/tick as a fill price; use a TWAP/oracle with a minimum observation window, or require an independent off-chain price feed (as the original report also recommended) for venue-priced pairs.
- Make `referencePrice`/`maxDeviationBps` mandatory for any venue-priced pair rather than optional.
- Apply a size/impact-aware pricing model instead of linear mid-price extrapolation across the whole notional.
- Re-enable (or reintroduce) a hard overfill/loss-bound cap so a manipulated or stale price cannot translate into unconditional full payout.

### Proof of Concept
1. Operator configures a venue-priced pair (e.g. USDC/CNGN) funded from a Uniswap V4 LP position, without setting `referencePrice`/`maxDeviationBps` for the chain (an explicitly supported, documented configuration).
2. Attacker takes a flash loan and swaps against the referenced Uniswap V4 pool to push its spot price/tick to a favorable extreme.
3. In the same block (or shortly after, since `refresh()` reads live `slot0` at fill time), attacker submits an `IntentGatewayV2` order sized to consume the exotic token leg at the manipulated rate.
4. `FXFiller.resolveLegRates` → `getVenueUsdPrice` → `computeDirectPoolPriceUsd` reads the manipulated `sqrtPriceX96`; with no guard configured, `checkPriceGuard` passes trivially.
5. `computeLegPolicyOutput` linearly extrapolates the manipulated rate over the full order notional; overfill clamping is disabled, so `FXFiller` fills the order in full at the manipulated price, transferring value from the solver's inventory to the attacker.
6. Attacker reverses the flash-loan swap, keeping the extracted output token minus flash-loan/gas fees.

	/**
	 * Validates a live venue quote against the static reference price for the chain.
	 * Returns true (pass) when no guard is configured, or no reference exists for the
	 * chain. Returns false when the quote (token1 per USD) deviates from the reference
	 * by more than `maxDeviationBps`, in which case the order must not be filled.
	 */
	private checkPriceGuard(orderId: string | undefined, chain: string, venueToken1PerUsd: Decimal): boolean {
		const guard = this.priceGuard?.get(chain)
		if (!guard || guard.reference.lte(0)) return true

		const deviationBps = venueToken1PerUsd.minus(guard.reference).abs().div(guard.reference).mul(10000)
		if (deviationBps.gt(guard.maxDeviationBps)) {
			this.logger.warn(
				{
					orderId,
					chain,
					venuePrice: venueToken1PerUsd.toString(),
					referencePrice: guard.reference.toString(),
					deviationBps: deviationBps.toFixed(2),
					maxDeviationBps: guard.maxDeviationBps,
				},
				"Rejecting order: Uniswap venue quote outside price-guard band",
			)
			return false
		}
		return true
	}

	private computeLegPolicyOutput(
		inputAmount: bigint,
		inputIsToken0: boolean,
		token0Decimals: number,
		token1Decimals: number,
		/**
		 * Token0 left in the pair's per-order exposure budget, or `null` to price the whole
		 * input unbudgeted. Only a price probe passes `null`: it commits no capital, so there
		 * is no exposure to ration, and a clamped quantity would silently misprice it.
		 */
		remainingToken0: Decimal | null,
		rate: Decimal,
	): { token0Used: Decimal; policyMaxOutput: bigint } | null {
		let legMaxToken0: Decimal
		if (inputIsToken0) {
			legMaxToken0 = new Decimal(formatUnits(inputAmount, token0Decimals))
		} else {
			legMaxToken0 = new Decimal(formatUnits(inputAmount, token1Decimals)).div(rate)
		}

		const token0ForLeg = remainingToken0 === null ? legMaxToken0 : Decimal.min(legMaxToken0, remainingToken0)
		if (token0ForLeg.lte(0)) {
			return null
		}

		let policyMaxOutput: bigint
		if (inputIsToken0) {
			// Output is token1: convert the token0 allocation at the pair rate.
			policyMaxOutput = BigInt(
				token0ForLeg.mul(rate).mul(new Decimal(10).pow(token1Decimals)).floor().toFixed(0),
			)
		} else {
			// Output is token0: pay out the token0 equivalent of the token1 input.
			policyMaxOutput = BigInt(token0ForLeg.mul(new Decimal(10).pow(token0Decimals)).floor().toFixed(0))
		}

		return { token0Used: token0ForLeg, policyMaxOutput }
	}

		leg: ResolvedLeg,
		cappedPairNotional: Decimal,

	): Promise<LegRates | null> {
		// Explicitly configured curves always win — the venue only prices pairs
		// with no curves at all (and never same-token pairs, where a venue quote
		// would just be the asset's own USD price, not a spread).
		const curveless = !leg.pair.bidPricePolicy && !leg.pair.askPricePolicy
		if (curveless && !isSameTokenPair(leg.pair) && USD_STABLE_SYMBOLS.has(normalizeSymbol(leg.pair.token0))) {
			const venueUsd = await venueUsdPrice(leg.token1Chain, leg.token1Address)

					return null

				// to report a round-trip margin against. The price guard above is
				// the venue-specific defense.
				const venueRate = new Decimal(1).div(venueUsd)
				return { rate: venueRate, oppositeRate: null, priceSource: "venue" }
			}

	async getExoticTokenPrice(chain: string, exoticToken: string): Promise<Decimal | null> {
		const state = this.stateByChain.get(chain)
		if (!state || !state.isHydrated()) return null

		try {
			await state.refresh()
		} catch (err) {
			this.logger.error({ err, chain }, "Failed to refresh state for price query")
			return null
		}

		const tokenLower = exoticToken.toLowerCase()
		let bestPrice: Decimal | null = null
		let bestLiquidity = 0n

		for (const pos of state.allPositions()) {
			if (pos.currency0.toLowerCase() !== tokenLower && pos.currency1.toLowerCase() !== tokenLower) continue
			const sdkPool = state.getSdkPool(pos.tokenId)
			if (!sdkPool) continue

			const result = this.computeDirectPoolPriceUsd(pos, sdkPool, chain)
			if (result && result.exoticToken.toLowerCase() === tokenLower) {
				const poolLiquidity = state.getPoolLiquidity(pos.tokenId)
				if (poolLiquidity > bestLiquidity) {
					bestPrice = result.priceUsd
					bestLiquidity = poolLiquidity
				}
			}
		}

		if (bestPrice) {
			this.logger.debug({ chain, token: tokenLower, priceUsd: bestPrice.toString() }, "Exotic token price computed")
		}
		return bestPrice
	}

`computeDirectPoolPriceUsd` returns the **raw pool mid** derived from `sqrtPriceX96`. The pool's
fee tier is read and stored on the hydrated position (`pos.fee`) but never applied to the price,
and there is no size or impact term — `computeLegPolicyOutput` extends the mid linearly across the
whole priced quantity. `checkPriceGuard` is the only defense on this path, and it checks deviation
from a static reference, not execution cost. A venue-priced pair that has to swap through its own
pool to source inventory pays a fee tier it never quoted against.
