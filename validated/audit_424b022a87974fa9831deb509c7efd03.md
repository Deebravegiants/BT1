## Title
Withdrawal status/hash misattributed across batched same-asset POA withdrawals - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal()` matches a withdrawal's on-chain outcome by `assetId` alone instead of by the withdrawal's actual index/identity, so when a batch contains two or more withdrawals of the same asset, the SDK reports the wrong withdrawal's completion status/tx hash for a given `WithdrawalIdentifier`.

### Finding Description
`createWithdrawalIdentifiers` (`packages/intents-sdk/src/core/withdrawal-watcher.ts:80-107`) assigns each withdrawal a per-bridge `index` and builds a `WithdrawalIdentifier` via `bridge.createWithdrawalIdentifier(...)`. For POA Bridge, that identifier's `index` is never actually used to disambiguate outcomes: `describeWithdrawal` looks up the whole batch status once and calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which is a `.find()` keyed purely on `assetId`: [1](#0-0) [2](#0-1) 

The code comment explicitly documents the limitation: "Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported." Because `findMatchingWithdrawal` returns the *first* array element whose `near_token_id` matches, and the POA API's withdrawal list order is stated to be unsorted ("Response list is unsorted, so we match by assetId instead of index" — line 318), calling `describeWithdrawal` for withdrawal index 0 and index 1 of the *same asset* in the same NEAR transaction returns the identical matched entry both times. The equality that should hold — "the on-chain outcome reported for withdrawal *N* is withdrawal *N*'s actual outcome" — is broken: two logically distinct withdrawals (potentially different amounts/destination addresses) collapse onto a single reported `status`/`txHash`.

### Impact Explanation
`watchWithdrawal` (`packages/intents-sdk/src/core/withdrawal-watcher.ts:20-78`) treats `status: "completed"` with a `txHash` as authoritative proof of settlement for that specific `WithdrawalIdentifier`, and consumers such as `waitForIntentSettlement`/`processWithdrawal` use this to resolve completion promises for each withdrawal in a batch. If a caller submits two `ft_withdraw` intents for the same NEP-141 asset (e.g., two different destination addresses/amounts) in one signed intent batch, both withdrawal slots can report the same destination tx hash as "completed," or the wrong slot's completion could be reported before the correct one actually settles. An integrator relying on per-withdrawal completion (e.g., to credit a user or release funds) could credit the same destination event twice, or mark a still-pending/failed withdrawal as completed based on the other entry's data — matching the impact class "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
This requires no malicious relayer/bridge/RPC action — it is triggered purely by a normal caller submitting a batch with two or more `ft_withdraw` intents for the same POA asset in a single NEAR transaction, a usage pattern the SDK's own `Bridge` interface and batch-withdrawal APIs support (`createWithdrawalIntents`, `createWithdrawalIdentifiers`, `WithdrawalParams[]`). The bug is unconditionally reachable whenever this pattern occurs and the API response ordering doesn't happen to coincide with submission order; the code comment confirms this is a known, currently-unhandled case rather than a defended edge condition.

### Recommendation
Disambiguate withdrawals of the same asset within `describeWithdrawal`/`findMatchingWithdrawal`, e.g., by sorting both the local withdrawal params and the API response by amount (as the code comment itself suggests) before pairing them by index, or by requesting/matching on a unique per-withdrawal identifier from the POA API if one becomes available. Until fixed, the SDK should reject or explicitly warn when a caller submits multiple same-asset POA withdrawals in a single batch, rather than silently reporting indistinguishable statuses.

### Proof of Concept
1. Submit a signed intent batch with two `ft_withdraw` intents both for `nep141:usdc.omft.near`: withdrawal A (index 0, 100 USDC to address X) and withdrawal B (index 1, 200 USDC to address Y).
2. `createWithdrawalIdentifiers` assigns `index: 0` to A and `index: 1` to B, both bridged via `PoaBridge`.
3. Call `describeWithdrawal` for A's identifier and for B's identifier. Both calls invoke `getWithdrawalStatusWithRetry` (same `tx.hash`) then `findMatchingWithdrawal(withdrawals, "nep141:usdc.omft.near")`, which returns the same array element (the first match) for both calls regardless of `index`.
4. If that matched entry has `status: "COMPLETED"` with `transfer_tx_hash: "0xY-tx"` (B's actual destination tx), `describeWithdrawal` for A also returns `{ status: "completed", txHash: "0xY-tx" }`, even though A's own destination transfer may still be pending or use a different hash — confirmed by the existing test `"matches withdrawal by assetId, not by index"` in `poa-bridge.test.ts:1054` which demonstrates the assetId-only matching behavior.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
