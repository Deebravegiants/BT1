Confirmed: `Utils::VerifiableQuery` only exposes `hmac` and `to_signable_string` [1](#0-0) , and for webhooks, `to_signable_string` returns only `@raw_body`, leaving all headers (`shop`, `topic`, `webhook_id`, `api_version`) unauthenticated by the HMAC [2](#0-1) . This is the finding.

### Title
Webhook shop-domain identity is not covered by the HMAC, enabling cross-tenant webhook spoofing via payload replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [3](#0-2) , while `#shop`, `#topic`, `#webhook_id`, and `#api_version` are read directly from HTTP headers that are never included in the HMAC computation [4](#0-3) . `Registry.process` validates only this body-derived HMAC and then dispatches the handler using the unauthenticated `request.shop` value [5](#0-4) .

### Finding Description
`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it against the `hmac` accessor via `OpenSSL.secure_compare` [6](#0-5) . For the OAuth `AuthQuery` type, `to_signable_string` includes `shop` in the signed parameters [7](#0-6) , correctly binding shop identity to the signature. However, for `Webhooks::Request`, `to_signable_string` returns `@raw_body` alone [8](#0-7) ; the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are parsed but never fed into the HMAC computation [9](#0-8) .

Equality that should hold but doesn't: `hmac_signed_bytes == bytes_that_determine_tenant_identity`. In fact `hmac_signed_bytes = raw_body` while `tenant_identity = shop-domain header`, i.e. two disjoint inputs. `Registry.process` raises only if the HMAC over the body fails [10](#0-9) , then immediately constructs `WebhookMetadata` using `request.shop` — the unauthenticated header — and passes it to the app's handler [11](#0-10) .

Because many webhook topics produce identical or predictable bodies for different shops (e.g. `orders/create` with a small deterministic payload, or any topic where the body content coincides for two different tenants), an unprivileged internet user who can observe or receive one legitimate webhook delivery (their own store, or any store where they can see the raw body/HMAC pair over an unauthenticated endpoint — public webhook endpoints have no other authentication per the docs) can replay that exact `raw_body` + `hmac` header pair to the victim app's webhook endpoint while substituting an arbitrary value in the `x-shopify-shop-domain` header. `HmacValidator.validate` will still pass, because it never inspects the `shop` header. The application-level handler receives `WebhookMetadata` with the attacker-chosen `shop`, causing it to process/store the data under the wrong tenant.

This directly matches the "field acted on but not covered by the HMAC" identity-binding failure class: the shop identity is *acted on* by the handler and by any app code trusting `data.shop` for tenant scoping, but it is not part of the *authenticated* bytes.

### Impact Explanation
This breaks the tenant boundary the HMAC is meant to enforce: an app cannot distinguish "this event genuinely originates from shop X" from "someone replayed a valid signature under a different claimed shop." Depending on how the host app scopes writes/deletes/notifications by `data.shop`, this enables cross-tenant data corruption or disclosure (e.g. marking another merchant's data as uninstalled, associating unrelated order data with the wrong shop, or triggering shop-scoped side effects for a shop the attacker doesn't operate) — a cross-tenant access impact.

### Likelihood Explanation
The webhook HTTP endpoint is, by design, internet-reachable and unauthenticated beyond the HMAC check — this is the gem's own documented processing model ("This will verify the request did indeed come from Shopify") [12](#0-11) , so any unprivileged actor who can capture one valid `(raw_body, hmac)` pair (from their own store's webhook, or a webhook whose body content is topic-generic) can immediately mount the replay against a different shop's identity. No secret key, access token, or privileged access is required — only observation of one legitimate delivery.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the signed material for webhooks, or independently verify `request.shop` against a value the app trusts by other means before dispatch. Concretely, `Webhooks::Request#to_signable_string` should not be the sole basis for trusting `shop`; either extend HMAC verification to cover header-derived identity, or have `Registry.process` cross-check `request.shop` against the session/shop context the app is actually processing on behalf of, rejecting mismatches.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and receives a legitimate `orders/create` webhook with body `B` and header `x-shopify-hmac-sha256: H` (valid for secret `S` and body `B`).
2. Attacker sends `POST /webhook` to the victim app with body `B`, header `x-shopify-hmac-sha256: H`, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Webhooks::Request.new` parses headers; `HmacValidator.validate` calls `to_signable_string` → returns `B`, computes HMAC with the app's real secret, compares to `H` → passes [3](#0-2) .
4. `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` [11](#0-10) , even though the payload never actually originated from `victim-shop.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
