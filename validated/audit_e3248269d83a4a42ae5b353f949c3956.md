## Title
Webhook shop attribution is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC of the raw request body, but the `shop` value that the handler subsequently trusts to attribute the event to a tenant is taken from an HTTP header that is **not** included in the signed material. This breaks the identity binding `hmac_covers(shop) == shop_used_for_attribution`, exactly the same class of bug as H-13's `totalWeight` vs. actual-weight mismatch: a piece of state used downstream (here, tenant identity) diverges from what the cryptographic check actually verified.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `shop` is read directly from an attacker-controllable header, entirely outside the HMAC: [2](#0-1) 

`Registry.process` validates only this body-only HMAC and then forwards `request.shop` (the unauthenticated header) straight into the handler as the tenant identifier: [3](#0-2) 

`Utils::HmacValidator.validate` confirms the signature is computed only over `to_signable_string` (the raw body), using the app's single, shop-independent `api_secret_key`: [4](#0-3) 

Because the same `api_secret_key` is used to sign webhooks for **every** shop that has installed the app, and the `shop-domain` header is never part of the signed bytes, any request bearing a body+HMAC pair that is valid for *one* installed shop remains HMAC-valid after the `x-shopify-shop-domain` (or `shopify-shop-domain`) header is swapped to point at a *different* installed shop. The equality that should hold — "the shop the HMAC proves the payload originated from" == "the shop the handler attributes the event to" — is broken: the HMAC only proves "signed by this app's secret," not "for this shop."

### Impact Explanation
This is a cross-tenant identity-binding failure: a party controlling one legitimate webhook delivery (e.g., an attacker who installs the target app on their own store to obtain a genuinely-signed webhook body/HMAC pair) can cause the app to process that payload under a victim shop's identity by altering only the unauthenticated `shop-domain` header. Any host application that relies on `WebhookMetadata#shop` (populated straight from `request.shop`) to select which tenant's data to mutate is exposed to cross-tenant data injection/corruption — satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation requires only the ability to send an HTTP POST to the app's public webhook endpoint with attacker-chosen headers plus one legitimately-signed body captured from any shop that has installed the app (including the attacker's own store) — no access token, `client_secret`, or privileged account is required, and no TLS interception is needed since the endpoint is meant to be internet-reachable.

### Recommendation
Bind the shop identity into the authenticated material, e.g., include the `shop-domain` (and ideally `webhook-id`/`topic`) in the HMAC-verified signable string, or independently verify that `request.shop` corresponds to a shop with an active, previously-established session/installation before dispatching to the handler, rather than trusting the header as-is.

### Proof of Concept
1. Install the app on attacker-controlled shop `evil.myshopify.com`; trigger a webhook (e.g., `orders/create`) and capture the raw body `B` and its valid `X-Shopify-Hmac-Sha256` header `H` (computed as `HMAC-SHA256(api_secret_key, B)`, per `hmac_validator.rb` line 26-31).
2. Replay a POST to the app's webhook endpoint with the same body `B` and header `H`, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds because it only recomputes the signature over `B` (`request.rb` `to_signable_string`, lines 35-38) — the shop header is never part of the signed input.
4. `Registry.process` (`registry.rb` lines 188-199) forwards `shop: request.shop` = `"victim.myshopify.com"` to the app's handler, which now processes attacker-supplied webhook content as if it originated from the victim tenant.
