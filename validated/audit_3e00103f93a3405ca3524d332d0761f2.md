Audit Report

## Title
Unbounded `Topics` array in web-api trigger requests enables synchronous CPU-exhaustion DoS that blocks all Gateway message processing - ([File: core/capabilities/webapi/trigger/trigger.go])

## Summary
`triggerConnectorHandler.processTrigger` iterates over every registered workflow trigger and, for each trigger, over every entry of the caller-supplied `payload.Topics` slice, with the only bound being that the slice is non-empty. Because `HandleGatewayMessage` runs synchronously and inline inside the single per-gateway-connection `readLoop`, an attacker-controlled request with a very large `Topics` array (still within the HTTP byte-size cap) causes CPU-bound, unbounded-time processing that delays delivery of all other queued/incoming Gateway messages for that connection.

## Finding Description
`processTrigger` reads `topics := payload.Topics` from the untrusted, attacker-controlled JSON-RPC payload and only checks `len(topics) == 0` before entering a nested `for _, trigger := range triggers { for _, topic := range topics { ... } }` loop [6](#0-5) . There is no upper bound on `len(topics)` anywhere in this path. The message is decoded via `ValidatedMessageFromReq`/`json.Unmarshal`, which performs no element-count limits on arrays inside the payload [7](#0-6) . The only size control anywhere in the pipeline is the HTTP request body byte limiter, `MaxRequestBytesLimiter`, applied to the entire request body — this bounds total bytes, not the number of array elements, so a payload under the cap can still contain tens of thousands of short topic strings [4](#0-3) .

Critically, the sender-allowlist check (`trigger.allowedSenders[sender.String()]`) happens *inside* the nested loop, after a topic has already matched, meaning the expensive iteration is not gated by authorization at all — every submitted topic is checked against every registered trigger's `allowedTopics` map regardless of whether the sender is authorized [8](#0-7) . `Message.Validate()` (invoked from `ValidatedMessageFromReq`) only validates signature format/length and derives the sender address from the signature via `ExtractSigner()` — it does not check the sender against any pre-existing allowlist before dispatch [1](#0-0) . Since signing merely requires possession of any ECDSA private key (self-generated, no registration needed) [2](#0-1) , any unprivileged actor can produce a validly-signed message.

`HandleGatewayMessage` (and thus `processTrigger`) is invoked synchronously and inline from the Gateway connector's single-threaded `readLoop`, which processes messages for a given gateway connection one at a time [5](#0-4) . Thus an oversized `Topics` array drives `O(registeredWorkflows × len(topics))` map-lookup iterations to run inline on that shared loop, delaying processing of subsequent legitimate messages on that connection.

## Impact Explanation
This is reachable by any actor able to send a `web_api_trigger` message to the Gateway with a self-signed message — no pre-registration, allowlisting, or elevated role is required to pay the CPU cost, since the allowedSenders check is evaluated only after a topic already matched inside the hot loop. A single oversized request stalls the shared per-connection connector read loop, delaying delivery of all other pending/incoming trigger messages for that DON's Gateway connection, which is a cross-tenant availability impact affecting unrelated workflows sharing the same connection.

## Likelihood Explanation
High. Constructing a large `Topics` array (e.g., tens of thousands of short strings) requires no special privilege and stays comfortably under typical HTTP body size limits. No bypass of any security control is needed because the size check (`len(topics) == 0`) does not bound the maximum, and the sender-authorization check does not gate entry into the loop.

## Recommendation
Enforce a strict maximum on `len(payload.Topics)` in `processTrigger` (and/or in `webapicap.TriggerRequestPayload` validation) before entering the nested loop, rejecting oversized requests early. Perform the sender-allowlist check once, up front, before iterating over topics/triggers, rather than per-match inside the loop. Consider dispatching `HandleGatewayMessage` handling off the synchronous `readLoop` into a bounded worker pool so a single expensive message cannot block unrelated Gateway traffic.

## Proof of Concept
1. As any unprivileged client, generate an ECDSA keypair and self-sign a `web_api_trigger` JSON-RPC message (via `Message.Sign`), setting `payload.Topics` to a large array (e.g., 50,000 short strings), staying under the Gateway's configured `MaxRequestBytesLimiter` byte cap.
2. Send the message through the Gateway HTTP/WS endpoint so it reaches `gatewayConnector.readLoop` → `triggerConnectorHandler.HandleGatewayMessage` → `processTrigger`.
3. Observe that `processTrigger` performs `registeredWorkflows × len(topics)` iterations synchronously inside the shared `readLoop` before the (irrelevant, since it fails after) `allowedSenders` check — measurable via increased latency/backlog for other concurrently queued Gateway messages on that connection. A Go benchmark/unit test calling `processTrigger` directly with a large `Topics` slice and measuring wall-clock time versus a small one demonstrates the unbounded cost scaling.

	defer c.closeWait.Done()

	defer cancel()

	for {

// ValidatedMessageFromReq validated and extracts a legacy Gateway Message
// from params field of JSON-RPC request
func ValidatedMessageFromReq(req *jsonrpc.Request[json.RawMessage]) (*api.Message, error) {
	if req.Version != "2.0" {
		return nil, errors.New("incorrect jsonrpc version")
	}
	if req.Method == "" {
		return nil, errors.New("empty method field")
	}
	if req.Params == nil {
		return nil, errors.New("missing params attribute")
	}
	var m api.Message
	err := json.Unmarshal(*req.Params, &m)
	if err != nil {
		return nil, fmt.Errorf("failed to unmarshal request params: %w", err)
	}
	m.Body.Method = req.Method
	m.Body.MessageID = req.ID
	err = m.Validate()
	if err != nil {
		return nil, err
	}
	return &m, nil
}
