### Title
Large RAY-scaled positions can permanently freeze a market once index growth overflows i128 - (File: `common/src/rates/simulate.rs`)

### Summary
A market containing sufficiently large supply or debt positions can reach a state where every pool operation reverts with `MathOverflow`. Accrual computes `scaled_balance * index` before applying the index ceiling; once index growth pushes that product above `i128::MAX`, `scaled_to_original` panics. Because every market mutation loads and synchronizes the market first, withdrawals, repayments, liquidations, new borrows, new supplies, and explicit index updates all hit the same panic. [1](#0-0) [2](#0-1) 

### Finding Description
`accrue_step` unscales `borrowed` with `borrow_index` and `supplied` with `supply_index` before calculating utilization and the next indexes. [3](#0-2) 

Both unscaling operations call `Ray::mul`, which uses checked fixed-point multiplication and panics on overflow. [4](#0-3) [5](#0-4) 

The later index ceiling does not prevent this state. `update_borrow_index` clamps the newly computed index, but the preceding unscaling of the existing scaled debt has already overflowed; `update_supply_index` similarly multiplies `supplied * old_index` before producing its bounded result. [6](#0-5) [7](#0-6) 

The overflow condition is therefore approximately:

```text
scaled_supply_or_debt * current_index / RAY > i128::MAX
```

For an 18-decimal market, one billion whole tokens produces a RAY-scaled balance of `1e36`; an index above roughly `170 * RAY` exceeds the `i128` value domain, while the configured borrow-index ceiling is `10^36`—a growth factor of `10^9` from the initial index. [8](#0-7) 

Once ledger time has advanced beyond `last_timestamp`, the pool cannot enter a recovery path because `Cache::elapsed_ms` remains nonzero and `global_sync` repeats the overflowing calculation. [9](#0-8) [10](#0-9) 

### Impact Explanation
This can permanently freeze all user funds and debt accounting in the affected `(hub_id, asset)` market absent a contract upgrade or other privileged recovery.

The freeze covers:

- `withdraw`: `ops::load_leg` calls `synced_market`, which invokes `global_sync` before shares are burned or cash is paid. [11](#0-10) 
- `repay`: repayment calls `load_leg` before resolving and burning debt shares. [12](#0-11) 
- `borrow` and `supply`: both use the same synchronized market loading path before minting shares. [13](#0-12) [14](#0-13) 
- `liquidate` touching that market: liquidation repayment and collateral withdrawal route through the pool's synced repay/withdraw operations. [15](#0-14) 
- `update_indexes`: the permissionless recovery call itself forwards to the pool accrual path and reverts. [16](#0-15) [17](#0-16) 

The failed operation rolls back before `last_timestamp` can be updated, so reducing the requested repayment or withdrawal amount does not bypass the panic. [10](#0-9) [9](#0-8) 

### Likelihood Explanation
Likelihood is constrained by the need for an extremely large position and sustained index growth, but the path uses normal unprivileged functionality: `supply`, `borrow`, and `update_indexes`.

An attacker or ordinary whale can establish a large supplied book and borrow utilization within the configured caps. As interest accrues, `borrow_index` and `supply_index` increase while the scaled share totals remain stored as RAY values. Once elapsed ledger time makes the next accrual step require a balance value outside `i128`, any caller invoking `update_indexes` triggers the first overflow; thereafter all operations touching that market re-enter the same failing accrual.

No oracle failure, privileged call, malicious token behavior, or transaction-resource exhaustion is required. The decisive flaw is that market admission and index caps independently bound amounts and indexes, but do not enforce the combined invariant that every stored scaled balance multiplied by every reachable index must remain representable in `i128`. [18](#0-17) 

### Recommendation
Enforce the product-domain invariant directly rather than relying on independent amount and index bounds.

- Add a market-level maximum for scaled supply and debt of `i128::MAX / (MAX_SUPPLY_INDEX_RAY / RAY)` and `i128::MAX / (MAX_BORROW_INDEX_RAY / RAY)`, respectively.
- Apply these limits to supply mints, borrow mints, liquidation credit, strategy-created debt, protocol-fee share minting, and bad-debt/revenue reclassification.
- Add a regression test that creates a large position, advances accrual until near the combined bound, and verifies `update_indexes`, `repay`, `withdraw`, and liquidation continue to work.
- For defense in depth, make accrual detect an impending `scaled * index` overflow before calling `scaled_to_original` and fail only the offending operation with a distinct, diagnosable error. A safer long-term fix is to use a wider intermediate representation for aggregate-value calculations.
- Add deployed-market monitoring for `scaled_supply * supply_index` and `scaled_debt * borrow_index` approaching `i128::MAX`, with intervention before the first irreversible overflow point.

### Proof of Concept
A reachable sequence is:

1. A caller creates or uses an account and calls controller `supply` with a large positive amount for a listed high-decimal market.
2. The caller posts collateral and calls `borrow` against that market, keeping utilization high.
3. As ledger time advances, anyone calls `update_indexes(caller, vec![hub_asset])`; the controller forwards the selected market to pool accrual. [19](#0-18) [16](#0-15) 
4. Once the index has grown enough that `scaled_debt * borrow_index` or `scaled_supply * supply_index` exceeds `i128::MAX`, `accrue_step` panics inside `scaled_to_original`. [3](#0-2) 
5. Subsequent calls to `update_indexes`, `repay`, or `withdraw` for the same market revert identically because their common `load_leg`/`synced_market` path runs `global_sync` first. [2](#0-1) 

The repository's boundary test reproduces this class with a one-billion-token, 18-decimal market at sustained high utilization: the explicit index update returns `MathOverflow`, and subsequent raw withdraw and repay calls return the same error while the borrow index remains below its configured ceiling. [20](#0-19)

```rust
use crate::constants::{MAX_BORROW_INDEX_RAY, MAX_SUPPLY_INDEX_RAY, RAY};
use crate::math::fp::Ray;
use crate::math::fp_core;
use crate::types::MarketParams;

/// Applies `interest_factor` to `old_index` to produce the new borrow index,
/// capped at `MAX_BORROW_INDEX_RAY`.
pub fn update_borrow_index(env: &Env, old_index: Ray, interest_factor: Ray) -> Ray {
    let new_index = old_index.mul(env, interest_factor);
    if new_index.raw() > MAX_BORROW_INDEX_RAY {
        return Ray::from(MAX_BORROW_INDEX_RAY);
    }
    new_index
}

/// Grows `old_index` by distributing `rewards_increase` over the total value
/// currently supplied (`supplied * old_index`). The division rounds down.
///
/// Returns `old_index` unchanged if `supplied` or `rewards_increase` is zero,
/// or if the total supplied value is zero. Clamps the result between
/// `old_index` (itself capped at `MAX_SUPPLY_INDEX_RAY`) and
/// `MAX_SUPPLY_INDEX_RAY`, so the returned index never decreases and never
/// exceeds the cap.
pub fn update_supply_index(env: &Env, supplied: Ray, old_index: Ray, rewards_increase: Ray) -> Ray {
    if supplied == Ray::ZERO || rewards_increase == Ray::ZERO {
        return old_index;
    }

    let total_supplied_value = supplied.mul(env, old_index);

    if total_supplied_value == Ray::ZERO {
        return old_index;
    }

    let new_value = total_supplied_value.checked_add(env, rewards_increase);
    let grown = fp_core::mul_div_floor_saturating(env, new_value.raw(), RAY, supplied.raw());

    let bounded_old = old_index.raw().min(MAX_SUPPLY_INDEX_RAY);
    Ray::from(grown.min(MAX_SUPPLY_INDEX_RAY).max(bounded_old))
```

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
```

```rust
/// Accrues interest, resolves the repay amount into burned debt shares and
/// overpayment, burns the shares, and credits the net repay to cash without
/// transferring the overpayment refund. Panics if a positive net repay would
/// burn zero scaled shares.
pub(crate) fn accounting(env: &Env, action: &PoolAction) -> RepayOutcome {
    let (mut cache, position) = ops::load_leg(env, action);
    let amount = action.amount;

    let (burned, overpayment) = cache.resolve_repay(amount, position);
    let net_repay = amount
        .checked_sub(overpayment)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow));
    assert_with_error!(
        env,
        net_repay == 0 || burned.raw() > 0,
        GenericError::RepayRoundsToZeroShares
    );

    let position = position.checked_sub(env, burned);
    cache.burn_debt(burned);

    cache.credit_cash(net_repay);
```

```rust
/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```
