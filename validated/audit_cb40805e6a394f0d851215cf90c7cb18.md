### Title
`BandwidthManager.purchase()` has no maximum-price protection, letting a governance tier-price update sandwich an in-flight purchase - ([File: evm/src/apps/BandwidthManager.sol])

### Summary
`BandwidthManager.purchase()` reads the current `tierPrice[tier]` at execution time and pulls that exact amount from `msg.sender` with no caller-supplied ceiling on cost, exactly mirroring the Beedle `borrow`/`refinance` pattern where the interest rate is read live from mutable pool state with no borrower-supplied cap.

### Finding Description
`purchase()` computes the amount to charge entirely from live contract state: [1](#0-0) 

`tierPrice[tier]` is mutable, updated at any time by an inbound `SetTiers` governance message via `onAccept`: [2](#0-1) 

A bandwidth purchaser has no way to bound `amount`: `purchase()` takes only `(app, tier, months, chain)` — no `maxAmount`/`maxPrice18d` parameter — so between the moment a purchaser quotes the price off-chain (via `tierPrice(tier)`), approves the ERC-20 allowance for that quoted amount, and their `purchase()` transaction lands, `tierPrice[tier]` can change. This is the same root cause as the referenced Beedle report: a value that determines how much the caller pays is read fresh from mutable storage at execution time, and the caller has no on-chain guard to cap it.

The documented purchase flow explicitly confirms this pattern — the caller reads `tierPrice()`, computes `cost`, approves exactly that amount, then calls `purchase()`: [3](#0-2) 

If `tierPrice[tier]` increases between the approval and the `purchase()` execution (e.g. because a `SetTiers` update lands in an intervening block), the purchase either reverts on insufficient allowance (safe but a griefed/failed tx) or — if the purchaser used an unlimited/`max` approval, which the docs do not discourage — `safeTransferFrom` silently pulls the new, higher amount: [4](#0-3) 

There is no `validUntil`/deadline/max-price check comparable to the one recently added to `IntentGatewayV2.fillOrder` (`FillOptions.validUntil`) specifically to protect a counterparty from a stale/changed price being executed later than intended: [5](#0-4) 

### Impact Explanation
A bandwidth purchaser who grants a standing/large approval to `BandwidthManager` (a normal integration pattern, and the one the official docs show) can be forced to pay an unexpectedly high amount for the same purchase if the tier price is raised between approval and execution, with no on-chain mechanism to cap their maximum spend. This is a concrete loss-of-funds vector directly analogous to the reported issue: the payer has no way to enforce "execute only if price ≤ X," so they can pay materially more than quoted for the exact same `(tier, months)` purchase. Because `SetTiers` can update any tier's price to an arbitrary value with a single message, the magnitude of overpayment is unbounded up to the purchaser's approved allowance.

### Likelihood Explanation
This requires only an ordinary sequence of events: a purchaser with a standing approval (a documented, expected pattern) submits `purchase()`, and a `SetTiers` update is processed in an intervening block — no attacker collusion or malicious governance intent is required, just an ordinary price update landing between a purchaser's quote and execution. This is a design gap (missing slippage control) rather than a governance-integrity issue, so it is a realistic and repeatable Medium-severity finding.

### Recommendation
Add a `maxAmount` (or `maxPrice18d`) parameter to `purchase()` and revert if the computed `amount` (or `total18d`) exceeds it, mirroring the `validUntil` protection already added to `IntentGatewayV2.fillOrder`. This lets a purchaser cap their maximum exposure at call time instead of relying on tight, single-use approvals as the only mitigation.

### Proof of Concept
1. Purchaser calls `tierPrice(tier)` off-chain, computes `cost`, and (per the documented pattern) approves `BandwidthManager` for `cost` (or, in a common integration, for a larger/unlimited amount to avoid repeated approvals).
2. Purchaser submits `purchase(app, tier, months, chain)`.
3. Before this transaction is mined, an `onAccept` `SetTiers` message updates `tierPrice[tier]` to a much higher value (`evm/src/apps/BandwidthManager.sol` lines 213-219).
4. Purchaser's `purchase()` executes against the new, higher `tierPrice[tier]`, computing a larger `amount` (lines 160-168) and pulling that larger amount via `safeTransferFrom` (line 170) — succeeding silently if the approval covers it, or reverting (denial of service) if it does not — in either case the purchaser had no way to cap their exposure to the price they originally quoted.

    function purchase(bytes calldata app, uint256 tier, uint256 months, bytes calldata chain)
        external
        returns (bytes32 commitment)
    {
        if (app.length == 0 || app.length > MAX_APP_LENGTH || chain.length == 0 || months == 0) {
            revert InvalidPurchase();
        }
        uint256 price18d = tierPrice[tier];
        if (price18d == 0) revert UnknownTier();

        uint256 total18d = price18d * months;
        address feeToken = IDispatcher(_host).feeToken();
        uint8 dec = IERC20Metadata(feeToken).decimals();
        uint256 scale = 10 ** (18 - dec);
        if (total18d % scale != 0) revert PriceNotRepresentable();
        uint256 amount = total18d / scale;

        IERC20(feeToken).safeTransferFrom(msg.sender, address(this), amount);

    /// Buy `months` of `tier` for `app` on `chain`.
    /// Caller must have already approved `manager` to spend the
    /// scaled fee-token amount returned by `quote()`.
    function buy(bytes calldata app, uint256 tier, uint256 months, bytes calldata chain)
        external
        returns (bytes32 commitment)
    {
        // Pull the fee token from the caller into this contract,
        // then re-approve the manager. (Or skip this contract and have
        // the user approve the manager directly — see below.)
        uint256 cost = quote(tier, months);
        address feeToken = IDispatcher(host).feeToken();
        IERC20(feeToken).transferFrom(msg.sender, address(this), cost);
        IERC20(feeToken).approve(address(manager), cost);

        commitment = manager.purchase(app, tier, months, chain);
    }

    /// Quote the fee-token cost of a `(tier, months)` purchase.
    function quote(uint256 tier, uint256 months) public view returns (uint256) {
        uint256 price18d = manager.tierPrice(tier);
        uint256 total18d = price18d * months;
        address feeToken = IDispatcher(host).feeToken();
        uint8 dec = IERC20Metadata(feeToken).decimals();
        return total18d / (10 ** (18 - dec));
    }
}
