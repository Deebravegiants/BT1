## Title
Uniswap V4 spot-price venue pricing lets an attacker flash-manipulate a pool to extract oversized fills from a solver's LP vault - (File: sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts)

### Summary
Simplex's Uniswap V4 "pool-based pricing" funding venue prices cross-asset order legs directly off the pool's current `slot0` (spot `sqrtPriceX96`), with no TWAP, no execution-size/impact adjustment, and only an *optional* static-reference deviation guard. An attacker can move the pool's spot price with a swap immediately before (or in the same block as) submitting an intent order, causing the solver to compute and deliver an inflated fill amount from its own Uniswap V4 LP position, mirroring the exact bug class in the referenced Notional report (spot balance used for pricing instead of a manipulation-resistant oracle).

### Finding Description
`UniswapV4FundingPlanner.getExoticTokenPrice` refreshes on-chain state and then derives price purely from the live pool: [1](#0-0) 

The USD price itself is the raw pool mid taken from `sdkPool.token0Price`/`token1Price` (derived from `sqrtPriceX96`), with no fee-tier or size adjustment: [2](#0-1) 

This is explicitly acknowledged in the project's own flow documentation, which states the pool mid is used "linearly across the whole priced quantity" with no size/impact term, and the only defense is an *optional*, static-reference deviation guard rather than a manipulation-resistant price source: [3](#0-2) 

The guard (`referencePrice`/`maxDeviationBps`) is optional and, when omitted, "leaves the chain unguarded": [4](#0-3) 

This is functionally identical to the reported Notional bug class: a spot-reserve-derived value (`virtualSupply`/pool balance there, `sqrtPriceX96`-derived mid here) is used to price/settle a financial operation instead of a time-weighted or otherwise manipulation-resistant value, and it is manipulable within a single transaction/block via a swap against the same pool.

### Impact Explanation
An attacker can perform a flash swap (or a same-block/adjacent-block trade) against the configured Uniswap V4 pool to push its spot price away from fair value, then submit (or have already pending) an intent order priced by `resolveLegRates` off that manipulated quote. Because `computeLegPolicyOutput` extends the manipulated mid price linearly across the full order size with no execution-cost or impact term, the solver's fill computation, its LP-position withdrawal plan, and the tokens it delivers from escrow all derive from an artificially skewed price. This lets an attacker extract more value than the user's escrowed input warrants directly from the solver's Uniswap V4 vault, i.e. concrete theft of solver-held liquidity through the intents fill path. When a chain has no `referencePrice`/`maxDeviationBps` configured (an explicitly supported configuration), there is no bound at all on how far the manipulated price can be pushed before a fill is produced.

### Likelihood Explanation
Any unprivileged actor can submit an intent order and simultaneously (or in a preceding transaction of the same block) trade against the referenced Uniswap V4 pool to shift its spot price — this requires no special privilege, only sufficient capital or a flash loan to move the specific pool used for pricing, which is realistic for lower-liquidity "exotic" token pools that are the primary use case for this pool-pricing feature (e.g., cNGN, ZARP). The price guard is optional per the filler's own configuration and documentation, so any deployment that omits it (a supported, documented configuration) is fully exposed.

### Recommendation
Do not price fills solely off the pool's instantaneous `slot0`/spot mid. Either require the `referencePrice`/`maxDeviationBps` guard unconditionally (make it mandatory rather than optional) or, preferably, replace/augment the spot read with a time-weighted average price (e.g., Uniswap V4's built-in oracle observations) so that a single-block/flash manipulation cannot move the price used to size a fill. Additionally, apply an execution-size/impact term (accounting for the pool's fee tier and depth) rather than extending the spot mid linearly across the whole order size.

### Proof of Concept
1. Attacker identifies a Simplex deployment whose `[vault.uniswapV4]` position for an exotic/USD pair has no `referencePrice`/`maxDeviationBps` guard configured (a supported configuration per `docs/content/developers/evm/simplex/pricing.mdx`).
2. Attacker swaps a large amount into/out of the referenced Uniswap V4 pool, moving `slot0`'s `sqrtPriceX96` far from the pool's normal mid (optionally via flash loan for capital efficiency).
3. Attacker immediately submits an intent order for the affected pair sized near `maxOrderSize`.
4. `resolveLegRates` → `venuePriceMemo()` → `UniswapV4FundingPlanner.getExoticTokenPrice` refreshes and reads the now-manipulated `slot0`, and `computeDirectPoolPriceUsd`/`computeLegPolicyOutput` compute the fill output from that manipulated mid with no impact adjustment.
5. The solver fills the order, withdrawing an inflated amount of the exotic token from its Uniswap V4 LP position relative to what the user's escrowed input is actually worth, transferring the manipulated spread to the attacker at the solver-vault's expense.

	async getExoticTokenPrice(chain: string, exoticToken: string): Promise<Decimal | null> {
		const state = this.stateByChain.get(chain)
		if (!state || !state.isHydrated()) return null

		try {
			await state.refresh()
		} catch (err) {
			this.logger.error({ err, chain }, "Failed to refresh state for price query")
			return null
		}

		const tokenLower = exoticToken.toLowerCase()
		let bestPrice: Decimal | null = null
		let bestLiquidity = 0n

		for (const pos of state.allPositions()) {
			if (pos.currency0.toLowerCase() !== tokenLower && pos.currency1.toLowerCase() !== tokenLower) continue
			const sdkPool = state.getSdkPool(pos.tokenId)
			if (!sdkPool) continue

			const result = this.computeDirectPoolPriceUsd(pos, sdkPool, chain)
			if (result && result.exoticToken.toLowerCase() === tokenLower) {
				const poolLiquidity = state.getPoolLiquidity(pos.tokenId)
				if (poolLiquidity > bestLiquidity) {
					bestPrice = result.priceUsd
					bestLiquidity = poolLiquidity
				}
			}
		}

		if (bestPrice) {
			this.logger.debug({ chain, token: tokenLower, priceUsd: bestPrice.toString() }, "Exotic token price computed")
		}
		return bestPrice
	}

	/**
	 * Computes the USD price of the non-stable token in a pool.
	 * Returns null if neither currency is USDC/USDT on this chain.
	 */
	private computeDirectPoolPriceUsd(
		pos: HydratedV4Position,
		sdkPool: V4Pool,
		chain: string,
	): { exoticToken: string; priceUsd: Decimal } | null {
		const usdc = this.configService.getUsdcAsset(chain).toLowerCase()
		const usdt = this.configService.getUsdtAsset(chain).toLowerCase()
		const c0 = pos.currency0.toLowerCase()
		const c1 = pos.currency1.toLowerCase()

		if (c0 === usdc || c0 === usdt) {
			// currency0 is stable → exotic is currency1
			// token1Price = "token0 per token1" = USD per exotic
			return {
				exoticToken: c1,
				priceUsd: new Decimal(sdkPool.token1Price.toFixed(18)),
			}
		}

		if (c1 === usdc || c1 === usdt) {
			// currency1 is stable → exotic is currency0
			// token0Price = "token1 per token0" = USD per exotic
			return {
				exoticToken: c0,
				priceUsd: new Decimal(sdkPool.token0Price.toFixed(18)),
			}
		}

		return null
	}

# Venue pricing (Uniswap V4 funded pairs)

Verified 2026-08-19.

```
resolveLegRates(...)
  curveless pair && token0 is a USD stable
    -> venuePriceMemo() -> getVenueUsdPrice(chain, token1)
         -> UniswapV4FundingPlanner.getExoticTokenPrice
              picks the position with the largest pool liquidity
              -> computeDirectPoolPriceUsd -> sdkPool.token0Price / token1Price
    -> checkPriceGuard(...)   reject if outside maxDeviationBps of the static reference
    -> rate = 1 / venueUsd
  otherwise -> the pair's ask/bid curve at the leg's notional
```

`computeDirectPoolPriceUsd` returns the **raw pool mid** derived from `sqrtPriceX96`. The pool's
fee tier is read and stored on the hydrated position (`pos.fee`) but never applied to the price,
and there is no size or impact term — `computeLegPolicyOutput` extends the mid linearly across the
whole priced quantity. `checkPriceGuard` is the only defense on this path, and it checks deviation
from a static reference, not execution cost. A venue-priced pair that has to swap through its own
pool to source inventory pays a fee tier it never quoted against.

## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.
