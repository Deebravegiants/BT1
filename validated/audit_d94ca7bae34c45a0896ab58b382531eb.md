## Title
Webhook `shop` (and other Shopify headers) are trusted without being covered by the HMAC signature, enabling cross-tenant webhook forgery - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` (and `topic`, `webhook_id`, `api_version`) purely from HTTP headers, while the HMAC signature verified by `Registry.process` only covers the raw request body. This breaks the intended binding `hmac == HMAC(secret, bytes_that_identify_the_tenant)`; instead the equality that actually holds is `hmac == HMAC(secret, raw_body)` while `shop` is unauthenticated header data acted upon by the handler.

### Finding Description
`Registry.process` validates a webhook solely via: [1](#0-0) 

`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` — it does not include `shop`, `topic`, `webhook_id`, or `api_version`: [3](#0-2) 

Yet `shop` (read straight from the `x-shopify-shop-domain` header) is what gets forwarded to the application's handler as the tenant identity: [4](#0-3) 

Because the Shopify HMAC secret is shared across all shops that install the app (it is the app's `client_secret`, not a per-shop secret), any merchant who installs the app can capture one legitimate `(raw_body, hmac)` pair from a webhook Shopify sends them. The `hmac` value remains valid for that exact `raw_body` regardless of which `x-shopify-shop-domain` header accompanies it, because that header is never part of the signed bytes. An attacker can therefore replay the same body with a forged `x-shopify-shop-domain` header naming a victim shop, and `HmacValidator.validate` will still return `true`.

This is precisely the "field acted on but not covered by the HMAC" class of bug called out for this scan: the check verifies `raw_body` bytes, but the code acts on `shop` bytes that were never part of what was verified.

### Impact Explanation
This allows cross-tenant forgery: an attacker-controlled shop can produce webhook deliveries that the host application will process as if they originated from an arbitrary victim shop (`request.shop` is passed unauthenticated into `WebhookMetadata` and the app's handler). Depending on how the host app keys off `shop` for topics like `app/uninstalled`, `customers/data_request`, `shop/redact`, or business webhooks such as `orders/create`, this can trigger tenant-impersonating side effects (state changes, data deletion/redaction flows, fake order/customer records) attributed to a shop the attacker does not control — a cross-tenant integrity/authentication issue.

### Likelihood Explanation
Any unprivileged internet user who can install the target app on their own (even free/dev) store gains a valid `(raw_body, hmac)` pair signed with the app's real secret, satisfying the "no privileged access, no leaked credentials" constraint. Swapping the `x-shopify-shop-domain` header and replaying the request to the app's public webhook endpoint is trivial and requires no access to secrets held by Shopify or the app.

### Recommendation
Bind the tenant identity into the verified bytes: include `shop`, `topic`, and `webhook_id` in `to_signable_string` (or otherwise cryptographically bind them, e.g. by validating that the shop domain associated with the delivery matches a value derived from data actually covered by the HMAC), so that a valid signature for one shop's payload cannot be replayed under a different shop's identity.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, receiving a legitimate webhook: `raw_body = '{"id":1}'`, `x-shopify-hmac-sha256 = H` (computed by Shopify with the app's `client_secret`).
2. Attacker POSTs the same `raw_body` and same `x-shopify-hmac-sha256: H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, raw_body)` — unaffected by the header change — and matches `H`, so validation passes: [5](#0-4) 
4. The handler is invoked with `shop: "victim.myshopify.com"` even though the request never originated from Shopify for that shop.
