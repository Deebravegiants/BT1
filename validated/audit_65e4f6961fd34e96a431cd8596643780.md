### Title
Attacker-controlled `feeStructure` allows relay fee to round to zero while `hasPaidToRelay` is falsely set - (File: `contracts/Hinkal.sol`)

### Summary
`Hinkal._internalTransact` lets the caller supply an arbitrary `CircomData.feeStructure` (`variableRate`, `flatFee`) with no on-chain or circuit-enforced binding to any relay-agreed rate. By choosing a tiny `variableRate`/`flatFee` combination that makes integer division round `relayFee` down to `0`, the attacker gets `hasPaidToRelay = true` set unconditionally, satisfying the `"relay not paid"` require while zero tokens are actually sent to `circomData.relay`.

### Finding Description
The broken equality: "fee actually owed to the relay for this withdrawal" should equal "fee actually transferred to `circomData.relay`" — under attacker-chosen `feeStructure`, the transferred amount is `0` while `circomData.relay != address(0)` is still asserted to have been paid.

In `contracts/Hinkal.sol` `_internalTransact`: [1](#0-0) 
`relayFee = sumAbs - recipientAmount` where `recipientAmount = ((10000 - variableRate) * (sumAbs - flatFee)) / 10000`. If the attacker picks `variableRate` small relative to `sumAbs` (or `flatFee = sumAbs`, or otherwise engineers rounding), `relayFee` computes to `0` via Solidity's floor-division. Crucially, `hasPaidToRelay = true` is set unconditionally inside the `if (circomData.relay != address(0))` block, **outside** the `if (relayFee > 0)` transfer branch: [2](#0-1) 
Then the closing check only verifies `hasPaidToRelay`, not that a nonzero amount was moved: [3](#0-2) 

`FeeStructure` is a plain field of `CircomData` chosen entirely by the calling user (prover), with no evidence of validation against a relay-registered rate — `RelayStore.sol` only tracks the relay whitelist (`isRelayInList`) and exposes a `calculateRelayFee` pure helper with the identical rounding behavior, but nothing calls it to cross-check `circomData.feeStructure` against an authoritative value: [4](#0-3) 
No hits were found tying `feeStructure`/relay validation into `HinkalHelper.sol`'s `performHinkalChecks`, and the circuit's public signals only constrain balance/amount consistency, not that a specific minimum relay fee was paid. `Transferer.sendToRelay`/`transferERC20TokenOrETH` calls are guarded by `if (relayFee > 0)`, so no revert occurs and the withdrawer receives 100% of `sumAbs`.

Existing guards do not prevent this: `performHinkalChecks`, `verifyProof`, `rootHashExists`, and the balance/slippage requires in `transact` (lines 111-146) all operate on `amountChanges`/balance deltas that are self-consistent regardless of how the `sumAbs` is split between relay and withdrawer — the split itself is never checked against an expected minimum, only that `hasPaidToRelay` boolean was flipped.

### Impact Explanation
The relay whitelisted in `circomData.relay` receives `0` in an operation the fee logic and `require` intend to compensate it for; the withdrawer (attacker or their designated `externalActionData.externalAddress`) receives the full `sumAbs`. This is a theft/permanent loss of protocol/relay fees for every withdrawal the attacker structures this way — matches the "High: theft or permanent freezing of protocol/relay fees" category. It is fully repeatable per transaction at attacker's discretion, at zero extra cost beyond normal gas, since `feeStructure` is freely chosen calldata.

### Likelihood Explanation
Preconditions are trivial and entirely within attacker control: they need any valid withdrawal (`deltaAmountChange < 0`) referencing a whitelisted `circomData.relay != address(0)`, and simply pick `flatFee`/`variableRate` such that `(10000 - variableRate) * (sumAbs - flatFee) / 10000 == sumAbs` (rounding to zero fee), e.g. `flatFee = 0`, `variableRate = 1` (1 bp) and `sumAbs` small enough that `variableRate * sumAbs / 10000 == 0` (any `sumAbs < 10000/variableRate`). No special role, front-running, or relay cooperation is required — the attacker fully controls the fee fields of their own `CircomData`/proof.

### Recommendation
Do not set `hasPaidToRelay = true` unconditionally; require an actual minimum fee transfer, or bind `feeStructure` to a relay-attested/registered rate (e.g., store canonical `flatFee`/`variableRate` per relay in `RelayStore` and require `circomData.feeStructure` to match it, or require `relayFee` computed off the registered rate to be `> 0` whenever `sumAbs > 0`). At minimum, change the guard to also verify `relayFee` is consistent with a protocol-mandated minimum rather than trusting attacker-supplied `feeStructure`.

### Proof of Concept
Foundry test outline:
1. Deploy `Hinkal` + `RelayStore`, whitelist `relay` address.
2. Craft a valid `_internalTransact` withdrawal path (via locally generated proof/circuit inputs) with `amountChanges[i] = -100` (small `sumAbs = 100`), `circomData.relay = relay`, `feeStructure = {feeToken: token, flatFee: 0, variableRate: 1}` (1 bp).
3. Confirm `((10000-1) * 100) / 10000 = 99` (recipientAmount), `relayFee = 100 - 99 = 1` — adjust `sumAbs` down (e.g. `sumAbs = 50`) so `((10000-1)*50)/10000 = 49` gives `relayFee=1`; push further to `sumAbs` such that `variableRate*sumAbs < 10000`, e.g. `sumAbs = 1`, `variableRate = 5000` (50%): `recipientAmount = (5000*1)/10000 = 0`, `relayFee = 1-0 = 1` — still nonzero; instead use `variableRate` small and `sumAbs` small so numerator `<10000`, e.g. `variableRate=1`, `sumAbs=50` → `recipientAmount=(9999*50)/10000=49`, `relayFee=1`. To force `relayFee=0` exactly, need `sumAbs - ((10000-variableRate)*sumAbs)/10000 == 0`, i.e. `variableRate*sumAbs < 10000` with `flatFee=0`. Choose `variableRate = 1`, `sumAbs = 9999` → numerator `variableRate*sumAbs = 9999 < 10000` → `relayFee=0`.
4. Assert before/after: `relay` token balance unchanged (`== 0` delta) while `externalActionData.externalAddress` balance increases by full `sumAbs`, and `transact` call succeeds without reverting on `"relay not paid"`.
5. Assert the equality break explicitly: `feeOwedToRelay (computed off registered rate, if any) != feeActuallyTransferred (0)`.
