### Title
Webhook `shop` identity claim is not covered by HMAC signature, enabling cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` identity used to route/attribute a webhook to a tenant purely from the `X-Shopify-Shop-Domain` HTTP header, while the HMAC signature that `Registry.process` verifies is computed only over the raw request body. This breaks the binding `hmac(bytes) == authenticated(shop)`: an attacker who has legitimately received one signed webhook (e.g., for their own store, using the same shared `client_secret` all installs share) can replay the identical `(body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header. The signature check still passes because the header is never part of the signed payload, and the gem hands the forged `shop` value to the app's handler as trusted data.

### Finding Description
- `Webhooks::Request#hmac` reads the signature from the `hmac-sha256` header, and `#to_signable_string` returns only `@raw_body`: [1](#0-0) 

- `#shop` is read straight from the (unauthenticated) `shop-domain` header, with no relation to the signed bytes: [2](#0-1) 

- `Registry.process` validates only the HMAC (over the body) and then trusts `request.shop` to build `WebhookMetadata` that is passed to the app's handler as the tenant identity for this event: [3](#0-2) 

- `HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (i.e., the body), never incorporating `shop`, `topic`, or `webhook_id`: [4](#0-3) 

Because the same app `client_secret` is shared across every shop that installs the app, any attacker who installs the app on their own store receives genuinely signed webhooks `(body, hmac)` for that body. Since the signature never binds to `shop`, the attacker can resend that exact `(body, hmac)` pair to the app's public webhook endpoint with a different `X-Shopify-Shop-Domain` header value naming a victim tenant. `Registry.process` will accept the HMAC (it matches the unmodified body) and dispatch the event to the handler labelled with the attacker-chosen `shop`, which is the field applications use to look up/scope tenant records (session/access token, DB row, etc.).

### Impact Explanation
This is a cross-tenant identity-binding bypass at the library layer: the security-relevant field (`shop`) that determines which tenant's data/session the webhook event is attributed to is not covered by the cryptographic check that is supposed to authenticate the request. Any application that uses `WebhookMetadata#shop` (the gem's documented mechanism for webhook consumers) to select the tenant's session/store record inherits a cross-tenant confusion vector purely from using the gem as documented — this satisfies the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is realistic for any attacker who can install the app on their own shop (a normal, unprivileged flow for public apps) — they trivially obtain valid `(body, hmac)` pairs signed with the shared `client_secret`, then replay them directly to the app's webhook HTTP endpoint (a public URL) with a forged `shop-domain` header, since no other request property is authenticated.

### Recommendation
Bind the identity fields into the signed payload verification, not just the raw body — e.g., verify the `shop`/`topic`/`webhook-id` headers against a signable representation that includes them (mirroring how `Auth::Oauth::AuthQuery#to_signable_string` incorporates `shop`), or require the application layer to independently authenticate/whitelist `shop` (e.g., against a known/installed shop list) before trusting it, and document this gap clearly since the current `to_signable_string` in `Webhooks::Request` only covers the body.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering a real event; Shopify sends a webhook `POST` with body `B` and header `X-Shopify-Hmac-Sha256: HMAC-SHA256(client_secret, B)`.
2. Attacker captures `(B, hmac)`.
3. Attacker sends `POST` to the app's public webhook endpoint with body `B`, the same `hmac` header, but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` — passes, because validation only hashes `@raw_body` (`lib/shopify_api/utils/hmac_validator.rb:12-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
5. `request.shop` returns `"victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/request.rb:20-23`), and the app's handler receives `WebhookMetadata` claiming the event belongs to the victim shop, even though it never occurred there.
