Confirmed: the bug-class from the PoolTogether report — an attacker-controlled callee consuming/returning outsized gas during a low-level call, made inside a loop over multiple items in one transaction, degrading gas available to the rest of the batch — has a concrete analog in Hyperbridge's message-delivery path.

### Title
Gas-griefing DoS via malicious `IApp` destination in batched `HandlerV2.handlePostRequests`/`handleGetResponses` — (File: `evm/src/core/HandlerV2.sol`, `evm/src/core/EvmHost.sol`)

### Summary
`HandlerV2.handlePostRequests` and `HandlerV2.handleGetResponses` iterate over a relayer-supplied batch of requests/responses in a single transaction, calling `host.dispatchIncoming(...)` for each item without any gas isolation between iterations. `EvmHost.dispatchIncoming` forwards an unbounded amount of gas to an arbitrary, attacker-influenced destination address via a raw `.call(...)`. A malicious `IApp` destination can consume (or force the loss of) almost all gas forwarded to it before failing, starving subsequent legitimate deliveries in the same batch — exactly the "malicious winner burns gas via a huge/expensive callee response, degrading the rest of the batch" pattern from the PoolTogether report.

### Finding Description
`HandlerV2.handlePostRequests` loops over `requestsLen` items and calls `host.dispatchIncoming(leaf.request, _msgSender())` for each in the same transaction: [1](#0-0) 

`handleGetResponses` has the identical pattern: [2](#0-1) 

`EvmHost.dispatchIncoming(PostRequest,...)` resolves `request.to` to an arbitrary address and makes a low-level call with no gas cap, catching only success/failure: [3](#0-2) 

The GET-response variant behaves the same way: [4](#0-3) 

Because no explicit gas stipend is passed to `.call(...)`, Solidity forwards essentially all gas remaining in the current frame (minus the 1/64 reserved by EIP-150) to the destination module's `onAccept`/`onGetResponse`. A destination contract is not vetted by the host — any contract with nonzero `extcodesize` at the decoded `to` address is called. An attacker can deploy such a contract as the target of one of their own dispatched requests (or otherwise get it included as one leaf of a relayer's batch alongside unrelated legitimate requests, since a relayer's `PostRequestMessage`/`GetResponseMessage` batches are constructed from whatever pending, provable items exist and are not filtered by "which app"). Inside `onAccept`, the malicious contract can burn most of the gas forwarded to it (e.g., a loop, or by returning a very large `RETURN` payload so memory-expansion costs consume the forwarded gas) so that the call fails by running entirely out of gas.

Critically, when a sub-call fails by exhausting *all* the gas forwarded to it (as opposed to merely reverting early), none of that gas is refunded to the caller — unlike an early revert, which returns the untouched portion. `dispatchIncoming` swallows this failure (`if (!success) { delete receipt; return; }`) so the outer `handlePostRequests`/`handleGetResponses` call does not revert, and the `for` loop proceeds to the next leaf — but with drastically less gas left in the transaction. Legitimate, otherwise-valid requests batched later in the same call can then themselves fail (their `onAccept` running low/out of gas), have their freshly-written receipts deleted, and be left undelivered, even though their proofs verified correctly and the relayer paid gas for them.

### Impact Explanation
This is a griefing/DoS vector against relayers and against legitimate cross-chain message delivery: a single malicious `IApp` deployment can, at attacker-chosen timing, cause co-batched legitimate `PostRequest`/`GetResponse` deliveries to fail (receipts rolled back, `PostRequestHandled`/`GetRequestHandled` never emitted), forcing relayers to pay gas for a failed delivery and resubmit. For GET responses this additionally skips the relayer fee payout (`IERC20(feeToken()).safeTransfer(relayer, fee)` is only reached on `success`), so the relayer's fee for `dispatchIncoming(GetResponse,...)` is withheld/lost for messages caught in the blast radius. Repeated exploitation can be used to selectively suppress delivery of specific competitor requests/responses that a relayer happens to batch together with the attacker's poisoned item, and to griefing-drain relayer gas budgets. This matches the Medium severity classification given to the analogous PoolTogether finding.

### Likelihood Explanation
Any address can deploy an `IApp`-shaped contract and become the destination (`to`) of a `PostRequest`/have a pending `GetRequest` whose response is delivered through this path — dispatch of requests/GET requests is permissionless from the app layer, and `handlePostRequests`/`handleGetResponses` are explicitly permissionless too (`notFrozen` is the only gate). No special privilege or timing is required beyond getting the malicious leaf included in the same MMR batch/transaction as targeted legitimate leaves, which a relayer naturally does when it batches all currently-provable pending items to amortize proof-verification cost.

### Recommendation
Cap the gas forwarded to each destination module call in `EvmHost.dispatchIncoming` (both `PostRequest` and `GetResponse`/timeout variants) to a fixed, generous-but-bounded stipend, and/or explicitly discard callee return data without decoding it into memory to avoid return-bomb amplification. Consider tracking gas actually consumed per dispatch and reverting/skipping remaining loop iterations gracefully if the transaction is close to exhaustion, rather than silently continuing with degraded gas. Additionally, consider isolating each `dispatchIncoming` call further (e.g., via a sub-call with an explicit `gas:` value sized from testing worst-case legitimate `onAccept` cost) so a single malicious module cannot starve sibling deliveries in the same batch.

### Proof of Concept
1. Attacker deploys `EvilApp` implementing `IApp.onAccept` that, upon being called, executes a gas-burning loop (or returns an oversized payload) sized to consume nearly all forwarded gas before failing (e.g., `while(true){}` guarded to consume ~(gasleft() - small_margin)`, or `return new bytes(huge_length)` after doing enough work to hit the memory-expansion wall).
2. Attacker dispatches a `PostRequest` (or has a pending `GetRequest`) whose `to`/`from` resolves to `EvilApp`.
3. A relayer submits `HandlerV2.handlePostRequests` (or `handleGetResponses`) with a batch containing the malicious leaf and one or more legitimate leaves destined for well-behaved apps, sized so the transaction's total gas limit is only slightly above what the legitimate leaves alone would need.
4. `dispatchIncoming` for the malicious leaf forwards ~63/64 of remaining gas to `EvilApp.onAccept`, which fully consumes it and fails via out-of-gas; `dispatchIncoming` swallows this (`!success` branch), rolling back only the malicious leaf's receipt.
5. The loop proceeds to the legitimate leaf(s) with insufficient gas remaining; their `onAccept` calls fail/run out of gas too, their receipts are deleted, and `PostRequestHandled`/`GetRequestHandled` is never emitted for them — despite valid proofs — requiring the relayer to resubmit and re-pay gas.

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }
