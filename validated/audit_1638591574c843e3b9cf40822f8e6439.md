Audit Report

## Title
Outbound HTTP response cache is keyed only by owner (not workflow), allowing cross-workflow cache confusion - (File: core/services/gateway/handlers/capabilities/v2/response_cache.go)

## Summary
The gateway's `responseCache` for outbound HTTP Action requests keys cached responses using `OutboundHTTPRequest.Hash()`, which by the test suite's own explicit assertions excludes `WorkflowID` and `CacheSettings`, including only method/URL/headers/body/`WorkflowOwner`. This directly contradicts the documented invariant in the component's README that cache entries are scoped per-workflow to prevent cross-workflow data leakage, allowing one workflow's cached HTTP response to be transparently served to a different workflow of the same owner.

## Finding Description
`gatewayHandler.makeOutgoingRequest` calls `h.responseCache.Fetch(httpCtx, req, callback, req.CacheSettings.Store)` whenever `req.CacheSettings.MaxAgeMs > 0`, and calls `h.responseCache.Set(req, outboundResp)` otherwise when `CacheSettings.Store` is true. Both `Fetch` and `Set` in `response_cache.go` use `req.Hash()` as the sole map key for `rc.cache`. The `response_cache_test.go` file contains explicit unit tests ("having different workflowID results in same Hash" and "having different cacheSettings results in the same Hash") that assert `Hash()` is identical regardless of `WorkflowID` and `CacheSettings`, while differing `WorkflowOwner` does change the hash. This means any two workflows sharing the same `WorkflowOwner` that issue HTTP requests with identical method/URL/headers/body will collide on the same cache entry, regardless of `WorkflowID`. This behavior directly contradicts the README's documented "Workflow Isolation" guarantee that cache entries are scoped by workflow ID.

## Impact Explanation
This breaks the documented per-workflow isolation boundary: a response fetched and cached on behalf of one workflow (owned by principal `O`) can be transparently served to a second, distinct workflow also owned by `O`, without any additional check, as long as method/URL/headers/body match. This can result in cross-workflow response corruption/confusion (stale or wrong data delivered to the wrong workflow, or unintended sharing of cached response headers/bodies), and can also cause a workflow author's intended `CacheSettings.Store=false` semantics to be bypassed via pollution from another workflow's `Store=true` write, since `CacheSettings` is excluded from the hash as well. The impact is scoped to workflows under the same owner (cross-owner leakage does not occur since `WorkflowOwner` is included in the hash), which limits severity, but it is a real violation of a documented isolation guarantee reachable through ordinary use of the HTTP Action capability.

## Likelihood Explanation
Any workflow belonging to an owner that runs multiple workflows can trigger this deterministically by issuing HTTP Action requests with `CacheSettings.MaxAgeMs > 0` that overlap in method/URL/headers/body with another of that owner's workflows (e.g., both querying a common external API). No race conditions, special privileges, or unusual timing are required — it is a direct, deterministic consequence of the cache key design, and the project's own test suite explicitly documents and asserts this exact behavior.

## Recommendation
Include `WorkflowID` in the `OutboundHTTPRequest.Hash()` computation (and reconsider whether `CacheSettings` should also factor into cache key or caching decisions) so that `responseCache` entries are truly scoped per workflow, matching the documented isolation guarantee in `core/services/gateway/handlers/capabilities/v2/README.md`. Alternatively, if owner-level sharing across workflows is an intentional design decision, update the README to remove or correct the "Workflow Isolation" claim and the "Cache Key: Generated from workflow ID and request hash" description to accurately reflect owner-level (not workflow-level) scoping.

func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

	// Slow path: singleflight deduplicates concurrent fetches per key.
	// Cache check + store happen inside the flight so the key isn't released
	// until the result is cached, closing the race window between singleflight
	// completion and cache write.
	result, _, _ := rc.flight.Do(cacheKey, func() (any, error) {
		// Re-check cache: a previous flight may have just stored the result.
		rc.cacheMu.RLock()
		cachedResp, exists := rc.cache[cacheKey]
		rc.cacheMu.RUnlock()
		if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
			rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
			return cachedResp.response, nil
		}

		response := fetchFn()

		if storeOnFetch && isCacheableStatusCode(response.StatusCode) {
			rc.cacheMu.Lock()
			rc.cache[cacheKey] = &cachedResponse{
				response: response,
				storedAt: time.Now(),
			}
			rc.cacheMu.Unlock()
		}

		return response, nil
	})

	return result.(gateway.OutboundHTTPResponse)
}

// Set caches a response if it is cacheable (2xx or 4xx and cache is empty or expired for the given request)
func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}
