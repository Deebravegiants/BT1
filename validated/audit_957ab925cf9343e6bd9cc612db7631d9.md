### Title
Excess native value paid during `EvmHost.dispatch`/`fundRequest` swaps is not refunded to the caller - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest` accept `msg.value` and swap it via `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(...)` to buy an exact amount of fee token, but never forward the router's ETH refund back to the original caller.

### Finding Description
When a user/keeper dispatches a POST or GET request (or funds an existing request) using native token payment, the exact fee-token amount needed is not known in advance, so callers must overpay `msg.value` to guarantee the swap succeeds. `EvmHost` performs the swap like this: [1](#0-0) 

```
function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
    if (msg.value > 0) {
        ...
        IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
            post.fee, path, address(this), block.timestamp
        );
    }
```

The same pattern is repeated for GET requests and for `fundRequest`: [2](#0-1) [3](#0-2) 

`swapETHForExactTokens` on a standard `UniswapV2Router02` refunds any unspent ETH to `msg.sender` of that call — but in this call chain, the router's `msg.sender` is `EvmHost` itself (since `EvmHost` is the direct caller of the router), not the original end user. `EvmHost` never captures that refund and forwards it to `_msgSender()`. There is no logic anywhere in `dispatch`/`fundRequest` to compute `msg.value - amountSpent` and send it back, and no `withdraw`-style function surfaced for users to reclaim it. As a result, any ETH refunded by the router accumulates as stuck balance in the `EvmHost` contract.

This is the exact bug class from the referenced Pyth `PythOracle.commit` report: a payable function performs a variable-cost operation funded by `msg.value`, and the unspent remainder is never routed back to the caller.

Notably, other apps in this same codebase (e.g., `IntentGatewayV2.placeOrder`/`_fillCrossChain`) correctly compute and refund unspent native value after doing the identical Uniswap swap pattern: [4](#0-3) 
which confirms that `EvmHost.dispatch`/`fundRequest` are missing the equivalent refund step that the rest of the protocol implements elsewhere.

### Impact Explanation
Every keeper/user who dispatches a POST/GET request or funds a request using native-token payment (the documented, first-class payment path per the docs: "User must send enough native tokens to cover fees... The Host will swap native -> feeToken") will systematically overpay to avoid reverts, and that overpayment is permanently locked in `EvmHost` with no path to recovery for the payer. Given `dispatch`/`fundRequest` are the core, unprivileged entry points for outbound messaging (used by any `IApp`, including token bridges, intents, and the LayerZero endpoint adapter), this results in a continuous, protocol-wide loss of native funds for anyone using native-token payment, satisfying "concrete... permanent freezing of funds" for callers.

### Likelihood Explanation
High likelihood: any relayer, dApp, or SDK integration using the documented native-payment path (`dispatch{value: msg.value}(...)`) on any EVM deployment of `EvmHost` will trigger this on every call, since the exact Uniswap swap cost cannot be known precisely off-chain and users are advised to overpay to avoid reverts.

### Recommendation
In `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, capture the amount actually spent by the swap (e.g., `amounts[0]` returned by `swapETHForExactTokens`) and refund `msg.value - amountSpent` to `_msgSender()` at the end of the function, following the same pattern already used in `IntentGatewayV2._placeOrder`/`_fillCrossChain` (compute `msgValue -= amounts[0]`, then `_sendValue(msg.sender, msgValue)` if `msgValue > 0`).

### Proof of Concept
1. User calls `EvmHost.dispatch{value: 5 ether}(post)` where `post.fee` only requires 0.01 ETH worth of swap input.
2. `swapETHForExactTokens{value: 5 ether}(post.fee, ...)` executes; the router refunds the unused ~4.99 ETH to `msg.sender`, which is `EvmHost`.
3. `EvmHost.dispatch` returns without ever inspecting or forwarding that refund; the ~4.99 ETH remains in `EvmHost`'s balance.
4. There is no user-facing function to reclaim this ETH — compare with `IntentGatewayV2.placeOrder`, tested explicitly in `testPlaceOrder_FeeSwap_RefundsExcessNativeToken` ( [5](#0-4) ), which shows the refund pattern that `EvmHost.dispatch` lacks.

    /// @notice placeOrder with fee swap refunds unused ETH after swapETHForExactTokens.
    function testPlaceOrder_FeeSwap_RefundsExcessNativeToken() public {
        uint256 inputAmount = 1000 * 1e6;
        uint256 feeAmount = 1 * 1e18; // 1 DAI worth of fees

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(usdc)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 1000 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 1000,
            nonce: 0,
            fees: feeAmount,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        uint256 userEthBefore = user.balance;

        vm.startPrank(user);
        usdc.approve(address(intentGateway), inputAmount);
        // Send 5 ETH for a fee swap that should cost much less
        intentGateway.placeOrder{value: 5 ether}(order, bytes32(0));
        vm.stopPrank();

        // User should get back most of the 5 ETH — the swap only needed a tiny fraction
        uint256 ethSpent = userEthBefore - user.balance;
        assertTrue(ethSpent < 1 ether, "User should have been refunded most of the 5 ETH");
        assertTrue(ethSpent > 0, "User should have spent some ETH on the fee swap");
    }
