# CVE-2025-50101 Analog Analysis: Attacker-Controlled Mint Decimals Cause Panics in Decimal Normalization (Permanent Fund Freeze)

### Title
Unbounded mint `decimals` value causes `checked_pow`/`unwrap` panic in decimal-normalization math, permanently freezing pool funds - (File: `program/src/math.rs`)

### Summary
CVE-2025-50101 describes a MySQL optimizer bug where crafted, in-bounds-but-extreme input causes the server to hang/crash (complete DoS). The analogous bug class in this codebase is a set of decimal-normalization helpers in `Calculator` that compute `10^decimals` using `U128::checked_pow(...).unwrap()`. Because `decimals` is stored as `amm.coin_decimals` / `amm.pc_decimals` (type `u8`, 0–255) and is populated directly from the SPL mint account's `decimals` field at pool creation, an unprivileged pool creator can register a pool for a custom mint with an extreme decimals value (well above the ~38 that fits into a `u128`). Every subsequent Deposit, Withdraw, or Swap on that pool then panics inside `Calculator::normalize_decimal_v2` / `restore_decimal`, aborting the transaction unconditionally and rendering the pool (and any coins already deposited into its vaults) permanently unusable.

### Finding Description
`Calculator::normalize_decimal`, `Calculator::restore_decimal`, and `Calculator::normalize_decimal_v2` in `program/src/math.rs` all compute a power-of-ten scaling factor and immediately `.unwrap()` the result: [1](#0-0) [2](#0-1) 

`U128::checked_pow` returns `None` on overflow. `U128`'s maximum representable value is roughly `3.4×10^38`, so `checked_pow(10, native_decimal)` overflows (returns `None`) for any `native_decimal` greater than about 38. Since `native_decimal` here is `amm.coin_decimals` / `amm.pc_decimals` — a `u8` field that can range 0–255 — any pool whose underlying SPL mint reports a decimals value above ~38 will make every call into these functions panic.

These normalization routines are invoked from the core, unprivileged-reachable instruction handlers:
- Deposit / PnL accounting path: `Self::calc_take_pnl` calls `Calculator::normalize_decimal_v2` on `total_pc_without_take_pnl` / `total_coin_without_take_pnl` before any liquidity math is done. [3](#0-2) 
- Withdraw path performs the identical normalization before computing PnL and moving vault funds. [4](#0-3) 
- `calc_take_pnl` itself additionally does `Calculator::restore_decimal` on `target.calc_pnl_x` / `target.calc_pnl_y` using `amm.pc_decimals` / `amm.coin_decimals`. [5](#0-4) 

Because `amm.coin_decimals`/`amm.pc_decimals` are fixed at pool `Initialize2` time from the coin/pc mint account's `decimals` field (an SPL Token Mint field fully controlled by whoever creates the mint being registered — pool creation via `Initialize2` is a permissionless, unprivileged operation), an attacker can:
1. Create a normal SPL mint with `decimals = 200` (or any value > ~38) using the standard SPL Token program (unprivileged, off the AMM program but a normal prerequisite for registering any new pool).
2. Call `Initialize2` to register an AMM pool for that mint, seeding the pool with some initial coin/pc liquidity into the vaults.
3. Any subsequent `Deposit`, `Withdraw`, `SwapBaseIn`, or `SwapBaseOut` instruction touching that pool reaches `calc_take_pnl` (directly or via the swap-adjacent PnL bookkeeping), which calls `Calculator::normalize_decimal_v2` / `restore_decimal`, triggering `checked_pow(...).unwrap()` on `None` and panicking, aborting the entire transaction with a runtime panic every single time.

The result is a pool that is permanently unusable: liquidity contributed during `Initialize2` (and any further deposits made before the decimals mismatch is discovered) can never be withdrawn, and the pool can never be swapped against, because every reachable instruction path unconditionally panics.

### Impact Explanation
This is a permanent freezing of funds. Once a pool is created against a mint with an out-of-range `decimals` value, any coin/pc tokens already sitting in the AMM's vaults (from the initial `Initialize2` liquidity provisioning) become permanently inaccessible, since `Withdraw` panics before it can transfer funds out. LP holders similarly cannot exit, and no swap volume can ever be routed through the pool. This matches the CVE's "hang or frequently repeatable crash (complete DOS)" bug class, translated to the Solana program context as an unconditional, deterministic panic on every instruction touching the affected account state.

### Likelihood Explanation
The attack requires only steps available to any unprivileged user: creating an SPL mint with an arbitrary `decimals` byte (standard SPL Token program functionality, no special privilege) and calling the permissionless `Initialize2` instruction to stand up a pool for it. No signer other than the pool creator/attacker is required, and no on-chain validation appears in the reviewed code to reject the pool if `decimals` exceeds a safe bound (the `checked_pow`/`unwrap` calls only fail at first use, not at pool-creation time).

### Recommendation
- Validate `coin_mint.decimals` and `pc_mint.decimals` during `Initialize2` and reject pool creation if they exceed a safe bound (e.g., ≤ 18, consistent with practically all real-world SPL tokens and comfortably below the `U128` power-of-ten overflow threshold).
- Replace the `.unwrap()` calls in `Calculator::normalize_decimal`, `restore_decimal`, and `normalize_decimal_v2` (`program/src/math.rs:80-116`) with proper `checked_pow`/`ok_or(AmmError::...)` error propagation so an unexpected decimals value produces a recoverable `ProgramError` instead of a panic, preventing any single malformed pool from becoming permanently stuck.

### Proof of Concept
1. Using the SPL Token program, create a new mint `M` with `decimals = 200` (a value the SPL Token program readily accepts, since `decimals` is a plain `u8`).
2. Call the AMM's `Initialize2` instruction to create a new pool using mint `M` as the coin (or pc) mint, supplying some initial coin/pc liquidity, e.g., 1000 units.
3. Attempt to call `Withdraw` (or `Deposit`, `SwapBaseIn`, `SwapBaseOut`) on the newly created pool.
4. Execution reaches `Processor::calc_take_pnl` → `Calculator::normalize_decimal_v2(total_pc_without_take_pnl, amm.pc_decimals=200, amm.sys_decimal_value)` → `U128::from(10).checked_pow(200.into())` returns `None` → `.unwrap()` panics, aborting the transaction.
5. Every subsequent transaction touching this pool (any Deposit/Withdraw/Swap) will panic identically, permanently freezing the funds already locked in the pool's vaults.
