### Title
Emporium "min-circuit" path (`erc20TokenAddresses.length == 0`) lets attacker execute arbitrary, unaccounted value-moving operations that drain any ETH/ERC20 balance held by the `Emporium` contract - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
When `circomData.erc20TokenAddresses.length == 0`, `Hinkal._externalTransact` builds a zero-length `deltaAmountChanges` array and `EmporiumUpgradeable.runAction`'s balance-accounting loops (`balancesBefore`/`balancesAfter`/`deltaAmountChanges`) all iterate zero times, so value conservation holds vacuously. Meanwhile `stack.ops.length` (fully attacker-controlled, decoded from `externalActionMetadata`) is unrelated to that length and is executed unconditionally in the loop at lines 91-118, letting the attacker run arbitrary `op.endpoint.call{value: op.value}(op.callData)` calls that move real ETH/ERC20 out of the `Emporium` contract with zero balance checks.

### Finding Description
The broken equality: **number of value-moving ops executed (`stack.ops.length`, attacker-chosen) != number of token slots accounted for conservation (`circomData.erc20TokenAddresses.length`)**. When the attacker sets `erc20TokenAddresses = []`:

- `Hinkal._externalTransact` allocates `deltaAmountChanges` of length 0 [1](#0-0) .
- `EmporiumUpgradeable.runAction` computes `balancesBefore`/`balancesAfter` over the same empty array, and the final accounting loop `for (i = 0; i < circomData.erc20TokenAddresses.length; i++)` never executes [2](#0-1) , [3](#0-2) .
- The outer balance-conservation loop in `Hinkal.transact` (`balanceDif`/slippage checks) also iterates over `circomData.erc20TokenAddresses.length`, i.e. zero times [4](#0-3) .
- Meanwhile the ops loop `for (uint256 i = 0; i < stack.ops.length; i++)` executes fully, with `stack` decoded directly from attacker-supplied `circomData.externalActionData.externalActionMetadata` [5](#0-4) .

Root cause / why guards fail:
- `CircomDataBuilder.formInputForCircom` routes to `formInputEmporiumMin` whenever `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0`, producing only 3 public signals (`emporiumMessage`, `timeStamp`, `calldataHash`) [6](#0-5) .
- `MainEVMCircuitMin` never constrains `calldataHash` to anything - it only outputs `message <== Poseidon(1)([messageSeed])` - so the circuit does not bind `stack.ops` content at all [7](#0-6) .
- `verifyWallet` is the only other place `stack.ops` is checked, via an EIP-712 signature recovered against `stack.signerAddress`; but if the attacker sets `stack.signerAddress == address(0)` (the "CASE 2 / stateless" path), `verifyWallet` returns immediately after marking the anti-replay flag, performing **no validation of `stack.ops` whatsoever** [8](#0-7) .
- `getHashedCalldata`/`calldataHash` check in `performHinkalChecks` only enforces that the attacker's declared `calldataHash` matches their own submitted calldata - it does not restrict the content of that calldata, so it provides no protection against the attacker choosing arbitrary `stack.ops` [9](#0-8) .

Attacker call: submit `Hinkal.transact` with `dimensions.tokenNumber = 0`, `circomData.erc20TokenAddresses = []`, `externalActionId = HINKAL_EMPORIUM_ACTION_ID`, and `externalActionMetadata` decoding to an `EmporiumStack` with `signerAddress = address(0)` and `ops` containing N calls whose `endpoint.call{value: op.value}(op.callData)` drain whatever ETH/ERC20 balance the `Emporium` contract currently holds to attacker-controlled addresses. Only a trivially self-chosen `messageSeed` is needed to produce a valid min-circuit proof - no real secret is proven.

### Impact Explanation
Any ETH/ERC20 balance resident in the shared `Emporium` contract at call time (e.g., dust left over from prior multi-hop swaps that touched a token not listed in a previous call's `erc20TokenAddresses`, unswept remainders, or funds momentarily in flight from other users' transactions) can be drained in a single call, to any number of destinations, with zero accounting. This is repeatable every time the `Emporium` contract accumulates any balance, and there is no upper bound on the number of ops (and hence the number of distinct balances/tokens) drained per call. This matches the Critical category: direct theft of in-flight/protocol-held user funds via calls a wallet owner or prover never authorized.

### Likelihood Explanation
Preconditions: attacker needs the `Emporium` contract to hold a non-zero balance of some asset (realistic given its role as a shared multi-step DeFi router for many users' transactions) and needs to be able to submit a `transact` call with `erc20TokenAddresses = []` and `externalActionId = HINKAL_EMPORIUM_ACTION_ID` with `signerAddress = 0`. The attacker needs no special role - just the ability to generate the trivial min-circuit proof (self-chosen `messageSeed`) and craft `externalActionMetadata`. Cost is minimal (gas only); the attack is repeatable any time exploitable balance accrues in `Emporium`.

### Recommendation
- Do not allow the "min circuit" / zero-token path to execute stateless (`signerAddress == address(0)`) ops with nonzero `op.value` or ERC20-moving `callData`; require `erc20TokenAddresses.length == 0` implies all ops are either signer-authenticated (`invokeWallet && signerAddress != 0`, cryptographically bound via `_hashEmporiumOps`) or provably zero-value/no-token-moving.
- Alternatively, always compute `balancesBefore`/`balancesAfter` for a fixed, protocol-known set of tokens actually touched by `stack.ops` (or force `erc20TokenAddresses` to include every token any op could move), so accounting can never be vacuously satisfied while ops move real value.
- Bind `stack.ops` (or its hash) into the min circuit's public inputs so ops are provably constrained even in the reduced-input path.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable` (as allowed recipient/external action), and a mock ERC20/target. Seed the `Emporium` proxy with ETH and a mock ERC20 balance (simulating leftover balance from a prior transaction/dust).
2. Craft `CircomData` with `erc20TokenAddresses = []`, `amountChanges = []`, `onChainCreation = []`, `slippageValues = []`, `dimensions.tokenNumber = 0`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, and `externalActionMetadata` = ABI-encoded `EmporiumStack{ signerAddress: address(0), ops: [5 EmporiumOperation entries each calling a "drain" function on the mock ERC20/target transferring balance to attacker] }`.
3. Generate a valid min-circuit proof locally for `MainEVMCircuitMin` (trivial, self-chosen `messageSeed`), matching `buildVerifierId(dimensions, HINKAL_EMPORIUM_ACTION_ID)`.
4. Call `Hinkal.transact(a, b, c, dimensions, circomData)` from an unprivileged EOA.
5. Assert: all 5 ops succeed; `Emporium`'s ETH/ERC20 balance goes to 0 and attacker's balance increases by the full amount; assert no `require` in `Hinkal.transact` (balanceDif==0==0) or `EmporiumUpgradeable.runAction` (`balancesBefore.length==0==balancesAfter.length`) ever fires, proving the drain was completely unaccounted for.
