### Title
Interest accrual overflows `i128` on large RAY balances and permanently freezes the market - (File: common/src/rates/scaling.rs)

### Summary

Large, otherwise valid markets can grow their borrow and supply indexes until `scaled_shares * index / RAY` no longer fits in `i128`. `accrue_step` performs this multiplication before applying the nominal borrow-index ceiling, so an `i128::MAX` value boundary is reached while the index remains far below `MAX_BORROW_INDEX_RAY`. The resulting `MathOverflow` is hit by every operation that synchronizes the market, permanently preventing repayments, withdrawals, liquidations, and further index updates.

### Finding Description

`scaled_to_original` converts scaled RAY balances to their current value with `scaled.mul(index)`, which evaluates `scaled * index / RAY` and rejects results that do not fit in `i128`. [1](#0-0) [2](#0-1) 

Every accrual step computes both total debt and total supplied value through this conversion before calculating utilization, updating the borrow index, or updating the supply index. [3](#0-2) 

The borrow-index ceiling is `1e36` raw RAY, equivalent to an index of `1e9`, while an 18-decimal market holding one billion whole tokens has a scaled balance of `1e36`; therefore value multiplication overflows once the index exceeds approximately `170`, far below the configured cap. [4](#0-3) [5](#0-4) 

The pool calls `global_sync` before each mutation leg, and `update_indexes` calls the same accrual path directly. [6](#0-5) [7](#0-6) 

A caller can trigger the condition through the permissionless `update_indexes(caller, assets)` path, and the same panic prevents later calls to `withdraw`, `repay`, `borrow`, `liquidate`, and other operations involving the affected market. [8](#0-7) [9](#0-8) 

### Impact Explanation

This permanently freezes user funds in the affected market. Suppliers cannot withdraw because `withdraw` first synchronizes indexes; borrowers cannot repay because `repay` also synchronizes before burning debt shares; liquidators cannot reduce the unsafe debt because liquidation legs use the same synced-market path. Direct pool payments and recapitalization do not remove the oversized scaled balances, so the next accrual still overflows.

Because the panic happens before the debt position can be reduced, there is no unprivileged recovery path. The repository already contains a regression demonstrating that a one-billion-token, 18-decimal market at 98% utilization reaches `MathOverflow`, while `borrow_index` remains below `MAX_BORROW_INDEX_RAY`, and that both withdrawal and repayment subsequently fail. [10](#0-9) 

### Likelihood Explanation

Likelihood is medium. The attack requires a market configuration that permits a very large balance and a high-utilization period under a steep rate curve, but all amounts used in the demonstrated path are within the protocol's representable cap domain. For 18 decimals, `max_cap_for_decimals` allows approximately 170 billion whole tokens, while one billion whole tokens is sufficient to create the vulnerable scaled balance. [11](#0-10) 

A single unprivileged address can own multiple account IDs: one account supplies the liquidity asset, another supplies collateral and borrows the liquidity asset. Once market utilization is high, the caller only needs to wait for index growth and then call `update_indexes`; the overflow is an intrinsic arithmetic boundary rather than a race or privileged configuration bypass.

### Recommendation

Constrain index growth by the market's scaled balances, not only by `MAX_BORROW_INDEX_RAY`. Before accepting or accruing an index, enforce bounds such as:

```rust
borrow_index <= i128::MAX / borrowed.raw()
supply_index <= i128::MAX / supplied.raw()
```

with appropriate margin for fee share minting and subsequent additions. Alternatively, represent aggregate debt and supply values in `I256` and redesign all downstream transfer and repayment amounts so they never require unrepresentable `i128` token amounts.

Add a regression test asserting that `update_indexes`, `repay`, `withdraw`, and `liquidate` cannot hit `MathOverflow` for every stored scaled balance and index admitted by market caps.

### Proof of Concept

One attacker can use two owned account IDs:

```text
let big18 = HubAssetKey { hub_id: spoke_hub, asset: BIG18_TOKEN };
let col   = HubAssetKey { hub_id: spoke_hub, asset: COL_TOKEN };

// Account A creates liquidity.
let supplier_id = controller.supply(
    attacker,
    0,
    spoke_id,
    vec![(big18, 1_000_000_000 * 10^18)],
);

// Account B supplies collateral and borrows 98% of BIG18 liquidity.
let borrower_id = controller.supply(
    attacker,
    0,
    spoke_id,
    vec![(col, sufficient_collateral)],
);

controller.borrow(
    attacker,
    borrower_id,
    vec![(big18, 980_000_000 * 10^18)],
    Some(attacker),
);

// After sustained high utilization has grown the index:
controller.update_indexes(attacker, vec![big18]);
```

The resulting `scaled * index / RAY` result exceeds `i128::MAX` while `borrow_index < MAX_BORROW_INDEX_RAY`, so the call fails with `MathOverflow`; subsequent `withdraw`, `repay`, and liquidation attempts fail on the same pre-operation accrual.

```rust
/// Returns the largest cap, in asset base units, whose ray-scaled form still
/// fits in `i128`.
///
/// Returns 0 when `asset_decimals > RAY_DECIMALS`, since the ray form is not
/// representable in that case. Enforced by
/// [`require_cap_within_asset_domain`], so stored caps can never overflow the
/// asset→ray rescale.
pub fn max_cap_for_decimals(asset_decimals: u32) -> i128 {
    let Some(exp) = RAY_DECIMALS.checked_sub(asset_decimals) else {
        return 0;
    };
    let upscale = 10i128
        .checked_pow(exp)
        .expect("10^(RAY_DECIMALS - asset_decimals) fits i128 for asset_decimals <= RAY_DECIMALS");
    i128::MAX / upscale
}

/// Panics with `CollateralError::AssetDecimalsTooHigh` if `asset_decimals`
/// exceeds `RAY_DECIMALS`, or with `CollateralError::InvalidBorrowParams` if
/// `cap` exceeds the value returned by `max_cap_for_decimals`.
pub fn require_cap_within_asset_domain(env: &Env, cap: i128, asset_decimals: u32) {
    if RAY_DECIMALS.checked_sub(asset_decimals).is_none() {
        panic_with_error!(env, CollateralError::AssetDecimalsTooHigh);
    }
    assert_with_error!(
        env,
        cap <= max_cap_for_decimals(asset_decimals),
        CollateralError::InvalidBorrowParams
    );
```
