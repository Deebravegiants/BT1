## Title
Debug-level HTTP request logging exposes plaintext passwords in GraphQL mutations (`updateUserPassword`, `createAPIToken`, `deleteAPIToken`) - ([File: core/web/router.go])

## Summary
The Gin logging middleware `loggerFunc`, registered globally for all routes including `POST /query`, logs the full request body at `Debug` level via `readBody`/`readSanitizedJSON`. `readSanitizedJSON` only redacts top-level keys in the JSON body and does not recurse into nested objects, so GraphQL requests — which always nest mutation arguments inside a `variables` object — bypass the password blacklist entirely, causing plaintext passwords to be written to logs whenever `Log.Level = 'debug'`.

## Finding Description
`loggerFunc` is registered globally in `NewRouter` via `engine.Use(...)`, applying to every route, including the authenticated GraphQL endpoint `POST /query`. [1](#0-0) [2](#0-1) 

It reads the full request body and logs it at `Debug` level through `readBody`: [3](#0-2) 

`readBody` calls `readSanitizedJSON`, which unmarshals the body into a flat `map[string]any` and redacts only top-level keys matching the `blacklist` (`password`, `newpassword`, `oldpassword`, etc., plus any key containing "password"): [4](#0-3) [5](#0-4) 

GraphQL requests are shaped as `{"query": ..., "variables": {...}}`, and mutation input fields (`oldPassword`, `newPassword`, or the API-token `password`) are always nested inside `variables`, never at the top level. Because `readSanitizedJSON` never recurses, these fields are never inspected or redacted, and the raw values pass straight into the log line's `"body"` field. This is confirmed directly by the code, which only iterates over the top-level map (`for k, v := range dst`) with no recursive handling of nested maps.

## Impact Explanation
When `Log.Level = 'debug'` is set — a standard, documented, non-privileged configuration option (default is `'info'`, but `'debug'` is explicitly supported and commonly used for troubleshooting) — any authenticated user's own password (submitted via `updateUserPassword`, `createAPIToken`, or `deleteAPIToken` GraphQL mutations) is written in plaintext to the node's logs. This maps to the in-scope impact category of secret/credential exfiltration: anyone with read access to the logs (e.g., another operator, log aggregation systems, or local filesystem access) can recover the password and use it for account takeover of the node's admin UI/API. The severity is meaningfully mitigated by the fact that log access itself requires some level of host or infrastructure access, but the vulnerability is a genuine code defect distinct from that access requirement — the redaction mechanism explicitly exists to prevent exactly this outcome and fails silently for the GraphQL surface while working correctly for legacy REST endpoints.

## Likelihood Explanation
Triggering the bug requires no special privilege beyond being an authenticated node user performing a normal, expected action (changing their own password or creating/deleting their own API token) — this is not admin-only or requiring any escalation. The only precondition is that the node operator has set `Log.Level = 'debug'`, which is a supported and non-exotic configuration (used for troubleshooting, and even shown as the example value in `docs/CONFIG.md` and `core/config/docs/example-config.toml`). Given the existence of the blacklist redaction mechanism specifically designed to prevent password logging, this is a genuine regression/gap rather than an intentional design choice, and is easily and repeatably reproducible.

## Recommendation
Modify `readSanitizedJSON` (and `redact`) in `core/web/router.go` to recursively walk nested JSON objects and arrays, redacting blacklisted keys at any depth, not just top-level keys. Alternatively, special-case the `/query` GraphQL route to sanitize the parsed `variables` tree recursively (or block logging bodies for `/query` entirely) before passing it to `loggerFunc`.

## Proof of Concept
1. Configure a node with `Log.Level = 'debug'` in `config.toml` (a supported configuration option per `core/config/docs/core.toml`).
2. As an authenticated user, send:
```
POST /query
{"query":"mutation($input: UpdatePasswordInput!){ updateUserPassword(input:$input){ ... } }",
 "variables":{"input":{"oldPassword":"CurrentSecretPass123!","newPassword":"NewSecretPass456!"}}}
```
3. Inspect the node's logs — the `Debugw` entry for `POST /query` contains a `"body"` field with the full JSON, including `oldPassword` and `newPassword` in plaintext, since `readSanitizedJSON` only inspects the top-level keys `query`/`variables`/`operationName`.
4. As a Go unit test: call `readSanitizedJSON` directly with a nested JSON body containing a `variables.input.oldPassword` field and assert the returned string still contains the plaintext password (proving no redaction occurs), contrasted with a flat body where `password` at the top level is correctly redacted.

func readSanitizedJSON(buf *bytes.Buffer) (string, error) {
	var dst map[string]any
	err := json.Unmarshal(buf.Bytes(), &dst)
	if err != nil {
		return "", err
	}

	cleaned := map[string]any{}
	for k, v := range dst {
		if isBlacklisted(k) {
			cleaned[k] = "*REDACTED*"
			continue
		}
		cleaned[k] = v
	}

	b, err := json.Marshal(cleaned)
	if err != nil {
		return "", err
	}
	return string(b), err
}
