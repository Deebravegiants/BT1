### Title
Webhook `shop`, `topic`, and `webhook_id` fields are trusted despite not being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values are read directly from unauthenticated HTTP headers and passed on to the app's webhook handler as trusted, verified data. Since Shopify's own delivery mechanism binds these header values to the body, this gem's design assumes both come from Shopify — but nothing in the code actually ties the `shop-domain` header to the signed body, so a caller who can obtain any one validly-signed webhook body/HMAC pair can replay it with an arbitrary `shop-domain` header and have it accepted as authentic.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, and `webhook_id` are pulled straight from headers, entirely outside of what is HMAC-verified: [2](#0-1) 

`Registry.process` validates the HMAC (which only proves the *body bytes* were signed with the app's secret) and then immediately trusts `request.shop` and `request.topic`, handing them to the app's handler as `WebhookMetadata`: [3](#0-2) 

This is the same identity-binding failure pattern as the MIMO report: a value that is *used* by privileged/tenant-scoped logic (here, `shop`) is not covered by the check that is supposed to establish trust (the HMAC over `to_signable_string`). The equality that should hold is:

`shop header used by handler == shop the HMAC-signed body was actually generated for`

but the code never enforces this — it only enforces `hmac(raw_body) == provided_hmac`, independent of any header value.

The gem's own documentation instructs apps to trust `data.shop` as "the shop domain of the webhook" and describes `Registry.process` as verifying "the request did indeed come from Shopify" — i.e., apps are expected, per the documented API, to key per-tenant logic (job routing, credential lookups, data writes) off `data.shop` without additional out-of-band verification: [4](#0-3) [5](#0-4) 

### Impact Explanation
Any actor who can obtain one legitimately-signed webhook delivery for a shop they control (e.g., by installing the app on their own free/trial store — an action available to any unprivileged internet user) can capture the exact `raw_body` + valid `x-shopify-hmac-sha256` value from that delivery. Because the `shop-domain` header is not part of the signed content, the attacker can resend the identical body/HMAC pair to the app's webhook endpoint with the `shop-domain` header changed to a victim shop. `HmacValidator.validate` will still pass (the body and its HMAC are unmodified), and the app's handler will process this as authentic data attributed to the victim shop — a cross-tenant data confusion/injection primitive, since the app never independently confirms that the signed body actually originated from the shop named in the header.

### Likelihood Explanation
Exploitation requires no privileged credentials, no access token, and no `client_secret` — only the ability to install the target app on any Shopify store (a normal, unprivileged action), capture one real webhook delivery, and replay it against the app's public webhook URL with a modified header. This is fully reachable through the gem's documented, intended usage pattern (`Registry.process` + `WebhookHandler#handle`), not a misuse of undocumented internals.

### Recommendation
Bind the tenant-identifying and dispatch-relevant fields into the HMAC-verified content, or otherwise cryptographically tie them to the body/signature. At minimum, `Request#to_signable_string` (or a new verification step in `Registry.process`) should incorporate `shop`, `topic`, and `webhook_id` so that tampering with these headers invalidates the HMAC, matching the security guarantee the documentation implies ("will verify the request did indeed come from Shopify").

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, satisfying legitimate OAuth/webhook subscription.
2. Shopify sends a legitimate webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`, a JSON body, and `x-shopify-hmac-sha256: <valid signature over raw_body>`.
3. Attacker captures the exact `raw_body` and `x-shopify-hmac-sha256` value.
4. Attacker POSTs the identical `raw_body` to the same endpoint but sets `x-shopify-shop-domain: victim.myshopify.com` (and optionally a topic of interest), keeping the same `x-shopify-hmac-sha256`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `hmac(raw_body)`, still passes.
6. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and processes the attacker-controlled body as if it were genuine data from the victim's shop. [6](#0-5) [3](#0-2)

# typed: strict

module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end

      sig { returns(String) }
      def topic
        T.cast(shopify_header("topic"), String)
      end

      sig { returns(String) }
      def shop
        T.cast(shopify_header("shop-domain"), String)
      end

      sig { returns(String) }
      def api_version
        T.cast(shopify_header("api-version"), String)
      end

      sig { returns(String) }
      def webhook_id
        T.cast(shopify_header("webhook-id"), String)
      end

      sig { override.returns(String) }
      def to_signable_string
        @raw_body
      end

      sig { returns(T::Hash[String, T.untyped]) }
      def parsed_body
        JSON.parse(@raw_body)
      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
