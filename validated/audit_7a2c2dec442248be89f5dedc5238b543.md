### Title
Emporium's per-transaction `erc20TokenAddresses` scoping lets a CASE 2 op drain any unlisted token balance held by the shared Emporium contract - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction` only snapshots and re-checks balances for the tokens listed in the *current* caller's `circomData.erc20TokenAddresses`, while the ops array executed in between (`stack.ops`, including CASE 2 stateless calls) is fully attacker-controlled and can target *any* endpoint, including an unrelated ERC20 that happens to sit in Emporium's own balance. Because `EmporiumUpgradeable` is a persistent, shared singleton contract (registered once in `externalActionMap` and reused by every user), any token balance it holds outside the caller's chosen token list is invisible to the balance-conservation check and can be siphoned to the attacker with zero UTXO/nullifier footprint.

### Finding Description
The broken equality: **every token balance that leaves the Emporium contract must be represented in `amountChanges`/a minted UTXO for that token** (enforced by the `balancesBefore`/`balancesAfter` loop over `circomData.erc20TokenAddresses` in `runAction`, [1](#0-0) ). That loop, and the corresponding `BalanceChangeShouldBePositive()` guard, is indexed strictly by `circomData.erc20TokenAddresses` [2](#0-1) , so a token that the caller simply omits from that array is never sampled before or after the ops loop.

The ops loop itself lets the caller specify arbitrary `endpoint`/`callData` for CASE 2 ("Stateless Interaction") entries, restricted only to not being `callHinkalWallet`/`doSendToRelay` selectors [3](#0-2) . Since this call is `op.endpoint.call(...)` made *by the Emporium contract itself*, an attacker can set `op.endpoint = tokenB` and `op.callData = abi.encodeWithSelector(IERC20.transfer.selector, attacker, tokenBBalance)` — a plain ERC20 `transfer` only requires `msg.sender` (Emporium) to be the balance holder, no approval needed.

Nothing in `performHinkalChecks`, `dimensionsCheck`, or `checkOnchainCreation` in `HinkalHelper.sol` constrains which tokens ops may touch relative to `erc20TokenAddresses` [4](#0-3) ; they only check array-length/dimension consistency for the tokens the attacker *chose* to declare. Additionally, `verifyWallet` performs no EIP-712 signature check at all when `stack.signerAddress == address(0)` [5](#0-4) , so an attacker submitting their own proof/deposit fully controls the ops array with no counter-signature required.

Attacker's exact call: submit `Hinkal.transact` with a self-generated proof depositing a trivial amount of `tokenA` (listed in `erc20TokenAddresses = [tokenA]`), `externalActionData.externalActionId` = Emporium, and `externalActionMetadata` encoding an `EmporiumStack` with `signerAddress = address(0)` and one CASE 2 op whose `endpoint = tokenB` and `callData = transfer(attacker, Emporium's tokenB balance)`. `_externalTransact` in `Hinkal.sol` pushes the attacker's own `tokenA` deposit into Emporium before `runAction` executes [6](#0-5) ; the ops loop then drains `tokenB`; `balancesBefore`/`balancesAfter` for `[tokenA]` show exactly the expected deposit, so `handleOut` mints a clean UTXO for `tokenA` while `tokenB` leaves with no amountChange, no nullifier, no UTXO [7](#0-6) .

Existing guards fail because: `verifyProof`/circuit constraints only bind the fields the attacker themselves chose to include for their own tokens; `rootHashExists`/`insertNullifiers` only govern the attacker's own spent leaves; `performHinkalChecks` never inspects op contents; the Emporium balance loop is structurally scoped to the caller-supplied token array, not to "all tokens the ops touched."

### Impact Explanation
Any ERC20 balance sitting in the shared `EmporiumUpgradeable` contract that is not part of the current caller's declared token list can be permanently stolen by any unprivileged attacker, with no on-chain trace tying the loss to a nullifier or amountChange. This is direct theft of funds held by the protocol's Emporium contract (whether from a prior user's leftover balance, an unswept router refund, or any other source), matching the Critical category (direct theft of in-flight/shielded funds with proof/accounting bypass).

### Likelihood Explanation
Preconditions: `EmporiumUpgradeable` must hold a nonzero balance of some token not declared by the attacker's transaction. This is plausible in practice since ops can call arbitrary external endpoints (routers, aggregators) that may leave dust, partial refunds, or unexpected-token payouts in Emporium's balance from any prior transaction. Attacker cost is a single trivial-value `transact` call funding only `tokenA`; no signature from any other party is needed because `signerAddress` can be zero. The attack is repeatable every time Emporium accumulates an unlisted-token balance.

### Recommendation
Track and validate Emporium's balance for every token that ops in the stack could plausibly touch, not just `circomData.erc20TokenAddresses`. Concretely: restrict CASE 2 `op.endpoint` calls to a pre-approved allow-list of endpoints per token, or require that any token whose balance changes during the ops loop be explicitly declared and accounted for in `erc20TokenAddresses`/`amountChanges` (e.g., snapshot balances of a superset of known/registered tokens, or disallow direct `token.transfer`-shaped calldata to arbitrary token contracts from CASE 2).

### Proof of Concept
Foundry test outline:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`, register Emporium as external action.
2. Simulate Emporium holding an untracked `tokenB` balance (e.g., direct `tokenB.transfer` to the Emporium contract address, representing leftover/refund funds).
3. As attacker, generate a valid proof for a trivial `tokenA` deposit with `erc20TokenAddresses = [tokenA]` only, and craft `EmporiumStack` with `signerAddress = address(0)` and one CASE 2 op: `endpoint = tokenB`, `callData = abi.encodeWithSelector(IERC20.transfer.selector, attacker, tokenBBalance)`.
4. Call `Hinkal.transact(...)`.
5. Assert: (a) `tokenA` balance/UTXO accounting passes (`balanceChange == amountChanges`/`utxoAmount` for tokenA); (b) `tokenB.balanceOf(attacker)` increased by `tokenBBalance` while `tokenB.balanceOf(Emporium)` dropped to 0; (c) no nullifier was inserted and no UTXO/commitment was emitted for `tokenB`, proving the value transfer has zero footprint in `CircomData`/public inputs.

    function handleOut(
        int256 balanceChange,
        CircomData calldata circomData,
        uint256 i
    ) internal returns (UTXO memory outUtxo) {
        // total change can be less than zero if there was some balance before the call -> that's why we have <=
        if (balanceChange <= 0) {
            return outUtxo;
        }

        transferERC20TokenOrETH(
            circomData.erc20TokenAddresses[i],
            msg.sender,
            uint256(balanceChange)
        );

        outUtxo = UTXO(
            uint256(balanceChange),
            circomData.erc20TokenAddresses[i],
            circomData.stealthAddressStructure,
            circomData.timeStamp
        );
    }
