### Title
Order deadline checks use raw `block.number` instead of chain-aware block height, breaking expiry semantics on Arbitrum - ([File: evm/src/apps/IntentGatewayV2.sol], [File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.sol` (the production intent-gateway contract, and its Tron fork) compares `order.deadline` against the raw `block.number` opcode to decide whether an order has expired for cancellation/fill authorization. On Arbitrum, `block.number` does not return the L2 block height — it returns the (approximate) L1 block number the sequencer received the transaction at, which advances far slower than, and is numerically unrelated to, the L2 height that `order.deadline` is denominated in. This is the same bug class as the reported finding (wrong block reference used for time-bound verification on L2 chains).

### Finding Description
The codebase itself acknowledges this exact problem. In the newer `IntentsBase.sol` (used by `intentsv2`), a dedicated helper is used specifically to avoid this bug: [1](#0-0) 

This function explicitly documents that "for Arbitrum chains that is the L2 block number, but the `block.number` opcode there returns the approximate L1 block number, so the ArbSys precompile is queried instead," and is used correctly for deadline comparisons in that module: [2](#0-1) 

However, the production `IntentGatewayV2.sol` (non-v2/v3 legacy path) and its Tron fork never adopted this fix, and instead compare deadlines against the raw `block.number` opcode: [3](#0-2) 

Foundry tests confirm this divergence is a known, exploitable discrepancy on Arbitrum — the test explicitly simulates the case where the ArbSys-reported L2 height has passed the deadline while `block.number` (L1-synced) has not: [4](#0-3) 

Since `IntentGatewayV2.sol` (unlike `IntentsBase.sol`) uses the raw opcode rather than `_blockNumber()`, any order deadline set with the intent of it being an L2 block height (the documented and tested semantics per `IntentsBase.sol`) is instead checked against a number that grows at the L1 rate. This directly parallels the external report's root cause: consensus/verification logic in the reported `Ledger.sol` used `block.number` for time-based sequencing on an L2 chain, producing an inaccurate/misleading result compared to `block.timestamp`-anchored (or, here, ArbSys-anchored) expectations.

### Impact Explanation
On Arbitrum deployments of the legacy `IntentGatewayV2.sol`, `order.deadline` comparisons (`order.deadline <= block.number` / `order.deadline >= block.number`) are checked against the wrong quantity:
- Orders can fail to expire when their L2-height deadline is reached, since L1-synced `block.number` lags far behind, permanently blocking the user's expected right to unilaterally cancel and reclaim escrowed funds after the deadline (freezing of funds for the deadline window duration, which can be indefinite in practice given the L1/L2 block-number gap).
- Conversely, orders can be treated as "not yet expired" by a check meant to gate an owner-only cancel path, or as "expired" prematurely, depending on how far L1 and L2 heights have diverged, enabling unauthorized cancel/fill actions inconsistent with the user's and filler's intended deadline.

Because escrowed input tokens are held by the gateway pending order fulfillment/cancellation, incorrect deadline evaluation directly risks fund freezing or unauthorized order state transitions — matching the Medium-severity impact criteria (permanent freezing of funds / unauthorized action).

### Likelihood Explanation
This is triggered by ordinary, unprivileged use of the intent-gateway on an Arbitrum deployment: any user placing an order with a deadline denominated in L2 block heights, or any filler/relayer invoking `cancelOrder`/`fillOrder` after the intended deadline, hits this code path. No special privileges or governance are required — it is reachable purely through the normal order lifecycle (`placeOrder`, `cancelOrder`, `fillOrder`) on any Arbitrum-family chain where the legacy `IntentGatewayV2.sol` (or its Tron fork, if deployed to an Arbitrum-like L2 with similar sequencer semantics) is used.

### Recommendation
Replace the raw `block.number` checks in `evm/src/apps/IntentGatewayV2.sol` and `evm/tron/contracts/apps/IntentGatewayV2.sol` with the same `_blockNumber()` (ArbSys-aware) helper already implemented and tested in `evm/src/apps/intentsv2/IntentsBase.sol`, so that deadline semantics are consistent across the legacy and v2/v3 intent-gateway implementations.

### Proof of Concept
1. Deploy the legacy `IntentGatewayV2.sol` on Arbitrum One.
2. `placeOrder` with `order.deadline` set to a target L2 block height (as documented/expected per `modules/pallets/intents-coprocessor/src/types.rs` comment: "`deadline` is the EVM block number beyond which the gateway treats the order as expired").
3. Wait until the real Arbitrum L2 height (`ArbSys.arbBlockNumber()`) passes `order.deadline`, while the L1-synced `block.number` opcode remains well below it (as demonstrated by the existing test `testFillOrderNotExpiredOnArbitrumUsesArbSys`/expiry test pattern in `evm/tests/foundry/IntentGatewayV2Test.sol` lines 1759-1781, but applied to the legacy contract instead of `IntentsBase`-derived ones).
4. Call `cancelOrder` from the destination chain: since `IntentGatewayV2.sol` checks `order.deadline >= block.number` using the raw opcode, the "not yet expired, owner-only" branch is incorrectly taken (or vice versa), diverging from the actual L2 elapsed time — allowing an unintended actor to cancel, or blocking the rightful owner from a timely cancel/refund.

```text
    /**
     * @dev Returns the current block number of the host chain. Order deadlines are
     * denominated in the block heights Hyperbridge tracks for each state machine —
     * for Arbitrum chains that is the L2 block number, but the `block.number` opcode
     * there returns the approximate L1 block number, so the ArbSys precompile is
     * queried instead. The chain id check keeps the bytecode identical across all
     * chains, preserving the deterministic CREATE2 deployment addresses.
     * @return The chain-appropriate current block number.
     */
    function _blockNumber() internal view returns (uint256) {
        if (block.chainid == ARBITRUM_ONE || block.chainid == ARBITRUM_NOVA || block.chainid == ARBITRUM_SEPOLIA) {
            return IArbSys(ARB_SYS).arbBlockNumber();
        }
        return block.number;
    }
```
