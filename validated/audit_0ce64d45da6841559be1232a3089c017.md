### Title
Unbounded reliance on manipulable Uniswap V4 spot price for solver fill-sizing, with overfill clamp explicitly disabled - ([File: sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts])

### Summary
`UniswapV4FundingPlanner.getExoticTokenPrice` / `computeDirectPoolPriceUsd` prices an "exotic" IntentGateway asset directly off a Uniswap V4 pool's current `sqrtPriceX96` (`sdkPool.token0Price`/`token1Price`), with no TWAP and no size/impact term. [1](#0-0)  This spot price feeds `FXFiller.resolveLegRates`/`referenceRate` in the Simplex solver, which sizes how much output a solver commits to an IntentGateway order, and the only defense is an optional, static `checkPriceGuard` (`referencePrice`/`maxDeviationBps`) that operators may leave unconfigured. [2](#0-1)  Worse, the code comment and logic in `fx.ts` explicitly document that the per-leg overfill clamp against this venue price has been **disabled**: it now only warns instead of rejecting/capping an output amount that exceeds `(1 + maxOverfillBps) × user-requested`, an amount that was specifically meant to protect "against a bug / stale cache / manipulated venue price." [3](#0-2) 

### Finding Description
This is a direct analog of the Lodestar Finance exploit: Lodestar's lending market trusted a manipulable, single-source price for `plvGLP` to determine how much collateral could be "borrowed" against, and an attacker inflated that price in-transaction to drain the pool. Here, the Simplex intent-solver's pricing of a curveless ("venue-priced") pair is likewise a raw, un-TWAP'd Uniswap V4 pool mid computed as `sdkPool.token0Price`/`token1Price` off live `sqrtPriceX96`. [4](#0-3)  A user (order placer, an unprivileged actor) can move that pool's price with a swap in the same block/transaction before or alongside placing an IntentGateway order, causing the solver's `resolveLegRates`/`computeLegPolicyOutput` path to compute an inflated `policyMaxOutput` for the exotic token leg. [5](#0-4) 

Normally an "overfill ceiling" (`(output.amount * (10000n + maxOverfillBps)) / 10000n`) would have capped how far a manipulated price could push the solver's payout beyond what the user actually requested. The code now deliberately disables this clamp and only logs a warning ("Overfill ceiling exceeded — clamp disabled, filling unclamped amount"), meaning the solver fills the entire, unclamped, manipulated-price-derived amount. [3](#0-2)  The only remaining safeguard is `checkPriceGuard`, which is explicitly optional per-position config (`referencePrice`/`maxDeviationBps` "go together — one without the other is rejected" but omitting both entirely "leaves the chain unguarded"). [6](#0-5) 

Because the fill goes through `IntrinsicIntents`/IntentGateway's `fillOrder`, and the escrowed input is released to the solver strictly pro-rata to the output actually provided, an attacker who manipulates the pool price to make the solver believe the exotic asset is worth much less than it is can cause the solver to hand out far more of the exotic asset than the user's escrowed input is worth — draining the solver's Uniswap V4 LP-backed inventory for an underpriced input, or conversely inflate valuation to extract atomic same-token cross-chain margin. This is the classic price-oracle manipulation → over-extension of funds pattern from Lodestar, transplanted onto the reachable intent-fill path (`fillOrder` dispatched by any unprivileged order placer/solver interaction).

### Impact Explanation
An attacker manipulating the venue-priced pool (e.g., a low-liquidity Uniswap V4 position backing a pair, especially likely for "exotic" non-major assets per the docs' own examples like CNGN/ZARP) can force the FXFiller solver to overfill an order without the previously-existing ceiling protecting it, directly costing the solver its own inventory (Uniswap V4 LP position tokens) beyond what any objectively fair price would justify. This is a concrete theft/loss-of-funds vector against solver capital reachable from a single submitted order plus an on-chain swap, satisfying High severity per the reachable-path and impact requirements.

### Likelihood Explanation
Likelihood is High when: (1) the pair has no static curves and instead is entirely venue-priced from Uniswap V4 (a documented, supported configuration), and (2) the operator has not configured `referencePrice`/`maxDeviationBps` for that position — which the docs describe as an explicit opt-in, implying deployments without it exist and are "unguarded" by design. [6](#0-5)  Even with the guard configured, an attacker can move price within the allowed `maxDeviationBps` band and still exploit the disabled overfill clamp, since the clamp check operates independently of, and after, the price guard. The commit history/comment itself documents this as a known, intentional regression ("clamp is DISABLED... this removes the per-leg loss bound that previously protected against... manipulated venue price"), indicating the vulnerable condition is currently live in the codebase rather than hypothetical. [3](#0-2) 

### Recommendation
- Re-enable the overfill clamp as a hard cap (not warn-only) so `policyMaxOutput` is bounded to `(1 + maxOverfillBps) × output.amount` regardless of venue price source.
- Make `checkPriceGuard` (`referencePrice`/`maxDeviationBps`) mandatory for any venue-priced (curveless) pair rather than optional, or require a TWAP/multi-block price rather than raw `sqrtPriceX96` spot pricing in `computeDirectPoolPriceUsd`.
- Consider sourcing venue price from a manipulation-resistant reference (e.g., time-weighted average tick, or cross-checking against a second independent venue/oracle) before sizing fills.

### Proof of Concept
Conceptual (no test harness available in this pass to execute live, and the exact numeric magnitude of the swap needed depends on the target pool's live liquidity depth, which cannot be verified without direct on-chain access; further validation via a Devin session running `sdk/packages/simplex/src/tests/strategies/fx.price-guard.test.ts`-style fixtures with `maxDeviationBps` unset or wide, and the overfill clamp behavior asserted, would concretely reproduce the loss):
1. Attacker (or colluding party) identifies a Uniswap V4 pool backing a Simplex "exotic" pair with no `referencePrice`/`maxDeviationBps` guard configured for that chain, per `docs/content/developers/evm/simplex/pricing.mdx`.
2. Attacker swaps against that pool to move `sqrtPriceX96` so the exotic token appears artificially cheap in USD terms.
3. Attacker places an IntentGateway order for USDC → exotic token sized so that, at the manipulated price, `resolveLegRates` computes a large `policyMaxOutput` exceeding `(1+maxOverfillBps) × output.amount`.
4. `FXFiller.calculateProfitability` logs "Overfill ceiling exceeded — clamp disabled, filling unclamped amount" but proceeds to fill the full, unclamped amount from the solver's V4 LP position (`sdk/packages/simplex/src/strategies/fx.ts:678-701`).
5. Solver's `fillOrder` dispatches the escrow release for the user's (attacker-controlled) input, while the solver has paid out an inflated amount of the exotic token relative to fair value, realizing the loss for the solver's inventory analogous to Lodestar's price-inflated over-borrow.

	async getExoticTokenPrice(chain: string, exoticToken: string): Promise<Decimal | null> {
		const state = this.stateByChain.get(chain)
		if (!state || !state.isHydrated()) return null

		try {
			await state.refresh()
		} catch (err) {
			this.logger.error({ err, chain }, "Failed to refresh state for price query")
			return null
		}

		const tokenLower = exoticToken.toLowerCase()
		let bestPrice: Decimal | null = null
		let bestLiquidity = 0n

		for (const pos of state.allPositions()) {
			if (pos.currency0.toLowerCase() !== tokenLower && pos.currency1.toLowerCase() !== tokenLower) continue
			const sdkPool = state.getSdkPool(pos.tokenId)
			if (!sdkPool) continue

			const result = this.computeDirectPoolPriceUsd(pos, sdkPool, chain)
			if (result && result.exoticToken.toLowerCase() === tokenLower) {
				const poolLiquidity = state.getPoolLiquidity(pos.tokenId)
				if (poolLiquidity > bestLiquidity) {
					bestPrice = result.priceUsd
					bestLiquidity = poolLiquidity
				}
			}
		}

		if (bestPrice) {
			this.logger.debug({ chain, token: tokenLower, priceUsd: bestPrice.toString() }, "Exotic token price computed")
		}
		return bestPrice
	}

	private async resolveLegRates(
		orderId: string | undefined,
		leg: ResolvedLeg,
		cappedPairNotional: Decimal,
		venueUsdPrice: (chain: string, token1Address: string) => Promise<Decimal | null>,
	): Promise<LegRates | null> {
		// Explicitly configured curves always win — the venue only prices pairs
		// with no curves at all (and never same-token pairs, where a venue quote
		// would just be the asset's own USD price, not a spread).
		const curveless = !leg.pair.bidPricePolicy && !leg.pair.askPricePolicy
		if (curveless && !isSameTokenPair(leg.pair) && USD_STABLE_SYMBOLS.has(normalizeSymbol(leg.pair.token0))) {
			const venueUsd = await venueUsdPrice(leg.token1Chain, leg.token1Address)
			if (venueUsd) {
				// Guard compares the venue's token1-per-USD quote against the static reference.
				if (!this.checkPriceGuard(orderId, leg.token1Chain, new Decimal(1).div(venueUsd))) {
					return null
				}
				// A pool mid is ONE price, not a book: there is no opposite side
				// to report a round-trip margin against. The price guard above is
				// the venue-specific defense.
				const venueRate = new Decimal(1).div(venueUsd)
				return { rate: venueRate, oppositeRate: null, priceSource: "venue" }
			}
		}

		const askRate = leg.pair.askPricePolicy?.getPrice(cappedPairNotional) ?? null
		const bidRate = leg.pair.bidPricePolicy?.getPrice(cappedPairNotional) ?? null

		const rate = leg.inputIsToken0 ? askRate : bidRate
		if (!rate) {
			this.logger.debug(
				{ orderId, pair: `${leg.pair.token0}/${leg.pair.token1}`, inputIsToken0: leg.inputIsToken0 },
				"Rejecting leg: direction disabled for one-sided LP",
			)
			return null
		}
		return { rate, oppositeRate: leg.inputIsToken0 ? bidRate : askRate, priceSource: "policy" }

## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.

```toml lineNumbers
[vault.uniswapV4]
# referencePrice is the expected cNGN per USD;
# reject if the quote is more than 2% off.
# The two go together — one without the other is rejected.
[[vault.uniswapV4.positions]]
chain           = "EVM-8453"
tokenId         = "2087350"
referencePrice  = "1575"
maxDeviationBps = 200
```
