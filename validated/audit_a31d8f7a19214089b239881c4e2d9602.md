### Title
Reserve manipulation via swap can drive normalized pc/coin reserves to zero, causing a division-by-zero panic in `calc_take_pnl` that permanently freezes deposits/withdrawals/swaps - ([File: program/src/processor.rs])

### Summary
Analogous to the Hyperdrive `addLiquidity` griefing bug, an attacker can drive one side of the AMM's reserves down to a very small raw amount via a normal swap. Because the reserve is subsequently re-normalized to a fixed internal decimal precision (`sys_decimal_value`) before being used as a divisor in the PnL/"take-profit" calculation, small raw reserve values round down to `0`, and the resulting division by zero causes any subsequent instruction touching the pool (`Deposit`, `Withdraw`, `SwapBaseIn/Out`, `WithdrawPnl`) to panic, freezing the pool.

### Finding Description
Every instruction that reads pool reserves (`process_deposit`, `process_withdraw`, `process_swap_base_in`/`_out` and their `_v2` variants, `process_withdrawpnl`) computes the "normalized" reserves via `Calculator::normalize_decimal_v2`: [1](#0-0) 

then passes them into `Calculator::calc_take_pnl`, which divides by the normalized pc-reserve value (`x1`) without any zero-check: [2](#0-1) 

`normalize_decimal_v2` computes `val * sys_decimal_value / 10^native_decimal`, using plain integer division. If the raw reserve `val` is small relative to `10^native_decimal / sys_decimal_value`, the result truncates to `0`. A swap can legally reduce a vault's raw balance down to `total_reserve - 1` (i.e., leave only 1 raw unit) because the only guard is a strict inequality: [3](#0-2) [4](#0-3) 

The same strict-inequality check exists in `process_swap_base_out`/`_v2`: [5](#0-4) 

Once a vault's raw balance is small enough that `normalize_decimal_v2` truncates it to `0`, the *next* transaction that calls `calc_take_pnl` (deposit, swap, or `WithdrawPnl`) will divide by that `0` value (`x2.checked_mul(y1).unwrap().checked_div(x1).unwrap()` — `.unwrap()` on a division-by-zero panics the Solana program), aborting the transaction. Critically, this check runs at the *start* of every instruction using pre-transfer reserves, so the attacker's own drain transaction succeeds, but it leaves the on-chain vault balance in the "poisoned" state for all subsequent transactions.

`process_withdraw` is the only instruction with a conditional bypass (`if amm.status != AmmStatus::WithdrawOnly.into_u64()`), but that status can only be set by the pool admin via `SetParams`, not by an ordinary LP: [6](#0-5) 

Because `Deposit` always calls `calc_take_pnl` unconditionally, and any deposit would need to first read reserves (still poisoned) before injecting funds, LPs cannot "fix" the pool by adding liquidity either.

### Impact Explanation
Once the reserve of one token is small enough for `normalize_decimal_v2` to round to `0`, the AMM pool becomes permanently unusable for ordinary users: `Deposit`, `Withdraw` (unless in admin-only `WithdrawOnly` status), `SwapBaseIn`, `SwapBaseOut` (and their `_v2` variants) all panic. This freezes all LP funds locked in the pool's vaults, since no path other than an admin-triggered status change can bypass `calc_take_pnl`. This matches the "permanent freezing of user or LP funds" impact class from the validation criteria.

### Likelihood Explanation
The precision loss is determined by `pc_decimals`/`coin_decimals` versus `sys_decimal_value` (a configurable, typically `10^6`-scale value set at pool creation). For any token with more decimals than `log10(sys_decimal_value)` (e.g., 9-decimal SPL tokens against a `10^6` `sys_decimal_value`), a swap that drives the raw vault balance below roughly `10^(native_decimal - 6)` units suffices to zero out the normalized value. This is a large but bounded amount relative to typical pool sizes and requires paying the AMM swap fee on nearly the entire opposite-side reserve, similar to the "high cost of attack" caveat DELV raised for the original Hyperdrive report — it is economically expensive but not otherwise restricted by any protocol logic (any unprivileged trader with sufficient capital, or via a flash-loan-funded single transaction, can execute the near-full-drain swap).

### Recommendation
- Guard `calc_take_pnl` (and any other divisor derived from normalized reserves) against zero denominators, returning a graceful error (e.g. `AmmError::CalcPnlError`) instead of panicking via `.unwrap()` on `checked_div`.
- Enforce a minimum raw and/or normalized reserve floor in `process_swap_base_in`/`_out` (and `_v2`) so that a single swap cannot reduce either side's normalized reserve below a safe non-zero threshold.
- Consider allowing `Withdraw` to bypass `calc_take_pnl` automatically (not just via admin-set `WithdrawOnly` status) when the PnL calculation would fail, so LPs always retain an emergency exit even if the pool state is poisoned.

### Proof of Concept
1. Attacker (or any unprivileged trader) observes a pool where `pc_decimals` (or `coin_decimals`) is large relative to `amm.sys_decimal_value` (e.g., 9 vs `10^6`).
2. Attacker submits `SwapBaseIn` (`PC2Coin` direction) with `amount_in` sized so that `swap_amount_out` is `total_pc_without_take_pnl - 1` (or as close to the strict-inequality boundary as fees allow), per the check at: [4](#0-3) 
   This transaction succeeds because `calc_take_pnl` in this same transaction uses the *pre-swap* reserves, which are still non-zero.
3. The AMM's pc vault now holds a tiny raw balance (e.g., `1000` raw units with 9 decimals), which normalizes via `Calculator::normalize_decimal_v2(1000, 9, 1_000_000)` = `1000 * 1_000_000 / 10^9` = `1` — or, with an even smaller residual balance, exactly `0`.
4. Any subsequent user calling `Deposit`, `SwapBaseIn`/`SwapBaseOut`, or `WithdrawPnl` triggers `calc_take_pnl` with `x1 = 0`, causing `checked_div(x1).unwrap()` at `program/src/processor.rs:208` to panic, aborting their transaction.
5. LPs attempting `Withdraw` are also blocked unless the AMM admin has separately placed the pool in `AmmStatus::WithdrawOnly`, which an ordinary user cannot trigger — resulting in a frozen pool. [7](#0-6)
