Found the analog. `extract_signer` in `modules/pallets/ismp/src/host.rs` is the exact structural match for the Mattermost bug: it accepts relayer-attribution data on an **unsigned** extrinsic path without cryptographically verifying it against the actual transaction submitter, exactly like Mattermost trusted a remote's claimed reaction identity without validating it against the actual event.

### Title
Unverified relayer attribution in `extract_signer` allows forging relayer identity on request/response receipts - (File: `modules/pallets/ismp/src/host.rs`)

### Summary
`handle_unsigned` (`modules/pallets/ismp/src/lib.rs:614-644`) processes `RequestMessage`/`ResponseMessage` submitted as **unsigned** extrinsics. Each message carries an attacker-controlled `signer: Vec<u8>` field. `Pallet::store_request_receipt` / `store_response_receipt` (`modules/pallets/ismp/src/host.rs:261-283`) call `extract_signer(signer)` to derive the "relayer" credited in `RequestReceipts`/`ResponseReceipts`. [1](#0-0)  `extract_signer` performs **no signature verification**: if `signer.len() <= 32` it is accepted verbatim as the relayer identity; only if `>32` bytes is it decoded as a `Signature` enum and `sig.signer()` extracted — but `Signature::signer()` (`modules/utils/crypto/src/verification.rs:109-115`) just returns the embedded public key/address field from the (unverified) struct, it does not call `.verify(...)`. So `extract_signer` never calls `Signature::verify`; it only decodes the enum and reads the claimed public key/address out of it.

### Finding Description
The core ISMP `handle_unsigned` message-processing path (`modules/ismp/core/src/handlers/request.rs:112` and `response.rs:102`) is: `let signer = host.store_request_receipt(&wrapped_req, &msg.signer)?;` — this is the value later emitted in `Event::PostRequestHandled { relayer: signer, .. }` [2](#0-1)  and stored on-chain in `RequestReceipts`/`ResponseReceipts` (used by EVM's `dispatchIncoming` analog and by downstream fee accumulation as the "delivering relayer"). Because this call arrives via an **unsigned extrinsic**, there is no origin-check that binds `msg.signer` to whoever actually broadcast the transaction. Any submitter (an unprivileged relayer, i.e. anyone able to construct and validate a `ResponseMessage`/`RequestMessage` with a valid state proof) can set `msg.signer` to an arbitrary ≤32-byte value, or to a syntactically well-formed `Signature { public_key, signature }` struct with a bogus/reused signature bytes field — since `extract_signer` never verifies the signature over the message payload, only `Signature::decode` succeeds and `.signer()` (i.e. the embedded public key) is trusted blindly. The real signature-checking logic exists elsewhere in the codebase (`fee_handler.rs:190-198`, `messaging-incentives/src/lib.rs:148-152` call `verify_and_get_sr25519_pubkey`), proving the protocol *intends* signer identity to be cryptographically bound — but `extract_signer`, the function that actually persists the attributed relayer on the request/response receipt used for downstream reward/attribution logic, skips that check entirely. This mirrors the Mattermost defect precisely: data describing "who performed this action" arriving over an unauthenticated/permissionless channel (synced reactions from a remote / an unsigned ISMP message from any relayer) is persisted and acted upon without validating that the claimed identity is legitimate.

### Impact Explanation
The attributed "relayer" on `RequestReceipts`/`ResponseReceipts` is the value consumed by fee/reward accounting elsewhere in the protocol (e.g. `pallet-ismp-relayer`'s `decode_receipt_relayer` in `modules/pallets/relayer/src/accumulate.rs:317-351`, and the outbound-request-delivery-claim flow which decodes this exact receipt slot to determine payout recipient, `docs/outbound-request-incentivization.md:130-138`). An attacker who submits the deliverable message first (racing legitimate relayers, which is trivial since delivery is permissionless and gas-competitive) can set `msg.signer` to an arbitrary 32-byte value or forged `Signature` struct naming themselves (or anyone) as the delivering relayer without ever proving control of that identity. Downstream reward/fee-accumulation code that trusts this on-chain receipt as ground truth for "who delivered this message" can then be manipulated into crediting relayer rewards/fees to an account that never produced a valid signature — a form of forged message-delivery attribution enabling theft of relayer rewards.

### Likelihood Explanation
High reachability: `handle_unsigned` is explicitly designed to be callable by anyone without fees (`"This allows users execute ISMP datagrams for free. Use with caution."`, `modules/pallets/ismp/src/lib.rs:604`), and `msg.signer` is fully attacker-controlled wire data. No special privilege is needed beyond constructing a valid state proof for the request/response batch itself (which any relayer/user can do). The only friction is racing the legitimate relayer to submit first, which is normal MEV-style competition in this protocol's design.

### Recommendation
In `extract_signer` (`modules/pallets/ismp/src/host.rs:351-359`), require that any `Signature`-encoded `signer` be *verified* via `Signature::verify(&message_digest, None)` against the actual message payload (as `fee_handler.rs` and `messaging-incentives` already do) before extracting and persisting the recovered address/public key as the attributed relayer, rather than trusting the raw, unauthenticated bytes/`.signer()` field. Reject receipts whose signer cannot be cryptographically verified against the submitted message.

### Proof of Concept
1. Attacker observes (or races) a deliverable `RequestMessage`/`ResponseMessage` with a valid membership/state proof for a legitimate cross-chain request.
2. Attacker submits their own `handle_unsigned` extrinsic with the identical proof/requests but sets `msg.signer` to an arbitrary 32-byte value, e.g. their own account bytes, or a `Signature::Sr25519 { public_key: attacker_pubkey, signature: garbage }` (>32 bytes so it goes through the decode branch).
3. `Pallet::execute` → `handlers::handle` → `store_request_receipt`/`store_response_receipt` → `extract_signer` accepts this without verifying `garbage` against any message digest, storing `attacker_pubkey` (or the raw ≤32-byte value) as the relayer in `RequestReceipts`/`ResponseReceipts`.
4. `Event::PostRequestHandled{ relayer: attacker, .. }` is emitted and the on-chain receipt now attributes delivery to the attacker.
5. Downstream, `pallet-ismp-relayer`'s fee/outbound-delivery-claim flow reads this receipt slot as proof of "who delivered" and pays out based on it, crediting the attacker despite never having produced (or being able to produce) a genuine signature.

fn extract_signer(signer: &[u8]) -> Result<Vec<u8>, Error> {
	if signer.len() > 32 {
		Signature::decode(&mut signer.as_ref())
			.map(|sig| sig.signer())
			.map_err(|_| Error::SignatureDecodingFailed)
	} else {
		Ok(signer.to_vec())
	}
}
