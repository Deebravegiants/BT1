### Title
Unsynchronized live config mutation allows fraud/liveness enforcement to change mid-signup, enabling inconsistent enrollment decisions - ([File: src/plans/mod.rs], [File: src/config.rs], [File: src/brokers/observer.rs])

### Summary
The orb periodically downloads a fresh backend `Config` and swaps it into a shared `Arc<Mutex<Config>>` with no versioning, no two-step commit, and no guarantee that a signup transaction observes a single consistent snapshot. Because individual signup stages independently re-acquire the lock and read only the fields they need at that moment, a config change delivered by the backend mid-signup can be observed inconsistently across the stages of the very same signup — the class of bug described in the external report (privileged party changes system parameters that "take effect immediately," with no advance notice or mandatory delay, producing unpredictable behavior for an in-flight user transaction).

### Finding Description
`Observer::config_update` (the `DefaultPlan` implementation) polls on `CONFIG_UPDATE_INTERVAL` and, whenever it fires, spawns a task that downloads a new config and unconditionally replaces the entire shared object: [1](#0-0) 

`Config::download_and_store` performs the same unguarded whole-object replacement: [2](#0-1) 

There is no timelock, no staging/pending-config step, and no check for whether a signup is currently in progress — `before_config_update` simply defaults to `true` and nothing in `MasterPlan` prevents `config_update` from firing during `do_signup`.

Within a single signup, the fields of `Config` are *not* captured once and threaded through consistently. Instead, each stage re-locks `orb.config` and reads a fresh copy at the moment it executes:

- `do_signup` reads one destructured snapshot (`self_serve`, `pcp_v3`, QR expiration, relay timeouts, etc.) at the top of the function: [3](#0-2) 
- `detect_face` re-reads `self_serve` independently later in the same signup: [4](#0-3) 
- `biometric_capture` re-reads config again for capture timeout and clones the whole (possibly now-different) config into the capture plan: [5](#0-4) 
- `verify_user_qr_code` re-reads `user_qr_validation_use_full_operator_qr` / `user_qr_validation_use_only_operator_location` independently before contacting the backend: [6](#0-5) 
- `check_signup_conditions` re-reads `block_signup_when_no_internet` independently: [7](#0-6) 

The `Config` struct also carries fraud/liveness-relevant fields — `fraud_check_engine_config`, `child_threshold`, and the `self_serve_*` gating flags — that are part of this same globally-mutable, freely-swappable object: [8](#0-7) 

Because a background task can replace `Config` at any point between these independent lock acquisitions, a single signup transaction can start under one policy (e.g., strict QR validation, `block_signup_when_no_internet = true`, a given `child_threshold`/`fraud_check_engine_config`) and finish under a materially different one, with no atomicity guarantee across the transaction and no advance warning to the orb operator or user that the rules changed mid-flight. This mirrors the reported bug class exactly: privileged changes "take effect immediately," and — intentionally or through unlucky timing — different phases of one user-facing operation can enforce inconsistent security-relevant policy.

### Impact Explanation
If a backend-pushed config update (weakened `fraud_check_engine_config`, relaxed `child_threshold`, disabled `block_signup_when_no_internet`, or altered `user_qr_validation_use_full_operator_qr`/`user_qr_validation_use_only_operator_location`) lands between the point where `do_signup` snapshots config and the point where `detect_face`, `verify_user_qr_code`, `biometric_capture`, or the eventual fraud-detection step re-read config, the signup can complete under a mix of old and new policy. This can degrade fraud/liveness enforcement for a specific in-flight signup or apply mismatched under-age/child thresholds between capture and identification stages, i.e., a fraud/liveness-bypass-adjacent inconsistency for that one enrollment, without any log/alert distinguishing "policy changed mid-signup" from normal operation.

### Likelihood Explanation
`CONFIG_UPDATE_INTERVAL` polling is unconditional background behavior (not gated on signup state), and a full signup (QR scan, face detection, biometric capture, fraud pipeline) spans multiple seconds, giving a realistic window for a scheduled/backend-side config push to race with an active signup. The trigger does not require a malicious operator or hardware access — a normal backend config rollout during business hours could unintentionally hit this window, and the report's own examples note this can happen "purely accidentally" as well as via deliberate timing.

### Recommendation
Snapshot the `Config` once per signup transaction (or take the mutex/clone at `do_signup` entry and thread that single value through every downstream fraud/liveness/QR-validation decision) instead of re-locking and re-reading fresh config at each stage. Defer `config_update` swaps while `signup_flag` is set (the code already has a signup-in-progress flag it could consult via `before_config_update`), or double-buffer config: apply newly downloaded config only at safe signup boundaries (`before_config_update` returning `false` during an active signup, applying the pending update once `after_signup` completes).

### Proof of Concept
Not applicable in the classic exploit sense (no attacker-controlled trigger is required); the issue is a race/consistency defect. It can be demonstrated by: (1) starting a signup, (2) triggering `Config::download_and_store` with a materially different `fraud_check_engine_config`/`child_threshold`/`user_qr_validation_*` value between the `do_signup` config snapshot (`src/plans/mod.rs:497-506`) and a later independent read such as `verify_user_qr_code` (`src/plans/mod.rs:1588-1598`) or `biometric_capture` (`src/plans/mod.rs:1167-1178`), and (3) observing that the later stage enforces the new policy while earlier decisions were made under the old one — confirming the lack of a per-transaction consistent snapshot.

    fn config_update(&mut self, observer: &mut Observer) -> Result<()> {
        if self.before_config_update()? {
            match observer.config_update.as_mut().map(future::FutureExt::now_or_never) {
                Some(None) => return Ok(()),
                Some(Some(result)) => result??,
                None => {}
            }
            let config = Arc::clone(&observer.config);
            let ui = observer.ui.clone();
            observer.config_update = Some(tokio::spawn(async move {
                if let Ok(new_config) = Config::download().await {
                    *config.lock().await = new_config;
                    config.lock().await.propagate_to_ui(ui.as_ref());
                }
                Ok(())
            }));
        }
        Ok(())
    }
