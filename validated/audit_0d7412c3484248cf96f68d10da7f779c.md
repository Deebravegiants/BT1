### Title
Webhook `shop` (and `topic`) identity fields are not covered by HMAC verification, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw HTTP body, while the `shop`, `topic`, `webhook_id`, and `api_version` values used to build `WebhookMetadata` (passed to the app's `WebhookHandler#handle`) are read directly, unauthenticated, from HTTP headers. [1](#0-0) 

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

`Registry.process` validates the HMAC against that signable string via `Utils::HmacValidator.validate`, which only ever checks `verifiable_query.to_signable_string` (i.e., the raw body) against the secret: [3](#0-2) 

Once the HMAC passes, `Registry.process` builds `WebhookMetadata` directly from `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` — all of which are pulled straight from attacker-controllable HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, `shopify-api-version`) and never included in the signed payload: [4](#0-3) [5](#0-4) 

This breaks the identity binding that a `shop`/`topic`-scoped HMAC should provide: the equality `shop verified by HMAC == shop delivered to handler` does not hold, because the HMAC only binds `body`, not `shop`. The `WebhookMetadata.shop` field, which downstream app code uses to key its per-tenant data/session lookups, is therefore not authenticated at all — an unprivileged internet user who can obtain any single valid `(body, hmac)` pair signed with the app's secret (e.g., by installing the app on their own shop and capturing one of their own legitimately-delivered webhooks, whose body content they can influence, such as an `orders/create` or `products/update` payload) can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header to any arbitrary value. The signature still validates because headers are outside the signed scope, but the handler receives forged `shop`/`topic` metadata.

### Impact Explanation
This allows cross-tenant webhook forgery: an attacker-controlled shop can cause the app to process a webhook that claims to originate from a victim shop, with attacker-influenced body content. Since app-side webhook handlers commonly use `WebhookMetadata#shop` to look up the target tenant's session/access token and perform tenant-scoped side effects (e.g., writing data, triggering redact/data-request flows, updating per-shop state), this crosses the tenant boundary that the HMAC is meant to enforce — a Critical/High-severity impact (cross-tenant access) per the identity-binding class described in the source report (non-compliant token / unchecked field trusted downstream of a partial integrity check).

### Likelihood Explanation
Any internet-reachable party who can install the target app on a shop they control (a normal, low-privilege onboarding step for public/embedded Shopify apps) can generate at least one legitimately HMAC-signed webhook body under the app's real secret, then replay it with forged headers to the app's public webhook endpoint. No access token, `client_secret`, or privileged account is required — only the ability to trigger a webhook on one's own installed shop and to send an HTTP request with modified headers, which is well within "unprivileged internet user" capability.

### Recommendation
Bind the shop/topic identity to the signed payload instead of trusting headers post-hoc: either (a) include the `shop`, `topic`, and `webhook_id` header values in the string that is HMAC-verified (matching what Shopify actually signs), or (b) require host applications to cross-check `WebhookMetadata.shop` against the shop associated with the currently loaded session/store *before* the HMAC-gated handler runs, and document clearly that `request.shop`/`request.topic` are not currently covered by `HmacValidator.validate` so implementers do not treat them as authenticated.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and registers/receives a legitimate webhook (e.g., `orders/create`) with body `B`, correctly signed as `HMAC_secret(B)` by Shopify.
2. Attacker replays this exact `(B, HMAC_secret(B))` pair directly to the app's public webhook endpoint, but changes the `x-shopify-shop-domain` header to `victim-shop.myshopify.com` (and optionally the topic/webhook-id headers).
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC_secret(request.to_signable_string)` == `HMAC_secret(B)` — this passes because the body `B` is unchanged. [4](#0-3) 
4. `WebhookMetadata` is constructed with `shop: "victim-shop.myshopify.com"` (from the forged header) and passed to the registered handler, which now processes attacker-influenced content under the victim tenant's identity. [6](#0-5)
