Audit Report

## Title
Missing request-ID collision check in legacy WebAPI trigger handler allows cross-user response hijacking - ([File: core/services/gateway/handlers/capabilities/handler.go])

## Summary
`HandleLegacyUserMessage` in the Gateway's legacy `web_api_trigger` path stores the caller-supplied callback in the shared `h.savedCallbacks` map keyed solely by the client-controlled `MessageID`, with no check for whether an entry already exists under that key. This allows an unprivileged second caller to overwrite another in-flight caller's saved callback so that a later DON response is delivered to the wrong client.

## Finding Description
`gateway.ProcessRequest` dispatches legacy DON-ID-addressed requests to `handler.HandleLegacyUserMessage` [1](#0-0) . Inside that handler, after payload/timestamp/method validation, the callback is registered with an unconditional map write: [2](#0-1) 
No prior lookup of `h.savedCallbacks[msg.Body.MessageID]` is performed before this assignment, unlike every other equivalent request-tracking map in the codebase, which check-then-insert: the v2 HTTP trigger handler's `setupCallback` [3](#0-2) , the Vault handler's `newActiveRequest` [4](#0-3) , and the outgoing connector's `responses.new` [5](#0-4) .

`msg.Validate()` only checks length/format constraints on `MessageID` (non-empty, ≤128 bytes, no trailing null byte) and derives `Sender` from the signature, but never ties `MessageID` uniqueness to the sender or checks for collisions against in-flight requests [6](#0-5) . Thus any signer (an unprivileged client with any valid keypair, since there's no allowlist enforced here — the code even has a `// TODO: apply allowlist and rate-limiting here` comment) [7](#0-6)  can choose an arbitrary `MessageID` that collides with another caller's in-flight ID.

When a DON node responds, `handleWebAPITriggerMessage` looks up and deletes the entry purely by `MessageID`, routing the response to whichever callback is currently stored: [8](#0-7) . If an attacker's registration for the same `MessageID` overwrote the legitimate caller's entry before the DON responds, the attacker receives the legitimate caller's response instead, and the legitimate caller's request silently hangs (no error, no response).

## Impact Explanation
This maps to the "cross-user response confusion" impact category: an unprivileged client can capture another user's `web_api_trigger` response by colliding on `MessageID`, and simultaneously cause denial of service for the original legitimate requester whose callback is silently dropped. This is a genuine broken invariant reachable via the public Gateway HTTP endpoint, consistent with the check-then-insert pattern enforced everywhere else in the same codebase (v2 HTTP trigger handler, Vault handler, outgoing connector) but missing specifically in this legacy code path.

## Likelihood Explanation
Exploitation requires the attacker to know or predict the target's `MessageID` and to win a race window between the victim's registration and the DON's response. Since `MessageID` is entirely client-supplied and not scoped to a session, sender address, or nonce enforced server-side, an attacker controlling their own `MessageID` choice can deliberately target any ID they can observe or guess (e.g., through predictable client-side ID generation, or IDs otherwise leaked/observable). This makes exploitation plausible in realistic deployments, though the precise entropy/predictability of legitimate clients' `MessageID` generation could not be fully confirmed from the indexed code.

## Recommendation
In `HandleLegacyUserMessage`, before writing to `h.savedCallbacks`, check for an existing entry under `h.mu.Lock()` and reject the request (e.g., return a conflict error via the callback) if the `MessageID` is already in use, mirroring `httpTriggerHandler.setupCallback`, `vault.newActiveRequest`, and `responses.new`.

## Proof of Concept
1. Attacker crafts and signs a legacy `web_api_trigger` `Message` with `MessageID = "X"` and the same `DonID` as a target victim's in-flight request (attacker only needs any valid keypair since no allowlist is enforced on this path).
2. Attacker submits this message to the Gateway's JSON-RPC endpoint slightly after the victim's legitimate request with the same `MessageID = "X"` has been registered but before the DON responds.
3. The unconditional write at `core/services/gateway/handlers/capabilities/handler.go:412` overwrites the victim's `savedCallbacks["X"]` entry with the attacker's callback.
4. When the DON node responds with `MessageID = "X"`, `handleWebAPITriggerMessage` (lines 148-161) delivers the response to the attacker's callback, while the victim's original request never completes.
5. A Go unit test can directly call `handler.HandleLegacyUserMessage` twice with the same `MessageID` from two different `Callback` instances and assert that only one callback ultimately receives the DON's response while the other never does, confirming the missing collision check.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
	delete(h.savedCallbacks, msg.Body.MessageID)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JSONRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageID) == 0 || len(m.Body.MessageID) > MessageIDMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageID, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonID) == 0 || len(m.Body.DonID) > MessageDonIDMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonID, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
