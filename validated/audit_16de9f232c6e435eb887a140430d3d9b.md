### Title
Webhook shop-domain (tenant identifier) is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC signature validated by `Utils::HmacValidator.validate` covers the body bytes only, not the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers [1](#0-0) . `Registry.process` uses this same HMAC check as the sole authenticity gate, then trusts `request.shop` (read straight from the unauthenticated header) to build the `WebhookMetadata` passed to the handler [2](#0-1) . This breaks the identity binding `shop authenticated == shop consumed by handler`: the HMAC authenticates the body, but the tenant identifier used by the application is an entirely separate, unsigned field.

### Finding Description
`Request#hmac` decodes the `x-shopify-hmac-sha256` header [3](#0-2) , and `HmacValidator.validate_signature` recomputes the HMAC over `verifiable_query.to_signable_string` and compares it with `OpenSSL.secure_compare` [4](#0-3) . For `Webhooks::Request`, `to_signable_string` is defined as `@raw_body` only [1](#0-0) . None of `shop`, `topic`, `webhook_id`, or `api_version` — all parsed directly from client-controlled HTTP headers in the constructor [5](#0-4)  — are part of the signed payload.

`Registry.process` gates on `Utils::HmacValidator.validate(request)` and, once it passes, forwards `request.topic` and `request.shop` unmodified to the registered handler via `WebhookMetadata.new` [2](#0-1) . Because `shop` is not bound to the signature, the equality the library implicitly guarantees — "the `shop` field the handler receives is the shop the HMAC was computed for" — does not hold. An attacker who can obtain any one validly-signed `(body, hmac)` pair (trivially available to them if they install the app on their own store and trigger a webhook for their own shop) can replay that exact body/HMAC pair while substituting an arbitrary `x-shopify-shop-domain` header. `HmacValidator.validate` still returns `true` because it only checks the body bytes, and `Registry.process` will hand the handler a `WebhookMetadata` claiming to be from the victim shop of the attacker's choosing.

### Impact Explanation
This is a cross-tenant identity confusion: host applications built on this gem are expected to use `WebhookMetadata#shop` as the trusted tenant key to look up/update per-shop state (sessions, orders, inventory, etc.) once `HmacValidator.validate` succeeds. Since `shop` is not covered by the HMAC, an attacker can make the application process attacker-controlled webhook payloads (fully valid body content of their choosing, since it's their own shop's webhook) under the identity of a different, victim shop. This crosses the tenant boundary and satisfies the "cross-tenant access" criteria for Critical impact, since the application has no cryptographic assurance that the `shop` field is genuine.

### Likelihood Explanation
Likelihood is high for anyone who is a legitimate but unprivileged user of the app (i.e., installs the app on their own shop): they can trivially generate an arbitrary number of validly-signed `(body, hmac)` pairs by triggering webhook-eligible actions on their own store, then replay those pairs to the app's webhook endpoint with a forged `shop-domain` header. No access token, `client_secret`, or privileged account is required — only the ability to receive one's own webhook deliveries, which any merchant installing the app has by default.

### Recommendation
Include the tenant-identifying header (`shop-domain`, and ideally `topic`/`webhook-id`) in the HMAC-signed material, or otherwise cryptographically bind them to the payload before trusting them, e.g., by changing `Request#to_signable_string` to canonicalize and include `shop`, `topic`, and `webhook_id` alongside the raw body, and re-validating with the same construction. If Shopify's own webhook HMAC only signs the body, the gem should document this explicitly and warn implementers that `WebhookMetadata#shop` cannot be trusted as an authenticated tenant boundary without additional out-of-band verification (e.g., cross-checking against sessions/shops already known to be installed, or validating against the request's actual delivery source).

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and triggers a webhook event (e.g., `orders/create`).
2. Shopify delivers `POST /webhooks` with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(secret, B)` and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker captures `(B, H)` and replays it to the same endpoint with headers unchanged except `x-shopify-shop-domain: victim.myshopify.com`.
4. `Webhooks::Request.new` parses headers, `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `to_signable_string` (`= B`) and compares to `H` — validation succeeds since the body is unchanged [1](#0-0) [4](#0-3) .
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)` [6](#0-5) , causing the host application to process attacker-supplied data under the victim's tenant identity.

        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
