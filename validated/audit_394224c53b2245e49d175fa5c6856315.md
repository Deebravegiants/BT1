### Title
POA Bridge withdrawal status matches by `assetId` only, causing wrong destination tx hash reported for batched same-asset withdrawals - ([File: packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts])

### Summary
`waitForWithdrawalCompletion`/`findMatchingWithdrawal` resolves the destination transaction for a withdrawal by matching solely on `assetId` (`near_token_id`), never on amount, destination address, or withdrawal index. When a caller batches two or more withdrawals of the same token in a single intent (a supported, public SDK feature via `withdrawalParams: WithdrawalParams[]`), the completion-status lookup cannot distinguish between them and will report the same destination transaction hash to more than one withdrawal — an integrator consuming `destinationTx`/`hash` per withdrawal can end up crediting/confirming the wrong (or duplicate) withdrawal.

### Finding Description
`findMatchingWithdrawal` is implemented as: [1](#0-0) 

It is called from `waitForWithdrawalCompletion`, which only carries `WithdrawalCriteria = { assetId: string }`: [2](#0-1) 

The code's own comment acknowledges the equality being broken: matching is done purely by `assetId`, so "multiple withdrawals of the same token in a single transaction are not supported" — yet the public SDK API (`sdk.processWithdrawal`, `sdk.waitForWithdrawalCompletion`, `sdk.createWithdrawalCompletionPromises`) accepts and processes exactly this scenario without any validation rejecting or deduplicating same-asset batch withdrawals: [3](#0-2) [4](#0-3) 

The equality that should hold is: *the destination tx hash returned for withdrawal index N must correspond to the on-chain settlement of withdrawal N* (matched by amount/destination, not merely by `assetId`). Because the match key is only `assetId`, two withdrawals of `usdc.omft.near` to different destination addresses/amounts in the same batch both resolve against the same POA bridge record (the `Array.find` first match), so `watchWithdrawal` in `packages/intents-sdk/src/core/withdrawal-watcher.ts` (which calls `bridge.describeWithdrawal` per withdrawal identifier and trusts the returned `status.txHash`) will report an identical `{ hash }` for multiple, distinct withdrawals.

### Impact Explanation
This falls under "a status or hash misreport making an integrator credit or refund twice." An integrator relying on `sdk.processWithdrawal`/`sdk.waitForWithdrawalCompletion` per-withdrawal result to confirm settlement (e.g., mark an order/withdrawal as completed with a specific destination tx hash) could mark two different withdrawals as completed using the same tx hash, or attribute the wrong recipient's payout to the wrong destination hash — a concrete on-chain/off-chain state mismatch with financial/audit consequences, analogous to the `orderId` reuse issue in the referenced report (event/report data not uniquely tied to the actual underlying settlement).

### Likelihood Explanation
No special privilege is required — the caller only needs to submit a normal batch withdrawal (`WithdrawalParams[]`) containing two or more entries with the same `assetId`, a feature explicitly supported by `sdk.processWithdrawal`/`signAndSendWithdrawalIntent`/`waitForWithdrawalCompletion`. There is no guard anywhere in `sdk.ts` or `poa-bridge.ts` preventing or deduplicating same-asset batches before they reach `waitForWithdrawalCompletion`, so this is trivially reachable through documented public API usage.

### Recommendation
Extend `WithdrawalCriteria` to include enough discriminating fields (destination address, amount, and/or withdrawal index/nonce) so `findMatchingWithdrawal` can uniquely bind each requested withdrawal to its actual on-chain record, or reject/serialize batches containing duplicate `assetId` entries until the POA Bridge API supports disambiguation as noted in the existing code comment.

### Proof of Concept
1. Call `sdk.processWithdrawal({ withdrawalParams: [ {assetId: "nep141:usdc.omft.near", amount: 100n, destinationAddress: "0xAAA...", feeInclusive:false}, {assetId: "nep141:usdc.omft.near", amount: 200n, destinationAddress: "0xBBB...", feeInclusive:false} ] })`.
2. Both withdrawals settle via the POA bridge in the same underlying NEAR transaction.
3. `createWithdrawalCompletionPromises` invokes `watchWithdrawal` for each entry; both entries call `describeWithdrawal` → `getWithdrawalStatus` → `findMatchingWithdrawal(result.withdrawals, { assetId: "nep141:usdc.omft.near" })`.
4. Because `findMatchingWithdrawal` only checks `assetId`, `.find()` returns the same (first) withdrawal record for both, so `destinationTx[0]` and `destinationTx[1]` report the identical `txHash`, even though the two withdrawals went to different destination addresses with different amounts — as confirmed by the existing unit test that demonstrates matching purely by `assetId`: [5](#0-4)

	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});
	}
