### Title
Non-embedded session lookup trusts an unsigned `shopify_app_session` cookie value as the session ID, enabling cross-tenant session hijack — (File: `lib/shopify_api/utils/session_utils.rb`, `lib/shopify_api/auth/oauth/session_cookie.rb`)

### Summary
For non-embedded apps (and as the embedded fallback when no JWT is present), `ShopifyAPI::Utils::SessionUtils.current_session_id` derives the "current session" identity directly from the raw `shopify_app_session` cookie value, with no cryptographic binding to the shop, user, or issuing server. [1](#0-0)  The predicate the gem relies on is: `cookie bytes == session identity`, but the cookie is a plain `T::Struct` value with no HMAC/signature. [2](#0-1) 

### Finding Description
`SessionCookie` is a bare struct (`name`, `value`, `expires`) with no signing mechanism at all. [2](#0-1)  After OAuth completes, `Oauth.validate_auth_callback` sets this cookie's `value` to the deterministic, predictable session id `session.id` (which is `"offline_#{shop}"` for offline sessions or `"#{shop}_#{associated_user.id}"` for online sessions). [3](#0-2) [4](#0-3) 

`SessionUtils.cookie_session_id` then simply returns whatever value is present in that cookie, unverified: [5](#0-4) . This is used both for non-embedded apps and as the fallback path for embedded apps when no `shopify_id_token` is supplied: [1](#0-0) .

Compare this to the JWT-backed path in the same method: when a Shopify ID token is present, the session id is derived from a payload that is HMAC-verified against `Context.api_secret_key` inside `JwtPayload.new`, so `shop`/`sub` are cryptographically bound to Shopify's issuance. [6](#0-5)  The cookie path has no equivalent — the "authenticated shop" that a caller believes it is retrieving is actually just "the shop named in whatever bytes arrived in a cookie named `shopify_app_session`," with the equality `authenticated_shop == cookie_value_shop` never actually enforced by any signature check in this gem.

Because the session id format (`offline_{shop}` / `{shop}_{user_id}`) is fully documented and deterministic, any unprivileged user can construct a value for a target shop and present it as their own cookie's value. If the host application uses `SessionUtils.current_session_id` to key its session-repository lookup (as the gem's own docs direct integrators to do) and does not itself add integrity protection (e.g. Rails `cookies.signed`/`cookies.encrypted`), the returned "current session id" is attacker-choosable, letting one tenant's browser session retrieve and operate under a different, victim shop's stored `Session` (including its access token) merely by setting a cookie value — a cross-tenant identity binding break, not merely a "host app misuse" issue, because the gem itself provides no way to verify the cookie's authenticity: `SessionCookie` has no HMAC field or verification method at all, unlike every other identity-bearing structure in this codebase (`AuthQuery`, `Webhooks::Request`) which implement `Utils::VerifiableQuery` and go through `HmacValidator`. [7](#0-6) [8](#0-7) 

### Impact Explanation
If exploited, an attacker gains cross-tenant access: retrieval of a `Session` object (and its `access_token`) belonging to a different shop/merchant, purely by supplying a forged, unsigned cookie value. This matches the Critical-impact category of "cross-tenant access." The severity depends on whether the host application layers its own signing on top of the cookie (which the gem's docs do not enforce or even recommend using `cookies.signed`/`cookies.encrypted` explicitly) — but the gem-level `SessionCookie`/`SessionUtils` code path itself carries zero integrity guarantee, which is the root cause inside this gem's scope.

### Likelihood Explanation
Likelihood is moderate: it requires (a) a host application that stores multiple shops' sessions in a repository keyed by the id format the gem produces, and (b) that uses `SessionUtils.current_session_id`/`cookie_session_id` output directly as the lookup key without adding its own cookie signing. Session id formats (`offline_#{shop}`, `#{shop}_#{user_id}`) are public/deterministic and documented, so no secret knowledge is needed by the attacker beyond the target shop's domain.

### Recommendation
- Make `SessionCookie` a `VerifiableQuery`-like structure: HMAC the cookie value (session id) with `Context.api_secret_key` at creation time in `Oauth.validate_auth_callback`, and verify that HMAC in `SessionUtils.cookie_session_id` before trusting the value, mirroring the pattern already used for `AuthQuery` and `Webhooks::Request`.
- Alternatively, explicitly document (and ideally enforce via the API) that callers must only accept this cookie via a cryptographically signed/encrypted cookie jar (e.g., Rails `cookies.signed`) and add a runtime check/warning if a plain cookie hash is passed to `SessionUtils.current_session_id`.

### Proof of Concept
1. Merchant A's app is non-embedded (or an embedded fallback scenario with no JWT sent). App backend uses `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)` to resolve "the current session" and then loads the `Session` from its own repository by that id. [1](#0-0) 
2. Attacker knows (from the OAuth docs / offline session id scheme) that offline session ids are formatted as `"offline_#{shop}"`. [9](#0-8) 
3. Attacker sets their browser's `shopify_app_session` cookie to `offline_victim-shop.myshopify.com`.
4. `SessionUtils.cookie_session_id` returns this attacker-supplied string unchanged/unverified. [5](#0-4) 
5. The host app looks up `victim-shop`'s stored `Session` (with its real access token) using this attacker-supplied id and treats the attacker's request as authenticated for `victim-shop`, resulting in cross-tenant access to the victim merchant's data/access token.
