### Title
Excess native ETH swapped in `EvmHost.dispatch`/`fundRequest` is refunded to the Host contract itself instead of the caller, permanently trapping user funds - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest` all accept `msg.value` and swap it for the exact `feeToken` amount needed via `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(...)`. Any dispatcher, relayer, or bandwidth purchaser calling these functions with `msg.value` greater than the actual ETH cost of the swap has the difference refunded by the router/wrapper — but that refund is sent to `msg.sender` **of the swap call**, which is `EvmHost` itself, not the original transaction caller.

### Finding Description
In `dispatch(DispatchPost)`: [1](#0-0) 

and the analogous `dispatch(DispatchGet)`: [2](#0-1) 

and `fundRequest`: [3](#0-2) 

In each case, the full `msg.value` is forwarded to the router (`swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`). This function only ever consumes what is needed to buy exactly `fee`/`amount` of `feeToken`; the remaining ETH is refunded by the router to its immediate caller. Because `EvmHost` is the one invoking the router, that refund lands back on `EvmHost`'s own balance — not on `_msgSender()`, the actual transaction sender who overpaid.

This is confirmed by the project's own wrapper implementations and tests. The `UniV3UniswapV2Wrapper.swapETHForExactTokens` explicitly refunds unspent ETH to `msg.sender` of the wrapper call: [4](#0-3) 

and the `UniV4UniswapV2Wrapper` test explicitly documents that "refund returns to caller" (i.e., whichever contract called the swap, not the end user): [5](#0-4) 

By contrast, `IntentGatewayV2` correctly handles this same pattern: it captures the `amounts[0]` actually spent from the swap's return value, subtracts it from the tracked `msgValue`, and then explicitly forwards any leftover native ETH back to the real caller via `_sendValue(msg.sender, msgValue)`: [6](#0-5) 

`EvmHost.dispatch`/`fundRequest` perform no equivalent bookkeeping or refund step after the swap — the returned `amounts` array from `swapETHForExactTokens` is discarded entirely, and there is no logic anywhere in `EvmHost.sol` that forwards its native balance back out to callers.

### Impact Explanation
Any user, relayer, or integrating contract that dispatches a POST/GET request or funds a pending request by sending native ETH (as documented and recommended in the project's own docs for native-token payment flows) and overestimates the ETH needed for the fee swap will have the surplus permanently captured by the `EvmHost` contract instead of returned to them. Since exact off-chain fee estimation is inherently imprecise (quoted amounts drift with AMM price movement between quote and execution, and the docs themselves warn against on-chain `quote()` due to sandwich risk), overpayment is a normal, expected occurrence for legitimate callers — not an edge case. This results in permanent loss of user ETH with no recovery mechanism, satisfying the required "permanent freezing/loss of funds" impact bar for an unprivileged caller (a single dispatch transaction).

### Likelihood Explanation
High likelihood: every documented native-token dispatch flow (`sendMessageWithNative`, `readRemoteBalance`, `fundRequest`) instructs users to send `msg.value` as an approximate/generous ETH amount and rely on the Host to swap and refund excess, exactly the anti-pattern demonstrated by the original Mover finding. Any slippage between the quoted fee estimate and the actual swap execution price (unavoidable due to AMM price movement, MEV, or conservative safety margins added by integrators) triggers the loss on essentially every native-token dispatch.

### Recommendation
After each `swapETHForExactTokens` call in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, capture the `amounts[0]` (ETH actually spent) returned by the router and refund the difference (`msg.value - amounts[0]`) back to `_msgSender()`, mirroring the pattern already implemented correctly in `IntentGatewayV2._sendValue`. Alternatively, add a `receive()`/sweep path so any ETH held incidentally by `EvmHost` can be reclaimed by the original overpaying party.

### Proof of Concept
1. Caller invokes `EvmHost.dispatch(DispatchPost)` with `post.fee = 100` (feeToken units) and sends `msg.value = 1 ether`, expecting only a small fraction to be spent on the ETH→feeToken swap for 100 units of `feeToken`.
2. `swapETHForExactTokens{value: 1 ether}(100, path, address(this), block.timestamp)` executes, spending e.g. `0.01 ether` and refunding `0.99 ether` back to `msg.sender` of the swap call — `EvmHost`.
3. `EvmHost`'s function returns normally; the `0.99 ether` remains in `EvmHost`'s balance.
4. No code path in `EvmHost.sol` ever forwards this ETH back to the original caller; it is permanently stuck (or, if any privileged sweep function exists elsewhere in governance, is diverted away from the rightful owner rather than refunded), reproducing the "excess ETH not refunded" bug class from the referenced Mover finding.
