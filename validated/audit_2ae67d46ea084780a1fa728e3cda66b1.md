### Title
Pool refunds unmeasured "overpayment" out of real custody, draining supplier funds and leaving the market unable to honor withdrawals - (contracts/pool/src/ops/repay.rs)

### Summary

The DoS class of CVE-2017-10286 (a crash/hang that renders the service unavailable) maps onto XOXNO Lending's pool settlement layer: `ops::repay::apply` and `ops::recapitalize::apply` refund a computed excess to the payer straight out of the pool's token custody, sized from the *declared* `amount` rather than a measured inbound balance delta, while the `cash` book is only credited for the applied portion. The pool's own test suite demonstrates that a repay declared on a zero-debt market pays the entire declared amount back out of custody without any inbound transfer having occurred, leaving `cash` unchanged while the real balance is gone. From then on, `require_reserves` admits exits the SAC transfer cannot fulfill: withdrawals, borrows and flash loans revert on token transfer, i.e. the market permanently reports itself solvent while unable to pay — supplier funds are effectively stolen/frozen and the contract cannot operate for lack of token funds.

### Finding Description

`contracts/pool/src/ops/repay.rs` resolves the repay purely arithmetically:

```rust
// contracts/pool/src/ops/repay.rs
let (burned, overpayment) = cache.resolve_repay(amount, position);   // line 44
let net_repay = amount.checked_sub(overpayment)...                 // line 45
assert_with_error!(env, net_repay == 0 || burned.raw() > 0, ...);  // line 48 (passes when net_repay == 0)
cache.credit_cash(net_repay);                                      // line 57
...
outcome.cache.transfer_out(payer, outcome.overpayment);            // line 32
```

`overpayment` equals `amount - current_debt`. On a market with zero debt, `resolve_repay` takes the full-close branch: `overpayment == amount`, `burned == 0`, `net_repay == 0`, and the `RepayRoundsToZeroShares` assert passes on its `net_repay == 0` disjunct. `transfer_out` then sends `amount` of real custody to the payer with `cash` untouched.

`contracts/pool/src/ops/recapitalize.rs` has the identical shape:

```rust
// contracts/pool/src/ops/recapitalize.rs
let applied = amount.min(guards::backing_shortfall(&cache));   // line 52
let refund = amount.checked_sub(applied)...;                 // line 53
cache.credit_cash(applied);                                  // line 57
...
outcome.cache.transfer_out(&payer, outcome.refund);          // line 34
```

On a fully-backed market `backing_shortfall` is zero, so the entire declared `amount` is "refunded" out of custody.

The pool's own tests prove the mechanic and its consequence (`contracts/pool/tests/flows.rs`):

- `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` (lines 3590–3610): `repay(payer, ract(0, custody_before))` with nothing transferred in and `borrowed == 0` pays the payer the full declared amount; the pool balance drops to zero while `cash` is unchanged.
- `assert_unfunded_refund_drained_custody` (lines 3378–3401): `token.balance(pool) == 0` after the refund while `cash` is untouched — "the market reports itself solvent and cannot pay", and `Cache::require_reserves` "reads the book, not the balance, so it admits exits that then fail inside the SAC transfer" (lines 3404–3406).

### Impact Explanation

Each call converts up to `amount` of supplier principal sitting in the pool's token custody into a "refund" to the attacker, without debiting `cash`, burning shares, or checking reserves. Because the book keeps claiming the paid-out funds are present, the deficit surfaces as reverts inside downstream SAC transfers: `withdraw`, `borrow` and `flash` all pass `require_reserves` against the inflated `cash` figure and then fail at the token transfer. Result: theft of user funds and/or a market permanently unable to honor redemptions — the exact "complete DOS / hang" availability impact of the reference CVE, plus realized loss of custody. Both accepted impact classes are met: theft of user funds and a contract unable to operate from lack of token funds.

### Likelihood Explanation

Reachability is the crux and is partially caveated. The pool-level functions trust the declared amount and do not measure the inbound balance delta themselves; the tests show `repay` executing with a generated payer address and zero inbound transfer, so if pool ops are reachable outside the controller the attack is one transaction and fully repeatable across every listed market. If pool ops are gated to the configured controller address, the same drain is reachable through the controller's `repay`/liquidation full-close/`recapitalize` paths only when the inbound token delivers less than the declared amount (fee-on-transfer/deflationary tokens) — which the rules exclude as token semantics. The finding therefore stands where the pool trusts declared amounts (as its tests exercise directly) but should be verified against the exact auth gate in `contracts/pool/src/lib.rs`, whose contents were not fully confirmed within this review.

### Recommendation

Measure receipts instead of trusting declared amounts:

1. In `ops::repay::accounting` and `ops::recapitalize::accounting`, cap `overpayment`/`refund` by the balance delta the pool actually received during this call (snapshot token balance before the controller's inbound transfer, or have the caller pass the measured receipt), and never `transfer_out` more than `received - credited`.
2. Alternatively, debit `cash` for the refund or route refunds through `require_reserves` so the book cannot overstate custody.
3. Add a postcondition that `cash <= token.balance(pool)` (or reconcile the book) after any op that moves tokens out without burning shares.

### Proof of Concept

On a live market with `borrowed == 0` (or a fully-backed market for `recapitalize`) and pool custody `B`:

1. Attacker calls `pool.repay(payer: attacker, action: PoolAction { hub_asset, amount: B })` (or `pool.recapitalize(hub_asset, payer: attacker, amount: B)`).
2. `resolve_repay` computes `overpayment = B`, `net_repay = 0`; the zero-shares assert passes. `cache.credit_cash(0)` leaves `cash == B` while `transfer_out(attacker, B)` empties custody.
3. Any subsequent supplier `withdraw` passes `require_reserves` (book still shows `B` cash) and reverts in the SAC `transfer` — permanent freeze of all remaining supplier claims in that market.

Reference implementation of step 2 exists verbatim in `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` (`contracts/pool/tests/flows.rs:3590`).
