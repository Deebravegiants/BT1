I have enough evidence now to write the analog finding.### Title
Simplex Uniswap V4 venue pricing uses unmitigated single-block spot price as an intent-fill oracle - ([File: sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts])

### Summary
Simplex, the Hyperbridge Intent Gateway solver reference implementation, can price cross-asset legs directly off a Uniswap V4 pool's current tick/`sqrtPriceX96` instead of a static curve. This spot price is read via `getSlot0`/`getLiquidity` with no TWAP, and is fed straight into the amount the solver commits to deliver when bidding on and filling a user's intent order. This mirrors the Chronos/`gamma`-style incident, where a concentrated-liquidity pool's manipulable instantaneous state was used as ground truth by dependent contracts/off-chain logic and was moved with a flash loan to extract value.

### Finding Description
`UniswapV4FundingPlanner.getExoticTokenPrice` picks the most-liquid configured position and derives price from `computeDirectPoolPriceUsd`, which the code's own flow documentation states returns "the **raw pool mid** derived from `sqrtPriceX96`" with "no size or impact term" [1](#0-0) .

The underlying state is refreshed by a single `eth_call` pair to `StateView.getSlot0`/`getLiquidity` at the current block, with no time-weighting: [2](#0-1) . `getExoticTokenPrice` calls `state.refresh()` and then picks the position with the largest liquidity, feeding the freshly-read spot price straight out: [3](#0-2) .

The only defense is `checkPriceGuard`, which is optional (`priceGuard` may be `undefined` per chain) and only rejects a quote that deviates from a **static** `referencePrice` by more than `maxDeviationBps` — it does not account for pool depth, execution/slippage cost, or fee tier, and an attacker can manipulate price within the configured band and still profit: [4](#0-3) . Configuration explicitly allows the guard to be entirely omitted ("omit both to leave the chain unguarded"): [5](#0-4) .

This price also feeds `referenceRate`, which sizes the order's USD notional used to select the **confirmation-depth policy** — the code comment itself acknowledges "a manipulated pool understating the value would shrink the reorg protection — the exact attack the guard exists to stop," meaning even the guard's designed threat model is exactly a flash-loan pool manipulation, yet it remains optional and imprecise: [6](#0-5) .

An unprivileged actor (any user able to place an Intent Gateway order, or an attacker capable of a flash loan on the referenced Uniswap V4 pool) can:
1. Flash-loan swap against the thin/target pool to move `sqrtPriceX96` in one block.
2. In the same block/transaction bundle, submit (or have ready) an intent order sized against the now-skewed venue price, or wait for the solver's phantom-bid/fill cycle to read the manipulated spot price.
3. Force the solver to bid/fill at the manipulated price — either draining the solver's escrowed inventory at a bad rate, or causing an under-collateralized confirmation depth to be selected for a since-manipulated notional, weakening reorg protection on the actual cross-chain settlement.

### Impact Explanation
This directly reaches the "intent solver" surface explicitly in scope: the solver's fill decision and the resulting `RedeemEscrow`/settlement message dispatched through the Intent Gateway are priced from a manipulable on-chain value. A successful attack can cause concrete theft (solver over-delivers output tokens or the confirmation policy under-protects settlement against a reorg due to a manipulated USD notional) — consistent with a Medium severity, single-instance financial loss, matching the reported Chronos loss scale.

### Likelihood Explanation
Likelihood depends on operational configuration: it requires (a) a solver operator to enable pool-based Uniswap V4 pricing without a `referencePrice`/`maxDeviationBps` guard (explicitly documented as a supported, valid configuration), or (b) a guard configured wide enough / a pool thin enough that a flash loan can move price within the allowed band while remaining profitable. Given flash loans are permissionless and the guard's stated threat model is precisely this scenario yet remains optional and non-depth-aware, exploitation is realistic against any solver instance running unguarded or loosely-guarded pool pricing on a thin pool.

### Recommendation
- Make the price guard mandatory whenever Uniswap V4 pool pricing is enabled (reject boot instead of allowing "unguarded" configuration).
- Replace or augment the raw `sqrtPriceX96` spot read with a TWAP/observation-based price, or require a minimum pool liquidity/depth threshold before trusting the spot quote.
- Extend `checkPriceGuard` to account for execution size/impact and the pool's fee tier, not just static deviation from a reference price.
- Apply the same hardened pricing path to `referenceRate`'s confirmation-depth sizing, since a manipulated notional there degrades reorg protection independently of the trade-pricing guard.

### Proof of Concept
Conceptual (no on-chain harness available in the indexed codebase to fully simulate a live flash loan against a real deployed pool):
1. Operator runs Simplex with `[vault.uniswapV4]` configured for a pair (e.g. USDC/cNGN) and either no `referencePrice`/`maxDeviationBps` guard, or a wide band, as shown supported in `filler-config-example.toml` [7](#0-6) .
2. Attacker flash-loans a large swap through the referenced Uniswap V4 pool, shifting `sqrtPriceX96`/`tick` within one block.
3. Attacker (or a colluding/awaiting counterpart) submits/holds an Intent Gateway order priced off that pair; the solver's `getExoticTokenPrice` reads the manipulated `slot0` on its next `refresh()` call [2](#0-1)  and bids/fills at the skewed rate, or `referenceRate` under-sizes the confirmation-depth policy for the order's true USD value [6](#0-5) .
4. Attacker reverses the flash-loan swap in the same transaction, pocketing the solver's over-delivery (or exploits the weakened reorg confirmation depth to double-spend/reorg the settlement).

I could not find an on-chain test or simulation in the indexed codebase that exercises this end-to-end against live liquidity (the relevant Vitest files are marked `describe.skip` and require live mainnet RPCs/private keys), so full exploitation economics (achievable deviation vs. flash-loan cost) could not be numerically verified here.

	async getExoticTokenPrice(chain: string, exoticToken: string): Promise<Decimal | null> {
		const state = this.stateByChain.get(chain)
		if (!state || !state.isHydrated()) return null

		try {
			await state.refresh()
		} catch (err) {
			this.logger.error({ err, chain }, "Failed to refresh state for price query")
			return null
		}

		const tokenLower = exoticToken.toLowerCase()
		let bestPrice: Decimal | null = null
		let bestLiquidity = 0n

		for (const pos of state.allPositions()) {
			if (pos.currency0.toLowerCase() !== tokenLower && pos.currency1.toLowerCase() !== tokenLower) continue
			const sdkPool = state.getSdkPool(pos.tokenId)
			if (!sdkPool) continue

			const result = this.computeDirectPoolPriceUsd(pos, sdkPool, chain)
			if (result && result.exoticToken.toLowerCase() === tokenLower) {
				const poolLiquidity = state.getPoolLiquidity(pos.tokenId)
				if (poolLiquidity > bestLiquidity) {
					bestPrice = result.priceUsd
					bestLiquidity = poolLiquidity
				}
			}
		}

		if (bestPrice) {
			this.logger.debug({ chain, token: tokenLower, priceUsd: bestPrice.toString() }, "Exotic token price computed")
		}
		return bestPrice
	}

	/**
	 * Validates a live venue quote against the static reference price for the chain.
	 * Returns true (pass) when no guard is configured, or no reference exists for the
	 * chain. Returns false when the quote (token1 per USD) deviates from the reference
	 * by more than `maxDeviationBps`, in which case the order must not be filled.
	 */
	private checkPriceGuard(orderId: string | undefined, chain: string, venueToken1PerUsd: Decimal): boolean {
		const guard = this.priceGuard?.get(chain)
		if (!guard || guard.reference.lte(0)) return true

		const deviationBps = venueToken1PerUsd.minus(guard.reference).abs().div(guard.reference).mul(10000)
		if (deviationBps.gt(guard.maxDeviationBps)) {
			this.logger.warn(
				{
					orderId,
					chain,
					venuePrice: venueToken1PerUsd.toString(),
					referencePrice: guard.reference.toString(),
					deviationBps: deviationBps.toFixed(2),
					maxDeviationBps: guard.maxDeviationBps,
				},
				"Rejecting order: Uniswap venue quote outside price-guard band",
			)
			return false
		}
		return true
	}

	/**
	 * Minimum-size reference rate (token1 per token0) for a leg's pair: the
	 * bid curve at 0 (the side token1-input legs trade at), falling back to the
	 * ask curve, then the live venue quote for venue-priced pairs.
	 */
	private async referenceRate(
		leg: ResolvedLeg,
		venueUsdPrice: (chain: string, token1Address: string) => Promise<Decimal | null>,
	): Promise<Decimal | null> {
		const policy = leg.pair.bidPricePolicy ?? leg.pair.askPricePolicy
		if (policy) {
			const rate = policy.getPrice(new Decimal(0))
			return rate.gt(0) ? rate : null
		}
		// Venue-priced pair: token0 is USD-stable (constructor invariant), so the
		// venue's USD-per-token1 quote inverts straight into token1-per-token0.
		const venueUsd = await venueUsdPrice(leg.token1Chain, leg.token1Address)
		if (!venueUsd) return null
		const venueRate = new Decimal(1).div(venueUsd)
		// Same guard as trade pricing: this rate sizes the order's USD notional
		// for confirmation depth, and a manipulated pool understating the value
		// would shrink the reorg protection — the exact attack the guard exists
		// to stop. Refusing to size skips the order, consistent with pricing.
		if (!this.checkPriceGuard(undefined, leg.token1Chain, venueRate)) return null
		return venueRate
	}

**File:** docs/content/developers/evm/simplex/pricing.mdx (L68-72)
```text
## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.
```
