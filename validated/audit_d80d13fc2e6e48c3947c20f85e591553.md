## Analysis

The reported Sense Finance bug is a classic "unrestricted approve entry point" — any caller can force a shared contract to call `IERC20.approve()` for an arbitrary spender/amount, letting anyone sweep whatever tokens the contract is holding. Hyperbridge has a directly analogous unrestricted call surface in `CallDispatcher`.

### Title
Unrestricted `CallDispatcher.dispatch()` lets anyone force arbitrary ERC20 `approve()`/transfers of any tokens held by the dispatcher - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch()` executes an arbitrary, caller-supplied `Call[]` array with a raw low-level `.call{value: call.value}(call.data)` and has no access control on `msg.sender` whatsoever. [1](#0-0) 

### Finding Description
`CallDispatcher` is a generic execution proxy that `IntentGatewayV2` (predispatch/postdispatch calldata) and `HyperFungibleToken`/`WrappedHyperFungibleToken` (cross-chain calldata execution) route tokens through, and the design explicitly acknowledges the dispatcher "holds tokens temporarily during execution." [2](#0-1) 

Its `dispatch(bytes memory encoded)` function decodes an arbitrary `Call[]` and executes each entry — `to.call{value: call.value}(call.data)` — with no restriction on `msg.sender`, no allowlist of callers, and no ownership check:
```solidity
function dispatch(bytes memory encoded) external {
    Call[] memory calls = abi.decode(encoded, (Call[]));
    ...
    (bool success, bytes memory result) = to.call{value: call.value}(call.data);
    if (!success) revert CallFailed(to, result);
}
``` [1](#0-0) 

The intended flow assumes the transfer-in, `dispatch()`, and sweep-back are all atomic within one transaction (e.g. `IntentsBase._execute` sweeps only the enumerated output-asset tokens after invoking the postdispatch call): [3](#0-2) 

However, because `dispatch()` is completely permissionless, this atomicity assumption is not a real security boundary — it only holds for the *intended* caller (the gateway/HFT contract in the same transaction). Any token balance that ends up sitting in the `CallDispatcher` for any other reason (a token not enumerated in `order.output.assets` that the postdispatch/predispatch calldata acquires, calldata that mints/unlocks HFT tokens `to` the dispatcher address which isn't fully consumed by the attached `Call[]`, accidental direct transfers, or leftover native ETH accepted via `receive()`) can be drained by **anyone**, at any later block, by simply calling `CallDispatcher.dispatch()` directly with a `Call[]` that does `IERC20(token).approve(attacker, type(uint256).max)` followed by `transferFrom`, or a direct `transfer`/native-value forwarding call. This is functionally identical to the reported `RollerPeriphery.approve()` bug: an unauthenticated, arbitrary-parameter `approve()`/spend primitive reachable by any address, sitting in front of pooled token balances.

### Impact Explanation
Any ERC20 (or native ETH) balance that a `CallDispatcher` instance holds outside the exact, atomic window the owning application controls is permanently stealable by an arbitrary unprivileged transaction sender. Because `CallDispatcher` is shared infrastructure wired into `IntentGatewayV2` order fills/predispatch and `HyperFungibleToken`/`WrappedHyperFungibleToken` calldata execution, this is a concrete theft-of-funds vector against user/solver assets that transiently pass through the dispatcher, not merely a griefing or DoS issue. This satisfies the "concrete theft ... of funds" bar.

### Likelihood Explanation
The attack requires no privilege, no proof, and no timing race beyond "the dispatcher currently holds a non-zero balance it shouldn't" — which can arise from unswept dust for tokens not in the enumerated sweep list, a partially-completed multi-call batch, or third-party/accidental transfers directly to the dispatcher's `receive()`/ERC20 balance. Given `CallDispatcher` accepts native ETH unconditionally via `receive()` and has no rescue/access-controlled sweep function of its own, unclaimed value naturally accumulates over the contract's lifetime and is a standing target.

### Recommendation
Restrict `CallDispatcher.dispatch()` so it can only be invoked by the specific owning application contract(s) (e.g., an `onlyOwner`/allowlisted-caller modifier set at deployment, matching the per-app dispatcher deployment pattern already used in `DeployBridgeToken.s.sol`/`DeployHFT.s.sol`/`DeployWrappedHFT.s.sol`), or alternatively make `CallDispatcher` a one-shot, single-transaction-scoped executor that self-destructs/cannot retain balances between calls. At minimum, add a governance-only emergency sweep function and disallow arbitrary `approve()`-shaped calldata targets from being dispatched by non-owning callers.

### Proof of Concept
1. Any token balance ends up left on a deployed `CallDispatcher` instance (e.g., a postdispatch call in `IntentsBase._execute` swaps into a token not listed in `order.output.assets`, so the sweep loop at [4](#0-3)  never accounts for it and it remains on the dispatcher).
2. Attacker (any EOA, no permission needed) calls `CallDispatcher.dispatch(abi.encode(calls))` directly, where `calls[0] = Call({to: leftoverToken, value: 0, data: abi.encodeWithSelector(IERC20.approve.selector, attacker, type(uint256).max)})`.
3. Since `dispatch()` has no `msg.sender` check [5](#0-4) , the call succeeds and `CallDispatcher` grants the attacker unlimited allowance over the leftover token.
4. Attacker calls `leftoverToken.transferFrom(dispatcher, attacker, balance)` to drain it.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

Existing `CallDispatcher` deployments are listed on the [contract addresses](/developers/evm/contract-addresses/mainnet) page.

            if (token == address(0)) {
