## Analog Found: Unchecked division / integer-underflow panic in `Processor::calc_take_pnl` reachable from `Deposit`, `Withdraw`, and `WithdrawPnl`

### Title
Unvalidated arithmetic in `calc_take_pnl`/`calc_x_power` can panic on attacker-influenced pool state, permanently freezing LP withdrawals - (File: `program/src/processor.rs`, `program/src/math.rs`)

### Summary
CVE-2017-9123 is a crash caused by a parser trusting attacker-supplied file data to drive a calculation (`lqt_frame_duration`) without validating the values first, leading to an invalid memory read/crash. The analogous bug class here is unchecked arithmetic (division/subtraction) driven by pool state that a user can push toward degenerate values (zero) through normal, permissionless instructions, causing a Rust panic (`unwrap()` on `None`) instead of a graceful error.

### Finding Description
`Calculator::calc_x_power` divides by `current_y` with no zero-check: [1](#0-0) 

`Processor::calc_take_pnl` then further divides by `x1` and subtracts `x2`/`y2` from `x1`/`y1`, all via bare `.unwrap()` calls instead of `.ok_or(...)`-guarded error handling: [2](#0-1) 

`x1`/`y1` are derived from `total_pc_without_take_pnl` / `total_coin_without_take_pnl`, which are computed from live vault balances minus the pool's accumulated `need_take_pnl_pc`/`need_take_pnl_coin`: [3](#0-2) 

This function, `calc_take_pnl`, is invoked from `process_deposit`, `process_withdraw`, and `process_withdrawpnl` — all reachable by an unprivileged liquidity provider via ordinary transactions: [4](#0-3) [5](#0-4) [6](#0-5) 

If a sequence of ordinary swaps and withdrawals drives one side of the pool (post-normalization `x1` or `y1`) to zero or causes `x2`/`y2` (computed via `integer_sqrt` and division) to exceed `x1`/`y1` due to rounding, the `.checked_div(...).unwrap()` or `.checked_sub(...).unwrap()` calls panic instead of returning a handled `AmmError`. Because this state (vault balances vs. `need_take_pnl_*`) is persisted on-chain, the degenerate condition is not transient — every subsequent call to `Deposit`, `Withdraw`, or `WithdrawPnl` that re-derives the same `x1`/`y1` will panic identically until liquidity conditions change, which in a drained pool may never happen.

### Impact Explanation
A panic aborts only the single transaction on Solana (no memory corruption occurs, unlike the native crash in the CVE), so this is not remote code execution. However, if the degenerate arithmetic state becomes persistent for the pool, `Withdraw` and `WithdrawPnl` become permanently unusable for that pool, which constitutes freezing of LP funds already deposited — they cannot be redeemed. This satisfies the "permanent freezing of user or LP funds" impact bar.

### Likelihood Explanation
Reaching the exact zero/underflow condition requires precise conditions on `need_take_pnl_pc`/`need_take_pnl_coin` versus vault balances and decimal normalization rounding, and I could not empirically confirm (within the available tooling) a concrete sequence of Deposit/Withdraw/Swap instructions that drives `x1` or `y1` to exactly zero or causes `x2 > x1`/`y2 > y1` in practice — the fee/pnl accounting includes several rounding and `saturating_sub` steps elsewhere that may make the degenerate state unreachable in the normal instruction flow. This uncertainty means the likelihood is moderate-to-speculative rather than confirmed; a full proof-of-concept would require running the on-chain program with a crafted state sequence, which is outside what I can verify via static code search alone.

### Recommendation
Replace all bare `.unwrap()` calls in `calc_x_power`, `calc_take_pnl`, and related decimal-normalization helpers in `program/src/math.rs` and `program/src/processor.rs` with `.ok_or(AmmError::...)?` propagation, and explicitly guard against `x1 == 0`/`y1 == 0` and `x2 > x1`/`y2 > y1` before performing the subtraction/division, returning a defined `AmmError` instead of panicking.

### Proof of Concept
Not established with certainty. I identified the unchecked-arithmetic code paths (`calc_x_power`'s division by `current_y`, and `calc_take_pnl`'s division by `x1` and subtractions of `x2`/`y2`) that lack `checked_*` error handling and are reachable from permissionless `Deposit`/`Withdraw`/`WithdrawPnl` instructions, but I could not confirm within the indexed code a concrete instruction sequence that drives the pool state to the exact degenerate values needed to trigger the panic. This would need to be validated with a running test harness (unit tests such as `test_calc_take_pnl` / `test_calc_pnl_precision` in `program/src/processor.rs:3057-3212` show the intended normal-path behavior but do not test the zero/underflow edge cases).         // must be use u256, because u128 may be overflow
        let x_power = last_x

        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {

            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
