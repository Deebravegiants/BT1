## Title
Webhook `shop`, `topic`, and `webhook_id` headers are trusted for tenant/handler attribution without being covered by the HMAC signature — cross-tenant webhook spoofing (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers that are never included in the signed material. `ShopifyAPI::Webhooks::Registry.process` validates only the body HMAC and then unconditionally trusts `request.shop` and `request.topic` to dispatch the payload to a handler and attribute it to a merchant. This breaks the intended binding: `verified_bytes == attributed_tenant/handler`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are pulled from headers that are excluded from that signable string: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `verifiable_query.to_signable_string` (i.e., the body): [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.topic` for handler dispatch and `request.shop` for tenant attribution in the data passed to the app's handler, with no cross-check that these header values were part of what was actually authenticated: [4](#0-3) 

Because Shopify apps share a single `api_secret_key` across all installations of the app (it is the app's client secret, not a per-shop secret), any party who can obtain one valid `(raw_body, hmac)` pair for the app — for example by installing the app on their own store and observing a real webhook delivery — possesses a signature that remains valid for that exact body regardless of which `shop-domain`/`topic`/`webhook-id` headers accompany it. The equality the library should enforce is:

`hmac_valid(raw_body) ⇒ (shop header, topic header) are the ones Shopify actually sent for that body`

but the library only proves `hmac_valid(raw_body)` and separately, unauthenticated, trusts the `shop-domain` and `topic` headers.

### Impact Explanation
An attacker who legitimately installs the target app on their own (attacker-controlled) shop can capture a real, validly-signed webhook body/HMAC pair delivered to their own store. They can then submit that same raw body and HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim merchant's domain (and/or `x-shopify-topic` with a different registered topic). Because `Registry.process` never verifies that the `shop`/`topic` headers were part of the signed content, the request passes HMAC validation and is dispatched to the handler with `WebhookMetadata.shop` set to the victim's shop and/or routed to a different handler than Shopify intended. This is a cross-tenant attribution bypass: the host application built on this gem's webhook processing primitive receives merchant-attributed data that did not actually originate from, or was not verified for, that merchant.

### Likelihood Explanation
The attacker only needs the ability to install the app on a shop they control (any unprivileged developer/merchant can do this for public or unlisted apps) and to send an HTTP POST to the app's public webhook endpoint with attacker-chosen headers — no access token, API secret, or privileged account is required.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signable content (or otherwise cryptographically bind them to the verified payload) before `Registry.process` uses them for tenant attribution and handler dispatch, or require the host application to independently verify `request.shop` against a known/authorized shop list before trusting `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, triggering a real webhook (e.g., `orders/create`) with body `B` and Shopify-computed header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(api_secret_key, B)`, per `HmacValidator.compute_signature`, `lib/shopify_api/utils/hmac_validator.rb:33-40`).
2. Attacker replays this request to the app's webhook endpoint but rewrites `x-shopify-shop-domain: victim-shop.myshopify.com` (headers are otherwise untouched, body `B` and `hmac H` unchanged).
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim-shop.myshopify.com", hmac-sha256: H...})` builds successfully — only presence of headers is checked, not cross-binding (`lib/shopify_api/webhooks/request.rb:45-63`).
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, B)` and compares to `H` — it matches, since `B` and `H` are unchanged (`lib/shopify_api/utils/hmac_validator.rb:13-22`, `lib/shopify_api/webhooks/registry.rb:190`).
5. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: ..., ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the host app to process attacker-supplied content as if it were authenticated data from the victim's shop.
