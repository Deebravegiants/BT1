### Title
Webhook `shop` identity is not bound to the HMAC signature, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and `ShopifyAPI::Utils::HmacValidator.validate` verifies the HMAC exclusively over that body. The `shop` value that `ShopifyAPI::Webhooks::Registry.process` hands to the app's handler is read straight from the `x-shopify-shop-domain` HTTP header, which is completely outside the HMAC-covered bytes. This breaks the identity binding `verified_bytes == bytes_the_handler_trusts_as_tenant`: a payload can be cryptographically valid (signed with the app's shared `client_secret`) while its declared shop is attacker-chosen.

### Finding Description
- `Request#to_signable_string` only returns `@raw_body`: [1](#0-0) 
- `Request#shop` is read from an unauthenticated header, not from anything inside the signed body: [2](#0-1) 
- `HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string` (i.e., the body), never the headers: [3](#0-2) 
- `Registry.process` validates the HMAC and then immediately forwards the unauthenticated `request.shop` to the handler as if it were trusted tenant identity: [4](#0-3) 
- The documented usage pattern explicitly instructs apps to key their per-tenant processing (e.g., job dispatch, DB writes) off `data.shop`: [5](#0-4) 

Because the webhook HMAC secret (`Context.api_secret_key`, the app's `client_secret`) is the same for every shop that has the app installed, a `(raw_body, hmac)` pair that is valid for one shop's genuine webhook is *also* a valid HMAC pair when replayed with a different `x-shopify-shop-domain` header — the gem never checks that the header matches anything the signature covers. This is the exact bug class identified in the report (a field that is acted upon — here, the tenant identifier used by the handler — but not covered by the authenticity check), applied to the identity binding `shop_used_by_handler == shop_that_actually_sent_the_request`.

### Impact Explanation
Any internet user who can obtain a single genuine, validly-HMAC'd webhook body for the target app (trivially available to anyone who installs the app on their own store/dev shop, since the shared secret is the app's `client_secret`, not per-shop) can replay that exact body to the app's webhook endpoint with a forged `x-shopify-shop-domain` header naming a victim shop. `HmacValidator.validate` still returns `true` because it only checks the body bytes, and `Registry.process` passes the forged shop straight to the app's handler as `WebhookMetadata#shop`. Per the gem's own documented usage, this value is used to select which tenant's data/job/session gets acted on. This constitutes cross-tenant data injection/corruption — attacker-controlled data attributed to and processed under a victim merchant's identity — which maps to Critical: cross-tenant access.

### Likelihood Explanation
Requires only: (1) ability to install/trial the app on an attacker-controlled shop to obtain one legitimate `(raw_body, hmac)` sample (no privileged credentials, access tokens, or `api_secret_key` needed), and (2) sending a forged HTTP request to the app's public webhook endpoint. No interaction with the victim or possession of victim secrets is required.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the material verified by the HMAC, or independently authenticate the shop domain against the session/shop the app expects for that endpoint before trusting `WebhookMetadata#shop`. At minimum, `ShopifyAPI::Webhooks::Registry.process` should cross-check `request.shop` against an expected/known shop (e.g., the shop tied to the webhook subscription or the shop derived from a signed source) rather than treating the raw header as trusted identity.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a genuine webhook, capturing `raw_body` and the `x-shopify-hmac-sha256` header value.
2. Attacker POSTs to the app's webhook endpoint with the same `raw_body`/`hmac` header but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the HMAC: [6](#0-5) 
4. The app's handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker-controlled>, ...)` and performs tenant-scoped work (per the documented pattern) under the victim's identity, even though the request never actually originated from Shopify on behalf of that shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
