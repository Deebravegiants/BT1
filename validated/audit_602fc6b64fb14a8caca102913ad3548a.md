### Title
Unguarded fee-refund transfer in `EvmHost.dispatchTimeOut()` lets one blacklisted `payer`/`meta.sender` permanently DoS batched timeout delivery for all other users - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatchTimeOut()` (both the `PostRequestTimeout` and `GetRequestTimeout` overloads) refunds the relayer fee to `meta.sender` with a bare `safeTransfer`, outside of the success-checked low-level call that protects the app callback. `HandlerV2.handlePostRequestTimeouts` / `handleGetRequestTimeouts` invoke `host.dispatchTimeOut(...)` in an unguarded `for` loop over a batch of timeouts. If any single request's `payer` is (or becomes) blacklisted on `feeToken()` (e.g. USDC-style tokens), that one revert propagates out of the loop and reverts the *entire batch*, blocking delivery of every other unrelated request's timeout in that transaction. This is the same bug class as the PoolTogether `RngRelayAuction.rngComplete()` finding — a direct, unguarded token transfer to an attacker-influenceable address inside a multi-item settlement loop — but here it is worse because it blocks arbitrary third parties' timeout refunds, not just the attacker's own reward.

### Finding Description
`dispatch(DispatchPost memory post)` lets the caller set an arbitrary `payer` address that will later receive the fee refund on timeout: [1](#0-0) 

When a request times out, `EvmHost.dispatchTimeOut(PostRequestTimeout, ...)` first safely invokes the app's `onPostRequestTimeout` via a checked low-level `.call` (failures here are caught and retried), but then unconditionally calls `IERC20(feeToken()).safeTransfer(meta.sender, meta.fee)` with no try/catch: [2](#0-1) 

The `GetRequestTimeout` overload has the identical pattern: [3](#0-2) 

Both are called from `HandlerV2` inside unguarded loops that process a whole batch of timeouts in a single transaction: [4](#0-3) [5](#0-4) 

If `feeToken()` is a token with a blacklist mechanism (USDC-style) and any single request's recorded `payer` (`meta.sender`) is on that blacklist, the `safeTransfer` call reverts. Because the call site in `HandlerV2` has no try/catch around `host.dispatchTimeOut(...)`, this revert bubbles up and reverts the *whole* `handlePostRequestTimeouts`/`handleGetRequestTimeouts` transaction — including timeouts for completely unrelated requests bundled in the same proof/batch.

### Impact Explanation
Any account (attacker) can dispatch a low-value POST or GET request with `fee > 0` and `payer` set to an address they control that is presently, or can be made, blacklisted on the configured `feeToken`. Once that request times out, it becomes a permanent poison pill: any relayer that includes it in a batched `handlePostRequestTimeouts`/`handleGetRequestTimeouts` call will have their entire transaction revert, denying timeout-refund delivery for every other unrelated request bundled alongside it. This is a griefing/DoS vector against the relayer network's batching path that can stall legitimate users' fee refunds and request-timeout state transitions indefinitely unless every relayer's software is specially hardened to detect and permanently exclude the poisoned commitment from all future batches — a real permanent-freezing-of-funds/availability risk for the affected commitments and a broad throughput/availability risk for the batch-timeout delivery path.

### Likelihood Explanation
Likelihood is high: dispatching a request with a self-chosen `payer` costs only the relayer fee and gas, requires no privileged role, and the USDC (or similar) blacklist status is entirely at the attacker's own discretion (self-blacklist is not required by USDC's issuer — but any already-blacklisted address, or an address later blacklisted for unrelated reasons such as by the token issuer or a sanctions list, is fully sufficient). Relayers naturally batch multiple pending timeouts together for gas efficiency, making accidental co-bundling with a poisoned request likely absent specific mitigation.

### Recommendation
Wrap the fee-refund transfer in `dispatchTimeOut` (both overloads) and the reward transfer in `dispatchIncoming(GetResponse, ...)` in a try/catch (or a low-level `.call` with a success check), mirroring the pattern already used for the `IApp` callback. On failure, credit the amount to a per-user claimable balance (`claimable[token][user] += amount`) that the affected party can withdraw independently via a separate `claim()` function, rather than pushing the transfer inline inside a batch-processing loop.

### Proof of Concept
1. Attacker calls `EvmHost.dispatch(DispatchPost{... fee: X, payer: BLACKLISTED_ADDR, timeout: T})`, setting `payer` to an address already on the fee token's blacklist (or one they can get blacklisted).
2. The request is delivered or times out; a relayer collects a non-membership proof and calls `HandlerV2.handlePostRequestTimeouts(host, message)` where `message.timeouts` bundles this poisoned request together with N other unrelated, legitimate timed-out requests.
3. Inside the loop, `host.dispatchTimeOut(...)` is invoked for the poisoned request; `IERC20(feeToken()).safeTransfer(meta.sender, meta.fee)` reverts because `meta.sender` is blacklisted.
4. The revert is not caught anywhere in `handlePostRequestTimeouts`, so the entire transaction reverts, and none of the N legitimate requests receive their timeout processing/refund in this batch.
5. Any relayer that keeps including the poisoned commitment in future batches will keep failing; relayers must manually detect and isolate it, effectively DoSing batched timeout delivery until specifically hardened.

    function dispatchTimeOut(
        GetRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onGetTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit GetRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }

    function handlePostRequestTimeouts(IHost host, PostRequestTimeoutMessage calldata message)
        external
        notFrozen(host)
    {
        uint256 delay = block.timestamp - host.stateMachineCommitmentUpdateTime(message.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        // fetch the state commitment
        StateCommitment memory state = host.stateMachineCommitment(message.height);
        if (state.stateRoot == bytes32(0)) revert StateCommitmentNotFound();
        uint256 timeoutsLength = message.timeouts.length;

        for (uint256 i = 0; i < timeoutsLength; ++i) {
            PostRequest memory request = message.timeouts[i];
            // timed-out?
            if (request.timeout() > state.timestamp) revert MessageNotTimedOut();

            // known request? also serves as source check
            bytes32 requestCommitment = request.hash();
            FeeMetadata memory meta = host.requestCommitments(requestCommitment);
            if (meta.sender == address(0)) revert UnknownMessage();

            bytes[] memory keys = new bytes[](1);
            keys[0] = bytes.concat(REQUEST_RECEIPTS_STORAGE_PREFIX, requestCommitment);

            // verify state trie non-membership proofs
            PolkadotTrie.StorageValue memory entry = PolkadotTrie.VerifyProof(state.stateRoot, message.proof, keys)[0];
            if (entry.value.length != 0) revert InvalidProof();

            host.dispatchTimeOut(PostRequestTimeout(request, _msgSender()), meta, requestCommitment);
        }
    }
