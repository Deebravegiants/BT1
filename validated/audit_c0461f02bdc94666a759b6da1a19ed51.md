### Title
Webhook `shop` identity is taken from an unauthenticated header not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw HTTP body, while the `shop` value that is handed to the application's webhook handler is read straight from the `x-shopify-shop-domain` / `shopify-shop-domain` header, which is never included in the HMAC-covered bytes.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is a completely separate accessor pulled from an HTTP header: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC using `verifiable_query.to_signable_string` (the body) and the app's single `api_secret_key`, and compares it against the `hmac` header value: [3](#0-2) 

`Registry.process` only checks this body HMAC before dispatching to the handler, and then builds `WebhookMetadata` using `request.shop` verbatim, with no cross-check that the signed body actually originated for that shop: [4](#0-3) 

The `shop` field is explicitly documented as trustworthy tenant-identifying data that host apps use to route/attribute the webhook (e.g. `shop_domain: data.shop`): [5](#0-4) 

Because the same `api_secret_key` is shared across all shops that installed the app, and the HMAC never binds the `shop` header to the body, the equality the gem implicitly assumes — `shop delivered in the header == shop that produced the HMAC-signed body` — is not enforced anywhere. Any user who can get the app installed on a shop they control (an ordinary, unprivileged merchant relative to other tenants of the same app) can capture one legitimately HMAC-signed webhook body from their own shop, then resend that exact body/HMAC pair to the app's webhook endpoint with the `x-shopify-shop-domain` header swapped to an arbitrary victim shop. `Utils::HmacValidator.validate` will still return `true` because it only checks body bytes against the shared secret, and `Registry.process` will call the app's handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop.

### Impact Explanation
This breaks the tenant boundary the gem is expected to guarantee to consuming applications: "this webhook body was produced by shop X." A host application that uses `data.shop` (as the gem's own documentation instructs) to look up a per-shop session/access token, write per-tenant records, or gate per-shop business logic will process attacker-controlled body content under an arbitrary victim shop's identity — a cross-tenant data integrity/confusion issue reachable by any app-installing user without needing the `api_secret_key`, an access token, or any privileged account.

### Likelihood Explanation
Exploitation only requires the ability to install the target app on a shop the attacker controls (the normal, unprivileged way any merchant uses a Shopify app) and the ability to send an HTTP POST to the app's public webhook endpoint with a modified header — no secret material, session, or elevated privilege is needed. The header is fully attacker-controlled and is never bound to the signed payload, so the bypass is deterministic once the attacker has one legitimately signed body from their own shop.

### Recommendation
Bind the `shop` (and ideally `topic`/`api_version`) to the HMAC-verified material, e.g. by including the `shop`, `topic`, and `webhook_id` headers in the signable string, or by requiring the host application to independently verify that `request.shop` matches the tenant the current handler invocation is scoped to before trusting it. At minimum, document/enforce that `data.shop` must never be used as the sole authorization key for tenant-scoped operations without an additional binding to the signed body.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`) to their own registered endpoint, capturing the raw request body `B` and the valid `x-shopify-hmac-sha256` header `H` computed over `B` with the app's shared `api_secret_key`.
2. Attacker replays a POST to the app's public webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged), but `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `H` against `B` — this passes because `to_signable_string` never includes the shop header: [6](#0-5) 
4. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's orders/create payload>, ...)`, causing the application to attribute attacker-controlled data to `victim-shop`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
