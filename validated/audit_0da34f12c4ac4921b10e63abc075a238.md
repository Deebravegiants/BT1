### Title
Cross-key ciphertext replay bypasses per-key binding in `@exodus/storage-encrypted` due to `key` being ignored by `encrypt`/`decrypt` - ([File: adapters/storage-encrypted/src/storage.ts])

### Summary
`transformOnWrite`/`transformOnRead` in `adapters/storage-encrypted/src/storage.ts` call `encrypt(Buffer.from(wrapped))` and `decrypt(ciphertext)` without ever passing the storage `key` into the cipher call, even though `@exodus/transform-storage`'s `transformOnRead`/`transformOnWrite` do forward `key` as a parameter. Because a single wallet-wide `SodiumEncryptor` secretbox key (e.g. `WALLET_INFO`) is used for every logical key in a given namespace, a ciphertext produced for one storage key decrypts successfully and is returned as valid data under any other storage key sharing the same underlying `unsafeStorage`/encryptor.

### Finding Description
`transformStorage` (libraries/transform-storage/src/transform.ts, lines 25-56) passes `key` into both `onRead`/`onWrite` callbacks and into `get`/`set`/`batchGet`/`batchSet`. `createStorageEncrypted` (adapters/storage-encrypted/src/storage.ts, lines 35-62) supplies these callbacks but discards `key` entirely: [1](#0-0) 

`transformOnWrite` only stringifies the value and calls `encrypt(Buffer.from(wrapped))` — no AAD, nonce derivation, or key-binding tied to the storage key. `transformOnRead` receives `key` only for logging purposes (`swallowDecryptionErrors` warn message) and calls `decrypt(ciphertext)` unconditionally, with no check that the ciphertext "belongs" to `key`.

The encryptor itself (`features/keychain/module/crypto/sodium.js`, `encryptSecretBox`/`decryptSecretBox`) derives its secret purely from `(seedId, keyId)` — i.e., a single symmetric key per wallet-info key-id, shared across every storage key in that namespace: [2](#0-1) 

The README for `@exodus/storage-encrypted` confirms that a single `cryptoFunctions.encrypt/decrypt` pair (bound to one `keyId`, e.g. `WALLET_INFO`) is shared for the whole namespace's storage instance: [3](#0-2) 

Given the precondition stated in the question (attacker can write/copy a raw ciphertext string in `unsafeStorage` between two logical keys, e.g. via a namespace collision or a storage adapter allowing raw copy without going through `transformStorage.set`), the flow `unsafeStorage.set('keyB', ciphertextFromKeyA)` → `transformStorage.get('keyB')` → `transformOnRead(ciphertext, 'keyB')` will successfully decrypt because `decrypt()` has no way to validate that the ciphertext was originally produced for `'keyA'` vs `'keyB'`. There is no AAD binding the key name (or account/origin identity) into the ciphertext, so `ACCOUNT_SCOPING`/`ORIGIN_SCOPING` enforced only by storage-key naming convention (e.g. `'accountA:approvedOrigin'` vs `'accountB:approvedOrigin'`) is purely logical, not cryptographic.

### Impact Explanation
If any code path in the wallet allows an unprivileged attacker to copy a raw ciphertext value from one logical storage key to another within the same encrypted namespace (e.g., a bug in a namespacing/storage adapter, or a batchSet/import/migration path that doesn't go through the encrypted `transformStorage.set`), the attacker could make consent/lock-state data (e.g., `approvedOrigin` for one account, or `lockState`) validate successfully under a different key, causing cross-account/cross-origin consent or lock-state confusion. This matches "wrong-account/origin access" impact class in principle.

However, this is a latent design weakness in `@exodus/storage-encrypted`, not by itself a demonstrated live exploit: the question's own precondition — "attacker can write/copy a raw value in the underlying `unsafeStorage` between two logical keys without going through `transformStorage.set`" — is an assumed capability, not one shown to be reachable from an ordinary dapp/origin/deeplink/RPC input in this codebase. I found no concrete evidence in the indexed code of `connected-origins`, `approvedOrigin`, or `lockState` modules exposing a raw-copy/write-arbitrary-key primitive to an unprivileged origin. The `namespace()` prefixing scheme (`libraries/browser-extension-adapters/unsafe-storage/storage.js`, `adapters/storage-enhancers/namespacing.js`) explicitly guards against `!`-injection to prevent namespace collisions, which is the most obvious way an attacker-controlled string could cross namespace boundaries.

### Likelihood Explanation
Low, absent a separately-demonstrated primitive that lets an unprivileged actor write/copy raw values across storage keys. The vulnerability is real as a cryptographic design gap (no AAD/key binding), confirmed directly in the encrypted storage adapter code, but exploitability depends entirely on an attacker already possessing write access to `unsafeStorage` at an arbitrary key of their choosing without going through normal API/consent flows — a precondition not established as reachable via ordinary dapp/origin requests in this codebase.

### Recommendation
Bind the storage key (and ideally account/origin identity) into the ciphertext as authenticated associated data or by mixing it into a per-key derived nonce, so `encrypt`/`decrypt` in `adapters/storage-encrypted/src/storage.ts` reject ciphertext moved to a different logical key. Concretely, thread `key` through to `cryptoFunctions.encrypt(data, { aad: key })` / `decrypt(ciphertext, { aad: key })`, and update `SodiumEncryptor.encryptSecretBox`/`decryptSecretBox` to support AAD (e.g. via a secretbox construction using key as part of the nonce or as authenticated data), then verify AAD mismatch throws a "wrong key" error on read.

### Proof of Concept
Unit test in `adapters/storage-encrypted/test/index.spec.ts` style:
1. Instantiate `createStorageEncrypted({ storage: inMemoryStorage, cryptoFunctionsPromise })` with a real `sodiumEncryptor` bound to a single `seedId`/`keyId`.
2. `await storage.set('accountA:approvedOrigin', { origin: 'evil.com', approved: true })`.
3. Read the raw ciphertext directly: `const raw = await inMemoryStorage.get('accountA:approvedOrigin')`.
4. Copy it to a different key in the raw store: `await inMemoryStorage.set('accountB:approvedOrigin', raw)`.
5. `const result = await storage.get('accountB:approvedOrigin')`.
6. Assert: currently `result` resolves successfully to `{ origin: 'evil.com', approved: true }` instead of throwing a "wrong key"/AAD-mismatch error — demonstrating the ciphertext is not bound to its logical key.

  const transformOnRead = async (ciphertextB64: string | undefined, key: string) => {
    const { decrypt } = await cryptoFunctions
    if (!ciphertextB64) return

    const ciphertext = Buffer.from(ciphertextB64, 'base64')
    let decrypted
    try {
      decrypted = await decrypt(ciphertext)
    } catch (err) {
      if (swallowDecryptionErrors && isDecryptionError(err as Error)) {
        logger.warn(`Failed to decrypt value for key: ${key}`, err)
        return
      }

      throw err
    }

    return JSON.parse(decrypted.toString())
  }
