### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, and `Utils::HmacValidator` verifies the HMAC solely against that body. The `shop-domain` header, which `Registry.process` uses to attribute the webhook to a specific merchant/tenant, is never part of the signed material. An attacker who legitimately owns one shop that the app is installed on can replay their own genuinely-signed webhook body/HMAC pair while swapping the `x-shopify-shop-domain` (or `shopify-shop-domain`) header to any other shop, and the library will accept it as valid and hand it to the handler as if it originated from the spoofed tenant.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

only the `@raw_body` is signed. The `shop` accessor is read straight from an unauthenticated header with no cryptographic binding to the HMAC: [2](#0-1) 

`Registry.process` validates the HMAC and then trusts `request.shop` for dispatch without any additional check that it matches the tenant the signature was actually generated for: [3](#0-2) 

Because the app's `client_secret`/`api_secret_key` is shared across every shop that has the app installed, any merchant who installs the app can trigger a real, validly-signed webhook delivery to their own endpoint (e.g. by updating an order in their own store). They can then capture that `raw_body` + `x-shopify-hmac-sha256` pair and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` re-computes the HMAC only over `to_signable_string` (the body), so the signature still checks out even though the `shop` value has been altered — the identity binding `HMAC-covered bytes == data acted on by the handler` is broken specifically for the `shop` field.

This is the "field acted on but not covered by the HMAC" bug class described in the report, applied to the tenant-identifying header rather than a numeric amount.

### Impact Explanation
Any handler that uses `WebhookMetadata#shop` (constructed directly from `request.shop`, see `lib/shopify_api/webhooks/registry.rb:198`) to select which merchant's data/session to update is exposed to cross-tenant data confusion/injection: an attacker-controlled event body can be delivered under a victim shop's identity. Depending on how the consuming application persists or reacts to webhook data keyed by `shop`, this can result in writing attacker-supplied data into another tenant's records — a cross-tenant access issue.

### Likelihood Explanation
The attacker only needs to be a legitimate (even trial/free) installer of the app to obtain one authentically-signed webhook body/HMAC pair for their own shop, which they can then replay with a different `shop-domain` header value. No access to `api_secret_key`, access tokens, or any privileged credential is required — only network access to the app's public webhook endpoint. This satisfies the "unprivileged internet user" threat model.

### Recommendation
Include the tenant-identifying header (`shop-domain`) in the signable material used for HMAC verification, or otherwise cryptographically bind it before dispatch — e.g., require callers to separately verify `request.shop` against a registered/known shop for the session before trusting it, and document this expectation prominently. At minimum, `Registry.process` should not treat `request.shop` as authenticated purely because the body-only HMAC passed; the gem should either sign the shop domain as part of the verifiable payload or expose an explicit API for callers to cross-check the shop against their own tenant registry before invoking the handler.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`. Attacker triggers a real webhook (e.g., `orders/create`) to their own registered endpoint, capturing the raw body and the `x-shopify-hmac-sha256` header Shopify computed with the app's shared secret.
2. Attacker POSTs the exact same body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the request; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the (unchanged) raw body against the secret: [4](#0-3) 
4. `Registry.process` then invokes `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` with `shop == "victim-shop.myshopify.com"`, even though the body/content was never generated for, nor authorized by, that shop.
