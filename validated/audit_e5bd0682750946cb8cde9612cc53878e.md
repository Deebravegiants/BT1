### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing shop-identity spoofing on replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then hands the handler a `shop` value taken directly from an unauthenticated HTTP header. The HMAC binding does not cover the shop identity, so the value the host application uses to determine "which tenant does this event belong to" is not the value that was actually verified.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header with no cryptographic binding to the signed payload: [2](#0-1) [3](#0-2) 

`Registry.process` validates only the HMAC (over the body) and then constructs `WebhookMetadata` using `request.shop`, which is passed unchanged to the app's handler: [4](#0-3) 

The identity binding the gem should be enforcing is:
`shop authenticated by HMAC == shop value used to route/attribute the webhook event`

Because the HMAC is computed over `@raw_body` alone, this equality never actually holds — the `shop` field that host applications rely on (`data.shop` in `WebhookMetadata`) is fully attacker-controllable at the header level for any request that carries a body/HMAC pair the attacker has previously observed (e.g., captured from a legitimate webhook delivery, a shared proxy/CDN log, or any party positioned to see one genuine webhook). Replaying that same body+HMAC pair with a modified `shopify-shop-domain` header passes `Utils::HmacValidator.validate` (which only checks the body) unmodified, while the handler receives an attacker-chosen `shop`.

### Impact Explanation
If a host application uses `WebhookMetadata#shop` (as returned by this gem) to select which merchant/tenant record to update, delete, or read (a documented, intended use of this field), an attacker who can produce or replay one valid body+HMAC pair can cause the event to be attributed to a different shop than the one that actually sent it. This is a cross-tenant identity-confusion primitive rooted entirely in this gem's verification logic (the HMAC binding excludes the field the API surfaces as authoritative), not a misuse of an undocumented feature — `shop` is a first-class, documented accessor on `WebhookMetadata`/`Request`.

### Likelihood Explanation
Exploitation requires an attacker to have observed one legitimate raw_body+HMAC pair for any shop (a low bar in many deployments: logging systems, HTTP proxies, CDNs, or a shop the attacker controls) and to be able to deliver a crafted request to the app's webhook endpoint with a different `shop-domain` header — no secret is required. This is a moderate-likelihood, self-contained gap in the library's authentication design rather than a theoretical concern.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) header values into the value verified by HMAC, or otherwise document loudly that `Request#shop` is unauthenticated and must never be trusted for tenant attribution without an independent lookup (e.g., cross-checking against a known/registered shop record) before use.

### Proof of Concept
1. Attacker captures a legitimate webhook delivery for `shop-a.myshopify.com`: raw body `B` and its valid `x-shopify-hmac-sha256` header `H` (computed by Shopify over `B` with the app's secret).
2. Attacker replays a POST to the app's webhook endpoint with the same body `B` and header `H`, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B) == H` — this still passes. [5](#0-4) 
4. `WebhookMetadata.new(... shop: request.shop ...)` is built with `shop == "shop-b.myshopify.com"`, and the registered handler executes as if the event originated from `shop-b`, even though it never did.
