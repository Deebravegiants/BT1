## Title
Webhook Shop/Topic Identity Spoofing via HMAC That Only Covers Raw Body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw request body only, while the `shop`, `topic`, and `webhook_id` values used downstream by `ShopifyAPI::Webhooks::Registry.process` are read directly from unauthenticated HTTP headers. Because these identity fields are never included in the HMAC computation, an attacker who can obtain any one valid `(body, hmac)` pair signed with the app's real secret (e.g. from a genuine webhook delivered for their own installed test shop) can replay that exact body/hmac to the app's public webhook endpoint while freely rewriting the `X-Shopify-Shop-Domain` and `X-Shopify-Topic` headers to impersonate a different shop and/or topic.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, and `webhook_id` are pulled straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`HmacValidator.validate` verifies only `verifiable_query.to_signable_string` against `verifiable_query.hmac`: [3](#0-2) 

`Registry.process` trusts `request.shop` and `request.topic` as authenticated identity once the HMAC check passes, and forwards them into the handler without any further binding check (e.g. verifying the shop matches an installed/known shop, or that the webhook_id/topic combination was actually registered for that specific shop): [4](#0-3) 

The equality that should hold is: `shop header value == shop that produced the signed body`. Since the HMAC signs only the body bytes, this equality is never checked — the gem verifies "bytes(body) are authentic" but the application (following the documented usage pattern in `docs/usage/webhooks.md`) acts on "this shop sent these bytes," which is a broader, unverified claim.

### Impact Explanation
This breaks the tenant binding between the cryptographically verified payload and the shop identity the host application acts upon. An attacker who has captured (or can generate, e.g. by installing the app on their own free/dev shop and triggering an event with attacker-controlled data such as a product title/body) one valid `(raw_body, hmac)` pair can resend that exact pair to the app's public webhook URL with a forged `x-shopify-shop-domain` header naming any victim shop, and the forged `x-shopify-topic`/`x-shopify-webhook-id` headers of their choosing. `HmacValidator.validate` will pass because it only checks the body bytes against the shared secret, and `Registry.process` will dispatch the attacker-controlled body to the handler tagged as belonging to the victim shop and topic. This is a cross-tenant data-integrity/impersonation vector: any downstream logic that trusts `WebhookMetadata#shop` (e.g., updating merchant-scoped records, triggering redaction/compliance flows, invalidating merchant data) can be triggered for a shop the attacker does not control, using attacker-chosen body content.

### Likelihood Explanation
Exploitation requires only network access to the app's public webhook endpoint and possession of one legitimately-signed `(body, hmac)` pair, which is trivially obtainable by any developer/attacker who installs the app on a free development store and lets Shopify deliver a genuine webhook for an event whose body content they control (e.g. product/collection title, order note, page content). No possession of `client_secret`, access tokens, or privileged accounts is required — this fits the "unprivileged internet user" threat model.

### Recommendation
Bind the shop identity (and ideally topic/webhook id) into the verified signature domain rather than trusting raw headers post-hoc:
- Require the host application to cross-check `request.shop` against a known/installed-shop list before acting (document this explicitly), and/or
- Extend `to_signable_string` / add an additional check in `Registry.process` that ties `webhook_id` to a previously registered `(shop, topic)` pair recorded at registration time, rejecting mismatches.
- At minimum, document loudly in `webhooks.md` that `data.shop`/`data.topic` are NOT covered by the HMAC and must be independently validated by the host app against its own tenant store before use.

### Proof of Concept
1. Attacker installs the target app on their own Shopify development store (`attacker.myshopify.com`) and grants it the webhook-eligible scope.
2. Attacker triggers a genuine webhook event with attacker-chosen body content (e.g., updates a product title to arbitrary JSON-safe content), causing Shopify to deliver a real webhook: `raw_body = B`, `X-Shopify-Hmac-Sha256 = HMAC(secret, B)`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: products/update`.
3. Attacker captures this exact `(B, hmac)` pair (available client-side/log-side since it's their own store).
4. Attacker sends a new POST directly to the victim app's public webhook route with the same `raw_body = B` and `X-Shopify-Hmac-Sha256` header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and any `X-Shopify-Topic`/`X-Shopify-Webhook-Id` of choice.
5. `HmacValidator.validate` in [5](#0-4)  succeeds because it only recomputes the HMAC over `B`.
6. `Registry.process` in [4](#0-3)  dispatches the handler with `shop: "victim-shop.myshopify.com"` and attacker-controlled body `B`, even though `victim-shop` never sent this webhook.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
