### Title
Webhook `shop` header is not covered by the HMAC signature, allowing cross-tenant shop-domain spoofing in `ShopifyAPI::Webhooks::Registry.process` - (File: lib/shopify_api/webhooks/registry.rb, lib/shopify_api/webhooks/request.rb, lib/shopify_api/utils/hmac_validator.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the `shop` value taken from an HTTP header (`x-shopify-shop-domain`/`shopify-shop-domain`) that is never included in the signed material, and passes that header value to the app's handler as the tenant identifier.

### Finding Description
`Registry.process` calls `Utils::HmacValidator.validate(request)` before dispatching to the handler: [1](#0-0) 

`HmacValidator.validate` verifies the HMAC using `verifiable_query.to_signable_string`, which for `Webhooks::Request` is defined to be only the raw body: [2](#0-1) [3](#0-2) 

The `shop` accessor, however, is read directly from an HTTP header and is never part of `to_signable_string`, so it is completely outside the cryptographic binding: [4](#0-3) 

`Registry.process` nonetheless forwards this unauthenticated `request.shop` straight into `WebhookMetadata`, which the app-supplied handler receives as the authoritative tenant/shop identifier for the event: [5](#0-4) [6](#0-5) 

The gem's own documentation instructs integrators to use `data.shop` as the shop-domain key for downstream processing (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), confirming that the gem presents `shop` as a value that has been authenticated by `Registry.process`: [7](#0-6) 

The binding that should hold is: `shop header value == shop that produced/authorized the signed HMAC body`. Because the HMAC only covers the raw body, an attacker who controls a legitimate shop (and can therefore obtain validly-HMAC-signed webhook deliveries for that shop, or otherwise control the raw bytes reaching the endpoint while keeping a body they can compute a valid HMAC for) can submit a request with the same/any valid `(body, hmac)` pair while substituting an arbitrary value in the `x-shopify-shop-domain` header. `Registry.process` will accept it as valid (`Utils::HmacValidator.validate` only checks body vs. hmac) and hand the handler a `WebhookMetadata` claiming to be from a *different* shop than the one that actually authorized the signed payload.

### Impact Explanation
Any app whose webhook handler uses `data.shop` (as the gem's own docs instruct) to key tenant-scoped operations — writing to a shop's record, dispatching background jobs scoped `by shop_domain`, updating per-shop state/counters, or looking up an access token/session for that shop — can have data attributed to, or actions performed against, the wrong tenant. This is a cross-tenant integrity issue: the equality `authenticated_shop == acted_on_shop` is broken because `shop` never enters the HMAC computation. Since the underlying HTTP transport does not TLS-pin the header to Shopify (a reverse proxy, load balancer, or misconfigured header pass-through, or an attacker directly posting to the exposed webhook endpoint with a self-obtained valid HMAC for content they control), the gem provides no verification tying the claimed shop to the signed bytes at all, so the app is left with an identifier it is told (by the API) is trustworthy but which the gem itself does not cryptographically bind.

### Likelihood Explanation
Exploitability depends on the attacker being able to produce a `(body, hmac)` pair the validator accepts (e.g., by owning a real shop from which they can capture/replay a real webhook, or in setups where the webhook endpoint is reachable with attacker-influenced headers independent of Shopify's delivery), while freely varying the `shop` header. Given that `HmacValidator` and `Webhooks::Request` are the only lines of defense and neither considers `shop`, `topic`, or `webhook_id` as signed material, this is a structural gap in the gem's verification logic rather than a theoretical edge case, matching the class of bug described in the report (authenticated bytes vs. trusted-but-uncovered field).

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the value that is cryptographically verified, or explicitly document and enforce that `data.shop` must be re-validated by the caller against the session/shop associated with the delivery. Concretely:
- Extend `Utils::VerifiableQuery`/`Webhooks::Request#to_signable_string` so the signable string incorporates the header-derived `shop` (matching how Shopify actually computes the webhook HMAC, if it does), or
- Have `Registry.process` independently confirm that `request.shop` corresponds to a shop for which the topic/registration is expected, rejecting mismatches, and
- Update `docs/usage/webhooks.md` to warn that `data.shop` is not part of the HMAC-verified payload if that remains the case, so integrators do not treat it as authenticated.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw POST body `B` and the corresponding valid `x-shopify-hmac-sha256` header `H` computed by Shopify over `B` with the app's `client_secret`.
2. Attacker replays the same `(B, H)` pair to the app's webhook endpoint but rewrites the `x-shopify-shop-domain` header to `victim-shop.myshopify.com`.
3. `Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate`, which only recomputes the HMAC over `B` and compares to `H` — validation succeeds because `shop` is not part of `to_signable_string`: [3](#0-2) [8](#0-7) 
4. `Registry.process` invokes the handler with `WebhookMetadata.new(... shop: request.shop ...)`, i.e., `shop: "victim-shop.myshopify.com"`, even though the signed body/content actually originated from `attacker-shop.myshopify.com`: [9](#0-8) 
5. Any handler logic keyed on `data.shop` (per the documented pattern) now operates against `victim-shop.myshopify.com` using attacker-controlled body content, demonstrating the broken binding between the authenticated bytes and the acted-upon tenant.
