### Title
Webhook Shop Identity Not Bound to HMAC Signature Allows Cross-Tenant Webhook Spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates the HMAC signature over the raw request body only, while the `shop` (and `topic`/`api_version`/`webhook_id`) values used to route and process the webhook are taken from unauthenticated HTTP headers that are never included in the signed data. This breaks the identity binding `shop_authenticated == shop_acted_on`, allowing an attacker who obtains one validly-signed webhook body (e.g. from their own shop, since `api_secret_key` is shared by the app across all merchants) to replay it with a forged `shop-domain` header pointing at a victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes/verifies the HMAC exclusively against this signable string: [2](#0-1) 

Meanwhile, `Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all read straight from the request headers, which are not part of the signed payload: [3](#0-2) 

`Registry.process` validates the HMAC and then hands the header-derived `shop` value directly to the handler as authoritative tenant identity, without any additional check that it corresponds to the shop that actually produced/owns the signed body: [4](#0-3) 

Because the app's `api_secret_key` used for HMAC computation is a single, shared per-app secret (not per-shop), a body captured from a legitimate webhook delivered to the attacker's own store — with a valid HMAC — can be replayed to the app's webhook endpoint with the `shopify-shop-domain` (or `x-shopify-shop-domain`) header rewritten to any other merchant's domain. `Utils::HmacValidator.validate` will still pass because it only checks the (unchanged) body against the shared secret; `Registry.process` will then pass `WebhookMetadata` with `shop:` set to the attacker-chosen victim domain to the host application's handler, which typically uses `data.shop` as the tenant key to look up sessions, credentials, or trigger shop-scoped business logic.

This mirrors the report's core bug class: an identity value (public key / shop) that participates in downstream trust decisions is not actually bound by the cryptographic verification (aggregate signature / HMAC) that is supposed to authenticate it.

### Impact Explanation
An unprivileged internet user who controls any single shop that installs the app can capture one legitimately-signed webhook and cross-tenant-spoof it to make the receiving application believe an operation belongs to a different merchant. Depending on how the host app keys logic off `WebhookMetadata#shop` (e.g., session lookup, GDPR/mandatory webhook handling, inventory/order-sync triggers), this enables cross-tenant confusion — the app can be tricked into acting under, or attributing data to, a shop the attacker does not control. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only: (1) installing the app on any shop (achievable by any merchant/attacker), (2) capturing one webhook delivery for that shop, and (3) resending the identical body with a modified `shop-domain` header to the app's public webhook endpoint. No secrets belonging to the victim are needed, and the HMAC check in `Utils::HmacValidator` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) provides no protection because it never covers the `shop` header. This is a low-effort, repeatable attack.

### Recommendation
Include the shop domain (and ideally topic/webhook id) as part of the signed/verified data, or otherwise cryptographically/contextually bind the `shop` value to the verified payload before it is trusted — e.g., have `Utils::HmacValidator`/`Registry.process` cross-check the header-derived shop against an out-of-band source of truth (such as a shop value embedded in the JSON body, when Shopify includes one) rather than trusting the raw header verbatim. At minimum, document that `data.shop` from `WebhookMetadata` must not be trusted for authorization decisions unless independently corroborated.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(api_secret_key, B)`), and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the exact same body `B` and HMAC `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) recomputes HMAC over `B` only — matches `H` — validation passes.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and invokes the host handler, which now processes/acts as if the (attacker-controlled) payload came from the victim shop.
