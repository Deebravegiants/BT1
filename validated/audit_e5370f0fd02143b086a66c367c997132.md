Confirmed: `CallDispatcher.dispatch()` at [1](#0-0) has no access control whatsoever, and this same contract instance is shared as `_params.dispatcher` across every `placeOrder`/`fillOrder` predispatch and postdispatch call in `IntentGatewayV2`/`IntentsBase._execute` [2](#0-1)  and by every `HyperFungibleToken`/`WrappedHyperFungibleToken` deployment's `onAccept` [3](#0-2) . ### Title
Permissionless `CallDispatcher.dispatch()` lets anyone front-run and grief token approvals used by IntentGatewayV2/HyperFungibleToken calldata execution - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher` is a single, shared, unauthenticated contract used as the execution sandbox for every order's `predispatch`/`postdispatch` calldata in `IntentGatewayV2` and for every `HyperFungibleToken`/`WrappedHyperFungibleToken` `onAccept` calldata payload. Its `dispatch(bytes)` function is `external` with no caller restriction, so anyone can invoke it directly with an arbitrary `Call[]` — including `approve()` calls on arbitrary ERC20 tokens to arbitrary spenders, from the `CallDispatcher`'s own address.

### Finding Description
`CallDispatcher.dispatch` is defined as:
```solidity
function dispatch(bytes memory encoded) external {
    Call[] memory calls = abi.decode(encoded, (Call[]));
    ...
    (bool success, bytes memory result) = to.call{value: call.value}(call.data);
    if (!success) revert CallFailed(to, result);
}
``` [4](#0-3) 
There is no `onlyGateway`/`onlyHost`/`msg.sender` check restricting who can call `dispatch`. This same address is the singleton `_params.dispatcher` used by `IntentsBase._execute` for order output calldata (postdispatch) [5](#0-4) , by `IntentGatewayV2.placeOrder` for predispatch calldata [6](#0-5) , and by `HyperFungibleToken`/`WrappedHyperFungibleToken.onAccept` for cross-chain calldata execution [3](#0-2) .

Because it is permissionless, an attacker can directly call `CallDispatcher.dispatch()` to set an `approve(spender, amount)` from the dispatcher's address on any ERC20 token/spender pair before a legitimate order's calldata executes the same `approve()`. Docs explicitly acknowledge orders commonly encode `approve(router, amount)` calls in their `Call[]` for swap-then-escrow/fill-then-swap patterns (e.g. `IERC20.approve.selector, UNISWAP_V2_ROUTER, amount`) [7](#0-6) . For tokens like USDT that reject a non-zero→non-zero allowance change, an attacker's front-run `approve` leaves a stray non-zero allowance on the dispatcher for that token/spender; the victim's subsequent legitimate `approve()` call (embedded in their order's predispatch/postdispatch `Call[]`) then reverts, and since `dispatch` reverts the *entire* batch on any single call failure (`if (!success) revert CallFailed`), the whole order fill/placement transaction reverts.

### Impact Explanation
Because `IntentGatewayV2.dispatch()`-driven predispatch executes before escrow and postdispatch executes as part of `fillOrder`, an attacker can repeatedly front-run and cause the `CallDispatcher` batch to revert for any order whose calldata approves a stray-allowance-sensitive token (e.g. USDT) to a router the attacker has already griefed. This denies the ability to place orders using swap-then-escrow patterns, or blocks solvers from completing `fillOrder` for orders with fill-then-swap postdispatch calldata — a griefing DoS on the intent-fill/order-placement path, analogous to the reported `RouterSwapExecutor` DoS since both stem from an externally-reachable executor contract whose approval state can be manipulated by an unprivileged third party ahead of a victim's approve call.

### Likelihood Explanation
`dispatch()` requires no privilege and no funds — anyone can call it directly on-chain at any time, and front-running a pending `placeOrder`/`fillOrder` transaction that embeds a known router/token approve call is straightforward via public mempool observation. The affected pattern (embedding `approve()` calls in predispatch/postdispatch `Call[]`) is the officially documented usage pattern for swap-then-escrow and fill-then-swap flows.

### Recommendation
Restrict `CallDispatcher.dispatch()` to be callable only by the trusted contracts that are expected to invoke it (`IntentGatewayV2`, `HyperFungibleToken`, `WrappedHyperFungibleToken` deployments), e.g. via a constructor-set allowlist or `onlyRole`/`onlyOwner`-style modifier, so an unprivileged third party cannot inject arbitrary calls (including approvals) from the dispatcher's address. Alternatively/additionally, have order-embedded approval calls use `forceApprove`-style reset-to-zero-then-set semantics, or deploy a fresh, disposable dispatcher/executor per order rather than a shared singleton, so no attacker-controlled allowance state can persist across unrelated orders.

### Proof of Concept
1. Attacker observes IntentGatewayV2's configured `CallDispatcher` address (public via `_params.dispatcher`) and a target router `R` and stray-allowance-sensitive token `T` (e.g. USDT) that legitimate orders are known to approve for swaps in their predispatch/postdispatch `Call[]`.
2. Attacker calls `CallDispatcher.dispatch(abi.encode([Call({to: T, value: 0, data: abi.encodeWithSelector(IERC20.approve.selector, R, 1)})]))` directly — this succeeds since `dispatch` has no access control, leaving `T.allowance(dispatcher, R) == 1`.
3. A user's `placeOrder` transaction (or a solver's `fillOrder`) is submitted with predispatch/postdispatch calldata containing `Call({to: T, value:0, data: approve(R, largerAmount)})` intended to fund a subsequent swap.
4. Because `T` (e.g. USDT) rejects setting a non-zero allowance over an existing non-zero allowance, the embedded `approve` call reverts inside `CallDispatcher.dispatch`, which reverts the entire batch (`CallFailed`), causing the victim's `placeOrder`/`fillOrder` transaction to revert.
5. Attacker can repeat step 2 after each of the victim's retries (re-griefing with a new dust allowance), indefinitely blocking that token/router combination for calldata-bearing orders.
