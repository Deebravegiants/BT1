### Title
Unbounded per-signature ECDSA recovery loop in `EcdsaBeefy.verifyMmrUpdateProof` causes gas cost to scale linearly with the relay chain's authority set size, risking DoS of consensus updates - (File: evm/src/consensus/EcdsaBeefy.sol)

### Summary
`EcdsaBeefy.sol` verifies BEEFY consensus proofs by requiring a 2/3+1 supermajority of ECDSA signatures from the current (or next) Polkadot relay chain authority set, and the verification loop performs an `ECDSA.recover` plus a `keccak256` and merkle-leaf construction for every single signature supplied. This is structurally the same bug class as the reported `CouncilMembers::_retrieve()` issue: an internal function whose gas cost is directly proportional to the size of a set that is expected to grow over time (there, NFT-holding council members; here, BEEFY authority-set validators), with no batching, no off-chain aggregation, and no cap enforced on-chain.

### Finding Description
`verifyMmrUpdateProof` computes `sigLen = relayProof.signedCommitment.votes.length`, requires `sigLen` to clear the supermajority threshold against the authority set size (`checkParticipationThreshold`), and then iterates over every vote performing `ECDSA.recover` and building a merkle leaf: [1](#0-0) 

The number of signatures required scales directly with `authoritySet.len` — i.e. with the size of the Polkadot relay chain's validator set, which is a governance-controlled but externally-growing quantity, not bounded by this contract. As the doc comment itself acknowledges, this ECDSA verifier is already "the most gas-expensive verifier" precisely because ECDSA signatures cannot be aggregated: [2](#0-1) 

There is no upper bound on `authoritySet.len` or `sigLen` enforced anywhere in this contract — any relayer submitting a proof must supply signatures from a supermajority of whatever size the authority set has grown to, and the contract will loop that many times performing `ecrecover` (one of the more expensive EVM precompiles) on every call to `verify`.

### Impact Explanation
As the Polkadot relay chain's validator/authority set size increases over time (a normal, expected, non-malicious evolution of the underlying network that this contract does not control), the gas cost of `verify()` grows linearly and unboundedly. Once the required number of signatures × per-signature cost (ECDSA recovery + merkle leaf hashing + calldata cost of the votes array) approaches the destination chain's block gas limit, `EcdsaBeefy.verify()` becomes impossible to execute in a single transaction. Since this is the sole consensus-verification entry point used by `IConsensusV2` callers (e.g. `EvmHost`) for chains configured to use the ECDSA BEEFY client, this permanently freezes that route: no further consensus proofs can be accepted, `StateMachineUpdated` can never advance, and no cross-chain requests/responses/timeouts destined through that route can ever be delivered or proven — a "route unable to deliver messages" condition, matching High severity per the analog issue's own framing ("the contract will reach an unusable state").

### Likelihood Explanation
This does not require any malicious actor — it is triggered purely by organic authority-set growth on the source relay chain, which is outside the control of the destination-chain contract or any Hyperbridge relayer. Any relayer submitting a legitimate, honestly-generated proof for a large authority set is forced to include a supermajority of signatures, and cannot reduce this cost (ECDSA does not support signature aggregation). The risk is deterministic and worsens monotonically as the validator set grows, exactly mirroring the reported issue's growth pattern.

### Recommendation
Avoid on-chain verification of a linearly-scaling signature set for consensus finality. Migrate to (or make default) the zkBEEFY / SP1-based consensus client referenced in the project's own documentation, which amortizes verification cost to be constant regardless of authority set size, instead of `EcdsaBeefy`'s per-signature ECDSA recovery loop. If `EcdsaBeefy` must remain supported, enforce a hard cap on `authoritySet.len` (and therefore `sigLen`) at authority-set-rotation time so verification cost can never exceed a safe fraction of the destination chain's block gas limit.

### Proof of Concept
1. Assume the Polkadot relay chain authority set (`authoritySet.len`) grows to N validators such that the required supermajority (`2N/3 + 1`) signatures, each requiring an `ECDSA.recover` call plus merkle-leaf hashing inside `verifyMmrUpdateProof` (evm/src/consensus/EcdsaBeefy.sol:140-159), exceeds the destination EVM chain's block gas limit.
2. Any relayer attempting to submit a legitimate BEEFY consensus proof via `EcdsaBeefy.verify()` (called through `IConsensusV2`/`EvmHost`) cannot fit the required number of signature recoveries into a single transaction.
3. `verify()` can no longer succeed for any subsequent authority set update, permanently stalling `latestHeight`/`nextAuthoritySet` progression for that consensus client, and blocking delivery of every cross-chain message routed through it.
