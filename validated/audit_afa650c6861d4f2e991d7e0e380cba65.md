### Title
Paymaster relayer rotation can permanently strand EntryPoint stake, deposit and fee surplus with no recovery path - (File: `modules/pallets/intents-coprocessor/src/lib.rs`, `evm/src/apps/*Paymaster*.sol`)

### Summary
`pallet-intents-coprocessor::set_paymaster_relayer` dispatches a `PaymasterSetRelayer` governance request to a per-chain `SimplexPaymaster` contract to rotate the single relayer address authorized to deliver every `onAccept` governance action, including the withdrawal/unlock paths for the EntryPoint deposit, stake, and fee surplus. Once armed, every recovery function on the paymaster is gated behind `_checkRelayer`, and there is no "unblock"/failsafe path independent of that gate — mirroring the FiatDAO `Blocklist`/`VotingEscrow` bug class where a legitimate, non-malicious change to an access-control list (a "migration" of the allowed address) can trap funds belonging to accounts that had done nothing wrong, with no on-chain mechanism to reverse the effect for the stranded funds.

### Finding Description
The design decision doc for the paymaster relayer gate documents this explicitly: `SimplexPaymaster.onAccept` accepts every relayer while `_relayer` is unset, and only the currently-authorised one afterward; `migrate` and the `SetRelayer` request both refuse a zero relayer going forward, so once armed the gate can never be reopened. [3](#0-2) 

Critically, the same document states the accepted risk in the exact shape of the reported bug class: "once armed, every recovery path sits behind the gate, so a lost or withholding relayer key strands the deposit, stake and surplus for good," and warns that dispatching a second `SetRelayer`/`UpgradeContract` while a prior one is still undelivered can result in an unintended relayer ending up as "the sole key" because requests never expire and the relayer itself picks delivery order. [1](#0-0) 

This is structurally identical to the FiatDAO finding: `Blocklist`'s value (the trusted, must-be-correct address/set) can be changed via a normal operational action (a migration), and once changed, an account that was never previously screened is now denied every self-service exit path (`withdraw`, `quitLock`, `delegate`), with the only recovery being a full redeployment — i.e., a privileged, out-of-band fix, not something the affected party or protocol can trigger on demand. In the Hyperbridge analog, `set_paymaster_relayer` (called through ordinary `T::GovernanceOrigin`, not a compromised key) is the "change of blocklist" moment: [4](#0-3)  — after this dispatches, and until (or unless) the `PaymasterSetRelayer` request actually lands and is honestly relayed, every governance action on the paymaster — withdrawals, unlocking the EntryPoint stake, sweeping surplus — is gated on delivery from the new relayer alone, exactly as `Blocklist`'s check in `checkBlocklist()` cuts off `withdraw()`, `quitLock()`, and `delegate()` for a newly (and possibly erroneously) blocked account.

### Impact Explanation
If the rotation lands on an address that is unreachable, offline, has lost its key, or (per the documented "never dispatch a second SetRelayer while one is undelivered" warning) an unintended stale request is delivered out of order, the paymaster's EntryPoint stake, native deposit, and any accumulated fee surplus become permanently unreachable on that chain — there is no owner key, no fallback governance path, and no unblock/emergency function, since the contract "has no owner key" by design and every recovery path is intentionally routed exclusively through the relayer gate. This is a concrete permanent freezing of funds (ERC-4337 stake/deposit plus fee revenue), reachable purely from a single, ordinary governance dispatch that any relayer subsequently delivers — no compromised key or malicious intent is required, only an operational mistake or a relayer that goes dark, which is precisely the "blocklist migration error" scenario the FiatDAO report calls out as the realistic trigger.

### Likelihood Explanation
The rotation extrinsic (`set_paymaster_relayer`) is a normal governance operation expected to run periodically as relayer infrastructure changes; the decision doc itself flags the ordering hazard ("never dispatch a second `SetRelayer`... since requests never expire and the relayer picks delivery order") as a live operational risk the team already anticipated but did not eliminate. Given ISMP request delivery has no expiry and delivery order is chosen by whichever relayer processes it, a routine rotation combined with any relayer downtime or an out-of-order stale delivery is a realistic, non-adversarial trigger — matching the "most likely to occur as an error during a migration" framing of the original finding.

### Recommendation
Add a bounded, non-relayer-gated recovery path for the paymaster's own funds (stake unlock/withdraw, deposit withdraw, surplus sweep), e.g., a delay-guarded fallback that a designated non-relayer key (or the `intents-coprocessor` pallet's governance origin directly, without going through the relayer-gated `onAccept`) can trigger if the current relayer fails to acknowledge a `SetRelayer`/`PaymasterSetRelayer` delivery within a bounded window. At minimum, enforce single-flight rotation on-chain (reject dispatching a new `SetRelayer` while a prior one is outstanding, rather than relying on the operational warning in the decision doc) to remove the "stale request delivered out of order" hazard called out in the design notes.

### Proof of Concept
1. Governance calls `set_paymaster_relayer(state_machine, new_relayer)` (an ordinary, honest governance action, analogous to a "blocklist migration"). [5](#0-4) 
2. The dispatched `PaymasterSetRelayer` request is delivered by some relayer and `SimplexPaymaster` sets `_relayer = new_relayer`, per the documented one-way gate (`migrate`/`SetRelayer` refuse zero from then on). [6](#0-5) 
3. `new_relayer` loses its key, goes offline, or a second stale `SetRelayer` request delivered out of order (per the documented "never dispatch a second SetRelayer" hazard) leaves an unintended address as the sole authorized relayer. [1](#0-0) 
4. Every subsequent attempt to unlock the EntryPoint stake, withdraw the deposit, or sweep fee surplus reverts because `onAccept`'s relayer check now requires delivery from an address nobody controls — the paymaster's funds are permanently stranded with no on-chain unblock mechanism, exactly as `Blocklist`'s missing unblock function trapped a wrongly-blocked `VotingEscrow` account's tokens.

		/// Rotate the only relayer whose governance deliveries the paymaster accepts. The request
		/// itself has to be delivered by the relayer on record, so verify the previous rotation
		/// landed before dispatching another. Weighed as `upgrade_paymaster`, the same lookup and
		/// dispatch.
		#[pallet::call_index(20)]
		#[pallet::weight(T::WeightInfo::upgrade_paymaster())]
		pub fn set_paymaster_relayer(
			origin: OriginFor<T>,
			state_machine: StateMachine,
			relayer: H160,
		) -> DispatchResult {
			T::GovernanceOrigin::ensure_origin(origin)?;
			ensure!(!relayer.is_zero(), Error::<T>::InvalidPaymasterRelayer);

			let paymaster =
				Paymasters::<T>::get(state_machine).ok_or(Error::<T>::PaymasterNotFound)?;

			Self::dispatch(
				state_machine,
				paymaster,
				RequestKind::PaymasterSetRelayer { relayer }.encode_body(),
			)?;

			Self::deposit_event(Event::PaymasterRelayerUpdateInitiated { state_machine, relayer });

			Ok(())
		}
