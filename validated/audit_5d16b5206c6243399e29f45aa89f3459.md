## Title
Webhook `shop` identity is taken from an HTTP header that is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` (and `topic`/`webhook_id`) from HTTP headers, but `Utils::HmacValidator` only verifies the raw request **body** against the HMAC. The header that the host application uses to bind the payload to a specific merchant is never covered by the signature it "passes."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes/compares the HMAC purely against that signable string: [2](#0-1) 

Meanwhile `shop`, `topic`, and `webhook_id` are read straight from headers with no cryptographic binding to the body or to each other: [3](#0-2) 

`Registry.process` validates only the HMAC and then hands `request.shop` (and `request.topic`) directly to the app's registered handler as the tenant identity for the payload: [4](#0-3) 

This breaks the intended identity binding `shop_verified == shop_acted_on`. The equality that should hold is:
`HMAC(secret, raw_body) valid ⇒ shop header authentically originated together with that body`

but the implementation only proves `HMAC(secret, raw_body) valid`, and `shop` is accepted from an unauthenticated, unsigned header — exactly the "field acted on but not covered by the HMAC" pattern (analogous to the `amount` used in the post-transfer-fee calculation not matching the `amount` actually verified/received in the reported finding).

### Impact Explanation
Because `shop` is not part of the signed material, a valid `(raw_body, hmac)` pair captured from any real webhook delivery (e.g., a webhook sent to an attacker's own shop/store, which is delivered by Shopify to the attacker's own configured endpoint credentials-free of any secret) can be replayed to the app's webhook endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header rewritten to a **different, victim** shop. The HMAC check still succeeds because it only validates the body, and the handler then processes/attributes that body's data as if it belongs to the victim tenant. This is a cross-tenant data-confusion primitive: an unprivileged party who merely installs the app on their own shop can manufacture webhook events that the host application will bind to a different merchant's tenant, without ever knowing `api_secret_key`.

### Likelihood Explanation
Any user of the multi-tenant app (an ordinary merchant, not requiring any privileged access) can install the app to receive real, validly signed webhook bodies for at least one topic they control, then replay the exact same body/HMAC to the shared webhook endpoint while substituting an arbitrary `shop-domain` header value. No secret, token, or elevated privilege is required — only network access to the app's public webhook endpoint, which is designed to be internet-reachable.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the value that is actually HMAC-verified, or otherwise cryptographically tie the header-derived identity to the signed body — e.g., by including the relevant headers in the signable string, or by requiring host applications to independently confirm the `shop` header corresponds to a session/shop that legitimately owns the webhook subscription (e.g., cross-check against `webhook_id` registered for that shop) before trusting `WebhookMetadata#shop` for tenant-scoped actions.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; capture a legitimate webhook delivery: raw body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC over `B` computed with the app's `api_secret_key`, unknown to attacker but irrelevant since `H`/`B` are simply replayed).
2. POST to the app's public webhook endpoint with the same raw body `B` and same `x-shopify-hmac-sha256: H`, but set `x-shopify-shop-domain: victim.myshopify.com` and any desired `x-shopify-topic`.
3. `Utils::HmacValidator.validate` succeeds (only `B`/`H` checked) — see [5](#0-4) .
4. `Registry.process` invokes the registered handler with `shop: "victim.myshopify.com"`, causing the host app to process/store the attacker-supplied payload under the victim's tenant.
