### Title
Predictable, non-random session identifier used as the non-embedded auth cookie value enables session fixation - (File: lib/shopify_api/auth/oauth.rb)

### Summary
For non-embedded apps, `ShopifyAPI::Auth::Oauth.validate_auth_callback` sets the post-login session cookie's value to `session.id`, and `ShopifyAPI::Auth::Session.from` derives that id deterministically as `"#{shop}_#{associated_user.id}"` (online) or `"offline_#{shop}"` (offline). Unlike the pre-auth cookie value, which is a fresh `SecureRandom.alphanumeric` nonce, the post-auth cookie value is not random — it is a pure function of two values that are frequently knowable or guessable by an unprivileged party: the shop's `myshopify.com` domain and the target user's numeric Shopify user id.

### Finding Description
The identity binding that should hold is:
`session_lookup_key == f(random, per-authentication secret bound to this browser's OAuth transaction)`

What the code actually implements is:
`session_lookup_key == f(shop, associated_user.id)` — a value computable by anyone who knows (or can enumerate) the shop domain and the target's user id, i.e. it is not bound to the specific authenticated browser/session at all.

Trace:
1. `begin_auth` correctly issues a random nonce as the pre-auth cookie value: `state = SecureRandom.alphanumeric(NONCE_LENGTH)`, `cookie = SessionCookie.new(value: state, ...)`. [1](#0-0) 
2. After OAuth completes, for non-embedded apps the cookie's value is overwritten with the deterministic `session.id`, not a fresh random value: [2](#0-1) 
3. `Session.from` computes that id purely from `shop` and `associated_user.id` (or just `shop` for offline sessions), with no random component: [3](#0-2) 
4. The documented, non-embedded retrieval path (`SessionUtils.current_session_id` → `cookie_session_id`) simply echoes the raw cookie value back as the session lookup key, with no signature/HMAC check binding it to the browser that performed OAuth: [4](#0-3) 

This mirrors the bug class in the reference report: an identity/authorization check is performed on one value (the random `state` nonce, verified during the callback) while a *different*, unauthenticated/unbound value (the deterministic `session.id`) becomes the durable credential that the rest of the system trusts thereafter. The nonce that was actually verified (`state == auth_query.state`) is discarded, and the cookie is repointed to a value that never went through any verification against the current browser.

### Impact Explanation
This is a session-fixation primitive: an attacker who can predict or pre-set a victim's `shopify_app_session` cookie to a value equal to `"#{shop}_#{user_id}"` (or `"offline_#{shop}"`) before or during the victim's login, can subsequently present that same, now-attacker-known cookie value to the host application's session store and be treated as though they hold the victim's authenticated session — including whatever the store returns keyed by that id (typically the merchant's offline/online access token). Because the identifier depends only on public/enumerable inputs (shop domain, and often small sequential Shopify staff user ids), no secret possession by the attacker is required, satisfying the "session fixation or forced OAuth completion" High-impact category.

### Likelihood Explanation
Exploitation requires the ability to set a cookie value in the victim's browser for the app's own origin (e.g. via cookie tossing on a shared/sibling domain, a cross-site scripting or cookie-injection primitive elsewhere on the app's domain, or simply the attacker using their own browser with a pre-known target id if the store trust boundary is per-cookie-value rather than per-browser). This is the gem's own documented, out-of-the-box behavior — the docs explicitly describe reading `cookies[...]` back verbatim as the session id — so it is not caused by host misuse of the API. Whether it is practically exploitable further depends on how the host app's session store is implemented, which is outside this gem, so full end-to-end confirmation could not be verified within this gem alone.

### Recommendation
Do not use the deterministic `session.id` (or any value derivable purely from `shop`/`user_id`) directly as the cookie's bearer value. Instead, keep issuing a fresh, unguessable random token for the cookie on successful OAuth completion (as is already done pre-auth with `SecureRandom.alphanumeric`), and maintain a server-side mapping from that random token to the actual `session.id`/access token, so the cookie value itself carries no attacker-predictable identity information.

### Proof of Concept
1. Attacker knows (or enumerates) `shop = "victim-shop.myshopify.com"` and a target staff `associated_user.id = 42` (Shopify staff ids are typically small sequential integers, and app-installing merchants often reveal them, e.g. through app UI, support requests, or their own prior installs).
2. Attacker computes the eventual session cookie value that any legitimate OAuth completion for that user will produce: `"victim-shop.myshopify.com_42"`, matching `Session.from`'s id formula. [5](#0-4) 
3. Attacker sets `shopify_app_session=victim-shop.myshopify.com_42` in the victim's browser ahead of time (session fixation via any cookie-setting vector on the app's origin).
4. Victim completes OAuth normally; the host app's `validate_auth_callback` sets the cookie to exactly that predicted value. [6](#0-5) 
5. Attacker, already knowing this fixed value, submits requests using `shopify_app_session=victim-shop.myshopify.com_42`; `SessionUtils.cookie_session_id` returns it unverified, and any host session store keyed on this id resolves to the victim's stored access token. [4](#0-3)
