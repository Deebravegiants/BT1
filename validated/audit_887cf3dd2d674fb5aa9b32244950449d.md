Audit Report

## Title
Missing return after failed email-claim extraction allows session creation with empty email in OIDC exchange handler - (File: core/sessions/oidcauth/oidc.go)

## Summary
`handleTokenExchange` fails to `return` after it cannot type-assert the `email` claim to a string, so execution continues using the empty `email` value while a role has already been resolved from the ID token's group claims, resulting in a persisted, authenticated session with an empty-string email and a legitimately-derived role.

## Finding Description
At `core/sessions/oidcauth/oidc.go:226-230`, the code does: [1](#0-0) 
This type-assertion failure branch logs an error and calls `c.String(http.StatusInternalServerError, ...)` but does not `return`. Since `c.String` in Gin only writes a response body and does not abort the handler chain, execution falls through to role mapping and session persistence.

Role mapping is derived independently from `idClaims` (group claims), not from `email`: [2](#0-1) 

The session is then inserted using the empty `email` value paired with the valid role: [3](#0-2) 

The handler proceeds to set the session cookie and return HTTP 200 success: [4](#0-3) 

`AuthorizedUserWithSession` later resolves this session back to a `clsessions.User{Email: "", Role: <role>}` without further validating the email field, so the empty-email, role-bearing session is fully usable for subsequent authenticated requests: [5](#0-4) 

This exactly matches the code as it exists in this repository — the missing `return` is confirmed at lines 226-230, and there is no other guard (no early-return check on `email == ""`, no validation before the INSERT) that would prevent this path from completing.

## Impact Explanation
This decouples authenticated role assignment from a valid, IdP-asserted identity: any completed OIDC exchange in which the identity provider omits (or the code fails to extract) the `email` claim — while still supplying group claims that satisfy one of `AdminClaim`/`EditClaim`/`RunClaim`/`ReadClaim` — results in a valid, cookie-backed session mapped to `user_email = ''` and a real RBAC role, up to Admin. Because `FindUser`/`AuthorizedUserWithSession` treat this as a normal authenticated `User`, it constitutes a node API role-bypass / authentication integrity issue, and because all such empty-email sessions collapse to the same identity, it also causes cross-user response confusion for any per-user email-keyed logic elsewhere in the system.

## Likelihood Explanation
Exploitability depends on the specific OIDC identity provider's token content: it requires the `email` claim to be absent/non-string while the configured group claim (`oidcCfg.ClaimName()`) is present and satisfies a role mapping. This is not something an OIDC-conformant provider correctly configured with an `email` scope would normally produce, but the OAuth2 scopes requested by `oauth2Config` include `"email"` only as a request hint — the actual ID token content is controlled by the identity provider (or a malicious/compromised one), not validated as mandatory by this code before use. The flow is reachable via the standard `/oidc-login` → `/oidc-exchange` endpoints without any elevated privilege, so once the provider-side condition is met, exploitation from an already-authorized OIDC login flow is deterministic and repeatable — the bug is a genuine unguarded code defect, not a hypothetical.

## Recommendation
Add `return` immediately after the `c.String(http.StatusInternalServerError, "Failed to get email from claims")` call at line 229 (and similarly consider `return` after the other error-logged-but-not-aborted branch at line 259 for the INSERT failure) so the handler aborts before creating any session or logging a successful login when the email claim cannot be extracted.

## Proof of Concept
1. Configure OIDC with a test identity provider that issues an ID token with valid group claims (matching one of `AdminClaim`/`EditClaim`/`RunClaim`/`ReadClaim`) but no `email` claim (or `email` as a non-string type).
2. Complete `/oidc-login` → `/oidc-exchange` as an unauthenticated client with a valid `code`/`state`.
3. Observe: server logs "Failed to get email from claims" yet still responds `200 OK` `{"success": true}`, inserting a row into `oidc_sessions` with `user_email = ''` and `user_role = <derived role>`, and sets the session cookie.
4. Use the returned cookie against an authenticated endpoint; `AuthorizedUserWithSession` (`core/sessions/oidcauth/oidc.go:349-391`) returns `User{Email: "", Role: <derived role>}`, granting access at that role.

// AuthorizedUserWithSession will return the API user associated with the Session ID if it
// exists and hasn't expired
func (oi *oidcAuthenticator) AuthorizedUserWithSession(ctx context.Context, sessionID string) (clsessions.User, error) {
	if len(sessionID) == 0 {
		return clsessions.User{}, errors.New("session ID cannot be empty")
	}
	var foundUser clsessions.User
	err := sqlutil.TransactDataSource(ctx, oi.ds, nil, func(tx sqlutil.DataSource) error {
		// Query the oidc_sessions table for given session ID, user role and email are saved after the id claims is provided and validated
		var foundSession struct {
			UserEmail string
			UserRole  clsessions.UserRole
			Valid     bool
		}
		if err := tx.GetContext(ctx, &foundSession,
			"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM oidc_sessions WHERE id = $1",
			sessionID, oi.config.SessionTimeout().Duration(),
		); err != nil {
			if errors.Is(err, sql.ErrNoRows) {
				return clsessions.ErrUserSessionExpired
			}
			return err
		}
		if !foundSession.Valid {
			// Sessions expired, purge
			return clsessions.ErrUserSessionExpired
		}
		foundUser = clsessions.User{
			Email: foundSession.UserEmail,
			Role:  foundSession.UserRole,
		}
		return nil
	})
	if err != nil {
		if errors.Is(err, clsessions.ErrUserSessionExpired) {
			if _, execErr := oi.ds.ExecContext(ctx, "DELETE FROM oidc_sessions WHERE id = $1", sessionID); execErr != nil {
				oi.lggr.Errorf("error purging stale OIDC session: %v", execErr)
			}
		}
		return clsessions.User{}, err
	}
	return foundUser, nil
}
