This confirms the finding: `Registry.process` (lib/shopify_api/webhooks/registry.rb:189-199) validates HMAC via `HmacValidator.validate(request)`, which only signs `@raw_body` (`Request#to_signable_string`, lib/shopify_api/webhooks/request.rb:35-38). The `shop`, `topic`, `webhook_id`, and `api_version` fields come from separate HTTP headers (`Request#shop`, lines 20-23) that are never included in the HMAC-signable string, yet they are trusted and forwarded verbatim into `WebhookMetadata` (lib/shopify_api/webhooks/webhook_handler.rb:6-12) that host application handlers use to key per-tenant logic.

### Title
Webhook shop-domain header is not bound to the HMAC signature, enabling cross-tenant webhook relabeling - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authentic for whatever `shop` (and `topic`/`webhook_id`) it carries as long as the HMAC over the raw body validates. But the HMAC never covers those header fields, so the shop identity delivered to the app's handler is not cryptographically bound to the signed payload.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no relation to the signed content [2](#0-1) . `Registry.process` validates only `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (i.e. the body) and compares it against the `hmac` header [3](#0-2) [4](#0-3) . After that single check passes, `request.shop` is trusted and forwarded unchanged into `WebhookMetadata`, which is the sole tenant-identifying field host applications receive in their handler [5](#0-4) [6](#0-5) .

The equality the gem should guarantee is: `shop_bound_by_signature == shop_delivered_to_handler`. In reality: `shop_delivered_to_handler = header["shop-domain"]` (attacker-controllable), while `shop_bound_by_signature` is undefined — the signature says nothing about which shop the body belongs to. Because a single app-level `api_secret_key` is shared across every installed shop, any body+HMAC pair that is valid for shop A's webhook remains a perfectly valid signature no matter which `shop-domain` header accompanies it. An unprivileged user who has installed the app on their own (low-privileged) store can capture one legitimate webhook delivery (body + `hmac-sha256` header) that Shopify sent to the app's public webhook endpoint, then replay the exact same body/HMAC to the same endpoint while substituting a victim shop's domain in the `shop-domain` header. `HmacValidator.validate` still returns `true` (the body/HMAC pair is unmodified and valid), so `Registry.process` dispatches the handler with `WebhookMetadata.shop` set to the victim's domain.

### Impact Explanation
Any host application that uses `WebhookMetadata#shop` to select per-tenant records, storage keys, or session/credential lookups (a standard and gem-documented usage pattern) can be tricked into associating the replayed payload with the wrong tenant, i.e. cross-tenant data confusion/access — one of the explicitly in-scope Critical impacts.

### Likelihood Explanation
The webhook receiver endpoint is normally exposed publicly on the internet for Shopify to call, so no credentials beyond installing the app once as a normal (unprivileged) merchant are required to obtain a valid body+HMAC pair for replay; only header substitution is needed afterward, which the gem does not detect.

### Proof of Concept
```ruby
# Attacker installs app on their own shop "attacker.myshopify.com" and
# receives one legitimate webhook delivery from Shopify:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => "<captured, valid Base64 HMAC for the captured body>",
  "x-shopify-shop-domain" => "attacker.myshopify.com",
  "x-shopify-webhook-id" => "captured-id",
  "x-shopify-api-version" => "2024-01",
}
raw_body = "<captured legitimate JSON body>"

# Attacker replays it, only swapping the shop-domain header to a victim shop:
forged_headers = headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) still succeeds because the HMAC only
# covers raw_body (lib/shopify_api/webhooks/request.rb:35-38), so the
# handler is invoked with WebhookMetadata.shop == "victim-shop.myshopify.com".
```

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the HMAC-signable content, or require the caller to independently verify `request.shop` against a known/registered shop list before trusting it for tenant selection; at minimum, document in `Utils::HmacValidator`/`Webhooks::Registry` that `shop`, `topic`, and `webhook_id` headers are unauthenticated and must not be used for tenant-sensitive decisions without an out-of-band shop check.
