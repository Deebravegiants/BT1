Audit Report

## Title
Vault gateway/DON handlers log the full incoming JSON-RPC request — including the bearer JWT/auth token — at Debug level before authorization or redaction - ([File: core/services/gateway/handlers/vault/handler.go], [File: core/capabilities/vault/gw_handler.go])

## Summary
`HandleJSONRPCUserMessage` in `core/services/gateway/handlers/vault/handler.go` and `HandleGatewayMessage` in `core/capabilities/vault/gw_handler.go` both log the entire `jsonrpc.Request[json.RawMessage]` object via structured logging (`"request", req` / `"req", req`) before the request is authorized. Since the `jsonrpc.Request` type (from `github.com/smartcontractkit/chainlink-common/pkg/jsonrpc2`) carries an `Auth` field populated with the caller's bearer JWT, this token is written verbatim into Debug logs on every inbound vault request, and the `Authorizer`/`JWTBasedAuth` machinery uses this same JWT to establish caller identity for vault operations.

## Finding Description
The exact log lines match the claim precisely: [1](#0-0) [2](#0-1) [3](#0-2) 

Both log statements fire before `h.requestProcessor.ProcessRequest`/authorization completes, and pass the full `req` struct to the structured logger without any field-level redaction. The `jsonrpc.Request` type is imported from the external `chainlink-common` module (`jsonrpc "github.com/smartcontractkit/chainlink-common/pkg/jsonrpc2"`), and its `Auth` field is referenced and used for authorization throughout the vault authorizer code (`core/capabilities/vault/authorizer.go`, `core/capabilities/vault/jwt_based_auth.go`, `core/capabilities/vault/gateway_vault_request_processor.go`), confirming this field carries the bearer credential used to authenticate/authorize vault requests. [4](#0-3) 

The existing regression test only covers the "invalid params" rejection path and explicitly filters out the Debug-level whole-request log, confirming this pre-existing gap is untested and unaddressed: [5](#0-4) 

**Unresolved uncertainty**: I could not locate/read the `jsonrpc2.Request` struct definition itself in this repo (it lives in the external `chainlink-common` module, which is not indexed here), so I cannot fully confirm the exact field name/tag of the `Auth` field or verify there is no custom `MarshalJSON`/`String()`/zap `MarshalLogObject` implementation on that type that redacts sensitive fields before being handed to the structured logger. No such redaction method was found via search within this repo, and none of the code I could inspect (handler.go, gw_handler.go, authorizer.go) shows any redaction applied at the call site. Given the absence of any redaction logic found and the explicit acknowledgment in the test file's comment referencing this exact log line as a known, unaddressed issue, the claim is well-supported by the available evidence, though full certainty on the external type's serialization behavior would require inspecting the `chainlink-common` module directly.

## Impact Explanation
This is a credential/secret-disclosure issue: an operator or any process with read access to Debug-level logs on the vault gateway or DON node can recover live JWT bearer tokens used to authorize Vault secrets operations (create/update/delete/list). Since the JWT is the sole authorization artifact bound to a caller's identity/ownership in `AuthorizeRequest`, its disclosure allows replay/impersonation of that caller's Vault requests — this maps to the in-scope "key/secret exfiltration" / "gateway request impersonation" impact categories.

## Likelihood Explanation
The log statement fires unconditionally on every inbound vault request reaching the gateway or DON handler, regardless of whether the request is ultimately authorized — no attacker action beyond a normal, unprivileged JSON-RPC request with a valid `Authorization: Bearer <jwt>` header is required to cause the token to be written to logs. The only precondition is that Debug-level logging is enabled, which is a common (though non-default) operational configuration for troubleshooting production gateway/DON deployments.

## Recommendation
- Remove `req`/full-request from the log calls at `core/services/gateway/handlers/vault/handler.go:403` and `core/capabilities/vault/gw_handler.go:182`; log only safe fields (`method`, `requestID`) as already done elsewhere in the codebase (e.g., `gateway_vault_request_processor.go`'s `authorizeAndStamp`).
- Avoid logging the full `response` object at Info level in `gw_handler.go:231`; log only non-sensitive identifiers.
- If the `jsonrpc2.Request`/`Response` types are shared across the codebase, consider implementing a redacting `String()`/`MarshalLogObject` method upstream in `chainlink-common` so any future logging call sites are automatically safe.

## Proof of Concept
1. Deploy a Vault-enabled gateway/DON node with logger level set to `debug`.
2. As an unprivileged client, send a valid JSON-RPC vault request (e.g., `vault_secretsList`) to the gateway with `Authorization: Bearer <jwt>`.
3. Observe gateway/DON log output for the `"handling vault request"` (handler.go:403) or `"received message from gateway"` (gw_handler.go:182) log entries — the JWT supplied in `req.Auth` appears in the serialized `request`/`req` field.
4. Confirm via a Go unit test analogous to `TestVaultHandler_InvalidParamsDoesNotLogRawParams`, but observing Debug-level logs and asserting the `Auth`/JWT value does NOT appear in log output for a normal (not invalid-params) request — this test would currently fail, demonstrating the leak.
