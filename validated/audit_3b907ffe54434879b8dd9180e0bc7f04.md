### Title
Permanent max router allowance + fully attacker-controlled `externalActionMetadata` lets `router.call` pull unbounded `inputToken` from `LifiExternalAction`, draining stranded/residual balances - (File: contracts/external-actions/swaps/LifiExternalAction.sol, contracts/TransfererBase.sol)

### Summary
`LifiExternalAction.callRouter` calls `approveUnlimited(inputToken, router)` before blindly executing `router.call(externalActionMetadata)`, and once the allowance reaches `type(uint256).max` it is never reduced. Because `inputAmount` is never enforced as an upper bound on what the router's call can actually pull via `transferFrom`, and `externalActionMetadata` is fully attacker-chosen calldata to the same fixed `router` address, an attacker can supply a tiny `deltaAmounts[0]` but craft calldata invoking a different router function that pulls any residual `inputToken` balance sitting in the contract, using the standing max allowance.

### Finding Description
The equality that should hold is:
`amount pulled from LifiExternalAction by router.transferFrom == uint256(-deltaAmounts[0])` (the `inputAmount` Hinkal transferred in for this call).

Trace:
- `Hinkal._externalTransact` transfers exactly `inputAmount = uint256(-deltaAmounts[0])` of `inputToken` into `LifiExternalAction` before calling `runAction` → `swap`. [1](#0-0) 
- `swap` calls `callRouter(inputToken, inputAmount, outputToken, externalActionMetadata)`, but `inputAmount` is **only used to compute `swappedAmount` via output-token balance diff**; it is never passed into the router call nor used to cap what the router can pull. [2](#0-1) 
- Before the raw `router.call(externalActionMetadata)`, `approveUnlimited` is invoked, which only re-approves if current allowance `< type(uint256).max / 2`; once a legitimate first swap pushes allowance to `type(uint256).max`, all subsequent calls leave that max allowance untouched. [3](#0-2) 
- `router` is fixed at construction and not attacker-controlled, but `externalActionMetadata` is arbitrary calldata to that address, entirely chosen by the transaction's prover (an unprivileged attacker who can generate their own proof/UTXOs and set every `CircomData` field including `externalActionData.externalActionMetadata`). [4](#0-3) 
- There is no balance check on `inputToken` before/after the router call — only `outputToken`'s balance diff is measured (`swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore`). Nothing constrains how much `inputToken` the router's `transferFrom` (triggered inside `externalActionMetadata`) actually removes from `LifiExternalAction`. [5](#0-4) 

Root cause: the contract relies entirely on the router's *own* internal accounting of how much of the approved allowance to consume, while giving it a standing `type(uint256).max` allowance and letting the caller pick which router function to invoke. If a prior swap (this attacker's own or someone else's) left any `inputToken` dust/residual balance in `LifiExternalAction` (e.g., router used less than the granted `inputAmount`, since `swap()` never sweeps unused `inputToken` back to the sender), that residual becomes drainable: the attacker deposits a minimal `inputAmount`, but the router function invoked pulls more (up to the entire allowance-enabled balance) because nothing ties the `transferFrom` amount to `inputAmount`/`deltaAmounts[0]`.

None of the existing guards catch this: `performHinkalChecks`, `verifyProof`, and the circuit's `inTotal + amountChanges === outTotal` constrain Hinkal's internal UTXO bookkeeping and the `deltaAmounts` the *prover claims*, but they do not, and cannot, constrain what an external contract's `router.call` actually executes once given a standing max ERC-20 allowance and free-form calldata. The circuit has no visibility into or constraint over `router`'s internal `transferFrom` logic.

### Impact Explanation
An attacker can steal any `inputToken` balance that ends up sitting in `LifiExternalAction` beyond what the current transaction's `deltaAmounts[0]` accounts for — this includes dust/residual left behind by other users' earlier swaps that under-consumed their granted `inputAmount`, or by the attacker's own prior swaps. Because `router` is a fixed external address whose functions may be freely selected via `externalActionMetadata`, this is not merely a theoretical routing quirk but a genuine unauthorized token movement: value leaves the contract that the current transaction's proof/`deltaAmounts` never accounted for. This matches "theft of shielded or in-flight user funds" (Critical) when the residual belongs to another user's incomplete/leftover swap, since the router call is executing a transfer that neither the wallet owner nor the prover of that original deposit ever authorized for this purpose. It is repeatable each time residual balance accumulates in the contract.

### Likelihood Explanation
Preconditions: (1) at least one prior swap through `LifiExternalAction` for the target `inputToken` has already pushed the allowance to `type(uint256).max` (a very common, unavoidable steady state after any successful swap), and (2) some non-zero `inputToken` balance is left stranded in the contract (plausible whenever a router swap consumes less than the full approved/transferred `inputAmount`, since `swap()` never returns unused `inputToken` to the caller). Attacker cost is a single normal deposit/transact with a small `inputAmount` and custom `externalActionMetadata` targeting a different router function — well within the described unprivileged attacker capability (crafting `CircomData`, generating their own proof, choosing `externalActionMetadata`). This is realistically exploitable whenever residual balance exists, and is repeatable per opportunity.

### Recommendation
- In `LifiExternalAction.callRouter` (and any other `ExternalActionSwap` implementation), measure `inputToken` balance before and after the router call and require the actual decrease equals exactly `inputAmount`, reverting otherwise.
- Prefer per-call bounded approvals (`approveERC20Token(inputToken, router, inputAmount)` then reset to 0 after the call) instead of a permanent `type(uint256).max` allowance, so a malicious `externalActionMetadata` cannot pull more than intended regardless of which router function is invoked.
- Sweep any leftover `inputToken` (i.e., `inputAmount - actualConsumed`) back to `msg.sender`/`circomData` recipient at the end of `swap()` so residual balances never accumulate in the contract.

### Proof of Concept
Foundry test plan:
1. Deploy `LifiExternalAction` with a mock `router` and mock `inputToken`/`outputToken` ERC20s, plus a mock `hinkalHelper`.
2. Simulate a first legitimate swap (via `runAction`/`swap`) with `inputAmount = X` where the mock router's swap function only consumes `X/2` via `transferFrom`, leaving `X/2` stranded in `LifiExternalAction`. Confirm allowance from `LifiExternalAction` to `router` is now `type(uint256).max`.
3. Craft a second `CircomData`/`deltaAmounts` with `inputAmount = ε` (tiny), but set `externalActionMetadata` to call a *different* mock-router function that calls `transferFrom(LifiExternalAction, router, X/2 + ε)` (or any amount exceeding `ε`), relying on the pre-existing max allowance.
4. Call `runAction` for the second transact.
5. Assert: `inputToken.balanceOf(LifiExternalAction)` before second call minus after call `> ε` (i.e., strictly greater than `uint256(-deltaAmounts[0])`), proving `router.call` pulled more `inputToken` than Hinkal sent for that transaction — breaking the intended equality `amount pulled == -deltaAmountChanges[0]`.

```text
    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
```
