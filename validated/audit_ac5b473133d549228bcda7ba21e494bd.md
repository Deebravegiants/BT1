## Title
Unbacked mint via `WrappedHyperFungibleToken.send()` failing to verify actual tokens received for fee-on-transfer/rebasing underlying tokens - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`WrappedHyperFungibleToken` implements the lock/unlock side of the HyperFungibleToken bridge: it locks an underlying ERC20 on the home chain and dispatches a POST request that causes the remote `HyperFungibleToken` to mint the *nominal* amount. `send()` trusts `params.amount` as the amount actually locked instead of measuring the contract's real balance delta, so any underlying token that does not deliver exactly `params.amount` to the contract (fee-on-transfer tokens, or a rebasing token that has a negative rebase between approval and transfer) causes the destination chain to mint more supply than is actually escrowed on the home chain.

### Finding Description
In `send()`, tokens are pulled with a plain `safeTransferFrom`, and the full `params.amount` is then encoded into the cross-chain `Message.amount` used to mint on the destination: [1](#0-0) 

There is no balance-before/after check here, unlike the pattern the codebase already uses elsewhere for exactly this class of token. `IntentGatewayV2` explicitly guards against non-standard transfer semantics by snapshotting balances and using the actually-received delta for escrow accounting: [2](#0-1) 

`WrappedHyperFungibleToken` has no equivalent guard. On `onAccept`/mint on the remote `HyperFungibleToken`, the full nominal `message.amount` is minted regardless of what was actually locked: [3](#0-2) 

And on the home chain, `unlock` (via `onAccept`/`onPostRequestTimeout`) always transfers the full nominal `message.amount` out of the contract's underlying balance, again without any check that the contract actually holds that amount as opposed to what it nominally believes it locked: [4](#0-3) 

If the underlying is fee-on-transfer, the contract receives `params.amount - fee` but the bridge still mints `params.amount` on the destination chain — this is an immediate unbacked mint. If the underlying is a negative-rebasing token, the contract's stored/locked balance can shrink after the fact (independent of any single transfer), so the sum of all outstanding minted/wrapped supply across chains can exceed what the home-chain escrow actually holds, meaning some future `unlock` calls will revert (funds permanently stuck for the last claimants) or, combined with fee-on-transfer type effects, allow early claimants to drain more value than they contributed.

### Impact Explanation
This is a direct violation of the 1:1 backing invariant documented for the HFT escrow model ("the supply of this token is always backed by the pallet's/wrapper's escrow account", per `BridgeToken.sol`'s docstring analog). An unbacked mint on the remote chain, or insolvency of the home-chain escrow, is a concrete theft/loss-of-funds primitive: users can mint more wrapped value than was actually escrowed, and/or later legitimate unlock/refund calls fail because the underlying balance has been silently reduced by transfer fees or negative rebases accumulated over many bridging operations.

### Likelihood Explanation
Any owner can configure `_underlying` to an arbitrary ERC20 via `configure()`; nothing in `WrappedHyperFungibleToken` restricts the underlying to non-fee-on-transfer/non-rebasing tokens, and the contract is explicitly designed as a generic "wrapper for existing ERC20 tokens." Deploying it against a deflationary/fee-on-transfer or rebasing asset (which is common in production DeFi) is a single, ordinary `send()` transaction away from triggering the mismatch — no privileged or adversarial setup beyond normal usage is required.

### Recommendation
In `send()`, measure the contract's underlying balance before and after `safeTransferFrom` and encode the actual received delta into `Message.amount` (mirroring the fee-on-transfer handling already used in `IntentGatewayV2`), or explicitly document/enforce (e.g. via an allow-list or an assertion of standard ERC20 semantics) that only standard, non-rebasing, non-fee-on-transfer tokens may be configured as `_underlying`.

### Proof of Concept
1. Deploy `WrappedHyperFungibleToken` with `_underlying` set to a fee-on-transfer token charging, e.g., 1% on transfer.
2. User calls `send({amount: 1000e18, ...})`. `safeTransferFrom` moves only 990e18 into the contract (`WrappedHyperFungibleToken.sol:272`), but the dispatched `Message.amount` is still `1000e18` (`WrappedHyperFungibleToken.sol:238-243`).
3. On the remote chain, `HyperFungibleToken.onAccept` mints `1000e18` to the beneficiary (`HyperFungibleToken.sol:301`) even though only `990e18` is actually locked on the home chain.
4. Repeating this drains the escrow's backing ratio; eventually a legitimate `unlock`/refund for `message.amount` on the home chain (`WrappedHyperFungibleToken.sol:323`/`361`) will revert due to insufficient underlying balance, freezing funds for whoever's request is processed last.

        uint256 msgValue = msg.value;
        if (_isWeth && msgValue >= params.amount) {
            msgValue = msgValue - params.amount;
            IWETH(_underlying).deposit{value: params.amount}();
        } else {
            IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
        }

        DispatchPost memory request = _buildDispatchPost(params);
        bytes32 commitment;
        if (msgValue > 0) {
            commitment = IDispatcher(_host).dispatch{value: msgValue}(request);
        } else {
            commitment = dispatchWithFeeToken(request);
        }

        emit Sent({
            from: msg.sender,
            to: params.to,
            dest: string(params.dest),
            amount: params.amount,
            commitment: commitment
        });
    }

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }
