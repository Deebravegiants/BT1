### Title
Large scaled debt can overflow during index accrual and permanently freeze a market - ([File: common/src/rates/index.rs](common/src/rates/index.rs))

### Summary

An unprivileged user can create a sufficiently large scaled-debt position in a high-decimal market. After the borrow index grows enough, the permissionless `Controller::update_indexes` path reaches `calculate_supplier_rewards`, which multiplies the stored scaled debt by the new index in `i128`. The product can exceed `i128::MAX` before `MAX_BORROW_INDEX_RAY` is checked, causing `MathOverflow`. Because every pool mutation synchronizes interest before applying the operation, the same panic subsequently blocks withdrawal, repayment, liquidation, and further index updates for that market.

### Finding Description

`Controller::update_indexes` is callable by any authorized caller and forwards the selected `HubAssetKey` list to the pool. [1](#0-0)  The pool entrypoint calls the market accrual implementation. [2](#0-1)  Accrual processes elapsed time in chunks and invokes `accrue_step` with the stored scaled `borrowed`, `supplied`, borrow index, and supply index. [3](#0-2) 

Inside `calculate_supplier_rewards`, the pool computes `borrowed.mul(old_borrow_index)` and `borrowed.mul(new_borrow_index)`. [4](#0-3)  These products are direct fixed-point multiplications through `scaled_to_original`, which delegates to `Ray::mul`. [5](#0-4)  A sufficiently large scaled-debt total therefore overflows the `i128` result when the index grows enough, even though the resulting borrow index itself remains below the configured index cap.

The borrow-index cap does not prevent this case: `update_borrow_index` first multiplies `old_index` by the interest factor and only afterward compares the product to `MAX_BORROW_INDEX_RAY`. [6](#0-5)  More importantly, the freezing overflow occurs when multiplying the outstanding scaled debt by an index during reward calculation, before the cap can bound the debt-value product.

### Impact Explanation

The overflow causes a permanent market-level denial of service. Once the stored scaled debt and accrued index reach the overflowing combination, every later accrual reattempts the same multiplication. Because market operations synchronize interest before mutating state, suppliers cannot withdraw, borrowers cannot repay, and liquidators cannot liquidate debt in the affected market. The existing regression test explicitly observes `MathOverflow`, verifies that `borrow_index < MAX_BORROW_INDEX_RAY`, and confirms that both `withdraw` and `repay` fail afterward. [7](#0-6) 

This permanently freezes user funds and prevents the market from operating until an out-of-band code or state repair is performed.

### Likelihood Explanation

The attack is economically constrained but does not require privileged execution. It requires a listed market whose configured caps and token supply admit a very large deposit, followed by borrowing a large fraction of that market using collateral supplied elsewhere. Both `supply` and `borrow` are ordinary controller entrypoints; `account_id = 0` allows the attacker to create the required account. [8](#0-7)  Once the position exists, any caller can trigger the condition through `update_indexes`; no privileged call is needed at that point. [1](#0-0) 

Likelihood depends on deployment-specific asset decimals, caps, liquidity, collateral value, and rate parameters. Markets with lower balances or caps small enough that `scaled_debt * index` cannot reach `i128::MAX` are not affected.

### Recommendation

Bound every multiplication before it is performed rather than relying on post-product index caps.

In `update_borrow_index`, cap the multiplication factor before multiplication, for example by comparing `interest_factor` with `MAX_BORROW_INDEX_RAY / old_index` or by using saturating fixed-point multiplication. In `calculate_supplier_rewards` and `scaled_to_original`, compute `scaled * index` with widened or saturating arithmetic and clamp debt/value intermediates before subtracting. Equivalent protection should be added to `update_supply_index` and `supply_index_reward_shortfall`, which perform the same class of scaled-share multiplication. [9](#0-8)  The result should prefer deterministic saturation to the protocol’s economic cap over reverting, while preserving the existing rounding and bad-debt invariants.

### Proof of Concept

The repository already contains a production-path regression test demonstrating the frozen-market state:

1. Create a high-decimal market.
2. Supply `1_000_000_000 * 10^18` raw units.
3. Borrow 98% of that amount using collateral in another market.
4. Advance accrual until the scaled debt multiplied by the grown index exceeds `i128::MAX`.
5. Call permissionless `update_indexes` for the affected `HubAssetKey`.
6. The call fails with `MathOverflow`; subsequent `withdraw` and `repay` calls fail for the same reason.

The relevant test constructs those exact positions and observes that the index cap did not engage before the overflow. [10](#0-9)  It then proves that exits and repayments remain blocked by the same `MathOverflow`. [11](#0-10)

pub fn update_supply_index(env: &Env, supplied: Ray, old_index: Ray, rewards_increase: Ray) -> Ray {
    if supplied == Ray::ZERO || rewards_increase == Ray::ZERO {

/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
    std::println!(
        "ray-value cliff reached after {years} years at 98 percent utilization on the XLM curve; last index x{:.1}",
        last.borrow_index as f64 / RAY as f64
    );
