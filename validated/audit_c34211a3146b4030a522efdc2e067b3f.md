## Finding [1](#0-0) 

### Title
Unchecked ERC20/TRC20 boolean return value in `IntentGatewayV2.withdraw` permits silent-fail token transfers to drain escrow accounting without paying beneficiaries - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.withdraw()` (Tron variant) settles escrowed order inputs and transaction fees using a raw low-level `.call` to the token's `transfer` selector, checking only that the call did not revert (`success`) but never inspecting the ABI-decoded boolean return value that ERC20/TRC20 explicitly permits tokens to use to signal failure without reverting.

### Finding Description
In `withdraw(WithdrawalRequest memory body, bool isRefund)`, both the per-token payout loop and the transaction-fee payout use: [2](#0-1) 

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```

The check only verifies the low-level call did not revert; it discards the returned data entirely and never decodes/validates it as `true`. Per the ERC20 standard, `transfer` is allowed to return `false` on failure instead of reverting — a compliant call to such a token (or a non-standard TRC20 on Tron, which is explicitly why this file avoids `SafeERC20.safeTransfer` even though `SafeERC20` is imported and aliased at the top of the contract) succeeds at the EVM/TVM call level while the token balance transfer silently does not happen.

Despite this, `withdraw()` unconditionally proceeds to decrement escrow accounting and emit success events regardless of whether the underlying value transfer actually occurred: [3](#0-2) 

The same pattern also affects the `SweepDust` governance path in `onAccept`, but the unprivileged-reachable route is `withdraw()`, invoked from the `RedeemEscrow`/`RefundEscrow` branches of `onAccept`: [4](#0-3) 

and from the `onGetResponse` refund path: [5](#0-4) 

Both are reached through ordinary relayed cross-chain message delivery (a relayer submitting a proof-backed POST/GET response), which is exactly the "relayed proof, dispatched request" surface in scope. `authenticate()` gates the caller/source of the request but does nothing to validate the token transfer outcome inside `withdraw()`.

### Impact Explanation
If the escrowed token (input token or fee token) is one that returns `false` instead of reverting on failed transfer (e.g. insufficient balance/allowance edge cases in certain token implementations, or paused/blacklisted-recipient tokens that return `false`), `withdraw()` will:
1. Mark the order commitment `_filled[body.commitment] = beneficiary` (irreversibly closing the order),
2. Decrement `_orders[body.commitment][token] -= amount` as if paid out,
3. Emit `EscrowReleased`/`EscrowRefunded`,

while the beneficiary receives nothing. The escrowed tokens remain stuck in the gateway contract with the accounting already zeroed out for that beneficiary/commitment, and there is no legitimate additional withdrawal path since the order is already marked filled/refunded. This is a permanent loss of user funds — the exact "unintended consequences" class flagged by the external report for unchecked return values on token transfer calls (analogous to `EToken.sol`/`USDEToken.sol` findings).

### Likelihood Explanation
The likelihood depends on a token used as an intent input/fee token exhibiting return-false-on-failure semantics — a documented, standards-compliant ERC20 behavior, and one the code's own comments/imports imply awareness of (raw `.call` used specifically to accommodate non-standard TRC20 tokens on Tron, which is the deployment target of this exact file). Any solver/order-filler routing through such a token, or a fee-token balance edge case at settlement time, triggers the silent failure without any additional attacker privilege — it requires only a normal cross-chain settlement/refund flow to complete with a marginal/failing transfer.

### Recommendation
Decode and validate the boolean return value (when present) from the low-level `token.call`, or replace the raw call with `SafeERC20.safeTransfer`/`safeTransferFrom` (already imported and used elsewhere in the sibling EVM `IntentGatewayV2.sol`) with an explicit compatibility fallback for non-standard TRC20 tokens that truly return no data, rather than accepting any non-reverting call as success.

### Proof of Concept
1. Configure an order input/fee token `T` that implements `transfer` to return `false` (not revert) when, e.g., the gateway's balance is momentarily insufficient due to a race/dust condition, or `T` is a token that blacklists `beneficiary` and returns `false` for blacklisted recipients (a real-world ERC20 pattern).
2. A relayer submits a valid `RedeemEscrow` proof for a filled order paying out in token `T` to a blacklisted/edge-case `beneficiary`.
3. `onAccept` → `withdraw()` executes `token.call(...)`; `T.transfer` returns `false` but the outer call does not revert, so `success == true`.
4. `withdraw()` proceeds: `_filled[commitment]` is set, `_orders[commitment][token] -= amount` is decremented, `EscrowReleased` is emitted — the order is permanently closed with no tokens delivered to `beneficiary`, and the escrowed `T` balance remains stuck in the contract unattributed to any recoverable claim.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
