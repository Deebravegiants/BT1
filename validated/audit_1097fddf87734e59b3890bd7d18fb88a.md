### Title
Consensus relayer reward silently skipped for entire batch when a non-consensus message occupies index 0 - (File: modules/pallets/consensus-incentives/src/impls.rs)

### Summary
`pallet-consensus-incentives` implements `FeeHandler::on_executed`, which `pallet-ismp`'s `Pallet::execute` calls after processing a relayer-submitted batch of ISMP messages [1](#0-0) . The handler determines whether *any* relayer in the batch gets paid solely by inspecting `messages.get(0)` — the first message in the whole submitted batch — and requires that first message to be a `Message::Consensus` variant in order to recover the signer/relayer account [2](#0-1) . If it is not, `maybe_relayer_account` is `None` and the whole reward-distribution loop over `StateMachineUpdated` events is skipped, even though later messages in the same batch may include valid, signed consensus messages that genuinely advanced the state machine height.

### Finding Description
`on_executed` receives `Vec<MessageWithWeight>` (the full batch of messages executed in one call, which may freely mix `Message::Consensus`, `Message::Request`, `Message::Response`, `Message::Timeout` per the shared `ismp::messaging::Message` enum) plus the `Vec<IsmpEvent>` produced by executing them [3](#0-2) . The relayer-identification logic only examines index 0:

```rust
let maybe_relayer_account = messages.get(0).and_then(|first_message| {
    if let Message::Consensus(consensus_msg) = &first_message.message {
        ...
        .map(|pub_key| pub_key.into())
    } else {
        None::<[u8; 32]>
    }
});
``` [2](#0-1) 

The subsequent reward-distribution loop is gated entirely on `if let Some(relayer_account) = maybe_relayer_account`, and iterates the already-collapsed `highest_per_state_machine` map derived from `StateMachineUpdated` events in the batch [4](#0-3) . There is no fallback that scans the rest of `messages` for a `Message::Consensus` entry, nor any per-`StateMachineUpdated`-event correlation back to whichever consensus message actually produced it. Consequently, whenever a relayer batch is executed with a non-consensus message first (e.g. `[Request, Consensus, Consensus, ...]` — a realistic composition since `pallet-ismp`'s `execute` accepts an arbitrary `Vec<Message>` in one call [5](#0-4) ), the entire batch's consensus reward is dropped, regardless of how many legitimate `StateMachineUpdated` events and signed consensus messages are present later in the array. This mirrors the reported bug class exactly: correctness/reward computation is gated on a property of the *first* array element instead of being evaluated per-element or independently of ordering.

### Impact Explanation
This causes relayers who legitimately deliver consensus updates (critical for keeping destination light clients current, as documented in the pallet's own README/reward mechanism [6](#0-5) ) to receive zero reward and zero reputation-asset mint for that batch whenever the message ordering happens to place a non-consensus message first. Because `LastRewardedHeight` is only advanced when `process_message` runs, this reward isn't merely delayed — it is permanently unpaid for the consensus progress covered by that batch (the reward formula is `(LatestHeight - PreviousHeight) * CostPerBlock`, and the next successful call will only reward the delta from the new baseline, meaning the skipped span is fully lost). This is a form of unbacked/lost fund distribution where the treasury retains funds that should have flowed to the relayer, functionally identical to the reported "user receives less rewards than eligible" bug — Medium severity, direct fund-accounting error reachable by any relayer submitting a mixed batch through the standard permissionless message-submission path.

### Likelihood Explanation
Message ordering within a batch is a normal, unprivileged, externally-influenced property: a batch executed via `pallet-ismp::execute` can contain any mix of message types depending on what a relayer chooses to submit or how messages happen to be queued/batched by tesseract or by any other unsigned submitter. No malicious intent is required — this can occur in ordinary operation whenever a relayer combines a consensus proof with other message types (or when a non-consensus message is queued ahead of a consensus message for gas-batching reasons), making the likelihood of triggering this at least occasionally moderate-to-high in production relaying.

### Recommendation
Do not gate reward eligibility on `messages.get(0)`. Instead, scan the full `messages` vector for `Message::Consensus` entries (there may legitimately be more than one, and rewards should be correlated per-consensus-message/`StateMachineUpdated` pair rather than assuming a single relayer signed the whole batch), recover the relayer account from whichever consensus message(s) are present, and only skip the reward path when no consensus message exists anywhere in the batch.

### Proof of Concept
1. A relayer (or the tesseract outbound task, per its own batching logic) submits `pallet-ismp::execute` with `messages = [Message::Request(..), Message::Consensus(valid_signed_consensus_proof)]` where the consensus message legitimately advances `StateMachineId::X` and produces an `Event::StateMachineUpdated { state_machine_id: X, latest_height: H }` in `events`.
2. `pallet-ismp::execute` calls `T::FeeHandler::on_executed(messages_with_weights, events)` [7](#0-6) .
3. Inside `on_executed`, `messages.get(0)` returns the `Request` message, which is not `Message::Consensus`, so `maybe_relayer_account` resolves to `None` [2](#0-1) .
4. The `if let Some(relayer_account) = maybe_relayer_account` block is skipped entirely; `process_message` is never invoked for state machine `X`, so no treasury transfer, no `RelayerRewarded` event, no reputation mint, and `LastRewardedHeight` is not updated [4](#0-3) .
5. On the next batch where a consensus message correctly lands at index 0, `calculate_reward` uses `LastRewardedHeight` (still stale from before step 1) as the baseline, so the relayer is only ever paid for blocks after that stale baseline plus whatever new blocks the second update covers — the block-span covered by the dropped batch is never compensated.

	pub fn execute(messages: Vec<Message>) -> Result<Vec<events::Event>, Error<T>> {
		let host = Pallet::<T>::default();

		let message_results = messages
			.iter()
			.map(|msg| handle_incoming_message(&host, msg.clone()))
			.collect::<Result<Vec<_>, _>>()
			.map_err(|err| {
				log::debug!(target: "ismp", "Handling Error {:#?}", err);
				Pallet::<T>::deposit_event(Event::<T>::Errors { errors: vec![err.into()] });
				Error::<T>::InvalidMessage
			})?;

		let messages_with_weights = message_results
			.iter()
			.zip(messages)
			.map(|(result, message)| MessageWithWeight { message, weight: result.weight() })
			.collect::<Vec<_>>();

		let events = message_results
			.into_iter()
			// check that requests will be successfully dispatched
			// so we can not be spammed with failing txs
			.map(|result| match result {
				MessageResult::Request { events, .. } |
				MessageResult::Response { events, .. } |
				MessageResult::Timeout { events, .. } => events,
				MessageResult::ConsensusMessage(events) => events.into_iter().map(Ok).collect(),
				MessageResult::FrozenClient(_) => vec![],
			})
			.flatten()
			.collect::<Result<Vec<_>, _>>()
			.map_err(|err| {
				log::debug!(target: "ismp", "Handling Error {:#?}", err);
				Pallet::<T>::deposit_event(Event::<T>::Errors { errors: vec![err.into()] });
				Error::<T>::InvalidMessage
			})?;

		T::FeeHandler::on_executed(messages_with_weights, events.clone())
			.map_err(|_| Error::<T>::ErrorChargingFee)?;

			// `(latest_commitment_height, previous_commitment_height)` pair on
			// every iteration and pays the same block-span reward N times.
			// Collapse the per-state-machine event stream to the single highest
			// `latest_height` so each state machine receives one reward per
			// batch, sized by the actual span of its commitment advance.
			let mut highest_per_state_machine: BTreeMap<StateMachineId, u64> = BTreeMap::new();
			for event in events {
				if let IsmpEvent::StateMachineUpdated(update) = event {
					highest_per_state_machine
						.entry(update.state_machine_id)
						.and_modify(|h| {
							if update.latest_height > *h {
								*h = update.latest_height;
							}
						})
						.or_insert(update.latest_height);
				}
			}

					StateMachineHeight { id: state_machine_id.clone(), height: latest_height };

					state_machine_height,
					state_machine_id,
					relayer_account.clone().into(),
				);
			}

```markdown
The pallet's core logic revolves around a reward mechanism triggered by successful consensus updates of a State machine.

### Reward Mechanism

* **Trigger**: The incentive process is triggered when the `on_executed` hook from the `FeeHandler` trait is called. The pallet filters for `ConsensusMessage` types.
* **Relayer Identification**: The pallet cryptographically recovers the relayer's public key from the signature attached to the `ConsensusMessage` to identify who should receive the reward.
* **Reward Calculation**: The reward is calculated based on how much "progress" a consensus update represents. The formula is:
  
  ```latex
    Reward=(LatestHeight - PreviousHeight) * CostPerBlock
  ```
    * **LatestHeight & PreviousHeight**: These values are fetched from the `IsmpHost` and represent the latest and previously known heights of the remote state machine.
    * **CostPerBlock**: This is a configurable value stored in the `StateMachinesCostPerBlock` map that defines the reward amount per block for each state machine.
* **Reward Distribution**: The calculated reward amount is transferred from the `TreasuryAccount` to the identified relayer.
* **Reputation Minting**: Alongside the token reward, the pallet mints a `ReputationAsset` of the same value to the relayer as an on-chain record of their contributions.
```
