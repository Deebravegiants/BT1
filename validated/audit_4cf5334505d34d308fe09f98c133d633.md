## Title
Webhook HMAC verification covers only the request body, not the `shop`/`topic`/`webhook-id` headers, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw request body. The `shop`, `topic`, and `webhook-id` values that are read from unauthenticated HTTP headers and then handed to the app's webhook handler as trusted, verified data are never included in the signed material. Any party able to obtain one valid `(body, hmac)` pair — including a merchant triggering a webhook on their own installed shop — can replay that pair against the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (and/or topic) header, and the signature check still passes.

### Finding Description
`Registry.process` gates all webhook handling on a single check: [1](#0-0) 

That check delegates to `Utils::HmacValidator.validate`, which computes the signature over `verifiable_query.to_signable_string` and compares it to `verifiable_query.hmac`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from headers that are never fed into the signature: [3](#0-2) 

After the HMAC check succeeds, `Registry.process` treats `request.shop` as trustworthy and hands it directly to the app's handler: [1](#0-0) 

The binding that should hold is:
`hmac_valid(body, secret) == true` should imply `(body, shop, topic, webhook_id)` together were what Shopify actually sent for that shop/topic. Instead the equality that actually holds is only `hmac_valid(body, secret) == true`, independent of `shop`/`topic`/`webhook_id`. This breaks the identity binding between the authenticated bytes (body) and the tenant/topic metadata the app acts on (`shop`, `topic`).

### Impact Explanation
Because the shared `api_secret_key` is the same for every shop that installs the app, any merchant can generate a legitimately-signed `(body, hmac)` pair for their own shop (e.g., by triggering a normal webhook event for their own store, which they fully control as an "unprivileged" merchant relative to other tenants). They can then replay that exact `raw_body` + `hmac` header to the app's webhook endpoint while setting `X-Shopify-Shop-Domain` to a victim shop's domain (and optionally a different registered topic). `HmacValidator.validate` still returns `true` because it never inspects the headers, and `Registry.process` dispatches the handler with `WebhookMetadata#shop` set to the victim's domain and attacker-chosen body content. Any app logic keyed by `shop` (e.g., upserting order/product/customer records, billing state, or triggering shop-scoped side effects) can be corrupted or cross-contaminated this way — a cross-tenant integrity/confidentiality impact.

### Likelihood Explanation
Any user of the gem who can install the app on a shop they control (a normal, unprivileged action) can trivially capture a valid `(body, hmac)` pair for arbitrary content and replay it with a spoofed `shop` header. No knowledge of `api_secret_key` is required — only the ability to receive one's own valid webhook, which is a basic capability of any merchant using the app. This makes the likelihood high wherever an app's webhook handler makes any tenant-scoped decision based on `WebhookMetadata#shop` or `#topic` without independently corroborating them (e.g., against a stored per-shop secret or session store), which the gem's public API implicitly encourages by exposing `shop`/`topic` as verified fields once `HmacValidator.validate` passes.

### Recommendation
Bind the identifying metadata to the signature, not just the payload bytes. Options:
- Compute the webhook signature (or an additional check) over `shop + topic + webhook_id + body`, or otherwise cryptographically bind the header values that the app relies on.
- At minimum, document loudly in `Webhooks::Request`/`Registry.process` that `shop`/`topic`/`webhook_id` are **unauthenticated** header values and that handlers must independently verify `shop` against their own session/store records before trusting it, rather than presenting `WebhookMetadata` as fully "verified" once `HmacValidator.validate` succeeds.
- Consider deriving `shop` exclusively from the verified session/store lookup rather than from the header value inside `WebhookMetadata`.

### Proof of Concept
1. App has two shops installed: `victim-shop.myshopify.com` and `attacker-shop.myshopify.com`, both sharing the app's single `api_secret_key`.
2. Attacker (a legitimate merchant of `attacker-shop`) triggers a normal webhook event on their own shop (e.g., updates a product), capturing the resulting POST request: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (a valid HMAC of `B` under the shared secret, computed by Shopify).
3. Attacker replays the exact same request to the app's webhook endpoint, but rewrites:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   - keeps `X-Shopify-Hmac-Sha256: H` and body `B` unchanged.
4. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` whose `shop` is `victim-shop.myshopify.com` but whose `to_signable_string` is still `B`.
5. `Utils::HmacValidator.validate` recomputes `HMAC(B, secret)` and finds it equals `H` — validation passes.
6. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-controlled data under `victim-shop`'s identity. [1](#0-0) [4](#0-3) [2](#0-1)

          received_signature = verifiable_query.hmac

module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end

      sig { returns(String) }
      def topic
        T.cast(shopify_header("topic"), String)
