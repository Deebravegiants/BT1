### Title
`CallDispatcher.dispatch` has no caller restriction, letting anyone drain any transient balance it holds - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher.dispatch(bytes)` is `external` with no access-control modifier at all — any address can call it directly with an arbitrary `Call[]` payload naming any contract as `to`. [1](#0-0)  The contract is shared across `IntentGatewayV2`/`ExtrinsicIntents` (predispatch/postdispatch calldata) and `HyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable` (post-mint/unlock calldata), and it also has an unrestricted `receive()` so it can accumulate ETH. [2](#0-1)  This mirrors the CVE-2022-23112 pattern: a component that is supposed to act only on behalf of a trusted orchestrator (the Jenkins Overall/Read caller in the CVE; the gateway/token contract here) is missing the permission check, so an unprivileged caller can direct it to "connect" to an attacker-chosen target using whatever balance/approvals it is currently holding.

### Finding Description
Every legitimate flow (`IntentGatewayV2._execute`, `IntentsBase._execute`, `WrappedHyperFungibleTokenUpgradeable.onAccept`) assumes it is the exclusive, atomic caller of `CallDispatcher.dispatch` within its own transaction, immediately followed by a sweep of any residual token/ETH balance back to the calling contract. [3](#0-2) [4](#0-3)  But `dispatch` itself enforces no `msg.sender` check, so nothing prevents a third party from calling `CallDispatcher.dispatch` directly at any point the contract holds a balance — e.g., between the moment assets are transferred to the dispatcher (`_sendValue(dispatcher, amount)` / `safeTransferFrom(msg.sender, dispatcher, amount)`) and the point the orchestrating contract's own `dispatch` call executes and sweeps the funds. [5](#0-4)  Because `CallDispatcher` is a single shared, stateless-permission contract used by multiple apps, any ETH sent to it via its open `receive()`, or any dust left over from an interrupted/failed sequence, sits under no owner check and can be swept out by anyone via a crafted `Call[]` that transfers the token/ETH to an attacker address.

### Impact Explanation
If `CallDispatcher` is ever left holding a balance outside of a fully atomic single-transaction orchestration (e.g., a reentrant/interleaved call sequence, an unswept dust remainder, or funds sent directly to its `receive()`), any unprivileged address can call `dispatch()` to redirect that balance to an address of their choosing — a direct, unauthorized fund-draining primitive analogous to using someone else's trusted "credentials" (the dispatcher's balance/allowances) against an attacker-specified destination, exactly the bug class described in CVE-2022-23112.

### Likelihood Explanation
Exploitability depends on `CallDispatcher` momentarily holding non-zero balance visible to an outside caller between the funding step and the orchestrator's own `dispatch`+sweep call within the same transaction (which normal EVM execution does not expose to interleaving from other transactions), or on residual balances left by reverted/partial `predispatch`/`postdispatch` sequences or direct sends to `receive()`. I could not fully verify, within the available index, whether any code path leaves state where `CallDispatcher` retains a balance across transaction boundaries (which would make this trivially exploitable) versus only holding funds transiently within a single atomic call from a trusted contract (which would make the missing check unreachable in practice). This uncertainty should be resolved with a live code review/session before treating this as a definitively exploitable finding.

### Recommendation
Restrict `CallDispatcher.dispatch` (and ideally the `receive()` path or fund sweeping) to a caller allowlist (e.g., the registered `IntentGatewayV2`/`ExtrinsicIntents`/`HyperFungibleToken` instances that are configured to use it), or make the dispatcher single-use/ephemeral per orchestration (e.g., deployed per-call via `CREATE2` and self-destructed/swept atomically) so no address other than the intended orchestrator can ever invoke it or benefit from any balance it holds.

### Proof of Concept
Conceptual PoC (unverifiable without a full session, since it hinges on the dispatcher retaining balance across calls):
1. Wait for/observe a state where `CallDispatcher` holds a non-zero ERC20 or ETH balance (e.g., direct transfer to its `receive()`, or dust left after a reverted predispatch/postdispatch sequence).
2. Call `CallDispatcher.dispatch(abi.encode(calls))` directly as any EOA, with `calls = [Call({to: token, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, balance)})]` (or a native transfer `Call` for ETH).
3. `dispatch()` performs `to.call(...)` with no caller check, transferring the dispatcher's held funds to the attacker. [1](#0-0)

```text
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
```
