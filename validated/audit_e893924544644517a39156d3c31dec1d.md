### Title
Webhook `shop`, `topic`, `webhook-id` and `api-version` headers are trusted without being covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` but binds the HMAC signature to the raw request body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers and never mixed into the signed material. `Registry.process` validates the HMAC and then dispatches the handler using these unauthenticated header values, so the "shop" identity that the app associates with a given webhook payload is never actually bound to the signature that proves the payload's authenticity.

### Finding Description
`HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to `verifiable_query.hmac` [1](#0-0) . For webhooks, `to_signable_string` returns only the raw body:

```ruby
def to_signable_string
  @raw_body
end
``` [2](#0-1) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all pulled from headers with no cryptographic binding to the signature at all:

```ruby
def topic
  T.cast(shopify_header("topic"), String)
end

def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [3](#0-2) 

`Registry.process` validates only the body's HMAC and then dispatches directly using these unauthenticated header fields:

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [4](#0-3) 

The identity binding that should hold is: `hmac_valid(raw_body) == true` **implies** `shop header == shop that Shopify actually generated this payload for`. In this implementation that equality does not hold — `hmac_valid(raw_body)` only proves the body bytes were produced by someone holding `api_secret_key`; it says nothing about which shop/topic/webhook-id the sender attaches via headers. Any actor capable of obtaining one genuine `(raw_body, hmac)` pair for a webhook topic (e.g., an attacker who installs the app on their own store and receives a real webhook — an ordinary, unprivileged action requiring no special credentials) can replay that exact body+HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain`, `x-shopify-topic`, `x-shopify-webhook-id`, and `x-shopify-api-version` headers with values pointing at a different, victim tenant. `HmacValidator.validate` still returns `true` because it only re-derives the signature from the (unchanged) body, so `Registry.process` happily hands the forged `WebhookMetadata` (with the attacker-chosen `shop`) to the host application's handler.

### Impact Explanation
This breaks the tenant boundary that webhook processing is supposed to enforce: a host application handler that trusts `WebhookMetadata#shop` (e.g., to look up the correct merchant record, update the correct shop's local data, or trigger side effects scoped to that shop) can be made to act on a real, HMAC-valid payload while believing it belongs to an unrelated shop, or under an unrelated topic. Since `topic` also flows unchecked into `@registry[request.topic]`, an attacker can additionally cause payloads meant for one topic to be dispatched to a handler registered for a completely different topic. This is a cross-tenant/cross-context confusion vulnerability reachable by any actor who can obtain one legitimate webhook delivery (installing the app on their own store is sufficient) — no leaked secret or privileged access is required.

### Likelihood Explanation
Medium-to-High: obtaining a genuine `(raw_body, hmac)` pair requires only installing the target app on any Shopify store (or otherwise triggering any webhook topic the app subscribes to), which is an ordinary, unprivileged action. Forging headers on an HTTP POST to the app's public webhook endpoint requires no special access. The only constraint is that the attacker's own webhook body must be usable/meaningful once attributed to the victim shop, but for many topics (e.g., app/uninstalled, shop/update, or any handler that primarily keys off the `shop` field in `WebhookMetadata` rather than deeply validating body contents) this is directly exploitable.

### Recommendation
Bind the identity fields into the signed material, not just the body. At minimum, `Request#to_signable_string` should incorporate `shop`, `topic`, `webhook_id`, and `api_version` (in addition to the body), or `Registry.process` should independently verify that these header values are consistent with data embedded/expected in the verified body before dispatch. Alternatively, require the host application to confirm that `request.shop` matches an already-known, provisioned session/shop before invoking the handler, rather than trusting the header value as-is.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw POST body `B` and the legitimate `x-shopify-hmac-sha256` header value `H` that Shopify computed over `B` with the app's real `api_secret_key`.
2. Attacker sends a new POST to the app's webhook endpoint with the *same* body `B` and header `x-shopify-hmac-sha256: H`, but sets:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: orders/create` (or any other registered topic)
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`= B`) and successfully matches `H` [5](#0-4) .
4. The handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: parsed(B), ...)` [6](#0-5) , causing the host application to process attacker-controlled data as if it originated from `victim-shop.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
