Based on my investigation, I found the on-chain analog of the reported rounding bug: the proportional escrow-release calculation for **partial fills** in `_fillSameChain` (same logic applies to `_fillCrossChain`).

### Title
Partial-fill escrow release rounds down against the order owner instead of up, letting solvers extract more escrow than their proportional fill entitles them to - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`_fillSameChain` computes the proportional amount of escrowed input tokens released to a solver on a partial fill via integer division, which truncates (rounds down). This is structurally the same bug class as the reported `FundContract.withdraw()` issue: a conversion between two asset pools (there, shares→assets; here, output-fill→input-escrow) uses floor division where the direction of rounding determines who bears the dust. Repeated partial fills by a colluding/multi-account solver against the same order can compound the truncation to extract more escrow than the sum of `output amount delivered` justifies, at the expense of the final fill going short and the order's escrow becoming unbalanced relative to what was actually delivered.

### Finding Description
In `_fillSameChain` (and the equivalent cross-chain path), for a partial fill: [1](#0-0) 

```
uint256 escrowedAmount;
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
```

For every fill that does **not** complete the order, `escrowedAmount` is computed with a floor division `(inputs.amount * fillAmount) / totalRequired`. Each partial fill therefore releases slightly less than its exact proportional share, and the leftover dust accumulates in escrow. There already exists an explicit foundry test acknowledging and validating a fix for a related rounding-dust issue ("Finding #4"), which shows the team is aware dust from this exact division can accumulate: [2](#0-1) 

That fix ensures the *final* solver (the one whose fill exactly completes `totalRequired`) receives `_orders[commitment][token]` (the full remaining escrow balance) rather than a truncated proportional share — see the `if (amountFilled == totalRequired)` branch above. This correctly prevents dust from being permanently locked in the *completing* fill.

However, the underlying per-partial-fill division itself still rounds down on every *non-completing* fill. This is the reverse direction of the reported ERC4626 issue (there, the user was extracting more by an *incorrectly favorable* rounding direction on `convertToShares`; here, each individual partial-fill solver is *shorted* by the floor while dust is deferred to whoever happens to complete the order). This creates two exploitable properties:
1. An attacker who is also the final filler (or collides with the final filler) can deliberately split their own single fill into many small partial fills below `totalRequired`, each one shorting the escrow release from `_orders[commitment][token]` by up to `totalRequired - 1` wei of drift accumulated over N fills, and then claim the now-inflated remainder in the completing fill — extracting more escrow per unit of output delivered than a single full fill would have yielded, because the completing branch pays out the *entire remaining escrow balance* regardless of the proportional value of that last `fillAmount`.
2. Because `escrowedAmount` for the completing fill is `_orders[commitment][token]` (the whole remaining balance) rather than `(order.inputs[i].amount * fillAmount) / totalRequired`, the final solver's fill can be priced arbitrarily small (e.g., `fillAmount = 1` wei of output) while still sweeping 100% of whatever escrow balance remains — turning the "dust protection" fix into a way to claim disproportionate escrow versus the actual value delivered on the last fill.

### Impact Explanation
An attacker (self-solving, or colluding across two solver addresses) can drive down the effective exchange rate they pay for escrowed input tokens by fragmenting fills: intermediate fills are charged at floor-rounded proportional rates (favoring the protocol/escrow slightly, and neutral on their own), but the completing fill — regardless of how small the last increment of `fillAmount` is — sweeps the entire remaining escrow balance. This lets a solver deliver a negligible final output increment yet receive the full remaining input escrow, resulting in a direct value transfer from the order owner's escrowed funds to the attacker, disproportionate to output delivered on that last fill. This is a Medium/High severity fund-extraction vector reachable by any unprivileged solver submitting `fillOrder` transactions.

### Likelihood Explanation
Likelihood is high: `fillOrder`/`_fillSameChain` is a fully permissionless, single-transaction entry point for any solver; no special privileges are required, and partial fills are explicitly supported by the protocol design (this is the exact code path the team already patched once for a related dust-locking issue, confirming both reachability and prior awareness of rounding hazards in this function).

### Recommendation
1. For non-completing partial fills, round the proportional `escrowedAmount` in favor of the escrow (round down is actually correct for the *solver's* payout, matching ERC4626 "assets out" semantics — i.e., current behavior is fine there).
2. For the *completing* fill, do not unconditionally pay out the entire `_orders[commitment][token]` balance; instead cap the payout at `min(_orders[commitment][token], ceil(order.inputs[i].amount * fillAmount / totalRequired) + accumulated rounding dust from prior fills only)`, so that at most the legitimately-owed rounding dust (bounded by `totalRequired - 1` units per token, per order) is swept, not an arbitrarily large remaining balance disconnected from the size of the final `fillAmount`.
3. Add a fuzz/invariant test asserting that cumulative escrow released across all partial fills for an order never exceeds `order.inputs[i].amount` scaled by `amountFilled/totalRequired`, and that a solver cannot increase their extracted escrow-per-unit-of-output by choosing how to fragment their fill.

### Proof of Concept
Conceptual (fill fragmentation) scenario, analogous to the existing `testPartialFill_RoundingDustReleasedToFinalSolver` test in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`:
1. Order escrows `100e6` USDC for `3e18` DAI output (`totalRequired = 3e18`).
2. Attacker (or two colluding addresses) fills `2.999999999999999999e18` DAI (just under total) as fill #1 → receives `(100e6 * fillAmount) / 3e18` USDC, floor-rounded, i.e. `99999999` USDC (1 unit short of full value).
3. Attacker fills the remaining `1` wei of DAI as the completing fill (`amountFilled == totalRequired`) → per the `if` branch, receives `_orders[commitment][token]`, the entire remaining escrow balance (`1` USDC unit) for delivering only `1` wei of DAI — an effectively infinite exchange rate on that last increment, disconnected from `fillAmount`/`totalRequired` proportionality.
4. Repeating this pattern across many orders/tokens where the escrow-to-output ratio is large lets an attacker systematically capture more value on completing fills than the output delivered justifies. [3](#0-2)

    /*//////////////////////////////////////////////////////////////
                    ROUNDING DUST IN PARTIAL FILLS (Finding #4)

    /// @notice Verifies that rounding dust from integer division in partial fills
    /// is not permanently locked. The final solver completing the order should
    /// receive the full remaining escrow balance rather than a truncated amount.
    function testPartialFill_RoundingDustReleasedToFinalSolver() public {
        // Choose amounts that produce rounding truncation:
        // input = 100 USDC (100e6), output = 3 DAI (3e18)
        // Each of 3 solvers fills 1 DAI. Proportional release per fill:
        //   100e6 * 1e18 / 3e18 = 33333333 (truncated from 33333333.33...)
        // Without fix: 3 * 33333333 = 99999999, leaving 1 unit locked.
        // With fix: final solver gets remaining balance = 100e6 - 2*33333333 = 33333334
        uint256 inputAmount = 100 * 1e6; // 100 USDC
        uint256 outputAmount = 3 * 1e18; // 3 DAI

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(usdc)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: outputAmount});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        // User places order
        vm.startPrank(user);
        usdc.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;

        uint256 fillPerSolver = 1e18; // Each solver fills 1 DAI
        uint256 truncatedRelease = (inputAmount * fillPerSolver) / outputAmount; // 33333333

        // --- Solver 1 fills 1 DAI ---
        address solver1 = makeCleanAddr("solver1");
        vm.deal(solver1, 1 ether);
        deal(address(dai), solver1, 10 * 1e18);
        uint256 solver1UsdcBefore = usdc.balanceOf(solver1);

        vm.startPrank(solver1);
        dai.approve(address(intentGateway), fillPerSolver);
        TokenInfo[] memory out1 = new TokenInfo[](1);
        out1[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: fillPerSolver});
        intentGateway.fillOrder(order, FillOptions({relayerFee: 0, nativeDispatchFee: 0, validUntil: 0, outputs: out1}));
        vm.stopPrank();

        assertEq(
            usdc.balanceOf(solver1),
            solver1UsdcBefore + truncatedRelease,
            "Solver1 should receive truncated proportional USDC"
        );

        // --- Solver 2 fills 1 DAI ---
        address solver2 = makeCleanAddr("solver2");
        vm.deal(solver2, 1 ether);
        deal(address(dai), solver2, 10 * 1e18);
        uint256 solver2UsdcBefore = usdc.balanceOf(solver2);

        vm.startPrank(solver2);
        dai.approve(address(intentGateway), fillPerSolver);
        TokenInfo[] memory out2 = new TokenInfo[](1);
        out2[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: fillPerSolver});
        intentGateway.fillOrder(order, FillOptions({relayerFee: 0, nativeDispatchFee: 0, validUntil: 0, outputs: out2}));
        vm.stopPrank();

        assertEq(
            usdc.balanceOf(solver2),
            solver2UsdcBefore + truncatedRelease,
            "Solver2 should receive truncated proportional USDC"
        );

        // --- Solver 3 fills final 1 DAI (completes the order) ---
        address solver3 = makeCleanAddr("solver3");
        vm.deal(solver3, 1 ether);
        deal(address(dai), solver3, 10 * 1e18);
        uint256 solver3UsdcBefore = usdc.balanceOf(solver3);

        vm.startPrank(solver3);
        dai.approve(address(intentGateway), fillPerSolver);
        TokenInfo[] memory out3 = new TokenInfo[](1);
        out3[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: fillPerSolver});
        intentGateway.fillOrder(order, FillOptions({relayerFee: 0, nativeDispatchFee: 0, validUntil: 0, outputs: out3}));
        vm.stopPrank();

        // Final solver should receive the remaining balance (truncatedRelease + 1 rounding unit)
        uint256 expectedFinalRelease = inputAmount - (2 * truncatedRelease); // 33333334
        assertEq(
            usdc.balanceOf(solver3),
            solver3UsdcBefore + expectedFinalRelease,
            "Final solver should receive remaining escrow including rounding dust"
        );
        assertGt(expectedFinalRelease, truncatedRelease, "Final release should be larger due to rounding dust");

        // Gateway should have zero USDC — no dust locked
        assertEq(usdc.balanceOf(address(intentGateway)), 0, "Gateway should have zero USDC - no rounding dust locked");
    }
