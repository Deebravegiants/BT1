### Title
Webhook `shop-domain` header is trusted for tenant attribution but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by HMAC-verifying the raw request body, then hands the caller-supplied `shop-domain` header straight through as the tenant identifier — without that header ever being part of the signed material. Any entity that can obtain one valid `(raw_body, hmac)` pair for the app (e.g., by installing the app on their own shop) can replay that pair to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header naming a different, victim shop, and the library will report the event as originating from the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

The `shop` accessor, however, is read directly from an attacker-controlled header and is never included in the signed data: [2](#0-1) 

`Registry.process` verifies the request purely via `Utils::HmacValidator.validate(request)`, which — per `HmacValidator#validate_signature` — only hashes `verifiable_query.to_signable_string` (the raw body) against `Context.api_secret_key`: [3](#0-2) 

Once that check passes, `process` immediately forwards `request.shop` — the unverified header value — to the handler as the tenant identity, with no further binding check between the signed body and the claimed shop: [4](#0-3) 

Because `Context.api_secret_key` is the single app-wide client secret (identical across every merchant installation of the app), any shop that installs the app receives webhook deliveries whose HMAC is computed with the *same* secret as every other shop's deliveries. A merchant that has installed the app can therefore capture one of their own legitimate webhook deliveries (valid `raw_body` + valid `hmac`), then re-POST that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with a different, victim shop's domain. `HmacValidator.validate` will still pass (it only checks the body/secret pair), and `Registry.process` will call the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain.

This is precisely the class of bug described in the reference report: a value that is *acted on* by downstream logic (here, the shop used for tenant attribution/storage) is not covered by the same integrity check (the HMAC) that authenticates the rest of the message — breaking the intended binding `verified_bytes == acted_upon_identity`.

### Impact Explanation
Any consumer of this gem's webhook processing API that uses `WebhookMetadata#shop` to key persisted data, dispatch tenant-scoped side effects, or make authorization decisions can have entirely attacker-controlled (but validly-signed) payloads attributed to a shop the attacker does not control. This is a cross-tenant data-integrity/access issue: a low-privilege actor (any merchant who can install the app) can inject fabricated webhook events into another merchant's data pipeline within the host application, without ever needing the victim's or the app's credentials.

### Likelihood Explanation
Exploitation requires only that the attacker install the target app on a shop they control (a normal, unprivileged action available to any Shopify merchant) and can send arbitrary HTTP requests to the app's public webhook endpoint — no `api_secret_key`, access tokens, or TLS interception are needed. The replay itself is a simple HTTP POST with a modified header, and the signature is verified successfully because the shop field was never part of what was signed.

### Recommendation
Bind the shop identity to the signed payload. At minimum, `Registry.process` (or `HmacValidator`) should require the webhook subscription's known `shop` (looked up via `webhook_id`, or via a per-shop secret/session) to match `request.shop`, or the signable string should incorporate the shop domain and topic so that a valid signature cannot be replayed against a different tenant. If Shopify's real webhook protocol does not sign the shop header, the gem should explicitly document that `WebhookMetadata#shop` is unauthenticated and must not be trusted for tenant attribution without additional verification (e.g., matching it against a previously registered webhook/shop record).

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, receiving a legitimate webhook delivery with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker crafts a new HTTP POST to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid), but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H` using the shared `api_secret_key`.
4. `Registry.process` invokes `handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed_body, ...))`, causing the host application to process an attacker-fabricated payload as if it came from `victim-shop.myshopify.com`. [4](#0-3)
