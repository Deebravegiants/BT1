### Title
Webhook `shop` domain is not covered by HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity via HMAC-SHA256 computed only over the raw request body [1](#0-0) , while the `shop` field used to identify the tenant that owns the webhook is read directly from an unauthenticated HTTP header [2](#0-1) . `Registry.process` validates the HMAC and then hands the handler a `WebhookMetadata` struct built from `request.shop`, without any check binding that header to the signed content [3](#0-2) .

### Finding Description
The identity binding that should hold is: `shop header value == shop that produced/authorized the signed body`. In this gem, `HmacValidator.validate` only proves `HMAC(raw_body, api_secret_key) == received_signature` [4](#0-3) ; it never incorporates the `shop-domain` header into the signed material. Since a single app-level `api_secret_key` is shared by Shopify to compute the HMAC for every shop that installs the app (there is no per-shop secret), any two webhook deliveries for the same app produce HMACs computed with the identical secret. An attacker who controls their own shop installation of the app receives legitimately-signed webhook deliveries (correct HMAC over a body they can also observe/replay). They can then replay that same body+HMAC pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header for a victim shop's domain. `HmacValidator.validate` still succeeds because it never looks at headers, only `@raw_body` [1](#0-0) . `Registry.process` then dispatches to the handler with `shop: request.shop` set to the attacker-chosen victim domain [3](#0-2) .

The gem's own documentation confirms host apps are expected to trust `data.shop` directly to key persistence/business logic (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), with no guidance to cross-check it against anything else [5](#0-4) . Because the gem presents `Registry.process` as having fully "verified the request did indeed come from Shopify" [6](#0-5) , host applications reasonably treat `data.shop` as an authenticated tenant identifier — but the gem's verification never actually binds shop identity to the signed bytes.

### Impact Explanation
This breaks the tenant/shop identity binding at the point the gem is documented as providing full authenticity verification, allowing an attacker who controls one shop's installation to inject attacker-controlled webhook payloads (topic/body pairs they can obtain legitimately-signed copies of) that get attributed to a victim shop, i.e. cross-tenant data injection into whatever job/queue/database record the host app associates with `data.shop`. This matches the High/Critical "cross-tenant access" impact class, since the whole authenticity guarantee of `Registry.process` is undermined for the identity field host apps rely on most.

### Likelihood Explanation
Any developer of an app that allows multiple/public installs can reproduce this: install the app on a shop they control, capture a real signed webhook delivery, then replay the same raw body and HMAC header to the app's public webhook URL with a forged `x-shopify-shop-domain` header pointing at any other shop. No access token, `client_secret`, or privileged credential is required — only the ability to install/interact with the app as an ordinary merchant and to send a normal HTTP POST to the app's publicly-reachable webhook endpoint.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-signed material, or otherwise require host applications to validate `request.shop` against a shop known to be associated with the signing HMAC (e.g. per-shop signing or a documented explicit cross-check against a stored `access_token`/shop record) before trusting `WebhookMetadata#shop`. At minimum, the gem's documentation and `Registry.process` contract should be updated to make explicit that the `shop` header is unauthenticated and must be independently validated by the host app.

### Proof of Concept
1. Install a target Shopify app on attacker-owned shop `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) and capture the raw POST body `B` and its `x-shopify-hmac-sha256` header `H` — `H = HMAC_SHA256(api_secret_key, B)`, valid because the app's `api_secret_key` is shared across shops.
2. Send a new POST to the app's public webhook endpoint with the same raw body `B`, the same `x-shopify-hmac-sha256: H`, `x-shopify-topic: orders/create`, but `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `@raw_body` only [1](#0-0)  and succeeds since the body/signature pair is unchanged.
4. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker-controlled content>, ...)` [7](#0-6) , causing the host application to process attacker data under the victim shop's tenant context.
