### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw request body only, while the `shop` attribute (sourced from the `shopify-shop-domain`/`x-shopify-shop-domain` header) is never included in that signature. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then trusts `request.shop` to attribute the payload to a tenant when invoking the handler. This mirrors the reported bug class: a field that is *acted on* (used for identity/tenant attribution) is not *covered* by the cryptographic check that is supposed to authenticate the request.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from an HTTP header with no cryptographic binding to the body or the HMAC: [2](#0-1) 

`HmacValidator.validate` / `validate_signature` compute the digest solely from `verifiable_query.to_signable_string` (i.e., the raw body) and compare it to the `hmac` header — the shop header plays no role in the computation: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately uses `request.shop` (the unauthenticated header) to construct `WebhookMetadata` passed to the app's handler, which uses it to attribute the webhook to a specific merchant/tenant: [4](#0-3) 

The equality that should hold is:
`shop_bound_by_hmac == shop_used_for_tenant_attribution`

In reality: `shop_bound_by_hmac = ∅` (the HMAC covers only the JSON body bytes) while `shop_used_for_tenant_attribution = header["shop-domain"]`. Because these two values are decoupled, anyone able to obtain one validly-signed `(raw_body, hmac)` pair for the app (e.g., by installing the app on their own free/development store and capturing a legitimate webhook sent by Shopify, since the HMAC secret is the app's single shared `client_secret`, not per-shop) can resubmit that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary victim `shop-domain` header. `HmacValidator.validate` still returns `true` (it never looks at the header), and `Registry.process` dispatches the payload to the handler tagged with the attacker-chosen shop.

### Impact Explanation
This is a cross-tenant confusion vector: an app built on this gem that trusts `WebhookMetadata#shop` (i.e., `request.shop`) to key business logic — e.g., updating a customer/order/inventory record "for shop X" — can be made to apply attacker-controlled webhook data under a victim shop's identity, or to trigger mandatory GDPR webhooks (`shop/redact`, `customers/redact`, `customers/data_request`) against a victim shop the attacker does not control. Since the only thing checked is that *some* valid webhook body+HMAC pair was produced by Shopify for *some* shop under the same app, this crosses a tenant boundary without any privileged credential belonging to the victim, satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Exploitability requires only: (1) the attacker being able to install the target app on any shop they control (a normal, unprivileged action available to any internet user who can create a Shopify dev/trial store), and (2) capturing one legitimately-signed webhook delivery from Shopify (trivial, since the app owner's webhook endpoint is typically public and delivery is automatic). No access to `api_secret_key`, access tokens, or victim credentials is needed — only the HMAC secret's *effect* (a valid signature Shopify itself produced), which is shared across all shops using the app. This keeps the likelihood realistic and squarely in scope (it does not require possession of `client_secret`, only a message Shopify signed with it).

### Recommendation
Bind the shop identity into the authenticated payload rather than trusting an unauthenticated header for tenant attribution:
- Include the `shop-domain` (and ideally `webhook-id`/`api-version`) header value in the HMAC-signable string (`to_signable_string`), matching the header content the handler will rely on, or
- Independently verify that the shop derived from the webhook belongs to a session/installation the app has record of, rather than trusting the header value verbatim once the raw-body HMAC passes.

### Proof of Concept
1. Attacker installs the victim's app on `attacker-shop.myshopify.com` (a normal, unprivileged signup).
2. Shopify sends a legitimate webhook to the app's endpoint with headers `shopify-shop-domain: attacker-shop.myshopify.com`, `shopify-hmac-sha256: <valid_hmac>` and some `raw_body`.
3. Attacker captures `(raw_body, valid_hmac)` — trivial since it's their own store's webhook traffic.
4. Attacker POSTs the same `raw_body` and `valid_hmac` to the same endpoint, but with header `shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` because it only hashes `raw_body`: [5](#0-4) 
6. `Registry.process` dispatches to the app's handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON>)`: [4](#0-3) 
7. Any app logic keyed on `data.shop` now processes attacker-controlled data as if it belongs to the victim shop.
