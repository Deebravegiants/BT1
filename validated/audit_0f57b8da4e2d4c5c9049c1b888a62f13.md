### Title
Webhook shop/topic/webhook-id headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the HMAC only over the raw request body (`to_signable_string` returns `@raw_body`), while the `shop`, `topic`, `api_version`, and `webhook_id` fields — which are read straight from HTTP headers — are never included in the signed material. `Registry.process` trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` passed to the app's handler without any additional binding to the HMAC. Any party capable of replaying a validly-signed webhook body (e.g., a user who owns/controls one shop connected to the app, or anyone who observes/replays one legitimate webhook delivery) can resend the same body with a different `shopify-shop-domain` header and have it accepted as coming from a different shop, since the signature check is indifferent to header values.

### Finding Description
`Request#hmac` and `Request#to_signable_string` establish what is authenticated: [1](#0-0) 

Only `@raw_body` is signed. `shop`, `topic`, `webhook_id`, and `api_version` are pulled directly from headers with no cryptographic binding: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop`/`request.topic` to dispatch the handler and build `WebhookMetadata`: [3](#0-2) 

`HmacValidator.validate` only checks `verifiable_query.to_signable_string` against the HMAC, i.e., only the body, never the headers: [4](#0-3) 

This breaks the identity binding: `hmac_valid(body) == true` should imply `shop_header == shop_that_actually_sent(body)`, but the equality the code actually checks is only `hmac_valid(body)`, independent of `shop_header`. Consequently `shop_header` can be swapped freely as long as the attacker can supply (or replay) any body/HMAC pair that was validly generated with the app's secret for any topic/shop — the header claiming which shop the payload belongs to is unauthenticated.

### Impact Explanation
Host applications rely on `WebhookMetadata#shop` (built directly from the unauthenticated `shop-domain` header) to determine which merchant/tenant a webhook payload belongs to, and route or persist data accordingly (order updates, GDPR data-request payloads, uninstall notifications, etc.). By resending a captured/legitimate body with an altered `shopify-shop-domain` header, an attacker can cause the app to attribute another shop's webhook data/event to a shop of the attacker's choosing (or vice versa), producing cross-tenant data confusion — e.g., causing a shop-uninstall or app/uninstalled webhook payload to be attributed to a victim shop, or having one shop's order/customer data associated with another tenant's session-scoped storage. This crosses the tenant boundary the HMAC is meant to protect and matches the report's underlying pattern of a field being acted upon without being part of the authenticated data.

### Likelihood Explanation
Likelihood is Low-to-Medium: the attacker needs access to at least one validly-signed webhook body (trivially obtainable by installing the app on a shop they control, since Shopify sends real webhooks to any installed shop) and the ability to resubmit that exact body to the app's webhook endpoint with a modified shop header, which is straightforward since headers are not part of the signed payload and most host frameworks accept arbitrary headers on POST requests.

### Recommendation
Include the security-relevant headers (`shop`, `topic`, `api_version`, `webhook_id`) in the signable string used for HMAC computation, or otherwise cryptographically bind them (e.g., derive the shop solely from a value embedded in the signed body, or require the caller to separately validate that `request.shop` matches an expected/allow-listed shop for the currently processing session before trusting it in `WebhookMetadata`).

### Proof of Concept
1. App has two shops installed: `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`.
2. Shopify sends a legitimate webhook to the app for `attacker-shop.myshopify.com` with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)`.
3. Attacker captures this request and resends it to the app's webhook endpoint, changing only the header `x-shopify-shop-domain` to `victim-shop.myshopify.com` (topic/body unchanged).
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes `HMAC(secret, B)` (body unchanged) and it matches — validation succeeds.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and dispatches to the app's handler, which now processes attacker-controlled event data as if it originated from the victim shop.
