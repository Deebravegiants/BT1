### Title
`_withdraw` releases escrowed intent funds via multiple unguarded external calls that can permanently freeze escrow if any single transfer or beneficiary reverts - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`_withdraw`, invoked from `IntentGatewayV2.onAccept` when a `RedeemEscrow`/`RefundEscrow` ISMP message is delivered, loops over every escrowed token and pushes funds out via `_sendValue` (raw ETH `.call`) or `IERC20.safeTransfer`, then pushes accumulated fee-token proceeds to the same beneficiary. Unlike `publicMint`, where a failed external call simply reverts an atomic, freely-resubmittable user transaction, here the "transaction" is a fixed, cryptographically-committed ISMP message body (token list, amounts, beneficiary) that a relayer must deliver byte-for-byte identically on every retry.

### Finding Description
`_withdraw` performs one push-transfer per escrowed token plus one for the fee token, all in the beneficiary's favor, with no isolation between them: [1](#0-0) 

Each iteration is a live external call: `_sendValue(beneficiary, amount)` (raw `.call{value}` that reverts on failure) for native tokens, or `IERC20(token).safeTransfer(beneficiary, amount)` for ERC-20s: [2](#0-1) [3](#0-2) 

This is reached from the unprivileged, relayer-driven `onAccept` handler (dispatched by the Hyperbridge ISMP host after a proof-verified cross-chain settlement message): [4](#0-3) 

If **any** of these calls fails — e.g. the beneficiary address is a contract without a `receive()`/payable fallback (native-token case, since `_sendValue` requires `sent == true`), or one of the escrowed ERC-20s is a pausable/blacklistable token (e.g. USDC/USDT) whose transfer to that specific beneficiary is disallowed, or the fee token transfer at line 476 fails — the entire `onAccept` call reverts. Because the message body (`beneficiary`, `tokens[]`, `commitment`) is fixed by the original order and cannot be altered by the relayer, retries hit the exact same revert every time. There is no way to skip the poisoned token/leg and release the rest, and no alternate pull-based recovery path.

### Impact Explanation
This differs materially from the reference `publicMint` finding, whose resolution ("failed transactions can be resubmitted") relied on the fact that the failing call was not intrinsically bound to fixed calldata — a user could alter parameters or wait out the failure. Here, the ISMP message content is committed and immutable once dispatched from the destination chain (`RedeemEscrow`/`RefundEscrow` bodies are derived from `order` and `_orders[commitment]` state). If the beneficiary (solver, for `RedeemEscrow`, or user, for `RefundEscrow`) is unable to receive even one of the escrowed tokens, or the fee-token leg reverts, the entire settlement is permanently unexecutable: the message can never be delivered successfully, the escrow entry is never zeroed, and the order can never be finalized (`_filled` is never set) or its underlying tokens ever released to anyone else. This is a permanent freezing of the escrowed input funds on the source chain — a Medium/High severity outcome, going beyond a mere resubmit-and-retry DoS because it targets a route that cannot recover on its own.

### Likelihood Explanation
The trigger conditions are realistic and partly attacker-controllable: an order's `beneficiary`/`solver` address is chosen by the filler for `RedeemEscrow`, and the `user` for `RefundEscrow` is the order's own creator — either party (or a malicious actor front-running/targeting a rival solver) can construct an order or fill whose beneficiary is a non-payable contract or is deny-listed on one of the multiple escrowed tokens, deliberately or accidentally freezing that specific escrow forever. No special privileges are required; a single order placement plus fill is enough to reach `_withdraw` through the normal, unprivileged ISMP settlement path.

### Recommendation
Isolate each token release from the others (e.g. wrap each transfer/`_sendValue` in a try/catch or a low-level call whose failure is only recorded, not reverted-on) and move to a pull-based claim pattern for the beneficiary, rather than pushing every leg atomically inside `onAccept`. At minimum, ensure a single poisoned leg (an unreceivable ETH beneficiary, a blacklisted ERC-20 recipient, or a reverting fee-token transfer) cannot block finalization and release of the other, healthy legs of the same escrow.

### Proof of Concept
1. User places a cross-chain order whose `output.beneficiary` (for `RedeemEscrow`) or `order.user` (for `RefundEscrow`) is set to a contract address with no `receive()`/payable fallback, and whose escrow inputs include the native token (`address(0)`).
2. Order is filled/cancelled normally; the destination or source gateway dispatches the `RedeemEscrow`/`RefundEscrow` ISMP POST request with the fixed `WithdrawalRequest` body.
3. Relayer delivers the message; `IntentGatewayV2.onAccept` → `authenticate` → `withdraw(body, ...)` → `_withdraw` is invoked.
4. Inside the loop, `_sendValue(beneficiary, amount)` at [5](#0-4)  reverts because `beneficiary` cannot accept ETH, causing the whole `onAccept` transaction — and hence the entire settlement — to revert.
5. Any relayer resubmitting the identical proof/message hits the same revert indefinitely; the escrowed tokens (including any non-native legs in the same `body.tokens[]` array) remain locked in the gateway with no code path to release them.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        if (finalize) {
            uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
            if (fees > 0) {
                delete _orders[body.commitment][TRANSACTION_FEES];
                IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
            }

            if (isRefund) {
                emit EscrowRefunded({commitment: body.commitment, tokens: body.tokens});
            } else {
                emit EscrowReleased({commitment: body.commitment, tokens: body.tokens});
            }
        }
    }
