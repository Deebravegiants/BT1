## Analysis

The Ostium exploit's core mechanic — a price the protocol trusted because it passed a signature/registration check, with no sanity check against real market value, then fed directly into a payout calculation — has a structural analog in Hyperbridge's Phantom Order price-snapshot pipeline used for intent quoting.

`aggregatePhantomBids`/`isVerifiedSolverBid` treats a bid as trustworthy purely because its solver signature recovers to the sender and that sender's EOA is EIP-7702-delegated to the (public, well-known) `SolverAccount` implementation contract — there is no registration or permissioning beyond self-delegation, which any EOA can perform unilaterally (exactly as Simplex's own `DelegationService.setupDelegation` does, with no protocol-side gate). [1](#0-0) [2](#0-1) [3](#0-2) 

Once "verified," a leg's price is a `weightedMedian` — explicitly documented as a *selection*, not a blend — so a solver holding over half a leg's weight publishes its exact quoted number verbatim, with no bound against a reference price: [4](#0-3) [5](#0-4) 

That published median is then consumed directly to size real orders: `PhantomSnapshotIntentQuoteStrategy.quoteSnapshot` computes `amountOut = (netAmountIn * snapshot.medianPrice) / snapshot.standardAmount` with only structural validation (`standardAmount>0`, `medianPrice>0`, `bidCount>0`), never a deviation/sanity check against any independent reference: [6](#0-5) [7](#0-6) 

The docs explicitly recommend this as the source of truth for constructing real `placeOrder` amounts: [8](#0-7) [9](#0-8) 

This is the same failure shape as Ostium: an "authorized-looking" but economically ungrounded price is accepted and used to move real value, because the only gate is identity/authorization, not plausibility. The weight-by-real-inventory design limits — but does not eliminate — this, since it only requires an attacker to hold a controlling share of a *particular leg's* backing inventory (realistic on thin/low-liquidity corridors), not the whole market.

### Title
Unbounded Phantom-order price snapshot lets a self-delegated solver dictate real IntentGateway order pricing - (File: sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts)

### Summary
`aggregatePhantomBids` treats a bid as trustworthy solely because it carries a valid solver signature and the sender is EIP-7702-delegated to the public `SolverAccount` contract — a self-service action any EOA can perform without permission. It never checks the *plausibility* of the quoted price against any independent reference. Because `weightedMedian` is a selection (it returns one bidder's raw number) rather than a blend, a solver controlling the majority of real inventory for a specific, thinly-quoted leg can publish an arbitrary price. That price is persisted as `PhantomOrderPriceSnapshotV2` and consumed verbatim by `PhantomSnapshotIntentQuoteStrategy` to compute the `amountIn`/`amountOut` the SDK recommends for a real `placeOrder` call — the exact same "authorized-but-unvalidated report drives an on-chain payout" pattern that let Ostium's exploiter dictate a fake BTC price.

### Finding Description
`isVerifiedSolverBid` (`sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts:913-979`) accepts a bid once: (1) the solver signature recovers to the sender over the correct userOpHash, (2) the nonce binds it to this order/session, and (3) the sender's EOA is EIP-7702-delegated to a configured `SolverAccount` address. None of these checks constrain the *value* being quoted — they only authenticate *who* is quoting. Delegation to `SolverAccount` is a self-service, permissionless action (`DelegationService.setupDelegation`, `sdk/packages/simplex/src/services/DelegationService.ts:404-486`); any attacker can perform it directly with `signAuthorization`, with no protocol-level registration or allowlisting.

Per-leg pricing (`sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts:1523-1563`) weights each quote by the bidder's real balance of that leg's output token and then applies `weightedMedian`, which — per the pipeline's own documentation — "returns one bidder's exact integer, so a solver holding over half the leg's weight sets the published price verbatim" (`sdk/packages/indexer/docs/ai/flows/phantom-price-snapshot-to-pool-rates-phantombidwindowexhausted.md:11-13`). There is no bound comparing the published price against a market reference, and `validateSnapshot` (`sdk/packages/sdk/src/protocols/intents/quote/phantomSnapshot.ts:132-145`) only checks structural non-zero fields, not plausibility.

The resulting `medianPrice` is fed directly into `quoteSnapshot` to compute real order amounts (`sdk/packages/sdk/src/protocols/intents/quote/phantomSnapshot.ts:83-101`), and the docs instruct integrators to use those amounts verbatim for `order.inputs`/`output.assets` in a real `placeOrder` call (`docs/content/developers/evm/intent-gateway/placing-orders.mdx:225-234`).

### Impact Explanation
An attacker who dominates the real, on-chain-verifiable inventory backing one leg of a thinly-quoted Phantom pair (realistic for low-liquidity corridors such as the documented USDC/cNGN pair) can publish an arbitrarily skewed price. Any counterparty (a user or integrator) who prices a real order via `quoteIntent({strategy: "phantom_snapshot"})` and places it on that basis will escrow the wrong amount of tokens relative to the requested output, or receive an output amount computed from a fabricated rate. A solver (including the attacker acting as filler) can then fill that order at the distorted terms, extracting value directly from the escrowed user funds — a concrete theft of funds triggered by an unauthenticated-for-value price input, mirroring Ostium's mechanism where a signature-valid but economically fabricated report drove a real payout.

### Likelihood Explanation
Delegating to `SolverAccount` requires no permission and is a documented, self-service EIP-7702 action. Dominating the weight of a single leg only requires holding more of that leg's output token on the destination chain than any other bidder for that specific window — plausible on illiquid or newly-supported pairs, and the attacker controls the timing (bid right before a target window closes). The barrier is capital-for-one-leg, not a protocol-level trust compromise, making this considerably easier to stage than a validator/consensus-level attack.

### Recommendation
- Bound the accepted `medianPrice` (and the underlying quotes contributing to it) against an independent reference price (e.g., a second oracle, a TWAP, or cross-checking against `indexed_rates`/on-chain DEX pools) before persisting a `PhantomOrderPriceSnapshotV2`, rejecting or flagging snapshots that deviate beyond a configured tolerance.
- Require a minimum number of independent, non-affiliated bidders (not just non-zero weight) per leg before a snapshot is considered authoritative, so a single controlling solver cannot unilaterally set the published rate.
- Treat `phantom_snapshot`-derived amounts as advisory rather than authoritative in the SDK/docs, and recommend integrators cross-check against `indexed_rates` or apply an explicit slippage/sanity bound before submitting `placeOrder`.

### Proof of Concept
1. Generate a fresh EOA and self-sign an EIP-7702 authorization delegating it to the public `SolverAccount` contract address for the target chain (no registration needed — mirrors `DelegationService.setupDelegation`, `sdk/packages/simplex/src/services/DelegationService.ts:404-486`), then submit the delegation transaction directly.
2. Acquire a small amount of the target leg's output token (e.g., cNGN) on the destination chain — enough to exceed the combined weight of any other bidder quoting that leg in the current Phantom bid window (trivial on a thin/low-competition corridor).
3. Submit a UserOperation-style bid for the order/leg with a solver signature over the correct `userOpHash`, bound via the nonce key to the target commitment/session (satisfying `isVerifiedSolverBid`, `sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts:913-979`), quoting an extreme output amount.
4. When `PhantomBidWindowExhausted` fires, `aggregatePhantomBids` counts the bid (delegation + signature check pass), and since the attacker holds the dominant weight for that leg, `weightedMedian` publishes the attacker's exact quoted number into `PhantomOrderPriceSnapshotV2` (`sdk/packages/sdk/src/protocols/indexer/.../handlePhantomOrderPrices.handler.ts:208-226`).
5. Any integrator calling `IntentGateway.quoteIntent({ strategy: "phantom_snapshot", ... })` receives `amountIn`/`amountOut` computed from the poisoned median (`sdk/packages/sdk/src/protocols/intents/quote/phantomSnapshot.ts:83-101`) and, following the documented flow, places a real order using those amounts (`docs/content/developers/evm/intent-gateway/placing-orders.mdx:225-234`).
6. The attacker (or a colluding filler) fills that order via the real `fillOrder` path at the distorted terms, extracting the mispriced value from the victim's escrowed funds.

async function isDelegatedToSolverAccount(
	evmRpcUrl: string,
	account: string,
	solverAccounts: readonly string[],
): Promise<boolean> {
	const response = await rpcCall(evmRpcUrl, {
		id: 1,
		jsonrpc: "2.0",
		method: "eth_getCode",
		params: [account, "latest"],
	})
	// Anything that is not a code string means the node did not answer the question. Reading that
	// as "no delegation" is how a throttled endpoint silently unseats a real solver: the bid is
	// dropped, the legs only it quoted vanish, and the pool reports zero depth it actually has.
	if (typeof response.result !== "string") {
		throw new PhantomRpcError(`eth_getCode returned no code for ${account} on ${evmRpcUrl}`)
	}

	const code = response.result.toLowerCase()
	if (!code.startsWith(DELEGATION_INDICATOR_PREFIX)) return false

	const delegate = `0x${code.slice(DELEGATION_INDICATOR_PREFIX.length)}`
	return solverAccounts.some((solverAccount) => solverAccount.toLowerCase() === delegate)
}

	private quoteSnapshot(
		params: QuoteIntentParams,
		protocolFeeBps: bigint,
		snapshot: PhantomOrderPriceSnapshot,
	): PhantomSnapshotQuoteIntentResult {
		if (params.amountIn !== undefined) {
			const netAmountIn = deductProtocolFee(params.amountIn, protocolFeeBps)
			const amountOut = (netAmountIn * snapshot.medianPrice) / snapshot.standardAmount
			if (amountOut <= 0n) {
				throw new InvalidPhantomSnapshotError(snapshot.commitment, "quote rounds down to zero output")
			}
			return this.buildResult("EXACT_INPUT", params.amountIn, amountOut, protocolFeeBps, snapshot)
		}

		if (params.amountOut === undefined) throw new Error("Quote amount is missing after validation")
		const netAmountIn = divCeil(params.amountOut * snapshot.standardAmount, snapshot.medianPrice)
		const amountIn = grossUpForProtocolFee(netAmountIn, protocolFeeBps)
		return this.buildResult("EXACT_OUTPUT", amountIn, params.amountOut, protocolFeeBps, snapshot)
	}

	private validateSnapshot(snapshot: PhantomOrderPriceSnapshot): void {
		if (snapshot.standardAmount <= 0n) {
			throw new InvalidPhantomSnapshotError(snapshot.commitment, "standardAmount must be greater than zero")
		}
		if (snapshot.medianPrice <= 0n) {
