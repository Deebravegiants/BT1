### Title
Withdraw and borrow authorize against the stale stored `account.owner` instead of the live position-NFT owner, so a prior owner keeps full spending authority after transferring the NFT - (File: contracts/controller/src/account.rs)

### Summary
`withdraw`, `borrow`, `multiply`, `flash_position`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, and `migrate_from_blend` all gate account access through `require_owner_or_delegate` / `is_owner_or_delegate`, which compares `caller` to the `owner` field stored inside the `Account` struct at creation time. Ownership of an account, however, is defined by the position-NFT token (`owner_of`), and NFT transfer is an in-scope unprivileged action. Nothing in the controller resynchronizes `account.owner` on or after an NFT transfer, so after selling or transferring the position NFT, the previous owner (and their registered delegates) can still pass the authorization check and drain the account's collateral, while the actual new NFT holder is rejected.

### Finding Description
In `contracts/controller/src/account.rs`:

- `create_account` fixes `account.owner` once, at mint: `let account = Account { owner: owner.clone(), ... }` (account.rs:64-70).
- `is_owner_or_delegate` decides spending authority purely from that stored field: `if caller == owner { return true; }` plus a delegate-list lookup keyed by the stored owner (account.rs:115-127).
- `require_owner_or_delegate` panics only when `is_owner_or_delegate` returns false (account.rs:130-140).
- In contrast, `require_account_owner` reads `storage::account_owner(env, account_id)` and compares it to the caller (account.rs:143-148) — a separate owner source used only for `renew_account`/`add_delegate`/`remove_delegate`. The fund-moving paths never consult it.

There is no code path that writes `account.owner` after creation — it is set only inside `create_account`. Meanwhile the position NFT is freely transferable via the stock OZ `NonFungibleToken`/`transfer`/`transfer_from` surface on `PositionNft` (contract.rs:131-133), and `mint`/`burn` are controller-only but transfer is not. So the two notions of "owner" diverge permanently the moment an NFT moves:

- NFT `owner_of` → new holder (owns the account economically and controls `renew_account`/delegate management via `require_account_owner`).
- Stored `account.owner` → old holder (retains `require_owner_or_delegate` authority over `withdraw`, `borrow`, and all strategy entrypoints).

This is the analog of the CVE class: an authorization decision made against stale/incorrect ownership state rather than the authoritative ownership record, granting a no-longer-authorized party access to protected resources.

### Impact Explanation
Theft of user funds. A seller lists/sells their position NFT (or is tricked into transferring it). After the transfer settles, the seller calls `controller.withdraw(caller=seller, account_id, ...)` — `caller.require_auth()` succeeds because the seller signs, and `require_owner_or_delegate` succeeds because `account.owner` still equals the seller. All withdrawable collateral is pulled to an account the seller no longer owns under the NFT record. Alternatively the seller calls `borrow` to max out debt against the collateral and withdraws the proceeds, leaving the NFT buyer with an insolvent husk. Delegates registered under the old owner also retain authority (`is_owner_or_delegate` falls back to the delegate list keyed by stored owner), so a stale position-manager delegation compounds the exposure.

### Likelihood Explanation
The attack requires only an NFT transfer followed by a standard `withdraw`/`borrow` call by the prior owner — both fully unprivileged, in-scope actions. Any secondary-market trade, OTC sale, wallet migration, or accidental transfer of a position NFT creates the window, and it never closes because `account.owner` is immutable. The check itself is a plain equality test with no expiry, so the exploit is deterministic and repeatable on every market the account holds.

### Recommendation
Make the fund-moving paths resolve ownership the same way `require_account_owner` does: read the live owner from the position NFT (`storage::account_owner` / `owner_of`) inside `is_owner_or_delegate`/`require_owner_or_delegate` instead of trusting `account.owner`, or remove `account.owner` from `Account` entirely and always consult the NFT. Key the delegate list to the current NFT owner (or to the `account_id`) and clear/re-scope delegates on NFT transfer so stale delegations cannot persist across ownership changes.

### Proof of Concept
1. Alice calls `supply(caller=alice, account_id=0, spoke_id, hub_asset, amount)` → account 1 created, NFT id 1 minted to Alice; `Account.owner = alice` is stored (account.rs:64-70).
2. Alice transfers NFT id 1 to Bob via `position_nft.transfer`/`transfer_from` (stock OZ surface, contract.rs:131-133). NFT `owner_of(1) = bob`; `Account.owner` remains `alice`.
3. Alice calls `withdraw(caller=alice, account_id=1, hub_asset, to=alice, amount)`. `alice.require_auth()` passes; `require_owner_or_delegate` hits `caller == account.owner` (account.rs:121) and passes despite Alice no longer owning the account.
4. Collateral is released to Alice; Bob — the legitimate owner per the NFT — has no path to prevent it and cannot even pass `require_owner_or_delegate` himself for `withdraw` (`bob != account.owner`, and he is not in the delegate list stored under `alice`).

Consistency evidence: `renew_account`/`add_delegate`/`remove_delegate` already treat `storage::account_owner` (the NFT owner) as authoritative (account.rs:217-258), confirming the codebase recognizes NFT ownership as the real record — the monetary paths simply fail to enforce it.

Note on confidence: the divergence between the stored `Account.owner` and NFT `owner_of`, and the absence of any write to `account.owner` post-creation, are established by the code above. The exact internals of `storage::account_owner` were not read in this pass; if it were to return the stored `account.owner` rather than the NFT owner, then `require_account_owner` would share the same staleness, which would strengthen (not weaken) the finding.
