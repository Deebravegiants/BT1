### Title
Webhook `shop-domain` and `topic` headers are not covered by the HMAC signature, enabling cross-tenant webhook impersonation - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the webhook HMAC over the raw body only, while the `shop`, `topic`, and `webhook_id` values used by `ShopifyAPI::Webhooks::Registry.process` to attribute and route the webhook are read from unsigned HTTP headers. This breaks the intended binding `hmac == sign(secret, shop || topic || body)`; in reality `hmac == sign(secret, body)` only, so `shop` (tenant identity) and `topic` are free variables an attacker can set independently of a valid signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, and `#webhook_id` are read straight from HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`) that are never mixed into `to_signable_string`: [2](#0-1) 

`Registry.process` validates the HMAC (body only) and then trusts `request.shop`, `request.topic`, and `request.webhook_id` verbatim to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

Because the signature only authenticates the byte content of the body, any `(raw_body, hmac)` pair that was ever legitimately produced by Shopify for the app's own `api_secret_key` remains valid for that body forever, regardless of which shop headers are attached to it. An attacker who can install the app on their own store (unprivileged relative to any other tenant) receives real webhook deliveries — each a valid `(body, hmac)` pair signed with the app's secret. They can then replay that exact body/hmac to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header (and/or `X-Shopify-Topic`) to impersonate a different, victim shop. `HmacValidator.validate` still returns `true` because it only checks `@raw_body`, and `Registry.process` will happily dispatch the handler with `shop: <victim-shop>`, `topic: <attacker-chosen-topic>` even though neither was part of the signed payload.

### Impact Explanation
This is a cross-tenant identity spoofing vector: the shop-to-webhook binding that application handlers rely on for tenant isolation is not authenticated. An app handler that keys writes/lookups off `WebhookMetadata#shop` (e.g. to update per-shop billing state, uninstall/redact data, or trigger shop-scoped side effects) can be made to act on behalf of an arbitrary victim shop using a signature that was only ever valid for the attacker's own, differently-shaped body content. This matches the "cross-tenant access" High/Critical impact category since it lets an attacker with only their own (unprivileged) shop installation forge webhook attribution for any other merchant.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the app (a normal, unprivileged onboarding flow for any public Shopify app) to obtain at least one legitimately-signed `(body, hmac)` sample, then resend it with modified `shop-domain`/`topic` headers — no possession of `api_secret_key` or any other credential is required. This is straightforward to automate and does not depend on any host-application misuse; the gem's own `Request`/`Registry` API surfaces `shop` and `topic` as if they were authenticated when they are not.

### Recommendation
Bind `shop-domain`, `topic`, and `webhook_id` into the signed material verified by `HmacValidator`, or otherwise cryptographically tie the webhook's declared shop/topic to the signature (e.g., include them in `to_signable_string`, or independently confirm the shop against a store known to be associated with the specific `webhook_id`/subscription before dispatch). At minimum, document in `Webhooks::Request` that `shop`/`topic`/`webhook_id` are unauthenticated and must not be used for tenant-identity decisions without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own (attacker-controlled) shop `attacker.myshopify.com`, receiving a legitimate webhook delivery with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for the app's `api_secret_key`) and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker resends the identical raw body `B` and header `X-Shopify-Hmac-Sha256: H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (and optionally a different `X-Shopify-Topic`).
3. `Utils::HmacValidator.validate(request)` calls `request.to_signable_string`, which returns only `B`; since `H` is a valid HMAC of `B`, validation succeeds: [4](#0-3) 
4. `Registry.process` proceeds to call `handler.handle` with `shop: "victim.myshopify.com"` even though that value was never covered by the signature, demonstrating the broken shop-identity binding.
