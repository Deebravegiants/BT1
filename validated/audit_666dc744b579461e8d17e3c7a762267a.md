### Title
Webhook shop-domain and topic headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then dispatches the handler using the `shop`, `topic`, and `webhook_id` values taken from unauthenticated HTTP headers. Because the HMAC only signs the body, any attacker who possesses one valid `(body, hmac)` pair — trivially obtainable by installing the app on their own shop — can replay that pair against the webhook endpoint while substituting an arbitrary victim shop domain, causing the host app to process attacker-controlled data as if it originated from the victim tenant.

### Finding Description
`Utils::HmacValidator.validate` computes the expected signature purely from `verifiable_query.to_signable_string` and the app's shared secret: [1](#0-0) 

For a webhook `Request`, `to_signable_string` returns only the raw body — the `shop`, `topic`, `api_version`, and `webhook_id` headers are read separately and are never part of the signed material: [2](#0-1) 

`Registry.process` then validates the HMAC and, immediately after, dispatches the handler using the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id`: [3](#0-2) 

This breaks the identity binding `shop authenticated by HMAC == shop acted upon by the handler`. The HMAC only proves "this body was signed with the app's secret"; it proves nothing about which shop sent it. Since a single app's `client_secret` is shared across every shop that installs the app, an attacker who installs the app on their own (attacker-controlled) shop legitimately receives real webhooks with valid `(raw_body, hmac)` pairs signed with that shared secret. The attacker can then POST that exact body and HMAC to the app's webhook endpoint while setting `x-shopify-shop-domain` (and optionally `x-shopify-topic`) to a victim shop's domain. `HmacValidator.validate` still passes (it never looked at those headers), and `Registry.process` calls the registered handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` attributing the attacker's body to the victim shop.

### Impact Explanation
Any host application that trusts `WebhookMetadata#shop` returned by `Registry.process` to key writes, look up the corresponding merchant session/access token, or trigger shop-scoped business logic (e.g., updating settings, mandatory compliance webhooks such as `customers/redact` or `shop/redact`, order/inventory sync) can have that logic executed against, or attributed to, a shop the attacker does not control. This is a cross-tenant confusion vulnerability: the attacker only needs to control one shop that installs the app to forge events for arbitrary other shops using that app, without ever obtaining the target's credentials.

### Likelihood Explanation
Exploitation requires no privileged access beyond installing the target app on any shop the attacker controls (a normal, unprivileged action available to any merchant/developer), and no possession of the app's `client_secret`, access tokens, or victim credentials. Capturing one's own legitimately delivered webhook body/HMAC pair and replaying it with a modified `shop-domain` header is straightforward and fully reachable through this gem's documented `Registry.process` entry point.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the HMAC-verified material, or otherwise authenticate the header-derived shop against an independent trusted channel (e.g., cross-check against the shop stored for a specific webhook subscription ID that was registered earlier) before dispatching to a handler. At minimum, document that `WebhookMetadata#shop` is not cryptographically authenticated and must not be trusted without additional verification by the host application.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC-SHA256(client_secret, B)`).
2. Attacker replays a POST to the app's webhook endpoint with the same body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` recomputes `HMAC-SHA256(client_secret, B)` and finds it matches `H`, so validation passes: [4](#0-3) 
4. The registered handler is invoked with `WebhookMetadata` whose `shop` is `victim-shop.myshopify.com`, even though the body/content actually originated from the attacker's own shop.
