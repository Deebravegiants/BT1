### Title
User-controlled route `swap` bytes let attacker-deployed contracts run under the swapper's authorization tree and drain wallet tokens - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The controller's router-strategy entrypoints (`swap_collateral`, `swap_debt`, `multiply`, `repay_debt_with_collateral`) accept opaque `swap: StrategySwap` bytes and hand them to the configured router inside the caller's `require_auth` context. The router resolves pool/token addresses straight out of that payload with no allowlist, so a malicious route places attacker code on the call stack beneath the victim's authorization. Any `token.transfer(victim, attacker, x)` that code performs is recorded — and, if the victim signs the simulated auth tree, authorized — as a child of the victim's own invocation. This is the on-chain analog of the command-injection class (GHSA-4j54-mxf6-wxx2): untrusted input reaching an invocation sink.

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs:13-55` forwards caller-supplied `swap` bytes to `router.execute_strategy` with only an exact-amount input-transfer authorization and a post-hoc output measurement. Neither the controller nor the router constrains which contract addresses the route names as hop pools. The threat model itself acknowledges this: "The router calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization" (`docs/explanation/threat-model.md:154-158`).

The test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` proves the exploit end-to-end through `swap_collateral`:

- `UnlistedPoolRouter::execute_strategy` invokes `route.hop_pool` taken verbatim from the payload (lines 39-47).
- `RogueHopPool::swap` executes `token::Client::transfer(&victim, &to, &amount)` on an arbitrary wallet token (lines 62-71).
- `simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry` (lines 195-227) shows the stolen transfer recorded as a child of Alice's `swap_collateral` auth entry, and `enforced_auth_...` (lines 229-269) shows the transfer executes once the poisoned tree is signed.

### Impact Explanation
Theft of user funds. A victim who signs a `swap_collateral`, `swap_debt`, `multiply`, or `repay_debt_with_collateral` transaction containing an attacker-crafted route loses any token balance their address holds, in any token — including tokens the protocol never listed. The recorded child invocation is indistinguishable from a legitimate nested auth unless the client decodes the full route and rejects unexpected children, which the protocol itself does not enforce on-chain. Loss is bounded only by the victim's wallet balances, not by the routed amount.

### Likelihood Explanation
High for users executing routes built by untrusted quote sources: the route is opaque XDR bytes, and standard simulation-based signing surfaces the extra transfer only as an auth-tree child that most wallets do not render. The attacker needs no privilege — they only need a victim to submit their crafted `swap` bytes through a normal permissionless entrypoint. The route must still satisfy `verify_router_output` (positive measured output) and the final account risk gates, but the rogue pool can pass a fair-looking output through the router while stealing unrelated tokens, so these checks do not block the theft.

### Recommendation
Maintain an on-chain allowlist of venue pool/token contracts in the swap aggregator (governance-managed), and reject routes naming unlisted addresses. Additionally, have the controller or router enforce that the only auth children beneath the swap invocation are the declared input transfer and explicitly expected venue pulls — e.g., by scoping `authorize_as_current_contract` entries and documenting/rejecting any extra `require_auth` target reachable from route-named code. Clients should decode `swap_xdr` before signing, but the invariant belongs on-chain.

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:

1. Register `UnlistedPoolRouter` as the swap aggregator and deploy `RogueHopPool` with plan `(alice, wallet_token, attacker, WALLET_BALANCE)` (lines 90-119).
2. Encode a `RoutedSwap` naming the rogue pool as `hop_pool` and pass it as `route` to `controller.swap_collateral(alice, account_id, USDC, amount, ETH, route)` (lines 134-163).
3. In recording mode the rogue pool's `transfer(alice → attacker, WALLET_BALANCE)` is attached under Alice's `swap_collateral` auth entry (lines 195-227); signing that tree executes the theft while the swap still pays fair output and the account stays solvent (lines 258-269).
