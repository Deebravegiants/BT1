### Title
Webhook `shop-domain` identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, never including the `X-Shopify-Shop-Domain` header. `Registry.process` validates only that signature and then trusts the header-derived `shop` value to identify the tenant for the webhook handler. Any party who can obtain one validly-signed webhook body (e.g., by installing the app on their own store) can replay that exact body with a different `shop-domain` header and have it accepted as an authentic event for an arbitrary victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read directly from an attacker/Shopify-controlled header, completely independent of anything that is verified: [2](#0-1) 

`HmacValidator.validate` verifies the HMAC using exactly `to_signable_string` (the body) and nothing else: [3](#0-2) 

`Registry.process` performs this single HMAC check and then immediately hands the header-derived, *unauthenticated* `shop` value to the webhook handler as the tenant identity: [4](#0-3) 

The identity binding that should hold is:
`shop that produced the valid signature == shop the handler is told the event belongs to`

Because the signable string never includes the shop header, this equality is never enforced. All shops share the same app `client_secret`, so a body that is validly signed for shop A remains validly signed for any other shop label. An attacker who is themself a legitimate (even free/trial) installer of the app can capture one authentic `hmac-sha256` + body pair delivered to their own store, then replay that exact body to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) with a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` passes the spoofed victim shop straight into `WebhookMetadata.shop` for the handler.

### Impact Explanation
This breaks the tenant boundary the gem is expected to guarantee for webhook processing: the "authenticated" shop and the "acted-upon" shop are two different, unlinked values. A host application built on top of `ShopifyAPI::Webhooks::Registry` that trusts `WebhookMetadata#shop` (as the documented API instructs it to) will process attacker-chosen shop identities for legitimately-signed payloads, letting a single app installer forge webhook events attributed to any other merchant using the same app — i.e., cross-tenant access, which is a Critical-severity impact per the given classification.

### Likelihood Explanation
The prerequisite is low: any unprivileged party can install the target Shopify app on a store they control (many apps offer free/dev installs) and thereby receive one genuinely HMAC-signed webhook body for a topic of their choosing. Replaying that body with a different `shop-domain` header requires only basic HTTP tooling — no access token, `client_secret`, or privileged account is needed, and the shared secret across all shops of an app means the signature check can never distinguish shops on its own.

### Recommendation
Bind the shop identity into what is authenticated. Either fold the `shop-domain` header into `Request#to_signable_string` and reject webhooks whose signed shop does not match the header (not possible with Shopify's current HMAC scheme, since Shopify itself only signs the body), or — more practically for this gem — require and document that callers must cross-check `WebhookMetadata#shop` against a shop the app has an active, stored session/install record for before acting on the payload, and expose that check as part of `Registry.process` rather than leaving it entirely to the host application's discretion.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. topic `customers/redact` with body `B`, correctly signed as `hmac = HMAC-SHA256(client_secret, B)`.
2. Attacker sends a new POST to the app's webhook endpoint with the same raw body `B`, the same `X-Shopify-Hmac-Sha256: hmac` header, but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` whose `shop` is `victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`= B`) and succeeds, since the shop header was never part of the signed content. [5](#0-4) 
5. The handler is invoked with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", ...)`, causing the host app to perform victim-shop-scoped actions (e.g., redaction/uninstall logic) triggered entirely by the attacker.
