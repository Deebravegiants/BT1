### Title
Webhook shop-tenant spoofing: `X-Shopify-Shop-Domain` header is trusted for tenant routing but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then hands the caller-supplied `shop-domain` header straight through to the app's handler as the authoritative tenant identifier. The header is never included in the signed payload, so the binding "HMAC-authenticated request == request that actually originated for the claimed shop" does not hold.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw JSON body: [1](#0-0) 

while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from unauthenticated HTTP headers: [2](#0-1) 

`Registry.process` validates only the body's HMAC (`Utils::HmacValidator.validate(request)`, which internally calls `verifiable_query.to_signable_string`, i.e. the raw body) and then constructs the metadata passed to the app's handler directly from `request.shop`: [3](#0-2) 

Because the webhook signing secret (`Context.api_secret_key`, the app's `client_secret`) is identical for every shop that has installed the app — it is not shop-specific — any merchant who has installed the app receives genuine `(raw_body, hmac)` pairs signed with that same shared secret for their own store's events. Nothing in the gem binds that signature to the `shop-domain` header. An attacker who is one tenant of a multi-tenant app can therefore replay a body/HMAC pair they legitimately received, while substituting a different value in the `X-Shopify-Shop-Domain` header, and `HmacValidator.validate` (which never inspects headers) still succeeds: [4](#0-3) 

The documented API explicitly instructs host applications to trust `data.shop` as "The shop domain of the webhook" and route/act on it directly (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), so this is not a case of the host app ignoring documented guidance — the gem's own contract presents an unauthenticated field as if it were verified.

The equality that should hold but doesn't: `shop_header == shop_that_produced_the_HMAC(raw_body, client_secret)`. In reality the gem only proves `HMAC(raw_body, client_secret)` is valid for *some* shop using this app; it says nothing about which shop the header claims.

### Impact Explanation
This breaks the tenant-authentication boundary the gem is expected to provide (Critical - cross-tenant access): a malicious merchant/tenant of a multi-tenant Shopify app can forge webhook deliveries that the host application will process as if they came from a different, victim shop, using nothing but a body/HMAC pair they legitimately possess from their own store's real traffic. Depending on how the host app persists webhook-driven state per shop (which the docs explicitly encourage keying off `data.shop`), this enables cross-tenant data injection/corruption attributed to a shop the attacker does not control.

### Likelihood Explanation
Any merchant that installs the target app on their own store can trivially capture a valid `(raw_body, X-Shopify-Hmac-Sha256)` pair from webhooks Shopify sends them (e.g. via their own endpoint logs or a proxy), since these are delivered directly to their configured callback URL. Re-sending that same body/signature to the app's webhook endpoint with a different `X-Shopify-Shop-Domain` header requires no secret knowledge and no special access beyond having installed the app once. This is a low-effort, no-privilege-escalation attack.

### Recommendation
Bind the shop identity into the authenticated payload rather than trusting the header standalone:
- Cross-check the `shop-domain` header value against a shop that is actually known/installed for this app (e.g. look up a stored session/install record) before invoking the handler, and reject if no matching install exists.
- Where feasible, incorporate the shop domain into the value that is HMAC-verified (Shopify's own webhook signing does not sign headers, so this must be enforced at the application layer within the gem, e.g. by requiring/validating the shop against `Context`'s known store of installed shops before calling `handler.handle`).
- At minimum, update `Registry.process`/documentation to make explicit that `data.shop` is unauthenticated and must be independently verified by the host app against its own install records before being used for tenant-scoped actions.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker.myshopify.com`.
2. Shopify delivers a genuine webhook to the app's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)`. The attacker captures `B` and `H` (both delivered directly to a URL they control/observe).
3. Attacker sends a new HTTP request to the same webhook endpoint with identical body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (a shop the attacker does not own).
4. `ShopifyAPI::Webhooks::Request.new` parses this forged request; `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(client_secret, B)` and it matches `H`, so validation succeeds: [5](#0-4) 
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed_body, ...)`: [6](#0-5) 
   The host application processes the attacker's event data as if it were an authentic event for `victim.myshopify.com`.
