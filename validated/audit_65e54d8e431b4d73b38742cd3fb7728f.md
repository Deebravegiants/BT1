### Title
Missing zero-address validation on `order.output.beneficiary` allows permanent loss of solver-provided output funds - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol], [File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
`IntentGatewayV2.placeOrder` and the internal fill paths (`_fillSameChain` in `IntrinsicIntents.sol` and `_fillCrossChain` in `ExtrinsicIntents.sol`) never validate that `order.output.beneficiary` is non-zero before deriving an `address` from it and transferring solver-supplied tokens/ETH to it, analogous to `transferPosition` in the referenced Sherlock finding not checking `recipient != address(0)`.

### Finding Description
`IntentGatewayV2.placeOrder` accepts a user-supplied `Order` struct containing `order.output.beneficiary` (a `bytes32`) with no validation: [1](#0-0) 

When a solver fills the order, both the same-chain and cross-chain fill paths derive an EVM `address` from this field with a raw bit-cast and immediately send the solver's tokens/ETH to it:

Same-chain fill (`_fillSameChain`): [2](#0-1) 

Cross-chain fill (`_fillCrossChain`): [3](#0-2) 

In neither path is `beneficiary` (nor the derived `address`) checked against `address(0)`. If `order.output.beneficiary` is `bytes32(0)`, `address(uint160(uint256(order.output.beneficiary)))` resolves to `address(0)`, and the fill logic will send the `totalRequired` (plus any beneficiary surplus share) output tokens or native ETH straight to `address(0)` via `IERC20.safeTransferFrom(msg.sender, beneficiary, ...)` or a raw `.call{value: ...}`, permanently destroying the transferred funds.

### Impact Explanation
Because `beneficiary` is set by the order creator (the user) rather than the solver, the primary victim of a zero-beneficiary order is the solver who fills it — their output tokens are burned to `address(0)` with no way to recover them. This can be exploited as griefing against automated solver bots that do not sanity-check `beneficiary != 0` before committing capital to `fillOrder`, or it can result in accidental permanent loss of funds due to a client-side bug that leaves `beneficiary` unset. Since the escrowed inputs are still released to the solver as normal (via `_withdraw`), the user effectively obtains the input assets in exchange for the solver having burned real value, and the solver has no recourse — this is a concrete case of permanent freezing/destruction of transferred funds, matching the Medium severity of the original finding.

### Likelihood Explanation
Likelihood is moderate: it requires either a solver's off-chain validation to omit the beneficiary check (plausible for high-throughput automated fillers optimizing for speed) or a client bug that leaves the beneficiary field zero-initialized when constructing an order. No privileged role is needed — any user can place an order with `beneficiary = bytes32(0)`, and any solver's normal `fillOrder` call becomes the vector that destroys funds.

### Recommendation
Add a zero-address check on the derived beneficiary address, either at order placement (`placeOrder`) or immediately after deriving `beneficiary` in `_fillSameChain` and `_fillCrossChain`, e.g.:
```solidity
address beneficiary = address(uint160(uint256(order.output.beneficiary)));
if (beneficiary == address(0)) revert InvalidBeneficiary();
```
This mirrors the recommended fix for the original report (reject `address(0)` recipients) and should be applied consistently everywhere a `bytes32` beneficiary/recipient is bit-cast to an `address` before a transfer in the intents flow.

### Proof of Concept
1. User calls `placeOrder` with `order.output.beneficiary = bytes32(0)` and any valid input/output token amounts — `placeOrder` (evm/src/apps/IntentGatewayV2.sol:194-226) performs no validation on `beneficiary` and escrows the user's input tokens normally.
2. A solver (unaware or not checking beneficiary) calls `fillOrder` with matching `FillOptions.outputs`.
3. Execution routes to `_fillSameChain` (evm/src/apps/intentsv2/IntrinsicIntents.sol:53-143), which computes `beneficiary = address(uint160(uint256(order.output.beneficiary))) == address(0)`.
4. The solver's ERC20 tokens are transferred via `IERC20(token).safeTransferFrom(msg.sender, beneficiary, beneficiaryTotal)` (line 102) or native ETH via `beneficiary.call{value: beneficiaryTotal}("")` (line 99) — both send value to `address(0)`, which for standard ERC20 tokens with no zero-address guard succeeds and permanently burns the funds (for ETH, `address(0).call` also succeeds, sending ETH into an unrecoverable address).
5. The order is marked filled and the user still receives their escrowed input tokens from `_withdraw`; the solver's output funds are irrecoverably lost.

Note: This analysis is based on statically reading the fill logic in `IntrinsicIntents.sol` and `ExtrinsicIntents.sol`; I did not find any offsetting zero-address check elsewhere in `IntentsBase.sol` within the portions indexed, but the full file was not entirely covered by tool output, so it is possible (though I found no evidence of it) that some other layer (e.g., off-chain relayer/solver tooling) enforces this check before submission.
