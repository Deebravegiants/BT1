### Title
Withdrawal status/hash misreported for same-token batched withdrawals due to assetId-only matching - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal` resolves the on-chain outcome of a specific withdrawal (identified by NEAR tx hash + `index`) by matching the POA Bridge API response using `assetId` only, ignoring `index`. When a single NEAR transaction contains more than one withdrawal intent for the same token (same `assetId`), the function can report the status/tx hash of the wrong withdrawal, breaking the equality "status/hash reported == the on-chain outcome of *this* withdrawal."

### Finding Description
`createWithdrawalIdentifier` builds a `WithdrawalIdentifier` that carries `index` (the position of this specific withdrawal intent among possibly several in the same NEAR transaction) together with `tx.hash`: [1](#0-0) 

However, `describeWithdrawal` never uses `args.index` to disambiguate. It calls `findMatchingWithdrawal`, which filters the API's `withdrawals` array purely by `assetId`: [2](#0-1) [3](#0-2) 

The comment in the code itself acknowledges the limitation: "matching by assetId... This means multiple withdrawals of the same token in a single transaction are not supported." `Array.prototype.find` returns only the *first* array element with a matching `assetId`, regardless of which index the caller actually asked about. If a caller submits two (or more) `ft_withdraw` intents for the same token in one NEAR transaction (e.g., withdrawing the same token to two different destination addresses, or using the SDK's atomic multi-intent publishing feature described in the README), calling `describeWithdrawal` for index 1 will still return whatever withdrawal record for that `assetId` is found first in the (explicitly "unsorted") API response — which may belong to index 0's withdrawal instead.

This breaks the equality: *the status/txHash reported for withdrawal N == the actual on-chain outcome of withdrawal N*. Instead, the SDK may report withdrawal N as `completed` with a `txHash` that actually corresponds to a different withdrawal's outcome (possibly to a different destination, or possibly one that failed while the other succeeded).

### Impact Explanation
An integrator (wallet, exchange, custody system) that relies on `sdk.waitForWithdrawalCompletion` / `describeWithdrawal` per-index to decide when to mark a specific withdrawal request as settled, retry it, or release custody could:
- Mark withdrawal N as completed based on a `txHash` belonging to a different withdrawal (the wrong on-chain transfer), causing a false "success" report while the actual withdrawal for N is still pending or failed.
- Conversely, treat a genuinely completed withdrawal as still pending/failed because the matched record belongs to a sibling withdrawal, potentially prompting the integrator to re-issue/refund the same withdrawal — a double-credit/refund scenario.

This matches the "a status or hash misreport making an integrator credit or refund twice" bucket in the High impact category, since the misreport is not the attacker's own balance loss but a wrong-outcome report for a *specific* withdrawal record that an external system uses to decide crediting/refunding.

### Likelihood Explanation
This requires a normal (non-malicious) usage pattern: a single NEAR transaction/intent batch withdrawing the same POA-bridged token more than once (to the same or different destinations) — something the SDK itself supports via multiple `withdrawalParams`/atomic multi-intent publishing. It does not require validator, relayer, or admin misbehavior — it is a straightforward consequence of the matching logic ignoring `index`, and is explicitly flagged as a known gap in the code's own comment, confirming the root cause is real and reachable through ordinary multi-withdrawal use, not merely theoretical.

### Recommendation
Disambiguate matches using more than `assetId`: additionally match on `destinationAddress`/`amount` (or track a per-index stable ordering key if the POA API can supply one), and only fall back to "first assetId match" when there is a single withdrawal per token in the transaction. At minimum, explicitly detect the case where more than one withdrawal shares the same `assetId` for a given `tx.hash` and refuse to resolve status for such indices (return `pending`/throw an explicit "cannot disambiguate" error) rather than silently returning a possibly-wrong match.

### Proof of Concept
1. Submit a single NEAR transaction with two `ft_withdraw` intents for the same POA-bridged token (`assetId = "nep141:eth-...omft.near"`), one to `destinationAddress: A` and one to `destinationAddress: B`.
2. `createWithdrawalIdentifier` is called twice, producing `{ index: 0, tx }` and `{ index: 1, tx }`, both with the same `assetId`.
3. Call `describeWithdrawal({ index: 1, tx, withdrawalParams: { assetId, destinationAddress: B, ... } })`.
4. Internally, `findMatchingWithdrawal` filters the (unsorted) API withdrawals list by `assetId` alone and returns `withdrawals.find(w => nep141:${w.data.near_token_id} === assetId)`, which may be the entry belonging to `destinationAddress: A` (index 0), not `B` (index 1).
5. The caller polling index 1 receives `{ status: "completed", txHash: <A's tx hash> }` even though B's withdrawal may still be pending or failed — an incorrect status/hash report for that specific withdrawal request.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
