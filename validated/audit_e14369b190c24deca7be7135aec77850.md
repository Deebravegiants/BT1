### Title
Attacker-controlled QR code `parameters` value ≥ 8 causes `assert_eq!` panic in `SweepConfiguration::parse_configuration_value` - ([File: src/plans/biometric_capture/mirror_sweep.rs])

### Summary
The `parameters` field of a `signup_extension_config` parsed from a presented QR code is converted with `u8::from_str_radix(parameter, 8)` and fed into `SweepConfiguration::new`/`parse_configuration_value` without range validation. Any octal string that decodes to a `u8` value ≥ 8 (e.g. `"10"` → 8, `"11"` → 9, up to `"377"` → 255) produces a binary representation longer than 3 bits, which trips the `assert_eq!` in `parse_configuration_value`, panicking the running task.

### Finding Description
`Plan::from<biometric_capture::Plan>` (mirror_sweep.rs, lines 166-189) builds the mirror-sweep configuration directly from attacker-controlled QR data: [1](#0-0) 

The `parameters` string originates from the user QR-code regex capture group `parameters` in `Data::from_signup_extension` (`src/plans/qr_scan/user.rs`, lines 144-157), which an unprivileged attacker fully controls by presenting a crafted QR code (mode `3` = `MirrorSweepExtension`, followed by an arbitrary `parameters` octal string).

`u8::from_str_radix(parameter, 8)` only rejects strings containing invalid octal digits or values that overflow `u8` (i.e. > 255); it does **not** reject valid octal encodings of values between 8 and 255 (e.g. `"10"`, `"11"`, `"377"`), since those still fit in a `u8`. The resulting `configuration_value` is passed unchecked into `SweepConfiguration::parse_configuration_value`: [2](#0-1) 

For any `configuration_value >= 8`, `format!("{configuration_value:0>3b}")` produces more than 3 characters (e.g. `8` → `"1000"`, `255` → `"11111111"`), so `assert_eq!(binary_repr.chars().count(), 3, ...)` fails and the task panics. There is no upstream validation clamping `configuration_value` to the 0-7 range before this call — the code comment even acknowledges the parsing should be "moved to QR code scanning phase" to "handle/fail early" but that has not been implemented.

### Impact Explanation
This is a signup-state wedge / denial-of-service: an unprivileged attacker can crash the orb-core signup task mid-flow simply by presenting a QR code with `mode=3` (`MirrorSweepExtension`) and a `parameters` value like `"10"` (octal 8) instead of a valid `0-7` value, causing the biometric-capture plan/broker task to panic. Depending on how the async task panic propagates through the broker/plan supervision, this can abort the in-progress signup and disrupt orb availability for subsequent signups until process/task recovery.

### Likelihood Explanation
The path is gated behind the `internal-data-acquisition` cargo feature (`src/plans/qr_scan/user.rs`, `#[cfg(feature = "internal-data-acquisition")]`), which controls whether `QR_CODE_SIGNUP_EXTENSION` parsing and `SignupMode`/`SignupExtensionConfig` construction are compiled in at all. If this feature is enabled in the deployed orb-core binary (as the question's premise assumes — "unprivileged attacker set their own user/operator QR-code signup_extension_config parameters field"), the trigger requires only presenting a single crafted QR code to the cameras; no operator/root access, hardware tampering, or backend collusion is needed, and it is fully repeatable. I could not verify from the available index whether `internal-data-acquisition` is a default/production-enabled feature in the shipped binary — this should be confirmed before treating the finding as exploitable in production.

### Recommendation
Validate `configuration_value` at parse time (ideally in `SignupMode`/`SignupExtensionConfig` parsing in `src/plans/qr_scan/user.rs`) and reject/clamp any octal `parameters` string that decodes to a value outside `0..=7`, returning `None`/falling back to a default instead of propagating an out-of-range `u8` into `SweepConfiguration::new`. Additionally, replace the `assert_eq!` panic in `parse_configuration_value` with a graceful `Result`/fallback path so malformed input from an untrusted QR code can never crash the running task.

### Proof of Concept
Unit test to add to `src/plans/biometric_capture/mirror_sweep.rs` tests module:
```rust
#[test]
#[should_panic(expected = "Mirror Sweep configuration value needs to be octal")]
fn configuration_value_ge_8_panics() {
    // "10" in octal == 8 decimal, a value an attacker can encode via
    // u8::from_str_radix("10", 8) in the QR code `parameters` field.
    let value = u8::from_str_radix("10", 8).unwrap();
    let _ = SweepConfiguration::new(value); // panics inside parse_configuration_value
}
```
Expected result: the test panics with the `assert_eq!` message from `parse_configuration_value`, demonstrating that an octal `parameters` string fully controllable via the QR code (`"10"`, `"11"`, ..., `"377"`) crashes the mirror-sweep configuration path instead of being rejected as invalid input.
