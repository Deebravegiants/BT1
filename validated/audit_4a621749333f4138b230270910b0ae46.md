### Title
Emporium Min-circuit drains any leftover ERC20 balance held by the Emporium contract with zero balance accounting - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
When `CircomData.erc20TokenAddresses.length == 0` and `externalActionId == HINKAL_EMPORIUM_ACTION_ID`, `formInputForCircom` routes proof verification to `formInputEmporiumMin`, which only feeds `emporiumMessage`, `timeStamp`, `calldataHash` to the verifier, matching `MainEVMCircuitMin`, a circuit that performs no balance, nullifier, or root-binding constraints at all. Because every balance-accounting loop in `Hinkal.transact` and `EmporiumUpgradeable.runAction` iterates `circomData.erc20TokenAddresses` (length 0 in this path), an attacker can encode an `EmporiumStack` operation that directly calls `transfer()` on any ERC20 token whose balance happens to sit on the Emporium proxy, and no code path ever checks or reverts on that balance change.

### Finding Description
The broken equality: tokens leaving the Emporium during the action must equal `-deltaAmountChanges` (funds that were supposed to leave) reconciled against `balancesBefore`/`balancesAfter` for that token; but `deltaAmountChanges` and both balance snapshots are all sized to `circomData.erc20TokenAddresses.length`, which is forced to `0` by the Min-circuit path selection in `formInputForCircom`: [1](#0-0) 

`dimensionsCheck` only enforces internal-consistency of array lengths against `dimensions.tokenNumber`; setting `tokenNumber = 0` makes every relevant array length 0 and the check passes trivially: [2](#0-1) 

The corresponding circuit for this path, `MainEVMCircuitMin`, performs no token/amount/nullifier/root constraints whatsoever — it only outputs `Poseidon(messageSeed)`: [3](#0-2) 

In `Hinkal.transact`, the balance-diff/slippage loop over `circomData.erc20TokenAddresses` never executes when the array is empty, so no accounting occurs on the caller side either: [4](#0-3) 

Inside `EmporiumUpgradeable.runAction`, `balancesBefore`/`balancesAfter` are computed via `getBalancesForArray(circomData.erc20TokenAddresses)`, which is empty, and the reconciliation loop (`balanceChange` vs `deltaAmountChanges`, `BalanceChangeShouldBePositive` revert) is bounded by the same empty length, so it never runs for any token that isn't listed: [5](#0-4) 

The op-execution loop (CASE 2, stateless interaction) executes an arbitrary low-level call from the Emporium proxy's own context whenever `stack.signerAddress == address(0)` (skipping the EIP-712 signature check in `verifyWallet`, which then only marks `usedMessages[circomData.emporiumMessage]`): [6](#0-5) [7](#0-6) 

**Attacker's exact call:** Attacker generates a valid but unconstrained Min-circuit proof for their own arbitrary `messageSeed`/`emporiumMessage`, a valid historical `rootHashHinkal` (any prior root, not bound by the circuit in this path), `circomData.erc20TokenAddresses = []`, `circomData.externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, and `externalActionMetadata = abi.encode(EmporiumStack{signerAddress: address(0), ops: [{endpoint: T, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, T.balanceOf(emporiumProxy)))}]})`. Calling `Hinkal.transact` with this data reaches `_externalTransact` → `EmporiumUpgradeable.runAction` → CASE 2 → `T.transfer(attacker, amount)` executed with `msg.sender == emporiumProxy`, draining `T`'s balance to the attacker with no equality ever consulted for token `T` because it is absent from `circomData.erc20TokenAddresses`.

**Why existing guards fail:** `performHinkalChecks` (calldata-hash self-consistency, `dimensionsCheck`, `checkOnchainCreation`) only validates internal consistency of attacker-supplied, zero-length arrays — none reference `T`. `verifyProof`/`buildVerifierId` succeed because the Min verifier (`VerifierEVMMin0v4`, 3 public inputs) is a legitimately registered verifier for this action, and the Min circuit itself constrains nothing about tokens or balances. `rootHashExists` only checks a globally valid Merkle root exists, unrelated to token `T`. No slippage/balance-diff `require` in `Hinkal.sol` or `EmporiumUpgradeable.sol` executes for tokens outside `circomData.erc20TokenAddresses`.

### Impact Explanation
Any unprivileged attacker can steal the entire ERC20 balance of any token that happens to be held by the Emporium proxy contract at the time of the attack — funds belonging to other users or the protocol (e.g., dust, refunds, or intermediate balances left between legitimate multi-step Emporium sessions, a scenario the code's own comment acknowledges as expected: "the only case when balanceChange can be < 0, when there were some funds on emporium before the call"). This is direct theft of in-flight/parked user or protocol funds with zero cost beyond gas and a self-generated proof, and is repeatable against every token address and every occurrence of a nonzero Emporium balance. This matches the Critical category: direct theft of in-flight user funds via a proof/verification bypass (the Min circuit provides no real constraint on the action performed).

### Likelihood Explanation
Preconditions: the token `T` must have a nonzero balance sitting on the Emporium proxy (plausible any time a multi-op Emporium session leaves intermediate token balances, or ETH/token dust from partial fills, refunds, or failed cleanup). Attacker cost is a single transaction with a self-generated Min-circuit proof (no dependency on any other user's keys, no privileged role required, no need to match a specific signer since `signerAddress = address(0)` skips signature verification). This is straightforward to execute repeatedly whenever the precondition holds, making it highly feasible for a motivated attacker who monitors the Emporium proxy's token balances.

### Recommendation
Do not allow the Min-circuit/empty-`erc20TokenAddresses` path to be combined with arbitrary `EmporiumOperation.endpoint.call` execution. Either: (1) require `circomData.erc20TokenAddresses` to include every token address touched by any `op.endpoint`/`op.callData` in the `EmporiumStack` (validated on-chain, not just left to the circuit), so balance reconciliation always applies; or (2) restrict the Min-circuit path to only the stateful `invokeWallet`/signed-wallet flow (disallow `signerAddress == address(0)` combined with arbitrary stateless calls), since the Min circuit provides no economic constraints and should never authorize direct low-level calls from the Emporium's own balance context.

### Proof of Concept
Hardhat fork test:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable` (proxy), register `VerifierEVMMin0v4` for the Min verifierId (`buildVerifierId(Dimensions{tokenNumber:0,...}, HINKAL_EMPORIUM_ACTION_ID)`), and a mock ERC20 `T`.
2. Simulate leftover balance: transfer `1000 T` directly to the Emporium proxy address (representing dust/in-flight funds from a prior legitimate session).
3. As an unprivileged attacker EOA, construct `EmporiumStack{signerAddress: address(0), ops: [{endpoint: T, invokeWallet: false, value: 0, callData: T.interface.encodeFunctionData("transfer", [attacker, 1000e18])}]}`, compute `calldataHash` via `getHashedCalldata`, generate a Min-circuit proof for arbitrary `messageSeed`, and build `CircomData` with `erc20TokenAddresses = []`, `externalActionId = HINKAL_EMPORIUM_ACTION_ID`, a valid `rootHashHinkal`/`rootHashHinkalIndex`.
4. Call `Hinkal.transact(a, b, c, dimensions{tokenNumber:0,...}, circomData)`.
5. Assert: tx succeeds; `T.balanceOf(emporiumProxy)` goes from `1000e18` to `0`; `T.balanceOf(attacker)` increases by `1000e18`; and confirm no `require` in `Hinkal.sol:97-146` or `EmporiumUpgradeable.sol:132-151` (`balanceDif == ...`, `BalanceChangeShouldBePositive`) was ever evaluated for `T` (e.g., by checking these loops execute 0 times since `circomData.erc20TokenAddresses.length == 0`).

    function runAction(
        CircomData calldata circomData,
        int256[] calldata deltaAmountChanges
    ) external override onlyAllowedRecipient returns (UTXO[] memory) {
        EmporiumStack memory stack = abi.decode(
            circomData.externalActionData.externalActionMetadata,
            (EmporiumStack)
        );

        uint256[] memory balancesBefore = getBalancesForArray(
            circomData.erc20TokenAddresses
        );

        verifyWallet(stack, circomData);

        for (uint256 i = 0; i < stack.ops.length; i++) {
            EmporiumOperation memory op = stack.ops[i];

            bool success;
            bytes memory err;

            // CASE 1: Stateful Interaction
            if (op.invokeWallet && stack.signerAddress != address(0)) {
                (success, err) = IHinkalWallet(stack.signerAddress)
                    .callHinkalWallet(op.endpoint, op.callData, op.value);
            }
            // CASE 2: Stateless Interaction
            else {
                bytes4 selector = bytes4(op.callData);
                if (
                    selector == IHinkalWallet.callHinkalWallet.selector ||
                    selector == IHinkalWallet.doSendToRelay.selector
                ) {
                    revert UnauthorizedWalletCall();
                }

                (success, err) = op.endpoint.call{value: op.value}(op.callData);
            }

            if (!success) {
                revert CallFailed(err);
            }
        }

        payRelayFees(circomData, stack.signerAddress, deltaAmountChanges);

        uint256[] memory balancesAfter = getBalancesForArray(
            circomData.erc20TokenAddresses
        );

        UTXO[] memory utxoSet = new UTXO[](
            circomData.erc20TokenAddresses.length
        );

        uint256 utxoSetLength;

        for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++) {
            int256 balanceChange = int256(balancesAfter[i]) -
                int256(balancesBefore[i]);

            if (deltaAmountChanges[i] < 0) {
                balanceChange -= deltaAmountChanges[i];
                // this equation reads: total change of emporium balance = what was moved to emporium (-deltaAmountChange) + how emporium balance changed through tx (balanceChange)
            }

            // the only case when balanceChange can be < 0, when there were some funds on emporium before the call
            if (balanceChange < 0) {
                revert BalanceChangeShouldBePositive();
            }

            UTXO memory utxoOut = handleOut(balanceChange, circomData, i);

            if (utxoOut.amount > 0) {
                utxoSet[utxoSetLength++] = utxoOut;
            }
        }

        if (utxoSetLength < circomData.erc20TokenAddresses.length) {
            utxoSet.skipLast(
                circomData.erc20TokenAddresses.length - utxoSetLength
            );
        }

        return utxoSet;
    }
