### Title
Webhook `shop-domain` identity is trusted by `Registry.process` while excluded from the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` extracts `topic`, `shop`, `api_version`, and `webhook_id` directly from unauthenticated HTTP headers (`x-shopify-*`), but its `to_signable_string` — the data covered by the HMAC check — is only the raw request body. `Registry.process` validates the HMAC and then immediately trusts `request.shop` to build `WebhookMetadata` passed to the app's handler, without the `shop` value itself ever being bound to the signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are read straight from headers with no cryptographic binding: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which only checks the body against the secret, then constructs `WebhookMetadata` directly from `request.shop` (the header) and hands it to the merchant-supplied `handler.handle`: [3](#0-2) 

`HmacValidator.validate` computes the HMAC purely over `to_signable_string`, i.e. the body, and never incorporates `shop`: [4](#0-3) 

The identity binding that should hold is: `shop header used by the app == shop actually bound by the HMAC signature`. Here, the HMAC only authenticates *that Shopify (or anyone holding the secret) produced this exact body*; it does not authenticate *which shop* the payload originated from. Because the `shop-domain` header sits outside the signed payload, if two shops on the same app happen to receive webhook bodies that are byte-identical (or an app operator/relay forwards a validly-signed body under a different `shop-domain` header — e.g., a shared reverse proxy, logging/replay tooling, or a bug in the host framework that mixes up headers vs. body across concurrent requests), the gem will report a valid `HmacValidator.validate` result and dispatch `WebhookMetadata` labeling the data as belonging to whatever shop is in the header, not necessarily the shop that produced/owns that signed body.

### Impact Explanation
This is a tenant-identity binding defect: the value used for tenant routing (`request.shop`, consumed by the host app to select per-shop state, tokens, or database rows) is unauthenticated relative to the HMAC that is supposed to prove authenticity of the webhook payload. This matches the "shop authenticated versus the shop bound by the HMAC" analog class called out in the rules, and could lead to cross-tenant data being attributed to the wrong shop if the header can be influenced independently of the signed body (e.g., through a misconfigured/compromised intermediary, an app-side bug forwarding webhooks across shops, or any component between Shopify and the final handler that can rewrite headers post-signature verification but pre-dispatch).

### Likelihood Explanation
Exploitability strictly through this gem's own logic is limited: Shopify's webhook delivery is expected to set the header and body consistently for a given shop, and there is no in-gem code path that lets an unprivileged internet user directly forge `shop-domain` while keeping a valid HMAC over an arbitrary body without already knowing the app's `client_secret` (out of scope per the rules). Exploitation would require an intermediary/proxy layer or host-app defect that decouples the header from the signed body — a scenario the rules classify as depending on integration/deployment factors outside pure library code, and not a directly reachable unprivileged exploit against the gem alone.

### Recommendation
Bind `shop` (and ideally `topic`/`api_version`) into the value verified against the HMAC, or otherwise document/assert that `request.shop` must not be trusted independently of the signed payload. Concretely, either include the `x-shopify-shop-domain` header content in the canonical signable string (mirroring Shopify's HMAC verification guidance, which historically signs only the body but relies on TLS + direct delivery to guarantee header/body correlation), or have `Registry.process` cross-check `request.shop` against the shop embedded in `request.parsed_body` (many webhook payloads include shop-scoped identifiers) before dispatch.

### Proof of Concept
Not independently exploitable purely within this gem without an external component decoupling the `x-shopify-shop-domain` header from the signed body; a full PoC would require simulating such an intermediary, which is outside the gem's own code path.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
