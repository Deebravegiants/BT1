### Title
Missing access control in `HyperFungibleTokenImpl::superApprove()` allows arbitrary theft of any holder's token balance - (File: evm/src/utils/HyperFungibleTokenImpl.sol)

### Summary
`HyperFungibleTokenImpl::superApprove()` sets an unlimited `ERC20` allowance from an arbitrary `owner` to an arbitrary `spender` and has no access control whatsoever, mirroring the reported `RFPSimpleStrategy::setPoolActive()` class of bug: a state-mutating function that is clearly meant to be privileged (or at least caller-scoped) but carries no modifier restricting who can invoke it or on whose behalf.

### Finding Description
`HyperFungibleTokenImpl` is the ERC-20 implementation used by Hyperbridge's cross-chain fungible token bridging (it exposes `mint`/`burn` gated by `MINTER_ROLE`/`BURNER_ROLE`) [1](#0-0) . Alongside the properly-gated `mint`/`burn`/role-management functions [2](#0-1) , the contract exposes:

```solidity
function superApprove(address owner, address spender) public {
    _approve(owner, spender, type(uint256).max);
}
``` [3](#0-2) 

This function takes an arbitrary `owner` address and grants `spender` (also arbitrary, and settable to `msg.sender`) an unlimited allowance over `owner`'s balance, without checking `msg.sender == owner`, without any role check, and without any `onlyRole`/`onlyOwner` modifier — despite `AccessControlEnumerable` already being in scope and used for every other privileged mutator in the same contract [4](#0-3) . Any unprivileged caller can invoke `superApprove(victim, attacker)` and then call `transferFrom(victim, attacker, victimBalance)` to drain the victim's entire balance of the bridged token.

### Impact Explanation
This is a direct concrete theft-of-funds primitive reachable by a single unprivileged transaction: any address can set itself (or a colluding address) as an unlimited spender for any token holder and drain their balance via `transferFrom`. Because this token is the mint/burn implementation used for cross-chain token transfers, this directly threatens user funds bridged through Hyperbridge's token-bridge integration.

### Likelihood Explanation
Likelihood is high: the function is `public`/`external`-callable with no restriction, requires no special conditions, and the exploit (approve then transferFrom) is a single, trivial two-step transaction available to any address, including a contract-based attacker for atomicity.

### Recommendation
Restrict `superApprove` so it can only be called by the token owner themselves (i.e., drop the `owner` parameter and use `msg.sender`), or gate it behind an appropriate role (e.g. `onlyRole(DEFAULT_ADMIN_ROLE)`) if it is only meant for privileged/test tooling, and clearly document/remove it from production deployments if it exists purely as a test helper as the comment suggests ("Helper function for tests") [5](#0-4) .

### Proof of Concept
1. Attacker calls `token.superApprove(victim, attacker)` — succeeds with no access control, setting `allowance[victim][attacker] = type(uint256).max`.
2. Attacker calls `token.transferFrom(victim, attacker, token.balanceOf(victim))`, draining the victim's entire balance. [3](#0-2)
