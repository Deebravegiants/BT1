Based on the analysis, I've confirmed the vulnerability pattern in the webhook HMAC verification design.

### Title
Webhook shop identity spoofing via unsigned `x-shopify-shop-domain` header — HMAC only covers body, not tenant-identifying header - ([File: lib/shopify_api/webhooks/request.rb], [File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` value from an HTTP header that is never included in the HMAC signature computation, while `ShopifyAPI::Webhooks::Registry.process` passes that unverified `shop` value straight into the handler's trusted `WebhookMetadata`. This breaks the equality `bytes verified == bytes acted on`: the HMAC covers only `@raw_body`, but the identity field consuming apps rely on (`shop`) comes from a header outside that signed scope.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Request#shop` is read from the `shopify-shop-domain` / `x-shopify-shop-domain` header, entirely outside that signable string [2](#0-1) . `HmacValidator.validate` verifies the signature strictly against `to_signable_string`, i.e. the body bytes only [3](#0-2) . `Registry.process` then calls `Utils::HmacValidator.validate(request)` to gate execution, and on success forwards `request.shop` (the unauthenticated header value) directly into `WebhookMetadata`, which the app-supplied handler treats as the trusted tenant identity for the webhook [4](#0-3) .

Because the app's `api_secret_key` is shared across every merchant who installs the app (it is not per-shop), any merchant who installs the app can legitimately trigger webhook events for their own store and receive a body + valid HMAC signed with that shared secret. Since the header carrying the shop identity is not part of the signed content, that attacker-controlled merchant can replay the same body/HMAC pair while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` will still return `true` because the body is unchanged, and `Registry.process` will hand the handler a `WebhookMetadata` claiming to be from the victim shop.

### Impact Explanation
This is a cross-tenant identity binding break: the equality the library should enforce is `shop-used-by-handler == shop-cryptographically-bound-to-request`, but it instead enforces only `body-used-by-handler == body-cryptographically-bound-to-request`. Any app that uses `WebhookMetadata#shop` (as returned by `Registry.process`/`request.shop`) to select which merchant's data/session to act on — a documented, expected usage of this field — can be tricked into performing tenant-scoped side effects (e.g., data mutation, deauthorization flows on mandatory topics like `shop/redact`, `customers/redact`, `customers/data_request`) attributed to a shop that never sent the request. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitability requires only that the attacker be a legitimate, unprivileged installer of the target app on their own store (no leaked secrets, no privileged access, no TLS interception) — well within the "unprivileged internet user" threat model. The attacker needs a webhook body that is shop-independent or attacker-influenceable (many webhook bodies, e.g., `app/uninstalled`, mandatory GDPR topics, or generic product/order payloads without an embedded shop domain check, satisfy this).

### Recommendation
Bind the shop identity into the signed material the library verifies: include the `shop-domain` (and ideally `topic`/`webhook-id`) header value in `Request#to_signable_string`, or otherwise require callers to cross-check `request.shop` against an independently trusted value (e.g. compare against the shop hydrated from the app's own session store) before trusting `WebhookMetadata#shop`. At minimum, document prominently that `request.shop` is unauthenticated and must not be used as the sole tenant selector.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, obtaining the shared `api_secret_key` webhook signature behavior (not the secret itself).
2. Attacker triggers a webhook event that produces a body with no shop-specific content Shopify actually POSTs it with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of body>`.
3. Attacker replays this exact body and HMAC to the app's webhook endpoint, but changes the header to `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds the request; `Registry.process` calls `Utils::HmacValidator.validate(request)` [5](#0-4)  — validation succeeds because it only checks the (unmodified) body.
5. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built with `shop == "victim.myshopify.com"` [6](#0-5)  and passed to the app's handler as if genuinely originating from the victim shop.
