### Title
Webhook `shop-domain`, `topic`, `webhook_id`, and `api-version` headers are not covered by the HMAC signature, allowing shop/topic spoofing on replayed webhook bodies - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the `shop-domain` and `topic` HTTP headers — which are never included in the signed material — to build the `WebhookMetadata` passed to the app's handler.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop`, `topic`, `api_version`, and `webhook_id` are read straight from attacker-controllable HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, which computes `HMAC(secret, to_signable_string)` — i.e., HMAC over the body only — and compares it to the `hmac-sha256` header, then immediately trusts `request.shop`/`request.topic` to construct `WebhookMetadata` and dispatch to the registered handler: [3](#0-2) [4](#0-3) 

The binding that should hold is:
`HMAC-verified bytes == bytes acted upon (shop, topic, webhook_id)`
but the actual relationship is:
`HMAC-verified bytes (raw body only) ⊂ bytes acted upon (raw body + shop-domain + topic + webhook_id headers)`

Because Shopify computes the webhook HMAC over the body alone (this is a genuine constraint of Shopify's own webhook signing, not unique to this gem), a shop that has the app installed receives real, validly-signed webhook deliveries for its own store. An unprivileged attacker who controls such a shop can capture one of these deliveries (body + valid `X-Shopify-Hmac-Sha256`) and replay the identical body+HMAC pair directly to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) with a different, victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the body against the shared `client_secret`, and `Registry.process` passes the attacker-chosen `shop`/`topic` through unchanged to the app's `WebhookHandler#handle`: [5](#0-4) 

This is a case of "a field acted on but not covered by the HMAC": `shop` (the tenant identity used by the handler to decide which merchant's data/session to act on) is not part of the signed payload, so it is not actually authenticated even though the request as a whole appears "HMAC valid."

### Impact Explanation
Any handler that uses `WebhookMetadata#shop` to look up/act on a specific merchant's session, data, or state (the documented and expected usage pattern for this gem, per `docs/usage/webhooks.md` and the `WebhookHandler` interface) can be made to act on a shop the attacker doesn't own, using a webhook the attacker forged only by relabeling headers on a body they legitimately received for their own shop. Depending on the topic replayed (e.g., `app/uninstalled`, `customers/data_request`, `shop/update`), this enables cross-tenant confusion — for example forcing an app to process a fabricated lifecycle event against a victim shop's stored session/access token — which crosses the tenant boundary via a purely unprivileged, credential-less request to the app's own webhook endpoint.

### Likelihood Explanation
Requires only that the attacker control one shop with the app installed (a normal unprivileged merchant/developer action, not a privileged account) and know/guess a victim's `*.myshopify.com` domain, which is often public. No secrets, tokens, or social engineering are needed — only the ability to send an HTTP request with modified headers to the app's public webhook endpoint.

### Recommendation
Bind the identity fields to the signed content instead of trusting bare headers: include `shop`, `topic`, and `webhook_id` in the value that is HMAC-verified (e.g., derive/verify them against a signed manifest, or require the host application to independently confirm that `shop` is a shop actually associated with an active installation/session before dispatching), and document that `Request#shop`/`#topic` must not be treated as authenticated on their own.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) and capture the raw POST: body `B` plus header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the app's `client_secret`).
2. Replay the exact same request to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com` (keep `X-Shopify-Hmac-Sha256: H` and body `B` unchanged).
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` builds successfully; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and matches `H` — validation passes.
4. `Registry.process` builds `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: parsed(B), ...)` and dispatches it to the registered handler, which now acts as though this event genuinely originated from `victim.myshopify.com`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

        end
