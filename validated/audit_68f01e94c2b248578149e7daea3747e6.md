### Title
Webhook `shop-domain` (and other Shopify headers) are not covered by HMAC validation, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values are read from HTTP headers that are excluded from the HMAC computation. `Registry.process` validates the HMAC and then unconditionally trusts `request.shop` (and `request.topic`) taken from these unauthenticated headers to build the `WebhookMetadata` object dispatched to the host application's webhook handler.

### Finding Description
The intended binding is: `hmac == HMAC(shared_secret, entire_authenticated_message)`, where the authenticated message should include every field the application later acts on (in particular the `shop` identity used to route/attribute the webhook). Instead, in this gem:

- `Utils::HmacValidator.validate` computes `computed_signature = HMAC_SHA256(api_secret_key, verifiable_query.to_signable_string)` and compares it to `verifiable_query.hmac` [4](#0-3) .
- For webhooks, `to_signable_string` is defined as `@raw_body` only [5](#0-4) .
- `shop`, `topic`, `webhook_id`, `api_version` are all sourced from HTTP headers (`shopify-shop-domain`/`x-shopify-shop-domain`, etc.) that are never included in `to_signable_string` [6](#0-5) .
- `Registry.process` validates the HMAC of the body, then directly forwards `request.shop` and `request.topic` — values that are not covered by that HMAC — into `WebhookMetadata` handed to the application's handler [3](#0-2) .

Because the HTTP framework's request object is constructed by the host app from the incoming request (headers plus body) and passed into `Request.new(raw_body:, headers:)`, an attacker who is able to submit arbitrary HTTP headers to the app's webhook endpoint (a public, unauthenticated endpoint by design) can pair a *previously observed, legitimately-HMAC'd body* with a **forged `shop-domain` header** pointing at a victim shop, or a forged `topic` header, without invalidating the signature check — because the signature never covered those header values in the first place. This breaks the intended identity binding: `shop authenticated == shop the handler acts on`.

### Impact Explanation
This enables cross-tenant confusion: a webhook whose HMAC was legitimately produced for shop A's body can be replayed/relabeled by an unprivileged internet user as being for shop B (or for a different topic than actually occurred), since `shop` and `topic` are never part of the signed payload. Any host application that uses `WebhookMetadata#shop` (as documented/intended usage of this gem, `handler.handle(data: WebhookMetadata.new(topic: ..., shop: request.shop, ...))`) to look up shop-specific sessions/config, gate mandatory compliance webhooks (`shop/redact`, `customers/redact`, `customers/data_request`), or dispatch business logic keyed by shop, can be made to act on the wrong tenant's data — a cross-tenant access impact.

### Likelihood Explanation
The webhook receiving endpoint is inherently public/unauthenticated at the HTTP layer (that's the nature of a webhook callback), and the header-vs-body signing split is a structural property of this gem's `Request`/`HmacValidator` design, not a host-app misconfiguration. Exploitation only requires network access to the app's webhook endpoint and knowledge/capture of one valid `(body, hmac)` pair (e.g., from the attacker's own shop's legitimate webhook deliveries), then replaying it with a forged `shop-domain` header.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` values in the HMAC-covered signable content for webhooks, or otherwise cryptographically bind the header-derived identity fields to the signed body (e.g., verify `shop-domain` against a canonical shop record obtained independently, or require the app to additionally validate that `request.shop` matches an expected/pre-registered shop before trusting it). At minimum, document clearly that `WebhookMetadata#shop`/`#topic` are unauthenticated header values and must not be trusted for authorization decisions without independent verification.

### Proof of Concept
1. Attacker owns/controls shop A and registers a webhook; Shopify sends a legitimate webhook delivery with body `B` and `shopify-hmac-sha256: HMAC(secret, B)`, `shopify-shop-domain: shop-a.myshopify.com`.
2. Attacker captures this valid `(B, hmac)` pair.
3. Attacker POSTs to the app's public webhook endpoint with the same body `B` and the same valid `hmac` header, but sets `shopify-shop-domain: shop-b.myshopify.com` (victim shop) and/or a different `shopify-topic`.
4. `Utils::HmacValidator.validate(request)` succeeds because it only hashes `@raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
5. `Registry.process` dispatches to the registered handler with `WebhookMetadata.new(shop: "shop-b.myshopify.com", topic: <forged topic>, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the host application to process/attribute the webhook to shop B despite it never having sent this data.
