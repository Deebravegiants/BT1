### Title
Session-token issuer context is not validated when deriving Admin session storage keys, allowing non-admin (e.g. checkout/extension) ID tokens to be accepted as admin session credentials - ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
`ShopifyAPI::Utils::SessionUtils.session_id_from_shopify_id_token` (used by the documented entry point `current_session_id`) derives the session-storage lookup key for the merchant's Admin session purely from the JWT's `dest` (shop) and `sub` claims, never checking the `iss` claim that indicates whether the token was actually issued for an **admin** embedded-app context. `ShopifyAPI::Auth::JwtPayload` already implements the correct check (`admin_session_token?`, based on `iss.end_with?("/admin")`) but only applies it to gate `shopify_user_id` - it is never enforced before a session id is derived and handed back to the host application to look up a stored (and potentially highly privileged, access-token-bearing) `Session`.

### Finding Description
`ShopifyAPI::Auth::JwtPayload#initialize` decodes and HMAC-verifies any Shopify-issued ID token, checking only `aud == Context.api_key`: [1](#0-0) 

The `iss` claim distinguishes the token's issuing context - e.g. `"https://shop.myshopify.io/admin"` for an embedded admin session token versus `"https://shop.myshopify.io/checkouts"` for a Checkout UI Extension token (confirmed by the test fixtures using `@checkout_ui_extension_jwt_payload`): [2](#0-1) 

The class provides a helper to distinguish these contexts: [3](#0-2) 

but that helper is used **only** inside `shopify_user_id`: [4](#0-3) 

`SessionUtils.session_id_from_shopify_id_token` never calls `admin_session_token?`. It accepts any valid token (as long as `aud` matches the app's API key and the signature verifies) and builds the Admin session lookup key from `payload.shop` (the `dest` claim) alone, or combined with `payload.sub`: [5](#0-4) 

For **offline** sessions the key is `"offline_#{shop}"` - it does not even incorporate `sub`, so it is identical regardless of whether the token came from the admin iframe or from a Checkout UI Extension / POS extension / other non-admin context, as long as `dest` resolves to the same shop domain.

This breaks the intended identity binding: **the session-storage key used to retrieve the merchant's Admin API credentials should be bound to "this JWT was issued for the admin embedded-app context" (`iss` ends in `/admin`)**, but the code only binds it to "this JWT's `aud`/`dest` match this app/shop," which is satisfied by tokens minted for unrelated, lower-privilege surfaces (e.g., a Checkout UI Extension running in an anonymous customer's browser).

### Impact Explanation
Per `docs/getting_started.md`, `current_session_id`/`session_id_from_shopify_id_token` is the gem's documented, primary mechanism for embedded apps to resolve which stored `Session` (and therefore which Admin API access token) to use for an incoming request: [6](#0-5) 

Checkout UI Extension (and other non-admin extension) session tokens are, by Shopify design, exposed to and readable by client-side extension JavaScript running in an unauthenticated customer's browser session - they are not admin-only secrets. Because this gem does not verify `iss` before deriving the lookup key, an attacker who can obtain such a token for a target shop can present it (e.g. via `Authorization: Bearer`) to a host app built on this gem, and the gem will compute the exact same session id (`"offline_#{shop}"`) that the app would otherwise use to fetch the merchant's real offline Admin session. If the host application follows the gem's documented pattern of using this id to load and reuse a persisted Admin session, this results in unauthorized use of the merchant's Admin API credentials by an unprivileged party - crossing the tenant/privilege boundary between "unauthenticated customer-facing extension context" and "merchant Admin session." This matches the Critical bar (authentication bypass / theft-equivalent misuse of a merchant access token) since the check that should gate this (`admin_session_token?`) already exists in the codebase but is not applied at the point where it matters.

### Likelihood Explanation
Likelihood is High for apps that use both Checkout/POS UI Extensions and the Admin API through the same client. The only prerequisite is that: (1) the app has a valid extension-context ID token issued by Shopify for the same `api_key`/shop (which is intentionally accessible to extension JS in the customer's browser), and (2) the host app follows this gem's documented `current_session_id` usage. No secret material, no access token, and no privileged account are required from the attacker.

### Recommendation
In `ShopifyAPI::Auth::JwtPayload`, expose and enforce an issuer/context check (reusing/generalizing `admin_session_token?`) as part of token validation itself, and have `SessionUtils.session_id_from_shopify_id_token` reject (raise `Errors::InvalidJwtTokenError`) any token whose `iss` does not end in `/admin` before deriving `jwt_session_id`/`offline_session_id`. This binds the session-storage lookup key to "token was issued for the admin embedded context," closing the gap between non-admin extension tokens and admin session identity.

### Proof of Concept
1. Obtain (via legitimate use of a Checkout UI Extension in the target shop, as an anonymous customer) a valid Shopify ID token with claims like:
```ruby
{
  iss: "https://shop.myshopify.io/checkouts",
  dest: "https://shop.myshopify.io",
  aud: "<app_api_key>",
  sub: "gid://shopify/Customer/123456789",
  exp: ..., nbf: ..., iat: ..., jti: "..."
}
```
(mirrors `@checkout_ui_extension_jwt_payload` in `test/auth/jwt_payload_test.rb` lines 23-32) - signed by Shopify with the app's `api_secret_key`, exactly like an admin token.
2. Call, as documented:
```ruby
ShopifyAPI::Utils::SessionUtils.current_session_id(token, nil, false)
```
3. Observe that this returns `"offline_shop.myshopify.io"` - identical to the id that would be returned for a genuine admin embedded-app session token - because `session_id_from_shopify_id_token` never checks `iss`: [7](#0-6) 
4. A host app that looks up its stored offline `Session` (containing the merchant's Admin access token) using this id will hand Admin API access to the holder of the customer-facing checkout extension token.

        def session_id_from_shopify_id_token(id_token:, online:)
          raise Errors::MissingJwtTokenError, "Missing Shopify ID Token" if id_token.nil? || id_token.empty?

          payload = Auth::JwtPayload.new(id_token)
          shop = payload.shop

          if online
            jwt_session_id(shop, T.must(payload.sub))
          else
            offline_session_id(shop)
          end
        end

        sig { params(shop: String, user_id: String).returns(String) }
        def jwt_session_id(shop, user_id)
          "#{shop}_#{user_id}"
        end

        sig { params(shop: String).returns(String) }
        def offline_session_id(shop)
          "offline_#{shop}"
        end
```

#### Getting Session ID From Embedded Requests

If your app uses client side rendering instead of server side rendering, you will need to use App Bridge's [authenticatedFetch](https://shopify.dev/docs/apps/auth/oauth/session-tokens/getting-started) to make authenticated API requests from the client.

For *embedded* apps:

If you have an `HTTP_AUTHORIZATION` header or `id_token` from the request URL params , you can pass that as `shopify_id_token` into:
- `ShopifyAPI::Utils::SessionUtils.current_session_id(shopify_id_token, nil, true)` for online (user) sessions or
- `ShopifyAPI::Utils::SessionUtils.current_session_id(shopify_id_token, nil, false)` for offline (store) sessions.

`current_session_id` accepts shopify_id_token in the format of `Bearer this_token` or just `this_token`.

You can also use this method to get session ID:
- `ShopifyAPI::Utils::SessionUtils::session_id_from_shopify_id_token(id_token: id_token, online: true)` for online (user) sessions or
- `ShopifyAPI::Utils::SessionUtils::session_id_from_shopify_id_token(id_token: id_token, online: false)` for offline (store) sessions.
```
