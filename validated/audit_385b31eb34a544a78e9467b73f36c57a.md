### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor sourced entirely from the client-supplied `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header [1](#0-0) , but the webhook HMAC is computed and validated only over the raw request body [2](#0-1) . `Utils::HmacValidator.validate` simply recomputes the HMAC over `to_signable_string` and compares it to the header-supplied signature [4](#0-3) , so the shop-domain value is never bound to the signature. `Registry.process` treats a valid HMAC as sufficient authorization and passes the unverified `request.shop` straight into `WebhookMetadata`, which application handlers use as the tenant/shop identity for the event [3](#0-2) .

### Finding Description
The identity binding that should hold is: `shop domain attributed to the event == shop domain the HMAC-signed body actually originated from`. This gem breaks that equality. The HMAC only proves "this body byte-string was produced (or witnessed) by someone holding the app's `client_secret`" — it says nothing about which shop the request claims to be from, because the shop-domain header is excluded from `to_signable_string`.

An unprivileged internet user who legitimately installs the app on their own store (or otherwise obtains a genuine webhook delivery, e.g. from Shopify's webhook testing feature) receives a webhook body plus a correctly-computed HMAC for that body, computed with the app's `client_secret`. Because many webhook topics share a body schema across all shops that trigger them (e.g. `app/uninstalled`, `shop/update`, or any webhook whose body an attacker controls or can predict), the attacker can replay the exact same `raw_body` and HMAC value to the app's webhook endpoint while substituting an arbitrary victim `X-Shopify-Shop-Domain` header. `Utils::HmacValidator.validate` still succeeds because it only checks the body bytes against the signature [5](#0-4) , and `Registry.process` forwards the forged shop identity to the handler unchanged [6](#0-5) .

### Impact Explanation
This crosses a tenant boundary: an attacker-controlled webhook body, valid under the shared app-level `client_secret`, can be attributed to any victim shop domain the attacker chooses. Applications built on this gem that key data (uninstall handling, redaction, subscription state, order/customer records) off `WebhookMetadata#shop` without independent verification will process attacker-injected events as if they originated from the victim's store — a cross-tenant data integrity/authentication issue directly caused by an incomplete HMAC binding in this gem's `Webhooks::Request`/`Registry`.

### Likelihood Explanation
Likelihood is Medium: exploitation requires the attacker to already have (or be able to trigger) at least one genuine, validly-signed webhook body for a topic whose payload is shop-independent or attacker-influenceable (installing the app on a shop they control is sufficient to receive real webhooks), then replay it with a different shop-domain header. No access to the `client_secret`, access tokens, or the victim's credentials is required.

### Recommendation
Bind the shop-domain (and ideally topic/webhook-id) into the signed material, or otherwise cross-check `request.shop` against a shop known to be associated with a currently-installed session before trusting it. At minimum, `Webhooks::Registry.process` should refuse to act on `request.shop` unless the app independently confirms that shop has an active installation/session, rather than trusting the header value solely because the body-only HMAC validated.

### Proof of Concept
1. Install the target app on `attacker.myshopify.com`; capture a genuine webhook delivery, e.g. `app/uninstalled` with body `raw_body` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, raw_body)`.
2. Send a forged HTTP request to the app's webhook endpoint with the same `raw_body` and `X-Shopify-Hmac-Sha256: H`, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Webhooks::Request.new` accepts it (all required headers present) [7](#0-6) ; `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against `H` [8](#0-7) .
4. `Registry.process` invokes the app's handler with `WebhookMetadata(shop: "victim.myshopify.com", ...)` [6](#0-5) , causing the app to act on behalf of `victim.myshopify.com` (e.g. mark it uninstalled, purge data, or apply attacker-controlled state) despite the attacker having no relationship to that shop.
