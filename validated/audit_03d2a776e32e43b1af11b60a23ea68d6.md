### Title
Webhook shop/topic identity spoofing via HMAC that only covers the raw body - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `HmacValidator.validate` cryptographically proves nothing about the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. `Registry.process` nonetheless trusts these unauthenticated headers to determine which shop/tenant and which handler logic a webhook belongs to.

### Finding Description
The identity binding that should hold is: `hmac == HMAC(secret, shop ‖ topic ‖ body)` so that the `shop` and `topic` used by the handler are the same `shop`/`topic` the merchant/Shopify actually signed. Instead, the binding implemented is `hmac == HMAC(secret, body)` only [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are read verbatim from HTTP headers with no cryptographic tie to the HMAC [5](#0-4) .

`Registry.process` validates only the HMAC and then trusts `request.topic` (to pick the handler) and `request.shop` (passed into `WebhookMetadata` and handed to the app's handler code) unconditionally: [3](#0-2) 

Because any legitimate merchant (including an attacker who installs the app on their own free/trial shop — an unprivileged internet user, no special credentials needed) will receive genuinely HMAC-signed webhook deliveries from Shopify for their own shop, the attacker can capture such a delivery (valid HMAC over the raw body) and replay it to the app's webhook endpoint while swapping the `x-shopify-shop-domain` and/or `x-shopify-topic` headers. Since these headers are excluded from the signed string, the HMAC remains valid, and the handler will process the payload as if it came from a different shop or for a different topic than what was actually signed by Shopify for the attacker's own shop.

### Impact Explanation
This breaks the tenant-binding guarantee webhook consumers rely on: apps use `data.shop` from `WebhookMetadata` to decide which tenant's data/state to mutate (e.g., mark subscription cancelled, disable app access, process GDPR `customers/redact`/`shop/redact`). An attacker can forge a cross-tenant webhook (e.g., claim a `shop/redact` or `app/uninstalled` event for a victim shop) using only a body they legitimately received for their own shop, as long as the body content is shop-agnostic or replayable (many webhook topics have bodies with little/no shop-specific data, or the attacker can trigger events with attacker-influenced body content on their own shop). This can cause cross-tenant state corruption or trigger privileged app-side actions attributed to the wrong merchant — a High-severity impact given the identity/tenant boundary is crossed with no credential requirement beyond installing the app once on a shop the attacker controls.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to install/operate the target app on a shop they control (freely available, no special privilege) and to capture at least one genuine webhook delivery, then replay it with modified headers against the same endpoint. No access token, `client_secret`, or victim credential is required — only observation of one legitimate webhook payload for a topic whose body doesn't strictly need to vary with the impersonated shop.

### Recommendation
Include the `shop-domain`, `topic`, and ideally `webhook-id`/`api-version` headers in the HMAC-signed string (bind them to the signature) rather than signing the raw body alone, or otherwise cryptographically bind the shop/topic to the payload before dispatching to `WebhookHandler#handle`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and registers for topic `T` with an HTTP delivery.
2. Shopify sends a genuine webhook: headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: T`, `x-shopify-hmac-sha256: <valid HMAC of raw_body>`, plus `raw_body: B`.
3. Attacker replays the exact same `raw_body: B` and `x-shopify-hmac-sha256` value to the same webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com` (and/or `x-shopify-topic` to a more sensitive topic already registered by the app, if body `B` is compatible).
4. `Utils::HmacValidator.validate` recomputes the HMAC over `raw_body` only, which still matches, so `Registry.process` treats the forged request as authentic and invokes the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", topic: T, body: B, ...)` [6](#0-5) , causing the app to act on the wrong tenant.
