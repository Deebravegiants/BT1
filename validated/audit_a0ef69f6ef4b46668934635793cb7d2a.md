### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `Request#shop` is read verbatim from the unauthenticated `X-Shopify-Shop-Domain` / `shopify-shop-domain` header. `Registry.process` validates the HMAC over the body only, then forwards `request.shop` unchanged to the app's handler as the trusted tenant identifier. This is the exact identity-binding gap the analog targets: a field ("shop") is acted on (used as the tenant key delivered to the host app) but is never covered by the HMAC that is supposed to authenticate the message.

### Finding Description
The HMAC validation flow is:
- `HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to `verifiable_query.hmac`. [1](#0-0) 

- For webhooks, `to_signable_string` is defined as just `@raw_body` — the shop-domain header is not included in the signed material at all: [2](#0-1) 

- `Registry.process` validates the HMAC and then immediately trusts `request.shop` (parsed straight from the header) as the identity passed to the handler: [3](#0-2) 

Because the shop identity that reaches `WebhookMetadata` (`shop: request.shop`) is never bound into the cryptographic proof, two different (body, shop) pairs that share the same body produce the same valid HMAC. Any tenant that has installed the app (an "unprivileged internet user" with respect to other merchants using the same app, since they only have their own store) receives genuine Shopify-signed webhooks — (body, HMAC) pairs computed with the app's shared `client_secret` — for events in their own store. Nothing stops that tenant from replaying an intercepted (body, HMAC) pair to the app's webhook endpoint while swapping only the `shop-domain` header to a victim shop's domain. `Registry.process` will validate correctly (because the HMAC only ever covered the body) and the handler will process attacker-supplied webhook data attributed to the victim shop.

This breaks the equality the identity binding is supposed to guarantee:
`shop authenticated by HMAC` == `shop used as tenant/session key by the handler`
Here the left side does not exist — no shop value participates in the signature at all — while the right side (`request.shop`) is fully attacker-controlled input from an unauthenticated header.

### Impact Explanation
This enables cross-tenant data injection/confusion: a malicious merchant who has installed the target app on their own store can cause the app to process fabricated webhook events (their own valid Shopify signature, arbitrary body content within what Shopify allows for that topic) as if they originated from a different, victim merchant's shop. Depending on how the host application uses `WebhookMetadata#shop` (e.g., to look up the merchant record, update order/customer data, or grant/revoke entitlements), this can lead to cross-tenant access or corruption of another merchant's data — matching the "cross-tenant access" Critical impact category, since the gem's own webhook-processing API hands this unauthenticated value directly to the host as if it were verified.

### Likelihood Explanation
Any merchant that installs the app can generate legitimate signed webhook traffic for their own store at will (e.g., by triggering `orders/create`), then simply forward the intercepted request to the app's public webhook endpoint with a modified shop header — no access to `api_secret_key`, access tokens, or victim credentials is required. The only prerequisite is having installed the app once, which is the normal, unprivileged way any internet user (merchant) interacts with an app.

### Recommendation
Bind the shop identity into the authenticated material, or otherwise verify it out-of-band, before trusting it:
- Do not rely on the `shop-domain` header alone as an authenticated tenant identifier in `Webhooks::Request`/`Registry.process`.
- Cross-check `request.shop` against the shop for which the webhook subscription was registered/stored (e.g., verify a session exists for that shop and that the app is actually installed there), or require the host application to independently confirm the shop before trusting `WebhookMetadata#shop`.
- Document clearly (and ideally enforce in `Registry.process`) that `shop-domain` is not covered by the signature and must be corroborated against known installed-shop state before being used as a tenant key.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Attacker triggers an event (e.g., creates an order) causing Shopify to POST a legitimately HMAC-signed webhook to the app's registered endpoint, with headers:
   - `X-Shopify-Shop-Domain: attacker.myshopify.com`
   - `X-Shopify-Hmac-Sha256: <valid HMAC of body B>`
   - body `B`
3. Attacker captures `(B, valid HMAC)` and replays it to the same endpoint, only changing the header to:
   - `X-Shopify-Shop-Domain: victim.myshopify.com`
4. `Registry.process` calls `HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` — unchanged, so it matches `<valid HMAC of body B>` and passes. [4](#0-3) 
5. The handler receives `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: <attacker-controlled JSON parsed from B>, ...)` and processes it as if it were a genuine event from `victim.myshopify.com`. [5](#0-4)
