### Title
Route-chosen hop pools can inject arbitrary `require_auth` calls into the caller's signed auth tree and drain the caller's wallet — (File: contracts/controller/src/strategies/swap.rs)

### Summary

The controller's strategy entrypoints (`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, `flash_position`) forward caller-supplied `swap` route bytes to the router, which dispatches hops to **unallowlisted, route-chosen pool contracts**. Any contract reached this way can call `from.require_auth()` on the transaction signer (Soroban non-root invoker auth) — e.g. `token.transfer(victim, attacker, victim_balance)`. Simulation records that unauthorized invocation as an extra sub-invocation under the victim's `swap_collateral`/`execute_strategy` auth root, and once the wallet signs the recorded tree, the theft executes. This is the on-chain analog of GHSA-4fgq-fpq9-mr3g: code reachable from untrusted input performs privileged actions that ride on a consent decision (the signature) the user made for a different, narrower purpose.

### Finding Description

`swap_tokens` authorizes one exact input transfer and calls `router.execute_strategy(controller, amount_in, swap)` inside the flash guard, with `swap` being attacker-influenceable route bytes [1](#0-0) . The router decodes the program and calls `venues::dispatch_hop` at whichever `pool` address each hop names — there is no venue/pool allowlist (INV-STRAT-03 covers Blend pools only) [2](#0-1) .

Because Soroban satisfies `require_auth` for an address from *anywhere* in the signed invocation tree (non-root auth), a rogue hop pool executed mid-route can call `token.transfer(alice, attacker, balance)` on any token the caller holds. The repository's own adversarial test proves the full chain:

- Simulation mode records the rogue pool's `transfer(victim → attacker)` as a sub-invocation under the victim's `swap_collateral` auth root — exactly what a wallet then presents for signing [3](#0-2) .
- With the simulated (poisoned) tree signed, the call succeeds and the victim's entire wallet balance of an unrelated token moves to the attacker [4](#0-3) .
- The `RogueHopPool` fixture shows the primitive: an attacker-deployed contract named by the route performs an arbitrary `from.require_auth()`-gated token transfer [5](#0-4) .

The user's signed root only names `swap_collateral(...)` — the theft payload is appended beneath it by simulation, invisible to a signer who reviews only the top-level call, mirroring "execution before/without informed consent" of the reference bug.

### Impact Explanation

Theft of user funds. The loss is not bounded by `amount_in`: any token held by the caller's address (or any `require_auth`-protected action reachable for that address — NFT transfers, other protocols' entrypoints that accept non-root auth) can be drained in the same transaction the victim believed was a single collateral swap. The attacker receives the tokens directly; nothing in the controller's post-swap measurement (`RouterOverspend`, `NoSwapOutput`) observes the rogue transfer because it touches neither the controller's input nor output token balances [6](#0-5) .

### Likelihood Explanation

Requires the victim to execute a strategy call carrying an attacker-crafted route (e.g. a compromised quote response or phishing frontend) and to sign the simulated auth tree without inspecting sub-invocations — a precondition comparable to the reference report's "start the tool in an untrusted directory" and standard wallet UX makes nested auth entries easy to miss. A single unprivileged address both deploys the rogue pool and authors the route; no privileged state, leaked key, or oracle manipulation is needed. The router explicitly supports arbitrary `pool` addresses per hop, so the malicious venue needs no allowlisting [7](#0-6) .

### Recommendation

Constrain what code can run inside a signed strategy invocation:

- Enforce a governance-managed venue/pool allowlist in the router's `dispatch_hop` (extend the existing approval-list pattern used for Blend pools to route pools), so only known venue contracts execute under the caller's auth tree.
- Alternatively/additionally, execute hop pools through a contract boundary that cannot propagate `require_auth` for the original sender — e.g. have the router refuse `require_auth`-issuing pools by design is not enforceable on Soroban, so allowlisting is the practical control.
- Document for integrators that route bytes must originate from a trusted quote source and that signers must audit every sub-invocation in the simulated auth tree before signing.

### Proof of Concept

Existing harness test demonstrates end-to-end theft:

1. Attacker deploys `RogueHopPool(victim=alice, token=wallet_token, to=attacker, amount=alice_balance)` [8](#0-7) .
2. Alice calls `controller.swap_collateral` with a route whose hop names the rogue pool. Under `mock_all_auths` (recording mode = real `simulateTransaction`), `env.auths()` returns the poisoned tree containing `transfer(alice → attacker, WALLET_BALANCE)` under Alice's `swap_collateral` root [3](#0-2) .
3. Alice signs the recorded tree; `enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer` shows the transfer executes and `balance(alice) = 0`, `balance(attacker) = WALLET_BALANCE`, while the swap itself settles "fairly" so nothing else trips [9](#0-8) .

Caveat: the exploit depends on the victim signing a tree that visibly contains the extra transfer, so practical severity is bounded by wallet/auth-entry transparency — analogous to the UI:P/user-interaction factor in the source advisory.

fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);

    let stolen_transfer = MockAuthInvoke {

## Authorization model

The only signature is the sender's. `execute_strategy` calls `sender.require_auth()`, and the sender's auth entry must cover the nested `token_in.transfer(sender, router, total_in)`; simulation produces that tree (`transaction.simulated = true` envelopes already carry it — `attach_simulated_transaction` copies the simulator's `auth` into the op — and `simulateTransaction` produces it for a locally built one). Do **not** `transfer` or `approve` tokens to the router beforehand: the router pulls the input itself, and tokens sent ahead of time are not credited.

Every venue call is self-authorized by the router with invoker-contract auth (`venues/auth.rs::authorize_as_current` → `env.authorize_as_current_contract`): Phoenix and Sushi (`HopContext::authorize_pool_pull`) and Aquarius (`aquarius/pool.rs::invoke_pool_swap`) register `token_in.transfer(router, pool, amount_in)` before the pool pulls; Comet registers `token_in.approve(router, pool, amount_in, expiry)`, then `swap_exact_amount_in` with a nested entry for the pool's `transfer_from`, then clears the allowance; Soroswap transfers from the router to the pool directly. None of these appear in the sender's auth tree.

A contract calling the router (the lending controller in `contracts/controller/src/strategies/swap.rs`, or your own) is the `sender`: it runs `authorize_transfer_as_current(token_in, self, router, amount_in)` (`common/src/token.rs`) immediately before `execute_strategy(self, amount_in, swap)` and measures its own balance deltas afterward (`RouterOverspend = 501`, `NoSwapOutput = 502` in `common/src/errors.rs`). Details in [composition.md](composition.md).
