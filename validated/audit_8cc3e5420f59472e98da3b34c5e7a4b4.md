### Title
Webhook shop/topic identity spoofing via HMAC that only covers the body, not the headers - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying an HMAC over the raw request body, then trusts the `shop`, `topic`, `webhook_id`, and `api_version` values taken from unauthenticated HTTP headers to decide which handler runs and which shop the payload is attributed to. Because the signature does not cover these identity fields, any party who can obtain one validly-signed webhook body (trivially, by triggering an event on their own store, since they are a legitimate, unprivileged install of the app) can replay that exact `body` + `hmac` pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header. The app will treat the forged request as authentic and attribute it to the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `shop`, `topic`, `webhook_id`, and `api_version` are read directly from HTTP headers, which are not part of what gets signed: [2](#0-1) [3](#0-2) 

`Utils::HmacValidator.validate` only checks that the received HMAC matches `HMAC(secret, to_signable_string)`, i.e. `HMAC(secret, raw_body)`: [4](#0-3) 

`Registry.process` uses the validated request's (unauthenticated) `shop` and `topic` to select and invoke the handler, passing `request.shop` straight into `WebhookMetadata`: [5](#0-4) 

The identity binding that should hold is:
`shop authenticated by the signature == shop the handler acts on`

but the actual binding enforced is only:
`HMAC(secret, raw_body) == received_hmac`, with `shop` (and `topic`) taken from an entirely separate, unauthenticated channel (headers).

Since an app's `api_secret_key` is shared across every shop that installs the app, any unprivileged party who installs the app on their own store is a legitimate holder of Shopify-signed webhook bodies for that secret. They can capture one genuine `(raw_body, hmac)` pair generated by Shopify for their own shop, then send it directly to the app's public webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop and/or the `x-shopify-topic` header changed to whichever topic they want the app to believe occurred. `HmacValidator.validate` still returns `true` (the body/hmac pair is genuinely valid), and `Registry.process` dispatches to the handler under the victim shop's identity.

### Impact Explanation
This crosses a tenant boundary without needing the victim's credentials or the app's `client_secret`: an attacker who is merely an installed (unprivileged) user of the app can make the host application execute its webhook business logic (e.g., order/customer/app-uninstalled processing, data writes keyed by `shop`) as if the event happened on a different merchant's store. Depending on what the host app does in its handler (common patterns: update local DB records for `shop`, mark subscription/billing state, revoke or grant data, sync inventory), this enables cross-tenant data corruption or cross-tenant state manipulation, matching the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any app using this gem's webhook registry as documented: the only thing required is (1) the ability to install the app on any shop (including the attacker's own free/dev store) to legitimately receive at least one signed webhook, and (2) network access to the app's public webhook endpoint. No secrets, tokens, or privileged access to the victim shop are required — only the ability to swap header values on a replayed HTTP request, which is entirely within the capability of an "unprivileged internet user."

### Recommendation
Bind `shop`, `topic`, and any other dispatch-relevant identity fields into the value that is actually verified, e.g. include them in `to_signable_string`, or independently re-derive/verify the shop from a source that is cryptographically tied to the signed payload (Shopify includes `shop_id`/`shop_domain` inside most webhook payload bodies — cross-check header values against the body's own shop identifier before dispatch). At minimum, reject webhooks where the header-derived shop is not consistent with a shop identifier embedded in the signed body.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` (no special privilege needed — any developer/merchant can do this).
2. Attacker triggers a webhook event (e.g., `orders/create`) on their own store, capturing the resulting webhook HTTP request Shopify sends to the app, including `raw_body` and the `x-shopify-hmac-sha256` header — both are validly signed with the app's shared `api_secret_key`.
3. Attacker sends a new HTTP POST directly to the app's webhook endpoint using the exact same `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and/or a different `x-shopify-topic`.
4. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:26-40`) succeeds because it only checks the body signature. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) dispatches the handler with `shop: "victim-shop.myshopify.com"`, causing the host app to process attacker-supplied data under the victim's tenant identity.
