### Title
`recapitalize` pays out an unfunded refund, draining pool custody while the cash book still counts it — ([File: contracts/pool/src/ops/mod.rs, exercised at contracts/pool/tests/flows.rs:3408-3483])

### Summary
Analogous to CVE-2018-19211 — where ncurses proceeded to a dereference path even after detecting a "dubious character" — the pool's `recapitalize` entrypoint proceeds to an outbound token transfer even though the expected inbound recapitalization payment never arrived. A single unprivileged call drains the pool's real token custody while the internal `cash` book continues to claim the funds are present.

### Finding Description
`LiquidityPoolInterface::recapitalize(env, hub_asset, payer, amount)` is a permissionless pool entrypoint meant to let a payer inject tokens to cover bad debt. The implemented path treats `payer` as the *recipient* of a refund and transfers `amount` tokens out of the pool without first measuring an inbound payment. The test `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` demonstrates the sequence exactly:

- `t.client().recapitalize(&hub(&t.asset), &payer, &custody)` sends the pool's entire token balance to an arbitrary `payer` — `token.balance(&t.pool) == 0` afterward [1](#0-0) 
- The `cash` book still reports `>= deposit`, because the book was credited (or never debited) as if the recapitalization had been funded [2](#0-1) 

This is the "proceed past detection" pattern: the code commits to the settlement leg (token transfer) without enforcing the funding leg, exactly like ncurses committing to the dereference path after flagging the dubious name.

### Impact Explanation
Two concrete harms, both reachable by one unprivileged `recapitalize` call:

1. **Theft of user funds**: the attacker names themselves `payer` and receives up to the pool's full custody for a market, with no tokens deposited.
2. **Protocol insolvency / freezing of remaining suppliers**: `recapitalize` never mints shares, so the `cash` book still counts the drained tokens. `require_reserves` reads the book — not the balance — so subsequent `withdraw`s pass the pool's own `InsufficientLiquidity`/`PoolInsolvent` guards and then fail inside the SAC transfer (`BalanceError = 10`), permanently trapping suppliers whose book value is uncollateralized [3](#0-2) 

### Likelihood Explanation
`recapitalize` requires no admin or controller role — the test calls it directly on the pool client with a freshly generated `payer` address, and it is listed among the permissionless entrypoints (`scripts/permissionless_entrypoints.txt`). The only precondition is an existing market with token custody, which every supplied market has.

### Recommendation
Make `recapitalize` settle atomically like the other measured-receipt paths: transfer `amount` *from* `payer` *to* the pool (with `payer.require_auth()`), or measure the pool's balance delta around the call and only credit the cash book for tokens actually received. Never emit an outbound transfer in a recapitalization flow, and reconcile `cash` against real custody rather than crediting the book unconditionally.

### Proof of Concept
The in-repo test is already a working PoC:

```rust
// contracts/pool/tests/flows.rs
let custody = token.balance(&t.pool);
t.client().recapitalize(&hub(&t.asset), &payer, &custody);
assert_eq!(token.balance(&t.pool), 0);          // custody stolen
assert!(t.state_snapshot().cash >= deposit);    // book still claims it
// supplier withdraw now fails inside the SAC transfer (error 10)
t.client().try_withdraw(&receiver, &false, &t.wdr(supplied, i128::MAX, 0));
```

An attacker repeats this per market/`hub_asset` with `payer = attacker` and `amount = pool balance`.
