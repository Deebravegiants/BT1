### Title
Unauthenticated D-Bus signup signal emission allows spoofed `signup_started`/`signup_finished` events - (File: src/dbus.rs)

### Summary
`orb-core` registers a D-Bus interface on the session bus that emits `signup_started` and `signup_finished` signals to notify other local processes of signup lifecycle events. Like the `TokenVault.sol` `DepositClaimable`/`RedeemClaimable` emitters in the external report, these are broadcast-only notifications with no sender authentication, so any local, unprivileged process sharing the session bus can forge these signals to mislead consumers about the orb's signup state.

### Finding Description
`orb-core` defines a `Signup` D-Bus interface with two signal-emitting methods, `signup_started` and `signup_finished(success: bool)`, under the well-known name `org.worldcoin.OrbCore1` at path `/org/worldcoin/OrbCore1/Signup`: [1](#0-0) 

The connection is created on the **session bus** (not the system bus, and with no polkit/D-Bus policy shown restricting senders): [2](#0-1) 

These signals are emitted by `MasterPlan` at the true start/finish of a signup: [3](#0-2) [4](#0-3) 

D-Bus signals are broadcast messages: any peer connected to the same session bus can emit a message with an arbitrary `interface`/`path`/`member` triple (e.g., `org.worldcoin.OrbCore1.Signup`, `/org/worldcoin/OrbCore1/Signup`, `signup_started`) regardless of whether it owns the `org.worldcoin.OrbCore1` well-known name — ownership of a name only matters for point-to-point method calls, not for signal emission. There is no code visible in `orb-core` that validates the signal sender's UID/PID via `GetConnectionUnixUser`/`GetConnectionCredentials` before trusting these signals. Consequently, this mirrors the report's bug class exactly: a function/mechanism whose sole purpose is to emit an event, with parameters supplied by the caller and no access control, enabling forged or DoS-level event floods that mislead anything subscribed to the events.

### Impact Explanation
Any process co-resident on the same session bus as `orb-core` (an unprivileged local agent/process trust-boundary issue, in scope per the "agent-IPC trust boundaries" analog) can:
- Emit fake `signup_finished(success: true)` signals to make external consumers of this interface believe a signup completed successfully when none occurred, or vice-versa, producing a misattributed/spoofed signup lifecycle event.
- Flood the bus with spurious `signup_started`/`signup_finished` signals, a low-cost local DoS against any downstream listener of this interface, analogous to the report's concern about "off-chain infrastructure" DoS via fraudulent event floods.

This is scoped to whatever local component subscribes to `org.worldcoin.OrbCore1.Signup` signals; no direct code was found in this repository that consumes them (subscribers likely live in a separate service, e.g. orb-ui or a supervisor process, outside this repo's indexed contents), so the concrete downstream consequence (e.g., whether it affects fraud/liveness state or is purely UI/telemetry) could not be fully confirmed from the available index.

### Likelihood Explanation
Exploitation requires only local access to the same D-Bus session that `orb-core` uses — no special privilege, hardware access, or remote network position is needed, matching the "unprivileged-user"/"agent-IPC" analog class. Given the signal-emission mechanism relies on no sender verification, likelihood of successful spoofing (given local bus access) is high, but real-world impact depends on whether any privileged decision-making component trusts these signals without independent verification, which could not be confirmed here.

### Recommendation
- Restrict the D-Bus connection to the system bus with an explicit D-Bus policy (`busconfig`) that only allows the trusted UID running `orb-core` to own/emit under `org.worldcoin.OrbCore1.Signup`.
- Have any consumer of these signals verify the signal's actual sender identity (via `org.freedesktop.DBus.GetConnectionCredentials`/`GetConnectionUnixUser`) rather than trusting the interface/path/member alone.
- If these signals are purely informational/UI-facing and carry no security-relevant decision weight, document that explicitly; otherwise, avoid making any fraud/liveness/signup-state decision based solely on these D-Bus signals.

### Proof of Concept
On a machine with access to the same D-Bus session as the orb-core process (e.g., another local unprivileged process/user session), a signal can be emitted without owning the `org.worldcoin.OrbCore1` name:

```
dbus-send --session --type=signal \
  /org/worldcoin/OrbCore1/Signup \
  org.worldcoin.OrbCore1.Signup.signup_finished boolean:true
```

Any process subscribing with a match rule such as `interface='org.worldcoin.OrbCore1.Signup'` will receive this as if it were emitted by the genuine `orb-core` process, matching the signal shapes declared in [5](#0-4) .

/// `Signup` is a DBus interface that emits signals related to signup events.
///
/// At the moment, the only signal emitted is for signups starting.
pub struct Signup;

#[dbus_interface(name = "org.worldcoin.OrbCore1.Signup")]
impl Signup {
    /// Emits a signal when a signup is started.
    #[dbus_interface(signal)]
    pub async fn signup_started(ctxt: &SignalContext<'_>) -> Result<()>;

    /// Emits a signal when a signup is completed
    #[dbus_interface(signal)]
    pub async fn signup_finished(ctx: &SignalContext<'_>, success: bool) -> Result<()>;
}
