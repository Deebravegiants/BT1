## Analysis

The bug class described in the report — a function/binding lacking a check that ties an *action* to a *verified identity* — maps cleanly onto how `ShopifyAPI::Webhooks::Registry.process` authenticates the tenant (`shop`) of an inbound webhook.

### Finding: Webhook shop identity not covered by HMAC — cross-tenant webhook spoofing

**File:** `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`

`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

The `shop` accessor, however, is read directly from an unauthenticated HTTP header (`shopify-shop-domain` / `x-shopify-shop-domain`), which is never part of the signed payload: [2](#0-1) 

`Registry.process` validates the request purely against that body-only HMAC, then forwards `request.shop` straight to the app's handler as the trusted tenant identifier: [3](#0-2) 

`Utils::HmacValidator.validate` recomputes the HMAC over `verifiable_query.to_signable_string` (the raw body) and compares it to the `hmac-sha256` header — it never incorporates `shop`: [4](#0-3) 

The library's own documentation asserts this call "will verify the request did indeed come from Shopify," implying the whole payload — including the shop identity — is authenticated: [5](#0-4) 

### Finding Description
The identity binding that should hold is: `shop header value == shop that produced the HMAC-signed body`. Because the HMAC only signs `@raw_body`, this equality is never checked. An unprivileged app-installer (any user who can install the app on their own trial/development store — no `api_secret_key`, no privileged account, no TLS interception required) can capture one legitimate webhook delivery for their own shop (valid body + valid HMAC), then replay that exact body to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds because the body is unchanged, and `Registry.process` passes the attacker-chosen `shop` value into `WebhookMetadata`, which the host app trusts to route/attribute the update (e.g., `shop_domain: data.shop` per the documented handler pattern): [6](#0-5) 

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: an attacker who legitimately controls one shop can inject data attributed to an arbitrary other shop into the host application's webhook handling pipeline (cross-tenant access/data confusion), satisfying the Critical "cross-tenant access" category, since no merchant credentials, access tokens, or `client_secret` are needed — only replay of a body they already legitimately received.

### Likelihood Explanation
Moderate-to-high: requires only a public/free trial store to receive one legitimate webhook and standard HTTP tooling to replay it with a modified header against the target app's public webhook endpoint; no secrets are needed.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) in the signed material verified for webhooks, or independently corroborate the header-derived `shop` against a value obtained from a source Shopify does cover with a trusted signature, before dispatching to `WebhookHandler#handle`.

### Proof of Concept
1. Install the app on attacker-controlled store `attacker.myshopify.com`; capture a real webhook POST (body `B`, valid `X-Shopify-Hmac-Sha256: H`).
2. Replay: `POST /callback/orders/create` with the same body `B` and header `H`, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Registry.process` → `HmacValidator.validate` passes (body/HMAC untouched) → handler receives `WebhookMetadata(shop: "victim.myshopify.com", body: B, ...)`, causing the host app to act on data attributed to `victim.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
