### Title
Unchecked `u256`→`u32`/`u64` conversion of relayer-supplied SP1 BEEFY proof fields causes a runtime panic (DoS) - ([File: evm/rust/src/conversions.rs])

### Summary
The BEEFY SP1 consensus-proof path converts an untrusted, ABI-decoded `SP1BeefyProof.commitment.blockNumber` / `validatorSetId` (`U256`) into Rust `u32`/`u64` using `.try_into().expect(...)`, without any bounds validation before the conversion. Any account able to submit a BEEFY consensus proof can trigger this `.expect()` panic with an out-of-range value, matching the CVE-2020-6078 pattern of unchecked parsing of attacker-controlled message fields leading to an unhandled failure/crash instead of a typed, rejectable error.

### Finding Description
In `evm/rust/src/conversions.rs`, the conversion from the Solidity ABI type `SP1Beefy::SP1BeefyProof` into the internal `beefy_verifier_primitives::Sp1BeefyProof` does: [1](#0-0) 
```rust
impl From<crate::sp1_beefy::SP1Beefy::SP1BeefyProof> for Sp1BeefyProof {
    fn from(value: crate::sp1_beefy::SP1Beefy::SP1BeefyProof) -> Self {
        Sp1BeefyProof {
            block_number: value
                .commitment
                .blockNumber
                .try_into()
                .expect("block number out of bounds"),
            validator_set_id: value
                .commitment
                .validatorSetId
                .try_into()
                .expect("validator set id out of bounds"),
            ...
```
`blockNumber` and `validatorSetId` in the Solidity ABI struct are `uint256`, but the Rust representation only holds `u32`/`u64` respectively. If a submitter supplies a value greater than `u32::MAX` (for `blockNumber`) or `u64::MAX` (for `validatorSetId`), the `.expect()` calls panic instead of returning a decode/validation error.

This conversion is reached by an unprivileged submitter through `pallet-beefy-consensus-proofs::verify_and_apply`, which decodes the ABI payload (properly, with `.map_err(...)?`) and then calls `.into()` on the decoded struct, invoking the vulnerable, panicking conversion: [2](#0-1) 
```rust
let consensus_proof = match proof_type {
    types::PROOF_TYPE_SP1 => {
        let abi_proof =
            <ismp_abi::sp1_beefy::SP1Beefy::SP1BeefyProof as SolType>::abi_decode_params(
                abi_payload,
            )
            .map_err(|_| Error::<T>::AbiDecodeFailed)?;
        let scale_proof: beefy_verifier_primitives::Sp1BeefyProof = abi_proof.into();
        ...
```
Note that every other decode/parse step in this same function (and throughout the consensus-client stack — GRANDPA, BEEFY, sync-committee, parachain clients) is deliberately converted into a typed `Error` via `.map_err(...)?`, which is exactly the pattern the codebase uses elsewhere to guard against malformed message fields (see `modules/consensus/beefy/verifier/src/lib.rs:229-236`, which was previously hardened against an analogous unchecked-index panic on `leaf_indices[0]`). The `From<SP1BeefyProof>` conversion is the one remaining spot in this call path where an attacker-controlled numeric field bypasses that pattern and panics via `.expect()` instead.

This is directly analogous to CVE-2020-6078: a message-parsing function (`mdns_recv`) failed to check/validate a parsed field, leading the caller to use bad data and crash. Here, the ABI-decode step succeeds, but the subsequent unchecked numeric narrowing conversion of a relayer-supplied field panics.

### Impact Explanation
A panic inside pallet extrinsic execution during proof verification is a `Result unable to deliver messages` / message-route-availability issue: it can abort the transaction's execution context, and depending on execution backend (native vs wasm) can affect availability of the consensus-update dispatch path used to deliver BEEFY/SP1 consensus updates and, transitively, all downstream cross-chain message delivery gated on this consensus client being updated. Because `verify_and_apply` is reachable from an unsigned/permissionless proof-submission entry point (as documented for the overall `handle_unsigned`/proof-submission flow), a single malformed message field from any relayer can panic execution rather than being rejected with a typed error — a denial-of-service on the BEEFY consensus-update route.

### Likelihood Explanation
High: the ABI type is `uint256` and the internal type is `u32`/`u64`, so an out-of-range value is only a single crafted field away, requires no special privilege, and requires no cryptographic forgery — only a syntactically valid but numerically out-of-range proof submission that otherwise ABI-decodes successfully.

### Recommendation
Replace both `.try_into().expect(...)` calls in `evm/rust/src/conversions.rs`'s `From<SP1BeefyProof> for Sp1BeefyProof` (and any other `From` impls following the same pattern, e.g. `evm/rust/src/conversions.rs:368-389`'s `leaf_index` narrowing) with fallible conversions that propagate a typed error (or clamp/reject) all the way back through `verify_and_apply`'s `Error::<T>::AbiDecodeFailed`/a new dedicated error variant, so out-of-range relayer-supplied numeric fields are rejected rather than causing a panic.

### Proof of Concept
1. Craft an SP1 BEEFY consensus proof payload where the ABI-encoded `SP1BeefyProof.commitment.blockNumber` (a `uint256`) is set to a value `> u32::MAX` (e.g., `0x1_0000_0000`), with the rest of the payload otherwise well-formed enough to pass `abi_decode_params`.
2. Submit this payload as the `PROOF_TYPE_SP1` proof to `pallet-beefy-consensus-proofs`'s proof-submission call (`verify_and_apply` path in `modules/pallets/beefy-consensus-proofs/src/lib.rs`).
3. `abi_decode_params` succeeds; `abi_proof.into()` invokes `evm/rust/src/conversions.rs`'s `From<SP1BeefyProof> for Sp1BeefyProof`, which calls `.try_into().expect("block number out of bounds")` on the oversized value, panicking instead of returning a typed error.

Note: I was unable to fully confirm within the available tool calls whether `submit_proof`/the entry point invoking `verify_and_apply` is unsigned (`ensure_none`) or merely permissionlessly signed (`ensure_signed`) — the grep for `submit_proof`/origin patterns in `modules/pallets/beefy-consensus-proofs/src/lib.rs` returned matches but I could not read the file contents before the tool budget ran out. If it turns out this entry point requires a privileged origin, this finding would not qualify under the "unprivileged" scope constraint; based on the module's stated purpose (permissionless proof submission mirroring `pallet-ismp::handle_unsigned`) and the doc language for BEEFY/SP1 uncle/rotation routing in the surrounding code, it is most likely reachable by any account/relayer, but this should be verified against the actual `#[pallet::call]` definition before treating this as fully confirmed.
