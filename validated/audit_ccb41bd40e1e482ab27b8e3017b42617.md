### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity of an incoming webhook (`shop`) directly from the `x-shopify-shop-domain` HTTP header, but the HMAC signature that `Registry.process` verifies is computed only over the raw request body. The `shop` field is never part of the signed material, so it is not cryptographically bound to the HMAC that authenticates the webhook. Anyone who can obtain a single genuine `(body, hmac)` pair signed with the app's `api_secret_key` — which happens automatically for any store that installs the app, since Shopify signs every outbound webhook with the app's shared secret — can replay that exact body/HMAC pair while substituting an arbitrary victim `shop-domain` header, and `Registry.process` will accept it as an authentic webhook for that victim shop.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

`Request#shop` is read straight from an unauthenticated header with no cross-check against the signed payload: [2](#0-1) [3](#0-2) 

`HmacValidator.validate` verifies the HMAC purely against `to_signable_string` (the body), never touching `shop`, `topic`, or any header: [4](#0-3) 

`Registry.process` calls this validator and then forwards `request.shop` — the unauthenticated header value — as the tenant identifier passed to the app's handler: [5](#0-4) 

This breaks the intended identity binding:
`shop authenticated by HMAC` ≠ `shop delivered to the handler as WebhookMetadata#shop`

Concretely: any store that installs the app receives real webhooks signed with the app's `api_secret_key` (the secret is shared across all shops using that app, by Shopify's design). An attacker who controls such a store can capture one legitimate `(raw_body, x-shopify-hmac-sha256)` pair for a topic whose body doesn't need to vary per victim (e.g. `app/uninstalled`, `shop/redact`, `customers/redact`, or any topic where the attacker can shape the body content via their own store data), then POST it to the app's webhook endpoint again, keeping the body and HMAC bytes identical but swapping only the `x-shopify-shop-domain` header to a victim shop. Since the header is outside the signed bytes, `HmacValidator.validate` still returns true, and `Registry.process` hands the handler a `WebhookMetadata` claiming the event is for the victim shop while carrying attacker-chosen body content.

### Impact Explanation
This is a cross-tenant identity-spoofing vector: it lets one tenant (an app-installing attacker) forge webhook events that the host application will process as if they originated from a different, victim tenant, with attacker-influenced body content. Depending on how the host app's registered handlers use `WebhookMetadata#shop` (e.g., to look up/mutate per-shop records, trigger GDPR data deletion, mark a shop as uninstalled, or update billing/subscription state), this enables cross-tenant data corruption or triggering privileged per-tenant actions against a shop the attacker does not control — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Requires only that the attacker be able to install the target app on some store they control (an unprivileged, self-service action) and be able to reach the app's public webhook endpoint — no access to `api_secret_key`, access tokens, or the victim's credentials is needed. The attacker never needs to compute a valid HMAC themselves; they simply replay one they legitimately received.

### Recommendation
Bind the tenant identity to the signed content. At minimum, include `shop-domain` (and ideally `topic`/`webhook-id`) in the HMAC-signed material verified by `HmacValidator`, or have `Request#to_signable_string` incorporate the relevant headers alongside the body so `OpenSSL.secure_compare` in `lib/shopify_api/utils/hmac_validator.rb` authenticates the full tuple `(shop, topic, body)` rather than the body alone.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Shopify sends a legitimate webhook (e.g. `app/uninstalled`) to the app's endpoint with headers:
   `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over body B>`, body `B`.
3. Attacker captures `(B, HMAC)` and re-sends an HTTP request to the same webhook endpoint, keeping body `B` and `x-shopify-hmac-sha256` unchanged, but rewrites the header to `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which validates successfully because it only checks `request.to_signable_string` (`B`) against the HMAC — see `lib/shopify_api/utils/hmac_validator.rb:26-31` and `lib/shopify_api/webhooks/request.rb:35-38`.
5. The handler receives `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim-shop.myshopify.com", body: ..., ...)` per `lib/shopify_api/webhooks/registry.rb:198-199`, and the host app processes an uninstall/data event for `victim-shop.myshopify.com` that never actually occurred.
