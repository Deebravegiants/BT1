### Title
Action-level residual/approval siphon via unconstrained `externalActionMetadata` in `ExternalActionSwap.swap` - (File: contracts/external-actions/swaps/ExternalActionSwap.sol)

### Summary
`ExternalActionSwap.swap` never ties the amount the LI.FI router is allowed to pull to the officially accounted `inputAmount = uint256(-deltaAmounts[0])`. Combined with `approveUnlimited` (max, persistent allowance to `router`) and `swappedAmount` being derived solely from an output-token balance diff, any token balance stranded in the action (dust, partial-fill refunds, direct transfers) can be swept by the next caller and credited entirely to their own output UTXO, while `Hinkal.transact`'s invariant checks only look at the Hinkal contract's own balance sheet, not the action's.

### Finding Description
The invariant that should hold is: tokens actually consumed/produced by the action for a given transaction == `-deltaAmountChanges` that `Hinkal._externalTransact` sent it for that transaction [1](#0-0) .

In `ExternalActionSwap.swap`, `inputAmount` is computed from `deltaAmounts[0]` (the amount Hinkal actually transferred to the action for this call) [2](#0-1) , but this value is only used to *label* the router call; it is never enforced as an upper bound on what the router is allowed to pull. `LifiExternalAction.callRouter` grants `router` an unlimited, persistent allowance via `approveUnlimited` and then executes attacker-controlled `externalActionMetadata` verbatim, measuring `swappedAmount` purely as the output-token balance delta of the action contract [3](#0-2) . Nothing in this call restricts the router's pull to `inputAmount`; the amount actually consumed is whatever the attacker encoded inside `externalActionMetadata`, up to the full standing allowance and the action's real token balance [4](#0-3) .

Back in `swap`, the entire measured `swappedAmount` (fees deducted) is forwarded to `msg.sender` (the Hinkal contract) and packaged into a single output `UTXO` for the caller's own `stealthAddressStructure` [5](#0-4) .

`Hinkal.transact`'s balance/UTXO equality check only compares Hinkal's *own* balance delta against `amountChanges[i] + utxoAmount` [6](#0-5) . Hinkal's balance for the input token decreases by exactly the accounted `inputAmount` (transferred to the action before `runAction` is invoked) [7](#0-6) , and Hinkal's balance for the output token increases by exactly `amountToSendToHinkal`, which equals `utxoAmount`. Both sides of the top-level equality hold — the check is blind to the fact that the action itself consumed more input token than `inputAmount` (using leftover balance already sitting at the action's address, pulled through the standing unlimited allowance) to inflate `swappedAmount`, and thus the caller's UTXO.

Root cause: any ERC20 balance parked at the action's address that is not accounted for by the current transaction's `deltaAmountChanges` — from a prior partial-fill refund by the router (many aggregator facets return unspent input to `msg.sender`, which is the action, since the action never sweeps input-token residue), rounding dust from `swappedAmount - totalFee`, or a stray direct transfer — remains reachable via the never-revoked-to-zero unlimited approval. Because `externalActionMetadata` is fully attacker-controlled and unconstrained by the proof/circuit as far as the "amount pulled from the action" is concerned, an attacker can craft a swap call that drains this stranded balance through the router in the same transaction as their own legitimate small deposit, and receive the combined output as their own private UTXO. `SafeERC20`/`approveApprove` semantics are not what create the gap here — the gap is the absence of any code that checks "input token consumed by the router == `inputAmount`" or that sweeps/limits residual balances before/after each swap.

### Impact Explanation
An unprivileged attacker can capture value that does not belong to them: any residual balance stranded in the `ExternalActionSwap`/`LifiExternalAction` contract (from a prior user's partial-fill refund, protocol fee-rounding dust, or accidental transfer) can be claimed as extra output value attributed solely to the attacker's own UTXO, in excess of what Hinkal actually sent the action for that transaction. This is direct theft of value that was parked in an in-flight action on behalf of the protocol/other users, matching the Critical category ("direct theft of shielded or in-flight user funds"). It is repeatable every time residual balance re-accumulates in the action.

### Likelihood Explanation
Requires: (1) some non-zero balance to exist at the action's address that is not tied to the current transaction's accounted `deltaAmountChanges` (achievable via router partial-fill refunds that LI.FI facets commonly issue, rounding dust from fee subtraction, or simply an attacker/anyone sending tokens directly to the well-known action address), and (2) the action's standing `approveUnlimited` allowance to `router` being large enough to cover it (always true since it is set to `type(uint256).max`). The attacker needs only to be able to call `Hinkal.transact` with a legitimate small deposit and self-crafted `externalActionMetadata` — no privileged role is needed. Given `approveUnlimited` is deliberately designed to never re-approve to zero once high enough, this condition persists indefinitely once residual value exists, making exploitation low-cost and repeatable.

### Recommendation
- Do not measure `swappedAmount` purely by output-token balance diff without also verifying that the input-token balance decreased by no more than `inputAmount` (i.e., check and cap actual input consumption against the officially accounted `inputAmount`, reverting or refunding excess).
- Avoid `approveUnlimited`; instead approve exactly `inputAmount` per call (`approveERC20Token`) and reset the allowance to zero after the router call so no standing allowance persists between transactions.
- Add an explicit sweep/accounting step so that any token balance in the action beyond what this transaction's `deltaAmountChanges` accounts for cannot be silently included in the next swap's measured output — e.g., snapshot and require `inputToken` balance-diff of the action equals `inputAmount` before/after the router call.

### Proof of Concept
Foundry plan:
1. Deploy `Hinkal`, `HinkalHelper`, and `LifiExternalAction` against a mock LI.FI router that supports a "refund unspent input" facet function.
2. User A performs a legitimate `Hinkal.transact` swap where the mock router deliberately refunds a portion of the input token back to the action (simulating a partial fill), leaving residual `inputToken` balance stuck at the action's address; assert this residual is non-zero and unaccounted (`action.balanceOf(inputToken) > 0` after A's tx completes cleanly).
3. Attacker B crafts their own small deposit (`deltaAmounts[0]` small) and constructs `externalActionMetadata` for the mock router that pulls the full action balance (residual + B's new deposit) via the pre-existing unlimited allowance, swapping it all to `outputToken`.
4. Assert: `swappedAmount` (and therefore B's minted output UTXO amount) > `uint256(-deltaAmounts[0])` for B's own transaction, i.e., B's output UTXO value exceeds `-deltaAmountChanges` Hinkal sent the action in B's transaction — proving the equality "tokens leaving the action in a tx == -deltaAmountChanges Hinkal sent it that tx" is broken and B captured A's stranded value.
5. Assert Hinkal's own top-level balance/UTXO checks in `transact` (lines 97–146) still pass, showing existing guards do not catch this leak.

    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
