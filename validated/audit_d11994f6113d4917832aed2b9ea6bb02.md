### Title
Webhook `shop` (and `topic`/`api-version`/`webhook-id`) headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then unconditionally trusts the `shop` (and other) headers to identify which merchant the payload belongs to. Because the signature never covers those headers, any request whose raw body carries a valid HMAC can have its `shop-domain` header freely substituted, letting an attacker attribute webhook data (and any tenant-scoped side effects the host app performs) to a shop of their choosing.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read from HTTP headers that are never part of the signed content: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)`, which computes `HMAC(secret, request.to_signable_string)` i.e. `HMAC(secret, raw_body)` only: [3](#0-2) 

After that check passes, `process` immediately trusts `request.shop` (from the unauthenticated header) to build the `WebhookMetadata` handed to the app's handler: [4](#0-3) 

The binding the gem should enforce is: `hmac == HMAC(secret, raw_body || shop || topic || ...)`, i.e. the identity fields used by the handler must be covered by the same signature that authenticates the request. Instead the gem enforces `hmac == HMAC(secret, raw_body)` while treating `shop` (an unsigned field) as authenticated. Any two requests with the same raw body but different `shop-domain` header both pass `HmacValidator.validate`, since the header plays no role in signature computation.

### Impact Explanation
Because a merchant who installs the app controls their own shop and can trigger arbitrary legitimate webhook deliveries (each with a body validly HMAC-signed by Shopify using the app's `api_secret_key`), an attacker-merchant can capture such a signed body and resubmit it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop. `Registry.process` will accept the HMAC (it never checked the header) and hand the handler a `WebhookMetadata` claiming the payload is for the victim shop. Any app logic that trusts `data.shop` for tenant-scoped actions (e.g. `shop/redact`, `customers/redact`, `app/uninstalled`, order/customer updates) is invoked as if it originated from the victim tenant — breaking tenant isolation and constituting cross-tenant access/injection into another merchant's data pipeline.

### Likelihood Explanation
Exploitation only requires an attacker to be able to install the app on their own store (a normal, unprivileged action) and capture one webhook delivery from Shopify for that store, then replay it against the app's public webhook endpoint with a modified `shop-domain` header. No access to `api_secret_key`, access tokens, or any privileged account is required.

### Recommendation
Include the identifying headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signable content that the HMAC validates, or otherwise verify these header values against the shop derived from an authenticated source (e.g., cross-check against sessions/webhook subscription records) before dispatching to the handler, so the signature binds to the same fields the handler consumes.

### Proof of Concept
1. App receives a legitimate Shopify webhook for `attacker-shop.myshopify.com` with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)`.
2. Attacker resends `POST /webhooks` with the same body `B`, the same valid HMAC header, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B)` — this still matches. [5](#0-4) 
4. The handler executes with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to act on victim-shop's behalf using attacker-controlled webhook content.
