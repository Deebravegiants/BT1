### Title
Withdraw permanently DoS'd by division-by-zero panic in `calc_take_pnl` when a drained vault's decimal-normalized reserve floors to zero - (File: `program/src/processor.rs`)

### Summary
`Processor::calc_take_pnl` divides by the decimal-normalized reserve `x1` without checking it for zero. An unprivileged swapper can legally drain a vault (via `SwapBaseOut`) down to a tiny non-zero raw balance whose *decimal-normalized* value floors to `0` (because `normalize_decimal_v2` truncates when `native_decimal > sys_decimal` digits). Any subsequent `Withdraw` call then panics with an unwrapped divide-by-zero, permanently bricking withdrawals for every LP in the pool.

### Finding Description
`process_withdraw` computes normalized reserves and, unless the pool is in `WithdrawOnly` status, calls `Self::calc_take_pnl`: [1](#0-0) 

Inside `calc_take_pnl`, the gating check at the top compares *raw* pool amounts (`pool_pc_amount`/`pool_coin_amount`), not the normalized `x1`/`y1` values passed in: [2](#0-1) 

If that raw-value check passes (which it can even when the *normalized* `x1` is 0, since the two use different value spaces), execution proceeds to: [3](#0-2) 

`y2 = x2.checked_mul(y1).unwrap().checked_div(x1).unwrap()` will panic if `x1 == 0`.

`x1` is produced by `Calculator::normalize_decimal_v2`, which truncates via integer division and can legitimately return `0` for a small but non-zero raw reserve when `pc_decimals` (or `coin_decimals`) exceeds the digit-width implied by `sys_decimal_value`: [4](#0-3) 

An unprivileged attacker can reach this state entirely through normal, permitted instructions: repeatedly (or in one large trade) call `SwapBaseOut`/`SwapBaseOut2` to withdraw almost the entire pc (or coin) reserve — the only guard is `swap.amount_out >= total_pc_without_take_pnl` returning `InsufficientFunds`, so the attacker can always leave 1 raw unit in the vault: [5](#0-4) 

Once the raw reserve is small enough that its `normalize_decimal_v2` result is `0`, every future `Withdraw` call (from any LP, unless the pool authority separately transitions the pool to `WithdrawOnly` status, which is a privileged action) will hit the `calc_take_pnl` division and panic, aborting the transaction.

### Impact Explanation
This permanently freezes all remaining LP funds in the affected pool: `Withdraw` is the only instruction that returns coin/pc/lp tokens to liquidity providers, and it will unconditionally panic for as long as the pool remains in a non-`WithdrawOnly` swap-permitted status. Ordinary LPs have no way to recover their stake without privileged intervention (an admin explicitly setting `WithdrawOnly` via `SetParams`), which is outside the reach of a normal user. This matches the CVE's "hang or crash" bug class, escalated here to concrete, persistent freezing of user/LP funds.

### Likelihood Explanation
The precondition (decimal mismatch between `pc_decimals`/`coin_decimals` and `sys_decimal_value` large enough that a non-zero raw balance normalizes to zero) is a normal, expected configuration for pools pairing high-decimal tokens (e.g., 9-decimal SOL-wrapped mints) with a coarser `sys_decimal_value`. Draining a vault to near-zero via `SwapBaseOut` requires only a single attacker-controlled transaction with no special privileges, and the resulting DoS is deterministic and repeatable (any subsequent Withdraw panics), giving this a Medium-to-High practical likelihood.

### Recommendation
In `Calculator::calc_take_pnl` (and any other caller of `checked_div` on `x1`), explicitly check `x1 != 0` (and `y1 != 0`) before dividing and return `AmmError::CheckedDivOverflow` or skip the PnL-taking step gracefully instead of unwrapping. Additionally, align the gating comparison in `calc_take_pnl` to use the same normalized value space (`x1`/`y1`) as the later division, rather than mixing raw and normalized quantities.

### Proof of Concept
1. Create/target a pool where `pc_decimals` (or `coin_decimals`) is large relative to `amm.sys_decimal_value` (e.g., `pc_decimals = 9`, `sys_decimal_value = 10^6`), such that any raw pc balance below 1000 normalizes to `0` via `normalize_decimal_v2`.
2. Submit a `SwapBaseOut` (or `SwapBaseOut2`) instruction with `amount_out = total_pc_without_take_pnl - 1`, driving the pc vault raw balance down to `1`. [5](#0-4) 
3. Submit any `Withdraw` instruction (from any LP holding LP tokens). `process_withdraw` computes `x1 = normalize_decimal_v2(1, 9, 10^6) = 0` and calls `calc_take_pnl`, which panics at `checked_div(x1)`. [1](#0-0) 
4. All future `Withdraw` calls on this pool panic identically until a privileged party changes `amm.status` to `WithdrawOnly`, permanently freezing LP funds in the meantime.

        // e.g., amm.sys_decimal_value is 10**6, native_decimal is 10**9, price is 1.23, this function will convert (1.23*10**9) -> (1.23*10**6)
        //let ret:u64 = val.checked_mul(amm.sys_decimal_value).unwrap().checked_div((10 as u64).pow(native_decimal.into())).unwrap();
        let ret_mut = (U128::from(val))
            .checked_mul(sys_decimal_value.into())
            .unwrap();
