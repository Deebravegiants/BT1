### Title
Webhook `shop` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, but the `shop` value used to route the event to the merchant-facing handler is taken from an HTTP header that is never included in the signed material. This breaks the intended binding "the shop the HMAC vouches for" == "the shop the handler acts on," analogous to the reported `basisPoints`-style logic gap where a value that participates in downstream logic (`clientConfig.basisPoints`) is not properly constrained/verified before use.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop` is read directly from the `x-shopify-shop-domain` / `shopify-shop-domain` header, completely independent of the signed payload: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `verifiable_query.to_signable_string` (the body), never against the `shop` header: [3](#0-2) 

`Registry.process` gates on this same body-only HMAC check and then dispatches to the app's handler using the *unverified* `request.shop`: [4](#0-3) 

By contrast, the library's own OAuth `AuthQuery` (also a `VerifiableQuery`) demonstrates the correct pattern: it explicitly folds `shop` into the signed string so the shop identity cannot be altered without invalidating the HMAC: [5](#0-4) 

The webhook path does not follow this pattern — `shop` is excluded from `to_signable_string`, so the HMAC only proves "this body was produced using the app's shared `api_secret_key`" and says nothing about which shop it belongs to.

Because `api_secret_key` is a single per-app secret shared across every shop that installs the app, any attacker who controls one shop that has the app installed (a completely unprivileged, non-admin capability — anyone can install/uninstall a public app on a development store) can capture a legitimate `(raw_body, hmac)` pair from a real webhook delivered for their own store. They can then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop. `Utils::HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` forwards `WebhookMetadata` with the attacker-chosen `shop` value to the app's handler, which the host application will trust as the tenant identity when writing to its per-shop-keyed session/data store.

### Impact Explanation
This is a cross-tenant confusion vulnerability: an attacker with access to only their own (attacker-controlled) shop’s webhook traffic can produce webhook events that a host application will process as if they originated from a different, victim shop, because the shop identity is never cryptographically bound to the payload the HMAC actually protects. Depending on how the host app's `WebhookHandler#handle` implementation keys off `data.shop` (e.g., to look up/update per-shop records, uninstall state, billing state, or fulfilled order data), this enables data injection/corruption into another merchant's tenant scope — a cross-tenant access impact.

### Likelihood Explanation
Medium-to-High: exploitation requires the attacker to install the target app on any shop they control (a normal, unprivileged, publicly available action for any Shopify app listed on the App Store or dev app), then capture and replay a webhook to the app's public webhook endpoint with a modified `shop` header. No access to the app's `client_secret`/`api_secret_key`, no admin privileges, and no interaction with the victim shop are required.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the HMAC-protected material for webhook requests, e.g., by having `Webhooks::Request#to_signable_string` incorporate the shop header alongside the raw body (mirroring how `AuthQuery#to_signable_string` includes `shop`), or by independently verifying that the `shop` header matches a shop for which an active session/installation exists before dispatching to the handler. At minimum, document that `data.shop` from `WebhookMetadata` is unauthenticated and must not be trusted as a tenant key without additional server-side verification (e.g., cross-checking against a known-installed shop list).

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (an app publicly installable by anyone), obtaining a legitimate webhook delivery:
   - Headers: `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over body>`, body `B`.
2. Attacker resends the exact same body `B` and `x-shopify-hmac-sha256` value to the same webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers (only header *presence* is checked in the constructor): [6](#0-5) 
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (== `B`) and successfully matches the replayed `hmac`, since `shop` was never part of the signed content.
5. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, and the host app processes/stores data as belonging to `victim-shop.myshopify.com`, even though the payload actually originated from the attacker's own shop.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
