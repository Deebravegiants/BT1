### Title
Attacker-supplied swap route grafts a hidden `token.transfer(victim → attacker)` onto the victim's signed auth tree, draining arbitrary wallet tokens — (File: contracts/swap-aggregator/src/execute/mod.rs)

### Summary
CVE-2020-11880 let a crafted `mailto?attach=` parameter smuggle an unintended local file into an email the user believed they were composing — the privileged action (attaching `.bash_history`) rode invisibly inside an operation the user authorized. XOXNO Lending has the same shape: `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply` accept opaque attacker-constructed `swap` route bytes; each `Swap` op resolves its `pool` address straight from the caller-controlled `assets` vector, so a hop can point at an attacker-deployed contract. That contract can call `token.transfer(victim, attacker, amount)` on any token the victim holds, and the Soroban host grafts that sub-invocation onto the victim's `require_auth` tree. A wallet that presents only the root invocation lets the victim sign away unrelated wallet funds while believing they authorized a routine collateral swap.

### Finding Description
`controller::swap_collateral` (and siblings) route through `swap_tokens`, which passes the raw `StrategySwap` bytes to `router.execute_strategy` with no venue/pool allowlist (contracts/controller/src/strategies/swap.rs:34-38). Inside the aggregator, `execute_op` builds `SwapHop { pool: ctx.assets.get_unchecked(op.idx_a), .. }` — the pool address is fully payload-controlled — and calls `venues::dispatch_hop` on it (contracts/swap-aggregator/src/execute/mod.rs:152-165). The dispatched "pool" is invoked as arbitrary contract code under the caller's authorization context.

The harness test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` proves the primitive end-to-end:

- `RogueHopPool::swap` reads a stored plan and executes `token::Client::transfer(&victim, &attacker, &amount)` on a token the protocol never listed (lines 56-71).
- In recording/simulation mode the rogue transfer is attached as a child of the caller's `swap_collateral` auth entry (`simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry`, lines 195-227): the recorded tree shows `alice → swap_collateral → transfer(alice, attacker, WALLET_BALANCE)`, Alice's wallet is emptied to the attacker, and the swap still pays a fair output so nothing looks wrong.
- In enforcing mode the transfer fails if the signed tree omits it, but succeeds the moment the victim signs the tree simulation produced (lines 230-268) — i.e., the only barrier is whether the signing UX surfaces a nested sub-invocation beneath an innocuous root. The `source_account_credentials_bind_the_rogue_transfer` test (lines 323-368) shows the same grafting works even under source-account credentials.

This is the DeFi analog of `attach=.bash_history`: a non-RFC parameter (`swap` route bytes naming an arbitrary pool) silently attaches a privileged side effect (transfer of an unrelated wallet token) inside an action the user consented to (a collateral swap). Both controller paths and direct `swap-aggregator::execute_strategy` calls expose it, since `run` also invokes payload-chosen `pool` addresses under `sender.require_auth` (execute/mod.rs:51-52, 152-165).

### Impact Explanation
Theft of user funds. The stolen asset need not be a listed market asset or part of the victim's position — the rogue hop transfers any token held in the victim's wallet (`WALLET_BALANCE` of an unlisted token in the test, lines 22, 224-225), up to whatever amounts the victim signs for. Because the swap itself settles correctly (fair output credited to the victim's position), neither the controller's `verify_router_output` check (swap.rs:75-83) nor min-out slippage protections detect the theft. The same primitive could target allowances-free assets only; SAC `transfer` requires only auth, so any token balance is in scope.

### Likelihood Explanation
Medium. Exploitation requires the victim to submit a transaction containing attacker-supplied route bytes — the normal flow already encourages this, since route bytes come from an off-chain quote service (per `skills/xoxno-lending-contracts/composing.md`: "Route bytes come from the quote service; do not construct `StrategyPayload` on-chain"), so users routinely sign payloads they did not construct and cannot decode. A compromised or malicious quoter/front-end, or a phishing flow, delivers the poisoned route. The theft succeeds if the wallet's signature UI presents the root `swap_collateral` invocation without prominently rendering nested `transfer` sub-invocations — the documented KMail-style gap between what the user sees and what the signature commits to. No privilege, leaked key, or protocol misconfiguration is required; the venue set is deliberately unallowlisted.

### Recommendation
Treat hop `pool` addresses as untrusted code that must not reach the signer's auth context:

- Restrict `dispatch_hop`/venues to governance-allowlisted pool contract addresses (or WASM hash allowlists) for each venue type, reverting on unlisted pools, in `contracts/swap-aggregator/src/execute/mod.rs` / `venues/mod.rs`.
- If arbitrary pools must remain reachable, document for integrators that routes must only be built by trusted quoters, and add a router-level guard that rejects any `require_auth` escalation — practically, Soroban cannot sandbox sub-auth from inside the callee, so the allowlist is the enforceable fix.
- At minimum, surface the risk in the SDK so wallets/quoters know the full signed tree (not the root) is the consent boundary.

### Proof of Concept
The repo's own harness demonstrates it:

1. Deploy `UnlistedPoolRouter` (test double for the aggregator) and set it via `set_swap_aggregator`; deploy `RogueHopPool` with plan `(victim=alice, wallet_token, to=attacker, amount=WALLET_BALANCE)` (test file lines 90-100, 56-60).
2. Craft `RoutedSwap { hop_pool: rogue_pool, min_out: FAIR_OUT_ETH, token_in: USDC, token_out: ETH }` XDR and submit `swap_collateral(alice, account_id, USDC, SWAP_IN, ETH, route)` (lines 111-157).
3. `simulateTransaction` records an auth tree whose `swap_collateral` root carries a child `transfer(alice, attacker, WALLET_BALANCE)` (asserted at lines 206-222). Alice's wallet balance of the unrelated token drops to 0 and the attacker receives it (lines 224-225), while her ETH supply balance is credited the fair output (line 226).
4. In enforcing mode, signing the recorded (poisoned) tree makes the same call succeed and executes the theft (lines 258-268).
