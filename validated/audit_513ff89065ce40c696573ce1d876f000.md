### Title
Missing contract-existence check before dispatching GET responses and GET timeouts allows relayers to drain relayer fees without ever delivering the message - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatchIncoming(PostRequest, address)` guards its low-level call to the destination module with an `extcodesize` check, returning early if the destination has no code [1](#0-0) . The sibling functions `dispatchIncoming(GetResponse, address)` and `dispatchTimeOut(...)` omit this check entirely and go straight to a low-level `.call()` on an address derived from attacker-influenced request data [2](#0-1) [3](#0-2) .

### Finding Description
In Solidity, a low-level `.call()` to an address with no deployed code (an EOA, an unused address, or a self-destructed contract) trivially returns `success = true` with empty return data — no code actually executes. This is exactly the "unclear check" bug class from the reference report: an external call is made and its `success` flag is trusted as proof that the intended handler logic ran, without first validating that the target is even a contract capable of running that logic.

`dispatchIncoming(PostRequest memory request, address relayer)` correctly defends against this by checking `extcodesize(destination) == 0` and returning early before ever attempting the call and before mutating fee-relevant state [1](#0-0) .

`dispatchIncoming(GetResponse memory response, address relayer)` does not perform this check. It writes replay-protection state, calls `_bytesToAddress(response.request.from).call(...)`, and — as long as `success == true` — proceeds to pay the relayer the escrowed fee and emit `GetRequestHandled`: [2](#0-1) 

`dispatchTimeOut(GetRequestTimeout memory timeout, FeeMetadata memory meta, bytes32 commitment)` has the identical pattern for GET timeouts, refunding the relayer fee on `success == true`: [3](#0-2) 

Because `response.request.from` (and `timeout.request.from`) is data carried in the original `GetRequest` that was dispatched on the source chain — and is only interpreted as an address via `_bytesToAddress`, with no code check on the destination — a relayer can construct or select a GET request/response/timeout whose `from` field decodes to an address with no code on this chain. The `.call()` then trivially succeeds (empty bytecode execution), `success` is `true`, and the fee-paying/refunding branch executes even though no actual `onGetResponse`/`onGetTimeout` handler logic ever ran.

### Impact Explanation
This breaks the intended invariant that relayer fees are only paid out when the destination module genuinely processed the incoming message. A relayer who can influence or pick GET requests to relay (or who colludes with/creates the source-side dispatch specifying a non-contract `from`) can:
- Collect the relayer fee for a GET response (`_requestCommitments[commitment].fee`) via `dispatchIncoming(GetResponse,...)` without any app ever receiving `onGetResponse`.
- Collect the relayer fee refund via `dispatchTimeOut(...)` without any app ever receiving `onGetTimeout`.

This is a direct fee-accounting/theft vulnerability reachable from a single relayed proof, consistent with the scope's "relayer fee and reward accounting" and "unbacked mint / forged message delivery" categories — funds move to the relayer while the corresponding message-delivery guarantee (and any state change an app expected) is silently skipped. It also creates state inconsistency: `_responseReceipts`/replay-protection is committed to as "handled" and the commitment is deleted, permanently preventing the real destination app from ever receiving the response, i.e. a permanent freezing/loss of the intended message for the app while the relayer is paid as if delivery succeeded.

### Likelihood Explanation
Reachable directly from `IHandlerV2`-authorized relayer calls into `EvmHost.dispatchIncoming`/`dispatchTimeOut` (both gated only by `restrict(_hostParams.handler)`, i.e. any account that can drive the standard relayer flow through the handler). No admin/governance/consensus compromise is required — only a normal relayed GET-response or GET-timeout proof whose associated `from` address happens to (or is engineered to) have no code on the destination chain. The `dispatchIncoming(PostRequest,...)` sibling function demonstrates the developers were aware this check is necessary; its absence on the GET-response/timeout paths appears to be an oversight rather than an intentional design choice.

### Recommendation
Add the same `extcodesize`/`code.length == 0` guard used in `dispatchIncoming(PostRequest,...)` to both `dispatchIncoming(GetResponse memory response, address relayer)` and `dispatchTimeOut(GetRequestTimeout memory timeout, FeeMetadata memory meta, bytes32 commitment)` before performing the low-level `.call()`, returning early (without paying/refunding any fee and without committing "handled" state) if the resolved destination address has no code — mirroring the pattern at `evm/src/core/EvmHost.sol` lines 794-803.

### Proof of Concept
1. On the source chain, dispatch (or select an already-dispatched) `GetRequest` whose `from` field is (or can be made to) decode to an address with no deployed code on the destination chain (e.g., a fresh EOA address, or an address that has not yet had a contract deployed).
2. Relay the corresponding `GetResponse` (or let it time out) through the standard `HandlerV2` → `EvmHost.dispatchIncoming(GetResponse,...)` / `dispatchTimeOut(...)` path.
3. Inside `EvmHost`, `_bytesToAddress(response.request.from).call(abi.encodeWithSelector(IApp.onGetResponse.selector, ...))` executes against the no-code address and returns `success = true` (empty call to non-contract), since no `extcodesize` check gates the call as it does for `dispatchIncoming(PostRequest,...)`.
4. The `if (!success)` branch is skipped; the relayer fee (`_requestCommitments[commitment].fee` or `meta.fee`) is transferred to the relayer via `IERC20(feeToken()).safeTransfer(...)`, and `GetRequestHandled`/`GetRequestTimeoutHandled` is emitted — even though no `IApp` implementation ever ran `onGetResponse`/`onGetTimeout`.
5. Repeat for any GET response/timeout the relayer can influence to harvest fees without genuine message delivery, while the "handled"/deleted commitment state permanently prevents the real recipient from later processing the message.

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }
```

    function dispatchTimeOut(
        GetRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onGetTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit GetRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }
```
