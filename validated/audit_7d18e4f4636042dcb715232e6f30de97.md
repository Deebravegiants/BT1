## Analog Vulnerability Found

### Title
Anyone can permissionlessly trigger `IntentGatewayV2.cancelOrder()` after order deadline with an attacker-chosen (including zero) relayer fee, marking the order filled while the compensating cross-chain message may never be relayed — ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
`IntentGatewayV2.cancelOrder()` routes to `_cancelFromDest()` when called on the destination chain. Once `order.deadline` has passed, the authorization check is skipped entirely, so **any address** — not just the order's user, a solver, or the protocol — may invoke it. `_cancelFromDest` immediately performs an irreversible local state change (`_filled[commitment] = user`) and then dispatches a Hyperbridge POST (`RefundEscrow`) back to the source chain, using a caller-supplied `options.relayerFee` and a hardcoded `timeout: 0` (never expires). [1](#0-0) 

### Finding Description
`cancelOrder` dispatches to `_cancelFromDest` for destination-chain cancellations: [1](#0-0) 

The deadline gate is the *only* authorization check, and it is bypassed entirely once `order.deadline < _blockNumber()`:
```solidity
function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
    if (order.deadline >= _blockNumber()) {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
    }
    _filled[commitment] = address(uint160(uint256(order.user)));
    _post(order, _body(RequestKind.RefundEscrow, commitment, order.inputs, order.user), options.relayerFee, msg.value);
}
```
After the deadline, the function is fully unprotected — any address can call it. `_post` builds a `DispatchPost` with `fee: relayerFee` (attacker-controlled) and `timeout: 0` (never times out): [2](#0-1) 

If the caller supplies `msg.value == 0` (the `nativeFee` argument passed into `_post`), execution falls through to `dispatchWithFeeToken(request)`, which only pulls fee tokens from the payer (`msg.sender`, i.e., the attacker) if `request.fee > 0`: [3](#0-2) 

An attacker can therefore call `cancelOrder` with `options.relayerFee = 0` and `msg.value = 0`, at zero cost, immediately after the order deadline passes — the same "unprotected function that dispatches a cross-chain message with attacker-controlled/insufficient relayer fee" pattern flagged in the source report (there, `xcall`'s `relayerFee`/`delegate` were set from `msg.value`/`msg.sender` by an unprotected caller). Here, `IDispatcher.dispatch`'s `notFrozen` modifier is the only host-side gate — it performs no minimum-fee enforcement: [4](#0-3) 

Since `timeout: 0` means the request never times out and can never be refunded/retried via the timeout path, a zero-fee `RefundEscrow` request has no economic incentive for relayers to deliver it and no protocol-enforced fallback other than someone voluntarily calling `fundRequest` to top up the fee later.

### Impact Explanation
Once `_cancelFromDest` executes, `_filled[commitment]` is permanently set, which blocks the order from ever being filled by a solver on the destination chain — this state change is irreversible and happens in the *same* transaction as the attacker's call, regardless of whether the compensating `RefundEscrow` message is ever delivered. Meanwhile the escrowed input tokens on the source chain remain locked in escrow, contingent on a message that an attacker can strand with a zero relayer fee and no timeout. This can desynchronize the source and destination chain state (order marked filled/cancelled on destination, but escrow never released on source) and freeze user funds until a good-faith third party discovers and pays to `fundRequest` the stuck commitment — mirroring the "contracts on two chains out of sync with possible loss of funds" impact described in the source report.

### Likelihood Explanation
Reachable with a single unprivileged transaction by any address once an order's deadline has elapsed — no special role, timing precision, or capital is required (fee and native value can both be zero). This makes the attack trivially and repeatedly executable against any expired cross-chain order that has not yet been cancelled by its legitimate owner or a relayer.

### Recommendation
- Enforce a minimum relayer fee (or require a non-zero fee) when dispatching `RefundEscrow` from `_cancelFromDest`, or restrict who may call `cancelOrder` after the deadline (e.g., require the caller to be the order's `user`, a registered relayer, or bond/self-pay a guaranteed minimum fee).
- Consider setting a non-zero `timeout` on the `RefundEscrow` dispatch so that, if underfunded and undelivered, the request can time out and trigger `onPostRequestTimeout` to reconcile/unlock state deterministically instead of remaining indefinitely stuck.
- Alternatively, decouple the irreversible `_filled[commitment]` write from the dispatch call, or add a recovery path that allows the order owner to re-trigger/re-fund the stalled cancellation message without depending on an arbitrary caller's fee choice.

### Proof of Concept
1. A cross-chain order is created with `order.deadline = D` on the destination chain.
2. Block height passes `D`.
3. Attacker (any address, no special permissions) calls `IntentGatewayV2.cancelOrder(order, options)` where `options.relayerFee = 0` and sends `msg.value = 0`.
4. `_cancelFromDest` executes: `_filled[commitment]` is set (order permanently blocked from being filled), and `_post` dispatches a `RefundEscrow` `DispatchPost` with `fee: 0`, `timeout: 0` via `dispatchWithFeeToken`, which skips the fee-token transfer since `request.fee == 0`.
5. The dispatched request sits in `EvmHost`'s `_requestCommitments` with `FeeMetadata.fee == 0` and no timeout — relayers have no incentive to deliver it, and it can never expire to trigger a refund path, leaving the user's escrowed tokens on the source chain stuck until someone manually calls `fundRequest` to add an incentive.
