### Title
Webhook HMAC does not bind the `shop` header, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable string from the raw body only, while the shop identity (`x-shopify-shop-domain` / `shopify-shop-domain` header) is read separately and never covered by the HMAC. `Registry.process` validates only the body signature and then forwards the unauthenticated `shop` header straight to the handler as the trusted identity of the request, breaking the intended binding: `hmac == HMAC(body)` should imply `shop == <shop the HMAC was actually issued for>`, but the gem only guarantees the former.

### Finding Description
`Utils::HmacValidator.validate` computes `computed_signature = compute_signature(verifiable_query.to_signable_string, secret)` and only compares this against the received `hmac`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw request body — the `shop` (and `topic`, `api_version`, `webhook_id`) headers are excluded from what is signed: [2](#0-1) 

`Registry.process` validates the HMAC of the body, then trusts `request.shop` (parsed straight from the unauthenticated header) as the tenant identity passed to the handler: [3](#0-2) 

Because the signature only certifies `(body, secret) -> hmac`, and never certifies which shop that body/hmac pair belongs to, any valid `(body, hmac)` pair obtained from Shopify for one shop remains valid when replayed with a different `x-shopify-shop-domain` value. `HmacValidator.validate` will still return `true`, and `Registry.process` will call the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` — where `shop` is attacker-controlled — while the app believes the webhook (and its body) was authenticated end-to-end for that shop.

### Impact Explanation
This is a cross-tenant identity binding break: the equality the gem should guarantee is `hmac valid ⇒ (shop, body) pair originated together from Shopify`, but it only guarantees `hmac valid ⇒ body originated from Shopify (for some shop)`. Any unprivileged actor who can obtain one legitimately-signed webhook delivery (e.g., by installing the target app on their own store and receiving a real webhook) can replay that exact body/HMAC to the app's webhook endpoint with an arbitrary victim `shop` header. Applications built on this gem's documented `Registry.process`/`WebhookMetadata` API (which is the gem's own trust boundary for webhook shop identity) will process data attributed to the wrong merchant — enabling cross-tenant data injection/corruption keyed off the spoofed `shop`, which qualifies as Critical (cross-tenant access).

### Likelihood Explanation
Likelihood is meaningful but not trivial: the attacker needs at least one valid `(body, hmac)` pair from the target app, which they can obtain by being a legitimate (even free/dev) installer of the app on their own shop and capturing a real webhook delivery. No secret key, leaked credential, or privileged access is required — only normal, unprivileged interaction with the app as any merchant.

### Recommendation
Include the shop domain (and ideally topic/webhook-id/api-version) in the signable string used for webhook HMAC validation, or otherwise cryptographically bind the shop to the signature (e.g., verify the shop against a shop known/expected by the app, not solely a header value), so that `to_signable_string` in `lib/shopify_api/webhooks/request.rb` cannot be replayed across shops.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, with a valid `x-shopify-hmac-sha256` for the JSON body `{"id":1,...}`.
2. Attacker replays the exact same raw body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers, `Utils::HmacValidator.validate` recomputes the HMAC over the (unchanged) body and it matches (since `to_signable_string` only depends on body): [4](#0-3) 
4. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` with `shop == "victim-shop.myshopify.com"` even though the body/HMAC pair was never issued for that shop: [3](#0-2)
