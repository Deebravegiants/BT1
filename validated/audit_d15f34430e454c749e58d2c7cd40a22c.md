### Title
Webhook `shop-domain` header is trusted for tenant routing but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook by validating an HMAC that is computed **only over the raw request body**, then hands off a `WebhookMetadata` struct whose `shop` field is read from an **unauthenticated HTTP header** to the app's handler. The binding "bytes verified == bytes the shop identity is derived from" does not hold: the HMAC proves the body's integrity/authenticity, but the `shop` value used for tenant routing is never part of the signed material.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` computes the HMAC over `to_signable_string` (i.e., the body) and compares it to the `hmac-sha256` header: [2](#0-1) 

`Request#shop` is read straight from the `shop-domain` header, which is not part of the signed string at all: [3](#0-2) 

`Registry.process` validates only the HMAC, and then unconditionally trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

`WebhookMetadata#shop` is the tenant identity the handler receives to act on: [5](#0-4) 

Because a single `api_secret_key` is shared across every shop that installs the app, and the signature only ever covers the body bytes, the identity binding that should hold is:

`bytes verified by HMAC == bytes that determine the shop the app acts on`

but in this gem it is actually:

`bytes verified by HMAC (raw_body) ⊄ shop identity (unauthenticated header)`.

Any unprivileged internet user who controls (or has previously observed, e.g. from their own installed shop's webhook deliveries) a `(body, hmac)` pair valid under the app's shared secret can resend that exact body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain`/`shopify-shop-domain` header value. `Registry.process` will still pass HMAC validation (since only the body is checked) and will invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen shop domain, along with the replayed body content.

### Impact Explanation
This breaks the tenant boundary that the whole webhook flow is supposed to establish: the app relies on `Registry.process`/`WebhookMetadata#shop` as the authenticated tenant identifier when routing webhook data to per-shop business logic (e.g., looking up that shop's session, updating that shop's local records). Because `shop` is never bound to the HMAC, an attacker can present authentic-looking webhook traffic under an arbitrary shop domain, letting them inject or attribute webhook-triggered actions/data to a shop they do not control — a cross-tenant data-integrity/confusion issue reachable purely from an unprivileged internet client with no access token, no `client_secret`, and no privileged account, satisfying the "cross-tenant access" impact bucket.

### Likelihood Explanation
Likelihood is moderate-to-high in typical multi-tenant app deployments:
- The webhook endpoint is a public, internet-reachable HTTP route by design (`docs/usage/webhooks.md`).
- An attacker only needs one valid `(body, hmac)` pair signed with the app's shared secret — trivially obtainable by installing the app on any shop they control and capturing a real webhook delivery, since the same `api_secret_key` signs traffic for all shops of that app.
- No credential, access token, or `client_secret` possession is required to mount the header-substitution replay; only observation of one legitimately delivered webhook for the attacker's own tenant.
- Exploitability is bounded by how much the host handler trusts `data.shop` without independent verification, but the gem's own `Registry.process`/`WebhookMetadata` API is what feeds this unauthenticated value forward as the trusted tenant key, so the flaw is in the gem's identity binding, not merely a documented-API misuse by the host.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`/`api_version`) header values into the signed material, or otherwise cryptographically bind the shop identity to the payload before exposing it via `WebhookMetadata`:
- Extend `VerifiableQuery#to_signable_string` for `Webhooks::Request` to include the `shop-domain`, `topic`, and `webhook_id` header values canonicalized together with the raw body, and validate against that combined string in `HmacValidator`.
- Alternatively, cross-check `request.shop` against a known/allow-listed set of installed shops (session store) before dispatching to `handler.handle`, rejecting webhook deliveries for shops the app does not recognize as having a valid installation, so an unauthenticated header value can never be used standalone as the tenant key.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker-shop.myshopify.com`; capture one legitimate webhook delivery (raw body `B`, header `x-shopify-hmac-sha256: H`) sent by Shopify for that shop — `H` is a valid HMAC of `B` under the app's shared `api_secret_key`.
2. Send a forged POST to the app's webhook endpoint with the same raw body `B` and header `x-shopify-hmac-sha256: H`, but set `x-shopify-shop-domain: victim-shop.myshopify.com` and any desired `x-shopify-topic`.
3. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) succeeds because it only checks `B` against `H`.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) proceeds and calls `handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed(B), ...))`, causing the app's business logic to act as if this webhook data legitimately originated from `victim-shop.myshopify.com`, even though nothing about that shop identity was authenticated.
