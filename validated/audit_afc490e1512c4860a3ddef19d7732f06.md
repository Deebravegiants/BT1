## Title
Unauthenticated relayer identity in `pallet-ismp`'s `handle_unsigned` allows forged fee/reward attribution to arbitrary accounts - (File: `modules/pallets/ismp/src/host.rs`)

### Summary
The Kavita CVE stems from a token-issuance path that accepts an unproven claim of identity (a username) as if it were cryptographically authenticated. `pallet-ismp`'s message-handling path has the same class of flaw: the `signer`/relayer-attribution field carried in every `RequestMessage`/`ResponseMessage` submitted through the permissionless, unsigned `handle_unsigned` extrinsic is stored as the authoritative "relayer" identity without ever being cryptographically verified. An unprivileged caller can name **any account** as the delivering relayer, and that unverified identity subsequently drives relayer fee/reward accounting in `pallet-ismp-relayer`.

### Finding Description
`handle_unsigned` is deliberately permissionless and unsigned so anyone can submit ISMP messages for free given a valid proof: [1](#0-0) 

Each `Message::Request`/`Message::Response` carries a `signer: Vec<u8>` field that is documented as "Ideally should be their account identifier" — i.e. it is caller-supplied, unauthenticated data: [2](#0-1) 

When the request/response is routed, the host stores this raw `signer` value as the receipt's relayer via `extract_signer`: [3](#0-2) 

`extract_signer` only decodes the bytes; when the payload decodes as a `Signature`, it calls `.signer()`, **never `.verify()`**: [4](#0-3) 

`Signature::signer()` simply returns the embedded `address`/`public_key` field verbatim — it performs no ECDSA/Sr25519/Ed25519 check that the enclosed "signature" bytes were ever produced by that key: [5](#0-4) 

Because SCALE decoding only validates structure (enum discriminant + length-prefixed byte vectors), an attacker can submit `Signature::Evm { address: <any 20+ bytes>, signature: <garbage> }.encode()` (or any bytes ≤32) as `msg.signer`. This is accepted, and `RequestReceipts`/`ResponseReceipts` on the destination substrate chain (which can be Hyperbridge itself) are populated with the attacker-chosen identity — with zero proof that identity ever authorized or performed the delivery.

This corrupted receipt is exactly the value `pallet-ismp-relayer::accumulate_fees` later decodes to attribute delivery credit and pay out fees: [6](#0-5) [7](#0-6) 

Contrast this with `pallet-messaging-incentives`, which handles the identical `Message.signer` field correctly by actually verifying the embedded signature before trusting it: [8](#0-7) 

The missing verification step in `pallet-ismp::host.rs`/`crypto_utils::Signature::signer()` is the exact analog of Kavita's flaw: an unauthenticated field that is supposed to represent a cryptographically-proven identity is instead trusted at face value, letting an unprivileged, unauthenticated caller impersonate any account for attribution purposes.

### Impact Explanation
`RequestReceipts`/`ResponseReceipts` "relayer" identity is the sole input `pallet-ismp-relayer::accumulate` uses (via `decode_receipt_relayer`) to decide which account's `Fees` balance is credited for a delivery on substrate destinations. Since this identity is never cryptographically bound to whoever actually paid for/submitted the delivering transaction, the fee/reward accounting for relayers on substrate destinations is not trustworthy: an unprivileged submitter of `handle_unsigned` can attribute delivery credit to an arbitrary account of their choosing rather than to a party that ever proved control of it. This directly undermines relayer fee and reward accounting, one of the flagged reachable-impact categories, and is reachable from a single unsigned, permissionless extrinsic.

### Likelihood Explanation
`handle_unsigned` is explicitly designed to be callable by anyone with a valid proof, so the attack requires no privileges beyond normal relaying capability, and the malformed `signer` bytes are trivial to construct (no cryptography needed to decode successfully). Any relayer or observer of public request/response data can trigger this at will.

### Recommendation
Bind the `signer` field to a real proof of key ownership before trusting it for attribution: require `pallet-ismp::host.rs::extract_signer` to call `Signature::verify` (over a canonical message tied to the specific request/response commitment, mirroring `pallet-messaging-incentives::relayer_for`'s `verify_and_get_sr25519_pubkey` pattern) rather than the unauthenticated `Signature::signer()` accessor, and reject the message if verification fails.

### Proof of Concept
1. Observe a legitimate, unclaimed cross-chain `PostRequest`/`GetRequest` targeting a substrate destination chain (or Hyperbridge itself) and obtain its valid delivery proof (public information via RPC/indexer).
2. Submit `pallet_ismp::handle_unsigned` with that valid proof but set `signer = Signature::Evm { address: <arbitrary/victim address>, signature: vec![0u8; 65] }.encode()`.
3. `extract_signer` decodes the bogus `Signature` successfully and returns `address` unchanged (`Signature::signer()` never validates `signature` against `address`), storing it in `RequestReceipts[commitment]`.
4. When `pallet-ismp-relayer::accumulate_fees` later proves this receipt via state proof, `decode_receipt_relayer` returns the same attacker-chosen `address`, and the delivery fee is credited to that account in `Fees::<T>` — an identity that never signed anything and may not even correspond to a real keypair.

fn extract_signer(signer: &[u8]) -> Result<Vec<u8>, Error> {
	if signer.len() > 32 {
		Signature::decode(&mut signer.as_ref())
			.map(|sig| sig.signer())
			.map_err(|_| Error::SignatureDecodingFailed)
	} else {
		Ok(signer.to_vec())
	}
}

	/// Recover the relayer's account from the sr25519 signature on a
	/// `Message`'s `signer` field. Returns `None` if the message has
	/// no signer (e.g. consensus messages) or the signature is bad.
	fn relayer_for(message: &Message) -> Option<T::AccountId> {
		let (signer, signed) = match message {
			Message::Request(msg) =>
				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
			Message::Response(msg) =>
				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
			_ => return None,
		};
		Signature::decode(&mut &signer[..])
			.ok()?
			.verify_and_get_sr25519_pubkey(&signed, None)
			.ok()
			.map(T::AccountId::from)
	}
