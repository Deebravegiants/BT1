Confirms the interface: `HmacValidator.validate` only checks bytes returned by `to_signable_string`, and for webhooks that's solely the raw HTTP body.### Title
Webhook shop identity is taken from an unauthenticated header while the HMAC only signs the request body, enabling cross-tenant webhook replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but `Utils::HmacValidator` only verifies the raw request body against the app's shared `api_secret_key`. Because the header is never part of the signed bytes, any party who can obtain one valid `(body, hmac)` pair for the shared app secret — trivially available to any merchant who installs the app on their own store, since Shopify's HMAC secret is shared across all shops of an app — can replay that same body/HMAC pair to the app's webhook endpoint with a forged `shop-domain` header naming a different, victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Request#shop` is read straight from the (attacker-suppliable) header without any cryptographic binding [2](#0-1) . `HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it against the received HMAC using the app's `api_secret_key` [3](#0-2) . The `VerifiableQuery` interface only requires `hmac` and `to_signable_string`, so nothing else — topic, shop, webhook-id, api-version — is part of the authenticated bytes [4](#0-3) . `Registry.process` accepts any request that passes this body-only HMAC check and then dispatches to the app's handler using the unauthenticated `shop` value from the header [5](#0-4) .

This is exactly the "bytes verified versus bytes parsed" identity-binding break described in the analog scope: the equality that should hold is `shop_bound_by_hmac == shop_used_by_handler`, but instead `shop_used_by_handler` comes from a header that is outside the HMAC's coverage.

### Impact Explanation
Because Shopify webhooks for a given app all share the same `api_secret_key` across every installing shop, an attacker who installs the target app on their own (attacker-controlled) shop can trigger any webhook topic on their own store, capture the genuine `(raw_body, hmac)` pair Shopify sends them, and then POST that exact body/HMAC to the app's webhook endpoint again while substituting the `shop-domain` header of a victim shop. `HmacValidator.validate` will report the request as valid (it only checks the body), and `Registry.process` will hand the attacker-chosen body to the app's webhook handler tagged as coming from the victim shop. Depending on the handler's logic (e.g., `customers/data_request`, `shop/redact`, order/customer data processing, GDPR mandatory webhooks, or any app-specific handler that trusts `shop` to select or mutate per-tenant data), this can be leveraged for cross-tenant data corruption, spoofed events, or triggering of privileged per-tenant automation for a shop the attacker does not control — a direct cross-tenant boundary violation.

### Likelihood Explanation
Likelihood is not trivial to fully confirm without host-application review: exploitation requires (1) the app's webhook handler to actually rely on `WebhookMetadata#shop` to select tenant-specific behavior or storage (this gem cannot guarantee that, and is outside `lib/shopify_api/webhooks/registry.rb`'s control), and (2) the app secret to be shared across installs as is standard for Shopify apps. Both conditions are the normal, expected configuration for a Shopify app, and no special privilege, leaked credential, or TLS interception is required — only becoming a legitimate merchant installer of the target app, which is normal unprivileged internet-user access. This keeps likelihood realistic and reachable purely through this gem's own webhook verification code path.

### Recommendation
Bind the tenant identity into the authenticated bytes rather than trusting an unauthenticated header:
- Extend `VerifiableQuery`/`to_signable_string` for webhook requests to incorporate the `shop` (and ideally `topic`/`webhook_id`) into the signed material, or independently verify shop identity against a known/registered shop record before dispatching.
- Where Shopify's HMAC scheme genuinely covers only the body (this is Shopify's documented behavior, not something the gem controls), the gem should at minimum document/require that host applications cross-check `webhook_id` idempotency and confirm `shop` against a session/store already known to the app before trusting `WebhookMetadata#shop`, and ideally provide a stricter validation helper that rejects reuse of `(webhook_id, shop)` pairs.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` using their own store (no special privilege required).
2. Attacker triggers a webhook topic they control (e.g. `orders/create`) on their own shop; Shopify delivers `raw_body` plus `x-shopify-hmac-sha256` computed with the app's shared `api_secret_key`, and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker replays the exact same `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but replaces the header with `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` recomputes the HMAC solely over `raw_body` [6](#0-5)  and it matches, so `Registry.process` invokes the registered handler with `shop: "victim-shop.myshopify.com"` [5](#0-4) , even though the payload never actually originated from or was authorized for that shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
