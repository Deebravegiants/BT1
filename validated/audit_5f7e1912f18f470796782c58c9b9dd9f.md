### Title
Consensus client can irrecoverably expire while `EvmHost` is frozen/paused - (File: `evm/src/core/HandlerV2.sol`)

### Summary
`HandlerV2.handleConsensus` rejects consensus updates whenever the host is frozen (`FrozenStatus.Incoming` or `FrozenStatus.All`), yet the unrecoverable `ConsensusClientExpired()` check is computed purely from wall-clock elapsed time since the last successful consensus update (`consensusUpdateTime()`), with no adjustment for time the host spent frozen. Just like the referenced `TokenSale.hasSaleEnded()` bug — where the sale's end-state can flip from `false` to `true` purely because of elapsed pause time, without the pause period being excluded — a `EvmHost` that stays frozen for longer than `unStakingPeriod()` becomes permanently unable to accept any further consensus proofs once unfrozen, since the expiry clock kept running during the freeze.

### Finding Description
`setFrozenState` lets the admin (or handler) put the host into `FrozenStatus.Incoming`/`All`, which blocks `handleConsensus` via the `notFrozen(host)` modifier: [1](#0-0) 

While frozen, no consensus proof can be processed and `_consensusUpdateTimestamp` is not advanced — it is only updated inside `storeConsensusState`, which is only reachable through a successful `handleConsensus` call: [2](#0-1) 

Meanwhile, `handleConsensus`'s liveness check compares `block.timestamp` (which keeps advancing during the freeze) against the stale `consensusUpdateTime()`: [3](#0-2) 

The comment on the guarding error makes clear this state is final: [4](#0-3) 

This is not a hypothetical operational mode — the shipped admin-relayer intentionally keeps the host frozen (`FrozenStatus.All`) between updates and only briefly unfreezes it around each `handleConsensus` call: [5](#0-4) 

`setFrozenState` itself performs no time bookkeeping and can be triggered by the admin for benign reasons (incident response, planned maintenance, relayer outage) without malicious intent: [6](#0-5) 

If the host stays frozen for a duration greater than or equal to `unStakingPeriod()` (minimum 24 hours per `InvalidUnstakingPeriod`), the very next `handleConsensus` call after unfreezing will observe `delay >= unStakingPeriod` and revert with `ConsensusClientExpired()` — permanently, since `consensusUpdateTime()` can never be advanced without first passing this same check.

### Impact Explanation
Once tripped, `handleConsensus` can never succeed again for that consensus client. Since state-machine commitments (used by both `handlePostRequests`/`handleGetResponses` and `handlePostRequestTimeouts`/`handleGetRequestTimeouts`) are only stored via consensus updates, the host becomes permanently unable to accept any new proofs from the counterparty chain — no further requests, responses, or timeouts can be relayed. This constitutes a permanent route failure that freezes all funds locked in pending cross-chain messages and future messages routed through that host, matching the "route unable to deliver messages" / "permanent freezing of funds" impact bar.

### Likelihood Explanation
The bug requires no malicious actor: it triggers purely from the host remaining frozen (via `setFrozenState`, an intended and normal admin/handler operation, actively used by the in-repo admin-relayer design) for longer than the configured `unStakingPeriod`. Any outage, delay, or deliberate maintenance pause on the relayer/admin side that exceeds this window (which can be as short as 24 hours) is sufficient to hit the unrecoverable state — a realistic and plausible operational scenario rather than an edge case.

### Recommendation
Track cumulative frozen duration (or the timestamp at which the host most recently transitioned out of a frozen state) and exclude it from the `ConsensusClientExpired` delay computation, or freeze/pause the `_consensusUpdateTimestamp` clock itself while `_frozen != FrozenStatus.None`, so that elapsed time while incoming consensus updates were administratively blocked cannot count toward `unStakingPeriod` expiry.

### Proof of Concept
1. Deploy `EvmHost` with `unStakingPeriod = 24 hours` (minimum allowed).
2. Successfully call `handleConsensus` once, setting `consensusUpdateTime() = T0`.
3. Admin calls `setFrozenState(FrozenStatus.All)` (a normal operational action, e.g. as used by the admin-relayer between updates), see `evm/src/core/EvmHost.sol:746-753`.
4. Wait/allow more than 24 hours to pass while the host remains frozen (relayer outage, delayed unfreeze transaction, etc.) — during this window `handleConsensus` cannot be called because of `notFrozen(host)` in `evm/src/core/HandlerV2.sol:108-112`.
5. Admin calls `setFrozenState(FrozenStatus.None)` and submits a fresh, valid consensus proof to `handleConsensus`.
6. `delay = block.timestamp - consensusUpdateTime() >= unStakingPeriod` is now true purely due to the freeze duration, so the call reverts with `ConsensusClientExpired()` (`evm/src/core/HandlerV2.sol:144-146`) — permanently, since this is the only path that could have advanced `consensusUpdateTime()`.
