Unsound `String::from_utf8_unchecked` on attacker-controlled cross-chain POST body causes undefined behavior in `pallet-ismp-demo` (`IsmpModuleCallback::on_accept`) - (File: modules/pallets/demo/src/lib.rs)

### Summary
`pallet-ismp-demo`'s ISMP module callback converts an incoming POST request's raw `body` bytes directly into a Rust `String` using the unsafe, unchecked UTF‑8 constructor whenever the request's source chain is an EVM state machine. Any unprivileged sender on a connected EVM chain (or any relayer who delivers a proof for such a request) fully controls `request.body` and can supply arbitrary non‑UTF‑8 bytes, producing a `String` that violates Rust's core UTF‑8 invariant — the direct analog of the reported Mattermost Mobile bug where an attacker-controlled field is force-cast to `String` and crashes the app.

### Finding Description
`IsmpModuleCallback::on_accept` handles the `Request::Post` dispatched to this module (`from`/`to` = `PALLET_ID` `b"ismp-ast"`) once `pallet-ismp`'s `handle_unsigned` extrinsic validates the state/membership proof and routes the request via `IsmpRouter::module_for_id`: [1](#0-0) 

```rust
impl<T: Config> IsmpModule for IsmpModuleCallback<T> {
	fn on_accept(&self, request: PostRequest) -> Result<Weight, anyhow::Error> {
		let source_chain = request.source;

		match source_chain {
			StateMachine::Evm(_) => Pallet::<T>::deposit_event(Event::Request {
				source: source_chain,
				data: unsafe { String::from_utf8_unchecked(request.body) },
			}),
```

`request.body` is arbitrary bytes chosen by whoever dispatches the original `DispatchPost` on the EVM source chain (e.g. any EVM contract calling `IDispatcher.dispatch`), and it reaches this module unmodified after `pallet-ismp::handlers::request::handle` validates only membership/timeout/duplication — not the byte content of `body`. `String::from_utf8_unchecked` is documented as safe only when the caller guarantees valid UTF-8; here that guarantee is not checked at all, so any non‑UTF‑8 payload creates a `String` whose internal invariant is broken. This is stored into `Event::Request { data: String, .. }`, a SCALE‑encoded, `TypeInfo`-derived enum variant that is then encoded, deposited into on‑chain events, and later re‑serialized/read by RPC, indexers, or any downstream code that treats the `String` as valid UTF‑8 (e.g., `.chars()`, slicing, `to_string()`, JSON serialization). Because the type invariant is violated at the language level, this is undefined behavior, not merely an error that can be caught — it can manifest as a panic, memory-unsafety-adjacent misbehavior, or crashes/faults in any consumer (RPC nodes, indexers, block explorers) that decodes/renders this event, exactly mirroring the mobile client crash pattern in CVE‑2025‑20630 where a hostile payload field is force-cast to an assumed type.

Compare this to the codebase's own hardened pattern for exactly this class of bug (`as_utf8_string` deserializer), which was fixed specifically because an unchecked byte→string operation on untrusted input previously crashed a production RPC worker: [2](#0-1) 

The demo pallet's `on_accept` was not brought in line with that fix and still performs the unchecked conversion.

### Impact Explanation
`pallet-ismp-demo` (`IsmpDemo`) is compiled into and wired into production/testnet parachain runtimes (`gargantua`, `nexus`) as pallet index 52, with its `IsmpModuleCallback` registered against the reserved module id `PALLET_ID = b"ismp-ast"`: [3](#0-2) [4](#0-3) 

Because `handle_unsigned` is a permissionless, unsigned, fee-free extrinsic that anyone can submit with a valid proof for a message whose `to` field targets `ismp-ast`, an unprivileged EVM-side sender (application, relayer, or attacker) can trigger this code path at will. The result is a soundness violation (broken `String` invariant) in a live parachain runtime's event log — this can crash or corrupt downstream infrastructure (RPC nodes serving `state_getStorage`/event queries, indexers such as the SubQuery-based indexer in this repo, and block explorers) that consumes the emitted `Event::Request.data` field, which matches the "Medium" severity, availability-only crash class (`C:N/I:N/A:H`) of the referenced CVE.

### Likelihood Explanation
High for triggering the unsafe operation: dispatching a POST with a non-UTF‑8 body from any EVM chain connected to the parachain requires only a normal `IDispatcher.dispatch` call (no special privilege) plus a relayer submitting the resulting membership proof via `handle_unsigned` — both are standard, expected relayer/dispatcher operations already exercised throughout the codebase. The severity of the resulting undefined behavior/crash depends on which downstream consumer decodes the corrupted `String`, but the root-cause unsafe cast itself is trivially and reliably reachable.

### Recommendation
Replace the unchecked conversion with a fallible one and reject/sanitize invalid UTF‑8 instead of asserting an invariant that untrusted data cannot guarantee, mirroring the existing `as_utf8_string`/`StateMachine::Display` fallback pattern already used elsewhere in this codebase:
```rust
StateMachine::Evm(_) => {
    let data = String::from_utf8(request.body)
        .map_err(|_| IsmpError::Custom("invalid utf-8 in request body".to_string()))?;
    Pallet::<T>::deposit_event(Event::Request { source: source_chain, data });
},
```
Alternatively, change the `Event::Request::data` field to `Vec<u8>` and perform UTF‑8 interpretation only at the display/serialization boundary with `String::from_utf8_lossy` or an explicit fallible decode, never via `from_utf8_unchecked` on attacker-controlled bytes.

### Proof of Concept
1. On a connected EVM chain, any contract calls `IDispatcher.dispatch(DispatchPost{ dest: <parachain>, to: b"ismp-ast", body: <bytes containing e.g. 0xFF 0xFE>, ... })`.
2. A relayer (or the attacker themselves, since `handle_unsigned` is permissionless) submits `pallet_ismp::handle_unsigned` with a valid membership proof for this request once the source chain's state is finalized/verified.
3. `pallet-ismp` validates the proof and routes the request to `IsmpModuleCallback::<T>::on_accept` via the module id `b"ismp-ast"`.
4. `on_accept` executes `unsafe { String::from_utf8_unchecked(request.body) }` on the attacker-supplied non‑UTF‑8 bytes, producing a `String` with a broken invariant, which is deposited as `Event::Request { data, .. }` on-chain.
5. Any RPC endpoint, indexer, or explorer that reads and decodes this event's `data` field as a UTF‑8 `String` (e.g., for JSON serialization or display) invokes undefined behavior / can panic, causing a denial of service in that consuming service — analogous to the reported mobile crash from an uncastable field.
