### Title
Emporium `signerAddress == 0` min-proof path lets an attacker drive arbitrary unauthenticated external calls from the Emporium contract while `erc20TokenAddresses.length == 0` disables all balance accounting - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol, contracts/CircomDataBuilder.sol, circuits/MainEVMCircuitMin.circom)

### Summary
When `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `formInputForCircom` routes to `formInputEmporiumMin`, whose circuit (`MainEVMCircuitMin`) only constrains `message == Poseidon(messageSeed)` and leaves `calldataHash`/`outTimeStamp` completely unconstrained. Combined with `EmporiumUpgradeable.verifyWallet` skipping all signature checks when `EmporiumStack.signerAddress == address(0)`, an unprivileged attacker can force `EmporiumUpgradeable.runAction` to execute an arbitrary `op.endpoint.call{value: op.value}(op.callData)` from Emporium's own identity while the balance-accounting loop iterates zero times, so any outflow is completely unaccounted for.

### Finding Description
The invariant the question tests is: *assets Emporium can move in a tx == assets accounted for in `balancesBefore`/`balancesAfter`*. This is broken.

- `CircomDataBuilder.formInputForCircom` selects `formInputEmporiumMin` whenever `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0`: [1](#0-0) 
- `formInputEmporiumMin` produces only `[emporiumMessage, timeStamp, calldataHash]` as public signals: [2](#0-1) 
- The corresponding circuit `MainEVMCircuitMin` only constrains `message <== Poseidon(messageSeed)`; `outTimeStamp` and `calldataHash` are declared as circuit signals but never appear in any constraint: [3](#0-2) . Because these two public signals are never used in the R1CS, their corresponding IC contribution in the Groth16 verification equation is effectively neutral, meaning a single proof generated against arbitrary `calldataHash`/`timeStamp` verifies for those same values trivially and provides no cryptographic binding between the proof and the actual `externalActionMetadata` (`EmporiumStack`) content — the only thing the on-chain code separately checks is that `calldataHash` matches `keccak256` of the caller-supplied `CircomData` fields (`getHashedCalldata`), which is a plain hash check the attacker (who controls every field) can always satisfy: [4](#0-3) .
- `EmporiumUpgradeable.runAction` decodes the attacker-supplied `EmporiumStack` and calls `verifyWallet`, which **returns immediately with no signature check at all** when `stack.signerAddress == address(0)` (only marking the message as used): [5](#0-4) 
- For each op, when `invokeWallet` is false or `signerAddress == 0` (CASE 2), Emporium performs an arbitrary `op.endpoint.call{value: op.value}(op.callData)` with only a check against the `callHinkalWallet`/`doSendToRelay` selectors: [6](#0-5) 
- Because `circomData.erc20TokenAddresses.length == 0`, `balancesBefore`/`balancesAfter`/the accounting loop in `runAction`, and the slippage/balance loop in `Hinkal.transact`, all iterate zero times, so no balance change from the arbitrary call is checked or reverted: [7](#0-6) [8](#0-7) 

The only remaining guard is `onlyAllowedRecipient`, which checks `msg.sender == Hinkal` (the allowlisted caller for `runAction`), not any per-user authorization of the ops themselves: [9](#0-8) . That guard restricts who can invoke `runAction`, not what the `EmporiumStack.ops` are allowed to do.

Net effect: any unprivileged caller of `Hinkal.transact` can pick a fresh `messageSeed`/`emporiumMessage` nonce, supply `erc20TokenAddresses = []`, generate a trivially satisfiable min-circuit proof, and set `EmporiumStack.signerAddress = address(0)` with arbitrary `ops`, causing Emporium to execute those calls unauthenticated, with zero balance/slippage accounting to catch any resulting fund movement (e.g., `token.transferFrom(victim, attacker, amount)` if any user has a standing allowance for the Emporium contract, or draining any token/ETH balance Emporium itself happens to hold).

### Impact Explanation
Direct theft of any funds Emporium can move via an unauthenticated call: tokens for which a victim has granted a standing `approve` to the Emporium contract address, or any ERC20/ETH balance transiently held by Emporium, can be moved to the attacker with no on-chain accounting to detect or block the transfer. This is repeatable per fresh, unused `emporiumMessage` nonce and costs the attacker only gas plus trivial local proof generation (no real cryptographic work, since `MainEVMCircuitMin` is nearly unconstrained). This matches the Critical category: direct theft of shielded or in-flight user funds / executing calls or moving assets never authorized by their owner.

### Likelihood Explanation
Preconditions: (1) the Emporium min-path must be reachable by any caller of `Hinkal.transact` (confirmed — it is a public, permissionless entrypoint), (2) `HINKAL_EMPORIUM_ACTION_ID` must be registered to point at the deployed `EmporiumUpgradeable` (`registerExternalAction`, standard deployment configuration), (3) a target with either a standing token approval to Emporium or a nonzero balance held by Emporium. Preconditions (1) and (2) are baseline deployment facts, not privileged actions the attacker needs; precondition (3) depends on real-world usage patterns (whether any user or flow ever leaves an approval or balance on the Emporium contract), which is plausible given `EmporiumStack`'s stateless call design but not independently confirmed by a specific approval-granting code path found in this codebase.

### Recommendation
1. In `MainEVMCircuitMin`, actually constrain `calldataHash` and `outTimeStamp` to the witnessed values (or otherwise cryptographically bind the proof to the specific `externalActionMetadata`/ops being executed) so the min-proof cannot be considered valid for arbitrary/unrelated call content.
2. Require a real authorization check in `verifyWallet` even when `signerAddress == address(0)` — e.g., disallow the "no signature" branch entirely for `EmporiumStack`s containing stateless calls (CASE 2) to arbitrary `op.endpoint`, or require `signerAddress != address(0)` whenever ops target token contracts / external calls that could move funds.
3. Do not allow `erc20TokenAddresses.length == 0` to bypass balance accounting when `EmporiumStack.ops` are non-empty and contain calls to arbitrary endpoints; require that every token potentially touched by an op be included in `erc20TokenAddresses` so `balancesBefore`/`balancesAfter` accounting always applies.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable` (proxy), register `HINKAL_EMPORIUM_ACTION_ID -> Emporium`, allowlist Hinkal as Emporium's recipient.
2. Deploy a mock ERC20; have a "victim" account `approve(EmporiumAddress, 1000e18)` (simulating a standing approval), and mint/hold `1000e18` tokens for the victim.
3. As attacker (unprivileged EOA), construct `CircomData` with `erc20TokenAddresses = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionData.externalActionMetadata = abi.encode(EmporiumStack({signerAddress: address(0), ops: [EmporiumOperation({endpoint: token, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transferFrom, (victim, attacker, 1000e18))})], ...}))`.
4. Choose a fresh `messageSeed`, compute `emporiumMessage = Poseidon(messageSeed)`, compute `calldataHash = getHashedCalldata(circomData)` locally, generate a valid Groth16 proof for `MainEVMCircuitMin` with those public inputs (trivially constructible since only `message` is constrained).
5. Call `Hinkal.transact(a, b, c, dimensions, circomData)`.
6. Assert: `token.balanceOf(victim)` decreased by `1000e18` and `token.balanceOf(attacker)` increased by `1000e18`, while `newBalances == oldBalances` for the (empty) `erc20TokenAddresses` array in `Hinkal.transact`, i.e., no slippage/balance check ever fired to prevent or detect the theft — demonstrating the broken equality "assets moved == assets accounted for."
