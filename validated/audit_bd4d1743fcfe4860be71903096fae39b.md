### Title
Confused-deputy token theft via forged inner `CircomData` in Emporium op calls to `DepositOnChainUtxosExternalAction.runAction` - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction` executes attacker-supplied `EmporiumOperation.callData` against attacker-supplied `op.endpoint` via a raw low-level `call`, with no constraint that any `CircomData` struct encoded inside that calldata matches the outer, proof-verified `circomData` that `Hinkal.transact` checked. An attacker can encode a call to `DepositOnChainUtxosExternalAction.runAction` with a forged inner `CircomData` (`originalSender = victim`) to pull the victim's tokens (already approved to that action from prior legitimate deposits) into the Emporium contract's balance, which is then legitimately converted into the attacker's own UTXO by the outer, honestly-proved transaction.

### Finding Description
The broken equality: the `circomData.originalSender` / `circomData.stealthAddressStructure` values that `DepositOnChainUtxosExternalAction.runAction` acts upon when authorizing `transferERC20TokenFrom` must equal the values bound into the *same* proof verified by `getSignedMessageHash`/`performHinkalChecks` in the current `Hinkal.transact` call. That equality is never enforced when `DepositOnChainUtxosExternalAction` is reached indirectly through an Emporium op.

Path:
1. Attacker calls `Hinkal.transact` with their own valid proof over an *outer* `circomData` (their own funds, `originalSender == msg.sender` per `performHinkalChecks`, [1](#0-0) ), whose `externalActionData.externalActionId` points to the deployed `EmporiumUpgradeable`.
2. `Hinkal._externalTransact` forwards this outer `circomData` to `EmporiumUpgradeable.runAction` [2](#0-1) .
3. `EmporiumUpgradeable.runAction` decodes `circomData.externalActionData.externalActionMetadata` into an `EmporiumStack` fully controlled by the attacker, including `EmporiumOperation[] ops` with attacker-chosen `endpoint` and `callData` [3](#0-2) .
4. `verifyWallet` is trivially bypassed by setting `stack.signerAddress = address(0)`, which skips the EIP-712 signature check entirely [4](#0-3) .
5. In the "Stateless Interaction" branch, the op is executed as `op.endpoint.call{value: op.value}(op.callData)` [5](#0-4) . The only restriction is on the selector for `callHinkalWallet`/`doSendToRelay`; any other selector, including `DepositOnChainUtxosExternalAction.runAction`, is allowed.
6. The attacker crafts `op.callData = abi.encodeCall(runAction, (forgedCircomData, [0,...]))` where `forgedCircomData.originalSender = victim` and `forgedCircomData.stealthAddressStructure` is the attacker's own H0/H1. This `forgedCircomData` is an independent calldata blob decoded fresh via `abi.decode`/direct call — it is *not* the same object as the outer, proof-verified `circomData`, and it was never passed through `performHinkalChecks`, `verifyProof`, or `getSignedMessageHash`.
7. Inside `DepositOnChainUtxosExternalAction.runAction`, the only gate is `onlyAllowedRecipient` (checks `msg.sender`, i.e. `EmporiumUpgradeable`, is in its `isAllowedRecipient` mapping) [6](#0-5)  — there is no check that `forgedCircomData` was ever proof-verified. It then calls `transferERC20TokenFrom(tokenAddress, userAddress, msg.sender, tokenTotal)` where `userAddress = forgedCircomData.originalSender = victim` and `msg.sender = EmporiumUpgradeable` [7](#0-6) . If the victim previously approved `DepositOnChainUtxosExternalAction` (a normal precondition for using its legitimate on-chain-UTXO deposit feature), the ERC20 `transferFrom(victim, EmporiumUpgradeable, tokenTotal)` succeeds, pulling victim funds into Emporium's balance.
8. Crucially, the `utxoSet` *returned* by this nested `runAction` call is discarded — `EmporiumUpgradeable.runAction`'s op loop only inspects `(success, err)` from the low-level call and never propagates return data [8](#0-7) . Instead, `EmporiumUpgradeable.runAction` measures its own `balancesBefore`/`balancesAfter` [9](#0-8) , and the stolen-token balance increase is captured and converted into a legitimate UTXO via `handleOut`, credited under the outer, honestly-proved `circomData.stealthAddressStructure` (the attacker's own). That UTXO is what `Hinkal.transact`'s `insertCommitments`/`onChainCommitments` loop actually commits [10](#0-9) .

So the forged inner `stealthAddressStructure`/`originalSender` never needs to be proof-consistent — it only needs to pass `DepositOnChainUtxosExternalAction`'s local checks (`userAddress != 0`, `H0x` implicitly nonzero from whatever the attacker sets) to authorize the `transferFrom`. The actual laundering into a spendable shielded balance happens entirely through the legitimately-proved outer transaction.

### Impact Explanation
Direct theft of a victim's ERC20 allowance previously granted to `DepositOnChainUtxosExternalAction`, converted into shielded value under the attacker's control without the victim's consent, matching the "Critical - direct theft of shielded or in-flight user funds" category. This is repeatable per victim/token/allowance up to the full approved amount, and repeatable across any external action that (a) trusts `circomData.originalSender` for `transferFrom`-style pulls and (b) lists `EmporiumUpgradeable` in its `isAllowedRecipient` set.

### Likelihood Explanation
This requires two preconditions not fully confirmed from the indexed code:
1. `DepositOnChainUtxosExternalAction` (or any other action with a similar trust pattern) must have `EmporiumUpgradeable`'s address registered via `setAllowedRecipients`/constructor as an allowed caller — this is an owner-controlled configuration decision, not something I could verify is actually deployed this way from the available files (no deployment/registration scripts were found in the index).
2. The victim must have an outstanding ERC20 allowance to `DepositOnChainUtxosExternalAction` at the time of the attack — a plausible but not guaranteed state for users of that feature.

If both preconditions hold, the attack is cheap (a single self-funded `transact` call, no special roles needed) and fully repeatable. The root-cause defect — `EmporiumUpgradeable`'s op loop executing fully attacker-controlled calldata against arbitrary endpoints without binding any embedded `CircomData` to the outer verified proof — is confirmed in code regardless of the specific registration state.

### Recommendation
- In `EmporiumUpgradeable.runAction`, disallow ops whose target is a registered Hinkal external action (or more generally, enforce an allowlist of endpoints callable from ops that excludes any contract implementing `IExternalActionV2`), or
- Require that any nested `CircomData` used by a callee originate from — and be checked equal to — the outer, currently-verified `circomData` (e.g., by not allowing arbitrary calldata construction for `runAction`-shaped calls), and
- In `DepositOnChainUtxosExternalAction` (and similar actions), do not trust `circomData.originalSender` merely because `msg.sender` is an allowed recipient; only trust `originalSender` when the caller is `Hinkal` itself, since only `Hinkal.transact` binds `originalSender` to the proof via `performHinkalChecks`.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`, `DepositOnChainUtxosExternalAction`; register `EmporiumUpgradeable` as an allowed recipient of `DepositOnChainUtxosExternalAction` (simulating the assumed production wiring).
2. Victim approves `DepositOnChainUtxosExternalAction` for `X` tokens and holds `X` tokens.
3. Attacker generates a valid proof for their own outer `circomData` (`originalSender = attacker`, `externalActionId = EMPORIUM_ID`), with `externalActionMetadata` encoding an `EmporiumStack` with `signerAddress = address(0)` and one op: `endpoint = DepositOnChainUtxosExternalAction`, `callData = abi.encodeCall(runAction, (forgedCircomData, [0]))` where `forgedCircomData.originalSender = victim`, `forgedCircomData.stealthAddressStructure` = attacker's H0/H1.
4. Call `Hinkal.transact(...)` as attacker.
5. Assert: victim's token balance decreases by `X` (or the pulled amount), `EmporiumUpgradeable`'s balance increases correspondingly, and after `Hinkal.transact` completes, a new commitment/UTXO is inserted into the Merkle tree under the attacker's `stealthAddressStructure` (outer, correctly-proved `circomData`) for that value — proving the stolen funds became a spendable shielded balance for the attacker while the forged inner `stealthAddressStructure` was never checked against any proof.

    function runAction(
        CircomData calldata circomData,
        int256[] calldata deltaAmountChanges
    ) external override onlyAllowedRecipient returns (UTXO[] memory) {
        EmporiumStack memory stack = abi.decode(
            circomData.externalActionData.externalActionMetadata,
            (EmporiumStack)
        );

        uint256[] memory balancesBefore = getBalancesForArray(
            circomData.erc20TokenAddresses
        );

        verifyWallet(stack, circomData);

        for (uint256 i = 0; i < stack.ops.length; i++) {
            EmporiumOperation memory op = stack.ops[i];

            bool success;
            bytes memory err;

            // CASE 1: Stateful Interaction
            if (op.invokeWallet && stack.signerAddress != address(0)) {
                (success, err) = IHinkalWallet(stack.signerAddress)
                    .callHinkalWallet(op.endpoint, op.callData, op.value);
            }
            // CASE 2: Stateless Interaction
            else {
                bytes4 selector = bytes4(op.callData);
                if (
                    selector == IHinkalWallet.callHinkalWallet.selector ||
                    selector == IHinkalWallet.doSendToRelay.selector
                ) {
                    revert UnauthorizedWalletCall();
                }

                (success, err) = op.endpoint.call{value: op.value}(op.callData);
            }

            if (!success) {
                revert CallFailed(err);
            }
        }

        uint256[] memory balancesAfter = getBalancesForArray(
            circomData.erc20TokenAddresses

            circomData.erc20TokenAddresses.length
        );
