### Title
Webhook `shop`, `topic`, and `webhook_id` headers are trusted without HMAC coverage, enabling cross-tenant webhook data spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates the incoming webhook solely via `Utils::HmacValidator.validate(request)`, but the HMAC signature only covers the raw request body, not the `shop-domain`, `topic`, or `webhook-id` HTTP headers. Those header-derived fields are nonetheless passed to the app's handler as trusted identity metadata (`WebhookMetadata#shop`, `#topic`, `#webhook_id`), breaking the equality "shop authenticated == shop the handler acts on."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors, however, are read directly from unauthenticated HTTP headers with no cryptographic binding to the signed body: [2](#0-1) 

`HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest` over `verifiable_query.to_signable_string` (i.e. the body only) and compares it against the `hmac` header: [3](#0-2) 

`Registry.process` treats a passing HMAC check as proof the entire request — including `request.shop` — is authentic, then forwards `request.shop`/`request.topic`/`request.webhook_id` straight into the handler without any additional verification: [4](#0-3) 

The struct passed to app handlers explicitly carries `shop` as a trusted field of type `String`, with no indication to implementers that it is unauthenticated: [5](#0-4) 

The documentation reinforces this false guarantee, stating that `Registry.process` "will verify the request did indeed come from Shopify" before invoking the handler, without qualifying that only the body — not the shop/topic/webhook-id headers — is verified: [6](#0-5) 

Because the HMAC secret (`api_secret_key`) is shared across all shops installing a given app (not per-shop), any tenant that legitimately receives one valid webhook delivery for their own shop possesses a valid `(body, hmac)` pair signed with that app-wide secret. Since headers are not part of the signed content, that same `(body, hmac)` pair remains valid when replayed to the app's webhook endpoint with the `shop-domain` header rewritten to a different, victim tenant. `Registry.process` will accept it (HMAC over body still matches) and dispatch it to the handler tagged with the attacker-chosen `shop`, breaking the binding between "shop that actually sent the authenticated bytes" and "shop the app believes it is acting on behalf of."

### Impact Explanation
This breaks the tenant isolation the gem is documented to provide via `Registry.process`. An app that keys any per-shop side effect (data writes, cache invalidation, notification dispatch, billing events, audit logs) off `WebhookMetadata#shop` can be made to apply a webhook payload under a different shop's identity, corrupting data or triggering unauthorized state changes cross-tenant. This matches the "cross-tenant access" impact category.

### Likelihood Explanation
The attacker only needs their own (or any) legitimately webhook-registered shop to capture one valid `(raw_body, hmac)` sample — a routine, unprivileged capability for any merchant installing the app. No access to `api_secret_key`, access tokens, or other shops' credentials is required, only the ability to replay an HTTP POST with modified headers to the public webhook endpoint. This is a moderate-likelihood, low-effort attack path, and is not mitigated by anything in this gem's own code path.

### Recommendation
Include the `shop-domain`, `topic`, and `webhook-id` header values in the signed material verified by `HmacValidator`, or otherwise cryptographically bind them to the request (e.g., have `to_signable_string` incorporate the headers Shopify itself signs, matching what Shopify's servers actually compute over). At minimum, document prominently that `shop`/`topic`/`webhook_id` on `WebhookMetadata` are unauthenticated header values and that host applications must independently verify `shop` against their own installed-shop records before trusting it for tenant-scoped operations.

### Proof of Concept
1. App receives a legitimate webhook for `shop-a.myshopify.com` with body `{"id":1}` and a valid `x-shopify-hmac-sha256` computed over that body using the app's shared `api_secret_key`.
2. Attacker (who controls `shop-a`, an installed tenant) captures this `(raw_body, hmac)` pair.
3. Attacker replays the identical HTTP request to the app's public webhook endpoint but changes the `x-shopify-shop-domain` header to `victim-shop.myshopify.com`, leaving `raw_body` and `x-shopify-hmac-sha256` unchanged.
4. `HmacValidator.validate` recomputes the HMAC over `raw_body` only — it matches, since headers aren't part of the signable string (`lib/shopify_api/webhooks/request.rb:35-38`).
5. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body:, ...))`, and the app now processes attacker-controlled `shop-a` data as though it belongs to `victim-shop`.
