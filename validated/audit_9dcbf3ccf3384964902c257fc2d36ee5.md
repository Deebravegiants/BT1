This vulnerability class maps directly onto Shopify webhook signature verification: the request body is HMAC-verified, but the `shop` identity used to route/attribute the webhook is taken from an unauthenticated header and is never bound into that signature.

### Title
Webhook Shop-Domain Header Not Bound by HMAC Enables Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking that the HMAC over the raw request body matches, but the `shop` value attached to the resulting `WebhookMetadata` (and passed to the app's handler) is read directly from an HTTP header that is never included in the signed payload.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop` is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, with no cross-check against anything cryptographically bound to the body: [2](#0-1) 

`Registry.process` verifies only the HMAC of the body, then forwards `request.shop` straight into `WebhookMetadata` without any binding check between the verified body and the claimed shop: [3](#0-2) 

`HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the supplied `hmac`; since `to_signable_string` is just the raw body, the shop header plays no role in this computation: [4](#0-3) 

The broken identity binding, stated as an equality that should hold but doesn't:
`shop_claimed_in_header == shop_that_produced_the_HMAC-signed_body` — the gem enforces neither side of this equality; it only checks `HMAC(body) == received_hmac`, which is independent of the `shop` header value entirely.

Because the app's `api_secret_key` is shared across every shop that installs the app (it is not a per-shop secret), any merchant who has legitimately installed the app can obtain a validly-signed `(raw_body, hmac)` pair for their own shop's webhook traffic, then resend that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header (e.g., a victim shop's domain). `HmacValidator.validate` will still pass because it never inspects the header, and the handler will receive `WebhookMetadata` claiming to originate from the victim shop.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook delivery: an attacker who is merely one authorized-but-unprivileged installer of the app can make the host application believe/act on a webhook that appears to originate from a shop they do not own. Depending on how the host app's handler consumes `WebhookMetadata#shop` (e.g., session lookups, data writes, uninstall/GDPR flows keyed by shop), this enables cross-tenant data injection/corruption or triggering shop-scoped app logic (such as data-deletion or credential-teardown paths keyed by `shop`) against another merchant's tenant — a cross-tenant access impact.

### Likelihood Explanation
Likelihood is high for any attacker who is a legitimate installer of the target app on their own store (an "unprivileged internet user" relative to other tenants of that app): they only need to capture one webhook delivery for their own shop (trivial, since Shopify delivers these to their own registered endpoint or they can proxy/log it) and replay the body+HMAC pair with a modified shop header.

### Recommendation
Bind the shop identity into the verified payload rather than trusting the header independently:
- Include the shop domain (and/or webhook id) in the HMAC-signable string, or
- Require the caller to supply/verify the shop out-of-band (e.g., cross-check `request.shop` against a shop associated with the specific webhook subscription/registration id looked up server-side) before constructing `WebhookMetadata`, so `handler.handle` never receives an unauthenticated shop claim paired with someone else's signed body.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and captures a legitimately delivered webhook: raw body `B` with header `x-shopify-hmac-sha256: H` (valid for the app's `api_secret_key`) and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the identical body `B` and HMAC `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` and finds it equals `H` — validation succeeds, since the header is not part of the signed string: [5](#0-4) 
4. `Registry.process` builds `WebhookMetadata` with `shop: request.shop` = `"victim-shop.myshopify.com"` and invokes the host app's handler as if the (attacker-controlled) body genuinely came from the victim shop.
