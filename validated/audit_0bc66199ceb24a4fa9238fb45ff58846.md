Unbounded, statically-weighted `handle_unsigned` message batch enables free-transaction-pool-validation DoS - (File: `modules/pallets/ismp/src/lib.rs`)

### Summary
`pallet_ismp::Call::handle_unsigned` accepts an unbounded `Vec<Message>` where each `Message::Request`/`Message::Response`/`Message::Timeout` variant in turn carries unbounded `Vec<PostRequest>` / `Vec<GetRequest>` (each with an unbounded `keys: Vec<Vec<u8>>`), yet the call is annotated with a single static weight `weight()` (`Weight::from_parts(300_000_000, 0)`) that does not scale with the size of the batch. Because this is an unsigned extrinsic, `ValidateUnsigned::validate_unsigned` unconditionally calls `Self::execute(messages.clone())` — which runs the full membership/state-proof trie verification pipeline over every request/key in the batch — on every full node that receives the gossiped transaction, before any block-inclusion weight accounting is even relevant. This mirrors the aimhubio/aim CVE-2024-12778 pattern: an API surface (there, `/metrics`; here, the p2p-broadcast unsigned extrinsic path) that lacks a cap on the number of items processed per call, letting a single crafted request/transaction force disproportionate, uncapped CPU work on every node that touches it.

Because none of `execute`, `handle_unsigned`, `validate_unsigned`, `RequestMessage`, `ResponseMessage`, or `GetRequest` enforce a maximum count on messages, requests, or keys, and the declared extrinsic weight is a flat constant rather than one that scales with the batch (e.g., via a linear/quadratic weight function keyed off `messages.len()`), an attacker can build a `handle_unsigned` call whose encoded size approaches the runtime's extrinsic/block-length limit but whose semantic content (number of requests × number of keys per request) is maximized, forcing every full node that validates the gossiped transaction to perform a correspondingly large amount of trie-proof verification work for a single, free (fee-less, unsigned) submission.

### Impact Explanation
This is a network/consensus-layer availability issue analogous to the referenced aim DoS: a single unprivileged submission (any peer can gossip an unsigned extrinsic) forces disproportionate CPU work on every full node validating it, with no batch-size ceiling gating that work. Repeated submission of such extrinsics (which cost nothing since `handle_unsigned` messages are processed "for free") can degrade transaction-pool validation throughput and block-production responsiveness across the network — a route becoming unable to process legitimate ISMP message delivery in a timely fashion, which is the closest Hyperbridge-specific analog to "a route unable to deliver messages" called out in scope. This qualifies as Medium/High severity under the CVSS 3.0 AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:H profile of the source report, since only availability is impacted and no funds are directly stolen.

### Likelihood Explanation
The `handle_unsigned` call is explicitly designed to be free and open to any submitter (unsigned origin, "permits anyone execute ISMP messages for free"), so no privileged role or prior state is needed to reach this path — any relayer-class actor (or anyone able to submit to the node's RPC/gossip layer) can construct and broadcast such a transaction. The only barrier is that `validate_unsigned` requires the batch to pass `Self::execute`, meaning fields like proof bytes must at least decode; however, decoding and iterating a large but internally consistent-looking `Vec<GetRequest>`/`Vec<PostRequest>` with many entries/keys (even ones that ultimately fail proof verification after doing the trie-walk work) is sufficient to consume verification-time CPU on every node that revalidates the gossiped extrinsic, since the constant-time rejections (timeouts, dedup, has-receipt checks) still require walking the whole vector before proof verification, and proof verification itself is not gated by a hard, config-enforced max count.

### Recommendation
- Enforce a `MaxRequestsPerMessage` / `MaxKeysPerGetRequest` bound (analogous to `MaxCallSize` already used in `pallet-call-decompressor`) checked in `validate_unsigned`/`handle_unsigned` *before* any proof verification or trie walk begins, rejecting oversized batches immediately.
- Make the declared `#[pallet::weight(...)]` for `handle_unsigned` a function of `messages.len()` (and ideally of the aggregate request/key counts), so `CheckWeight`-style accounting reflects real cost and overly large batches are priced or rejected rather than executed for free.
- Consider capping `GetRequest.keys.len()` at the type level (bounded vec) so a single request cannot smuggle an unbounded key list into `verify_state_proof`.

### Proof of Concept

2. Submit it unsigned to any Hyperbridge node's transaction pool (no fee, no signature required, per `handle_unsigned` doc/`ensure_none` check at `modules/pallets/ismp/src/lib.rs:377`).
3. Every full node that receives the gossiped extrinsic invokes `ValidateUnsigned::validate_unsigned` (`modules/pallets/ismp/src/lib.rs:614-626`), which calls `Self::execute(messages.clone())`, iterating the full request/key list and performing trie-membership/state-proof verification work proportional to the crafted batch size, before the extrinsic is ultimately rejected for an invalid proof — repeat submissions at high frequency degrade node responsiveness.

pub fn verify_child_trie_membership<H: IsmpHost>(
	root: H256,
	proof: &[Vec<u8>],
	keys: Vec<Vec<u8>>,

	let db = StorageProof::new(proof.to_vec()).into_memory_db::<BlakeTwo256>();
	let trie = TrieDBBuilder::<LayoutV0<BlakeTwo256>>::new(&db, &root).build();

			return Err(SubstrateEvmError::KeyNotFound(key));
		}
	}

}
