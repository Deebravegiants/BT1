### Title
`numberToBigEndian` truncates the TON Connect timestamp via 32-bit `>>=`, producing a wrong locally-computed intent hash for large timestamps - (File: `packages/intents-sdk/src/intents/intent-hashes/ton-connect.ts`)

### Summary
`numberToBigEndian` in `computeTonConnectHash` encodes the 8-byte timestamp field using `num & 0xff` / `num >>= 8` in a loop, but JavaScript's `>>=` operator first coerces its operand to a 32-bit signed integer (`ToInt32`). For any timestamp value ≥ 2^31 (or ≥ 2^32 depending on the byte position), the coercion silently discards the high-order bits, so the emitted 8-byte big-endian timestamp diverges from the correct 64-bit encoding that the real signed TON Connect message (and therefore the relay's/on-chain's real intent hash) uses. This breaks `computeIntentHash(multiPayload) == intent_hash` exactly as claimed.

### Finding Description
`computeTonConnectHash` calls:
```ts
numberToBigEndian(Number(timestamp), 8)
``` [1](#0-0) 

and `numberToBigEndian` is:
```ts
function numberToBigEndian(num: number, bytes: number): Uint8Array {
	const result = new Uint8Array(bytes);
	for (let i = bytes - 1; i >= 0; i--) {
		result[i] = num & 0xff;
		num >>= 8;
	}
	return result;
}
``` [2](#0-1) 

`>>=` in JS performs `ToInt32` on its operand before shifting. For values above `2**31-1`, `ToInt32` wraps to a negative 32-bit value and subsequent arithmetic (sign-extending) right shifts propagate 1-bits into vacated high positions instead of the correct zero-fill; for values `>= 2**32` the low 32 bits are dropped outright on the very first shift. I hand-traced `numberToBigEndian(2**32 + 5, 8)`: byte[7]=5 (correct), but the internal `num` collapses to `0` after the first shift instead of `16777216`, causing byte[2] to be `0` instead of the correct `1` — a genuine, verifiable divergence from the true 64-bit big-endian encoding `00 00 00 01 00 00 00 05`.

The `timestamp` value flows unmodified from the wallet's own TonConnect signature response into the multiPayload used for hashing:
```ts
case "TON_CONNECT": {
	return {
		standard: "ton_connect",
		...
		timestamp: signature.signatureData.timestamp,
		...
	};
}
``` [3](#0-2) 

This is exactly the value that was included in the real bytes the wallet signed and that the relay/on-chain verifier uses to compute the authoritative `intent_hash`. Any wallet/counterparty that reports the timestamp in a unit exceeding 2^31 (e.g., milliseconds instead of seconds, as many wallet SDKs default to `Date.now()`) causes the SDK's local hash to diverge from the real one, while the signature itself remains valid (it was computed by the wallet over the true byte encoding, not through this buggy JS function).

The divergence is consumed here:
```ts
if (this.onBeforePublishIntent) {
	const intentHash = await computeIntentHash(multiPayload);
	await this.onBeforePublishIntent({ intentHash, intentPayload, multiPayload, relayParams });
}
``` [4](#0-3) 

`onBeforePublishIntent`'s documented purpose is "persistence, logging, analytics, etc.": [5](#0-4) 

An integrator following this documented API to persist the intent hash before publish, then later calling `waitForIntentSettlement`/`getIntentStatus` with that stored hash, will poll for a hash that never matches the relay's real `intent_hash` for TON Connect payloads with out-of-range timestamps.

None of the repo's existing guards (`assert`, `validateAddress`, `validateWithdrawal`, `FeeExceedsAmountError`, nonce/signature checks in the intents contract) touch this local hash-recomputation path — they operate on amount/address/fee validation, not on reproducing the exact byte encoding of a signed TonConnect message.

### Impact Explanation
This is a hash-misreport bug: the integrator-tracked `intentHash` (obtained via `onBeforePublishIntent`) will not equal the actual settled `intent_hash` returned by the relay/contract for affected ton_connect payloads. Consequences:
- `waitForIntentSettlement`/`getIntentStatus` keyed on the wrong hash will report `NOT_FOUND` or time out even though the withdrawal has actually settled on-chain.
- An automated integrator flow may treat this as a failure and resubmit `signAndSendIntent` for the same withdrawal, causing the caller to authorize/settle the withdrawal amount twice (their own funds debited twice from the Intents contract balance), which matches the "status/hash misreport causing double credit/refund" Critical/High category.
- This is repeatable on every call where the wallet reports a timestamp ≥ 2^31 (deterministic bug, not timing-dependent).

### Likelihood Explanation
- Precondition: `standard === "ton_connect"` and the wallet-produced `timestamp` field exceeds `2**31` (this includes any wallet emitting millisecond-precision timestamps, a known common unit mismatch, or any timestamp value close to/after the 2038 second-based rollover).
- No special privilege is needed — the value is taken as-is from the wallet's own `signatureData.timestamp` and forwarded through `prepareSwapSignedData` without range validation.
- Zero attacker cost: any counterparty/wallet naturally reporting ms-based timestamps triggers it; no crafted malicious payload needed beyond the natural, plausible unit mismatch described in the question.
- Reachable only if the integrator uses the documented `onBeforePublishIntent` hook's `intentHash` for tracking, which is exactly what the hook is designed and documented for, not a misuse of an escape hatch.

### Recommendation
Rewrite `numberToBigEndian` to use `BigInt` (or unsigned/logical operations) so it correctly encodes numbers beyond the 32-bit signed integer range, e.g.:
```ts
function numberToBigEndian(num: number, bytes: number): Uint8Array {
	let n = BigInt(num);
	const result = new Uint8Array(bytes);
	for (let i = bytes - 1; i >= 0; i--) {
		result[i] = Number(n & 0xffn);
		n >>= 8n;
	}
	return result;
}
```
Additionally, validate/normalize the incoming `timestamp` (reject or convert values clearly out of the expected UNIX-seconds range) before hashing.

### Proof of Concept
Vitest plan:
1. Add a BigInt-based reference encoder:
```ts
function referenceBigEndian(num: number, bytes: number): Uint8Array {
	let n = BigInt(num);
	const out = new Uint8Array(bytes);
	for (let i = bytes - 1; i >= 0; i--) {
		out[i] = Number(n & 0xffn);
		n >>= 8n;
	}
	return out;
}
```
2. Directly test the internal helper's behavior by exercising it through `computeTonConnectHash` with a crafted `timestamp` of `2 ** 32 + 5` (or `1762354640123`, a plausible ms timestamp) and assert:
```ts
expect(numberToBigEndianExported(2 ** 32 + 5, 8)).not.toEqual(referenceBigEndian(2 ** 32 + 5, 8));
```
(export `numberToBigEndian` for the test, or reimplement the loop inline in the test to demonstrate the divergence.)
3. Propagate to `computeTonConnectHash`: construct two `MultiPayload` fixtures identical except computed via the buggy vs. reference encoders (patch/mimic the reference inline), compute `sha256` over both messages, and assert the hashes differ — proving `computeIntentHash(multiPayload)` (buggy) ≠ the hash that would be produced by (and match) the relay's authoritative `intent_hash` computed with correct 64-bit encoding.
4. Optionally mock `intentRelayer.publishIntent` in an `intent-executer.test.ts`-style test to return a `ticket`/`intent_hash` computed with the reference encoder, and assert that the `intentHash` passed into `onBeforePublishIntent` (computed via the real, buggy `computeTonConnectHash`) does not equal it for a ms-scale timestamp.
