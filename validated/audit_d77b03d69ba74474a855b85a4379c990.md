### Title
Wallet Contract silently upgrades an intended zero/limited access-key allowance to `Allowance::Unlimited` - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `near-wallet-contract` (ETH-emulation wallet contract) converts a decoded `AddKey` action from a signed Ethereum-style transaction into a NEAR `Promise::add_access_key_allowance_with_nonce` call. When translating the requested `FunctionCall` permission's allowance, the code falls back to `Allowance::Unlimited` whenever `Allowance::limited(...)` returns `None`, which happens whenever the requested allowance amount is `Balance::ZERO`. This mirrors the reported `Synth.approveAndCall` bug class: instead of honoring the exact/minimal permission that was requested, the code silently grants the maximum possible permission.

### Finding Description
In `action_to_promise`, the `AddKey` branch for `FunctionCall` permissions does: [1](#0-0) 

```rust
near_action::AccessKeyPermission::FunctionCall(access) => Ok(Promise::new(target)
    .add_access_key_allowance_with_nonce(
        action.public_key,
        access.allowance.and_then(Allowance::limited).unwrap_or(Allowance::Unlimited),
        access.receiver_id,
        access.method_names.join(","),
        action.access_key.nonce,
    )),
```

`access.allowance` is an `Option<Balance>` decoded directly from the ETH-emulated `AddKey` action fields (`is_limited_allowance` / `allowance`), which are attacker/relayer-influenced input parsed from the RLP transaction payload (see `abi_encode`/decode round-trip in `runtime/near-wallet-contract/implementation/wallet-contract/src/types.rs` and `integration-tests/src/tests/features/wallet_contract.rs:438-450`, which show `allowance` and `is_limited_allowance` are independently settable fields). `near_sdk::Allowance::limited(amount)` is documented/implemented to return `None` when the balance is zero (it maps to a `NonZeroU128`-backed variant), matching the semantics that `Some(Balance::ZERO)` is not a meaningful "limited" allowance.

The bug is that `.unwrap_or(Allowance::Unlimited)` treats "limited-but-zero" the same as "no limit was requested," collapsing a request for a *minimal/zero* spending permission into the *maximal* possible spending permission (unlimited $NEAR for gas/fees to the given `receiver_id`/`method_names`). This is the direct analog of `Synth.approveAndCall` approving `type(uint256).max` instead of the specific `amount`: the code has the exact value needed (`Some(Balance::ZERO)`), but a fallback path silently substitutes the maximum value instead of preserving/rejecting the requested value.

Compare with the correctness invariant documented for native access keys, where `None` (not `Some(0)`) is the only sentinel meaning "unlimited": [2](#0-1) 

### Impact Explanation
An access key added through the wallet contract's ETH-transaction path that the signer intended to be tightly restricted (allowance = 0, or any other value that ends up producing a `None` from `Allowance::limited`) instead receives `Allowance::Unlimited`. Because `FunctionCallPermission` allowance directly bounds how much of the account's `$NEAR` balance can be spent on gas/fees by that key (see `check_and_compute_new_allowance` in `runtime/runtime/src/verifier.rs:239-260`), this silently expands the authorized spending capability of a newly-added access key on the user's own wallet-contract account from "effectively none" to "the entire account balance." If that key is later exposed, reused by an untrusted relayer, or otherwise misused, the wallet account's balance can be drained for gas/fee spend far beyond what the account owner authorized — an unauthorized state/balance-change condition, without any node, validator, or network-layer compromise involved; it is reachable purely by submitting a normal signed transaction through `rlp_execute`. [3](#0-2) 

### Likelihood Explanation
This path triggers deterministically whenever any RLP-encoded transaction executed through `rlp_execute` contains an `AddKey` action with `FunctionCall` permission and an allowance value that decodes to zero (or otherwise maps to `None` in `Allowance::limited`). No privileged role, validator behavior, or race condition is required — it is a straightforward, always-reachable logic error in action translation for any account owner using the wallet contract's ETH-transaction emulation feature.

### Recommendation
Do not conflate "`Allowance::limited` returned `None`" with "unlimited was requested." Preserve the distinction between `access.allowance == None` (explicitly unlimited, per `FunctionCallPermission` semantics) and `access.allowance == Some(0)` (an invalid/degenerate limited request). Concretely:
- If `access.allowance` is `None`, use `Allowance::Unlimited`.
- If `access.allowance` is `Some(x)`, either reject the action as invalid when `x == 0` (returning a `UserError`), or map it to the smallest valid non-zero limited allowance, but never silently fall through to `Allowance::Unlimited`.

### Proof of Concept
1. Craft a valid RLP-encoded, signed Ethereum-style transaction whose decoded `near_action::Action::AddKey` contains `AccessKeyPermission::FunctionCall { allowance: Some(Balance::ZERO), receiver_id, method_names }` (i.e., `is_limited_allowance = true`, `allowance = 0` in the ABI encoding shown in `integration-tests/src/tests/features/wallet_contract.rs:438-450`).
2. Submit it via `WalletContract::rlp_execute(target, tx_bytes_b64)`.
3. Observe that `action_to_promise` (lib.rs:484-496) converts this into `add_access_key_allowance_with_nonce(..., Allowance::Unlimited, ...)` because `Allowance::limited(Balance::ZERO)` returns `None`, so `unwrap_or(Allowance::Unlimited)` is taken.
4. Query the resulting access key on-chain (`view_access_key`) and confirm its `allowance` is unlimited (`None`) rather than the requested zero/limited value — verifying the escalation.

Note: I could not directly inspect the `near_sdk::Allowance` enum/`limited` implementation source (it is an external crate dependency, not vendored in this repo), so the exact zero-maps-to-`None` behavior is inferred from its documented `NonZeroU128`-based semantics and the naming/usage pattern in this codebase rather than from reading its source directly. If `Allowance::limited` behaves differently than assumed (e.g., zero maps to `Some(Limited(0))` instead of `None`), the concrete triggering condition would need to be re-verified, though the general code smell of `unwrap_or(Allowance::Unlimited)` collapsing any `None` case from a fallible conversion into the maximal-privilege variant remains.

fn check_and_compute_new_allowance(
    access_key: &AccessKey,
    account_id: &AccountId,
    public_key: &PublicKey,
    total_cost: Balance,
) -> Result<Option<Balance>, InvalidTxError> {
    let Some(fc) = access_key.permission.function_call_permission() else {
        return Ok(None);
    };
    let Some(allowance) = fc.allowance else {
        return Ok(None);
    };
    let new_allowance = allowance.checked_sub(total_cost).ok_or_else(|| {
        InvalidTxError::InvalidAccessKeyError(InvalidAccessKeyError::NotEnoughAllowance {
            account_id: account_id.clone(),
            public_key: public_key.clone().into(),
            allowance,
            cost: total_cost,
        })
    })?;
    Ok(Some(new_allowance))
}
