### Title
Webhook HMAC Signature Does Not Cover the `shop-domain` Header, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the tenant-identifying `shop-domain` header (and `topic`/`webhook-id`/`api-version`) are read directly from unauthenticated headers and never included in the HMAC-covered bytes. This lets an attacker who can obtain any one valid `(body, hmac)` pair replay it against the app's webhook endpoint with an arbitrary `shop-domain` header, causing the handler to process attacker-chosen data under a victim shop's identity.

### Finding Description
`Registry.process` verifies a webhook exclusively via `Utils::HmacValidator.validate(request)`: [1](#0-0) 

That validator computes the signature purely from `verifiable_query.to_signable_string`: [2](#0-1) 

And `Request#to_signable_string` is defined as just the raw body — no headers are folded into the signed bytes: [3](#0-2) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from attacker-controllable headers with no cross-check against the signed payload: [4](#0-3) 

The unvalidated `shop` is then handed directly to the application's webhook handler as the tenant identity: [5](#0-4) 

This mirrors the report's bug class exactly: a field that is *acted on* (the `shop-domain` header, used to bind incoming data to a tenant) is not *covered by the HMAC* (which binds only the raw body). The binding the code implicitly assumes is:
`hmac_valid(body) == (shop_header_is_authentic)`
but the actual equality that holds is only `hmac_valid(body) == (body_is_authentic)`. The `shop-domain` header is disjoint from what is cryptographically verified.

### Impact Explanation
An attacker who can obtain one legitimate `(raw_body, hmac)` pair for *any* shop that installed the app (e.g., their own store where they installed the same public app) can replay that exact body/hmac to the target application's webhook endpoint while substituting the `shop-domain` (and other) headers to point at a victim shop. Because `HmacValidator.validate` only checks the body against the shared `api_secret_key` (which is identical across all installs of the same app, not per-shop), the forged request passes validation. The handler then processes attacker-supplied data as if it originated from the victim shop — a cross-tenant data injection/spoofing primitive. Depending on how the consuming application keys state off `WebhookMetadata#shop` (e.g., updating that shop's local records, billing, inventory, order state), this can lead to cross-tenant data corruption or unauthorized actions attributed to another merchant, satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Moderately likely to be reachable: any developer/attacker can install the same public app onto their own (attacker-controlled) store to legitimately receive real, correctly-signed webhook deliveries, then simply replay the captured HTTP POST to the app's public webhook endpoint with a modified `shop-domain` header. No secret material or victim-side compromise is required — only a body/hmac pair from a webhook the attacker legitimately received for their own tenant.

### Recommendation
Bind the header values into the signed content, not just the raw body — e.g., include `shop`, `topic`, `webhook_id`, and `api_version` in `to_signable_string` (matching what Shopify actually includes when computing its HMAC, if it does), or independently verify the `shop-domain` header corresponds to the intended, installed shop for the app (cross-reference with a known/stored shop record) before trusting it. At minimum, do not treat `request.shop` as an authenticated value when it hasn't been bound to the signature.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and receives a legitimate webhook POST with body `B` and header `x-shopify-hmac-sha256: H` (a valid HMAC of `B` under the shared `api_secret_key`), plus `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker replays the identical request to the same endpoint, changing only `x-shopify-shop-domain` to `victim-shop.myshopify.com` (and optionally `topic`/`webhook-id` to trigger a different handler code path).
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only — validation succeeds because `B` and `H` are unchanged.
4. `handler.handle` is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to act on `B`'s contents under the victim shop's identity.
