### Title
Out-of-gas-equivalent DoS via unbounded nested loop in Web API trigger topic matching - (File: core/capabilities/webapi/trigger/trigger.go)

### Summary
`triggerConnectorHandler.processTrigger` performs a nested loop over every registered workflow trigger and every attacker-supplied topic string in a single web-api-trigger gateway message, with no upper bound on the number of topics a request may contain. This mirrors the reported Telcoin bug class: an O(triggers × items) double loop driven by unprivileged, externally-supplied data, where cost grows unboundedly with attacker input and with the number of registered workflows on the node.

### Finding Description
`HandleGatewayMessage` decodes the incoming JSON-RPC/legacy gateway message body and, for the `web-api-trigger` method, unmarshals the payload directly into `webapicap.TriggerRequestPayload` without validating the size of `Topics`: [1](#0-0) 

The `TriggerRequestPayload.Topics` field is a plain `[]string` with no schema-level or code-level length constraint, only requiring it be non-empty: [2](#0-1) [3](#0-2) 

`processTrigger` then snapshots all currently-registered triggers (one per registered workflow on the node) and runs a nested loop, comparing every trigger against every topic in the request: [4](#0-3) 

This is structurally identical to the reported pattern: for every incoming message, the handler iterates the full set of "plugins" (here, registered triggers) crossed with attacker-controlled per-request data (here, `Topics`), giving cost `O(len(triggers) * len(topics))` per single message, with no cap on either dimension from the caller's perspective. The only gate before this loop executes is a stale-message timestamp check and, for legacy messages, a TODO-marked allowlist/rate-limit check that is explicitly unimplemented: [5](#0-4) 

For the v2 gateway path (`HandleGatewayMessage` in trigger.go), per-sender rate limiting is only applied per-matched-trigger inside the inner loop body, i.e., after the expensive scan has already been paid for every trigger×topic pair: [6](#0-5) 

so it does not bound the up-front matching cost of a single oversized request.

### Impact Explanation
As the number of registered workflow triggers on a node grows (which is expected over time as more workflows subscribe to the web-api-trigger capability) and/or as an attacker submits a request with a very large `Topics` array (unbounded JSON array, limited only by generic message-size limits, if any, upstream), the per-message CPU cost of `processTrigger` grows multiplicatively. A single crafted message can force the node to perform a large number of map lookups and string comparisons synchronously while holding no external throttle, degrading or blocking processing of the trigger connector handler for that node and delaying/denying legitimate trigger delivery to all registered workflows — a node-level DoS reachable from an unprivileged external caller through the gateway, analogous to the referenced "out of gas with nested loop across all plugins" issue.

### Likelihood Explanation
Reachable directly from an unprivileged client: any actor able to reach the gateway's web-api-trigger endpoint (an intentionally externally-facing HTTP/gateway surface) can submit a `TriggerRequestPayload` with an arbitrarily large `Topics` array. No authentication beyond a valid message signature and non-stale timestamp is required before the nested loop executes, and per-sender rate limiting (where present) only throttles *after* a match is found, not the initial O(n×m) scan.

### Recommendation
- Enforce a maximum length on `TriggerRequestPayload.Topics` (and validate it in `processTrigger`/`HandleGatewayMessage` before iterating), rejecting oversized requests early.
- Avoid the full triggers × topics cross product: index triggers by topic (e.g., `map[topic][]*webapiTrigger`) so lookups are O(len(topics)) instead of O(len(triggers) × len(topics)).
- Apply per-sender rate limiting before the matching loop runs, not only after a match, to bound the cost attackers can impose per unit time regardless of match outcome.
- Implement the still-outstanding "TODO: apply allowlist and rate-limiting" gate in the legacy handler path before message processing begins.

### Proof of Concept
1. Register N legitimate workflow triggers via `RegisterTrigger`, each with its own `allowedTopics`/`allowedSenders`/`rateLimiter`, as in `NewTrigger`/`RegisterTrigger`. [7](#0-6) 
2. Send a single signed `web-api-trigger` gateway message whose `TriggerRequestPayload.Topics` contains a very large array of distinct topic strings (e.g., tens of thousands), none of which need to match any `allowedTopics` to force full iteration.
3. `HandleGatewayMessage` → `processTrigger` executes the nested loop over all N triggers × all M topics, consuming CPU proportional to N×M for this single message, with no per-request cap enforced. [8](#0-7) 
4. Repeating this from a single (or few) unauthenticated senders, given no upfront size/allowlist gate for legacy messages, can starve the trigger connector handler on the node.

func (h *triggerConnectorHandler) HandleGatewayMessage(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) error {
	msg, err := hc.ValidatedMessageFromReq(req)
	if err != nil {
		h.lggr.Errorw("error validating message from request", "err", err, "request", req)
		return nil
	}
	body := &msg.Body
	sender := ethCommon.HexToAddress(body.Sender)
	var payload webapicap.TriggerRequestPayload
	err = json.Unmarshal(body.Payload, &payload)
	if err != nil {
		h.lggr.Errorw("error decoding payload", "err", err)
		err = h.sendResponse(ctx, gatewayID, body, ghcapabilities.TriggerResponsePayload{Status: "ERROR", ErrorMessage: fmt.Errorf("error %s decoding payload", err.Error()).Error()})
		if err != nil {
			h.lggr.Errorw("error sending response", "err", err)
		}
		return nil
	}

func (h *triggerConnectorHandler) RegisterTrigger(ctx context.Context, req capabilities.TriggerRegistrationRequest) (<-chan capabilities.TriggerResponse, error) {
	cfg := req.Config
	if cfg == nil {
		return nil, errors.New("config is required to register a web api trigger")
	}

	reqConfig, err := h.ValidateConfig(cfg)
	if err != nil {
		return nil, err
	}

	if len(reqConfig.AllowedSenders) == 0 {
		return nil, errors.New("allowedSenders must have at least 1 entry")
	}

	h.mu.Lock()
	defer h.mu.Unlock()
	_, errBool := h.registeredWorkflows[req.TriggerID]
	if errBool {
		return nil, fmt.Errorf("triggerId %s already registered", req.TriggerID)
	}

	rateLimiterConfig := reqConfig.RateLimiter
	commonRateLimiter := ratelimit.RateLimiterConfig{
		GlobalRPS:      rateLimiterConfig.GlobalRPS,
		GlobalBurst:    int(rateLimiterConfig.GlobalBurst),
		PerSenderRPS:   rateLimiterConfig.PerSenderRPS,
		PerSenderBurst: int(rateLimiterConfig.PerSenderBurst),
	}

	rateLimiter, err := ratelimit.NewRateLimiter(commonRateLimiter)
	if err != nil {
		return nil, err
	}

	allowedSendersMap := map[string]bool{}
	for _, k := range reqConfig.AllowedSenders {
		allowedSendersMap[k] = true
	}

	allowedTopicsMap := map[string]bool{}
	for _, k := range reqConfig.AllowedTopics {
		allowedTopicsMap[k] = true
	}

	ch := make(chan capabilities.TriggerResponse, defaultSendChannelBufferSize)

	h.registeredWorkflows[req.TriggerID] = &webapiTrigger{
		workflowID:     req.Metadata.WorkflowID,
		allowedTopics:  allowedTopicsMap,
		allowedSenders: allowedSendersMap,
		ch:             ch,
		config:         *reqConfig,
		rateLimiter:    rateLimiter,
	}

	return ch, nil
}
