### Title
Permissionless BSC validator-set rotation can be skipped by a strict epoch equality check, permanently freezing consensus updates from that state machine - (File: `modules/ismp/clients/bsc/src/lib.rs`)

### Summary
The BSC consensus client's `verify_consensus` promotes a pending validator set (`next_validators`) to `current_validators` only when the *exact* equality `attested_epoch == rotation_epoch` holds and the attested header has reached `rotation_block`. Since epochs are a monotonically increasing function of block number, a relayer who submits (or is forced/racing to submit) an update whose `attested_epoch` has advanced *past* `rotation_epoch` — skipping the exact epoch window — will never trigger the promotion again, because `attested_epoch` cannot decrease. This mirrors the WithdrawProxy bug class: a guard/state transition ("claim `finalAuctionEnd` reset only when `current epoch == CLAIMABLE_EPOCH`" / "promote `next_validators` only when `attested_epoch == rotation_epoch`") that depends on hitting an exact, monotonically-advancing counter value, which an adversarial or merely out-of-order submission can permanently skip.

### Finding Description
`verify_consensus` in `modules/ismp/clients/bsc/src/lib.rs` performs: [1](#0-0) 

The promotion branch is only entered when `attested_epoch == rotation_epoch`. If any permissionless relayer submits a `BscClientUpdate` whose `attested_header.number` already falls in an epoch *strictly greater* than `rotation_epoch` (which is entirely plausible since anyone can call the handler with any valid, further-ahead BSC header once produced by the chain, and multiple relayers race to submit updates), `next_validators` is left `Some(..)` forever and `current_validators` is never rotated, since `attested_epoch` can only increase across submissions (headers must be `> consensus_state.finalized_height`, enforced above at line 88). There is no fallback path that promotes the pending set once the exact epoch window has passed.

The code comments explicitly acknowledge a defensive check for the resulting inconsistency: [2](#0-1) 

`ensure_finalized_epoch_consistent` is invoked to reject "any update that would leave `finalized_height` running ahead of the validator set the client holds — this would permanently strand the client." This confirms the underlying vulnerability class is understood by the developers (a monotonically-advancing counter skipping the exact match window bricks state), but the mitigation only *rejects the update* rather than *guaranteeing forward progress can still occur*. If `ensure_finalized_epoch_consistent` rejects every update once epoch skip has occurred (because `next_validators.is_some()` never becomes false and the finalized height can never validly advance without crossing through the exact rotation epoch), the consensus client for the affected `Evm(chain_id)` state machine becomes permanently unable to accept new consensus updates — i.e., a liveness freeze — unless a relayer happens to submit an update landing precisely in `rotation_epoch`, which is not guaranteed and can be griefed by a competing relayer submitting a later-epoch header first (front-running the correct-epoch update, analogous to the sandwich attack in the original report).

This is directly analogous to the WithdrawProxy bug: both rely on an "exactly-equal, monotonically-advancing counter" gate (`CLAIMABLE_EPOCH` for `W`, `rotation_epoch` for BSC validator promotion) to perform a critical state transition (`finalAuctionEnd` reset / validator set rotation), and both can be permanently bypassed by any unprivileged party submitting a transaction/update that advances the counter past the required value before the exact-match transition fires.

### Impact Explanation
If the epoch-exact rotation window is skipped, the BSC consensus client becomes unable to make further valid progress for that state machine (since every subsequent update is either rejected by `ensure_finalized_epoch_consistent` or otherwise causes an epoch/validator-set mismatch). This freezes state-membership/non-membership proof verification, request/response delivery, and timeout processing for BSC on Hyperbridge — a route unable to deliver messages, matching the "unsound state commitment" / "route unable to deliver messages" acceptance criteria. Recovery would require governance to reinitialize the consensus client (`create_client`), constituting a high-severity liveness/freezing bug reachable by any relayer submitting a normal consensus update.

### Likelihood Explanation
Likelihood is Medium: the client update path is permissionless (any relayer can submit `ConsensusMessage`/`update_client`), and BSC epochs advance deterministically with block height, so any relayer (malicious or simply not carefully timing their submission) racing ahead can submit a header past `rotation_epoch` before an honest relayer submits the epoch-matching update, especially since block production is fast and predictable. No special privileges or fund outlay beyond gas are required.

### Recommendation
Change the promotion condition from strict equality (`attested_epoch == rotation_epoch`) to `attested_epoch >= rotation_epoch` (while still requiring `attested_number >= next_validators.rotation_block` and validating `source_header_epoch` appropriately for cross-epoch headers), so that promotion is guaranteed to occur on the first update that reaches or passes the rotation point rather than requiring an exact epoch match that can be skipped. Add regression tests submitting updates that skip directly from before `rotation_epoch` to after it, asserting the validator set is still correctly rotated and the client is not stranded.

### Proof of Concept
Conceptual PoC (extending the existing BSC client test suite, e.g. `modules/consensus/bsc/prover/src/test.rs`):
1. Initialize a BSC consensus state with `current_validators` = validator set V1 and `next_validators` = Some(V2, rotation_block = R), where R falls at the boundary of `epoch_length`.
2. Submit `verify_consensus` update #1 with an `attested_header.number` inside `rotation_epoch` but below `rotation_block` (legal, no promotion yet) — this advances `finalized_height`.
3. Submit `verify_consensus` update #2 with `attested_header.number` in the *next* epoch after `rotation_epoch` (skipping the exact `rotation_epoch` window, but still `> consensus_state.finalized_height`, so accepted by the initial expiry check).
4. Observe that `attested_epoch != rotation_epoch` in step 3's promotion check, so `next_validators` remains `Some`, `current_validators` remains V1 (stale).
5. Any further legitimate update either fails `ensure_finalized_epoch_consistent` (client permanently stuck) or accepts a header signed by a validator set (V1) that BSC itself has already rotated away from, corrupting state verification. [3](#0-2) [4](#0-3)
