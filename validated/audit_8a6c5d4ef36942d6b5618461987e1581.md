## Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The gem's webhook signature verification only authenticates the raw HTTP body; it never authenticates the `shop-domain` (or `topic`, `webhook-id`, `api-version`) headers. Any party who can obtain one genuine `(body, HMAC)` pair — trivially available to anyone who installs the app on their own store — can replay that pair to the app's public webhook endpoint while substituting an arbitrary victim `shop-domain` header. The signature still validates because the shop identity is not part of what is signed, so the host application ends up processing attacker-controlled data under the identity of a shop it never came from.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from unauthenticated HTTP headers: [2](#0-1) 

`Utils::HmacValidator.validate_signature` computes the HMAC purely over `verifiable_query.to_signable_string` (i.e., the body) and compares it against the `hmac-sha256` header: [3](#0-2) 

`Webhooks::Registry.process` uses this HMAC-only check as the sole gate before trusting `request.shop` for dispatch: [4](#0-3) 

The identity binding the gem should provide is:
`HMAC_valid(secret, body) == true` should imply `shop header == shop that produced this body`.

In reality the equality that actually holds is only `HMAC_valid(secret, body) == true` regardless of the `shop-domain` header value, because the header is never an input to the HMAC computation. Consequently `request.shop` (and thus `WebhookMetadata#shop` passed to the host app's handler) can be set to any string by the caller of the HTTP endpoint, independent of whose secret-signed body is being replayed.

### Impact Explanation
This breaks the tenant boundary the webhook subsystem is supposed to enforce: a genuine `(body, hmac)` pair legitimately produced for shop A can be replayed against the same public webhook endpoint with the `shop-domain` header set to victim shop B. `Registry.process` will pass HMAC validation and invoke the registered handler with `WebhookMetadata.new(topic: ..., shop: "B", body: <A's data>, ...)`. Any host application that uses `data.shop` to select which tenant's records to create/update/delete (the documented and expected usage pattern) will apply attacker-influenced data under another tenant's identity — a cross-tenant integrity/confidentiality violation reachable by any unprivileged internet user who can install the app once on a store they control.

### Likelihood Explanation
Any Shopify merchant (including an attacker) can freely install a public app on a free development store, causing Shopify to deliver genuine, correctly-signed webhooks to the app's endpoint. Capturing one such `(raw_body, x-shopify-hmac-sha256)` pair requires no special privilege or leaked secret. The webhook endpoint is a public HTTP endpoint by design, so replaying the captured body with an attacker-chosen `shop-domain` header is straightforward and repeatable for any target shop domain string.

### Recommendation
Bind the shop (and ideally topic/webhook-id) to the signature verification instead of trusting it as a bare header: either verify the signed body against an expected shop known independently (e.g., only accept a webhook if `shop` matches a value already associated with a stored session before this request), or require the host application to cross-check `request.shop` against session storage keyed by an out-of-band verified value before acting on the payload. At minimum, document explicitly and loudly that `shop` is unauthenticated metadata and must never be trusted for tenant selection without an additional, independently authenticated lookup.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and lets Shopify deliver a real webhook (e.g. `orders/create`) to the app's public webhook endpoint. Attacker captures the exact `raw_body` and the `x-shopify-hmac-sha256` header value — both fully valid, produced with the real `api_secret_key` unknown to the attacker.
2. Attacker crafts a new POST to the same public webhook endpoint reusing the identical `raw_body` and `x-shopify-hmac-sha256`, but sets:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic`: same or different registered topic
3. `Utils::HmacValidator.validate` recomputes HMAC over `raw_body` only [3](#0-2)  — validation succeeds because the body/secret pair is genuine.
4. `Registry.process` dispatches to the app's handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker's own order data>)` [5](#0-4) , causing the host application to write/act on attacker-supplied data as if it belonged to `victim-shop.myshopify.com`.
