### Title
Webhook `shop-domain` (and `topic`/`api-version`/`webhook-id`) headers are trusted without being covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies webhook authenticity by HMAC-validating only the raw request body, then blindly trusts the `shop-domain` header taken from the same request to identify which merchant the payload belongs to. Because the HMAC signature never covers the shop identity, any actor able to obtain one valid `(body, hmac)` pair — trivially available to anyone who installs the (public) app on their own store — can replay that exact body/hmac to the app's webhook endpoint while substituting an arbitrary victim `shop-domain` header, and the gem will report the request as authentic for the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` reads `shop`, `topic`, `api_version`, and `webhook_id` straight from HTTP headers: [1](#0-0) 

The only thing the HMAC actually signs is the raw body: [2](#0-1) 

`HmacValidator.validate` computes and compares the signature purely against `to_signable_string`, i.e. the body — it never incorporates `shop`, `topic`, or any other header: [3](#0-2) 

`Registry.process` performs the HMAC check and then immediately trusts `request.shop` (and `request.topic`, etc.) to build the `WebhookMetadata` passed to the app's handler — the field that identifies *which tenant* the webhook is for is never bound to the value that was cryptographically verified: [4](#0-3) 

The app's per-app `api_secret_key` is shared across *all* shops that install the app — it is not shop-specific. So a valid HMAC only proves "Shopify's webhook infrastructure produced this body," not "this body belongs to shop X." Consequently:

`shop authenticated by HMAC (proof that the app's secret produced the signature over this body)` ≠ `shop the handler acts on (the unauthenticated shop-domain header)`

Any user who installs the app on their own store can trigger a webhook with attacker-controlled body content, capture the resulting valid `(body, hmac)` pair, and resend that exact pair to the app's public webhook endpoint with the `shop-domain` header changed to a victim shop's domain (and/or `topic`/`webhook_id` changed to route to a different handler). `Registry.process` will pass HMAC validation (body untouched) and hand the handler a `WebhookMetadata` claiming the payload is for the victim shop, with attacker-chosen body content.

### Impact Explanation
This breaks the tenant isolation the gem is expected to provide for webhook processing: an unprivileged user (any merchant who can install the app) can make the app process arbitrary, attacker-chosen webhook data under a victim shop's identity — a cross-tenant confusion/access vector. Depending on how the host app's handler uses `shop`/`body` (e.g., to update per-shop records, trigger sync operations, or influence session/data lookups keyed by shop), this can lead to data corruption or unauthorized actions attributed to a victim merchant, matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation requires only:
1. The ability to install the app on an attacker-controlled store (available to any unprivileged internet user for public apps), to obtain one genuine `(body, hmac)` pair with attacker-influenced content.
2. The ability to send an HTTP POST to the app's public webhook endpoint with modified headers — no credentials, tokens, or victim cooperation needed.

No reliance on the host application deviating from the gem's documented flow — `Registry.process` is exactly the API the gem exposes for webhook handling, and it is this method's own trust boundary that is flawed.

### Recommendation
Incorporate the identity-relevant headers (`shop-domain`, `topic`, `api-version`, `webhook-id`) into the signed payload verification, or otherwise cryptographically bind them to the body before trusting them — e.g., verify the HMAC over a canonical string that concatenates the body with the shop/topic headers, or require correlating the shop-domain header against a value obtained through an independently authenticated channel (such as a lookup keyed by `webhook_id` recorded at registration time) rather than trusting the header verbatim once the body-only HMAC passes.

### Proof of Concept
1. Attacker installs the target app on their own development/trial store `attacker.myshopify.com`.
2. Attacker triggers a webhook whose body content they control (e.g. edits a product to fire `products/update`), and captures the exact `raw_body` and `X-Shopify-Hmac-SHA256` header Shopify sends to the app's webhook endpoint — this HMAC is valid because it's computed with the app's real `api_secret_key`.
3. Attacker crafts a new HTTP POST to the same app webhook endpoint, re-using the captured `raw_body` and `hmac` header unmodified, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally a different `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
4. `ShopifyAPI::Webhooks::Request.new` accepts the headers, `HmacValidator.validate` succeeds (body unchanged), and `Registry.process` invokes the app's handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker-controlled>, ...)`, causing the app to process attacker-controlled data under the victim shop's identity.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
