### Title
Malicious swap route can transfer unrelated wallet assets under the caller’s authorization - (File: contracts/controller/src/strategies/swap.rs)

### Summary
`swap_collateral` accepts caller-controlled route bytes and executes route-selected contracts during an authorized account operation. A malicious route contract can request an unrelated token transfer from the caller; transaction simulation records it as an additional child authorization, and if the caller signs that poisoned tree, the transfer succeeds even though the controller only intended to authorize the strategy itself.

### Finding Description
The public `swap_collateral` entrypoint accepts raw `swap: Bytes` and forwards it into `process_swap_collateral`. [1](#0-0)  The caller is authenticated and must own or delegate the account, after which the controller withdraws collateral and passes the unchanged route bytes to the swap helper. [2](#0-1) 

`swap_tokens` creates a narrow contract-auth entry allowing only the configured router to pull `amount_in`, but that protects the controller’s contract authorization rather than sandboxing route execution. [3](#0-2) [4](#0-3)  The post-call checks measure only the controller’s input spend and output receipt; they do not constrain which contracts the payload invokes or what additional `require_auth` requests those contracts make. [5](#0-4) 

A route-selected contract can therefore call `token.transfer(victim, attacker, amount)` for a token completely unrelated to the lending market. [6](#0-5)  The harness demonstrates that recording mode places that transfer beneath the caller’s `swap_collateral` authorization, while signing the resulting tree makes the transfer execute. [7](#0-6) 

### Impact Explanation
An attacker who supplies a malicious route can steal arbitrary token balances from a user who signs the poisoned authorization tree, in addition to the collateral intentionally routed through the strategy. [8](#0-7)  The proof transfers the victim’s entire unrelated `WALLET_BALANCE` to the attacker while still returning a valid strategy output. [9](#0-8) 

This is theft of user funds and is not bounded by `amount_in`, route minimum output, collateral withdrawal, or the final health-factor check. [10](#0-9) 

### Likelihood Explanation
The attacker can deploy the malicious route contract and distribute or embed the route bytes without privileged access. [8](#0-7)  The victim must sign a transaction whose authorization tree contains the extra transfer, so exploitation requires user interaction and a wallet/client that does not reject the unexpected child invocation. [11](#0-10) 

Because the route can still pay a fair output and leave the lending position healthy, the controller’s measured-settlement and solvency checks do not reveal or prevent the unrelated wallet transfer. [12](#0-11) 

### Recommendation
Do not allow user-supplied routes to invoke arbitrary pool or venue contracts. Enforce a governance-managed venue/pool allowlist at the router boundary, or constrain encoded routes to audited venue adapters whose destination contracts are independently validated. Until protocol-level confinement exists, the controller and all signing clients must reject any `swap_collateral`, `swap_debt`, `multiply`, `repay_debt_with_collateral`, or direct router authorization tree containing children beyond the expected token transfer.

### Proof of Concept
1. Alice owns a healthy account with USDC collateral and holds `WALLET_BALANCE` of an unrelated token.
2. Attacker deploys `RogueHopPool(victim=Alice, token=wallet_token, to=attacker, amount=WALLET_BALANCE)`.
3. Attacker gives Alice route bytes naming that pool while advertising a fair USDC-to-ETH swap. [8](#0-7) 
4. Alice invokes `swap_collateral(caller=Alice, account_id, current=USDC, amount=SWAP_IN_USDC, new=ETH, swap=route)`. [13](#0-12) 
5. During route execution, the pool calls `wallet_token.transfer(Alice, attacker, WALLET_BALANCE)`. [6](#0-5) 
6. Simulation records that transfer as a child of Alice’s `swap_collateral` authorization; signing the returned tree makes the call succeed and leaves Alice’s unrelated wallet balance at zero. [7](#0-6)

fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);
    assert_eq!(s.t.supply_balance_raw(ALICE, "USDC"), usdc_before);

    // Same route, with the tree that simulation returned.
    let stolen_transfer = MockAuthInvoke {
        contract: &s.wallet_token,
        fn_name: "transfer",
        args: (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        sub_invokes: &[],
    };
    s.try_swap_with_signed_tree(&rogue, core::slice::from_ref(&stolen_transfer))
        .expect("the poisoned tree authorizes the rogue transfer");
    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);

That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
