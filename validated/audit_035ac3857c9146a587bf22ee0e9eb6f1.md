### Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` are trusted from unauthenticated headers while the HMAC only covers the raw body - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` exposes `shop`, `topic`, `webhook_id`, and `api_version` by reading them directly from HTTP headers, but `to_signable_string`—the value verified by `Utils::HmacValidator`—is defined as the raw body only, never the headers.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates authenticity solely via `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` and HMAC-compares it against the `hmac-sha256`/`x-shopify-hmac-sha256` header [2](#0-1) . The signable string is defined as:

```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from the `shopify-*`/`x-shopify-*` headers with no cryptographic binding to the HMAC at all:

```ruby
def topic
  T.cast(shopify_header("topic"), String)
end

def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [3](#0-2) 

These unauthenticated values are then handed to the app's registered `WebhookHandler` unchanged:

```ruby
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
  body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
``` [4](#0-3) 

The gem's own documentation instructs integrators to key persistence/enqueue logic off `data.shop` directly:

```ruby
def handle(data:)
  puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
  perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
end
``` [5](#0-4) 

The identity binding that should hold is: **HMAC-verified bytes == the tenant-identifying bytes the app acts on**. Here, `hmac` is computed over `@raw_body` only, while the app acts on `shop` (and `topic`/`webhook_id`) sourced from headers that are completely outside the signed material. Any unprivileged party who can present a header set alongside a raw body whose HMAC matches — e.g., a merchant who has legitimately installed the app and thus regularly receives genuine `(raw_body, hmac)` pairs for their own shop — can replay that exact body with a forged `shopify-shop-domain` (and/or `shopify-topic`/`shopify-webhook-id`) header pointing at a different, victim shop. `Utils::HmacValidator.validate` will still pass because it never looks at the headers, and `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing. Following the gem's documented pattern, host apps use `data.shop` to decide which merchant's records to update/enqueue work for. Because `shop` is unauthenticated relative to the HMAC, an attacker who possesses at least one legitimate `(raw_body, hmac)` pair (trivially available to any shop that has installed the app, since Shopify sends them real webhooks) can cause the app to attribute and act on that webhook body under an arbitrary victim `shop` value — a cross-tenant data-integrity issue reachable without any of the app's own credentials.

### Likelihood Explanation
Likelihood is limited by two factors: (1) the attacker needs a genuine `(raw_body, hmac)` pair, which requires having received at least one real webhook (e.g., being an installed/unprivileged merchant of the target app), and (2) exploitation depends on the host application's handler trusting `data.shop` for tenant-scoped effects, which is exactly the pattern the gem's own documentation recommends. Given how ubiquitous webhook-driven per-shop side effects are in Shopify apps, and that this requires no access to `client_secret`, access tokens, or privileged accounts, this is a realistically reachable, moderate-likelihood path.

### Recommendation
Bind the header-derived identity fields into the HMAC-verified material rather than trusting them independently. For example:
- Extend `to_signable_string` (or add a separate verification step) that includes `shop`, `topic`, and `webhook_id` alongside the raw body so tampering with any of them invalidates the HMAC, or
- Have `Registry.process` cross-check the header-derived `shop` against a shop known to be registered for that specific webhook subscription before invoking the handler, and document clearly that `data.shop` is not authenticated by the HMAC on its own.

### Proof of Concept
1. App A is installed on `attacker-shop.myshopify.com` and legitimately registers an `orders/create` webhook.
2. Shopify sends a webhook with raw body `B` and header `shopify-hmac-sha256: H`, where `H = HMAC(secret, B)`. This is a genuine `(B, H)` pair the attacker/merchant has full access to (their own browser/network can observe it, or their own server logs it).
3. Attacker replays a new HTTP request to the app's same webhook endpoint reusing raw body `B` and header `shopify-hmac-sha256: H` unchanged, but sets `shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `shopify-webhook-id`).
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` recomputes HMAC over `@raw_body` (`B`) only and it matches `H`, so validation passes [6](#0-5) .
5. `Registry.process` invokes `handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))`, and any app logic keyed on `data.shop` (as the docs recommend) now operates against the victim shop's tenant using attacker-controlled body content.
