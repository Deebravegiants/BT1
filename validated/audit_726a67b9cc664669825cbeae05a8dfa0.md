### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing tenant spoofing of processed webhook data - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates the webhook HMAC only against the raw request body, then hands the caller a `WebhookMetadata` struct whose `shop` field is read directly from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, never bound to the HMAC-verified payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` computes/compares the HMAC exclusively over that signable string [2](#0-1) . The `shop` accessor, however, is read straight from the `shop-domain` header, which is never part of the signed material [3](#0-2) .

`Registry.process` verifies the HMAC and then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`, `request.api_version`) to build `WebhookMetadata`, which is passed to the app's handler as the tenant identity for this event: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))` [4](#0-3) . `WebhookMetadata.shop` is a plain `String` field with no further validation [5](#0-4) .

The binding that should hold is:
`hmac_verified_bytes == bytes_that_determine_tenant_and_routing`

but in this code it is actually:
`hmac_verified_bytes (raw_body only) != bytes_used_for_tenant_identity (shop header, unauthenticated)`

Because the HMAC only covers the JSON body and not the headers, any party who can produce one genuinely-signed webhook request (e.g., a merchant who installs the app on their own store, `shop-A.myshopify.com`, and captures a real Shopify-delivered webhook, which includes a valid HMAC over that specific body) can resend the exact same body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a different shop, `shop-B.myshopify.com`. The HMAC check still passes (it only checks the body), and `Registry.process` forwards `shop: "shop-B.myshopify.com"` to the handler together with shop-A's body data.

### Impact Explanation
This breaks the tenant/identity binding on which the host application relies to route webhook data and to select per-shop credentials/state. If the host app uses `WebhookMetadata#shop` to decide which merchant record/session/access token an event applies to (as the built-in `WebhookMetadata` struct is explicitly designed for), an attacker-controlled `shop` value lets one tenant's webhook payload be attributed to (and processed under) a different tenant, i.e. cross-tenant data confusion facilitated entirely by this gem's own webhook-processing API. This matches the "Critical – cross-tenant access" impact category, since the field that binds a verified payload to a specific merchant is not covered by the same authentication mechanism (HMAC) that verifies the payload's integrity.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one genuinely-signed webhook (trivial for any merchant who installs the app on their own shop and captures Shopify's webhook delivery), and requires the host app to trust `WebhookMetadata#shop` for tenant routing without independent verification — which is the documented, intended use of this field. No access token, `client_secret`, or privileged access is needed; the attacker only replays an HTTP request they already legitimately received, with one header modified.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-signed material, or independently verify that the `shop-domain` header matches a shop that Shopify's signature can be shown to originate from before exposing it to the handler. At minimum, document that `WebhookMetadata#shop` is unauthenticated and must not be used for tenant identification without additional verification, or have `Registry.process` cross-check the header-derived shop against something bound to the signed body (e.g., the app should be required to pass the expected shop and the library should assert equality) before dispatching to the handler.

### Proof of Concept
1. Install the target app on `shop-a.myshopify.com` and capture a real webhook POST from Shopify: body `B`, headers including `x-shopify-hmac-sha256: H` (valid HMAC of `B`) and `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Replay this exact POST to the app's webhook endpoint, changing only `x-shopify-shop-domain` to `shop-b.myshopify.com`.
3. `HmacValidator.validate` recomputes HMAC over the unchanged body `B` and it matches `H`, so `Registry.process` proceeds [6](#0-5) .
4. The handler receives `WebhookMetadata` with `shop == "shop-b.myshopify.com"` and `body == B` (shop-a's data), demonstrating that shop-a's payload has been attributed to shop-b purely because the `shop` header is outside the HMAC's protection.
