Audit Report

## Title
JWT replay-guard TOCTOU race in HTTP Trigger gateway allows duplicate workflow trigger execution - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

## Summary
`WorkflowMetadataHandler.Authorize` checks JWT replay status via `jwtCache.isReplay()` and records usage via `jwtCache.recordUsage()` as two separate, non-atomic critical sections guarded by independent lock acquisitions on `jwtReplayCache.mu`. This creates a genuine check-then-act race window: two concurrent requests carrying the identical single-use JWT can both observe `isReplay == false` before either calls `recordUsage`, allowing the same JWT to authorize two (or more) workflow trigger dispatches.

## Finding Description
`Authorize` calls `h.jwtCache.isReplay(claims.ID)` under a read lock at [1](#0-0) , releasing the lock immediately after the membership check. Only after subsequent authorized-key validation does it call `h.jwtCache.recordUsage(claims.ID)` under a separate write-lock acquisition at [2](#0-1) . The underlying `isReplay`/`recordUsage` methods confirm these are two distinct, non-atomic lock sections: [3](#0-2) .

This is reachable directly from `HandleUserTriggerRequest → authorizeRequest → WorkflowMetadataHandler.Authorize` on every inbound HTTP trigger request: [4](#0-3) , with `authorizeRequest` calling `Authorize` directly: [5](#0-4) .

The one existing deduplication mechanism, `setupCallback`'s `requestID` uniqueness check, does not close this gap: it keys on the client-supplied `req.ID`, not the JWT `jti`, at [6](#0-5) . An attacker sending the same JWT with two different `requestID` values bypasses that check entirely while still hitting the JWT race in `Authorize`.

The codebase's own vault capability demonstrates the correct atomic pattern for the identical problem: `RequestReplayGuard.CheckAndRecord` performs lookup-and-insert under a single mutex acquisition [7](#0-6) , and this design is validated by a dedicated concurrency test (`TestRequestReplayGuard_ConcurrentAccess`), for which `jwtReplayCache` has no analog.

## Impact Explanation
An attacker holding a single valid signed JWT for one workflow trigger (the same precondition needed to trigger the workflow once at all) can fire it concurrently to get the trigger dispatched to the DON more than once. This breaks the intended single-use/exactly-once guarantee of the replay cache, resulting in duplicate/unauthorized workflow executions and potential duplicate side effects (e.g., duplicate on-chain actions). This maps to the in-scope "unauthorized job run" impact category, since it is a concrete authentication/replay-protection bypass reachable by an unprivileged external actor with no operator or admin access required.

## Likelihood Explanation
Exploitation requires only possession of one valid JWT (already needed to trigger the workflow at all) and the ability to send it twice concurrently over HTTP — no special network position, credentials, or cooperation from the node operator. The race window is bounded by map lock hold time (very short), but it is real, deterministic under concurrent load, and trivially reproducible with a Go test spawning two goroutines calling `Authorize` with the same JWT.

## Recommendation
Combine `isReplay` and `recordUsage` into a single atomic `CheckAndRecord(jti)`-style method guarded by one lock acquisition, following the pattern already used in `vault.RequestReplayGuard.CheckAndRecord`. Call this single method once from `Authorize` instead of the separate `isReplay`/`recordUsage` calls, and add a concurrency test analogous to `TestRequestReplayGuard_ConcurrentAccess` asserting exactly one of N concurrent identical-JWT requests succeeds.

## Proof of Concept
1. Obtain one valid JWT for an HTTP Trigger workflow request (`jti = X`).
2. Spawn two goroutines that each call `WorkflowMetadataHandler.Authorize(workflowID, token, req)` with the same JWT, with a small synchronization point ensuring both pass `isReplay` before either calls `recordUsage` (or simply run under `-race`/high concurrency to reproduce naturally).
3. Observe both calls return `(key, nil)` without error, indicating the same single-use JWT authorized two separate trigger dispatches — verifiable via a unit test analogous to `TestRequestReplayGuard_ConcurrentAccess` but targeting `jwtReplayCache`/`Authorize`, asserting that more than one call succeeds.

```go
func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}
```

```go
func (h *httpTriggerHandler) authorizeRequest(ctx context.Context, workflowID string, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback) (*gateway_common.AuthorizedKey, error) {
	h.lggr.Debugw("authorizing request", "workflowID", workflowID, "requestID", req.ID)
	key, err := h.workflowMetadataHandler.Authorize(workflowID, req.Auth, req)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInvalidRequest, "Auth failure: "+err.Error(), callback)
		return nil, errors.Join(errors.New("auth failure"), err)
	}
	return key, nil
}
```

```go
func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
```
