### Title
Duplicate `address(0)` entries in `erc20TokenAddresses` let `Hinkal.transact` double-count `msg.value`, minting unbacked shielded ETH - (File: contracts/Hinkal.sol)

### Summary
`Hinkal.transact` computes `balanceDif` per index of `circomData.erc20TokenAddresses` and, for every index equal to `address(0)`, adds the full `msg.value` again on top of the raw balance delta [1](#0-0) . Because nothing in `dimensionsCheck`/`performHinkalChecks` enforces uniqueness of token addresses across slots, an attacker can list `address(0)` twice, causing `msg.value` to satisfy two independent per-slot balance equations instead of one, letting a single real ETH deposit back two separate shielded ETH outputs.

### Finding Description
The equality that must hold is: **real ETH received by the contract in this call (`msg.value`) == sum of ETH-backed accounting terms (`amountChanges` + `utxoAmount`) attributed across all `address(0)` slots**. The code breaks this by re-adding `msg.value` once per matching index rather than once per unique token.

Trace:
- `transact` snapshots `oldBalances`/`newBalances` via `getBalancesForArray(circomData.erc20TokenAddresses)`, which reads `address(this).balance` once per array entry, so duplicate `address(0)` entries just read the identical balance twice [2](#0-1) .
- In `_internalTransact`, for a deposit slot (`deltaAmountChange > 0`), `transferERC20TokenFromOrCheckETH(address(0), ..., address(this), amount)` only asserts `msg.value == amount`; it performs no actual transfer and does not track/consume `msg.value`, so the same check can pass independently for every duplicated `address(0)` slot with `amount == msg.value` [3](#0-2) [4](#0-3) .
- Back in `transact`, for every index `i` where `erc20TokenAddresses[i] == address(0)`: `balanceDif = newBalances[i] + msg.value - oldBalances[i]`. Since `newBalances[i0]==newBalances[i1]` and `oldBalances[i0]==oldBalances[i1]` for duplicated indices, both slots get the identical `balanceDif == msg.value` (assuming no other ETH movement) [5](#0-4) .
- The core balance equation is checked per index: `balanceDif == (onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount(i)` [6](#0-5) . With `balanceDif == msg.value` at both duplicate indices, the attacker can set `amountChanges[i0] = msg.value` (real deposit, backed) and `amountChanges[i1] = msg.value` (a second, unbacked "deposit") and both checks pass, because the check never verifies that the *same* real ETH isn't being claimed twice.

The attacker's exact call: submit `Hinkal.transact` with `dimensions.tokenNumber = 2` (or more), `erc20TokenAddresses = [address(0), address(0)]`, `amountChanges = [msg.value, msg.value]`, `onChainCreation = [false, false]`, `slippageValues` set to permissive values, `inputNullifiers` for both slots set to all-zero (valid for pure-deposit slots since `checkOnchainCreation` only forces zero nullifiers when `onChainCreation==true`), and `outCommitments`/`encryptedOutputs` containing two freshly-generated commitments of value `msg.value` each, owned by the attacker. Since the attacker fully controls circuit inputs and can generate their own valid proof, the circuit's per-slot equation (`inTotal[i] + amountChanges[i] === outTotal[i]`) is trivially satisfiable for both slots independently — the circuit has no notion that two slots share the same underlying token/balance.

None of the existing guards catch this: `dimensionsCheck` only validates array-length equality, never address uniqueness [7](#0-6) ; `performHinkalChecks`/`checkOnchainCreation` likewise never inspect for duplicate token entries [8](#0-7) ; `getBalancesForArray` naively re-reads the same global balance per index without deduplication [9](#0-8) .

### Impact Explanation
An attacker deposits `X` real wei once but mints `2X` (or `N*X` with `N` duplicate `address(0)` slots) worth of shielded ETH commitments backed by only `X` real ETH in the contract. This is direct minting of shielded value without backing, causing protocol insolvency once the extra shielded ETH is later withdrawn by the attacker — matching the "Critical: minting shielded value without backing" category. The attack is fully repeatable per transaction and scales with the number of duplicate entries (bounded only by gas/array-size limits), so an attacker can drain the pool by repeating the call.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs to be able to call `transact` (any unprivileged depositor can), craft `CircomData` with duplicate `address(0)` entries, and generate a valid proof for their own chosen public inputs (explicitly within attacker capability per the rules). No special tree state, no relay privilege, and no reliance on other users' funds are required — cost is just the real ETH deposited once, `X`, for a mint of `N*X`. This is highly feasible and repeatable.

### Recommendation
Deduplicate `erc20TokenAddresses` before or during the balance-verification loop in `Hinkal.transact`: compute the real balance delta once per unique token address (as `_calcTokenChangesForProoflessDeposit`/`_handleTransfersFromProoflessDeposit` already do for `prooflessDeposit`), add `msg.value` exactly once to the ETH term, and then distribute/require the sum of `amountChanges[i] + utxoAmount(i)` across all indices sharing that token address to equal that single delta. Alternatively, explicitly reject duplicate entries in `erc20TokenAddresses` inside `dimensionsCheck`/`performHinkalChecks`.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal` + `HinkalHelper` with a real Merkle/Poseidon setup (or the project's existing test harness) and a working local proof generator (snarkjs/circom artifacts from the repo, as permitted).
2. Craft `CircomData` with `dimensions.tokenNumber = 2`, `erc20TokenAddresses = [address(0), address(0)]`, `amountChanges = [X, X]`, `onChainCreation = [false, false]`, `inputNullifiers = [[0],[0]]`, two fresh `outCommitments` of amount `X` each owned by the attacker, permissive `slippageValues`, `originalSender = attacker`, `relay = address(0)`.
3. Generate a valid Groth16 proof for these public inputs using the attacker's own witness.
4. Call `hinkal.transact{value: X}(a, b, c, dimensions, circomData)`.
5. Assert both balance equations in the loop pass (tx succeeds) and record `address(this).balance` delta == `X`.
6. Assert the sum of value across the two newly inserted off-chain commitments (the attacker's minted UTXOs) == `2*X`.
7. Assertion of the broken equality: `address(this).balance_after - address(this).balance_before (== X)` != `sum(amountChanges) + sum(utxoAmount) (== 2X)`, proving unbacked minting.

    function checkOnchainCreation(
        CircomData calldata circomData
    ) internal pure {
        bool isInternalTransaction = circomData
            .externalActionData
            .externalActionId == 0;

        for (uint i = 0; i < circomData.onChainCreation.length; i++) {
            if (circomData.onChainCreation[i]) {
                require(
                    !isInternalTransaction,
                    "onChainCreation not allowed for internal transactions"
                );
                require(
                    circomData.amountChanges[i] == 0,
                    "amountChanges must be zero when onChainCreation is true"
                );
                for (
                    uint j = 0;
                    j < circomData.inputNullifiers[i].length;
                    j++
                ) {
                    require(
                        circomData.inputNullifiers[i][j] == 0,
                        "inputNullifiers must be zero when onChainCreation is true"
                    );
                }
            }
        }
    }

    ///@notice make performance checks for transactions
    ///@dev Check if transacaction is valid before making it

    function performHinkalChecks(
        CircomData calldata circomData,
        Dimensions calldata dimensions,
        address sender
    ) external view returns (uint256[] memory) {
        require(
            (circomData.originalSender == address(0) &&
                circomData.relay != address(0)) ||
                (circomData.originalSender == sender &&
                    circomData.relay == address(0)),
            "invalid value for originalSender"
        );

        require(
            CircomDataBuilder.getHashedCalldata(circomData) ==
                circomData.calldataHash,
            "Calldata Hash Integrity Check Failed"
        );
        relayerIsValid(circomData.relay);
        dimensionsCheck(circomData, dimensions);
        checkOnchainCreation(circomData);

        return
            CircomDataBuilder.formInputForCircom(
                block.chainid,
                hinkalAddress,
                circomData
            );
    }
