### Title
Webhook `shop` tenant identifier is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` value from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature that `Registry.process` validates only covers the raw request body. Because the header is not bound into the signed content, any party who can obtain one validly-signed webhook payload (e.g., a merchant who installs the app and receives webhooks for their own store) can replay that exact body to the app's webhook endpoint while substituting a different shop domain in the header. The HMAC check still passes, and the host application dispatches the handler with an attacker-chosen `shop`, breaking the tenant boundary the app relies on for routing/authorization of webhook data.

### Finding Description
`Utils::HmacValidator.validate` computes and compares an HMAC over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` is defined to be only the raw HTTP body, while `shop` is read from a header that is completely outside of what gets signed: [2](#0-1) 

`Registry.process` validates the HMAC of the request and then trusts `request.shop` (from the unsigned header) as the tenant identity to build `WebhookMetadata` passed to the app's handler: [3](#0-2) 

This breaks the intended identity binding: `shop_header_used_for_tenant_dispatch == shop_that_the_HMAC_actually_authenticates`. Before an attack: a legitimate webhook for shop A arrives with header `shop-domain: A` and a body whose HMAC is valid for secret `api_secret_key`. After the attack: the attacker replays the identical body but with header `shop-domain: B`. `Utils::HmacValidator.validate` still returns `true` because it never inspects the header, so `Registry.process` proceeds and calls the handler with `shop: "B"` even though the signed content was never associated with shop B by Shopify.

### Impact Explanation
An unprivileged internet user who has legitimately installed the app on their own store (a normal, low-privilege action — no `api_secret_key`, access token, or leaked credential is required) can capture a webhook payload Shopify sends them, which is validly HMAC-signed with the app's shared secret for arbitrary future replay. That user can then forge requests to the app's public webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header value, causing the host application (any consumer built on `ShopifyAPI::Webhooks::Registry.process`) to process webhook content under a `shop` value the attacker controls. Depending on how the host app keys data on `WebhookMetadata#shop` (order data ingestion, GDPR `customers/redact` / `shop/redact` processing, cache invalidation, billing state, etc.), this enables cross-tenant data injection or corruption — writing/replaying one tenant's data or mandatory-compliance events into another tenant's context. This matches the "cross-tenant access" Critical impact category since the attacker crosses a tenant boundary using only their own valid installation, without stealing any other party's credentials.

### Likelihood Explanation
Likelihood is significant: the attacker only needs to install the app once (a normal, no-privilege action), capture one webhook body they legitimately received, and replay it with a modified header to the app's public webhook endpoint. No secret material, TLS interception, or victim credentials are needed — the header is not authenticated at all, so any value can be supplied.

### Recommendation
Bind the tenant identity into the signed material, or independently verify it. Concretely:
- Include the `shop-domain` (and ideally `topic`/`webhook-id`) header value in `Webhooks::Request#to_signable_string`, matching how Shopify actually computes/expects the signature scope, or
- Have `Registry.process` cross-check `request.shop` against known/expected values for the delivery (e.g., reject if the shop hasn't previously completed OAuth with this app, or require the caller to supply the expected shop out-of-band and compare it), and treat header-derived `shop` as untrusted until corroborated by the signed body content.

### Proof of Concept
1. Attacker installs the app for `attacker-shop.myshopify.com` and receives a legitimate webhook: body `B`, headers including `X-Shopify-Hmac-Sha256: <valid-hmac-for-B>` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker resends the exact same body `B` and the same valid `X-Shopify-Hmac-Sha256` header to the app's webhook endpoint, but replaces `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body normally (all required headers present).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `@raw_body` (`to_signable_string`), not the shop header: [4](#0-3) 
5. `Registry.process` proceeds to call the registered handler with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body, even though Shopify never issued this webhook for `victim-shop.myshopify.com`: [5](#0-4)

          received_signature = verifiable_query.hmac
