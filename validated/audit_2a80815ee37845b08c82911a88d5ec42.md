### Title
IntentGatewayV2 escrow deposit and settlement functions have no pause/circuit-breaker gate, unlike every other HyperApp in the codebase - (File: evm/src/apps/IntentGatewayV2.sol)

### Summary
Every other cross-chain application contract in this codebase (`HyperFungibleToken`, `HyperFungibleTokenUpgradeable`, `WrappedHyperFungibleToken`, `WrappedHyperFungibleTokenUpgradeable`, `HyperbridgeLzEndpoint`) consistently gates its fund-moving entry points (`send`, `onAccept`, `onPostRequestTimeout`, `transfer`) with a `whenNotPaused` modifier so an owner can halt the contract in an emergency. `IntentGatewayV2.sol`, the contract that escrows user funds for cross-chain intents (`placeOrder`, `fillOrder`, `onAccept` for `RedeemEscrow`/`RefundEscrow`), has no `whenNotPaused`, `Pausable`, or `_paused` state at all.

### Finding Description
Grepping `evm/src/apps/IntentGatewayV2.sol` for `whenNotPaused|_paused|Pausable|pause()` returns no matches. The contract's constructor documents an "Privileged admin for future upgrade-gated actions (e.g. pausing)" [1](#0-0)  but no such pause mechanism is wired into `placeOrder`, `fillOrder`, or `onAccept`. A project changelog entry confirms this was deliberate and explicitly notes the paused getter was unused and never actually declared in the gateway: [2](#0-1) 

By contrast, every sibling HyperApp gates its analogous deposit/mint/receive paths: [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

This mirrors the C4 finding's bug class exactly: a fund-accepting entry point (`deposit`/escrow) that is missing the pause check present on its sibling functions, allowing deposits/settlement to proceed even when the protocol operator has determined operations must halt.

### Impact Explanation
`IntentGatewayV2.placeOrder` locks user tokens into escrow, and `onAccept` releases that escrow to fillers/solvers or refunds it based on relayed ISMP messages (`RedeemEscrow`/`RefundEscrow`). If any exploitable bug is later found in the escrow accounting, commitment hashing, protocol-fee computation, or relayer-authorization logic of this contract (several of which are independently complex, e.g., fee-on-transfer handling, partial fills, protocol fee deduction), the admin has no way to halt new escrow deposits (`placeOrder`) or settlements (`fillOrder`/`onAccept`) while a fix is prepared — unlike `HyperFungibleToken` and `HyperbridgeLzEndpoint`, whose owners can immediately call `pause()` to stop `send`/`onAccept`. This is a freezing/loss-of-funds amplifier: an in-progress exploit or a discovered critical bug in the intents flow cannot be stopped at the contract level, only by disabling relayers or the host globally (which does not stop `placeOrder`, since that path never calls the host/dispatcher for the deposit itself).

### Likelihood Explanation
Likelihood of the missing gate being exercised is effectively 100% in any incident scenario since `placeOrder` and `fillOrder` are always open to any address by design; the absence of a pause switch means there is no mitigation and no way to reduce likelihood of continued exploitation once a bug is found, only after-the-fact global measures (e.g., freezing the host, which does not affect same-chain flows like `placeOrder` or `fillOrder` that don't require the host to dispatch).

### Recommendation
Add `Pausable`/`whenNotPaused` (or an equivalent `_paused` flag gated behind the immutable `_owner`) to `IntentGatewayV2`, applied to `placeOrder`, `fillOrder`, and the escrow-redemption/refund branches inside `onAccept`, consistent with the pattern already used in `HyperFungibleToken`, `WrappedHyperFungibleToken`, and `HyperbridgeLzEndpoint`. If EIP-170 size constraints are the reason it was dropped, consider moving pause state to a separate minimal storage slot check (a single `bool` + revert) rather than the full OZ `Pausable` import, to keep bytecode size down while still providing an emergency stop.

### Proof of Concept
1. Deploy `IntentGatewayV2` per `evm/tests/foundry/IntentGatewayV2Test.sol` setup.
2. Discover/simulate any bug in escrow settlement (e.g., a fee-accounting or commitment-hash mismatch) that permits a solver to redeem more escrow than was legitimately owed.
3. Attempt to call the contract's pause mechanism to halt further `placeOrder`/`fillOrder` calls while investigating — there is no such function; `grep -n "whenNotPaused\|Pausable\|_paused" evm/src/apps/IntentGatewayV2.sol` returns nothing.
4. Users and solvers can continue to call `placeOrder`/`fillOrder` indefinitely, continuing to escrow and drain funds through the exploitable path, because unlike `HyperFungibleToken.send`/`onAccept`, `IntentGatewayV2` has no `pause()`/`whenNotPaused` to stop it.
