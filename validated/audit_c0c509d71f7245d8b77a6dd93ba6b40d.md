### Title
Webhook `shop`, `topic`, `webhook_id` and `api_version` are trusted by `Webhooks::Registry.process` without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw HTTP body [1](#0-0) , so `Utils::HmacValidator.validate` verifies the HMAC over the body alone [2](#0-1) . The `shop`, `topic`, `webhook_id`, and `api_version` values, read directly from unauthenticated HTTP headers [3](#0-2) , are never bound to that signature. `Webhooks::Registry.process` nonetheless treats these header-derived fields as authenticated tenant identity when it dispatches to the handler [4](#0-3) .

### Finding Description
This mirrors the report's bug class: one code path (`transfer()`) enforces an invariant while a sibling path (`transferFrom()`) omits it, breaking an identity binding. Here the binding that should hold is:

`request.hmac verified == (body, shop, topic) that Registry.process trusts`

but the actual implementation only enforces:

`request.hmac verified == body`

`Request#hmac` is computed from the `shopify-hmac-sha256`/`x-shopify-hmac-sha256` header [5](#0-4) , and `to_signable_string` returns only `@raw_body` [6](#0-5) . `HmacValidator.validate` computes the signature purely over that signable string with the app's shared `api_secret_key` [2](#0-1) . Because Shopify uses the same app-level secret for every shop that installs the app, a given `(body, hmac)` pair is valid for that body regardless of which shop it is attributed to.

`Registry.process` calls `Utils::HmacValidator.validate(request)` and, once it passes, unconditionally forwards `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` — all read from headers that are not part of the signed material — into `WebhookMetadata` handed to the app's handler [4](#0-3) [7](#0-6) . The library exposes no mechanism for the host app to detect that these fields were forged; the passing HMAC check is presented as proof of authenticity for the whole request, when it only authenticates the body bytes.

### Impact Explanation
This is a cross-tenant identity confusion: an unprivileged party who installs the multi-tenant app on their own shop legitimately receives real webhooks with valid `(body, hmac)` pairs signed with the app's shared `api_secret_key`. Because the `shop` header is not covered by the signature, that same attacker can POST the identical body/HMAC to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` (and/or `shopify-topic`, `webhook-id`) header for a victim shop. `Registry.process` will validate the HMAC (it only checks the body) and pass the forged `shop`/`topic` through to the handler as if it were an authenticated fact about the sender. Any host application that uses `WebhookMetadata#shop` to select which tenant's data/session to update — the intended and documented use of this field — can be tricked into attributing attacker-supplied data to another shop, i.e., cross-tenant access/injection. This satisfies the "cross-tenant access" Critical impact bucket.

### Likelihood Explanation
Webhook endpoints are, by design, public HTTP endpoints with no authentication other than the HMAC check that this gem performs; an attacker only needs to be an app installer (unprivileged, no special credentials, no access token or `client_secret` required) to obtain a valid `(body, hmac)` pair and replay it with a different `shop`/`topic` header value against the same endpoint. Likelihood is moderate-to-high wherever the host app trusts `WebhookMetadata#shop`/`#topic` for tenant routing, which is the standard usage pattern documented for this library.

### Recommendation
Include `shop`, `topic`, and `webhook_id`/`api_version` in the signable string (or otherwise cryptographically bind them to the HMAC/secret verification), analogous to how `Auth::Oauth::AuthQuery#to_signable_string` binds `shop` into its signed payload [8](#0-7) . At minimum, `Webhooks::Registry.process` should not treat header-derived `shop`/`topic` as verified identity when only the body has been authenticated; document this clearly, or require the host app to independently confirm the shop against a value obtained through an already-authenticated channel (e.g., session) before trusting it.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com`. Shopify sends a real webhook to the app's public endpoint with body `B` and header `shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker records `(B, H)` and issues a new POST to the same endpoint with:
   - Body: `B` (unchanged)
   - Header `shopify-hmac-sha256: H` (unchanged)
   - Header `shopify-shop-domain: victim.myshopify.com` (forged)
3. `Webhooks::Request.new` parses headers/body normally [9](#0-8) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(api_secret_key, B)` and compares against `H` — it matches because only the body is signed [10](#0-9) .
5. `Registry.process` builds `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` and invokes the handler, which believes this data legitimately originates from `victim.myshopify.com` [11](#0-10) .

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
