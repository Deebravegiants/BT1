### Title
Webhook HMAC does not bind the `shop-domain` header, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable representation from the raw request body only, while the shop identity used to route and process the webhook is read from an unauthenticated header. This breaks the equality `hmac_verified_bytes == bytes_that_determine_tenant`, letting an attacker who legitimately receives one valid webhook (e.g., for their own shop) replay it against the same endpoint with a forged `shop-domain`/`x-shopify-shop-domain` header, causing the app to process attacker-controlled webhook data under a victim shop's identity.

### Finding Description
`Webhooks::Registry.process` authenticates an inbound webhook solely via: [1](#0-0) 
```
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
``` [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string`: [2](#0-1) 

and `Webhooks::Request#to_signable_string` returns **only the raw request body**: [3](#0-2) 

Meanwhile, the shop identity that is forwarded to the handler as the tenant context comes from an HTTP header that is never part of the signed material: [4](#0-3) 

So the binding the code implicitly assumes — "HMAC-authenticated bytes == the shop this webhook belongs to" — does not hold. Shopify's genuine webhook HMAC is computed only over the body for a given shop/topic pair, but nothing in this gem cryptographically ties that body+HMAC pair to the `shop-domain` header value that the host application will use to select the tenant/session. An attacker who legitimately receives (or triggers) one real webhook delivery for their own store — a completely unprivileged action, since any merchant can install a public app and receive webhooks for their own shop — obtains a `(raw_body, hmac)` pair that is valid for that body regardless of the `shop-domain` header. Because `HmacValidator.validate` never inspects `request.shop`, the attacker can POST the same body and the same HMAC to the app's webhook endpoint while substituting an arbitrary victim `shop-domain` header. `Registry.process` will accept it (`HmacValidator.validate(request)` succeeds because it only checks the body) and pass `shop: request.shop` (the forged victim shop) to the handler.

### Impact Explanation
This is a cross-tenant identity-binding break: verified bytes (body) are decoupled from the identity field host applications rely on (`WebhookMetadata#shop`) to select which tenant/session the webhook payload is applied to. Any host application built on this gem that trusts `data.shop` from `WebhookMetadata` — the documented and expected usage — can be made to ingest attacker-supplied payload content attributed to a shop the attacker doesn't own, corrupting or forging data (e.g., customer/order/redact records) under another merchant's tenant.

### Likelihood Explanation
High: `shop-domain` is a plain, attacker-controlled HTTP header on the same request the attacker constructs; no secret material is required beyond obtaining any one legitimate `(body, hmac)` pair, which is trivially available to any merchant with the app installed on their own store (an unprivileged actor by the rules of this exercise).

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signed material verified for webhooks, or otherwise cryptographically bind `request.shop` to the HMAC before it is trusted — e.g., verify the HMAC using a canonicalized string that incorporates the header value, or independently confirm the resolved shop belongs to an existing offline session before dispatching the webhook to the handler.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com` and captures a real webhook delivery: raw body `B` with header `X-Shopify-Hmac-Sha256: H` (valid because `HmacValidator` only signs `B`).
2. Attacker POSTs to the app's webhook endpoint with the same body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Webhooks::Request#hmac` and `#to_signable_string` only look at `B`, so `Utils::HmacValidator.validate(request)` returns `true`. [5](#0-4) 
4. `Registry.process` proceeds and invokes `handler.handle(data: WebhookMetadata.new(..., shop: "victim.myshopify.com", body: JSON.parse(B), ...))`, so the host app processes attacker-chosen content under the victim shop's identity. [1](#0-0)
