### Title
Webhook shop-domain and topic headers are trusted for handler dispatch but are not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `api_version`, and `webhook_id` from HTTP headers, but the HMAC signature validated by `ShopifyAPI::Webhooks::Registry.process` only covers the raw request body, not these headers. This breaks the identity binding: `shop header == shop that produced the signed bytes`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` computes/compares the HMAC solely against that signable string using the app's single, shop-independent `api_secret_key` [2](#0-1) . Meanwhile, `Request#shop` and `Request#topic` are read directly from the `shopify-shop-domain` / `shopify-topic` headers, which are never part of the signed bytes [3](#0-2) .

`Registry.process` validates the HMAC and then immediately dispatches to the topic handler using the unauthenticated `request.shop` and `request.topic` values, with no cross-check that the shop actually matches the tenant the body was generated for: [4](#0-3) 

Because the same `api_secret_key` signs webhook bodies for every shop that has the app installed, any merchant that has installed the app can obtain a validly-signed `(raw_body, hmac)` pair for their own shop (e.g. by triggering a webhook event on their own store) and then replay that exact body/HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` (and/or `shopify-topic`) header with a victim shop's domain. `HmacValidator.validate` will still pass, because it only checks the body bytes, and `Registry.process` will hand the handler a `WebhookMetadata` object claiming the victim's `shop` with attacker-controlled body content.

### Impact Explanation
This is a cross-tenant identity-binding break: the tenant identifier (`shop`) used to route/attribute webhook data is not bound to the same signed bytes that authenticate the request. Any handler that trusts `WebhookMetadata#shop` as the source of truth for which merchant the payload belongs to (a normal and encouraged usage pattern per this library's own webhook API) can be made to process attacker-supplied data under a victim shop's identity - i.e., cross-tenant data injection/spoofing, which maps to the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only an unprivileged attacker who can install the app on their own shop (any public app listing satisfies this) and control the HTTP request to the app's webhook endpoint - no `api_secret_key`, access token, or privileged account is needed. The attacker never needs to forge an HMAC; they replay a genuinely valid one and swap an unsigned header. This is fully within the "unprivileged internet user" threat model of the prompt.

### Recommendation
Include the `shop` (and ideally `topic`) header value inside the HMAC-signable material, or explicitly document/require that `Registry.process` (or downstream handlers) independently authenticate `request.shop` against a value derived from data that Shopify actually signs (e.g., verifying the shop is one that legitimately has an active session/registration for that specific webhook subscription id) before trusting it for tenant attribution.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook event (e.g., `orders/create`) on their own shop, capturing the POST body `B` and the valid `x-shopify-hmac-sha256` value `H` (computed with the app's `api_secret_key` over `B`).
3. Attacker replays `POST /webhooks` with body `B`, header `x-shopify-hmac-sha256: H` (unchanged, still valid since `HmacValidator` only checks `B`), but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` passes because it only validates `B` against `H`. `Registry.process` dispatches to the handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"` and `body == B` (attacker-controlled), even though the victim shop never sent this webhook. [5](#0-4)

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
