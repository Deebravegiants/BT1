### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing shop-attribution spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw HTTP body (`to_signable_string` returns `@raw_body`) via `Utils::HmacValidator.validate`, but the `shop` value used to attribute the webhook to a tenant is read from the `X-Shopify-Shop-Domain` header, which is never included in the HMAC-signed material. This breaks the identity binding: `hmac(raw_body) == valid` is treated as proof that `shop-domain header == the shop that sent this payload`, which is false.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns `@raw_body`: [1](#0-0) 

Meanwhile `shop` is parsed straight from an unauthenticated header and exposed as a first-class accessor used for tenant identification: [2](#0-1) 

`Registry.process` validates the HMAC (which only covers `raw_body`) and then immediately trusts `request.shop` (and `request.topic`, `request.api_version`, `request.webhook_id`, all header-derived and unsigned) to build the metadata handed to the app's handler: [3](#0-2) 

`WebhookMetadata` treats `shop` as a trusted, verified field for the handler to act on: [4](#0-3) 

The `HmacValidator.validate` call only ever recomputes and compares against `to_signable_string`, i.e. the raw body — it has no knowledge of, and does not bind, the shop-domain header: [5](#0-4) 

Because `shop` is excluded from the signed content, any unprivileged internet user who possesses one valid `(raw_body, hmac)` pair for a given topic — which they can trivially obtain by installing the app on their own store and triggering a webhook to their own publicly reachable endpoint — can resend that exact same body/HMAC pair to the app's webhook endpoint while substituting an arbitrary value in the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header. `Registry.process` will pass HMAC validation (since the body/HMAC pair is genuinely valid) and will hand the app's handler a `WebhookMetadata` claiming the payload came from the attacker-chosen `shop`, breaking the binding `authenticated_body == shop_domain_claimed`.

### Impact Explanation
This is a cross-tenant identity confusion: the gem hands host applications data that is only partially authenticated, with the tenant-identifying field (`shop`) fully attacker-controlled while looking verified (it arrived after `HmacValidator.validate` succeeded). Any host application that follows the documented pattern of using `WebhookMetadata#shop` to select which merchant record to update (a reasonable and expected usage, e.g., for `shop/redact`, `customers/redact`, `customers/data_request`, or any per-shop data sync) can be tricked into applying webhook-driven mutations under an arbitrary shop's identity, i.e., cross-tenant access to another merchant's records via data attributed to the wrong tenant.

### Likelihood Explanation
Likelihood is high for any app that receives webhooks for more than one shop (which is the normal SaaS multi-tenant case): the attacker only needs their own legitimate install (or any store on which they can trigger any webhook topic) to obtain a valid `(body, hmac)` pair, then a single unauthenticated HTTP POST with a forged header to reuse it against a different claimed shop.

### Recommendation
Do not rely on a header value that isn't part of the HMAC signature to identify the tenant. Either:
- Cross-check `request.shop` against the shop associated with the specific webhook subscription/session the app expects for that endpoint before dispatching to the handler, or
- Extend the signable payload/verification so that the shop domain is cryptographically bound (Shopify's own HMAC does not include headers, so this must be handled by deriving shop identity only from data that is verifiable, e.g. via the registered webhook's known destination, not from an unauthenticated header), or
- Document loudly, and enforce in `Registry.process`, that `WebhookMetadata#shop` must never be used for authorization/tenant-selection decisions without an additional out-of-band verification step.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers (or waits for) a webhook, e.g. `orders/create`, capturing the raw JSON body `B` and the header `X-Shopify-Hmac-Sha256: H` that Shopify sent — this `(B, H)` pair is valid because it was legitimately computed by Shopify with the app's `client_secret`.
2. Attacker sends a POST to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid), header `X-Shopify-Topic: orders/create` (unchanged), but header `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (forged).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because `to_signable_string` only compares `B` against `H`, regardless of the shop header: [6](#0-5) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and `body` from the attacker's own order, and any host app logic keyed on `data.shop` (e.g. "update this shop's latest order record") now operates as if the payload legitimately came from `victim-shop.myshopify.com`.
