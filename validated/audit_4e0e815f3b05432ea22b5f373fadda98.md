### Title
Protocol-fee-reduced amounts used for escrow but full (pre-fee) amounts used for refund/cancel withdrawal, causing over-payment / accounting mismatch - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.placeOrder` (Tron variant) computes a protocol-fee-reduced amount and stores that reduced amount as the on-chain escrow balance, but `cancelOrder` builds the refund `WithdrawalRequest` using the original, unreduced `order.inputs` amounts. This is the exact class of bug described in the analog report: a derived value (fee-adjusted amount) is applied inconsistently across call sites — some code paths use the "new" (reduced) value, others use the "old" (raw) value — causing the contract to misstate balances.

### Finding Description
In `placeOrder`, the protocol fee is deducted from each input and the *reduced* amount is what actually gets escrowed and used for the commitment hash: [1](#0-0) 
and the reduced amount is what is written into the `_orders` escrow mapping: [2](#0-1) 

However, `cancelOrder` — reachable by any order owner, an unprivileged caller — constructs the `WithdrawalRequest` for both the same-chain refund path and the cross-chain `RefundEscrow` dispatch using the raw, un-reduced `order.inputs`, not the fee-reduced amounts that were actually escrowed:

Same-chain refund: [3](#0-2) 

Cross-chain source-side cancel dispatch: [4](#0-3) 

Destination-side `RefundEscrow` dispatch: [5](#0-4) 

These `body.tokens[i].amount` values then flow into `withdraw()`, which reads `amount = body.tokens[i].amount` (the caller-supplied, unreduced figure) and only checks `_orders[body.commitment][token] == 0` for *existence*, not equality, before proceeding to redeem: [6](#0-5) 

This mirrors the reported vulnerability class precisely: `placeOrder`/escrow treats "amount after fee applied" as the canonical balance (analogous to `applyInterest` returning the new balance), while `cancelOrder` treats the raw input as the transferable amount (analogous to call sites that use `applyInterest`'s return value as only the delta/without adding). The result is a mismatch between the value actually escrowed and the value the refund path attempts to pay out.

### Impact Explanation
If `withdraw()`'s subsequent (unseen, past line 700) logic transfers `amount` (the raw, pre-fee value from `body.tokens`) to the beneficiary rather than the value actually recorded in `_orders[commitment][token]`, a cancelling order owner would receive back more than was ever escrowed for their order — the protocol fee amount that was already retained as dust — draining that surplus from the gateway's shared token balance (funded by other users' escrow). This is a concrete theft/insolvency vector: repeated cancellations would over-drain the contract, potentially leaving later legitimate withdrawals (fills or other refunds) unable to be paid — a freezing-of-funds condition for other users. Even if downstream logic clamps the transfer to the stored `_orders` value, the inconsistency between the committed/escrowed value and the value used to build the outgoing cross-chain `RefundEscrow` request risks the destination-chain storage proof / commitment verification failing (since the storage slot key is derived from `commitment`, which is hashed with the reduced inputs at `placeOrder` time but the `WithdrawalRequest.tokens` field embeds the raw amount) — potentially bricking legitimate order cancellations, a route-unable-to-deliver-message condition.

### Likelihood Explanation
High. `cancelOrder` is a normal, unprivileged, user-reachable entry point required whenever a protocol fee is non-zero (the documented default is 5–30 bps and cannot be zero for any fee-configured deployment), so the divergent code path executes on essentially every cancellation in a fee-enabled deployment.

### Recommendation
Ensure `cancelOrder` builds the `WithdrawalRequest.tokens` from the same fee-reduced amounts that were stored in `_orders[commitment][token]` at `placeOrder` time (i.e., persist/recompute `reducedInputs` the same way, or read the actual escrowed value directly from `_orders`) rather than reusing the caller-supplied `order.inputs`. Add an explicit equality/consistency assertion in `withdraw()` between `body.tokens[i].amount` and the stored `_orders[commitment][token]` value instead of only checking for non-zero, so any future divergence reverts rather than silently over/under-paying.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) with `protocolFeeBps > 0`.
2. User calls `placeOrder` with `inputs[0].amount = 1000`. Contract escrows `reducedInputs[0].amount = 1000 - fee` in `_orders[commitment][token]` (verified by the reduced-amount escrow tests in the same-chain test suite, e.g. `testProtocolFeeWith10Percent`). [7](#0-6) 
3. Before any fill, the user calls `cancelOrder` on the same chain. The `WithdrawalRequest` is built with `tokens: order.inputs`, i.e., the full pre-fee `1000`, not the escrowed `1000 - fee`.
4. `withdraw()` reads `amount = 1000` from `body.tokens[0].amount`, confirms `_orders[commitment][token] != 0`, and (per the observed code up to line 700) proceeds to redeem using this raw `amount` rather than the smaller escrowed value — over-paying the user by the protocol fee amount that was never actually held for their order.

Note: the exact transfer statement inside `withdraw()` beyond line 700 could not be retrieved before the tool budget was exhausted, so the final confirmation that the raw (rather than clamped) amount is transferred is inferred from the code shown (`uint256 amount = body.tokens[i].amount;`) and the surrounding existence-only check; a Devin session with full file access should verify lines 700+ of `evm/tron/contracts/apps/IntentGatewayV2.sol` to confirm the exact transfer amount used.
