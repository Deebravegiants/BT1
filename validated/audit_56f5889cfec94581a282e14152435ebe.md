### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , so `Utils::HmacValidator.validate(request)` proves only that the *body bytes* were signed with the app's `client_secret` — it says nothing about the `shop`, `topic`, or `webhook_id` values, which are read straight from HTTP headers [2](#0-1) . `Registry.process` validates the HMAC and then dispatches the handler using `request.shop` taken from that unauthenticated header [3](#0-2) .

### Finding Description
The identity binding that should hold is:
`shop bound by HMAC == shop the handler acts on`

In this gem it instead holds:
`bytes verified by HMAC (raw_body only) != shop-domain header used to build WebhookMetadata`

Because `to_signable_string` only covers `@raw_body` [1](#0-0) , the `shopify-shop-domain` (and `shopify-topic`/`shopify-webhook-id`) headers are fully attacker-controllable metadata that never gets checked against the signature. `Registry.process` calls `Utils::HmacValidator.validate(request)` — which recomputes the HMAC only from `to_signable_string` (the body) [4](#0-3)  — and, once that passes, immediately builds `WebhookMetadata` using `request.shop`, `request.topic`, and `request.webhook_id` straight from headers [5](#0-4) .

Any party who has legitimately received one valid `(body, hmac)` pair for a topic from Shopify — e.g., a malicious merchant/developer who installed the same app on their own store and thus has valid webhook deliveries signed with the app's shared `client_secret` — can resend that exact same body and HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` (and/or `shopify-topic`, `shopify-webhook-id`) header with a different tenant's shop domain. `HmacValidator.validate` will still return `true` because it only checks the body, and the handler will execute believing the event legitimately originates from and pertains to the victim shop.

### Impact Explanation
This breaks the tenant boundary the HMAC is meant to enforce: an app's webhook handler can be tricked into performing actions (data updates, redaction/uninstall workflows, session/tenant bookkeping keyed by shop, etc.) attributed to a shop that never sent that webhook. This is a cross-tenant confusion vulnerability — a High/Critical-class impact category (cross-tenant access) achieved purely by header manipulation, without needing the app's `client_secret`, an access token, or any privileged credential, since the attacker only needs one legitimate webhook delivery to their own store.

### Likelihood Explanation
Any merchant who installs the app (a normal, unprivileged action) receives real webhook deliveries with valid HMACs for their own shop. Replaying the body+HMAC with a forged `shop-domain` header is a trivial HTTP-level manipulation requiring no cryptographic secret, making this readily reachable by any unprivileged internet user who can install the app once.

### Recommendation
Bind the shop (and topic/webhook id) into the signable content that `HmacValidator` verifies, or independently authenticate/authorize the `shop-domain` header against the shop the handler expects (e.g., verify it matches a shop with an active, matching session/webhook subscription) before dispatching. At minimum, `to_signable_string` in `lib/shopify_api/webhooks/request.rb` should not be the sole basis for trusting `request.shop`; the identity used to key data mutations must be cryptographically bound, not read from an unauthenticated header.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, triggering a legitimate webhook (e.g., `orders/create`) delivery with body `B` and header `shopify-hmac-sha256: H` (valid HMAC of `B` under the app's `client_secret`), plus header `shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker replays this exact HTTP POST to the app's webhook endpoint, changing only `shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`= B`, unchanged) and succeeds [6](#0-5) .
4. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` [5](#0-4) , causing the app to process/act on data as if it came from the victim shop, even though the HMAC never validated that association.
