## Analog Found

Every other credential-issuing grant path in this library (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`) sanitizes the caller-supplied `shop` string through `Utils::ShopValidator.sanitize!` before it is used to build the host that receives `client_secret`. The Authorization Code Grant path (`Oauth.validate_auth_callback`) does not.

### Title
Authorization Code Grant sends `client_secret` to an unvalidated `shop` host - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the OAuth token-exchange request host directly from `auth_query.shop` without ever passing it through `Utils::ShopValidator.sanitize!`, unlike every sibling credential-granting method in the same module tree.

### Finding Description
`validate_auth_callback` only checks the HMAC of the query string and that the `state` cookie matches: [1](#0-0) 

It then constructs `null_session = Auth::Session.new(shop: auth_query.shop)` and builds an `HttpClient` whose request host is `session.shop`: [2](#0-1) 

That request body contains `client_secret: Context.api_secret_key`: [3](#0-2) 

No call to `Utils::ShopValidator.sanitize!` exists anywhere in `lib/shopify_api/auth/oauth.rb`. This is inconsistent with the rest of the credential-issuing methods, which all validate `shop` first: [4](#0-3) [5](#0-4) [6](#0-5) 

The `ShopValidator` module exists precisely to bind a `shop` value to the set of trusted Shopify domains (`shopify.com`, `myshopify.com`, `myshopify.io`, `spin.dev`, `shop.dev`), rejecting anything else: [7](#0-6) 

The equality this omission breaks is: **shop value verified as bound by HMAC signature ≠ shop value verified as a trusted Shopify domain.** The HMAC over `auth_query.to_signable_string` proves only that whoever produced the `hmac` value knew the app's `api_secret_key` and applied it to the exact set of query params (`code`, `host`, `shop`, `state`, `timestamp`): [8](#0-7) 

The HMAC binds `shop` to *the rest of the signed request*, but never checks that `shop` is actually a `*.myshopify.com`/trusted domain, so it does not perform the role that `ShopValidator` plays elsewhere in this codebase.

### Impact Explanation
If an app's `redirect_uri` allow-list or its own callback route can be reached with a `shop` value that legitimately carries a valid HMAC for that value (e.g., because the host application forwards query parameters from an untrusted source into `AuthQuery`, or because Shopify itself would sign whatever `shop` the merchant-facing OAuth screen embeds), the app's `client_secret` would be transmitted, unvalidated, to `https://<shop>/admin/oauth/access_token`. This is a credential-leakage-into-a-non-Shopify-host class of bug per the audit's stated impact list (credential leakage / SSRF carrying the app's credentials to a host other than the intended Shopify tenant).

### Likelihood Explanation
This is Medium-to-uncertain likelihood as an *independently exploitable* bug in this gem alone: exploiting it purely from the unprivileged-internet-user side requires either (a) a real Shopify-signed callback for a non-`myshopify` `shop` value (not something Shopify would sign under normal OAuth), or (b) a host application that echoes attacker-controlled `shop`/`hmac` pairs into `AuthQuery` without itself validating the domain first — which shifts blame toward the integrating app. However, the omission is real and directly contradicts this library's own established pattern (`ClientCredentials`, `RefreshToken`, `TokenExchange.migrate_to_expiring_token` all validate `shop` at this exact point before spending `client_secret`), so it is a genuine, fixable defense-in-depth gap in the gem itself, not merely "host app ignoring documented API" — the documented parameter table for `begin_auth`/`validate_auth_callback` says `shop` should be `{exampleshop}.myshopify.com` but the library never enforces that invariant on the callback path the way it does elsewhere.

### Recommendation
In `ShopifyAPI::Auth::Oauth.validate_auth_callback`, call `Utils::ShopValidator.sanitize!(auth_query.shop)` (as done in `ClientCredentials`, `RefreshToken`, and `TokenExchange.migrate_to_expiring_token`) and use the sanitized value to construct `null_session` and the resulting `Session`, raising `Errors::InvalidShopError` for any `shop` outside the trusted domain list before the `client_secret` is ever sent.

### Proof of Concept
Not independently demonstrable purely as an unprivileged internet user against this gem in isolation — a valid `hmac` for an attacker-chosen `shop` requires either a genuine Shopify-issued callback (which Shopify would only sign for real `myshopify.com` shops) or a host application defect that forwards unauthenticated `shop`/`hmac` pairs. What can be verified statically is that this code path is the only credential-granting flow in the auth module lacking the `ShopValidator.sanitize!` call that every sibling method uses: [9](#0-8)

```ruby
        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
            access_token_response: Oauth::AccessTokenResponse.from_hash(session_params))
```
