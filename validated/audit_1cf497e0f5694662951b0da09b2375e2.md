### Title
Unbounded, permissionless micro-partial-fills of same-chain intent orders enable griefing of order beneficiaries and solvers - (File: evm/src/apps/intentsv2/IntrinsicIntents.sol)

### Summary
`IntrinsicIntents._fillSameChain` (invoked from `IntentGatewayV2.fillOrder`) allows any unprivileged caller to repeatedly submit tiny partial fills against a same-chain order, with no minimum fill-size check. This mirrors the Debita M-16 bug class: absence of a minimum order/loan size lets an unprivileged actor fragment a single position into an unbounded number of tiny operations, griefing the counterparties who must process, track, and pay gas for each fragment.

### Finding Description
`fillOrder` on same-chain orders routes to `_fillSameChain`, which computes `fillAmount = solverAmount > remaining ? remaining : solverAmount` per output asset [1](#0-0) . There is no lower bound on `solverAmount`/`options.outputs[i].amount`; the only checks are `remaining == 0 || solverAmount == 0` to skip a no-op fill [2](#0-1) . Any address can call `fillOrder` (there is no solver allowlist unless `solverSelection` is enabled, and even then any selected/unselected caller can still submit output tokens as long as amount > 0) with `solverAmount = 1` wei, causing:
- A proportional escrow release computed as `(order.inputs[i].amount * fillAmount) / totalRequired` [3](#0-2) ,
- Storage write to `_partialFills[commitment][outputToken]` [4](#0-3) ,
- A token transfer to the beneficiary and a `PartialFill` event emission [5](#0-4) ,
- A call into `_withdraw`, which reads/writes `_orders[commitment][token]` for each escrowed token [6](#0-5) .

Because a single order can have an unbounded number of tiny partial fills (down to 1 wei per call, limited only by external gas cost, not by protocol rule), a malicious actor can fragment one user's order into thousands of `fillOrder` transactions. Each fragment:
- Forces the beneficiary to receive many tiny transfers instead of one settlement, complicating off-chain accounting/indexing (the whitepaper explicitly frames the SDK/filler bots around discrete `OrderPlaced`/`PartialFill`/`OrderFilled` events, e.g. `IntentOrderStatus.PARTIAL_FILL` [7](#0-6) ).
- Forces any *other* legitimate solver wanting to fill the remainder to compete against a rapidly shrinking `remaining` value and to pay gas per attempted fill that may partially or fully fail to acquire meaningful escrow, since `_partialFills` state changes on every call.
- Causes the user's escrow (`_orders[commitment][token]`) to be decremented in many small storage-write transactions rather than one, and — combined with the known rounding-dust handling path already present in the code (`testPartialFill_RoundingDustReleasedToFinalSolver`) — increases the surface for repeated rounding truncation across a large number of fills [8](#0-7) .

This is directly analogous to the Debita M-16 root cause: no minimum order/loan size, permitting a public/unprivileged role (there, the aggregator; here, any solver calling `fillOrder`) to split a single position into countless micro-operations.

### Impact Explanation
An attacker (any address, no special role required) can grief:
- **The order's beneficiary/user**, who must reconcile potentially thousands of tiny output transfers instead of a clean settlement, and whose escrow release is spread across many transactions rather than the intended few.
- **Legitimate competing solvers**, who must repeatedly re-check `_partialFills`/`remaining` state and risk wasted gas racing a rapidly-fragmenting order, or who receive proportionally smaller-than-expected escrow due to prior micro-fills consuming the "first fill gets surplus" path (`alreadyFilled == 0 && solverAmount > totalRequired`) — an attacker filling with 1 wei first denies any subsequent solver the surplus-capture branch [9](#0-8) .
- **Gas costs**: each 1-wei fill still costs the attacker gas, but it inflicts state growth and processing overhead disproportionate to any value moved, degrading protocol usability without requiring any privileged access, matching the "no minimum size" griefing pattern described in the source report.

This does not directly cause fund loss but permanently degrades usability/UX and can be used to grief specific counterparties at will, consistent with a Medium-severity griefing/DoS-style finding.

### Likelihood Explanation
High feasibility: `fillOrder`/`_fillSameChain` is a public, unauthenticated entry point reachable by any address holding a trivial amount of the required output token (as low as 1 wei of an ERC-20, or the smallest native-token unit). No minimum fill size, cooldown, or per-order fill-count cap exists in the code inspected. The attack requires no privileged role, matching the report's "aggregator is a public role and anyone can match orders" precondition.

### Recommendation
Introduce a minimum fill-size constraint in `_fillSameChain` (e.g., a per-pair or per-order minimum expressed as basis points of `totalRequired`, or an absolute minimum token amount), rejecting `fillOrder` calls whose `solverAmount` (per output asset) falls below the threshold unless it completes the order (i.e., always allow the final fill that fully satisfies `remaining`). Optionally cap the total number of partial fills permitted per order commitment.

### Proof of Concept
Conceptual reproduction using the existing test harness pattern (`evm/tests/foundry/IntentGatewayV2SameChainTest.sol`):
1. User places a same-chain order with `inputAmount = 1000 USDC`, `outputAmount = 1000 DAI` (as in `_placeStandardOrder`) [10](#0-9) .
2. An attacker (any account holding DAI) repeatedly calls `fillOrder` with `outputs[0].amount = 1` (1 wei of DAI), e.g. 1000 times, each succeeding because `remaining == 0 || solverAmount == 0` is the only guard [11](#0-10) .
3. Each call emits a separate `PartialFill` event and moves 1 wei DAI to `beneficiary` plus a proportional 1-USDC-scale fraction of escrow to the attacker, fragmenting what should be a single settlement into 1000 transactions/events, and forcing any legitimate solver attempting to fill the remainder to contend with constantly shifting `_partialFills` state.

This confirms the missing-minimum-size griefing vector is reachable via a standard, unprivileged `fillOrder` call, without requiring any admin/governance/relayer role.
