### Title
Concurrent unawaited `write()` calls race on shared `blobKey`/`metadata` closure state, causing data loss/corruption - ([File: libraries/seco-rw/src/index.js])

### Summary
`createSecoRW`'s `write()` reads and mutates the shared closure variables `blobKey`/`metadata` without any locking or in-flight-write tracking. Two concurrent `write()` calls issued before either resolves both observe `metadata` as falsy, both take the expensive `else` branch (deriving fresh salt/`blobKey`/`metadata` via `secoFile.write(..., { passphrase, overwrite: true })`), and both unconditionally overwrite the closure state and the on-disk file when they resolve, in whichever order the underlying `fs.outputFile` and encryption promises actually settle. [1](#0-0)  This is not merely theoretical: `SecoKeyval`, the direct consumer of `seco-rw`, itself exercises this pattern via `Promise.all` over multiple `kv.set()` calls in its own test suite, and `SecoKeyval.batch()`/`.set()` provide no serialization/queueing over `this._seco.write()`. [2](#0-1) 

### Finding Description
`write(data)` in `seco-rw` branches on the closure variable `metadata`:
- If `metadata` is set, it reuses the cached `blobKey`/`metadata` (cheap path).
- If not, it calls `secoFile.write(file, data, { passphrase, overwrite: true, header })`, which derives a brand-new scrypt salt/`blobKey`/`metadata` and writes the encrypted file, then stores the result into the shared `blobKey`/`metadata` closure variables. [3](#0-2) 

`secoFile.write` performs `encrypt(data, options)` and then `await fs.outputFile(file, encryptedData)`, returning the derived `blobKey`/`metadata` for that specific write. [4](#0-3) 

If a caller fires two `write()` calls back-to-back without awaiting the first (e.g., `SecoKeyval.batch()` invoked concurrently, as literally done in `libraries/seco-keyval/src/seco-keyval.test.js`'s `getAllData()` test via `Promise.all(...map(key => kv.set(...)))`), both calls see `metadata === undefined` and both take the `else` branch, each independently deriving distinct `blobKey`/`metadata` and independently calling `fs.outputFile` to the same path with `overwrite: true`. [5](#0-4) [6](#0-5) 

Because `fs.outputFile` writes are not coordinated, disk-write completion order is not guaranteed to match JS promise-resolution order for the two `secoFile.write()` calls. Whichever `write()` promise resolves *last* unconditionally overwrites `blobKey`/`metadata` in the `seco-rw` closure (lines 16-17), regardless of whether that call's `fs.outputFile` actually was the one that last touched the physical file. There is no mutex/queue, no check for an in-flight write, and no validation that the cached `blobKey`/`metadata` still correspond to the bytes on disk. Read()'s own re-derivation (`read()` always calls `secoFile.read` fresh with `passphrase`, not the cached key) means immediate reads recover, but any subsequent `write()` calls (which use the `if (metadata)` fast path) will re-encrypt using a `blobKey` that may not match the salt/metadata actually persisted by the "losing" write, and the losing write's payload (which could be a different/older snapshot of `SecoKeyval`'s in-memory data) may end up being the one durably persisted, silently discarding the other write's data.

### Impact Explanation
This is a data-integrity/storage-authenticity bug on the wallet's local secure-container: an unserialized pair of concurrent `write()` calls can result in the on-disk file's content/metadata not matching the write that "won" in the closure state, or the persisted account data being the older/stale payload from a losing write while the newer, intended data is silently dropped. Impact is limited to local storage-integrity/corruption or lost-write scenarios for whatever consumer issues overlapping writes (e.g., `SecoKeyval.set`/`batch`/`setAllData`) — it does not itself constitute key/secret disclosure or cross-origin/cross-account authorization bypass, since `read()` re-derives from `passphrase` independently rather than trusting the possibly-stale cached `blobKey`.

### Likelihood Explanation
Requires a caller to violate the documented single-writer expectation of `seco-rw`/`SecoKeyval` by issuing two `write()`/`set()`/`batch()` calls concurrently without awaiting the first. `seco-keyval`'s own test suite does exactly this (`Promise.all` over concurrent `kv.set()` calls), showing the library does not itself enforce write serialization and that this usage pattern is not merely hypothetical — it already occurs in first-party code paths that call `SecoKeyval`. [5](#0-4)  Whether any production dapp/RPC-reachable code path (rather than only the test) drives concurrent unawaited writes to the same `SecoKeyval`/`seco-rw` instance was not confirmed within the indexed code; this analysis is scoped to the mechanism inside `seco-rw`/`seco-keyval` itself.

### Recommendation
Serialize all `write()` (and ideally `read()`) calls on a given `createSecoRW` instance through an internal promise chain/mutex (e.g., queue each `write()` after the previous pending operation resolves) so that at most one `secoFile.write` is in flight at a time, and ensure `blobKey`/`metadata` are only committed after confirming the corresponding `fs.outputFile` was the last to complete for that path. Consider also having `SecoKeyval.batch()` explicitly queue/serialize calls rather than relying on callers to await each `set()`/`delete()`.

### Proof of Concept
Integration test in `libraries/seco-rw/test/seco-rw.test.js`:
```js
test('concurrent unawaited write() calls race on blobKey/metadata', async (t) => {
  const testFile = tempfile('.seco')
  const file = createSecoRW(testFile, Buffer.from('opensesame'), { appName: 'Exodus', appVersion: '1.0.0' })

  const dataA = Buffer.from('AAAAAAAAAA')
  const dataB = Buffer.from('BBBBBBBBBB')

  // Fire both without awaiting the first
  const pA = file.write(dataA)
  const pB = file.write(dataB)
  await Promise.all([pA, pB])

  const finalData = await file.read()
  // Expect final on-disk content deterministically equals exactly one of dataA/dataB,
  // and that repeated reads are stable (not flapping between blobKeys/metadata).
  t.assert(
    finalData.toString('utf8') === dataA.toString('utf8') ||
    finalData.toString('utf8') === dataB.toString('utf8'),
    'file should contain exactly one write, not corrupted/mixed'
  )
  const finalData2 = await file.read()
  t.equal(finalData.toString('utf8'), finalData2.toString('utf8'), 'read is deterministic/stable')
})
```
Run this test repeatedly (or with artificial delay injected into `fs.outputFile`/`encrypt` to widen the race window) to demonstrate nondeterministic or corrupted outcomes, and additionally add a `SecoKeyval`-level test that concurrently calls `kv.set()` for multiple keys via `Promise.all` and asserts all keys are present after reopening — matching the existing `getAllData()` test pattern in `libraries/seco-keyval/src/seco-keyval.test.js`.

export async function write (file: string, data: BufOrStr, options = {}) {
  options = { overwrite: false, ...options }

  if (!options.overwrite && await fs.pathExists(file)) throw new Error(`${file} exists. Set 'overwrite' to true.`)

  const { encryptedData, blobKey, metadata } = encrypt(data, options)

  await fs.outputFile(file, encryptedData)

  return { blobKey, metadata }
}
