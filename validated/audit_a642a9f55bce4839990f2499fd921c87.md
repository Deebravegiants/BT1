Based on my research, the Hyperbridge codebase doesn't contain a "matched funds" vault mechanism like the emojicoin arena, but it has a structurally similar economic-incentive surface that is reachable by an unprivileged actor and vulnerable to the same class of bug: **price-setting by a majority-weight bidder in the phantom-order liquidity oracle that then prices real intent fills.**

### Title
Solver-controlled weighted-median oracle in `aggregatePhantomBids` lets an unprivileged filler set the published intent-quote price by temporarily dominating a leg's liquidity weight - (File: `sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts`)

### Summary
Hyperbridge periodically generates "phantom orders" that solicit real solver bids purely for price discovery. Each bid's influence on the resulting price ("the crank" analog here is the bid-window close / `PhantomBidWindowExhausted`) is weighted by the solver's own on-chain balance of the output token at snapshot time, and the result is fed directly into `PhantomSnapshotIntentQuoteStrategy`, which prices *real* user intent orders.

### Finding Description
`weightedMedian` explicitly returns one bidder's exact quoted value once that bidder holds ≥50% of the total weight for a leg — this is documented in code as intentional selection behavior: "a solver holding over half the leg's weight sets the published price verbatim" [1](#0-0) . The weight for each quote is nothing more than the bidding solver's live wallet balance of the leg's output token on the destination chain, read at bid-aggregation time: [2](#0-1) .

Because the weight source is a simple balance read (native + vault positions) rather than a stake that is locked, escrowed, or slashed, an attacker who is a permissionless filler can:
1. Temporarily acquire a large balance of a leg's output token (e.g., via flash borrow or short-term capital) right before the phantom order's bid window closes.
2. Submit a phantom bid quoting an extreme (very favorable-to-solver) price for that leg, guaranteed to dominate the weighted median because their momentary balance outweighs every other bidder: [3](#0-2) .
3. The resulting `PhantomOrderPriceSnapshotV2.medianPrice` is written verbatim from that single quote, with `lowestPrice`/`highestPrice` forcibly overwritten to the same value so downstream consumers cannot detect the manipulation: [4](#0-3) .
4. `PhantomSnapshotIntentQuoteStrategy.quote()` then uses this manipulated `medianPrice` directly to price *real* user intent orders (`amountOut = netAmountIn * snapshot.medianPrice / snapshot.standardAmount`): [5](#0-4) .

This is the same bug class as the reported issue: an attacker manufactures artificial weight/eligibility (many small pools → here, one inflated balance) ahead of a periodic selection event (crank scheduling → here, bid-window close), then exploits the resulting privileged position (buy into the selected pool → here, dictate the published exchange rate) to extract value from the system's economic mechanism, this time from real users who get quoted against the manipulated rate rather than from a matched-funds vault.

### Impact Explanation
A manipulated `medianPrice` directly determines `amountOut`/`amountIn` for any real intent order quoted via the Phantom snapshot strategy. An attacker who transiently inflates their balance to dominate the weight can force the published rate to any value they choose, then either front-run/back-run their own quote as the filling solver, or simply degrade the rate served to genuine users trading that pair — a direct value-extraction/loss-of-funds vector for counterparties relying on the quote.

### Likelihood Explanation
The only barrier is momentarily holding (not locking) a majority of one leg's output-token balance on the destination chain at snapshot time — no stake is escrowed, no cooldown or minimum holding period is enforced, and phantom orders run on a fixed periodic interval that is fully observable on-chain, making the "when" of the attack predictable. This lowers the bar compared to genuinely competing on real fills.

### Recommendation
- Require weight to derive from a bonded/locked stake (or an average balance over a window) rather than an instantaneous spot balance, so it cannot be manufactured for a single snapshot.
- Cap any single solver's contribution to a leg's total weight (e.g., a max weight share per solver) so no bidder can single-handedly set `weightedMedian` verbatim.
- Consider requiring multiple independent solvers above a minimum bid count before a snapshot is treated as authoritative for real-order pricing, and/or bound how far a new snapshot may move the price from the prior one.

### Proof of Concept
1. Identify an upcoming phantom order leg for token pair (A, B) from the periodic phantom-order generator.
2. Shortly before `PhantomBidWindowExhausted` fires for that order, acquire (e.g., flash-borrow) enough of token B on the destination chain to exceed every other bidder's declared B balance.
3. Submit a phantom bid (`place_bid`) quoting an extreme `solverAmount` for that leg.
4. `aggregatePhantomBids` weights the quote by the attacker's balance [6](#0-5) ; since the attacker's weight exceeds 50% of total, `weightedMedian` returns the attacker's exact price [7](#0-6) .
5. Return the borrowed capital; the manipulated `PhantomOrderPriceSnapshotV2` persists and is served to all subsequent real quote requests via `PhantomSnapshotIntentQuoteStrategy.quote()` until the next window.

export function weightedMedian(entries: { price: bigint; weight: bigint }[]): bigint {
	const sorted = [...entries].sort((a, b) => (a.price < b.price ? -1 : a.price > b.price ? 1 : 0))
	const totalWeight = sorted.reduce((acc, e) => (e.weight > 0n ? acc + e.weight : acc), 0n)

	if (totalWeight === 0n) {
		return sorted[Math.floor(sorted.length / 2)].price
	}

	let cumulative = 0n
	for (const entry of sorted) {
		if (entry.weight <= 0n) continue
		cumulative += entry.weight
		if (cumulative * 2n >= totalWeight) return entry.price
	}
	return sorted[sorted.length - 1].price
