### Title
Unbounded normalized-decimal multiplication in `calc_take_pnl` allows a pool creator to permanently freeze deposit/withdraw/swap/PNL flows for an entire pool - (File: program/src/processor.rs)

### Summary
`Processor::calc_take_pnl` (`program/src/processor.rs:167-281`) computes `pool_pc_amount.checked_mul(pool_coin_amount).unwrap()` and `calc_pc_amount.checked_mul(calc_coin_amount).unwrap()` on `U128` values that are derived from vault token amounts normalized via `Calculator::normalize_decimal_v2` (`program/src/math.rs:106-116`), which scales a raw `u64` amount by `amm.sys_decimal_value` and divides by `10^native_decimal`. Because `Initialize2` (`program/src/processor.rs:549-864`) is a fully permissionless, pool-creator-controlled instruction that accepts arbitrary SPL mints (with attacker-chosen decimals, e.g. `0`) and an attacker-chosen `init_coin_amount`/`init_pc_amount` up to `u64::MAX`, a malicious pool creator can engineer a pool whose normalized `x`/`y` values are large enough that their product overflows `U128` (~3.4e38). This is directly analogous to CVE-2018-20199's root cause class: an arithmetic/bounds assumption in a numeric transform (windowed output addition in `ifilter_bank`) that is not actually guaranteed for all valid inputs, causing an unconditional crash (there: NULL deref/segfault; here: `unwrap()` panic on `None` from `checked_mul`).

### Finding Description
`calc_take_pnl` is invoked from every fund-moving instruction that already has liquidity in the pool: `process_deposit` (`processor.rs:1166-1173`), `process_withdraw` (~`processor.rs:1495-1502` region), `process_withdrawpnl` (`processor.rs:1495-1502`), and the swap handlers (`processor.rs:1818` region for `process_swap_base_in`/`process_swap_base_out`). Its first act is:
```
processor.rs:190-191
if pool_pc_amount.checked_mul(pool_coin_amount).unwrap()
    >= (calc_pc_amount).checked_mul(calc_coin_amount).unwrap()
```
Both operands are `U128` values built from `normalize_decimal_v2(total_amount, decimals, sys_decimal_value)` (`math.rs:106-116`), which itself does an unchecked (but `.unwrap()`-guarded) `checked_mul`/`checked_div`. Since `Initialize2` lets an unprivileged pool creator pick both mints (hence `coin_decimals`/`pc_decimals`) and the vault seed amounts (`init.init_pc_amount`, `init.init_coin_amount`, transferred verbatim into the vaults, e.g. `processor.rs:835-841`), a pool can be initialized with a token of `decimals = 0` and a near-`u64::MAX` vault balance. `normalize_decimal_v2` then produces a normalized value on the order of `amount * sys_decimal_value`, and squaring two such values (as done at line 190-191) exceeds `U128::MAX`, making `checked_mul` return `None`, and the `.unwrap()` panics.

Because the panic occurs on state (`AmmInfo`/`TargetOrders`/vault balances) that only changes as a result of successfully completing one of these same instructions (which themselves cannot complete because they panic before doing any transfer), the pool becomes permanently unusable: any `Deposit`, `Withdraw`, `WithdrawPnl`, `SwapBaseIn`, or `SwapBaseOut` against that `AmmInfo` will always hit the same overflow and abort. There is no recovery path exposed to accounts/instructions in the program, so any liquidity subsequently deposited into (or already present in) the pool's vaults becomes permanently unreachable through the program's SPL token CPI paths in `Invokers`.

Note: I could not fully verify within the available search budget whether `process_initialize2` enforces any bound on `init_coin_amount`/`init_pc_amount` or mint decimals beyond `amm_coin_vault.amount == 0` checks; the code inspected (`processor.rs:835-864`) shows only an "amount must be non-zero" check, not an upper bound, and no restriction on decimals was found. If such a bound exists elsewhere in `state.rs`'s `AmmInfo::initialize`, it was not identified in the portions of the file reviewed, so this should be double-checked before rollout of a fix.

### Impact Explanation
This meets the "permanent freezing of user or LP funds" bar: once a pool is initialized in an overflow-triggering configuration, the pool's coin/pc vaults and any LP tokens minted against it become permanently non-withdrawable and non-swappable via the program (every code path that would move funds calls `calc_take_pnl` first and panics). This is a Medium/High-severity denial-of-service against on-chain funds, matching CVE-2018-20199's bug class (an unguarded arithmetic operation in a specific input configuration causing an unconditional crash), adapted to the "permanent freeze" impact bar required for this program.

### Likelihood Explanation
`Initialize2` is reachable by any signer in a single transaction with fully attacker-chosen mint accounts and attacker-chosen `init_pc_amount`/`init_coin_amount` (subject only to non-zero vault balance checks observed). No privileged signer or off-chain component is required. The only extra step for an attacker is to also mint/control a custom SPL token with `decimals = 0` (or generally low decimals) and supply a large amount to the vault, which is trivial and entirely within the "unprivileged pool creator" scope allowed by this analog set.

### Recommendation
Replace the `.unwrap()` calls on `checked_mul` in `calc_take_pnl` (`processor.rs:190-191` and the related arithmetic later in the same function) and in `normalize_decimal_v2`/`restore_decimal` (`math.rs:96-116`) with `.ok_or(AmmError::CalculationExRateFailure)` (or similar), returning a normal `ProgramError` instead of panicking. Additionally, consider using a wider integer type (e.g., `U256`) for the `pool_pc_amount * pool_coin_amount` comparison to avoid overflow for legitimately large but valid pools, and/or bound the accepted mint decimals/initial vault amounts in `process_initialize2` to values that keep normalized values within safe multiplication ranges.

### Proof of Concept
1. Attacker creates two SPL mints, `mint_a` with `decimals = 0` and `mint_b` with normal decimals (e.g. 9).
2. Attacker calls `Initialize2` (`program/src/instruction.rs:332-354`, dispatched to `Processor::process_initialize2`, `processor.rs:549`) as the pool creator, supplying `init_coin_amount` close to `u64::MAX` for `mint_a` as the coin vault and a modest `init_pc_amount` for `mint_b`.
3. Pool initializes successfully (only a non-zero-vault check is enforced, per `processor.rs:858-860`).
4. Any subsequent call to `Deposit`, `Withdraw`, `WithdrawPnl`, `SwapBaseIn`, or `SwapBaseOut` on this pool invokes `Calculator::normalize_decimal_v2` on the coin side, producing a `U128` value on the order of `u64::MAX * sys_decimal_value`; `calc_take_pnl`'s `pool_pc_amount.checked_mul(pool_coin_amount).unwrap()` (or the `calc_pc_amount.checked_mul(calc_coin_amount).unwrap()` on the other side) overflows `U128`, `checked_mul` returns `None`, and `.unwrap()` panics, aborting the transaction.
5. Because the pool state that drives this computation cannot be changed without going through one of the panicking instructions, the pool (and any coin/pc/LP tokens locked in it) is permanently frozen. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)
