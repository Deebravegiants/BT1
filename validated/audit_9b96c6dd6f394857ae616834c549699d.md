## Finding: `CallDispatcher.dispatch` has no access control and lets anyone drain any token/ETH balance the shared dispatcher happens to be holding

### Title
Unrestricted `CallDispatcher.dispatch` allows theft of any token/ETH dust left temporarily or permanently in the shared dispatcher contract - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch(bytes memory encoded)` is `external` with zero access control — no `onlyHost`, no caller allowlist, no ownership check [1](#0-0) . It decodes an arbitrary `Call[]` array and executes each entry against any contract with `to.call{value: call.value}(call.data)`, so anyone can direct the dispatcher's current balance (native or ERC-20) anywhere. This mirrors the reported `RouterTokenHelper.transferAllTokens` bug class exactly: a permissionless "sweep/execute arbitrary calls from this contract's balance" primitive with no restriction on caller or destination.

### Finding Description
`IntentGatewayV2`/`IntentsBase` treats `CallDispatcher` as a single shared, protocol-wide contract referenced via `_params.dispatcher`, used by every order's predispatch and postdispatch calldata execution (docs describe it as a canonical deployment, not per-order) [2](#0-1) .

During predispatch, assets are pushed into the dispatcher, the untrusted `order.predispatch.call` is executed, and only the tokens explicitly listed in `order.inputs` are swept back to the gateway: [3](#0-2) 

During postdispatch (`_execute`), only the tokens listed in `order.output.assets` (`outputsLen`) are swept back as "dust": [4](#0-3) 

Because the sweep loops are bounded strictly by the order's declared token lists, any token or ETH balance the untrusted calldata produces or leaves behind that is *not* in that declared list (e.g. an intermediate swap-hop token, leftover approval dust, a failed/partial multi-hop route, or balance from a concurrent/prior order using the same shared dispatcher) is never recovered by the gateway. Since `CallDispatcher.dispatch` itself has no caller restriction, that residual balance is directly and permanently stealable by anyone: an attacker simply calls `dispatcher.dispatch(abi.encode([Call{to: strayToken, value: 0, data: transfer(attacker, balance)}]))` (or a native-value `Call` to sweep leftover ETH) at any point after the order's calldata executes and before the gateway's own sweep call runs, or for any token type the gateway never planned to sweep at all.

This is structurally identical to the reported bug: `RouterTokenHelper.transferAllTokens` was a public, unrestricted "sweep this contract's balance to any recipient" function reachable by anyone; `CallDispatcher.dispatch` is the same shape — a shared utility contract whose current balance can be redirected anywhere by any caller, no `onlyHost`/`onlyGateway` guard, no reentrancy consideration for the fact that it is shared across all orders and gateways.

### Impact Explanation
Any native or ERC-20 balance that transiently or permanently sits in the shared `CallDispatcher` — dust from predispatch/postdispatch swap calldata, tokens outside the order's declared input/output list, or ETH sent via `receive()` [5](#0-4)  — can be permissionlessly redirected to an attacker-chosen address. Because the dispatcher is shared across the whole `IntentGatewayV2` deployment (all orders, all users, all solvers), this is not a self-inflicted loss confined to one order's caller; it is theft of protocol users'/solvers' funds sitting in a shared, unprotected contract. This satisfies concrete theft of funds.

### Likelihood Explanation
High. No special conditions or races beyond "some token balance ends up in the dispatcher outside the exact set the gateway sweeps." Given predispatch/postdispatch calldata routes through DEXes and arbitrary calls (explicitly documented as supporting multi-step swap flows), any multi-hop swap, partial fill, or slightly mismatched declared-asset list versus actual calldata effects will leave sweepable dust. An attacker only needs to watch the dispatcher's token balances and call `dispatch()` directly — no proof, no relayer, no privileged role required.

### Recommendation
Restrict `CallDispatcher.dispatch` to only be callable by an authorized/registered caller (e.g., the `IntentGatewayV2`/`IntentsBase` contracts that own the specific execution context), or deploy a fresh, single-use `CallDispatcher` instance per order/execution rather than sharing one instance across the whole protocol, so no balance can ever be observed or drained by an unrelated third party between executions.

### Proof of Concept
1. A user places an order with `predispatch.call` that swaps ETH → tokenA → tokenB via a DEX, but `order.inputs` only declares tokenB as the required input.
2. Due to slippage/rounding or an extra hop, some tokenA dust remains in the shared `CallDispatcher` after `IntentGatewayV2`'s sweep loop (which only sweeps tokens present in `order.inputs`) [6](#0-5) .
3. An attacker, observing the dispatcher's tokenA balance, calls `CallDispatcher.dispatch(abi.encode([Call({to: tokenA, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, danglingBalance)})]))` directly — no authorization is checked [7](#0-6) .
4. The dangling tokenA balance is transferred to the attacker with no way for the protocol or the original order's parties to reclaim it.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

## Calldata

Orders support arbitrary calldata execution at two points in the lifecycle — before escrow (predispatch) and after fill (postdispatch). Both are executed through the `CallDispatcher` contract, which takes an ABI-encoded `Call[]` array:

```solidity
struct Call {
    address to;      // Target contract (must have code, reverts with NotContract otherwise)
    uint256 value;   // ETH to send with call
    bytes data;      // Calldata to execute
}
```

The `CallDispatcher` executes each call sequentially and reverts the entire batch if any call fails.

### Predispatch

The `predispatch` field in `Order` contains calldata to execute *before* escrowing inputs. The predispatch assets specified in `DispatchInfo.assets` are transferred to the `CallDispatcher`, the encoded calls are executed, and the resulting tokens are transferred back to the gateway for escrow. This enables swap-then-escrow patterns — for example, a user sends ETH which the `CallDispatcher` swaps to DAI on Uniswap, and the resulting DAI is escrowed as the order input.

### Postdispatch

The `call` field in `PaymentInfo` contains calldata to execute *after* the order is filled. This enables fill-then-act patterns — for example, output tokens received from the solver are routed through a DeFi protocol before reaching the beneficiary.

Execution timing differs by mode:

- **Same-chain**: Calldata executes only after the order is **fully filled**. Partial fills do not trigger calldata — only the final fill that completes the order executes it. This ensures all output tokens are available when the calls run.
- **Cross-chain**: Calldata executes **immediately** after the solver delivers output tokens to the beneficiary, before the settlement message is dispatched back to the source chain.

After execution, any tokens remaining in the `CallDispatcher` are swept back to the gateway and collected as dust (emitting `DustCollected` for each token). When postdispatch calldata is present, 100% of any surplus (solver overpayment) goes to the protocol rather than being split with the beneficiary — this prevents manipulation of surplus distribution through calldata side effects.
