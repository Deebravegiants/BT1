### Title
Webhook `shop-domain` header is trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes `shop`, `topic`, `webhook_id`, and `api_version` as plain HTTP headers, but the HMAC signature validated by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body (`to_signable_string` returns `@raw_body`). Any unprivileged party who has captured one legitimate, signed webhook body (e.g. sent by Shopify to their own app installation) can replay the exact same body/HMAC pair while substituting an arbitrary `shop-domain` header. The signature still validates because the header is not part of the signed content, so `ShopifyAPI::Webhooks::Registry.process` will hand the handler a `WebhookMetadata` object whose `shop` field is fully attacker-controlled.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) 

Only `@raw_body` is fed into the HMAC computation. `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from attacker-controllable headers: [2](#0-1) 

`HmacValidator.validate` verifies only `verifiable_query.to_signable_string` against the HMAC, so it never binds the `shop-domain` (or any other) header to the signature: [3](#0-2) 

`Registry.process` trusts `request.shop` (and the other headers) once the body HMAC passes, and forwards them unchecked to the registered handler: [4](#0-3) 

The identity binding that should hold is: `shop header used to attribute/process the webhook == shop that Shopify actually signed the payload for`. Because the signature covers only the body, this binding is broken — the equality `signed_bytes == parsed_shop-header` is never enforced. An attacker who owns any installation of the app (even a free/trial store) can capture a legitimate `(raw_body, hmac)` pair from their own webhook deliveries and resend it with the `shop-domain` header rewritten to any other shop domain the app serves.

### Impact Explanation
Whether this is exploitable in a given host application depends on how it uses `WebhookMetadata#shop`, but this gem's own documented contract is that the `shop` value returned from `Request`/passed to handlers is validated data safe for tenant attribution once `HmacValidator.validate` succeeds. Since a low-privilege attacker (any merchant who installs the app, i.e. an "unprivileged internet user" from Shopify's perspective) can forge this attribution to point at a *different* tenant's shop domain while keeping the signature valid, this breaks the tenant-isolation boundary the gem is supposed to enforce for webhook processing — the exact class of bug called out in the rules ("a field acted on but not covered by the HMAC"). This enables cross-tenant data injection/confusion in any host application that keys persistence, authorization, or business logic off `WebhookMetadata#shop`.

### Likelihood Explanation
High likelihood of a working exploit path: no secrets, tokens, or privileged access are required beyond installing the app once (or observing a single legitimate webhook delivery to a controlled endpoint). The attacker only needs to replay an HTTP POST with modified headers — the HMAC check is unaffected because it only ever hashes `@raw_body`.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed material, or otherwise cryptographically bind them to the payload before trusting them (e.g. require the host application to independently verify `shop` came from the same webhook delivery Shopify signed, following Shopify's official webhook verification guidance which recommends only trusting the body HMAC for payload integrity and separately validating the shop against a known/installed shop list rather than trusting the header value for tenant attribution).

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com`; capture a legitimate webhook delivery, e.g.
```
POST /webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <valid-hmac-of-body>
x-shopify-shop-domain: attacker-shop.myshopify.com
Body: {"id": 1, "note": "hello"}
```
2. Verify the HMAC is computed only from the JSON body: [5](#0-4) 
3. Replay the identical body and HMAC, but change the header:
```
x-shopify-shop-domain: victim-shop.myshopify.com
```
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` still returns `true` because it only re-hashes `@raw_body`: [6](#0-5) 
5. `ShopifyAPI::Webhooks::Registry.process` invokes the handler with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop == "victim-shop.myshopify.com"`, even though the payload was never sent for that shop: [7](#0-6)
