### Title
Webhook `shop` (and other Shopify headers) are trusted for tenant identification without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC signature over the raw request body, then unconditionally forwards the `shop`, `topic`, `webhook_id`, and `api_version` values taken from HTTP headers to the app's handler. Because the HMAC is computed only over the body bytes and never binds the headers, an attacker who can obtain any one validly-signed webhook body (e.g. from their own installed shop) can replay it against the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` (or `shopify-shop-domain`) header, and the library will treat the payload as authenticated for that attacker-chosen shop.

### Finding Description
`Request#hmac` reads the signature strictly from the `hmac-sha256` header, and `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) 

`Registry.process` verifies only this HMAC and then reads `shop`, `topic`, and `webhook_id` straight from unauthenticated headers to construct `WebhookMetadata`, which is handed to the app's handler as the trusted tenant identity: [3](#0-2) 

`HmacValidator.validate` confirms the signature check is computed purely against `verifiable_query.to_signable_string` (the body), never the headers: [4](#0-3) 

The binding that should hold is:
`bytes_verified_by_HMAC == bytes_used_to_identify_the_tenant (shop)`

but in practice:
`bytes_verified_by_HMAC (raw_body only) != bytes_acted_on (shop header, topic header, webhook_id header)`

Any party in possession of one legitimately-signed webhook body/HMAC pair (trivially obtainable by installing the app on their own store and receiving a real webhook) can resend that exact body+HMAC to the app's public webhook endpoint while substituting a victim's `shop-domain` header. `HmacValidator.validate` will still pass (it never looks at the header), so `Registry.process` will invoke the handler believing the event legitimately originates from the victim shop.

### Impact Explanation
This breaks the shop/tenant identity binding the whole webhook-processing flow depends on. Any app that uses `request.shop`/`data.shop` (as the documented usage pattern in `docs/usage/webhooks.md` instructs) to look up per-shop state, apply per-shop business logic, or fetch/act on behalf of a shop's stored session, can be made to act on a victim shop's identity using attacker-controlled (replayed) body content. This is a cross-tenant confusion/access primitive reachable by any unprivileged internet user who can install the app once (to legitimately harvest one signed payload) and then target the endpoint with a forged shop header.

### Likelihood Explanation
High likelihood: no secrets, tokens, or privileged access are required. An attacker only needs to (1) install the app on a shop they control to receive one real, validly HMAC-signed webhook, and (2) resend that raw body with a modified `shop-domain` header to the shared webhook endpoint. The library's `process` method has no additional binding step, so the forged request is accepted as fully valid.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header values into the signed payload verification, e.g. include the shop domain in the signable string computed by `HmacValidator`, or require host applications to cross-check `request.shop` against the shop associated with the currently active/looked-up session before trusting it. At minimum, document and enforce that `shop` must be independently confirmed against a known/registered shop list before being used to key any per-tenant state, since it is presently unauthenticated header data.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives one legitimate webhook (e.g. `orders/create`) with body `B` and a valid header `x-shopify-hmac-sha256: H` (`H = HMAC-SHA256(secret, B)`).
2. Attacker POSTs to the app's webhook route with the exact same raw body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` which recomputes HMAC over `B` only and succeeds, since `B`/`H` are unmodified: [5](#0-4) 
4. The handler is invoked with `WebhookMetadata` whose `shop` is `"victim-shop.myshopify.com"`, even though the payload never originated from Shopify for that shop: [6](#0-5)

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
