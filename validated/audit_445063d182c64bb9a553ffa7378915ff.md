### Title
Historical Analog: Treasury Payout Expiry Was Not Reset on Failed Retry Attempts, Unfairly Penalizing Claimants — Already Fixed (pallet-treasury)

### Summary
The reported bug class — a time-boxed "position" (escrow redemption vs. treasury payout) that gets forcibly cancelled/penalized once its expiry passes, even though the user made good-faith, timely attempts that failed for reasons outside their control (insufficient liquidity/collateral) — has a documented, real analog in `pallet-treasury`. This was already identified and fixed via a PR captured in `prdoc/stable2503/pr_7959.prdoc`.

### Finding Description
The prdoc explicitly describes the exact same root cause pattern as the external report: a `Payout`'s `expire_at` field is set once when a spend is approved, and previously was **not reset** when a claim attempt failed due to insufficient liquidity. This meant a user who tried to claim before expiry, but failed only because funds weren't yet available, would still have their payout expire on the original schedule — "effectively penalizing the claimant in the same way as if they had never requested the payout in the first place." [1](#0-0) 

This is structurally identical to the reported Solidity issue: an entity with a deadline (`redemption`/`Payout`) is penalized/expired despite the user acting correctly, because a failed retry (due to insufficient reserves/liquidity, not user fault) doesn't reset or account for the legitimate attempt.

The fix (already merged into this codebase, per the prdoc) makes the pallet reset `payout.expire_at` using `PayoutPeriod` on every valid payout attempt, so liquidity shortages no longer unfairly cost the user their window to claim. [2](#0-1) 

I attempted to directly inspect the current `pallet_treasury::lib.rs` `payout`/`check_status` logic to confirm the fix is present in the checked-out code, but ran out of tool iterations before completing that read. The `prdoc` file's existence strongly indicates the fix has landed (prdocs in this repo are changelog records for merged PRs), but I could not do a final line-by-line confirmation of the exact reset logic in `substrate/frame/treasury/src/lib.rs`.

### Impact Explanation
If the fix were absent, unprivileged users submitting a spend `payout` claim that fails purely due to protocol-side insufficient funds would lose their payout entirely once the (unmoved) expiry passes, despite having acted correctly and promptly — a direct funds-loss/unfair-penalization impact matching the Medium/Medium severity of the original report.

### Likelihood Explanation
Since this is a **historical, already-remediated** issue (evidenced by the prdoc), the likelihood of it being currently exploitable in this codebase is low — the fix has been applied to `pallet-treasury`. This should be reported as a confirmation of an already-fixed analog rather than a live vulnerability, unless further investigation of `substrate/frame/treasury/src/lib.rs` reveals the fix was reverted or is incomplete.

### Recommendation
Verify in `substrate/frame/treasury/src/lib.rs` that the `expire_at` reset logic described in `pr_7959.prdoc` is actually present in the current `payout`/`check_status` call path, and that no other pallet (e.g., `substrate/frame/multi-asset-bounties/src/lib.rs`'s `retry_payment` for `FundingAttempted`/`RefundAttempted`/`PayoutAttempted` states) reintroduces the same class of bug by failing to reset any time-boxed expiry/grace-period field on a failed-but-legitimate retry attempt. [3](#0-2) 

### Proof of Concept
Not applicable as a live PoC — this finding is based on the documented historical fix in `prdoc/stable2503/pr_7959.prdoc`, not a currently reproducible exploit. A concrete PoC would require confirming (via a running node/test harness, which I do not have access to in this ask-only session) whether `substrate/frame/treasury/src/lib.rs`'s current payout logic still resets `expire_at` on retries as described, or whether a regression has been introduced.
