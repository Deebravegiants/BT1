### Title
Webhook shop/topic identity headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `HmacValidator.validate` only proves the *body bytes* were signed with the app secret. The `shop-domain`, `topic`, `webhook-id`, and `api-version` headers — which the gem uses to build `WebhookMetadata` and route/attribute the event to a specific merchant — are never part of the signed material. This breaks the intended identity binding: `verified(body) ⇏ verified(shop, topic)`.

### Finding Description
`ShopifyAPI::Webhooks::Request` reads `shop`, `topic`, `webhook_id`, and `api_version` purely from HTTP headers: [1](#0-0) 

`to_signable_string`, used by the HMAC check, returns only `@raw_body`: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the HMAC strictly over that signable string: [3](#0-2) 

`Registry.process` treats a passing HMAC check as sufficient proof of authenticity, and then dispatches the handler using the *unauthenticated* `shop`, `topic`, `webhook_id`, and `api_version` values pulled straight from the request headers: [4](#0-3) 

Because the shop domain and topic are documented as the fields host apps use to determine "which shop"/"which resource" a webhook belongs to: [5](#0-4) [6](#0-5) 

An unprivileged internet user who can install the app on their own store (a completely normal, unprivileged action) will receive genuinely Shopify-signed webhooks for their own shop — i.e., a real `(body, hmac)` pair signed with the app's secret. Because the header fields are excluded from the signed payload, that same attacker can replay the exact body/HMAC pair directly to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header with an arbitrary victim shop domain. `HmacValidator.validate` will still return `true`, because it only checks that the body matches the signature — it never validates that the signature was produced *for that shop*. `Registry.process` then calls the handler with `WebhookMetadata(shop: <forged victim shop>, topic: ..., body: <attacker's own event payload>)`, causing the host application to process attacker-controlled data under another tenant's identity.

### Impact Explanation
This is a cross-tenant identity confusion inside the gem's own webhook-authenticity primitive: a value ("this request is validated for shop X") is trusted by the host application via `WebhookMetadata#shop`, but is never actually protected by the cryptographic check the gem performs. Any consuming application that uses `data.shop` (as the shipped documentation and example handler recommend) to select the tenant/session context to act on will process forged, attacker-supplied content attributed to a shop they don't own. This satisfies the "Critical – cross-tenant access" bar: an attacker with no more than their own (unprivileged) app installation can inject events that the app believes originated from an arbitrary other merchant.

### Likelihood Explanation
Likelihood is moderate-to-high for apps that follow the documented pattern of trusting `data.shop`/`data.topic` for tenant routing (exactly as shown in `docs/usage/webhooks.md`). The prerequisite — installing the app on an attacker-owned store to obtain one legitimately signed `(body, hmac)` pair — is achievable by any unprivileged internet user for any public Shopify app, and replaying the request directly to the app's public webhook endpoint requires no special access or secret knowledge.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) in the HMAC-signed material, or otherwise cryptographically bind them to the body before dispatch — e.g., compute a canonical string of `shop|topic|body` (or verify these values against Shopify metadata obtained independently, such as looking up the currently registered webhook and comparing shop context from an authenticated session) rather than trusting header-derived values whenever `HmacValidator.validate` only covers the body.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com`, triggers an event (e.g. creates an order) that causes Shopify to send a legitimately signed webhook: body `B`, header `X-Shopify-Hmac-Sha256: H = HMAC(secret, B)`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker captures this exact HTTP request (body `B` and header `H` unmodified).
3. Attacker resends the request directly to the app's public webhook endpoint, changing only `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` (and/or the `X-Shopify-Topic` header, since it is likewise unsigned).
4. `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` and compares it to `H` — this still matches, because `to_signable_string` only used `B`. Validation passes.
5. `Registry.process` invokes the registered handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: B, topic: <forged/attacker-chosen>, ...)`, causing the host app to process attacker-controlled data as if it came from the victim shop.
