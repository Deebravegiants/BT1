## Title
Reentrant external transfer before escrow-accounting update in `IntentGatewayV2.withdraw` (Tron variant) - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron port of the Intent Gateway (`evm/tron/contracts/apps/IntentGatewayV2.sol`) reintroduces the exact bug class behind the Paribus incident: a Compound-V2-style violation of checks-effects-interactions where the escrow-accounting state (`_orders[commitment][token]`) is decremented **after** the external token/ETH transfer, and the public entry point that reaches this code, `cancelOrder`, carries no reentrancy guard — unlike the hardened EVM sibling contract.

### Finding Description
`withdraw()` sends funds to `beneficiary` before updating internal escrow accounting: [1](#0-0) 

Compare this to the canonical EVM implementation, `IntentsBase._withdraw`, which decrements `_orders[body.commitment][token]` **before** performing the transfer: [2](#0-1) 

The EVM `IntentGatewayV2.cancelOrder` is additionally protected with `nonReentrant`: [3](#0-2) 

The Tron `cancelOrder`, which reaches `withdraw` directly on the same-chain path, has no such guard: [4](#0-3) [5](#0-4) 

The only mitigating control is that `withdraw` sets `_filled[body.commitment] = beneficiary` before the loop [6](#0-5) , and `cancelOrder` checks `_filled[commitment] != address(0)` at its top [7](#0-6) . This blocks the most direct double-cancel/double-withdraw for the *same* order commitment. However, the transaction-fee payout still reads and clears `_orders[...][TRANSACTION_FEES]` only after an external `.call` [8](#0-7) , and the per-token accounting for the *currently processing* token remains stale for the duration of that external call — a pattern only safe as long as every reachable code path re-checks `_filled` before touching escrow, which is a fragile invariant to maintain given `withdraw` is invoked from three separate entry points (`cancelOrder` same-chain, `onAccept` RedeemEscrow/RefundEscrow, `onGetResponse`).

### Impact Explanation
Directly analogous to the Paribus Compound-V2-fork reentrancy: any token/ETH transfer performed before the corresponding internal ledger update creates a reentrancy window. Here the window is largely closed by the `_filled` gate, but the missing `nonReentrant` modifier on `cancelOrder` (present in the audited EVM contract but absent from the Tron port) and the stale-accounting-during-external-call pattern represent a real deviation from the safe pattern the rest of the codebase enforces, and any future code path added to `onAccept`/`onGetResponse`/`cancelOrder` that doesn't independently re-check `_filled` would reopen a concrete fund-draining reentrancy on escrowed user assets and protocol fees.

### Likelihood Explanation
Medium: `cancelOrder` is a permissionless, unprivileged entry point reachable directly by any order owner (or by anyone after order expiry on the destination-cancel path) with a native-ETH-input order and an attacker-controlled beneficiary contract, satisfying the "external call before effects" root cause. Full fund theft from third parties requires either a future code change that omits the `_filled` re-check or a hook-capable token in the flow; as currently written the immediate `_filled` gate limits (but does not architecturally guarantee) exploitability.

### Recommendation
Port the CEI fix from `IntentsBase._withdraw` into the Tron `IntentGatewayV2.withdraw`: decrement `_orders[body.commitment][token]` (and delete `TRANSACTION_FEES`) before issuing the external transfer. Add `nonReentrant` to `cancelOrder` in the Tron contract to match `evm/src/apps/IntentGatewayV2.sol`, and audit all other Tron-specific app contracts for the same divergence from the hardened EVM patterns.

### Proof of Concept
1. Place a same-chain order with a native-ETH input and `order.user` = attacker-controlled contract `Reenterer`.
2. Call `cancelOrder(order, options)`; this invokes `withdraw(body, true)`, which sets `_filled[commitment] = Reenterer` and then sends ETH via `beneficiary.call{value: amount}("")` before decrementing `_orders[commitment][address(0)]`.
3. `Reenterer.receive()` fires during the transfer and attempts to re-enter `cancelOrder` for the same order — currently blocked by the `_filled` check, but demonstrates that the only safety net is that single mapping check rather than the CEI ordering itself; any future entry path that forgets to check `_filled` before invoking `withdraw` would allow a second payout against the not-yet-decremented `_orders[commitment][token]` balance.         address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();

                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }
