### Title
Webhook HMAC signature does not bind the `shop`/`topic` identity headers, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from unauthenticated HTTP headers and passed straight through to the host application's handler (`WebhookMetadata`). The HMAC check in `Utils::HmacValidator`/`Webhooks::Registry.process` therefore proves only that the *body bytes* were signed by Shopify with the app's secret — it proves nothing about which shop or topic that body belongs to.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are pulled from headers with no cryptographic binding to the body: [2](#0-1) 

`to_signable_string` — the value that actually gets HMAC-verified — returns `@raw_body` alone: [3](#0-2) 

`Registry.process` validates the HMAC over that body-only string, then immediately trusts the header-derived `topic` and `shop` to route the payload to the app's handler as identity/tenant data: [4](#0-3) 

`WebhookMetadata.shop` is a plain, unauthenticated `String` field delivered to the app: [5](#0-4) 

This is the exact bug class described in the report: a value used to make an identity/authorization decision (here, "which tenant does this webhook belong to") is not covered by the same cryptographic check (`hmac`) that is used to prove authenticity. The equality that should hold is:
`hmac_signed_bytes == bytes_that_determine_tenant_identity`
but in this gem: `hmac_signed_bytes = raw_body` while `tenant_identity = header["shop-domain"]`, so the two are disjoint.

Because Shopify computes the HMAC only over the JSON body (a documented, expected part of Shopify's own webhook design), this by itself is not a defect introduced by this gem — however, this gem additionally provides zero secondary binding (e.g. it does not require or verify that the shop asserted in headers matches a shop the caller expects, nor does it expose any API to cross-check `shop` against a known/registered value). Any caller who can (a) obtain one legitimately-signed `(body, hmac)` pair — trivial for a merchant who has installed the app in their own store and receives real webhooks for their own shop — and (b) can deliver an HTTP request to the app's shared webhook endpoint with attacker-chosen headers, can resend that exact `(body, hmac)` pair with a forged `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header. `Utils::HmacValidator.validate` will still pass because it only checks the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming to be from a different (victim) shop.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to provide via HMAC verification: the receiving application is led to believe attacker-supplied body content originated from a shop it did not originate from, and will process it under that victim shop's identity in the handler. Depending on how the host app implements its webhook handler (e.g., using `shop` to select which merchant's data/session to update), this can lead to cross-tenant data corruption or logic being triggered against a shop the attacker doesn't control — satisfying the "cross-tenant access" criterion in the rules (Critical).

### Likelihood Explanation
Medium-to-High. The prerequisite (obtaining one legitimately-HMAC-signed body from a webhook the attacker's own installed shop received) is realistic for any single-tenant merchant installer, and no privileged credential, TLS interception, or knowledge of `api_secret_key` is required. The remaining requirement — the ability to POST to the app's public webhook endpoint with custom headers — is trivial since that endpoint by design must accept internet-originated POSTs.

### Recommendation
Bind the tenant/topic identity into the value that is HMAC-verified, or independently verify header-derived `shop`/`topic` against a value the host application already trusts (e.g., require the caller to supply the expected shop and compare it, or include the relevant headers into the signable string alongside guidance in the docs that headers must not be trusted without secondary verification). At minimum, document prominently that `WebhookMetadata#shop`/`#topic` are **not** authenticated by the HMAC check and that host applications must independently corroborate `shop` against a session/store they control before acting on webhook data.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers/receives a real webhook, capturing the raw JSON body `B` and the valid `X-Shopify-Hmac-Sha256` header `H` (`H = HMAC-SHA256(api_secret_key, B)`).
2. Attacker sends a new POST request to the app's shared webhook endpoint with the same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(api_secret_key, B)` — matches `H`, so validation passes: [6](#0-5) 
4. `Registry.process` dispatches to the registered handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: B, ...)`, even though body `B` never originated from `victim-shop`: [4](#0-3)
