### Title
Webhook shop/topic/webhook-id identity not bound by HMAC, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `topic`, `shop`, `api_version`, and `webhook_id` are read directly from unauthenticated HTTP headers. [1](#0-0)  `Registry.process` validates only the body's HMAC via `Utils::HmacValidator.validate(request)` and then unconditionally trusts `request.shop`/`request.topic`/`request.webhook_id` to build the `WebhookMetadata` passed to the app's handler as the authenticated tenant/event identity. [2](#0-1)  This mirrors the Pendle bug class: a value that is *acted upon* (the shop/topic identity used for tenant routing) is not covered by the cryptographic check (the HMAC over the signable string), so the two "sides" of the binding — bytes verified vs. bytes parsed as identity — diverge.

### Finding Description
`HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` header. [3](#0-2)  For `Webhooks::Request`, `to_signable_string` is defined as just `@raw_body` [4](#0-3) , meaning the signature binds only the body bytes — the `shop`, `topic`, `webhook_id`, and `api_version` values are never part of the signed material even though they are read straight from caller-supplied HTTP headers. [5](#0-4)  `Registry.process` performs the HMAC check and then immediately constructs `WebhookMetadata.new(topic: request.topic, shop: request.shop, ..., webhook_id: request.webhook_id)`, handing this "authenticated" struct to the host app's `handler.handle(data:)`. [2](#0-1)  The equality the gem implicitly claims to guarantee is:

`hmac_valid(request) == (shop_header, topic_header, webhook_id_header, body are all authentic and bound together)`

but the actual guarantee is only `hmac_valid(request) == (body is authentic)`. Any attacker who can obtain one genuine `(body, hmac)` pair signed with the app's `client_secret` — trivially available to any merchant who installs the app on their own store and receives ordinary webhooks for that store — can resend that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) header with a different shop's domain. The signature still validates because it never covered those fields, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the body belongs to the victim shop.

### Impact Explanation
Handlers built on this gem's `WebhookHandler` interface are expected to trust `data.shop` as the authenticated tenant for the webhook payload (e.g., to look up the corresponding session/access token or to write data scoped to that shop). Because `shop` is not bound to the HMAC, an attacker who possesses one valid signed webhook body (from their own installed store) can make the host application process that body under a different shop's identity — a cross-tenant confusion primitive. Depending on how the host app models the topic/body pairing, this can lead to writing or triggering business logic against another merchant's tenant context using attacker-controlled body content, i.e., cross-tenant access, which is a Critical-severity outcome under the stated impact categories.

### Likelihood Explanation
Low-to-medium: it requires the attacker to (a) have at least one shop where the target app is installed (to obtain a genuinely signed body/HMAC pair — trivial for any public app since anyone can install it on a dev/test store), and (b) the host app's handler to key any privileged or cross-tenant-sensitive action off `data.shop`/`data.topic` without additional out-of-band verification. This is analogous to the original report's prerequisite ("a reward-token list state that must exist") — a real but narrow precondition, not requiring any secret leakage, TLS interception, or privileged account.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` (and `api_version`, if relevant to handler dispatch) in the material verified by `to_signable_string`, or otherwise cryptographically bind them to the raw body before trusting them for tenant/topic routing — mirroring the original fix's principle of not treating unauthenticated/uninitialized data as authoritative. At minimum, document that `WebhookMetadata#shop`/`#topic` are unauthenticated relative to the HMAC and must not be used as the sole tenant selector without additional verification (e.g., matching against a previously stored session for that shop).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`; Shopify sends a legitimate webhook with body `B` and valid `X-Shopify-Hmac-Sha256: HMAC(secret, B)`.
2. Attacker resends `POST /webhooks` to the host app with the same body `B` and same HMAC header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally a different `X-Shopify-Topic`).
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body normally. [6](#0-5) 
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `to_signable_string` (`@raw_body`), unchanged. [7](#0-6) 
5. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built with `shop == "victim-shop.myshopify.com"` and handed to the app's handler as if Shopify itself vouched for that shop/body pairing. [8](#0-7)

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
