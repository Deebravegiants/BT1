### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `shop`, `topic`, `webhook_id`, and `api_version` headers when building the `WebhookMetadata` passed to the host app's handler. The `shop` identity that the handler receives is not bound to the HMAC that proves the request originated from Shopify.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0)  The `shop`, `topic`, `webhook_id`, and `api_version` accessors are read directly from HTTP headers without any cryptographic binding: [2](#0-1) 

`Registry.process` validates only this body-HMAC via `Utils::HmacValidator.validate(request)`, then immediately builds `WebhookMetadata` using `request.shop` (and other header values) and forwards it to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate_signature` computes the HMAC purely over `verifiable_query.to_signable_string` (i.e., the raw body for webhooks) and compares it with `OpenSSL.secure_compare`: [4](#0-3) 

The identity binding that should hold is: **the `shop` value delivered to the handler == the `shop` that the HMAC-covered bytes were generated for**. Because the signable string is only the body, this equality never holds — the header `shop` is fully attacker-controlled independent of the HMAC. As the docs confirm, `data.shop` is the value host apps are expected to use to key merchant identity/session lookups in their webhook handler: [5](#0-4) 

### Impact Explanation
Any entity that has legitimately installed the app on their own store (an "unprivileged" tenant relative to other merchants) receives real webhooks with a valid `x-shopify-hmac-sha256` computed over a body they can also observe/control the shape of (e.g. by triggering `orders/create`, `app/uninstalled`, etc. on their own shop). Because the HMAC never covers the `x-shopify-shop-domain` header, that attacker can replay the exact same raw body + HMAC to the app's public webhook endpoint while substituting any victim shop's domain in the `shop-domain` header. `Registry.process` will accept the request (HMAC check passes, since it only checks the body) and hand the handler a `WebhookMetadata` claiming to be from the victim shop. If the host app's handler uses `data.shop` to look up sessions/access tokens, write merchant-scoped records, or attribute billing/inventory events (the exact pattern the library's own documentation recommends: `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), this crosses tenant boundaries — a classic authenticated-shop vs. shop-used-as-key mismatch, matching the “Critical – cross-tenant access” category.

### Likelihood Explanation
Reachable by any unprivileged internet user who can install the app on a store they control (a normal, low-privilege action) and can freely POST to the app's public webhook route with arbitrary headers, since nothing about the endpoint requires additional secrets beyond a previously-observed valid `(body, hmac)` pair. No access to `api_secret_key`, access tokens, or TLS interception is required — only replay of a webhook they legitimately received for their own shop with modified header.

### Recommendation
Do not trust the unauthenticated `shop`/`topic`/`webhook_id`/`api_version` headers as identity. At minimum, include the `shop-domain` (and ideally topic/webhook_id) in the signed payload, or independently verify `request.shop` corresponds to a shop for which this app holds an active session/registration before dispatching to the handler. Alternatively, extend `to_signable_string` in `lib/shopify_api/webhooks/request.rb` to bind the identifying headers into the HMAC computation, matching what Registry.process ultimately relies on.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw body `B` and the resulting valid header `x-shopify-hmac-sha256: H = HMAC(api_secret_key, B)`.
2. Attacker POSTs directly to the app's webhook endpoint with:
   - `x-shopify-topic: orders/create`
   - `x-shopify-hmac-sha256: H` (unchanged)
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (changed)
   - body: `B` (unchanged)
3. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` whose `hmac` still matches `B`, so `HmacValidator.validate` returns true (per `lib/shopify_api/utils/hmac_validator.rb`).
4. `Registry.process` calls the handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed_body_of_B, ...)`, i.e., data purportedly from `attacker-shop` is processed as if it came from `victim-shop`.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
