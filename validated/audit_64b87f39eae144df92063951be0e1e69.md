Found a concrete, reachable analog in `pallet-hyper-fungible-token`.

### Title
`update_token`'s `remove_chains` path deletes the source-authentication mapping needed to refund/deliver in-flight escrowed native-asset transfers, permanently freezing funds - (File: `modules/pallets/hyper-fungible-token/src/lib.rs`)

### Summary
`update_token` lets `CreateOrigin` remove a chain's configuration for a token via `TokenUpdate.remove_chains`, deleting `TokenContracts`, `ContractToAsset`, and `Precisions` entries for that `(asset, chain)` pair with no check for outstanding in-flight or escrowed funds tied to that route, mirroring the reported `removePToken` bug class (removal of asset/route bookkeeping without accounting for funds still committed to it).

### Finding Description
For a native asset, `send()` locks user funds into the pallet's custody account (`Self::pallet_account()`) and dispatches a cross-chain `Message` to the peer contract registered in `TokenContracts`/`ContractToAsset` for that destination chain: [1](#0-0) 

Both the receive path (`on_accept`) and the timeout/refund path (`on_timeout`) authenticate and price the message solely by looking up `ContractToAsset::<T>::get(source/dest, &from/to)` and `Precisions::<T>::get(asset, chain)`: [2](#0-1) [3](#0-2) 

`update_token`'s removal loop unconditionally deletes exactly these entries for a chain, with no check on whether there are pending sends still escrowed for that route: [4](#0-3) 

Because `on_timeout` requires `ContractToAsset::<T>::get(dest, &to)` to succeed (`HftError::UnknownContractOnTimeout` otherwise) and this same map is what `remove_chains` deletes, any transfer that was `send()`-escrowed before the governance-gated `update_token` removal, but whose ISMP request has not yet timed out or been delivered, becomes unrecoverable: `on_accept` on the destination will fail authentication just the same way if that side also drops its mapping, and — critically — if the *source* chain (the one holding escrow) removes the chain entry before the timeout fires, the eventual `on_timeout` refund call reverts with `UnknownContractOnTimeout`, since it cannot resolve `local_asset_id`. The escrowed native asset sits permanently in `Pallet::<T>::pallet_account()` with no code path capable of releasing it back to the sender (the only refund logic is gated on the now-deleted mapping).

### Impact Explanation
This is a permanent freezing-of-funds bug reachable by an ordinary unprivileged relayer/dispatcher flow: any user's outstanding `send()` funds an escrow, and a single governance/CreateOrigin call to `update_token` removing that chain (e.g. to fix a broken/compromised destination contract, exactly the scenario the Origin team cited as their rationale for keeping `removePToken` unchecked) can strand user funds indefinitely, since `on_timeout` cannot recover them without the deleted `ContractToAsset` entry. This meets the "permanent freezing of funds" acceptance bar.

### Likelihood Explanation
Likelihood is Medium: it requires the `CreateOrigin` (a privileged but expected-to-be-used-defensively actor, per the Origin team's stated rationale for the analogous bug) to call `update_token` with `remove_chains` while transfers are in flight — a realistic operational scenario (deprecating/migrating a chain or reacting to a compromised peer contract) rather than a contrived edge case, and no additional check prevents it.

### Recommendation
Before removing a chain from `TokenContracts`/`ContractToAsset`/`Precisions`, either (a) block removal while any known in-flight requests for that `(asset, chain)` pair are outstanding, or (b) preserve the `ContractToAsset` reverse-mapping (or a dedicated historical mapping) long enough for `on_timeout` refunds to still resolve `local_asset_id`/`erc_decimals`, so escrowed funds can always be released back to their original owner even after the route is deregistered for new sends.

### Proof of Concept
1. `CreateOrigin` registers asset `A` (native) for `StateMachine::Evm(X)` via `register_token`.
2. User calls `send()` with `asset_id = A`, `destination = Evm(X)`; funds are locked into `pallet_account()`, and a `DispatchPost` is emitted with a timeout.
3. Before the request is delivered or times out, `CreateOrigin` calls `update_token` with `remove_chains = [Evm(X)]` for asset `A` (e.g., to react to a compromised destination contract) — this deletes `TokenContracts`, `ContractToAsset`, and `Precisions` for `(A, Evm(X))`.
4. When the request eventually times out, `pallet-ismp` invokes `on_timeout`, which calls `ContractToAsset::<T>::get(dest, &to)` — this now returns `None`, so the call returns `Err(HftError::UnknownContractOnTimeout)`.
5. The user's escrowed funds remain in `Pallet::<T>::pallet_account()` with no remaining code path to release them back to the sender.
