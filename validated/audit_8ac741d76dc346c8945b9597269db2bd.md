### Title
Unbounded Commitment Payload Causes O(n²) Gas Blowup in `Codec.Encode` on the Permissionless `handleConsensus` Path - (File: evm/src/consensus/Codec.sol)

### Summary
`handleConsensus()` in `HandlerV2.sol` is a permissionless entry point that lets any caller submit a BEEFY consensus proof for verification. In `EcdsaBeefy.verifyMmrUpdateProof`, the commitment's `payload` array (an attacker-supplied array of `(bytes2 id, bytes data)` pairs decoded straight from the submitted proof) is re-serialized via `Codec.Encode(commitment)`, which builds the encoded byte string by repeatedly calling `bytes.concat(payload, ...)` inside a `for` loop over `commitment.payload`.

### Finding Description
`Codec.Encode(Commitment memory commitment)` accumulates the encoded payload as follows: [1](#0-0) 

Each iteration of the loop reassigns `payload = bytes.concat(payload, ...)`. In Solidity, `bytes.concat` allocates a brand-new memory buffer and copies the entire existing contents plus the new chunk into it every time it is called — there is no in-place append. Growing a buffer this way across `n` iterations does `O(n)` copies whose sizes sum to `O(n²)` total bytes copied, exactly the same complexity-class bug as the `Base62.decode` issue in the reference report.

This function is reached directly from `EcdsaBeefy.verifyMmrUpdateProof`, which is invoked by `EcdsaBeefy.verify`, which is called from the permissionless `handleConsensus` entry point: [2](#0-1) [3](#0-2) 

`commitment.payload` is decoded from `proof` (the caller-supplied `bytes calldata`) via `abi.decode(proof, (RelayChainProof, ParachainProof))` inside `verify()`, and nothing in `verifyMmrUpdateProof` bounds `commitment.payload.length` before the `Codec.Encode` call — the only checks performed before reaching `Codec.Encode` are the authority-set id and signature-count threshold checks, neither of which constrain the payload array size.

### Impact Explanation
Unlike the off-chain Discourse worker-pool exhaustion, EVM execution is metered by gas paid by the caller, so this is not literally a shared-thread-pool DoS. However, it is a genuine correctness/availability hazard on the message-delivery-critical path: an attacker can craft a `RelayChainProof` with a `commitment.payload` array containing many entries (e.g. hundreds of small `PayloadItem`s), forcing `Codec.Encode` into quadratic-cost recopying. Because this call happens *before* the expensive signature/membership verification failure can be detected, a well-crafted but ultimately-invalid proof can be made to consume gas disproportionate to its "useful" size, and — more importantly — a legitimate large-but-valid-shaped payload can push a proof to the block gas limit purely due to this quadratic re-encoding overhead, causing `handleConsensus` calls to revert with out-of-gas even where the actual signature-set is small and would otherwise be cheap to verify. Since `handleConsensus` gates the entire message-delivery pipeline (POST/GET request/response handling all depend on a fresh consensus state), an attacker able to force legitimate consensus updates against a specific authority-set epoch to consistently blow the gas limit can stall message delivery for that route — a route-unable-to-deliver-messages condition.

### Likelihood Explanation
Medium. `handleConsensus` is fully permissionless and reachable by anyone with a syntactically valid but semantically spurious proof structure (the `payload` array length is attacker-controlled independent of the number of real BEEFY payload IDs, since the loop that reads `MMR_ROOT_PAYLOAD_ID` at line 144-148 simply scans the whole array and does not cap its size). The attacker pays their own gas for the encode-and-fail attempt, so this is closer to a griefing/self-limited cost than a shared-resource exhaustion, which somewhat limits severity relative to the reference off-chain worker-pool bug, but the quadratic blow-up is real and unbounded, and it sits directly upstream of the "which authority set signed this" hash comparison used for ECDSA `ecrecover`, meaning it always executes on every `handleConsensus` call regardless of whether the signatures ultimately verify.

### Recommendation
Bound `commitment.payload.length` (and each `data` element's length) to a small constant before entering `Codec.Encode`/`verifyMmrUpdateProof`, and rewrite `Codec.Encode` to pre-compute total length and write into a single pre-allocated buffer (e.g. via `abi.encodePacked` accumulation into a fixed-size scratch buffer or manual `mstore` writes) instead of repeated `bytes.concat` reallocation, eliminating the O(n²) growth entirely.

### Proof of Concept
1. Construct a `BeefyConsensusProof` whose `RelayChainProof.signedCommitment.commitment.payload` array contains, say, 500 `PayloadId` entries (only one of which needs to be the real `mh` MMR-root id; the rest can be arbitrary 2-byte ids with arbitrary `data`).
2. Ensure `sigLen`/`authoritySet.len` still satisfy `checkParticipationThreshold` so the code path reaches `Codec.Encode(commitment)` (line 152 of `EcdsaBeefy.sol`).
3. Call `handleConsensus(host, proof)` with this crafted proof.
4. Observe gas consumption in `Codec.Encode`'s loop growing quadratically with payload length via repeated `bytes.concat` reallocation, dramatically exceeding the cost expected for a payload of that byte size, and compare against a baseline single-payload-entry proof of equivalent total byte size to demonstrate the non-linear (quadratic) scaling.

    function Encode(Commitment memory commitment) internal pure returns (bytes memory) {
        uint256 payloadLen = commitment.payload.length;
        bytes memory payload = bytes("");
        for (uint256 i = 0; i < payloadLen; i++) {
            payload = bytes.concat(
                payload,
                abi.encodePacked(commitment.payload[i].id),
                ScaleCodec.encodeBytes(commitment.payload[i].data)
            );
        }

        return bytes.concat(
            ScaleCodec.encodeUintCompact(payloadLen),
            payload,
            ScaleCodec.encode32(commitment.blockNumber),
            ScaleCodec.encode64(commitment.validatorSetId)
        );
    }
