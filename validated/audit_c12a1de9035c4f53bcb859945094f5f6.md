### Title
Webhook `shop-domain` header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and exposes an HMAC-verifiable signature over the raw request body only, while the `shop` (tenant identity) is read from the unauthenticated `X-Shopify-Shop-Domain` header. An attacker who can obtain one genuinely-signed webhook (e.g. by installing the app on their own store) can replay that payload with a modified `shop-domain` header pointing at a victim shop; `Utils::HmacValidator.validate` will still pass because the HMAC only signs `@raw_body`.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header without any cryptographic binding to the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` verifies `verifiable_query.hmac` against `verifiable_query.to_signable_string` only: [3](#0-2) 

Because `to_signable_string` (the bytes covered by the HMAC) is disjoint from `shop` (the field the host application is expected to trust as the tenant identifier), the identity binding `shop-used-for-tenant-lookup == shop-cryptographically-verified` does not hold. This is precisely the "field acted on but not covered by the HMAC" class: the gem verifies bytes (`@raw_body`) but the caller is meant to trust a value (`shop`) that was never part of what was verified.

### Impact Explanation
Any unprivileged actor who can install the merchant's app on a store they control (a normal, unprivileged flow for public/embedded Shopify apps) receives genuinely HMAC-signed webhook deliveries for their own shop. They can capture one such request and resend it (or forge an equivalent one, since only the body needs to match a real signed body — a webhook payload is otherwise attacker-influenced content for many topics) with the `X-Shopify-Shop-Domain` header rewritten to a victim shop domain. Because this gem's own `Request#shop` accessor — the only shop-identity accessor it exposes, and the one host applications use to pick the tenant's session/access token — is unauthenticated, host code that follows the gem's documented pattern (validate via `HmacValidator.validate`, then use `request.shop` to select per-tenant state) will process/attribute the webhook under the wrong tenant's session. This is a cross-tenant confusion vulnerability rooted entirely in this gem's `Request`/`HmacValidator` design, not in host misuse.

### Likelihood Explanation
High reachability: any app developer, including a hostile one, can register their own store, receive a valid signed webhook, and replay it with a different `shop-domain` header value against the same public webhook endpoint — no access token, `client_secret`, or privileged account is needed to mount the attack itself (only knowledge of the target's public webhook URL, which is standard and typically documented/public). The only barrier is timing/reuse of one previously delivered, correctly-signed body, which is trivial to satisfy for topics whose payload shape is generic/predictable across shops.

### Recommendation
Include the shop-domain (and ideally the API version/topic) in the signed material used by `Request#to_signable_string`, or otherwise cryptographically bind the `shop-domain` header to the verified HMAC before exposing `Request#shop`, so that a payload verified for shop A cannot be relabeled as belonging to shop B.

### Proof of Concept
```ruby
# Attacker installs the app on their own store "attacker.myshopify.com" and
# receives a genuine webhook delivery with headers:
#   X-Shopify-Hmac-Sha256: <valid hmac for raw_body>
#   X-Shopify-Shop-Domain: attacker.myshopify.com
#   X-Shopify-Topic: orders/create
#   X-Shopify-Webhook-Id: ...
# and some raw_body B.

headers = {
  "x-shopify-hmac-sha256" => captured_valid_hmac,
  "x-shopify-shop-domain" => "victim.myshopify.com", # rewritten
  "x-shopify-topic" => "orders/create",
  "x-shopify-webhook-id" => "1",
}

req = ShopifyAPI::Webhooks::Request.new(raw_body: captured_body, headers: headers)
ShopifyAPI::Utils::HmacValidator.validate(req) # => true, because HMAC only covers raw_body
req.shop # => "victim.myshopify.com" (untrusted, attacker-controlled, but "verified" by the gem's own check)
```
The host application, following the gem's intended usage (`HmacValidator.validate(req)` then trusting `req.shop`), now processes attacker-controlled data under the victim tenant's identity.
