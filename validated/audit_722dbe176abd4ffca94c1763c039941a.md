## Title
Anyone can front-run and permanently squat a lockup account's deterministic address via `LockupFactory::create` - (File: `lockup-factory/src/lib.rs`)

### Summary
This is a direct NEAR analog of the reported `CoverRightTokenFactory` issue: a public, permissionless factory function derives a **deterministic, front-runnable** target account/address purely from public inputs, and deploys to it before any privileged/legitimate actor gets a chance to reserve it. In `LockupFactory::create`, the lockup account ID is computed solely from `sha256(owner_account_id)` and the factory's own account ID, with no unique salt/nonce tied to the caller or the funding transaction. [1](#0-0) 

### Finding Description
`create` is a public, unprivileged, payable method: any account can call it with any `owner_account_id` as long as they attach at least `MIN_ATTACHED_BALANCE`. [2](#0-1) 

The resulting lockup account name is fully deterministic and computable off-chain by anyone who knows (or predicts) the intended `owner_account_id` — e.g. a publicly known employee/investor account that the foundation or a funder intends to set up a lockup for: [3](#0-2) 

Because NEAR account names are globally unique and `create_account()` fails if the account already exists, an unprivileged attacker can:
1. Predict/learn the `owner_account_id` that a legitimate funder intends to use.
2. Call `create` first themselves (with only the minimum deposit, and attacker-chosen `lockup_duration`, `vesting_schedule`, `release_duration`, `whitelist_account_id`), which deploys the real lockup contract binary but pre-occupies the deterministic account name `sha256(owner_account_id)[..20].<factory>`.
3. When the legitimate funder later calls `create` with the same `owner_account_id` intending to fund the real, correctly-configured lockup, the `create_account()` action fails because the account name is already taken. The whole action batch in that receipt fails, `is_promise_success()` returns `false` in the callback, and the deposit is simply refunded to the legitimate funder: [4](#0-3) 

The legitimate, canonical, deterministic lockup address for that `owner_account_id` is now permanently unusable — the account already exists with attacker-chosen lockup parameters and cannot be recreated at that name. There is no on-chain reservation, nonce, or authorization check tying the deterministic address to a specific, privileged, or first-come funding party beyond simple transaction ordering, so a well-resourced/front-running attacker with no special privileges can win the race deterministically once they observe the target `owner_account_id`.

### Impact Explanation
This maps to the "factory refund" flow explicitly called out in scope: the legitimate funding call is forced through the refund path, and the intended, expected deterministic lockup account for the given owner becomes permanently squatted with attacker-chosen (potentially minimal/degenerate) lockup terms, rather than the terms the real funder intended. This is a permanent, irrecoverable griefing of the intended lockup account provisioning for a specific owner — the legitimate large deposit can never land at the expected, protocol-computed address for that owner again.

### Likelihood Explanation
The entrypoint is fully public and unprivileged (`create` has no access control), and the target address is deterministic and computable by anyone who can guess or observe the `owner_account_id` ahead of time (e.g. from an announcement, an on-chain hint, or a mempool-visible pending transaction). The only cost to the attacker is the minimum attached deposit (`MIN_ATTACHED_BALANCE`), which is refundable in spirit but not economically prohibitive relative to the disruption caused to an intended lockup of a much larger amount.

### Recommendation
Do not derive the lockup account ID purely from a public, guessable value (`owner_account_id`) with no binding to caller identity or a unique creation request. Options include: requiring `create` to be called only by an authorized/whitelisted funder or the foundation, incorporating a caller-specific or factory-issued nonce/salt into the account ID derivation, or maintaining an on-chain reservation/registry so that a specific `owner_account_id` can only have its canonical lockup created once via an authorized flow (analogous to verifying calls are routed only through the intended privileged entry point, as recommended for the original `CoverRightTokenFactory` finding).

### Proof of Concept
1. Attacker observes/learns that a lockup for `owner_account_id = "alice.near"` is intended to be created via `LockupFactory::create` (e.g., from a public announcement or vesting schedule disclosure).
2. Attacker computes `lockup_account_id = hex(sha256("alice.near")[..20]) + "." + <factory_account_id>` off-chain (same formula as `lockup-factory/src/lib.rs:119-121`).
3. Attacker calls `create(owner_account_id: "alice.near", lockup_duration: 0, ...)` attaching only `MIN_ATTACHED_BALANCE`, before the legitimate funder's transaction is included.
4. The attacker's transaction succeeds and creates/deploys the lockup contract at the deterministic address with attacker-chosen (minimal/degenerate) terms.
5. The legitimate funder's later `create("alice.near", <real large deposit>, <real vesting schedule>, ...)` call executes `create_account()` on the already-existing account, the action fails, and `on_lockup_create` refunds the funder's deposit — the canonical, intended lockup for `alice.near` can never be created at that address again.

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
