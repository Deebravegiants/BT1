### Title
RAY-scaled debt/supply valuation overflows before index caps and permanently freezes a market - (File: common/src/rates/simulate.rs)

### Summary
A sufficiently large market can grow its borrow or supply index until `scaled_shares * index / RAY` exceeds the `i128` result domain. Accrual computes these unscaled values before applying the index caps, so `accrue_step` panics with `MathOverflow` even though both stored indexes remain below `MAX_BORROW_INDEX_RAY` and `MAX_SUPPLY_INDEX_RAY`. [1](#0-0) [2](#0-1) 

Because every pool mutation synchronizes the market before mutating it, the first failing accrual prevents repayment, withdrawal, liquidation, further supply, borrowing, recapitalization, and index maintenance for that market. [3](#0-2) [4](#0-3) 

### Finding Description
The controller exposes permissionless `supply`, `borrow`, and `update_indexes`; `supply` accepts a `Vec<(HubAssetKey, i128)>`, `borrow` accepts a collateral-backed `Vec<(HubAssetKey, i128)>`, and `update_indexes` accepts `Vec<HubAssetKey>`. [5](#0-4) [6](#0-5) 

The pool's `global_sync` loops over elapsed time in chunks of at most `MAX_COMPOUND_DELTA_MS`, but chunking does not bound the value represented by the accumulated scaled shares. [7](#0-6) 

Each chunk calls `accrue_step`, whose first operations compute `scaled_to_original(borrowed, borrow_index)` and `scaled_to_original(supplied, supply_index)`. [8](#0-7) 

`scaled_to_original` delegates to `Ray::mul`, and `Ray::mul` delegates to `mul_div_half_up`; `mul_div_half_up` returns a panic-inducing `MathOverflow` when the exact quotient cannot fit in `i128`. [9](#0-8) [10](#0-9) [11](#0-10) 

The overflow can happen before `update_borrow_index` gets an opportunity to clamp the next index, because it is the valuation of the already-stored `borrow_index` that panics. [2](#0-1) 

Cap validation only ensures that a cap's initial asset-to-RAY representation fits `i128`; it does not reserve headroom for future index multiplication. [12](#0-11) [13](#0-12) 

After a failure, the transaction reverts before `mark_accrued` can store a newer `last_timestamp`, so the same overflowing chunk is recomputed by every later call. [7](#0-6) 

### Impact Explanation
This is a permanent freezing-of-funds condition for the affected `(hub_id, asset)` market. Suppliers cannot withdraw, borrowers or third parties cannot repay, liquidators cannot execute debt repayment or collateral seizure, and `recapitalize` cannot repair the market because each path first synchronizes interest and hits the same panic. [3](#0-2) [14](#0-13) [15](#0-14) 

The production regression test demonstrates the terminal state directly: after `update_indexes` fails with `MathOverflow`, both a one-unit withdrawal and a repayment fail with the same error while the borrow index remains below `MAX_BORROW_INDEX_RAY`. [16](#0-15) 

### Likelihood Explanation
Likelihood is Medium. An unprivileged user cannot trigger this with an ordinary amount; the market's scaled share total must be large enough that index growth can drive `scaled * index / RAY` past `i128::MAX`. The tested configuration uses a very large 18-decimal market and high utilization, but the configured cap boundary permits the initial RAY representation while leaving no representation headroom for later index growth. [17](#0-16) [12](#0-11) 

No privileged action, oracle manipulation, malformed token, or off-chain component is required to reach the failing arithmetic once such a book exists: permissionless `controller.update_indexes(caller, [hub_asset])` invokes the pool's accrual path, and the same arithmetic runs before ordinary repayments and withdrawals. [18](#0-17) [19](#0-18) 

### Recommendation
Make scaled-value arithmetic saturate or use a wider intermediate representation before converting back to `Ray`, rather than panicking on the stored-state valuation.

Specifically:

- Replace `scaled_to_original`'s half-up `Ray::mul` path with a checked/saturating primitive appropriate for aggregate market valuation.
- Keep `borrow_index` and `supply_index` capped, but ensure the cap is enforced before the unrepresentable multiplication is repeated on every subsequent call.
- Add a market-scale invariant that bounds `scaled * MAX_*_INDEX_RAY / RAY`, not merely the initial `scaled` value, to the domain used by accrual.
- Treat the existing regression `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` as a failing safety case: after the fix it should continue past the former overflow boundary, clamp at the index cap, or fail a bounded setup precondition rather than freezing after funds are deposited. [20](#0-19)

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

/// Computes `x * y / d` rounded half up. Requires `x >= 0`, `y >= 0`, and `d > 0`; a
/// `debug_assert` checks this in debug builds. Panics with `GenericError::DivisionByZero` if
/// `d == 0`, and with `GenericError::MathOverflow` if any other precondition is violated or if
/// the result does not fit in `i128`.
pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.
    require_nonzero_divisor(env, d);
    debug_assert!(
        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}

/// Returns the largest cap, in asset base units, whose ray-scaled form still
/// fits in `i128`.
///
/// Returns 0 when `asset_decimals > RAY_DECIMALS`, since the ray form is not
/// representable in that case. Enforced by
/// [`require_cap_within_asset_domain`], so stored caps can never overflow the
/// asset→ray rescale.
pub fn max_cap_for_decimals(asset_decimals: u32) -> i128 {
    let Some(exp) = RAY_DECIMALS.checked_sub(asset_decimals) else {
        return 0;
    };
    let upscale = 10i128
        .checked_pow(exp)
        .expect("10^(RAY_DECIMALS - asset_decimals) fits i128 for asset_decimals <= RAY_DECIMALS");
    i128::MAX / upscale
}
