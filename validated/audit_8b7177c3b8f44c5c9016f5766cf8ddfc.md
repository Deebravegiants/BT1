Confirmed: `ProxyModule::on_response` in `parachain/runtimes/gargantua/src/ismp.rs` claims in its comment to enforce the bandwidth gate "mirroring the request path in `on_accept`," but the actual `try_consume` call is entirely absent from the function body — it goes straight from the destination-chain check to module dispatch.

### Title
Bandwidth gate is never enforced on `GetResponse` delivery, allowing unmetered response traffic - (File: parachain/runtimes/gargantua/src/ismp.rs)

### Summary
`ProxyModule::on_accept` correctly calls `pallet_bandwidth::BandwidthGate::try_consume(source, from, bytes)` before routing a `PostRequest` to its destination module [1](#0-0) . The sibling `on_response` handler carries a comment stating it "Mirrors the request path in `on_accept`" for exactly this purpose, but never actually calls `try_consume` anywhere in its body before dispatching to the destination module callback [2](#0-1) . This is structurally the same bug class as the Discourse advisory: an authorization/metering gate exists and is documented as applying uniformly, but one of the two code paths that should enforce it (POST vs. GET-response) silently skips the check, and the omission only becomes visible when read against the parallel, correctly-gated code path.

### Finding Description
The bandwidth subsystem is designed to meter "outbound traffic per (source chain, app)" and reject messages once a subscription's byte allowance is exhausted [3](#0-2) . The documentation explicitly states: "Every non-purchase POST request from a registered source chain runs through `BandwidthGate::try_consume`," and separately: step 9-11 describe the dispatch/gate flow only in terms of POST dispatch [4](#0-3) . In the runtime's actual `IsmpRouter` implementation (`ProxyModule`), the `on_accept` (POST) path enforces the gate via `try_consume(&request.source, &request.from, bytes)`, skipping only registered purchase messages [5](#0-4) .

The `on_response` (GET response) path, however, has a comment claiming the same enforcement ("Bandwidth gate. Mirrors the request path in on_accept: the chain and module that produced the response pay for the bytes they deliver") but the code beneath it only checks `response.dest_chain() != HostStateMachine::get()` and then dispatches directly to the destination pallet's `on_response` callback — there is no `try_consume` call at all [2](#0-1) .

By contrast, `pallet-state-coprocessor`'s own `handle_get_requests` — a separate, independent code path for GET requests submitted via `handle_unsigned` — does correctly call `<T as Config>::BandwidthGate::try_consume(&response.get.source, &response.get.from, bytes)` per response before minting relayer reputation [6](#0-5) . This confirms the gate is intended to be applied to GET-response traffic as well, and that its absence in `ProxyModule::on_response` is an authorization/metering gap rather than an intentional design choice — exactly mirroring Discourse's `can_chat?` checking one necessary condition (group membership) while silently omitting the other (`chat_enabled`).

`GetResponse` delivery is reachable by any relayer submitting `HandlerV2.handleGetResponses` on the EVM side or the equivalent Substrate response path, which the ISMP core `handlers::response::handle` routes to `IsmpModule::on_response` on successful proof verification [7](#0-6) . Once the state/membership proof for the response is valid, `ProxyModule::on_response` is invoked with no bandwidth check, so an app that has exhausted (or never purchased) its bandwidth allowance can still receive/relay unlimited amounts of `GetResponse` traffic and consume unmetered chain-storage/computation resources tied to its module's `on_response` handler.

### Impact Explanation
This breaks the metering invariant relied upon by the Bandwidth product: an app is supposed to be "closed for business" once its subscription is empty, forcing a top-up purchase before continuing [8](#0-7) . Because `on_response` never calls `try_consume`, any module reachable through the GET-response path bypasses metering entirely and indefinitely, regardless of allowlist status or subscription balance. This is a route that is supposed to be gated (paid) but is left permanently open, i.e., a bypass of the fee/bandwidth accounting the protocol depends on for its GET-response delivery route — matching the "relayer fee and reward accounting" / unmetered-route class explicitly in scope.

### Likelihood Explanation
High likelihood of exploitation for any app or relayer that wants free GET-response bandwidth: it requires no privileged access, only submitting a normal `GetResponse` message with a valid state proof through the standard relayer flow (`HandlerV2.handleGetResponses` → `host.dispatchIncoming` → `on_response`), which is precisely the intended, unprivileged, single-transaction delivery path for relayers/response producers.

### Recommendation
Add the same `try_consume` bandwidth-gate call in `ProxyModule::on_response` that already exists in `on_accept`, keyed on `response.get.source` and `response.get.from` (mirroring `pallet-state-coprocessor`'s `handle_get_requests` implementation), before dispatching to the destination module's `on_response` callback. Add a regression test asserting that an app with an exhausted/absent subscription is rejected on the `GetResponse` delivery path exactly as it is on the `PostRequest` path.

### Proof of Concept
1. Do not purchase (or exhaust) a bandwidth subscription for `(sourceChain, appModuleId)`, and do not add `appModuleId` to the `Allowlist`.
2. Have the app on the source chain dispatch a `GetRequest` (bandwidth is not checked on requests originating locally — only inbound POSTs are gated in `on_accept`).
3. Obtain a valid state proof for the corresponding `GetResponse` and submit it via the standard relayer flow to `HandlerV2.handleGetResponses` (EVM) or the equivalent Substrate response handler, which invokes `ismp::core::handlers::response::handle`, which calls `IsmpModule::on_response` after proof verification [7](#0-6) .
4. Observe that `ProxyModule::on_response` dispatches directly to the destination pallet's `on_response` without any `BandwidthGate::try_consume` call or `GateError` rejection, succeeding regardless of the app's subscription state [2](#0-1) , in contrast to the equivalent POST path which would reject the same app with `GateError::NoAllowance` [5](#0-4) .

	fn on_accept(&self, request: PostRequest) -> Result<Weight, anyhow::Error> {
		// Bandwidth gate. Always-enforce unless the `no-bandwidth` flag
		// is set; skipped for purchase messages so the recharge flow
		// itself doesn't need bandwidth. With the flag on the gate is a
		// no-op and this block is compiled out entirely.
		#[cfg(not(feature = "no-bandwidth"))]
		if !pallet_bandwidth::Pallet::<Runtime>::is_purchase_message(&request) {

				&request.from,

				anyhow!(
					"bandwidth gate: {err} (source={:?}, from={:x?})",
					request.source,
					request.from
				)
			})?;
		}

	fn on_response(&self, response: GetResponse) -> Result<Weight, anyhow::Error> {
		// Bandwidth gate. Mirrors the request path in `on_accept`: the chain
		// and module that produced the response pay for the bytes they
		// deliver. Compiled out when the `no-bandwidth` flag is on.
		if response.dest_chain() != HostStateMachine::get() {
			return Ok(Weight::from_parts(0, 0));
		}

		let dest = &response.get.from;

		let pallet_id = ModuleId::from_bytes(dest).map_err(|err| Error::Custom(err.to_string()))?;

		match pallet_id {

			_ => Err(anyhow!("Destination module not found")),
