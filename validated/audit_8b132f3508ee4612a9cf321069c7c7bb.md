Based on my investigation, I've identified a genuine analog vulnerability in the gateway's HTTP response cache.

### Title
Cross-workflow HTTP response cache poisoning/leakage due to WorkflowID-agnostic cache key (workflow isolation bypass) - (File: `core/services/gateway/handlers/capabilities/v2/response_cache.go`)

### Summary
The gateway's `responseCache` is documented as providing "workflow-scoped caching" with "Workflow Isolation: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage" [1](#0-0) . However, the actual cache key, produced by `gateway.OutboundHTTPRequest.Hash()`, explicitly excludes `WorkflowID` and only differentiates on `WorkflowOwner`, method, URL, headers, and body, as proven by the test itself: `"having different workflowID results in same Hash"` [2](#0-1) , while the comment in the cache struct confirms the key is `"a hash of the request (method, URL, headers, body, workflowOwner)"` [3](#0-2) .

### Finding Description
`responseCache.Set` and `responseCache.Fetch` key stored HTTP responses purely by `req.Hash()` [4](#0-3) , and `Fetch` returns a previously cached response whenever `MaxAgeMs > 0` and the hash matches [5](#0-4) . Since the hash omits `WorkflowID`, any two different workflows belonging to the same `WorkflowOwner` that issue an HTTP action with the same method/URL/headers/body will share a single cache entry, contradicting the documented per-workflow isolation guarantee. This is directly analogous to the Leantime "insufficiently protected credentials" advisory: improper cache scoping/control causes a response intended for one execution context to be served to another, unrelated context — here, one workflow execution can receive cached HTTP response data (which may include sensitive data returned by the external endpoint, e.g., tokens or PII in the JSON body) that was originally fetched for a *different* workflow, without ever re-issuing the request or being authorized for that data. The gateway trust model is designed to isolate workflows even under the same owner ("Workflow Isolation" is called out explicitly as a security property in the README), so any workflow able to reach `MethodHTTPAction` with attacker-controlled `CacheSettings.MaxAgeMs` can retrieve stale, cross-workflow cached responses.

### Impact Explanation
An attacker (or malicious/compromised workflow) can obtain HTTP responses intended for another workflow of the same owner without making the actual outbound HTTP call, potentially disclosing sensitive response bodies (tokens, secrets embedded in API responses, session data) that were cached from a request made under different, more privileged workflow/execution context. It also enables workflow-to-workflow cache poisoning: a malicious workflow can pre-populate the cache with attacker-controlled content that a legitimate workflow will later consume as if it came from a trusted external endpoint (impacting integrity of downstream automated decisions/fund movement in CRE workflows).

### Likelihood Explanation
Reachable directly from any workflow node request handled via `MethodHTTPAction` message flow (`gatewayHandler.HandleNodeMessage` → `makeOutgoingRequest` → `responseCache.Fetch`/`Set`) [6](#0-5) . No special privilege beyond being an allowlisted workflow node is required — an attacker only needs to control `CacheSettings.MaxAgeMs`/`Store` and match method/URL/headers/body of a target workflow's request, which is plausible since URLs/methods are often well-known integration endpoints.

### Recommendation
Include `WorkflowID` (or a stronger workflow-execution scoping value) in the cache key computed by `Hash()`, or explicitly scope the `responseCache` map by workflow ID in addition to the request hash, so that cache entries cannot be shared across workflow executions. Update/remove the misleading "Workflow Isolation" documentation once fixed, and add a regression test asserting different `WorkflowID` values produce different cache entries.

### Proof of Concept
1. Workflow A (owner `0xOwner`) issues an HTTP action to `https://api.example.com/data` with `CacheSettings.Store=true` and headers `{"Authorization": "<token-A>"}`. The gateway fetches and caches the response under `Hash(method, url, headers, body, "0xOwner")`.
2. Workflow B (same owner `0xOwner`, different `WorkflowID`) issues an HTTP action to the same URL/method/headers/body but with `CacheSettings.MaxAgeMs > 0`. Because `WorkflowID` is not part of the hash (see `response_cache_test.go` lines 139-149), Workflow B's `Fetch` call hits the same cache entry and receives Workflow A's cached response without the gateway ever validating that B is authorized to see A's data. ## 3. HTTP Action Message Handling

### 3.1 Process Flow

1. **Request Reception**: Gateway receives HTTP action request from a workflow node
2. **Rate Limiting**: Validates node rate limits
3. **Request Parsing**: Extracts `OutboundHTTPRequest` from the JSON-RPC message
4. **Cache Check**: Determines if request should use cached response or fetch fresh data
5. **HTTP Execution**: Makes actual HTTP request to external endpoint
6. **Response Caching**: Stores cacheable responses (2xx, 4xx status codes) only if `CacheSettings.Store` is `true`
7. **Node Response**: Sends HTTP response back to requesting node

### 3.2 Caching Behavior

- **Cacheable Responses**: 2xx (success) and 4xx (client error) status codes.
- **Cache TTL**: Configurable, default 10 minutes
- **Cache Key**: Generated from workflow ID and request hash
- **Cache Invalidation**: Time-based expiration with periodic cleanup
- **Cache Strategy**: All cacheable responses are cached; Non-zero `CacheSettings.MaxAgeMs` determines whether to return a cached value or make a fresh request
- **Workflow Isolation**: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage

func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

	// Slow path: singleflight deduplicates concurrent fetches per key.
	// Cache check + store happen inside the flight so the key isn't released
	// until the result is cached, closing the race window between singleflight
	// completion and cache write.
	result, _, _ := rc.flight.Do(cacheKey, func() (any, error) {
		// Re-check cache: a previous flight may have just stored the result.
		rc.cacheMu.RLock()
		cachedResp, exists := rc.cache[cacheKey]
		rc.cacheMu.RUnlock()
		if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
			rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
			return cachedResp.response, nil
		}

		response := fetchFn()

		if storeOnFetch && isCacheableStatusCode(response.StatusCode) {
			rc.cacheMu.Lock()
			rc.cache[cacheKey] = &cachedResponse{
				response: response,
				storedAt: time.Now(),
			}
			rc.cacheMu.Unlock()
		}

		return response, nil
	})

	return result.(gateway.OutboundHTTPResponse)
}
