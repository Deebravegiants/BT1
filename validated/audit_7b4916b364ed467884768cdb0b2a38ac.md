Based on my investigation, I've confirmed the vulnerability. Here is the analysis:

### Title
Webhook shop-domain header not covered by HMAC signature allows cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while the `shop`, `topic`, `webhook_id`, and `api_version` values consumed downstream are all read directly from HTTP headers that are never included in the HMAC-signed content [2](#0-1) . `Registry.process` validates only the HMAC over the body and then trusts `request.shop` and `request.topic` unconditionally to build `WebhookMetadata` handed to the app's handler [3](#0-2) .

### Finding Description
The identity binding broken here is: **HMAC-verified bytes (`raw_body`) ≠ bytes acted upon (`shop`, `topic`, `webhook_id`, `api_version` headers)**. `Utils::HmacValidator.validate` computes `HMAC(api_secret_key, request.to_signable_string)` and constant-time-compares it to the `hmac-sha256` header [4](#0-3) , but `to_signable_string` for a webhook request only ever returns the raw body — it never mixes in the shop domain, topic, or webhook id [1](#0-0) . Critically, the app's `api_secret_key` (`client_secret`) used to sign webhooks is the *same* secret shared across all shops that install the app, not a per-shop secret — this is confirmed by the OAuth code path which sends the same `client_secret` for every shop's token exchange [5](#0-4) .

An unprivileged internet user can install the target public app on their own (e.g., free trial) Shopify store, an action requiring no special privilege. Doing so, they will receive genuine webhook deliveries with a body+HMAC pair that is valid under the app's shared secret. Because the `shop-domain` header is excluded from the signed payload, the attacker can replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header (and potentially `topic`/`webhook_id`) to name a victim shop. `Utils::HmacValidator.validate` will still pass because it only checks the untouched `raw_body` [6](#0-5) , and `Registry.process` will invoke the app's handler believing the event legitimately originated from the victim shop [7](#0-6) .

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce: an attacker who only controls their own store's webhook traffic can cause the app to process (and act on, e.g. create/update/delete records, revoke access, or trigger `shop/redact`/`customers/redact` mandatory compliance flows) data attributed to a different merchant's shop. This is a cross-tenant access issue, matching the Critical impact category (cross-tenant access) defined in scope.

### Likelihood Explanation
Likelihood is realistic: becoming an "installer" of a public Shopify app on a free/dev store is trivial for any internet user, and once installed, they legitimately receive at least one valid `(body, hmac)` pair signed with the shared app secret. Replaying it with a modified `shop-domain` header requires no cryptographic secret and only basic HTTP tooling (e.g., curl/Postman) against the app's public webhook endpoint.

### Recommendation
Include the trust-critical headers (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signable content in `Request#to_signable_string`, or independently verify that `shop` matches a shop the app has an active session/install for before trusting it in `WebhookMetadata`. At minimum, document that consuming apps must not treat `data.shop` as authenticated purely by HMAC validity and must cross-check it against their own install records.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, unprivileged action).
2. Shopify sends a webhook to the app: body `B`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: HMAC(secret, B)`.
3. Attacker intercepts/logs this delivery (e.g., via a proxy they control since it's their own store's webhook), then replays the identical `B` and `hmac-sha256` value to the app's public webhook endpoint but with header `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because it only hashes `B` [1](#0-0) .
5. `Registry.process` calls the app handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", topic: ..., body: B, ...)` [8](#0-7) , and the app processes the forged event as if it were legitimately for the victim shop.
