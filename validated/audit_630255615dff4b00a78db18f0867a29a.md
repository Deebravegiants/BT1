Based on my investigation, I found a genuine analog to the "quorum computed before vote, then state changes" bug class in `orb-core`.

### Title
Stale `user_centric_signup` flag captured at QR-scan time causes fraud/failure signups to bypass the authoritative backend enrollment check - (File: `src/plans/mod.rs`)

### Summary
In `Governor.sol`, `quorumVotes` is snapshotted at proposal creation and never re-verified against the total supply at vote time, so a state change after the snapshot silently weakens the security guarantee. `orb-core` has the same class of bug: `user_centric_signup` is snapshotted from the backend at QR-scan time, held unchanged through the entire (multi-second, network- and AI-inference-bound) capture pipeline, and then used to decide whether to skip the backend's authoritative `enroll_user` call entirely - even when the local pipeline determined the signup was fraudulent or failed.

### Finding Description
`qr_codes.user_data.user_centric_signup` is fetched once, early, in `verify_user_qr_code` via `backend::user_status::request` [1](#0-0) , and the resulting flag is carried unchanged through the whole signup flow in the `QrCodes`/`ResolvedQrCodes` structs [2](#0-1) .

Later, in `do_signup`, after the QR scan, operator relay announcement, `sleep(3000ms)`, biometric capture, biometric pipeline, and fraud detection have all completed (i.e., potentially a long time after the snapshot), that same stale flag decides the enrollment path:

```
let success = if user_centric_signup && !orb.config.lock().await.ignore_user_centric_signups {
    debug_report.enrollment_status(match signup_reason {
        SignupReason::Normal => enroll_user::Status::Success,
        _ => enroll_user::Status::Error,
    });
    signup_reason == SignupReason::Normal
} else {
    Box::pin(self.enroll_user(orb, debug_report, &capture, pipeline.as_ref(), signup_reason)).await.is_success()
};
``` [3](#0-2) 

When `user_centric_signup` is `true`, the call to `self.enroll_user(...)` - which is the only code path that talks to the backend's `signup_post`/`signup_poll` endpoints to record and authoritatively adjudicate the signup (dedup, fraud, inflight-match detection, uniqueness) - is skipped entirely. Success is instead derived purely from local `signup_reason`, which is itself computed from the orb's own local fraud detector [4](#0-3) . The reference `enroll_user::run` flow shows the backend-driven cases this bypasses, e.g. backend duplicates, inflight matches, and backend-detected fraud [5](#0-4) .

This mirrors the Governor pattern exactly: a security-relevant decision variable (`quorumVotes` / `user_centric_signup`) is fixed at an early snapshot point and consumed later without being refreshed, even though the backend value it represents could legitimately change (e.g., an operator/admin could revoke `user_centric_signup` eligibility, or update fraud/ban status for that `user_id` between QR scan and enrollment) within the multi-second capture window.

### Impact Explanation
If backend-side eligibility for skipping enrollment changes during the capture window, the orb will report a locally-determined success/fraud status without ever notifying the backend of the actual biometric signup event through `enroll_user`. This can result in signups being locally marked `Success`/`Error` inconsistent with what the backend's authoritative dedup/fraud system would have determined, i.e., a form of cross-signup state bleed / misattributed signup outcome, since the backend never gets a chance to catch backend-side duplicate/fraud conditions for this specific signup attempt.

### Likelihood Explanation
The window between the QR-scan-time snapshot and the `user_centric_signup` check is non-trivial: it spans an explicit `sleep(3000ms)`, `biometric_capture`, `biometric_pipeline`, and `detect_fraud` [6](#0-5) , all of which are network/AI-inference bound and can take much longer than a single block/request. Any backend-side change to a user's eligibility during this window is silently ignored.

### Recommendation
Re-fetch or re-validate `user_centric_signup` (and related eligibility fields) immediately before the branch at `src/plans/mod.rs:639`, or always route through `enroll_user` when `signup_reason != SignupReason::Normal` regardless of `user_centric_signup`, so that fraud/failure outcomes are still reported to the backend's authoritative enrollment endpoint.

### Proof of Concept
1. Orb scans a user QR code; backend returns `user_centric_signup: true` for the associated `user_id` at time T0 [7](#0-6) .
2. Between T0 and the completion of biometric capture/pipeline/fraud-detection (several seconds later), the backend independently determines this `user_id` is fraudulent/duplicate/banned (a state change analogous to tokens minted between quorum snapshot and vote).
3. The orb's local fraud detector may or may not flag the same signup; regardless, because `user_centric_signup` was `true` in the stale snapshot, `do_signup` never calls `enroll_user`, so the backend is never informed of this specific signup attempt via `signup_post`/`signup_poll` [3](#0-2) .
4. Result: the orb records a locally-determined outcome that bypasses the backend's authoritative, up-to-date enrollment adjudication.
