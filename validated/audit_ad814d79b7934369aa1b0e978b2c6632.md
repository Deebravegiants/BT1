This confirms the finding. The gem's own documentation (`docs/usage/webhooks.md:125`) explicitly states that `Registry.process` "will verify the request did indeed come from Shopify" — implying the gem itself, not the host app, is responsible for authenticating the request, including the `shop` field passed to `data.shop` in the handler, per `docs/usage/webhooks.md:14` and `docs/usage/webhooks.md:25-26`. Since the HMAC signature computed by `Utils::HmacValidator.validate` only covers `@raw_body` and never `shop`, the "verification" claim is false with respect to the shop identity. This is a genuine gem-level defect, not host misuse of documented API.

### Title
Webhook `shop` field is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, excluding the `shopify-shop-domain` header from the HMAC-signed material. `ShopifyAPI::Webhooks::Registry.process` validates only this body-only HMAC and then forwards the unauthenticated `shop` value straight to the app's webhook handler as the trusted tenant identity.

### Finding Description
`Utils::HmacValidator.validate` computes and checks the signature using `verifiable_query.to_signable_string`, which for webhook requests is defined as just `@raw_body`: [1](#0-0) 
The `shop` accessor is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never included in the signable string: [2](#0-1) 

`Registry.process` validates the HMAC and, upon success, immediately trusts `request.shop` as the tenant identity when invoking the handler: [3](#0-2) 

The identity binding that should hold is: `shop header verified by HMAC == shop passed to WebhookMetadata.shop`. In reality, the HMAC only binds `raw_body`, so `shop` is a field acted on but never covered by the HMAC — exactly the vulnerability class in scope.

Because Shopify apps use a single, app-wide `api_secret_key` to sign webhooks for *every* installed shop (not a per-shop secret), any unprivileged internet user who installs the target app on their own store receives genuine webhook deliveries with a valid `(raw_body, hmac)` pair signed under that shared secret. Nothing in the signed material ties that `hmac` to their own shop domain. The attacker can replay the exact same `raw_body` + `hmac` header to the same app's webhook endpoint while substituting the `shopify-shop-domain` header (and topic if desired) with an arbitrary victim shop domain. `HmacValidator.validate` still succeeds because it never looks at the shop header, and `Registry.process` dispatches the handler with `shop: request.shop` pointing at the victim tenant, while `body` contains attacker-controlled data from the attacker's own shop.

The documentation for this API explicitly promises that `Registry.process` "will verify the request did indeed come from Shopify" before invoking the handler with `data.shop` as the shop identity, so host apps are entitled to rely on `data.shop` as authenticated: [4](#0-3) [5](#0-4) 

### Impact Explanation
This breaks the tenant boundary the gem is documented to enforce: an attacker who legitimately installs the app on their own store can forge webhook deliveries that are processed as if they came from any other merchant's shop, with attacker-chosen topic and body content. Depending on how the host app uses `data.shop`/`data.body` (e.g., updating shop settings, triggering `app/uninstalled` cleanup, writing customer/order records, or GDPR `customers/redact` / `shop/redact` compliance actions keyed by `shop`), this enables cross-tenant data corruption or triggering of privileged per-shop workflows attributed to a shop the attacker does not control — a cross-tenant access vulnerability.

### Likelihood Explanation
High likelihood: no leaked credentials, no privileged account, and no interaction with `api_secret_key` are required — only self-service app installation (available to any internet user for public apps) and the ability to send one crafted HTTP POST with a captured `raw_body`/`hmac` pair and a modified `shop` header to the app's public webhook endpoint.

### Recommendation
Include the `shop` domain (and ideally `topic`/`webhook_id`) in the HMAC-signed material, or otherwise cryptographically bind the shop identity to the signed body before trusting `request.shop` in `Registry.process`. At minimum, `to_signable_string` in `lib/shopify_api/webhooks/request.rb` should incorporate the shop header, and validation should reject requests where the shop bound in the signature doesn't match the header used for dispatch.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker.myshopify.com`, a store they control, triggering the app's webhook subscription (e.g., `orders/create`).
2. Shopify delivers a legitimate webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and some `raw_body` (attacker fully controls the order content since it's their own store).
3. Attacker captures `raw_body` and `x-shopify-hmac-sha256` from this real delivery.
4. Attacker sends a new POST to the same webhook endpoint, keeping `raw_body` and `x-shopify-hmac-sha256` identical, but sets `x-shopify-shop-domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` accepts the crafted headers, `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the hmac, and `Registry.process` invokes the handler with `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: <attacker-controlled>, ...)`, so the host app processes attacker-controlled data as if it originated from `victim.myshopify.com`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
```
