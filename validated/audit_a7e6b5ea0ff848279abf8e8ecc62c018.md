### Title

Interest accrual overflows total RAY value and permanently freezes a market - ([File: `contracts/pool/src/interest.rs`])

### Summary

Interest accrual computes `borrowed * borrow_index` and `supplied * supply_index` as `i128` RAY values before applying the borrow-index ceiling. Once either product exceeds `i128::MAX`, `accrue_step` panics with `MathOverflow`; because `global_sync` runs before pool mutations, repayment, withdrawal, liquidation and recapitalization can no longer complete for that market. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description

Each accrual chunk begins by unscaling the market’s scaled debt and supply with `scaled_to_original`, which performs checked `scaled * index` multiplication. The result—not merely the index—must fit in `i128`. [4](#0-3) [5](#0-4) 

The borrow-index cap is applied only after `old_index.mul(interest_factor)` and, more importantly, after the already-grown `borrowed * old_index` product has been evaluated. Consequently, a sufficiently large book can cross the RAY-value limit while its borrow index remains below `MAX_BORROW_INDEX_RAY`. [6](#0-5) [7](#0-6) 

`update_indexes` and all state-changing pool legs load a synchronized market; `global_sync` must finish before the requested mutation executes. Once one chunk panics, the cache is not marked accrued and every later call retries the same overflowing calculation. [8](#0-7) [9](#0-8) [10](#0-9) 

The repository’s regression test demonstrates that a 98%-utilized billion-token market can hit this value ceiling before the index cap, after which `withdraw` and `repay` both fail with `MathOverflow`. [11](#0-10) 

### Impact Explanation

This is permanent freezing of all funds and accounting actions for the affected `(hub_id, asset)` book: suppliers cannot withdraw, borrowers cannot repay, and liquidators cannot use liquidation paths that first synchronize the market. [12](#0-11) [3](#0-2) 

The failure also prevents protective actions from reducing risk because repayment and liquidation still execute interest accrual first. Since the panic occurs before mutation and commit, there is no in-contract partial-progress or skip-accrual recovery path. [9](#0-8) [10](#0-9) 

### Likelihood Explanation

The trigger requires a very large admitted book and sustained positive utilization so accrued RAY value eventually exceeds `i128::MAX`; it is therefore not reachable from ordinary small balances. [13](#0-12) 

However, valid listing caps can admit up to the token-to-RAY domain maximum, and the protocol explicitly notes that bounded indexes do not guarantee accrued totals fit. Any permissionless `update_indexes` call after the threshold is crossed can expose the condition, and no victim approval or privileged action is then needed. [14](#0-13) [8](#0-7) 

### Recommendation

Bound market value conservatively before accrual instead of bounding only the indexes. In particular:

- Enforce a persisted `borrowed * borrow_index` and `supplied * supply_index` ceiling below `i128::MAX`, with sufficient headroom for the next accrual chunk.
- Have `accrue_step` detect overflowing unscale operations and clamp accrual deterministically rather than allowing a typed panic to become a permanent market lock.
- Alternatively, add a recovery path that can mark or advance `last_timestamp` safely without requiring the overflowing total-value computation, while preserving conservative debt accounting.
- Reduce admitted caps or add runtime capacity checks so `supplied * MAX_SUPPLY_INDEX_RAY` and projected debt value remain inside the RAY domain. [15](#0-14) [13](#0-12) 

### Proof of Concept

A state satisfying `borrowed_scaled * borrow_index > i128::MAX` causes the first unscale in `accrue_step` to overflow before rate selection or index capping can help. The same panic then occurs in `update_indexes`, `withdraw`, `repay` and liquidation because each path calls `synced_market`/`global_sync` first. [7](#0-6) [9](#0-8) 

The repository already contains a deterministic reproduction in `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap`: it creates a billion-unit 18-decimal market, borrows 98% of it, advances years until `update_indexes` returns `MathOverflow`, verifies the index cap was not reached, and confirms both withdrawal and repayment fail with the same error. [16](#0-15)

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;

        remaining = remaining.saturating_sub(chunk);

pub fn update_supply_index(env: &Env, supplied: Ray, old_index: Ray, rewards_increase: Ray) -> Ray {
    if supplied == Ray::ZERO || rewards_increase == Ray::ZERO {
        return old_index;
    }

    let total_supplied_value = supplied.mul(env, old_index);

    if total_supplied_value == Ray::ZERO {
        return old_index;
    }

    let new_value = total_supplied_value.checked_add(env, rewards_increase);
    let grown = fp_core::mul_div_floor_saturating(env, new_value.raw(), RAY, supplied.raw());

    let bounded_old = old_index.raw().min(MAX_SUPPLY_INDEX_RAY);
    Ray::from(grown.min(MAX_SUPPLY_INDEX_RAY).max(bounded_old))
}

/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);

| Bound | Consequence |
|---|---|
| Asset decimals 0..=18 | Exact token-to-RAY upscaling. Below 3: collateral only, no flash loans, no liquidation fee, its account's only supply position, at least 2 whole units while in debt |
| Both indexes initially RAY; ceiling 10^36 | 10^9 times initial index; protocol constants |
| Supply-index floor 10^24 | At most 1,000 times the shares minted at index one for the same deposit |
| Borrow APR maximum 2 RAY | 200% annual rate; not a bound on balance growth alone |
| Token-to-RAY input maximum `i128::MAX / 10^(27-d)` | About 170.14 billion whole tokens, before other limits |
| Deposit conversion at the supply-index floor | About 170.14 million whole tokens before scaled-share overflow |

The token-to-RAY maximum is also the admitted cap maximum. Accrued position
values and market totals must independently fit the RAY domain; valid caps and
bounded indexes do not guarantee that future accrual fits. Value overflow can
occur before the index ceiling and block repayment/withdrawal because those
operations accrue first. At the borrow-index ceiling, further accrual produces
no borrower interest. No dedicated ceiling alarm is emitted.
