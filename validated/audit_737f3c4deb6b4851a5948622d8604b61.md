### Title
Webhook tenant (`shop`) header is not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from only the raw request body [2](#0-1) , while the `shop` (tenant identity) is read from the unsigned `shopify-shop-domain` / `x-shopify-shop-domain` header [3](#0-2) . `Registry.process` validates the HMAC and then passes this unauthenticated `shop` value directly to the app's webhook handler [1](#0-0) .

### Finding Description
The identity binding that should hold is: **the `shop` value attributed to a webhook event == the tenant whose secret produced the HMAC over that payload**. Instead, `HmacValidator.validate` calls `verifiable_query.to_signable_string`, and for `Request` that method returns `@raw_body` only [2](#0-1) , and `HmacValidator` computes/compares the signature over that string only [4](#0-3) . The `shop` accessor is derived from the `shop-domain` header, which is never included in the signable string, so it is never bound to the HMAC at all.

Since the app's `client_secret` is shared across all shops that install the app (it is not a per-shop secret — see `Context.api_secret_key` used uniformly in `HmacValidator`), any legitimate merchant (an unprivileged actor who installs the app on their own store) can:
1. Install the app on their own shop and receive a real webhook (valid raw body + valid HMAC, both computed with the app's single shared secret).
2. Replay that exact `raw_body`/`hmac-sha256` pair directly to the app's public webhook endpoint, but substitute the `shop-domain` header with a victim shop's domain.
3. `Registry.process` at [5](#0-4)  passes HMAC validation (body+hmac are legitimately paired) and forwards `request.shop` — now the victim's domain — to the handler as `WebhookMetadata`.

Because the webhook endpoint is a normal public HTTP endpoint the app exposes (not a mutually authenticated channel), no TLS interception or privileged access is required — only the ability to install the app once on an attacker-controlled shop, which is the intended unprivileged flow for any merchant.

### Impact Explanation
This breaks the shop/tenant identity boundary: the host application's webhook handler consumes attacker-controlled data (the replayed body) while believing it originates from — and is authorized to act on behalf of — a different tenant's `shop` domain. Any app that keys per-tenant state, session lookups, or side effects (order/customer records, GDPR redact triggers, billing state, etc.) off `WebhookMetadata#shop` without further check is vulnerable to cross-tenant data corruption/confusion using only the credentials/documents obtainable from installing the app once. This matches the Critical "cross-tenant access" impact category, since the gem itself supplies no mechanism binding the `shop` header to the signed payload.

### Likelihood Explanation
Likelihood is high for any app that (a) is installed by more than one merchant (typical for any public/multi-tenant app) and (b) relies on `WebhookMetadata#shop` from this gem as the trust anchor for tenant identity, which is the documented/intended usage pattern for `Registry.process` and `WebhookHandler#handle`. No secret, elevated privilege, or network position is required — just the standard unprivileged app-install flow on an attacker-owned shop plus a single unauthenticated POST to the app's own public webhook endpoint.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-signable string, or otherwise cryptographically bind them to the verified body, e.g.:
```ruby
def to_signable_string
  "#{shop}\n#{@raw_body}"
end
```
and verify server-side that the resulting `shop` matches an actual installed/authorized session for that shop before dispatching to the handler, rather than trusting the header value on its own.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a real event (e.g., `orders/create`) so Shopify sends a legitimately signed webhook: `raw_body = B`, header `x-shopify-hmac-sha256 = HMAC(secret, B)`, header `x-shopify-shop-domain = attacker-shop.myshopify.com`.
2. Attacker captures `B` and the valid HMAC value (they are the intended recipient of this webhook, so no interception is needed).
3. Attacker sends a POST directly to the app's public webhook endpoint with the same `B` and the same valid `x-shopify-hmac-sha256` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` [6](#0-5) , which succeeds because it only checks `B` against the HMAC, ignoring the `shop` header [7](#0-6) .
5. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)` [8](#0-7) , causing the app to process attacker-supplied data under the victim's tenant identity.
