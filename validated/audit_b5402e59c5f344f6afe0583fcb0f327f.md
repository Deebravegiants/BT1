### Title
Missing Storage Gap in `IntentsBase` Upgradeable Base Contract Risks Corrupting Escrow State on Future Upgrades - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentsBase` is the shared storage-holding abstract base contract for the UUPS-upgradeable `IntentGatewayV2`, inherited diamond-style by `IntrinsicIntents` and `ExtrinsicIntents`, which are both then inherited by the concrete `IntentGatewayV2` contract deployed behind an ERC1967 proxy. Unlike `SimplexPaymaster.sol`, which explicitly reserves `uint256[48] private __gap;` for future storage additions, `IntentsBase` declares no storage gap at all.

### Finding Description
`IntentGatewayV2` is deployed as an upgradeable proxy whose implementation can be swapped by governance via `onAccept`/`Execute` → `upgradeToAndCall`, as shown extensively in the test suite (`evm/tests/foundry/IntentGatewayV2Test.sol`) and documented in the changelog for the relayer-allowlist feature. Its inheritance graph is:

```
EIP712
  |
IntentsBase  (all shared storage: _filled, _nonce, _params, _orders, _instances, _partialFills, _destinationProtocolFees, _paused, _relayer)
 /       \
IntrinsicIntents  ExtrinsicIntents
 \       /
IntentGatewayV2
``` [1](#0-0) 

`IntentsBase` declares all of the gateway's storage variables directly, ending with `_paused` and `_relayer` appended at the end "to preserve existing storage slots": [2](#0-1) 

There is no `__gap` reservation after these variables, in contrast to `SimplexPaymaster.sol`, which explicitly carries one for exactly this purpose: [3](#0-2) 

Because `IntrinsicIntents` and `ExtrinsicIntents` are both declared as `abstract contract ... is IntentsBase` with no storage of their own visible in the relevant sections, any future storage variable added at the end of `IntentsBase` (e.g., during a governance-driven upgrade adding a new feature) will occupy the next storage slot after `_relayer`. If either `IntrinsicIntents` or `ExtrinsicIntents` is upgraded independently to add its own new storage variable in the same slot region — or if a new intermediate contract is introduced in the diamond — there is no reserved buffer to absorb the shift, and slot assignment across the diamond becomes fragile and error-prone across upgrades.

This is precisely the storage-layout risk the reference report describes for `OrderProcessor`/`BuyOrderIssuer`/`SellOrderProcessor`: a base contract with shared, mutable escrow-critical storage, inherited by multiple children that are combined into one final upgradeable implementation, with no `__gap` to safely absorb new state in future upgrades.

The tests already demonstrate how storage-slot-sensitive this contract is — `_filled` must stay at slot 2 for cross-chain proof verification (`FILLED_SLOT_BIG_ENDIAN_BYTES`), and `_relayer` must stay packed at slot 13 offset 1 behind `_paused`: [4](#0-3) [5](#0-4) 

This level of manual slot-pinning is fragile precisely because there is no gap; every future upgrade requires the developer to manually reason about exact slot placement across all four contracts in the diamond rather than relying on a gap to safely absorb new variables.

### Impact Explanation
`IntentsBase`'s storage directly backs escrowed user funds (`_orders` mapping tracking per-commitment, per-token escrowed amounts, and `_filled`/`_partialFills` tracking fill state) as well as the gateway's governance/relayer-gating state (`_params`, `_relayer`, `_paused`). A storage collision introduced by a future upgrade that adds a variable to `IntentsBase` (or to one of its two children independently) without careful, manual gap accounting could corrupt `_orders` accounting or the relayer/pause gate, leading to loss of escrowed funds, incorrect fill accounting, or governance authorization bypass. Given the contract already requires hand-verified slot placement (as evidenced by the dedicated slot-pinning tests), the absence of a gap significantly raises the likelihood of a silent, hard-to-detect storage corruption bug being introduced in a future governance-approved upgrade — impacting user escrow funds across all supported chains where `IntentGatewayV2` is deployed with an identical address.

### Likelihood Explanation
`IntentGatewayV2` upgrades are gated to a single authorized relayer and to Hyperbridge as the message source, so this is not an issue exploitable by an arbitrary attacker in isolation — it manifests only when the maintainers themselves perform a future upgrade. However, upgrades are a normal, expected, recurring part of this contract's lifecycle (the codebase already ships `IntentGatewayV2Upgraded` test scaffolding and a documented migration path via `migrate`/`Execute`), making it a real and recurring engineering risk rather than a hypothetical one, consistent with why the sibling `SimplexPaymaster` contract already adopted a `__gap`.

### Recommendation
Add an explicit storage gap (e.g., `uint256[50] private __gap;`) at the end of `IntentsBase`, sized to absorb reasonably anticipated future additions, mirroring the approach already used in `SimplexPaymaster.sol`. Since `IntrinsicIntents` and `ExtrinsicIntents` currently declare no state of their own, also consider adding smaller gaps to each of them individually so that future feature-specific state can be added to the correct branch of the diamond without needing to touch the shared base or manually recompute every other contract's slot offsets.

### Proof of Concept
Not applicable as an executable PoC — this is a storage-layout design gap that only manifests when a future upgrade adds new state. The layout-fragility can be demonstrated conceptually by extending `IntentsBase` with a new state variable and re-running `testFilledMappingStaysAtSlotTwo` / `testRelayerSharesSlotThirteenWithPaused` in `evm/tests/foundry/IntentGatewayV2Test.sol`, which will fail unless the new variable is manually placed to avoid disturbing the pinned slots — confirming there is no `__gap` currently protecting against this class of regression.
