### Title
Exposure of CatFee API Key/Secret in Relayer Logs via `Debug`-derived `CatFeeConfig` - (File: `tesseract/messaging/tron/src/lib.rs`)

### Summary
The TRON relayer client logs its full `CatFeeConfig` struct—including the plaintext `api_key` and `api_secret` used for CatFee HMAC-signed bandwidth-purchase requests—at the default `info` log level whenever CatFee integration is enabled, mirroring the CWE-532 "Insertion of Sensitive Information into Log File" pattern in the referenced advisory (unmasked credential/pre-signed-URL logging).

### Finding Description
`CatFeeConfig` derives `Debug` and stores `api_key`/`api_secret` as plain `String` fields with no redaction: [1](#0-0) .

In `TronClient::new`, when the operator configures CatFee credentials (used to purchase TRON energy/bandwidth before broadcasting transactions), the code logs the entire config with the `{:#?}` pretty-debug formatter at `info` level:
`log::info!(target: LOG_TARGET, "CatFee integration enabled: {:#?}", catfee_config);` [2](#0-1) .

Because `LOG_TARGET` is `"messaging-tron"` with no crate-specific suppression [3](#0-2) , and the relayer's global tracing/log filter defaults to `LevelFilter::INFO` [4](#0-3) , this statement fires unconditionally on every relayer startup at the normal operating log level — not gated behind a debug/verbose flag, unlike the Gradle advisory's `--info` requirement. Relayer logs are commonly shipped to third-party log aggregators, CI systems, or monitoring dashboards, so the CatFee API key and secret end up persisted in plaintext wherever those logs are collected.

### Impact Explanation
Anyone with read access to the relayer's log output (log aggregator, CI artifact, monitoring tool, or a misconfigured public log stream) obtains the operator's CatFee `api_key` and `api_secret` in plaintext. With these, an attacker can forge HMAC-SHA256 signed requests to the CatFee API (per the documented `Base64(HMAC-SHA256(secret, timestamp+method+path))` scheme) [5](#0-4) , impersonating the relayer's account to place unauthorized TRON energy purchase orders, drain the operator's CatFee account balance, or disrupt the relayer's bandwidth-purchasing capability — directly affecting the "bandwidth purchaser" role called out in scope. This is a confidentiality-only impact (no direct fund theft on Hyperbridge itself), matching the original advisory's `C:H/I:N/A:N` profile.

### Likelihood Explanation
High likelihood: the leak occurs automatically and unconditionally at default log verbosity whenever an operator enables CatFee integration — no special flags, attacker interaction, or race condition is required. Any standard log-collection pipeline (common in production relayer deployments) will capture and persist the secret.

### Recommendation
Implement a custom `Debug`/`Display` for `CatFeeConfig` that masks `api_key` and `api_secret` (e.g., print only a prefix or `"***"`), or explicitly log only the non-sensitive fields (`api_base`, `timeout`) instead of the whole struct. Apply the same masking pattern already used elsewhere in the codebase for secrets, e.g. `maskSecret`/`maskUrlKey` in the Simplex setup API [6](#0-5) .

### Proof of Concept
1. Configure a TRON relayer instance with `catfee_api_key` and `catfee_api_secret` set in `TronConfig`.
2. Start the relayer with default logging (`RUST_LOG` unset, defaults to `info`).
3. Observe the startup log line `"CatFee integration enabled: CatFeeConfig { api_key: "<real-key>", api_secret: "<real-secret>", ... }"` emitted via `log::info!` in `TronClient::new` at [7](#0-6) .
4. Any party with access to the collected log stream can extract the credentials and forge signed CatFee API requests as described in `generate_signature` [8](#0-7) .

	///
	/// Signature format: Base64(HMAC-SHA256(secret, timestamp + method + requestPath))
	/// where requestPath includes query parameters
	fn generate_signature(&self, timestamp: &str, method: &str, request_path: &str) -> String {
		let message = format!("{}{}{}", timestamp, method, request_path);

		let mut mac = HmacSha256::new_from_slice(self.config.api_secret.as_bytes())
			.expect("HMAC can take key of any size");
		mac.update(message.as_bytes());

		BASE64.encode(mac.finalize().into_bytes())
	}
