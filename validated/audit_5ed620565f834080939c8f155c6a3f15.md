`setNonceRandomBytes`/`customRandomBytes` are referenced only inside `IntentPayloadBuilder` and its own test suite [1](#0-0)  — there is no wiring anywhere in `sdk.ts`, the bridge `createWithdrawalIntents`/`validateWithdrawal` implementations, or the `WithdrawalParams`/`RouteConfig` types that lets a counterparty-controlled `routeConfig`, `assetId`, `destinationAddress`, `memo`, `quoteHashes`, `nonce`, or `signedIntents` value reach `setNonceRandomBytes` [2](#0-1) [3](#0-2) . `setNonceRandomBytes` is a builder method that must be invoked directly by the integrator's own application code before calling `buildWithSalt`/`build` [4](#0-3) .

The threat model in this audit restricts the attacker to an unprivileged NEAR Intents user, a counterparty whose strings get forwarded through documented SDK inputs, or a permissionless solver — and explicitly rejects findings that require "the integrator to deliberately misuse a documented escape hatch." Since reaching `encodeNonce` with a fixed, low-entropy `randomBytes` value requires the integrator itself to call the documented `setNonceRandomBytes` API with a poorly chosen constant (exactly the kind of deliberate misuse the rules exclude), and no attacker-controlled parameter reaches this path, the premise of a counterparty "controlling `routeConfig`/pre-build hook" to reach `setNonceRandomBytes` does not hold in this codebase.
