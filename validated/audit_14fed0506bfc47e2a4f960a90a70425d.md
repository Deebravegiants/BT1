## Title
Webhook HMAC does not bind the `shop-domain` identity, allowing cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates only the HMAC of the raw request body before dispatching the webhook to the app's handler with the `shop` value taken directly from the unauthenticated `shop-domain` header. Because the HMAC signature does not cover the shop identity, any party who can obtain one valid `(body, hmac)` pair for the shared app secret can replay that pair with an arbitrary `shop-domain` header and have the app process it as if it originated from a different, unrelated tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `hmac` is read straight from the `hmac-sha256` header: [1](#0-0) [2](#0-1) 

`ShopifyAPI::Utils::HmacValidator.validate` computes `HMAC-SHA256(api_secret_key, to_signable_string)` and compares it to the received HMAC — it never incorporates `shop`, `topic`, or `webhook_id`: [3](#0-2) 

`Registry.process` checks only this body HMAC, then dispatches the handler using `request.shop`, which is read verbatim from the `shop-domain` header and is not part of the signed material: [4](#0-3) [5](#0-4) 

The identity binding that is broken is: `HMAC(raw_body, api_secret_key)` valid ⇏ `shop-domain header == shop that actually produced raw_body`. The `api_secret_key` is a single value shared by the app across *all* of its installations (it is not per-shop), so a valid `(body, hmac)` pair obtained from a legitimate webhook delivered to one tenant is cryptographically valid for every tenant. `Registry.process` treats HMAC validity as proof of both body integrity and shop authenticity, but it only proves the former.

The gem's own documentation confirms the host app is expected to trust `data.shop` as the shop identity coming out of `process`, with no guidance to separately re-verify it: [6](#0-5) [7](#0-6) 

### Impact Explanation
An attacker who is a legitimate (but unprivileged) installer of the target app — e.g., they sign up their own trial/development shop — can trigger real webhook deliveries to their own callback endpoint and thereby obtain valid `(raw_body, hmac-sha256)` pairs signed with the app's `api_secret_key`. Because the signature never binds `shop-domain`, the attacker can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header with any victim shop's domain. `Registry.process` will accept it as valid (HMAC still matches) and hand the handler a `WebhookMetadata` claiming to be for the victim shop with attacker-chosen body content. Any host app that persists or acts on webhook data keyed by `data.shop` (the documented and intended usage pattern) will attribute forged data to another tenant — a cross-tenant data-integrity/spoofing issue that maps to the "Critical - cross-tenant access" impact category, since the app's core multi-tenant boundary (which shop a payload belongs to) is not authenticated by this gem despite exposing `process` as the sole verification primitive.

### Likelihood Explanation
Moderate-to-low but concrete: it requires the attacker to be an installer of the same app (trivial — most Shopify apps are installable by any store, including free dev stores) and to control an HTTP endpoint reachable from the internet to receive the legitimate webhook and then replay it against the victim's/app's public webhook route. No secrets, employee access, or the app's `client_secret`/access tokens are needed — only observation of one legitimate webhook delivery for their own shop. This is a purely gem-level gap: `HmacValidator`/`Request`/`Registry` never offer a way to bind or verify shop identity, so no amount of "correct" host-app usage of the documented API closes it.

### Recommendation
Include the shop domain (and ideally the topic/webhook id) in the HMAC-signed material, or provide a documented API path for the host application to fetch/compare `shop` against the set of shops actually installed with a token issued via this gem's OAuth/token-exchange flow, and update `Utils::HmacValidator` / `Webhooks::Request#to_signable_string` accordingly so `process` can genuinely authenticate the shop identity, not just body integrity.

### Proof of Concept
1. App has two installations: attacker's own dev shop `attacker.myshopify.com` and victim shop `victim.myshopify.com`, both using the same `ShopifyAPI::Context.api_secret_key`.
2. Attacker triggers any subscribed webhook event on their own shop (e.g., `orders/create`) and captures the raw POST: `raw_body`, and header `X-Shopify-Hmac-Sha256: <hmac>`.
3. Attacker resends this exact `raw_body` and `hmac-sha256` header to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(raw_body, api_secret_key) == received_hmac` — true, because neither `raw_body` nor `api_secret_key` changed. [4](#0-3) 
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: <attacker-controlled parsed body>, ...)`, and any host-app logic that trusts `data.shop` as the authenticated tenant identity (per the documented usage pattern) processes/attributes the forged payload to the victim shop.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
