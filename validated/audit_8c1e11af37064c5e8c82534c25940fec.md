## Title
Missing relayer-allowlist gate on Tron's `IntentGatewayV2.onAccept`/`onGetResponse` — escrow settlement callbacks are reachable by any deliverer - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

## Summary
The Ethscriptions.com incident stemmed from a smart-contract-level access-control gap that let callers pull assets out of escrow that were never assigned to them. The closest reachable analog in this codebase is a real divergence between the EVM `IntentGatewayV2`/`ExtrinsicIntents` implementation and the Tron port: the EVM version was hardened with a single-relayer allowlist gate (`_checkRelayer`) in front of `onAccept`/`onGetResponse`, but the Tron contract still lacks that gate entirely.

## Finding Description
On the primary EVM implementation, `ExtrinsicIntents.onAccept` and `onGetResponse` both call `_checkRelayer(incoming.relayer)` before any request body is decoded: [1](#0-0) [2](#0-1) 

This gate was intentionally added, per the recorded change log entry: "The gateway now accepts `onAccept` and `onGetResponse` deliveries only from a single authorised relayer... The check runs before the message body is decoded, so escrow redemptions, refunds and every governance action, upgrades included, are covered." [3](#0-2) 

The files that were touched to add this gate are explicitly enumerated in that change log and only cover the `evm/src/apps/...` tree, not the Tron contracts tree. [4](#0-3) 

Inspecting the Tron equivalent confirms the gate is absent: `onAccept` decodes the request kind and, for `RedeemEscrow`/`RefundEscrow`, only calls `authenticate(incoming.request)` — there is no `_checkRelayer`/`checkRelayer` call anywhere in this file: [5](#0-4) 

Likewise `onGetResponse` on Tron proceeds straight to reading the storage-proof value with no relayer check: [6](#0-5) 

whereas the EVM `onGetResponse` performs `_checkRelayer(incoming.relayer)` first: [2](#0-1) 

## Impact Explanation
The relayer allowlist was added specifically because escrow redemption/refund and governance-adjacent delivery paths need to be restricted to a single authorised deliverer; the flow documentation states this control is what stands between "anyone" and having their delivery accepted for `onAccept`/`onGetResponse`, and that without it "a fresh proxy... accepts every relayer." [7](#0-6) 

On the Tron deployment, this protection is simply not present in the withdraw/settlement code path, meaning `RedeemEscrow`/`RefundEscrow` (and the governance actions `NewDeployment`/`UpdateParams`/`SweepDust`) can be submitted by any address able to satisfy the ISMP handler's proof requirements, not just the operator-designated relayer that the rest of the protocol assumes is exclusively trusted. This is a security-control regression on the escrow release/settlement surface (`withdraw`) touched directly by unprivileged message delivery, matching the report's bug class of a contract-level access gap on a withdrawal function.

## Likelihood Explanation
This is triggerable by any address that can call `handlePostRequests`/`handleGetResponses` against the Tron `IsmpHost`/handler with a validly-proven request/response — i.e., any unprivileged relayer/dispatcher on the network, not a privileged or governance actor. No special permissions are required to attempt delivery; the only gate that the EVM branch relies on for this purpose is exactly the one missing here.

## Recommendation
Port the `_relayer`/`_checkRelayer` gate (and its `setRelayer`/`migrate`/`initialize` wiring) from `evm/src/apps/intentsv2/ExtrinsicIntents.sol` and `IntentsBase.sol` into `evm/tron/contracts/apps/IntentGatewayV2.sol`, calling it at the top of `onAccept` and `onGetResponse` before any request-kind dispatch, matching the EVM implementation exactly, and add a Tron-side regression test mirroring `testRejectedDeliveryStaysRetryableThroughHost` to lock in the behavior.

## Proof of Concept
1. Deploy/observe the Tron `IntentGatewayV2` with a placed cross-chain order and legitimate escrow in `_orders[commitment][token]`.
2. Have any non-designated address relay the proven `RedeemEscrow`/`RefundEscrow` `IncomingPostRequest` (or `IncomingGetResponse`) to the Tron ISMP handler — this succeeds because `onAccept`/`onGetResponse` contains no `_checkRelayer` equivalent, only `onlyHost` and `authenticate(request)`, unlike the reference implementation in `ExtrinsicIntents.sol` at lines 330-331 and 360-361.
3. Compare against the EVM `IntentGatewayV2Test.sol` suite, which explicitly tests that a non-allowlisted relayer's delivery reverts and is retryable only by the authorised relayer — no equivalent test/enforcement exists for the Tron contract.

3. `ExtrinsicIntents.onAccept` runs `onlyHost`, then `_checkRelayer(incoming.relayer)`, which reverts
   with `Unauthorized` when a relayer is set and the delivery is from anyone else. Only then is the
