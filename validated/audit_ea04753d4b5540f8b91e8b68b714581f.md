### Title
Missing minimum-received / max-fee guard lets `protocolFeeBps` drift silently reduce a placer's escrowed order inputs - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.placeOrder()` deducts a protocol fee from every input amount using whichever `protocolFeeBps` (or per-destination override) is live **at execution time**, and computes the order commitment and escrow amounts from that fee-reduced value. The `Order` struct and `placeOrder()` signature carry no field that lets the user bound the acceptable fee or the minimum amount that must be escrowed, so if the effective rate changes between when the user builds/signs the transaction (or reads a quote) and when it is actually mined, the user is silently escrowed for less than they expected with no revert path — the same missing-slippage-guard root cause as the referenced Size `compensate()` finding.

### Finding Description
`placeOrder()` reads the fee rate to apply on the fly: [1](#0-0) 

```solidity
bytes32 destinationHash = keccak256(order.destination);
uint256 protocolFeeBps = _destinationProtocolFees[destinationHash];
if (protocolFeeBps == 0) {
    protocolFeeBps = _params.protocolFeeBps;
}
...
uint256 protocolFee = (originalAmount * protocolFeeBps) / 10_000;
uint256 reducedAmount = originalAmount - protocolFee;
```

`_params.protocolFeeBps` and `_destinationProtocolFees[...]` are mutable at any time via the governance-driven `_updateParams` path invoked from `onAccept`: [2](#0-1) 

The `Order` struct and the `placeOrder(Order, bytes32 graffiti)` signature contain no `minReceivedAmount`, `maxFeeBps`, or similar bound. Off-chain, the SDK's `quoteIntent()` / `readProtocolFeeBps()` reads the *current* fee at quote time only, and the docs explicitly warn that the escrowed amount is fee-reduced and must not be adjusted client-side: [3](#0-2) 

Because the fee rate used is whatever is live when the transaction is finally included — not what the user observed when constructing/signing it — any mempool delay, gas-price competition, or a routine (non-malicious) governance fee update landing first will silently change the escrowed `reducedAmount` and the resulting commitment the user is bound to, with the user having no way to specify "escrow at least X" or to have the transaction revert instead of proceeding on worse terms. This is structurally identical to the Size `Compensate.sol` issue: a value the user assumes is fixed at submission time (the amount actually locked/escrowed, net of an incidental protocol charge) is instead computed against state that can change before inclusion, and the struct offers no minimum-amount field to guard it.

Notably, the codebase's own `FillOptions.validUntil` field, added specifically to bound stale pricing for solver fills, shows the team is aware of this general TOCTOU staleness class: [4](#0-3) 

but no symmetric protection exists for the order-placer side against `protocolFeeBps` / per-destination fee drift.

### Impact Explanation
An order placer can have more of their input tokens diverted to protocol dust than expected, and the order they end up placing (based on the resulting commitment) will require a smaller amount from solvers/escrow release than they intended, purely because a fee-rate change intervened between transaction construction and mining. There is no on-chain way to cap this or make the transaction revert instead, so the funds are locked into a smaller, worse order without user consent for that specific execution. This can occur during entirely normal protocol operation (routine fee-parameter tuning by governance plus ordinary chain congestion), not only via attacker action, mirroring the "normal user flow" classification from the referenced report.

### Likelihood Explanation
Requires only an ordinary `placeOrder()` call plus a fee-rate change (global `protocolFeeBps` or a per-destination override) landing in a block before the user's transaction — a routine governance operation combined with normal transaction-inclusion timing, not an attack requiring special access. This can happen incidentally any time governance retunes fees while user transactions are in flight.

### Recommendation
Add an optional bound to `placeOrder()` (e.g., a per-input `minAmount` or an overall `maxProtocolFeeBps` parameter) and revert if the fee actually applied would reduce any input below the caller-specified floor, mirroring the mitigation already applied to the solver side via `FillOptions.validUntil`.

### Proof of Concept
1. User calls `quoteIntent()` / reads `params()` and observes `protocolFeeBps = 5` (0.05%) for their destination, and builds `order.inputs[0].amount = 100_000000` (100 USDC) expecting `reducedAmount = 99_950000`.
2. Before the user's `placeOrder` transaction is mined, governance dispatches an `UpdateParams` message (via `onAccept`) raising `_destinationProtocolFees[destinationHash]` to, say, 500 bps (5%), as shown in `_updateParams`: [5](#0-4) 
3. The user's `placeOrder` transaction is then included, reads the new `protocolFeeBps = 500`, and silently escrows only `95_000000` USDC instead of the `99_950000` USDC the user expected — the commitment is computed over this reduced value with no revert and no way for the user to have specified a floor.

```text
### Protocol fees

Before escrowing, the contract deducts a protocol fee from each input amount:

```
protocolFee = input.amount × protocolFeeBps / 10_000
reducedAmount = input.amount − protocolFee
```

The fee is retained in the gateway as dust (emitting `DustCollected`), and per-destination overrides take precedence over the global `protocolFeeBps` when set. Current deployments charge **5 bps (0.05%)**. For a 100 USDC input:

| Item | Amount |
| --- | ---: |
| USDC transferred from your wallet | 100.000000 USDC |
| Protocol fee: `100 × 5 / 10,000` | 0.050000 USDC |
| Amount actually escrowed and offered to solvers | 99.950000 USDC |

The commitment hash is computed over the **fee-reduced inputs** — solvers read the reduced amounts from the `OrderPlaced` event and only need to match those. The fee is deducted at placement and is **not refunded** if the order expires, receives no bids, or is cancelled; a cancellation returns the remaining escrow and `order.fees`, but not the protocol fee.

<Callout type="warn">
Do not build an order by reducing the input yourself to account for the protocol fee. Send the gross input amount and use the amounts returned by `quoteIntent()`. The quote prices the fee-reduced escrow amount; reducing it again would make the order smaller than intended.
</Callout>
```
