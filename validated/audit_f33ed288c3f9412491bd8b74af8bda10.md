### Title
`HyperFungibleTokenUpgradeable`/`WrappedHyperFungibleTokenUpgradeable` `initialize` has no caller/atomicity guard, allowing front-run of proxy ownership - ([File: sdk/packages/core/contracts/apps/HyperFungibleTokenUpgradeable.sol])

### Summary
`HyperFungibleTokenUpgradeable.initialize` and `WrappedHyperFungibleTokenUpgradeable.initialize` are `public virtual initializer` functions that set `initialOwner` (via `OwnableUpgradeable`) with no restriction on who may call them and no built-in guarantee that they execute atomically with proxy deployment [1](#0-0) . This mirrors exactly the bug class in the external report: a delegatecall-proxy `initialize` function that any address can call first if the deployer deploys the proxy and then calls `initialize` in a separate transaction, rather than passing initialization data atomically in the proxy constructor.

### Finding Description
The token contract documents that "the owner configures which chains this token can communicate with and the address of the corresponding deployment on each chain" [2](#0-1) , storing this in `_supportedChains`, a mapping from chain identifier to trusted peer module id [3](#0-2) . `initialize` only calls `__HyperFungibleToken_init`, which sets `Ownable_init(initialOwner)` with no access control gating who may call `initialize` itself [4](#0-3) . The same pattern exists in `WrappedHyperFungibleTokenUpgradeable.initialize` [5](#0-4) .

By contrast, other upgradeable Hyperbridge contracts in the same repo — `IntentGatewayV2` and `SimplexPaymaster` — explicitly recognize and defend against this exact bug class: they add an `onlyFresh` modifier (`_getInitializedVersion() != 0` check) combined with atomic `ERC1967Proxy` deployment carrying the init calldata in the constructor, and document the rationale in their changelogs/decisions: "`initialize` has no caller restriction, because a bare proxy is initialized atomically in its constructor" [6](#0-5) ; the design decision doc spells out the exact hole being closed . `SimplexPaymaster` follows the identical mitigation pattern [7](#0-6) .

The `HyperFungibleTokenUpgradeable`/`WrappedHyperFungibleTokenUpgradeable` SDK base contracts, however, have no equivalent `onlyFresh`-style protection, and no deployment script in the repository enforces atomic proxy initialization for them (no references found in `*.s.sol` deployment scripts) — meaning any integrator deploying these via a bare proxy and a follow-up `initialize()` call, rather than encoding `initialize` calldata directly into the proxy constructor, exposes an initialization race.

### Impact Explanation
If an attacker front-runs `initialize`, they become the `Ownable` owner of the token bridge application. Since the owner configures `_supportedChains` (the trusted peer contract per remote chain) which the mint/receive path (`onAccept`) relies on to authorize incoming cross-chain messages, an attacker-owner can register their own malicious "peer" address for a chain of their choosing. They can then relay a forged incoming message purporting to come from that trusted peer, minting arbitrary amounts of the token with no backing burn on the source side — an unbacked mint. Alternatively, the attacker can simply prevent proper configuration, permanently bricking legitimate cross-chain routes for that token deployment.

### Likelihood Explanation
Any deployer who instantiates these upgradeable token base contracts via a standard "deploy proxy, then call initialize" flow (rather than passing init data atomically in the proxy constructor) is directly exposed; the window is a single front-runnable transaction on a public mempool, requiring no privileged access — consistent with the "unprivileged" reachability required by the analog rules.

### Recommendation
Add a constructor that calls `_disableInitializers()` on the implementation (already present) and additionally guard `initialize` the way `IntentGatewayV2`/`SimplexPaymaster` do: enforce that deployment always encodes `initialize` calldata atomically into the `ERC1967Proxy` constructor, and/or add a check equivalent to `onlyFresh`/require the caller to be a designated deployer, so `initialize` cannot be raced by an unrelated address.

### Proof of Concept
1. Deployer deploys `HyperFungibleTokenUpgradeable` implementation and an `ERC1967Proxy` pointing to it without encoding `initialize` calldata in the proxy constructor.
2. Attacker observes the pending/mempool proxy deployment (or the gap between proxy deployment and the deployer's `initialize` call) and submits `initialize(name, symbol, attacker)` with higher gas, becoming `owner`.
3. Attacker calls the owner-gated chain-configuration function to register a malicious peer for an arbitrary chain id in `_supportedChains`.
4. Attacker relays a forged cross-chain message claiming to originate from that "trusted" peer; `onAccept` mints tokens to the attacker with no corresponding burn, per the design described at [8](#0-7) .

    modifier onlyFresh() {

        _;
    }

    /**
     * @dev One-time init of a bare proxy: registers the peers, each bound to `address(this)`,
     * stores the params, arms the relayer gate, and lands at `VERSION`. Refused on any proxy
     * already at a version, see `onlyFresh`.
     * @param p The initial gateway configuration parameters.
     * @param peerChains State-machine ids of the cross-chain peers to register, each bound to this
     * gateway's own address so no peer address is carried in the proxy's init data.
     * @param relayer The only relayer whose deliveries are accepted. Zero leaves the gate open.
     */
    function initialize(Params memory p, bytes[] memory peerChains, address relayer)
        public
        onlyFresh
        reinitializer(VERSION)
    {
        uint256 peersLength = peerChains.length;
        for (uint256 i = 0; i < peersLength; i++) {
            Deployment memory deployment = Deployment({chain: peerChains[i], gateway: address(this)});
            _addDeployment(deployment);
        }
        _validateParams(p);
        _params = p;
        _setRelayer(relayer);
    }
