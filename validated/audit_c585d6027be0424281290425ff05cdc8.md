### Title
Webhook shop identity spoofing — HMAC covers only the raw body, not the `shop-domain` header, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable content from the raw body alone, while the shop identity (`shop-domain` header) that `Registry.process` later trusts and hands to the app's webhook handler is never covered by the HMAC.

### Finding Description
`Request#to_signable_string` only returns `@raw_body`: [1](#0-0) 

The `shop` accessor is read straight from the (uncovered) `shop-domain`/`x-shopify-shop-domain` header: [2](#0-1) 

`Registry.process` validates only the HMAC of the body and then forwards `request.shop` directly into the handler's metadata, with no additional binding check between the verified bytes and the shop claim: [3](#0-2) 

The identity binding that should hold is:
`HMAC_valid(raw_body, secret) == true` should imply `shop_header == shop_that_actually_generated(raw_body)`.

In this implementation, the equality that is actually checked is only `HMAC(raw_body) == received_hmac`; the `shop-domain` header is completely outside that computation, so:
`verified(raw_body) ≠ verified(shop_header)`.

Any entity that can obtain one valid `(raw_body, hmac)` pair signed with the app's `api_secret_key` — e.g. a merchant who installs the app on their own store and receives a legitimate webhook for a generic/non-shop-specific event — can replay that exact body+HMAC to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. `HmacValidator.validate` will still return `true` because it only recomputes the HMAC over `raw_body`, and `Registry.process` will hand the forged shop identity straight to the app's `handler.handle`, which typically uses `data.shop` to look up the tenant's stored session/access token and take action.

### Impact Explanation
This breaks the tenant boundary the webhook subsystem is supposed to enforce: an attacker who is a legitimate (if malicious) merchant of the app can cause the host application to process/attribute webhook events under a victim shop's identity (`WebhookMetadata#shop`), enabling cross-tenant confusion — e.g. triggering shop-scoped side effects (data writes, uninstall/redact handling, cache invalidation) keyed to a shop they do not control. This matches the Critical "cross-tenant access" impact category, since the shop-identity claim used to select which tenant's data/session is affected is not cryptographically bound to the authenticated payload.

### Likelihood Explanation
Requires no privileged credentials, access tokens, or `api_secret_key` knowledge — only the ability to install the app on any store (self-serve, unprivileged) to harvest one valid signed webhook body, and the ability to POST directly to the app's public webhook endpoint (which is exposed to the internet by design). The main constraint is finding a webhook topic/body that is shop-agnostic in content (so the replay is plausible for a different shop), which is feasible for several standard topics whose payload doesn't itself encode the shop.

### Recommendation
Bind the shop identity into the verified data before trusting it:
- Include the `shop-domain` (and ideally `webhook-id`/`topic`) in the value that is HMAC-verified, or
- After HMAC validation, cross-check `request.shop` against the shop associated with the session/access token the app already has on file for that webhook, rejecting mismatches, or
- Require callers of `Registry.process` to supply the expected shop and assert equality with `request.shop` prior to invoking the handler.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook event whose body content is generic (not shop-specific), capturing the raw POST body and the `x-shopify-hmac-sha256` value Shopify sent.
2. Attacker POSTs the same raw body + same HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into a request object; `HmacValidator.validate` recomputes HMAC over `raw_body` only (per `to_signable_string`), matches the replayed HMAC, and returns `true`: [4](#0-3) 
4. `Registry.process` proceeds and calls the registered handler with `shop: "victim-shop.myshopify.com"`, even though the payload never actually originated from that shop.
