## Analysis

The reported analog is a real, currently-present bug in the Tron variant of the IntentGateway. Unlike the primary EVM implementation, which explicitly hardens `placeOrder` against fee-on-transfer tokens by measuring pre/post balances and using the *actual received* amount for escrow crediting and commitment hashing [1](#0-0) , the Tron port of `IntentGatewayV2` credits escrow using the nominal, requested amount (only adjusted for the protocol fee) with no verification that this amount was actually received by the contract.

### Title
Fee-on-transfer tokens cause escrow over-crediting and insolvency in Tron `IntentGatewayV2.placeOrder` - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `placeOrder()`'s direct-transfer branch calls `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then unconditionally credits `_orders[commitment][token] += reducedInputs[i].amount`, where `reducedInputs[i].amount` is derived only from the user-specified `order.inputs[i].amount` minus the protocol fee — it is never checked against the token balance actually received by the contract.

### Finding Description
`placeOrder` in the Tron gateway computes `reducedInputs` purely from `order.inputs[i].amount` and `protocolFeeBps` [2](#0-1) . In the no-predispatch branch it then pulls tokens via `safeTransferFrom` and immediately credits the escrow mapping with the pre-computed `reducedInputs[i].amount`, without measuring the contract's actual balance change: [3](#0-2) 

If `token` charges a transfer fee (deflationary/fee-on-transfer token), `address(this)` receives strictly less than `order.inputs[i].amount`, yet `_orders[commitment][token]` is still credited with the full (fee-only-reduced) `reducedInputs[i].amount`. This is exactly the bug class from the referenced Sherlock report against `AutoRoller.onSponsorWindowOpened`, where the contract assumes it receives the full transferred amount.

By contrast, the primary EVM `IntentGatewayV2` (via `ExtrinsicIntents`/`IntrinsicIntents`) explicitly guards against this by snapshotting `balBefore = IERC20(token).balanceOf(address(this))`, performing the transfer, then setting `order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore` before computing the commitment and crediting escrow [4](#0-3) , and this behavior is explicitly tested with a `FeeOnTransferToken` mock [5](#0-4) . The Tron variant lacks this safeguard entirely in the non-predispatch path.

### Impact Explanation
Because `_orders[commitment][token]` (the escrow ledger the contract believes it holds) is inflated relative to the actual token balance held by the contract, the contract becomes insolvent for that token by the fee amount on every order placed with a fee-on-transfer input token. When a solver later fills the order and the settlement message triggers `withdraw()` (crediting the solver the full escrowed/committed amount), the contract will pay out more than it actually holds for that token, effectively depleting balances that back *other* users' unrelated escrowed orders in the same token. This is a fund-freezing/shortfall condition across the escrow pool — other legitimate order owners may later be unable to have their escrow redeemed or refunded in full, since the token balance has been drained by prior over-credited redemptions.

### Likelihood Explanation
This is triggerable by any unprivileged user simply by placing an order (`placeOrder`) using a fee-on-transfer ERC20 as an input token — no special privileges, governance, or admin action required. The only precondition is that the deployment accepts arbitrary ERC20 tokens as order inputs (which is the design, since `TokenInfo.token` is user-supplied). This makes it directly reachable from a single `placeOrder` transaction.

### Recommendation
Apply the same fee-on-transfer safeguard used in the primary EVM implementation to the Tron contract: measure `balanceOf(address(this))` before and after each `safeTransferFrom` in the non-predispatch branch, and use the actual received delta (rather than the nominal `order.inputs[i].amount`/`reducedInputs[i].amount`) both for the commitment hash and for the `_orders` escrow credit. The predispatch/dispatcher-sweep branch should similarly verify final balances on `address(this)` after the sweep transfer, not just balances observed on the `dispatcher`.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` and initialize with `protocolFeeBps = 0` for simplicity.
2. Deploy a fee-on-transfer ERC20 (e.g., 1% fee) and mint tokens to a user.
3. User calls `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000e18}`.
4. `reducedInputs[0].amount` computes to `1000e18` (no protocol fee), and `safeTransferFrom(user, address(this), 1000e18)` only delivers `990e18` to the gateway due to the 1% transfer fee.
5. `_orders[commitment][FOT]` is nonetheless set to `1000e18` — a 10e18 (1%) shortfall between recorded escrow and actual token balance.
6. Repeating this with multiple orders compounds the shortfall; eventually a `withdraw()`/redeem call for an earlier order will succeed by consuming balance that was actually escrowed for a different, later order, leaving that later order's rightful owner unable to fully redeem or cancel.

    function testPlaceOrder_FeeOnTransferToken_WithProtocolFee() public {
        IntentGatewayV2 gatewayWithFees = _deployGatewayProxy();
        Params memory intentParams = Params({
            host: address(host),
            dispatcher: address(dispatcher),
            solverSelection: false,
            surplusShareBps: SURPLUS_SHARE_BPS,
            protocolFeeBps: PROTOCOL_FEE_BPS, // 30 bps
            priceOracle: address(0)
        });
        gatewayWithFees.initialize(intentParams, new bytes[](0), address(0));

        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% transfer fee
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 receivedAfterTransferFee = inputAmount - (inputAmount * 100) / 10000; // 990
        uint256 protocolFee = (receivedAfterTransferFee * PROTOCOL_FEE_BPS) / 10000;
        uint256 expectedEscrow = receivedAfterTransferFee - protocolFee;

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(gatewayWithFees), inputAmount);
        gatewayWithFees.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Reconstruct commitment: inputs mutated to received, then reduced by protocol fee
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedEscrow; // commitment is hashed with reduced amount
        bytes32 commitment = keccak256(abi.encode(order));

        assertEq(
            gatewayWithFees._orders(commitment, address(fot)),
            expectedEscrow,
            "Escrow should equal received minus protocol fee"
        );
