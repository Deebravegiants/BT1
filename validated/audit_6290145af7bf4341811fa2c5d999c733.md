### Title
Unauthenticated Arbitrary Runtime Call Dispatch via Crafted Cross-Chain Calldata - ([File: modules/pallets/hyper-fungible-token/src/module.rs])

### Summary
CVE-2024-31777 describes an unrestricted-file-upload bug: a crafted file submitted to an unprivileged endpoint is trusted and later executed without validating that its content came from an authorized/expected source. The reachable analog in this codebase is `pallet-hyper-fungible-token`'s `IsmpModule::on_accept`, which decodes an optional, fully attacker-controlled "calldata" payload out of an incoming cross-chain token message and dispatches it as a real `RuntimeCall` — but only actually verifies a cryptographic signature over that payload in one of two code branches. In the other branch it silently accepts the payload and derives the dispatch origin directly from attacker-supplied bytes, with no signature check at all.

### Finding Description
`on_accept` in [1](#0-0)  authenticates only that the incoming `PostRequest.from`/`source` pair maps to a registered `ContractToAsset` entry — i.e., that the message comes from a known bridged token contract, not that any particular *user* authorized the embedded calldata.

After minting/transferring tokens to the beneficiary, if `message.data` is non-empty the pallet decodes a `SubstrateCalldata` struct containing a `runtime_call` and an *optional* `signature`: [2](#0-1) 

- If `signature` is `Some(..)`, the pallet verifies it over `(nonce, runtime_call)` against the beneficiary's key and uses the beneficiary as the dispatch origin — this path is sound.
- If `signature` is `None`, the pallet takes the branch below with **no verification whatsoever**, deriving the origin straight from `message.from` (an ABI field fully controlled by whoever calls `send()` on the source-chain contract) and converts it to a Substrate `AccountId`: [3](#0-2) 

It then decodes and dispatches the attacker-supplied `runtime_call` under that derived origin with no further authorization check beyond the runtime's `BaseCallFilter`: [4](#0-3) 

This is structurally the same bug class as CVE-2024-31777: a payload originating from an unprivileged, single transaction (a normal token `send()` call reachable by any user, per the source contract flow) is trusted and executed by a privileged destination handler (`Dispatchable::dispatch`) without validating that the *content* (the embedded `runtime_call`) was actually authorized by anyone — the "crafted file" here is the crafted `data` field of a cross-chain transfer, and the "arbitrary code execution" is dispatch of an arbitrary allowed `RuntimeCall` under a derived account.

I was not able to fully verify, within the available context, how `T::EvmToSubstrate::convert` maps EVM addresses to Substrate `AccountId`s (e.g., whether it uses a collision-resistant prefix scheme like Frontier's `AccountId20`/checksum scheme, which would prevent an attacker's own address from being mapped onto an existing privileged account). If that mapping is a naive zero-padding of the 20-byte EVM address into 32 bytes, this would additionally enable account-identity collision with legitimately-created 32-byte Substrate accounts, materially increasing the severity. This point is flagged as unverified and should be checked directly in `modules/pallets/hyper-fungible-token/src/impls.rs`.

### Impact Explanation
Even under the conservative reading (no collision, origin is always the attacker's own derived account), this is a serious authentication-bypass: it allows anyone who can call the source-chain token contract to dispatch an arbitrary runtime call on the destination chain (subject only to `BaseCallFilter`) with zero signature or replay protection, purely by omitting the `signature` field of the calldata. Any privileged or sensitive extrinsic reachable through `BaseCallFilter` that is gated only by "signed origin" rather than a specific permissioned origin becomes reachable this way without the user proving intent for that specific call. If the EVM→Substrate address derivation is not collision-resistant, the impact escalates to unauthorized dispatch of calls under arbitrary/foreign account identities — satisfying "unauthorized app action" and potentially "theft of funds" if a colliding account holds balance or permissions.

### Likelihood Explanation
High for the base authentication-bypass: the vulnerable code path is reached by a completely ordinary, unprivileged cross-chain token transfer where the sender simply omits the optional signature in the calldata — no special conditions, proofs, or governance access needed. The bridged token contract's `send()` function is a normal user-facing entry point (see the "Execute optional calldata" comment at [5](#0-4) ), so any user of the deployed HFT bridge can trigger it once a token pair is configured.

### Recommendation
Require a valid signature over `(nonce, runtime_call)` unconditionally whenever `message.data` is non-empty — remove the unsigned/`None`-signature branch entirely, or if it must be kept for UX reasons, restrict the origin in that branch to a Substrate/EVM address explicitly opted-in by that same account beforehand (not silently derived from message fields with no proof of key ownership). Additionally, verify and document that `T::EvmToSubstrate::convert` cannot produce a 32-byte `AccountId` that collides with any real, independently-created Substrate account (e.g., by using a fixed non-Substrate-reachable prefix like Frontier's canonical scheme), and add an explicit test asserting this non-collision property.

### Proof of Concept
1. Attacker calls `send()` (or equivalent) on the source-chain HFT token contract for a registered token pair, from an address they control, setting `params.data` to an ABI-encoded `SubstrateCalldata { runtime_call: <encoded call>, signature: None }`, where `<encoded call>` is any call permitted by `BaseCallFilter` (e.g., a governance-adjacent extrinsic, an `Assets::transfer`, or any dispatchable gated only by "must be signed").
2. The message is relayed and delivered to `on_accept` in [2](#0-1) .
3. Because `signature` is `None`, the pallet skips all cryptographic verification and computes `origin = T::EvmToSubstrate::convert(H160::from(message.from))` at [3](#0-2) .
4. The pallet dispatches `runtime_call` as `RawOrigin::Signed(origin)` at [6](#0-5) , executing attacker-chosen logic with no proof that any private key ever authorized that specific call.
