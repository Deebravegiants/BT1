Audit Report

## Title
Unsynchronized Map Access in `WorkflowMetadataHandler.Authorize` Causes Data Race with Concurrent Metadata Sync - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

## Summary
`WorkflowMetadataHandler.Authorize` reads `h.authorizedKeys[workflowID]` without acquiring `h.mu.RLock()`, while the periodic `syncMetadata` goroutine replaces `h.authorizedKeys`, `h.workflowRefToID`, `h.workflowIDToRef`, and `h.workflowShards` wholesale under `h.mu.Lock()`. Since `Authorize` is invoked on every external HTTP trigger request via `authorizeRequest`, this produces a genuine, easily reachable data race between unprivileged request traffic and a background timer goroutine.

## Finding Description
`Authorize` at [1](#0-0)  directly indexes `h.authorizedKeys[workflowID]` with no lock acquired anywhere in the function body. Meanwhile `syncMetadata` at [2](#0-1)  takes `h.mu.Lock()` and reassigns `h.authorizedKeys` (and the three other map fields) as a whole new map value, running on a periodic ticker configured via `MetadataAggregationIntervalMs` and started in `Start` at [3](#0-2) . All other readers of these same fields — `GetWorkflowID`, `GetWorkflowReference`, and `WorkflowShards` — correctly acquire `h.mu.RLock()` as shown at [4](#0-3)  and [5](#0-4) , confirming `Authorize` is the sole outlier and that the lock is intended to guard exactly these fields. `Authorize` is reached from `httpTriggerHandler.authorizeRequest`, called for every inbound unprivileged HTTP trigger request, so the race is triggerable purely by normal external client traffic without any credential beyond a validly signed JWT for a registered workflow (which an attacker would need anyway to reach this code path, but the race itself does not require valid auth — even a JWT for an unregistered workflow ID reaches the unsynchronized read at line 92).

## Impact Explanation
This is a genuine unsynchronized concurrent Go map read/write on `h.authorizedKeys`, which Go's runtime treats as undefined behavior and can non-deterministically crash the process with `fatal error: concurrent map read and write`. Since this handler backs the gateway's node/workflow-trigger API, an unhandled crash terminates the whole gateway process, denying service to all workflows and tenants served by that instance — a legitimate availability impact affecting the node API authentication path for the HTTP Trigger capability.

## Likelihood Explanation
The race requires no special timing manipulation, no privileged access, and no malicious node — it simply requires ordinary external HTTP trigger request traffic to happen to overlap with the periodic `syncMetadata` tick (default interval configurable via `MetadataAggregationIntervalMs`, commonly on the order of a minute). Given realistic production request volume, such overlap will occur routinely rather than being a rare or exotic condition, making this a systemic implementation bug rather than a hypothetical corner case.

## Recommendation
Acquire `h.mu.RLock()`/`RUnlock()` in `Authorize` around the read of `h.authorizedKeys[workflowID]` (and the subsequent lookup within the returned `keys` map, since that submap could otherwise be swapped concurrently with the read of its contents), matching the pattern already used in `GetWorkflowID`, `GetWorkflowReference`, and `WorkflowShards`. Audit for any other unsynchronized reads/writes of `authorizedKeys`, `workflowRefToID`, `workflowIDToRef`, or `workflowShards` and document that `h.mu` must guard all access to these fields.

## Proof of Concept
1. Start a `WorkflowMetadataHandler` with at least one workflow registered so `authorizedKeys` is populated and `syncMetadata` runs on its configured ticker.
2. Concurrently, in a tight loop, call `Authorize(workflowID, validJWT, req)` from multiple goroutines while `syncMetadata` is invoked repeatedly (e.g., by manually invoking it in a loop from a separate goroutine, or by configuring a very short `MetadataAggregationIntervalMs` in a test).
3. Run under `go test -race` (or the full binary under `-race`); the race detector flags a data race on `h.authorizedKeys` between the read in `Authorize` (line 92) and the write in `syncMetadata` (line 178), or in a non-instrumented run under sustained concurrent load this manifests as a `fatal error: concurrent map read and write` process crash.
