## Title
Unbounded price-impact tolerance in native-token fee swaps allows sandwich extraction of user-supplied ETH surplus - (File: `evm/src/core/EvmHost.sol`, `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest` all swap `msg.value` native tokens into the protocol's `feeToken` via `IUniswapV2Router02.swapETHForExactTokens`, using the caller's entire `msg.value` as the implicit price ceiling with no independently configurable minimum-output / maximum-slippage parameter. `IntentGatewayV2.placeOrder`'s fee-escrow path does the same thing. This exactly matches the reported bug class: an unprivileged caller who sends a safety buffer of ETH (larger than the expected swap cost, to avoid reverts from minor price drift) can have that entire buffer consumed by a sandwich attacker, because the only bound on execution price is the size of the buffer itself.

### Finding Description
In `evm/src/core/EvmHost.sol`: [1](#0-0) 

The same unbounded pattern recurs in `dispatch(DispatchGet)` and `fundRequest`: [2](#0-1) [3](#0-2) 

In all three, `post.fee` / `get.fee` / `amount` is the exact output requested, and `msg.value` is used directly as `amountInMax` for `swapETHForExactTokens`. There is no independent slippage or price-limit parameter the caller can tune below their `msg.value`; the *only* protection against overpaying is `msg.value` itself. Any caller who — reasonably, to avoid a revert from natural price drift between quoting off-chain (as the docs explicitly instruct: `quote()` "is vulnerable to sandwich attacks. Only use it off-chain") and executing on-chain — sends extra ETH as a buffer, hands an MEV searcher exactly the room needed to sandwich the trade: front-run to inflate the ETH/feeToken price, let the victim's `swapETHForExactTokens` consume up to their full buffer, then back-run to restore price and capture the difference. Because `dispatch()`/`fundRequest()` are `payable` and callable by any address, this is reachable from a single submitted transaction with no privileged role required.

`IntentGatewayV2.placeOrder` reproduces the same pattern for order-fee escrow: [4](#0-3) 

The project's own test acknowledges users routinely overpay ETH as a buffer for this exact code path: [5](#0-4) 

Here the test sends 5 ETH for a fee swap that "should cost much less" — precisely the surplus-buffer scenario the original report describes, and precisely the scenario an MEV searcher can exploit since the swap has no slippage bound independent of the buffer size.

### Impact Explanation
Any user or contract dispatching an ISMP request with native-token payment, funding a pending request, or placing an intent order with native-token fees and providing a reasonable ETH buffer against price drift can lose that entire buffer to a sandwiching MEV actor. This is a direct, unbacked loss of user funds triggered by ordinary use of a core, permissionless entry point (`EvmHost.dispatch`, `fundRequest`, `IntentGatewayV2.placeOrder`), not a privileged or governance-only path.

### Likelihood Explanation
Every call to `dispatch()`/`fundRequest()`/`placeOrder()` with native-token payment is public and MEV-searchable in the public mempool; sandwiching such swaps is a well-established, cheap, and automatable strategy, and the docs themselves note the underlying quote is already sandwich-vulnerable. Any user who pads `msg.value` for safety (as demonstrated in the codebase's own test) is exposed on essentially every transaction.

### Recommendation
Add an explicit, caller-supplied `minAmountOut`/`maxSlippageBps` (or equivalent `sqrtPriceLimitX96`-style bound distinct from `msg.value`) to `DispatchPost`/`DispatchGet`/`fundRequest`/`placeOrder`'s native-fee-swap paths, and pass it into the underlying router call instead of relying solely on `msg.value` as the ceiling. Alternatively, validate the realized swap price against a trusted oracle (as `SimplexPaymaster` already does via `InvalidSlippage`/oracle bound in `swapAndDeposit`) before accepting the swap result.

### Proof of Concept
1. Attacker monitors mempool for a `EvmHost.dispatch{value: X}(DispatchPost{fee: F, ...})` transaction where `X > amountRequiredAtFairPrice(F)` (a normal buffer).
2. Attacker front-runs with a large ETH→feeToken swap on the same Uniswap V2 pool used by `_hostParams.uniswapV2`, raising the ETH price of `feeToken`.
3. Victim's transaction executes `swapETHForExactTokens{value: X}(F, [WETH, feeToken], address(this), block.timestamp)`; because the pool price is now worse, the swap consumes a much larger portion of `X` (up to all of it) to obtain the fixed output `F`, versus the fair-price amount it would have consumed absent manipulation.
4. Attacker back-runs, selling feeToken back for ETH, capturing the price-impact profit — funds that would otherwise have been left in the victim's contract balance / refunded.
5. Same sequence applies against `fundRequest` and `IntentGatewayV2.placeOrder`'s `order.fees > 0`, `msgValue > 0` branch.

    function testPlaceOrder_FeeSwap_RefundsExcessNativeToken() public {
        uint256 inputAmount = 1000 * 1e6;
        uint256 feeAmount = 1 * 1e18; // 1 DAI worth of fees

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(usdc)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 1000 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 1000,
            nonce: 0,
            fees: feeAmount,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        uint256 userEthBefore = user.balance;

        vm.startPrank(user);
        usdc.approve(address(intentGateway), inputAmount);
        // Send 5 ETH for a fee swap that should cost much less
        intentGateway.placeOrder{value: 5 ether}(order, bytes32(0));
        vm.stopPrank();

        // User should get back most of the 5 ETH — the swap only needed a tiny fraction
        uint256 ethSpent = userEthBefore - user.balance;
        assertTrue(ethSpent < 1 ether, "User should have been refunded most of the 5 ETH");
        assertTrue(ethSpent > 0, "User should have spent some ETH on the fee swap");
    }
