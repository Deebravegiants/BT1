### Title
Webhook HMAC validation covers only the raw body, not the `shop-domain` header — cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authenticated once `Utils::HmacValidator.validate(request)` succeeds, and then hands the handler a `WebhookMetadata` built from `request.shop`, which comes from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header. The HMAC, however, is computed only over the raw request body — the `shop`, `topic`, `webhook_id`, and `api_version` headers are never part of the signed data.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop`, `topic`, `webhook_id`, and `api_version` are all read straight out of unauthenticated headers: [2](#0-1) 

`Utils::HmacValidator.validate` only ever checks the signable string (i.e. the body) against the computed HMAC: [3](#0-2) 

`Registry.process` treats a passing HMAC check as full authentication of the request ("came from Shopify") and immediately forwards the unauthenticated `shop` header value to the app's handler as the tenant identifier: [4](#0-3) 

The gem's own documentation reinforces the misplaced trust, stating that `Registry.process` "will verify the request did indeed come from Shopify" and that `data.shop` is "The shop domain of the webhook", implying it is a trustworthy, verified value: [5](#0-4) [6](#0-5) 

Because the same `Context.api_secret_key` is used to sign webhooks for every shop that installs the app, and because the signature covers only the body, an attacker who controls a shop that has the app installed (i.e., any merchant able to install a public/development app) can capture one of their own legitimately-signed webhook deliveries (body + valid `hmac-sha256` header) and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop's domain (and/or the `topic`/`webhook-id` headers changed). `HmacValidator.validate` will still pass because it only checks the untouched body against the secret, but `Registry.process` will dispatch the handler with `shop: <victim-shop>`, `topic: <attacker-chosen>`, causing the host application — which trusts `data.shop` as the authenticated tenant key (as shown in the gem's own example, `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) — to process attacker-supplied content under another tenant's identity.

The identity binding broken is:
`shop authenticated by HMAC` ≠ `shop delivered to handler as WebhookMetadata#shop`

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: a request cryptographically proven to only originate from an app with knowledge of the shared secret can be relabeled to any shop the attacker chooses, without ever needing that shop's cooperation or credentials. Host applications that key data storage/business logic on `data.shop` (the gem's own documented pattern) can be made to associate attacker-controlled webhook content with a different merchant's tenant — a cross-tenant data injection.

### Likelihood Explanation
Any user able to install the target public/custom app on a shop they control can trivially capture one valid webhook delivery (body + `hmac-sha256`) for that shop, since Shopify sends real webhooks to any installed app's registered endpoint. Replaying it with a modified `shop-domain` (and other) header requires no special access, no secret disclosure, and no interception of another tenant's traffic — only a standard HTTP client.

### Recommendation
Extend the webhook HMAC verification (or an additional binding) to cover the `shop`, `topic`, `webhook_id`, and `api_version` values that are trusted downstream, or independently verify that the delivered `shop` corresponds to an actual known/installed shop with a stored session for this app before dispatching to the handler, rather than trusting the header value once the body-only HMAC passes.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`, triggering a real webhook, e.g. `orders/create`, and captures the raw POST: body `B` and header `x-shopify-hmac-sha256: H` (valid, since Shopify signed `B` with the app's shared secret).
2. Attacker sends a new POST to the app's webhook endpoint with the identical body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`).
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` recomputes the HMAC over `B` only and it matches `H`, so validation passes: [7](#0-6) 
4. `Registry.process` invokes the registered handler with `shop: "victim-shop.myshopify.com"` and attacker-controlled `body`, even though the data never originated from `victim-shop`: [8](#0-7)
