### Title
Unsigned cross-chain calldata dispatch trusts source-supplied `from` as dispatch origin - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`Flask-Caching`'s CVE is a CWE-502 issue: untrusted bytes are deserialized into a live object whose type/behavior an attacker controls, and the deserialized object is then acted upon without further authorization. The structural analog in this codebase is `pallet-hyper-fungible-token`'s `on_accept` handler, which SCALE-decodes attacker-influenced calldata directly into a `T::RuntimeCall` and dispatches it against a runtime origin, with the origin itself derived from unauthenticated fields of the same untrusted message when no signature is attached.

### Finding Description
In `modules/pallets/hyper-fungible-token/src/module.rs`, `on_accept` decodes the ISMP post-request body into a `Message`, then, if `message.data` is non-empty, decodes it into `SubstrateCalldata` [1](#0-0) .

If `substrate_data.signature` is `None`, the dispatch origin is computed straight from `message.from` — bytes carried in the same cross-chain message body, with no cryptographic binding to a signature over the actual `runtime_call` payload: [2](#0-1) 

The arbitrary SCALE bytes are then decoded into a live `RuntimeCall` and dispatched with `Signed(origin)`: [3](#0-2) 

The only gate on which dispatchables can be reached is `BaseCallFilter::contains`, which is a coarse, runtime-wide filter (not scoped to bridge-safe calls) [4](#0-3) . In the unsigned branch, the "origin" is not actually the true off-chain caller — it is whatever `message.from` value was placed into the message by the source-chain contract call that produced this ISMP request. Authentication of the ISMP request itself only establishes that it came from a contract address mapped in `ContractToAsset` [5](#0-4) ; it does not attest that the specific `from` account inside the ABI-encoded `Message` was the actual initiator, nor that the initiator intended to authorize the enclosed `runtime_call`. This mirrors the Pickle bug-class: the untrusted, decoded payload directly drives both "who is dispatching" and "what gets dispatched," with the only defense being a generic type/allow-list filter rather than message-integrity binding.

### Impact Explanation
If the source-chain bridge/entrypoint contract allows a caller to set `from`/calldata independently of `msg.sender` (or if any other path can populate a `Message` with attacker-chosen `from` and `data`), an attacker can impersonate an arbitrary Substrate `AccountId` (via `beneficiary_bytes`/`from_bytes` conversion) and dispatch any call permitted by `BaseCallFilter` as that account — e.g. moving assets, calling pallet extrinsics that assume a legitimate signed origin, or interacting with other pallets on behalf of a victim account, all without ever presenting a valid signature. This is unauthorized app action / potential unbacked value transfer initiated purely by a crafted cross-chain message, satisfying the "unauthorized app action" / "theft of funds" bar.

### Likelihood Explanation
Reachable by a single relayed ISMP post request from a mapped source contract; requires only that the source-side contract construction of `Message.from`/`Message.data` is not strictly tied to `msg.sender`, which is a real-world integration risk for any generic ERC-20/HFT bridge front-end since this pallet's own SCALE-decode-and-dispatch logic performs no independent verification for the unsigned branch. Given the code explicitly supports two paths (signed and unsigned) it should be assumed both are expected to be reachable in production deployments.

### Recommendation
Do not allow the no-signature branch to derive a dispatch origin from message-embedded `from` bytes for privileged extrinsic dispatch. Require a signature (over `runtime_call` plus nonce, as already implemented in the `Some(signature)` branch) for any calldata execution, or restrict the unsigned branch to a narrowly scoped, pre-approved allow-list of no-op/refund-safe calls rather than `BaseCallFilter::contains` (which is a general runtime policy, not a bridge-specific one). Additionally, verify at the source-contract level that `from` in the ABI-encoded `Message` is cryptographically tied to the actual caller (e.g., always `msg.sender`), so this pallet cannot be handed an attacker-chosen origin.

### Proof of Concept
1. Attacker calls the source-chain bridging entrypoint (mapped in `ContractToAsset`) supplying a `Message` where `to`/`from` are attacker-chosen 20/32-byte identifiers and `data` is a SCALE-encoded `SubstrateCalldata { signature: None, runtime_call: <arbitrary call permitted by BaseCallFilter> }`.
2. The relayer delivers this as an ISMP `PostRequest`; `on_accept` runs [6](#0-5) .
3. Since `substrate_data.signature` is `None`, origin resolves to `T::EvmToSubstrate::convert(...)`/raw 32-byte account derived from `message.from`, which the attacker fully controls in the payload they submitted [2](#0-1) .
4. `runtime_call` is decoded and dispatched as `Signed(origin)` without any proof the victim/account owner authorized it [3](#0-2) , executing any call not blocked by `BaseCallFilter`.
