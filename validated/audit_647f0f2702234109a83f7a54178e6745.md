### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Utils::HmacValidator.validate` authenticates that body against the app's shared `client_secret`. The `shop` value, however, is read from the `X-Shopify-Shop-Domain` HTTP header, which is *not* part of the signed bytes. `Registry.process` accepts any request whose body-HMAC is valid and then forwards `request.shop` unchanged to the app's webhook handler as an authenticated tenant identifier.

### Finding Description
The intended binding is: `hmac == HMAC(secret, bytes_delivered_by_shopify_for_shop_X)` should imply `shop == X`. In this gem that equality does not hold, because:

- `Request#to_signable_string` returns `@raw_body` only [1](#0-0) .
- `Request#shop` is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic tie to the body or to the HMAC [4](#0-3) .
- `HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it with the received HMAC — it never inspects `shop` [5](#0-4) .
- `Registry.process` raises only if the HMAC over the body is invalid, then immediately builds `WebhookMetadata` using `request.shop`, treating it as a verified tenant identifier and dispatching it to the app's handler [6](#0-5) .

Crucially, the HMAC secret (`Context.api_secret_key`) is the same for every shop that installs the app — it is not a per-shop key. So an attacker who controls a shop that has legitimately installed the app can capture real, validly-signed webhook deliveries for their own shop (raw body + `X-Shopify-Hmac-Sha256`), then replay that identical body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header value naming a victim shop. `HmacValidator.validate` still passes, because it only checks the body bytes against the shared secret, and `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain, per the documented handler contract that trusts `data.shop` [7](#0-6) .

### Impact Explanation
This breaks the equality "shop authenticated by HMAC == shop stored/acted upon by the host application," letting an unprivileged attacker (any merchant who can install the app) inject webhook payloads that appear to the host application to originate from a shop they do not control. Depending on how the host implementation keys webhook processing (order sync, product updates, uninstall/GDPR events, etc.) by `data.shop`, this can lead to cross-tenant data corruption or cross-tenant data disclosure — writing or triggering actions against a victim tenant's records using attacker-supplied body content. This matches the "cross-tenant access" Critical impact category, since the trust boundary between tenants is defined entirely by this unauthenticated header.

### Likelihood Explanation
Likelihood is high for any app built on the documented API: no privileged credentials are required beyond the ability to install the app for one's own store (a low bar for any public/embedded app), and the only work needed is capturing one legitimately delivered webhook and replaying it with a modified header — both raw body and HMAC can be reused verbatim since neither depends on the shop field.

### Recommendation
Bind `shop` into the signed material, or otherwise cryptographically tie it to a value Shopify actually signs. Concretely:
- Include the shop domain in `to_signable_string` (or verify it against an independently-fetched, session-bound shop associated with the specific webhook subscription/`webhook_id`) before trusting `request.shop`.
- At minimum, document and enforce that host applications must cross-check `data.shop` against a shop for which they have registered that specific `webhook_id`/topic combination, rather than treating the header as self-authenticating.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, unprivileged install).
2. Shopify delivers a legitimate webhook to the app's endpoint: raw body `B`, header `X-Shopify-Hmac-Sha256: H` (computed by Shopify over `B` using the shared `client_secret`), and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker replays this exact request to the same endpoint, changing only `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`, keeping body `B` and HMAC header `H` unchanged.
4. `ShopifyAPI::Webhooks::Request.new` parses this into `shop == "victim-shop.myshopify.com"` while `hmac == H`.
5. `HmacValidator.validate` recomputes `HMAC(secret, B)`, which still equals `H`, so validation succeeds.
6. `Registry.process` invokes the registered handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, and the host application processes attacker-controlled content under the victim shop's identity.
