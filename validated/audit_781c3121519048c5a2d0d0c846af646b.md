The delegate-grant mechanism looks like the strongest capture-replay analog. Let me verify what authority delegates actually hold and whether the stale-grant re-arming path is exploitable.### Title
Stale `DelegateGrant` replays and re-arms old delegate authority when the position NFT returns to the original owner - ([File: contracts/controller/src/storage/account.rs](contracts/controller/src/storage/account.rs))

### Summary
Analogous to CVE-2021-38296 (capture-replay of an authentication credential), the controller "captures" a delegate authorization in a `DelegateGrant` stamped with `granted_by`, and that stale credential is silently "replayed" — reactivated without any fresh authorization — if the position NFT ever returns to `granted_by`. `get_delegates` only checks `grant.granted_by == current_owner`; an NFT transfer makes the grant dormant but does not delete it. Because `position-nft transfer` requires only `from.require_auth()`, a holder can force the token back onto the original owner, re-arming the prior delegate list.

### Finding Description
`DelegateGrant` is a single per-account record keyed by `ControllerKey::Delegates(account_id)`, stamped with the granting owner: [1](#0-0) 

Reads are filtered by owner, so a transfer disables the grant — but storage is untouched: [2](#0-1) 

The stale entry persists and becomes live again the moment `owner_of(account_id) == grant.granted_by` once more. The only purge paths require the *new* owner to call `add_delegate`/`remove_delegate` (`remove_delegate` deletes grants stamped by a different owner) — an owner who simply holds and later sells back never purges it: [3](#0-2) 

The NFT itself confirms `transfer` needs only `from` authorization — the recipient never consents, so anyone who holds the token can push it back to `granted_by`: [4](#0-3) 

Delegates are governance-activated position managers, and per the protocol's own docs they "may borrow or withdraw to arbitrary recipients" — i.e., delegate authority is full account control: [5](#0-4) 

### Impact Explanation
Theft of user funds. Once the grant re-arms, every delegate on the stale list regains the ability to invoke owner-level controller entrypoints (`borrow`, `withdraw`, `multiply`, `swap_collateral`, etc.) against the account. A user who sold a position and later reacquired the same token id (ids are never reused) — or who had the token forced back to them — is exposed to a delegate they believe was revoked by the sale. There is no event, no expiry, and no re-authorization; the "captured" grant replays verbatim.

### Likelihood Explanation
Requires (a) a prior `add_delegate` by owner A, (b) A's NFT moving to a holder who never writes the delegate entry, and (c) the token returning to A. Condition (c) is attacker-influenceable: an attacker who acquires the token (market purchase of a position with a dormant grant, visible via persistent storage) can `transfer` it back to A without A's signature, then trigger or benefit from the re-armed manager. The constraint that delegates must be governance-activated managers (`set_account_delegate` asserts `is_active`) limits who sits on the delegate list, but registered automation/strategy managers are exactly the kind of contract a user grants once and forgets — and a malicious or compromised registered manager, or one with permissionless trigger functions and attacker-directable payouts, turns the replay into a drain. [6](#0-5) 

### Recommendation
Bind the grant to an ownership epoch rather than an address. E.g., store an `ownership_epoch`/`grant_nonce` in `AccountMeta` that the controller bumps whenever it observes `owner_of` change (or hook NFT transfer via the controller), and have `get_delegates` additionally require `grant.epoch == meta.epoch`. Simpler alternative: delete `Delegates(account_id)` eagerly — since `transfer` on the NFT cannot call into the controller, add a lazy purge: record `last_seen_owner` alongside the grant and overwrite (not just filter) on any account load where the owner differs. At minimum, `get_delegates` returning a mismatched `granted_by` should delete the entry rather than leave it dormant.

### Proof of Concept
1. Alice owns position `account_id = N` and calls `controller.add_delegate(alice, N, M)` where `M` is an active position manager. `DelegateGrant{granted_by: alice, delegates: [M]}` is stored.
2. Alice sells the position: `position_nft.transfer(alice, bob, N)`. The grant is dormant — `get_delegates(N, bob)` is empty — but `ControllerKey::Delegates(N)` still holds Alice's grant. Bob never calls `add_delegate`/`remove_delegate`, so no purge occurs.
3. Attacker acquires `N` from Bob (or attacker was Bob), then calls `position_nft.transfer(attacker, alice, N)` — valid because only `from` authorizes. Alice never signed anything touching delegates.
4. `owner_of(N) == alice == grant.granted_by`; `get_delegates(N, alice)` returns `[M]`. The stale authorization has replayed.
5. `M` (or anyone able to trigger `M`'s strategy entrypoints) invokes `controller.borrow`/`withdraw` on `account_id = N` to an arbitrary recipient, draining Alice's collateral up to her LTV.

```rust
pub(crate) fn get_delegates(env: &Env, account_id: u64, owner: &Address) -> Vec<Address> {
    get_user::<DelegateGrant>(env, &ControllerKey::Delegates(account_id))
```

```rust
pub(crate) fn remove_delegate(
    env: &Env,
    account_id: u64,
    owner: &Address,
    delegate: &Address,
) -> bool {
    let key = ControllerKey::Delegates(account_id);
    let Some(grant) = get_user::<DelegateGrant>(env, &key) else {
        return false;
    };
    if grant.granted_by != *owner {
        env.storage().persistent().remove(&key);
        return false;
    }
    let mut delegates = grant.delegates;
    let Some(index) = delegates.first_index_of(delegate) else {
        return false;
    };
    delegates.remove(index);
    set_delegates(env, account_id, owner, &delegates);
    true
}
```

```rust
fn set_account_delegate(
    env: &Env,
    caller: &Address,
    account_id: u64,
    delegate: &Address,
    add: bool,
) {
    caller.require_auth();
    require_account_owner(env, account_id, caller);
    if add {
        // Reject dormant grants that could gain authority on later manager activation.
        assert_with_error!(
            env,
            storage::get_position_manager(env, delegate).is_some_and(|c| c.is_active),
            GenericError::NotAuthorized
        );
    }

    let changed = if add {
        storage::add_delegate(env, account_id, caller, delegate)
    } else {
        storage::remove_delegate(env, account_id, caller, delegate)
    };
```
