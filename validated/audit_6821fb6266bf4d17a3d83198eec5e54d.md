### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` field entirely from the unauthenticated `X-Shopify-Shop-Domain` HTTP header, while the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` validates is computed only over the raw request body. Because the shop identity is never bound into the signed material, an attacker who owns any shop that has the app installed can replay a body/HMAC pair legitimately produced for their own webhook, while substituting the `shop-domain` header for a victim shop, and have the library accept it as authentic. This is the direct analog of the reported bug class: "a field acted on but not covered by the HMAC."

### Finding Description
`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it with `OpenSSL.secure_compare`: [1](#0-0) 

For webhook requests, `to_signable_string` returns only the raw HTTP body — the `shop` value is read separately from an HTTP header and is not part of the signed string at all: [2](#0-1) 

`Registry.process` performs exactly one check — that the HMAC matches the raw body — and then dispatches the handler using the attacker-controllable, unsigned `request.shop` value: [3](#0-2) 

Because `Context.api_secret_key` (the app's client secret) is a single value shared across every shop that has the app installed, the HMAC computed for a message from Shop A is not shop-specific — it will validate identically no matter what the `shop-domain` header says. This is confirmed by the test suite, which builds the HMAC purely from the body and shows `shop` is read independently: [4](#0-3) 

The breaking equality is:
`shop authenticated by HMAC` (nothing — HMAC only covers the body) ≠ `shop the handler is told the event came from` (`request.shop`, taken from an unauthenticated header).

### Impact Explanation
An attacker who controls any shop with the app installed (i.e., an unprivileged tenant of the app, not requiring any special credential) can:
1. Trigger a legitimate webhook delivery to their own endpoint (e.g., `orders/create`) — this is a valid, correctly-signed `(raw_body, hmac)` pair signed with the app's shared `api_secret_key`.
2. Replay that exact body/HMAC to the app's webhook endpoint, but swap the `X-Shopify-Shop-Domain` header to name any *other* installed shop.
3. `HmacValidator.validate` returns `true` (the HMAC only checked the body), and `Registry.process` calls the app's handler with `WebhookMetadata.shop` set to the victim shop, while the payload content belongs to the attacker.

This lets one tenant's data be attributed to and processed under a different tenant, i.e. cross-tenant contamination/access — depending on how the hosting app's handler uses `data.shop` (e.g., to select which merchant's DB record to update/delete, or to trigger app-side side effects), this can corrupt or leak data across shop boundaries, or force app-uninstall/reinstall logic under the wrong tenant.

### Likelihood Explanation
No secret material is required beyond becoming an app user (installing a free/dev app is a normal unprivileged action), and the exploit only needs to capture one webhook delivery from the attacker's own store and replay it with a modified header, which is fully within reach of an unprivileged internet user/tenant.

### Recommendation
Bind the shop identity into the signed material, or otherwise cross-verify it against something authenticated:
- Compute/verify the HMAC using a per-shop secret (if available), or
- Include the `shop` header value in `to_signable_string` (this requires a change to the Shopify webhook signing contract, which the gem alone cannot unilaterally fix), or
- At minimum, cross-check `request.shop` against a shop domain already known to be enrolled in the app's session store before dispatching to handlers, and document to consumers that `data.shop` from `WebhookMetadata` must not be trusted without an independent lookup (e.g., resolve the target shop only via a topic/webhook-id lookup performed against Shopify, not from the header alone).

### Proof of Concept
```ruby
# Attacker controls "attacker-shop.myshopify.com", which has the app installed.
# Shopify delivers a legitimately-signed webhook to the attacker for their own shop:
raw_body = '{"id":1,"note":"hello"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# Attacker forges a request to the app's webhook endpoint, reusing the
# valid (raw_body, hmac) pair but claiming it belongs to the victim shop:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # unsigned, attacker-controlled
}

req = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# This succeeds: HMAC validation only checks raw_body, not shop-domain.
ShopifyAPI::Webhooks::Registry.process(req)
# => handler.handle(WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: {...attacker's data...}, ...))
```
