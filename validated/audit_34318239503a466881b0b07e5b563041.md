### Title
Webhook `shop-domain` and `topic` headers are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature solely over the raw request body, while the `shop` and `topic` fields — read from unauthenticated HTTP headers — are passed downstream to the app's webhook handler as trusted identity metadata. The equality the gem should enforce is `hmac_secret(bytes_verified) == bytes_acted_on`, but here `bytes_verified = raw_body` while `bytes_acted_on = {raw_body, shop_header, topic_header}`. The `shop` and `topic` headers break out of the HMAC binding entirely.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` and `Request#topic` are derived straight from attacker-controllable HTTP headers (`shopify-shop-domain` / `x-shopify-shop-domain`, `shopify-topic` / `x-shopify-topic`), with no cryptographic tie to the signed body: [2](#0-1) 

`Registry.process` validates only the body-derived HMAC via `Utils::HmacValidator.validate(request)`, then immediately forwards the unauthenticated `request.shop` and `request.topic` values into `WebhookMetadata` handed to the app's handler: [3](#0-2) 

`HmacValidator.validate_signature` recomputes the HMAC only from `verifiable_query.to_signable_string` (the raw body for webhooks) and compares it to the `hmac-sha256` header — it never incorporates `shop` or `topic`: [4](#0-3) 

Because the `client_secret`/`api_secret_key` used to sign webhooks is the **same secret for every shop** that has installed a given app, any merchant who has installed the app on their own store legitimately receives valid `(body, hmac)` pairs signed with that shared secret. Such a merchant (an "unprivileged internet user" relative to any *other* tenant of the app) can replay that valid body+HMAC to the app's webhook endpoint while forging the `shopify-shop-domain` header to name a victim shop, and/or forging `shopify-topic` to pick a different registered handler. `HmacValidator.validate` still returns `true` because it only checks the body bytes, so `Registry.process` happily dispatches the forged `shop`/`topic` to the handler as if they were authentic.

### Impact Explanation
This lets one tenant (merchant) of a multi-tenant Shopify app forge webhook events attributed to a different tenant, since `shop` is not bound to the HMAC. Host applications commonly use `WebhookMetadata#shop` to select which merchant's session/data record to update (e.g., uninstall processing, order/customer data writes, GDPR redact handlers), so a forged `shop` value can cause cross-tenant data corruption or unauthorized actions against a merchant who never sent the request — a cross-tenant access issue within the gem's own trust boundary.

### Likelihood Explanation
Requires only that the attacker be a merchant who has installed the app (no privileged credentials, no `api_secret_key`, no TLS interception) and can capture at least one legitimate webhook delivery to their own endpoint (trivially observable, since they control the endpoint). They then replay it against the shared app endpoint with a modified `shop-domain`/`topic` header. This is a realistic, low-effort attack path reachable purely through this gem's public `Registry.process` / `Request` API as documented for consumers.

### Recommendation
Bind the `shop` (and ideally `topic`) into the signed material used for verification, or otherwise cross-check the header-derived `shop` against an authenticated source (e.g., require the caller to supply the expected shop and compare it, or validate the shop is one with a currently valid installation/session before dispatch) rather than trusting header values whose only "protection" is an HMAC that covers unrelated bytes (the body). At minimum, document prominently that `Request#shop`/`#topic` are unauthenticated and must not be used as a tenant-selection key without additional verification.

### Proof of Concept
1. App `A` is installed on attacker's own shop `attacker.myshopify.com` and on victim shop `victim.myshopify.com`, both webhooks signed with the same `client_secret`.
2. Attacker triggers/receives a legitimate webhook delivery to their own store, capturing `raw_body` and its valid `X-Shopify-Hmac-Sha256` header.
3. Attacker POSTs the same `raw_body` and `hmac-sha256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `HmacValidator.validate(request)` in `lib/shopify_api/utils/hmac_validator.rb` returns `true` (body signature matches).
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` builds `WebhookMetadata` with `shop: "victim.myshopify.com"` and invokes the handler, which the host app trusts as data belonging to the victim tenant.
