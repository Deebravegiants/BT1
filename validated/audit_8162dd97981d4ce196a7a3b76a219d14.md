### Title
Secure-element signup signature omits operator/distributor binding, enabling misattributed signup - ([File: src/plans/enroll_user.rs])

### Summary
`make_signature()` in `src/plans/enroll_user.rs` computes and secure-element-signs a digest that is supposed to cryptographically attest to the integrity of a signup submission, but the digest only covers a subset of the fields that are actually sent to the backend in the same request. Just like the reported GMX bug computes slippage protection against the user's *stated* deposit instead of the actual (leveraged) amount deposited, this signature is computed over a *subset* of the signup data while the backend receives — and treats as covered — a superset that includes the operator/distributor identity, region, and geolocation.

### Finding Description
`make_signature` hashes only: `ORB_ID`, `user_qr_code.user_id`, `pipeline.v2.ir_net_version`, `pipeline.v2.iris_version`, and the plain iris/mask codes (not their MPC shares) for both eyes: [1](#0-0) 

That signature is then submitted as one field among many others that are *not* part of the signed digest, via `signup_post::request`, notably `distributorId` (the operator/attribution QR code), `region`, `latitude`/`longitude`, and `reason`: [2](#0-1) 

The call site passes `self.operator_qr_code` (the distributor/operator attribution) into the request independently of the signature computation, which only receives `user_qr_code` and `pipeline`: [3](#0-2) 

Because the cryptographic protection (secure-element signature) is computed on a narrower basis than the actual payload it accompanies, the “protected” quantity (iris identity binding) is decoupled from the operator/distributor attribution that determines credit/commission and audit trail for the signup, mirroring the root cause of the reported analog: a security-relevant amount/threshold computed against a proxy value instead of the real value being committed.

### Impact Explanation
If the `distributorId` (operator attribution) sent alongside the signature can diverge from what the signature's issuer intended (e.g. due to a race in `QrCodes` resolution, a compromised/rogue operator QR reused across sessions, or any code path that swaps `operator_qr_code` after the signature is computed), the backend cannot detect the inconsistency by validating the signature — the signature stays valid for the iris codes and user id, but says nothing about which operator/distributor is credited for the signup. This can lead to misattributed signups (a directly accepted impact category), since operator attribution is a security/business-relevant claim about the signup that is unprotected by the same integrity mechanism that protects the biometric identity binding.

### Likelihood Explanation
The `operator_qr_code` and `user_qr_code`/`pipeline` values used to build the request are threaded through several async plan stages (`QrCodes`, `ResolvedQrCodes`, `scan_remaining_qr_codes`) before reaching `enroll_user::Plan::run`; any future refactor or bug in that chain that changes which operator context accompanies a given biometric signature would not be caught by signature verification, since operator/distributor identity was never part of the signed digest to begin with. No privileged access is required to exploit divergence — an unprivileged flow (normal operator/user QR scanning sequence) is sufficient.

### Recommendation
Include `operator_qr_code.user_id` (and ideally `s3_region`, `signup_reason`) in the `make_signature` digest so the secure-element signature binds the full submitted signup context, not just the iris codes and user id — analogous to fixing the slippage check to use the actual (leveraged) deposit value instead of the user's stated value.

### Proof of Concept
1. Observe that `make_signature` (src/plans/enroll_user.rs:290-304) hashes only `ORB_ID`, `user_qr_code.user_id`, `ir_net_version`, `iris_version`, and iris/mask codes.
2. Observe that `signup_post::request` (src/backend/signup_post.rs:98-143) additionally transmits `operator_qr_code.user_id` as `distributorId`, `s3_region` as `region`, and `signup_reason`, none of which are part of the signed digest.
3. Any component or future change that supplies a different `operator_qr_code` value than the one implicitly intended at signature-creation time (while keeping the same `user_qr_code`/`pipeline`) produces a request whose signature still validates, yet whose operator attribution is disconnected from what was cryptographically attested — demonstrating the signature protects a strict subset of the data it is presented as covering.

fn make_signature(user_qr_code: &qr_scan::user::Data, pipeline: &Pipeline) -> Result<String> {
    let mut ctx = Context::new(&SHA256);
    ctx.update(ORB_ID.as_str().as_bytes());
    ctx.update(user_qr_code.user_id.as_bytes());
    ctx.update(pipeline.v2.ir_net_version.as_bytes());
    ctx.update(pipeline.v2.iris_version.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code_version.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code_version.as_bytes());
    let signed = secure_element::sign(ctx.finish())?;
    Ok(BASE64.encode(&signed))
}
