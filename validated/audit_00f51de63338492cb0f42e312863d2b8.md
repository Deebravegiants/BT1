### Title
Webhook `shop`/`topic` identity fields are not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then trusts the `shop`, `topic`, `webhook_id`, and `api_version` values taken from HTTP headers that are *not* part of the signed material, and hands them to the host application's handler as if they were verified.

### Finding Description
`Utils::HmacValidator.validate` computes and compares an HMAC over `verifiable_query.to_signable_string`. For webhook requests, `Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers, none of which are included in `to_signable_string`: [2](#0-1) 

`Registry.process` validates only the body HMAC and then forwards the unauthenticated `request.shop` and `request.topic` values directly into `WebhookMetadata`, which is delivered to the app's handler as trusted identity data: [3](#0-2) 

`WebhookMetadata.shop` is a plain `String` const with no binding back to the HMAC-covered body: [4](#0-3) 

The broken identity binding, expressed as an equality that the gem fails to enforce:
`shop_covered_by_hmac == shop_delivered_to_handler`
In reality, only `raw_body_covered_by_hmac == raw_body` is enforced; `request.shop` (and `request.topic`) can be swapped freely by an attacker without invalidating the HMAC check, because they are never part of `to_signable_string`.

### Impact Explanation
An unprivileged internet user who can obtain any single valid `(raw_body, hmac)` pair — e.g., by installing the host app on their own store and capturing one of their own legitimate webhook deliveries — can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header with a victim shop's domain. `Registry.process` will accept the request (HMAC matches, since only the body is checked) and invoke the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: attacker_controlled_json, ...)`. Any host application that keys its persistence, authorization, or session lookups (a documented and expected pattern — see `WebhookMetadata` usage) off `data.shop` will process attacker-supplied data attributed to the victim tenant, achieving a cross-tenant data-injection/confusion condition. This satisfies the "cross-tenant access" Critical-impact criterion, since it breaks the tenant boundary the identity field is meant to enforce.

### Likelihood Explanation
Any developer/merchant can install a public app to generate a legitimate `(body, hmac)` pair for themselves, and the webhook HTTP endpoint is by design internet-reachable with no other authentication. Swapping a header on a replayed HTTP request requires no special privilege. The only constraint is that the attacker must craft or wait for a body they want attributed to the victim, which is fully within their control.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` header values (not just the raw body) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the verified payload before constructing `WebhookMetadata`, matching how Shopify's own webhook signing scheme should be verified end-to-end for identity-bearing headers.

### Proof of Concept
1. Attacker installs the host app on their own shop `attacker-shop.myshopify.com` and triggers a webhook (e.g., `products/create`) with attacker-controlled body content.
2. Attacker's endpoint receives the legitimate webhook: `raw_body = B`, header `x-shopify-hmac-sha256 = H` (valid for `B` under the app's `api_secret_key`), `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker resends the exact same `raw_body = B` and `x-shopify-hmac-sha256: H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes the HMAC over `B` only, which still matches `H`, so `Registry.process` proceeds.
5. The registered handler receives `WebhookMetadata(shop: "victim-shop.myshopify.com", body: parsed(B), topic: ..., ...)`, and any app logic keyed on `data.shop` now operates on attacker-controlled data as if it belonged to the victim shop.
