## Analog Found

### Title
State-commitment "latest height" pointer is reset to a fixed sentinel instead of the real prior height on veto, reopening the entire historical height range for commitment overwrite - ([File: evm/src/core/EvmHost.sol])

### Summary
The X.Org CVE describes a device whose grab/freeze state is tied to one context; when the device is reattached to a different master without properly clearing/restoring that state, a stale pointer is left referencing invalid data, causing out-of-bounds access. `EvmHost.deleteStateMachineCommitmentInternal` has the same defect class: it "reattaches" the state-machine's `latestStateMachineHeight` pointer to a hardcoded sentinel value (`1`) instead of the real previous canonical height, leaving a stale/incorrect pointer that reopens far more of the commitment history than intended for overwrite.

### Finding Description
`deleteStateMachineCommitmentInternal` is the fisherman-veto path, reachable by any relayer/fisherman that submits a valid fraud proof through the handler: [1](#0-0) 

When the vetoed height equals the current `_latestStateMachineHeight`, the code resets the pointer to the constant `1` rather than to the actual last-known-good height (as the substrate implementation does with `PreviousStateMachineHeight`): [2](#0-1) 

Contrast this with `HandlerV2.handleConsensus`, which gates every incoming intermediate state solely by `intermediate.height > latestHeight`: [3](#0-2) 

and `storeStateMachineCommitment`, which unconditionally overwrites whatever commitment already exists at a given height with no check that the height was already finalized/immutable: [4](#0-3) 

Because the veto resets the pointer to `1` instead of the true previous height, every height between `1` and the vetoed height — not just the vetoed one — becomes eligible for re-storage. The substrate pallet at least reopens only the range back to `PreviousStateMachineHeight` (documented and unit-tested at [5](#0-4) ), but `EvmHost` has no equivalent "previous height" bookkeeping at all, so it collapses to the constant `1`, reopening the entire historical range of that state machine to commitment overwrite by the next relayer-submitted consensus proof.

### Impact Explanation
Any relayer that subsequently calls `handleConsensus` with a proof whose intermediate states include heights previously considered final (heights between `1` and the old `latestStateMachineHeight`) can overwrite already-settled `StateCommitment`s for that state machine, since the only guard (`intermediate.height > latestHeight`) is neutralized once `latestHeight` collapses to `1`. This corrupts previously-finalized state roots used by `handlePostRequests`, `handleGetResponses`, and timeout handlers to verify membership/non-membership proofs, i.e. an unsound state commitment that a relayer can subsequently use to forge or replay message delivery/timeout proofs against a rolled-back or attacker-influenced state root.

### Likelihood Explanation
The trigger is a single, permissionless fisherman veto (`deleteStateMachineCommitment`, restricted only to the `handler` contract but driven by any party submitting a valid fraud proof) followed by any subsequent, otherwise-legitimate `handleConsensus` call from any relayer — no privileged or admin access is required. Every state machine that has ever had a fraud proof processed against its latest height is affected.

### Recommendation
Track the actual previous canonical height per state machine (mirroring pallet-ismp's `PreviousStateMachineHeight`) in `EvmHost`, and on veto reset `_latestStateMachineHeight[stateMachineId]` to that stored previous height instead of the hardcoded `1`, so only the narrow range genuinely affected by the veto is reopened for resubmission.

### Proof of Concept
1. Consensus proofs advance `stateMachineId X` to height `1000` via `storeStateMachineCommitment`, setting `_latestStateMachineHeight[X] = 1000`.
2. A fisherman detects fraud at height `1000` and calls `deleteStateMachineCommitment`, which sets `_latestStateMachineHeight[X] = 1` (per [6](#0-5) ) instead of the real prior canonical height (e.g. `950`).
3. Any relayer submits `handleConsensus` with a proof containing intermediate states for heights `2..999` (previously final, uncontested commitments). Because `latestHeight` is now `1`, the check `intermediate.height > latestHeight` passes for all of them, and `host.storeStateMachineCommitment` overwrites the previously-final `StateCommitment`s for those heights.
4. The relayer now targets `handlePostRequests`/`handleGetResponses` proofs against one of the overwritten heights, using the newly-injected (stale/attacker-favorable) `overlayRoot`/`stateRoot` to forge delivery or manipulate message-membership results that would not have validated against the original, correctly-finalized commitment.

// Vetoing the *latest* height resets the latest pointer, which re-opens that height
// for honest resubmission. The resubmission gets a second queue entry, and the stale
// twin ahead of it evicts the live commitment one insertion early. This pins that
// wart: it costs the height one insertion of retention and burns one queue slot,
// which is negligible against the configured caps but is not a no-op.
#[test]
fn vetoed_latest_height_that_is_resubmitted_evicts_one_insertion_early() {
	let mut ext = new_test_ext();
	ext.execute_with(|| {
		let host = Ismp::default();
		let id = queue_test_state_machine();
		let store = |height: u64| {
			host.store_state_machine_commitment(
				StateMachineHeight { id, height },
				queue_test_commitment(),
			)
			.unwrap();
			host.store_latest_commitment_height(StateMachineHeight { id, height }).unwrap();
		};

		pallet_ismp::Pallet::<Test>::update_commitment_caps(
			RuntimeOrigin::root(),
			BTreeMap::from([(id, 2)]),
		)
		.unwrap();

		store(10);
		store(11);

		// Vetoing the latest height rolls the latest pointer back to 10, so the
		// consensus handler would accept 11 again: it is not below the latest and
		// its commitment is now absent.
		host.delete_state_commitment(StateMachineHeight { id, height: 11 }).unwrap();
		assert_eq!(host.latest_commitment_height(id).unwrap(), 10);

		store(11);
		assert!(host.state_machine_commitment(StateMachineHeight { id, height: 11 }).is_ok());
		// Two queue entries now point at height 11: the stale one and the live one.
		assert_eq!(StateCommitmentQueue::<Test>::get(id, 1), Some(11));
		assert_eq!(StateCommitmentQueue::<Test>::get(id, 2), Some(11));

		// Evicting the stale entry at index 1 deletes the live commitment for 11,
		// one insertion before the entry at index 2 would have.
		store(12);
		assert!(host.state_machine_commitment(StateMachineHeight { id, height: 11 }).is_err());
		assert!(host.state_machine_commitment(StateMachineHeight { id, height: 12 }).is_ok());
		// The queue still counts index 2 as live, so the burnt slot leaves this
		// chain retaining one fewer commitment than its cap of 2.
		assert_eq!(
			CommitmentQueueStates::<Test>::get(id),
			CommitmentQueueState { head: 2, tail: 4 }
		);
		assert_eq!(StateCommitmentQueue::<Test>::get(id, 2), Some(11));
	})
}
