### Title
Webhook `shop`/`topic` identity is trusted from unauthenticated headers while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Registry.process` accepts the request purely based on `Utils::HmacValidator.validate(request)` succeeding against that body [2](#0-1) . The `shop`, `topic`, and `webhook_id` values that are then handed to the application's webhook handler as trusted tenant-identifying metadata (`WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)`) are read straight from HTTP headers [3](#0-2)  that are never included in the HMAC-signed content.

### Finding Description
This mirrors the reported bug class: a field that is acted upon (`shop`, used as the tenant identity for the webhook) is not covered by the integrity check (the HMAC only signs `@raw_body`). The equality that should hold is:

`shop authenticated by HMAC == shop used to key/attribute the webhook`

but in this code the left side doesn't exist at all — no header is bound into `to_signable_string`, only the body is [1](#0-0) . Since the app's `client_secret`/`api_secret_key` is a single shared secret for the app (identical across every shop/tenant that installs it), any tenant who legitimately controls a webhook delivery from their own shop can compute a valid HMAC over an arbitrary raw body using that same shared secret, then attach forged `x-shopify-shop-domain`/`shopify-shop-domain` and `x-shopify-topic` headers claiming to be a different shop or a different (possibly more sensitive) topic. `HmacValidator.validate` only recomputes the signature from `to_signable_string` (the body) and secure-compares it [4](#0-3) ; it has no way to detect that the `shop-domain`/`topic` headers were substituted, because those fields were never part of the signed string in the first place.

### Impact Explanation
If a host application trusts `WebhookMetadata#shop` (as the library's own registry code does when constructing the metadata passed to handlers) as the tenant key for writing/reading data, an attacker who is a legitimate (even free-tier) merchant of the app can forge webhook deliveries that are misattributed to a different shop. Combined with a body the attacker fully controls (since it's their own body, correctly HMAC'd with the shared secret), this is a cross-tenant identity confusion: the signature only proves "signed by an app installer," not "this event belongs to shop X." This matches the Critical criterion of cross-tenant access through a broken identity binding.

### Likelihood Explanation
Exploitation requires only that the attacker be able to receive a legitimately signed webhook to their own endpoint or otherwise obtain one HMAC/body pair signed with the shared `api_secret_key`, and that they can then replay it to the target app's webhook endpoint with modified `shop-domain`/`topic` headers. No secret material beyond what a normal, unprivileged merchant already possesses through app installation is required, and the header parsing (`shopify_header`) accepts either legacy or new-format headers without any additional binding [5](#0-4) .

### Recommendation
Bind the security-relevant headers (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) into the signed content that `HmacValidator` checks — i.e., extend `VerifiableQuery#to_signable_string` for `Webhooks::Request` to canonically include these header values alongside the raw body, or independently verify `request.shop` against the caller's own list of currently-installed shops before trusting it, rather than relying solely on body-HMAC success for both integrity and shop attribution.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`; the app's `client_secret` is shared across all installs.
2. Attacker triggers/receives a legitimate webhook delivery, obtaining a raw body `B` and its valid `x-shopify-hmac-sha256` signature `H = HMAC_SHA256(client_secret, B)`.
3. Attacker crafts a new HTTP POST to the app's webhook endpoint with the same body `B` and signature `H`, but sets `x-shopify-shop-domain: victim.myshopify.com` (and/or a different `x-shopify-topic`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` [6](#0-5) , which recomputes HMAC over `B` only and succeeds, since `B` and `H` are unchanged and match.
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` [7](#0-6)  despite the event actually originating from the attacker, allowing cross-tenant data confusion if the host app trusts this field as-is.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
