### Title
Loaded-accounts-data-size cap silently clamps the fee-charged size instead of preserving the true measured size on fee-only failure - (File: `svm/src/account_loader.rs`)

### Summary
The reported analog is structurally similar to the `RewardsClaimer` bug: a value that legitimately exceeds an admin/consensus-set cap (`maxClaimPerWallet` vs. `requested_loaded_accounts_data_size_limit`) is not tracked/preserved past the cap — the excess is discarded and replaced by the cap value itself, rather than the actual measured quantity. In `svm/src/account_loader.rs`, `LoadedTransactionDataSize::increase_calculated_data_size` accumulates the true loaded size, but the conversion `From<LoadedTransactionDataSize> for u32` reports `min(loaded_accounts_data_size, requested_loaded_accounts_data_size_limit)` rather than the real measured size once the transaction is over budget.

### Finding Description
`LoadedTransactionDataSize` tracks two things: the actual accumulated `loaded_accounts_data_size` and the `requested_loaded_accounts_data_size_limit` (the SIMD/compute-budget cap, default or user-set via `ComputeBudgetInstruction::set_loaded_accounts_data_size_limit`, capped at `MAX_LOADED_ACCOUNTS_DATA_SIZE_BYTES`). [1](#0-0) 

When `increase_calculated_data_size` is called and the running total exceeds the limit, it returns `TransactionError::MaxLoadedAccountsDataSizeExceeded`, but the internal `loaded_accounts_data_size` field has already been updated to the (potentially much larger) real measured value before the check fails. [2](#0-1) 

The `From<LoadedTransactionDataSize> for u32` impl, however, reports `value.loaded_accounts_data_size.min(value.requested_loaded_accounts_data_size_limit)` — i.e. it clamps the value down to the cap for external consumers (fee/cost accounting), discarding the true measured size analogous to how `userPendingRewards` was zeroed instead of carrying forward the true entitlement past `maxClaimPerWallet`. [3](#0-2) 

This clamped value is exactly what feeds fee-only transaction accounting: the integration test `fee_only_loaded_transaction_data_size` demonstrates that once a transaction blows the loaded-accounts-data-size limit (under `define_ltds_fee_only_semantics`), the reported `loaded_accounts_data_size()` used for fee-only committed transactions is set to `size_limit` — the cap — rather than the true `other_accounts_size` that was actually loaded/measured. [4](#0-3) 

### Impact Explanation
The loaded-accounts-data-size figure directly feeds the cost model, which converts it into a compute-unit cost component (`loaded_accounts_data_size_cost`) used both for cost-tracker block/account limit enforcement and for `fee_only`/failed-transaction fee computation. [5](#0-4) 

Because the value used downstream is capped to the requested limit rather than reflecting the actual (larger) accounts data footprint that was loaded before the check failed, a transaction that vastly exceeds its declared limit is billed/costed only up to the cap — materially underpricing the true resource consumption for fee-only ("processed-but-failed due to size") transactions. This mirrors the reward bug's core defect: silently discarding the true value in favor of the cap, producing under-accounting rather than accurate tracking of the real magnitude.

### Likelihood Explanation
This path is reachable by any unprivileged user: simply issue `ComputeBudgetInstruction::set_loaded_accounts_data_size_limit` with a small limit and reference accounts whose true data size far exceeds it. This is confirmed directly by the existing test `fee_only_loaded_transaction_data_size`, which is specifically designed to exercise this exact clamping behavior under `define_ltds_fee_only_semantics` (a real, activatable feature gate), making the condition trivially and repeatably triggerable without any special privileges. [6](#0-5) 

### Recommendation
Preserve and report the true accumulated `loaded_accounts_data_size` in `LoadedTransactionDataSize` regardless of whether the limit was exceeded, rather than clamping the value that feeds fee/cost accounting to the requested limit. If clamping is retained for internal cap enforcement (aborting further loads), the value surfaced to `CostModel`/fee-only paths should reflect the real measured size so that block-cost limits and fee-only charges are not systematically underestimated for transactions that intentionally or accidentally request a low limit while loading much larger account sets.

### Proof of Concept
The existing test `fee_only_loaded_transaction_data_size` in `svm/tests/integration_test.rs` (lines 3624–3770) is itself a proof of concept: it constructs a transaction with `set_loaded_accounts_data_size_limit(size_limit)` where `size_limit = (other_accounts_size / 2).max(1)`, so the real loaded size (`other_accounts_size`) is roughly double the declared limit. The assertion at lines 3743–3752 shows that under `define_ltds_fee_only_semantics`, the reported `loaded_accounts_data_size()` for the failed/fee-only transaction equals `size_limit` (the cap) — not the true `other_accounts_size` that was actually loaded — demonstrating that the excess data size is silently dropped from the value used for fee accounting. [7](#0-6)

#[derive(PartialEq, Eq, Debug, Clone)]
struct LoadedTransactionDataSize {
    loaded_accounts_data_size: u32,
    requested_loaded_accounts_data_size_limit: u32,
}

impl LoadedTransactionDataSize {
    fn with_max_size(requested_loaded_accounts_data_size_limit: u32) -> Self {
        Self {
            loaded_accounts_data_size: 0,
            requested_loaded_accounts_data_size_limit,
        }
    }

    fn increase_calculated_data_size(
        &mut self,
        data_size_delta: usize,
        error_metrics: &mut TransactionErrorMetrics,
    ) -> Result<()> {
        // this branch is unreachable in practice (though not by construction),
        // since it would imply an account >4gb in size
        let Ok(data_size_delta) = u32::try_from(data_size_delta) else {
            self.loaded_accounts_data_size = u32::MAX;
            error_metrics.max_loaded_accounts_data_size_exceeded += 1;
            return Err(TransactionError::MaxLoadedAccountsDataSizeExceeded);
        };

        self.loaded_accounts_data_size = self
            .loaded_accounts_data_size
            .saturating_add(data_size_delta);

        if self.loaded_accounts_data_size > self.requested_loaded_accounts_data_size_limit {
            error_metrics.max_loaded_accounts_data_size_exceeded += 1;
            Err(TransactionError::MaxLoadedAccountsDataSizeExceeded)
        } else {
            Ok(())
        }
    }
}

impl From<LoadedTransactionDataSize> for u32 {
    fn from(value: LoadedTransactionDataSize) -> Self {
        value
            .loaded_accounts_data_size
            .min(value.requested_loaded_accounts_data_size_limit)
    }
}

// Get actual transaction execution costs from transaction commit results
fn get_transaction_costs<'a, Tx: TransactionWithMeta>(
    bank: &Bank,
    commit_results: &[TransactionCommitResult],
    sanitized_transactions: &'a [Tx],
) -> Vec<Option<TransactionCost<'a, Tx>>> {
    assert_eq!(sanitized_transactions.len(), commit_results.len());

    commit_results
        .iter()
        .zip(sanitized_transactions)
        .map(|(commit_result, tx)| {
            if let Ok(committed_tx) = commit_result {
                Some(CostModel::calculate_cost_for_executed_transaction(
                    tx,
                    committed_tx.executed_units,
                    committed_tx.loaded_account_stats.loaded_accounts_data_size,
                    &bank.feature_set,
                ))
            } else {
                None
            }
        })
        .collect()
}
