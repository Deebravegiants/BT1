### Title
Duplicate native-ETH (`address(0)`) entries in `erc20TokenAddresses` let a single `msg.value` satisfy the balance equation multiple times, minting unbacked shielded ETH - (File: contracts/Hinkal.sol)

### Summary
`transact()` in `contracts/Hinkal.sol` never enforces that `circomData.erc20TokenAddresses` contains no duplicate entries. When the native-coin placeholder `address(0)` appears more than once in that array, the ETH-specific branch of the balance-equation check re-adds the same `msg.value` for every occurrence, letting an attacker back two (or more) separate `amountChanges[i]` deposit entries with a single real ETH payment.

### Finding Description
`HinkalHelper.dimensionsCheck` only validates array *lengths* against `dimensions.tokenNumber`; it never checks that `circomData.erc20TokenAddresses` entries are distinct: [1](#0-0) 

In `Hinkal.transact`, balances are captured once for the whole array before and after the internal/external transfer step, and for every index whose token is `address(0)` the code adds `msg.value` back into the diff: [2](#0-1) 

`getBalancesForArray` reads the contract's ETH balance for every `address(0)` entry, so `oldBalances[i]` and `newBalances[i]` are identical across all duplicated `address(0)` indices (there's only one real ETH balance). The deposit-side transfer helper only checks equality, it never "consumes" `msg.value`: [3](#0-2) 

Consequence: if `erc20TokenAddresses = [address(0), address(0)]` with `amountChanges = [X, X]` and `onChainCreation = [false, false]`, and the caller sends `msg.value = X`:
- In `_internalTransact`, for both `i=0` and `i=1`, `deltaAmountChange = X > 0`, so `transferERC20TokenFromOrCheckETH` is called twice, each time only requiring `msg.value == X` — a check that is trivially satisfied twice by the same, unconsumed `msg.value`. [4](#0-3) 
- No actual second ETH transfer occurs (since `_to == address(this)`), so the contract's real balance only ever increases by `X`.
- Back in `transact`, for both `i=0` and `i=1`: `balanceDif = (newBalances[i]-oldBalances[i]) + msg.value = 0 + X = X`, which independently equals `amountChanges[i] + utxoAmount` for **both** indices.

Both balance-equation checks pass even though only `X` ETH was ever received, breaking the core invariant the check is meant to enforce ("change in balance should equal change in off-chain/on-chain UTXOs"), because it silently double-counts a value that was never actually paid twice.

### Impact Explanation
This is a Critical finding: it allows minting shielded value without backing. The attacker can drive two (or more) `amountChanges[i]` deposit legs — each contributing to newly created off-chain/on-chain commitments (`outCommitments`/`onChainCreation`) worth `X` ETH — while only depositing `X` ETH once. The shielded pool ends up crediting `2X` (or more, with more duplicates) in new UTXOs backed by a single real `X` ETH deposit, directly draining the pool's real ETH reserve relative to its accounted shielded liabilities.

### Likelihood Explanation
The attacker only needs to construct `circomData` with a duplicated `address(0)` entry (an unprivileged, ordinary user submitting their own proof/inputs for their own deposit), matching `dimensions.tokenNumber` accordingly, and produce a valid ZK proof for that shape (the circuit is dimensioned per `tokenNumber` and there is no evidence in the accessible Solidity layer that duplicate ERC-20/native addresses within one transaction are rejected). No special privileges, relayer collusion, or admin keys are required — it is entirely constructible by a normal user calling `transact()` directly.

### Recommendation
In `HinkalHelper.dimensionsCheck` (or in `Hinkal.transact` before balance accounting), enforce that all entries of `circomData.erc20TokenAddresses` are unique, rejecting any transaction where the same token address (including `address(0)`) appears more than once. Alternatively, aggregate `amountChanges`/`slippageValues` per unique token address once before computing/comparing `balanceDif`, so `msg.value` (and any ERC-20 balance delta) can only be attributed once per underlying asset, regardless of how many times it appears in the array.

### Proof of Concept
1. Attacker prepares `circomData` for `Hinkal.transact` with:
   - `erc20TokenAddresses = [address(0), address(0)]`
   - `amountChanges = [X, X]`
   - `onChainCreation = [false, false]`
   - Corresponding nullifiers/commitments/slippage values consistent with a valid proof for `dimensions.tokenNumber = 2`.
2. Attacker generates a valid ZK proof for these public inputs (dimension-consistent; nothing in `HinkalHelper.dimensionsCheck` rejects duplicate token addresses).
3. Attacker calls `transact{value: X}(...)`.
4. In `_internalTransact`, both loop iterations (`i=0`, `i=1`) call `transferERC20TokenFromOrCheckETH(address(0), ..., X)`, both succeeding because `msg.value == X` is checked (not decremented) each time. [5](#0-4) 
5. Post-transfer balance check computes `balanceDif = X` for both `i=0` and `i=1`, matching `amountChanges[i] + utxoAmount` for each, so both `require` statements pass. [6](#0-5) 
6. Two full sets of output commitments worth `X` each are inserted into the tree, crediting `2X` of shielded ETH value for a real deposit of only `X`.

    function _internalTransact(CircomData calldata circomData) private {
        bool hasPaidToRelay = false;
        for (uint64 i = 0; i < circomData.erc20TokenAddresses.length; i++) {
            int256 deltaAmountChange = _calculateDeltaAmount(circomData, i);

            if (deltaAmountChange > 0) {
                require(
                    circomData.externalActionData.externalAddress == msg.sender,
                    "Deposit should come from the sender"
                );
                transferERC20TokenFromOrCheckETH(
                    circomData.erc20TokenAddresses[i],
                    circomData.externalActionData.externalAddress,
                    address(this),
                    uint256(circomData.amountChanges[i])
                );
            } else {
                uint256 sumAbs = uint256(-deltaAmountChange);
                uint256 relayFee = 0;
                if (circomData.relay != address(0)) {
                    uint256 flatFee = circomData.feeStructure.feeToken ==
                        circomData.erc20TokenAddresses[i]
                        ? circomData.feeStructure.flatFee
                        : 0;

                    require(
                        sumAbs >= flatFee,
                        "Relay Fee is over withdraw amount"
                    );

                    uint256 recipientAmount = ((10000 -
                        circomData.feeStructure.variableRate) *
                        (sumAbs - flatFee)) / 10000;

                    relayFee = sumAbs - recipientAmount;

                    if (relayFee > 0) {
                        transferERC20TokenOrETH(
                            circomData.erc20TokenAddresses[i],
                            circomData.relay,
                            relayFee
                        );
                    }
                    hasPaidToRelay = true;
                }
                if (sumAbs - relayFee > 0) {
                    transferERC20TokenOrETH(
                        circomData.erc20TokenAddresses[i],
                        circomData.externalActionData.externalAddress,
                        sumAbs - relayFee
                    );
                }
            }
        }
        require(
            circomData.relay == address(0) || hasPaidToRelay,
            "relay not paid"
        );
    }
