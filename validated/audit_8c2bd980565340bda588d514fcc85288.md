### Title
Chainlink circuit-breaker price manipulation in `SimplexPaymaster._getOraclePrice` allows mispriced ERC-20 gas payments - (`evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster` prices ERC-20 gas payments purely from `AggregatorV3Interface.latestRoundData()`, validating only that the answer is positive and not stale. It never checks the answer against the underlying Chainlink aggregator's `minAnswer`/`maxAnswer` circuit-breaker bounds, so a crashing native asset or token price gets clamped at the aggregator's floor instead of reflecting the real market price, letting any bandwidth purchaser (a UserOperation sender) underpay for gas in the registered ERC-20 token.

### Finding Description
`_getOraclePrice` fetches `latestRoundData()` and only guards against non-positive and stale answers: [1](#0-0) 

This price feeds directly into `_tokenPrice`, which is used by `_fetchDetails` — invoked during ERC-4337 `_validatePaymasterUserOp`/`postOp` handling for every submitted UserOperation — to compute how much of the registered ERC-20 (`nativeUsd * tokenDecimals * (1+markup) / tokenUsd`) the sender must pay for gas: [2](#0-1) [3](#0-2) 

Chainlink aggregators enforce internal `minAnswer`/`maxAnswer` circuit breakers; when the true price moves outside that band, `latestRoundData()` keeps returning the clamped boundary value rather than reverting or signaling staleness. Because `_getOraclePrice` treats any positive, fresh answer as valid, a native-asset (or token) price crash below the aggregator's `minAnswer` is silently accepted as the floor price. This is reachable by any unprivileged UserOperation sender — no special privilege is required to trigger `_fetchDetails`/`_tokenPrice` — since gas-payment pricing runs on every incoming paymaster-sponsored UserOperation.

The same unchecked price also feeds `swapAndDeposit`'s `amountOutMin` calculation used when swapping accrued ERC-20 fees for native gas via the router, so a clamped price additionally distorts the treasury's fee-recycling swap execution price: [4](#0-3) 

### Impact Explanation
If the native asset (e.g., BNB, ETH) price crashes far below the Chainlink aggregator's `minAnswer` floor while the token (e.g., a stablecoin) oracle remains accurate, `_tokenPrice` computes an inflated `nativeUsd`, causing UserOperation senders to overpay in the ERC-20 token relative to the actual gas cost — or, in the token-price-crash direction, causes senders to significantly underpay, letting the paymaster's ERC-20 balance be drained relative to the native gas it actually spent from the EntryPoint deposit. Because the paymaster sponsors gas from its own EntryPoint deposit and is only reimbursed via the mispriced ERC-20 charge, a sustained divergence directly transfers value from the paymaster's treasury to UserOperation senders, or vice versa — a concrete funds-loss condition reachable from an ordinary token/gas-payment path.

### Likelihood Explanation
This requires only that one of the configured Chainlink feeds' underlying asset price move outside that specific aggregator's `minAnswer`/`maxAnswer` band — a real, historically observed event (e.g., LUNA/BSC precedent cited in the source report) — combined with any user submitting a UserOperation through the paymaster during that window. No governance or relayer collusion is needed; the mispricing is automatic and silent because `_getOraclePrice` has no bounds check, only staleness/positivity checks.

### Recommendation
Extend `_getOraclePrice` to fetch each configured aggregator's `minAnswer`/`maxAnswer` (via `AggregatorV2V3Interface`/proxy `aggregator()` + `minAnswer()`/`maxAnswer()`, or governance-configured bounds stored alongside `TokenConfig`) and revert (or fail over to a secondary source) when `answer <= minAnswer || answer >= maxAnswer`, mirroring the staleness/positivity checks already present at [5](#0-4) .

### Proof of Concept
1. Governance registers a token with a Chainlink `nativeOracle` whose underlying aggregator has `minAnswer = $X`.
2. The native asset's real market price crashes to well below `$X` (e.g., a LUNA-style event); the aggregator's `latestRoundData()` continues returning `answer = minAnswer` with a fresh `updatedAt`.
3. `_getOraclePrice` accepts this answer since it is positive and not stale (`evm/src/utils/SimplexPaymaster.sol:662-676`).
4. Any user submits a UserOperation with `paymasterData` mode `0x00`/`0x02` naming a registered token; `_fetchDetails`/`_tokenPrice` compute `tokenPrice` using the stale-but-valid clamped `nativeUsd`, overcharging or undercharging the ERC-20 amount relative to the true native gas cost (`evm/src/utils/SimplexPaymaster.sol:524-546, 653-658`), draining paymaster value over repeated operations while the price band is being violated.

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
