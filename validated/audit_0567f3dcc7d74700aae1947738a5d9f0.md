**Rationale:**

The scenario requires forging a JMT root hash collision, not exploiting a logic flaw. `ensure_transaction_infos_match` performs a byte-for-byte equality check between the locally re-computed `TransactionInfo` (built from the node's own honest execution) and the claimed `TransactionInfo` supplied by the peer/chunk. [1](#0-0)  This isn't a "merkle root only" comparison — the compared struct also embeds `state_change_hash`, which is a direct hash of the transaction's write set (not routed through any tree), computed by the executor from the transactions it actually applied. [2](#0-1) 

For the described attack to succeed, a malicious chunk would need to simultaneously:
1. Produce a different `FungibleStore` leaf value (wrong balance) while keeping the JMT `state_checkpoint_hash` (a SHA3-256-based merkle root) identical to the honest root — i.e., a second-preimage/collision on the state tree.
2. Also produce a colliding `write_set_hash`/`state_change_hash` for a different write set, since that hash is checked independently of the merkle tree in `ensure_match_transaction_info`. [3](#0-2) 

Both are infeasible under standard cryptographic assumptions (SHA3-256 collision resistance), not logic gaps in this file.

Additionally, the "expected" side of the chunk comparison is not the crafted input — it is derived from the node's own independent re-execution and previously accumulator-proof-verified data. `verify_chunk_result` first verifies the supplied `transaction_infos` extend the parent accumulator via `verify_extends_ledger` (itself checked against the target ledger info, which is authenticated by validator BLS signatures elsewhere), and only then diffs them against the locally computed `ledger_update_output`. [4](#0-3)  So a crafted balance delta doesn't just need to survive one hash-root comparison in this file — it needs to simultaneously fool the local re-execution result, the independent write-set hash check, the JMT inclusion structure, and the validator-signed ledger info, none of which are bypassed by this file alone.

Since exploiting this requires breaking a collision-resistant hash function (and/or forging validator signatures) rather than exploiting an actual logic/authorization gap reachable from unprivileged input, it does not meet the custody-impact bar for this review.

    pub fn ensure_transaction_infos_match(
        &self,
        transaction_infos: &[TransactionInfo],
    ) -> Result<()> {
        ensure!(
            self.transaction_infos.len() == transaction_infos.len(),
            "Lengths don't match. {} vs {}",
            self.transaction_infos.len(),
            transaction_infos.len(),
        );

        let mut version = self.first_version();
        for (txn_info, expected_txn_info) in
            zip_eq(self.transaction_infos.iter(), transaction_infos.iter())
        {
            ensure!(
                txn_info == expected_txn_info,
                "Transaction infos don't match. version:{version}, txn_info:{txn_info}, expected_txn_info:{expected_txn_info}",
            );
            version += 1;
        }
        Ok(())
    }
