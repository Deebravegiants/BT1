Audit Report

## Title
Gateway HTTP Action response cache key omits `WorkflowID`, causing cross-workflow response (including headers) sharing for same-owner workflows - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

## Summary
The Gateway's HTTP Action v2 response cache keys entries solely by `req.Hash()`, which per the test suite and code excludes `WorkflowID` from the hash computation while including `WorkflowOwner`. This directly contradicts the component's own documented guarantee that "Cache entries are scoped by workflow ID to prevent cross-workflow data leakage," and allows two distinct workflows under the same owner to receive each other's cached HTTP responses (including headers such as `Set-Cookie`/auth tokens) when they issue identical outbound requests with caching enabled.

## Finding Description
`responseCache.Fetch` and `responseCache.Set` use `req.Hash()` as the sole cache map key [1](#0-0) [2](#0-1) . The package comment itself states the hash is composed of "method, URL, headers, body, workflowOwner" — notably omitting `WorkflowID` [3](#0-2) .

This is confirmed by the test suite, which explicitly asserts that identical requests differing only in `WorkflowID` produce the *same* hash, while differing `WorkflowOwner` produces a different hash [4](#0-3) .

This behavior directly contradicts the documented contract in the package's own README: "Cache Key: Generated from workflow ID and request hash" and "Workflow Isolation: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage" [5](#0-4) .

The cached value is the full `OutboundHTTPResponse` struct, which includes `Headers`/`MultiHeaders` (potentially containing `Set-Cookie`, bearer tokens, etc.) as populated from the actual external endpoint response in `createHTTPRequestCallback` [6](#0-5) . The caching path is driven from `makeOutgoingRequest`, which calls `Fetch`/`Set` keyed only by the request hash whenever `CacheSettings.MaxAgeMs > 0` or `CacheSettings.Store` is true [7](#0-6) .

No existing check (rate limiting, auth, or the cache logic itself) re-validates or partitions by `WorkflowID`; the isolation is asserted only in documentation, not enforced in code.

## Impact Explanation
Any workflow owner operating (or controlling) multiple distinct workflows can cause one workflow's cached HTTP response — including any session cookies, CSRF tokens, or per-request authorization artifacts returned by an external endpoint — to be served to a second, different workflow (different `WorkflowID`) under the same owner, provided both issue byte-identical outbound HTTP requests (method/URL/headers/body) with caching enabled via the public `CacheSettings` field. This is a cross-workflow information disclosure / cache-poisoning primitive that breaks the explicitly documented workflow-isolation guarantee of the gateway's shared in-memory response cache. This maps to the in-scope "cross-user response corruption" impact category for the gateway.

## Likelihood Explanation
Exploitation requires only: (1) one owner deploying two workflows (a normal, unprivileged, common scenario — no special role or credential beyond normal workflow deployment), and (2) both workflows making identical HTTP Action requests with `CacheSettings.Store`/`MaxAgeMs` set, which is standard, documented, unprivileged capability configuration exposed through the HTTP Action's public request schema. No malicious node, gateway operator, or network-layer compromise is needed. The behavior is deterministic and repeatable, as directly demonstrated by the existing `TestRequestHash` unit test in the repository.

## Recommendation
Include `WorkflowID` in the cache key computation (`OutboundHTTPRequest.Hash()`) so cache entries are truly scoped per-workflow as documented, not merely per-owner. Additionally, evaluate whether headers carrying session/authorization material (e.g., `Set-Cookie`, `Authorization`) should be excluded from cached response storage entirely, or the caching feature should be restricted to idempotent, non-session-bearing endpoints.

## Proof of Concept
1. Run the existing test `TestRequestHash`/subtest "having different workflowID results in same Hash" in `core/services/gateway/handlers/capabilities/v2/response_cache_test.go`, which already demonstrates that two `OutboundHTTPRequest` values differing only by `WorkflowID` hash identically.
2. Integration-level PoC: Workflow A (`WorkflowOwner=0xOwner`, `WorkflowID=A`) issues `GET https://api.example.com/session` with `CacheSettings{Store:true, MaxAgeMs:600000}`; the gateway caches the response (including `Set-Cookie`) keyed by `req.Hash()`.
3. Workflow B (`WorkflowOwner=0xOwner`, `WorkflowID=B`) issues the identical request with `CacheSettings.MaxAgeMs>0`; because `Hash()` ignores `WorkflowID`, `responseCache.Fetch` returns Workflow A's cached response (including its `Set-Cookie`/session header) to Workflow B.
