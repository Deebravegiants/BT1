### Title
Unbounded cycle traversal in `AncestryChain::ancestry` allows a relayed GRANDPA finality proof to hang the verifier in an infinite loop - ([File: modules/consensus/grandpa/primitives/src/justification.rs])

### Summary
The bug class in CVE-2018-11507 is a long/unbounded loop driven entirely by attacker-supplied data during parsing/traversal, with no bound on iterations. The GRANDPA consensus client's `AncestryChain::ancestry` walk over relayer-supplied `unknown_headers`/`votes_ancestries` has the same defect: it walks parent-hash pointers with no cycle detection and no iteration cap, and every node in the walk is drawn from a `BTreeMap` built directly from attacker-controlled header data.

### Finding Description
`AncestryChain::ancestry` in `modules/consensus/grandpa/primitives/src/justification.rs`: [1](#0-0) 

walks backward from `block` to `base` by repeatedly looking up `current_header.parent_hash()` in a map built from the relayer-supplied header list (`AncestryChain::new`, lines 161-167). There is no visited-set / cycle check and no maximum iteration count. Because header hashes are computed over attacker-chosen content, and `parent_hash` is just a plain field inside that content, an attacker can construct a small set of headers whose `parent_hash` fields point to each other in a cycle (H1.parent_hash = hash(H2), H2.parent_hash = hash(H1), etc.) without needing to invert any hash function — they simply pick the field value freely and compute the hash afterward. If none of the cycle members equals `base`, the `while current_hash != base` loop in `ancestry` will loop forever, since `self.ancestry.get(&current_hash)` always succeeds for every hash in the cycle.

This function is called from two attacker-reachable consensus-verification paths:
- `GrandpaJustification::verify_with_voter_set`, which builds `AncestryChain` from `self.votes_ancestries` (fully relayer-supplied) and calls `ancestry(base_hash, signed.precommit.target_hash)` for each precommit: [2](#0-1) 
- `verify_grandpa_finality_proof`, which builds `AncestryChain` from `finality_proof.unknown_headers` (also relayer-supplied) and calls `headers.ancestry(from, target.hash())`: [3](#0-2) 

Both entry points are exercised by the ISMP GRANDPA consensus client's `verify_consensus`/fraud-proof handling, which is invoked from a permissionless, unsigned consensus-message dispatch — i.e., any relayer can submit a crafted `ConsensusMessage`/`FinalityProof` containing a header cycle, matching the report's requirement of "a single relayed proof" reaching a core consensus-verification path.

### Impact Explanation
An infinite loop inside consensus proof verification, executed during extrinsic/runtime dispatch, blocks the executing thread indefinitely with no weight-metering escape (Substrate's weight system is a pre-declared cost estimate, not an instruction-level watchdog for unbounded native loops). This can hang the collator/validator process processing the extrinsic, effectively halting block production for the chain that hosts the GRANDPA light client — a route that becomes permanently unable to deliver/verify further consensus updates and, by extension, unable to deliver ISMP messages relying on that consensus client. This matches "a route unable to deliver messages" / denial of service of a core dispatch path.

### Likelihood Explanation
Any unprivileged relayer can submit a consensus update; constructing a header cycle requires no cryptographic break, only picking header field values and computing their own hashes, which is trivial. The only requirement is that the crafted headers pass whatever cheap pre-checks exist before the ancestry walk (e.g., min/max-by-number selection of `base`/`target`), which do not defend against cycles among the remaining headers. This makes the likelihood high given a determined submitter.

### Recommendation
Add cycle protection and a hard iteration bound to `AncestryChain::ancestry`: track visited hashes in a set and abort with `Error::NotDescendent` (or a new "cycle detected" error) once a hash repeats, and additionally cap the walk length to `votes_ancestries.len()` / `unknown_headers.len()` (the walk can never legitimately need more steps than there are supplied headers). Apply the same defensive bound anywhere else `parent_hash`-following traversals are done over relayer-supplied header sets.

### Proof of Concept
1. Craft two headers `H1`, `H2` (or more) where `H1.parent_hash = H2.hash()` and `H2.parent_hash = H1.hash()`, satisfying any lightweight shape checks (e.g., they can still be included in `unknown_headers`/`votes_ancestries`).
2. Ensure `H2.hash()` (or the chosen `block` argument) is not equal to trusted `base`/`from`.
3. Submit this pair as part of a `FinalityProof`/`GrandpaJustification` via the relayer's permissionless consensus-update extrinsic.
4. `verify_grandpa_finality_proof` (or `GrandpaJustification::verify`) calls `AncestryChain::ancestry(base, block)`, which enters the `H1 <-> H2` cycle and never reaches `base`, looping forever and hanging the executing node.

Note: I was unable to fully verify the exact upstream dispatch call-site (`pallet-ismp` handler that ultimately invokes `verify_consensus`) or whether any length/shape pre-check on `unknown_headers`/`votes_ancestries` exists elsewhere in the pipeline that could block this specific cycle shape, due to index/context limits on further file reads in this session. If such a check exists (e.g., strict ancestor-chain-only header sets with no duplicate/cyclic hashes enforced earlier), it would need to be confirmed against `modules/ismp/clients/grandpa/src/consensus.rs` and `tesseract/consensus/grandpa/src/lib.rs` before treating this as fully exploitable end-to-end.

impl<H: HeaderT> finality_grandpa::Chain<H::Hash, H::Number> for AncestryChain<H>
where
	H::Number: finality_grandpa::BlockNumberOps,
{
	fn ancestry(
		&self,
		base: H::Hash,
		block: H::Hash,
	) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
		let mut route = vec![block];
		let mut current_hash = block;
		while current_hash != base {
			match self.ancestry.get(&current_hash) {
				Some(current_header) => {
					current_hash = *current_header.parent_hash();
					route.push(current_hash);
				},
				_ => return Err(finality_grandpa::Error::NotDescendent),
			};
		}
		Ok(route)
	}

	mut consensus_state: ConsensusState,
	finality_proof: FinalityProof<H>,
) -> Result<(ConsensusState, H, Vec<H256>, AncestryChain<H>), Error>
where
	H: Header<Hash = H256, Number = u32>,
	H::Number: finality_grandpa::BlockNumberOps + Into<u32>,
{
	// First validate unknown headers.
	let headers = AncestryChain::<H>::new(&finality_proof.unknown_headers);

	let target = finality_proof
		.unknown_headers
		.iter()
		.max_by_key(|h| *h.number())
		.ok_or(Error::UnknownHeadersEmpty)?;

	// this is illegal
	if target.hash() != finality_proof.block {
		Err(Error::LatestBlockMismatch)?;
	}

	let justification =
		GrandpaJustification::<H>::decode_all(&mut &finality_proof.justification[..])
			.map_err(|e| Error::DecodeJustification(alloc::format!("{e:?}")))?;

	if justification.commit.target_hash != finality_proof.block {
		Err(Error::JustificationTargetMismatch)?;
	}

	let from = consensus_state.latest_hash;

	let base = finality_proof
		.unknown_headers
		.iter()
		.min_by_key(|h| *h.number())
		.ok_or(Error::UnknownHeadersEmpty)?;

	if base.number() < &consensus_state.latest_height {
		headers
			.ancestry(base.hash(), consensus_state.latest_hash)
			.map_err(|_| Error::InvalidAncestry)?;
	}

	let finalized = headers.ancestry(from, target.hash()).map_err(|_| Error::InvalidAncestry)?;
