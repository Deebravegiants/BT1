Audit Report

## Title
Web-API trigger fires the same workflow multiple times per request when multiple attacker-supplied topics match one workflow's allowlist - ([File: core/capabilities/webapi/trigger/trigger.go])

## Summary
`processTrigger` in `core/capabilities/webapi/trigger/trigger.go` iterates every registered trigger and every attacker-supplied topic in `payload.Topics`; whenever a topic matches `trigger.allowedTopics`, it sends a `TriggerResponse` on `trigger.ch`. The `break` intended to stop further sends for that trigger is nested inside a `select` statement, so it only exits the `select`, not the topic loop, allowing a single request with multiple matching topics to emit multiple identical-`TriggerEventID` `TriggerResponse`s to the same workflow.

## Finding Description
`processTrigger` loops `for _, trigger := range triggers { for _, topic := range topics { if trigger.allowedTopics[topic] { ... trigger.ch <- tr ... } } }` (lines 106-155). The comment at line 151 claims a topic match can "only be triggered once," relying on `break` at line 152, but that `break` is scoped to the `select` block (lines 145-153), not the `for _, topic := range topics` loop — a well-known Go `break`-scoping pitfall. If `payload.Topics` contains N topics that are all present in the same workflow's `allowedTopics` map, the send at line 149 executes N times for that one trigger. The `TriggerEventID` computed at line 120 (`body.Sender + payload.TriggerEventId`) does not depend on `topic`, so all N sends carry the identical execution identity but are delivered as N separate `capabilities.TriggerResponse` values, causing the workflow engine to start N executions for what `TriggerEventId` was meant to uniquely identify as one event. `Topics` is decoded directly from attacker-supplied gateway request JSON with no uniqueness constraint beyond non-empty, and the only gating checks (`allowedSenders`, rate limiter) are evaluated per-topic-match, not once per trigger, so they do not prevent the duplication.

## Impact Explanation
An already-`allowedSenders`-authorized but otherwise unprivileged caller of the Web API trigger gateway endpoint can multiply the number of workflow executions triggered by a single logical event by including several topics from the same workflow's `allowedTopics` in one request. Since workflows can perform side-effecting actions (on-chain writes, external calls), this causes duplicate/unauthorized job runs from what should be a single triggering event, violating the once-per-`TriggerEventId` semantics the code itself documents as intended.

## Likelihood Explanation
Exploitation requires only being a routine sender already listed in a workflow's `allowedSenders` (a standard, unprivileged precondition for using the Web API trigger at all) and knowledge of that workflow's configured `allowedTopics` list. No race condition, timing dependency, or elevated privilege is needed — a single crafted request suffices, and it is fully repeatable.

## Recommendation
Use a labeled break (e.g., `matchLoop: for _, topic := range topics { ... select { case trigger.ch <- tr: break matchLoop } }`) or a boolean flag checked after the inner loop to ensure at most one `TriggerResponse` is sent per trigger per request regardless of how many of its topics matched.

## Proof of Concept
1. Register a trigger via `RegisterTrigger` with `AllowedTopics = ["topic_a", "topic_b"]` and `AllowedSenders` containing the test sender's address.
2. Call `processTrigger` (or send the equivalent gateway `web_api_trigger` JSON-RPC message) with `payload.Topics = ["topic_a", "topic_b"]` and a single `TriggerEventId`.
3. Observe that `trigger.ch` receives two `capabilities.TriggerResponse` values, both with the same `Event.ID` (`TriggerEventID`), confirming duplicate delivery from one request — this can be asserted directly in a Go unit test against `processTrigger` by reading twice from the returned channel.
