### Title
`deserialize` performs case-sensitive matching of `HttpOnly`/`Secure` cookie attribute names, silently dropping these flags on round-trip - (File: modules/networking-common/src/cookie/deserialize.ts)

### Summary
`deserialize` in `modules/networking-common/src/cookie/deserialize.ts` matches cookie attribute names (`HttpOnly`, `Secure`, `Max-Age`, `Expires`) via an exact-string `Map` lookup, but RFC 6265 requires cookie attribute names to be treated case-insensitively. Any `Set-Cookie` string using a differently-cased attribute name (e.g. `httponly`, `SECURE`, `HTTPONLY`) is not recognized by `FACTORIES.get(key)` and is instead stored as an arbitrary extension property, causing `serialize(deserialize(x))` to permanently drop the `HttpOnly`/`Secure` flag.

### Finding Description
`deserialize` builds a lookup table `FACTORIES` keyed by the exact strings `'Max-Age'`, `'HttpOnly'`, `'Expires'`, `'Secure'` [1](#0-0) . When parsing each `key=value` pair from the cookie string, it does `FACTORIES.get(key)` with the raw, unmodified case of the parsed key [2](#0-1) . If the attacker/server sends the attribute in any case other than the exact capitalization hard-coded in `FACTORIES` (e.g. `httponly` or `SECURE`, both of which are valid per RFC 6265 since attribute-name matching there is explicitly case-insensitive), the lookup fails, and the code falls through to the generic branch `cookie[toFirstLower(key)] = value`, storing it under the literal (lowercased-first-letter) attribute name instead of the canonical `httpOnly`/`secure` fields.

Consequently, `cookie.httpOnly` / `cookie.secure` remain `undefined` even though the source string declared the flag. When this `Cookie` object is later fed into `serialize` (`modules/networking-common/src/cookie/serialize.ts`), the boolean-flag branch never emits `HttpOnly`/`Secure` because the corresponding key is either absent or has an `undefined` value, which `serializeProp` explicitly drops [3](#0-2) . The round-trip `serialize(deserialize(x))` therefore silently strips the security-relevant flag for any RFC6265-valid but non-canonically-cased input, unlike the vendored `deserialize.spec.ts`, which only exercises the canonical casing (`HttpOnly`, `Secure`) and would not catch this [4](#0-3) .

No case-normalization step exists anywhere between the parsed `key` and the `FACTORIES.get(key)` lookup, and `validators.ts` performs only name/value/domain checks, not attribute-name normalization, so nothing else in the pipeline compensates for this [5](#0-4) .

### Impact Explanation
If this `serialize`/`deserialize` pair is used anywhere the wallet re-persists or re-emits a previously parsed `Set-Cookie` string (e.g., a caching/migration layer built on `networking-common`), an attacker-controlled or network-observed cookie string using non-canonical attribute casing will have its `HttpOnly`/`Secure` protection permanently stripped after the round-trip. A cookie re-emitted without `Secure` could be transmitted over plaintext HTTP by a subsequent consumer, and a cookie re-emitted without `HttpOnly` could become accessible to script-based cookie theft (e.g. via injected JS in a webview), both weakening session-cookie confidentiality/integrity against a network or script-based attacker. This matches a STORAGE_INTEGRITY class issue: silent loss of a protective attribute during serialization round-trip.

### Likelihood Explanation
The trigger requires only that a `Set-Cookie` value use non-canonical casing for `HttpOnly`/`Secure`/`Max-Age`/`Expires` (e.g. `httponly`, `secure`, `max-age`), all of which are valid and fairly common in real server responses (many servers/lowercase-by-convention emit lowercase attribute names). This is fully attacker/server-controlled and deterministic — no privileged state or social engineering is needed, only a response containing a cookie header with alternate casing. However, I could not confirm from the indexed code that `serialize`/`deserialize` (as opposed to native `CookieManager.setFromResponse` used directly with the raw string, as seen in `networking-mobile/src/cookie/cookie-jar.ts`) are actually chained together anywhere in the current codebase — the only usages found are re-exports in `modules/networking-common/src/cookie/index.ts` and the module's own spec files. This limits certainty about real-world reachability/exploitability of the round-trip in production code paths, though the mobile `CookieJar.set` does call `validate()` and native `set`/`get` on `Cookie` objects that could originate from a `deserialize` call elsewhere in the wallet not covered by the indexed search.

### Recommendation
Normalize the parsed attribute `key` (e.g., lowercase it) before the `FACTORIES.get(key)` lookup in `deserialize.ts`, and correspondingly key `FACTORIES` by lowercase names, to make attribute matching RFC6265-compliant and case-insensitive. Add property-based/differential tests asserting `deserialize(serialize(c))` and `serialize(deserialize(x))` preserve `httpOnly`/`secure` for all valid casings of the attribute names.

### Proof of Concept
```ts
import serialize from './serialize'
import deserialize from './deserialize'

it('preserves HttpOnly/Secure regardless of attribute casing (RFC6265 case-insensitivity)', () => {
  const original = 'session=abc123; httponly; secure'
  const cookie = deserialize(original)

  // Expected per RFC6265: attribute names are case-insensitive
  expect(cookie.httpOnly).toBe(true)
  expect(cookie.secure).toBe(true)

  const roundTripped = serialize(cookie)
  expect(roundTripped).toContain('HttpOnly')
  expect(roundTripped).toContain('Secure')
})
```
Expected current (buggy) behavior: `cookie.httpOnly`/`cookie.secure` are `undefined`, and `roundTripped` omits `HttpOnly`/`Secure` entirely, demonstrating the silent loss of the protective flags.
