### Title
Unbounded scaled-balance growth overflows accrual math and permanently freezes a market — no withdraw, repay, or liquidation - (File: common/src/rates/scaling.rs)

### Summary
Analogous to CVE-2017-9022 (unvalidated input reaching an arithmetic primitive that crashes the process), the pool accrues interest by calling `scaled_to_original` on `borrowed`/`supplied` without validating that the resulting RAY-denominated value fits in `i128`. Because every mutating verb runs `interest::global_sync` first, once a market's scaled value crosses the `i128::MAX` ceiling the accrual panics with `MathOverflow` on every subsequent call, permanently freezing the market. An unprivileged user can push a market to this state via ordinary `supply`/`borrow` on a high-decimals, steep-curve asset.

### Finding Description
`interest::global_sync` (`contracts/pool/src/interest.rs:20-33`) is executed before every market mutation, and each chunk calls `accrue_step` (`common/src/rates/simulate.rs:51-78`), which evaluates:

```rust
let borrowed_original = scaled_to_original(env, borrowed, borrow_index);
let supplied_original = scaled_to_original(env, supplied, supply_index);
```

`scaled_to_original` (`common/src/rates/scaling.rs:14-16`) is `scaled.mul(env, index)` — a RAY-scaled multiply that panics with `MathOverflow` when `shares × index` exceeds `i128::MAX`. There is no guard that caps `supplied`/`borrowed` so that `shares × index ≤ i128::MAX`; the index caps (`MAX_BORROW_INDEX_RAY`, `MAX_SUPPLY_INDEX_RAY` = 1e36) engage only on the *index*, not on the scaled *value*. The harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361`) demonstrates exactly this: a market with ~`1e36` raw-ray shares (1 billion tokens at 18 decimals) at ~98% utilization on the steep XLM curve grows the borrow index past ~170×, the next accrual panics inside `scaled_to_original`, and every later `update_indexes`, `withdraw`, and `repay` reverts with `MathOverflow` — the index cap never engages. The test also notes the documented bound in `docs/reference/formulas.md` is wrong, so this is not a documented ADR choice.

Like the CVE, the defect is a missing domain check on inputs fed into a math primitive; unlike a transient revert, the panic is *sticky* — it fires inside `global_sync`, which precedes all state mutation, so the revert cannot be bypassed by any unprivileged entrypoint (`supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, `flash_loan`, `update_indexes` all accrue first). `recapitalize` also accrues, so even the designed recovery path is blocked.

### Impact Explanation
Permanent freezing of all user funds in the affected market: suppliers cannot withdraw, borrowers cannot repay, liquidators cannot liquidate, and the market cannot be resuscitated because every path — including `recapitalize` — reverts in `global_sync` before touching state. This satisfies "permanent freezing of funds" / "contract unable to operate".

### Likelihood Explanation
Reachable by a single unprivileged address via `supply` + `borrow`; no governance, oracle, or admin action required. The barrier is economic: it needs a very large principal (order 10^27 raw units — feasible on high-decimal or low-price tokens) and sustained high utilization over enough compounding windows for the index to multiply the scaled balance past `i128::MAX`, or a smaller principal combined with bad-debt/index dynamics. The minted-supply caps (`calculate_scaled_cap`) saturate rather than bound the ceiling, and `lift_caps`-style governance raising of caps is a normal configuration. Given the capital and time requirements, this is Medium.

### Recommendation
Cap scaled balances so that `supplied × supply_index` and `borrowed × borrow_index` provably stay below `i128::MAX` — e.g., enforce a maximum scaled-share total per market in `supply`/`borrow`/revenue minting (a "value ceiling" alongside the index caps), or make `global_sync` clamp accrual (saturate the index at the point where scaled values overflow) instead of panicking, so exits remain possible even if further interest cannot accrue.

### Proof of Concept
The repository's own regression test reproduces it:

```rust
// tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321
let principal = BILLION * 10i128.pow(18);        // 1e27 whole tokens @ 18 decimals
t.supply_raw(BOB, "BIG18", principal);           // unprivileged supply
let debt = principal / 100 * 98;                 // 98% utilization
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);              // unprivileged borrow

loop {
    t.advance_time(YEAR_SECS);
    if let Err(e) = t.try_update_indexes_for(&["BIG18"]) { break e; } // MathOverflow
}
// Afterwards, all of these revert with MathOverflow (34):
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

Once `borrowed × borrow_index` (or `supplied × supply_index`) exceeds `i128::MAX`, `accrue_step`'s `scaled_to_original` panics on every call, permanently freezing the market before the `MAX_BORROW_INDEX_RAY` cap can engage.
