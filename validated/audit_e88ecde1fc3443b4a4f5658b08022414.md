## Finding: Missing para-lifecycle check in on-demand order placement

<title>
Missing ParaLifecycle validation in `do_place_order`/`pop_assignment_for_cores` allows resource seizure of on-demand core assignments by non-live paras - (File: polkadot/runtime/parachains/src/on_demand/mod.rs)
</title>

### Summary
`Pallet::<T>::do_place_order` and `Pallet::<T>::pop_assignment_for_cores` in the on-demand pallet perform no `ParaLifecycle` check on the target `para_id`. An unprivileged signed account can place (and pay for) on-demand orders for a `para_id` that is still `Onboarding` (reserved+registered but not yet a live `Parathread`), and the scheduler's coretime assigner will still pop and assign a pool core to that `para_id` each eligible block, wasting core-assignment slots that could have served a live, functioning parathread.

### Finding Description
`do_place_order` (`polkadot/runtime/parachains/src/on_demand/mod.rs:471-558`) only validates the spot price and queue capacity before charging the sender and pushing `para_id` into the order queue: [1](#0-0) 
There is no call to `paras::Pallet::<T>::is_parathread(para_id)` or any `ParaLifecycle` check anywhere in this function, nor in the public extrinsics `place_order_allow_death`/`place_order_keep_alive`/`place_order_with_credits` that call it: [2](#0-1) 

Downstream, `pop_assignment_for_cores` simply pops entries from the queue based on position/affinity, with no lifecycle filtering: [3](#0-2) 

The scheduler's coretime assigner (`assigner_coretime/mod.rs`) forwards pool-core requests unconditionally to this same function via `AccessMode::pop_assignment_for_ondemand_cores`, again without any lifecycle gate: [4](#0-3) 
and `advance_assignments_single_impl` calls this for every pool core each block: [5](#0-4) 

`ParaLifecycle` explicitly models the ~2-session `Onboarding` delay before a para becomes a stable `Parathread`/`Parachain`, and exposes `is_parathread()`/`is_stable()` helpers precisely for this purpose: [6](#0-5) 
None of these helpers are consulted anywhere in the on-demand order-placement or core-popping path. Existing tests for `place_order_*` and `pop_assignment_for_cores_works` always advance blocks until `Paras::is_parathread(para_id)` becomes true before placing orders, which is consistent with an implicit (but unenforced) assumption that orders are only placed for live paras — this assumption is never checked in the actual pallet code: [7](#0-6) 

An attacker only needs `reserve` + `register` (both unprivileged/user-payable actions elsewhere in the registrar) to obtain a valid, existing `ParaId` in `Onboarding` state, and can then immediately call `place_order_allow_death`/`place_order_with_credits` for that `para_id`. The order is accepted, fees are charged, and the queue entry is created. When `pop_assignment_for_cores`/`advance_assignments` runs for a pool core, this `para_id` is a normal, eligible candidate for assignment — it consumes an assignment slot for that scheduling round even though it can never produce a validly-backed candidate (no PVF/validation code is live yet), because `check_descriptor_version_and_signals`/`sanitize_backed_candidates` in `paras_inherent` would reject any actual candidate for a non-onboarded para at the backing stage, not at the scheduling/assignment stage.

### Impact Explanation
Because the on-demand queue enforces "only one order per `ParaId` assigned per scheduling round" but performs no liveness check, an attacker can repeatedly queue orders for their own `Onboarding` para and cause the coretime assigner to hand it a pool-core assignment slot each eligible round. That slot is guaranteed to go unused for the round (no valid candidate can ever be backed for a non-live para), starving legitimate, already-live parathreads of that pool-core capacity for the duration of the attack — concretely a resource-seizure DoS against the shared on-demand/pool core assignment queue, bounded by the ~2-session onboarding window but real for that period.

### Likelihood Explanation
Fully unprivileged and trivially repeatable: reserve a `ParaId`, register it (both standard user-payable registrar operations), then immediately call `place_order_allow_death`/`place_order_with_credits` before the para completes onboarding. No special origin, proxy, or governance action is required, and the attack can be repeated every block while the queue has room and the attacker is willing to pay the spot price (spot price grows with traffic, providing only an economic — not a protocol-level — disincentive).

### Recommendation
Add a `ParaLifecycle` check (e.g. `ensure!(paras::Pallet::<T>::is_parathread(para_id) || paras::Pallet::<T>::is_parachain(para_id), Error::<T>::...)`, or more precisely `is_stable()`) in `do_place_order` before charging the sender and pushing to the queue, and/or filter `pop_assignment_for_cores` results by current para lifecycle before finalizing a core assignment, returning unspent/unassignable orders to a state that doesn't consume a core slot.

### Proof of Concept
Rust unit test in `polkadot/runtime/parachains/src/on_demand/tests.rs`:
1. Reserve/register a `para_id` (e.g. via `schedule_blank_para` but do NOT run to the block where `Paras::is_parathread(para_id)` becomes true — assert it remains in `Onboarding`/`!is_parathread`).
2. Fund an account and call `OnDemand::place_order_allow_death(RuntimeOrigin::signed(alice), amt, para_id)`.
3. Assert (current behavior, demonstrating the bug) that this call succeeds (`assert_ok!`) despite `!Paras::is_parathread(para_id)`.
4. Advance blocks and call `OnDemand::pop_assignment_for_cores(block_num, 1)`, asserting it yields `Some(para_id)` even though the para is still `Onboarding`.
5. Expected fixed behavior: step 2 should fail with a new lifecycle-related error, or step 4 should filter out `para_id` and return `None`/skip it.

pub enum ParaLifecycle {
	/// Para is new and is onboarding as an on-demand or lease holding Parachain.
	Onboarding,
	/// Para is a Parathread (on-demand parachain).
	Parathread,
	/// Para is a lease holding Parachain.
	Parachain,
	/// Para is a Parathread (on-demand parachain) which is upgrading to a lease holding Parachain.
	UpgradingParathread,
	/// Para is a lease holding Parachain which is downgrading to an on-demand parachain.
	DowngradingParachain,
	/// Parathread (on-demand parachain) is queued to be offboarded.
	OffboardingParathread,
	/// Parachain is queued to be offboarded.
	OffboardingParachain,
}

impl ParaLifecycle {
	/// Returns true if parachain is currently onboarding. To learn if the
	/// parachain is onboarding as a lease holding or on-demand parachain, look at the
	/// `UpcomingGenesis` storage item.
	pub fn is_onboarding(&self) -> bool {
		matches!(self, ParaLifecycle::Onboarding)
	}

	/// Returns true if para is in a stable state, i.e. it is currently
	/// a lease holding or on-demand parachain, and not in any transition state.
	pub fn is_stable(&self) -> bool {
		matches!(self, ParaLifecycle::Parathread | ParaLifecycle::Parachain)
	}
