The `internal_withdraw` function in `staking-pool/src/internal.rs` deducts the user's `unstaked` balance and `last_total_balance` synchronously, then fires off `Promise::new(account_id).transfer(amount)` without attaching any `.then()` callback to verify success.

### Title
Failed NEAR transfer in `StakingContract::internal_withdraw` permanently debits the delegator's balance with no retry or refund - (File: staking-pool/src/internal.rs)

### Summary
`internal_withdraw` in `staking-pool/src/internal.rs` decrements the delegator's `unstaked` balance and the contract's `last_total_balance` *before* firing an unattached `Promise::new(account_id).transfer(amount)` [1](#0-0) . There is no `.then()` callback attached to check whether the transfer succeeded, unlike other cross-contract calls in the same contract (e.g. `internal_restake` attaches `on_stake_action` as a callback) [2](#0-1) . If the outbound transfer fails (e.g., the destination account was deleted between the `withdraw` call submission and execution, a scenario the project's own README acknowledges as possible), the delegator's accounted `unstaked` balance is never restored.

### Finding Description
The public entrypoints `withdraw` and `withdraw_all` are callable by any unprivileged delegator and route to `internal_withdraw` [3](#0-2) . Inside `internal_withdraw`, the flow is:
1. Assert sufficient unstaked balance and unlock epoch has passed.
2. `account.unstaked -= amount;` and save the account.
3. `Promise::new(account_id).transfer(amount);`
4. `self.last_total_balance -= amount;`

There is no promise result check (`is_promise_success()`), no callback, and no compensating logic if the transfer fails. This mirrors the external H-2 report's root cause: a failed outbound transfer is not tracked or retried, and the accounting is updated as if the transfer had already succeeded. The staking-pool README explicitly acknowledges this failure mode only for the owner-deletes-their-own-account edge case, and describes the recovery mechanism as: the un-transferred NEAR remains on the contract balance, and on the next `ping()` call it gets picked up by `internal_ping`'s reward calculation (`total_balance - last_total_balance`) and redistributed as a reward to *all* current stakers pro-rata by shares, not returned to the account whose withdrawal failed [4](#0-3) [5](#0-4) .

This means: once a withdrawal transfer fails for any reason (not just self-deletion by the account holder — any account in a state that rejects a plain NEAR transfer, or any transient cross-shard/receipt failure), the specific delegator's already-decremented `unstaked` balance is not restored, and the corresponding value is absorbed into the pool's total staked balance and effectively transferred to other delegators (and the owner's fee) at the next `ping()`. This directly violates the guarantee stated in the same README: "If a user deposited X, the user should be able to withdraw at least X" [6](#0-5) .

### Impact Explanation
This falls under the "Permanent freezing, unrecoverable lock, or irrevocable loss of user or protocol funds in ... unstake-withdraw ... flows" category. A delegator who successfully unstakes and waits out the unlock period can have their rightful withdrawal permanently redirected to other pool participants if the transfer promise fails for any reason outside their control (the failure need not be self-inflicted — it can result from the recipient's own account state changing, or any transient error causing the transfer action within the receipt to fail while the contract's own state mutation already happened synchronously). The affected delegator's on-chain accounted `unstaked` balance is reduced with no path to reclaim the actual NEAR, and no admin/retry function exists elsewhere in the contract to compensate them.

### Likelihood Explanation
The likelihood is low-to-moderate: it requires the transfer action to fail after `internal_withdraw` has already committed the balance decrement. Known triggers include the delegator's own account being deleted concurrently with the withdraw call being processed (acknowledged in the project's own docs) or the account exceeding storage/registration constraints at the time of receipt processing. This is not a purely self-harm scenario in the general case (contract state can be affected by relayers, key rotations, or race conditions outside the withdrawing user's control at call time), and the resulting loss is borne entirely by the individual delegator while their NEAR is redistributed to others.

### Recommendation
Attach a `.then()` callback (similar to `on_stake_action`) to the withdrawal transfer that checks `is_promise_success()`, and on failure, restores `account.unstaked += amount` and `self.last_total_balance += amount`, so a failed transfer is rolled back to the delegator's balance instead of being silently redistributed to the pool.

### Proof of Concept
1. Delegator A deposits and stakes NEAR, then calls `unstake` for `X` and waits `NUM_EPOCHS_TO_UNLOCK` (4) epochs.
2. Delegator A's account is deleted (or becomes unable to receive a plain transfer) via a submitted transaction that lands in the same or an adjacent block/receipt window as their `withdraw(X)` call.
3. `withdraw(X)` executes: `internal_withdraw` decrements `account.unstaked` by `X` and `last_total_balance` by `X`, then issues `Promise::new(account_id).transfer(X)`.
4. The transfer action fails at receipt execution time (target account non-existent) — this failure is never observed by the contract because no callback is attached [7](#0-6) .
5. The `X` NEAR remains on the contract's balance. On the next `ping()`, `internal_ping` computes `total_reward = total_balance - last_total_balance` including this `X`, and distributes it to the owner and all current stakers by share price, permanently reallocating what was Delegator A's rightful withdrawal [8](#0-7) .

                account_id, amount, account.unstaked
            )

        );

    /// Distributes rewards after the new epoch. It's automatically called before every action.
    /// Returns true if the current epoch height is different from the last epoch height.
    pub(crate) fn internal_ping(&mut self) -> bool {
        let epoch_height = env::epoch_height();
        if self.last_epoch_height == epoch_height {
            return false;
        }
        self.last_epoch_height = epoch_height;

        // New total amount (both locked and unlocked balances).
        // NOTE: We need to subtract `attached_deposit` in case `ping` called from `deposit` call
        // since the attached deposit gets included in the `account_balance`, and we have not
        // accounted it yet.
        let total_balance =
            env::account_locked_balance() + env::account_balance() - env::attached_deposit();

        assert!(
            total_balance >= self.last_total_balance,
            "The new total balance should not be less than the old total balance"
        );
        let total_reward = total_balance - self.last_total_balance;
        if total_reward > 0 {
            // The validation fee that the contract owner takes.
            let owners_fee = self.reward_fee_fraction.multiply(total_reward);

            // Distributing the remaining reward to the delegators first.
            let remaining_reward = total_reward - owners_fee;
            self.total_staked_balance += remaining_reward;

            // Now buying "stake" shares for the contract owner at the new share price.
            let num_shares = self.num_shares_from_staked_amount_rounded_down(owners_fee);
            if num_shares > 0 {
                // Updating owner's inner account
                let owner_id = self.owner_id.clone();
                let mut account = self.internal_get_account(&owner_id);
                account.stake_shares += num_shares;
                self.internal_save_account(&owner_id, &account);
                // Increasing the total amount of "stake" shares.
                self.total_stake_shares += num_shares;
            }
            // Increasing the total staked balance by the owners fee, no matter whether the owner
            // received any shares or not.
            self.total_staked_balance += owners_fee;

            env::log(
                format!(
                    "Epoch {}: Contract received total rewards of {} tokens. New total staked balance is {}. Total number of shares {}",
                    epoch_height, total_reward, self.total_staked_balance, self.total_stake_shares,
                )
                    .as_bytes(),
            );
            if num_shares > 0 {
                env::log(format!("Total rewards fee is {} stake shares.", num_shares).as_bytes());
            }
        }

        self.last_total_balance = total_balance;
        true
    }
