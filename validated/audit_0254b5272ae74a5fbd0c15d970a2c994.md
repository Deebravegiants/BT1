Confirmed: `SimplexPaymaster.sol` contains no sequencer-uptime check anywhere in the codebase (the only `Sequencer` matches in the repo are unrelated Arbitrum Orbit consensus-client code, not this contract), and it is deployed on multiple Chainlink-fed L2s (Base, Optimism, Arbitrum, BSC) per `sdk/packages/indexer/src/addresses/chainlink-price-feeds.addresses.ts`.

### Title
Missing L2 sequencer-uptime check in `SimplexPaymaster` oracle pricing lets users pay with stale Chainlink prices during/after a sequencer outage - (File: evm/src/utils/SimplexPaymaster.sol)

### Summary
`SimplexPaymaster` prices ERC-20 gas payments using Chainlink `AggregatorV3Interface.latestRoundData()` for both the native/USD and token/USD feeds, checking only for a non-positive answer and for a maximum staleness window (`maxOracleAge`), but never checking whether the L2 sequencer is up via Chainlink's L2 sequencer-uptime feed. The paymaster is deployed on rollups (Base, Optimism, Arbitrum) whose Chainlink feeds can return a technically "fresh" (`updatedAt` within `maxOracleAge`) but stale/incorrect price when the sequencer has been down and just recovered, or when the feed silently stops updating during an outage while still within the allowed staleness window.

### Finding Description
`_getOraclePrice` is the sole gate on oracle data used for pricing: [1](#0-0) 

It reverts only on `answer <= 0` or on `updatedAt` older than `maxOracleAge` (bounded to at most 7 days via `MAX_ORACLE_AGE`): [2](#0-1) 

There is no call to, or interface for, a Chainlink `L2SequencerUptimeFeed` (no `sequencer`/`answeredInRound`-based grace-period check exists anywhere in `SimplexPaymaster.sol`). This is the same root cause as the referenced report: on Optimistic/other rollups, if the sequencer goes offline, the L2 execution environment can keep serving the last cached Chainlink answer as "current" (or the feed can resume with a first post-recovery update that doesn't yet reflect the true market price), and a consumer with only a staleness bound — not a sequencer-liveness bound — will accept it as valid. `_tokenPrice` feeds this value directly into the price charged for every UserOperation: [3](#0-2) 

which is used both to size `prefundAmount` charged to the solver/user in `_prefund`/`_fetchDetails`, and to size swap output minimums in `_swapAndDeposit`-style fee recycling that references `_tokenPrice`.

### Impact Explanation
Any unprivileged user submitting a UserOperation through this paymaster (mode 0x00 permit or mode 0x02 Permit2) is priced from `_tokenPrice`, which is unprotected against sequencer downtime. If the true price of the native asset or the paying token has moved during/after a sequencer outage while the last-cached Chainlink answer stays within `maxOracleAge`, users can be charged too little (draining treasury/paymaster value on every op processed) or too much (overcharging users), both of which are direct fund-accounting corruption reachable from a single, ordinary transaction with no special privilege. This matches Medium severity per the analog report: incorrect pricing derived from unchecked oracle data during sequencer downtime causing value to move incorrectly.

### Likelihood Explanation
The paymaster is explicitly deployed to native L2 rollups with real sequencers (Base, Optimism, Arbitrum) per the configured Chainlink feed addresses, so the sequencer-downtime precondition is a real operational scenario (not theoretical), and every UserOperation processed during/shortly after such an event is exposed — no attacker coordination or governance compromise is required, only ordinary sequencer downtime coinciding with price movement.

### Recommendation
Add a Chainlink L2 sequencer-uptime feed check (with the standard grace period, e.g. Chainlink's recommended pattern of reverting if the sequencer is down or has been up for less than a grace period, commonly 3600 seconds) in `_getOraclePrice` (or a wrapper called before it), reverting `_tokenPrice`/`getTokenPrice`/`estimateTokenCost` whenever the sequencer feed reports down or still within its grace period, for every chain where `SimplexPaymaster` is deployed on a rollup with a sequencer.

### Proof of Concept
1. Deploy `SimplexPaymaster` on an L2 (e.g. Base) as configured, with `nativeOracle`/token oracles pointing at real Chainlink feeds and `maxOracleAge` set near its allowed maximum.
2. The L2 sequencer goes offline; the Chainlink feed's `updatedAt` stops advancing but remains within `maxOracleAge`, or the sequencer resumes and the feed's first post-recovery update reflects a price that hasn't converged with the true market price yet.
3. A user submits a UserOperation through the paymaster; `_fetchDetails` → `_tokenPrice` → `_getOraclePrice` returns the stale/incorrect answer, passing both the `answer > 0` and staleness checks.
4. `prefundAmount` is computed from this incorrect price and charged/refunded incorrectly relative to the true market rate, as demonstrated by the existing `testStaleOracleReverts`/`testNonPositiveOraclePriceReverts` tests in `evm/tests/foundry/SimplexPaymasterTest.t.sol` which show the contract only guards against gross staleness and non-positive answers, not sequencer-driven price staleness: [4](#0-3)

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
