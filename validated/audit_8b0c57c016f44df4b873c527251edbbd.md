### Title
Stale account risk parameters can liquidate healthy accounts or shield unhealthy accounts - (File: contracts/controller/src/risk/totals.rs)

### Summary
XOXNO Lending stores liquidation-relevant risk parameters on each supply position instead of reading the active spoke asset configuration during liquidation. A governance change therefore does not affect existing positions until `update_account_threshold` successfully restamps them. Because liquidation uses the stale stored threshold, an account can be liquidated under obsolete parameters, while another account can remain unliquidatable under obsolete favorable parameters.

### Finding Description
`calculate_account_risk_totals` values every supply position with its persisted `position.liquidation_threshold` when deriving `weighted_collateral` and `health_factor`. [1](#0-0)  `build_liquidation_plan` directly requires that stored-parameter health factor to be below `1 WAD` before liquidation proceeds. [2](#0-1) 

The active configuration is applied only by the separate permissionless `update_account_threshold` path. [3](#0-2)  That refresh is gated:

- liquidation-favorable changes are skipped unless the hypothetical health factor is at least `1.05`; [4](#0-3) 
- a full refresh reverts if the final health factor is below `1.05`. [5](#0-4) 

Thus, after a ready governance operation changes an asset threshold, the committed configuration and the risk state used by `liquidate` can diverge. An unprivileged liquidator can call `liquidate(liquidator, account_id, debt_payments, SeizeMode::Transfer)` while the stale health factor is below one. Conversely, an account can remain unliquidatable when its stored threshold is higher than the active threshold and the refresh is intentionally skipped or reverts.

### Impact Explanation
A borrower can lose collateral and liquidation bonus even though the account would be healthy under the active risk configuration. In the reverse direction, protocol liquidation can be delayed while debt accrues and collateral prices move, increasing the likelihood of bad debt socialization.

### Likelihood Explanation
The condition requires a governance risk-parameter change that moves an account across the liquidation boundary while its position still contains the old threshold. The subsequent liquidation path is permissionless. The `1.05` refresh gate widens the affected range because an account that is merely healthy under the new parameters may still be unable to receive the updated tuple.

### Recommendation
Use the active liquidation threshold for liquidation eligibility, or synchronously resolve each supplied asset's current configuration inside `build_liquidation_plan` before calculating `health_factor`. If staged account migration is intended, liquidation should account for the pending effective threshold rather than treating the stale position tuple as authoritative.

### Proof of Concept
Assume collateral value `C = 100 USD`, debt `D = 80 USD`, and the stored position threshold is `75%`.

1. Governance executes a ready operation changing the asset's liquidation threshold to `83%`.
2. The stored health factor remains `100 * 0.75 / 80 = 0.9375`.
3. Under active parameters, health would be `100 * 0.83 / 80 = 1.0375`.
4. `update_account_threshold(caller, true, [account_id])` reverts because the resulting health factor is below the required `1.05`, leaving the stale threshold persisted.
5. A liquidator calls `liquidate(liquidator, account_id, [(debt_hub_asset, debt_amount)], SeizeMode::Transfer)`.
6. `build_liquidation_plan` accepts liquidation using the stale `0.9375` health factor and seizes collateral even though the account is healthy under current risk parameters.

For the reverse case, use stored `85%` and updated `78%`. The stored health factor is `1.0625`, while active health is `0.975`. The liquidation-favorable update is skipped because the hypothetical health factor is below `1.05`; liquidation then rejects the still-unhealthy account because the stale health factor is above one.

/// Refreshes the liquidation threshold, bonus, and fees together. With debt,
/// changes favoring liquidators require hypothetical health factor >= 1.05.
pub(crate) fn apply_gated_liquidation_params(
    env: &Env,
    cache: &mut Context,
    account: &Account,
    hub_asset: &HubAssetKey,
    position: &mut AccountPosition,
    effective_config: &AssetConfig,
) {
    if favors_liquidator(position, effective_config)
        && !account.debt_free()
        && !clears_min_hf(
            env,
            cache,
            account,
            hub_asset,
            position,
            effective_config.liquidation_threshold,
        )
    {
        return;
    }

    position.liquidation_threshold = effective_config.liquidation_threshold;
    position.liquidation_bonus = effective_config.liquidation_bonus;
    position.liquidation_fees = effective_config.liquidation_fees;
}
