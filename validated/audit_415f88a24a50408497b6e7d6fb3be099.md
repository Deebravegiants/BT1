### Title
IntentGatewayV2 escrow accounting does not reconcile with actual token balance, causing permanent freezing of escrowed funds for rebasing/balance-modifying tokens - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentGatewayV2` escrows arbitrary ERC-20 tokens supplied by users in `placeOrder` and tracks the escrowed amount per `(commitment, token)` in the `_orders` mapping. Release of that escrow (`fillOrder`, `RedeemEscrow`, `RefundEscrow`, order cancellation) always transfers the *recorded* accounting amount rather than re-checking it against the gateway's actual current token balance. If the escrowed token's balance can change outside of transfers (rebasing, elastic-supply, negative-rebase, or any token whose `balanceOf` can decrease while custodied), the sum of all outstanding `_orders[...][token]` entries can exceed the real balance held by the contract, and a later beneficiary's withdrawal will revert, permanently freezing their funds.

### Finding Description
`placeOrder` measures the *actual amount received* at deposit time via balance-before/after diffing (to handle fee-on-transfer tokens) and stores that in escrow: [1](#0-0) [2](#0-1) 

This correctly protects against fee-on-transfer deflation *at the moment of deposit* (confirmed by the fee-on-transfer test suite), but it does nothing about balance changes that occur *after* escrow while tokens sit in the contract — which is exactly the class covered by rebasing/elastic-supply tokens, since `balanceOf` for such tokens can decrease without any `transfer` call touching the escrowed balance.

The withdrawal path never re-measures the actual balance; it simply decrements the internal accounting and transfers the recorded amount: [3](#0-2) 

The same unconditional-amount transfer pattern (fixed amount from `WithdrawalRequest`, not validated against real balance) is duplicated in the Tron variant: [4](#0-3) 

`_withdraw`/`withdraw` is reachable by an unprivileged path: a solver filling a same-chain order (`fillOrder` → `_withdraw`), a cross-chain `RedeemEscrow`/`RefundEscrow` message delivered via `onAccept` after being relayed through Hyperbridge (`ExtrinsicIntents.sol` `onAccept`), or a `onGetResponse`-driven refund after cancellation — all of which are triggerable by ordinary users/solvers/relayers, not privileged admins.

Because escrow for a given token is a shared pool across every order that used that token (the contract holds one aggregate `balanceOf(token)` backing many independent `_orders[commitment][token]` entries), a negative rebase or other exogenous balance shrinkage affecting the pooled balance means whichever order is settled last for that token will find `IERC20(token).safeTransfer(beneficiary, amount)` reverting because the contract's real balance is less than the sum of amounts still recorded as owed. This is the same "Alice withdraws first, Bob's identical claim then reverts" failure mode described in the original Noya `AccountingManager` report, mapped onto the intents escrow.

### Impact Explanation
Funds get permanently stuck in the `IntentGatewayV2` contract. The affected withdrawer's `EscrowReleased`/`EscrowRefunded` transaction reverts every time it is retried (the shortfall does not go away), so a legitimate user or solver can never redeem their portion of the escrow. This is a direct freezing-of-funds condition, satisfying "Medium/High" impact criteria (permanent freezing of user funds) even though it requires a specific token property (balance mutation outside transfer) to be exploitable/triggered.

### Likelihood Explanation
`IntentGatewayV2` is a generic, permissionless intents gateway that accepts arbitrary ERC-20 `token` addresses supplied by the order creator in `TokenInfo.token` — there is no allowlist visible in `placeOrder`. Any deployment that is paired with a rebasing, elastic-supply, or otherwise balance-mutating token (a broad and increasingly common token category) is exposed. Cross-chain orders additionally hold escrow for an unbounded duration awaiting relayed `RedeemEscrow`/`RefundEscrow` messages, widening the window during which a rebase can erode the pooled balance before settlement.

### Recommendation
- Before transferring in `_withdraw`/`withdraw`, clamp the transferred amount to `min(recordedAmount, IERC20(token).balanceOf(address(this)))`, or re-measure the actual balance change per token at withdrawal.
- Alternatively, disallow rebasing/elastic-supply tokens at the protocol level (documented restriction + optional token allowlist), since escrow accounting fundamentally assumes token balances are only affected by transfers it controls.
- Consider tracking escrow as shares of a per-token pool (rather than fixed absolute amounts) if support for rebasing tokens is required, mirroring the recommended fix in the original Noya report (measure balance immediately before/after each transferring routine and reconcile allocations to it).

### Proof of Concept
1. Deploy `IntentGatewayV2` and use a negative-rebase ERC-20 (`tokenA`) as the order input token.
2. Alice places an order with 1000 `tokenA` as input; `placeOrder` records `_orders[commitmentA][tokenA] = 1000` after confirming actual receipt (see `evm/src/apps/IntentGatewayV2.sol:320-322`).
3. Bob places another order with 1000 `tokenA`; `_orders[commitmentB][tokenA] = 1000`. Gateway now holds 2000 `tokenA` total, backing two independent escrow entries.
4. `tokenA` rebases down 10% while both orders are still outstanding (no transfer occurs, `balanceOf(gateway)` alone shrinks to 1800).
5. A solver fills Alice's order first; `fillOrder` → `_fillSameChain`/`_fillCrossChain` → `_withdraw` transfers 1000 `tokenA` to the filler, succeeding because 1800 ≥ 1000, leaving the gateway with 800 `tokenA`.
6. A solver attempts to fill Bob's order; `_withdraw` tries `IERC20(tokenA).safeTransfer(beneficiary, 1000)` but the gateway only holds 800 `tokenA`. The `safeTransfer` reverts (`ERC20: transfer amount exceeds balance` or equivalent), and this revert is permanent — Bob's escrow can never be redeemed, and his 1000 `tokenA` worth of input tokens is stuck in the contract forever.

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
