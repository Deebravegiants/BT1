## Analysis

The Convex bug's root cause is a **permissionless external function whose funds-moving side effects are relied upon by a higher-level contract's balance-diff accounting**, letting anyone front-run/interfere with money that the protocol assumes only it controls. Hyperbridge has a direct structural analog in the shared `CallDispatcher` contract used by `IntentGatewayV2`/`IntentsBase` (and `HyperFungibleToken`/`WrappedHyperFungibleToken*`) for predispatch/postdispatch calldata execution.

`CallDispatcher.dispatch()` has **no access control whatsoever** — no `onlyOwner`, no caller allowlist, not even a `msg.sender` check: [1](#0-0) 

This single `CallDispatcher` instance is a **persistent, shared contract** referenced via `_params.dispatcher`, reused across every `placeOrder`/`fillOrder` call on `IntentGatewayV2`: [2](#0-1) 

During predispatch, assets are sent to the dispatcher, an arbitrary user-supplied `predispatch.call` is executed on it, and then the protocol sweeps back **only the tokens listed in `order.inputs`**: [3](#0-2) 

The same pattern exists on the postdispatch/output side in `_execute`, which sweeps back **only tokens listed in `order.output.assets`**: [4](#0-3) 

Since the predispatch/postdispatch `call` is arbitrary calldata (e.g., a swap, unwrap, or claim), it can produce token types, dust, or ETH that are **not** among the tokens the sweep loop iterates over. Any such balance is left stranded on the shared `CallDispatcher`. Because `dispatch()` has zero access control, **any third party** — not just `IntentGatewayV2` — can call it directly and instruct the dispatcher to transfer its currently-held ETH or ERC20 balance to an address of their choosing, exactly as Convex's `getReward(account, true)` could be invoked by anyone to move funds that a higher-level contract's diff-based accounting assumed it alone controlled.

### Title
Unrestricted `CallDispatcher.dispatch()` lets anyone drain tokens/ETH stranded by predispatch/postdispatch calldata sweeps - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher.dispatch()` is a fully permissionless function on a single, persistent, shared contract used by `IntentGatewayV2.placeOrder`, `IntentsBase._execute` (fillOrder output calldata), and the `HyperFungibleToken`/`WrappedHyperFungibleToken*` `onAccept` calldata paths. The gateway's post-execution sweep only recovers balances for tokens explicitly listed in `order.inputs` / `order.output.assets`, so any token type (or ETH dust) produced by the arbitrary predispatch/postdispatch call that isn't in that list remains on the dispatcher. Because `dispatch()` checks nothing about `msg.sender`, any unrelated address can call it directly and command the dispatcher to send its held balance anywhere.

### Finding Description
`dispatch()` decodes a `Call[]` and executes each `to.call{value}(data)` with no restriction on who invokes it: [1](#0-0) 

`IntentGatewayV2.placeOrder`'s predispatch flow sends order assets to this shared dispatcher, executes the user-supplied `predispatch.call`, then sweeps back only the amounts for `order.inputs`: [5](#0-4) 

`_execute` (postdispatch/output calldata during `fillOrder`) follows the identical pattern, sweeping back only `order.output.assets`: [4](#0-3) 

`HyperFungibleTokenUpgradeable.onAccept` and `WrappedHyperFungibleTokenUpgradeable` also route arbitrary destination calldata through the same shared `dispatcher`: [6](#0-5) 

Any output of the arbitrary calldata that isn't one of the explicitly enumerated tokens (e.g. a bonus/reward token from a swap, referral token, rounding remainder in a token not part of the order, or ETH left after a partial `Call.value` spend) is never swept and simply sits on the dispatcher. Since `dispatch()` has no caller restriction, anyone can subsequently call it with `Call({to: strandedToken, data: transfer(attacker, balance)})` or `Call({to: attacker, value: dispatcher.balance})` and steal it — this is functionally identical to Convex's permissionless `getReward()` being callable by anyone to move funds a higher-level contract assumed it exclusively controlled.

### Impact Explanation
Funds routed through the shared `CallDispatcher` that fall outside the enumerated `order.inputs`/`order.output.assets` set are permanently exposed to theft by any unprivileged address — a direct, unbacked loss of user/protocol funds, not merely a temporary lock. Given the `CallDispatcher` is shared across all `IntentGatewayV2` orders and all `HyperFungibleToken`-family calldata executions, the blast radius covers every deployment referencing the same dispatcher address.

### Likelihood Explanation
Any order/message with non-trivial predispatch or postdispatch calldata (swaps, unwraps, multi-hop routes) commonly yields dust, rounding remainders, or secondary reward/referral tokens beyond the declared input/output set. An attacker only needs to observe such a transaction (or scan the dispatcher's balances) and issue a single unprivileged `dispatch()` call to sweep the residue — no special permissions, timing precision, or protocol interaction is required, making this straightforward to exploit opportunistically.

### Recommendation
Restrict `CallDispatcher.dispatch()` to a caller allowlist (e.g., only the configured `IntentGatewayV2`/`IntentsBase`/`HyperFungibleToken` instances, or `onlyOwner`), or make the dispatcher ephemeral per-call (e.g., deployed via `CREATE2`/minimal proxy per order and self-destructed/never reused after the sweep) so no cross-transaction residual balance can accumulate on a permissionless shared contract. Additionally, have the sweep logic in `placeOrder`/`_execute` enumerate and recover *all* token balances actually held by the dispatcher post-call, not just the ones declared in the order.

### Proof of Concept
1. A user calls `IntentGatewayV2.placeOrder` with a `predispatch.call` that swaps ETH via a router for `order.inputs[0].token = DAI`, but the swap path also yields a small amount of a secondary reward token (or leaves ETH dust because `Call.value` under-spends).
2. `placeOrder`'s sweep loop (lines 260–299) only builds `transferCalls` for the DAI amount in `order.inputs`; the reward token / ETH dust remains on `_params.dispatcher`.
3. An unrelated attacker, watching the shared `CallDispatcher` address, submits a direct transaction: `CallDispatcher(dispatcher).dispatch(abi.encode([Call({to: rewardToken, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, rewardToken.balanceOf(dispatcher))})]))`.
4. Since `dispatch()` performs no caller check, the call succeeds and the stranded reward tokens/ETH are transferred to the attacker, permanently and unrecoverably diverting funds that should have accrued to the protocol/user.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
