### Title
Attacker-Controlled Router Calldata Lets Users Bypass the Variable-Rate Protocol Fee in `ExternalActionSwap` - (File: contracts/external-actions/swaps/ExternalActionSwap.sol)

### Summary
This is the same root-cause class as the Sudoswap finding: the fee logic assumes the value that must be taxed lands in the contract that collects the fee, but the contract only *infers* that value from its own balance delta rather than from the amount actually moved. In `ExternalActionSwap.swap()`, the percentage-based (`variableRate`) protocol/relay fee is computed from `swappedAmount`, which is derived purely from the `ExternalActionSwap` contract's own token-balance change around the `callRouter()` call [1](#0-0) . The router calldata (`externalActionMetadata`) that is forwarded verbatim to the fixed `router` address is attacker-supplied and executed with no constraint on the swap's output recipient [2](#0-1) . By crafting calldata whose embedded receiver is the attacker's own EOA instead of the `ExternalActionSwap` contract, the on-contract balance delta (and therefore `swappedAmount`) can be driven to ~0 while the router still performs a real swap using the input funds withdrawn from the shielded pool, so the attacker receives the real output value externally while the protocol's `variableRate` fee is computed on (near) zero.

### Finding Description
`Hinkal._externalTransact()` withdraws the input token amount (`deltaAmountChanges[i] < 0`) from the shielded pool directly to `circomData.externalActionData.externalAddress`, i.e. the `ExternalActionSwap` contract [3](#0-2) . Inside `swap()`, `callRouter()` is invoked, and the swap output amount is measured only as the difference between the contract's own token balance before and after the router call:
```
uint256 balanceBefore = getERC20OrETHBalance(outputToken);
... router.call(externalActionMetadata) ...
swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
``` [2](#0-1) 

The `externalActionMetadata` passed to the router is fully attacker-controlled calldata (typical LI.FI / aggregator generic-swap data includes an explicit output receiver field). Nothing in `swap()` or `callRouter()` forces the router to deliver the output tokens back to `address(this)`. If the calldata specifies the attacker's own address as receiver, `getERC20OrETHBalance(outputToken)` after the call is unchanged, so `swappedAmount ≈ 0`.

Downstream, the protocol/relay percentage fee is:
```
uint256 hinkalFee = hinkalHelper.calculateRelayFee(swappedAmount, 0, circomData.feeStructure.variableRate);
``` [4](#0-3) 

With `swappedAmount ≈ 0`, `hinkalFee ≈ 0`, regardless of how much real value the router actually delivered to the attacker off-contract. Only the (optional) flat fee, deducted earlier from `inputAmount` when `inputToken == feeStructure.feeToken`, is still collected — the proportional fee tied to the size of the swap is entirely avoided.

This is structurally identical to the Sudoswap bug: the fee-taking code assumes the taxed value is held by the contract performing the accounting (`_factory`/pair in Sudoswap; `ExternalActionSwap` here), but an `assetRecipient`-equivalent (the router-controlled output recipient) can be pointed elsewhere, leaving the fee-collector with zero balance to tax from.

Note: `circomData.externalActionData` (which contains `externalActionMetadata`) is included in `calldataHash`, which is checked in `HinkalHelper.performHinkalChecks` and fed as a circuit public input [5](#0-4) [6](#0-5) . This only proves the metadata is exactly what the prover intended to submit — it does not constrain the *contents* of that metadata (e.g., the embedded receiver address), so a self-authorized, unprivileged EOA can still choose calldata that redirects the swap output.

### Impact Explanation
This is theft of protocol/relay fee revenue (High impact per the given rubric: "theft ... of protocol/relay fees"). The attacker does not lose any of their own shielded balance — they receive the full real swap output externally at their own address while only paying the flat fee, permanently denying the protocol/relay the `variableRate` cut it is entitled to on every swap routed this way. Because `ExternalActionSwap`/`LifiExternalAction` is a core, always-available external action (not an admin/relay-only feature), this is repeatable on every swap transaction.

### Likelihood Explanation
High. Any user who can generate a valid Hinkal proof (i.e., any regular unprivileged user of the protocol) can supply their own `externalActionMetadata` for the LI.FI/router call, since that field is only integrity-checked (hashed) against the prover's intent, not content-validated. Aggregator calldata formats commonly expose a receiver/recipient parameter that can be set independently of the caller contract, making this trivially exploitable without any special access.

### Recommendation
Do not derive the fee base from the executing contract's own balance delta when the router call is attacker-supplied calldata. Instead:
- Require (and enforce on-chain, not just via calldata hash) that the router call's output receiver is hardcoded to `address(this)` (the `ExternalActionSwap`/`LifiExternalAction` contract), e.g., by constructing the calldata parameters on-chain rather than accepting an opaque blob, or by using a router feature that lets the caller override/verify the receiver.
- Alternatively, pull the fee from the actual swap output before any receiver-controlled distribution happens, e.g., by using a router integration pattern that guarantees funds route through this contract first (analogous to Spearbit's recommendation to pay fees "from the original caller"/from wherever funds provably reside, rather than assuming a fixed intermediary holds them).
- Add an invariant check that `swappedAmount` is not implausibly small relative to `inputAmount` and market rates enforced via `circomData.slippageValues[1]`, though the primary fix should ensure the receiver of the router-controlled swap cannot be redirected away from the fee-collecting contract.

### Proof of Concept
1. Attacker deposits/holds a shielded UTXO of `inputToken` worth `V`.
2. Attacker generates a valid Hinkal transaction proof for a swap external action (`LifiExternalAction`), setting `deltaAmountChanges[0] = -V` (input) and `deltaAmountChanges[1] = 0` expected output claim in the shielded pool (or minimal, matching `slippageValues[1]`).
3. Attacker crafts `externalActionMetadata` for the LI.FI router such that the swap's output receiver field is set to the attacker's own external EOA instead of `address(this)` (the `LifiExternalAction` contract).
4. `Hinkal._externalTransact` transfers `V` of `inputToken` to `LifiExternalAction`; `swap()` calls `callRouter()`, which executes the router call — the router pulls `inputToken` from `LifiExternalAction` via `approveUnlimited` and sends the real swapped `outputToken` value directly to the attacker's EOA [2](#0-1) .
5. `getERC20OrETHBalance(outputToken)` on `LifiExternalAction` shows no meaningful increase, so `swappedAmount ≈ 0`, `hinkalFee ≈ 0` [7](#0-6) .
6. Only the flat fee (if `feeToken == inputToken`) is collected by the relay; the attacker walks away with the full swap output off-protocol while the protocol/relay is shorted the entire variable-rate fee it should have collected on amount `V`.

    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
