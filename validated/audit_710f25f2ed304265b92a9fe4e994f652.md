### Title
`WrappedHyperFungibleToken.send()` accepts fee-on-transfer underlying tokens and dispatches the pre-fee amount, over-crediting the destination chain - (File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol / WrappedHyperFungibleTokenUpgradeable.sol)

### Summary
`WrappedHyperFungibleToken` (and its upgradeable twin) implements the lock/unlock side of the HyperFungibleToken bridge: it locks an arbitrary configured `_underlying` ERC20 on the home chain and relies on peer `HyperFungibleToken` contracts to mint the same amount on other chains. `send()` pulls tokens via `safeTransferFrom` but never verifies the amount actually received by the contract before dispatching the cross-chain message with the user-supplied `params.amount`. If `_underlying` is a fee-on-transfer (or rebasing/deflationary) token, the wrapper receives less than `params.amount` yet instructs the destination chain to mint/unlock the full `params.amount`, exactly analogous to the Notional finding where `secondaryBorrowCurrencies` assets were never checked for `hasTransferFee` even though the primary borrow currency was.

### Finding Description
In `send()`, the contract does:
```solidity
IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
...
DispatchPost memory request = _buildDispatchPost(params); // uses params.amount verbatim
``` [2](#0-1) 

There is no balance-before/after check as used elsewhere in the codebase specifically to guard against fee-on-transfer tokens (see `IntentGatewayV2.placeOrder`, which explicitly snapshots `balanceOf` and reduces the recorded/committed amount to the actual received value): [1](#0-0) 

Because `_buildDispatchPost` encodes `params.amount` (not the actual received balance) into the `Message.amount` field that peer `HyperFungibleToken` contracts mint on delivery, every fee-on-transfer-token send silently under-collateralizes the wrapper: the wrapper holds `params.amount - fee` but has promised `params.amount` worth of mintable/unlockable supply on the destination side(s). This deficit accumulates across all sends of that token. The `onAccept`/`onPostRequestTimeout` unlock paths also use `safeTransfer(beneficiary, message.amount)` (the nominal amount) without accounting for possible additional transfer fees, compounding the shortfall whenever the underlying is later unlocked back on the home chain. [4](#0-3) 

The owner configures `_underlying` freely via `configure()`, and nothing in the contract or its interface restricts it to non-fee tokens, so this is reachable by any token holder who owns/permissions a wrapper for a fee-on-transfer token, or simply by a wrapper deployment that later has its underlying replaced/is unaware the token later adds a fee (e.g., upgradeable/pausable fee tokens).

### Impact Explanation
Each `send()` call with a fee-on-transfer underlying creates a shortfall between the wrapper's actual token custody and the aggregate amount it has promised to back on remote chains. Because the wrapper is the sole backing for freely mintable wrapped supply on peer chains, this shortfall is a real accounting break: eventually redemptions/unlocks on the home chain will fail for the last users to redeem (insufficient balance in the wrapper), causing permanent freezing of funds for some depositors, and it also lets any user extract more value out cross-chain than they actually locked in, i.e. the destination chain mints supply that is not fully backed. This matches "unbacked mint" / "permanent freezing of funds" impact criteria.

### Likelihood Explanation
Triggering requires only calling the already-public, unprivileged `send()` function with a fee-on-transfer token configured as `_underlying` — a single user transaction reachable exactly like the reference Notional bug's `secondaryBorrowCurrencies` gap. The codebase already demonstrates awareness of and mitigation for this exact class of bug in `IntentGatewayV2` (dedicated `FeeOnTransferToken` tests and balance-based accounting), but the equivalent defense was never applied to `WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable`, indicating an inconsistent application of the same safeguard across the codebase (the same root cause pattern as the external report).

### Recommendation
In `send()`, measure `_underlying` balance before and after `safeTransferFrom` and use the actual delta as the dispatched `Message.amount` (mirroring the pattern already used in `IntentGatewayV2.placeOrder`), rather than trusting `params.amount`. Alternatively, explicitly disallow configuring fee-on-transfer/rebasing tokens as `_underlying` during `configure()`.

### Proof of Concept
1. Owner calls `configure()` on `WrappedHyperFungibleToken` with `_underlying` set to a fee-on-transfer ERC20 (e.g., 1% fee), `isWeth = false`.
2. Attacker approves the wrapper and calls `send({dest: chainB, to: attacker, amount: 1000e18, ...})`.
3. `safeTransferFrom` pulls 1000e18 but the wrapper only receives 990e18 due to the 1% fee; the wrapper's underlying balance is 990e18.
4. `_buildDispatchPost` encodes `Message.amount = 1000e18` (the full, pre-fee amount) into the POST request dispatched to chain B.
5. On chain B, the peer `HyperFungibleToken.onAccept` mints 1000e18 wrapped tokens to the attacker (matching the escrow/commitment tests pattern in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol` which show the codebase's expected correct behavior is to use actually-received amounts, e.g. `testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`).
6. The wrapper is now backing 1000e18 of minted wrapped supply with only 990e18 of actual underlying custody — a 10e18 shortfall that grows with every fee-on-transfer send, eventually preventing later unlocks from completing at face value. [5](#0-4)

            msgValue = msgValue - params.amount;

        }

            from: msg.sender,
            to: params.to,
            dest: string(params.dest),
            amount: params.amount,

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }
