### Title
Webhook Shop/Topic Identity Spoofing — HMAC Covers Only the Raw Body, Not the Trusted `shop`/`topic` Headers - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by HMAC-verifying the raw request body, then unconditionally trusts the `shop-domain` and `topic` HTTP headers to decide which shop the payload belongs to and which handler receives it. Because the HMAC signature does not cover any header, an unprivileged internet user who legitimately owns a shop with the app installed (and therefore legitimately receives real, correctly-signed webhooks for their own store) can replay a genuine `body`+`hmac` pair while swapping the `shop-domain` (and/or `topic`) headers to any value they choose. The check still passes, and the forged shop identity is handed to the app's handler as an authenticated fact.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are read directly from attacker-controllable HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) [3](#0-2) 

`HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string` (i.e., the raw body) and compares it to the `hmac` header: [4](#0-3) 

`Registry.process` gates entirely on that body-only HMAC check, then dispatches based on the unauthenticated `topic` header and forwards the unauthenticated `shop` header straight to the app's handler as `WebhookMetadata#shop`: [5](#0-4) 

The identity binding that should hold is:
`hmac(body, secret) == received_hmac` **should imply** `shop_header == shop_that_actually_produced_body` (and `topic_header == topic_that_actually_produced_body`).

In the current implementation this equality is never enforced — only `hmac(body, secret) == received_hmac` is checked, while `shop` and `topic` are parsed, not verified. The library's own documentation reinforces the false assumption that HMAC validation proves shop/topic authenticity: "This will verify the request did indeed come from Shopify and then call the specified handler for that webhook" (`docs/usage/webhooks.md`), yet nothing ties the verified bytes to the claimed shop or topic.

### Impact Explanation
Any merchant who installs the app (an "unprivileged internet user" relative to other tenants of the same app) receives real webhooks from Shopify with valid `hmac-sha256`/body pairs for their own store. Since the signature covers only the body, that attacker can capture one such genuine request and replay it directly to the app's public webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop's domain (and, since `topic` is also unauthenticated, the `x-shopify-topic` header changed to any registered topic, including the mandatory `customers/redact`, `customers/data_request`, or `shop/redact` topics). `Registry.process` will accept the forged headers as long as body+hmac still match, invoke the handler chosen by the forged `topic`, and deliver `WebhookMetadata` claiming the forged `shop` — causing the host application to act on attacker-supplied data under a victim's tenant identity. This is a cross-tenant identity-confusion vulnerability: it lets a low-privileged, unauthenticated-relative-to-other-tenants party inject data or trigger sensitive lifecycle handlers (GDPR/mandatory webhooks, order/customer processing, etc.) attributed to a shop they do not control.

### Likelihood Explanation
Exploitation only requires: (1) installing the target app on any shop (or otherwise obtaining one real webhook delivery, which many apps expose via public install), and (2) sending a crafted HTTP POST with the captured body/HMAC and altered headers to the app's public webhook URL — no access to `api_secret_key`, tokens, or the target's account is needed. This is realistically reachable by any internet user who is (or can briefly become) a customer/merchant of the app.

### Recommendation
Include the shop domain, topic, and webhook id in the signed material (or otherwise cryptographically bind them to the verified body), or require the host application to cross-check `data.shop`/`data.topic` against a shop that is independently known to be enrolled (e.g., an existing stored session) before trusting them. At minimum, update `Utils::VerifiableQuery`/`HmacValidator` usage for webhooks so that `to_signable_string` — or an additional check in `Registry.process` — incorporates the header values that the handler is later trusted with, and correct the documentation's claim that HMAC validation proves the request "did indeed come from Shopify" for a specific shop/topic.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; register for topic `orders/create`.
2. Capture a legitimate Shopify webhook delivery to the app, e.g.:
   ```
   POST /callback/orders/create
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid-hmac-of-body>
   x-shopify-shop-domain: attacker.myshopify.com
   { "id": 1, "note": "attacker-controlled" }
   ```
3. Replay the identical body and `x-shopify-hmac-sha256` value, but change:
   ```
   x-shopify-shop-domain: victim.myshopify.com
   ```
4. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only hashes the unchanged body. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` invokes the `orders/create` handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker's data>, ...)`, causing the app to process attacker-controlled content as if it originated from `victim.myshopify.com`.
