### Title
Webhook `shop`/`topic`/`webhook-id` headers are trusted for routing and downstream identity without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)`, but `Request#to_signable_string` returns only the raw body. The `shop`, `topic`, and `webhook_id` values are read straight from unauthenticated HTTP headers and handed to the application's handler as trusted identity, breaking the intended binding `hmac_signed_bytes == acted_on_identity`.

### Finding Description
`Registry.process` does:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
``` [1](#0-0) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to `verifiable_query.hmac`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns **only `@raw_body`**, while `shop`, `topic`, and `webhook_id` are parsed from headers and are not part of the signed material:
```ruby
def hmac
  Digest.hexencode(Base64.decode64(...))
end
def shop
  T.cast(shopify_header("shop-domain"), String)
end
def to_signable_string
  @raw_body
end
``` [3](#0-2) 

The equality the code implicitly assumes but does not enforce is: `bytes_verified_by_hmac == identity_acted_on (shop header)`. In reality, `bytes_verified_by_hmac == raw_body only`, and `identity_acted_on = unauthenticated shop header`. Because the HMAC is computed with the app's single shared `api_secret_key` across *all* shops that installed the app [4](#0-3) , any tenant of the app that legitimately receives one valid `(body, hmac)` pair for their own shop can replay that exact body+hmac to the app's webhook endpoint while substituting a different `shopify-shop-domain` header. `HmacValidator.validate` will still return `true` (the body-derived signature matches), and `Registry.process` will forward the attacker-chosen `shop` value to the handler as if Shopify itself asserted it belonged to that shop.

### Impact Explanation
Handlers are documented to use `data.shop` as the trusted tenant identifier to route/act on data (e.g., "look up the record for `data.shop` and update it"), as shown in the gem's own webhook usage docs. [5](#0-4)  Since `shop` is not bound to the signature, a malicious merchant with the app installed on their own store can capture one legitimately signed webhook body from Shopify (delivered to their own store) and resend it to the app's public webhook endpoint with an arbitrary victim `shop` header. Any handler logic that trusts `data.shop` for tenant lookups (session retrieval, record updates, cache keys, etc.) can be tricked into acting on a different tenant's data using attacker-controlled content but a validated-looking HMAC. This is a cross-tenant confusion issue matching the report's "unvalidated identity used downstream despite adjacent validation passing" pattern.

### Likelihood Explanation
Any merchant who installs the app is, by definition, an "unprivileged" actor relative to other tenants and receives real webhooks with valid `(body, hmac)` pairs for their own shop as part of normal operation — no secret leakage, TLS interception, or privileged access is required to obtain one. Replaying that captured pair to the same public webhook URL with a modified `shop` header is trivial (a single HTTP request). The severity of the eventual impact still depends on how a given handler uses `data.shop`, but the gem provides no protection and its own example handler pattern uses `data.shop` directly for downstream routing.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header values in the HMAC-signed material, or otherwise cryptographically bind them to the verified body (e.g., derive/verify shop via a separate authenticated channel such as looking up the shop from a previously stored, access-token-verified session rather than trusting the raw header). At minimum, document prominently that `data.shop` from `WebhookMetadata` must not be treated as authenticated on its own, and require host apps to cross-check it against known installed shops before use.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`; Shopify sends a legitimate webhook `POST /callback/orders/create` with body `B` and header `shopify-hmac-sha256: HMAC(secret, B)` and `shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker captures `B` and the valid HMAC value (they own this shop's webhook endpoint/logs).
3. Attacker resends the same request to the app's public webhook endpoint, replacing only `shopify-shop-domain` with `victim-shop.myshopify.com` (topic/webhook-id can also be altered):
```ruby
ShopifyAPI::Webhooks::Registry.process(
  ShopifyAPI::Webhooks::Request.new(
    raw_body: B,
    headers: {
      "shopify-hmac-sha256" => captured_hmac,     # still valid: HMAC only covers B
      "shopify-topic" => "orders/create",
      "shopify-shop-domain" => "victim-shop.myshopify.com",  # forged
    }
  )
)
```
4. `Utils::HmacValidator.validate` returns `true` because it only checks `B` against the signature. `Registry.process` calls the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to act on/attribute attacker-controlled content to `victim-shop`.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
```
