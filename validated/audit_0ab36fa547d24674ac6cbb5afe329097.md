### Title
Webhook `shop` (tenant) identifier is not covered by the HMAC, enabling cross-tenant webhook spoofing via replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw request body, while the `shop` (tenant identity) is read from an unauthenticated header and passed on to the app's webhook handler as trusted tenant context.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no relation to the HMAC computation at all [2](#0-1) . `HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (i.e., the body) and compares it against the `hmac` header using `OpenSSL.secure_compare` [3](#0-2) . `Registry.process` treats a passing HMAC check as authorization to hand `request.shop` straight into `WebhookMetadata` as the trusted tenant identifier for the handler [4](#0-3) .

The identity binding that should hold is: `shop-that-produced-the-HMAC == shop-value-the-app-acts-on`. Because the app's `api_secret_key`/`client_secret` (used to compute the HMAC) is the same for every shop that installed the app — it is not per-shop — any two legitimate webhook deliveries for the *same app* (from Shop A and Shop B) are signed with the same secret. An attacker who can capture one legitimate `(raw_body, hmac)` pair (e.g., from their own shop, or a shop they control, or via a proxy/logged request) can replay that exact body+HMAC to the app's webhook endpoint while substituting `shopify-shop-domain: victim-shop.myshopify.com`. `HmacValidator.validate` still succeeds because it never inspects the shop header, and `Registry.process` calls the handler with `shop: request.shop` set to the attacker-chosen value [5](#0-4) .

The gem's own documentation reinforces that host apps are expected to use `data.shop` as the tenant key for follow-up processing (e.g., looking up a shop's session/DB record before doing work), rather than deriving it from the URL path or another authenticated source: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` [6](#0-5) .

### Impact Explanation
This breaks tenant isolation: an attacker who controls or has observed one legitimate webhook (same app, any shop) can forge a webhook that the host application will process as if it originated from a different, arbitrary merchant shop, because the `shop` field consumed by the application layer is never bound to the HMAC. Depending on how the host app keys its data by `data.shop` (as the gem's own docs recommend), this enables cross-tenant data confusion/injection — writing or triggering actions against a victim shop's records using attacker-controlled body content signed under the shared app secret.

### Likelihood Explanation
Exploitation requires the attacker to have captured at least one valid `(body, hmac)` pair for the app (trivially achievable if the attacker's own shop has the app installed, since they receive real webhooks from Shopify for their own shop), then replay it with a different `shop-domain` header value. No access to `api_secret_key` or any access token is required. This satisfies the cross-tenant-access impact category without any credential leakage.

### Recommendation
Do not treat `request.shop` as trusted tenant context on its own. `HmacValidator`/`Request#to_signable_string` should incorporate the `shop-domain` header (and ideally `webhook-id`/topic) into the signed material, or `Registry.process` should independently verify that the shop reported by the header matches a shop that the app expects to receive this specific webhook for (e.g., cross-check against a known/registered shop list or the resource referenced in the body) before dispatching to the handler.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook delivery, capturing `raw_body` and `x-shopify-hmac-sha256`.
2. Attacker replays the same `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the same shared `api_secret_key` [7](#0-6) .
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and the attacker-controlled body, and (per documented usage) performs shop-scoped work keyed on this unauthenticated value [5](#0-4) .
