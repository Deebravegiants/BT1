### Title
Permanent freezing of escrowed intent funds when the beneficiary address is blacklisted by the input/fee token - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentsBase._withdraw` (used by both cross-chain settlement via `onAccept` and same-chain cancellation) pushes escrowed tokens directly to a fixed `beneficiary` address derived from the `Order` (`order.user`) or the solver's address using `IERC20.safeTransfer`. If the escrowed token (e.g. USDC) or the fee token implements an address blacklist and the beneficiary is blacklisted after the order/commitment is created, every settlement attempt reverts permanently, freezing the escrowed funds with no recovery path.

### Finding Description
In `evm/src/apps/intentsv2/IntentsBase.sol` at `_withdraw`: [1](#0-0) 
tokens are transferred with `IERC20(token).safeTransfer(beneficiary, amount)` to a `beneficiary` decoded straight from the `WithdrawalRequest.beneficiary` field, and the accrued relayer/protocol fee token is likewise pushed via `safeTransfer(beneficiary, fees)`: [2](#0-1) 

This beneficiary is fixed once the `Order` is created — for refunds/cancels it's `order.user` (baked into the commitment hash `keccak256(abi.encode(order))`), and for fills it's the solver address supplied in the `WithdrawalRequest` built from `msg.sender` at fill time: [3](#0-2) [4](#0-3) 

Cross-chain settlement is delivered by the ISMP host via `onAccept`, invoked through `EvmHost.dispatchIncoming`: [5](#0-4) 
When the low-level `.call` to `onAccept` fails (e.g. because `safeTransfer` reverts on a blacklisted recipient), the host deletes the request receipt "so that it can be retried" and returns. However, retrying does **not** help here: the beneficiary address is immutable in the message body/commitment, so every subsequent delivery attempt will hit the exact same reverting `safeTransfer` call. There is no mechanism in `IntentsBase`/`ExtrinsicIntents`/`IntrinsicIntents` to redirect the beneficiary, pull-pattern the withdrawal, or otherwise recover the escrow if the designated recipient becomes blacklisted by the escrowed token or the fee token.

This differs from `HyperFungibleToken`/`WrappedHyperFungibleToken`, which mint tokens to the recipient on success or re-mint to the sender on timeout — a blacklist on the underlying ERC20 mint call is a separate consideration there, but the intents flow specifically moves *pre-escrowed, real* collateral directly to a hard-coded address with no fallback, and a single reverting transfer aborts the entire settlement (all input tokens in the order, plus the accrued fee), not just the affected token.

### Impact Explanation
If `order.user` (refund/cancel beneficiary) or the filling solver's address is later blacklisted by the escrowed token or the Hyperbridge fee token (both commonly implemented with USDC or similar compliance-gated stablecoins), the entire `RedeemEscrow`/`RefundEscrow` settlement for that order permanently reverts. The escrowed input tokens (and the transaction fee token component) become permanently frozen inside the gateway contract with no path to recovery, since:
- The beneficiary is embedded in the order commitment and/or fixed at fill time and cannot be changed post-hoc.
- Unlike `Pool.removeCollateral`'s liquidation escape hatch in the original report, there is no alternate actor or path (e.g., liquidation, admin sweep to a different address) that can extract the escrow to an unblacklisted account.
- `EvmHost.dispatchIncoming`'s retry mechanism cannot resolve this because retries replay the same deterministic revert.

This is a concrete permanent freezing of user/solver funds, meeting the High severity bar.

### Likelihood Explanation
Requires only that the escrowed token (or Hyperbridge's fee token) supports blacklisting (realistic for USDC-based pools, which are explicitly a supported asset class for this gateway) and that the specific `order.user` or solver address is later blacklisted — an externally triggered, not protocol-controlled, event, but plausible over the lifetime of any order given compliance actions are outside the protocol's control. No malicious actor needs to be involved; a single already-placed order with a subsequently sanctioned/blacklisted address is enough to lock those funds forever.

### Recommendation
Avoid unconditional push transfers to a beneficiary baked into the commitment. Options:
- Convert `_withdraw` to a pull-based/claim pattern: on settlement, credit an internal balance mapping for the beneficiary, and let the beneficiary (or a designated proxy) call a separate `claim(token)` function to pull funds, isolating a reverting transfer to only that specific claim rather than blocking the whole settlement/order.
- Wrap the `safeTransfer` calls in a try/catch (or a low-level call check) so that a failing transfer for one beneficiary escrows the funds into a fallback holding balance instead of reverting the entire withdrawal, and allow the affected party to specify an alternate receiving address (e.g. via a signed message) to sweep from the fallback balance.
- At minimum, allow `order.user` to update the beneficiary address for refunds (similar to the original report's "allow specifying a `to` address" recommendation) before the blacklisting occurs, or provide a governance/admin sweep for stuck escrow tied to blacklisted beneficiaries after a timeout.

### Proof of Concept
1. User places a cross-chain order via `IntentGatewayV2.placeOrder`, escrowing USDC as input; `order.user = alice`.
2. Alice's address is later blacklisted by USDC (external compliance action).
3. Order expires unfilled; Alice or anyone (post-deadline) calls `cancelOrder` on the destination chain, which dispatches `RefundEscrow` to the source chain: [6](#0-5) 
4. On the source chain, the relayer delivers the message; `EvmHost.dispatchIncoming` calls `onAccept`, which routes to `_withdraw` with `beneficiary = alice`: [7](#0-6) 
5. `IERC20(USDC).safeTransfer(alice, amount)` reverts because `alice` is blacklisted, causing `onAccept` to fail; `EvmHost.dispatchIncoming` deletes the receipt "so it can be retried," but every future relayer resubmission replays the identical revert.
6. The escrowed USDC is permanently stuck in the `IntentGatewayV2` contract, with no mechanism to redirect it to an unblacklisted address.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
