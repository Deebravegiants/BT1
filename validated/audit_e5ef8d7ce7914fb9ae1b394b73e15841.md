## Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then immediately reads the `shop-domain` header — which is not part of the signed material — and forwards it unverified to the app's handler as the tenant identifier for the event.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop` is read straight from a separate header with no cryptographic binding to the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC (over body only) and then dispatches the handler using `request.shop` taken directly from the unauthenticated header: [3](#0-2) 

`HmacValidator.validate` computes the digest exclusively from `verifiable_query.to_signable_string`, confirming the shop field never enters the signed string: [4](#0-3) 

The broken identity binding, stated as an equality that should hold but doesn't:

`shop authenticated by HMAC == shop delivered to the app's WebhookMetadata.shop`

Only the raw JSON body is authenticated; the `shop-domain` header used to attribute the event to a tenant is not. The gem's own documentation instructs integrators to key merchant-scoped work directly off this unauthenticated field: [5](#0-4) 

### Impact Explanation
An unprivileged attacker who has installed the app on their own store (an ordinary, unprivileged merchant relationship with the app — not a privileged account) receives genuine, correctly HMAC-signed webhook deliveries for their own shop. Because the signature covers only `@raw_body` and never the `shop-domain` header, the attacker can replay that same signed body to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. The HMAC check in `Registry.process` still passes (it only re-hashes the body), and the handler receives `WebhookMetadata` claiming the event originated from the victim shop, causing the app to record/act on data (e.g. `orders/create`, `app/uninstalled`, GDPR topics) attributed to a tenant the attacker does not control. This is a cross-tenant impersonation/data-injection primitive rooted entirely in this gem's authentication boundary.

### Likelihood Explanation
Any app developer who follows the gem's documented pattern (`data.shop` as the tenant key, as shown in `docs/usage/webhooks.md`) is exposed. Exploitation requires no secrets beyond a normal app install (attacker owns/controls a legitimate store, generating authentic signed webhook bodies), and only a header value needs to be changed on replay — well within reach of an unprivileged internet-capable actor able to send arbitrary HTTP requests to the app's public webhook endpoint.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header value in the signable string used for HMAC validation, or otherwise cryptographically bind the shop claim to the payload before it is exposed via `WebhookMetadata#shop`, so that `Registry.process` rejects any request where the authenticated shop and the header-reported shop diverge.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H = HMAC_SHA256(client_secret, B)`.
2. Attacker resends the exact same body `B` and the exact same `H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`= B`) and succeeds because `B` and `H` are unchanged.
4. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: B, ...)`, causing the app to process/store data as if it came from `victim-shop`, despite the attacker never having access to `victim-shop`'s credentials.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
