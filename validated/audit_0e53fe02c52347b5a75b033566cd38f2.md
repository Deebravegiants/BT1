Based on my analysis, the strongest analog to the reported bug class ("a field acted on but not covered by the HMAC") is confirmed in the webhook processing path.

### Title
Webhook `shop-domain` header is trusted and dispatched to handlers without being covered by the HMAC signature, enabling cross-tenant webhook confusion - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, excluding the `shop-domain`, `topic`, `api-version`, and `webhook-id` headers from the HMAC-covered content. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC over the body alone and then passes the unauthenticated `request.shop` value straight to the host application's webhook handler as the identity of the tenant that the payload belongs to.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over whatever `to_signable_string` returns and compares it to the `hmac` field using `Context.api_secret_key`: [1](#0-0) 

For webhooks, `to_signable_string` is defined to be only the raw body: [2](#0-1) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from HTTP headers with no cryptographic binding to the body or the HMAC: [3](#0-2) 

`Registry.process` only checks HMAC validity, then forwards the unauthenticated `request.shop` into the handler's `WebhookMetadata` as if it were verified: [4](#0-3) 

Because `Context.api_secret_key` is a single, app-wide secret shared across every shop that installs the app (it is not per-shop), any two webhook deliveries to the same app — regardless of which shop triggered them — are signed with the same key. An attacker who controls a shop where the app is installed (an "unprivileged internet user" from the target app's perspective, since they only need to install the app on their own store) can:
1. Trigger/capture a legitimate webhook delivery to their own shop, obtaining a `(raw_body, hmac)` pair that is valid under `Context.api_secret_key`.
2. Replay that exact `raw_body` and `hmac` to the same app's webhook endpoint, but substitute the `X-Shopify-Shop-Domain` header with a victim shop's domain.
3. Because `shop` is not part of `to_signable_string`, the HMAC check in `Registry.process` still passes, and the handler receives `WebhookMetadata` claiming the (attacker-controlled) body belongs to the victim shop.

This breaks the identity binding `shop-domain-header == shop-that-produced-this-body`, which host applications reasonably assume holds once `Registry.process` succeeds (the library's whole purpose is to authenticate webhook shop/topic/body as a unit). Applications that key persistence, deduplication, tenant-scoped side effects, or `customers/redact`/`shop/redact` compliance actions off `WebhookMetadata#shop` without independent verification (which the gem's own docs do not instruct them to add) can have attacker-chosen data attributed to an arbitrary victim shop.

### Impact Explanation
This satisfies the "cross-tenant access" Critical impact bucket: a payload/tenant binding that the gem is responsible for verifying (webhook authenticity) can be forged to attribute one shop's data to another shop, without requiring the attacker to possess the app's `client_secret`, an access token, or any privileged account — only the ability to install the app on a shop they control (a normal, expected, low-privilege interaction) and to send arbitrary HTTP requests to the app's public webhook endpoint.

### Likelihood Explanation
Reachability is direct and requires no special conditions: any consumer of `ShopifyAPI::Webhooks::Registry.process` that exposes a webhook endpoint is affected, since HMAC validation always uses `Request#to_signable_string`, which unconditionally excludes shop, topic, and webhook id. The prerequisite (installing the app on an attacker-controlled shop and observing one legitimate webhook) is realistic for any public or freely-installable app.

### Recommendation
Bind the identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) into the value that is HMAC-verified — e.g., include them in the canonical signable string, or independently verify `shop` against a separately-authenticated source (such as a stored session/access token lookup) before trusting it in `WebhookMetadata`. At minimum, document prominently that `WebhookMetadata#shop` is not authenticated by the HMAC and must not be used as a sole tenant identifier for state-changing actions.

### Proof of Concept
```ruby
require "shopify_api"

ShopifyAPI::Context.setup(
  api_key: "key", api_secret_key: "shared_app_secret",
  host: "example.com", scope: [], is_embedded: false, is_private: false, api_version: "2024-01"
)

body = '{"id":1,"note":"attacker controlled"}'
hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), "shared_app_secret", body)
)

# Step 1: attacker captures this (body, hmac) pair from a webhook delivered to
# their own shop "attacker-shop.myshopify.com" (legitimately signed by Shopify
# using the app's single shared api_secret_key).

# Step 2: attacker replays it against the app's webhook endpoint, substituting
# the shop-domain header for the victim shop.
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => hmac,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not covered by HMAC
  "x-shopify-webhook-id" => "forged-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HMAC validation succeeds (it only checks `body`), and the registered handler
# receives WebhookMetadata with shop: "victim-shop.myshopify.com", even though
# the payload actually originated from the attacker's own shop.
```

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
