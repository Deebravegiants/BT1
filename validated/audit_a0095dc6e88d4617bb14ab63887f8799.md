Webhook shop-domain identity not bound to HMAC signature enables cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#hmac` is verified only against the raw JSON body of a webhook, while the `shop` value used to attribute the event to a tenant is taken from an unauthenticated header that is excluded from the signed content.

### Finding Description
The external report's bug class is "a value used for a critical decision is not bound by the same check that authenticates the request." In this gem, `Utils::HmacValidator.validate` authenticates a webhook by recomputing the HMAC over `verifiable_query.to_signable_string` and comparing it to the `hmac` field, using `Context.api_secret_key` (the app's single client secret, shared across every installed shop) [1](#0-0) .

For webhooks, `Request#to_signable_string` returns only `@raw_body`; it does not include the `shop`, `topic`, `webhook_id`, or `api_version` header values [2](#0-1) . The `shop` accessor is derived purely from the `x-shopify-shop-domain`/`shopify-shop-domain` header, which is never covered by the signature [3](#0-2) .

`Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant identity passed to the app's handler, with no separate check binding shop to the signed bytes: [4](#0-3) 

Because the HMAC secret is the app's `api_secret_key` and is identical for all shops using the app (not a per-shop secret), any `(raw_body, hmac)` pair that is valid for one shop's webhook remains cryptographically valid when the `shop-domain` header is swapped to name a different, victim shop — the signature check in `HmacValidator.validate_signature` only compares the digest of the body, so it cannot detect this substitution: [5](#0-4) .

This is precisely the identity-binding break the prompt calls out: "a field acted on but not covered by the HMAC" — here, `shop` is acted on (used to route/attribute the event) but not covered by the HMAC.

### Impact Explanation
An unprivileged internet user who can obtain (or generate) one legitimately HMAC-signed webhook body/signature pair — e.g., by installing the target app on their own store (many apps are publicly installable) and capturing a real webhook delivery — can replay that exact body and HMAC to the app's webhook endpoint while substituting the `shop-domain` header to name an arbitrary victim shop. `HmacValidator` will still validate because it never inspects the header, so `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop and treat the forged event as if it originated from that tenant [6](#0-5) . Depending on how the host app trusts this field (as most documented handler examples do — see `docs/usage/webhooks.md`), this can drive cross-tenant state changes: forged `app/uninstalled` or `shop/redact` events causing deletion of a victim shop's stored session/data, or forged order/product events being attributed to and processed under the wrong tenant's session/store. This matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Medium-to-High: the webhook endpoint is, by design, a public unauthenticated HTTP endpoint (the whole point of `HmacValidator` is to authenticate otherwise-anonymous POSTs), so the attacker only needs network access plus one legitimately-signed webhook body, which is trivial to acquire by installing the target app on an attacker-owned/test store when the app allows public installs. No merchant credentials, access tokens, or `client_secret` are needed.

### Recommendation
Include the tenant-identifying header (at minimum `shop`, ideally also `topic` and `webhook_id`) in the HMAC-signed content, or independently bind the verified `shop` to session/registration state (e.g., only accept the webhook if `shop` matches an existing registered session for that topic) rather than trusting the unauthenticated header outright. `Request#to_signable_string` should be changed to sign a canonical representation that incorporates these header values, and `Utils::HmacValidator`/`Webhooks::Request` should reject requests whose header-derived identity was not part of the signed payload.

### Proof of Concept
1. Attacker installs the vulnerable app on their own (attacker-controlled) shop `attacker.myshopify.com`, obtaining a valid session.
2. Shopify (or the attacker, replaying Shopify's own delivery) sends a real webhook to the app's callback URL:
   - Headers: `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: app/uninstalled`, `x-shopify-hmac-sha256: <valid HMAC over raw_body>`
   - Body: `{}` (or whatever Shopify sends for that topic)
3. Attacker captures the raw body and the `x-shopify-hmac-sha256` value.
4. Attacker replays the exact same body and HMAC header to the same endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (`@raw_body` only, per `lib/shopify_api/webhooks/request.rb:36-38`) using `Context.api_secret_key` — identical to step 2's secret — so validation succeeds.
6. `handler.handle(data: WebhookMetadata.new(shop: request.shop, ...))` is invoked with `shop = "victim-shop.myshopify.com"`, and the app processes an `app/uninstalled` (or other) event as if it came from the victim shop, even though the victim shop never sent it — a cross-tenant integrity violation stemming from the `shop` field being outside the HMAC's coverage.

          received_signature = verifiable_query.hmac
