### Title
Webhook HMAC verification does not bind the `shop`, `topic`, or `webhook_id` headers, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a successful HMAC check as proof that the entire webhook request — including which shop and topic it belongs to — came from Shopify. In reality the HMAC only covers the raw request body; the `shop`, `topic`, `webhook_id`, and `api_version` values are read straight from unauthenticated HTTP headers and handed to the handler unmodified.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are all read from headers that are never part of the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e. the raw body only) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` uses that same result to gate dispatch, then builds `WebhookMetadata` directly from the unauthenticated header-derived fields (`request.shop`, `request.topic`, `request.webhook_id`, `request.api_version`) and passes it to the app-registered handler: [4](#0-3) 

The documentation explicitly tells integrators that `process` "will verify the request did indeed come from Shopify," implying the whole request, including the shop attribution, is authenticated: [5](#0-4) 

This is the same bug class as the report: an identity-relevant field (`contractor`/signer in the original; here `shop`/`topic`/`webhook_id`) is acted upon by downstream logic without being covered by the authentication check (HMAC), so the equality `bytes verified == bytes used to authorize the action` does not hold — the verified bytes are `raw_body` only, but the bytes used to attribute the webhook to a tenant are the unauthenticated headers.

### Impact Explanation
Since the HMAC is computed with the app's single shared `api_secret_key` and does not bind the body to a specific shop or topic, any body+HMAC pair that was legitimately generated by Shopify for *some* installation of the app (e.g. the attacker's own shop, which they fully control after installing the app) remains valid when replayed with different `x-shopify-shop-domain`, `x-shopify-topic`, and `x-shopify-webhook-id` header values. This lets a malicious installer attribute arbitrary (attacker-chosen) webhook topic/shop metadata to a body they legitimately captured, causing the host application's handler to process data under another tenant's identity — a cross-tenant confusion, which falls under the "Critical - cross-tenant access" bucket.

### Likelihood Explanation
Exploitation requires the attacker to have captured one genuine `(raw_body, hmac)` pair, which is trivially achievable by any actor able to install the app on their own shop (a normal, low-privilege action, not requiring the app's `client_secret` or any leaked credential). From there, replaying the same raw body with rewritten headers against the app's public webhook endpoint requires no further authentication.

### Recommendation
Include the shop domain, topic, and (if used for idempotency/dispatch) webhook id in the HMAC-signed payload, or otherwise re-verify that the `shop` header value matches a shop the app has an active session/installation for before dispatching to a handler. At minimum, update `to_signable_string` (or add a separate binding check in `Registry.process`) so the verified bytes cover every field the handler relies on for tenant attribution, and correct the documentation so it does not claim the entire request (rather than just the body) is verified.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw POST body and the `x-shopify-hmac-sha256` header Shopify sent.
2. Attacker replays the exact same body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and/or a different `x-shopify-topic`.
3. `HmacValidator.validate` succeeds because it only checks the (unmodified) body against the (unmodified) HMAC: [6](#0-5) 
4. `Registry.process` dispatches the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: <attacker-chosen>, ...)`, and the host application acts on attacker-controlled tenant/topic data believing it was authenticated by Shopify.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
