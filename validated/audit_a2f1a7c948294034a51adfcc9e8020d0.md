## Title
Webhook shop/topic identity not covered by HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop`, `topic`, and `webhook_id` values used to route and process the webhook are read directly from unauthenticated HTTP headers. `Webhooks::Registry.process` validates only the body's HMAC and then dispatches to the handler using these unauthenticated header values, breaking the equality "the entity whose bytes are HMAC-verified" == "the entity attributed to the processed event."

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, and `webhook_id` are pulled straight from headers with no cryptographic binding to the signature: [2](#0-1) 

`Webhooks::Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` (which calls `to_signable_string`, i.e. the body only), then immediately trusts `request.shop` and `request.topic` to build `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` only ever authenticate `verifiable_query.to_signable_string` against the app's `api_secret_key`: [4](#0-3) 

Because the app's `client_secret`/`api_secret_key` is shared across every shop that has installed the app (it is not a per-shop secret), any shop that installs the app can legitimately receive a genuine `(raw_body, hmac)` pair from Shopify. That pair remains valid regardless of which `shopify-shop-domain` / `shopify-topic` header values are attached to it, because those headers are never part of the signed content. An attacker who controls one installed shop can therefore replay a validly-HMAC'd webhook body to the app's webhook endpoint while substituting a different shop's domain in the `shopify-shop-domain` header (and/or a different topic), and `Registry.process` will accept it as authentic and dispatch it to the handler attributing the data to the spoofed shop.

This mirrors the reported bug class directly: just as the Merkle proof was checked without binding it to `questID`/`period`, here the HMAC proof is checked without binding it to `shop`/`topic`, so "shop authenticated" (implicitly, whoever holds a valid secret-derived HMAC) diverges from "shop attributed to the event" (the header value the handler trusts).

### Impact Explanation
This breaks the shop/tenant identity binding used by any host application that stores or acts on webhook data keyed by `WebhookMetadata#shop` (i.e. the normal usage pattern documented for this gem). An attacker-controlled shop can forge webhook events that the host app will process as belonging to a different, victim shop, resulting in cross-tenant data confusion/injection — classified as cross-tenant access under the impact criteria.

### Likelihood Explanation
Requires the attacker to control at least one shop that has installed the target app (a realistic bar for a public app) and the ability to send raw HTTP requests to the app's public webhook endpoint. No access token, `client_secret`, or privileged access is required — only observation of legitimately delivered webhook traffic to their own shop.

### Recommendation
Include `shop` (and ideally `topic`) as part of the HMAC-verified signable content, or otherwise cryptographically bind the header-derived `shop`/`topic` values to the verified payload before they are trusted by `Registry.process` / passed to `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a real webhook: raw body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's shared secret), header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the identical `(B, H)` pair to the app's webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `H` against `B` — this still passes because `to_signable_string` never includes the shop header [1](#0-0) .
4. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` [5](#0-4) , causing the host app to process attacker-controlled data under the victim shop's identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
