The `report`-style re-entrancy report doesn't map to anything in this Ruby gem (no cross-contract callback pattern exists here), but the underlying bug class — "a field acted on but not covered by the HMAC" — has a direct, concrete analog in the webhook verification path.

### Title
Webhook `shop`/`topic`/`webhook_id` fields are trusted for tenant routing but are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from HTTP headers and are never included in the HMAC-signed content. `Registry.process` validates only the body's HMAC and then forwards the unauthenticated `shop` header value straight to the host application's handler for tenant identification.

### Finding Description
`Request#to_signable_string` is defined as `@raw_body` only [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are pulled from headers via `shopify_header` [2](#0-1) . `Registry.process` validates HMAC using `Utils::HmacValidator.validate(request)`, which calls `to_signable_string` (body only), then immediately builds `WebhookMetadata` using `request.shop`, `request.topic`, and `request.webhook_id` taken from the unauthenticated headers, passing it to the host app's handler [3](#0-2) . `WebhookMetadata.shop` is a plain `String` field intended for tenant-scoped dispatch by the handler [4](#0-3) .

This breaks the identity binding: `shop trusted by handler for tenant routing` ≠ `shop cryptographically bound in the HMAC`. The gem's `HmacValidator.validate` only proves "this body was signed with the app secret"; it proves nothing about which shop's header value accompanies it, since the header is outside the signed string [5](#0-4) .

### Impact Explanation
An unprivileged user who legitimately installs the app on their own store (or otherwise legitimately triggers/captures one valid webhook delivery, body+HMAC pair, from Shopify for their own shop) can replay that exact body and HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or topic/webhook-id) header for a victim shop domain. Because the signature check only covers `@raw_body`, the forged request passes `HmacValidator.validate` and the host app's handler receives `WebhookMetadata` claiming it originated from the victim shop. Any host app that uses `data.shop` for tenant-scoped side effects (e.g., updating per-shop records, processing `app/uninstalled`, `customers/redact`, `shop/redact`, order/customer state) can be manipulated into taking action against, or associating attacker-supplied data with, a different merchant's tenant — a cross-tenant integrity issue.

### Likelihood Explanation
Exploitability requires only a body+HMAC pair the attacker can legitimately obtain (e.g., by installing the app themselves and observing/capturing one of their own store's webhook deliveries), and no access to `api_secret_key`, access tokens, or any privileged credential of the victim. This is squarely within the scope of an "unprivileged internet user" with no special access, since headers on an inbound HTTP request are fully attacker-controlled independent of the signed body.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (in addition to the body) in the HMAC-signed content, or otherwise cryptographically bind them (e.g., verify the resolved shop domain against a shop the host app knows to be genuinely subscribed to that specific webhook/HMAC), before exposing `WebhookMetadata` to handlers. At minimum, document prominently that `shop`/`topic`/`webhook_id` are unauthenticated and must be independently validated by host applications against known/subscribed shops before being used for any tenant-scoped action.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and triggers a real webhook (e.g., `orders/create`) — Shopify sends a request with a valid `X-Shopify-Hmac-Sha256` computed over the JSON body using the app's real `client_secret`.
2. Attacker captures the raw body and HMAC header from that delivery.
3. Attacker resends the identical body + HMAC to the app's webhook endpoint, changing only `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` (and optionally the topic/webhook-id headers).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `to_signable_string` (`@raw_body`), so validation succeeds [3](#0-2) .
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and performs tenant-scoped processing believing the data originated from the victim shop.
