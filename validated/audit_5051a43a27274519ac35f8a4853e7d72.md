### Title
Recompute of stale delegation stake in `Stakes::upsert_stake_delegation` can desynchronize aggregate `delegated_stakes`/`VoteAccounts` stake totals from actual per-account stakes - ([File: runtime/src/stakes.rs])

### Summary
This is the same bug class as the reported VotingEscrow issue: a "global accumulator" (here, per-validator `delegated_stakes` and `VoteAccounts` stake totals) is maintained incrementally via deltas computed by *re-deriving* an old value at update time, instead of using the exact value that was originally added to the accumulator. If the re-derivation function's inputs (feature flags controlling stake math) differ from what was in effect when the value was originally added, the "old" value used to compute the delta is wrong, and the aggregate drifts away from the true sum of individual stakes — exactly the "recompute old point, then apply delta" pattern described in the VotingEscrow report.

### Finding Description
`Stakes<StakeAccount>::upsert_stake_delegation` [1](#0-0)  updates the running per-validator stake accumulators (`delegated_stakes` and `vote_accounts` stake) whenever a stake account is overwritten. When an existing entry is replaced (`Some(old_stake_account)` branch), it does **not** reuse the stake value that was actually added the last time this account was upserted. Instead it recomputes the "old" effective stake from scratch:

```
let old_stake = delegation_effective_stake(
    old_delegation,
    self.epoch,
    &self.stake_history,
    new_rate_activation_epoch,
    use_fixed_point_stake_math,
);
``` [2](#0-1) 

and then applies the delta between the freshly-computed `stake` (new) and this freshly-recomputed `old_stake`:
```
if voter_pubkey != old_voter_pubkey || stake != old_stake {
    self.sub_delegated_stake(&old_voter_pubkey, old_stake);
    self.add_delegated_stake(voter_pubkey, stake);
    self.vote_accounts.sub_stake(&old_voter_pubkey, old_stake);
    self.vote_accounts.add_stake(&voter_pubkey, stake);
}
``` [3](#0-2) 

`new_rate_activation_epoch` and `use_fixed_point_stake_math` are both passed in per-call from the caller's live feature-set snapshot (`check_and_store` passes them straight through) [4](#0-3) , and `delegation_effective_stake` dispatches to either `stake_v2` or the legacy `stake()` warmup/cooldown math depending on the `use_fixed_point_stake_math` flag [5](#0-4) . The two math paths (fixed-point vs legacy floating "effective stake" activation/deactivation math) are not guaranteed to produce bit-identical results for the same delegation and epoch.

This means: if the value that was actually added into `delegated_stakes`/`vote_accounts` for this stake account at its previous upsert was computed under one `use_fixed_point_stake_math` setting (or `new_rate_activation_epoch` value), but a later upsert of the *same* stake account (in the same cached `self.epoch`) recomputes "old_stake" using a *different* setting (e.g., because the `upgrade_bpf_stake_program_to_v5_1` / fixed-point-math feature activated between the two stores, or `new_warmup_cooldown_rate_epoch` changed), the subtracted `old_stake` will not equal what was actually added previously. The aggregate accumulator (`delegated_stakes` sum and `VoteAccounts` stake) then diverges from the true sum of individually-computed effective stakes — precisely the "sum of accounts != global accumulator" defect described in the report, just applied to Agave's stake/vote-account aggregate cache rather than veALCX's global bias.

### Impact Explanation
`delegated_stakes` and `VoteAccounts` stake totals computed by `StakesCache` feed directly into consensus-critical and reward-critical calculations: vote-weight/consensus fork-choice via `EpochStakes`, and stake-weighted reward point calculations (`calculate_reward_points_partitioned`, `calculate_block_reward`, `calculate_alpenglow_points`) which divide by `total_active_stake`/denominators derived from these caches [6](#0-5) . A drifted aggregate (versus the true per-account sum) means individual validators' computed reward shares no longer sum correctly against the true total delegated stake, which can result in over/under distribution of staking rewards and skewed effective-stake accounting used for consensus weighting — a value-loss/incorrect-distribution class issue, not merely cosmetic.

### Likelihood Explanation
This requires a change in `use_fixed_point_stake_math` or `new_warmup_cooldown_rate_epoch` to take effect *between* two upserts of the same stake account while `self.epoch` in the `Stakes` cache stays fixed (i.e., within processing of a single epoch's blocks, before/after a mid-epoch feature-flag transition is observed by different call sites, or across the exact epoch boundary where the cache's stored `epoch` hasn't yet been refreshed). Feature activation is not attacker-controlled in the general case (it's a network governance event), and the code includes a `refresh_delegated_stakes` mechanism seemingly meant to recompute stakes wholesale after such rate/math transitions, suggesting awareness of this general risk class. Reaching this exact stale-recompute path (rather than the bulk refresh path) requires the precise sequencing of an in-flight feature transition combined with mid-epoch account re-delegation, which is a narrow, non-attacker-triggerable window rather than a routinely reachable unprivileged-user bug — likelihood is low without further evidence that the two code paths (targeted upsert vs. `refresh_delegated_stakes`) can race or diverge in practice.

### Recommendation
Store the previously-applied effective stake value alongside (or instead of only) the raw delegation in the cache entry, so that on overwrite the code subtracts the *exact* amount that was actually added last time, rather than re-deriving it under potentially different math-mode/rate-activation parameters. Alternatively, guarantee (with an assertion/test) that `delegation_effective_stake` is invoked with identical `new_rate_activation_epoch`/`use_fixed_point_stake_math` parameters for both the add and subtract sides of every upsert within a given `Stakes.epoch`, and audit whether `refresh_delegated_stakes` is guaranteed to run atomically before any targeted upsert can observe a changed math mode.

### Proof of Concept
Conceptual reproduction (could not fully execute in this read-only review; needs a Devin session with test tooling to confirm empirically):
1. Construct a `Stakes<StakeAccount>` cache at a fixed `epoch`.
2. Upsert a stake account A with `use_fixed_point_stake_math = false`, capturing the `delegated_stakes` total for its validator.
3. Upsert stake account A again (same pubkey, same delegation fields) with `use_fixed_point_stake_math = true`, without changing `self.epoch`.
4. Compare the recomputed `old_stake` (legacy math) used for subtraction against the actual value that was added in step 2 (fixed-point math); if `Delegation::stake()` and `Delegation::stake_v2()` diverge for this delegation/epoch/history combination, the resulting `delegated_stakes` sum will not equal the sum of individually recomputed stakes for all cached accounts — reproducing the reported "sum of balances != global accumulator" defect.

    fn upsert_stake_delegation(
        &mut self,
        stake_pubkey: Pubkey,
        stake_account: StakeAccount,
        new_rate_activation_epoch: Option<Epoch>,
        use_fixed_point_stake_math: bool,
    ) {
        debug_assert_ne!(stake_account.lamports(), 0u64);
        let delegation = stake_account.delegation();
        let voter_pubkey = delegation.voter_pubkey;
        let stake = delegation_effective_stake(
            delegation,
            self.epoch,
            &self.stake_history,
            new_rate_activation_epoch,
            use_fixed_point_stake_math,
        );
        match self.stake_delegations.insert(stake_pubkey, stake_account) {
            None => {
                self.add_delegated_stake(voter_pubkey, stake);
                self.vote_accounts.add_stake(&voter_pubkey, stake);
            }
            Some(old_stake_account) => {
                let old_delegation = old_stake_account.delegation();
                let old_voter_pubkey = old_delegation.voter_pubkey;
                let old_stake = delegation_effective_stake(
                    old_delegation,
                    self.epoch,
                    &self.stake_history,
                    new_rate_activation_epoch,
                    use_fixed_point_stake_math,
                );
                if voter_pubkey != old_voter_pubkey || stake != old_stake {
                    self.sub_delegated_stake(&old_voter_pubkey, old_stake);
                    self.add_delegated_stake(voter_pubkey, stake);
                    self.vote_accounts.sub_stake(&old_voter_pubkey, old_stake);
                    self.vote_accounts.add_stake(&voter_pubkey, stake);
                }
            }
        }
    }

#[inline]
pub(crate) fn delegation_effective_stake<T: StakeHistoryGetEntry>(
    delegation: &Delegation,
    epoch: Epoch,
    history: &T,
    new_rate_activation_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    if use_fixed_point_stake_math {
        delegation.stake_v2(epoch, history, new_rate_activation_epoch)
    } else {
        #[allow(deprecated)]
        delegation.stake(epoch, history, new_rate_activation_epoch)
    }
}
