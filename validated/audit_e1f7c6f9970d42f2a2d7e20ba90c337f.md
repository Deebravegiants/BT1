### Title
Webhook `shop` (and `topic`/`webhook-id`/`api-version`) identity fields are not covered by the HMAC signature, allowing cross-tenant spoofing of webhook metadata - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates only that the HMAC over the raw request body matches the app's `client_secret`; it does not bind the `shop-domain`, `topic`, `webhook-id`, or `api-version` HTTP headers to that signature before passing them, unauthenticated, to the merchant's `WebhookHandler` as the tenant identity (`WebhookMetadata#shop`).

### Finding Description
`Registry.process` performs exactly one authenticity check: [1](#0-0) 

The HMAC validation itself only ever signs `@raw_body`: [2](#0-1) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers with no cryptographic binding to the HMAC digest: [3](#0-2) 

`Utils::HmacValidator.validate` confirms this — the signable string used for comparison is `to_signable_string` (the raw body only), and `verifiable_query.hmac` is compared against a digest computed solely over that body: [4](#0-3) 

`process` then forwards the unauthenticated `request.shop` header value directly into `WebhookMetadata`, which apps use as the tenant identifier to route data/select credentials: [5](#0-4) [6](#0-5) 

This is the same class of bug as the reported analog: a field that the caller/handler acts on as an authenticated identity (`shop`) is not covered by the integrity check (HMAC), exactly like Solmate's `safeTransferFrom` returning success without verifying the piece of state (codesize) the caller relies on. Here the broken equality is:

`hmac_signed_bytes (raw_body) != identity_bytes_trusted_by_handler (shop-domain header)`

Because Shopify computes the HMAC only over the JSON body (which is often identical or near-identical across different shops for the same topic, e.g. `shop/redact`, `customers/data_request`, or any webhook with an empty/templated payload), a valid `(body, hmac)` pair obtained for one shop can be replayed with a forged `x-shopify-shop-domain` header for a different shop, and `Registry.process` will accept it as valid and hand the attacker-controlled `shop` value to the app's handler.

### Impact Explanation
If a host application uses `WebhookMetadata#shop` as the tenant key (a documented, expected usage pattern per `docs/usage/webhooks.md`) to look up sessions/access tokens or to attribute data (e.g., GDPR `customers/redact`, `shop/redact` mandatory webhooks, or order/product webhooks with generic/empty bodies), an attacker who can obtain one legitimately-signed webhook body+HMAC pair (e.g., from their own installed/dev store) can replay it with a different `shop-domain` header to make the gem report a different shop as the source. This crosses the tenant boundary the HMAC check is meant to enforce and can lead to cross-tenant data corruption/exfiltration or wrongful GDPR redaction execution against the wrong shop.

### Likelihood Explanation
Exploitability depends on the webhook body being reusable/predictable independent of the shop (true for topics with empty or template-fixed bodies, and generally the header separation applies to every webhook regardless of body). No secret material is required — only HTTP access to the app's public webhook endpoint and one legitimately obtained `(raw_body, hmac)` sample, which any developer with their own installed app instance can generate. This keeps the attack within the "unprivileged internet user" threat model.

### Recommendation
Include the `shop-domain`, `topic`, `webhook-id`, and `api-version` header values in the HMAC-signed material (or otherwise cryptographically bind them, e.g., by hashing headers+body together and validating against a signature that covers all fields), so `Registry.process` cannot be tricked into treating attacker-supplied header values as authenticated identity data.

### Proof of Concept
1. Attacker installs the app on their own dev shop `attacker.myshopify.com` and triggers a webhook whose body is fixed/empty for a given topic (e.g., `shop/redact` or any topic emitted with `{}`/templated JSON).
2. Attacker records the resulting `x-shopify-hmac-sha256` value Shopify computed over that body using the app's real `client_secret`.
3. Attacker POSTs to the app's webhook endpoint with the same `raw_body` and same `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim.myshopify.com` and desired `x-shopify-topic`/`x-shopify-webhook-id`.
4. `Utils::HmacValidator.validate` succeeds (per `lib/shopify_api/utils/hmac_validator.rb:26-31`, only the body is checked) and `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-199`) calls the handler with `WebhookMetadata(shop: "victim.myshopify.com", ...)`, even though the request never came from Shopify on behalf of `victim.myshopify.com`.
