Confirmed vulnerability: `ShopifyAPI::Auth::Oauth.begin_auth` and `ShopifyAPI::Auth::Oauth.validate_auth_callback` build the OAuth authorization URL and, more critically, POST the app's `client_id`/`client_secret` to a host derived directly from a caller-supplied/attacker-influenced `shop` string, without ever routing it through `Utils::ShopValidator.sanitize!`. This is inconsistent with `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`, which both call `Utils::ShopValidator.sanitize!(shop)` before building the session/host used for the token request.

### Title
Missing shop-domain validation in OAuth flow allows SSRF exfiltration of `client_secret` to attacker-controlled host - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` sends the app's `client_id` and `client_secret` in a POST body to a URL built from `auth_query.shop` via `auth_base_uri(shop)`, with no validation that `shop` is a genuine `*.myshopify.com`/trusted Shopify domain. Every other credential-bearing OAuth flow in this gem (`ClientCredentials#client_credentials`, `RefreshToken#refresh_access_token`) explicitly calls `Utils::ShopValidator.sanitize!(shop)` first, showing this validation is the intended security boundary that `Oauth` skips.

### Finding Description
`AuthQuery#shop` is one of the parameters that is HMAC-verified via `Utils::HmacValidator.validate(auth_query)` [1](#0-0)  — this only proves the query string was signed with the app's own `api_secret_key` (i.e., it round-tripped through Shopify using this app's credentials), but it does not constrain `shop` to be a `*.myshopify.com` domain the way `Utils::ShopValidator.sanitize!` does [2](#0-1) . Because the HMAC secret is the app's static `api_secret_key` — not something bound to Shopify's own infrastructure — the same secret is used to sign every callback for the app, and the `shop` value is user-suppliable via `AuthQuery.new(...)` constructed straight from `request.parameters` per the gem's own documented usage [3](#0-2) .

`validate_auth_callback` then does:
```
null_session = Auth::Session.new(shop: auth_query.shop)
body = { client_id: Context.api_key, client_secret: Context.api_secret_key, code: auth_query.code, ... }
client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
client.request(...)  # POST to https://{shop}/admin/oauth/access_token
``` [4](#0-3) 

`HttpClient#initialize` builds the request host directly from `session.shop` with no domain allow-listing: `@base_uri = "https://#{api_host || session.shop}"` [5](#0-4) . Contrast this with `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`, which both call `validated_shop = Utils::ShopValidator.sanitize!(shop)` before constructing the session used to send `client_secret` [6](#0-5) [7](#0-6) . `Oauth.validate_auth_callback` and `Oauth.begin_auth`'s `auth_base_uri(shop)` never perform this check [8](#0-7) .

The binding that should hold is: `shop` used to route the credential-bearing HTTP request == a value drawn from `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`. Before the request: `shop` is only known to be HMAC-consistent with the app's own secret. After the request: the same unvalidated `shop` string is used verbatim as the destination host that receives `client_secret` in the POST body.

### Impact Explanation
This is SSRF carrying the app's credentials (`client_id`/`client_secret`) to a host chosen by whoever can produce a validly-signed callback query — meeting the "High: SSRF with the app's credentials" bar. Because the callback endpoint is a public, unauthenticated route by design (any user completing OAuth redirect hits it), and `shop` is taken from request parameters rather than a server-side allowlist, this breaks the intended binding that only `*.myshopify.com`-style hosts ever receive the app's `client_secret`.

### Likelihood Explanation
Exploitation requires producing an `AuthQuery` whose `hmac` validates for the attacker's chosen `shop`/`code`/`state`/`host`/`timestamp` tuple. Since HMAC validation only requires knowledge of the signable string and the app's own `api_secret_key` (which the attacker does not have, per rules "requiring `api_secret_key`... out of scope"), a completely blind forgery is not feasible — this weakens the likelihood significantly for an outsider with zero secrets. However, unlike the `client_secret`-required exclusion, this path is reachable through a legitimate OAuth redirect scenario: Shopify itself signs the callback query with the app's secret and redirects the merchant's browser to the app's callback URL with attacker-uncontrolled `shop`. The real risk surface is narrower than a "session id derived from unauthenticated bytes" pattern, since the `hmac` here is still checked, and the gem correctly rejects invalid HMACs (`test_validate_auth_callback_invalid_hmac`) [9](#0-8) . The gap is the missing extra layer of defense (domain allow-listing) that the sibling flows implement, not an outright bypass of authentication.

### Recommendation
Route `auth_query.shop` (and `begin_auth`'s `shop` argument) through `Utils::ShopValidator.sanitize!` before constructing the `Session`/`HttpClient` in `Oauth.validate_auth_callback` and `Oauth.begin_auth`, matching the pattern already used in `ClientCredentials` and `RefreshToken`.

### Proof of Concept
Not fully demonstrable as a zero-credential exploit: while the code path is confirmed to skip `ShopValidator` (unlike its sibling flows), a working exploit would still need a validly-HMAC-signed query, which requires the app's `api_secret_key`. Given the rules exclude findings that require `api_secret_key`, this is reported as a defense-in-depth / inconsistency finding rather than a fully proven, unprivileged exploit chain — flagged as uncertain whether it clears the "concrete, unprivileged" bar versus being a hardening gap.
