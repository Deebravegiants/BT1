### Title
Arbitrary `op.endpoint` call in `EmporiumUpgradeable.runAction` lets attacker drain any ERC20/ETH balance held by Emporium that is outside `circomData.erc20TokenAddresses` - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction` executes attacker-supplied `EmporiumOperation[]` via a raw low-level `op.endpoint.call{value: op.value}(op.callData)` with `op.endpoint` completely unconstrained to the tokens listed in `circomData.erc20TokenAddresses`. Because the balance-conservation loop (`balancesBefore`/`balancesAfter`, `handleOut`, `BalanceChangeShouldBePositive`) only iterates `circomData.erc20TokenAddresses`, an attacker can craft an op that calls `transfer` on any other ERC20 that Emporium happens to hold (e.g. stranded residue from a prior transaction) and send it straight to their own EOA, with zero accounting entry and zero UTXO minted.

### Finding Description
The broken equality: **tokens leaving `EmporiumUpgradeable` == `Σ(-deltaAmountChanges[i])` Hinkal sent to it this tx, for every token that actually left.** After the fix should hold, but for a token `tokenB ∉ circomData.erc20TokenAddresses`, the left side (`Z` tokens transferred out via the op) has no corresponding right-side term at all — `tokenB` is never read into `balancesBefore`/`balancesAfter`, never checked by `balanceDif >= slippageValues[i]` (`contracts/Hinkal.sol:110-114`), never checked by `BalanceChangeShouldBePositive` (`EmporiumUpgradeable.sol:142-144`), and never turned into a UTXO by `handleOut` (`EmporiumUpgradeable.sol:162-184`).

Code path:
- `EmporiumUpgradeable.runAction` (`EmporiumUpgradeable.sol:76-160`) decodes `EmporiumStack` from `circomData.externalActionData.externalActionMetadata`, which is fully attacker-controlled (the attacker crafts their own `CircomData` for their own transact call).
- With `stack.signerAddress == address(0)`, `verifyWallet` (`EmporiumUpgradeable.sol:302-316`) only marks `emporiumMessage` used and returns — **no EIP-712 signature is checked at all** in this "stateless" branch.
- The op loop (`EmporiumUpgradeable.sol:91-118`) then executes `op.endpoint.call{value: op.value}(op.callData)` for the "Stateless Interaction" branch with no restriction that `op.endpoint` be one of `circomData.erc20TokenAddresses`. The only filter is blocking the `callHinkalWallet`/`doSendToRelay` selectors, which is irrelevant to a plain `transfer` call.
- Because this call is made directly from `EmporiumUpgradeable`, calling `tokenB.transfer(attackerEOA, Z)` succeeds as an ordinary self-initiated transfer, moving `Z` tokens of `tokenB` from Emporium's balance to the attacker — regardless of whether `tokenB` appears anywhere in `circomData.erc20TokenAddresses`.
- `dimensionsCheck` (`contracts/HinkalHelper.sol:64-171`) and `formInputForCircom`/`formInputEmporiumMin` (`contracts/CircomDataBuilder.sol:134-161`) allow `circomData.erc20TokenAddresses.length == 0` for the Emporium external action, meaning the attacker can submit a minimal/trivial valid ZK proof (no real deposits, no nullifiers) that only commits to `emporiumMessage`, `timeStamp`, `calldataHash` — none of which constrain the semantics of `op.endpoint`/`op.callData`.
- `onlyAllowedRecipient` only checks that `msg.sender == Hinkal` calling into `runAction`; it does not constrain what `runAction` itself does internally.

Existing guards fail to catch this because they are all scoped to `circomData.erc20TokenAddresses`, and there is no on-chain or in-circuit constraint tying the set of tokens an op is allowed to touch to that array.

### Impact Explanation
Any real ERC20 (or ETH) balance sitting in `EmporiumUpgradeable` outside the current transaction's `erc20TokenAddresses` set — whether from a prior stranding bug, a fee-on-transfer/rounding residue, a direct mistaken/partial transfer, or funds momentarily in flight for another user's pending action — can be swept in full to an attacker EOA with a single, unauthenticated (`signerAddress = address(0)`), minimal-proof transaction. This is direct theft of protocol/in-flight user funds with zero balance-equation coverage and zero UTXO minted, matching the Critical category ("direct theft of shielded or in-flight user funds ... with no proof coverage"). The attack is fully repeatable for every token balance Emporium accumulates and costs the attacker only gas plus proof generation for a trivial zero-value CircomData.

### Likelihood Explanation
Preconditions: `EmporiumUpgradeable` must hold a nonzero balance of some ERC20/ETH not included in the attacker's chosen `erc20TokenAddresses` for that call (via stranding, rounding, or any residual deposit). Given this, the attack requires no privileged role, no wallet signature, and no interaction with any other user — the attacker crafts their own `CircomData`/`Dimensions`/`externalActionMetadata`, generates their own (potentially trivial, zero-amount) proof, and calls `Hinkal.transact` once. This is straightforward and repeatable each time Emporium accumulates a spare balance.

### Recommendation
Constrain `op.endpoint` calls inside `runAction` so they cannot move balances of tokens outside `circomData.erc20TokenAddresses`, e.g. by disallowing raw calls to addresses that are ERC20 contracts unless they're in the token list, or by re-checking Emporium's balance for every token it holds (not just the ones declared in `circomData.erc20TokenAddresses`) before/after the op loop and reverting on any unaccounted decrease. Alternatively, restrict stateless (`signerAddress == address(0)`) ops to a safelist of endpoints/selectors that cannot exfiltrate arbitrary token balances, and require `circomData.erc20TokenAddresses` to cover every token address referenced by `op.endpoint` in the ops array.

### Proof of Concept
1. Foundry test: deploy `EmporiumUpgradeable`, `Hinkal`, `HinkalHelper`, a real ERC20 `tokenB`. Directly mint/transfer `Z` tokenB into `EmporiumUpgradeable` (simulating stranded residue, consistent with the given precondition).
2. Build a `CircomData` with `erc20TokenAddresses = []` (or `[tokenA]`, unrelated to `tokenB`), `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionData.externalActionMetadata = abi.encode(EmporiumStack({signerAddress: address(0), ops: [EmporiumOperation({endpoint: tokenB, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attackerEOA, Z))})], ...}))`.
3. Generate a locally valid proof for this minimal/zero-amount CircomData (no nullifiers needed since `erc20TokenAddresses` is empty/unrelated) and call `Hinkal.transact(...)` as `attackerEOA`.
4. Assert: `tokenB.balanceOf(attackerEOA)` increases by `Z`; `tokenB.balanceOf(EmporiumUpgradeable)` decreases by `Z`; the emitted `UTXO[]`/`onChainCommitments` never reference `tokenB`; and no `require` in `Hinkal.sol` or `EmporiumUpgradeable.sol` (balance/slippage checks) reverted — proving the transfer is completely outside the balance-conservation equation.
