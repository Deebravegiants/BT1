### Title
Cross-chain intent settlement permanently bricked if a blacklisted address is set as the escrow beneficiary - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentsBase._withdraw()`, invoked from `ExtrinsicIntents.onAccept()` when a `RedeemEscrow`/`RefundEscrow` message is delivered, marks the order `finalize`d and then unconditionally uses `SafeERC20.safeTransfer` to send escrowed input tokens to the `beneficiary` decoded from the cross-chain message. If that token is a blacklist-capable stablecoin (e.g. USDC) and the beneficiary address is (or becomes) blacklisted, the transfer reverts and the entire `onAccept` call reverts, undoing the `_filled[body.commitment] = beneficiary` write as well. This mirrors the Axis Finance M-2 pattern where a single blacklisted counterparty (`pfBidder`) permanently bricks settlement because refund/payout logic is not separated from the finalize/settle step.

### Finding Description
`_withdraw` is the single settlement path for releasing an order's escrowed inputs, for both the `RedeemEscrow` (solver payout) and `RefundEscrow` (user refund) cases: [1](#0-0) 

Both are triggered exclusively through `ExtrinsicIntents.onAccept`: [2](#0-1) 

The beneficiary comes directly from the message body with no allow/blacklist check performed before the transfer:
- For `RedeemEscrow`, the beneficiary is the solver address that called `fillOrder` on the destination chain (`msg.sender` cast to `bytes32`), see `_fillCrossChain`'s dispatch of the redeem message. [3](#0-2) 
- For `RefundEscrow`, the beneficiary is `order.user`. [4](#0-3) 

Because `_filled[commitment]` is set inside the same call as the token transfer (not before, and not separated from it), any revert in the transfer loop reverts the whole `onAccept` transaction — the order is never marked finalized and the escrow can never be released: [5](#0-4) 

Once a cross-chain order is filled on the destination chain, `_filled[commitment]` there is set to the solver, permanently preventing any other solver from filling it or the destination-side cancellation path from re-triggering a refund: [6](#0-5) 

So once `_fillCrossChain` executes and the `RedeemEscrow` message is dispatched, there is exactly one path back to the source chain to release the escrow — `onAccept` → `_withdraw`. If the solver address hardcoded as beneficiary in that message is blacklisted on the escrowed input token (which may happen after the fill, since blacklisting is enforced by the token issuer at transfer time, not at fill time), every future relayer delivery attempt of that same message will re-execute `_withdraw` and revert identically. There is no retry-with-different-beneficiary, no partial split of "refund vs payout" logic, and no alternate exit: the user already lost the destination-chain output tokens to the solver, and the solver can never claim the escrowed input tokens because the transfer always reverts. The escrow is permanently frozen in the gateway contract.

This is structurally identical to the Sherlock M-2 report: `AuctionHouse.settle()` does the blacklisted-partial-fill-bidder payout inline with the finalize step, so a blacklisted address bricks settlement for everyone; here `_withdraw` does the blacklisted-solver/user payout inline with the `_filled` finalize step, bricking that order's escrow permanently (with no way to split out a safe finalize from an unsafe transfer).

### Impact Explanation
Permanent freezing of the order's escrowed input tokens. The user has already surrendered their escrowed tokens (locked at `placeOrder` time) and, on the destination chain, has already received/lost value to the solver (order is `_filled` there), so there is no cancellation path back. On the source chain, the `RedeemEscrow` message can never be successfully applied because the transfer to the blacklisted beneficiary always reverts, so `_orders[commitment][token]` balances and `_filled[commitment]` can never update — the tokens are stuck in the `IntentGatewayV2`/`ExtrinsicIntents` contract forever, with no governance sweep path (dust-sweep only handles protocol dust, not live per-order escrow, see `_sweepDust`). This qualifies as concrete, permanent freezing of user/solver funds reachable from a single relayed cross-chain fill message — a Medium/High severity issue by the same reasoning as the referenced Sherlock report.

### Likelihood Explanation
Reachable by any solver filling a cross-chain order with a blacklist-capable input token (e.g., USDC) — a single unprivileged `fillOrder` transaction on the destination chain triggers this dependency. The solver's address does not need to be blacklisted at fill time; it is sufficient for the issuer to blacklist it before the `RedeemEscrow` message is relayed and applied (a window that can span multiple blocks/chains), or for a user's own refund address to be blacklisted before `RefundEscrow` is applied. Given real-world stablecoin blacklisting events are not rare (e.g., sanctions enforcement, court orders), and the intent gateway explicitly supports arbitrary ERC-20 inputs, this is a realistic, moderate-likelihood scenario, matching the accepted severity of the analogous Axis Finance finding.

### Recommendation
Separate the "finalize" bookkeeping (`_filled[commitment] = beneficiary`, escrow balance decrement, event emission) from the token transfer itself. On transfer failure (e.g., wrap the `safeTransfer` in a try/catch or a low-level call check), fall back to crediting the beneficiary's amount into an internal, per-beneficiary claimable balance mapping instead of reverting the whole settlement, and expose a separate `claim()`/`sweep()` function that lets the beneficiary (or an alternate designated recipient) pull the funds later, or redirect them to a different address without blocking the order's finalization. This mirrors the fix Axis Finance adopted (Axis-Fi/moonraker#140) of decoupling settlement finalization from per-bidder payout/refund delivery.

### Proof of Concept
1. User places a cross-chain order on chain A with `inputs = [USDC, amount]`, destination chain B.
2. Solver `S` calls `fillOrder` on chain B, providing the required outputs to the beneficiary; `ExtrinsicIntents._fillCrossChain` sets `_filled[commitment] = S` on chain B and dispatches a `RedeemEscrow` post-request back to chain A with `beneficiary = S` (see `evm/src/apps/intentsv2/ExtrinsicIntents.sol:164-219`).
3. Before the relayer delivers the message to chain A, USDC issuer blacklists address `S` (e.g., due to unrelated sanctions/compliance action).
4. Relayer submits proof, Hyperbridge host calls `ExtrinsicIntents.onAccept` → `_withdraw(body, false, true)` on chain A (`evm/src/apps/intentsv2/IntentsBase.sol:451-470`).
5. `IERC20(USDC).safeTransfer(S, amount)` reverts because `S` is blacklisted; the entire `onAccept` transaction reverts, so `_filled[commitment]` on chain A is never set and `_orders[commitment][USDC]` is never decremented.
6. Every subsequent relayer attempt to deliver the same (or a retried) `RedeemEscrow` message hits the identical revert. The order can never be finalized on chain A: the user's escrowed USDC is permanently stuck in the gateway, while chain B already recorded the order as filled by `S` — no refund and no payout is possible ever.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function _fillCrossChain(Order calldata order, FillOptions calldata options, bytes32 commitment) internal {
        uint256 outputsLen = order.output.assets.length;

        _filled[commitment] = msg.sender;

        uint256 msgValue = msg.value;
        address beneficiary = address(uint160(uint256(order.output.beneficiary)));
        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {
            bytes32 outputToken = order.output.assets[i].token;
            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            if (solverAmount < totalRequired) revert InvalidInput();

            (uint256 protocolShare, uint256 beneficiaryShare) =
                _splitSurplus(solverAmount - totalRequired, order.output.call.length > 0);

            if (token == address(0)) {
                if (msgValue < solverAmount) revert InsufficientNativeToken();
                uint256 beneficiaryTotal = totalRequired + beneficiaryShare;
                _sendValue(beneficiary, beneficiaryTotal);
                msgValue -= (beneficiaryTotal + protocolShare);
            } else {
                IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare);
                if (protocolShare > 0) {
                    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
                }
            }
            if (protocolShare > 0) emit DustCollected(token, protocolShare);
            outputFills[i] = TokenInfo({token: outputToken, amount: totalRequired});
        }

        _execute(order, outputsLen);

        // Native dispatch fee only if the solver sent enough to cover it; else the fee token.
        uint256 nativeFee = options.nativeDispatchFee;
        if (nativeFee > msgValue) nativeFee = 0;
        msgValue -= nativeFee;
        _post(
            order,
            _body(RequestKind.RedeemEscrow, commitment, order.inputs, bytes32(uint256(uint160(msg.sender)))),
            options.relayerFee,
            nativeFee
        );

        // Refund any unspent native tokens to the solver.
        if (msgValue > 0) {
            _sendValue(msg.sender, msgValue);
        }

        emit OrderFilled({commitment: commitment, filler: msg.sender, outputs: outputFills, inputs: order.inputs});
    }
