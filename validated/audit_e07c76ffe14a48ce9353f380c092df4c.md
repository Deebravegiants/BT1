## Analog Found

### Title
Residual tokens left in the shared `CallDispatcher` after `HyperFungibleToken`/`WrappedHyperFungibleToken` calldata execution can be permanently lost or stolen via front-running - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
The reported bug is that Axelar's `Executor._executeWithToken()` approves tokens to an arbitrary `callTo` target and, if that target doesn't pull the full approved amount, the leftover tokens are stranded in the `Executor` with no recovery path. The equivalent pattern exists in Hyperbridge's `HyperFungibleToken`/`WrappedHyperFungibleToken` calldata-execution feature: tokens are minted/unlocked directly to a `to` address (which the docs recommend setting to the `CallDispatcher`) and then `CallDispatcher.dispatch()` is invoked to run sender-supplied calls against those tokens. Unlike `IntentGatewayV2`/`IntentsBase`, which explicitly sweep any residual balance out of the dispatcher back to the protocol after executing calldata, the HFT/WrappedHFT `onAccept` path has no such sweep step, and `CallDispatcher.dispatch()` itself is a completely unrestricted, callable-by-anyone function.

### Finding Description
In `HyperFungibleToken.onAccept()` / `WrappedHyperFungibleToken.onAccept()`, the destination-chain beneficiary of a cross-chain transfer is minted/unlocked tokens first, and only afterward is `message.data` forwarded to the `CallDispatcher`: [1](#0-0) 

Per the documented usage pattern, when calldata needs to spend the bridged tokens, the sender sets `to` to the `CallDispatcher` address so the minted/unlocked tokens land there before `dispatch()` runs the attached `Call[]`: [2](#0-1) 

`CallDispatcher.dispatch()` has no access control whatsoever — any address can call it with an arbitrary `Call[]` to move funds the dispatcher happens to be holding: [3](#0-2) 

If the attached `Call[]` (set by the original cross-chain sender, potentially not fully accounting for rounding, slippage, or partial swap execution) does not consume 100% of the tokens delivered to the `CallDispatcher`, the residual balance is left sitting in the dispatcher contract. Because `dispatch()` is public and unrestricted, any third party watching the chain can immediately call `dispatch()` themselves with a `Call` that transfers out that residual balance to their own address — this is a strictly worse outcome than simple fund-freezing, since it enables outright theft of the dust by anyone, not just permanent loss.

This is in direct contrast to how `IntentGatewayV2`/`IntentsBase` use the very same `CallDispatcher`: after executing output calldata, they explicitly measure and sweep any leftover dispatcher balance back into the app contract in the same atomic call, before any outsider gets a chance to interact with it: [4](#0-3) 

HFT/WrappedHFT's `onAccept` has no equivalent sweep-back logic after invoking `ICallDispatcher(_dispatcher).dispatch(message.data)` for either the mint/unlock-then-execute (HFT) or unlock/unwrap-then-execute (WrappedHFT) paths: [5](#0-4) 

### Impact Explanation
This is reachable by any relayer delivering a legitimate cross-chain HFT/WrappedHFT transfer whose attached calldata does not perfectly consume all delivered tokens (e.g., due to slippage tolerance on a swap, rounding, or a bug/misconfiguration in the sender-supplied `Call[]`). Once such a delivery completes, the leftover balance sits in the shared, unrestricted `CallDispatcher`, where any third party can drain it via a direct `dispatch()` call — a concrete theft of user/bridge funds, not merely a freezing of funds. Given the `CallDispatcher` is a shared, well-known deployment used across multiple Hyperbridge apps (per the docs, referenced on the public contract-addresses page), it is a natural target for automated bots to monitor and drain opportunistically. This qualifies as Medium risk, matching the severity of the analogous LiFi/Axelar finding.

### Likelihood Explanation
Likelihood is moderate: it requires (a) a cross-chain HFT/WrappedHFT transfer with attached calldata that leaves a non-trivial residual balance in the dispatcher, and (b) an opportunistic actor monitoring the dispatcher's balance/mempool to race a `dispatch()` call before any legitimate recovery. Since composable calldata execution (swaps, deposits) is an advertised, encouraged use case, and swaps commonly leave small residuals (due to `swapExactTokensForTokens`-style calls with output-side leftover or `approve`+partial-spend patterns), this scenario is realistically expected to occur over time, and the unrestricted nature of `dispatch()` guarantees drainability once dust exists.

### Recommendation
- Restrict `CallDispatcher.dispatch()` so it can only be invoked by trusted, registered caller contracts (e.g., the specific HFT/WrappedHFT/IntentGateway instances), rather than being fully public.
- After executing sender-supplied calldata in `HyperFungibleToken.onAccept()`/`WrappedHyperFungibleToken.onAccept()`, mirror `IntentsBase._execute()`'s pattern: measure the dispatcher's token balance before/after and sweep any residual back to the beneficiary or to a documented protocol-owned recovery address, emitting a `DustCollected`-style event.
- Document this token-handling/dust behavior explicitly for integrators, similar to the `AxelarFacet.md` recommendation in the referenced report.

### Proof of Concept
1. A user bridges tokens cross-chain via `HyperFungibleToken.send()` with `to = CALL_DISPATCHER` and `data` encoding a swap call (e.g., `swapExactTokensForTokens`) that, due to slippage, does not spend the entire minted amount.
2. The relayer delivers the message; `onAccept()` mints the full amount to the `CallDispatcher`, then calls `dispatch(message.data)`, which executes the swap and leaves a residual token balance in the `CallDispatcher`.
3. An attacker (or bot) observes the `CallDispatcher`'s non-zero token balance and calls `CallDispatcher.dispatch()` directly with a `Call[]` such as `{to: token, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, residualBalance)}`.
4. Since `dispatch()` has no access control, this call succeeds, transferring the residual bridged tokens to the attacker — funds that were never returned to the legitimate beneficiary or protocol.

```text
Both contracts support optional calldata execution on the destination chain via the `CallDispatcher`. By passing a non-empty `data` field in `SendParams`, the sender can trigger arbitrary contract calls on the destination chain immediately after tokens are minted or unlocked. This enables composable cross-chain workflows like transfer-and-swap (e.g., bridge USDC then swap to WETH via UniswapV2), transfer-and-stake, or transfer-and-deposit into a lending protocol — all in a single cross-chain operation.

The `data` field is an ABI-encoded `Call[]` array, where each `Call` specifies a target contract, a native value to forward, and the calldata to execute. On the destination chain, the HFT contract mints or unlocks tokens to the `to` address, then forwards the entire `data` payload to the `CallDispatcher`, which executes each call sequentially. If the calls need to spend the bridged tokens (e.g., approve then swap), set `to` to the `CallDispatcher` address so tokens are delivered directly to it.

For code examples, see the [HyperFungibleToken](/developers/evm/hyper-fungible-token/hyper-fungible-token#calldata-execution) and [WrappedHyperFungibleToken](/developers/evm/hyper-fungible-token/wrapped-hyper-fungible-token#calldata-execution) pages.

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.
```

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }
