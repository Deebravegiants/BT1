### Title
Unbounded per-byte reputation mint lets an unprivileged relayer buy collator selection - (File: `modules/pallets/messaging-incentives/src/lib.rs`)

### Summary
The C4 finding is about `DAO.setAdvanceIncentive` having no upper bound on `incentive`, so `advance()` mints `incentive * 1e18` MALT with no ceiling — an unbounded multiplier on a mint. The strongest reachable analog in this repo is not admin-side: `pallet-messaging-incentives` mints `ReputationAsset` to a relayer as `bytes × MintPerByte`, where `MintPerByte` is a fixed, governance-set rate but `bytes` is the *unbounded, attacker-controlled* size of the request body the relayer itself constructs and signs. That reputation balance is then the sole ranking criterion `pallet-collator-manager` uses to select block-producing collators, so inflating it inflates real, security-relevant privilege (block production, treasury rewards, and fisherman veto authority), not just an internal score.

### Finding Description
`Pallet::message_bytes` computes the mint multiplicand directly from the size of an ISMP `Request`'s body: [1](#0-0) 

`on_executed` then multiplies this unbounded `bytes` value by the fixed `MintPerByte` rate and mints the product to whichever account's signature is recovered from the message: [2](#0-1) 

There is no maximum on `bytes` in this code path (no `MaxRequestBodySize`/body-length cap was found anywhere in the pallet or its callers), so the mint amount for a single message is only limited by whatever the transaction/weight envelope permits, not by anything the incentive logic itself enforces — structurally the same class of bug as `advanceIncentive` having no ceiling before being multiplied into a mint.

The minted `ReputationAsset` is not a cosmetic score: `pallet-collator-manager::new_session` ranks every bonded candidate strictly by this balance and hands the top-ranked controllers the collator seat for the next session: [3](#0-2) 

Becoming a collator grants block production, `0.7 BRIDGE` per-block treasury rewards, and fisherman veto signing rights (per the collator docs), i.e. real economic and consensus-relevant privilege gated purely on this reputation balance.

### Impact Explanation
An unprivileged actor who can get itself recognized as "the relayer" for a delivered ISMP message (by controlling the signer key on a `Message::Request`/`Message::Response`, which any relayer legitimately does) can pad request bodies to inflate `bytes` and mint outsized `ReputationAsset` relative to genuinely useful message delivery. Because `pallet-collator-manager` selects collators purely by this balance, an attacker can out-rank honest operators and seize collator seats without commensurate real service to the network, or — combined with a large-enough single delivery — dominate the candidate ranking in one session. Sitting collators are also block producers and fisherman veto signers, so this converts an incentive-accounting flaw into a path toward influencing block production and L2 fraud-veto authority: an "unauthorized app action" gated on the exploitable balance. This is reachable from a single relayer-submitted transaction with no admin/governance involvement, satisfying the rules' bar for a permissioned-action-reachable finding.

### Likelihood Explanation
Medium. The attacker needs no special role beyond being a message relayer (which is permissionless), and the only friction is the cost of constructing and delivering an oversized request body, bounded by ordinary transaction-size/weight limits rather than by any explicit cap in the incentive logic. Repeated over many messages/sessions, this compounds; a single sufficiently large delivery can already produce an outsized one-time mint. The `set_mint_per_byte` rate itself is governance-controlled and fixed, so the exploitable degree of freedom is squarely the unbounded `bytes` term, not an admin-set value — this is what keeps the analog within the unprivileged-reachable rule.

### Recommendation
Cap the per-message (and/or per-session) bytes counted toward the reputation mint, e.g. clamp `message_bytes` per request or per batch to a governance-configured maximum, mirroring how `pallet-bandwidth` bounds allowance consumption. Consider also weighting collator selection by delivered message *count* over a rolling window rather than raw cumulative byte-mint balance, so a single oversized delivery cannot dominate ranking.

### Proof of Concept
1. Relayer crafts and signs an ISMP `Message::Request` whose `requests[].body` is padded to the maximum size the block/weight limits allow (there is no explicit cap in `message_bytes`).
2. Deliver the message through `pallet-ismp`; `FeeHandler::on_executed` is invoked, which calls `Pallet::message_bytes` and mints `bytes × MintPerByte` `ReputationAsset` to the relayer's recovered account (`modules/pallets/messaging-incentives/src/lib.rs:126-186`).
3. Repeat cheaply across multiple deliveries/sessions to accumulate a `ReputationAsset` balance far above what honest relayers earn for equivalent real message-delivery work.
4. At the next session boundary, `pallet-collator-manager::new_session` ranks candidates by this balance (`modules/pallets/collator-manager/src/lib.rs:511-542`) and selects the attacker's controller account into the active collator set, granting block-production and fisherman-veto privileges disproportionate to actual service rendered.

		match message {
			Message::Request(req) => req
				.requests
				.iter()
				.map(|p| core::cmp::max(p.body.len() as u32, 32))
				.sum::<u32>(),

		}
	}

	fn on_executed(
		messages: Vec<MessageWithWeight>,
		_events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let rate = MintPerByte::<T>::get();
		if !rate.is_zero() {
			for mw in &messages {
				let bytes = Self::message_bytes(&mw.message);
				let bytes_balance: BalanceOf<T> = (bytes as u128).saturated_into();
				let amount = rate.saturating_mul(bytes_balance);
				if amount.is_zero() {
					continue;
				}
				if let Some(relayer) = Self::relayer_for(&mw.message) {
					match T::ReputationAsset::mint_into(&relayer, amount) {
						Ok(_) =>
							Self::deposit_event(Event::ReputationMinted { relayer, bytes, amount }),
						Err(err) => log::warn!(
							target: "messaging-incentives",
							"reputation mint failed for {bytes}b: {err:?}",
						),
					}
				}
			}
		}
		Ok(PostDispatchInfo { actual_weight: None, pays_fee: Pays::No })
	}
