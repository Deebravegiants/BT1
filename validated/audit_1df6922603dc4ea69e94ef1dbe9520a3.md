### Title
Cross-tenant session hijacking via guessable, unsigned cookie-based session identifier - (File: `lib/shopify_api/utils/session_utils.rb`)

### Summary
For non-embedded apps (and as a fallback for embedded apps), `ShopifyAPI::Utils::SessionUtils.current_session_id` returns the raw, unauthenticated value of the `shopify_app_session` cookie as the session identifier used to look up a merchant's `Session` (and therefore its Shopify access token) in session storage. This session identifier is not a random secret — it is a fully deterministic string derived from public data (`offline_#{shop}` or `#{shop}_#{associated_user_id}`), and is set into that very cookie by `ShopifyAPI::Auth::Oauth.validate_auth_callback`. No cryptographic binding (HMAC, signature, or expiry check) ties the cookie's bytes to the legitimate session owner, breaking the intended equality "cookie value == identifier of a session the current unauthenticated request is entitled to."

### Finding Description
Two code paths exist for identifying "the current session":
1. Embedded apps with an `id_token`: cryptographically verified via `Auth::JwtPayload`, which HMAC-validates the token with `Context.api_secret_key` and checks `aud == Context.api_key` before deriving the session id — this path is properly bound. [1](#0-0) 
2. Non-embedded apps (and embedded apps without an id token) read the session id straight from a cookie with zero verification: [2](#0-1) [3](#0-2) 

The value placed into that cookie is not a random opaque token — it is the literal, deterministic `Session#id` computed from public/guessable inputs: [4](#0-3) [5](#0-4) 

And this deterministic id is what `Oauth.validate_auth_callback` writes back into the `shopify_app_session` cookie for non-embedded/legacy flows: [6](#0-5) 

Contrast this with the OAuth nonce cookie, which correctly uses a high-entropy secret (`SecureRandom.alphanumeric(NONCE_LENGTH)`) precisely because a guessable/replayable value in that slot is dangerous: [7](#0-6) 

The documentation confirms this cookie-based flow is the gem's intended, documented API for non-embedded apps, and explicitly states session persistence (i.e., looking the returned id up in a store) is delegated to the consuming app — meaning any app following this gem's documented contract inherits the flaw: [8](#0-7) 

Because the identifier is `offline_#{shop}` (fully public — the shop's `myshopify.com` domain) or `#{shop}_#{associated_user_id}` (shop domain plus a small/sequential Shopify user id), an attacker can compute a target's exact session id without ever observing the victim's real cookie, and simply present it as their own `shopify_app_session` cookie value to the vulnerable app.

### Impact Explanation
This breaks the tenant boundary: an attacker sets `shopify_app_session=offline_victim-shop.myshopify.com` (or the online variant with a guessed `associated_user_id`) on their own request to the app, and — following the gem's documented usage — the app resolves this into the victim's real `Auth::Session`, including its Shopify Admin API access token. The attacker can then make Admin API calls against the victim's shop using the app's client, achieving cross-tenant access to another merchant's store data and credentials, which is one of the explicitly in-scope Critical impacts.

### Likelihood Explanation
Likelihood is moderate-to-high for offline sessions: `offline_#{shop}` requires only knowledge of the target's `myshopify.com` domain, which is often public. For online sessions, the attacker additionally needs a valid `associated_user_id`, which is a small/sequential Shopify user identifier and enumerable/brute-forceable in many deployments. No secret, XSS, or CSRF is required — the attacker only needs to set a cookie header on their own outbound request, something any internet user fully controls.

### Recommendation
Do not use a deterministic, guessable string as the cookie-carried session identifier. Instead:
- Generate a high-entropy, random opaque token (like the OAuth `state` nonce) at session-creation time, store the mapping `opaque_token -> session.id` server-side, and set only the opaque token in the `shopify_app_session` cookie.
- Alternatively, HMAC-sign the cookie value (`session.id` plus an expiry) with `Context.api_secret_key` and verify the signature in `SessionUtils.cookie_session_id`/`current_session_id` before trusting it, mirroring the protection already given to the JWT path.
- Document clearly (and, where possible, enforce in `SessionUtils`) that raw cookie values must never be used directly as a trusted lookup key into a store containing access tokens.

### Proof of Concept
1. Attacker learns/guesses the victim shop's domain, `victim-shop.myshopify.com` (public storefront URL).
2. Attacker sends a request to the vulnerable non-embedded app with header `Cookie: shopify_app_session=offline_victim-shop.myshopify.com`.
3. The app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)` per the documented pattern, which returns `"offline_victim-shop.myshopify.com"` unmodified: [9](#0-8) 
4. The app looks this id up in its session store (as instructed by the docs) and obtains the victim's real `Session`, including `access_token`, then uses it to serve the attacker's request — granting the attacker access to the victim shop's Admin API.

#### Cookie
Cookie based authentication is not supported for embedded apps due to browsers dropping support for third party cookies due to security concerns. Non-embedded apps are able to use cookies for session storage/retrieval.

For *non-embedded* apps, you can pass the cookies into:
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, true)` for online (user) sessions or
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)` for offline (store) sessions.
