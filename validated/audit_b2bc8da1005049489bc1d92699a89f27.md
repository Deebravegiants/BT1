### Title
Webhook HMAC validation covers only the raw body, not the `shop-domain` header — enables cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely via `Utils::HmacValidator.validate(request)`, and that validator computes/verifies the HMAC exclusively over `request.to_signable_string`, which returns the raw request body only. [1](#0-0) [2](#0-1)  The `shop` value that is subsequently handed to the app's handler (`WebhookMetadata.shop`) is read from the `x-shopify-shop-domain` HTTP header, which is never included in the signed bytes. [3](#0-2) [4](#0-3) 

### Finding Description
`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` using the app's `api_secret_key` (shared across every shop that installs the app) and compares it to the `hmac` field of the request: [5](#0-4) 

For `Webhooks::Request`, `to_signable_string` is defined as just the raw body: [2](#0-1) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from HTTP headers that are completely outside of what the HMAC covers: [6](#0-5) 

`Registry.process` uses exactly this validator as its sole authentication gate, then trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` passed into the app's registered handler: [7](#0-6) 

This breaks the intended identity binding: **bytes verified (raw body signed with the shared app secret) ≠ bytes that determine tenant (the `shop-domain` header)**. Because the app's `api_secret_key` is the same for every merchant that installs the app, any unprivileged internet user who operates their own shop can install the app, legitimately receive a validly-signed webhook (any `raw_body`/`hmac` pair delivered to their own endpoint), and then replay that exact `raw_body` + `hmac` to the same endpoint while substituting an arbitrary victim shop domain in the `x-shopify-shop-domain` header. `HmacValidator.validate` still returns `true` because it only checks the body bytes, and `Registry.process` will invoke the app's handler with `shop: "<attacker-chosen-victim-shop>.myshopify.com"`.

### Impact Explanation
This is a cross-tenant access primitive: the gem hands the host application webhook data that is attributed to an arbitrary, attacker-controlled shop identity, despite claiming it was cryptographically validated. Any app logic that trusts `WebhookMetadata.shop` to select per-tenant state (e.g., updating billing status, triggering `customers/redact` / `shop/redact` data handling, writing to a tenant-keyed session/store, or triggering side effects scoped "for shop X") can be made to act on behalf of a shop the attacker does not control. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
The prerequisite is only that the attacker be able to install the app on their own shop (or otherwise obtain one valid `raw_body`/HMAC pair for the shared `api_secret_key`) — no access token, refresh token, or `client_secret` theft is required, and no privileged account is needed. The attack is a simple header substitution on a replayed HTTP request to the app's public webhook endpoint, which is directly enabled by this gem's own `Request`/`HmacValidator`/`Registry.process` implementation, not by any misuse of a documented API by the host app.

### Recommendation
Bind the tenant-identifying fields into the signed material, or otherwise cryptographically tie `shop`, `topic`, and `webhook_id` to the HMAC before trusting them:
- Extend `Webhooks::Request#to_signable_string` (or add a secondary check in `HmacValidator`/`Registry.process`) so that `shop`, `topic`, and `webhook_id` are included in what's verified, not just the raw body.
- Alternatively, require callers/handlers to cross-check `request.shop` against an out-of-band trusted store identity (e.g., a known/registered shop list) before acting on the webhook payload, and document this requirement clearly since currently the gem's API implies `process` fully authenticates the tuple.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives (via normal Shopify webhook delivery) a real webhook POST with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker resends the exact same request to the app's webhook endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but replacing `x-shopify-shop-domain: attacker-shop.myshopify.com` with `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. The host app calls `ShopifyAPI::Webhooks::Registry.process(request)`. `Utils::HmacValidator.validate(request)` recomputes `HMAC-SHA256(api_secret_key, B)`, which still equals `H`, so validation passes. [8](#0-7) 
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)`, even though the request never touched Shopify infrastructure for `victim-shop`. [4](#0-3)
