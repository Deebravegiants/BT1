## Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC of the raw request body, but the shop identity that the handler acts on (`request.shop`) is read from an HTTP header that is never included in the HMAC-signed material. Anyone who can obtain one genuine `(raw_body, hmac)` pair for any shop (trivially available to any developer who installs a public app into their own store) can replay that exact pair while substituting the `shopify-shop-domain` header for a victim shop, and the request still passes validation.

### Finding Description
`Utils::HmacValidator.validate` computes/verifies the signature only over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns just the raw body: [2](#0-1) 

But `request.shop`, `request.topic`, and `request.webhook_id` are all parsed straight out of HTTP headers, which are not part of the signed payload at all: [3](#0-2) 

`Registry.process` validates only the body HMAC, then hands the *header-derived* shop value to the app's handler as the trusted tenant identifier: [4](#0-3) 

The equality the code implicitly assumes is:

`shop bound by HMAC == shop acted on by handler`

but in reality:

`shop bound by HMAC (none — HMAC only covers raw_body) ≠ shop passed to WebhookMetadata (headers["shopify-shop-domain"], attacker-controlled)`

Because the header is outside the signed scope, an attacker who owns any shop that has the target app installed (a normal, unprivileged action — installing a public app on a free/dev store) can capture one legitimate webhook delivery (valid `raw_body` + valid `hmac-sha256` header for their own shop), then replay that exact body/HMAC pair to the app's webhook endpoint while swapping `x-shopify-shop-domain` to a victim's `*.myshopify.com` domain. `HmacValidator.validate` recomputes the HMAC over the (unchanged) body and it still matches, so `Registry.process` proceeds and invokes the app's handler with `shop: <victim-shop>`.

### Impact Explanation
This breaks the tenant isolation boundary that host applications rely on: they use `WebhookMetadata#shop` as the authoritative identifier of which merchant's data a webhook event pertains to (e.g., to look up or update per-shop records, trigger per-shop side effects, or attribute billing/usage events). An attacker can inject data or trigger handler logic that is falsely attributed to a shop they do not control, i.e., cross-tenant access/contamination — a Critical-severity impact per the given rubric.

### Likelihood Explanation
Likelihood is high for any app whose handler logic trusts `data.shop` for tenant scoping (the documented usage pattern in this gem, see `WebhookMetadata` construction in `Registry.process`). The prerequisite — obtaining one valid `(raw_body, hmac)` pair — requires nothing more than installing the target (public) app into any shop the attacker controls, which is unprivileged and inexpensive. No access token, `api_secret_key`, or victim credentials are required; only network access to replay the captured HTTP request with a modified header.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the value that is authenticated, or otherwise cryptographically tie the header claims to the signed body, for example:
- Include the `shopify-shop-domain` (and `topic`) header values in the string that `HmacValidator` verifies for `Webhooks::Request`, mirroring how `Auth::Oauth::AuthQuery#to_signable_string` binds `shop` into its signed string.
- Alternatively, require host applications to independently corroborate `request.shop` against a shop they already have an active session for before trusting it, and document this gap prominently since the gem currently implies the shop is authenticated once `Registry.process` succeeds.

### Proof of Concept
1. Attacker creates/owns Shop A and installs the target (public) app, causing Shopify to deliver a legitimate webhook to the app's endpoint with a valid `x-shopify-hmac-sha256` for some `raw_body` (e.g., `orders/create` for Shop A).
2. Attacker captures the exact `raw_body` and `x-shopify-hmac-sha256` value from that request (they control the receiving endpoint, or can intercept their own traffic).
3. Attacker sends a new HTTP request to the app's webhook endpoint using:
   - the identical `raw_body`
   - the identical `x-shopify-hmac-sha256` header value
   - `x-shopify-shop-domain` header rewritten to `victim-shop.myshopify.com`
   - `x-shopify-topic` optionally rewritten as desired
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over the unchanged `raw_body` and succeeds: [5](#0-4) 
5. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, causing the host app to process/attribute the (attacker-supplied) event as belonging to the victim shop.
