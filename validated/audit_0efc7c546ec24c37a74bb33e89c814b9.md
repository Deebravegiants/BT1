### Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` headers are trusted by `Registry.process` without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/registry.rb](lib/shopify_api/webhooks/registry.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook by checking the HMAC over the raw request body only, then unconditionally forwards the `shop-domain`, `topic`, `webhook-id`, and `api-version` HTTP headers to the host application's handler as trusted, tenant-identifying data - even though none of those header values are covered by the HMAC.

### Finding Description
`Registry.process` calls `Utils::HmacValidator.validate(request)` before dispatching to the handler: [1](#0-0) 

The HMAC validation, however, is only computed over `to_signable_string`, which for `Webhooks::Request` is defined as the raw body - not any header: [2](#0-1) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from unauthenticated HTTP headers: [3](#0-2) 

`HmacValidator.validate` only ever inspects `verifiable_query.hmac` and `verifiable_query.to_signable_string`, so it has no way to bind the header values to the signature: [4](#0-3) 

After the (body-only) HMAC check passes, `Registry.process` builds a `WebhookMetadata` object directly from these unauthenticated headers and passes it to the app's handler: [1](#0-0) 

The documented usage pattern explicitly instructs integrators to use `data.shop` as the tenant key for routing/attribution (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, ...)`): [5](#0-4) 

The identity binding that should hold is: `shop used by the handler == shop that the HMAC-signed body actually originated from`. Because the HMAC covers only the body bytes and not the `shop-domain` header, this equality is not enforced by the gem. An attacker who controls a shop that has the same app installed (a normal, unprivileged app install - no special privilege needed) can capture one of their own legitimately-signed webhook deliveries (valid HMAC computed by Shopify using the app's real `api_secret_key` over that specific body), then replay the identical `raw_body` + `hmac-sha256` header to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header value (e.g., a victim's shop domain, or any string). `HmacValidator.validate` will still return `true` because it only checks the body against the HMAC, and `Registry.process` will hand the handler a `WebhookMetadata` whose `shop` field is entirely attacker-controlled.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to establish for webhook processing: the `shop` value handed to the host application's handler as an authenticated fact is not actually authenticated. Any app that uses `data.shop` (as the official docs recommend) to look up per-merchant records, attribute events, or gate per-tenant business logic can be made to process/attribute a real, validly-HMAC-signed payload under an attacker-chosen shop identity. Combined with a normal (unprivileged) app install by the attacker, this allows cross-tenant data confusion/injection - falling under the "cross-tenant access" Critical impact category, since the gem itself asserts (via `Registry.process`'s successful return / no exception) that the webhook is authentic and shop-attributed when in fact the shop attribution is forgeable.

### Likelihood Explanation
Likelihood is moderate-to-high in any deployment following the documented pattern: an attacker only needs to install the app on a shop they control (a standard, unprivileged action any developer/merchant can do), trigger any webhook event, capture the raw body + valid `hmac-sha256` header from their own delivery, and replay it to the app's public webhook endpoint with a modified `shop-domain` header. No access to `api_secret_key`, access tokens, or any elevated privilege is required.

### Recommendation
Bind the shop (and ideally topic/webhook id/api-version) to the HMAC-protected content, or otherwise verify the `shop-domain` header value against an independently-trusted source (e.g., cross-check against the shop registered for the webhook subscription, or validate that the shop is one for which the app holds an active, previously-established session/installation) before constructing `WebhookMetadata`. At minimum, document loudly that `data.shop` is not covered by the HMAC and must not be trusted for tenant-identification purposes without additional verification, or change `Request#to_signable_string`/`HmacValidator` usage to incorporate the header values that downstream code treats as authenticated.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, unprivileged install).
2. Attacker triggers any subscribed webhook event (e.g., `orders/create`) and captures the resulting HTTP request Shopify sends to the app: raw body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker replays a forged request to the same app's webhook endpoint:
   - Body: `B` (unchanged)
   - `X-Shopify-Hmac-Sha256: H` (unchanged, still valid since it only signs the body)
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (attacker-chosen)
   - `X-Shopify-Topic`, `X-Shopify-Webhook-Id`, `X-Shopify-Api-Version`: attacker-chosen
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H`: [6](#0-5) 
5. `Registry.process` builds `WebhookMetadata` using `request.shop` (= `victim-shop.myshopify.com`, attacker-controlled) and invokes the app's handler, which per the documented pattern will process/attribute this valid-body webhook as belonging to `victim-shop.myshopify.com`. [1](#0-0)

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
