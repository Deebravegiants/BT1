### Title
Webhook `shop` (and `topic`/`webhook_id`) fields are not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's authenticity solely via `Utils::HmacValidator.validate`, which checks the HMAC against `Request#to_signable_string`. That method returns only the raw HTTP body — never the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. Those header values are nonetheless passed straight into `WebhookMetadata` and delivered to the app's handler as trusted identifiers, breaking the binding `shop attested to handler == shop covered by HMAC`.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) 

Specifically, `to_signable_string` only returns `@raw_body`: [2](#0-1) 

while `shop`, `topic`, `webhook_id` and `api_version` are read directly from unauthenticated headers: [3](#0-2) 

`HmacValidator.validate_signature` computes the HMAC exclusively over `verifiable_query.to_signable_string` (i.e., the body), using `Context.api_secret_key`, which is the app's single secret shared across every shop that installs the app: [4](#0-3) 

`Registry.process` only calls this HMAC check, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` when building the metadata delivered to the handler: [5](#0-4) 

Because the HMAC secret is identical for all shops that install a given app, and the `shop-domain` header is never part of the signed bytes, a request whose body+HMAC pair was legitimately produced for shop A (e.g., an attacker's own store, which they fully control and can trigger webhooks on) will pass HMAC validation even when replayed with the `X-Shopify-Shop-Domain` header changed to shop B. The library provides no mechanism to detect this because the shop identity is parsed but never verified.

### Impact Explanation
This breaks the tenant isolation the HMAC check is supposed to guarantee: `Utils::HmacValidator.validate(request)` returning true is treated by host apps (per the gem's documented usage, `handler.handle(data: WebhookMetadata...)`) as proof the payload came from `request.shop`. An attacker who has installed the app on any shop can forge webhook events "from" any other shop hosted by the same app, injecting fabricated order/customer/product data attributed to a victim tenant. Depending on how the host processes this data (e.g., writing to a shop-keyed database row, triggering shop-scoped side effects), this is a cross-tenant data injection / cross-tenant access primitive.

### Likelihood Explanation
Any unprivileged user can install a public app on their own development/test store, receive one legitimately signed webhook, and replay it with a modified `shop-domain` header to the app's public webhook endpoint. No access token, secret, or privileged account is required beyond controlling one installation of the target app — a routine and low-cost precondition for an "unprivileged internet user."

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-covered signable string, or have `Registry.process` independently verify that the `shop` header matches an expected/authorized value before dispatching to the handler, so the HMAC check actually binds the shop to the signature it validates.

### Proof of Concept
1. Install the target Shopify app on attacker-controlled shop `attacker.myshopify.com`; the app registers a webhook (e.g., `orders/create`).
2. Trigger the webhook; capture the raw body and the `X-Shopify-Hmac-Sha256` value Shopify computed with the app's shared `client_secret`.
3. Replay the exact same body and HMAC header to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which succeeds because it only checks the (unchanged) body against the (unchanged) HMAC — see [6](#0-5) .
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` sourced from the forged header [7](#0-6) , causing the host application to process attacker-supplied data as if it belonged to the victim tenant.
