### Title
Unauthorized cross-account message signing via unchecked `walletAccount` identifier in `messageSigner.signMessage` - (File: `features/message-signer/src/module/message-signer.ts`)

### Summary
`MessageSigner.signMessage` accepts a `walletAccount` parameter that can be either a `WalletAccount` instance or a bare string identifier, and when it is a string it is resolved directly against the wallet's full internal account list with no check that the calling context is actually authorized to sign with that specific account.

### Finding Description
`SignMessageParams.walletAccount` is typed as `WalletAccount | string` [1](#0-0) . Inside `signMessage`, `#normalizeWalletAccount` resolves a string value by looking it up directly in `walletAccountsAtom` (the atom holding *all* of the wallet's accounts) and returns whatever `WalletAccount` instance matches that key — with no verification that this account is the one the caller is entitled to use: [2](#0-1) 

The resolved account is then handed straight to the signer (`seedBasedMessageSigner` or `hardwareMessageSigner`) which performs the actual cryptographic signing, again without re-validating account ownership/authorization against the caller: [3](#0-2) 

The public API surface (`messageSignerApi`) forwards the caller-supplied params verbatim to this module, adding no additional authorization layer of its own: [4](#0-3) 

This is structurally the same root cause as the Tapioca `_participateOnTOLP` bug: an identifier that should be scoped to "the caller's own resource" (`tOLPTokenId` in the original bug, `walletAccount` here) is instead accepted verbatim from input and trusted to resolve to the correct, authorized resource, without any ownership/authorization check tying the identifier back to the calling principal (the connected dApp/origin or active session).

### Impact Explanation
If any caller of this API (e.g., a background/RPC bridge layer that exposes `messageSigner.signMessage` to a connected dApp/origin) forwards an attacker/dApp-controlled `walletAccount` string without first constraining it to the account(s) the origin is actually connected to, a malicious or compromised origin could request a signature from a *different* wallet account than the one it is connected to (cross-account privilege bleed). Because signing is delegated straight to the seed-based or hardware signer, the result is a valid signature produced under the victim account, which is the exact class of "unauthorized signing" impact called for by the analog.

### Likelihood Explanation
The likelihood of practical exploitation depends entirely on whether an upstream boundary (browser-extension RPC bridge, `connected-origins` connection binding, or UI confirmation flow) restricts the `walletAccount` value passed into this call to the account(s) actually connected/approved for the requesting origin. I was not able to locate, within the indexed portion of the repository, the specific RPC/bridge handler that wires an untrusted dApp request into `messageSignerApi.signMessage`, so I cannot confirm with certainty that such a binding check is missing at that boundary — this module-level code path itself performs no such check, but the enforcement (if any) could exist entirely outside what the index surfaced. This is a gap in what I could verify.

### Recommendation
At the point where `walletAccount` is accepted from an external/untrusted caller (dApp RPC request), verify that the resolved `WalletAccount` matches an account explicitly connected/authorized for that origin/session (analogous to `connectedOrigins.getConnectedAccounts`) before calling into `messageSigner.signMessage`. Additionally, consider having `MessageSigner.signMessage` itself accept an explicit "authorized account(s)" context and assert membership, rather than trusting a bare string identifier resolved against the full account set.

### Proof of Concept
Conceptual PoC (pending confirmation of the exact untrusted entry point):
1. A dApp is connected to origin `evil.com` only for wallet account `exodus_1`.
2. If the RPC bridge forwards the dApp's `signMessage` request (including a `walletAccount` field) directly to `exodus.messageSigner.signMessage({ walletAccount: 'exodus_0', ... })` without checking that `exodus_0` is the account connected to `evil.com`:
```js
await exodus.messageSigner.signMessage({
  walletAccount: 'exodus_0',   // not the account connected to this origin
  baseAssetName: 'ethereum',
  purpose: 44,
  message: { rawMessage: Buffer.from('...') },
})
```
`#normalizeWalletAccount` resolves `'exodus_0'` from the full `walletAccountsAtom` [5](#0-4)  and signs with that account's key, producing a signature for an account the origin was never authorized to use.

```typescript
  #normalizeWalletAccount = async (
    walletAccount: WalletAccount | string
  ): Promise<WalletAccount> => {
    if (typeof walletAccount === 'string') {
      const walletAccounts = await this.#walletAccountsAtom.get()
      const instance = walletAccounts[walletAccount]
      assert(instance, `wallet account ${walletAccount} not found`)

      return instance
    }

    return walletAccount
  }
```
