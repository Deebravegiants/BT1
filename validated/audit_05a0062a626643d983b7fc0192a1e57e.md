### Title
Webhook Shop-Domain Header Not Bound by HMAC Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` computes the HMAC-verifiable payload from the raw body only, excluding the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers. `ShopifyAPI::Utils::HmacValidator.validate` therefore only proves the JSON body bytes were signed by the app's `api_secret_key`; it proves nothing about which shop or topic the signature was intended for. `ShopifyAPI::Webhooks::Registry.process` nevertheless trusts `request.shop` and `request.topic` directly out of the unauthenticated headers and forwards them to the host app's handler as `WebhookMetadata`, which per the gem's own documentation is meant to identify "The shop domain of the webhook."

### Finding Description
The webhook HMAC binding is:

`equality that should hold`: `hmac == HMAC(api_secret_key, shop ‖ topic ‖ body ‖ ...)`

but the actual implementation is: [1](#0-0) 

only `@raw_body` is signed. The `shop`, `topic`, `webhook_id`, and `api_version` accessors are read straight from attacker-controllable HTTP headers with no cryptographic tie to the HMAC: [2](#0-1) 

`HmacValidator.validate` verifies exactly and only `to_signable_string`, i.e. the body: [3](#0-2) 

`Registry.process` validates the HMAC once, then unconditionally uses the unauthenticated `request.shop`/`request.topic` to route the event and construct the tenant-identifying `WebhookMetadata` passed to the app's handler: [4](#0-3) 

`WebhookMetadata.shop` is documented as the way apps identify "The shop domain of the webhook," and the docs' example handler uses `data.shop` directly to route/attribute work to a tenant: [5](#0-4) [6](#0-5) 

Because a single app's `api_secret_key` is shared across every merchant that installs the app, any legitimate `(raw_body, hmac)` pair obtained from a real webhook delivery — including one delivered to a shop the attacker legitimately controls/installs the app on — remains HMAC-valid forever, for any `shop-domain`/`topic` header the attacker chooses to attach to it. Before the request: `shop` (header, attacker-controlled) ≠ `shop` (cryptographically bound, none). After processing: `WebhookMetadata.shop` is still the attacker-controlled value, and the host application acts on it as if Shopify itself attested to that shop identity.

### Impact Explanation
This is a cross-tenant identity-binding break: an attacker (any user who can install the app, which is the normal path for a public/dev app) can capture a real `(body, hmac)` pair from a webhook sent by Shopify for their own store, then replay it to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header naming a victim merchant. `HmacValidator.validate` will report success and `Registry.process` will invoke the app's handler with `WebhookMetadata.shop` equal to the victim's domain and attacker-chosen `topic`/`webhook_id`, while `body` is JSON content the attacker fully controls by shaping data in their own store (e.g. order/customer fields) before triggering the real webhook. This lets the attacker inject fabricated events — attributed to any other merchant using the same app — including sensitive lifecycle topics such as `customers/redact` or `shop/redact`, corrupting or exfiltrating the victim's tenant state inside the host application. This satisfies the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation requires only: (1) the attacker installs the target app on any shop they control (trivial, e.g. a free development store) to legitimately receive real, validly-signed webhooks, and (2) the ability to POST to the app's public webhook callback endpoint with custom headers, which is inherent to how webhook endpoints work. No access to `api_secret_key`, access tokens, or the victim's environment is needed.

### Recommendation
Include the shop domain (and topic/webhook id, if they must be trusted) inside the HMAC-signable string, or otherwise bind `Request#shop`/`Request#topic` cryptographically before they are used to build `WebhookMetadata`. At minimum, `Registry.process` should verify a shop-header value against something other than an unauthenticated header (e.g. compare it against a known/registered shop or ensure the value cannot be spoofed independently of the body's HMAC), and documentation should be updated once fixed to still recommend treating `data.shop` as trusted only after such binding exists.

### Proof of Concept
1. Attacker creates or uses a shop `attacker-shop.myshopify.com` and installs the vulnerable app, then triggers a real event (e.g. `orders/create`) with attacker-controlled order content.
2. Shopify sends a legitimately-HMAC-signed webhook to the app:
   ```
   POST /webhooks
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid-hmac-of-body>
   X-Shopify-Shop-Domain: attacker-shop.myshopify.com
   Body: {...attacker-crafted JSON...}
   ```
3. Attacker replays the exact same body and HMAC value, only changing the shop header:
   ```
   POST /webhooks
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <same-valid-hmac-of-body>
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   Body: {...same attacker-crafted JSON...}
   ```
4. `ShopifyAPI::Webhooks::Request#to_signable_string` returns the same `raw_body`, so `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-22`) succeeds.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and invokes the app handler as if Shopify confirmed this event belongs to the victim shop, even though the victim never sent or authorized it.
