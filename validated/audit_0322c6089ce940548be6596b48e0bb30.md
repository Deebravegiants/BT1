## Finding

### Title
Webhook shop-domain identity is trusted without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw body only, while the shop identity (`X-Shopify-Shop-Domain` header) that `Registry.process` later hands to the app's webhook handler is never included in that signed material. This breaks the equality `shop authenticated by HMAC == shop delivered to handler`, letting anyone who can obtain one validly-signed webhook body/HMAC pair (e.g. by triggering a webhook on their own, attacker-controlled shop) replay it against the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop.

### Finding Description
The HMAC binding is defined in `Request#to_signable_string`, which returns only `@raw_body`: [1](#0-0) 

`hmac` is likewise derived purely from the `hmac-sha256` header, and `shop` is read from a separate, unauthenticated header: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then unconditionally trusts `request.shop` as the identity passed to the registered handler: [3](#0-2) 

`Utils::HmacValidator.validate` simply recomputes the signature over `verifiable_query.to_signable_string` (i.e. the body) and compares it — it never incorporates the shop header: [4](#0-3) 

Because the signature only binds the *body*, not the *shop*, the two sides of the identity equality diverge: the HMAC authenticates "this body was produced by Shopify using our `api_secret_key`", but the code (and downstream app logic via `WebhookMetadata`) treats the `shop-domain` header as if it were equally authenticated evidence of *which tenant* that body belongs to.

### Impact Explanation
An attacker who controls (or has free/trial access to) any shop that has this app installed can trigger a webhook delivery with a body they influence (many webhook topics contain attacker-writable fields, e.g. `orders/create`, `customers/create`, `carts_update`). They receive a legitimate `X-Shopify-Hmac-Sha256` value computed by Shopify over that body using the app's real `api_secret_key` — no leaked credential is required, since Shopify itself performs the signing on the attacker's own shop's traffic. The attacker then resends that exact body + HMAC to the app's public webhook endpoint, substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `Registry.process` will accept the HMAC (it never checked the shop) and dispatch attacker-controlled data tagged as belonging to the victim shop to the app's handler, causing cross-tenant data confusion/injection in the host application's own data store keyed by `WebhookMetadata#shop`.

### Likelihood Explanation
Webhook endpoints are internet-reachable by design and no privileged credential, access token, or `client_secret` is required — the attacker only needs an ordinary/trial shop where the target app is installed (or where they can otherwise cause the app to receive one authentic webhook body/signature pair) and the ability to POST to the app's public webhook route with modified headers, both trivially available to an unprivileged actor.

### Recommendation
Bind the shop domain into the value verified by the HMAC (e.g. include the `shop-domain` header, or an app-side registered mapping of webhook-id → expected shop, in the signable material or as an additional post-validation check), or otherwise cross-check `request.shop` against a shop the app has actually installed/registered a webhook subscription for before dispatching to handlers, instead of trusting the unauthenticated header outright.

### Proof of Concept
1. Attacker installs/owns `attacker-shop.myshopify.com`, which has the vulnerable app installed and a webhook topic (e.g. `orders/create`) registered.
2. Attacker performs an action on their own shop that causes Shopify to deliver a webhook to the app, with body content they influence. Shopify computes and sends a valid `X-Shopify-Hmac-Sha256` over that exact raw body using the app's `api_secret_key`, plus `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures this raw body and its valid HMAC, then crafts a new POST to the app's webhook endpoint using the identical body and `X-Shopify-Hmac-Sha256` value, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses it; `Utils::HmacValidator.validate` succeeds because it only checks the body-derived signature (`lib/shopify_api/utils/hmac_validator.rb:12-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
5. `Registry.process` calls the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled>, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the host app to act on attacker data under the victim's tenant identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
