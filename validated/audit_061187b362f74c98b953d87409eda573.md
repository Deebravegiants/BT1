### Title
Permissionless `CallDispatcher.dispatch()` allows any unprivileged caller to drain tokens, standing approvals, or native ETH left in the shared dispatcher - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch()` is functionally the same failure class as the qwed-mcp `parse_expr()` bug: an "evaluator" that executes fully attacker-controlled input (`Call[].to/.value/.data`) with the contract's own authority, and applies **no restriction on who may invoke it or in what context**. Just as `parse_expr()` had no `global_dict` allowlist restricting what the expression could reach, `CallDispatcher.dispatch()` has no caller/context allowlist restricting who can trigger execution or what it may act on. Any address — not just `IntentGatewayV2`, `HyperFungibleToken`, or `WrappedHyperFungibleToken` — can call it directly to make the dispatcher execute arbitrary calls with its own balance and standing token approvals.

### Finding Description
`CallDispatcher.dispatch(bytes memory encoded)` decodes an ABI-encoded `Call[]` and executes each call with `to.call{value: call.value}(call.data)`, where `to`, `value`, and `data` are entirely attacker-supplied: [1](#0-0) 

There is no `onlyHost`, `onlyGateway`, or any access-control modifier on `dispatch()` — it is `external` with zero restriction, exactly mirroring the missing sandbox in `verify_math_expression()`. The interface docstring itself calls it a dispatcher for "untrusted call(s)": [2](#0-1) 

This single `CallDispatcher` instance is shared across `HyperFungibleToken`/`WrappedHyperFungibleToken` (`onAccept`, `_dispatcher`) and `IntentGatewayV2` (`predispatch`/`postdispatch`), all of which route mint/escrow value through it before or after the dispatcher executes attacker-chosen calls: [3](#0-2) [4](#0-3) 

The project's own docs acknowledge the danger of standing approvals left on the dispatcher, but this is only advisory — nothing in the contract enforces it: [5](#0-4) 

Because `dispatch()` is callable by anyone at any time, any value that transiently sits in the dispatcher — native ETH via its unrestricted `receive()`, ERC20 balances left as "dust" that don't match a known output-asset list, or an ERC20 allowance the dispatcher granted to a router/protocol during a legitimate predispatch/postdispatch call (e.g. the documented `approve(UNISWAP_V2_ROUTER, type(uint256).max)` pattern shown in the docs) — can be swept out by an unprivileged third party simply by calling `dispatch()` directly with a `Call` that spends that balance/allowance to an attacker-controlled address. This is the same "no namespace restriction" root cause as the CVE: execution power is granted unconditionally to whoever supplies the payload, with no allowlist of targets/callers analogous to the missing `global_dict={"__builtins__": {}}`.

Additionally, because `dispatch()` has no reentrancy guard, if any call in a batch invokes a token/contract with reentrant callback hooks (e.g. ERC-777-style tokens), the callback can re-enter `dispatch()` mid-execution while the current order's assets are still sitting in the dispatcher and before the sweep-back transfer executes, letting the reentrant caller redirect those funds before the legitimate flow finishes.

### Impact Explanation
Any ETH, ERC20 dust, or standing approval left in the shared `CallDispatcher` — arising from normal `IntentGatewayV2` predispatch/postdispatch flows or `HyperFungibleToken`/`WrappedHyperFungibleToken` calldata delivery — is stealable by an unprivileged third party with a single transaction, satisfying "concrete theft of funds" via a permissionless call to a fund-adjacent, reachable contract. This is a Critical-class unauthorized-app-action bug: the dispatcher performs privileged token movements (`transferFrom`/`transfer`/native sends) on behalf of whichever address happens to call it, without verifying the caller is one of the trusted apps that is supposed to own the moment-in-time balance/allowance.

### Likelihood Explanation
High. No special privileges, governance compromise, or malicious-node assumption is needed — this is directly reachable from a single, unprivileged, permissionless call to `CallDispatcher.dispatch()`, which is publicly deployed and callable by design (per the interface's own "dispatch untrusted calls" comment). Any window where dust, an approval, or reentrant execution leaves value in the dispatcher is directly and trivially exploitable.

### Recommendation
Restrict `CallDispatcher.dispatch()` to only be callable by the specific app contract(s) that are meant to use it (`onlyAuthorizedCaller` allowlist set at construction/config, mirroring `onlyHost`), or deploy a fresh, single-use dispatcher per call so no shared, standing state (balance/allowance) can ever exist between transactions. Add a reentrancy guard on `dispatch()`. Enforce exact-amount approvals (revoke after use) instead of relying on documentation-only guidance, and sweep any non-listed token balances back to the calling app rather than leaving them on the dispatcher.

### Proof of Concept
1. `IntentGatewayV2.fillOrder()` executes a postdispatch call via `_execute()` that has the `CallDispatcher` approve a router with `type(uint256).max` (as shown in the project's own documented Uniswap example) as part of a legitimate swap-then-deliver flow: [6](#0-5) 
2. In a later, unrelated transaction, an attacker calls `CallDispatcher.dispatch()` directly (no access control gate exists) with a `Call` targeting that router, invoking a swap function that pulls from the dispatcher's still-standing allowance and any token balance (dust) currently held by the dispatcher, directing proceeds to the attacker's address: [1](#0-0) 
3. Because `dispatch()` never checks `msg.sender`, this succeeds regardless of who calls it, confirming the permissionless drain.

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

Existing `CallDispatcher` deployments are listed on the [contract addresses](/developers/evm/contract-addresses/mainnet) page.
