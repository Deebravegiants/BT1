## Title
Unrestricted `CallDispatcher.dispatch()` Allows Anyone to Drain Any Funds Held by the Shared Dispatcher Contract - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch()` has no access control whatsoever — any address can call it directly and force the dispatcher to execute an arbitrary, attacker-supplied `Call[]` array in the dispatcher's own context. Because `CallDispatcher` is a single, shared, reusable contract that multiple `HyperFungibleToken`/`WrappedHyperFungibleToken` deployments and `IntentGatewayV2` route bridged tokens and native ETH through, any balance it is holding — even transiently, or as leftover dust — can be swept out by an unprivileged caller before the legitimate gateway/token flow consumes it, exactly the same root cause as the referenced report: a callback/entry-point that executes attacker-controlled parameters against a contract that can legitimately hold funds, with no restriction on who triggers it.

### Finding Description
`CallDispatcher.dispatch()` is defined with no modifier or `msg.sender` check at all: [1](#0-0) 

It accepts native ETH via a public `receive()`, decodes an attacker-supplied `Call[]`, and executes `to.call{value: call.value}(call.data)` for every entry — all from the dispatcher's own address as `msg.sender`. This is documented as intentionally "used to dispatch untrusted call(s)": [2](#0-1) 

The dispatcher is meant to be used only as a transient pass-through within a single atomic transaction: `HyperFungibleToken.onAccept` mints tokens directly to the dispatcher (when the sender sets `to = dispatcher`) and immediately calls `dispatch()` in the same call: [3](#0-2) 

`IntentGatewayV2`/`IntentsBase._execute` follows the identical pattern — assets are pushed to the dispatcher, `dispatch()` is called, and only afterward is any residual balance swept back: [4](#0-3) 

The documentation itself acknowledges the dispatcher "holds tokens temporarily during execution" and that sweeps happen only "after execution": [5](#0-4) 

Because a single `CallDispatcher` instance is shared across many independent token and intent-gateway deployments ("Existing `CallDispatcher` deployments are listed on the contract addresses page"), and `dispatch()` carries zero authorization, any balance it is currently holding — dust left behind when a swap/route in a prior `Call[]` doesn't fully consume the tokens it received, excess native ETH forwarded via `Call.value` that the target doesn't consume, or funds mistakenly sent directly to the dispatcher's `receive()` — is completely unprotected. Exactly as in the referenced flashloan-griefing report (an unprivileged caller invokes a callback with attacker-chosen parameters against a contract that happens to be holding funds), any address can call `CallDispatcher.dispatch()` directly with a `Call[]` such as `{to: token, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, dispatcher.balance)}` or `{to: attacker, value: address(dispatcher).balance, data: ""}` to steal whatever the dispatcher currently holds.

### Impact Explanation
This allows outright theft of funds: any ERC20 balance or native ETH sitting in the shared `CallDispatcher` at any point in time — whether because a prior legitimate route under-consumed the assets sent to it, a `Call` sequence partially completed leaving unswept dust, or a user error sent funds directly to it — can be swept by any unprivileged third party, permanently and irreversibly, before the legitimate owner's sweep/dispatch logic runs. Since the dispatcher is shared infrastructure used by every `HyperFungibleToken`/`WrappedHyperFungibleToken` deployment and `IntentGatewayV2`, this is a systemic drain vector rather than one isolated to a single deployment.

### Likelihood Explanation
The attack requires only a single unauthenticated transaction calling `dispatch()` directly with attacker-chosen `Call[]` — no proofs, consensus verification, or relayer cooperation needed. The only precondition is that the dispatcher currently holds a nonzero balance, which is plausible any time a routed swap/call sequence doesn't perfectly zero out the dispatcher's balance within the same transaction, or between the moment tokens/ETH land in the dispatcher and the moment the initiating contract's own `dispatch()`/sweep call executes (both of which are external calls the dispatcher itself does not control or authenticate).

### Recommendation
Restrict `CallDispatcher.dispatch()` to a caller allow-list (e.g., an `onlyAuthorizedCaller` modifier checking `msg.sender` against a registry of gateways/tokens permitted to use this dispatcher instance), or make the dispatcher single-use/ephemeral per call (e.g., deploy a fresh, self-destructing dispatcher per operation, or require the caller to pass a commitment/capability token minted atomically by the legitimate flow). At minimum, add a reentrancy/ownership guard so that only the contract that funded a given `dispatch()` invocation in the same transaction can trigger it.

### Proof of Concept
1. Assume `CallDispatcher` at address `D` currently holds `100 DAI` (e.g., left over from a prior `IntentGatewayV2` predispatch swap that didn't fully consume the approved amount, or a `HyperFungibleToken.onAccept` call-dispatch flow where the destination call under-spent the minted tokens).
2. Attacker calls, with no special privileges:
```solidity
Call[] memory calls = new Call[](1);
calls[0] = Call({
    to: address(DAI),
    value: 0,
    data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, 100 ether)
});
CallDispatcher(D).dispatch(abi.encode(calls));
```
3. Since `dispatch()` has no access control, this executes `DAI.transfer(attacker, 100 ether)` from `D`'s own balance, transferring the dust/leftover funds to the attacker regardless of which gateway or token originally routed them into `D`.

     *  @dev reverts if the target is not a contract or if any of the calls reverts.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

Existing `CallDispatcher` deployments are listed on the [contract addresses](/developers/evm/contract-addresses/mainnet) page.
