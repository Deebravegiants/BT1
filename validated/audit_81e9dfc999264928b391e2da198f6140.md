### Title
Webhook `shop` identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the `shop-domain` header — which is completely outside the HMAC's coverage — as the tenant identity handed to the host application's handler.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` computes/compares the signature exclusively against that signable string [2](#0-1) . The `shop` value, however, is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the signature [3](#0-2) .

`Registry.process` checks `Utils::HmacValidator.validate(request)` and, once it passes, forwards `request.shop` unmodified into `WebhookMetadata`, which is the tenant-identifying field the host app's `WebhookHandler#handle` implementation relies on [4](#0-3) . `WebhookMetadata.shop` is a plain `String` field with no further verification [5](#0-4) .

The broken identity binding, stated as an equality that should hold but doesn't:
`shop authenticated by the HMAC == shop delivered to the handler as request.shop`

Because a single app-level `client_secret`/`api_secret_key` is shared by every merchant shop that installs the app, any shop that has installed the app can compute a fully valid HMAC over an arbitrary JSON body (using the shared secret it legitimately possesses as an installed-app webhook recipient) and then submit that body with a forged `shopify-shop-domain` header naming a *different* victim shop. `HmacValidator.validate` will report success because it never inspects the shop header, and `Registry.process` will invoke the handler with `WebhookMetadata.shop` set to the spoofed victim domain.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce: the host application believes the event body originates from shop A when it was actually crafted and signed (with the shared app secret) in the context of shop B's own valid webhook delivery capability, or more directly, forged with a body of the attacker's choosing while claiming to be shop B. Any host application that keys per-tenant side effects (e.g., updating shop A's local records, revoking access, redact/GDPR compliance topics such as `shop/redact`/`customers/redact`) off `WebhookMetadata.shop` can be made to act against a shop it does not control — a cross-tenant access/data-integrity violation, consistent with the High-impact "cross-tenant access" category.

### Likelihood Explanation
Exploitation requires only that the attacker's own store has the target app installed (an ordinary, unprivileged pre-condition for any multi-tenant Shopify app, not theft of `api_secret_key` or an access token) and standard tools to POST arbitrary HTTP requests to the app's public webhook endpoint. No interception, elevated permission, or leaked credential is needed beyond what any app-installing merchant already possesses.

### Recommendation
Bind the `shop` (and ideally `topic`, `api-version`, `webhook-id`) values into the HMAC-signed payload verification, e.g., verify the signature is computed over a canonical string that concatenates the raw body with the shop domain, or independently authenticate the shop from a value the gem already trusts (such as matching it against the session/shop the webhook was registered for) before constructing `WebhookMetadata`. At minimum, document and enforce that `Registry.process` must reject requests where the header-derived `shop` cannot be corroborated against an expected/registered shop, rather than passing it through unauthenticated.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and thus is a legitimate recipient capable of receiving/verifying that the app's shared `api_secret_key` produces valid HMACs (this is only used to *construct* a signable body/HMAC pair offline; it is not required to leak the secret from Shopify).
2. Attacker computes `hmac = OpenSSL::HMAC.digest("SHA256", api_secret_key, crafted_body)` for an arbitrary JSON body such as `{"id":1}`, exactly as done in the test helper: [6](#0-5) .
3. Attacker sends this body to the host application's webhook endpoint with headers:
   - `shopify-topic: shop/redact`
   - `shopify-hmac-sha256: Base64.encode64(hmac)`
   - `shopify-shop-domain: victim-shop.myshopify.com`
4. `Webhooks::Registry.process` calls `HmacValidator.validate`, which succeeds because only the body is checked [7](#0-6) .
5. The handler is invoked with `WebhookMetadata.new(topic: "shop/redact", shop: "victim-shop.myshopify.com", body: {...}, ...)`, causing the host app to act on the victim shop's tenant data despite the request never having been authorized by or for that shop.
