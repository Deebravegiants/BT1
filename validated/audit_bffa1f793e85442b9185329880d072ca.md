### Title
`createWithdrawalIntents`/`signAndSendWithdrawalIntent` accept `amount == feeEstimation.amount` and silently produce a zero-amount withdrawal intent that still charges the fee - ([File: packages/intents-sdk/src/sdk.ts])

### Summary
`IntentsSDK.createWithdrawalIntents` (and the `signAndSendWithdrawalIntent` wrapper that calls it) compute `actualAmount = withdrawalParams.amount - feeEstimation.amount` when `feeInclusive` is true, but never verify `actualAmount > 0n`. The `FeeExceedsAmountError` guard exists only in `_estimateWithdrawalFee`, so any caller who invokes `createWithdrawalIntents`/`signAndSendWithdrawalIntent` directly with a `feeEstimation.amount` equal to `withdrawalParams.amount` gets a signed `ft_withdraw`/`mt_withdraw`/`native_withdraw` intent with `amount: "0"` while the `token_diff` intent still moves the full fee.

### Finding Description
Equality claimed to hold: `destinationAmount(shown to caller) == destinationAmount(delivered on-chain)`.

Trace:
- `packages/intents-sdk/src/sdk.ts:334-372` (`createWithdrawalIntents`):
```
const actualAmount = args.withdrawalParams.feeInclusive
    ? args.withdrawalParams.amount - args.feeEstimation.amount
    : args.withdrawalParams.amount;

await bridge.validateWithdrawal({ ..., amount: actualAmount, ... });
return bridge.createWithdrawalIntents({ withdrawalParams: {...args.withdrawalParams, amount: actualAmount}, feeEstimation: args.feeEstimation, ... });
```
There is **no** check that `actualAmount > 0n` here.

- Compare to `_estimateWithdrawalFee` (`packages/intents-sdk/src/sdk.ts:408-453`), which is the *only* place the guard exists:
```
if (args.withdrawalParams.feeInclusive) {
    if (args.withdrawalParams.amount <= fee.amount) {
        throw new FeeExceedsAmountError(fee, args.withdrawalParams.amount);
    }
}
```
This check uses `<=`, so it does reject the equality case — but only inside `_estimateWithdrawalFee`. It is not re-applied by `createWithdrawalIntents` or by `signAndSendWithdrawalIntent` (`sdk.ts:689-743`), both of which are public, independently callable entry points (`IIntentsSDK.createWithdrawalIntents`, `IIntentsSDK.signAndSendWithdrawalIntent`, `shared-types.ts:176-205`).

- Downstream bridge implementations do not add their own `amount > 0` assertion either:
  - `bridges/omni-bridge/omni-bridge.ts:283-330` and `omni-bridge-utils.ts:29-76` build `ft_withdraw` with `amount: amount.toString()` unconditionally, while still emitting the `token_diff` intent that debits the fee-quote input token.
  - `bridges/direct-bridge/direct-bridge-utils.ts:19-61`, `bridges/aurora-engine-bridge/aurora-engine-bridge-utils.ts:11-51`, and `bridges/poa-bridge/poa-bridge-utils.ts:6-26` likewise stringify `amount` with no positivity check.
  - `bridges/hot-bridge/hot-bridge.ts:177-252` has a sanity `assert(intent.amounts[0] === amount.toString(), ...)`, which only checks consistency with the computed amount, not that the amount is nonzero.

Root cause: the invariant "withdrawal amount after fee deduction must be positive" is enforced in exactly one of the two code paths that compute `actualAmount` from the same formula, and the other path (`createWithdrawalIntents`, and therefore `signAndSendWithdrawalIntent`) is missing it. A caller that supplies (directly or via a stale/self-sourced `feeEstimation`) an `amount` equal to `feeEstimation.amount` bypasses the only existing check and gets a signed, published intent that debits the fee (via `token_diff`) and consumes the nonce, while the on-chain withdrawal leg moves `0`.

Why existing guards fail: `validateWithdrawal` (bridge-specific) only checks minimum-amount/trustline/address constraints, not "amount != 0 caused by fee-equal edge case"; none of the bridges independently assert `actualAmount > 0n`; `FeeExceedsAmountError` is thrown by `_estimateWithdrawalFee` only, and nothing forces callers of `createWithdrawalIntents`/`signAndSendWithdrawalIntent` to have gone through that function first with the exact same `amount`/`feeEstimation` pair.

### Impact Explanation
- What is signed: an intent bundle containing a `token_diff` (debiting the full fee amount from the signer) and a zero-amount `ft_withdraw`/`mt_withdraw`/`native_withdraw`.
- What is debited: the fee, in full, from the caller's intents balance.
- What is misrouted: nothing is misrouted, but nothing of value reaches the destination — the caller is shown/expects a withdrawal of some positive `withdrawalParams.amount` but the destination chain receives `0`.
- Repeatability: repeatable per call, deterministic whenever `amount == feeEstimation.amount` with `feeInclusive: true` and the call bypasses `_estimateWithdrawalFee`'s check.
- Matches the "fee error draining a material share of the amount" Critical category, since 100% of the withdrawal amount is consumed as fee with zero delivered.

### Likelihood Explanation
- Preconditions: `feeInclusive: true`, and `withdrawalParams.amount === feeEstimation.amount` at the time `createWithdrawalIntents`/`signAndSendWithdrawalIntent` is invoked.
- This requires either (a) calling these methods directly without first running `estimateWithdrawalFee` on the identical amount, or (b) reusing a `feeEstimation` object obtained for a different amount/time that happens to equal the withdrawal amount (e.g., stale fee cache, or fee estimation for one amount reused for another). Both are realistic integration patterns since `feeEstimation` is a plain, caller-supplied structure and the SDK's own README documents fetching it once and passing it along to `signAndSendWithdrawalIntent` separately — nothing in the type system or runtime prevents mismatched pairs.
- If the normal SDK flow is always `estimateWithdrawalFee()` → `signAndSendWithdrawalIntent()` with the exact same params on every call, the bug is not triggered because the upstream `<=` check already rejects equality. The vulnerability specifically manifests when integrators (or code paths) skip or decouple that step, which is plausible but not the SDK's own enforced invariant — a defense-in-depth gap.

### Recommendation
Add the same `actualAmount > 0n` guard (or reuse `FeeExceedsAmountError`) directly inside `createWithdrawalIntents` (`sdk.ts:342-344`) before calling `bridge.validateWithdrawal`/`bridge.createWithdrawalIntents`, so the check is enforced regardless of whether `_estimateWithdrawalFee` was called first. This closes the gap for both `createWithdrawalIntents` and `signAndSendWithdrawalIntent`.

// packages/intents-sdk/src/sdk.createWithdrawalIntents.zero-amount.test.ts
it("createWithdrawalIntents(): rejects or never emits a zero-amount withdrawal when amount == feeEstimation.amount", async () => {
  const sdk = new IntentsSDK({ referral: "", intentSigner });

  const withdrawalParams = {
    assetId: "nep141:btc.omft.near",
    amount: 1500n, // exactly equal to fee
    destinationAddress: "bc1qsfq3eat543rzzwargvnjeqjzgl4tatse3mr3lu",
    feeInclusive: true,
  };

  const feeEstimation = {
    amount: 1500n,
    quote: null,
    underlyingFees: { [RouteEnum.PoaBridge]: { relayerFee: 1500n } },
  };

  const intentsP = sdk.createWithdrawalIntents({ withdrawalParams, feeEstimation });

  // EXPECTED (secure): should throw FeeExceedsAmountError, matching _estimateWithdrawalFee's `<=` check
  await expect(intentsP).rejects.toThrow(FeeExceedsAmountError);
