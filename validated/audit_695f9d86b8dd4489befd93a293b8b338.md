### Title
Emporium's stateless op-execution mode lets any Emporium-allowed caller drain non-ERC20 assets (e.g. Uniswap V3 LP NFTs) left custodied by the shared `EmporiumUpgradeable` contract from a prior user's operation - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction()` only reconciles ERC20/ETH balances listed in `circomData.erc20TokenAddresses` before and after executing a batch of arbitrary calls (`stack.ops`). When an op is executed in "stateless" mode (`op.invokeWallet == false`), the call is made directly from the Emporium contract itself (`op.endpoint.call{value: op.value}(op.callData)`), so any non-fungible or otherwise untracked asset acquired during that call (e.g. a Uniswap V3 position NFT, an LP receipt token, a staking receipt) is left owned by the shared, multi-tenant Emporium contract rather than by the depositing user. Because Emporium tracks solvency purely via `getBalancesForArray(circomData.erc20TokenAddresses)` deltas, this leftover asset is completely invisible to the balance equation and to any subsequent caller's accounting - exactly the "funds outside the vault, in dynamic accounts as tokens/positions but still owned by the [shared] contract" failure mode described in the report.

### Finding Description
`runAction` computes solvency purely from ERC20/ETH balances of the token list supplied in `circomData`: [1](#0-0) 

For CASE 2 ("Stateless Interaction"), the call target and calldata are attacker-controlled (subject only to the EIP-712 signature check when `stack.signerAddress != address(0)`, but that check is entirely skipped when `stack.signerAddress == address(0)`): [2](#0-1) [3](#0-2) 

`verifyWallet` only reverts on unused-message/signature checks when a `signerAddress` is present; with `signerAddress == address(0)` it just marks the message used and returns, imposing no restriction on `op.endpoint`/`op.callData` beyond the anti-reentry selector check for `callHinkalWallet`/`doSendToRelay`: [4](#0-3) 

Any address holding `onlyAllowedRecipient` access (i.e. reachable through `Hinkal._externalTransact`, callable by any prover with a valid zk-SNARK proof, not an owner/admin) can therefore direct Emporium to `call()` an arbitrary contract, e.g. Uniswap V3's `NonfungiblePositionManager.mint(...)`, using the ERC20 balance Emporium is holding for that transaction (bounded by `deltaAmountChanges`, so no over-withdrawal from the shielded pool is required to trigger this). The resulting position NFT is minted to `address(this)` (the Emporium contract) because the low-level call executes with `msg.sender == Emporium`. Because `circomData.erc20TokenAddresses` never includes ERC-721 token IDs, the NFT is not reflected anywhere in the balance-diff loop, so `handleOut` mints no UTXO for it and the pre/post ERC20 balance check happily passes (the tokens simply "left" Emporium's ERC20 balance and the corresponding delta is fully consumed, satisfying `balanceChange >= 0`): [5](#0-4) 

The Uniswap V3 position (or any other non-tracked asset) is now permanently held by the shared `EmporiumUpgradeable` contract with zero on-chain record of which user funded it. Because Emporium is the literal owner/`msg.sender` for any future stateless call it executes, **any other unprivileged user** can subsequently submit their own (unrelated, even zero-value) valid Emporium transaction whose `op.callData` calls `NonfungiblePositionManager.collect(...)`, `decreaseLiquidity(...)`, or `transferFrom(address(this), attacker, tokenId)` on that same position manager - all of which succeed because `msg.sender == Emporium == owner` requires no prior approval. The stolen tokens returned from that call land back in Emporium's ERC20 balance and are then legitimately swept out to `msg.sender` as a fresh UTXO via `handleOut`, i.e. minted as shielded value belonging to the attacker.

This breaks the intended equality "value moved by Hinkal / an external action is always fully accounted for in the balance equation" - the value silently exits ERC20-balance tracking into an untracked asset class held by a shared custodian, and can be re-captured by any subsequent unrelated caller.

### Impact Explanation
This is theft of another user's protocol-custodied funds by an unprivileged actor with no special role, matching "High: theft or permanent freezing of protocol/relay fees ... executing calls or moving assets a wallet owner or prover never authorised," and arguably escalates to Critical (theft of shielded/in-flight user funds) once the stolen value is re-shielded as a UTXO for the attacker via `handleOut`. The original user whose deposit funded the mint permanently loses the value (their proof was validly consumed, their shielded balance debited, but the corresponding real-world asset is later drained by someone else).

### Likelihood Explanation
Likelihood is Low/Medium in practice: it requires (a) at least one legitimate integration/config that allows stateless (`invokeWallet == false`, `signerAddress == address(0)`) Emporium ops to target a contract that can leave the Emporium contract holding a non-ERC20 receipt (NFT/LP token/position) rather than immediately returning ERC20s, and (b) an attacker who discovers/enumerates that leftover asset (e.g., via on-chain events revealing `tokenId`s minted to the Emporium address). Given `op.endpoint`/`op.callData` are unrestricted for the stateless path and the token id / asset location is derivable from public chain data (mint events, `ownerOf` enumeration), this is realistically exploitable wherever Emporium is wired up to interact with any protocol that issues non-fungible or otherwise off-ledger receipts.

### Recommendation
- Disallow stateless (`signerAddress == address(0)`, no wallet indirection) execution against endpoints capable of returning/holding non-ERC20 receipts (NFTs, LP shares) to the Emporium contract itself; force all such interactions through a per-user `IHinkalWallet` (`invokeWallet == true`) so custody never mixes across users.
- Alternatively, maintain an explicit registry inside Emporium of any non-ERC20 assets it ends up holding, tagged to the depositing user/message, and require any op that would leave residual custody at `address(this)` to be rejected or fully swept/verified back into the tracked ERC20 balance set before `runAction` returns.
- As an immediate mitigation (matching the original report's suggestion), restrict/allowlist `op.endpoint` targets for the stateless path to only those known to fully settle in the declared `circomData.erc20TokenAddresses` set within the same call.

### Proof of Concept
1. User A submits a valid Hinkal proof/`CircomData` with `externalActionData.externalAddress = Emporium`, withdrawing `X` USDC from the shielded pool (`deltaAmountChanges[0] = -X`), with an `EmporiumStack` containing a stateless op (`invokeWallet=false`, `signerAddress=address(0)`) whose `callData` calls Uniswap V3 `NonfungiblePositionManager.mint(...)` using the `X` USDC held by Emporium (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:91-118`). The mint succeeds; the LP NFT (`tokenId = N`) is minted to `address(this)` == Emporium. USDC balance of Emporium decreases by `X`, matching `deltaAmountChanges`, so `balanceChange == 0` and no UTXO is created for it (`EmporiumUpgradeable.sol:132-151`) - the position is now silently custodied by Emporium with no on-chain link to User A.
2. Attacker (any other prover, needs no special role) observes the `Mint`/`Transfer` event revealing `tokenId = N` owned by the Emporium contract.
3. Attacker submits their own valid Hinkal proof (even for an unrelated/zero deposit) to Emporium with a stateless op calling `NonfungiblePositionManager.collect(N, ...)` (or `decreaseLiquidity` + `collect`, or `transferFrom(Emporium, attacker, N)`), which succeeds because `msg.sender == Emporium == owner of N`.
4. The collected/withdrawn USDC increases Emporium's tracked ERC20 balance, producing a positive `balanceChange` in `handleOut`, which mints a fresh UTXO to the attacker (`EmporiumUpgradeable.sol:146-150`), completing the theft of User A's original deposit.
