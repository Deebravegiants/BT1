This confirms the vulnerability. The docs explicitly state that `Registry.process` "will verify the request did indeed come from Shopify" (line 125 of `docs/usage/webhooks.md`), and the `data.shop` field is documented as "The shop domain of the webhook" (line 14) intended to be trusted by the host app to key data per-tenant (as shown in the example handler passing `shop_domain: data.shop` at line 26). But the HMAC only signs the raw body, never the shop header, breaking that trust guarantee.

### Title
Webhook `shop` field is not covered by HMAC verification, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's authenticity using only the HMAC of the raw request body, then trusts the `shop-domain` header verbatim and passes it to the app's webhook handler as the authoritative shop for the event. Since the `shop-domain` header is not part of the HMAC-signed content, any party capable of obtaining one valid `(body, hmac)` pair for the shared app secret can replay it with an arbitrary `shop-domain` header, causing the host application to attribute the payload to a different (victim) shop.

### Finding Description
`Registry.process` performs exactly one authenticity check: [1](#0-0) [2](#0-1) 

The check is `Utils::HmacValidator.validate(request)`, which computes the signature over `request.to_signable_string`: [3](#0-2) 

`to_signable_string` returns only `@raw_body`. It does **not** include the `topic`, `shop-domain`, `webhook-id`, or `api-version` headers: [4](#0-3) 

`HmacValidator.validate` then computes `HMAC-SHA256(api_secret_key, raw_body)` and compares it to the `hmac` header: [5](#0-4) 

Once this body-only HMAC check passes, `Registry.process` builds `WebhookMetadata` using `request.shop`, which is read straight from the unauthenticated `shop-domain` header, with no cross-check against the body content or against any shop-specific secret: [6](#0-5) [7](#0-6) 

The binding that should hold is: `shop that the app attributes the event to == shop the HMAC-signed payload was actually generated for`. Because `to_signable_string` excludes the shop header, this equality is never enforced — the HMAC only proves "the body was generated using this app's `api_secret_key`", not "this specific shop generated this event." Since `api_secret_key` is the app's single client secret shared across **every** shop that installs the app (not a per-shop secret), any merchant who has legitimately installed the app on their own store can capture a valid `(raw_body, hmac)` pair (e.g., by triggering a benign webhook such as `app/uninstalled` on their own shop, or via a local dev app grant), then replay that exact body+HMAC directly to the app's public webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. The signature still validates (it only checks the body), but `request.shop` now falsely claims to be the victim.

The docs confirm this field is meant to identify "The shop domain of the webhook" and is the value host applications are expected to key their per-tenant logic on (session lookup, data association, uninstall handling, etc.): [8](#0-7) 

### Impact Explanation
This breaks the tenant-isolation guarantee the gem is documented to provide ("verify the request did indeed come from Shopify" for *that* shop). An attacker who is an ordinary, unprivileged installer of the app on their own shop can forge a webhook that a host application will process as if it came from an arbitrary victim shop — for example, replaying a forged `app/uninstalled` event to trigger session/data deletion for a victim tenant, or injecting crafted `orders/create`/`customers/update` payloads that get associated with and processed against the victim shop's records. This is a cross-tenant confusion/forgery vulnerability reachable without any credentials beyond having installed the app once on one's own store, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
High. No secret material belonging to the victim or the merchant's `api_secret_key` is required — the attacker only needs one legitimate, self-generated webhook body+HMAC pair from their own shop (trivially obtainable by any developer/merchant who installs the app) and the ability to POST directly to the app's public webhook URL with a custom `shop-domain` header, entirely bypassing Shopify's servers.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the HMAC-verified surface, or otherwise cryptographically tie the claimed shop to the signed body — for example, by including the `shop-domain`, `topic`, and `webhook-id` headers in `to_signable_string` (mirroring what Shopify actually signs) so `HmacValidator.validate` fails if any of them are altered, rather than validating the raw body alone.

### Proof of Concept
1. App installs on attacker's own shop `attacker.myshopify.com`, using the app's single shared `api_secret_key`.
2. Attacker triggers any subscribed webhook (e.g. `app/uninstalled`) on their own shop and captures the raw POST: body `B`, headers including `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the shared `api_secret_key`) and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker sends a direct POST to the app's webhook endpoint with the same body `B` and the same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H` [3](#0-2) .
5. `Registry.process` invokes the app's handler with `shop: "victim.myshopify.com"` [6](#0-5) , causing the host app to act on victim tenant data based on a forged event.
