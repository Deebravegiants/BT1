### Title
Webhook shop/topic identity is not covered by HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (and `topic`) used to dispatch webhook data from unauthenticated HTTP headers, while `Utils::HmacValidator` only verifies the HMAC over the raw request body. This breaks the identity binding "the shop that produced/authorized the signed payload == the shop attributed to the payload when processed", allowing a malicious merchant to replay their own validly-signed webhook body against a different shop's identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` (and `#topic`, `#webhook_id`, `#api_version`) are pulled straight from HTTP headers, which are never included in the signable string: [2](#0-1) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (i.e. the body) and compares it against `verifiable_query.hmac`: [3](#0-2) 

`Registry.process` treats HMAC success as proof of authenticity for the whole request, then dispatches using the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id`: [4](#0-3) 

Because Shopify's webhook HMAC is computed over the body only (this is inherited from Shopify's own webhook signing scheme and this gem's verifier faithfully mirrors it), the `shop-domain`/`topic`/`webhook-id` headers are not bound to the signature at all. Any entity that can obtain one validly-signed `(raw_body, hmac)` pair for the app — trivially available to any merchant who installs the app on their own store and triggers a webhook event (e.g. `orders/create`) — can replay that exact body+hmac pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header (and/or `x-shopify-topic`, `x-shopify-webhook-id`). `HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` will hand the handler a `WebhookMetadata` whose `shop` is the attacker-chosen victim shop while `body`/`topic` are attacker-controlled from their own legitimately-signed payload.

This is exactly the "field acted on but not covered by the HMAC" identity-binding class: the equality that should hold is `shop_that_authorized(hmac, body) == shop_attributed_to(body)`, but the gem lets an attacker make `shop_attributed_to(body)` diverge from the true source shop.

### Impact Explanation
Any host application that trusts `WebhookMetadata#shop` (returned by this gem after `process` succeeds) to scope tenant data — the documented and intended usage pattern — can be made to apply attacker-controlled webhook content under a victim shop's tenant context. This is a cross-tenant data-integrity/confusion issue: an unprivileged merchant (attacker) who has ordinary access to only their own store can inject data or trigger tenant-scoped side effects (e.g. order/customer records, GDPR redact-type flows, inventory updates) attributed to a different merchant's shop, without any credentials belonging to the victim or to the app itself.

### Likelihood Explanation
Any merchant who installs the app (a normal, unprivileged action requiring no special access) automatically obtains one or more genuinely HMAC-signed webhook deliveries for their own store by simply performing ordinary actions (creating an order, updating a product, etc.). Capturing raw request bodies and headers sent to their own publicly reachable webhook endpoint is trivial. Replaying the captured `(body, hmac)` while swapping the shop-domain header requires no cryptographic secret and no interaction with Shopify's systems.

### Recommendation
Bind the shop (and topic) identity into the HMAC-verified surface, e.g. by including `shop-domain`/`topic`/`webhook-id` in the signable payload used by `HmacValidator`, or by having the host application independently authenticate the shop identity through an out-of-band, already-authorized session/mapping (not header-only) before trusting `request.shop`. At minimum, document loudly that `request.shop`/`request.topic` are NOT covered by the HMAC and must not be trusted for tenant routing without additional verification (e.g. cross-checking against a known/registered shop for that webhook subscription id).

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers, say, an `orders/create` event, causing Shopify to POST a webhook to the app's endpoint with headers:
   - `x-shopify-hmac-sha256: <valid HMAC over raw body>`
   - `x-shopify-shop-domain: attacker.myshopify.com`
   - `x-shopify-topic: orders/create`
2. Attacker captures the exact `raw_body` and `x-shopify-hmac-sha256` value from that delivery (they control the endpoint, e.g. via a request logger or their own dev tunnel).
3. Attacker crafts a new HTTP POST to the same webhook endpoint, keeping `raw_body` and `x-shopify-hmac-sha256` identical, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the untouched body/HMAC pair:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
```
5. `handler.handle` is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: request.parsed_body, ...)`, causing the app to process attacker-controlled data as if it originated from `victim-shop.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
