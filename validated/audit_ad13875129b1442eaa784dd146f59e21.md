### Title
Webhook `shop-domain` header is not bound by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` claims to "verify the request did indeed come from Shopify" before invoking the app's handler, but the HMAC check only covers the raw request body, not the `shop-domain` header that identifies which merchant the webhook belongs to. Because the signing secret (`Context.api_secret_key`) is the same for every shop that installs a given app, a merchant who has installed the app can capture a legitimately-signed webhook delivered to their own store and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header swapped to a victim shop's domain. The signature still validates, and the handler is invoked believing the payload originated from the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `shop` is read directly from a header outside the signed payload: [1](#0-0) 

`HmacValidator.validate` computes/compares the signature strictly against `to_signable_string`, i.e. the body bytes, using the app's shared `api_secret_key`: [2](#0-1) 

`Registry.process` only calls `Utils::HmacValidator.validate(request)` and then forwards `request.shop` straight into the handler's metadata with no additional binding check between the header-supplied shop and the verified body: [3](#0-2) 

The documentation explicitly tells integrators that `Registry.process` "will verify the request did indeed come from Shopify," implying the whole request — including the shop identity — is authenticated: [4](#0-3) 

This breaks the intended identity binding: **shop header claimed == shop the signature actually authenticates**. In reality, the equality that holds is only `HMAC(raw_body, api_secret_key) == received_hmac`; the `shop` header is unauthenticated attacker-controlled data acted upon by the handler (`data.shop`).

### Impact Explanation
Because `api_secret_key` is shared across all installs of the same app, any merchant who installs the app (an unprivileged, non-victim tenant) can obtain validly-signed webhook bodies for their own shop and replay them against the app's webhook endpoint while forging the `shop-domain` header to point at a different, victim shop. Any app logic that trusts `WebhookMetadata#shop` (e.g., to select which tenant's records to create/update, or to attribute the payload to a specific merchant) can be tricked into writing or acting on attacker-supplied data under another tenant's identity — a cross-tenant data-integrity/impersonation issue reachable purely from the gem's documented API.

### Likelihood Explanation
Exploitability requires the attacker to be a legitimate (if malicious) installer of the target app — an unprivileged position relative to other merchants using the same app — and to know or guess a victim shop's `myshopify.com` domain (which is public/discoverable). No access token, `api_secret_key`, or privileged access is required; only observation of one webhook delivery to their own store and a modified HTTP replay.

### Recommendation
Bind the shop identity to the verified payload instead of trusting the header in isolation: include the shop domain in the HMAC-covered signable string, or cross-check the header-supplied `shop-domain` against the shop associated with the specific webhook subscription/session that received the request before invoking the handler. At minimum, update `ShopifyAPI::Webhooks::Registry.process` and its documentation to make clear that `shop` is not covered by Shopify's HMAC and must be independently validated by the consuming application against a trusted session/shop record.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and registers for a webhook topic (e.g., `orders/create`).
2. Shopify delivers a webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over raw body>`, and the JSON body.
3. Attacker captures the raw body and HMAC, then re-sends the identical body/HMAC to the same endpoint but replaces the header with `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks the raw body against the shared secret.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` invokes the app's handler with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, causing the application to process attacker-controlled data as if it belongs to `victim.myshopify.com`.
