Confirmed. `WebhookMetadata` is constructed directly from `request.shop`/`request.topic` with no independent validation against the HMAC-signed content.

### Title
Webhook shop/topic/id headers are unauthenticated because the HMAC only covers the raw body, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
The webhook signature verification in this gem authenticates only the raw request body. The `shop-domain`, `topic`, `api-version`, and `webhook-id` values — which are trusted as the identity of the tenant the event belongs to — are read straight from HTTP headers and are never included in the HMAC computation. Anyone capable of obtaining one valid webhook delivery (e.g. by installing the app on their own store, which requires no privileged access) can replay that body with its untouched, still-valid HMAC while swapping the `shop-domain` header to any other shop, and the gem will accept it and hand it to the app's handler as if it came from the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all separate accessors that read directly from headers and are not part of the signed material: [2](#0-1) 

`HmacValidator.validate` computes the signature exclusively over `verifiable_query.to_signable_string`, i.e. the body, and compares it against the `hmac-sha256` header: [3](#0-2) 

`Registry.process` gates only on this body-only HMAC check, then forwards `request.shop` (an unauthenticated header value) straight into `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The binding that should hold is: `shop authenticated by HMAC == shop acted upon by the handler`. Because the HMAC is computed over the body only, this equality does not hold — the `shop-domain` header can be freely substituted after a genuinely-signed body is obtained, without invalidating the HMAC.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook delivery: an entity that has installed the app on *any* store (an ordinary, unprivileged action requiring no special credentials, leaked secrets, or victim interaction) can, from a single legitimately received webhook, produce forged deliveries that the app's handler will process as belonging to a **different, arbitrary shop**. Depending on the handler logic (e.g. `shop/redact`, `customers/data_request`, order/customer sync, GDPR webhooks, billing state changes), this enables cross-tenant data manipulation or disclosure — the app will act on/for a shop the attacker does not control, using data (body) associated with the attacker's own shop. This matches the Critical "cross-tenant access" impact category: the HMAC only proves "this body was signed by Shopify for this app," never "this body came from this specific shop."

### Likelihood Explanation
High. No credentials, secrets, or privileged access are needed beyond installing the app on a store the attacker controls (the normal, intended, unprivileged way any merchant uses the app) and being able to POST to the app's public webhook endpoint (which must be internet-reachable by design for Shopify to deliver webhooks). Capturing one's own valid webhook body+HMAC pair and replaying it with a modified `shop-domain` header is trivial and requires no exploitation of TLS, no reverse engineering of secrets, and no interaction with the victim.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`, or at minimum `shop-domain`) in the signed material that is verified, or independently cross-check `shop-domain` against a value derived from data that is covered by the HMAC (e.g. embed/verify the shop domain in the body, or validate it against the session/store that registered the webhook, per topic). Do not treat any header as authenticated unless it is provably covered by the HMAC signature.

### Proof of Concept
1. Install the app on shop `attacker.myshopify.com`; receive a legitimate webhook, capturing `raw_body`, the `x-shopify-hmac-sha256` header, and other headers.
2. Send a new HTTP request to the app's public webhook endpoint with the exact same `raw_body` and `x-shopify-hmac-sha256` value, but with `x-shopify-shop-domain` changed to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present); `HmacValidator.validate` succeeds because it only checks the body against the HMAC, which is unchanged and still valid.
4. `Registry.process` invokes the registered handler with `WebhookMetadata#shop == "victim.myshopify.com"`, even though the event body actually originated from the attacker's own shop.
