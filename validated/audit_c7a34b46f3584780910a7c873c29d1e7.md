The HMAC only signs the raw body, never the shop header.### Title
Webhook shop-domain identity spoofing via HMAC that only covers the request body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) for an inbound webhook purely from the unauthenticated `X-Shopify-Shop-Domain` HTTP header, while `ShopifyAPI::Utils::HmacValidator` only verifies the HMAC over the raw request body. The `shop` field is never included in the signed material, so its value can be altered without invalidating the HMAC check.

### Finding Description
`Webhooks::Request#shop` reads the shop identity straight from a header: [1](#0-0) 

The signable string used for HMAC verification is only the raw JSON body, never the headers: [2](#0-1) 

`Registry.process` verifies only that HMAC (i.e., body integrity/authenticity), then immediately hands the handler a `WebhookMetadata` object built from `request.shop`, which is the unauthenticated header value, alongside the verified body: [3](#0-2) 

`HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` header/param — for webhooks this is `HMAC(secret, raw_body)` only: [4](#0-3) 

The identity binding that should hold is: `shop_attributed_to_handler == shop_that_the_HMAC_authenticates`. In this implementation that equality never holds, because the HMAC only authenticates `(secret, raw_body)`, not `(secret, raw_body, shop)`. Consequently:
- **Before** attacker action: a shop that receives a genuine webhook has a body `B` and a valid `hmac = HMAC(secret, B)`, delivered with header `shop-domain: shop-A.myshopify.com`.
- **After** attacker action: the attacker (who legitimately installed the app on their own shop, or intercepted/observed one of their own webhook deliveries) resends the exact same `B` and `hmac` to the app's webhook endpoint, but substitutes the header `shop-domain: shop-B.myshopify.com` (a victim tenant). `HmacValidator.validate` still returns true because it only checks `B`/`hmac`; `Registry.process` then invokes the app's handler with `WebhookMetadata(shop: "shop-B.myshopify.com", body: B, ...)`.

This is documented as the intended tenant-attribution field for host apps (`docs/usage/webhooks.md`: "`shop`, `String` - The shop domain of the webhook"), so downstream apps built on this gem's documented contract (e.g., `perform_later(shop_domain: data.shop, webhook: data.body)`) will process attacker-supplied webhook content under a victim shop's identity, without the gem doing anything to prevent it.

### Impact Explanation
This crosses a tenant boundary: an unprivileged attacker who only needs to be able to install the target app on their own (or any) shop — or simply intercept one legitimate delivery to their own shop — can inject arbitrary webhook payloads that the host application will treat as authentic data belonging to an unrelated victim shop. Any app logic keyed off `data.shop` for tenant-scoped storage, deduplication, order/customer processing, or session lookups can be corrupted or used to write/act on the wrong tenant's records. This matches the "cross-tenant access" criteria (Critical) since the HMAC-authenticated payload is misattributed to an arbitrary target tenant purely by manipulating an unauthenticated header.

### Likelihood Explanation
High. No secrets are required beyond receiving one legitimate webhook (which any shop that installs the app will receive automatically). The attacker only needs to control the outgoing HTTP headers of a replayed request to the app's own publicly reachable webhook endpoint, which is straightforward for any internet client (curl/Burp), since `Registry.process` performs no additional binding check between the signed body and the declared shop.

### Recommendation
Bind the shop identity into the authenticated material, or otherwise cryptographically/contextually verify it before trusting `request.shop`:
- Extend `to_signable_string` for webhook `Request` (or add a secondary check) to incorporate the `shop-domain` header into what is HMAC-verified, mirroring how `AuthQuery#to_signable_string` includes `shop` in its signable params (see `lib/shopify_api/auth/oauth/auth_query.rb`).
- At minimum, cross-check `request.shop` against an expected/registered shop for the specific webhook subscription (e.g., correlate with the shop that owns the `webhook_id`) rather than trusting the header verbatim, and document this requirement clearly so host apps don't rely on `data.shop` as if it were authenticated.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers/receives one genuine webhook (e.g., `orders/create`), capturing:
   - raw body `B`
   - header `X-Shopify-Hmac-Sha256: <valid hmac for B>`
2. Attacker crafts a new HTTP POST to the app's public webhook endpoint with:
   - Body: unchanged `B`
   - Headers: `X-Shopify-Topic: orders/create`, `X-Shopify-Hmac-Sha256: <same captured hmac>`, `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Registry.process` constructs `Webhooks::Request` from these headers/body; `Utils::HmacValidator.validate` succeeds because it only checks `HMAC(secret, B)`, which still matches.
4. The handler receives `WebhookMetadata(shop: "victim-shop.myshopify.com", body: B, ...)` and processes/stores the attacker's data as if it belonged to `victim-shop.myshopify.com`, achieving cross-tenant data injection.
