### Title
Venue-priced (Uniswap V4) fills ignore the pool's swap fee tier, letting intent submitters systematically extract the solver's margin - ([File: sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts])

### Summary
For curveless pairs configured with `[vault.uniswapV4]`, `FXFiller.resolveLegRates` prices fills directly off `UniswapV4FundingPlanner.getExoticTokenPrice`, which returns the raw pool mid-price (`sdkPool.token0Price`/`token1Price`) with the pool's own `fee` tier read but never subtracted. Any user who submits an intent-gateway order matched against a venue-priced pair is quoted (and filled) at a price that omits the cost the solver actually incurs when it swaps through that same pool to source inventory, or when `UniswapV4FundingPlanner.planWithdrawalForToken` decreases liquidity to fund the fill.

### Finding Description
`UniswapV4FundingPlanner.computeDirectPoolPriceUsd` derives `priceUsd` purely from `sdkPool.token0Price`/`token1Price`, i.e., the pool's instantaneous `sqrtPriceX96`-derived mid, with no adjustment for the pool's `fee` (stored on `pos`/`poolKey.fee`) and no size/impact term. [1](#0-0) 

This price is consumed unmodified in `FXFiller.resolveLegRates`, which is on the order-fill path: for a curveless pair whose `token0` is a USD stable, it takes `venueUsd = getVenueUsdPrice(...)`, inverts it into `venueRate`, and returns it directly as the fill rate after only a static-deviation check via `checkPriceGuard` — there is no adjustment for the swap fee or execution cost the solver will actually pay to source the output token. [2](#0-1) 

`checkPriceGuard` only rejects when the venue quote deviates from a fixed `referencePrice` by more than `maxDeviationBps`; it is not a cost/fee check and does not detect a systematically fee-blind price that is always self-consistent with the pool's live mid. [3](#0-2) 

The same unadjusted rate is also used by `referenceRate` to size confirmation-depth requirements, compounding the mispricing into risk-control sizing as well. [4](#0-3) 

The maintainers' own internal note documents this exact gap: "the pool's fee tier is read and stored on the hydrated position (`pos.fee`) but never applied to the price... A venue-priced pair that has to swap through its own pool to source inventory pays a fee tier it never quoted against." [5](#0-4) 

### Impact Explanation
Every fill of a venue-priced pair prices the solver's inventory at the pool mid rather than mid-minus-fee-minus-impact. Because the solver must later withdraw/rebalance through the same pool (or an equivalent-fee pool) to restock the token it just sold, it pays the fee tier (e.g., 5, 30, or 100 bps) plus any real slippage that was never subtracted from what it charged the counterparty. An unprivileged user who repeatedly places orders against a venue-priced pair extracts, order after order, the difference between the naive mid and the true execution cost — a durable value leak from the solver's capital with no bound other than `order.fees`/spread, none of which the current pricing accounts for.

### Likelihood Explanation
This triggers on the ordinary, unprivileged path any intent submitter already uses: dispatching an order matched to a curveless, Uniswap-V4-funded pair, exactly as documented in `docs/content/developers/evm/simplex/pricing.mdx` (`## Pool-Based Pricing`). No special permissions, governance action, or malicious operator behavior is required — a normal user or automated arbitrage bot placing orders against any solver that has enabled `[vault.uniswapV4]` pool pricing without a curve will realize this on every fill.

### Recommendation
Deduct the pool's `fee` (in `poolKey.fee`, already read and stored per position) from the venue mid before it is used as `venueRate`/`venueUsd`, and additionally apply a price-impact/slippage estimate sized to the order notional (mirroring `spreadBps` used for LP redemption slippage) rather than treating the whole quantity as fillable at the raw mid. `checkPriceGuard` should remain as an independent sanity check against stale/manipulated reference prices, not a substitute for cost-aware pricing.

### Proof of Concept
1. Configure `[vault.uniswapV4]` with a position on a 0.30% (or higher) fee-tier pool and a curveless pair (`USDC`/`EXOTIC`) with no `bidPriceCurve`/`askPriceCurve`, per `docs/content/developers/evm/simplex/pricing.mdx`.
2. An intent submitter dispatches an order buying `EXOTIC` for `USDC`. `FXFiller.resolveLegRates` calls `getVenueUsdPrice` → `UniswapV4FundingPlanner.getExoticTokenPrice` → `computeDirectPoolPriceUsd`, which returns the raw pool mid with no fee subtracted.
3. `checkPriceGuard` passes because the quote is close to `referencePrice` (the mid genuinely reflects the pool's current state — only the fee is missing).
4. The solver fills the order at the fee-blind rate, then later calls `planWithdrawalForToken` to pull `EXOTIC` liquidity from the same V4 position, paying the pool's real swap fee to restock — a cost never recovered from the counterparty.
5. Repeating step 2 indefinitely lets any user (or bot) capture the fee-tier's worth of value from the solver on every fill, with no code path currently subtracting it.

	private checkPriceGuard(orderId: string | undefined, chain: string, venueToken1PerUsd: Decimal): boolean {
		const guard = this.priceGuard?.get(chain)
