### Title
Missing Slippage/Refund Protection in `EvmHost.dispatch()` and `fundRequest()` Native-Token Fee Swaps Causes Permanent Loss of User Overpayment - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` accept native token (`msg.value`) and swap it for the exact fee-token amount required via `swapETHForExactTokens`, but never capture the actual amount spent or refund the leftover ETH to the caller. This is the direct analog of the reported bug class: users interacting with fee-paying dispatch functions have no slippage/overpayment protection, and any native token sent above what the swap consumes is stranded in the `EvmHost` contract rather than returned to the payer.

### Finding Description
In `evm/src/core/EvmHost.sol`: [1](#0-0) 

```solidity
function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
    if (msg.value > 0) {
        address[] memory path = new address[](2);

        IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
    }

```

The same pattern is repeated in `dispatch(DispatchGet memory get)` [2](#0-1)  and `fundRequest()` [3](#0-2) .

`swapETHForExactTokens` is called with the caller's *entire* `msg.value` and an exact output amount (`post.fee` / `get.fee` / `amount`). Because it's an exact-output swap, Uniswap V2's router computes the required input, executes the swap, and refunds any unspent ETH **to the caller of the swap function** — which is `EvmHost` itself, not the original dispatcher (`_msgSender()`). `EvmHost` never reads the returned `amounts[0]` (actual ETH spent) nor forwards the difference back to `_msgSender()`.

This is confirmed by contrast with `IntentGatewayV2.placeOrder()`, which performs the identical exact-output swap but correctly captures the return value and refunds the difference to the user: [4](#0-3) 

```solidity
uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msgValue}(
    order.fees, path, address(this), block.timestamp
);
msgValue -= amounts[0];
...
// Refund any unspent native tokens to the user.
if (msgValue > 0) {
    _sendValue(msg.sender, msgValue);
}
```

`EvmHost.dispatch()` and `fundRequest()` are missing this exact accounting/refund step. Since callers cannot precisely predict the AMM's on-chain price at execution time (the documentation itself explicitly warns against using `quote()` on-chain because "it uses Uniswap's `getAmountsIn`, making it vulnerable to sandwich attacks" — [5](#0-4) ), users must overpay `msg.value` with margin to guarantee the swap succeeds. Every unit of that margin — and any additional margin needed if the pool price is worse than expected due to volatility or a sandwich attack — is silently retained by `EvmHost` instead of being returned.

### Impact Explanation
Any unprivileged actor who dispatches a POST/GET request or funds a pending request using native token payment permanently loses the unspent portion of their `msg.value`. This is systemic: `dispatch()` is the core entry point reachable by every app built on `HyperApp`/`IDispatcher`, and by the documentation's own guidance, safe usage requires sending a native-token buffer above the estimated fee — that buffer is unrecoverable. Over time this represents unbounded, uncompensated fund loss for ordinary users of the messaging layer, and the value accumulates in the `EvmHost` contract with no user-facing mechanism to reclaim it (no `receive()`-triggered refund path was found tied to `_msgSender()`; the excess simply sits as the contract's ETH balance).

### Likelihood Explanation
High likelihood of occurrence in normal operation, not just under attack: any dApp integrator following the documented pattern of `IDispatcher(host()).dispatch{value: msg.value}(...)` (as advised in `docs/content/developers/evm/messaging/post-requests.mdx` / `get-requests.mdx`) will trigger this path whenever `msg.value` exceeds the exact swap cost — which is unavoidable since the exact price is unknown pre-transaction and the docs themselves discourage on-chain quoting. A sandwich attacker can also intentionally push the AMM price against the user before their dispatch executes, forcing them to either revert (DoS) or overpay more heavily, all of which is retained by `EvmHost` rather than refunded — amplifying the loss with no way for the user to recover the difference.

### Recommendation
Mirror the pattern already implemented correctly in `IntentGatewayV2.placeOrder()`: capture the `amounts` array returned by `swapETHForExactTokens` in `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, compute `msg.value - amounts[0]`, and refund the difference to `_msgSender()` via a safe ETH transfer. Additionally, consider allowing callers to supply an `amountInMaximum`/slippage bound so a sandwiched price cannot silently consume an unbounded amount of the user's sent value up to `msg.value`.

### Proof of Concept
1. Deploy `EvmHost` with a configured Uniswap V2 router and fee token, as in the existing test suite (`evm/tests/foundry/ConfiguredWrapperForkTest.t.sol`, `evm/tests/foundry/IntentGatewayV2Test.sol`).
2. Call `EvmHost.dispatch{value: 5 ether}(DispatchPost({..., fee: 1e18 fee-token-units, ...}))` where the actual required ETH input to buy `1e18` fee tokens is only a fraction of `5 ether` (analogous to the IntentGatewayV2 test `testPlaceOrder_FeeSwap_RefundsExcessNativeToken`, [6](#0-5) , which sends 5 ETH for a swap that "should cost much less").
3. Observe that `msg.sender`'s ETH balance decreases by the full `5 ether` (unlike the `IntentGatewayV2` test where `ethSpent < 1 ether` is asserted after refund) because `EvmHost.dispatch()` never returns the excess — the Uniswap router refunds it to `EvmHost`'s own balance, and `EvmHost` has no logic to forward it to the original caller.
4. Repeat for `EvmHost.dispatch(DispatchGet)` and `EvmHost.fundRequest()` to confirm the same missing-refund behavior in both code paths. [7](#0-6) [8](#0-7) [9](#0-8)

    /// @notice placeOrder with fee swap refunds unused ETH after swapETHForExactTokens.
    function testPlaceOrder_FeeSwap_RefundsExcessNativeToken() public {
        uint256 inputAmount = 1000 * 1e6;
        uint256 feeAmount = 1 * 1e18; // 1 DAI worth of fees

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(usdc)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 1000 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 1000,
            nonce: 0,
            fees: feeAmount,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        uint256 userEthBefore = user.balance;

        vm.startPrank(user);
        usdc.approve(address(intentGateway), inputAmount);
        // Send 5 ETH for a fee swap that should cost much less
        intentGateway.placeOrder{value: 5 ether}(order, bytes32(0));
        vm.stopPrank();

        // User should get back most of the 5 ETH — the swap only needed a tiny fraction
        uint256 ethSpent = userEthBefore - user.balance;
        assertTrue(ethSpent < 1 ether, "User should have been refunded most of the 5 ETH");
