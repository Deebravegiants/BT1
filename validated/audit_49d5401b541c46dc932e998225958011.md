### Title
Webhook `shop-domain` header is trusted for tenant identification but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating only the raw request body against the HMAC, then hands the caller-supplied `shop-domain` header to the app's handler as the trusted tenant identifier, without that header ever being part of the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic linkage to the body or the HMAC [2](#0-1) . `Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` (which calls `to_signable_string`, i.e. only the body) and, once that passes, immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app-defined handler: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` [3](#0-2) . The gem's own documentation instructs integrators to treat `data.shop` as the authoritative shop domain for the webhook (e.g., to route/attribute work per-tenant) [4](#0-3) .

This breaks the intended binding: `HMAC-signed bytes == bytes acted on for tenant identity`. In reality, `HMAC-signed bytes (raw_body only) ⊂ bytes acted on (raw_body + shop header)`. An attacker who captures/replays any legitimate webhook payload+HMAC pair addressed to their own shop can resend the identical body and valid HMAC to the app's webhook endpoint while substituting an arbitrary `shop-domain` header value. Because the header is not part of the signed string, `Utils::HmacValidator.validate` still returns `true`, and the handler receives a forged `shop` value with a body that legitimately passed HMAC verification.

### Impact Explanation
Any host application following the gem's documented pattern (using `data.shop` to select which merchant's records to update, e.g. `perform_later(shop_domain: data.shop, ...)` as shown in the gem's own webhook doc) is exposed to cross-tenant action: an attacker who legitimately receives webhooks for their own shop (any Shopify merchant/app installer) can forge the shop attribution of that payload to point at a different merchant, causing the host app to process/attribute data under the wrong tenant. This matches the "cross-tenant access" bucket, since a valid HMAC signature does not guarantee the shop-tenant identity field associated with it.

### Likelihood Explanation
Likelihood is high for any attacker who can install the app on their own shop (or otherwise legitimately receive one valid webhook + HMAC for some shop) — no access to the app's `client_secret` or `api_secret_key` is required. They only need to intercept/replay their own valid webhook delivery while modifying the `shop-domain` header, since nothing in the gem enforces that the header matches signed content.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`, `api_version`) in the signable material, or otherwise independently verify that the `shop-domain` header corresponds to a shop this app is installed on / expects a webhook from, before trusting it in `WebhookMetadata`. At minimum, document that `data.shop` from `ShopifyAPI::Webhooks::Request` is not covered by the HMAC and must not be used as a sole tenant-authorization signal.

### Proof of Concept
1. App installs webhook handler per `docs/usage/webhooks.md`, using `data.shop` to select the tenant record to update.
2. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`) for their own shop, capturing the raw POST body and the valid `X-Shopify-Hmac-Sha256` header Shopify computed for that body.
3. Attacker replays the identical body + HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` verifies the HMAC against `to_signable_string` (raw body only) and returns `true` [5](#0-4) .
5. `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)` [3](#0-2) , and the host app performs tenant-scoped work under the wrong (victim) shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
