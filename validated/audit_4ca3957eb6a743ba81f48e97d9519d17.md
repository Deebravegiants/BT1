### Title
Webhook `shop`/`topic`/`webhook_id` headers are not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then dispatches to the registered handler using `shop`, `topic`, and `webhook_id` values that are read directly from unauthenticated HTTP headers. Because those identity fields are never included in the HMAC signable string, an attacker who can obtain any one genuine `(body, hmac)` pair signed by the target app's secret (e.g. by installing the public app on their own store and receiving a real webhook) can replay that exact body/hmac while substituting the `shop-domain` and `topic` headers with arbitrary values, causing the app to process attacker‑chosen events as if they came from a victim shop.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` field using a constant-time comparison: [1](#0-0) 

For webhooks, `ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are parsed straight out of HTTP headers that are never part of that signable string: [3](#0-2) 

`ShopifyAPI::Webhooks::Registry.process` validates the HMAC (over the body only) and then, on success, dispatches to the topic handler using `request.shop` and `request.topic` unchanged from the unauthenticated headers: [4](#0-3) 

The broken identity binding is:
`shop/topic/webhook_id used to attribute and route the webhook` ≠ `shop/topic/webhook_id covered by the HMAC (which is empty — only the body is signed)`.

Since the app's `client_secret`/`api_secret_key` is the same for every shop that installs the app, any attacker who can install the app on their own (unprivileged) shop receives legitimate webhook deliveries signed with that shared secret. They can capture one valid `(raw_body, X-Shopify-Hmac-Sha256)` pair and replay it to the target app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header pointing at a victim shop and/or a forged `X-Shopify-Topic` header. `Utils::HmacValidator.validate` will still succeed because it only checks the body bytes against the secret, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the victim shop and an attacker-chosen topic.

### Impact Explanation
This crosses a tenant boundary: an attacker-controlled shop can cause the app to process a webhook event as though it originated from an arbitrary victim shop, with an attacker-chosen topic (e.g. `app/uninstalled`, `shop/redact`, `customers/redact`, or any other topic the host app has registered a handler for). Depending on what the host app's handler does with `shop`/`topic` (revoking sessions, deleting merchant data, triggering GDPR redaction, writing to the wrong tenant's records), this can lead to cross-tenant data corruption/deletion or forced logout/deauthorization of a victim shop — all without the victim's consent, mirroring the reported bug class of "no consent validation for the party being acted upon."

### Likelihood Explanation
Requires only that the attacker be able to install the app on their own store (a completely unprivileged, ordinary usage path for a public Shopify app) to obtain one valid signed webhook body, plus the ability to send arbitrary HTTP requests to the app's public webhook endpoint. No access token, `api_secret_key`, or privileged account is required.

### Recommendation
Include the routing/identity fields (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC signable string, or otherwise cryptographically bind them to the body (e.g., verify `shop` against the session/shop that the app expects for that webhook subscription, or require Shopify's newer webhook headers to be part of the signed payload) before dispatching to handlers in `ShopifyAPI::Webhooks::Registry.process`.

### Proof of Concept
1. Attacker installs the target public app on their own store `attacker.myshopify.com` and lets Shopify deliver one real webhook (any topic the app has registered), capturing the raw POST body `B` and its `X-Shopify-Hmac-Sha256` header value `H` (computed by Shopify with the app's `api_secret_key`).
2. Attacker sends a POST to the app's webhook endpoint with:
   - body = `B`
   - `X-Shopify-Hmac-Sha256` = `H`
   - `X-Shopify-Shop-Domain` = `victim-shop.myshopify.com`
   - `X-Shopify-Topic` = any topic registered in the app (can differ from the original topic)
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers, `Utils::HmacValidator.validate` succeeds because it only checks `B`/`H`, and `Registry.process` calls the topic handler with `shop: "victim-shop.myshopify.com"` and the attacker-chosen `topic`, even though neither value was ever authenticated.
