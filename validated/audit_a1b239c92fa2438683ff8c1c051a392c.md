## Title
Webhook `shop-domain` header is trusted for tenant attribution while HMAC only signs the raw body, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw request body, but then hands the handler a `shop` value taken from an unauthenticated HTTP header. Because the header is not part of the signed material, any bytes that produce a valid HMAC (i.e. any body Shopify has legitimately signed for *some* shop, including the attacker's own shop) can be replayed with an arbitrary `shop-domain`/`x-shopify-shop-domain` header, causing the app to process/attribute the webhook data to a shop the attacker does not control.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `VerifiableQuery` and defines: [1](#0-0) 

`hmac` is read from the `hmac-sha256` header, `shop` is read from the `shop-domain` header, and: [2](#0-1) 

`to_signable_string` — the value that is actually HMAC-verified — returns only `@raw_body`. The `shop`, `topic`, `webhook_id`, and `api_version` values, all taken straight from client-controlled HTTP headers, are never included in the signed material.

`HmacValidator.validate` verifies exactly this signable string: [3](#0-2) 

`Registry.process` then does: [4](#0-3) 

The equality the library implicitly relies on is:

`shop that produced a valid signature over this body` == `shop header value passed to the handler as request.shop`

But the signature only proves "this body was produced by Shopify for *a* shop that has this app installed" — it says nothing about which shop's header accompanies it. An attacker who owns/controls a shop that has installed the app receives real, correctly-signed webhooks from Shopify for their own shop (any topic they can trigger, e.g. `orders/create`). They can capture the `raw_body` + `hmac-sha256` header of one such webhook and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop. `HmacValidator.validate` still succeeds (it never looks at the shop header), and `Registry.process` passes the forged shop through to the handler as `WebhookMetadata#shop`, which per the documented usage is what apps rely on to route the payload to per-tenant storage/queues: [5](#0-4) 

The doc explicitly states this call "will verify the request did indeed come from Shopify," which overstates what is actually checked — only the body's origin is verified, not the header-derived shop identity that downstream code is expected to trust.

### Impact Explanation
This breaks the tenant boundary: an unprivileged user who merely installs the app on their own store (no special privilege, no access token/secret required) can inject attacker-controlled webhook payloads that the host application will process as if they originated from an arbitrary victim shop of the attacker's choosing. Depending on how the host app's handler uses `data.shop` (e.g. to select the tenant record, enqueue background jobs keyed by shop, or update local per-shop state), this enables cross-tenant data corruption/confusion — one of the qualifying "Critical: cross-tenant access" impacts, since the tenant used to record/act on the data is not actually the tenant the data came from.

### Likelihood Explanation
Any developer/merchant can install the target app on a shop they control and thereby obtain legitimately-signed webhook bodies for that shop at will (simply performing normal store actions, e.g. creating an order, triggers Shopify to send a correctly HMAC-signed webhook). Replaying that exact body with a modified `shop-domain` header to the app's public webhook endpoint requires only a basic HTTP client — no secrets, tokens, or elevated access are needed. This is a low-effort, reliably reproducible attack path.

### Recommendation
Do not use the client-supplied `shop-domain` (or `topic`/`webhook-id`) header as a trusted identifier by itself. At minimum:
- Cross-check the `shop` header against the shop associated with the specific `webhook_id`/subscription (e.g. by looking up the webhook registration/shop mapping server-side) before dispatching to the handler, or
- Include the header values (shop, topic, webhook id) as part of the HMAC-verified material where feasible, or clearly document that `request.shop` is unauthenticated and must be independently corroborated (e.g. against an existing session record) by the consuming application before being trusted for tenant routing.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger any subscribed webhook (e.g. `orders/create`) to receive a legitimate request from Shopify:
   - `raw_body = '{"id":1,...}'`
   - `headers["x-shopify-hmac-sha256"] = <valid HMAC of raw_body>`
   - `headers["x-shopify-shop-domain"] = "attacker.myshopify.com"`
2. Replay the exact same `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but set:
   - `headers["x-shopify-shop-domain"] = "victim.myshopify.com"`
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` and `ShopifyAPI::Webhooks::Registry.process(request)` (`lib/shopify_api/webhooks/registry.rb:188-200`) pass HMAC validation because `to_signable_string` only checks `raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`), and the handler receives `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: <attacker's data>, ...)` — attributing attacker-controlled data to the victim shop.
