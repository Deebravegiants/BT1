## Finding: Webhook `shop` identity is not covered by the HMAC signature, enabling cross‑tenant webhook spoofing

### Title
Webhook `shop-domain` header is unauthenticated (not covered by HMAC) allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authentic once `Utils::HmacValidator.validate` succeeds, and then hands the handler a `WebhookMetadata` object that includes `shop: request.shop`. However, the HMAC signature only covers the raw request body — never the `shop-domain` header — so the tenant identity delivered to the app's webhook handler is completely unauthenticated, even though the whole point of HMAC validation is to prove "this webhook, including which shop it's for, really came from Shopify."

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `shop` is read straight from an attacker-controllable HTTP header, never mixed into the signable string: [2](#0-1) 

`HmacValidator.validate`/`validate_signature` compares only `verifiable_query.to_signable_string` (i.e., the body) against the HMAC: [3](#0-2) 

`Registry.process` gates on this HMAC check and then forwards `request.shop` — the unauthenticated header value — to the handler as the trusted tenant identifier: [4](#0-3) 

The binding that is broken is: **shop authenticated (implied by a passing HMAC check) ≠ shop actually bound to the signed bytes**. The gem signs off on the webhook's authenticity via `InvalidWebhookError`/no-error, but the `shop` field the app relies on to select per-merchant data/session is outside that cryptographic guarantee.

### Impact Explanation
Any actor who can obtain one legitimate `(raw_body, hmac)` pair from Shopify — trivially available to anyone who installs the app on their own store and receives one real webhook — can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` / `shopify-shop-domain` header for a victim shop. `HmacValidator.validate` still returns `true` (only the body is checked), so `Registry.process` invokes the handler with `WebhookMetadata(shop: "<victim-shop>", body: <attacker's own webhook payload>, topic: ...)`. If the host application relies on this gem's HMAC validation to trust `data.shop` (which is exactly the API contract `WebhookMetadata` provides), an attacker can inject fabricated events attributed to a different merchant — cross-tenant data pollution or unauthorized state changes keyed off the spoofed shop. This matches the "cross-tenant access" Critical impact category, since the shop identity crossing tenant boundaries is exactly what should have been bound by the signature and is not.

### Likelihood Explanation
Likelihood is high: the attacker only needs to control one shop where the target app is installed (a normal merchant/developer capability) to capture a valid `(body, hmac)` pair, then send an unauthenticated HTTP POST to the app's public webhook endpoint with a forged shop header — no access to `api_secret_key`, tokens, or privileged accounts is required.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-covered signable string for webhooks, or otherwise cryptographically bind the `shop-domain` header to the signature (e.g., verify it out-of-band against the shop associated with the specific `webhook_id`/subscription, or require the host app to separately validate `shop` against a known/allowed list before trusting it). At minimum, document clearly that `WebhookMetadata#shop` is not authenticated by `Registry.process` and must not be trusted for tenant selection without additional verification.

### Proof of Concept
1. Install/operate the target app on an attacker-controlled store `attacker.myshopify.com`.
2. Capture a real webhook delivery Shopify sends to the app, e.g.:
   - `raw_body = '{"id":123,"note":"payload"}'`
   - `X-Shopify-Hmac-Sha256: <valid-hmac-for-raw_body>`
   - `X-Shopify-Shop-Domain: attacker.myshopify.com`
3. Replay the request to the app's webhook endpoint unchanged except:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
4. `ShopifyAPI::Webhooks::Registry.process` computes:
   ```ruby
   Utils::HmacValidator.validate(request) # true, only checks raw_body
   handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: request.parsed_body, ...))
   ```
   as seen in [4](#0-3) 
   — the handler now believes attacker-supplied content originated from `victim-shop.myshopify.com`.
