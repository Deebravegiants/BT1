### Title
Unhandled exception in `getIconData`'s image `load` handler causes the extension's icon/metadata promise (and RPC bridge) to hang indefinitely - ([File: libraries/browser-extension-rpc/src/metadata.js])

### Summary
`getIconData` wraps `img.crossOrigin = 'anonymous'` around a canvas draw/read sequence but only guards the `error` event, not exceptions thrown inside the `load` handler. [1](#0-0)  A malicious dapp that fully controls its own document (favicon `<link>` or default `/favicon.ico`) can serve an image that decodes with zero width/height (or otherwise causes `getImageData`/`drawImage` inputs to be degenerate), causing a `DOMException` to be thrown inside the unguarded `load` listener. Because that exception occurs asynchronously inside `addEventListener('load', ...)`, it never reaches the surrounding `Promise` executor as a rejection - `resolve()` is simply never called, and the returned promise hangs forever.

### Finding Description
`getIconData` computes canvas dimensions from `getIconDimensions(img, ICON_MAX_SIZE)`. [2](#0-1)  If the loaded image has `naturalWidth`/`naturalHeight` of `0` (e.g., an SVG favicon with explicit `width="0" height="0"`, or other degenerate image that still fires a `load` event), `ratio` becomes `NaN`, the `else` branch is taken, and `height` (and thus `canvas.height`) becomes `0`. [2](#0-1)  The subsequent call `ctx.getImageData(0, 0, width, height)` with a zero dimension throws an `IndexSizeError` per the Canvas spec, and this call is not wrapped in a `try/catch` — only `img.onerror` is handled. [3](#0-2)  Because this throw happens inside the `load` event listener (an async callback, not the synchronous body of the `new Promise((resolve) => {...})` executor), it does not reject the returned promise — it surfaces only as an uncaught runtime exception, and `resolve` is never invoked, so `getIconData`'s promise never settles.

This promise is awaited in the content script's top-level `metadata` promise chain, `const icon = await getIcon()`, which is itself awaited on every single incoming RPC message: `const senderMetadata = await metadata` inside `transport.on('data', ...)`. [4](#0-3)  A permanently-pending `metadata` promise therefore blocks all RPC message processing for that injected content script/tab, not just icon rendering.

The question's premise about CORS-tainted canvases (`crossOrigin='anonymous'` set before `img.src`) is less reliable as an attack vector, since compliant browsers reject a cross-origin `anonymous` request lacking proper CORS headers with an `error` event (handled by `img.onerror`) rather than a tainted successful `load`. The more concrete and browser-independent vector is a favicon whose decoded intrinsic dimensions are degenerate (e.g., `0`), which reliably reaches the unguarded `getImageData` call inside `load`.

### Impact Explanation
This is a denial-of-service of the dapp-connect/RPC bridge: a malicious dapp page can make the extension's injected `content.js` RPC transport hang forever on `await metadata`, preventing any RPC call/response from being processed for that tab. [5](#0-4)  This matches a "hang/DoS of the dapp-connect approval flow" impact rather than key/secret compromise — no signing, storage, or origin-trust logic is bypassed.

### Likelihood Explanation
Fully attacker-controlled: any dapp can set its own `<link rel="icon">` (or rely on the fallback `${document.location.origin}/favicon.ico`) to a resource that decodes with zero intrinsic dimensions. [6](#0-5)  No special privileges, social engineering, or browser bugs are required beyond serving a crafted favicon, making this reliably reproducible.

### Recommendation
Wrap the canvas draw/read logic (`ctx.drawImage`/`ctx.getImageData`) in a `try/catch` inside the `load` handler, and call `resolve(null)` on any exception (mirroring the existing `img.onerror` fallback), and additionally guard against zero-valued `width`/`height` before invoking `getImageData`.

### Proof of Concept
Unit test plan for `getIconData` (or `getIcon`):
1. Mock `Image` so that setting `.src` synchronously (or via microtask) dispatches a `load` event, with `naturalWidth = 0` and `naturalHeight = 0` (simulating a degenerate/zero-dimension favicon).
2. Mock `document.createElement('canvas')` and its `getContext('2d')` to return a real/spy `getImageData` that throws `DOMException('IndexSizeError')` when called with `width === 0 || height === 0`.
3. Call `getIconData(href)` and assert that the returned promise either resolves (e.g., to `null`) within a bounded time, rather than hanging indefinitely — currently the promise never settles and the test would time out, demonstrating the DoS.

```javascript
const getIconDimensions = (image, size) => {
  const ratio = image.width / image.height

  let width, height, dWidth, dHeight, dx, dy

  if (ratio > 1) {
    width = Math.min(image.width, size)
    dWidth = width
    height = width
    dHeight = Math.round(width / ratio)
    dx = 0
    dy = Math.floor((dWidth - dHeight) / 2)
  } else {
    height = Math.min(image.height, size)
    dHeight = height
    width = height
    dWidth = Math.round(height * ratio)
    dy = 0
    dx = Math.floor((dHeight - dWidth) / 2)
  }

  return { width, height, dWidth, dHeight, dx, dy }
}
```

```javascript
const getIconData = (href) => {
  const img = new Image()

  img.crossOrigin = 'anonymous'
  img.src = href

  return new Promise((resolve) => {
    img.addEventListener('load', () => {
      const canvas = document.createElement('canvas')
      const ctx = canvas.getContext('2d')
      const dimensions = getIconDimensions(img, ICON_MAX_SIZE)

      const width = dimensions.width
      const height = dimensions.height

      canvas.width = width
      canvas.height = height

      ctx.drawImage(img, dimensions.dx, dimensions.dy, dimensions.dWidth, dimensions.dHeight)

      const { data } = ctx.getImageData(0, 0, width, height)

      resolve({ width, height, data: base64(data) })
    })

    // If can't compute, enable connecting dapp without icon. UI will render empty state
    img.onerror = () => resolve(null) // eslint-disable-line unicorn/prefer-add-event-listener
  })
```
