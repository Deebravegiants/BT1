### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` (parsed from the unsigned `shopify-shop-domain`/`x-shopify-shop-domain` header) as the authoritative tenant identity for the webhook. An attacker who can obtain any single valid `(raw_body, hmac)` pair signed with the app's shared secret can replay it to the app's public webhook endpoint with an arbitrary `shop-domain` header, and the HMAC check will still pass because the header is not part of the signed material.

### Finding Description
The binding that should hold is: `hmac == HMAC(secret, signable_bytes)` where `signable_bytes` should bind together everything the receiver later treats as authenticated (the shop identity in particular), i.e. `shop_acted_on == shop_covered_by_hmac`.

In this gem, that equality is broken:
- `to_signable_string` only returns `@raw_body`: [1](#0-0) 
- `shop` is read straight from an HTTP header that is never included in the signable string: [2](#0-1) 
- `Registry.process` verifies the HMAC over the body only, then immediately forwards the (unverified) `request.shop` header value to the app's handler as the authoritative tenant: [3](#0-2) 
- `HmacValidator.validate` recomputes the signature purely from `to_signable_string`, so it is blind to header values: [4](#0-3) 

The gem's own documentation instructs developers to rely on this `process` call as the mechanism that "will verify the request did indeed come from Shopify" and then hands the caller a `WebhookMetadata` with a `shop` field intended to identify which tenant the payload belongs to: [5](#0-4) [6](#0-5) 

Because `shop` is documented as a trusted, verified field of the processed webhook but is never cryptographically bound to the body/HMAC, any party who can produce one legitimately-signed `(body, hmac)` pair for the app (e.g., by installing the app on their own store and triggering a webhook) can resend that exact body/HMAC to the app's webhook URL while substituting the `shop-domain` header for a victim shop's domain. `Registry.process` will accept it as authentic and dispatch it to the handler labeled as belonging to the victim shop.

### Impact Explanation
This breaks the shop/tenant identity binding the whole webhook-processing API is built around, allowing an attacker who controls one tenant (their own installed shop) to inject and impersonate webhook data as if it originated from a different, victim tenant. Any app that keys per-tenant business logic (order processing, inventory, GDPR/customer data, billing side effects, deduplication via `webhook_id`) off `WebhookMetadata#shop` as returned by this gem is exposed to cross-tenant data poisoning/confusion, matching the "cross-tenant access" Critical-impact category, since the identity of the tenant is fully attacker-controlled independent of the cryptographic proof.

### Likelihood Explanation
The webhook endpoint is a public, unauthenticated HTTP endpoint by design (that's the entire reason HMAC verification exists). Obtaining one valid `(body, hmac)` pair only requires installing the app on any shop (including the attacker's own, potentially free/dev shop) and waiting for/triggering a real webhook delivery. Replaying with a modified header requires no secret material at all. This is exploitable by any unprivileged internet user who can install the target app once.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the signable payload used for HMAC verification, or otherwise cryptographically tie the `shopify-shop-domain` header to the verified body (e.g., require the app to independently confirm the shop against its own installed-shop/session store before trusting `WebhookMetadata#shop`, and make this an explicit, mandatory step in `Registry.process` rather than leaving it as an undocumented caller responsibility). At minimum, update `to_signable_string` in `lib/shopify_api/webhooks/request.rb` to incorporate the shop/topic headers so `HmacValidator.validate` fails when they are tampered with.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and registers for a webhook topic (e.g., `orders/create`) via the normal OAuth + `Registry.register` flow.
2. Attacker triggers the event (e.g., creates an order) and captures the raw POST the app's webhook endpoint receives, including the legitimate `shopify-hmac-sha256` header and body.
3. Attacker resends the identical `raw_body` and `hmac` header to the same webhook endpoint, but replaces `shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged header successfully (headers are only checked for presence, not authenticity) — `lib/shopify_api/webhooks/request.rb:45-63`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only and matches — `lib/shopify_api/webhooks/registry.rb:188-190`, `lib/shopify_api/utils/hmac_validator.rb:26-31`.
6. The handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: attacker-controlled data, ...)` — `lib/shopify_api/webhooks/registry.rb:198-199` — despite the payload never having originated from or been signed for that shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
