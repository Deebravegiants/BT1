Based on my investigation, I found a genuine analog to the `setLpToken` bug class in the wallet-accounts module.

### Title
Unrestricted `compatibilityMode` mutation on existing `WalletAccount` permanently breaks address/key derivation and can strand user funds - (File: `features/wallet-accounts/src/module/wallet-accounts.ts`)

### Summary
`LiquidityProviders.setLpToken` allowed an already-used, funds-bearing pointer (`lpToken`) to be repointed at will, breaking `removeLiquidity` for anyone who had already interacted under the old pointer. In Hydra, `WalletAccount.compatibilityMode` plays an analogous role for Bitcoin-like/EVM-like assets: it selects the BIP44 purpose/derivation-path template (`m/44'`, `m/49'`, `m/84'`, or MetaMask-style `m/44'/60'/0'/0/N`) used to derive every receive/change address and signing key for that account. The `updateWalletAccount` helper used by the wallet-accounts `update`/`updateMany` API only guards `source`, `id`, and `index` from being changed, and only conditionally guards `seedId`; `compatibilityMode` is not in the protected list and can be freely overwritten on an already-in-use account, changing which derivation path is used for that account going forward.

### Finding Description
`compatibilityMode` directly determines the derivation path via `getKeyIdentifier`/`getSupportedPurposes`, which is fed into `address-provider` to compute `keyIdentifier.derivationPath` for both receiving and signing: [1](#0-0) [2](#0-1) 

For MetaMask-mode Ethereum accounts, the whole path is pinned to `m/44'/60'/0'/0/${accountIndex}` (ignoring the exodus-mode `m/44'/60'/${accountIndex}'/0/${addressIndex}` scheme entirely): [3](#0-2) 

The `WalletAccount` update path (`updateWalletAccount`) enumerates only `source`, `id`, `index` as immutable, and only conditionally protects `seedId`: [4](#0-3) 

`compatibilityMode` is absent from this list, so nothing in the update path prevents an already-created, already-funded `WalletAccount`'s `compatibilityMode` from being changed after receive addresses under the old mode have been shared with counterparties or funds have been received. This mirrors the report's root cause exactly: a pointer that determines how a user's assets are located/keyed can be silently repointed post-use, with no built-in migration.

### Impact Explanation
If `compatibilityMode` for an existing wallet account is switched (e.g., from default/`exodus` mode to `metamask` mode, or from `bip84` to `bip44` for Bitcoin-family assets), every subsequent `getAddress`/`getDefaultAddress`/`getEncodedPublicKey`/signing call for that wallet account will derive a *different* key/derivation path than the one used to receive prior funds. Balances and UTXOs previously discovered under the old derivation path can silently disappear from the wallet's view (since balance scanning also depends on `compatibilityMode`-derived paths), and new transactions will be signed with a different keypair than the one controlling the old funds — effectively the same "funds become unreachable through the intended UI path" outcome the C4 report describes for `setLpToken`. As in the original finding, funds are not cryptographically destroyed (the master seed still exists and the old path can, in principle, be re-derived by restoring the previous `compatibilityMode`), which is why the original bug was downgraded to Medium; the same reasoning applies here.

### Likelihood Explanation
This requires that some caller (background Devin session, internal API misuse, or a plugin/migration bug) invoke `walletAccounts.update`/`updateMany` with a changed `compatibilityMode` on an account that has already been used. I did not find evidence that untrusted/unprivileged, user-facing code paths currently expose an unguarded UI control to flip `compatibilityMode` for an existing (non-newly-created) account — the mutation risk is at the module/API level, not confirmed to be reachable by a remote attacker or dapp. This should be treated as a defense-in-depth gap rather than a confirmed exploited path; verifying reachability from the SDK/API surface (`features/wallet-accounts` public API, `features/application`) requires further review of full API-layer code that indexing coverage did not surface.

### Recommendation
- Add `compatibilityMode` to the immutable-field assertions in `updateWalletAccount` (alongside `source`, `id`, `index`) once an account has been created/used, or require an explicit, audited migration flow analogous to what the C4 report recommends for `lpToken`.
- If `compatibilityMode` changes must be supported (e.g. one-time inference for legacy accounts, as seen in the `multi-seed-wallet-accounts` migration), gate them so they can only be set from `undefined` to a value once, never overwritten afterward.
- Emit a warning/analytics event and require explicit user confirmation (data-loss warning) before allowing any `compatibilityMode` change on an account with existing balance/history.

### Proof of Concept
1. Create a `WalletAccount` with `source: 'seed', index: 0, seedId: 'A'` and no `compatibilityMode` (defaults to standard Exodus BIP84/BIP44 derivation).
2. Receive Bitcoin/Ethereum funds to the address derived via `addressProvider.getDefaultAddress`, which uses `keyIdentifier.derivationPath` computed from the account's `compatibilityMode` [1](#0-0) .
3. Call `walletAccounts.update(...)` (or `updateMany`) on that same account, changing `compatibilityMode` to `'metamask'`. `updateWalletAccount` permits this because `compatibilityMode` is not in its protected-fields list [5](#0-4) .
4. Subsequent calls to `getDefaultAddress`/`getEncodedPublicKey`/signing for this wallet account now derive `m/44'/60'/0'/0/0` instead of the original path [6](#0-5) , causing the wallet UI to no longer locate/sign for the previously funded address.

**Note on coverage:** I could not fully trace whether `compatibilityMode` is exposed for mutation through the public wallet-accounts API/redux slice reachable from untrusted UI/dapp surfaces (e.g., `features/wallet-accounts/src/module/utils.ts`, `features/application/src/api/index.ts`) due to index size limits; a Devin session with full repo access would be needed to confirm the exact reachable entry point(s) for this mutation and any additional guardrails present at the API layer.

const updateWalletAccount = (
  walletAccounts: Record<string, WalletAccount> = Object.create(null),
  walletAccount: string,
  newData: Record<string, unknown>
) => {
  const before = walletAccounts[walletAccount]

  if (!before) throw new Error(`${walletAccount} is not a known wallet account`)

  if (walletAccount === DEFAULT_WALLET_ACCOUNT.toString() && newData.enabled === false) {
    throw new Error("Can't disable default walletAccount")
  }

  const after = new WalletAccount({
    ...before,
    ...newData,
  })

  for (const key of ['source', 'id', 'index']) {
    assert(
      (before as unknown as Record<string, unknown>)[key] ===
        (after as unknown as Record<string, unknown>)[key],
      `cannot change account ${key}`
    )
  }

  assert(
    !before.seedId || before.seedId === after.seedId,
    'seedId can only be set if previously undefined'
  )

  return after
}
