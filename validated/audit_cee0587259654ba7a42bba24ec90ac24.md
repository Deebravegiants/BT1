### Title
Unbounded pool-creator-supplied mint decimals cause a `checked_pow` overflow panic in `Calculator::normalize_decimal_v2`, permanently freezing pool funds - (File: `program/src/math.rs`, `program/src/processor.rs`)

### Summary
`Processor::process_initialize2` only sanity-checks `coin_mint.decimals` indirectly (via the LP "minimum liquidity" subtraction), but never bounds-checks `pc_mint.decimals` (or, in edge cases, `coin_mint.decimals` beyond that one subtraction). Both values are stored verbatim into `AmmInfo.pc_decimals` / `AmmInfo.coin_decimals` and later fed as the exponent to `10^decimals` inside `Calculator::normalize_decimal_v2`/`normalize_decimal`/`restore_decimal`, which are called on every `Deposit`, `Withdraw`, `WithdrawPnl`, and swap instruction. Because SPL Token mints allow an arbitrary `u8` decimals value (0–255) with no protocol-level cap, a pool creator can initialize a pool with a mint whose `decimals` is large enough that `U128::from(10).checked_pow(decimals)` overflows the 128-bit integer type, causing the trailing `.unwrap()` to panic on every subsequent instruction touching that pool.

### Finding Description
`Calculator::normalize_decimal_v2` computes: [1](#0-0) 
which calls `U128::from(10).checked_pow(U128::from(native_decimal))`. `U128` here is a fixed 128-bit integer (`construct_uint! { pub struct U128(2); }`): [2](#0-1) 
`10^n` overflows a 128-bit unsigned integer once `n` is roughly ≥ 39, well within the legal `u8` range (0–255) that the SPL Token program accepts for a mint's `decimals` field.

`native_decimal` is populated directly from the mint account's `decimals` field at pool creation time: [3](#0-2) 
`amm.initialize(...)` stores `coin_mint.decimals` and `pc_mint.decimals` unchanged into `AmmInfo`: [4](#0-3) 

The only place `coin_mint.decimals` is indirectly bounded is the LP "minimum liquidity" subtraction, which uses a plain `u64` pow (overflowing around decimals ≥ 20) and therefore would abort `Initialize2` before completion if `coin_mint.decimals` is too large: [5](#0-4) [6](#0-5) 
Critically, this check only exercises `coin_mint.decimals` (used for `lp_decimals`); `pc_mint.decimals` is never run through any pow/overflow check during `Initialize2`, so it can be set arbitrarily high (up to 255) without preventing pool creation.

Once the pool exists with an oversized `amm.pc_decimals`, every reachable instruction that calls `normalize_decimal_v2`/`restore_decimal` on `total_pc_without_take_pnl` will panic and abort:
- `process_deposit` → `calc_total_without_take_pnl_no_orderbook` + `normalize_decimal_v2` at deposit accounting.
- `process_withdraw`: [7](#0-6) 
- `process_withdrawpnl`: [8](#0-7) 
- `process_swap_base_in` / `process_swap_base_out` (and V2 variants) which perform the same normalization before computing swap amounts.

Because every state-mutating instruction for that pool (including `Withdraw`) unconditionally computes this normalization before doing anything else, a pool created with a poisoned `pc_mint` decimals value becomes permanently unusable: no LP can ever withdraw their deposited coin/pc tokens from the vaults again, since the withdraw path itself panics before any token transfer executes.

### Impact Explanation
Any tokens already deposited into the pool's `coin_vault`/`pc_vault` (by the creator during `Initialize2`, and potentially by other LPs who deposit before anyone notices the pool is defective) become permanently locked — `Withdraw` and `WithdrawPnl` both panic before they can transfer funds out, and there is no alternate/emergency-withdraw path that bypasses `normalize_decimal_v2`. This matches the "permanent freezing of user or LP funds" impact criterion. This is High severity because it requires no privileged signer and can be triggered by any unprivileged pool creator using a completely standard, unmodified SPL Token mint (arbitrary `decimals` is a fully supported, in-spec token feature).

### Likelihood Explanation
High likelihood: creating an SPL Token mint with `decimals = 200` (or any value ≥ ~39) is a single standard `initialize_mint` call with default SPL Token program — no privileged keys, no modified builds, no off-chain/validator assumptions. The attacker then simply calls `Initialize2` with this mint as `pc_mint`, which the current code accepts without any decimals bound check on the `pc_mint` side.

### Recommendation
- Explicitly validate `coin_mint.decimals` and `pc_mint.decimals` in `process_initialize2` against a safe maximum (e.g., ensure `10u128.checked_pow(decimals)` and `10u128.checked_pow(decimals) * sys_decimal_value` do not overflow, and reject with `AmmError::InvalidInput`/similar if they do).
- Replace all `.unwrap()` calls in `Calculator::normalize_decimal`, `normalize_decimal_v2`, and `restore_decimal` with proper `checked_*` error propagation (`ok_or(AmmError::...)?`) instead of panicking, so malformed pools fail gracefully rather than becoming permanently stuck, and consider adding a genuinely no-normalization emergency withdrawal path that does not depend on `decimals`-based math.

### Proof of Concept
1. Attacker creates a new SPL Token mint `M` via the standard Token program with `decimals = 200` (no restriction on this value in the token program).
2. Attacker calls `Initialize2` on the Raydium AMM program, supplying `M` as `amm_pc_mint` (and any normal mint as `amm_coin_mint`), with nonzero `init_pc_amount`/`init_coin_amount`. This succeeds because only `coin_mint.decimals` feeds the overflow-prone LP subtraction at [6](#0-5) ; `pc_mint.decimals` is stored unchecked via `amm.initialize(...)`.
3. Any subsequent call to `Deposit`, `Withdraw`, `WithdrawPnl`, or any swap instruction against this pool computes `Calculator::normalize_decimal_v2(total_pc_without_take_pnl, amm.pc_decimals /* =200 */, amm.sys_decimal_value)`, which panics inside `.checked_pow(...).unwrap()` at [1](#0-0) , aborting the transaction.
4. Because `process_withdraw` itself panics before performing any token transfer (see [7](#0-6) ), the coin/pc tokens already sitting in `amm_coin_vault`/`amm_pc_vault` from step 2 can never be withdrawn — permanent freezing of those funds.
