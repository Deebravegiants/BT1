### Title
Webhook shop identity spoofing via unauthenticated `shop-domain` header - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook only by HMAC-verifying the raw request body, but the `shop` identity that is handed to the app's webhook handler is read from an HTTP header that is never covered by that HMAC. This breaks the intended binding `HMAC-covered bytes == identity used by handler`, allowing a replayed/relabeled webhook body to be attributed to an arbitrary shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC purely over `to_signable_string` (the raw body) and compares it to the `hmac-sha256` header: [2](#0-1) 

But the `shop` value that is passed downstream to the app's handler comes from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is completely outside the signed material: [3](#0-2) 

`Registry.process` validates only the HMAC of the body and then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`, `request.api_version`) to build the metadata delivered to the registered handler: [4](#0-3) 

The identity binding that should hold is:
`HMAC-verified bytes == bytes that determine the tenant (shop) the handler acts on`

Here it does not: the HMAC verifies `body`, but the tenant identity fed to `WebhookHandler#handle` is taken from `headers["shopify-shop-domain"]`, which is attacker-controllable and unauthenticated by this gem.

Any party that can obtain one genuine, validly-signed webhook body+HMAC pair for topic `T` (e.g., by installing the merchant's app on their own store and receiving a real webhook for it) can replay that exact `raw_body`/`hmac-sha256` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with an arbitrary target shop domain. `HmacValidator.validate` will still return `true` (it only checks the body), and `Registry.process` will invoke the topic handler with `WebhookMetadata.new(... shop: request.shop ...)` populated with the attacker-chosen shop. Any host application that uses `data.shop` from the handler to look up/act on that shop's session or resources (a documented, expected usage pattern per `WebhookMetadata`) will act on the wrong tenant using attacker-supplied data — i.e., cross-tenant data injection/impersonation through this gem's own webhook-verification API.

### Impact Explanation
This meets the "Critical – cross-tenant access" bar: an attacker who legitimately possesses one valid signed webhook payload (trivially obtainable by installing the app themselves, no `api_secret_key` or access-token theft required) can cause the app to process that payload as though it belongs to a different, arbitrary merchant shop. Since `ShopifyAPI::Webhooks::Registry.process` is the gem's documented and exclusive entry point for verifying and dispatching webhooks, and it hands the caller an unauthenticated `shop` value alongside a "verified" status, downstream apps that trust this contract (a reasonable expectation, since HMAC validation is the gem's whole job) will merge/attribute cross-tenant data.

### Likelihood Explanation
High feasibility: any user who can install the target app (even on their own free/dev store) can capture one legitimate `(raw_body, hmac-sha256)` pair and shop-domain header, then craft a new HTTP POST to the app's public webhook URL with the original body/HMAC and a forged `shopify-shop-domain` header. No secret material or session/token theft is required — only observation and replay of one legitimate webhook the attacker is already entitled to receive.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the material verified against the HMAC, or at minimum have `Utils::HmacValidator`/`Registry.process` cross-check the header-provided `shop` against a value that Shopify itself signs (Shopify webhook HMACs are computed over the raw body only by spec, so the fix must happen at the app-integration layer): `Registry.process` should require or strongly document that host apps must independently authenticate `WebhookMetadata#shop` (e.g., only trust it in combination with knowledge of which shop's endpoint/secret pairing produced it) rather than exposing it as a verified field. At minimum, update the documentation/contract of `WebhookMetadata` to make explicit that `shop` is NOT covered by the HMAC and must not be trusted as an authenticated tenant identifier without additional binding (e.g., per-shop webhook endpoints, or validating shop against known installed shops before using it as a lookup key).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw body `B` and the resulting `x-shopify-hmac-sha256: H` header sent by Shopify (computed as `HMAC-SHA256(api_secret_key, B)`).
2. Attacker sends a POST to the app's public webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256: H` (unchanged)
   - Header `x-shopify-topic: orders/create` (unchanged)
   - Header `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
3. In the app, `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(api_secret_key, B)` and compares it to `H` — this succeeds because the body wasn't modified: [5](#0-4) 
4. `Registry.process` then calls the registered handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: <attacker's order data>, ...)`: [6](#0-5) 
5. The host application, trusting the gem's HMAC-verified webhook flow, processes/attributes attacker-controlled order data as belonging to `victim-shop.myshopify.com`.
