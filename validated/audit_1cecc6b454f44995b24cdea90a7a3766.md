### Title
Min-circuit Emporium path lets any user run arbitrary self-calls from Emporium's identity, draining tokens Emporium holds while balance accounting is skipped - (File: contracts/CircomDataBuilder.sol / contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
When `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `formInputForCircom` routes to `formInputEmporiumMin`, whose only public constraints are `emporiumMessage`, `timeStamp`, `calldataHash` — none of which bind to ownership of funds, a nullifier, or a real UTXO. `EmporiumUpgradeable.runAction` then decodes an attacker-supplied `EmporiumStack` and, when `stack.signerAddress == address(0)`, skips ECDSA signature verification entirely (`verifyWallet` returns early) while still executing every `op` as a raw external call from the Emporium contract's own identity. Because `circomData.erc20TokenAddresses` is empty, the pre/post balance accounting loop in `runAction` (and the mirrored one in `Hinkal.transact`) never executes, so any value Emporium's contract balance holds can be moved out via attacker-crafted calldata (e.g. `ERC20.transfer(attacker, balance)`) with zero accounting and zero revert conditions.

### Finding Description
The broken equality is: **assets Emporium can move in a tx == assets accounted for in `balancesBefore`/`balancesAfter`**.

- `formInputForCircom` selects the trivial "min" input set whenever `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0`: [1](#0-0) 
- `dimensionsCheck` only requires `erc20TokenAddresses.length == amountChanges.length == onChainCreation.length == slippageValues.length == inputNullifiers.length == dimensions.tokenNumber`; setting `dimensions.tokenNumber = 0` makes every one of these arrays legally empty: [2](#0-1) 
- The Min circuit input contains no `rootHashHinkal` binding to the attacker's own UTXO, no nullifiers, and no amountChanges — the message is only pinned as `message <== Poseidon(1)([messageSeed])` in the general circuit template, and the attacker fully controls `messageSeed`, so this is trivially provable for any self-chosen `emporiumMessage`. [3](#0-2) 
- `rootHashExists` accepts `_root == 0` whenever the tree is still at its minimum index, and any historical root at any valid index otherwise — it does not bind the root to anything the attacker deposited. [4](#0-3) 
- `_externalTransact` builds `deltaAmountChanges` with length `erc20TokenAddresses.length` (zero in this path) and forwards straight to `EmporiumUpgradeable.runAction`: [5](#0-4) 
- Inside `runAction`, `stack` is decoded from attacker-controlled `externalActionData.externalActionMetadata`, `balancesBefore`/`balancesAfter` are computed only over the (empty) `erc20TokenAddresses` array, `verifyWallet` skips signature checks entirely when `stack.signerAddress == address(0)`, and every op then executes as `op.endpoint.call{value: op.value}(op.callData)` with `msg.sender == Emporium contract`: [6](#0-5) [7](#0-6) 
- The balance-change accounting loop that would normally catch a negative/unauthorized shift (`BalanceChangeShouldBePositive`) iterates `circomData.erc20TokenAddresses`, which is empty, so it never runs: [8](#0-7) 
- Back in `Hinkal.transact`, the top-level slippage/balance-diff loop is likewise driven by `circomData.erc20TokenAddresses` and is a no-op for an empty array: [9](#0-8) 

Exploit flow: attacker calls `Hinkal.transact` with `dimensions.tokenNumber = 0`, `circomData.erc20TokenAddresses = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionData.externalAddress = <real Emporium address>`, and `externalActionData.externalActionMetadata` encoding an `EmporiumStack{signerAddress: address(0), ops: [{endpoint: token, invokeWallet: false, value: 0, callData: transfer(attacker, tokenBalance)}, ...]}`, plus a locally-generated, trivially-satisfiable Min-circuit proof. `verifyWallet` performs no signature check (since `signerAddress == 0`), the loop executes the attacker's ops directly from Emporium's address, and no balance accounting anywhere in the call stack observes or reverts on the resulting outflow.

### Impact Explanation
Any ERC20/ETH balance that the Emporium contract is holding at call time — whether from a prior legitimate deposit step ("parked" balance awaiting a subsequent op in a multi-tx flow), dust left over from partial swaps, or funds deposited by another user's in-flight transaction in the same block — can be stolen in full by any unprivileged caller, with zero accounting trail and no revert path. This is direct theft of in-flight/parked user or protocol funds via calls the fund owner never authorized, matching Critical severity ("direct theft of shielded or in-flight user funds" / "executing calls or moving assets a wallet owner or prover never authorised"). The attack is repeatable every time Emporium holds a nonzero balance, and across a batch of same-block transactions the attacker can order their min-path drain immediately after any transaction that increases Emporium's balance and before the balance is swept back out.

### Likelihood Explanation
Preconditions: (1) Emporium contract must hold a nonzero token/ETH balance at the moment of attack — plausible any time a user's transaction moves funds into Emporium as an intermediate step (deposit-then-op flows, or a prior partially-completed multi-op tx), or if any rounding/leftover balance exists; (2) attacker needs no special role — they only need to generate a proof for the trivial Min circuit (self-chosen `messageSeed`) and craft `EmporiumStack` calldata, both fully within an unprivileged EOA's capability; (3) `usedMessages[emporiumMessage]` just needs a fresh nonce, trivial to satisfy. Attacker cost is one transaction's gas. This is directly reachable through the public `Hinkal.transact` entrypoint with no admin/relay/owner privileges required.

### Recommendation
- Reject the Min-path entirely when `externalActionData.externalActionMetadata` decodes to an `EmporiumStack` with non-empty `ops`, or require `erc20TokenAddresses.length > 0` (and full accounting) whenever `stack.ops.length > 0`.
- Never allow `EmporiumUpgradeable.runAction` to skip `verifyWallet`'s signature check based solely on `signerAddress == address(0)` unless there is an independent guarantee that `ops` cannot move real value out of Emporium (e.g., disallow raw `.call` with arbitrary `callData`/`value` in that branch, or require the balances-accounting loop to cover *all* tokens actually touched, not just the caller-declared `erc20TokenAddresses`).
- Track Emporium's actual token inventory (e.g., via an internal ledger of per-token amounts deposited/owed) rather than trusting the caller-supplied `erc20TokenAddresses` array to determine which balances to check.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`, register `HINKAL_EMPORIUM_ACTION_ID -> Emporium address`.
2. Fund Emporium directly with an ERC20 token (simulating a parked balance from a prior legitimate deposit step), e.g. `token.mint(emporium, 1000e18)`.
3. As an unprivileged attacker EOA (no deposits, no role), build `CircomData` with `dimensions.tokenNumber = 0`, `erc20TokenAddresses = []`, `amountChanges = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionData.externalAddress = emporium`, `externalActionData.externalActionMetadata = abi.encode(EmporiumStack({signerAddress: address(0), ops: [EmporiumOperation({endpoint: address(token), invokeWallet: false, value: 0, callData: abi.encodeCall(token.transfer, (attacker, 1000e18))})], maxFee: 0, deadline: block.timestamp})`, and a fresh `emporiumMessage`.
4. Generate a locally computed Groth16 proof for the Min circuit statement (`message == Poseidon(messageSeed)`) with an attacker-chosen `messageSeed`; set `rootHashHinkal = 0`, `rootHashHinkalIndex` at tree's minimum index (valid per `rootHashExists`).
5. Call `Hinkal.transact(a, b, c, dimensions, circomData)` from the attacker EOA.
6. Assert: `token.balanceOf(emporium) == 0` and `token.balanceOf(attacker) == 1000e18` after the call, while `oldBalances == newBalances == []` at the `Hinkal.transact` level (both empty, so the equality "assets moved == assets accounted" is violated: 1000e18 moved, 0 accounted).
