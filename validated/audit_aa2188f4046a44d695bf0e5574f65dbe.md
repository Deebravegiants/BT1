Confirmed: `purchase()` in `BandwidthManager.sol` is fully permissionless — anyone can specify an arbitrary `app` identifier to credit, and `pallet-bandwidth` on Hyperbridge appends the resulting `Subscription` to that app's FIFO list, capped at `MAX_SUBSCRIPTIONS = 1024`, evicting the oldest entry (even if it still has substantial `remaining_bytes`) once the cap is hit.

### Title
Permissionless bandwidth purchases let a griefer evict a victim app's paid, unexpired subscription from the 1024-cap FIFO queue - (File: `modules/pallets/bandwidth/src/lib.rs`)

### Summary
`BandwidthManager::purchase()` [1](#0-0)  lets any caller credit bandwidth to an arbitrary `app` byte-string, dispatching a `BandwidthPurchaseMsg` that `pallet-bandwidth::on_accept` turns into a new `Subscription` pushed onto that `(app_chain, app)` FIFO list via `push_subscription` [2](#0-1) . The list is capped at `MAX_SUBSCRIPTIONS = 1024` [3](#0-2) ; pushing past the cap evicts index 0 unconditionally, regardless of how many bytes remain on it [4](#0-3) .

### Finding Description
This mirrors the reported bug class: a shared, capacity-limited, FIFO queue tied to a victim's identifier can be filled by an unprivileged third party to evict the victim's legitimate, still-valid entry — exactly as the attacker in the external report fills the `UnstakeCooldown` queue slots keyed to the victim's `receiver` address to push out the real withdrawal.

Here, the queue key is `(app_chain, app)` where `app` is attacker-controlled input to `purchase()` — there is no ownership check tying `app` to `msg.sender` [5](#0-4) . Any account can call `purchase(app=<victim_app>, tier=TierOne, months=1, chain=...)` repeatedly (1024+ times) using the cheapest tier. Each purchase appends a new `Subscription` to the victim app's list. Once the list hits 1024 entries, every subsequent purchase evicts the oldest entry — which, after enough spam purchases, becomes the victim's own real, high-value, unexpired subscription (large `remaining_bytes`, long `expires_at`) purchased before the attack began [6](#0-5) .

The eviction is unconditional on remaining balance or expiry — `push_subscription` always evicts index 0 (`list.remove(0)`) when the list is full, with no preference for evicting empty/expired entries first [4](#0-3) . Because same-tier repurchases "don't stack, they queue" (per the module doc), and because gate-consumed entries only pop once fully drained to zero, an attacker's flood of minimal purchases will, over 1024 sequential inbound `BandwidthPurchaseMsg` deliveries, permanently flush out the victim's real allowance before it's ever consumed by the gate.

### Impact Explanation
This is a permanent freezing/loss-of-funds bug: the victim paid real fee-token value for a `Subscription` with real `remaining_bytes`, and a third party can force its eviction (and permanent loss, as `SubscriptionEvicted` documents: "`lost_bytes` is what the user paid for and won't get to use") without spending anywhere near the same value — the attacker only needs 1024 cheap `TierOne` purchases (100 KB each at $50/purchase per the docs) to guarantee eviction of any single victim entry regardless of its size, since the eviction always targets the oldest slot irrespective of value. A well-resourced app can be forced to lose an arbitrarily large already-paid bandwidth allocation for a comparatively bounded attacker cost, and losing that allowance blocks the app's inbound ISMP message delivery via the `BandwidthGate` (`try_consume` failing with `NoAllowance`/`Insufficient`) — a route unable to deliver messages until the app re-purchases.

### Likelihood Explanation
Likelihood is high: `purchase()` requires no relationship to the target app, no allowlist check, and no minimum stake beyond the tier price; the flood is a sequence of ordinary permissionless transactions from any account, and the `app_chain`/`app` fields in `BandwidthPurchaseMsg` are entirely attacker-supplied [7](#0-6) . Any competitor or griefer targeting a known dApp's bandwidth-metered address can execute this at any time.

### Recommendation
Scope `purchase()`/credit authority so bandwidth can only be topped up by (or explicitly delegated by) the app being credited, or — if third-party sponsorship must remain permissionless — change the eviction policy in `push_subscription` to prefer evicting already-expired or fully-drained subscriptions before ever evicting a live one with remaining bytes, and/or raise/parametrize `MAX_SUBSCRIPTIONS` per app with a cost-weighted admission control so cheap spam purchases cannot cheaply displace an already-paid, high-value entry.

### Proof of Concept
1. Victim `app` legitimately purchases a `TierFour` (8 MB, e.g., 1-year duration) subscription via `BandwidthManager.purchase()`, crediting a large `Subscription{remaining_bytes: 8_388_608, expires_at: far_future}` at index 0 of `Allowance[(app_chain, app)]`.
2. Attacker calls `purchase(app=victim_app, tier=TierOne, months=1, chain=app_chain)` 1024 times from any account (cheapest tier, no ownership check needed) [1](#0-0) .
3. Each inbound purchase message triggers `push_subscription`, appending to the FIFO list; once length hits 1024, subsequent pushes call `list.remove(0)`, which starts consuming the queue from the victim's legitimate entry once every earlier spam entry has been shoved past it in insertion order — in practice, the victim's real entry (inserted before the spam) is evicted on the attacker's 1025th purchase since it now sits at index 0 [4](#0-3) .
4. `SubscriptionEvicted{lost_bytes: 8_388_608, ...}` is emitted — the victim's paid-for, unused allowance is gone [6](#0-5) .
5. Any inbound message from the victim's real traffic now hits `BandwidthGate::try_consume`, which fails with `NoAllowance`/`Insufficient` since the drained/spam entries carry negligible bytes, blocking legitimate message delivery until the victim repurchases.
