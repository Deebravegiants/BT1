### Title
Webhook shop-domain identity spoofing via replay — HMAC covers only the raw body, not the `X-Shopify-Shop-Domain` header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop` value used to identify the tenant for a webhook is read from an unauthenticated HTTP header. The `Registry.process` method validates only the body/HMAC pair and then hands the header-derived, unverified `shop` value straight to the app's `WebhookHandler`. This breaks the identity binding "shop authenticated == shop acted upon."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, by contrast, is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic binding to the body or to the HMAC: [2](#0-1) 

`Registry.process` validates the request using `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `to_signable_string` (i.e., the body) via `OpenSSL.secure_compare`: [3](#0-2) 

Once that body-only signature checks out, `process` immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`) and forwards them, unverified, to the app-provided handler: [4](#0-3) 

`WebhookMetadata.shop` is documented as "The shop domain of the webhook" and is the value apps are expected to use to attribute/act on the incoming payload (e.g., to key their per-shop job or data store): [5](#0-4) [6](#0-5) 

**Identity binding broken (equality that should hold but doesn't):**
`shop_that_produced_valid_HMAC == shop_the_handler_believes_it_is_processing_for`

The HMAC only proves "this body byte-string was signed by our `client_secret`" — it proves nothing about which shop the body belongs to, since `shop` is never part of `to_signable_string`. An unprivileged party who can obtain one legitimately-HMAC-signed `(raw_body, hmac)` pair for their own installed shop (e.g., by installing the target app on a shop they control and capturing/replaying a webhook their own shop received, since nothing stops an app owner from proxying/forwarding/logging inbound requests to their own endpoint) can resend that same body+HMAC to the app's webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header value. `HmacValidator.validate` still passes (only the body/HMAC pair matters), and `Registry.process` will hand the handler a `WebhookMetadata` claiming to be for the spoofed shop while carrying the attacker-controlled body content.

### Impact Explanation
This crosses a tenant boundary: an app that uses `data.shop` to key per-shop state (job queue partitioning, database writes, cache invalidation, mandatory GDPR webhook handling such as `shop/redact`/`customers/redact`, etc.) can be made to apply attacker-supplied, arbitrary webhook body content under a victim shop's identity. This is a cross-tenant data integrity/confusion vector directly caused by an identity field ("shop") that is acted upon but is not covered by the HMAC — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires the attacker to hold at least one valid `(raw_body, hmac)` pair signed with the app's `client_secret` — but critically, the attacker does **not** need to know the `client_secret` itself. Any user who installs the target public app on a shop they control will legitimately receive properly signed webhooks addressed to that shop; they can capture the exact bytes of one such request (raw body + `hmac-sha256` header) via their own reverse proxy/inspection of traffic to their own endpoint, since they own that endpoint. They can then replay the identical body+HMAC to the target app's webhook endpoint while altering only the `shop-domain` header. Because `Request`/`HmacValidator` never bind `shop` to the signed content, the forged request passes validation. This requires no leaked secrets, no privileged account, and no TLS interception of Shopify's traffic — only ordinary unprivileged use of the app (installing it) plus control of one's own inbound endpoint, making it a realistic and moderately likely attack path.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`/`api_version`) to the cryptographic verification, not just the raw body:
- Include the `shop-domain` header value in `to_signable_string` (or perform a secondary check), so a mismatch between the header used to compute an expected signature and the header actually received causes verification failure.
- Alternatively/additionally, cross-check `request.shop` against the shop associated with the app's own webhook registration/session store before invoking the handler, rejecting any webhook whose header shop was never subscribed to the topic in question.
- At minimum, document this gap explicitly and instruct implementers of `WebhookHandler` to independently verify `data.shop` is a shop that has actually installed the app / has an active session before trusting it for tenant-scoped actions.

### Proof of Concept
```ruby
# Step 1 (attacker installs the target app on their own shop "attacker.myshopify.com")
# and captures one legitimately Shopify-signed webhook their own endpoint receives:
raw_body = '{"id": 1, "note": "hello"}'
hmac_b64 = "captured-base64-hmac-from-real-shopify-webhook-for-attacker-shop"

# Step 2: attacker replays the exact same body+hmac to the app's webhook endpoint,
# but swaps only the shop-domain header to the victim shop:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => hmac_b64,       # unchanged, still valid for raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",  # forged
  "x-shopify-webhook-id" => "forged-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) succeeds because it only checks raw_body against hmac.
# The handler receives WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker JSON>, ...)
# and will act on it as if Shopify itself reported this event for victim-shop.
```
