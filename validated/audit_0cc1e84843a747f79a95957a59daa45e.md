### Title
BidCache in intents-coprocessor RPC accumulates unbounded, size-bounded-only-by-TTL memory from unprivileged `place_bid` mempool spam - ([File: modules/pallets/intents-coprocessor/rpc/src/lib.rs])

### Summary
`BidCache::insert` (`modules/pallets/intents-coprocessor/rpc/src/lib.rs:111-129`) grows an in-memory `HashMap<H256, OrderBids>` with unbounded per-order `Vec<BidEntry>` for every distinct `(commitment, filler)` pair observed in the transaction pool, with no per-order cap and no global cap on tracked commitments. Eviction only happens on a periodic timer (`remove_expired`, driven by `cleanup_interval` in `run_bid_watcher`), not on insertion size. An unprivileged actor can submit many cheap `place_bid` extrinsics with distinct commitments and/or distinct signer accounts (fillers) faster than the TTL sweep clears them, driving unbounded memory growth in the node process serving the intents RPC, mirroring the MongoDB CVE pattern of "internal processes persisting longer than anticipated" causing accumulated memory pressure.

### Finding Description
`run_bid_watcher` (`modules/pallets/intents-coprocessor/rpc/src/lib.rs:331-380`) subscribes to `pool.import_notification_stream()` and, for every incoming transaction that decodes as a `pallet_intents_coprocessor::Call::place_bid`, calls `bid_cache.insert(commitment, filler, user_op)` unconditionally — this path requires no signature verification beyond what `extract_bid` performs to pull out `(commitment, filler, user_op)`, and it fires as soon as a transaction is *ready* in the pool, before block inclusion. This means:

1. Any account can submit a `place_bid(commitment, user_op)` extrinsic for an arbitrary attacker-chosen `commitment` (an order hash need not even correspond to a real order) and an arbitrary-length `user_op` byte blob.
2. `BidCache::insert` (lines 111-129) does an unconditional `bids.entry(commitment).or_insert_with(...)`, appending a new `BidEntry{filler, user_op}` to `OrderBids.entries: Vec<BidEntry>` whenever the `filler` (signer) is new for that commitment.
3. There is no cap on: (a) the number of distinct commitments tracked, (b) the number of distinct fillers per commitment, or (c) the size of `user_op` cached per entry.
4. Cleanup only happens via `remove_expired` (lines 149-154), invoked strictly on a fixed timer tick (`cleanup_interval`) in `run_bid_watcher`'s `tokio::select!` loop — it is never invoked based on cache size or memory pressure, and does not remove individual stale bids from a `Vec<BidEntry>`, only whole `OrderBids` entries once *all* of them have aged past `ttl`.
5. Because transaction-pool "ready" status can be reached without ever landing on-chain (mempool spam, transactions replaced/dropped, or transactions that simply won't be included due to fee/priority), an attacker can flood the pool with many low-cost `place_bid` transactions across many synthetic commitments/fillers between two `cleanup_interval` ticks, each one adding an entry that persists in memory for up to `ttl` (this pattern directly parallels the CVE's root cause: a background process/cursor state persisting "longer than anticipated" while unbounded work accumulates).

This is reachable purely by an unprivileged bidder/filler submitting transactions to the mempool of a node running the intents RPC service — no admin/governance/collator privilege needed.

### Impact Explanation
Every full/RPC node running `run_bid_watcher` for the intents-coprocessor pallet can have its `BidCache` grown without bound between TTL sweeps by a low-cost mempool-spam attack, consuming node memory and potentially causing OOM-driven crashes or severe RPC service degradation on the intents RPC path used for bid discovery (`intents_getBidsForOrder`, `intents_subscribeBids`). This is a resource-exhaustion / availability issue against the RPC-serving nodes that unprivileged intent solvers and bandwidth purchasers rely on for sub-second bid discovery, potentially disrupting order matching/settlement flow for the intents system. It does not directly forge messages or mint tokens, but it degrades a component in the reachable "intent solver" path named in scope.

### Likelihood Explanation
Likelihood is high: the attack requires only submitting many low-value `place_bid` extrinsics with distinct commitments/fillers to the mempool; these do not need to be included in a block (mempool "ready" status is sufficient to trigger caching), so the attacker's cost is bounded by transaction-pool acceptance fees/spam-prevention (if any) rather than by on-chain execution cost or the 0.01 BRIDGE bid deposit noted elsewhere in the docs (that deposit only applies to *landed* bids, not merely pooled ones). Any node with `run_bid_watcher` running is affected simultaneously.

### Recommendation
- Bound `BidCache` total memory: cap the number of tracked commitments (LRU eviction) and the number of entries per commitment (e.g., reject/replace lowest-priority bid past a max fillers-per-order limit).
- Cap `user_op` size accepted into the cache (mirror any on-chain size limit for `place_bid`'s `user_op`).
- Trigger `remove_expired` (or a partial sweep) opportunistically on insert when the cache exceeds a size threshold, not only on the fixed timer.
- Consider only caching bids for currently known/open order commitments (validate against on-chain/offchain order state) rather than arbitrary attacker-supplied hashes.

### Proof of Concept
1. Run a node exposing the intents RPC with `run_bid_watcher` active and a `cleanup_interval` of, e.g., 30s.
2. From many funded accounts, submit a flood of `place_bid(commitment_i, user_op)` extrinsics using freshly generated random `commitment_i` values (one per submission) and distinct signer accounts, keeping submission rate high enough that more entries are added than the TTL sweep removes.
3. Since `extract_bid` only requires the extrinsic to decode as a signed `place_bid` call (no validation that the commitment corresponds to a real, still-open order), every submission that reaches "ready" in the pool triggers `BidCache::insert`, growing the `HashMap`/`Vec<BidEntry>` structures.
4. Observe the RPC node process's memory grow roughly linearly with the number of distinct `(commitment, filler)` pairs submitted, bounded only by `ttl`, independent of whether any transaction is ever included in a block. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

#[derive(Clone, Debug)]
struct BidEntry {
	filler: Vec<u8>,
	user_op: Vec<u8>,
}

#[derive(Clone, Debug)]
struct OrderBids {
	first_seen: Instant,
	entries: Vec<BidEntry>,
}

/// In-memory bid cache.
pub struct BidCache {
	bids: RwLock<HashMap<H256, OrderBids>>,
	ttl: Duration,
}

impl BidCache {
	pub fn new(ttl: Duration) -> Self {
		Self { bids: RwLock::new(HashMap::new()), ttl }
	}

	pub fn insert(
		&self,
		commitment: H256,
		filler: Vec<u8>,
		user_op: Vec<u8>,
	) -> Result<(), String> {
		let entry = BidEntry { filler: filler.clone(), user_op };

		let mut bids = self.bids.write().map_err(|e| format!("BidCache lock poisoned: {e}"))?;
		let order = bids
			.entry(commitment)
			.or_insert_with(|| OrderBids { first_seen: Instant::now(), entries: Vec::new() });
		if let Some(existing) = order.entries.iter_mut().find(|e| e.filler == filler) {
			*existing = entry;
		} else {
			order.entries.push(entry);
		}
		Ok(())
	}

	pub fn remove_expired(&self) -> Result<(), String> {
		let now = Instant::now();
		let mut bids = self.bids.write().map_err(|e| format!("BidCache lock poisoned: {e}"))?;
		bids.retain(|_commitment, order| now.duration_since(order.first_seen) < self.ttl);

pub fn extract_bid<T, Extra>(encoded: &[u8]) -> Option<(H256, Vec<u8>, Vec<u8>)>
where
	T: pallet_intents_coprocessor::Config,
	T::RuntimeCall: frame_support::traits::IsSubType<pallet_intents_coprocessor::Call<T>>
		+ DecodeWithMemTracking,
	T::AccountId: Encode + From<[u8; 32]> + DecodeWithMemTracking,
	Extra: DecodeWithMemTracking,
{
	let xt = sp_runtime::generic::UncheckedExtrinsic::<
		sp_runtime::MultiAddress<T::AccountId, ()>,
		T::RuntimeCall,
		sp_runtime::MultiSignature,
		Extra,
	>::decode(&mut &encoded[..])
	.ok()?;

	let filler = match &xt.preamble {
		sp_runtime::generic::Preamble::Signed(address, _, _) => match address {
			sp_runtime::MultiAddress::Id(id) => id.encode(),
			_ => return None,
		},
		_ => return None,
	};

	match xt.function.is_sub_type()? {
		pallet_intents_coprocessor::Call::place_bid { commitment, user_op } =>
			Some((commitment.clone(), filler, user_op.to_vec())),
		_ => None,
	}
}

pub async fn run_bid_watcher<P, Block, T, Extra>(
	pool: Arc<P>,
	bid_cache: Arc<BidCache>,
	bid_sender: broadcast::Sender<RpcBidInfo>,
	cleanup_interval: Duration,
) where
	Block: BlockT,
	P: TransactionPool<Block = Block> + 'static,
	T: pallet_intents_coprocessor::Config,
	T::RuntimeCall: frame_support::traits::IsSubType<pallet_intents_coprocessor::Call<T>>
		+ DecodeWithMemTracking,
	T::AccountId: Encode + From<[u8; 32]> + DecodeWithMemTracking,
	Extra: DecodeWithMemTracking + Send + 'static,
{
	use futures::StreamExt;

	let mut stream = pool.import_notification_stream();
	let mut timer = tokio::time::interval(cleanup_interval);

	loop {
		tokio::select! {
			Some(tx_hash) = stream.next() => {
				let tx = match pool.ready_transaction(&tx_hash) {
					Some(tx) => tx,
					None => continue,
				};

				let extrinsic_bytes = tx.data().encode();

				if let Some((commitment, filler, user_op)) = extract_bid::<T, Extra>(&extrinsic_bytes) {
					log::info!(
						target: LOG_TARGET,
						"bid in mempool for {commitment:?}",
					);
					if let Err(e) = bid_cache.insert(commitment, filler.clone(), user_op.clone()) {
						log::warn!(target: LOG_TARGET, "failed to cache bid: {e}");
						continue;
					}

					let _ = bid_sender.send(RpcBidInfo { commitment, filler, user_op });
				}
			}
			_ = timer.tick() => {
				if let Err(e) = bid_cache.remove_expired() {
					log::warn!(target: LOG_TARGET, "failed to clean bid cache: {e}");
				}
			}
		}
	}
}
