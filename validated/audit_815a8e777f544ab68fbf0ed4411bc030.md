### Title
Stale stored owner authorizes ex-owner to withdraw/borrow after position-NFT transfer — (File: contracts/controller/src/account.rs)

### Summary
The controller authorizes privileged position operations (`withdraw`, `borrow`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, `multiply`, `migrate_from_blend`, delegate checks inside `supply`) by comparing the caller against `account.owner`, a field written once at account creation, instead of the current position-NFT holder. Ownership of an account is transferable via the position NFT, but `Account.owner` is never resynced on transfer, so a seller retains full withdrawal and borrowing rights over an account they no longer own — the exact class of bug as the Chamilo endpoint that authenticated but did not authorize: authentication via `require_auth` succeeds for a stale credential while a sensitive capability is reachable.

### Finding Description
- `create_account_with` sets `Account { owner: owner.clone(), ... }` at mint time (`account.rs` line 65). There is no code path in the controller that updates `account.owner` afterward.
- `is_owner_or_delegate` returns `true` when `caller == owner` where `owner` is the stale stored field (`account.rs` lines 121–127), and `require_owner_or_delegate` (lines 130–140) gates every funds-moving entrypoint on it.
- `process_withdraw` loads the account and calls `require_owner_or_delegate(env, account_id, caller, &account.owner)` (`positions/supply.rs` lines 149–152), then pays out to `to.unwrap_or(caller)` — so the previous owner can drain collateral to themselves. The same stale check fronts `process_borrow`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, `multiply`, `migrate_from_blend`, and the new-asset gate in `require_third_party_existing_supply` (`supply.rs` lines 86–96).
- By contrast, `require_account_owner` (account.rs lines 143–148) correctly resolves ownership through `storage::account_owner` (the NFT), used only by `renew_account` and delegate management — proving the contract has two divergent notions of "owner" and the fund-moving paths use the weaker one.
- An unprivileged attacker sells/gifts the NFT for a funded account on a marketplace or peer transfer (position-nft `transfer`/`approve` are in-scope entrypoints), then calls `withdraw(account_id, [(hub_asset, 0 /* withdraw-all sentinel */)], Some(attacker))` or `borrow` to extract all collateral and max debt, leaving the buyer with an empty or insolvent account.

### Impact Explanation
Theft of user funds and protocol insolvency: the ex-owner can withdraw all supplied collateral to an arbitrary recipient (`to` parameter) and can additionally borrow against the collateral, leaving bad debt socialized onto suppliers if the buyer is unaware. Any account whose NFT has ever changed hands is fully drainable by its previous holder.

### Likelihood Explanation
A single unprivileged address can execute the attack with one NFT sale and one `withdraw` call. No privileged access, oracle manipulation, or race is needed — only the ordinary, advertised transferability of position NFTs. Every post-transfer state persists indefinitely because nothing restamps `account.owner`.

### Recommendation
In `is_owner_or_delegate`/`require_owner_or_delegate`, resolve the owner via `storage::account_owner(env, account_id)` (NFT owner) rather than the stale `Account.owner` field, or update `Account.owner` whenever the NFT is burned/transferred (e.g., have the NFT contract notify the controller, or drop the stored field entirely). The third-party supply gate in `require_third_party_existing_supply` must use the same NFT-derived owner check.

### Proof of Concept
1. Alice calls `supply(alice, 0, spoke_id, [(usdc_key, 1_000e6)])` → account `A` minted; `account.owner = alice`, NFT `A` held by Alice.
2. Alice sells/transfers NFT `A` to Bob via position-nft `transfer`. `Account.owner` still equals `alice` (`account.rs:65`, never updated).
3. Alice calls `withdraw(alice, A, [(usdc_key, 0)], Some(alice))`. `require_owner_or_delegate` passes because `caller == account.owner` (`account.rs:121`); `settle_withdraw` pays the full position to Alice (`supply.rs:152,189-198`).
4. Bob owns NFT `A` but the account is empty; Alice can also front-run with `borrow` to leave Bob an insolvent account.

Caveat: I verified the stale-owner check paths and the dual owner-resolution functions, but did not fully read `contracts/position-nft/src/contract.rs` to confirm whether the NFT contract calls back into the controller to resync `Account.owner` on transfer; if such a sync exists the finding is mitigated, but no controller-side update path was found in the searched scope.
