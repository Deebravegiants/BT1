### Title
`Initialize2` uses a permissionless, unauthenticated `market` account as the sole seed for AMM PDAs, allowing pool front-running / initial-price hijacking - (`program/src/processor.rs::process_initialize2`)

### Summary
`process_initialize2` derives every critical AMM account (coin vault, pc vault, LP mint, target orders, and the `AmmInfo` account itself) deterministically from `[program_id, market_account.key, seed]` via `get_associated_address_and_bump_seed`, and the `market_account` is explicitly documented as "Just a seed for AMM account. Can be any account" — it is never checked to be an OpenBook/Serum market owned by the market program, nor tied to any authorized creator. Because these addresses are fully predictable and creation is first-come-first-served (a second attempt fails with `RepeatCreateAmm`), any unprivileged actor can front-run a legitimate pool creator's `Initialize2` transaction for the same `market` seed and set the pool's `init_coin_amount`/`init_pc_amount` to an arbitrary, attacker-favorable ratio, exactly analogous to the front-running of Curve's `setPool`/TWAP initialization in the referenced report.

### Finding Description
In `process_initialize2` [1](#0-0) , the vault/mint/target-order/amm PDAs are derived via `get_associated_address_and_bump_seed(program_id, market_address, associated_seed, program_id)` [2](#0-1) , which only mixes in `program_id`, the caller-supplied `market_account.key`, and a fixed seed string — there is no dependency on a creator-chosen nonce, on the coin/pc mint pair, or on any signer other than "whoever submits first."

The instruction documentation itself confirms `market_info` is unauthenticated: "Just a seed for AMM account. Can be any account" [3](#0-2) , and no ownership/program check is performed on it in `process_initialize2`, unlike `amm_config_info` which is checked against a PDA and program ownership [4](#0-3) .

`generate_amm_associated_spl_token`/`generate_amm_associated_account` create these PDAs by `system_instruction::allocate`/`assign` only if the account doesn't already exist, and reject the attempt entirely with `AmmError::RepeatCreateAmm` if the target address is already owned by something other than the system program [5](#0-4) [6](#0-5) .

The initial LP amount and the resulting pool price are derived purely from whatever `init_coin_amount`/`init_pc_amount` the *first successful* caller supplies: [7](#0-6) 

Because the `market` seed can be predicted (e.g., watching a mempool for a legitimate creator's `CreatePool` transaction, or simply picking the same OpenBook market pubkey the project intends to use), an attacker can submit their own `Initialize2` first, using minimal token amounts and an extreme `init_coin_amount:init_pc_amount` ratio to set an arbitrary initial exchange rate for that market seed permanently (since the PDAs, once created, cannot be recreated by the legitimate team — any retry with the same `market` key hits `RepeatCreateAmm`).

### Impact Explanation
This is a High-severity issue because it lets an unprivileged attacker permanently hijack the initial price and LP-token distribution of any new AMM pool tied to a specific `market` seed before the legitimate creator's transaction lands:
- The legitimate creator's `Initialize2` transaction reverts (`RepeatCreateAmm`) since the vault/mint/amm PDAs are already owned.
- The attacker, with a small amount of capital, sets a heavily skewed `init_coin_amount`/`init_pc_amount` ratio and receives the corresponding disproportionate initial LP mint [8](#0-7) .
- Any subsequent depositors/swappers interacting with that pool are forced to trade against/deposit into an attacker-controlled, economically incorrect initial price, resulting in direct fund loss for legitimate LPs/traders and unbacked/incorrect pool accounting from inception — matching the report's core impact class ("unable to correctly initialize", price/accounting corruption reachable purely via front-running an unprivileged, permissionless initialization instruction).

### Likelihood Explanation
`Initialize2` is a fully permissionless instruction reachable by any signer with a wallet and token balances; no admin or config gating exists on who may call it or what `market` account/coin-pc amounts they choose. Any actor monitoring the mempool for a specific token's pool-launch attempt (a common, publicly observable event) can trivially craft and submit a front-running transaction with the identical `market` seed and their own account set. This requires no privileged keys and only a single attacker transaction, making the likelihood high whenever a pool launch is anticipated or observed.

### Recommendation
- Bind the derived PDAs to more than just `market_account.key` — e.g., require `market_account` to actually be owned by/validated against the configured OpenBook program (as historically intended), or incorporate the `coin_mint`/`pc_mint` pair and/or a creator-signed nonce into the seed derivation so the address space cannot be squatted using an arbitrary market key.
- Alternatively/additionally, require that the `user_wallet_info` signer match a pool-creation authorization recorded elsewhere (e.g., only the account that created/owns the referenced market can call `Initialize2` for it), removing the "first submitter wins" race entirely.

### Proof of Concept
1. Project team prepares to launch a pool for `TOKEN/USDC` by choosing an OpenBook `market` pubkey `M` and plans to call `Initialize2` with `init_coin_amount = 1_000_000`, `init_pc_amount = 1_000_000` (fair price).
2. Attacker observes the pending transaction (or independently learns `M` will be used) and computes the same deterministic PDAs: `get_associated_address_and_bump_seed(program_id, M, COIN_VAULT_ASSOCIATED_SEED, ...)`, etc. [2](#0-1) .
3. Attacker submits `Initialize2` first with the same `market = M`, `coin_mint`/`pc_mint`, but `init_coin_amount = 1`, `init_pc_amount = 1_000_000_000_000` (or vice versa), funded with a trivial amount of tokens.
4. Attacker's transaction lands first: `generate_amm_associated_spl_token`/`generate_amm_associated_account` successfully create the vaults/mint/amm accounts and assign ownership [9](#0-8) ; the pool is initialized at the attacker's extreme price and the attacker receives the corresponding initial LP tokens [10](#0-9) .
5. The legitimate team's original `Initialize2` transaction now fails with `AmmError::RepeatCreateAmm` since all target PDAs already exist and are no longer owned by the system program [6](#0-5) , permanently blocking correct initialization for that `market` seed and leaving the pool at the attacker-controlled price.
