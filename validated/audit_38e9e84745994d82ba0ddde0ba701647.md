### Title
Permanent market freeze: `borrowed * borrow_index` overflows `i128` inside accrual before the index cap can engage, bricking every verb on the market - (File: common/src/rates/index.rs)

### Summary
CVE-2016-0656 is a local availability-loss bug in InnoDB. The analog in XOXNO Lending is a permanent denial-of-service of an entire pool market: once a market's scaled debt grows large enough that `borrowed_scaled_ray * borrow_index` exceeds `i128::MAX`, the interest accrual that runs at the head of every mutating entrypoint panics with `MathOverflow` forever. No repay, withdraw, borrow, liquidate, clean_bad_debt, flash_loan, or recapitalize can ever execute on that market again, so all supplied funds in it are permanently frozen. The borrow-index ceiling `MAX_BORROW_INDEX_RAY` does not prevent this because the overflow happens on the value product (`scaled shares × index`), not on the index itself.

### Finding Description
Every market mutation loads the market through `Cache::load` and runs `interest::global_sync` before touching state (`contracts/pool/src/interest.rs:20-33`). `global_sync` calls `accrue_chunk` → `accrue_step`, which splits accrued interest via `calculate_supplier_rewards`. That function computes:

```rust
// common/src/rates/index.rs:80-81
let old_total_debt = borrowed.mul(env, old_borrow_index);
let new_total_debt = borrowed.mul(env, new_borrow_index);
```

`borrowed` is the scaled-debt share count in raw RAY units (asset amount rescaled to 27 decimals), and `Ray::mul` panics on `i128` overflow. The index cap in `update_borrow_index` (`common/src/rates/index.rs:13-19`) clamps the *index* to `MAX_BORROW_INDEX_RAY = 1e36` (`common/src/constants/pool.rs:19`), but the value ceiling is `i128::MAX ≈ 1.7e38`, so a scaled debt of `1e36` overflows after only ~170x of index growth — far below the cap. The in-repo test documents exactly this:

```rust
// tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:315-360
// "A billion whole tokens is 1e36 raw ray; the value ceiling is i128::MAX, 170 times that.
//  ... the index grows past 170x ... and the next accrual panics inside scaled_to_original.
//  Every verb accrues first, so the market freezes: no repay, no withdraw, no liquidation.
//  The index cap never engages."
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

Because `global_sync` is unconditional and the panic aborts the transaction, the failure is *sticky*: state is never written, so the next caller hits the identical overflow. There is no owner-only rescue path that skips accrual — `update_params`, `update_indexes`, `seize_positions`, `recapitalize`, and `claim_revenue` all go through the same `Cache::load`/accrue sequence. Once the cliff is crossed, the market is permanently bricked.

Reachability by a single unprivileged address: supply caps are per-market configuration, but `calculate_scaled_cap` notes the cap check "fails open" via saturation (`common/src/rates/scaling.rs:18-33`), and caps are only validated to be within asset domain, not to bound scaled-debt to a safe share count. A whale supplying a large position in a high-decimals asset and borrowing at high utilization pushes `borrowed_scaled` toward `1e36`; sustained high utilization on a steep rate curve then compounds the index past the ~170x product cliff. From that point any unprivileged call to `update_indexes`/`repay`/`withdraw` on the controller triggers the panic and locks the market for everyone.

### Impact Explanation
Permanent freezing of all funds in the affected `(hub, token)` market: every supplier's deposit, including unrelated users', becomes unreachable because `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, `flash_loan`, `recapitalize`, and `claim_revenue` all accrue first and all panic. Bad debt on that market can never be written down, so a simultaneous under-collateralization event cannot be resolved — compounding into insolvency. This matches the accepted "permanent freezing of funds" / "contract unable to operate" impact class, and the repo's own regression test asserts the freeze rather than treating it as intended behavior.

### Likelihood Explanation
Medium. The trigger requires (a) a large scaled-debt base — realistic only for high-decimals assets at whale scale or with loose supply caps, and (b) enough compound accrual for `borrowed * index` to cross `i128::MAX`, which the test shows occurring within tens of years on the steep segment of the XLM-style curve at ~98% utilization. No privileged action is needed to reach the state — `supply` and `borrow` are unprivileged — and once reached, any unprivileged `update_indexes`/`repay` call detonates it. There is no self-healing path, so the earliest moment of overflow is the permanent freeze point.

### Recommendation
Cap the *value product*, not just the index. Concretely:

- In `accrue_step`/`calculate_supplier_rewards` (`common/src/rates/index.rs:73-89`), use `mul_div`-style saturating arithmetic or early-clamp `new_borrow_index` so that `borrowed.mul(new_borrow_index)` stays within `i128::MAX`, e.g. clamp `new_borrow_index` to `min(MAX_BORROW_INDEX_RAY, i128::MAX * RAY / borrowed)` before computing debt values.
- Alternatively, enforce at listing/`update_params` time that `max_cap` cannot admit a scaled-supply/scaled-debt whose product with `MAX_BORROW_INDEX_RAY` would overflow — extend `require_cap_within_asset_domain` to check the share-domain headroom.
- Add a regression test asserting the index cap engages *before* the value ceiling for the maximum configurable cap at each supported decimals.

### Proof of Concept
The in-repo test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-360`) is a working PoC:

1. Supply `1e9 * 1e18` raw units of an 18-decimals asset (`borrowed_scaled ≈ 1e36`).
2. Borrow ~98% of it via the unprivileged controller `borrow`.
3. Advance ledger time; call the unprivileged `update_indexes` each period.
4. Within ~40 years of simulated time, one accrual panics with `MathOverflow` (#33) inside `scaled_to_original`/`calculate_supplier_rewards` while `borrow_index < MAX_BORROW_INDEX_RAY` — proving the index cap never engaged.
5. Subsequently `try_withdraw_raw(BOB, ...)` and `try_repay(ALICE, ...)` both revert with `MathOverflow`; the market is frozen permanently for all users.
