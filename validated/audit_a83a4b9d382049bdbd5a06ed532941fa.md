## #Vulnerability Found

### Title
Webhook `shop` identity is not bound by the HMAC signature, enabling shop-domain spoofing on replayed webhooks - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw request body only, while the `shop` (merchant identity) is read straight from the unauthenticated `X-Shopify-Shop-Domain` header. `Registry.process` verifies the HMAC and then forwards `request.shop` to the app's webhook handler as trusted merchant identity, even though that field was never covered by the signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) [3](#0-2) 

`Registry.process` validates the HMAC against `to_signable_string` (i.e., only the body), then immediately reads `request.shop` from the header and passes it to the app handler as authenticated merchant context: [4](#0-3) 

The equality the HMAC is supposed to guarantee is:
`hmac == HMAC(client_secret, body + shop + topic)` bound to a specific `shop`.

What is actually verified is only:
`hmac == HMAC(client_secret, body)`

with `shop` supplied out-of-band and unauthenticated. Any two requests with identical bodies but different `X-Shopify-Shop-Domain` headers produce the exact same valid HMAC.

### Impact Explanation
An unprivileged actor who legitimately installs the app on their own development/trial store (unprivileged internet user, no special credentials needed) will receive genuine webhook deliveries signed with the app's shared `client_secret` (the same secret is used for all installs of an app). By capturing one such valid `(raw_body, hmac)` pair and replaying it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim merchant's domain, the request still passes `HmacValidator.validate` because the shop header is not part of the signed content. The handler then processes data under `WebhookMetadata(shop: <victim-shop>, ...)` — a cross-tenant identity confusion. Depending on how the host app wires this (e.g., GDPR `shop/redact`, `customers/redact`, `app/uninstalled` handlers keyed off `shop`), this can trigger state changes, data deletion, or session/token revocation attributed to the wrong tenant, i.e., cross-tenant impact without ever needing the app's `client_secret`.

### Likelihood Explanation
Requires only: (1) the attacker installs the target app on their own shop (an unprivileged action), and (2) the attacker can send arbitrary HTTP requests to the app's public webhook endpoint with custom headers — both trivially available to any internet user, no `api_secret_key` or access token needed.

### Recommendation
Bind the shop (and topic) identity into the HMAC computation, or otherwise ensure the caller cross-checks `request.shop` against the shop context the webhook is being processed for before trusting it — e.g., include `shop-domain` and `topic` headers in `to_signable_string`, matching Shopify's tenant-binding guarantees, not just body integrity.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Shopify sends a legitimate webhook (e.g., `orders/create`) to the app with a valid `X-Shopify-Hmac-Sha256` computed over the raw body using the app's `client_secret`.
3. Attacker captures `raw_body` and `hmac`, then POSTs the identical body/hmac to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` in `Registry.process` (`lib/shopify_api/webhooks/registry.rb:190`) succeeds because it only checks `raw_body` against the HMAC.
5. `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` (`lib/shopify_api/webhooks/registry.rb:198-199`) is invoked with `shop == "victim-shop.myshopify.com"`, even though this webhook was never sent by Shopify for that shop.
