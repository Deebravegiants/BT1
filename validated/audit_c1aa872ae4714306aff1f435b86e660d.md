### Title
`describeWithdrawal` in PoaBridge misreports withdrawal status when multiple withdrawals of the same asset share one intent transaction - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` looks up the on-chain withdrawal record by matching only on `assetId`, ignoring the `index` field of `WithdrawalIdentifier`. When a single NEAR intent transaction contains two or more withdrawals of the same token (e.g. batched withdrawals to different destination addresses), the code cannot distinguish between them and will report the status/txHash of whichever matching record happens to be first, for every withdrawal identifier of that asset.

### Finding Description
`describeWithdrawal` fetches all withdrawals for a given NEAR tx hash and then calls `findMatchingWithdrawal`, which selects a withdrawal purely by `nep141:${w.data.near_token_id} === assetId`: [1](#0-0) 

This function is documented as a known limitation ("multiple withdrawals of the same token in a single transaction are not supported"), but it is still wired into the production `describeWithdrawal` API, which is the source of truth for "is this specific withdrawal done and what is its destination-chain tx hash": [2](#0-1) 

The `index` field that `createWithdrawalIdentifier` assigns per-bridge-route is never used to disambiguate between multiple same-asset withdrawals: [3](#0-2) [4](#0-3) 

`createWithdrawalIdentifiers`/`waitForWithdrawalCompletion` call `describeWithdrawal` once per withdrawal entry with the same `withdrawalParams.assetId` but different indexes/destinations, and each call independently re-runs `findMatchingWithdrawal`, returning the same (first-matching) record for all of them: [5](#0-4) 

This breaks the equality that should hold: *the status/txHash reported for withdrawal N is the on-chain outcome of withdrawal N specifically* — not of some other withdrawal of the same asset in the batch. If withdrawal #0 (destination A, amount X) completes and withdrawal #1 (destination B, amount Y) is still pending or failed, `describeWithdrawal({index:1, assetId, ...})` will still return withdrawal #0's `COMPLETED` status and `transfer_tx_hash`.

### Impact Explanation
An integrator relying on `sdk.waitForWithdrawalCompletion` / `createWithdrawalCompletionPromises` / `describeWithdrawal` to decide when to credit a user or mark a withdrawal as settled would receive a **false "completed" status with a transfer tx hash that does not correspond to that withdrawal**. This can cause:
- Premature/duplicate crediting: the integrator marks withdrawal #1 as delivered (using withdrawal #0's tx hash) while withdrawal #1's funds have not actually landed, or land later with a different hash — a status/hash misreport that can make an integrator credit twice or refund incorrectly.
- Silent stuck funds: if withdrawal #0 fails and #1 succeeds, `findMatchingWithdrawal` (which uses `.find()`, returning the first match) could report the failed status/hash for the successful withdrawal, causing the integrator to treat working funds as failed and take unnecessary "stuck funds" recovery action.

This matches the "status or hash misreport making an integrator credit or refund twice" / "withdrawal stuck until manual intervention" High-impact criteria, since no malicious behavior is required — it triggers whenever a caller legitimately batches two withdrawals of the same NEP-141 asset (e.g. paying out two different users the same token in one settlement) via `PoaBridge`.

### Likelihood Explanation
Likelihood is limited by the precondition that two-or-more withdrawals of the *same* asset must be routed through `PoaBridge` within the *same* NEAR intent transaction — the SDK does support constructing and sending multiple withdrawals in a single `withdrawalParams` array/intent, and this pattern (e.g., a batch payout job paying multiple recipients the same token) is realistic for integrators. The bug is deterministic once that precondition is met (not probabilistic), and the code comment confirms the maintainers are aware of the limitation but the fallback (silently returning the wrong record) is worse than throwing/erroring.

### Recommendation
- In `findMatchingWithdrawal`, when multiple withdrawals for the same `assetId` are found in the response, disambiguate using additional deterministic criteria (e.g., match on amount + destination address, or reject/throw when the count of API-side and locally-tracked same-asset withdrawals differ, per the existing code comment's suggested ordering-by-amount approach) rather than silently returning `.find()`'s first match.
- Until POA API supports precise per-withdrawal identification, `describeWithdrawal`/`getWithdrawalStatusWithRetry` should refuse to report a definitive status (throw or return an explicit "ambiguous/untrackable" status) whenever more than one same-asset withdrawal exists for the same `tx.hash`, instead of returning a misleading "completed" status tied to the wrong withdrawal.
- Add an explicit invariant check in `createWithdrawalIdentifiers` warning/erroring when batching multiple same-asset withdrawals through `PoaBridge`, since status tracking for that combination is unsupported.

### Proof of Concept
1. Caller submits one NEAR intent transaction containing two POA-bridge withdrawals of `nep141:usdc.omft.near`: withdrawal #0 → address A, withdrawal #1 → address B.
2. `createWithdrawalIdentifiers` assigns `index: 0` and `index: 1` to the two `WithdrawalIdentifier`s for `PoaBridge` (per-route counter), per [4](#0-3) .
3. Caller invokes `sdk.waitForWithdrawalCompletion` for both. Internally, `PoaBridge.describeWithdrawal` is called twice, once per identifier, both with the same `withdrawalParams.assetId`.
4. The POA Bridge API returns both withdrawal records in its `withdrawals` array for the tx hash — say withdrawal-to-A is `COMPLETED` with `transfer_tx_hash: "0xA"`, and withdrawal-to-B is still `PENDING`.
5. `findMatchingWithdrawal(response.withdrawals, "nep141:usdc.omft.near")` returns the **same** first record (`0xA`, `COMPLETED`) for *both* calls, since it only filters on `assetId` ( [6](#0-5) ).
6. Both `describeWithdrawal({index:0,...})` and `describeWithdrawal({index:1,...})` return `{ status: "completed", txHash: "0xA" }`, even though withdrawal #1 to address B has not completed and its actual destination hash (once it completes) will differ.
7. The integrator, trusting the SDK's per-withdrawal result, marks withdrawal #1 as delivered to B using tx hash `0xA` — a misreport that can lead to double-crediting or incorrect reconciliation.

		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
