## Title
Permanent underflow DoS in `pallet-asset-rewards` freezes all staked funds and rewards once a pool's `last_update_block` is updated past `expiry_block` — (File: `substrate/frame/asset-rewards/src/lib.rs`)

## Summary
`update_pool_rewards` unconditionally sets `last_update_block` to the current, uncapped block number [1](#0-0) , while `reward_per_token` computes elapsed blocks as `last_block_reward_applicable(expiry_block).ensure_sub(last_update_block)` [2](#0-1) , which is only valid when `last_update_block <= expiry_block`. Once any call advances `last_update_block` past a pool's `expiry_block` while the pool still has staked tokens, every subsequent call on that pool permanently underflows and reverts, including the admin's own recovery calls.

## Finding Description
`last_block_reward_applicable` clamps `now` to `expiry_block` but returns `expiry_block` for any `now >= expiry_block` [3](#0-2) . Meanwhile `update_pool_rewards` stores the raw, unclamped current block number into `last_update_block` [4](#0-3) . This asymmetry means: once a call occurs after expiry, `last_update_block` becomes greater than `expiry_block`. On the next call, `reward_per_token` computes `expiry_block.ensure_sub(last_update_block)`, which underflows because `last_update_block > expiry_block`, returning `Err(ArithmeticError)` and aborting the extrinsic [2](#0-1) .

Critically, this underflow path is only reached when `pool_info.total_tokens_staked` is non-zero, since a zero-staked pool takes an early-return branch that bypasses the subtraction entirely [5](#0-4) . As long as any stake remains, the bug is reachable.

All staker-facing mutating entry points (`stake`, `unstake`, `harvest_rewards`) route through `update_pool_and_staker_rewards`, which calls `reward_per_token` then `update_pool_rewards` [6](#0-5) , and are invoked at the top of `stake` [7](#0-6) , `unstake` [8](#0-7) , and `harvest_rewards` [9](#0-8) . The admin-only `set_pool_reward_rate_per_block` and `set_pool_expiry_block` also call `reward_per_token` first before applying any update [10](#0-9) [11](#0-10) , meaning there is no in-protocol recovery path once the underflow condition is triggered — even `set_pool_expiry_block`, which would otherwise extend the pool and fix the state going forward, itself reverts before it can apply the fix.

## Impact Explanation
Once triggered by a normal post-expiry call, every subsequent mutating call on the pool (`stake`, `unstake`, `harvest_rewards`, and both admin remedies) reverts with `ArithmeticError`. Because `unstake` itself goes through the identical reverting code path, staked tokens frozen via `AssetsFreezer` become permanently unrecoverable, and any pending reward-asset balance in the pool account becomes unreachable via `harvest_rewards`. This is a complete, permanent fund lock and denial of service for the affected pool with no admin-level remedy, which is a severe impact class (permanent loss of user funds).

## Likelihood Explanation
This requires no privileged role or attacker-specific setup. Any unprivileged staker calling `unstake` or `harvest_rewards` after `expiry_block` (both explicitly permitted post-expiry per the `ensure!(now > pool_info.expiry_block || caller == staker, BadOrigin)` checks) naturally advances `last_update_block` past `expiry_block`. This is normal, expected usage of an expired pool — a single such call, followed by any second mutating call on the same pool while stake remains, deterministically triggers the permanent underflow. The condition is highly likely to occur organically for any pool that isn't emptied of all stake before/at expiry.

## Recommendation
In `update_pool_rewards`, clamp the stored `last_update_block` to `last_block_reward_applicable(pool_info.expiry_block)` rather than the raw current block number, mirroring the clamp already used in `reward_per_token`, so `last_update_block` never exceeds `expiry_block`.

## Proof of Concept
1. `create_pool` with `expiry_block = E` (e.g. block 25).
2. Staker stakes non-zero tokens before expiry (`total_tokens_staked > 0`).
3. Advance `System::set_block_number` to a block past `E` (e.g. 30) and call `unstake` for a partial amount, or `harvest_rewards` — succeeds; `update_pool_rewards` sets `last_update_block = 30` (uncapped, > `E`).
4. Advance to a later block (e.g. 40) and call `stake`, `unstake`, `harvest_rewards`, or the admin's `set_pool_reward_rate_per_block`/`set_pool_expiry_block` on the same pool — `reward_per_token` computes `last_block_reward_applicable(25) = 25`, then `25.ensure_sub(30)`, which underflows and returns `Err(ArithmeticError)`, reverting the extrinsic.
5. Repeat step 4 with any other account, including the admin — all revert identically, permanently locking staked funds and reward-asset balances in the pool.

This matches the exact code paths in `substrate/frame/asset-rewards/src/lib.rs` for `update_pool_rewards`, `reward_per_token`, and `last_block_reward_applicable`, and no existing guard (the `BadOrigin` checks in `unstake`/`harvest_rewards`, or the admin checks in `set_pool_expiry_block`/`set_pool_reward_rate_per_block`) prevents or clamps this state before the underflow occurs.
