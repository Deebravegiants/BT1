### Title
Webhook shop/topic identity is trusted from unauthenticated headers while only the body is HMAC-verified - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from HTTP headers that are never covered by the signature. `ShopifyAPI::Webhooks::Registry.process` validates only the body HMAC and then forwards the unauthenticated `shop`/`topic` header values straight to the host application's webhook handler. This breaks the binding: `HMAC-authenticated sender == origin of the claimed shop`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` and `Request#topic` are pulled straight from headers with no cryptographic binding to the body or its HMAC: [2](#0-1) 

`Registry.process` validates only the HMAC of `request` (i.e., the body) and then hands `request.shop`/`request.topic` — both unauthenticated — to the handler alongside the (authenticated) body: [3](#0-2) 

Because the HMAC secret (`Context.api_secret_key`, the app's `client_secret`) is identical for every shop that installs the app, any merchant who legitimately installs the app can:
1. Trigger a real Shopify webhook to their own endpoint (or capture one sent through this library), obtaining a request whose body carries a genuinely valid `x-shopify-hmac-sha256` signature.
2. Replay that exact HTTP request to the app's webhook endpoint, changing only the `x-shopify-shop-domain` (and optionally `x-shopify-topic`) header to name a different, victim shop.
3. `Utils::HmacValidator.validate` still succeeds because it only re-hashes `@raw_body`, which is untouched.
4. `Registry.process` builds `WebhookMetadata` with `shop: <victim-domain>` (attacker-chosen) but `body: request.parsed_body` (still the attacker's own shop's data), and invokes the app-registered handler with it.

The equality that should hold — "shop the HMAC authenticates" == "shop passed to the handler" — is broken: the HMAC only authenticates *that some installed shop of this app* produced the bytes, not *which* shop the header claims.

### Impact Explanation
Most Shopify apps key their tenant data off `WebhookMetadata#shop` (e.g., to decide which merchant record/database row a webhook payload updates). A malicious-but-legitimately-installed merchant can use this gap to inject or poison data attributed to another tenant (`shop` field mismatched from the actual signer), which is a cross-tenant integrity/data-isolation break — no `api_secret_key`, access token, or privileged access is required, only ordinary app installation available to any internet user who can install a Shopify app.

### Likelihood Explanation
Any user who can install the target Shopify app (a routine, unprivileged action) automatically receives real webhooks with genuinely valid HMACs for their own shop's events, and HTTP header replay/tampering is trivial to perform against any HTTP endpoint. No secret material or elevated privilege is needed to exploit the missing header-shop binding.

### Recommendation
Bind the `shop` (and `topic`) claim into the value that is HMAC-verified — e.g., include the `x-shopify-shop-domain` and `x-shopify-topic` header values in `to_signable_string` (matching Shopify's documented practice of validating relevant headers, not just the raw body), or require the host application to cross-check `request.shop` against an independently known/authorized shop (e.g., a registered session/shop list) before acting on the payload, rejecting webhooks whose header-claimed shop cannot be corroborated.

### Proof of Concept
1. Install the target app on shop `attacker.myshopify.com`; capture a legitimate webhook POST it sends to the app's endpoint, e.g. `orders/create` with headers:
   ```
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC over body>
   x-shopify-shop-domain: attacker.myshopify.com
   ```
2. Replay the identical request to the same endpoint, only replacing:
   ```
   x-shopify-shop-domain: victim.myshopify.com
   ```
   (body and `x-shopify-hmac-sha256` unchanged).
3. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) succeeds because it only checks the untouched raw body.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the handler with `shop: "victim.myshopify.com"` and the attacker's own order body — the handler now attributes attacker-controlled data to the victim tenant.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
