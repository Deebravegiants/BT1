### Title
EvmHost.dispatch/fundRequest do not refund excess native-token payment, permanently trapping user ETH - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` accept `msg.value` and swap it for the exact `feeToken` amount via `swapETHForExactTokens`, but never capture the amount actually spent nor refund the leftover ETH to the caller. Any ETH sent beyond what is needed to cover `post.fee`/`get.fee`/`amount` is refunded by the Uniswap router to `msg.sender` of the swap call — which is `EvmHost` itself, not the original transaction sender — leaving that ETH stranded in the host contract with no accounting or recovery path for the user.

### Finding Description
In `dispatch(DispatchPost)`: [1](#0-0) 

the contract does:
```solidity
IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
```
`UniswapV2Router02.swapETHForExactTokens` only consumes the amount of ETH required to obtain exactly `post.fee` output tokens; any unused portion of `msg.value` is refunded via `TransferHelper.safeTransferETH(msg.sender, leftover)` where `msg.sender` (from the router's perspective) is `EvmHost`, not the account that called `dispatch`. `EvmHost` does not capture the swap's return value (the array of `[amountIn, amountOut]`) and has no logic afterward to forward the refunded leftover ETH back to `_msgSender()`. The identical pattern is repeated in `dispatch(DispatchGet)`: [2](#0-1) 
and in `fundRequest`: [3](#0-2) 

This is the same root-cause class as the reported `FeeBuyback.submit` issue: the contract accepts `msg.value` for payment but does not account for/return any surplus, so any overpayment becomes an unrecoverable donation trapped in the contract balance.

By contrast, the codebase demonstrates the correct pattern elsewhere: `IntentGatewayV2` captures the `amounts` returned by `swapETHForExactTokens`, decrements the tracked `msgValue` by the actual amount spent, and explicitly refunds the remainder to the caller: [4](#0-3) 
This same defensive pattern is absent in `EvmHost`'s three payable dispatch/fund entry points.

Additionally, callers who use `IHyperFungibleToken.send()`, `WrappedHyperFungibleToken.send()`, `HyperApp.dispatchWithFeeToken`-adjacent native-payment helpers, or any custom `IApp` that calls `IDispatcher(host()).dispatch{value: msg.value}(...)` inherit this bug transitively, since they simply forward `msg.value` to `EvmHost.dispatch` without any independent overpayment protection (as documented, users are expected to send exactly enough native token for the swap, but any miscalculation, price movement between quote and execution, or slippage buffer results in silent fund loss).

### Impact Explanation
Any user or contract that dispatches a POST/GET request or funds a pending request using native-token payment and sends more ETH/native token than strictly required for the Uniswap swap to the exact `feeToken` fee amount will have the surplus permanently stuck in `EvmHost`, with no function exposed to reclaim it for that specific payer. Because `quote()` (used off-chain for estimation) is explicitly documented as being sandwich-attack-prone and only an estimate, real-world callers routinely pad `msg.value` to guard against slippage — meaning surplus loss is a realistic, frequent occurrence rather than an edge case. This is a direct, permanent loss of user funds (native token) at one of the most heavily used entry points in the protocol (every cross-chain POST/GET dispatch paid in native token). This qualifies as Medium severity: unbacked/unrecoverable fund loss for the fee payer, though it does not compromise protocol solvency, message integrity, or allow theft of others' funds.

### Likelihood Explanation
High likelihood of occurrence in practice: every dispatch/fundRequest call using native-token payment risks leaving dust, and since exact swap amounts are unpredictable on-chain (AMM price impact, MEV, quote staleness) it is expected that most native-fee payers overpay. However, per-transaction loss size is generally small (Uniswap slippage margin), which is reflected in the Medium severity rather than High/Critical.

### Recommendation
Capture the return value of `swapETHForExactTokens` in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, and refund `msg.value - amountIn` (the ETH actually spent) back to `_msgSender()` via a low-level call, mirroring the pattern already implemented in `IntentGatewayV2._placeOrder`/`_fillCrossChain`. Example:
```solidity
if (msg.value > 0) {
    uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
        post.fee, path, address(this), block.timestamp
    );
    uint256 refund = msg.value - amounts[0];
    if (refund > 0) {
        (bool ok,) = _msgSender().call{value: refund}("");
        require(ok, "refund failed");
    }
}
```

### Proof of Concept
1. Deploy `EvmHost` with a configured `uniswapV2` router and `feeToken`.
2. Caller calls `dispatch(DispatchPost{fee: 1e18, ...})` with `msg.value = 2 ether` (intentionally overpaying to cover expected slippage, as is standard practice since `quote()` is only an off-chain estimate).
3. `swapETHForExactTokens` only spends the ETH required to acquire exactly `1e18` fee tokens (e.g., 0.3 ETH) and refunds the remaining ~1.7 ETH to `address(this)` (EvmHost), increasing the host's ETH balance.
4. `dispatch` returns normally; no logic exists to forward the 1.7 ETH refund back to the caller.
5. `address(host).balance` permanently retains the surplus ETH; the original caller has no function to reclaim it, and it is never accounted for or emitted in any event — this can be verified against `evm/tests/foundry/EvmHostForkTest.sol` tests such as `testCanDispatchPostRequestWithNative`, none of which assert that the caller's balance is restored to `balanceBefore - actualCost` (compare with `evm/tests/foundry/IntentGatewayV2Test.sol:testPlaceOrder_FeeSwap_RefundsExcessNativeToken`, which explicitly asserts a refund occurs at the `IntentGatewayV2` layer — no equivalent test or refund logic exists for `EvmHost.dispatch`).
