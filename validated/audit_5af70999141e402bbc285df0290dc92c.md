Found a solid analog to the fee-on-transfer bug class: the webhook HMAC in this gem covers only the raw request body, not the shop/topic identity headers that the application actually acts on.### Title
Webhook `shop-domain` and `topic` headers are not covered by the HMAC signature, allowing cross-tenant shop impersonation - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then trusts the `shop-domain` and `topic` HTTP headers — which are *not* part of the signed material — to decide which tenant and which handler the payload belongs to.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The HMAC validator computes/compares the signature purely over that signable string: [2](#0-1) 

`Registry.process` gates handling on `HmacValidator.validate(request)` succeeding, then builds `WebhookMetadata` directly from the request's `shop`, `topic`, `webhook_id`, and `api_version` accessors — all of which are read straight from HTTP headers, never included in the HMAC-signed bytes: [3](#0-2) [4](#0-3) 

The identity binding that should hold is:
`hmac-verified(shop-domain header) == shop the payload actually originated from`

That binding does not exist: the HMAC only proves "this raw body byte-string was produced with the app's `client_secret`" — it says nothing about which shop or topic the sender claims via headers. Since Shopify uses one `client_secret` per app (not per shop), any merchant who installs the app on their own store legitimately receives webhooks with valid `(raw_body, hmac)` pairs signed with that same app secret. An attacker who controls such a store can capture one of these valid pairs and replay it to the app's public webhook endpoint with an arbitrary `shopify-shop-domain` (or `shopify-topic`, `shopify-webhook-id`) header. `HmacValidator.validate` still passes because it only checks the body, and `Registry.process` hands the forged `shop`/`topic` straight to the host app's `WebhookHandler#handle` as `WebhookMetadata`: [5](#0-4) 

Any host application that uses `data.shop` from `WebhookMetadata` to look up/act on a specific merchant's records (as the gem's own documentation instructs) will act on the attacker-chosen shop, using a body the attacker fully controls (since JSON content beyond required Shopify fields is otherwise unconstrained) — a genuine cross-tenant confusion, directly analogous to the `ERC4626` bug where `totalAssets` accounting used a value (`amount`) not adjusted for what actually happened downstream (the transfer fee), i.e. an unverified field is trusted as if it were verified.

### Impact Explanation
This falls under "cross-tenant access": an unprivileged internet user who has legitimate access to any single shop that installs the app can forge webhook events attributed to an arbitrary other shop, with a body of their choosing (subject to the target handler's minimal expected keys). Depending on how the host app's webhook handlers use `data.shop` (e.g., updating order/customer/subscription state, revoking access, writing to per-shop storage), this can lead to data corruption or state changes performed against a victim tenant using attacker-controlled data — a break of the tenant isolation boundary that `Registry.process`/`HmacValidator` is supposed to guarantee.

### Likelihood Explanation
Moderate-to-high: it requires the attacker to control (or briefly rent/trial) one shop where the target app is installed, and to know the app's public webhook receiver URL, both of which are readily available to any developer testing a public/embedded app. No possession of the app's `client_secret` or an access token is required — only a genuine webhook delivery from Shopify to the attacker's own store.

### Recommendation
Include shop-identifying and topic-identifying context in the HMAC-signed material, or otherwise cryptographically bind these headers to the payload before trusting them in `Registry.process`/`WebhookMetadata`. At minimum, document (and ideally enforce in the gem) that host applications must independently verify that the webhook's `shop` header corresponds to a shop with a currently valid, stored session/access token for that specific webhook subscription, rather than trusting the header value emitted from an HMAC check that never covered it.

### Proof of Concept
1. Attacker installs the target app on their own Shopify development store (unprivileged action, no special credentials needed beyond a free dev store).
2. Shopify delivers a legitimate webhook to the app's endpoint: body `B`, headers `shopify-hmac-sha256: HMAC(secret, B)`, `shopify-shop-domain: attacker-shop.myshopify.com`, `shopify-topic: orders/create`.
3. Attacker resends the exact same `raw_body: B` and `hmac` header to the app's webhook endpoint but sets `shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only checks `B` against the HMAC (`lib/shopify_api/webhooks/registry.rb:190`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
5. `Registry.process` invokes the app's handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", topic: "orders/create", body: parsed(B), ...)`, causing the host app to act on the victim shop's tenant context using attacker-supplied body content.
