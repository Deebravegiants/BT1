### Title
Webhook `shop-domain` Header Not Covered by HMAC Signature Enables Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop-domain` header — the field used by the application to attribute the webhook payload to a specific merchant — is never included in that signature. An unprivileged user who controls any single shop (e.g., a free/dev store) can capture one genuinely-signed webhook delivery and replay it to the app's webhook endpoint with a forged `shop-domain` header pointing at a victim shop. The HMAC check still passes (it only validates the body), and the handler processes the attacker-controlled body under the victim's tenant identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, entirely outside the signed material: [2](#0-1) 

`HmacValidator.validate` verifies the signature exclusively against `verifiable_query.to_signable_string`, i.e. the body: [3](#0-2) 

`Registry.process` checks only that HMAC validation passes, then hands the unauthenticated `request.shop` value straight to the registered handler as the tenant identity for the payload: [4](#0-3) 

This breaks the intended identity binding: `shop that produced/authorized the signed body == shop attributed to the payload by the app`. Because only the body is bound by HMAC, any actor who can obtain one validly-signed webhook (for a shop they legitimately control) can resend the exact same body/HMAC pair with a different `shop-domain` header value, and the app has no way to detect the mismatch — the check is permissive by construction, analogous to the WETH9 `approve` bug class where a field that is acted upon (`shop`) is not covered by the same atomic/cryptographic guarantee as the rest of the operation (`raw_body`).

### Impact Explanation
This is a cross-tenant data injection vector: an app that persists or acts on webhook body data keyed by `WebhookMetadata#shop` (e.g., writing "shop X's product was updated" to shop X's tenant record) can be made to apply attacker-controlled body content to a different (victim) shop's tenant data, since `shop` is fully attacker-controllable independent of the signature. Depending on how the host application's webhook handlers use `data.shop` (virtually always used as the tenant/row key), this can result in cross-tenant data corruption, unauthorized state changes on a victim's data, or triggering business logic (uninstall/reinstall flows, order/customer sync, etc.) against a shop the attacker does not have access to — matching the Critical "cross-tenant access" impact bucket.

### Likelihood Explanation
Requires only registering the target app on one attacker-controlled shop (unprivileged internet action — no `api_secret_key`, access token, or social engineering needed), capturing a single legitimately delivered webhook (raw body + `x-shopify-hmac-sha256`), and replaying it to the app's public webhook endpoint with a modified `x-shopify-shop-domain` header. All of the cryptographic material required (the HMAC) remains valid because it never covered the header field being tampered with.

### Recommendation
Include `shop-domain` (and ideally `topic`/`webhook-id`) in the signed/verified material, or independently verify that `request.shop` corresponds to a shop session/tenant the app actually expects for that specific HMAC-bound body (e.g., cross-check against a known list of installed shops and reject if the webhook's claimed shop was not the one that installed/owns the webhook subscription). At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be trusted as an identity boundary by consuming handlers without additional verification.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com` (free/dev store, no privileged access needed).
2. Trigger a webhook delivery (e.g., `products/update`) and capture the raw body `B` and its valid `x-shopify-hmac-sha256` header `H` (computed by Shopify using the app's real secret against `B`).
3. Replay the request to the app's webhook endpoint, keeping `x-shopify-hmac-sha256: H` and `x-shopify-topic` unchanged, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` succeeds because it only checks `H` against `B`, per `lib/shopify_api/webhooks/request.rb` and `lib/shopify_api/utils/hmac_validator.rb`.
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing attacker-controlled body content to be processed as if it originated from the victim shop.
