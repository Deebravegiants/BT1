### Title
Session Fixation via Predictable, Unsigned Session Cookie Value - ([File: lib/shopify_api/auth/session.rb], [File: lib/shopify_api/auth/oauth.rb], [File: lib/shopify_api/utils/session_utils.rb])

### Summary
For non-embedded apps, the gem sets a session-identifying cookie whose value is the deterministic, unsigned session `id` (`"offline_#{shop}"` or `"#{shop}_#{user_id}"`). This value carries no cryptographic binding to the OAuth transaction that produced it. Any party able to place this cookie in a victim's browser can force the host application to resolve a specific merchant's stored session — a session-fixation / cross-tenant identity binding failure.

### Finding Description
The identity binding that should hold is:

`session_id trusted by the host app via cookie == session_id produced from an HMAC/signature-verified OAuth transaction for that specific browser`

Instead, the binding that actually holds is only:

`session_id in cookie == deterministic_string(shop [, user_id])`

`Session.from` derives the session `id` purely from the `shop` string (and, for online sessions, the numeric `associated_user.id`), with no random or secret-derived component: [1](#0-0) 

`ShopifyAPI::Auth::Oauth.validate_auth_callback` then uses this predictable `session.id` directly as the value of the browser cookie for non-embedded apps: [2](#0-1) 

The cookie itself (`ShopifyAPI::Auth::Oauth::SessionCookie`) has no signature, MAC, or nonce field — it is a plain `name`/`value`/`expires` struct: [3](#0-2) 

On subsequent requests, `SessionUtils.current_session_id` (and `cookie_session_id`) trusts whatever value is present in this cookie as the lookup key for the merchant's stored session/access token, without any verification that it was actually issued by a validated OAuth flow: [4](#0-3) [5](#0-4) 

Because `"offline_#{shop}"` (and `"#{shop}_#{user_id}"`) is fully computable from public information (the shop's `myshopify.com` domain, and typically low, enumerable Shopify user IDs), an attacker does not need the `api_secret_key`, an access token, or any credential to compute the exact value the host app will treat as an authenticated session key for a specific victim merchant.

### Impact Explanation
This breaks the binding between "a request that completed HMAC-validated OAuth" and "a request the host app treats as an authenticated session," matching the High-impact category of session fixation / forced OAuth completion. If an attacker can get this cookie value written into a victim's browser (e.g., cookie-scope/tossing on a shared parent/sibling domain, a header-injection point in the host app, or any mechanism that lets a third party set a cookie for the app's domain), the host application's session-lookup layer will resolve the request to the victim's stored offline/online session and its access token — cross-tenant session hijacking without ever compromising Shopify credentials.

### Likelihood Explanation
The prerequisite is the ability to write a cookie named `shopify_app_session` into the victim's browser for the app's origin — this is not something the library itself provides, but the library actively removes the only defense (unpredictability/signing) that would make such an injected cookie harmless, since the value the library asks the host app to trust is 100% deterministic from public data. Any app built by following the gem's own documented `oauth.md` / `getting_started.md` flow inherits this weakness verbatim.

### Recommendation
Do not use the raw, deterministic `session.id` as the browser-facing cookie value. Instead, generate a random, unguessable, HMAC-signed cookie value at OAuth completion (e.g., sign `session.id` with `Context.api_secret_key`, or store a random opaque token mapped server-side to the session), and verify that signature/mapping in `SessionUtils.cookie_session_id` before trusting the extracted session id.

### Proof of Concept
1. Victim installs the app on `victim-shop.myshopify.com` (offline access, non-embedded), the merchant domain is discoverable (e.g., from the storefront).
2. Library computes `session.id = "offline_victim-shop.myshopify.com"` per `Session.from` and returns cookie `shopify_app_session=offline_victim-shop.myshopify.com`.
3. Attacker, without any Shopify credential, independently computes the identical string `"offline_victim-shop.myshopify.com"`.
4. Attacker uses any cookie-injection vector against the app's origin (cookie tossing from a related subdomain, response-header injection elsewhere in the host stack, etc.) to set `shopify_app_session=offline_victim-shop.myshopify.com` in a target browser (their own, or a session they control that reaches the app as this shop).
5. The host app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which returns the injected value unchanged, and the app's session repository resolves it to the victim's stored access token — granting the attacker's request the victim merchant's authenticated context.
