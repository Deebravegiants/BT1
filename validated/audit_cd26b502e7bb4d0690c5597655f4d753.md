### Title
OAuth callback sends `client_secret` and constructs the token-exchange host from an unsanitized `shop` parameter - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the POST request that carries the app's `client_secret` to `https://#{auth_query.shop}/admin/oauth/access_token` using `auth_query.shop` directly, without ever passing it through `Utils::ShopValidator.sanitize!`, unlike every sibling OAuth flow in this gem.

### Finding Description
The identity binding that should hold is: *the host that is validated as a trusted Shopify domain* == *the host that receives the app's `client_secret` and access-token request*. In `lib/shopify_api/auth/oauth.rb`, `validate_auth_callback` takes `auth_query.shop`, wraps it in a `null_session = Auth::Session.new(shop: auth_query.shop)` [1](#0-0) , and hands that session straight to `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")`, which sends `client_id`/`client_secret`/`code` to a URL derived from `session.shop` [2](#0-1) . No call to `Utils::ShopValidator.sanitize!` occurs anywhere in this method.

Every other credential-issuing flow in the gem explicitly sanitizes the `shop` value before it is used to build the request host:
- `ClientCredentials.client_credentials` calls `Utils::ShopValidator.sanitize!(shop)` before constructing the session used for the `client_secret` POST [3](#0-2) .
- `RefreshToken.refresh_access_token` does the same [4](#0-3) .
- `TokenExchange.exchange_token` derives `dest_shop` from the validated JWT `dest` claim (a value produced by decoding a token signed with `api_secret_key`, i.e., already trust-anchored) [5](#0-4) .

`Utils::ShopValidator` exists specifically to reject non-Shopify hosts (`TRUSTED_SHOPIFY_DOMAINS` allowlist covering `myshopify.com`, `shopify.com`, `myshopify.io`, `spin.dev`, `shop.dev`) and raises `Errors::InvalidShopError` otherwise [6](#0-5) . The CHANGELOG documents that this exact class of defect (shop domain must be verified as a `.myshopify.com` subdomain before use) was fixed once already, in v4.0.2 — "Verify that the shop domain is a subdomain of .myshopify.com which creating the session" [7](#0-6) , confirming this is a recognized, previously-patched vulnerability class for this gem that is not applied consistently to the `Oauth` callback path.

`Utils::HmacValidator.validate` does cover the `shop` field inside the signed string (`AuthQuery#to_signable_string` includes `shop`) [8](#0-7) [9](#0-8) . However, per the rules of this analysis, defenses that require possession of `api_secret_key` to forge are out of scope, and the report is about the missing *second* binding: nothing in `validate_auth_callback` constrains `auth_query.shop` to `Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS` the way `ClientCredentials`/`RefreshToken` do — the check that other, non-HMAC-validated call sites rely on is simply absent here, leaving the host-selection logic (`auth_base_uri`, and the URL built inside `Clients::HttpClient`) trusting a value whose only defense is a separate, unrelated code path.

### Impact Explanation
If the `shop` value used to build the outbound host for the `client_secret`-bearing access-token request can diverge from a genuine, allowlisted Shopify domain (e.g. through app-level plumbing that forwards a raw `shop` query parameter to `validate_auth_callback` without independent sanitization — the exact integration pattern the gem's own docs and examples show, passing `request.parameters` straight into `AuthQuery.new`), the app's `client_secret` is sent to an attacker-influenced host. This is SSRF with the app's credentials and directly risks `client_secret` exfiltration, matching the "High - SSRF with the app's credentials ... or credential leakage" impact tier.

### Likelihood Explanation
Likelihood is constrained by the fact that a valid HMAC over the query (computed with `api_secret_key`) is still required for `validate_auth_callback` to proceed past the `Utils::HmacValidator.validate` check, which normally requires Shopify itself to have generated the callback for a given `shop`. Because forging that signature requires the secret (explicitly out of scope per the rules), the exploitability of this specific gap independent of the HMAC gate is uncertain and I could not confirm within this codebase a path where an attacker fully controls `shop` while producing a passing HMAC. I flag this as a structural inconsistency/defense-in-depth gap relative to the gem's own established pattern (`ShopValidator.sanitize!` used everywhere else credentials are sent), rather than a fully demonstrated end-to-end bypass.

### Recommendation
Call `Utils::ShopValidator.sanitize!(auth_query.shop)` in `validate_auth_callback` before constructing `null_session`/`auth_base_uri`, mirroring `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`, so the host that receives the `client_secret` is always independently constrained to `Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS` regardless of how HMAC validation is configured or bypassed by an integrator.

### Proof of Concept
Could not be fully constructed within the scope of this analysis: exploitation requires demonstrating a `shop` value whose corresponding HMAC still validates against `Context.api_secret_key` while resolving to a non-Shopify host, which was not verifiable using the in-scope library code alone (this would depend on how the host application sources `auth_query` fields, which is out of scope per the "host application" exclusion rule). No further verification tools are available in this session, so this should be treated as an unconfirmed but code-supported structural gap, not a demonstrated exploit chain.

module ShopifyAPI
  module Utils
    module ShopValidator
      TRUSTED_SHOPIFY_DOMAINS = T.let(
        [
          "shopify.com",
          "myshopify.io",
          "myshopify.com",
          "spin.dev",
          "shop.dev",
        ].freeze,
        T::Array[String],
      )

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
