### Title
Webhook shop identity not bound to HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` fields—read from unauthenticated HTTP headers—are trusted and passed on to the registered webhook handler without being covered by the signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are pulled directly from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) with no cryptographic binding to those header values: [2](#0-1) 

`HmacValidator.validate` only checks the HMAC over `to_signable_string` (i.e., the body): [3](#0-2) 

`Registry.process` validates only this body HMAC, then dispatches to the app's handler using `request.shop` (and `request.topic`/`request.webhook_id`) taken straight from the unauthenticated headers: [4](#0-3) 

The identity binding that should hold is: `shop_that_produced_the_HMAC == shop_delivered_to_handler`. Because the signed bytes (body) are decoupled from the `shop-domain` header, an attacker who legitimately owns Shop A and receives genuine Shopify webhooks for Shop A (with a valid HMAC over that body) can replay the exact same body + HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` header with Shop B's (victim) domain. `HmacValidator.validate` still passes because it never examines the shop header, and `Registry.process` will invoke the app's handler with `WebhookMetadata.new(shop: "shop-b.myshopify.com", ...)` even though the payload was never actually sent by or about Shop B.

### Impact Explanation
This breaks the tenant boundary that host applications rely on: `WebhookMetadata#shop` is the value apps use to key data operations (e.g., look up/update per-shop records, react to `app/uninstalled`, GDPR redact topics, or business events) triggered by webhook delivery. An attacker who owns any shop that installs the app can forge webhook deliveries attributed to any other shop merely by copying a validly-signed body from their own store's webhook traffic and swapping the shop header, since the gem's `HmacValidator` provides no assurance that the claimed shop matches the shop that actually produced the signed bytes. This is a cross-tenant data/identity confusion issue reachable by any unprivileged, unauthenticated internet user with knowledge of one legitimate webhook body+HMAC pair (which any shop owner can trivially obtain by installing the app in their own store).

### Likelihood Explanation
Likelihood is high: any merchant/attacker who can install the target app on their own shop automatically receives legitimately signed webhook deliveries. Replaying the body with a modified `shop-domain` header (and optionally `topic`) is a simple HTTP replay; no secret material, TLS interception, or privileged access is required. The webhook endpoint is by design exposed to the internet.

### Recommendation
Bind the shop (and topic/webhook id, if they influence business logic) into the signed content, or otherwise ensure the trusted request-context values used for tenant identification are not accepted from unauthenticated headers independent of the signed body. At minimum, document/require that host applications cross-check `request.shop` against the tenant expected via `topic`+registration rather than trusting header-only mapping, and consider extending `to_signable_string` to reflect Shopify's authenticated request context.

### Proof of Concept
1. Attacker installs the vulnerable app on their own shop `attacker.myshopify.com` and configures it to receive a webhook (e.g., `orders/create`).
2. Shopify delivers a legitimate webhook to the app: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for `B` with the app's `client_secret`), header `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker captures this request and re-sends it to the same app endpoint, keeping body `B` and `X-Shopify-Hmac-Sha256: H` unchanged but replacing `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes HMAC over `B` only, matches `H`, returns `true`.
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: parsed(B), ...)`, causing the app to act on victim-shop data/state using attacker-controlled body content, despite the request never having originated from or concerning that shop.

          received_signature = verifiable_query.hmac
