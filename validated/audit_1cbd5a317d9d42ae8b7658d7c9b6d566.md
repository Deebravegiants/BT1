### Title
Webhook HMAC only signs the request body, not the `shop-domain` header, allowing shop identity spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook exclusively by checking that the HMAC covers the raw request body. The `shop` field that identifies which tenant/store the webhook belongs to is read directly from an HTTP header and handed to the application handler without ever being covered by, or bound to, that HMAC signature. This is the same class of bug as the analog report: a field ("`shop`") is acted upon by privileged logic (tenant attribution) while not being covered by the authentication check ("HMAC").

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, completely independent of the signed bytes: [2](#0-1) [3](#0-2) 

`Registry.process` validates only the HMAC (which, as shown above, is computed over the body alone) and then immediately forwards `request.shop` to the consumer's handler as the authoritative tenant identifier, with no cross-check that the signed body actually originated from that shop: [4](#0-3) 

The underlying HMAC computation confirms the signable string is the only thing verified — nothing header-derived (topic, shop, webhook id) is part of the signed material: [5](#0-4) 

**Broken identity binding (as an equality):**
`HMAC-verified(raw_body)` is treated as if it implied `shop == request.shop`, but in reality `verified_bytes = raw_body ≠ {raw_body, shop}`. The gem never asserts `hmac_signed_scope ⊇ {shop}`.

**Attack path:** An unprivileged attacker installs the app (or uses any store where the app is already installed, including a free/dev store they control) and configures/triggers a webhook whose body content they can influence (e.g., an `orders/create` payload with attacker-chosen line items, notes, customer fields, etc., or any other topic where some body content is attacker-influenced). Shopify legitimately signs that body with the app's `api_secret_key` and delivers it with headers identifying the attacker's own shop. The attacker intercepts/replays this exact request to the app's webhook endpoint but rewrites the `x-shopify-shop-domain` (or `shopify-shop-domain`) header to the victim's shop domain, leaving the raw body and HMAC untouched. Because `HmacValidator.validate` only recomputes the signature over `raw_body`, verification still succeeds, and `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: request.shop, ...)` pointing at the victim shop while carrying attacker-controlled body content, `request.parsed_body`, at line 198.

### Impact Explanation
This crosses a tenant boundary: data attributed to one shop (the victim) is actually attacker-controlled content that only proves authenticity for a completely different, attacker-owned shop. Any handler logic in the host application that trusts `WebhookMetadata#shop` to scope database writes, cache invalidation, notifications, or session/shop-key lookups can be corrupted with attacker data under a victim shop's identity — a cross-tenant access impact.

### Likelihood Explanation
The attacker only needs a store where the target app is installed (something achievable without any privileged credentials, e.g., a Shopify development or trial store) and the ability to intercept/replay their own webhook HTTP request with one header field modified. No access to `api_secret_key`, tokens, or victim credentials is required, and the gem's public, documented `Registry.process` flow is used exactly as intended by consumers, so the flaw is squarely inside the gem's verification logic, not a misuse of its API.

### Recommendation
Bind the tenant identity into the authenticated material. Options:
- Include the `shop` (and ideally `topic`/`webhook-id`) header values as part of the signable string that `HmacValidator` verifies, so any header tampering invalidates the signature.
- Alternatively, require callers to supply/verify the expected shop domain out-of-band (e.g., compare `request.shop` to a shop already known to be installed via the app's own session store) before trusting `WebhookMetadata#shop` for any tenant-scoped operation, and document this requirement clearly since the gem currently implies the header is already authenticated.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker.myshopify.com"
# and receives (or crafts, since content is attacker-influenced) a
# legitimately Shopify-signed webhook delivery:
raw_body = '{"id":1,"note":"payload attacker controls"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_secret, raw_body)

headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),   # still valid: signature only covers raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # tampered, header not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => passes HmacValidator.validate (signature matches raw_body)
# => handler invoked with WebhookMetadata(shop: "victim-shop.myshopify.com", body: attacker-controlled)
```
