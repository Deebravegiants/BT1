I have enough evidence to write up the finding now.### Title
Webhook shop/topic identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` trusts the `shop`, `topic`, and `webhook_id` values taken directly from unauthenticated HTTP headers when dispatching webhook data to app handlers, while the HMAC signature verified by `Utils::HmacValidator.validate` only covers the raw request body. This breaks the identity binding `signed_bytes == authenticated_shop`, allowing any party who possesses one validly-signed webhook body/HMAC pair (e.g., from their own store's legitimate installation) to relabel it as belonging to a different shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

and `shop`, `topic`, and `webhook_id` are read straight from headers with no cryptographic binding to that body: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC purely over `verifiable_query.to_signable_string`, i.e. the raw body only: [3](#0-2) 

`Registry.process` validates the HMAC, then immediately trusts `request.shop` and `request.topic` (unauthenticated headers) to build the metadata passed to the app's handler: [4](#0-3) 

This is inconsistent with how the gem handles the analogous OAuth callback, where `shop` **is** cryptographically bound into the signed string alongside `code`, `host`, `state`, and `timestamp`: [5](#0-4) 

Because the webhook `shop` header is excluded from the signed payload, the equality the app relies on for tenant isolation — "the shop that produced this signature" == "the shop this data will be attributed to" — does not hold. Anyone who can obtain one legitimately-signed `(raw_body, hmac)` pair from Shopify (trivially available to any merchant who installs the target app, even via a free/dev store) can replay that exact body and HMAC to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header. `HmacValidator.validate` will still pass because it only checks the body bytes, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload belongs to the attacker-chosen shop/topic.

### Impact Explanation
This is a cross-tenant data-integrity/confusion vulnerability: an attacker who legitimately installs the app on their own (possibly free/trial) store can forge webhook deliveries that the host application will process as if they came from a different, victim shop. Any app logic keyed on `WebhookMetadata#shop` (e.g., updating per-shop billing state, triggering per-shop side effects, `shop/redact`/`customers/redact` compliance handling, cache invalidation, provisioning) can be manipulated to act on the wrong tenant, since the library provides no guarantee that the `shop` field is authentic. This matches the "cross-tenant access" impact category, as the identity boundary between tenants is not enforced by the primitive the library exposes for this exact purpose (`HmacValidator.validate` on webhook requests).

### Likelihood Explanation
High. Any entity that can install the target Shopify app on a store (a routine, low-privilege action available to anyone with a Shopify Partner account) receives real, validly-signed webhooks for that store. The webhook endpoint is a public, unauthenticated HTTP endpoint by design (Shopify calls it directly), so replaying a captured body with modified headers requires no secret material — only observation of one legitimate delivery.

### Recommendation
Bind the shop (and ideally topic/webhook-id) identity into the value verified by the HMAC, or otherwise cryptographically/independently authenticate the `shop` header before trusting it for dispatch — e.g., derive/verify `shop` from a mechanism outside attacker control per delivery (Shopify's official guidance/newer schemes provide additional headers/anti-replay data), or require the app-level handler to cross-check `webhook_id`/`shop` against records obtained via an authenticated, out-of-band channel rather than trusting the header verbatim. At minimum, document explicitly that `request.shop`/`request.topic` are unauthenticated and must not be trusted as a tenant boundary without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` (or any dev/trial store).
2. Shopify sends a legitimate webhook to the app's public endpoint, e.g. body `{}` for topic `orders/create`, with headers:
   - `X-Shopify-Topic: orders/create`
   - `X-Shopify-Hmac-Sha256: <valid HMAC of body>`
   - `X-Shopify-Shop-Domain: attacker.myshopify.com`
3. Attacker captures the raw body and the `X-Shopify-Hmac-Sha256` value (no secret needed — this is just a network capture of a request delivered to infrastructure the attacker controls).
4. Attacker POSTs the identical body + identical `X-Shopify-Hmac-Sha256` to the same endpoint, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate` (called in `Registry.process`, `lib/shopify_api/webhooks/registry.rb:190`) recomputes the HMAC over `to_signable_string` (the raw body only) and it matches, so validation succeeds.
6. `Registry.process` invokes the app's handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: {...}, ...)`, causing the host application to act as if the event originated from `victim-shop.myshopify.com`.
