### Title
Webhook `shop` claimed by an unauthenticated header field, not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#shop` derives the tenant identity for an incoming webhook purely from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC verification computed via `to_signable_string` only ever covers the raw request body. An attacker who can reach the webhook endpoint can freely set `X-Shopify-Shop-Domain` to any value while keeping a valid `hmac-sha256`/body pair (e.g. replaying/forwarding a genuine webhook payload signed with the same `client_secret`, or, more generally, any consumer whose HMAC check design does not additionally re-bind the header), causing the host application to attribute the payload to an arbitrary shop.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are the two methods that `Utils::HmacValidator.validate` uses to authenticate a webhook: [1](#0-0) [2](#0-1) 

`to_signable_string` returns only `@raw_body`; it does not fold in `shop`, `topic`, `webhook_id`, or `api_version`. Yet `Request#shop`, the field host applications are expected to use to key their per-tenant `Session`/data lookups, is read straight from the `shopify-shop-domain` header with no cross-check against the signed body: [3](#0-2) 

`Utils::HmacValidator.validate` (and `validate_signature`) only proves that `OpenSSL::HMAC.hexdigest(secret, @raw_body)` matches the received `hmac-sha256` header — it says nothing about which shop sent it: [4](#0-3) 

The binding that should hold is:
`shop-claimed-by-header == shop-that-produced-the-HMAC-signed-bytes`

But the actual binding enforced is only:
`hmac-header == HMAC(secret, raw_body)`

These are not equivalent. Because the `shop-domain` header sits entirely outside the signed material, any request carrying a validly-HMAC'd body (which an attacker can obtain, e.g., by triggering/replaying an event for their own trial/dev shop, since `client_secret` is shared across all shops installing the same app) can be resent with a different `X-Shopify-Shop-Domain` header value, and `HmacValidator.validate` will still return `true`. This exactly mirrors the smart-contract analog's flaw of acting on a field (`newShare`) that isn't covered by the same integrity check as the rest of the state transition — here `shop` is acted upon (tenant routing) without being covered by the same HMAC that gates trust in the request.

### Impact Explanation
If a host application follows the gem's documented pattern of using `Webhooks::Request#shop` (after `HmacValidator.validate` returns true) to decide which merchant's session/data the webhook payload applies to, an attacker can cause a genuinely-signed webhook body to be attributed to a different, arbitrary shop domain. This is a cross-tenant integrity/confusion issue: data or side effects intended for shop A can be misdirected to be processed as if they belong to shop B, without possessing shop B's credentials — this maps to the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation only requires network access to the app's public webhook endpoint and one legitimately-signed webhook body (any shop, including the attacker's own free/dev store, generates such bodies since the same `client_secret` is used for the app across all installs). No token, credential, or privileged account is needed — only the ability to replay a POST with a modified header, which is a capability of any unprivileged internet user able to reach the endpoint.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the signed material used to authenticate webhooks, or otherwise cryptographically bind the header-derived `shop` to the verified payload rather than trusting the header independently of the HMAC check. At minimum, document that `Request#shop` is unauthenticated and must not be trusted for tenant routing decisions unless it is independently corroborated.

### Proof of Concept
1. Attacker's own shop (or any shop where the app is installed) triggers a webhook, producing `raw_body` and a valid `X-Shopify-Hmac-Sha256` header signed with the shared `client_secret`.
2. Attacker intercepts/replays this request to the app's webhook endpoint, changing only the `X-Shopify-Shop-Domain` header to `victim-shop.myshopify.com` (leaving `raw_body` and `hmac-sha256` untouched).
3. The app calls:
```ruby
request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Utils::HmacValidator.validate(request) # => true, since to_signable_string only checks @raw_body
request.shop # => "victim-shop.myshopify.com" (attacker-controlled)
```
4. The host application, trusting `request.shop` after a passing HMAC check, processes/stores the payload under `victim-shop.myshopify.com`'s session/data context, achieving cross-tenant data confusion.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
