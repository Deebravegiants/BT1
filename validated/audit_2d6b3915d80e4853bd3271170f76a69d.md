### Title
Unbounded `account_ids` / `keys` lists in `changes` (`EXPERIMENTAL_changes`) and related state-changes RPC methods enable RPC DoS - (File: chain/jsonrpc/src/lib.rs)

### Summary
The `changes`/`EXPERIMENTAL_changes` JSON-RPC method (and its sharded variants `block_effects`/`EXPERIMENTAL_changes_in_block`) accepts a `StateChangesRequestView` whose `account_ids` (or `keys`, for `SingleAccessKeyChanges`) field is an arbitrary-length `Vec<AccountId>`/`Vec<AccessKeyInfoView>` with no upper bound, analogous to the unbounded `FilterCriteria.Addresses` field in the reported minievm `eth_getLogs` issue.

### Finding Description
`process_basic_requests_internal` routes `"changes" | "EXPERIMENTAL_changes"` to `changes_in_block_by_type_sharded`, which deserializes the request straight into `RpcStateChangesInBlockByTypeRequest { state_changes_request: StateChangesRequestView, .. }` with no cap on the size of `account_ids`/`keys` [1](#0-0) .

The coordinator path then performs O(n) work directly proportional to the number of supplied account ids/keys for every single request, before any authentication or shard-availability check limits the cost:
- `extract_target_shards` maps every account id (or every key's account id) to a shard id [2](#0-1) .
- `filter_request_to_shard_group` re-iterates the full list again per shard group to build the sub-request sent to each shard-owning node [3](#0-2) .
- The local (non-sharded) handler `changes_in_block_by_type` forwards the entire unbounded `state_changes_request` to `ViewClientActor` via `GetStateChanges`, which performs a store lookup per account/key against the state-changes column for the block [4](#0-3) .

Unlike `eth_getLogs`'s `Topics`, which is explicitly capped (`maxTopics`), there is no analogous cap anywhere in nearcore's `RpcStateChangesRequest`/`StateChangesRequestView` parsing. The only mitigating control is the generic HTTP body-size limit, `RpcLimitsConfig::json_payload_max_size`, defaulting to 10MB, enforced by `RequestBodyLimitLayer` [5](#0-4) [6](#0-5) .

Because `AccountId`s are far shorter than Ethereum addresses (up to 64 bytes vs. a fixed 20-byte address, but typically much shorter in practice, e.g. `"a".repeat(2)+"..."`), an attacker can pack on the order of 10⁵–10⁶ account ids into a single 10MB request body, exactly mirroring the minievm PoC's arithmetic for the number of addresses fitting into a bounded body.

### Impact Explanation
An unauthenticated RPC client can submit a single `changes`/`EXPERIMENTAL_changes` (or `block_effects`) request containing hundreds of thousands of account ids. Each element triggers: (1) a `HashMap`/shard-layout lookup in `extract_target_shards`, (2) a second full-list filter pass per shard group in `filter_request_to_shard_group` when running in sharded mode, and (3) (in the non-sharded path) a state-changes store lookup per account id via `GetStateChanges`. Repeated concurrent requests of this shape can consume significant CPU/IO on the RPC-serving node(s), degrading or halting RPC service for legitimate users — a direct availability impact matching the "chain stall" / "unbounded resource use" class called out in the validation criteria. This does not affect chain consensus, but it does affect the RPC node's availability, which is the same class of impact confirmed as valid ("Medium/High" DoS) in the referenced report.

### Likelihood Explanation
Likelihood is high: the endpoint requires no authentication or special privilege, is reachable by any client capable of sending an HTTP POST to the public JSON-RPC port (default `0.0.0.0:3030`), and the only limiting factor is the generic 10MB body-size cap, which — per the referenced report's own arithmetic — is not sufficient to prevent the attack. No special network position or validator status is required.

### Recommendation
Add an explicit, low upper bound on the number of elements accepted in `StateChangesRequestView::AccountChanges`/`AllAccessKeyChanges`/`ContractCodeChanges`/`DataChanges` (`account_ids`) and `SingleAccessKeyChanges` (`keys`), similar to how other size-bounded RPC inputs are validated, and reject/`RequestValidationError` requests exceeding it before any shard-lookup or store-query work is performed in `changes_in_block_by_type_sharded` / `changes_in_block_by_type`.

### Proof of Concept
Send a single JSON-RPC request:
```json
{
  "jsonrpc": "2.0",
  "id": "dontcare",
  "method": "EXPERIMENTAL_changes",
  "params": {
    "block_id": "<recent-block-hash>",
    "changes_type": "account_changes",
    "account_ids": ["a0.near", "a1.near", ... /* hundreds of thousands of entries, staying under json_payload_max_size (10MB) */]
  }
}
```
This is parsed without any size validation by `process_basic_requests_internal` → `changes_in_block_by_type_sharded` [1](#0-0) , and each account id is iterated multiple times in `extract_target_shards`/`filter_request_to_shard_group` and against the state-changes store, mirroring the reported `eth_getLogs` `Addresses` DoS vector.

fn filter_request_to_shard_group(
    request: &StateChangesRequestView,
    shard_group: &[ShardId],
    shard_layout: &ShardLayout,
) -> StateChangesRequestView {
    let shard_set: HashSet<&ShardId> = shard_group.iter().collect();
    let filter_accounts = |account_ids: &[AccountId]| -> Vec<AccountId> {
        account_ids
            .iter()
            .filter(|id| shard_set.contains(&shard_layout.account_id_to_shard_id(id)))
            .cloned()
            .collect()
    };

    match request {
        StateChangesRequestView::AccountChanges { account_ids } => {
            StateChangesRequestView::AccountChanges { account_ids: filter_accounts(account_ids) }
        }
        StateChangesRequestView::SingleAccessKeyChanges { keys } => {
            let filtered: Vec<_> = keys
                .iter()
                .filter(|k| shard_set.contains(&shard_layout.account_id_to_shard_id(&k.account_id)))
                .cloned()
                .collect();
            StateChangesRequestView::SingleAccessKeyChanges { keys: filtered }
        }
        StateChangesRequestView::AllAccessKeyChanges { account_ids } => {
            StateChangesRequestView::AllAccessKeyChanges {
                account_ids: filter_accounts(account_ids),
            }
        }
        StateChangesRequestView::ContractCodeChanges { account_ids } => {
            StateChangesRequestView::ContractCodeChanges {
                account_ids: filter_accounts(account_ids),
            }
        }
        StateChangesRequestView::DataChanges { account_ids, key_prefix } => {
            StateChangesRequestView::DataChanges {
                account_ids: filter_accounts(account_ids),
                key_prefix: key_prefix.clone(),
            }
        }
    }

fn extract_target_shards(
    request: &StateChangesRequestView,
    shard_layout: &ShardLayout,
) -> HashSet<ShardId> {
    let account_ids: &[AccountId] = match request {
        StateChangesRequestView::AccountChanges { account_ids } => account_ids,
        StateChangesRequestView::SingleAccessKeyChanges { keys } => {
            return keys
                .iter()
                .map(|k| shard_layout.account_id_to_shard_id(&k.account_id))
                .collect();
        }
        StateChangesRequestView::AllAccessKeyChanges { account_ids } => account_ids,
        StateChangesRequestView::ContractCodeChanges { account_ids } => account_ids,
        StateChangesRequestView::DataChanges { account_ids, .. } => account_ids,
    };
    account_ids.iter().map(|id| shard_layout.account_id_to_shard_id(id)).collect()
}

    async fn changes_in_block_by_type(
        &self,
        request: RpcStateChangesInBlockByTypeRequest,
        source: RequestSource,
    ) -> Result<RpcStateChangesInBlockResponse, RpcStateChangesError> {
        let block: near_primitives::views::BlockView =
            self.view_client_send(GetBlock(request.block_reference)).await?;

        let block_hash = block.header.hash;

        if source == RequestSource::Coordinator {
            let epoch_id = EpochId(block.header.epoch_id);
            let shard_layout =
                self.shard_layout_for_epoch(&epoch_id).map_err(to_state_changes_internal)?;
            let required: Vec<ShardUId> =
                extract_target_shards(&request.state_changes_request, &shard_layout)
                    .into_iter()
                    .map(|shard_id| ShardUId::from_shard_id_and_layout(shard_id, &shard_layout))
                    .collect();
            if !required.is_empty() {
                self.ensure_chunks_applied(&block_hash, &required).await?;
            }
        }

        let changes = self
            .view_client_send(GetStateChanges {
                block_hash,
                state_changes_request: request.state_changes_request,
            })
            .await?;

        Ok(RpcStateChangesInBlockResponse { block_hash: block.header.hash, changes })
    }
