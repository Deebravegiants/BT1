Audit Report

## Title
JWT replay-protection check-then-act race in `WorkflowMetadataHandler.Authorize` allows a single-use JWT to authorize more than one workflow execution - (File: `core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go`)

## Summary
`WorkflowMetadataHandler.Authorize` performs the JWT anti-replay "check" (`isReplay`) and "record" (`recordUsage`) as two independently-locked, non-atomic operations, with unrelated work (`authorizedKeys` lookup, signer comparison) executed in between. This is a genuine TOCTOU bug: two concurrent `workflows.execute` HTTP trigger requests carrying the same signed JWT can both pass the `isReplay` check before either calls `recordUsage`, defeating the single-use guarantee of the JWT.

## Finding Description
`Authorize` is reachable directly from an unprivileged external caller via `httpTriggerHandler.HandleUserTriggerRequest` → `authorizeRequest` → `WorkflowMetadataHandler.Authorize`: <cite repo="AYontt/chainlink--018" path="core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go" start="368-376" /> Inside `Authorize`, the replay check is done early via `h.jwtCache.isReplay(claims.ID)`, and the corresponding write, `h.jwtCache.recordUsage(claims.ID)`, only occurs after the `authorizedKeys` map lookup and signer-key comparison: [1](#0-0)  The two cache operations use two separate locks (`RLock`/`RUnlock` for the check, a later independent `Lock`/`Unlock` for the write) with no atomic "check-and-set" primitive spanning them: [2](#0-1)  This confirms the claimed root cause: nothing prevents two concurrent goroutines from both observing `isReplay(jti) == false` before either records usage.

The downstream `setupCallback` dedupe operates on `requestID`, not on JWT `jti`: [3](#0-2)  so an attacker supplying distinct `requestID`s while reusing the same JWT is not blocked by that separate check, meaning the JWT-level race is not otherwise absorbed.

## Impact Explanation
This breaks the intended one-time-use contract of a JWT-authorized `workflows.execute` trigger. A holder of one previously-issued, still-valid JWT can, by racing two (or more) concurrent requests with distinct `requestID`s, cause the same JWT to authorize multiple independent workflow executions instead of exactly one. This maps to the in-scope "unauthorized job run" impact category for gateway request handling, since it lets a caller trigger extra job/workflow executions beyond what the single-use JWT was meant to permit, with associated rate-limit/cost implications not intended by the token issuer.

## Likelihood Explanation
The exploit requires only possession of one valid JWT (the normal credential needed to use this endpoint at all — no privilege escalation beyond what a legitimate caller already has) and the ability to fire two or more concurrent HTTP requests carrying it, which is trivial for any external client. The race window between `isReplay` and `recordUsage` spans an in-memory map lookup and string comparison — narrow, but real and non-theoretical, and increases in practice with client retry/duplicate-submission behavior common at gateways. This is a legitimate, reproducible TOCTOU condition rather than a purely speculative scenario.

## Recommendation
Make the check-and-record operation atomic under a single lock (e.g., replace `isReplay`/`recordUsage` with one `checkAndRecord(jti) bool` method holding a write lock across both the presence check and the insert), and invoke it immediately after JWT verification, before any other authorization logic (authorizedKeys lookup, signer comparison) executes.

## Proof of Concept
1. Obtain one valid, signed JWT (`jti` fixed) for an authorized `workflows.execute` request.
2. Concurrently fire two `HandleUserTriggerRequest` calls (e.g., via `httptest` against the gateway's HTTP trigger endpoint) using the same JWT in `req.Auth` but distinct `requestID`s.
3. A Go unit test directly exercising `jwtReplayCache` with two goroutines racing `isReplay` (both observing `false`) then both calling `recordUsage` demonstrates the non-atomic check-then-act window; an integration-level test on `WorkflowMetadataHandler.Authorize` with two concurrent calls using the same `claims.ID` shows both returning a non-error `*gateway.AuthorizedKey`, proving the JWT was accepted twice.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}
