### Title
Legacy `CoinStore::frozen` flag desynchronized from paired `FungibleStore` frozen flag, allowing frozen-account transfers to bypass freeze control - (File: `aptos-move/framework/aptos-framework/sources/coin.move`)

### Summary
`coin.move` maintains two independent custody-authority signals for the same logical balance once a `CoinType` is paired with a Fungible Asset: the legacy `CoinStore<CoinType>.frozen` flag and the `FungibleStore.frozen` flag on the paired primary store. `freeze_coin_store` / `unfreeze_coin_store` [1](#0-0)  update only the legacy `CoinStore.frozen` field via `FreezeCapability`, while balance and transfer operations after migration are serviced through `primary_fungible_store`/`fungible_asset`, whose withdraw/deposit authority is governed exclusively by `FungibleStore.frozen` [2](#0-1) . The only place these two flags are reconciled is `maybe_convert_to_fungible_store`, which syncs `frozen` at the moment of CoinStore→FungibleStore migration [3](#0-2) .

### Finding Description
This mirrors the external bug's shape: a security-relevant check ("is this frozen / stale?") is validated for one of two parallel state sources but not the other, and code that merges/derives from both proceeds using only the checked one. Here, once an account has already migrated to (or created) a primary fungible store, calling `freeze_coin_store<CoinType>` only sets `CoinStore.frozen = true`; it does not call into `fungible_asset::set_frozen_flag_internal` for the paired `FungibleStore`. Since `coin::balance` and `coin::withdraw`/transfer flows funnel real value movement through `primary_fungible_store`, which checks only `FungibleStore.frozen` [4](#0-3) , an account whose `CoinStore` is frozen via the legacy capability-holder path can still move funds held in its paired fungible store.

### Impact Explanation
If confirmed, this would let a "frozen" account continue to withdraw/transfer/receive assets recorded as custody-controlled (frozen) by a `FreezeCapability` holder, defeating freeze-based custody control for value already resident in (or later deposited/migrated into) the primary fungible store — a broken custody invariant (freeze control) rather than mere accounting noise.

### Likelihood Explanation
Likelihood depends on the exact call ordering: `maybe_convert_to_fungible_store` does synchronize `frozen` at migration time, so the desync would only be exploitable if (a) the fungible store is created independently of `CoinStore` migration (e.g., direct FA deposit) after `CoinStore` was frozen, or (b) `freeze_coin_store` is called on an account whose `CoinStore` no longer exists / has already been migrated, or (c) new deposits land in the FungibleStore after the CoinStore freeze without triggering `maybe_convert_to_fungible_store` again. I was **not able to fully trace all call sites and orderings within the remaining tool budget** to confirm whether `freeze_coin_store` is reachable at all once migration has occurred, or whether all paths force re-sync. This is the key uncertainty.

### Recommendation
Have `freeze_coin_store`/`unfreeze_coin_store` also update the paired `FungibleStore.frozen` flag (via the stored `PairedFungibleAssetRefs.transfer_ref_opt`) whenever a paired fungible asset/primary store exists, so both custody signals stay synchronized regardless of migration timing.

### Proof of Concept
Not independently constructed/verified — would require: (1) initializing a `CoinType` with freeze capability, (2) causing/creating a primary fungible store for an account (via `coin_to_fungible_asset` + `primary_fungible_store::deposit`, or direct FA deposit) without going through `maybe_convert_to_fungible_store`, (3) calling `freeze_coin_store` on that account, and (4) attempting `primary_fungible_store::transfer`/`withdraw` on that account's FA balance to see if it still succeeds despite the "frozen" `CoinStore`.

**Caveat / uncertainty**: I could not fully verify within the available investigation whether all realistic call paths force `CoinStore` and `FungibleStore` frozen states to stay synchronized (e.g., whether `freeze_coin_store` even remains callable/relevant post-migration in practice, or whether other guards prevent the divergent state from being reached). This candidate should be treated as a lead requiring further tracing of `CoinStore` lifecycle and all `frozen`-flag write sites before being treated as a confirmed, high-confidence finding.

    fun maybe_convert_to_fungible_store<CoinType>(
        account: address
    ) acquires CoinStore, CoinConversionMap, CoinInfo {
        if (exists<CoinStore<CoinType>>(account)) {
            let CoinStore<CoinType> { coin, frozen, deposit_events, withdraw_events } =
                move_from<CoinStore<CoinType>>(account);
            if (is_coin_initialized<CoinType>() && coin.value > 0) {
                let metadata = ensure_paired_metadata<CoinType>();
                let store =
                    primary_fungible_store::ensure_primary_store_exists(
                        account, metadata
                    );

                event::emit(
                    CoinStoreDeletion {
                        coin_type: type_info::type_name<CoinType>(),
                        event_handle_creation_address: guid::creator_address(
                            event::guid(&deposit_events)
                        ),
                        deleted_deposit_event_handle_creation_number: guid::creation_num(
                            event::guid(&deposit_events)
                        ),
                        deleted_withdraw_event_handle_creation_number: guid::creation_num(
                            event::guid(&withdraw_events)
                        )
                    }
                );

                if (coin.value == 0) {
                    destroy_zero(coin);
                } else {
                    fungible_asset::unchecked_deposit_with_no_events(
                        store.object_address(),
                        coin_to_fungible_asset(coin)
                    );
                };

                // Note:
                // It is possible the primary fungible store may already exist before this function call.
                // In this case, if the account owns a frozen CoinStore and an unfrozen primary fungible store, this
                // function would convert and deposit the rest coin into the primary store and freeze it to make the
                // `frozen` semantic as consistent as possible.
                if (frozen != fungible_asset::is_frozen(store)) {
                    fungible_asset::set_frozen_flag_internal(store, frozen);
                }
            } else {
                destroy_zero(coin);
            };
            event::destroy_handle(deposit_events);
            event::destroy_handle(withdraw_events);
        };

    #[legacy_entry_fun]
    /// Freeze a CoinStore to prevent transfers
    public entry fun freeze_coin_store<CoinType>(
        account_addr: address, _freeze_cap: &FreezeCapability<CoinType>
    ) acquires CoinStore {
        let coin_store = borrow_global_mut<CoinStore<CoinType>>(account_addr);
        coin_store.frozen = true;
    }

    #[legacy_entry_fun]
    /// Unfreeze a CoinStore to allow transfers
    public entry fun unfreeze_coin_store<CoinType>(
        account_addr: address, _freeze_cap: &FreezeCapability<CoinType>
    ) acquires CoinStore {
        let coin_store = borrow_global_mut<CoinStore<CoinType>>(account_addr);
        coin_store.frozen = false;
    }
