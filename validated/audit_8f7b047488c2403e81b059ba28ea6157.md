### Title
Webhook shop-domain identity is not covered by the HMAC signature, permitting cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authentic for whatever shop domain is present in the `X-Shopify-Shop-Domain` header, but the HMAC signature computed by `HmacValidator` only ever covers the raw request body, never the shop-domain header. This breaks the identity binding: `hmac_valid(body) == true` is treated as proof that `request.shop == "the shop the payload actually originated from"`, when in fact the HMAC only proves the body was produced by an app owning the shared `client_secret`, not that a specific header value is authentic.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string`, i.e. the raw body, using the app's `Context.api_secret_key`: [2](#0-1) 

`Registry.process` uses this HMAC check as the sole authenticity gate, then constructs `WebhookMetadata` using `request.shop`, which is parsed directly from the (unauthenticated) `shopify-shop-domain` / `x-shopify-shop-domain` header: [3](#0-2) [4](#0-3) 

Because Shopify signs webhook bodies with a single `client_secret` shared across all shops installed on the app (not a per-shop key), any unprivileged internet user who installs the app on a shop they control (e.g., a free development store) will receive genuine webhook deliveries with a valid HMAC for that body. That attacker can then replay the exact body+HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (it never inspects the header), so `Registry.process` invokes the app's handler with `WebhookMetadata.shop` set to the spoofed victim domain — an equality that should hold (`authenticated_shop == acted_on_shop`) is broken because the acted-on field (`shop`) is never part of the signed material.

### Impact Explanation
This is a cross-tenant identity-binding failure: a webhook payload/action can be attributed to an arbitrary shop domain that the attacker does not control and never proved ownership of via the signature. Any host application that uses `data.shop` from `WebhookMetadata` to select which tenant's records to create/update/delete (the exact pattern shown in the gem's own docs, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) can be made to write, delete, or otherwise mutate another merchant's data using content the attacker fully controls (their own shop's webhook body, e.g. `orders/create`, `app/uninstalled`, `shop/redact`, etc.), or to trigger deletion/redaction flows against a victim shop. This satisfies the "cross-tenant access" Critical impact criterion.

### Likelihood Explanation
Requires only that the attacker be able to install the app on any shop (including a free/dev store they control) to receive at least one legitimately-signed webhook body, and be able to send an HTTP request to the app's public webhook endpoint with a forged header — no access token, secret key, or privileged account is needed. This is fully reachable by an unprivileged internet user and requires no race condition or timing window, making it a reliably exploitable path rather than a theoretical one.

### Recommendation
Include the shop-domain (and ideally topic/webhook-id) in the material that is cryptographically bound to the request, or require host applications to cross-check the header shop against a list of shops that currently have this webhook subscription/session recorded, and document this requirement prominently. At minimum, `Utils::HmacValidator`/`Webhooks::Request` should not present `request.shop` as a trusted, verified identity to `WebhookMetadata` without it being covered by the signature — the gem should either verify shop domain via a separate authenticated channel (e.g., only accept domains for which a stored session/webhook registration exists) or clearly flag in `WebhookMetadata` that `shop` is unauthenticated header data requiring the caller to independently verify tenant ownership before acting on it.

### Proof of Concept
1. Attacker creates/owns `attacker-shop.myshopify.com`, installs the victim's app there, and triggers a webhook (e.g. `orders/create`). Shopify delivers a POST with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(client_secret, B)` — a fully valid, real signature for that body.
2. Attacker resends the identical body `B` and identical HMAC header to the same app's webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` parses `shop` as `victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(client_secret, B)` — identical to the header value — and returns `true`, per [5](#0-4) .
5. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: attacker-controlled JSON, ...)`, per [6](#0-5) , causing the host application to act on the victim tenant using attacker-controlled data.
