### Title
Webhook `shop` domain is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so the HMAC that `Registry.process` validates covers the payload bytes but never binds the `shop` (or `topic`/`webhook_id`) header that the app uses to identify which tenant the webhook belongs to. An attacker who can obtain any single validly-signed webhook (e.g., by installing the app on their own store) can replay that exact body+HMAC pair while substituting an arbitrary `X-Shopify-Shop-Domain` header, and the gem will accept it as an authentic webhook "from" the victim shop.

### Finding Description
`Request#hmac` is derived from the `hmac-sha256` header and `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

```ruby
def hmac
  Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
end
...
def to_signable_string
  @raw_body
end
```

The `shop` value comes straight from an unauthenticated header: [2](#0-1) 

`Registry.process` validates the request purely through `Utils::HmacValidator.validate(request)`, which — per `HmacValidator#validate_signature` — recomputes the HMAC only over `verifiable_query.to_signable_string` (i.e., the raw body) and compares it to the `hmac` header: [3](#0-2) [4](#0-3) 

The `shop` (and `topic`, `webhook_id`) fields are never part of the signed content, yet `Registry.process` forwards `request.shop` unchecked into `WebhookMetadata`, which is the value app handlers use to know which merchant/tenant the event is for:
```ruby
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
  body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
``` [5](#0-4) 

**Identity binding broken (equality that should hold but doesn't):**
`hmac-signed bytes == bytes the app trusts for tenant identity`. In reality, `hmac == HMAC(raw_body)` while `tenant identity == header["shop-domain"]`, a field entirely outside the signed payload. An attacker never needs `api_secret_key`: any legitimate webhook delivery received by the attacker's own store (a store they control) already carries a valid HMAC for that body. Swapping only the `shop-domain` header before feeding it to `Webhooks::Request.new` still passes `HmacValidator.validate`, because the header is not part of `to_signable_string`.

### Impact Explanation
`Registry.process` is the gem's sanctioned entry point for verifying and dispatching inbound webhooks; it is the security boundary host apps rely on to trust `WebhookMetadata#shop`. Since that field is unauthenticated, an attacker can make a legitimately-signed webhook request appear to originate from an arbitrary victim shop domain, causing the host application's handler logic (which typically loads a session/tenant record keyed by `data.shop`) to act on/for the wrong tenant — a cross-tenant confusion condition.

### Likelihood Explanation
Exploitation requires no secret key, tokens, or privileged access — only receipt of one validly-signed webhook, obtainable by installing/operating the attacker's own (unprivileged) Shopify development store and capturing any webhook delivery. The header can then be freely altered by any actor who can post to the app's webhook endpoint, since `Registry.process` does not reject bodies whose `shop` header differs from what was actually signed.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or otherwise cryptographically bind the shop domain) into the value that is HMAC-verified, or independently re-validate `request.shop` against a shop known to have originated the specific signed payload (e.g., verify against the known/allow-listed shop for the app installation before dispatching to the handler), rather than trusting the raw header.

### Proof of Concept
1. Install the app (or otherwise receive webhooks) on attacker-controlled store `attacker.myshopify.com`; capture a legitimate delivery: raw body `B`, and header `X-Shopify-Hmac-Sha256: H` (valid because Shopify signed `B` with the app's secret).
2. Replay the request to the app's webhook endpoint, keeping body `B` and header `X-Shopify-Hmac-Sha256: H` unchanged, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`= B`) and matches `H` — validation succeeds.
4. `request.shop` returns `"victim.myshopify.com"` (attacker-controlled header), and `WebhookMetadata.new(shop: request.shop, ...)` is passed to the app's handler, which now processes attacker-crafted data as if it belonged to the victim tenant.
