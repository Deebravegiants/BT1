Based on my research, I found a genuine Aptos-native analog to the EIP712 encoding-ambiguity bug class: **unprefixed, non-length-delimited concatenation of variable-length strings used as deterministic Move object-address seeds** for Digital Asset (Token Objects) collections and tokens.

### Title
Ambiguous, non-length-prefixed concatenation of `collection` and `name` in `token::create_token_seed` allows deterministic NFT/collection object-address collisions — ([File: aptos-move/framework/aptos-token-objects/sources/token.move])

### Summary
The EIP712 bug's root cause is that a dynamic-length field was concatenated into a digest without an unambiguous, length-preserving encoding (hash-of-contents), so two different logical inputs could produce the same encoded bytes. The Aptos analog is `create_token_seed` in `token.move`, which builds the deterministic seed used to derive a token's object address by naively concatenating `collection` bytes, a fixed `"::"` separator, and `name` bytes — with no length prefix on either string: [1](#0-0) 

This seed is fed straight into `object::create_object_address`, which just does `sha3_256(creator || seed || 0xFE)` with no additional structure: [2](#0-1) 

Since `"::"` is just two literal bytes and neither `collection` nor `name` is length-prefixed, two different `(collection, name)` pairs can serialize to the identical seed byte string, e.g.:
- `(collection="A::B", name="C")` → `"A::B" + "::" + "C"` = `"A::B::C"`
- `(collection="A", name="B::C")` → `"A" + "::" + "B::C"` = `"A::B::C"`

Both yield the exact same seed and, under the same creator address, the exact same object address. The same unprefixed-concatenation pattern (mirrored on the off-chain/Rust side) is used for both collections and tokens under one shared address-derivation scheme (`OBJECT_FROM_SEED_ADDRESS_SCHEME = 0xFE`), so a maliciously-named **collection** (e.g. named `"VictimCollection::VictimToken"`) can be crafted to land on the exact same address as a **token** legitimately named `"VictimToken"` inside a real `"VictimCollection"` collection — the two object types share the same seed→address function with no type-domain separation beyond the string contents themselves: [3](#0-2) 

### Finding Description
`object::create_named_object` derives a "named object" address purely from `sha3_256(creator_addr || seed || 0xFE)` and aborts if an `ObjectCore` already exists at that address: [4](#0-3) 

Both `Collection` and `Token` objects reuse this exact same function/scheme, differentiated only by the *content* of the seed they pass in (raw collection-name bytes vs. `collection || "::" || name`). Because the concatenation is not self-describing (no length prefixes, and `"::"` can itself appear inside either operand), the byte-level boundary between `collection` and `name` is not unique. This is structurally identical to the EIP712 bug: a dynamic field's boundary information is lost during concatenation, so distinct logical structures collapse onto the same digest/address.

The practical exploitation path requires that a single "creator" address (the signer passed into `create_named_object`) mint items whose `collection`/`name` strings are attacker-influenced — this occurs in permissionless or shared-creator minting flows (e.g., resource-account-backed NFT launchpads/marketplaces where the resource account is the on-chain "creator" for all users' mints, and users supply their own collection/token name strings). An attacker who can create a collection (or token) with a crafted name containing `"::"` can force their object's address to coincide with the deterministic address that a legitimate, not-yet-created `(collection, name)` pair would compute to under that same shared creator address.

### Impact Explanation
Once the attacker's colliding object is created first, `create_object_internal`'s `assert!(!exists<ObjectCore>(obj_addr), EOBJECT_EXISTS)` guarantees the legitimate mint at the "real" `(collection, name)` (or the legitimate `Collection`) can **never** be created at its canonical, expected, publicly-computable address — this is a permanent, non-recoverable loss of the ability to mint/hold the intended asset at its documented address (front-running/namespace-squatting a shared minting authority). This matches the gate's accepted impact: "Permanent lock or non-recoverable loss of object-held ... value," since dApps, indexers, and users that resolve token/collection identity by the deterministic `create_token_address`/`create_collection_address` view functions will be permanently unable to locate/mint the intended asset, and any protocol logic gated on "does token X exist at its canonical address" is corrupted.

### Likelihood Explanation
Likelihood is **conditional but realistic**: it requires a single creator/signer address under which multiple parties (or an attacker plus a legitimate future user) supply attacker-influenceable `collection`/`name` strings — a common pattern for shared resource-account-based NFT launchpads and marketplaces built on `aptos-token-objects`. It does not require any privileged role; the attacker only needs the ability to submit a collection or token name string of their choosing before the legitimate mint occurs. I was not able to fully verify (due to no further tool access) the exact Move source of `collection::create_collection_address`/its seed function to confirm 1:1 parity with the Rust mirror in `types/src/account_address.rs`, so the "collection vs. token" cross-type collision specifically should be treated as based on the confirmed Rust-side implementation and the identical scheme constant reused by `object::create_object_address`, rather than an independently re-verified Move-side collection seed. The `collection`-vs-`token` collision aside, the `token`-vs-`token` collision (different `(collection,name)` pairs colliding) is fully confirmed directly from the `create_token_seed` source shown above.

### Recommendation
Length-prefix (or otherwise unambiguously delimit) each dynamic-length component before concatenation, e.g. use BCS serialization of each string (which prepends a ULEB128 length) instead of raw byte concatenation with a literal separator:
```move
public fun create_token_seed(collection: &String, name: &String): vector<u8> {
    assert!(name.length() <= MAX_TOKEN_NAME_LENGTH, error::out_of_range(ETOKEN_NAME_TOO_LONG));
    let seed = bcs::to_bytes(collection);
    seed.append(bcs::to_bytes(name));
    seed
}
```
Apply the same fix to `create_token_name_with_seed` and ensure `collection::create_collection_address`'s seed derivation is likewise unambiguous (e.g., via BCS-encoded name rather than raw bytes), and add a distinct domain-separation byte per object subtype (collection vs. token vs. other named objects) so seeds from different object kinds can never collide even if their string contents happen to match.

### Proof of Concept
1. Attacker calls `collection::create_*_collection(attacker_signer, ..., name = string::utf8(b"A::B"), ...)` — collection names have no restriction against containing `"::"`.
2. Later, the same attacker (as the "creator" signer for a shared/launchpad resource account) calls `token::create_token(attacker_signer, collection_obj_named("A"), ..., name = string::utf8(b"B::C"), ...)` intending to mint a token in a *different* collection literally named `"A"`.
3. `create_token_seed(&"A".to_string(), &"B::C".to_string())` computes `"A" + "::" + "B::C"` = `"A::B::C"`.
4. This is byte-identical to the seed used when the attacker created the collection named `"A::B::C"`... (or more directly: `create_token_seed("A::B", "C")` == `create_token_seed("A", "B::C")` == `"A::B::C"`, verified directly from the source at `token.move:580-587`).
5. Whichever of the two colliding `(collection, name)` pairs is minted second will hit `object::create_object_internal`'s `assert!(!exists<ObjectCore>(obj_addr))` and permanently abort, since the address is already occupied — permanently preventing that legitimate token from ever being created at its expected, canonical address under that creator.

    public fun create_object_address(source: &address, seed: vector<u8>): address {
        let bytes = bcs::to_bytes(source);
        bytes.append(seed);
        bytes.push_back(OBJECT_FROM_SEED_ADDRESS_SCHEME);
        from_bcs::to_address(hash::sha3_256(bytes))
    }
