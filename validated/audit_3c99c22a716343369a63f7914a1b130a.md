### Title
JWT single-use replay guard has a check-then-act race allowing an HTTP trigger token to authorize two concurrent workflow executions - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

### Summary
The Quest.sol report's root cause is a non-atomic "check state, then act, then mark as consumed" sequence: `claim()` checks `isClaimed`, performs the payout, and only afterward calls `_setClaimed`, leaving a window where the "already consumed" guard can be raced. The `WorkflowMetadataHandler.Authorize` function in the gateway's HTTP trigger path has the same structural flaw applied to single-use JWT tokens: it checks whether a JWT `jti` has been seen (`isReplay`), performs the authorization work, and only afterward records the `jti` as used (`recordUsage`), with the check and the record protected by two separate, independently-acquired locks rather than one atomic operation.

### Finding Description
`Authorize` calls `h.jwtCache.isReplay(claims.ID)` first [1](#0-0) , and only calls `h.jwtCache.recordUsage(claims.ID)` at the very end, after the authorized-key lookup succeeds [2](#0-1) . The cache itself implements the check and the record as two independently-locked operations rather than a single atomic "check-and-set": [3](#0-2) 

Because `isReplay` takes an `RLock` and returns before `recordUsage` takes the `Lock` to insert the `jti`, two goroutines handling two concurrent HTTP trigger requests carrying the exact same signed JWT (same `jti`) can both observe `isReplay() == false` before either has recorded the `jti`. Both requests then pass the replay check and proceed to be dispatched to workflow nodes as legitimate `MethodWorkflowExecute` triggers, exactly mirroring how User A's `claim()` and User B's transfer can both "win" a race against a guard that is checked before it is durably updated.

### Impact Explanation
A JWT presented to the gateway's HTTP trigger handler is meant to be single-use (this is explicitly tested and documented behavior: replay must fail with "JWT token has already been used") [4](#0-3) . If the check-then-record window is won by two concurrent requests, a single externally-obtained (or naturally duplicated, e.g. retried by a client/proxy without idempotency) JWT can authorize the same workflow execution twice. This is an unauthorized/duplicate job run against the DON — the same class of impact called out as acceptable ("unauthorized job run") — reachable purely from an unprivileged, internet-facing client hitting the gateway's HTTP trigger endpoint, with no special privileges required beyond possessing one valid signed request JWT.

### Likelihood Explanation
Triggering the race only requires sending the same signed request (same body, same JWT) twice in quick succession — trivially reproducible by any client (accidental double-submit, retry logic, or a deliberate racer) without needing to compromise any key material. The window is small (two lock acquisitions apart) but is a genuine, unbounded TOCTOU race with no synchronization tying the read and write together, so it is a reliable finding under load/concurrency rather than a purely theoretical one.

### Recommendation
Make the check-and-record operation atomic: acquire a single lock for the whole "check jti / record jti" sequence in `jwtReplayCache`, or replace the check+record pair with a single `CheckAndRecord`-style method (as already used elsewhere in the codebase, e.g. `RequestReplayGuard.CheckAndRecord` [5](#0-4) ) that inserts the `jti` under one lock and returns whether it was already present, closing the race window entirely.

### Proof of Concept
1. Register a workflow and obtain one valid signed request JWT `T` (with `jti = J`) for a `MethodWorkflowExecute` HTTP trigger request, as in the existing replay test setup [6](#0-5) .
2. Concurrently call `WorkflowMetadataHandler.Authorize(workflowID, T, req)` from two goroutines at (near) the same time.
3. Both goroutines' `isReplay(J)` calls can return `false` before either goroutine's `recordUsage(J)` executes, because these are two separate lock acquisitions with no shared critical section [3](#0-2) .
4. Both calls to `Authorize` succeed and return a valid `AuthorizedKey`, causing the trigger handler to dispatch the workflow execution twice to workflow nodes using what should have been a strictly single-use token.

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}

// CheckAndRecord returns ErrRequestAlreadySeen if the digest was previously
// recorded and has not yet expired. Otherwise it records the digest with
// the given expiry timestamp (unix seconds, UTC).
//
// Expired entries are cleaned up on every call.
func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
