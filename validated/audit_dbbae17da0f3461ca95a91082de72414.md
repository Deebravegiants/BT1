This confirms the vulnerability. The gateway's `UserServerConfig` (path `/user`) accepts external JSON-RPC requests over TLS with no per-request signature requirement in the sample config beyond the standard gateway user-facing endpoint, and requests reach the Vault capability's `handleSecretsCreate`/`handleSecretsUpdate`/`handlePublicKeyGet` after only owner-authorization checks (not sanitization of internal errors). The code confirms the claim precisely as described: `GatewayHandler.errorResponse` at [1](#0-0)  unconditionally sets `Message: err.Error()` with no classification of internal vs. user-facing errors, unlike the sibling `confidentialrelay` handler's `errorResponse` at [2](#0-1) , which explicitly substitutes `internalErrorMessage` when `errorCode == jsonrpc.ErrInternal`.

The call sites confirmed as-described include `handleSecretsCreate`/`handleSecretsUpdate` passing `api.FatalError` with the raw underlying error [3](#0-2) , `handlePublicKeyGet` wrapping `fmt.Errorf("failed to get public key: %w", err)` under `api.HandlerError` [4](#0-3) , and `gatewayErrorResponse` forwarding any non-`InvalidVaultParamsError` (e.g., pipeline/authorization/public-key errors) verbatim [5](#0-4) . Note that `MethodPublicKeyGet` bypasses the authorization pipeline entirely and is reachable by any caller, per the `switch` in `HandleGatewayMessage` [6](#0-5) , while `MethodSecretsCreate`/`Update`/`Delete`/`List` require only passing `requestProcessor.ProcessRequest` (owner/JWT authorization) — not admin/operator privilege — before reaching the unredacted error path, satisfying the "unprivileged client" requirement.

I also confirmed `secretsService.CreateSecrets`/`UpdateSecrets`/`GetPublicKey` in `capability.go` can produce genuinely internal error strings (OCR/consensus failure text via `errors.New(resp.Error)`, marshal failures, decode/unmarshal failures of stored public-key state) as cited in the original report, none of which are redacted before reaching `gw_handler.go`.

This matches CWE-215 (information exposure through error messages) and is a concrete, reachable, code-level defect — not speculative — with a clear working defensive pattern already present elsewhere in the codebase (`confidentialrelay/handler.go`) that was not applied consistently to the Vault gateway handler.

Audit Report

## Title
Unredacted internal error messages returned to unprivileged clients via the Vault gateway handler - (File: `core/capabilities/vault/gw_handler.go`)

## Summary
`GatewayHandler.errorResponse` in `core/capabilities/vault/gw_handler.go` places `err.Error()` verbatim into the JSON-RPC `WireError.Message` field for every error code, including internal/system-level failures (`api.FatalError`, `api.HandlerError`) originating from OCR consensus errors, key marshal/unmarshal failures, and internal state decode errors. This contrasts with the sibling `confidentialrelay` handler, which explicitly redacts internal errors (`jsonrpc.ErrInternal`) to a generic message before returning them to callers, showing the intended and available defensive pattern was not applied here.

## Finding Description
`errorResponse` at `core/capabilities/vault/gw_handler.go:388-410` unconditionally writes `err.Error()` to the wire regardless of `errorCode`, whereas `confidentialrelay/handler.go`'s `errorResponse` (lines 1022-1049) substitutes `internalErrorMessage` whenever `errorCode == jsonrpc.ErrInternal`. Multiple call sites in `gw_handler.go` pass internal/system-level errors into this function without any sanitization:
- `handleSecretsCreate`/`handleSecretsUpdate` (lines 275-311) pass `api.FatalError` wrapping whatever `secretsService.CreateSecrets`/`UpdateSecrets` returned.
- `handlePublicKeyGet` (lines 364-373) wraps `fmt.Errorf("failed to get public key: %w", err)` under `api.HandlerError`; this method is dispatched directly without going through the owner-authorization pipeline (`HandleGatewayMessage`, lines 187-211), so it is reachable by any caller who can reach the gateway's user-facing endpoint.
- `gatewayErrorResponse` (lines 263-273) forwards any non-`InvalidVaultParamsError` — including raw pipeline/public-key-retrieval errors — under `api.HandlerError`.

Tracing into `core/capabilities/vault/capability.go` and `gateway_vault_request_processor.go`, the underlying errors that can flow through these paths include a raw OCR plugin response error string wrapped via `errors.New(resp.Error)`, a public-key marshal failure, and decode/unmarshal failures of the master public key's internal representation. None of these are guaranteed to be pre-sanitized before reaching `gw_handler.go`. The `Authorizer`/JWT/allowlist checks in `requestProcessor.ProcessRequest` gate *who* can submit create/update/delete/list requests, but they do not gate *what content* is placed into the error response once a request is accepted or fails validation — this is an independent, unaddressed defense gap.

## Impact Explanation
This is an in-scope information-disclosure defect (CWE-215 class): a caller able to reach the Vault gateway's user-facing JSON-RPC endpoint — including via `MethodPublicKeyGet`, which requires no authorization at all — can receive raw internal Go error text in place of the response on failure paths. This could expose internal identifiers, request IDs, or implementation/state details useful for follow-on attacks. It does not by itself achieve authentication bypass or fund movement, so impact is best characterized as a moderate-severity internal information disclosure rather than a critical vulnerability.

## Likelihood Explanation
Triggering internal-error conditions (transient OCR/consensus failures, malformed public-key state, marshal/unmarshal edge cases) is plausible under normal node operation and does not require any elevated privilege — any client capable of sending a JSON-RPC request to the gateway's Vault endpoint can potentially observe an unredacted error message when one of these system-level failures occurs. The precise sensitivity of leaked content depends on the runtime error surfaced, which limits (but does not eliminate) the practical severity.

## Recommendation
Apply the same redaction pattern used in `core/capabilities/confidentialrelay/handler.go`'s `errorResponse` to `core/capabilities/vault/gw_handler.go`: classify error codes (e.g., `api.FatalError`, `api.HandlerError` wrapping system-level errors) and substitute a generic internal-error message before writing to the `jsonrpc.WireError.Message` field, reserving verbatim error text only for explicitly classified user-input errors such as `InvalidVaultParamsError` and `api.UserMessageParseError`.

## Proof of Concept
1. Deploy or configure a test node with the Vault `GatewayHandler` wired to a `secretsService` mock/stub that returns a system-level error (e.g., simulate an OCR consensus failure by having `CreateSecrets` return `fmt.Errorf("error processing request %s: %w", requestID, errors.New("internal consensus timeout: peer 3 state mismatch"))`).
2. Send a `MethodSecretsCreate` JSON-RPC request through the gateway's node-facing test harness (as in `gw_handler_test.go`'s `TestGatewayHandler_HandleGatewayMessage` table) with a valid, authorized owner so the request passes `requestProcessor.ProcessRequest`.
3. Assert on the `jsonrpc.Response.Error.Message` returned via `SendToGateway`: observe that it contains the raw injected internal error string ("internal consensus timeout: peer 3 state mismatch") rather than a generic message, confirming the missing redaction in `GatewayHandler.errorResponse`.
4. Repeat for `MethodPublicKeyGet` with a `secretsService.GetPublicKey` stub returning a marshal/unmarshal error, and without any authorization/JWT header, to confirm the unauthenticated reachability of this leak via `handlePublicKeyGet`.

	}
