### Title
Webhook HMAC only signs the raw body, allowing shop-domain spoofing for cross-tenant webhook injection - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as verified once `Utils::HmacValidator.validate(request)` succeeds, and then hands the handler a `shop` value taken directly from the unauthenticated `shopify-shop-domain` HTTP header, even though that field was never part of the HMAC computation.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body: [1](#0-0) 

`#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, independent of that signature: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the HMAC over exactly `to_signable_string`, i.e. the raw body bytes only: [3](#0-2) 

`Registry.process` uses that HMAC check as the sole authentication gate for the whole request, then forwards `request.shop` (the unauthenticated header) to the app's handler as the tenant identifier: [4](#0-3) 

The gem's own documentation reinforces the false assumption that `process` fully authenticates the request and that the resulting `shop` field is trustworthy: "This will verify the request did indeed come from Shopify" and `data.shop` is documented simply as "The shop domain of the webhook": [5](#0-4) [6](#0-5) 

The identity binding that should hold is: `shop domain used to attribute webhook data == shop domain covered by the HMAC signature`. Here, the signature covers only the body bytes, so this equality never actually holds — `request.shop` can be any value the caller supplies in the header while `request.hmac` remains valid for a body the attacker legitimately obtained from Shopify for their own store.

### Impact Explanation
Any unprivileged internet user who has installed the target app on their own (e.g. free trial/dev) store can trigger a genuine Shopify webhook for that store, capturing a valid `(body, hmac)` pair signed by Shopify with the app's `client_secret` (a secret the attacker never needs to know). Because the header carrying the tenant identity is excluded from the signature, the attacker can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `Registry.process` will pass HMAC validation (body unchanged) and hand the handler a `WebhookMetadata` claiming the attacker-controlled body belongs to the victim shop. Any app that uses `data.shop` to key data storage, tenant lookup, or business logic (exactly as the documented handler pattern in `webhooks.md` line 26, `perform_later(topic: data.topic, shop_domain: data.shop, ...)`, encourages) will attribute forged data to a different tenant — a cross-tenant data-injection/confusion issue.

### Likelihood Explanation
Likelihood is meaningful: no leaked secrets or privileged access are required, only that the attacker be a legitimate installer of the target app on some shop they control, which is available to any internet user via normal app installation. The webhook endpoint is public by design (it must be, to receive Shopify's callbacks), so the replay is directly reachable.

### Recommendation
Bind the shop-domain (and topic) header into the value that is HMAC-verified, or otherwise cryptographically/independently confirm that the `shopify-shop-domain` header matches a shop for which the app holds an active installation/session before trusting it, rather than exposing it as a bare, unauthenticated field on `WebhookMetadata`. At minimum, document prominently that `data.shop` is not covered by the HMAC and must be independently validated by the host application against known installed shops before being used for tenant attribution.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and registers for a webhook topic (e.g. `orders/create`).
2. Attacker performs an action in their store that causes Shopify to send a real webhook POST to the app's endpoint, with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)` and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker intercepts/replays this request to the same public endpoint, keeping body `B` and header `H` identical, but changing `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request#hmac` reads `H` unchanged; `Utils::HmacValidator.validate` recomputes HMAC over `B` only and it matches `H`, so validation passes.
5. `Registry.process` invokes the handler with `WebhookMetadata` whose `shop` is `"victim.myshopify.com"` even though the body `B` actually came from the attacker's own store — demonstrating the unauthenticated shop-domain field can be freely spoofed while the request still passes HMAC verification.
