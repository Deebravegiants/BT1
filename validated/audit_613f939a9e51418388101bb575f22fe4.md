### Title
Webhook shop-domain, topic, and webhook-id headers are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `HmacValidator.validate` verifies the *payload* integrity but not the `shop-domain`, `topic`, `webhook-id`, or `api-version` HTTP headers. `Registry.process` nevertheless treats `request.shop` (parsed straight from the unauthenticated header) as the authoritative tenant identity when invoking the app's webhook handler.

### Finding Description
`HmacValidator.validate` computes/compares the HMAC over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` is defined to be exactly the raw JSON body, and `shop` is read from an entirely separate, HMAC-uncovered header: [2](#0-1) 

`Registry.process` validates the HMAC of the body, then unconditionally forwards `request.shop` (and `request.topic`, `request.webhook_id`, `request.api_version`) to the registered handler as trusted metadata: [3](#0-2) 

The equality the gem implicitly claims to guarantee is://
`hmac_valid(body) == true` implies `(body, shop, topic, webhook_id)` all originated from Shopify together.

In reality the gem only proves `hmac_valid(body) == true` implies `body` is untampered *bytes that some app-owning entity received a genuine webhook for at some point* — it says nothing about which shop, topic, or webhook-id those bytes are currently being claimed to belong to. Any actor who legitimately installs the app on their own store (an unprivileged, ordinary merchant — no special privilege required) will receive real webhook deliveries with valid HMACs computed over the body they control (by performing actions in their own store, e.g. `orders/create`). That party can replay the same raw body + valid HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header for an arbitrary victim shop domain. `HmacValidator.validate` still succeeds (it only checks the body bytes against the secret), and `Registry.process` hands the handler a `WebhookMetadata` claiming the (attacker-chosen) victim shop as the source: [4](#0-3) 

This is the exact bug class from the referenced report: a field (`shop`, `topic`, `webhook_id`) that is *acted on* by the trust boundary but *not covered by the cryptographic binding* (the HMAC), allowing the attacker to desynchronize the verified bytes from the identity used downstream — a cross-tenant identity-binding break rather than a payload-integrity break.

### Impact Explanation
Any app built on this gem that keys tenant-scoped behavior off `WebhookMetadata#shop` (this is the officially documented purpose of the field, per `docs/usage/webhooks.md`, and the only shop identifier the gem exposes to the handler) can be made to process attacker-supplied, self-authored webhook bodies under an arbitrary victim shop's identity. Depending on the handler, this enables cross-tenant data injection/corruption (e.g., writing attacker-controlled order/product/customer data into the victim shop's records, triggering tenant-scoped side effects such as billing, GDPR data-deletion actions attributed to the wrong shop, or state transitions keyed on `shop`). This satisfies the "cross-tenant access" Critical impact criterion, since the merchant/tenant boundary — the fundamental isolation guarantee of a multi-tenant Shopify app — is broken using only an ordinary, unprivileged app installation.

### Likelihood Explanation
Likelihood is high given the required capability is minimal: any user who can install the app on any Shopify store (a normal, low-privilege action available to any merchant) can capture at least one genuine `raw_body`+HMAC pair from their own store's webhook deliveries, then freely replay it against the app's public webhook endpoint with a forged `X-Shopify-Shop-Domain` header. No access token, `client_secret`, or credential theft is required — only the ability to receive one legitimate webhook and to send an HTTP POST with attacker-chosen headers to the app's public endpoint.

### Recommendation
Include the `shop-domain`, `topic`, and `webhook-id` (and `api-version`) header values in the signable string used for HMAC verification (or otherwise cryptographically bind them, e.g., by validating them out-of-band against Shopify's known store list per delivery), so a valid HMAC only ever attests to headers and body received together in the same, genuine delivery.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and legitimately receives an `orders/create` webhook: raw body `B`, with header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` under the app's `api_secret_key`), `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker POSTs to the app's webhook endpoint with the same body `B` and same HMAC header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged shop header; `Utils::HmacValidator.validate` succeeds because it only compares HMAC against `@raw_body` (`request.rb:35-38`, `hmac_validator.rb:26-31`).
4. `Registry.process` (`registry.rb:188-199`) invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's parsed body>, ...)`, and the app processes attacker-controlled data attributed to the victim tenant.
