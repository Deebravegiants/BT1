### Title
Missing enforcement of `slippageValues[1]` output floor in `ExternalActionSwap.swap()` allows relay/MEV sandwich theft of shielded swap proceeds - (File: `contracts/external-actions/swaps/ExternalActionSwap.sol`)

### Summary
`ExternalActionSwap.swap()` only checks that the user-committed minimum-output slippage value is non-zero, but never checks that the actual amount received from the external router call meets that floor. The committed `slippageValues[1]` is part of `CircomData` and therefore part of `calldataHash`/the ZK public-input vector that the user signs off on, but it is never compared against the on-chain execution result `swappedAmount`. This breaks the intended equality "user-approved minimum output ≤ actual output," letting a malicious/adversarial relay or any MEV actor sandwich the router call to extract the difference as risk-free profit, exactly the same "price used for the swap is not protected/verified" bug class as the referenced Uniswap `beforeSwap()` report (there, the pool used unprotected spot price for an internal swap; here, the wrapper executes an external router swap with a user-committed floor that is silently discarded).

### Finding Description
`swap()` requires `circomData.slippageValues[1] != 0` but never uses that value again: [1](#0-0) 

`callRouter()` (implemented by `LifiExternalAction`) simply measures `balanceAfter - balanceBefore` from an arbitrary externally-supplied router calldata blob and returns it as `swappedAmount`, with no minimum-output assertion at all: [2](#0-1) 

`swappedAmount` is then used, unchecked against any floor, to compute fees and to build the output UTXO that is credited to the shielded pool: [3](#0-2) 

`slippageValues` is a `CircomData` field that is hashed into `calldataHash` and validated by `HinkalHelper.performHinkalChecks` / `dimensionsCheck` (length check only) and `CircomDataBuilder.getHashedCalldata`: [4](#0-3) [5](#0-4) 

Because the field is bound into the signed calldata hash but the contract logic that is supposed to *enforce* it (`swap()`) drops the comparison, the equality that the ZK-committed public input is meant to guarantee ("minimum acceptable output for this swap") is never actually checked at execution time. The router call (`router.call(externalActionMetadata)`) executes against live on-chain liquidity at whatever price exists at inclusion time; since there is no minimum-output check, a relay (who controls transaction ordering/inclusion, per `relayerIsValid`) or any searcher can sandwich the router swap, driving `swappedAmount` arbitrarily low while it is still credited into the user's shielded UTXO, with the sandwicher pocketing the difference.

### Impact Explanation
This is theft of user funds: the relay/attacker can extract value from every swap external action processed by Hinkal by sandwiching the underlying DEX/aggregator trade, since the protocol never enforces the user's own committed minimum-output guarantee. This falls under "temporary freezing of user funds" at minimum (user receives less shielded value than intended) and effectively "theft of in-flight user funds" during the external action, since the loss is siphoned to the sandwiching relay/MEV actor rather than being a mistake solely affecting the attacker's own balance.

### Likelihood Explanation
High likelihood: any relay processing swap transactions (or a searcher watching the mempool for the router calldata submitted via `LifiExternalAction`) can trivially sandwich the trade. No privileged access beyond being an allowed relay (or observing/front-running the public router calldata) is required, and the bug is present on every swap that goes through `ExternalActionSwap.swap()`.

### Recommendation
In `ExternalActionSwap.swap()`, after computing `swappedAmount`, add an explicit check `require(swappedAmount >= uint256(circomData.slippageValues[1]), "swap output below minimum");` before proceeding to fee calculation and UTXO creation, so the ZK-committed slippage floor is actually enforced on-chain.

### Proof of Concept
1. User builds a shielded swap transaction off-chain with `circomData.slippageValues[1] = minOut` (their intended floor) and submits it through a relay.
2. `ExternalActionSwap.swap()` only checks `slippageValues[1] != 0` (`ExternalActionSwap.sol:53-56`), never comparing it to the actual result.
3. The relay (or any actor able to front/back-run the router calldata executed at `LifiExternalAction.callRouter` `router.call(externalActionMetadata)`) sandwiches the trade: sell before, let the user's swap execute at a worse price, buy back after.
4. `swappedAmount = balanceAfter - balanceBefore` is far below the user's intended `minOut`, but since it's never checked, the transaction still succeeds and the user's UTXO is created with the reduced amount (`ExternalActionSwap.sol:91-101`), while the sandwiching party captures the extracted value.

```text
    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
```
