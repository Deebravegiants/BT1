### Title
Webhook shop-tenant identity spoofing via unauthenticated `shop-domain` header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
The webhook processing pipeline authenticates only the request *body* via HMAC, but the `shop` value handed to the app's business logic (`WebhookMetadata#shop`) is read from an HTTP header that is never covered by that HMAC. This breaks the intended binding `authenticated_bytes == data_acted_on`, allowing a shop identity to be substituted after the signature check passes.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` with `to_signable_string` returning only the raw body: [1](#0-0) 

The `shop` accessor, however, is read from a separate header that is not part of the signed content: [2](#0-1) 

`Registry.process` validates the HMAC purely against the body and then forwards `request.shop` unchanged to the app handler as the authoritative tenant identifier: [3](#0-2) 

`WebhookMetadata` exposes `shop` as a plain, unauthenticated `String` field consumed by every `WebhookHandler#handle` implementation: [4](#0-3) 

Crucially, the HMAC secret used to sign webhooks is the app's single `client_secret`/`api_secret_key`, shared across every shop that has installed the app — it is not a per-shop secret: [5](#0-4) 

Because the signature covers only `@raw_body` and never the `shopify-shop-domain` / `x-shopify-shop-domain` header, an unprivileged user who legitimately installs the app on their **own** store receives genuinely-signed webhooks (valid HMAC, computed with the shared app secret). They can then replay that exact body+HMAC pair to the app's webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds because it never inspects the header, and `Registry.process` passes the attacker-controlled `shop` value straight into `WebhookMetadata`, which host applications use to key data storage, trigger shop-scoped side effects, or resolve `Auth::Session` records.

This is directly analogous to the reported Sway bug: a value is trusted to represent "the entity this data belongs to" while the actual verified quantity (the HMAC) covers something else entirely (the body, not the shop binding) — the wrong entity, so to speak, is treated as authoritative.

### Impact Explanation
If a host application uses `WebhookMetadata#shop` to select which merchant's data/session the webhook payload applies to (the documented and expected usage pattern, since this is the only shop field provided to handlers), an attacker can inject or overwrite data attributed to an arbitrary victim shop domain, or trigger shop-scoped business logic (e.g., `customers/redact`, `orders/create` side effects, session lookups) under a false tenant identity. This is a cross-tenant identity-binding break, matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Requires only: (1) attacker installs the target app on any shop they control (a normal, unprivileged action for any Shopify app that isn't invite-only), which yields a legitimately HMAC-signed webhook body, and (2) attacker replays that body to the app's public webhook endpoint with a forged `shop-domain` header. No access to `api_secret_key`, access tokens, or victim credentials is needed. This requires the host app to make trust decisions based on `WebhookMetadata#shop`, which is the field's entire documented purpose, making the likelihood high wherever this gem's webhook feature is used as intended.

### Recommendation
Bind the shop identity into the authenticated material: either include the `shop` (and ideally `topic`/`webhook-id`) in the HMAC-signable string, or require the caller to cross-check `request.shop` against the shop associated with an existing, independently-authenticated session/webhook registration before trusting it. At minimum, document prominently that `shop` in `WebhookMetadata` is unauthenticated and must not be used as a sole tenant-selection key.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a store they control) and triggers a webhook subscription (e.g., `orders/create`).
2. Shopify delivers a webhook to the app's endpoint with body `B`, and header `x-shopify-hmac-sha256: HMAC(client_secret, B)`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures this raw HTTP request (they control the receiving endpoint or a proxy in front of it).
4. Attacker resends the identical body `B` and identical `x-shopify-hmac-sha256` value to the same endpoint, but with header `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate` in `Registry.process` (`lib/shopify_api/webhooks/registry.rb:190`) succeeds because it only recomputes the HMAC over `raw_body`, ignoring the header. `WebhookHandler#handle` receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host app to process attacker-supplied data under the victim shop's identity.
