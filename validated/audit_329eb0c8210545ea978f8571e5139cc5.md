Audit Report

## Title
Malicious collator can permanently censor specific DMP messages by exploiting the weak `check_enough_messages_included_basic` advancement rule used for the DMQ path - ([File: cumulus/pallets/parachain-system/src/lib.rs], [File: cumulus/pallets/parachain-system/src/parachain_inherent.rs])

## Summary
The DMQ inbound message path in `enqueue_inbound_downward_messages` only calls the weak `check_enough_messages_included_basic("DMQ")` check [1](#0-0)  whereas the HRMP path calls the stricter `check_enough_messages_included_advanced` [2](#0-1) . This asymmetry lets a malicious collator hash any large-but-fitting DMP message (excluding it from execution) while satisfying the basic invariant with a trivial full message, permanently skipping the hashed message's execution while still advancing `LastProcessedDownwardMessage` past it.

## Finding Description
`into_abridged` [3](#0-2)  is only the honest algorithm used by `do_create_inherent`; a malicious collator is not required to use it, since it submits `InboundMessagesData` directly via the unsigned `set_validation_data` extrinsic that only `ensure_none` is checked on.

The two guards on the submitted collection are:
1. The DMQ head hash-chain assertion, which is representation-agnostic — both full (`extend_downward`) and hashed (`extend_with_hashed_msg`) messages feed the same chain [4](#0-3) . A collator can always compute the correct hash for any DMP message, since DMP messages are public relay-chain data, so this check does not distinguish an honest split from a malicious one.
2. `check_enough_messages_included_basic`, which only asserts `full_messages.len() >= 1` whenever `hashed_messages` is non-empty, with no relation to whether hashing was actually necessary for the size budget [5](#0-4) .

This is in contrast to `check_enough_messages_included_advanced`, which asserts that `full_messages_size + first_hashed_msg_max_size > max_full_messages_size`, i.e., hashing is only legal when it was necessary [6](#0-5) , and the code's own docstring explicitly warns that omitting/hashing more full messages than necessary "leads to censorship" [7](#0-6) . This advanced check is wired up only for HRMP [2](#0-1) , not for DMQ.

Only `full_messages` are dispatched to `T::DmpQueue::handle_messages` via `bounded_msgs_iter` [8](#0-7) , and `LastProcessedDownwardMessage` is advanced past hashed messages exactly as if they had been processed [9](#0-8) . Since messages up to `last_processed_msg` are dropped on subsequent blocks via `drop_processed_messages` [10](#0-9) , a hashed-but-never-executed message is permanently skipped with no re-delivery mechanism.

Notably, the exact same architectural gap exists in the HRMP path too — `flat_msgs_iter` also only iterates `full_messages` for dispatch [11](#0-10)  — but HRMP is protected by the advanced check while DMQ is not, confirming the asymmetry is a genuine gap rather than a mocked scenario.

## Impact Explanation
A malicious or colluding collator can selectively and permanently censor specific DMP messages (e.g., governance dispatches, XCM `Transact` messages) while producing an inherent that passes all on-chain validation, exactly matching the censorship scenario the code's own documentation warns against for this exact function [7](#0-6) . This is a real logic gap in the runtime pallet, not a node/relayer-only issue, since it is enforced (or not enforced) entirely within `enqueue_inbound_downward_messages`.

## Likelihood Explanation
This requires only a malicious/unprivileged collator producing blocks for the parachain — collators are an explicitly untrusted party in this threat model (the code's own docs on `check_enough_messages_included_advanced` acknowledge malicious collators as the threat actor). No relay-chain collusion, privileged keys, or victim mistakes are required; DMP message contents are public, so hash computation is trivially correct. The exploit is repeatable every block for any DMP message the collator wants to suppress.

## Recommendation
Apply `check_enough_messages_included_advanced` (or an equivalent size-based check using `messages_collection_size_limit()` and the max DMP message size) to the DMQ path in `enqueue_inbound_downward_messages`, replacing the current call to `check_enough_messages_included_basic("DMQ")`.

## Proof of Concept
Extend the existing test module in `parachain_inherent.rs` (as in the report): construct an `AbridgedInboundDownwardMessages` with a 1-byte `full_messages` entry and a large (e.g. 900-byte) `hashed_messages` entry that would fit under the size budget. `check_enough_messages_included_basic("DMQ")` passes without panicking on this crafted split, while `check_enough_messages_included_advanced` with equivalent size parameters panics on the identical data, demonstrating that the DMQ path (which only calls the basic check per `enqueue_inbound_downward_messages`) accepts a split that unnecessarily hashes a large, fitting DMP message — enabling the message to be marked processed via the MQC chain without ever being dispatched via `bounded_msgs_iter`/`handle_messages`.

	/// Drop all the messages up to `last_processed_msg`.
	pub fn drop_processed_messages(&mut self, last_processed_msg: &InboundMessageId) {
		let mut last_processed_msg_idx = None;
		let messages = &mut self.messages;
		for (idx, message) in messages.iter().enumerate().rev() {
			let sent_at = message.sent_at();
			if sent_at == last_processed_msg.sent_at {
				last_processed_msg_idx = idx.checked_sub(last_processed_msg.reverse_idx as usize);
				break;
			}
			// If we build on the same relay parent twice, we will receive the same messages again
			// while `last_processed_msg` may have been increased. We need this check to make sure
			// that the old messages are dropped.
			if sent_at < last_processed_msg.sent_at {
				last_processed_msg_idx = Some(idx);
				break;
			}
		}
		if let Some(last_processed_msg_idx) = last_processed_msg_idx {
			messages.drain(..=last_processed_msg_idx);
		}
	}

	pub fn into_abridged(
		self,
		size_limit: &mut usize,
	) -> AbridgedInboundMessagesCollection<Message> {
		let mut messages = self.messages;

		let mut split_off_pos = messages.len();
		for (idx, message) in messages.iter().enumerate() {
			if *size_limit < message.data().len() {
				break;
			}
			*size_limit -= message.data().len();

			split_off_pos = idx + 1;
		}

		let extra_messages = messages.split_off(split_off_pos);
		let hashed_messages = extra_messages.iter().map(|msg| msg.to_compressed()).collect();

		AbridgedInboundMessagesCollection { full_messages: messages, hashed_messages }
	}

	pub fn check_enough_messages_included_advanced(
		&self,
		collection_name: &str,
		size_info: AbridgedInboundMessagesSizeInfo,
	) {
		// We should check that the collection contains as many full messages as possible
		// without exceeding the max expected size.
		let AbridgedInboundMessagesSizeInfo { max_full_messages_size, first_hashed_msg_max_size } =
			size_info;

		let mut full_messages_size = 0usize;
		for msg in &self.full_messages {
			full_messages_size = full_messages_size.saturating_add(msg.data().len());
		}

		// The worst case scenario is that were the first message that had to be hashed
		// is a max size message.
		assert!(
			full_messages_size.saturating_add(first_hashed_msg_max_size) > max_full_messages_size,
			"[{}] Advancement rule violation: full messages size smaller than expected. \
			full msgs size: {}, first hashed msg max size: {}, max full msgs size: {}",
			collection_name,
			full_messages_size,
			first_hashed_msg_max_size,
			max_full_messages_size
		);
	}

	/// Returns an iterator over the messages that maps them to `BoundedSlices`.
	pub fn bounded_msgs_iter<MaxMessageLen: Get<u32>>(
		&self,
	) -> impl Iterator<Item = BoundedSlice<'_, u8, MaxMessageLen>> {
		self.full_messages
			.iter()
			// Note: we are not using `.defensive()` here since that prints the whole value to
			// console. In case that the message is too long, this clogs up the log quite badly.
			.filter_map(|m| match BoundedSlice::try_from(&m.msg[..]) {
				Ok(bounded) => Some(bounded),
				Err(_) => {
					defensive!("Inbound Downward message was too long; dropping");
					None
				},
			})
	}
