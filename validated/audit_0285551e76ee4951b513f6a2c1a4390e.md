### Title
Webhook `shop` (tenant) identifier is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, then dispatches to the app's handler using a `shop` value taken from an unauthenticated header. The HMAC does not bind the `shop` field, so a party who can obtain one valid `(body, hmac)` pair signed with the app's secret (e.g. from a webhook legitimately delivered for their own installed shop) can replay that exact body/hmac while substituting the `shopify-shop-domain` header for a victim shop, and the request will still pass validation.

### Finding Description
`Registry.process` performs the only authentication check for inbound webhooks: [1](#0-0) 

The HMAC check delegates to `Utils::HmacValidator.validate`, which recomputes the signature purely from `verifiable_query.to_signable_string`: [2](#0-1) 

For webhooks, `to_signable_string` is defined to be the raw body only — no other field is included: [3](#0-2) 

Yet `shop` (parsed straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header, with no cross-check against the signature) is passed to the app's handler as the tenant identifier for the event: [4](#0-3) [5](#0-4) [6](#0-5) 

The equality that should hold is: `shop bound by HMAC == shop delivered to handler`. In this implementation that equality is broken — the value verified by the HMAC (the body bytes) and the value trusted for tenant routing (the `shop` header) are disjoint. Any request whose body+HMAC pair is valid for the app's secret will be accepted regardless of which shop's domain is claimed in the header, because the header is never part of the signable string.

### Impact Explanation
Multi-tenant Shopify apps commonly key session/token lookups and per-tenant business logic off the `shop` value provided by `WebhookMetadata#shop`. Because that field carries no cryptographic binding to the signed body, an attacker who can obtain a single valid `(raw_body, hmac)` pair for the shared app secret (for instance by triggering a webhook against their own, legitimately installed shop) can resend that exact body/HMAC to the app's webhook endpoint while forging the `shop` header to a victim shop's domain. The handler, trusting `data.shop`, will process attacker-controlled body content as if it originated from the victim tenant — this is a cross-tenant confusion/spoofing primitive at the library layer, matching the "Critical - cross-tenant access" impact class, since it lets one tenant's authenticated webhook traffic be relabeled as another tenant's data.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one valid signed webhook body for the shared app secret — trivially available to any merchant who installs the app on their own store and can trigger any webhook topic (e.g., an `orders/create` test webhook), since Shopify signs all webhooks for an app with the same `client_secret`-derived key regardless of shop. No access token, `client_secret`, or privileged account is required beyond normal use of the app as an installed merchant. This makes the likelihood realistic for any app relying on this gem's default `Registry.process`/`Request` behavior for tenant identification.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-signable material, or otherwise cryptographically bind the claimed `shop` header to the verified body (e.g., derive/verify the shop from a value embedded in the signed payload, or maintain a per-shop webhook secret/allowlist and reject webhooks whose header shop was not the one that requested/owns the corresponding signed body). At minimum, document and enforce that consuming apps must independently verify `data.shop` is one they have on record with a matching installed session before trusting it, rather than treating a passed HMAC check as proof of the shop identity.

### Proof of Concept
1. App installs webhook handling via `ShopifyAPI::Webhooks::Registry.process`.
2. Attacker installs the app on their own shop `attacker.myshopify.com` and triggers a webhook (or replays a webhook fired for a topic they can generate), capturing the raw body `B` and its `hmac-sha256` header `H`, both valid for the app's `api_secret_key`.
3. Attacker crafts a new HTTP request to the app's webhook endpoint with the same body `B` and `hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com` and, if desired, a different `x-shopify-webhook-id`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body without validating any relationship between `shop` and the signed content [7](#0-6) .
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because `to_signable_string` (`@raw_body`) and `hmac` (`H`) are unchanged and still match the app secret [8](#0-7) .
6. `handler.handle` is invoked with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: parsed_body_from_B, ...)`, so the app processes attacker-supplied body content attributed to `victim.myshopify.com`.

          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
