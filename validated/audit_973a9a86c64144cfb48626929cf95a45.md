### Title
LimitRanger deletion-timestamp short-circuit allows LimitRange max bypass on pod `resize` subresource updates - ([File: plugin/pkg/admission/limitranger/admission.go])

### Summary
`LimitRanger.runLimitFunc` unconditionally skips all LimitRange min/max enforcement whenever `a.GetOldObject()`'s `DeletionTimestamp` is non-nil, with no scoping to the field(s) actually being changed. Because `DefaultLimitRangerActions.SupportsAttributes` explicitly allows the pod `resize` subresource to reach `runLimitFunc` even on Update, a namespace user who can delete a pod and also patch its `resize` subresource can set oversized CPU/memory requests/limits during the pod's termination grace period, bypassing LimitRange enforcement entirely.

### Finding Description
`runLimitFunc` retrieves the old object and, if present, checks `oldAccessor.GetDeletionTimestamp() != nil`, returning `nil` (admit) before any LimitRange lookup or `limitFn` invocation occurs: [1](#0-0) 

For ordinary (non-subresource) Pod updates, `SupportsAttributes` returns `false` outright because container resources are immutable on a normal pod update, so this deletion-timestamp bypass has no effect there — it's blocked by pod-update immutability validation regardless of LimitRanger: [2](#0-1) 

However, `SupportsAttributes` explicitly carves out the `resize` subresource, letting it flow into `runLimitFunc` on Update: [3](#0-2) 

The `resize` subresource is a legitimate resource-mutation channel (`podResizeStrategy.PrepareForUpdate`/`ValidateUpdate` only preserve container resources, ResizePolicy, and pod-level resources across the update; validation forbids removing values but does not forbid values that violate LimitRange max, since that is LimitRanger's job): [4](#0-3) 

Because `ValidatePodResize`/`podResizeStrategy` do not check `oldPod.DeletionTimestamp`, a pod that is already marked for deletion (non-nil `DeletionTimestamp`, still present during its termination grace period) remains eligible for a resize update. When such a resize request reaches `runLimitFunc`, the `oldAccessor.GetDeletionTimestamp() != nil` check fires and the function returns `nil` immediately — completely skipping `GetLimitRanges` and `PodValidateLimitFunc`/`PodMutateLimitFunc`, so LimitRange min/max/ratio constraints are never applied to the resize payload.

### Impact Explanation
An attacker with only namespace-scoped `delete` on pods and `patch`/`update` on the pods `resize` subresource can commit container resource requests/limits that exceed the namespace's LimitRange maximums into a terminating pod's spec, persisting an invalid/protected field into etcd in violation of the namespace's declared LimitRange policy. This is an admission-completeness bypass (LimitRange scoped resource-limit bypass) rather than a cluster-wide privilege escalation, matching a "persisted invalid/protected field via admission bypass" bounty class scoped to the namespace's LimitRange enforcement.

### Likelihood Explanation
Preconditions are minimal and realistic: the attacker only needs ordinary namespace RBAC to `delete` their own pod and to `patch`/`update` its `resize` subresource — both are commonly granted to workload owners. No special race condition is required beyond issuing the resize request within the pod's termination grace period window (default 30s, or attacker-controlled via `gracePeriodSeconds` on the delete call), making this reliably reproducible, not merely a narrow timing race.

### Recommendation
Scope the deletion-timestamp short-circuit in `runLimitFunc` so it does not apply to the `resize` subresource (or any path that mutates `Resources`), e.g., skip the short-circuit when `a.GetSubresource() == "resize"`, or move the check so it only applies to full-object Create/Update paths where resource fields are otherwise immutable.

### Proof of Concept
Integration test (extending `test/integration/pods/pods_test.go` style, akin to `TestPodResize`):
1. Create a namespace with a `LimitRange` capping container CPU/memory to e.g. `500m`/`512Mi` max.
2. Create a pod with `NodeName` set and `Status.ContainerStatuses[].Resources` populated (to satisfy `isPodResizeRequestSupported`) and resources within limits.
3. Call `client.CoreV1().Pods(ns).Delete(ctx, pod.Name, metav1.DeleteOptions{GracePeriodSeconds: &grace})` with a non-zero grace period so the pod object persists with a non-nil `DeletionTimestamp`.
4. Immediately call `client.CoreV1().Pods(ns).UpdateResize(ctx, pod.Name, patchedPod, metav1.UpdateOptions{})` setting `Containers[0].Resources.Requests/Limits` above the LimitRange max (e.g. `4` CPU, `4Gi` memory).
5. Assert the resize call succeeds without error (`err == nil`) and that `GET` on the pod shows the oversized resources persisted — demonstrating LimitRange max enforcement was bypassed solely because the old object had a `DeletionTimestamp`.
6. Control case: repeat without first deleting the pod and assert the same resize is rejected with a LimitRange "maximum ... usage" forbidden error, confirming the bypass is specifically due to the deletion-timestamp short-circuit.

func (podResizeStrategy) PrepareForUpdate(ctx context.Context, obj, old runtime.Object) {
	newPod := obj.(*api.Pod)
	oldPod := old.(*api.Pod)

	*newPod = *dropNonResizeUpdates(newPod, oldPod)

	// When pod-level resources are set or updated via resize, apply defaulting
	// so any unmanaged resources (e.g. memory when only CPU existed) are complete and consistent.
	if utilfeature.DefaultFeatureGate.Enabled(features.PodLevelResourcesFixDefaulting) {
		if newPod.Spec.Resources == nil && oldPod.Spec.Resources != nil {
			// preserve existing PLR for requests from potentially PLR-unaware clients that completely dropped the field
			newPod.Spec.Resources = oldPod.Spec.Resources.DeepCopy()
		}

		if newPod.Spec.Resources != nil {
			podutil.DefaultPodLevelResources(newPod)
		}
	}

	podutil.DropDisabledPodFields(newPod, oldPod)
	updatePodGeneration(newPod, oldPod)
}

func (podResizeStrategy) ValidateUpdate(ctx context.Context, obj, old runtime.Object) field.ErrorList {
	newPod := obj.(*api.Pod)
	oldPod := old.(*api.Pod)
	opts := podutil.GetValidationOptionsFromPodSpecAndMeta(&newPod.Spec, &oldPod.Spec, &newPod.ObjectMeta, &oldPod.ObjectMeta)
	opts.ResourceIsPod = true
	return corevalidation.ValidatePodResize(newPod, oldPod, opts)
}
