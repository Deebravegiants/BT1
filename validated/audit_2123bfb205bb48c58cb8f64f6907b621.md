## Analysis

This report's bug class — LP tokens minted via `min(amount0·S/r0, amount1·S/r1)` when deposits are disproportionate to reserves, silently "donating" the excess and mispricing the pool — has a direct architectural analog in alt.fun's graduation LP-seeding path, and the analog is only *partially* mitigated. [1](#0-0) 

### Title
Rebalance swap budget cap lets a well-funded hostile pre-seed leave the graduated HyperSwap LP permanently mispriced away from curve-close - (File: `packages/contracts/src/Bonding.sol`)

### Summary
`Bonding._seedRebalancing` defends against V2's `min()` donation formula by swapping the pre-seeded pair back toward the curve-close ratio before depositing. But the rebalance swap is capped at `maxSwap = _swapBudget(inventory)`, where `inventory` is only *Bonding's own* token/LT balance for this graduation (bounded by `LP_RESERVE`/`ltFromPair`), not by whatever amount is required to actually reach the target ratio. When an attacker pre-seeds the pair with reserves large enough that the required rebalance swap exceeds this budget, the swap is silently truncated, and `_routerDepositAndDispose` deposits into a pool that is still off the curve-close ratio — the exact "disproportionate deposit → mispriced/leaked value" failure mode from the referenced report, just occurring in the LP-seeding step instead of a generic `provide_liquidity` call.

### Finding Description
`_noFeeSwapInput` computes the no-fee swap input needed to hit the target ratio, then unconditionally truncates it to `maxSwap`: [2](#0-1) 

`maxSwap` is derived from Bonding's own inventory for this graduation, not from the size of the imbalance: [3](#0-2) 

The code's own comment on `_swapBudget` acknowledges the cap can bind for "catastrophic pre-seeds beyond our budget capacity" and explicitly accepts that outcome as "the alternative is bricking": [4](#0-3) 

When the cap binds, `_pairRebalance` still returns `true` (a non-zero, fee-quoted swap did execute) so `_seedRebalancing` does **not** fall back to `_seedDirectMint`; it proceeds straight to `_routerDepositAndDispose`, which deposits at whatever ratio the pool is left at post-swap: [5](#0-4) [6](#0-5) 

Because Bonding's LT/token inventory for a given graduation is capped (`ltFromPair` ≈ the ~$9K USD graduation threshold; `tokensForLP` ≤ `LP_RESERVE` = 250M), an attacker who pre-seeds the permissionless HyperSwap V2 pair (`factory.createPair` + `transfer` + `pair.mint`, as already described in the codebase's own threat model) with a sufficiently large LT or TOKEN reserve can force the required no-fee rebalance input past `maxSwap`. The swap then only partially closes the gap, and the router's `quote()`-based `addLiquidity` locks LP for `LPLock` at this residual off-ratio price — mispricing the pool away from curve close, exactly the accepted-impact class ("an LP seeded away from the curve close price").

The maintainers' own documentation confirms the automated regression coverage for this exact scenario ("wrong-opening-price... attacker-no-profit... properties are no longer enforced by automated tests") was removed: [7](#0-6) 

### Impact Explanation
A successful attack permanently mints the graduation LP (held by `LPLock`, which "has no withdraw path in v1") at a ratio that diverges from the true curve-close price. This is value leakage analogous to the referenced report: token/LT that should back the LP at the correct ratio is instead partially absorbed by the attacker's pre-existing (hostile) LP position under V2's `min()` formula for the *residual* imbalance the swap couldn't close, and the pool opens away from fair value — harming every future trader/LP who transacts against the mispriced pool until arbitrage (if it ever fully closes the larger gap) catches up. Given `LPLock` cannot rescue or rebalance after the fact, this mispricing is effectively permanent for the locked LP position.

### Likelihood Explanation
This requires a well-capitalized attacker to front-run `finalizeGraduation` between phase 1 (`_enterGraduating`) and phase 2, pre-seeding the HyperSwap pair with reserves large enough to exceed Bonding's own per-graduation inventory budget (bounded by ~$9K worth of LT and up to `LP_RESERVE` tokens). This is costly compared to the dust-preseed case the codebase already fully neutralizes, but is not capital-infeasible for a determined attacker targeting a specific high-value graduation, and — unlike the small-dust case — is not covered by any of the current automated invariant tests (`HostilePreSeed.t.sol` was removed).

### Recommendation
Cap `finalizeGraduation`'s tolerance for reserve imbalance rather than only capping the swap amount: if `_pairRebalance`'s swap is truncated by `maxSwap` before reaching the target ratio (i.e., the post-swap ratio still deviates from `tokensForLP/ltFromPair` by more than an acceptable bps threshold), fall back to `_seedDirectMint` (or another donation-bounded path) instead of proceeding to `_routerDepositAndDispose` at the still-skewed ratio, so that budget-capped rebalances can never lock LP away from curve close.

### Proof of Concept
1. Token nears graduation; `_enterGraduating` caches `tokensForLP`/`ltFromPair` (bounded by `LP_RESERVE` and the ~$9K USD trigger) and flips lifecycle to `Graduating`.
2. Before `finalizeGraduation` is called, attacker calls `factory.createPair(token, lt)` (permissionless), then transfers a very large LT balance (acquired externally, e.g., via `Zap`) and a modest TOKEN balance to the pair, and calls `pair.mint(attacker)` — establishing reserves whose ratio is far from `tokensForLP/ltFromPair` and whose absolute size is large relative to Bonding's own per-graduation inventory.
3. `finalizeGraduation` → `_seedUniswapV2Direct` → `_seedRebalancing` detects "Pool LT-rich" and calls `_pairRebalance` with `maxSwap = _swapBudget(tokenAddress.balanceOf(this))`, capped at 99% of Bonding's own token inventory (`packages/contracts/src/Bonding.sol:1333-1348`).
4. `_noFeeSwapInput` computes the theoretically required swap `s`, which exceeds `maxSwap` given the attacker's oversized LT reserve, so it is truncated to `maxSwap` (`packages/contracts/src/Bonding.sol:1507-1522`).
5. `_pairRebalance` executes the capped swap and returns `true` (non-zero, non-degenerate output), so `_seedRebalancing` proceeds to `_routerDepositAndDispose` instead of falling back to `_seedDirectMint`.
6. `_routerDepositAndDispose` deposits the remaining inventory via `router.addLiquidity(..., 1, 1, lpLock, ...)` at the still-skewed post-swap ratio, permanently locking `LPLock`'s LP at a price away from curve close.

## HyperSwap Pre-Seed Defense (Read This Before Touching `_seedUniswapV2Direct`)

The whole sub-system inside `_seedUniswapV2Direct` exists to defuse one specific attack class. It's the most subtle code in the package. Read this before touching any of the helpers (`_seedRebalancing`, `_pairRebalance`, `_routerDepositAndDispose`, `_noFeeSwapInput`).

### The exploit

A vanilla UniswapV2 pair is deployable by anyone: `factory.createPair(token, lt)` is permissionless, and after creation anyone can call `pair.mint(to)` against pre-transferred tokens. So between phase 1 (`_enterGraduating` flips lifecycle to `Graduating` and caches `tokensForLP / ltFromPair`) and phase 2 (`finalizeGraduation` mints LP via `pair.mint(lpLock)`), an attacker can:

1. Front-run by calling `factory.createPair(token, lt)` themselves
2. `transfer(pair, smallToken)` and `transfer(pair, smallLT)` at any ratio they choose
3. Call `pair.mint(attacker)` — they now own LP at a hostile reserve ratio

When our `pair.mint(lpLock)` runs in phase 2 against this non-empty pair, V2's mint formula picks up the existing reserves:

```
liquidity = min(amount0 · totalSupply / reserve0, amount1 · totalSupply / reserve1)
```

The `min(...)` arm whose denominator is bigger relative to its numerator wins, and the OTHER arm's "excess" deposit is donated pro-rata to existing LP holders — i.e. to the attacker. Two harms:

- **Wrong opening price.** Post-mint reserves are `(R_attacker + T_a, R_attacker + T_b)`, so the LP opens at `(R_a + T_a) / (R_b + T_b)`, NOT at the curve close `T_a / T_b`. A `$15` LT pre-seed at 50% off curve close opens the pool ~454 bps off.
- **LP capture.** The wasted-side excess goes to the attacker's LP claim. A `1 wei + 1 LT` pre-seed (~`$1` attack budget) captures ~34 bps of LP.

A cheaper variant skips step 3 entirely: `transfer(pair, dust) + pair.sync()` forces the stored reserves to the dust ratio without minting any LP, leaving the pair at `reserves > 0 && totalSupply == 0`. Regime 1 below covers both shapes by keying on supply rather than reserves.

    /// @dev Cap the rebalance swap at 99% of the available side's budget,
    ///      so the subsequent `addLiquidity` always has a non-zero amount
    ///      of BOTH sides to deposit. Without this, an extreme hostile
    ///      pre-seed (massively imbalanced reserves) drives the
    ///      unconstrained `_noFeeSwapInput` past our per-side budget,
    ///      `_pairRebalance` clamps to the full budget, and the swap
    ///      consumes 100% of one side. `_routerDepositAndDispose` then
    ///      skips `addLiquidity` (`remToken == 0` or `remLT == 0`),
    ///      `finalizeGraduation` returns `liquidity = 0`, and
    ///      `LPLock.recordLock(...)` records a zero-sized lock — the
    ///      attacker's pre-existing LP becomes 100% of the pool. Reserving
    ///      1% guarantees the deposit leg always lands AND mints non-zero
    ///      LP at the post-swap ratio. The 1% comes off the swap, not the
    ///      deposit — for any realistic pre-seed `s_unconstrained` is
    ///      orders of magnitude below `maxSwap`, so the cap doesn't bind
    ///      and behaviour is unchanged. It only kicks in for catastrophic
    ///      pre-seeds beyond our budget capacity, where the alternative
    ///      is bricking.
    function _swapBudget(
        uint256 budget
    ) internal pure returns (uint256) {
        return (budget * 99) / 100;
    }

    function _pairRebalance(
        RebalanceParams memory p
    ) internal returns (bool) {
        uint256 s = _noFeeSwapInput(p.reserveIn, p.reserveOut, p.targetN, p.targetD, p.maxSwap);
        if (s == 0) return false;

        // Quote from the pair so the output tracks its live fee; a value
        // derived from a stale fee rate would trip the pair's K-check.
        uint256 expectedOut = IUniswapV2Pair(p.pair).getAmountOut(s, p.tokenIn);
        if (expectedOut == 0) return false;

        IERC20(p.tokenIn).safeTransfer(p.pair, s);
        (uint256 amount0Out, uint256 amount1Out) = p.tokenInIs0 ? (uint256(0), expectedOut) : (expectedOut, uint256(0));
        IUniswapV2Pair(p.pair).swap(amount0Out, amount1Out, address(this), new bytes(0));
        return true;
    }

    function _noFeeSwapInput(
        uint256 reserveIn,
        uint256 reserveOut,
        uint256 targetN,
        uint256 targetD,
        uint256 maxSwap
    ) internal pure returns (uint256) {
        if (reserveIn == 0 || reserveOut == 0 || targetN == 0 || targetD == 0 || maxSwap == 0) {
            return 0;
        }
        uint256 product = Math.mulDiv(reserveIn * reserveOut, targetN, targetD);
        uint256 newIn = Math.sqrt(product);
        if (newIn <= reserveIn) return 0;
        uint256 s = newIn - reserveIn;
        return s > maxSwap ? maxSwap : s;
    }
