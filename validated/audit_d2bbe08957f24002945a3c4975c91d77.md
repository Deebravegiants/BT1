### Title
Webhook `shop-domain` and `topic` headers are trusted while unsigned, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC that `Utils::HmacValidator.validate` checks in `Webhooks::Registry.process` covers exclusively `@raw_body`. The `shop`, `topic`, `api_version`, and `webhook_id` values are read straight from HTTP headers and are never part of the signed material, yet they are trusted as the tenant/routing identity passed into the app's `WebhookHandler#handle`.

### Finding Description
`Webhooks::Request#to_signable_string` is defined as: [1](#0-0) 
which returns only `@raw_body`. `Webhooks::Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all derived from HTTP headers, not from the signed body: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it against `verifiable_query.hmac`: [3](#0-2) 

`Webhooks::Registry.process` validates the HMAC and then immediately trusts `request.topic` and `request.shop` (unsigned headers) to route to a handler and construct the `WebhookMetadata` passed into application logic: [4](#0-3) [5](#0-4) 

The identity binding that should hold is: `hmac == HMAC(secret, shop || topic || body)`, i.e., the tenant (`shop`) and event type (`topic`) the app acts on should be covered by the same HMAC that authenticates the payload. Instead the code only enforces `hmac == HMAC(secret, body)`, leaving `shop` and `topic` as attacker-controlled, unauthenticated headers that get bound to the body only by the caller's assertion, not by the signature.

Because a single `client_secret`/`api_secret_key` is shared across every merchant that installs the app, any user who can install the app on their own store (an "unprivileged internet user" with respect to *other* merchants' data) receives real Shopify webhooks with a valid HMAC computed over their own webhook body. That `(body, hmac)` pair remains valid for **any** `shop-domain` and `topic` header combination, because those headers never entered the signable string.

### Impact Explanation
This breaks the tenant/topic binding without needing the app's `client_secret`, an access token, or a leaked credential — the attacker only needs one legitimately-delivered webhook to their own store (which any developer can obtain by installing the target app on a shop they control). They can then replay the identical `raw_body` + `hmac` while setting `shop-domain` to a victim shop and/or `topic` to a different, more sensitive topic (e.g. `shop/redact`, `customers/data_request`, or any topic the app registered a sensitive handler for). `Registry.process` will accept the HMAC as valid and dispatch `WebhookMetadata` claiming the victim shop/topic to the app's handler, producing cross-tenant data injection/confusion in whatever downstream logic (billing, redaction, order sync, uninstall handling, etc.) keys off `data.shop` or `data.topic`. This matches the Critical bucket of "cross-tenant access" since the shop identity used by the handler is not the shop that actually produced the signed bytes.

### Likelihood Explanation
Low-to-moderate effort, no privileged material required: the attacker needs a developer/partner account and a store where they install the target app (a normal, unprivileged action), capture one webhook delivery, and then send a forged HTTP request directly to the app's webhook endpoint with modified `shop-domain`/`topic` headers but the original body and HMAC. The gem does nothing to prevent this because the validation function only signs body bytes, as confirmed in `hmac_validator.rb` and `request.rb`.

### Recommendation
Include `shop-domain`, `topic`, and ideally `api_version`/`webhook_id` in the signable string used for HMAC verification (or otherwise cryptographically bind the header values to the body before comparing), so that an attacker cannot substitute the tenant/topic while replaying a validly-signed body. Alternatively, cross-check the delivered `shop` against a shop known to have an active webhook registration/session before dispatching to the handler.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a normal, unprivileged installation) and triggers a webhook, e.g. `orders/create`, capturing the real HTTP request Shopify sends to the app's webhook endpoint, including body `B` and header `X-Shopify-Hmac-Sha256: H`.
2. `H = HMAC-SHA256(client_secret, B)` — verified only against `B` per: [1](#0-0) 
3. Attacker crafts a new request to the same webhook endpoint with the same body `B` and the same `hmac-sha256: H` header, but sets `shop-domain: victim-shop.myshopify.com` and, if useful, changes `topic` to a topic the app has a sensitive handler for.
4. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and finds it equal to `H`, passing validation: [6](#0-5) 
5. The request proceeds to `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))`, delivering forged `shop`/`topic` values to the app's business logic under the guise of a validly-signed webhook: [7](#0-6)
