This confirms the asymmetry: in `AuthQuery#to_signable_string` (`lib/shopify_api/auth/oauth/auth_query.rb:33-43`), every identity-relevant field (`shop`, `code`, `host`, `state`, `timestamp`) is included in the HMAC-signed string. In contrast, `Webhooks::Request#to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`) returns only `@raw_body`, while `shop`, `topic`, and `webhook_id` are read directly from unsigned HTTP headers and passed straight into the dispatched `WebhookMetadata` in `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`).

### Title
Webhook shop/topic identity fields are not covered by HMAC, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop` (tenant identifier) and `topic` (dispatch key) come from HTTP headers that are never included in the signed string. `Registry.process` validates only the body's HMAC and then trusts the unsigned headers to select the handler and populate `WebhookMetadata`, breaking the binding between "HMAC-authenticated bytes" and "shop/topic the app acts on."

### Finding Description
`Webhooks::Registry.process` validates a webhook by calling `Utils::HmacValidator.validate(request)` [1](#0-0) , which in turn calls `validate_signature`, comparing the received HMAC against a signature computed over `verifiable_query.to_signable_string` [2](#0-1) .

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` — it does not include the `shop`, `topic`, `webhook_id`, or `api_version` values [3](#0-2) . Those four fields are instead parsed straight out of attacker-controlled/transport-controlled HTTP headers with no cryptographic binding to the HMAC at all [4](#0-3) .

After HMAC validation succeeds, `Registry.process` uses the unsigned `request.topic` to select a handler from `@registry`, and forwards the unsigned `request.shop`, `request.topic`, and `request.webhook_id` directly into `WebhookMetadata` passed to the app's handler [1](#0-0) .

This is exactly the pattern called out in the report as an analog bug class: "a field acted on but not covered by the HMAC." Compare with `Auth::Oauth::AuthQuery`, where `shop` is explicitly folded into the signed string alongside `code`, `host`, `state`, and `timestamp` [5](#0-4) , so the OAuth callback path correctly binds the shop identity to the HMAC while the webhook path does not.

Any party capable of producing (or capturing) one valid `(raw_body, hmac)` pair signed with the app's `api_secret_key` for *any* topic/shop combination (e.g., a webhook Shopify legitimately delivers to the attacker's own store/app installation, since the attacker controls their own shop's webhook body content) can replay that exact body+HMAC to the target app's webhook endpoint while substituting the `shopify-shop-domain` and `shopify-topic` headers with any values of their choosing. `HmacValidator.validate` will still pass because it only checks the body bytes, and `Registry.process` will dispatch to whatever handler is registered for the forged topic, delivering attacker-chosen body content tagged as originating from an arbitrary victim shop.

### Impact Explanation
This breaks the shop/topic-to-HMAC identity binding relied upon by apps built on this gem: a handler for `orders/create`, `customers/redact`, etc. can be invoked with `WebhookMetadata#shop` set to any shop domain the attacker chooses, while the body content is whatever the attacker was able to get validly signed (from their own store's real webhook traffic). Apps that use `WebhookMetadata#shop` to look up per-tenant records, credentials, or to route mandatory GDPR webhooks (`shop/redact`, `customers/redact`, `customers/data_request`) can be tricked into acting on/for the wrong tenant — a cross-tenant data integrity and authorization issue.

### Likelihood Explanation
Exploitation requires only that the attacker be able to obtain one legitimately HMAC-signed webhook body from Shopify — trivially achievable by anyone who owns/operates a Shopify development store or app installation and subscribes their own store to a webhook topic. No access to the app's `api_secret_key`, access tokens, or privileged accounts is required; only the ability to send HTTP requests to the target app's public webhook endpoint with forged headers, which is exactly the "unprivileged internet user" scenario.

### Recommendation
Include `shop`, `topic`, and any other fields the app dispatches or trusts (e.g., `webhook_id`) in the HMAC-signable string for webhooks, mirroring what `AuthQuery#to_signable_string` does for OAuth callbacks — or, since Shopify's webhook HMAC scheme is header/body-based and not user-modifiable, have `Webhooks::Request`/`Registry` treat `shop`/`topic` headers as untrusted metadata and require the host application to cross-check them against out-of-band knowledge (e.g., the shop domain from an active session for that install) before acting on webhook content, rather than passing them straight into `WebhookMetadata` as authenticated identifiers.

### Proof of Concept
1. Attacker installs the target app on their own (attacker-controlled) Shopify development store, so the app subscribes attacker's store to some webhook topic (or attacker triggers a webhook by performing an action on their own store).
2. Shopify delivers a legitimately-signed webhook to the app's endpoint: headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid HMAC over raw_body>`, with `raw_body` containing attacker-crafted (but Shopify-accepted) order JSON.
3. Attacker captures this `(raw_body, hmac)` pair.
4. Attacker replays the exact same `raw_body` and `hmac` to the target app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com` and/or `x-shopify-topic` to `shop/redact` or another registered topic.
5. `Utils::HmacValidator.validate` in `hmac_validator.rb:26-31` recomputes the HMAC over `raw_body` only and finds it matches — validation succeeds.
6. `Registry.process` (`registry.rb:188-200`) dispatches based on the forged `topic` header and builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"`, even though that data never came from Shopify for that shop, letting the app's handler act on forged victim-tenant identity.
