## Title
Webhook shop-domain header spoofing due to HMAC binding only the raw body, not `shop`/`topic`/`webhook_id` headers - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating that the raw request body matches the HMAC signature. The `shop` (and `topic`/`webhook_id`/`api_version`) values that identify *which tenant* the webhook belongs to are read from unsigned HTTP headers and handed to the app's handler as trusted tenant identifiers, even though those header values are never included in the signable content.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw JSON body: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all parsed straight from HTTP headers that are never part of that signable string: [2](#0-1) 

`Registry.process` validates the HMAC of the whole request (which, per the above, only actually covers `@raw_body`) and then forwards `request.shop` directly to the handler as the authenticated tenant identifier, without any additional cross-check that this shop is the one whose secret produced the signature: [3](#0-2) 

The identity binding that should hold is: `shop header value == shop that generated this HMAC-signed payload`. Because the header is excluded from `to_signable_string`, that equality is never checked — any raw body + valid HMAC pair (which a merchant who has legitimately installed the app on their own shop can trivially produce, since the app's `api_secret_key`/webhook secret is shared across every install of the same app, not shop-specific) can be replayed against the webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header claiming to be a different, victim shop. The library will accept it as authentic and pass the attacker-chosen `shop` value on to the app's registered handler.

### Impact Explanation
This breaks the tenant-identity binding at the core of multi-tenant Shopify apps. A host application that (as documented/intended) uses `WebhookMetadata#shop` to route the payload to per-shop data (e.g., to select which shop's database record to update, or which shop's data the payload body should overwrite) can be tricked into applying attacker-supplied webhook data under a different, victim shop's identity — i.e., cross-tenant access/write, purely through the gem's own webhook verification API (`Registry.process` / `Utils::HmacValidator.validate`), not through host-app misuse of undocumented behavior.

### Likelihood Explanation
The webhook receiving endpoint is, by design, a public HTTP endpoint. The only prerequisite for an attacker is having legitimate access to their **own** installed instance of the app (a normal, unprivileged usage scenario — no leaked credentials, no `api_secret_key`, no TLS interception required) so they can capture a real `raw_body + hmac` pair delivered to their own store, then replay it with a forged `shop-domain`/`x-shopify-shop-domain` header value.

### Recommendation
Include the identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the value that is HMAC-verified, or otherwise cryptographically bind the shop identity to the payload (e.g., verify the `shop` header against the session/shop associated with the `access_token`/secret that generated the signature) before handing `WebhookMetadata` to the registered handler.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; trigger any webhook event (e.g. update a product) to receive a real webhook POST with a body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC(api_secret_key, B)`.
2. Replay a POST to the app's webhook endpoint with the exact same body `B` and header `X-Shopify-Hmac-Sha256: H`, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers, `Utils::HmacValidator.validate(request)` succeeds because it only checks `B` against `H` [4](#0-3) 
, and `Registry.process` invokes the handler with `shop: "victim.myshopify.com"` even though the payload actually originated from the attacker's own store.
