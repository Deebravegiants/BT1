## Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authenticated for a given shop once `Utils::HmacValidator.validate(request)` succeeds, but the HMAC signature only covers the raw request body, never the `shop-domain` header. Because the app's `api_secret_key` used to sign webhooks is shared across every shop that has the app installed (it is not per-shop), any tenant that can trigger a webhook for their own store can capture a validly-signed `(body, hmac)` pair and replay it against the app's webhook endpoint with the `shop-domain` header rewritten to point at a different, victim shop. The signature check still passes, and the handler receives attacker-controlled `shop`/`topic`/`webhook_id`/`api_version` metadata that it will treat as authenticated.

### Finding Description
`ShopifyAPI::Webhooks::Request#hmac` reads the `hmac-sha256` header, and `#to_signable_string` returns only the raw body bytes: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read straight from unauthenticated HTTP headers, with no cryptographic binding to the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the raw body), using the app's single shared secret (`Context.api_secret_key`, with fallback to `Context.old_api_secret_key`): [3](#0-2) 

`Registry.process` relies solely on this body-only check before dispatching to the app's handler with the header-derived (unauthenticated) `shop`, `topic`, `api_version`, and `webhook_id`: [4](#0-3) 

The identity binding that should hold is: `shop authenticated by HMAC == shop the handler attributes the webhook to`. Because the HMAC never covers the `shop-domain` header, this equality is not actually enforced — only `hmac-validity-of-body == true` is enforced, independent of which shop's header is attached.

### Impact Explanation
The `api_secret_key` (and `old_api_secret_key`) is the same value for all shops that install a given app - it is an app-level secret, not a per-shop secret. Consequently, a merchant/attacker who installs the app on their own store (an "unprivileged internet user" relative to other tenants of the same app) can obtain legitimately HMAC-signed webhook bodies from Shopify for their own store, then replay the exact `(body, hmac)` bytes to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` still succeeds because it never inspects the header, so `Registry.process` calls the app's webhook handler believing the payload was authenticated for the victim shop. Depending on how the host application persists/acts on webhook data (e.g., updating order/customer/inventory records keyed by `data.shop`), this enables cross-tenant data injection/corruption for other merchants using the same app — a cross-tenant access break.

### Likelihood Explanation
Exploitation requires only that the attacker be an app user (install the app on any shop, including a trial/free shop) and be able to trigger at least one real webhook delivery for their own store (trivial - e.g., create an order, update a product) to capture a valid `(body, hmac)` pair, then send a forged HTTP request to the app's public webhook endpoint with a different `shop-domain` header. No access to `api_secret_key`, tokens, or the victim's credentials is required, making this straightforward for any user with app access.

### Recommendation
Bind the shop identity into the value that is actually verified. Options:
- Include the `shop-domain` (and ideally `topic`) header value inside the string that is HMAC-verified (`to_signable_string`), rejecting the request if the header used for dispatch doesn't match what was signed.
- Alternatively/additionally, have `Registry.process` derive the authoritative shop from data embedded in the verified body (where available) rather than trusting the unauthenticated header, or require host applications to cross-check the header-derived shop against an independently known installed-shop list before acting on the payload.
- Document prominently that `shop-domain`/`topic`/`webhook_id`/`api_version` headers are NOT covered by the HMAC and must not be trusted as authenticated identifiers by consuming applications without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook (e.g., updates a product) and captures the real request Shopify sends to the app's webhook endpoint, including body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the app's shared `api_secret_key`).
3. Attacker replays a new HTTP POST to the same webhook endpoint with the identical body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Utils::HmacValidator.validate(request)` returns `true` (it only checks `B` against `H`).
5. `ShopifyAPI::Webhooks::Registry.process` dispatches to the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ..., body: parsed(B))`, and the host application processes attacker-controlled data as if it originated from the victim shop.
