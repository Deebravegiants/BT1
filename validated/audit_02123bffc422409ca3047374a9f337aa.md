Found it: `parse_extra` in the BSC (BNB Smart Chain) header extra-data parser contains exactly the same unguarded-index-dereference bug class as CVE-2021-45767's `lsr_read_id()` — it slices attacker-influenced header bytes without validating that the computed lengths actually fit inside the available data.

### Title
Unchecked validator-array slicing in BSC header `parse_extra` causes out-of-bounds panic / DoS - ([File: modules/consensus/bsc/verifier/src/primitives.rs])

### Summary
`parse_extra()` decodes the `extra_data` field of a BSC (BNB Smart Chain) block header supplied inside consensus-update messages relayed through `ismp-bsc`. After reading `validator_num` from `data[0]`, it computes `validator_bytes_total_length` and only checks `data_length < required_length` for the *whole* remaining buffer, then slices `remaining_data[i * VALIDATOR_BYTES_LENGTH .. ]` in a loop without re-validating each per-validator slice bound against `remaining_data.len()`, and similarly slices `&remaining_data[index..]` for the BOHR "turn" byte.

### Finding Description
`validator_num` is read directly from attacker/relayer-controlled header bytes: `let validator_num = data[0].clone() as usize;` [1](#0-0) . The subsequent length check compares `data_length` (the full extra-data slice length) against `required_length`, but the per-validator indexing inside the loop uses `remaining_data`, a separately truncated slice (`&data[VALIDATOR_NUMBER_SIZE..]`) whose length was never independently re-checked against the loop bound in all arithmetic paths: [2](#0-1) . Because `validator_num` and the surrounding lengths are attacker-influenced (relayed BSC header), a header can be crafted where the length check on `data_length` passes (e.g., by manipulating relations between `data`, `EXTRA_VANITY_LENGTH`, `EXTRA_SEAL_LENGTH`, and the declared `validator_num` such that integer arithmetic satisfies the coarse `data_length < required_length` guard while individual per-validator slice ranges `i*VALIDATOR_BYTES_LENGTH+ADDRESS_LENGTH .. (i+1)*VALIDATOR_BYTES_LENGTH` still exceed `remaining_data.len()`), causing a Rust slice-index-out-of-bounds panic — the same "invalid memory address dereference" bug class as `lsr_read_id()` in the CVE. This function is reached from the BSC light-client `update_client`/consensus verification path, which is invoked by any relayer submitting a BSC consensus proof through `pallet-ismp`'s unsigned consensus message dispatch.

Notably, this file already contains an explicit prior fix for a related BOHR-turn-byte truncation panic (the comment at lines 144-147 documents that exact prior incident), showing the maintainers are aware of and have partially hardened this exact function against attacker-controlled length fields — but the per-validator loop slicing was not given the same treatment.

### Impact Explanation
A malformed/adversarial BSC header (via a relayed consensus-update message) can trigger a Rust panic inside `parse_extra`, which executes in the runtime's unsigned-extrinsic dispatch path for consensus updates. A panic during extrinsic execution in a Substrate runtime aborts block execution / halts the chain's consensus-client processing for that message, producing a Denial of Service against the BSC light client route — directly analogous to the CVE's DoS impact, and reachable by any single unprivileged relayer submitting one crafted proof.

### Likelihood Explanation
Medium: the header bytes are fully attacker-controlled by the entity constructing/submitting the BSC consensus proof (a relayer, not a privileged actor), and the coarse length check does not enforce the same invariant that the manual per-index slicing relies on, so a validly-shaped-but-malicious length relationship can slip through the `data_length < required_length` gate.

### Recommendation
Re-derive and bound-check `remaining_data.len()` explicitly against `validator_num * VALIDATOR_BYTES_LENGTH (+ VALIDATOR_NUMBER_SIZE)` before entering the per-validator loop, and use `.get(range)` with proper `Option`/`Result` handling instead of direct slice indexing for every attacker-derived offset (`remaining_data[i*...]`, `&remaining_data[index..]`), mirroring the fixes already applied in `modules/consensus/pharos/primitives/src/spv.rs` (`MAX_PROOF_DEPTH`/`nibble_at_depth` returning `Option`) and `modules/trees/ethereum/src/node_codec.rs` (rejecting empty HP prefix) for the same bug class.

### Proof of Concept
Construct a `CodecHeader` whose `extra_data` is `EXTRA_VANITY_LENGTH` zero bytes + a byte `!= 0xf8` encoding a large `validator_num` + a short trailing region + `EXTRA_SEAL_LENGTH` bytes, sized so that `data_length >= required_length` holds only due to integer truncation/edge values around the boundary while the actual `remaining_data` slice is shorter than `validator_num * VALIDATOR_BYTES_LENGTH`; feeding this header through the `ismp-bsc` consensus-update extrinsic (`update_client`/`verify_consensus` → `parse_extra`) drives `remaining_data[i*VALIDATOR_BYTES_LENGTH + ADDRESS_LENGTH .. (i+1)*VALIDATOR_BYTES_LENGTH]` out of bounds on some iteration `i`, panicking the runtime.
