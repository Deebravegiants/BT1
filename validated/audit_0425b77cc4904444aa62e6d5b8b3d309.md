### Title
Unconstrained `EmporiumOperation.value`/`endpoint` in the zero-token "Min" proof path drains ETH stranded in `EmporiumUpgradeable` - (File: circuits/MainEVMCircuitMin.circom, contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
When `circomData.erc20TokenAddresses.length == 0` and the external action is the Emporium action, Hinkal routes to the trivial `MainEVMCircuitMin`/`formInputEmporiumMin` path, whose only public signals are `emporiumMessage`, `timeStamp`, and `calldataHash`. Because `circomData.erc20TokenAddresses` is empty, every balance-accounting loop in both `Hinkal.transact` and `EmporiumUpgradeable.runAction` iterates zero times, so the ops loop that actually moves ETH (`op.endpoint.call{value: op.value}(op.callData)`) executes with no accounting or revert path whatsoever, letting any unprivileged caller drain ETH already sitting in the Emporium contract to an arbitrary address.

### Finding Description
Broken equality: `address(emporium).balance_before == address(emporium).balance_after + amount_extracted_by_attacker` must hold across a `transact` call that does not legitimately withdraw Emporium's ETH; instead the attacker extracts the full pre-existing balance.

Path:
1. `Hinkal.transact` (`contracts/Hinkal.sol:30-168`) calls `hinkalHelper.performHinkalChecks`, which calls `CircomDataBuilder.formInputForCircom`. With `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, this returns `formInputEmporiumMin`'s 3-element vector (`emporiumMessage`, `timeStamp`, `calldataHash`) [1](#0-0) . This exactly matches the public inputs of `MainEVMCircuitMin`, whose only constraint is `message <== Poseidon(1)([messageSeed])` [2](#0-1) . No signal constrains any token, amount, nullifier, or op field — this proof requires no secret knowledge tied to any real UTXO, and any attacker can trivially generate a valid one (pick any `messageSeed`, compute Poseidon hash) as long as it matches an already-registered verifier for `(tokenNumber=0, nullifierAmount=0, outputAmount=0, HINKAL_EMPORIUM_ACTION_ID)`.
2. Because `circomData.erc20TokenAddresses` is empty:
   - In `Hinkal.transact`, `oldBalances`/`newBalances` arrays are empty, so the balance-diff/slippage/equality loop (lines 96-147) never executes — no check ties `balanceDif` to `amountChanges`/`utxoAmount`.
   - `_externalTransact` (`contracts/Hinkal.sol:234-261`) loops zero times, so no ETH is (or needs to be) transferred from Hinkal into Emporium for this call, but `IExternalActionV2.runAction` is still invoked unconditionally.
   - Inside `EmporiumUpgradeable.runAction` (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:76-160`), `balancesBefore`/`balancesAfter` are computed over the same empty `erc20TokenAddresses` array, so the post-loop balance-change/`revert BalanceChangeShouldBePositive()` guard (lines 132-151) also never executes.
   - However, the ops-execution loop (lines 91-118) is driven purely by `stack.ops` decoded from `externalActionMetadata` — completely independent of `erc20TokenAddresses`. With `signerAddress == address(0)` (skips EIP-712 signature check in `verifyWallet`, lines 302-349) and `op.invokeWallet == false`, execution falls to the stateless branch: `op.endpoint.call{value: op.value}(op.callData)` [3](#0-2) .
3. Attacker sets `op.value = address(emporium).balance` (any ETH left over from `receive()` at line 369) and `op.endpoint = attackerEOA`, `callData = ""`. This is a plain ETH transfer to an EOA, so it succeeds trivially, and there is no downstream check that examines Emporium's own balance at all in this call path.

Existing guards that fail to catch this: `dimensionsCheck` only validates array-length consistency, not that `tokenNumber == 0` implies no external ETH movement is permitted; `checkOnchainCreation` is irrelevant (no tokens); the balance/slippage equality in `Hinkal.transact` and the `BalanceChangeShouldBePositive` guard in `EmporiumUpgradeable.runAction` are both skipped because they iterate over the (attacker-chosen) empty `erc20TokenAddresses` array, even though the *ops* loop that moves real ETH still runs unconditionally.

### Impact Explanation
Any ETH balance resting in `EmporiumUpgradeable` (accumulated via its permissionless `receive()` function, from dust, refunds, or any prior operation) can be stolen outright by an unprivileged attacker to an address of their choosing, with zero cost beyond gas and generating a proof that requires no real secret. This is direct theft of protocol/user-adjacent funds held in a contract in the transaction path, repeatable every time Emporium accrues any ETH balance — matching "High: theft ... of protocol/relay fees" or, if depositor funds transiently pass through/rest in Emporium's balance during multi-step flows, potentially "Critical: direct theft of shielded or in-flight user funds."

### Likelihood Explanation
Preconditions are minimal and realistic: `EmporiumUpgradeable.receive()` is `external payable` with no access control [4](#0-3) , so ETH can land there via a stray transfer, a refunded op, or leftover dust from a legitimate withdrawal path. The attacker needs no privileged role, no victim key, and no real nullifier/UTXO — only a registered verifier for the `(0,0,0,HINKAL_EMPORIUM_ACTION_ID)` dimension tuple (which the "Min" proof system is explicitly designed to support, per `formInputEmporiumMin`). The attack is repeatable any time Emporium's balance is nonzero.

### Recommendation
In `EmporiumUpgradeable.runAction`, always account for ETH (e.g., treat `address(0)`/native balance as an implicit token even when `erc20TokenAddresses` is empty), and enforce that the sum of `op.value` across all ops does not exceed funds intentionally routed into Emporium for this specific call (not the contract's total balance). Alternatively/additionally, disallow the zero-token "Min" Emporium path from executing any op with `op.value > 0` or with `invokeWallet == false` and a `value`-bearing call to an arbitrary `endpoint`, since such ops have no corresponding balance/slippage verification when `tokenNumber == 0`.

### Proof of Concept

2. Register a verifier for `buildVerifierId(Dimensions({tokenNumber:0, nullifierAmount:0, outputAmount:0}), HINKAL_EMPORIUM_ACTION_ID)` pointing at the deployed `MainEVMCircuitMin` verifier (as the protocol must already do to support this Emporium-Min path).
3. Construct `CircomData` with `erc20TokenAddresses = []`, `amountChanges = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionData.externalActionMetadata = abi.encode(EmporiumStack({signerAddress: address(0), ops: [EmporiumOperation({endpoint: attackerEOA, invokeWallet: false, value: uint128(address(emporium).balance), callData: ""})], ...}))`, and `relay` set (or `originalSender == msg.sender`) to satisfy `performHinkalChecks`.

5. Call `Hinkal.transact(a, b, c, dimensions, circomData)` from `attackerEOA` (or via relay).
6. Assert `attackerEOA.balance` increased by exactly `1 ether` and `address(emporium).balance == 0`, while no nullifiers were inserted and no UTXOs were created — proving value left the protocol with zero backing.
