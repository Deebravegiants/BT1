### Title
Residual input-token dust in `ExternalActionSwap`/`LifiExternalAction` can be captured by a later user via unbounded router calldata - (File: contracts/external-actions/swaps/ExternalActionSwap.sol, contracts/external-actions/swaps/LifiExternalAction.sol)

### Summary
`ExternalActionSwap.swap()` never verifies that the router actually consumed the exact `inputAmount` it computed, and it never sweeps back any unspent `inputToken` balance to the caller (Hinkal). Combined with `LifiExternalAction.callRouter()` granting the router an **unlimited** approval and letting the router pull tokens according to fully attacker-controlled calldata (`externalActionMetadata`), any input-token dust left in the contract from a prior transaction can be redirected into a later, unrelated user's swap — letting that user mint an output UTXO backed partly by funds that were never debited from their own deposit.

### Finding Description
`swap()` computes `inputAmount = uint256(-deltaAmounts[0])` (minus flat fee if applicable) and passes it to `callRouter` [1](#0-0) , but `inputAmount` is only used by `LifiExternalAction.callRouter` to decide the native-vs-ERC20 branch — it is never passed into the router call itself, and the router is approved for `type(uint256).max` via `approveUnlimited` [2](#0-1) [3](#0-2) . The actual amount pulled by the router is dictated entirely by `externalActionMetadata`, which is user-supplied calldata forwarded via `_externalTransact` from `Hinkal.transact()` [4](#0-3) .

After the swap, only `outputToken`'s balance delta is measured (`getERC20OrETHBalance(outputToken)` before/after) to compute `swappedAmount` [2](#0-1) . There is no equivalent check that `inputToken`'s balance decreased by exactly `inputAmount`, and no `else`/sweep path returns any leftover `inputToken` back to Hinkal, unlike the `Emporium` external action, which explicitly reconciles and forwards the *entire* balance delta for every token in `handleOut` [5](#0-4) .

The outer invariant check in `Hinkal.transact()` only verifies that **Hinkal's own** balance changes match the declared `amountChanges`/created UTXOs [6](#0-5) ; it has no visibility into whether the external action contract itself ended a transaction holding excess `inputToken` — this exactly parallels the referenced GMX report's invariant ("contract should be cleared of token balances after every action") being silently violated at the external-action layer instead of the vault layer.

Because the router's unlimited allowance is not amount-scoped per transaction, if any prior swap leaves `inputToken` dust in the `ExternalActionSwap` contract (e.g., a router partial fill, rounding, or fee-path leftover), a subsequent user can submit `externalActionMetadata` that instructs the router to pull more of `inputToken` than the amount they personally had debited via `deltaAmounts[0]`, using the pre-existing unlimited approval and the contract's residual balance. The resulting `swappedAmount`/output UTXO would then be inflated beyond what the attacker actually deposited, while Hinkal's own balance-equation check passes because it only verifies the output side.

### Impact Explanation
This allows a user to mint an off-chain UTXO backed by value they never contributed, effectively appropriating funds that were "stuck" in the external-action contract — this is theft of in-flight/temporarily-frozen protocol funds through an external action a signer/prover never fully authorized for that beneficiary. It maps to Critical/High impact categories: unauthorized movement of assets and effective double-counting of value in the balance equation the protocol relies on for correctness.

### Likelihood Explanation
Exploitation requires a pre-existing residual balance of `inputToken` in the `ExternalActionSwap`/`LifiExternalAction` contract. Such dust can arise from ordinary LI.FI router behavior (partial fills, refunds, rounding) over the contract's operational lifetime, and once present, any user can craft `externalActionMetadata` to sweep it into their own swap — no privileged role, relayer collusion, or oracle assumption is required, only a crafted call to `Hinkal.transact()` with attacker-chosen router calldata.

### Recommendation
- In `ExternalActionSwap.swap()` / `LifiExternalAction.callRouter()`, snapshot and enforce that `inputToken` balance decreases by exactly `inputAmount` (revert otherwise), rather than only checking `outputToken`'s delta.
- Do not grant unlimited allowance to the router; approve only the exact `inputAmount` needed per call, and reset to zero afterward.
- Sweep back any residual `inputToken` balance to `msg.sender` (Hinkal) at the end of `swap()`, mirroring the reconciliation pattern already used in `EmporiumUpgradeable.handleOut`.

### Proof of Concept
1. A swap transaction executes with attacker-supplied `externalActionMetadata` that causes the LI.FI router to leave `D` amount of `inputToken` unspent inside `LifiExternalAction` (e.g., via a partial-fill route or refund behavior of the underlying DEX aggregator) — `swap()` does not detect or reclaim this, since it only measures `outputToken` deltas.
2. A second user (attacker) calls `Hinkal.transact()` with `deltaAmounts[0] = -X` (only depositing `X` of `inputToken`) but supplies `externalActionMetadata` whose calldata instructs the router to pull `X + D` of `inputToken` from `LifiExternalAction` (permitted by the pre-existing `type(uint256).max` approval from `approveUnlimited`).
3. `callRouter` returns `swappedAmount` computed purely from `outputToken` balance delta, which now reflects swapping `X + D`, not just `X`.
4. `swap()` creates a UTXO of `amountToSendToHinkal` derived from this inflated `swappedAmount`, and `Hinkal.transact()`'s balance-equation check on the output token passes because Hinkal's own balance did increase by that (inflated) amount — the attacker has captured the value `D` that belonged to no one but was administratively "lost" in the external action contract.

    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }

    ///@param circomData circom data.
    function _externalTransact(
        CircomData calldata circomData
    ) internal returns (UTXO[] memory) {
        require(
            externalActionMap[circomData.externalActionData.externalActionId] ==
                circomData.externalActionData.externalAddress &&
                circomData.externalActionData.externalAddress != address(0),
            "Unknown externalAddress"
        );

        int256[] memory deltaAmountChanges = new int256[](
            circomData.erc20TokenAddresses.length
        );
        for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++) {
            deltaAmountChanges[i] = _calculateDeltaAmount(circomData, i);
            if (deltaAmountChanges[i] < 0) {
                transferERC20TokenOrETH(
                    circomData.erc20TokenAddresses[i],
                    circomData.externalActionData.externalAddress,
                    uint256(-deltaAmountChanges[i])
                );
            }
        }

        return
            IExternalActionV2(circomData.externalActionData.externalAddress)
                .runAction(circomData, deltaAmountChanges);
    }
