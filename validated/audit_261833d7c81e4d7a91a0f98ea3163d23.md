Based on my research, I found a strong analog in `HyperFungibleToken.sol` (and its variants: `HyperFungibleTokenUpgradeable.sol`, `WrappedHyperFungibleToken.sol`, `WrappedHyperFungibleTokenUpgradeable.sol`) that matches the bug class from the report: a governance toggle (`removeChain`) can disable a route that in-flight, already-committed cross-chain operations still depend on, causing them to fail after value has already been irrevocably removed from the source side.

### Title
Owner-triggered `removeChain` can permanently strand in-flight burned tokens whose destination request is rejected on arrival - (File: sdk/packages/core/contracts/apps/HyperFungibleToken.sol)

### Summary
`removeChain` deletes a destination chain's peer mapping from `_supportedChains` at any time, with no check for whether outstanding cross-chain transfers targeting or originating from that chain are still in flight. Because `send()` burns tokens *before* the ISMP message is delivered and confirmed, and `onAccept` (the delivery hook) validates the request's source against the same `_supportedChains` mapping, a user's tokens can be burned on the source chain via a legitimate `send()` call, and then rejected on the destination chain if the owner calls `removeChain` for that route before the message is delivered — mirroring the reported Morpho-Aave issue where toggling a collateral flag doesn't account for positions/state that already depend on the old configuration.

### Finding Description
`addChain`/`removeChain` mutate `_supportedChains[chainId]` unconditionally: [1](#0-0) 

`send()` immediately burns the caller's tokens and only afterward builds/dispatches the cross-chain POST request via `_buildDispatchPost`, which reads the *current* `_supportedChains` mapping at call time: [2](#0-1) [3](#0-2) 

Because relayers deliver ISMP requests to the destination host asynchronously (subject to consensus finality and challenge periods, as documented in `handlers.rs` / `HandlerV2.sol`), there is a window between the burn on the source chain and the eventual `onAccept` call on the destination chain. If the contract owner calls `removeChain` on either the source (to prevent further sends) or, critically, if the destination contract's `onAccept` logic validates the inbound `request.source` against its own `_supportedChains`/peer mapping (mirrored in `HyperApp.sol` and the equivalent `Wrapped*` contracts), messages already burned and in flight will be rejected once the chain is de-registered — with no corresponding mint/refund path, since the burn already occurred atomically inside `send()` with no escrow or reversible step.

This is structurally the same bug class as the reported Morpho issue: a binary on/off governance toggle is applied globally and retroactively, without accounting for state (burned balances, in-flight requests) that was created under the old configuration. Just as disabling collateral status on Aave doesn't protect existing Morpho positions built on top of it, disabling a chain route here doesn't protect tokens already burned and committed to that route.

### Impact Explanation
This causes permanent, unbacked loss of user funds: tokens are burned on the source chain (supply reduced), but if the destination chain rejects the incoming request due to `removeChain` having been called in the interim, no mint occurs on the destination and no refund path exists in the burn/mint (`HyperFungibleToken`) design. This is a direct loss-of-funds condition reachable by any ordinary user performing a `send()`, contingent only on the owner's `removeChain` timing — which does not require malicious intent, just a routine operational chain deprecation performed while transfers are in flight (a foreseeable operational scenario, similar to the report's scenario of disabling a collateral asset that's already in active use).

### Likelihood Explanation
Likelihood is moderate: it requires the owner to call `removeChain` for a route while user transfers are still in the delivery pipeline (consensus finality + challenge period + relayer delivery latency), which is a realistic and even expected operational event (chain deprecation, migration, security incident response) rather than an edge case. The mismatch between "burn is instant/irreversible" and "delivery is asynchronous and subject to a since-changed on-chain config" is a systemic design gap, not a rare race condition.

### Recommendation
- Do not allow `removeChain` to affect requests that were dispatched before the removal; snapshot/version the peer registration per-request, or check the commitment status before allowing deregistration.
- Alternatively, decouple "stop accepting new sends" from "stop accepting deliveries," e.g., introduce a grace period or drain mechanism (similar to how consensus clients cannot be un-frozen but frozen clients still allow inspection) so in-flight burned amounts can still be minted on delivery even after a chain is deregistered for *new* sends.
- Consider an escrow/refund mechanism so that a rejected `onAccept` triggers a timeout-based refund path back to the sender rather than silently reverting with the tokens already burned and unrecoverable.

### Proof of Concept
1. Owner calls `addChain(destChain, peerModuleId)`, enabling route to `destChain`.
2. User calls `send({dest: destChain, amount: X, ...})` — tokens are burned immediately per [4](#0-3) , and an ISMP POST request is dispatched.
3. Before consensus finality/challenge period elapses and the relayer delivers the request, owner calls `removeChain(destChain)` per [5](#0-4)  (e.g., in response to an unrelated incident on that chain, or a routine deprecation).
4. When the relayer eventually submits the proof and the destination `onAccept`/peer-source check runs, the request's source module is no longer recognized as supported and the message is rejected (based on the same `_supportedChains` pattern used by `_buildDispatchPost`'s `UnsupportedChain` check).
5. Result: `X` tokens are permanently burned on the source chain with no equivalent mint on the destination chain and no refund path — a permanent, unbacked loss of user funds triggered by a single routine governance action colliding with a single user transaction, exactly analogous to the reported Morpho issue where a single governance toggle stops protecting users who already committed to the prior configuration.

**Note on confidence:** I was unable to directly view the `onAccept`/`HyperApp.sol` source-validation logic in this session due to a tool error on the final read attempt, so the exact mechanism by which the destination side validates `request.source` against `_supportedChains` (confirming the round-trip rejection path) is inferred from the symmetric `addChain`/`removeChain`/`UnsupportedChain` pattern used on the `send()` side, and the doc comment "After removal, transfers to/from this chain will revert" in [6](#0-5) , which explicitly states removal affects both directions ("to/from"). I recommend a Devin session with full file access to confirm the exact `onAccept` validation logic in `HyperApp.sol` before treating this as fully verified.

    function _buildDispatchPost(SendParams calldata params) internal view returns (DispatchPost memory) {
        bytes memory dest = _supportedChains[params.dest];
        if (dest.length == 0) revert UnsupportedChain();

        bytes memory body = abi.encode(Message({
            from: abi.encodePacked(msg.sender),
            to: params.to,
            amount: params.amount,
            data: params.data
        }));

        return DispatchPost({
            dest: params.dest,
            to: dest,
            body: body,
            timeout: params.timeout,
            fee: params.relayerFee,
            payer: msg.sender
        });
    }
