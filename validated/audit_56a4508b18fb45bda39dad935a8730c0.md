### Title
Permanent freezing of escrowed order funds via malicious `beneficiary` reverting native/ERC20 transfer in `withdraw()` - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.withdraw()`, invoked from `onAccept()` for both `RedeemEscrow` and `RefundEscrow` message kinds, releases escrowed order funds to a `beneficiary` address using a low-level `.call` (for native token) or raw `token.call(transfer(...))` (for ERC20), and reverts the **entire** withdrawal — for all tokens in the order, not just the failing one — if any single transfer fails. This mirrors the GG-4 bug class: a core fund-release path is gated on the unconditional success of an externally-controlled value transfer.

### Finding Description
`withdraw()` iterates over `body.tokens` and sends each token/native amount to `beneficiary`: [1](#0-0) 

If the native transfer fails, it reverts with `InsufficientNativeToken()`; if the ERC20 `transfer` call fails, it reverts with `TransferFailed()`. There is no way to skip or retry a single failing leg — the whole `withdraw` call (and therefore the whole `onAccept`) reverts.

`onAccept` is called by the host (`EvmHost.dispatchIncoming`) via a low-level `.call`: [2](#0-1) 

When `onAccept` reverts, `dispatchIncoming` deletes the request receipt "so that it can be retried" — but the retry re-executes the exact same message with the exact same `beneficiary`, so it will fail identically every time. For `RedeemEscrow`, the `beneficiary` is attacker/solver-controlled data carried in the cross-chain message body (decoded from `WithdrawalRequest`), and for `RefundEscrow` the beneficiary is the original order creator. In either case, an order can be crafted (or a beneficiary contract deployed) whose `receive()`/`fallback()` unconditionally reverts, or whose ERC20 `transfer` function is designed to fail. Once such a message is delivered, the escrowed tokens for that commitment become permanently unwithdrawable: the message can be resubmitted indefinitely but will always revert, so the escrow can never be released or refunded — a permanent freeze of the escrowed funds for that order.

This is analogous to the GG-4 finding: dividend payout (a value transfer with attacker-influenceable failure conditions) was made a hard precondition for the core deposit/withdraw logic, so failing that single transfer blocked the entire operation. Here, a single failing token/native leg blocks release of *all* escrowed tokens for the order, with no isolation or fallback (e.g., no "pull" pattern, no per-token skip-and-continue, no escrow sweep for stuck funds).

### Impact Explanation
Funds legitimately escrowed by users in `IntentGatewayV2` orders can become permanently locked if the `beneficiary` (solver on fill, or user on refund) is/becomes a contract that reverts on receiving the native token, or if one of the escrowed ERC20 tokens has a `transfer` implementation that can be made to fail for a specific recipient (fee-on-transfer/blacklist tokens, or a malicious token address supplied in the order). Since delivery of `RedeemEscrow`/`RefundEscrow` is retryable but idempotent-per-message, there is no recovery path once the failure is deterministic — this constitutes permanent freezing of escrowed funds, which is a fund-safety issue on a core cross-chain settlement path reachable by any order filler/creator.

### Likelihood Explanation
Medium-High. Any user creating an order, or any solver filling one, controls or can be tricked into using a `beneficiary`/token combination that deterministically reverts (e.g., a smart-contract wallet without a payable fallback, or a non-standard ERC20). No special privileges are required — this is reachable purely through normal order creation/fill/cancel flows that dispatch `RedeemEscrow`/`RefundEscrow` messages cross-chain.

### Recommendation
Decouple fund release from delivery success: use a pull-based withdrawal pattern (credit `beneficiary`'s balance in storage and let them separately claim), or process each token leg independently (try/catch or low-level call per leg with local accounting) so a single failing transfer cannot block release of the remaining tokens, and add an escape hatch (e.g., allow beneficiary or governance to redirect/retry with an alternate recipient) for stuck legs.

### Proof of Concept
1. User submits a cross-chain order via `IntentGatewayV2` escrowing token A (native) and token B (ERC20) for a fill on chain B.
2. Solver fills the order on chain B; a `RedeemEscrow` message is dispatched back to the source chain with `beneficiary = solver_address`, where `solver_address` is a contract with no payable `receive()`/`fallback()` (or that reverts unconditionally).
3. On delivery, `EvmHost.dispatchIncoming` calls `IntentGatewayV2.onAccept` → `withdraw(body, false)`.
4. The native-token leg `beneficiary.call{value: amount}("")` returns `sent = false`; `withdraw` reverts with `InsufficientNativeToken()`.
5. `dispatchIncoming` catches the revert, deletes the request receipt, and returns (per [2](#0-1) ), allowing indefinite resubmission of the identical message.
6. Every resubmission fails identically since `beneficiary` never changes — the escrowed tokens A and B remain permanently locked in `IntentGatewayV2`, unrecoverable by the user or solver.
