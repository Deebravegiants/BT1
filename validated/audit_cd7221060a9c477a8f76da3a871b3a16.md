### Title
Webhook `shop-domain` header is not covered by HMAC signature, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` and never includes the `x-shopify-shop-domain` header, yet `Registry.process` trusts `request.shop` (read directly from that header) to build `WebhookMetadata.shop` for the handler. Since HMAC validation via `Utils::HmacValidator.validate` only proves the raw body's integrity, an attacker who owns any valid webhook (from their own dev shop) can replay the same body/HMAC while swapping the `shop-domain` header to a victim shop, and the app will process it as if it came from the victim.

### Finding Description
The claimed binding: `HmacValidator.validate(request)` should guarantee `hmac == HMAC(secret, signable_string)` where `signable_string` fully determines every value trusted downstream, in particular `request.shop`. In this gem, `signable_string = request.to_signable_string = @raw_body` [1](#0-0) , while `request.shop` is read independently from `@headers["shopify-shop-domain"]`/`@headers["x-shopify-shop-domain"]` [2](#0-1) . So `shop` is not bound to the signature at all.

The validation path confirms this: `HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it only to `verifiable_query.hmac` [3](#0-2) ; the shop header plays no role. `Registry.process` then does: raise unless `HmacValidator.validate(request)` passes, then builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` and dispatches to the app's handler [4](#0-3) .

Exploit flow: The attacker installs the app on their own dev shop, receives a genuine webhook with a valid `hmac-sha256` header computed by Shopify over the raw body. The attacker replays the exact same raw body and HMAC to the app's webhook endpoint but changes only the `x-shopify-shop-domain` header to `victim-shop.myshopify.com`. `Request#initialize` only checks for header presence, not consistency with the signature [5](#0-4) . `HmacValidator.validate` succeeds because the body/hmac pair is unchanged. `Registry.process` then hands the handler `WebhookMetadata` claiming `shop: "victim-shop.myshopify.com"` while the actual data originates from the attacker. No existing guard (`ShopValidator`, `Context` checks, Sorbet typing) checks that the `shop` header is part of the signed payload — Sorbet only enforces types, not value binding.

### Impact Explanation
This is a cross-tenant authenticity bypass: the app's webhook handler will process attacker-controlled topic/body under the victim merchant's shop identity, causing the app to write, delete, or update data associated with the victim tenant based on attacker input (e.g., forged `orders/create`, `app/uninstalled`, or `customers/data_request` payloads attributed to the victim). This matches the "Critical - cross-tenant access" category. It is repeatable against any victim shop domain the attacker chooses, for every webhook topic the app subscribes to, and costs the attacker nothing beyond owning one dev shop with the app installed.

### Likelihood Explanation
Preconditions are minimal and fully within the documented unprivileged-attacker capability: register a dev shop, install the target app, receive one legitimately signed webhook, and replay it with a modified header. No app secret, access token, or victim credential is needed. The attack works against any app that relies on `ShopifyAPI::Webhooks::Registry.process` (the gem's own documented flow) and uses `WebhookMetadata.shop` to determine tenant scoping in its handler — which is exactly what the gem enables and encourages developers to do.

### Recommendation
Bind the shop (and ideally topic/webhook-id) to the value that is verified, not just to a raw header read post-validation. Concretely: change `Request#to_signable_string` to be strictly `@raw_body` per Shopify's documented HMAC scheme (this is Shopify's actual signing scheme and cannot be silently changed), but instead have `Registry.process` (or `HmacValidator.validate`) require that the caller supply the expected shop out-of-band (e.g., matched against a shop the app already has an active session/registration for), or otherwise document/enforce that `request.shop` from headers must never be treated as authenticated purely by HMAC success — apps must independently verify the shop is one they have installed for that specific webhook subscription/callback URL. At minimum, the gem should clearly document that `shop-domain` is NOT covered by the signature and should not be trusted for tenant scoping without additional verification (e.g., per-shop unique callback paths).

### Proof of Concept
```ruby
# test/webhooks/registry_shop_binding_test.rb
require "test_helper"

class RegistryShopBindingTest < Test::Unit::TestCase
  def setup
    ShopifyAPI::Context.setup(
      api_key: "key", api_secret_key: "secret", api_version: "2022-01",
      is_private: false, is_embedded: true, scope: "scope"
    )
    ShopifyAPI::Webhooks::Registry.clear
    @captured = nil
    handler = Class.new do
      define_singleton_method(:handle) { |data:| @@captured = data }
      def self.captured; @@captured; end
    end
    ShopifyAPI::Webhooks::Registry.add_registration(
      topic: "orders/create", delivery_method: :http, path: "/webhooks", handler: handler
    )
    @handler = handler
  end

  def test_hmac_does_not_bind_shop_domain
    raw_body = '{"id":1}'
    hmac = Base64.encode64(
      OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
    ).strip

    headers = {
      "x-shopify-topic" => "orders/create",
      "x-shopify-hmac-sha256" => hmac,
      "x-shopify-shop-domain" => "victim-shop.myshopify.com", # swapped by attacker
      "x-shopify-api-version" => "2022-01",
      "x-shopify-webhook-id" => "1",
    }
    request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)

    # HMAC validates even though shop header was swapped after signing
    assert ShopifyAPI::Utils::HmacValidator.validate(request)

    ShopifyAPI::Webhooks::Registry.process(request)

    # Handler receives victim shop, though attacker generated/controls the body
    assert_equal "victim-shop.myshopify.com", @handler.captured.shop
  end
end
```
This demonstrates both sides of the claimed equality diverge: `hmac == HMAC(secret, raw_body)` holds regardless of `shop-domain`, yet `request.shop` (untied to the signature) is trusted by `Registry.process` for tenant scoping.
