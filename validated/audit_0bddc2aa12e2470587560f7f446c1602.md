### Title
Webhook `shop` field is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook using only `Utils::HmacValidator.validate`, which HMACs the raw request body against the app's single, app-wide `api_secret_key`. The `shop` domain that identifies the tenant for the event is read straight from an HTTP header and is never part of the signed content, so it can be swapped without invalidating the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `#shop` is derived independently from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is not part of that signable string: [2](#0-1) 

`HmacValidator.validate` only checks `hmac == HMAC(secret, to_signable_string)`; it has no knowledge of, and never checks, the `shop` header: [3](#0-2) 

`Registry.process` calls this validator and then blindly forwards `request.shop` into `WebhookMetadata`, which is the value the app's handler is documented to trust as "The shop domain of the webhook": [4](#0-3) [5](#0-4) [6](#0-5) 

The identity binding that should hold is: `shop header value == shop that produced/authorized this signed body`. Because `api_secret_key` is a single app-level secret shared across every merchant that installs the app (not a per-shop secret), and the signed content excludes the `shop` header, any party who can obtain one validly-signed webhook body+HMAC pair for their *own* shop (e.g., by installing their own app instance/dev store and capturing a real webhook delivery) can replay that exact body and HMAC to the app's webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. `HmacValidator.validate` will still return `true` because it only checks the body against the shared secret; `Registry.process` will then hand the handler a `WebhookMetadata` whose `shop` field is attacker-controlled but is treated by the (documented) contract as an authenticated tenant identifier.

### Impact Explanation
This breaks the equality `authenticated shop == shop used for tenant-scoped action` inside the gem's own webhook verification path, which is exactly the class of binding this gem is responsible for (HMAC validation + `WebhookMetadata` construction). Any host application that follows the documented pattern (`data.shop`) to key per-tenant state, queue jobs, or select records to act on (as literally shown in `docs/usage/webhooks.md`: `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) can be made to attribute a webhook payload to a shop domain the request did not actually originate from — a cross-tenant confusion inside the gem's verified/trusted metadata, not merely "the host app ignoring documented behavior."

### Likelihood Explanation
Exploitation requires only: (1) the attacker's own legitimately signed webhook delivery (trivially obtainable by installing the app on any shop/dev store they control, since `api_secret_key` is shared across all installs of the app), and (2) the ability to POST an HTTP request with a forged `shop-domain` header to the app's public webhook endpoint. No access token, TLS interception, or privileged account is needed — this is reachable by any internet user with a store that has the app installed.

### Recommendation
Do not treat the `shop` header as authenticated data. At minimum, `Registry.process`/`WebhookMetadata` should require the caller to cross-check `request.shop` against a shop the app has an active, previously-registered session/webhook subscription for, or the gem should incorporate the shop domain into the value being HMAC-verified (mirroring how OAuth's `AuthQuery#to_signable_string` includes `shop` in its signed content) before exposing it as a trusted field to handlers.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. for `orders/create`, with a valid `x-shopify-hmac-sha256` computed by Shopify over the raw body using the app's shared `api_secret_key`.
2. Attacker replays the exact same `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present).
4. `Utils::HmacValidator.validate` recomputes `HMAC(api_secret_key, raw_body)` — unchanged, so it matches and returns `true` per `lib/shopify_api/utils/hmac_validator.rb:12-31`.
5. `Registry.process` builds `WebhookMetadata.new(... shop: request.shop ...)` with `shop == "victim-shop.myshopify.com"` per `lib/shopify_api/webhooks/registry.rb:198-199`, and invokes the handler, which — per the gem's own documented usage — trusts `data.shop` as the authenticated tenant identifier.
