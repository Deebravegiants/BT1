Based on the investigation, I found a concrete analog: `pallet-hyper-fungible-token`'s cross-chain calldata execution path lacks domain separation in the message it treats as authorization to dispatch a runtime call — a bug-class match to the Wazuh case where a message-protocol payload written by a lower-trust party is blindly trusted by a privileged executor without binding it to the intended execution context.

### Title
Hyper Fungible Token Cross-Chain Calldata Dispatch Lacks Domain Separation, Enabling Signed-Call Replay Across Chains - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`pallet-hyper-fungible-token`'s `on_accept` handler executes an embedded `runtime_call` on behalf of a beneficiary when the cross-chain message carries a `SubstrateCalldata` payload with a valid signature over `(nonce, runtime_call)`. That signed payload contains no binding to the destination chain, the source chain, the specific HFT contract/pallet instance, or a genesis/chain identifier — only a per-account nonce that is local to the executing chain. Any party who intercepts or later replays that signed payload (e.g. a relayer, a forwarding app, or the message itself submitted through a different Hyperbridge-connected chain sharing the same account scheme) can cause the same authorized call to be dispatched again wherever the beneficiary's nonce still matches, executing an action the signer never authorized for that specific chain/context.

### Finding Description
In `on_accept`, after minting/transferring the bridged tokens, the pallet decodes `SubstrateCalldata` from the message body and, if a `signature` is present, verifies it like this: [1](#0-0) 

The signed message is built purely from `(nonce, substrate_data.runtime_call)`: [2](#0-1) 

`nonce` here is `frame_system::Pallet::<T>::account_nonce(beneficiary)` — the destination chain's own system nonce for that account — not a value tied to this specific cross-chain message, the source chain, the destination chain's identity, or this pallet instance: [3](#0-2) 

There is no chain ID, genesis hash, HFT contract address, or ISMP request commitment mixed into the signed payload. Once the signature verifies, the call is dispatched with the beneficiary's own signed origin: [4](#0-3) 

and the nonce is only incremented after dispatch on that one chain: [5](#0-4) 

Because Substrate accounts (sr25519/ed25519) and Ethereum-style accounts (ecdsa) are chain-agnostic by design, and Hyperbridge is built to connect many chains running this same pallet, the identical `(nonce, runtime_call)` bytes and signature remain valid on every destination chain where the beneficiary account happens to share that same nonce value. A user who authorizes a calldata-carrying transfer intended for one specific destination chain has, without any additional protection, produced a signature that a message relayer or a copy of the cross-chain message re-submitted through a different connected chain can reuse to dispatch the identical call there — an action the user never intended for that chain. This is the same bug class as the Wazuh finding: a payload written/relayed by a lower-trust participant (the cluster protocol / here, any relayer forwarding the ISMP message) is consumed by a privileged executor (`wazuh-logcollector` as root / here, `on_accept`'s `runtime_call.dispatch`) without the executor validating that the payload's authorization is scoped to *this* execution context.

### Impact Explanation
An account holder's signed authorization for a specific cross-chain call can be replayed to trigger the same call on a different destination chain (or re-processed after re-registration of the same nonce), resulting in unauthorized app action: unintended fund transfers, governance-adjacent calls, or any other dispatchable reachable under the base call filter being executed against the victim's account outside the scope they signed for. Given `send` is a signed, permissionless extrinsic reachable by any unprivileged token bridger, and delivery/relay of the ISMP message is performed by unprivileged relayers, the exploit path is fully reachable from an ordinary transaction with no special privilege required by the attacker beyond copying/relaying the message.

### Likelihood Explanation
Requires: (1) a substrate account whose keypair/nonce state coincides across two or more Hyperbridge-connected chains running `pallet-hyper-fungible-token` (realistic since sr25519/ed25519/ecdsa keys are chain-agnostic and users commonly reuse the same account across parachains), and (2) an attacker (malicious/opportunistic relayer, or the sender crafting a message deliverable to more than one destination) able to submit/replay the identical message. Both are realistic in a multi-chain bridging deployment, though it depends on ecosystem-level account reuse rather than a single-transaction guaranteed trigger, making likelihood moderate.

### Recommendation
Bind the signed payload to the specific execution context: include the destination `StateMachine`/chain identifier (or genesis hash), the source chain identifier, the HFT pallet instance identifier, and ideally the ISMP request commitment hash in the data that is signed, in addition to the account nonce. Reject calldata execution if any of these bound values do not match the chain currently processing the message.

### Proof of Concept
1. Deploy `pallet-hyper-fungible-token` on two Hyperbridge-connected substrate chains, A and B, both accepting messages from the same EVM source contract and sharing the same beneficiary account scheme.
2. User signs `SubstrateCalldata { signature, runtime_call }` over `(nonce=0, runtime_call)` intending it to execute only on chain A via a `send` with `call_data` set.
3. The resulting cross-chain `Message` (with embedded `SubstrateCalldata`) is delivered to chain A; `on_accept` verifies the signature and dispatches `runtime_call` as the beneficiary, incrementing chain A's nonce to 1.
4. Because chain B independently tracks its own nonce for the same account (still 0) and the signed payload never referenced chain A specifically, a relayer/attacker submits the same message (or a message with the identical `SubstrateCalldata` bytes) to chain B; verification in `on_accept`'s Ed25519/Sr25519/Ecdsa branch succeeds again since it only checks `(nonce, runtime_call)` against chain B's local nonce=0, and the call is dispatched with `RawOrigin::Signed(beneficiary)` on chain B — an action the user never signed off on for that chain.
