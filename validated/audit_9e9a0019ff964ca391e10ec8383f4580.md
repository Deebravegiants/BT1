### Title
Opaque `swap` bytes let a route inject attacker-chosen contract calls under the caller's signed auth tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The controller treats `swap` as an opaque `Bytes` payload and forwards it to the configured router after exposing the caller through `require_authorized_caller` and granting only one exact input-token transfer for the controller itself. [1](#0-0) [2](#0-1) [3](#0-2)   
Because the route can place third-party code on the call stack while the caller's strategy authorization is active, a maliciously constructed route can cause an unrelated wallet-token `transfer` to be recorded as a child of the caller's controller authorization during simulation. [4](#0-3) 

### Finding Description
Public account strategies such as `multiply`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral` accept caller-supplied `swap: Bytes` without decoding or constraining the embedded program at the controller boundary. [5](#0-4) [1](#0-0)   
`swap_tokens` snapshots balances, authorizes only `token_in.transfer(controller, router, amount_in)` with no sub-invocations, executes `router.execute_strategy(controller, amount_in, swap)`, then accepts any positive measured `token_out` delta plus final account risk. [6](#0-5) [7](#0-6) [8](#0-7)   
The CVE analog is operand-versus-option confusion: a value supplied as data (`swap` route bytes) is interpreted lower in the stack as executable routing instructions, including which pool/contract addresses are invoked. [9](#0-8)   
The controller's exact input-transfer grant does not authorize unrelated wallet tokens, but Soroban simulation can record an extra nested transfer under the caller's strategy auth entry, so a wallet that signs the simulated tree makes that extra transfer valid. [7](#0-6) [10](#0-9) 

### Impact Explanation
A successful poisoned route can move tokens from the strategy caller's wallet that are not part of the collateral/debt being swapped, while still returning positive measured output and passing the controller's final risk checks. [8](#0-7) [10](#0-9)   
This is theft of user funds rather than a bad swap price: the loss can exceed the routed `amount_in` and is bounded by whatever unrelated-token transfer the signed auth tree contains. [10](#0-9) 

### Likelihood Explanation
The attacker needs the victim to execute a strategy with attacker-influenced `routeXdr`/`swap` bytes and sign the authorization tree produced by simulation without rejecting an unexpected child transfer. [11](#0-10) [12](#0-11)   
The on-chain path is reachable by an ordinary owner/delegate through `swap_collateral`, `swap_debt`, `multiply`, or `repay_debt_with_collateral`, and the controller intentionally does not validate the opaque bytes beyond non-emptiness and measured settlement. [13](#0-12) [14](#0-13) 

### Recommendation
Decode or constrain strategy route bytes at the controller boundary, or require the router/venue layer to use a governance allowlist of callable pool/token addresses before any venue invocation. [3](#0-2)   
At minimum, reject any caller authorization tree whose strategy entry contains children other than the single expected `token_in.transfer(controller, router, amount_in)` and surface that invariant to signing clients. [7](#0-6) [12](#0-11) 

### Proof of Concept
1. Victim has a valid account with supplied `USDC` collateral and holds an unrelated `wallet_token` in the same address. [15](#0-14)   
2. Attacker supplies a `swap` payload for `swap_collateral(caller=victim, account_id, current=USDC, amount, new=ETH, swap=routeXdr)` whose route reaches an attacker-controlled contract during settlement. [11](#0-10) [9](#0-8)   
3. The controller authorizes the caller, grants only the exact `USDC.transfer(controller, router, amount)` entry, and calls `execute_strategy` with the opaque bytes. [3](#0-2) [7](#0-6)   
4. The attacker contract invoked by the route attempts `wallet_token.transfer(victim, attacker, victim_balance)`; in recording/simulation this is attached beneath the victim's `swap_collateral` authorization entry rather than beneath the controller's no-subinvocation input grant. [10](#0-9)   
5. If the victim signs the simulated tree, the route can still pay enough `ETH` for `verify_router_output` and final risk to pass while the unrelated `wallet_token` balance is transferred to the attacker. [8](#0-7) [12](#0-11)

**File:** docs/explanation/threat-model.md (L154-165)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```
