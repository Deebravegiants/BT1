### Title
Excess/mismatched native ETH sent to `placeOrder` is permanently trapped and unaccounted for in the Tron `IntentGatewayV2` - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` accepts native ETH via `msg.value` for native-token order inputs and for solver fees, but unlike the canonical EVM implementation, it never refunds or otherwise accounts for leftover `msgValue` when the order does not consume all of it. This mirrors the reported `DepositStableCoinToDealer` bug class: a user's sent native currency silently fails to be recorded/returned by the contract, resulting in loss of funds.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `placeOrder` tracks unspent native value in a local `msgValue` variable, decrementing it as native-token inputs are escrowed [1](#0-0)  and, if `order.fees > 0`, using any remaining `msgValue` to swap for the fee token via Uniswap [2](#0-1) . After this, the function immediately emits `OrderPlaced` and returns, with no code path that refunds or reuses any positive `msgValue` remainder [3](#0-2) .

This is directly contradicted by the canonical, non-Tron `IntentGatewayV2.sol`, which contains an explicit final step: "Refund any unspent native tokens to the user," calling `_sendValue(msg.sender, msgValue)` when `msgValue > 0` [4](#0-3) . The Tron fork of the contract is missing this safeguard entirely, even though it otherwise mirrors the same input/fee escrow logic (including the exact-fee-consumption assumption for the Uniswap swap, which does not report or refund any surplus from `swapETHForExactTokens`, unlike the main contract which tracks `amounts[0]` to adjust `msgValue` at line 383-386 of the canonical contract [5](#0-4) ).

Any of the following mismatches on the Tron deployment causes native ETH to become permanently stuck in the contract with no escrow record and no way to reclaim it:
- A caller sends `msg.value` greater than the sum of native-token (`token == address(0)`) input amounts (an "overpayment," analogous to the reported bug's accidental extra ether).
- A caller mistakenly attaches `msg.value` for an order whose inputs are entirely ERC-20 (`token != address(0)`), expecting the same forgiving handling as the canonical contract.
- `order.fees > 0` and the Uniswap `swapETHForExactTokens` call consumes less than the full `msgValue` supplied, leaving a difference that is never captured back into `msgValue` (no `amounts[0]` handling exists in the Tron version).

### Impact Explanation
Ether sent by an unprivileged order-placer is neither escrowed in `_orders[...]`, nor swapped for fees, nor refunded — it is absorbed silently by the contract balance with no bookkeeping. This is a concrete, permanent loss of user funds for any transaction that supplies more native currency than exactly required (an easy user/integrator mistake given the SDK computes and forwards a combined `value` for input + fee amounts, e.g., `txValue = value + nativeValue` per `docs/content/developers/evm/intent-gateway/placing-orders.mdx` line 349). Because this trapped ether has no corresponding escrow entry, it cannot be recovered by cancellation, fill, or refund flows tied to `_orders[commitment][...]`.

### Likelihood Explanation
High: any normal user interacting with the Tron `IntentGatewayV2` who over-estimates the required native value (a common and expected occurrence when quoting fees or dealing with slippage in the fee-swap), or who mistakenly attaches `msg.value` to an ERC-20-only order, triggers the loss on every such call, with no special conditions or privileged access required. This is a single, ordinary `placeOrder` transaction from any unprivileged user.

### Recommendation
Add the same "refund unspent native tokens" logic present in the canonical `evm/src/apps/IntentGatewayV2.sol` (lines 394-397) to the Tron implementation: after the fee-escrow branch, if `msgValue > 0`, refund it to `msg.sender`. Additionally, capture the actual amount spent by `swapETHForExactTokens` (its `amounts[0]` return value) and only leave/refund the true remainder, matching the accounting fix already present in the canonical contract.

### Proof of Concept
1. On the Tron-deployed `IntentGatewayV2`, construct an `Order` with a single ERC-20 input (`token != address(0)`) and `order.fees == 0`.
2. Call `placeOrder{value: 1 ether}(order, graffiti)` — i.e., mistakenly attach native ETH even though no native input or fee is required.
3. Trace execution: the native-token branch is never entered (token != address(0) skips the `msgValue -=` decrement at line 454-460), `order.fees > 0` is false so the fee block is skipped, and the function proceeds directly to `emit OrderPlaced` at line 490 with no refund.
4. Result: the 1 ether sent by the user remains in the `IntentGatewayV2` contract's balance, is not reflected in `_orders[commitment][...]`, and cannot be withdrawn through `cancelOrder` or `fillOrder`, permanently freezing the user's funds — matching the reported "sent native ether will not be recorded in the contract" bug class.
