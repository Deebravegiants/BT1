### Title
Webhook Shop Attribution Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, but the `shop` value used to attribute the event to a tenant is read from an unauthenticated HTTP header that is never included in the signed material. Since the HMAC secret (`api_secret_key`, the app's `client_secret`) is shared across every shop that installs the app, any shop that has legitimately installed the app can generate a validly-signed body and then relabel it as coming from a different shop, defeating tenant isolation.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is populated from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is completely outside the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (the raw body only) and compares it with the `hmac` header using `OpenSSL.secure_compare`: [3](#0-2) 

`Registry.process` accepts the request once this body-only HMAC check passes, and then dispatches the handler using the header-derived, unauthenticated `shop`: [4](#0-3) 

The identity binding that should hold is:
`hmac_valid(body) == true` should imply `shop_header == shop_that_signed(body)`.

In this implementation, that equality does not hold: `hmac_valid(body)` only proves the body was produced using the app's single shared `client_secret` — it says nothing about *which* installed shop produced it. Because `api_secret_key` is one value shared by the app across all merchant installations (it is not a per-shop secret), any shop that has installed the app can capture (or self-generate, using its own real webhook deliveries) a `(raw_body, hmac)` pair that is valid, then submit it to the app's webhook endpoint with the `shopify-shop-domain` header changed to a victim shop's domain. `HmacValidator.validate` will still return `true` (it never looks at the shop header), and `Registry.process` will hand the payload to the topic handler tagged with the attacker-chosen `shop`, i.e., cross-tenant impersonation.

### Impact Explanation
This breaks tenant isolation for any app built on this gem's webhook processing: an attacker who has installed the app on their own (attacker-controlled) shop can forge webhook events that the host application will process as if they originated from an arbitrary victim shop. Depending on how the host app's webhook handlers use `WebhookMetadata#shop` (e.g., to look up records, create/update orders, fulfill orders, or trigger side effects), this can result in cross-tenant data corruption or unauthorized actions performed against a different merchant's data — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is realistic but requires the attacker to be able to generate at least one legitimately-HMAC'd webhook body (trivially achievable by installing the app on a shop they control and capturing/triggering any real webhook delivery, or by controlling the body content of a webhook they can influence, e.g. via their own store's events), and then replaying it to the shared webhook endpoint with a modified shop header. No access token, `client_secret`, or privileged account for the victim is required — only an ordinary developer/merchant relationship with the app on the attacker's own shop, which fits the "unprivileged internet user" threat model.

### Recommendation
Bind the shop identity to the signed material rather than trusting an unauthenticated header. Concretely, `HmacValidator`/`Request#to_signable_string` should incorporate the shop domain (and topic) into what's verified, or `Registry.process` should independently validate that the header-derived shop matches metadata that can only be produced by Shopify for that specific shop (for example, cross-checking against a per-shop registered secret, or requiring hosts to correlate webhook shop against the session/store used to register the webhook subscription, rather than the raw header value alone).

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and triggers any webhook (e.g. `orders/create`), capturing the exact raw JSON `body` and the resulting `X-Shopify-Hmac-Sha256` value — both are valid because they were computed by Shopify with the app's shared `client_secret`.
2. Attacker resends the same `raw_body` and same `hmac` value to the app's public webhook endpoint, but sets the header `shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers are present).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only and matches — validation succeeds despite the shop header being forged.
5. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)`, causing the host application to process attacker-controlled data as an authentic event from `victim-shop.myshopify.com`. [5](#0-4)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
