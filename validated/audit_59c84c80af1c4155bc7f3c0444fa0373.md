Confirmed vulnerability. Both `WrappedHyperFungibleToken` and its upgradeable counterpart lock tokens via `safeTransferFrom` without measuring actual balance received, then dispatch `params.amount` as-is in the cross-chain message — creating a mismatch that mirrors the reported fee-on-transfer bug class, but here the impact is worse: it results in an unbacked cross-chain liability rather than a simple revert.

### Title
Fee-on-transfer underlying tokens cause under-collateralized escrow in WrappedHyperFungibleToken.send() - (File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol)

### Summary
`WrappedHyperFungibleToken.send()` (and the identical `WrappedHyperFungibleTokenUpgradeable.send()`) locks `params.amount` of the underlying ERC20 via `safeTransferFrom(msg.sender, address(this), params.amount)` and then encodes the same `params.amount` into the cross-chain `Message` that is dispatched to the peer contract. If the underlying token charges a fee-on-transfer (e.g. USDT-style fee toggle, or any deflationary/tax token), the contract actually receives less than `params.amount`, but the dispatched message still promises the full `params.amount` to be unlocked on the destination side.

### Finding Description
In `send()`: [1](#0-0) 
the contract does not verify actual tokens received — it simply calls `safeTransferFrom` for `params.amount` and proceeds. The dispatched message body is built directly from `params.amount`: [2](#0-1) 

On the receiving side (whether that is a peer `WrappedHyperFungibleToken` unlocking the same underlying, or a `onPostRequestTimeout` refund), the full `message.amount` is transferred out of the contract's balance: [3](#0-2) [4](#0-3) 

This is the exact bug class described in the report (fee-on-transfer breaking accounting for `safeTransfer`/`safeTransferFrom` calls), but instead of a revert (as in the Aera Vault case), here the contract silently under-collects and still commits to paying the full nominal amount, causing systemic balance drain. The codebase's own `IntentGatewayV2` explicitly guards against this exact issue by measuring `balanceOf` before/after transfers and using the actual received amount, e.g.: [5](#0-4) 
demonstrating the project is aware of and mitigates fee-on-transfer risk elsewhere, but the mitigation is missing in `WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable`. The identical pattern also exists in `WrappedHyperFungibleTokenUpgradeable.send()`: [6](#0-5) 

### Impact Explanation
Every `send()` call with a fee-on-transfer underlying under-funds the contract's lockbox relative to the amount it commits to unlock on the destination chain (or refund on timeout). Repeated over time, this progressively drains the contract's actual token balance below its outstanding cross-chain liabilities, meaning legitimate later unlocks/refunds for other users will fail (insufficient balance) or, if front-run, the last users to attempt withdrawal lose funds permanently. This is a protocol-level accounting insolvency/fund-freezing issue reachable by any unprivileged user simply calling `send()` with a fee-on-transfer token configured as `_underlying`, categorized as Medium/High depending on whether such tokens are deployed as `_underlying` for a given wrapper instance.

### Likelihood Explanation
Likelihood depends on whether the token configured as `_underlying` for a given `WrappedHyperFungibleToken` deployment has (or can later enable) a transfer fee — this is owner-configured per deployment via `configure()`, so any deployment wrapping a token like USDT (which can toggle fees) or any standard fee-on-transfer/tax token is directly exposed. No special privileges are needed to trigger the drain — any regular `send()` caller does so unknowingly.

### Recommendation
Mirror the pattern already used in `IntentGatewayV2`: measure `IERC20(_underlying).balanceOf(address(this))` before and after the `safeTransferFrom` call in `send()`, and use the actual received delta (not `params.amount`) both when building the dispatched `Message.amount` and in the emitted `Sent` event, for both `WrappedHyperFungibleToken.sol` and `WrappedHyperFungibleTokenUpgradeable.sol`.

### Proof of Concept
1. Owner configures `WrappedHyperFungibleToken` with `_underlying` set to a token that charges a 1% fee on transfer (fee currently disabled or enabled).
2. Alice calls `send({amount: 1000e18, ...})`, approving 1000e18. `safeTransferFrom` executes, but due to the 1% fee the contract only receives 990e18.
3. The dispatched `Message.amount` is still `1000e18`, per `_buildDispatchPost` using `params.amount` directly.
4. On the destination chain, when the message is delivered via `onAccept`, or if it times out and `onPostRequestTimeout` fires, the contract attempts to transfer out `1000e18` even though the source contract's balance sheet is only backed by `990e18` of real collateral for this transfer.
5. Over many such transfers, the wrapper's real underlying balance falls short of the sum of nominal amounts it has committed to pay out, eventually causing unlock/refund transactions to revert (`ERC20InsufficientBalance`) for later users, freezing their funds.
