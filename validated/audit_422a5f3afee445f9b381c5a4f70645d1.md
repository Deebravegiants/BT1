### Title
Division-by-zero panic in `Processor::calc_take_pnl` when pool reserves reach zero after PnL accounting - (File: `program/src/processor.rs`)

### Summary
`Calculator::calc_take_pnl` (invoked from `process_deposit`, `process_withdraw`, `process_swap_base_in`, `process_swap_base_in_v2`, `process_swap_base_out`, `process_swap_base_out_v2`) divides by `x1`, the normalized "total pc without pnl" reserve, without checking that it is non-zero. If accumulated but not-yet-collected PnL (`amm.state_data.need_take_pnl_pc`) ever equals the real vault balance, `total_pc_without_take_pnl` becomes exactly `0`, `x1` becomes `0`, and the subsequent `checked_div(x1)` returns `None`, causing an `.unwrap()` panic. This mirrors the TFLite `GatherNd` bug class: an attacker-influenceable "shape"/denominator value collapses to zero and the reference implementation divides by it without guarding.

### Finding Description
`calc_total_without_take_pnl_no_orderbook` computes the pool's live reserves as vault balance minus the amount owed-but-not-yet-skimmed to the pool owner: [1](#0-0) 

This is a plain `checked_sub` that legitimately returns `0` (not an error) when `need_take_pnl_pc == pc_amount` (or the coin equivalent). The result is then normalized: [2](#0-1) 

and fed into `calc_take_pnl`, where `x1` (a `U256`) is used unconditionally as a divisor: [3](#0-2) 

`y2 = x2.checked_mul(y1).unwrap().checked_div(x1).unwrap();` — if `x1 == 0`, `checked_div` returns `None` and `.unwrap()` panics, aborting the transaction. There is no upstream check anywhere in `process_deposit` [4](#0-3) , `process_withdraw` [5](#0-4) , or the four swap handlers [6](#0-5) [7](#0-6)  that rejects a zero reserve before calling `calc_take_pnl`.

`need_take_pnl_pc`/`need_take_pnl_coin` are monotonically incremented on every swap/deposit/withdraw whenever price has moved favorably for the pool owner (inside the `if pool_pc_amount * pool_coin_amount >= calc_pc_amount * calc_coin_amount` branch of `calc_take_pnl`), while the real vault balance (`pc_amount`) can independently shrink through ordinary swaps. Because a single transaction on Solana may contain many instructions, an unprivileged attacker can chain repeated `SwapBaseIn`/`SwapBaseOut` instructions against the same pool inside one transaction, each incrementing `need_take_pnl_pc` and reducing the residual reserve, until the residual `total_pc_without_take_pnl` (or coin side) collapses to exactly `0` on a subsequent instruction in that same transaction — triggering the panic.

### Impact Explanation
A runtime panic aborts the transaction, but more importantly this is a state-dependent trap: once a pool's `need_take_pnl_pc`/`need_take_pnl_coin` reaches parity with the vault balance on one side, every future call to `Deposit`, `Withdraw`, and all four swap instructions for that pool will hit `calc_take_pnl` and panic (the only exception is `Withdraw` while `amm.status == WithdrawOnly`, which skips `calc_take_pnl` — see [8](#0-7) , but that status is admin-controlled). For any pool not in `WithdrawOnly`, this permanently freezes LP withdrawals, deposits and swaps, i.e., permanent freezing of LP and swapper funds in that pool, satisfying the "permanent freezing of user or LP funds" impact bar.

### Likelihood Explanation
Reaching the exact zero-crossing requires the `need_take_pnl_*` accumulator to exactly match the corresponding vault balance, which is a precise integer coincidence rather than something trivially forced in one shot; however, an attacker fully controls the sequence and sizes of swap instructions packed into a single transaction and can therefore search for/engineer this exact-zero condition against a target pool's current on-chain state (which is fully observable off-chain before submission). This makes the likelihood Medium rather than High/trivial, but it is a real, unprivileged, single-transaction-reachable path with attacker-chosen instruction data.

### Recommendation
In `Calculator::calc_take_pnl` (`program/src/processor.rs`), before computing `x2_power`/`y2`, check that `x1 != 0 && y1 != 0` (and likewise guard `total_pc_without_take_pnl`/`total_coin_without_take_pnl` being non-zero in `calc_total_without_take_pnl_no_orderbook`'s callers) and return `AmmError::CalcPnlError` (or a new dedicated error) instead of proceeding into the unchecked division. Replace the raw `.unwrap()` on `checked_div` in `calc_x_power`/`calc_take_pnl` with a `?`-propagated error so a zero reserve produces a graceful `ProgramError` instead of a panic.

### Proof of Concept
Conceptual PoC (cannot be executed without transaction/runtime access):
1. Identify a pool where `amm.state_data.need_take_pnl_pc` is close to the current `amm_pc_vault.amount` (or the coin-side equivalent), e.g., via RPC state.
2. Submit a single transaction containing several `SwapBaseIn`/`SwapBaseOut` instructions against that pool (looping/adjusting `amount_in`/`amount_out`) so that the final instruction causes `calc_total_without_take_pnl_no_orderbook` to yield `total_pc_without_take_pnl == 0` (or coin side `== 0`).
3. That instruction invokes `Self::calc_take_pnl` with `x1 == 0` (or `y1 == 0`), hitting `checked_div(x1).unwrap()` in [9](#0-8) , causing the instruction — and the whole transaction — to panic/abort.
4. Because `need_take_pnl_pc` is state that persists across transactions, the pool is left in a condition where every future `Deposit`/`Withdraw`/swap instruction re-triggers the same zero-division panic, freezing the pool.

    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
