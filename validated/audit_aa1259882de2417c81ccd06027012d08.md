## Finding

### Title
Webhook `shop` domain is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, then hands the caller-supplied `shop` header value straight to the app's webhook handler as the tenant identifier — without that header ever being part of the signed material.

### Finding Description
The gem's webhook verification path is: [1](#0-0) 

`Utils::HmacValidator.validate(request)` is the only authentication check performed before the handler is invoked with `shop: request.shop`.

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only the raw HTTP body — the shop domain is never included: [3](#0-2) 

`request.shop` itself is read straight from an HTTP header (`x-shopify-shop-domain` / `shopify-shop-domain`) with no relation to the HMAC-signed bytes: [4](#0-3) 

This is the exact identity-binding failure the report's bug class describes: `HMAC(secret, body)` is valid == `body was produced by Shopify`, but the code treats it as == `(body, shop) pair was produced by Shopify for that shop`. Those two statements are not equivalent because `shop` is excluded from the signable string.

### Impact Explanation
Because `shop` is not bound to the signature, a valid `(raw_body, hmac)` pair generated by Shopify for one tenant (attacker's own shop, which the attacker fully controls and can legitimately trigger events for, e.g. via `orders/create`) can be replayed to the same webhook endpoint with the `x-shopify-shop-domain` header rewritten to any other shop the app services. `Registry.process` will pass HMAC validation (it only checks the body) and will invoke the app's handler with `WebhookMetadata.new(shop: request.shop, ...)` claiming the payload belongs to the victim tenant: [5](#0-4) 

Any host application relying on this gem's `shop` field (as documented/intended for multi-tenant dispatch) to select the tenant record to create/update/delete will process attacker-controlled data under a victim shop's identity — i.e., cross-tenant write/access using only the attacker's own legitimately-obtained webhook material, without needing the victim's access token or `api_secret_key`. This satisfies the Critical bar ("cross-tenant access").

### Likelihood Explanation
Any unprivileged internet user who can install the app on their own shop (or who otherwise obtains one genuine Shopify webhook request+HMAC, e.g. via network capture since these endpoints are typically plain HTTP(S) POSTs) can trivially replay the request with an altered `X-Shopify-Shop-Domain` header. No secret material is required to forge the header — only reuse of a previously valid `(body, hmac)` pair. This is a pre-auth capability limited only by the shared `api_secret_key` for the app (same key for all shops), which is exactly the identity-binding gap this class of bug targets.

### Recommendation
Bind the tenant identity into the verified material, e.g.:
- Require the host application to independently confirm `request.shop` corresponds to a session/installation that this exact `(topic, webhook_id, body)` combination was expected for (e.g. cross-check against Shopify's `admin/api/webhooks` before trusting), or
- At minimum, document/emit the `shop` header as untrusted-for-authorization in `Webhooks::Request`/`WebhookMetadata`, and encourage handlers to correlate `webhook_id` via a GraphQL lookup (as `Registry.get_webhook_id` already does) scoped to the session/shop before acting, rather than trusting the header value directly for tenant selection.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and triggers a webhook (e.g., creates an order), causing Shopify to POST:
   ```
   POST /webhooks
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid hmac of raw_body with app secret>
   X-Shopify-Shop-Domain: attacker.myshopify.com
   Body: {"id":123, "line_items": [...] }
   ```
2. Attacker replays the identical body and HMAC header, only changing:
   ```
   X-Shopify-Shop-Domain: victim.myshopify.com
   ```
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `@raw_body` — the forged request passes validation.
4. The registered handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker-controlled>, ...)` and, if the host app uses `shop` to select which tenant's records to mutate, processes attacker data as if it belonged to `victim.myshopify.com`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
