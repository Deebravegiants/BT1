### Title
Zero-liquidity hostile-preseed graduation permanently bricks `finalizeGraduation` via `LPLock.recordLock`'s `ZeroAmount` guard - (File: packages/contracts/src/LPLock.sol / packages/contracts/src/Bonding.sol)

### Summary
`LPLock.recordLock` requires `amount != 0` and reverts with `ZeroAmount()` otherwise [1](#0-0) . `Bonding.finalizeGraduation` calls `recordLock(tokenAddress, lpPair, liquidity)` unconditionally with whatever `liquidity` the three-regime HyperSwap seeding path produced [2](#0-1) . The protocol's own code comments acknowledge that under an extreme, budget-capped hostile mint-preseed, `_routerDepositAndDispose` can end up with `remToken == 0` or `remLT == 0`, in which case `addLiquidity` is skipped and `finalizeGraduation` returns `liquidity = 0` [3](#0-2) . In that scenario `recordLock(token, lpPair, 0)` now reverts, so `finalizeGraduation` reverts and the token is stuck permanently in `Lifecycle.Graduating` — this is analogous to the CVE's class ("a single crafted/edge-case input crashes a code path that a remote/unprivileged party can trigger"), except here the crash is a permanent on-chain state freeze reachable by anyone.

### Finding Description
`_swapBudget` caps the rebalance swap at 99% of the available budget specifically "so the subsequent `addLiquidity` always has a non-zero amount of BOTH sides to deposit," and the natspec explicitly walks through the failure mode being guarded against: an extreme hostile pre-seed can push the unconstrained optimal swap (`_noFeeSwapInput`) past the per-side budget; `_pairRebalance` then clamps the swap to the full (99%-capped) budget, consuming (up to) the entire side; `_routerDepositAndDispose` then sees `remToken == 0` or `remLT == 0` and skips `addLiquidity` entirely, so `liquidity` returns as `0` from `_seedUniswapV2Direct` [4](#0-3) .

The comment says this scenario used to just "record a zero-sized lock" — i.e., the intended graceful degradation was that `LPLock.recordLock` would succeed with `amount = 0`, leaving the attacker's own pre-existing LP as effectively the entire pool (an accepted economic loss, not a freeze). But `LPLock.recordLock` as currently written explicitly disallows this: `if (amount == 0) revert ZeroAmount();` [5](#0-4) . Because `recordLock`'s one-shot sentinel (`lockedAt`) is only set on a successful call, a revert here means `finalizeGraduation`'s entire transaction reverts (state changes to the pair/token/LT during `_seedUniswapV2Direct` are rolled back), and `info.lifecycle` remains `Graduating` forever. There is no other function that can move the token out of `Graduating` — `_enterGraduating` is gated to only fire from `Lifecycle.Curve`, and `finalizeGraduation` is the sole permissionless exit — so the token, its 750M curve-raised tokens/LT, and the 250M `lpReserve` tokens held by `Bonding` are permanently locked with no recovery path, exactly the "brick" scenario the rest of the natspec (`AGENTS.md`'s "Phase 2 must never revert under any pre-seed shape") explicitly says must never happen [6](#0-5) .

The `1%` swap-budget reservation is a heuristic, not a proof: it guarantees a swap doesn't consume literally 100% of the pre-budget side, but it does not by itself guarantee `remToken > 0 && remLT > 0` in all cases (e.g. after `_swapBudget`'s 99% cap, or via rounding in `getAmountOut`/`_noFeeSwapInput`, or via the `_ltSwapInventory`/`protectedLT` saturating-subtract paths) — the very fact that the code's own comment walks through a concrete path to `liquidity == 0` shows the developers themselves considered this reachable, and the fix ("recording a zero-sized lock") was superseded by `LPLock.recordLock`'s `ZeroAmount` guard without updating the caller to handle that case (e.g., skipping the `recordLock` call, or accepting a zero record).

### Impact Explanation
If triggered, this permanently freezes: the entire curve's raised LT (all trader capital), the 750M sellable tokens' equivalent value, and the 250M `LP_RESERVE` tokens for that specific launched token — none of which can ever be recovered, since `Bonding` has no rescue/skip path once `Lifecycle.Graduating` is entered and `finalizeGraduation` is the only exit which will deterministically keep reverting on the same zero-liquidity computation (the cached `pendingGraduation` values are frozen, so retries reproduce the same `liquidity = 0` outcome). This is a permanent freezing of trader/creator funds for the affected token — squarely within the accepted impact class.

### Likelihood Explanation
This requires an attacker to construct a specific hostile mint-preseed shape (via front-running `factory.createPair` + `transfer` + `pair.mint`, permissionless steps documented in `AGENTS.md`) sized so that the optimal no-fee rebalance swap exceeds the per-side swap budget by enough that, after the 99% cap, the deposit leg still lands with one side at zero (e.g., due to a maximally lopsided ratio, similar to the `M-02` regime the existing fuzz test `testFuzz_hostilePreSeed_neverProfitable_neverBricks` exercises up to `seedMultiple` bound of 1000x). The cost of the attack is bounded by the size of the malicious LT/token deposit into the pre-created pair, and only needs to be executed once between phase 1 (`_enterGraduating`) and phase 2 (`finalizeGraduation`) for a specific token — a window the protocol's own keeper races to close within ~60 seconds, but any attacker watching for `TokenGraduating` events can front-run within that window. I could not fully verify from the available code/tests whether the current fuzz test (`testFuzz_hostilePreSeed_neverProfitable_neverBricks`) actually asserts `liquidity > 0` in every fuzzed case, or whether it might already be exposing/passing through a zero-liquidity revert that's silently tolerated by the fuzz harness — the test file wasn't fully readable within the tool budget available. Given the docs/comments treat "recording a zero-sized lock" as the accepted mitigated outcome and `LPLock.recordLock`'s `ZeroAmount` check appears to invalidate that assumption, this looks like a genuine regression rather than a purely theoretical edge case, but confirming exact reachability (exact bound on `seedMultiple`/ratio that produces `liquidity == 0` after the 99% cap) would require running the fuzz suite or manual numeric construction, which is out of scope for static review here.

### Recommendation
Either (a) change `LPLock.recordLock` to accept `amount == 0` (recording a zero-sized lock as the original design intended) so `finalizeGraduation` cannot revert on this path, or (b) change `Bonding.finalizeGraduation` to skip the `recordLock` call entirely when `liquidity == 0`, still flipping `info.lifecycle` to `Graduated` and emitting `TokenGraduated` with `liquidity = 0`. Add an explicit unit/fuzz test that drives `_routerDepositAndDispose` into the `remToken == 0`/`remLT == 0` branch and asserts `finalizeGraduation` succeeds (not just economically, but by not reverting) rather than relying only on the `_swapBudget` 99% heuristic.

### Proof of Concept
Conceptual reproduction (mirrors `test_M02_budgetCapped_stillOpensButOffPrice`-style setup already present in `TwoPhaseGraduation.t.sol`, e.g. around lines 871-917):
1. Launch a token and buy it into `Graduating` via `_enterGraduating`, caching `(tokensForLP, ltFromPair)`.
2. Front-run: create the HyperSwap pair, and mint LP into it at an extreme ratio chosen so that `_noFeeSwapInputUncapped` for the correcting swap exceeds the per-side budget (`(tokensForLP or ltFromPair) * 99 / 100`) by enough that, post-cap, `_routerDepositAndDispose` computes `remToken == 0` or `remLT == 0` (e.g., a sufficiently extreme multiple beyond what the existing `testFuzz_hostilePreSeed_neverProfitable_neverBricks`/M-02 test bounds cover, or a ratio combined with rounding that zeroes one remainder exactly).
3. Call `bonding.finalizeGraduation(tokenAddress)`.
4. Instead of the previously-intended "record a zero-sized lock," the call reverts inside `LPLock.recordLock` with `ZeroAmount()`.
5. Any subsequent call to `finalizeGraduation` for this token reproduces the same computation (cached `pendingGraduation` values are unchanged) and reverts identically — the token is permanently stuck in `Lifecycle.Graduating`.

    function recordLock(
        address token,
        address lpPair,
        uint256 amount
    ) external {
        LPLockStorage storage $ = _s();
        if (!$.isLocker[msg.sender]) revert NotAuthorized();
        if (lpPair == address(0)) revert ZeroAddress();
        if (amount == 0) revert ZeroAmount();
        // `lockedAt` is the one-shot sentinel: it is always set to a non-zero
        // timestamp on the first lock, so the guard holds for any `amount`.
        if ($.locks[token].lockedAt != 0) revert AlreadyLocked();
        if (IERC20(lpPair).balanceOf(address(this)) < amount) revert InsufficientLPBalance();
        $.locks[token] = LockInfo({lpPair: lpPair, amount: amount, lockedAt: block.timestamp});
        emit LPLocked(token, lpPair, amount);
    }

### Brick-resistance contract

`_seedUniswapV2Direct` MUST never revert under any pre-seed shape. The brick-resistance contract is the load-bearing security property — it ranks above the LP-capture defense, because a brick locks every holder in `Graduating` forever. The pre-seed defense is layered to honour this:

- **Regime 1/2 don't touch the router.** Even if the V2 router is misbehaving, the empty + donation paths run on direct pair calls.
- **`_pairRebalance` falls back to a direct mint when no swap can run.** `_noFeeSwapInput` may return `s == 0`, or the pair's fee-charging `getAmountOut(s)` may round to zero, against a pre-seed whose swap-output side is dust — `pair.swap` would otherwise revert with `INSUFFICIENT_OUTPUT_AMOUNT`.
