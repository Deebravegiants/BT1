**Analysis:**

The premise requires a "retry harness" that takes a `VMError` produced during multisig approval checks, calls `to_partial()`, and then re-`finish()`s it with an attacker-chosen `Location`. No such component exists in the actual multisig execution flow.

Tracing the real path: `execute_multisig_transaction` in [1](#0-0)  calls `execute_multisig_payload`, and on failure invokes `failure_multisig_payload_cleanup`, which converts the resulting `VMStatus` (already downgraded from `VMError` via `into_vm_status()`, not `to_partial()`) into a serializable `ExecutionError` via `TryFrom<VMStatus>` [2](#0-1) . This conversion reads `location` directly from the already-finished `VMStatus::MoveAbort`/`ExecutionFailure` variants — there is no intermediate `to_partial`/re-`finish` step, and no caller-supplied `Location` parameter anywhere in this flow.

Searching the codebase for `to_partial` usage confirms it is used only in internal VM/loader/interpreter machinery (e.g., [3](#0-2) , [4](#0-3) ), where the location is intentionally reset because the error needs to be re-attributed to a different, VM-determined module (e.g., the caller of a failing dependency) — never to an attacker-chosen or "unprivileged relayer"-chosen location. There is no code path where an unprivileged party supplies the `Location` used in a `finish()` call after `to_partial()`.

The `to_partial`/`finish` API itself is by design (`VMError` → `PartialVMError` → re-`finish`ed `VMError`), documented and intentional for cases where the VM runtime needs to attribute an error to the correct context [5](#0-4) . This is internal VM error-plumbing, not a custody control — it does not touch object ownership, fungible asset stores, multisig approval state, or any authority/capability check. The `multisig_account.move` module's `ExecutionError` struct only records `abort_location` as an informational string for event/history purposes [6](#0-5) ; it does not gate approval counts, ownership, or fund movement — mismattributing it would be cosmetic at most, and per the Decision Standard, cosmetic/event-level mismatches are explicitly out of scope.

Since (1) no real code path allows an unprivileged relayer to control the `Location` passed to `finish()` after `to_partial()`, and (2) even if it did, `abort_location` in the multisig cleanup flow is informational only and does not affect approval/authority/custody state, this does not meet the bar of crossing a real custody boundary.

impl TryFrom<VMStatus> for ExecutionError {
    type Error = anyhow::Error;

    fn try_from(status: VMStatus) -> anyhow::Result<ExecutionError> {
        match status {
            VMStatus::Error {
                status_code: error, ..
            } => Ok(ExecutionError {
                error_type: String::from("VMError"),
                abort_location: String::from(""),
                error_code: error as u64,
            }),
            VMStatus::MoveAbort {
                location: abort_location,
                code: error_code,
                // Note that we ignore the message here because ExecutionError has to be serialized
                // for multisig transactions and the serialization is not expected to fail.
                message: _,
            } => Ok(ExecutionError {
                error_type: String::from("MoveAbort"),
                abort_location: format!("{:?}", abort_location),
                error_code,
            }),
            VMStatus::ExecutionFailure {
                status_code,
                location,
                function: _,
                code_offset: _,
                message: _,
                sub_status: _,
            } => Ok(ExecutionError {
                error_type: String::from("MoveExecutionFailure"),
                abort_location: format!("{:?}", location),
                error_code: status_code as u64,
            }),
            _ => Err(anyhow::anyhow!(
                "Unknown error from vm status cannot be converted into `ExecutionError`: {:?}",
                status
            )),
        }
    }
