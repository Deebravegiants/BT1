### Title
Ambiguous withdrawal-status matching by `assetId` alone misreports completion status/txHash across batched same-asset withdrawals - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal()` resolves the on-chain status for a given `WithdrawalIdentifier` by calling `findMatchingWithdrawal()`, which selects the first API record whose `near_token_id` matches `assetId`, ignoring `index` and `destinationAddress`. When a batch (`sdk.processWithdrawal({ withdrawalParams: [w0, w1] })`) contains two withdrawals of the same asset to different destination addresses, both `describeWithdrawal()` calls query the POA API with the same `args.tx.hash` (the shared intent-settlement tx), receive the same withdrawal list, and both resolve to the same matched record — so one identifier can report the other's `status`/`transfer_tx_hash`.

### Finding Description
The broken equality is: `describeWithdrawal(wid_i).txHash` must equal the on-chain outcome for `wid_i.withdrawalParams.destinationAddress`, but instead it can equal the outcome for `wid_j.withdrawalParams.destinationAddress` (j ≠ i) when `wid_i.withdrawalParams.assetId === wid_j.withdrawalParams.assetId`.

Code path:
- `createWithdrawalIdentifiers()` assigns each withdrawal in a batch an `index` (per bridge route) but all share the same `intentTx` (the single settled NEAR transaction hash) — [1](#0-0) .
- `PoaBridge.getWithdrawalStatusWithRetry()` queries the POA bridge API using only `args.tx.hash`, returning the full list of withdrawals for that batch tx — [2](#0-1) .
- `describeWithdrawal()` then calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which matches only by `assetId`, not by `index` or `destinationAddress` — [3](#0-2) .
- `findMatchingWithdrawal()` uses `Array.prototype.find`, returning the *first* array element whose `near_token_id` maps to the asset — with no tie-breaking by `data.address` (which the API record does carry) or by amount/order — [4](#0-3) .

The code itself documents this as a known, unresolved limitation: "Currently only matches by assetId... multiple withdrawals of the same token in a single transaction are not supported" — [5](#0-4) . No other guard (`supports()`, `validateWithdrawal()`, or batch construction in `createWithdrawalIdentifiers`/`processWithdrawal`) deduplicates or otherwise prevents two same-`assetId` withdrawals to different addresses within one batch — [6](#0-5) . Since both identifiers query with the identical `tx.hash` and identical `assetId`, `findMatchingWithdrawal` deterministically returns the same record for both, regardless of `index`.

### Impact Explanation
An integrator relies on `describeWithdrawal()` (directly, or via `watchWithdrawal`/`waitForWithdrawalCompletion`/`processWithdrawal`) to decide when to credit, refund, or reconcile a specific destination address's withdrawal. With this bug, entry `i`'s reported `status`/`txHash` can actually belong to entry `j`'s destination address. This is a status/hash misreport that can cause an integrator to treat a withdrawal to address A as completed with a `txHash` that actually corresponds to funds sent to address B — a wrong-address completion report with no code-level recovery, matching the "status or hash misreport making an integrator credit or refund twice" impact category (High/Critical depending on how the integrator acts on it). It is fully repeatable for any batch containing ≥2 same-`assetId` POA withdrawals to different addresses; it requires no privileged access, only ordinary use of the public `processWithdrawal`/`describeWithdrawal` API by any caller.

### Likelihood Explanation
Preconditions are trivial and within normal SDK usage: any caller batches two (or more) `WithdrawalParams` with identical `assetId` but different `destinationAddress` in a single `processWithdrawal`/`signAndSendWithdrawalIntent` call routed through the POA bridge. No special token state, timing, or race condition is needed — the mismatch is deterministic given the API returns multiple records for the shared `tx.hash`. Attacker cost is zero beyond constructing an ordinary batch withdrawal request.

### Recommendation
Disambiguate `findMatchingWithdrawal` using more than `assetId`: match on `assetId` plus `data.address` (destination address), and when multiple withdrawals share both, fall back to matching by `amount`/relative ordering as the existing comment suggests, or track a bridge-side idempotency key if the POA API adds one. Until then, consider rejecting/flagging batches with duplicate `(assetId, destinationAddress)` pairs, or at least duplicate `assetId` entries, before dispatching to the POA route, or clearly document the constraint to callers to prevent unsafe batching.

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

			? args.withdrawalParams

		// Step 1: Estimate fee
		const feeEstimation = await (() => {
			if (args.feeEstimation != null) {
				return Array.isArray(args.feeEstimation)
					? args.feeEstimation

			return this.estimateWithdrawalFee({
				withdrawalParams,
				logger: args.logger,
			});
		})();

		// Step 2: Sign and send intent
		const { intentHash } = await this.signAndSendWithdrawalIntent({
			withdrawalParams,
			feeEstimation,
			referral: args.referral,
			intent: args.intent,
			logger: args.logger,
		});

		args.logger?.info("Intent published", { intentHash });

		// Step 3: Wait for intent settlement
		const intentTx = await this.waitForIntentSettlement({
			intentHash: intentHash,
			logger: args.logger,
		});

		args.logger?.info("Intent settled", { txHash: intentTx.hash });

		// Step 4: Wait for withdrawal completion
		const destinationTx = await this.waitForWithdrawalCompletion({
			withdrawalParams,
			intentTx,
