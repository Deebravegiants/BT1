### Title
Local orb-side "enrollment success" state trusted without backend commit in user-centric signups - ([File: src/plans/mod.rs])

### Summary
In `do_signup`, when a signup is flagged `user_centric_signup` (a flag supplied by the *user's own QR-code payload*, not verified against any authoritative server-side action for the enrollment itself), the Orb decides enrollment success purely from its own local, in-memory `signup_reason` value instead of calling the backend enrollment flow (`enroll_user::Plan::run`, which performs `signup_post`/`signup_poll` against the server and waits for the server's authoritative confirmation).

### Finding Description
The `do_signup` function computes `signup_reason` (`Normal`/`Fraud`/`Failure`) from local pipeline/fraud-detection results, then branches: [1](#0-0) 

For the `user_centric_signup` branch, `debug_report.enrollment_status(...)` and `success` are derived directly from the locally computed `signup_reason`, with **no** network round-trip to the backend to confirm the enrollment/identity binding. This is functionally the same class of bug as the referenced report: a piece of state ("this signup is verified/successful") is committed and acted upon (UI shows success, `SignupEnded{success: true}` is relayed to the app, debug report marked `signup_successful`) based on *local, uncommitted* computation, while the authoritative system-of-record (the backend, analogous to the Cosmos SDK ledger in the report) never independently validates or persists that outcome for this code path. In the non-user-centric branch, the same decision is derived by actually calling `enroll_user::Plan::run`, which submits to `signup_post`/polls `signup_poll` and only reports success after the backend commits it: [2](#0-1) 

`user_centric_signup` itself originates from data returned inside the *user's own QR code* payload (`orb_qr_link::UserData.user_centric_signup`), which is parsed and trusted by `user_status::request`: [3](#0-2) 

Because this flag flows from user/app-supplied data and determines whether the orb bypasses backend confirmation of the signup outcome, this is analogous to the report's "dirty state not committed before privileged action" — here, the privileged action (declaring a signup/enrollment as successfully verified and relaying that to downstream consumers) is taken on local, unconfirmed state instead of the authoritative source.

### Impact Explanation
If the local `signup_reason` computation can be influenced or is inconsistent with what the backend would determine (e.g. any discrepancy between local pipeline/fraud results and server-side validation, or the loss of a would-be backend-side duplicate/fraud check that the `enroll_user` path performs via `signup_post`), a signup could be misattributed as verified success without any backend confirmation step, in the `user_centric_signup` branch. This maps to the "misattributed signup / unauthorized signup" impact category, since the enrollment outcome that's reported to the app (`SignupEnded{success:true}`) and recorded in the debug report is derived without the same backend safety-net (duplicate detection, in-flight-match detection, server-side fraud detection) that the standard `enroll_user` flow provides.

### Likelihood Explanation
This code path is gated by config (`ignore_user_centric_signups`) and by the `user_centric_signup` flag carried in `authenticated_app_data` within the user's QR payload; it is exercised whenever the operator's Orb configuration does not force `ignore_user_centric_signups = true`. I could not fully verify from the indexed code how strongly `user_centric_signup` is authenticated end-to-end beyond the `user_data.verify(user_data_hash)` check shown, nor could I confirm what server-side checks (duplicate/fraud) are actually skipped as a result versus intentionally delegated elsewhere (e.g., to the app/orb-relay flow). This uncertainty limits confidence in exploitability without further investigation of the full backend contract for `user_centric_signup`.

### Recommendation
Do not report `signup_successful`/`enrollment_status(Success)` purely from local, uncommitted state (`signup_reason`) for `user_centric_signup`. If the design intends to skip the classic `enroll_user` HTTP flow for this mode, ensure there is still a positive, authoritative confirmation from the backend (or an explicit documented trust boundary) before marking a signup as successful and relaying that status onward, mirroring the commit-before-branch pattern recommended in the source report.

### Proof of Concept
Not independently reproducible from the indexed code alone — a full PoC would require exercising `do_signup` with `user_centric_signup = true` and a controlled/manipulated pipeline/fraud outcome, and observing that `enroll_user::Plan::run` (with its backend `signup_post`/`signup_poll` confirmation) is never invoked, which I could not execute given tool constraints (read-only code index, no test harness access).
