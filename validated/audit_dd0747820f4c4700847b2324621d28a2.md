### Title
Webhook `shop` tenant identifier is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the `shop` field used by the library to identify the tenant is read from an HTTP header that is never included in the signed bytes. `Registry.process` accepts any request whose body-HMAC is valid and then propagates the header-derived, unauthenticated `shop` value straight into `WebhookMetadata`, which host applications use to select/act on the tenant's session. This breaks the identity binding `shop authenticated == shop acted on`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `#shop` is read from an HTTP header that is completely disjoint from that signable string: [2](#0-1) [3](#0-2) 

`HmacValidator.validate` only verifies the bytes returned by `to_signable_string` against the received HMAC — it never touches headers such as `shop-domain`: [4](#0-3) 

`Registry.process` gates entirely on this body-only HMAC check and then trusts `request.shop` (an unauthenticated header) to build the `WebhookMetadata` object delivered to the host application's handler: [5](#0-4) 

Contrast this with the OAuth callback verifier in the same gem, `Auth::Oauth::AuthQuery`, which correctly folds `shop` into the HMAC-covered content: [6](#0-5) 

So the gem itself demonstrates the correct pattern (bind `shop` into the signed material) in one code path (`AuthQuery`) but omits it in the webhook path (`Request`). The equality that should hold — `shop bytes covered by HMAC == shop value acted upon by Registry/host app` — does not hold for webhooks.

### Impact Explanation
Any internet user can install the target Shopify app on a shop they themselves control (self-service, not privileged access to any victim). Shopify will then deliver a legitimate webhook to the app's public HTTP endpoint containing:
- a raw JSON body
- a valid `X-Shopify-Hmac-Sha256` computed with the app's `client_secret` over that body
- an `X-Shopify-Shop-Domain` header equal to the attacker's own shop

Because `HmacValidator.validate` (and hence `Registry.process`) only checks the raw body against the HMAC and never binds `shop-domain` into that computation, the attacker can replay the exact same body+HMAC pair directly to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `X-Shopify-Webhook-Id`) header with a victim shop's domain. `HmacValidator.validate` still returns `true` (the body bytes are unchanged and correctly signed), so `Registry.process` proceeds and hands the host application a `WebhookMetadata` claiming the data belongs to the victim shop. Any host app logic that keys tenant state, session lookup, or mutating actions off `WebhookMetadata#shop` (a documented, intended usage of this struct) will act on the victim's tenant using attacker-supplied content — a cross-tenant identity-binding bypass carried entirely through this gem's own webhook verification path.

### Likelihood Explanation
The webhook receiving endpoint is a public, unauthenticated HTTP endpoint by design (Shopify calls it directly). Obtaining a valid body+HMAC pair requires nothing more than installing the app on a shop the attacker controls — no `api_secret_key`, no leaked token, no privileged account is needed. The only technical step is forging/replacing one HTTP header on the way to the app's endpoint, which is trivial for anyone who can send arbitrary HTTP requests to that public endpoint.

### Recommendation
Bind the tenant identifier into the HMAC-covered material for webhooks, analogous to how `AuthQuery#to_signable_string` binds `shop`. Concretely, `Webhooks::Request#to_signable_string`/`HmacValidator` should not be the sole basis for trusting `shop`; the library should either (a) require the host app to independently confirm the shop against a known/registered shop domain before processing, or (b) fail closed if the delivered `shop-domain` cannot be cryptographically tied to the signed payload. At minimum, document prominently that `shop` on `WebhookMetadata` is not HMAC-verified and must not be used as a sole tenant-selection key without additional verification (e.g., cross-checking against the webhook subscription/topic registered per shop).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Trigger any subscribed webhook (e.g., `orders/create`); Shopify sends: body `B`, header `X-Shopify-Hmac-Sha256: HMAC(secret, B)`, header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker resends the identical body `B` and identical HMAC header directly to the app's public webhook endpoint, replacing only `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
4. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) verifies `B` against the HMAC — succeeds, since `shop` is not part of `to_signable_string`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-199`) proceeds and builds `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: parsed(B) ...)`, which the host app's handler consumes believing the data genuinely originated from `victim-shop.myshopify.com`.
