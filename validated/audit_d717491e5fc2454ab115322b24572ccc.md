### Title
Missing zero-address validation on `Order.output.beneficiary` permanently burns intent output funds - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`, `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`IntentGatewayV2.placeOrder` accepts an arbitrary, user-supplied `bytes32 beneficiary` inside `Order.output` with no validation that it is non-zero. When a solver later fills that order, both the same-chain and cross-chain fill paths decode this value straight into an `address` and send the filler's output tokens/native value directly to it, with no zero-address guard anywhere in the chain.

### Finding Description
`PaymentInfo.beneficiary` is a `bytes32` supplied entirely by the order-placer and is never validated: [1](#0-0) 

`IntentGatewayV2.placeOrder` stamps `order.user`, `order.source`, and `order.nonce`, but never touches or validates `order.output.beneficiary`: [2](#0-1) 

The only parameter validation routine in the intents stack, `_validateParams`, checks `host`, `dispatcher`, `surplusShareBps`, `protocolFeeBps`, and `priceOracle` — it never validates anything about individual orders or their beneficiaries: [3](#0-2) 

At fill time, both fill paths blindly cast the raw `bytes32` to an `address` and pay it directly:

Same-chain fill (`IntrinsicIntents._fillSameChain`): [4](#0-3) 

Cross-chain fill (`ExtrinsicIntents._fillCrossChain`): [5](#0-4) 

In both cases, when the output asset is the native token (`token == address(0)`), the payout is a raw low-level `.call{value: ...}("")` to `beneficiary`:
- same-chain: `(bool sent,) = beneficiary.call{value: beneficiaryTotal}(""); if (!sent) revert InsufficientNativeToken();`
- cross-chain: `_sendValue(beneficiary, beneficiaryTotal);`

A `.call` to `address(0)` succeeds (it is treated like sending ETH to any EOA with no code), so this never reverts. For ERC20 outputs, `IERC20(token).safeTransferFrom(msg.sender, beneficiary, ...)` is used; while most OZ-compliant tokens revert on transfers to the zero address, this is not guaranteed for every ERC20 that may be listed as an output asset, and the native-token path has no such implicit protection at all.

This is the exact bug class described in the external report: a caller-supplied address that "should not be set to zero" is never checked, and the zero value silently reaches a fund-moving call rather than being rejected up front.

### Impact Explanation
If an order is placed with `output.beneficiary = bytes32(0)` (accidentally or by a buggy integrator/SDK/relayer path building the order), any solver who fills it for the native-token leg sends the solver's real ETH to `address(0)`, and the order's intended payout is permanently and unrecoverably destroyed — the funds are gone from both the gateway and the solver with no way to reclaim them. Because a solver still gets to keep the input tokens escrowed from the original order (the input-side release to `msg.sender` is unaffected by the corrupted beneficiary), the order-placer never receives the swap output they paid for. This is a permanent loss-of-funds condition directly reachable by any account that can call `placeOrder` — an unprivileged, ordinary user action — with no admin or governance step required to trigger it.

### Likelihood Explanation
`placeOrder` is a completely permissionless, frequently used entry point, and `beneficiary` is a raw `bytes32` field with no SDK-side or on-chain enforcement preventing zero. A default-initialized struct (e.g., a bug in an integrating dApp, a partially-filled struct, or a naive encode of a `PaymentInfo` before the beneficiary is set) will silently produce `bytes32(0)`. There is no revert path anywhere between order placement and fund transfer that would catch this, so it can occur unintentionally in production integrations, not just via deliberate attack.

### Recommendation
Add an explicit zero-address check on `order.output.beneficiary` in `placeOrder` (and equivalently validate it before dispatching a cross-chain order), reverting with `InvalidInput()` if `address(uint160(uint256(order.output.beneficiary))) == address(0)`. As defense in depth, also guard the native-token payout paths in `_fillSameChain` and `_fillCrossChain` so a beneficiary of `address(0)` can never receive a `.call{value: ...}` transfer, matching the recommended short-term fix in the referenced report (add zero-address checks for every address parameter that must not be zero) and applying it specifically to the intents/escrow surface reachable by ordinary users and solvers.

### Proof of Concept
1. Any account calls `IntentGatewayV2.placeOrder(order, graffiti)` with `order.output = PaymentInfo({ beneficiary: bytes32(0), assets: [{token: bytes32(0) /* native */, amount: X}], call: "" })` and valid `inputs`. The call succeeds and escrows the input tokens (see `evm/src/apps/IntentGatewayV2.sol:194-415`, no beneficiary check).
2. A solver observes the order and calls `fillOrder` with matching `FillOptions.outputs`, sending `X` ETH as `msg.value`.
3. In `_fillSameChain` (`evm/src/apps/intentsv2/IntrinsicIntents.sol:57-106`), `beneficiary = address(uint160(uint256(0))) = address(0)`, and `beneficiary.call{value: X}("")` succeeds, permanently burning the solver's `X` ETH; the solver still receives the escrowed input tokens via `_withdraw`.
4. The order-placer never receives their intended output — the funds sent by the solver are irrecoverably lost at `address(0)`, and no revert or recovery mechanism exists anywhere in the flow.
