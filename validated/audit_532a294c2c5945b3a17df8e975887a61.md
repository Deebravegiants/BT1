### Title
Rebasing/interest-bearing input tokens escrowed by IntentGatewayV2 have their yield permanently locked due to static internal escrow accounting - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentGatewayV2`/`IntentsBase` escrows order input tokens in the `_orders[commitment][token]` mapping as a fixed numeric amount recorded at `placeOrder` time [1](#0-0) . If the escrowed token is a rebasing/interest-accruing ERC20 (e.g. stETH, aTokens), the contract's actual token balance can grow while the order sits in escrow, but `_withdraw`/`withdraw` only ever release the originally recorded `_orders[commitment][token]` amount and decrement it by exactly that [2](#0-1) . The rebase-accrued surplus is never attributed to any commitment and is not part of the user-facing escrow release path, so it becomes stuck in the contract, analogous to the reported `EnjoyoorsVaultDeposits._deposit` bug where internal balance tracking (`userSupply[token][msg.sender] += amount`) ignores rebasing growth.

### Finding Description
When a user places an order, `IntentGatewayV2._placeOrder` credits escrow as a static integer:
```solidity
_orders[commitment][token] = reducedInputs[i].amount;
``` [3](#0-2) 

The contract is explicitly built to measure *actual received balance* to defend against fee-on-transfer tokens at deposit time (balance-before/balance-after diffing) [4](#0-3) , but this only reconciles balance *at deposit*. It performs no analogous reconciliation at *release* time, nor does it periodically re-sync the escrow ledger to the token's live balance.

Release of escrow always uses the static `_orders[commitment][token]` figure:
```solidity
uint256 escrowed = _orders[body.commitment][token];
if (escrowed == 0) revert UnknownOrder();
_orders[body.commitment][token] = escrowed - amount;
IERC20(token).safeTransfer(beneficiary, amount);
``` [5](#0-4) 

If the escrowed input token rebases upward while an order is pending (waiting for a cross-chain fill, a GET-response cancellation check, or simply sitting until filled/cancelled), the contract's `balanceOf(this)` for that token increases beyond the sum of all `_orders[...][token]` entries. There is no mechanism in `IntentsBase`/`IntentGatewayV2` to attribute or release that surplus to the order's beneficiary — the only sweep path, `SweepDust` (`RequestKind.SweepDust`), is restricted to hyperbridge-originated governance requests and is intended for protocol-fee dust captured during `placeOrder`/`fillOrder`, not for arbitrary post-escrow token growth belonging to a specific commitment [6](#0-5) .

### Impact Explanation
Any solver or user who submits an order using a rebasing ERC20 as an input token will have their rebase rewards permanently locked in the gateway contract once escrowed, with no path for the depositor, solver, or protocol logic to recover them through the normal intent lifecycle (fill, cancel, refund, or redeem). This is a genuine freezing-of-funds condition reachable by an ordinary unprivileged user submitting a single `placeOrder` transaction with a rebasing token — no admin or governance action is required to trigger the loss, only to (partially) rescue it via the restricted `SweepDust` governance path, which routes to a governance-chosen beneficiary rather than the original depositor.

### Likelihood Explanation
Likelihood depends on whether integrators/solvers use rebasing tokens (stETH, aTokens, etc.) as intent inputs — the contract places no restriction preventing this, and its fee-on-transfer handling tests suggest it is intended to support "exotic" ERC20 behavior generally [7](#0-6) . The longer an order sits unfilled/unredeemed (e.g. cross-chain orders awaiting relayed proofs), the larger the accrued, unrecoverable surplus.

### Recommendation
Either explicitly disallow known rebasing tokens as intent inputs, or convert internal escrow accounting to a share-based model (mirroring the external report's primary recommendation): record a share of the token's balance at deposit time and compute the actual amount to release proportionally at withdrawal/refund/redeem time so that rebase gains (or losses) are attributed to the order's rightful owner rather than becoming stranded protocol dust.

### Proof of Concept
1. Deploy `IntentGatewayV2` and register a rebasing ERC20 (mock with a `rebase()`/`setBalance()` function that increases `balanceOf` for all holders proportionally) as an order input token.
2. User calls `placeOrder` with `inputs[0] = {token: rebasingToken, amount: X}`; contract escrows `_orders[commitment][token] = X` per `evm/src/apps/IntentGatewayV2.sol:364-373`.
3. Invoke the mock token's rebase function to increase `balanceOf(address(intentGateway))` by e.g. 5%, without any user interaction.
4. Solver fills or the order times out and is refunded/redeemed via `_withdraw`; the transferred amount is exactly `X` (per `evm/src/apps/intentsv2/IntentsBase.sol:461-469`), leaving the 5% rebase surplus permanently in the contract with no `_orders` entry referencing it and no user-callable function to claim it.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
