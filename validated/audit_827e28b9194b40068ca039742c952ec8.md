Audit Report

## Title
Unauthenticated resource-exhaustion via unbounded per-owner rate-limiter tenant creation in Vault gateway request validation - ([File: core/capabilities/vault/validator.go])

## Summary
`RequestValidator.ValidateSecretIdentifier` invokes three owner/namespace/key-length `BoundLimiter.Check` calls scoped via `contexts.WithCRE(ctx, contexts.CRE{Owner: idOwner})` using attacker-supplied identifier strings, and this function is called from every pre-authentication structural validator (`validateWriteRequest`, `ValidateDeleteSecretsRequest`, `ValidateListSecretIdentifiersRequest`) before `authorizeAndStamp`/`AuthorizeRequest` ever runs. The codebase's own comments and a dedicated regression test (`ciphertext_limiter_tenant_test.go`) confirm that checking a scoped `BoundLimiter` registers a persistent per-owner tenant with a background updater goroutine, and that this exact class of pre-auth registration was deliberately fixed for the ciphertext-size limiter (split into `ValidateCiphertextSizes`, deferred post-auth) — but the identical fix was never applied to the identifier length limiters.

## Finding Description
`ValidateSecretIdentifier` scopes three limiter checks (`MaxIdentifierOwnerLengthLimiter`, `MaxIdentifierNamespaceLengthLimiter`, `MaxIdentifierKeyLengthLimiter`) to the caller-supplied `idOwner` via `contexts.WithCRE`: [1](#0-0) 

This function is reached pre-authorization through three call sites: `validateWriteRequest` (used by `ValidateEncryptedSecretsStructure`, invoked for `SecretsCreate`/`SecretsUpdate` before `authorizeAndStamp`), `ValidateDeleteSecretsRequest`, and `ValidateListSecretIdentifiersRequest`: [2](#0-1) [3](#0-2) [4](#0-3) 

In `GatewayVaultRequestProcessor`, these validators run strictly before `authorizeAndStamp` (which calls `authorizer.AuthorizeRequest`), for all four vault write/delete/list request types: [5](#0-4) [6](#0-5) [7](#0-6) 

Critically, the code base explicitly documents this exact hazard and had already fixed it for the ciphertext-size limiter, deferring that specific check to `ValidateCiphertextSizes`, which is only invoked after `authorizeAndStamp` succeeds with the authorized owner: [8](#0-7) [9](#0-8) 

A dedicated regression test, `TestGatewayVaultRequestProcessor_ProcessRequest_UnauthorizedWriteNeverTouchesCiphertextLimiter`, exists precisely to guard against pre-auth tenant creation for the ciphertext limiter, and its comment states plainly that "checking `MaxCiphertextLengthLimiter` with an owner-scoped context registers a per-owner tenant (with a persistent background updater goroutine) in the limiter, so it must never be consulted before the request is authorized": [10](#0-9) [11](#0-10) 

No equivalent split/deferral or regression test exists for `MaxIdentifierOwnerLengthLimiter`, `MaxIdentifierNamespaceLengthLimiter`, or `MaxIdentifierKeyLengthLimiter` — a search across the repository confirms these are referenced only in `validator.go` (pre-auth call sites) and in unrelated OCR2 plugin test/config code, not in any post-auth-only path or gateway processor guard. `GatewayHandler.HandleGatewayMessage` is the gateway-connector entrypoint that dispatches every inbound `SecretsCreate`/`SecretsUpdate`/`SecretsDelete`/`SecretsList` message straight into `ProcessRequest` (i.e., into these pre-auth validators) with no prior authentication of the sender: [12](#0-11) 

## Impact Explanation
This is CWE-400 (Uncontrolled Resource Consumption): an unauthenticated request can force creation of a persistent, per-owner rate-limiter tenant (with its own background updater goroutine, per the codebase's own comments and tests) keyed off an attacker-controlled `owner`/`namespace`/`key` string, before authorization ever runs and regardless of whether the request is ultimately rejected. Repeated requests with distinct arbitrary owner values accumulate unbounded limiter tenants and goroutines in the vault-capable node/gateway process, a legitimate availability/resource-exhaustion impact for an unauthenticated party.

## Likelihood Explanation
High. No authentication, allowlist membership, or valid ownership is required to reach `ValidateSecretIdentifier` — `HandleGatewayMessage` runs `ProcessRequest` (and therefore the vulnerable validators) before `AuthorizeRequest` for `SecretsCreate`, `SecretsUpdate`, `SecretsDelete`, and `SecretsList`. Any client able to reach the gateway/connector with syntactically valid JSON-RPC requests can trigger this repeatedly with distinct owner strings, batched up to `MaxBatchSize` per request.

## Recommendation
Apply the same fix pattern already used for the ciphertext-size limiter: split `ValidateSecretIdentifier` into a stateless structural check (format/regex validation, performed pre-auth) and a separate owner/namespace/key length limiter check that is deferred until after `authorizeAndStamp` succeeds, using the authorized owner. Add a regression test analogous to `TestGatewayVaultRequestProcessor_ProcessRequest_UnauthorizedWriteNeverTouchesCiphertextLimiter` asserting that `MaxIdentifierOwnerLengthLimiter`/`MaxIdentifierNamespaceLengthLimiter`/`MaxIdentifierKeyLengthLimiter` are never consulted before authorization succeeds.

## Proof of Concept
1. As an unauthenticated client capable of reaching the gateway connector, send a `SecretsList` request with `owner: "owner-0001"` (or `SecretsCreate`/`SecretsUpdate`/`SecretsDelete` with an encrypted-secret/id referencing an arbitrary owner).
2. `GatewayHandler.HandleGatewayMessage` dispatches to `requestProcessor.ProcessRequest` → `processListSecretIdentifiersRequest` → `ValidateListSecretIdentifiersRequest` → `ValidateSecretIdentifier`, which calls `MaxIdentifierOwnerLengthLimiter.Check` scoped to `owner-0001`, registering a new limiter tenant and its background updater — before `authorizeAndStamp`/`AuthorizeRequest` runs.
3. Authorization subsequently fails (owner not allowlisted), but the tenant/goroutine created in step 2 is never torn down.
4. Repeat with `owner-0002`, `owner-0003`, ... to accumulate unbounded limiter tenants/goroutines, verifiable via a Go test that instruments a recording `BoundLimiter` (as in `recordingCiphertextLimiter`) wired into `MaxIdentifierOwnerLengthLimiter`, asserting checks are recorded for distinct unauthorized owners even when `AuthorizeRequest` returns an error.

func TestGatewayVaultRequestProcessor_ProcessRequest_UnauthorizedWriteNeverTouchesCiphertextLimiter(t *testing.T) {
	t.Parallel()

	for _, method := range []string{vaulttypes.MethodSecretsCreate, vaulttypes.MethodSecretsUpdate} {
		for _, stripOwnerPrefix := range []bool{false, true} {
			t.Run(fmt.Sprintf("%s/stripOwnerPrefix=%t", method, stripOwnerPrefix), func(t *testing.T) {
				t.Parallel()

				validator, recorder := mustNewRecordingValidator(t)

				// One-byte hex value under a fresh owner passes structure validation
				// (publicKey is nil so label validation is skipped), reaching authorization.
				secrets := []*vaultcommon.EncryptedSecret{
					{Id: &vaultcommon.SecretIdentifier{Owner: "0xnewowner", Key: "k"}, EncryptedValue: "00"},
				}
				req := mustWriteRequest(t, method, secrets)

				authorizer := vaultcapmocks.NewAuthorizer(t)
				authorizer.EXPECT().AuthorizeRequest(t.Context(), mock.Anything).Return(nil, errors.New("not authorized"))

				processor := mustNewGatewayVaultRequestProcessor(t, validator, authorizer, stripOwnerPrefix)
				_, err := processor.ProcessRequest(t.Context(), &req, nil)
				require.Error(t, err)
				require.ErrorContains(t, err, "request not authorized")
				require.Empty(t, recorder.recorded(), "owner-scoped ciphertext limiter must not be consulted before authorization")
			})
		}
