### Title
Stale user-QR validation state reused across signup without re-accrual of backend status - (File: src/plans/mod.rs)

### Summary
`LendingPair.liquidateAccount`'s bug class is: a critical state-changing operation consumes a cached/local snapshot of authorization state instead of re-fetching/refreshing it immediately before acting, letting a party exploit the staleness window. The closest reachable analog in orb-core is `MasterPlan::scan_remaining_qr_codes`, which reuses a previously-fetched `backend::user_status::UserData` (fetched once at QR-scan time) for the entire enrollment/signup pipeline as long as the *operator* QR-code timestamp hasn't expired — with no re-validation of the *user's* backend status right before the security-sensitive operations (enrollment request, PCP key usage) actually run.

### Finding Description
`user_status::request()` in [1](#0-0)  is the backend call that authorizes a user QR-code for signup: it returns `valid` and, if valid, backend-issued encryption keys and `authenticated_app_data` (identity commitment, `pcp_version`, `user_centric_signup`, `orb_relay_app_id`). This is the analog of the interest-rate/borrower-state accrual: it represents the authoritative, time-varying backend decision about whether this user is currently allowed to sign up.

In `MasterPlan::scan_remaining_qr_codes`, once a user QR-code has been scanned and validated (producing `QrCodes::Both { operator_data, user_qr_code, user_data, .. }`), that same `user_data` is later reused, "as-is," as long as the *operator* code hasn't expired — the user's authorization state itself is never re-checked: [2](#0-1) 

Note the guard is purely on `operator_data.timestamp.elapsed() < operator_qr_expiration_time`; there is no equivalent freshness check on when `user_data` was fetched from the backend. This cached `user_data` (and its embedded backend keys/flags) is what flows unmodified into `do_signup`, `enroll_user`, and PCP credential construction: [3](#0-2) [4](#0-3) 

This mirrors the reported bug precisely: `liquidateAccount` calls `_accrueAccountInterest` (a stale, non-refreshing read) instead of `accrueAccount` (which pulls the current, authoritative interest index) right before performing the liquidation decision. Here, the orb performs the entire signup/enrollment decision using a previously-fetched authorization snapshot instead of re-querying `user_status::request()` immediately before the security-sensitive `enroll_user`/PCP-upload steps, even though there is a legitimate multi-step delay (QR scan → 3s wait → biometric capture → biometric pipeline → enrollment) during which the backend's view of that user (e.g., fraud flags, revoked status, updated policy) could change.

### Impact Explanation
If a user's backend-side eligibility (fraud status, `user_centric_signup` flag, `pcp_version`, `orb_relay_app_id`, or data policy) changes between the initial QR validation and the actual enrollment call, the orb will still act on the original snapshot: it will proceed to run the full biometric pipeline, build the personal custody package, and call `enroll_user`/`signup_post::request` using the identity/keys/flags validated at scan time rather than at action time. Because `id_commitment` and PCP encryption keys are derived from this cached `UserData`, this can lead to enrollment attempts being carried out for a user whose current backend status should have blocked or altered them (e.g. re-checked fraud status, revoked signup eligibility, or changed `user_centric_signup`/`pcp_version` semantics), a form of authorization/state leakage analogous to the interest-skip bug — no direct destruction of biometric data occurs, but the orb can act on outdated authorization decisions instead of the current one.

### Likelihood Explanation
This path is reachable by any unprivileged operator/user flow using the self-serve or normal QR scanning process, since it only requires being inside the `operator_qr_expiration_time` window (which can be tens of seconds to minutes depending on config) between validation and the actual signup completion — no special privileges, hardware access, or malicious peer/operator behavior is required. However, exploiting the staleness in a meaningful way (i.e., causing a backend state transition to happen exactly within this window) depends on external timing and backend-side state changes, so likelihood is moderate rather than trivially reproducible on demand.

### Recommendation
Re-validate the user's backend status (re-invoke `backend::user_status::request`) immediately before the enrollment-critical steps (`enroll_user`/`signup_post::request`, or before assembling `personal_custody_package::Credentials`) rather than relying on the `user_data` captured at initial QR scan time. At minimum, add an explicit freshness/expiration check on `user_data`/its retrieval timestamp analogous to the operator QR expiration check, so a stale authorization snapshot cannot silently drive the final enrollment decision.

### Proof of Concept
1. Configure `operator_qr_expiration_time` to a non-trivial value (default config-driven).
2. Scan operator QR + user QR; `backend::user_status::request` succeeds and returns `UserData` reflecting the user's current backend status at that moment, cached into `QrCodes::Both`.
3. Delay entering `do_signup`/`scan_remaining_qr_codes` (e.g., due to biometric capture retries, slow pipeline) while staying within `operator_qr_expiration_time`.
4. During this window, have the backend change the user's authorization status (e.g., flag as fraud/duplicate, or change `user_centric_signup`/`pcp_version`).
5. Observe that `scan_remaining_qr_codes` takes the `QrCodes::Both { .. } if operator_data.timestamp.elapsed() < operator_qr_expiration_time` branch [5](#0-4)  and returns the original, now-stale `user_data` without re-querying the backend, allowing enrollment to proceed based on outdated authorization state.
