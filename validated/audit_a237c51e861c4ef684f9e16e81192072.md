### Title
Webhook shop identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` binds only the raw HTTP body to the HMAC signature, while the `shop` (and `topic`/`api_version`/`webhook_id`) values used for tenant identification and business logic are read from unauthenticated headers. `ShopifyAPI::Webhooks::Registry.process` accepts the request as valid whenever the raw-body HMAC checks out, then hands the header-derived `shop` value to the app's handler as the authoritative tenant identifier — an identity binding is broken in exactly the pattern the external report describes (a field acted on but not covered by the integrity check).

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` (and `topic`, `api_version`, `webhook_id`) are pulled straight from HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string`, i.e. the raw body, and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` treats this body-only HMAC check as sufficient authentication for the entire request, then forwards the unauthenticated `request.shop` (and topic/api_version/webhook_id) straight to the app's handler as `WebhookMetadata`: [4](#0-3) 

The equality the library implicitly claims to guarantee is:
`shop-that-signed-the-payload == shop-header-value-delivered-to-the-handler`

But the HMAC only proves `raw_body` was produced with `api_secret_key`; it says nothing about which shop domain that body belongs to. Any party capable of capturing one authentic webhook delivery for shop A (e.g. a legitimate merchant who has installed the app and can observe their own app's webhook traffic, or anyone with visibility into a request that transits an intermediary) can resend that exact signed body to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header for shop B. `Utils::HmacValidator.validate` will still return `true` because the signed bytes (raw body) are unchanged, yet `Registry.process` will call the handler with `WebhookMetadata#shop == shop B`, so an app that uses this value to select the tenant's session/database record (the documented and expected usage — see `docs/usage/webhooks.md`) will act on shop B's data/tenant context using content that was actually authorized only for shop A.

### Impact Explanation
This breaks the tenant boundary the HMAC is meant to establish: the library's own model tells app developers that `Utils::HmacValidator.validate`/`Registry.process` succeeding means the request is authentic for the shop identified in `WebhookMetadata#shop`. Since the shop identity is not covered by the signature, an attacker can present body content genuinely signed for tenant A as if it belongs to tenant B, resulting in cross-tenant data confusion/access when the host application (following the library's documented pattern) keys its business logic off `WebhookMetadata#shop`.

### Likelihood Explanation
High. No access token, `client_secret`, or privileged credentials are needed — only the ability to replay an HTTP POST to the app's public webhook endpoint with an attacker-controlled `shop-domain` header and a body/HMAC pair obtained from any single authentic webhook delivery (which the attacker's own installed instance of the app legitimately receives). No parsing/verification gap needs to be found elsewhere; this is a direct consequence of the library's `to_signable_string` implementation.

### Recommendation
Bind the shop identity to the signature verification, not just the raw body. Options:
- Extend `to_signable_string` (or add a second explicit check in `HmacValidator`/`Registry.process`) to incorporate the `shop-domain` header into what is HMAC-validated, or
- Cross-check `request.shop` against an independently-trusted value (e.g., the session/shop this webhook subscription was registered for) before invoking the handler, rejecting mismatches.
At minimum, the documentation and `Registry.process` should make explicit that `WebhookMetadata#shop` is unauthenticated and must not be trusted for tenant selection without an additional binding check.

### Proof of Concept
1. App installs webhook handler and receives an authentic webhook for `shop-a.myshopify.com`:
   ```
   POST /webhook
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of BODY using api_secret_key>
   x-shopify-shop-domain: shop-a.myshopify.com
   BODY: {"id":1,...}
   ```
2. Attacker (who received this webhook, e.g. as the legitimate owner of shop-a, or via a MITM/logging proxy) replays the exact same `BODY` and `x-shopify-hmac-sha256` value, but changes the header:
   ```
   POST /webhook
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <same valid HMAC, unchanged>
   x-shopify-shop-domain: shop-b.myshopify.com
   BODY: {"id":1,...}
   ```
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `BODY` against the HMAC — validation succeeds [5](#0-4) .
4. The handler receives `WebhookMetadata` with `shop: "shop-b.myshopify.com"` even though the payload/HMAC pair was only ever authorized for `shop-a.myshopify.com` [6](#0-5) , causing the host app to process shop-a's authenticated data under shop-b's tenant context.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
