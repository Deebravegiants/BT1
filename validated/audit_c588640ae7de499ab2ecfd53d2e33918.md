### Title
Predictable, unsigned session identifiers allow cross-tenant session hijacking - ([File: lib/shopify_api/auth/session.rb], [File: lib/shopify_api/auth/oauth.rb], [File: lib/shopify_api/utils/session_utils.rb])

### Summary
For non-embedded (and embedded-without-token) apps, `ShopifyAPI::Auth::Oauth.validate_auth_callback` stores the deterministic `Session#id` value directly as the cookie value, and `ShopifyAPI::Utils::SessionUtils.cookie_session_id` later trusts that raw cookie value as the session identifier with no additional signature or secret binding it to the browser that actually completed OAuth for that shop.

### Finding Description
`Session.from` builds the session `id` purely from public, guessable inputs: `"offline_#{shop}"` for offline tokens, or `"#{shop}_#{associated_user.id}"` for online tokens. [1](#0-0) 

After OAuth completes, `Oauth.validate_auth_callback` sets this same deterministic value as the raw content of the `shopify_app_session` cookie (for non-embedded apps), with no HMAC or signature over it: [2](#0-1) 

`SessionCookie` is a plain value/expiry struct with no signing support at all: [3](#0-2) 

When a later request comes in, `SessionUtils.current_session_id` -> `cookie_session_id` simply echoes back whatever value is present in the incoming `shopify_app_session` cookie as the trusted session id, used by the host application to look up the stored session (and its access token) — no verification that this value was ever actually issued by this gem's OAuth flow: [4](#0-3) [5](#0-4) 

The broken binding is:
`cookie_value_trusted_as_session_id == id_issued_by_this_gems_oauth_flow_for_the_authenticated_shop`

In reality, `cookie_value_trusted_as_session_id` is fully attacker-constructible (`"offline_" + any_known_myshopify_domain`), because the id has no random or secret component and the cookie carrying it is never signed. An unprivileged internet user who is a normal (or trial) merchant of the same app can set their own browser's `shopify_app_session` cookie to `offline_<victim-shop>.myshopify.com` (myshopify domains are guessable/enumerable, or simply known if the attacker has ever interacted with the victim's storefront) and present it to the host application, which will look it up in its session store and retrieve the victim shop's real session/access token.

### Impact Explanation
If exploited, this yields cross-tenant access: an attacker obtains the session object (and therefore the access token) belonging to a different merchant's shop, purely by guessing a predictable string and forging their own cookie — no credential of the victim or the app is required. This matches the "cross-tenant access" / "session fixation" impact category.

### Likelihood Explanation
Likelihood depends on how the host application's session storage is implemented (this is delegated outside this gem, e.g. to `shopify_app`), but this gem is the origin of both the predictable id generation and the unsigned cookie value that callers are told to trust as the session key. Any host app following the documented `validate_auth_callback` / `current_session_id` API as intended inherits this weakness without any additional mitigation from this gem.

### Recommendation
- Use a random, unguessable session id (e.g. `SecureRandom.uuid`, which `Session#initialize` already supports as a default) instead of the deterministic `"offline_#{shop}"` / `"#{shop}_#{user_id}"` scheme for values that will be exposed to the client via cookie.
- Sign or HMAC the cookie value (or use a signed/encrypted cookie jar) so that `cookie_session_id` can verify the value was actually issued by this gem's OAuth flow before treating it as a trusted lookup key.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`; note that offline sessions are keyed as `"offline_#{shop}"` per `Session.from`. [6](#0-5) 
2. Attacker learns/guesses the victim's myshopify domain, e.g. `victim-shop.myshopify.com` (public storefront domains are often discoverable).
3. Attacker sets their own `shopify_app_session` cookie to the value `offline_victim-shop.myshopify.com` and sends a request to the host application.
4. The host application calls `SessionUtils.current_session_id`, which returns the raw cookie value unchanged. [4](#0-3) 
5. The host app loads the session for id `offline_victim-shop.myshopify.com` from its session store, obtaining the victim's real access token, and processes the attacker's request as if it were the victim shop.

# typed: strict
# frozen_string_literal: true

module ShopifyAPI
  module Auth
    module Oauth
      class SessionCookie < T::Struct
        extend T::Sig

        SESSION_COOKIE_NAME = "shopify_app_session"

        const :name, String, default: SESSION_COOKIE_NAME
        const :value, String
        const :expires, T.nilable(Time)

        alias_method :eql?, :==
        sig { params(other: T.nilable(SessionCookie)).returns(T::Boolean) }
        def ==(other)
          return false unless other

          name == other.name &&
            value == other.value &&
            expires == other.expires
        end
      end
