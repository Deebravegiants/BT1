### Title
Pool `repay` refunds the full declared `amount` out of real token custody without verifying any inbound transfer or debiting `cash` — ([File: contracts/pool/src/ops/repay.rs](rs-lending-xlm--004/contracts/pool/src/ops/repay.rs))

### Summary
Analogous to the vesting `recoverERC20()` bypass, the pool's repay leg has a second, unaccounted exit path for tokens: the overpayment refund. `repay::apply` calls `transfer_out(payer, overpayment)` which moves real tokens but, unlike `borrow`/`withdraw`/`claim_revenue`, never calls `debit_cash` and never checks `require_reserves`. The function trusts that "the controller transfers the repay amount into the pool before this call," but nothing on-chain enforces that precondition. The codebase's own test `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` proves that a repay with no inbound transfer and no debt pays the entire declared amount out of pool custody with the cash book untouched.

### Finding Description
In `contracts/pool/src/ops/repay.rs:25-34`, `apply` resolves `(burned, overpayment) = cache.resolve_repay(amount, position)`, credits only `net_repay = amount - overpayment` to `cash`, and then unconditionally refunds `overpayment` to `payer` via `Cache::transfer_out`. `transfer_out` (`contracts/pool/src/cache/cash.rs:46-53`) performs a raw token transfer and explicitly "does not adjust accounting cash" and skips `require_reserves`. The pool therefore pays `overpayment` out of real custody regardless of how many tokens were actually received for this call.

When outstanding debt is zero, `resolve_repay` takes the full-close branch: `net_repay == 0` (allowed by the `RepayRoundsToZeroShares` assert at `repay.rs:48-52`), so `overpayment == amount` — the caller's entire declared `amount` is refunded from custody while `cash`, `supplied`, and `borrowed` are unchanged. This mirrors the report exactly: `claim()` updates `totalClaimed`, `recoverERC20()` does not; here the debt-burn/cash-credit path is "accounted" while the refund path silently spends the same physical balance.

The vulnerability materializes through the "already funded" repay surface: `repay_prefunded_position` (`contracts/controller/src/positions/debt.rs:235-256`) repays "a resolved debt from funds already received by the pool" and refunds excess to `refund_to`. Any strategy/liquidation flow that reaches this with a `req.amount` larger than the tokens actually delivered to the pool (e.g., a fee-on-transfer or deflationary inbound leg measured by declared rather than measured amount) produces an overpayment refund paid out of the pool's pre-existing reserves — other suppliers' liquidity — not out of the leg's proceeds. Additionally, if the pool's `repay` entrypoint does not independently require that funds arrived (I could not fully confirm the auth gating in `pool/src/lib.rs` from the indexed excerpts), a direct call `repay(payer = self, amount = pool_balance)` on a debt-free market reproduces the test and drains custody outright.

### Impact Explanation
Theft of user funds / protocol insolvency: the refund consumes real token balance backing supplier claims (`supplied` shares) while leaving `cash` unchanged, so books overstate reserves and later withdrawals/claims fail — the exact "claim ahead of schedule by bypassing the tracked counter" impact of the vesting bug.

### Likelihood Explanation
The unsafe primitive is confirmed by the in-repo test (`contracts/pool/tests/flows.rs:3578-3611`): a declared repay with zero funding and zero debt drains custody to `payer`. Reachability by an unprivileged address depends on whether any allowed entrypoint (repay, repay_debt_with_collateral, liquidation, or a direct pool call) lets the caller set `action.amount` above the measured inbound amount for a prefunded repay; the design relies on an off-chain ordering assumption rather than a balance-delta check, which is the root cause.

### Recommendation
Make the refund self-funded: either (a) measure the pool's actual balance delta for the leg and cap `overpayment` at `min(overpayment, received_delta)`, or (b) debit the refund from `cash` (`cache.debit_cash(overpayment)` inside `repay::apply` before `transfer_out`) so an unfunded refund panics with `InsufficientLiquidity` instead of spending the book silently. Apply the same fix to `ops::recapitalize::apply`, which the same test file documents as sharing the unfunded-refund gap.

### Proof of Concept
1. Market has `cash = C`, real custody `= C`, `borrowed = 0` (or attacker has fully repaid).
2. Attacker reaches a repay leg with `action.amount = C` while the pool receives `0` (direct call if auth-permitted, or a prefunded path where the promised inbound leg delivers less than declared).
3. `resolve_repay` returns `overpayment = C`, `net_repay = 0`; assert passes.
4. `transfer_out(attacker, C)` sends the full reserve; `cash` remains `C`, `supplied` unchanged.
5. Suppliers' shares are now unbacked — the contract cannot operate for lack of token funds.

Reference implementation in-repo: `contracts/pool/tests/flows.rs:3590-3611` executes exactly this sequence and asserts custody was drained with the book untouched.

Caveat: the index excerpts did not reveal whether `pool::repay` enforces `payer.require_auth()` only (exploitable directly) or a controller-only gate (exploitable only via an unmeasured prefunded strategy leg); the unsafe refund mechanic itself is confirmed.
