### Title
Missing L2 sequencer uptime check in `SimplexPaymaster` oracle pricing allows stale/incorrect gas-token pricing during sequencer downtime - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster._getOraclePrice` fetches Chainlink `latestRoundData()` and rejects non-positive answers and prices older than `maxOracleAge`, but never checks the Arbitrum/Optimism/Base L2 sequencer-uptime feed. When a sequencer goes down, Chainlink price feeds on these L2s can return the last cached round with a `updatedAt` timestamp that still looks fresh (because there is no new L2 block advancing `block.timestamp` at the same rate, or the grace period is not observed), so `_getOraclePrice` can accept a price that is effectively stale relative to real market conditions during/immediately after a sequencer outage.

### Finding Description
`_getOraclePrice` is: [1](#0-0) 
It is called from `_tokenPrice`, which prices both the native asset and the ERC-20 fee token via two separate Chainlink oracles: [2](#0-1) 
This is exactly the pattern flagged in the external report: `latestRoundData()` is trusted for price without any check on the health of the underlying L2 sequencer that relays these blocks/timestamps to the chain. Chainlink's documented mitigation for this is to also read a chain-specific `SequencerUptimeFeed` and reject pricing (or require a grace period after recovery) when the sequencer has been down. `SimplexPaymaster` implements neither.

The `nativeOracle` and per-token `tokenOracle` config are governance-set and immutable to attackers, but the deployment itself targets Arbitrum, Optimism and Base — the three most common L2s where Chainlink explicitly recommends a sequencer-uptime check: [3](#0-2) [4](#0-3) 

The deploy script confirms `maxOracleAge` is only tuned around heartbeat cadence, with no sequencer-feed parameter at all: [5](#0-4) 

### Impact Explanation
`SimplexPaymaster` is an unprivileged, permissionless ERC-4337 paymaster: any UserOperation sender can trigger `_tokenPrice`/`_getOraclePrice` through `fetchDetails`/`validate`/`estimateTokenCost` without any authorization check. If the sequencer for Arbitrum, Optimism, or Base goes down (or has just recovered, before Chainlink's recommended grace period), an attacker/solver can submit UserOperations that get priced off a Chainlink answer that is inconsistent with the true, live off-chain market price, letting them pay less token value than the real gas cost (or pull an artificially favorable gas-token conversion), causing a direct loss of the surplus/markup the paymaster is designed to collect, and in the worst case draining the paymaster's EntryPoint deposit faster than the treasury markup can compensate for it. This is a real fund-loss vector for a live, permissionless contract holding pooled gas deposits and collecting token markup for the treasury.

### Likelihood Explanation
Sequencer downtime on Arbitrum/Optimism/Base has occurred historically (documented multi-hour outages), and once it occurs, the missing check is silently exploitable by any unprivileged UserOperation sender interacting with the public paymaster — no governance or relayer compromise is required, only network conditions that Chainlink already warns integrators about.

### Recommendation
Add a chain-specific `SequencerUptimeFeed` (the standard `AggregatorV3Interface`-compatible feed Chainlink publishes per L2) as an additional governance-configurable parameter in `Params`. In `_getOraclePrice` (or a new `_checkSequencer` guard called before pricing), read `latestRoundData()` from that feed, revert if `answer == 1` (sequencer down), and enforce a grace period (e.g. Chainlink's recommended margin) after `startedAt` before trusting subsequent price answers, mirroring the existing `StaleOraclePrice`/`InvalidOraclePrice` revert pattern already present in the contract.

### Proof of Concept
1. Deploy `SimplexPaymaster` on Arbitrum/Optimism/Base per `evm/script/DeploySimplexPaymaster.s.sol`.
2. Simulate sequencer downtime: the underlying Chainlink price aggregator continues to report its last cached `answer`/`updatedAt` within `maxOracleAge` (as shown in `MockOracle` in the test suite, where `updatedAt` is only advanced when `setAnswer`/`setUpdatedAt` is explicitly called) even though the sequencer producing L2 blocks/timestamps is not live: [6](#0-5) 
3. During this window `_getOraclePrice` passes both `answer > 0` and `block.timestamp - updatedAt <= maxOracleAge` checks and returns a price computed from the stale feed.
4. A UserOperation submitted through `fetchDetails`/`validate` is priced (`_tokenPrice`) off this stale value, letting the sender under- or over-pay relative to the live market rate with no sequencer-liveness safeguard in place, as none of the existing tests (`testStaleOracleReverts`, `testNonPositiveOraclePriceReverts`) cover sequencer-down conditions: [7](#0-6)

    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
