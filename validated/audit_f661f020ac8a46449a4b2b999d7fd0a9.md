This confirms the vulnerability. The `Registry.process` method at [1](#0-0)  validates only `Utils::HmacValidator.validate(request)`, which in turn calls `request.to_signable_string` — and `Webhooks::Request#to_signable_string` returns only `@raw_body`, excluding all headers (`shop`, `topic`, `api_version`, `webhook_id`) from the signed content, as shown at [2](#0-1) . Yet `request.shop`, `request.topic`, and `request.webhook_id` — all derived purely from unauthenticated headers via `shopify_header` at [3](#0-2) [4](#0-3)  — are passed straight into the handler via `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` at [5](#0-4) .

### Title
Webhook shop/topic identity spoofing via unauthenticated headers not covered by HMAC - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body [6](#0-5) . The HMAC signature computed by `Utils::HmacValidator` is derived exclusively from `Webhooks::Request#to_signable_string`, which returns only `@raw_body` [2](#0-1) . The `shop`, `topic`, and `webhook_id` values that identify *which tenant and event* the payload belongs to are read directly from HTTP headers (`x-shopify-shop-domain`, `x-shopify-topic`, `x-shopify-webhook-id`) without any cryptographic binding to those values [7](#0-6) .

### Finding Description
This is the same identity-binding bug class as the external report (a value that is *acted upon* is not covered by the integrity check protecting the trusted channel). Here the binding that should hold is:

`hmac_valid(raw_body) ⇒ shop_header == shop_that_the_body_actually_belongs_to`

but the gem only checks `hmac_valid(raw_body)` and then trusts `shop_header` unconditionally for dispatch (`WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` at [5](#0-4) ).

Because the same `api_secret_key` is shared across *all* shops that install a given app, any merchant who has installed the app (an "unprivileged" party relative to other tenants of the same app) can capture a genuine webhook body + valid HMAC that Shopify sent for their own shop, and replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while altering the `x-shopify-shop-domain`, `x-shopify-topic`, or `x-shopify-webhook-id` headers. Because none of these headers are part of the signed content, the replayed request still passes `HmacValidator.validate` at [8](#0-7) , and the handler processes the body as if it legitimately came from the spoofed shop/topic/webhook id.

### Impact Explanation
This breaks the shop-identity boundary between tenants of a multi-tenant app: a merchant (or anyone who intercepts/replays one of their own legitimate webhook deliveries) can inject arbitrary webhook data attributed to a different shop into the host application's webhook handlers. Depending on how the host app uses `WebhookMetadata#shop` (e.g., to look up per-shop session/access tokens, update per-shop records, or trigger redaction/GDPR flows for `shop/redact`, `customers/redact`, `customers/data_request`), this can lead to cross-tenant data corruption or disclosure — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Any app merchant can trivially capture one legitimate webhook delivery to their own endpoint (bodies and HMACs are visible to the receiving app) and replay it with modified headers, since no additional secret or privileged access is required — only observation of one's own genuine webhook traffic, which satisfies the "unprivileged internet user" bar.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed content verified against the HMAC, or otherwise cryptographically bind them (e.g., require the app to independently confirm the `shop` against a known/expected value, such as validating against the shop tied to the specific `webhook_id` returned by Shopify's API) rather than trusting header-supplied values that fall outside `to_signable_string`.

### Proof of Concept
1. App receives a genuine webhook from Shopify for `shop-a.myshopify.com`, topic `orders/create`, with body `B` and valid header `x-shopify-hmac-sha256: H` (computed by Shopify over `B` only).
2. Attacker (owner/operator of `shop-a`, or anyone able to observe that webhook delivery) resends an HTTP POST to the app's webhook endpoint with the same body `B` and the same header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: shop-b.myshopify.com` and/or `x-shopify-topic: shop/redact`.
3. `ShopifyAPI::Webhooks::Request.new` parses these headers and `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `@raw_body` (`B`) only, matching `H` [6](#0-5) .
4. The handler for `shop/redact` (or whatever topic was spoofed) is invoked with `WebhookMetadata.new(topic: "shop/redact", shop: "shop-b.myshopify.com", body: JSON.parse(B), ...)`, causing the host application to act on data for `shop-b` that Shopify never actually sent for that shop.
