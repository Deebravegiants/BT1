Confirmed: `ShopifyAPI::Webhooks::Request` computes its HMAC only over the raw JSON body (`to_signable_string` returns `@raw_body`, `lib/shopify_api/webhooks/request.rb:35-38`), while `topic`, `shop`, `api_version`, and `webhook_id` are pulled straight from unauthenticated HTTP headers (`lib/shopify_api/webhooks/request.rb:15-33`). `Registry.process` validates only that HMAC-over-body (`lib/shopify_api/webhooks/registry.rb:189-190`) and then hands `request.shop` directly to the app's handler as the tenant identifier (`lib/shopify_api/webhooks/registry.rb:198-199`) — without re-deriving or binding shop identity from the signed payload.

### Title
Webhook Tenant Identity (`shop-domain`) Not Covered by HMAC Allows Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#hmac`/`to_signable_string` binds the HMAC signature exclusively to the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` fields — which `Registry.process` uses to route and attribute the webhook to a specific merchant/tenant — are read straight from HTTP headers that are never included in the signed material.

### Finding Description
The correct identity binding should be: `shop attributed by the app == shop that produced the signed body`. Instead the gem enforces only `HMAC(secret, raw_body) == provided_hmac`, independent of the `shopify-shop-domain` (or `x-shopify-shop-domain`) header value. [1](#0-0) [2](#0-1) 

Because every shop that installs the same app shares one `api_secret_key` (`ShopifyAPI::Context.api_secret_key`, used identically for all tenants in `Utils::HmacValidator.validate`), any merchant who legitimately installs the app can capture a valid `(raw_body, hmac)` pair from a webhook fired to their own shop, then replay that exact body+HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop's domain. `Utils::HmacValidator.validate(request)` still succeeds because it only checks the body signature, and `Registry.process` forwards `request.shop` (the attacker-controlled header) straight into `WebhookMetadata` for the app's handler to act on. [3](#0-2) 

This breaks the equality the app relies on for tenant isolation: `request.shop` (used to look up/write per-tenant records) is not the shop that actually authored the signed payload.

### Impact Explanation
This is a cross-tenant integrity issue: an attacker who is merely a legitimate (but malicious) merchant of the app can inject a validly-HMAC'd webhook payload while claiming it originated from a different, victim shop. Any host application that trusts `WebhookMetadata#shop` (populated from `request.shop`) to select which tenant's data to update — which is exactly the pattern the gem's own webhook processing API encourages — will apply attacker-controlled body content under another merchant's identity, i.e., cross-tenant access/injection.

### Likelihood Explanation
Reachable by any unprivileged internet user who can install the app (or observe/intercept one webhook delivery to any shop, since delivery is plain HTTP POST unless the endpoint is otherwise protected) and then replay a raw POST with a forged `shop-domain` header to the app's public webhook endpoint. No access token, `api_secret_key`, or privileged account is required — only a captured/generated valid `(body, hmac)` pair for some topic, which the attacker can produce themselves by installing the app on their own store.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the signable string used for the webhook HMAC check, or otherwise cryptographically bind the shop-domain header to the signed body before it is exposed via `Request#shop` / `WebhookMetadata`. At minimum, document that `request.shop` is not authenticated and must be independently verified against a known-installed shop list.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, triggering a legitimate webhook, e.g. `orders/create`.
2. Attacker's endpoint receives `raw_body` and header `Shopify-Hmac-Sha256: <hmac>` — a valid signature under the shared `api_secret_key`.
3. Attacker replays the identical `raw_body` and `Shopify-Hmac-Sha256` header to the same app's webhook endpoint, but sets `Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` (body/HMAC match), `Registry.process` proceeds, and the handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker's chosen payload>, ...)` — the app processes attacker-controlled data as if it came from the victim's shop.
