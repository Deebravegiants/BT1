### Title
Face self-custody candidate frame selection accepts any higher-scoring face in view, permanently overwriting the legitimate captured identity photo for the signup - ([File: src/plans/biometric_capture/mod.rs])

### Summary
`biometric_capture::Plan::handle_face_identifier` selects the "self-custody candidate" face frame — the RGB face image that gets permanently bound to the user's iris-based signup — purely by tracking the highest `IsValidOutput.score` seen across the entire capture session. Just like the reported `RAACMinter` bug where a transient spike in an instantaneous metric (`utilization`) gets latched into a persistent state (`emissionRate`), here a transient higher-scoring face frame (which could belong to a second person who briefly steps into the camera's view) overwrites the true candidate and is irreversibly latched for the remainder of the signup, with no re-validation that it corresponds to the same identity whose iris was captured.

### Finding Description
In `src/plans/biometric_capture/mod.rs`, the `Plan::handle_face_identifier` callback runs on every `face_identifier::Output::IsValidImage` result during biometric capture: [1](#0-0) 

Whenever a new frame's `output.score` exceeds the currently stored `self.self_custody_candidate_rgb` score, the code unconditionally overwrites the candidate:
```
if output.is_valid.map_or(false, |v| v) {
    let highest = self.self_custody_candidate_rgb.as_ref()
        .map_or(0.0, |p| p.estimate.score.unwrap_or_default());
    if output.score.is_some_and(|s| s > highest) {
        self.self_custody_candidate_rgb = Some(FrameInfoSelfCustodyCandidate::new(output, frame...));
        self.face_ir = self.last_face_ir.take();
        self.thermal = self.last_thermal.take();
    }
}
```
There is no check that the face belongs to the same person whose iris frames (`left_ir`/`right_ir`) were captured in the same session — the only gate is `is_valid` (an image-quality validity flag) and a strictly-greater score comparison. This mirrors the reported bug class exactly: an instantaneous, easily-spiked metric (frame validity score) is used to overwrite persistent state (the self-custody candidate) that survives for the rest of the process, even after the manipulating condition (a second face in frame) disappears.

Once selected, this frame is fed directly into the fraud/identity pipeline: `run_face_identifier` in `src/plans/biometric_pipeline/mod.rs` sends `face_self_custody_candidate` (built from `self_custody_candidate_rgb`) to the `face_identifier::Input::Estimate` model call alongside the genuine `frame_left`/`frame_right` images, producing both `FraudChecks` and the `Bundle` used for the user's self-custody package: [2](#0-1) 

The resulting `Capture::face_self_custody_candidate` is subsequently persisted into the Personal Custody Package and is used as the enrolled self-custody image bound to that signup (`src/plans/biometric_capture/mod.rs:587-600`), and identification images including this candidate are the ones stored/uploaded for the signup (`src/agents/image_notary.rs`, `save_identification_images_impl`). [3](#0-2) 

Additionally, this repository is the FOSS build in which fraud checks have been entirely stripped out — `detect_fraud` unconditionally returns `Ok(false)`: [4](#0-3) 

so no downstream fraud/consistency check exists to catch a face/iris identity mismatch introduced this way.

### Impact Explanation
An unprivileged bystander/accomplice standing near the legitimate user during biometric capture can transiently present a higher-quality/higher-score face to the RGB camera (e.g., better lighting, better angle, or simply a face the model scores higher) during the multi-second capture window. That face gets latched permanently as `self_custody_candidate_rgb`, and:
- The wrong person's face image gets bound into the resulting signup's Personal Custody Package and Bundle, alongside the genuine user's iris code — a form of cross-identity/cross-signup state bleed and misattributed biometric data disclosure.
- Because `detect_fraud` is a no-op in this build, there is no compensating control to catch the inconsistency between the enrolled iris and the enrolled face.
- This weakens any subsequent identity verification, account recovery, or dispute-resolution processes that rely on the self-custody photo actually depicting the iris owner.

### Likelihood Explanation
The capture window spans multiple seconds across two eye-scan objectives (`total_objectives`), during which any face passing the `is_valid` check with a higher score overwrites the stored candidate — no temporal debounce, no identity-consistency check with the iris being scanned, and no requirement that the winning frame be the same face throughout. Any bystander able to briefly enter the RGB camera's field of view during a live signup session can trigger this.

### Recommendation
- Bind the self-custody candidate selection to identity-consistency checks against the already-captured iris/face frames (e.g., require face embedding similarity to the primary detected face across the whole session) rather than a bare score comparison.
- Track a time-weighted/majority-vote quality measure instead of an unbounded, single-sample "highest wins" latch, so a momentary outlier frame cannot permanently override the true candidate.
- Reinstate (or replace) fraud/consistency checks so that a face/iris mismatch within a single signup is detected and the signup rejected.

### Proof of Concept
1. Begin a signup as the legitimate user; the biometric capture plan starts iterating IR/RGB objectives.
2. While the legitimate user's iris frames are being scored/stored in `left_ir`/`right_ir`, have a second person briefly lean into the RGB camera's frame with better lighting/angle so that `face_identifier::Output::IsValidImage` reports a higher `score` than the legitimate user's current best.
3. `handle_face_identifier` (src/plans/biometric_capture/mod.rs:295-320) overwrites `self_custody_candidate_rgb` with the second person's frame.
4. The second person steps out of frame; capture completes normally using the legitimate user's iris data.
5. `into_capture()` builds `Capture::face_self_custody_candidate` from the overwritten frame (src/plans/biometric_capture/mod.rs:566-599), which is then used to build the Bundle/PCP and stored identification images — permanently binding a stranger's face to the legitimate user's iris-based signup, with no fraud check (`detect_fraud` returns `Ok(false)`) to catch the mismatch.
