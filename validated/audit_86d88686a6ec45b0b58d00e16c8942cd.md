### Title
Webhook `shop` (and other headers) are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` verifies the JSON payload bytes but never binds the `shop`, `topic`, `webhook_id`, or `api_version` headers to that signature. `Registry.process` nevertheless trusts the unauthenticated `shop` header to build the `WebhookMetadata` passed to the app's handler, which host apps use as the tenant identifier for the event.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
which returns only `@raw_body`. The `shop`, `topic`, `webhook_id` and `api_version` accessors all read directly from HTTP headers that are never part of the signed string: [2](#0-1) [3](#0-2) 

`Registry.process` validates only this body-only HMAC, then constructs `WebhookMetadata` using the unauthenticated `request.shop` header and hands it to the registered handler: [4](#0-3) 

`WebhookMetadata.shop` is the only tenant/shop identity signal delivered to the app's webhook handler: [5](#0-4) 

The documented handler contract explicitly tells integrators to use `data.shop` to key their downstream processing (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`): [6](#0-5) 

Because Shopify apps use a single, shared `client_secret` across every shop that installs the app, the HMAC is computed with the same key regardless of which shop the webhook is destined for. Any merchant who installs the app is a legitimate recipient of real, validly-signed `(body, hmac)` pairs for their own shop. That merchant — an "unprivileged" actor with respect to other tenants of the same app — can capture one of these legitimate webhook deliveries and replay the identical body/HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` (or `x-shopify-shop-domain`) header with a victim shop's domain. Since the signature check only covers the raw body, the forged request passes `Utils::HmacValidator.validate` unchanged, and the app's handler receives `WebhookMetadata` attributing the payload to the victim shop.

This breaks the intended identity binding: `shop authenticated (via the shared-secret HMAC over the body) != shop stored/used as the tenant key (the unauthenticated header value placed into WebhookMetadata.shop)`.

### Impact Explanation
This enables cross-tenant confusion/injection: a malicious installer of the app can make the app process attacker-controlled (or replayed) webhook data under a victim shop's identity. Depending on how the host application uses `data.shop` (e.g., updating shop-scoped records, triggering GDPR `shop/redact`/`customers/redact`/`customers/data_request` mandatory webhook flows, or refreshing shop-scoped caches), this can lead to cross-tenant data corruption or unauthorized triggering of shop-scoped actions for a shop the attacker does not control — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Any merchant who installs the app already receives real, validly HMAC-signed webhook deliveries for their own shop from Shopify, giving them a ready supply of valid `(body, hmac)` pairs. Forging the shop header on a replayed request requires no secret material — only the ability to send an HTTP request with a different header value, which is well within reach of an "unprivileged" tenant of a multi-tenant app.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) to the value verified by the signature — e.g. include these fields in the signable string, or independently verify that the `shop` header belongs to a shop with an active installation/session for this app, or re-derive the shop from a trusted, uniquely-signed webhook attribute (some webhook payloads include the shop domain in the body itself) before trusting it for tenant attribution.

### Proof of Concept
1. App merchant A installs the app on `a.myshopify.com` and receives a legitimate `orders/create` webhook with a valid `X-Shopify-Hmac-SHA256` computed over the JSON body using the app's shared `client_secret`.
2. Merchant A intercepts this `(body, hmac)` pair.
3. Merchant A crafts a new POST to the app's webhook endpoint reusing the identical `body` and `hmac` headers, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `request.to_signable_string` (the raw body) against the hmac — this passes. [7](#0-6) 
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and processes the (attacker-supplied) body as if it originated from the victim shop.
