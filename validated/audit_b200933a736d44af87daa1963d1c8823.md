### Title
Webhook `shop` (and `topic`/`webhook_id`) identity is trusted from unauthenticated HTTP headers while only the raw body is covered by the HMAC, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating an HMAC over the raw request body only, then unconditionally trusts the `shop-domain` (and `topic`, `webhook-id`, `api-version`) HTTP headers to build the tenant identity passed to the app's handler. Because the HMAC signing key (`Context.api_secret_key`) is the app's single client secret shared across every shop that has installed the app, any shop that installs the app can generate a genuinely-signed webhook body for its own actions and then re-send that same signed body to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop. The signature still validates because the header is never part of the signed material, so the app processes attacker-supplied data as if it originated from the victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are read straight from HTTP headers with no cryptographic binding to the body or the HMAC: [2](#0-1) 

`Registry.process` validates only this body-derived HMAC via `Utils::HmacValidator.validate(request)`, then immediately builds `WebhookMetadata` using the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` values and dispatches it to the app's handler: [3](#0-2) 

`WebhookMetadata` treats `shop` as a first-class, trusted field the handler is meant to key tenant-specific behavior on: [4](#0-3) 

The identity binding that should hold is: `shop asserted to the handler == shop that produced/authorized the signed payload`. Because the HMAC secret is the app's `client_secret`, not a per-shop secret, and the `shop-domain` header is outside the signed bytes, this equality is never enforced by the gem. Any of the app's own installer shops (a legitimate, unprivileged relationship — no target credentials or secrets are needed) can capture a validly-signed webhook body for one of its own topics and replay it with the `shop-domain` header swapped to name a different, victim shop. `HmacValidator.validate` (which only ever compares `compute_signature(to_signable_string, secret)` against the header-decoded HMAC) still returns `true`: [5](#0-4) 

This is precisely the pattern flagged in the reference report: a value (`shop`) that is acted upon downstream (used as the tenant key for webhook handling) is not covered by the authenticity check (`HmacValidator`/HMAC), so "verified" and "acted-upon" data diverge.

### Impact Explanation
This crosses a tenant boundary: an attacker who legitimately installs the target app on their own store can forge webhook deliveries that the app will process as belonging to an arbitrary victim shop, since the gem hands the handler a `shop` value that was never authenticated. Any app that uses `WebhookMetadata#shop` to select the tenant record/session to mutate (e.g., updating orders, customer data, `shop/redact`, or billing state for "that shop") can be made to apply attacker-controlled webhook bodies against a different merchant's data — a cross-tenant access impact.

### Likelihood Explanation
Likelihood is high for any app that has more than one installing shop (which is the typical use case for a public/multi-tenant Shopify app): the attacker only needs their own install of the app to obtain a genuinely-signed webhook for a topic they control, then replay it with a modified `shop-domain` header value against the app's public webhook endpoint. No access token, `client_secret`, or privileged account is required — only ordinary use of the app as one of its many customers.

### Recommendation
Do not treat any HTTP header value (`shop-domain`, `topic`, `webhook-id`, `api-version`) as authenticated identity. Instead, bind the shop/topic identity into the signed material, e.g., by having `Request#to_signable_string` incorporate the header values (as Shopify's actual webhook contract intends the signature to cover the full delivery, not just the body), or by requiring the consuming app to cross-check `request.shop` against the shop tied to the session/subscription that registered the webhook before dispatching to the handler. At minimum, document and enforce that `WebhookMetadata#shop` must be re-validated against a known, previously-registered shop for that specific webhook subscription id before being trusted as a tenant key.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker.myshopify.com` (a normal, unprivileged action).
2. Shopify sends the attacker's app endpoint a legitimately HMAC-signed webhook, e.g. body `{"id":123,...}` with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`.
3. Attacker captures this exact `raw_body` + `hmac` pair (both valid, since the HMAC is only over the body) and re-POSTs it to the same app endpoint, replacing only the header:
   `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` — this passes because the signed bytes (`raw_body`) are unchanged. [6](#0-5) 
5. `WebhookMetadata.new(shop: request.shop, ...)` is built with `shop == "victim-shop.myshopify.com"` and dispatched to the app's handler, which now processes attacker-controlled data believing it is authoritative data from the victim shop. [7](#0-6)

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
