Based on my investigation, I found a concrete analog: `TokenExchange.exchange_token` derives the destination shop from a validated JWT (`jwt_payload.shop`, backed by HMAC-signed `dest` claim), but unlike every sibling OAuth-credential method in the same module/family, it never runs that shop string through `Utils::ShopValidator.sanitize!`.

### Title
Unsanitized JWT `dest` claim used directly as OAuth host bypasses `ShopValidator` trust boundary - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` extracts the shop from the session token's `dest` claim via `JwtPayload#shop` and uses it verbatim to build the request host for the `client_secret`-bearing token-exchange call, with no domain allow-list check. Every other credential-exchange method in the library (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`, `Clients::Graphql::Storefront#initialize`) enforces `Utils::ShopValidator.sanitize!` on the shop string before building a `Session`/request host, but `exchange_token` does not.

### Finding Description
`JwtPayload#shop` simply strips the `https://` prefix from the raw `dest` claim: `@dest.gsub("https://", "")` [1](#0-0) . The only cryptographic check performed is that the JWT signature verifies against `Context.api_secret_key` and that `aud == Context.api_key` [2](#0-1) . Nothing constrains `dest` to `*.myshopify.com`/`*.myshopify.io`/`spin.dev`/etc.

`TokenExchange.exchange_token` then does:
```
jwt_payload = ShopifyAPI::Auth::JwtPayload.new(session_token)
dest_shop = jwt_payload.shop
...
shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)
...
client = Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")
``` [3](#0-2) 

`Clients::HttpClient` builds the request URL from `session.shop`, so `dest_shop` becomes the literal host that receives the POST body containing `client_id` and `client_secret`: `client_id: ShopifyAPI::Context.api_key, client_secret: ShopifyAPI::Context.api_secret_key, ...` [4](#0-3) .

Compare this to the parallel `migrate_to_expiring_token` in the very same module, which validates the shop before doing the same thing: `validated_shop = Utils::ShopValidator.sanitize!(shop)` [5](#0-4) , and `ClientCredentials.client_credentials` / `RefreshToken.refresh_access_token`, which do the same [6](#0-5) [7](#0-6) . `ShopValidator` exists exactly to enforce `host validated == host that receives client_secret`, restricting to `TRUSTED_SHOPIFY_DOMAINS` [8](#0-7) .

The binding that should hold is: **host that received the app's `client_secret` == a trusted Shopify admin domain from `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`**. In `exchange_token`, this equality is never checked — the host is instead bound only to "whatever string is in the JWT's `dest` field, after signature verification and `aud` check." The JWT's cryptographic authenticity does not by itself guarantee `dest` is restricted to a Shopify domain, because `JwtPayload` performs no domain-format validation on `dest` at all — this is exactly the same class of "field trusted without additional binding check" as the Sherlock report's PT-restricted-redeem case, where a state condition (`mscale > 0`) was treated as sufficient without checking the additional restriction flag (`redeemRestricted`).

### Impact Explanation
If `dest` in the signed session token could ever contain a non-`myshopify` value — e.g., through a compromised/relayed App Bridge session token, a bug in Shopify's own token issuance, or (most realistically) a future regression/edge case that this library has *no* independent guard against — `exchange_token` would POST the app's `client_id` and `client_secret` in plaintext JSON to an attacker-influenced host. That is direct exfiltration of the app's `client_secret`, which the rules classify as Critical impact. The presence of `ShopValidator` and its use in every sibling method shows the maintainers themselves consider this exact host-vs-credential binding a required security control that this one call path (`exchange_token`) skips.

### Likelihood Explanation
Likelihood is Low but not zero: the JWT signature check does provide a strong barrier (an attacker would need the app's `api_secret_key` to forge `dest`, which is out of scope per the rules). However, this is precisely a defense-in-depth control gap rather than a "theoretical" note: it is the single asymmetric case among five structurally identical shop-to-host bindings in this codebase, and the fix for the others (added in the same PR, per `CHANGELOG.md` #1443) was deliberately not applied to `exchange_token`. Any code path where `dest` is not perfectly constrained upstream (malformed/legacy tokens, non-admin session tokens whose `dest` format differs, spoofed values slipping past leeway/verification edge cases) turns into full `client_secret` disclosure to an arbitrary host, with no independent check inside this gem to catch it.

### Recommendation
Apply the same trust boundary used elsewhere: validate `dest_shop` with `Utils::ShopValidator.sanitize!` (or `sanitize_shop_domain` plus explicit rejection) before constructing `shop_session` in `TokenExchange.exchange_token`, mirroring `migrate_to_expiring_token`, `ClientCredentials.client_credentials`, and `RefreshToken.refresh_access_token`.

### Proof of Concept
1. Assume a session token is received with a `dest` claim whose value has been altered post-verification-boundary (e.g. via a bug in an upstream relaying proxy, or a legacy/non-standard token issuer that still validates against the app's `api_secret_key`/`api_key` pair but does not constrain `dest` to a Shopify domain).
2. App calls:
   ```ruby
   ShopifyAPI::Auth::TokenExchange.exchange_token(
     session_token: attacker_influenced_token,
     requested_token_type: ShopifyAPI::Auth::TokenExchange::RequestedTokenType::OFFLINE_ACCESS_TOKEN,
   )
   ```
3. `JwtPayload#shop` returns the raw `dest` value verbatim (`lib/shopify_api/auth/jwt_payload.rb:48-50`), with no domain allow-list check.
4. `exchange_token` builds `Session.new(shop: dest_shop)` and immediately issues `client.request(... path: "access_token", body: { client_id:, client_secret:, ... })` to `https://#{dest_shop}/admin/oauth/access_token` (`lib/shopify_api/auth/token_exchange.rb:51-65`).
5. Contrast with `migrate_to_expiring_token`, which would have rejected an untrusted `dest_shop` via `Utils::ShopValidator.sanitize!` raising `Errors::InvalidShopError` (`lib/shopify_api/auth/token_exchange.rb:103`, `lib/shopify_api/utils/shop_validator.rb:56-64`).
