### Title
Unallowlisted route venues let caller-supplied pool code run under the caller's auth tree and drain the caller's wallet - (File: contracts/swap-aggregator/src/venues/mod.rs)

### Summary
`execute_strategy` routes every hop through a `pool` address taken verbatim from the caller-supplied `StrategySwap` payload, with no venue/pool allowlist. Any contract can therefore be placed on the call stack below the caller's `require_auth` entry, where it can issue `token.transfer(caller, attacker, amount)` calls that the host records as children of the caller's authorization. A client that signs the simulation-produced auth tree authorizes the theft — the exact on-chain analogue of passing a user-controlled URL to `addMediaFromUrl()` and having the server issue the request.

### Finding Description
The SSRF class is "server performs outbound interaction against an attacker-chosen target using its own authority." In XOXNO Lending the shape is:

1. An unprivileged user calls a controller strategy entrypoint that takes a `StrategySwap` — `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, or `flash_position` — which forwards the payload to the configured router in `swap_tokens` (`contracts/controller/src/strategies/swap.rs:34-38`). The controller grants exactly one input `transfer` auth and does not inspect the route.
2. The router's instruction loop calls `dispatch_hop`, which builds a `HopContext` from the raw `SwapHop` and invokes whichever venue adapter the payload names (`contracts/swap-aggregator/src/venues/mod.rs:34-40`). Every adapter then calls the payload's `hop.pool` address — e.g. Comet does `env.invoke_contract(&ctx.hop.pool, "swap_exact_amount_in", ...)` (`contracts/swap-aggregator/src/venues/comet.rs:30-34`). There is no registry or allowlist of pools anywhere in the dispatch path.
3. Inside that hop, the attacker-chosen contract executes arbitrary code *below* the sender's auth entry. If it calls `token.transfer(sender, attacker, amount)` on any token the sender holds, the host records the call as a child of the sender's `require_auth` invocation. The protocol's own harness proves both halves: recording mode attaches the rogue `transfer` under the caller's `swap_collateral` entry and enforcing mode executes it once that tree is signed (`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:195-269`).

The threat model itself states the consequence: "a route can put third-party code on the call stack below the caller's authorization... the loss is then the caller's wallet, not the routed amount, and neither the payload minimum nor the final risk gate bounds it" (`docs/explanation/threat-model.md:154-165`). The controller's measured-delta checks (`RouterOverspend`, `NoSwapOutput`) bound only the routed input, not wallet transfers the rogue hop code makes directly.

### Impact Explanation
Theft of user funds beyond the swapped amount. A poisoned route drains arbitrary balances (including tokens the protocol never listed) from any user whose client signs the simulated auth tree — demonstrated by the harness where Alice's entire `WALLET_BALANCE` moves to the attacker while the swap itself pays a fair output and all controller checks pass (`rogue_hop_pool_transfer_joins_caller_auth_tree.rs:224-226`). Losses are unbounded by `amount_in`, `min_out`, or the final health-factor gate.

### Likelihood Explanation
Any unprivileged address can submit the route. The exploit succeeds against the common wallet/client flow of "simulate → sign returned auth entries," which is exactly what `simulateTransaction` produces. Simulation shows a successful swap with correct output, so there is no visible signal short of decoding the auth tree's children — which current Stellar tooling does not surface by default. Severity Medium: real theft but conditioned on the victim signing the recorded tree rather than a self-serve drain.

### Recommendation
Validate hop `pool` addresses against a per-venue allowlist or pool-factory check inside `dispatch_hop` (or at minimum reject `hop.pool` addresses that are not verifiable DEX pool contracts), so caller-controlled XDR cannot place arbitrary code under the sender's auth. Independently, the controller could expose the resolved venue set and document that signers must reject any auth tree containing children other than the single input `transfer`.

### Proof of Concept
The repository already contains a full reproduction: `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`.

- `UnlistedPoolRouter` mirrors `execute_strategy` and invokes `route.hop_pool` (lines 39-47), matching the real router's unallowlisted dispatch in `venues/mod.rs`.
- `RogueHopPool::swap` calls `token.transfer(victim, attacker, WALLET_BALANCE)` on an unrelated wallet token (lines 62-71).
- `simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry` (line 195) shows `simulateTransaction`-style recording produces an auth entry with the theft nested under the caller's `swap_collateral` invocation, and Alice's balance goes to 0.
- `enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer` (line 230) confirms an honest empty-child tree fails closed, but the simulation-produced poisoned tree executes the transfer.

Conceptual flow against production entrypoints:

```text
attacker deploys RoguePool { victim=alice, token=X, to=attacker, amount=alice.balance(X) }
attacker builds StrategySwap { hops: [{ venue: CometDex, pool: RoguePool, token_in: USDC, token_out: ETH }] }
   (or serves it via a malicious quote/route to Alice)
alice calls controller.swap_collateral(alice, account, USDC, amt, ETH, swap)
  └─ controller authorizes USDC.transfer(controller, router, amt)
  └─ router.execute_strategy → dispatch_hop → invoke_contract(RoguePool, ...)
       └─ RoguePool calls X.transfer(alice, attacker, balance)   ← recorded under alice's auth
client signs simulated tree → enforcing host executes the wallet drain
```
