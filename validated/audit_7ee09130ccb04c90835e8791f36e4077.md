### Title
Delegate action ML-DSA signature verification compute is charged on the wrong shard when `fix_ml_dsa_cost_charging` is disabled, letting an attacker exceed the receiver shard's compute budget - (File: runtime/runtime/src/actions.rs)

### Summary
`apply_delegate_action` only records `delegate_signature_verification_compute` into `result.compute_usage` (the receiver shard's compute-limit tracking) when `apply_state.config.wasm_config.fix_ml_dsa_cost_charging` is `true`. When this flag is not yet active for the current protocol version, the actual, expensive `signed_delegate_action.verify()` call at line 458 still executes on the receiver shard, but the compute cost for it is not counted against that shard's `compute_limit` — the cost was instead pre-charged during transaction-to-receipt conversion on the signer shard, which never performs the verification itself.

### Finding Description
`apply_delegate_action` is reached whenever a chunk processes a `DelegateAction` receipt (a meta-transaction), which any unprivileged account can submit via a relayer or directly. [1](#0-0) 

The gating comment in the code itself documents the exact mechanism: gas for the ML-DSA verification is burnt at transaction conversion time on the signer shard, but the actual `verify()` (the expensive post-quantum signature check) runs later on the receiver shard inside `apply_delegate_action`. If `fix_ml_dsa_cost_charging` is `false`, the `safe_add_compute` call that would add `verify_compute` to `result.compute_usage` is skipped, so the receiver shard's compute-limit accounting does not reflect the CPU work it is about to perform for `signed_delegate_action.verify()`. The verification still runs unconditionally at line 458 regardless of the flag, so the CPU cost is real and unavoidable, but it is not deducted from the shard that actually incurs it.

An unprivileged attacker can craft repeated `SignedDelegateAction`s using ML-DSA-65 public keys (which have measurably higher verification cost than Ed25519, per `delegate_signature_verification_compute` and `signature_verification_costs`) and submit them as receipts targeting a shard. As long as that shard's active protocol version has `fix_ml_dsa_cost_charging` disabled, each such receipt's real verification cost escapes the receiver shard's `compute_limit` bookkeeping, even though gas/compute was already deducted on the (different) signer shard.

### Impact Explanation
This is a compute-metering-completeness / shard compute-limit bypass: the receiver shard chunk producer can be made to perform more actual CPU-bound signature-verification work per chunk than its `compute_limit` accounting reflects, because the cost is booked against the signer shard instead. This falls into the "gas or storage metering bypass" and "unbounded resource use" (chunk-application liveness risk) bounty classes, since it decouples enforced compute budgets from actual CPU consumption on the shard performing the work.

Note: this is not literally "zero-cost" work — gas/compute is still charged once, on the signer shard, at transaction-conversion time — but it is mischarged to a shard that does no verification, letting the actual verification cost on the receiver shard go unaccounted against that shard's own budget.

### Likelihood Explanation
Exploitability strictly requires the precondition that the currently active protocol version for the relevant shard has `fix_ml_dsa_cost_charging` disabled (i.e., prior to activation of this protocol feature/config value). If that flag is enabled network-wide (its intended, fixed state), the code path already meters the cost correctly and this issue does not apply. The repo's own test `test_delegate_action_meters_inner_verify_compute` (`runtime/runtime/src/actions.rs`) and `test-loop-tests/src/tests/ml_dsa_verification_cost.rs` show the fix and unfixed behavior are both parameterized/testable, confirming the flag genuinely toggles this metering gap. Whether this is currently live on mainnet depends on the protocol version rollout state, which could not be conclusively confirmed from the available index.

### Recommendation
Ensure `fix_ml_dsa_cost_charging` is unconditionally enabled (remove the flag once stabilized network-wide), or, until then, ensure the un-gated code path also enforces the receiver shard's `compute_limit` check against the actual verification cost (not merely relying on signer-shard pre-charging) so that no protocol-version window exists where a shard's real CPU work for delegate-action signature verification is unaccounted for locally.

### Proof of Concept
Extend `test_delegate_action_meters_inner_verify_compute` in `runtime/runtime/src/actions.rs`:
1. Run with `fix_ml_dsa_cost_charging = false`.
2. Construct N `SignedDelegateAction`s with ML-DSA-65 public keys, each requiring `signed_delegate_action.verify()`.
3. Call `apply_delegate_action` for each within a simulated chunk/apply loop.
4. Assert `result.compute_usage` remains `0` (or unchanged) after all N calls, while instrumenting/mocking `verify()` to confirm it was invoked N times.
5. Assert that this allows total actual verification work to exceed what `compute_limit` would normally permit if properly charged, demonstrating the receiver shard's compute-limit accounting gap.

pub(crate) fn apply_delegate_action(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    action_receipt: &VersionedActionReceipt,
    sender_id: &AccountId,
    signed_delegate_action: VersionedSignedDelegateActionRef<'_>,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    // The inner delegate signature is verified below, here on the receiver shard.
    // Meter its verification compute against this shard's `compute_limit`; the gas
    // for it was already burnt at tx conversion on the signer shard. Without the
    // fix the compute is instead mis-charged on the signer shard (which never runs
    // this verify), letting the work escape the receiver shard's budget. See
    // `signature_verification_cost`.
    if apply_state.config.wasm_config.fix_ml_dsa_cost_charging {
        let verify_compute = delegate_signature_verification_compute(
            &apply_state.config.fees,
            signed_delegate_action.delegate_action().public_key(),
        );
        result.compute_usage = safe_add_compute(result.compute_usage, verify_compute)?;
    }
    if !signed_delegate_action.verify() {
        result.result = Err(ActionErrorKind::DelegateActionInvalidSignature.into());
        return Ok(());
    }
