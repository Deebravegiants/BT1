### Title
Webhook shop identity spoofing — HMAC does not cover the `shop` field, allowing cross-tenant webhook impersonation - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop` (tenant identity) is read from an unsigned header. `ShopifyAPI::Webhooks::Registry.process` validates only the body's HMAC and then hands the unauthenticated `shop` value straight to the host app's webhook handler, breaking the binding between "bytes verified by HMAC" and "identity acted upon."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `Request#shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never part of the signed content: [1](#0-0) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` (which signs/compares only `to_signable_string`, i.e. the raw body), and then constructs `WebhookMetadata` directly from `request.shop`, `request.topic`, etc., passing it to the app's registered handler: [2](#0-1) 

`HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string`, using the app's single shared `Context.api_secret_key`: [3](#0-2) 

Because the same `api_secret_key` is used to validate webhooks from every shop that installs the app, and the HMAC is bound only to the request body (never to the shop domain), the equality the gem should be enforcing — `shop asserted-to-handler == shop cryptographically bound to signature` — never holds. Any party who can obtain one valid `(raw_body, hmac)` pair for the app (e.g. by triggering/inspecting a legitimate webhook delivered to their own shop, which they fully control) can replay that exact body+HMAC combination while substituting an arbitrary `shop-domain` header value. `Registry.process` will still consider the HMAC valid (it only checks the body) and will forward the attacker-chosen `shop` into `WebhookMetadata` passed to the host app's handler.

Documentation confirms host apps are expected to trust `data.shop` for per-tenant routing/storage: [4](#0-3) [5](#0-4) 

### Impact Explanation
This crosses the tenant boundary the gem is supposed to enforce: the `shop` value handed to the app's webhook handler is not cryptographically bound to the verified payload, so a malicious merchant with the app installed on their own shop can forge webhook deliveries that appear to originate from a victim shop. Any host app that uses `data.shop` (as documented) to write/update per-tenant records, queue tenant-scoped jobs, or gate business logic can be tricked into cross-tenant data corruption or disclosure — this maps to the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitability requires only that the attacker possess one app-installed shop of their own (a normal, unprivileged merchant) — they do not need the `api_secret_key`, an access token, or any privileged account. They can obtain a valid `(raw_body, hmac)` pair simply by triggering an ordinary webhook event on their own shop (e.g. creating an order) and capturing the delivered request, then replaying the identical body/HMAC with a forged `shop-domain` header to the app's public webhook endpoint. No timing race or interception is required, making this straightforward for any unprivileged internet user who is also an app-installing merchant.

### Recommendation
Bind the `shop` domain (and other routing-relevant headers, e.g. `topic`) into the HMAC-verified content, or independently verify the claimed shop domain against a known, previously-established mapping (e.g. the shop associated with the webhook's `webhook_id`/subscription) before trusting `request.shop`. At minimum, document prominently that `WebhookMetadata#shop` is not cryptographically authenticated and must not be trusted for tenant-scoping decisions without additional verification.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and registers/receives a legitimate webhook (e.g. `orders/create`), capturing the raw body and its valid `x-shopify-hmac-sha256` header — computed with the app's shared `api_secret_key` over the body only, per `Utils::HmacValidator.compute_signature`. [6](#0-5) 

2. Attacker replays the exact same raw body and HMAC to the app's public webhook endpoint but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` validates `Utils::HmacValidator.validate(request)` — which passes because it only checks the (unmodified) raw body against the shared secret — and then calls the handler with `WebhookMetadata.new(..., shop: "victim.myshopify.com", ...)`. [7](#0-6) 

4. The host app processes the payload as if it were a legitimate event from `victim.myshopify.com`, despite the payload actually originating from the attacker's own shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
