### Title
Protocol-contract recipient blocklist is incomplete — borrow/withdraw/flash legs reject only the leg's own pool and the controller, so proceeds sent to a *different* market's pool are stranded permanently - ([File: contracts/controller/src/positions/mod.rs])

### Summary
`require_external_recipient` was added (see test `GH-17`, `tests/test-harness/tests/controller/recipient_is_protocol_contract.rs`) to stop funds being sent to protocol addresses where accounting cannot recover them. It rejects exactly two addresses: `env.current_contract_address()` and `cache.cached_pool_address()` — the pool servicing the current leg. But the deployment runs one pool contract per asset (the test resolves distinct pools via `get_pool_address("ETH")` / `get_pool_address("USDC")`). A `borrow`, `withdraw`, or flash receiver addressed to *another* market's pool passes the check, the tokens are debited/burned on the books, and they land in a pool contract that has no market for that token and no sweep/claim entrypoint — the analog of a localhost check covering `127.0.0.1` but not the rest of the loopback range. ### Finding Description
`require_external_recipient` at `contracts/controller/src/positions/mod.rs:36-43` asserts only `recipient != current_contract && recipient != cached_pool_address`. It is shared by the debt, supply-withdrawal, and flash receiver paths (`positions/debt.rs`, `positions/supply.rs`, `strategies/flash_position.rs`, `strategies/flash_loan.rs` all call it). The pool is per-asset: `pool_borrow_call`/`pool_withdraw_call` transfer the leg's token from the leg's pool to an arbitrary `receiver` (`contracts/controller/src/external/pool.rs:30-62`). Because markets are keyed `(hub, token)` and each token has its own pool contract, "the set of addresses that silently strand tokens" is `{controller} ∪ {every listed pool}` — the check enumerates only two elements of that set.

### Impact Explanation
Permanent freezing of funds. If `receiver` names pool B while borrowing/withdrawing token A, pool A's `token.transfer(pool_A, pool_B, amount)` succeeds (a plain token transfer needs no pool-B authorization), the position is debited (debt minted or supply burned), and the tokens sit in pool B's balance uncredited to any market book — matching the documented behavior that "direct donations do not rewrite those books" and there is no pool entrypoint to recover a foreign token. The borrower still owes the debt; the withdrawn collateral is burned. This is the same stranding GH-17 was meant to prevent, reachable through the same entrypoints with a different, equally valid-looking address.

### Likelihood Explanation
Requires the caller to supply a harmful `receiver`, so it is self-inflicted rather than attacker-forced — but that is also true of the already-fixed GH-17 cases; the defense exists precisely because wrong-recipient calls are a realistic wallet/integration mistake (e.g., a UI passing the wrong market's pool address). Any unprivileged address can submit it via `borrow(account, id, legs, Some(other_pool))` or `withdraw(..., Some(other_pool))`, and via `flash_position`/flash-loan receiver parameters. Severity is bounded to the caller's own leg amounts; no third-party funds are taken.

### Recommendation
Maintain a registry-level check: on `borrow`/`withdraw`/flash receiver validation, iterate (or store a set of) all pool addresses known to the controller — e.g., a `DataKey::PoolAddr(address) -> ()` marker written when each market is created — and reject `recipient` if it matches any of them, not just the leg's cached pool. Alternatively, restrict `receiver` to the account's own address or an explicitly non-contract check where feasible.

### Proof of Concept
Setup as in `tests/test-harness/tests/controller/recipient_is_protocol_contract.rs` (`standard_two_asset_dust_disabled`, Alice supplied USDC):

```rust
let id = t.account_id(ALICE);
let alice = t.get_or_create_user(ALICE);
// Pool for the *other* asset — not the borrowed market's pool, not the controller.
let wrong_pool = t.get_pool_address("USDC");
let leg = vec![&t.env, (hub_asset(t.resolve_asset("ETH")), U)];

// Currently succeeds: wrong_pool != controller && wrong_pool != ETH pool.
t.ctrl_client()
    .borrow(&alice, &id, &leg, &Some(wrong_pool))
    .unwrap();
```

Result: ETH debt is minted for Alice and `U` ETH is transferred into the USDC pool contract, where it is an unbooked, unrecoverable donation — while `borrow(..., Some(get_pool_address("ETH")))` correctly reverts with `InvalidFlashloanReceiver`. The same holds for `withdraw` and for a flash receiver addressed to a foreign pool.

Uncertainty noted: `cached_pool_address()` is confirmed to be a single per-leg pool address (Context, `contracts/controller/src/context.rs`), and the test resolves distinct pools per asset; I did not enumerate every `require_external_recipient` call site, but the shared helper makes the gap uniform across all flows that use it.

/// Rejects pool and controller recipients with `InvalidFlashloanReceiver`.
/// Pool self-transfers debit cash without moving tokens; controller receipts
/// would remain unclaimed by balance-delta accounting.
pub(crate) fn require_external_recipient(env: &Env, cache: &mut Context, recipient: &Address) {
    let pool = cache.cached_pool_address();
    assert_with_error!(
        env,
        *recipient != env.current_contract_address() && *recipient != pool,
        FlashLoanError::InvalidFlashloanReceiver
    );
}

fn borrow_to_the_pool_is_rejected_before_cash_moves() {
    let mut t = setup();
    let id = t.account_id(ALICE);
    let pool = t.get_pool_address("ETH");
    let cash_before = t.pool_reserves("ETH");
    let alice = t.get_or_create_user(ALICE);
    let leg = vec![&t.env, (hub_asset(t.resolve_asset("ETH")), U)];
    let result = t.ctrl_client().try_borrow(&alice, &id, &leg, &Some(pool));
    assert_contract_error(map_try_ok_unit(result), errors::INVALID_FLASHLOAN_RECEIVER);
    assert_eq!(t.pool_reserves("ETH"), cash_before);
}
