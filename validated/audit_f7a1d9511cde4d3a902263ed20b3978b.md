### Title
Webhook shop/topic/id metadata not covered by HMAC verification enables cross-tenant webhook spoofing via replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook by calling `Utils::HmacValidator.validate(request)`, but the HMAC signature only ever covers the raw request body (`Request#to_signable_string` returns `@raw_body`). The `shop`, `topic`, `webhook_id`, and `api_version` fields — which are read straight from unauthenticated HTTP headers and forwarded to the app's handler as the tenant/routing identity — are never included in the signed bytes.

### Finding Description
`ShopifyAPI::Webhooks::Request` derives all of its identity fields from HTTP headers: [1](#0-0) 

Only `@raw_body` is fed into the signable string used for HMAC verification; `shop`, `topic`, `webhook_id`, and `api_version` are excluded. `Registry.process` validates the HMAC and then unconditionally trusts these header-derived fields to build the metadata handed to the app's handler: [2](#0-1) 

`HmacValidator.validate` computes and compares the signature purely against `verifiable_query.to_signable_string`, i.e. the body: [3](#0-2) 

The identity binding that should hold is: `shop header == shop cryptographically bound by HMAC`. In this implementation that equality never holds — the HMAC only binds the body, so `shop` (and `topic`/`webhook_id`) can be swapped freely on any request that carries a valid `(body, hmac)` pair, without needing the `api_secret_key`.

The gem's own documentation asserts a stronger guarantee than what's actually implemented: "This will verify the request did indeed come from Shopify" for the whole request, when in fact only the body bytes are verified: [4](#0-3) 

### Impact Explanation
An unprivileged party who can install the app on any shop (including their own dev/trial store — a normal, unprivileged action) will legitimately receive real webhook deliveries with a valid `(raw_body, x-shopify-hmac-sha256)` pair signed with the victim app's `api_secret_key`. By replaying that exact body/HMAC pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) headers with an arbitrary victim shop domain, the forged request still passes `HmacValidator.validate` (body-only check) and is dispatched to the handler tagged with `shop: <attacker-chosen shop>`. Any app that uses `WebhookMetadata#shop` to select which tenant's records to update (a documented, expected usage per `docs/usage/webhooks.md`) will apply the replayed body's data under the wrong tenant, causing cross-tenant data corruption/injection without ever needing the app's secret. This is a cross-tenant access impact.

### Likelihood Explanation
Likelihood is Low/Moderate: it requires the attacker to have first obtained one legitimate webhook delivery (trivial — install the app on any store they control) and to be able to reach the app's public webhook endpoint, both of which are realistic for an unprivileged external actor targeting a multi-tenant Shopify app built on this gem.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signable material for webhook requests, or otherwise cryptographically bind them to the verified body (e.g., derive the shop/topic from a signed envelope rather than raw headers). At minimum, document clearly that only the body is verified and that consumers must independently authenticate the shop domain against their own registered-shop records before trusting `WebhookMetadata#shop`.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; capture a legitimate webhook delivery: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the app's real `api_secret_key`), plus `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Replay a POST to the app's webhook endpoint with the same body `B` and same `X-Shopify-Hmac-Sha256: H`, but set `X-Shopify-Shop-Domain: victim.myshopify.com` (a shop the attacker does not control).
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `B` against `H` — this still succeeds because `B`/`H` are unchanged.
4. `handler.handle` is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-supplied body content as if it originated from `victim.myshopify.com`.
