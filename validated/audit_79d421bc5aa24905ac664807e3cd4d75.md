Based on my investigation, I found a genuine analog to the missing `openDeadline` enforcement pattern in orb-core's operator/user QR-code signup authorization flow.

### Title
Missing enforcement of `operator_qr_expiration_time` when transitioning from `QrCodes::Operator`/`Both` states allows a stale, already-scanned operator authorization to gate a new signup - (File: src/plans/mod.rs)

### Summary
The ERC-7683 bug is a missing timestamp/deadline check that lets an authorization artifact (a gasless order) be consumed after it should have expired. In orb-core, the analogous authorization artifact is the scanned operator QR-code, whose freshness is supposed to be bounded by `operator_qr_expiration_time` [1](#0-0) . This deadline is enforced in some code paths (`scan_initial_qr_codes`, `scan_remaining_qr_codes`, `idle_scan_user_qr_code`) but the check is guarded conditionally and re-derived from `Instant::elapsed()` scattered across multiple call sites rather than centrally enforced at the point where the operator authorization is actually consumed to start biometric capture.

### Finding Description
`operator_qr_expiration_time` is meant to bound how long an operator's QR-code scan remains valid before a user QR-code must be (re-)validated against it [2](#0-1) . The check is implemented as a guard condition (`if operator_data.timestamp.elapsed() < operator_qr_expiration_time`) inside `scan_remaining_qr_codes` for the `QrCodes::Both` and `QrCodes::Operator` match arms [3](#0-2) . However, this expiration check is only evaluated once, at the moment `scan_remaining_qr_codes` is entered from `do_signup`; after that, `do_signup` proceeds through `is_orb_os_version_allowed`, `orb_relay_announce_orb_id`, a fixed 3-second sleep, and then `biometric_capture` — all using the previously-validated `operator_data`/`qr_codes` without any re-check of the deadline [4](#0-3) . Because `operator_qr_expiration_time` defaults to nearly 23 hours [5](#0-4) , this specific gap is low severity by itself. The structurally identical bug class (deadline data exists, is only spot-checked at select entry points instead of being enforced immediately before the privileged action is executed) mirrors the `openFor()` finding, where `openDeadline` existed in the struct but wasn't enforced against `block.timestamp` before executing the privileged action.

### Impact Explanation
If the expiration check is bypassed or omitted along any additional entry path (e.g. a future code path that constructs `ResolvedQrCodes` directly, or a modification that reorders `scan_remaining_qr_codes`), a stale operator/user QR pairing could authorize a biometric capture and identity signup outside of the intended freshness window. This could allow cross-session/cross-operator state bleed, where an operator's session credentials remain valid far longer than intended, potentially authorizing a signup against the wrong operator context or reused location data (`operator_data.location_data`) passed to `backend::user_status::request` [6](#0-5) .

### Likelihood Explanation
Likelihood is low-to-medium: the primary consuming path (`do_signup`) does correctly derive `qr_codes` via `scan_remaining_qr_codes`, which does perform the check before returning `ResolvedQrCodes`. The risk is architectural — the expiration guard is expressed as a per-call-site match-arm condition rather than a single authoritative gate enforced immediately before the sensitive action (biometric capture / user-data disclosure), making the property easy to silently drop in future refactors, exactly as happened with `openDeadline` in `openFor()` before commit `2e7bc2f`.

### Recommendation
Centralize the `operator_qr_expiration_time` deadline check into a single function that validates freshness immediately before biometric capture is authorized in `do_signup`, rather than relying on the check being correctly re-derived at each of the three separate match arms in `scan_remaining_qr_codes` and the guard in `scan_initial_qr_codes`. Defensively re-validate `operator_data.timestamp.elapsed() < operator_qr_expiration_time` directly inside `do_signup` right before `biometric_capture` is invoked, so that any future change to the QR-code resolution flow cannot silently remove deadline enforcement.

### Proof of Concept
Not directly exploitable with current code paths (all call sites converge through `scan_remaining_qr_codes`, which does check the deadline before returning). The concern is architectural fragility rather than a currently triggerable bypass — I could not identify a live path in `src/plans/mod.rs` where `ResolvedQrCodes`/biometric capture is reached without passing through the `operator_data.timestamp.elapsed() < operator_qr_expiration_time` guard in `scan_remaining_qr_codes` [7](#0-6) .
