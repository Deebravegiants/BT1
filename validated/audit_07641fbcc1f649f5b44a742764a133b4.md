### Title
`Oauth.validate_auth_callback` sends `client_secret` to a `shop` host that is never checked against the trusted-domain allowlist - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::RefreshToken.refresh_access_token` and `ShopifyAPI::Auth::ClientCredentials.client_credentials` both call `Utils::ShopValidator.sanitize!(shop)` before building the session used to send the app's `client_secret` to `https://#{shop}/admin/oauth/access_token`. `ShopifyAPI::Auth::Oauth.validate_auth_callback` and `Oauth.begin_auth` never do this - they take `auth_query.shop` / `shop` as-is and hand it straight to `auth_base_uri(shop)` / `Session.new(shop:)`, which is subsequently used to POST the `client_id` + `client_secret` body during token exchange.

### Finding Description
`ShopValidator.sanitize!` exists specifically to bind an incoming `shop` string to Shopify's trusted domain list (`myshopify.com`, `myshopify.io`, `shopify.com`, `spin.dev`, `shop.dev`) before that value is used as the destination host for a request carrying the app's `client_secret`: [1](#0-0) [2](#0-1) 

`RefreshToken.refresh_access_token` and `ClientCredentials.client_credentials` both enforce this binding — `validated host == trusted Shopify host` — immediately before constructing the session/client used to send the secret: [3](#0-2) [4](#0-3) 

`Oauth.validate_auth_callback`, however, takes `auth_query.shop` directly — the value only travels through the HMAC check, never through `ShopValidator` — and uses it to build the `null_session` whose host receives the `client_id`/`client_secret` POST body: [5](#0-4) 

`auth_query.shop` is bound only by `HmacValidator`, which checks that `hmac == HMAC(secret, code|host|shop|state|timestamp)` — this proves the query wasn't tampered with by a party that lacks the secret, but it does **not** enforce that `shop` is an actual `*.myshopify.com`-family host: [6](#0-5) [7](#0-6) 

`Oauth.begin_auth` has the same gap on the way in: the `shop` parameter — documented as attacker/user-supplied ("A Shopify domain name…", populated straight from `request.headers["Shop"]` in the gem's own example) — is passed unsanitized into `auth_base_uri(shop)`: [8](#0-7) [9](#0-8) [10](#0-9) 

The identity binding that should hold is: `host that receives client_secret == host on ShopValidator's trusted-domain allowlist`. `RefreshToken`/`ClientCredentials` enforce this equality; `Oauth.begin_auth`/`Oauth.validate_auth_callback` do not, leaving the "host validated versus the host that receives the access token or `client_secret`" gap called out in the report's bug class.

### Impact Explanation
If an app follows the gem's own documented pattern — reading `shop` from an unauthenticated request header/param at the start of the flow (as shown in `docs/usage/oauth.md`) and building an `AuthQuery` from raw callback request parameters — an attacker who controls the initial `shop` value can redirect the OAuth "begin" step to an attacker-controlled host instead of `*.myshopify.com`. This is the exact class of bug `ShopValidator` was introduced to close (see `CHANGELOG.md` "Verify that the shop domain is a subdomain of .myshopify.com when creating the session"), yet the two `Oauth` entry points that a typical non-`ShopifyApp` integration relies on for the Authorization Code Grant flow don't call it. This satisfies the report's "High" bucket: SSRF/host confusion carrying the app's credentials (`client_id`/`client_secret`) toward a request that is expected to go only to Shopify.

### Likelihood Explanation
Medium. It requires the host application to pass an unsanitized `shop` value into `begin_auth`/`AuthQuery` — which is exactly the pattern the gem's own `docs/usage/oauth.md` example demonstrates (`shop = request.headers["Shop"]` then `begin_auth(shop: domain, ...)`), and is a documented, supported (non-`ShopifyApp`) usage path for this gem, not a misuse of the API.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop)` in `Oauth.begin_auth` before constructing `auth_base_uri(shop)`, and validate/normalize `auth_query.shop` through `ShopValidator` in `Oauth.validate_auth_callback` before it is used to build the `null_session`/`HttpClient` that transmits `client_id`/`client_secret`, mirroring the pattern already used in `RefreshToken.refresh_access_token` and `ClientCredentials.client_credentials`.

### Proof of Concept
1. Host app implements the documented flow from `docs/usage/oauth.md`:
```ruby
def login
  shop = request.headers["Shop"]  # attacker-controlled, e.g. "attacker.example"
  auth_response = ShopifyAPI::Auth::Oauth.begin_auth(shop: shop, redirect_path: "/auth/callback")
  redirect_to auth_response[:auth_route]
end
```
2. `Oauth.begin_auth("attacker.example", ...)` builds `auth_route = "https://attacker.example/admin/oauth/authorize?client_id=...&redirect_uri=...&state=..."` via `auth_base_uri` — no call to `ShopValidator` occurs anywhere in `lib/shopify_api/auth/oauth.rb`.
3. The victim's browser is redirected to the attacker's host with the app's `client_id`, `redirect_uri` and freshly minted `state` nonce, letting the attacker stage a fake authorization page and drive a forced/completed OAuth flow against the real app, something `RefreshToken`/`ClientCredentials` explicitly guard against for their own credential-bearing requests but `Oauth` does not.

          scope = if scope_override.nil?

            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)

          unless Context.setup?

          end

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",

          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

        end

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
            access_token_response: Oauth::AccessTokenResponse.from_hash(session_params))

        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
