### Title
Sender-authentication bypass for `RequestState` messages in orb-relay-client session loop - (File: `orb-relay-client/src/client.rs`)

### Summary
The `PollerAgent::main_loop` message-handling logic in the orb-relay client enforces a sender check (`src.id != self.config.dst_id`) for every incoming relayed payload except one: `self_serve::app::v1::RequestState`. This mirrors the reported bug class of "reply handlers that act on incoming messages without verifying the sender is the expected party for the current session," except here the state-leak occurs in the Orb-side relay client used during self-serve signups instead of a consensus `HandleReply`.

### Finding Description
In the relay client's main event loop, incoming `RelayConnectResponse::Payload` messages are matched and handled here: [1](#0-0) 

The logic is:
1. If the payload matches `self_serve::app::v1::RequestState`, the client immediately replies with `self.last_message.clone()` — **no check on `src.id` is performed at all**.
2. Only for every *other* payload type does the code verify `src.id == self.config.dst_id` before calling `self.handle_message(...)`.

This means the one authenticated-peer check (`src.id != self.config.dst_id`) that exists to ensure a message actually originated from the paired counterpart entity for this session/queue is explicitly skipped for `RequestState`. Any message classified as `RequestState` arriving on the stream — regardless of `src` — triggers re-transmission of `last_message`, which is exactly the "held ceremony/session state" analog to the reported `HandleReply` bug where the reply's origin and the active session key/party were never cross-checked (`reply.GetThresholdKey() == c.thresholdKey.Id` in the report). Here the analogous missing check would be `src.id == self.config.dst_id` (or equivalent session/entity binding) before honoring a `RequestState` request and echoing back session state.

`last_message` is the most recent `RelayConnectRequest` this Orb-side client sent to the app during a self-serve signup session — this can carry session-relevant payloads such as `common::v1::AnnounceOrbId` or `self_serve::orb::v1::SignupEnded`, as seen in `orb-relay-client/src/lib.rs` payload definitions and the flows exercised in `orb-relay-client/src/bin/manual-test.rs` (`orb_to_app_with_state_request`, `app_to_orb`, `orb_to_app`). This relay client is wired into the production self-serve signup flow via `orb_relay_announce_orb_id` referenced from `src/plans/mod.rs`. [2](#0-1) 

### Impact Explanation
Because the `RequestState` branch skips the peer-identity check that gates all other message types, any relayed message that the client library classifies as `RequestState` causes it to re-emit the last message state of the current signup session without confirming the requester is the legitimately paired app/session peer. Since the relay multiplexes app/orb entities by `src`/`dst` identity within a session queue and the check exists specifically to filter unexpected sources, bypassing it for this one message type re-introduces the same class of risk described in the report: state belonging to one session/ceremony can be handed out in response to a request that was never verified to come from that session's authenticated counterpart, resulting in cross-signup/session state disclosure (e.g. `AnnounceOrbId`/`SignupEnded` payloads tied to a specific signup).

### Likelihood Explanation
The vulnerable code path is on the standard message-processing hot path of every relay-connected session (`main_loop`), not a rare or debug-only branch, and it's exercised in the checked-in `manual-test.rs` scenario `orb_to_app_with_state_request`, confirming `RequestState` is a normal, always-available message type in the protocol. No additional privilege beyond being able to place a `RequestState`-typed message on the same relayed stream is needed to trigger the response; the code needed to also check `src.id` was already written for every other message type, indicating this was simply omitted for this branch rather than intentionally exempted for a documented reason.

### Recommendation
Add the same `src.id == self.config.dst_id` (or equivalent authenticated-peer/session binding) check to the `RequestState` branch before responding with `self.last_message`, mirroring the check used for all other payload types:
```rust
if self_serve::app::v1::RequestState::matches(&payload).is_some() {
    if src.id != self.config.dst_id {
        tracing::error!("Skipping RequestState from unexpected source: {:?}", src.id);
    } else {
        sender_tx.send(self.last_message.clone()).await.wrap_err("Failed to send outgoing message")?;
    }
} else if src.id != self.config.dst_id {
    ...
}
```

### Proof of Concept
1. Establish an Orb-side relay session for `orb_id`/`session_id` as in `orb_to_app_with_state_request` (`orb-relay-client/src/bin/manual-test.rs:268-364`).
2. Have the Orb send a normal state-bearing message (e.g. `AnnounceOrbId`) which becomes `last_message`.
3. From any entity capable of injecting a `RelayConnectResponse` payload matching `self_serve::app::v1::RequestState` into that stream — with an `src` value that does **not** equal `self.config.dst_id` — observe that `main_loop` at `client.rs:436-440` still sends back `last_message`, unlike any other message type which would be dropped at the `src.id != self.config.dst_id` check (`client.rs:441-445`).
