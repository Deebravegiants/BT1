### Title
Pool `repay` refunds an unfunded "overpayment" out of real custody — a repay with no inbound transfer drains pool reserves - (File: contracts/pool/src/ops/repay.rs)

### Summary
`ops::repay::apply` treats any declared amount above the position's outstanding debt as an "overpayment" and transfers it back to the payer with `transfer_out`. The refund is computed from the *declared* `action.amount`, never measured against an actual inbound transfer, and is never debited from `cash` or checked against `require_reserves`. The bug class of the external report — a resource released (freed) on stale/declared state rather than real state — maps directly: the pool releases custody for a repayment leg that may never have delivered funds.

### Finding Description
`ops::repay::accounting` resolves the declared `action.amount` into burned debt shares plus an `overpayment`, credits only `net_repay` to cash, commits state, and then `apply` calls `outcome.cache.transfer_out(payer, outcome.overpayment)` (contracts/pool/src/ops/repay.rs:25-34, 40-66). `overpayment` is derived purely from `resolve_repay(amount, position)` against the account's debt — when debt is zero or the declared amount exceeds it, the entire (or excess) amount is classified as refundable.

The refund assumes the controller already transferred `action.amount` into the pool before invoking the leg (per the module doc: "The controller transfers the repay amount into the pool before this call"). Nothing in the pool verifies that assumption: `transfer_out` pays real tokens from custody while `cash` only absorbs `net_repay`, and the refund path bypasses `require_reserves`. The pool's own test `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` (contracts/pool/tests/flows.rs:3578-3611) demonstrates it: calling `repay` on a market with zero debt and `amount = custody_before` credits nothing yet drains the entire pool balance to `payer`, leaving book `cash` unchanged while custody is emptied. The same gap is acknowledged for `ops::recapitalize::apply` (excess over the shortfall).

The analogous execution path for an unprivileged caller is `controller.repay(caller, account_id, payments)` where the controller pushes `PoolAction`s to `pool.repay`. Any path where the controller declares an amount larger than what actually arrived at the pool — a fee-on-transfer or deflationary debt token, or any accounting gap between the controller's declared leg and the measured inbound — produces a refund paid out of *other suppliers'* custody. More directly, if the pool's `repay` entrypoint is not restricted to the controller, the test itself shows a one-call drain of all reserves.

### Impact Explanation
Theft of user funds: every token of "overpayment" refunded is paid from pool custody that backs suppliers' shares. On a market with no debt, a declared repay equal to the pool's balance refunds the full balance to the caller while `cash` and `supplied` are untouched — suppliers' shares remain on the book but the tokens are gone (protocol insolvency / contract unable to operate from lack of token funds). The harness test asserts exactly this custody drain.

### Likelihood Explanation
Requires only an entrypoint that reaches `ops::repay::apply` with a declared amount not backed by an equal inbound transfer. The controller relies on pre-transferring the repay amount, so exploitability through `controller.repay` hinges on any discrepancy between declared and delivered tokens (non-standard token behavior is excluded by scope, but the pool-side invariant gap stands on its own). If `pool.repay` is callable without controller auth — which the direct `t.client().repay(&payer, ...)` test suggests — no preconditions beyond a market with zero or small debt are needed. This is deterministic and repeatable per market.

### Recommendation
Make the refund measured, not declared: compute `overpayment` as `max(0, actual_inbound - applied_repay)` using balance-delta measurement of the pool's token balance across the repay leg (the same "measured receipt" discipline the router strategies already use), or require `net_repay + overpayment <= received_amount` before `transfer_out`. Additionally, debit `cash` for the refund or route it through `require_reserves`, and restrict `pool.repay`/`recapitalize` to the controller if not already enforced.

### Proof of Concept
From `contracts/pool/tests/flows.rs:3589-3611` — a market with `borrowed == 0` and `cash == custody_before`; calling `repay(payer, action{amount: custody_before})` returns `actual_amount == 0` while `assert_unfunded_refund_drained_custody` confirms the full `custody_before` was transferred to `payer` with the book unchanged. Repeat per market to drain each pool book.

I was unable to fully verify the authorization gate on the pool's public `repay`/`recapitalize` ABI within the iteration limit — if those functions hard-require controller auth, the exploit narrows to paths where the controller's declared leg exceeds measured inbound delivery, which is still a real solvency gap but harder to reach.
