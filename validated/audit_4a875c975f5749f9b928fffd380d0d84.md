### Title
Webhook `shop-domain`, `topic`, and `webhook-id` metadata are trusted despite not being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then dispatches attacker-influenceable header values (`shop`, `topic`, `webhook_id`, `api_version`) to the handler as trusted metadata. The identity binding broken is: `hmac_valid(raw_body) == true` is treated as equivalent to `shop-domain header == shop that produced raw_body`, when in fact the HMAC never covers the header fields at all.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, then forwards the unverified header-derived `shop`/`topic`/`webhook_id` straight to the app's handler: [3](#0-2) 

Because a single app-level `client_secret` is used to compute the HMAC for every shop's webhooks (there is no per-shop signing key), a valid `(raw_body, hmac)` pair obtained from one tenant's webhook delivery remains cryptographically valid regardless of which `shop-domain`/`topic` header accompanies it. An attacker who can install the app on their own store (an ordinary, unprivileged action) legitimately receives real webhook deliveries with a valid body+HMAC for their own shop. They can replay that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header to name a victim shop. `HmacValidator.validate` only checks `verifiable_query.to_signable_string` (the body) against the secret — it never checks that the claimed `shop` or `topic` is consistent with the signed content — so the request passes validation and the handler receives `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` with a shop value that has no cryptographic relationship to the body that was actually signed. [4](#0-3) 

This is a structural analog to the reentrancy report's root cause: an operation is authorized/verified over one shape of data, but a different, unverified value is what is actually acted upon downstream — here, verification is over `raw_body` only, while the tenant-identifying/dispatch-routing fields (`shop`, `topic`) that determine *what happens with* that body are unauthenticated headers.

### Impact Explanation
This crosses a tenant boundary: a host application relying on this gem's `Registry.process`/`WebhookMetadata` to key business logic to `shop` (e.g., "apply this order payload to shop X's records") can be made to process a body meant for shop A under the identity of victim shop B, since the gem provides no signal that `shop` is untrustworthy. This satisfies the "cross-tenant access" criterion (Critical) as the library's public verification API silently returns a "verified" result for header/body combinations whose shop binding was never actually checked.

### Likelihood Explanation
Requires only an unprivileged actor able to install the target app on any shop (to obtain one legitimately signed body+HMAC) and the ability to POST to the app's public webhook endpoint with custom headers — no leaked secrets, no privileged account, and no reliance on the host ignoring documented behavior, since `Registry.process`/`HmacValidator.validate` is the gem's own documented verification primitive and it does not mention that only the body is covered.

### Recommendation
Bind the header-derived identity fields into the value verified by the HMAC, or otherwise cryptographically tie `shop`/`topic`/`webhook_id` to the signed payload before trusting them in `WebhookMetadata`. At minimum, `HmacValidator`/`Registry.process` should not be relied upon as proof that `shop`/`topic` are authentic; the gem should document this gap explicitly or extend `to_signable_string` (or a companion check) to incorporate the header fields that `process` subsequently trusts.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`) for that shop, capturing the raw body `B` and the valid `X-Shopify-Hmac-Sha256` header `H` (both signed with the app's single `client_secret`).
2. Attacker POSTs to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid because it only signs `B`), but `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and/or a different `X-Shopify-Topic`.
3. `ShopifyAPI::Webhooks::Request.new` parses the headers, `Registry.process` calls `Utils::HmacValidator.validate(request)` which succeeds (it only checks `B` against `H`), and the handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: <attacker-chosen>, body: JSON.parse(B), ...)`, causing the host app to act on attacker data under the victim shop's identity.           raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
