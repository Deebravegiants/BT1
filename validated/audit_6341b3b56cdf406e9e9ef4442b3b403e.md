### Title
Webhook `shop` (tenant) identity is trusted from an unauthenticated header while only the raw body is HMAC-verified, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while `shop` (the tenant identifier) is read from the `x-shopify-shop-domain`/`shopify-shop-domain` header, which is never part of the signed payload. `Webhooks::Registry.process` validates the HMAC and then forwards `request.shop` straight to the app's handler as the authoritative tenant identity. This breaks the intended binding `hmac == HMAC(secret, body ‖ shop)`; in reality the gem only enforces `hmac == HMAC(secret, body)`, so `shop` can be swapped for any value without invalidating the signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read from a header that is not covered by that signable string: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` (body-only) and `request.hmac`, then immediately trusts `request.shop` to build the metadata passed to the app-defined handler: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` only ever hash `verifiable_query.to_signable_string`, so for `Webhooks::Request` that is exclusively the raw body: [4](#0-3) 

Contrast this with the OAuth callback path, where the equivalent identity field (`shop`) *is* included in the signable string and is therefore actually bound to the HMAC: [5](#0-4) 

The intended security invariant for a webhook is: `hmac == HMAC(secret, body)` **and** `shop == the tenant whose secret produced that HMAC`. Because `shop` is carried in an unsigned header, the gem instead only guarantees `hmac == HMAC(secret, body)`, decoupled from `shop`. Any unprivileged user who can install the target app on their own (attacker-owned) shop can capture a genuine `(body, hmac)` pair that Shopify sends for their own store's webhook, then replay that exact body/HMAC to the app's webhook endpoint while substituting the `shop` header for a victim shop's domain. `Utils::HmacValidator.validate` still returns `true` (the body and HMAC match), and `Registry.process` calls the app's handler with `WebhookMetadata` claiming the event originated from the victim shop.

### Impact Explanation
Any app built on top of `ShopifyAPI::Webhooks::Registry` that uses `WebhookMetadata#shop` to select which merchant's session/access token/tenant record to act on (a normal, documented usage pattern) can be tricked into performing actions or reading/writing data under the wrong tenant. This is a cross-tenant confusion vulnerability: an attacker who legitimately controls one shop can impersonate another shop's webhook traffic for topics with attacker-predictable or attacker-replayable bodies (e.g., `app/uninstalled`, or any topic whose body content the attacker can also produce/guess for their own store), causing the app to execute victim-tenant logic (e.g., revoking/clearing the victim session, marking the victim shop as uninstalled, or writing attacker-controlled body content into the victim's tenant-scoped data).

### Likelihood Explanation
Likelihood is limited by the fact that the attacker must obtain a valid `(raw_body, hmac)` pair, which requires either owning a shop that installs the app (readily achievable via Shopify's free development/partner stores) or otherwise capturing a legitimately signed webhook delivery. Given that constraint is trivially satisfiable by any unprivileged developer, and the header substitution requires no special access, the practical likelihood is moderate-to-high wherever the host app relies on `WebhookMetadata#shop` for tenant selection.

### Recommendation
Bind `shop` (and ideally `topic`) into the HMAC-signable value, or otherwise cryptographically authenticate the shop domain claimed in headers before trusting it (e.g., verify it against the shop associated with the currently registered webhook subscription/session, not solely the header). At minimum, document that `WebhookMetadata#shop` is unauthenticated header data and must not be used as a sole tenant-selection key without cross-checking against a known, previously authenticated shop record.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a webhook whose body is fixed/predictable (e.g. an empty-body or attacker-controlled-content topic), capturing the genuine `x-shopify-hmac-sha256` value Shopify computed for that body.
2. Attacker sends a forged HTTP request to the app's webhook endpoint with:
   - `x-shopify-hmac-sha256`: the captured, valid HMAC
   - body: identical to the captured raw body
   - `x-shopify-shop-domain`: `victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present).
4. `Utils::HmacValidator.validate(request)` returns `true` because it only hashes `@raw_body`, matching the (valid, attacker-owned) HMAC.
5. `Registry.process` invokes the app handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, and any downstream logic keyed off `data.shop` now operates against the victim tenant using attacker-supplied trigger.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
