Audit Report

## Title
Global, unscoped `requestID` keyspace in the HTTP-trigger gateway handler lets any authenticated caller collide with and reject another workflow's in-flight request - (File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go)

## Summary
`httpTriggerHandler` maintains a single flat map `h.callbacks map[string]savedCallback` keyed only by the client-supplied JSON-RPC `id` field, with no workflow, workflow-owner, or requester scoping. [1](#0-0)  `setupCallback` rejects a request with `jsonrpc.ErrConflict` if that bare string key is already present in the map, regardless of which workflow the earlier occupant belonged to. [2](#0-1)  Since `validateRequestID` only checks for non-empty and absence of `/`, two independently authorized requests for two entirely different workflows can legitimately share the same `id`, and whichever reaches `setupCallback` first causes the second to be rejected. [3](#0-2) 

## Finding Description
The full request flow is: `validatedTriggerRequest` → `resolveWorkflowID` → `authorizeRequest` → `checkRateLimit` → `setupCallback` → `sendWithRetries`. [4](#0-3)  `authorizeRequest` verifies the JWT for the given `workflowID` (that the request is a legitimately signed, non-replayed call for *that* workflow) but does not tie the plaintext `id` string itself to a workflow, owner, or requester identity. [5](#0-4)  The uniqueness check in `setupCallback` operates purely on `h.callbacks[requestID]`, a single map shared across every workflow served by this handler instance. [2](#0-1)  The existing test suite documents only the same-workflow duplicate case (`req.ID` reused twice for the same registered workflow), confirming no cross-workflow namespacing exists in the tested behavior. [6](#0-5)  I confirmed by reading the full file that no additional scoping (e.g., prefixing the map key with `workflowID`) occurs anywhere between authorization and `setupCallback`; `req.ID` is passed through unmodified from `HandleUserTriggerRequest` at line 141 into `setupCallback`. [7](#0-6) 

This matches the described root cause: a non-secret, client-controlled identifier is used as the sole collision-detection key across trust boundaries (different workflow owners), so an authenticated party can deny a specific service to another authenticated party without needing their credentials — only knowledge of the exact `id` string they intend to use.

## Impact Explanation
The concrete impact is a single-request denial of service: a targeted, correctly-signed request for workflow B is rejected with `jsonrpc.ErrConflict` ("requestID: X has already been used...") if an attacker (owner of any other registered workflow A) submits a request with the identical `id` value first. [8](#0-7)  This is a genuine logic flaw in the gateway's request-handling code (not a volumetric/network DDoS), and it maps to the "gateway request corruption / cross-user interference" category rather than the "DDoS" exclusion in `SECURITY.md`, which targets network-layer flooding attacks against infrastructure, not a single-request logic collision. [9](#0-8) [10](#0-9) 

However, the practical severity is limited: the victim's request is simply rejected once (with a clear, actionable error) and can be retried immediately with a different `id`; there is no state corruption, no impersonation of the victim's execution, no fund movement, and no persistent denial (the attacker would have to win this race for every single victim request to sustain disruption). This is a narrow griefing/availability nuisance rather than a severe DoS.

## Likelihood Explanation
Exploitability hinges entirely on the attacker knowing, in advance, the exact `id` string the victim's client is about to submit. Request IDs are conventionally chosen by client SDKs to be high-entropy and unpredictable (e.g., UUIDs) precisely because they are also used downstream for execution-ID derivation (`workflows.EncodeExecutionID`, `GenerateExecutionIDWithTriggerIndex`). [11](#0-10)  I was unable to find production client code in this repository (only test helpers) that generates low-entropy or externally observable IDs, so the claim that "callers frequently choose low-entropy IDs" is unverified speculation rather than a demonstrated fact about real CRE clients. Without a verified low-entropy ID source in normal usage, the realistic likelihood of an attacker correctly guessing a victim's `id` before the victim's request lands is low.

## Recommendation
Scope the in-flight callback map key by `(workflowID, requestID)` — e.g., a composite key such as `workflowID + "/" + requestID` (the `/` character is already reserved and disallowed in user-supplied IDs, so it can safely be used as a separator) — so that ID collisions can only occur within the same workflow, matching the intended per-workflow uniqueness contract.

## Proof of Concept
1. Register two distinct workflows, A (attacker-owned) and B (victim-owned), on the same gateway node/handler instance, as in `createTestTriggerHandler`/`registerWorkflow` in the existing test file. [12](#0-11) 
2. Attacker sends a validly signed `workflows.execute` request for workflow A with `id = "X"`.
3. Before the victim's request for workflow B with `id = "X"` is processed, `setupCallback` inserts `"X"` into `h.callbacks` for workflow A's request. [2](#0-1) 
4. Victim's request for workflow B, with the same `id = "X"`, arrives and is rejected with `jsonrpc.ErrConflict`, exactly as demonstrated (for the same-workflow case) in the existing `"duplicate request ID"` test — the same code path fires irrespective of whether the first occupant belongs to a different workflow. [13](#0-12) 
5. A minimal Go integration test extending `createTestTriggerHandler` to register two workflows and submit colliding `id`s from each would concretely prove the cross-workflow rejection.

func (h *httpTriggerHandler) HandleUserTriggerRequest(ctx context.Context, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback, requestStartTime time.Time) error {
	triggerReq, err := h.validatedTriggerRequest(ctx, req, callback)
	if err != nil {
		return err
	}

	workflowID, err := h.resolveWorkflowID(ctx, triggerReq, req.ID, callback)
	if err != nil {
		return err
	}

	key, err := h.authorizeRequest(ctx, workflowID, req, callback)
	if err != nil {
		return err
	}

	if err = h.checkRateLimit(ctx, workflowID, req.ID, callback); err != nil {
		return err
	}

	strippedWorkflowID := strings.TrimPrefix(workflowID, "0x")
	legacyExecutionID, err := workflows.EncodeExecutionID(strippedWorkflowID, req.ID) //nolint:staticcheck // legacy ID kept for observability comparison
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error generating execution ID: " + err.Error())
	}
	// Workflows shouldn't use more than one HTTP trigger. If we ever need to support multiple triggers, we'd need to pass
	// trigger index to the Gateway handler and somehow allow senders to pick. For now, we use trigger index 0.
	// Execution IDs here are used only for logging.
	executionIDWithTriggerIndex, err := workflows.GenerateExecutionIDWithTriggerIndex(strippedWorkflowID, req.ID, 0)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error generating execution ID with trigger index: " + err.Error())
	}
	h.lggr.Debugw("processing request",
		"legacyExecutionID", legacyExecutionID,
		"executionIDWithTriggerIndex", executionIDWithTriggerIndex,
		"requestID", req.ID,
		"workflowID", workflowID)

	reqWithKey, err := reqWithAuthorizedKey(triggerReq, *key)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error marshaling trigger request: " + err.Error())
	}

	doneCh, err := h.setupCallback(ctx, req.ID, callback, requestStartTime, workflowID)
	if err != nil {
		return err
	}

	return h.sendWithRetries(ctx, legacyExecutionID, executionIDWithTriggerIndex, reqWithKey, workflowID, doneCh)
}

func (h *httpTriggerHandler) validateRequestID(ctx context.Context, requestID string, callback handlers.Callback) error {
	if requestID == "" {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "'id' field is required and cannot be empty. Use a new unique request 'id' for each request", callback)
		return errors.New("empty request ID")
	}
	// Request IDs from users must not contain "/", since this character is reserved
	// for internal node-to-node message routing (e.g., "http_action/{workflowID}/{uuid}").
	if strings.Contains(requestID, "/") {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "request ID must not contain '/'", callback)
		return errors.New("request ID must not contain '/'")
	}
	return nil
}

func (h *httpTriggerHandler) authorizeRequest(ctx context.Context, workflowID string, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback) (*gateway_common.AuthorizedKey, error) {
	h.lggr.Debugw("authorizing request", "workflowID", workflowID, "requestID", req.ID)
	key, err := h.workflowMetadataHandler.Authorize(workflowID, req.Auth, req)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInvalidRequest, "Auth failure: "+err.Error(), callback)
		return nil, errors.Join(errors.New("auth failure"), err)
	}
	return key, nil
}

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}
