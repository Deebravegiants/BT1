### Title
Webhook `shop` field is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` binds the HMAC only to the raw request body, while the `shop` (and `topic`, `api_version`, `webhook_id`) values are read from HTTP headers that are excluded from the signed payload. `Registry.process` validates the HMAC and then trusts `request.shop` to build the `WebhookMetadata` passed to the host app's handler, so the shop attribution can be forged independently of the signature that protects only the body.

### Finding Description
`Request#hmac` and `Request#to_signable_string` show that the signable content is `@raw_body` alone: [1](#0-0) [2](#0-1) 

`shop` is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never included in `to_signable_string`: [3](#0-2) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` (which calls `request.to_signable_string`, i.e. the body only) and then forwards `request.shop` unchecked into `WebhookMetadata`, which the host app's `WebhookHandler#handle` uses to scope tenant data: [4](#0-3) 

The binding that should hold is: `hmac == HMAC(secret, body ++ shop ++ topic)`, i.e. the shop identity should be cryptographically bound to the same signature that protects the payload. Instead, the gem only verifies `hmac == HMAC(secret, body)`, decoupling the trusted body from the untrusted shop header.

### Impact Explanation
Because the shop header is outside the HMAC's scope, any raw_body/hmac pair that was legitimately generated by Shopify for one merchant's webhook delivery remains valid if resubmitted to the app's public webhook endpoint with the `shopify-shop-domain` header changed to a different (victim) shop. `Utils::HmacValidator.validate` will still return `true` because it only recomputes the HMAC over `@raw_body`. The handler then receives a `WebhookMetadata` claiming the payload belongs to the victim shop while the actual signed body content is the attacker's own. Any host application logic that trusts `WebhookMetadata#shop` for tenant-keyed writes, uninstall/redact processing, or authorization decisions can be corrupted this way — a cross-tenant data/action confusion inside a gem-provided integrity check that developers are told to rely on (`Utils::HmacValidator.validate`).

### Likelihood Explanation
Webhook endpoints are public HTTP endpoints by design (Shopify posts to them without further authentication beyond the HMAC). Any unprivileged internet user who operates their own Shopify development shop can legitimately receive a real webhook (valid `raw_body` + `hmac` for their own shop), and then replay that exact body/HMAC pair to the target app's webhook URL with only the `shopify-shop-domain` header altered. No access token, `client_secret`, or privileged credential is required — only the ability to observe one legitimate webhook delivery for any shop and resend it with a modified header. This is a stronger, "identity-binding" version of the referenced report's pattern (a field acted upon but not covered by the integrity check).

### Recommendation
Include the `shop` (and ideally `topic`, `api_version`) header values in the signed payload used for verification, or otherwise cryptographically bind them to the validated body — e.g. require the host app to additionally verify that the `shop` returned matches an expected/registered shop for that webhook subscription, or extend `to_signable_string` to canonically include the relevant headers so `Utils::HmacValidator.validate` fails when they are altered.

### Proof of Concept
1. Attacker registers/owns `attacker-shop.myshopify.com` and receives a legitimate Shopify webhook: headers include `X-Shopify-Hmac-Sha256: <valid hmac>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, and some `raw_body`.
2. Attacker resends the identical `raw_body` and `X-Shopify-Hmac-Sha256` value to the target app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`= raw_body` only) — validation succeeds since body/hmac are untouched.
4. `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` is invoked with `shop == "victim-shop.myshopify.com"`, even though the body content actually originated from `attacker-shop.myshopify.com`, letting the attacker inject spoofed events attributed to the victim tenant.
