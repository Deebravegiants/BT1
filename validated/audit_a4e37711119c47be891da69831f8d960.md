### Title
Webhook `topic` and `shop` are read from unsigned headers and forwarded unchecked to the handler after only the body HMAC is verified - (File: `lib/shopify_api/webhooks/registry.rb`)

### Summary
`Webhooks::Registry.process` validates only the raw HTTP body against the HMAC, then uses `request.topic` and `request.shop` — both taken straight from HTTP headers that are never part of the signed payload — to select the handler and build the `WebhookMetadata` passed into application code. Since Shopify signs webhooks with a single app-wide secret shared across every installed shop, an attacker who owns their own development shop can capture one genuinely signed `(body, hmac)` pair and replay it against the victim app's webhook endpoint with swapped `X-Shopify-Topic`/`X-Shopify-Shop-Domain` headers, causing the handler to believe attacker-controlled data originated from a different shop/topic.

### Finding Description
The broken binding: the invariant assumed by callers of `process` is
`request.shop (delivered to handler) == shop that actually produced/authorized request.parsed_body`.
In reality:

- `HmacValidator.validate` computes the signature only over `to_signable_string`, which for `Webhooks::Request` returns `@raw_body` and nothing else: [1](#0-0) [2](#0-1) 
- `topic` and `shop` are pulled from headers with no cryptographic binding to the body or to each other: [3](#0-2) 
- `process` first checks the HMAC over the body only, then immediately trusts `request.topic` to select the handler and `request.shop` to construct `WebhookMetadata` that is handed to application code: [4](#0-3) 
- The secret used to compute/verify the HMAC, `Context.api_secret_key`, is a single value shared by the app across **all** installed merchant shops — it is not shop-specific: [5](#0-4) 

Because the secret is shared across tenants and the signature covers only the body, an unprivileged attacker can:
1. Create their own development shop and install the target app (permitted per the rules).
2. Register a webhook and let Shopify deliver a genuinely, validly-signed `(body, hmac)` pair to a server they control.
3. Replay that exact `body` + `hmac` to the victim app's public webhook-processing endpoint, but with `X-Shopify-Topic` and/or `X-Shopify-Shop-Domain` headers changed to arbitrary values (e.g., the victim's shop domain, or a different topic than what was actually signed).
4. `Utils::HmacValidator.validate` still returns `true`, because it only recomputes the HMAC over `@raw_body`, which is unchanged. `process` then uses the forged `topic` header to pick a (potentially different) handler and passes the forged `shop` header into `WebhookMetadata`, which application code typically uses to load/authorize per-shop state.

None of the existing guards catch this: `Context.setup?`/`private?`/`embedded?` and Sorbet typing do not validate any relationship between the signed body and the header-derived `topic`/`shop`; there is no cross-check anywhere in `registry.rb` or `request.rb` that the topic/shop implied by the body matches the header values.

`add_registration` itself is not attacker-reachable (it is called by the app developer at boot time with static topics), but it is the origin of the `@registry` keyed purely by `topic` string that `process` later looks up using the attacker-controlled header — this is what makes the topic-spoofing effective for handler selection.

### Impact Explanation
An attacker can cause the app's webhook handler to execute with a spoofed `shop` (and/or `topic`) value while still passing signature verification, using only their own legitimately-issued webhook. Any handler logic that trusts `WebhookMetadata#shop` to scope database writes/reads, cache invalidation, session lookups, or billing/entitlement changes can be tricked into acting on/for the wrong tenant — i.e., cross-tenant access, matching the Critical impact class. The attack is repeatable against any topic the app has registered and any victim shop domain the attacker chooses, requiring no credentials beyond the ability to install the app once on a shop they control.

### Likelihood Explanation
Preconditions are minimal and fully within the described attacker capability: install the app on a shop you control, receive one webhook, and replay it with different headers to the app's public webhook endpoint. No `api_secret_key`, access token, or victim cooperation is required. This is straightforward to automate and repeat against arbitrary target shop domains.

### Recommendation
Bind the header values into the signed payload the handler receives, or verify them against body-embedded shop/topic information before dispatch. Concretely: include `topic` and `shop-domain` in `to_signable_string` (mirroring what Shopify actually signs, per Shopify's own HMAC verification guidance), and/or independently confirm that the shop domain in the JSON body (where available) matches the header before invoking `handler.handle`.

### Proof of Concept
```ruby
# test/webhooks/registry_topic_spoof_test.rb
require "test_helper"

class RegistryTopicSpoofTest < Test::Unit::TestCase
  def setup
    ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", ...)
    ShopifyAPI::Webhooks::Registry.add_registration(
      topic: "orders/create", delivery_method: :http, path: "/webhooks",
      handler: victim_handler,
    )
  end

  def test_replayed_body_with_forged_shop_and_topic_passes_hmac
    raw_body = '{"id":1}'
    secret = ShopifyAPI::Context.api_secret_key
    hmac = Base64.encode64(OpenSSL::HMAC.digest("sha256", secret, raw_body)).strip

    # Attacker replays the SAME signed body but swaps shop/topic headers
    request = ShopifyAPI::Webhooks::Request.new(
      raw_body: raw_body,
      headers: {
        "x-shopify-hmac-sha256" => hmac,
        "x-shopify-topic" => "orders/create",
        "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker never owns this shop
        "x-shopify-api-version" => "2024-01",
        "x-shopify-webhook-id" => "1",
      },
    )

    assert ShopifyAPI::Utils::HmacValidator.validate(request) # signature still valid

    metadata_shop = nil
    victim_handler.define_singleton_method(:handle) { |data:| metadata_shop = data.shop }

    ShopifyAPI::Webhooks::Registry.process(request)

    # Handler received the attacker-forged shop despite the body never being
    # produced/authorized by that shop.
    assert_equal "victim-shop.myshopify.com", metadata_shop
  end
end
```
This demonstrates that the equality `request.shop == shop that authorized request.parsed_body` does not hold: the HMAC check passes on a replayed body while `shop`/`topic` are freely forgeable via headers.
