### Title
Webhook `shop-domain` Header Is Not Covered by HMAC, Enabling Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (and `topic`, `webhook_id`, `api_version`) attribute from the `X-Shopify-Shop-Domain` HTTP header, but `Utils::HmacValidator.validate` only verifies the HMAC over the raw request body (`to_signable_string` returns `@raw_body` only). `Registry.process` accepts any request whose body/HMAC pair is valid and then dispatches to the app's handler using the unauthenticated `shop` header value, breaking the equality "bytes verified by HMAC" == "shop attributed to the processed webhook."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` fields are all read straight from HTTP headers, none of which are included in the signable string: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)` — which internally calls `verifiable_query.to_signable_string` (the body only) — and, if it passes, immediately forwards `request.shop` (the unauthenticated header) into `WebhookMetadata` for the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate_signature` confirms the signature check is computed purely from `to_signable_string`: [4](#0-3) 

And `WebhookMetadata.shop` is a plain, unauthenticated field passed on to the handler: [5](#0-4) 

Because the HMAC is computed only over the raw body with the app's `api_secret_key`, any two webhook deliveries that happen to carry the *same raw body* (e.g., an empty `{}` payload for a topic like `app/uninstalled`, or any topic whose payload an attacker's own shop can make identical/predictable) will produce the *same valid HMAC signature*, independent of which shop they were generated for. An attacker who controls their own shop can capture (or predict) a genuinely-signed `(raw_body, hmac)` pair from a webhook Shopify sends to their app for their own shop, then replay that exact body+HMAC to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header with a victim shop's domain. `HmacValidator.validate` will still return `true` because it never looks at the header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming to be from the victim shop.

This breaks the intended binding: "the shop whose webhook body was actually HMAC-authenticated by Shopify" should equal "the shop the app processes the webhook as." Instead the app trusts the header's shop value with no cryptographic tie to the body that was actually verified.

### Impact Explanation
This is a cross-tenant identity-binding break at the "field acted on but not covered by the HMAC" pattern called out in scope. Any app whose `WebhookHandler#handle` implementation uses `WebhookMetadata#shop` to select/mutate/delete tenant-scoped state (a documented, expected usage pattern of this field) can be tricked into acting on the wrong tenant's data using a validly-signed-but-replayed body from an attacker-controlled shop. This satisfies the "cross-tenant access" criterion for Critical impact, since the vulnerability is reachable by any unprivileged internet user who can install the app on their own shop (to legitimately receive a signed webhook) and then replay the request to the app's public webhook endpoint with a forged header — no leaked credentials, TLS interception, or privileged account required.

### Likelihood Explanation
Likelihood is bounded by two factors that reduce but do not eliminate exploitability: (1) the attacker needs a raw body that is byte-identical (or otherwise producible) between their own shop's webhook and the topic/shape used against the victim — trivially true for topics with empty or highly predictable/constant bodies (e.g., `app/uninstalled`, or topics with only shop-invariant fields), and (2) it requires the host application to trust `WebhookMetadata#shop` for tenant selection, which is the officially documented/expected usage of that field. Given these are common, realistic conditions for real-world Shopify apps, likelihood is moderate-to-high for apps handling topics with predictable payloads.

### Recommendation
Bind the trusted identity fields into the HMAC-verified signable string, or independently authenticate the `shop` header against a value that is verifiable (e.g., cross-check `request.shop` against the shop associated with a valid, separately-verified session/webhook subscription id, or include shop/topic/webhook-id in the signable string used for the HMAC check) so that the header used for tenant dispatch cannot be swapped without invalidating the signature. At minimum, document prominently that `WebhookMetadata#shop` is not covered by the HMAC and must not be trusted for tenant selection without additional verification (e.g., against the app's own webhook-id ↔ shop registry).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers/receives a genuine webhook for a topic whose body is constant/predictable (e.g. `{}` for `app/uninstalled`), capturing the valid `X-Shopify-Hmac-Sha256` header and raw body Shopify sent.
2. Attacker sends a raw HTTP POST directly to the app's public webhook endpoint with:
   - Same raw body captured in step 1
   - Same `X-Shopify-Hmac-Sha256` header captured in step 1
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (forged)
   - `X-Shopify-Topic` / `X-Shopify-Webhook-Id` set as needed
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which validates successfully because it only checks the raw body against the secret — it never inspects the `shop-domain` header: [6](#0-5) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` despite the payload never actually originating from or being verified for that shop, and any tenant-scoped action taken by the handler (e.g. deleting local data associated with `victim-shop.myshopify.com`) is performed on the wrong tenant.
