This confirms the finding: the gem's own documentation states `Registry.process` "will verify the request did indeed come from Shopify" [1](#0-0) , and presents `data.shop` to the handler as trusted, verified webhook metadata [2](#0-1) , yet the HMAC signature computed by this gem only covers the raw body, never the `shop-domain` header.

### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [3](#0-2) , while `shop`, `topic`, `webhook_id`, and `api_version` are read directly and unauthenticated from HTTP headers [4](#0-3) . `Registry.process` validates only this body-derived HMAC and then, on success, builds a `WebhookMetadata` struct using the unauthenticated `request.shop` value and hands it to the app's handler as verified data [5](#0-4) .

### Finding Description
The identity binding that should hold is:
`HMAC-verified bytes (raw_body)` == `bytes used to determine the tenant (shop header used to populate WebhookMetadata#shop)`

This binding is broken: `HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`, which for webhooks is solely `@raw_body` [6](#0-5) . The `shop` field returned by `Request#shop` comes straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header with no cryptographic binding to the signed body [7](#0-6) .

Because the HMAC only proves "this body was signed by Shopify with our secret," and not "this body was sent for shop X," any two (body, hmac) pairs Shopify has legitimately produced for the *same app* remain valid regardless of which `shop-domain` header value accompanies them. An unprivileged party who operates their own shop that has installed the app (or who otherwise obtains one legitimately-signed body/HMAC pair sent to the app's webhook endpoint) can resend that exact body and HMAC to the app's webhook URL while substituting an arbitrary `x-shopify-shop-domain` header. `Registry.process` will accept it — `Utils::HmacValidator.validate(request)` succeeds because it only checks the body [8](#0-7)  — and the handler receives `WebhookMetadata` carrying the attacker-chosen `shop` value alongside genuine-looking, HMAC-verified `body` content [9](#0-8) .

Since the gem's own docs instruct developers that `process` "will verify the request did indeed come from Shopify" [1](#0-0)  and describe `data.shop` simply as "The shop domain of the webhook" without any caveat that it is unauthenticated [2](#0-1) , host applications are led to trust `data.shop` as the verified tenant identity for routing/storing webhook data (as shown in the gem's own example, `perform_later(topic: data.topic, shop_domain: data.shop, ...)` [10](#0-9) ). This is not a case of the host app ignoring documented behavior — it is following the gem's documented contract exactly, and the gem itself supplies the unverified value as if it were verified.

### Impact Explanation
This enables cross-tenant confusion: webhook payloads that are cryptographically proven to originate from Shopify for the app can be re-labeled with an arbitrary target shop domain by any party capable of triggering or replaying one legitimate webhook delivery to the app (e.g., a merchant with their own install of the app). If the host application uses `data.shop` (as documented and exemplified by the gem) to select the tenant record/session to update with `data.body`, an attacker can inject data attributed to Shopify into another merchant's tenant context — a cross-tenant integrity issue rooted in this gem's failure to bind the signed payload to the shop identity it reports.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one legitimately Shopify-signed (body, HMAC) pair delivered to the app's public webhook endpoint — obtainable by any merchant who installs the app themselves and receives real webhooks for their own store, or by intercepting/replaying a delivery to the public endpoint. No access to `api_secret_key`, access tokens, or `client_secret` is needed, satisfying the "unprivileged internet user" bar. Exploitation likelihood depends on how the host app uses `data.shop`, but the underlying binding failure is entirely within this gem's `HmacValidator`/`Webhooks::Request`/`Registry.process` code path.

### Recommendation
Include the shop-domain (and ideally topic/webhook-id) header values as part of the signed material verified by `HmacValidator`, or otherwise cryptographically bind `WebhookMetadata#shop` to the verified body (e.g., have `Request#to_signable_string` incorporate the normalized headers, not just `@raw_body`). At minimum, update documentation to explicitly warn that `data.shop` is not covered by the HMAC and must be independently corroborated (e.g., against the shop associated with the delivered `webhook_id`/registration) before being used for tenant-scoped writes.

### Proof of Concept
1. App registers `orders/create` webhook handler that does `perform_later(shop_domain: data.shop, webhook: data.body)` per the gem's documented example [10](#0-9) .
2. Attacker installs the app on their own shop `attacker-shop.myshopify.com` and captures a real Shopify webhook delivery `(raw_body, x-shopify-hmac-sha256, ...)` sent to the app's public webhook endpoint.
3. Attacker resends the identical `raw_body` and `x-shopify-hmac-sha256` value to the same endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` recomputes HMAC over `raw_body` only and it matches, since the header was never part of the signed content [6](#0-5) .
5. `Registry.process` proceeds and dispatches `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's own order data>, ...)` to the handler [11](#0-10) , causing the host app to process/store attacker-supplied, Shopify-signed-looking data under the victim tenant's identity.
