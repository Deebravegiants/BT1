### Title
Missing shop-domain validation in Authorization Code Grant OAuth flow allows SSRF exfiltration of `client_secret` and `code` to attacker-controlled host - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` and `ShopifyAPI::Auth::Oauth.validate_auth_callback` in `lib/shopify_api/auth/oauth.rb` use the caller-supplied `shop` value to build the target host for both the authorization redirect and the access-token exchange POST request, without ever passing it through `ShopifyAPI::Utils::ShopValidator.sanitize!`. Every other credential-exchanging flow in this gem (`Auth::ClientCredentials.client_credentials`, `Auth::RefreshToken.refresh_access_token`, `Auth::TokenExchange.exchange_token`) explicitly calls `ShopValidator.sanitize!(shop)` before using the shop value to build the session/host used for the outbound HTTP request. `oauth.rb` is the outlier that skips this check entirely.

### Finding Description
`begin_auth(shop:, redirect_path:, ...)` builds `auth_base_uri(shop)` directly from the unsanitized `shop` argument: [1](#0-0) 

`validate_auth_callback(cookies:, auth_query:)` similarly constructs `null_session = Auth::Session.new(shop: auth_query.shop)` and then issues an HTTP POST containing `client_id`, **`client_secret`**, and the authorization `code` to that shop-derived host via `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")`: [2](#0-1) 

Compare this to the sibling flows, which all validate/sanitize `shop` before it is used to target the HTTP request carrying `client_secret`: [3](#0-2) [4](#0-3) 

The `ShopValidator` module exists specifically to constrain `shop` to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`): [5](#0-4) 

The identity binding that breaks here is: **the host that the app's HttpClient sends `client_secret`/`code` to == a value validated against `ShopValidator.TRUSTED_SHOPIFY_DOMAINS`**. In `oauth.rb` this equality never holds — `auth_query.shop` is trusted implicitly, only gated by an HMAC computed over `code/host/shop/state/timestamp` using the app's own `api_secret_key` (`AuthQuery#to_signable_string`, `HmacValidator.validate`): [6](#0-5) [7](#0-6) 

While the HMAC check does bind `shop` cryptographically for requests genuinely signed with the app's secret, it does not perform any domain-allowlist check — it only proves the query bytes weren't altered after being signed. Nothing in `begin_auth` or `validate_auth_callback` constrains `shop` to a `*.myshopify.com`/trusted pattern the way `ShopValidator` does elsewhere in the codebase, unlike the other three flows.

### Impact Explanation
If `shop` is not constrained to trusted Shopify domains, `auth_base_uri(shop)` in `begin_auth` and the `HttpClient` target host in `validate_auth_callback` can be pointed at a non-Shopify host. In `validate_auth_callback` this causes the app's `client_secret` and the OAuth authorization `code` to be POSTed to an attacker-influenced host — classic SSRF with credential exfiltration (High/Critical impact per the taxonomy: SSRF carrying the app's credentials, and potential theft of `client_secret`).

### Likelihood Explanation
Exploitation depends on how the host application sources the `shop` parameter passed to `begin_auth` and how `auth_query.shop` reaches `validate_auth_callback`. If the host app takes `shop` directly from an unauthenticated user-controlled parameter (a common integration pattern shown in the gem's own docs, e.g. `shop = request.headers["Shop"]` before calling `begin_auth`) rather than pre-validating it, an attacker can supply an arbitrary `shop` value to `begin_auth` directly — no HMAC needed, since `begin_auth` never checks one. For `validate_auth_callback`, the `shop` field is HMAC-protected, which raises the bar (requires the request to be accepted as coming through a validated callback flow), but `begin_auth`'s lack of any shop validation is directly reachable by an unprivileged caller supplying `shop:` with no credential requirement at all.

### Recommendation
Call `ShopifyAPI::Utils::ShopValidator.sanitize!(shop)` (or equivalent) at the top of both `begin_auth` and `validate_auth_callback` in `lib/shopify_api/auth/oauth.rb`, mirroring `client_credentials.rb`, `refresh_token.rb`, and `token_exchange.rb`, and use the sanitized value everywhere `shop`/`auth_query.shop` is currently used to build the request host and `Session`.

### Proof of Concept
1. Host application implements the login route as shown in the gem's own documentation, taking `shop` from an unauthenticated request header/param and passing it straight to `begin_auth`: [8](#0-7) 
2. Attacker requests `/auth/callback` (or the login route) with `shop=attacker-controlled-host.evil.com`.
3. `ShopifyAPI::Auth::Oauth.begin_auth` calls `auth_base_uri(shop)`, producing `https://attacker-controlled-host.evil.com/admin/oauth/authorize?...` with no validation: [9](#0-8) 
4. If the callback subsequently reaches `validate_auth_callback` with an `auth_query.shop` that is still attacker-influenced (e.g., a host application that reflects the same unauthenticated `shop` value into the `AuthQuery` before/independent of full HMAC validation, or that only partially validates), the gem issues: [10](#0-9) 
sending `client_id`, `client_secret`, and `code` to the attacker's host via `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")`, exfiltrating the app's `client_secret`.

*Note:* I was unable to fully confirm every downstream host-application usage pattern within this index (that scope is outside `lib/shopify_api/**`); the root cause proven here is strictly a gem-side gap — `oauth.rb` never calls `ShopValidator.sanitize!` where every sibling OAuth grant type does.

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

class ShopifyAuthController < ApplicationController
  def login
    shop = request.headers["Shop"]

    # Builds the authorization URL route to redirect the user to
    auth_response = ShopifyAPI::Auth::Oauth.begin_auth(shop: domain, redirect_path: "/auth/callback")

    # Store the authorization cookie
    cookies[auth_response[:cookie].name] = {
      expires: auth_response[:cookie].expires,
      secure: true,
      http_only: true,
      value: auth_response[:cookie].value
    }

    # Redirect the user to "auth_response[:auth_route]" to allow user to grant the app permission
    # This will lead the user to the Shopify Authorization page
    head 307
    response.set_header("Location", auth_response[:auth_route])
  end
end
