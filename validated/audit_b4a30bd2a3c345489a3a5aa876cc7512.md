### Title
Permanent market freeze from RAY value overflow during interest accrual - (File: common/src/rates/simulate.rs)

### Summary

Large market positions can make `scaled * index` exceed the `i128` range before either index reaches its configured ceiling, causing `accrue_step` to panic with `MathOverflow`. [1](#0-0) [2](#0-1)  Because every pool mutation accrues the market before applying the operation, the overflow permanently prevents repayment, withdrawal, liquidation, bad-debt cleanup, and further index updates for that market. [3](#0-2) [4](#0-3) 

### Finding Description

`accrue_step` first reconstructs current supplied and borrowed values with `scaled_to_original`, which performs `scaled.mul(index)` and therefore evaluates `scaled * index / RAY` as an `i128` result. [5](#0-4) [2](#0-1)  `Ray::mul` delegates to `mul_div_half_up`, which panics with `GenericError::MathOverflow` when the representable result does not fit in `i128`. [6](#0-5) [7](#0-6) 

The later `borrow_index` cap does not prevent this condition because the unbounded position-value multiplication happens before the capped index can protect the calculation. [8](#0-7)  `global_sync` executes this accrual path before mutating operations, while `load_leg` is used by repay, withdraw, and other position legs. [9](#0-8) [3](#0-2) 

An unprivileged user can reach the affected path through `Controller::supply`, `Controller::borrow`, `Controller::withdraw`, `Controller::repay`, `Controller::liquidate`, `Controller::clean_bad_debt`, or `Controller::update_indexes` once an admitted market accumulates enough scaled exposure and index growth. [10](#0-9) [11](#0-10)  The repository’s long-horizon test demonstrates this exact failure: a one-billion-token 18-decimal market at sustained high utilization reaches the RAY value ceiling before the index cap, after which `update_indexes`, `withdraw`, and `repay` all return `MATH_OVERFLOW`. [12](#0-11) 

### Impact Explanation

The first transaction after the crossing point reverts during accrual and never commits a new `last_timestamp`, so every later transaction starts from the same unsafe state and hits the same panic. [3](#0-2) [13](#0-12)  Consequently, suppliers cannot withdraw collateral, borrowers cannot reduce debt, liquidators cannot unwind unhealthy accounts, and permissionless bad-debt processing cannot progress for the affected market. [14](#0-13)  This is permanent freezing of user funds for all positions depending on that market, not merely a temporary denial caused by a pause flag or stale oracle. [15](#0-14) 

### Likelihood Explanation

Exploitation requires an admitted asset with a sufficiently large cap and token supply, plus enough collateral-backed borrowing to keep utilization high while indexes grow. [16](#0-15)  Those conditions are within the protocol’s normal accounting domain because entry uses the configured cap and index to mint scaled shares, while no comparable invariant keeps `scaled * index` inside the `i128` result domain for future accrual. [17](#0-16) [18](#0-17)  The included regression test reaches the cliff at 98% utilization without changing market code and confirms that the index ceiling does not engage first. [19](#0-18) 

### Recommendation

Enforce a market-level exposure bound that accounts for the maximum future index, rather than only limiting admitted token amounts. [20](#0-19)  In particular, admission and usage checks should guarantee that `supplied * MAX_SUPPLY_INDEX_RAY / RAY` and `borrowed * MAX_BORROW_INDEX_RAY / RAY` remain representable, or `accrue_step` should be redesigned so utilization and interest can be calculated without materializing an overflowing position value. [21](#0-20)  If saturation is used for utilization, it must not silently continue accrual with a distorted denominator; the safer behavior is to reject additional exposure before the market enters the unsafe domain and preserve exit-only handling for already-admitted positions. [22](#0-21) [23](#0-22) 

### Proof of Concept

The repository test constructs the reachable state by supplying one billion 18-decimal units to `BIG18`, borrowing 98% of it against sufficient `COL`, and advancing ledger time until `update_indexes` panics. [24](#0-23) 

```rust
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);
let debt = principal / 100 * 98;
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);

loop {
    t.advance_time(YEAR_SECS);
    if t.try_update_indexes_for(&["BIG18"]).is_err() {
        break;
    }
}

assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

The failing transition occurs when `supplied * supply_index` or `borrowed * borrow_index` can no longer be represented as `i128`, and the stored `last_timestamp` is not advanced because `global_sync` panics before `mark_accrued` runs. [25](#0-24) [13](#0-12)  The test then verifies that both supplier exit and debt repayment fail with the same `MATH_OVERFLOW`, proving permanent loss of access rather than a single-transaction accounting error. [15](#0-14)

/// Computes `x * y / d` rounded half up. Requires `x >= 0`, `y >= 0`, and `d > 0`; a
/// `debug_assert` checks this in debug builds. Panics with `GenericError::DivisionByZero` if
/// `d == 0`, and with `GenericError::MathOverflow` if any other precondition is violated or if
/// the result does not fit in `i128`.
pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.
    require_nonzero_divisor(env, d);
    debug_assert!(
        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}

pub fn update_supply_index(env: &Env, supplied: Ray, old_index: Ray, rewards_increase: Ray) -> Ray {
    if supplied == Ray::ZERO || rewards_increase == Ray::ZERO {
        return old_index;
    }

    let total_supplied_value = supplied.mul(env, old_index);

    if total_supplied_value == Ray::ZERO {
        return old_index;
    }

    let new_value = total_supplied_value.checked_add(env, rewards_increase);
    let grown = fp_core::mul_div_floor_saturating(env, new_value.raw(), RAY, supplied.raw());

    let bounded_old = old_index.raw().min(MAX_SUPPLY_INDEX_RAY);
    Ray::from(grown.min(MAX_SUPPLY_INDEX_RAY).max(bounded_old))
