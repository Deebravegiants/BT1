This confirms the vulnerability. The library documents `data.shop` as a trusted field for identifying which merchant the webhook belongs to, but the code only signs the raw body.

### Title
Webhook `shop` header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while the `shop` (and `topic`/`webhook_id`) values are read directly from unauthenticated HTTP headers. `Registry.process` validates only the body-derived HMAC and then hands the attacker-controlled `shop` value straight to the app's webhook handler, breaking the binding between "the bytes that were HMAC-verified" and "the shop the app believes the data belongs to."

### Finding Description
`Utils::HmacValidator.validate` computes and compares the HMAC solely over `verifiable_query.to_signable_string`, which for webhooks is just `@raw_body`: [1](#0-0) 
The `shop` accessor, however, is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never part of the signed payload: [2](#0-1) 
`Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e. body integrity) and then immediately constructs `WebhookMetadata` using `request.shop`, `request.topic`, and `request.parsed_body`, passing it to the app's handler with no cross-check that the header-derived `shop` matches anything inside the signed body: [3](#0-2) 

The identity binding the gem effectively promises is `hmac(raw_body) == hmac(secret)` implies "this webhook, including its `shop`, is authentic." In reality the equality only holds for `raw_body`; `shop_header != shop_bound_by_hmac` because no such binding exists. The documentation explicitly tells app authors to trust and route on `data.shop`: [4](#0-3) 

**Exploit path:** Any unprivileged user who can install the app on their own store (a normal, unprivileged merchant) legitimately receives real webhook deliveries for their own shop — i.e., a valid `(raw_body, hmac)` pair signed with the app's `api_secret_key`, which they never need to know. That attacker can then resend an HTTP POST containing the *exact same* `raw_body` and `hmac-sha256` header to the app's webhook endpoint, but substitute the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still passes (it only checks the body), so `Registry.process` invokes the handler with `data.shop == "victim.myshopify.com"` even though the body content and HMAC were only ever authentic for the attacker's own shop.

### Impact Explanation
This is a cross-tenant data-integrity break: the app is tricked into attributing one shop's authentic webhook payload (orders, customers, uninstall notifications, etc.) to a different, victim tenant. Since most host apps (per the documented usage pattern) key their persistence, job queues, or business logic off `data.shop`, an attacker can inject fabricated events into another merchant's data/queue, trigger app-uninstall or GDPR-style flows for a shop they don't own, or pollute another tenant's records — a cross-tenant access/integrity violation reachable by any unprivileged internet user who has (or can obtain) one authentic webhook delivery of their own.

### Likelihood Explanation
Likelihood is meaningful: no secret material is required, no privileged Shopify credentials are needed, and the only prerequisite is installing the app once as a normal merchant to receive one legitimate webhook, then replaying it with a modified header against the app's public webhook endpoint. The webhook endpoint is publicly reachable by design (Shopify posts to it over the internet), so there is no network-position or credential barrier beyond having installed the app.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, or otherwise cross-validate the header-derived `shop` against a value not attacker-controlled (e.g., look up the shop from `webhook_id` via a stored subscription mapping, or require the host app to confirm `data.shop` has an active session before trusting it). At minimum, document prominently that `data.shop` is not covered by Shopify's webhook HMAC and must not be trusted for authorization/tenant-scoping without an independent check against a known/installed shop list.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` (unprivileged, self-service action) and receives a real webhook, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: HMAC(B, secret)` — both authentic, secret unknown to attacker.
2. Attacker resends to the app's public webhook endpoint:
   - `raw_body = B` (unchanged)
   - `x-shopify-hmac-sha256 = HMAC(B, secret)` (unchanged, still valid)
   - `x-shopify-shop-domain = victim-shop.myshopify.com` (changed)
   - `x-shopify-topic`, `x-shopify-webhook-id` optionally changed too, since they're also unauthenticated per [5](#0-4) 
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which returns `true` because it only checks `raw_body` against the HMAC.
4. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host app to process attacker-supplied data under the victim's tenant identity.
