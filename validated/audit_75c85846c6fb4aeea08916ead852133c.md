### Title
Missing L2 sequencer uptime check in SimplexPaymaster Chainlink price fetch enables stale-price gas-fee mispricing - (File: evm/src/utils/SimplexPaymaster.sol)

### Summary
`SimplexPaymaster` is deployed to multiple chains, including L2 rollups (Arbitrum, Optimism/OP-stack, Base) per its Chainlink price-feed address registry, and prices sponsored gas in ERC-20 tokens using Chainlink `AggregatorV3Interface.latestRoundData()`. Its staleness check only bounds the age of the last reported update; it never verifies that the L2's Chainlink sequencer-uptime feed is up, so during a sequencer outage a previously-cached, technically "fresh-timestamped" (per L1 clock) but stale round can still be accepted to price a user's gas payment.

### Finding Description
`_getOraclePrice` in `evm/src/utils/SimplexPaymaster.sol` reads `latestRoundData()` from both the native/USD and token/USD Chainlink feeds and only checks that the answer is positive and that `block.timestamp - updatedAt <= maxOracleAge`: [1](#0-0) 

This mirrors exactly the vulnerable pattern in the reported Notional issue (`getOraclePrice` in `TradingModule.sol`, checking only `block.timestamp - updatedAt <= maxOracleFreshnessInSeconds`) — no Chainlink L2 sequencer-uptime feed (`0xFdB631F5EE196F0ed6FAa767959853A9F217697D` on Arbitrum, etc.) is ever queried. When an Arbitrum/OP-stack/Base sequencer goes down, the last on-chain Chainlink round can remain within `maxOracleAge` (up to 7 days per `MAX_ORACLE_AGE`) even though the market price it reports is no longer reliable, because no new transactions (including keeper price pushes) execute to invalidate or refresh it during the outage: [2](#0-1) 

This price feeds directly into `_tokenPrice`, which is called by `_fetchDetails` (the ERC-4337 paymaster validation hook invoked for every sponsored `UserOperation`) to determine how much ERC-20 the user pays for gas, and by `_prefund`/`_erc20Cost` to actually pull tokens via `transferFrom`/Permit2: [3](#0-2) [4](#0-3) 

The `RegisterToken`/`UpdateParams` governance paths configure `nativeOracle` and per-token oracles but never wire in or check any sequencer-uptime feed: [5](#0-4) 

Any unprivileged actor submitting an ERC-4337 `UserOperation` through the paymaster (the entry point this contract exists to serve) reaches this pricing path — no governance or privileged role is required to trigger `_fetchDetails`/`_prefund`.

### Impact Explanation
During and immediately after an L2 sequencer outage, `_getOraclePrice` can return a mispriced (stale-but-not-expired) rate. An attacker submitting `UserOperation`s during that window can either:
- Underpay for sponsored gas by exploiting a stale low `nativeUsd`/high `tokenUsd` snapshot, draining value from the paymaster's treasury/deposit over many sponsored operations, or
- Cause legitimate users to overpay, depending on price drift direction.

Because the paymaster directly transfers ERC-20 tokens from users (`_prefund`) and reimburses itself from the `EntryPoint` deposit based on this price, systematic mispricing directly siphons paymaster-held funds — a concrete theft/fund-drain vector reachable from ordinary submitted transactions (bundler-relayed UserOperations), satisfying the "concrete theft" bar for a Medium-severity finding.

### Likelihood Explanation
L2 sequencer outages are a known, recurring operational risk on Arbitrum/OP-stack chains (documented history of multi-hour outages), and `MAX_ORACLE_AGE` allows staleness windows up to 7 days, and even the configured `maxOracleAge` (heartbeat-based, e.g. ~24h) is far longer than typical outage durations, so a real outage window comfortably fits inside the freshness bound. No attacker privilege is needed — any address can submit a sponsored `UserOperation` while the condition holds, making exploitation straightforward for anyone monitoring sequencer status pages/feeds.

### Recommendation
Add an L2 sequencer-uptime Chainlink feed check (per-chain configurable governance parameter, analogous to `nativeOracle`) in `_getOraclePrice`/`_tokenPrice`: fetch `latestRoundData()` from the sequencer-uptime feed, require `answer == 0` (up) and enforce a grace period after `startedAt` (recovery) before trusting price data, reverting `_fetchDetails`/pricing calls otherwise — mirroring Chainlink's documented L2 sequencer-feed example.

### Proof of Concept
1. On Arbitrum, the sequencer halts (as has occurred historically); Chainlink price feeds stop receiving new rounds but the last round's `updatedAt` remains within `maxOracleAge` (configurable up to `MAX_ORACLE_AGE = 7 days`).
2. Off-chain market prices for the native asset (ETH) or a registered fee token diverge sharply from the last on-chain round.
3. An attacker submits an ERC-4337 `UserOperation` with `paymasterData` selecting `SimplexPaymaster`; `_fetchDetails` calls `_tokenPrice` → `_getOraclePrice`, which accepts the stale round because only the timestamp bound is checked (`evm/src/utils/SimplexPaymaster.sol:662-668`).
4. `_prefund`/`_postOp` settle the sponsored gas at the stale, favorable-to-attacker rate, transferring under-priced ERC-20 from the user or over-crediting the paymaster's accounting, repeatable for every UserOperation submitted during the outage window — draining paymaster-held ERC-20/deposit value.

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
