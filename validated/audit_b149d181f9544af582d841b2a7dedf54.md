### Title
Unbounded accrued debt value overflows and permanently freezes a market - (File: common/src/rates/simulate.rs)

### Summary
A market with a sufficiently large scaled-debt balance can reach a state where `borrowed * borrow_index` no longer fits in `i128`. Because every pool mutation synchronizes interest before acting, the resulting `MathOverflow` blocks subsequent `withdraw`, `repay`, and liquidation-related pool operations, permanently freezing the market’s supplied funds absent a contract upgrade.

### Finding Description
`Controller::update_indexes` is callable by any authorized caller and forwards the selected markets to `LiquidityPool::update_indexes`. [1](#0-0) [2](#0-1) 

All regular pool mutations load the market through `synced_market`, which calls `interest::global_sync` before performing the requested operation. [3](#0-2)  `global_sync` invokes `accrue_step` for each elapsed accrual chunk. [4](#0-3) 

At the start of each step, the implementation computes the current debt value with `scaled_to_original(borrowed, borrow_index)`. [5](#0-4)  That helper is a RAY multiplication returning `Ray`, and the underlying fixed-point helper panics when the resulting `i128` value overflows. [6](#0-5) [7](#0-6) 

The borrow-index ceiling is applied to the next index value, not to the total RAY-denominated debt value. [8](#0-7)  Consequently, a large book can reach `borrowed * borrow_index > i128::MAX` while `borrow_index` remains below `MAX_BORROW_INDEX_RAY`. Once this occurs, the accrual panics before any state is committed, so the next operation starts from the same already-overflowing stored state and panics again.

This affects both withdrawals and repayments: `withdraw::accounting` and `repay::accounting` both call `ops::load_leg`, which invokes `synced_market`. [9](#0-8) [10](#0-9)  Liquidation and bad-debt paths are likewise unable to complete pool-side accounting because those operations use the same synchronized market-loading path. [11](#0-10) 

### Impact Explanation
The impact is permanent freezing of user funds at market scope. Suppliers cannot withdraw their deposits, borrowers or third parties cannot reduce the debt through `repay`, and liquidators cannot perform pool-side collateral or debt resolution once the stored scaled debt and index cross the `i128` product limit.

The locked state is self-reinforcing: the pre-operation accrual fails, no new timestamp or capped index is committed, and every retry recomputes the same overflowing product. Normal parameter updates also do not provide a non-upgrading escape because `update_params` accrues the old model before installing the new one. [12](#0-11) 

### Likelihood Explanation
Triggering the state requires a very large token-denominated debt balance and enough index growth for the RAY value to exceed `i128::MAX`. The attacker does not need a privileged role: the same unprivileged caller can create controlled accounts, supply the target asset and collateral, borrow through the normal `borrow` path, and later call `update_indexes`. Feasibility depends on an existing listed market allowing the required raw amount, collateralization, and utilization; acquiring or controlling that much supply may be economically difficult for low-cap assets, but no permissioned action is required once market parameters and token supply permit the position.

The repository’s own long-horizon scenario demonstrates the failure mode with a billion 18-decimal-token market at high utilization: the test observes `MathOverflow`, confirms that the index ceiling did not engage first, and then shows that both withdrawal and repayment fail. [13](#0-12) 

### Recommendation
Use saturating or wider arithmetic for total-debt valuation during accrual, or enforce a market-level debt-value ceiling below `i128::MAX` before the index can carry the book past that bound. At minimum, `accrue_step` should detect an overflowing `borrowed * borrow_index` product, clamp the relevant index or debt-value calculation to the protocol’s representable maximum, and commit a state that still permits repayments, withdrawals, and liquidations. Add regression coverage that verifies all rescue and exit paths remain executable at the numeric boundary.

### Proof of Concept
1. An unprivileged caller creates controlled accounts and calls `Controller::supply` for a high-decimal target asset with a raw amount large enough that `scaled_debt * index` can exceed `i128::MAX`.
2. The same caller supplies sufficient collateral and calls `Controller::borrow` on a controlled account to place the target market at sustained high utilization.
3. After interest has accrued, the caller invokes `Controller::update_indexes(caller, vec![target_hub_asset])`.
4. `global_sync` reaches `accrue_step`, where `scaled_to_original(borrowed, borrow_index)` overflows before `update_borrow_index` can cap the index. [14](#0-13) 
5. The transaction reverts without committing accrual. Subsequent calls to `withdraw` or `repay` again enter `load_leg` → `synced_market` → `global_sync` and revert with `MathOverflow` before either exit path can execute. [15](#0-14) 
6. The existing test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` reproduces this sequence and explicitly verifies the overflow followed by failed withdrawal and repayment. [16](#0-15)

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();

/// Applies `interest_factor` to `old_index` to produce the new borrow index,
/// capped at `MAX_BORROW_INDEX_RAY`.
pub fn update_borrow_index(env: &Env, old_index: Ray, interest_factor: Ray) -> Ray {
    let new_index = old_index.mul(env, interest_factor);
    if new_index.raw() > MAX_BORROW_INDEX_RAY {
        return Ray::from(MAX_BORROW_INDEX_RAY);
    }
    new_index
}

/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
