### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant spoofing of webhook events - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies webhook authenticity using `Utils::HmacValidator.validate(request)`, but the HMAC signable string is defined as only the raw request body [1](#0-0) . The `shop` (tenant identifier) is read directly from the unauthenticated `x-shopify-shop-domain` HTTP header [2](#0-1)  and is never included in the signed bytes. `Registry.process` passes this unauthenticated header value straight to the app's webhook handler as the trusted tenant identity [3](#0-2) .

### Finding Description
The binding the gem is supposed to enforce is: `shop == the tenant that produced the signed (raw_body, hmac) pair`. In reality the gem only proves `hmac == HMAC(secret, raw_body)` [4](#0-3) ; it never proves anything about the `shop-domain` header, since `to_signable_string` for a webhook `Request` returns only `@raw_body`, excluding every HTTP header [5](#0-4) .

Because the app's `client_secret` (used to compute the HMAC) is the same for every shop that installs the app, an attacker who controls any shop where the app is installed can:
1. Install the app on their own shop and receive a legitimate webhook delivery — capturing a valid `(raw_body, x-shopify-hmac-sha256)` pair.
2. Replay that exact body/HMAC to the app's webhook endpoint, but swap the `x-shopify-shop-domain` header to a victim shop's domain.
3. `HmacValidator.validate` still succeeds because it only checks the raw body against the shared secret [6](#0-5) .
4. `Registry.process` then invokes the app's handler with `shop: request.shop` set to the victim's domain and the attacker-controlled body content [7](#0-6) .

The gem's own documentation instructs consuming apps to treat `data.shop` as the trusted shop domain for the event (e.g., to key persistence or job dispatch), reinforcing that `shop` is meant to be an authenticated field: "`shop`, `String` - The shop domain of the webhook" and the example handler dispatches work keyed by `data.shop` (`perform_later(topic: data.topic, shop_domain: data.shop, ...)`) — this is the documented, intended use of the API surface, not a host-app misuse.

### Impact Explanation
This breaks the tenant-identity binding within the gem's own webhook-processing API: `Registry.process` hands the app an event that is verified to be genuinely from *some* installed shop (via a valid secret-derived HMAC over the body) but falsely attributed to an arbitrary other tenant (`shop` header is fully attacker-controlled and unauthenticated). Any app that uses `data.shop` from `WebhookMetadata` to select which tenant's records to create/update/delete (the exact pattern shown in the gem's own docs) can have data injected or state mutated under another merchant's identity — a cross-tenant integrity/isolation break directly caused by this gem's verification logic omitting the header from the signed payload.

### Likelihood Explanation
The attacker only needs the ability to install the target app on a shop they control (or observe a delivered webhook) — no `api_secret_key`, access token, or privileged access to the victim is required. Replaying an HTTP request with a modified header is trivial. The only variable is whether a given host app trusts `data.shop` for authorization decisions, which the gem's own documentation explicitly encourages.

### Recommendation
Include the shop/tenant-identifying header (and any other headers the consuming code relies on) in the HMAC-signed payload used by `Webhooks::Request#to_signable_string`, or otherwise cryptographically bind the `shop-domain` header value to the signature (e.g., concatenate it into the signable string before hashing) so a modified header invalidates the HMAC. Alternatively, document explicitly and prominently that `request.shop` is unauthenticated and must never be trusted without independent verification (e.g., cross-checking against a shop that has a registered/active session), and validate it against known/installed shops when there is one before dispatching to the handler.

### Proof of Concept
```ruby
# Attacker owns shop "attacker.myshopify.com" with the app installed and
# receives a legitimate webhook delivery for topic "orders/create":
raw_body = '{"id":1,"note":"legit order from attacker shop"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_CLIENT_SECRET, raw_body)
valid_hmac_b64 = Base64.encode64(hmac)

# Attacker replays the SAME body/hmac but swaps the shop-domain header
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac_b64,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # spoofed, unauthenticated
  "x-shopify-webhook-id" => "forged-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)

# This passes because HmacValidator only checks raw_body against the shared secret.
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(topic: "orders/create",
#      shop: "victim-shop.myshopify.com",  # attacker-controlled, falsely attributed
#      body: {...}, ...))

module ShopifyAPI

      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate(verifiable_query)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
