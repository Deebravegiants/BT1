### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) headers are trusted by `Webhooks::Registry.process` without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from unauthenticated HTTP headers and are handed to the host app's `WebhookHandler` as trusted tenant/routing identity.

### Finding Description
`Utils::HmacValidator.validate` verifies a request by computing `HMAC(secret, verifiable_query.to_signable_string)` and comparing it to the `hmac` field [1](#0-0) . For webhooks, `Webhooks::Request#to_signable_string` returns only `@raw_body` [2](#0-1) , while `shop`, `topic`, `webhook_id`, and `api_version` are parsed directly from the `shopify-*`/`x-shopify-*` headers with no cryptographic binding to the signature [3](#0-2) .

`Registry.process` validates only the HMAC over the body, then forwards `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` unchecked into `WebhookMetadata`, which is passed to the app-provided handler as the trusted context for the event [4](#0-3) [5](#0-4) .

The identity binding that should hold is: `shop header == shop cryptographically bound by the HMAC`. In this gem it does not — the equality actually enforced is only `HMAC(secret, raw_body) == received_hmac`; the `shop` (and `topic`/`webhook_id`) values are unauthenticated bytes that can be freely set by whoever sends the POST to the app's webhook endpoint, as long as the body bytes match a previously-obtained valid `(body, hmac)` pair.

### Impact Explanation
An unprivileged internet user who legitimately installs the app on a shop they control can trigger a real webhook (e.g. `orders/create`) and capture Shopify's genuine `(raw_body, hmac)` pair for their own shop. They can then replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header (e.g. a victim shop). `HmacValidator.validate` still passes because it only checks the body bytes, and `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop. Any host application that uses this gem's `shop` field to scope per-tenant data lookups/writes (as the documented usage pattern implies, since the gem hands the "trusted" shop to the handler after validating a "signed" webhook) is exposed to cross-tenant data confusion/write using data attributed to the wrong shop — a cross-tenant boundary violation stemming from this gem's own signature-scope design.

### Likelihood Explanation
Likelihood is moderate-to-high: exploitation requires no access to the app's `client_secret`, access tokens, or any privileged account — only a normal, self-service app installation (something any merchant/developer can do), and the ability to send an arbitrary HTTP POST with custom headers to the app's public webhook endpoint. The victim shop's domain is normally guessable/public (`*.myshopify.com`), and the attacker only needs *any* valid `(body, hmac)` pair, not one specific to the target.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-signable string for webhooks (or otherwise cryptographically bind them, mirroring how `Oauth::AuthQuery#to_signable_string` binds `shop`/`host`/`state` in the OAuth flow) so the gem cannot deliver an inconsistent, attacker-controlled tenant identity to the handler after reporting a "valid" HMAC. At minimum, document clearly that `Webhooks::Request#shop`/`topic`/`webhook_id` are NOT covered by HMAC verification, so host applications don't mistakenly treat them as authenticated.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and triggers a real webhook event, capturing the raw POST body and the `x-shopify-hmac-sha256` header value sent by Shopify.
2. Attacker replays that exact body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because `to_signable_string` only hashes the (unchanged) raw body [2](#0-1) [6](#0-5) .
4. The handler executes with `WebhookMetadata.shop == "victim-shop.myshopify.com"` [7](#0-6) , even though the payload actually originated from, and was signed for, the attacker's own shop.
