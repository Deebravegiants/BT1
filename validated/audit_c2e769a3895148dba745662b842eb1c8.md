### Title
Non-embedded session lookup trusts a raw, unsigned cookie value as the session identifier - ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
`ShopifyAPI::Utils::SessionUtils.current_session_id` derives the session id used to fetch a merchant's stored `Session` (and its access token) from the raw `shopify_app_session` cookie value for non-embedded apps, with no cryptographic binding verifying that the value actually originated from this gem's own OAuth flow.

### Finding Description
For embedded apps, `current_session_id` derives the session id from a verified JWT (`Auth::JwtPayload`), which is HMAC-signed by Shopify and whose `dest`/`sub` claims are cryptographically bound. [1](#0-0) 

For non-embedded apps, however, the id is taken verbatim from the `shopify_app_session` cookie via `cookie_session_id`, with no signature or MAC check at all: [2](#0-1) [3](#0-2) 

The cookie itself is a plain `SessionCookie` struct whose `value` is simply `session.id` (e.g. `"{shop}_{user_id}"` or `"offline_{shop}"`), set with no HMAC/signature over it: [4](#0-3) [5](#0-4) [6](#0-5) 

Because the session id format is deterministic and predictable (`"offline_#{shop}"` or `"#{shop}_#{user_id}"`), and the value returned by `current_session_id` is used directly by the host application to look up the stored `Session` object (containing the merchant's `access_token`), the identity binding that should exist is: **cookie value == cryptographically-verified proof of a specific `shop`/session**. Instead the binding actually enforced is only **cookie value == whatever bytes the client sent**, with no verification step in this gem.

This matches the report's underlying bug class — a value trusted and used to key/authorize an operation without validating that it is bound to the expected identity — mapped here to "a session id derived from unauthenticated bytes."

### Impact Explanation
If a host application relies on this gem's documented `current_session_id` cookie path as the sole mechanism to resolve "whose session/access token to use" (as the gem's own docs instruct for non-embedded apps), an attacker who can set/replay this cookie value (e.g., via a non-`httpOnly`/non-`secure` cookie, a subdomain cookie-tossing scenario, or simply guessing the deterministic `"offline_#{shop}"` pattern for a known store) can cause the application to fetch and use another merchant's stored `Session`/access token — a cross-tenant access condition. However, this only reaches "Critical - cross-tenant access" if the host's session store is keyed purely by this untrusted id with no additional authentication; the gem itself never signs or validates the cookie, so the guarantee it provides to callers is weaker than what the equivalent embedded/JWT path provides.

### Likelihood Explanation
Exploitability depends entirely on host-application behavior (whether the cookie is `httpOnly`/`secure`, whether the session store does any additional check, whether cookie value can be tossed/guessed). The gem's own code contributes no independent verification here, unlike the JWT/HMAC-protected embedded and OAuth-callback paths in the same file/class. This is a design weakness in the trust boundary of `SessionUtils`, not a directly, unconditionally exploitable bug purely within this gem.

### Recommendation
Do not treat the raw cookie value as a trustworthy, unauthenticated identity binding. Either sign/MAC the `SessionCookie` value (e.g., HMAC it with `Context.api_secret_key`, similar to `Utils::HmacValidator`) and verify that signature in `cookie_session_id`/`current_session_id` before returning it, or document explicitly and loudly that callers must independently authenticate the cookie's origin/session before trusting the returned id for token lookup.

### Proof of Concept
Conceptual PoC (illustrates the identity binding gap; exploitability requires a host app that keys its session store solely off this id):
1. Attacker learns/guesses a target shop's offline session id format: `"offline_target-shop.myshopify.com"` (deterministic per `Session.from`, `lib/shopify_api/auth/session.rb:116`).
2. Attacker sets a cookie named `shopify_app_session` with that value on a non-embedded app that uses `SessionUtils.current_session_id(nil, cookies, false)`.
3. `current_session_id` returns the attacker-supplied string unchanged (`lib/shopify_api/utils/session_utils.rb:29-36,68-71`) with no signature check.
4. If the host app looks up its `SessionStorage` by this returned id and passes the resulting `Session` (containing `target-shop`'s access token) into a `Clients::HttpClient`, the attacker's request is now authenticated as `target-shop` — a cross-tenant access breach originating from the missing binding in this gem's `SessionUtils`.

        def session_id_from_shopify_id_token(id_token:, online:)
          raise Errors::MissingJwtTokenError, "Missing Shopify ID Token" if id_token.nil? || id_token.empty?

          payload = Auth::JwtPayload.new(id_token)
          shop = payload.shop

          if online
            jwt_session_id(shop, T.must(payload.sub))
          else
            offline_session_id(shop)
          end
        end
