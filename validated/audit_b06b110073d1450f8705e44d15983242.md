### Title
`LockupContract::new` lacks a re-initialization guard (`assert!(!env::state_exists())`), allowing an unprivileged account to re-run initialization and seize owner control - (File: lockup/src/lib.rs)

### Summary
The external report describes a missing `onlyConstruction`-style guard on a Solidity `initialize` function, allowing it to theoretically be called more than once. The NEAR analog of this guard is the `assert!(!env::state_exists(), ...)` check that every other `#[init]` constructor in this repository uses. `LockupContract::new` in `lockup/src/lib.rs` is the only in-scope `#[init]` constructor that omits this check.

### Finding Description
Every other production `#[init]` constructor in scope explicitly guards against re-initialization:
- `multisig/src/lib.rs` `new`: `assert!(!env::state_exists(), "Already initialized");` [1](#0-0) 
- `staking-pool/src/lib.rs` `new`: `assert!(!env::state_exists(), "Already initialized");` [2](#0-1) 
- `staking-pool-factory/src/lib.rs` `new`: `assert!(!env::state_exists(), "The contract is already initialized");` [3](#0-2) 
- `whitelist/src/lib.rs` `new`: `assert!(!env::state_exists(), "Already initialized");` [4](#0-3) 
- `lockup-factory/src/lib.rs` `new`: `assert!(!env::state_exists(), "The contract is already initialized");` [5](#0-4) 

In contrast, `LockupContract::new` in `lockup/src/lib.rs` performs argument validation but never checks `env::state_exists()` before constructing and returning a fresh `Self`: [6](#0-5) 

Because near-sdk's `#[init]` macro (in the version used here) does not itself enforce a state-exists check — that is precisely why every sibling contract adds the assertion manually — `new` on the `LockupContract` remains callable as an ordinary public method after deployment. An unprivileged account can call `new` again with attacker-chosen parameters (e.g., their own `owner_account_id`, no vesting schedule, and manipulated `transfers_information`), which overwrites `owner_account_id`, `lockup_information`, `vesting_information`, `staking_information`, `staking_pool_whitelist_account_id`, and `foundation_account_id`.

### Impact Explanation
`owner_account_id` gates all fund-moving owner methods in `lockup/src/owner.rs` (transfer, staking, key management, etc.), confirmed by the numerous owner-authorization checks in that file. [7](#0-6)  Re-running `new` lets an attacker set themselves as `owner_account_id`, clear any vesting/foundation-termination protections (by omitting `vesting_schedule`/`foundation_account_id`), and set `lockup_information.lockup_amount` from the current account balance while disabling the lockup timestamp/duration. They could then call owner-only methods to transfer out the entire locked NEAR balance. This matches the "Critical" impact category: unauthorized transfer/withdrawal of locked funds reachable by an unprivileged user through a public-call/state-transition failure, and also the "Permanent freezing/irrevocable loss" category for the legitimate owner, since the vesting/foundation-termination protection can be stripped.

### Likelihood Explanation
Likelihood is high: `new` is a normal, non-private public contract method with no owner or predecessor restriction, callable by any account at any time after the initial deployment call completes — no privileged role, key, or trusted party is required. The only precondition is that the attacker knows/guesses valid parameter values, which are trivial (account IDs and simple structs), and the call is a single standard NEAR function call.

### Recommendation
Add `assert!(!env::state_exists(), "The contract is already initialized");` as the first statement of `LockupContract::new` in `lockup/src/lib.rs`, matching the pattern used in every sibling contract (`multisig`, `staking-pool`, `staking-pool-factory`, `whitelist`, `lockup-factory`). Additionally, add unit tests that assert calling `new` a second time on an already-initialized `LockupContract` panics.

### Proof of Concept
1. Deploy `lockup` contract normally via the standard batched `create_account + transfer + deploy_contract + function_call("new", ...)` flow, setting a legitimate `owner_account_id` and a vesting schedule/`foundation_account_id`.
2. From any unprivileged account, call:
```
lockup_contract.new(
    attacker_account_id,          // owner_account_id
    0,                             // lockup_duration
    None,                          // lockup_timestamp
    TransfersInformation::TransfersEnabled { transfers_timestamp: <now> },
    None,                          // vesting_schedule -> wipes vesting/termination protection
    None,                          // release_duration
    <valid whitelist account>,
    None                           // foundation_account_id
)
```
Since there is no `assert!(!env::state_exists())`, this call succeeds and overwrites contract state, since `lockup/src/lib.rs` lines 180-243 contain no such guard. [8](#0-7) 
3. The attacker, now `owner_account_id`, calls owner-only withdrawal/transfer methods in `lockup/src/owner.rs` to move the contract's NEAR balance to their own account.

        foundation_account_id: Option<AccountId>,

        assert!(

            "The staking pool whitelist account ID is invalid"
        );
        if let TransfersInformation::TransfersDisabled {
            transfer_poll_account_id,
        } = &transfers_information

            assert!(
                env::is_valid_account_id(transfer_poll_account_id.as_bytes()),
                "The transfer poll account ID is invalid"
            );
        }
        let lockup_information = LockupInformation {
            lockup_amount: env::account_balance(),
            termination_withdrawn_tokens: 0,
            lockup_duration: lockup_duration.0,
            release_duration: release_duration.map(|d| d.0),
            lockup_timestamp: lockup_timestamp.map(|d| d.0),
            transfers_information,
        };
        let vesting_information = match vesting_schedule {

                assert!(
                    foundation_account_id.is_none(),

            }
        };
        assert!(

                env::is_valid_account_id(foundation_account_id.as_ref().unwrap().as_bytes()),
            "Foundation account should be added for vesting schedule"
        );

        Self {
            owner_account_id,
            lockup_information,
            vesting_information,
            staking_information: None,
            staking_pool_whitelist_account_id,
            foundation_account_id,
        }
    }
