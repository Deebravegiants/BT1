### Title
Missing L2 sequencer-uptime check in SimplexPaymaster's Chainlink price consumption allows mispriced gas payments during sequencer downtime/recovery - (File: evm/src/utils/SimplexPaymaster.sol)

### Summary
`SimplexPaymaster` is deployed on multiple L2/L2-like chains (Arbitrum, Base, Polygon, BSC) to let any solver/user pay UserOperation gas in a stablecoin, converting cost via two Chainlink `AggregatorV3Interface` feeds (native/USD and token/USD). The oracle-reading helper `_getOraclePrice` only checks that the Chainlink answer is positive and that `block.timestamp - updatedAt <= maxOracleAge`; it never verifies that the L2 sequencer is (or recently was) up, matching the exact bug class described in the external report for `PriceFeed.sol`/`StorkOracleWrapper`. [1](#0-0) 

### Finding Description
`_getOraclePrice` is the sole gate on Chainlink data used throughout the contract's pricing logic (`_tokenPrice`, `swapAndDeposit`, `getTokenPrice`, `estimateTokenCost`): [2](#0-1) 

This function performs only a staleness/positivity check, never consulting an L2 sequencer-uptime oracle (e.g. Chainlink's `SequencerUptimeFeed`), even though the contract's own documentation states it is deployed on Arbitrum, Base, Polygon and BSC: [3](#0-2) 

On an L2 whose sequencer goes down and later recovers, Chainlink price feeds that rely on the sequencer to relay updates can present an answer whose `updatedAt` is still within `maxOracleAge` (i.e., "fresh" by the staleness check) yet reflects market conditions from before/around the outage rather than the true current price, exactly as described in Chainlink's L2 oracle-guidance. Because `_fetchDetails` (reachable by any unprivileged user submitting a UserOp through the ERC-4337 EntryPoint) calls `_tokenPrice` → `_getOraclePrice` with no additional check, the paymaster will convert native gas cost to token cost using this potentially stale/misleading price: [4](#0-3) 

The same unguarded `_getOraclePrice` call also determines the `amountOutMin` used in `swapAndDeposit`'s Uniswap swap, meaning a stale relative price during/after sequencer downtime can also produce an incorrect minimum-output bound for fee recycling: [5](#0-4) 

### Impact Explanation
Any unprivileged "bandwidth purchaser" (a solver or user submitting a paymaster-sponsored UserOp) can time a UserOp submission around an L2 sequencer outage/recovery window to have their gas priced against a token/USD or native/USD ratio that does not reflect the real market, since `maxOracleAge`-based staleness checks do not account for sequencer downtime. This can let a user underpay in stablecoins relative to the true gas cost, draining the paymaster's treasury/EntryPoint deposit over repeated operations — a permissionless, reachable path to fund loss for the protocol, matching the "concrete theft ... of funds" bar.

### Likelihood Explanation
L2 sequencer outages, while infrequent, are a known and recurring operational event on rollups (Arbitrum, Base). Any user who observes or anticipates such an event can submit a sponsored UserOp during the affected window without any special privilege, since `_fetchDetails`/`_getOraclePrice` are reached purely through normal EntryPoint UserOp flow. No governance or relayer permission is required to trigger the mispricing.

### Recommendation
Integrate a Chainlink L2 sequencer-uptime feed check (as documented at https://docs.chain.link/data-feeds/l2-sequencer-feeds#example-code) into `_getOraclePrice`, reverting or applying a grace period when the sequencer is down or was recently restored, mirroring the existing `StaleOraclePrice`/`InvalidOraclePrice` revert pattern.

### Proof of Concept
1. Deploy/observe `SimplexPaymaster` on an L2 (e.g., Base/Arbitrum) where the native/USD or token/USD Chainlink feed's `updatedAt` remains within `maxOracleAge` during a sequencer outage (feed simply stops advancing while the sequencer is down, then resumes).
2. During the outage or immediately after sequencer restoration (before the feed has caught up to the true post-outage price), any solver submits a UserOp with `paymasterData` referencing a registered stablecoin, invoking `_fetchDetails` → `_tokenPrice` → `_getOraclePrice` at [6](#0-5) .
3. Because both checks (`answer > 0`, `block.timestamp - updatedAt <= maxOracleAge`) pass, the paymaster computes `tokenPrice` from the outdated relative price and charges the solver accordingly, allowing systematic underpayment relative to actual gas cost, draining the paymaster's stablecoin/EntryPoint reserves over repeated ops.

    function _tokenPrice(TokenConfig memory cfg) internal view returns (uint256) {
        uint256 nativeUsd = _getOraclePrice(nativeOracle, nativeOracleDecimals);
        uint256 tokenUsd = _getOraclePrice(cfg.tokenOracle, cfg.tokenOracleDecimals);

        return (nativeUsd * (10 ** cfg.tokenDecimals) * (10_000 + markupBps)) / (tokenUsd * 10_000);
    }

    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
