### Title
Fee-on-transfer tokens cause escrow accounting to overstate holdings, permanently freezing/insolvent funds in Tron IntentGatewayV2 - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` does not include the fee-on-transfer (FOT) protection that the canonical EVM `IntentGatewayV2.sol` has. It escrows the *requested* input amount into `_orders[commitment][token]` instead of measuring the *actual* balance received by the contract, causing the internal accounting ledger to diverge from real token balances whenever a fee-on-transfer / deflationary ERC20 is used as an order input.

### Finding Description
In the canonical EVM contract, `placeOrder` snapshots `balanceOf` before and after `safeTransferFrom` and mutates `order.inputs[i].amount` to the actual amount received before it is used for the commitment/escrow bookkeeping: [1](#0-0) 

The Tron fork (`evm/tron/contracts/apps/IntentGatewayV2.sol`), however, computes `reducedInputs` (order amount minus protocol fee) *before* any transfer occurs, and in the non-predispatch branch simply calls `safeTransferFrom` and unconditionally credits the escrow ledger with the pre-transfer `reducedInputs[i].amount`, with no balance check at all: [2](#0-1) 

If `token` is a fee-on-transfer/deflationary ERC20, the contract's actual balance increase from `safeTransferFrom` will be less than `order.inputs[i].amount`, yet `_orders[commitment][token]` is credited with the full (protocol-fee-reduced but not transfer-fee-reduced) amount. This is the same root cause identified in the referenced report: bookkeeping assumes `received == requested` for a transfer-fee token.

Later, `withdraw()` (invoked from `onAccept`/`onGetResponse` for `RedeemEscrow`/`RefundEscrow`, or directly from `cancelOrder` for same-chain cancellations) transfers out exactly `body.tokens[i].amount` (the ledger-recorded, inflated amount) for that token, decrementing `_orders[body.commitment][token]` by that same inflated amount: [3](#0-2) 

Because `_orders[commitment][token]` is a per-token accumulator shared across all orders in that token (see `_orders[commitment][token] += reducedInputs[i].amount;`), an inflated credit for one FOT-input order means the contract's actual token balance for that asset is insufficient to satisfy the sum of all outstanding escrow claims recorded in `_orders`. Whichever withdrawal (fill redemption or cancellation refund) is processed later will either revert due to insufficient balance (permanently freezing funds/blocking withdrawal), or, if enough of a buffer exists from other unrelated deposits of the same token, silently drain balance belonging to other users' escrowed orders of that same token — an insolvency/fund-theft condition.

The predispatch branch (lines 416-446) at least measures `balance` on the dispatcher and reverts if `balance < requiredAmount`, so a single-input FOT token there is more likely to simply revert (a smaller availability issue) rather than corrupt accounting, but it still uses `reducedInputs[i].amount` (computed from the pre-transfer nominal amount, not measured actual receipt) as the escrow credit — the same class of assumption bug, just gated by an earlier revert-if-insufficient check rather than corrected via measurement.

### Impact Explanation
This is a Medium-to-High severity accounting bug: it can (a) revert `withdraw()` for any order using a fee-on-transfer token as an escrowed input asset — permanently locking user/solver funds since neither redemption nor refund can complete, and (b) if the same fee-on-transfer token is used across multiple concurrent orders/escrows, allow one inflated escrow claim to be satisfied by draining tokens belonging to other legitimately-escrowed orders, causing insolvency for those other order participants. This matches the "permanent freezing of funds" and "unsound state commitment"/accounting classes called out as in-scope impacts.

### Likelihood Explanation
Reachable by any unprivileged user calling `placeOrder` on the Tron `IntentGatewayV2` with a fee-on-transfer ERC20 as an input token — a single ordinary transaction with no special privileges. Hyperbridge/BendDAO-style intent gateways commonly accept arbitrary ERC20s as order inputs, and the Tron deployment explicitly still supports arbitrary token inputs (`address(uint160(uint256(order.inputs[i].token)))`), so the precondition (an FOT token being listed/used as input) is realistic wherever such tokens aren't explicitly disallowed. The bug is also directly analogous to a bug the team already fixed in the canonical EVM contract (confirmed by the `testPlaceOrder_FeeOnTransferToken_*` test suite in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`), indicating the Tron fork was not patched with the same fix, which strongly supports the finding's validity.

### Recommendation
Apply the same fix used in the canonical `evm/src/apps/IntentGatewayV2.sol`: snapshot `IERC20(token).balanceOf(address(this))` before and after each `safeTransferFrom` call in the non-predispatch branch of `placeOrder`, and credit `_orders[commitment][token]` (and compute `reducedInputs`/the commitment hash) using the actual measured received amount rather than the nominal `order.inputs[i].amount`. Apply the analogous fix to the predispatch branch so the escrow credit also reflects the balance actually swept back into the contract, not just the fee-adjusted nominal amount.

### Proof of Concept
1. Deploy a 1% fee-on-transfer ERC20 token `FOT` (as in `FeeOnTransferToken` test helper at `evm/tests/foundry/IntentGatewayV2SameChainTest.sol:2690-2735`).
2. On the Tron `IntentGatewayV2`, call `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000e18}` and no predispatch.
3. `safeTransferFrom(user, address(this), 1000e18)` executes; contract's actual `FOT` balance only increases by 990e18 (1% fee burned/collected).
4. `_orders[commitment][FOT] += reducedInputs[0].amount` credits (at minimum) `1000e18` minus any protocol fee — i.e., a value greater than the 990e18 actually held.
5. When the order is filled/redeemed (or cancelled) and `withdraw()` attempts to transfer `body.tokens[0].amount` (derived from this inflated `_orders` entry) to the beneficiary, the transfer either reverts (insufficient contract balance, freezing funds) or succeeds by consuming FOT tokens belonging to other unrelated escrowed orders (insolvency), depending on total contract `FOT` balance from other deposits.
