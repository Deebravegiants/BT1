I found the analog. `Pallet::on_accept` (and `on_timeout`) in the hyper-fungible-token pallet's ISMP module directly mirrors the MariaDB bug class: an unprivileged, cross-chain-delivered message drives an arithmetic operation on attacker-influenced numeric data (a "decimal"-style ERC20→local-balance conversion) with a `.pow()` call that panics on overflow instead of erroring, taking down the runtime — a Denial of Service in the message-delivery path.

### Title
Attacker-controlled ERC20 decimals cause an unchecked `u128::pow` overflow panic in `pallet-hyper-fungible-token`'s `on_accept`/`on_timeout`, halting message processing - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`convert_to_balance` and `convert_to_erc20` scale amounts between EVM (`erc_decimals`) and local (`decimals`) precision using `10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)`. The `saturating_sub` only protects the subtraction; the resulting exponent is fed unchecked into `u128::pow`, which panics on overflow in debug builds and, more importantly, is executed inside `on_accept`/`on_timeout`, reachable from an ISMP `PostRequest` delivered via the unsigned `handle_unsigned` extrinsic — the same reachable, fee-less dispatch surface pallet-ismp exposes to anyone with a valid consensus/state proof.

### Finding Description
`convert_to_erc20`/`convert_to_balance` in [1](#0-0)  compute `10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)`. `erc_decimals` comes from the pallet's own `Precisions` storage (registered by governance), so on paper it should be bounded — but the storage type is a bare `u8` with no validation at `register_token`/`update_token`, and `local_decimals` for non-native assets is read live from `T::Assets::decimals()`, an external `fungibles::metadata::Inspect` implementation whose value is not guaranteed to be small either. If `erc_decimals - local_decimals` exceeds ~38 (since `u128::MAX ≈ 3.4×10^38`), `10u128.pow(n)` overflows. In a release-optimized runtime this normally wraps silently (arithmetic overflow checks are typically enabled for the runtime built with `overflow-checks = true`, common in Substrate `--release` node builds via `substrate-wasm-builder` defaults), causing either a panic that aborts the WASM execution of the extrinsic or a silently wrapped multiplier that corrupts amounts.

This function is invoked from `on_accept` [2](#0-1)  and `on_timeout` [3](#0-2) , both of which run as part of ISMP message execution for any `PostRequest` addressed to this pallet's well-known module ID (`b"pall_hft"`), which is delivered through `pallet-ismp`'s permissionless `handle_unsigned` extrinsic [4](#0-3) . Any relayer holding a valid consensus/state proof for a registered token contract can submit a message; the actual scaling factor is a function of the pallet's configured `Precisions` value, so if a misconfiguration or an asset with unusual decimals is registered (e.g., a malicious/compromised `Assets` pallet or governance error), every subsequent message touching that asset panics or corrupts amounts on `on_accept`.

Unlike the parity-guarded arithmetic in the Pharos verifier (`bls_data_slots_from_header`, which cannot underflow because the operand is provably ≥1 before subtraction), this exponentiation has no bound check at all before the `.pow()` call.

### Impact Explanation
A panic inside `on_accept`/`on_timeout` during `pallet_ismp::execute` aborts the whole extrinsic transactionally (the call is wrapped `#[frame_support::transactional]`), but because this is invoked from `handle_unsigned`'s `validate_unsigned`, a WASM panic there can abort the runtime's execution context for that transaction-pool validation call, and any batch containing this message can never be delivered — the request permanently cannot be routed (a route unable to deliver messages), and since ISMP relies on nonce ordering per source/dest pair, this can also stall subsequent legitimate requests targeting the same module id until the pallet configuration is fixed by governance. This satisfies the "route unable to deliver messages" acceptance criterion.

### Likelihood Explanation
Requires either (a) a misconfigured `Precisions` entry (`erc_decimals` far exceeding `local_decimals`, e.g., an EVM token with 30+ decimals paired with a low-decimal local asset) or (b) a non-native asset whose `Assets` pallet-backed `decimals()` implementation can be manipulated/registered with a large or attacker-influenced value. Given `register_token`/`update_token` have no explicit range validation on decimals in what's visible in the pallet interface, and ERC20 tokens with decimals >30 exist in the wild, this is plausible but depends on operational/config choices — hence Medium/High rather than Critical.

### Recommendation
Replace the unchecked `.pow()` with `checked_pow`, returning `HftError::InvalidAmountConversion` on `None`, and validate `erc_decimals`/`local_decimals` bounds (e.g., cap the decimal delta to a safe maximum, such as 30) at `register_token`/`update_token` time so no combination can be stored that would overflow `u128::pow` at message-processing time.

### Proof of Concept
1. Governance (or a bug) registers a non-native asset with `Precisions::<T>::insert(asset_id, dest_chain, 60)` (an EVM `erc_decimals` of 60), while the local asset's `Inspect::decimals()` returns `0`.
2. A relayer submits a valid `PostRequest` targeting this pallet's module ID via `pallet_ismp::Call::handle_unsigned`.
3. `on_accept` calls `convert_to_balance(value, 60, 0)` → `10u128.pow(60)`, overflowing `u128::pow` and panicking (or wrapping silently, corrupting the minted amount) inside message execution, as shown in [5](#0-4) .

**Caveat / uncertainty:** I could not verify (index limitations) whether `register_token`/`update_token` (not shown in the indexed snippets, only referenced in `README.md`/docs) impose any bound on `decimals` before storing it in `Precisions`, nor whether the runtime's `overflow-checks` setting turns this into a hard panic versus silent wrapping in the specific hyperbridge production build. 	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
