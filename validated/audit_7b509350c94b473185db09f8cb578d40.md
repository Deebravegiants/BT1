### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop` value that is handed to the app's webhook handler as the tenant identifier is read from an unsigned HTTP header and is never covered by that HMAC.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no further validation [2](#0-1) . `Registry.process` validates the request purely with `Utils::HmacValidator.validate(request)` (which only checks the body-derived signature) and then immediately forwards `request.shop` into `WebhookMetadata` for the handler, with no check that the signed body actually corresponds to that shop [3](#0-2) .

This breaks the intended identity binding: `hmac(raw_body, client_secret)` should authenticate the tuple `(shop, raw_body)`, but the implementation only authenticates `raw_body`. The `client_secret` used to compute the HMAC is the app's single secret, shared across *every* shop that installs the app — it is not shop-specific. Any merchant who legitimately installs the app can therefore obtain genuinely-signed webhook deliveries (Shopify signs them with the app's shared secret) whose body content they control (e.g. by editing a product on their own store to trigger a `products/update` webhook with attacker-chosen fields). Because the `shop-domain` header is never part of the signed material, that attacker can replay the exact same body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a different, victim shop. The signature check still passes because it only verifies the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload came from the victim's shop [4](#0-3) .

Any host application that uses `request.shop` (as attributed by this gem) to select the per-tenant `Session`/access token, write to per-shop storage, or otherwise scope data by shop — which is the documented and expected usage pattern of `WebhookMetadata` — will apply the attacker's payload to the victim tenant's context.

### Impact Explanation
This is a cross-tenant confusion vulnerability: an unprivileged app-installer (any merchant who installs the app, which requires no special privilege) can cause data to be attributed to and processed under a different merchant's shop identity inside the host application, without ever needing the victim's or the app's credentials. This matches the "Critical – cross-tenant access" category, since the shop-binding equality `hmac_authenticated_shop == request.shop_used_for_tenant_routing` does not hold.

### Likelihood Explanation
Any developer/merchant with a free Shopify dev store can install the target app to become a legitimate webhook source, generate a signed webhook, capture it, and replay it with a modified `shop-domain` header — no source code access, secrets, or elevated privileges are required. The only precondition is that the host application actually relies on `request.shop` for tenant attribution, which is the only shop-identification API this gem exposes for webhooks, so it is the expected usage.

### Recommendation
Include the shop domain (and any other value used for tenant routing, e.g. topic/webhook id) in the signable material verified against the HMAC, or independently verify that the shop-domain header corresponds to a shop with an existing, previously-established session/registration before trusting it in `WebhookMetadata`. At minimum, document that `request.shop` is unauthenticated and must not be used as a sole tenant key without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a normal, unprivileged installation).
2. Attacker triggers an action (e.g., updates a product) causing Shopify to send a legitimately-HMAC-signed webhook to the app's endpoint, with headers such as:
   ```
   x-shopify-topic: products/update
   x-shopify-hmac-sha256: <valid-signature-over-body>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   ```
3. Attacker captures the raw body and the valid `x-shopify-hmac-sha256` value.
4. Attacker replays the identical raw body and HMAC to the app's webhook endpoint, but sets:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
5. `Webhooks::Request#hmac` still decodes/validates the same HMAC (`hmac_validator.rb` line 30 `secure_compare`), because `to_signable_string` only reflects the raw body, unaffected by the header swap [5](#0-4) .
6. `Registry.process` passes validation and invokes the handler with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop` is now `"victim-shop.myshopify.com"` [4](#0-3) , causing the host app to process attacker-controlled data as if it originated from the victim shop.
