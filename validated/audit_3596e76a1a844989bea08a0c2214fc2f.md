### Title
Bad-debt wipeout clamps `supply_index` up to `SUPPLY_INDEX_FLOOR_RAW`, resurrecting wiped suppliers' shares as phantom claims that drain later deposits - (File: contracts/pool/src/interest.rs)

### Summary
`apply_bad_debt_to_supply_index` socializes bad debt by scaling `supply_index` toward zero, but when the loss meets or exceeds total supplied value it clamps the index **up** to `SUPPLY_INDEX_FLOOR_RAW` (`RAY/1000`) instead of zeroing supplier claims. Every share that should have been destroyed keeps a residual claim. Since withdrawals are gated only by a cash check (`require_reserves`) and never by `require_backed_market`, a wiped-out supplier can withdraw the phantom claim and consume the next depositor's real tokens.

### Finding Description
In `contracts/pool/src/interest.rs:73-89`, `apply_bad_debt_to_supply_index` computes `remaining = total_supplied_value - capped` and a `reduction_factor`. When `bad_debt >= total_supplied_value`, `remaining = 0`, so `reduction_factor = 0` and `new_supply_index = 0` — but the result is `max`ed with `SUPPLY_INDEX_FLOOR_RAW`, leaving the index at `RAY/1000`. All existing scaled supply shares then unscale to `shares × RAY/1000`, a positive phantom claim backed by nothing.

The path is reachable by an unprivileged caller: `controller.liquidate` / `clean_bad_debt` emit `PoolSeizeEntry { side: Borrow }`, which `seize::apply` (`contracts/pool/src/ops/seize.rs:24-28`) routes into `apply_bad_debt_to_supply_index` and `burn_debt`. On a market whose outstanding bad debt meets/exceeds total supply value (e.g., a collateral crash on a small spoke book), this produces a full-wipeout state where survivors' shares are unbacked.

On withdrawal, `withdraw::gate_and_debit` (`contracts/pool/src/ops/withdraw.rs:111-119`) enforces `cache.require_reserves(net_transfer)`, `require_utilization_below_max`, and `require_supply_for_debt` — but **not** `require_backed_market`. So once any fresh supplier deposits (adding cash), the wiped-out holder's `resolve_withdrawal` returns a positive `gross` and the transfer succeeds, paying phantom value out of real cash.

The in-repo tests prove both halves:
- `test_raw_cache_floor_clamp_strands_claim_without_supply_guard` and `test_raw_cache_seizure_residual_would_drain_fresh_cash_without_supply_guard` (`contracts/pool/tests/interest.rs:373-495`): after the clamp, `unscale_supply_floor(old_scaled) > 0`, and withdrawal pays `gross == fresh deposit`, leaving `cash < bob_claim` — an honest supplier loses funds.
- `test_apply_bad_debt_exactly_at_total_supplied_hits_cap_and_floor` confirms the index lands on `SUPPLY_INDEX_FLOOR_RAW` rather than zero.

### Impact Explanation
Theft of user funds / protocol insolvency. After a bad-debt wipeout, holders of previously destroyed supply shares can withdraw `shares × RAY/1000` against any subsequently deposited cash. The pool becomes structurally insolvent: booked claims exceed `cash + debt`, and each phantom withdrawal is a direct transfer of a fresh depositor's principal to a wiped-out account that should hold zero value. Severity: High-to-Critical — loss scales with future deposits into the poisoned market.

### Likelihood Explanation
Triggering requires a bad-debt event whose ceiled debt value meets or exceeds total supplied value — i.e., a wipeout. That happens when a borrower's collateral collapses below debt (oracle-observed price crash, or a thin/young market where one undercollateralized remnant dominates the book) and a keeper or any user calls `clean_bad_debt`/`liquidate`, both unprivileged entrypoints. No privileged action is needed, and afterward only one fresh deposit is required to make the phantom claim payable. The residual is also permanent: nothing rewrites the already-stranded shares.

### Recommendation
Do not clamp the wiped index upward in isolation. When `capped == total_supplied_value` (full wipeout), either:
- Set `supply_index = SUPPLY_INDEX_FLOOR_RAW` **and** treat the market's remaining supply shares as worthless (e.g., record a wipeout flag / zero `supplied` and `revenue`, or gate withdrawals with `guards::require_backed_market`), or
- Reject the wipeout clamp and socialize proportionally so claims and backing stay consistent.

At minimum, add `guards::require_backed_market(env, cache)` to `withdraw::gate_and_debit` (and the seize/settlement legs) so an insolvent market cannot pay phantom claims against fresh cash.

### Proof of Concept
1. Market M has supplier A holding `scaled_A = 1_000_000 * RAY` and borrower debt that, after a collateral price crash, seizes as `bad_debt >= supplied * supply_index` (e.g., `2_000_000 * RAY` against `1_000_000 * RAY` of supply value).
2. Anyone calls `controller.clean_bad_debt` (or `liquidate` with the bad-debt leg) → `seize::apply` → `apply_bad_debt_to_supply_index` → `supply_index` clamps to `SUPPLY_INDEX_FLOOR_RAW` (`interest.rs:88`), `borrowed` burns to zero.
3. `unscale_supply_floor(scaled_A)` is now `scaled_A × RAY/1000 > 0` — a phantom claim. Cash is 0.
4. Victim B deposits `c` tokens (`supply` → `mint_supply` + `credit_cash`).
5. A calls `controller.withdraw(0)` (withdraw-all sentinel). `resolve_withdrawal` returns `gross = c`; `gate_and_debit` only requires `cash >= c`, which holds. A receives B's deposit; B's claim `unscale_supply_floor(scaled_B) = c` exceeds remaining `cash = 0`. B's funds are permanently lost.

Reproduced exactly by `test_raw_cache_floor_residual_can_consume_fresh_cash_without_supply_guard` (`contracts/pool/tests/interest.rs:317-369`) and `test_raw_cache_seizure_residual_would_drain_fresh_cash_without_supply_guard` (`:431-495`), which model the real mutating path (`global_sync`/`accrue_step`/`resolve_withdrawal`/`require_reserves`) used on-chain.

Caveat: whether `require_backed_market` is additionally enforced upstream of withdraw in the controller path was not fully verified within available iterations; the pool-level withdraw leg demonstrably omits it, and the shipped tests explicitly document the drain scenario as a known unguarded behavior.
