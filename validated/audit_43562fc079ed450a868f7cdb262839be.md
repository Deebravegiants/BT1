## Finding: Silent zero-share minting in `delegation_pool::add_stake` allows delegator stake to be absorbed by the pool without any share issuance

### Title
Delegator deposits are staked to the pool before share-rounding is checked, causing silent loss of principal - (`aptos-move/framework/aptos-framework/sources/delegation_pool.move`)

### Summary
This is the direct Aptos-native analog of the Sherlock H-3 pattern: assets are custodied by a pool before the corresponding "receipt" (strategy token / share) is minted, and the minting step can silently round down to zero without reverting.

### Finding Description
`add_stake` transfers the delegator's coins to the pool's stake account and calls `stake::add_stake` **before** shares are computed: [1](#0-0) 

The share-minting helper `buy_in_active_shares` silently returns `0` — without aborting — when the rounding of `amount_to_shares` yields zero: [2](#0-1) 

`amount_to_shares_with_total_coins` in `pool_u64.move` performs `coins_amount * total_shares / total_coins` when the pool is non-empty, which — exactly like the Solidity `_convertBPTClaimToStrategyTokens` numerator/denominator mismatch in the Sherlock report — rounds to zero whenever `coins_amount * total_shares < total_coins`: [3](#0-2) 

This condition is reachable in a live delegation pool because `total_coins` grows relative to `total_shares` over time as staking rewards accrue directly into `total_coins` without a matching share increase (share price > 1 coin/share). Once the share price is high enough, a delegator adding a modest `amount` can receive `new_shares == 0`, yet their coins have already been irreversibly staked into the pool via `stake::add_stake(amount)` at line 1501 above.

The only post-check is `assert_min_active_balance(pool, delegator_address)`, which validates the delegator's **total** active balance, not the marginal shares just purchased. A delegator who already holds an active balance above the minimum threshold will pass this check even though the new deposit purchased zero shares, meaning the added stake is retained by the pool and effectively distributed to all other active shareholders (a direct value transfer away from the depositor), while `add_stake` still emits a normal `AddStake` event implying success.

### Impact Explanation
This is a custody-accounting corruption: the depositor's APT is transferred into the pool's stake account and increases the pool's active coin balance, but the depositor's shares (`pool.active_shares`) are not increased, so their claim on withdrawal is unchanged. The excess value is not burned; it is permanently redistributed to the other shareholders of the pool, i.e. the depositor suffers a real, unrecoverable loss of principal to third parties, matching the "loss of assets" impact class from the seed report and the custody-corruption criterion ("moves value to the wrong holder").

### Likelihood Explanation
Likelihood is bounded by needing a pool where the coin/share ratio has already drifted upward enough (via commission/reward accrual mechanics on `pool.active_shares.total_coins()`) that a plausible small-to-moderate `amount - add_stake_fee` rounds to zero shares, combined with the depositor already holding balance above `MIN_COINS_ON_SHARES_POOL` so `assert_min_active_balance` does not catch it. This is data-dependent (pool age/ratio) rather than trivially triggerable on every pool, so likelihood is moderate rather than guaranteed-on-first-use as in the Sherlock PoC.

### Recommendation
`buy_in_active_shares` (and its `pending_inactive`/`inactive` counterparts) should abort instead of silently returning `0` whenever the caller-provided `coins_amount` is non-zero but resolves to zero shares, e.g. immediately after `stake::add_stake` in `add_stake`:
```move
let new_shares = buy_in_active_shares(pool, delegator_address, amount - add_stake_fee);
assert!(new_shares > 0, error::invalid_argument(EZERO_SHARES_MINTED));
```
This must happen before the transferred coins are considered "settled" so the transaction reverts atomically, consistent with the fix pattern from the seed report (`require(strategyTokensMinted != 0, ...)`).

### Proof of Concept
Conceptually (values illustrative, exact thresholds depend on live `total_coins`/`total_shares` ratio which requires runtime state and was not independently re-derived from a live pool state in this review):
1. Pool has accrued rewards such that `pool.active_shares.total_coins() = 10_000_000` and `total_shares = 5_000_000` (share price = 2 coins/share).
2. An already-active delegator (balance above `MIN_COINS_ON_SHARES_POOL`) calls `add_stake(pool_address, 1)` (1 octa after fee subtraction).
3. `amount_to_shares_with_total_coins(1, 5_000_000) = 1 * 5_000_000 / 10_000_000 = 0`.
4. `stake::add_stake(&owner, 1)` already executed at line 1501 [4](#0-3) , then `buy_in_active_shares` returns `0` silently [5](#0-4) , `assert_min_active_balance` passes because pre-existing balance was already sufficient.
5. Transaction succeeds; delegator's 1 octa is now part of the pool's coin balance but no share increase occurred — value silently transferred to other shareholders.

**Caveat:** I was not able to fully trace `assert_min_active_balance`'s exact threshold constant or confirm from live/test state exactly how large the coin/share ratio drift can get in practice within the available index; a background Devin session with full repo/test access would be needed to confirm the exact numeric conditions and any additional guards not surfaced by the search.

    /// Buy shares into the active pool on behalf of delegator `shareholder` who
    /// deposited `coins_amount`. This function doesn't make any coin transfer.
    fun buy_in_active_shares(
        pool: &mut DelegationPool,
        shareholder: address,
        coins_amount: u64,
    ): u128 acquires GovernanceRecords {
        let new_shares = pool.active_shares.amount_to_shares(coins_amount);
        // No need to buy 0 shares.
        if (new_shares == 0) { return 0 };

        // Always update governance records before any change to the shares pool.
        let pool_address = get_pool_address(pool);
        if (partial_governance_voting_enabled(pool_address)) {
            update_governance_records_for_buy_in_active_shares(pool, pool_address, new_shares, shareholder);
        };

        pool.active_shares.buy_in(shareholder, coins_amount);
        new_shares
    }

    /// Return the number of new shares `coins_amount` can buy in `self` with a custom total coins number.
    /// `amount` needs to big enough to avoid rounding number.
    public fun amount_to_shares_with_total_coins(self: &Pool, coins_amount: u64, total_coins: u64): u64 {
        // No shares yet so amount is worth the same number of shares.
        if (self.total_coins == 0 || self.total_shares == 0) {
            // Multiply by scaling factor to minimize rounding errors during internal calculations for buy ins/redeems.
            // This can overflow but scaling factor is expected to be chosen carefully so this would not overflow.
            coins_amount * self.scaling_factor
        } else {
            // Shares price = total_coins / total existing shares.
            // New number of shares = new_amount / shares_price = new_amount * existing_shares / total_amount.
            // We rearrange the calc and do multiplication first to avoid rounding errors.
            self.multiply_then_divide(coins_amount, self.total_shares, total_coins)
        }
    }
