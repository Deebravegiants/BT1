### Title
Simplex venue pricing derives from an unmanipulation-resistant Uniswap V4 spot price (`sqrtPriceX96`), open to flashloan/sandwich manipulation of intent fills - (File: `sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts`)

### Summary
Simplex's FX filler (an intent solver reachable by any unprivileged user placing a Hyperbridge cross-chain intent) prices "venue" pairs (no static curve configured) directly from a Uniswap V4 pool's live `sqrtPriceX96` spot price via `getSlot0`, exactly the pattern flagged in the source report (`uniPool.slot0()` spot price feeding a valuation function). There is no TWAP; the only mitigation is a static `referencePrice`/`maxDeviationBps` guard that is optional and can be left unconfigured ("unguarded").

### Finding Description
`UniswapV4FundingPlanner.getExoticTokenPrice` picks the most-liquid position and calls `computeDirectPoolPriceUsd`, which returns "the raw pool mid derived from `sqrtPriceX96`" [1](#0-0) , sourced from a live on-chain `getSlot0` read with no averaging window [2](#0-1) .

This price feeds directly into order pricing: `resolveLegRates` uses `venueUsdPrice` (this same spot mid) to compute the leg's rate for any curveless USD-quoted pair, subject only to `checkPriceGuard` [3](#0-2) , and `referenceRate`/`sizeOrder` use it as well [4](#0-3) . The project's own documentation confirms this is an unbounded spot read: "`computeDirectPoolPriceUsd` returns the **raw pool mid** derived from `sqrtPriceX96`... there is no size or impact term... `checkPriceGuard` is the only defense on this path, and it checks deviation from a static reference, not execution cost." [5](#0-4) 

The `referencePrice`/`maxDeviationBps` guard is optional per position and, per the docs, "the two fields must be set together; omit both to leave the chain unguarded" [6](#0-5) . Even when configured, it only bounds drift against a static number — an attacker can still manipulate the spot price by up to `maxDeviationBps` around that reference to bias the price, or manipulate freely if the guard is left unset, exactly mirroring the flashloan-manipulable spot-price pattern in the source report.

The overfill clamp that historically bounded loss from a "manipulated venue price" has also been explicitly disabled: "the clamp is DISABLED, so the filler fills the full computed amount even when it exceeds (1 + maxOverfillBps) × user-requested — including venue-priced legs (e.g. Uniswap V4)... this removes the per-leg loss bound that previously protected against a bug / stale cache / manipulated venue price. Output is no longer capped; we only emit a warning." [7](#0-6) 

### Impact Explanation
Any unprivileged user can submit an intent order and, in the same transaction context (flashloan/sandwich), push the referenced Uniswap V4 pool's `sqrtPriceX96` off its true value immediately before the solver quotes/fills. Because:
- The price feeding the fill (`computeLegPolicyOutput` × `rates.rate`) is the manipulated spot mid,
- The overfill clamp that would have limited losses is deliberately disabled,
- The only defense (`checkPriceGuard`) is optional and, even when present, only checks against a stale static reference within a configurable band,

an attacker can induce the solver to pay out venue-priced exotic tokens (or accept undervalued input) at a manipulated rate, directly transferring value from the solver's escrowed/withdrawn liquidity to the attacker. This is a direct theft-of-funds path against the solver's fill wallet/vault-funded Uniswap V4 LP positions.

### Likelihood Explanation
High. No special privilege is needed — placing an intent order that hits a venue-priced (curveless) pair is a normal, permissionless user action, and manipulating a Uniswap V4 pool's spot price with a flash loan is a well-known, low-cost, single-transaction attack. The vulnerability is amplified because: (1) `referencePrice`/`maxDeviationBps` guard is opt-in and can be entirely absent, and (2) the overfill/output clamp defense was explicitly disabled in a recent change, removing the last automated backstop against a manipulated venue price.

### Recommendation
- Replace the spot `sqrtPriceX96` read with a TWAP (time-weighted average price) over a meaningful window (e.g., using Uniswap's oracle observations) for all venue-priced quotes and fills.
- Make the `referencePrice`/`maxDeviationBps` guard mandatory (not optional) for any pair using pool-based ("venue") pricing, and tighten `maxDeviationBps` to a value consistent with realistic price movement, not with the attacker's manipulation budget.
- Re-enable (or replace) the disabled overfill/output clamp specifically for venue-priced legs so a spot-price spike cannot translate into an unbounded payout, independent of the guard's static reference.
- Consider requiring multiple independent price sources (e.g., pool TWAP + external oracle) to agree within tolerance before filling venue-priced legs.

### Proof of Concept
1. Attacker identifies a Simplex-configured trading pair with no static bid/ask curve, priced via `[vault.uniswapV4]` (per `docs/content/developers/evm/simplex/pricing.mdx`), with either no `referencePrice`/`maxDeviationBps` configured, or one wide enough to allow meaningful drift.
2. Attacker takes a flash loan and swaps heavily through the referenced Uniswap V4 pool to move `sqrtPriceX96` in the direction that undervalues the exotic token (or overvalues the stable side), then, in the same block/transaction bundle, submits (or has already pre-positioned) a Hyperbridge intent order against that pair.
3. Simplex's `FXFiller` calls `resolveLegRates` → `venueUsdPrice` → `UniswapV4FundingPlanner.getExoticTokenPrice` → `computeDirectPoolPriceUsd`, which reads the manipulated live `getSlot0` price [8](#0-7) .
4. `computeLegPolicyOutput` computes `policyMaxOutput` from this manipulated rate and, because the overfill clamp is disabled, the filler pays out the full manipulated amount without further capping [9](#0-8) .
5. Attacker reverses the flash-loan swap, restoring the pool price, and pockets the difference between the fair value and the manipulated fill amount, extracted from Simplex's funded liquidity.

	async getExoticTokenPrice(chain: string, exoticToken: string): Promise<Decimal | null> {
		const state = this.stateByChain.get(chain)
		if (!state || !state.isHydrated()) return null

		try {
			await state.refresh()
		} catch (err) {
			this.logger.error({ err, chain }, "Failed to refresh state for price query")
			return null
		}

		const tokenLower = exoticToken.toLowerCase()
		let bestPrice: Decimal | null = null
		let bestLiquidity = 0n

		for (const pos of state.allPositions()) {
			if (pos.currency0.toLowerCase() !== tokenLower && pos.currency1.toLowerCase() !== tokenLower) continue
			const sdkPool = state.getSdkPool(pos.tokenId)
			if (!sdkPool) continue

			const result = this.computeDirectPoolPriceUsd(pos, sdkPool, chain)
			if (result && result.exoticToken.toLowerCase() === tokenLower) {
				const poolLiquidity = state.getPoolLiquidity(pos.tokenId)
				if (poolLiquidity > bestLiquidity) {
					bestPrice = result.priceUsd
					bestLiquidity = poolLiquidity
				}
			}
		}

		if (bestPrice) {
			this.logger.debug({ chain, token: tokenLower, priceUsd: bestPrice.toString() }, "Exotic token price computed")
		}
		return bestPrice
	}

	/**
	 * Minimum-size reference rate (token1 per token0) for a leg's pair: the
	 * bid curve at 0 (the side token1-input legs trade at), falling back to the
	 * ask curve, then the live venue quote for venue-priced pairs.
	 */
	private async referenceRate(
		leg: ResolvedLeg,
		venueUsdPrice: (chain: string, token1Address: string) => Promise<Decimal | null>,
	): Promise<Decimal | null> {
		const policy = leg.pair.bidPricePolicy ?? leg.pair.askPricePolicy
		if (policy) {
			const rate = policy.getPrice(new Decimal(0))
			return rate.gt(0) ? rate : null
		}
		// Venue-priced pair: token0 is USD-stable (constructor invariant), so the
		// venue's USD-per-token1 quote inverts straight into token1-per-token0.
		const venueUsd = await venueUsdPrice(leg.token1Chain, leg.token1Address)
		if (!venueUsd) return null
		const venueRate = new Decimal(1).div(venueUsd)
		// Same guard as trade pricing: this rate sizes the order's USD notional
		// for confirmation depth, and a manipulated pool understating the value
		// would shrink the reorg protection — the exact attack the guard exists
		// to stop. Refusing to size skips the order, consistent with pricing.
		if (!this.checkPriceGuard(undefined, leg.token1Chain, venueRate)) return null
		return venueRate
	}

`computeDirectPoolPriceUsd` returns the **raw pool mid** derived from `sqrtPriceX96`. The pool's
fee tier is read and stored on the hydrated position (`pos.fee`) but never applied to the price,

```text
## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.
```
