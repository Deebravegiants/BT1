### Title
Unprivileged clients can hijack another user's Web API trigger response via `MessageID` collision in the Gateway's `savedCallbacks` map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The Gateway's legacy Web API capability handler stores per-request callbacks in a shared, unauthenticated map keyed only by a client-supplied `MessageID`/request `ID`. Unlike the analogous `OutgoingConnectorHandler`, which explicitly rejects a duplicate message ID, `handler.HandleLegacyUserMessage` performs an **unconditional overwrite** of any existing entry with the same key. This "update state before verifying exclusivity" pattern is the same class of bug as the Cream Finance exploit: state relevant to a still-in-flight operation (the pending callback awaiting a DON response) is silently mutated by a second, unrelated caller before the first operation completes, letting an unprivileged actor divert the eventual DON response to themselves.

### Finding Description
The JSON-RPC `ID` field on an incoming gateway request is copied verbatim into `api.Message.Body.MessageID`: [1](#0-0) 

This value is fully attacker-controlled by any unprivileged HTTP client calling the public gateway endpoint; the only validation applied is a length check: [2](#0-1) 

`HandleLegacyUserMessage` then stores the caller's `callback` in the handler's shared `savedCallbacks` map keyed by this attacker-controlled `MessageID`, with **no check for an existing entry**: [3](#0-2) 

When a DON node later responds for that `MessageID`, `handleWebAPITriggerMessage` looks the ID up in the map, deletes it, and forwards the response to *whatever callback is currently stored*, with no verification that it belongs to the original requester: [4](#0-3) 

Compare this to the sibling `OutgoingConnectorHandler`, which explicitly guards against this exact race by rejecting duplicate IDs: [5](#0-4) 

The Web API trigger path lacks this guard. If a second unprivileged client submits a request using the same `MessageID` while a first request is still pending (i.e., before the DON has responded), the second caller's callback silently overwrites the first caller's entry in the map. When the DON eventually responds (for either the first or second request — payloads are broadcast to all DON members regardless), the response is delivered to whichever callback remains registered, not necessarily to the client whose request produced it.

### Impact Explanation
This allows an unauthenticated/unprivileged external caller to:
- Receive another user's DON trigger response instead of their own (cross-user response confusion), potentially exposing response data intended for a different requester.
- Cause denial-of-service against a victim's pending request, which will instead time out because its registered callback was evicted.

This qualifies as a concrete cross-user response confusion vulnerability reachable purely from an unprivileged client HTTP request to the internet-facing gateway, mirroring the Cream Finance root cause of mutating shared state based on an externally influenced identifier without exclusivity/duplicate checks before completing the operation.

### Likelihood Explanation
Exploitation requires only:
1. Knowledge or predictability of a victim's `MessageID`/request `ID` (which is often a workflow-visible or otherwise guessable value, and in the worst case an attacker can simply flood many IDs to increase collision odds), and
2. A submission timed while the victim's request is still pending (default callback lifetime is up to 120 seconds per `defaultCallbackMaxAgeSec`), which is a comfortable race window.

No authentication bypass or privileged access is required — any client able to reach the gateway's public HTTP JSON-RPC endpoint can attempt this.

### Recommendation
Mirror the protection already used in `OutgoingConnectorHandler.responses.new(messageID)`: before inserting into `savedCallbacks`, check whether an entry already exists for that `MessageID` and reject the new request (return an error to the caller) rather than overwriting it. Additionally, consider scoping `MessageID` uniqueness per-DON/per-connection or deriving it server-side rather than trusting the raw client-supplied JSON-RPC `ID`.

### Proof of Concept
1. Client A sends a `web_api_trigger` legacy request to the gateway with `ID = "X"`. The gateway stores A's callback in `savedCallbacks["X"]` and forwards the request to all DON members (`core/services/gateway/handlers/capabilities/handler.go:411-419`).
2. Before any DON node responds, Client B (unprivileged, unrelated) sends its own `web_api_trigger` request also using `ID = "X"`. The gateway overwrites `savedCallbacks["X"]` with B's callback (same code path, no duplicate check).
3. A DON node processes and returns a `MethodWebAPITrigger` response tagged `MessageID = "X"`. `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds B's callback, deletes the entry, and delivers the response to B (`core/services/gateway/handlers/capabilities/handler.go:148-162`).
4. Client A's original HTTP request times out with no response, while Client B — who issued an entirely separate/no-op request — receives the DON's response data associated with Client A's trigger.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
	delete(h.savedCallbacks, msg.Body.MessageID)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JSONRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
