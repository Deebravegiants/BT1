### Title
Partial LI.FI swap fills permanently freeze residual input tokens in `LifiExternalAction`/`ExternalActionSwap` - (File: `contracts/external-actions/swaps/LifiExternalAction.sol`, `contracts/external-actions/swaps/ExternalActionSwap.sol`)

### Summary
`LifiExternalAction.callRouter()` only checks the *output*-token balance delta after calling the LI.FI router; it never verifies that the full `inputAmount` transferred into the contract was actually consumed by the router call. If the router only partially fills the swap (common with aggregator/DEX routes, exact-output swap types that refund unused input to `msg.sender` = the action contract itself, or multi-step routes where one leg reverts/short-fills), the unused input tokens remain stranded on the `LifiExternalAction` contract with no code path to reclaim or return them.

### Finding Description
In `ExternalActionSwap.swap()`, the full `inputAmount` (`uint256(-deltaAmounts[0])`) is assumed to be fully consumed by `callRouter()`: [1](#0-0) 

`LifiExternalAction.callRouter()` measures only the change in the **output** token balance and returns that as `swappedAmount`; it never checks how much of the **input** token balance was drawn down by the router call: [2](#0-1) 

The full `inputAmount` is pushed from `Hinkal.sol` to the `LifiExternalAction` contract *before* `runAction` is invoked: [3](#0-2) 

Because `Hinkal.sol`'s balance-equation check (`balanceDif == amountChanges + utxoAmount`) is computed purely from `Hinkal.sol`'s own balances, taken before/after the entire external-action call, it is already satisfied the moment the full input amount leaves `Hinkal.sol` — regardless of what the router actually consumes inside `runAction`: [4](#0-3) 

Any leftover input token that the LI.FI router did not spend (e.g. refunded by the router back to `msg.sender`, which here is the `LifiExternalAction` contract, not the end user) sits on the contract's own ERC20 balance. There is no sweep/rescue mechanism anywhere in the contract hierarchy (`Transferer.sol`, `TransfererBase.sol`, `ExternalActionBaseV2.sol`) to recover it, and it is not folded into the `outUtxo`/`utxoSet` returned to `Hinkal.sol`, so it is never re-minted as a shielded UTXO for the user either. [5](#0-4) 

This mirrors H-4 exactly: YearnProvider transferred the full share amount into itself and assumed `IYearn.withdraw()` fully consumed it, when partial-withdrawal is a normal Yearn behavior; here `LifiExternalAction` transfers the full input amount into itself and assumes the LI.FI router call fully consumes it, when partial fills/refunds are a normal LI.FI/DEX-router behavior.

### Impact Explanation
Any input-token remainder left unconsumed by the router is permanently frozen on the `LifiExternalAction` contract balance — it is neither returned to the user, credited as a shielded UTXO, nor recoverable by any admin/rescue function. This is a permanent freezing of user funds (Critical per the given impact taxonomy), and because the contract is shared across all users of the swap action, the frozen balance accumulates over time and could affect many users.

### Likelihood Explanation
This is reachable by any unprivileged user going through the normal `transact()` flow with `externalActionId` pointing at `LifiExternalAction`. The `externalActionMetadata` calldata for the LI.FI router call is constructed off-chain by the user/relayer and is not constrained on-chain to guarantee full consumption of the input amount — any LI.FI route type that supports partial fill, exact-output semantics, or a multi-step path where a later leg fails/short-fills will trigger the freeze without any special privilege or admin involvement.

### Recommendation
In `LifiExternalAction.callRouter()` (or in `ExternalActionSwap.swap()`), measure the input-token balance before/after the router call and require that it dropped by (at least) `inputAmount`, or — analogous to the H-4 fix — compute the actual amount consumed and return any residual input-token balance back to `msg.sender` (i.e., `Hinkal.sol`) as part of the returned `UTXO[]`, so it is re-minted for the user instead of being stranded.

### Proof of Concept
1. User calls `Hinkal.transact()` with `externalActionId` set to the LI.FI swap action, `erc20TokenAddresses = [inputToken, outputToken]`, and `amountChanges[0] = -inputAmount`.
2. `Hinkal._externalTransact()` transfers the full `inputAmount` of `inputToken` to `LifiExternalAction`.
3. `LifiExternalAction.callRouter()` calls the LI.FI `router` with attacker/relayer-supplied `externalActionMetadata` describing a route that, due to on-chain liquidity conditions or an exact-output/partial-fill route type, only consumes `inputAmount/2` of `inputToken`, refunding the rest to `msg.sender` (the `LifiExternalAction` contract).
4. `swappedAmount` is computed only from the output-token delta and returned; the leftover `inputAmount/2` of `inputToken` remains on `LifiExternalAction`'s balance.
5. `Hinkal.sol`'s balance-equation check for `inputToken` passes (its own balance already dropped by the full `inputAmount` in step 2), so the transaction completes successfully with no revert and no accounting of the stuck remainder — the leftover tokens are now permanently frozen on `LifiExternalAction` with no recovery path.

    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }

pragma solidity ^0.8.17;

import {CircomData} from "../types/CircomData.sol";
import {UTXO} from "../types/UTXO.sol";
import {IExternalActionV2} from "../types/IExternalActionV2.sol";
import {OwnerHinkal} from "../OwnerHinkal.sol";

abstract contract ExternalActionBaseV2 is IExternalActionV2, OwnerHinkal {
    mapping(address => bool) internal isAllowedRecipient;

    /*
     * @dev Modifier to check if the sender is allowed to call the action
     * @dev Used to handle VolatileTokenAction and Hinkal interactions
     */
    modifier onlyAllowedRecipient() {
        require(
            isAllowedRecipient[msg.sender],
            "ExternalActionBase: sender not allowed"
        );
        _;
    }

    constructor(address[] memory _allowedRecipients) {
        for (uint i = 0; i < _allowedRecipients.length; i++) {
            isAllowedRecipient[_allowedRecipients[i]] = true;
        }
    }

    function setAllowedRecipients(
        address[] calldata recipients
    ) external onlyOwner {
        for (uint i = 0; i < recipients.length; i++) {
            require(recipients[i] != address(0), "zero address!");
            isAllowedRecipient[recipients[i]] = true;
        }
    }

    function runAction(
        CircomData calldata circomData,
        int256[] calldata deltaAmountChanges
    ) external virtual returns (UTXO[] memory utxoSet) {}
}
