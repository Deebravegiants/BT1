## Title
`SignerCapabilityOfferProofChallengeV2` Lacks `chain_id` Domain Separation, Enabling Cross-Network Signer-Capability Grant Replay — (File: `aptos-move/framework/aptos-framework/sources/account/account.move`)

### Summary
`account::offer_signer_capability` authorizes granting a full `SignerCapability` (the ability to produce a `signer` for the offerer's account, i.e. total custody over that account's coins, objects, and resources) to a `recipient_address`, gated by an off-chain signature over `SignerCapabilityOfferProofChallengeV2`. Unlike its sibling struct `RotationCapabilityOfferProofChallengeV2`, which explicitly embeds `chain_id` "to prevent replaying the challenge message," `SignerCapabilityOfferProofChallengeV2` omits `chain_id` entirely. [1](#0-0) 

### Finding Description
The `SignerCapabilityOfferProofChallengeV2` struct is defined with only `sequence_number`, `source_address`, and `recipient_address`: [2](#0-1) 

Compare this to `RotationCapabilityOfferProofChallengeV2`, defined immediately above it, which the code comment explains was upgraded specifically to add `chain_id` and `source_address` "to prevent replaying the challenge message": [3](#0-2) 

`offer_signer_capability` builds the challenge and verifies it purely with `sequence_number`, `source_address`, `recipient_address` — no `chain_id`, no `address(this)`-equivalent (module/account address is fixed at `0x1` for both structs so that alone doesn't help), and no other network-binding value: [4](#0-3) 

This is structurally the same class of bug as the `Revolver.joinGame()` report: the signed preimage omits a domain/network identifier (there, `block.chainid`/`address(this)`; here, `chain_id`), so a signature valid in one deployment context is valid verbatim in another as long as `sequence_number` matches.

**Exploitability conditions**: Because `sequence_number` is the account's on-chain sequence number, the signature is bound to a particular sequence-number state of the account, not to a specific chain. This is exploitable when the same account address/key exists at the same sequence number on more than one Aptos network instance — most concretely:
- Devnet resets: devnet is periodically wiped and restarted from genesis. A user/account that existed on a previous devnet incarnation at sequence number `N` and later exists again at the same address with sequence number `N` on the new devnet incarnation would have any previously-signed (but not yet submitted, e.g. held by a malicious relayer/dApp) `SignerCapabilityOfferProofChallengeV2` signature remain valid.
- Any other same-chain-id-space forks/incarnations, or custom Aptos-based chains created by forking the framework, where the same account happens to share both the address/key and sequence-number history (e.g. a fresh account at sequence 0 provisioned identically on two networks by the same tooling/faucet).

An attacker (or the recipient itself who requested the signature for one purpose) holding a validly-signed `SignerCapabilityOfferProofChallengeV2` from context A can replay it verbatim on context B to obtain a `SignerCapability` offer over the victim's account there, and subsequently call `create_authorized_signer` to mint a `signer` for the victim account — full custody over any assets held at that address on chain B: [5](#0-4) 

### Impact Explanation
`SignerCapability` is one of the most powerful custody primitives in Aptos: `create_authorized_signer` returns a full `signer` for the offerer's address, which can move any `AptosCoin`, transfer any object owned directly by that address, execute arbitrary entry functions as that account, etc. An unintended cross-context grant of this capability is a takeover of account/resource-account control tied to live assets, matching the "Unauthorized takeover of ... resource-account control ... tied to live assets" custody-impact category. This is high severity because it results in complete authority transfer, not merely a griefing or availability issue.

### Likelihood Explanation
Likelihood is constrained relative to a public mainnet-vs-mainnet replay because it additionally requires the victim account to reach the *same* `sequence_number` on two chain instances with the *same* address/key — realistically arising from devnet resets/forks, custom chain deployments sharing genesis state, or test/staging environments that mirror mainnet account state. Within those realistic same-framework-deployment scenarios (which are common in the Aptos ecosystem given periodic devnet wipes and the framework being reused for L1/L2 chains), the missing `chain_id` is a genuine, reachable domain-separation gap with no other on-chain safeguard compensating for it — the sibling function `offer_rotation_capability` was already patched with `chain_id` precisely for this reason, showing the risk is well understood by the codebase's own authors but was not applied consistently to `offer_signer_capability`.

### Recommendation
Add `chain_id: u8` to `SignerCapabilityOfferProofChallengeV2` (mirroring `RotationCapabilityOfferProofChallengeV2`) and populate it with `chain_id::get()` in `offer_signer_capability`:
```move
struct SignerCapabilityOfferProofChallengeV2 has copy, drop {
    chain_id: u8,
    sequence_number: u64,
    source_address: address,
    recipient_address: address,
}
```
```move
let proof_challenge = SignerCapabilityOfferProofChallengeV2 {
    chain_id: chain_id::get(),
    sequence_number: get_sequence_number(source_address),
    source_address,
    recipient_address,
};
```
Note: this is a breaking change to the struct's BCS layout, so it requires careful coordination with SDKs/clients that construct and sign this struct off-chain (similar to how the V1→V2 migration for rotation capability was handled).

### Proof of Concept
Conceptual reproduction (cannot be executed without a live multi-network Aptos test harness, but derivable directly from the code above):
1. Alice creates account `A` on Devnet-Incarnation-1 at `sequence_number = 0`.
2. Alice signs `SignerCapabilityOfferProofChallengeV2 { sequence_number: 0, source_address: A, recipient_address: Mallory }` off-chain (e.g., as part of a dApp flow that never submits the resulting transaction), following the exact pattern used in the existing e2e test: [6](#0-5) 
3. Mallory holds this signature but does not submit it on Devnet-Incarnation-1.
4. Devnet is reset (a routine, documented Aptos devnet operation). Alice's account `A` is recreated at the same address with the same key at `sequence_number = 0` on Devnet-Incarnation-2 (e.g., via the same deterministic faucet/onboarding flow).
5. Mallory submits the previously-obtained signature to `account::offer_signer_capability` on Devnet-Incarnation-2. Verification succeeds because the preimage contains no `chain_id`/network identifier and `sequence_number`/`source_address`/`recipient_address` all still match.
6. Mallory calls `create_authorized_signer(mallory_signer, A)` and obtains a `signer` for Alice's account `A` on Devnet-Incarnation-2, gaining full custody over any assets Alice holds there. [5](#0-4) 

**Uncertainty**: I could not find a live multi-network test harness in the repo to empirically demonstrate cross-network replay end-to-end (index coverage is limited to what the search tools surfaced), so this PoC is derived analytically from the verified code paths above rather than an executed exploit trace. The core, verifiable fact is the structural asymmetry: `RotationCapabilityOfferProofChallengeV2` was deliberately given a `chain_id` field with an explicit anti-replay comment, while `SignerCapabilityOfferProofChallengeV2`, guarding an equally or more powerful custody grant, was not.
