### Title
Duplicate input tokens merge into one escrow bucket on Tron's `IntentGatewayV2.placeOrder`, enabling over-release of escrowed funds - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron fork of `IntentGatewayV2.placeOrder` credits escrow with `_orders[commitment][token] += reducedInputs[i].amount` and has no rejection of duplicate input tokens. The mainline EVM contract (`evm/src/apps/IntentGatewayV2.sol`) was patched to explicitly reject this case, with an accompanying regression test describing exactly this bug class ("same-chain partial fills over-release repeated input escrow"), but the Tron variant still contains the unpatched pattern.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `placeOrder` escrows each input leg with: [1](#0-0) 
```
// Store reduced amount (after protocol fees) in escrow
_orders[commitment][token] += reducedInputs[i].amount;
```
used identically in both the predispatch and non-predispatch escrow paths. There is no check that rejects two input legs referencing the same token address, unlike the patched mainline contract, which explicitly guards against this: [2](#0-1) 
```
// Phase 3: Credit escrow.
for (uint256 i; i < inputsLen;) {
    address token = address(uint160(uint256(order.inputs[i].token)));
    // Reject duplicate input tokens
    if (_orders[commitment][token] != 0) revert InvalidInput();
    _orders[commitment][token] = reducedInputs[i].amount;
    ...
```

The bug manifests during same-chain fills (`IntrinsicIntents._fillSameChain`), where escrow release for a fully-filled leg reads the entire per-token bucket rather than a per-leg amount: [4](#0-3) 
```
uint256 escrowedAmount;
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
```
When an order places two input legs of the same token (e.g. USDC), the escrow contributions merge into a single bucket at `placeOrder` time. If the order also has multiple output legs, when each output leg independently reaches full fill, the code reads and releases the *entire merged bucket* for that token again — because `escrowedAmount` is derived from the merged, cumulative `_orders[commitment][token]` value rather than the per-leg contribution. This double-counts/over-releases escrow to the solver relative to what was actually deposited for that specific leg, since the value in the bucket reflects both legs' combined deposit but is paid out once per leg that reaches full fill.

### Impact Explanation
This is the intents-escrow analog of the MasterChef finding: an unprivileged party (the order placer, and/or a colluding solver — same-chain same-actor case is trivially reachable) inflates an internal accounting bucket (`_orders[commitment][token]`) by crafting duplicate input legs of the same token, then drains more escrow than was legitimately deposited for that order during fill. Because the gateway holds a shared, fungible-token pool (not per-order segregated balances), the over-released amount is paid for out of the contract's aggregate token balance — i.e., out of other users' escrowed funds — constituting direct theft of escrowed assets from the protocol/other order placers. This satisfies the "concrete theft ... of funds" bar via inflated internal balance accounting, reachable from a single `placeOrder` + `fillOrder` transaction pair with no admin/governance involvement, matching the allowed category "intents escrow and bids."

### Likelihood Explanation
Medium-High. Exploitation only requires an unprivileged user to place an order with two input legs referencing the same ERC-20 token address and multiple output legs, then (as solver, potentially the same account) fill it — no special privileges, timing, or external state are needed. The mainline `IntentGatewayV2.sol` was already patched for exactly this defect, and a security audit specifically flagged and tested it (see the regression comment "Regression test for: same-chain partial fills over-release repeated input escrow"), confirming the bug is real and was exploitable prior to the fix. The Tron contract simply never received the equivalent fix.

### Recommendation
Port the duplicate-input-token rejection from `evm/src/apps/IntentGatewayV2.sol` (`if (_orders[commitment][token] != 0) revert InvalidInput();`, credited via assignment rather than `+=`) into `evm/tron/contracts/apps/IntentGatewayV2.sol`, and add the equivalent regression test (`testRevert_PlaceOrder_DuplicateInputTokens`) to the Tron test suite. Also add the duplicate-output-token rejection present in the mainline `placeOrder` (currently absent from the excerpt reviewed) if the Tron fork supports the same partial-fill mechanics, since a duplicate output token is a distinct but related over-release vector against `_partialFills`.

### Proof of Concept
1. User calls `placeOrder` on the Tron `IntentGatewayV2` with `order.inputs = [ {token: USDC, amount: 1200 USDC}, {token: USDC, amount: 1000 USDC} ]` and two output legs (e.g., DAI amounts 500 and 1000). Escrow credit loop runs `_orders[commitment][USDC] += 1200` then `+= 1000`, leaving `_orders[commitment][USDC] == 2200` (only 2200 USDC actually deposited, correctly, but now indistinguishable from two independent 1200/1000 legs).
2. Solver calls `fillOrder`/`_fillSameChain` (if the Tron contract's fill logic mirrors `IntrinsicIntents.sol`) supplying both DAI output legs in full. For leg 0 (`totalRequired = 500 DAI`), on full fill the code sets `escrowedAmount = _orders[commitment][USDC] == 2200` and transfers 2200 USDC to the solver. For leg 1 (`totalRequired = 1000 DAI`), on full fill it again reads `_orders[commitment][USDC] == 2200` and transfers another 2200 USDC.
3. Net effect: solver receives 4400 USDC in escrow release for an order that only escrowed 2200 USDC — an extra 2200 USDC drained from the gateway's pooled token balance (other users' escrow), while paying only 1500 DAI total in outputs.

Note: I could not directly confirm the Tron contract's `fillOrder`/same-chain fill implementation (no `_fillSameChain`/`_partialFills` symbols were found in `evm/tron/contracts/apps/IntentGatewayV2.sol` via search), so the exact PoC mechanics on the fill side are inferred from the mainline `IntrinsicIntents.sol` logic which the regression test targets. If the Tron variant does not implement same-chain partial fills at all, the exploitability is limited to whatever fill path it does use, but the escrow-credit code itself (`_orders[commitment][token] += ...` with no duplicate check) is confirmed unpatched, and the root-cause discrepancy vs. the fixed mainline contract stands as documented above.
