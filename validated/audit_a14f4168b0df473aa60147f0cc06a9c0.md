This confirms the core finding: the `Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop` is read directly from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header [2](#0-1) . The HMAC computed by `HmacValidator.validate_signature` is over `verifiable_query.to_signable_string` (body only) [3](#0-2) , so the `shop` header value is never bound into the signed bytes. Yet `Registry.process` passes this unauthenticated `request.shop` straight into `WebhookMetadata` delivered to the app's handler [4](#0-3) , and the gem's own documented handler pattern uses `data.shop` as the tenant identifier to dispatch/enqueue per-shop work [5](#0-4) .

### Title
Webhook `shop` identifier is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` field from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature validated by `HmacValidator` only covers the raw request body. An attacker who can produce (or replay) any request body whose HMAC matches a known/leaked secret-signed body for topic X can attach an arbitrary `shop` header value, causing the app's webhook handler to process the webhook under an attacker-chosen shop identity.

### Finding Description
`Webhooks::Request#to_signable_string` returns `@raw_body` only [1](#0-0) . `HmacValidator.validate` computes the signature strictly over `verifiable_query.to_signable_string` and compares it to the `hmac` header via `OpenSSL.secure_compare` [3](#0-2) . Meanwhile, `shop` is read independently from `shopify-shop-domain`/`x-shopify-shop-domain` headers [2](#0-1) , which are not part of the signed bytes at all.

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e., body/HMAC match) before dispatching to the handler using `request.shop` as the trusted tenant identity [4](#0-3) . There is no cross-check that the `shop` header is bound to, or consistent with, the signed payload. The equality the gem implicitly assumes but does not enforce is: `shop header value == shop that produced the HMAC-signed body`. That equality can be broken because the two are verified independently against disjoint inputs (headers vs. body).

Since Shopify's genuine webhook delivery does bind body+shop consistently, exploiting this from the internet requires the attacker to already possess a valid `(raw_body, hmac)` pair for the app's secret for some shop/topic (e.g., a previously observed/leaked webhook delivery, or a topic with attacker-influenced/predictable body content signed by Shopify for the attacker's *own* installed shop). With such a pair in hand, the attacker can resend the identical body+hmac while substituting the `X-Shopify-Shop-Domain` header for a *different* victim shop, and the gem will accept it as valid and hand `WebhookMetadata` with the victim's `shop` to the app's handler.

### Impact Explanation
This breaks the tenant boundary (cross-tenant access) the gem's webhook processing pipeline is meant to guarantee. The documented handler pattern in `docs/usage/webhooks.md` explicitly uses `data.shop` to key off per-shop jobs/records (`perform_later(topic: data.topic, shop_domain: data.shop, ...)`) [5](#0-4) . If a host app follows this documented pattern (as recommended), an attacker-controlled `shop` value can cause the app to write/process data attributed to a shop the attacker doesn't own, i.e., cross-tenant data confusion, which matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires the attacker to obtain at least one legitimately signed `(body, hmac)` pair — e.g., from their own shop's webhook delivery, from webhook logs, or from a topic where the body is attacker-influenced (such as `app/uninstalled` for their own dev store, or any topic whose JSON body content the attacker controls via normal store actions). Given that, they can replay the exact bytes while forging only the `shop` header, which travels over the network unauthenticated. This is plausible for a moderately capable unprivileged attacker but does require capturing/producing a valid signed body first, so likelihood is moderate rather than trivial.

### Recommendation
Bind the `shop` (and ideally `topic`, `api_version`, `webhook_id`) header values into the HMAC-covered signable string, or otherwise cryptographically verify the header values against the payload, rather than trusting `X-Shopify-Shop-Domain` as an unauthenticated identity field. At minimum, document that `data.shop` from `WebhookMetadata` must not be treated as authenticated unless applications independently corroborate it (e.g., against a shop already known to have installed the app via a valid access token), and consider raising `InvalidWebhookError` if the `shop` domain format/known-shop check fails.

### Proof of Concept
```ruby
# Attacker has obtained one valid (raw_body, hmac) pair for the app's secret,
# e.g. from a webhook delivered for their own shop "attacker-shop.myshopify.com".
raw_body = '{"id":123,"note":"hello"}'
hmac_b64 = "captured-valid-base64-hmac-for-raw_body"

# Attacker replays the same bytes but swaps the shop-domain header to a victim shop.
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => hmac_b64,          # still valid, body unchanged
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, unauthenticated
  "x-shopify-webhook-id" => "any-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
# HmacValidator.validate(request) succeeds because it only checks raw_body against hmac.
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
# The app's handler now processes/attributes this webhook to "victim-shop.myshopify.com".
```
