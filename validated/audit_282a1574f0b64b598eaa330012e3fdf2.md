## Analysis Result

### Title
Unwhitelisted order input token can permanently freeze escrowed funds in Intent Gateway - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
The Intent Gateway lets a user escrow an arbitrary set of ERC-20 tokens as `order.inputs` with no token whitelist check at `placeOrder` time. When escrow is released — on fill (`RedeemEscrow`), on refund (`RefundEscrow`), or on same-chain cancel — `_withdraw` iterates over **all** tokens in the order in a single loop and calls `safeTransfer` for each. If any one of those tokens is a malicious/rogue ERC-20 that unconditionally reverts on `transfer`, the entire `_withdraw` call reverts, which blocks release of every other (legitimate) token escrowed for that same order commitment. This mirrors the OpenQ finding: a single rogue deposited token breaks the payout loop and freezes co-mingled honest funds.

### Finding Description
`placeOrder`/escrow accepts any ERC-20 address for `order.inputs[i].token` — there is no whitelist analogous to a "NFT not accepted" check. Release of escrow is performed by `_withdraw`, which loops over `body.tokens` and calls `IERC20(token).safeTransfer(beneficiary, amount)` for each entry in a single atomic loop, with no isolation or try/catch around any individual transfer: [1](#0-0) 

The Tron variant of the same logic uses a low-level call and explicitly reverts on failure (`TransferFailed`), which is equally vulnerable: [2](#0-1) 

Because a single order can escrow multiple different tokens (`order.inputs` is an array), a user can place an order that mixes a legitimate token (e.g. USDC) with a rogue token crafted to always revert on `transfer`/`transferFrom`. Once a solver fills that order and the settlement message reaches `_withdraw` (via `onAccept` for cross-chain `RedeemEscrow`/`RefundEscrow`, or directly for same-chain fills/cancels), the loop hits the rogue token and reverts the whole call — including the legitimate USDC leg that would otherwise have paid out the solver (on fill) or refunded the user (on cancel): [3](#0-2) [4](#0-3) 

Since the malicious token will deterministically revert every time `transfer` is invoked, retrying the settlement message (relayer resubmission) never succeeds — the escrowed legitimate tokens for that commitment can never be released to the solver nor refunded to the user, resulting in a permanent freeze of funds for that order.

### Impact Explanation
This is a permanent freezing-of-funds vulnerability: any legitimately escrowed token co-located in an order with a rogue token becomes unrecoverable — neither the solver (who provided real output assets and is owed the escrowed input) nor the original user (via refund/cancel) can ever retrieve it, because `_withdraw`'s single loop has no per-token fault isolation. There is no escape hatch (no admin sweep of individual order escrow, no skip-on-failure) — `_orders[commitment][token]` balances for the entire order remain stuck forever.

### Likelihood Explanation
Any user can reach `placeOrder` with an arbitrary `TokenInfo.token` address for one of possibly several inputs — no whitelist gate exists. Deploying a trivial ERC-20 that always reverts on `transfer` is a single, cheap, fully unprivileged transaction. A solver who is unaware of the malicious token composition of an order (or an attacker acting as the order's own creator to grief a solver who fills it) can trigger this deterministically on the very first settlement attempt.

### Recommendation
- Isolate token transfers per-order-token in `_withdraw` (and the Tron equivalent `withdraw`) so a revert on one token does not prevent release of the others — e.g. wrap each `safeTransfer` in a low-level call/try-catch and track/emit failed transfers as "stuck" for later manual sweep, rather than reverting the whole batch.
- Alternatively, introduce a token whitelist/allowlist check at `placeOrder` (mirroring how NFT deposits are restricted in the referenced report) to prevent arbitrary/unverified ERC-20s from ever entering escrow.
- Add a governance-only recovery path to sweep out or "skip" a specific poisoned token from an order's escrow record without blocking the release of the rest.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC-20 whose `transfer`/`transferFrom` always `revert()`.
2. Attacker (as order creator) calls `placeOrder` with `order.inputs = [ {token: USDC, amount: 1000e6}, {token: EvilToken, amount: 1} ]`, escrowing both tokens — accepted without any whitelist check, per `evm/src/apps/intentsv2/IntentsBase.sol`/`IntentGatewayV2.sol` `placeOrder` flow.
3. A solver fills the order on the destination chain, delivering the requested outputs to the beneficiary in good faith, expecting to redeem the escrowed USDC + EvilToken via the `RedeemEscrow` message.
4. When the source chain's `onAccept` processes the `RedeemEscrow` request and calls `_withdraw` (`evm/src/apps/intentsv2/IntentsBase.sol:451-470`), the loop transfers USDC successfully but reverts on `EvilToken.transfer`, reverting the entire transaction.
5. The solver can never claim the escrowed USDC (nor can the user cancel/refund it, since `_cancelSameChain`/`_cancelFromSource`/`_cancelFromDest` also route through the same `_withdraw`) — the funds are permanently frozen in the gateway contract.

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
