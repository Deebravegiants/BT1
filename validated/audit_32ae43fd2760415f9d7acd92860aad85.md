### Title
Webhook `shop-domain` is trusted without being covered by the HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC of the raw request body. The `shop-domain` value that is subsequently handed to the app's handler as the identity of the acting tenant is read straight from an HTTP header and is never included in the signed material, so it can be freely set by whoever sends the request.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the HMAC over `verifiable_query.to_signable_string`. For webhook requests, `Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop` accessor, however, is derived purely from the `x-shopify-shop-domain` (or `shopify-shop-domain`) header, which is not part of the signed payload at all: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately forwards `request.shop` to the app's handler as the authoritative tenant identity: [3](#0-2) 

Because `Context.api_secret_key` is the single `client_secret` shared by the app across **every** merchant that installs it, a valid `(raw_body, hmac)` pair generated for **one** shop is cryptographically valid for **any** shop under the same app — the HMAC binds the body to "this app's secret", not to a specific tenant. The library performs no check that the `shop-domain` header is consistent with anything inside the HMAC-covered body.

The identity binding that should hold is:
`shop authenticated by HMAC == shop delivered to the handler as request.shop`

but the code only guarantees:
`body integrity verified by HMAC != shop attribution trusted by handler`

### Impact Explanation
An attacker who legitimately installs the target app on their own Shopify store (a routine, unprivileged action) can trigger any webhook topic whose payload contains attacker-influenced content (e.g. `products/update` with a crafted title, `orders/create` with attacker-supplied note/line items, `customers/update`, custom metafields, etc.). Shopify will deliver this webhook to the attacker's registered endpoint, correctly signed with the app's shared `client_secret`. The attacker then replays the exact same raw body and `X-Shopify-Hmac-Sha256` header to the target app's real webhook endpoint, only changing the `X-Shopify-Shop-Domain` header to a victim shop that also uses the same app.

`Registry.process` will:
1. Recompute the HMAC over the (unmodified) raw body using the shared secret — validation succeeds, since it's genuinely Shopify-signed data.
2. Read `shop` from the attacker-controlled header and pass it, unverified, to the handler as the tenant the event belongs to.

The application logic (which trusts the library's `WebhookMetadata#shop`) will then persist or act on attacker-controlled data as if it originated from the victim's store — i.e., cross-tenant data injection/spoofing into another merchant's account, satisfying the "cross-tenant access" Critical impact criterion.

### Likelihood Explanation
Any developer or trial user can install the target app on their own free/dev store to obtain a genuinely signed `(body, hmac)` pair — no leaked secrets or privileged access required. Replaying that pair with a modified `shop-domain` header against the app's public webhook endpoint requires only basic HTTP tooling. The only prerequisite is that the target app processes some webhook topic whose body content is at least partially attacker-influenced, which is common (product/order/customer webhooks).

### Recommendation
Bind the trusted shop identity to data that is actually covered by the HMAC:
- Prefer deriving `shop` from a field inside the signed JSON body (Shopify includes shop-identifying data such as the domain or `admin_graphql_api_id` in many payloads) rather than from an unauthenticated header, or
- At minimum, cross-check the header-supplied `shop-domain` against an expected/registered shop for that specific webhook subscription (e.g., verify it matches the shop the app expects to receive this webhook_id/topic from) before invoking the handler, and document to consumers that `request.shop` is not currently bound by the HMAC.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and registers a webhook (e.g. `products/update`) pointing to a server they control.
2. Attacker edits a product title to embed malicious/crafted data and triggers the webhook; Shopify delivers:
   - Headers: `x-shopify-hmac-sha256: <valid-hmac>`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: products/update`
   - Body: `{"id":..., "title":"<crafted payload>", ...}`
3. Attacker captures this raw body and the valid `hmac` value (both created with the app's shared `client_secret`).
4. Attacker sends the same raw body and `hmac` header to the target app's real webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` at [4](#0-3)  validates the HMAC successfully (body unmodified), then calls the handler with `shop: "victim.myshopify.com"` even though the data actually originated from the attacker's own shop, demonstrating the broken binding.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
