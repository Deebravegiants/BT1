### Title
Swap/Deposit instructions trust attacker-supplied "source" token account and delegate authority instead of binding it to the actual token-account owner - (File: program/src/processor.rs)

### Summary
`process_swap_base_in`, `process_swap_base_out`, `process_swap_base_in_v2`, `process_swap_base_out_v2`, and `process_deposit` accept a `user_source`/`user_source_coin`/`user_source_pc` token account and a separate `user_source_owner`/`source_owner_info` account purely as instruction parameters. The code only requires that the "owner" account is a transaction signer; it never checks that this signer is actually the `owner` field recorded on the source SPL token account [1](#0-0) . The subsequent SPL token transfer is then issued with that signer passed as the transfer authority [2](#0-1) . The SPL Token program itself will accept this "authority" not only if it's the true account owner, but also if it is merely an approved *delegate* with a sufficient allowance on that account, exactly like the ERC20 `transferFrom` pattern referenced in the report.

### Finding Description
The `Invokers::token_transfer` helper simply builds an `spl_token::instruction::transfer` where `owner` is whatever account the caller supplied as the "source owner" [3](#0-2) . Nowhere in `process_swap_base_in` (and equivalently in the other swap variants and in `process_deposit`) does the program compare the unpacked source token account's `owner` field against the signer that was passed in — it only verifies `user_source_owner.is_signer` [1](#0-0) , and separately checks that the source account is not literally the AMM's own vault [4](#0-3) . No check exists tying `user_source_info`'s recorded owner to `user_source_owner.key`.

Because the SPL Token program permits a transfer whose "authority" is a *delegate* with an outstanding approval (not just the literal account owner), any attacker who is—intentionally or unintentionally—an approved delegate on someone else's token account (from a leftover/failed approval, an unlimited approval, or an approval larger than what was ultimately consumed) can submit a swap where:
- `user_source_info` = the victim's token account (which still has a non-zero allowance to the attacker)
- `user_source_owner` = the attacker's own wallet, signed by the attacker
- `user_destination_info` = the attacker's own destination account

The program will happily debit the victim's account into the AMM vault and credit the swap output to the attacker's own wallet, since it never verifies `user_source_owner.key == user_source.owner`. This is the exact same bug class as the `CoverReassurance` report: an arbitrary account's approved balance can be swept by anyone holding a stale/unlimited allowance, with no way to distinguish this from a legitimate transfer.

### Impact Explanation
This allows outright theft of user funds from any token account that has a non-zero SPL delegate approval to an attacker-controlled key, redirected into the attacker's own destination account through a swap (or a deposit that mints LP tokens to the attacker). This is a direct, unauthorized transfer of user funds — a Critical/High-severity impact under the theft-of-user-funds category.

### Likelihood Explanation
Exploitation requires only that some account has previously approved a delegate allowance that is still outstanding — a common occurrence via unlimited approvals to routers/aggregators, failed transactions that didn't revoke the allowance, or partial approvals. Given how common "approve max" patterns are for SPL token accounts interacting with routers, and that any signer holding such a delegate approval can just call the standard `SwapBaseIn`/`SwapBaseOut`/`Deposit` instructions with attacker-chosen destination accounts, the likelihood of exploitation is realistic and requires no privileged access — just a single crafted transaction with attacker-chosen accounts.

### Recommendation
For every "source" token account used in `process_deposit`, `process_swap_base_in`, `process_swap_base_out`, and their `_v2` variants, explicitly verify that the supplied `user_source_owner`/`source_owner_info` account matches the `owner` field of the unpacked source token account (i.e., `user_source.owner == *user_source_owner.key`) before invoking the transfer, rather than relying solely on `is_signer` and on the implicit trust the SPL Token program places in delegated approvals.

### Proof of Concept
1. Victim `V` approves account `A` (attacker) as delegate on `V`'s coin token account for amount `X` (e.g., via a normal "approve" for a router, or a failed/partial deposit flow that left a residual allowance).
2. Attacker submits `SwapBaseIn` (or `SwapBaseOut`) with:
   - `user_source_info` = `V`'s coin token account
   - `user_source_owner` = `A`'s wallet (signer)
   - `user_destination_info` = `A`'s own pc token account
3. `process_swap_base_in` only checks `user_source_owner.is_signer` and that the source isn't literally the AMM vault [5](#0-4) ; it never checks that `A` is the actual owner of `V`'s token account.
4. `Invokers::token_transfer` issues `spl_token::instruction::transfer` with `owner = A` [2](#0-1) , which the SPL Token program accepts because `A` holds a delegate approval on `V`'s account, moving `V`'s coin into the AMM vault.
5. The corresponding output leg credits `A`'s own destination account [6](#0-5) , completing the theft of `V`'s approved balance.
