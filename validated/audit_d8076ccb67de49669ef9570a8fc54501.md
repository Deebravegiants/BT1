### Title
DirectBridge storage-deposit cache key `${contractId}${accountId}` lacks a separator, allowing cross-account cache collisions in `estimateWithdrawalFee` - (File: `packages/intents-sdk/src/bridges/direct-bridge/direct-bridge.ts`)

### Summary
`DirectBridge.getCachedStorageDepositValue` builds its LRU cache key by naively concatenating `contractId` and `accountId` with no delimiter [1](#0-0) . Because NEAR account IDs are variable-length strings drawn from the same character set for both the token contract and the destination account, two distinct `(contractId, accountId)` pairs can produce an identical concatenated string, causing `estimateWithdrawalFee` to silently reuse another pair's cached `[minStorageBalance, userStorageBalance]`.

### Finding Description
The broken equality is:
`getCachedStorageDepositValue(contractId, accountId)` should return the storage-deposit state that actually corresponds to `(contractId, accountId)`. Instead, because the cache key is `key = contractId + accountId` with no separator [2](#0-1) , any `(contractId2, accountId2)` such that `contractId2 + accountId2 === contractId + accountId` (e.g. one contract ID being a string-prefix of the other, with the remainder shifted into the account ID) will hit the same cache entry.

`estimateWithdrawalFee` calls this cache lookup with `tokenAccountId` parsed from the caller-supplied `assetId` and `args.withdrawalParams.destinationAddress` (both attacker-controlled inputs from an ordinary SDK caller) [3](#0-2) . If a prior call (by the same or a different user of a shared `DirectBridge` instance) populated the cache under a key that happens to collide with the attacker's chosen `(contractId, destinationAddress)` concatenation, `getCachedStorageDepositValue` returns the cached tuple without re-querying `getNearNep141StorageBalance`/`getNearNep141MinStorageBalance` [4](#0-3) . The resulting `minStorageBalance`/`userStorageBalance` pair, and hence `feeAmount = minStorageBalance - userStorageBalance` and `feeEstimation.amount`/`underlyingFees.storageDepositFee`, are computed from the wrong destination's storage state [5](#0-4) .

No existing guard prevents this: `validateAddress` only checks that `destinationAddress` is a syntactically valid NEAR account id, it does not prevent two distinct valid ids from colliding after concatenation with a distinct `contractId`; `withdrawalParamsInvariant` performs basic shape checks unrelated to this cache key; and `supports()`/`compareAddresses` are unrelated to storage-deposit caching. The cache key construction itself is the root cause and is not mitigated anywhere else in `DirectBridge`.

### Impact Explanation
When a false cache hit occurs, `createWithdrawalIntents` derives `storageDeposit` for the NEP-141 withdraw intent from the mis-attributed `feeEstimation` via `getUnderlyingFee(..., "storageDepositFee")` [6](#0-5) . Two failure modes follow:
- If the colliding cached entry indicates the (wrong) account is already registered/has sufficient storage, the real destination's storage requirement is understated (possibly to `0n`), so the withdraw intent under-provisions storage. This can cause the on-chain `ft_transfer_call`/registration to fail for the real destination, leaving the withdrawal stuck and requiring manual intervention.
- If the colliding cached entry indicates the wrong account needs a deposit, the user can be overcharged a storage fee they don't actually owe.

Either outcome is a fee-computation/routing error driven by another account's cached state, matching the "fee overcharge" / "withdrawal stuck until manual intervention" High-severity categories; it does not, on the evidence in this file alone, directly cause outright loss of principal, since NEAR storage-deposit shortfalls are enforced by the token contract itself, not by this SDK.

### Likelihood Explanation
Exploitability requires: (1) a shared, long-lived `DirectBridge` instance (e.g., integrator running the SDK server-side across users) so cache entries persist across calls/users within the 1-hour TTL [7](#0-6) ; (2) two NEP-141 `assetId`s whose real contract IDs, when concatenated with attacker-chosen/known destination account IDs, produce identical strings. Since both `contractId` (constrained to real supported token contracts) and `accountId`/`destinationAddress` (freely chosen NEAR account-id strings) are string-composable, such a collision is a straightforward string-construction exercise once a target `(contractId2, accountId2)` is known/guessed, not a cryptographic collision — attacker cost is low and the attack is repeatable per matching pair.

### Recommendation
Use a delimiter that cannot appear in either component, or otherwise unambiguously encode the key, e.g. `` `${contractId}:${accountId}` `` (NEAR account IDs cannot contain `:`), or key the cache with a tuple/composite structure (e.g., a nested `Map` per `contractId`) instead of raw string concatenation.

### Proof of Concept
```ts
// direct-bridge.cache-collision.test.ts
import { DirectBridge } from "./direct-bridge";

it("returns wrong cached storage state for colliding contractId+accountId concatenation", async () => {
  const bridge = new DirectBridge({ envConfig, nearProvider, solverRelayApiKey });

  // Seed cache for (contractId2="a", accountId2="bc123") -> victim's real storage state
  // key = "a" + "bc123" = "abc123"
  (bridge as any).storageDepositCache.set("abc123", [1000n, 1000n]); // victim: fully funded, fee = 0

  const getNearNep141StorageBalanceSpy = vi.spyOn(utils, "getNearNep141StorageBalance");
  const getNearNep141MinStorageBalanceSpy = vi.spyOn(utils, "getNearNep141MinStorageBalance");

  // Attacker calls with contractId1="ab", accountId1="c123"
  // key = "ab" + "c123" = "abc123" -> collides with seeded entry
  const fee = await bridge.estimateWithdrawalFee({
    withdrawalParams: {
      assetId: "nep141:ab", // parses to contractId "ab"
      destinationAddress: "c123",
      routeConfig: undefined,
    },
  });

  // Assert no RPC re-query happened (false cache hit)
  expect(getNearNep141StorageBalanceSpy).not.toHaveBeenCalled();
  expect(getNearNep141MinStorageBalanceSpy).not.toHaveBeenCalled();

  // Assert the wrong (victim's) cached value was used, giving fee = 0
  // even though the real (contractId="ab", accountId="c123") pair was never actually checked
  expect(fee.underlyingFees[RouteEnum.NearWithdrawal].storageDepositFee).toBe(0n);
});
```
This demonstrates that `estimateWithdrawalFee` for `(contractId="ab", accountId="c123")` silently consumes the cached storage state seeded for the distinct pair `(contractId2="a", accountId2="bc123")`, confirming the missing-separator cache-key collision.
