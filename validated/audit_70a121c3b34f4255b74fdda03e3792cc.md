## Title
Unprotected spot-price AMM swap for fee-token conversion enables sandwich/flash-loan value extraction - (File: `evm/src/core/EvmHost.sol`, `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, `EvmHost.fundRequest`, and `IntentGatewayV2._fillOrder`'s fee-collection path all convert a caller-supplied `msg.value` of native ETH into the protocol fee token by calling Uniswap V2's `swapETHForExactTokens` directly against the live pool reserves, with no slippage/maximum-input parameter distinct from the caller's own `msg.value` and a `deadline` set to `block.timestamp` (i.e. no real deadline protection). This is the same bug class as the Synth `realise` flash-loan finding: a value derived from instantaneous AMM spot price is used to move real funds, with no TWAP/oracle and no anti-manipulation safeguard.

In every case the router is invoked with `swapETHForExactTokens(exactFeeTokenOut, [WETH, feeToken], recipient, block.timestamp)`. The only bound on how much ETH the swap can consume is the caller's supplied `msg.value` itself — there is no independently configured `amountInMax` reflecting a fair/expected price, and `block.timestamp` as the deadline provides no MEV protection. The docs for the off-chain `quote()` helper explicitly acknowledge this class of risk exists for fee estimation ("vulnerable to sandwich attacks... use only off-chain"), but the actual on-chain payment path in `dispatch`/`fundRequest`/`_fillOrder` still executes the real swap against the manipulable spot price with no additional guard: [5](#0-4) 

Because these routers/pools are typically thin, single-purpose pools deployed just to bridge native ETH to the configured `feeToken` (as validated by `ConfiguredWrapperForkTest`), they are inexpensive to manipulate with a flash loan or a same-block sandwich, exactly the attack vector described in the reference report.

### Impact Explanation
Any unprivileged account can dispatch a `POST`/`GET` request, call `fundRequest`, or place an intent order paying with native ETH. An attacker monitoring the mempool (or bundling atomically) can:
1. Front-run the victim's `dispatch`/`fundRequest`/`fillOrder` transaction by swapping WETH→feeToken (or the reverse) in the same pool to push the spot price so that acquiring `post.fee`/`order.fees` worth of `feeToken` requires materially more ETH input than fair value.
2. The victim's transaction then executes `swapETHForExactTokens`, consuming a manipulated (inflated) amount of the victim's own ETH to obtain the exact fee-token output.
3. The attacker back-runs to reverse their initial trade, netting the price impact extracted from the victim as profit — concrete theft of user funds, directly analogous to the value extraction in the referenced report, but here realized against every unprivileged sender who dispatches a message or funds/places an order with native ETH, rather than only against LP-token holders.

Because these fee-swap pools are typically small/dedicated liquidity, they are cheap to move, making the attack economically favorable even without a flash loan, matching the report's note that "the attack does not necessarily require a flash loan."

### Likelihood Explanation
High reachability: no privileged role is required — dispatching a POST/GET request, funding a request, or filling/placing an intent order with `msg.value > 0` are all core, frequently used unprivileged entry points into `EvmHost` and `IntentGatewayV2`. The vulnerable code path executes on every native-ETH-funded call, and MEV searchers routinely automate sandwich attacks against on-chain swaps with predictable slippage bounds tied only to the transaction's own `msg.value`.

### Recommendation
- Do not derive the ETH cost of a fee-token amount purely from the live pool spot price at execution time. Either:
  - Require callers to explicitly pass a caller-chosen `amountInMax` (distinct from `msg.value`, refundable) and a real deadline, so users/integrators can bound acceptable slippage, or
  - Use a TWAP-based quote (or Chainlink price feed) to sanity-check the swap result and revert if it deviates beyond a configured tolerance from the on-chain spot price, similar to the referenced report's recommendation of TWAP/Chainlink oracles plus an anti-flash-loan formula.
- Ensure any ETH refunded by the router for unused input is returned to the original caller (`msg.sender`/`_msgSender()`), not retained by the `Host`/`IntentGatewayV2` contract.
- Consider routing large/relayer-fee-critical payments exclusively through the `feeToken` path (`dispatchWithFeeToken`) and treating the native-ETH convenience path as bounded/rate-limited, since it is the only one exposed to spot-price manipulation.

### Proof of Concept
1. Attacker identifies a pending `dispatch(DispatchPost{...})` (or `fundRequest`/`fillOrder`) transaction paying with native ETH, targeting `EvmHost`'s configured `WETH/feeToken` Uniswap V2 pool (see `HostParams.uniswapV2` at [6](#0-5) ).
2. Attacker front-runs with a large WETH→feeToken (or feeToken→WETH) swap in the same pool to shift the reserve ratio so that `swapETHForExactTokens(post.fee, [WETH, feeToken], host, block.timestamp)` requires substantially more ETH input than the pre-manipulation fair price.
3. Victim's `dispatch` transaction executes at the manipulated price, consuming the extra ETH from `msg.value` with no independent slippage cap.
4. Attacker back-runs to unwind their position, capturing the price-impact profit extracted from the victim — mirroring the flash-loan/spot-price extraction technique from the reference finding, applied here to `EvmHost.dispatch`/`fundRequest` and `IntentGatewayV2._fillOrder`'s native-ETH fee-payment path rather than to `Synth.realise`.
