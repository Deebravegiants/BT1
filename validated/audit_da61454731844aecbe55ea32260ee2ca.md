### Title
Webhook shop/topic identity binding is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC-verifiable string solely from the raw HTTP body, while the `topic`, `shop`, `api_version`, and `webhook_id` values used to route and label the webhook are read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` verifies the HMAC against the body only, then trusts `request.shop` and `request.topic` from the headers to dispatch the handler and populate `WebhookMetadata`. This is the same class of bug as the reported staking issue: a "permissive" check (HMAC over body) is treated as if it authenticates a broader claim (topic/shop identity) that it does not actually cover.

### Finding Description
`to_signable_string` returns only `@raw_body`: [1](#0-0) . The `topic` and `shop` accessors pull from HTTP headers that are never included in the signed payload: [2](#0-1) .

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` (which calls `request.to_signable_string`, i.e. body-only) and then immediately dispatches based on `request.topic` and forwards `request.shop` to the handler without any binding check between the verified body and these header-derived values: [3](#0-2) .

`HmacValidator.validate` and `validate_signature` only assert that the computed signature over `to_signable_string` matches the received `hmac` — they never reference `shop` or `topic`: [4](#0-3) .

The identity binding that should hold is: `HMAC(secret, raw_body) == received_hmac` **implies** `(topic, shop) is authentic`. In reality the equality only proves `raw_body` integrity; `topic` and `shop` are asserted, not proven, because they live in headers outside the signed string.

### Impact Explanation
The gem's own documentation states that `handler.handle` receives `data.shop` and `data.topic` as trusted, verified identifiers used by host apps to route business logic per-tenant (e.g., "which shop does this webhook belong to"). Because `shop`/`topic` are not part of the signed bytes, any component sitting between Shopify and the app's webhook endpoint that can influence headers independently of the body (e.g., a shared/misconfigured reverse proxy, a webhook-forwarding integration, or any request path where headers and body are set from different untrusted sources) can cause the library to report a different `shop` or `topic` than the one whose signature was actually verified. This breaks the cross-tenant boundary the gem is meant to enforce (`shop` is the tenant identity used to scope subsequent handling), which maps to the "cross-tenant access" / scope-check-bypass class of impact called out in the rules.

This is analogous to the reported bug: a check that is supposed to gate/attest a specific claim (rewards tied to non-expired stake; webhook attribution tied to a specific shop/topic) is computed over a narrower scope (round eligibility ignoring expiry; body bytes ignoring headers) than the claim it is used to authorize.

### Likelihood Explanation
Exploitation requires a scenario where an unprivileged actor can present headers that diverge from the signed body while keeping a body+HMAC pair that Shopify actually signed — realistically only in deployments with header-rewriting proxies, or in test/replay harnesses that don't re-validate that headers match the originally delivered request. This is a real gap in the library's own trust boundary (host apps cannot detect it by following the documented API), but it depends on the surrounding request pipeline permitting header/body divergence, so likelihood is environment-dependent rather than trivially exploitable over the open internet against a stock deployment.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable/verifiable string (or otherwise cryptographically bind them to the body) so that `HmacValidator.validate` attests to the full tuple `(shop, topic, body)` rather than `body` alone. At minimum, document and enforce that the webhook handler must independently verify `shop` against session/tenant storage before trusting it for tenant-scoped operations.

### Proof of Concept
Conceptual (cannot be executed without a live proxy/harness):
1. Capture a legitimate webhook POST with `raw_body = B`, `X-Shopify-Hmac-Sha256 = HMAC(secret, B)`, `X-Shopify-Shop-Domain = shop-a.myshopify.com`, `X-Shopify-Topic = orders/create`.
2. Construct a new request with the same `raw_body = B` and same `hmac` header, but replace `X-Shopify-Shop-Domain` with `shop-b.myshopify.com` (a different tenant) and/or `X-Shopify-Topic` with a different topic value.
3. Call `ShopifyAPI::Webhooks::Registry.process(ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: tampered_headers))`.
4. `Utils::HmacValidator.validate(request)` still returns `true` because it only checks `B` against the HMAC as shown at [5](#0-4) , and the handler is invoked with `shop: "shop-b.myshopify.com"` / the tampered topic, as shown at [6](#0-5) , even though only the body was ever cryptographically verified.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
