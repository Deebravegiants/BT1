### Title
Passphrase cache does not enforce the user-configured auto-lock TTL while the session is not yet marked inactive — stale `maxTtl` window instead of updated `ttl` ([File: features/application/src/modules/passphrase-cache.ts])

### Summary
`PassphraseCache` caches the wallet's decrypted passphrase in session storage with an expiry governed by two different, inconsistently maintained time windows: `addedAt + maxTtl` (used while the session has not been marked "inactive") and `inactiveAt + ttl` (used only after an idle/inactivity event has been recorded). Similar to the Deli-Swap `_upsertIncentive()` bug — where `_updatePoolByPid()` was skipped on one code path, leaving `lastUpdated` stale and causing the next elapsed-time computation to use the wrong time base — `changeTtl()` here updates the TTL value used only in the *inactive* branch, while the *active* branch continues to validate the cached passphrase against the fixed `maxTtl` set at construction time, never the user's newly configured shorter `ttl`.

### Finding Description
`PassphraseCache.get()` decides whether to hand back the cached plaintext passphrase using two mutually exclusive branches: [1](#0-0) 

- If `inactiveAt` is set, validity is `inactiveAt + ttl > Date.now()` (uses the live `TTL_KEY` value).
- Otherwise (session considered "active"), validity is `addedAt + this.#maxTtl > Date.now()` — this **always** uses the fixed `maxTtl` computed once in the constructor from static config, never the dynamically configurable auto-lock timer. [2](#0-1) 

`changeTtl()` is the only path that updates the effective TTL after the passphrase has already been cached: [3](#0-2) 

It writes the new value to `autoLockTimerAtom` and, if a passphrase is currently cached, updates `TTL_KEY` in storage and reschedules the inactivity-clear alarm — but it never touches `addedAt`, and it has zero effect on the "active" branch of `get()`, which is hard-bound to `this.#maxTtl` (a constant derived from `config.maxTtl`, defaulting to 60 minutes) set only in the constructor: [4](#0-3) [5](#0-4) 

This mirrors the root cause of the report exactly: a piece of state that should be refreshed/consistently reflected whenever the "rate"/window configuration changes (`_updatePoolByPid` in the original; the effective TTL boundary here) is instead only updated on one conditional branch (`inactiveAt`/inactive-session path via `changeTtl`), leaving the other branch (`addedAt`/active-session path) to keep using a stale, wider time window (`maxTtl` fixed at construction) that does not reflect the user's newly configured, shorter security setting.

### Impact Explanation
The passphrase cache holds the plaintext master secret that unlocks the wallet and authorizes signing — this is the strongest possible secret in the trust model. A user who reduces the auto-lock timer (e.g., to protect against a shared/public machine or after realizing their default timeout is too long) expects the cached secret to expire quickly. Because the "active" branch of `get()` is permanently pinned to `maxTtl` (defaulting to 60 minutes) regardless of the configured `ttl`, the cached passphrase remains retrievable from session storage for up to `maxTtl` after being cached, as long as no inactivity event has fired to populate `INACTIVE_AT_KEY`. An attacker who gains local/transient access to the browser extension's session storage during that window (e.g., a shared computer scenario, or any local vector capable of reading extension storage) can retrieve the plaintext wallet passphrase well beyond the user's intended, shorter protection window, leading to full unauthorized wallet unlock and signing capability.

### Likelihood Explanation
Exploitation requires only that (a) passphrase caching is enabled (`cachePassphrase` config), (b) the user has configured a shorter auto-lock timer than `maxTtl` believing it limits exposure, and (c) the attacker obtains local read access to the extension's session storage before an idle event has fired. No privileged keys or remote compromise are needed — this is a pure logic/timing-window inconsistency reachable through normal user settings changes, not a hypothetical edge case.

### Recommendation
Make the "active" branch validity check consistent with the currently configured TTL instead of the static `maxTtl`, and have `changeTtl()` unconditionally refresh whichever time base is relevant to the currently cached passphrase (both `addedAt`-relative and `inactiveAt`-relative checks), analogous to calling `_updatePoolByPid()` unconditionally before applying the new rate in the original fix. Concretely, `get()` should bound the active-session grace period by `min(configuredTtl, maxTtl)`, and `changeTtl()` should reset `addedAt` (or otherwise recompute the active-session expiry) whenever a passphrase is currently cached, not just refresh `TTL_KEY` for the inactive branch.

### Proof of Concept
1. Enable `cachePassphrase` with default `passphraseCacheMaxTtl` (60 minutes) via `features/application/src/index.ts` config. [6](#0-5) 
2. Unlock the wallet — `PassphraseCache.set()` stores `passphrase`, `addedAt = Date.now()`, `ttl = autoLockTimerAtom` (e.g., default long value). [7](#0-6) 
3. Immediately call `changeTtl(1 minute)` to tighten the auto-lock timer for security. `autoLockTimerAtom` and `TTL_KEY` are updated to 1 minute, but `addedAt` is untouched. [3](#0-2) 
4. Keep the session "active" (no inactivity/idle callback fires `scheduleClear()` to set `INACTIVE_AT_KEY`).
5. Wait more than 1 minute (but less than 60 minutes) — call `get()`. Since `inactiveAt` is unset, the check falls to `addedAt + maxTtl > Date.now()`, which is still true, so the plaintext passphrase is returned/remains cached in storage — despite the user having configured a 1-minute auto-lock timer.

Note: I was unable to fully trace, from the indexed context alone, every call site that invokes `PassphraseCache.scheduleClear()` (e.g., the exact idle/activity-detection wiring in `features/application/src/modules/application.ts` or `plugins/lifecycle.ts`), so confirmation of precisely which real-world conditions delay the "inactive" marking should be verified in a full Devin session with complete repository access.

    const [passphrase, addedAt, inactiveAt, ttl] = (await this.#storage.batchGet([
      PASSPHRASE_KEY,
      ADDED_AT_KEY,
      INACTIVE_AT_KEY,
      TTL_KEY,
    ])) as [string, number, number, number]

    if (passphrase) {
      if (inactiveAt) {
        if (inactiveAt + ttl > Date.now()) {
          this.#logger.log('fetched cached passphrase, in activity period')
          return passphrase
        }
      } else if (addedAt + this.#maxTtl > Date.now()) {
        this.#logger.log('fetched cached passphrase')
        return passphrase
      }

      this.#logger.log('fetched expired passphrase, clearing and preventing unlock')
      void this.clear()
    }

  async changeTtl(ttl: number) {
    const newTtl = Math.min(this.#maxTtl, ttl)

    await this.#autoLockTimerAtom.set(newTtl)

    const passphrase = await this.#storage.get(PASSPHRASE_KEY)
