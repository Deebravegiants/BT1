Webhook `shop-domain`, `topic`, `webhook_id`, and `api_version` are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers and are never included in the HMAC-verified data. `Registry.process` trusts these header-derived fields and forwards them unchanged into the handler as the tenant/topic identity of the event.

### Finding Description
`HmacValidator.validate` only proves that `computed_signature == received_signature` where `computed_signature` is derived from `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` is defined to be just the raw body: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from HTTP headers with no cryptographic binding to the body/HMAC at all: [3](#0-2) [4](#0-3) 

`Registry.process` verifies the HMAC (which only covers the body) and then unconditionally uses `request.shop`, `request.topic`, and `request.webhook_id` — none of which were part of the signed data — to construct the metadata handed to the app's handler: [5](#0-4) 

The identity binding that should hold is: `shop_attributed_to_event == shop_that_produced_and_signed_the_body`. Because `shop` (and `topic`/`webhook_id`) sit outside the HMAC, that equality is never enforced — only "the body bytes are unmodified" is proven, not "these header values belong to this body."

### Impact Explanation
A merchant who has legitimately installed the app is a valid HMAC holder for their own shop's webhooks (Shopify signs their webhook payloads with the app's shared `client_secret`, which every merchant's webhook traffic uses). Such a merchant can capture one of their own genuine `(raw_body, hmac)` pairs and replay it to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header with another tenant's shop domain or a different topic/id. `HmacValidator.validate` still succeeds because it only checks the body against the same secret, and `Registry.process` will invoke the handler believing the event came from the victim shop/topic. Any app logic keyed off `WebhookMetadata#shop` (e.g., updating per-shop state, crediting billing events, redirecting `shop/redact`/`customers/redact` compliance actions, or writing tenant-scoped records) can be corrupted or misattributed to another tenant — a cross-tenant integrity/confidentiality violation using no privileged credentials beyond the attacker's own valid app installation.

### Likelihood Explanation
The attack requires no secret-key knowledge, only a single legitimate webhook delivery to the attacker's own shop (trivial to obtain by installing the app and triggering any subscribed event) and a raw HTTP replay to the app's public webhook route with a modified header — well within reach of any unprivileged internet-facing app installer.

### Recommendation
Include `shop`, `topic`, and (if relevant) `webhook_id`/`api_version` in the HMAC-signed payload used by `to_signable_string`, or otherwise cryptographically bind these header values to the signed body (e.g., use Shopify's documented `X-Shopify-Hmac-Sha256` scheme strictly as documented — verify that the header values match those Shopify actually sent for that body — and reject/flag any mismatch rather than trusting arbitrary header content once the body's HMAC checks out).

### Proof of Concept
1. Install the app on shop `attacker.myshopify.com`; trigger a webhook (e.g., `orders/create`) and capture the delivered `raw_body` and `x-shopify-hmac-sha256` header — both valid and verifiable with the app's `client_secret`.
2. Replay the identical `raw_body`/HMAC to the app's webhook endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com` (and/or change `x-shopify-topic`).
3. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-199`) calls `HmacValidator.validate`, which passes because it only checks the (unchanged) raw body. The handler then receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"`, despite the payload never actually originating from or being signed for that shop.
