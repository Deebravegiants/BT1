### Title
Hardcoded fallback signing secret for telemetry relayer authentication - (File: `tesseract/messaging/telemetry/src/main.rs`)

### Summary
The telemetry server's socket.io relayer-authentication check falls back to a fixed, publicly-known secret (`"1234567890abcdef1234567890abcdef1234567890abcdef1234567890abcdef"`) whenever `TELEMETRY_SECRET_KEY` is not baked in at compile time, allowing anyone to forge valid ECDSA signatures and register as an "authenticated" relayer on any state machine.

### Finding Description
`on_connect` derives an `ecdsa::Pair` from bytes obtained via `option_env!("TELEMETRY_SECRET_KEY")`, falling back to the literal hex string `1234567890abcdef1234567890abcdef1234567890abcdef1234567890abcdef` when the compile-time environment variable is unset: [1](#0-0) 

It then treats a valid signature over `data.metadata` under this key pair as proof of authenticity, inserting the claimed `(StateMachine, H160)` relayer address into the shared `AppState`: [2](#0-1) 

Because this fallback secret is a hardcoded literal committed to the source tree (identical to the CVE-2026-85391 pattern of a hardcoded signing secret in a public repo), any deployment that does not set the `TELEMETRY_SECRET_KEY` build-time variable uses this exact known key. An unauthenticated actor with network access to the telemetry socket.io endpoint can derive the same `ecdsa::Pair` from the public bytes, sign arbitrary `(StateMachine, H160)` metadata, and be accepted as an "online relayer" for any network without holding any real relayer key. The `/:network` HTTP route then serves this attacker-controlled `H160` list to any caller as the set of currently-online relayers for that `StateMachine`: [3](#0-2) 

### Impact Explanation
The telemetry service is the mechanism by which Hyperbridge advertises which relayer addresses are currently online per state machine. Forging entries lets an attacker inject arbitrary/spoofed relayer addresses (including addresses they do not control, or addresses associated with victim relayers) into this "online" list, or flood/poison it, which can mislead operators, monitoring systems, or any downstream logic that trusts this endpoint to decide relayer liveness/selection. Since the trust anchor (the signing key) is a hardcoded value in the public repository rather than a per-deployment secret, this is a systemic, not deployment-specific, weakness — every default deployment that forgets to override `TELEMETRY_SECRET_KEY` at build time shares the exact same compromised key.

### Likelihood Explanation
High if the build-time env var is not overridden: `option_env!` only substitutes a value if `TELEMETRY_SECRET_KEY` was set in the build environment at compile time; if operators run the published binary/image as-is (the common path, analogous to using a shipped `docker-compose.yml`), the hardcoded fallback is what's compiled in, and the secret is visible to anyone reading the source. No authentication bypass beyond reading public source code and computing an ECDSA signature is required.

### Recommendation
Remove the hardcoded fallback entirely; fail fast (`expect`/`panic` at startup, or refuse to bind) if `TELEMETRY_SECRET_KEY` is not supplied, and require it to be injected as a genuine runtime secret (e.g., via `std::env::var` read at process start from a secrets manager) rather than a compile-time literal with a public default. Rotate the key and audit any indexed/aggregated relayer-liveness data collected via this endpoint.

### Proof of Concept
1. Read the public source to obtain the fallback secret: `1234567890abcdef1234567890abcdef1234567890abcdef1234567890abcdef`.
2. Locally construct `sp_core::ecdsa::Pair::from_seed_slice(&from_hex(secret))` as done in [4](#0-3) .
3. Craft `Message { metadata: vec![(StateMachine::Evm(<any_chain_id>), H160::from(<any_address>))], signature: vec![] }`, sign `metadata.encode()` with the derived pair, and connect to the telemetry socket.io namespace with this payload as the `auth` object (mirrors the existing test harness at [5](#0-4) ).
4. The server accepts the forged signature, adds the attacker-chosen address as "online" for the chosen state machine, and it becomes visible to anyone querying `GET /:network`.

Note: I was unable to fully trace whether/where this telemetry "online relayers" list is consumed by other production paths (e.g., solver/relayer selection, fee routing) beyond the standalone `telemetry` binary itself — no other crate in the repo appears to import `telemetry_server` as a client, based on available search results. If this endpoint is purely advisory/monitoring with no on-chain or fund-moving consequence, the impact would be closer to "monitoring" and out of the requested scope; this could not be conclusively confirmed with the tools available.

async fn online(
	Path(network): Path<String>,
	state: AxumState<SharedAppState>,
) -> Result<Json<Vec<H160>>, AppError> {
	let network = StateMachine::from_str(&network).map_err(|err| anyhow!("{err}"))?;
	let relayers = state
		.read()
		.await
		.networks
		.get(&network)
		.map(|map| map.keys().cloned().collect::<Vec<_>>())
		.unwrap_or(vec![]);

	Ok(Json(relayers))
}
