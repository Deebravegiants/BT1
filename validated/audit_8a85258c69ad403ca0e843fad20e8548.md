## Title
Webhook `shop` domain is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes/verifies the webhook HMAC over the raw request body only, while the `shop` (and `topic`/`webhook-id`) values used downstream by the registry/handler are read straight from unauthenticated HTTP headers. This breaks the identity binding `hmac_covers(bytes) == bytes_used_to_identify_tenant`, allowing a party who legitimately receives one authentic webhook (e.g., from their own shop where the app is installed) to replay the exact body+HMAC pair while substituting an arbitrary `shop-domain` header, causing the app to process the webhook under a different, attacker-chosen shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`Webhooks::Request#shop` (and `topic`, `webhook_id`, `api_version`) are pulled straight from headers, which are not part of the signed material: [2](#0-1) 

`Registry.process` verifies the HMAC over the request (which, per above, only binds the body) and then unconditionally trusts `request.shop` to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` performs a byte-exact HMAC check, but the bytes it verifies (`raw_body`) are not the same bytes the library uses to identify the tenant (`shopify-shop-domain` header): [4](#0-3) 

Because every shop that installs the app shares the same `api_secret_key`-derived HMAC, a valid `(body, hmac)` pair obtained from one authentic webhook delivery (e.g., to the attacker's own shop, which they legitimately control) remains valid for *any* `shop-domain` header value the attacker chooses to attach. The equality the code implicitly relies on — "shop header value == shop that produced this signed body" — does not hold, since the header is entirely outside the signed scope.

### Impact Explanation
If a host application uses `WebhookMetadata#shop` (as returned by this gem) to select which tenant's data to update/create/delete — a standard multi-tenant webhook handling pattern — an attacker who is a genuine (if malicious) app-installing merchant can forge webhook deliveries that appear to originate from a *different* shop, since the HMAC check passes and the shop value is taken on faith. This is a cross-tenant data confusion/access vector: attacker-controlled webhook payloads (order data, GDPR payloads, uninstall events, etc.) can be attributed to and processed against a victim shop's tenant context inside the host application, without needing the app's `api_secret_key`, access token, or any credential belonging to the victim.

### Likelihood Explanation
Likelihood is high for any host application that trusts `data.shop` from `WebhookMetadata` to key its tenant storage/lookup (a common and reasonable assumption given the field is only exposed after "HMAC validation" succeeds). The attacker only needs to install the app on a shop they control (an ordinary, unprivileged action) to obtain one authentic `(body, hmac)` pair, then can replay it with an arbitrary `shop-domain` header value.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` header values in the signable string (or otherwise cryptographically bind them, e.g. by deriving/verifying a per-shop signature, or by requiring host apps to independently confirm the shop's install/session state) rather than only signing the raw body in `Webhooks::Request#to_signable_string`. At minimum, document loudly that `WebhookMetadata#shop` is unauthenticated and must not be trusted as a tenant key without cross-checking against a known, installed shop record.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and configures a webhook subscription.
2. Shopify delivers a legitimate webhook: body `B`, header `x-shopify-hmac-sha256: HMAC(secret, B)`, header `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker replays this exact request to the app's webhook endpoint but changes only the header:
   `x-shopify-shop-domain: victim.myshopify.com` — the body `B` and `x-shopify-hmac-sha256` are left unchanged.
4. `Utils::HmacValidator.validate` succeeds because it only checks `B` against the unchanged HMAC (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
5. `Registry.process` builds `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`) and invokes the app's handler as if the event genuinely came from `victim.myshopify.com`.
