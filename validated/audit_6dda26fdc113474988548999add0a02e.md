### Title
`placeOrder()` fee-swap via `swapETHForExactTokens` has no enforced price bound, enabling sandwich/MEV extraction of user's escrowed ETH - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.placeOrder()` performs an on-chain, unprotected DEX swap to acquire the fee token whenever a user pays `order.fees` in native ETH, mirroring the exact bug class from the SponsorVault finding: swapping through an external exchange with no meaningful slippage/price bound, letting a searcher sandwich the transaction and extract value from the user.

### Finding Description
When `order.fees > 0` and the caller sent native ETH (`msgValue > 0`), the contract swaps ETH for a fixed amount of the fee token via UniswapV2: [1](#0-0) 

```solidity
if (order.fees > 0) {
    address feeToken = IDispatcher(hostAddr).feeToken();
    if (msgValue > 0) {
        address uniswapV2 = IDispatcher(hostAddr).uniswapV2Router();
        address WETH = IUniswapV2Router02(uniswapV2).WETH();
        address[] memory path = new address[](2);
        path[0] = WETH;
        path[1] = feeToken;
        uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msgValue}(
            order.fees, path, address(this), block.timestamp
        );
        msgValue -= amounts[0];
    } else {
        IERC20(feeToken).safeTransferFrom(msg.sender, address(this), order.fees);
    }
    _orders[commitment][TRANSACTION_FEES] = order.fees;
}
```

This is `swapETHForExactTokens(order.fees, path, address(this), block.timestamp)` called with the entire remaining `msgValue` as `msg.value`. In UniswapV2Router semantics, the caller's `msg.value` acts as the implicit `amountInMax` for an exact-output swap: the router will accept spending up to the full `msgValue` to obtain the fixed `order.fees` output, refunding only the unspent remainder. There is no protocol- or user-supplied ceiling on the *effective exchange rate* — no quote-derived `amountInMax` tighter than the full leftover balance, and `deadline = block.timestamp` provides no MEV protection since it's satisfied trivially within the same block.

This is functionally identical to the SponsorVault `reimburseLiquidityFees()` bug: an external token-exchange call is made to fulfill a fixed obligation, using the exchange's live price with no bound tying the swap to a fair/expected rate.

### Impact Explanation
An attacker observing a pending `placeOrder()` transaction with a native-ETH fee payment can sandwich it: buy the fee token (or sell WETH into the pool) before the victim's transaction to inflate the effective ETH price of the fixed `order.fees` output, then reverse the trade after. Because the router's only constraint is `msgValue` (which the user typically over-supplies to guarantee the swap succeeds, per the SDK's `nativeFee` buffering logic), the swap will consume up to that entire buffer at the manipulated price rather than reverting, silently transferring the price-impact loss from the user to the attacker. This results in direct fund loss for users placing orders with native-token fee payment — a concrete theft of value via MEV, matching the accepted analog bug class.

### Likelihood Explanation
Any unprivileged user calling `placeOrder()` with `order.fees > 0` and paying in native ETH triggers this path; no special permissions are required. Sandwiching this specific swap is straightforward for any searcher watching the public mempool/bundler feed, and the exact-output amount (`order.fees`) plus a generous `msgValue` buffer (as documented in the SDK's `quoteOrderFees`/`nativeFee` flow) gives the attacker a wide, predictable window to extract value. Likelihood is high whenever this fee-payment path is used with meaningful ETH amounts.

### Recommendation
Compute an on-chain `amountInMax` bound from a trusted price source (e.g., `priceOracle` already wired into `Params`, similar to `SimplexPaymaster.swapAndDeposit`'s oracle-derived `amountOutMin`/slippage check) rather than implicitly allowing the router to spend the entire `msgValue`. Enforce a tight, oracle- or off-chain-quote-derived maximum input (or minimum output for exact-in variants) and revert if the live pool price deviates beyond an acceptable slippage tolerance, and use a short real deadline rather than `block.timestamp`.

### Proof of Concept
1. Attacker monitors the mempool/bundler for a `placeOrder()` call with `order.fees > 0` and a native `msgValue` sent for the fee swap.
2. Front-run: attacker swaps WETH→feeToken (or otherwise moves the pool) to spike the WETH price of `feeToken` in the UniswapV2 pool referenced by `IDispatcher(hostAddr).uniswapV2Router()`.
3. Victim's `placeOrder()` executes `swapETHForExactTokens(order.fees, [WETH, feeToken], address(this), block.timestamp){value: msgValue}` — since the only constraint is the full `msgValue`, the manipulated price is accepted and a much larger `amounts[0]` (ETH spent) is deducted from `msgValue`.
4. Back-run: attacker reverses the pool manipulation, capturing the price-impact profit extracted from the victim's over-spent ETH.
5. Victim receives a smaller-than-expected ETH refund (`_sendValue(msg.sender, msgValue)` at line 396) — the difference is the attacker's MEV profit. [2](#0-1)
