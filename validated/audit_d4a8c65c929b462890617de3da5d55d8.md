## Finding

The vulnerability described is real: `DeleteKey` cleanup only purges **requests originated by** the removed key, not **confirmations cast by** that key on other, still-pending requests. Since `confirm()` never re-validates that each already-stored public key in a request's confirmation set is still a currently valid signer, a stale confirmation from a removed key still counts toward the `num_confirmations` threshold.

### Root cause

`confirm()` checks the threshold purely by set cardinality, with no revalidation of the keys already stored in the set: [1](#0-0) 

`DeleteKey` execution only cleans up requests **created** by the removed key (`r.signer_pk == pk`, the request's originator), and clears `num_requests_pk` for that key — it never scans `self.confirmations` to strip the removed key out of confirmation sets belonging to other requests it had merely confirmed: [2](#0-1) 

So if key `A` confirms request `R` (created by key `X`), and is later removed from the account via a separate `DeleteKey` request, `R`'s confirmation set (`self.confirmations[R]`) still contains `A`'s public key indefinitely. When subsequent valid signers confirm `R`, `A`'s stale vote is silently counted toward `self.num_confirmations`, effectively lowering the real quorum of currently-authorized keys required to execute the request.

### Impact

This breaks the k-of-n authorization guarantee of the multisig: a request can execute (e.g., a `Transfer` moving funds, or an `AddKey`/`FunctionCall` action) with fewer *currently valid* signer confirmations than `num_confirmations` requires, because one or more votes originate from keys already revoked on-chain. This matches "High: Unauthorized execution, confirmation bypass... that lets an unprivileged user perform actions beyond intended authority."

### Proof of concept (conceptual unit test)

1. Deploy `MultiSigContract::new(3)` with on-chain full-access keys `X`, `A`, `B`, `C`.
2. `X` calls `add_request(Transfer{...})` → `request_id = R` (not auto-confirmed by `X`... or `X` confirms too, doesn't matter as long as `< 3`).
3. `A` calls `confirm(R)` → `confirmations[R] = {A}` (count 1, below threshold 3).
4. Separately, `X`/`B`/`C` create+confirm a `DeleteKey{public_key: A}` request against `receiver_id = current_account_id`, reaching threshold and executing — this calls `promise.delete_key(A)` and removes any requests `A` had *created*, but `R` (created by `X`) is untouched; `confirmations[R]` still contains `A`.
5. `B` calls `confirm(R)` → count becomes 2, stored: `{A, B}`.
6. `C` calls `confirm(R)` → count reaches `2 + 1 = 3 >= 3`, `execute_request` fires the `Transfer` — even though only `X`(implicit)/`B`/`C` are truly still-authorized signers and `A`'s vote is stale.

A concrete Rust test would assert that after step 4, `A`'s public key is removed on-chain, then perform steps 5–6, and show `execute_request` still fires (funds move) using the stale confirmation — demonstrating the quorum was met with fewer than `num_confirmations` currently-valid signers.

### Recommendation

When executing `DeleteKey`, also scan all pending `self.confirmations` entries (not just requests authored by the removed key) and remove the deleted public key from every confirmation set. Alternatively/additionally, `confirm()` could validate, at the point a threshold is reached, that all keys in the confirmation set are still present among the account's authorized keys before calling `execute_request`.     pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
