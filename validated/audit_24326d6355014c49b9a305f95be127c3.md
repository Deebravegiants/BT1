### Title
Webhook shop-domain field is trusted for tenant identification without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then hands `request.shop` (an unauthenticated HTTP header value) to the app's handler as the tenant identifier.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `shop`, `topic`, `webhook_id`, `api_version` are all read straight from HTTP headers with no cryptographic binding to the signed content [2](#0-1) . `Utils::HmacValidator.validate` only recomputes the HMAC over `verifiable_query.to_signable_string` (i.e., the raw body) and compares it to the `hmac` header [3](#0-2) . `Registry.process` raises only if that body HMAC check fails, then immediately builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` and dispatches it to the registered handler [4](#0-3) .

The binding that should hold is: `hmac_verified_bytes == tenant_identifying_bytes`. Here, `hmac_verified_bytes` = raw body only, while `tenant_identifying_bytes` = `shop` header, which is disjoint from the signed content. Because the HMAC secret (`api_secret_key`/`client_secret`) is shared across every shop that has the app installed, any shop that installs the app can receive a genuine webhook from Shopify for its own store — a real `raw_body` + valid `hmac` pair signed with the app's shared secret. That attacker-controlled tenant can then replay the exact same body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header with a victim shop's domain. `HmacValidator.validate` still succeeds because it never inspects the shop header, and `Registry.process` forwards the forged `shop` value straight to the handler as trusted tenant data.

### Impact Explanation
Any host application that follows the gem's own documented pattern — trusting `WebhookMetadata#shop` returned by `Registry.process` to select which merchant's session/data to act on — can be made to apply another merchant's webhook body under an attacker-chosen tenant. This is a cross-tenant data-integrity break sourced entirely from this gem's `Request`/`HmacValidator`/`Registry` code: the "authenticated shop" (bytes verified by HMAC) and the "shop used for tenant lookup" (bytes taken from an unauthenticated header) are not the same, satisfying the report's identity-binding-break pattern and the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only an internet-accessible install of the target app on any shop the attacker controls (a normal, unprivileged onboarding step for any Shopify app), from which the attacker legitimately receives real webhook deliveries with valid HMACs signed by the shared `api_secret_key`. No access token, `api_secret_key` value, or privileged account is needed — only the ability to capture one webhook POST and replay it with a modified header, which any unprivileged user with a free/dev shop can do.

### Recommendation
- Short term: include `shop` (and ideally `topic`/`webhook_id`) in the HMAC-covered signable content, or independently verify the `X-Shopify-Shop-Domain` header against a value derived from data that is inside the signed body/lookup path, before constructing `WebhookMetadata`.
- Long term: document/enforce that consumers must not trust `WebhookMetadata#shop` unless the gem cryptographically binds it to the signature; add regression tests that assert `Registry.process` rejects a request whose body+hmac pair was replayed under a different shop header than the one used at delivery time.

### Proof of Concept
1. Attacker installs the victim app on their own shop `attacker.myshopify.com`; the app registers a webhook, e.g. `orders/create`.
2. Attacker triggers that webhook and captures the raw POST: body `B`, and headers `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` computed with the app's shared `api_secret_key`), `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: orders/create`.
3. Attacker resends the identical request to the app's webhook endpoint, changing only `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body normally [5](#0-4) ; `HmacValidator.validate` recomputes HMAC over `B` only, matches `H`, and returns `true` [3](#0-2) .
5. `Registry.process` proceeds and calls the handler with `shop: "victim.myshopify.com"` and the attacker's own order body, causing the host app to process attacker-controlled data under the victim's tenant identity [4](#0-3) .

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
