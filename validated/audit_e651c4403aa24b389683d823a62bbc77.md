### Title
Case-sensitive `compareAddresses` self-address check bypassed by uppercase BTC bech32 address, later collapsed to the token address by `deriveOmniWithdrawIntentParams` - (File: packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts)

### Summary
`OmniBridge.validateWithdrawal` guards against self-collision by comparing `args.destinationAddress` to the bridged token's own destination-chain address with `compareAddresses`, but for Bitcoin this comparison is a literal, case-sensitive `a === b` check [1](#0-0) . `deriveOmniWithdrawIntentParams`, called later to build the actual signed recipient, lowercases any `bc1`-prefixed address case-insensitively before embedding it as `recipient` [2](#0-1) . The validation step's canonicalization is weaker than the recipient-construction step's, allowing a BIP-173-valid, all-uppercase `BC1...` address that differs byte-for-byte from `destTokenAddress` to pass the guard and then normalize to exactly `destTokenAddress` when embedded into the signed intent.

### Finding Description
The broken equality: the string validated by `validateWithdrawal`'s self-collision guard (`args.destinationAddress` as supplied, compared via `compareAddresses(destTokenAddress, args.destinationAddress, "bitcoin")` at [3](#0-2) ) is not guaranteed to equal the string embedded as `recipient` in the signed `ft_withdraw` intent produced by `deriveOmniWithdrawIntentParams` and `createWithdrawIntentsPrimitive` [4](#0-3) [5](#0-4) .

Root cause: `compareAddresses` for `Chains.Bitcoin` (and other UTXO/base58 chains) does a raw case-sensitive string comparison with no bech32 canonicalization [1](#0-0) , whereas `deriveOmniWithdrawIntentParams` explicitly lowercases any address matching `/^bc1/i` (case-insensitive match, case-normalizing transform) before using it to build `recipient` [6](#0-5) . BIP-173 bech32 permits an address to be entirely uppercase (case must be internally consistent, but either case is valid), so `validateAddress` — which only needs to validate bech32 well-formedness — can accept an all-uppercase `BC1...` string that is a case-only variant of the token's canonical lowercase destination address.

Exploit flow:
1. Attacker (an ordinary user) determines/obtains the canonical destination-chain address of the bridged token (`destTokenAddress`, returned lowercase by `getBridgedToken`/`getAddress`) for the asset being withdrawn.
2. Attacker calls a withdrawal with `destinationAddress` equal to that same address but re-cased to all-uppercase (`BC1Q...`), which is a bech32-valid string and passes `validateAddress`.
3. `validateWithdrawal`'s guard runs `compareAddresses(destTokenAddress, args.destinationAddress, "bitcoin")`, which is `a === b` — the lowercase canonical string never equals the uppercase attacker string, so the guard does not throw and the withdrawal is accepted as valid [3](#0-2) .
4. `createWithdrawalIntents` subsequently calls `deriveOmniWithdrawIntentParams`, whose BTC branch matches `/^bc1/i` and lowercases the address, producing a `recipient` that is now byte-identical to `destTokenAddress` [2](#0-1) .
5. The signed intent's `ft_withdraw.msg.recipient` (embedded via `createWithdrawIntentsPrimitive`) equals the token's own destination-chain address, so funds are routed to the bridge/token's own account rather than the user-intended distinct address [7](#0-6) .

Why existing guards fail: `validateAddress` only checks bech32 well-formedness, not case-canonical equality to any specific address; `compareAddresses` for Bitcoin performs no normalization at all (unlike EVM chains, which use `getAddress` for checksum normalization, or Aptos/Starknet, which have a dedicated hex-normalizing comparator) [8](#0-7) .

### Impact Explanation
If exploitable, the signed `ft_withdraw` intent's `recipient` would resolve to the token's own destination-chain (vault/connector) account rather than a genuinely distinct address the user controls, i.e., funds routed to the wrong destination with no recovery path — matching the Critical severity bar (funds delivered to a wrong address/contract, unauthorized by user intent, no recovery).

### Likelihood Explanation
This requires: (1) a Bitcoin-route withdrawal, (2) the attacker knowing/guessing the exact canonical `destTokenAddress` for the asset (obtainable via the same `getBridgedToken` RPC call `validateWithdrawal` itself uses, which is a public NEAR view call), and (3) constructing a same-address, different-case (all-uppercase, BIP-173-valid) bech32 string. Whether this is truly reachable depends on two unverified facts I could not fully confirm from the available code: (a) whether `validateAddress`'s Bitcoin/bech32 validation actually accepts an all-uppercase `BC1...` string as valid (I could not read the full `validateAddress.ts` implementation to confirm this), and (b) whether `destTokenAddress` for a BTC-destination route is ever a real, funds-holding bech32 address (rather than a special non-address token identifier) that could plausibly be the same address the attacker's own withdrawal would otherwise target. Given the code comment in `omni-withdraw-params.ts` explicitly acknowledging "Omni contract only accepts lowercase bech32 addresses; uppercase/mixed-case bech32 is spec-valid but rejected on-chain," it strongly suggests uppercase bech32 does pass whatever upstream format checks exist and is deliberately normalized only at the derivation step — supporting that the ordering gap is real, but I could not fully trace `validateAddress.ts`'s internal logic to close this gap with certainty.

### Recommendation
Make `compareAddresses`'s Bitcoin case perform the same canonicalization `deriveOmniWithdrawIntentParams` uses before comparing (lowercase any `bc1`-prefixed address, and/or canonicalize both sides consistently for base58 legacy addresses too), and/or perform the self-collision check in `validateWithdrawal` against the same canonicalized address (i.e., derive/lowercase `args.destinationAddress` once, and pass that single canonical value to both `compareAddresses` and to `deriveOmniWithdrawIntentParams`) so validation and signing operate on identical byte-for-byte strings.

// vitest, mocking only the HTTP/RPC calls that back getBridgedToken/getTokenDecimals/getFee
it("bypasses self-collision guard via uppercase BTC bech32 case variant", async () => {
  const destTokenAddress = "bc1qxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx"; // canonical, lowercase
  const attackerDestination = destTokenAddress.toUpperCase(); // BIP-173 valid, same bech32 payload

  // mock getBridgedToken to return destTokenAddress; mock getFee/getTokenDecimals etc.

  await expect(
    omniBridge.validateWithdrawal({
      assetId: "nep141:btc-token.near",
      amount: 100_000n,
      destinationAddress: attackerDestination,
      feeEstimation,
    }),
  ).resolves.not.toThrow(); // guard bypassed: compareAddresses(destTokenAddress, attackerDestination, "bitcoin") === false

  const intents = await omniBridge.createWithdrawalIntents({
    withdrawalParams: {
      assetId: "nep141:btc-token.near",
      amount: 100_000n,
      destinationAddress: attackerDestination,
    },
    feeEstimation,
  });

  const ftWithdraw = intents.find((i) => i.intent === "ft_withdraw");
  const msg = JSON.parse(ftWithdraw.msg);
  expect(msg.recipient.toLowerCase()).toBe(`btc:${destTokenAddress}`); // recipient collapses to token's own address
});
