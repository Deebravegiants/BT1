### Title
Batch account-lock check/lock loops are unsynchronized, allowing two same-batch transactions to hold a write lock on the same account simultaneously - ([File: accounts-db/src/account_locks.rs])

### Summary
`AccountLocks::try_lock_transaction_batch` performs all `can_lock_accounts` validity checks for the entire batch in one pass over `validated_batch_keys`, and only afterwards performs the actual `lock_accounts` mutations in a second pass. Because the check pass never mutates lock state, two (or more) transactions in the same batch that write the same account will both observe the same "unlocked" state during validation and both be marked `Ok`, and since `lock_accounts`/`lock_write` unconditionally increments the write-lock counter without re-checking, both end up "locked" concurrently.

### Finding Description
The relevant code is: [1](#0-0) 

The first `for_each` loop iterates over the whole batch and calls `can_lock_accounts` (a pure read-only check against `self.write_locks`/`self.readonly_locks`) for each transaction, but does not call `lock_accounts` in between iterations. Only after this loop finishes checking every transaction does the second `.map(...)` pass run `lock_accounts`, which calls `lock_write`/`lock_readonly`: [2](#0-1) 

Critically, `lock_write` unconditionally increments the counter with no re-validation against the current lock state: [3](#0-2) 

Given a batch `[tx1, tx2]` where both write account `A`, and `A` is not locked prior to the batch:
1. Check pass: `can_lock_accounts` for `tx1` sees `A` unlocked → `Ok`. `can_lock_accounts` for `tx2` also sees `A` unlocked (nothing was locked yet, since locking happens in the second pass) → `Ok`.
2. Lock pass: `tx1`'s `lock_accounts` sets `write_locks[A] = 1`. `tx2`'s `lock_accounts` (unconditionally) sets `write_locks[A] = 2`.

Both transactions receive `Ok(())` from `try_lock_transaction_batch`, meaning both are treated by the caller as holding an exclusive write lock on `A` and can proceed to be loaded/executed/committed concurrently against the same account. This breaks the account-lock exclusivity invariant that downstream banking-stage/replay code (e.g., `consumer.rs::process_and_record_transactions`, `TransactionBatch`) relies on to guarantee only one transaction may mutate an account at a time within a batch.

An unprivileged attacker only needs to submit ≥2 transactions in the same batch that write to the same account (e.g., their own account, or any account they can name) via the normal RPC/TPU submission path; no special privileges, staked node, or leader control is required — this only requires ordinary transaction construction and submission.

### Impact Explanation
This is a lock-exclusivity violation that would allow two transactions to be loaded, executed, and (assuming no other subsystem re-validates) committed against the same account within the same batch, without waiting for each other. This risks double-reading/writing an account before conflicting writes are serialized, which can lead to incorrect account state (a form of lamport-conservation or state-correctness violation) and diverging results depending on execution timing — matching Agave's "double settlement / undeclared account mutation / value creation-loss" bounty category.

### Likelihood Explanation
Preconditions are minimal and fully attacker-controlled: submit ≥2 transactions writing the same account together in one batch (this is exactly how `consumer.rs`'s `process_and_record_transactions` and the schedulers group and lock transactions). No mocked paths, no validator/operator control needed. The bug is deterministic given the code structure (separate check-then-lock passes with no synchronization between them), so it is fully repeatable.

### Recommendation
Interleave the check and lock steps per-transaction inside a single pass so that each transaction's `can_lock_accounts` check is evaluated against the lock state that already reflects all prior successfully-locked transactions in the same batch, e.g.:
```rust
validated_batch_keys
    .into_iter()
    .map(|available_keys| {
        available_keys.and_then(|keys| {
            self.can_lock_accounts(keys.clone())?;
            self.lock_accounts(keys);
            Ok(())
        })
    })
    .collect()
```

### Proof of Concept
```rust
#[test]
fn test_try_lock_transaction_batch_same_account_exclusivity() {
    let mut account_locks = AccountLocks::default();
    let key = Pubkey::new_unique();

    for n in 2..=8usize {
        account_locks = AccountLocks::default(); // reset between trials
        let batch: Vec<TransactionResult<_>> = (0..n)
            .map(|_| Ok(vec![(&key, true)].into_iter()))
            .collect();

        let results = account_locks.try_lock_transaction_batch(batch);

        let ok_count = results.iter().filter(|r| r.is_ok()).count();
        let err_count = results
            .iter()
            .filter(|r| *r == &Err(TransactionError::AccountInUse))
            .count();

        // Expected invariant: exactly one Ok, n-1 AccountInUse errors.
        assert_eq!(ok_count, 1, "n={n}: expected exactly one successful lock");
        assert_eq!(err_count, n - 1, "n={n}: expected all others to fail with AccountInUse");
    }
}
```
With the current implementation, this test fails: `ok_count` will be `n` (all transactions succeed) instead of `1`, because the check pass runs entirely before any locks are taken, demonstrating the exclusivity violation.

    pub fn try_lock_transaction_batch<'a>(
        &mut self,
        mut validated_batch_keys: Vec<
            TransactionResult<impl Iterator<Item = (&'a Pubkey, bool)> + Clone>,
        >,
    ) -> Vec<TransactionResult<()>> {
        validated_batch_keys.iter_mut().for_each(|validated_keys| {
            if let Ok(keys) = validated_keys.as_ref()
                && let Err(e) = self.can_lock_accounts(keys.clone())
            {
                *validated_keys = Err(e);
            }
        });

        validated_batch_keys
            .into_iter()
            .map(|available_keys| available_keys.map(|keys| self.lock_accounts(keys)))
            .collect()
    }

    fn lock_accounts<'a>(&mut self, keys: impl Iterator<Item = (&'a Pubkey, bool)>) {
        for (key, writable) in keys {
            if writable {
                self.lock_write(key);
            } else {
                self.lock_readonly(key);
            }
        }
    }

    #[cfg_attr(feature = "dev-context-only-utils", qualifiers(pub))]
    fn is_locked_readonly(&self, key: &Pubkey) -> bool {
        self.readonly_locks.get(key).is_some_and(|count| *count > 0)
    }

    #[cfg_attr(feature = "dev-context-only-utils", qualifiers(pub))]
    fn is_locked_write(&self, key: &Pubkey) -> bool {
        self.write_locks.get(key).is_some_and(|count| *count > 0)
    }

    fn can_read_lock(&self, key: &Pubkey) -> bool {
        // If the key is not write-locked, it can be read-locked
        !self.is_locked_write(key)
    }

    fn can_write_lock(&self, key: &Pubkey) -> bool {
        // If the key is not read-locked or write-locked, it can be write-locked
        !self.is_locked_readonly(key) && !self.is_locked_write(key)
    }

    fn lock_readonly(&mut self, key: &Pubkey) {
        *self.readonly_locks.entry(*key).or_default() += 1;
    }

    fn lock_write(&mut self, key: &Pubkey) {
        *self.write_locks.entry(*key).or_default() += 1;
    }
