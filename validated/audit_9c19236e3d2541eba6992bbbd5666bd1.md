### Title
Bandwidth gate is documented but not enforced on the `GetResponse` delivery path in `ProxyModule::on_response` - ([File: parachain/runtimes/gargantua/src/ismp.rs])

### Summary
`pallet-bandwidth`'s `BandwidthGate::try_consume` is the mechanism that meters and charges ISMP traffic per `(source, app)` pair, mirroring how `disableFileAccess`/`disableUrlAccess` are meant to gate sensitive Nodemailer sinks regardless of which code path reaches them. In the Hyperbridge runtime, the enforcement is explicit and correct on the inbound POST path (`ProxyModule::on_accept`), but the `on_response` callback that delivers an inbound `GetResponse` to a local module carries only a comment claiming the same gate is mirrored there ("Bandwidth gate. Mirrors the request path in `on_accept`...") without any corresponding `try_consume` call in the function body.

### Finding Description
`ProxyModule::on_accept` in both `parachain/runtimes/gargantua/src/ismp.rs` and `parachain/runtimes/nexus/src/ismp.rs` explicitly meters every non-purchase inbound `PostRequest` before routing it: [1](#0-0) 

By contrast, `ProxyModule::on_response`, which is the callback invoked when an inbound `GetResponse` is delivered to a locally-registered module, contains a comment stating the gate is "mirrored" from the request path, yet the function body performs only chain/module routing with no `try_consume` call: [2](#0-1) 

This is structurally the same root cause as the reported Nodemailer issue: a security/metering control (`disableFileAccess`/`disableUrlAccess` there, `BandwidthGate::try_consume` here) is correctly wired into one code path that reaches a sensitive resource (file/URL access there; bandwidth-metered message delivery here), but a second code path that reaches the same class of resource either omits the check or is documented as enforcing it without actually doing so. The separate, unrelated billing point in `pallet-state-coprocessor`'s response-handling code charges bandwidth against `response.get.source`/`response.get.from` when GET responses are verified via proof and inserted into the MMR — that is a distinct accounting event tied to relayer-proof verification, not the same call site as `ProxyModule::on_response`'s module-delivery callback. Whether that state-coprocessor charge is the sole real enforcement point, or whether `on_response` was intended to independently charge the destination module for local delivery bytes and simply never got the `try_consume` call implemented, could not be fully confirmed because I was unable to re-open `modules/pallets/state-coprocessor/src/impls.rs` and `modules/pallets/bandwidth/src/lib.rs` in full during this pass (tool calls failed on the final iteration). The comment in `on_response` combined with the absence of any `try_consume` call in that specific function is nonetheless a directly observable inconsistency in the repository.

### Impact Explanation
If `on_response` module delivery is meant to be an independently billable event distinct from the proof-verification billing in state-coprocessor, its absence means a module that only pays for outbound requests (or not at all, depending on how allowances are apportioned between request and response legs) could receive an unbounded volume of `GetResponse` deliveries without bandwidth being deducted for that leg — a metering/billing bypass that lets unpriced traffic flow through a component whose entire purpose (per its own comment) is to prevent that. Because bandwidth allowances back real economic value (purchased via `BandwidthManager.purchase()` and tracked as a finite, sellable resource), a silent gap here would allow relayers/apps to consume protocol resources they did not pay for, which is a resource-theft/underbilling issue analogous in class to the reported CWE-862 (missing authorization/enforcement) bug.

### Likelihood Explanation
Reachability requires only that a source chain's app dispatch a `GetRequest` that resolves to a response destined for a module on this runtime — a standard, unprivileged path already used by ordinary GET-based ISMP traffic, requiring no special privilege beyond normal message dispatch. However, I could not fully verify within the available tool budget whether the billing already occurs at the state-coprocessor proof-verification step for the exact same bytes that `on_response` would otherwise charge, which is necessary to determine whether this is a genuine double-gap or an intentional single point of billing with a stale/misleading comment.

### Recommendation
Confirm in `modules/pallets/state-coprocessor/src/impls.rs` whether `BandwidthGate::try_consume` already charges the full response payload for every dest-chain-matching `GetResponse` at proof-verification time; if so, either delete the misleading "mirrors the request path" comment in `ProxyModule::on_response` (since it implies enforcement that isn't there) or, if module-delivery bytes are supposed to be billed independently at this second call site, add the missing `try_consume(&response.get.source, &response.get.from, bytes)` call (guarded by the same `#[cfg(not(feature = "no-bandwidth"))]` flag) before dispatching to the destination module, mirroring the pattern used in `on_accept`.

### Proof of Concept
Not independently reproducible from static review alone given the incomplete file access in this pass; a Devin agent with full repository access should: (1) read `modules/pallets/state-coprocessor/src/impls.rs` in full to trace every `BandwidthGate::try_consume` call site and confirm which bytes/parties are billed for a `GetResponse`; (2) read `parachain/runtimes/{gargantua,nexus}/src/ismp.rs` `on_response` in full; (3) write an integration test that dispatches a `GetRequest`, delivers its `GetResponse` through the module-delivery path, and asserts whether `pallet_bandwidth::Allowance` is decremented for that delivery — if it is not decremented while `on_accept`-routed POSTs are, the gap is confirmed as a real, exploitable metering bypass.

	fn on_accept(&self, request: PostRequest) -> Result<Weight, anyhow::Error> {
		// Bandwidth gate. Always-enforce unless the `no-bandwidth` flag
		// is set; skipped for purchase messages so the recharge flow
		// itself doesn't need bandwidth. With the flag on the gate is a
		// no-op and this block is compiled out entirely.
		#[cfg(not(feature = "no-bandwidth"))]
		if !pallet_bandwidth::Pallet::<Runtime>::is_purchase_message(&request) {
			let bytes = ismp::abi::encode_post_request(&request).len() as u32;
			<pallet_bandwidth::Pallet<Runtime> as pallet_bandwidth::BandwidthGate>::try_consume(
				&request.source,
				&request.from,

	fn on_response(&self, response: GetResponse) -> Result<Weight, anyhow::Error> {
		// Bandwidth gate. Mirrors the request path in `on_accept`: the chain
		// and module that produced the response pay for the bytes they
		// deliver. Compiled out when the `no-bandwidth` flag is on.
		if response.dest_chain() != HostStateMachine::get() {
			return Ok(Weight::from_parts(0, 0));
		}

		let dest = &response.get.from;

		let pallet_id = ModuleId::from_bytes(dest).map_err(|err| Error::Custom(err.to_string()))?;

		match pallet_id {
			pallet_ismp_demo::PALLET_ID =>
				pallet_ismp_demo::IsmpModuleCallback::<Runtime>::default().on_response(response),
			_ => Err(anyhow!("Destination module not found")),
		}
	}
