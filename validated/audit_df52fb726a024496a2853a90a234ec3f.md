### Title
Simplex FX solver prices venue-funded legs from the raw Uniswap V4 pool spot price, letting an intent submitter manipulate the pool in the same transaction flow to drain the solver's LP position - ([File: sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts])

### Summary
Simplex's `FXFiller` prices "venue-priced" (curveless) pairs directly from the live spot price of a configured Uniswap V4 pool instead of a manipulation-resistant TWAP. `UniswapV4FundingPlanner.getExoticTokenPrice` reads the pool's current `sqrtPriceX96` via `computeDirectPoolPriceUsd`, and `FXFiller.resolveLegRates` turns that instantaneous quote directly into the fill rate for an order leg, with `computeLegPolicyOutput` extending it linearly across the whole filled quantity. This is architecturally identical to the ElevateFi bug: a financial payout is derived from a raw, atomically-manipulable AMM price rather than a time-weighted or otherwise defended reference.

### Finding Description
`UniswapV4FundingPlanner.getExoticTokenPrice` ( [1](#0-0) ) selects the most-liquid configured V4 position for the exotic token and calls `computeDirectPoolPriceUsd`, which returns `sdkPool.token0Price`/`token1Price` — the pool's raw mid-price derived straight from the current `sqrtPriceX96` slot0 state ( [2](#0-1) ). There is no TWAP, no volume/impact adjustment, and the pool's own fee tier is never applied to the quoted price, as documented in the flow notes: "computeDirectPoolPriceUsd returns the raw pool mid... there is no size or impact term... checkPriceGuard is the only defense on this path, and it checks deviation from a static reference, not execution cost" ( [3](#0-2) ).

This price is consumed by `FXFiller.resolveLegRates`, which for a curveless USD-stable-token0 pair does `venueRate = 1 / venueUsd` and returns it as the fill rate after only a `checkPriceGuard` check ( [4](#0-3) ). `checkPriceGuard` only rejects a quote if a `referencePrice`/`maxDeviationBps` pair has been explicitly configured for that chain; if no guard is configured (`guard` is `undefined`), it returns `true` unconditionally, passing any price through ( [5](#0-4) ). The docs confirm this is optional and by default absent: "The two fields must be set together; omit both to leave the chain unguarded" ( [6](#0-5) ).

The resolved rate then flows unmodified into `computeLegPolicyOutput`, which extends it linearly over the entire leg notional (`token0ForLeg.mul(rate)...`) to determine `policyMaxOutput` — the amount of the exotic token the solver commits to pay out ( [7](#0-6) ). This output is then funded by withdrawing liquidity from the same manipulated Uniswap V4 position via `planWithdrawalForToken` ( [8](#0-7) ).

An unprivileged order submitter can therefore, within one or two adjacent transactions before Simplex fills the order:
1. Swap against the same Uniswap V4 pool that prices the exotic token to push its spot price far from fair value (e.g., make the exotic token look artificially cheap in USD).
2. Submit (or already have pending) an IntentGateway order that requests a large amount of the exotic token, paying in the USD-stable `token0`.
3. Simplex's FXFiller reads the manipulated spot price (no guard configured, or within `maxDeviationBps` if the guard is loose), computes an inflated `policyMaxOutput`, and fills the order by withdrawing liquidity from its own V4 position.
4. The attacker reverses the manipulating swap, keeping the surplus tokens paid out by the solver at the manipulated rate.

This is the same root cause as the ElevateFi PoC: a payout-determining price sourced from a single, atomically-manipulable AMM state read, defended only by an optional/static deviation check rather than manipulation resistance (e.g., TWAP, execution-cost-aware pricing, or same-block detection).

### Impact Explanation
A successful manipulation directly drains the solver's Uniswap V4 LP position (real, on-chain locked capital) for less than fair value, and/or causes the solver to release exotic tokens far above what the input consideration is worth. Since `checkPriceGuard` is optional and per-chain, any venue-priced pair on a chain without a configured `referencePrice`/`maxDeviationBps` — the documented default state — is fully exposed with no defense at all. This is a concrete theft-of-funds vector against solver-held liquidity reachable from a single unprivileged intent submission plus an ordinary AMM swap.

### Likelihood Explanation
The attack requires only: (1) enough capital or flash-loan access to move the spot price of the specific low/medium-liquidity Uniswap V4 pool configured for a given exotic token pair, and (2) submitting an intent order sized against the exposure the pool manipulation creates, timed so the solver reads the manipulated price before it reverts or before arbitrage corrects it. Thinly-liquid "exotic" tokens (the class this feature targets — e.g., cNGN as used throughout the tests and docs) are inherently easier to move than deep majors, and the guard is opt-in and per-chain, so any misconfigured or newly added chain/position is unprotected by default.

### Recommendation
- Never price a payout directly from a single spot read of `sqrtPriceX96`; use a TWAP (Uniswap V4 truncated oracle observations, or an external oracle) as the price source, or require the guard (`referencePrice`/`maxDeviationBps`) to be mandatory rather than optional for every venue-priced pair.
- Bound `computeLegPolicyOutput`'s payout by the pool's own execution cost/impact (a real quote against the position, not a linear extension of the mid) so a manipulated mid cannot be extended arbitrarily across the whole order size.
- Detect and reject same-block or immediately-preceding large swaps against the priced pool before trusting its spot price for a fill.

### Proof of Concept
Conceptually mirrors `ElevateFi_exp.sol`'s reserve-pump pattern, adapted to Simplex's venue pricing:
1. Attacker swaps a large amount into/out of the configured Uniswap V4 pool for `(USDC, EXOTIC)` to skew `sqrtPriceX96` so `token1Price`/`token0Price` reports EXOTIC as far cheaper in USD than fair value.
2. Attacker (or an accomplice) submits an `IntentGatewayV2` order requesting a large `EXOTIC` output for a modest `USDC` input, on a pair configured with `[vault.uniswapV4]` and no (or a loose) `referencePrice`/`maxDeviationBps` guard, per `sdk/packages/simplex/src/config/filler-toml.ts` and `docs/content/developers/evm/simplex/pricing.mdx`.
3. `FXFiller.resolveLegRates` → `getExoticTokenPrice` → `computeDirectPoolPriceUsd` reads the manipulated `sqrtPriceX96` and returns the skewed price; `checkPriceGuard` passes (no guard configured).
4. `computeLegPolicyOutput` extends this skewed rate over the whole leg, and `UniswapV4FundingPlanner.planWithdrawalForToken` withdraws liquidity from the solver's position to fund the inflated output, which is delivered to the attacker's order.
5. Attacker reverses the initial swap, realizing the EXOTIC tokens obtained at a fraction of fair USDC cost, funded from the solver's own LP position.

	private computeLegPolicyOutput(
		inputAmount: bigint,
		inputIsToken0: boolean,
		token0Decimals: number,
		token1Decimals: number,
		/**
		 * Token0 left in the pair's per-order exposure budget, or `null` to price the whole
		 * input unbudgeted. Only a price probe passes `null`: it commits no capital, so there
		 * is no exposure to ration, and a clamped quantity would silently misprice it.
		 */
		remainingToken0: Decimal | null,
		rate: Decimal,
	): { token0Used: Decimal; policyMaxOutput: bigint } | null {
		let legMaxToken0: Decimal
		if (inputIsToken0) {
			legMaxToken0 = new Decimal(formatUnits(inputAmount, token0Decimals))
		} else {
			legMaxToken0 = new Decimal(formatUnits(inputAmount, token1Decimals)).div(rate)
		}

		const token0ForLeg = remainingToken0 === null ? legMaxToken0 : Decimal.min(legMaxToken0, remainingToken0)
		if (token0ForLeg.lte(0)) {
			return null
		}

		let policyMaxOutput: bigint
		if (inputIsToken0) {
			// Output is token1: convert the token0 allocation at the pair rate.
			policyMaxOutput = BigInt(
				token0ForLeg.mul(rate).mul(new Decimal(10).pow(token1Decimals)).floor().toFixed(0),
			)
		} else {
			// Output is token0: pay out the token0 equivalent of the token1 input.
			policyMaxOutput = BigInt(token0ForLeg.mul(new Decimal(10).pow(token0Decimals)).floor().toFixed(0))
		}

		return { token0Used: token0ForLeg, policyMaxOutput }
	}
