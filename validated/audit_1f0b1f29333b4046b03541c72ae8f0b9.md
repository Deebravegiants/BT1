### Title
Webhook `shop` field is not covered by the Shopify HMAC signature, enabling cross-tenant webhook shop-spoofing/replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating an HMAC over the raw request body, but the `shop` value handed to the application's handler is read from an HTTP header that is completely outside that signature. This breaks the intended binding `authenticated_bytes == data_acted_on`, because the signature only covers `raw_body` while `request.shop` (and `topic`, `webhook_id`, `api_version`) come from unauthenticated headers.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 

`to_signable_string` returns only `@raw_body`. `hmac` is read from the `hmac-sha256` header. `shop` (`shop`) is read independently from the `shop-domain` header — it plays no role in the signed payload at all.

`Registry.process` verifies the webhook using only this body-based HMAC and then immediately trusts `request.shop`: [2](#0-1) 

`Utils::HmacValidator.validate` computes `HMAC(api_secret_key, to_signable_string)` and compares it with `OpenSSL.secure_compare`: [3](#0-2) 

Since `to_signable_string` for a webhook is only the raw body, the check proves "this body byte-string was HMAC-signed with `api_secret_key`" — it proves nothing about which shop the request claims to be from. The `shop` value flows straight into `WebhookMetadata` and is handed to the app's `WebhookHandler#handle`, which the gem's own documentation shows apps using directly as a tenant key (e.g. `shop_domain: data.shop`): [4](#0-3) 

Because Shopify signs webhooks per-app (not per-shop) with the single `api_secret_key`, any two webhooks delivered to the same app — regardless of which installed shop they originated from — carry a validly-signed body under the exact same secret. An attacker who is an unprivileged merchant/owner of their own shop (Shop A) — a completely legitimate "install the app on my store" scenario requiring no credentials belonging to the target — can capture one of their own genuine webhook deliveries (valid `raw_body` + valid HMAC), then replay that exact `raw_body`/HMAC pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop (Shop B). `HmacValidator.validate` still succeeds (it never looked at the shop header), and `Registry.process` calls the handler with `shop: "victim-shop.myshopify.com"` and Shop A's captured body. This is precisely the "field acted on but not covered by the HMAC" analog: the equality `shop_authenticated == shop_used_by_handler` does not hold — the signature authenticates only the body, while the shop identity used for tenant routing/session lookup downstream is taken from an unsigned header.

### Impact Explanation
This crosses the tenant boundary that the webhook is meant to protect: a genuine app installer can force the app to process attacker-supplied (but validly-signed) webhook content under an arbitrary victim shop's identity. Depending on how the host app keys work off `data.shop` (as the documented pattern of using it for job/session lookups and record writes suggests), this can lead to cross-tenant data injection/corruption — writing content in the name of a shop the attacker does not control. This matches the "Critical - cross-tenant access" impact category, since it is a violation of shop-tenant isolation reachable purely through this gem's HMAC-checking and header-parsing logic.

### Likelihood Explanation
Likelihood is bounded by the fact that the attacker must first obtain one legitimately-signed webhook payload, which they can do trivially by installing the app on their own store (no privileged access or secrets needed) and capturing a delivery to their own endpoint. Replaying it against the same app's endpoint with a different shop header is a simple HTTP request. The `to_signable_string`/`HmacValidator` design makes this reachable purely by design of this gem's verification scope, not by misuse of a documented API — the gem instructs developers to treat `data.shop` from `Registry.process` as trustworthy for identifying the shop.

### Recommendation
Bind the shop identity into the authenticated material, or explicitly document/require that consumers cross-check `request.shop` against a shop that is independently known to have an active install/session before trusting it for any tenant-scoped side effect. At minimum, `Webhooks::Request#to_signable_string`/`HmacValidator` should incorporate the `shop-domain` header (and ideally `topic`/`webhook-id`) into the signed material it validates, or `Registry.process` should verify that the resolved `shop` corresponds to a topic/webhook_id combination previously seen only for that shop, preventing header substitution against a captured valid body+signature pair.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and lets Shopify deliver a legitimate webhook (e.g. `orders/create`) to the app's public endpoint. They capture the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header value `H` (valid because `H = HMAC_SHA256(api_secret_key, B)`).
2. Attacker crafts a new HTTP POST to the same public webhook endpoint with:
   - Body = `B` (unchanged)
   - `X-Shopify-Hmac-Sha256` = `H` (unchanged)
   - `X-Shopify-Shop-Domain` = `victim-shop.myshopify.com` (changed)
   - `X-Shopify-Topic`, `X-Shopify-Webhook-Id` optionally changed too (also unsigned)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, B)` and matches `H` — validation passes (see `lib/shopify_api/utils/hmac_validator.rb:26-31` and `lib/shopify_api/webhooks/request.rb:35-38`).
4. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though the content actually originated from, and was only ever HMAC-authenticated for, the attacker's own shop.
