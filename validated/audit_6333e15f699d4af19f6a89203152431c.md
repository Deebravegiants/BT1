### Title
`IntentGatewayV2.placeOrder` applies governance-mutable `protocolFeeBps`/destination fee at execution time with no user-supplied minimum, letting a fee update front-run a pending order and silently shrink the user's escrowed/quoted amount - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`placeOrder` reads the currently active protocol fee (`_destinationProtocolFees[destinationHash]` or the global `_params.protocolFeeBps`) at execution time and deducts it from the user's input before computing the escrow amount and commitment hash [1](#0-0) . Like the FrankenDAO `Staking.stake` finding — where `monsterMultiplier`/`baseVotes`/etc. are governance-settable and can be changed to shrink the voting power a staker receives with no `minVotingPower` guard — here `protocolFeeBps` and the per-destination fee override are governance-settable (via `UpdateParams`, delivered through the ISMP host) and can be raised right before a user's `placeOrder` transaction lands, with no user-supplied minimum-escrowed-amount (or maximum-fee) parameter to protect against it.

### Finding Description
`placeOrder` computes the fee to apply only at execution time: [2](#0-1) 
and then derives the escrowed/quoted amount and the on-chain commitment from that live fee value: [3](#0-2) 

Both `_params.protocolFeeBps` and `_destinationProtocolFees[...]` are governance parameters updated by a privileged `UpdateParams` message (visible in the same pattern reused across the Tron and SDK-mirrored copies of the contract, and exercised in tests that call `onAccept` with a `RequestKind.UpdateParams` body to change `protocolFeeBps`/`destinationFeeBps`) [4](#0-3) . The documentation confirms this is a normal operational lever ("per-destination overrides take precedence over the global `protocolFeeBps` when set") and that the fee is deducted at placement with no refund on expiry/cancellation [5](#0-4) .

A user (or the SDK on their behalf) builds an `Order` and a `quoteIntent()` estimate based on the fee bps observed at quote time, then submits `placeOrder`. Because the function trusts whatever fee value is live when the transaction is mined — with no parameter carrying the user's expected/maximum fee or minimum acceptable escrowed amount — a governance update to raise `protocolFeeBps` (or add/raise a destination-specific override) landing between quote and execution silently reduces the escrowed amount the user gets matched against, exactly the analog of the missing `minVotingPower` in the original report: a state variable settable by a privileged actor can be changed to the detriment of the caller's expected result, with no on-chain guard rejecting the transaction when the outcome falls below what the caller intended.

### Impact Explanation
If the fee is raised between the time a user is quoted an order and the time `placeOrder` executes (whether via ordinary governance timing or deliberate front-running of a pending transaction), the user's tokens are irrevocably reduced by an unexpectedly larger protocol fee — funds are permanently lost as "dust" retained by the gateway, and per the docs this fee "is not refunded" even if the order later expires or is cancelled [6](#0-5) . Because the deducted amount also determines the commitment hash and the amount solvers are matched against, the mismatch is silent (no revert) and only observable after the fact.

### Likelihood Explanation
The parameters are explicitly designed to be governance-adjustable ("Current deployments charge 5 bps... per-destination overrides take precedence"), and the contract exposes no way for a caller to bound the fee they are willing to accept. Any legitimate parameter update (or a malicious/compromised governance actor) that changes fee bps while user transactions are in flight in the mempool will trigger this without any special exploit — it requires only ordinary transaction-ordering conditions, making it a realistic and even non-adversarial occurrence rather than a purely theoretical one.

### Recommendation
Add an optional `minReceivedAmount`/`maxProtocolFeeBps` parameter to `placeOrder` (analogous to the recommended `minVotingPower` in the original report) that the caller supplies based on the fee/quote observed off-chain, and revert if the fee actually applied at execution time would reduce the escrowed input below that threshold (or exceed the caller's specified max fee bps).

### Proof of Concept
1. User calls `quoteIntent()`/observes `_params.protocolFeeBps = 5` (0.05%) and prepares `placeOrder` for `inputAmount = 1000 USDC`, expecting `reducedAmount = 999.5 USDC` to be escrowed.
2. Before the user's transaction is mined, governance (or a compromised/malicious relayer of the `UpdateParams` message) submits an `onAccept` call with `RequestKind.UpdateParams` raising `protocolFeeBps` to `1000` (10%), as exercised in `testProtocolFeeWith10Percent` [7](#0-6) .
3. The user's `placeOrder` transaction then executes, reading the new `protocolFeeBps = 1000` at line 335 and escrowing only `900 USDC` instead of the expected `999.5 USDC` [8](#0-7) .
4. `placeOrder` has no field to reject this outcome — it succeeds unconditionally, and the extra ~99.5 USDC is retained by the gateway as `DustCollected`, unrecoverable to the user even by cancellation.

```text
### Protocol fees

Before escrowing, the contract deducts a protocol fee from each input amount:

```
protocolFee = input.amount × protocolFeeBps / 10_000
reducedAmount = input.amount − protocolFee
```

The fee is retained in the gateway as dust (emitting `DustCollected`), and per-destination overrides take precedence over the global `protocolFeeBps` when set. Current deployments charge **5 bps (0.05%)**. For a 100 USDC input:

| Item | Amount |
| --- | ---: |
| USDC transferred from your wallet | 100.000000 USDC |
| Protocol fee: `100 × 5 / 10,000` | 0.050000 USDC |
| Amount actually escrowed and offered to solvers | 99.950000 USDC |

The commitment hash is computed over the **fee-reduced inputs** — solvers read the reduced amounts from the `OrderPlaced` event and only need to match those. The fee is deducted at placement and is **not refunded** if the order expires, receives no bids, or is cancelled; a cancellation returns the remaining escrow and `order.fees`, but not the protocol fee.

<Callout type="warn">
Do not build an order by reducing the input yourself to account for the protocol fee. Send the gross input amount and use the amounts returned by `quoteIntent()`. The quote prices the fee-reduced escrow amount; reducing it again would make the order smaller than intended.
</Callout>
```
