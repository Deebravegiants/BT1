Audit Report

## Title
Missing role-based permission check on node pprof/debug endpoints allowing low-privilege user to access sensitive diagnostics - (File: core/web/router.go)

## Summary
The `/v2/debug/pprof/*` routes registered by `metricRoutes` in `core/web/router.go` are mounted inside the authenticated `authv2` group but are not wrapped with `auth.RequiresAdminRole`, `RequiresEditRole`, or `RequiresRunRole`, unlike almost every other sensitive route in that file. Any authenticated user, including the lowest-privileged `UserRoleView` account, can therefore access full Go `pprof` introspection (heap dumps, goroutine stacks, cmdline, CPU/execution traces).

## Finding Description
`metricRoutes(r *gin.RouterGroup)` builds `pprofGroup := r.Group("/debug/pprof")` and registers all standard `net/http/pprof` handlers directly with no additional middleware: [1](#0-0) 

It is called at the end of `v2Routes` on the `authv2` group, which only requires session/token authentication with no role check: [2](#0-1) [3](#0-2) 

By contrast, nearly every sensitive endpoint registered on `authv2` is explicitly wrapped in a role check such as `auth.RequiresAdminRole`, `RequiresEditRole`, or `RequiresRunRole` (e.g. user management, key import/export, transfers): [4](#0-3) 

The role-check middlewares are defined in `core/web/auth/auth.go`, confirming that `RequiresRunRole`/`RequiresEditRole`/`RequiresAdminRole` reject `UserRoleView` (and, respectively, `UserRoleRun`) unless explicitly wrapped: [5](#0-4) 

`metricRoutes` uses none of these wrappers, so any authenticated user (including `UserRoleView`) reaches the pprof handlers.

However, this specific finding is **not present in the existing RBAC regression test map** (`routesRolesMap` in `core/web/auth/auth_test.go`), which enumerates dozens of `/v2/*` paths and their expected role requirements but contains no entry for `/v2/debug/pprof/*`: [6](#0-5) 

This confirms the report correctly identified that pprof routes are excluded from the RBAC test coverage — supporting that this is a genuine gap rather than a documented/intended exception.

## Impact Explanation
A user provisioned with only `UserRoleView` can call `GET /v2/debug/pprof/heap`, `/goroutine`, `/cmdline`, `/profile`, and `/trace` (with attacker-controlled `seconds` parameter). These can leak: full process memory contents (potentially including decrypted secrets/private keys held in memory), goroutine stacks revealing internal architecture, and process command-line arguments. This is a legitimate role/permission-check bypass — a `view`-role account obtaining access equivalent to (or worse than) `admin`-level diagnostic capability, mapping to the "node API authentication or role bypass" impact category.

## Likelihood Explanation
Likelihood is high wherever a node operator provisions read-only API accounts (a documented, supported role), since a single authenticated `GET` request is sufficient with no further exploitation chain, no admin/host access, and no social engineering required — only possession of any valid `view`-role session/token, which is the intended, unprivileged floor of the node's own RBAC model.

## Recommendation
Wrap the pprof route group in `metricRoutes` with an explicit `auth.RequiresAdminRole` (or at minimum `RequiresEditRole`) middleware, consistent with how other sensitive `/v2` endpoints in `core/web/router.go` are protected. Add corresponding entries to `routesRolesMap` in `core/web/auth/auth_test.go` so `TestRBAC_Routemap_*` catches regressions.

## Proof of Concept
1. As an admin, create a user with `UserRoleView` (e.g., via `POST /v2/users` with role `view`).
2. Authenticate as that view-only user (session cookie or API token via `AuthenticateByToken`/`AuthenticateBySession`).
3. Issue `GET /v2/debug/pprof/heap?debug=1` (or `/v2/debug/pprof/cmdline`, `/v2/debug/pprof/goroutine?debug=2`) using the view-only credentials.
4. Observe `200 OK` with full pprof output, whereas equivalent-sensitivity endpoints elsewhere in the router return `401`/`403` for the same role, per `TestRBAC_Routemap_ViewOnly` in `core/web/auth/auth_test.go`.
5. As a Go integration test: extend `routesRolesMap` with `/v2/debug/pprof/heap` (and siblings) marked as admin-only (`false, false, false`), run `TestRBAC_Routemap_ViewOnly`, and observe it fails today (returns 200 instead of the expected 403/401), proving the gap.

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// RequiresEditRole extracts the user object from the context, and asserts the user's role is at least
// 'edit'
func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// RequiresAdminRole extracts the user object from the context, and asserts the user's role is 'admin'
func RequiresAdminRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role != clsessions.UserRoleAdmin {
			c.Abort()
			addForbiddenErrorHeaders(c, "admin", string(user.Role), user.Email)
			jsonAPIError(c, http.StatusForbidden, errors.New("Forbidden"))
			return
		}
		handler(c)
	}
}
