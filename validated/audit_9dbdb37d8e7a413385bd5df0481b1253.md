### Title
Stale residual balance sweep in EmporiumUpgradeable.runAction lets any unprivileged caller steal a router refund parked in a prior transaction - (contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction` computes the amount to send out as an output UTXO purely from a before/after balance diff taken *within the current call*, adjusted only by the caller's own `deltaAmountChanges`. It never verifies that a positive balance increase actually originated from funds this same transaction deposited. An attacker who crafts an op that pulls a stranded refund (e.g. a DEX router's delayed "claim"/"sweep" function owed to Emporium from an earlier, unrelated user's swap) into Emporium's balance can have that entire amount paid out as their own output UTXO, at essentially zero declared deposit.

### Finding Description
The invariant that should hold is: *tokens leaving the Emporium action in a transaction == -deltaAmountChanges Hinkal sent it in that same transaction*. `EmporiumUpgradeable.runAction` breaks this invariant.

`runAction` snapshots balances before running `stack.ops` [1](#0-0) , then executes an attacker-fully-controlled list of arbitrary external calls [2](#0-1) . Because `verifyWallet` returns immediately with no signature check whenever `stack.signerAddress == address(0)` [3](#0-2) , the "Stateless Interaction" branch lets any unprivileged caller specify an arbitrary `op.endpoint`/`op.callData` (only `callHinkalWallet`/`doSendToRelay` selectors are blocked) [4](#0-3) .

After the ops run, the amount to release is computed as:
```
balanceChange = balancesAfter[i] - balancesBefore[i];
if (deltaAmountChanges[i] < 0) balanceChange -= deltaAmountChanges[i];
``` [5](#0-4) 
and any positive `balanceChange` is unconditionally paid out via `handleOut`, which transfers the tokens and mints a `UTXO` addressed to `circomData.stealthAddressStructure` — a field fully controlled by the calling attacker [6](#0-5) .

The flaw: for `deltaAmountChanges[i] >= 0` (no deposit declared for token `i`), `balanceChange` is simply `balancesAfter[i] - balancesBefore[i]` with no requirement that this increase came from funds *this* transaction supplied. If a prior, unrelated Emporium transaction left an obligation on an external router (e.g. a partially-filled swap whose unused input/output must be claimed via a separate `refund()`/`sweep()` call, with Emporium as the original `msg.sender`/beneficiary at the router), any later attacker can:
1. Include that token in `circomData.erc20TokenAddresses` with `amountChanges[i] = 0` (so `deltaAmountChanges[i] = 0`, no deposit required).
2. Add an `op` in `stack.ops` calling the router's public claim/refund/sweep function, causing it to push the stranded tokens into Emporium's balance during this call.
3. Set `circomData.stealthAddressStructure` to their own address.

`balanceChange` becomes the claimed refund amount, `handleOut` pays it to Hinkal, and Hinkal's own bookkeeping check `balanceDif == amountChanges[i] + utxoAmount` is satisfied trivially (`amountChanges[i]=0`, `utxoAmount=refund`, and Hinkal's balance did increase by exactly that amount) [7](#0-6) . Every existing guard (`performHinkalChecks`, `verifyProof`, `rootHashExists`, `insertNullifiers`, `onlyAllowedRecipient`) is satisfied because they only validate the attacker's *own* inputs/nullifiers/roots — none of them tie a positive `balanceChange` in the external action back to the transaction that actually generated it. The invariant Hinkal enforces (`balanceDif == amountChanges[i] + utxoAmount`) is a *local* consistency check between Hinkal and the action for the current call; it says nothing about whether the funds behind `utxoAmount` were rightfully deposited in this same call versus swept in from a stale, previously-stranded obligation belonging to a different user's transaction.

### Impact Explanation
This is a direct theft of value: funds that are owed back to a prior user (or to the protocol) as a delayed router refund can be redirected into a completely unrelated, unprivileged attacker's own shielded UTXO. The attacker pays essentially nothing (zero or minimal declared deposit) and receives the full stranded amount as spendable shielded balance. This matches the Critical category: "direct theft of shielded or in-flight user funds." The attack is repeatable any time such a residual exists and is discoverable/claimable by a public router function.

### Likelihood Explanation
Exploitability depends on: (1) a prior Emporium-routed operation leaving a claimable, un-swept balance at an external router or endpoint that Emporium previously interacted with as `msg.sender`, and (2) that claim/refund mechanism being callable by anyone and depositing funds back to Emporium's address. Given that `stack.ops` allows fully arbitrary calls to arbitrary endpoints with `signerAddress == address(0)` (no signature required), the attacker's cost to attempt this is just gas plus proof generation for a legitimate own-UTXO transaction; no privileged role is needed. Whether such stranded refunds exist depends on the specific routers integrated via `op.endpoint`, but the contract provides no defense against this class of external residual regardless.

### Recommendation
Do not treat every positive `balanceChange` as belonging to the current caller. Track and require that funds leaving the action in a transaction are strictly bounded by `-deltaAmountChanges` sent to it in that same transaction (i.e., cap `handleOut`'s payout to at most the amount attributable to `deltaAmountChanges`, or explicitly disallow any output for tokens with `deltaAmountChanges[i] >= 0` unless the increase can be attributed to a specific, provably-owned pending claim). Alternatively, require external actions to sweep/settle any router refunds synchronously within the same transaction that created the obligation, and add an explicit accounting ledger (e.g., per-token "owed to X" bookkeeping) rather than relying on instantaneous before/after balance diffs.

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable` with a mock router that models a two-step swap: `swap()` pulls tokens and only partially fills, and a separate public `claimRefund(address recipient)` that anyone can call to push the unused amount to `recipient` (simulating a router-owed refund to Emporium).
2. Tx1 (victim): call `Hinkal.transact` with an Emporium op that calls `router.swap(...)`, leaving a refund obligation recorded in the router for Emporium's address, without an accompanying `claimRefund` op. Assert Emporium's on-chain token balance is unaffected but the router holds `R` tokens earmarked for Emporium.
3. Tx2 (attacker): craft `circomData` with `amountChanges[i] = 0` for the refund token, `stealthAddressStructure` = attacker's own, and a `stack.ops` entry calling `router.claimRefund(emporiumAddress)`.
4. Assert: before Tx2, `attackerShieldedBalance(token) == 0`; after Tx2, `attackerShieldedBalance(token) == R` while `attackerDeltaAmountChanges[i] == 0` (i.e., attacker deposited nothing for this token this transaction) — violating `tokens leaving action this tx == -deltaAmountChanges Hinkal sent it this tx`.
5. Confirm all standard Hinkal checks (`verifyProof`, `rootHashExists`, nullifier insertion, `balanceDif == amountChanges[i] + utxoAmount`) pass without reverting, demonstrating existing guards do not catch the misattribution.
