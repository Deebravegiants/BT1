### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signature only over the raw request body, while the `shop` (and `topic`) values used to route and identify the tenant for webhook processing are taken from unauthenticated HTTP headers. This breaks the intended binding between "the bytes verified by HMAC" and "the bytes acted upon as the tenant identifier."

### Finding Description
`Utils::HmacValidator.validate` checks a `VerifiableQuery`'s `hmac` against `compute_signature(verifiable_query.to_signable_string, secret)` [1](#0-0) . For webhooks, `to_signable_string` returns only `@raw_body` [2](#0-1) . The `shop`, `topic`, `webhook_id`, and `api_version` values are all pulled directly from HTTP headers and are never included in the signable string [3](#0-2) .

`Registry.process` validates only that the HMAC of the body is correct, then immediately trusts `request.shop` as the tenant identifier and forwards it to the app's webhook handler: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [4](#0-3) .

The identity binding that should hold is: `shop_used_for_tenant_routing == shop_that_the_HMAC_signature_actually_authenticates`. Because the HMAC only authenticates `raw_body`, this equality does not hold — the `shop-domain` header can be swapped for any value without invalidating the signature, as long as the body is unchanged.

### Impact Explanation
Cross-tenant access: An attacker who can obtain any one legitimately-signed webhook payload (trivial — anyone can install the app on their own store, which is a completely unprivileged action, and receive a real, validly-signed webhook for their own shop) can replay that exact `raw_body` + `hmac-sha256` header pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header (e.g., a victim merchant's domain). `HmacValidator.validate` will report the signature as valid (it never looks at the shop header), and `Registry.process` will hand the attacker-chosen body to the merchant's webhook handler tagged with the victim's shop, in the same call. Any host application that uses `WebhookMetadata#shop` to select which tenant's records to look up, update, or delete (which is the gem's documented purpose for this field, per `docs/usage`) will act on the wrong tenant's data. This satisfies "cross-tenant access" per the rules.

### Likelihood Explanation
The attack requires no privileged credentials, no access token, and no knowledge of `api_secret_key`: an attacker only needs to be an app user on their own store to generate at least one authentic body/HMAC pair and then send an HTTP POST with modified headers to the app's public webhook receiving endpoint. This is exactly the kind of unprivileged, internet-reachable identity-binding break the analog class targets.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed material, or otherwise cryptographically bind them to the body before trusting them for tenant routing — e.g., mirror Shopify's evolving `X-Shopify-Hmac-Sha256` semantics but additionally require validating `shop-domain` against a store-specific secret/state that only the legitimate shop could produce, or require the host app to independently confirm the shop identity through an authenticated channel (such as a stored per-shop verification value) rather than trusting the header outright.

### Proof of Concept
1. Attacker installs the target app on their own development/free store `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook event (e.g., `orders/create`) and captures the raw POST: `raw_body` and header `shopify-hmac-sha256: <valid signature>` from the app's real webhook receiver, exactly as constructed in `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` [5](#0-4) .
3. Attacker resends this exact `raw_body` and `shopify-hmac-sha256` value to the app's webhook endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` recomputes HMAC over `raw_body` only and it matches, so `Registry.process` proceeds [6](#0-5) .
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled body content, despite the signature never having authenticated that shop value.

          received_signature = verifiable_query.hmac

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
