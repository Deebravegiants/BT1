## Analysis

The bug-class here is an **identity-binding break**: a field that is acted upon by the code is not actually covered by the cryptographic signature that is supposed to authenticate the request. In the TOKE-8 report, `userRewardPerTokenPaid` accounting relied on a rewarder still being in a loop it had been removed from. The reachable analog in this gem is in the webhook HMAC verification path.

### Root cause

`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

But `shop` (and `topic`, `api_version`, `webhook_id`) are read straight from caller-supplied HTTP headers, never mixed into the signed string: [2](#0-1) 

`Registry.process` verifies the HMAC over that same `Request` object, then immediately trusts `request.shop` to build the tenant-identifying `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (the raw body) and compares it to the `hmac` header — it never binds `shop`: [4](#0-3) 

### Title
Webhook `shop` identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#shop` is read from the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) HTTP header, but `Request#to_signable_string` — the data that `HmacValidator` actually authenticates — only contains the raw request body. The equality the gem should enforce is `hmac == HMAC(secret, shop || raw_body)`, but it actually only enforces `hmac == HMAC(secret, raw_body)`. Because a single `api_secret_key` signs webhooks for every shop installed on a multi-tenant app, any merchant who installs the app can capture a legitimately-signed webhook delivered to their own endpoint and replay the identical `(raw_body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary victim shop domain in the `shop-domain` header. `Utils::HmacValidator.validate` still returns `true` (the body/hmac pair is authentic), but `Webhooks::Registry.process` then hands the handler a `WebhookMetadata` claiming the payload originated from the attacker-chosen `shop`.

### Finding Description
Shopify signs webhook bodies with the app's `api_secret_key`, which is shared across all shops that installed the app — it is not a per-shop secret. The gem's `HmacValidator` (used identically for OAuth callbacks and webhooks via the shared `Utils::VerifiableQuery` interface) validates authenticity purely by recomputing an HMAC over `to_signable_string`. For OAuth callbacks, `AuthQuery#to_signable_string` deliberately includes `shop` in the signed string, correctly binding shop identity to the signature. For webhooks, however, `Request#to_signable_string` includes only `@raw_body`; `shop`, `topic`, `api_version`, and `webhook_id` are all taken from unauthenticated headers and never checked against anything the signature covers. [5](#0-4) 

An unprivileged user who is a legitimate merchant of the app (i.e., has installed it on their own store and can therefore receive real webhooks) can:
1. Capture a real Shopify webhook delivery: `(raw_body, X-Shopify-Hmac-Sha256)`, which is validly signed with the app's shared secret.
2. Re-send that exact `raw_body` and `hmac` header to the app's webhook endpoint, but replace `X-Shopify-Shop-Domain` with a victim shop's domain.
3. `HmacValidator.validate` passes because it only checks `raw_body` against `hmac`.
4. `Registry.process` builds `WebhookMetadata` using the attacker-controlled `shop` value and dispatches it to the app's handler as if Shopify itself asserted this event belongs to the victim shop. [3](#0-2) 

### Impact Explanation
This breaks the identity binding the gem is supposed to guarantee between "HMAC-authenticated webhook" and "the shop it claims to be from." Any app logic that trusts `WebhookMetadata#shop` to key persistence, authorization, or side effects (e.g., mandatory `shop/redact`, `customers/redact`, `customers/data_request` compliance webhooks, or app-specific business logic keyed by shop) can be tricked into acting on behalf of, or against, a shop the attacker does not control — a cross-tenant confusion enabled entirely within this gem's trust boundary.

### Likelihood Explanation
Requires only an app installation by the attacker (a normal, unprivileged action available to any merchant) and the ability to POST arbitrary HTTP requests with attacker-chosen headers to the app's public webhook endpoint — no access to the app's `api_secret_key`, access tokens, or victim credentials is needed. The vulnerability is directly reachable through the gem's documented `Webhooks::Registry.process` / `Webhooks::Request` API.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the value that `Request#to_signable_string` returns, or otherwise cryptographically bind the shop header to the signature check, matching the pattern already used in `Auth::Oauth::AuthQuery#to_signable_string`, which explicitly folds `shop` into the signed string.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Shopify sends attacker a legitimate webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(api_secret_key, B)`), `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker replays to the app's webhook endpoint:
   ```
   POST /webhooks HTTP/1.1
   X-Shopify-Topic: customers/redact
   X-Shopify-Hmac-Sha256: H
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   Body: B
   ```
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `Utils::HmacValidator.validate(request)` returns `true` since it only checks `B` against `H`. [6](#0-5) 
5. `Registry.process` invokes the app's handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", ...)`, even though Shopify never sent any webhook for `victim-shop`.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
