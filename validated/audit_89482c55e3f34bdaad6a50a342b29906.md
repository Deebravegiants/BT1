### Title
Webhook shop-domain and topic headers are not covered by the HMAC signature, breaking the shop/tenant binding - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` fields — all read from unauthenticated HTTP headers — are handed to the webhook handler as if they were verified. `ShopifyAPI::Webhooks::Registry.process` then dispatches to the handler using `request.shop` after only validating the HMAC against the body, letting an attacker who possesses one valid `(body, hmac)` pair for their own shop re-attribute that payload to an arbitrary victim shop.

### Finding Description
`Utils::VerifiableQuery#to_signable_string` is the value that gets HMAC-verified by `Utils::HmacValidator.validate`: [1](#0-0) 

For webhooks, `to_signable_string` is defined to be only the raw body: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers, none of which are included in the signed content: [3](#0-2) 

`Registry.process` validates only the HMAC (i.e., only the body) and then forwards `request.shop` (and `request.topic`) unchanged to the app's handler as if they were authenticated attributes of the request: [4](#0-3) 

The gem's own documentation tells host developers that calling `Registry.process` "will verify the request did indeed come from Shopify" and that `data.shop` is "The shop domain of the webhook", encouraging developers to use it as an authenticated tenant identifier (e.g. `perform_later(shop_domain: data.shop, ...)`): [5](#0-4) [6](#0-5) 

This breaks the binding `shop authenticated by HMAC == shop attributed to the tenant/session key`: the HMAC only authenticates that the *body bytes* were produced with the app's `client_secret`; it says nothing about which shop the header claims to be from. Any unprivileged internet user who can install the app on a shop they control (e.g. a dev/partner store) can obtain a legitimately-signed `(raw_body, hmac)` pair from their own shop's real webhook delivery, then replay it to the same endpoint with the `x-shopify-shop-domain` (and optionally `x-shopify-topic`) header rewritten to a victim shop's domain. The HMAC check still passes (it never looked at the header), and the handler receives `WebhookMetadata` claiming the payload originated from the victim shop.

### Impact Explanation
This is a cross-tenant attribution/spoofing bypass: an attacker-controlled body can be delivered to a host application under the identity of a shop the attacker does not own and has no session for. Any host app logic keyed on `data.shop` (data storage, per-tenant job dispatch, deduplication, billing/usage tracking, GDPR data-request/erasure handling, etc.) can be corrupted or manipulated on behalf of another merchant, without the attacker ever obtaining that merchant's access token or credentials. This matches the "Critical – cross-tenant access" impact category, since the tenant boundary (shop identity) is not actually bound to the HMAC that is meant to authenticate the request.

### Likelihood Explanation
Exploitation requires only: (1) the ability to install the target app on any Shopify store the attacker controls — trivial for any developer/partner account — to legitimately trigger one real webhook delivery and capture its raw body + valid HMAC, and (2) the ability to send an arbitrary HTTP request to the app's public webhook endpoint with a modified `shop-domain` header. No merchant credentials, access tokens, or `client_secret` knowledge are needed. This is realistically exploitable by any unprivileged internet user with a free developer store.

### Recommendation
Bind the tenant-identifying fields into the HMAC-signable content (or otherwise cryptographically bind `shop`, `topic`, `webhook_id` to the verified payload), or require callers to cross-check `request.shop` against a known/installed shop for the app (e.g. an existing offline session) before treating it as trusted. At minimum, update the documentation to stop asserting that `Registry.process` verifies the request "did indeed come from Shopify" for the shop/topic headers, since only the body is authenticated.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a shop they control) and triggers any registered webhook topic (e.g. `orders/create`), capturing the real delivery: raw body `B`, and header `x-shopify-hmac-sha256: H` (valid HMAC of `B` with the app's `client_secret`), and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker POSTs to the same app webhook endpoint with body `B` and header `x-shopify-hmac-sha256: H` unchanged, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`= B`) and matches `H` — validation succeeds [7](#0-6) .
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)` [8](#0-7) , causing the host app to process attacker-supplied data as though it belongs to `victim-shop.myshopify.com`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
