## Finding

### Title
Webhook shop-domain identity spoofing via HMAC that only signs the raw body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identifier (`shop`) from the unauthenticated `X-Shopify-Shop-Domain` header, while the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` validates only covers the raw request body. An attacker who legitimately installs the app on their own shop (and therefore possesses genuine, correctly-signed webhook deliveries for that shop, since the HMAC secret is the app's shared `client_secret`, not a per-shop secret) can replay a valid `(body, hmac)` pair while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. The signature still validates, and the forged shop is handed to the app's webhook handler as if authenticated.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop` accessor, however, is read straight from an unsigned header: [2](#0-1) 

`HmacValidator.validate` computes the signature exclusively over `to_signable_string` (the body) and compares it against the `hmac` value, never incorporating `shop`, `topic`, `api_version`, or `webhook_id`: [3](#0-2) 

`Registry.process` validates the HMAC, then immediately forwards the unauthenticated `request.shop` to the application's handler with no further binding check: [4](#0-3) 

Because a Shopify app's webhook HMAC secret (`Context.api_secret_key`) is shared across *every* shop that installs the app (it is not per-tenant), any merchant who installs the app receives genuinely signed `(body, hmac)` pairs for their own shop. Since the shop identity is carried in a header that is excluded from the signed bytes, that merchant can take their own valid signed payload and simply swap `X-Shopify-Shop-Domain` to name a different, victim shop. `HmacValidator.validate` will still accept it because the bytes it verifies (`@raw_body`) are unchanged, but the tenant identity the library reports to the application (`request.shop` / `WebhookMetadata#shop`) does not match the tenant that produced the signed bytes. This is exactly the "bytes verified vs. bytes/fields acted on" identity-binding break: the equality `shop_used_by_handler == shop_that_produced_the_HMAC` is not enforced anywhere in the gem.

### Impact Explanation
Any host application that uses `request.shop`/`WebhookMetadata#shop` (as the documented API instructs) to select which tenant's data to update, delete, or query — which is the standard pattern for mandatory compliance webhooks like `customers/redact`, `shop/redact`, `app/uninstalled`, and any topic carrying shop-scoped state — can be made to act on an attacker-chosen victim shop using data supplied by the attacker. This is a cross-tenant integrity/confidentiality issue reachable by any unprivileged party who can install the app on their own store, satisfying the "cross-tenant access" Critical-impact criterion.

### Likelihood Explanation
Exploitation only requires becoming a legitimate (even free/trial) installer of the target app to obtain one authentic signed webhook payload, then replaying it with a modified header — no access token, `client_secret`, or privileged account is required beyond ordinary app installation. This is realistically reachable by any internet user who can install a public Shopify app.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the signed material, or independently verify that the shop named in the header matches a shop known to have generated the payload (e.g., require the raw body itself to embed/attest the shop, or maintain a per-shop signing check) before handing `request.shop` to handlers. At minimum, document prominently that `shop`, `topic`, and other headers are unauthenticated and must not be trusted for tenant routing without independent verification — and ideally include them in `to_signable_string` so `HmacValidator` binds them cryptographically.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook (e.g., `orders/create`) to receive a legitimate delivery: body `B`, header `X-Shopify-Hmac-Sha256: H` (computed by Shopify over `B` using the app's shared `client_secret`), and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Replay a POST to the app's webhook endpoint with the same body `B` and same `H`, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `@raw_body` only — it matches `H`, so validation passes: [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and attacker-controlled body content, and performs its shop-scoped logic (e.g., data redaction, order sync) against the victim tenant.
