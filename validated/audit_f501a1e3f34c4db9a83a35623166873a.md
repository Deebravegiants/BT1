### Title
Webhook HMAC covers only the request body, not the `shop-domain`/`topic` headers, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates its HMAC signature using only the raw request body. The `shop-domain`, `topic`, `webhook-id`, and `api-version` headers—which the registry uses to identify the tenant and dispatch the payload—are never part of the signed data. Any party who possesses one valid `(body, hmac)` pair signed with the app's `client_secret` (e.g., an attacker who owns a shop that has installed the app, and therefore legitimately receives signed webhooks for their own shop) can resend that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header. The signature will still validate, and the handler will process the payload as if it originated from the victim shop.

### Finding Description
The identity binding that should hold is:
`shop header used by Registry.process == shop actually authenticated by the HMAC`

In this codebase that binding is broken:
- `HmacValidator.validate` calls `validate_signature`, which computes the HMAC solely over `verifiable_query.to_signable_string` [4](#0-3) .
- `Webhooks::Request#to_signable_string` returns `@raw_body` and nothing else [5](#0-4) .
- `Webhooks::Request#shop`, `#topic`, `#webhook_id`, `#api_version` are all read directly from attacker-controlled HTTP headers, none of which feed into `to_signable_string` [6](#0-5) .
- `Registry.process` only checks `Utils::HmacValidator.validate(request)` before trusting `request.topic` and `request.shop` to route and label the payload passed to the app's handler [3](#0-2) .

Since every shop installed on the same app shares the same `client_secret` (Shopify apps use one `client_secret` across all their merchants), a single valid signed body can be replayed with a forged `shop-domain` header. This is exactly the bug class from the reference report: "a field acted on but not covered by the HMAC" — here the tenant identifier (`shop`) is acted upon by `Registry.process`/`WebhookMetadata` but is outside the HMAC-covered bytes, mirroring the report's core flaw where a message-routing/identity field is decoupled from the mechanism meant to authenticate it.

### Impact Explanation
This is a cross-tenant data/action confusion: the handler receives `WebhookMetadata` claiming to be for shop B while the payload really originated (and was signed) for shop A. Depending on what the host app's webhook handler does (e.g., update records keyed by `shop`, trigger uninstall/redact flows, mark orders paid, sync inventory), this can let one merchant's traffic be misattributed to another merchant's tenant records purely by forging an HTTP header, satisfying the "cross-tenant access" Critical-impact criterion.

### Likelihood Explanation
Exploitation requires the attacker to obtain at least one legitimately-signed `(body, hmac)` pair, which is trivial for anyone who can install the app on their own store (a standard, unprivileged action for any Shopify merchant/developer) and capture their own inbound webhook request. No access to `api_secret_key`, TLS interception, or any privileged account is required — only observation of one's own legitimately received webhook.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed material, or otherwise cryptographically bind them to the body (e.g., compute the signature over a canonical string containing headers + body) so that a signature can only validate for the exact header/body combination it was issued for.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC of `B` with the shared `client_secret`).
2. Attacker replays this exact HTTP request to the app's public webhook endpoint, only modifying `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim.myshopify.com", hmac-sha256: H...})` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only and finds it matches `H`, so validation succeeds [7](#0-6) .
4. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed_body_of_B, ...)`, causing the host application to process attacker-controlled data under the victim's tenant identity.
