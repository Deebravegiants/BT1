### Title
Attacker-controlled `signup_extension` flag on operator QR-code bypasses real backend operator verification - (File: src/plans/mod.rs)

### Summary
`verify_operator_qr_code` in `src/plans/mod.rs` short-circuits real backend validation of an operator QR-code whenever the *scanned* QR-code data reports `signup_extension() == true`, unconditionally returning a synthetic "valid" `LocationData` instead of calling `backend::operator_status::request`. This is structurally the same bug class as the reported C4 finding: a boolean flag that is supposed to only apply to a specific mode is used, without checking whether the corresponding code path (the actual backend call) was ever exercised, causing the security check to be skipped for a whole class of inputs.

### Finding Description
`verify_operator_qr_code` is the function responsible for confirming with the backend that an operator (distributor) QR-code is legitimate before proceeding with a signup session and before recording `operator_location_data` used later for compliance/session records: [1](#0-0) 

The relevant branch is:
```rust
if qr_code.signup_extension() || self.operator_qr_code_override.is_some() {
    return Ok(Some((0, backend::operator_status::LocationData {
        team_operating_country: "DEV".to_string(),
        session_coordinates: Coordinates { latitude: 0.0f64, longitude: 0.0f64 },
        stationary_location_coordinates: None,
    })));
}
```
`self.operator_qr_code_override` is a developer/CLI-only override (not reachable by an unprivileged party scanning a QR code in the field), but `qr_code.signup_extension()` is derived directly from the *content of the scanned QR code string* via `qr_scan::user::Data`/`qr_scan::operator::Data::try_parse`, i.e., attacker-controlled input that a person presenting a QR code to the Orb fully controls: [2](#0-1) 

Whenever the scanned "operator" QR-code sets the `signup_extension` bit, the entire online operator-identity check (`backend::operator_status::request`, which validates the operator id against the backend and returns real geo/location data) is skipped, and the function fabricates a "DEV"/`(0.0, 0.0)` location result and reports success: [3](#0-2) 

This is invoked from both the self-serve initial-scan path and the standard scan path: [4](#0-3) [5](#0-4) 

The pattern mirrors the C4 report exactly: a single boolean derived from attacker/caller-supplied data (`useUnderlying` in the C4 bug vs. `signup_extension()` here) determines whether a security-relevant backend call is made at all, and when the flag is set the code takes a path that was designed for an internal/dev/data-acquisition use case but is reachable by anyone who can present a crafted QR-code to the camera.

### Impact Explanation
If `signup_extension()` can be set to `true` by presenting a specially crafted operator QR-code (the parsing logic in `qr_scan::operator::Data::try_parse` accepts any `user::Data`-shaped code, gated only by requiring `signup_extension_config.is_some()` when the flag is set), an unauthorized party can make the Orb accept an operator QR-code as valid without ever confirming it against the backend `distributor/.../status` endpoint. This allows an unverified/unauthorized "operator" identity to be accepted, and the downstream code (e.g. `debug_report::builder`, `personal_custody_package::Credentials { operator_qr_code, .. }`) will bind the resulting signup and stored biometric package to this unverified operator identity — a misattributed-operator / authorization-bypass condition consistent with the "misattributed signup" impact class.

### Likelihood Explanation
Exploitability hinges on whether the "signup_extension"/"data acquisition" code path is actually reachable outside the `internal-data-acquisition` build feature and whether an ordinary presented QR-code (not requiring physical/hardware access, not a malicious node/operator per the exclusion rules) can set this bit. From the code visible, `signup_extension()` and `signup_extension_config` live on `qr_scan::user::Data`, and the gating I could partially confirm (`#[cfg(feature = "internal-data-acquisition")]` checks in `scan_operator_qr_code`/`handle_user_qr_code`) suggests this feature is intended for internal R&D builds, filtering out `signup_extension` codes when `data_acquisition` is disabled. I was not able to fully verify, within the available index, whether `verify_operator_qr_code`'s bypass branch is reachable in a production (non-`internal-data-acquisition`) build, or whether an additional gate exists upstream that always filters out `signup_extension` operator codes before reaching this function in production configurations. This uncertainty affects whether the finding is exploitable by an unprivileged field attacker in production vs. only in internal/R&D builds — the latter would fall under the "test-only paths"/no-impact exclusion.

### Recommendation
Do not let `verify_operator_qr_code` skip the backend call based solely on a QR-code-supplied `signup_extension` flag. Either (a) require an orb-side, non-scannable configuration/feature flag (already the case for `operator_qr_code_override`) to gate the bypass, decoupled from the QR content, or (b) still call `backend::operator_status::request` for `signup_extension` operator codes and require the backend to explicitly authorize the data-acquisition mode for that operator, ensuring the "DEV" location/success path can never be produced from data an unauthenticated third party fully controls.

### Proof of Concept
1. Build/operate an Orb in a configuration where the `signup_extension`-tagged operator QR-code path is reachable (i.e., not filtered upstream).
2. Craft an operator QR-code string that `qr_scan::user::Data::try_parse` will parse such that `signup_extension() == true` and `signup_extension_config.is_some()` (satisfying the filter in `qr_scan::operator::Data::try_parse`, `src/plans/qr_scan/operator.rs:41-44`).
3. Present this QR-code to the Orb during `scan_initial_qr_codes`/`scan_remaining_qr_codes` (`src/plans/mod.rs:749-868`).
4. Observe that `verify_operator_qr_code` (`src/plans/mod.rs:1551-1557`) short-circuits and returns `Ok(Some((0, LocationData{team_operating_country:"DEV",...})))` without ever calling `backend::operator_status::request`, i.e., without validating operator identity/location against the backend, and the signup proceeds using this fabricated operator status.

    /// Checks if `qr_code` is a valid operator QR-code through the backend.
    #[allow(clippy::cast_possible_truncation)]
    async fn verify_operator_qr_code(
        &self,
        orb: &mut Orb,
        qr_code: &qr_scan::user::Data,
        qr_capture_start: Instant,
    ) -> Result<Option<(u64, backend::operator_status::LocationData)>> {
        if qr_code.signup_extension() || self.operator_qr_code_override.is_some() {
            return Ok(Some((0, backend::operator_status::LocationData {
                team_operating_country: "DEV".to_string(),
                session_coordinates: Coordinates { latitude: 0.0f64, longitude: 0.0f64 },
                stationary_location_coordinates: None,
            })));
        }
        let http_start = Instant::now();
        match backend::operator_status::request(qr_code).await {
            Ok(backend::operator_status::Status { valid: true, location_data, reason: _ }) => {
                let location_data = location_data
                    .expect("to always have a result from the backend if valid == true");
                orb.ui.qr_scan_success(QrScanSchema::Operator);
                dd_incr!("main.count.global.distr_code_validated");
                tracing::info!("Operator QR-code validated: {qr_code:?}");
                dd_timing!("main.time.signup.distr_qr_code_capture", qr_capture_start);
                return Ok(Some((http_start.elapsed().as_millis() as u64, location_data)));
            }
            Ok(backend::operator_status::Status { valid: false, .. }) => {
                orb.ui.qr_scan_fail(QrScanSchema::Operator);
                dd_incr!("main.count.signup.result.failure.distr_qr_code", "type:invalid_qr");
            }
            Err(_) => {
                orb.ui.qr_scan_fail(QrScanSchema::Operator);
            }
        }
        Ok(None)
    }

/// Makes a validation request.
pub async fn request(qr_code: &qr_scan::user::Data) -> Result<Status> {
    let request = super::client()?
        .get(format!(
            "{}/api/v1/distributor/{}/orb/{}/status",
            *SIGNUP_BACKEND_URL, qr_code.user_id, *ORB_ID
        ))
        .basic_auth(&*ORB_ID, Some(get_orb_token()?));
    let status: Status = match request.send().await?.error_for_status() {
        Ok(response) => response.json().await?,
        Err(err) => {
            tracing::error!("Received error response {err:?}");
            return Err(err.into());
        }
    };
    if !status.valid {
        tracing::info!(
            "Operator QR-code invalid: {qr_code:?}, reason: {:?}",
            status.reason.as_deref().unwrap_or("<empty>")
        );
        return Ok(status);
    }
    if status.location_data.is_none() {
        tracing::error!("Operator location data are missing");
        return Ok(Status {
            valid: false,
            location_data: None,
            reason: Some("Operator location data are missing".to_string()),
        });
    }
    Ok(status)
}
