### Title
Unsigned cross-chain calldata execution authenticates the dispatch origin from an unverified message field, enabling runtime-call execution as an arbitrary victim account - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`pallet_hyper_fungible_token::on_accept` allows an incoming ISMP `PostRequest` to carry ABI-encoded `data` containing a SCALE-encoded `RuntimeCall` to dispatch on the destination chain. When `SubstrateCalldata.signature` is `None`, the pallet derives the dispatch `origin` purely from `message.from` (an application-layer bytes field inside the ABI body) via `T::EvmToSubstrate::convert`, and then calls `runtime_call.dispatch(RawOrigin::Signed(origin))` — without any cryptographic signature proving that the holder of that account actually authorized this specific runtime call.

### Finding Description

`T::EvmToSubstrate` in its default implementation (`modules/pallets/hyper-fungible-token/src/types.rs:130-138`) is a pure, public, deterministic function: `AccountId = zero_pad(evm_address)`. Anyone in the world can compute, for any target victim's substrate `AccountId32` (or any EVM address), the exact `message.from` bytes needed to make `T::EvmToSubstrate::convert` yield that victim's account — with no possession of a private key required.

The `signature` field exists specifically to bind a runtime call cryptographically to the account it will execute as (verified against `nonce` + `runtime_call` for Ed25519/Sr25519, or ECDSA-recovered and checked equal to `beneficiary` for Ecdsa). The unsigned branch bypasses this binding entirely: it treats the unauthenticated `message.from` claim as sufficient proof of authorization to dispatch a `RawOrigin::Signed` call as that account — structurally identical to the advisory's flaw, where an unverified identity claim (`email`) was trusted as sufficient for authentication instead of requiring a proof of ownership.

Critically, `message.from` in the unsigned path is *not* validated against anything besides being decodable bytes of the right length — it is not required to equal the actual EVM `msg.sender` that dispatched the corresponding burn/transfer, nor is it required to equal `beneficiary` (`message.to`). The pallet's `on_accept` authentication only checks that the *module/contract* (`request.from`/`source`) is a registered peer (`ContractToAsset::get(source, &from)`); it does not police what the *application-level* `message.from` field inside the ABI body contains. Whether an attacker can freely choose an arbitrary `message.from` depends on the specific `HyperFungibleToken`/`WrappedHyperFungibleToken` deployment on the source EVM chain, but the destination-side pallet code makes no cryptographic attempt to verify the claimed identity before dispatching a privileged call under it — the entire security property rests on trusting the peer contract's encoding discipline rather than an on-chain, per-call cryptographic check.

### Impact Explanation
A successful forgery/misuse of the unsigned calldata path lets an attacker cause arbitrary (non-filtered) `RuntimeCall`s to be dispatched with `RawOrigin::Signed(victim_account)` on the destination chain. Because `BaseCallFilter` is the only gate, any call the runtime does not explicitly filter (governance votes, XCM transfers, staking operations, proxy/permission grants, treasury spends the victim is authorized for, etc.) can be executed as the victim without their signature. This is unauthorized app action / potential unbacked state mutation attributable to an account that never authorized it — matching the "unauthorized app action" acceptance criterion.

### Likelihood Explanation
Reachable by anyone able to dispatch (or influence the encoding of) an ISMP `PostRequest` body destined for a `pallet-hyper-fungible-token` deployment with cross-chain calldata enabled — i.e., an unprivileged sender on the paired EVM chain calling the peer contract's `send()`/transfer function with attacker-chosen `data`. No relayer collusion or privileged access is required beyond normal message relaying, which any unprivileged relayer performs. The likelihood that the peer EVM contract's encoding of `message.from` can be influenced or is not tightly bound to `msg.sender` in every deployment is unverified from the available EVM contract snippets alone (the reviewed `HyperFungibleToken.sol` hard-codes `from: abi.encodePacked(msg.sender)`), so exploitability depends on whether any registered peer implementation deviates from that binding, or whether runtime integrators rely on the unsigned path believing it to be safely attributed.

### Recommendation
Remove the no-signature calldata-dispatch branch, or require a real cryptographic signature (as already implemented for Ed25519/Sr25519/Ecdsa) for every runtime call dispatched with `RawOrigin::Signed`. If a signature-less path must remain, dispatch such calls under a distinct, clearly weaker origin (e.g., a purpose-built origin that cannot perform privileged/asset-moving actions) rather than `RawOrigin::Signed(origin)`, and never derive that origin from an unauthenticated `message.from` field alone.

### Proof of Concept
1. Attacker (or any relayer) constructs/observes an ISMP `PostRequest` whose ABI body decodes to `Message { from: <victim's EVM address padded>, to: <anything>, amount: <anything>, data: SubstrateCalldata { signature: None, runtime_call: <SCALE-encoded privileged call> } }`, sent from a registered peer contract/chain.
2. On delivery, `pallet_hyper_fungible_token::on_accept` runs `T::EvmToSubstrate::convert(H160::from_slice(&from_bytes[..]))`, producing `victim_account = zero_pad(victim_evm_address)` deterministically, with no signature check.
3. `runtime_call.dispatch(RawOrigin::Signed(victim_account))` executes the attacker-supplied call as if `victim_account` had signed it — even though the victim never produced a signature over `(nonce, runtime_call)`.
4. Any call not excluded by `BaseCallFilter` succeeds, attributed to the victim's account. [1](#0-0) [2](#0-1)
