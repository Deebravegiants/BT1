This confirms the vulnerability. The docs explicitly show the intended trust model: the `shop` field from `data.shop` (derived from the `X-Shopify-Shop-Domain` header) is treated as the authenticated tenant identifier and passed directly into application logic (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), yet this field is never part of the HMAC-covered payload.

### Title
Webhook HMAC does not bind the shop-domain header, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, excluding the `X-Shopify-Shop-Domain` header value that is exposed via `Request#shop`. `Registry.process` validates the HMAC over the body only, then forwards `request.shop` unchecked to the application's webhook handler as the authenticated tenant identifier.

### Finding Description
`Utils::HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest(sha256, secret, verifiable_query.to_signable_string)` and compares it to the `hmac` accessor of the `VerifiableQuery` implementation. [1](#0-0) 

For `Webhooks::Request`, `to_signable_string` is defined as just `@raw_body`, while `shop` is read independently from the `shopify-shop-domain` / `x-shopify-shop-domain` header and is not included anywhere in the signed string. [2](#0-1) 

`Registry.process` validates only `Utils::HmacValidator.validate(request)` (i.e. the body's HMAC), and then unconditionally trusts `request.shop` as the tenant when constructing `WebhookMetadata` passed to the app's handler: [3](#0-2) 

The identity binding that should hold is: `hmac_signed_bytes == bytes_the_app_attributes_to_a_shop`. Here, `hmac_signed_bytes = raw_body` but `bytes_the_app_attributes_to_a_shop = raw_body + shop-domain header`. Because the header is outside the signed bytes, any two requests carrying the same body and a validly-computed HMAC (for that body) will pass validation regardless of which shop-domain header accompanies them.

An unprivileged internet user who has legitimate access to their own shop's app installation (e.g., a free Shopify development/trial store, an option open to anyone) will receive genuine Shopify-signed webhook deliveries containing a `(raw_body, hmac)` pair valid under the app's `client_secret`. Since the endpoint is a public HTTP callback URL with no additional authentication (that's the entire purpose of webhook HMAC validation), the attacker can directly POST that captured `(raw_body, hmac)` pair to the same endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds because the header was never part of the signed content, and `Registry.process` then invokes the app's handler believing the event legitimately originated from the victim shop.

### Impact Explanation
This breaks the tenant boundary the gem is documented to provide: `data.shop` is the field applications are told to trust as "The shop domain of the webhook" and to use for shop-scoped state changes (job dispatch, data writes, redaction processing, etc.), per the gem's own documentation. [4](#0-3)  Forging the shop attribution of an otherwise validly-signed webhook payload is a cross-tenant integrity violation — the app can be made to process/attribute another merchant's event stream (or the attacker's own event content) as if it came from a different, victim shop, without knowledge of `api_secret_key`. Depending on how the host app keys per-shop side effects (queue jobs, redaction, uninstall handling, order/customer processing) off `data.shop`, this can lead to cross-tenant data corruption or spoofed lifecycle events (e.g. spoofing `app/uninstalled` or `shop/redact` against a shop the attacker doesn't own).

### Likelihood Explanation
Requires only: (1) legitimate access to receive at least one real webhook for an attacker-controlled shop (trivially obtainable — any developer can create a Shopify partner/dev store and install the target app), and (2) the ability to send an arbitrary HTTP POST to the app's public webhook callback URL with custom headers, which is inherent to how these endpoints work. No secret material, session, or privileged account is required.

### Recommendation
Include the shop-domain (and ideally topic and webhook-id) in the signed content verified against the HMAC, or otherwise cryptographically bind the shop identity to the payload before trusting `request.shop`. At minimum, document that `X-Shopify-Shop-Domain` is not covered by the webhook HMAC and that integrators must independently verify the shop is one for which they have an active, expected subscription/session before acting on the payload.

### Proof of Concept
1. Attacker installs the target app on their own Shopify development store `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header value `H` that Shopify computed with the app's `client_secret`.
2. Attacker sends a new POST directly to the app's public webhook callback URL with:
   - Body: `B` (unchanged)
   - Header `X-Shopify-Hmac-Sha256: H` (unchanged)
   - Header `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (changed)
   - Header `X-Shopify-Topic`, `X-Shopify-Webhook-Id` as needed to route to a registered handler.
3. The app builds `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` and calls `Registry.process(request)`.
4. `Utils::HmacValidator.validate(request)` succeeds because `to_signable_string` only ever hashes `B`, which is unchanged. [5](#0-4) 
5. `Registry.process` calls the registered handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, so the application performs shop-scoped side effects attributing attacker-supplied content to the victim shop. [6](#0-5)
