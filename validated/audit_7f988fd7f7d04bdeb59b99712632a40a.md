### Title
Webhook `shop` identity is asserted from an unauthenticated header and is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop` identity that `Registry.process` hands to the app's webhook handler is read from an independent, unsigned HTTP header (`X-Shopify-Shop-Domain`). The binding "HMAC-verified bytes == shop asserted to the handler" does not hold, so a request whose body+HMAC pair is a legitimately signed webhook (obtainable by anyone who can trigger a real webhook, e.g. by installing the app on their own store) can be replayed with the `shop-domain` header rewritten to a victim shop, and the library will pass that forged shop identity to the app as if it were authentic.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is derived purely from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is never part of the signed content: [2](#0-1) 

`Registry.process` validates the HMAC over the request (i.e., over the body only) and then dispatches the handler using `request.shop`, taking that header value at face value as the tenant identity: [3](#0-2) 

`Utils::HmacValidator.validate` confirms this: it only ever compares `verifiable_query.hmac` against a signature computed from `verifiable_query.to_signable_string` (the body), never incorporating `shop`: [4](#0-3) 

Because the app's `api_secret_key` (used to sign webhooks) is shared across every shop that installs the app, and the HMAC never encodes which shop it belongs to, any correctly-signed `(raw_body, hmac)` pair - even one legitimately produced for the attacker's own shop - remains valid when replayed with a different `shop-domain` header value. The identity binding the gem should enforce is:
`shop authenticated by HMAC == shop delivered to WebhookMetadata`
but in fact the gem only authenticates the body; `shop` is taken from unauthenticated bytes.

### Impact Explanation
This is a cross-tenant identity-binding bypass: an unprivileged attacker who has installed the target app on their own (attacker-controlled) shop can capture a genuine, correctly-signed webhook delivery (body + `X-Shopify-Hmac-Sha256`) from Shopify for their own shop, then POST that exact body/HMAC to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain` with a victim shop's domain. `Registry.process` will accept it (HMAC validates, since it only checks the body) and invoke the app's handler with `WebhookMetadata#shop` set to the victim's domain. Any host application logic that uses this `shop` value to key session/data lookups (e.g. `shop/redact`, `customers/data_request`, `customers/redact`, `app/uninstalled`, order/customer webhooks) can be tricked into applying attacker-supplied payloads to another tenant's records/session state - a cross-tenant data-integrity and potential data-exfiltration/GDPR-workflow bypass.

### Likelihood Explanation
Moderate-to-high: the attacker only needs a Shopify Partner/dev store (trivial and free) to legitimately install the target app and receive real signed webhooks; no access to the app's `client_secret` or any privileged account is required, and the header substitution requires only a raw HTTP request to the app's public webhook endpoint.

### Recommendation
Bind the shop identity to the cryptographic proof: include the `shop-domain` (and `topic`, `webhook-id`) header values in the HMAC-signable content, or require the caller to independently verify that the shop in the `WebhookMetadata` corresponds to a shop with an active, previously-established session/install record before trusting it, rather than trusting the unauthenticated header value from `Request#shop`.

### Proof of Concept
1. Install the target Shopify app on attacker-owned shop `attacker.myshopify.com`; trigger any subscribed webhook topic (e.g. `orders/create`) to receive a genuine delivery with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC-SHA256(api_secret_key, B)`).
2. Replay the captured request to the app's webhook endpoint, keeping `B` and `H` unchanged but setting `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(api_secret_key, B)` and matches `H` — validation passes.
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)`, i.e., attacker-controlled data is delivered to the app tagged as belonging to the victim shop.
