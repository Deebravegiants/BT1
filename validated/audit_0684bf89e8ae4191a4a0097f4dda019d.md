Audit Report

## Title
Fee-on-transfer / non-standard ERC20 tokens break custody accounting in `ERC20Transactor` - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `ERC20Transactor::deposit_asset_with_surplus` credit/release the XCM-requested `amount` into `AssetsInHolding` based solely on the ERC20 contract's boolean `transfer` return value, without verifying the actual balance delta moved. For fee-on-transfer, deflationary, or rebasing ERC20 tokens, the real tokens moved into/out of the checking account can differ from `amount`, decoupling the XCM executor's bookkeeping from real custody.

## Finding Description
In `withdraw_asset_with_surplus`, the transactor calls `IERC20::transferCall` for `amount` and, once it observes `!did_revert()` and a decoded `true` return, unconditionally constructs `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))` — using the requested `amount`, not any measured balance change of the checking account [1](#0-0) . Symmetrically, `deposit_asset_with_surplus` transfers `amount` from the checking account to the beneficiary and treats a `true` return as fully successful, again without checking the beneficiary's actual balance increase [2](#0-1) .

The matcher backing this transactor, `ERC20Matcher` / `IsLocalAccountKey20`, matches any location of the shape `(0, [AccountKey20 { .. }])` with no allow-list or registration check whatsoever [3](#0-2) . This confirms the transactor is fully permissionless: any deployed `pallet-revive` contract address can be referenced as an XCM asset id and immediately be transacted through this code path — there is no allow-listing guard mitigating the missing balance-delta check.

`ERC20Transactor` is included in `AssetTransactors` on Asset Hub Westend, so it is reachable from ordinary unprivileged XCM execution entry points [4](#0-3) .

## Impact Explanation
Because the code trusts the requested `amount` combined with a boolean success flag instead of measuring `balanceOf` before/after the transfer, an attacker who deploys a fee-on-transfer/deflationary ERC20 contract can cause the XCM executor's in-memory `AssetsInHolding` to be credited with more value than what actually lands in the `TransfersCheckingAccount` (on withdraw), or can cause the beneficiary to receive less than `amount` while the deposit is reported as fully successful (on deposit). Repeated over many transactions, this decouples the aggregate "virtual" ERC20 credit recognized by the XCM executor from the real ERC20 balance actually held in the checking account, which is a genuine custody-accounting bug rather than a purely cosmetic issue.

## Likelihood Explanation
Triggering this requires no special privilege: any account can deploy an ERC20 contract via `pallet-revive` with non-standard `transfer` semantics (fee-on-transfer is a common, trivially implementable pattern) and reference it as an `AccountKey20` XCM asset id — the matcher imposes no allow-list, so exploitation is available to any unprivileged user submitting an XCM program (e.g., via `pallet_xcm::execute`) that involves `WithdrawAsset`/`DepositAsset` against such a token.

## Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, query `balanceOf` of the checking account/beneficiary before and after the `transfer` call and use that measured delta — not the requested `amount` — when constructing or releasing the `Erc20Credit`. Alternatively, restrict `ERC20Matcher` to a governance-curated allow-list of contracts verified to be standards-compliant, non-fee-on-transfer, non-rebasing ERC20 tokens.

## Proof of Concept
1. Deploy a `pallet-revive` ERC20 contract whose `transfer` withholds e.g. 5% of `value` on every call but otherwise returns `true` and does not revert.
2. From an unprivileged account, submit an XCM program (e.g. via `pallet_xcm::execute`) referencing asset id `Location(0, [AccountKey20 { key: <contract_address> }])` with `amount = 1000`, containing `WithdrawAsset` followed by an instruction consuming the resulting holding.
3. Per `withdraw_asset_with_surplus` (lines 166–203 of `erc20_transactor.rs`), only 950 real tokens land in `ERC20TransfersCheckingAccount`, but `Erc20Credit(1000)` is credited into `AssetsInHolding`, demonstrating the accounting desync described above.

/// `Contains<Location>` implementation that matches locations with no parents,
/// a `PalletInstance` and an `AccountKey20` junction.
pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}

/// [`xcm_executor::traits::MatchesFungibles`] implementation that matches
/// ERC20 tokens.

	MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>;
