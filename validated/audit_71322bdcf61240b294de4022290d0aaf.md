### Title
Webhook `shop`, `topic`, and `webhook_id` fields are not covered by HMAC verification, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so the HMAC signature validated by `Utils::HmacValidator.validate` binds *only* the body bytes to the app's `api_secret_key`. It does not bind the `x-shopify-shop-domain`, `x-shopify-topic`, `x-shopify-webhook-id`, or `x-shopify-api-version` headers. `Registry.process` trusts these unbound headers directly when constructing the `WebhookMetadata` passed to the app's handler, breaking the identity binding: `shop authenticated (HMAC(secret, body) valid) ≠ shop the handler believes sent the data (request.shop header)`.

### Finding Description
`Request#to_signable_string` is defined as:
```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

`Utils::HmacValidator.validate` computes `HMAC-SHA256(api_secret_key, verifiable_query.to_signable_string)` and compares it to the `hmac` header using `OpenSSL.secure_compare` [2](#0-1) . Since `to_signable_string` is only the raw body, the signature says nothing about which shop, topic, or webhook id the body is associated with.

`Registry.process` uses this validation result to gate processing, then reads `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` straight from headers and passes them into `WebhookMetadata`, which is handed to the app-supplied `handler.handle`:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [3](#0-2) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all simple header reads with no cryptographic tie to the body or to each other:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [4](#0-3) 

`WebhookMetadata` is a plain struct that simply carries whatever `Registry.process` supplied, with no independent verification: [5](#0-4) 

**Exploitable identity binding failure:** the equality the code implicitly relies on is `HMAC(secret, raw_body) valid ⇒ (shop, topic, webhook_id) in headers are authentic for that body`. This equality does not hold, because `secret` is only mixed with `raw_body`. Any attacker who can obtain one valid `(raw_body, hmac)` pair — trivially available since they can install the target app on their *own* development/test store and legitimately receive real webhook deliveries for that store — can then replay that exact `raw_body` + `hmac` pair to the app's webhook endpoint while substituting arbitrary values for `x-shopify-shop-domain`, `x-shopify-topic`, and `x-shopify-webhook-id`. The `HmacValidator.validate` check still passes because it only checks the body bytes, and `Registry.process` will happily dispatch the handler with a spoofed `shop` (and/or spoofed `topic`) as if Shopify had sent that webhook for a different merchant.

This is functionally identical to the report's bug class: a field that is *acted upon* (here, `shop`/`topic`, used to route/attribute the webhook and select the handler) is not covered by the authenticity check (the HMAC), letting an unprivileged actor forge the field while keeping the check green.

### Impact Explanation
This enables cross-tenant webhook spoofing: an attacker can make a host application believe a webhook (with attacker-chosen body content and topic) originated from a shop they don't operate. Depending on how the host app's `WebhookHandler` implementations use `data.shop` and `data.topic` (which is the intended usage pattern promoted by this gem, e.g. looking up/mutating that shop's session/record, deleting shop data for `shop/redact`, or acting on `app/uninstalled`), this can lead to unauthorized cross-tenant actions being triggered against a victim shop's app record. This matches the Critical "cross-tenant access" impact category, since the boundary broken is exactly the tenant-isolation guarantee the HMAC check is supposed to provide.

### Likelihood Explanation
Likelihood is realistic but requires the attacker to first obtain a legitimately-signed `(raw_body, hmac)` pair, which is straightforward for any developer who can install the target app on a shop they control (a normal, unprivileged onboarding flow, not requiring the app's `client_secret`). Many webhook topics (e.g., ones with minimal/templated JSON bodies) make this pair easy to acquire and predict; the topic and shop headers are freely re-writable in the replayed HTTP request since they are ordinary headers, not covered by the signature.

### Recommendation
Include the routing/identity fields (`shop`, `topic`, and ideally `webhook_id`/`api_version`) in the signable string used for HMAC verification, or independently authenticate the `shop`/`topic` headers against Shopify (e.g., verify that the shop domain is expected/registered, and reject if the topic doesn't match the handler that would validate the body's schema). At minimum, document and encourage validating `shop` against an app's known/installed shops before trusting `WebhookMetadata#shop` in handler logic, and consider binding the header values into the HMAC computation, mirroring how `Auth::Oauth::AuthQuery#to_signable_string` binds `code`, `host`, `shop`, `state`, and `timestamp` together [6](#0-5) .

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and receives a legitimate webhook delivery, e.g. for `app/uninstalled` with body `{}`:
   - Headers: `x-shopify-topic: app/uninstalled`, `x-shopify-hmac-sha256: <valid_hmac_for_{}>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker crafts a new HTTP POST to the app's webhook endpoint reusing the exact same body `{}` and the exact same `x-shopify-hmac-sha256` value, but sets:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: shop/redact` (or any topic registered by the app whose handler doesn't validate the body schema strictly)
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which computes `HMAC(secret, "{}")` — identical to step 1's value — so validation passes [7](#0-6) .
4. The registered handler for `shop/redact` (or whichever topic was spoofed) is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "shop/redact", body: {}, ...)`, causing the host application to perform shop-redaction (or other topic-specific) logic against `victim-shop.myshopify.com`, a shop the attacker does not control and never triggered this action for.
