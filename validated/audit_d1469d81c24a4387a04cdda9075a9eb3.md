Based on the investigation, there is a plausible analog to the "missing elliptic-curve validity check on inputs" bug class, located in the QR-code/signup key-decoding path rather than in a smart contract verifier.

### Title
Missing Curve25519 Point Validation on User/Backend Public Keys Used to Encrypt Biometric Data - (File: `src/backend/user_status.rs`)

### Summary
`decode_public_key` in `src/backend/user_status.rs` only checks that a base64-decoded key is exactly 32 bytes long and wraps it directly into a `sodiumoxide::crypto::box_::PublicKey` without verifying it is a valid, full-order Curve25519 point. [1](#0-0) 

### Finding Description
The function `decode_public_key` decodes the `self_custody_public_key` (originating from user/app-controlled `orb_qr_link::UserData`, whose integrity is only checked against a QR-embedded hash via `user_data.verify(user_data_hash)`) as well as the backend-provided iris/face/tier2 encryption keys, and constructs a `PublicKey` from any 32-byte value: [2](#0-1) 

No check is performed that the 32 bytes correspond to a valid, full-order point on Curve25519 (i.e., rejecting the identity element or low-order/torsion points). These `PublicKey`s — most notably `self_custody_user_public_key`, which is populated from data supplied through the user-scanned QR-code/app flow — are subsequently propagated into `personal_custody_package::Credentials` and used to encrypt the user's biometric material (iris/face images) via libsodium sealed-box encryption referenced in `src/plans/personal_custody_package.rs` and `src/agents/image_notary.rs`. [3](#0-2) [4](#0-3) 

Curve25519/X25519 clamps scalar multipliers, so a small-order or degenerate public key forces the resulting shared secret used for encryption into a small, predictable set of values (or a fixed value for the identity point) regardless of the sender's ephemeral private key. This mirrors the report's core complaint: skipping "is this a valid point on the curve" checks on attacker-influenced curve points before they're consumed by cryptographic operations that assume well-formed group elements.

### Impact Explanation
If an unprivileged user/app supplies a degenerate `self_custody_public_key` through the signup QR flow, and orb-core accepts it without curve-membership/order validation, the resulting sealed-box ciphertext protecting iris/face biometric images could be decryptable by any party who knows the (small, enumerable) set of possible shared secrets — without needing the legitimate private key. This is a concrete biometric data disclosure risk for the specific user's uploaded/retained iris and face images tied to that signup.

### Likelihood Explanation
Exploitation requires an attacker to control or manipulate the QR-code-derived app data used for `self_custody_public_key` (or the matching `user_data_hash`), which is within the "unprivileged user" trust boundary explicitly in scope. Actual exploitability further depends on whether the underlying `sodiumoxide`/libsodium sealed-box implementation performs its own internal all-zero shared-secret rejection (libsodium's `crypto_box_seal` does reject the all-zero case since v1.0.16), which would mitigate the worst-case (identity-point) scenario but not necessarily the broader small-subgroup case. I was not able to fully confirm from available index content the exact call site and library version behavior for the sealed-box encryption call in `personal_custody_package.rs`/`image_notary.rs` before the tool budget ran out, so likelihood should be treated as uncertain pending direct inspection of those files and the `sodiumoxide`/libsodium version in use.

### Recommendation
In `decode_public_key`, after decoding the 32 bytes, explicitly reject known low-order/identity points (the standard Curve25519 small-order point blacklist) before constructing the `PublicKey`, matching the general principle in the referenced report that curve-point validity should be explicitly checked rather than implicitly relied upon by downstream primitives.

### Proof of Concept
Not constructed — would require confirming the exact sealed-box encryption call site and the specific `sodiumoxide`/libsodium version's internal safeguards, which the available index did not fully expose. A Devin session with full file access to `src/plans/personal_custody_package.rs` and `src/agents/image_notary.rs` (the `sealedbox` call sites) would be needed to construct a concrete PoC (craft a small-order 32-byte key as `self_custody_public_key`, drive it through the signup flow, and verify predictable/derivable shared secret in the resulting sealed box).

**Uncertainty note:** Due to index size limits, I could not retrieve the exact `sealedbox::seal` call sites in `src/plans/personal_custody_package.rs` and `src/agents/image_notary.rs`, nor confirm the exact libsodium/sodiumoxide version behavior regarding small-order key rejection. Confirming these would require a Devin session with full repository access.

fn decode_public_key(payload: &str) -> Result<PublicKey> {
    let bytes = BASE64.decode(payload.as_bytes())?;
    let bytes = <[u8; 32]>::try_from(bytes)
        .map_err(|x| eyre!("incompatible public key length: {}", x.len()))?;
    Ok(PublicKey(bytes))
}
