Confirmed: the webhook `to_signable_string` returns only the raw body, and `HmacValidator.validate` signs/verifies solely against that string. None of `topic`, `shop`, or `webhook_id` (parsed from headers) are part of the signed material.

### Title
Webhook shop-domain, topic, and webhook-id headers are not covered by the HMAC, allowing an authenticated attacker to relabel a genuine webhook as belonging to another shop - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` by signing only the raw request body (`to_signable_string` returns `@raw_body`), while `shop`, `topic`, and `webhook_id` are read directly from unauthenticated HTTP headers. `Registry.process` accepts the request once `Utils::HmacValidator.validate` succeeds on the body alone, then dispatches `WebhookMetadata` (including `shop:` and `topic:`) to the host app's handler.

### Finding Description
The identity binding that should hold is: `hmac == HMAC(secret, body || shop || topic || webhook_id)`, i.e. every field the host app acts on as tenant/topic identity should be covered by the signature. Instead, the actual binding implemented is `hmac == HMAC(secret, body)` only: [1](#0-0) 

`shop`, `topic`, and `webhook_id` are parsed straight from headers with no cryptographic tie to the signed body: [2](#0-1) 

`HmacValidator.validate`/`validate_signature` only ever hashes `verifiable_query.to_signable_string`, which for this class is the raw body: [3](#0-2) 

`Registry.process` trusts this validation and forwards the header-derived `shop`/`topic`/`webhook_id` straight to the handler as authenticated metadata: [4](#0-3) 

An attacker who legitimately controls a Shopify store (any developer/merchant account) can register a webhook for that store and receive genuine, correctly-HMAC-signed deliveries from Shopify for arbitrary bodies they can influence (e.g. a `products/create` payload whose contents they fully control). Because the HMAC covers only the body, the attacker can take that genuinely-signed request and replay it to the victim app's shared webhook endpoint after swapping only the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header to any value of their choosing — the signature still validates since the body is untouched.

### Impact Explanation
`Registry.process` passes the forged `shop` value into `WebhookMetadata` without any additional check, so the host application's webhook handler processes attacker-controlled data while believing it originated from a different, arbitrary shop. Since webhook handlers commonly use `shop` to select the tenant's session/store record for side effects (e.g., updating that shop's data, deciding which tenant's webhook this is), this breaks the shop-authentication boundary and enables cross-tenant data confusion/injection — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only that the attacker control any Shopify store capable of subscribing a webhook to the target app's endpoint path (a normal unprivileged action available to any app install), plus the ability to send an HTTP POST with modified headers to the app's public webhook URL — no access to `api_secret_key`, tokens, or the victim's credentials is needed. This is a purely internet-facing, unprivileged attack path.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the material that is signed/verified — i.e., derive `to_signable_string` (or a dedicated verification input) from the concatenation of the raw body and these header values (or otherwise cryptographically bind them), and reject/re-verify if any of these headers do not match what was signed.

### Proof of Concept
1. Attacker creates a normal Shopify development store and installs the target app, allowing them to receive genuine `X-Shopify-Hmac-Sha256`-signed webhook deliveries from Shopify with a body they can shape (e.g. by creating a product with attacker-controlled `title`/fields).
2. Attacker captures this genuine delivery: `raw_body`, `X-Shopify-Hmac-Sha256`, `X-Shopify-Topic`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker replays the exact same `raw_body` and `X-Shopify-Hmac-Sha256` to the victim app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` (unchanged), so `Utils::HmacValidator.validate` succeeds: [5](#0-4) 
5. `Registry.process` calls the handler with `shop: "victim-shop.myshopify.com"` even though the payload actually originated from the attacker's own store, achieving cross-tenant identity confusion. [6](#0-5)

        def validate(verifiable_query)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
