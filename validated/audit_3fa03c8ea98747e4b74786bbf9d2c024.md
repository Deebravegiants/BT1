### Title
Unbounded attacker-controlled scrypt `n`/`r`/`p` parameters in SECO metadata enable pre-auth DoS - ([File: libraries/secure-container/src/crypto.js])

### Summary
`decrypt()` in `libraries/secure-container/src/index.js` decodes attacker-supplied `metadata.scrypt.{n,r,p}` fields and passes them unvalidated into `stretchPassphrase`/`scrypt()` before any passphrase-based authentication succeeds. Because the SHA-256 checksum guarding the file is not a keyed MAC, an attacker can trivially craft a `.seco`/QR payload with valid checksum but extreme `n`/`r`/`p`, forcing massive CPU/memory consumption in `scrypt()` prior to auth.

### Finding Description
The call chain is: `decrypt(encryptedData, passphrase)` → `conFile.decode` → `conMetadata.decode(fileObj.metadata)` → `conMetadata.decryptBlobKey(metadata, passphrase)` → `boxDecrypt` → `stretchPassphrase(passphrase, scryptParams)` → `scrypt(passphrase, salt, { N: n, r, p, dkLen: 32 }, 'buffer')`. [1](#0-0) 

`metadata.js`'s `struct` declares `n`, `r`, `p` as plain `UInt32BE` fields with no range restriction, and `decode()` performs no bounds validation, only a byte-length warning: [2](#0-1) 

`stretchPassphrase` and `boxDecrypt` forward these values directly into `scrypt()` without any sanity checks (no cap on `N`, `r`, `p`, or `N*r*128` memory bound): [3](#0-2) [4](#0-3) 

Before decoding metadata, `decrypt` only checks a SHA-256 checksum of `metadata`+`blob`: [5](#0-4) 

This checksum is computed with plain `sha256` (not HMAC/keyed), so an attacker crafting the entire file from scratch (e.g., import backup, QR/deeplink payload) can freely set `n`/`r`/`p` to extreme values (up to `2^32-1` each, since they're `UInt32BE`) and simply recompute the matching checksum themselves — no valid passphrase or secret knowledge is required to pass this check. This means the flow reaches `scrypt()` with attacker-controlled `N`/`r`/`p` regardless of whether the supplied passphrase is correct, since key derivation happens unconditionally before the AES-GCM auth tag (which would validate correctness) is even checked.

### Impact Explanation
An attacker who can get a crafted `.seco` file or QR/deeplink import processed by the wallet (e.g., "restore from backup" or "import wallet" flow calling `decrypt`) can force the wallet's JS runtime to attempt scrypt with parameters like `N=2^31`, causing an attempted allocation of gigabytes-to-exabytes of memory (`~ N * r * 128` bytes) and/or pegging CPU for an extended period. This crashes or hangs the wallet process during the unlock/import path, a denial-of-service that blocks legitimate use and can be leveraged in crash-and-retry patterns against the unlock flow. This matches a resource-exhaustion / DoS impact class rather than direct key compromise.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs to supply file bytes (no valid passphrase, no privileged state) through any import/QR/deeplink path that eventually calls `decrypt(encryptedData, passphrase)`. Because the checksum is an unkeyed SHA-256 (not a MAC), the attacker can compute a self-consistent, valid file with malicious `scrypt` parameters, making this fully attacker-reproducible and not dependent on guessing any secret.

### Recommendation
Enforce strict bounds on `metadata.scrypt.n`, `r`, and `p` immediately after `conMetadata.decode()` (or inside `decode`/`stretchPassphrase`/`boxDecrypt`) — e.g., reject if `n` is not a power of two within an allowed range (such as `<= 2^20`), `r * p` is bounded, and the total derived memory cost `128 * n * r` does not exceed a fixed ceiling (e.g., a few tens of MB), throwing before invoking `scrypt()`. Additionally, consider binding the checksum to a fixed/allow-listed set of scrypt parameters or authenticating the metadata with a MAC that isn't fully attacker-forgeable.

### Proof of Concept
Fuzz/unit test plan for `libraries/secure-container/src/__tests__/crypto.test.js` or new test:
1. Build a `metadata` object via `conMetadata.create()` then override `metadata.scrypt = { salt, n: 2**31, r: 8, p: 1 }`.
2. Encode metadata/blob with `conFile.encode`, compute checksum via `conFile.computeChecksum` (attacker can do this without knowing the passphrase).
3. Call `decrypt(encryptedData, 'any-passphrase')` and assert that the call either:
   - throws a clear "scrypt parameters out of bounds" error immediately after `conMetadata.decode`, **before** `stretchPassphrase`/`scrypt()` is invoked, or
   - is rejected under a strict resource/time budget.
4. Current behavior: no such bound exists in `metadata.js` or `crypto.js`, so the call proceeds into `scrypt()` with attacker-chosen `N`, demonstrating the missing guard (expected to hang/OOM in a real run, so the PoC should assert on presence/absence of a pre-flight validation function rather than actually executing the huge scrypt call).

```javascript
export async function decrypt(encryptedData, passphrase) {
  const fileObj = conFile.decode(encryptedData)

  const checksum = await conFile.computeChecksum(fileObj.metadata, fileObj.blob)
  if (!fileObj.checksum.equals(checksum))
    throw new Error('seco checksum does not match; data may be corrupted')

  const metadata = conMetadata.decode(fileObj.metadata)
  const blobKey = await conMetadata.decryptBlobKey(metadata, passphrase)
  const header = conHeader.decode(fileObj.header)
  const data = await conBlob.decrypt(fileObj.blob, metadata, blobKey)

  return { data, blobKey, metadata, header }
}
```

```javascript
export function createScryptParams(params = {}) {
  return { salt: randomBytes(32), n: 16_384, r: 8, p: 1, ...params }
}

// always returns 32 byte key
export async function stretchPassphrase(passphrase, { salt, n, r, p } = createScryptParams()) {
  const key = await scrypt(passphrase, salt, { N: n, r, p, dkLen: 32 }, 'buffer')
  return { key, salt }
}
```

```javascript
export async function boxDecrypt(passphrase, blob, { iv, authTag }, scryptParams) {
  scryptParams = { ...createScryptParams(), ...scryptParams }
```
