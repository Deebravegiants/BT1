### Title
Emporium Min-proof path lets an unprivileged attacker bypass EIP712 authorization and all balance accounting to drain any assets held by the Emporium contract - (File: contracts/CircomDataBuilder.sol / contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
When `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `formInputForCircom` routes to `formInputEmporiumMin`, which only proves `message == Poseidon(messageSeed)` — a value the attacker fully controls and can satisfy with zero real funds. Because `erc20TokenAddresses` is empty, every balance-accounting loop that would normally constrain what Emporium is allowed to move (`Hinkal.transact`'s balance-diff loop and `EmporiumUpgradeable.runAction`'s `balancesBefore`/`balancesAfter` loop) never executes, while the `stack.ops` loop still executes unconditionally. Combined with `signerAddress == address(0)` short-circuiting `verifyWallet`'s EIP-712 signature check, an attacker can force Emporium to execute arbitrary calls from its own identity with no signature and no accounting whatsoever.

### Finding Description
The claimed invariant is: *assets Emporium can move in a transaction == assets accounted for in `balancesBefore`/`balancesAfter`*. This is broken.

Path:
1. `Hinkal.transact` calls `hinkalHelper.performHinkalChecks` → `CircomDataBuilder.formInputForCircom`. With `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, it selects `formInputEmporiumMin`, whose only public/private signals are `emporiumMessage`, `timeStamp`, `calldataHash` [1](#0-0) . The underlying circuit `MainEVMCircuitMin` only proves `message <== Poseidon(messageSeed)` — a trivial, self-satisfiable statement requiring no ownership of any UTXO, root, or nullifier [2](#0-1) .
2. `Hinkal.transact` computes `oldBalances`/`newBalances` over `circomData.erc20TokenAddresses`, and the balance-diff/slippage/UTXO-accounting loop (`for (uint64 i; i < circomData.erc20TokenAddresses.length; i++)`) is skipped entirely when that array is empty, so no balance change is ever checked against `amountChanges`/`slippageValues` [3](#0-2) .
3. `_externalTransact` also has an empty `deltaAmountChanges` array (loop bound = `erc20TokenAddresses.length == 0`), so no deposit is forced into Emporium before `runAction`, but it still calls `IExternalActionV2(externalAddress).runAction(circomData, deltaAmountChanges)` unconditionally [4](#0-3) .
4. Inside `EmporiumUpgradeable.runAction`, `balancesBefore`/`balancesAfter` are again computed over the (empty) `circomData.erc20TokenAddresses`, so the post-loop balance-change check (`balanceChange < 0` revert, `handleOut`) never executes [5](#0-4) . Meanwhile the `stack.ops` loop runs regardless of the token array length, performing `op.endpoint.call{value: op.value}(op.callData)` for every op with Emporium as `msg.sender` [6](#0-5) .
5. `verifyWallet` is meant to gate the `ops` via an EIP-712 signature from `stack.signerAddress`, but if the attacker sets `stack.signerAddress == address(0)`, the function returns immediately after marking the message used, with **no signature check at all** [7](#0-6) .

Root cause: the Min-proof optimization assumes an empty `erc20TokenAddresses` array implies "no assets are at stake," but it does not disable or gate the `ops` execution loop, which is unconditional and independent of the token-array length. The `onlyAllowedRecipient` modifier only restricts *who* can call `runAction` (Hinkal itself) [8](#0-7) , not what the decoded `EmporiumStack.ops` are allowed to do once inside; it provides no defense against a self-authored, un-signed op list.

The attacker's call: `Hinkal.transact` with a proof for `MainEVMCircuitMin` (self-chosen `messageSeed`), `circomData.externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `circomData.erc20TokenAddresses = []`, and `circomData.externalActionData.externalActionMetadata = abi.encode(EmporiumStack{signerAddress: address(0), ops: [{endpoint: <target>, invokeWallet: false, value: <X>, callData: <arbitrary calldata>}], ...})`. None of `performHinkalChecks` (calldata-hash integrity, `dimensionsCheck`, `checkOnchainCreation`), `verifyProof`, `rootHashExists`, or the balance/slippage `require`s constrain the content or destination of `op.callData`, because they all key off the (empty) token array or off values the attacker fully controls.

### Impact Explanation
Any ETH or ERC20 balance held by the Emporium contract at call time (e.g. leftover funds from interrupted/atomic multi-leg swap or bridge flows, fees, or funds transferred to it as part of a legitimate but not-yet-finalized transaction) can be moved out by an attacker's arbitrary `op.endpoint.call` with zero signature and zero accounting. This is theft of in-flight/protocol-held funds via calls "a wallet owner or prover never authorised," matching Critical (direct theft of shielded or in-flight user funds) since Emporium acts on behalf of users' funds during multi-step external actions and its identity (`msg.sender == Emporium`) may be trusted by other contracts (e.g. other registered external actions or approvals granted to Emporium). This is repeatable every time Emporium holds a nonzero balance and is not rate-limited beyond one `emporiumMessage` nonce per transaction (trivially rotated by the attacker each time).

### Likelihood Explanation
Preconditions: Emporium must hold some balance (ETH/ERC20) at attack time — this can occur naturally in atomic multi-leg/bridge flows or from stray deposits/approvals. The attacker needs no privileged role, no valid UTXO, no signature from any real user — they self-generate the Min proof, self-craft the `EmporiumStack` with `signerAddress = address(0)`, and pay only gas. This is a low-cost, low-skill, highly feasible and repeatable attack whenever Emporium's balance is nonzero.

### Recommendation
- Do not allow `EmporiumStack.ops` to execute when `signerAddress == address(0)` unless `erc20TokenAddresses.length > 0` is also enforced with full balance accounting; more robustly, always require a valid signed authorization for `ops` execution, regardless of `signerAddress`, or bind the Min-proof path to a strictly no-op/no-external-call code path (message-cancellation/administrative use only).
- Gate the Min-proof selection (`formInputEmporiumMin`) so it can never trigger execution of `stack.ops`; the Min path should be restricted to scenarios that provably cannot move value (e.g., require `stack.ops.length == 0` when `erc20TokenAddresses.length == 0`).
- Make `EmporiumUpgradeable.runAction`'s balance-accounting loop bound to something derived independently of attacker-controlled `erc20TokenAddresses` (e.g., record and re-check balances for every address touched by `ops`, or require `erc20TokenAddresses` to reflect all tokens referenced in `ops`).

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable` (as a registered external action with `HINKAL_EMPORIUM_ACTION_ID`), and an ERC20 token.
2. Fund the Emporium proxy directly with e.g. 100 tokens (simulate in-flight balance) and record `emporiumBalanceBefore`.
3. Locally generate a valid Groth16 proof for `MainEVMCircuitMin` using a self-chosen `messageSeed` (`message = Poseidon(messageSeed)`), and build `CircomData` with:
   - `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`
   - `erc20TokenAddresses = []`
   - `externalActionMetadata = abi.encode(EmporiumStack({signerAddress: address(0), ops: [{endpoint: address(token), invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, 100e18))}], maxFee: 0, deadline: type(uint256).max, v:0, r:0, s:0}))`
   - valid `rootHashHinkal`/`rootHashHinkalIndex` from any existing Merkle root, consistent `calldataHash` via `getHashedCalldata`.
4. Call `Hinkal.transact(a, b, c, dimensions, circomData)` from an attacker EOA holding no shielded UTXOs.
5. Assert: transaction succeeds (no revert), `token.balanceOf(attacker) == attackerBalanceBefore + 100e18`, `token.balanceOf(emporium) == emporiumBalanceBefore - 100e18`.
6. Assert the broken equality directly: compute `balancesBefore`/`balancesAfter` as the contract would (both empty arrays, i.e., length 0) and show they impose zero constraint despite `token.balanceOf(emporium)` having changed by 100e18 — demonstrating assets moved != assets accounted.
