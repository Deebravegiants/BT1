### Title
Dispatched requests with a `timeout` shorter than the destination's `challengePeriod` become permanently undeliverable, freezing relayer fees - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch()` and the Substrate `pallet-ismp` dispatcher both compute a request's `timeoutTimestamp` as `now + timeout`, an offset supplied entirely by the calling application/dispatcher, with no check that this offset exceeds the destination's configured `challengePeriod`. Because `HandlerV2` only allows a request to be delivered once the `challengePeriod` has elapsed on the state commitment, a request whose relative `timeout` is shorter than that `challengePeriod` will always be past its `timeoutTimestamp` the moment it becomes deliverable — mirroring the reported Gitcoin bug where a missing ordering check between two time-bound windows (`applicationsEndTime` vs `roundStartTime`) let one window's actions permanently disadvantage participants in the other window.

### Finding Description
When a request is dispatched, the timeout is stored as an absolute timestamp derived from a relative offset: [1](#0-0) 

```
uint64 timeoutTimestamp = post.timeout == 0 ? 0 : uint64(block.timestamp) + uint64(post.timeout);
```

No lower bound is enforced on `post.timeout` relative to `challengePeriod()`. The same pattern exists in the Substrate dispatcher: [2](#0-1) 

On the delivery side, `HandlerV2.handlePostRequests` requires that the `challengePeriod` has elapsed relative to the state commitment update time *before* it will even attempt to verify inclusion, and separately rejects any request whose `timeout()` has already passed: [3](#0-2) 

```
uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(request.proof.height);
uint256 challengePeriod = host.challengePeriod();
if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();
...
if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();
```

The same `verify_delay_passed`/challenge-period gate exists on the Substrate side: [4](#0-3) 

If a dispatcher supplies a `timeout` smaller than (or close to) the destination's `challengePeriod`, the request's `timeoutTimestamp` will be reached before the `challengePeriod` gate opens on the destination. Consequently `handlePostRequests`/`handleGetResponses` will *always* revert with `MessageTimedOut`/reject the message, and the request can never be delivered — exactly analogous to the reported issue where a missing ordering constraint between two time windows (`roundStartTime` vs `applicationsEndTime`) let one phase begin before the other properly concluded, structurally disadvantaging one side of the process. Here, the "voting" phase (challenge period) can never legitimately begin before the "application" phase (timeout) has already elapsed, permanently locking out delivery.

### Impact Explanation
Any relayer fee collected up-front in `dispatch()` (`IERC20(feeToken()).safeTransferFrom(...)` / native swap) is only refunded when the timeout is explicitly processed via `handlePostRequestTimeouts`, which itself requires the *same* `challengePeriod` to elapse on a non-membership proof: [5](#0-4) 

Since the request can never be delivered, the funds are only recoverable through the timeout path, and any application logic gated on request delivery success (vs. timeout) is forced down the failure/timeout path unconditionally — a "route unable to deliver messages" as defined in the acceptance criteria, with relayer fees frozen until a timeout is separately proven and processed.

### Likelihood Explanation
This requires no privileged or admin action — it is directly reachable by any unprivileged application calling `IDispatcher.dispatch()` (or the pallet-ismp `dispatch_request` extrinsic) with a `timeout` value shorter than the configured `challengePeriod` for the destination. This can happen accidentally (a naive integrator picking a short timeout without knowledge of `challengePeriod()`) or be triggered deliberately by a dispatcher wanting to guarantee its own or another party's message fails, since `challengePeriod()` is a public view function.

### Recommendation
Enforce in `dispatch()` (both EVM and Substrate paths) that `post.timeout` (when non-zero) must be greater than the configured `challengePeriod` for the destination state machine, mirroring the recommended fix in the original report (`require(roundStartTime > applicationsEndTime)`): add `require(post.timeout == 0 || post.timeout > challengePeriod(), "Host: timeout too short")` (or the Substrate equivalent) before computing `timeoutTimestamp`.

### Proof of Concept
1. Destination host has `challengePeriod = 1000` seconds.
2. An application calls `EvmHost.dispatch(DispatchPost{ ..., timeout: 10 })`, i.e. `timeoutTimestamp = block.timestamp + 10`.
3. Consensus/state commitment for the source chain height containing this request is only usable for delivery on the destination after `challengePeriod` (1000s) has elapsed since `stateMachineCommitmentUpdateTime`.
4. By the time `handlePostRequests` can pass its `ChallengePeriodNotElapsed` check (`delay >= 1000`), `block.timestamp >= dispatchTime + 1000 > dispatchTime + 10 = leaf.request.timeout()`, so `handlePostRequests` unconditionally reverts with `MessageTimedOut` for every relayer attempt.
5. The request commitment remains only reachable via `handlePostRequestTimeouts`, which itself requires the same `challengePeriod` gate on a non-membership proof height — the payer's fee is locked until that separate proof/processing occurs, and the message is never delivered.

    function handlePostRequests(IHost host, PostRequestMessage calldata request) external notFrozen(host) {
        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(request.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 requestsLen = request.requests.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](requestsLen);

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // check destination
            if (!leaf.request.dest.equals(host.host())) revert InvalidMessageDestination();
            // check time-out
            if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.request.hash());

pub fn verify_delay_passed<H>(host: &H, proof_height: &StateMachineHeight) -> Result<bool, Error>
where
	H: IsmpHost,
{
	let update_time = host.state_machine_update_time(*proof_height)?;
	let delay_period = host
		.challenge_period(proof_height.id)
		.ok_or(Error::ChallengePeriodNotConfigured { state_machine: proof_height.id })?;
	let current_timestamp = host.timestamp();
	Ok(delay_period.as_secs() == 0 || current_timestamp.saturating_sub(update_time) > delay_period)
}
