### Title
Webhook `shop` identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then dispatches the handler using a `shop` value read verbatim from the `X-Shopify-Shop-Domain` header — a field that is never included in the signed material. Any party who can obtain one genuinely-signed `(body, hmac)` pair (e.g. by installing the app on their own store and receiving a real webhook) can replay that exact body/HMAC pair while substituting an arbitrary `shop-domain` header, and the library will accept it as an authentic webhook "from" the victim shop.

### Finding Description
The HMAC-covered content for a webhook request is defined as only the raw body: [1](#0-0) 

The `shop` accessor, by contrast, is read directly from an attacker-controlled header with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` when building the data passed to the app's webhook handler: [3](#0-2) 

The identity binding this breaks (as an equality that should hold but doesn't) is:

`shop_bound_by_hmac(request) == request.shop`

In reality, `to_signable_string` (the HMAC-signed material) is a function only of `raw_body`, independent of `shop`. So for any two shop domains `A` (attacker) and `B` (victim), if the webhook body content is identical or attacker-predictable (many topics, e.g. mandatory compliance topics or app lifecycle topics, have bodies with static/predictable shape), a `(raw_body, hmac)` pair validly produced for shop `A`'s webhook remains HMAC-valid when replayed with `shop-domain: B`. The library provides no mechanism to detect this and does not document that `shop` is unauthenticated relative to the signature, so host applications built on the documented `WebhookMetadata#shop` value (used, per the `shopify_app` reference pattern in this repo's own docs, to key session/store lookups) will act on an attacker-chosen shop identity.

### Impact Explanation
This is a cross-tenant identity confusion: an app that keys any per-shop action (data lookup, GDPR redaction workflows, uninstall cleanup, billing state changes) off `WebhookMetadata#shop` can be induced to perform that action against a shop the attacker does not control, using only a webhook the attacker legitimately received for their own store. This matches the "cross-tenant access" Critical-impact category, since the attacker never needs the app's `client_secret` or any privileged credential — only ordinary installation of the app on a store they control (an unprivileged action available to any merchant/developer).

### Likelihood Explanation
Exploitability requires: (1) the attacker installs the target app on their own shop (routine, unprivileged), (2) they capture one legitimate webhook delivery (trivial — apps must expose a public endpoint to receive it), and (3) they replay it with a modified `shop-domain` header to the same endpoint. No secret material, MITM, or social engineering is required. The main constraint is that the webhook body must not itself leak/require the true shop domain in a way the host app cross-checks — which is not something this gem enforces or documents, so it is a latent risk for any handler that trusts `WebhookMetadata#shop`.

### Recommendation
Bind the shop identity to the signed material, e.g. include the `X-Shopify-Shop-Domain` header value in the HMAC-signable string (analogous to how `Auth::Oauth::AuthQuery#to_signable_string` includes `shop`), or clearly document in `WebhookMetadata` that `shop` is unauthenticated and must be independently verified by the host application (e.g. against a registered shop/session store) before use.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and registers to receive, e.g., the `app/uninstalled` webhook (or any topic whose body is static/predictable).
2. Shopify delivers a legitimate request to the app's webhook endpoint:
   ```
   X-Shopify-Topic: app/uninstalled
   X-Shopify-Hmac-Sha256: <valid HMAC over body>
   X-Shopify-Shop-Domain: attacker.myshopify.com
   Body: {}
   ```
3. Attacker resends the identical body and HMAC to the same endpoint, replacing only the shop header:
   ```
   X-Shopify-Shop-Domain: victim.myshopify.com
   ```
4. `Utils::HmacValidator.validate` in `lib/shopify_api/webhooks/registry.rb:190` succeeds because it only checks the (unchanged) body against the (unchanged) HMAC.
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, causing the host application to act as though the event originated from `victim.myshopify.com`.
