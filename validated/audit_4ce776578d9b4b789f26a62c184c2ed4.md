### Title
Cost model's `calculate_allocated_accounts_data_size` only inspects top-level System Program instructions and misses CPI-invoked allocations, under-counting block account-data-size usage - ([File: cost-model/src/cost_model.rs])

### Summary
`CostModel::calculate_allocated_accounts_data_size` (backed by `calculate_account_data_size_on_instruction` and `calculate_account_data_size_on_deserialized_system_instruction`) only walks the transaction's top-level compiled instructions and only recognizes an allocation when the *top-level* `program_id` equals `system_program::id()`. Any account allocation performed via a cross-program invocation (CPI) from a custom BPF program into the System Program (`CreateAccount`, `CreateAccountWithSeed`, `Allocate`, `AllocateWithSeed`, `CreateAccountAllowPrefund`) is invisible to this static estimator, so the transaction's reported `allocated_accounts_data_size` is 0 (or otherwise understated) while the SVM actually allocates the real bytes at execution time.

### Finding Description
`CostModel::calculate_allocated_accounts_data_size` iterates `instructions: impl Iterator<Item = (&'a Pubkey, SVMInstruction<'a>)>`, which for `calculate_cost`/`calculate_cost_for_executed_transaction` comes from `transaction.program_instructions_iter()` — the flat list of top-level instructions compiled into the transaction message (see call sites at [1](#0-0)  and [2](#0-1) ). For each `(program_id, instruction)` pair, `calculate_account_data_size_on_instruction` checks whether the *top-level* `program_id` equals `system_program::id()`; only then does it deserialize the instruction data and delegate to `calculate_account_data_size_on_deserialized_system_instruction`, which returns `Some(space)` for the allocating variants: [3](#0-2) [4](#0-3) 

If the top-level `program_id` is anything else (e.g., an attacker-deployed custom program), the branch returns `SystemProgramAccountAllocation::None` unconditionally, regardless of what that program does internally: [5](#0-4) 

However, at execution time, a custom program can `invoke()`/`invoke_signed()` a CPI into the System Program's `create_account`, `allocate`, `allocate_with_seed`, etc. That CPI is a real system-program instruction executed by the SVM and results in real account-data growth (subject only to the runtime-enforced `MAX_PERMITTED_ACCOUNTS_DATA_ALLOCATIONS_PER_TRANSACTION` cap, which is a correctness/resource guard, not a cost-accounting mechanism). Because the CPI instruction never appears in `transaction.program_instructions_iter()` (that iterator only reflects the statically compiled top-level instruction list, not the dynamic CPI call tree resolved during execution), `calculate_allocated_accounts_data_size` returns 0 (or an undercount) for that portion of work, and the resulting `TransactionCost.allocated_accounts_data_size` — which feeds `CostTracker`'s block-level accounts-data-size accounting — never reflects the true allocation performed. `calculate_cost_for_executed_transaction` is only invoked with actual **loaded_accounts_data_size** (from account loading, not from this allocation estimator) and does not recompute `allocated_accounts_data_size` from real post-execution account growth either — it re-derives it the same way, from static top-level instructions, so it inherits the same blind spot even post-execution.

No existing guard corrects this: the `MAX_PERMITTED_ACCOUNTS_DATA_ALLOCATIONS_PER_TRANSACTION` clamp in `calculate_allocated_accounts_data_size` (lines 291-301) operates only on the sum of statically-recognized top-level allocations, so it clamps an already-wrong (too low) number rather than the true allocation performed via CPI.

### Impact Explanation
This falls under the "compute-budget/cost-model under-pricing" bounty category identified in the prompt: an unprivileged attacker can make the cost model materially undercount real work performed. By deploying an ordinary, permissionless BPF program that CPIs into the System Program to create/allocate accounts, then invoking that program from a top-level instruction, the attacker's transaction is charged `allocated_accounts_data_size = 0` for what is, at execution, genuine account-data growth. Since `CostTracker` uses `allocated_accounts_data_size` to bound per-block account-data growth (`MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA`-style limits), an attacker (or a set of colluding unprivileged senders) can pack many such CPI-based allocation transactions into a block far beyond the intended account-data-size budget, exhausting a resource dimension the cost tracker is specifically meant to bound, without ever exceeding the tracked cost. This does not break SVM-level correctness (the per-transaction hard cap `MAX_PERMITTED_ACCOUNTS_DATA_ALLOCATIONS_PER_TRANSACTION` still applies at execution), but it defeats the *block-level* accounting invariant that `allocated_accounts_data_size` should upper-bound (or at least approximate) real allocation work across the block.

### Likelihood Explanation
High feasibility, fully reachable by an unprivileged actor:
1. Deploying an arbitrary BPF program is a standard, permissionless operation on Solana (program deployment itself is a normal transaction, not requiring elevated privileges).
2. That program's logic simply performs `solana_system_interface`/`system_instruction::create_account` (or `allocate`) via CPI — an extremely common and legitimate pattern (e.g., PDA account creation) that requires no special conditions, malformed data, or fuzzing; it is deterministic and 100% repeatable.
3. The attacker then submits the invoking transaction to any public RPC/TPU with no signature/lock/nonce/status-cache obstruction — write-locks, signatures, and nonces are irrelevant to this accounting gap.
4. No feature gate or sanitize step inspects the CPI tree for cost purposes; `program_instructions_iter()` structurally cannot see CPI-invoked instructions because they don't exist in the compiled message.

### Recommendation
The static, pre-execution cost estimator cannot see CPI-time invocations by design (it operates before execution). The fix should be applied at `calculate_cost_for_executed_transaction`, which already has access to post-execution info: extend it to also accept and use the actual measured accounts-data-size delta produced during execution (analogous to how it already receives `actual_loaded_accounts_data_size_bytes`), rather than recomputing `allocated_accounts_data_size` from the static, top-level-only instruction scan. Concretely:
- Add a real post-execution "accounts data size delta" measurement threaded from the SVM/account-loader execution path (which already tracks per-transaction allocation for enforcing `MAX_PERMITTED_ACCOUNTS_DATA_ALLOCATIONS_PER_TRANSACTION`) into `calculate_cost_for_executed_transaction`, and use that measured value (clamped to the same max) in place of / in addition to `calculate_allocated_accounts_data_size`'s static estimate when updating `CostTracker` after execution.
- Ensure `CostTracker`'s block-level accounts-data-size bookkeeping is updated from this post-execution, CPI-aware value rather than solely from the pre-execution estimate.

### Proof of Concept
```rust
// cost-model/src/cost_model.rs (new test)
//
// Demonstrates that a transaction whose top-level instruction invokes a
// custom program which internally issues a CPI `create_account` to the
// System Program is scored with allocated_accounts_data_size == 0, even
// though real account-data allocation occurs at execution.

#[test]
fn test_calculate_allocated_accounts_data_size_missed_via_cpi() {
    // Top-level instruction targets a *custom* program id (not system_program::id()),
    // simulating a program that will, at runtime, CPI into
    // system_instruction::create_account(..., space = 10_000, ...).
    let custom_program_id = Pubkey::new_unique();
    let transaction = Transaction::new_unsigned(Message::new(
        &[Instruction::new_with_bincode(
            custom_program_id,
            &0_u8, // arbitrary instruction data telling the on-chain program to CPI-allocate
            vec![],
        )],
        Some(&Pubkey::new_unique()),
    ));
    let sanitized_tx = RuntimeTransaction::from_transaction_for_tests(transaction);

    // Cost model estimate: 0, because it only inspects the top-level instruction's
    // program_id, which is `custom_program_id`, not system_program::id().
    let estimated = CostModel::calculate_allocated_accounts_data_size(
        sanitized_tx.program_instructions_iter(),
        &FeatureSet::all_enabled(),
    );
    assert_eq!(estimated, 0);

    // In a full SVM execution/integration test, running this transaction against a
    // program that performs `invoke(&system_instruction::create_account(..., 10_000, ...), ...)`
    // would show real post-execution account data growth of 10_000 bytes for the
    // created account, i.e. actual_allocated_accounts_data_size == 10_000 >> estimated (0).
    // This violates the invariant estimate >= actual (COST_UPPER_BOUND).
}
```
A full integration-level PoC (in `svm/tests` or `runtime/src/bank` test harness) would: (1) deploy a minimal BPF program performing `invoke(&system_instruction::create_account(...))`, (2) submit an invoking transaction, (3) capture `CostModel::calculate_allocated_accounts_data_size` pre-execution (expect 0) and compare against the measured post-execution account data-size delta for the newly created account (expect > 0), asserting the invariant `estimate >= actual` fails.

        program_id: &Pubkey,
        instruction: SVMInstruction,

            if let Ok(instruction) =
                limited_deserialize(instruction.data, solana_packet::PACKET_DATA_SIZE as u64)

                    instruction,
                    feature_set,

                SystemProgramAccountAllocation::Failed
            }
