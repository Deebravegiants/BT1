### Title
FXFiller's Uniswap V4 Venue Pricing Uses Unmitigated Pool Spot Price, Enabling Flash-Loan Price Manipulation to Drain Solver Funds - ([File: sdk/packages/simplex/src/strategies/fx.ts])

### Summary
Simplex's `FXFiller` strategy prices curve-less cross-asset pairs directly from the current Uniswap V4 pool tick (spot price derived from `sqrtPriceX96`), exactly the vulnerability class described in the CurvePriceProvider report: an on-chain AMM spot price is trusted as ground truth for asset valuation with no TWAP, and can be manipulated within a single transaction/flash loan.

### Finding Description
`UniswapV4FundingPlanner.getExoticTokenPrice` picks the most-liquid position for a token and calls `computeDirectPoolPriceUsd`, which returns the **raw pool mid** derived from `sqrtPriceX96 → token0Price/token1Price`, with no averaging over time and no execution-size/impact adjustment [1](#0-0) [2](#0-1) .

This spot price feeds directly into `FXFiller.resolveLegRates`, which prices a curve-less pair leg as `rate = 1 / venueUsd` whenever `token0` is a USD stablecoin, and into `referenceRate`, which sizes the order's USD notional for reorg-protection confirmation depth [3](#0-2) [4](#0-3) .

The only defense is `checkPriceGuard`, which compares the live quote against a **static, operator-set `referencePrice`** within `maxDeviationBps` — but this guard is explicitly optional; leaving both fields unset "leaves the chain unguarded" [5](#0-4) [6](#0-5) . Even when configured, the guard only bounds deviation from a stale reference — it does not detect or prevent a same-block manipulation that stays within the configured band, nor does it apply any TWAP.

The docs themselves acknowledge the exact risk: "Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote" and the internal flow notes confirm "`checkPriceGuard` is the only defense on this path, and it checks deviation from a static reference, not execution cost" [7](#0-6) .

Critically, the manipulated rate is not merely advisory — it is used to compute the actual token amount the solver pays out (`policyMaxOutput`) via `computeLegPolicyOutput`, and the codebase confirms the previous overfill-loss bound has been **disabled** (warn-only), so "the filler fills the full computed amount even when it exceeds ... including venue-priced legs (e.g. Uniswap V4)" [8](#0-7) .

### Impact Explanation
An attacker who manipulates the exotic/stablecoin Uniswap V4 pool price (e.g. via a flash loan swap) immediately before or within the same block as placing an intent order against a Simplex solver's venue-priced pair can force `resolveLegRates` to compute a distorted `rate`. Since the overfill clamp is disabled and there is no execution-cost/impact term applied to the quoted mid, the solver's `fillOrder` call pays out based on this manipulated rate, directly transferring solver-owned funds (from its wallet or Uniswap V4 LP position) to the attacker at a price divorced from real market value — a direct theft of solver/intent-solver funds. This also corrupts the `referenceRate`-derived USD sizing used for cross-chain confirmation-depth (reorg protection), potentially under-protecting the fill against a reorg.

### Likelihood Explanation
Likelihood is high for any solver operator who enables `[vault.uniswapV4]` pool-based pricing without configuring `referencePrice`/`maxDeviationBps` (both optional), or whose configured band is wide enough to tolerate a single-block price swing achievable with a flash loan against a thinly-liquid pool. The attack requires only a standard flash loan and an intent order submission — both unprivileged actions reachable by any user of the intents/order-flow, matching exactly the bug class in the reported CurvePriceProvider finding (spot price used as ground truth with no TWAP).

### Recommendation
- Require `referencePrice`/`maxDeviationBps` (or an equivalent external price feed) for every Uniswap V4 venue-priced position rather than leaving it optional; refuse to price a pair with no guard configured.
- Replace or supplement the raw pool mid with a time-weighted average price (TWAP) over multiple blocks, consistent with the original CurvePriceProvider fix, which removed spot-price-based oracles entirely.
- Re-enable (or make mandatory) an overfill/loss-bound clamp on venue-priced legs so a bad quote cannot translate into unbounded payout, restoring the previously-disabled protection noted in `fx.ts`.
- Apply an execution-size/impact adjustment to the quoted mid rather than extending it linearly across the whole fill quantity.

### Proof of Concept
1. Attacker identifies a Simplex solver operating a curve-less `[[pairs]]` entry priced from a `[vault.uniswapV4]` position with no `referencePrice`/`maxDeviationBps` configured (an explicitly supported, documented configuration) [9](#0-8) .
2. Attacker takes a flash loan and swaps heavily through the pool backing the solver's V4 position, moving `sqrtPriceX96` (and thus `token0Price`/`token1Price`) far from fair value.
3. In the same block (or before the solver's next `refresh()`), attacker places an intent order sized to exploit the distorted rate.
4. `FXFiller.resolveLegRates` → `getVenueUsdPrice` → `UniswapV4FundingPlanner.getExoticTokenPrice` returns the manipulated mid; `checkPriceGuard` passes trivially (no guard configured) [10](#0-9) .
5. `computeLegPolicyOutput` computes `policyMaxOutput` from this rate, and because the overfill clamp is disabled, the solver's `fillOrder` UserOperation pays out the full manipulated amount [11](#0-10) .
6. Attacker repays the flash loan and keeps the difference between the manipulated payout and the actual value delivered — funds drained from the solver's wallet/LP position.

	 * Validates a live venue quote against the static reference price for the chain.
	 * Returns true (pass) when no guard is configured, or no reference exists for the
	 * chain. Returns false when the quote (token1 per USD) deviates from the reference
	 * by more than `maxDeviationBps`, in which case the order must not be filled.
	 */
	private checkPriceGuard(orderId: string | undefined, chain: string, venueToken1PerUsd: Decimal): boolean {
		const guard = this.priceGuard?.get(chain)

				},
				"Rejecting order: Uniswap venue quote outside price-guard band",
			)
			return false
		}
		return true
	}

	 * Minimum-size reference rate (token1 per token0) for a leg's pair: the
	 * bid curve at 0 (the side token1-input legs trade at), falling back to the
	 * ask curve, then the live venue quote for venue-priced pairs.
	 */
	private async referenceRate(
		leg: ResolvedLeg,
		venueUsdPrice: (chain: string, token1Address: string) => Promise<Decimal | null>,
	): Promise<Decimal | null> {
		const policy = leg.pair.bidPricePolicy ?? leg.pair.askPricePolicy
		if (policy) {
			const rate = policy.getPrice(new Decimal(0))
			return rate.gt(0) ? rate : null
		}
		// Venue-priced pair: token0 is USD-stable (constructor invariant), so the
		// venue's USD-per-token1 quote inverts straight into token1-per-token0.
		const venueUsd = await venueUsdPrice(leg.token1Chain, leg.token1Address)
		if (!venueUsd) return null
		const venueRate = new Decimal(1).div(venueUsd)

		// for confirmation depth, and a manipulated pool understating the value
		// would shrink the reorg protection — the exact attack the guard exists
		// to stop. Refusing to size skips the order, consistent with pricing.
		if (!this.checkPriceGuard(undefined, leg.token1Chain, venueRate)) return null
		return venueRate
	}

## Pool-Based Pricing

When **`[vault.uniswapV4]`** lists at least one position, cross-asset pairs without curves derive bid/ask prices from **Uniswap V4 pool state** (current tick). The pool acts as the price oracle instead of a static curve. Note this yields a **single** price used in both directions — a venue-priced pair has no bid/ask spread of its own, so its margin comes from `order.fees` alone.

With Uniswap V4 positions configured, you can **omit** `bidPriceCurve` and `askPriceCurve` on the pair. Pool pricing requires the pair's `token0` to be a USD stablecoin, and same-token pairs always need their curve. The optional **`spreadBps`** field (basis points) sets the slippage tolerance for on-chain LP redemptions; defaults to `50` (0.50%).

Uniswap V4 venue pricing uses pools that pair the exotic token with **USDC or USDT** (addresses from your chain config). When multiple positions exist for the same exotic token on a chain, the most-liquid qualifying pool's price is used.

[[pairs]]

maxOrderSize = "5000"       # no curves — priced from the pool

[vault.uniswapV4]

    { chain = "EVM-8453", tokenId = "2087350" },
]

## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.
