### Title
Webhook `shop` identity is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authenticated once `Utils::HmacValidator.validate(request)` succeeds, and then hands the handler a `WebhookMetadata` object built from `request.shop`. However, the HMAC signature only ever covers the raw request body — never the `shop-domain` header — so the "shop" identity attached to an HMAC-verified webhook is not actually bound by that verification.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the signature purely from `to_signable_string` and compares it to the `hmac-sha256` header: [2](#0-1) 

`Registry.process` gates all further processing on this HMAC check, then immediately builds `WebhookMetadata` using `request.shop`, which is read straight from the (unsigned) `shopify-shop-domain`/`x-shopify-shop-domain` header: [3](#0-2) [4](#0-3) 

The identity binding that should hold is: `shop that produced the HMAC-signed bytes == shop attributed to the webhook by the handler`. Because the header carrying the shop is entirely outside the signed content, this equality is never enforced — any request with a *valid* body+HMAC pair (which an attacker can obtain by simply capturing a genuine webhook delivered to their own, legitimately-installed shop) can be replayed with an arbitrary `shop-domain` header value and will still pass `Utils::HmacValidator.validate`.

The gem's own documentation reinforces that this field is meant to be trusted by the host application: `Registry.process`'s doc explicitly says it "will verify the request did indeed come from Shopify," and `data.shop` is documented as "The shop domain of the webhook" with no caveat that it is unauthenticated: [5](#0-4) [6](#0-5) 

### Impact Explanation
An attacker who has legitimately installed the target app on their own shop (an ordinary, unprivileged merchant account — no `api_secret_key`, access token, or special privilege required) receives real webhook deliveries with valid `X-Shopify-Hmac-Sha256` signatures for their own shop's data. Since the HMAC never covers the `shop-domain` header, the attacker can resend that exact body/HMAC pair to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop. `Registry.process` will accept it as authentic (HMAC check passes) and dispatch it to the handler as if it belonged to the victim shop, via `WebhookMetadata#shop`. Any host application that uses `data.shop` to route, associate, or persist webhook data by tenant (as the gem's own documentation and example handler encourage) will attribute attacker-controlled data to another tenant — a cross-tenant data injection/confusion issue.

### Likelihood Explanation
Exploitation only requires an attacker to install the target app on a shop they control (the normal, expected way to legitimately interact with any Shopify app) and to be able to send an arbitrary HTTP request to the app's public webhook endpoint with a modified header — no secrets, tokens, or privileged access are needed. The relevant code path (`Registry.process` → `HmacValidator.validate` → `request.shop`) is exercised on every webhook delivery.

### Recommendation
Include the shop domain (and other identity-relevant headers such as topic/webhook id) in the HMAC-signable content, or otherwise cryptographically bind them to the verified payload, so that `Utils::HmacValidator.validate` cannot succeed unless the `shop-domain` header matches what was actually signed by Shopify for that specific delivery. At minimum, document prominently that `request.shop`/`WebhookMetadata#shop` is not covered by the HMAC and must not be trusted for tenant attribution without additional server-side verification (e.g., cross-checking against a known/installed shop list).

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a genuine webhook, e.g. `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for secret `S`).
2. Attacker POSTs the exact same body `B` and header `X-Shopify-Hmac-Sha256: H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Utils::HmacValidator.validate(request)` recomputes HMAC over `@raw_body` only (`to_signable_string`), which still equals `H`, so validation succeeds.
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)`, causing the host app to process/store attacker-controlled webhook data under the victim shop's tenant.
