### Title
Webhook `shop-domain`, `topic`, and `webhook-id` headers are trusted for tenant identification without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary

### Finding Description
This is the same bug class as the PoolTogether finding: a value that is *acted on* by downstream logic is not included in the set of bytes that are cryptographically verified. In PoolTogether, `canaryClaimCount` was used to compute fees but excluded from the value that gated the fee computation. Here, `ShopifyAPI::Webhooks::Request` computes its HMAC over the raw HTTP body only: [1](#0-0) 

while `shop`, `topic`, and `webhook_id` — the fields that downstream app logic uses to select the tenant and the business action to run — are read straight from unauthenticated HTTP headers: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, then immediately hands the header-derived `topic` and `shop` to the app's handler as trusted tenant/routing identifiers: [3](#0-2) 

and these are placed into the `WebhookMetadata` struct that the handler is expected to key business logic on: [4](#0-3) 

The equality that should hold but doesn't:
`bytes_covered_by_hmac == bytes_the_handler_trusts_as(shop, topic, webhook_id)`

In fact `bytes_covered_by_hmac == raw_body` only, while `shop`, `topic`, `webhook_id` come from `shopify-*`/`x-shopify-*` headers that are never mixed into `to_signable_string`.

### Impact Explanation
Because the signature only binds the body, any party who can obtain one genuine `(body, hmac)` pair signed with the app's `client_secret` (e.g., an attacker who installs the app on their own store and receives real webhooks for actions they themselves triggered) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) to claim it originated from a different, victim shop. `HmacValidator.validate` will still pass because it only re-derives the signature from `@raw_body`, and `Registry.process` will then dispatch to the handler with `shop` set to the victim's domain. If the host application uses `WebhookMetadata#shop` (as documented/intended) to select which tenant's data store to write to, this yields cross-tenant data injection/corruption — e.g. forging `customers/redact` or `shop/redact` mandatory-compliance webhooks against an arbitrary shop, or feeding attacker-controlled body content into another tenant's business logic. This matches the Critical "cross-tenant access" impact bucket.

### Likelihood Explanation
Likelihood is moderate-to-high for any app that trusts `WebhookMetadata#shop` for tenant routing (which is the documented purpose of the field) and that has at least one other webhook-generating tenant (e.g. any developer/store that installs the app, including the attacker's own free dev store). No access to `api_secret_key`, tokens, or the victim's credentials is required — only possession of one legitimately-signed webhook body/HMAC pair from any shop, which any app installer can obtain by causing a webhook to fire on their own store.

### Recommendation
Include the identifying headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signable content used for HMAC verification, or otherwise cryptographically bind them to the body (e.g., verify the `shop`/`topic` against Shopify's own webhook-delivery record via a secondary signed channel), so that a valid signature cannot be replayed under a different shop/topic identity.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com` and configures a webhook subscription (e.g. `products/update`) that fires with a request body under their control.
2. Shopify delivers the webhook to the app: headers include `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <hmac(raw_body)>`, and body `raw_body`.
3. Attacker captures `(raw_body, hmac)` — both are legitimately signed by Shopify with the app's `client_secret`, since `to_signable_string` returns only `raw_body`:
   `lib/shopify_api/webhooks/request.rb:35-38`.
4. Attacker replays the exact same `raw_body`/`hmac` pair to the app's public webhook endpoint, but changes the `X-Shopify-Shop-Domain` header to `victim.myshopify.com` (and/or the topic/webhook-id headers).
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the HMAC (`lib/shopify_api/webhooks/registry.rb:190`, `lib/shopify_api/utils/hmac_validator.rb:13-31`).
6. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker-controlled>, ...)` and, if it uses `shop` to select the victim's stored data/tenant context, executes attacker-controlled logic against the victim's tenant.
