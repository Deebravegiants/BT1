### Title
Missing source validation for `RequestState` messages allows cross-session state disclosure - ([File: orb-relay-client/src/client.rs])

### Summary
The `orb-relay-client` `PollerAgent::main_loop` enforces a source-identity check (`src.id != self.config.dst_id`) before accepting any relayed message, in order to prevent a multiplexed relay connection from acting on messages that did not originate from the expected counterpart. However, this check is completely bypassed for messages matching `self_serve::app::v1::RequestState`, which unconditionally causes the client to resend its last outgoing message to whoever sent the `RequestState` payload, without validating that the sender is the expected `dst_id`.

### Finding Description
In `PollerAgent::main_loop`, incoming `RelayPayload`s are dispatched as follows: [1](#0-0) 

The `if self_serve::app::v1::RequestState::matches(&payload).is_some()` branch is evaluated first and, if it matches, immediately re-sends `self.last_message` — the exact same source-identity check (`src.id != self.config.dst_id`) that is applied to every other payload type is skipped entirely for this message kind. The code's own author-comment on `PollerAgent` acknowledges that the underlying relay transport multiplexes messages from different sources onto the same connection: [2](#0-1) 

This means the `src.id` check exists specifically as a defense against exactly this multiplexing scenario, i.e., the client cannot otherwise rely on the transport layer to guarantee that only the intended session partner can deliver messages to a given connection. By exempting `RequestState` from that check, any entity capable of reaching the relay connection (any src) can force this client (used by both the Orb side, and the App side of a self-serve signup, see `Client::new_as_orb`/`new_as_app`) to re-emit its most recently sent message — which can carry signup-state payloads such as `AnnounceOrbId`, `CaptureStarted`, `SignupEnded`, `CaptureTriggerTimeout`, etc. — to that unverified requester instead of the true session counterpart.

This directly parallels the reported bug class: a validation performed for other code paths (source/authorization validation before acting) is selectively omitted for one specific "instruction"/message type, letting an entity outside the expected trust boundary trigger a privileged action (here: forced replay/disclosure of session state) via that one path.

### Impact Explanation
Because the relay connection is explicitly documented to multiplex several sources, an attacker who can establish any relay session that gets multiplexed onto the same underlying connection (or otherwise deliver a `RequestState` payload to this stream) can:
- Force the Orb-side client to resend the last message it sent for a signup session (potentially leaking signup/session lifecycle state, e.g. `SignupEnded`, `CaptureStarted`) to an unintended party.
- Cause cross-signup state bleed between sessions that share the same underlying relay connection/queue, since a party outside the intended `src_id`/`dst_id` pairing can pull state without passing the source check that guards every other message type.

This does not directly leak biometric image data, but it does leak/replay signup session-state signaling outside its intended `src`/`dst` boundary, which is the same class of unauthorized-cross-boundary-action impact described in the source report (unauthorized action injected because a security-relevant field was not validated).

### Likelihood Explanation
Exploitation only requires the ability to deliver a `RequestState`-typed payload onto a relay connection shared/multiplexed with the target session — no signature forgery or cryptographic break is needed, and the bypass is unconditional (it does not depend on race conditions or timing). The likelihood is bounded by how strictly the relay server itself isolates sessions on the wire, but the client-side code explicitly does not defend against this scenario for `RequestState`, despite defending against it for every other message.

### Recommendation
Apply the same `src.id != self.config.dst_id` validation to the `RequestState` branch before resending `last_message`, i.e., move the `RequestState` handling after (or make it conditioned on) the source-identity check at [3](#0-2) , so that only the expected counterpart (`dst_id`) can trigger a state resync/replay.

### Proof of Concept
1. Establish two relay client connections against the same underlying multiplexed relay connection/queue as an active Orb⇄App signup session (per the `PollerAgent` comment, this is an existing architectural condition for messages to reach `main_loop`).
2. From a connection whose `src.id` does not equal the target's configured `dst_id`, send a payload that unpacks to `self_serve::app::v1::RequestState` (see `orb-relay-client/src/lib.rs` `PayloadMatcher` impl at lines 32-43).
3. Observe that `PollerAgent::main_loop` (`orb-relay-client/src/client.rs`, lines 436-440) resends `self.last_message` to the sender's connection instead of hitting the `src.id != self.config.dst_id` rejection branch (lines 441-446) that governs every other payload type — regardless of the sender's identity.
