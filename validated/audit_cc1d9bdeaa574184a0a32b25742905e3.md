### Title
Local-only success determination for user-centric signups skips backend enrollment/duplicate/fraud verification - ([File: src/plans/mod.rs])

### Summary
When a user QR-code carries `user_centric_signup = true` (and the orb config `ignore_user_centric_signups` is not set), `do_signup()` derives the final `success` / `enrollment_status` for a signup entirely from the *locally computed* `signup_reason`, without ever calling `enroll_user()` — the function that actually sends the signup to the backend (`signup_post::request`) and polls (`signup_poll::request`) for the backend's authoritative confirmation (duplicate detection, backend fraud detection, uniqueness/dedup checks, etc.). This mirrors the "discrepancy between redeemed and owed" bug class in the report: two values that are supposed to be equal (locally-computed success vs. backend-confirmed success) are not actually reconciled — the code just trusts the local value.

### Finding Description
In `src/plans/mod.rs`, `do_signup()` computes `signup_reason` purely from on-device state: [1](#0-0) 

For the "normal" (non-user-centric) path, this `signup_reason` is only a precursor: `enroll_user()` is invoked, which calls the backend `signup_post`/`signup_poll` endpoints and only returns `Status::Success` if the backend later confirms `status: Completed, success: true`: [2](#0-1) 
The backend poll response comment explicitly documents that a `Completed`/`success:false` result covers "Backend duplicates," "Backend inflight matches," and "Backend detected fraud" — i.e., checks that exist *only* on the backend side.

However, when `user_centric_signup` is true, this entire backend confirmation step is skipped, and success is derived only from the local `signup_reason`: [3](#0-2) 

Because the FOSS build has all on-device fraud checks stripped (`N_FRAUD_CHECKS: usize = 0`, `detect_fraud()` always returns `Ok(false)`), `signup_reason` will essentially always resolve to `SignupReason::Normal` whenever the biometric pipeline succeeds: [4](#0-3) [5](#0-4) 

Meanwhile, the Personal Custody Package (PCP) — which contains the user's encrypted iris/face biometric data, iris-code signature (secure-element-signed), and identity commitment — is already built and uploaded to the backend *before* this success determination is made: [6](#0-5) 

So the orb reports/records `enrollment_status = Success` and treats the signup as completed for the user-centric path without ever confirming with the backend that the signup was not a duplicate, was not flagged by server-side fraud detection, or was otherwise accepted. `user_centric_signup` itself originates from `authenticated_app_data` in the user-status response, which is verified via `user_data.verify(user_data_hash)` against the QR-code hash, so it is a legitimate value from the backend/app — but even a legitimately-set flag causes the orb to skip the equality check between "locally believed success" and "backend-confirmed success": [7](#0-6) [8](#0-7) 

### Impact Explanation
This is analogous to the audited `CreditCaller` issue where an assumed equality (`amountOut == repayAmountIn`) is not actually enforced, causing incorrect state. Here, the assumed equality is "local pipeline success ⇒ backend enrollment success." The impact:
- A signup can be marked `Success` on the orb (`debug_report.enrollment_status`, `report_signup_reason`, UX success feedback) even though the backend's dedup/fraud/inflight-match checks — which are the actual identity-binding and fraud-enforcement authority — were never consulted for that signup.
- This creates a cross-signup state bleed / misattributed signup risk: the orb's local record of "signup completed successfully" can diverge from the backend's ground truth, since the only source of truth ever queried in this branch is the orb's own (in FOSS, non-existent) fraud checks.
- Because `user_centric_signup` is a value provided/authenticated through the app-controlled QR flow, an attacker able to influence or replay app-side session data (or exploit the app-centric path) could obtain a "successful" local enrollment without backend-side duplicate/liveness enforcement ever executing, since the branch that runs those checks (`enroll_user()`) is bypassed entirely.

### Likelihood Explanation
The `user_centric_signup` code path is a normal production branch (not test-only, not requiring privileged/hardware access) triggered whenever the app/backend user data indicates app-centric signups and `ignore_user_centric_signups` is false (the default is `false`, i.e., this bypass is enabled by default per `Config::default()`): [9](#0-8) 
This makes the condition reachable during normal unprivileged-user signup flow whenever the app requests a user-centric signup, which is an ordinary, non-privileged operational mode.

### Recommendation
Do not derive final signup success purely from locally computed `signup_reason` for user-centric signups. Either:
1. Always route through `enroll_user()` (or an equivalent backend confirmation call) regardless of `user_centric_signup`, so backend-side duplicate/fraud/uniqueness checks are always the authoritative source of "success," or
2. If a lighter-weight backend confirmation is desired for user-centric mode, still require an explicit backend acknowledgment (e.g., a status call) before marking `enrollment_status::Success`, rather than trusting the orb's own `signup_reason`.
In general, ensure that any "success" state recorded/reported by the orb is reconciled against the backend's authoritative computation before being treated as final, the same way `amountOut` should have been validated against `repayAmountIn` in the audited contract.

### Proof of Concept
1. Configure (or have backend/app supply) a user QR-code session where `authenticated_app_data.user_centric_signup == true` and the QR's `user_data_hash` matches (a normal, legitimately-authenticated app-centric session).
2. Ensure `ignore_user_centric_signups` remains `false` (the default).
3. Complete a normal biometric capture/pipeline on the orb such that `pipeline.is_some()` and `fraud_detected == false` (trivially true in the FOSS build, since `detect_fraud()` always returns `false`).
4. Observe in `do_signup()` (`src/plans/mod.rs:639-656`) that `success` and `debug_report.enrollment_status` are set to `Success` purely from `signup_reason == SignupReason::Normal`, with `enroll_user()` (and thus `signup_post`/`signup_poll`, which perform backend duplicate/fraud checks) never invoked.
5. Compare against the non-user-centric branch (`src/plans/mod.rs:646-656`), which requires `enroll_user::Status::is_success()` — itself gated on a backend `Completed`/`success:true` poll response (`src/plans/enroll_user.rs:146-176`) — demonstrating the discrepancy: one code path enforces backend confirmation, the other assumes it.
