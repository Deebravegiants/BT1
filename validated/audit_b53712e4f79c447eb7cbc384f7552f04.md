Found the vulnerability: `ShopifyAPI::Auth::Oauth.begin_auth` builds the OAuth authorization redirect URL directly from the caller-supplied `shop` string without any domain validation, whereas other sensitive flows in this same gem (`TokenExchange.migrate_to_expiring_token`) explicitly route the `shop` parameter through `Utils::ShopValidator.sanitize!` before using it to build a request host.

### Title
Unvalidated `shop` parameter in `Oauth.begin_auth` allows OAuth authorization request (and later access-token exchange) to be sent to an attacker-controlled host - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` interpolates the caller-supplied `shop` string directly into the authorization URL host via `auth_base_uri(shop)`, with no call to `Utils::ShopValidator.sanitize!`/`sanitize_shop_domain`, unlike `TokenExchange.migrate_to_expiring_token`, which validates `shop` through `ShopValidator` before using it to build a request host.

### Finding Description
`begin_auth` computes the OAuth authorize URL as: [1](#0-0) 
and `auth_base_uri` builds the request host straight from the `shop` argument: [2](#0-1) 

There is no sanitization step comparable to `Utils::ShopValidator.sanitize!`, which exists precisely to prevent an arbitrary attacker-controlled string from being treated as a Shopify host: [3](#0-2) 

Contrast this with `TokenExchange.migrate_to_expiring_token`, which validates `shop` before constructing the session/host used for the outbound request carrying `client_id`/`client_secret`: [4](#0-3) 

The equality this breaks: the host that receives the OAuth authorization redirect (and, on completion, the host that later receives `client_secret`+authorization `code` in `validate_auth_callback`'s `client.request` call) must equal a genuine `*.myshopify.com` (or otherwise trusted Shopify) domain. `auth_base_uri` never enforces `shop == trusted_shopify_domain`; it directly does `"https://#{shop}/admin"`. Documented usage in `docs/usage/oauth.md` even shows apps deriving `shop` from user-supplied HTTP headers (`shop = request.headers["Shop"]`) and passing it straight to `begin_auth`, since the gem's own API contract implies `shop` need only be a String — it provides no built-in guard the way `ShopValidator` does elsewhere in the same module tree.

Note: `validate_auth_callback` itself is protected, because `auth_query.shop` there is covered by the Shopify-computed HMAC (`to_signable_string`) before the `client.request` call to the access-token endpoint is made using that shop. But `begin_auth` has no equivalent binding — the value used to build the outbound authorize-request host is never verified to be a genuine Shopify domain at all.

### Impact Explanation
If a host application follows the exact pattern shown in this gem's own documentation (taking `shop` from a request header/param and forwarding it unmodified to `begin_auth`), an attacker can supply a malicious `shop` value (e.g., `evil.com`) causing the gem to construct and return an authorize URL pointing at `https://evil.com/admin/oauth/authorize?...&client_id=<app client id>...`. This discloses the app's `client_id` and intended scopes to an attacker-controlled host and can be used to redirect victims through a forged OAuth-like flow, ultimately enabling forced/incorrect OAuth completion. This aligns with the High-impact category "session fixation or forced OAuth completion."

### Likelihood Explanation
Likelihood is high given that: (1) the gem's own documentation instructs developers to source `shop` from an unauthenticated HTTP header, and (2) the gem provides no default sanitization path in this specific flow even though it has a `ShopValidator` utility that is used elsewhere for the exact same purpose (validating a `shop` string before it's used to build a request host).

### Recommendation
Route the `shop` parameter through `Utils::ShopValidator.sanitize!` (or `sanitize_shop_domain`) inside `ShopifyAPI::Auth::Oauth.begin_auth` before it is used in `auth_base_uri`, raising `Errors::InvalidShopError` for any value that isn't a trusted Shopify domain — mirroring the pattern already used in `TokenExchange.migrate_to_expiring_token`.

### Proof of Concept
1. Host app follows the documented pattern: `shop = request.headers["Shop"]` (untrusted, attacker-controlled).
2. Attacker sends `Shop: evil.com` and triggers the app's login route.
3. `ShopifyAPI::Auth::Oauth.begin_auth(shop: "evil.com", redirect_path: "/auth/callback")` executes `auth_base_uri("evil.com")` → returns `"https://evil.com/admin"`, and `auth_route` becomes `"https://evil.com/admin/oauth/authorize?client_id=<app_id>&scope=...&redirect_uri=...&state=..."`.
4. The app redirects the browser to this attacker-controlled host, exposing `client_id`, requested `scope`, and the `redirect_uri`/state cookie flow to the attacker's server, with no domain check anywhere in `lib/shopify_api/auth/oauth.rb` to prevent it.

          scope = if scope_override.nil?
            ShopifyAPI::Context.scope

            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }

        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
