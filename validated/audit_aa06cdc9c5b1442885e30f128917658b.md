Audit Report

## Title
CORS wildcard-origin allowlist bypass via missing label-boundary check enables origin spoofing - ([File: core/services/gateway/network/httpserver.go])

## Summary
The gateway's `isAllowedOrigin` function in `core/services/gateway/network/httpserver.go` validates wildcard CORS entries (e.g. `https://*.ethereum.org`) using a bare `strings.HasSuffix(originHost, allowedHost)` check without enforcing a DNS label boundary. This allows an attacker-controlled domain such as `evilethereum.org` to match the allowed suffix `ethereum.org`, causing the server to echo back an attacker's spoofed `Origin` in `Access-Control-Allow-Origin`.

## Finding Description
In `isAllowedOrigin`, after stripping the `*.` prefix from a configured wildcard entry, the code checks `strings.HasSuffix(originHost, allowedHost)` [1](#0-0) . Since `HasSuffix` performs a raw string suffix match rather than checking for a proper subdomain boundary (a preceding `.`), any origin ending literally with the configured suffix — including unrelated domains like `evilethereum.org`, `notethereum.org`, or `attacker-ethereum.org` — will incorrectly satisfy the check for an allowed entry of `ethereum.org`. This function is invoked directly in `handleRequest`, the entry point for every request to the gateway's user-facing HTTP server, which sets `Access-Control-Allow-Origin` to the raw, attacker-supplied `Origin` header value when `isAllowedOrigin` returns true [2](#0-1) . There is no other validation layer (no exact-match-only fallback, no label-boundary re-check) that would catch this before the header is set.

## Impact Explanation
This is a genuine CORS allowlist logic bug: an unprivileged attacker who registers a domain ending in the operator's configured allowed suffix can have their origin treated as trusted, causing the gateway to grant cross-origin read access (via browser fetch) to responses from the `/user` endpoint that were only intended for legitimate subdomains of the trusted domain. This maps to the in-scope "cross-user response corruption" / gateway request impersonation impact category, since it allows an attacker's web page to read gateway JSON-RPC responses across origins that the operator did not intend to trust.

## Likelihood Explanation
Exploitation requires only that the operator enable `CORSEnabled = true` with a `*.`-prefixed wildcard entry in `CORSAllowedOrigins` — a documented and supported configuration, as evidenced by the existing test `TestHTTPServer_HandleRequest_CORSEnabled_FromAllowedOriginWildcards` using `https://*.ethereum.org` [3](#0-2) . No credentials, privileged role, or victim interaction beyond visiting the attacker's page is needed; the attacker only needs to register a domain string ending in the configured suffix and send a crafted `Origin` header, which is achievable by any unprivileged network client/browser.

## Recommendation
Fix the wildcard suffix check to enforce a DNS label boundary, e.g., use `originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost)` instead of a bare `strings.HasSuffix(originHost, allowedHost)`, so that `evilethereum.org` cannot match the allowed suffix `ethereum.org`.

## Proof of Concept
1. Configure the gateway with `CORSEnabled = true` and `CORSAllowedOrigins = ["https://*.ethereum.org"]`.
2. From an attacker-controlled page served at `https://evilethereum.org`, issue a cross-origin `fetch` to the gateway's `/user` path with header `Origin: https://evilethereum.org`.
3. `splitURL` parses `originHost = "evilethereum.org"`; the configured wildcard host becomes `allowedHost = "ethereum.org"` after stripping `*.`; `strings.HasSuffix("evilethereum.org", "ethereum.org")` returns `true`, so `isAllowedOrigin` returns `true`.
4. The server responds with `Access-Control-Allow-Origin: https://evilethereum.org`, allowing the attacker's page to read the response body via the browser's fetch API.
5. This can be validated by extending `TestHTTPServer_HandleRequest_CORSEnabled_FromAllowedOriginWildcards` in `core/services/gateway/network/httpserver_test.go` with an origin of `https://evilethereum.org` against the allowed entry `https://*.ethereum.org`, and confirming the `Access-Control-Allow-Origin` header is incorrectly set to the attacker's origin.
