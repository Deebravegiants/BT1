### Title
Signup/Enrollment Marked `Success` Without Backend Verification in User-Centric Signup Mode - ([File: src/plans/mod.rs])

### Summary
When a signup is flagged as `user_centric_signup` and the orb config does not override this (`ignore_user_centric_signups == false`), the orb sets `enroll_user::Status::Success` purely from a **locally computed** `signup_reason` value, completely bypassing the backend enrollment call (`enroll_user::Plan::run`, which normally posts to `signup_post::request` and polls `signup_poll::request` for server-side confirmation). This is the same bug class as the reported `claimPromo()` issue: a state field (`enrollment_status`/signup success) is advanced to a "completed/successful" terminal state without validating the underlying condition it is supposed to represent (i.e., a real backend-verified, unique enrollment).

### Finding Description
In `do_signup`, `signup_reason` is derived entirely from local, orb-side computations: [1](#0-0) 

`fraud_detected` comes from `detect_fraud`, but all fraud checks have been stripped out and the function unconditionally returns `false`: [2](#0-1) 

Then, when `user_centric_signup` is `true` (set from `authenticated_app_data.user_centric_signup`, sourced from `backend::user_status`) and the orb has not been configured to ignore user-centric signups, the code sets the enrollment status to `Success` directly from `signup_reason`, without ever calling the backend enrollment/verification flow (`enroll_user`), which is the only path that submits the biometric codes to the backend for duplicate/fraud/uniqueness checking and polls for a definitive `Completed`/`success: true` response: [3](#0-2) 

Contrast this with the "else" branch, which is the only path that actually verifies success server-side via `signup_post`/`signup_poll`: [4](#0-3) 

This mirrors the reported bug class exactly: a status field is transitioned to a terminal "success" state based on a value that was never independently validated against the authoritative backend record (analogous to `claimPromo()` setting `status: 'claimed'` without validating `txHash` against an on-chain receipt). Here, `signup_reason == SignupReason::Normal` is treated as proof of a valid, unique, non-fraudulent enrollment, but it is only proof that the local pipeline produced a result and that the (permanently disabled) local fraud check didn't flag anything — it is not proof that the backend has verified uniqueness/deduplication of the iris code, which is the actual invariant the "Success" status is supposed to guarantee.

### Impact Explanation
If `user_centric_signup` is set (a legitimate app-driven flow) and `ignore_user_centric_signups` is not enabled in orb config, a signup can be marked `Success`/enrolled without the backend ever validating or deduplicating the biometric enrollment. Combined with `detect_fraud` being a stub that always returns `false`, there is no gate — local or remote — preventing a duplicate/fraudulent enrollment from being recorded as a successful signup in this mode. This can lead to unauthorized or misattributed signups being accepted, and a cross-signup state bleed (bypassing the backend's inflight/duplicate detection that the normal `enroll_user` path relies on).

### Likelihood Explanation
Reachable whenever the backend/app sets `user_centric_signup: true` for a session and the orb is not configured with `ignore_user_centric_signups`. No attacker privilege beyond normal signup flow is required to trigger this code path; the only precondition is the deployment's use of the app-centric signup mode, which is a supported, non-privileged production flow, not a test-only or hardware-only path.

### Recommendation
1. Do not short-circuit enrollment success based solely on the local `signup_reason` value; always require backend confirmation (via `signup_post`/`signup_poll`, as done in the non-user-centric branch) before marking `enrollment_status` as `Success`, even in user-centric signup mode.
2. Restore actual fraud/duplicate detection in `detect_fraud` (currently hard-stubbed to `Ok(false)`), or ensure an equivalent server-side check is mandatory before any success state is recorded.
3. Add an explicit invariant check (akin to a "status must currently be pending" guard) ensuring `enrollment_status` can only transition to `Success` once verified against backend/server records, not from local orb-only signals.

### Proof of Concept
1. Backend issues a QR/session with `authenticated_app_data.user_centric_signup = true` (a supported, non-privileged app flow) and orb config does not set `ignore_user_centric_signups`.
2. User completes biometric capture; the biometric pipeline produces any non-`None` result (`pipeline.is_none()` false), so `signup_reason` resolves to `SignupReason::Normal` at `src/plans/mod.rs:565-571` regardless of whether this is a duplicate/fraudulent capture, since `detect_fraud` always returns `false` (`src/plans/mod.rs:1390-1406`).
3. Execution reaches `src/plans/mod.rs:639-645`; since `user_centric_signup` is true, `enrollment_status` is set to `enroll_user::Status::Success` directly, and `enroll_user::Plan::run` (the only code path that calls the backend `signup_post`/`signup_poll` to verify uniqueness/fraud/success) is never invoked.
4. `result.success` becomes `true` at `src/plans/mod.rs:660-661`, and the signup is treated as a fully verified, successful enrollment despite no backend-side validation ever having occurred.
