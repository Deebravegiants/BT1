### Title
Excessive native token payment to `EvmHost.dispatch()`/`fundRequest()` is permanently trapped as "dust" instead of refunded - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all accept `msg.value` and forward the *entire* amount to `UniswapV2Router02.swapETHForExactTokens{value: msg.value}(...)`, requesting only the exact fee amount (`post.fee`, `get.fee`, or `amount`). Any unspent native token from that swap is refunded by the router back to the caller of the swap, which is `EvmHost` itself — not the original transaction sender. That leftover ETH lands in `EvmHost` via its `receive()` function, which is explicitly documented as accepting "dust" with no code path that returns it to the depositor.

### Finding Description
In `EvmHost.sol`: [1](#0-0) 

and the analogous `dispatch(DispatchGet)` at: [2](#0-1) 

and `fundRequest`: [3](#0-2) 

Each of these functions passes `msg.value` in full to `swapETHForExactTokens`, requesting only the exact `fee`/`amount` argument. The Uniswap V2 router refunds unspent ETH to whoever called it — here, `EvmHost` — and `EvmHost` explicitly acknowledges and keeps this: [4](#0-3) 

Unlike `IntentGatewayV2`/`ExtrinsicIntents`/`IntrinsicIntents`, which explicitly track a running `msgValue` and refund the unspent remainder to `msg.sender` after every native-token operation (see `testPlaceOrder_RefundsExcessNativeToken`, `testFillOrder_RefundsSolverExcessNativeToken`), `EvmHost.dispatch()`/`fundRequest()` has no such accounting or refund step. Any user/HyperApp that overestimates the native value needed for a fee swap (e.g. by including a slippage buffer, or by sending a fixed `msg.value` regardless of the on-chain quote) permanently loses the difference — it becomes indistinguishable "dust" inside `EvmHost`.

This is the exact analog of the Sherlock finding: the validation logic only checks that the amount supplied is *sufficient* (`msg.value` covers `post.fee`/`get.fee`/`amount`), never that it is *exact*, and the excess is not returned to the payer but retained by the contract.

### Impact Explanation
Every unprivileged caller who dispatches a POST/GET request or funds a pending request with native token (the normal, documented payment path per `docs/content/developers/evm/messaging/post-requests.mdx`, "Native Token Payment") risks losing any overpayment above the fee-swap requirement. Given `quote()` is explicitly documented as unreliable on-chain (sandwich-attack prone) and users are told to over-provision `msg.value` for safety margin, this is a systemic, reachable loss-of-funds bug for any single dispatch transaction, not a contrived edge case. Funds are permanently locked in `EvmHost` with no depositor-facing recovery mechanism (unlike `IntentGatewayV2`'s governance `SweepDust`, which returns swept funds to a beneficiary but never to the original overpayer).

### Likelihood Explanation
High. Any HyperApp or end user calling `dispatch()`/`fundRequest()` with native token and a conservative/rounded `msg.value` (as the docs themselves suggest doing, since `quote()` should not be trusted precisely on-chain) will trigger this on essentially every transaction where the actual Uniswap swap cost is less than the value sent.

### Recommendation
Track the actual amount spent by the swap (`amounts[0]` returned by `swapETHForExactTokens`) and refund `msg.value - amounts[0]` back to `_msgSender()` in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, mirroring the pattern already used in `IntentGatewayV2`/`IntrinsicIntents`/`ExtrinsicIntents` (`msgValue -= amounts[0]; ... _sendValue(msg.sender, msgValue);`), instead of silently retaining the excess as host-owned "dust".

### Proof of Concept
1. Deploy `EvmHost` with a configured Uniswap V2 router and fee token.
2. Caller invokes `dispatch{value: 5 ether}(post)` where `post.fee` only requires e.g. 0.01 ether worth of native token to swap for the fee token (as demonstrated in `testPlaceOrder_FeeSwap_RefundsExcessNativeToken` for `IntentGatewayV2`, which explicitly asserts most of an over-provisioned 5 ETH is refunded to the user).
3. In `IntentGatewayV2`, the leftover ETH is refunded to the caller; in `EvmHost.dispatch()`, the identical `swapETHForExactTokens{value: msg.value}` call is made with **no equivalent refund logic** — the unspent ETH is returned to `EvmHost` (via its documented dust-collecting `receive()`), not to the caller, and remains permanently stuck in the host contract.
