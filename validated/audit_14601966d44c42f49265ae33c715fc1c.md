### Title
Webhook `shop` and `topic` identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` fields — which are the identity/routing fields the host application trusts after `HmacValidator.validate` succeeds — are read straight from unauthenticated HTTP headers.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `Request#shop` and `Request#topic` are pulled from the `shopify-shop-domain` / `shopify-topic` headers, which are never mixed into the signable string: [2](#0-1) 

`Registry.process` validates the request with `Utils::HmacValidator.validate(request)`, which in turn calls `verifiable_query.to_signable_string` (i.e., the raw body) and compares it against `verifiable_query.hmac`: [3](#0-2) 

Immediately after this check passes, `Registry.process` treats `request.shop` and `request.topic` as trustworthy and forwards them to the app's handler: [4](#0-3) 

The broken identity binding, expressed as an equality that should hold but does not:

`bytes_verified_by_hmac (raw_body)` ≠ `bytes_the_handler_acts_on (shop, topic, webhook_id, api_version headers)`

Because the app's `client_secret` (and therefore the HMAC secret) is shared across every shop that installs the app — it is not per-shop — any attacker who installs the app on their own shop receives genuine, validly-signed webhook deliveries. The attacker can then replay the exact same `raw_body` + `X-Shopify-Hmac-Sha256` header while swapping the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header to any other shop/topic value. `HmacValidator.validate` still succeeds because it only checks the untouched raw body bytes, so `Registry.process` dispatches the handler with a `WebhookMetadata` claiming the payload came from the victim shop/topic.

### Impact Explanation
This is a cross-tenant identity-binding break: an unprivileged attacker (any merchant who can install the app on their own shop) can cause the host application to process a webhook payload attributed to an arbitrary victim shop or topic, even though only the raw body — not the shop or topic — was actually authenticated. Any host logic that keys authorization, data mutation, or account state decisions off `WebhookMetadata#shop`/`#topic` (e.g., GDPR mandatory topics like `shop/redact` or `customers/redact`, `app/uninstalled` cleanup, order/customer processing) can be tricked into acting on a shop the attacker doesn't control. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any app that receives webhooks and naively trusts `WebhookMetadata#shop`/`#topic` once `Registry.process` (or `HmacValidator.validate`) returns true — the gem's own naming and API strongly implies these fields are verified once the HMAC check passes, but they are not. No secret or privileged access is required beyond installing the app on an attacker-owned shop to obtain one legitimately signed webhook body/HMAC pair to replay with forged headers.

### Recommendation
Bind the identity headers into the signed material, or otherwise cryptographically tie `shop`/`topic`/`webhook_id` to the raw body before trusting them, e.g., include the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, and `X-Shopify-Webhook-Id` header values in `Request#to_signable_string` (or require the host app to independently confirm `shop` against a known/installed shop list) before constructing `WebhookMetadata`. At minimum, document clearly that `shop`/`topic` are not covered by the signature and must not be used for authorization decisions without additional verification.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`; Shopify sends a legitimate webhook to the app's endpoint with headers `X-Shopify-Topic: customers/redact`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-raw_body>`, and some `raw_body`.
2. Attacker captures this request (it is addressed to their own server/controller).
3. Attacker resends the identical `raw_body` and `X-Shopify-Hmac-Sha256` header, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`; since `to_signable_string` only covers `raw_body`, validation succeeds.
5. `handler.handle` is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "customers/redact", ...)`, causing the host application to act (e.g., delete data, disable resources) as if Shopify itself sent this instruction for `victim-shop.myshopify.com`.
