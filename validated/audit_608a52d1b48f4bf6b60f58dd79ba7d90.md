### Title
Webhook HMAC does not cover the shop-attribution header, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by recomputing an HMAC over the raw request body and comparing it to the `hmac-sha256` header. The `shop-domain` header — the value the gem hands to the app's webhook handler as the authoritative tenant identifier — is never included in the signed material, so it is trusted without being bound to the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read directly from unauthenticated HTTP headers: [2](#0-1) 

`Registry.process` validates the webhook using only `Utils::HmacValidator.validate(request)`, which internally calls `verifiable_query.to_signable_string` (body only) and secure-compares it against the header-supplied HMAC: [3](#0-2) [4](#0-3) 

After HMAC passes, the handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` — `request.shop` is the unauthenticated header value: [5](#0-4) 

Because Shopify webhooks for a given app are all signed with the same `client_secret` (shared across every shop that installs the app), any merchant who installs the app is a legitimate recipient of validly-signed `(body, hmac)` pairs for their own shop. The webhook endpoint is a normal public HTTP endpoint (no Shopify IP allow-listing is performed by this gem), so that merchant can POST the captured `(body, hmac)` pair directly to the app's callback path while substituting the `shopify-shop-domain` header (and `webhook-id`/`topic`, if the body's schema allows) for a victim shop. `Registry.process` will accept the request as valid because HMAC verification never touched the header, and the handler will execute believing the event/data belongs to the victim shop.

The broken binding, expressed as an equality that fails to hold: `bytes_covered_by_hmac (raw_body) == bytes_used_to_attribute_the_event_to_a_shop (shop-domain header)`.

### Impact Explanation
Any application logic that keys off `WebhookMetadata#shop` (e.g., to look up/act on the corresponding shop's stored access token, to update per-shop records, or to trigger internal actions scoped "as this shop") can be tricked into treating attacker-controlled or attacker-selected shop identity as authentic, since the gem itself asserts the webhook is "verified" once HMAC passes. This is a cross-tenant identity confusion: a merchant/attacker who is only entitled to act on their own tenant's data can cause the app to process a validly-authenticated body under a victim tenant's identity.

### Likelihood Explanation
Any developer/merchant who has installed the app receives real webhook deliveries (body + valid HMAC) for their own shop and can trivially replay them with a modified `shop-domain` header directly to the public webhook endpoint — no privileged credentials, access tokens, or `client_secret` knowledge are required, only observation of one's own legitimate webhook traffic.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) as signed material verified against the request, or independently verify the shop-domain header against session/shop records already known to be valid for the topic before dispatching to handlers, so that the trusted identity cannot diverge from the HMAC-covered bytes.

### Proof of Concept
1. App is installed on Shop A (attacker) and Shop B (victim), both using the same app `client_secret`.
2. Attacker's own shop receives a legitimate webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` with the shared `client_secret`), header `x-shopify-shop-domain: shopA.myshopify.com`.
3. Attacker crafts a new POST to the app's registered webhook path with the same body `B` and same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: shopB.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only and finds it matches `H` — validation succeeds.
5. The handler is invoked with `WebhookMetadata#shop == "shopB.myshopify.com"`, even though the data actually originated from Shop A's webhook stream, letting the attacker inject data/events attributed to Shop B.
