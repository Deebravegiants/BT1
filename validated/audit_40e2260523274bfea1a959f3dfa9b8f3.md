### Title
Webhook `shop-domain` is trusted for tenant attribution but is not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the webhook HMAC only over the raw request body, while the `shop` (tenant identifier) is read from a separate, unsigned header. `Registry.process` accepts any request whose body-HMAC validates and then hands `request.shop` straight to the app's handler as the tenant identifier, so the value that identifies *which merchant* the payload belongs to is never bound by the signature that is supposed to authenticate the request.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, entirely independent of the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` (which calls `request.to_signable_string`, i.e. only the body) and then forwards `request.shop` to the handler unchanged: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` only ever signs/compares `verifiable_query.to_signable_string`, so for webhooks that string is the raw body — the shop header plays no role in the cryptographic check: [4](#0-3) 

The identity binding that should hold is:
`shop-domain header used by the handler for tenant attribution == shop bound inside the HMAC-verified bytes`

That equality does not hold: the HMAC only proves the body bytes are unmodified and were signed with the app's `client_secret`; it says nothing about which shop the header claims to be. Since the app's `client_secret` is the same for every merchant using the app, any address that legitimately installs the app on **its own** shop can obtain a validly-signed `(body, hmac)` pair for its own webhook traffic, then resend that exact `(body, hmac)` pair to the app's public webhook endpoint while substituting a victim's `shop-domain` value in the header. `Registry.process` will accept it (HMAC still matches the unchanged body) and dispatch it to the handler tagged with the victim's shop, via `WebhookMetadata.new(... shop: request.shop ...)`.

### Impact Explanation
This breaks the shop/session identity boundary the gem is supposed to provide to host applications: an unprivileged actor who is simply a legitimate merchant of the app can forge webhook events that the host app's handler will process as belonging to a different tenant (cross-tenant data injection/corruption, and potentially cross-tenant access if the handler uses `shop` to look up or write per-tenant records). This matches the Critical "cross-tenant access" category, since the field the app relies on to select the tenant is not authenticated by the same mechanism that is supposed to authenticate the whole request.

### Likelihood Explanation
Likelihood is high for any app that installs on multiple merchants: the attacker needs no privileged credential, access token, or the app's `client_secret` — only their own legitimate installation to harvest a valid `(body, hmac)` pair, and a normal HTTP request to the app's public webhook URL with a forged `shop-domain` header. No TLS interception or local access is required.

### Recommendation
Bind the shop identity into the verified bytes, or verify it out-of-band against a trusted source (e.g., the app's own installation/session store) rather than trusting the header value once the body HMAC passes. Concretely, `Request#to_signable_string` should not be the only signal used; `Registry.process` (or the host app) should cross-check `request.shop` against a known, previously-authenticated shop record (e.g., an existing offline session for that shop) before dispatching, and reject webhooks whose claimed shop has no corresponding authenticated session.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a genuine webhook: body `B`, header `shopify-shop-domain: attacker.myshopify.com`, header `shopify-hmac-sha256: H` (valid HMAC of `B` with the app's `client_secret`, per `lib/shopify_api/webhooks/request.rb` and `lib/shopify_api/utils/hmac_validator.rb`).
2. Attacker POSTs to the app's public webhook endpoint with the same body `B` and same `H`, but sets header `shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (= `B`) and finds it matches `H`, so validation passes (`lib/shopify_api/webhooks/registry.rb:190`).
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though the payload never originated from, nor was authenticated as coming from, `victim.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
