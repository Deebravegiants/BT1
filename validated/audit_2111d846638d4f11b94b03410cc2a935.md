### Title
Same-chain order cancellation can frontrun a solver's `fillOrder`/UserOperation, griefing the solver's gas with no way to recoup it - (File: evm/src/apps/IntentGatewayV2.sol)

### Summary
`fillOrder` checks `_filled[commitment] != address(0)` and, for cross-chain fills, `select()`-staged transient authorization, but neither check protects the solver from a user racing `cancelOrder()` into the same block/mempool window as the solver's fill transaction. If the user (order owner, who is always authorized to cancel before the deadline) submits `cancelOrder()` first, the solver's subsequent `fillOrder()` call reverts with `Filled()`, and the solver has already spent gas building/broadcasting the transaction — exactly the same "frontrun-then-revert" griefing pattern as the reported `execute_dca_order` issue, except the analogous "approval" here is the order's escrow/fill-eligibility state rather than an ERC-20 allowance.

### Finding Description
`fillOrder` at [1](#0-0)  revalidates `_filled[commitment] != address(0)` and, when `solverSelection` is enabled, the transient-storage selection hash, immediately before dispatching to `_fillSameChain`/`_fillCrossChain`. `cancelOrder` at [2](#0-1)  lets the order owner mark the order filled/cancelled (`_cancelSameChain`, or destination-side `_filled[commitment] = user` in the cross-chain destination path) at any point before expiry, with no cooperation from or notice to a solver who has already committed a fill transaction to the mempool.

Because a solver typically wins the auction, builds `fillOrder` (or an ERC-4337 `UserOperation` embedding it) and broadcasts it, a griefing order owner can observe the pending fill transaction and submit `cancelOrder()` with higher gas/priority fee to land first. The solver's `fillOrder` transaction is included after `_filled[commitment]` is already non-zero, and reverts with `Filled()` — consuming the solver's gas for a transaction that can never succeed once outpaced. For the ERC-4337 bidding path, the same-block risk is heightened: the solver's `validateUserOp` in `SolverAccount.sol` succeeds (validation only checks the signature/session binding, not order state) so the EntryPoint charges gas to the solver's prefund even though execution reverts inside `fillOrder`. [3](#0-2) 

Note: the docs and code comments for `SolverAccount.sol` explicitly acknowledge and mitigate one closely related griefing vector — third parties stripping the commitment/session signature from a public bid to consume the solver's nonce — via the `_containsFillOrder` guard on the standard 65-byte signature path. [4](#0-3)  That mitigation, however, only prevents *bid-signature replay/stripping*; it does nothing to prevent the order owner from racing a legitimate, correctly-formed `cancelOrder()` ahead of a legitimately-selected solver's `fillOrder()`.

### Impact Explanation
This is a griefing/gas-loss vector for solvers, not a fund-theft or fund-freezing bug: the user's own escrowed tokens are refunded normally via `cancelOrder`, and the solver never sends its output tokens (the revert happens before any token transfer in `_fillSameChain`/`_fillCrossChain`). The impact is limited to wasted solver gas and disincentivized participation, mirroring the reported issue's "Medium" characterization (bots lose gas, no direct protocol fund loss). This does not rise to concrete theft, permanent freezing, unbacked mint, or forged message delivery.

### Likelihood Explanation
Likelihood is moderate: it requires a griefing order owner to actively watch the mempool/bundler for a solver's fill transaction (or its own auction-losing outcome) and race it with a cancellation, paying gas to do so with no direct profit motive beyond harming a specific solver — similar cost/benefit asymmetry as the original report (attacker pays less gas than the victim bot).

### Recommendation
Not materially different from the reported recommendation: introduce a commit/lock window (e.g., disallow `cancelOrder` for some grace period after a `select()`/solver-authorization event has been staged on-chain for a commitment) or require the destination-side cancel path to check for a fresh solver selection before allowing cancellation to preempt an in-flight, already-authorized fill.

### Proof of Concept
Not independently executed/verified with a live fork or unit test in this pass — this is derived from static code reading of `fillOrder`/`cancelOrder`/`SolverAccount.validateUserOp`. A concrete PoC would: (1) place a same-chain order, (2) have a solver call `select()` (or sign a bid) authorizing itself, (3) have the order owner call `cancelOrder()` in an earlier or same-block position, (4) show the solver's subsequent `fillOrder()`/UserOperation reverts with `Filled()` after gas has already been spent/charged. I was unable to run this against the Foundry test suite (`evm/tests/foundry/IntentGatewayV2Test.sol`, `IntentGatewayV2SameChainTest.sol`) in this session to confirm exact revert ordering and gas-charging semantics under ERC-4337 bundling; a Devin session with repo execution access would be needed to validate this empirically.

    function fillOrder(Order calldata order, FillOptions calldata options) public payable nonReentrant {
        uint256 blockNumber = _blockNumber();
        if (order.deadline < blockNumber) revert Expired();
        // The solver's own bound on how long its quoted price stands. Zero means unbounded,
        // which is the right default for a solver filling directly — it is only at risk from
        // its own staleness. It matters for a bid signed through the coprocessor, where the
        // order placer chooses the moment of execution and nothing else caps the wait.
        if (options.validUntil != 0 && blockNumber > options.validUntil) revert FillExpired();
        bytes32 commitment = keccak256(abi.encode(order));

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain && orderSource != currentChain) revert WrongChain();
        if (!isSameChain && orderDest != currentChain) revert WrongChain();

        if (_filled[commitment] != address(0)) revert Filled();

        if (_params.solverSelection) {
            bytes32 storedSelectionHash;
            assembly {
                storedSelectionHash := tload(commitment)
            }

            bytes32 expectedSelectionHash = keccak256(abi.encode(msg.sender, order.session));
            if (storedSelectionHash != expectedSelectionHash) revert Unauthorized();
        }

    function cancelOrder(Order calldata order, CancelOptions calldata options) public payable nonReentrant {
        bytes32 commitment = keccak256(abi.encode(order));

        if (_filled[commitment] != address(0)) revert Filled();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        // Emitted here, once, rather than from each of the three routes below. Every check those
        // routes make — Unauthorized, NotExpired, UnknownOrder — reverts, and a revert discards
        // logs, so an early emit can never announce a cancellation that did not happen. Emitting
        // before the branch also keeps `EscrowRefunded` the last log on the same-chain route, where
        // the refund is processed in this same transaction. Three emit sites cost bytecode this
        // contract does not have: it sits within ~100 bytes of the EIP-170 limit.
        emit OrderCancelled({commitment: commitment, canceller: msg.sender});

        if (isSameChain) {
            // Checked here rather than inside `_cancelSameChain`, which used to re-read `host()`,
            // re-query the host's state machine id and re-hash `order.source` to reach the same
            // answer this function already has. Same check, one external call fewer.
            if (currentChain != orderSource) revert WrongChain();
            _cancelSameChain(order, commitment);
        } else if (currentChain == orderSource) {
            _cancelFromSource(order, options, commitment);
        } else if (currentChain == orderDest) {
            _cancelFromDest(order, options, commitment);
        } else {
            revert WrongChain();
        }
    }

    function validateUserOp(PackedUserOperation calldata op, bytes32 userOpHash, uint256 missingAccountFunds)
        public
        override
        onlyEntryPoint
        returns (uint256)
    {
        if (op.signature.length == ECDSA_SIGNATURE_LENGTH) {
            if (_containsFillOrder(op.callData)) return ERC4337Utils.SIG_VALIDATION_FAILED;
            return super.validateUserOp(op, userOpHash, missingAccountFunds);
        }

        // Expected format: abi.encodePacked(commitment, solverSignature, sessionSignature)
        // commitment: 32 bytes, solverSignature: 65 bytes, sessionSignature: 65 bytes
        if (op.signature.length < INTENT_SELECT_SIGNATURE_LENGTH) return ERC4337Utils.SIG_VALIDATION_FAILED;

        bytes32 commitment = bytes32(op.signature[0:32]);
        bytes calldata solverSignature = op.signature[32:97];
        bytes calldata sessionSignature = op.signature[97:162];

        // Call IntentGatewayV2.select to recover the sessionKey. This also stages the
        // transient-storage selection that fillOrder enforces at execution.
        SelectOptions memory selectOptions =
            SelectOptions({commitment: commitment, solver: address(this), signature: sessionSignature});
        bytes memory selectCalldata = abi.encodeWithSelector(SELECT_SELECTOR, selectOptions);
        (bool success, bytes memory returnData) = INTENT_GATEWAY_V2.call(selectCalldata);

        if (!success || returnData.length < 32) return ERC4337Utils.SIG_VALIDATION_FAILED;

        address sessionKey = abi.decode(returnData, (address));
        uint192 userOpNonce = uint192(uint256(keccak256(abi.encodePacked(commitment, sessionKey))));
        if (uint192(op.nonce >> 64) != userOpNonce) return ERC4337Utils.SIG_VALIDATION_FAILED;
        if (!_rawSignatureValidation(userOpHash, solverSignature)) return ERC4337Utils.SIG_VALIDATION_FAILED;

        // Pay for gas if needed
        _payPrefund(missingAccountFunds);

        return ERC4337Utils.SIG_VALIDATION_SUCCESS;
    }
