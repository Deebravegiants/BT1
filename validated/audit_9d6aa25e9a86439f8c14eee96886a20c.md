### Title
Webhook HMAC only authenticates the raw body, not the `shop`/`topic`/`webhook-id` headers, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` verifies the request body against the app's shared `client_secret`, but never covers the `shop-domain`, `topic`, or `webhook-id` headers that `Registry.process` trusts to route and attribute the webhook. Because the same `client_secret` HMAC key is shared across every shop that installs the app, any unprivileged user who installs the app on their own (attacker-controlled) shop can capture one legitimate `(raw_body, hmac)` pair and replay it with a forged `x-shopify-shop-domain` header naming a victim shop. `Registry.process` will still call `Utils::HmacValidator.validate(request)` successfully (it only checks the body) and will dispatch the handler with `shop: request.shop` set to the attacker-chosen victim domain.

### Finding Description
The identity binding that should hold is:
`hmac_verified_bytes == bytes_the_handler_attributes_to_a_shop`

In `lib/shopify_api/webhooks/request.rb`:
```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

only `@raw_body` is included in the signable string, while `shop`, `topic`, and `webhook_id` are read straight from attacker-controllable headers:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [2](#0-1) 

`Registry.process` then only checks the HMAC of the body and directly forwards the unverified `request.shop` to the handler:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [3](#0-2) 

Since the app's `client_secret` (the HMAC key) is identical for every shop that installs the app, an unprivileged attacker who installs the app on their own store obtains a valid `(raw_body, hmac)` pair without any special privilege or leaked credential. Replaying that exact body/HMAC while substituting a victim shop's domain in `x-shopify-shop-domain` passes `HmacValidator.validate` (which never inspects the shop header) and results in the handler processing data as if it originated from the victim tenant.

### Impact Explanation
This breaks the tenant-authentication boundary: `request.shop`, which the host application uses to key sessions, look up merchant records, or drive tenant-scoped business logic (e.g. `app/uninstalled`, `shop/redact`, order or customer processing), is completely uncoupled from the HMAC that is supposed to prove the request is legitimate for that tenant. An attacker can attribute arbitrary attacker-chosen payloads to any target shop domain, which the Rules classify as cross-tenant access (Critical impact).

### Likelihood Explanation
Likelihood is elevated because obtaining a valid `(body, hmac)` pair requires only installing the app once on an attacker-controlled/dev store — no leaked secret, no privileged account, and no access to the victim's credentials — and the `shop-domain` header is fully attacker-controlled input to `Webhooks::Request.new`.

### Recommendation
Include the identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the verified body (e.g., verify a canonical string of `shop|topic|webhook_id|raw_body`) so that the shop attribution cannot be altered without invalidating the signature.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers any webhook (e.g. `orders/create`), capturing the raw JSON body `B` and its valid header `x-shopify-hmac-sha256: H` (computed by Shopify using the app's shared `client_secret`).
2. Attacker sends a forged HTTP request to the app's webhook endpoint with:
   - `x-shopify-shop-domain: victim.myshopify.com`
   - `x-shopify-topic: orders/create`
   - `x-shopify-hmac-sha256: H`
   - body: `B` (unchanged)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `B` and succeeds. [4](#0-3) 
4. The registered handler is invoked with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the host application to process attacker-controlled data as belonging to the victim tenant.
