### Title
Unrestricted `superApprove` in `HyperFungibleTokenImpl` allows any caller to grant themselves unlimited allowance over any token holder's balance - (File: evm/src/utils/HyperFungibleTokenImpl.sol)

### Summary
`HyperFungibleTokenImpl.sol`, the cross-chain fungible token implementation used for `HyperFungibleToken`/`ERC6160Ext20`-style token bridging on Hyperbridge, gates every other privileged mutation (`mint`, `burn`, `grantMinterRole`, `grantBurnerRole`, `revokeMinterRole`, `revokeBurnerRole`) behind `AccessControlEnumerable` role checks, but exposes `superApprove(address owner, address spender)` as a fully public function with no access control at all.

### Finding Description
The contract correctly enforces role-based authorization for all sensitive state changes: [1](#0-0) 

and for role administration: [2](#0-1) 

However, the last function in the contract breaks this pattern entirely: [3](#0-2) 

`superApprove(owner, spender)` calls the internal `_approve(owner, spender, type(uint256).max)` directly, setting `owner`'s ERC-20 allowance for `spender` to the maximum `uint256` value. Unlike `mint`/`burn`, which require `MINTER_ROLE`/`BURNER_ROLE`, `superApprove` has **no modifier, no role check, and no `msg.sender == owner` check** — it is `public` and callable by anyone, for any `owner`/`spender` pair, exactly like the SSO advisory's `registerSSOProvider`, which enforced admin-only semantics on every sibling endpoint (`list`, `get`, `update`, `delete`) but omitted the equivalent check on `create`. Here, every other state-mutating entry point in the same contract enforces `onlyRole`, but `superApprove` — which is even more powerful, since it grants a spending allowance rather than merely creating a governance record — enforces nothing.

An attacker can call `superApprove(victim, attacker)` for any address holding this token, then immediately call the standard ERC-20 `transferFrom(victim, attacker, balanceOf(victim))` to drain the victim's entire balance, without any prior relationship, role, or permission.

### Impact Explanation
This is a direct, unauthorized-fund-theft vulnerability. Any account holding balances of a `HyperFungibleTokenImpl`-deployed token (used across Hyperbridge's ERC6160/HyperFungibleToken cross-chain token bridging contracts) can have its entire balance stolen by any unprivileged third party in a single transaction pair (`superApprove` + `transferFrom`). This satisfies "concrete theft... of funds" and maps to CWE-269/CWE-285/CWE-863 (missing authorization on a privileged state-mutating function), matching the bug class of the reference SSO advisory: a sibling function among role-gated management operations is missing the authorization check the others enforce.

### Likelihood Explanation
Trivial and always reachable: `superApprove` is `public`, requires no special state, no proof, no prior interaction, and can be called by anyone against any address with a nonzero balance of the token. The docstring frames it as a "test helper," but it is not restricted to test environments, is compiled into the production contract, and is reachable in any live deployment of `HyperFungibleTokenImpl`.

### Recommendation
Remove `superApprove` from the production contract, or at minimum restrict it to `onlyRole(DEFAULT_ADMIN_ROLE)` combined with `msg.sender == owner`/an explicit signature-based approval, matching the authorization discipline already applied to every other mutating function in the contract (`mint`, `burn`, and the four role-management functions).

### Proof of Concept
1. Deploy or locate a live `HyperFungibleTokenImpl` token with `victim` holding a nonzero balance.
2. From any unprivileged `attacker` address, call:
   `token.superApprove(victim, attacker)` — this succeeds with no access-control revert and sets `allowance(victim, attacker) = type(uint256).max`.
3. From `attacker`, call:
   `token.transferFrom(victim, attacker, token.balanceOf(victim))` — this succeeds because of the allowance set in step 2, fully draining `victim`'s balance to `attacker`.
