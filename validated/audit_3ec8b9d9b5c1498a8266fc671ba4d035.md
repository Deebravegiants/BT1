### Title
Webhook shop identity trusted from an unauthenticated header while HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)`, which computes the HMAC over `request.to_signable_string` — the **raw body only**. The `shop` (and `topic`/`webhook_id`) values that the handler receives and acts on come straight from HTTP headers that are never included in the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) . `Utils::HmacValidator.validate` computes and compares the HMAC using exactly that signable string: [2](#0-1) . The `shop`, `topic`, `webhook_id`, and `api_version` accessors are all read from HTTP headers that are not part of this signed string: [3](#0-2) .

`Registry.process` validates the HMAC and then immediately hands the header-sourced `request.shop` to the handler as the trusted tenant identifier: [4](#0-3) .

The identity binding this breaks is: **`hmac-verified bytes` (body only) ≠ `shop` used by the handler to attribute the event to a tenant**. Because a single app has exactly one `api_secret_key` shared across every shop that installs it (`Context.api_secret_key` is global, not per-shop — see `HmacValidator.validate`), any merchant who has installed the app can receive a legitimately-signed webhook body+HMAC pair for their *own* shop, then replay that identical `(raw_body, X-Shopify-Hmac-Sha256)` pair to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) with a victim shop's value. `HmacValidator.validate` still succeeds because it only re-derives the HMAC from the body, and `Registry.process` will invoke the handler with `WebhookMetadata.new(... shop: request.shop ...)` pointing at the victim tenant, even though the payload actually originated from — and describes — the attacker's own shop.

### Impact Explanation
This is a cross-tenant identity-confusion primitive: a merchant that is unprivileged with respect to another merchant's tenant can cause the host application to process attacker-controlled webhook data (body content genuinely HMAC-valid, but for the wrong shop) as if it belonged to a victim shop. Any host application logic that uses `WebhookMetadata#shop` to select which tenant's records to create/update/delete (a very common pattern, e.g., "look up shop record by `shop`, then persist `body`") is exposed to cross-tenant data injection/corruption. This satisfies the "cross-tenant access" Critical impact bucket in scope.

### Likelihood Explanation
Exploitation requires only: (1) installing the app as an ordinary, unprivileged merchant so as to receive real webhooks (self-service, no special privilege), and (2) replaying a captured request to the app's public webhook endpoint with a modified `shop-domain` (and optionally `topic`/`webhook-id`) header — no access to `api_secret_key` or any credential is required, since the HMAC bytes are reused verbatim. The gem provides no header-binding or replay protection (no nonce, no per-shop signing key, no binding of headers into the signed string), so likelihood is high wherever a host app trusts `WebhookMetadata#shop`/`#topic` without independently correlating it to the registered destination or an expected shop list.

### Recommendation
Bind the identity-bearing headers into the HMAC-signed material (or otherwise cryptographically bind `shop`, `topic`, and `webhook_id` to the body before comparison), and/or require the consuming `WebhookHandler#handle` implementation to receive an explicitly-verified shop rather than exposing an unauthenticated header value as trusted metadata. At minimum, document prominently that `WebhookMetadata#shop`/`#topic`/`#webhook_id` are **not** covered by the HMAC and must not be trusted for tenant attribution without additional verification (e.g., cross-checking against the app's own installed-shop registry).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, receives a legitimate webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker POSTs to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - `X-Shopify-Hmac-Sha256: H` (unchanged)
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (forged)
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(api_secret_key, B)` and finds it equal to `H` — validation passes: [5](#0-4) .
4. The handler executes with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: B, ...)`, causing the host app to associate attacker-controlled data `B` with `victim-shop.myshopify.com`'s tenant.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
