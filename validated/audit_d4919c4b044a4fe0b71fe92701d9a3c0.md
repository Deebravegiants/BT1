### Title
Frequent forced accrual converts supplier yield entirely into protocol revenue via floored supply-index division - (File: common/src/rates/index.rs)

### Summary
`update_supply_index` distributes each accrual step's supplier rewards by computing `floor((supplied_value + rewards) * RAY / supplied)`. When a step's `rewards_increase` is smaller than one index quantum (`supplied * old_index / RAY` growth granularity), the floored quotient equals `old_index`, the supply index does not move, and `supply_index_reward_shortfall` books the **entire** step's supplier rewards — not just a dust residual — to protocol revenue shares. Because accrual runs inside every mutating pool operation and `update_indexes`, any unprivileged address can trigger accrual at arbitrarily fine cadence, shrinking per-step rewards below the quantum and permanently redirecting supplier yield to the treasury.

### Finding Description
In `accrue_step` (common/src/rates/simulate.rs:51-93), one compounding step:
1. Computes `supplier_rewards` from the borrow-index delta via `calculate_supplier_rewards` (common/src/rates/index.rs:73-89).
2. Calls `update_supply_index`, which floors the index growth: `grown = floor((supplied*old_index + rewards) * RAY / supplied)` (index.rs:41). If `rewards * RAY < supplied`, `grown == old_index` (bounded below by `bounded_old`, index.rs:43-44) so the index is unchanged.
3. `supply_index_reward_shortfall` then computes `rewards_increase - distributed` (index.rs:60-63); with `distributed = 0` the shortfall equals the full `rewards_increase`.
4. The shortfall is added to `protocol_reward` and minted as `revenue_shares` (simulate.rs:80-87), which are booked via `cache.accrue_revenue` in `accrue_chunk` (contracts/pool/src/interest.rs:39-53) and accrue to the protocol, not suppliers.

Borrowers are charged the full interest through `update_borrow_index` (which uses half-up `mul`, not floor), but suppliers receive none of it — the protocol captures 100% of the step's rewards.

The trigger is `rewards_increase * RAY < supplied`, i.e. per-step supplier interest smaller than the index granularity over total supply. Per-step interest scales linearly with `delta_ms` while `supplied` is fixed, so calling an accrual-triggering entrypoint (`update_indexes`, `supply`, `withdraw`, `borrow`, `repay`, `liquidate`, `flash_loan`, etc. — any path that builds a `Cache` and runs `global_sync`) at high frequency shrinks `delta_ms` until rewards fall below the quantum. Large `supplied`, low utilization, and low borrow rates all lower the threshold. Unlike the intended dust residual (< 1 quantum per step), under sustained forced accrual effectively *all* supplier yield is diverted to revenue for as long as the cadence is maintained.

### Impact Explanation
Permanent redirection of unclaimed supplier yield to protocol revenue. Supplier positions keep the same scaled shares against an unmoved supply index, so the accrued interest they were owed is instead minted as revenue shares claimable only by the treasury. This matches "theft of unclaimed yield": value charged to borrowers never reaches suppliers. Over any interval, an attacker can ensure suppliers' realized APR collapses toward zero while borrowers still pay full interest, with the difference accruing to `revenue`.

### Likelihood Explanation
Any unprivileged address can invoke accrual at high frequency at only transaction-cost; no position, capital, or timing advantage is required. The condition `rewards * RAY < supplied` is easiest on high-supply/low-borrow markets and hardens the lower `delta_ms` is pushed — Soroban ledger close times bound the minimum chunk, but each ledger-level call still reduces rewards proportionally, and on thin-interest markets even ordinary accrual cadence can satisfy the inequality. The attacker does not directly profit (revenue is treasury-owned), so this is griefing/donation rather than extraction, which lowers practical motivation but not feasibility.

### Recommendation
Carry forward undistributed rewards instead of re-booking them as revenue: keep a pending-rewards accumulator that is added to the next step's `rewards_increase` before `update_supply_index` runs, so sub-quantum rewards compound until they can move the index. Alternatively, compute `new_supply_index` via `old_index + floor(rewards * RAY / supplied_value)` and only treat the sub-quantum remainder (strictly less than one index quantum of value, not the whole reward) as shortfall. Ensure `simulate_update_indexes` stays bit-identical with `accrue_step` after the change.

### Proof of Concept
Setup: a market with `supplied = S` scaled shares, `supply_index = I`, `borrowed = B`, utilization giving annual borrow rate `r`.

1. At `t0`, attacker calls `pool.update_indexes` (or any mutating op) to force `global_sync`.
2. At `t0 + δ` (small `δ`), attacker calls it again. `accrue_chunk` runs `accrue_step` with `delta_ms = δ`.
3. `interest_factor ≈ 1 + per_ms * δ / RAY`; `new_total_debt - old_total_debt = accrued_interest ≈ B * I_b * per_ms * δ / RAY²`; `supplier_rewards = accrued_interest * (BPS - reserve_factor) / BPS`.
4. Choose `δ` (or rely on a high-`S` market) so that `supplier_rewards * RAY < S`. Then in `update_supply_index`:
   `new_value = S*I + supplier_rewards`; `floor(new_value * RAY / S) = floor(I*RAY + supplier_rewards*RAY/S) = I*RAY` (integer division drops the `< 1` term) → `grown == I` → `new_supply_index = I`.
5. `supply_index_reward_shortfall` returns `supplier_rewards - 0 = supplier_rewards`; `accrue_step` adds it to `protocol_reward` and `protocol_fee_shares` mints it into `supplied`/`revenue`.
6. Repeat every ledger. Suppliers' index never moves while the condition holds; all borrower interest for the interval is converted into protocol revenue shares.

Concrete sketch: `S = 1e33` scaled shares (≈ 1e6 tokens at 27-dec scaling), `B*I_b` debt value `1e30`, `per_ms ≈ 1.7e15` (~5.4% APR), `reserve_factor = 0`. Per-ms rewards ≈ `1e30 * 1.7e15 / 1e27 ≈ 1.7e18` ray. Quantum is `S / RAY = 1e6` ray of value per index unit — wait, the condition is `rewards * RAY < S*I` contribution: index moves iff `rewards * RAY / S ≥ 1`, i.e. `rewards ≥ S/RAY = 1e6` ray. Per-ms rewards `1.7e18 >> 1e6`, so on this market capture requires ~sub-microsecond cadence — infeasible. On a market where `S` is `1e6`× larger relative to debt (e.g., `S = 1e39`, or utilization near zero so `accrued_interest ≈ 0`), per-ledger rewards fall below `S/RAY` and each step's entire reward is captured. The vulnerability therefore materializes on high-supply, near-zero-utilization markets (a routine state for newly listed or dormant assets) where even ordinary accrual cadence already zeroes supplier yield and routes it to treasury.
