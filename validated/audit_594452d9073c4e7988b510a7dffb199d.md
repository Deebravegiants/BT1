Audit Report

## Title
CORS `isAllowedOrigin` wildcard suffix match lacks a label boundary, allowing origin allowlist bypass — ([File: core/services/gateway/network/httpserver.go])

## Summary
The Gateway's `isAllowedOrigin` function validates the `Origin` header against configured `CORSAllowedOrigins`, but for wildcard entries (`*.domain.com`) it uses a bare `strings.HasSuffix(originHost, allowedHost)` check without requiring a `.` boundary before the matched suffix. This allows any domain that merely ends with the same byte sequence (e.g., `evilethereum.org` vs. allowed `*.ethereum.org`) to pass validation and be reflected back as a trusted `Access-Control-Allow-Origin`.

## Finding Description
In `core/services/gateway/network/httpserver.go`, the wildcard branch of `isAllowedOrigin` strips the `*.` prefix and performs an unanchored suffix check: [1](#0-0) 

This check does not verify that the character immediately preceding the matched suffix is a `.`, so it fails to distinguish a genuine subdomain relationship from an unrelated domain that happens to share a trailing byte sequence. For example, with `CORSAllowedOrigins: ["https://*.ethereum.org"]`, the stripped `allowedHost` is `ethereum.org`, and `strings.HasSuffix("evilethereum.org", "ethereum.org")` evaluates to `true`, even though `evilethereum.org` is a wholly separate, attacker-registrable domain.

The result is then used directly in `handleRequest` to set CORS response headers, reflecting the attacker-controlled origin verbatim: [2](#0-1) 

The existing test suite `TestHTTPServer_HandleRequest_CORSEnabled_FromAllowedOriginWildcards` only exercises the true-subdomain case (e.g., `remix.ethereum.org` against `*.ethereum.org`) and does not test the boundary-omission scenario, so this gap is unexercised in CI: [3](#0-2) 

No other check compensates for this — scheme and port are validated correctly, but the host suffix comparison itself is the sole (and flawed) gate for wildcard matches.

## Impact Explanation
This is a genuine CORS allowlist bypass in the Gateway's internet-facing HTTP server. When an operator configures a wildcard `CORSAllowedOrigins` entry (a supported, documented configuration pattern, as referenced in `core/scripts/gateway/sample_config.toml` and `core/scripts/gateway/sample_config_tls.toml`), an attacker who registers a domain ending in the same substring as the allowed domain can have their page's cross-origin browser requests to the Gateway's `ProcessRequest` endpoint succeed with `Access-Control-Allow-Origin` reflecting their own origin. This lets an attacker-controlled web page read JSON-RPC-style Gateway responses that should be restricted to legitimate trusted frontends — a concrete allowlist bypass affecting cross-origin response confidentiality for an unprivileged, internet-facing endpoint.

## Likelihood Explanation
Exploitability requires only that the operator has configured at least one wildcard CORS entry, which is a normal supported configuration rather than a misuse of the system. Domain registration to craft a suffix-colliding name (e.g., `evilethereum.org` vs `*.ethereum.org`) is trivial and requires no privileges — any attacker can register such a domain and host a page that issues cross-origin requests from a victim's browser to the Gateway.

## Recommendation
Enforce a proper DNS label boundary in the wildcard suffix comparison, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost) {
        return true
    }
}
```
Additionally, add regression tests covering suffix-collision cases like `evilethereum.org` against `*.ethereum.org` to prevent recurrence.

## Proof of Concept
1. Configure the Gateway with `CORSEnabled: true` and `CORSAllowedOrigins: ["https://*.ethereum.org"]`.
2. Send an HTTP request to the Gateway's configured `Path` with header `Origin: https://evilethereum.org`.
3. Observe that `isAllowedOrigin` returns `true` (via `strings.HasSuffix("evilethereum.org", "ethereum.org")`), and the response includes `Access-Control-Allow-Origin: https://evilethereum.org`, `Access-Control-Allow-Methods: GET, POST, OPTIONS`, and `Access-Control-Allow-Headers: Content-Type`.
4. A Go unit test analogous to `TestHTTPServer_HandleRequest_CORSEnabled_FromAllowedOriginWildcards` in `core/services/gateway/network/httpserver_test.go`, but asserting `resp.Header.Get("Access-Control-Allow-Origin") == ""` for origin `https://evilethereum.org`, would fail against current code, confirming the bypass.

func TestHTTPServer_HandleRequest_CORSEnabled_FromAllowedOriginWildcards(t *testing.T) {

	_, handler, url := startNewServer(t, 100_000, 100_000, true,
		[]string{"https://*.ethereum.org", "https://*.valid.domain.com", "http://*.gov"})
