### Title
Fee-on-transfer input tokens cause escrowed accounting to exceed actual balance held in `IntentGatewayV2.placeOrder` (Tron variant) - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` calculates the escrowed/committed input amounts from the user-declared `order.inputs[i].amount` *before* any token transfer takes place, and never reconciles this figure against the tokens the contract actually received via `safeTransferFrom`. When an input token charges a transfer fee (fee-on-transfer / deflationary ERC20), the gateway's internal ledger (`_orders[commitment][token]`) will record more tokens than are actually held in the contract, exactly analogous to the reported Allo `_fundPool()` issue where `increasePoolAmount` was updated using the pre-fee amount.

### Finding Description
In the direct-transfer branch of `placeOrder` (no predispatch), the contract does: [1](#0-0) 

`reducedInputs[i].amount` used here is computed earlier purely from `order.inputs[i].amount` (the amount the user claims to send), reduced only by the protocol fee — it is never adjusted for any fee the ERC20 token itself deducts on transfer: [2](#0-1) 

The `safeTransferFrom` call at line 459 pulls `order.inputs[i].amount` from `msg.sender`, but for a fee-on-transfer token the contract actually receives `amount - fee`. The code does not measure `balanceOf(address(this))` before/after the transfer (unlike the predispatch branch of the same function, which does compare `balance` against `requiredAmount` and emits `DustCollected` for excess — see lines 421-438 — but even there the credited escrow is still `reducedInputs[i].amount`, not the measured `balance`, so the "dust" check only guards against excess but not against a shortfall). The result is `_orders[commitment][token] += reducedInputs[i].amount` recording an amount that is provably higher than `IERC20(token).balanceOf(address(this))` actually increased by.

This is the same root cause as the referenced Allo `Allo.sol#_fundPool()` bug: crediting internal accounting with the pre-fee/nominal amount instead of the measured, actual received amount. Notably, the sibling non-Tron implementation at `evm/src/apps/IntentGatewayV2.sol` was hardened against exactly this class of bug — it snapshots `balanceOf` before and after each `safeTransferFrom` and mutates `order.inputs[i].amount` to the actually-received amount before computing `reducedInputs`/`commitment` (see the "Phase 1"/"Phase 2" comments): [3](#0-2) [4](#0-3) 

The dedicated fee-on-transfer regression tests confirm this fix exists for the main EVM contract: [5](#0-4) 

But the Tron variant (`evm/tron/contracts/apps/IntentGatewayV2.sol`) never received this fix in its direct-transfer path.

### Impact Explanation
Because `_orders[commitment][token]` overstates the tokens actually held, the escrow ledger is unbacked for that order. Downstream, `cancelOrder`/`withdraw` use `order.inputs` (the nominal, pre-fee amount) to compute refunds and release funds: [6](#0-5) 

A refund or fill payout based on the overstated nominal amount will attempt to transfer out more of the fee-on-transfer token than the gateway actually holds. This can (a) cause reverts that permanently lock the order/escrow (denial of withdrawal — freezing of the user's other, unrelated escrowed funds sharing the token balance pool, since the contract co-mingles all orders' balances of a given token), or (b) drain balance belonging to other orders' escrow of the same token to cover the shortfall, effectively stealing funds from other users' orders. Either outcome is a concrete freezing/theft-of-funds condition reachable directly by any unprivileged caller of `placeOrder` using a standard fee-on-transfer ERC20 as an order input — no privileged role required.

### Likelihood Explanation
Likelihood is Medium: it requires the deployer/market to support a fee-on-transfer token as an intent input (e.g., USDT-style tokens with fee switches, or any deflationary/rebasing token), which is plausible for a general-purpose intents/bridging gateway that does not explicitly document exclusion of such tokens (the sibling implementation explicitly added support/handling for exactly this token class, showing it is an anticipated real-world scenario for this codebase). Any user calling `placeOrder` with such a token triggers the bug in a single transaction; no attacker collusion or special timing needed.

### Recommendation
Mirror the fix already present in `evm/src/apps/IntentGatewayV2.sol`: in the non-predispatch branch, snapshot `IERC20(token).balanceOf(address(this))` before calling `safeTransferFrom`, compute the actual received amount as the post-transfer balance delta, mutate `order.inputs[i].amount` to that measured value, and only then compute `reducedInputs`/`protocolFee`/`commitment` and credit `_orders[commitment][token]` with the measured amount. Apply the same balance-based accounting consistently to the predispatch branch so `reducedInputs` (and thus escrow credit) is always derived from measured balances rather than the nominal/user-declared amount.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 (e.g., 1% fee) and mint tokens to `user`.
2. `user` calls `IntentGatewayV2.placeOrder` (Tron variant) with `order.inputs[0] = {token: FOT, amount: 1000e18}`, no predispatch, `protocolFeeBps = 0`.
3. Inside `placeOrder`, `reducedInputs[0].amount = 1000e18` (unchanged since no protocol fee) is computed before transfer at lines 382-384.
4. `IERC20(FOT).safeTransferFrom(user, address(this), 1000e18)` at line 459 actually delivers only `990e18` to the gateway (1% fee retained by the token contract), but `_orders[commitment][FOT] += 1000e18` is credited regardless — a 10e18 token discrepancy between escrow accounting and `FOT.balanceOf(address(this))`.
5. When `cancelOrder`/`withdraw` later attempts to release `order.inputs[0].amount = 1000e18` (or a subsequent fill draws down the shared token bucket), the contract lacks sufficient FOT balance, causing either a revert (funds frozen) or the shortfall being paid out of other orders' escrowed FOT balance (funds stolen from other users), analogous to `testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived` demonstrating the correct behavior that the Tron contract fails to replicate.     /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
