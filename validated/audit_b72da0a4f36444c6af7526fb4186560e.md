### Title
`Webhooks::Request#shop`/`api_version`/`topic`/`webhook_id` are read from unsigned headers, letting a replayed body be attributed to an arbitrary shop - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC that `HmacValidator.validate` checks covers exclusively the JSON body [1](#0-0) [2](#0-1) . The `shop`, `topic`, `api_version`, and `webhook_id` values that `Registry.process` hands to the host app's `WebhookHandler` via `WebhookMetadata` all come from `shopify_header`, which just reads raw request headers with no cryptographic binding to the signed body [3](#0-2) [4](#0-3) . An attacker who owns any legitimate dev shop and receives one validly-signed webhook can replay that exact body/HMAC pair while swapping the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-api-version`, `x-shopify-webhook-id`) header, and the gem will report it to the handler as a validly-signed webhook belonging to a different, victim shop.

### Finding Description
The binding the gem's documentation implies is:
`WebhookMetadata#shop == the shop for which the signed body was actually generated by Shopify`

Tracing the code shows this binding does not hold, because it was never enforced:
- `HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to `verifiable_query.hmac` [5](#0-4) .
- For `Webhooks::Request`, `to_signable_string` is exactly `@raw_body` — no headers are included in the signed material [1](#0-0) .
- `shop`, `topic`, `api_version`, and `webhook_id` are all derived purely from headers via the private `shopify_header`, which simply does `@headers["shopify-#{name}"] || @headers["x-shopify-#{name}"]` with no relation to `@raw_body` or the HMAC [6](#0-5) [3](#0-2) .
- `Registry.process` only checks the HMAC (`Utils::HmacValidator.validate(request)`) and then immediately constructs `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` from these unsigned header values, passing it straight to the app's `handler.handle` [4](#0-3) .

Documentation instructs app authors to trust `data.shop` directly as "The shop domain of the webhook" with no caveat, and shows it being used to key work (`shop_domain: data.shop`) [7](#0-6) .

Exploit flow for the unprivileged attacker described in the rules (they may create their own dev shop, install their own app, and receive their own validly-signed webhooks):
1. Attacker installs their app on their own shop `attacker-shop.myshopify.com` and receives a legitimately-signed webhook: body `B`, headers including `x-shopify-hmac-sha256: H` (valid for `B`) and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker replays a POST to the app's webhook endpoint with the same body `B` and same `H`, but with `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `topic`/`api_version`/`webhook_id`, since none of those are signed either).
3. `HmacValidator.validate` recomputes the HMAC over `B` only, matches `H`, and returns `true` — the header substitution is invisible to the check [8](#0-7) .
4. `Registry.process` builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and calls the handler, which (per documented usage) uses `data.shop` to decide whose records to update [9](#0-8) .

No existing guard intercepts this: there is no `ShopValidator.sanitize!` call on the webhook shop domain anywhere in the webhook path (only OAuth/token-exchange code paths use `ShopValidator`), and `HmacValidator` never inspects headers at all.

### Impact Explanation
This lets an attacker who controls one legitimately-signed webhook body attribute that webhook, with an app-accepted valid signature, to an arbitrary victim shop domain of their choosing. If the host app (as documented) uses `WebhookMetadata#shop` to select which merchant's database rows/queue/job to act on, this is a cross-tenant confusion / forged-webhook-acceptance issue: a "signed" (HMAC-valid) request is processed under the identity of a shop that did not send it and had no part in generating it. This matches "Critical - authentication bypass (forged webhook ... accepted as authentic)" since the app's webhook trust boundary (HMAC valid ⇒ trust the shop header) is broken. It is repeatable at will by anyone who can obtain any one valid signed body (trivial for an attacker on their own dev shop), and can be aimed at any victim shop domain string of the attacker's choosing, without needing anything from the victim.

### Likelihood Explanation
Preconditions are minimal and fully within the unprivileged attacker's reach: they need only their own dev shop, their own webhook subscription, and the ability to POST to the app's public webhook endpoint (a documented, unauthenticated public route) — no secret key, access token, or victim cooperation required. Constructing the replay is a single HTTP POST with one header value changed. This is highly feasible and fully repeatable.

### Recommendation
Bind the identifying metadata to the signature. At minimum, `Webhooks::Request#to_signable_string` should incorporate the shop domain (and ideally topic/api_version/webhook_id) into the signed material, or the gem should require/verify that `shop` matches an out-of-band trusted value (e.g., cross-check against an active `Auth::Session` for that shop, or validate the shop domain format/ownership via `ShopValidator` plus correlating stored webhook subscription metadata) before handing `WebhookMetadata` to the handler. Documentation should explicitly warn that `data.shop`/`data.topic`/`data.api_version`/`data.webhook_id` are unauthenticated header values not covered by the HMAC, and instruct hosts to derive shop identity independently (e.g., from the session established during OAuth) rather than trusting the header verbatim.

### Proof of Concept
```ruby
# test/webhooks/registry_replay_test.rb
require_relative "../test_helper"

class WebhookReplayTest < Minitest::Test
  def test_same_signature_different_shop_headers_both_accepted
    secret = ShopifyAPI::Context.api_secret_key
    body = '{"id":1}'
    hmac = Base64.strict_encode64(
      OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, body)
    )

    received_shops = []
    handler = Class.new do
      include ShopifyAPI::Webhooks::WebhookHandler
      define_method(:handle) { |data:| received_shops << data.shop }
    end.new

    ShopifyAPI::Webhooks::Registry.add_registration(
      topic: "orders/create", delivery_method: :http, path: "cb", handler: handler
    )

    ["attacker-shop.myshopify.com", "victim-shop.myshopify.com"].each do |shop|
      req = ShopifyAPI::Webhooks::Request.new(
        raw_body: body,
        headers: {
          "x-shopify-topic" => "orders/create",
          "x-shopify-hmac-sha256" => hmac,
          "x-shopify-shop-domain" => shop,
        },
      )
      ShopifyAPI::Webhooks::Registry.process(req)
    end

    # SIGNATURE COVERAGE assumption fails: one signature over one body
    # was accepted for two different shops.
    assert_equal(["attacker-shop.myshopify.com", "victim-shop.myshopify.com"], received_shops)
  end
end
```
This demonstrates that a single `(body, hmac)` pair, valid under `HmacValidator.validate`, is accepted by `Registry.process` under two distinct `shop` values supplied purely via the unsigned `x-shopify-shop-domain` header, confirming the signature-coverage invariant does not extend to `WebhookMetadata#shop`.
