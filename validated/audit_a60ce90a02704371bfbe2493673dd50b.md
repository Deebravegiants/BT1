### Title
Unredacted logging of biometric identity data (`identity_commitment`, self-custody keys) at INFO level - (File: `src/backend/user_status.rs`)

### Summary
`src/backend/user_status.rs` logs the entire backend-authenticated user data structure — including the user's `identity_commitment` and `self_custody_public_key` — to the standard `tracing` log stream at `info` level, unconditionally, every time a user QR-code is validated during a normal signup. This mirrors the reported bug class ("excessive logging of sensitive data … increasing risk of data exposure") but the analog here concerns biometric-identity-linked data rather than HTTP credentials.

### Finding Description
In the QR-code validation flow, once the backend responds with `authenticated_app_data`, the orb immediately logs the full struct: [1](#0-0) 

This `orb_qr_link::UserData` payload deserialized from the backend response contains `identity_commitment` and `self_custody_public_key` among other fields, as seen in how it is later destructured: [2](#0-1) 

Unlike the feature-gated `log_iris_data` helper — which only logs raw iris/mask codes when the orb is compiled with the `log-iris-data` cargo feature (off by default) — [3](#0-2)  and [4](#0-3) , this `tracing::info!("User QR-data: {user_data:?}")` call is compiled into every production build and executes on every valid user-QR scan, regardless of feature flags. There is no redaction wrapper analogous to the `Password` newtype used elsewhere in the codebase to suppress `Debug` output of secrets: [5](#0-4) .

Similarly, on an invalid QR code the raw `qr_code` (containing `user_id` and `user_data_hash`) is logged at `info` level as well: [6](#0-5) , using the `Debug` derive on `qr_scan::user::Data`: [7](#0-6) .

Because `identity_commitment` is the value used to bind a specific human to a World ID identity, and `self_custody_public_key` is the user's own custody key, writing these to orb logs (which are collected off-device for debugging/telemetry, per `src/logger.rs`) creates an avoidable channel for identity-linkage data to leak beyond the intended signup pipeline, without any redaction as recommended by the original report.

I also reviewed the several `tracing::debug!("Sending request {:#?}", request)` calls in `src/backend/{signup_post,signup_poll,s3_region,presigned_url,upload_personal_custody_package}.rs`, which log full `reqwest::Request`/`RequestBuilder` objects that carry the `basic_auth` (orb token) header. I could not confirm from the available code whether `reqwest`'s `Debug` implementation redacts the `Authorization` header (the `http` crate supports marking header values "sensitive" so they print as `Sensitive` rather than the actual value) — this depends on `reqwest`'s internal behavior, which is outside this repo. This part is a "hint" only and not confirmed as a concrete vulnerability in-repo; the confirmed, in-scope finding is the unredacted `user_data`/`qr_code` logging above, which requires no external library assumptions.

### Impact Explanation
An attacker or operator with access to the orb's log output (local log files, journald, or any remote log/telemetry sink the orb forwards logs to) can recover a signing user's `identity_commitment` and `self_custody_public_key` directly from `info`-level logs, without needing to compromise the backend or intercept TLS traffic. This enables cross-referencing a specific signup session to a specific on-chain/World ID identity commitment, undermining the confidentiality goals that the rest of the pipeline (encrypted PCP packages, `Password` redaction, feature-gated iris logging) is designed to protect.

### Likelihood Explanation
This code path executes on every successful user QR-code validation in default (non-test, non-special-feature) builds — it requires no attacker action beyond normal use of the orb and access to its logs, which are already collected for operational/debug purposes. Likelihood is high; the only barrier is the attacker/insider needing read access to the orb's log output.

### Recommendation
Remove or redact the `tracing::info!("User QR-data: {user_data:?}")` and the QR-code `Debug` logging on the invalid-code path. If needed for debugging, implement a redacted `Debug`/`Display` (similar to the `Password` newtype in `mecard.rs`) that masks `identity_commitment`, `self_custody_public_key`, and `user_id`, or move such diagnostics behind an explicit, off-by-default feature flag (as already done for `log_iris_data`), and ensure any log aggregation strips these fields before persistence/export.

### Proof of Concept
1. Perform a normal signup flow where a user presents a valid QR code.
2. Observe orb log output (stdout/log file) during `user_status::request` execution.
3. The line `"User QR-data: UserData { identity_commitment: ..., self_custody_public_key: ..., ... }"` appears at `info` level, exposing the identity-linked fields in plaintext logs: [1](#0-0) .
