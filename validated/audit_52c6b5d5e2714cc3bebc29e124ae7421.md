### Title
`verifyWallet` signature check omits `feeStructure.feeToken`, letting the relay/caller pull any ERC20 from the signer's wallet up to `stack.maxFee` units - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
The `EmporiumSignature` EIP-712 typehash only commits to `message, ops, maxFee, deadline` and never includes `feeStructure.feeToken` or `feeStructure.flatFee`, and `verifyWallet` only enforces `circomData.feeStructure.flatFee > stack.maxFee` as a numeric bound with no token binding. Because `circomData.feeStructure` is calldata supplied at call time (not part of the signed payload), any unprivileged caller (the relay, or anyone able to invoke `runAction` through the allowed-recipient path) can pick an arbitrary `feeToken` while keeping `flatFee <= stack.maxFee`, causing `payRelayFees`/`sendToRelayFromWallet` to call `IHinkalWallet(signerAddress).doSendToRelay(relay, flatFee, feeToken)` and pull up to `maxFee` units of that arbitrary token straight from the victim's wallet.

### Finding Description
Broken equality: the token+amount actually debited from the wallet by `doSendToRelay` must equal exactly what `stack.signerAddress` cryptographically authorized. In fact only the numeric bound `flatFee <= maxFee` is authorized; `feeToken` is completely unconstrained by the signature.

Code path:
- `EMPORIUM_SIGNATURE_TYPEHASH` excludes `feeStructure`/`feeToken`: [1](#0-0) 
- `verifyWallet` recovers the signer over that limited typehash and only checks `flatFee > maxFee`: [2](#0-1) 
- `payRelayFees` reads `feeStructure.feeToken`/`flatFee` straight from `circomData` (caller-supplied, unsigned) and, if the fee token isn't among the withdrawal tokens in `erc20TokenAddresses`, falls into the branch that unconditionally pays the relay `feeStructure.flatFee` of `feeStructure.feeToken` directly from the wallet: [3](#0-2) 
- `sendToRelayFromWallet` invokes `IHinkalWallet(signerAddress).doSendToRelay(relay, relayFee, feeToken)`: [4](#0-3) 
- `HinkalWallet.doSendToRelay` is gated only by `onlyEmporium` (the Emporium contract itself), not by any per-token authorization, and unconditionally calls `sendToRelay(relay, actualAmount, erc20TokenAddress)`: [5](#0-4) 

Since `Emporium` (the contract enforcing `onlyEmporium`) is exactly the contract choosing `erc20TokenAddress` from unsigned `circomData`, the wallet has no independent means to verify the fee token/amount matches what its owner signed. `runAction` is reachable via `onlyAllowedRecipient`, and the caller supplying `circomData` (including `feeStructure`) is not necessarily the signer — it can be the relay or any party permitted to submit the transaction (per the threat model, an unprivileged actor able to craft every field of `CircomData`). No cross-chain redeploy is even required: within a single call on a single chain/instance, the fee token is entirely decoupled from the signature.

### Impact Explanation
An attacker (relay or any party who assembles the `CircomData` submitted to `runAction`) can force the signer's `HinkalWallet` to pay up to `stack.maxFee` units of an arbitrary ERC20 token — a token the signer never intended and never authorized for fee payment — via `doSendToRelay`. This is "executing... moving assets a wallet owner ... never authorised," matching the High severity category (theft of user funds / moving assets never authorized in that specific token), and in the worst case (relay paid in a worthless token while a valuable token is pulled from the wallet under the guise of `flatFee`) it also results in theft or permanent freezing of protocol/relay fees. It is repeatable on every `runAction` call for as long as a valid `stack` signature (with a still-unused `emporiumMessage`) exists, since the signature never commits to `feeToken`.

### Likelihood Explanation
No special privileges are required: any address able to submit the `circomData`/`stack` pair to `runAction` (e.g., the relay executing the meta-transaction, which per the threat model is only "not... a whitelisted relay" but any generic caller assembling calldata) can freely choose `feeStructure.feeToken` while satisfying `flatFee <= stack.maxFee`. The precondition is simply a valid, unused, unexpired `EmporiumStack` signature from the victim — a normal, expected operating state of the protocol, not an edge case. Attacker cost is negligible (gas only); the vulnerability is present on every invocation of `verifyWallet`.

### Recommendation
Include `feeStructure.feeToken` (and ideally `feeStructure.flatFee`/`variableRate`) inside `EMPORIUM_SIGNATURE_TYPEHASH` so the signer explicitly commits to the fee token and amount, e.g. add a `feeToken`/`feeStructure` field to the typed struct and hash it into `hashedMessage` in `verifyWallet`. Alternatively, require `circomData.feeStructure.feeToken` to equal a token address that is itself part of the signed `EmporiumSignature` payload, and revert if it doesn't match.

### Proof of Concept
Foundry test outline:
1. Deploy `EmporiumUpgradeable`, `HinkalWallet` for a victim signer, and fund the wallet with USDC and WETH.
2. Victim signs an `EmporiumStack` off-chain with `maxFee = 100`, intending fee token = USDC (informally — not encoded in the signature).
3. Attacker calls `runAction` with the same `(v,r,s)`, `stack.maxFee = 100`, but `circomData.feeStructure = {feeToken: WETH, flatFee: 100}`, and `erc20TokenAddresses` not containing WETH (triggering the `!foundToken` branch).
4. Assert `verifyWallet` does not revert (signature still recovers correctly, `flatFee <= maxFee` holds).
5. Assert `HinkalWallet.doSendToRelay` is called with `(relay, 100, WETH)` and that the wallet's WETH balance decreases by 100, despite the signature never referencing WETH — proving the equality "amount+token debited == amount+token signer authorized" is broken.
