### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, but the `shop` value that the gem hands to the app's handler is taken from an unauthenticated header that is excluded from that signature. This breaks the identity binding `shop verified by HMAC == shop delivered to the handler`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`Registry.process` validates the HMAC using exactly that signable string, and then trusts `request.shop` (read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, never part of the HMAC input) when building the `WebhookMetadata` passed to the app's handler: [2](#0-1) [3](#0-2) 

`HmacValidator.validate` only checks `verifiable_query.to_signable_string` against the computed signature — it has no knowledge of, and does not bind, any other field of the `VerifiableQuery` implementation: [4](#0-3) 

Because the app's `client_secret` (`api_secret_key`) is shared across every shop that installs the app, any merchant who has installed the app receives genuine webhook deliveries — real `(raw_body, hmac)` pairs signed with that shared secret. Such a merchant (an unprivileged actor with respect to any *other* tenant) can capture one legitimate webhook delivered to their own shop and replay it to the app's public webhook endpoint while rewriting only the `shopify-shop-domain` header to a victim shop's domain. Since `to_signable_string` never includes the shop domain, `HmacValidator.validate` still returns `true`, and `Registry.process` forwards `shop: request.shop` (attacker-controlled) to the handler as if Shopify itself had certified that binding: [5](#0-4) 

The gem's own documentation instructs host apps to trust `data.shop` as "The shop domain of the webhook" without warning that it is unauthenticated relative to the HMAC, reinforcing that this is a gap in the library's guarantee, not merely host-app misuse: [6](#0-5) [7](#0-6) 

### Impact Explanation
This crosses a tenant boundary: an attacker who is a legitimate (but unprivileged, non-victim) merchant can make the app process attacker-supplied body content under the identity of a different, victim shop. Any host application that uses `WebhookMetadata#shop` (as the gem's own docs instruct) to route data updates, cache invalidation, GDPR/redaction actions, or session lookups per-shop will act on forged data attributed to the wrong tenant — a cross-tenant access/data-integrity issue satisfying the "Critical - cross-tenant access" impact bar, since the identity (shop) binding that the handler relies on is not actually authenticated by this gem.

### Likelihood Explanation
Likelihood is bounded by the need for the attacker to already have a legitimate app installation (so they receive at least one genuine signed webhook, e.g. `orders/create` on their own store) and to send a forged HTTP request directly to the app's exposed webhook callback URL with a modified `shop-domain` header — both are within reach of an unprivileged internet user / low-tier merchant, no `api_secret_key` or access token of the victim is required, and the replayed HMAC remains valid indefinitely for that body since expiry is not enforced by `HmacValidator`.

### Recommendation
Bind the trusted identity to the signed payload: include the shop domain (and ideally topic/webhook id) inside the signable content actually verified by the HMAC, or otherwise cryptographically tie the header-derived `shop` to the signed body (e.g., require the app to independently confirm that a matching, previously-issued webhook subscription/session exists for that `shop` before trusting the payload). At minimum, document explicitly in `docs/usage/webhooks.md` that `data.shop` is not authenticated by the HMAC and must not be trusted without additional verification.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and has installed the app,
# so Shopify legitimately delivers a webhook to them:
raw_body = '{"id":1,"note":"hello"}'
real_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_CLIENT_SECRET, raw_body)

# Attacker replays it against the app's public webhook endpoint,
# only changing the shop-domain header to the victim's shop:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(real_hmac), # still valid! body unchanged
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (only raw_body is checked)
# => handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...))
# The host app now processes attacker-controlled data under the victim shop's identity.
```

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

          received_signature = verifiable_query.hmac
