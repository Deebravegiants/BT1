### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authenticated once `Utils::HmacValidator.validate(request)` succeeds, but the HMAC is computed only over the raw request body, never over the `shop-domain` header that the gem subsequently trusts to identify which merchant the event belongs to. Any attacker who can obtain one legitimately-signed webhook (e.g., by installing the app on their own store) can replay that exact `{body, hmac}` pair while swapping the `x-shopify-shop-domain` header, and the gem will hand the attacker-controlled payload to the handler labeled as coming from a victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors read directly from unauthenticated request headers with no cryptographic binding to the signed content: [2](#0-1) 

`HmacValidator.validate` computes the HMAC solely from `to_signable_string` (the body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` accepts the request purely on that body-only check, then constructs `WebhookMetadata` using `request.shop` taken straight from the header, and dispatches it to the app's handler as if it were verified provenance: [4](#0-3) 

The identity binding that should hold is: `shop header used by the handler == shop that the HMAC-secret-holder (Shopify) actually generated this exact byte sequence for`. Because the header is excluded from the signable string, this equality is never enforced — only `hmac(body) == received_hmac` is checked, independent of which shop header accompanies it.

The gem's own documentation reinforces that host apps are expected to rely on this exact flow as sufficient verification: "This will verify the request did indeed come from Shopify" is stated immediately before showing `Registry.process` as the complete verification step, with no mention that `data.shop` must be independently re-validated against a known/installed shop list. [5](#0-4) 

### Impact Explanation
An attacker who installs the target app on any shop they control (a routine, unprivileged action — most Shopify apps allow free/dev-store installs) receives genuine `{raw_body, hmac}` pairs signed by the app's `api_secret_key` for events they themselves trigger (e.g., `orders/create`, `customers/create`, `products/update`), and the body content of those events is largely attacker-chosen (order notes, customer emails, product fields, etc., depending on topic). The attacker can then POST that same `raw_body` + `hmac` to the app's public webhook endpoint while substituting `x-shopify-shop-domain` with a victim shop's domain. `HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` forwards `WebhookMetadata` with `shop` set to the victim's domain to the application's handler. Any host application logic that trusts `data.shop` to route data, create/update per-shop records, or take actions keyed by shop (exactly as shown in the gem's own documented handler example, which uses `data.shop` for `shop_domain:`) will attribute attacker-controlled data to a shop the attacker does not own — a cross-tenant data-integrity/spoofing impact.

### Likelihood Explanation
High reachability: the vulnerable code path (`Request#to_signable_string`, `HmacValidator.validate`, `Registry.process`) is exactly the flow documented and recommended for all webhook consumers of this gem. No secrets, privileged accounts, or host-application deviation from documented usage are required — only the ability to install the target app on an attacker-controlled shop, which is standard for most public Shopify apps.

### Recommendation
Bind the shop (and ideally topic/webhook-id) to the signed content, or otherwise verify it out-of-band before trusting it:
- Include the `shop-domain` header (and other identifying headers) in the value fed to `HmacValidator`/`to_signable_string`, so an HMAC computed for one shop's payload cannot be replayed with a different shop header, or
- Require callers of `Registry.process` to supply the shop the request is expected for and assert `request.shop == expected_shop`, and/or require that the shop have an active, known session/webhook registration before dispatching to the handler.
- Update `docs/usage/webhooks.md` to explicitly instruct developers to re-validate `data.shop` against a known installed-shop list, since HMAC validation alone does not authenticate the shop header.

### Proof of Concept
```ruby
# 1. Attacker installs the app on their own shop "attacker.myshopify.com"
#    and triggers e.g. an orders/create event with attacker-chosen body content.
#    Shopify sends a legitimately signed webhook:
raw_body = '{"id":1,"note":"pwned"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_secret, raw_body) # computed server-side by Shopify, captured by attacker

# 2. Attacker replays the exact body+hmac to the app's public webhook endpoint,
#    but swaps the shop-domain header to the victim's shop:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",  # not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (body-only check passes)
# => handler.handle(data: WebhookMetadata(shop: "victim-shop.myshopify.com", body: {"id"=>1,"note"=>"pwned"}, ...))
```
The host application's handler now processes attacker-controlled data under the victim shop's identity, despite the attacker never having a valid session or credentials for that shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
