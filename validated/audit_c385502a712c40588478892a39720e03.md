### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `shop-domain` header when constructing the `WebhookMetadata` passed to the app's handler. Since the `X-Shopify-Hmac-Sha256` signature is computed only over the raw body and not over the shop identifier, the shop value that the handler acts on is not bound to the signature that authenticates the request.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` header without any cryptographic binding: [2](#0-1) 

`Registry.process` validates the HMAC (over body only) and then forwards `request.shop` unchanged to the handler: [3](#0-2) 

The HMAC secret (`Context.api_secret_key`) is the app's single `client_secret`, shared across every merchant shop that has installed the app — it is not shop-specific: [4](#0-3) 

Because of this, `HmacValidator.validate` only proves "this body was signed by the app's secret" (i.e., it genuinely came from Shopify for *this app*), not "this body belongs to shop X." The equality that should hold — `shop authenticated by HMAC == shop the handler acts on` — does not: the `shop` field is acted on by `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` but is entirely outside the signed byte range.

### Impact Explanation
Any actor who can obtain one genuinely-signed webhook delivery for the app (e.g., an ordinary merchant who has installed the app receiving their own `orders/create` webhook, which is trivial to trigger by placing a test order) possesses a `(raw_body, hmac)` pair that is valid under the app's shared secret. That pair can be replayed to the app's webhook endpoint with the `shop-domain` header rewritten to a different (victim) shop. `Registry.process` will accept it — the HMAC check passes because it never looked at the shop header — and the handler will process attacker-supplied body content attributed to the victim shop's `WebhookMetadata#shop`. If the host application uses `data.shop` to look up the victim's session/store data or to perform tenant-scoped writes, this results in cross-tenant data injection/confusion driven entirely by an unprivileged app-installer, without needing the victim's access token or `client_secret`.

### Likelihood Explanation
Exploitation requires only: (1) being any merchant/tester who can install the app and receive one legitimate webhook (freely available to anyone who installs a public/dev app), and (2) sending an HTTP POST to the app's public webhook endpoint with a forged `shop-domain` header — no access token, no secret, no privileged account needed. This satisfies the "unprivileged internet user" bar in the rules.

### Recommendation
Bind the shop identity into the authenticated material, e.g. include `shop-domain` (and ideally `webhook-id`/`api-version`) in the signable string, or independently verify that `request.shop` corresponds to a shop with an active, stored session/installation for this app before invoking the handler. At minimum, document that `WebhookMetadata#shop` is unauthenticated and must be revalidated by the host app against its own installation records before being trusted for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target app on their own store (`attacker.myshopify.com`) and triggers an `orders/create` webhook, capturing the raw POST body `B` and the valid `X-Shopify-Hmac-Sha256` header `H` (valid because it's signed with the app's single shared `client_secret`).
2. Attacker sends a new POST to the app's webhook endpoint:
   - Body: `B` (unchanged)
   - Header `X-Shopify-Hmac-Sha256: H` (unchanged)
   - Header `X-Shopify-Shop-Domain: victim.myshopify.com` (forged)
   - Header `X-Shopify-Topic: orders/create` (unchanged)
3. `ShopifyAPI::Utils::HmacValidator.validate` recomputes HMAC over `raw_body` only and it matches `H`, so validation succeeds: [5](#0-4) 
4. `Registry.process` proceeds and calls the registered handler with `shop: "victim.myshopify.com"` and the attacker's body `B`: [3](#0-2) 
5. Any host-application logic keyed on `data.shop` (e.g., loading the victim's stored session, writing order data scoped to the victim) now operates on attacker-controlled content while believing it originated from the victim shop.

**Note on uncertainty:** This finding is scoped to the library's own request-validation logic (`lib/shopify_api/webhooks/*`); the actual downstream impact depends on how a host application uses `WebhookMetadata#shop`, which is outside this gem. I could not find any additional binding check (e.g., cross-referencing `shop` against a stored subscription/session) elsewhere in `lib/shopify_api/**` that would mitigate this.
