## #Valid Finding

### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented as verifying "the request did indeed come from Shopify" before invoking the app's handler with the shop domain taken from the request. In reality, the HMAC only signs the raw body — none of the identifying headers (`shop-domain`, `topic`, `api-version`, `webhook-id`) are part of the signed material. An attacker who can obtain one valid `(body, hmac)` pair for *any* shop (including their own store, which they fully control) can replay that same body/HMAC to the app's webhook endpoint while substituting an arbitrary `shop-domain` header, and the gem will accept it as an authentic webhook for that other shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all read directly from unauthenticated headers, with no cryptographic binding to the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string`, i.e., the raw body, and compares it against the `hmac` header: [3](#0-2) 

`Registry.process` relies solely on this body-only HMAC check, then constructs `WebhookMetadata` using `request.shop` (and `request.topic`) taken straight from the header — with no independent verification that the `shop` header actually matches the shop for which the body/HMAC pair was generated: [4](#0-3) 

The gem's own documentation asserts stronger guarantees than are actually provided — it tells integrators that `process` "will verify the request did indeed come from Shopify" and that `data.shop` is "The shop domain of the webhook", implying the shop identity is authenticated: [5](#0-4) [6](#0-5) 

The identity binding that should hold is:
`shop authenticated by HMAC == shop attributed to the processed webhook (request.shop)`

Because the HMAC only covers `@raw_body`, this equality does not actually hold — `request.shop` can be set to any value independent of what the HMAC certifies.

### Impact Explanation
Any app built on this gem's documented `Registry.process` API attributes incoming webhook data to `request.shop` without any means to detect that this value is not bound to the signature. An attacker who operates their own Shopify store (an unprivileged, standard action — no special credentials needed) can:
1. Trigger a webhook event for their own store and capture the resulting `(raw_body, x-shopify-hmac-sha256)` pair (e.g., by pointing their own webhook subscription at an attacker-controlled endpoint temporarily).
2. Replay that exact body and HMAC to the target app's real webhook endpoint, but with the `x-shopify-shop-domain` header changed to a victim shop's domain.
3. `HmacValidator.validate` succeeds because it only checks the body's HMAC, and `Registry.process` calls the app's handler with `shop: <victim-domain>` even though the payload was never generated for that shop.

This is a cross-tenant identity-binding break: data the app believes originated from — and is scoped to — the victim shop is actually attacker-controlled content signed for a different tenant. Depending on how the host app uses `data.shop` (e.g., to look up the shop's stored access token/session and perform actions, or to write/update records keyed by shop), this can lead to writing forged data into another tenant's records, triggering privileged per-shop workflows for a shop the attacker doesn't own, or corrupting per-tenant business logic — a cross-tenant access impact.

### Likelihood Explanation
Likelihood is high for any app that follows the gem's own documented `Registry.process` usage exactly as shown in `docs/usage/webhooks.md`. No secrets, tokens or elevated access are required — only the ability to register/trigger a webhook on the attacker's own store (default merchant capability) and to send an HTTP POST to the app's public webhook endpoint (which by design must be internet-reachable to receive Shopify's callbacks).

### Recommendation
Include the identifying headers (`shop-domain`, `topic`, `api-version`, `webhook-id`) in the signed material used for verification, or otherwise cryptographically bind them (e.g., verify the `shop-domain` header against an out-of-band expectation, or require the webhook path itself to encode/verify the shop when possible). At minimum, `to_signable_string` should not be limited to the raw body if downstream code (`Registry.process`, `WebhookMetadata`) treats header-derived fields as trusted/authenticated identifiers. Update `docs/usage/webhooks.md` to accurately describe exactly what is verified if the header fields remain unauthenticated, so integrators do not treat `data.shop` as authenticated.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and has installed the target app.
# Step 1: Attacker triggers any webhook event on their own store and captures
# the real raw body + HMAC that Shopify sent (e.g. by temporarily pointing the
# webhook subscription to a request-capture endpoint they control).
captured_body = '{"id": 123, "note": "hello"}'
captured_hmac = "x-shopify-hmac-sha256-value-computed-by-shopify-for-attacker-shop"

# Step 2: Attacker replays the exact same body/hmac pair to the target app's
# public webhook endpoint, but swaps the shop-domain header to the victim shop.
forged_headers = {
  "x-shopify-topic"        => "orders/create",
  "x-shopify-hmac-sha256"  => captured_hmac,       # still valid: body unchanged
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com", # forged, not covered by HMAC
  "x-shopify-webhook-id"   => "any-value",
  "x-shopify-api-version"  => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_body, headers: forged_headers)

# Passes verification: HmacValidator only checks captured_body against the secret.
ShopifyAPI::Webhooks::Registry.process(request)
# => Handler is invoked with data.shop == "victim-shop.myshopify.com",
#    even though the payload was never generated for that shop.
```

To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
