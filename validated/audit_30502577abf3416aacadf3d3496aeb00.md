Audit Report

## Title
CORS wildcard-subdomain suffix check in Gateway `UserServerConfig` HTTP server allows origin allowlist bypass - ([File: core/services/gateway/network/httpserver.go])

## Summary
The Gateway's `isAllowedOrigin` function in `core/services/gateway/network/httpserver.go` implements wildcard CORS origin matching (`*.domain.com`) using a bare `strings.HasSuffix` check with no domain-label boundary enforcement. This allows any domain that merely ends with the configured suffix string (e.g. `fakeethereum.org` matching `*.ethereum.org`) to be treated as an allowed origin, even though it is not a genuine subdomain.

## Finding Description
In `isAllowedOrigin`, after matching scheme and port, the wildcard branch strips the `*.` prefix from the allowed host and then checks `strings.HasSuffix(originHost, allowedHost)`: [1](#0-0) . This is a pure string-suffix comparison with no requirement that the preceding character be a `.`, so `originHost = "fakeethereum.org"` and `allowedHost = "ethereum.org"` satisfy `HasSuffix` despite `fakeethereum.org` not being a subdomain of `ethereum.org` at all.

This function directly gates the CORS response headers in `handleRequest`, which echoes the caller-supplied `Origin` back verbatim into `Access-Control-Allow-Origin` when `isAllowedOrigin` returns true: [2](#0-1) . The same request path also forwards any client-supplied `Authorization: Bearer` token to `ProcessRequest`: [3](#0-2) . No other validation, allowlist normalization, or label-boundary check exists upstream to compensate for this flaw.

## Impact Explanation
If a Gateway operator configures a wildcard `CORSAllowedOrigins` entry (e.g. `*.ethereum.org`), an attacker who registers or controls any domain whose name simply ends with that string (e.g. `fakeethereum.org`, cheap and easy to register) can serve a malicious web page from that domain. A victim's browser visiting that page will have its cross-origin fetch/XHR requests to the Gateway's user-facing endpoint granted `Access-Control-Allow-Origin` for the attacker's exact origin, letting the attacker's script read JSON-RPC responses returned by DON handlers that would otherwise be same-origin-protected. This is a concrete allowlist bypass leading to cross-origin/cross-user response disclosure, an in-scope Chainlink Gateway impact category.

## Likelihood Explanation
Exploitation requires only: (1) the Gateway operator to have configured a wildcard CORS entry — a normal, supported, documented configuration option, not a misconfiguration outside intended use; and (2) the attacker registering an inexpensive look-alike domain ending in the configured suffix. No credentials, node/DON access, or privileged role is needed — the trigger is an ordinary browser request with an attacker-chosen `Origin` header, which is fully unprivileged-client-triggerable and deterministic/repeatable.

## Recommendation
Enforce a label boundary in the wildcard match, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    base := allowedHost[2:]
    if originHost == base || strings.HasSuffix(originHost, "."+base) {
        return true
    }
}
```
Add regression tests asserting `fakeethereum.org` is rejected against a `*.ethereum.org` allowlist entry, complementing the existing tests at `core/services/gateway/network/httpserver_test.go`.

## Proof of Concept
1. Configure `UserServerConfig.CORSAllowedOrigins = ["https://*.ethereum.org"]`.
2. Send an HTTP request to the Gateway user endpoint with header `Origin: https://fakeethereum.org`.
3. Observe `isAllowedOrigin` strips the wildcard to `ethereum.org` and `strings.HasSuffix("fakeethereum.org", "ethereum.org")` returns `true`, causing the server to respond with `Access-Control-Allow-Origin: https://fakeethereum.org` — confirmable by extending the existing test table in `core/services/gateway/network/httpserver_test.go` (`TestHTTPServer_HandleRequest_CORSEnabled_FromAllowedOriginWildcards`) with the origin `https://fakeethereum.org` and asserting the header is (incorrectly) set.
