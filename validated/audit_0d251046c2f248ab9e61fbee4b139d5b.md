### Title
Webhook topic and shop are not part of the HMAC-signed bytes, allowing topic/handler confusion via replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `HmacValidator.validate` computes/compares the signature solely against that signable string [2](#0-1) . `Registry.process` then dispatches to a handler using the unauthenticated `request.topic` header and forwards the equally unauthenticated `request.shop` header straight into the handler as trusted metadata [3](#0-2) .

### Finding Description
The binding that should hold is: `topic value inside HMAC-signed bytes == topic value Registry dispatches on`. Tracing the code shows this is false — there is no topic (or shop, api-version, webhook-id) inside the signed bytes at all:

- `Request#to_signable_string` returns `@raw_body` only [1](#0-0) .
- `topic`, `shop`, `api_version`, `webhook_id` are read directly from attacker-suppliable HTTP headers with no cryptographic binding to the body [4](#0-3) [5](#0-4) .
- `HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` header; it never touches `topic` or `shop` [6](#0-5) .
- `Registry.process` validates HMAC, then looks up `@registry[request.topic]` (attacker-controlled header) and calls `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))`, propagating both attacker-controlled `topic` and `shop` into the handler as if they were authenticated [3](#0-2) .

Attack flow: an unprivileged attacker installs the target app on their own development shop (legitimate action) and registers a webhook subscription for some topic (e.g. `orders/create`). Shopify sends a legitimately-signed callback to the attacker's own endpoint: `raw_body = B`, `hmac = H = HMAC(api_secret_key, B)`, headers `x-shopify-topic: orders/create`, `x-shopify-shop-domain: attacker-shop.myshopify.com`. The attacker now crafts a direct HTTP POST to the target app's shared webhook endpoint using body `B` and header `x-shopify-hmac-sha256: H` unchanged, but sets `x-shopify-topic` to a different, more sensitive registered topic (e.g. `app/uninstalled`, `customers/data_request`, `shop/redact`, or any other handler the app registered) and/or an arbitrary `x-shopify-shop-domain` value (e.g. a victim shop's domain). Because `HmacValidator.validate` only checks `B` against `H`, the signature still validates. `Registry.process` then dispatches to whichever handler is registered for the attacker-chosen topic and calls it with the attacker-chosen `shop` value and the attacker's own body content, believing both to be authentic.

None of the existing guards catch this: `HmacValidator.validate` is body-only by construction [7](#0-6) ; there is no `ShopValidator.sanitize!`, `state` comparison, or JWT `aud` check in this webhook path since webhooks don't use session tokens; `Context.setup?`/`private?`/`embedded?` are irrelevant to webhook processing; Sorbet typing only enforces that `topic`/`shop` are `String`, not that they match anything cryptographically bound to the body.

### Impact Explanation
An attacker can cause the app to invoke an arbitrary registered webhook handler (chosen by the attacker via the `x-shopify-topic` header) with an attacker-forged `shop` value and attacker-supplied body content, while the request still passes signature validation. If any handler in the app trusts `data.shop` to identify which merchant a webhook concerns (a very common pattern — e.g., looking up that shop's access token, deleting shop data, marking a shop as uninstalled, or triggering GDPR-type deletion for a shop the attacker names), this becomes cross-tenant impersonation: the attacker can make the app believe an event happened for a victim shop when it did not, using only their own dev-shop-issued signature. This matches Critical severity (authentication bypass of topic/shop scoping enabling cross-tenant action) since the "shop" and "topic" fields — which downstream handler code is expected to trust as authenticated — are fully attacker-controlled and unbound from the signed payload.

### Likelihood Explanation
Preconditions: the attacker needs a valid webhook subscription for the target app on any shop they control (trivial, no special access needed — this is exactly the attacker capability granted in scope) and knowledge of the app's single shared webhook endpoint URL (also typically discoverable/documented). Cost is one legitimate webhook delivery capture plus one crafted HTTP replay with modified headers — fully repeatable against any topic registered in `@registry` and any `shop` string the attacker chooses, with no rate limits on header values. Feasibility is high: no secret material, no TLS interception, and no elevated privilege is required.

### Recommendation
Bind `topic` (and ideally `shop`, `api-version`, `webhook-id`) into the signable string used for HMAC verification, or otherwise cryptographically tie the dispatch key to the signed body — e.g., have `to_signable_string` include a canonicalized representation of the relevant headers, or require the app to look up expected topic per registered callback URL rather than trusting the `x-shopify-topic` header for dispatch. At minimum, document that `shop` and `topic` in `WebhookMetadata` are unauthenticated header values and must not be trusted by handler implementations without independent verification (e.g., confirming the shop has an active, previously-established session/installation before acting).

### Proof of Concept
```ruby
# test/webhooks/topic_replay_test.rb
require_relative "../test_helper"

module ShopifyAPITest
  module Webhooks
    class TopicReplayTest < Test::Unit::TestCase
      def setup
        super
        @raw_body = '{"id":123,"note":"hello"}'
        secret = ShopifyAPI::Context.api_secret_key
        @valid_hmac = Base64.encode64(
          OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, @raw_body)
        ).strip
      end

      def build_request(topic)
        ShopifyAPI::Webhooks::Request.new(
          raw_body: @raw_body,
          headers: {
            "X-Shopify-Topic" => topic,
            "X-Shopify-Hmac-Sha256" => @valid_hmac,
            "X-Shopify-Shop-Domain" => "attacker-shop.myshopify.com",
            "X-Shopify-Api-Version" => "2024-01",
            "X-Shopify-Webhook-Id" => "1",
          },
        )
      end

      def test_same_signed_body_validates_under_two_different_topics
        request_a = build_request("orders/create")
        request_b = build_request("app/uninstalled") # attacker-chosen, more sensitive topic

        assert(ShopifyAPI::Utils::HmacValidator.validate(request_a))
        assert(ShopifyAPI::Utils::HmacValidator.validate(request_b))

        # Binding under test: topic in signed bytes vs topic used for dispatch.
        # to_signable_string is identical for both (body only), proving topic
        # is not bound into the HMAC despite Registry.process dispatching on it.
        assert_equal(request_a.to_signable_string, request_b.to_signable_string)
        refute_equal(request_a.topic, request_b.topic)
      end
    end
  end
end
```
This demonstrates that one Shopify-issued signature validates under two different `x-shopify-topic` values, confirming `Registry.process`'s topic-based dispatch (`lib/shopify_api/webhooks/registry.rb:192`) is not cryptographically bound to the signed content produced by `Request#to_signable_string` (`lib/shopify_api/webhooks/request.rb:36-38`).
