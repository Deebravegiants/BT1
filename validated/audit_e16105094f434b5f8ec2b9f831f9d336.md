### Title
Cross-Tenant Webhook Spoofing via Unbound `shop` Field in HMAC Verification - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/utils/hmac_validator.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, using the app's single, global `api_secret_key`. The `shop` field that identifies which tenant the webhook belongs to is taken from the `X-Shopify-Shop-Domain` header and is never included in the signed content, so it is never cryptographically bound to the verified payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0)  while `shop` is read from a separate, unsigned header: [2](#0-1) 

`Utils::HmacValidator.validate` computes/compares the HMAC using `verifiable_query.to_signable_string` (the raw body only) against the app-wide `Context.api_secret_key`: [3](#0-2) 

`Registry.process` then trusts `request.shop` as the tenant identity and forwards it, unchecked, into the handler's `WebhookMetadata`: [4](#0-3) [5](#0-4) 

The broken identity binding, stated as an equality that should hold but doesn't:
`HMAC_valid(raw_body, api_secret_key) == true` is treated as proof that `shop == authentic_shop_for(raw_body)`, but in fact the HMAC only proves `raw_body` was generated with knowledge of `api_secret_key` — it says nothing about which shop header accompanies that body. Since `api_secret_key` is a single value shared across every shop that has installed the app (confirmed by `Context.setup`'s single `api_secret_key` parameter used across all `Auth`/`Webhooks` flows), any entity holding a valid `(raw_body, hmac)` pair for one shop can resubmit it with an arbitrary `X-Shopify-Shop-Domain` header and it will still pass validation.

An unprivileged internet user who legitimately installs the target app on their own free/trial development store receives valid webhook deliveries (body + `X-Shopify-Hmac-Sha256`) signed with the app's global `api_secret_key`. They can replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` will still return `true` (the body/secret pair is genuine), and `Registry.process` will invoke the handler with `WebhookMetadata.shop` set to the victim's domain, causing the host application to process attacker-controlled data as if it originated from, and pertains to, the victim shop.

### Impact Explanation
This crosses a tenant boundary: an attacker with only their own (self-installed) shop's credentials can inject data attributed to a different merchant's shop into the host application's webhook processing pipeline, since the shop identity is not bound to the cryptographic proof of authenticity. Depending on how the host app keys its data/session lookups off `WebhookMetadata.shop` (e.g. `orders/create`, `app/uninstalled`, GDPR webhooks), this can lead to cross-tenant data corruption, spoofed app-uninstall/customer-data-erasure events against a victim shop, or injection of forged order/customer data into another merchant's records — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high: any user can install the app for free on a development/trial store to legitimately obtain a valid `(raw_body, hmac)` pair, then simply resend that HTTP request with a different `Shop-Domain` header value to the app's public webhook endpoint. No secrets belonging to the victim, no TLS interception, and no privileged access are required — only reuse of the attacker's own legitimately-received webhook payload.

### Recommendation
Bind the `shop` field into the HMAC-verified content, or otherwise cryptographically tie the shop identity to the signed payload, before trusting it. Concretely, `Webhooks::Request#to_signable_string` should incorporate `shop` (and ideally `topic`/`webhook_id`) into the signed string, or the library should require/validate that `shop` corresponds to an app-registered installation (e.g. checking it against a session store) before constructing `WebhookMetadata`, rather than passing through an unauthenticated header verbatim.

### Proof of Concept
1. Attacker installs the target Shopify app on their own free development store `attacker-shop.myshopify.com`.
2. Shopify delivers a legitimate webhook (e.g. `orders/create`) to the app's registered endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker intercepts/logs this legitimate request (they own the endpoint traffic path or simply reuse their own request/response as any webhook consumer would have visibility into their own deliveries).
4. Attacker replays the exact same request to the app's webhook endpoint, unmodified except for the `X-Shopify-Shop-Domain` header, changed to `victim-shop.myshopify.com`.
5. `ShopifyAPI::Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes `HMAC-SHA256(api_secret_key, B)`, which still equals `H`, so validation passes.
6. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb` line 190 onward) invokes the app's handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)`, causing the host app to process attacker-supplied data as belonging to the victim shop.
