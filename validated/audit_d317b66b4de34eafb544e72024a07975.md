### Title
Webhook `shop` (and `topic`/`webhook-id`) header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `Registry.process` trusts the unauthenticated `shop-domain` header to build the `WebhookMetadata` passed to the app's webhook handler. Because the HMAC never covers the `shop` header, an attacker who controls one legitimate installation of the app can replay a validly-signed webhook body while swapping the `shop-domain` header to any other tenant, and the signature check still passes.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

which returns `@raw_body` only. The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all read straight from HTTP headers that are never part of the signed bytes: [2](#0-1) 

`HmacValidator.validate` computes and compares the signature purely over `verifiable_query.to_signable_string`: [3](#0-2) 

`Registry.process` then validates the HMAC and immediately trusts `request.shop` (from the unauthenticated header) to construct the `WebhookMetadata` object handed to the app's business logic: [4](#0-3) 

The identity binding that should hold is: `shop-domain header == shop that produced/authorized the signed body`. Because the signature only covers the body, this equality is never checked — the `shop` value acted upon (used as the tenant key passed to `handler.handle`) is disjoint from what the HMAC actually verifies (raw body bytes only). Any holder of a validly-signed webhook body (e.g., an attacker with their own paid/free installation of the app, who receives real webhooks for their own store) can capture a legitimate `(body, hmac)` pair and resend it with an arbitrary `x-shopify-shop-domain` header, since the app's `client_secret` (the HMAC key) is shared across all shops using the same app, not shop-specific.

### Impact Explanation
This breaks the tenant boundary the webhook handler relies on: the app processes a foreign/attacker-supplied `shop` value as if it were authenticated, while the actual signed content came from the attacker's own store. Depending on the handler's logic, this enables cross-tenant data confusion — e.g., writing state, disabling access, or triggering redaction/data actions against a victim shop's session/records using data that was never actually produced for that shop. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only that the attacker control one legitimate app installation (any developer/merchant with the app installed can receive real, validly-signed webhooks for their own shop) and be able to send arbitrary HTTP requests to the app's webhook endpoint with a modified `shop-domain` header — both are unprivileged, internet-accessible actions. No access token, `client_secret`, or privileged account is needed.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`) header values in the bytes covered by the HMAC verification, or independently authenticate the `shop-domain` header against the tenant expected for that specific signed request. At minimum, `to_signable_string` should bind the raw body to the shop domain the app registered the webhook against so that swapping the header invalidates the signature.

### Proof of Concept
1. App has two merchants installed: Attacker-owned `attacker.myshopify.com` and Victim `victim.myshopify.com`, both sharing the same app `client_secret`.
2. Attacker triggers/receives a legitimate webhook for their own shop, capturing `raw_body` and the resulting `x-shopify-hmac-sha256` value (computed by Shopify using the shared `client_secret` over the body only).
3. Attacker replays the exact same `raw_body` and `hmac` header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds successfully; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the shared secret [5](#0-4) .
5. `handler.handle` is invoked with `WebhookMetadata` carrying `shop: "victim.myshopify.com"` [6](#0-5) , causing the app to act on attacker-controlled data under the victim's tenant identity.
