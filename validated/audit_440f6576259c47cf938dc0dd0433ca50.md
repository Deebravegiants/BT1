### Title
Cost model's `allocated_accounts_data_size` ignores CPI-nested allocations and is never trued-up to actual `accounts_resize_delta`, allowing the per-block accounts-data-growth budget to be underpriced/bypassed - ([File: cost-model/src/cost_model.rs])

### Summary
`CostModel::calculate_allocated_accounts_data_size` only inspects top-level `SystemInstruction` calls via `transaction.program_instructions_iter()`, so any account-data growth performed through a CPI into the system program (e.g., a custom program that internally calls `system_instruction::allocate`/`create_account`) is invisible to the cost model. Critically, `CostModel::calculate_cost_for_executed_transaction` — the function that is supposed to "true up" costs with real execution data — recomputes `allocated_accounts_data_size` from the exact same static top-level instruction iterator instead of the actual post-execution `accounts_resize_delta`, so the undercount is never corrected before it is committed into `CostTracker`.

### Finding Description
`CostModel::calculate_allocated_accounts_data_size` (`cost-model/src/cost_model.rs:265-301`) walks `instructions: impl Iterator<Item = (&Pubkey, SVMInstruction)>` and only recognizes allocation when `program_id == system_program::id()` at that iterator level [1](#0-0) . This iterator, `transaction.program_instructions_iter()`, only yields the transaction's top-level compiled instructions — it has no visibility into instructions a program issues via CPI. `calculate_cost` (pre-execution estimate) calls it with `transaction.program_instructions_iter()` [2](#0-1) , and `calculate_cost_for_executed_transaction` (the post-execution "true-up") calls it again with the *same* static `transaction.program_instructions_iter()` [3](#0-2) . Only `programs_execution_cost` and `loaded_accounts_data_size_cost` are replaced with actual execution figures; `allocated_accounts_data_size` is not derived from the real `accounts_resize_delta`/`AccountsDeltas` that SVM actually records per transaction [4](#0-3) .

Separately, the real per-transaction data-growth hard cap is enforced deep in `TransactionAccounts::can_data_be_resized` against a single global `resize_delta` cell shared across the whole `TransactionContext`, regardless of whether the resize was requested by a top-level instruction or a nested CPI [5](#0-4) . That path bounds a single transaction to at most `MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION` (== `MAX_PERMITTED_ACCOUNTS_DATA_ALLOCATIONS_PER_TRANSACTION`) bytes of real growth, but it does not report that real number back into `CostTracker`. The real accounts-data-size change is separately tracked into the bank's global counter via `update_accounts_data_size_delta_on_chain` from `AccountsDeltas::accounts_resize_delta` [6](#0-5) , entirely independent from `CostTracker::allocated_accounts_data_size`.

The consequence: `CostTracker::would_fit`'s block-wide budget check compares `self.allocated_accounts_data_size` (an aggregate of the *static, CPI-blind* per-tx estimates) against `self.limits.allocated_data_size` (`MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA = 100_000_000` bytes) [7](#0-6) [8](#0-7) . If an unprivileged attacker's transactions perform account-data growth exclusively through a CPI into the system program (not a top-level `CreateAccount`/`Allocate` instruction), `calculate_allocated_accounts_data_size` returns `0` (or an undercount) for those transactions both before and after execution, so `CostTracker::add_transaction_cost`/`try_add` [9](#0-8)  books zero (or too little) growth for a transaction that can legitimately grow account data up to `MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION` per tx (per the hard enforcement in `can_data_be_resized`). The intended per-block `allocated_data_size` budget invariant is thereby underpriced/bypassable, with no post-hoc correction, since the "actual cost" recomputation path never substitutes real `accounts_resize_delta` for this field.

### Impact Explanation
This falls under the "cost-model underpricing" bounty category: an unprivileged attacker packing many CPI-based-allocation transactions into a block can drive real per-block account-data growth (tracked separately via `accounts_data_size_delta_on_chain`) well past the `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` limit that `CostTracker` is supposed to enforce, since the tracker never sees the true growth for these transactions. This is a resource-accounting/DoS-adjacent issue (excess account-data growth per block beyond the designed safety budget), not a funds-loss bug — each individual transaction is still bounded by the hard per-transaction cap in `can_data_be_resized`, but the aggregate per-block cap that `CostTracker` is meant to enforce can be silently exceeded across many transactions in the same block.

### Likelihood Explanation
Fully unprivileged and repeatable: the attacker only needs to deploy (or reuse) an ordinary on-chain program that performs `system_instruction::allocate`/`create_account` via CPI rather than as a top-level instruction, then submit ordinary transactions invoking it — no leader/validator control, no staking, no crafted snapshots required. This works with the default `program_instructions_iter()`-based static analysis in both `calculate_cost` and `calculate_cost_for_executed_transaction`, and is reproducible in a standard integration test against `Bank`/`CostTracker`.

### Recommendation
Replace the static-instruction-based `allocated_accounts_data_size` in `calculate_cost_for_executed_transaction` with the actual post-execution `AccountsDeltas::accounts_resize_delta` (already available on `TransactionExecutionDetails`) so the cost tracker's accounting is trued up to real account growth, mirroring how `loaded_accounts_data_size_cost` is already trued up with `committed_tx.loaded_account_stats.loaded_accounts_data_size`.

### Proof of Concept
Integration test plan (using `Bank`/`CostTracker` as in `runtime/src/bank/tests.rs` and `core/src/banking_stage/consumer.rs` test patterns):
1. Deploy a small BPF program `cpi_allocator` whose instruction handler performs a CPI into the system program's `Allocate`/`CreateAccount` for a target account (space = e.g. 9_000_000 bytes), instead of the transaction issuing `system_instruction::allocate` at top level.
2. Build a transaction whose only top-level instruction invokes `cpi_allocator` (no top-level `system_program` instruction).
3. Compute `estimated = CostModel::calculate_cost(&tx, &bank.feature_set).allocated_accounts_data_size()` — assert `estimated == 0`.
4. Execute the transaction via `bank.load_execute_and_commit_transactions(...)`, capture `committed_tx` and `bank.load_accounts_data_size_delta_on_chain()` before/after — assert the real delta grew by ~9_000_000 bytes.
5. Compute `actual = CostModel::calculate_cost_for_executed_transaction(&tx, committed_tx.executed_units, committed_tx.loaded_account_stats.loaded_accounts_data_size, &bank.feature_set).allocated_accounts_data_size()` — assert `actual == 0` (still undercounted), demonstrating that the "true-up" function fails to reconcile with the real `accounts_resize_delta` recorded in `AccountsDeltas`.
6. Repeat step 1–5 across many transactions/slots and assert `bank.read_cost_tracker().unwrap().allocated_accounts_data_size` stays at/near 0 while `bank.load_accounts_data_size_delta_on_chain()` grows well past `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` (100_000_000 bytes) within a single block/slot, proving the intended per-block budget invariant is bypassed.

    pub(crate) fn can_data_be_resized(
        &self,
        old_len: usize,
        new_len: usize,
    ) -> Result<(), InstructionError> {
        // The new length can not exceed the maximum permitted length
        if new_len > MAX_ACCOUNT_DATA_LEN as usize {
            return Err(InstructionError::InvalidRealloc);
        }
        // The resize can not exceed the per-transaction maximum
        let length_delta = (new_len as i64).saturating_sub(old_len as i64);
        if self.resize_delta.get().saturating_add(length_delta)
            > MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION
        {
            return Err(InstructionError::MaxAccountsDataAllocationsExceeded);
        }
        Ok(())
    }

    ) -> Result<(), CostTrackerError> {
        let cost: u64 = tx_cost.sum();

        if self.block_cost().saturating_add(cost) > self.limits.block_cost {

            return Err(CostTrackerError::WouldExceedBlockMaxLimit);
