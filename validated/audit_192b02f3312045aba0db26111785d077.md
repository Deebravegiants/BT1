Confirmed: none of `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, or `fundRequest()` in `EvmHost.sol` capture the `amounts` array returned by `swapETHForExactTokens` or refund any leftover native token to `_msgSender()`. There is no `receive()`/withdraw path for stray ETH visible in this contract either, so any leftover ETH from the swap is unrecoverable by the depositor. This is a direct, unprivileged-user-reachable analog of the DODO finding: a caller supplies native token as payment, the actual amount consumed is computed from mutable, front-runnable AMM reserves, and the difference is not returned to the payer.

### Title
Unrefunded native-token overpayment in `EvmHost.dispatch`/`fundRequest` due to `swapETHForExactTokens` without leftover refund - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` accept `msg.value` and swap it for an exact amount of fee token via Uniswap V2's `swapETHForExactTokens`, but never capture the swap's return value or refund any unspent native token to the caller [1](#0-0) .

### Finding Description
`swapETHForExactTokens(post.fee, path, address(this), block.timestamp)` is called with `{value: msg.value}`, and the Uniswap V2 router refunds any unused ETH to its caller — which is `EvmHost` itself, not the original `_msgSender()` — because `EvmHost` never reads the returned `amounts` array nor forwards the difference back to the user [1](#0-0) . The same pattern is repeated identically in `dispatch(DispatchGet)` [2](#0-1)  and `fundRequest` [3](#0-2) .

Because `post.fee`/`get.fee`/`amount` is a fixed feeToken output and the amount of ETH the router actually spends is priced off the pool's current reserves at execution time, any user who supplies `msg.value` with a safety buffer above the exact spot price (the documented, recommended practice since the frontend `quote()` call is explicitly flagged as imprecise and sandwich-vulnerable, per the docs' own warning) will have the unspent remainder silently swallowed by the contract instead of returned. This is structurally the same defect class as the DODO report: an amount computed from live, manipulable reserves is used to settle a user-facing transaction with no accounting/return of the residual value the user actually supplied, and the shortfall accrues to the protocol/pool side rather than the payer. An attacker can additionally manipulate the local Uniswap V2 pool's reserves (e.g., via a sandwich trade before the victim's `dispatch` transaction) to widen the gap between the price the user estimated off-chain and the pool state at execution, maximizing the amount of native token that ends up trapped for any given `msg.value`.

Contrast this with `IntentGatewayV2`'s own `placeOrder`, which performs the identical swap but *does* capture `amounts[0]` and refunds the leftover native token to `msg.sender` [4](#0-3)  — confirming this refund logic is the expected/needed pattern and that `EvmHost` is missing it.

### Impact Explanation
Any unprivileged caller of `dispatch()`/`fundRequest()` who pays in native token loses the ETH sent in excess of the exact amount the router needed to acquire the fee token, with no path to reclaim it — this is a permanent, protocol-level loss/freezing of user funds triggerable from a single ordinary transaction (the primary entry point documented for POST/GET dispatch fee payment). Given that `dispatch()` is the core entry point for essentially all outbound ISMP messages, this affects every application and user paying fees in native token across the `EvmHost` deployment.

### Likelihood Explanation
High. Overpaying `msg.value` on `dispatch`/`fundRequest` is the normal, documented usage pattern — the docs explicitly instruct developers to estimate fees off-chain via `quote()` and warn that this estimate is imprecise and sandwich-attack-prone, meaning a safety margin is the expected behavior, guaranteeing routine leftover ETH on essentially every native-token dispatch. No special privilege or complex setup is needed; a griefer can additionally manipulate the router pool's reserves to enlarge the leftover for any given transaction.

### Recommendation
In `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, capture the `amounts` array returned by `swapETHForExactTokens` and refund `msg.value - amounts[0]` back to `_msgSender()` (mirroring the pattern already implemented in `IntentGatewayV2.placeOrder`), or add a `minAmountIn`/`maxAmountIn`-style guard plus explicit ETH refund logic so no native token payment is ever retained beyond what the swap actually consumed.

### Proof of Concept
1. Attacker observes/front-runs the local Uniswap V2 WETH/feeToken pool to move its reserves so that acquiring `post.fee` feeToken now costs less ETH than the pool state the user priced their `msg.value` buffer against (or simply relies on the normal safety margin any caller adds when using `dispatch()`).
2. A user calls `EvmHost.dispatch(DispatchPost)` with `msg.value` set to a reasonable buffer above the estimated cost of `post.fee`.
3. `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` executes, consuming only `amounts[0] < msg.value` ETH and refunding `msg.value - amounts[0]` to `address(this)` (i.e., `EvmHost`), per Uniswap V2 Router semantics.
4. `EvmHost` never reads `amounts` and never sends any ETH back to the user; the request is dispatched as if the transaction cost exactly `msg.value`.
5. The difference is permanently retained by `EvmHost` with no accounting entry (`FeeMetadata` only records `post.fee` in feeToken terms) and no function to withdraw it back to the payer.
