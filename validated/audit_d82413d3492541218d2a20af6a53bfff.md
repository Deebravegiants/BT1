### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) headers are not bound by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable representation from the raw body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read from unauthenticated HTTP headers. `Registry.process` treats a valid HMAC as proof that the *entire request*, including the shop identity, is genuine, then forwards the unauthenticated `shop` value to the host application's handler. This breaks the intended binding `hmac(secret, request) == request.shop`, letting any actor who can obtain one valid `(raw_body, hmac)` pair signed with the app's shared secret replay it under an arbitrary `shop-domain` header.

### Finding Description
The identity binding an HMAC is supposed to provide is: *the bytes that determine tenant/shop context are exactly the bytes that were verified*. Here that binding is broken:

- `to_signable_string` returns only the raw body: [1](#0-0) 
- `shop`, `topic`, `webhook_id`, `api_version` are derived purely from headers and are never part of the signed content: [2](#0-1) 
- `HmacValidator.validate` only checks `verifiable_query.to_signable_string` against the app's shared `api_secret_key`: [3](#0-2) 
- `Registry.process` accepts the request once the body-only HMAC checks out, then routes `request.shop` (an unauthenticated header) straight into the handler's tenant context: [4](#0-3) 

Because `api_secret_key` is a single, app-wide secret shared by every shop that installs the app (not a per-shop secret), any merchant who installs the app can legitimately receive a valid `(raw_body, X-Shopify-Hmac-Sha256)` pair for their own store's webhook traffic. That attacker can then replay the exact same body/HMAC to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) with a victim shop's domain. `HmacValidator.validate` still succeeds because it never inspects those headers, and `Registry.process` will dispatch the payload to the handler tagged with the attacker-chosen `shop`, exactly as documented: the handler receives `data.shop` as the "shop domain of the webhook" without any cryptographic guarantee behind it. [5](#0-4) 

### Impact Explanation
Host applications are expected to use `WebhookMetadata#shop` to select the tenant record to read or mutate (this is literally what the gem's own documentation recommends, e.g. `shop_domain: data.shop`) [6](#0-5) . A forged shop header lets one authenticated (installed) merchant cause the host app to apply another merchant's webhook body under a victim's tenant context — i.e., cross-tenant data injection/corruption using only the ability to install the app and capture one legitimate webhook delivery. This matches the "cross-tenant access" critical-impact category.

### Likelihood Explanation
Any user who can install the app on a real Shopify store (a normal, unprivileged action) automatically obtains valid `(body, hmac)` pairs for real webhook events sent to their own endpoint. Forging headers on an HTTP POST to the app's own publicly reachable webhook route requires no secret knowledge beyond that — it is a pure client-side HTTP crafting exercise, requiring no access to `api_secret_key`, tokens, or TLS interception.

### Recommendation
Include the header-derived identity fields (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signable string, or otherwise cryptographically bind them to the verified body (e.g., require the host app to independently verify `shop` against a previously stored, per-installation webhook secret/shop mapping) before `Registry.process` dispatches to handlers. At minimum, document prominently that `data.shop`/`data.topic` are unauthenticated and must not be trusted for authorization decisions without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and registers a webhook (e.g. `orders/create`).
2. Shopify delivers a webhook to the app's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)` — attacker captures `B` and `H` (they control the endpoint or can sniff their own traffic).
3. Attacker sends a new POST to the same app endpoint with identical body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this into `shop == "victim.myshopify.com"`, `to_signable_string == B`.
5. `HmacValidator.validate` recomputes `HMAC-SHA256(api_secret_key, B) == H` → passes.
6. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the host app to process attacker-controlled data as though it originated from the victim shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
