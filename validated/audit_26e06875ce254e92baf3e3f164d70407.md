### Title
Webhook `shop` and `topic` identity is not covered by the HMAC signature, enabling cross‑tenant replay - (`File: lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop`, `topic`, and `webhook_id` that are handed to the registered handler directly from unauthenticated HTTP headers, while `Utils::HmacValidator` only verifies the raw request body against `Context.api_secret_key`. Because the HMAC never covers the shop/topic identity, any attacker who captured a single legitimate webhook payload+signature pair can replay the exact same body/HMAC against the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header for a different tenant, and the signature check will still pass.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the HMAC only over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns solely the raw HTTP body (`@raw_body`), and the `hmac` value is decoded straight from the `hmac-sha256` header: [2](#0-1) 

The `shop`, `topic`, and `webhook_id` accessors, however, are read from separate, unsigned headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`): [3](#0-2) 

`Webhooks::Registry.process` validates the HMAC (which only proves the body bytes were signed by Shopify for *some* shop/topic) and then dispatches the handler using the unauthenticated `request.shop` / `request.topic` values: [4](#0-3) 

The identity binding that should hold is: `shop bound by HMAC == shop acted upon by the handler`. Here that equality does not hold — the HMAC binds only the body bytes, not the shop/topic header values that `WebhookMetadata` is built from. An attacker who has legitimately received (or otherwise obtained) one genuine `body + hmac-sha256` pair delivered to the app for shop A can POST that identical body and signature to the app's webhook endpoint while setting `x-shopify-shop-domain` to shop B. `HmacValidator.validate` still succeeds because it never inspects the shop header, and the handler is invoked believing the (attacker‑controlled) shop/topic values are authentic.

### Impact Explanation
This crosses the tenant boundary that Shopify webhook signing is meant to guarantee: the app's handler code (session lookup, data writes, GraphQL calls made with the "wrong" shop's session, etc.) can be induced to process a genuine payload under a forged tenant identity. Depending on how the host app implements its `WebhookHandler`, this can result in cross‑tenant data confusion/access — data or events belonging to one merchant being attributed to and acted on for another merchant's session — which matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires the attacker to already possess one valid `(raw_body, hmac)` pair for their own shop's webhook (trivial — they can install the app on their own store and observe/log the webhook delivered to their own endpoint or proxy), then replay it against the app's public endpoint with a modified shop header. No access token, `client_secret`, or privileged account is needed — this is achievable by any unprivileged internet user who can install the target app once and reach the same webhook endpoint. The gem provides no separate authentication of the shop/topic identity beyond this always-permissive header read.

### Recommendation
Bind the shop and topic identity into the verified signature surface, or otherwise cryptographically tie the `shop`/`topic` header values to the signed body before trusting them in `Webhooks::Registry.process`. At minimum, applications should be warned (and the gem should consider enforcing) that `request.shop`/`request.topic` are unauthenticated and must not be used as the sole tenant-resolution key without corroborating them against a known/expected registration (e.g., matching against the shop for which the topic was registered, or requiring the caller to supply the expected shop and reject mismatches).

### Proof of Concept
1. Attacker installs the target app on their own store (`attacker-shop.myshopify.com`) and registers/receives a real webhook (e.g. `orders/create`), capturing the raw body and the `x-shopify-hmac-sha256` header value Shopify sent.
2. Attacker crafts a new HTTP POST to the app's webhook endpoint with:
   - the identical raw body and `x-shopify-hmac-sha256` value captured above,
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (or any target tenant),
   - `x-shopify-topic` optionally altered.
3. `ShopifyAPI::Webhooks::Request.new` parses these headers normally.
4. `Utils::HmacValidator.validate` recomputes the HMAC over the raw body only and it matches, since the header changes are irrelevant to the signature: `lib/shopify_api/utils/hmac_validator.rb` lines 26‑31 and `lib/shopify_api/webhooks/request.rb` lines 10‑13, 35‑38.
5. `Webhooks::Registry.process` calls the app's handler with `WebhookMetadata` carrying `shop: "victim-shop.myshopify.com"` even though the payload was genuinely generated for `attacker-shop.myshopify.com`: `lib/shopify_api/webhooks/registry.rb` lines 188‑200.
