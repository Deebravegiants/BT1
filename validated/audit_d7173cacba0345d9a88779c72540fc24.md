### Title
IntentGatewayV2 same-chain fills only release escrow for inputs paired by index with outputs, permanently freezing unpaired input tokens - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
`_fillSameChain` assumes `order.inputs[i]` always corresponds 1:1 to `order.output.assets[i]` and only ever builds an `escrowedInputs`/release array of length `order.output.assets.length`. Nothing in `placeOrder` (`evm/src/apps/IntentGatewayV2.sol`) enforces `order.inputs.length == order.output.assets.length`. If an order has more input tokens than output tokens, the input tokens at indices `>= outputsLen` are escrowed at `placeOrder` time but never referenced by any release path once the order is marked filled, permanently freezing them — the same class of bug as the referenced report, where an array/mapping is indexed under an unvalidated assumption of correspondence between two different token collections, producing lost/misaccounted funds.

### Finding Description
`placeOrder` escrows every token in `order.inputs` into `_orders[commitment][token]` with no cross-check against `order.output.assets.length`: [1](#0-0) 

For same-chain fills, `_fillSameChain` iterates only over `outputsLen = order.output.assets.length` and, for each `i`, reads the *paired* input at the same index to compute the escrow amount to release: [2](#0-1) [3](#0-2) 

`_filled[commitment]` is set to the solver at the very start of the function, before the loop even runs to completion: [4](#0-3) 

Once `_filled[commitment]` is non-zero, `_cancelSameChain` — the only other path that can move escrowed funds for a same-chain order — is blocked, since it requires the caller to be `order.user` and does not check `_filled`, but in practice a filled order's escrow entries for indices `>= outputsLen` were never decremented, and the withdrawal path (`_withdraw`) only iterates the `WithdrawalRequest.tokens` array that `_fillSameChain` builds (size `outputsLen`): [5](#0-4) 

So if `order.inputs.length > order.output.assets.length`, the extra input token(s) at index `outputsLen..inputsLen-1` remain forever recorded in `_orders[commitment][token]` with the underlying ERC20/native balance sitting in the contract, but with no code path left that ever references that `(commitment, token)` pair again — the order is now "filled" and can't be cancelled, and the fill logic never iterates past `outputsLen`. The contrast with the cross-chain path (`ExtrinsicIntents._fillCrossChain`), which posts the *entire* `order.inputs` array unconditionally for release regardless of `outputsLen`, confirms that the intended semantics never anticipated (nor guarded against) an inputs/outputs length mismatch on the same-chain path: [6](#0-5) 

This is directly analogous to the reported Vault.vy issue: an index/array is treated as if it has a guaranteed 1:1 correspondence with another array of a different denomination/purpose, with no validation enforcing that correspondence, leading to funds being mis-tracked and effectively lost.

### Impact Explanation
Any user input token whose index falls beyond `order.output.assets.length` becomes permanently locked in the `IntentGatewayV2` contract with no on-chain path to recover it once a solver fills the order: cancellation is blocked (order already "filled"), and the fill's release array structurally excludes it. This is a direct, permanent freezing of user funds reachable purely through a normal `placeOrder`/`fillOrder` sequence — no privileged or malicious actor is required, only an order whose `inputs` array is longer than its `output.assets` array (a state the contract itself never rejects).

### Likelihood Explanation
`placeOrder` performs no validation that `order.inputs.length == order.output.assets.length`; the only validations present are duplicate-output-token checks and per-asset zero-amount checks. Any wallet/dApp/user constructing an order with an extra input leg (e.g., to fund calldata execution costs or from an SDK bug) triggers the freeze automatically once a solver fills the order — no attacker collusion needed, and the SDK's own order-construction helpers (`TokenInfo[]` for `inputs` and `output.assets`) do not enforce equal lengths either based on the API surface reviewed.

### Recommendation
- In `placeOrder`, explicitly require `order.inputs.length == order.output.assets.length` (reverting with `InvalidInput`) if same-chain proportional-release-by-index is the intended design, or
- Decouple escrow release for same-chain fills from a strict index pairing: track/release the full `order.inputs` array on full fill (mirroring `_fillCrossChain`'s unconditional posting of `order.inputs`), and only use per-leg proportional math for genuine "swap legs" that are explicitly modeled/declared as such rather than inferred from array position.

### Proof of Concept
1. User calls `placeOrder` with `order.inputs = [USDC(1000), DAI(500), WETH(1)]` and `order.output.assets = [DAI(900)]` (2 extra "unpaired" inputs beyond the single output). `placeOrder` escrows all three tokens into `_orders[commitment][...]` with no length check (`evm/src/apps/IntentGatewayV2.sol:363-373`).
2. A solver calls `fillOrder` → `_fillSameChain`. `outputsLen = 1`; the loop only processes `i = 0`, computing `escrowedInputs[0]` from `order.inputs[0]` (USDC) and releasing it to the solver via `_withdraw`.
3. `_filled[commitment]` was already set to the solver at function entry (`IntrinsicIntents.sol:56`), finalizing the order.
4. `order.inputs[1]` (DAI 500) and `order.inputs[2]` (WETH 1) remain recorded in `_orders[commitment][DAI]` / `_orders[commitment][WETH]` and as real ERC20 balances held by the gateway contract, but no further call (`fillOrder` reverts as already filled; `cancelOrder` is blocked because the order is filled) can ever reference or release them — they are permanently stuck.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
