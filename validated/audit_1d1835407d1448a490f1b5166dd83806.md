### Title
`liquidate` has no minimum-seizure/bonus slippage bound: a raced liquidator repays debt and can receive zero collateral — (File: contracts/controller/src/positions/liquidation/mod.rs)

### Summary
`liquidate(liquidator, account_id, debt_payments, seize_mode)` recomputes the repayment/seizure plan entirely from live state at execution and pulls the liquidator's debt tokens before any seizure is applied. There is no caller-supplied `min_seized`/`min_bonus_bps`/`max_payment` parameter, so between simulation (`get_liquidation_estimate`) and execution a competing liquidation, index accrual, or threshold restamp can shrink the collateral backing the plan — including to a plan that pulls repayment while seizing nothing. This mirrors the StakingBonus bug: the user's commitment is irreversible, the reward is decided by mutable state, and no `minBonus`-style bound exists in the call data.

### Finding Description
`process_liquidation` takes only `debt_payments` and `seize_mode`; the bonus and seizure are derived inside `build_liquidation_plan` from the account's current positions, indexes and cached prices [1](#0-0) . The plan is built at execution time, not from caller-pinned expectations, and the repayment tokens are pulled by `apply_liquidation_repayments` via `transfer_amount_measured` before seizures run [2](#0-1) . Only then is the seizure applied, floor-scaled to the measured receipt [3](#0-2) .

Crucially, `bonus_ray = max(0, capped_ray − base_ray)`, so seizure cap or rounding can zero out the bonus while the repayment stands [4](#0-3) , and the protocol's own liquidation runbook warns that "the contract accepts a liquidation that repays debt and seizes nothing, so the liquidator would pay and receive no collateral" [5](#0-4)  and tells integrators to "re-simulate after every competing liquidation" [6](#0-5) . Planning drops legs that round to zero tokens or shares [7](#0-6) , and in the full-close band "a partial keeps the account's `C / D` and HF, so large accounts can be closed in slices" [8](#0-7)  — so a frontrunning liquidation does not necessarily push HF to 1 (which would safely revert via `HealthFactorTooHigh` [9](#0-8) ), it can instead leave the account liquidatable with collateral already depleted.

### Impact Explanation
Theft of funds / unclaimed yield for the liquidator. Like the StakingBonus user whose NFT locks for 4 years with `bonus = 0`, a liquidator's debt repayment is the irreversible "lock": once pulled, the borrower keeps the debt reduction, while the scaled/capped seizure can return zero bonus or zero collateral. There is no way for the caller to express "revert if I don't receive at least X," so the loss is borne entirely by the slower caller.

### Likelihood Explanation
Liquidations are inherently competitive and raced; `is_liquidatable`/`get_liquidation_estimate` are simulation-time values that any earlier transaction (a competing `liquidate`, `update_indexes` accrual, an oracle price update within bands, `update_account_threshold` restamping collateral weights) invalidates. In the band region `D ≤ C < D·(1+base)` a competing partial liquidation preserves HF < 1 while draining collateral, so the follow-on call neither reverts nor restores the quoted bonus. The documentation's explicit warning to re-simulate after competing liquidations confirms this is an expected, reachable ordering.

### Recommendation
Add a caller-supplied bound to `liquidate` — e.g. a `min_seized_usd_wad` or `expected bonus_bps`/`min_bonus_bps` argument (analogous to the report's `minBonus`) — and revert if the executed plan's total seizure or `result.bonus_bps` falls below it. Alternatively revert when the post-scaling seizure vector is empty while any repayment was pulled. Until then, callers must simulate and submit atomically, as the runbook already advises.

### Proof of Concept
Sketch against the existing harness (`tests/test-harness`):

```rust
// 1. ALICE supplies USDC, borrows ETH; price drops so HF < 1.
// 2. LIQUIDATOR_A calls get_liquidation_estimate(payments, Transfer):
//    plan shows seized_collaterals non-empty, bonus_rate_bps > 0.
// 3. Before A's tx lands, LIQUIDATOR_B executes a partial liquidation
//    in the full-close band (D <= C < D*(1+base)), which keeps C/D and
//    HF < 1 but removes most of each collateral leg.
// 4. A's liquidate() executes: build_liquidation_plan recomputes on the
//    thinned collateral; seizure legs round to zero tokens/shares and are
//    dropped (or capped_ray <= base_ray makes bonus_ray = 0).
// 5. apply_liquidation_repayments still pulls A's debt tokens and
//    apply_repay_batch credits the repayment; A receives nothing or
//    only principal with zero bonus.
// Assert: token debt was transferred from A, ALICE's debt decreased,
// and A's received collateral is 0 (or seized == principal, bonus == 0)
// despite the estimate having quoted a positive bonus.
```

The acceptance of a repay-without-seizure liquidation is corroborated by the documented integrator mitigation ("reject an estimate whose `seized_collaterals` is empty") rather than by an on-chain revert.

```rust
pub(crate) fn process_liquidation(
    env: &Env,
    liquidator: &Address,
    account_id: u64,
    debt_payments: &Vec<HubPayment>,
    seize_mode: SeizeMode,
) -> u64 {
    liquidator.require_auth();
    validation::require_not_flash_loaning(env);

    let mut account = storage::get_account(env, account_id);

    let mut cache = Context::new(env);

    require_non_empty_payments(env, debt_payments);

    // Reject an unusable receiver before moving tokens.
    let mut receiver = resolve_seize_receiver(
        env, liquidator, account_id, &account, seize_mode, &mut cache,
    );

    // Share payment normalization and positivity checks with the estimate view.
    let liquidation_plan = plan::build_liquidation_plan(env, &account, debt_payments, &mut cache);
    let offered = liquidation_plan
        .repayment
        .full_close
        .then(|| payments::aggregate_positive_payments(env, debt_payments));

    let result = liquidation_plan.into_result();

    require_non_empty_payments(env, &result.repaid);
```

```markdown
**Full-close band: partials and signed over-offers both work.** When total
collateral is at least the debt but below `debt × (1 + base bonus)`, the quote
is the whole debt at `bonus_rate_bps` = the HF-preserving cap
(`floor(HF × BPS / p) − BPS`, about `(C / D − 1) × BPS`, never below zero),
and any smaller repayment is accepted at that bonus. A partial keeps the
account's `C / D` and HF, so large accounts can be closed in slices. Whenever
the quote is the whole debt, nothing is trimmed: the controller pulls each
merged offered amount, the pool refunds what exceeds each leg's debt at
execution (the estimate's `refunds`), and every unit of each leg's ceiled debt
is credited. An over-offer signed at simulation still matches after interest
accrues. The liquidator must hold the full offered amount.
```

```markdown
**Insolvent accounts are capped at what the collateral backs.** When collateral
is below debt, the quote is `floor(C / (1 + base))` at the base bonus. A larger
offer is trimmed from the last leg backward, each kept leg rounded down to whole
token units, so the payment never exceeds the quote. A leg whose kept amount
rounds to zero is dropped and refunded whole; when no leg remains the estimate
shows a zero payment and `liquidate` reverts with `InvalidPayments`
(`controller #16`). Because the trimmed amount is what the controller pulls, a
transfer signed for more fails authorization instead of paying for collateral
that is no longer there. Re-simulate after every competing liquidation.
```
