### Title
Webhook `shop`, `topic`, and `webhook-id` identifiers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb), [File: lib/shopify_api/webhooks/registry.rb](lib/shopify_api/webhooks/registry.rb))

### Summary
`Utils::HmacValidator.validate` only authenticates the raw HTTP body of a webhook request. The `shop-domain`, `topic`, and `webhook-id` values, which are used by `Registry.process` to identify the tenant and route the payload to a handler, are taken from HTTP headers that are never included in the signed bytes. Any actor capable of receiving one genuine, correctly-signed webhook for a shop they control can replay the identical body+HMAC to the app's webhook endpoint while substituting a different `shop-domain` (and/or `topic`/`webhook-id`) header, and the request will still pass HMAC validation.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate_signature` computes the signature over exactly that signable string and compares it to the received `hmac` header: [2](#0-1) 

`Registry.process` uses `request.shop` and `request.topic` — both plain headers, `shopify-shop-domain` / `shopify-topic`, that are read verbatim and never appear in `to_signable_string` — to route and attribute the webhook, after only checking that the HMAC (which never covered these fields) is valid: [3](#0-2) [4](#0-3) 

The identity binding that should hold is:
`HMAC(raw_body, api_secret_key) is valid  ⇒  (shop, topic, webhook_id) in the request are the values Shopify actually sent`

But the code only proves:
`HMAC(raw_body, api_secret_key) is valid  ⇒  raw_body is unmodified`

The `shop`, `topic`, and `webhook_id` fields are outside that equality — they are trusted bytes, not verified bytes.

### Impact Explanation
Because the app's `api_secret_key` is shared across every shop that installs the app (it is not per-shop), any merchant/tenant who installs the app and receives a legitimately signed webhook for their own shop can capture that `(raw_body, hmac)` pair and resend it to the app's public webhook endpoint with the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header rewritten to point at a different, victim tenant. `Utils::HmacValidator.validate` still returns `true` because it only checks the body, so `Registry.process` will dispatch the handler with `WebhookMetadata.shop` set to the attacker-chosen victim shop while `body` still contains the attacker's own shop's data. This is a cross-tenant identity-confusion vector: application logic that trusts `data.shop` from `WebhookMetadata` (which every consuming app is expected to do, since that's the field this gem exposes specifically for tenant attribution) can be made to apply attacker-controlled data/state changes against another tenant's context.

### Likelihood Explanation
Any user who can install the app on a shop they control (an "unprivileged internet user" relative to other tenants) can trigger a real webhook delivery for that shop, capture the `raw_body` and its HMAC header from their own inbox/logs, and replay it against the shared public webhook endpoint with a forged `shop-domain` header — no access to `api_secret_key`, access tokens, or any other tenant's credentials is required.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed payload used for HMAC verification, or independently bind the `shop` value to data already authenticated in the body (Shopify webhook bodies typically don't carry the shop domain, so the safer fix is to require the shop to be established out of band, e.g. via a per-shop webhook signing secret or an additional signed header) so that `request.shop`/`request.topic` cannot be altered without invalidating the HMAC.

### Proof of Concept
```ruby
# 1. Attacker installs the app on their own shop and receives a genuine webhook:
raw_body = '{"id":123,"note":"hello"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "attacker-shop.myshopify.com", # original
}

# 2. Attacker replays the SAME body+hmac but swaps the shop header to a victim tenant:
forged_headers = headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# 3. HMAC validation still succeeds because it only checks raw_body:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# 4. Registry.process dispatches the handler with data.shop == "victim-shop.myshopify.com"
ShopifyAPI::Webhooks::Registry.process(request)
```
