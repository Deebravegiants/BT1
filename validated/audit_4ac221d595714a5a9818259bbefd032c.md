### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor sourced entirely from the incoming HTTP header, while the HMAC integrity check performed by `Utils::HmacValidator` is computed solely over the raw request body. This breaks the identity binding: `shop header value == shop value trusted by the handler` is never checked against `shop bound inside the HMAC-signed payload`, because no such binding exists at all.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

`Request#shop` (and `topic`, `webhook_id`, `api_version`) are pulled straight from headers with no cryptographic tie to the signed content: [2](#0-1) 

`Registry.process` validates the HMAC and then unconditionally forwards `request.shop` to the handler as the tenant identifier, with no secondary check that the shop matches anything derivable from the signed payload: [3](#0-2) 

`Utils::HmacValidator.validate` only recomputes the HMAC from `verifiable_query.to_signable_string` (i.e. the raw body for webhooks) and compares it to the received `hmac`: [4](#0-3) 

This is a genuine deficiency of *this gem's* trust boundary: `HmacValidator.validate` returns `true` for **any** shop-domain header value as long as the `(body, hmac)` pair is valid for the shared `api_secret_key` — the gem provides no API to bind the two, and passes the unbound `shop` straight into `WebhookMetadata` used by host app handlers. Contrast this with the OAuth callback path, where `Auth::Oauth::AuthQuery#to_signable_string` explicitly includes `shop` (and `host`) inside the signed string, so `shop` there **is** bound to the HMAC: [5](#0-4) 

The webhook path has no equivalent binding, which is the asymmetry that creates the vulnerability.

### Impact Explanation
Any unprivileged user who can install the target app on **their own** development/free Shopify store will legitimately receive real webhook deliveries with a valid `X-Shopify-Hmac-Sha256` signature computed with the app's shared `api_secret_key` (a secret the attacker never needs to know or steal — Shopify computes it for them). Because the signature covers only the body, the attacker can replay that exact `(body, hmac)` pair directly to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with any victim shop's domain. `Utils::HmacValidator.validate` will report the request as authentic, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event belongs to the victim shop. Depending on how the host app's handler uses `data.shop` (e.g., updating per-shop settings, triggering `app/uninstalled` cleanup, processing GDPR `customers/redact` or `shop/redact` requests, or writing order/customer data under the wrong shop's session/storage key), this enables cross-tenant data corruption or state confusion — satisfying the High-severity "scope/identity check bypass across tenants" category.

### Likelihood Explanation
Likelihood is High: webhook endpoints are unauthenticated public HTTP endpoints by design (Shopify calls them directly), the attacker only needs a free/dev store to obtain one valid `(body, hmac)` sample, and no special privileges, secrets, or social engineering are required — only a straightforward HTTP replay with a modified header.

### Recommendation
Bind the tenant identity into the verified material before trusting it: either include the `shop-domain`, `topic`, and `webhook-id` headers in the HMAC-signable string (mirroring what `AuthQuery#to_signable_string` already does for OAuth), or require host applications to cross-validate `request.shop` against an independently retrieved, already-authenticated session/shop record before acting on the payload, and document this requirement prominently in `Registry.process`/`Webhooks::Request`.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled development store `attacker-shop.myshopify.com`.
2. Trigger any webhook topic the app registers for (e.g., `orders/create`) and capture the raw POST body plus the `X-Shopify-Hmac-Sha256` header sent by Shopify — this signature is valid because it's computed with the app's real `api_secret_key` over the body only, per: [1](#0-0) 
3. Replay that captured request to the same webhook endpoint, but replace the `X-Shopify-Shop-Domain` header with `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds (same body, same hmac), and `Registry.process` invokes the registered handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, as shown by: [3](#0-2) 
5. Any handler logic keyed on `data.shop` now operates against the victim tenant using attacker-supplied event data.
