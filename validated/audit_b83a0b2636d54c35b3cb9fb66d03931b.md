### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook shop-spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes/validates the webhook HMAC over the raw request body only, but the `shop` field that the gem hands to application webhook handlers is read directly from the unauthenticated `x-shopify-shop-domain` / `shopify-shop-domain` header. Because the identity-binding value (`shop`) is disjoint from the value actually covered by the HMAC (`raw_body`), a party who can obtain one validly-signed webhook (e.g., from their own installed shop) can resubmit that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header, causing the receiving application to attribute attacker-controlled webhook data to a victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `Request#shop` is pulled straight from the header, with no cryptographic binding to that same signed payload: [2](#0-1) 

`Registry.process` validates only the HMAC-over-body, then trusts `request.shop` unconditionally when building the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` confirms the equality it checks is `computed_signature(raw_body) == hmac header`, which says nothing about which shop the body belongs to: [4](#0-3) 

The identity binding that should hold is: `shop header == shop that produced/authorized this exact raw_body`. Because the signature only proves `raw_body` was generated with knowledge of `api_secret_key` (true for **any** shop that has installed the app, since the same `client_secret` signs webhooks for every tenant), it does not prove which shop produced it. An attacker who legitimately installs the app on their own (attacker-controlled) shop can trigger a real, validly-HMAC'd webhook for arbitrary content they control (e.g. by editing a product to control fields serialized into the webhook body), capture the `(raw_body, hmac)` pair, and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. `Registry.process` will pass HMAC validation (it only checks `raw_body` vs `hmac`) and will invoke the handler with `WebhookMetadata.shop` set to the victim's domain, `WebhookMetadata.body` set to attacker-controlled content.

### Impact Explanation
This breaks the tenant isolation the gem is supposed to provide between shops: an app relying on the gem's parsed `WebhookMetadata.shop` to key database writes, trigger jobs "for that shop", or otherwise act on a per-tenant basis can be made to associate/process attacker-chosen webhook content under a victim shop's identity — a cross-tenant data-integrity/confidentiality violation reachable by any unprivileged actor who installs the app on their own shop (a normal, unprivileged onboarding action), satisfying the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any application that trusts `WebhookMetadata.shop` as returned by this gem without independently re-validating it against its own list of installed/known shop domains (which the gem does not do or document as required). No secrets, tokens, or privileged access are needed — only the ability to install the app on an attacker-owned development store (a normal unauthenticated/self-service action) and intercept one's own outgoing webhook.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, or otherwise cryptographically tie the header-supplied shop domain to the signed payload before exposing it via `WebhookMetadata`. At minimum, document/require that consuming apps must independently verify `WebhookMetadata.shop` is a known/installed shop before trusting it, and consider having `Registry.process` accept an allow-list of expected shops.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, obtaining valid OAuth access.
2. Attacker performs an action that triggers a subscribed webhook topic (e.g. `products/update`) with attacker-chosen body content.
3. Shopify signs and sends the webhook: `X-Shopify-Hmac-Sha256: HMAC(raw_body, api_secret_key)`, `X-Shopify-Shop-Domain: attacker.myshopify.com`.
4. Attacker intercepts this request, then re-sends the identical `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint but with `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. `HmacValidator.validate` succeeds (it only checks `raw_body` against the HMAC header), and `Registry.process` calls the handler with `WebhookMetadata.shop == "victim.myshopify.com"` and attacker-controlled `body`, per: [5](#0-4)
