### Title
`TokenExchange.exchange_token` sends the app's `client_secret` to a shop host derived from an unvalidated JWT `dest` claim - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` builds the OAuth token-exchange request host directly from the session token's `dest` claim, without ever running it through `Utils::ShopValidator`, even though the sibling method `migrate_to_expiring_token` in the same file explicitly performs that validation before use.

### Finding Description
`exchange_token` decodes the caller-supplied `session_token` via `ShopifyAPI::Auth::JwtPayload.new(session_token)` and takes `dest_shop = jwt_payload.shop` unchecked: [1](#0-0) 

`JwtPayload` itself only verifies the HS256 signature and that `aud == Context.api_key`; it performs no check that `dest`/`shop` is a trusted Shopify-owned domain: [2](#0-1) 

`dest_shop` is then used to build a `Session`, which is fed straight into `Clients::HttpClient`, and the request body containing `client_id`/`client_secret` is POSTed to `/admin/oauth/access_token` on that host: [3](#0-2) 

Compare this to `migrate_to_expiring_token` in the exact same module, which explicitly sanitizes the `shop` argument with `Utils::ShopValidator.sanitize!(shop)` — raising `Errors::InvalidShopError` for any non-`TRUSTED_SHOPIFY_DOMAINS` value — before building the identical `client_secret`-bearing request: [4](#0-3) 

`ShopValidator` was purpose-built to guard exactly this class of request (the CHANGELOG explicitly ties its introduction to hardening `shop`/`dest`-derived hostnames used for OAuth requests), and its allow-list (`myshopify.com`, `myshopify.io`, `spin.dev`, `shop.dev`, `shopify.com`) demonstrates that `dest`-style values are not assumed inherently safe: [5](#0-4) [6](#0-5) 

The identity binding that is broken: **host that receives `client_secret` (`https://#{dest_shop}/admin/oauth/access_token`) must equal a host validated as a trusted Shopify domain** — this equality is enforced in `migrate_to_expiring_token` but not in `exchange_token`, even though both methods perform the same sensitive action (POSTing the app's `client_secret`) using a shop value that ultimately originates from data outside this gem's control (the `dest` claim of a JWT that a caller/host application hands to the library).

### Impact Explanation
If `exchange_token` is reached with a `session_token` whose `dest` claim is not a `*.myshopify.com`/trusted-domain-shaped value (e.g., due to a malformed/unexpected token from a non-standard surface, or a host application that does not restrict which tokens it forwards), the library will construct an outbound HTTPS request to that host and place the app's `client_secret` (plus `client_id`) into the POST body sent there. Exfiltration of `client_secret` is a Critical-severity outcome per the scoped impact list, since it allows full app impersonation across all merchants.

### Likelihood Explanation
Exploitability depends entirely on whether a `dest` value outside `ShopValidator`'s trusted set can reach `exchange_token` with a validly-signed JWT — this requires the token to have been signed with the app's own `api_secret_key`/`old_api_secret_key`, which is Shopify's (or the token issuer's) responsibility, not something an anonymous internet attacker can forge on their own. I could not confirm from the code available whether Shopify's real token-issuance guarantees `dest` is always constrained to the trusted-domain list, or whether some legitimate flow (e.g., checkout/customer-account extension tokens, mentioned in the CHANGELOG as having relaxed `sub`/`sid` requirements) could produce a `dest` outside that set. Given this uncertainty, likelihood is assessed as **Medium**: the code-level asymmetry between the two methods in the same file is concrete and provable, but a full end-to-end exploit chain from an unprivileged internet user without any assumption about token issuance could not be fully verified.

### Recommendation
Apply the same `Utils::ShopValidator.sanitize!(dest_shop)` call in `exchange_token` that `migrate_to_expiring_token` already performs, before constructing the `Session`/`HttpClient` used to send the `client_secret`-bearing token-exchange request. This closes the inconsistency and ensures every code path that transmits `client_secret` is gated by the same trusted-domain check.

### Proof of Concept
Not independently reproducible from the gem alone, since it requires a validly HS256-signed JWT (signed with the app's `api_secret_key`) whose `dest` claim is an untrusted host — a precondition outside this library's control. The concrete, code-provable issue is the asymmetric validation shown above:
- `exchange_token`: `dest_shop = jwt_payload.shop` used directly → `lib/shopify_api/auth/token_exchange.rb:41,51,65`
- `migrate_to_expiring_token`: `validated_shop = Utils::ShopValidator.sanitize!(shop)` used instead → `lib/shopify_api/auth/token_exchange.rb:103-104,115`
