### Title
Webhook `shop-domain` and `topic` headers are trusted for tenant/handler routing without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a `Request` as "verified" once `Utils::HmacValidator.validate(request)` succeeds, then unconditionally forwards `request.shop` and `request.topic` to the app's handler as trusted, tenant-identifying data. But the HMAC only ever signs the raw request body — the `shop-domain`, `topic`, `webhook-id`, and `api-version` values are read straight from unauthenticated HTTP headers and never enter the signed bytes. This breaks the identity binding `hmac_covers(shop) == shop_acted_on`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from attacker-writable HTTP headers via `shopify_header`, with no cryptographic tie to the body: [2](#0-1) [3](#0-2) 

`HmacValidator.validate` computes the signature purely over `to_signable_string` (i.e., the body) and HMAC-compares it to the `hmac-sha256`/`x-shopify-hmac-sha256` header: [4](#0-3) 

`Registry.process` gates on that same check and then hands `request.shop` (and `request.topic`, `request.webhook_id`, `request.api_version`) directly to the developer's handler as if they were authenticated fields of the verified request: [5](#0-4) 

Because the same `api_secret_key` is shared across every shop that installs the app, any attacker who can obtain one valid `(raw_body, hmac)` pair — trivially, by installing the app on their own store and capturing a webhook delivery, or by re-using any publicly known/fixed body such as `"{}"` (as literally used in this gem's own test fixtures) — can replay that exact body and signature to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` and `x-shopify-topic` header. `HmacValidator.validate` will still return `true` because it never inspected those headers, and `Registry.process` will invoke the handler believing the event legitimately originated from the victim shop and topic named in the (forged) headers.

### Impact Explanation
This is a cross-tenant identity-binding break: the gem authenticates the payload bytes but lets the caller freely choose which tenant (`shop`) and which business event (`topic`) those authenticated bytes are attributed to. Any app whose webhook handlers key persistence, authorization, or side effects off `WebhookMetadata#shop`/`#topic` (the natural and expected usage, since these are the fields `Registry.process` exposes right after "verifying" the request) can be made to apply another merchant's data/actions to the attacker-chosen shop, or to invoke handlers for topics that were never actually fired for that shop — a cross-tenant access primitive reachable by any unprivileged internet user who can send one crafted HTTP POST to the app's public webhook route.

### Likelihood Explanation
High. No secrets are required: the attacker only needs one legitimate `(body, hmac)` pair, which is easy to obtain (install the app on their own shop, or exploit that the HMAC is only over the body — an attacker-controlled shop's own genuine webhook for a trivial/known body such as `{}` works immediately, as shown by this gem's own test fixtures using raw body `"{}"`). No TLS interception, credential leakage, or privileged access is needed; the webhook HTTP endpoint is by design internet-reachable.

### Recommendation
- Do not treat `shop`, `topic`, `webhook_id`, or `api_version` as authenticated once the HMAC check passes. Document clearly that only the raw body is covered by the HMAC.
- Require host applications to independently confirm `request.shop` against a known/installed shop record (session store) before acting on webhook data, and consider binding `topic`/`webhook_id` to server-side webhook subscription records rather than trusting the header value for dispatch.
- If feasible, extend the signable string (or provide a secondary verification step) to also bind `shop` and `topic`, e.g. by cross-checking the webhook_id against Shopify's Admin API to confirm the subscription's shop/topic match the headers before invoking handlers.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com`, obtaining a live webhook delivery (or simply computes locally that for `raw_body = "{}"`, `hmac = Base64.encode64(OpenSSL::HMAC.digest("sha256", api_secret_key, "{}"))`) — the app's `api_secret_key` is shared across all shops, so this signature is valid for every tenant.
2. Attacker POSTs to the app's webhook endpoint with:
   - `x-shopify-hmac-sha256`: the valid signature for body `"{}"`
   - `x-shopify-shop-domain`: `victim-shop.myshopify.com`
   - `x-shopify-topic`: any topic registered with the app (e.g. `app/uninstalled`, `customers/redact`)
   - body: `{}`
3. `Registry.process` calls `HmacValidator.validate(request)` → `true` (body matches signature) as in [6](#0-5) .
4. The registered handler for that topic is invoked with `WebhookMetadata` carrying `shop: "victim-shop.myshopify.com"`, which the attacker fully controlled and which was never covered by the HMAC, per [7](#0-6) .

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
