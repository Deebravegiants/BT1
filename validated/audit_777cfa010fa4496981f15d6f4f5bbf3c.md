### Title
Unchecked `U128`→`u64` truncation in `swap_token_amount_base_out` fee scaling lets an attacker specify an `amount_out` that under-charges `amount_in` - (File: `program/src/processor.rs`)

### Summary
`process_swap_base_out` / `process_swap_base_out_v2` compute the required input amount for a requested output amount using 128-bit math and then convert the result to `u64` with the truncating `U128::as_u64()` (from the `uint` crate), instead of a checked/range-validated conversion. Because the divisor used in `swap_token_amount_base_out` (`total_pc/coin_without_take_pnl - amount_out`) can be made arbitrarily small by an attacker who freely chooses `amount_out`, the pre-cast `U128` value can be pushed far above `u64::MAX` while still fitting in `U128`. The subsequent `.as_u64()` silently keeps only the low 64 bits, so an attacker can pick an `amount_out` value such that the wrapped `swap_in_after_add_fee` is small, paying far less than the economically correct input for a large output.

### Finding Description
In `Calculator::swap_token_amount_base_out` (`program/src/math.rs`, lines 327-367) the amount-in is computed as: [1](#0-0) 
`amount_in = coin * amount_out / (pc - amount_out)` (or the symmetric `PC2Coin` case). The subtraction `total_pc_without_take_pnl.checked_sub(amount_out)` only fails (panics via `.unwrap()`) when `amount_out > total_pc_without_take_pnl`; a value very close to, but below, the reserve (e.g. `total_pc_without_take_pnl - 1`) is legal and yields a denominator of `1`, so `amount_in` becomes roughly `coin * amount_out`, i.e. up to ~`u64::MAX²` in magnitude — comfortably representable in `U128` (max ≈ 3.4e38) but far larger than `u64::MAX` (≈1.8e19).

Back in `process_swap_base_out` (`program/src/processor.rs`), this oversized `U128` is scaled by the fee factor and then truncated to `u64` with no range check: [2](#0-1) 

The only validation on `amount_out` happens *after* this truncating cast, and only checks the upper bound relative to the pool reserve — it does not prevent the divisor from becoming a small, attacker-chosen value: [3](#0-2) 

The exact same pattern (compute in `U128`, truncate with `.as_u64()`, check bounds afterward) exists in the CPI-guarded variant `process_swap_base_out_v2`: [4](#0-3) [5](#0-4) 

Because the pool reserves (`total_pc_without_take_pnl`, `total_coin_without_take_pnl`) are public on-chain state, and the fee constants (`swap_fee_numerator`/`denominator`) are fixed, an attacker fully controls every input to the modular arithmetic `swap_in_after_add_fee = (coin * amount_out * fee_denom / (fee_denom - fee_num)) mod 2^64` performed off-chain before submitting the transaction. This is a deterministic, invertible/searchable equation in the single unknown `amount_out` (bounded by `< total_pc_without_take_pnl`), so an attacker can pre-compute (or brute-force over the small remaining search space) an `amount_out` value for which the wrapped, truncated `swap_in_after_add_fee` is arbitrarily small (even 1 or near-zero, subject to the `!= 0` check), while `amount_out` itself remains large (up to just under the full pool reserve).

### Impact Explanation
This is a critical accounting break: an unprivileged swapper can withdraw close to the entire opposite-side reserve of the pool while paying a truncated/wrapped, attacker-selected — and arbitrarily small — amount of the input token. This directly drains LP/pool funds (theft of user/LP funds) and produces an insolvent pool (the constant-product invariant is violated because the real, un-truncated input amount was never actually collected). Both `SwapBaseOut` instructions (`process_swap_base_out` and `process_swap_base_out_v2`) are reachable by any signer supplying arbitrary `amount_out`/`max_amount_in` in a single transaction, with only standard, unprivileged account checks (vault/mint/authority PDA checks) — none of which prevent this.

### Likelihood Explanation
High. The exploit requires only:
1. Reading current public pool reserves (`amm_pc_vault.amount`, `amm_coin_vault.amount`, `amm.state_data.need_take_pnl_*`) to compute `total_pc/coin_without_take_pnl`.
2. Off-chain arithmetic (using 128/256-bit big integers) to search for an `amount_out < total_pc_without_take_pnl` whose corresponding truncated `swap_in_after_add_fee` is small enough to satisfy the attacker's own token balance and desired `max_amount_in`.
3. Submitting a single `SwapBaseOut`/`SwapBaseOut2` instruction with attacker-chosen accounts (their own source/destination token accounts) — no special privileges, validator collusion, or off-chain infrastructure changes are needed.

### Recommendation
Replace all truncating `.as_u64()` (and `.as_u128()`) conversions on values computed from unconstrained/attacker-influenced 128-bit or 256-bit arithmetic with the existing checked helper `Calculator::to_u64`/`Calculator::to_u128` (which use `try_into` and return `AmmError::ConversionFailure` on overflow), specifically:
- `program/src/processor.rs`: the `.as_u64()` calls in `process_swap_base_out` (line 2191) and `process_swap_base_out_v2` (line 2570), and the `.as_u64()` result of `swap_token_amount_base_in` used in `process_swap_base_in`/`_v2` (lines 1982, 2384) for defense in depth.
- `program/src/math.rs`: `InvariantToken::exchange_coin_to_pc`/`exchange_pc_to_coin` and `InvariantPool::exchange_pool_to_token`/`exchange_token_to_pool` (lines 391, 398, 414, 421, 446, 453, 468, 475), and `swap_token_amount_base_out`'s internal computations, so that any value that cannot fit in `u64` causes the instruction to fail instead of silently wrapping.

Additionally, tighten the ordering/logic so that the denominator (`reserve - amount_out`) cannot be driven arbitrarily close to zero without an explicit, checked, non-truncating computation of `amount_in`.

### Proof of Concept
1. Query the pool's `amm_pc_vault`/`amm_coin_vault` balances and `amm.state_data.need_take_pnl_pc/coin` to derive `total_pc_without_take_pnl` (`P`) and `total_coin_without_take_pnl` (`C`), and read `amm.fees.swap_fee_numerator`/`swap_fee_denominator` (`n`, `d`).
2. Off-chain, for direction `Coin2PC`, compute `f(amount_out) = ceil(C * amount_out * d / ((P - amount_out) * (d - n))) mod 2^64` for candidate `amount_out` values in `[P - K, P - 1]` for a small search window `K` (e.g. a few thousand), until an `amount_out` is found where `f(amount_out)` is small (e.g. below the attacker's own token balance and desired `max_amount_in`).
3. Submit `SwapBaseOut` (or `SwapBaseOut2`) with:
   - `amount_out` = the chosen value (just under `P`),
   - `max_amount_in` = the small truncated value found in step 2,
   - attacker-owned `user_source`/`user_destination` token accounts.
4. The instruction passes all existing checks (`user_source.amount < swap_in_after_add_fee` and `swap.max_amount_in < swap_in_after_add_fee` both use the *already-truncated* small value, and `swap.amount_out >= total_pc_without_take_pnl` is false by construction), transferring only the tiny truncated `swap_in_after_add_fee` from the attacker while paying out `amount_out` (≈ the entire pc reserve) from the vault.

*(Note: exact numeric values for a concrete `amount_out` producing a specific small wrapped result were not computed in this analysis — that requires running the modular search with the pool's live `U128`/`uint` arithmetic; the vulnerability's root cause and reachability, however, are fully confirmed in the cited code paths.)*
