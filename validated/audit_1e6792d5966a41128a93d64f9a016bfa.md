### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating that the HMAC over the *raw body* matches the app's secret, then unconditionally trusts the `shop-domain` header to attribute the event to a tenant. Because the shop identity is never part of the signed material, any unprivileged internet user who can obtain one genuinely-signed `(body, hmac)` pair (e.g., a webhook their own store legitimately receives after installing the target app) can replay that exact body/HMAC to the app's public webhook endpoint with a forged `shopify-shop-domain` header pointing at a *different* victim shop. The HMAC check still passes — it never validated the shop — so the handler receives attacker-controlled data falsely attributed to the victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop` accessor pulls the tenant identity straight from an unauthenticated header, with nothing tying it to the signed bytes: [2](#0-1) 

`HmacValidator.validate` computes the HMAC purely over `verifiable_query.to_signable_string` (i.e., the raw body), and never touches the shop header: [3](#0-2) 

`Registry.process` performs the HMAC check and, immediately after, constructs `WebhookMetadata` using `request.shop`, treating it as authenticated tenant context passed on to the app's handler: [4](#0-3) 

The identity binding that should hold is:
`shop_covered_by_hmac == shop_used_for_tenant_attribution (request.shop)`

In reality: `shop_covered_by_hmac` is undefined/empty (HMAC signs only `@raw_body`), while `shop_used_for_tenant_attribution` is taken verbatim from the caller-supplied `shopify-shop-domain` header. Since these are never bound together, `Utils::HmacValidator.validate(request)` returning `true` says nothing about which shop the payload belongs to — it only proves the *body* bytes were signed by the app's secret at some point (by Shopify, for whatever shop originally triggered that webhook).

An attacker who has installed the target app on their own store (a normal, unprivileged install available to anyone) will legitimately receive Shopify-signed webhooks for that store. They can capture one `(raw_body, hmac header)` pair and POST it directly to the app's public webhook endpoint, substituting the `shopify-shop-domain` header with a victim shop's domain. `Registry.process` will validate the HMAC (still valid, since only the body is checked) and forward `data.shop == <victim shop>` to the app's handler, along with the attacker's own webhook body/topic.

### Impact Explanation
This is a cross-tenant identity-binding bypass: an app that uses `data.shop` from `WebhookMetadata` (as documented for handler implementations) to select the session, access token, or database row for the tenant will process attacker-supplied webhook content under a victim shop's identity. Depending on what the topic/body does downstream (e.g., order-processing side effects, inventory sync, GDPR compliance webhooks, or any per-shop record keyed by `data.shop`), this can lead to cross-tenant data corruption or forged events attributed to a shop the attacker does not own — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation requires no privileged credentials: the attacker only needs to install the target app on any store they control (a completely unprivileged, self-service action for any public Shopify app) to obtain one valid `(body, hmac)` pair for a topic of their choosing, and then send an ordinary unauthenticated HTTP POST to the app's public webhook URL with a spoofed `shopify-shop-domain` header. No secret key, access token, or social engineering is needed.

### Recommendation
Bind the shop identity into the verified signable material, or otherwise cross-check the `shop-domain` header against a value derived from data the app already trusts for that installation (e.g., verifying the shop against the currently registered/expected webhook subscriptions per shop, or including shop in the canonical string checked against session state) before using `request.shop` for tenant attribution. At minimum, document prominently that `request.shop` is unauthenticated and must not be trusted for tenant routing without an independent verification step (e.g., matching against a known, previously-established session/shop record) in the host application.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, unprivileged install) and triggers a subscribed topic (e.g. `orders/create`), receiving a genuine webhook request:
   - `raw_body = '{"id":1,...}'`
   - `x-shopify-hmac-sha256 = Base64(HMAC-SHA256(api_secret_key, raw_body))`
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
2. Attacker replays the identical `raw_body` and `x-shopify-hmac-sha256` value to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only (per `Request#to_signable_string`) and finds it matches — the shop header is never part of the check: [5](#0-4) 
4. The registered handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: <attacker's body>, ...)`, causing the app to process attacker-controlled webhook content under the victim shop's tenant context.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
