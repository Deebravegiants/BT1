### Title
Atomic multi-token escrow withdrawal reverts entirely on a single non-standard token transfer, permanently freezing funds for all other components - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.withdraw()` iterates over all escrowed input tokens of an order and transfers each one to the beneficiary in a single loop. If any one of these token transfers fails (fee-on-transfer, blacklist, timelock, pausable, or any non-standard/misbehaving ERC-20), the entire `withdraw` call reverts, blocking redemption/refund of every other (well-behaved) token in the same order. This mirrors the `BasicIssuanceModule` redemption bug class cited in the report, where looping through multiple components with a single failure point reverts the whole operation.

### Finding Description
`withdraw()` is invoked from `onAccept` when handling `RequestKind.RedeemEscrow` or `RequestKind.RefundEscrow` messages, and also from `onGetResponse` for timeout-based refunds: [1](#0-0) [2](#0-1) 

The withdrawal loop itself transfers each escrowed token to the beneficiary and reverts the whole transaction with `TransferFailed()`/`InsufficientNativeToken()` if any single transfer in the array fails: [3](#0-2) 

Because `Order.inputs` (and thus `body.tokens`) is an arbitrary array of tokens chosen by the order creator (user), a single order can escrow multiple different ERC-20 tokens as inputs. If any one of these tokens is non-standard (fee-on-transfer, blacklistable, pausable, or has a bug that makes `transfer` revert or return unexpected data in a way `.call` treats as failure), the `for` loop in `withdraw()` has no isolation between iterations — one bad token blocks redemption/refund of all the other, perfectly fine tokens escrowed under the same `commitment`.

This is directly analogous to `BasicIssuanceModule.redeem()` in the referenced Set Protocol audit finding, where looping through all components and reverting the whole redemption on any single transfer failure prevents users from recovering value from components that would otherwise be redeemable.

### Impact Explanation
An order with multiple input tokens (a legitimate use case supported by `Order.inputs` array) becomes permanently unredeemable/unrefundable if even one of its input tokens is or becomes non-standard (e.g., issuer blacklists the escrow contract or beneficiary, imposes a transfer fee causing balance mismatches leading to revert conditions elsewhere, or is paused). Since `withdraw` is atomic across all tokens in the order, the user's other, perfectly redeemable token balances become permanently frozen in escrow alongside the problematic one. This is a permanent freezing-of-funds impact, matching the Medium severity classification of the original finding.

### Likelihood Explanation
Likelihood is driven by user/order composition, not by any privileged actor: any ordinary user creating a multi-input order in `IntentGatewayV2`/`ExtrinsicIntents` chooses which tokens to include, and a solver later triggers `RedeemEscrow`/`RefundEscrow` dispatch that is delivered to this `withdraw` function. If any one of the chosen input tokens is blacklist-capable, pausable, or otherwise non-standard (which is not restricted by the protocol), the freeze condition can be triggered without any privileged intervention — it only requires normal usage plus one problematic token in the token list.

### Recommendation
Do not perform escrow withdrawal for all tokens atomically in a single reverting loop. Instead, either:
1. Wrap each individual token transfer in `withdraw()` in a try/catch (or low-level call without immediate revert), track per-token success/failure, and only revert on failures deemed unrecoverable, allowing the other tokens to be released; or
2. Change the accounting model so `withdraw` credits per-token internal balances (already tracked via `_orders[commitment][token]`) and expose a separate, per-token `claim(token)` function that lets beneficiaries pull each token independently, so one failing token cannot block the others.

### Proof of Concept
1. User places a cross-chain order via `IntentGatewayV2.placeOrder` (or `ExtrinsicIntents`) with two input tokens: `TokenA` (standard ERC-20) and `TokenB` (a token that blacklists the intent gateway/beneficiary or reverts on transfer to certain addresses).
2. The order fails to fill and times out, or is filled, triggering a `RefundEscrow`/`RedeemEscrow` message dispatched to the destination gateway.
3. `onAccept` decodes the `WithdrawalRequest` and calls `withdraw(body, ...)`.
4. In the loop at [4](#0-3) , the transfer of `TokenB` fails (`success == false`), causing `revert TransferFailed()`.
5. Because the whole `withdraw` call reverts, the escrowed `TokenA`, which would have transferred successfully, is never released — the order's `_orders[commitment][TokenA]` balance remains permanently locked in the contract with no way to retry excluding `TokenB`.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }
