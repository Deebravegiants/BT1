### Title
Litecoin address validation accepts legacy Bitcoin P2SH addresses, causing withdrawals to be sent to wrong-network destinations - ([File: packages/intents-sdk/src/lib/validateAddress.ts])

### Summary
`validateLitecoinAddress` explicitly cannot distinguish a legitimate Litecoin legacy P2SH address (prefix `3`, version byte `0x05`) from a Bitcoin P2SH address using the identical prefix and version byte, and the code comment itself acknowledges this ambiguity. Since `HotBridge.validateWithdrawal` uses this function as the sole gate for Litecoin destination addresses, and the same unmodified string is later passed as the withdrawal receiver, a user can submit a valid Bitcoin address as their Litecoin withdrawal destination and have HOT pay out to that address on the Litecoin network.

### Finding Description
The broken equality: "the address that passed `validateWithdrawal` for `Chains.Litecoin`" should equal "an address that is actually reachable/controlled by the intended recipient on the Litecoin network." This equality is broken because `validateLitecoinAddress` in [1](#0-0)  treats any base58 string with version byte `0x05` and a valid checksum as acceptable — this is the *same* version byte used for Bitcoin P2SH addresses, and the code comment explicitly states: "[Inference] This also matches Bitcoin P2SH; cannot distinguish by prefix+version alone."

The path: `HotBridge.validateWithdrawal` calls `validateAddress(args.destinationAddress, assetInfo.blockchain)` for `assetInfo.blockchain === Chains.Litecoin`, which dispatches to `validateLitecoinAddress` per [2](#0-1) . This is confirmed in the bridge's own test suite, which validates against `Chains.Litecoin` blockchain routing through this same call: [3](#0-2) . The unit test fixtures for `validateLitecoinAddress` themselves include `3GoitrULXWigQqj4fV6FMVqtz8mru5auYh` as an "accepted" P2SH legacy address [4](#0-3) , and the BCH test fixtures show `3J98t1WpEZ73CNmQviecrnyiWrnqRhWNLy` is a legitimate Bitcoin-family P2SH address with the same version byte structure [5](#0-4) , confirming the format collision is real and not merely theoretical.

`destinationAddress` is a plain string field on `WithdrawalParams` passed through the `Bridge` interface to `createWithdrawalIntents` [6](#0-5) ; there is no chain-specific address re-derivation/reformatting step for Bitcoin-family chains anywhere in the validated code paths — the string that passed `validateAddress` is the same string that flows into intent construction as the receiver. Neither `compareAddresses` (token-address collision check) nor the Stellar-only trustline check in `validateWithdrawal` [7](#0-6)  perform any additional network-disambiguation for Litecoin.

### Impact Explanation
A user (or an integrator forwarding a counterparty-supplied address) submits a Litecoin withdrawal with a syntactically valid Bitcoin P2SH address as `destinationAddress`. `validateWithdrawal` does not throw. The unmodified address is then encoded into the on-chain/off-chain withdrawal intent as the Litecoin payout destination. Because Bitcoin and Litecoin are separate, non-interoperable networks, funds sent to that address on the Litecoin chain are not spendable by anyone (the hash160 payload is meaningless on a chain where the corresponding P2SH script/redeem script may not exist, or worse, could correspond to an address controlled by an unrelated third party on Bitcoin who cannot even claim it since it was never broadcast there). This matches Critical severity: funds delivered to a wrong-network destination with no recovery path, entirely from the withdrawer's own mistaken/attacker-crafted input reaching an unvalidated boundary.

### Likelihood Explanation
No special privilege is required — this is triggerable by any ordinary caller of `HotBridge.validateWithdrawal`/`createWithdrawalIntents` for a Litecoin-chain nep245 asset, simply by supplying a valid legacy Bitcoin P2SH string (trivially obtainable, e.g., any public BTC address). This is fully repeatable per withdrawal and costs nothing extra to trigger since it just requires passing a syntactically-valid but wrong-network string.

### Recommendation
Litecoin legacy P2SH addresses (`3...`, version `0x05`) are inherently indistinguishable from Bitcoin P2SH addresses by format alone. Either: (1) reject the `3...`/`0x05` legacy P2SH format entirely for Litecoin and require the newer unambiguous `M...`/`0x32` P2SH prefix, or (2) cross-check against Bitcoin's own address validator and reject any address that validates successfully as both a Bitcoin P2SH and Litecoin P2SH address, surfacing an explicit ambiguity error requiring the user to use an unambiguous address format.

```ts
// hot-bridge.test.ts (vitest)
it("rejects Bitcoin P2SH address supplied as Litecoin destination", async () => {
  const btcP2shAddress = "3J98t1WpEZ73CNmQviecrnyiWrnqRhWNLy"; // valid BTC P2SH, version 0x05
  const bridge = new HotBridge({
    envConfig: configsByEnvironment.production,
    hotSdk: {} as unknown as HotOmniSdk,
  });

  // Currently this resolves (BUG): should throw InvalidDestinationAddressForWithdrawalError
  await expect(
    bridge.validateWithdrawal({
      assetId: "nep245:v2_1.omni.hot.tg:<litecoin-chain-id>_<token>",
      amount: 1n,
      destinationAddress: btcP2shAddress,
    }),
  ).rejects.toThrow(InvalidDestinationAddressForWithdrawalError);

  // Confirm the same unmodified string would be the receiver of the built intent
  const intents = await bridge.createWithdrawalIntents({
    withdrawalParams: { assetId: "...", amount: 1n, destinationAddress: btcP2shAddress },
    feeEstimation: { ... },
  });
  expect(intents.find(i => "receiver" in i)?.receiver).not.toBe(btcP2shAddress);
});
```
