## Title
Unbounded Ancestor-Walk Infinite Loop in GRANDPA Finality Proof Verification, Triggerable by Unauthenticated Header Data — ([File: modules/consensus/grandpa/primitives/src/justification.rs])

## Summary
`AncestryChain::ancestry` walks a chain of attacker-supplied headers from a target hash back toward a base hash using a `while current_hash != base` loop with no cycle detection and no iteration bound. Critically, `verify_grandpa_finality_proof` invokes this ancestry walk **before** the cryptographic GRANDPA justification is verified, so a submitter can craft `unknown_headers` whose `parent_hash` fields form a cycle that never reaches the trusted base hash. This drives the loop into permanent non-termination — a direct structural analog of CVE‑2012‑2138, where `@CopyFrom` failed to reject an ancestor→descendant relationship and looped forever. The path is reachable by anyone via the unsigned `pallet-ismp::handle_unsigned` extrinsic (and even earlier, during `validate_unsigned` mempool validation), with zero authentication of the header data that drives the loop.

## Finding Description
`AncestryChain::ancestry` has no protection against cyclic `parent_hash` references among the supplied headers: [1](#0-0) 

```rust
fn ancestry(&self, base: H::Hash, block: H::Hash) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
    let mut route = vec![block];
    let mut current_hash = block;
    while current_hash != base {
        match self.ancestry.get(&current_hash) {
            Some(current_header) => {
                current_hash = *current_header.parent_hash();
                route.push(current_hash);
            },
            _ => return Err(finality_grandpa::Error::NotDescendent),
        };
    }
    Ok(route)
}
```

`self.ancestry` is a `BTreeMap` built directly from the attacker-supplied `unknown_headers: Vec<H>` inside a `FinalityProof`: [2](#0-1) 

Each `H` is a full Substrate-style header whose `parent_hash` field is an arbitrary, submitter-controlled value — it is not required to reflect an actual chain relationship, only to decode successfully. A submitter can craft two headers `H_a`/`H_b` where `H_a.parent_hash == H_b.hash()` and `H_b.parent_hash == H_a.hash()`, forming a two-node cycle that is always present in `self.ancestry` (so `.get()` never misses and never hits the `NotDescendent` exit).

The decisive flaw is *where* this walk is invoked in `verify_grandpa_finality_proof`: [3](#0-2) 

```rust
let from = consensus_state.latest_hash;
...
let finalized = headers.ancestry(from, target.hash()).map_err(|_| Error::InvalidAncestry)?;

// 2. verify justification.
justification
    .verify(consensus_state.current_set_id, &consensus_state.current_authorities)
    .map_err(...)?;
```

`headers.ancestry(from, target.hash())` executes **before** any GRANDPA signature/commit validation (`justification.verify`). If the attacker sets `target` (the header with the highest `number()` in `unknown_headers`) to be part of the crafted cycle, and the cycle never reaches `from` (the trusted, on-chain `consensus_state.latest_hash`, which the attacker simply omits from their header set), the loop in `ancestry()` never terminates — all before a single signature is checked.

This function is reached by any unprivileged caller through `GrandpaConsensusClient::verify_consensus`, which decodes an attacker-supplied `ConsensusMessage`/`FinalityProof` and calls `verify_grandpa_finality_proof`: [4](#0-3) 

That in turn is dispatched from `pallet-ismp`'s unsigned extrinsic: [5](#0-4) 

and, worse, from `ValidateUnsigned::validate_unsigned`, which runs `Self::execute(messages.clone())` on every submission attempt during **mempool validation**, before the transaction is even included in a block: [6](#0-5) 

This mirrors the Sling `@CopyFrom` bug class precisely: an operation that walks a claimed ancestor/descendant relationship without validating that the relationship is acyclic and terminates, reachable by an unprivileged remote caller, causing denial of service via infinite loop.

## Impact Explanation
This is a route-availability/denial-of-service vulnerability with no privilege requirements:
- Any account (or even an unsigned network peer submitting to the transaction pool) can submit a crafted `ConsensusMessage` containing a GRANDPA `FinalityProof` with a two-node cyclic `unknown_headers` set.
- The offending `ancestry()` call executes before signature checks, so no valid GRANDPA authority signatures are needed at all.
- Because Substrate runtime execution is not instruction-gas-metered the way EVM is, an infinite loop inside `on-chain`/mempool-validation logic can hang the validating node's execution thread indefinitely (also growing `route` unboundedly, adding memory pressure), effectively halting collator/validator block production or transaction-pool processing — a chain-wide route/message delivery outage until the node is manually restarted.
- This satisfies "a route unable to deliver messages" under the acceptance criteria.

## Likelihood Explanation
Likelihood is high: constructing two headers with mutually-referencing `parent_hash` fields requires no privileged keys, no valid GRANDPA signatures, and no special chain state — only crafting a SCALE-decodable header structure with a chosen `parent_hash` value, which is entirely attacker-controlled. The vulnerable code path (`validate_unsigned`) is even executed at the mempool-admission layer, meaning the DoS can be triggered before block inclusion is required.

## Recommendation
- Add cycle detection to `AncestryChain::ancestry` (e.g., track a `visited` set of hashes and error out immediately if a hash is revisited), and/or bound the maximum number of hops by `self.ancestry.len()`.
- Reorder `verify_grandpa_finality_proof` so that `justification.verify(...)` (which validates the GRANDPA commit signatures) runs before any `headers.ancestry(...)` call operates on unauthenticated header data — or otherwise ensure the header set is proven consistent before being walked.
- Consider validating that headers in `unknown_headers` form a genuine, strictly-decreasing-by-number parent chain before constructing/using `AncestryChain`.

## Proof of Concept
1. Construct headers `H_a` and `H_b` (same `HeaderT` type used by the target GRANDPA consensus client) such that:
   - `H_a.parent_hash = H_b.hash()`
   - `H_b.parent_hash = H_a.hash()`
   - `H_a.number()` is the maximum among the submitted `unknown_headers = [H_a, H_b]`
2. Build a `FinalityProof { block: H_a.hash(), justification: <any bytes that decode to a `GrandpaJustification`>, unknown_headers: vec![H_a, H_b] }`.
3. Wrap it in the appropriate `ConsensusMessage` variant matching the target consensus state's state machine (per `envelope_matches_state_machine` in `modules/ismp/clients/grandpa/src/consensus.rs`).
4. Submit as `pallet_ismp::Call::handle_unsigned { messages: vec![Message::Consensus(consensus_message)] }` as an unsigned extrinsic (or simply broadcast it to the network so `validate_unsigned` runs).
5. Observe that `verify_grandpa_finality_proof` → `AncestryChain::ancestry(consensus_state.latest_hash, H_a.hash())` never terminates, since the walk cycles between `H_a` and `H_b` indefinitely without ever equaling `consensus_state.latest_hash`, hanging the executing node.
