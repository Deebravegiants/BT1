## Title
CORS Origin Allowlist Bypass via Improper Suffix Check in Gateway `isAllowedOrigin` - (File: core/services/gateway/network/httpserver.go)

## Summary
The Gateway HTTP server's `isAllowedOrigin` function validates wildcard CORS allowlist entries (e.g. `*.ethereum.org`) using an unanchored `strings.HasSuffix(originHost, allowedHost)` check instead of verifying a proper `.`-delimited subdomain boundary. This lets an attacker who controls a domain merely ending in the same literal string (e.g. `evil-ethereum.org`), rather than a true subdomain of the allowed domain, pass the origin check.

## Finding Description
In `isAllowedOrigin`, the wildcard branch strips the `*.` prefix from the configured allowed host and then does: [1](#0-0) 
`strings.HasSuffix(originHost, allowedHost)` returns `true` for `originHost = "evil-ethereum.org"` and `allowedHost = "ethereum.org"` since the string literally ends with `"ethereum.org"`, even though there is no `.` separator making it a genuine subdomain. This result is used directly to set the reflected CORS header: [2](#0-1) 
No other check (scheme/port comparisons at lines 172-179, exact-match at 181-183) mitigates this, since those checks pass trivially when scheme/port match and the wildcard branch is reached specifically because the exact match failed.

## Impact Explanation
This is a legitimate CORS allowlist bypass reachable by any unprivileged external actor who registers a domain name ending in an operator's configured wildcard suffix without a dot boundary. It allows an attacker-controlled web page to receive `Access-Control-Allow-Origin` reflecting its spoofed origin and read Gateway JSON responses cross-origin — a cross-origin response exposure on the Gateway's public HTTP API, mapping to the "gateway request impersonation / cross-user response corruption" impact category described in scope.

## Likelihood Explanation
Exploitation only requires the operator to configure at least one wildcard entry in `CORSAllowedOrigins` (a documented, supported pattern per the existing test suite, e.g. `TestHTTPServer_HandleRequest_CORSEnabled_FromAllowedOriginWildcards`) and the attacker to register/host a domain ending in that suffix — a low-cost, purely external action requiring no credentials, privileges, or host access. The existing negative test (`TestHTTPServer_HandleRequest_CORSEnabled_FromNotAllowedOriginWildcards`) only exercises origins that don't end with the suffix string at all, and does not cover the actual bypass case (suffix match without a dot boundary), confirming the gap is untested and unfixed in this code.

## Recommendation
Require the character preceding the matched suffix to be `.`, or equivalently match `originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost)`, so only the bare domain or true subdomains satisfy the wildcard rule.

## Proof of Concept
1. Start the Gateway HTTP server with `CORSEnabled: true` and `CORSAllowedOrigins: []string{"https://*.ethereum.org"}` (as in `startNewServer` helper in `core/services/gateway/network/httpserver_test.go`).
2. Send a request with header `Origin: https://evil-ethereum.org`.
3. Observe the response includes `Access-Control-Allow-Origin: https://evil-ethereum.org`, confirming the bypass — this can be added as a Go test case analogous to `TestHTTPServer_HandleRequest_CORSEnabled_FromAllowedOriginWildcards`, asserting the header is set for `origin := "https://evil-ethereum.org"` when the allowlist is `https://*.ethereum.org`.
