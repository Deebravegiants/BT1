Audit Report

## Title
On-Chain AMM Quote Used for Fee-Asset Swap Without User-Supplied Slippage Bound Enables Front-Running/Sandwich Overpayment - (File: `substrate/frame/transaction-payment/asset-conversion-tx-payment/src/payment.rs`)

## Summary
`SwapAssetAdapter::withdraw_fee` computes the amount of a non-native `asset_id` to withdraw for a fee by calling `S::quote_price_tokens_for_exact_tokens(asset_id, A::get(), fee, true)` against live pool reserves and then immediately executes `S::swap_tokens_for_exact_tokens` using that quote as the exact input amount, with no independent slippage bound supplied by the fee payer. [1](#0-0)  This differs from the pallet's own swap extrinsics such as `swap_exact_tokens_for_tokens`, which accept a caller-supplied `amount_out_min`/`amount_in_max` explicitly for slippage protection. [2](#0-1) 

## Finding Description
The quoting function itself documents that "the price may have changed by the time the transaction is executed" and recommends using a min/max parameter to control slippage, confirming the intended protection pattern that `withdraw_fee` does not use. [3](#0-2)  In `withdraw_fee`, the quote taken at extrinsic-preparation time is used directly as the exact swap-input amount:

```rust
let asset_fee =
    S::quote_price_tokens_for_exact_tokens(asset_id.clone(), A::get(), fee, true)
        .filter(|asset_fee| !asset_fee.is_zero())
        .ok_or(InvalidTransaction::Payment)?;
...
let (fee_credit, change) = match S::swap_tokens_for_exact_tokens(
    vec![asset_id, A::get()],
    asset_fee_credit,
    fee,
) { ... };
``` [4](#0-3) 

Both the quote and the swap read the same pool reserves at the same point in block execution (the `prepare` step of the `TransactionExtension`, called from `ChargeAssetTxPayment::prepare`). [5](#0-4)  There is no `Val`/`Pre` field, extension parameter, or config option through which the fee payer can specify a maximum acceptable `asset_id` cost — `ChargeAssetTxPayment` only carries `tip` and `asset_id`. [6](#0-5)  This means an attacker who can achieve favorable transaction ordering (front-running/sandwiching within the same block) can move the pool price of `asset_id` against `A::get()` immediately before the victim's extension executes, causing the victim to be quoted and charged an inflated `asset_fee`.

## Impact Explanation
Any user paying fees via a non-native asset through `pallet-asset-conversion-tx-payment`'s `SwapAssetAdapter` can be forced to overpay `asset_id` for a fixed native fee amount `fee`, with the attacker profiting from the manipulated AMM spread on their surrounding swap. This is a genuine value-transfer loss for the fee payer rooted in the SDK's own fee-charging logic, not a third-party or governance-only issue, and is consistent with the codebase's own admission that these quotes are not safe to use without a slippage bound. [3](#0-2) 

## Likelihood Explanation
Exploitation only requires the ability to submit ordinary swap extrinsics against the same pool and achieve favorable ordering (tip-based prioritization or MEV), which any unprivileged user can attempt; no privileged role, governance action, or protocol misuse is needed. `withdraw_fee`'s `change.peek().is_zero()` check only verifies the swap consumed the exact quoted amount — it does not, and cannot, detect that the quote itself was inflated by manipulation. [7](#0-6) 

## Recommendation
Extend `ChargeAssetTxPayment` (and `OnChargeAssetTransaction::withdraw_fee`) to accept an optional caller-supplied maximum acceptable `asset_id` cost, analogous to `amount_in_max` in `swap_tokens_for_exact_tokens`, and reject the transaction in `validate`/`prepare` if the quoted/actual cost exceeds that bound, rather than relying solely on the freshly computed on-chain quote.

## Proof of Concept
1. Victim submits a transaction using `ChargeAssetTxPayment` with `asset_id = X` to pay a fee `F` in native asset `A`, entering the mempool.
2. Attacker submits a large swap of `A` into `X` in the same pool, ordered before the victim's transaction in the block (via higher tip or MEV), spiking the `X`/`A` price.
3. During `prepare`, the victim's `withdraw_fee` executes `quote_price_tokens_for_exact_tokens(X, A, F, true)`, returning an inflated `asset_fee` reflecting the manipulated reserves. [8](#0-7) 
4. The inflated `asset_fee` of `X` is withdrawn from the victim and swapped for exactly `F` of `A`. [9](#0-8) 
5. Attacker submits a back-run swap reversing step 2 later in the same block, extracting the price-impact profit; the victim has paid more `X` than absent manipulation, with no parameter available to have prevented it. A unit test can be constructed in `substrate/frame/transaction-payment/asset-conversion-tx-payment/src/tests.rs` that manipulates pool reserves via an interleaved swap between quoting and execution, then asserts the fee payer's `asset_id` debit exceeds the pre-manipulation quote.
