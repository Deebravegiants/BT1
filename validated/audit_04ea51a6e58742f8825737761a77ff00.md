This confirms the vulnerability: `Webhooks::Request` derives `topic`, `shop`, `api_version`, and `webhook_id` entirely from unauthenticated HTTP headers [1](#0-0) , while `to_signable_string` (the value that is actually HMAC-verified) is only `@raw_body` [2](#0-1) . `Registry.process` verifies only this HMAC and then dispatches the handler with `request.shop` taken straight from the unauthenticated header [3](#0-2) .

### Title
Webhook `shop` (and `topic`/`webhook_id`) header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing via body replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so `ShopifyAPI::Utils::HmacValidator.validate` cryptographically authenticates the body bytes but not the `shopify-shop-domain`, `shopify-topic`, or `shopify-webhook-id` headers that `Registry.process` trusts to route and attribute the webhook to a specific merchant.

### Finding Description
`HmacValidator.validate_signature` computes `OpenSSL::HMAC.hexdigest` over `verifiable_query.to_signable_string` and compares it to the `hmac` value returned by the object [4](#0-3) . For `Webhooks::Request`, `to_signable_string` is defined as just `@raw_body` [2](#0-1) , and `hmac` is parsed from the `x-shopify-hmac-sha256`/`shopify-hmac-sha256` header [5](#0-4) . The `shop`, `topic`, `api_version`, and `webhook_id` accessors are read straight from headers with no cryptographic binding to the body or the HMAC [1](#0-0) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` before invoking the registered handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` [3](#0-2) . Because the signature check never touches the `shop`/`topic`/`webhook_id` headers, the equality the gem is supposed to guarantee — "the shop that produced the HMAC == the shop attributed to the event" — does not actually hold. Anyone who has ever received one genuine, correctly-HMAC'd webhook delivery for the app's `client_secret` (e.g., because they installed the app on their own store, a legitimately obtainable, unprivileged action) can capture that `raw_body` + valid `hmac`, then replay it to the app's public webhook endpoint with the `shopify-shop-domain` header rewritten to a victim store, and `HmacValidator.validate` will still return `true` because the body bytes it authenticates are unchanged.

### Impact Explanation
This breaks the tenant-identity binding the gem is relied on to enforce for webhook authenticity: an unprivileged actor (able to install the app on their own store, which is a normal unauthenticated onboarding flow) can produce webhook deliveries that a host application will process as if they originated from an arbitrary victim shop domain, since `request.shop` — the only tenant identifier surfaced by the gem — is attacker-controlled and outside the HMAC boundary. Any host logic that uses `WebhookMetadata#shop` to look up sessions, trigger per-tenant side effects, or route data by shop is exposed to cross-tenant event injection, matching the "cross-tenant access" impact category.

### Likelihood Explanation
High for any app that allows self-installation (nearly all public Shopify apps do): an attacker only needs to install the app on their own development store to obtain one valid `(raw_body, hmac)` pair for a topic of interest, then can replay it indefinitely with any spoofed `shop` header value, since the header is never part of the signed material and there's no nonce/timestamp binding in `Request` to prevent replay-with-header-substitution.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` header values in the signable string (or otherwise cryptographically bind them, e.g., by requiring the host application to independently verify `shop` against a known/expected value from its own session store) so that `HmacValidator.validate` fails if any of these attacker-visible headers are altered relative to what was actually signed by Shopify.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, triggering a legitimate webhook delivery, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H` (valid for secret `S` and body `B`).
2. Attacker captures the raw request `(headers, B)`.
3. Attacker POSTs to the app's public webhook endpoint with the same body `B` and the same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged shop header [6](#0-5) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` [7](#0-6) .
5. The registered handler executes with `WebhookMetadata#shop == "victim.myshopify.com"`, even though Shopify never sent this event for that shop — a cross-tenant, forged-identity event is accepted as authentic.
