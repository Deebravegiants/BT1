## Custody Analog Found: Multisig Timelock Bypass via Pre-Existing Pending Transactions

### Title
Newly-configured multisig timelock can be instantly bypassed by transactions created before the timelock existed - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
The custom `MultisigAccountTimeLock` feature added to `multisig_account.move` computes the timelock "elapsed" window from the **absolute creation time of the pending transaction** (`pending_transaction.creation_time_secs`), not from the time the timelock was actually configured. This mirrors the Zetachain bug class: a security-control update (the restricted-address list / here, the timelock policy) does not correctly bind to the state it is meant to gate, so already-existing state (a stale pending transaction) is evaluated as if the control had always been active.

### Finding Description
`can_execute_with_timelock` is the sole gate deciding whether a multisig transaction must wait for the timelock period before execution: [1](#0-0) 

```
inline fun can_execute_with_timelock(multisig_account: address, sequence_number: u64, num_approvals: u64): bool {
    if (exists<MultisigAccountTimeLock>(multisig_account)) {
        let multisig_account_resource = &MultisigAccountTimeLock[multisig_account];
        let timelock = multisig_account_resource.timelock_period;
        let override_threshold = multisig_account_resource.override_threshold;
        let pending_transaction = get_transaction(multisig_account, sequence_number);
        let elapsed = now_seconds() - pending_transaction.creation_time_secs;
        (override_threshold.is_some() && &num_approvals >= override_threshold.borrow()) || elapsed >= timelock
    } else {
        true
    }
}
```

The invariant this control is supposed to preserve: once a timelock is configured on a multisig account, every future-executed transaction must wait `timelock_period` seconds from the moment the timelock's protection actually applied, so that co-owners have a real window to detect and reject a malicious pending transaction.

The bug: `elapsed` is computed against `creation_time_secs`, which is set once, at `create_transaction`/`create_transaction_with_hash` time — **before** any timelock existed. If an owner (e.g., a compromised co-owner) creates a malicious transaction (draining funds from a resource-account-controlled treasury, rotating owners, or reassigning module/object ownership) while no timelock is configured, and the remaining owners subsequently add a timelock via `upsert_timelock` specifically to defend against it, the newly-added timelock provides **zero protection** for that pending transaction: `now_seconds() - creation_time_secs` can already exceed `timelock_period` the instant the timelock is added (or shortly after), since the creation timestamp predates the timelock's existence. The attacker only needs to gather the normal `num_signatures_required` approvals (which was already achievable pre-timelock) to execute immediately, defeating the entire purpose of the just-added safety control.

This is functionally identical to the seed bug: a security list/policy (`restrictedAddressBook` in Zetachain; the timelock gate here) is not correctly re-applied/re-bound to already-existing state (previously loaded addresses; a previously-created pending transaction) when the policy is updated, silently rendering the protection inert for that state.

Supporting evidence that this exact scenario is *not* covered/guarded against: all existing tests configure the timelock **before** creating the transaction, e.g.: [2](#0-1) 

None of the tests validate that a transaction created prior to `upsert_timelock` correctly inherits the new waiting period from the moment the timelock was set, rather than from its own (stale) creation time.

### Impact Explanation
This is a custody-grade, mainnet-relevant control-bypass:
- Multisig accounts are resource accounts that can hold APT, fungible-asset stores, object ownership/extend/transfer authority, and code-object upgrade authority.
- The timelock is the owners' primary emergency brake against a compromised/malicious co-owner (or already-obtained sufficient approvals) draining or reassigning custody of these assets.
- Because the timelock window is anchored to the transaction's original creation time instead of to the timelock's activation time, an attacker who front-runs the timelock's creation with a malicious pending transaction bypasses the entire protection, allowing unauthorized transfer/reassignment of multisig-held value with no delay, defeating the recovery/detection window the owners just enabled.

### Likelihood Explanation
Likelihood is high in the realistic scenario that motivates adding a timelock in the first place: owners typically add a timelock *in response to* a suspicious pending transaction or a suspected compromised co-owner, i.e., exactly when a malicious transaction is already pending. In that exact situation, this bug guarantees the newly added timelock cannot block the transaction it was meant to stop.

### Recommendation
Anchor the elapsed-time check to the effective start of the timelock's protection for a given transaction, not solely to the transaction's absolute creation time. For example, store `timelock_activated_at` in `MultisigAccountTimeLock` and use `elapsed = now_seconds() - max(pending_transaction.creation_time_secs, timelock_activated_at)` (or explicitly disallow lowering effective wait time for transactions predating timelock activation, requiring `timelock_activated_at + timelock_period` as the earliest execution time for any transaction created before the timelock existed).

### Proof of Concept
1. Multisig account with `num_signatures_required = 2`, 3 owners, **no timelock** configured.
2. Compromised/malicious owner creates transaction draining the account's assets; a second colluding/compromised owner approves it (2-of-3 met). Transaction is now executable immediately (no timelock exists yet).
3. Honest third owner notices the pending transaction and calls `upsert_timelock(multisig_signer, 3600, ...)` to impose a 1-hour delay, intending to buy time to reject it.
4. Because `pending_transaction.creation_time_secs` was set before step 3, and enough time has already elapsed since the transaction's original creation (e.g., it sat pending for over an hour before anyone noticed), `elapsed >= timelock` is already true the moment the timelock is added.
5. The attacker calls `validate_multisig_transaction`/executes the transaction; `can_execute_with_timelock` returns `true` immediately, and the funds/ownership transfer executes despite the freshly configured timelock — the safety control never actually delayed anything.

I could not directly view the `upsert_timelock` function body or the `MultisigTransaction`/`MultisigAccountTimeLock` struct field definitions (only inferred their fields/usage from `can_execute_with_timelock` and the test names) due to tool-call limits, so I cannot fully confirm whether `upsert_timelock` sets any additional safeguard (e.g., a minimum delay applied uniformly to all pending transactions) that might partially mitigate this. A Devin session with full file access should verify `upsert_timelock`'s implementation to confirm no such mitigation exists before treating this as fully confirmed.

    /// Return true if the transaction with given transaction id can be executed immediately, or it has to wait
    /// for the timelock to expire.
    inline fun can_execute_with_timelock(multisig_account: address, sequence_number: u64, num_approvals: u64): bool {
        if (exists<MultisigAccountTimeLock>(multisig_account)) {
            let multisig_account_resource = &MultisigAccountTimeLock[multisig_account];
            let timelock = multisig_account_resource.timelock_period;
            let override_threshold = multisig_account_resource.override_threshold;

            // Get the pending transaction to check if the timelock has expired
            // Assume that the transaction has already been checked to exist and is valid
            let pending_transaction = get_transaction(multisig_account, sequence_number);

            // Use subtraction to avoid overflow (now_seconds() >= creation_time_secs is always true)
            let elapsed = now_seconds() - pending_transaction.creation_time_secs;

            // If the number of approvals meets the override threshold, or the timelock has expired, allow execution
            (override_threshold.is_some() && &num_approvals >= override_threshold.borrow()) || elapsed >= timelock
        } else {
            true
        }
    }
