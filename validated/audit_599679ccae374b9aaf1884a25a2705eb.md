### Title
`compareAddresses` uses raw string equality for Zcash, missing TEX/transparent dual-encoding — self-send guard bypass - (File: packages/intents-sdk/src/lib/compareAddresses.ts)

### Summary
`compareAddresses` canonicalises addresses for EVM, hex-field, TON, Tron and Stellar chains before comparing, but for Zcash (and other UTXO/simple chains) it falls back to raw `a === b` string equality. Zcash defines two textual encodings of the exact same 20-byte transparent P2PKH hash — legacy base58check `t1…`/`t3…` addresses and ZIP-320 `tex1…` bech32m addresses — both of which pass `validateAddress`. Supplying the `tex1…` encoding of a token's `t1…` address defeats the `compareAddresses` check in `OmniBridge.validateWithdrawal`.

### Finding Description
The broken equality is: for two Zcash address strings `t` (token address, base58 `t1…`/`t3…` form as returned by `getAddress(destTokenOmniAddress)`) and `d` (attacker-supplied `destinationAddress`), if `t` and `d` decode to the same underlying transparent pubkey hash, `compareAddresses(t, d, chain)` must return `true`.

In `compareAddresses.ts`, Zcash is routed to the generic branch: [1](#0-0) 
which does only `a === b`, with no chain-specific canonicalisation (unlike the EVM/hex/TON/Tron/Stellar branches above it).

`validateAddress` for Zcash accepts three independent textual forms — legacy transparent (`t1`/`t3`, base58), TEX (`tex1…`, bech32m encoding of a 20-byte hash per ZIP-320), and Unified Addresses (`u1…`): [2](#0-1) 

ZIP-320 TEX addresses are, by design, an alternate bech32m encoding of the *same* 20-byte transparent P2PKH hash that a legacy `t1…` base58check address encodes. They are two different strings for the identical spendable account. Because `compareAddresses` never decodes either form for Zcash, `compareAddresses(t1Address, tex1Address, chain)` returns `false` even when they resolve to the same account.

In `OmniBridge.validateWithdrawal`, the destination token's address is compared to the user-supplied destination using exactly this function: [3](#0-2) 
If `destTokenAddress` is a `t1…`/`t3…` string and the attacker submits the TEX-encoding of the same hash as `destinationAddress`, `validateAddress` accepts it, `compareAddresses` returns `false`, and `DestinationAddressMatchesTokenAddressError` is never thrown — bypassing the self-send guard.

### Impact Explanation
This defeats a defense-in-depth check whose stated purpose is to block withdrawals whose destination is literally the token's own on-chain account. Note that Zcash is a UTXO chain, not a smart-contract chain: unlike an EVM ERC-20 contract address, a `t1…` transparent address is a normal spend-controlled account, not necessarily an unrecoverable sink. Whether this bypass results in permanent, unrecoverable loss (as opposed to funds landing at a spendable-but-wrong account) depends on what `destTokenOmniAddress` concretely represents for Zcash-routed assets inside `@omni-bridge/core`'s `getBridgedToken`, which is outside this repo and could not be verified from the available index. The demonstrably broken invariant — `compareAddresses` failing to recognise two encodings of the same Zcash account as equal — is confirmed at the code level regardless of that external detail.

### Likelihood Explanation
Preconditions: an OmniBridge-routed Zcash withdrawal whose token address on Zcash is expressed in `t1…`/`t3…` form; attacker (any unprivileged user) supplies the TEX (`tex1…`) re-encoding of that same hash as `destinationAddress`. Both forms independently pass `validateAddress`. No special privileges, relayer collusion, or contract admin action needed — a single call to `processWithdrawal`/`createWithdrawalIntents` with an attacker-chosen `destinationAddress` is sufficient. Repeatable on every call.

### Recommendation
In `compareAddresses.ts`, add a Zcash-specific canonicalisation branch that decodes both `t1`/`t3` base58check addresses and `tex1` bech32m addresses down to their common 20-byte transparent-hash payload (and rejects/handles Unified Addresses appropriately) before comparing, mirroring the pattern already used for Tron's base58/hex dual encoding.

import { compareAddresses } from "../lib/compareAddresses";
import { validateAddress } from "../lib/validateAddress";
import { Chains } from "../lib/caip2";

// t1Address and tex1Address encode the identical 20-byte transparent P2PKH hash
// (constructed per ZIP-320 / base58check spec).
const t1Address = "t1TokenTransparentAddressXXXXXXXXX"; // token's t1 address
const tex1Address = "tex1<bech32m-encoding-of-same-20-byte-hash>";

test("Zcash TEX/t1 dual encoding bypasses compareAddresses", () => {
  expect(validateAddress(t1Address, Chains.Zcash)).toBe(true);
  expect(validateAddress(tex1Address, Chains.Zcash)).toBe(true);

  // Both strings denote the SAME account, so this should be true but isn't:
  expect(compareAddresses(t1Address, tex1Address, Chains.Zcash)).toBe(false); // BUG: should be true
});

function validateZcashAddress(address: string) {
	// Transparent address validation
	if (address.startsWith("t1") || address.startsWith("t3")) {
		// t1 for P2PKH addresses, t3 for P2SH addresses
		return /^t[13][a-km-zA-HJ-NP-Z1-9]{33}$/.test(address);
	}

	// TEX address validation
	const expectedHrp = "tex";
	if (address.startsWith(`${expectedHrp}1`)) {
		try {
			const decoded = bech32m.decodeToBytes(address);
			if (decoded.prefix !== expectedHrp) {
				return false;
			}
			return decoded.bytes.length === 20;
		} catch {
			return false;
		}
	}

	// Unified address validation
	if (address.startsWith("u1")) {
		return validateZcashUnifiedAddress(address);
	}

	return false;
}
