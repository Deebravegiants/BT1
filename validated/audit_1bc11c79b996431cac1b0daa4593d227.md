The `findMatchingWithdrawal` logic in both `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` and `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts` matches withdrawal status responses **only by `assetId`** (via `near_token_id`), not by `destinationAddress` or `amount`. When a single NEAR transaction contains multiple withdrawals of the same asset, the code returns the *first* array match regardless of which specific withdrawal (destination/amount) it actually belongs to — an unprivileged equality break: "the withdrawal reported completed" is not provably "the withdrawal the caller actually requested."

### Title
Withdrawal status misattribution when multiple same-asset withdrawals exist in one transaction - (packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts, packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`findMatchingWithdrawal` matches POA Bridge withdrawal status entries solely by `assetId`/`near_token_id`, ignoring `destinationAddress` and `amount`. If a NEAR transaction batches multiple withdrawals of the same token (e.g., to two different destination addresses in one intent execution), `describeWithdrawal`/`waitForWithdrawalCompletion` will return the tx hash and status of an unrelated withdrawal of the same asset instead of the one actually requested by the caller.

### Finding Description
`findMatchingWithdrawal` in [1](#0-0)  only checks `nep141:${w.data.near_token_id} === criteria.assetId` and returns the first array match. The same limitation is documented and implemented identically in `PoaBridge.describeWithdrawal` at [2](#0-1) , which explicitly comments "Response list is unsorted, so we match by assetId instead of index" [3](#0-2) .

The docstring on `findMatchingWithdrawal` itself acknowledges: "multiple withdrawals of the same token in a single transaction are not supported" [4](#0-3) . This breaks the equality that "the tx hash/status returned for withdrawal N" equals "the on-chain outcome for withdrawal N specifically" — instead it silently returns the outcome for *any* withdrawal of the same asset in the batch, which could be a different destination address, amount, or even a still-pending/failed one being reported as another's success.

This is directly analogous to the M-14 pattern: an on-chain state (liquidation type/withdrawal outcome) is attributed based on a coarse, non-unique key (partyA/assetId) rather than the specific caller-supplied unit of work (per-liquidator contribution/per-withdrawal identity), so a status gets misassigned across otherwise-independent operations.

### Impact Explanation
If an integrator batches multiple same-asset withdrawals to different destination addresses in a single NEAR intent transaction (a supported use case per the SDK's `createWithdrawalCompletionPromises` batching API), `describeWithdrawal` for withdrawal index 1 could report the tx hash belonging to withdrawal index 0 (or vice versa) as "completed." An integrator relying on this status to credit/finalize a withdrawal could **credit the wrong withdrawal as settled while the actual one remains pending**, or report a transfer as completed with a `txHash` that corresponds to a different destination/amount — a status misreport that can cause an integrator to prematurely mark an unrelated recipient's transfer as done, or fail to detect that the intended withdrawal actually failed/reverted while a same-asset sibling succeeded.

### Likelihood Explanation
Requires the caller to batch two-or-more same-`assetId` withdrawals within one signed intent transaction and then use per-withdrawal `describeWithdrawal`/`waitForWithdrawalCompletion` polling to determine completion — a pattern explicitly supported by the SDK's public withdrawal-completion API (`createWithdrawalIdentifier` takes an `index` specifically to disambiguate multiple withdrawals in one tx). No malicious actor needed; it's a correctness bug reachable by any legitimate multi-withdrawal batch of the same token.

### Recommendation
Match withdrawals using a discriminating key beyond `assetId` — e.g., include `destinationAddress` and `amount` (and memo, if applicable) in `WithdrawalCriteria`, and where the POA API doesn't return enough info to disambiguate multiple same-token/same-destination withdrawals, sort candidates by amount as the docstring itself suggests, consuming matched entries so they aren't reused for a different index.

### Proof of Concept
1. Construct and submit a single intent transaction containing two `ft_withdraw` primitives for the same `assetId` (e.g., `nep141:btc.omft.near`) to two different destination addresses `A` and `B`.
2. Call `describeWithdrawal` for the withdrawal identifier at `index: 0` (intended for destination `A`).
3. The POA Bridge API returns an unsorted `withdrawals` array containing both entries; `findMatchingWithdrawal` returns `withdrawals.find(w => nep141:${w.data.near_token_id} === assetId)`, which is simply the **first** array element matching the asset — this may be the entry for destination `B`, not `A`.
4. The SDK reports `{ status: "completed", txHash: <B's tx hash> }` for the request intended for `A`, even though `A`'s withdrawal may still be pending or may have failed. [5](#0-4) , the repo's own test named "matches withdrawal by assetId, not by index" demonstrates this behavior is intentional current design, not merely a latent bug — but it still results in status misattribution for any batch containing more than one withdrawal of the same asset.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}
