### Title
Unescaped colon in `destinationMemo` allows XRP destination-tag injection via `createWithdrawMemo` - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge-utils.ts])

### Summary
`createWithdrawMemo` joins `"WITHDRAW_TO"`, the destination address, and the caller-supplied `xrpMemo` with `:` with no escaping or validation that `xrpMemo` (i.e. `destinationMemo`) is free of colons. Since `destinationMemo` is forwarded verbatim from the integrator/attacker with no format check anywhere in the withdrawal path, an attacker can inject extra `:`-delimited fields into the memo that the PoA relayer parses, breaking the equality between the tag the user intended and the tag encoded in the memo the relayer actually reads.

### Finding Description
The equality that must hold is: `intended_destination_tag(destinationMemo) == parsed_destination_tag(memo_after_split(":"))`. Tracing the code:

- `createWithdrawMemo` builds `memo = ["WITHDRAW_TO", normalizedAddress, xrpMemo].join(":")` with zero escaping. [1](#0-0) 
- `createWithdrawIntentPrimitive` passes `params.destinationMemo` straight through as `xrpMemo` into the memo. [2](#0-1) 
- `PoaBridge.createWithdrawalIntents` forwards `args.withdrawalParams.destinationMemo` unmodified into `createWithdrawIntentPrimitive`. [3](#0-2) 
- `PoaBridge.validateWithdrawal` validates the destination *address* format via `validateAddress`, checks min withdrawal amount, and — for XRPL — only checks whether `requireDestinationTag` is set and throws if `destinationMemo` is falsy; it never validates the **content/format** of `destinationMemo` (e.g., that it is purely numeric with no `:`). [4](#0-3) 

So an attacker/integrator-supplied `destinationMemo = "123:evil"` combined with a valid XRPL address produces `"WITHDRAW_TO:<addr>:123:evil"`, i.e. 4 colon-delimited fields instead of the expected 3. Nothing in this repo's reachable code path (`validateAddress`, `validateWithdrawal`, `createWithdrawMemo`) rejects or sanitizes this, so the divergence between the caller's intended single tag (`"123"`) and whatever the relayer's `:`-splitting parser extracts (which depends entirely on the relayer's own parsing logic, out of scope here) is real and unguarded at the SDK layer.

### Impact Explanation
This affects the `memo` field embedded in the `ft_withdraw` intent that gets signed and submitted to `intents.near`, which is subsequently used by the (out-of-repo) PoA relayer to determine the XRPL destination tag for payout. If the relayer's parser treats the extra segment as an unintended field or a corrupted/truncated tag, funds can be paid to the correct XRPL address but with a wrong or malformed destination tag, which for exchanges enforcing exact tag matching can strand funds irrecoverably — matching the Critical category ("funds delivered to a wrong address/chain/contract with no recovery" in the tag-matching sense). This is repeatable on every withdrawal call where the caller controls `destinationMemo`.

### Likelihood Explanation
Preconditions: any caller (ordinary user or integrator forwarding attacker-controlled strings, per the threat model) invoking the SDK's withdrawal path with `destinationMemo` containing a `:` character and a legitimate XRPL `destinationAddress`. No special privileges, race conditions, or contract-state dependencies are required — this is a pure input-validation gap reachable via any public withdrawal call (`createWithdrawIntentPrimitive` / `PoaBridge.createWithdrawalIntents`). The cost to the attacker is a single crafted string; the SDK's own validation (`validateWithdrawal`) does not check memo content, only address format and tag-presence, so the malformed memo passes through unmodified into the signed intent.

### Recommendation
In `createWithdrawMemo` (or earlier, in `validateWithdrawal`), reject/sanitize `destinationMemo`/`xrpMemo` values containing `:` (or any character with special meaning to the relayer's memo parser) before constructing the memo string, e.g. throw a validation error such as `InvalidDestinationMemoError` if `xrpMemo.includes(":")`, and additionally enforce that XRP destination tags are numeric (`/^\d+$/`) as required by XRPL's actual tag format.

### Proof of Concept
```ts
// packages/intents-sdk/src/bridges/poa-bridge/poa-bridge-utils.test.ts
import { describe, it, expect } from "vitest";
import { createWithdrawIntentPrimitive } from "./poa-bridge-utils";

describe("createWithdrawMemo colon injection", () => {
  it("emits an ambiguous memo when destinationMemo contains a colon", () => {
    const intent = createWithdrawIntentPrimitive({
      assetId: "nep141:xrp.omft.near", // XRPL asset
      destinationAddress: "rN7n7otQDd6FczFgLdSqtcsAUxDkw6fzRH", // valid XRPL classic address
      destinationMemo: "123:evil",
      amount: 1000n,
    });

    const fields = intent.memo.split(":");

    // Intended equality: caller wanted a single tag field "123"
    // Actual: memo contains 4 fields, not 3, so the tag is ambiguous
    expect(fields.length).toBeGreaterThan(3);
    expect(intent.memo).toBe(
      "WITHDRAW_TO:rN7n7otQDd6FczFgLdSqtcsAUxDkw6fzRH:123:evil",
    );
  });
});
```
This demonstrates that `destinationMemo = "123:evil"` produces a memo with more than the expected 3 `:`-delimited fields (`WITHDRAW_TO`, address, tag), proving the equality between the caller's intended single tag and the actually-encoded memo content is broken at the SDK layer, with no validation in `validateWithdrawal` or `createWithdrawMemo` preventing it.
