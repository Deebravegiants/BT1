The `ShopifyAPI::Webhooks::Request#to_signable_string` (which is what `HmacValidator` HMACs over) only covers `@raw_body`, while `shop` (the tenant identity used downstream by `WebhookMetadata` and app handlers) is read from an unauthenticated header (`shopify-shop-domain` / `x-shopify-shop-domain`) that is never included in the signed material.

### Title
Webhook Shop-Domain Header Not Covered by HMAC Allows Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body via `Utils::HmacValidator.validate(request)` [1](#0-0) . The `shop` value that is subsequently trusted and forwarded to the app's webhook handler as the tenant identifier is read straight from an HTTP header (`shopify-shop-domain`/`x-shopify-shop-domain`) that is never included in the HMAC-signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [2](#0-1) . The `shop` accessor, however, comes from a header that is completely outside that signable string: [3](#0-2) 

`HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against the `hmac` header [4](#0-3) , so the equality actually being enforced is `HMAC(body) == received_hmac`, not `HMAC(body, shop) == received_hmac`. The `shop` header is never bound into this equality.

`Registry.process` trusts the unauthenticated `request.shop` and forwards it directly into `WebhookMetadata`, which is what app-provided handlers use to attribute the webhook to a tenant: [5](#0-4) [6](#0-5) 

Since a merchant/attacker can legitimately install the app on their own shop and receive genuine Shopify webhooks (each with a valid `body` + `hmac-sha256` pair signed with the app's shared `api_secret_key`), they possess a valid `(body, hmac)` pair. Because the header carrying the tenant (`shop-domain`) is not part of the signed material, that same valid `(body, hmac)` pair can be replayed to the app's webhook endpoint with an arbitrary `shopify-shop-domain` header value (e.g., a victim shop's domain) and it will still pass `HmacValidator.validate`. The app's handler will then process/attribute this forged webhook as if it came from the victim shop.

### Impact Explanation
This breaks the tenant identity binding the whitelisting-analog bug class targets: the shop identity acted upon by the handler (`data.shop`) is not the shop that produced the HMAC-verified bytes. Any app that uses `data.shop` from `WebhookMetadata` to look up sessions, attribute state changes, or perform shop-scoped side effects (as the docs explicitly instruct: `perform_later(topic: data.topic, shop_domain: data.shop, ...)` [7](#0-6) ) can be tricked into cross-tenant data confusion/writes using only a legitimately obtained webhook from the attacker's own shop. This matches "cross-tenant access" impact.

### Likelihood Explanation
Any developer/merchant capable of installing the app on their own store (an ordinary, low-privilege action) can capture real webhook deliveries (valid body + HMAC) and replay them to the app's public webhook endpoint with a modified `shop-domain` header. No access token, `client_secret`, or privileged access is required — only the ability to receive one webhook for a shop they control and to make an HTTP request to the app's public webhook callback URL.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) in the HMAC-signed material, or independently verify that the `shop` header value corresponds to a shop with a legitimate, currently-registered installation/session before trusting it in `WebhookMetadata`. At minimum, `Request#to_signable_string` should not omit identity-bearing headers that are subsequently trusted by consumers of `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header value — both valid, since they were produced by real Shopify infrastructure using the app's shared secret.
2. Attacker sends a new POST request to the app's webhook endpoint with:
   - The exact same `raw_body` and `X-Shopify-Hmac-Sha256` header captured in step 1.
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (any target shop domain).
   - `X-Shopify-Topic` and `X-Shopify-Webhook-Id` set arbitrarily/reused.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because `to_signable_string` only hashes `raw_body`, which is unchanged [2](#0-1) .
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and performs shop-scoped processing believing it originated from `victim-shop.myshopify.com`, even though it did not.
