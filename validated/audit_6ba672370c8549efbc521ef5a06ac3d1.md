### Title
Governance updating an `IntentGatewayV2`/`ExtrinsicIntents` remote instance address permanently freezes escrow for orders already in flight - (File: `evm/src/apps/intentsv2/IntentsBase.sol`, `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`IntentsBase` stores the registered remote gateway address for each state machine in `_instances[keccak256(stateMachineId)]`, and both authentication of incoming settlement messages and outbound addressing of settlement messages are resolved *live* against this mapping rather than being pinned at `placeOrder` time. When governance re-registers a chain's gateway address via `RequestKind.NewDeployment` (e.g. because the remote gateway had to be redeployed at a new address), any order that was placed while the old address was registered, and whose `RedeemEscrow`/`RefundEscrow` settlement message is still in flight or not yet dispatched, can permanently fail authentication and never release its escrow — mirroring the reported Gitcoin bug where renaming a `Profile` silently invalidated the `acceptedRecipientId` anchor that `submitUpcomingMilestone()` depended on.

### Finding Description
`_instances` is a single mutable mapping keyed by `keccak256(stateMachineId)` that is used for two purposes that are supposed to stay in sync across chains: [1](#0-0) 

- Outbound addressing: `_instance(order.source)` is resolved and used to build the `to` field of the `RedeemEscrow`/`RefundEscrow` post request at fill/cancel time. [2](#0-1) 

- Inbound authentication: on the settling chain, the incoming settlement message is authenticated by checking that the request's `from` address equals the *currently registered* instance for `request.source` (the pattern is explicit in the Tron fork of the same contract family): [3](#0-2) 

The mapping is only ever overwritten, never versioned or made order-specific: [4](#0-3) 

`ExtrinsicIntents.onAccept` applies `NewDeployment` for any Hyperbridge-sourced request without any check for orders that reference the old address still being in flight: [5](#0-4) 

Concretely: a user places a cross-chain order on chain A destined for chain B (`order.source = A`, `order.destination = B`). A solver fills it on B and dispatches `RedeemEscrow` back to A, addressed to `instance(A)` as currently known on B. If, between order placement and the solver's fill/dispatch (or between dispatch and delivery), governance issues a `NewDeployment` on chain A that changes `_instances[keccak256(B)]` (e.g., B's gateway is migrated to a new proxy/address after a redeploy), then chain A's `authenticate()`/`_authenticate()` check on the incoming `RedeemEscrow` will compare the message's `request.from` (the *old* B gateway address that actually escrowed nothing — it dispatched from its real address) against the *new* registered instance for B, and reject it. Because the destination gateway's real on-chain address cannot retroactively become the new one, this specific message can never be authenticated again. The equivalent situation applies to `RefundEscrow` and to the GET-based cancellation path (`onGetResponse`) when the roles are reversed. This is architecturally identical to the reported bug: a mutable identity binding (`Profile -> anchor`, here `stateMachineId -> gateway address`) is updated by a legitimate, non-malicious administrative action, silently invalidating a reference (`acceptedRecipientId`, here the addressing/authentication key baked into an in-flight order) that a completion function (`submitUpcomingMilestone`, here `onAccept`'s `RedeemEscrow`/`RefundEscrow` handling) depends on, resulting in permanent inaccessibility of the associated funds.

### Impact Explanation
Escrowed input tokens for any order caught mid-flight during an instance-address migration become permanently unrecoverable: `_withdraw` is never reached because `_authenticate`/`authenticate` reverts on every retry, and the message can never be re-signed from the "new" address since the historical fill/cancel actually occurred against the old instance. This is a direct, unbacked freezing of user/solver funds in the intents escrow with no on-chain recovery path, which qualifies as Medium/High severity permanent freezing of funds.

### Likelihood Explanation
This requires a legitimate governance action (`NewDeployment`, used for chain onboarding or gateway re-registration/migration) to occur while orders referencing the previous instance are unsettled — a realistic, foreseeable operational event (chain redeployments, gateway migrations, correcting a misconfigured address) rather than an attack. No malicious actor is needed; ordinary, sanctioned use of the `NewDeployment` governance action triggers the freeze, so likelihood is non-trivial for the maintained system's normal lifecycle (chain migrations, redeployments) rather than a contrived edge case.

### Recommendation
Do not use a single live, overwritable `_instances` mapping for authenticating messages tied to already-created orders. Instead, either (a) snapshot the resolved instance address into the order/commitment at `placeOrder`/fill time and authenticate against that snapshot rather than the live mapping, or (b) keep a set of historically-valid instance addresses per chain (accepting messages from any previously-registered address for some grace/drain period) so in-flight orders can still settle after a `NewDeployment` update, similar to how `Registry` should preserve the old anchor→profile binding (or `RFPSimpleStrategy` should not solely rely on the anchor) across a rename.

### Proof of Concept
1. Governance registers `instanceB` for chain `B` via `NewDeployment` on chain `A`'s `ExtrinsicIntents`/`IntentGatewayV2` (`_addDeployment`, `IntentsBase.sol:581-584`).
2. User calls `placeOrder` on chain `A` with `order.source = A`, `order.destination = B`; tokens are escrowed.
3. A solver fills the order on chain `B` (deployed at `instanceB`), which dispatches a `RedeemEscrow` post request back to `A`, `from = instanceB` (`IntentsBase.sol:395-405`, `ExtrinsicIntents.sol` `_post`).
4. Before this message is delivered/authenticated on `A`, Hyperbridge governance dispatches `NewDeployment` for chain `B` pointing at `instanceB2` (e.g., a genuine re-deployment), updating `_instances[keccak256(B)] = instanceB2` on chain `A` (`IntentsBase.sol:581-584`).
5. The relayer delivers the pending `RedeemEscrow` message to `A`; `ExtrinsicIntents.onAccept` calls `_authenticate(incoming.request)`, which computes `instance(B) == instanceB2 != request.from (instanceB)` and reverts with `Unauthorized` (`ExtrinsicIntents.sol:330-336`, authentication pattern shown in `evm/tron/contracts/apps/IntentGatewayV2.sol:292-300`).
6. The message can never be re-delivered successfully (the solver's real dispatch address `instanceB` cannot change), so `_withdraw` never runs and the solver's already-provided output tokens plus the user's escrowed input tokens tied to that order are permanently stuck.

    /**
     * @dev Resolves the IntentGateway instance address for a given state machine.
     * Reverts with `UnknownInstance` if no remote deployment has been registered for that chain.
     * @param stateMachineId The raw state machine identifier bytes.
     * @return The gateway address for the given state machine.
     */
    function _instance(bytes calldata stateMachineId) internal view returns (address) {
        address gateway = _instances[keccak256(stateMachineId)];
        if (gateway == address(0)) revert UnknownInstance();
        return gateway;
    }
