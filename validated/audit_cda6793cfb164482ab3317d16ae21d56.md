## Analog Found: Webhook shop identity spoofing — HMAC validates the body, not the shop that the gem attributes it to

### Title
Webhook request shop/topic identity not covered by HMAC, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented to "verify the request did indeed come from Shopify" before invoking the app's handler, but the HMAC computed by `Utils::HmacValidator` only signs the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values that the gem hands to the developer's handler as trusted identity come straight from unauthenticated HTTP headers, with no binding to the HMAC at all.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` computes/compares the signature purely from that signable string against the app's shared `api_secret_key` [2](#0-1) . Meanwhile, `shop`, `topic`, and `webhook_id` are read directly from the `shopify-shop-domain`, `shopify-topic`, and `shopify-webhook-id` headers with no cryptographic binding to the body or the HMAC [3](#0-2) .

`Registry.process` performs exactly one check — `Utils::HmacValidator.validate(request)` — and then forwards the unverified `request.shop`, `request.topic`, and `request.webhook_id` straight into `WebhookMetadata` passed to the handler: [4](#0-3) .

The identity binding that should hold is: `shop asserted in WebhookMetadata.shop == shop that actually produced (body, hmac)`. Since the HMAC secret (`Context.api_secret_key`) is the *app's* single client secret — shared across every shop that installs the app — and is not shop-specific, any two genuine webhook deliveries for two different shops with the same body content produce the identical HMAC. An attacker who controls one shop with the app installed (trivial: install your own public app on a free/dev store) can capture their own genuine `(raw_body, hmac)` pair from Shopify, then replay it to the webhook endpoint with the `shopify-shop-domain` header rewritten to name a victim shop. `HmacValidator.validate` still succeeds (it never looks at the shop header), so `Registry.process` calls the handler with `WebhookMetadata.shop` set to the victim's domain.

The gem's own documentation instructs developers to trust `data.shop` as the shop identifier once `Registry.process` returns without raising, and shows using it directly to route/persist webhook data (`perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [5](#0-4) , and the "Process a Webhook" section explicitly states this call "will verify the request did indeed come from Shopify" [6](#0-5) . This is precisely the documented usage pattern, not a case of the host app deviating from documented behavior — the gem's guarantee ("verified request") is broader than what it actually checks (verified *body*, unverified *shop*).

### Impact Explanation
Cross-tenant access/data injection: an attacker with a legitimate but unprivileged installation of the target app on their own store can cause the host application to attribute attacker-supplied webhook data to an arbitrary victim shop domain, since `shop` is never bound to the HMAC. Depending on the host's handler logic (which the gem's own docs encourage to key off `data.shop`), this can corrupt or overwrite another merchant's records, trigger actions against the wrong tenant, or be used to probe/attack multi-tenant state keyed by shop domain — satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Requires only: (1) the attacker's own (or any) shop having the target app installed and subscribed to at least one webhook topic (a low bar — public apps are installable by any Shopify Partner/dev store), and (2) capturing one legitimate webhook body it received (its own data) and replaying it with a modified `X-Shopify-Shop-Domain` header value. No access to the app's `client_secret`, access tokens, or the victim's credentials is needed. This is realistic and requires no social engineering.

### Recommendation
`Registry.process` / `Webhooks::Request` should not treat the `shop-domain` header as an authenticated identity on its own. At minimum, the gem should document (and ideally enforce) that the resolved `shop` from a webhook must be cross-checked against a shop for which the app holds an active session/webhook registration before being trusted, or the shop domain should be corroborated via an independent authenticated channel (e.g., matching against `Registry`'s known registrations per shop) rather than being passed through as verified purely because the body-only HMAC matched.

### Proof of Concept
1. Attacker installs the target (public) app on `attacker-shop.myshopify.com` and registers for `orders/create`.
2. Shopify delivers a genuine webhook to the app's callback URL:
   - Headers: `X-Shopify-Hmac-Sha256: <valid-hmac-for-body>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`
   - Body: `{"id": 1, "note": "malicious payload"}` (fully attacker-controlled, since it is the attacker's own store's order).
3. Attacker captures `raw_body` and the `X-Shopify-Hmac-Sha256` value from this legitimate request.
4. Attacker replays the identical `raw_body` + `X-Shopify-Hmac-Sha256` to the same app endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only re-derives the HMAC from `raw_body` and the app's shared secret [7](#0-6) .
6. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: {"id": 1, "note": "malicious payload"}, ...)` [8](#0-7) , causing the host app to process attacker-controlled data as though it originated from the victim shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
