### Title
Webhook `shop` and `topic` identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing via HMAC/body replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw request body only (`to_signable_string` returns `@raw_body`), while the `shop` and `topic` values used by `ShopifyAPI::Webhooks::Registry.process` to dispatch the webhook are taken from unauthenticated HTTP headers that are never included in the signed material. This breaks the identity binding `HMAC(secret, bytes_verified) == bytes_used_for_dispatch`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read directly from HTTP headers, which are never part of the signable string: [2](#0-1) 

`Registry.process` validates the HMAC over the request (i.e. only over `raw_body`) and then, once validation succeeds, unconditionally trusts `request.shop` and `request.topic` from the (unsigned) headers to select the handler and build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` only confirms that `computed_signature(to_signable_string, secret) == received_signature`; it says nothing about which shop or topic the payload is "supposed" to belong to: [4](#0-3) 

The `WebhookMetadata` struct that is delivered to the host application's handler directly carries this unauthenticated `shop` field as the trusted tenant identifier: [5](#0-4) 

Because the same `client_secret` is shared by every merchant installation of a given app, any merchant who installs the app (including an attacker who installs their own test store) can legitimately trigger a webhook delivery and thereby obtain a valid `(raw_body, hmac)` pair signed with the app's `api_secret_key`. That pair is not bound to any particular shop or topic — only to the body bytes. The attacker can then replay that exact body and HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` and/or `X-Shopify-Topic` headers to any value they choose (e.g., a victim's shop domain, or a more sensitive topic such as `customers/redact`). `Registry.process` will accept it: the HMAC still validates, since it only ever checked the body, and the handler is invoked with `WebhookMetadata.shop` set to the attacker-chosen domain. This is the "field acted on but not covered by the HMAC" binding break called out in the review rules — the equality that should hold, `hmac_signed_bytes == identity_fields_used_for_dispatch`, does not hold here.

### Impact Explanation
Any application built on this gem that uses `WebhookMetadata#shop` or `#topic` from the `handle` callback as an authenticated tenant identifier (e.g., to update per-shop state, to trigger data/redaction workflows for `customers/redact` or `shop/redact`, or to key storage lookups) can be made to act on behalf of a shop the request did not actually originate from. This is a cross-tenant identity-binding bypass reachable by any unprivileged internet user who can install the app once (or otherwise obtain one valid signed body/HMAC pair) and can send arbitrary HTTP requests to the app's public webhook endpoint.

### Likelihood Explanation
The library performs no shop/topic binding of its own, so the exploitability entirely depends on: (1) an attacker being able to obtain one valid `(raw_body, hmac)` pair for the shared `api_secret_key` — trivially available to any merchant who installs the app, since that pair is per-event, not per-shop-secret; and (2) the webhook endpoint being reachable over the internet, which is a documented requirement for Shopify webhook delivery. No credential leakage or privileged access is required beyond normal app installation, which is available to any user of a public app.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) in the signed material used by `to_signable_string`, or independently verify that `request.shop` matches an expected/registered shop for the delivered `webhook_id`/subscription before dispatching to the handler. At minimum, document prominently that `WebhookMetadata#shop`/`#topic` are unauthenticated header values and must not be trusted as tenant identifiers without additional verification (e.g., cross-checking against the shop associated with the currently active session/webhook registration).

### Proof of Concept
1. Attacker installs the target app on their own (attacker-controlled) store, satisfying normal OAuth. Shopify delivers a legitimate webhook to the app's registered endpoint, e.g.:
   ```
   POST /webhooks
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid-hmac-of-body>
   X-Shopify-Shop-Domain: attacker-shop.myshopify.com
   Body: {"id": 1, ...}
   ```
   The attacker captures `Body` and `X-Shopify-Hmac-Sha256` — these are valid for the app's shared `client_secret`.
2. Attacker replays this exact `Body` and `X-Shopify-Hmac-Sha256` value directly to the app's public webhook endpoint, but sets:
   ```
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   X-Shopify-Topic: customers/redact
   ```
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers (only header *presence* is checked, not content) and `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only verifies the (unchanged) body bytes against the (unchanged) HMAC.
4. The host application's `WebhookHandler#handle` is invoked with `WebhookMetadata.new(topic: "customers/redact", shop: "victim-shop.myshopify.com", ...)`, causing the app to perform victim-shop-scoped actions (e.g., data deletion/redaction) triggered entirely by the attacker, without the victim shop ever sending this request.
