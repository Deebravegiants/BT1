Based on my research, I did not find a literal ERC20-vs-ERC1155 interface mismatch in this codebase — Hyperbridge's vault/token contracts (`HyperFungibleToken`, `WrappedHyperFungibleToken`, `IntentGatewayV2`) are all designed and documented around ERC-20 only, with no ERC-1155 dependency anywhere, so there's no "vault promises ERC1155, delivers ERC20" analog. However, I found a closely related bug class — code silently trusting a low-level token call's `success` flag without validating the token's actual boolean return, which is the same root cause category (code makes an incorrect assumption about a token's interface/behavior, causing accounting and funds handling to desync from reality) — in the Tron variant of `IntentGatewayV2`.

### Title
Unchecked ERC20 return value in `withdraw()`/`placeOrder()` lets non-standard tokens silently fail transfers while escrow accounting still marks the order settled - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`evm/tron/contracts/apps/IntentGatewayV2.sol` imports and declares `using SafeERC20 for IERC20` [1](#0-0) , but several of its token-transfer paths bypass `SafeERC20` and instead perform a raw low-level `.call` with `IERC20.transfer.selector`, only checking that the *call itself* succeeded — not that the token's returned boolean was `true`.

### Finding Description
In `withdraw()`, which is invoked when a `RedeemEscrow`/`RefundEscrow` ISMP message is delivered by a relayer, tokens are released like this:

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
...
_orders[body.commitment][token] -= amount;
``` [2](#0-1) 

Because `success` only reflects whether the external call reverted, an ERC-20 implementation that returns `false` on a failed transfer (rather than reverting) — a well-known non-standard-token pattern — will make `success == true` even though no tokens moved. The function proceeds to decrement `_orders[...]`, mark the order filled/refunded, and emit `EscrowReleased`/`EscrowRefunded`, permanently losing the escrow accounting for tokens that were never actually delivered. The same unchecked pattern appears in the `SweepDust` handling and predispatch/fee-token transfer paths of the same contract [3](#0-2) [4](#0-3) .

This directly contrasts with the primary EVM `IntentsBase.sol`/`IntentGatewayV2.sol`, which consistently use `SafeERC20.safeTransfer`/`safeTransferFrom` for the analogous escrow release logic [5](#0-4) , confirming the Tron variant's manual low-level call is an inconsistent, weaker re-implementation of the same "token interface" assumption that the original report flags (code assumes standard-conforming token semantics that some tokens do not honor).

### Impact Explanation
For any input/output token configured on Tron's `IntentGatewayV2` that returns `false` instead of reverting on a failed transfer (a common quirk among non-standard or malicious TRC20/ERC20-style tokens), the escrow accounting is decremented and the order is finalized as filled/refunded while the beneficiary never receives the tokens — a permanent loss/freezing of escrowed user or solver funds, reachable by any relayer delivering a normal `RedeemEscrow`/`RefundEscrow` message once such a token is in use.

### Likelihood Explanation
Triggering requires the gateway to be configured with (or a user to place an order using) a token whose `transfer` returns `false` on failure instead of reverting — not the default OpenZeppelin behavior but a documented common quirk in the wider token ecosystem. Any relayer or the solver escrow-release flow (`withdraw`, `SweepDust`) is otherwise unprivileged and directly reachable, so the only precondition is the token choice, not privileged access.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `evm/tron/contracts/apps/IntentGatewayV2.sol` (`withdraw`, `SweepDust`, transaction-fee release, and the predispatch sweep) with `SafeERC20.safeTransfer`/`safeTransferFrom`, which is already imported and used elsewhere in the same file, so the boolean return value (or absence of one) is properly validated before escrow state is mutated.

### Proof of Concept
1. Configure/register an input or output token on the Tron `IntentGatewayV2` whose `transfer()` returns `false` on failure instead of reverting (e.g., insufficient balance, blacklist, or paused state that the token signals via return value).
2. A user places an order using this token as input; a solver fills it, and Hyperbridge delivers the `RedeemEscrow` message.
3. `withdraw()` calls `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))`. The external call succeeds at the EVM level (`success == true`) but returns `false` because the token refuses the transfer.
4. `withdraw()` does not check the returned boolean, so it proceeds to decrement `_orders[commitment][token]` and emits `EscrowReleased`, marking the order finalized — the beneficiary receives nothing, and the escrowed funds are unrecoverable through the normal flow.
