### Title
Unsigned `shop-domain` header is trusted as the webhook's tenant identity - (`lib/shopify_api/webhooks/request.rb`)

### Finding Description
The claimed binding is: `Request#shop` == a value inside `Request#to_signable_string`. Tracing the code shows this is false.

`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` (i.e. the raw body) and `secure_compare`s it against the decoded `hmac-sha256` header: [2](#0-1) 

But `Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all read straight from HTTP headers, none of which are included in `@raw_body`: [3](#0-2) [4](#0-3) 

`Registry.process` validates only the body's HMAC, then hands `request.shop` (an unsigned header value) into `WebhookMetadata`, which the app's `WebhookHandler#handle` treats as the authenticated tenant identity: [5](#0-4) 

Exploit flow: an attacker registers their own webhook endpoint on their own development shop (permitted by the attacker model) and receives one legitimately-signed webhook — a valid `(raw_body, x-shopify-hmac-sha256)` pair signed with the app's real `api_secret_key`. The attacker then replays that exact `raw_body` and `x-shopify-hmac-sha256` value directly to the app's public webhook endpoint, but substitutes an arbitrary `x-shopify-shop-domain` (e.g. a victim merchant's domain) and/or a different `x-shopify-topic`/`x-shopify-webhook-id`. `HmacValidator.validate` recomputes HMAC over `raw_body` only, which is unchanged, so `secure_compare` succeeds. `Registry.process` then calls `handler.handle` with `WebhookMetadata#shop` set to the attacker-chosen victim domain, `topic`, `api_version`, and `webhook_id` all attacker-controlled, while the app believes the whole envelope was authenticated by Shopify.

The "Base64.decode64 permissiveness" and "webhook-id replay tracking" framing in the question is not the actual root cause — `Base64.decode64` only decodes the `hmac-sha256` header value itself and does not affect `shop-domain` comparison at all, and there is no digest collision needed. The real defect is structural: SIGNATURE COVERAGE is violated because `shop`, `topic`, `api_version`, and `webhook_id` are never part of the string passed to `HmacValidator`, so they can be forged independently of a valid signature as long as the attacker can supply *some* valid `(body, hmac)` pair (trivially obtainable from their own shop's webhooks).

No existing guard catches this: `HmacValidator.validate` only checks body/HMAC equality; `ShopValidator.sanitize!` isn't invoked anywhere in this path; there's no delivery-id or nonce tracking in this gem at all.

### Impact Explanation
`WebhookMetadata#shop` is exposed to the host app's handler as the trusted tenant identifier, and the app is expected to key all downstream logic (data writes, redaction, order sync, etc.) off it. Because this value is a raw unsigned header, any attacker who can obtain a single valid `(body, hmac)` pair from their own shop's webhook traffic can attribute arbitrary (topic, body-consistent) webhook events to any other victim shop domain of their choosing, repeatedly and against arbitrary victims, as long as the app's public webhook endpoint accepts direct HTTP POSTs. This is a cross-tenant authentication bypass: unauthenticated header data is treated as authenticated tenant identity, matching Critical - authentication bypass.

### Likelihood Explanation
Preconditions are modest: the attacker needs one legitimately signed webhook payload from any shop they control (freely obtainable per the attacker model) and the app's webhook endpoint must be reachable via direct HTTP POST (true for any standard Rack/Rails app using this gem's webhook processing, since nothing in this gem restricts caller IP or origin). No secrets, no signature forgery, and no timing attack are required — only header substitution on a replayed request. This makes the attack cheap, repeatable, and usable against any shop domain string the attacker chooses.

### Recommendation
Do not treat `shop-domain`, `topic`, `api_version`, or `webhook_id` headers as trusted/authenticated unless they are cryptographically bound to the signed payload. Either include these header values in the string handed to `HmacValidator` (mirroring Shopify's actual webhook signing scheme, which signs the raw body but expects the shop domain to be reconciled against the OAuth/install record for that endpoint), or require the host app to cross-check `request.shop` against a known, previously-registered shop for that specific installation/route before trusting it in `WebhookHandler#handle`. At minimum, document that `Request#shop` is unauthenticated and must not be relied upon for tenant isolation without independent verification.

### Proof of Concept
```ruby
# test/webhooks/request_shop_spoof_test.rb
require "test_helper"

class RequestShopSpoofTest < Test::Unit::TestCase
  def setup
    ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", ...)
    @raw_body = '{"id":1,"foo":"bar"}'
    @hmac = Base64.encode64(
      OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), "secret", @raw_body)
    ).strip
  end

  def test_same_signature_accepted_for_two_different_shops
    headers1 = {
      "x-shopify-topic" => "orders/create",
      "x-shopify-hmac-sha256" => @hmac,
      "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
      "x-shopify-api-version" => "2023-10",
      "x-shopify-webhook-id" => "dup-id-1",
    }
    headers2 = headers1.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")

    req1 = ShopifyAPI::Webhooks::Request.new(raw_body: @raw_body, headers: headers1)
    req2 = ShopifyAPI::Webhooks::Request.new(raw_body: @raw_body, headers: headers2)

    assert ShopifyAPI::Utils::HmacValidator.validate(req1)
    assert ShopifyAPI::Utils::HmacValidator.validate(req2)

    assert_equal "attacker-shop.myshopify.com", req1.shop
    assert_equal "victim-shop.myshopify.com", req2.shop
    # Same body + same valid HMAC, but two different "authenticated" shops.
    refute_equal req1.shop, req2.shop
  end
end
```
This demonstrates that identical, validly-signed webhook bodies produce two different `Request#shop` values that both pass `HmacValidator.validate`, confirming `shop` is never covered by the signature.
