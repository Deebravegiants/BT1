### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only signs the raw request body; the `shop` (and `topic`, `webhook_id`, `api_version`) values are read from HTTP headers that are never included in the HMAC computation. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then unconditionally trusts `request.shop` as the tenant identity passed to the app's handler. An unprivileged attacker who legitimately installs the app on their own store can capture one of their own valid, HMAC-signed webhook deliveries and replay it to the app's webhook endpoint after swapping only the shop-domain header, producing a request that still passes HMAC validation but is now attributed to an arbitrary victim shop.

### Finding Description
The identity binding that should hold is:

`shop domain trusted by the handler == shop domain that Shopify actually generated/signed the webhook for`

In `lib/shopify_api/webhooks/request.rb`: [1](#0-0) 
`shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, while: [2](#0-1) 
`to_signable_string` — the only material fed to `HmacValidator` — returns `@raw_body` alone. The shop header (and topic/webhook_id/api_version headers) are excluded from the signable string entirely.

`HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over `to_signable_string` with the app's `api_secret_key` and compares it to the `hmac` header: [3](#0-2) 
Since the signable string never contains the shop domain, the HMAC only proves "this body was signed with our secret" — it proves nothing about which shop the request claims to be from.

`Registry.process` then treats a passing HMAC check as sufficient to trust `request.shop` as the authenticated tenant identity and hands it straight to the registered handler: [4](#0-3) 

The gem's own documentation reinforces that developers are expected to rely on this "verification" as tenant-authenticated: "This will verify the request did indeed come from Shopify and then call the specified handler for that webhook," with `data.shop` presented as a trustworthy field consumers can key persistence/business logic on: [5](#0-4) [6](#0-5) 

Because `client_secret`/`api_secret_key` is a single app-level secret shared across every shop that installs the app (not a per-shop secret), any user can install the app on their own store — a normal, unprivileged action — and receive a real webhook delivery with a valid HMAC for a body they now possess. Nothing in the signed material binds that HMAC to their shop domain, so they can resend the identical `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the shop-domain header for a victim shop's domain. `HmacValidator.validate` still succeeds, and `Registry.process` calls the handler with the victim's shop as `data.shop` alongside the attacker's captured body/topic.

### Impact Explanation
This breaks the shop-identity binding that webhook consumers rely on for tenant isolation. Any application logic that uses `data.shop` from `WebhookMetadata` to look up per-tenant sessions/access tokens, write to per-shop records, or trigger shop-scoped side effects (exactly the pattern the gem's own documentation recommends, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) can be made to act on behalf of, or write attacker-controlled data into, a shop the attacker does not own. This is a cross-tenant access primitive achieved purely through this gem's webhook verification API, without needing `api_secret_key`, an access token, or a privileged account — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any app that accepts public installs (including free/trial installs) and that uses `Registry.process`/`WebhookMetadata#shop` as documented. The attacker only needs: (1) their own shop's real app installation to trigger a webhook of their choosing and capture its raw body + HMAC, and (2) the ability to POST to the target app's public webhook endpoint with a modified `Shopify-Shop-Domain` header — both require nothing beyond normal unauthenticated/unprivileged interaction with the merchant-facing app installation flow and the app's public webhook route.

### Recommendation
Bind the shop identity into the value that is actually verified:
- Include the shop domain (and ideally topic/webhook_id) inside the signed material used by `to_signable_string`, or
- Cross-check the shop-domain header against a shop identifier embedded in the JSON body (most Shopify webhook payloads include shop-scoped resource ids/`admin_graphql_api_id` fields tied to a known session), and reject the webhook if they don't match, or
- At minimum, document prominently that `request.shop`/`data.shop` is NOT authenticated by the HMAC and must be independently validated (e.g., against a known list of shops that have installed the app and match `webhook_id`/topic registrations) before being used for any tenant-scoped action.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` (a normal, unprivileged app install).
2. Attacker triggers an event (e.g., updates a product) that fires a subscribed webhook to the app's public webhook endpoint. Attacker captures the raw request: `raw_body`, and headers `shopify-hmac-sha256: H`, `shopify-shop-domain: attacker.myshopify.com`, `shopify-topic: products/update`.
3. Attacker replays this exact `raw_body` and `hmac` to the same webhook endpoint, but sets `shopify-shop-domain: victim.myshopify.com`.
4. Server builds `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` and calls `ShopifyAPI::Webhooks::Registry.process(request)`.
5. `Utils::HmacValidator.validate(request)` succeeds because `to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`) only checked `raw_body`, which is unchanged.
6. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the handler with `WebhookMetadata.new(topic: "products/update", shop: "victim.myshopify.com", body: <attacker's captured body>, ...)`, causing the app to process attacker-controlled data as if it originated from `victim.myshopify.com`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
