### Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` fields are trusted from unsigned HTTP headers while the HMAC covers only the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` accepts a webhook if `Utils::HmacValidator.validate(request)` succeeds, but the HMAC is computed only over `Request#to_signable_string`, which returns the raw body. The `shop`, `topic`, `webhook_id`, and `api_version` values are read straight from HTTP headers that are never included in the signed material, so the identity of "which shop/topic this payload belongs to" is unauthenticated even though the payload itself is verified.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop`, `topic`, `webhook_id`, and `api_version` are pulled from headers that are not part of that signable string: [2](#0-1) 

`HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest` over `verifiable_query.to_signable_string` (i.e., the raw body only) using `Context.api_secret_key`, which is the same secret for every shop that installs the app: [3](#0-2) 

`Registry.process` trusts the header-derived `request.shop`/`request.topic`/`request.webhook_id` once the HMAC check passes, and forwards them directly to the handler as the payload's identity: [4](#0-3) 

The equality that should hold is: `shop authenticated by HMAC == shop attributed to the payload by the handler`. Because the HMAC only binds the body bytes and never binds the `shop-domain` header, this equality does not hold — two different header values can accompany the exact same signed body and both pass validation.

### Impact Explanation
Since `Context.api_secret_key` is a single, app-wide secret (not per-shop), any legitimate webhook delivered to shop A carries a valid HMAC for its body regardless of which shop header accompanies it. A user in control of one tenant's webhook endpoint traffic (e.g., a merchant who installed the app, or anyone who can capture a delivered webhook to their own shop) can resend the same raw body with a different `x-shopify-shop-domain` (and/or `x-shopify-topic`/`x-shopify-webhook-id`) header. `HmacValidator.validate` will still return `true` because it only checks the body bytes, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the data belongs to a different shop/topic than the one it actually came from. This is a cross-tenant identity-attribution bypass: the app's webhook handler cannot distinguish "verified data for shop B" from "shop A's verified data relabeled as shop B," because the binding between the cryptographic guarantee and the tenant identity is broken at the header/body boundary.

### Likelihood Explanation
Exploitation only requires the ability to send an HTTP POST to the app's public webhook endpoint with a previously-seen (or self-generated, if the attacker's own shop is a legitimate app install) valid `(body, hmac)` pair and an attacker-chosen `shop-domain`/`topic`/`webhook_id` header — no access token, `client_secret`, or privileged account is required, satisfying the "unprivileged internet user" threat model. The main practical constraint is obtaining a valid `(body, hmac)` pair, which any shop that has installed the app can produce for itself and then relabel.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook_id`, `api_version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the body (e.g., compute the HMAC over a canonical concatenation of headers + body) so that the verified signature is tied to the specific shop/topic/webhook_id it was issued for, not just the raw bytes of the body.

### Proof of Concept
1. App has one shared `api_secret_key`. Shop A (attacker-controlled, legitimately installed) receives a real webhook:
   - Headers: `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid HMAC of raw_body>`
   - Body: `{"id":123, ...}`
2. Attacker resends the identical raw body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` builds a `Request` where `hmac` is unchanged and `shop` is now `"shop-b.myshopify.com"`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`@raw_body`, unchanged) — validation succeeds.
5. The handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "shop-b.myshopify.com", body: <shop A's data>, ...)`, causing the app to process shop A's data as if it belonged to shop B.
