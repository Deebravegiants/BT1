### Title
Attacker can steal any user's stake released through a stateless Emporium op via balance-diff `handleOut` - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction()` credits an ERC20 balance increase observed on the Emporium contract to whichever caller's `runAction` transaction produced it, with no binding to the address/proof that originally created the position. When a victim locks/stakes funds via a *stateless* op (`op.invokeWallet == false`, so the external protocol sees `msg.sender == Emporium`), any unprivileged attacker can later trigger the unlock/withdraw call themselves and have `handleOut` sweep the released tokens into their own UTXO.

### Finding Description
Broken equality: `principal_released_to == account that submitted the requestWithdraw() proof (the victim)`; the actual code enforces only `principal_released_to == whichever caller's runAction observes the balance increase on Emporium`.

`EmporiumUpgradeable.runAction` executes a stack of `EmporiumOperation`s. For each op, if `op.invokeWallet && stack.signerAddress != address(0)`, the call is routed through the caller's personal `HinkalWallet` contract (`IHinkalWallet(stack.signerAddress).callHinkalWallet(...)`), so `msg.sender` at the external protocol is the user's own dedicated wallet address [1](#0-0) . Otherwise (Case 2, "Stateless Interaction"), the call is made directly as `op.endpoint.call{value: op.value}(op.callData)`, meaning `msg.sender` at the external protocol is the shared `EmporiumUpgradeable` contract itself [2](#0-1) .

After executing the ops, the function computes `balanceChange = balancesAfter[i] - balancesBefore[i]` (adjusted for deposits via `deltaAmountChanges`) for each token, and unconditionally calls `handleOut`, which transfers the entire positive `balanceChange` to `msg.sender` (the Hinkal core contract, on behalf of whoever submitted this particular proof/tx) and mints a UTXO tied to that caller's `stealthAddressStructure` [3](#0-2) .

Exploit flow:
1. Victim stakes into a locked-staking protocol via a stateless Emporium op (`invokeWallet=false`), so the staking position (and any pending `requestWithdraw()` cooldown state) is registered against Emporium's own address, not the victim's identity.
2. Victim calls `requestWithdraw()` through a stateless op — this changes no ERC20 balance (`balanceChange == 0`), so no UTXO is produced and nothing prevents anyone else from acting next.
3. After the cooldown elapses, ATTACKER (an unrelated unprivileged user) submits their own Hinkal transaction whose `CircomData.externalActionData` targets Emporium with a stateless op calling `withdraw()` on the same staking contract, with `erc20TokenAddresses` including the underlying token.
4. The staking contract releases the victim's principal to `msg.sender`, which is Emporium (since Emporium was the address that called `requestWithdraw()`/is the registered staker).
5. `runAction` observes `balancesAfter[i] - balancesBefore[i] > 0` for that token and `handleOut` sends the entire amount to the attacker's `msg.sender`/proof, minting a UTXO for the attacker.

No existing guard prevents this: `onlyAllowedRecipient` only checks that `msg.sender` (Hinkal core) is an allowed caller of `runAction`, not who "owns" the position [4](#0-3) ; `verifyWallet`/`usedMessages` only dedupes `emporiumMessage` replay and validates EIP-712 signatures for stateful (`invokeWallet`) ops, it does nothing for stateless ops where `stack.signerAddress == address(0)` [5](#0-4) ; the circuit-level checks (`inTotal+amountChanges===outTotal`, nullifier/root checks) only constrain the attacker's own UTXO accounting, not who is entitled to the raw ERC20 balance increase sitting on the shared Emporium contract. Since Emporium acts as a single, shared on-chain identity for all stateless interactions, any externally-visible unlock event on that identity is fungible and un-attributable to a specific victim once it becomes a plain ERC20 balance on Emporium.

### Impact Explanation
Direct theft of a victim's locked/staked principal by an unrelated unprivileged attacker, matching the Critical category ("direct theft of shielded or in-flight user funds"). This is repeatable against any protocol integration where Emporium is used in stateless mode to hold a persistent, cooldown-gated position (staking, vesting claims, timelocked withdrawals, etc.) — any attacker can front-run/race the second-step call after the victim's first-step call and after the cooldown window opens.

### Likelihood Explanation
Requires: (1) an external protocol with a multi-step lock/cooldown/withdraw pattern reachable via Emporium ops, (2) the victim (or the wallet-UX flow) using the stateless (`invokeWallet=false`) op path rather than routing the call through their personal `HinkalWallet`, and (3) the attacker monitoring on-chain `requestWithdraw()`-type calls attributable to Emporium and waiting out the cooldown. All of this is achievable by any EOA with no privileged role — the attacker only needs to submit a normal Hinkal external-action transaction with `CircomData` naming the same `endpoint`/`callData` and token. Likelihood is architecture-dependent (it hinges on a real target protocol using an address-bound cooldown mechanism and users/integrators choosing the stateless op path for it), but nothing in the reviewed contracts prevents it once those conditions hold.

### Recommendation
For any operation that creates persistent, address-bound state at an external protocol (locks, stakes, cooldown withdrawals), disallow the stateless path or require `invokeWallet=true` with a per-user `HinkalWallet` so the external position is bound to the user's own wallet address rather than the shared Emporium contract. Alternatively, bind the second-step call to a stored record (per victim's proof/commitment) created during the first stateless call, and only release the corresponding balance increase to a proof that references that same record/nullifier.

### Proof of Concept
Foundry fork test plan:
1. Deploy a `MockLockedStaking` contract with `stake(uint256)`, `requestWithdraw()` (records `block.timestamp` cooldown per `msg.sender`), and `withdraw()` (requires cooldown elapsed, transfers `principal` to `msg.sender`).
2. Deploy `EmporiumUpgradeable`, register it as allowed recipient in Hinkal core, whitelist `MockLockedStaking` as an allowed `endpoint`.
3. Victim: submit a Hinkal external-action tx with a stateless `EmporiumOperation{endpoint: staking, invokeWallet:false, callData: stake(amount)}`, then a second tx with stateless op `requestWithdraw()`. Assert `balanceChange == 0` and no UTXO minted to victim for this call.
4. Warp time past cooldown.
5. Attacker (different EOA, own deposit/proof, own `stealthAddressStructure`): submit a Hinkal external-action tx with stateless op `withdraw()` on the same staking contract, `erc20TokenAddresses` = [stakingToken].
6. Assert: `MockLockedStaking` balance moves from staking contract to Emporium (`balanceChange == victimPrincipal`), `handleOut` transfers `victimPrincipal` to attacker's UTXO (assert attacker's shielded balance increases by `victimPrincipal`, and victim's shielded balance is unaffected/zero for that position) — i.e., assert `principal_released_to == attacker`, not `victim`.

    function handleOut(
        int256 balanceChange,
        CircomData calldata circomData,
        uint256 i
    ) internal returns (UTXO memory outUtxo) {
        // total change can be less than zero if there was some balance before the call -> that's why we have <=
        if (balanceChange <= 0) {
            return outUtxo;
        }

        transferERC20TokenOrETH(
            circomData.erc20TokenAddresses[i],
            msg.sender,
            uint256(balanceChange)
        );

        outUtxo = UTXO(
            uint256(balanceChange),
            circomData.erc20TokenAddresses[i],
            circomData.stealthAddressStructure,
            circomData.timeStamp
        );
    }
