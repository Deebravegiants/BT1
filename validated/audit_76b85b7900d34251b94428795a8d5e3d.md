### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing shop-spoofing on an otherwise validly-signed webhook - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as verified once `Utils::HmacValidator.validate` succeeds, and then passes `request.shop` (parsed from the `x-shopify-shop-domain`/`shopify-shop-domain` header) straight to the handler as the trusted tenant identifier. However the HMAC is computed only over the raw body, never over the shop-domain header, so the "verified" and "trusted" scopes diverge: the byte range that is cryptographically checked is not the same as the field that identifies which merchant/tenant the event belongs to.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `shop` is read from an unauthenticated header with no cryptographic binding to the body or to the HMAC at all: [2](#0-1) 

`Utils::HmacValidator.validate_signature` computes the signature only from `verifiable_query.to_signable_string` (i.e., the raw body) and compares it with the value in the `hmac-sha256` header: [3](#0-2) 

`Registry.process` uses this single HMAC check as the sole authenticity gate for the whole request, and then forwards the *unverified* `shop` header value to the handler: [4](#0-3) 

The identity binding that should hold is:
`hmac == HMAC(secret, raw_body ∥ shop)` (or the shop otherwise cryptographically bound to the signed payload)

but what is actually checked is:
`hmac == HMAC(secret, raw_body)` while `shop` is taken verbatim from a header that plays no part in that computation.

Because two different HTTP headers (`hmac-sha256` and `shop-domain`) are independently attacker-controllable in the request that reaches this gem's `Request.new`, and only one of them is bound by the signature, a request whose body+hmac pair is a valid, previously-observed Shopify signature (e.g., replayed from a webhook the attacker's own shop legitimately received) can be resubmitted with an arbitrary `shop-domain` header value. `HmacValidator.validate` still returns `true` because it never looks at the shop header, and `Registry.process` calls the handler with `WebhookMetadata#shop` set to the attacker-chosen shop while the `body`/`topic` are from the attacker's own legitimately-received webhook.

The gem's own documentation reinforces that host apps are meant to rely on this check as full authentication of the request ("This will verify the request did indeed come from Shopify") and hands `data.shop` to the handler as an already-verified per-tenant identifier, so this is not merely a host-application misuse of an undocumented API — the gem's documented contract implies `shop` is safe to use for tenant attribution once `process` succeeds.

### Impact Explanation
This breaks a tenant/authentication boundary: a party that operates their own installed shop (an "unprivileged" caller relative to other merchants, not requiring `api_secret_key` or any merchant's access token) can cause a multi-tenant host application to attribute a webhook payload/body to a different shop than the one Shopify actually sent it for, since `data.shop` is trusted for tenant routing/dispatch by design (per `docs/usage/webhooks.md`). Depending on how the host app keys per-tenant jobs/state off `data.shop` (exactly as shown in the gem's own documented example, `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), this enables cross-tenant data injection/confusion. This aligns with the High severity "cross-tenant access" category.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one validly-signed webhook body+HMAC pair for their own installed shop (trivial to obtain, since any shop owner receives their own shop's Shopify webhooks) and to control the HTTP headers of the request delivered to the app's webhook endpoint, which is standard for any endpoint reachable over HTTP. No secret key, access token, or privileged credential is needed to perform the header substitution itself. Likelihood is moderate-to-high wherever a host app uses `data.shop` for tenant-sensitive decisions, which is the intended usage pattern shown in this gem's docs.

### Recommendation
Bind the shop identifier into the value that is cryptographically verified, e.g. include the `shop-domain` header (and ideally `topic`/`webhook-id`) in the signable string used by `HmacValidator`, or independently validate that the shop-domain header matches a shop already known/authorized by the app (e.g., cross-check against the shop stored for the session that most recently confirmed OAuth for that shop) before trusting `WebhookMetadata#shop`. At minimum, update `docs/usage/webhooks.md` to explicitly warn that `data.shop` is not covered by the HMAC and must be revalidated by the host app against its own list of installed shops before being used for any tenant-keyed action.

### Proof of Concept
1. Shop A (attacker-controlled, legitimately installed app) receives a real Shopify webhook: body `B`, header `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: shopA.myshopify.com`. This is a legitimate signature Shopify computed over `B` only, per `to_signable_string`.
2. Attacker resends the exact same body `B` and `hmac-sha256: H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: shopB.myshopify.com` (any other shop the app also serves).
3. `ShopifyAPI::Webhooks::Request.new` parses the forged shop header without complaint.
4. `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` and compares to `H` — it matches, since the shop header was never part of the signed material (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
5. `Registry.process` calls the host app's handler with `WebhookMetadata.new(... shop: "shopB.myshopify.com" ...)`, even though the payload actually originated for `shopA` (`lib/shopify_api/webhooks/registry.rb:198-199`).
6. Any host logic that dispatches/attributes work per `data.shop` (as documented in `docs/usage/webhooks.md:26`) now processes shop A's webhook body under shop B's identity.
