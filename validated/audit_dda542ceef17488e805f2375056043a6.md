Found a concrete analog: the `convert_to_balance` / `convert_to_erc20` decimal-conversion helpers in `pallet-hyper-fungible-token`.

### Title
Truncating decimal-downscale in `convert_to_balance` under-credits inbound HFT transfers, permanently burning dust on every cross-chain receive - ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
`convert_to_balance`, used to convert an inbound ERC20 `U256` amount (18-decimal, EVM side) into the local substrate balance when a `HyperFungibleToken`/`WrappedHyperFungibleToken` message is received, performs a plain integer division that always truncates toward zero, discarding the fractional remainder instead of rounding in the recipient's favor.

### Finding Description
`convert_to_balance` divides the incoming ERC20-precision `U256` value by `10^(erc_decimals - local_decimals)` and parses the quotient into the local balance type: [1](#0-0) 

This is the destination-side counterpart of `convert_to_erc20`, which scales the local balance *up* to ERC20 precision when sending, an operation that is always exact and loses nothing: [2](#0-1) 

The asymmetry is the same shape as the Mellow `ratiosX96Value` bug: one side of a value-transfer computation (the credit given to the counterparty) is computed with a flooring division instead of a ceiling division, so the party receiving value is always paid `floor(x)` rather than `x`. In the Mellow case this let withdrawing users take slightly more than their share from the vault; here it does the opposite in terms of location but the same in effect — inbound mint/unlock amounts to the recipient are silently rounded down, and the discarded remainder is neither minted, refunded, nor tracked anywhere. Every single cross-chain receive through this pallet (mint on `native: false` assets, or unlock/transfer on `native: true` assets) loses `erc20_amount mod 10^(erc_decimals - local_decimals)` local-balance units.

Because `T::Decimals`/`Precisions` are governance-configured per remote chain, and EVM-side amounts are always 18-decimal while many local Substrate assets use lower precision (e.g. 6 or 10 decimals), the divisor `10^(erc_decimals - local_decimals)` is routinely large (up to `10^12` or more), making the truncated remainder non-negligible in relative terms for small transfers and guaranteed on essentially every transfer whose 18-decimal amount isn't an exact multiple of the scale factor.

### Impact Explanation
This is a real, permanent, protocol-wide fund loss (a freezing/burning of value) rather than a benign rounding epsilon: value that was locked/burned on the source chain is never fully re-minted/unlocked on the destination, and there is no sweep or dust-collection mechanism analogous to the `DustCollected` events seen in `IntentGatewayV2`/`ExtrinsicIntents`. Over the lifetime of the bridge this compounds into unbacked-supply drift between the two sides of every asset pair that has decimal mismatch, and it disadvantages every ordinary bridging user (not an attacker-controlled edge case), satisfying "concrete... permanent freezing of funds" for a reachable, unprivileged path: any user calling `send` on the source chain and having the destination pallet apply `convert_to_balance` to credit them.

### Likelihood Explanation
High likelihood of occurring on essentially every transfer: it requires no attacker action, only that `erc_decimals != local_decimals` (the common case for e.g. 18-decimal EVM ERC20 vs 6/10/12-decimal Substrate assets) and that the transferred amount is not a coincidentally exact multiple of the scale factor. This is the default, unprivileged, single-transaction path (`send` → ISMP dispatch → `onAccept`/receive handler applying `convert_to_balance`), squarely within the allowed "token bridger mint/burn" scope.

### Recommendation
Round the destination credit up (ceiling division) rather than down, mirroring the fix applied to the Mellow `ratiosX96Value` issue and consistent with how `IntentGatewayV2`/`ExtrinsicIntents` already round in the *protocol's* favor for fee/dust calculations elsewhere in this codebase:
```rust
pub fn convert_to_balance<B: core::str::FromStr>(
    value: U256,
    erc_decimals: u8,
    local_decimals: u8,
) -> Result<B, B::Err> {
    let divisor = U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32));
    let rounded_up = (value + divisor - U256::from(1u8)) / divisor;
    rounded_up.to_string().parse::<B>()
}
```
Alternatively, if under-crediting the recipient (rather than over-crediting) is the intentionally safe direction from the protocol's perspective, at minimum the truncated remainder must be tracked and swept (e.g. emitted as an event and accumulated per-asset) rather than silently discarded, so it is not permanently and unrecoverably lost.

### Proof of Concept
1. Governance registers an asset with `erc_decimals = 18` (standard EVM precision) and `local_decimals = 6` (e.g. a USDC-like Substrate asset) via `create_erc6160_asset`/`update_asset_precision`.
2. A user on the EVM side bridges an amount whose 18-decimal representation is `1_000_000_000_000_999_999` (i.e., `1e6 + 0.000000999999` in 6-decimal terms).
3. On receipt, the pallet computes `convert_to_balance(1_000_000_000_000_999_999, 18, 6)` = `1_000_000_000_000_999_999 / 10^12` = `1_000_000` (floor), discarding `999_999` raw ERC20-precision units (i.e., `0.000000999999` local-decimal units) with no event, no credit, and no path to recover it.
4. Repeated over the lifetime of the bridge across many such transfers, this systematically under-mints/under-unlocks value relative to what was locked/burned on the source chain, with the lost amount permanently unrecoverable by any party. [3](#0-2)

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
