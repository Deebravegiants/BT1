## Title
Tron `IntentGatewayV2.placeOrder` mis-accounts fee-on-transfer token deposits into escrow, causing insolvent/locked escrow balances - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` pulls ERC20 order inputs with a raw `safeTransferFrom` and then credits the escrow mapping `_orders[commitment][token]` with the *nominal* (fee-adjusted-only-by-protocol-fee) amount instead of the amount the contract actually received. For fee-on-transfer tokens, this causes the recorded escrow to exceed the real token balance held by the contract, exactly the bug class described in the referenced `TimeLockPool` report.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, the non-predispatch branch of `placeOrder` does: [1](#0-0) 

```solidity
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
...
_orders[commitment][token] += reducedInputs[i].amount;
```
`reducedInputs[i].amount` is derived purely from `order.inputs[i].amount` minus an optional protocol fee percentage — it is never adjusted for what the contract actually received from the `transferFrom` call. This is in stark contrast to the mainline EVM `IntentGatewayV2.sol` (`evm/src/apps/IntentGatewayV2.sol`), which explicitly measures actual received tokens: [2](#0-1) 

The mainline contract even has dedicated regression tests validating this behavior for fee-on-transfer tokens (`testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`, `testPlaceOrder_FeeOnTransferToken_WithProtocolFee`), confirming the project is aware of and defends against this exact bug class on other deployments: [3](#0-2) 

The predispatch branch of the Tron contract has the same flaw — it only validates `dispatcher` balance against the intended `requiredAmount` and still credits escrow with `reducedInputs[i].amount` rather than any measured delta: [4](#0-3) 

Later, when the order is filled/cancelled/refunded cross-chain, `withdraw()` transfers out exactly the escrowed nominal `amount` for each token: [5](#0-4) 

Because escrow bookkeeping was inflated at deposit time relative to the tokens actually custodied, the contract can end up promising more of a fee-on-transfer token than it holds.

### Impact Explanation
When a fee-on-transfer (or deflationary/rebasing-with-fee) token is used as an order input on the Tron `IntentGatewayV2`, the contract records an escrow entry larger than its real token balance. Since escrow accounting is shared pool-style bookkeeping (multiple orders' tokens sit in the same contract balance), this creates insolvency: some later order's withdrawal/refund for that token will either revert (temporarily freezing funds until new deposits backfill the shortfall) or, because `withdraw()` only checks the low-level `call` success and not the ERC20 return value, a token that returns `false` on insufficient balance instead of reverting would let `_filled`/`_orders` state update as if the transfer succeeded while the beneficiary receives nothing — a real loss of funds. This directly matches the "concrete theft or permanent freezing of funds" bar for the escrow token-bridge/intents path.

### Likelihood Explanation
Reachable from a single unprivileged `placeOrder` transaction supplying any fee-on-transfer ERC20 as an input token — no special privileges required. Likelihood depends on the operator whitelisting or users choosing such tokens as inputs, which the contract does not prevent.

### Recommendation
Mirror the fix already present in the mainline EVM `IntentGatewayV2.sol`: measure the contract's (or dispatcher's) token balance before and after each `safeTransferFrom`/sweep and use the actual delta — not the caller-supplied `order.inputs[i].amount` — both for the amount stored in `_orders[commitment][token]` and for the amount hashed into the commitment. Additionally, replace the raw `token.call(...transfer...)` success-only checks in `withdraw()` with `SafeERC20.safeTransfer`, which is already imported (`using SafeERC20 for IERC20;`) but unused for these transfers.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` with `depositToken` set to a 1% fee-on-transfer ERC20 (as modeled by `FeeOnTransferToken` in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`).
2. User A calls `placeOrder` with `inputs[0].amount = 1000e18`. The contract only receives `990e18` tokens, but `_orders[commitment][token]` is credited with (approximately) `1000e18` (minus any protocol fee, but not the transfer-fee).
3. User B places a similar order; contract again receives less than credited.
4. When redemption/refund messages arrive via `onAccept` → `withdraw()` for these commitments, cumulative escrowed amounts exceed the actual token balance held by the contract, causing a later `withdraw()` call to revert (funds frozen) or, if the token silently returns `false`, to record a beneficiary as paid without actually transferring tokens (fund loss).

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
