### Title
Webhook `shop-domain` (and `topic`, `webhook-id`) header is trusted by `Registry.process` but not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook by checking only that the HMAC over the raw request body is valid, then unconditionally trusts the `shop-domain` header taken from `Request#shop` to identify the tenant for the handler. Because the HMAC signature covers only `@raw_body` and not the `shop`, `topic`, or `webhook-id` header values, any request bearing a body/HMAC pair that is valid for *some* shop can have its `shop-domain` header rewritten to a different tenant, and `Registry.process` will still accept it and route the (attacker-influenced) body to the handler under the spoofed shop identity.

### Finding Description
`Webhooks::Request` exposes `shop`, `topic`, and `webhook_id` purely from HTTP headers, with no cryptographic binding to those values: [1](#0-0) 

`to_signable_string` — the data that is actually HMAC-verified — is defined as just the raw body:
```ruby
def to_signable_string
  @raw_body
end
``` [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` and, on success, immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`) to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` only checks `verifiable_query.to_signable_string` (i.e., the body) against the HMAC using the app's `api_secret_key`: [4](#0-3) 

The identity binding that should hold is: `hmac == HMAC(secret, body || shop || topic || webhook_id)`. Instead, this gem only enforces `hmac == HMAC(secret, body)`, and the `shop` used by `Registry.process` (and passed on to the merchant/tenant-routing logic of the host app) is disjoint from what the signature actually authenticates.

### Impact Explanation
This breaks the shop/tenant identity binding for webhook delivery. An app that hosts multiple merchants (a very common integration pattern for this gem, since `WebhookMetadata.shop` is the field host apps use to select the tenant record to update) can be attacked as follows: any party capable of submitting a POST to the app's webhook endpoint with a body and HMAC that are valid for *their own* shop (which is trivial to obtain — every legitimate webhook delivery to that same endpoint is such a pair) can replay that exact body/HMAC while substituting the `shop-domain` header for a victim shop. `Registry.process` will pass HMAC validation (validation is body-only) and hand the handler a `WebhookMetadata` claiming the payload originated from the victim shop. If the host app trusts `WebhookMetadata.shop` to select/update per-tenant data (the intended and documented usage), this enables cross-tenant data corruption/injection using another merchant's shop identity — satisfying the "cross-tenant access" criteria, since the binding between the authenticated bytes (body) and the acted-upon identity field (shop) is missing.

### Likelihood Explanation
Likelihood is bounded by the fact that the attacker needs at least one genuine valid body+HMAC pair, which is straightforward to obtain: they can register their own shop/app instance, trigger a real webhook to their own endpoint (any topic they can trigger, e.g. `orders/create` with attacker-controlled order content since Shopify does not scope the signature to a specific merchant), capture the raw body and its HMAC, and then submit that exact byte-for-byte body/HMAC to the app's webhook endpoint again while manipulating the `shop-domain` (and/or `topic`/`webhook-id`) header value, since none of those headers factor into the signature. No access to the app's `client_secret` or another merchant's access token is required — only network access to the webhook receiver route.

### Recommendation
Bind the identity fields used by the handler to the HMAC verification. Concretely, change `to_signable_string` (or the validation call site) to include `shop`, `topic`, and `webhook_id` alongside the raw body, or otherwise require that `Registry.process` independently authenticate the shop identity (e.g., via a per-shop secret or session lookup) rather than trusting an unauthenticated header value that isn't covered by the signature.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and triggers a webhook delivery for a topic the app subscribes to, capturing the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header value `H` (valid because `H = HMAC(secret, B)` per Shopify's real delivery).
2. Attacker resends a POST to the app's webhook endpoint with the same body `B` and same `H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B) == H` — this succeeds because `B` and `H` are unchanged. [5](#0-4) 
4. `Registry.process` builds `WebhookMetadata` using `request.shop`, which now returns `"victim.myshopify.com"`, and calls the app's handler with that (spoofed) tenant identity and the attacker-supplied body content. [6](#0-5) 
5. Any host-app logic that trusts `WebhookMetadata.shop` for tenant routing (the gem's documented usage pattern) processes attacker-controlled data under the victim's tenant identity.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
