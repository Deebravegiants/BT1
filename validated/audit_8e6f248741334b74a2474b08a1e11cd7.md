This confirms the critical link: `walletAccount.seedId` flows directly into `keychain.signBuffer({ seedId, keyId, ... })` for transaction signing [1](#0-0)  and message signing [2](#0-1) , and into `keychain.exportKey` for public key derivation [3](#0-2) . The keychain enforces that a seed with that ID must actually be loaded (`assert(this.#masters[seedId], ...)`) [4](#0-3) , which limits practical exploitability to seed IDs of seeds already present in the keychain (i.e., the attacker can only rebind to a seed already loaded in this wallet instance — not an arbitrary external secret).

The `update`/`updateMany` API is directly exposed via `walletAccountsApi` without any allow-listing/scrubbing of the `seedId` field [5](#0-4) , and the SDK docs confirm `update` accepts an arbitrary `walletAccountFields` object from the caller [6](#0-5) .

### Title
`seedId` immutability assertion in `updateWalletAccount` can be bypassed for accounts with `seedId` undefined, allowing cross-seed rebinding of a wallet account - (File: features/wallet-accounts/src/module/wallet-accounts.ts)

### Summary
The assertion `!before.seedId || before.seedId === after.seedId` in `updateWalletAccount` only prevents *changing* an already-set `seedId`; it does not prevent *setting* an arbitrary `seedId` on an account whose `seedId` is currently `undefined` [7](#0-6) . Because `update`/`updateMany` are exposed publicly through `walletAccountsApi` with no field allow-listing [5](#0-4) , and `seedId` is later used verbatim for key derivation/signing [8](#0-7) , a wallet account with no seed bound yet (e.g. a hardware or custodial account, or an exodus account before `#replaceAll`/lifecycle assigns its primary seed) could be silently bound to a different, already-loaded seed in the same wallet.

### Finding Description
`updateWalletAccount` builds `after` by merging `newData` onto `before` and only guards against changing `source`, `id`, `index`, and an *already-set* `seedId` [9](#0-8) . `WalletAccounts.update`/`updateMany` pass caller-supplied `data` straight into `updateWalletAccount` with no filtering of which fields may be set [10](#0-9) , and this method is surfaced directly as `walletAccounts.update` on the public SDK/API surface [5](#0-4) . Unlike `createMany`, which explicitly asserts `!data.seedId || data.seedId === primarySeedId` for `EXODUS_SRC` accounts before forcing `data.seedId = primarySeedId` [11](#0-10) , `updateWalletAccount` has no equivalent restriction tying an attacker-supplied `seedId` to the wallet's actual primary/derived seed. In the existing test suite, the only covered negative case is updating `seedId` on an account that *already* has one set [12](#0-11) ; there is no test (or code path) rejecting the case where `before.seedId` is falsy/undefined and `newData.seedId` is attacker-controlled.

### Impact Explanation
If reached with `before.seedId` undefined (this state is expected for non-exodus sourced accounts, e.g. hardware/custodial wallet accounts, per `#persistWalletAccounts`/`#replaceAll` logic that only forces `seedId` for `EXODUS_SRC`), an attacker able to invoke `update`/`updateMany` could bind that account name to any `seedId` string of their choosing. Downstream signing/derivation code (`SeedBasedTransactionSigner`, `SeedBasedMessageSigner`, `public-key-provider`) trusts `walletAccount.seedId` unconditionally when calling into the keychain [1](#0-0) . The keychain does gate on `this.#masters[seedId]` being populated [4](#0-3) , so the attacker cannot forge signatures under a truly external/unknown seed, but in a genuine multi-seed wallet where the victim has multiple seeds loaded, this allows silently rebinding one account entry to a *different* one of the user's own already-loaded seeds — causing wrong-seed signing/address derivation for that account (cross-seed account confusion), which matches a "wrong-account/origin access" style impact rather than full secret disclosure.

### Likelihood Explanation
Exploitability depends entirely on whether an untrusted caller (dapp/RPC/API consumer) can reach `walletAccounts.update`/`updateMany` with attacker-influenced `data`, and whether a target wallet account with `seedId` currently undefined exists (true for hardware/custodial accounts by design, and transiently possible for exodus accounts depending on timing/lifecycle ordering). The `walletAccountsApi` exposes `update` with no scoping of allowed fields, so if the surrounding RPC/dapp permission layer does not itself block passing a `seedId` field, the assertion in `updateWalletAccount` alone will not stop it.

### Recommendation
In `updateWalletAccount`, disallow `newData.seedId` from ever being set by generic update paths; require `seedId` to be derived internally (mirroring the `createMany` pattern of asserting it against the wallet's own primary/derived seed) rather than accepted from `newData` at all, e.g. `assert(newData.seedId === undefined || newData.seedId === before.seedId, 'seedId cannot be set via update')`, and route any legitimate seedId assignment through a dedicated internal method that consults `wallet.getPrimarySeedId()` or an equivalent trusted seed registry.

### Proof of Concept
Unit test in `features/wallet-accounts/src/module/__tests__/index.test.ts`, extending the existing `update`/`updateMany` describe blocks:

const updateWalletAccount = (
  walletAccounts: Record<string, WalletAccount> = Object.create(null),
  walletAccount: string,
  newData: Record<string, unknown>
) => {
  const before = walletAccounts[walletAccount]

  if (!before) throw new Error(`${walletAccount} is not a known wallet account`)

  if (walletAccount === DEFAULT_WALLET_ACCOUNT.toString() && newData.enabled === false) {
    throw new Error("Can't disable default walletAccount")
  }

  const after = new WalletAccount({
    ...before,
    ...newData,
  })

  for (const key of ['source', 'id', 'index']) {
    assert(
      (before as unknown as Record<string, unknown>)[key] ===
        (after as unknown as Record<string, unknown>)[key],
      `cannot change account ${key}`
    )
  }

  assert(
    !before.seedId || before.seedId === after.seedId,
    'seedId can only be set if previously undefined'
  )

  return after
}
