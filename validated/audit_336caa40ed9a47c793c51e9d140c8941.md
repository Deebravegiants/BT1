### Title
Webhook shop-domain header is not bound to the HMAC-signed body, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw body only, while the `shop` (and `topic`, `webhook_id`, `api_version`) values used downstream by `Registry.process` are taken from unauthenticated HTTP headers. The equality the code implicitly relies on — "the shop that produced/authenticated this signed body" == "the shop the handler is told the event came from" — does not actually hold, because the header is never covered by the HMAC.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `api_version`, and `webhook_id` are read straight from HTTP headers with no cryptographic binding to that body: [2](#0-1) 

`Registry.process` validates only the HMAC of the request (i.e., of the body) and then immediately trusts `request.shop`, `request.topic`, etc. to build the metadata handed to the app's handler: [3](#0-2) 

The library validates that *a* payload was signed with the app's shared `client_secret` (the same secret is used for every shop the app is installed on), but it does not validate that the `shop`-domain header actually corresponds to the shop that produced that signed body. This breaks the implicit binding `authenticated_body.shop == header.shop`. For any multi-tenant app (the standard Shopify app model), the same `client_secret` signs webhooks for every installed shop, so a valid `(body, hmac)` pair obtained from one tenant is cryptographically valid for any other tenant as well — only the header claims which tenant it "belongs" to, and that header is unauthenticated.

### Impact Explanation
This is a tenant-boundary break, not a documentation/host-app misuse issue: `Registry.process` (the gem's own public API) hands the handler a `WebhookMetadata` whose `shop` field looks validated (it comes right after `HmacValidator.validate` succeeds) but is not actually bound to the signed payload. An app author reasonably assumes that once `Registry.process`/`HmacValidator.validate` pass, both the body and the shop attribution are authentic. A merchant/attacker who operates their own shop with the app installed can capture a genuinely Shopify-signed webhook body+HMAC for an event they control (e.g., `orders/create` with attacker-controlled order data), then resend the identical body/HMAC to the app's webhook endpoint while swapping the `X-Shopify-Shop-Domain` header to a victim shop's domain. `HmacValidator.validate` still succeeds (it only checks the body), and the handler is invoked believing the (attacker-controlled) data belongs to the victim's shop — i.e., cross-tenant data confusion/injection using data attributed to a shop the attacker doesn't control.

### Likelihood Explanation
Likelihood requires only that the attacker be a legitimate merchant using the app (which many Shopify apps allow anyone to install) and knowledge of the app's webhook endpoint (typically documented/discoverable). No possession of the app's `client_secret` or any victim credential is required — the attacker relies entirely on Shopify's own legitimate signing of their own shop's traffic, then replays it with a forged header. This is a realistic, unprivileged-internet-user attack path reachable purely through this gem's documented `Webhooks::Request` / `Registry.process` API.

### Recommendation
Bind the tenant/topic identity into the signed material, or independently verify it out-of-band:
- Include `shop`, `topic`, and `webhook_id` in the signable string (would require coordinating with Shopify's webhook signing scheme, which is likely infeasible unilaterally), or
- More practically, have `Registry.process` require the caller/handler to cross-check `request.shop` against an app-known set of shops that have a currently valid, matching webhook registration/subscription id (`webhook_id` returned by Shopify's registration APIs) before trusting the shop attribution, and document prominently that `request.shop` is **not** covered by the HMAC and must not be trusted for authorization decisions without additional verification (e.g., matching against the `webhookId` returned when the topic was registered for that specific shop).
- At minimum, update documentation/warnings on `Webhooks::Request` and `WebhookMetadata` to explicitly state that `shop` is unauthenticated relative to the signed body, so app authors do not conflate the two.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker-shop.myshopify.com` (legitimate, no special privilege needed).
2. Attacker triggers an event covered by a registered webhook topic (e.g., `orders/create`) with attacker-chosen order data.
3. Shopify sends a legitimately signed webhook to the app's endpoint:
   - Headers: `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid HMAC of body>`
   - Body: attacker-controlled JSON.
4. Attacker captures this `(body, hmac)` pair and resends it directly to the app's webhook endpoint with the header rewritten to `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate(request)` succeeds because it only checks the (unchanged) body against the (unchanged) HMAC: [4](#0-3) 
6. `Registry.process` invokes the handler with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body, even though that shop never sent this event: [3](#0-2)
