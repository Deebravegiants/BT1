Confirmed: `docs/usage/webhooks.md:125` explicitly documents that `Registry.process` "will verify the request did indeed come from Shopify" — this is the gem's documented guarantee that the entire webhook, including the shop it's attributed to, has been authenticated. ### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity fields are not covered by the HMAC signature, allowing a valid signed webhook body to be replayed under a spoofed tenant identity - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `#shop`, `#topic`, `#webhook_id`, and `#api_version` are read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC over the body only and then forwards `request.shop` verbatim to the app's handler as the trusted tenant identifier, breaking the binding `HMAC-verified bytes == trusted shop`.

### Finding Description
`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`, and for webhooks that method is defined as simply the raw body: [1](#0-0) [2](#0-1) [3](#0-2) 

`Registry.process` checks only this body-bound HMAC and then immediately trusts `request.shop` (and `request.topic`/`webhook_id`/`api_version`) — all header-derived, unsigned values — to build the `WebhookMetadata` handed to the app's handler: [4](#0-3) 

Because `shop` is never part of `to_signable_string`, the equality the gem should guarantee — "the shop attributed to this webhook" == "the shop whose secret produced this HMAC" — does not hold. Any raw body + valid HMAC pair remains valid under **any** `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header value, since the signature is agnostic to headers entirely. The documentation explicitly promises that `Registry.process` "will verify the request did indeed come from Shopify" for the whole request, which is not true of the `shop` field: [5](#0-4) 

### Impact Explanation
This crosses a tenant boundary: an app that operates multiple merchant tenants (the standard multi-tenant Shopify app model this gem is built for) relies on `data.shop` to route/attribute incoming webhook data per the documented handler contract: [6](#0-5) 

An attacker who legitimately installs the app on their own store (an "unprivileged internet user" with respect to any *other* tenant) will receive genuine, correctly-HMAC-signed webhooks from Shopify for their own shop. Because the signature does not cover the shop header, the attacker can capture one such valid `(raw_body, hmac)` pair and replay the exact same bytes to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop domain. `HmacValidator.validate` still succeeds (it never inspected the header), and the handler receives `WebhookMetadata` claiming the payload originated from the victim tenant — this is cross-tenant data/event injection using only the attacker's own legitimately-issued webhook credentials, no access to `client_secret`, tokens, or the victim's data required.

### Likelihood Explanation
Any developer following the gem's own documented usage (`Registry.process`, `Request.new(raw_body:, headers:)`) is exposed; nothing in the gem warns that `shop`, `topic`, `webhook_id`, or `api_version` are unauthenticated. The only prerequisite is that the attacker be an installer of the target app on any shop — a normal, unprivileged capability for a public app — making this straightforward to reach without any elevated access.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable string used for HMAC verification (Shopify's own guidance is that only the raw body is signed for webhook delivery integrity, but the gem should not expose an unauthenticated `shop` accessor as if it were verified data — the docs and API should clearly demarcate that `shop`/`topic`/etc. are unauthenticated header values, or the gem should independently cross-check `request.shop` against session storage / the tenant that owns `webhook_id` before dispatching to the handler).

### Proof of Concept
```ruby
# Attacker installs the app on shop "attacker.myshopify.com" and captures a
# legitimately Shopify-signed webhook for their own shop, e.g. orders/create:
raw_body   = '{"id":1,"note":"hello"}'
valid_hmac = "shopify-hmac-sha256-value-computed-by-shopify-for-attacker-shop"

# Attacker replays identical bytes but swaps only the shop header:
forged_headers = {
  "x-shopify-topic"        => "orders/create",
  "x-shopify-hmac-sha256"  => valid_hmac,          # unchanged, still valid
  "x-shopify-shop-domain"  => "victim.myshopify.com", # spoofed
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) succeeds because to_signable_string == raw_body only.
# The handler receives WebhookMetadata(shop: "victim.myshopify.com", ...), a forged tenant identity.
```

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

module WebhookHandler

      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
