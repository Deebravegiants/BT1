Based on the code explored, I found a valid analog to the CVE-2020-27756 divide-by-zero bug class.

### Title
Divide-by-zero panic in AMM swap math when pool reserves are fully drained via `need_take_pnl` accounting - ([File: program/src/math.rs])

### Summary
`Calculator::swap_token_amount_base_in` / `swap_token_amount_base_out` and the `InvariantPool`/`InvariantToken` exchange helpers in `program/src/math.rs` compute swap and LP-redemption ratios using `checked_div(...).unwrap()` on denominators derived directly from live, attacker-influenceable pool state (`total_pc_without_take_pnl`, `total_coin_without_take_pnl`, `lp_amount`) without any prior validation that these denominators are non-zero. [1](#0-0) [2](#0-1) 

### Finding Description
`swap_token_amount_base_in` computes `denominator = total_coin_without_take_pnl.checked_add(amount_in).unwrap()` and then divides by it; `swap_token_amount_base_out` computes `denominator = total_pc_without_take_pnl.checked_sub(amount_out).unwrap()` (or the coin equivalent) and divides by it. [3](#0-2)  These are called directly from the four public swap instruction handlers (`SwapBaseIn`/`SwapBaseOut`, both v1 and v2 paths) using vault balances read straight from the token accounts and `AmmInfo.state_data.need_take_pnl_pc/coin`, via `calc_total_without_take_pnl_no_orderbook`. [4](#0-3) [5](#0-4) [6](#0-5) 

If `total_pc_without_take_pnl` or `total_coin_without_take_pnl` becomes `0` (e.g., a vault reserve is fully swapped out, or `need_take_pnl_*` accounting drives the "without-pnl" balance to exactly match the raw vault amount) the `swap_token_amount_base_out` subtraction path or the base-in division can hit a zero denominator, and `.unwrap()` on the resulting `None`/panic aborts the transaction. All of this state is reachable and steerable by an unprivileged trader issuing repeated swap instructions with attacker-chosen `amount_in`/`amount_out`, with no privileged signer required. [7](#0-6) 

Similarly, `InvariantPool::exchange_pool_to_token`/`exchange_token_to_pool` (used in LP mint/redeem math for `Deposit`/`Withdraw`) divide by `self.token_total`, which is `amm.lp_amount`; if a pool's LP supply is driven to zero (or a coin/pc side used as `token_coin`/`token_pc` in `InvariantToken` reaches zero), the same `.unwrap()`-on-zero-denominator pattern applies. [8](#0-7) [9](#0-8) 

This mirrors the CVE-2020-27756 bug class: attacker-influenced values flow into arithmetic used as a divisor without a guard, and the fix pattern recommended for ImageMagick (checked reciprocal / explicit zero-check before dividing) is exactly what's missing here — the code instead relies on `unwrap()`, converting the "undefined behavior" of the C bug into a hard Rust panic in the Solana runtime.

### Impact Explanation
A panic inside instruction processing causes the transaction to abort. If this can be triggered deterministically once a pool reaches a drainable/zero-reserve state (through legitimate large swaps that push a reserve toward zero, or through PnL-take accounting edge cases), any subsequent swap/withdraw call that hits the same zero-denominator branch will always fail, permanently freezing further swaps and/or LP withdrawals against that pool for all users — this satisfies the "permanent freezing of user or LP funds" criterion. The `.unwrap()` calls do not corrupt state (Rust panics don't cause silent numeric UB the way the C divide-by-zero does), but the availability impact (irrecoverable freezing) is the practical equivalent for this codebase.

### Likelihood Explanation
Reaching a zero denominator requires driving `total_pc_without_take_pnl`/`total_coin_without_take_pnl` or `amm.lp_amount` to exactly zero, which is an edge condition not trivially reachable in one transaction under normal fee/pnl accounting, since `swap_token_amount_base_in`/`out` include fee deductions and reserves are unlikely to hit exactly zero from typical swap amounts. I could not fully verify from the available code whether `process_deposit`/`process_withdraw` contain additional guards (e.g., minimum-liquidity locks) that prevent `lp_amount` or a vault-side reserve from ever reaching zero — the deposit/withdraw handler bodies were not fully inspected within the available iterations. This limits confidence that the zero-denominator state is practically reachable by an unprivileged actor without such additional guards being bypassed.

### Recommendation
Replace `.unwrap()` on divisions in `swap_token_amount_base_in`, `swap_token_amount_base_out`, `InvariantPool::exchange_pool_to_token`/`exchange_token_to_pool`, and `InvariantToken::exchange_coin_to_pc`/`exchange_pc_to_coin` with explicit zero-denominator checks that return a proper `AmmError` (e.g., `AmmError::ZeroDenominator` or similar) instead of panicking, and add explicit checks in the swap/deposit/withdraw processors that reject operations when `total_pc_without_take_pnl`, `total_coin_without_take_pnl`, or `amm.lp_amount` are zero before invoking these math helpers.

### Proof of Concept
Not independently verified against a running validator; conceptually: (1) attacker identifies or drives a pool where `total_coin_without_take_pnl` (or `total_pc_without_take_pnl`) approaches its minimum, (2) attacker submits a `SwapBaseOut` instruction whose `amount_out` is set such that `total_pc_without_take_pnl.checked_sub(amount_out)` (or the coin equivalent) equals the total reserve, driving the subsequent divisor to `0` in `swap_token_amount_base_out`, causing `.unwrap()` to panic and abort the transaction, and — if the resulting state is unrecoverable — causing all further swaps in that direction to permanently fail.     pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }

    pub fn swap_token_amount_base_in(
        amount_in: U128,
        total_pc_without_take_pnl: U128,
        total_coin_without_take_pnl: U128,
        swap_direction: SwapDirection,
    ) -> U128 {
        let amount_out;
        match swap_direction {
            SwapDirection::Coin2PC => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (coin + amount_in) * (pc - amount_out) = coin * pc
                // => amount_out = pc - coin * pc / (coin + amount_in)
                // => amount_out = ((pc * coin + pc * amount_in) - coin * pc) / (coin + amount_in)
                // => amount_out =  pc * amount_in / (coin + amount_in)
                let denominator = total_coin_without_take_pnl.checked_add(amount_in).unwrap();
                amount_out = total_pc_without_take_pnl
                    .checked_mul(amount_in)
                    .unwrap()
                    .checked_div(denominator)
                    .unwrap();
            }
            SwapDirection::PC2Coin => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (pc + amount_in) * (coin - amount_out) = coin * pc
                // => amount_out = coin - coin * pc / (pc + amount_in)
                // => amount_out = (coin * pc + coin * amount_in - coin * pc) / (pc + amount_in)
                // => amount_out = coin * amount_in / (pc + amount_in)
                let denominator = total_pc_without_take_pnl.checked_add(amount_in).unwrap();
                amount_out = total_coin_without_take_pnl
                    .checked_mul(amount_in)
                    .unwrap()
                    .checked_div(denominator)
                    .unwrap();
            }
        }
        return amount_out;
    }

    pub fn swap_token_amount_base_out(
        amount_out: U128,
        total_pc_without_take_pnl: U128,
        total_coin_without_take_pnl: U128,
        swap_direction: SwapDirection,
    ) -> U128 {
        let amount_in;
        match swap_direction {
            SwapDirection::Coin2PC => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (coin + amount_in) * (pc - amount_out) = coin * pc
                // => amount_in = coin * pc / (pc - amount_out) - coin
                // => amount_in = (coin * pc - pc * coin + amount_out * coin) / (pc - amount_out)
                // => amount_in = (amount_out * coin) / (pc - amount_out)
                let denominator = total_pc_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_coin_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
            SwapDirection::PC2Coin => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (pc + amount_in) * (coin - amount_out) = coin * pc
                // => amount_out = coin - coin * pc / (pc + amount_in)
                // => amount_out = (coin * pc + coin * amount_in - coin * pc) / (pc + amount_in)
                // => amount_out = coin * amount_in / (pc + amount_in)

                // => amount_in = coin * pc / (coin - amount_out) - pc
                // => amount_in = (coin * pc - pc * coin + pc * amount_out) / (coin - amount_out)
                // => amount_in = (pc * amount_out) / (coin - amount_out)
                let denominator = total_coin_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_pc_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
        }
        return amount_in;
    }
