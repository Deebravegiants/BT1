### Title
Missing chain-type binding check allows a TON_CONNECT signature to be verified against an unrelated user's TON address - ([File: packages/internal-utils/src/utils/prepareBroadcastRequest.ts])

### Summary
`prepareSwapSignedData` in `packages/internal-utils/src/utils/prepareBroadcastRequest.ts` builds the `signed_data` payload sent to the solver relay for intent settlement. For most signature standards the on-chain identity is recovered from the signature itself (e.g. `ecrecover` for ERC191/TIP191, or the embedded `public_key` for NEP413), so the caller-supplied `userInfo.userChainType`/`userAddress` cannot be used to impersonate anyone. But for standards where the `public_key`/`address` field is derived directly from the caller-supplied `userInfo.userAddress` rather than from the signature payload, the function must verify that `userInfo.userChainType` actually matches the signature's `type` before trusting that address — otherwise the wrong address gets bound to the signature. [1](#0-0) [2](#0-1) 

### Finding Description
The `SOLANA` and `STELLAR_SEP53` branches both derive the outgoing `public_key` from `userInfo.userAddress` and both explicitly `assert(userInfo.userChainType === "solana"/"stellar", "User chain and signature chain must match")` before doing so — this is the intended equality check binding the address to the signature type. The `WEBAUTHN` branch delegates to `makeWebAuthnMultiPayload`, which has its own equivalent assert. [3](#0-2) 

However, the `TON_CONNECT` branch also derives its `public_key` field directly from `userInfo.userAddress` (`ed25519:${base58.encode(hex.decode(userInfo.userAddress))}`), but it has **no equivalent assert** checking `userInfo.userChainType === "ton"`: [4](#0-3) 

This breaks the equality that every other address-derived branch enforces: "the address bound into the signed payload must be the one whose chain type was actually validated for this signature." If a caller invokes `prepareSwapSignedData`/`publishIntent` with a `TON_CONNECT` signature object but supplies a `userInfo` whose `userAddress`/`userChainType` do not actually correspond to the TON signer that produced the signature (e.g., stale or mismatched session state after switching accounts/chains, analogous to the SurrealDB `USE` database-switch bug where the `$auth` context carried over unchecked into the new context), the resulting `signed_data.public_key` will point at a different TON identity than the one that actually authorized the intent, while the signature blob itself is opaque to this function (no server-side recomputation of the address from the signature at this layer catches the mismatch before submission).

### Impact Explanation
If exploitable, this allows an intent to be published under (attributed to) a TON address that was never cryptographically bound to the actual signer at this stage of client-side payload construction, mirroring the CWE-287 class in the source advisory (identity from one context leaking into another). Downstream, whether this can actually cause fund misdelivery depends on the relay/contract still verifying the raw ed25519 signature against the `public_key` on-chain — if that check is correct, this specific bug would be caught server-side and only result in a rejected request, not an actual fund loss. I could not fully verify from the code available in-scope whether any additional caller-side guard exists upstream of `publishIntent`/`prepareSwapSignedData` that already enforces `userChainType === signature.type` before this function is invoked, since the call sites for the SDK's wallet flow were not fully resolvable within the indexed scope.

### Likelihood Explanation
Low-to-Medium. Triggering this requires the caller of `prepareSwapSignedData` to pass a `TON_CONNECT`-typed signature together with a `userInfo` object whose chain type/address do not match — this would typically require a bug in the wallet-integration/session layer that supplies `userInfo`, not attacker control over `prepareSwapSignedData`'s inputs directly. This is analogous to the original SurrealDB issue, which also required a specific state (matching record IDs across databases) rather than being directly attacker-triggerable in isolation.

### Recommendation
Add the same defensive assertion used in the `SOLANA` and `STELLAR_SEP53` branches to the `TON_CONNECT` branch: `assert(userInfo.userChainType === "ton", "User chain and signature chain must match")` before deriving `public_key`/`address` from `userInfo.userAddress`. This restores the equality invariant that every branch deriving identity from caller-supplied `userInfo` (rather than recovering it from the signature) must verify the chain-type binding first.

### Proof of Concept
Not independently verifiable as a full end-to-end exploit within the indexed scope — the concrete path would be: call `prepareSwapSignedData({ type: "TON_CONNECT", ... }, { userAddress: "<attacker-controlled-or-stale-address>", userChainType: "ton" })` where the caller's session/account-switch logic failed to refresh `userInfo` to match the actual signer of the TON_CONNECT signature; the function will silently emit `signed_data.public_key` derived from the stale/wrong `userAddress` with no internal check, unlike the SOLANA/STELLAR_SEP53 paths which would `assert`-fail on such a mismatch. export function prepareSwapSignedData(
	signature: WalletSignatureResult,
	userInfo: { userAddress: string; userChainType: AuthMethod },
): Params<PublishIntentRequest>["signed_data"] {
	const signatureType = signature.type;
	switch (signatureType) {
		case "NEP413": {
			return {
				standard: "nep413",
				payload: {
					message: signature.signedData.message,
					nonce: base64.encode(signature.signedData.nonce),
					recipient: signature.signedData.recipient,
					callbackUrl: signature.signedData.callbackUrl,
				},
				public_key: signature.signatureData.publicKey, // publicKey is already in the correct format
				signature: transformNEP141Signature(signature.signatureData.signature),
			};
		}

		case "ERC191": {
			return {
				standard: "erc191",
				payload: signature.signedData.message,
				signature: transformERC191Signature(signature.signatureData),
			};
		}

		case "SOLANA":
			assert(
				userInfo.userChainType === "solana",
				"User chain and signature chain must match",
			);
			return {
				standard: "raw_ed25519",
				payload: new TextDecoder().decode(signature.signedData.message),
				// Solana address is its public key encoded in base58
				public_key: `ed25519:${userInfo.userAddress}`,
				signature: transformED25519Signature(signature.signatureData),
			};

		case "WEBAUTHN": {
			return makeWebAuthnMultiPayload(userInfo, signature);
		}

		case "TON_CONNECT": {
			return {
				standard: "ton_connect",
				address: signature.signatureData.address,
				domain: signature.signatureData.domain,
				timestamp: signature.signatureData.timestamp,
				payload: signature.signatureData.payload,
				public_key: `ed25519:${base58.encode(hex.decode(userInfo.userAddress))}`,
				signature: `ed25519:${base58.encode(base64.decode(signature.signatureData.signature))}`,
			};
		}

		case "STELLAR_SEP53": {
			assert(
				userInfo.userChainType === "stellar",
				"User chain and signature chain must match",
			);
			return {
				standard: "sep53",
				payload: signature.signedData.message,
				// We should encode the Stellar address to base58
				public_key: `ed25519:${base58.encode(
					stellarAddressToBytes(userInfo.userAddress),
				)}`,
				signature: transformED25519Signature(signature.signatureData),
			};
		}

		case "TRON": {
			return {
				standard: "tip191",
				payload: signature.signedData.message,
				signature: transformERC191Signature(signature.signatureData), // TIP-191 is compatible with ERC191
			};
		}

		default:
			signatureType satisfies never;
			throw new Error("exhaustive check failed");
	}
}
