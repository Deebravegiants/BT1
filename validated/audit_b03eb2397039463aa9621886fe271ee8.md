### Title
Non-USDC/LT ERC20 tokens (and stray LT/USDC dust) accidentally sent to `Zap` are permanently frozen with no recovery path - ([File: packages/contracts/src/Zap.sol])

### Summary
`Zap` is a pass-through contract that pulls USDC, mints/redeems LT, and forwards tokens to users, but it has **no owner-only sweep/rescue function** for any ERC20 balance it happens to hold. Both sibling contracts in the same codebase — `Bonding` and `FeeVault` — explicitly solved this exact problem class (stray/donated asset recovery), but `Zap` was left without an equivalent mechanism.

### Finding Description
`Zap.sol` [1](#0-0)  only defines storage, events, and errors; there is no `sweep`, `rescue`, `withdraw`, or `onlyOwner`-gated transfer function anywhere in the contract (confirmed by exhaustive grep for `onlyOwner`, `sweep`, `rescue`, `withdraw` patterns — zero hits besides fee-setter/initializer/upgrade functions).

Compare this to the two other UUPS contracts in the same protocol that hold third-party assets:
- `FeeVault.sweepDonations()` permissionlessly sweeps any USDC balance above the tracked `totalAccruedCreator + protocolBalance` to `feeTo` [2](#0-1) .
- `Bonding._sweepLTToOwner` sweeps any LT balance above the earmarked `protectedLT` to the owner at the end of every `finalizeGraduation`, emitting `LTRescued` [3](#0-2) .

`Zap`'s buy/sell flow (`_executeBuy` / `_sellInternal`) does refund unconsumed USDC and LT to the caller **within the same transaction** [4](#0-3) , but this only covers dust generated by Zap's own internal mint/curve-buy math in that specific call. It provides no mechanism to recover:
- A direct/accidental `IERC20(lt).transfer(zapAddress, amount)` or `usdc.transfer(zapAddress, amount)` from any unrelated wallet.
- Any ERC20 (including a launched `Token` or any LT) donated straight to the `Zap` address outside of a `buy`/`sell` call.

Because `Zap` is `UUPSUpgradeable` and `Ownable2StepUpgradeable`, the owner could in principle push an upgrade to add a sweep function, but as deployed there is no on-chain function that can move a stray balance out of `Zap` — it is permanently stuck under normal operating assumptions (no upgrade guaranteed to happen).

### Impact Explanation
This matches the external report's bug class directly: any USDC, LT, or launched `Token` mistakenly sent to `Zap` (e.g., a trader fat-fingering the `Zap` address instead of calling `buy`/`sell`, or misconfigured tooling) is permanently frozen — the sender loses the funds with no recovery path, and unlike `Bonding`/`FeeVault` there isn't even a permissionless or owner path to redirect it to a legitimate destination (creator/protocol/owner). This is a genuine freezing-of-funds issue reachable by any unprivileged wallet's ordinary mistake.

### Likelihood Explanation
Medium likelihood: accidental transfers to a well-known, actively-used contract address (`Zap` is the primary user-facing entry point, so its address is widely referenced/copied by users, wallets, and integrators) are a realistic and recurring class of user error, as acknowledged by the original report and by the protocol's own remediation of the identical pattern in `Bonding` and `FeeVault`.

### Recommendation
Add a permissionless or owner-gated sweep function to `Zap` mirroring `FeeVault.sweepDonations()` / `Bonding._sweepLTToOwner`: track the USDC/LT balances that are legitimately "in flight" during a `buy`/`sell` call (which should be zero at rest since `Zap` is not meant to hold balances between transactions), and allow any balance held by `Zap` outside of an active call to be swept to the owner or to `FeeVault`. For arbitrary non-USDC/LT/Token ERC20s, add a generic `sweepToken(address token, address to)` owner-only function.

### Proof of Concept
1. A user or bot intends to call `Zap.buy(tokenAddress, usdcAmount, ...)` but instead executes `usdc.transfer(zapAddress, usdcAmount)` directly (e.g., copy-paste error, wrong function selector in a script, or sending the LT/launched Token directly instead of going through `buy`/`sell`).
2. The USDC/LT/Token now sits in `Zap`'s balance.
3. Since `Zap.sol` exposes no `sweep`/`rescue`/`withdraw` function (verified via full-file grep for `onlyOwner`, `sweep`, `rescue`, `withdraw` — no matches beyond fee-setters/initializer/`_authorizeUpgrade`), and the existing `_executeBuy`/`_sellInternal` refund logic only operates on balances computed within that single call's local variables (not `balanceOf(address(this))`), the donated balance is never referenced or moved by any subsequent call.
4. The funds remain permanently stuck in `Zap`, unlike the identical scenario in `FeeVault` (recoverable via `sweepDonations()`) or `Bonding` (recoverable via the `_sweepLTToOwner`/`protectedLT` mechanism in `finalizeGraduation`).

    /// @notice Sweep unbacked USDC (donations) to `feeTo`. Required because
    ///         direct USDC transfers would otherwise inflate `balanceOf` above
    ///         the accrual tally and silently mask the `accrue` underfund
    ///         check. Permissionless — funds always go to the admin-set `feeTo`.
    function sweepDonations() external nonReentrant returns (uint256 amount) {
        FeeVaultStorage storage $ = _s();
        uint256 backed = $.totalAccruedCreator + $.protocolBalance;
        uint256 balance = $.usdc.balanceOf(address(this));
        if (balance <= backed) revert NothingToClaim();
        amount = balance - backed;
        address feeTo_ = $.feeTo;
        $.usdc.safeTransfer(feeTo_, amount);
        emit DonationsSwept(feeTo_, amount);
    }

    /// @dev Send LT held by this contract above `keep` to the owner,
    ///      emitting `LTRescued`. Called at the end of
    ///      `finalizeGraduation` with `keep = protectedLT` (any escrow
    ///      that doesn't belong to this graduation), so only THIS
    ///      graduation's rebalance residue lands on the owner. No-op on
    ///      the empty-pair fast path (nothing to sweep).
    function _sweepLTToOwner(
        address lt,
        uint256 keep
    ) internal {
        uint256 bal = IERC20(lt).balanceOf(address(this));
        if (bal <= keep) return;
        uint256 amount = bal - keep;
        address recipient = owner();
        IERC20(lt).safeTransfer(recipient, amount);
        emit LTRescued(lt, recipient, amount);
    }
