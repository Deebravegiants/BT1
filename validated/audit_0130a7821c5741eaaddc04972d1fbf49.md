**Reasoning:**

`get_reads_needing_exchange` and its implementations [1](#0-0)  are part of the Block-STM / sequential execution engine's internal bookkeeping for delayed fields (AggregatorV2). They compute, from the *transaction's own actual read and write sets recorded during execution*, which resources contain a delayed-field id that must be exchanged back to a concrete value before being materialized into the output. The read set here is not something an unprivileged attacker can decouple from the write set independently — it is derived directly from what the VM/Move code actually touched during execution, tracked by `LatestView`'s `captured_reads`/`unsync_map` (parallel path) or `read_set.resource_reads` (sequential path) [2](#0-1) .

Concretely, whether a resource is included is determined by `does_value_need_exchange`/`filter_value_for_exchange`, which checks the actual layout and delayed-field identifiers embedded in the value that was read, not by any signer-controlled flag: [3](#0-2) . There is no code path connecting this mechanism specifically to a "dispatch-hook-config resource" vs. its "linked aggregator" as two independently toggleable custody objects — the coupling the question assumes (that a hook config and its balance aggregator must be exchanged "together") does not correspond to any invariant enforced or referenced anywhere in this exchange logic; it treats each resource key independently based on what layout/delayed-field ids it actually contains, which is the correct semantics for arbitrary resources containing aggregators.

Even granting the premise, this logic operates purely on data already produced by that same transaction's own execution — it cannot be leveraged by an unprivileged caller to rewrite another party's fungible-asset metadata, freeze authority, dispatch hooks, or object ownership, since materialization only ever writes back values for keys that transaction already validly read/wrote under existing Move/type-system authority checks (`FungibleStore`/`DispatchFunctionStore` capability rules are enforced at the Move level, not at this resolver layer). No unprivileged entrypoint (transaction, package, view, authenticator, API, or bytecode) is shown to cross into a custody boundary controlling ownership, mint/burn, freeze, or upgrade authority. This is an internal execution-engine consistency mechanism, not an asset-custody control, so it falls outside the required custody-impact gate.

    fn get_reads_needing_exchange_sequential(
        &self,
        read_set: &HashSet<T::Key>,
        unsync_map: &UnsyncMap<T::Key, T::Tag, ValueWithLayout<T::Value>, DelayedFieldID>,
        delayed_write_set_ids: &HashSet<DelayedFieldID>,
        skip: &HashSet<T::Key>,
    ) -> Result<BTreeMap<T::Key, (StateValueMetadata, u64, TriompheArc<MoveTypeLayout>)>, PanicError>
    {
        read_set
            .iter()
            .filter_map(|key| {
                if skip.contains(key) {
                    return None;
                }

                match unsync_map.fetch_data(key) {
                    Some(ValueWithLayout::Exchanged(value, Some(layout))) => self
                        .filter_value_for_exchange(
                            value.as_ref(),
                            &layout,
                            delayed_write_set_ids,
                            key,
                        ),
                    Some(ValueWithLayout::Exchanged(_, None)) => None,
                    Some(ValueWithLayout::RawFromStorage(_)) => Some(Err(code_invariant_error(
                        "Cannot exchange value that was not exchanged before",
                    ))),
                    None => None,
                }
            })
            .collect()
