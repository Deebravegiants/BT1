Based on the investigation, there is a valid analog in the webhook HMAC verification path, matching the "field acted on but not covered by the HMAC" bug class from the rules.

### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from the raw HTTP body only, while the `shop` identity used for dispatching webhook data to the app's handler comes from an unsigned HTTP header. Any actor who can obtain one valid HMAC-signed webhook body (e.g., a merchant with the app installed on their own store, receiving their own legitimate webhooks) can replay that exact body to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header, and the library will still accept it as authentic for the spoofed shop.

### Finding Description
`Webhooks::Request#to_signable_string` only returns `@raw_body`: [1](#0-0) 

`shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is not part of the signed data: [2](#0-1) 

`Registry.process` validates only the body HMAC via `Utils::HmacValidator.validate(request)`, and then forwards `request.shop` (the unauthenticated header) directly into the handler as the tenant identity, with no cross-check that the signed content actually belongs to that shop: [3](#0-2) 

`HmacValidator.validate` recomputes the HMAC purely from `to_signable_string` (i.e. the raw body) and the app's `client_secret`, and only compares the digest — it never binds `shop` into the computed signature: [4](#0-3) 

The identity binding broken here is: `shop_header == shop_bound_by_hmac` is assumed true by `Registry.process`, but the actual equality enforced by the code is only `hmac(body) == hmac(body)` — `shop` is never part of that equation. Concretely: any party that legitimately receives a valid webhook delivery for their own shop (all merchants who install the app share the same `client_secret` since Shopify computes the HMAC using the app's `client_secret`, not a per-shop secret) can capture the raw body + HMAC pair, then POST it to the same endpoint with a different `shop-domain` header value. The signature still validates because it depends only on the body and the shared `client_secret`, so the app processes the payload as belonging to the spoofed shop.

### Impact Explanation
This breaks the tenant boundary between different shops (merchants) using the same app: a legitimate but unprivileged merchant (tenant A) can forge webhook deliveries that the app attributes to a shop it does not control (tenant B). Depending on what the host app's webhook handlers do with `WebhookMetadata#shop` (e.g. `orders/create`, `app/uninstalled`, `customers/data_request`), this can lead to cross-tenant data injection, triggering privileged per-shop actions, or corrupting another tenant's records — meeting the Critical "cross-tenant access" bar defined in scope.

### Likelihood Explanation
Any app that has been installed by at least one shop already possesses a stream of validly-HMAC'd webhook bodies (its own legitimate deliveries), since the HMAC key (`client_secret`) is shared across all shops using the same app, not shop-specific. Replaying a captured body with a modified `shop-domain` header requires no cryptographic secret and no privileged access beyond having installed the app once — an unprivileged-relative-to-other-tenants actor.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the value that is verified, not just the raw body — e.g., include `shop-domain`, `topic`, and `webhook-id` headers in the signable string used by `HmacValidator`, or otherwise cryptographically bind the header-derived `shop` to the verified payload before it is trusted and forwarded to handlers in `Registry.process`.

### Proof of Concept
1. App is installed on `shop-a.myshopify.com`; attacker controls that shop and can receive its own legitimate webhook deliveries (raw body + `shopify-hmac-sha256` header), since Shopify signs webhooks with the app's shared `client_secret`.
2. Attacker replays the exact same raw body and HMAC value to the app's webhook endpoint, but sets `shopify-shop-domain: shop-b.myshopify.com` (or `x-shopify-shop-domain`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC from `request.to_signable_string` (the raw body only) and finds it matches — validation passes.
4. `handler.handle` is invoked with `WebhookMetadata.new(shop: "shop-b.myshopify.com", ...)`, so the host application processes attacker-supplied data as authentic for `shop-b`, even though `shop-b` never sent this webhook and Shopify never signed anything binding this payload to `shop-b`.
