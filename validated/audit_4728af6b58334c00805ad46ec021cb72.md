### Title
Execution-order (CEI) violation in `IntentGatewayV2.withdraw` lets a malicious order beneficiary re-enter and drain/duplicate escrow before balances are decremented - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron deployment of `IntentGatewayV2` implements escrow release in `withdraw()` with the exact "withdraw/transfer-before-effects" ordering flaw described in the reference report: the external token/ETH transfer is executed *before* the corresponding escrow accounting (`_orders[body.commitment][token] -= amount`) is updated, and before the transaction-fee escrow is cleared. This is the same class of bug as `unwrapWethWithFee` (external transfer performed prior to the state change that should have consumed the balance), and it exists in a token/escrow-release path that is directly reachable by an intent solver/beneficiary.

### Finding Description
`withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` is called from `onAccept()` whenever a `RedeemEscrow`/`RefundEscrow` message is delivered: [1](#0-0) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;

    for (uint256 i; i < len;) {
        ...
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();

        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");
            if (!sent) revert InsufficientNativeToken();
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
            if (!success) revert TransferFailed();
        }

        _orders[body.commitment][token] -= amount;   // <-- effect happens AFTER the external call
        ...
    }
    ...
}
```

The transaction-fee payout has the same ordering issue: [2](#0-1) 

Note the fee token is invoked with a raw low-level `.call` to `transfer`, and `_orders[body.commitment][TRANSACTION_FEES]` is deleted only after that external call returns.

This is a direct regression relative to the main EVM `IntentsBase._withdraw` implementation, which already applies the corrected CEI ordering (decrement escrow *before* the external transfer) as a documented fix for exactly this class of reentrancy: [3](#0-2) 

```solidity
_orders[body.commitment][token] = escrowed - amount;
if (token == address(0)) {
    _sendValue(beneficiary, amount);
} else {
    IERC20(token).safeTransfer(beneficiary, amount);
}
```

The project's own reentrancy regression tests confirm the security model requires effects-before-interactions for this exact code path (`IntrinsicIntentsReentrancyTest.sol`), and that `beneficiary` is fully attacker-controlled (an arbitrary contract address supplied in the `Order`/`WithdrawalRequest`): [4](#0-3) 

Because the Tron contract still uses the pre-fix ordering, a malicious `beneficiary` contract's `receive()`/token `transfer` hook fires while `_orders[commitment][token]` (and `_orders[commitment][TRANSACTION_FEES]`) still hold their pre-withdrawal values. From that callback the beneficiary can re-enter any externally reachable function of the same contract (e.g. `placeOrder`, `cancelOrder`, or — if the host/relayer flow allows a second `onAccept` dispatch for a related commitment before the first completes) and observe/act on stale escrow state, or in the worst case (depending on host call semantics on Tron) trigger a second `withdraw` for the same commitment before the balance is zeroed out, double-spending the escrow.

### Impact Explanation
This function moves real user/solver funds (native TRX/ETH and ERC-20 tokens escrowed by `placeOrder`, plus protocol/relayer transaction fees). An execution-order flaw here is a concrete theft-of-funds / escrow-integrity vector: it violates the checks-effects-interactions pattern that the rest of the codebase (main EVM `IntentsBase`) has already been hardened against for this identical function, indicating the Tron contract is a stale, unpatched fork. Given the severity classification the codebase itself assigns to this bug class (the `IntrinsicIntentsReentrancyTest.sol` suite exists specifically to prevent "fee theft" and "multi-output escrow theft" via this pattern), this is a Medium-severity finding consistent with the reference report's classification.

### Likelihood Explanation
The `beneficiary` field of an `Order`/`WithdrawalRequest` is attacker-controlled (any address, including a malicious contract), and `withdraw()` is reached whenever Hyperbridge delivers a `RedeemEscrow`/`RefundEscrow` message for an order that a malicious actor placed or filled naming themselves as beneficiary — a normal, permissionless usage path of the Intent Gateway. No special privilege is required beyond acting as a solver/order-beneficiary, which is exactly the "intent solver" actor class in scope.

### Recommendation
Apply the same CEI fix already present in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw` to the Tron contract's `withdraw()`: decrement `_orders[body.commitment][token]` (and delete `_orders[body.commitment][TRANSACTION_FEES]`) *before* performing the external `.call`/`transfer` to the beneficiary, for both the token loop and the fee payout.

### Proof of Concept
Conceptually mirrors the project's own `ReentrantBeneficiary` test harness in `IntrinsicIntentsReentrancyTest.sol`, applied to the Tron contract's un-patched `withdraw()`:
1. Attacker places/fills an order naming a malicious contract as `beneficiary`, with a native-ETH/TRX output and an escrowed `TRANSACTION_FEES` balance.
2. Hyperbridge delivers `RedeemEscrow`, `onAccept` → `withdraw()` runs; on the `beneficiary.call{value: amount}("")` line, the malicious beneficiary's `receive()` fires while `_orders[commitment][token]` and `_orders[commitment][TRANSACTION_FEES]` are still non-zero.
3. From `receive()`, the malicious contract re-enters another externally reachable function that reads `_orders[commitment][...]` (e.g., a second withdrawal path, or any function relying on the stale escrow balance) to extract value beyond what it is entitled to, before the outer call finishes zeroing the balances.

Note: I could not fully trace every possible reentry target reachable from the Tron `IntentGatewayV2` `receive()` callback within this pass (the file is large and I did not exhaust all externally-callable functions), so the exact secondary call that completes the double-spend is not concretely demonstrated here — this should be verified against the full contract (and Tron's `onAccept`/host call semantics) before remediation is scoped, but the root-cause CEI violation itself is confirmed directly from the code.
