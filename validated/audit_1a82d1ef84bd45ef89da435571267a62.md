### Title
Creator fee balance is permanently frozen if the creator's address is blocklisted by USDC - ([File: packages/contracts/src/FeeVault.sol])

### Summary
`FeeVault.claim()` always pays out to `msg.sender`, and `Bonding.transferCreator` only reassigns *future* fee attribution — it never migrates an already-accrued `creatorBalance` in `FeeVault` to a new address. If a creator's address is ever blocklisted by USDC (a centrally-censorable stablecoin, exactly like the USDT/USDC blocklist scenario in the source report), the USDC `safeTransfer` inside `claim()` will permanently revert for that address, and there is no mechanism to redirect the already-pooled balance elsewhere.

### Finding Description
Fees accrue per-creator in `FeeVault.accrue`, keyed by the `creator` address passed in from `Bonding.tokenInfo(token).creator`: [1](#0-0) 

The only exit for that pooled balance is `claim()`, which hard-codes the recipient to `msg.sender` and zeroes the mapping entry before transferring: [2](#0-1) 

`Bonding.transferCreator(tokenAddress, newCreator)` exists to move the *creator role* for a token, but per the project's own documentation it only redirects **future** fee attribution — it does not touch balances already sitting in `FeeVault.creatorBalance[oldCreator]`: [3](#0-2) 

Since fees are paid out in real USDC (a token with an owner-controlled blocklist function), once a creator address is blocklisted, `IERC20(usdc).safeTransfer(msg.sender, amount)` inside `claim()` will revert for that address forever. Any `creatorBalance[creator]` already accrued at that point — and any that continues to accrue on future trades against tokens they created before `transferCreator` is called — is permanently unclaimable. There is no admin override, no "claim to arbitrary address" variant, and no way to migrate a stranded balance to a fresh, unblocked address; the funds sit in the vault's book-kept `creatorBalance` mapping indefinitely, exactly mirroring the `SolverVaults` bug class (a receiver locked in with no cancel/edit path).

### Impact Explanation
This is a permanent freeze of creator funds inside `FeeVault`, matching the "locked funds into the vault" impact class from the source report. The creator permanently loses access to already-earned protocol fees (0.25% of every buy/sell on their launched token), with no on-chain recovery path short of a contract upgrade.

### Likelihood Explanation
Likelihood is bounded by USDC's blocklist being invoked against the specific creator address, which is outside the protocol's control but a real, documented centralized-stablecoin risk (the same risk class cited in the original report). Any creator who accumulates meaningful fees and is later sanctioned/blocklisted (e.g., OFAC-listed) triggers this permanently, with no dependency on any other on-chain actor.

### Recommendation
Add a way to redirect an already-accrued `creatorBalance` to a new recipient — e.g., an owner-gated or creator-signed `claimTo(address recipient)` function, or extend `transferCerator`-equivalent logic in `FeeVault` to also migrate the outstanding `creatorBalance[oldCreator]` to `newCreator` when `Bonding.transferCreator` is called, so a creator (or the protocol, in coordination with the creator) can move stranded funds to an unblocked address before/at the time the role transfers.

### Proof of Concept
1. Creator `C` launches a token via `Zap.createToken`; trading generates buy/sell fees that accrue into `FeeVault.creatorBalance[C]` via `Zap._accrueFee` → `FeeVault.accrue`.
2. USDC's centralized admin blocklists address `C` (out-of-protocol event, same precondition as the original report).
3. `C` calls `FeeVault.claim()`. Execution reaches `$.usdc.safeTransfer(msg.sender, amount)`; USDC's transfer implementation reverts because `C` is blocklisted.
4. `Bonding.transferCreator(token, newAddress)` can reassign future attribution, but the existing `creatorBalance[C]` mapping entry (verified in `FeeVault.sol` lines 127-135) is untouched and remains permanently claimable only by the now-blocked `C`. The pooled USDC stays locked in `FeeVault` with no recovery path.

```text
    function accrue(
        address token,
        address creator,
        uint256 creatorAmount,
        uint256 protocolAmount,
        bool isBuy
    ) external onlyDepositor {
        FeeVaultStorage storage $ = _s();
        if (creatorAmount > 0) {
            if (creator == address(0)) revert ZeroAddress();
            $.creatorBalance[creator] += creatorAmount;
            $.totalAccruedCreator += creatorAmount;
            $.lifetimeCreatorEarned[creator] += creatorAmount;
        }
        if (protocolAmount > 0) {
            $.protocolBalance += protocolAmount;
            $.lifetimeProtocolEarned += protocolAmount;
        }
        if ($.usdc.balanceOf(address(this)) < $.totalAccruedCreator + $.protocolBalance) {
            revert UnderfundedAccrual();
        }
        emit FeeAccrued(token, creator, creatorAmount, protocolAmount, isBuy);
    }
```

```text
    function claim() external nonReentrant returns (uint256 amount) {
        FeeVaultStorage storage $ = _s();
        amount = $.creatorBalance[msg.sender];
        if (amount == 0) revert NothingToClaim();
        $.creatorBalance[msg.sender] = 0;
        $.totalAccruedCreator -= amount;
        $.usdc.safeTransfer(msg.sender, amount);
        emit CreatorFeesClaimed(msg.sender, amount);
    }
```

```markdown
- **Accrual:** `Zap` transfers the fee USDC to `FeeVault`, then calls `FeeVault.accrue(token, creator, creatorAmount, protocolAmount, isBuy)`. Creator attribution comes from `Bonding.tokenInfo(token).creator` (set at launch, updatable via `transferCreator`).
- **Claims:** `FeeVault.claim()` pays the caller their pooled USDC balance across every token they've launched. `FeeVault.claimProtocol()` is permissionless and pays the configured `feeTo` — anyone can trigger the payout, but funds always go to the admin-set address.
- **Lifetime counters:** `lifetimeCreatorEarned(creator)` / `lifetimeProtocolEarned` never decrement on claim, so the UI can render "total earned / claimed / claimable" consistently.
- **Router swapability:** The vault has an owner-controlled depositor allowlist. A new router is whitelisted, the old router removed, and creator balances are untouched during the transition.
- `transferCreator(tokenAddress, newCreator)` (on `Bonding`) — transfers role and future fee attribution.
```
