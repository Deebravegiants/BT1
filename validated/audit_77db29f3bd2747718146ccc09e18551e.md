## Finding

### Title
Webhook Shop Domain Header Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (and `topic`, `webhook_id`, `api_version`) values used by application webhook handlers directly from unauthenticated HTTP headers, while the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` verifies covers only the raw request body. An attacker who can obtain any single validly-signed webhook body/HMAC pair (trivially available to anyone who installs the app on their own shop) can replay that body and signature to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header, and the library will treat the request as authentically originating from that spoofed shop.

### Finding Description
`Utils::HmacValidator.validate` computes the signature strictly over `verifiable_query.to_signable_string` and compares it to the `hmac` value provided by the caller: [1](#0-0) 

For webhooks, `Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from caller-supplied HTTP headers with no cryptographic binding to the HMAC at all: [3](#0-2) 

`Registry.process` validates only the body-derived HMAC and then dispatches the handler using the unauthenticated `request.shop`: [4](#0-3) 

The identity binding broken here is: **shop-domain header used by the handler ≠ shop bound by the HMAC signature**. Since the signature is computed purely from `raw_body`, the value of the `shop-domain` header can be swapped freely by anyone submitting the HTTP request to the app's public webhook endpoint without invalidating the signature — as long as they possess *any* valid `(raw_body, hmac)` pair signed with the app's secret. Such a pair is trivially obtainable by any unprivileged internet user who installs the app on their own store: Shopify will deliver a genuine webhook (with a valid signature) to that user for their own shop, and the attacker can capture and replay it against the same endpoint, replacing the `shop-domain` header with a victim shop's domain.

### Impact Explanation
This breaks the tenant isolation the host application relies on: `WebhookMetadata.shop` is the field host apps use to look up per-shop tokens/state and to decide which merchant's data/action the webhook pertains to. A forged `shop-domain` combined with a replayed-but-validly-signed body lets an unprivileged attacker impersonate webhook traffic for a shop they do not control (e.g., trigger `app/uninstalled`, `shop/redact`, or other lifecycle/data-processing handlers attributed to a victim shop), which is a cross-tenant confusion vector — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation only requires: (1) the attacker installs the app on a shop they control to legitimately receive at least one signed webhook, and (2) the app's webhook receiving endpoint is internet-reachable (which is required by design, per the documented usage pattern where `Registry.process` is called directly from a public controller action). No access to `api_secret_key`, tokens, or the target shop is needed. This is a realistic, low-effort attack path for any internet user with an app installation.

### Recommendation
Bind the shop identity to the signed content, or otherwise cryptographically tie the `shop-domain`, `topic`, and `webhook_id` headers to the HMAC verification — e.g., include these header values as part of `to_signable_string`, or independently verify that the `shop-domain` header matches a shop for which the app holds/expects an active installation/session before dispatching to handlers. At minimum, document/require that consuming applications validate `data.shop` against known installed shops before performing privileged operations.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`. Shopify sends a legitimate webhook, e.g. for `orders/create`, to the app's public endpoint with headers:
```
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <valid HMAC of raw_body using app's api_secret_key>
x-shopify-shop-domain: attacker-shop.myshopify.com
```
2. Attacker captures this exact `raw_body` and `x-shopify-hmac-sha256` value (both are visible to them as they run their own receiving endpoint/logging, or a proxy).
3. Attacker replays the identical `raw_body` and `x-shopify-hmac-sha256` to the same app endpoint but with:
```
x-shopify-shop-domain: victim-shop.myshopify.com
```
4. `Utils::HmacValidator.validate` recomputes the HMAC over `raw_body` only — which is unchanged — so validation succeeds: [4](#0-3) 
5. The registered handler is invoked with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, even though the request never originated from Shopify on behalf of that shop. [5](#0-4)

# typed: strict

module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end

      sig { returns(String) }
      def topic
        T.cast(shopify_header("topic"), String)
      end

      sig { returns(String) }
      def shop
        T.cast(shopify_header("shop-domain"), String)
      end

      sig { returns(String) }
      def api_version
        T.cast(shopify_header("api-version"), String)
      end

      sig { returns(String) }
      def webhook_id
        T.cast(shopify_header("webhook-id"), String)
      end

      sig { override.returns(String) }
      def to_signable_string
        @raw_body
      end

      sig { returns(T::Hash[String, T.untyped]) }
      def parsed_body
        JSON.parse(@raw_body)
      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
