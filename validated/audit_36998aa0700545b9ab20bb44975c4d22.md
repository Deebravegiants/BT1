### Title
Webhook `shop`/`topic` identity spoofing via HMAC that only covers the raw body — ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw HTTP body, while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then unconditionally trusts these header-derived fields, including `shop`, when invoking the app's handler. An attacker who obtains any single valid `(raw_body, hmac)` pair for the app can replay it with an arbitrary `shopify-shop-domain` (and/or `shopify-topic`) header and have the app process it as if it came from a different, victim shop.

### Finding Description
The identity binding that should hold is:

`shop asserted in the request headers == shop whose bytes were actually HMAC-signed by Shopify`

In this gem that equality is never enforced.

- `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
- `Request#shop`, `#topic`, `#api_version`, `#webhook_id` are pulled straight from headers, none of which are part of the signed material: [2](#0-1) 
- `Registry.process` only checks the HMAC (which covers the body) and then forwards `request.shop` (and `request.topic`) unchanged into the handler's `WebhookMetadata`: [3](#0-2) 

Because Shopify signs the body with the same app-level `api_secret_key` regardless of which shop sent it, an HMAC that is valid for shop A's webhook delivery remains byte-for-byte valid when the same body is resent with shop B's domain in the `shopify-shop-domain` header (and/or a different `shopify-topic`). `HmacValidator.validate` re-derives the signature purely from `to_signable_string` (the body) and compares it to the header-provided `hmac`, with no cross-check against `shop`/`topic`: [4](#0-3) 

The gem's own documentation instructs apps to trust `data.shop` as "The shop domain of the webhook" and shows it being used directly as tenant context (`shop_domain: data.shop`) — this is the intended, documented usage pattern, not an app author's mistake: [5](#0-4) [6](#0-5) 

### Impact Explanation
This is a cross-tenant confusion vector: an attacker who has captured or otherwise obtained one legitimately-delivered `(body, hmac)` pair — no access token, no `api_secret_key`, no privileged account needed — can submit it to the app's public webhook endpoint with a forged `shopify-shop-domain` header naming any other shop (and optionally a forged `shopify-topic`). `Registry.process` will validate successfully (the body's HMAC is untouched) and hand the handler a `WebhookMetadata` claiming that data belongs to the victim shop/topic. Any app that keys per-tenant side effects (job dispatch, database writes, cache invalidation, per-shop state transitions) off `data.shop` as documented will attribute attacker-controlled/replayed data to an arbitrary tenant, which is a cross-tenant data integrity/confusion issue.

### Likelihood Explanation
Webhook endpoints are public HTTP endpoints exposed by the merchant app; no authentication is required to reach them. The only prerequisite is obtaining one valid `(body, hmac)` sample, which is inherent to how webhooks are delivered (e.g., via logs, proxies, or simply observing one's own app's inbound webhook traffic for a different install). No secret material is required to exploit the spoof of `shop`/`topic` once such a sample exists, since those fields sit entirely outside the signed payload.

### Recommendation
Bind the identity fields into the signed material, or otherwise reject requests where the claimed `shop` is not consistent with a known/expected value:
- Include `shop`, `topic`, and `webhook_id` in `to_signable_string` (this would require Shopify to sign them, so this must be coordinated with Shopify's webhook delivery format) — not feasible unilaterally in the gem.
- More practically within the gem: expose an API/require callers to supply an expected shop (e.g., resolved from the registered webhook path/shop context) and have `Registry.process` verify `request.shop` matches an install actually known to the app, or at minimum document unambiguously — beyond the current example — that `data.shop`/`data.topic` are **not** covered by the HMAC and must not be trusted without independent verification against the app's own shop/session records before use.

### Proof of Concept
1. App registers a webhook handler for topic `orders/create` and exposes `POST /callback/orders/create`, following the documented pattern:
```ruby
ShopifyAPI::Webhooks::Registry.process(
  ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
)
```
2. Shopify delivers a legitimate webhook for shop `real-shop.myshopify.com`:
```
POST /callback/orders/create
shopify-topic: orders/create
shopify-hmac-sha256: <valid-hmac-of-raw-body>
shopify-shop-domain: real-shop.myshopify.com
Body: {"id":123, ...}
```
3. Attacker captures this exact `(raw_body, shopify-hmac-sha256)` pair and replays it to the same endpoint, changing only the shop header:
```
POST /callback/orders/create
shopify-topic: orders/create
shopify-hmac-sha256: <same-valid-hmac-of-same-raw_body>
shopify-shop-domain: victim-shop.myshopify.com
Body: {"id":123, ...}   # unchanged
```
4. `HmacValidator.validate` recomputes the HMAC solely from the (unchanged) body and confirms it matches — `Errors::InvalidWebhookError` is not raised.
5. `Registry.process` builds `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: ..., ...)` and invokes the handler, which (per the documented pattern) attributes the replayed order data to `victim-shop.myshopify.com` even though Shopify never sent this webhook for that shop.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
