## Title
Quadratic-complexity DoS in GRANDPA justification ancestry verification — ([File: modules/consensus/grandpa/primitives/src/justification.rs])

### Summary
CVE-2021-2065 is a MySQL optimizer bug where an authenticated attacker submits a query the optimizer processes in a computationally excessive way, hanging the server (availability-only impact, no confidentiality/integrity loss). The closest reachable analog in Hyperbridge is `GrandpaJustification::verify_with_voter_set` in `modules/consensus/grandpa/primitives/src/justification.rs`, which, for every precommit in an attacker-supplied consensus proof, re-walks an ancestry chain from scratch — a pattern whose cost scales with `precommits × chain_length` rather than `chain_length` alone, and is reachable by any relayer submitting a single unsigned GRANDPA consensus update.

### Finding Description
`verify_with_voter_set` iterates every precommit in `self.commit.precommits` and, for each one, calls `ancestry_chain.ancestry(base_hash, signed.precommit.target_hash)`: [1](#0-0) 

`AncestryChain::ancestry` performs an unbounded, per-call linear walk backward through a `BTreeMap` of headers until it reaches `base`: [2](#0-1) 

Both `self.commit.precommits` (bounded only by the size of the authority set, which for a large relay chain can be in the hundreds to low thousands) and `votes_ancestries`/`unknown_headers` (bounded only by extrinsic/RPC payload size limits, i.e., potentially thousands of headers) are attacker-supplied via the unsigned consensus message. Because the ancestry walk is repeated once per precommit rather than computed once and reused, the total work is `O(precommits × chain_length)` hash-map lookups and vector pushes, executed synchronously inside `verify_grandpa_finality_proof` / `verify_parachain_headers_with_grandpa_finality_proof`: [3](#0-2) 

This is invoked from the ISMP GRANDPA consensus client's `verify_consensus`/`verify_fraud_proof` entry points, which are reachable by any relayer submitting a consensus update or fraud proof — no special privilege is required: [4](#0-3) 

This mirrors the MySQL optimizer bug class: a syntactically valid, unprivileged-submitted input drives the verifier into a super-linear amount of work before rejecting it, potentially stalling block execution/import for the duration of the call.

### Impact Explanation
If exploitable at scale, this can cause the runtime to spend substantially more time verifying a single malicious GRANDPA justification than an honest one of comparable byte size, potentially delaying block production/import (a hang/DoS on the node processing the extrinsic) — matching the CVSS 3.1 Availability-only impact profile of the reference CVE (C:N/I:N/A:H).

### Likelihood Explanation
Exploitability depends on parameters I could not fully verify with the tools available:
- The maximum number of precommits (bounded by authority-set size, which is chain-configuration-dependent and not obviously capped in this code).
- The maximum length of `votes_ancestries`/`unknown_headers` (I found no `MAX_HEADERS`/`MaxAncestry`-style constant in the verifier or primitives crate limiting this; the only related references are in the prover and test/tesseract crates, which are off-chain tooling, not on-chain enforcement).
- Whether extrinsic length limits or weight-metering in `pallet-ismp`/`ismp-grandpa` already bound the practical size of `votes_ancestries` and `precommits` tightly enough to make the quadratic blowup immaterial.

Because I could not confirm an explicit cap on ancestry length or precommit count in the on-chain verification path, I cannot assert with certainty that this is exploitable to a "hang" as severe as the MySQL CVE — it may already be bounded by extrinsic-size/weight limits enforced elsewhere in `pallet-ismp` that I did not locate in the indexed content.

### Recommendation
- Compute the ancestry route from `base` to the highest target once (or cache per-target results), rather than re-deriving it per precommit, to reduce the algorithm from `O(precommits × chain_length)` to `O(chain_length)`.
- Add explicit, enforced upper bounds on `votes_ancestries.len()` and `commit.precommits.len()` in `GrandpaJustification::verify_with_voter_set` (or upstream in the ISMP client) before performing any ancestry walk, analogous to the `MAX_PROOF_DEPTH` guard already used in the Pharos SPV verifier and the `MAX_EXTRINSIC_DECODE_DEPTH_LIMIT` guard in `pallet-call-decompressor`.

### Proof of Concept
I could not construct a concrete, verified PoC within this investigation because:
1. I could not confirm the exact caller-enforced bounds (if any) on `votes_ancestries` length and authority-set/precommit count for the GRANDPA client as configured in this repo's runtime.
2. Confirming actual wall-clock impact would require running the verifier with a large authority set and a long ancestry chain to measure whether the quadratic term becomes practically significant versus existing weight/extrinsic-size limits.

A conceptual PoC: construct a `FinalityProof` with `unknown_headers` forming one long linear chain (near the practical extrinsic-size limit) and a `commit` with precommits from as many authorities as the trusted authority set permits, each precommit targeting the far end of that chain — forcing `verify_with_voter_set` to re-walk the full chain once per precommit.

impl<H: HeaderT> finality_grandpa::Chain<H::Hash, H::Number> for AncestryChain<H>
where
	H::Number: finality_grandpa::BlockNumberOps,
{
	fn ancestry(
		&self,
		base: H::Hash,
		block: H::Hash,
	) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
		let mut route = vec![block];
		let mut current_hash = block;
		while current_hash != base {
			match self.ancestry.get(&current_hash) {
				Some(current_header) => {
					current_hash = *current_header.parent_hash();
					route.push(current_hash);
				},
				_ => return Err(finality_grandpa::Error::NotDescendent),
			};
		}
		Ok(route)
	}

pub fn verify_grandpa_finality_proof<H>(
	mut consensus_state: ConsensusState,
	finality_proof: FinalityProof<H>,
) -> Result<(ConsensusState, H, Vec<H256>, AncestryChain<H>), Error>
where
	H: Header<Hash = H256, Number = u32>,
	H::Number: finality_grandpa::BlockNumberOps + Into<u32>,
{
	// First validate unknown headers.
	let headers = AncestryChain::<H>::new(&finality_proof.unknown_headers);

	let target = finality_proof
		.unknown_headers
		.iter()
		.max_by_key(|h| *h.number())
		.ok_or(Error::UnknownHeadersEmpty)?;

	// this is illegal
	if target.hash() != finality_proof.block {
		Err(Error::LatestBlockMismatch)?;
	}

	let justification =
		GrandpaJustification::<H>::decode_all(&mut &finality_proof.justification[..])
			.map_err(|e| Error::DecodeJustification(alloc::format!("{e:?}")))?;

	if justification.commit.target_hash != finality_proof.block {
		Err(Error::JustificationTargetMismatch)?;
	}

	let from = consensus_state.latest_hash;

	let base = finality_proof
		.unknown_headers
		.iter()
		.min_by_key(|h| *h.number())
		.ok_or(Error::UnknownHeadersEmpty)?;

	if base.number() < &consensus_state.latest_height {
		headers
			.ancestry(base.hash(), consensus_state.latest_hash)
			.map_err(|_| Error::InvalidAncestry)?;
	}

	let finalized = headers.ancestry(from, target.hash()).map_err(|_| Error::InvalidAncestry)?;

	// 2. verify justification.
	justification
		.verify(consensus_state.current_set_id, &consensus_state.current_authorities)
		.map_err(|e| Error::JustificationVerify(e.to_string()))?;

	// Sets new consensus state, optionally rotating authorities
	consensus_state.latest_hash = target.hash();
	consensus_state.latest_height = (*target.number()).into();
	if let Some(scheduled_change) = find_scheduled_change::<H>(&target) {
		consensus_state.current_set_id += 1;
		consensus_state.current_authorities = scheduled_change.next_authorities;
	}

	Ok((consensus_state, target.clone(), finalized, headers))
}
