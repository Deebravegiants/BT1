Confirmed: `CallDispatcher.dispatch(bytes)` (`evm/src/utils/CallDispatcher.sol:44`) has **no access control** — any external account can call it directly, not just `IntentGatewayV2`/`ExtrinsicIntents`. This is the exact reachable analog of the FootiumEscrow bug class: a shared custody contract whose control/asset residency changes between "owners" (here, between successive orders/predispatch-postdispatch calls), where a spending authorization (`approve`) granted for one operation is never revoked, and the shared contract is directly reachable by anyone to weaponize that stale allowance against whatever balance the dispatcher is holding at that moment.

### Title
Unrestricted, allowance-persisting `CallDispatcher.dispatch` lets anyone drain escrowed order funds mid-flight - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher` is a single, stateless, shared singleton (`_params.dispatcher`) used by every `IntentGatewayV2`/`ExtrinsicIntents` order for predispatch and postdispatch calldata execution [1](#0-0) . Its `dispatch(bytes)` function is `external` with **no caller restriction** and executes arbitrary `Call[]` (`to`, `value`, `data`) against arbitrary targets [2](#0-1) . Legitimate order flows route `approve()` calls through it (e.g. `IERC20.approve(uniswapRouter, type(uint256).max)`) as part of predispatch/postdispatch swaps [3](#0-2) , and these approvals are never reset to zero after the swap — the contract only sweeps *token balances* back to the gateway, not allowances [4](#0-3) .

### Finding Description
This mirrors the FootiumEscrow pattern exactly: a shared asset-holding contract (escrow / `CallDispatcher`) whose "controller" changes from transaction to transaction (previous club owner → new owner; one order's predispatch call → the next order's assets in flight), while a standing operator approval granted under the earlier controller survives and is never invalidated when control changes hands. Here the exposure is worse than in the original report because `dispatch` is not even gated to the calling app — anyone can call `CallDispatcher.dispatch` directly.

Concretely:
1. A legitimate order's predispatch/postdispatch call approves a DEX router for `type(uint256).max` on some token (e.g. USDC) via the shared `CallDispatcher` [3](#0-2) .
2. `IntentsBase._execute`/`IntentGatewayV2.placeOrder` sweep the dispatcher's *token balance* back to the protocol contract after the calldata runs [5](#0-4) [6](#0-5) , but the approval to the router remains active on the dispatcher indefinitely.
3. Because `dispatch` has no access control, an attacker (or the router itself, if malicious/compromised, or anyone who can front-run) can call `CallDispatcher.dispatch` directly at any point later, executing `router.transferFrom(dispatcher, attacker, amount)` (or any call the standing approval permits) against whatever balance the dispatcher is holding at that instant — e.g. tokens transferred into the dispatcher by the *next* order's predispatch/postdispatch transfer, before the sweep call executes.
4. Since multiple orders can be in flight (predispatch transfers assets to the dispatcher, dispatches calls, then sweeps — three separate external calls in sequence, per `IntentGatewayV2.placeOrder`), an attacker who front-runs or sandwiches between the "transfer assets to dispatcher" step and the "sweep" step can call `dispatch` with a `transferFrom`/`transfer` payload authorized by a stale approval from an unrelated prior order, stealing the escrowed input tokens of a completely different user's in-flight order.

### Impact Explanation
This is a direct theft-of-funds vector reachable by any unprivileged address from a single transaction. Escrowed user input tokens or solver output tokens transiting through the shared `CallDispatcher` between the "assets transferred in" and "assets swept out" steps of `placeOrder`/`fillOrder` can be stolen by exploiting a standing approval left by an unrelated order's calldata, with no privileged role required to trigger the theft.

### Likelihood Explanation
Likelihood is high on any deployment where predispatch/postdispatch calldata routes through a DEX with `approve(router, max)` (as shown in the repo's own test, `testPostdispatchTokenSweep`) [7](#0-6) , since that max approval never expires and `CallDispatcher.dispatch` is callable by anyone with no restriction [8](#0-7) . The attacker only needs to observe a pending order transaction (mempool) that transfers assets into the dispatcher and race a `dispatch` call before the gateway's own sweep call lands in the same or a following block.

### Recommendation
- Restrict `CallDispatcher.dispatch` to only be callable by the registered gateway/dispatcher owner (`onlyGateway`/`onlyOwner` style check), removing the fully public entry point.
- Deploy a fresh, single-use `CallDispatcher` (or ephemeral clone) per order/call rather than a shared singleton, so no approval can outlive the order it was created for.
- After executing calldata that grants approvals, explicitly reset the approval to zero (`approve(spender, 0)`) as part of the same dispatch batch, in addition to sweeping balances.

### Proof of Concept
Conceptual reproduction (cannot be executed without a full fork test harness, but the vulnerable code paths are confirmed above):
1. Order A's predispatch calldata (run via `CallDispatcher.dispatch`) includes `USDC.approve(routerX, type(uint256).max)` and a swap, per the pattern already exercised in `testPostdispatchTokenSweep` [9](#0-8) .
2. After Order A completes, `USDC.allowance(dispatcher, routerX) == type(uint256).max` persists since only balances are swept, not allowances [5](#0-4) .
3. Attacker watches the mempool for Order B's `placeOrder`/`fillOrder` transaction, which transfers USDC to the same dispatcher address before the transfer-back/sweep call executes [10](#0-9) .
4. Attacker (impersonating or colluding as `routerX`, or via any call chain reaching `routerX.transferFrom`) calls `CallDispatcher.dispatch(...)` directly — no restriction exists on the caller [8](#0-7)  — with a `Call` to `USDC.transferFrom(dispatcher, attacker, balance)`, using the standing max allowance to drain Order B's escrowed USDC before the gateway's own sweep transaction executes.

        if (order.output.call.length == 0) return;

                }
            }

        }

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
