### Title
Zap trusts BounceTech LT's reported `mint()`/`redeem()` return value instead of measured balance-diff, so any mismatch DoSes buys/sells or strands funds - ([File: packages/contracts/src/Zap.sol])

### Summary
`Zap._executeBuy` and `Zap._sellInternal` treat the `ltAmount`/`baseAmount` values *returned* by the external `IBounceLeveragedToken.mint()` / `.redeem()` calls as ground truth for how much LT/USDC the contract actually received, with **no balance-before/after verification**. Every subsequent transfer, approval, and refund in the same call is sized off that unverified return value. This is the same root-cause class as the HATS finding: an external protocol call's *reported* amount is trusted and propagated into transfers that require the *actually received* amount to match, with no tolerance/balance-diff check at all.

### Finding Description
In `_executeBuy`, `ltMinted` is taken directly from the external call's return value: [1](#0-0) 

`ltMinted` is then used to size the router approval and drive `_buyOnCurve`/`_buyOnUniswapV2`: [2](#0-1) 

and to compute the LT-excess refund and the pro-rated fee, both sized off the trusted `ltMinted`/`amountInUsed` values, not off a measured LT balance: [3](#0-2) 

Symmetrically, on the sell side `grossUsdc` is taken straight from `redeem()`'s return value and used to compute `usdcOut`, which is then transferred to the user: [4](#0-3) 

There is no `balanceOf` check anywhere in `Zap.sol` around these calls — confirmed by grep, zero matches. `IBounceLeveragedToken.mint`/`redeem` are documented only by natspec comment ("USDC → LT", "LT → USDC") with no on-chain guarantee that the returned `ltAmount`/`baseAmount` equals what `Zap` actually receives: [5](#0-4) 

This is structurally identical to the reported `DLoopCoreBase._deposit()` bug: an external call's reported/expected amount is used to drive `IERC20.safeTransfer`/`forceApprove`/`transferFrom` sizing downstream, instead of the balance actually observed to have moved into the contract. In the audited report, at least a tolerance check exists (and is itself buggy); here in Zap there is no check whatsoever — any deviation between `mint()`'s/`redeem()`'s reported output and the LT's actual token movement (e.g., a BounceTech-side entry/exit fee, rounding quirk in a future LT implementation, or any other divergence between "reported minted" and "actually credited") propagates unchecked into `forceApprove`, `bonding_.buy()`'s `transferFrom`, the `IERC20(lt).safeTransfer` excess refund, or the final `$.usdc.safeTransfer(msg.sender, usdcOut)`.

### Impact Explanation
- **Buy-side DoS**: if the actual LT balance credited to `Zap` after `mint()` is even 1 wei less than the reported `ltMinted`, `forceApprove(curveRouter, ltAmount)` still succeeds, but `bonding_.buy()`'s internal `transferFrom(Zap, pair, ltAmount)` (or the post-buy `IERC20(lt).safeTransfer(msg.sender, ltExcess)`) reverts on insufficient balance, since `ltAmount`/`ltExcess` are sized off the untrusted return value, not off `IERC20(lt).balanceOf(address(this))`. This bricks every buy for that token, since `_buyInternal` is `nonReentrant` and has no fallback path.
- **Sell-side fund loss/DoS**: if `redeem()`'s actual USDC delivered to `Zap` is less than the reported `grossUsdc`, `$.usdc.safeTransfer(msg.sender, usdcOut)` reverts (DoS on sells — the *only* exit path for holders per the codebase's own documentation, since redeem is the sole atomic sell mechanism). If actual delivered is *more* than reported, the excess is permanently stranded in `Zap` with no sweep mechanism, a straightforward value leak.
- Both directions match the "Validate" criteria: concrete theft/permanent freezing of trader funds (buys bricked, or LT/USDC excess stranded with no recovery function in `Zap.sol`).

### Likelihood Explanation
Medium-High: `Zap` places unconditional trust in `IBounceLeveragedToken.mint`/`redeem` return values, which is only safe as long as BounceTech's LT implementation never diverges from an exact 1:1 match between "reported minted/redeemed amount" and "actual balance delta". `BounceTech` is an external, independently upgradeable dependency (the codebase's own docs, e.g. `docs/contracts-scope.md` and `AGENTS.md`, already flag LT-side behaviors like pausing, retirement, and buffer depletion as accepted risk categories the protocol must react to) — any BounceTech-side behavior change (fee tweak, rounding change, streaming-fee snapshot timing) that creates even a 1-wei mismatch between the returned amount and the observed balance delta triggers this class immediately and unconditionally, with no tolerance band to absorb it, unlike the audited `DLoopCoreBase` case which at least attempted one.

### Recommendation
Replace every trust-the-return-value pattern in `Zap._executeBuy`/`_sellInternal` with balance-diff verification: snapshot `IERC20(lt).balanceOf(address(this))` (or `usdc.balanceOf`) before and after `mint()`/`redeem()`, and use the observed delta — not the function's return value — to size all downstream `forceApprove`, `transferFrom`-triggering calls, and `safeTransfer` refunds. This removes the unchecked trust boundary between `Zap` and an externally-upgradeable LT contract.

### Proof of Concept
1. A hypothetical (or future) BounceTech LT `mint()` implementation returns `ltAmount = X` (matching today's `baseToLtAmount` math) but, due to an internal fee/rounding path change, actually credits `Zap` with `X - 1` wei of LT.
2. Trader calls `Zap.buy(tokenAddress, usdcAmount, 0, address(0))`.
3. `_executeBuy` sets `ltMinted = X` from the trusted return value, calls `_buyOnCurve(tokenAddress, lt, ltMinted)`, which does `IERC20(lt).forceApprove(curveRouter, X)` and `bonding_.buy(X, tokenAddress, 0, msg.sender)`.
4. `Bonding`/`Router`'s internal `transferFrom(Zap, pair, X)` reverts because `Zap`'s actual LT balance is only `X - 1`.
5. The entire `buy` transaction reverts — permanent DoS of the buy path for as long as the mismatch persists, with no code path in `Zap.sol` capable of detecting or working around it.

        // Refund LT we minted but the curve didn't consume. In the
        // floor-bump branch with supply-tight this is the meaningful
        // overshoot; on the dust-cap branch it's at most sub-wei from
        // `_computeBuy`'s round-up; on the non-cap and post-graduation
        // branches it's identically zero (`amountInUsed == ltMinted` by
        // construction). Sent to `msg.sender` — `_buyInternal` is
        // `nonReentrant`, mirroring the safe-transfer-at-end-of-flow
        // pattern used for the USDC refund below.
        uint256 ltExcess = ltMinted - amountInUsed;
        if (ltExcess > 0) {
            IERC20(lt).safeTransfer(msg.sender, ltExcess);
        }

        // Pro-rate fees against the LT actually consumed by the curve.
        // For non-cap and dust-cap buys `amountInUsed ≈ ltMinted` so
        // `effectiveBaseSpent ≈ baseToConvert` and behaviour matches the
        // pre-floor-bump formula. The floor-bump branch overshoots the
        // mint past what the curve consumes; charging fee on the minted
        // size (rather than the consumed slice) would over-charge users
        // who hit this dust band.
        uint256 effectiveBaseSpent = (amountInUsed * baseToConvert) / ltMinted;
        // Round the prorated fee up in favour of the protocol and creator, then
        // cap it at the gross fee already withheld so the refund can't underflow
        // and a full-size buy never charges more than `feeOnGross`.
        actualFee = Math.mulDiv(usdcAmount * buyFeeBps_, effectiveBaseSpent, BPS_DENOM * netUsdc, Math.Rounding.Ceil);
        if (actualFee > feeOnGross) actualFee = feeOnGross;

        // `amountInUsed` (the curve-consumed LT) is not read by the caller, so
        // repurpose this return to report the USDC the trade actually spent on
        // the launched token: the curve-consumed slice plus the retained fee.
        // Using `effectiveBaseSpent` (not `baseToConvert`) excludes any LT
        // refunded to the buyer in the floor-bump branch, so the amount tracks
        // `tokensOut`. Equals the submitted amount on every non-capped buy.
        amountInUsed = effectiveBaseSpent + actualFee;
