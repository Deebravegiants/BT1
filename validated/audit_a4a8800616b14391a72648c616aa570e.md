### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing of processed webhooks - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's authenticity solely via `Utils::HmacValidator.validate`, which HMACs only the raw request body. The `shop` value used to identify the tenant for the webhook (`request.shop`, sourced from the `x-shopify-shop-domain`/`shopify-shop-domain` header) is never included in the signed content, so it can be freely changed by anyone who can produce a request with a *valid* `(body, hmac)` pair, without invalidating the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from an HTTP header with no cryptographic binding to the HMAC: [2](#0-1) 

`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (the body only) and compares it to the `hmac` header — it never touches `shop`: [3](#0-2) 

`Registry.process` accepts the request once the (body-only) HMAC validates, then dispatches to the handler using the unauthenticated `request.shop`: [4](#0-3) 

The `shop` field is explicitly documented as the tenant identifier apps are expected to key their post-webhook actions on (e.g. looking up sessions/tokens, enqueuing per-shop jobs): [5](#0-4) 

The identity binding that should hold is: `shop authenticated by HMAC == shop used by the handler to act on data`. Because `shop-domain` sits outside the signed bytes, this equality is not enforced by the gem — bytes verified (body) != bytes acted on for tenant identity (body + unsigned header).

### Impact Explanation
Any entity capable of installing the app on their own store (a legitimate but unprivileged tenant) receives genuinely signed webhooks with a valid `(body, hmac)` pair for their own shop. Because the `shop-domain` header is excluded from the signature, that attacker can resend the same body/HMAC to the app's webhook endpoint while swapping the `x-shopify-shop-domain` header to a victim shop's domain. `Registry.process` will accept the signature as valid (it only checks the body) and hand the handler a `WebhookMetadata` whose `shop` is the attacker-chosen victim domain. Any host application following the gem's documented pattern (keying per-shop business logic, storage, or side effects off `data.shop`) will attribute attacker-controlled webhook content to the wrong tenant — a cross-tenant data/action confusion.

### Likelihood Explanation
The prerequisite (obtaining one legitimately signed webhook body+HMAC pair, e.g. by installing the app on any store) is achievable by an unprivileged internet user for any app that allows public installs, and topics with attacker-influenceable body content (e.g. topics tied to store/customer data the attacker controls) make the replayed content directly useful. No access token, `client_secret`, or privileged account is required — only the gem's own signature-verification and dispatch code path is exercised.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the signed material checked during webhook processing, or otherwise cryptographically/authoritatively verify the `shop-domain` header (e.g., reconcile it against a shop recorded for that specific `webhook_id`/session rather than trusting the header verbatim) before passing it to `WebhookMetadata`. At minimum, document prominently that `data.shop` is not verified by the HMAC and must not be trusted for tenant-scoping decisions without additional verification by the host app.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) and capture the raw POST body `B` plus the `x-shopify-hmac-sha256` header `H` sent to the callback URL — `H` is a valid HMAC of `B` under the app's `api_secret_key`, per [6](#0-5) .
2. Send a new POST to the same webhook endpoint with the identical body `B` and `x-shopify-hmac-sha256: H`, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged header unmodified [2](#0-1) , `Registry.process` validates the HMAC successfully (body unchanged) and invokes the handler with `shop: "victim.myshopify.com"` [7](#0-6) , causing the host app's handler to process attacker-controlled data under the victim's tenant identity.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
