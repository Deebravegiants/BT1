Based on my investigation, I found a valid analog to the reported vulnerability class in the `IntentGatewayV2` contracts.

### Title
Surplus split ratio can be changed by governance between order placement and fill, making surplus distribution to the order beneficiary unpredictable - (File: evm/src/apps/intentsv2/ExtrinsicIntents.sol)

### Summary
The reported bug class is that a fee percentage applied at claim time (rather than locked at order-creation time) can be changed by governance while the order/request is in flight, making the payout unpredictable for the party who initiated the transaction. `IntentGatewayV2`'s `surplusShareBps` parameter exhibits the same pattern: it is read live at fill time via `_splitSurplus`, not locked into the order's commitment at placement time.

### Finding Description
When a user places an order, only `protocolFeeBps` (and any destination-specific override) is deducted from `order.inputs` and baked into the order's commitment hash at placement time [1](#0-0) . This fee is therefore immutable for the life of that specific order — a later `UpdateParams` governance message cannot retroactively change it, since the commitment already commits to the reduced amount.

However, `surplusShareBps` — the ratio used to split solver overpayment (surplus) between the beneficiary and the protocol — is **not** committed at order placement. It is only referenced at fill time, inside `_fillCrossChain`, via `_splitSurplus(solverAmount - totalRequired, ...)`: [2](#0-1) 

The live `_params.surplusShareBps` value used by `_splitSurplus` can be changed at any time via a `UpdateParams` cross-chain governance message, processed in `onAccept`: [3](#0-2) 

Because the order's commitment hash does not encode `surplusShareBps`, an order can be placed under one surplus-split ratio and filled under a different one after a legitimate governance update lands mid-flight — mirroring exactly the reported bug class where "fees can be changed during the batch" (i.e., between order submission and order settlement).

### Impact Explanation
The order creator and the solver cannot predict, at placement time, how much of any solver overpayment (surplus) will be delivered to the beneficiary versus retained by the protocol. If governance lowers `surplusShareBps` after an order is placed but before it is filled, the beneficiary receives less than expected from surplus; if governance raises it, the protocol collects less dust than intended. While this does not directly enable theft of principal (input/output amounts are unaffected — only the surplus split ratio is subject to change), it does create unpredictable payouts for a legitimate value transfer path reachable by any user/solver pair, consistent with the "Medium" severity class of the analog report (fee changed mid-lifecycle, unpredictable to the affected party).

### Likelihood Explanation
This requires only two conditions: (1) a governance-driven `UpdateParams` message be dispatched and delivered while an order is still pending (a routine, non-malicious governance action, not requiring any admin misbehavior), and (2) a solver overpay the order's required output (a normal occurrence solvers may do to win auctions/be helpful, or that already commonly happens per the docs' description of surplus handling). Both are plausible in normal operation, not requiring any adversarial insider action, since the change is a standard published parameter change process.

### Recommendation
Snapshot `surplusShareBps` (and any other fill-time-applied fee ratio) into the order's commitment at placement time, the same way `protocolFeeBps` is baked into the reduced input amount, so that the split ratio used at fill time is guaranteed to match what the user/solver agreed to when the order was created — rather than reading the live, governance-mutable `_params.surplusShareBps` at fill time.

### Proof of Concept
1. Governance sets `_params.surplusShareBps = 10000` (100% to beneficiary) and a user places a cross-chain order.
2. Before a solver fills the order, governance dispatches an `UpdateParams` message changing `surplusShareBps` to `0` (100% to protocol), processed via `onAccept` → `_updateParams` [3](#0-2) .
3. A solver fills the order via `_fillCrossChain`, overpaying the required output amount. `_splitSurplus` now applies the new (0%) split, so the beneficiary receives none of the surplus that would have gone to them under the terms in effect when the order was placed [2](#0-1) .
4. The order's commitment hash was computed at placement with no dependency on `surplusShareBps`, so this discrepancy is undetectable/unpreventable by the user or solver at order-creation time.

**Note on confidence:** I could not view the full definition of `_splitSurplus` itself (only its call site) within the available index, nor could I fully confirm whether `IntrinsicIntents.sol` (same-chain fill path) has an identical or different exposure. A Devin session with full repository access would be needed to inspect `_splitSurplus`'s implementation and the same-chain fill path in `IntrinsicIntents.sol` to confirm the scope is identical there.
