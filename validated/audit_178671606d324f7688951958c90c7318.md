### Title
Stale user identity/key material from QR-scan-time validation is reused unchecked when finalizing biometric signup - (File: `src/plans/mod.rs`)

### Summary
`backend::user_status::UserData` (encryption public keys, `self_custody_user_public_key`, `id_commitment`, `pcp_version`) is fetched once when the user QR code is scanned, and then held unchanged in memory through the entire remainder of the signup (biometric capture, pipeline processing, fraud detection) before being used to build the Personal Custody Package (PCP) credentials that bind the freshly captured biometric data to that identity/key material. There is no re-validation of this data at the point where it is actually consumed (encryption + upload), mirroring the FraxPoolV3 bug class where a value computed at request time is trusted unchanged at execution time.

### Finding Description
`backend::user_status::request` performs the authoritative check of the user QR code and returns `UserData`, including cryptographic key material used to encrypt biometric payloads and the `self_custody_user_public_key`/`id_commitment` used for identity binding: [1](#0-0) [2](#0-1) 

This `UserData` is captured once in `verify_user_qr_code`/`handle_user_qr_code`/`scan_user_qr_code` and stored as part of `QrCodes::Both` / `ResolvedQrCodes`: [3](#0-2) [4](#0-3) [5](#0-4) 

`scan_remaining_qr_codes` only re-checks the *operator* QR code's timestamp against `operator_qr_expiration_time` (up to 23 hours by default); the `user_data` fetched at scan time is passed through unchanged whenever the cached `QrCodes::Both` branch is taken: [6](#0-5) [7](#0-6) 

Later, in `do_signup`, after a multi-second-to-minutes delay for biometric capture (`sleep(Duration::from_millis(3000))`), the full biometric pipeline, and fraud detection, this same stale `qr_codes.user_data` (via `qr_codes.try_into()`) is used, without any re-verification against the backend, to construct `personal_custody_package::Credentials` — binding the just-captured iris/face biometric data to the key material and identity commitment fetched at the earlier scan time: [8](#0-7) [9](#0-8) 

No code path re-invokes `backend::user_status::request` (or otherwise re-confirms key validity/currency) between the initial scan and the point where the PCP credentials are finalized and the biometric payload is encrypted and queued for upload via `data_uploader`: [10](#0-9) [11](#0-10) 

### Impact Explanation
The values that dynamically determine which cryptographic identity a user's biometric data is bound to (`self_custody_user_public_key`, `id_commitment`, backend encryption keys) are "locked in" at QR-scan time but consumed much later, at the moment biometric ciphertext is actually produced and uploaded. If backend-side state relevant to that user changes in the window between the QR-code validation and the PCP build (e.g., the same user is concurrently going through key rotation, account recovery, or a second signup attempt on the same or another orb changes their `UserData` server-side), orb-core will still encrypt and upload the newly captured biometric material bound to the now-stale key/identity data instead of the current one. This can result in biometric data being encrypted/committed under a key or identity commitment that no longer represents the authoritative user state at capture time — a cross-signup/misattributed-identity binding issue, analogous to a user losing correctness guarantees because a dynamically-computed value was allowed to go stale between "transaction creation" (QR scan) and "transaction execution" (PCP encryption/upload).

### Likelihood Explanation
Likelihood is moderate: the window between the QR scan and the PCP credential build spans a fixed 3-second wait plus the full biometric capture and pipeline/fraud-detection processing, which is a non-trivial amount of time under orb-core's control, and the code contains no explicit mechanism to invalidate or refresh `user_data` mid-signup. The trigger requires an external state change on the backend side within that window, which is not attacker-controlled by an unprivileged user directly, but the software has no safeguard (equivalent of `maxCollateralIn`/`maxFXSIn`) to detect or reject execution on stale identity/key data, so any legitimate backend-side change during that window is silently accepted.

### Recommendation
- **Short term:** Re-validate (or at minimum re-fetch a freshness token/hash for) `UserData` immediately before constructing `personal_custody_package::Credentials` in `do_signup`, and abort the signup if the key material/identity commitment no longer matches what the backend currently reports.
- **Long term:** Treat all backend-supplied, dynamically fetched values consumed at a later execution point (user status, operator status, config thresholds) as expiring inputs — bind them to an explicit staleness window analogous to `operator_qr_expiration_time`, and require re-validation before they are used to finalize security-relevant actions such as biometric encryption/upload.

### Proof of Concept
1. Operator/user QR flow proceeds through `scan_remaining_qr_codes`, calling `backend::user_status::request` once, capturing `UserData` (backend keys, `self_custody_user_public_key`, `id_commitment`) — see `src/plans/mod.rs:1085-1091` and `src/backend/user_status.rs:145-163`.
2. `do_signup` sleeps 3 seconds, then runs biometric capture and pipeline processing (`src/plans/mod.rs:550-562`), during which the backend's authoritative state for that user could change (e.g. key rotation, concurrent signup elsewhere).
3. Without any re-check, `qr_codes.try_into()` (`src/plans/mod.rs:1898-1938`) builds `Credentials` directly from the stale `UserData` captured in step 1.
4. `build_pcp` encrypts the just-captured biometric data using these stale keys and the result is queued for upload via `data_uploader` (`src/plans/mod.rs:599-636`, `src/agents/data_uploader.rs:169-217`), completing the signup bound to identity/key material that may no longer be current on the backend.
