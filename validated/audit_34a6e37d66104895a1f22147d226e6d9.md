## Finding: mTLS Authentication Bypass via Cache Key Omitting Client Certificate in Gateway HTTP Action Response Cache

### Title
Response cache key omits mTLS client credentials, allowing cached mTLS-authenticated responses to be served to unauthenticated requests - (File: `core/services/gateway/handlers/capabilities/v2/response_cache.go`)

### Summary
This is directly analogous to CVE-2025-46722: the underlying bug class is a cache/hash key that is built from an *incomplete* serialization of the request object, so two requests that are actually different in security-relevant respects collide on the same cache key and one identity's cached response leaks to the other. In vLLM, the missing metadata was image `size`/`mode`/`info`; in this repo, the missing metadata is the mTLS client credential (`Mtls`) used to authenticate an `OutboundHTTPRequest` to an external endpoint.

### Finding Description
The gateway's `responseCache` explicitly documents that its cache key is "a hash of the request (method, URL, headers, body, workflowOwner)" [1](#0-0) . Tests confirm this: `CacheSettings` and `WorkflowID` do not affect the hash, while `WorkflowOwner` does [2](#0-1) . Notably, `req.Mtls` (the client private key/certificate used to authenticate to the external endpoint) is not part of this documented key set.

The `Fetch` method looks up/stores entries purely by `req.Hash()` and, on a cache hit, returns the previously stored response **without invoking `fetchFn`**, i.e., without ever making the outbound HTTP call: [3](#0-2) 

The actual outbound call — including mTLS client authentication — happens inside `createHTTPRequestCallback`/`send`, which is only reached on a cache miss: [4](#0-3) 

Because `Mtls` is not part of the cache key, a request that supplies the *same* `Method`, `URL`, `MultiHeaders`, `Body`, and `WorkflowOwner` as a previously cached, mTLS-authenticated request — but supplies no `Mtls` field (or a different/invalid one) — will hit the same cache entry and receive the response that was originally obtained using the legitimate client certificate, without ever presenting valid credentials.

### Impact Explanation
This allows a requester within the gateway's trust boundary (any workflow node able to submit `OutboundHTTPRequest`/`MethodHTTPAction` messages, i.e., an unprivileged DON-side actor relative to the mTLS-protected endpoint) to obtain the content of an mTLS-authenticated response without possessing the client certificate/private key required to authenticate to that endpoint. This is a concrete authentication bypass / cross-context response disclosure: the response cache does not scope access by the credential that was required to obtain the underlying data, only by owner/method/URL/headers/body. This matches the report's core weakness class — an incomplete object serialization used as a cache/hash key causing unintended cache hits and data exposure across contexts that should be distinguished (CWE-1023/CWE-1288 analog).

### Likelihood Explanation
Exploitation requires: (1) `CacheSettings.Store`/`MaxAgeMs` enabled for the target request (attacker-influenced since these are part of the attacker-controlled `OutboundHTTPRequest` [5](#0-4) ), (2) knowledge of the target `Method`/`URL`/`MultiHeaders`/`Body`/`WorkflowOwner` combination that was previously mTLS-authenticated and cached, and (3) submission within the cache TTL window (default 10 minutes per the module README). Given workflow authors control most of these fields themselves and TTLs can be minutes, likelihood is moderate — it does not require compromising the mTLS private key at all, only replaying/matching the non-credential fields of a request.

### Recommendation
Include a fingerprint of `req.Mtls` (e.g., hash of the certificate, or simply whether Mtls is set/its identity) in `OutboundHTTPRequest.Hash()` so that requests using different (or absent) client credentials never collide on the same cache entry as an mTLS-authenticated request. More generally, the cache key must incorporate every field that affects the authentication/authorization context of the outbound call, not just the fields listed in the current comment (method, URL, headers, body, workflowOwner).

### Proof of Concept
1. Workflow step A sends an `OutboundHTTPRequest{Method: "GET", URL: "https://internal-secure.example.com/data", MultiHeaders: H, Body: B, WorkflowOwner: O, Mtls: validCert, CacheSettings: {MaxAgeMs: 600000, Store: true}}`. The gateway performs the mTLS handshake, gets a sensitive 200 response, and caches it under `Hash(Method, URL, H, B, O)` [6](#0-5) .
2. Within the TTL, workflow step B (no `Mtls` set, or an invalid one) sends `OutboundHTTPRequest{Method: "GET", URL: "https://internal-secure.example.com/data", MultiHeaders: H, Body: B, WorkflowOwner: O, CacheSettings: {MaxAgeMs: 600000}}`.
3. `Hash()` is identical to step 1's key (Mtls is excluded), so `Fetch` returns the cached sensitive response from step 1 without ever attempting the mTLS handshake [3](#0-2) .

func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}
```

func (h *gatewayHandler) send(ctx context.Context, httpReq network.HTTPRequest, req gateway_common.OutboundHTTPRequest) (*network.HTTPResponse, error) {
	if req.Mtls == nil {
		return h.httpClient.Send(ctx, httpReq)
	}

	if h.httpClientFactory == nil {
		return nil, errors.New("nil http client factory, cannot make mtls request")
	}

	// Instantiate a throwaway HTTP client with the provided Mtls client certificate provided.
	// We do this to ensure that we don't accidentally leak auth'd connections to other users.
	// Note: this isn't a DOS vector because
	// a) we have a global rate limit above which limits abuse
	// b) we apply rate limits limiting the ability of sending nodes to spam requests
	// c) we apply per-owner rate limits in the action capability in the
	// workflow node limiting the ability of users to abuse this flow by spamming Mtls requests.
	// The client enforces the mtls concurrency limit internally (on the request's
	// capped-timeout context) before delegating to the underlying transport.
	client, err := h.httpClientFactory(network.HTTPClientConfig{
		Mtls: &gateway_common.MtlsAuth{
			PrivateKey:  req.Mtls.PrivateKey,
			Certificate: req.Mtls.Certificate,
		},
		ConcurrencyLimiter: h.mtlsConcurrencyLimiter,
	})
	if err != nil {
		return nil, fmt.Errorf("failed to instantiate http client for mtls request: %w", err)
	}
```
