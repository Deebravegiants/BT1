### Title
Unchecked `U128::as_u64()` truncation in `swap_in_after_add_fee` allows draining pool reserves while paying a truncated (near-zero) input amount - (File: `program/src/processor.rs`, functions `process_swap_base_out` / `process_swap_base_out_v2`)

### Summary
`process_swap_base_out` and `process_swap_base_out_v2` compute the amount a swapper must pay (`swap_in_after_add_fee`) as a `U128` value and convert it to `u64` with the crate's `U128::as_u64()` truncating cast, without any bounds check that the `U128` value actually fits in 64 bits. This mirrors the reported bug class (unsafe/unchecked casts corrupting asset-value fields such as `interest_rate`/`bpf`): here the truncated value directly determines how many tokens are pulled from the swapper before the pool pays out `swap.amount_out`.

### Finding Description
In `swap_token_amount_base_out` (`program/src/math.rs:327-367`), for `SwapDirection::Coin2PC`:
```
let denominator = total_pc_without_take_pnl.checked_sub(amount_out).unwrap();
amount_in = total_coin_without_take_pnl.checked_mul(amount_out).unwrap().checked_ceil_div(denominator).unwrap()
``` [1](#0-0) 

`amount_out` is attacker-controlled (`swap.amount_out` from `SwapInstructionBaseOut`), and `denominator` becomes small as `amount_out` approaches `total_pc_without_take_pnl`. This makes `amount_in` (a `U128`) grow arbitrarily large — well beyond `u64::MAX` — since `total_coin_without_take_pnl` and `amount_out` are both up to `u64::MAX` in magnitude and the division by a near-zero denominator inflates the product.

This `U128` value (`swap_in_before_add_fee`) is then scaled up further by the fee factor and cast down with `.as_u64()`:
```
let swap_in_after_add_fee = swap_in_before_add_fee
    .checked_mul(amm.fees.swap_fee_denominator.into())
    .unwrap()
    .checked_ceil_div(...)
    .unwrap()
    .as_u64();
``` [2](#0-1) [3](#0-2) 

The `uint` crate's `U128::as_u64()` (via `construct_uint!` in `program/src/math.rs:11-16`) truncates to the low 64 bits rather than reverting when the value overflows `u64`, unlike the `Self::to_u64()` helper defined in the same file which uses `TryInto` and returns an `AmmError::ConversionFailure` on overflow:
```
pub fn to_u64(val: u128) -> Result<u64, AmmError> {
    val.try_into().map_err(|_| AmmError::ConversionFailure)
}
``` [4](#0-3) 

The safe `to_u64` conversion is used elsewhere (e.g. `program/src/math.rs:126-128`, `150-158`), but it is **not** used for `swap_in_after_add_fee` in either `process_swap_base_out` or `process_swap_base_out_v2`; both call the unchecked `.as_u64()` directly on the fee-adjusted `U128` value: [5](#0-4) [6](#0-5) 

Downstream, the truncated `swap_in_after_add_fee` is what is actually transferred from the user:
```
if user_source.amount < swap_in_after_add_fee { return Err(...); }
if swap.max_amount_in < swap_in_after_add_fee { return Err(...); }
...
Invokers::token_transfer(..., swap_in_after_add_fee)?;
...
Invokers::token_transfer_with_authority(..., swap.amount_out)?;
``` [7](#0-6) 

Because the slippage/balance checks (`user_source.amount < swap_in_after_add_fee`, `swap.max_amount_in < swap_in_after_add_fee`) are performed against the *already-truncated* value, they provide no protection: an attacker can choose `swap.amount_out` close to `total_pc_without_take_pnl` (or `total_coin_without_take_pnl` for `PC2Coin`) so that the true required input wraps around `u64`, and the truncated `swap_in_after_add_fee` becomes an arbitrarily small (even near-zero) number that trivially satisfies `user_source.amount >= swap_in_after_add_fee` and `swap.max_amount_in >= swap_in_after_add_fee`.

The only remaining guard is `swap.amount_out >= total_pc_without_take_pnl` (or coin equivalent), checked after the truncated value has already been computed and used: [8](#0-7) 
which only prevents draining 100% of reserves, not draining an amount just short of it while paying almost nothing.

### Impact Explanation
This is a critical accounting/solvency break reachable by any unprivileged swapper via a single `SwapBaseOut`/`SwapBaseOutV2` transaction with attacker-chosen `amount_out` and `max_amount_in`. An attacker can withdraw close to the entire pc (or coin) vault balance while transferring in a truncated, attacker-favorable (potentially near-zero) amount, resulting in direct theft/drain of pool and LP funds and insolvent pool accounting (`total_pc_without_take_pnl`/`total_coin_without_take_pnl` invariants broken).

### Likelihood Explanation
Reachable directly by any swapper supplying `amount_out` close to the pool's opposite-side reserve in a `SwapBaseOut`/`SwapBaseOutV2` instruction — no privileged signer or special build config needed. The only precondition is a pool with sufficiently large reserve values or an `amount_out` chosen close enough to the reserve to force the `U128` intermediate past `u64::MAX` after the fee-inflation multiply; given `u64::MAX` reserves are plausible for real pools and fee inflation multiplies by `swap_fee_denominator` (typically 10000), the overflow threshold is reachable well before reserves hit `u64::MAX` themselves.

### Recommendation
Replace the unchecked `.as_u64()` calls for `swap_in_after_add_fee` in `process_swap_base_out` and `process_swap_base_out_v2` with the existing checked `Calculator::to_u64(...)` helper (or an equivalent `try_into`/`u64::try_from` with explicit error), so any value that does not fit in `u64` reverts the transaction with `AmmError::ConversionFailure` instead of silently truncating.

### Proof of Concept
1. Attacker identifies (or over time causes via legitimate swaps) a pool where `total_coin_without_take_pnl` is large.
2. Attacker submits `SwapBaseOut` (`swap_direction = Coin2PC`) with `amount_out` chosen just below `total_pc_without_take_pnl` so that `denominator = total_pc_without_take_pnl - amount_out` is very small.
3. `amount_in = total_coin_without_take_pnl * amount_out / denominator` computed in `swap_token_amount_base_out` becomes a huge `U128` value.
4. `swap_in_after_add_fee = amount_in * swap_fee_denominator / (swap_fee_denominator - swap_fee_numerator)` further inflates this value past `u64::MAX`.
5. `.as_u64()` truncates it to a small/attacker-favorable `u64`.
6. Checks `user_source.amount < swap_in_after_add_fee` and `swap.max_amount_in < swap_in_after_add_fee` pass trivially since the truncated value is small.
7. `Invokers::token_transfer` pulls only the truncated (small) amount from the attacker, while `Invokers::token_transfer_with_authority` pays out the full `swap.amount_out` (near the entire pc vault) to the attacker's destination account.

    pub fn swap_token_amount_base_out(
        amount_out: U128,
        total_pc_without_take_pnl: U128,
        total_coin_without_take_pnl: U128,
        swap_direction: SwapDirection,
    ) -> U128 {
        let amount_in;
        match swap_direction {
            SwapDirection::Coin2PC => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (coin + amount_in) * (pc - amount_out) = coin * pc
                // => amount_in = coin * pc / (pc - amount_out) - coin
                // => amount_in = (coin * pc - pc * coin + amount_out * coin) / (pc - amount_out)
                // => amount_in = (amount_out * coin) / (pc - amount_out)
                let denominator = total_pc_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_coin_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
```
