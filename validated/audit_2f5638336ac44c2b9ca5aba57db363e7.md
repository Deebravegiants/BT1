### Title
Fee-token-collision + zero-relay bypass lets a swap actually spend the full pre-fee input, letting the attacker capture the flat/relay fee as extra output while stranding the Hinkal protocol fee - (File: contracts/external-actions/swaps/ExternalActionSwap.sol)

### Summary
`ExternalActionSwap.swap()` only *arithmetically* deducts `flatFee` from a local `inputAmount` variable when `feeToken == inputToken`; it never actually reserves or holds back that amount of tokens before calling `callRouter`. In `LifiExternalAction.callRouter`, the ERC20 branch grants `approveUnlimited(inputToken, router)` and then executes attacker-supplied `externalActionMetadata` directly against the router - the pulled amount is decided entirely by that calldata, not by the `inputAmount` argument. Combined with the fact that `_externalTransact` (unlike `_internalTransact`) has no "relay not paid" enforcement, an attacker can set `circomData.relay == address(0)` to skip both `sendToRelay` calls, letting the router consume the *full* pre-fee balance while the fee amounts are merely subtracted from the user's output UTXO rather than paid out - so the flat fee's value effectively flows back to the attacker as extra output tokens, and the Hinkal protocol fee is silently stranded (unpaid to anyone).

### Finding Description
The equality that should hold is:

`tokens leaving the action (into the router) == inputAmount (the fee-reduced value swap() believes it sent)`

Trace:
- `_externalTransact` (contracts/Hinkal.sol:244-256) sends the FULL `-deltaAmountChanges[0]` of `inputToken` to the action, before any fee accounting. [1](#0-0) 
- `swap()` computes `inputAmount = uint256(-deltaAmounts[0])` then, only if `feeToken == inputToken`, does `inputAmount -= flatFee` — a purely local, cosmetic reduction. [2](#0-1) 
- `callRouter` is invoked with this `inputAmount`, but in `LifiExternalAction.callRouter`'s ERC20 branch, `inputAmount` is **never used** to constrain the transfer: it just grants unlimited approval and forwards attacker-controlled `externalActionMetadata` to the fixed `router` address, which pulls whatever amount the calldata specifies via its own `transferFrom`. [3](#0-2) 
- Since the action's actual balance of `inputToken` is the full pre-fee amount, and approval is unlimited, the attacker's own off-chain-crafted router calldata can request a swap of the FULL balance (`inputAmount + flatFee`) instead of the reduced `inputAmount`. `swappedAmount = balanceAfter - balanceBefore` of `outputToken` then reflects this larger, unconstrained swap.
- Back in `swap()`, `hinkalFee` and `relayFee` are computed and paid via `sendToRelay`, which is a no-op if `circomData.relay == address(0)`. [4](#0-3) [5](#0-4) 
- `_internalTransact` explicitly reverts with `"relay not paid"` if `relay != address(0)` and no fee was actually transferred, but `_externalTransact` has no equivalent guard. [6](#0-5) 

By setting `circomData.relay = address(0)`, the attacker avoids the revert that would otherwise occur from `sendToRelay` trying to move `flatFee` worth of `inputToken` out of an action whose balance was already fully drained by the router. `totalFee` (`hinkalFee`, since `outputToken != feeToken`) is still subtracted from `amountToSendToHinkal`, but never delivered anywhere — it is simply left stranded in the action contract, while the value corresponding to the un-reserved `flatFee` (which was actually swapped along with the rest of the input) is captured in the attacker's larger output UTXO.

The `Hinkal.sol` balance-equality checks (`balanceDif == amountChanges[i] + utxoAmount`) do not catch this: the input-side equality only verifies Hinkal's own balance change matches the circuit-proven withdrawal (unaffected by what the action does with those tokens internally), and the output-side equality is satisfied by construction since `utxoSet[0].amount` is set directly to whatever `amountToSendToHinkal` the action computed. The only bound on the output is the slippage **floor** (`circomData.slippageValues[1]`), which does not prevent an inflated output. [7](#0-6) 

### Impact Explanation
The attacker receives an inflated output-token UTXO funded by the flat fee that should have gone to the relay, while the Hinkal protocol fee (`hinkalFee`) computed off the inflated `swappedAmount` is deducted from the user's credited amount but never paid to anyone — it is stranded in the `LifiExternalAction` contract with no recovery path visible in this contract. This is theft/permanent freezing of protocol and relay fees (High severity per the given rubric), repeatable on every swap transaction the attacker performs through this action.

### Likelihood Explanation
No privileged role is required. The attacker only needs to: hold funds in the shielded pool (or deposit them), set `feeStructure.feeToken == erc20TokenAddresses[0]` (input token), set `relay = address(0)`, and craft `externalActionMetadata` for the fixed router (e.g., a LI.FI diamond call) that pulls the full pre-fee balance rather than the reduced amount. All of these fields are fully attacker-controlled per the stated threat model. The only dependency is that the target router's calldata format allows specifying an arbitrary source amount, which is standard for aggregator routers such as LI.FI.

### Recommendation
Do not rely on a local `inputAmount` variable to represent the fee-reserved amount. Either: (1) physically segregate the `flatFee` portion of `inputToken` before calling `callRouter` (e.g., transfer it out to the fee sink/hold separately), so the router can never touch it regardless of approval size; and/or (2) bound the router's allowance to exactly the intended `inputAmount` instead of `approveUnlimited`; and/or (3) enforce, similar to `_internalTransact`'s `"relay not paid"` check, that fees are always accounted for in `_externalTransact`/`ExternalActionSwap.swap()` even when `relay == address(0)` (e.g., route the fee to a treasury address instead of silently skipping it), so `totalFee` can never be silently dropped from `amountToSendToHinkal` without being delivered somewhere.

### Proof of Concept
Foundry fork test plan:
1. Deploy `LifiExternalAction` with a mock `router` whose fallback, on receiving calldata, calls `IERC20(inputToken).transferFrom(action, router, IERC20(inputToken).allowance(action, router) == type(uint256).max ? balanceOf(action) : decodedAmount)` — i.e., simulate a real aggregator pulling an attacker-chosen amount encoded in `externalActionMetadata`, then transfers a proportional amount of `outputToken` back to the action based on a fixed exchange rate.
2. Register this action in `Hinkal`, generate a valid proof/`circomData` for a shielded balance where `erc20TokenAddresses = [inputToken, outputToken]`, `feeStructure.feeToken = inputToken`, `feeStructure.flatFee = F`, `relay = address(0)`, `deltaAmounts[0] = -(inputAmount + F)`.
3. Craft `externalActionMetadata` so the mock router pulls the full `inputAmount + F` balance instead of `inputAmount`.
4. Call `Hinkal.transact(...)` and assert:
   - `swappedAmount` (recovered via emitted UTXO amount / balance diff on `outputToken`) corresponds to swapping `inputAmount + F`, not `inputAmount`.
   - `amountToSendToHinkal` (the UTXO credited to attacker) exceeds the fair value computable from `inputAmount` alone (i.e., `swappedAmount_fair(inputAmount) < amountToSendToHinkal`).
   - No tokens were transferred to any relay address (since `relay == address(0)`), and `hinkalFee`-worth of `outputToken` remains stuck in the `LifiExternalAction` contract post-transaction, unclaimed.
   - Confirm the transaction does NOT revert (proving the `relay = address(0)` bypass avoids the insufficient-balance revert that would occur with `relay != address(0)`).

    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
