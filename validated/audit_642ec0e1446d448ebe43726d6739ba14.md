### Title
`limitSecretReferences` fails to restrict Secrets referenced via Projected volumes, CSI volumes, or generic ephemeral volumes - ([File: plugin/pkg/admission/serviceaccount/admission.go])

### Summary
The `Plugin.limitSecretReferences` function, which enforces that a Pod may only reference Secrets its ServiceAccount is authorized to use (`serviceAccount.Secrets`), only inspects `volume.VolumeSource.Secret`, `EnvVar.ValueFrom.SecretKeyRef`, and `EnvFromSource.SecretRef`. It never inspects `volume.VolumeSource.Projected.Sources[].Secret`, `volume.VolumeSource.CSI`, or `volume.VolumeSource.Ephemeral`, allowing a pod spec to reference an arbitrary namespace Secret through those paths and bypass the enforcement entirely.

### Finding Description
`limitSecretReferences` builds `mountableSecrets` from `serviceAccount.Secrets` and then walks `pod.Spec.Volumes`, checking only `source.Secret` (direct Secret volume) at [1](#0-0) , plus container/init-container `Env`/`EnvFrom` SecretKeyRef/SecretRef references at [2](#0-1) . It does not walk `volume.VolumeSource.Projected.Sources`, nor does it inspect `volume.VolumeSource.CSI` or `volume.VolumeSource.Ephemeral`. Consequently, a Pod spec such as `spec.volumes[].projected.sources[].secret.name=<unauthorized secret>` sails through this check untouched, even though its effect (making the kubelet fetch and mount an arbitrary namespace Secret) is functionally identical to a plain Secret volume. Since Pod creation only requires RBAC `create` on `pods` (not `get` on `secrets` — the kubelet fetches Secret content using its own credentials), this is exactly the control gap `LimitSecretReferences`/`enforce-mountable-secrets` is meant to close for direct Secret volumes but leaves open for the Projected/CSI/ephemeral paths.

### Impact Explanation
Where `LimitSecretReferences` (`--admission-control-config-file` flag) or the per-ServiceAccount `kubernetes.io/enforce-mountable-secrets` annotation is enabled as the sole boundary preventing a namespace's pods from mounting Secrets outside the ones explicitly listed on their ServiceAccount, an attacker who can create Pods (but lacks `get`/`list` on `secrets`) can still exfiltrate the contents of any Secret in the same namespace by referencing it through a Projected volume's `secret` source (or via CSI/ephemeral volume secret references), matching the "unauthorized cross-tenant/cross-boundary secret read" impact class.

### Likelihood Explanation
Requires only namespace-scoped RBAC to create Pods and requires the cluster/service account to have `LimitSecretReferences` enabled or the SA annotated with `enforce-mountable-secrets=true` — both realistic, intentional hardening configurations. The bypass is a single-request Pod creation with a Projected volume; fully repeatable and does not depend on timing or race conditions.

### Recommendation
Extend `limitSecretReferences` to walk `volume.VolumeSource.Projected.Sources` and check each `ProjectedVolumeSource.Sources[].Secret.Name` against `mountableSecrets`, and add equivalent checks (or explicit denial/opt-out policy) for `CSI` and `Ephemeral` volume sources that can indirectly reference Secrets, so the enforcement is applied consistently across all volume mechanisms capable of exposing Secret data.

### Proof of Concept
Add a table-driven test case to `plugin/pkg/admission/serviceaccount/admission_test.go` mirroring the existing "limits pod secret references" tests:
1. Set `LimitSecretReferences = true` on the `Plugin`, and register a `ServiceAccount` with `Secrets: []corev1.ObjectReference{{Name: "foo"}}`.
2. Construct a Pod with `spec.volumes = [{Name: "vol", VolumeSource: {Projected: {Sources: [{Secret: {LocalObjectReference: {Name: "bar"}}}]}}}]` where `"bar"` is NOT in the ServiceAccount's `Secrets` list.
3. Call `Admit`/`Validate` on the Pod create request.
4. Assert that admission currently **succeeds** (no error returned) despite `"bar"` not being authorized — proving the gap — then, after the fix, assert it returns an error equivalent to `"volume with secret.secretName=\"bar\" is not allowed because service account ... does not reference that secret"`.
