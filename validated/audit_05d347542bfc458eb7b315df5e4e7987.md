### Title
Pool silently accepts direct token transfers that are never credited and cannot be recovered - (File: contracts/pool/src/cache/cash.rs)

### Summary
The pool contract holds real token balances but tracks reserves only through its internal `cash` accounting ledger. Any tokens transferred directly to the pool address (e.g., by a user mistake, or a token contract transfer outside `supply`) inflate the physical balance above accounting cash. No entrypoint lets the sender — or anyone — withdraw the unaccounted excess, so the tokens are permanently locked for their sender.

### Finding Description
- The pool debits outbound transfers only against accounting `cash`: `Cache::debit_cash` calls `require_reserves(amount)`, which checks `self.cash >= amount`, not the actual token balance (`contracts/pool/src/cache/cash.rs:15-41`). `transfer_out` then moves tokens to the recipient (`cash.rs:46-53`).
- `withdraw` transfers out only `net_transfer`, an amount derived from burning supply shares — never from the contract's token balance (`contracts/pool/src/ops/withdraw.rs:111-119`, `48`).
- Correspondingly, `supply` credits cash only for the transferred amount in the operation; a raw `token::Client::transfer` to the pool address credits no shares and no cash.
- The net effect: physical balance ≥ accounting cash, with the difference stranded. There is no sweep/recover entrypoint in `contracts/pool/src` (the only recovery-adjacent op is `recapitalize`, which recapitalizes bad debt from existing resources and never refunds stray senders — searches for `recover`/`sweep`/`rescue` in pool/controller return only the unrelated swap-aggregator `sweep` and governance timelock `recovery`).

Analog mapping to the report: like `OZVotingAdaptor` accepting Ether with no receive-guard and owner-only `recoverEther`, the pool accepts unaccounted token deposits with no revert and no recovery path for the depositor.

### Impact Explanation
Permanent freezing of funds: any address that transfers the market asset directly to the pool contract loses the tokens irreversibly. They cannot be withdrawn by the sender (no shares minted), and no entrypoint extracts the excess balance to return it.

### Likelihood Explanation
Reachable by any unprivileged address via a plain token `transfer` to the pool contract address — no special privileges needed. Mistaken deposits are a well-documented occurrence; unlike EVM contracts that can revert on `receive`, a Soroban token transfer to a contract address cannot be blocked by the pool, which makes the missing recovery path the only safeguard, and it does not exist. Likelihood of occurrence over the protocol lifetime is moderate; severity Medium consistent with the source report.

Caveat: if `recapitalize` or revenue accounting ever absorbs the physical-vs-accounting surplus into protocol revenue, the tokens are still lost to the depositor — the freeze impact stands regardless.

### Recommendation
Add a permissionless or admin sweep entrypoint on the pool (and controller if it ever holds balances) that computes `token_balance - accounting_cash` for each (hub, token) book and either refunds the surplus or routes it into revenue shares — analogous to the report's suggested guard/recovery, adapted to Soroban where receive-reverts are impossible.

### Proof of Concept
1. Pool `P` for asset `A` has accounting `cash = X` and token balance `X`.
2. Unprivileged user `U` calls `token::Client(A).transfer(U, P, k)` — succeeds; balance becomes `X + k`, accounting `cash` remains `X`.
3. `U` holds zero supply shares; `withdraw`/`supply`/`recapitalize` offer no path to retrieve `k`. `withdraw` is gated by `require_reserves(net_transfer)` against `cash` (`cash.rs:15-21`), so no flow ever distributes the surplus.
4. `k` is permanently locked in `P` for `U`.
