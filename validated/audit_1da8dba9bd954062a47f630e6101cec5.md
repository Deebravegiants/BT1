### Title
Redeemable escrowed tokens released without checking ERC20 transfer return value in `IntentGatewayV2.withdraw` (Tron) - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
In the Tron-specific `IntentGatewayV2` contract, the internal `withdraw()` function releases escrowed intent tokens to a beneficiary using a raw low-level `.call()` to the token's `transfer` function, checking only that the call did not revert (`success`) but never inspecting the ABI-decoded boolean return value. Non-reverting ERC20/TRC20 tokens that signal failure by returning `false` will cause the escrow accounting to be updated and the order marked filled/refunded as if the transfer succeeded, while the beneficiary never actually receives the tokens.

### Finding Description
`withdraw()` is invoked from `onGetResponse` (via the GET-response timeout/refund flow) to release escrowed order inputs and transaction fees held by the gateway back to a beneficiary: [1](#0-0) 

For every escrowed token, the code does:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
This pattern only reverts when the low-level call itself reverts (e.g. out-of-gas, or a `require`/`revert` inside the token). Many ERC20/TRC20 tokens implement failure semantics by returning `false` instead of reverting (this is the exact bug class cited in the external report). Because the ABI-encoded return data is never decoded and checked, `success` remains `true` even though no tokens moved, and the function proceeds to:
- decrement `_orders[body.commitment][token] -= amount` (escrow accounting reduced as if paid out)
- set `_filled[body.commitment] = beneficiary` (order marked as filled/refunded)
- emit `EscrowRefunded`/`EscrowReleased`

The same unchecked-return pattern is also used for the transaction-fee payout in the same function: [2](#0-1) 

Note that elsewhere in the same contract, token intake correctly uses OpenZeppelin's `SafeERC20.safeTransferFrom`, which reverts on a `false` return value: [3](#0-2) 

but the `withdraw()` payout path was not implemented with the same safe wrapper, creating an inconsistency between the deposit-side and payout-side ERC20 handling.

### Impact Explanation
If the escrowed token returns `false` on a failed transfer instead of reverting, the escrow state is permanently decremented and the order is marked as filled/refunded, but the beneficiary's tokens are never delivered. The user's (or solver's) claim on the escrowed asset is irrecoverably lost — this is a direct, permanent loss-of-funds condition for anyone using a non-standard ERC20/TRC20 as an intent input or fee token on the Tron deployment of `IntentGatewayV2`.

### Likelihood Explanation
This path is reachable by any counterparty in the intents flow (an order placer or solver requesting a refund/withdrawal through the ISMP GET-response/refund mechanism) with no privileged access required — it triggers on every `withdraw()` call once a false-returning token is configured as an intent input or fee token. Given Tron's TRC20 ecosystem includes tokens with historically non-standard, non-reverting failure semantics (similar to mainnet USDT-style behavior), the likelihood of hitting this condition is realistic for tokens not vetted to strictly revert on failure.

### Recommendation
Replace the raw `.call()` + `success`-only check in `withdraw()` with `SafeERC20.safeTransfer` (already imported and used elsewhere in the contract), which decodes and validates the boolean return value (or treats no-return as success only per EIP-20 optional return semantics) and reverts on `false`:
```solidity
IERC20(token).safeTransfer(beneficiary, amount);
```
Apply this to both the per-token escrow release loop and the transaction-fee payout in `withdraw()`.

### Proof of Concept
1. Deploy a mock TRC20 token whose `transfer()` returns `false` on failure (e.g., due to a paused state or blacklist) instead of reverting.
2. Configure an order with this token as an input asset, escrow it via `placeOrder`.
3. Trigger a refund path that calls `onGetResponse` → `withdraw(body, true)`, with the mock token's transfer configured to return `false` (e.g. beneficiary is blacklisted).
4. Observe: `success` is `true` (the call itself doesn't revert), so execution continues; `_orders[commitment][token] -= amount` executes and `EscrowRefunded` is emitted, yet the beneficiary's token balance is unchanged — the escrowed funds are now unrecoverable since the order is marked filled and cannot be re-claimed.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }
