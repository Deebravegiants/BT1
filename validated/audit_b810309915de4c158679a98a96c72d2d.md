The report's bug class ("check something before trusting it in a loop/critical decision") maps here to a genuine identity-binding failure in webhook processing: the `shop` identity that the library hands to the host application is **not covered by the HMAC** that the library itself validates.

### Title
Webhook shop-domain spoofing via HMAC that only signs the body, not the shop header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` identity exclusively from the `X-Shopify-Shop-Domain`/`shopify-shop-domain` HTTP header, while `Utils::HmacValidator.validate` only verifies the HMAC over the raw request body. Because the shop header is never part of the signed content, an attacker who obtains one genuine, HMAC-signed webhook body (trivially available by installing the target app on their own store) can replay that exact body with a forged `shop-domain` header pointing at a victim shop. The signature still validates, and the app's webhook handler receives a `WebhookMetadata` object claiming the payload came from the victim shop.

### Finding Description
`Request#shop` reads directly from headers: [1](#0-0) 

But the signable string used for HMAC verification is only the raw body: [2](#0-1) 

`Utils::HmacValidator.validate` computes/compares the signature purely against `to_signable_string` (i.e., the body), never the headers: [3](#0-2) 

`Registry.process` trusts `request.shop` as the merchant identity once `HmacValidator.validate` passes, and forwards it unchanged to the app's handler: [4](#0-3) 

The identity binding that should hold is: `hmac(body, client_secret) == received_hmac` **and** `shop == the shop that body was signed for`. In reality only the first half is checked — the `shop` value is taken from an unauthenticated header, so the two can diverge freely.

### Impact Explanation
This breaks the shop/tenant boundary that host applications rely on when processing webhooks (e.g., updating/deleting records keyed by `shop`, or triggering the mandatory GDPR topics like `customers/redact`, `shop/redact`, `customers/data_request` also routed through this same `process` method). An attacker can cause the app to act on arbitrary shop identities using a validly-signed payload they legitimately received for their own store, effectively achieving cross-tenant data manipulation without ever needing the app's `client_secret`. Per the impact list, cross-tenant access is rated Critical.

### Likelihood Explanation
Exploitation requires no privileged credentials: any user can install the target app on their own free/dev store to receive a legitimate, correctly-signed webhook body+HMAC, then replay that body to the app's public webhook endpoint with a modified `shop-domain` header. Likelihood is High since this only depends on the app being embedded/installable and reachable, both standard conditions for Shopify apps using this gem's webhook processing.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) as part of the HMAC-signed material, or otherwise cryptographically bind the shop identity to the verified body before trusting it — e.g., validate that the `shop` header corresponds to a shop with a known, previously stored active session/token before dispatching to the handler, rather than trusting the header value outright.

### Proof of Concept
1. Install the target Shopify app on attacker-controlled store `attacker.myshopify.com`; capture a legitimate webhook delivery, e.g. `orders/create`, with its raw body and `X-Shopify-Hmac-Sha256` header (valid signature computed by Shopify over that body).
2. Replay the identical raw body and HMAC header to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `HmacValidator.validate(request)` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks the body against the HMAC.
4. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` builds `WebhookMetadata.new(... shop: request.shop ...)` using the attacker-forged `shop-domain` header, and the app's handler processes the payload as if it came from `victim.myshopify.com`.
