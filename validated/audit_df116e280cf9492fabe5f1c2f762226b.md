### Title
Webhook shop/topic identity fields are not covered by HMAC verification, allowing cross-tenant metadata spoofing - ([File: lib/shopify_api/webhooks/registry.rb], [File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates only the raw webhook body bytes via HMAC, but passes `shop`, `topic`, and `webhook_id` — all sourced from unauthenticated HTTP headers — straight to the host app's handler. Anyone who can produce (or replay) a body/HMAC pair valid under the app's `api_secret_key` can attach an arbitrary `shop-domain` header, breaking the binding between the authenticated payload and the tenant it is attributed to.

### Finding Description
`Utils::HmacValidator.validate` computes and compares an HMAC solely over `to_signable_string`, which for `Webhooks::Request` returns `@raw_body` only: [1](#0-0) 

The `hmac`, `shop`, `topic`, `api_version`, and `webhook_id` accessors are all read straight from HTTP headers, none of which participate in the signed string: [2](#0-1) 

`Registry.process` validates only this body HMAC, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` when constructing `WebhookMetadata` for the handler: [3](#0-2) 

`WebhookMetadata.shop` is a plain, unauthenticated `String` field that becomes the tenant identity the host application's handler relies on: [4](#0-3) 

The identity-binding equality that should hold is: `hmac_signed_bytes == (body, shop, topic)`; instead the implementation only enforces `hmac_signed_bytes == (body)`, while `shop` and `topic` are asserted independently and unauthenticated. This is exactly the "field acted on but not covered by the HMAC" analog called out in the rules: the merchant-identifying field (`shop`) that the handler treats as ground truth for which tenant a webhook belongs to is never part of what is cryptographically verified.

### Impact Explanation
Because the merchant identity (`shop`) is decoupled from the HMAC-authenticated content, an attacker who controls or observes one legitimate, correctly-signed webhook delivery (e.g., from their own shop A, which they can trigger arbitrarily since they administer that shop) can replay the exact same `raw_body` + `hmac-sha256` header to the app's webhook endpoint while substituting the `shop-domain` header for shop B. `HmacValidator.validate` will still succeed, because it only checks the HMAC of the untouched body against the app's own `api_secret_key` — a signature Shopify itself produced and which remains valid for that body regardless of which shop-domain header accompanies it. The host handler then processes attacker-influenced content (from shop A) under the identity of an arbitrary, unrelated shop B, corrupting per-tenant state, mixing data across tenants, or triggering business logic (e.g., data deletion, subscription changes, order processing) for a merchant the attacker does not control. This is a cross-tenant confusion vulnerability rooted entirely in this gem's own verification method, not in any host application's misuse.

### Likelihood Explanation
Exploitation requires no possession of the app's `api_secret_key`, access token, or any privileged credential — only the ability to receive one genuine webhook delivery for a shop the attacker legitimately administers (trivial, since merchants freely trigger events like `orders/create` on their own store) and the ability to POST an HTTP request to the app's public webhook endpoint with a modified `shop-domain` header, which any unprivileged internet user can do once they know the endpoint URL (commonly documented/predictable). This satisfies the "unprivileged internet user" and "no privileged credential" constraints in scope.

### Recommendation
Bind the tenant identity to the authenticated payload instead of trusting the unauthenticated header in isolation:
- Include `shop`, `topic`, and `webhook_id` in the HMAC-signable string (or otherwise cryptographically bind them to the body) so header tampering invalidates the signature.
- Alternatively/additionally, require host applications to verify that `request.shop` corresponds to a shop with an active, previously-established webhook registration/session before dispatching to a handler, and document this as a mandatory step in `Registry.process`.
- At minimum, treat `shop` in `WebhookMetadata` as unauthenticated data and clearly document that handlers must not use it as a sole tenant-authorization signal.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker-shop.myshopify.com` (shop A) and triggers any subscribed webhook topic (e.g., `orders/create`), capturing the resulting POST: headers `x-shopify-topic`, `x-shopify-hmac-sha256`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, and raw JSON body `B`.
2. Attacker computes/observes that `hmac-sha256` is valid for body `B` under the app's secret (it was legitimately produced by Shopify for shop A's webhook).
3. Attacker replays the identical raw body `B` and identical `x-shopify-hmac-sha256` value to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Webhooks::Request.new` parses headers/body normally (no cross-check between shop and hmac): [5](#0-4) 
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `raw_body` and succeeds because the body is unchanged: [6](#0-5) 
6. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker-supplied body content, believing it is authentic data from the victim's shop.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
