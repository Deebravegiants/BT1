### Title
Webhook shop-domain identity spoofing via HMAC that only covers the body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw request body. The `shop` (and `topic`/`webhook_id`) values that the handler subsequently trusts as the tenant identity are taken from HTTP headers that are **not** included in the HMAC-signed content, so they can be freely rewritten by anyone able to produce one valid (body, HMAC) pair for the shared app secret.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to the value in the `hmac` field [1](#0-0) . For webhook requests, `to_signable_string` returns only `@raw_body`: [2](#0-1) .

The `shop`, `topic`, and `webhook_id` accessors used downstream are all read straight from HTTP headers, which are excluded from the signed content entirely: [3](#0-2) .

`Registry.process` treats a passing HMAC check as sufficient authentication and then forwards the unauthenticated `shop` header value straight to the caller's handler as the trusted tenant identity: [4](#0-3) .

Because every shop that installs the app shares the same `client_secret`/`api_secret_key`, the HMAC computed over a given body is identical no matter which shop it is claimed to belong to. This breaks the identity binding: `shop header claimed == shop the HMAC actually authenticates` does not hold, since the HMAC authenticates only the *body bytes*, not the *shop* that the header claims.

An attacker who legitimately installs the app on their own store (an unprivileged action available to anyone) will receive real, validly-signed webhooks from Shopify to their own endpoint. They can capture any one `(raw_body, x-shopify-hmac-sha256)` pair from their own shop, then replay that exact body and HMAC to the app's public webhook endpoint while substituting `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) with a victim shop's domain. `HmacValidator.validate` will still succeed (since the body/HMAC pair is unmodified), and `Registry.process` will invoke the handler with `WebhookMetadata.new(shop: <victim-shop>, ...)`, causing the host application to process attacker-chosen data attributed to a shop the attacker does not control.

### Impact Explanation
This is a cross-tenant identity-confusion primitive: an attacker-controlled webhook payload (from their own store) can be delivered to the application as if it originated from a different, victim shop, purely by rewriting an unauthenticated header. Any application logic that keys off `WebhookMetadata#shop` (e.g., updating shop-scoped records, triggering shop-scoped side effects, un-installing/installing state, order/customer data ingestion) can be manipulated cross-tenant. This satisfies the "cross-tenant access" criterion because the security boundary broken is `shop authenticated` (by HMAC) vs. `shop the application trusts and acts on` (from an unsigned header).

### Likelihood Explanation
Exploitation requires only: (1) the ability to install the target app on an attacker-controlled shop (a normal, unprivileged action any Shopify merchant/developer can perform), and (2) the ability to send arbitrary HTTP requests to the app's public webhook endpoint (which is unauthenticated by design, relying solely on HMAC). No access token, `client_secret`, or privileged account is required — the attacker never needs to know the secret, they only need one valid signed sample produced by Shopify itself for their own tenant.

### Recommendation
Bind the tenant identity into the authenticated material before trusting it:
- Include `shop`, `topic`, and `webhook_id` in the HMAC-signed content (this requires coordination since Shopify controls what it signs), or
- At minimum, cross-check the `shop` header against an application-level allow-list/expected value (e.g., the shop the webhook subscription was registered for, tracked via `webhook_id`) before invoking the handler, rather than trusting the header verbatim.
- Document prominently in `Registry.process`/`WebhookMetadata` that `shop` is not covered by the HMAC and must not be treated as authenticated on its own.

### Proof of Concept
1. Install the app on attacker-owned shop `attacker.myshopify.com`; trigger any webhook topic the app subscribes to (e.g., `orders/create`) and capture the raw POST body `B` and header `x-shopify-hmac-sha256: H` sent by Shopify.
2. Replay to the app's webhook endpoint:
```
POST /webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: H
x-shopify-shop-domain: victim.myshopify.com
x-shopify-webhook-id: <any>
x-shopify-api-version: 2024-01

<B>
```
3. `Utils::HmacValidator.validate` succeeds because `H` matches the HMAC of `B` using the shared `api_secret_key` [5](#0-4) .
4. The registered handler is invoked with `WebhookMetadata` whose `shop` is `victim.myshopify.com`, even though the body `B` was generated for the attacker's own shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
