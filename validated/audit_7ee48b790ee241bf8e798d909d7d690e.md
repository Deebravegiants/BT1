### Title
Escrow refunds in the Intent Gateway can be permanently frozen when the fixed beneficiary (`order.user`) cannot receive the token - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
Like the EigenLayer `StrategyManager.thirdPartyTransfersForbidden` issue — where a withdrawal is hard-coded to go to a fixed address that later becomes unable to receive the transfer, permanently blocking withdrawal — Hyperbridge's Intent Gateway hard-codes the refund/cancel beneficiary to `order.user` with no ability to redirect it, and reverts the entire settlement if that transfer fails.

### Finding Description
`IntentsBase._withdraw()` transfers escrowed input tokens to `beneficiary` and reverts the whole call if the transfer fails, with no fallback path: [1](#0-0) 

For cross-chain cancellation initiated from the destination chain, the beneficiary of the resulting `RefundEscrow` message is always `order.user` and cannot be changed by the caller (even a third-party relayer acting on the user's behalf after expiry cannot redirect it): [2](#0-1) 

The same-chain cancel path likewise always refunds to `order.user`: [3](#0-2) 

This "fixed beneficiary, no redirect" design is explicitly documented as intentional: *"the refund always goes to order.user. An outside caller cannot redirect the refund."* [4](#0-3) [5](#0-4) 

For native-token escrow, the same fixed-beneficiary transfer uses a raw call with no recovery path if the beneficiary cannot accept ETH: [6](#0-5) 

This is the same root-cause shape as the EigenLayer report: a withdrawal path is permanently bound to one specific receiving address (there, the withdrawer set at `queueWithdrawals` time; here, `order.user` fixed at order placement/commitment time), and if an external condition later makes that specific address unable to receive the asset — a blocklist-capable ERC-20 (e.g. USDC) blacklisting `order.user`'s address after the order was placed but before settlement, or `order.user` being/becoming a contract that reverts on plain ETH receipt — every attempt to settle that specific escrow (`RefundEscrow`, `RedeemEscrow` via same-chain cancel path, or destination-triggered refund) reverts and can never succeed, because the code offers no alternate beneficiary and no split/partial-delivery fallback (contrast with `WrappedHyperFungibleTokenUpgradeable`, which explicitly re-wraps ETH into WETH if the native push fails, precisely to avoid this class of permanent lock): [7](#0-6) 

### Impact Explanation
Once the escrow-decrementing revert occurs, the whole transaction reverts (so accounting is not corrupted), but the escrowed input tokens/native value for that specific order become permanently unwithdrawable: there is no code path to change `order.user`/beneficiary, so the order can never be refunded or cancelled successfully. This is a permanent freezing of funds for the affected order, satisfying the required impact bar even though (unlike the EigenLayer bug, which can be systemic across all withdrawals of a strategy) it is scoped per-order to whichever `order.user` address becomes unable to receive the asset.

### Likelihood Explanation
Reachable directly by a normal, unprivileged user: any account can call `placeOrder`, escrow an ERC-20 that has admin-controlled blocklisting (USDC, USDT, and similar are widely used as bridge/intent inputs), and later have that same address sanctioned/blacklisted by the token issuer before the order settles or is cancelled — a realistic, externally-triggerable event outside Hyperbridge's control, mirroring exactly how EigenLayer governance could flip `thirdPartyTransfersForbidden` after a withdrawal was already queued. The same class of failure applies to any contract-type `order.user` for native-ETH orders whose receive/fallback later reverts or runs out of gas.

### Recommendation
Do not let a failed final transfer to a hard-coded beneficiary permanently deadlock the whole withdrawal:
- Add a pull-based fallback: if the direct `safeTransfer`/native `.call` to `beneficiary` fails, credit an internal claimable balance for that beneficiary (or `order.user`) instead of reverting, so the depositor/relayer can retry from a different unblocked address or claim later.
- For native ETH, mirror the existing `WrappedHyperFungibleTokenUpgradeable` pattern of falling back to a wrapped/ERC-20 delivery when the raw `.call` fails, instead of unconditionally reverting with `InsufficientNativeToken`.
- Consider allowing governance/relayer-assisted redirection of the beneficiary in a documented recovery flow when the original address is provably incapable of receiving the asset.

### Proof of Concept
1. User calls `placeOrder` with `order.user = U` and escrows USDC (`inputs`).
2. Before the order is filled, the token issuer blacklists `U` (analogous to EigenLayer setting `thirdPartyTransfersForbidden = true` on a strategy after a withdrawal was queued).
3. User (or, after expiry, any relayer) calls `cancelOrder` → `_cancelFromDest`/`_cancelSameChain`, which dispatches/executes a withdrawal with `beneficiary = order.user = U`. [2](#0-1) 
4. `_withdraw()` calls `IERC20(USDC).safeTransfer(U, amount)`, which reverts because `U` is blacklisted. [8](#0-7) 
5. The entire cancellation/refund transaction reverts every time it is retried, and there is no alternate beneficiary path — the escrowed USDC is permanently stuck.

```text
    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
```

```text
    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
```

```text
**Cancel from source chain**: The user calls `cancelOrder()` on the source chain, which dispatches a `DispatchGet` storage read request to query the destination chain's fill status. The `CancelOptions.height` must be greater than `order.deadline` — this ensures the proof is taken from a block after the order has expired. A relayer processes this request on Hyperbridge by providing storage proofs from the destination chain. If the storage slot for `_filled[commitment]` is empty (order unfilled), Hyperbridge dispatches a response back to the source chain. The `onGetResponse` handler verifies the empty proof and calls `withdraw()` to refund the escrowed tokens to the user. If the order was filled, the response contains a non-empty value and the handler reverts with `Filled()`.

![Cancel from Source Chain](./images/intent-gateway-cancel-source.svg)

**Cancel from destination chain**: Before the deadline, only the order owner can call `cancelOrder()` on the destination chain. After the deadline, anyone can cancel. The function marks the order as cancelled locally (`_filled[commitment] = user`) to prevent future fills, then dispatches a cross-chain `RefundEscrow` message back to the source chain. When the source chain receives this message via `onAccept()`, it calls `withdraw()` to refund the escrowed tokens to the user and emits `EscrowRefunded(commitment, tokens)`.
```
