### Title
Webhook `shop-domain`, `topic`, `api-version`, and `webhook-id` fields are trusted for tenant/event identification but are not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authenticated once `Utils::HmacValidator.validate(request)` succeeds, and then forwards `request.shop`, `request.topic`, `request.api_version`, and `request.webhook_id` to the app's handler as trusted, verified fields. However, the HMAC signature only ever covers the raw request body — none of these header-derived fields are included in the signed material, so an attacker who can produce (or replay) a body/HMAC pair that validates can freely set the `shop`, `topic`, `webhook-id`, and `api-version` headers to arbitrary values without invalidating the signature check.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it against `verifiable_query.hmac` [1](#0-0) 

For `ShopifyAPI::Webhooks::Request`, `to_signable_string` returns only `@raw_body`, and `hmac` is decoded from the `hmac-sha256` header — none of `shop`, `topic`, `webhook_id`, or `api_version` are part of the signed string [2](#0-1) 

`Registry.process` validates the HMAC and, on success, immediately builds `WebhookMetadata` from the unauthenticated `request.shop`, `request.topic`, `request.api_version`, and `request.webhook_id` fields and hands them to the registered handler as if the whole request (including these identity fields) had been verified [3](#0-2) 

This breaks the intended identity binding `authenticated_shop == shop_used_by_handler`. Concretely: for any webhook body an attacker can obtain a validly-signed HMAC for (e.g. by triggering a real webhook event on a shop they control, or reusing an idempotent-body webhook), they can resend the exact same `raw_body`/`hmac-sha256` pair while substituting any other value in the `x-shopify-shop-domain` (and `x-shopify-topic`/`x-shopify-webhook-id`/`x-shopify-api-version`) header, since none of these are covered by the signature comparison in `validate_signature` [4](#0-3) 

This is analogous to the report's off-by-one class of bug in that it is a binding/consistency defect between "what is verified" and "what is acted upon" — here the field acted upon (`shop`, used by host apps to key sessions/tenants) is not the field covered by the cryptographic check.

### Impact Explanation
Any application built on this gem that uses `WebhookMetadata#shop` (sourced from `request.shop`) to select the tenant/session/data scope for processing a webhook is exposed to cross-tenant confusion: an attacker with a validly HMAC-signed body (obtainable from their own shop's real webhook traffic) can cause the handler to process that body under a different shop's identity. Depending on how the host application uses `shop` (e.g., to fetch/select an access token, to write to shop-scoped storage, or to bypass mandatory-topic compliance-flow handling), this can lead to cross-tenant data confusion in the webhook pipeline.

### Likelihood Explanation
Exploitation is straightforward for any actor who has one legitimate shop/app installation and control over an HTTP endpoint that forwards headers/body to the gem's `Webhooks::Request.new` — no possession of the app's `client_secret` or another merchant's token is required, only a previously valid signed body from any shop. This satisfies the "unprivileged internet user" bar since the header fields are attacker-controlled bytes that are never covered by the signature check inside this gem.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signable string used by `Webhooks::Request#to_signable_string`, or otherwise cryptographically/contractually bind these header values to the signed body (e.g., document that `shop` must be independently verified against the caller's `X-Shopify-Shop-Domain` and installed-shop registry before use, and make `WebhookMetadata` reflect that these fields are unauthenticated unless the host validates them). At minimum, update the gem's documentation and `WebhookMetadata` to make explicit that only `body` is HMAC-verified and that `shop`/`topic`/`webhook_id`/`api_version` must not be treated as authenticated by `Registry.process` alone.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and captures (or triggers) a legitimate webhook delivery with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
2. Attacker resends a request to the app's webhook endpoint with the same body `B` and the same `hmac-sha256` header `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally forges `topic`/`webhook-id`/`api-version`).
3. `Webhooks::Request.new` parses these headers [5](#0-4) 
`Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H` [6](#0-5) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` despite the request never having been cryptographically tied to that shop [7](#0-6)

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
