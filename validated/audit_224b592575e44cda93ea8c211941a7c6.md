### Title
POA Bridge withdrawal status/hash matched only by `assetId`, misreporting completion for batched same-token withdrawals - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts, packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts)

### Summary
`PoaBridge.describeWithdrawal` (and the lower-level `waitForWithdrawalCompletion` helper in `internal-utils`) resolve the completion status/`txHash` of a specific withdrawal by matching the POA Bridge API response purely on `assetId` (`near_token_id`), ignoring the withdrawal's `index`. When a single NEAR transaction contains two or more withdrawals of the same token (same `assetId`), every one of those withdrawals resolves to the *first* matching entry returned by the API, so distinct withdrawals report the same `status`/`txHash`.

### Finding Description
`findMatchingWithdrawal` in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` (lines 409-427) does: [1](#0-0) 

and is called from `describeWithdrawal`, which is keyed only on `args.withdrawalParams.assetId`, deliberately dropping `args.index`: [2](#0-1) 

The same pattern exists in the lower-level helper used elsewhere: [3](#0-2) 

Both functions' own doc comments admit the limitation explicitly: *"Currently only matches by assetId... multiple withdrawals of the same token in a single transaction are not supported."*

The SDK's public batch-completion API, `IntentsSDK.createWithdrawalCompletionPromises` / `waitForWithdrawalCompletion` (`packages/intents-sdk/src/sdk.ts`, lines 557-609), explicitly supports arrays of `WithdrawalParams` sharing one `intentTx`, assigning each withdrawal a distinct `index` and creating one polling promise per index: [4](#0-3) 

Because `describeWithdrawal` never uses that `index` to disambiguate withdrawals of the same `assetId`, when two withdrawals of the same token are batched into one intent tx (e.g., two `ft_withdraw`/`mt_withdraw` of `nep141:usdc.omft.near` to different destination addresses in one signed payload), both index-0 and index-1 polling promises will match `Array.prototype.find`'s first hit — i.e., the *same* API record — and both will report the same `status` and the same `transfer_tx_hash`, even though the underlying withdrawals are genuinely distinct, going to different destination addresses with different amounts.

This breaks the equality "status/txHash reported for withdrawal N == the actual on-chain outcome for withdrawal N": one caller-supplied withdrawal is left permanently unmatched against its true on-chain hash, while another withdrawal's real hash gets attributed to it.

### Impact Explanation
An integrator using `IntentsSDK.waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` for a batch containing multiple same-token withdrawals will receive an incorrect `txHash` for at least one of them. Since this hash is typically used by an integrator's backend to credit/refund a user or mark a withdrawal complete, this can cause:
- A withdrawal marked "completed" against a `txHash` that actually belongs to a different destination/amount (misreport), potentially causing the integrator to credit or reconcile against the wrong on-chain transfer.
- Duplicate reporting of the same `txHash` for two logically distinct withdrawals, which can lead to double-crediting logic downstream if hash uniqueness is assumed per withdrawal.

This matches the "status or hash misreport making an integrator credit or refund twice" category (High).

### Likelihood Explanation
No malicious action is required — this is triggered purely by legitimate usage: any consumer that batches ≥2 withdrawals of the same token to different destinations in one signed intents payload (a supported, documented SDK feature) and calls `waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` will hit this. The code authors were aware of the limitation (per the inline comments), but the SDK's public batch API does not guard against or reject this exact combination, so it is reachable by unprivileged, non-malicious use of the public interface.

### Recommendation
Extend `findMatchingWithdrawal` (both in `poa-bridge.ts` and `internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`) to disambiguate withdrawals of the same `assetId` — e.g., sort/match by `(assetId, amount, destinationAddress)` tuple as suggested in the existing comment, or reject/throw when the POA API returns more matches than can be safely disambiguated for a given `index`, instead of silently returning the first match for every caller.

### Proof of Concept
1. Build a NEAR transaction with two `ft_withdraw` intents for the same token `nep141:usdc.omft.near`, to two different destination addresses/amounts, batched in one signed payload (index 0 and index 1).
2. Call `sdk.createWithdrawalCompletionPromises({ withdrawalParams: [w0, w1], intentTx })`.
3. Mock/observe the POA Bridge `getWithdrawalStatus` response containing two `COMPLETED` withdrawal records for `near_token_id: "usdc.omft.near"` with different `transfer_tx_hash` values (analogous to the existing test `"matches withdrawal by assetId, not by index"` in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.test.ts` lines 1054+, but with two entries for the *same* token).
4. Both promises resolve to the same `transfer_tx_hash` (the first array element), demonstrating that index-1's reported completion hash does not correspond to its actual on-chain withdrawal.

		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});
