Confirmed: this is a real logic bug — the transaction executor (any multisig owner submitting the execution transaction) fully controls what `transaction_context::multisig_payload()`/`inner_entry_function_payload()` returns, and this can diverge from the entry function that actually executes.

### Title
Multisig executor can decouple `transaction_context::inner_entry_function_payload()` from the entry function actually invoked, letting Move modules that authorize by this native payload be bypassed — ([File: aptos-move/framework/aptos-framework/sources/transaction_context.move])

### Summary
`TransactionMetadata::multisig_payload` (and thus `user_transaction_context::MultisigPayload.entry_function_payload`, surfaced to Move via `transaction_context::inner_entry_function_payload()`) is built directly from the **submitted transaction's own executable field**, not from the entry function that the VM actually resolves and runs.

### Finding Description
`TransactionMetadata::new` sets `multisig_payload` straight from what the caller put in the transaction payload: [1](#0-0) 

This gets converted into the native `MultisigPayload` seen by Move via `as_multisig_payload()`, which again just mirrors `self.transaction_payload` (the *declared/provided* payload on the outer txn), not the resolved one: [2](#0-1) 

Separately, the VM computes the **actually executed** payload via a completely different path: `execute_multisig_transaction` converts the submitted executable into `provided_payload` bytes and calls `multisig_account::get_next_transaction_payload`, which returns either the on-chain-stored payload (if one exists) or the provided one, and only *conditionally* enforces that they match: [3](#0-2) 

The Move-side prologue check `validate_multisig_transaction` only compares `payload` against the stored hash if `transaction.payload_hash.is_some()`, and only compares against the fully-stored payload if the feature `abort_if_multisig_payload_mismatch_enabled` is on **and** the provided payload is non-empty: [4](#0-3) 

So an executor (any owner submitting the execution transaction, who is unprivileged with respect to *this* particular approved payload beyond being a co-owner) can:
1. Have the multisig transaction proposal created with the full `EntryFunction` payload stored on-chain (`create_transaction`, i.e. `transaction.payload.is_some()`, `payload_hash.is_none()`).
2. Submit the execution transaction with an **empty executable** (`TransactionExecutableRef::Empty`), so `provided_payload` is `vec![]`.
3. `validate_multisig_transaction`'s hash check is skipped (`payload_hash` is `None`), and the payload-match check is skipped because `!payload.is_empty()` is false (payload provided is empty) — the prologue passes.
4. `get_next_transaction_payload` (executed via `GET_NEXT_TRANSACTION_PAYLOAD`) returns the on-chain-stored full payload, so the VM actually executes the originally approved entry function.
5. Meanwhile, `TransactionMetadata::multisig_payload` was built from the txn's own executable, which was `Empty`/no entry function → `transaction_context::multisig_payload()` returns `MultisigPayload { entry_function_payload: None, .. }`, and `inner_entry_function_payload()` returns `Option::None`.

A Move module that authorizes multisig-controlled actions by inspecting `transaction_context::inner_entry_function_payload()` (e.g., treating `None` as "unrestricted"/"pre-existing whitelisted flow" or comparing the declared function name to a policy) would see `None` while the multisig account's authority is actually being exercised to invoke a specific, possibly different, entry function on-chain.

### Impact Explanation
Any custody-critical Move module built on top of `transaction_context::inner_entry_function_payload()` to gate which function a multisig is allowed to invoke (e.g. only permit `withdraw`/`transfer` up to a limit, or an allow-list of entry functions callable under multisig authority) can be bypassed. The multisig account's signer capability is still exercised for the resolved on-chain payload, so an attacker (a multisig owner who can get the execution transaction included, without needing full quorum consensus on the *executed content* being distinguishable from `None`) can trick such a policy module into treating the invocation as unrestricted, letting an unapproved-looking/uncontrolled function execute under the multisig account's authority. This is a genuine custody-boundary issue: it changes what a downstream authorization module believes is being authorized versus what is actually authorized to execute with the multisig account's authority.

### Likelihood Explanation
This requires only standard multisig usage (`create_transaction` storing the full payload on-chain) plus submitting the execution transaction with an empty executable — no special privilege beyond being one of the multisig owners entitled to execute the already-approved transaction. It does not require bypassing quorum: the entry function that runs is exactly the one that was approved by quorum. The vulnerability is specifically that the *reported* native payload used by third-party Move modules for authorization purposes is wrong, not that unauthorized execution content runs. This significantly narrows real-world impact to modules that specifically rely on `transaction_context::inner_entry_function_payload()` (or `multisig_payload()`) as an authorization signal, rather than relying on the actual executed transaction.

### Recommendation
Populate `TransactionMetadata::multisig_payload` (and hence `user_transaction_context::MultisigPayload`) from the resolved payload returned by `get_next_transaction_payload` (i.e., the one that is actually executed), not from the raw submitted executable. Alternatively, always enforce `abort_if_multisig_payload_mismatch_enabled`-style hash/payload matching unconditionally (not skip when the provided payload is empty) so `transaction_context`'s view is guaranteed consistent with the executed payload.

### Proof of Concept
1. Create multisig account `M` with owners `[A, B]`, threshold 2.
2. `A` calls `multisig_account::create_transaction(M, payload=bcs(MultisigTransactionPayload::EntryFunction(sensitive_fn)))` — full payload stored on-chain.
3. Deploy a policy module `guard` whose entry point checks `transaction_context::multisig_payload()` and, when `inner_entry_function_payload()` is `None`, treats the call as unrestricted (or skips a function-name allow-list check) before letting the multisig proceed with an authorized action.
4. `B` approves; quorum reached.
5. `B` submits the execution transaction using the *empty-executable* multisig transaction form (`TransactionExecutableRef::Empty`, i.e. no `transaction_payload` on the outer `Multisig`/`TransactionPayloadInner::V1` executable).
6. Observe: `validate_multisig_transaction` prologue succeeds (hash check skipped, empty-payload match check skipped); VM resolves and executes `sensitive_fn` via `get_next_transaction_payload` under `M`'s authority.
7. Inside `sensitive_fn`'s execution context (or a module it calls that reads `transaction_context::inner_entry_function_payload()`), assert that the native payload returns `Option::None`, proving the guard module's view ("no restricted function declared") diverges from the actual invoked function `sensitive_fn`.
