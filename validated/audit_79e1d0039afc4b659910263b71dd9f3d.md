### Title
Webhook shop-domain identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, while the tenant-identifying `shop` (and `topic`/`webhook_id`/`api_version`) values are taken from unauthenticated HTTP headers that are never included in the signed material. This mirrors the reported analog class: a value that downstream logic treats as "verified/authoritative" (the wormhole chain id acted upon without being covered by any binding check) is not actually part of what was cryptographically verified.

### Finding Description
The HMAC check is performed by `ShopifyAPI::Utils::HmacValidator.validate`, which calls `verifiable_query.to_signable_string` and compares an HMAC-SHA256 computed with `Context.api_secret_key` against the supplied signature: [1](#0-0) 

For webhooks, `ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body — nothing else: [2](#0-1) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are all read directly from HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, `shopify-api-version`), none of which participate in `to_signable_string`: [3](#0-2) 

`Registry.process` validates only the HMAC (over the body) and then immediately trusts `request.shop` as the tenant identity passed to the app's handler: [4](#0-3) 

The equality that should hold but does not:
`shop_bound_by_hmac == shop_used_by_handler`

In reality: `shop_used_by_handler = header["x-shopify-shop-domain"]` (attacker-controlled bytes) while `shop_bound_by_hmac` is undefined — the HMAC binds nothing about the shop at all. Any entity capable of obtaining one valid `(body, hmac)` pair signed with the app's real `api_secret_key` — for example, the owner/operator of their own, legitimately-installed store, who receives real webhook deliveries from Shopify for topics on their own tenant — can replay that exact body and HMAC to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. Because the header is not covered by the signature, `HmacValidator.validate` still returns `true`, and `Registry.process` calls the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: attacker_controlled_json, ...)`.

### Impact Explanation
This breaks the tenant/authentication boundary the gem is documented to provide: apps are told to trust `data.shop` from `WebhookMetadata` as the origin store for the webhook payload: [5](#0-4) 

An unprivileged attacker who controls only their own Shopify store (no privileged relationship to the victim tenant, no leaked secrets) can inject attacker-controlled data into another tenant's processing pipeline by impersonating that tenant's shop domain in the header, while still passing HMAC validation. This is cross-tenant data injection/impersonation into the app's webhook processing — since apps typically use `data.shop` to select which tenant's records/session to update, this can lead to poisoning or corrupting a victim merchant's data, or performing tenant-scoped actions attributed to the wrong shop. This satisfies the "cross-tenant access" criterion.

### Likelihood Explanation
Likelihood is realistic but requires that the attacker be able to obtain at least one valid `(raw_body, hmac)` pair produced with the real `api_secret_key`. The most direct route is that the attacker operates their own store that has genuinely installed the target app; Shopify itself will then deliver real, validly-signed webhooks (body + `x-shopify-hmac-sha256`) to the app's endpoint for the attacker's own topics/events. The attacker only needs to capture one such delivery (e.g., by controlling the receiving proxy/logs for their own installed shop, which they are entitled to do) and can then freely replay the body+HMAC to the same public endpoint URL with a forged `x-shopify-shop-domain` header. No `api_secret_key`, access token, or social engineering is required — only ordinary use of the app as a legitimate merchant.

### Recommendation
Bind the tenant/topic identity into the material that is verified, or otherwise cryptographically tie the header values to the request before trusting them:
- Recommended: verify that the `shop` value in the header matches a shop for which the app has an active, previously-established session/webhook registration before dispatching to the handler, rather than trusting it unconditionally.
- Longer-term: extend `Request#to_signable_string` (or add a secondary check) that incorporates `shop`, `topic`, and `webhook_id` into a value that is verified against a per-registration or per-shop secret/nonce, so that replaying a body signed for tenant A cannot be relabeled as belonging to tenant B.
- At minimum, document prominently that `data.shop` in `WebhookMetadata` is not covered by the HMAC and must not be trusted as an unforgeable tenant identifier without additional verification (e.g., cross-checking against known, previously-registered shops).

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` (a normal, unprivileged merchant action).
2. Shopify delivers a legitimate webhook to the app's endpoint, e.g. for `orders/create`:
   - Headers: `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid HMAC over BODY>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-webhook-id: ...`
   - Body: `BODY` (JSON payload for the attacker's own order — attacker fully controls the content of this order via their own store, e.g., custom line-item names/notes containing malicious payloads).
3. Attacker captures this exact `BODY` and `x-shopify-hmac-sha256` value (they can intercept it on infrastructure they control, or via a proxy in front of their own webhook receiver).
4. Attacker crafts a new raw HTTP POST directly to the app's public webhook endpoint, reusing the identical `BODY` and `x-shopify-hmac-sha256`, but sets:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
5. `ShopifyAPI::Webhooks::Request.new` parses successfully (all three required headers present), and `Registry.process` calls `Utils::HmacValidator.validate(request)`: [6](#0-5) 
   This returns `true` because validation only checks `HMAC(BODY, api_secret_key)`, which is unchanged and still valid.
6. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: attacker_controlled_json, ...)`, causing the app to process attacker-controlled content as if it originated from `victim-shop.myshopify.com`.

Note: I was not able to locate the `WebhookMetadata` class definition itself in the indexed portion of the codebase (only its usage in `registry.rb` and `webhook_handler.rb`), so I cannot confirm from source whether any additional field-level constraints exist there; based on `docs/usage/webhooks.md` and the `Registry.process` call site, `shop` is passed through unmodified from `Request#shop`.

          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
