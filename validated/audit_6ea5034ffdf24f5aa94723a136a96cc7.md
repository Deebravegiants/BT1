### Title
Webhook `shop-domain`, `topic`, and `webhook-id` headers are trusted but not covered by the HMAC signature, enabling cross-tenant webhook spoofing/replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` exposes `shop`, `topic`, `webhook_id`, and `api_version` accessors that read directly from unauthenticated HTTP headers, while `to_signable_string` (the data actually protected by the HMAC check) is only the raw request body. [1](#0-0)  `Utils::HmacValidator.validate` verifies the HMAC exclusively against `to_signable_string`, i.e. `@raw_body`, so none of the header-derived fields participate in the signature check. [2](#0-1)  `Registry.process` trusts these unauthenticated fields once the body HMAC passes, and forwards `request.shop`, `request.topic`, and `request.webhook_id` into `WebhookMetadata`, which is delivered to the host application's handler as if it were authenticated Shopify data. [3](#0-2) [4](#0-3) 

### Finding Description
This is the same bug class as the external report: a value that is used to make an authorization/identity decision is not covered by the cryptographic check that is supposed to bind it. In `ValidatorSanityChecker`, the tolerances used inside `checkValidatorSanity` were mutable by anyone, so the check's outcome could be manipulated independent of any privileged decision. Here, the analog is an identity-binding break: **the `shop` domain a webhook is attributed to is not covered by the HMAC that "authenticates" the webhook.**

`Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac` header. [5](#0-4)  For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` — the JSON payload bytes — never the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. [6](#0-5)  This means: any request whose **body** matches a body that was legitimately HMAC-signed by Shopify secret key will pass `Registry.process`'s HMAC check, *regardless of what `shop-domain` header accompanies it*, because `process` only calls `Utils::HmacValidator.validate(request)` before trusting `request.shop`. [7](#0-6) 

The equality that should hold is: `shop authenticated by HMAC == shop the handler is told the data belongs to`. In this implementation that equality is never enforced — the HMAC binds only the body bytes, not the shop-domain header that `WebhookMetadata#shop` is populated from. [4](#0-3) 

Concretely: an attacker who legitimately installs the app on their own store (or otherwise legitimately triggers a webhook body+HMAC pair, e.g. by observing their own webhook deliveries) can replay that exact body+HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value (e.g. a victim's shop domain). The HMAC check still passes (it only validates the body), and the host application's webhook handler receives `WebhookMetadata` claiming the data came from the victim shop. [7](#0-6)  If the host app uses `data.shop` to select which tenant's session/store record to update (the documented and expected usage pattern), this causes cross-tenant data confusion driven entirely by attacker-controlled, unauthenticated header content.

### Impact Explanation
This breaks the identity binding between "the entity whose secret signed this data" and "the tenant the data is attributed to," directly enabling cross-tenant access/confusion — one of the qualifying Critical/High impacts (cross-tenant access). An attacker with no privileged credentials, and only the ability to trigger ordinary webhook events for their own shop, can make the host application process/store data under a different shop's identity.

### Likelihood Explanation
Likelihood is moderate to high in real deployments: any developer using this gem's documented `Registry.process`/`WebhookHandler#handle` flow and trusting `WebhookMetadata#shop` as an authenticated tenant identifier (which is the natural, encouraged usage per the gem's own webhook handler contract) is exposed. The attacker only needs to control an app installation on any shop to obtain a valid body+HMAC pair, then can forge headers on the replayed request since nothing in this library rejects a header/HMAC mismatch of the shop field.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header values inside the string that is HMAC-verified, or otherwise separately authenticate the `shop` claim against server-side webhook subscription state before handing it to `WebhookMetadata`. At minimum, `to_signable_string` in `lib/shopify_api/webhooks/request.rb` should incorporate the shop-domain header so `Utils::HmacValidator.validate` binds the shop attribution to the signature, matching Shopify's actual webhook HMAC computation semantics.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and triggers any webhook (e.g. `orders/create`), capturing the raw body `B` and the corresponding `x-shopify-hmac-sha256` value `H` (computed over `B` with the app's shared secret).
2. Attacker sends a new HTTP request to the app's webhook endpoint with:
   - body = `B`
   - `x-shopify-hmac-sha256` = `H`
   - `x-shopify-shop-domain` = `victim-shop.myshopify.com`
   - `x-shopify-topic`, `x-shopify-webhook-id` unchanged or forged.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(B, secret) == H` — this succeeds. [8](#0-7) [9](#0-8) 
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the attacker-supplied `shop-domain` header, and invokes the host app's handler with `data.shop == "victim-shop.myshopify.com"` despite the data actually originating from `attacker.myshopify.com`. [10](#0-9)

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
