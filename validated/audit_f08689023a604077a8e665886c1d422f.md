### No vulnerability found for this question.

Analysis: for `feeInclusive: false`, both `_estimateWithdrawalFee` and `createWithdrawalIntents` in `packages/intents-sdk/src/sdk.ts` compute `actualAmount = withdrawalParams.amount` (no fee subtraction occurs in this branch) — the ternary `args.withdrawalParams.feeInclusive ? amount - fee.amount : amount` only subtracts the fee when `feeInclusive` is `true`. [1](#0-0) [2](#0-1) 

Both the estimation path and the withdrawal-creation path apply the identical `actualAmount` formula and pass it to `bridge.validateWithdrawal`'s min-amount check, so there is no divergence between "min check runs against `actualAmount`" vs "fee-less amount elsewhere" — they are the same value when `feeInclusive` is `false`. The premise that an amount above `min_withdrawal_amount` becomes "below it after fee subtraction" cannot occur in the `feeInclusive: false` branch since no subtraction happens. [3](#0-2) 

Separately, `PoaBridge.createWithdrawalIntents` adding `relayerFee` on top of `amount` when `feeInclusive` is `false` is by design: destination receives `amount`, and the intent debits `amount + relayerFee`, matching the invariant `sum(debits) == amount + fee`. [4](#0-3) 

The only way to create an actual mismatch between the displayed `feeEstimation.amount` and the `relayerFee` actually applied would require the caller to supply an internally-inconsistent `feeEstimation` object (where `underlyingFees.PoaBridge.relayerFee` differs from `feeEstimation.amount`) via the documented `feeEstimation` escape hatch in `signAndSendWithdrawalIntent`. Since that same caller is also the one who must provide the `intentSigner` to authorize the resulting debit, this is self-inflicted misuse of a documented parameter rather than an attack on an unprivileged third party, which the rules explicitly exclude ("reject anything requiring the integrator to deliberately misuse a documented escape hatch"). [5](#0-4) [6](#0-5)

export function getUnderlyingFee<
	R extends keyof UnderlyingFees,
	K extends keyof NonNullable<UnderlyingFees[R]>,
>(
	feeEstimation: FeeEstimation,
	route: R,
	feeKey: K,
): NonNullable<UnderlyingFees[R]>[K] {
	const routeFees = feeEstimation.underlyingFees?.[route];
	if (routeFees === undefined) {
		throw new Error(
			`Missing underlying fees for route "${String(route)}". Fee estimation must populate underlyingFees before creating withdrawal intents.`,
		);
	}
	return (routeFees as NonNullable<UnderlyingFees[R]>)[feeKey];
}
