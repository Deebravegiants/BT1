### Title
Unchecked ERC20 return value in escrow withdrawal and dust sweep allows silent-failing tokens to be marked as delivered - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.withdraw()` and the `SweepDust` handler in `onAccept()` release escrowed ERC20 tokens using a raw low-level `.call` to `transfer`, checking only that the call itself did not revert (`success`) and never decoding/validating the returned `bool`. Any ERC20 that follows the standard's permitted behavior of returning `false` on failure instead of reverting will cause the contract to treat the transfer as successful, decrement escrow accounting, and emit success events — while the beneficiary never actually receives the funds.

### Finding Description
In `withdraw()`, escrowed tokens are released with: [1](#0-0) 

and outstanding transaction fees are released the same way: [2](#0-1) 

The `SweepDust` request kind, handled in `onAccept`, has the identical pattern: [3](#0-2) 

In all three cases, `success` only reflects whether the external call reverted, not whether the token's `transfer` function actually returned `true`. Non-compliant ERC20 tokens (e.g., older/broken implementations) are permitted by the ERC20 spec to return `false` instead of reverting on transfer failure. For such tokens, `token.call(...)` returns `(true, encodedFalse)`, so `success` is `true`, and the code proceeds as if the transfer succeeded.

This is the exact bug class described in the referenced report: `transferFrom`/`transfer` calls whose boolean return value is not checked, letting failed transfers be treated as successful.

Immediately after the unchecked transfer in `withdraw()`, escrow state is unconditionally decremented: [4](#0-3) 

and `_filled[body.commitment]` is set at the top of the function regardless of transfer outcome: [5](#0-4) 

This means once the "transfer" call returns without reverting, the commitment is marked filled/refunded and the escrow balance is wiped, even though the beneficiary never received the tokens.

Note that other transfer paths in the same file and in the sibling `evm/src/apps/IntentGatewayV2.sol` correctly use `IERC20.safeTransferFrom`/`safeTransfer` from OpenZeppelin's `SafeERC20`, e.g.: [6](#0-5) 
which reverts on a `false` return. The `withdraw()` and `SweepDust` paths are inconsistent with this pattern and use the raw, unchecked `.call` instead.

### Impact Explanation
This is reachable by any relayer/solver delivering a cross-chain `RedeemEscrow`, `RefundEscrow`, or `SweepDust` message that resolves to a token which returns `false` on failed transfer (rather than reverting) — for example due to a paused token, blacklist, or non-standard implementation. When that occurs:
- The escrow accounting (`_orders[commitment][token]`) is permanently zeroed out and `_filled[commitment]` is set, so the beneficiary has no further recourse to claim the funds — this is a **permanent freezing/loss of user funds** inside the escrow.
- `SweepDust` similarly finalizes dust distribution and emits `DustSwept` even though no tokens moved, silently misreporting protocol state.

This affects real user funds locked in intent escrows and is directly reachable from the intended cross-chain message-delivery flow (an `onAccept` call authenticated as coming from the counterpart gateway/hyperbridge), not requiring any privileged or malicious actor beyond a token that doesn't strictly follow the "revert on failure" convention.

### Likelihood Explanation
Likelihood depends on a non-standard/failing ERC20 being configured as an intent input/output token, which is plausible given intent-gateway systems are designed to support arbitrary tokens across chains, some of which historically return `false` rather than reverting (well documented as the "missing return value" / non-compliant `transfer` class of bugs, the same class covered by the referenced report).

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` + `success`-only check in `withdraw()` (both the token loop and the fee-token branch) and in the `SweepDust` handler with OpenZeppelin's `SafeERC20.safeTransfer`, consistent with the rest of the codebase (e.g., the `safeTransferFrom`/`safeTransfer` calls already used elsewhere in this file), so that a `false` return value causes a revert instead of being silently accepted as success.

### Proof of Concept
1. Configure/escrow an ERC20 token whose `transfer` implementation returns `false` on failure instead of reverting (e.g., due to being paused or the recipient being blacklisted, as with some real-world stablecoins/tokens).
2. Have hyperbridge deliver an authenticated `RedeemEscrow` (or `RefundEscrow`) request to `onAccept`, invoking `withdraw()` for that token/commitment.
3. Inside `withdraw()`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `(true, abi.encode(false))` because the low-level call itself doesn't revert.
4. `success` is `true`, so `TransferFailed` is never triggered; `_orders[body.commitment][token] -= amount` executes and `_filled[body.commitment]` is already set, finalizing the withdrawal.
5. The beneficiary's token balance is unchanged (transfer failed), but the escrow is marked as released — the funds are permanently unrecoverable through this contract's accounting. [7](#0-6)
