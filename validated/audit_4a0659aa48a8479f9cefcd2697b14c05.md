### Title
Webhook `shop-domain` (and other Shopify headers) are not covered by the HMAC signature, allowing tenant-spoofed webhook delivery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes/validates the HMAC only over the raw request body, but derives the tenant-identifying `shop` attribute (plus `topic`, `webhook_id`, `api_version`) from HTTP headers that are completely outside the signed payload.

### Finding Description
`Utils::HmacValidator.validate` verifies `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)` [1](#0-0) . For webhooks, `to_signable_string` returns only `@raw_body` [2](#0-1) . The `shop` value used to attribute the webhook to a tenant is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the HMAC-signed body [3](#0-2) . `Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e., body integrity) before forwarding `request.shop` unchanged into `WebhookMetadata` that is handed to the app's registered handler [4](#0-3) .

The broken identity binding is: `shop-domain header == authenticated tenant`, when in fact only `raw_body == HMAC(raw_body, client_secret)` is enforced; the header is fully attacker-controlled independent of the signature.

### Impact Explanation
Any party capable of obtaining one genuine `(raw_body, hmac)` pair signed by Shopify — trivially available to any merchant who installs the app on their own store and receives a legitimate webhook to their own endpoint — can replay that exact body/HMAC pair while substituting an arbitrary `shopify-shop-domain` header value naming a different, victim shop. Because the gem never binds the shop header into the signature check, the request still passes `HmacValidator.validate`, and the host application (following the gem's documented pattern of trusting `WebhookMetadata.shop`) will process the payload as if it originated from the victim tenant. In multi-tenant apps that key session/data lookups off `WebhookMetadata.shop`, this enables cross-tenant data confusion/injection under another merchant's identity.

### Likelihood Explanation
Any user who can install the app as a merchant (an "unprivileged internet user" relative to other tenants) can obtain a valid signed webhook body/HMAC for their own shop and then relay it to the app's webhook endpoint with a forged shop header, requiring no access to `api_secret_key` or any victim credentials.

### Recommendation
Include the shop domain (and other trust-critical headers such as topic/webhook_id) in the signable string used for HMAC verification, or otherwise cryptographically bind the header-derived `shop` value to the signed body before it is passed to `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a legitimate webhook POST with a valid `x-shopify-hmac-sha256` for some `raw_body`.
2. Attacker replays the identical `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because only `raw_body` is signed/verified [5](#0-4) .
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` even though the payload was never actually issued by/for that shop [6](#0-5) .
