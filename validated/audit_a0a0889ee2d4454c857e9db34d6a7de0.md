Webhook `shop` field is not covered by the HMAC, allowing cross-tenant impersonation via replayed webhook body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the HMAC over the raw request body only, while the `shop` (and `topic`, `webhook_id`) values come from HTTP headers that are entirely excluded from the signed content. The gem's own documentation instructs host apps to trust `data.shop` from `WebhookMetadata` as the tenant identity for the event. Because the header is not bound to the signature, a user who legitimately installs the app on their own shop (and therefore receives genuine webhook deliveries with valid HMACs over the body) can capture one such request and replay it against the app's webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop, while the HMAC check still passes.

### Finding Description
`Request#hmac` reads the signature from the `hmac-sha256` header and `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate_signature` computes the HMAC purely over `verifiable_query.to_signable_string` (i.e., the raw body) and compares it to the received signature: [2](#0-1) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers, independent of the signed payload: [3](#0-2) 

`Registry.process` only checks that the HMAC over the body is valid, then constructs `WebhookMetadata` directly from these unauthenticated header values and hands it to the app's handler: [4](#0-3) [5](#0-4) 

The gem's own documentation tells integrators to use `data.shop` as the shop-domain identity for downstream processing (e.g., enqueuing per-tenant jobs), reinforcing that this field is treated as trusted/authenticated: [6](#0-5) 

**Broken identity binding (as an equality):**
`shop authenticated by HMAC` should equal `shop delivered to the handler`, but in this implementation:
`HMAC-verified bytes = raw_body` ≠ `shop identity used by handler = header["x-shopify-shop-domain"]`

Before the attack: attacker installs the app on their own shop `attacker.myshopify.com` and Shopify legitimately delivers a webhook (e.g. `orders/create`) with a valid `x-shopify-hmac-sha256` computed over the body using the app's real `api_secret_key`.

After the attack: attacker POSTs the exact same raw body and HMAC header to the app's webhook endpoint, but substitutes `x-shopify-shop-domain: victim-shop.myshopify.com`. `HmacValidator.validate` still returns `true` because it only checks the body bytes, which are unchanged. `Registry.process` proceeds to invoke the handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"` even though the payload never originated from, and has nothing to do with, that shop.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing. Any host application that follows the documented pattern of using `data.shop` to scope database writes, background jobs, or cache invalidation for a specific merchant can be manipulated into applying attacker-supplied (though structurally valid) webhook data under a victim shop's identity, i.e., cross-tenant access/data corruption without ever needing the victim's credentials. This satisfies the "Critical - cross-tenant access" bar, since the attacker only needs to be an unprivileged app installer on any shop (including their own) to forge the tenant attribution of an otherwise-authentic webhook.

### Likelihood Explanation
Likelihood is meaningful but not trivial: the attacker needs a legitimate app install to obtain at least one genuine `(body, hmac)` pair, and the practical damage depends on what body content the handler needs (e.g., an `orders/create` webhook, which the attacker fully controls the content of on their own shop). Since webhook payload content is attacker-controlled for their own shop, and only the shop-domain header needs to be swapped, exploitation requires no cryptographic secret and no interaction with Shopify beyond a normal app install — this is straightforward for anyone who can install the app.

### Recommendation
Bind the shop domain (and ideally topic/webhook id) into the HMAC-verified content, or independently verify that the `shop` header value corresponds to a shop for which the request's HMAC/API secret combination is valid (e.g., look up the expected secret per-shop and/or cross-check the shop domain against session/token issuance records) before trusting `WebhookMetadata#shop`. At minimum, document prominently that `data.shop` is unauthenticated header data and must not be used as an unverified tenant key by host applications, or extend `to_signable_string` to include the header fields so `HmacValidator` binds them cryptographically.

### Proof of Concept
1. Install the app on `attacker.myshopify.com`; trigger `orders/create` to receive a genuine webhook POST with headers `x-shopify-hmac-sha256: <valid_hmac>`, `x-shopify-shop-domain: attacker.myshopify.com`, and some raw JSON body `B`.
2. Resend that exact same body `B` and the same `x-shopify-hmac-sha256` value to the app's webhook endpoint, but replace the header with `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` passes because it only hashes `B`.
4. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` builds `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: B, ...)` and calls the handler, which — per the documented usage pattern — will process/enqueue work attributed to `victim-shop.myshopify.com` using attacker-controlled body content.
