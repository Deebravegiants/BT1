### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook only by validating the HMAC over the raw request body, then unconditionally trusts the `shop`, `topic`, and `webhook_id` values taken from unauthenticated HTTP headers when building the `WebhookMetadata` handed to the app's handler. Because the HMAC signature never covers these headers, the `shop` value used to attribute the webhook to a tenant is not bound to the cryptographic proof that the payload originated from Shopify.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cross-check against the signed content: [1](#0-0) [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` and, once that passes, forwards `request.shop` straight into `WebhookMetadata` without any additional binding check: [3](#0-2) 

`HmacValidator.validate` only ever calls `verifiable_query.to_signable_string`, i.e. only the body bytes, against `Context.api_secret_key`: [4](#0-3) 

The `api_secret_key` used to compute this HMAC is the app's single global client secret — it is not shop-specific. Any merchant who installs the app (an ordinary, unprivileged action, not requiring any victim credential) will legitimately receive webhooks whose body+HMAC pair is valid under that same global secret. The `shop-domain` header that identifies which tenant the event belongs to is never part of that signed content.

The identity binding that should hold is:
`shop-domain used to attribute the event == shop-domain covered by the HMAC-verified bytes`

but the actual binding enforced by the code is only:
`HMAC(body) verified == body unchanged`,
with `shop` taken from an entirely separate, unauthenticated channel (the header).

### Impact Explanation
An attacker who has installed the app on their own store (which is an ordinary, unprivileged flow available to any internet user, not a "privileged account" in the sense excluded by scope) can capture one of their own genuine, validly-HMAC-signed webhook deliveries and resend it to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to a victim merchant's domain. Because `Utils::HmacValidator.validate` only checks the body against the shared secret, the forged request passes validation, and the host application's webhook handler is invoked with `WebhookMetadata#shop` equal to the victim's shop and the attacker-controlled body/topic. Any host application that uses `data.shop` to key merchant records (e.g. processing `app/uninstalled`, `shop/update`, `customers/data_request`, order/customer webhooks) can be manipulated into attributing attacker-controlled event data to an arbitrary victim tenant — a cross-tenant integrity violation.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the app on a shop they control (a normal unprivileged action) and send a crafted HTTP request with a valid HMAC/body pair they legitimately received, plus an altered shop header, to the app's public webhook endpoint. No access to the victim's credentials, the app's `client_secret`, or any privileged account is required.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is authenticated, e.g. by including these header values in the signable string used by `Utils::HmacValidator`, or by requiring host apps to independently verify that the `shop-domain` header matches an actively installed/authorized shop before trusting `WebhookMetadata#shop`. At minimum, document clearly that `request.shop` is unauthenticated and must not be trusted for tenant attribution without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com`, completing normal OAuth.
2. Attacker triggers any webhook event (e.g., updates a product) and captures the resulting POST body and its `X-Shopify-Hmac-Sha256` header — both valid under the app's global `api_secret_key`.
3. Attacker resends the exact captured body and HMAC header to the app's webhook endpoint, but replaces `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because the body is unchanged, and dispatches the handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, i.e. the app now processes attacker-controlled data as if it came from the victim's shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
