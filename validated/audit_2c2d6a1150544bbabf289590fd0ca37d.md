### Title
Same-asset batch withdrawals report the wrong destination tx hash/status via POA bridge index-blind matching - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` matches withdrawal status purely by `assetId`, ignoring the `index` that uniquely identifies each withdrawal in a batch. When `sdk.processWithdrawal`/`createWithdrawalCompletionPromises` is used with multiple withdrawals of the **same** asset in one intent (e.g., two USDT withdrawals to two different destination addresses), every one of those withdrawals resolves to the *first* matching entry returned by the POA API, regardless of which index it actually corresponds to.

### Finding Description
`findMatchingWithdrawal` in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` (lines 409-427) selects a withdrawal from the POA API response using only:
```
withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId)
``` [1](#0-0) 

`describeWithdrawal` (lines 313-343) calls this helper with only the `assetId`, discarding the `index`/`destinationAddress`/`amount` fields of the `WithdrawalIdentifier` that were supposed to disambiguate multiple withdrawals within the same NEAR transaction: [2](#0-1) 

The `Bridge` interface's `createWithdrawalIdentifier`/`describeWithdrawal` contract is explicitly designed to support batch withdrawals with distinct `index` values per withdrawal [3](#0-2) , and `watchWithdrawal` in `core/withdrawal-watcher.ts` polls `describeWithdrawal` per-`WithdrawalIdentifier` and returns whatever hash is reported as the completed destination transaction [4](#0-3) . `sdk.waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` then hand these per-index results directly back to the integrator as authoritative completion records, indexed to `withdrawalParams[i]` [5](#0-4) [6](#0-5) .

The code comment itself admits the gap: "Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported" [7](#0-6) . Rather than failing safely (erroring or returning "unknown"), the function silently returns `.find()`'s first match for *every* index that shares the same `assetId`, so a batch of `N` same-asset withdrawals to different destination addresses/amounts will all report the same (first) `transfer_tx_hash` and "completed" status — an equality break between "status/hash reported" and "actual on-chain outcome for that specific withdrawal index."

### Impact Explanation
This breaks the required equality "a status or hash misreport making an integrator credit or refund twice" (explicitly listed as an acceptable High-severity impact). An integrator relying on `sdk.processWithdrawal`/`waitForWithdrawalCompletion` for a batch of same-asset withdrawals (e.g., paying out multiple different users/addresses of the same token in one NEAR intent transaction) will:
- Believe withdrawal #2 (and any further same-asset withdrawal) completed with the destination tx hash that actually belongs to withdrawal #1, potentially crediting/marking-settled the wrong destination or double-crediting based on one real on-chain transfer while a second, distinct transfer's real hash is never surfaced.
- Conversely, if the first-matched withdrawal fails/refunds while a later one with the same asset succeeds, `describeWithdrawal` will report the (wrong) failed/pending status for all of them, potentially leaving a completed withdrawal unresolved or mis-flagged.

This is not a "malicious relayer/bridge/API" trust issue — the POA API returns a correct list of individual withdrawal records; the misreport is purely an SDK-side matching bug that discards the withdrawal index/destination it was given.

### Likelihood Explanation
Requires a batch withdrawal (multi-element `WithdrawalParams[]` in a single `processWithdrawal`/`signAndSendWithdrawalIntent` call) where two or more entries share the same `assetId` routed through POA bridge — this is a normal, unprivileged usage pattern explicitly supported by the SDK's batch API (`estimateWithdrawalFee`, `signAndSendWithdrawalIntent`, `waitForWithdrawalCompletion` all accept arrays) and requires no attacker-controlled input beyond constructing such a batch, which any caller (or their own application logic) can do inadvertently.

### Recommendation
Update `findMatchingWithdrawal` (and its duplicate in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`) to disambiguate matches by more than `assetId` — incorporate `destinationAddress`/`amount` (and consume/remove matched entries so repeated calls for the same batch don't return the same entry twice), or explicitly throw/return an "unsupported" status when multiple withdrawals share the same asset in a single transaction, instead of silently returning the first match for every index.

### Proof of Concept
1. Call `sdk.processWithdrawal({ withdrawalParams: [ {assetId:"nep141:usdt...near", amount:100n, destinationAddress:"addrA"}, {assetId:"nep141:usdt...near", amount:200n, destinationAddress:"addrB"} ] })` — a single NEAR intent transaction settles two USDT withdrawals to different destinations.
2. POA bridge processes both withdrawals; its status API returns two entries with `near_token_id: "usdt...near"`, differing `transfer_tx_hash`/`address`/`amount`.
3. `watchWithdrawal` is invoked twice (index 0 and index 1) via `createWithdrawalCompletionPromises`/`waitForWithdrawalCompletion`; both calls hit `PoaBridge.describeWithdrawal`, which calls `findMatchingWithdrawal(withdrawals, "nep141:usdt...near")` — `.find()` returns the **same first entry** for both index 0 and index 1 [1](#0-0) .
4. The integrator receives `destinationTx[0] === destinationTx[1]` (same `txHash`/status) even though the on-chain transfers to `addrA` and `addrB` are distinct, causing a status/hash misreport for one of the two withdrawals.

function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

**Option B: Independent Promises (`createWithdrawalCompletionPromises`)**

For scenarios where fast withdrawals (Solana ~2s) shouldn't wait for slow ones (Bitcoin ~1hr), use `createWithdrawalCompletionPromises` to get promises that resolve independently:

```typescript
// Get array of promises - one per withdrawal
const promises = sdk.createWithdrawalCompletionPromises({
    withdrawalParams,
    intentTx
});

// Fire and forget - handle each independently
promises[0].then(tx => saveUsdc(tx)).catch(err => logError(0, err));
promises[1].then(tx => saveBtc(tx)).catch(err => logError(1, err));

// Or await a specific withdrawal (fast chain first)
const usdcTx = await promises[0];
await notifyUser('USDC received', usdcTx.hash);

// Or process as they complete with backpressure
const pending = new Map(promises.map((p, i) => [i, p]));
while (pending.size > 0) {
    const { index, tx } = await Promise.race(
        [...pending.entries()].map(async ([i, p]) => ({ index: i, tx: await p }))
    );
    pending.delete(index);
    await saveSuccess(index, tx);  // Backpressure maintained
}

// Or wait for all with independent error handling
const results = await Promise.allSettled(promises);
for (const [i, result] of results.entries()) {
    if (result.status === 'fulfilled') {
        await saveSuccess(i, result.value);
    } else {
        await saveFailure(i, result.reason);
    }
}
