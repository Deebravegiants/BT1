### Title
Webhook `shop` and `topic` identity are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signature over the raw request body only, while the `shop` (tenant identity) and `topic` values are taken from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates only the body HMAC and then forwards the unauthenticated `shop`/`topic` header values straight to the app's webhook handler as trusted, "verified" data. An attacker who can obtain any single validly-signed webhook body (e.g. by installing the app on their own shop) can replay that exact body/HMAC pair while substituting the `shop-domain` (and/or `topic`) header to impersonate a different tenant.

### Finding Description
`Request#hmac` and `Request#to_signable_string` bind the signature check exclusively to `@raw_body`: [1](#0-0) [2](#0-1) 

`shop` and `topic` are read directly from attacker-controllable HTTP headers with no cryptographic binding to that body: [3](#0-2) 

`HmacValidator.validate` only recomputes and compares the HMAC over `to_signable_string` (the body), never over `shop`/`topic`: [4](#0-3) 

`Registry.process` treats a passing HMAC check as proof the whole request — including `request.shop` and `request.topic` — is authentic, and passes them on to the app-supplied handler as `WebhookMetadata`: [5](#0-4) 

The documented contract for `Registry.process` explicitly tells integrators that it "will verify the request did indeed come from Shopify", and instructs handlers to trust `data.shop` as the tenant identifier: [6](#0-5) [7](#0-6) 

The identity binding that should hold is: `shop reported to handler == shop the HMAC was actually computed for`. Because `to_signable_string` only covers `@raw_body`, this equality is not enforced — any request with a body whose HMAC an attacker can produce (trivially possible using their own legitimately-installed shop's real webhook, captured once) can be replayed with a forged `shop-domain`/`topic` header and will still pass `HmacValidator.validate`.

### Impact Explanation
An app that follows the gem's documented pattern (trusting `data.shop` from `WebhookMetadata` to select which tenant's records to update, per the exact example in the docs) can be made to write, delete, or process data under an attacker-chosen shop identity while only holding a legitimately-signed webhook from the attacker's own (or any) installed shop. This is a cross-tenant identity confusion: the HMAC proves "some legitimate installed shop sent this body," not "this specific shop sent this body," yet the gem hands the caller-supplied shop value to the handler as if it were verified. This can result in cross-tenant data corruption/disclosure in multi-tenant apps relying solely on `shopify_api`'s webhook verification.

### Likelihood Explanation
Exploitation requires only unprivileged capability: install the target app (or otherwise obtain one legitimate webhook body+HMAC pair, e.g. from your own shop), then replay it to the app's public webhook endpoint with a modified `shop-domain`/`topic` header. No access token, `client_secret`, or privileged account is needed — the attack is purely against the webhook ingestion endpoint. Likelihood is moderate: it depends on the host app treating `data.shop` as an authoritative tenant selector without any secondary check (e.g., confirming the shop has an active session/installation matching that webhook_id), which is exactly what the gem's own documentation encourages.

### Recommendation
Include `shop` and `topic` (and ideally `webhook_id`) in the signed material validated against the HMAC, or otherwise cryptographically bind them to the request (e.g., validate that the reported `shop` corresponds to a shop with a currently registered subscription for that `webhook_id`/`topic` before dispatching to the handler). At minimum, update `Request#to_signable_string` so the HMAC check fails if the `shop-domain` or `topic` headers are altered independently of the body, and document that `data.shop` must still be cross-checked by the app against known installed shops before being used as a tenant key.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and registers/receives one real webhook, capturing the exact `raw_body` and the `x-shopify-hmac-sha256` header Shopify computed for it.
2. Attacker replays this exact `raw_body` + `x-shopify-hmac-sha256` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com` (and optionally alters `x-shopify-topic`).
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers; `HmacValidator.validate` succeeds because it only recomputes the HMAC over `raw_body`, which is unchanged (`lib/shopify_api/webhooks/request.rb` lines 10-23, 35-38; `lib/shopify_api/utils/hmac_validator.rb` lines 12-31).
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(topic: "victim's topic", shop: "victim.myshopify.com", body: <attacker's data>, ...)` (`lib/shopify_api/webhooks/registry.rb` lines 188-200), and the app processes/stores it as if it legitimately originated from `victim.myshopify.com`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
