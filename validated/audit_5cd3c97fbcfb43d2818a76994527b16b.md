### Title
Route-controlled pool can move unrelated caller assets through the signed authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
`swap_collateral` accepts caller-supplied route bytes and invokes the configured swap router after authorizing only the controller's input-token transfer. The router decodes arbitrary pool, token, and venue addresses from the route and invokes the selected pool. Because `caller.require_auth()` remains the root authorization for the whole strategy, a malicious pool can request an unrelated `token.transfer(caller, attacker, amount)` during the route; simulation records it as a child of the caller's `swap_collateral` authorization, and execution succeeds if the caller signs that returned tree.

### Finding Description
`process_swap_collateral` authorizes `caller` and verifies ownership or delegation, but accepts the opaque `swap` bytes without constraining the venues encoded inside it [1](#0-0) . The strategy then passes those bytes to `withdraw_and_swap_from_supply` [2](#0-1) .

`swap_tokens` authorizes only one exact `token_in.transfer(controller, router, amount_in)`, but then calls `router.execute_strategy(controller, amount_in, swap)` with the unmodified route [3](#0-2) . The router builds each `SwapHop` from caller-controlled `assets` registry indices, including the `pool` address [4](#0-3) . A venue such as Phoenix then invokes that payload-selected `pool.swap` [5](#0-4) .

The vulnerability class maps directly to arbitrary path selection: the route's pool address is the analog of an attacker-controlled filesystem path, and Soroban authorization permits that selected code to add an unrelated caller authorization request beneath the root controller call. The repository's focused authorization test demonstrates that a rogue hop can transfer an unrelated wallet token from the swap caller to an attacker, that simulation records the transfer under `swap_collateral`, and that signing that poisoned tree makes the transfer execute [6](#0-5) . The enforced-auth test further shows that the same transaction succeeds precisely when the signed tree includes the rogue transfer [7](#0-6) .

The same route surface is also reachable through `swap_debt`, `repay_debt_with_collateral`, and `multiply`, but `swap_collateral` provides the simplest single-call proof path [8](#0-7) .

### Impact Explanation
An attacker can steal unrelated token balances from a user who signs a malicious swap route. The stolen asset need not be a listed collateral or debt asset, need not be `token_in`, and is not bounded by `amount_in`, route output, minimum-output checks, or the final health-factor check.

The malicious route can still return enough `token_out` to satisfy `dispatch_hop`'s measured positive-output requirement and the controller's final account checks [9](#0-8) . Consequently, the lending operation can appear economically successful while an unrelated wallet transfer is bundled into the same authorization.

### Likelihood Explanation
Likelihood is Medium. The attacker needs no privileged role, leaked key, upgrade, oracle failure, or protocol parameter change: they can deploy a pool contract, encode its address into the route registry, and return enough output for the swap to pass. However, exploitation requires a victim to sign the authorization tree containing the extra transfer; users or clients that decode and compare the simulated authorization tree can reject it.

This is more dangerous than ordinary route-quality risk because the loss is not limited to poor execution of the declared input amount: the route can authorize movement of a separate token held directly by the caller.

### Recommendation
Enforce a governance-managed venue or pool allowlist before dispatching route hops, or otherwise restrict route-selected contract calls to authenticated, reviewed pool implementations. The router should not treat the payload's `assets` registry as sufficient authority to invoke arbitrary pool code.

Until every venue is allowlisted, wallets and SDKs must decode the complete simulated authorization tree and reject any child invocation other than the exact expected strategy/input transfer. This mitigates the client-side path but does not remove the contract-level exposure.

### Proof of Concept
1. Alice owns a lending account and holds an unrelated token `W`.
2. The attacker deploys `RoguePool`, configured with `(victim=alice, wallet_token=W, to=attacker, amount=W.balance(alice))`.
3. The attacker prepares `swap_collateral(alice, account_id, current=USDC_market, amount, new=ETH_market, swap=route)` where the route's `assets` registry contains `RoguePool`, `USDC`, and `ETH`, and its swap instruction selects that pool.
4. `RoguePool.swap` sends enough `ETH` to the router for the measured-output checks and calls `W.transfer(alice, attacker, W.balance(alice))`.
5. Simulation attaches the `W.transfer` as a child of Alice's `swap_collateral` authorization.
6. If Alice signs the returned tree, the strategy completes, ETH is supplied to her account, and all `W` moves to the attacker.

The harness reproduces this sequence: simulation records the theft as a child authorization and moves Alice's wallet balance to the attacker [6](#0-5) , while enforcing mode rejects an honest tree and accepts the poisoned tree [10](#0-9) .
