## Title
Predictable, Unsigned Offline Session ID Doubles as the Non‑Embedded Session Cookie, Enabling Cross‑Tenant Session Hijacking - (File: `lib/shopify_api/auth/session.rb`)

### Summary
For offline (non‑user) sessions, `ShopifyAPI::Auth::Session.from` assigns the session `id` as a fully deterministic string built only from the public shop domain (`"offline_#{shop}"`), with no random or secret component. `ShopifyAPI::Auth::Oauth.validate_auth_callback` then uses this exact deterministic ID as the literal value of the session cookie handed to the browser for non-embedded apps, and `ShopifyAPI::Utils::SessionUtils.cookie_session_id` later returns that raw cookie value unverified as the lookup key for the stored session/access token. Because the ID a legitimate app is told to store its session under (per this gem's own documented storage pattern) is identical to a value any unprivileged party can compute from nothing but a public `*.myshopify.com` domain, the binding "possession of this cookie value ⟺ completed OAuth for this shop" does not hold.

### Finding Description
`Session.from` computes the session id for offline sessions purely from the `shop` argument: [1](#0-0) 

```ruby
if is_online
  ...
  id = "#{shop}_#{associated_user.id}"
else
  id = "offline_#{shop}"
end
```

`shop` is the Shopify domain (e.g. `example.myshopify.com`), which is public information — it's the same string used in the store's public storefront URL and is required as an input parameter to this gem's own OAuth‑initiation API (`Oauth.begin_auth(shop:, ...)`), so any internet user can supply/guess it.

`Oauth.validate_auth_callback` then sets this deterministic `session.id` directly as the plaintext value of the browser session cookie for non-embedded apps: [2](#0-1) 

```ruby
cookie = if Context.embedded?
  SessionCookie.new(value: "", expires: Time.now)
else
  SessionCookie.new(
    value: session.id,
    expires: session.expires ? session.expires : nil,
  )
end
```

No HMAC, signature, or any secret-derived value is mixed into this cookie — it is the raw, predictable identifier. The cookie itself is defined with no cryptographic protection: [3](#0-2) 

On subsequent requests, the gem reads this cookie back and returns it verbatim as the effective session id, with no check that it was ever actually issued by this gem's OAuth flow: [4](#0-3) 

```ruby
def cookie_session_id(cookies)
  cookies[Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME]
end
```

This is the exact identifier the gem's own documentation instructs developers to use as the storage key for the `Session` object (including its `access_token`): [5](#0-4) 

```ruby
serialized_data = session.serialize
redis.set("session:#{session.id}", serialized_data)
...
serialized_data = redis.get("session:#{session_id}")
session = ShopifyAPI::Auth::Session.deserialize(serialized_data)
```

Because `session.id == "offline_#{shop}"` is a pure function of public information, and `cookie_session_id` returns that string unauthenticated, the equality the system is supposed to enforce —

`cookie_value presented by a browser` ⟺ `id of a Session object that this app's OAuth flow actually created for that browser after real Shopify authorization`

— is broken: an attacker can construct the right-hand value themselves without ever completing OAuth, merely by knowing the target's shop domain.

### Impact Explanation
This is a session fixation / cross-tenant session hijacking issue (High): an unprivileged attacker who knows a target's `*.myshopify.com` domain (public, or trivially discoverable/guessable) can set their own browser's `shopify_app_session` cookie to `offline_{target-shop}.myshopify.com` and present it to any host application built following this gem's own documented cookie/session-storage pattern. If the host app's session store is keyed by this id (as this repo's own migration guide instructs), the attacker's request will resolve to the victim shop's persisted `Session`, including its offline `access_token`, granting cross-tenant access to that merchant's data without ever performing OAuth.

### Likelihood Explanation
High. No credentials, TLS interception, or social engineering are required — only knowledge of a shop's `myshopify.com` domain, which is routinely public (storefront URL, app listing, etc.). The exploit only requires setting an HTTP cookie, and it directly follows the storage pattern this repository itself documents for consumers.

### Recommendation
- Do not let the OAuth-issued session cookie value be a deterministic function of the shop domain alone. Generate a random, non-guessable session identifier (as is already done for `Session.temp`/random ids via `SecureRandom.uuid`) and keep any deterministic "offline_#{shop}" style key as an internal lookup detail, not as bearer material sent to the browser.
- If a cookie must carry the session id, sign/HMAC it (similar to `Utils::HmacValidator`) so `cookie_session_id` can verify authenticity before trusting the value, rather than returning the raw cookie content unchecked.
- Update the documented storage examples (`BREAKING_CHANGES_FOR_V16.md`) to avoid encouraging keying storage directly and solely by a predictable `session.id` when that same id is exposed as a cookie value.

### Proof of Concept
1. App is configured for non-embedded OAuth (Authorization Code Grant) and persists sessions the way this repo documents: `redis.set("session:#{session.id}", serialized_data)`.
2. Attacker knows the victim's shop domain `victim-shop.myshopify.com` (public).
3. Attacker computes, without any interaction with Shopify or the app: `offline_victim-shop.myshopify.com` (matches `Session.from`'s `id = "offline_#{shop}"` logic at `lib/shopify_api/auth/session.rb:116`).
4. Attacker sets this value as their browser's `shopify_app_session` cookie and sends a request to the app.
5. The app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)` → `cookie_session_id` → returns `offline_victim-shop.myshopify.com` unmodified (`lib/shopify_api/utils/session_utils.rb:68-71`).
6. The app looks up `redis.get("session:offline_victim-shop.myshopify.com")`, which (if the victim shop previously installed the app) returns the victim's real `Session`, including its `access_token`.
7. Attacker's request is now authenticated as the victim shop, achieving cross-tenant access/token theft.
