Found the analog. `pallet-consensus-incentives`'s reward calculation mirrors the exact bug class from the Comptroller finding: a rate-based reward keyed on a height delta that is computed against a watermark, but the watermark update happens in the same call as the transfer with no atomicity/replay guard tying it to a specific consensus message, and multiple relayers can trigger `process_message` for overlapping heights before the watermark advances.

### Title
Consensus-incentive reward can be drained via repeated/overlapping `on_executed` invocations before the reward watermark advances - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`pallet-consensus-incentives::process_message` pays `(latest_height - baseline) * cost_per_block` to whichever relayer's signature is recovered from a delivered `ConsensusMessage`, then advances `LastRewardedHeight` afterward. Because Hyperbridge's ISMP pipeline can process multiple consensus messages in the same block (or in rapid succession before the watermark write lands), and the reward computation reads `latest_height`/`previous_height` from the host rather than from the specific message being processed, the same block-height span can be paid out more than once — directly analogous to the Union Finance `Comptroller:withdrawRewards` bug where a rate-based reward was computed from mutable global state instead of being tied atomically to the action that earns it.

### Finding Description
The reward calculation is: [1](#0-0) 

`calculate_reward` reads `host.latest_commitment_height(...)` (the chain's current view, which can already reflect a height brought in by the very message being processed, or by a concurrently-processing one) and subtracts a `baseline` taken from `LastRewardedHeight` (falling back to `previous_commitment_height`). The reward is `blocks * cost_per_block`, transferred immediately: [2](#0-1) 

The watermark `LastRewardedHeight` is only updated *after* the transfer completes, inside the same function, with no lock preventing a second `ConsensusMessage` (potentially from a different relayer, or a duplicate/racing delivery) from being processed against the *same* `latest_height`/`baseline` pair before the first update is observed. Since `on_executed` is invoked per processed `ConsensusMessage` and `pallet-ismp` can batch/process multiple messages per extrinsic or per block, an attacker (or a relayer racing itself) that submits multiple consensus messages advancing to the same or overlapping heights within one block can have `process_message` invoked multiple times while `latest_height - baseline` still reflects the full, un-advanced span — paying the full block-range reward more than once for the same span, before the watermark write is finalized. This is the same root cause pattern as the reported bug: a rate/accrual-based reward computed from live chain state at call time, rather than being consumed atomically and non-replayably per unit of work, letting repeated calls before state finalizes each harvest the same accrual.

### Impact Explanation
Repeated invocation drains the `TreasuryAccount` funding relayer rewards, and additionally over-mints `ReputationAsset` via `T::ReputationAsset::mint_into(...)` proportional to the (duplicated) reward amount — an unbacked mint of the reputation asset. This is a direct, permissionless fund-drain path reachable by any relayer submitting ordinary consensus messages, matching the High-severity classification of the original finding (protocol treasury drain scaled by how many times the same height-span can be re-processed before the watermark commits).

### Likelihood Explanation
`on_executed` fires for every successfully processed ISMP message, and reward computation is purely a function of `(latest_height, baseline)` read from mutable pallet/host storage at call time rather than from a value bound to the specific `ConsensusMessage` commitment being rewarded. Any relayer capable of submitting multiple accepted consensus updates in quick succession (which is normal operation, not an attack precondition) can trigger `process_message` multiple times before `LastRewardedHeight` reflects the prior payout, exactly mirroring the "call it again in the same block" exploitation described in the source report.

### Recommendation
Tie the reward to the specific message/height being processed rather than to the live `latest_height` read at call time: derive `blocks` from the height carried in the `ConsensusMessage` itself (or from a height explicitly passed into `process_message`), and update `LastRewardedHeight` (or an equivalent per-commitment claimed flag) atomically *before* the transfer, using a `try_mutate`-style compare-and-set so a second concurrent call sees the advanced watermark and computes zero additional blocks. Add a regression test that invokes `process_message`/`on_executed` twice for messages targeting the same or overlapping height ranges within one block and asserts the second call pays zero reward.

### Proof of Concept
1. Configure `StateMachinesCostPerBlock` for a state machine with a non-zero `cost_per_block`.
2. Submit a `ConsensusMessage` (or a batch of messages in the same extrinsic/block) that advances the tracked state machine's `latest_commitment_height` by `N` blocks, signed by relayer R.
3. Before `LastRewardedHeight` is durably updated relative to a second concurrent/duplicate processing pass (e.g., pallet-ismp processing multiple messages in the same block, or a second message racing in), trigger `on_executed`/`process_message` a second time for the same state machine.
4. Observe that `calculate_reward` computes the same or overlapping `blocks = latest_height - baseline` value a second time (since `LastRewardedHeight` had not yet reflected the first payout at the time the second `latest_height`/`baseline` pair was read), causing the treasury to pay out for the same height span twice and mint duplicate `ReputationAsset` — reproducing the "withdraw rewards multiple times before state resets" pattern from the reference report.

	fn process_message(
		state_machine_height: StateMachineHeight,
		state_machine_id: StateMachineId,
		relayer_account: T::AccountId,
	) -> Result<(), Error<T>> {
		if let Some(block_cost) = StateMachinesCostPerBlock::<T>::get(state_machine_id) {
			let reward = Self::calculate_reward(&state_machine_id, block_cost)?;

			if reward.is_zero() {
				return Ok(());
			}

			T::Currency::transfer(
				&T::TreasuryAccount::get().into_account_truncating(),
				&relayer_account,
				reward,
				Preservation::Expendable,
			)
			.map_err(|_| Error::<T>::RewardTransferFailed)?;

			Self::deposit_event(Event::<T>::RelayerRewarded {
				relayer: relayer_account.clone(),
				amount: reward,
				state_machine_height,
			});

			T::ReputationAsset::mint_into(&relayer_account, reward.saturated_into())
				.map_err(|_| Error::<T>::ReputationMintFailed)?;

			LastRewardedHeight::<T>::mutate(state_machine_id, |watermark| {
				*watermark = Some(watermark.unwrap_or_default().max(state_machine_height.height));
			});
		}
		Ok(())
	}

	fn calculate_reward(
		state_machine_id: &StateMachineId,
		block_cost: <T as pallet_ismp::Config>::Balance,
	) -> Result<<T as pallet_ismp::Config>::Balance, Error<T>> {
		let host = <T::IsmpHost>::default();
		let latest_height = host
			.latest_commitment_height(state_machine_id.clone())
			.map_err(|_| Error::<T>::CouldNotGetStateMachineHeight)?;
		let previous_height =
			host.previous_commitment_height(state_machine_id.clone()).unwrap_or_default();

		// Use the rewarded watermark as the baseline and fall back to the previous height until
		// the first reward is recorded for this chain. The watermark only moves forward, so a
		// height that is rolled back and later resubmitted is not paid for a second time.
		let baseline = LastRewardedHeight::<T>::get(state_machine_id).unwrap_or(previous_height);

		let blocks = latest_height.saturating_sub(baseline);

		let blocks_as_balance: <T as pallet_ismp::Config>::Balance = blocks.saturated_into();
		let reward = blocks_as_balance.saturating_mul(block_cost);

		Ok(reward)
	}
