Confirmed root cause: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`), while `shop` is read straight from an unauthenticated header (`lib/shopify_api/webhooks/request.rb:20-23`). `HmacValidator.validate` only checks bytes against `to_signable_string` [1](#0-0) , so the `shop` field is never part of the HMAC-covered bytes. `Registry.process` passes this unauthenticated `shop` straight into `WebhookMetadata` used by the host app's handler [2](#0-1) , and the gem's own docs instruct apps to key their tenant logic off `data.shop` [3](#0-2) .

### Title
Webhook `shop` domain is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `hmac` and `to_signable_string` solely from the raw body, while `shop` (and `topic`, `webhook_id`, `api_version`) are read from HTTP headers that are never included in the signed bytes.

### Finding Description
`Request#to_signable_string` only returns `@raw_body`: [4](#0-3) 
and `shop` is pulled from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not covered by that signable string: [5](#0-4) 
`HmacValidator.validate` verifies the HMAC only over `to_signable_string`: [1](#0-0) 
`Registry.process` accepts the request once this body-only HMAC check passes, then trusts `request.shop` to build `WebhookMetadata` handed to the app's handler: [2](#0-1) 

This breaks the binding: `shop header authenticated == shop the handler acts on`. An unprivileged internet user who has access to any single genuine `(raw_body, hmac)` pair signed by Shopify for a topic they legitimately receive (e.g. by installing the target app on their own free/dev shop and receiving a real webhook such as `app/uninstalled`, `shop/redact`, or `orders/create`) can replay that exact body and HMAC to the app's public webhook endpoint while substituting the `shopify-shop-domain` header with an arbitrary victim shop domain. Because the domain header is outside the signed bytes, `HmacValidator.validate` still returns true, and `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain.

### Impact Explanation
Per the gem's documented usage, host applications key their per-tenant logic directly off `data.shop` (e.g., to route jobs, update per-shop records, or process GDPR-mandatory topics like `shop/redact` and `customers/redact`) [3](#0-2) . Since the gem is the trust boundary that verifies "this event genuinely concerns shop X," and it fails to bind `shop` into the signature, an attacker can make the app's webhook handler act on a victim's tenant using a signature the attacker legitimately obtained for their own shop. This is a cross-tenant identity-binding failure that can trigger tenant-scoped actions (e.g., triggering redaction/deregistration flows or corrupting/attributing data to a shop the attacker doesn't control).

### Likelihood Explanation
Any developer or attacker can install the target app for free on a throwaway/dev store, capture one legitimate webhook `(raw_body, hmac)` pair sent to their own endpoint, then replay it against the app's production webhook URL with a modified `shop-domain` header. No access token, `api_secret_key`, or privileged access is required — only reachable, public webhook endpoints and a shop the attacker legitimately controls.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`, `api_version`) header values in the bytes covered by `to_signable_string`, or otherwise cryptographically bind the shop-domain header to the payload before trusting it (Shopify does sign the raw body per delivery, but the current implementation should authenticate the specific header values it hands to consumers rather than only the body). At minimum, document/require host apps to independently verify shop identity (e.g., cross-check `data.shop` against a shop that has an existing, registered webhook subscription/session) before acting on webhook content.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a shop they control) and lets it register webhooks normally.
2. Shopify delivers a legitimate webhook to the app's public endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and some JSON `raw_body`.
3. Attacker captures this `(raw_body, hmac)` pair.
4. Attacker sends a new POST to the same public webhook endpoint with the identical `raw_body` and `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` computes the HMAC only over `raw_body` and returns `true`, since it never inspects the shop header.
6. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) invokes the app's handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the payload/signature actually belongs to `attacker-shop.myshopify.com`.
