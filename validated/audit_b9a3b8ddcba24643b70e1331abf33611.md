### Title
Webhook `shop` (and `topic`) identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` (and `topic`) values from HTTP headers that are excluded from the HMAC-signed content, while `ShopifyAPI::Webhooks::Registry.process` trusts those header-derived values to attribute the webhook payload to a specific merchant. This breaks the binding `HMAC-verified bytes == bytes used to identify the shop`, mirroring the reported bug class where a value acted upon downstream (the LP withdrawal destination) differs from the value actually protected by the cryptographic check (the burn target).

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it against the received HMAC: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw request body: [2](#0-1) 

But `shop` (and `topic`, `webhook_id`, `api_version`) are read straight from HTTP headers, which are never part of the signed content: [3](#0-2) 

`Registry.process` validates only the HMAC of the body, then unconditionally forwards `request.shop` and `request.topic` (unverified headers) to the app's handler as the tenant identity for the payload: [4](#0-3) 

So the equality the code needs to hold is: `shop bound by HMAC == shop delivered to the handler`. In reality: `shop delivered to the handler` comes from the `shopify-shop-domain` header, which is completely outside the HMAC computation, which only covers `@raw_body`. Anyone who can obtain one validly-signed webhook body/HMAC pair for their own shop (trivial — install the app and receive a real webhook for their own tenant) can resend the same raw body with the same valid HMAC but an arbitrary `shopify-shop-domain` header value. `Utils::HmacValidator.validate` still returns `true` because it only checks the body bytes, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload belongs to a different shop of the attacker's choosing.

### Impact Explanation
This is a cross-tenant identity confusion: the app's own webhook processing pipeline will attribute attacker-controlled webhook data to an arbitrary victim shop domain while a legitimately valid HMAC is present, defeating the purpose of the signature check as a tenant-authenticity guarantee. Any host application logic that keys database writes, cache updates, entitlement changes, or reinstall/uninstall handling off `WebhookMetadata#shop` can be tricked into applying attacker-supplied data under another merchant's identity — a cross-tenant access impact.

### Likelihood Explanation
Exploitation only requires the attacker to install the app on a shop they control (an ordinary, unprivileged action any developer/merchant can take), capture one legitimate webhook delivery for their own shop, and replay it with a modified `shopify-shop-domain` header. No access to `api_secret_key` or any victim credentials is required, and the HMAC check as implemented in this gem provides no protection against it.

### Recommendation
Bind the shop (and ideally topic/webhook id) identity into the value that is cryptographically verified, e.g. include `shop`, `topic`, and `webhook_id` in the signable string used by `HmacValidator`, or otherwise cryptographically bind the header values to the signed body before trusting `request.shop` in `Registry.process` / `WebhookMetadata`.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com` and capture a legitimately delivered webhook: raw body `B`, headers including `x-shopify-hmac-sha256: H` (valid for `B`) and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Replay the exact same request to the app's webhook endpoint, changing only `x-shopify-shop-domain` to `victim-shop.myshopify.com` (leave body `B` and `x-shopify-hmac-sha256: H` unchanged).
3. `Utils::HmacValidator.validate` in `Registry.process` recomputes the HMAC over `B` only, which still matches `H`, so the check passes.
4. `Registry.process` builds `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` and invokes the app's handler, which now processes attacker-controlled data as if it originated from `victim-shop.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
