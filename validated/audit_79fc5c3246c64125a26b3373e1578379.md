### Title
Webhook `shop-domain` header is trusted for tenant identification but is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identifier (`shop`) that is handed to the consuming app's webhook handler directly from the unauthenticated `X-Shopify-Shop-Domain` / `shopify-shop-domain` HTTP header, while `Utils::HmacValidator` only verifies the raw request body. The `shop` field that a merchant's app uses to route/scope tenant data is never part of the signed payload, breaking the binding `bytes verified == bytes acted on`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

but `Request#shop` is read straight from a header that is not part of that signable string: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `to_signable_string` (i.e., the raw body) and compares it against the `hmac-sha256` header: [3](#0-2) 

`Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` to authenticate the webhook, and then immediately forwards `request.shop` (the unauthenticated header value) into `WebhookMetadata`, which is the object the app's own `WebhookHandler#handle` implementation is expected to trust as the tenant identifier: [4](#0-3) [5](#0-4) 

The `hmac` validation only proves that the *body bytes* originated from Shopify using the app's `client_secret`; it proves nothing about which shop sent it. Because the same `client_secret` is shared across every shop that has the app installed, any merchant with the app installed (i.e., an authenticated-but-unprivileged tenant of the multi-tenant app, which is exactly the class of "unprivileged internet user" allowed by scope here since they hold no special credentials to the app or other tenants) can capture a genuine Shopify-issued `(raw_body, hmac)` pair delivered to their own webhook endpoint, and replay that exact body+HMAC pair while substituting the `X-Shopify-Shop-Domain` header for a victim shop. `Utils::HmacValidator.validate` will still return `true` because the signed bytes (raw body) are unchanged, and `Registry.process` will hand the handler a `WebhookMetadata` whose `shop` is now the victim's domain paired with content that never actually belonged to that shop.

This exactly matches the report's bug class: a field ("shop") that a downstream trust decision is based on is not covered by the same integrity check ("hmac") that is presented as proof of authenticity — an equality the code implicitly assumes (`hmac-verified body ⇒ shop-domain header is authentic`) that does not actually hold.

### Impact Explanation
Applications built on this gem are documented to use `WebhookMetadata#shop` to determine which tenant's data the webhook body applies to (e.g., to look up/update the corresponding shop record, decrement inventory, cancel orders, etc.). Because `shop` is unauthenticated relative to the HMAC, an attacker (any shop merchant/customer with the app installed on their own low-privilege store) can cause the handler to process data under a different shop's identity — a cross-tenant confusion/spoofing primitive. This satisfies the "Critical: cross-tenant access" impact bucket defined by the rules, since it lets one tenant inject data attributed to another tenant purely by manipulating a header, without any leaked credentials.

### Likelihood Explanation
Exploitability requires only: (1) being an app user on some shop (no special privilege), (2) intercepting or observing one's own legitimate webhook delivery (raw body + `hmac-sha256` header — trivially available to the attacker since it's delivered to their own endpoint or logged), and (3) resending it to the same endpoint with a modified `shop-domain` header. No knowledge of `client_secret`, access tokens, or victim credentials is required. This is a low-effort, repeatable replay, making likelihood high wherever an app's `WebhookHandler` trusts `WebhookMetadata#shop` as the tenant key (which is the intended and documented usage pattern for this field).

### Recommendation
Bind the shop identity to the cryptographic proof instead of trusting an out-of-band header:
- Extend `VerifiableQuery`/`to_signable_string` for webhooks to include the `shop-domain`, `topic`, and `webhook-id` header values in the signed material, or otherwise cross-check that the shop in the payload matches the one the app expects for that installation/session before dispatching to the handler.
- At minimum, document explicitly in `lib/shopify_api/webhooks/registry.rb` and `webhook_handler.rb` that `WebhookMetadata#shop` is *not* authenticated by the HMAC and that consuming applications must independently verify the shop is one they have an active, matching session/installation for before trusting the payload.
- Consider adding replay protection (e.g., binding `webhook_id`/timestamp uniqueness) since the current scheme also permits verbatim body replay to the same or different shop context.

### Proof of Concept
```ruby
# Attacker owns shop "attacker-shop.myshopify.com" and has the app installed.
# Shopify sends the attacker a legitimately signed webhook for their own shop:
raw_body = '{"id": 1, "note": "genuine order payload"}'
hmac_header = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_client_secret, raw_body)
# (attacker captures this raw_body/hmac pair from their own webhook delivery logs)

# Attacker replays the exact same body+hmac, but swaps the shop-domain header:
forged_headers = {
  "x-shopify-topic"        => "orders/create",
  "x-shopify-hmac-sha256"  => Base64.encode64(hmac_header),
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com", # <-- not covered by hmac
  "x-shopify-webhook-id"   => "replayed-id",
  "x-shopify-api-version"  => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# HmacValidator only checks raw_body against the hmac, so this still passes:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# Registry.process will call the app's handler with:
#   WebhookMetadata(shop: "victim-shop.myshopify.com", body: {"id"=>1, ...}, ...)
# even though the payload never originated from, or was authorized by, that shop.
ShopifyAPI::Webhooks::Registry.process(request)
```
