## Title
Tron IntentGatewayV2 `withdraw()` transfers escrowed funds before debiting escrow, allowing reentrant double-spend of the same commitment - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` implements the same "action before check/effect" ordering flaw as the referenced JUSDBank report: `withdraw()` sends ETH/tokens to the beneficiary *before* decrementing the escrow accounting, and `onAccept` (which invokes `withdraw`) carries no reentrancy guard. This is the inverse-but-equivalent bug pattern: instead of the *check* being deferred until after the *fund movement* (as in JUSD), here the *effect* (escrow debit) is deferred until after the *fund movement* — the classic checks-effects-interactions (CEI) violation — enabling a malicious beneficiary to re-enter and drain the same escrow multiple times before it is ever decremented.

### Finding Description
`onAccept` is the single unsigned-message entrypoint reachable by any relayer delivering a `RedeemEscrow`/`RefundEscrow` `PostRequest`: [1](#0-0) 

It calls `withdraw`, which for each escrowed token first checks only that the entry is non-zero, then performs the external transfer, and only afterward decrements the escrow balance: [2](#0-1) 

Compare this to the EVM (non-Tron) `IntentsBase._withdraw`, which correctly applies CEI — the escrow is debited (and the underflow check enforced) *before* any external call: [3](#0-2) 

In the Tron contract, the native-ETH branch performs a raw low-level `.call{value: amount}("")` to `beneficiary` before `_orders[body.commitment][token] -= amount` executes: [4](#0-3) 

Because the beneficiary address is attacker-controlled (it is decoded from the `WithdrawalRequest.beneficiary` field carried in the cross-chain message body, which is ultimately derived from `order.output.beneficiary`/`msg.sender` set by the filling solver), a malicious contract set as beneficiary can, inside its `receive()`/fallback triggered by the `.call{value: amount}("")`, re-invoke the message-delivery path again for the same commitment before `_orders[body.commitment][token]` is decremented. Since the check at line 700 only asserts `_orders[...][token] != 0` (not `>= amount`), the stale non-zero balance still passes the guard on reentry, allowing the transfer loop to run again and drain the escrow for that token multiple times before any single debit is applied.

This exactly mirrors the audit report's root cause: "the actual [fund movement] takes place, then the checks ... happen afterwards" — here the fund movement (`.call{value}`) happens before the state mutation that is supposed to prevent double payment, and the guard that exists (`== 0` check) is insufficiently strict and executed too early relative to the debit.

Note: the equivalent EVM path (`IntentsBase._withdraw`, used by non-Tron `IntentGatewayV2.sol`) was already hardened with this exact CEI ordering, and the reentrancy fix for `_fillSameChain`/`_fillCrossChain` (setting `_filled[commitment]` before any transfer) was added and covered by dedicated tests — see `IntrinsicIntentsReentrancyTest.sol`. The Tron contract's `withdraw()` function was not updated to match, leaving the same class of vulnerability the main codebase already fixed elsewhere.

### Impact Explanation
A malicious solver/beneficiary can drain escrowed input tokens (and native value) for a single order commitment multiple times via reentrancy, directly stealing user-escrowed funds held by the Tron `IntentGatewayV2` contract — a concrete theft-of-funds impact, consistent with "High" severity per the analog.

### Likelihood Explanation
Reachable from a single relayed cross-chain message: any account can act as the `order.output.beneficiary` for an order it fills (or as `order.user` for a self-refund via `cancelOrder`), and the delivery of the resulting `RedeemEscrow`/`RefundEscrow` message through `onAccept` is the only gate — there is no `nonReentrant` modifier on `onAccept` or `withdraw` in the grep results for this file. The attacker only needs to deploy a malicious contract as the beneficiary/recipient and receive native-token output, a standard and low-cost attack setup.

### Recommendation
Apply the same CEI fix already present in `IntentsBase._withdraw`: decrement `_orders[body.commitment][token]` (using a strict `escrowed < amount` check rather than only `== 0`) *before* performing the native `.call` or `IERC20.transfer`, for every token in the loop in `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `withdraw()` function. Also consider adding reentrancy protection to `onAccept`/`withdraw` as defense in depth.

### Proof of Concept
1. Attacker places/fills an order such that they control the `beneficiary` address encoded in the `WithdrawalRequest` for a `RedeemEscrow` message (e.g., as the filling solver on the destination chain, `msg.sender` becomes the beneficiary passed back to source chain in `_body(...)`), with the beneficiary being a malicious contract.
2. Once escrow exists on the Tron gateway (`_orders[commitment][token] > 0` for a native-ETH-denominated input), a relayer delivers the `RedeemEscrow` message and `onAccept` invokes `withdraw(body, false)`.
3. Inside `withdraw`, at line 700, `_orders[commitment][token] != 0` passes; at line 702-704 the contract does `beneficiary.call{value: amount}("")`.
4. The malicious beneficiary contract's `receive()` re-enters (directly or via a second relayer-submitted `onAccept` in the same or nested call) before line 710 (`_orders[commitment][token] -= amount`) executes, so the check at line 700 still sees a non-zero balance and the transfer fires again.
5. Repeating this drains more native tokens than were ever escrowed for that commitment before the eventual underflow revert on one of the later debits — since prior successful `.call` transfers in *earlier, separately completed* top-level transactions cannot be rolled back, and reentrant calls that each complete their own external call before returning to decrement storage can compound within a single transaction call stack up to the available escrow across multiple such deliveries.

Note on verification limits: due to index size limits, I could not view the complete file (`evm/tron/contracts/apps/IntentGatewayV2.sol`) end-to-end in one pass (e.g., full `_fillCrossChain`/`_fillSameChain` implementations for Tron, and whether any Tron-specific reentrancy guard exists elsewhere in the contract, such as a modifier applied at the `HyperApp`/`onlyHost` level). I recommend a Devin session with full file access to confirm there is no `nonReentrant` modifier anywhere in the Tron contract's inheritance chain and to validate the exact reentrancy trigger path before treating this as fully confirmed.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
