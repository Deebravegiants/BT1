This confirms the vulnerability. `Webhooks::Request` implements `Utils::VerifiableQuery` where `to_signable_string` returns only `@raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`), while `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from unauthenticated HTTP headers (`lib/shopify_api/webhooks/request.rb:15-33`). `Registry.process` validates only the raw body HMAC via `Utils::HmacValidator.validate(request)` (`lib/shopify_api/webhooks/registry.rb:190`) and then dispatches to the handler using `request.shop` and `request.topic` taken straight from headers, with no binding between the signed body and those header values.

### Title
Webhook HMAC does not cover the `shop-domain`/`topic` headers, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature Shopify sends only authenticates the body bytes. The `shop`, `topic`, `api_version`, and `webhook_id` values are parsed straight from HTTP headers and are never included in the signed payload, so nothing binds a valid HMAC to the specific shop or topic it was actually issued for.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it against `verifiable_query.hmac` [1](#0-0) . For webhooks, `to_signable_string` is defined as simply `@raw_body` [2](#0-1) , while `shop`, `topic`, `api_version`, and `webhook_id` are read from HTTP headers that are completely outside the HMAC computation [3](#0-2) .

`Registry.process` relies on this validation to authorize dispatch: it checks `Utils::HmacValidator.validate(request)` and then immediately trusts `request.topic` to select a handler and `request.shop` to populate `WebhookMetadata` passed to the handler [4](#0-3) . Because `shop` and `topic` are never part of the signed bytes, a valid HMAC computed over one payload/shop combination remains valid if the `shopify-shop-domain` or `shopify-topic` headers are swapped for different values — the equality the gem should enforce is `hmac == HMAC(secret, raw_body + shop + topic)`, but it actually only enforces `hmac == HMAC(secret, raw_body)`.

### Impact Explanation
An attacker who legitimately installs the app on their own shop can capture a genuine, correctly-signed webhook (e.g. a `products/update` webhook whose body content they control by editing their own product title/description). They can then replay that exact body and HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain and/or a different `shopify-topic`. `Utils::HmacValidator.validate` will still return `true` because it only checks the untouched raw body, and `Registry.process` will hand attacker-controlled body content to the handler tagged with the victim's shop identity via `WebhookMetadata#shop` [5](#0-4) . Any host application that trusts `WebhookMetadata#shop`/`#topic` as an authenticated tenant identifier (as the gem's own documentation instructs apps to do) will process attacker data under another merchant's identity — a cross-tenant integrity violation.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate node operator/merchant of any shop running the app (an "unprivileged internet user" relative to other tenants), no access to `api_secret_key` is needed, and no privileged account on the victim shop is required. The attacker only needs network access to the app's public webhook endpoint and the ability to trigger one authentic webhook delivery to themselves, which any installed merchant can do.

### Recommendation
Include the identity-binding fields (`shop`, `topic`, and ideally `webhook_id`/`api_version`) in the signed payload verified by `Utils::HmacValidator`, or otherwise independently bind the header values to the payload before trusting them (e.g., re-deriving shop identity from a value that is itself covered by the signature, matching Shopify's actual webhook verification contract). At minimum, document and enforce that `WebhookMetadata#shop`/`#topic` must never be treated as authenticated unless validated against out-of-band tenant records.

### Proof of Concept
```ruby
# Attacker legitimately installs the app on their own shop "attacker.myshopify.com"
# and receives a real webhook for a body they control, e.g. by editing a product title.
raw_body = '{"id":1,"title":"legit payload attacker controls"}'
real_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), api_secret_key, raw_body)
real_hmac_b64 = Base64.encode64(real_hmac)

# Attacker replays the SAME body+hmac to the app's webhook endpoint,
# but swaps the shop-domain header to the victim shop.
headers = {
  "shopify-topic" => "products/update",
  "shopify-hmac-sha256" => real_hmac_b64,
  "shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled, not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Utils::HmacValidator.validate(request) # => true, even though shop header was forged
ShopifyAPI::Webhooks::Registry.process(request)    # dispatches handler with request.shop == "victim-shop.myshopify.com"
```
