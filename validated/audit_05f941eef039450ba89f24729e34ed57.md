### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop-attribution spoofing via signature replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) that is handed to the app's webhook handler from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but the HMAC signature validated by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body. An attacker who can obtain one validly-signed webhook delivery (e.g. from their own installed shop) can replay it with an arbitrary `shop-domain` header value while keeping the original body and HMAC intact, and the gem will accept the request as valid and report it as originating from the attacker-chosen shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is read directly from an unauthenticated header and is never mixed into the signable string: [2](#0-1) 

`ShopifyAPI::Utils::HmacValidator.validate` (and `validate_signature`) only computes/compares the HMAC over `verifiable_query.to_signable_string`, i.e., the body — the `shop` header plays no role in the signature check: [3](#0-2) 

`Registry.process` validates the HMAC and then constructs `WebhookMetadata` — which is passed to the app's handler as the trusted tenant identity — directly from `request.shop`: [4](#0-3) [5](#0-4) 

The binding that should hold is: `shop attributed to the webhook == shop whose secret produced the HMAC over the entire authenticated payload`. In this implementation the equality actually enforced is: `HMAC(raw_body, secret) == HMAC(raw_body, secret)`, with `shop` entirely excluded from the signed material. Since Shopify apps typically share one `api_secret_key` across all installed shops (the same app secret is used to sign every merchant's webhooks), any user who has installed the app on their own store can capture one legitimately-signed delivery and resend it with the `shop-domain` header rewritten to any other shop domain string — the signature still validates because the body (which the signature covers) is unchanged, while the `shop` value delivered to the handler is fully attacker-controlled.

### Impact Explanation
This breaks the tenant boundary that `Registry.process`/`WebhookHandler.handle` is expected to enforce: the `data.shop` value handed to the application is supposed to reliably identify which merchant a webhook event belongs to, and apps commonly use it to select the session/access-token/database record to act on for that event. An attacker can forge webhook deliveries that pass HMAC validation yet claim to be for an arbitrary shop, resulting in cross-tenant data being attributed/written to a shop the attacker does not control. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation only requires the attacker to install the app on any shop they control (a standard, unprivileged path for any Shopify app that supports public installs) and to capture one webhook delivery, which is then replayed with a modified header. No access to `api_secret_key` or any other secret is required, since the signature is unaffected by header contents.

### Recommendation
Include the `shop` domain (and ideally `topic`) inside the signed content, or otherwise cryptographically bind the shop identity to the signature — e.g. compute/verify the HMAC over a canonical string incorporating `shop-domain` in addition to the raw body, or require the application to independently verify that `request.shop` corresponds to a shop with a currently active, previously-authenticated session before trusting it for tenant selection.

### Proof of Concept
```ruby
# Attacker installs the app on shop-attacker.myshopify.com and receives a legitimate webhook:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => real_hmac_from_shopify, # valid, computed by Shopify over the body only
  "x-shopify-shop-domain" => "shop-attacker.myshopify.com",
}
body = '{"id":1,...}' # captured raw body, unchanged

# Attacker replays the SAME body + SAME hmac, but swaps the shop header:
forged_headers = headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => Utils::HmacValidator.validate(request) returns true (HMAC only covers `body`),
#    handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)) is invoked
#    even though this event never came from victim-shop.
```
