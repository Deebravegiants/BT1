### Title
Webhook HMAC does not cover the `shop-domain` header, allowing cross-tenant webhook shop-identity spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the shop identity used downstream by the webhook processing pipeline is taken from the unauthenticated `x-shopify-shop-domain` / `shopify-shop-domain` header. The HMAC therefore does not bind the shop identity to the verified bytes, breaking the equality `shop authenticated by HMAC == shop trusted for webhook processing`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `Request#shop` is read directly from the `shop-domain` header without any cryptographic binding to that value: [2](#0-1) 

`Registry.process` validates the request using `Utils::HmacValidator.validate(request)`, which only verifies `request.to_signable_string` (i.e., the raw body) against the HMAC, then dispatches the handler using `request.shop`, which was never covered by that validation: [3](#0-2) 

`HmacValidator.validate` and `validate_signature` confirm the signable string (body-only) is the only material verified against the secret: [4](#0-3) 

Because the header carrying the shop's tenant identity is excluded from the signed content, a request whose body+HMAC pair is valid for one shop can be replayed with the `shop-domain` header value swapped to any other shop, and it will still pass `HmacValidator.validate`. The `WebhookMetadata` passed to the app's handler will report the attacker-chosen shop instead of the shop that actually produced/authorized the payload.

### Impact Explanation
This breaks the identity binding between the cryptographically verified bytes and the tenant (shop) that the host application will treat the event as belonging to, enabling cross-tenant webhook confusion: an app's webhook handler can be made to process a legitimately-signed payload under an attacker-chosen shop domain. Depending on how the host application keys per-shop side effects (e.g., syncing data, revoking access, updating records) off `WebhookMetadata#shop`, this can result in cross-tenant data corruption or unauthorized actions being attributed to/applied against a shop that never sent the webhook.

### Likelihood Explanation
Exploitation requires the attacker to possess one legitimately HMAC-signed body/HMAC pair (e.g., from a webhook delivered to their own shop, which they control) and the ability to submit an HTTP request to the app's webhook endpoint with a modified `shop-domain` header while reusing the original raw body and HMAC — no `client_secret` or access token is needed since the signature check only covers the body.

### Recommendation
Include the shop domain (and other identity-relevant headers such as topic) in the signable content, or independently verify that the `shop-domain` header matches an expected/allow-listed shop before trusting it in `WebhookMetadata`. At minimum, document and encourage host applications to cross check `request.shop` against a shop known to have installed the app before acting on the payload.

### Proof of Concept
1. App installed on `shop-a.myshopify.com`; Shopify delivers a legitimate webhook with body `B` and `x-shopify-hmac-sha256` computed over `B` using the app's `client_secret`.
2. Attacker (who controls `shop-a`, an unprivileged/legitimate merchant of the app) captures this valid `(B, HMAC)` pair.
3. Attacker sends a POST to the app's webhook endpoint with the same body `B` and same HMAC header, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(B)`; validation succeeds because `to_signable_string` never included the shop header.
5. The handler is invoked with `WebhookMetadata.shop == "shop-b.myshopify.com"`, even though the payload actually originated from `shop-a`, achieving cross-tenant shop-identity spoofing at the webhook layer.
