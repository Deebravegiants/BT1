Based on my research, I found a concrete analog in alt.fun's `Zap.createToken` flow.

### Title
Unvalidated creator-supplied `ltAddress` lets a malicious creator install an attacker-controlled "LT" as a token's trusted reserve asset, enabling theft of all buyers' USDC - (File: packages/contracts/src/Zap.sol)

### Summary
CVE-2022-48217 is a bug class about a component trusting an attacker-controlled parameter (`old_tf_topic_name`/`new_tf_topic_name`) to redirect its behavior to an unintended target, with the vendor's mitigation being "the programmer must validate parameters." alt.fun has the same shape: `Zap.createToken` / `Zap.createTokenWithPermit` accept a caller-supplied `params.ltAddress` that becomes the token's permanent, trusted reserve asset for every future trader's funds, with essentially no validation beyond a zero-address check.

### Finding Description
`Zap._createTokenInternal` only checks `params.ltAddress == address(0)` before calling `Bonding.launch`: [1](#0-0) 

There is no check that `ltAddress` is a genuine, protocol-recognized BounceTech LT (e.g., no allowlist/registry lookup, no interface/behavior verification). `Factory.createPair` is likewise generic and only enforces role/zero-address/no-duplicate-pair checks — it has no concept of a "legitimate LT": [2](#0-1) 

Once a token is launched with an attacker-chosen `ltAddress`, every subsequent `Zap.buy` for that token mints real USDC into that attacker-controlled contract and trusts whatever "tokens out"/exchange-rate values it reports (per the documented reserve-asset design where LT `exchangeRate`/mint/redeem are read live and trusted): [3](#0-2) 

Because the "LT" is an arbitrary contract of the creator's choosing rather than a vetted, protocol-approved asset, the creator fully controls `mint`/`redeem`/`exchangeRate` semantics for that contract instance. Real buyers' USDC sent via `Zap.buy` is transferred into this attacker-defined contract believing it to be a genuine LT.

### Impact Explanation
An attacker who launches a token via `Zap.createToken` with a self-authored "LT" contract can:
- Report an inflated `exchangeRate`/mint amount to make the curve believe minimal USDC backs a large LT balance, letting the attacker buy the entire 750M curve-sellable supply cheaply while genuine USDC from other unrelated buyers piles up inside their contract.
- Withhold or redirect the USDC that legitimate buyers send in via the mint call, since the "LT" contract is code the attacker fully controls.

This is concrete theft of trader funds reachable purely through `Zap.createToken`/`Zap.buy`, both explicitly in-scope unprivileged entry points.

### Likelihood Explanation
High — this requires no special access. Any address can call `Zap.createToken` with an arbitrary `ltAddress` pointing to a contract they deployed themselves, then advertise the token normally so unsuspecting buyers call `Zap.buy`.

### Recommendation
Require `ltAddress` to be checked against a protocol-maintained allowlist/registry of vetted BounceTech LT deployments (or a factory-verified bytecode/interface check) before `Bonding.launch` accepts it, rather than trusting any creator-supplied address as the reserve asset.

### Proof of Concept
1. Attacker deploys `EvilLT`, a contract that implements the LT interface (`mint`, `redeem`, `exchangeRate`, `baseToLtAmount`, `ltToBaseAmount`, `minTransactionSize`) but returns attacker-favorable values on `mint`/`exchangeRate` and allows the attacker to withdraw any USDC sent to it.
2. Attacker calls `Zap.createToken({..., ltAddress: address(EvilLT)}, seedUsdcAmount)` — passes because the only check is `ltAddress != address(0)` (`Zap.sol:222`).
3. Victims discover the token and call `Zap.buy(tokenAddress, usdcAmount, minTokensOut, referrer)`, sending real USDC that gets minted into `EvilLT`.
4. Attacker's `EvilLT.mint` logic diverts/retains the USDC (e.g., only forwards a fraction to satisfy curve accounting while keeping the rest), or the attacker simply withdraws accumulated USDC from `EvilLT` directly, resulting in permanent loss of victims' funds with no recourse in `Bonding`/`Zap`/`Pair`, none of which validate the LT's legitimacy.

    function _createTokenInternal(
        Bonding.LaunchParams calldata params,
        uint256 seedUsdcAmount
    ) internal returns (address tokenAddr) {
        if (params.ltAddress == address(0)) revert InvalidInput();
        // Mandatory seed buy. See `MIN_SEED_USDC` for the no-cap rationale.

        (tokenAddr,) = _s().bonding.launch(params, msg.sender);
        emit TokenCreated(tokenAddr, msg.sender, params.ltAddress);

    function createPair(
        address tokenA,
        address tokenB
    ) external onlyRole(BONDING_ROLE) returns (address) {
        if (tokenA == address(0) || tokenB == address(0)) revert ZeroAddress();
        if (router == address(0)) revert NoRouter();
        if (_pairs[tokenA][tokenB] != address(0)) revert PairExists();

        Pair pair = new Pair(router, tokenA, tokenB);
        _pairs[tokenA][tokenB] = address(pair);
        _pairs[tokenB][tokenA] = address(pair);

        pairFor[tokenA] = address(pair);
        ltFor[tokenA] = tokenB;

        emit PairCreated(tokenA, tokenB, address(pair), ++pairCount);
        return address(pair);
    }

## Buy Flow

1. `Zap.buy(tokenAddress, usdcAmount, minTokensOut, referrer)`
2. `Zap` pulls `usdcAmount` USDC and deducts the 0.75% Alt Fun fee up-front (forwarded to `FeeVault`, split 0.5% protocol / 0.25% creator). The fee is charged on every buy — curve **and** post-graduation — not just curve trades.
3. Net USDC is minted to LT
4. If on curve: routes through `Bonding.buy()` (the internal AMM `Router.sol`). If graduated: swaps on HyperSwap V2 (TOKEN/LT pool). The 0.75% Alt Fun fee is identical on both paths; post-grad, HyperSwap also charges its own 0.3% LP fee on the swap leg, on top of the Alt Fun fee.
5. Tokens sent to user; on a capped buy, any LT minted but not consumed by the curve is returned directly as LT, while unconverted USDC and the pro-rata fee over-charge are refunded in USDC

**Overflow buy protection.** On the final buy that would empty the curve, `Router.buy` caps `tokensOut` at the pair's real token balance and back-calculates the LT actually required (`amountInUsed`). `Bonding.buy` returns both `tokensOut` and `amountInUsed`. `Zap.buy` transfers the LT it minted but the curve didn't consume (`ltMinted - amountInUsed`) straight back to the buyer as LT — it is **not** redeemed, since round-tripping the dust overshoot through `redeem()` would re-incur the LT's redemption fee. Net USDC that was never minted into LT, plus the pro-rata fee over-charge, is refunded separately in USDC.
