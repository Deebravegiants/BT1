### Title
Unchecked-length copy into a fixed 32-byte buffer in `hyper-fungible-token`'s calldata origin resolution causes a runtime panic on a single relayed cross-chain message - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
The ALPINE-CVE-2022-24052 report describes a heap-based buffer overflow caused by copying attacker-controlled, variable-length data into a fixed-length buffer without first validating its length. The same bug class — a `copy_from_slice` into a fixed-size array performed without a preceding length check — is present in `Pallet::on_accept` of the `hyper-fungible-token` ISMP module, reachable from a single relayed cross-chain `PostRequest` carrying attacker-chosen ABI-encoded calldata.

### Finding Description
`on_accept` decodes the incoming request body into a `Message` and, when the message carries optional calldata (`message.data` non-empty), resolves an `origin` `AccountId` to dispatch a runtime call as. When no signature is supplied and the source chain is not EVM, the code does: [1](#0-0) 

```rust
let from_bytes = message.from.as_ref();
if source.is_evm() {
    T::EvmToSubstrate::convert(H160::from_slice(
        &from_bytes[from_bytes.len() - 20..],
    ))
} else {
    let mut account = [0u8; 32];
    account.copy_from_slice(from_bytes);
    account.into()
}
```

`account.copy_from_slice(from_bytes)` panics whenever `from_bytes.len() != 32`. `message.from` is a field of the ABI-decoded `Message` struct at [2](#0-1) , taken directly from the cross-chain request `body`, which is fully attacker-controlled by whatever application dispatched the original message on the source chain. Notably, the sibling conversion just above it for `message.to` explicitly validates the length before copying (`to_bytes.len() == 32` / `== 20`, else returns `HftError::InvalidRecipientLength`) — see [3](#0-2)  — but the equivalent guard is missing on the `from_bytes` path when `source` is non-EVM and no `signature` is present.

This mirrors the CVE's root cause exactly: a fixed-size destination buffer receives a copy of externally supplied bytes whose length was never checked against the buffer size before the copy executes.

### Impact Explanation
Rust's `copy_from_slice` panics (rather than corrupting memory) on a length mismatch, but that panic occurs deep inside runtime/module dispatch invoked from `pallet_ismp::Pallet::execute` via `handle_unsigned` (see [4](#0-3) ), which is the pallet's unsigned, permissionless entrypoint for delivering relayed ISMP messages. A panic raised inside WASM runtime execution is not a recoverable `Result` — it traps block/extrinsic execution. Any relayer or attacker able to get a single malformed `PostRequest` accepted by `on_accept` (source non-EVM, `data` present, no `signature`, `from` of a length other than 32) can force this panic on every node that attempts to execute the block containing it, which is a "route unable to deliver messages" condition for this application pallet — validators/collators either reject the block or repeatedly fail to execute it, halting further processing through this dispatch path until intervention.

### Likelihood Explanation
The path is reachable by a single relayed message: any account controlling (or forging on) a non-EVM `source` state machine can dispatch a `PostRequest` to a chain running `hyper-fungible-token`, with an ABI-encoded `Message.data` (non-empty, `SubstrateCalldata.signature = None`) and an arbitrary-length `Message.from`. No special privileges are required, and it only needs to pass ISMP request delivery/proof verification like any legitimate message — the crash occurs after acceptance, in application-level module handling.

### Recommendation
Validate `from_bytes.len()` before the `copy_from_slice`, mirroring the existing guard used for `to_bytes` a few lines above: accept exactly 32 bytes (and/or left-pad a 20-byte EVM-style address), and return `Err(HftError::InvalidRecipientLength(from_bytes.len()))` (or an equivalent new error variant) for any other length instead of panicking.

### Proof of Concept
1. From a non-EVM `source` state machine, dispatch (or have a relayer submit via `handle_unsigned`) a `PostRequest` whose `body` ABI-decodes into a `Message` with:
   - `data` = ABI-encoded `SubstrateCalldata { signature: None, runtime_call: <any> }` (non-empty),
   - `from` = any byte string whose length is not 32 (e.g., 5 bytes or 40 bytes).
2. Ensure `ContractToAsset`/`Precisions` mappings exist so execution reaches the "Execute optional calldata" branch.
3. When the pallet processes the message via `Pallet::on_accept`, execution reaches:
   `account.copy_from_slice(from_bytes)` with `from_bytes.len() != 32`, which panics and aborts execution of the block/extrinsic, effectively halting delivery through this path.

Note: I could not directly inspect the `Message`/ABI struct definition (its `from` field type/`SolValue` layout) in this pass to fully confirm it is unconditionally attacker-controlled bytes rather than a fixed-width ABI type; this should be verified against `modules/pallets/hyper-fungible-token/src/types.rs` (or wherever `Message` and `SubstrateCalldata` are declared) before treating this as fully confirmed.
