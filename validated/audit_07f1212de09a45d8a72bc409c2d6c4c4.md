### Title
Webhook `shop`, `topic`, and `webhook-id` headers are trusted for tenant/topic routing without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body when computing the HMAC, while `shop`, `topic`, and `webhook_id` are read directly from unauthenticated HTTP headers. `Registry.process` uses these header-derived values — most importantly `shop` — to route the webhook to a handler and to build `WebhookMetadata`, without any check that the header value is actually bound to the HMAC-verified payload.

### Finding Description
The identity binding that should hold is: `shop header == shop that produced/authorized the HMAC-covered body`. Instead, the gem verifies `HMAC(secret, raw_body)` only: [1](#0-0) 

but exposes `shop`, `topic`, and `webhook_id` purely from headers that are never included in the signed material: [2](#0-1) 

`HmacValidator.validate` confirms this: it only compares a signature computed over `verifiable_query.to_signable_string`, i.e. the raw body: [3](#0-2) 

`Registry.process` then trusts `request.topic` to pick the handler and forwards `request.shop` straight into `WebhookMetadata`, which the host application uses to attribute the payload to a tenant: [4](#0-3) 

Because `shop` (and `topic`/`webhook_id`) sit outside the HMAC's coverage, any request that carries a *valid* `(body, hmac)` pair for the app's secret will pass `Utils::HmacValidator.validate` regardless of what `shop`/`topic`/`webhook_id` headers say. The gem's documented contract is that the HMAC guarantees "this webhook body genuinely came from Shopify for the app," but it silently extends that guarantee to `shop`, which is never mixed into the signed bytes.

### Impact Explanation
A merchant who has the app installed on their own store can legitimately trigger a real Shopify webhook delivery to the app's endpoint (e.g. `orders/create`, `customers/data_request`) with attacker-influenced body content. They can capture that exact `(body, hmac)` pair from their own webhook delivery and replay it against the app's endpoint while substituting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with a *different, victim* shop domain that also has the app installed. Because `to_signable_string` never incorporates `shop`, `HmacValidator.validate` still succeeds, and `Registry.process` dispatches the handler with `WebhookMetadata#shop` set to the victim's shop. Any host application logic keyed off `data.shop` (the gem's own documented per-tenant identifier) will now write or act on attacker-controlled data under the victim's tenant — a cross-tenant confusion enabled purely by this gem's incomplete HMAC coverage.

### Likelihood Explanation
This requires no access to the app's `client_secret`, access tokens, or any other credential — only the ability to install the app on one's own store (a normal unprivileged action) and intercept/replay one's own legitimate webhook deliveries, which is straightforward with a proxy in front of the registered webhook URL.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) as part of the signed/verified material, or independently validate that the `shop` header matches metadata embedded in the verified body/topic before constructing `WebhookMetadata`. At minimum, `to_signable_string` in `lib/shopify_api/webhooks/request.rb` should not allow tenant-identifying headers to be decoupled from the HMAC-covered body when they are used for routing and tenant attribution downstream.

### Proof of Concept
1. Attacker's own store `attacker.myshopify.com` has the target app installed; they perform an action that triggers a real webhook (e.g. `orders/create`) to the app's webhook endpoint. They capture the raw request: headers include `x-shopify-hmac-sha256: <validHmac>`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`, and body `B`.
2. Attacker replays this exact request to the same endpoint, only changing `x-shopify-shop-domain` to `victim.myshopify.com` (a real shop with the app installed), keeping `<validHmac>` and body `B` unchanged.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (only body `B`) — the check passes because body and HMAC are unchanged: [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop` now resolves to `victim.myshopify.com`, even though the HMAC never covered that value: [6](#0-5) 
5. The host application processes attacker-controlled body `B` as if it legitimately originated from `victim.myshopify.com`, achieving cross-tenant data injection/confusion.
