### Title
Precision loss in `convert_to_balance` causes permanent fund loss for HyperFungibleToken cross-chain transfers with high `erc_decimals`-`local_decimals` gaps - (File: modules/pallets/hyper-fungible-token/src/impls.rs)

### Summary
`convert_to_balance()` in the `hyper-fungible-token` pallet divides the incoming ERC20-denominated `U256` amount by `10^(erc_decimals - local_decimals)` using plain integer division. Any burned/locked amount on the EVM `HyperFungibleToken` side smaller than that divisor is truncated to zero on the Substrate side — an exact analog of the reported `Scaler.scale()` precision-loss bug, but here it causes **permanent loss of user funds already burned on the source chain**, not just under-reported voting power.

### Finding Description
`HyperFungibleToken.send()` on the EVM side burns `params.amount` of the token from the caller and dispatches an ISMP POST request carrying the raw `amount` (in the EVM token's own decimals) [1](#0-0) .

When this request lands on the Substrate side, `Pallet::on_accept` converts the ERC20 amount to the local balance via `convert_to_balance`, using the registered `erc_decimals` (destination-chain precision, from `Precisions` storage) and the local asset's `decimals` [2](#0-1) .

`convert_to_balance` performs integer division that truncates toward zero:
```rust
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
``` [3](#0-2) 

`register_token`/`update_token` enforce `config.decimals >= local_decimals` [4](#0-3) , so `erc_decimals >= local_decimals` always holds, meaning the divisor `10^(erc_decimals - local_decimals)` is always well-defined and can be large whenever the EVM token has substantially more decimals than the local asset (e.g. an 18-decimal ERC20 bridged to a 6- or 10-decimal Substrate asset). Any raw ERC20 `amount` value smaller than that divisor — i.e. a real, non-trivial economic value on the EVM side — is floor-divided to `0`.

Critically, the tokens were already irrevocably burned on the EVM `HyperFungibleToken` contract before dispatch (`_burn(msg.sender, params.amount)` in `send()`), so once the amount truncates to zero on delivery, the value is unrecoverable through the normal path: `_mint(beneficiary, 0)` mints nothing. The same `convert_to_balance` function, with the identical truncation, is also used in the timeout/refund path (`on_timeout`) [5](#0-4) , so even a timed-out request cannot restore the lost value — the refund itself rounds to zero for the same amounts.

### Impact Explanation
This is a direct, permanent loss-of-funds bug reachable by any ordinary token bridger using the `HyperFungibleToken.send()` path — no privileged action required beyond normal token registration (which is expected to configure decimals for legitimate tokens, not attacker-controlled). Any user bridging an amount whose raw value (in the destination `Precisions`-registered `erc_decimals`) is smaller than `10^(erc_decimals - local_decimals)` has their tokens burned on the source chain and receives zero tokens on the destination — with no avenue for recovery, since both delivery (`on_accept`) and refund (`on_timeout`) use the same lossy conversion. This matches the "token bridge mint/burn" reachable category and constitutes concrete permanent freezing/loss of user funds.

### Likelihood Explanation
Likelihood is High: this triggers on ordinary user transactions whenever a token pair has a meaningful decimals gap (a very plausible, non-adversarial configuration — e.g. bridging an 18-decimal EVM token to a lower-decimal Substrate asset), and does not require any malicious actor, governance compromise, or unusual state. Small/dust transfers, or any transfer below the scaling threshold, silently destroy value.

### Recommendation
Change `convert_to_balance` to reject (or round up/require) conversions that would truncate a non-zero value to zero, e.g.:
```rust
let divisor = 10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32);
let scaled = value / U256::from(divisor);
if scaled.is_zero() && !value.is_zero() {
    return Err(...); // reject dust that cannot be represented, or use ceiling division
}
```
Alternatively, enforce a minimum transferable amount at the EVM `send()` level (reject amounts below the known destination divisor) so tokens are never burned/locked when the destination-side amount would round to zero, and apply the same fix to the `on_timeout` refund path.

### Proof of Concept
1. Register a token via `register_token` with `local_decimals = 6` (Substrate asset) and `config.decimals = 18` (EVM `HyperFungibleToken` contract's ERC20 decimals) — this passes the `ErcDecimalsBelowLocal` check since `18 >= 6`.
2. A user calls `HyperFungibleToken.send()` on the EVM chain with `amount = 999_999_999_999` (< `10^12`, i.e., less than 0.000001 tokens in 18-decimal terms but a legitimate dust-level real value) — tokens are burned via `_burn(msg.sender, amount)`.
3. On delivery, `on_accept` computes `erc_decimals - local_decimals = 12`, divisor `= 10^12`, and `convert_to_balance(999_999_999_999, 18, 6)` divides `999_999_999_999 / 10^12 = 0`.
4. `amount = 0` is minted/transferred to the beneficiary — the user's burned tokens are permanently lost.
5. If the message instead times out, `on_timeout` performs the identical division and also refunds `0`, confirming there is no recovery path.
