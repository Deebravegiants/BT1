### Title
Webhook shop-domain spoofing via HMAC/header binding gap enables cross-tenant webhook confusion - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as fully authenticated once `Utils::HmacValidator.validate(request)` succeeds, and then forwards `request.shop` (and `topic`, `webhook_id`, `api_version`) unchanged to the app's handler as trusted, verified metadata. In reality, the HMAC signature Shopify computes only covers the raw request body — never the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, `X-Shopify-Webhook-Id`, or `X-Shopify-Api-Version` headers. This is the same class of bug as the report: a field that is *acted on* (the tenant identity, `shop`) is not covered by the *cryptographic binding* (the HMAC), so the two can be desynchronized without invalidating the check.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0)  while `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers with no cryptographic linkage to the signed body: [2](#0-1) 

`Registry.process` performs a single boolean gate — `Utils::HmacValidator.validate(request)` — and then unconditionally trusts every attribute of `request`, including `request.shop`, to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the received signature — for a `Webhooks::Request` this is `HMAC(secret, raw_body)` only: [4](#0-3) 

Because the app's shared `client_secret` is the same for every shop that has the app installed, any shop where the attacker is a merchant/collaborator can trigger a real webhook (e.g., `orders/create`) and legitimately obtain a `(raw_body, hmac)` pair that validates. Nothing prevents that pair from being replayed to the same webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a different, victim shop's domain — `HmacValidator.validate` still returns `true` because it never inspects the shop header at all.

**Identity binding broken (as equality):**
`shop_header_claimed == shop_that_actually_produced_and_authorized(raw_body, hmac)` is never checked. The gem only checks `HMAC(secret, raw_body) == received_hmac`, which is independent of `shop_header_claimed`.

### Impact Explanation
Any app built on this gem that keys its multi-tenant data model, access-token lookups, or side effects (order sync, fulfillment, customer records, billing actions, etc.) off `WebhookMetadata#shop` will process attacker-supplied event bodies under a spoofed tenant identity. Since `Registry.process` provides no separate binding between `shop` and the signed bytes, an unprivileged internet user who can install the app on any shop (including a free/trial shop they control) can forge cross-tenant webhook deliveries — a cross-tenant access vector, consistent with the Critical impact category (cross-tenant access via a broken identity binding), without needing the app's `client_secret`, an access token, or any privileged account.

### Likelihood Explanation
Exploitation requires only: (1) installing the target app on any shop the attacker controls (a normal, unprivileged operation for public apps), (2) capturing one legitimate `(raw_body, X-Shopify-Hmac-Sha256)` pair from a webhook Shopify sends to the app for that shop, and (3) POSTing that exact body/HMAC pair directly to the app's public webhook endpoint with a forged `X-Shopify-Shop-Domain` header. No secret material, TLS interception, or social engineering is needed, and the gem's own `Registry.process`/`HmacValidator` code provides no defense against this — the check is architecturally incapable of catching it because the shop header is outside the signed payload.

### Recommendation
Do not treat `Utils::HmacValidator.validate(request)` as validating the entire `Request`, including its headers. At minimum:
- Include the tenant-identifying headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signable payload used for verification, or otherwise cryptographically bind them to the body (e.g., verify `shop` against a value embedded/echoed in the payload or against the session/shop that the app independently expects for that specific webhook subscription/topic).
- At the very least, document clearly in `Registry.process`/`WebhookMetadata` that `shop`/`topic`/`webhook_id` are **not** covered by the HMAC and require independent verification (e.g., cross-checking against an installed-shop registry) by the host application before being trusted for authorization decisions.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers a webhook event (e.g. creates an order), so Shopify POSTs a legitimately-signed webhook to the app's endpoint:
   - Headers: `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`, `X-Shopify-Hmac-Sha256: <valid HMAC of body>`
   - Body: attacker-controlled JSON (attacker fully controls this event's field values, e.g. `email`, custom line items, etc., since it's their own shop/order).
2. Attacker captures the raw request body bytes and the exact `X-Shopify-Hmac-Sha256` value.
3. Attacker replays the identical body and HMAC header directly to the app's public webhook URL, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, raw_body)` — this still matches, because `shop` was never part of the signed input: [5](#0-4) 
5. The check passes and `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built with `shop = "victim-shop.myshopify.com"` and handed to the app's handler as fully trusted, verified data — even though the body content originated from the attacker's own shop, not the victim's: [6](#0-5)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
