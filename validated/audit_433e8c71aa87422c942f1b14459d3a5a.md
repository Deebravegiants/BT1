### Title
Checks-Effects-Interactions violation in `withdraw()` allows reentrant over-claiming of escrowed order funds - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2` releases escrowed order tokens to a beneficiary via a raw `token.call(...)` *before* decrementing the `_orders[commitment][token]` escrow accounting, unlike the hardened EVM version which decrements first. A malicious, attacker-controlled ERC20 used as an order's input token can re-enter during the transfer and drain more value than was ever escrowed for that commitment — the same "claim more than what was recorded" bug class as the reported over-claiming issue, just realized through reentrancy rather than a missing `totalAmount` check.

### Finding Description
`withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` performs, per token in the withdrawal request: [1](#0-0) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    ...
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();

        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");
            ...
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
            ...
        }

        _orders[body.commitment][token] -= amount;   // effect happens AFTER the external call
        ...
    }
```

The only guard is `_orders[body.commitment][token] == 0` (escrow non-empty), not `amount <= _orders[body.commitment][token]`. The escrow debit (`-= amount`) happens strictly *after* the external `token.call`. Since `order.inputs[i].token` is fully attacker-chosen at `placeOrder` time (any ERC20 address, including one the attacker deployed and controls the bytecode of), the "ERC20" `transfer()` invoked during withdrawal can execute arbitrary attacker logic, including re-entering `withdraw()` (or any other state-mutating function reachable from `onAccept`) before the escrow accounting is updated.

This is the exact defect class the audit report describes: a value-releasing function ("claim") that fails to bind the amount released against the authoritative committed record before performing the payout, letting an actor extract more than was ever escrowed for the commitment. This repo has already independently identified and fixed this exact CEI ordering in the mainline EVM contract's `_withdraw`: [2](#0-1) 

```solidity
function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
    ...
    uint256 escrowed = _orders[body.commitment][token];
    if (escrowed == 0) revert UnknownOrder();

    _orders[body.commitment][token] = escrowed - amount;   // effect BEFORE interaction
    if (token == address(0)) {
        _sendValue(beneficiary, amount);
    } else {
        IERC20(token).safeTransfer(beneficiary, amount);
    }
}
```

The Tron contract at `evm/tron/contracts/apps/IntentGatewayV2.sol` was not updated to this same ordering, and it also uses a raw low-level `.call` to an arbitrary token contract rather than `safeTransfer`, which is exactly the primitive needed for a malicious token to hijack control flow mid-payout.

### Impact Explanation
Any account can `placeOrder()` with a self-deployed malicious ERC20 as an input token. Once a solver fills that order and the cross-chain `RedeemEscrow`/`RefundEscrow` message triggers `onAccept` → `withdraw()`, the malicious token's `transfer()` implementation runs with control of execution before `_orders[commitment][token]` is decremented. It can re-enter and trigger further releases against the same (not-yet-decremented) escrow balance, or manipulate other accounting state that reads `_orders` mid-flight, permanently draining more of the gateway's real (non-malicious) token/native balances than the attacker ever escrowed — a direct theft-of-funds / unbacked-payout scenario reachable from a single relayed cross-chain message with no privileged access required.

### Likelihood Explanation
High. `order.inputs[i].token` is entirely attacker-controlled at order-placement time — no allowlist is enforced on escrowable tokens in this contract. Deploying a malicious ERC20 and placing an order with it is a single unprivileged transaction; getting a real (or self-controlled) solver/relayer to complete the fill/redeem flow is the normal, expected path for the protocol, requiring no special conditions beyond routine use.

### Recommendation
Apply the same checks-effects-interactions fix already present in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw` to `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw`: decrement `_orders[body.commitment][token]` by `amount` (reverting on underflow, i.e. rejecting `amount > escrowed`) *before* performing the token/native transfer, and replace the raw `token.call(...)` with `SafeERC20.safeTransfer`, matching the mainline contract. Additionally consider a `nonReentrant` guard on the withdrawal path as defense in depth.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC20 whose `transfer(address to, uint256 amount)` calls back into `IntentGatewayV2` (e.g., re-invoking the delivery path that leads to `withdraw()` for the same `commitment`, or exploiting the reentrant window against another commitment sharing this token) before returning.
2. Attacker calls `placeOrder()` escrowing `amount = X` of `EvilToken` for a same-chain or cross-chain order.
3. A solver fills the order; the settlement message reaches `onAccept()` → `withdraw()`.
4. During the `token.call(transfer, beneficiary, amount)` step, `EvilToken.transfer` re-enters before `_orders[commitment][token] -= amount` executes, causing a second release to be authorized against the still-unchanged (non-zero) escrow balance.
5. The gateway ends up paying out more value than was ever escrowed for the commitment, i.e., unbacked disbursement / theft of protocol funds.
