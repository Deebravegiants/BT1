### Title
Attacker-supplied malicious ERC20 can spoof `balanceOf` to satisfy the balance equation and mint unbacked shielded UTXOs - ([File: contracts/Hinkal.sol])

### Summary
The balance-equality check in `Hinkal.transact` (`contracts/Hinkal.sol:78-146`) trusts `getBalancesForArray`, which calls `balanceOf(address(this))` on every token address supplied by the caller in `circomData.erc20TokenAddresses`. Because a caller may list any ERC20 contract they deploy themselves, they can implement `balanceOf` to detect the two distinct read points (`oldBalances` at line 78 and `newBalances` at line 88) and return values engineered so `balanceDif == amountChanges[i] + utxoAmount` regardless of any real token movement.

### Finding Description
Equality claimed broken: `balanceDif` (derived purely from `balanceOf` reads at `contracts/Hinkal.sol:78` and `:88`) versus actual physical custody change of tokens held by `Hinkal`.

Code path: [1](#0-0) 
`oldBalances`/`newBalances` are collected strictly via `getBalancesForArray(circomData.erc20TokenAddresses)` — an array fully controlled by the caller, with no on-chain allowlist restricting which ERC20 contracts may be referenced. `balanceDif` is then computed as `newBalances[i] - oldBalances[i]` (or adjusted for `msg.value` for the native-token sentinel `address(0)`). [2](#0-1) 
The core accounting invariant then requires `balanceDif == (onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount`. This is the *only* place the protocol checks that the SNARK-proven internal accounting (`amountChanges`, `utxoAmount`, both freely chosen by the prover subject to circuit constraints on internal consistency) corresponds to something that actually happened on-chain in terms of real token custody.

Root cause: this check assumes `balanceOf` is an honest, non-reentrant, stateless reporter of real token custody. Nothing in `performHinkalChecks`, `verifyProof`, `rootHashExists`, or the circuit constraints (`inTotal + amountChanges === outTotal`, `OverflowPreventer`, etc.) validates that `erc20TokenAddresses[i]` is a legitimate, well-behaved ERC20 — those constraints only enforce *internal* arithmetic consistency of the shielded pool, not correspondence to real value. Since an unprivileged attacker can deploy their own ERC20 and self-list it in `erc20TokenAddresses`, they fully control what `balanceOf(address(hinkal))` returns at both read points. A contract that keeps an internal call counter and returns `oldValue` on the first call and `oldValue + amountChanges[i] + utxoAmount` (or whatever satisfies the equation) on the second call will make `balanceDif` match the required value with zero real value ever entering or leaving the contract.

Attacker's exact call: attacker deploys `EvilToken`, lists it as `circomData.erc20TokenAddresses[i]`, self-generates a valid proof for their own commitments with `amountChanges[i]` and an off-chain `utxoAmount` of their choosing (e.g., 1,000,000 tokens), and calls `Hinkal.transact(...)`. `EvilToken.balanceOf(hinkal)` returns a crafted value on the second invocation so the equality holds, `insertNullifiers`/`insertCommitments` proceed normally, and a new shielded UTXO for `EvilToken` with the attacker-chosen amount is committed into the tree — fully unbacked by any real transfer.

Why existing guards fail: `performHinkalChecks`, `dimensionsCheck`, `verifyProof`, `rootHashExists`, and the circuit's internal arithmetic constraints only validate proof/commitment/nullifier consistency and the shielded pool's *closed* arithmetic; none of them constrain `erc20TokenAddresses` to a whitelist of real, trusted tokens, and none of them independently confirm token custody outside of the single, spoofable `balanceOf` read pair.

### Impact Explanation
The attacker can mint a shielded UTXO for an arbitrary amount of a self-deployed token with no backing collateral, satisfying the Critical category "minting shielded value without backing." Because the token is self-deployed and self-listed, this by itself does not directly drain other users' real assets of *other* tokens; but it lets the attacker mint arbitrary, self-created shielded balances that pass all on-chain accounting checks, and repeatably (once per transaction, unlimited transactions) create long-lived commitments in the Merkle tree recorded as legitimate protocol state. If the attacker later relists the same malicious token address in contexts where legitimate holders also transact in tokens sharing that address space, or where the created UTXO can be laundered/exchanged via other Hinkal flows (external actions/hooks) into other tokens, this could escalate to draining shared reserves. At minimum this breaks the fundamental "backing" invariant of the protocol for any attacker-controlled token.

### Likelihood Explanation
Preconditions are minimal and fully within an unprivileged attacker's control: deploy an ERC20 with a stateful `balanceOf`, list it in `erc20TokenAddresses`, and generate a self-consistent proof (attacker owns the input/output commitments and thus the circuit constraints trivially hold for internally-consistent values). No relay, admin, or victim cooperation is required. Cost is only gas plus the trivial cost of deploying the malicious token. It is fully repeatable per transaction.

### Recommendation
Do not rely solely on `balanceOf` deltas from arbitrary, caller-supplied token addresses as the sole physical-reality check. Options: (1) require tokens used in `erc20TokenAddresses` to come from a protocol-maintained allowlist/registry vetted by governance rather than being freely specified by `circomData`; (2) perform balance reads using `SafeERC20`-style calls plus additional invariant checks (e.g., verify `totalSupply`/code-size/absence of proxy delegatecall patterns) — though this is not a complete fix since `balanceOf` can still lie for any code; (3) most robust: track custody using internal accounting for reserves the protocol manages (e.g., mirror deposits/withdrawals independent from live `balanceOf` reads, or use pull-based deposit patterns with `transferFrom` return value checks and a separate ledger of "shielded-pool-owned balance" not derived from live external calls at two points within the same transaction).

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal` with required constructor args (merkle args, helper, helper manager) and a `VerifierFacade` mock that accepts a stubbed valid proof (or use real proof generation for an internally consistent commitment set owned by the attacker).
2. Deploy `EvilToken` implementing `IERC20`, with `balanceOf(address who)` that: on 1st call returns `_baseBalance`; on 2nd call (tracked via a counter incremented each call) returns `_baseBalance + expectedAmountChange + expectedUtxoAmount`.
3. Register `EvilToken` in `circomData.erc20TokenAddresses[0]`, set `circomData.amountChanges[0] = expectedAmountChange`, `circomData.onChainCreation[0] = false`, and craft an off-chain UTXO commitment for `EvilToken` with `utxoAmount = expectedUtxoAmount` matching the attacker's own proof/circuit inputs.
4. Call `hinkal.transact(a, b, c, dimensions, circomData)` from an unprivileged attacker EOA, with `EvilToken` never transferring any real tokens to/from `Hinkal` (i.e., no `transfer`/`transferFrom` logic invoked at all, or it's a no-op).
5. Assert:
   - `balanceDif` computed inside `transact` (`newBalances[0]-oldBalances[0]`) equals `amountChanges[0] + utxoAmount` (both sides captured via emitted events or a test harness exposing internal state).
   - The transaction succeeds and `insertCommitments` stores a new commitment for `EvilToken` with `utxoAmount`.
   - Confirm via `EvilToken`'s internal ledger (or absence of any real transfer call) that zero real tokens moved into/out of `Hinkal`, proving the mint is fully unbacked.

Note: I was unable to fully inspect `getBalancesForArray`'s exact implementation file (likely `HinkalBase.sol` or `Transferer.sol`) within the available tool calls to confirm whether it uses `staticcall` or a try/catch wrapper that might alter reentrancy/state assumptions; a background Devin session with full repo access should verify this detail before finalizing the PoC.
