### Title
Webhook shop identity is unauthenticated (not covered by HMAC) allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, but the `shop` value used downstream to attribute/route the webhook to a tenant is read from an HTTP header that is never included in that signature. This breaks the equality that should hold: `shop covered by the verified HMAC == shop the application acts on`.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 

`to_signable_string` returns only `@raw_body`, so the HMAC (`hmac-sha256` header, verified via `HmacValidator.validate`) authenticates the byte content of the body — nothing else.

However, the `shop` accessor used to identify *which tenant* the webhook belongs to is pulled straight from the `X-Shopify-Shop-Domain` HTTP header, independent of the signed body: [2](#0-1) 

Likewise `topic`, `api_version`, and `webhook_id` are all taken from headers that are outside the HMAC-signed data: [3](#0-2) 

The documented consumption pattern confirms `request.shop` (via `WebhookMetadata.shop`) is the value handlers use to attribute work to a specific store — e.g. enqueuing a background job keyed by `shop_domain`: [4](#0-3) [5](#0-4) 

`Registry.process` only checks the HMAC over the request (i.e., over `@raw_body`) before invoking the handler with the header-derived shop/topic/webhook_id metadata — it performs no check that the `shop-domain` header is consistent with anything inside the signed body.

**Identity binding broken (as equality):**
`shop authenticated by HMAC` (∅ — HMAC only covers raw body bytes) `≠` `shop the application uses as the tenant key` (`X-Shopify-Shop-Domain` header, unauthenticated).

### Impact Explanation
Because the shop-domain header sits outside the signed payload, any party who can obtain one legitimately-signed `(raw_body, hmac)` pair for their own shop (any merchant that installs the app can trivially do this, since they receive their own webhooks) can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header value naming a different, victim tenant. Since `HmacValidator.validate` only checks the raw body bytes against the secret, the forged request passes validation, and the handler is invoked believing the webhook body belongs to the victim shop. Depending on how the host application uses `data.shop` (as documented: to key jobs, look up the corresponding session/access token, or write data under that shop's tenant record), this enables cross-tenant data confusion/injection — the exact class of impact ("cross-tenant access") called out as in-scope, achieved without any access token, secret, or privileged account, purely by an internet user capable of installing the app on their own store to obtain a valid signed webhook and then replaying it against the shared public webhook endpoint with a different `shop-domain` header.

### Likelihood Explanation
Likely reachable: webhook endpoints are, by design, publicly reachable without further authentication (verification is expected to be solely via the HMAC check), and any user can self-install the app to legitimately harvest a valid `(body, hmac)` pair for a topic of their choosing. Forging the `X-Shopify-Shop-Domain` header on a direct HTTP POST requires no special access.

### Recommendation
Bind the shop identity to the signed material, not just to a header. Options:
- Include the shop-domain (and topic/webhook-id) in the HMAC computation (`to_signable_string`) instead of, or in addition to, the raw body, so any header tampering invalidates the signature.
- Alternatively, cross-check the `shop-domain` header against a shop identifier embedded in the parsed body/topic where available, and reject on mismatch.
- Document/enforce that consumers must not trust `request.shop`/`data.shop` for tenant attribution unless it is cryptographically bound to the verified payload.

### Proof of Concept
1. Attacker installs the target app on their own development store, and registers for a webhook topic (e.g., `orders/create`), receiving a valid webhook POST to the app's public callback endpoint with headers `X-Shopify-Hmac-Sha256: <hmac>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, and the raw JSON body.
2. Attacker resends the identical raw body and `X-Shopify-Hmac-Sha256` value to the same endpoint, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request#hmac`/`to_signable_string` only look at the raw body, so `HmacValidator.validate` still succeeds (the body bytes and secret match).
4. `Registry.process` invokes the app's handler with `data.shop == "victim-shop.myshopify.com"`, causing the host application to process attacker-controlled webhook content under the victim tenant's identity.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
