This confirms the vulnerability: the gem's own documentation states `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" — but the HMAC only covers the raw body, not the `shop`, `topic`, or `webhook_id` headers that the app trusts as tenant identity.

### Title
Webhook HMAC covers only the request body, not the `shop-domain`/`topic`/`webhook-id` headers, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` (invoked from `ShopifyAPI::Webhooks::Registry.process`) authenticates solely the JSON body bytes. The `shop`, `topic`, and `webhook_id` accessors are read straight from HTTP headers and are never included in the signed material, yet `Registry.process` forwards them unauthenticated into `WebhookMetadata` passed to the app's `WebhookHandler`.

### Finding Description
`Request#hmac` is decoded from the `shopify-hmac-sha256`/`x-shopify-hmac-sha256` header, and `Request#to_signable_string` returns just `@raw_body`: [1](#0-0) 

`Registry.process` relies entirely on this validation before dispatching to the handler with `request.shop`, `request.topic`, and `request.webhook_id`, none of which were part of the signed bytes: [2](#0-1) 

`HmacValidator.validate` computes the HMAC only over `verifiable_query.to_signable_string`, which for webhooks is the body: [3](#0-2) 

This breaks the intended identity binding `HMAC(secret, signed_bytes) == received_hmac` from also covering `shop`. The documentation explicitly promises that `Registry.process` "will verify the request did indeed come from Shopify," implying the whole message (including which shop it's for) is authenticated: [4](#0-3) 

In practice: an attacker who has captured or replayed one legitimate Shopify webhook delivery (body + valid HMAC digest for that body, e.g. from their own shop's webhook or a leaked delivery log) can resubmit that exact `raw_body`/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header to name a *different* victim shop. Because `to_signable_string` never includes the shop header, `HmacValidator.validate` still returns `true`, and `Registry.process` calls the handler with `WebhookMetadata.new(shop: <attacker-chosen shop>, ...)`, causing the host application to attribute the (attacker-controlled/replayed) payload to a tenant it did not originate from.

### Impact Explanation
This crosses the tenant boundary the gem is supposed to enforce: an app relying on `data.shop` from `WebhookMetadata` to route data/updates to per-tenant storage will process attacker-influenced webhook content under an arbitrary victim shop's identity, since the shop identity is unauthenticated relative to the payload. This matches the Critical "cross-tenant access" impact category, since data intended for/about one shop can be injected/attributed to another shop purely by manipulating an unsigned header.

### Likelihood Explanation
Likelihood is Medium-High for any app that operates a public webhook endpoint (a documented, standard integration pattern) and stores/acts on more than one shop: the attacker needs only one legitimately-signed webhook payload (their own shop's, or one otherwise captured) and the ability to POST to the app's webhook route with modified headers — no secret material or privileged account required.

### Recommendation
Include the tenant-identifying headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signed material used for HMAC verification — e.g. bind them via an HMAC-covered canonical string (as Shopify does not sign these headers itself, the gem should derive/verify shop identity through another authenticated channel, such as looking up the webhook subscription by `webhook_id` via the Admin API using a session already bound to the expected shop) rather than trusting the raw header value as the authenticated tenant for the payload. At minimum, document prominently that `shop`/`topic`/`webhook_id` are NOT covered by the HMAC and must not be trusted as tenant identifiers without independent verification (e.g., matching against a shop's own persisted webhook registration ID).

### Proof of Concept
1. App receives a legitimate Shopify webhook for `shop-a.myshopify.com` with body `B` and header `shopify-hmac-sha256: H`, where `H = HMAC(secret, B)`.
2. Attacker (who controls or observed this delivery, e.g. it was sent to their own app's endpoint for their own shop) replays the exact `(B, H)` pair to the victim app's webhook route, but sets `shopify-shop-domain: shop-b.myshopify.com` (a different, victim shop) instead of `shop-a.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "shopify-shop-domain" => "shop-b.myshopify.com", "shopify-hmac-sha256" => H})` is constructed; `hmac` still decodes to `H`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which computes `HMAC(secret, request.to_signable_string)` = `HMAC(secret, B)` = `H`, matching — validation succeeds.
5. The handler is invoked with `WebhookMetadata.new(shop: "shop-b.myshopify.com", body: JSON.parse(B), ...)`, and the host app processes/stores `B`'s data as belonging to `shop-b`, even though it was never actually sent by Shopify for `shop-b`. [5](#0-4) [6](#0-5)
