Based on my investigation, I found a valid analog in `EvmHost.sol`'s fee-payment swap logic, reachable from any unprivileged message dispatcher submitting a POST or GET request.

### Title
Unbounded native-token-to-fee-token swap in `EvmHost.dispatch()` allows sandwich attacks that overcharge dispatchers with no slippage protection - (File: `evm/src/core/EvmHost.sol`)

### Summary
When a caller dispatches a POST or GET request paying with native token (`msg.value`), `EvmHost.dispatch()` swaps the entire `msg.value` for an exact amount of fee tokens (`post.fee`/`get.fee`) via `swapETHForExactTokens`, with no minimum-output or maximum-input protection beyond the raw `msg.value` itself, and no explicit refund-to-caller path for unspent ETH.

### Finding Description
Both `dispatch(DispatchPost)` and `dispatch(DispatchGet)` perform this pattern: [1](#0-0) [2](#0-1) 

`swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` uses the caller's full `msg.value` as the implicit `amountInMax` for an exact-output swap, and sets the swap recipient/`msg.sender` for the router call to `address(this)` (the `EvmHost` contract), not the original dispatcher. This is directly analogous to the reported `SingleSidedLiquidityVault.withdraw` issue: a caller-facing operation that depends on an AMM price at execution time has no independently-validated bound protecting the caller from adverse price movement, and the only "protection" is a raw value the caller themselves must guess correctly off-chain. Because Uniswap V2's `swapETHForExactTokens` refunds any unspent ETH to `msg.sender` of the router call — which here is `EvmHost`, not the dispatching user — any leftover ETH from an over-provisioned `msg.value` is retained by the host contract rather than returned to the caller. Combined with the deadline being `block.timestamp` (no real time buffer, so it offers no protection against being included in a manipulated block), a searcher can sandwich the dispatch transaction to move the ETH/feeToken price unfavorably right before it executes, which will either (a) cause the swap to consume more of the provided `msg.value` than the honest price would have required (with the excess not returned to the caller), or (b) cause the transaction to revert if `msg.value` is insufficient at the manipulated price, forcing failed dispatches and wasted gas for legitimate relayers/apps that pay fees this way.

### Impact Explanation
This affects any unprivileged actor dispatching a POST/GET request and paying fees in native token — a common, permissionless path (any `HyperApp`, intent order placer with `nativeValue`, or direct integrator calling `IDispatcher.dispatch{value}`). A sandwiching searcher can extract value from dispatchers by manipulating the local Uniswap V2 pool price around the dispatch transaction, causing the dispatcher to receive less favorable execution and, because unspent ETH is refunded to the host contract instead of the caller, potential permanent loss of the excess for that specific caller (locked/stranded in `EvmHost`, effectively a griefing/theft vector against the fee-paying party). This qualifies as a Medium-severity "concrete...permanent freezing of funds" style issue matching the report's financial-loss class.

### Likelihood Explanation
Uniswap V2 pools backing `feeToken`/native pairs on EVM chains are typically not extremely deep for niche fee tokens, and dispatch transactions are public in the mempool prior to inclusion, making sandwich attacks straightforward for MEV searchers. Every native-token-funded `dispatch()` call is exposed to this, making the likelihood non-trivial for any chain where the configured Uniswap V2 pool has moderate-to-thin liquidity.

### Recommendation
Require callers to supply an explicit `amountInMax` (distinct from `msg.value`, or bounded relative to an oracle/TWAP price) for the native-to-fee-token swap, and refund any genuinely unspent ETH directly to `_msgSender()` rather than leaving it in the `EvmHost` contract. Additionally, replace `block.timestamp` as the swap deadline with a caller-supplied deadline to give real sandwich/staleness protection.

### Proof of Concept
1. Attacker observes a pending `dispatch(DispatchPost)` (or `DispatchGet`) transaction in the mempool with `msg.value = X` intended to cover `post.fee` fee-tokens via the configured Uniswap V2 pool.
2. Attacker front-runs with a large buy of the fee token against native token, moving the pool price so that more native ETH is required to receive `post.fee` fee-tokens.
3. The victim's `swapETHForExactTokens{value: X}(post.fee, path, address(this), block.timestamp)` executes at the manipulated price:
   - If `X` still covers the manipulated price, the router consumes more ETH than the fair-market amount and refunds the (now smaller) leftover to `address(this)` (the `EvmHost` contract) rather than the caller — the caller's unrecovered ETH is effectively lost.
   - If `X` no longer covers the manipulated price, the call reverts (`INSUFFICIENT_INPUT_AMOUNT`/similar), and the entire dispatch fails, wasting the caller's gas.
4. Attacker back-runs to reverse the price manipulation and capture the spread, profiting from the victim's overpayment. [1](#0-0) [2](#0-1)
