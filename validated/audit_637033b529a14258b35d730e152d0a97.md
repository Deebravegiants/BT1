Based on my research, I found a real analog in `pallet-hyper-fungible-token`'s decimal-scaling helpers.

### Title
Incorrect decimal scaling in `convert_to_balance`/`convert_to_erc20` silently drops scaling when local decimals exceed ERC20 decimals - ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
`pallet-hyper-fungible-token`'s `send`/`on_accept` handlers convert amounts between the local (Substrate) asset precision and the ERC20 (EVM) precision using `convert_to_erc20` and `convert_to_balance`. Both helpers use `erc_decimals.saturating_sub(local_decimals)` to derive the scale factor, which silently becomes `0` (a no-op scale of `10^0 = 1`) whenever `local_decimals > erc_decimals`, instead of correctly dividing/multiplying by the inverse factor in that case — the same class of mistake as the reported `MarketFinancials::trade_pt` bug, where the wrong arithmetic direction/rate was applied to a cross-unit conversion.

### Finding Description
`convert_to_erc20` is documented as "Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision": [1](#0-0) 

and `convert_to_balance` as "Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision": [2](#0-1) 

Both use `erc_decimals.saturating_sub(local_decimals)`. This is only correct under the implicit assumption `erc_decimals >= local_decimals` (which happens to hold for the shipped `BridgeToken` example, 18 vs 12 decimals). If a token is registered where the local asset has *more* decimals than its EVM ERC20 counterpart (e.g., a local 18-decimal asset paired with a 6-decimal ERC20 like USDC), `saturating_sub` clamps to `0`, so `convert_to_erc20` multiplies by `10^0 = 1` instead of dividing by `10^12`, and `convert_to_balance` divides by `10^0 = 1` instead of multiplying by `10^12`. This is exactly the reported bug class: the wrong operation (or a degenerate no-op) is substituted for the correct scaling direction in a value conversion used to size a cross-chain transfer.

`send()` calls `convert_to_erc20(amount, erc_decimals, decimals)` to build the outbound `Message.amount` that the EVM `HyperFungibleToken`/`WrappedHyperFungibleToken` contract will mint: [3](#0-2) 

`register_token`/`update_token` populate the `Precisions` map with the EVM-side decimals for a token pair; I was not able to fully confirm (tool budget exhausted before reading `register_token`'s validation logic in `module.rs`/`lib.rs`) whether the pallet enforces `erc_decimals >= local_decimals` at registration time. If it does not, a token owner (or the pallet's privileged `CreateOrigin`, depending on config) registering a pair with `local_decimals > erc_decimals` would cause every subsequent `send` to mint on the EVM side an amount `10^(local_decimals - erc_decimals)` times larger than intended, and every `on_accept` to under-credit the local balance by the same factor.

### Impact Explanation
If reachable with attacker-controlled decimal configuration (i.e., if `register_token`/`update_token` do not enforce `erc_decimals >= local_decimals`), this is an unbacked-mint / fund-freezing bug: the EVM contract would mint far more tokens than were escrowed/burned on the Substrate side (inflating supply beyond backing), while the reverse path (`on_accept`, mint on the Substrate side) would under-mint, effectively stranding value burned on the EVM side. Both are Critical/High-severity token-bridge integrity issues (unbacked mint, permanent freezing of funds) squarely within the requested "token bridge mint/burn" reachable-path category.

### Likelihood Explanation
Likelihood depends entirely on whether decimal validation exists at token registration and whether `CreateOrigin` is permissioned in a way that could plausibly configure such a pair (deliberately or by misconfiguration) — I could not verify this within my remaining tool budget. If `register_token` is privileged/governance-only and always validates `erc_decimals >= local_decimals`, this finding has no exploitable path and should be considered informational only. This is a genuine gap in my analysis: I found the flawed arithmetic (`saturating_sub`) but not confirmation of the calling-context guardrails.

### Recommendation
1. Replace the `saturating_sub`-based single-direction scaling with a signed/bidirectional comparison that multiplies when `erc_decimals > local_decimals` and divides when `local_decimals > erc_decimals` (mirroring the `adjustDecimals` pattern already used correctly elsewhere in the SDK: [4](#0-3) ).
2. Regardless, add an explicit runtime check in `register_token`/`update_token` that rejects (or the code deliberately restricts) configurations where the assumption `erc_decimals >= local_decimals` is violated, and add tests exercising `local_decimals > erc_decimals`.

### Proof of Concept
Not able to fully construct on-chain reproduction without confirming `register_token`'s validation path (session ended before reading `module.rs`/`lib.rs` extrinsic body for `register_token`). Conceptually: register a token with `local_decimals = 18`, `erc_decimals = 6`; call `send(amount = 1)` (1 local unit = 1e-18 asset); `convert_to_erc20` computes `erc_decimals.saturating_sub(local_decimals) = 0`, so `erc20_amount = 1 * 10^0 = 1` instead of the correct `1 / 10^12` (which should round to 0 or require a minimum), or in the more dangerous general case with larger amounts, the EVM side receives an amount 10^12× larger than what was escrowed.

**Caveat:** I was unable to confirm within available tool calls whether `register_token` validates decimal ordering, so this finding's exploitability is unconfirmed — a background Devin session with full repo access should verify `register_token`/`update_token` in `modules/pallets/hyper-fungible-token/src/lib.rs` and `module.rs` before treating this as a confirmed, exploitable vulnerability rather than a code-quality/latent-bug finding.

export function adjustDecimals(feeInFeeToken: bigint, fromDecimals: number, toDecimals: number): bigint {
	if (fromDecimals === toDecimals) return feeInFeeToken
	if (fromDecimals < toDecimals) {
		const scaleFactor = BigInt(10 ** (toDecimals - fromDecimals))
		return feeInFeeToken * scaleFactor
	} else {
		const scaleFactor = BigInt(10 ** (fromDecimals - toDecimals))
		return (feeInFeeToken + scaleFactor - 1n) / scaleFactor
	}
}
