Audit Report

## Title
Unauthenticated panic (DoS) via negative-count `strings.Repeat` in HTTP-trigger workflow ID/owner normalization - ([File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go])

## Summary
`validateHexInput` only bounds the total length of the raw `workflowID`/`workflowOwner` string and does not require the `"0x"` prefix to be present, so a full-length (66 or 42 character) lowercase hex string with no `"0x"` prefix passes validation. That same string is then passed unchanged into `normalizeHex`, where `strings.Repeat("0", expectedHexLength-len(hexStr))` is computed without a bounds check; when the prefix is absent, `len(hexStr)` equals the full validated length, making the count negative and causing an unrecovered panic (`strings: negative Repeat count`). [1](#0-0) [2](#0-1) 

## Finding Description
`validateHexInput(input, expectedLength)` rejects inputs longer than `expectedLength` but accepts inputs of exactly `expectedLength` regardless of whether the `"0x"` prefix is present, since `hex.DecodeString` is applied to whatever remains after `strings.TrimPrefix(input, "0x")` (a no-op if the prefix is absent): [1](#0-0) 

`normalizeHex` is then called with the same raw value from `resolveWorkflowID`: [3](#0-2) 

Inside `normalizeHex`, `hexStr := strings.TrimPrefix(input, "0x")` is again a no-op for a prefix-less input, so for a 66-character `workflowID` with no `"0x"` prefix, `expectedHexLength := length - 2 = 64` and `strings.Repeat("0", 64-66)` is called with a negative count, which panics: [2](#0-1) 

This is reached from `HandleUserTriggerRequest` via `resolveWorkflowID`, which executes *before* `authorizeRequest` and `checkRateLimit`: [4](#0-3)  Consequently, no valid signature, key, or registered workflow is required — the only preconditions are that the request passes JSON parsing and the earlier field-presence/format checks in `validateWorkflowFields`/`validateWorkflowID`/`validateWorkflowOwner`, none of which reject a prefix-less, full-length hex string. [5](#0-4) 

No `recover()` exists anywhere in `core/services/gateway/**` outside of a test file, so nothing in this handler's call chain guards against the panic; whether the panic is contained to a single connection/request or crashes the whole gateway process depends on the outer transport (e.g., `net/http`'s automatic per-connection panic recovery vs. a persistent websocket/goroutine dispatch loop without recovery), which I could not fully confirm from the indexed code within the available search budget — the `core/services/gateway/api` and `core/services/gateway/network` packages did not show an obvious `ServeHTTP`/dispatch site tying `HandleUserTriggerRequest` to a specific transport handler with recovery semantics.

## Impact Explanation
This is a genuine, unauthenticated denial-of-service bug: an unrecovered panic in request-handling code triggered before any authentication/authorization step. At minimum, it aborts processing of the offending request/connection; if the goroutine executing `HandleUserTriggerRequest` lacks any `recover()` in its call stack (which appears to be the case based on the codebase search), an unrecovered panic in Go terminates the entire process, since goroutine panics are not process-isolated. This maps to the CWE-400/DoS impact category referenced in the report.

## Likelihood Explanation
High. Triggering requires a single, unauthenticated JSON-RPC `workflows.execute` POST to the gateway's HTTP trigger endpoint with a `workflowID` (or `workflowOwner`) that is exactly the expected length (66 or 42 characters) of lowercase hex digits and omits the `"0x"` prefix. No valid key, signature, prior workflow registration, or rate-limit bypass is needed, since the panic occurs in `resolveWorkflowID` → `normalizeHex`, ahead of `authorizeRequest` and `checkRateLimit`.

## Recommendation
1. In `normalizeHex`, guard against a negative repeat count: only pad when `expectedHexLength > len(hexStr)`; otherwise treat the input as invalid/oversized and return an error instead of silently truncating or panicking.
2. In `validateHexInput`, validate the hex payload length *after* stripping the optional `"0x"` prefix, and enforce an exact expected length for the stripped payload, rejecting inputs that are already full-length but missing the prefix.
3. Add a `recover()` wrapper around per-request dispatch in the gateway's JSON-RPC handling path as defense-in-depth so a single malformed request cannot take down the whole gateway process.

## Proof of Concept
Send a `workflows.execute` JSON-RPC request to the gateway's HTTP trigger endpoint with `workflowID` set to a 66-character lowercase hex string with no `"0x"` prefix, e.g. `"abcdefabcdefabcdefabcdefabcdefabcdefabcdefabcdefabcdefabcdefabcd"`. This passes `validateHexInput(workflowID, 66)` (length ≤ 66, valid hex after no-op trim), then in `resolveWorkflowID` → `normalizeHex(workflowID, 66)` computes `strings.Repeat("0", 64-66)`, panicking with `strings: negative Repeat count`. A Go unit test calling `normalizeHex("abcdef...cd" /* 66 chars, no 0x */, 66)` directly reproduces the panic without any network setup, and an integration test through `httpTriggerHandler.HandleUserTriggerRequest` with the same crafted `workflowID` demonstrates the unauthenticated, pre-authorization reachability.

func validateHexInput(input string, expectedLength int) error {
	if input != strings.ToLower(input) {
		return errors.New("must be lowercase")
	}

	if len(input) > expectedLength {
		return fmt.Errorf("hex string too long: expected at most %d characters, got %d", expectedLength, len(input))
	}

	hexStr := strings.TrimPrefix(input, "0x")
	_, err := hex.DecodeString(hexStr)
	if err != nil {
		return errors.New("must be a valid hex string")
	}

	return nil
}

// normalizeHex normalizes a hex string by stripping 0x prefix, padding with leading zeros, and adding 0x prefix back
func normalizeHex(input string, length int) string {
	hexStr := strings.TrimPrefix(input, "0x")
	// length-2 because we'll add "0x" prefix
	expectedHexLength := length - 2
	paddedHex := strings.Repeat("0", expectedHexLength-len(hexStr)) + hexStr
	return "0x" + paddedHex
}
