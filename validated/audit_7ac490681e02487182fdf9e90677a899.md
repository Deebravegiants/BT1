### Title
Emporium's aggregate-only `BalanceChangeShouldBePositive` check permits attribution-blind fund extraction leaving stranded victim balances vulnerable to sweep - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction`'s solvency check compares only the aggregate token balance of the Emporium contract before and after a call, not per-depositor amounts. An attacker can construct a CASE 2 (`op.invokeWallet == false`) stateless call that moves out exactly their own deposited amount, leaving any other stranded balance (e.g. a victim's residual funds from a prior partially-executed op) untouched and the check passing with `balanceChange == 0`.

### Finding Description
Broken equality: the code enforces `aggregate_emporium_balance_conservation` (i.e. `balancesAfter[i] - depositAmount_i >= balancesBefore_pre_deposit[i]`) but never enforces `per_depositor_balance_conservation`.

Tracing `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:76-160`:
- `balancesBefore` is captured via `getBalancesForArray` [1](#0-0)  after `_externalTransact` in `Hinkal.sol` has already transferred any deposit (`deltaAmountChanges[i] < 0`) into Emporium [2](#0-1) . So `balancesBefore[i]` already equals `X + Y` where `X` is any pre-existing (e.g. stranded) balance and `Y` is the attacker's fresh deposit.
- The ops loop executes CASE 2 stateless calls with no restriction beyond blocking `callHinkalWallet`/`doSendToRelay` selectors: `(success, err) = op.endpoint.call{value: op.value}(op.callData);` [3](#0-2) . This lets the attacker target the ERC20 token contract directly (e.g. `token.transfer(attacker, Y)`), moving funds out of Emporium's balance without going through the `handleOut`/UTXO accounting path at all.
- The check itself: `balanceChange = balancesAfter[i] - balancesBefore[i]; if (deltaAmountChanges[i] < 0) balanceChange -= deltaAmountChanges[i]; if (balanceChange < 0) revert BalanceChangeShouldBePositive();` [4](#0-3) . Substituting: `balancesAfter[i] = X + Y - Y = X`, so `balanceChange = X - (X+Y) - (-Y) = 0`. The check passes (`0` is not `< 0`).
- `handleOut` only creates a UTXO / returns funds to `msg.sender` (the Hinkal contract) when `balanceChange > 0` [5](#0-4) ; with `balanceChange == 0` no UTXO is minted for the attacker (they already extracted `Y` directly via the CASE 2 call), and the victim's `X` remains sitting as raw ERC20 balance on the Emporium contract, completely untracked by any shielded UTXO commitment.
- `getERC20OrETHBalance`/`getBalancesForArray` in `contracts/Transferer.sol:149-176` confirm the balance source is the raw `balanceOf(address(this))`/`address(this).balance`, with zero per-user state anywhere in `EmporiumStorage`.

None of the other guards (`verifyWallet`'s signature/nonce/`usedMessages` check [6](#0-5) , `onlyAllowedRecipient`, `payRelayFees`) constrain which tokens the CASE 2 `op.endpoint.call` can touch or to whom the ERC20 transfer inside it is addressed — they only govern that the op *stack itself* was authorized, not the destination of arbitrary calls made from within it.

### Impact Explanation
This confirms that the revert protects only Emporium's aggregate solvency, not attribution of whose funds compose that balance. It is the enabling mechanism for a subsequent theft: any stranded balance left by a previous user's transaction (whether from a partial/failed accounting path or an earlier attacker's own extraction) is completely unprotected and can be drained by any later CASE 2 op targeting the token contract directly, since the check never inspects recipient identity or ties `balanceChange` to a specific depositor's UTXO. This is Critical severity as claimed by the parent finding since it underlies direct theft of shielded/unshielded value cross-user, though this specific check by itself doesn't move stolen funds — it merely fails to prevent the theft path once a stranded balance exists.

### Likelihood Explanation
Requires only: (1) some stranded balance to exist on the Emporium contract (a precondition established in the related "root cause" question(s) about how funds get stranded), and (2) an attacker capable of crafting an ordinary deposit + CASE 2 withdrawal circomData, which is fully within the unprivileged attacker's capability (deposit own funds, generate own proof, choose `externalActionMetadata`/`EmporiumStack`). No privileged role or victim cooperation needed. Repeatable every time a stranded balance exists.

### Recommendation
Track per-depositor/per-UTXO Emporium balances (or require that `balanceChange` be computed strictly against `balancesBefore` measured prior to any deposit for *this* op, and reconcile any residual balance back into a UTXO or revert) rather than relying purely on aggregate `balanceOf` deltas. Additionally restrict CASE 2 `op.endpoint.call` targets/selectors so that arbitrary ERC20 `transfer`/`transferFrom` calls against tracked tokens cannot bypass the `handleOut` UTXO-minting path entirely.

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable`, a mock ERC20, and a mock `Hinkal` caller (or use the real `Hinkal.sol` with a whitelisted `externalActionMap` entry for Emporium).
2. Simulate a "victim stranding" tx: craft a CASE 2 op whose `callData` transfers only part of a deposited amount `X+Z` out, leaving `X` sitting on Emporium as raw `balanceOf`, with `balanceChange` computed as `>=0` so no revert fires, and no UTXO minted for the stranded `X`.
3. Assert `getERC20OrETHBalance(token) == X` on Emporium after step 2.
4. Attacker deposits `Y` via `deltaAmountChanges[i] = -int256(Y)` and submits a CASE 2 op calling `token.transfer(attacker, Y)` directly.
5. Assert `runAction` does NOT revert (`balanceChange == 0`).
6. Assert `getERC20OrETHBalance(token) == X` still (untouched, proving victim's stranded balance survives and remains attacker-sweepable in a subsequent tx).
7. Assert attacker's own token balance increased by exactly `Y`, confirming the attacker extracted only their own funds while the check provided no signal distinguishing `X` from `Y`.
