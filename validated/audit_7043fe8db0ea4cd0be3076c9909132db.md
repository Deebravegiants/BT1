### Title
Missing output-side derivation-path validation allows attacker-tagged outputs to bypass Ledger change/self-output detection - (File: features/hw-ledger/src/module/assets/utils/psbt.ts)

### Summary
`assertPsbtOnlyHasAllowedDerivationPaths` in `psbt.ts` only validates BIP32/Taproot derivation metadata attached to **inputs** of a PSBT, mirroring the "too soft check" pattern from the reference report (validating only part of the necessary condition — `received>0` instead of `received==_amount`). It never validates derivation metadata attached to **outputs**, even though `tagPsbtWithDerivationPaths` also writes/overwrites output derivation data that is used by the Ledger app + wallet policy to decide whether an output is "ours" (i.e., change, not requiring explicit user confirmation).

### Finding Description
In `signTransaction` (`features/hw-ledger/src/module/assets/bitcoin.ts`), a third-party-supplied PSBT is processed as follows: [1](#0-0) 

1. `tagPsbtWithDerivationPaths` scans every input and output, computing each own address's `scriptPubKey` from `derivationPathToPublicKeyMap`, and if a match is found it calls `psbt.setOutputBip32Derivation` / `setOutputTapBip32Derivation` for that output index.
2. `assertPsbtOnlyHasAllowedDerivationPaths` is then called as a "sanity check" — but its implementation only loops `for (let i = 0; i < psbt.getGlobalInputCount(); i++)` and only reads `psbt.getInputKeyDatas`/`getInputBip32Derivation`/`getInputTapBip32Derivation`. It never inspects `psbt.getGlobalOutputCount()` or any output-side derivation data: [2](#0-1) 

Because a PSBT arriving from an untrusted third party can pre-populate arbitrary `BIP32_DERIVATION`/`TAP_BIP32_DERIVATION` output fields (this is standard, attacker-controllable PSBT metadata), and because `tagPsbtWithDerivationPaths`'s output-tagging loop only *adds/overwrites* data for outputs it recognizes as its own by scriptPubKey match — it does **not** strip or validate any pre-existing output derivation metadata on outputs that do *not* match one of the wallet's own scriptPubKeys: [3](#0-2) 

This is structurally identical to the reported bug class: the code performs a check that is a strict subset of what's required (checking inputs only, when the correct invariant is "no unauthorized derivation-path claims anywhere in the PSBT, inputs *and* outputs"), and there is no code-comment or documented rationale for why output-side validation is omitted.

### Impact Explanation
Ledger hardware wallets use wallet-policy + attached BIP32 derivation metadata to determine which outputs are "change" belonging to the signer and therefore do not need to be displayed to the user for explicit confirmation. If an attacker can supply/tamper with a PSBT (e.g., through a malicious dApp, a compromised swap/exchange integration, or a man-in-the-middle on an unsigned PSBT passed to `signTransaction`) and attach forged output derivation metadata that happens to satisfy the wallet policy's matching criteria but corresponds to a scriptPubKey the code did not itself compute as "ours," the missing output validation means there's no `assertPsbtOnlyHasAllowedDerivationPaths`-style backstop to catch it before submission to the Ledger device. This is the same class of "fake-change-output" PSBT attack that can cause the signer to unknowingly and irrevocably sign a transaction sending funds to an attacker address without an on-device confirmation prompt — a direct wallet-compromise / unauthorized-signing impact.

### Likelihood Explanation
Moderate. Exploitability depends on precise details of how the Ledger firmware/`AppClient.signPsbt` interprets pre-existing vs freshly-set output derivation records, and whether `setOutputBip32Derivation` fully overwrites conflicting existing PSBT fields for record types the app also reads (key data can differ per public key, so multiple output derivation records could coexist for the same output index under different keys). This function is only reachable through code that already signs third-party-originated PSBTs (`params.signableTransaction` is caller-supplied), which is the primary usage in this module. It is not reachable through fully trusted, self-generated transactions only.

### Recommendation
Add a symmetric output-side check, analogous to `assertPsbtOnlyHasAllowedDerivationPaths` for inputs, that:
1. Iterates `psbt.getGlobalOutputCount()`.
2. For every output derivation entry (`BIP32_DERIVATION`/`TAP_BIP32_DERIVATION`) whose `masterFingerprint` matches ours, verifies the path is in the allow-listed `derivationPaths`.
3. Additionally verifies that the derivation path's corresponding computed `scriptPubKey` actually matches the output's real `scriptPubKey` (not just that a matching fingerprint+path pair exists), to prevent a mismatched derivation-path/scriptPubKey pairing from being accepted as "our own" output.
Alternatively/additionally, strip any pre-existing output BIP32 derivation fields from the incoming PSBT before `tagPsbtWithDerivationPaths` re-populates only the outputs it independently verified via its own `computeScriptPubKeyToDerivationPathMap`, ensuring no attacker-supplied output metadata can survive into the data sent to the Ledger device.

### Proof of Concept
Conceptual PoC (cannot be fully executed without hardware-in-the-loop, but demonstrates the code path gap):
1. Construct a PSBT with two outputs: Output 0 = attacker's destination address (external payment), Output 1 = legitimate wallet change address.
2. Attacker (or a malicious/compromised dApp constructing the PSBT for the user to sign) additionally attaches a forged `BIP32_DERIVATION`/`TAP_BIP32_DERIVATION` record to Output 0 using the victim's real `masterFingerprint` and an allow-listed derivation path (obtainable from prior, legitimate wallet interactions, e.g. observed receive addresses), while the scriptPubKey of Output 0 is actually the attacker's address (i.e., an inconsistent pairing).
3. Pass this PSBT into `signTransaction` (`features/hw-ledger/src/module/assets/bitcoin.ts:84`).
4. `tagPsbtWithDerivationPaths` only tags outputs it computes match a known scriptPubKey (attacker's Output 0 does not match), so it does not overwrite the forged derivation record already present on Output 0 supplied by attacker.
5. `assertPsbtOnlyHasAllowedDerivationPaths` is called next but — per `psbt.ts:19-49` — only checks input derivation data, leaving the forged output derivation record on Output 0 completely unvalidated and unremoved.
6. The PSBT (with forged Output 0 derivation data intact) is passed to `app.signPsbt`. Depending on Ledger firmware/wallet-policy behavior, Output 0 may be treated as the signer's own change output and excluded from the mandatory on-device recipient confirmation, allowing the transaction to be signed and broadcast without the user ever being shown that funds are going to the attacker's address.

Note: Full confirmation of exploitability requires validating exact Ledger firmware/`@exodus/ledger-bitcoin` `AppClient.signPsbt` semantics for handling conflicting/duplicate output derivation records, which is outside what can be verified purely from the indexed repository contents.

export function assertPsbtOnlyHasAllowedDerivationPaths(
  psbt: PsbtV2,
  masterFingerprint: string,
  derivationPaths: string[]
) {
  for (let i = 0; i < psbt.getGlobalInputCount(); i++) {
    const BIP32_DERIVATION = 6
    const TAP_BIP32_DERIVATION = 22
    const publicKeysNormal = psbt.getInputKeyDatas(i, BIP32_DERIVATION)
    const publicKeysTap = psbt.getInputKeyDatas(i, TAP_BIP32_DERIVATION)

    // First we validate that any BIP32 derivation params that were
    // pre-assigned by a third-party (potentially malicious)
    // is actually allowed by our "derivationPaths".
    for (const publicKey of publicKeysNormal) {
      const bip32Derivation = psbt.getInputBip32Derivation(i, publicKey)
      if (bip32Derivation) {
        assertAllowedDerivation(bip32Derivation, masterFingerprint, derivationPaths)
      }
    }

    // Repeat for TapBip32Derivation
    for (const publicKey of publicKeysTap) {
      const tapBip32Derivation = psbt.getInputTapBip32Derivation(i, publicKey)

      if (tapBip32Derivation) {
        assertAllowedDerivation(tapBip32Derivation, masterFingerprint, derivationPaths)
      }
    }
  }
}
