### Title
Webhook `shop-domain` header is trusted but not covered by the HMAC signature, enabling cross-tenant spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its verifiable HMAC signature over the raw HTTP body only, never over the `shop-domain`, `topic`, `api-version`, or `webhook-id` headers. `Registry.process` validates only that HMAC and then forwards the unauthenticated `shop` header value straight to the application's webhook handler as the tenant identifier. This breaks the intended binding: `shop asserted-in-header == shop that produced the signed body`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all read directly from HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Registry.process` validates only the body's HMAC via `HmacValidator.validate(request)`, which internally calls `verifiable_query.to_signable_string` (i.e., the raw body) — never the headers: [3](#0-2) [4](#0-3) 

After this single check, `request.shop` (fully attacker-controlled, unauthenticated) is passed into `WebhookMetadata` and handed to the host application's handler as the trusted tenant identifier: [5](#0-4) 

**Equality that should hold but doesn't:** `shop_header_value == shop_that_generated(hmac(raw_body, api_secret_key))`. Because the secret key (`Context.api_secret_key`) is the same app-wide `client_secret` shared across every merchant install of the app — not a per-shop secret — any two shops installing the same app share the identical HMAC key. Consequently a valid `(raw_body, hmac)` pair generated by webhook traffic to Shop A remains a cryptographically valid pair regardless of which `shop-domain` header accompanies it. Before the request: `shop == real_shop`. After an attacker (who controls a webhook-emitting event on their own installed shop, or who can otherwise capture a body+HMAC pair) resubmits the same body/HMAC to the app's public webhook endpoint with `x-shopify-shop-domain` rewritten to a victim's domain: `shop == victim_shop` while the signature still validates successfully, because the signature never covered the shop field.

### Impact Explanation
This is a cross-tenant confusion vector matching the "Critical - cross-tenant access" impact category. The gem's documented contract (see `docs/usage/webhooks.md`) is that `Registry.process` "will verify the request did indeed come from Shopify" before invoking the handler with the shop from the webhook. Host applications built on this API therefore reasonably use `WebhookMetadata#shop` as an authenticated tenant selector (e.g., to look up which merchant's session/access token to use, or which merchant's records to update) — but the gem never actually authenticates that field. An attacker who can produce or replay any valid `(body, hmac)` pair for the shared app secret can direct the resulting webhook processing at an arbitrary victim shop identifier, causing the host app to attribute/apply data intended for one tenant to another tenant.

### Likelihood Explanation
Likelihood is bounded by the difficulty of obtaining a valid `(raw_body, hmac)` pair, since the app secret itself is not exposed by the gem. However, an attacker only needs *one* shop installation of the target app (a very low bar for public/open-install Shopify apps) to legitimately receive real webhook deliveries with valid HMACs, and can then replay those bodies against the same public endpoint with a forged `shop-domain` header — no secret material needs to be recovered. The vulnerability requires no privileged token, TLS interception, or social engineering, only an unauthenticated HTTP POST to the app's public webhook route.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`api-version`) header values in the signable content that `HmacValidator` verifies, or otherwise cryptographically bind the shop identity to the body before trusting it (e.g., require the caller to independently confirm the `shop` against a per-shop lookup keyed by a value that is itself authenticated). At minimum, document explicitly that `WebhookMetadata#shop` is not authenticated by `Registry.process` and must not be used as a tenant boundary without additional verification.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`, both sharing the same `Context.api_secret_key` (app `client_secret`).
2. Shopify sends a legitimate webhook to the app for `attacker-shop`, e.g., `orders/create` with body `B` and header `x-shopify-hmac-sha256: HMAC(B, secret)`; attacker captures `B` and the HMAC.
3. Attacker POSTs to the same webhook endpoint with unchanged body `B` and HMAC, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-199`) calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `raw_body` (`lib/shopify_api/webhooks/request.rb:36-38`, `lib/shopify_api/utils/hmac_validator.rb:27-31`) — validation succeeds because the secret and body are unchanged.
5. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, causing the host application to process attacker-controlled data under the victim shop's tenant context.
