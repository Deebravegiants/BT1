### Title
Balance-weighted phantom-order median price can be set verbatim by a solver's transiently inflated token balance, mispricing IntentGateway quotes - (File: `sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts`)

### Summary
Phantom-order bid prices are weighted by each solver's live, unlocked ERC-20/vault balance of the leg's output token, read at aggregation time with no staking, time-lock, or historical-average requirement. `weightedMedian` is a selection function, not a blend: once one bidder's weight is ≥50% of the leg's total weight, that bidder's exact quoted price becomes the published `medianPrice` verbatim. A solver can borrow a large balance of the output token (e.g., via a flash loan or any transient same-block funding), submit an extreme quote, get counted as majority weight, have the median snap to its price, then immediately return the borrowed funds — all with no economic cost proportional to the amount manipulated, only capital that need not be held past the same transaction/block.

### Finding Description
The weighting function that decides a phantom leg's published price is a naive, unlocked balance read: [5](#0-4) 

This weight is used directly by `weightedMedian`, which is a **selection** algorithm — it returns one bidder's exact price whenever that bidder's weight passes the 50% cumulative-weight threshold: [6](#0-5) 

The per-leg result — `medianPrice`, and `lowestPrice`/`highestPrice` deliberately overwritten to equal it — is persisted and fed into pool rates with no sanity/outlier check against prior snapshots: [7](#0-6) 

The rate then merges into `LiquidityPool.sellRate`/`buyRate` and is consumed as the default, no-fallback pricing source for real order quoting: [8](#0-7) [9](#0-8) 

This mirrors the reported bug class exactly: a balance-derived ratio (there, `_BASE_TARGET_`/`_QUOTE_TARGET_` and share pricing; here, the leg's weighted median price) is computed from a spot balance that a single transaction can transiently inflate, letting the attacker's manufactured balance dictate a downstream accounting/pricing value that other, unrelated parties then rely on.

### Impact Explanation
An intent solver (an explicitly in-scope, unprivileged actor) who can source a large transient balance of a leg's output token — via flash loan, temporary transfer from an affiliate, or a same-block loop through a DEX/vault — can become the majority-weight bidder for a phantom leg and dictate `medianPrice` to any value it likes (bounded only by the haircut logic, which does not bound manipulation, only shave a fixed bps). This directly poisons `LiquidityPool.sellRate`/`buyRate`, which `IntentGateway.quoteIntent`/`IndexedRateIntentQuoteStrategy` uses to compute `amountIn`/`amountOut` for real user orders with no fallback source. Users or the SDK's own `execute()` flow constructing real orders off a poisoned rate can be induced to escrow too much input or accept too little output relative to the true market, transferring value to whichever solver later fills the mispriced order — a concrete loss to users placing intents. This qualifies as a route/pricing oracle a single unprivileged actor can force into an unsound state.

### Likelihood Explanation
Likelihood is high for a resourced actor: no privilege, staking, or governance is required — only holding a large balance of the output token for the duration of one bid submission and one aggregation window (`PhantomBidWindow`). Flash-loanable tokens (stablecoins, DAI, most ERC-20s used as intent legs) make the "transient balance" condition trivial to satisfy for essentially free, and repeating it every window lets an attacker keep the published rate skewed persistently.

### Recommendation
Do not weight (or gate majority-selection in) `weightedMedian` by a single spot `balanceOf`/`maxWithdraw` read. Options: (1) require the weighting balance to be time-averaged or read at a historical/committed block rather than at aggregation time, so it cannot be manufactured in the same transaction as the bid; (2) cap any single solver's weight contribution to a fraction of total weight (e.g., no bidder may exceed 33–40% of a leg's cumulative weight) so no bidder can unilaterally become the selected median; (3) require solvers to lock/stake the balance being counted (e.g., via an escrow/collateral commitment) for a cooldown period spanning the bid window; (4) cross-check a new `medianPrice` against the pool's prior `sellRate`/`buyRate` and reject/flag snapshots that move a rate beyond a bounded deviation without corroborating depth from multiple independent solvers.

### Proof of Concept
1. Attacker controls or borrows (flash loan) a very large balance of token `B` (leg's output token) on the destination chain, exceeding all legitimate solvers' combined holdings of `B`.
2. Attacker signs and submits a `UserOperation` bid for the active phantom order leg quoting an extreme, favorable-to-attacker price for `B`, satisfying `isVerifiedSolverBid` (a legitimate EIP-7702-delegated SolverAccount signs it).
3. When `PhantomBidWindowExhausted` fires, `aggregatePhantomBids` reads the attacker's `balanceOf(B)` (see `getTotalSolverBalance`), computing weight ≫ all other bidders combined.
4. `weightedMedian` reaches ≥50% cumulative weight at the attacker's price and returns it verbatim as `medianPrice` (`weightedMedian`, lines 709-724).
5. `PhantomOrderPriceSnapshotV2` and `updateLiquidityPools` write this price into `LiquidityPool.sellRate`/`buyRate`.
6. Attacker returns the borrowed `B` (flash loan repayment) in the same transaction/block — no capital lock-up required.
7. A subsequent user calling `IntentGateway.quoteIntent` (default `indexed_rates` strategy, no fallback) receives an `amountIn`/`amountOut` computed from the poisoned `sellRate`/`buyRate`, and places a real order on unfavorable terms that a solver (potentially the same attacker) fills at the manipulated rate.

//
// Callers must not hand this an entry set whose weights are all zero: with nothing to weight by it
// can only pick a quote by position, and for an even-sized set that position is the upper of the
// two middles — so "the median" becomes "whoever quoted higher", settable by a solver holding no
// inventory at all. aggregatePhantomBids drops such legs instead of pricing them. The fallback
// below stays only so an unguarded caller gets a number rather than a crash; treat reaching it as
// a caller bug.
export function weightedMedian(entries: { price: bigint; weight: bigint }[]): bigint {
	const sorted = [...entries].sort((a, b) => (a.price < b.price ? -1 : a.price > b.price ? 1 : 0))
	const totalWeight = sorted.reduce((acc, e) => (e.weight > 0n ? acc + e.weight : acc), 0n)

	if (totalWeight === 0n) {
		return sorted[Math.floor(sorted.length / 2)].price
	}

	let cumulative = 0n
	for (const entry of sorted) {
		if (entry.weight <= 0n) continue
		cumulative += entry.weight
		if (cumulative * 2n >= totalWeight) return entry.price
	}
	return sorted[sorted.length - 1].price
}
