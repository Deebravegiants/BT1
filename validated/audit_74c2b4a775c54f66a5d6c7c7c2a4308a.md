This confirms the vulnerability: the gem's documented webhook contract explicitly relies on `data.shop` (`docs/usage/webhooks.md:14,26`) as the tenant identifier for the host app's downstream logic (`perform_later(topic: data.topic, shop_domain: data.shop, ...)`), while `ShopifyAPI::Webhooks::Request#to_signable_string` signs only `@raw_body` [1](#0-0) , leaving the `shopify-shop-domain` header [2](#0-1)  completely uncovered by the HMAC that `Registry.process` checks before dispatching to the handler [3](#0-2) .

### Title
Webhook `shop` identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating `Utils::HmacValidator.validate(request)`, which computes the signature over `request.to_signable_string` — defined as the raw JSON body only. The `shop` value that is forwarded to the app's webhook handler (and that the app is documented to use as the tenant key) comes from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is never included in the signed bytes. This breaks the equality "shop authenticated == shop acted on": the gem authenticates `hmac(raw_body)` but acts on an independently-supplied, unauthenticated `shop` header.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` by defining:
```ruby
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

`shop` is read straight from a header with no cryptographic tie to the body:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [2](#0-1) 

`Utils::HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it to the `hmac` header, so it only ever authenticates the body bytes, not `shop`, `topic`, `webhook_id`, or `api_version`: [4](#0-3) 

`Registry.process` uses exactly this check before invoking the app's handler with the unauthenticated `shop`:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [3](#0-2) 

The gem's own documentation instructs app authors to treat `data.shop` as the tenant/shop key for downstream processing (e.g. enqueuing `shop_domain: data.shop`), confirming that `shop` is meant to identify which merchant/tenant the payload belongs to: [5](#0-4) 

Because the app's `api_secret_key` is shared across all shops that install the app (it is not per-shop), any unprivileged merchant who has installed the app can trigger a legitimate webhook delivery for their own store (e.g. `orders/create`) and thereby obtain a body + valid `x-shopify-hmac-sha256` pair signed with that shared secret. Since the HMAC never covers the `shop` header, that same body/HMAC pair remains valid when replayed with the `shopify-shop-domain` header changed to a different, victim shop's domain — `HmacValidator.validate` still returns `true`, and the handler receives `shop: "victim-shop.myshopify.com"` paired with attacker-controlled/attacker-known body content.

Equality that should hold but doesn't:
`shop authenticated by HMAC` == `shop delivered to the handler`
In reality: `hmac` binds only `raw_body`; `shop` is taken from an independent, unauthenticated header, so the two are decoupled.

### Impact Explanation
This is a cross-tenant identity-binding break as explicitly scoped in this exercise: the gem allows an unprivileged party (any merchant who has installed the multi-tenant app) to make the app process attacker-controlled webhook data under an arbitrary victim shop's identity. Depending on how the host app uses `data.shop` (session/store lookup, tenant-scoped writes, redaction/data-request compliance actions such as `customers/redact`, `shop/redact`), this can lead to cross-tenant data confusion or corruption — for example, causing the app to apply attacker-supplied order/customer data or trigger GDPR redaction logic against a shop the attacker does not control. This matches the "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is realistic but requires the attacker to be an already-installed, unprivileged user of the app (a legitimate merchant tenant) — no access to `api_secret_key`, access tokens, or TLS interception is needed. They only need to: (1) trigger a real webhook for their own shop to capture a valid `(raw_body, hmac)` pair, and (2) send an HTTP POST to the app's webhook endpoint with that same body/HMAC but a forged `shopify-shop-domain` header naming the victim shop. This requires no privileged credentials and is directly reachable through the gem's documented `Registry.process` entry point.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and has installed the target app.
# Step 1: Attacker triggers a real webhook (e.g. by creating an order in their own shop)
# and captures the raw POST body + "x-shopify-hmac-sha256" header Shopify sent to the app,
# both computed using the shared app api_secret_key:
raw_body = '{"id":1,"note":"pwned"}'
hmac_header = "<valid-signature-for-raw_body-with-shared-secret>"

# Step 2: Attacker replays the same body/hmac pair to the same endpoint,
# but swaps the shop-domain header to the victim's shop:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => hmac_header,          # still valid: HMAC only covers raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, unauthenticated
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => Utils::HmacValidator.validate(request) returns true (body/hmac match)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: ..., ...))
# The app's handler now processes attacker-controlled data under the victim's identity.
```

### Recommendation
Bind `shop` (and ideally `topic`/`api_version`) into the signed material, or otherwise cryptographically tie the header values to the request that is authenticated — e.g., have `to_signable_string` incorporate a canonicalized representation of the relevant headers alongside the body, or require the host application to independently verify that `shop` corresponds to a shop with an active, previously-established session/installation before trusting webhook payloads for that shop.
