### Title
Webhook `shop-domain` header is trusted for tenant identification without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` value that identifies which merchant/tenant the webhook belongs to is read from an unauthenticated HTTP header. Because the HMAC does not bind the shop identity to the signed bytes, and because the same `api_secret_key` is shared across every shop that has installed the app, any merchant who has installed the app can produce a body+HMAC pair that is valid for the app, then replay it to the app's webhook endpoint with the `shop-domain` header swapped to a victim shop, causing the app to process attacker-controlled data under the victim's identity.

### Finding Description
`Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

but `shop` is read straight from the `x-shopify-shop-domain` / `shopify-shop-domain` header, which is not part of that signed string: [2](#0-1) 

`Webhooks::Registry.process` validates only the HMAC over the body, then immediately trusts `request.shop` (the unsigned header) to dispatch tenant-scoped data to the app's handler: [3](#0-2) 

The identity binding that should hold is: `shop asserted to the handler == shop the HMAC was computed for`. Because `api_secret_key` is a single per-app secret shared by every shop that installs the app, and the shop header is excluded from the signable string, this equality does not hold — the HMAC only proves "this body was produced by Shopify for this app," not "this body concerns this specific shop." Any tenant of the app (or anyone who can capture one legitimate webhook delivery for any shop using the app) can take a valid `(body, hmac)` pair from their own shop and resend it to the app's webhook endpoint with an arbitrary `shop-domain` header. `HmacValidator.validate` will still pass because it never inspects `shop`: [4](#0-3) 

### Impact Explanation
This breaks the tenant boundary that `shop` is meant to enforce: the app's webhook handler receives a `WebhookMetadata` whose `shop` field is fully attacker-controlled even though the HMAC is valid, letting a malicious/compromised merchant tenant inject or misattribute webhook data to another tenant (cross-tenant access), which is called out explicitly in the acceptance criteria as a Critical-class impact.

### Likelihood Explanation
Requires only that the attacker's own store has the target app installed (a routine, low-privilege capability for anyone who can install a public app), no `api_secret_key` or access-token theft is needed, and no privileged Shopify actions are required — only the ability to trigger one webhook delivery for their own shop and replay it to the app's public webhook endpoint with a modified header, which is trivial for any unprivileged internet user who controls a shop.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the HMAC-signed payload used by `to_signable_string`, or otherwise cryptographically bind `request.shop` to the HMAC verification so a replay against a different shop fails validation. At minimum, require the caller (host app) to check `request.shop` against a shop that is expected/known to have the corresponding registration before dispatching to the handler.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`.
2. Attacker triggers a webhook event on their shop (e.g., product create) whose body content they control.
3. Shopify sends the webhook to the app's endpoint with a valid `x-shopify-hmac-sha256` (computed with the app's shared `api_secret_key`) and header `x-shopify-shop-domain: attacker.myshopify.com`.
4. Attacker intercepts/replays this exact request to the app's webhook endpoint but rewrites the header to `x-shopify-shop-domain: victim.myshopify.com`, keeping body and HMAC unchanged.
5. `ShopifyAPI::Webhooks::Registry.process` validates the (unchanged) HMAC successfully via `Utils::HmacValidator.validate`, then calls the handler with `shop: "victim.myshopify.com"` and the attacker-controlled body, causing the app to process/store attacker data as though it originated from the victim tenant.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
