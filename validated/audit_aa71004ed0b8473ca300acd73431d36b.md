### Title
Webhook Tenant Spoofing via Unsigned `shop-domain` Header - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by HMAC-validating the raw request body, but the `shop` value handed to every app-supplied `WebhookHandler` is read from a header that is never covered by that HMAC. Because Shopify's app-wide HMAC secret (`api_secret_key`) is shared across every shop that installs the app, any merchant/tenant who installs the app can obtain a body with a valid signature for arbitrary content of their choosing, then replay that request with the `shop-domain` header swapped to a different, victim tenant. The equality the gem is supposed to enforce — "the shop the HMAC-signed payload was produced for" == "the shop the handler receives" — is never checked.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [3](#0-2) 
`Request#shop` is derived independently from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of that signable string: [2](#0-1) 
`HmacValidator.validate` only recomputes/compares the HMAC over `verifiable_query.to_signable_string` (i.e., the body) against `verifiable_query.hmac`: [5](#0-4) 
`Registry.process` gates dispatch only on that body-HMAC check, then builds `WebhookMetadata` using the unverified `request.shop`, `request.topic`, `request.api_version`, and `request.webhook_id` and forwards it to the app's handler: [4](#0-3) 

Since Shopify signs webhooks with the app's single, shared `api_secret_key` for all installed shops (not a per-shop secret), an attacker who is any legitimate tenant of the app can:
1. Trigger a webhook delivery to their own store carrying attacker-controlled body content (e.g., customer/order/product data they fully control in their own shop).
2. Capture the resulting valid `(raw_body, hmac)` pair, which was computed with the same `api_secret_key` used for every tenant.
3. Replay the request to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to a victim shop's domain (and topic/webhook-id headers changed if desired, since those are equally unauthenticated).
4. `Registry.process` verifies the HMAC (succeeds, because body+secret are unchanged) and calls the handler with `data.shop == "victim-shop.myshopify.com"` and attacker-chosen `data.body`.

This breaks the binding `shop that produced/owns the signed bytes == shop attributed to the resulting WebhookMetadata`, letting one tenant inject arbitrary attacker-controlled data into another tenant's processing path — a cross-tenant integrity/access violation carried entirely through this gem's own webhook-verification API.

### Impact Explanation
Any host application that uses `data.shop` from `WebhookMetadata` to key persistence, cache invalidation, uninstall/redact handling, or entitlement logic (the documented/expected usage of this API) can have another tenant's identity spoofed with attacker-chosen body content, since the gem itself never binds `shop` to the signed bytes. This matches the Critical "cross-tenant access" impact category: a merchant who is a legitimate but unprivileged user of the shared app can affect another merchant's tenant data/processing without ever obtaining that merchant's credentials.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the app on a shop they control (a normal, unprivileged installation any Shopify merchant can do) and be able to send an arbitrary HTTP request to the app's public webhook endpoint (webhook endpoints are internet-reachable by design, with no other authentication layer expected). No secret material, TLS interception, or social engineering is required — only observation/capture of one's own legitimately-signed webhook traffic and simple header substitution.

### Proof of Concept
1. Attacker installs the target app on their own Shopify dev/test store, giving them a valid, shared `api_secret_key`-signed webhook stream.
2. Attacker triggers an event (e.g., updates a customer's `note` field to attacker-chosen JSON) causing the app to receive `POST /webhooks` with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(secret, B)` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures this request, then resends it to the same endpoint, replacing only `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (all other headers/body unchanged).
4. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against the unchanged HMAC (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
5. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, causing the host app to process attacker-controlled data under the victim shop's identity.

### Recommendation
Include the shop domain (and topic/webhook-id, or at minimum shop) in the HMAC-verifiable material, or independently verify that the `shop-domain` header corresponds to a shop actually entitled to send this signed payload (e.g., cross-check against a shop-specific secret or a previously established session/access-token record for that shop) before constructing `WebhookMetadata` and dispatching to the handler.
