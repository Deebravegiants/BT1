### Title
Webhook shop identity used for tenant dispatch is not covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop` value used to identify the tenant for the webhook handler is read from an HTTP header that is never included in the signed bytes. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then dispatches to the handler using this unauthenticated `shop` value, breaking the equality "bytes verified == bytes used to identify the tenant."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is not part of the signable string at all: [2](#0-1) [3](#0-2) 

`HmacValidator.validate` verifies `verifiable_query.hmac` against `verifiable_query.to_signable_string` — for `Request`, that string is the raw body only: [4](#0-3) 

`Registry.process` validates the HMAC and then immediately builds `WebhookMetadata` using `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` — none of which are covered by the HMAC — and dispatches it to the app-registered handler as the authoritative tenant identifier: [5](#0-4) 

Because only the raw body is signed, the tuple `(shop, topic, webhook_id, api_version)` can be freely modified by anyone who can present a `(body, hmac)` pair that is valid for the shared `api_secret_key` — a pair that is trivially obtainable by any merchant/tenant that has legitimately installed the app, since Shopify computes this same HMAC over the body with the app's single shared secret for every shop that installs the app. A merchant who has installed the app (an "unprivileged" tenant relative to other tenants of the same app) can capture one of their own legitimate webhook deliveries (body + valid HMAC), then replay that exact body and HMAC to the app's webhook endpoint while substituting a different `shop-domain` header value belonging to another (victim) shop. The gem's `Registry.process` will pass HMAC validation (since the body/HMAC pair is genuinely valid) and then hand the handler a `WebhookMetadata` claiming the payload originated from the victim shop, when in reality only the *body* was authenticated — the shop attribution was not. This breaks the identity binding: `hmac_valid(body) == true` is being treated as `shop_header_authentic == true`, but the two are not the same value — the header is parsed from unauthenticated bytes while only body bytes are cryptographically verified.

### Impact Explanation
If a host application's webhook handler uses `WebhookMetadata#shop` to look up which tenant's database row/record to update (a standard, expected usage pattern, exactly as shown in `Registry.process`'s dispatch to `handler.handle(data: WebhookMetadata.new(... shop: request.shop ...))`), an attacker who is a legitimate (if low-privileged) tenant of the app can force cross-tenant data operations to be attributed to, or applied against, a victim shop's data by replaying a validly-HMAC'd payload with a forged `shop-domain` header. This is a cross-tenant integrity issue rooted entirely in this gem's `Request`/`Registry` code, not in host-application misuse — the gem hands the handler an authoritative-looking `shop` field despite never protecting it with the HMAC it just validated.

### Likelihood Explanation
Requires only: (1) the attacker legitimately installs the target app on their own shop to obtain a valid `(body, hmac)` pair for at least one webhook topic, and (2) the ability to send an arbitrary HTTP request to the app's publicly reachable webhook endpoint with a forged `shop-domain` header — both are within reach of an ordinary unprivileged internet user/merchant, with no need for `api_secret_key`, access tokens, or any privileged access.

### Recommendation
Include the shop domain (and ideally topic/webhook-id/api-version) in the HMAC-signed bytes, or otherwise independently authenticate the `shop-domain` header against a set of shops that are actually authorized/installed for this app (e.g., a stored session/shop registry) before trusting it in `WebhookMetadata`. At minimum, document prominently that `WebhookMetadata#shop` is not itself covered by the webhook signature and must be independently verified by the host application against its own install records before being used as a tenant key.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Attacker triggers/receives a legitimate webhook, capturing `raw_body` and the valid `x-shopify-hmac-sha256` header (computed by Shopify over `raw_body` with the app's shared `api_secret_key`).
3. Attacker POSTs the exact same `raw_body` and `hmac` header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body successfully; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `@raw_body` against the HMAC (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:12-31`).
5. `Registry.process` builds `WebhookMetadata` with `shop: request.shop` = `"victim-shop.myshopify.com"` and dispatches to the app's handler (`lib/shopify_api/webhooks/registry.rb:188-199`), which now performs its logic (e.g. record update) believing it originates authentically from the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
