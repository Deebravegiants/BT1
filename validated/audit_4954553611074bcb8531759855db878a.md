### Title
Webhook HMAC only covers the raw body, not the `shop-domain`/`topic`/`webhook-id` headers, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw request body via HMAC. The `shop`, `topic`, `webhook_id`, and `api_version` values are read straight from unauthenticated HTTP headers and are never included in the signed payload, so they can be freely modified without invalidating the HMAC check.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are derived from headers that are not part of that signable string: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC strictly against `to_signable_string` (the body), never against the headers: [3](#0-2) 

`Registry.process` accepts the request once the body-only HMAC passes, then constructs the webhook payload handed to the app's handler using the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id`: [4](#0-3) 

Because every shop that installs an app shares the same app-level `api_secret_key`, any merchant that has legitimately received a webhook (a valid `(raw_body, hmac)` pair signed by the app's own secret) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header with a different shop's domain. `HmacValidator.validate` will still pass because it only checks the body signature, yet `Registry.process` will hand the handler a `WebhookMetadata` object attributing the (attacker-supplied) body to the victim shop. The equality that should hold — "shop whose secret validated this HMAC" == "shop the handler is told the data belongs to" — is broken, since the shop identity is never bound into the signed material.

### Impact Explanation
This breaks a tenant-isolation boundary: an unprivileged internet user who is merely a merchant with the app installed (or anyone who can capture one valid webhook body/HMAC pair) can forge webhook events attributed to an arbitrary other shop. Depending on the handler logic in the host application (e.g., updating shop-scoped records, disabling billing, processing app-uninstalled events, or triggering data sync) this results in cross-tenant data injection/corruption — a High/Critical-class cross-tenant access impact, since the identity binding (shop) that host apps rely on to segregate tenant data is not authenticated by this gem.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: the attacker doesn't need the app secret itself, only one captured valid `(body, hmac)` pair (which they can obtain trivially from their own store's webhook deliveries, since it's their own tenant that is already receiving genuine, correctly-signed webhooks). They then only need to change unauthenticated headers to target a different shop identity.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the signed material used for verification—e.g., verify the `x-shopify-shop-domain` header against a value derived from context that is independently established (such as checking the shop exists in the app's own session/store before trusting `request.shop`), or include the header values in the HMAC computation to mirror Shopify's authenticated context rather than trusting raw headers as-is.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook delivery: raw body `B` with header `x-shopify-hmac-sha256: H` (valid HMAC of `B` using the app's `api_secret_key`) and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker POSTs the exact same body `B` and the exact same `x-shopify-hmac-sha256: H` to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `@raw_body` only (`Request#to_signable_string`) — it matches `H`, so validation succeeds.
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: ..., webhook_id: ...)` and invokes the app's handler as if `victim.myshopify.com` sent this data, even though the data actually originated from the attacker's own shop.

        def validate(verifiable_query)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
