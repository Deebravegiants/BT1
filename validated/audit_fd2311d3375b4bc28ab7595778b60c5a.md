### Title
Missing duplicate-input-token rejection in Tron `IntentGatewayV2.placeOrder` allows escrow-bucket merging and same-chain partial-fill over-release - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` accumulates escrow into `_orders[commitment][token]` with `+=` and never rejects an order whose `inputs` array names the same token twice, unlike the canonical EVM contract, which explicitly guards against this with `if (_orders[commitment][token] != 0) revert InvalidInput();`. This reproduces a bug class the EVM contract has an explicit regression test for ("same-chain partial fills over-release repeated input escrow").

### Finding Description
`placeOrder` in `evm/src/apps/IntentGatewayV2.sol` rejects duplicate input tokens per commitment before crediting escrow: [1](#0-0) 

This check exists specifically because same-chain partial fills in `IntrinsicIntents._fillSameChain` compute the escrow to release per **output index `i`** using `order.inputs[i].amount` and the shared bucket `_orders[commitment][token]`: [2](#0-1) 

If two input legs reference the same token, the escrow bucket for that token is shared across both legs, but the per-leg proportional release math (`order.inputs[i].amount * fillAmount / totalRequired`, and the full-release branch that reads the *entire* bucket `_orders[commitment][token]` on `amountFilled == totalRequired`) assumes the bucket is sized for a single leg. This lets solvers over-release escrow across multiple output legs backed by the same merged input bucket — the exact regression covered by `testRevert_PlaceOrder_DuplicateInputTokens`: [3](#0-2) 

The Tron port of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, does **not** carry this guard. Its `placeOrder` credits escrow additively for every input leg with no non-zero check: [4](#0-3) [5](#0-4) 

This mirrors the Sherlock Carousel finding precisely: the balance/limit check that is supposed to prevent a state inconsistency (`_orders[commitment][token] != 0`) is present in one code path (the "current" check equivalent to Carousel's `balanceOf(...) < _assets`) but the analogous safeguard for the cumulative/updated case is missing in a sibling implementation of the same contract, permitting funds to be over-released relative to what was actually escrowed for a given leg.

### Impact Explanation
An order placer can submit a same-chain order on the Tron deployment with two (or more) input legs pointing at the same ERC-20 token address but different output legs. Because `_orders[commitment][token]` merges both legs' escrow into one bucket while the fill/release logic in `IntrinsicIntents._fillSameChain` (which the Tron contract also relies on/mirrors for partial-fill accounting) computes releases per leg against `order.inputs[i].amount`, a colluding solver (or the order placer acting as solver) can drive multiple partial/full fills that collectively drain more of the merged bucket than any single leg was entitled to, resulting in direct theft of escrowed user funds from the gateway. This is a concrete loss-of-funds / unbacked-release bug, not merely a DoS.

### Likelihood Explanation
Likelihood is high: `placeOrder` is a fully public, unprivileged entry point reachable by any user submitting an order with attacker-chosen `inputs`, and no additional privilege or timing condition is required — only the absence of the duplicate-token check that the main EVM contract added specifically to close this gap. Any user/solver pair can construct the duplicate-token order and drive the exploit through ordinary `fillOrder` calls.

### Recommendation
Port the same duplicate-input-token guard from `evm/src/apps/IntentGatewayV2.sol` into `evm/tron/contracts/apps/IntentGatewayV2.sol`: before/while crediting `_orders[commitment][token]`, revert with `InvalidInput()` if the bucket for that `(commitment, token)` pair is already non-zero (or otherwise enforce one entry per token per order), matching the fix and regression test already present for the canonical EVM contract (`testRevert_PlaceOrder_DuplicateInputTokens`, `testRevert_PlaceOrder_DuplicateInputTokens_WithProtocolFee`).

### Proof of Concept
1. Build an `Order` with `inputs = [ {token: USDC, amount: A1}, {token: USDC, amount: A2} ]` and two output legs (e.g., two different DAI amounts), each proportionally tied to one input leg.
2. Call `placeOrder` on the Tron `IntentGatewayV2` — it succeeds and sets `_orders[commitment][USDC] = A1 + A2` (merged bucket), whereas the intended per-leg entitlement is `A1` for leg 0 and `A2` for leg 1.
3. As solver, fully fill leg 0 (output index 0) with the *first* output's amount. `_fillSameChain`-style logic (which the Tron contract reuses the same escrow map and partial-fill semantics for) releases `escrowedAmount = _orders[commitment][USDC]` (the whole merged bucket, `A1+A2`) instead of `A1`, because the full-release branch reads the shared bucket directly rather than a per-leg allocation.
4. The solver now walks away with `A1 + A2` for output leg 0 alone, while output leg 1 still expects its own USDC allocation that no longer exists in escrow — the gateway is left short, and the user/protocol absorbs the loss when leg 1 attempts to release its now-nonexistent escrow.
5. `evm/tests/foundry/IntentGatewayV2SameChainTest.sol:testRevert_PlaceOrder_DuplicateInputTokens` (lines 2115–2148) documents that this exact scenario is rejected on the main EVM contract but is not covered/rejected on the Tron contract, confirming the regression is reintroduced there.
