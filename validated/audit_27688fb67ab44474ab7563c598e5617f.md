### Title
Unbounded `order.inputs` / `order.output.assets` arrays enable a gas-exhaustion DoS that permanently freezes escrowed funds in `IntentGatewayV2` / `IntentsBase` - (File: `evm/src/apps/intentsv2/IntentsBase.sol`, `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.placeOrder()` never bounds the length of `order.inputs` or `order.output.assets`. Every downstream operation that must eventually release escrow — `_withdraw()` (called from `fillOrder`, `cancelOrder`, and the cross-chain `onAccept` handler for `RedeemEscrow`/`RefundEscrow` messages) — iterates over these caller-supplied arrays with a plain `for` loop. This is the exact "push pattern" gas-exhaustion class described in the external report: an array whose size is controlled by an untrusted party can be grown large enough that the loop consumes more gas than a single block can provide, permanently DoS-ing the function that would otherwise release funds.

### Finding Description
`placeOrder()` only validates `order.inputs.length == 0` and rejects duplicate tokens; it does not cap the number of input or output legs: [1](#0-0) 

The escrow-release routine `_withdraw()` loops once per token in `body.tokens` (which mirrors `order.inputs`), performing an `SLOAD`, an arithmetic update, and an external `safeTransfer`/native call per iteration: [2](#0-1) 

`_withdraw` is the terminal step for:
- `fillOrder` (same-chain) via `_fillSameChain`, [3](#0-2) 
- the cross-chain settlement path, where an inbound ISMP `RedeemEscrow`/`RefundEscrow` post-request is delivered through `HandlerV2.handlePostRequests` → `host.dispatchIncoming` → the IntentGateway's `onAccept` callback → `_withdraw`. [4](#0-3) 

Because `order.inputs`/`order.output.assets` lengths are fully attacker/user controlled at `placeOrder` time and are never capped, a user (or an order crafted to grief itself, or a relayed cross-chain settlement carrying the same unbounded `WithdrawalRequest.tokens` array) can make the withdrawal loop's gas cost exceed the destination chain's block gas limit. Once that happens, `_withdraw` can never complete — not in `fillOrder`, `cancelOrder`, nor the `onAccept` handler invoked by relayer-delivered ISMP messages — so the escrowed tokens for that order commitment become permanently unrecoverable.

Related unbounded loops that widen the same exposure exist in `placeOrder`'s fee/predispatch phases and `_execute`'s output sweep, all keyed off the same unbounded array lengths: [5](#0-4) [6](#0-5) 

### Impact Explanation
This is a permanent freezing-of-funds bug reachable from a single, unprivileged `placeOrder` transaction and completed via a normal relayed ISMP message delivery (`handlePostRequests` → `onAccept` → `_withdraw`). Once an order is placed with a sufficiently large `inputs`/`output.assets` array, no future call path (`fillOrder`, `cancelOrder`, or the relayer-delivered settlement message) can execute `_withdraw` to completion, and the escrowed principal is locked in the contract with no recovery mechanism. This matches the report's "Critical — push pattern" bug class: an attacker-sized array denies the release-of-funds path.

### Likelihood Explanation
Likelihood is high for a self-inflicted or griefing scenario: constructing an order with hundreds/thousands of `TokenInfo` legs costs only calldata/storage gas at `placeOrder` time (which is comparatively cheap since it can be spread with fewer external calls per leg than the multi-step `_withdraw`/`_execute` paths), while the victim-side `_withdraw`/`_execute` loop performs an external token transfer per entry, multiplying gas cost per element. No permission check exists on the size of these arrays anywhere in `placeOrder`, `fillOrder`, `cancelOrder`, or the ISMP `onAccept` dispatch path.

### Recommendation
- Enforce a hard cap (e.g., `MAX_ORDER_LEGS`) on `order.inputs.length` and `order.output.assets.length` in `placeOrder`, reverting with a dedicated error if exceeded.
- Alternatively, convert the escrow-release pattern from push (iterate-and-transfer-all-in-one-call) to pull (per-token claim function), so a single oversized order cannot block the entire withdrawal in one transaction.
- Apply the same bound to the encoded `WithdrawalRequest.tokens` accepted by `onAccept`, independent of the `placeOrder` check, since that data arrives from a cross-chain message and must be validated as untrusted input on its own.

### Proof of Concept
1. Attacker (or careless user) calls `placeOrder` with `order.inputs` and `order.output.assets` each containing N distinct `TokenInfo` entries (N chosen so that `N × (SLOAD + external transfer + SSTORE)` gas exceeds the destination chain's block gas limit, e.g. several hundred legs).
2. `placeOrder` succeeds since there is no length cap; tokens are escrowed under the order's commitment.
3. For a same-chain order, any subsequent `fillOrder`/`cancelOrder` call that reaches `_withdraw(body, ...)` with `body.tokens.length == N` cannot fit in a block; every attempt reverts with an out-of-gas condition regardless of the gas limit sent, since it exceeds the network's block gas limit.
4. For a cross-chain order, the relayed `onAccept` call carrying the matching `WithdrawalRequest` similarly cannot complete via `HandlerV2.handlePostRequests`, so the message can never be successfully delivered and the source-chain escrow is never released.
5. The escrowed tokens for that commitment remain locked in `IntentGatewayV2`/`IntentsBase` permanently.
