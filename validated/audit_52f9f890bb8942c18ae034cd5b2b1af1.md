This confirms the finding. The library's own documentation (`docs/usage/webhooks.md:125`) explicitly says `Registry.process` "will verify the request did indeed come from Shopify" — but the verification only proves the *body* bytes came from Shopify's HMAC signer; it never proves which *shop* the body belongs to. That is exactly the "field acted on but not covered by the HMAC" identity-binding break called out in the rules.

### Title
Webhook `shop` (and `topic`/`webhook_id`) header is not bound to the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `HmacValidator.validate` verifies the HMAC exclusively over that raw body string. The `shop` (and `topic`, `webhook_id`, `api_version`) values are read from separate, unauthenticated HTTP headers that are never included in the signed material.

### Finding Description
`Request#to_signable_string` at [1](#0-0)  returns just `@raw_body`. `Registry.process` at [2](#0-1)  calls `Utils::HmacValidator.validate(request)`, which computes `HMAC(secret, to_signable_string)` and compares it to the `hmac` header via `OpenSSL.secure_compare` ( [3](#0-2) ). Once that check passes, `Registry.process` builds `WebhookMetadata` directly from `request.shop`, `request.topic`, and `request.webhook_id` — all parsed from headers in `Request#shop`/`#topic`/`#webhook_id` ( [4](#0-3) ) — without any cryptographic tie to the signed body.

The identity-binding equality that should hold is: `shop asserted to the handler == shop whose secret produced the HMAC over this exact (body, shop, topic) tuple`. In reality the code only proves `HMAC(secret, body)` is valid; it never proves `HMAC(secret, shop)` or `HMAC(secret, body‖shop)`. Any party who is a legitimate merchant of the installing app receives a genuine webhook (valid body + valid HMAC) for their *own* shop, then can replay that exact `raw_body`/`hmac-sha256` pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (and/or `x-shopify-topic`) header. `HmacValidator.validate` still succeeds because it only checks the body bytes, and `Registry.process` hands the handler a `WebhookMetadata` claiming the forged shop/topic.

The library's own documentation states this method "will verify the request did indeed come from Shopify" ( [5](#0-4) ) and instructs developers to key their business logic straight off `data.shop` ( [6](#0-5) ), so the documented, intended usage pattern trusts an unauthenticated field.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce: an attacker who controls one installed shop can forge webhook events (e.g. `app/uninstalled`, `shop/update`, `orders/create`) attributed to a victim shop that also uses the same app, causing the host application to mutate or leak data under the wrong tenant's identity — cross-tenant access/integrity violation, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any app whose webhook endpoint is shared across shops (the standard multi-tenant SaaS pattern this gem targets). The only prerequisite is that the attacker be a real merchant of the app (no special privilege) with the ability to trigger any webhook topic for their own store and then send a manually crafted HTTP request with modified headers to the app's public webhook endpoint — well within an "unprivileged internet user" (here: unprivileged merchant) capability.

### Recommendation
Bind the shop (and ideally topic) identity into the verified material: either include `shop-domain`/`topic` in `to_signable_string`, or — since Shopify itself doesn't sign headers — require callers to cross-check `request.shop` against the shop stored for the specific webhook subscription/session before invoking the handler, and document this requirement prominently instead of implying header trust is safe. At minimum, update `docs/usage/webhooks.md` to warn that `data.shop`/`data.topic` are not covered by the HMAC and must be revalidated against the caller's own session/tenant records before use.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers, say, an `orders/create` event, receiving from Shopify a POST with `raw_body = B` and header `x-shopify-hmac-sha256 = HMAC(secret, B)` (valid, since it's genuinely from Shopify).
2. Attacker crafts a new HTTP request to the app's public webhook endpoint, reusing the identical `raw_body = B` and `x-shopify-hmac-sha256` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`).
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` parses `shop` as `victim-shop.myshopify.com` [7](#0-6) .
4. `Registry.process` calls `HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and it matches, since `B` is unchanged [8](#0-7) .
5. The registered handler is invoked with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body:, ...)` [9](#0-8) , causing the host app to act on `victim-shop`'s tenant data using attacker-controlled body content.
