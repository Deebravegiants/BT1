This confirms the vulnerability: `withdraw()` transfers exactly `body.tokens[i].amount` out of the escrow record, and that amount (originally credited during `placeOrder`) is based on `order.inputs[i].amount` (the pre-transfer, user-specified amount reduced only by the protocol fee), never on the actual token balance the contract received. Since `placeOrder`'s non-predispatch branch does `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` with no balance check, a fee-on-transfer token causes the escrow ledger (`_orders[commitment][token]`) to be inflated beyond what the contract actually holds — exactly the bug class from the reference report, but landing on the shared escrow pool that backs every other order's funds. ### Title
Fee-on-transfer tokens let `IntentGatewayV2.placeOrder` (Tron variant) over-credit escrow, draining the shared token pool - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment of `IntentGatewayV2` credits an order's escrow with the user-declared `order.inputs[i].amount` (minus protocol fee) instead of the amount actually received via `safeTransferFrom`, unlike the hardened EVM mainline contract which measures `balanceOf` before/after the transfer.

### Finding Description
In `placeOrder`, the non-predispatch branch performs:
```solidity
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
...
_orders[commitment][token] += reducedInputs[i].amount;
``` [1](#0-0) 
`reducedInputs[i].amount` is derived purely from `order.inputs[i].amount` and the protocol fee percentage — it is never reconciled against what the contract actually received: [3](#0-2) 

If `token` charges a transfer fee (or otherwise delivers less than requested), the contract's real balance increase is smaller than `reducedInputs[i].amount`, yet the full (un-discounted) amount is recorded as escrowed for that commitment in the shared `mapping(bytes32 => mapping(address => uint256)) public _orders`. The predispatch branch has the same flaw: it computes `dust` correctly against the dispatcher's balance, but still credits `_orders[commitment][token] += reducedInputs[i].amount` (the pre-fee-on-transfer amount) rather than the amount the contract actually received from the sweep transfer: [4](#0-3) 

Later, `withdraw()` (called from `onAccept` for `RedeemEscrow`/`RefundEscrow`, from `cancelOrder`, and from `onGetResponse`) blindly transfers out `body.tokens[i].amount` and decrements `_orders[body.commitment][token]` by that same amount, trusting the ledger value rather than actual token holdings: [2](#0-1) 

Because `_orders` is a single shared per-token accounting ledger across all orders/commitments in the contract, an inflated entry for one order does not just affect that order — it can be redeemed against the pooled token balance that also backs other users' legitimately-escrowed orders (or other tokens' `token.call` transfers, since `transfer` failures are only checked via `success`, not by verifying sufficient balance beforehand). This can result in later legitimate redemptions failing (transfer reverts due to insufficient balance → funds partially frozen) or, in a first-mover scenario, allow one filler/solver to redeem the over-credited amount at the expense of subsequently placed orders sharing the pool.

### Impact Explanation
This is a Medium/High-severity accounting bug: it enables loss of funds for other order participants in the same contract (shared escrow pool drained beyond actual token backing) or permanent freezing of legitimately escrowed funds once the pool is short. It directly matches the "unbacked accounting causing loss/freezing of funds" acceptance criteria, reachable from a single unprivileged `placeOrder` call using any fee-on-transfer ERC20 as an input token.

### Likelihood Explanation
Likelihood is Medium: it requires the deployment to accept a fee-on-transfer (or otherwise non-standard-transfer) ERC20 as an escrowable input token. Given `IntentGatewayV2` is a generic, permissionless intents gateway that accepts arbitrary `TokenInfo.token` addresses supplied by any user in `order.inputs`, nothing in the contract prevents whitelisting or use of such tokens, and the sibling EVM contract (`evm/src/apps/IntentGatewayV2.sol`) already had to be patched for exactly this class of token, confirming it is an expected/realistic token type for this protocol.

### Recommendation
Mirror the fix already present in `evm/src/apps/IntentGatewayV2.sol`: measure `IERC20(token).balanceOf(address(this))` before and after each `safeTransferFrom`/sweep, and set `order.inputs[i].amount` (and therefore `reducedInputs[i].amount` and the value credited to `_orders`) to the actual received delta rather than the caller-specified amount, for both the direct-transfer and predispatch code paths in the Tron `IntentGatewayV2.sol`.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` with a fee-on-transfer ERC20 (e.g., 1% fee) as an allowed input token, `protocolFeeBps = 0` for simplicity.
2. User calls `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000e18}` and `approve`s the gateway for `1000e18`.
3. `safeTransferFrom` pulls `1000e18` nominally but the contract's actual balance only increases by `990e18` (1% fee burned/redirected).
4. `_orders[commitment][FOT]` is set to `1000e18` (no protocol fee ⇒ `reducedInputs == order.inputs`), while the contract only holds `990e18` of `FOT`.
5. When the order is filled/redeemed via `onAccept`→`withdraw`, the contract attempts to transfer `1000e18` `FOT` out of a pool that only received `990e18` for this order — either succeeding by consuming `10e18` from other orders' escrowed `FOT` balance (theft) or reverting once the shared pool is exhausted (freezing legitimate withdrawals), as demonstrated by the equivalent fee-on-transfer regression tests already written for the patched EVM contract (`evm/tests/foundry/IntentGatewayV2SameChainTest.sol` lines 2441-2494) which show the *correct* balance-diff behavior — the Tron contract lacks this logic entirely.
