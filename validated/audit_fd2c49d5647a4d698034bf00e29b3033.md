Audit Report

## Title
Gateway HTTP-action response cache key omits `WorkflowID`, breaking the documented workflow-isolation guarantee and allowing cross-workflow response/cache confusion - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

## Summary
The `responseCache` used by the Gateway's HTTP Action handler keys cached HTTP responses solely by `req.Hash()`, which — per the package's own unit tests — excludes `WorkflowID` and `CacheSettings` from its computed value. This contradicts the package's documented design ("Cache Key: Generated from workflow ID and request hash", "Workflow Isolation: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage"), allowing two distinct workflows (sharing the same `WorkflowOwner`) issuing identical outbound HTTP requests to read/write the same cache entry.

## Finding Description
`gatewayHandler.makeOutgoingRequest` unmarshals a node-supplied `OutboundHTTPRequest` and dispatches it to `h.responseCache.Fetch`/`Set` using the request itself as the cache key input [1](#0-0) . Internally, `responseCache.Fetch`, `Set`, and `isExpiredOrNotCached` all key the cache map purely by `req.Hash()` [2](#0-1) .

The package README explicitly documents that the cache key should be "Generated from workflow ID and request hash" and that entries are "scoped by workflow ID to prevent cross-workflow data leakage" [3](#0-2) . However, the package's own unit tests directly demonstrate that `Hash()` ignores both `WorkflowID` and `CacheSettings`: `require.Equal(t, hash1, hash2, "Hash should be the same regardless of WorkflowID")` and the analogous assertion for `CacheSettings` [4](#0-3) . The struct comment in `response_cache.go` itself acknowledges the hash is only over "method, URL, headers, body, workflowOwner" — not `WorkflowID` — confirming the root cause is intrinsic to the type's `Hash()` implementation, which is not scoped by workflow identity as documented [5](#0-4) .

As a result, any two workflows under the same `WorkflowOwner` that issue an outbound HTTP action with an identical method/URL/headers/body will collide on the same cache slot, regardless of `WorkflowID` or their individually configured `CacheSettings` (freshness/store policy).

## Impact Explanation
This is a genuine discrepancy between documented behavior and implementation: the isolation boundary described in the README ("Workflow Isolation... to prevent cross-workflow data leakage") is not enforced at the code level. A workflow can be served an HTTP response fetched to satisfy a different workflow's request, and a workflow with a strict `MaxAgeMs` freshness requirement can receive stale/foreign data cached under looser settings from another workflow, since `CacheSettings` don't factor into cache-entry identity either. This maps to a "cross-user/cross-workflow response corruption" class of impact. The severity is limited by the fact that the colliding workflows must (a) share the same `WorkflowOwner` and (b) issue requests with an identical hash input (method, URL, headers, body) — the leaked data is limited to what would be an identical fetched response for equivalent-looking outbound requests, but the differing `WorkflowID`/`CacheSettings` mean the confusion is real and not purely cosmetic.

## Likelihood Explanation
This is reachable by any unprivileged workflow node already authorized to use the Gateway's HTTP action capability — no privilege escalation or additional authentication bypass is required, only that two workflows under the same owner make requests with identical method/URL/headers/body, which is plausible for common third-party API integrations using default headers/bodies.

## Recommendation
Incorporate `WorkflowID` (and ideally `CacheSettings`) into the cache key computation so that `Fetch`/`Set`/`isExpiredOrNotCached` operate on truly workflow-scoped keys, e.g., derive the map key as a combination of `WorkflowID` and `req.Hash()` rather than `req.Hash()` alone, and update/verify the `Hash()` implementation and its tests to reflect the corrected scoping.

## Proof of Concept
The existing test `TestRequestHash` subtests "having different workflowID results in same Hash" and "having different cacheSettings results in the same Hash" directly demonstrate the flaw [4](#0-3) . An integration-level PoC: Workflow A (`WorkflowID=wf-A`) issues an `OutboundHTTPRequest` to a given URL with `CacheSettings{Store:true, MaxAgeMs:600000}` via `gatewayHandler.makeOutgoingRequest`; the response is cached under `req.Hash()`. Workflow B (`WorkflowID=wf-B`, same owner) issues the identical method/URL/headers/body with `CacheSettings{MaxAgeMs:1000}`; because `req.Hash()` ignores `WorkflowID`, Workflow B's `Fetch` call reads Workflow A's cached entry as demonstrated by the cache map lookup in `Fetch` [6](#0-5) .

// isExpiredOrNotCached returns true if the cached response is expired or not cached.
// IMPORTANT: this method does not lock the cache map. MUST be called with cacheMu write-locked.
func (rc *responseCache) isExpiredOrNotCached(req gateway.OutboundHTTPRequest) bool {
	cachedResp, exists := rc.cache[req.Hash()]
	if !exists || time.Now().After(cachedResp.storedAt.Add(rc.ttl)) {
		return true
	}
	return false
}

// Fetch fetches a response from the cache if it exists and
// the age of cached response is less than the max age of the request.
// If the cached response is expired or not cached, it fetches a new response from the fetchFn
// and caches the response if it is cacheable and storeOnFetch is true.
//
// The mutex is only held during cache map access (microseconds), not during fetchFn execution.
// Singleflight deduplicates concurrent requests to the same cache key so only one fetchFn
// runs per key, while requests to different keys execute in parallel.
// Cache read and write happen inside the singleflight callback to ensure the key remains
// in-flight until the result is stored, preventing duplicate fetches.
func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

	// Slow path: singleflight deduplicates concurrent fetches per key.
	// Cache check + store happen inside the flight so the key isn't released
	// until the result is cached, closing the race window between singleflight
	// completion and cache write.
	result, _, _ := rc.flight.Do(cacheKey, func() (any, error) {
		// Re-check cache: a previous flight may have just stored the result.
		rc.cacheMu.RLock()
		cachedResp, exists := rc.cache[cacheKey]
		rc.cacheMu.RUnlock()
		if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
			rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
			return cachedResp.response, nil
		}

		response := fetchFn()

		if storeOnFetch && isCacheableStatusCode(response.StatusCode) {
			rc.cacheMu.Lock()
			rc.cache[cacheKey] = &cachedResponse{
				response: response,
				storedAt: time.Now(),
			}
			rc.cacheMu.Unlock()
		}

		return response, nil
	})

	return result.(gateway.OutboundHTTPResponse)
}

// Set caches a response if it is cacheable (2xx or 4xx and cache is empty or expired for the given request)
func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}

### 3.2 Caching Behavior
