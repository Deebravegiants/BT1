## Title
Hardcoded `deadline = block.timestamp` in `EvmHost`'s native-fee swap paths enables stale-price execution and sandwich attacks - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchGet)` and `EvmHost.fundRequest` both allow a caller to pay protocol/relayer fees in native token, in which case the contract swaps ETH for an exact amount of `feeToken()` via the configured Uniswap V2 router. In both cases the `deadline` argument passed to `swapETHForExactTokens` is hardcoded to `block.timestamp`, which is the exact bug class described in the external report.

### Finding Description
In `dispatch`: [1](#0-0) 

and in `fundRequest`: [2](#0-1) 

Both call `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(amount, path, address(this), block.timestamp)`. Because `deadline` is set to `block.timestamp` at execution time rather than a caller-supplied future bound, the deadline check inside the router (`require(deadline >= block.timestamp)`) is always trivially true no matter when the transaction is eventually mined. This means a `dispatch`/`fundRequest` transaction that sits in the mempool (due to low gas price, congestion, or is deliberately held by an MEV searcher) carries no real staleness protection: it can be executed at an arbitrary later block, at a completely different feeToken/ETH price, with the caller's originally intended parameters (`amount` as the fixed exact output, `msg.value` as the implicit max input).

This is functionally identical to the reported `DEXAdapter.sol` issue: since the swap is exact-output (fixed `amount` of `feeToken`, variable ETH input bounded by `msg.value`), an attacker/MEV bot can manipulate the pool price (front-run) so that the required ETH input approaches or exceeds `msg.value`, then back-run to restore price, extracting value from the pool at the caller's expense, or forcing the transaction to revert (DoS on fee funding) after gas is spent.

### Impact Explanation
Both `dispatch` and `fundRequest` are unprivileged, externally reachable entry points used to pay for and top-up relayer fees for outgoing Hyperbridge requests. A successful sandwich degrades the ETH/feeToken exchange rate the caller receives, meaning less of the caller's ETH is efficiently converted (or more ETH than expected is consumed/refunded back into `EvmHost` rather than to the user), effectively causing a loss of value for users funding requests, directly impacting relayer fee/reward accounting for message dispatch. Because `swapETHForExactTokens` refunds unspent ETH to `msg.sender` of the swap call (i.e., `EvmHost` itself, not the original transaction sender), any leftover ETH from a manipulated swap is stranded inside the host contract rather than returned to the user, compounding the loss.

### Likelihood Explanation
Any user paying via native ETH for `dispatch(DispatchGet)` or `fundRequest` is exposed whenever their transaction is not the very next transaction mined (mempool visibility, moderate network congestion, or a bundler/MEV searcher watching for it) — a common and easily triggerable condition, not requiring privileged access.

### Recommendation
Do not hardcode `deadline = block.timestamp`. Add a `deadline` (and ideally a `minFeeTokenOut`/max-slippage bound distinct from `amount`) as a caller-supplied parameter to `dispatch` and `fundRequest`, validated to be in the future, so stale transactions revert instead of executing at an arbitrary later price.

### Proof of Concept
1. User A calls `fundRequest(commitment, amount)` with `msg.value` covering current market price for `amount` feeToken, expecting near-immediate inclusion.
2. Transaction sits in the mempool (low fee/congestion).
3. An MEV bot detects the pending call, front-runs the Uniswap V2 pool to shift the ETH/feeToken price, sandwiching the exact-output swap so the pool absorbs value at A's expense, then back-runs to restore price — profiting at A's cost, since `block.timestamp` deadline never blocks the delayed execution.
4. Alternatively, price movement while pending causes the required ETH input to exceed `msg.value`, causing the whole `fundRequest`/`dispatch` call to revert regardless of how much time has passed, without any legitimate expiry semantics.
