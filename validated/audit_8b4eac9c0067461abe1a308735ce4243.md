Based on my investigation, I found a genuine analog to the Admidio incomplete-fix pattern (a security gate added to one implementation of a function but not propagated to a sibling/duplicate implementation of the same logic).

### Title
Tron `IntentGatewayV2.onAccept` is missing the relayer-authorization gate present in the EVM sibling — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The EVM `IntentGatewayV2`/`ExtrinsicIntents` delivery path was hardened so that `onAccept` (and `onGetResponse`) reject any relayer other than the one explicitly configured via `setRelayer`, closing a route where a forged/compromised handler could report an arbitrary relayer and let an unauthorized party settle escrow. This gate was documented and tested as `_checkRelayer(incoming.relayer)` [1](#0-0) , added alongside the `HostManager` relayer gate in the same hardening effort [2](#0-1) , with `setRelayer` and `_checkRelayer` implemented in `evm/src/apps/intentsv2/ExtrinsicIntents.sol` [3](#0-2) .

The Tron deployment of the sibling `IntentGatewayV2` contract, however, never received this gate: its `onAccept` only runs `onlyHost` plus `authenticate()` (source-instance check) for `RedeemEscrow`/`RefundEscrow`, with no relayer allowlist at all [4](#0-3) , and `onGetResponse` similarly has no relayer check before calling `withdraw` [5](#0-4) .

### Finding Description
`IntentGatewayV2` is deployed both on standard EVM chains (`evm/src/apps/IntentGatewayV2.sol`, `evm/src/apps/intentsv2/ExtrinsicIntents.sol`) and separately for Tron (`evm/tron/contracts/apps/IntentGatewayV2.sol`) — a duplicated implementation of the same escrow/settlement logic maintained in parallel, exactly the "sibling handler" shape described in the Admidio report (`item_delete` fixed, `field_delete` left vulnerable). The relayer-gating hardening (`_relayer` / `setRelayer` / `_checkRelayer`) was applied only to the `evm/src/apps/intentsv2` implementation and is absent from the Tron copy's `onAccept` and `onGetResponse`, which still authorize purely on `onlyHost` + source-instance authentication [6](#0-5) .

As documented in the flow notes, the relayer address checked in `onAccept` is only as trustworthy as `_hostParams.handler`, which a `SetHostParam` governance message can replace [7](#0-6) . On a Tron deployment lacking the `_checkRelayer` gate, any relayer that can get a proof accepted by the handler (including via a forged/compromised handler swap, or simply any permissionless relayer under the intended open-relaying model if the deployment ever restricted delivery) can deliver `RedeemEscrow`/`RefundEscrow` and immediately trigger `withdraw()`, releasing escrowed input tokens and fees to whatever `beneficiary` is encoded in the request body — without the same-relayer restriction the rest of the protocol now relies on for this attack surface.

### Impact Explanation
This is an "unauthorized app action" / "forged message delivery leads to fund release" class issue exactly analogous to the CWE-862 (missing authorization) advisory: the security invariant ("only the authorized relayer may deliver governance/settlement-sensitive callbacks after a handler-authenticity compromise") that was deliberately added to protect the escrow settlement path in one implementation is silently absent in the parallel Tron implementation of the identical contract, leaving escrowed user funds on Tron exposed to the exact attack (`testForgedHandlerSwapIsRefused`-style) that the EVM fix was written to close.

### Likelihood Explanation
Reachable by any relayer able to have a delivery accepted through the Tron gateway's handler for the `IntentGatewayV2.onAccept`/`onGetResponse` entrypoints — a single relayed message. It requires the handler-authenticity precondition (e.g., a governance-level handler swap or any weakening of consensus proof verification) to actually diverge from the "any relayer is fine" baseline; absent such a compromise the impact is limited to disabling the intended defense-in-depth. Given the codebase's own hardening commit explicitly calls this out as the attack the gate exists for, and the Tron contract is a live, separately-audited deployment target, this is a real regression risk rather than a theoretical one.

### Recommendation
Port the `_relayer` state variable, `setRelayer`, and `_checkRelayer` gate (and the corresponding `Execute`/`upgradeToAndCall` host-only pattern if applicable) from `evm/src/apps/intentsv2/ExtrinsicIntents.sol` into `evm/tron/contracts/apps/IntentGatewayV2.sol`, applying the same check to `onAccept` (for `RedeemEscrow`/`RefundEscrow`) and `onGetResponse` before any withdrawal logic runs. Audit all other Tron-specific contract copies under `evm/tron/contracts/` for the same class of drift against their EVM counterparts.

### Proof of Concept
Not independently exploitable purely from the index without confirming the exact conditions under which Tron's handler/relayer address can diverge from the intended one; the concrete root-cause diff is directly demonstrated by comparing:
- `evm/src/apps/intentsv2/ExtrinsicIntents.sol:75-78` (`_checkRelayer`) and its call site in `onAccept`
- `evm/tron/contracts/apps/IntentGatewayV2.sol:629-638` (`onAccept`, no relayer check)

A full PoC (e.g., replaying `testForgedHandlerSwapIsRefused`-style scenario against the Tron contract) would require exercising the Tron contract's host/handler wiring in a Foundry test, which was not available within the scope of this analysis — recommend a background engineering session to write and run that test against `evm/tron/contracts/apps/IntentGatewayV2.sol`.

    /**
     * @dev Once a relayer is set, rejects deliveries from anyone else before the body is read. The
     * host records the revert as undelivered, so the authorised relayer can resubmit. While unset,
     * every delivery passes: a proxy from before the gate stays open until `migrate` arms it.
     * @param relayer The account that submitted the message to the handler.
     */
    function _checkRelayer(address relayer) internal view {
        address authorised = _relayer;
        if (authorised != address(0) && relayer != authorised) revert Unauthorized();
    }

    /**
     * @dev Rotates the authorised relayer. Host-only, so reachable only through an `Execute`
     * request, which delegatecalls it with the host still `msg.sender`.
     * Leaves `version()` alone; `initialize` and `migrate` arm a proxy on its way to `VERSION`.
     * @param relayer The account whose deliveries are accepted from now on. Zero reopens the gate.
     */
    function setRelayer(address relayer) external onlyHost {
        _setRelayer(relayer);
    }
