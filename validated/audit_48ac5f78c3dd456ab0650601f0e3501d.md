Confirmed: the main EVM `IntentGatewayV2`/`IntentsBase.sol` uses `SafeERC20.safeTransfer` consistently for escrow withdrawal [1](#0-0) , but the Tron variant's `withdraw` and `onAccept` (`SweepDust`) paths use a raw low-level `.call` with `IERC20.transfer.selector` and only check that the call didn't revert — they never inspect/decode the returned boolean [2](#0-1) [3](#0-2) .

### Title
Unchecked ERC20 return value in `IntentGatewayV2.withdraw`/`SweepDust` lets escrow be marked settled without tokens actually moving - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron `IntentGatewayV2.withdraw()` function (reached via `onAccept` for `RedeemEscrow`/`RefundEscrow` requests) and the `SweepDust` admin action move ERC20 tokens using a raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and treat the transfer as successful whenever the low-level call itself doesn't revert, without checking the returned `bool`. [4](#0-3) [5](#0-4) [6](#0-5) 

### Finding Description
`withdraw()` is invoked from `onAccept` when a hyperbridge-relayed `RedeemEscrow`/`RefundEscrow` request arrives (fill settlement or a source-chain refund) [7](#0-6) , and also directly from `onGetResponse` for cross-chain-cancel confirmations. For each escrowed token it does:

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
_orders[body.commitment][token] -= amount;
```

`success` only reflects whether the call reverted, not whether `transfer` returned `true`. Any ERC20 whose `transfer` implementation returns `false` on failure instead of reverting (a well-known non-standard-but-real behavior class, the same class the reported `SecondaryRewarder.recover` USDT bug belongs to) will make this code treat a failed transfer as successful. `_filled[body.commitment]` is set unconditionally before the loop and the per-token escrow (`_orders[body.commitment][token]`) is decremented right after the "successful" call, so the order is marked delivered/redeemed and can never be retried — even though the tokens never left the contract. The same unchecked pattern is used for `TRANSACTION_FEES` payout and for the governance-only `SweepDust` action. This directly contradicts the audited pattern used everywhere else in the codebase (`IntentsBase.sol`, `HyperFungibleToken.sol`, `WrappedHyperFungibleToken.sol`, `EvmHost.sol`), which all use OpenZeppelin's `SafeERC20.safeTransfer`, precisely to guard against tokens with this behavior. [8](#0-7) 

### Impact Explanation
Because escrow accounting is finalized (`_filled` set, `_orders` decremented) based purely on call success rather than actual token movement, a token that returns `false` instead of reverting causes: (1) permanent loss of the beneficiary's/solver's escrowed funds — they are stranded in the contract with no accounting path pointing to them anymore, since the withdrawal is considered already completed; (2) the same risk applies to protocol `TRANSACTION_FEES` and to `SweepDust`, meaning governance-swept dust could silently fail to move while the event still fires as if it succeeded. This is a concrete freezing-of-funds condition reachable by any user who places or fills an order using such a token, matching a Medium-severity unchecked-ERC20-return-value class.

### Likelihood Explanation
The intents flow is fully permissionless — a user's `placeOrder`/`fillOrder` selects the escrowed token, and settlement flows through `onAccept`/`onGetResponse` automatically once the hyperbridge relayer delivers the message. No privileged actor is needed to reach `withdraw()`; it fires for every cross-chain fill/refund settlement. The main hazard is limited to tokens with the "return false, don't revert" behavior, which is a real (if less common) subset of ERC20-like tokens.

### Recommendation
Use `SafeERC20.safeTransfer` (already imported and aliased with `using SafeERC20 for IERC20;` in this same file) for the beneficiary transfer, the transaction-fee payout, and the `SweepDust` transfer, consistent with `IntentsBase.sol`'s `_withdraw`. If a low-level call must be retained (e.g. for Tron TRC20 quirks), decode and check the return data as `success && (returndata.length == 0 || abi.decode(returndata, (bool)))`.

### Proof of Concept
1. Deploy a non-standard ERC20 whose `transfer()` returns `false` on failure rather than reverting (e.g., insufficient balance due to a hook, fee-on-transfer edge case, or deliberately buggy/malicious token accepted for an order).
2. A user places an order (`placeOrder`) with this token as an input, escrowing it in `IntentGatewayV2`.
3. A solver fills the order on the destination chain; the relayer delivers the `RedeemEscrow` request back to the source `IntentGatewayV2`, invoking `onAccept` → `withdraw()`.
4. Have the token's `transfer()` return `false` for this specific call (e.g., contract-controlled condition, or simply a token that always returns `false` on a corner case such as zero remaining allowance/paused state).
5. `success` is `true` (the call didn't revert), so `TransferFailed` is not raised; `_filled[commitment]` is set and `_orders[commitment][token]` is decremented — the escrow accounting treats the order as settled while the beneficiary never received the tokens, which are now permanently stuck with no code path referencing them.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];

            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
