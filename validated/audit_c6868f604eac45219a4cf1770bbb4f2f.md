Now I have the key evidence needed. `placeOrder` and `fillOrder` are `nonReentrant`, but that guard protects only `IntentGatewayV2`'s own storage against reentrancy through the gateway — it does **not** protect the shared `CallDispatcher` singleton, whose `dispatch()` function has no access control and no reentrancy guard at all.

### Title
Unrestricted `CallDispatcher.dispatch()` allows theft of tokens/ETH the dispatcher is holding mid-flight - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch()` is a public, unauthenticated function that executes attacker-supplied `(to, value, data)` tuples from the dispatcher's own context, exactly mirroring the `fillZrxQuote` pattern in the referenced report: an arbitrary external call is made from a contract that legitimately holds/controls value, and nothing restricts who can trigger it or what target/calldata it executes.

### Finding Description
`CallDispatcher.dispatch(bytes memory encoded)` decodes a `Call[]` array and performs `to.call{value: call.value}(call.data)` for each entry with no `onlyX` modifier and no reentrancy guard: [1](#0-0) 

Unlike `Swap.sol`'s `fillZrxQuote` (which was at least gated inside the `Swap` contract's own function), `CallDispatcher.dispatch` is directly callable by **anyone**, at **any time**, independent of `IntentGatewayV2`, `HyperFungibleToken`, or `WrappedHyperFungibleToken`. It is documented as a single shared, standing deployment reused across all of these apps ("Existing `CallDispatcher` deployments are listed on the contract addresses page"): [2](#0-1) 

The dispatcher legitimately and transiently holds real value in multiple flows:
- `IntentGatewayV2.placeOrder` sends predispatch input assets to the dispatcher, calls `dispatch()`, then sweeps balances back via a second `dispatch()` call: [3](#0-2) 
- `IntentsBase._execute` sends output assets through the dispatcher for postdispatch calldata, then sweeps residual balances back: [4](#0-3) 
- `HyperFungibleToken`/`WrappedHyperFungibleToken.onAccept` can deliver minted/unlocked tokens directly `to` the `CallDispatcher` address and then forward `message.data` to it: [5](#0-4) 
- It also has an unrestricted `receive() external payable {}`, so anyone can push ETH into it: [6](#0-5) 

Because `dispatch()` itself performs raw `to.call{value: call.value}(call.data)` from the dispatcher's own address — which is the true owner of any tokens/ETH it is holding at that moment — an attacker does not even need the "approve then `transferFrom`" trick from the original report. A direct `Call({to: token, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, dispatcher.balanceOf())})` moves the dispatcher's *own* balance to the attacker, since `CallDispatcher` is the caller (`msg.sender` inside `transfer`), and no allowance check applies. The `IntentGatewayV2`/`IntentsBase` call sites are `nonReentrant` on their own storage, but that guard is scoped to `IntentGatewayV2`, not to the independently-callable `CallDispatcher` contract — a directly-submitted transaction to `CallDispatcher.dispatch()` is not a reentrant call into the gateway at all, so the gateway's guard provides no protection to funds sitting in the shared dispatcher.

### Impact Explanation
Any window in which the shared `CallDispatcher` holds a nonzero ERC20/ETH balance (predispatch/postdispatch legs of `IntentGatewayV2` orders, `HyperFungibleToken`/`WrappedHyperFungibleToken` cross-chain deliveries routed `to` the dispatcher, or accidental/dust transfers) is directly drainable by any unprivileged address that races to call `dispatch()` first. Since the dispatcher is a single standing deployment shared by every app that uses it, a drain affects funds belonging to whichever user's order/transfer is mid-flight at that time — output tokens meant for a beneficiary, input tokens mid-predispatch-sweep, or bridged tokens en route to a recipient. This is concrete theft of user/solver/protocol funds.

### Likelihood Explanation
Exploitability depends on finding/creating a moment where the dispatcher genuinely holds value across an attacker-observable boundary (e.g. mempool visibility of a `placeOrder`/`fillOrder`/`onAccept` transaction before its internal sweep executes, or a transaction that is not fully atomic with the sweep). I was not able to fully confirm from the available code slices whether every legitimate call path keeps token custody in the dispatcher fully atomic within a single transaction with no observable intermediate state (mempool front-running of the *same* transaction is not possible, but if any code path performs the transfer-in and the `dispatch()` sweep call as **separate top-level transactions**, or if a `dispatch()` call's own external sub-call can reenter `dispatch()` before the caller's sweep runs, the attack is directly exploitable with high likelihood). This distinction could not be fully verified with the tools available in this pass.

### Recommendation
- Restrict `CallDispatcher.dispatch()` to a caller allowlist (e.g., only `IntentGatewayV2`, `HyperFungibleToken`, `WrappedHyperFungibleToken` instances), analogous to the recommended `zrxTo` whitelist in the original report — but here the fix should whitelist *callers* of `dispatch`, not just call targets.
- Add a reentrancy guard to `dispatch()` itself so a malicious `to` target invoked mid-loop cannot reenter and redirect funds before the outer sweep completes.
- Avoid designing any flow where the shared dispatcher's token/ETH custody spans more than one atomic transaction; if such a window is unavoidable, deploy an ephemeral, single-use dispatcher per operation instead of a shared standing contract.

### Proof of Concept
Conceptual (pending confirmation of a concrete cross-transaction custody window):
1. Attacker observes (or triggers) a state where `CallDispatcher` holds `X` tokens (e.g. before `IntentGatewayV2.placeOrder`'s second `dispatch(transferCalls)` sweep executes, or before `IntentsBase._execute`'s sweep-back step).
2. Attacker calls `CallDispatcher.dispatch(abi.encode([Call({to: token, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, X)})]))` directly — no permission is required since `dispatch()` has no access control.
3. `CallDispatcher`, as `msg.sender` of the inner call and true owner of the tokens, transfers `X` tokens to the attacker.
4. The original caller's subsequent sweep/withdrawal now finds a depleted balance, causing loss of funds for the intended beneficiary/solver/user.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
