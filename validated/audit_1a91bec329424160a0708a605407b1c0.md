### Title
Webhook `shop-domain` header is trusted for tenant dispatch but excluded from HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines `to_signable_string` to return only the raw HTTP body: [1](#0-0) 

The `shop` (and `topic`, `webhook_id`, `api_version`) values are read directly from HTTP headers and are never part of the HMAC-signed material: [2](#0-1) 

`Utils::HmacValidator.validate` recomputes the signature purely from `to_signable_string` (the body) and compares it against the `hmac` header: [3](#0-2) 

`Registry.process` treats a successful HMAC check as authorization to trust the entire request, including `request.shop`, and dispatches it to the handler as the tenant identity for the event: [4](#0-3) 

The resulting `WebhookMetadata.shop` field is what host applications use to resolve which merchant/tenant a webhook belongs to: [5](#0-4) 

This is the identity-binding break described by the analog class: the byte range **verified** by the HMAC (raw body only) is not the same as the byte range **acted on** as tenant identity (the `shop-domain` header). Formally: `hmac_covers(raw_body) ≠ shop_used_for(tenant_dispatch)`.

### Impact Explanation
An attacker who is a legitimate, unprivileged user of the app (e.g., installs the app on their own store) will receive genuinely-signed webhook deliveries from Shopify for their own shop — a valid `(raw_body, hmac)` pair signed with the app's `client_secret`, which the attacker never needs to know. Because the `shop-domain` header is outside the signed payload, the attacker can replay that exact `raw_body`/`hmac` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain. `Utils::HmacValidator.validate` still passes (it only checks the body), and `Registry.process` calls the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain. Any host application logic that uses this `shop` field to select a session, tenant record, or perform tenant-scoped side effects (a common, documented usage pattern for this gem) will act on the wrong tenant — a cross-tenant confusion driven entirely by the gem's failure to bind an authenticated identity field into the signature it verifies.

### Likelihood Explanation
Exploitation requires no secrets, no privileged account, and no access to the target tenant — only that the attacker be able to install the app once on a store they control (a normal, unprivileged action for any Shopify merchant/developer) and be able to send an HTTP request to the app's public webhook endpoint with a modified header. This is directly reachable through the gem's own public `Webhooks::Request` / `Webhooks::Registry.process` API exactly as documented, with no reliance on host-app misconfiguration beyond following the gem's own instructions.

### Recommendation
Bind the tenant/shop identity into the verified material rather than trusting an unauthenticated header for dispatch. Concretely, include the `shop-domain` (and ideally `topic`/`webhook_id`) header bytes in `Request#to_signable_string`, or independently cross-check the `shop` header value against a shop already known/authorized for the resolved webhook_id/registration before invoking the handler with it, so that `hmac_covers(...) == shop_used_for(tenant_dispatch)` holds.

### Proof of Concept
1. App developer/attacker installs the app on their own store `attacker.myshopify.com`, and their webhook endpoint receives a legitimate delivery:
   - headers: `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, `x-shopify-topic: orders/create`
   - body: `{"id":123, ...}`
2. Attacker replays the identical body and `x-shopify-hmac-sha256` value to the same endpoint, but changes only:
   - `x-shopify-shop-domain: victim.myshopify.com`
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds the request; `hmac` and `to_signable_string` are unaffected by the header change: [6](#0-5) 
4. `Utils::HmacValidator.validate(request)` returns `true` because it only checks `raw_body` against the secret: [7](#0-6) 
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(... shop: request.shop ...)`, where `request.shop` is now `"victim.myshopify.com"` even though the payload was never signed for that tenant: [8](#0-7)
