## Title
EcdsaBeefy/SP1Beefy Solidity consensus clients accept state commitments for any parachain in the relay-chain proof without checking it is a configured/tracked route - ([File: evm/src/consensus/EcdsaBeefy.sol])

## Summary
The CVE describes TLS clients that validate a certificate chain's signature but fail to check whether the chain's root corresponds to a *configured* (trusted) CA — i.e., a cryptographically valid chain is accepted even though it does not terminate at an intentionally-trusted anchor. The structurally analogous pattern in Hyperbridge is: a BEEFY consensus proof is fully and correctly verified (signatures, authority-set membership, MMR inclusion), but the resulting per-parachain state commitment is accepted for *whatever parachain ID is embedded in the proof*, without checking that this parachain ID is one Hyperbridge actually configured/intends to trust for that consensus client.

## Finding Description
`EcdsaBeefy.verifyParachainHeaderProof` (`evm/src/consensus/EcdsaBeefy.sol:198-229`) decodes each parachain header contained in the proof and unconditionally builds an `IntermediateState` from `para.id`: [1](#0-0) 
There is no check anywhere in this function (or in `SP1Beefy.verifyConsensus`, `evm/src/consensus/SP1Beefy.sol:114-177`) that `para.id` is a parachain this Hyperbridge deployment is meant to track. Compare this with the Substrate/Rust BEEFY consensus client, `modules/ismp/clients/beefy/src/consensus.rs:113-118`, which explicitly gates each parachain header behind an allow-list before constructing the intermediate commitment: [2](#0-1) 
and behind `state_machine()`'s registration check, `modules/ismp/clients/beefy/src/consensus.rs:241-243`: [3](#0-2) 
The GRANDPA and Optimism/Tendermint/Pharos Rust clients follow the same pattern (`SupportedStateMachines::<T>::contains_key`, `Parachains::<T>::contains_key`), consistently enforcing "is this state machine ID a configured root of trust" before accepting a commitment for it.

The only mitigating check downstream is in `HandlerV2._updateConsensusState`/verify flow (`evm/src/core/HandlerV2.sol:155-164`): [4](#0-3) 
which only stores a commitment when `latestHeight != 0`, i.e., the state machine ID must have been previously initialized. This limits — but does not eliminate — the exposure: any parachain ID that was ever initialized (e.g. during genesis/consensus-client creation, or via an earlier legitimate update for a chain later meant to be deprecated) continues to have its state commitments silently kept fresh by any relayer who includes that parachain's header in a BEEFY proof, with no on-chain allow-list to stop it, unlike the Substrate side.

## Impact Explanation
Because the EVM-side BEEFY/SP1-BEEFY clients have no explicit "supported/tracked parachain" allow-list (the Rust implementation has one), any already-initialized `stateMachineId` keeps accruing genuine — but potentially unintended — state commitments as long as a relayer chooses to include that parachain's header in a relay-chain proof. This breaks the intended access-control model where only specific, deliberately configured parachains should be able to have their state trusted by an EVM Hyperbridge deployment, analogous to a TLS client accepting a validly-signed certificate chain whose root was never actually configured as trusted. If a state machine ID is ever deprecated/rotated by governance without removing its `latestStateMachineHeight` entry, or if any parachain ID happens to coincide with one already tracked, its state commitment can continue to be updated and later used to satisfy `verify_membership`/message-delivery checks (`HandlerV2.handlePostRequests`, `handleGetResponses`) for that state machine, potentially allowing message delivery/state proofs to be accepted from a source the operators no longer intend to trust.

## Likelihood Explanation
Exploitation requires no privileged access — any unprivileged relayer can submit a BEEFY/SP1-BEEFY consensus proof containing parachain headers of their choosing (as long as they are genuinely finalized on the relay chain and included in the signed MMR root), and the EVM consensus client will happily update the corresponding commitment for any previously-initialized `stateMachineId`. The precondition (an ID with `latestHeight != 0`) makes brand-new/never-configured chains safe, but any chain that was ever set up (including ones later intended to be frozen/removed from trust) remains open to continued, unpermissioned updates.

## Recommendation
Add an explicit on-chain allow-list of tracked/supported state machine IDs (parachain IDs) to `EcdsaBeefy.sol` and `SP1Beefy.sol`, mirroring `is_parachain_tracked`/`SupportedStateMachines` in the Rust clients, and filter `verifyParachainHeaderProof`/`verifyConsensus` output to only emit `IntermediateState`s for IDs present in that list. Ensure governance can add/remove entries from this list independently of `latestStateMachineHeight`, so that deprecating a state machine actually stops further trust extension rather than relying solely on the `latestHeight != 0` heuristic in `HandlerV2`.

## Proof of Concept
1. Hyperbridge Nexus (`stateMachineId = 3367`) is registered on an EVM deployment with `latestStateMachineHeight(3367) != 0`.
2. Suppose governance decides to deprecate trust in a second parachain, `stateMachineId = X`, that was also previously initialized (e.g. during a migration or a prior configuration), but no code path in `EcdsaBeefy.sol`/`SP1Beefy.sol` removes its nonzero `latestStateMachineHeight`.
3. An unprivileged relayer subscribes to BEEFY justifications, obtains a legitimately signed relay-chain commitment, and constructs a `RelayChainProof`/`ParachainProof` (or SP1 proof) that includes parachain `X`'s finalized header alongside the merkle multiproof against the MMR leaf's `parachain_heads_root` — exactly as done in `evm/tests/rust/src/tests/ecdsa_beefy.rs:242-250`. [5](#0-4) 
4. Calling `EcdsaBeefy.verify` with this proof succeeds (all signature/MMR/multiproof checks pass because the data is genuine), and returns an `IntermediateState` for `stateMachineId = X`.
5. `HandlerV2` stores this commitment because `latestStateMachineHeight(X) != 0`, silently extending "trust" in `X`'s state despite there being no Solidity-side allow-list check equivalent to the Rust `is_parachain_tracked` gate that would have rejected it.

Note: I was unable to fully verify from the index whether any admin/governance function exists in `EvmHost.sol` to explicitly deregister or zero out a `stateMachineId`'s height once initialized (the grep matches for `latestStateMachineHeight` in `EvmHost.sol`/`TestnetHost.sol` were not read in full due to iteration limits), so the exact operational conditions under which a "deprecated but still nonzero" state machine ID would arise in production configuration are not fully confirmed. A Devin session with full repository access would be needed to confirm whether such a deregistration path exists and to size the real-world likelihood more precisely.
