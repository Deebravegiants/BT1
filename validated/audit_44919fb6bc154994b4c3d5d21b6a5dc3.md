### Title
CallDispatcher.dispatch() has no caller/target whitelist, allowing anyone to steal leftover tokens temporarily held by the shared dispatcher - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher.dispatch()` is the Hyperbridge analog of LiFi's unwhitelisted `Executor._executeSwaps()`. It executes attacker-supplied `Call[]` arrays (arbitrary `to`/`value`/`data`) against any contract with no restriction on `msg.sender` and no allow-list of callable targets or function selectors, exactly the pattern flagged in the external report. Unlike LiFi's `Executor`, which at least gates `_executeSwaps` behind `IAxelarExecutable`'s authenticated entrypoint, `CallDispatcher.dispatch()` is a bare `external` function callable by anyone directly, and the same `CallDispatcher` instance is shared across `IntentGatewayV2`, `HyperFungibleToken`, `WrappedHyperFungibleToken`, and `BridgeToken` on a given chain.

### Finding Description
`CallDispatcher.dispatch()` decodes an arbitrary `Call[]` from its input and executes every call with no origin check and no target/selector whitelist: [1](#0-0) 

This contract is designed to *temporarily* hold funds while executing composable flows:
- `IntentGatewayV2.placeOrder()` transfers predispatch input assets to the dispatcher, then calls `dispatch(order.predispatch.call)` before sweeping the resulting balance back to the gateway: [2](#0-1) 
- `IntentsBase._execute()` runs postdispatch calldata via the same dispatcher after filling an order, then sweeps residual balances back as "dust": [3](#0-2) 
- `HyperFungibleToken`/`WrappedHyperFungibleToken.onAccept()` mint/unlock tokens then forward `message.data` to the same dispatcher; the docs explicitly instruct integrators to set the recipient `to` field to the `CallDispatcher` address so bridged tokens land there before further calls run: [4](#0-3) 

The project's own documentation acknowledges the exact risk pattern from the external report — that the dispatcher "holds tokens temporarily during execution" and warns against unlimited allowances in `Call[]` payloads: [5](#0-4) 

Because `dispatch()` has no access control at all, this guidance is not actually enforced on-chain: any address can call the shared `CallDispatcher` directly (not through `IntentGatewayV2` or the HFT contracts) with a crafted `Call[]` that, e.g., calls `token.transfer(attacker, balance)` or `token.transferFrom(...)` against a stale allowance, sweeping out any tokens or allowances that happen to be sitting in (or approved to) the dispatcher at that moment — whether left over from a reverted/partial swap, an approve-then-swap sequence that didn't consume the full allowance, or any other integrator that reuses the same deployed `CallDispatcher` (deploy scripts show one `CallDispatcher` shared by `IntentGatewayV2`, `HyperFungibleToken`, `WrappedHyperFungibleToken`, and `BridgeToken` per chain).

### Impact Explanation
If any ERC-20 balance or non-zero allowance is ever left on the `CallDispatcher` — from a partially-consumed swap in an intent fill/predispatch, an approve-then-swap `Call[]` that doesn't reset the allowance, or a failed/aborted downstream call whose token transfer already landed — any unprivileged address can drain it in a single transaction by calling `dispatch()` directly with its own `Call[]`. This is a concrete theft-of-funds primitive reachable from a single externally submitted transaction, matching the "concrete theft ... of funds" bar in the validation rules.

### Likelihood Explanation
Likelihood is elevated relative to the original LiFi finding because `dispatch()` has no caller authentication whatsoever (LiFi's `Executor._executeSwaps` is at least reachable only through the authenticated Axelar executable path). The dispatcher is also explicitly designed and documented to hold tokens/allowances mid-flow (predispatch escrow assets, postdispatch DEX routing, bridged-token calldata execution), and is a long-lived, address-shared singleton across multiple apps rather than a per-call ephemeral contract, increasing the window and surface for residual balances/allowances to accumulate.

### Recommendation
- Restrict `CallDispatcher.dispatch()` to only be callable by the specific app contracts it was deployed to serve (an allow-list of caller addresses set at construction/configuration), analogous to adding the missing whitelist recommended in the original report.
- Alternatively/additionally, deploy a fresh, single-use `CallDispatcher` (e.g., via `CREATE2`/minimal proxy) per `dispatch()` invocation so no funds or allowances can persist between calls, eliminating the shared-state theft window entirely.
- Ensure any `Call[]` that grants allowances always resets them to zero (or uses `permit`/exact-amount approvals) after use, and add an explicit sweep/self-destruct step so the dispatcher never carries a non-zero balance across transactions.

### Proof of Concept
1. Any user's `IntentGatewayV2.placeOrder()` (or `HyperFungibleToken.onAccept()`) predispatch/postdispatch flow leaves a residual ERC-20 balance or non-zero allowance on the shared `CallDispatcher` (e.g., a DEX swap `Call[]` approves the router for more than is consumed, or a swap partially fails to sweep all output tokens).
2. An attacker observes (via mempool or on-chain state) that `CallDispatcher` now holds `X` tokens or a spendable allowance.
3. The attacker calls `CallDispatcher.dispatch(abi.encode([Call({to: token, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, X)})]))` directly — no authentication is required since `dispatch()` performs no `msg.sender` check, per `evm/src/utils/CallDispatcher.sol` lines 44-62.
4. The call succeeds, transferring the leftover tokens to the attacker.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

Existing `CallDispatcher` deployments are listed on the [contract addresses](/developers/evm/contract-addresses/mainnet) page.
