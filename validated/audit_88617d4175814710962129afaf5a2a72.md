### Title
Webhook `shop-domain` header is not covered by HMAC verification, allowing tenant-identity spoofing in `ShopifyAPI::Webhooks::Request` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body via `Utils::HmacValidator.validate(request)` [1](#0-0) . The `shop` value that is forwarded to the host application's handler as the tenant identifier, however, comes from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is never part of the signed payload.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [2](#0-1) , and `HmacValidator.validate_signature` computes/compares the HMAC exclusively over that signable string [3](#0-2) . Meanwhile `Request#shop` simply reads the `shopify-shop-domain` header with no cryptographic binding to the body or the HMAC [4](#0-3) .

This breaks the intended identity binding: `shop_authenticated == shop_used_by_handler`. Concretely:
- Before the attack: a legitimate webhook for shop A arrives with body B, HMAC = HMAC(secret, B), and header `shopify-shop-domain: A.myshopify.com`. `Registry.process` validates HMAC(B) and passes `shop: "A.myshopify.com"` to the handler [1](#0-0) .
- After the attack: any party who has received one genuine webhook delivery (body B, valid HMAC) — e.g., a merchant installing the app on their own low-privilege shop — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still returns `true` because it only checks `raw_body` against the signature, which is unchanged. `Registry.process` then raises no error and calls `handler.handle(data: WebhookMetadata.new(topic:, shop: request.shop, body: request.parsed_body, ...))`, delivering a payload tagged with the attacker-chosen victim shop [1](#0-0) .

Any host application that uses `data.shop` (or `request.shop`) to select which tenant's session/data to update — the documented purpose of this field — is misled into applying the attacker's webhook body under the victim's tenant identity, i.e., cross-tenant confusion enabled entirely by this gem's verification logic.

### Impact Explanation
This is a cross-tenant identity-binding bypass: the field that determines *which merchant* a webhook payload is attributed to (`shop`) is not covered by the same cryptographic proof (`hmac`) that the gem uses to certify the payload is authentic. An attacker who can obtain (or self-generate, e.g., by installing the app on their own store and receiving a webhook) one valid `(body, hmac)` pair can relabel it to any target shop domain and have it accepted as authentic by `Registry.process`, matching the "field acted on but not covered by the HMAC" identity-binding class. Depending on how the host app implements its handler (e.g., updating per-shop state, deleting data on `shop/redact`, disabling features), this can lead to cross-tenant data corruption purely through this gem's own verification contract.

### Likelihood Explanation
Exploitation requires only the ability to send an HTTP request to the app's webhook endpoint with attacker-controlled headers and a previously-observed valid `(raw_body, hmac)` pair — no `api_secret_key`, access token, or privileged account is required. Obtaining one genuine `(body, hmac)` pair is trivial for anyone who installs the app on their own shop and receives any webhook (even a repeatable/generic one like `app/uninstalled` or `shop/redact`).

### Recommendation
Include the `shop` (and ideally `topic`, `webhook-id`) values in the signable string used for HMAC verification, or otherwise cryptographically bind the shop domain to the signed payload before it is trusted by `Registry.process` / exposed via `WebhookMetadata`.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; capture any inbound webhook request: raw body `B`, header `x-shopify-hmac-sha256: H` (valid for `B`), `x-shopify-shop-domain: attacker.myshopify.com`.
2. Replay the exact same body `B` and HMAC header `H` to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` only and matches `H`, so validation succeeds [5](#0-4) .
4. The handler is invoked with `WebhookMetadata` where `shop == "victim.myshopify.com"`, even though the payload/HMAC never originated from Shopify for that shop [6](#0-5) .
