### Title
Misplaced `break` inside `select` fails to terminate the topic loop in `processTrigger`, causing duplicate trigger executions per request - ([File: core/capabilities/webapi/trigger/trigger.go])

### Summary
In `triggerConnectorHandler.processTrigger`, after successfully delivering a `TriggerResponse` to a registered workflow's channel, the code attempts to stop iterating over the remaining topics with a `break` statement placed inside a `select` case. In Go, `break` only terminates the innermost `for`, `switch`, or `select` — since it is nested inside `select`, it exits only the `select`, not the enclosing `for _, topic := range topics` loop, contradicting the developer's own comment on the same line.

### Finding Description
`processTrigger` iterates over every registered `webapiTrigger` and, for each one, iterates over every topic supplied in the external request's payload: [1](#0-0) 

When a topic matches `trigger.allowedTopics` and the sender/rate-limit checks pass, the code sends a `TriggerResponse` into the workflow's channel and intends to stop processing further topics for that same trigger: [2](#0-1) 

The comment `// Sending n topics that match a workflow with n allowedTopics, can only be triggered once.` makes the intent explicit: only one execution should be emitted per external request, no matter how many topics match. However, the `break` on line 152 is inside the `select` statement's `case trigger.ch <- tr:` branch. Per Go language semantics, `break` inside `select` only exits the `select`, not the surrounding `for _, topic := range topics` loop. Execution falls through to the next iteration of the `topic` loop, and if additional topics in the same request also match `trigger.allowedTopics`, the sender/rate-limit checks are re-evaluated and, if they pass again, another `TriggerResponse` with the same `TriggerEventID` (`body.Sender + payload.TriggerEventId`, independent of topic) is sent to the same workflow channel again.

This is structurally the same class of bug as the referenced Solidity finding: a control-flow statement (`break`) is expected to terminate loop processing at a certain point but, due to its placement/scope, does not actually do so, causing the function to keep iterating and perform unintended additional work.

### Impact Explanation
An unprivileged external caller reaching this code via the gateway (`HandleGatewayMessage` → `processTrigger`) can submit a single `web_api_trigger` request whose `Topics` list contains multiple strings that are all present in one workflow's `allowedTopics` set: [3](#0-2) [4](#0-3) 

Because the loop is not actually terminated after the first successful delivery, the same request causes the trigger channel to receive multiple `TriggerResponse` events (one per matching topic), which in turn causes the workflow engine to start multiple workflow executions from a single external message — an unintended duplicate/unauthorized job run triggered by a single unprivileged request. This can also amplify rate-limiter bypass, since each additional topic re-checks (not accumulates) `trigger.rateLimiter.Allow`, allowing more executions per request than the rate limiter's per-request intent.

### Likelihood Explanation
Any external, unprivileged caller who can reach the gateway's web API trigger endpoint and knows (or guesses) a workflow's configured `AllowedTopics` can trigger this by simply listing more than one matching topic in a single request payload — no special privileges are required beyond being an allowed sender for that trigger, which is the normal, expected caller for this endpoint.

### Recommendation
Use a labeled loop (or a boolean flag / early `return`/`goto`) so that once a matching topic successfully delivers the event, the outer `for _, topic := range topics` loop is actually terminated, e.g.:
```go
topicLoop:
for _, topic := range topics {
    if trigger.allowedTopics[topic] {
        ...
        select {
        case <-ctx.Done():
            trigger.chWriteMu.Unlock()
            return nil
        case trigger.ch <- tr:
            trigger.chWriteMu.Unlock()
            break topicLoop
        }
    }
}
```

### Proof of Concept
1. Register a workflow trigger with `AllowedTopics = ["topicA", "topicB"]` and an allowed sender address.
2. As that allowed sender, send a single `web_api_trigger` gateway message with `payload.Topics = ["topicA", "topicB"]`.
3. In `processTrigger`, the inner loop matches `topicA` first: sender/rate-limit checks pass, a `TriggerResponse` is sent to `trigger.ch`, and the `select`'s `break` only exits the `select`.
4. The loop continues to `topicB`, which also matches `trigger.allowedTopics`; sender/rate-limit checks are re-evaluated and pass again, sending a second `TriggerResponse` with the same `TriggerEventID` to the same channel.
5. The workflow engine receives two trigger events for what the caller submitted as a single request, resulting in duplicate workflow execution from one external call.

func (h *triggerConnectorHandler) HandleGatewayMessage(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) error {
	msg, err := hc.ValidatedMessageFromReq(req)
	if err != nil {
		h.lggr.Errorw("error validating message from request", "err", err, "request", req)
		return nil
	}
	body := &msg.Body
	sender := ethCommon.HexToAddress(body.Sender)
	var payload webapicap.TriggerRequestPayload
	err = json.Unmarshal(body.Payload, &payload)
	if err != nil {
		h.lggr.Errorw("error decoding payload", "err", err)
		err = h.sendResponse(ctx, gatewayID, body, ghcapabilities.TriggerResponsePayload{Status: "ERROR", ErrorMessage: fmt.Errorf("error %s decoding payload", err.Error()).Error()})
		if err != nil {
			h.lggr.Errorw("error sending response", "err", err)
		}
		return nil
	}

	switch body.Method {
	case ghcapabilities.MethodWebAPITrigger:
		resp := h.processTrigger(ctx, gatewayID, body, sender, payload)
		var response ghcapabilities.TriggerResponsePayload
		if resp == nil {
			response = ghcapabilities.TriggerResponsePayload{Status: "ACCEPTED"}
		} else {
			response = ghcapabilities.TriggerResponsePayload{Status: "ERROR", ErrorMessage: resp.Error()}
			h.lggr.Errorw("Error processing trigger", "gatewayID", gatewayID, "body", body, "response", resp)
		}
		err = h.sendResponse(ctx, gatewayID, body, response)
		if err != nil {
			h.lggr.Errorw("Error sending response", "body", body, "response", response, "err", err)
		}
		return nil
