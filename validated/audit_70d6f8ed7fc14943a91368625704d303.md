### Title
Webhook `shop-domain`, `topic`, `api_version`, and `webhook_id` are trusted by handlers despite not being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from unauthenticated HTTP headers. `Registry.process` validates only the body/HMAC pair and then hands the header-derived `shop` value straight to the app's `WebhookHandler` as trusted tenant identity, breaking the intended binding `shop verified by HMAC == shop acted upon`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` (and `topic`, `api_version`, `webhook_id`) are pulled straight from HTTP headers, never included in the signable content: [2](#0-1) 

`Registry.process` validates the request using `HmacValidator.validate`, which only checks `hmac` against `to_signable_string` (i.e., the raw body) as shown in `HmacValidator#validate_signature`: [3](#0-2) 

After that single check passes, `Registry.process` immediately trusts `request.shop` (a header value never covered by the HMAC) and forwards it as authoritative tenant identity to the host application's handler: [4](#0-3) [5](#0-4) 

This is the exact bug-class pattern described in the report — "a field acted on but not covered by the HMAC" — mapped to Morpho's failure to validate state before trusting IRM output. Here, the gem validates only the raw body's integrity but trusts the `shop` field (analogous to an untrusted state variable) that determines which tenant's data pipeline is invoked, without binding it cryptographically.

By contrast, the OAuth callback path (`AuthQuery`) correctly includes `shop` inside the signed payload, so `shop` there is bound to the HMAC: [6](#0-5) 

This shows the webhook path is an inconsistent design: the identity field (`shop`) that downstream code (`WebhookMetadata.shop`) treats as authoritative for tenant routing is excluded from the very signature meant to authenticate the message's origin.

### Impact Explanation
Any attacker who is themselves a legitimate (if unprivileged) installer of the vulnerable app on their own shop can capture one of their own genuinely Shopify-signed webhook deliveries (raw body + valid `x-shopify-hmac-sha256`). Because the signature covers only the body, they can resend that exact body/HMAC pair directly to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header with an arbitrary victim shop's domain. `HmacValidator.validate` still succeeds (the body/HMAC pair is genuinely valid), so `Registry.process` proceeds and calls the app's handler with `WebhookMetadata.shop` set to the attacker-chosen victim shop. If the host application uses this trusted `shop` value to look up the victim's session/access token, write data associated with the victim tenant, or bypass per-shop authorization checks (a documented and expected usage pattern for this API, since the gem provides `shop` specifically for that purpose), this results in cross-tenant data injection/access — a Critical-impact outcome under the given classification.

### Likelihood Explanation
Exploitation requires no possession of the app's `client_secret`/access token and no MITM: the attacker only needs to be a normal (even free) installer of the target app on any shop, allowing them to receive at least one legitimately HMAC-signed webhook they can replay with a forged domain header. This is a realistic, low-barrier attack path for any external actor able to install the app.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`) values in the material that is HMAC-verified, or otherwise cryptographically bind them to the raw body before trusting them (e.g., verify against Shopify's TLS-terminated request source, or require the host app to cross-check `shop` against a known/registered shop list before use). At minimum, update `Request#to_signable_string` to incorporate the `shopify-shop-domain` header so that `HmacValidator.validate` fails if that header is altered independently of the signed body.

### Proof of Concept
1. Attacker installs the vulnerable app on `attacker-shop.myshopify.com` and triggers a real event (e.g., creates an order) so Shopify sends a legitimately signed webhook to the app's public webhook endpoint, e.g.:
```
POST /webhooks HTTP/1.1
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <valid HMAC over the raw JSON body>
x-shopify-shop-domain: attacker-shop.myshopify.com
x-shopify-webhook-id: ...
x-shopify-api-version: 2024-01

{...order json...}
```
2. Attacker captures this exact raw body and its valid `x-shopify-hmac-sha256`.
3. Attacker resends the identical body and HMAC header to the same endpoint, but replaces the header:
```
x-shopify-shop-domain: victim-shop.myshopify.com
```
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `hmac` against `raw_body` — unaffected by the domain header change: [7](#0-6) 
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and processes/persists the payload as if it genuinely originated from the victim's shop, even though the victim never sent this webhook.
