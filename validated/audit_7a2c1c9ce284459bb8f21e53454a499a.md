### Title
Webhook shop-domain (and topic/webhook-id) headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from unauthenticated HTTP headers. `Webhooks::Registry.process` validates only the body's HMAC and then dispatches the handler using the unauthenticated `shop` value, so the identity the app acts on (the shop) is not bound to the signature that was actually verified.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from HTTP headers with no cryptographic binding to the request: [2](#0-1) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` (the body) and compares it to the `hmac` header, using `Context.api_secret_key`: [3](#0-2) 

`Registry.process` checks only this body-HMAC, then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`) to build the data passed to the app's handler: [4](#0-3) 

Because `api_secret_key` is a single per-app secret shared across every shop that installs the app (it is not per-shop/session-scoped — see how the same `Context.api_secret_key` is used everywhere, e.g. `HmacValidator`, `JwtPayload`), any merchant on the app can obtain a validly-signed webhook for their own store (the body+HMAC pair Shopify sent them) and replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain. The HMAC check still passes, because it only verifies the body, not the shop header. The handler then executes attacker-supplied data under the victim's shop identity:

```
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
  body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
``` [5](#0-4) 

This breaks the equality that should hold: `shop authenticated by HMAC == shop the handler acts on`. Before the attack, both sides are the attacker's own shop; after the attack, the header-derived `shop` is the victim's domain while the only thing actually verified (the body/HMAC) still belongs to the attacker's own webhook.

### Impact Explanation
This is a cross-tenant data-integrity break: a shop with no access to the victim's data can cause the host application to process webhook events (create/update handlers, order/customer/GDPR data, etc.) tagged as belonging to another merchant's shop, since `WebhookMetadata#shop` is what apps typically use to look up the tenant's session/store record before acting. This matches the Critical "cross-tenant access" category defined by the rules.

### Likelihood Explanation
Any unprivileged internet user who can install the app on their own shop (which is the normal, unprivileged path for any Shopify app) automatically receives real HMAC-signed webhooks from Shopify for their own store and can capture body+HMAC pairs without needing `api_secret_key`, an access token, or any elevated privilege. Replaying the request with a modified shop header is a trivial HTTP manipulation, requiring only that the host app trusts the `shop` field from `WebhookMetadata` (the gem's own documented/intended usage pattern) to select a tenant.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable content that the HMAC covers (or otherwise cryptographically bind them to the verified body), so that changing any of these header values invalidates the HMAC. At minimum, document and enforce that `shop` must be independently cross-checked against a known/allow-listed value before it is used to resolve a tenant/session — the gem should not present the header-derived shop as verified when only the body has been checked.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook, e.g.:
   ```
   POST /webhooks
   x-shopify-topic: customers/data_request
   x-shopify-hmac-sha256: <valid HMAC of body B>
   x-shopify-shop-domain: attacker.myshopify.com
   Body: B
   ```
2. Attacker resends the exact same body `B` and HMAC header, but changes only:
   ```
   x-shopify-shop-domain: victim.myshopify.com
   ```
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` using the app's single `api_secret_key` — it matches, since `B` and the secret are unchanged: [6](#0-5) 
4. `process` proceeds to call `handler.handle(data: WebhookMetadata.new(..., shop: "victim.myshopify.com", body: parsed(B), ...))`, causing the app to act on/for `victim.myshopify.com` using attacker-controlled body content, despite never having verified anything belonging to that shop. [7](#0-6)

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
