### Title
Fail-open authorization gate on stage builds allows biometric capture and PCP build despite blocked orb software version - ([File: src/plans/mod.rs])

### Summary
In `MasterPlan::do_signup`, when `is_orb_os_version_allowed` returns `false`, the non-stage build path correctly returns `Ok(result)` immediately, aborting the signup. On stage-feature builds, however, the code only calls `notify_failed_signup` and does not return, so execution falls through to `scan_remaining_qr_codes` completion checks, `biometric_capture`, `biometric_pipeline`, `detect_fraud`, and `build_pcp`.

### Finding Description
The relevant code is: [1](#0-0) 
```rust
if !self.is_orb_os_version_allowed(debug_report).await {
    #[cfg(feature = "stage")]
    notify_failed_signup(orb, Some(SignupFailReason::SoftwareVersionBlocked));
    #[cfg(not(feature = "stage"))]
    return Ok(result);
}
```
The `#[cfg(not(feature = "stage"))]` branch is the only branch with a `return`. On a stage-feature build, the `if` block only notifies the failure and then falls through to the rest of `do_signup`, which proceeds to sleep, call `self.biometric_capture(...)`, `self.biometric_pipeline(...)`, `self.detect_fraud(...)`, and ultimately `self.build_pcp(...)` [2](#0-1) . This is a genuine, exact-file/function-supported divergence between the two cfg branches: one branch aborts, the other does not.

### Impact Explanation
If this path is reachable in a real fielded orb build (i.e., stage feature is compiled into orbs deployed to a staging backend that still process real users' biometrics), the intended fail-closed authorization gate for deprecated/blocked orb software versions is bypassed on that build variant: a full biometric capture, fraud pipeline, and PCP (personal custody package) build/upload can complete even though the backend explicitly flagged the orb's software version as not allowed. This would undermine a pre-capture authorization control and could let devices with revoked/blocked software continue enrolling users and uploading biometric packages.

### Likelihood Explanation
This requires the orb to be running a build compiled with the `stage` feature and the backend responding that the orb software version is not allowed. Whether this constitutes an in-scope, exploitable "production" condition is uncertain from the code alone — I could not confirm from the available files whether the `stage` feature reflects a real deployed staging fleet (which processes genuine biometric signups from real users, making the bug material) or a developer/test-only build configuration excluded by the audit rules ("test-only cfg paths"). The `stage` feature is referenced across several files (`src/config.rs`, `src/consts.rs`, `src/debug_report.rs`, `src/backend/endpoints.rs`, `src/brokers/observer.rs`, `src/plans/enroll_user.rs`, `src/agents/python/iris/mod.rs`, `src/agents/image_notary.rs`), suggesting it toggles backend endpoints/behavior for a staging environment rather than being purely a unit-test cfg, which would argue for in-scope impact, but this is not conclusively verified.

### Recommendation
Make the failure path fail-closed unconditionally regardless of build feature: call `notify_failed_signup` (if desired, gated by `stage` for the notification behavior only) and then always `return Ok(result);` outside of any `cfg` exclusivity, e.g.:
```rust
if !self.is_orb_os_version_allowed(debug_report).await {
    #[cfg(feature = "stage")]
    notify_failed_signup(orb, Some(SignupFailReason::SoftwareVersionBlocked));
    return Ok(result);
}
```

### Proof of Concept
Integration test compiled with `--features stage`:
1. Mock/stub `MasterPlan::is_orb_os_version_allowed` (or the backend response it depends on) to return `false`.
2. Drive `do_signup` through `start_signup` and `scan_remaining_qr_codes` with valid QR codes so it reaches the version-allowed check.
3. Assert that `biometric_capture`, `biometric_pipeline`, and `build_pcp` are NOT invoked, and that the returned `SignupResult.success` is `false` immediately after the version check — i.e., assert the call sequence stops at line 525 rather than falling through to line 553 (`biometric_capture`) and beyond.
4. Current code will fail this assertion on `stage` builds, confirming the fall-through bypass.
