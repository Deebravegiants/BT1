I now have enough evidence to build the analog. The mechanism in `HandlerV2.handlePostRequests` and `handleGetResponses` mirrors the DebtManager report exactly: a batch of items is checked against a *snapshot* of on-chain state (`host.requestReceipts(...)` / `host.responseReceipts(...)`), then processed in a loop; if any single item's state changed between snapshot-check and execution (i.e., someone else delivered that one leaf first), the *entire* batch call reverts, and this is compounded by `batchCall`'s atomicity across `handleConsensus` + `handlePostRequests`/`handleGetResponses` in one transaction.

### Title
Griefing DoS via front-run duplicate delivery reverting `HandlerV2.batchCall`/`handlePostRequests`/`handleGetResponses` batches - (File: evm/src/core/HandlerV2.sol)

### Summary
`HandlerV2.handlePostRequests` and `HandlerV2.handleGetResponses` verify a Merkle multi-proof for a batch of leaves and then, in a second loop, dispatch each leaf after checking `host.requestReceipts(...)` / `host.responseReceipts(...)` is still empty [1](#0-0) . Both handler functions are permissionless — "anyone can call them to relay messages" [2](#0-1) . Because the "already delivered" check is re-evaluated per-leaf against live storage rather than against the state that was true when the proof/batch was assembled, any third party can front-run a large in-flight batch by delivering just one of its leaves individually (a cheap, valid, permissionless call), causing the whole multi-leaf `handlePostRequests`/`handleGetResponses` transaction — and, if wrapped, the entire `batchCall` containing a `handleConsensus` + N request/response calls — to revert with `DuplicateMessage()` [3](#0-2) .

### Finding Description
`handlePostRequests` builds `leaves` from `request.requests[i]`, verifies the multiproof against the state-machine commitment, and only afterwards loops a second time to check `host.requestReceipts(leaf.request.hash()) != address(0))`, reverting the *whole call* with `DuplicateMessage()` if any single leaf was already delivered [4](#0-3) . `handleGetResponses` has the identical pattern using `host.responseReceipts(...)` [5](#0-4) .

This is the same class of bug as the reported `DebtManager.manualAllocation` issue: a batched operation is validated/executed against a system state `s` that is snapshotted (via the merkle proof / receipt-emptiness assumption) at build time, but by the time the transaction lands on-chain the state may have transitioned to `s'` for one sub-item, causing a revert that discards work done for *all* other, still-valid sub-items in the batch. Here the "buffer" analog is trivial: delivering a single already-known-valid leaf ahead of the relayer's batch (which is completely free for anyone to do, since delivery is permissionless and proofs for already-finalized commitments are public/derivable) guarantees the victim relayer's larger batch reverts.

The blast radius is amplified by `batchCall`, which is explicitly documented as "Atomic, any failure reverts the entire batch" [6](#0-5) . The relayer/messaging client (`tesseract`) routinely batches a `handleConsensus` call together with N application messages into one `batchCall` for gas efficiency [7](#0-6) , and dispatches through this atomic path whenever the batch has ≥2 messages [8](#0-7) . An attacker who front-runs delivery of just one leaf inside that batch (e.g. one of the requests destined for `BandwidthManager`/`pallet-bandwidth` or an `IntentGateway` settlement message) forces the relayer's entire `batchCall` — including the consensus update and every other unrelated, still-undelivered request/response — to revert.

### Impact Explanation
This is a griefing/DoS vector on message delivery reachable by any unprivileged actor (no special permissions needed to call `handlePostRequests`/`handleGetResponses`/`batchCall`). Repeated front-running can be used to:
- Waste relayer gas on every submission attempt, degrading the economics of self-relay and third-party relaying.
- Delay delivery of time-sensitive cross-chain messages (e.g. `BandwidthPurchaseMsg` credits, `IntentGateway` `RedeemEscrow`/`RefundEscrow` settlement messages) toward their `timeoutTimestamp`, risking `MessageTimedOut()` reverts that can strand escrowed funds or force cancellation/refund flows for orders that would otherwise have settled on time. This makes the destination effectively "a route unable to deliver messages" for the duration of the attack, and can push otherwise-fillable intents into timeout/refund paths against user/solver intent.
- Compound with `batchCall`'s atomicity: a single cheap front-run transaction nullifies a much larger, more expensive relayer transaction bundling consensus + multiple messages.

### Likelihood Explanation
Likelihood is high: the front-running primitive (delivering a single already-provable leaf ahead of a bigger batch) requires no privileged role, no capital at risk beyond gas, and is trivially automatable by watching the public mempool/relayer traffic or simply re-submitting known-valid `handlePostRequests`/`handleGetResponses` calldata for one leaf faster than the original batch. There is a financial/competitive incentive for a rival relayer to do exactly this to force retries and capture relayer-fee credit for messages it deliberately re-orders, mirroring the "financial incentive" framing in the original report.

### Recommendation
Make batch delivery resilient to individual already-delivered leaves instead of reverting the whole call:
- In `handlePostRequests` and `handleGetResponses`, skip (rather than revert on) leaves whose receipt already exists, continuing to dispatch the remaining leaves in the batch, e.g.:
```solidity
for (uint256 i = 0; i < requestsLen; ++i) {
    PostRequestLeaf memory leaf = request.requests[i];
    if (host.requestReceipts(leaf.request.hash()) != address(0)) continue; // already delivered, skip instead of revert
    host.dispatchIncoming(leaf.request, _msgSender());
}
```
- Alternatively, keep the strict `DuplicateMessage()` revert for a single-leaf call, but require relayers/`batchCall` users to pre-filter already-delivered leaves off-chain before proof generation and additionally provide a "best-effort" batch entrypoint that doesn't propagate one leaf's staleness into a full-batch revert.
- For `batchCall`, consider offering a non-atomic variant (or documenting/encouraging relayers to keep `handlePostRequests`/`handleGetResponses` out of the same atomic batch as `handleConsensus` when message counts are large) so a single stale leaf cannot also roll back an otherwise-successful consensus update.

### Proof of Concept
1. Relayer A observes N finalized POST requests destined for the same destination chain and builds a `PostRequestMessage` batch of all N leaves plus their shared multiproof, then wraps `handleConsensus(...)` + `handlePostRequests(...)` into one `batchCall(...)` per `submit_batch_messages` [7](#0-6) .
2. Attacker B observes Relayer A's pending transaction (or independently derives that leaf `k` is already provable) and submits a single-leaf `handlePostRequests` call for leaf `k` alone, with higher gas/priority, so it lands first.
3. Leaf `k`'s receipt is now non-empty (`host.requestReceipts(leaf_k.hash()) != address(0)`).
4. Relayer A's batch transaction executes: the second loop in `handlePostRequests` reaches leaf `k`, evaluates `host.requestReceipts(leaf_k.hash()) != address(0)`, and reverts with `DuplicateMessage()` [1](#0-0) .
5. Because this call was itself one delegatecall inside `batchCall`, the whole `batchCall` reverts per its documented atomic semantics [6](#0-5) , discarding the consensus update and all other N-1 legitimate, undelivered requests, forcing Relayer A to rebuild and resubmit the entire batch (minus leaf `k`) while any short-timeout messages in that batch move closer to `MessageTimedOut()`.

    function handlePostRequests(IHost host, PostRequestMessage calldata request) external notFrozen(host) {
        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(request.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 requestsLen = request.requests.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](requestsLen);

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // check destination
            if (!leaf.request.dest.equals(host.host())) revert InvalidMessageDestination();
            // check time-out
            if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.request.hash());
        }

        bytes32 root = host.stateMachineCommitment(request.proof.height).overlayRoot;
        if (root == bytes32(0)) revert StateCommitmentNotFound();
        bool valid = MerkleMountainRange.VerifyProof(root, request.proof.multiproof, leaves, request.proof.leafCount);
        if (!valid) revert InvalidProof();

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // duplicate request?
            if (host.requestReceipts(leaf.request.hash()) != address(0)) revert DuplicateMessage();
            host.dispatchIncoming(leaf.request, _msgSender());
        }
    }
