### Title
RAY-scaled interest accrual overflows `i128` and permanently freezes a large market - (File: common/src/rates/index.rs)

### Summary
Interest accrual computes total debt and supplied value as `scaled_shares * index`; although the intermediate product uses `I256`, the final value must fit in an `i128`-backed `Ray` and otherwise panics with `MathOverflow`. [1](#0-0) [2](#0-1)  Because every pool mutation synchronizes interest before applying the requested operation, crossing this value boundary makes subsequent `withdraw`, `repay`, liquidation-related settlement, and explicit `update_indexes` calls fail before they can change state. [3](#0-2) [4](#0-3) 

### Finding Description
`Ray::mul` delegates to `mul_div_half_up`, which tries a checked `i128` fast path and then an exact `I256` calculation before converting the result back to `i128`. [5](#0-4) [6](#0-5)  If the exact RAY-scaled value exceeds `i128::MAX`, the conversion returns `None` and the caller raises `GenericError::MathOverflow`. [7](#0-6) [8](#0-7) 

During accrual, `calculate_supplier_rewards` evaluates both `borrowed * old_borrow_index` and `borrowed * new_borrow_index`, while `update_supply_index` evaluates `supplied * old_index`. [9](#0-8) [10](#0-9)  The fixed `MAX_BORROW_INDEX_RAY` ceiling is `10^36`, but it is applied only after the index multiplication; it does not prevent the smaller `i128` total-value ceiling from being reached first. [11](#0-10) [12](#0-11) 

The trigger is reachable through the permissionless controller path `update_indexes(caller, assets)`, which only authorizes the caller and forwards the selected `HubAssetKey` list to the pool. [13](#0-12)  The pool then loads each market and invokes `global_sync`, whose chunked calls to `accrue_step` perform the overflowing value calculations. [14](#0-13) [15](#0-14) 

### Impact Explanation
A sufficiently large RAY-scaled debt or supply balance can make `scaled_shares * index` exceed `i128::MAX` before the configured index ceiling is reached. [12](#0-11) [16](#0-15)  Since synchronization happens before market mutations, the overflow leaves existing suppliers unable to withdraw and borrowers unable to repay through normal controller entrypoints. [3](#0-2) [17](#0-16) 

The existing harness demonstrates the concrete failure mode: repeated `update_indexes` eventually returns `MathOverflow`, the borrow index remains below `MAX_BORROW_INDEX_RAY`, and both withdrawal and repayment fail with the same error. [18](#0-17)  This permanently freezes the market’s token funds absent a privileged contract upgrade or equivalent out-of-band recovery path.

### Likelihood Explanation
The exploit does not require a privileged role at trigger time: an unprivileged caller can build borrowing power through `supply` and `borrow`, then call `update_indexes` once enough ledger time has elapsed. [19](#0-18) [13](#0-12)  The practical precondition is a listed market whose permitted liquidity, caps, collateral pricing, and utilization allow RAY-scaled shares large enough that ordinary index growth reaches the `i128` value boundary; the harness uses a billion-token 18-decimal market at 98% utilization. [20](#0-19)  This severe scale and elapsed-time requirement lowers the likelihood, but the resulting market-wide freeze supports Medium severity.

### Recommendation
Cap indexes dynamically by the value domain before evaluating total debt or supply, for example by clamping the next index to at most `i128::MAX / scaled_shares` rather than relying only on `MAX_BORROW_INDEX_RAY` or `MAX_SUPPLY_INDEX_RAY`. [11](#0-10) [10](#0-9)  Accrual should saturate predictably at that market-specific value ceiling, or store the affected aggregate values in a wider representation, so repayment, withdrawal, liquidation, and recapitalization remain executable. [4](#0-3)  Borrow and supply admission should also reject positions that would make near-term index growth unable to fit the RAY-value domain. [21](#0-20) 

### Proof of Concept
A caller supplies collateral, borrows enough of an existing large market to create the oversized scaled-debt book, advances ledger time, and invokes `update_indexes` for that `HubAssetKey`. [22](#0-21) [13](#0-12) 

```rust

let debt = principal / 100 * 98;

supply(
    attacker,
    0,
    spoke_id,
    vec![(collateral_key, sufficient_collateral)],
);

let borrower_id = /* returned account id */;

borrow(
    attacker,
    borrower_id,
    vec![(big18_key, debt)],
    Some(attacker),
);

loop {
    advance_ledger_time();
    if update_indexes(attacker, vec![big18_key]).is_err() {
        break;
    }
}
```

```rust
/// Computes `x * y / d` rounded half up. Returns `None` if `x < 0`, `y < 0`, `d <= 0`, or the
/// result does not fit in `i128`.
pub fn try_mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> Option<i128> {
    if x < 0 || y < 0 || d <= 0 {
        return None;
    }
    let half = d / 2;

    // Fast path: the biased product fits `i128`, so the whole computation is
    // native. `x * y + half` is non-negative here, so `/` is the floor the
    // widened path would produce.
    if let Some(biased) = x
        .checked_mul(y)
        .and_then(|product| product.checked_add(half))
    {
        return Some(biased / d);
    }

    let (x256, y256, d256) = to_i256_operands(env, x, y, d);
    x256.mul(&y256)
        .add(&I256::from_i128(env, half))
        .div(&d256)
        .to_i128()
```

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}
```
