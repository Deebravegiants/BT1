### Title
Webhook `shop-domain`, `topic`, and `webhook-id` headers are trusted by the handler despite being excluded from HMAC verification, enabling cross-tenant webhook replay - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body [1](#0-0) , so `Utils::HmacValidator.validate` authenticates nothing but the payload bytes. The `shop`, `topic`, and `webhook_id` accessors are read straight from HTTP headers that are never part of the signed string [2](#0-1) . `Registry.process` validates only the HMAC and then forwards these unauthenticated header values into `WebhookMetadata`, which the app-provided handler treats as trusted identity data [3](#0-2) .

### Finding Description
The binding that should hold is: `shop` (and `topic`/`webhook_id`) delivered to the handler == `shop` (and `topic`/`webhook_id`) that Shopify actually signed for that webhook delivery. In this gem, only `raw_body` is covered by the HMAC signature check: `to_signable_string` returns `@raw_body` unconditionally [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are derived from `shopify_header(...)` lookups on the raw HTTP headers with no cryptographic binding to the body or to each other [2](#0-1) .

`Registry.process` performs exactly one check — `Utils::HmacValidator.validate(request)` — before dispatching to the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id)` [4](#0-3) . Since the HMAC only proves "this body was signed with the shared secret at some point," any request carrying a previously-valid `(raw_body, hmac)` pair will pass validation regardless of what `shop-domain`, `topic`, or `webhook-id` headers accompany it in this particular delivery.

This mirrors the report's bug class: a value ("shop"/"topic") is *acted upon* by the handler as if authenticated, but is *not covered* by the HMAC that is meant to establish trust — exactly the identity-binding gap the SEDA `gasPrice` report illustrates (a value used trustingly without validating the property that guarantees its integrity).

### Impact Explanation
An attacker who owns any store that can receive webhooks from the app (e.g., their own development/trial store with the app installed) can capture a legitimate `(raw_body, X-Shopify-Hmac-Sha256)` pair from a webhook Shopify sent them. Because the HMAC is body-only, the attacker can replay that exact body/HMAC to the app's public webhook endpoint while substituting `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) with a victim shop's domain. `HmacValidator.validate` still returns `true` (body unchanged), and the handler receives `WebhookMetadata` claiming the data belongs to the victim shop. Any handler logic that keys off `data.shop` (e.g., looking up that shop's session/access token to act on the payload, writing per-shop records, or deduplicating by `webhook_id`) can be tricked into processing attacker-supplied data under a victim tenant's identity — a cross-tenant data-integrity/access issue.

### Likelihood Explanation
Requires only that the attacker control (or briefly interact with) one shop capable of receiving genuine webhooks from the same app installation — no `api_secret_key`, access token, or privileged access is needed, since replay only requires reusing already-observed header/body pairs against the public webhook endpoint. Actually mounting the attack requires the app's webhook handler to trust `data.shop`/`data.topic` for tenant-sensitive actions, which is the documented and expected usage pattern of `WebhookMetadata`.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable string alongside the body (mirroring how `AuthQuery#to_signable_string` binds `code`, `host`, `shop`, `state`, `timestamp` together [5](#0-4) ), or have `Registry.process`/`WebhookHandler` consumers independently corroborate `shop` against a known/expected tenant (e.g., cross-check against an active session) before trusting it for tenant-scoped operations.

### Proof of Concept
1. App has two installs: attacker's store `attacker.myshopify.com` and victim's store `victim.myshopify.com`.
2. Shopify sends attacker a legitimate webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for `B`), `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker replays to the same webhook endpoint with body `B`, `X-Shopify-Hmac-Sha256: H` unchanged, but `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` [6](#0-5) , which passes because only `B` is signed.
5. Handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` and processes attacker-controlled body `B` as though it originated from the victim's store.
