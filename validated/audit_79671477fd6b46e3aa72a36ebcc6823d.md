### Title
Webhook `shop`/`topic` identity not covered by HMAC verification allows shop/topic confusion in `Webhooks::Registry.process` - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` in `Registry.process` authenticates solely the JSON body bytes. The `shop`, `topic`, and `webhook_id` values used to route and label the event (`request.shop`, `request.topic`, `request.webhook_id`) are read straight from HTTP headers and are never part of the signed material.

### Finding Description
`Request#to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`) returns `@raw_body` only: [1](#0-0) 
Meanwhile `shop`, `topic`, `api_version` and `webhook_id` are pulled from headers with no cryptographic binding to the body: [2](#0-1) 

`Registry.process` verifies the HMAC and then immediately builds `WebhookMetadata` using `request.shop` and `request.topic` taken from those unauthenticated headers: [3](#0-2) 

The identity binding broken is: `HMAC-verified bytes == raw_body` but `shop used by handler != value covered by HMAC`. Any party capable of obtaining one genuine, validly-signed webhook body/HMAC pair from Shopify for their **own** shop (which any merchant who installs the app can trivially do by triggering a webhook event) can replay that exact body+HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header for a different value. `Utils::HmacValidator.validate` will still pass, because it only checks that the body matches the HMAC — it has no knowledge of which shop or topic the signature was originally computed for. Downstream, `Registry.process` calls the registered handler with `shop: request.shop` set to the attacker-chosen value, so the host application's webhook handler processes data as if it originated from a different, potentially cross-tenant shop.

This exactly matches the requested bug class: "a field acted on but not covered by the HMAC" — here, `shop`/`topic` are fields the handler acts on (routing, tenant attribution) while the HMAC covers `raw_body` alone.

### Impact Explanation
This enables cross-tenant confusion: an app's webhook handler (built against `WebhookMetadata#shop`) can be made to believe legitimate, HMAC-verified data belongs to a shop the attacker does not control. Depending on how a consuming app uses `shop` in `WebhookMetadata` (e.g. as a lookup key to fetch/attach a session or write into that shop's tenant record), this can lead to writing or associating attacker-controlled (but otherwise validly signed) data into another tenant's context — a cross-tenant access impact per the accepted-impact list.

### Likelihood Explanation
Requires no possession of `api_secret_key`: the attacker only needs to be able to trigger one real, Shopify-signed webhook delivery for their own installed store (a completely unprivileged app-merchant capability) and be able to POST a modified request (headers) to the target app's public webhook endpoint. This is a realistic, low-effort attack path reachable purely through the gem's own webhook-verification/dispatch logic (`Utils::HmacValidator.validate` + `Registry.process`), not dependent on the host app misusing an undocumented API — the gem itself performs no binding between the verified bytes and the header-derived `shop`/`topic` before handing them to the handler.

### Recommendation
Extend `VerifiableQuery`/HMAC verification for webhooks (or add a separate mandatory check in `Registry.process`) to bind `shop`, `topic`, and `webhook_id` into the signed material or otherwise validate them against an expected/allow-listed value (e.g., require the caller to supply the expected shop and compare it to `request.shop`, or otherwise document to consumers that `shop` from `WebhookMetadata` must not be trusted for tenant attribution). At minimum, document prominently that `request.shop`/`WebhookMetadata#shop` are unauthenticated and must be independently corroborated (e.g., against the shop tied to the merchant's own registered endpoint) before being used for tenant-sensitive operations.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers any subscribed webhook topic (e.g. `orders/create`) — Shopify delivers a body `B` with a valid `X-Shopify-Hmac-Sha256` header `H` computed over `B` using the app's real `api_secret_key`.
2. Attacker captures `B` and `H` and replays them directly to the app's public webhook endpoint, but sets:
   - `X-Shopify-Shop-Domain: victim.myshopify.com`
   - `X-Shopify-Hmac-Sha256: H` (unchanged)
   - `X-Shopify-Topic`: unchanged or altered to a registered topic.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(raw_body) == H`: [4](#0-3) 
4. The handler is invoked with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, even though the actual signed payload `B` was generated for `attacker.myshopify.com`.
