### Title
Excess native ETH/BNB sent to `EvmHost.dispatch`/`fundRequest` is refunded to the Host contract, not the caller, permanently trapping user funds - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest` accept native token payment and swap `msg.value` for `feeToken` via the local Uniswap V2 router, using `address(this)` (the `EvmHost` contract) as both the swap caller and the token recipient. Any unspent native token from the swap (dust ETH) is refunded by the Uniswap router's `swapETHForExactTokens` back to its immediate caller — which is `EvmHost` itself, not the original transaction sender. `EvmHost` never forwards this refund to `_msgSender()`/`post.payer`, so any excess native value a user or integrating `HyperApp` sends is permanently absorbed into the `EvmHost` contract balance.

### Finding Description
In `dispatch(DispatchPost)`: [1](#0-0) 
the call is `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp);`. The same pattern exists in `dispatch(DispatchGet)`: [2](#0-1) 
and in `fundRequest`: [3](#0-2) 

Standard `UniswapV2Router02.swapETHForExactTokens` (and the project's own wrapper implementations, e.g. `UniV3UniswapV2Wrapper.swapETHForExactTokens`, which explicitly documents "if !sent revert; refund dust to msg.sender") refund unused ETH to `msg.sender` of the swap call. Because `EvmHost` itself is the caller of `swapETHForExactTokens{value: msg.value}(...)`, any dust/excess ETH is refunded to `EvmHost`'s own address, not routed back out to the original dispatcher (`_msgSender()` for `dispatch`, or the caller for `fundRequest`). There is no subsequent line in any of these three functions that measures a balance delta and forwards leftover ETH back to the caller — unlike the intents contracts in this same repo (`IntentGatewayV2`, `ExtrinsicIntents`, `IntrinsicIntents`), which explicitly track `msgValue` and call `_sendValue(msg.sender, msgValue)` for any unspent value. `EvmHost` has no equivalent refund step.

The documentation itself confirms user-facing callers are expected to send `msg.value` covering the fee and that the Host "handles the Uniswap swap," implying dust should return to the user, but the code path shows otherwise: [4](#0-3) 

### Impact Explanation
Any unprivileged dispatcher — a `HyperApp` forwarding `msg.value` on behalf of a user, or a direct caller of `IDispatcher(host()).dispatch{value: ...}(...)` / `fundRequest{value: ...}(...)` — permanently loses any ETH sent in excess of the amount required by the Uniswap swap to cover `post.fee`/`get.fee`/`amount`. Because slippage and swap-path pricing are variable and hard for a caller to predict exactly, overpayment is a routine occurrence (as the SDK docs themselves warn: "User must send enough native tokens to cover fees"), so this is not an edge case but a systematic loss vector on every native-token-funded POST, GET, or `fundRequest` call. The lost ETH accumulates in the `EvmHost` contract with no user-facing recovery mechanism visible in this file. This is a permanent freezing/loss of user funds, matching Medium severity per the report analog.

### Likelihood Explanation
High likelihood: this triggers on ordinary usage whenever a caller doesn't send the exact wei amount needed for the fee swap (which is the norm given AMM price movement between quote and execution, per the docs' own fee-estimation guidance). No malicious actor or special preconditions are required — it happens to any well-intentioned integrator or end user who pads `msg.value` for safety margin, which is standard practice explicitly encouraged in the "Estimating Fees" documentation examples.

### Recommendation
In `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, snapshot `address(this).balance` (or the returned `amounts[0]` spent) before/after the `swapETHForExactTokens` call and forward any leftover ETH back to `_msgSender()` (or `post.payer`), mirroring the refund pattern already implemented in `evm/src/apps/IntentGatewayV2.sol` and `evm/src/apps/intentsv2/ExtrinsicIntents.sol`/`IntrinsicIntents.sol` (`_sendValue(msg.sender, msgValue)`).

### Proof of Concept
1. A `HyperApp` calls `IDispatcher(host()).dispatch{value: msg.value}(post)` with `post.fee = X` feeToken units, but the required native input to obtain exactly `X` feeToken via `swapETHForExactTokens` is `Y < msg.value` (e.g., due to conservative client-side fee estimation or price movement between quote and execution).
2. `EvmHost.dispatch` executes `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)`.
3. The router spends `Y` wei and refunds `msg.value - Y` wei to its caller — `EvmHost` — via `TransferHelper.safeTransferETH(msg.sender, msg.value - amounts[0])` (standard Uniswap V2 Router behavior) or the equivalent wrapper refund path.
4. `EvmHost.dispatch` completes and returns `commitment` without ever forwarding the `msg.value - Y` wei back to the original caller; it now sits as part of `EvmHost`'s native balance permanently, with no code path in `EvmHost.sol` observed to return it to that specific caller. [1](#0-0)

### Native Token Payment

For native token payments, dispatch directly and let the Host handle the Uniswap swap:

```solidity lineNumbers title="MyApp.sol"
contract MyApp is HyperApp {
    function sendMessageWithNative(
        bytes memory message,
        bytes memory dest,
        uint64 timeout,
        address to,
        uint256 relayerFee
    ) public payable returns (bytes32) {
        DispatchPost memory post = DispatchPost({
            body: message,
            dest: dest,
            timeout: timeout,
            to: abi.encode(to),
            fee: relayerFee,
            payer: msg.sender
        });
        
        // User must send enough native tokens to cover fees
        // The Host will swap native -> feeToken via Uniswap
        return IDispatcher(host()).dispatch{value: msg.value}(post);
    }
}
```
