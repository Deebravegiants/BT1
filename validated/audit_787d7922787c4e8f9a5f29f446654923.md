# Reachable Arithmetic-Overflow Panic in Pharos Validator-Set Storage-Key Derivation - (File: `modules/consensus/pharos/verifier/src/state_proof.rs`)

## Summary

`bls_data_slots_from_header` in `modules/consensus/pharos/verifier/src/state_proof.rs:639-653` derives a slot count from a fully attacker-controlled 256-bit "string header" value taken from an **unverified** `storage_values` entry, and is invoked from `compute_all_storage_keys` **before any Merkle/state-root proof check runs**. A crafted header value drives an unchecked `usize` addition (`str_len + 31`) to overflow, which panics under the overflow-checked arithmetic Substrate runtimes are typically compiled with — this is the same bug class as CVE-2020-36420 (a malformed length/range field reaching a reachable assertion/panic and crashing execution), except here the trigger is a completely unauthenticated proof structure, not even a valid partial proof.

## Finding Description

`verify_validator_set_proof` (`state_proof.rs:74-94`) processes a submitted `ValidatorSetProof` in this order:

1. `compute_all_storage_keys::<H>(&proof.storage_values, &layout)` — operates on raw, **unverified** `storage_values` [1](#0-0) 
2. `verify_all_storage_proofs(...)` — the actual cryptographic check against `state_root` [2](#0-1) 
3. `decode_validator_set_from_storage(...)` — only reached after (2) succeeds [3](#0-2) 

Inside step 1, `compute_all_storage_keys` calls `bls_data_slots_from_header(&storage_values[idx])` on attacker-supplied bytes with **no proof check having occurred yet**: [4](#0-3)

`bls_data_slots_from_header` is: [5](#0-4) 

```rust
pub fn bls_data_slots_from_header(header_value: &[u8]) -> Result<usize, Error> {
	let header_val = decode_u256_from_storage(header_value)?;
	let header_bytes = header_val.to_big_endian();
	let lowest_byte = header_bytes[31];

	if lowest_byte & 1 == 0 {
		Ok(0)
	} else {
		let length = (header_val - 1) / 2;
		let str_len = length.low_u64() as usize;
		Ok((str_len + 31) / 32)
	}
}
```

`decode_u256_from_storage` only rejects values longer than 32 bytes; any 32-byte (or shorter) value the attacker supplies is accepted as a full-range `U256`. If the attacker sets the low bit (making it "odd"/long-string) and sets the low 64 bits to `0xFFFF_FFFF_FFFF_FFFF` (or otherwise near `usize::MAX`), `str_len` becomes `usize::MAX` (or very close to it) after truncation via `.low_u64() as usize`. The next line, `str_len + 31`, is an unchecked `usize` addition that overflows. Substrate/Polkadot-SDK runtimes conventionally build with `overflow-checks = true` in the runtime profile specifically so integer overflow traps rather than silently wrapping — meaning this overflow panics the WASM execution instead of returning a typed `Error`.

This exactly mirrors the CVE-2020-36420 bug class: a length/range-like field parsed from untrusted, not-yet-authenticated input reaches an unchecked arithmetic operation that trips a reachable panic/trap, rather than the parser rejecting it as a typed error the way the rest of this exact same file guards against elsewhere (`decode_u256_from_storage` rejecting oversized values, `MAX_VALIDATORS` bound, `InsufficientStorageValues`/`InsufficientPoolIds` checks, etc.). Note the *post-verification* twin of this function, `decode_bls_key_from_string_slot` (`state_proof.rs:217-283`), has the identical `str_len + 31` pattern at line 250, but that one only runs after a real proof has been accepted, so it is far less reachable than the pre-verification copy in `bls_data_slots_from_header`.

## Impact Explanation

Any party able to submit a Pharos consensus/validator-set update message (an unsigned, permissionless `handle_unsigned`-style dispatch, consistent with every other consensus client in this codebase — BEEFY, BSC, GRANDPA, sync-committee — which all route unauthenticated proof bytes into their respective verifiers through `ConsensusClient::verify_consensus`) can submit a `ValidatorSetProof` whose `storage_values` contain no valid proof data at all, only a single maliciously-crafted "BLS header" value. This reaches the panic before any cryptographic check, aborting execution of the extrinsic/block. Because this is reachable from a fee-less unsigned transaction that any submitter can broadcast, this is a low-cost, repeatable denial-of-service against the node processing the Pharos consensus-update path — halting message delivery for that light client and, if triggered during block execution/import rather than only mempool validation, risking that specific route becoming unable to deliver messages.

## Likelihood Explanation

High. No valid header rotation, no BLS signature, no actual chain state, and no real Merkle proof are required — only a syntactically valid `ValidatorSetProof` (SCALE-decodable) with a `storage_values[idx]` entry equal to a specific 32-byte value that is odd and whose low 64 bits are large. This is trivial to construct and requires no privileged role, matching the "unprivileged message dispatcher/relayer" reachability bar.

## Recommendation

Use checked/saturating arithmetic in `bls_data_slots_from_header` (and the analogous computation in `decode_bls_key_from_string_slot`), e.g. `str_len.checked_add(31).ok_or(Error::InvalidBlsStringLength)? / 32`, and additionally bound `str_len` to a sane maximum (e.g., reject anything larger than a small constant such as 128 bytes, since BLS public keys are fixed-size ~48-byte values) before it is used in any arithmetic, mirroring the existing `MAX_VALIDATORS` / `InvalidBlsStringLength` guard style already used elsewhere in this file.

## Proof of Concept

1. Construct a `ValidatorSetProof` where:
   - `storage_values[0]` = any value decodable as `totalStake` (e.g., 0).
   - `storage_values[1]` = `1` (declares `count = 1` validator).
   - `storage_values[2]` = any 32-byte pool id.
   - `storage_values[3]` (the validator's BLS header slot) = a 32-byte value that is odd (LSB = 1) and whose low 8 bytes are `0xFF FF FF FF FF FF FF FF` (i.e., `header_val` ≡ a value making `length.low_u64()` close to `u64::MAX`).
   - `storage_proof` = empty/irrelevant (never reached).
2. Submit this as the proof payload of the Pharos consensus update message via the corresponding unsigned dispatch (as with other consensus clients in this codebase, e.g. `Ismp::handle_unsigned` wrapping a `Message::Consensus` routed to the Pharos consensus client).
3. `verify_validator_set_proof` → `compute_all_storage_keys` → `bls_data_slots_from_header` computes `str_len ≈ usize::MAX`, and `str_len + 31` overflows `usize`, panicking the runtime under overflow-checked arithmetic before any cryptographic proof check is performed.
