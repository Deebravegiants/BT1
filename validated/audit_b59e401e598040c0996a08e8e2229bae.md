## Title
Webhook `shop` (and `topic`/`api-version`/`webhook-id`) identity fields are not covered by the HMAC signature, allowing shop-spoofed webhook delivery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` value from an HTTP header, while `to_signable_string` — the value that is actually HMAC-verified — only covers the raw request body. Any attacker who can obtain one validly-signed webhook body/HMAC pair (e.g., by installing the app on their own free development store and receiving a genuine Shopify-signed webhook) can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `shop-domain` header value. The signature check passes, and the handler processes the payload under a different shop's identity.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery` by comparing `hmac` against a signature computed over `to_signable_string`: [1](#0-0) 

For webhooks, `Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

But `Request#shop` (the tenant identity used downstream) is parsed straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never part of the signed material: [3](#0-2) [4](#0-3) 

`Registry.process` validates only the HMAC (i.e. only the body) and then hands `request.shop` straight to the handler as the tenant identifier, with no additional cross-check against the signed content: [5](#0-4) 

This breaks the intended binding: `HMAC(secret, raw_body) == received_hmac` is treated as proof that **all** identity fields of the request (topic, shop, api-version, webhook-id) are authentic, when in fact only `raw_body` is covered. `shop` used by the handler ≠ `shop` bound by the signature.

### Impact Explanation
Because `shop` is not bound to the signature, an attacker who has installed the target app on their own (free/dev) store can capture a genuinely Shopify-signed webhook (valid `raw_body` + `hmac`) sent to their own installation, then resend that exact body/HMAC pair to the app's webhook endpoint with a forged `x-shopify-shop-domain` header pointing at a victim shop (or any arbitrary value). The `HmacValidator.validate` check still passes (it only checks the body), and `Registry.process` will invoke the registered handler with `WebhookMetadata#shop` set to the attacker-chosen value. Any app logic that uses `data.shop` to select per-tenant state, look up sessions/access tokens, or perform tenant-scoped actions can be tricked into acting on/for a shop that never actually sent the event — a cross-tenant confusion primitive.

### Likelihood Explanation
No secrets or privileged access are required. Any unprivileged internet user can create a free Shopify partner/dev store, install the target app, trigger an event to receive one legitimately-signed webhook, and replay it against the public webhook endpoint with a modified shop header. This requires no knowledge of `api_secret_key` and no interception of a victim's credentials — it depends only on the gem's own webhook `Request`/`Registry` verification logic, which is fully in-scope (`lib/shopify_api/webhooks/**`).

### Recommendation
Include `shop`, `topic`, `api-version`, and `webhook-id` in the signable material (or otherwise cryptographically bind them, e.g. by validating that the header-derived shop matches an app-known, previously-registered shop/session before trusting it), so that any header value used to select tenant context is covered by the HMAC rather than treated as authenticated once only the body has been verified. At minimum, document that `WebhookMetadata#shop` is not guaranteed authentic and instruct consumers to cross-check it against their own session store rather than trusting it directly.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and configures a webhook (e.g. `orders/create`).
2. Shopify sends a genuine webhook to the app: `raw_body = B`, header `x-shopify-hmac-sha256 = H` (valid HMAC of `B` with the app's real `api_secret_key`), `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures `(B, H)` and replays a new HTTP POST to the same app webhook endpoint with the same body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `@raw_body` (`Request#to_signable_string`), matches `H`, and passes: [5](#0-4) 
5. The handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)`, even though the body/event actually originated from the attacker's own shop — demonstrating the shop identity is not bound by the signature.

          received_signature = verifiable_query.hmac
