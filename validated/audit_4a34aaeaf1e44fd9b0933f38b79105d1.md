### Title
Unrestricted `CallDispatcher.dispatch` lets anyone drain any ETH balance held by the shared CallDispatcher - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher` accepts arbitrary native ETH via an empty `receive()` and exposes `dispatch(bytes)` as a fully public, unauthenticated entry point that can move out the contract's own ETH balance to any address the caller supplies. This is the same class of bug as the reported `PeripheryPayments.refundETH` issue: a contract that can hold ETH exposes a permissionless function that lets *anyone* claim/move that ETH, with no access control tying the caller to the funds.

### Finding Description
`CallDispatcher.sol` defines: [1](#0-0) 

- `receive() external payable {}` accepts ETH from anyone with no bookkeeping of who sent it.
- `dispatch(bytes memory encoded)` is `external` with no caller restriction (no `onlyOwner`, no check that `msg.sender` is a particular `IntentGatewayV2`/`IntrinsicIntents` instance). It decodes a `Call[]` and, for each entry, executes `to.call{value: call.value}(call.data)` — meaning the caller fully controls `to`, `value`, and `data`, and `value` is drawn directly from `CallDispatcher`'s own balance.

The `CallDispatcher` is used by the Intents apps (`IntentsBase._execute`, `IntentGatewayV2`/`IntrinsicIntents`) to run predispatch/postdispatch calldata during order fills: assets are transferred to the dispatcher, `dispatch()` runs, and residual balances are swept back to the gateway afterward in the same transaction: [2](#0-1) 

Between the moment assets/ETH land on `CallDispatcher` and the moment they are swept back (or in any case where ETH is sent to it directly, e.g. accidental transfers, leftover dust from a reverted/partial external call, or a race within the same block before the sweep-back transaction is mined), the ETH sitting in `CallDispatcher` is claimable by anyone: an attacker simply calls `dispatch()` themselves with a `Call[]` whose `to` is an attacker-controlled contract and whose `value` equals the dispatcher's balance. The only guard in `dispatch()` is that `to` must have code (`extcodesize > 0`), which is trivially satisfied by deploying any contract.

### Impact Explanation
Any native ETH balance that transiently or accidentally resides in `CallDispatcher` — a contract with no owner/access control and a bare `receive()` — is directly stealable by any address. Because `CallDispatcher` is a shared execution helper for the Intents gateways' predispatch/postdispatch calldata (swap-then-escrow and fill-then-act flows), this constitutes concrete theft of funds that were never intended to be held permissionlessly by anyone other than the orchestrating gateway. This matches the severity bar (concrete theft of funds) required for this analog.

### Likelihood Explanation
Likelihood is contingent on ETH actually landing in `CallDispatcher`'s balance outside of an atomic, already-swept transaction (e.g., a user/solver accidentally sending ETH directly to the contract, or leftover value between the external call execution and the subsequent sweep-back call in `IntentsBase._execute`/order fill flow). Given that `CallDispatcher` is `payable` via `receive()` and is a well-known, address-computable contract used across all Intent gateway deployments, an attacker can monitor its balance and opportunistically call `dispatch()` the moment it becomes non-zero. This is a real, reachable vector but depends on the window in which stray ETH is observable in the contract, which I could not fully bound without deeper tracing of every call path that funds `CallDispatcher` (e.g., whether any other test or integration deliberately funds it and leaves residual value across multiple transactions).

### Recommendation
Restrict `CallDispatcher.dispatch` to only the calling gateway/app that funded it for the current call (e.g., require `msg.sender` to be an allow-listed `IntentGatewayV2`/`IntrinsicIntents` instance, or make the dispatcher non-reentrant/single-shot per funding transaction), and/or track owed balances per depositor so `dispatch()` can only spend funds attributable to the immediate caller's own deposit rather than the contract's total balance. At minimum, add a guard so `dispatch()` cannot spend more `value` than was supplied by the current caller in the same call context, closing the window where residual/stray ETH becomes globally claimable.

### Proof of Concept
1. Any account (accidentally or otherwise) sends ETH to `CallDispatcher` via its bare `receive()`, or ETH is left over in `CallDispatcher` between an order's predispatch/postdispatch execution and the sweep-back transaction.
2. An attacker observes `address(CallDispatcher).balance > 0`.
3. Attacker deploys a trivial contract `Sink` with a `receive()`/fallback that accepts ETH.
4. Attacker calls `CallDispatcher.dispatch(abi.encode([Call({to: address(Sink), value: address(CallDispatcher).balance, data: ""})]))`.
5. `dispatch()` executes `to.call{value: call.value}(call.data)` unconditionally since there is no caller check, transferring the entire dispatcher balance to the attacker's `Sink` contract. [3](#0-2)

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
