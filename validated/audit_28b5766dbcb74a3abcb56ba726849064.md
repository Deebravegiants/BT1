### Title
Webhook `shop` Identity Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the value used for HMAC validation from the raw request body only, while the `shop` (tenant) identity that gets handed to the application's webhook handler is read from an HTTP header that is never part of the signed material. An attacker who legitimately controls any Shopify store can capture a genuine, correctly-signed webhook delivery for their own shop and replay it to the same endpoint with a forged `X-Shopify-Shop-Domain` header, causing the host application to process the payload as if it originated from an arbitrary other shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, however, is read straight from the `x-shopify-shop-domain` / `shopify-shop-domain` header, a value that is not fed into the signable string at all: [2](#0-1) 

`Utils::HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` (i.e., the raw body) against the received HMAC, using `Context.api_secret_key`: [3](#0-2) 

`Registry.process` accepts the request purely on that body-only HMAC check, then forwards `request.shop` (the unauthenticated header) straight into the handler: [4](#0-3) 

The equality the gem implicitly claims to enforce is:
`shop delivered to handler == shop that the HMAC signature authenticates`

In reality the code only proves:
`raw_body signed with api_secret_key == raw_body received`

The `shop` value is never part of that equality, so it can be freely substituted by anyone able to submit a request to the webhook endpoint, as long as they can pair it with *some* valid `(body, hmac)` combination.

### Impact Explanation
Any user who operates their own (even a free development) Shopify store is, by Shopify's normal webhook delivery mechanism, given a legitimately signed `(body, hmac)` pair whenever an event fires on their store. Because the header carrying `shop` is outside the signed content, that same unprivileged user can resend the exact body/HMAC pair to the app's public webhook endpoint while substituting `X-Shopify-Shop-Domain` with a victim shop's domain. `Utils::HmacValidator.validate` still returns `true` (the body/HMAC pair is valid), and `Registry.process` dispatches to the handler with `WebhookMetadata` claiming the event came from the victim shop: [5](#0-4) 

Any host application that trusts `WebhookMetadata#shop` to key per-tenant records (billing state, inventory sync, redact/GDPR flows, uninstall bookkeeping, etc.) can be made to apply another merchant's event data to the attacker-chosen tenant, i.e. cross-tenant data corruption/exfiltration triggered purely with attacker-controlled inputs and no knowledge of the app's `client_secret` or any merchant access token.

### Likelihood Explanation
The attack requires no secret material — only signing up for/operating any Shopify store to obtain a valid `(body, hmac)` pair from Shopify's own webhook delivery, and knowledge of the target app's public webhook URL (typically documented/predictable). Forging the header value and replaying the request is trivial with any HTTP client, since nothing in `Request` or `Registry` binds the header-derived `shop` to the signed body.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the material that is authenticated, or otherwise verify the header-derived `shop` against an independently trusted value before handing it to the handler:
- Require host apps / the gem to bind `shop` cryptographically, e.g. by validating that `request.shop` corresponds to a shop with a currently installed/active session before dispatch, or
- Extend `to_signable_string` in `Request` to incorporate the `shop`, `topic`, and `webhook_id` headers so a replayed payload for shop A cannot be relabelled as shop B without invalidating the HMAC.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers any subscribed webhook topic (e.g. updates a product), causing Shopify to POST a legitimately signed webhook to the app's public endpoint with headers:
   ```
   X-Shopify-Topic: products/update
   X-Shopify-Hmac-Sha256: <valid HMAC over body>
   X-Shopify-Shop-Domain: attacker.myshopify.com
   ```
2. Attacker replays the identical body and `X-Shopify-Hmac-Sha256` value to the same endpoint, but changes only:
   ```
   X-Shopify-Shop-Domain: victim.myshopify.com
   ```
3. `Utils::HmacValidator.validate` succeeds because `to_signable_string` only checks the (unchanged) raw body against the (unchanged) HMAC.
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, and any tenant-scoped side effects (data updates, redaction bookkeeping, etc.) are applied under the victim's identity using attacker-supplied body content.
