### Title
StateMachine string encoding/decoding interpretation conflict allows request misrouting via malicious `dest`/`source` bytes - ([File: modules/ismp/core/src/host.rs])

### Summary
`StateMachine`'s `Display`/`FromStr` round-trip is not injective when the embedded raw byte payload (`Substrate`, `Tendermint`, or `Relay.relay` 4-byte identifiers) contains the ASCII `-` delimiter byte. Because the wire-level `dest`/`source` fields of an ISMP `PostRequest` are free-form attacker-supplied bytes that get canonicalized into a delimited string and later re-parsed with `str::split('-')`, an unprivileged dispatcher can craft a `dest`/`source` value that different parsing call sites interpret as different `StateMachine`s — the same class of bug as CVE-2025-13033 (interpretation conflict / CWE-436) where a quoted local-part containing `@` caused SMTP and RFC-compliant parsers to disagree on the recipient.

### Finding Description
`StateMachine::Display` encodes a state machine identifier as a hyphen-delimited string: [1](#0-0) 

For the `Relay` variant it produces `"RELAY-{relay}-{para_id}"`, and for `Substrate`/`Tendermint` it interpolates the raw 4-byte identifier directly as UTF-8 into the string, e.g. `"SUBSTRATE-{4-byte-id}"`.

`StateMachine::FromStr` reverses this by naively splitting on `'-'` and indexing/`.last()`-ing the resulting segments: [2](#0-1) [3](#0-2) 

Nothing prevents the 4-byte `Substrate`/`Tendermint`/`Relay.relay` identifiers from containing the byte `0x2D` (`'-'`) themselves — these are opaque consensus-state identifiers, not validated to be delimiter-free. When such an identifier contains an embedded `-`, `Display` produces a string with *more* hyphen-delimited segments than `FromStr` expects, so `split('-').last()` / `.get(1)` picks the wrong segment. This means the byte sequence that was canonically encoded does not deterministically round-trip: a component reading the raw bytes (e.g. for commitment hashing/equality checks) and a component calling `StateMachine::from_str` on the same string (e.g. for routing/consensus-state selection) can derive **different logical `StateMachine` values** from identical wire data — exactly the "interpretation conflict" bug class in the Nodemailer advisory.

This exact `from_str` path is reached when converting an incoming ABI-encoded ISMP `PostRequest` (as processed by the relayer/handler path from an untrusted relayed message) back into the internal router type: [4](#0-3) 

The `source`/`dest` fields being converted here are raw bytes taken verbatim from the dispatched/relayed request (`value.source`, `value.dest`), which originate from whatever the dispatching application encoded — apps built on `IDispatcher`/`DispatchPost` (such as `HyperFungibleToken.send()`) construct `dest` from caller-controlled `SendParams.dest` bytes, so an unprivileged sender fully controls this payload.

### Impact Explanation
A crafted `dest`/`source` byte string can cause the commitment/raw-byte view of the request to disagree with the `StateMachine` value that routing/validation logic derives from `StateMachine::from_str`. This can result in a request being routed to, or accepted as originating from, a different consensus state/parachain identifier than what its committed bytes represent — an unsound state/route interpretation that can bypass per-chain authorization checks (e.g. peer/source-contract checks keyed on the parsed `StateMachine`) or misdeliver a message to an unintended destination consensus client, undermining `pallet-ismp`/`EvmHost` message routing integrity.

### Likelihood Explanation
Exploitability requires only that an unprivileged application dispatch a `PostRequest` with a crafted 4-byte `Substrate`/`Tendermint`/`Relay` identifier segment containing the `-` byte, which is entirely within a caller's control (no special privileges needed) and low complexity to construct, but the ultimate practical effect depends on how a specific downstream component reasons about the mismatched string versus the raw bytes.

### Recommendation
Make the `StateMachine` string encoding unambiguous and injective: length-prefix or otherwise encode the embedded byte identifiers so that `FromStr` cannot misparse hyphen-containing payloads (e.g., hex-encode the 4-byte ids instead of interpreting them as UTF-8/raw bytes in `Display`, or use a delimiter that is validated to never appear in `Substrate`/`Tendermint`/`Relay.relay` values), and reject registration/encoding of any such identifier containing the delimiter character.

### Proof of Concept
1. Construct `StateMachine::Relay { relay: *b"AB-C", para_id: 1000 }` (relay bytes deliberately include `-`).
2. `Display` renders this as `"RELAY-AB-C-1000"`.
3. Feed this string into `FromStr::from_str`: `values = ["RELAY","AB","C","1000"]`; `values.get(1)` yields `"AB"` (not 4 bytes) causing failure, or with a different 4-byte payload chosen so `values.get(1)` happens to be 4 bytes, a completely different `relay`/`para_id` pair than originally encoded is reconstructed.
4. Route this crafted string through `TryFrom<PostRequest> for router::PostRequest` (`modules/ismp/core/src/abi.rs:92-111`) as an incoming request's `dest`, demonstrating that the parsed `StateMachine` diverges from the raw bytes originally committed to.
