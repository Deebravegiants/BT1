### Title
Pausing `HyperFungibleToken`/`WrappedHyperFungibleToken` blocks timeout refunds, permanently freezing user funds mid-transfer - (File: `sdk/packages/core/contracts/apps/HyperFungibleToken.sol`)

### Summary
`HyperFungibleToken`, `HyperFungibleTokenUpgradeable`, `WrappedHyperFungibleToken`, and `WrappedHyperFungibleTokenUpgradeable` all guard `onPostRequestTimeout()` — the sole recovery path that refunds a sender when their outbound cross-chain transfer fails to be delivered — with the same `whenNotPaused` modifier used on `send()` and `onAccept()`. This mirrors the reported Tapioca `BigBang`/`Singularity` finding, where `notPaused` was applied indiscriminately to `repay()` and `liquidate()`, blocking exactly the functions needed to de-risk the system during an emergency instead of only blocking new risk-taking actions (`borrow()`).

### Finding Description
`send()` burns (or locks, for the wrapped variant) the user's tokens on the source chain and dispatches a POST request cross-chain: [1](#0-0) 

If that request is never delivered before its timeout, the *only* mechanism to make the user whole is `onPostRequestTimeout()`, which re-mints the burned tokens back to the original sender: [2](#0-1) 

Both `send()` and `onPostRequestTimeout()` share the exact same `whenNotPaused` gate; there is no separate, always-available recovery path analogous to allowing `repay()`/`liquidate()` while blocking `borrow()`. The same pattern is repeated in the upgradeable and wrapped variants: [3](#0-2) [4](#0-3) 

At the host level, when the timeout callback reverts (which it will while paused, since `whenNotPaused` reverts), `EvmHost.dispatchTimeOut` preserves the commitment for a retry rather than deleting it and refunding the relayer fee: [5](#0-4) 

So while the request itself is not lost, the user's already-burned/locked principal cannot be recovered — and relayers who submit the timeout proof are not paid — for as long as the token contract stays paused. The docs and tests confirm this is intentional/expected current behavior, not an incidental gap: [6](#0-5) [7](#0-6) 

The pause is owner-triggered ("emergency situations or during migrations"), and is exactly the scenario in which users are most likely to need their locked-in-flight funds returned (e.g., a detected bug in the bridge, a compromised peer contract, or an ongoing exploit). By gating the refund path behind the same switch that halts everything else, the contract removes the one function that mitigates harm during an incident — paralleling the Tapioca finding where pausing removed exactly the de-risking tools (`repay`/`liquidate`) needed during a crisis.

### Impact Explanation
Any user whose `send()` transaction is in flight (dispatched but not yet delivered/timed out) when the owner pauses the contract cannot reclaim their burned/locked tokens via `onPostRequestTimeout()` until the contract is unpaused. If the pause is prolonged (e.g., because the very incident that triggered the pause takes time to resolve, or governance/owner key issues delay unpausing), those funds are frozen for that entire duration — a "temporary but indefinite" freezing of user funds that, in the worst case (owner key loss, prolonged incident response, or a pause that is never lifted because the underlying issue can't be fixed), becomes a permanent freeze. This directly matches the accepted "permanent freezing of funds" impact category, since the *only* return path (`onPostRequestTimeout` mint-back) is disabled precisely when it is most needed.

### Likelihood Explanation
The owner can call `pause()` unilaterally at any time; no special conditions are required to reach the vulnerable state, and it is realistic for a pause to be exercised specifically in reaction to a security incident (the scenario the pause is meant for), which is also the scenario where fast, unblocked refunds matter most. Any user with a pending, not-yet-timed-out or already-timed-out-but-unprocessed transfer at that moment is directly affected.

### Recommendation
Do not gate the refund/recovery path with the same pause switch used for new outbound sends and inbound mints. Specifically, remove `whenNotPaused` from `onPostRequestTimeout()` (and the analogous timeout handler in the wrapped variants), so that pausing only blocks new `send()`/`onAccept()` activity while still allowing already-initiated transfers to be safely refunded to their original senders. If a stricter emergency stop is genuinely required (e.g., suspicion that the mint-back logic itself is compromised), gate it with a distinct, separately-controlled circuit breaker rather than reusing the general `Pausable` state.

### Proof of Concept
1. User calls `send()` on `HyperFungibleToken`, burning `amount` tokens and dispatching a POST request with a `timeout` of, say, 3600 seconds. [1](#0-0) 
2. Before the message is delivered, the owner calls `pause()` in response to an incident. [8](#0-7) 
3. The request times out. A relayer submits the timeout proof through `EvmHost`, which invokes `onPostRequestTimeout` on the token contract. [9](#0-8) 
4. `onPostRequestTimeout` reverts due to `whenNotPaused`, so the mint-back to the user never happens; `EvmHost` re-stores the commitment for a future retry and does not refund the relayer fee. [2](#0-1) 
5. The user's burned tokens remain unrecoverable for the entire duration the contract stays paused — the exact freezing-of-funds pattern described in the referenced Tapioca finding, where pausing blocked the loss-mitigating function instead of only the risk-increasing one.

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({from: message.from, to: beneficiary, source: string(request.source), amount: message.amount});
    }

    function dispatchTimeOut(
        PostRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onPostRequestTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit PostRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }
```

## Pausability

Both contracts inherit from OpenZeppelin's `Pausable`. The owner can pause and unpause all operations:

```solidity lineNumbers
IHyperFungibleToken(tokenAddress).pause();
IHyperFungibleToken(tokenAddress).unpause();
```

When paused, `HyperFungibleToken` blocks all ERC20 transfers (`transfer` and `transferFrom`) in addition to cross-chain `send()` and `onAccept()`. This is a full stop on all token movement — use it for emergency situations or during migrations.
