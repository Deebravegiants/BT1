### Title
Unrestricted strategy routes let malicious venues attach caller-funded token transfers to a signed authorization tree - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
Medium. Strategy swaps accept an opaque, caller-controlled route and execute it through the configured router without constraining which venue or token contracts may run beneath the caller’s authorization. [1](#0-0)  A malicious venue can therefore request an unrelated token transfer from the caller during `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, or `multiply`; if the simulated authorization tree is signed, the unrelated assets are transferred even though the lending strategy itself remains solvent. [2](#0-1) 

### Finding Description
`swap_collateral` authenticates `caller` and verifies that the caller owns or delegates the account, then forwards the caller-supplied `swap` payload into the strategy execution path. [3](#0-2)  `swap_tokens` loads only the configured router address, invokes `execute_strategy(&controller, &amount_in, swap)`, and does not inspect or allowlist the venue addresses encoded inside the opaque route. [1](#0-0) 

The controller grants the router one exact transfer authorization for controller-held input and subsequently validates only the controller’s input spend and positive output-delta. [4](#0-3)  That authorization protects the routed controller balance, but it does not bound other contract calls that request `caller.require_auth()` deeper in the route. [5](#0-4) 

Soroban simulation records such a nested caller-authenticated call as a child of the top-level strategy invocation; the repository’s rogue-hop test demonstrates that a venue can add `token.transfer(victim, attacker, amount)` beneath `swap_collateral`, and that signing the returned tree makes the transfer succeed. [6](#0-5) 

### Impact Explanation
A malicious route can steal wallet assets unrelated to the collateral being swapped, including assets not listed by the protocol. [2](#0-1)  The venue can simultaneously provide a small amount of the requested output asset so `verify_router_output` and the final account-risk checks still pass. [7](#0-6)  This is theft of user funds rather than a bad-trade loss: the stolen amount is outside the measured input, output, slippage, and lending-position accounting. [8](#0-7) 

### Likelihood Explanation
Exploitation does not require an administrator key, oracle manipulation, or control of the configured router; the attacker only needs an unallowlisted route hop compatible with the router ABI. [1](#0-0)  It does require the victim to execute an attacker-supplied route and sign the authorization tree containing the additional transfer, so exploitation depends on route delivery and how clearly the wallet or SDK displays nested authorization entries. [9](#0-8) 

### Recommendation
Restrict strategy routes to governance-approved venue/token contracts instead of accepting arbitrary encoded hop addresses, and reject dynamically supplied venue contracts in the router. [1](#0-0)  Clients should simulate and enforce the exact expected authorization tree for each strategy: for `swap_collateral`, reject any unexpected caller child invocation before signing; where an initial payment is legitimate, compare the child contract, function, recipient, and amount exactly. [10](#0-9)  Add regression tests asserting that an arbitrary venue cannot append token, NFT, or controller calls requiring the caller’s authorization. [6](#0-5) 

### Proof of Concept
1. The attacker deploys a contract that conforms to a route-hop ABI accepted by the configured router and supplies a route containing that contract as a hop. [1](#0-0) 
2. The victim calls `Controller::swap_collateral(caller = victim, account_id = victim_account, current = X, amount = amount_x, new = Y, swap = attacker_route)`, where the victim also owns unrelated token `T`. [11](#0-10) 
3. The controller authenticates the victim, withdraws `X` into controller custody, and invokes the router with `attacker_route`. [3](#0-2) 
4. During route execution, the malicious venue calls `T.transfer(victim, attacker, balance_t)`; simulation records that transfer as a child invocation under the victim’s `swap_collateral` authorization. [2](#0-1) 
5. The victim signs the poisoned tree; the venue sends a positive amount of `Y` to the controller, so input/output measurements and final risk checks pass while `balance_t` is transferred to the attacker. [4](#0-3)

fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);
    assert_eq!(s.t.supply_balance_raw(ALICE, "USDC"), usdc_before);

    // Same route, with the tree that simulation returned.
    let stolen_transfer = MockAuthInvoke {
        contract: &s.wallet_token,
        fn_name: "transfer",
        args: (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        sub_invokes: &[],
    };
    s.try_swap_with_signed_tree(&rogue, core::slice::from_ref(&stolen_transfer))
        .expect("the poisoned tree authorizes the rogue transfer");
    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
}

/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
}
