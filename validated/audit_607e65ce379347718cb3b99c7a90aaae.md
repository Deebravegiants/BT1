### Title
Unchecked i128 value growth in interest accrual permanently freezes a market - (File: common/src/rates/simulate.rs)

### Summary
CVE-2017-12864 is an integer overflow caused by arithmetic on an input whose length was never bounded. The analog in XOXNO Lending is `accrue_step` (`common/src/rates/simulate.rs:51-94`), which computes `scaled_to_original(env, borrowed, borrow_index)` — i.e. `borrowed * borrow_index / RAY` — via `mul_div_half_up`/`mul_div` primitives that panic with `GenericError::MathOverflow` when the product does not fit `i128`. Neither `borrowed` (scaled debt shares) nor `borrow_index` growth is bounded against that product ceiling before the multiply runs, and the borrow-index cap `MAX_BORROW_INDEX_RAY` engages only *after* the multiplication, so the value ceiling is reached first. Because `interest::global_sync` (`contracts/pool/src/interest.rs:20-33`) runs `accrue_step` before every market mutation, once the product exceeds `i128::MAX` every entrypoint on that market — supply, borrow, repay, withdraw, seize/liquidate, `update_indexes` — reverts permanently.

### Finding Description
`simulate.rs::accrue_step` first materializes the debt and supply values with `scaled_to_original` at lines 60-61, and the borrow index itself is updated by `update_borrow_index` at line 66 — both are `x * y / RAY` computations over values that are attacker-influenced (total debt principal via `borrow`, index growth via elapsed time and the rate curve). The pool-side driver `contracts/pool/src/interest.rs::accrue_chunk` invokes this for every chunk up to `MAX_COMPOUND_DELTA_MS` and it is unconditionally invoked by `global_sync` whenever `elapsed_ms() > 0` (`contracts/pool/src/cache/mod.rs:134-141`). The overflow is therefore not a per-call input problem: it is accumulated in committed state (`borrowed` shares, `borrow_index`), so no later call can route around it. The in-repo test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361`) demonstrates this exact sequence end-to-end: `update_indexes`, `withdraw`, and `repay` all revert with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY`, i.e. the index cap never protects the multiplication. `docs/reference/invariants.md` (INV-IDX-01) concedes "Debt-value overflow can still revert accrual before that ceiling is reached" — the bound exists, the enforcement does not.

### Impact Explanation
Permanent freezing of funds and protocol insolvency on the affected market. Once `borrowed * borrow_index` exceeds `i128::MAX`: suppliers can never withdraw (every withdrawal accrues first), borrowers can never repay, liquidators cannot clean positions, and `clean_bad_debt`/`recapitalize` paths that touch the market also accrue first. All cash held by the pool for that market is locked forever. This is reachable entirely through unprivileged entrypoints: `supply`/`borrow` build the position and the permissionless `update_indexes` (or any verb) triggers the panic.

### Likelihood Explanation
The trigger requires a very large market — on the order of ~10^38 ray-value of outstanding debt, e.g. a billion-scale 18-decimal token borrowed to ~98% utilization on a steep rate curve, sustained for multiple years. The domain ceiling is `i128::MAX / 10^(27-decimals)` units per `Ray::from_asset`, so the attacker must genuinely supply/borrow at near the representable maximum; the XLM-curve test reaches the cliff purely through normal supply + borrow + time with caps lifted to `max_cap_for_decimals` (a governance-set cap at the representable maximum). It is capital-intensive but requires no privilege, no oracle manipulation, and no code flaw other than the missing bound — consistent with Medium/High likelihood at the upper end of market scale.

### Recommendation
Bound the product before multiplying: in `accrue_step`/`update_borrow_index`, clamp `borrow_index` growth (or short-circuit accrual) when `borrowed * borrow_index / RAY` would exceed `i128::MAX`, so the index effectively stops accruing instead of reverting — the same graceful-cap semantics the code already applies at `MAX_BORROW_INDEX_RAY`. Alternatively, cap `supplied`/`borrowed` share totals at `i128::MAX / MAX_BORROW_INDEX_RAY` so the product is representable by construction, keeping `scaled_to_original` total.

### Proof of Concept
Pinned by `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361`:

```rust
let principal = BILLION * 10i128.pow(18);          // whale-scale 18-dec market
t.supply_raw(BOB, "BIG18", principal);
t.borrow_raw(ALICE, "BIG18", principal / 100 * 98); // ~98% utilization
loop {
    t.advance_time(YEAR_SECS);
    if let Err(e) = t.try_update_indexes_for(&["BIG18"]) { break e; }
}
// MATH_OVERFLOW; index cap never engaged
assert!(last.borrow_index < MAX_BORROW_INDEX_RAY);
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

Every subsequent verb reverts inside `scaled_to_original` during `global_sync`, leaving supplier principal and all market cash permanently frozen.
