### Title
Webhook Cross-Tenant Spoofing via Unsigned `shop-domain` Header — (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are trusted and forwarded to the handler unauthenticated. Because a single app-wide `client_secret` is used to sign webhooks for every shop that installs the app, any merchant who installs the app on their own store can capture a genuinely Shopify-signed webhook body and replay it against the app's webhook endpoint with a forged `shop-domain` header, causing the app to attribute attacker-controlled data to a victim tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` verifies exactly that signable string (the body) against the HMAC header, and nothing else: [2](#0-1) 

`Registry.process` only calls `HmacValidator.validate(request)` and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build `WebhookMetadata` passed to the handler: [3](#0-2) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are pulled straight from HTTP headers with no cryptographic binding to the HMAC-verified body: [4](#0-3) 

The identity binding that is broken is:
`shop-domain header used by the handler` == `shop domain that the HMAC-signed bytes were actually generated for`

Since Shopify signs webhooks for *every* installed shop using the *same* app `client_secret`, a merchant who installs the public app on their own shop legitimately receives a body+HMAC pair that is valid for the app's secret, but that pair carries no information tying it to that specific shop — the shop identity travels only in an unsigned header. That attacker-controlled merchant can therefore submit that valid (body, hmac) pair to the app's webhook endpoint while substituting a different `shop-domain` header value (e.g., a victim shop that also has the app installed), and `Registry.process` will accept it and hand the attacker's body to the handler tagged with the victim's `shop`.

### Impact Explanation
This is a cross-tenant confusion vulnerability: an app that keys any state (order records, customer records, entitlements, sync triggers, etc.) off `WebhookMetadata#shop` can be made to apply attacker-controlled webhook payloads to a victim tenant's data, without the attacker ever needing to leak or possess the `client_secret`. This matches the Critical "cross-tenant access" impact category, since it lets one tenant (an unprivileged installer of the app) inject data attributed to another tenant purely by exploiting this gem's failure to bind the `shop` header to the HMAC-covered bytes.

### Likelihood Explanation
Likelihood is realistic for any app that is publicly installable: obtaining a valid (body, HMAC) pair only requires installing the app on an attacker-controlled shop and triggering an event (e.g., `orders/create`) that the app subscribes to — no secret material needs to be exfiltrated. The only additional step is replaying that captured HTTP request with a modified `shop-domain` header directly at the app's public webhook endpoint.

### Recommendation
Bind the identity fields to the signed bytes rather than trusting bare headers: either (a) include `shop-domain`, `topic`, and `webhook-id` in the HMAC-signable string alongside the body, or (b) after HMAC validation, independently re-derive/verify the shop from a source that is itself cryptographically tied to the request (e.g., cross-check against the shop associated with the currently registered webhook subscription/session, not the header value alone).

### Proof of Concept
1. Install the target app (any public app accepting installs) on attacker-controlled shop `attacker.myshopify.com`.
2. Trigger a subscribed webhook topic (e.g., create an order) so Shopify sends a legitimately-signed webhook: body `B` with header `X-Shopify-Hmac-Sha256: H` (valid, since Shopify signs with the app's shared `client_secret`) and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Capture this request, then replay it to the app's webhook endpoint, keeping `body=B` and `hmac=H` unchanged but setting `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` (which only checks `B` against `H`) passes, and `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: B, ...)`, causing the app to process attacker-chosen data under the victim's tenant identity. [5](#0-4)
