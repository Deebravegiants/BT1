## Analysis

The Hats/Velvet-Capital report describes a class of bug where a **cryptographic authorization artifact (a signature/permit) is not bound to who may submit/execute it**, so a third party can observe it in the mempool and front-run its consumption, invalidating an intended batched/sequenced flow and DoS-ing or wasting the gas of the legitimate party.

NEAR has no ERC20-style `permit()`, but it has a structurally identical primitive: **`DelegateAction`/`SignedDelegateAction`** (NEP-366 meta-transactions), where a user signs an action off-chain and a **relayer** wraps and submits it, paying gas on the user's behalf. Crucially, the signed payload is not bound to a specific relayer, and nonce validation jumps the access key's nonce directly to whatever value was consumed rather than incrementing by one — this reproduces the exact "front-run + skip-ahead invalidates queued items" pattern from the report.

### Title
Meta-transaction (`DelegateAction`) nonce validation lets any observer front-run and invalidate a user's queued, unrelayed delegate actions - (File: `runtime/runtime/src/actions.rs`)

### Summary
`validate_delegate_action_key` accepts any `DelegateAction` whose `nonce` is strictly greater than the signer's current access-key (or gas-key) nonce, and on success sets the access key's nonce directly to that submitted value rather than incrementing it by one. Because a `SignedDelegateAction` is not cryptographically bound to a specific relayer/predecessor, anyone who observes it (e.g., in the public mempool while the intended relayer's transaction is pending) can extract it and resubmit it themselves in their own transaction ahead of the intended flow, or use it to jump the sender's nonce forward and thereby invalidate any lower-nonce delegate actions the sender has queued for later relaying.

### Finding Description
`DelegateAction` includes a `nonce` field described as ensuring "the same delegate action is not sent twice by a relayer" and that it "should match for given account's public_key. After this action is processed it will increment." [1](#0-0) 

The runtime enforces this with a simple "greater-than-current" check, not a strict `+1` sequential check, and sets the stored nonce directly to the just-validated value: [2](#0-1) [3](#0-2) 

Critically, nothing in this validation ties the `DelegateAction` to the relayer that is supposed to submit it — the design explicitly notes: "All actions inside `delegate_action.actions` are submitted with the `delegate_action.sender_id` as the predecessor... and the relayer (predecessor of `DelegateAction`) as the signer," but the relayer identity is whoever happens to wrap and submit the transaction, not a party bound into the signed payload. [4](#0-3) 

Because a transaction may carry only a single `DelegateAction`, any workflow that needs to relay multiple sequenced actions signed by the same access key (the meta-tx analog of "batched permits") must submit them as separate transactions with increasing nonces: [5](#0-4) 

An attacker who sees one of these signed, not-yet-included delegate actions in the mempool (transactions are gossiped before inclusion) can extract its bytes and submit it themselves via a transaction of their own, before the legitimate relayer's transaction for an earlier-nonced delegate action lands. Since the nonce is jumped directly to the submitted value rather than incremented by one, this single front-run action invalidates *every* other pending delegate action signed by that key with a lower nonce — they will all fail the `delegate_nonce.nonce() <= current_nonce` check and revert with `DelegateActionInvalidNonce` once processed. [6](#0-5) 

This is the exact structural analog of the reported issue: a signature/authorization not bound to its intended executor, exposed in a public mempool prior to inclusion, that can be front-run to force reverts on a batch of related, sequentially-nonced items — wasting the legitimate relayer's/user's gas and blocking their intended state transitions.

### Impact Explanation
A malicious actor can grief a relayer or user by:
- Watching the mempool for a `SignedDelegateAction`.
- Extracting and resubmitting it (or a higher-nonce sibling from the same batch) via their own transaction ahead of the legitimate relayer.
- Causing the intended relayer's transaction(s) with lower nonces to fail on execution, wasting relayer-paid gas (since gas costs for delegate actions are paid by the relayer/outer signer) and blocking the user's intended meta-transaction(s) from executing as designed.

This is a griefing / gas-wasting / availability impact on the meta-transaction relaying flow rather than a fund-theft bug, consistent in severity with the original Medium-severity report (unrelated to permit funds theft — it's a deposit/flow DoS).

### Likelihood Explanation
Requires only observing the public mempool/network for a `SignedDelegateAction` and submitting a transaction with better propagation/priority — no special privileges, validator status, or trusted role needed. Any relayer-based application that queues multiple sequential delegate actions for the same access key (a natural pattern for batching meta-transactions, mirroring the "batched permits" scenario in the report) is exposed.

### Recommendation
Consider one or more of:
- Requiring strict sequential nonce validation (`NonceMode::Strict`, already implemented for regular transactions) to be usable for `DelegateAction`/`DelegateActionV2` as well, so a single front-run cannot "skip ahead" and invalidate multiple queued lower-nonce actions at once. [7](#0-6) 
- Documenting/enforcing that relayers should not pre-sign or broadcast batches of delegate actions with far-future nonces without accounting for this front-run/skip-ahead risk, and re-checking on-chain nonce state immediately before submission to avoid wasted gas.

### Proof of Concept
1. Alice signs `DelegateAction`s with nonces `n+1 .. n+5` against her access key (current nonce `n`), intending relayer R to submit them one per transaction, in order.
2. Attacker M observes the `n+5` delegate action (e.g., from R's broadcast transaction while pending, or from any channel where these signed payloads are shared ahead of submission) and submits it himself in his own transaction, which lands first.
3. `validate_delegate_action_key` accepts nonce `n+5 > n` and sets `access_key.nonce = n+5` directly. [8](#0-7) 
4. R's transactions carrying nonces `n+1..n+4` now fail `delegate_nonce.nonce() <= current_nonce` (since `current_nonce` is now `n+5`), reverting with `DelegateActionInvalidNonce` and wasting R's attached gas. [2](#0-1)
