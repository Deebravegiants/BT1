This confirms the vulnerability: the `shop` field is passed to the handler (`WebhookMetadata.new(... shop: request.shop ...)`) but `Request#to_signable_string` only returns `@raw_body` — the `shop-domain`, `topic`, `api-version`, and `webhook-id` headers are never part of the HMAC-signed payload.This confirms the full picture — `Registry.process` explicitly documents itself as verifying "the request did indeed come from Shopify" (`docs/usage/webhooks.md:125`), yet the `shop` field it hands to the handler is taken from an unauthenticated header, not from the signed payload.

### Title
Cross-Tenant Webhook Spoofing via Unsigned `shop-domain` Header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's HMAC before dispatching it to the app's handler, but the HMAC only covers the raw request body. The `shop-domain` header — which is passed to the handler as the authoritative tenant identifier — is never included in the signed bytes. An attacker who can obtain any one genuinely-signed webhook payload for the shared app secret (e.g. by installing the app on their own shop, a normal unprivileged action) can replay that exact body with a forged `shop-domain` header for a victim shop, and the gem will report it as valid and hand the handler `shop: <victim-shop>`.

### Finding Description
`Utils::HmacValidator.validate` computes/verifies the HMAC using `verifiable_query.to_signable_string` and the app's secret: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw body: [2](#0-1) 

But `shop` (along with `topic`, `api_version`, `webhook_id`) is read from an HTTP header that is completely outside this signed string: [3](#0-2) 

`Registry.process` validates the HMAC over the body only, then forwards the *header-derived* `request.shop` straight to the app's handler as the trusted tenant identifier: [4](#0-3) 

The equality the code implicitly assumes is:
`shop authenticated by HMAC == shop delivered to handler`

But in reality: `bytes verified by HMAC (raw_body only) != bytes read for shop (shop-domain header)`. Since the header is not bound into the signature, any two values can be paired: a body whose HMAC is valid for the app's secret, together with an arbitrary `shop-domain` header value.

The gem's own documentation reinforces that host apps are meant to treat `Registry.process` as verifying provenance end-to-end ("This will verify the request did indeed come from Shopify"), and the example handler in the docs uses `data.shop` directly as the tenant key for enqueuing follow-up work: [5](#0-4) [6](#0-5) 

### Impact Explanation
This is a cross-tenant access primitive: the `shop` value delivered to the app's business logic is unauthenticated even though the gem asserts the whole request "did indeed come from Shopify." Because the app's `client_secret`/webhook secret is shared across all shops that install the app, any attacker who can install the app on a shop they control can legitimately receive HMAC-valid webhook bodies, then replay them against the app's webhook endpoint with a different `shop-domain` header, causing the app to process (and potentially trigger downstream side effects, cache poisoning, or state updates) attributed to a victim shop it does not control.

### Likelihood Explanation
Any developer can install a Shopify app on a shop they own (unprivileged, no special credentials needed beyond a normal storefront/dev account), capture one real webhook delivery for a subscribed topic, and then replay the raw body to the app's public webhook route with a modified `shop-domain` header (and, if the topic-derived data isn't checked against topic header either, `topic`/`webhook_id` too). No access token, API secret, or privileged account is required — only network access to the app's own webhook endpoint.

### Recommendation
Bind the `shop`, `topic`, `api_version`, and `webhook_id` values into the HMAC-verified material — e.g., include the header values that will be trusted downstream in `to_signable_string`, or independently cross-check the header-derived shop against a shop value embedded in the (currently opaque) JSON body before constructing `WebhookMetadata`. At minimum, document clearly that `request.shop` is not covered by the HMAC and must not be trusted as an authenticated tenant identifier without additional verification (e.g., comparing it against a shop already known/stored for the given `webhook_id`/topic subscription).
