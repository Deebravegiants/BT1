Audit Report

## Title
Gateway HTTP Action leaks detailed SSRF-block reasons (scheme/port/IP) to the requesting workflow - ([File: core/services/gateway/network/httpclient.go])

## Summary
The gateway's HTTP action capability differentiates outbound request failures into blocked-scheme, blocked-port, blocked-IP, disabled-redirect, and live-network-error categories via `isBlockedRequest`, and forwards the underlying, only partially-sanitized error text verbatim as `OutboundHTTPResponse.ErrorMessage` to the workflow that issued the request. A workflow author who fully controls the `URL` field of an `OutboundHTTPRequest` can use these differentiated messages as an oracle to enumerate which internal hosts/ports are allowlist-blocked versus actually reachable/dialed from the gateway's network.

## Finding Description
`httpClient.Send` classifies every failed outbound request with `isBlockedRequest`, which uses `errors.As` to detect `safeurl.AllowedPortError`, `safeurl.AllowedSchemeError`, `safeurl.AllowedIPError`, `safeurl.InvalidHostError`, `safeurl.IPv6BlockedError`, and the local `redirectsDisabledError` type [3](#0-2) . When blocked, the error is wrapped as `fmt.Errorf("%w: %w", ErrBlockedRequest, truncatedErr)`, where `truncateLogError` only rewrites the `*url.Error.URL` field to `scheme://host` but leaves the wrapped `Err` (the original safeurl error, e.g. `"port: 8080 not found in allowlist"`, `"ip: 169.254.0.1 not found in allowlist"`, `"scheme: file not found in allowlist"`) intact [2](#0-1) [5](#0-4) . Test expectations in `httpclient_test.go` corroborate these exact distinguishing message formats.

This detailed error is propagated with no redaction into the capability response: `createHTTPRequestCallback` sets `ErrorMessage: err.Error()` for every failure branch, only varying the `IsExternalEndpointError`/`IsValidationError` booleans and log level based on the error class [1](#0-0) . The response is then dispatched back to the requesting node asynchronously in `makeOutgoingRequest` via `sendResponseToNode`, ultimately reaching the workflow that issued the HTTP action call [4](#0-3) .

Existing authorization (`AllowListBasedAuth.AuthorizeRequest`) only verifies that the outbound request digest was pre-authorized by the workflow owner on-chain; it does not restrict or sanitize the semantic content of the `URL` field a workflow can specify, nor does it apply any masking to the returned error text. There is no generic/uniform error substitution analogous to the `internalErrorMessage` pattern used elsewhere in this package for the blocked-request path.

## Impact Explanation
This is an information-disclosure / SSRF-oracle issue rather than a direct authentication bypass or fund-movement bug. A workflow author (who only needs the ability to register and submit a normal workflow through the CRE workflow registry/gateway — not node-operator or admin access) can supply arbitrary URLs in `OutboundHTTPRequest.URL` and use the differentiated `ErrorMessage` text to distinguish "blocked by scheme/port/IP allowlist" from "reachable and attempted" (network error/timeout), enabling systematic enumeration of the gateway node's internal network topology (live internal hosts, open ports, allowlist boundaries) without any independent network access. This maps to an information-disclosure impact consistent with CWE-203/SSRF-oracle class issues, mirroring the cited Gitea CVE-2021-45325 pattern.

## Likelihood Explanation
Any workflow able to invoke the HTTP action capability with an attacker-controlled `URL` can trigger this on every request; the classification and echoing logic execute unconditionally for all outbound requests, so exploitation is repeatable and requires no elevated privilege beyond normal workflow authorship/submission.

## Recommendation
Return a single generic error string (e.g., "request blocked" or a shared `internalErrorMessage`-style constant already used elsewhere in this package) for all `ErrBlockedRequest` cases in `createHTTPRequestCallback`'s `ErrorMessage` field, while retaining the detailed `truncateLogError` output only in server-side `Warnw`/`Errorw` logs and metrics. Consider also collapsing the distinction visible between blocked and live-network failures (`ErrHTTPSend`/`ErrHTTPRead`) in the response payload, or ensure `IsExternalEndpointError`/`IsValidationError` flags are the only signal exposed, without host/scheme/port-specific text.

## Proof of Concept
1. Deploy a workflow authorized to invoke the gateway's HTTP action capability.
2. Set `OutboundHTTPRequest.URL` sequentially to `http://169.254.169.254`, `http://10.0.0.5:22`, `http://10.0.0.5:9999`, and `file:///etc/passwd`, and submit each via the workflow.
3. Inspect the resulting `OutboundHTTPResponse.ErrorMessage` for each request: blocked-IP, blocked-port, and blocked-scheme cases return distinguishable safeurl reason text (`"ip: ... not found in allowlist"`, `"port: ... not found in allowlist"`, `"scheme: ... not found in allowlist"`), while a reachable/live address returns a different, generic `ErrHTTPSend`/timeout-class message.
4. Repeat across a range of internal candidate hosts/ports to build a map of the gateway's reachable internal infrastructure purely from response text, confirming the oracle.

func truncateLogError(err error) error {
	var urlErr *url.Error
	if !errors.As(err, &urlErr) {
		return err
	}
	u, parseErr := url.Parse(urlErr.URL)
	if parseErr != nil {
		return urlErr.Err
	}
	// trim to scheme + host only
	sanitized := &url.Error{Op: urlErr.Op, URL: u.Scheme + "://" + u.Host, Err: urlErr.Err}
	return sanitized
}

// isBlockedRequest checks if an error is caused by blocked/invalid input (e.g., blocked IP, invalid scheme, blocked headers)
// It checks for safeurl typed errors.
func isBlockedRequest(err error) bool {
	if err == nil {
		return false
	}

	// Check safeurl typed errors - use errors.As for type checking
	var (
		ipv6Err              *safeurl.IPv6BlockedError
		portErr              *safeurl.AllowedPortError
		schemeErr            *safeurl.AllowedSchemeError
		invalidHostErr       *safeurl.InvalidHostError
		ipErr                *safeurl.AllowedIPError
		redirectsDisabledErr *redirectsDisabledError
	)

	return errors.As(err, &ipv6Err) ||
		errors.As(err, &portErr) ||
		errors.As(err, &schemeErr) ||
		errors.As(err, &invalidHostErr) ||
		errors.As(err, &ipErr) ||
		errors.As(err, &redirectsDisabledErr)
}
