### Title
Webhook Shop Domain Header Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by verifying the HMAC over the raw request body, then hands the attacker-controllable `shop-domain` header straight to the app's handler as the authenticated tenant identifier, without that header ever being covered by the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `shop` is read directly from the `x-shopify-shop-domain`/`shopify-shop-domain` header with no cryptographic binding to it: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` (the body), never incorporating the shop header: [2](#0-1) 

`Registry.process` accepts the request once the body HMAC checks out, then forwards `request.shop` (the unauthenticated header value) to the handler as the tenant/shop identity: [3](#0-2) 

Because the HMAC secret (`Context.api_secret_key`, the app's `client_secret`) is shared across **all** shops that install the app, any shop that installs the app can capture a legitimately-signed `(body, hmac)` pair from its own genuine webhook deliveries. Since the HTTP endpoint receiving webhooks is just a normal internet-reachable endpoint (not mTLS/IP-restricted to Shopify), that shop owner can replay the same body and `hmac-sha256` value directly to the app, while freely setting the `x-shopify-shop-domain` header to a victim shop's domain. `HmacValidator.validate` will still pass because it never checked the shop header, and the handler will process the spoofed body as if it originated from the victim shop.

This breaks the intended identity binding: `authenticated_shop (HMAC-covered) == shop_used_by_handler (header)`. The header is trusted despite not being part of the signed payload.

### Impact Explanation
This allows a low-privileged actor (any merchant who can install the multi-tenant app) to inject arbitrary webhook payloads attributed to a different, victim shop into the host application's webhook handler. Depending on what the host app's handler does with `WebhookMetadata#shop` (e.g., look up/update per-shop records, trigger emails, sync inventory, etc.), this constitutes cross-tenant data injection/corruption — a Critical-class boundary crossing (cross-tenant access) enabled entirely by this gem's webhook verification primitive not binding the shop identity to the signature.

### Likelihood Explanation
Requires only: (1) attacker is a legitimate but unprivileged installer of the target multi-tenant app (to obtain one valid signed webhook body/hmac pair for their own shop), and (2) network access to POST to the app's public webhook endpoint with a forged `x-shopify-shop-domain` header. No access token, `client_secret`, or privileged account is required — the shared app secret and header-based shop attribution make this straightforward to exploit.

### Recommendation
Have `Registry.process` (or `HmacValidator`) cross-check that the `shop` extracted from the request actually corresponds to a known, previously-recorded installation/session for that shop (e.g., verify a stored per-shop secret/session), or otherwise bind the `shop-domain` value into the material that's HMAC-verified, so that the shop identity cannot be forged independently of the signed body.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, receiving genuine webhooks (e.g. `orders/create`) signed with the app's shared `client_secret`.
2. Attacker captures one such request: raw body `B` and header `x-shopify-hmac-sha256: H` (valid for `B` under the shared secret).
3. Attacker POSTs directly to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged, still valid), but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:13-22`) returns `true` because it only checks `H` against `B`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the handler with `shop: "victim.myshopify.com"`, even though the payload actually originated from the attacker's own shop.
