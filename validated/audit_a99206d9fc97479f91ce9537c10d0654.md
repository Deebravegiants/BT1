### Title
Unconstrained `EmporiumOperation.callData` lets an unprivileged caller sweep any ERC20/ETH balance held by `EmporiumUpgradeable`, bypassing all balance accounting - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction` only checks that the *net* balance change of tokens listed in `circomData.erc20TokenAddresses` is non‑negative and reconciles it against `deltaAmountChanges`; it never restricts which contracts/calldata the attacker‑supplied `stack.ops` can target. Because `stack.signerAddress` can legally be `address(0)`, `verifyWallet` skips all signature validation on `ops`, so an unprivileged caller fully controls `op.endpoint`/`op.callData`/`op.value` and can direct the Emporium contract (the `msg.sender` of the inner call) to transfer out any token balance it holds — including one that is deliberately left out of `circomData.erc20TokenAddresses` for that transaction — with zero accounting or revert.

### Finding Description
The invariant that should hold is: *tokens leaving the Emporium action contract in a transaction == the sum of `-deltaAmountChanges` Hinkal sent it plus whatever `handleOut` returns as declared UTXOs*. This is only enforced for indices present in `circomData.erc20TokenAddresses`: [1](#0-0) 

That loop only iterates `circomData.erc20TokenAddresses`. The `stack.ops` array executed just before it, however, is completely independent of that list: [2](#0-1) 

`op.endpoint.call{value: op.value}(op.callData)` is executed with the Emporium contract as `msg.sender`. The only gate on this content is `verifyWallet`, but when `stack.signerAddress == address(0)` it returns immediately, doing nothing more than marking `emporiumMessage` used: [3](#0-2) 

So an attacker can build a stack (fully attacker-controlled `externalActionMetadata`) with an op such as `endpoint = <token>`, `callData = abi.encodeWithSelector(IERC20.transfer.selector, attackerAddress, residualBalance)`, for a token that the attacker simply omits from `circomData.erc20TokenAddresses` in that same transaction (or `circomData.amountChanges[i] == 0` for it). Because that token index never appears in the `balancesBefore`/`balancesAfter` reconciliation loop, `balanceChange` is never computed for it and `BalanceChangeShouldBePositive()` can never fire — the transfer to the attacker's address is invisible to every check in `runAction`, in `Hinkal._externalTransact`, and in the circuit (`inTotal + amountChanges[i] === outTotal` is only asserted per declared `erc20TokenAddresses[i]`).

Any balance the Emporium contract is holding qualifies as "residual" for this attack: leftover deposits from an action that under-consumed `-deltaAmountChanges` in a previous call, dust from partial-fill router refunds, or stray transfers. The "tree has exactly one leaf" detail is a convenience for building the attacker's own proof cheaply (with one leaf, `roots[MINIMUM_INDEX]` equals that leaf directly, simplifying the Merkle path needed to submit *any* valid `transact()` call) — it is not required by the vulnerability itself, since the malicious op can also be smuggled into a transaction that spends zero real inputs (`inAmounts[i][j] == 0` disables the root-hash equality check per `ForceEqualIfEnabled` in the circuit).

### Impact Explanation
Any ERC20 or ETH balance sitting in the `EmporiumUpgradeable` contract for a token not declared in the current call's `erc20TokenAddresses` can be transferred to an address of the attacker's choosing, with no requirement that it match `deltaAmountChanges` or be represented by an output UTXO. If the parked balance originates from another user's in-flight deposit or refund, this is direct theft of user funds routed through the protocol (Critical). At minimum, it is theft of protocol-held/relay-adjacent balances and execution of asset-moving calls that neither the depositor nor any proof ever authorized (High). The attack is repeatable every time the Emporium contract accrues an untracked balance.

### Likelihood Explanation
The attacker needs only: (1) the ability to submit any valid `transact()` call through the normal Emporium `externalActionId` path (achievable with their own funds/UTXOs, since `signerAddress = address(0)` needs no signature at all), and (2) knowledge that the Emporium contract holds a non-zero balance of some token not listed by the victim/attacker's own `erc20TokenAddresses`. Detecting such a balance is trivial (public `balanceOf` read). Cost is one transaction; feasibility is high because none of `performHinkalChecks`, `verifyProof`, `rootHashExists`, or the balance/slippage requires constrain calls to endpoints/tokens outside the declared `erc20TokenAddresses` array.

### Recommendation
Restrict `EmporiumOperation.endpoint` (and any token addresses touched by `callData`) to be members of `circomData.erc20TokenAddresses`, or otherwise force the post-op balance reconciliation loop to cover every token the ops interact with (e.g., by requiring `ops` to only call pre-approved router/endpoint contracts, and by measuring balances for the full universe of tokens an op can move, not just the declared set). Additionally, require an EIP-712-style validation of `stack.ops` content even when `signerAddress == address(0)`, or disallow direct ERC20 `transfer`/`transferFrom`/`approve` selectors as op targets entirely.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, and `EmporiumUpgradeable`; register the Emporium action.
2. Seed a "residual" balance on the Emporium contract for token `R` (simulate a stranded balance, e.g. by directly minting/transferring `R` tokens to the Emporium address, representing a prior stuck deposit not captured by any accounted transaction).
3. As an unprivileged attacker EOA, generate a normal, unrelated valid proof for a `transact()` call to the Emporium action using a dummy token `D` (with `amountChanges[D] == 0`, `erc20TokenAddresses = [D]`), and craft `externalActionMetadata` = `EmporiumStack{signerAddress: address(0), ops: [{endpoint: R, invokeWallet: false, value: 0, callData: abi.encodeWithSelector(IERC20.transfer.selector, attacker, residualAmount)}]}`.
4. Call `Hinkal.transact(...)`.
5. Assert: (a) `R.balanceOf(attacker) == residualAmount` after the call; (b) the transaction did not revert with `BalanceChangeShouldBePositive`; (c) `circomData.erc20TokenAddresses` never contained `R`, i.e., `deltaAmountChanges` for `R` was never computed/checked, proving tokens left the action outside the `-deltaAmountChanges` accounting equality.
