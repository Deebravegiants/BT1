### Title
Webhook shop attribution is not covered by HMAC, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb], [File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, but then trusts the unauthenticated `shop-domain` header to determine which tenant (shop) the webhook belongs to. Because the HMAC signature never covers the shop identity, an attacker who obtains any one valid `(raw_body, hmac)` pair for the shared app secret can replay it while claiming an arbitrary `shop-domain`, causing the handler to process attacker-controlled data under a victim shop's identity — a cross-tenant authentication bypass, structurally analogous to the mTOFT report's pattern of a value being acted upon without being covered by the same integrity check that "authenticates" the operation.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the signature only from `verifiable_query.to_signable_string` and the app's `api_secret_key`: [1](#0-0) 

For webhook requests, `to_signable_string` returns only the raw HTTP body — it deliberately excludes the `shop-domain` header: [2](#0-1) 

The `shop` accessor reads directly from the (unauthenticated) `shopify-shop-domain` / `x-shopify-shop-domain` header: [3](#0-2) 

`Registry.process` then validates only the HMAC of the body, and — without any cross-check that the signed body actually belongs to the claimed shop — forwards the header-derived `request.shop` value straight into the handler as the tenant identity: [4](#0-3) 

Since every shop installed on a given app shares the same `api_secret_key` (`Context.api_secret_key` is a single, app-wide secret, not per-shop), any attacker who legitimately installs the app on their own store can receive a genuinely-signed webhook (correct HMAC, correct body) for their own shop, and then replay that exact `(body, hmac)` pair directly to the app's public webhook endpoint while substituting the `shop-domain` header with an arbitrary victim shop domain. The equality the code should enforce — "the shop whose secret validated this payload" == "the shop attributed to the resulting business action" — is never checked; only body integrity is checked, and shop identity rides along unauthenticated.

### Impact Explanation
This allows an unprivileged (but app-installing) attacker to inject fabricated, HMAC-"valid" webhook events that the host application will process as if they originated from a different, victim shop. Depending on what the host app's webhook handlers do with `WebhookMetadata#shop` (e.g., updating per-shop records, honoring `shop/redact`/`customers/redact` compliance webhooks, or driving business logic keyed by shop), this is a cross-tenant data integrity/authentication issue: the library asserts a false "this webhook is authenticated for shop X" guarantee to the app. This matches the Critical category of cross-tenant access via an identity-binding gap that mirrors the report's fee-double-transfer class of bug: a step whose result is trusted without an intact link back to the value that was actually verified.

### Likelihood Explanation
Likelihood is high for any attacker capable of installing the target app on a store they control (a standard, unprivileged action for any Shopify merchant/developer) — no leaked secrets, tokens, or privileged access are required. Once they capture one legitimate webhook delivery, they can replay it indefinitely against the same endpoint with a forged `shop-domain` header, since the gem performs no per-shop binding check.

### Recommendation
Bind the shop identity into the value that is HMAC-verified, or otherwise cryptographically/logically tie the validated payload to the claimed shop before dispatching to handlers:
- Include the `shop-domain` (and ideally `webhook-id`/`api-version`) in the signable string used for HMAC validation, or
- After HMAC validation, cross-check the claimed `shop` against an independent per-shop record (e.g., a registered webhook subscription ID/shop mapping) before invoking the handler, rejecting mismatches.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw POST body `B` and the `x-shopify-hmac-sha256` header value `H` that Shopify sent to the app's callback endpoint. `H` is valid because `HMAC(secret, B) == H`.
2. Attacker sends their own POST request directly to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - `x-shopify-hmac-sha256`: `H` (unchanged, still valid since only `B` is signed)
   - `x-shopify-shop-domain`: `victim-shop.myshopify.com` (forged)
   - `x-shopify-topic`, `x-shopify-webhook-id`: attacker-chosen
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(secret, B) == H`.
4. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, causing the host app to process attacker-supplied data under the victim shop's identity. [4](#0-3)
