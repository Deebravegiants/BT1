### Title
Emporium `runAction` Allows Arbitrary Calls to Tokens Outside the Declared `erc20TokenAddresses` Set, Bypassing the Balance-Invariant Check - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction()` executes an attacker-supplied list of `EmporiumOperation`s (`stack.ops`) via arbitrary `op.endpoint.call(op.callData)`, and only afterwards checks that the Emporium contract's balance did not decrease — but that post-check iterates solely over `circomData.erc20TokenAddresses`, the token list the *caller themselves declares*. Any `op.endpoint` (e.g. an ERC20 the Emporium is currently holding on behalf of the shielded pool) that is *not* included in that declared list is never balance-checked at all, so an unprivileged EOA can use a trivial/self-authorized proof to make Emporium issue arbitrary state-changing calls (e.g. `approve`) against pooled funds it holds, with zero validation.

### Finding Description
`runAction` in [1](#0-0)  decodes an `EmporiumStack` from `circomData.externalActionData.externalActionMetadata` — data fully controlled by whoever calls `Hinkal.transact()` — and for each `op` in `stack.ops` executes:

```solidity
(success, err) = op.endpoint.call{value: op.value}(op.callData);
```

The only safety net is the selector check blocking `callHinkalWallet`/`doSendToRelay`, and the post-loop balance-invariant check: [2](#0-1) 

This loop only iterates `circomData.erc20TokenAddresses`, an array chosen by the *same caller* who chose `op.endpoint`/`op.callData`. Nothing forces every `op.endpoint` that is an ERC20 token to be present in `erc20TokenAddresses`. As a result:

1. An attacker submits `stack.signerAddress = address(0)` so `verifyWallet` returns immediately without any signature check ( [3](#0-2) ).
2. Attacker declares `circomData.erc20TokenAddresses` = some token(s) they actually own/deposit in this tx (or none at all), so the balance-invariant loop only "watches" those tokens.
3. Attacker includes an `EmporiumOperation` with `endpoint = <pooled ERC20 the Emporium contract is currently holding on behalf of the shielded pool>` and `callData = abi.encodeCall(IERC20.approve, (attacker, type(uint256).max))`.
4. Because `approve()` never changes `balanceOf(Emporium)`, and because that token isn't in the declared `erc20TokenAddresses` list, the post-check never examines it — `balanceChange` for the watched tokens still satisfies `>= 0`, so the whole transaction succeeds.
5. Emporium (msg.sender inside the low-level `call`) has now granted the attacker unlimited allowance over its pooled token balance, which the attacker can drain in a follow-up `transferFrom` call outside of any Hinkal-mediated flow.

This is the same authorization-gap class as the report: a check exists (`balanceChange >= 0`), but it is scoped narrowly enough (only to caller-declared tokens) that an attacker can route the unauthorized action (an `approve`/state-changing call) through a path the check never covers, letting an operation proceed that was never actually authorized against the funds it affects.

### Impact Explanation
This lets an unprivileged EOA obtain unlimited ERC20 approval (or perform any other non-balance-affecting state change, e.g. staking/permission grants) over funds pooled in the `Emporium` contract that belong to the shielded pool/other users, with no signer authorization and no relevant balance check. Subsequent `transferFrom` drains those pooled funds — direct theft of shielded/in-flight user funds, i.e. a Critical-impact unauthorized asset movement never approved by any prover or signer for that specific token.

### Likelihood Explanation
Reachable by any unprivileged EOA in one `Hinkal.transact()` call with `externalActionId` pointing at Emporium; requires only a valid proof for the attacker's own (possibly zero/dust-value) shielded balance and `signerAddress = address(0)` in the metadata — no admin/relayer/owner privileges needed. High likelihood given the check gap is deterministic, not probabilistic.

### Recommendation
Require every `op.endpoint` that will alter allowance/approval/ownership state (or at minimum, every address touched by `stack.ops`) to be a member of `circomData.erc20TokenAddresses`, or maintain a full snapshot/diff of *all* tokens the Emporium could plausibly hold (not just caller-declared ones) before/after the ops loop. More robustly, restrict permitted `op.endpoint` targets to an allow-list of vetted integration contracts, and explicitly disallow `approve`/`increaseAllowance`/`setApprovalForAll`-style selectors on arbitrary tokens unless the target is included and separately validated in the balance/approval invariant.

### Proof of Concept
1. Attacker owns (or proofless-deposits) a trivial/dust amount of TokenA and gets a valid Hinkal proof for a transaction with `circomData.erc20TokenAddresses = [TokenA]`, `externalActionId` = Emporium's id.
2. `circomData.externalActionData.externalActionMetadata` encodes an `EmporiumStack` with `signerAddress = address(0)` and `ops = [{ endpoint: TokenB (an ERC20 the Emporium currently holds a large balance of), invokeWallet: false, value: 0, callData: abi.encodeWithSelector(IERC20.approve.selector, attacker, type(uint256).max) }]`.
3. Call `Hinkal.transact(...)`. Execution reaches `_externalTransact` → `EmporiumUpgradeable.runAction()` ( [4](#0-3) ).
4. `runAction` executes `TokenB.call(approve(attacker, max))` from Emporium's context; since `TokenB` is not in `circomData.erc20TokenAddresses`, the post-loop balance check at lines 132-151 never inspects `TokenB`'s balance, and the only checked token (`TokenA`) satisfies `balanceChange >= 0` trivially.
5. Transaction succeeds. Attacker now separately calls `TokenB.transferFrom(Emporium, attacker, TokenB.balanceOf(Emporium))`, draining pooled TokenB funds.

    function runAction(
        CircomData calldata circomData,
        int256[] calldata deltaAmountChanges
    ) external override onlyAllowedRecipient returns (UTXO[] memory) {
        EmporiumStack memory stack = abi.decode(
            circomData.externalActionData.externalActionMetadata,
            (EmporiumStack)
        );

        uint256[] memory balancesBefore = getBalancesForArray(
            circomData.erc20TokenAddresses
        );

        verifyWallet(stack, circomData);

        for (uint256 i = 0; i < stack.ops.length; i++) {
            EmporiumOperation memory op = stack.ops[i];

            bool success;
            bytes memory err;

            // CASE 1: Stateful Interaction
            if (op.invokeWallet && stack.signerAddress != address(0)) {
                (success, err) = IHinkalWallet(stack.signerAddress)
                    .callHinkalWallet(op.endpoint, op.callData, op.value);
            }
            // CASE 2: Stateless Interaction
            else {
                bytes4 selector = bytes4(op.callData);
                if (
                    selector == IHinkalWallet.callHinkalWallet.selector ||
                    selector == IHinkalWallet.doSendToRelay.selector
                ) {
                    revert UnauthorizedWalletCall();
                }

                (success, err) = op.endpoint.call{value: op.value}(op.callData);
            }

            if (!success) {
                revert CallFailed(err);
            }
        }
