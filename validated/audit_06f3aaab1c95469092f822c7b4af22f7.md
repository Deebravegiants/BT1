## Analog Found

### Title
Unrestricted `CallDispatcher.dispatch` lets any caller plant standing ERC20 approvals that drain funds the shared dispatcher later holds for other orders - ([File: evm/src/utils/CallDispatcher.sol])

### Summary
`CallDispatcher.dispatch(bytes)` is an unauthenticated, externally-callable function that executes fully attacker-controlled `Call[]` entries (arbitrary `to` and `data`, including `value`) directly from the dispatcher contract's own context, with no allow-list on `to`/`data` and no restriction on who may call `dispatch`. `IntentGatewayV2` treats this single dispatcher instance (`_params.dispatcher`) as a shared, reusable escrow-execution buffer for *all* orders placed by *all* users — both for `predispatch` (user assets are moved to the dispatcher before predispatch calls run) and for `output.call`/postdispatch execution (solver-delivered output tokens are routed through the dispatcher). This mirrors the JOJO report's bug class: an unchecked "asset"/target parameter combined with an arbitrary low-level call lets an attacker corrupt a shared contract's ERC20 approvals and later steal balances that legitimately belong to other participants.

### Finding Description
`CallDispatcher.dispatch` has no caller restriction and no validation of the `to`/`data` fields in each `Call`: [1](#0-0) 

Because this function is `external` with no `onlyGateway`/`onlyOwner` modifier, **any address** can call `dispatcher.dispatch(...)` directly — not just `IntentGatewayV2`. An attacker can submit:
```solidity
Call({ to: USDC, value: 0, data: abi.encodeWithSelector(IERC20.approve.selector, attacker, type(uint256).max) })
```
This makes the dispatcher itself grant the attacker a standing, unlimited allowance over its own `USDC` balance, with the call executing as `msg.sender = dispatcher`.

`IntentGatewayV2` reuses this exact dispatcher address as a **shared singleton across every order and every user**:
- `predispatch`: caller's real escrow assets are transferred into the dispatcher, then `dispatcher.dispatch(order.predispatch.call)` runs, and only afterward are balances swept back via `IERC20(token).transfer(...)` calls issued through the same dispatcher: [2](#0-1) 

- `output`/postdispatch: solver-delivered output tokens can be routed to the dispatcher (`beneficiary = dispatcher`) and `order.output.call` is dispatched there before any dust sweep: [3](#0-2) 

Since the dispatcher never resets or revokes approvals it grants (there is no code path that calls `approve(x, 0)` after use), any standing approval an attacker plants via a direct, unauthenticated `dispatch()` call persists indefinitely. Because the dispatcher is the *same* contract instance used by every subsequent order's predispatch/postdispatch flow, whenever it transiently or residually holds a real balance of the token the attacker pre-approved (e.g., unswept dust from a DeFi call that touches a token not listed in that order's `output.assets`/`inputs`, or fee-on-transfer/callback-token reentrancy windows during `dispatch`), the attacker can call `token.transferFrom(dispatcher, attacker, balance)` directly on the ERC20 — completely bypassing `IntentGatewayV2` — and steal funds that belong to other users' orders or to the protocol's dust accounting.

### Impact Explanation
This breaks the core assumption that the dispatcher only ever moves value on behalf of the order that funded it. A pre-planted standing approval effectively gives the attacker a permanent claim on any current or future balance of the approved token that lands on the dispatcher, regardless of which user's order caused it to be there. This can result in outright theft of escrowed user funds or protocol dust routed through the shared `CallDispatcher`, satisfying the "concrete theft of funds" bar.

### Likelihood Explanation
The attack requires zero privilege: `dispatch()` is callable by any EOA/contract with no gateway restriction, and the `Call.to`/`Call.data` fields are entirely attacker-supplied with the only check being `extcodesize(to) != 0`. Planting the malicious approval costs a single transaction. Triggering the drain merely requires the token to at some later point transiently reside on the dispatcher — which is a normal, expected occurrence in both the predispatch and postdispatch flows across the lifetime of the shared dispatcher.

### Recommendation
Restrict `CallDispatcher.dispatch` to be callable only by the trusted gateway/dispatcher-owning contract (e.g., an `onlyGateway` modifier bound to the configured `IntentGatewayV2` address), and/or make the dispatcher stateless per-call by deploying an ephemeral/minimal-proxy dispatcher per order rather than reusing one singleton across all users. Additionally, disallow or explicitly revoke any `approve`-type calls issued through `dispatch`, and sweep/verify zero residual balance and zero non-order-specific allowances on the dispatcher at the end of every `dispatch()` invocation.

### Proof of Concept
1. Attacker calls `CallDispatcher(dispatcher).dispatch(abi.encode([Call({to: USDC, value: 0, data: abi.encodeWithSelector(IERC20.approve.selector, attacker, type(uint256).max)})]))` directly — no relation to any order, no gateway involvement required, since `dispatch` has no access control (`evm/src/utils/CallDispatcher.sol:44`).
2. `USDC.allowance(dispatcher, attacker)` is now `type(uint256).max`, permanently, since nothing ever revokes it.
3. At any later point when a legitimate `placeOrder`/`fillOrder` predispatch or postdispatch flow causes `USDC` to transiently or residually sit on the dispatcher (`evm/src/apps/IntentGatewayV2.sol:235-289`, `evm/src/apps/intentsv2/IntentsBase.sol:498-527`), the attacker calls `USDC.transferFrom(dispatcher, attacker, USDC.balanceOf(dispatcher))` directly on the token contract, stealing those funds before the gateway's own sweep/accounting logic can claim them.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
