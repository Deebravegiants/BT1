## Analog Vulnerability Found [1](#0-0) 

### Title
Order-dependent, non-atomic read-modify-write of the extra-seeds list allows a "removed" seed's private key material to resurrect after a race between `addSeed`/`removeManySeeds` - (File: `features/wallet/module/wallet.js`)

### Summary
`Wallet.removeManySeeds` and `Wallet.addSeed` both perform an unsynchronized read-modify-write cycle on the same persisted `extraSeeds` collection (`#getExtraSeeds()` → mutate in memory → `#setExtraSeeds()`), exactly mirroring the reported `OperatorsRegistry.removeValidators` bug class: two logically independent calls that touch a shared indexed/keyed collection, with no snapshot/version check and no mutual exclusion, so the final persisted state depends entirely on which call's write lands last, not on the semantics the caller intended.

### Finding Description
`removeManySeeds` reads the current `extraSeeds` array, computes `remainingSeeds` (seeds not being removed) and `seedsToRemove`, then writes back `remainingSeeds` via `#setExtraSeeds`, and only afterwards removes the corresponding key material from the in-memory keychain: [2](#0-1) 

`addSeed` follows the identical unsynchronized pattern — read `#getExtraSeeds()`, push, `#setExtraSeeds()`: [3](#0-2) 

Unlike `create`/`import`, which are wrapped in `makeConcurrent({ concurrency: 1 })` to serialize access: [4](#0-3) 

`addSeed`, `removeManySeeds`, and `removeSeed` have **no such guard**. Because every step (`#getExtraSeeds`, `getSeedId`, `#setExtraSeeds`, `#keychain.removeSeeds`) is `await`-ed, the JS event loop can interleave two concurrent calls between their read and their write, producing a classic lost-update race — the same "order of calls affects resulting set" bug class described in the report.

Concrete race: given `extraSeeds = [A, B, C]`, two concurrent calls `removeManySeeds(['A'])` and `removeManySeeds(['B'])` both read `[A, B, C]` before either writes. If `removeManySeeds(['A'])`'s write (`[B, C]`) completes, then `removeManySeeds(['B'])`'s stale write (`[A, C]`) completes last, the persisted `extraSeeds` storage ends up containing `A` again — even though `A` was explicitly removed and its key material was already deleted from the live keychain via `#keychain.removeSeeds`.

The impact is not just lost bookkeeping: on the next `unlock()`, all persisted `extraSeeds` are unconditionally re-added to the keychain: [5](#0-4) 

So the seed `A` — which the user explicitly and successfully asked to remove — silently resurrects into the active, unlocked keychain and becomes usable for signing again, without any further user action or confirmation.

### Impact Explanation
A user who removes a seed (e.g., because its mnemonic is suspected compromised, shared, or simply meant to be permanently deleted) can, purely due to an incidental race between two of their own async calls (e.g., rapid double-tap in the UI, or an `addSeed` overlapping a `removeSeed`), end up with that seed's private key material silently persisted in `walletStorage` and reloaded into the live keychain on the next unlock. This directly undermines the user's explicit key-removal action and results in a private key remaining signing-capable when it should have been permanently destroyed — a concrete wallet-compromise-adjacent outcome (unauthorized/unexpected signing capability for a seed the user believed removed).

### Likelihood Explanation
No external attacker or malicious peer is required — this is reachable purely from the app's own async API surface. Any UI flow that allows two seed-mutation calls (`addSeed`, `removeSeed`, `removeManySeeds`) to be triggered close together (double-clicks, retries after timeout, background sync racing with a user action, or promise `.allSettled` batch flows already present in tests) can trigger the interleaving, since none of these methods are serialized via `makeConcurrency`. The existing test suite even demonstrates `Promise.all` usage over `removeManySeeds`/`addSeed`-like flows in adjacent modules (e.g. `wallet-accounts` explicitly hardening `createMany` with `makeConcurrent` after a documented "data lost on concurrent create calls" bug), showing this race class is a recognized real risk in this codebase, but here it remains unaddressed for `addSeed`/`removeManySeeds`.

### Recommendation
Wrap `addSeed`, `removeManySeeds` (and thus `removeSeed`) in the same `makeConcurrent({ concurrency: 1 })` serialization already used for `create`/`import`, so that reads and writes of `extraSeeds` cannot interleave. Additionally, await `#removeManySeedsMetadata(seedIds)` on line 191 (currently fire-and-forget) to avoid a related unawaited-write hazard.

### Proof of Concept
```js
// extraSeeds initially: [A, B, C]
await Promise.all([
  wallet.removeManySeeds([seedIdA]),
  wallet.removeManySeeds([seedIdB]),
])
// Depending on interleaving, storage.extraSeeds can end up as [A, C]
// (A resurrected) instead of the expected [C].
await wallet.lock()
await wallet.unlock()
// keychain now re-contains A's key material, even though it was
// explicitly removed and confirmed removed from the keychain earlier.
```
