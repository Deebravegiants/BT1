## Title
Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop` value it then hands to the app's handler as the tenant identifier is taken from an HTTP header that is never included in the signed content. Because all shops installed on an app share the same `api_secret_key`, any merchant who can get one legitimately-signed webhook delivered to the app can replay it with a forged `shop-domain` header naming a different (victim) shop, and the library will accept it as authentic for that victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop` is read straight from the (attacker-controlled) `shopify-shop-domain` / `x-shopify-shop-domain` header, with no cryptographic tie to the body or to any other verified value: [2](#0-1) 

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, which internally calls `verifiable_query.to_signable_string` (i.e., the raw body only) and never inspects `shop`: [3](#0-2) [4](#0-3) 

After the HMAC check passes, `request.shop` (the unauthenticated header value) is forwarded directly to the app's handler as the tenant identity for the event: [5](#0-4) 

The broken equality is: **`shop` authenticated by the HMAC (none) ≠ `shop` acted on by the handler (`request.shop` header)**. Since the same `api_secret_key` is shared by every shop that installs the app, an attacker who controls their own shop installation can obtain a validly-signed webhook (body + HMAC) from Shopify for their own tenant, then re-POST that exact body/HMAC pair to the app's webhook endpoint while swapping only the `shop-domain` header to name a victim shop. `HmacValidator.validate` still succeeds because it only checks the raw body against the shared secret, and `Registry.process` dispatches the event to the handler tagged with the forged victim shop.

### Impact Explanation
This breaks the tenant boundary the webhook interface is supposed to guarantee: the shop identity delivered to app business logic (`WebhookMetadata#shop`) is not authenticated at all, only the payload bytes are. Any app that uses `WebhookMetadata#shop` to select which tenant's records to create/update/delete (a normal and expected usage pattern for webhook handlers) can be made to write, or act on, data under a victim shop's identity using content the attacker fully controls (their own shop's webhook body). This is a cross-tenant access/data-integrity violation attributable to the gem's own webhook verification, not to host misuse, because the gem's `VerifiableQuery`/`HmacValidator` contract signs only the body and the `Request` class exposes `shop` as if it were trustworthy alongside the HMAC-verified fields.

### Likelihood Explanation
Likely for any developer building on this gem: `request.shop` is presented via `WebhookMetadata` next to HMAC-validated data with no documentation warning that it is unauthenticated, so it is natural to trust it as the tenant key. The prerequisite — attacker controls one legitimate shop installation of the target app — is realistic for any public app since installation itself requires no special privilege.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the HMAC-signable content, or otherwise cryptographically bind the header-derived `shop` value to the verified payload (e.g., cross-check against a `shop` field embedded in the JSON body, or reject when a session/shop record can't be correlated). At minimum, document clearly that `Request#shop` is not covered by the HMAC and must not be used as a trusted tenant identifier without additional verification.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and receives a real Shopify webhook to their endpoint:
raw_body = '{"id":1,"note":"hello"}'
real_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# Attacker replays it, forging the shop header to point at a victim tenant:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(real_hmac), # still valid, computed over raw_body only
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not covered by HMAC at all
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => passes Utils::HmacValidator.validate(request) (only raw_body is checked)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: attacker_json, ...))
```
`Registry.process` raises no error and dispatches the event as if it genuinely originated from `victim-shop.myshopify.com`. [3](#0-2)
