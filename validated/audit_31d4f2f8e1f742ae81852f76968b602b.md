### Title
Webhook `shop-domain` header is not covered by HMAC signature, enabling cross-tenant replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `request.shop` is read straight from the unauthenticated `shop-domain` header [2](#0-1) . `Utils::HmacValidator.validate` only ever verifies `raw_body` against `Context.api_secret_key` [3](#0-2) , so the header used by `Registry.process` to attribute the webhook to a shop (`WebhookMetadata.new(... shop: request.shop ...)`) is never bound to the signed bytes [4](#0-3) .

### Finding Description
The binding claimed to hold is: `bytes_verified (to_signable_string == @raw_body)` == `bytes_used_for_routing (shop-domain header)`. Tracing the code shows this is false: `to_signable_string` is exactly `@raw_body` and nothing else [1](#0-0) ; `shop` is derived purely from `shopify_header("shop-domain")`, a value taken verbatim from caller-supplied headers with no cross-check against the body or the HMAC [2](#0-1) [5](#0-4) . `HmacValidator.validate_signature` computes `HMAC(secret, to_signable_string)` and compares it to `verifiable_query.hmac`, using `Context.api_secret_key`/`old_api_secret_key`, which are the app's client secret shared across every shop that installs the app (not a per-shop key) [6](#0-5) .

Because the secret is the same for all shops, a body+HMAC pair legitimately delivered to the attacker's own dev-shop endpoint will pass `HmacValidator.validate` for the exact same bytes no matter what headers accompany it. `Registry.process` calls `Utils::HmacValidator.validate(request)` and, once true, immediately trusts `request.shop`, `request.topic`, and `request.parsed_body` to dispatch to the registered handler with no additional verification that the shop header corresponds to the body or to any known/installed shop [4](#0-3) . Since the attacker directly controls the raw HTTP request sent to the app's webhook endpoint (they are not relying on Shopify's delivery infrastructure to reach the app - they POST it themselves), they can capture a genuine `(raw_body, hmac)` pair from a webhook Shopify sent them for their own shop and resend it to the victim app's webhook endpoint with `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) rewritten to the victim's domain. `validate` still returns `true` because it only checks `raw_body`, and `request.shop` now returns the attacker-chosen victim domain.

None of the existing guards prevent this: `ShopValidator.sanitize!` is used elsewhere (OAuth/token flows) but is never invoked in `Webhooks::Request` or `Registry.process` [4](#0-3) ; there is no `state` comparison, JWT `aud` check, or `Context` guard applicable to webhook processing; Sorbet typing only enforces `String` type on `shop`, not provenance.

### Impact Explanation
Any app that keys off `request.shop` (or the `shop` field of `WebhookMetadata`) to look up a session/store row and perform per-tenant side effects (e.g., updating victim shop state, revoking data, writing audit logs, GDPR redact processing) can be made to attribute an attacker-controlled, attacker-authored payload to an arbitrary victim shop domain, as long as the body content itself is not independently cross-validated against the header. This is repeatable against arbitrary victim shop domains from a single captured signed payload, since the shared app secret means the signature never needs to be regenerated per target - only the header is changed per victim. This matches the Critical "cross-tenant access" category: one tenant's forged request is processed as another tenant's authenticated event.

### Likelihood Explanation
Preconditions: the attacker needs only to install the target app on their own (free) development shop, receive one real webhook callback (trivial - webhooks are sent automatically on many events, or the attacker can trigger one), and have network access to POST directly to the app's public webhook endpoint. No credentials, secrets, or victim cooperation are required. The cost per victim is a single crafted HTTP POST with a rewritten header; the entire class of attacks (arbitrary future replays, arbitrary victim domains) is available from that one captured payload.

### Recommendation
`Webhooks::Request#to_signable_string` and `HmacValidator` only reflect the actual Shopify webhook signing scheme, which Shopify itself defines as HMAC over the raw body with the app's shared client secret - the `X-Shopify-Shop-Domain` header is not, and cannot be, covered by this HMAC on Shopify's side either. The gem cannot unilaterally add shop-domain coverage since it cannot alter what Shopify signs. The realistic mitigation is documentation/API-level: host apps must independently verify that `request.shop` corresponds to a shop with an active session/install for this app (e.g., look up a stored session and reject processing if none exists), and should treat `request.shop` as an untrusted routing hint validated against known installed shops, not as an authenticated identity. Optionally, the gem could expose a helper that requires callers to pass an expected/allow-listed shop domain into `Registry.process`/`Webhooks::Request` and raise if it doesn't match a session store lookup, but this is inherently an application-layer responsibility given Shopify's own signing scheme.

### Proof of Concept
minitest + WebMock plan (no live shop):
1. Set `ShopifyAPI::Context.setup(api_secret_key: "shhh", ...)`.
2. Compute `hmac = Base64.encode64(OpenSSL::HMAC.digest("sha256", "shhh", raw_body))` for a fixed `raw_body = '{"id":1}'` — this simulates a genuine Shopify-signed webhook delivered to the attacker's own dev shop.
3. Build `request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: {"shopify-topic" => "orders/create", "shopify-hmac-sha256" => hmac, "shopify-shop-domain" => "attacker-shop.myshopify.com"})` and assert `ShopifyAPI::Utils::HmacValidator.validate(request)` is `true` and `request.shop == "attacker-shop.myshopify.com"`.
4. Build `forged_request` with the **same** `raw_body` and `hmac`, but `"shopify-shop-domain" => "victim-shop.myshopify.com"`.
5. Assert `ShopifyAPI::Utils::HmacValidator.validate(forged_request)` is still `true` while `forged_request.shop == "victim-shop.myshopify.com"` — demonstrating the signature covers `raw_body` only and never binds to `shop`, i.e., `bytes_verified != bytes_used_for_routing`.
6. Optionally call `ShopifyAPI::Webhooks::Registry.process(forged_request)` (with a stubbed handler registered for `"orders/create"`) and assert the handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"`, proving end-to-end cross-tenant misattribution.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
