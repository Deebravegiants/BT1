## Title
SimplexPaymaster uses a single `maxOracleAge` staleness bound for both the native/USD and token/USD Chainlink feeds - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster` prices every gas payment by combining two independent Chainlink feeds — `nativeOracle` (native asset/USD) and a per-token `tokenOracle` (token/USD) — but validates freshness of both feeds against the exact same governance-configured `maxOracleAge` value, even though the contract's own documentation acknowledges Chainlink heartbeats vary drastically per feed/chain ("BSC stablecoins ~27s, Base/Ethereum stablecoins up to 24h"). This is the identical bug class as the reported `ChainLinkOraclePivot` finding: pairing feeds with very different heartbeats under one shared staleness threshold either lets a fast-heartbeat feed serve stale data (if the threshold is tuned to the slow feed) or makes the slow feed permanently "stale" (if tuned to the fast feed).

### Finding Description
`_getOraclePrice` is the single freshness gate used for every Chainlink read in the contract: [1](#0-0) 

It is called twice back-to-back with two *different* oracles but the *same* `maxOracleAge`: [2](#0-1) 

and again in the swap-pricing path: [3](#0-2) 

`maxOracleAge` is a single global parameter, set once for the whole contract regardless of which token/native pair is being priced: [4](#0-3) [5](#0-4) 

The contract's own comment on `TokenConfig`/`Params` explicitly acknowledges the heartbeat mismatch across chains/tokens ("BSC stablecoins ~27s, Base/Ethereum stablecoins up to 24h") yet only a single `maxOracleAge` field exists to bound both the fast native feed and the slow token feed (or vice versa) simultaneously: [6](#0-5) 

Governance's only lever, `_setParams`, enforces a single ceiling (`MAX_ORACLE_AGE = 7 days`) but no per-feed granularity, so operators are forced to either:
- set `maxOracleAge` high enough to tolerate the slowest paired feed's heartbeat, which means the faster feed's staleness check silently accepts prices that are far more stale than that feed's own heartbeat implies (fresh-looking check, stale real data), or
- set `maxOracleAge` low enough for the fast feed, which spuriously reverts on the legitimately-slow feed, denying service. [7](#0-6) 

### Impact Explanation
This is Medium severity because it silently degrades price integrity for a component that moves real funds on every reachable call:
- `_fetchDetails`/`_tokenPrice`, reached by any unprivileged UserOperation submitted through this paymaster, computes the ERC-20 gas price users are actually charged in `_prefund`/`postOp`. If the native/USD leg is allowed to be stale relative to its true heartbeat because `maxOracleAge` was tuned to the slower token feed, users can be systematically over- or under-charged relative to the real native gas cost, and an attacker who can influence timing (e.g. during an outage/deviation of the faster feed) can extract value from either the user or the paymaster's treasury.
- `swapAndDeposit` computes `amountOutMin` from the very same pair of feeds with the very same shared bound; a stale native/USD (or token/USD) price accepted under a loosely-tuned `maxOracleAge` directly weakens the slippage floor for actual on-chain token→native swaps, letting MEV/front-running siphon value out of the swap — concrete fund loss.

### Likelihood Explanation
Likelihood is realistic rather than theoretical: the contract is meant to be deployed across multiple chains (BSC, Base, Ethereum per its own comments) where per-feed heartbeats genuinely differ by orders of magnitude (27s vs 24h), so *any* correctly-configured deployment covering more than one heartbeat class is forced into this tradeoff by construction — there is no configuration of the single `maxOracleAge` that is simultaneously safe for both a 27s-heartbeat feed and a 24h-heartbeat feed. Every UserOperation processed by the paymaster, and every `swapAndDeposit` call, exercises this shared check.

### Recommendation
Track staleness bounds per-feed instead of one global value: add a `maxOracleAge` (or heartbeat) field to `TokenConfig` for the token feed, and a separate dedicated bound for `nativeOracle`, then have `_getOraclePrice` take the feed-specific bound as a parameter instead of reading the single global `maxOracleAge` state variable.

### Proof of Concept
1. Governance deploys `SimplexPaymaster` supporting a token whose Chainlink feed has a 24h heartbeat (e.g. `USDC/USD`) alongside a native asset feed with a 27s heartbeat (e.g. `BNB/USD`), and sets `maxOracleAge = 24h` so the USDC feed check in `_getOraclePrice` doesn't spuriously revert.
2. The `BNB/USD` feed's `latestRoundData().updatedAt` is now up to 24h old (e.g. during a feed outage or deviation-threshold quiet period) yet `block.timestamp - updatedAt <= maxOracleAge` still holds, so `_getOraclePrice` at `evm/src/utils/SimplexPaymaster.sol:666` does not revert.
3. `_tokenPrice` (`evm/src/utils/SimplexPaymaster.sol:653-658`) computes a gas price using this up-to-24h-stale native/USD price, mischarging every UserOperation processed through `_fetchDetails`/`_prefund` during that window.
4. Separately, `swapAndDeposit` (`evm/src/utils/SimplexPaymaster.sol:464-467`) derives `amountOutMin` from the same stale native price, letting the resulting swap execute at a worse-than-fair rate, extractable by any actor able to influence execution ordering.

        if (p.maxOracleAge == 0 || p.maxOracleAge > MAX_ORACLE_AGE) revert InvalidOracleAge(p.maxOracleAge);

                nativeOracle: nativeOracle,

    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
