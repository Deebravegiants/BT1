### Title
Unchecked ERC-20 return value in `withdraw()` allows escrow to be marked settled without tokens ever leaving the contract - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron `IntentGatewayV2` contract does not use `SafeERC20` for escrow payouts. Instead, `withdraw()` performs a raw low-level `.call` to the token's `transfer` function and only checks that the call did not revert (`success`), never decoding/validating the returned `bool`. For any ERC-20/TRC-20 token that signals failure by returning `false` rather than reverting, the accounting proceeds as if the transfer succeeded while the beneficiary never receives the tokens, and the escrow balance is permanently decremented so the funds can never be reclaimed.

### Finding Description
`withdraw()` is the internal function that releases escrowed order inputs (and fee-token proceeds) to a beneficiary on `RedeemEscrow`/`RefundEscrow` settlement: [1](#0-0) 

Both the per-token transfer and the fee transfer use the same unsafe pattern: [2](#0-1) 

The same anti-pattern is used earlier in `SweepDust` handling within `onAccept`: [3](#0-2) 

In each of these spots, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` returns `(bool success, bytes memory data)`. `success` is `true` whenever the callee contract executes without reverting — it says nothing about the ERC-20 semantic result encoded in `data`. Standard-compliant tokens revert on failure so this incidentally "works" for them, but any token (fee-on-transfer variant with an internal balance check that returns `false`, a paused/blacklist-style token, or any non-standard TRC-20) that returns `false` instead of reverting will pass the `if (!success) revert TransferFailed();` check even though no tokens moved.

Critically, right after this unchecked transfer, the escrow ledger is unconditionally decremented:
```solidity
_orders[body.commitment][token] -= amount;
```
There is no re-check of the token balance delta (unlike `placeOrder`/`fillOrder` elsewhere in the codebase, which snapshot balances before/after specifically to handle non-standard token behavior — see `IntentGatewayV2SameChainTest.sol` fee-on-transfer tests). Once `_orders[...]` is decremented, the funds cannot be re-withdrawn through any other code path — `withdraw()` is the only function that pays out escrow, and it is gated to run once per commitment/token via the `_orders[...] == 0` guard.

Note that the mainline EVM `IntentGatewayV2` (`evm/src/apps/intentsv2/IntentsBase.sol`) uses `IERC20(token).safeTransfer(...)` via OpenZeppelin's `SafeERC20`, which correctly reverts on a `false` return: [4](#0-3) 
The Tron variant deliberately diverges from this and re-introduces the exact bug class (unchecked ERC-20 return value) described in the external report.

### Impact Explanation
`withdraw()` is reached via two permissionless, relayer/gateway-driven paths:
- `onAccept` handling `RedeemEscrow`/`RefundEscrow` requests delivered by any relayer completing a cross-chain intent fill or refund.
- `onGetResponse`, reached after a relayer submits a storage proof for a cancel-from-source flow.

If the escrowed input or fee token is (or becomes, via governance-added token support) a non-standard token that returns `false` on failure instead of reverting, an attacker/solver can engineer a transfer failure (e.g. triggering an internal balance/allowance edge case, a paused state, or a blacklist condition on the beneficiary) so that `success == true` but no tokens are moved. The contract nonetheless marks the order filled/refunded and decrements the escrow permanently. This is a permanent freezing/loss of user or solver funds with no recovery path — the escrowed tokens remain stuck in the contract while the internal accounting says they were already paid out.

### Likelihood Explanation
Likelihood depends on which tokens are supported as intent inputs/outputs or as the protocol fee token on Tron deployments; TRC-20 tokens have historically had more variance in ERC-20 return-value compliance than mainnet ERC-20s (this is also presumably *why* this file avoids `SafeERC20`/`safeTransferFrom` for its escrow release path, unlike its EVM counterpart). Any token onboarded to this gateway that can return `false` instead of reverting (deliberately or via a bug) makes this directly and repeatably triggerable by any party able to influence a transfer's success (e.g. a blacklisted beneficiary address, or a token with insufficient contract balance that fails gracefully).

### Recommendation
Replace all raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` occurrences in `evm/tron/contracts/apps/IntentGatewayV2.sol` (in `withdraw()` for both token and fee payouts, and in the `SweepDust` handler) with OpenZeppelin's `SafeERC20.safeTransfer`, consistent with the rest of the codebase (`IntentsBase.sol`, `HyperFungibleToken.sol`, mainline `IntentGatewayV2.sol`). If a specific TRC-20 on Tron is known to not strictly conform to bool-return semantics, use a balance-delta check (before/after) as is already done for fee-on-transfer tokens in `placeOrder`, rather than relying solely on low-level call success.

### Proof of Concept
1. Governance/owner registers a token `T` on the Tron `IntentGatewayV2` deployment where `T.transfer` returns `false` on failure instead of reverting (e.g., a token with a `transfer` that checks `balanceOf[to] + amount <= type(uint256).max` and returns `false` on overflow, or a blacklist-gated token).
2. A user places a cross-chain order with `T` as an input token; it gets escrowed in `_orders[commitment][T]`.
3. A solver fills the order on the destination chain; Hyperbridge relays a `RedeemEscrow` request back to this Tron gateway.
4. `onAccept` → `withdraw()` is invoked with `beneficiary` set to an address for which `T.transfer` returns `false` (e.g., blacklisted, or one that triggers an internal failure condition) without reverting.
5. `token.call(...)` returns `success = true` (external call executed) even though `T`'s internal transfer logic returned `false` and moved no tokens.
6. `if (!success) revert TransferFailed();` does not trigger; `_orders[body.commitment][token] -= amount;` executes, permanently zeroing out the escrow record.
7. The beneficiary never receives token `T`, and there is no remaining code path to reclaim the escrowed amount — funds are permanently stuck in the contract.
