### Title
Unbounded router approval + unchecked `externalActionMetadata` in `LifiExternalAction`/`ExternalActionSwap` allows draining tokens the balance-equation check never inspects - (File: contracts/external-actions/swaps/LifiExternalAction.sol, contracts/external-actions/swaps/ExternalActionSwap.sol)

### Summary
`ExternalActionSwap.swap` and `LifiExternalAction.callRouter` never bind the actually-swapped `fromToken`/`fromAmount` to the `inputToken`/`inputAmount` derived from the ZK-committed `circomData`. Combined with `TransfererBase.approveUnlimited` granting the router a persistent, effectively infinite `type(uint256).max` allowance per token [1](#0-0) , an attacker can craft router calldata that pulls a *different*, more valuable ERC20 balance sitting in the `LifiExternalAction` contract (already infinitely approved from a prior legitimate swap) while declaring a cheap/dust token as the transaction's `inputToken`. Hinkal's post-transaction balance-equation check only verifies balances for the two tokens listed in `circomData.erc20TokenAddresses`, so the drained token's balance change is never inspected, and the resulting proceeds are wrapped into a new UTXO the attacker controls.

### Finding Description
`ExternalActionSwap.swap` derives `inputToken`/`inputAmount` purely from `circomData.erc20TokenAddresses[0]` / `deltaAmounts[0]` and calls `callRouter` with attacker-supplied `externalActionMetadata`: [2](#0-1) 

`LifiExternalAction.callRouter` only calls `approveUnlimited(inputToken, router)` and then blindly forwards the raw calldata to the router without validating that the router actually consumes `inputToken`/`inputAmount`: [3](#0-2) 

`approveUnlimited` sets a `type(uint256).max` approval for the router that is never revoked and persists indefinitely across all future transactions for that specific token: [1](#0-0) 

Because `swappedAmount` is measured purely as `getERC20OrETHBalance(outputToken) - balanceBefore` on the `LifiExternalAction` contract itself (not tied to what the router actually consumed for `inputToken`), and because `router.call(externalActionMetadata)` executes fully attacker-chosen calldata, an attacker can instruct the router to pull a *different* token Y (for which the router already holds an infinite approval from any prior swap that used Y as `inputToken`) from `LifiExternalAction`'s own balance, swap it for `outputToken`, and have the resulting `swappedAmount` credited to a new shielded UTXO.

Back in `Hinkal.sol.transact`, the balance-equation/slippage check only iterates `circomData.erc20TokenAddresses` — the two tokens the attacker chose to declare (a cheap token Z as input, and `outputToken`): [4](#0-3) 

Token Y's balance loss inside `LifiExternalAction` is never part of this array and is therefore never validated against `slippageValues` or `amountChanges`. The equality broken is: "value moved by [an] external action but not counted in the balance equation" — exactly the class called out for this scan, and directly analogous to the DODO `withdrawToNativeChain`/`_doMixSwap` bug where `params.fromToken` was never checked against the actually-deposited token.

### Impact Explanation
An attacker can mint a shielded UTXO backed by tokens they never deposited, by draining any ERC20 balance sitting in the `LifiExternalAction` contract for which the router has ever received infinite approval (a normal, expected side effect of every prior legitimate swap of that token). This is direct theft of protocol/shared-contract-held funds and results in unbacked shielded value being inserted into the Merkle tree for the attacker, matching the Critical impact criterion "minting shielded value without backing."

### Likelihood Explanation
Likelihood depends on `LifiExternalAction` holding a spendable balance of a token that the router has previously been infinitely approved for (e.g., residual dust from rounding between `inputAmount` approved and the amount the router actually consumes in a prior swap, or any balance intentionally/accidentally left in the contract). This is a normal, recurring state given `approveUnlimited`'s never-revoked design, rather than a rare or attacker-manufactured precondition, making exploitation realistic over the contract's operational lifetime as balances accumulate.

### Recommendation
In `ExternalActionSwap.swap`/`LifiExternalAction.callRouter`, verify that the router calldata's effective consumption is bounded to exactly `inputToken` and does not exceed `inputAmount` — e.g., snapshot and check the pre/post balance of `inputToken` on `LifiExternalAction` itself (not just `outputToken`), and revert if more than `inputAmount` of `inputToken` was consumed. Additionally, avoid persistent unlimited approvals; approve only the exact `inputAmount` needed per swap (`approveERC20Token` already exists in `TransfererBase.sol`) so a stale infinite allowance cannot be leveraged against unrelated balances.

### Proof of Concept
1. Transaction 1 (legitimate): Attacker or any user performs a normal swap with `inputToken = Y` (a valuable token), `inputAmount = 1000`. `LifiExternalAction.callRouter` calls `approveUnlimited(Y, router)`, granting the router `type(uint256).max` allowance for Y. Suppose due to router-side rounding/partial fill, `50` units of `Y` remain unconsumed and stay in `LifiExternalAction`'s balance (or such dust otherwise accumulates over time).
2. Transaction 2 (attack): Attacker calls `Hinkal.transact` declaring `circomData.erc20TokenAddresses = [Z, outputToken]` (Z = a cheap/dust token), with `amountChanges[0] = -1` (deposit 1 wei of Z). `circomData.externalActionData.externalActionMetadata` is crafted LI.FI calldata that instructs the router to `transferFrom(LifiExternalAction, router, 50)` of token `Y` (using the still-valid infinite allowance from Transaction 1) and swap it for `outputToken`.
3. `LifiExternalAction.callRouter` executes `router.call(externalActionMetadata)`; the router pulls `50` of `Y`, swaps it, and `swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore` reflects the proceeds of swapping `Y`, not `Z`.
4. `Hinkal.sol`'s post-check only validates balances for `Z` and `outputToken`, both of which balance correctly (Z: -1 as declared; outputToken: `amountToSendToHinkal` matches the new UTXO amount) — token `Y`'s loss is invisible to the check.
5. Attacker receives a new shielded UTXO for `outputToken` funded by `Y`'s balance that was never theirs, having deposited only 1 wei of `Z`.

```text
    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
```
