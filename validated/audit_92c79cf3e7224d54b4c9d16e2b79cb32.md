Webhook `shop-domain` header is trusted without HMAC binding, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signature only over the raw request body, while the `shop`, `topic`, `api_version`, and `webhook_id` values are read directly from unauthenticated HTTP headers. `Registry.process` validates the HMAC and then forwards these header-derived values, unmodified, to the app's webhook handler. This breaks the intended identity binding: `HMAC(client_secret, raw_body) == header["hmac-sha256"]` is verified, but `request.shop` (used by the handler to determine which merchant/tenant the event belongs to) is never covered by that signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all read straight from headers with no cryptographic tie to the body or to each other: [2](#0-1) 

`HmacValidator.validate` only checks `HMAC(secret, to_signable_string) == hmac`: [3](#0-2) 

`Registry.process` performs this HMAC check and then immediately trusts `request.shop`/`request.topic`/etc. to build `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The invariant that should hold is: *the `shop` value delivered to the handler must be cryptographically bound to the same signed message as the body it is paired with.* Instead, the equality actually enforced is `HMAC(secret, body) == hmac`, decoupled from `shop`. Since `shop-domain`, `topic`, `api-version`, and `webhook-id` headers are excluded from the signable string, any request with a *valid* `(body, hmac)` pair — for example one an attacker legitimately received for their own store's webhook, or one replayed/relayed from a public source — can be POSTed to the app's webhook endpoint with an arbitrary `shop-domain` header substituted, and it will still pass `HmacValidator.validate`. This is the same class of bug as the analog report: two values that are supposed to be tied together (here, "shop claimed" vs. "shop the signed payload legitimately belongs to") are not actually bound by the check performed, letting an attacker satisfy the check while supplying a value for the unbound field of their choosing.

### Impact Explanation
If a host application uses `request.shop` (surfaced as `WebhookMetadata#shop`) to select which merchant's record to update, delete, or resync (a documented and expected use per this gem's own `docs/usage/webhooks.md` pattern), an attacker who can obtain any one valid `(raw_body, hmac)` pair — including from their own shop's genuine webhook deliveries — can relabel it with a different `shop-domain` header and have the app process it as if it originated from a different, victim tenant. This crosses a tenant boundary using the app's own trusted webhook path, matching the "cross-tenant access" impact category, without requiring `api_secret_key`, an access token, or any other credential.

### Likelihood Explanation
Likelihood is moderate: the attacker needs at least one valid signed webhook body (trivially obtainable by owning any store that installs the target app, or by intercepting/replaying a delivery to their own endpoint), and the target app's public webhook URL. No secret material is required. The main constraint is that the exploit is only impactful if the host app dispatches/branches its business logic using `WebhookMetadata#shop` — which is exactly the field this gem exposes to callers as the trusted tenant identifier, per `webhook_handler.rb` and the docs.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the HMAC-covered signable string (or otherwise cryptographically bind them to the body, e.g., via a MAC over `headers + body`), so that `Utils::HmacValidator.validate` fails if any of these fields are altered independently of the signature. At minimum, document and/or enforce that `WebhookMetadata#shop` must not be trusted as an unbound identity claim, or cross-check it against the session/shop the app expects for that webhook subscription.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, or otherwise captures one valid webhook delivery `(raw_body, X-Shopify-Hmac-Sha256: H)` sent to their webhook endpoint.
2. Attacker crafts a new HTTP POST to the app's public webhook endpoint using the same `raw_body` and `hmac-sha256` header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)` — this passes because `to_signable_string` only checks `raw_body`, which is unchanged. [5](#0-4) 
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)` and, if it uses `shop` to locate/update tenant data, performs the action against the victim's tenant using data or intent controlled by the attacker.
