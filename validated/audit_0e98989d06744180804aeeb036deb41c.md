Audit Report

## Title
Missing slippage protection in `SwapFirstAssetTrader::refund_weight` XCM asset swap - (File: cumulus/primitives/utility/src/lib.rs)

## Summary
`SwapFirstAssetTrader::refund_weight` calls `SwapCredit::swap_exact_tokens_for_tokens(vec![Target::get(), refund_swap_asset], refund, None)` with `amount_out_min` hardcoded to `None`, while `buy_weight` uses the bounded `swap_tokens_for_exact_tokens`. Because `pallet-asset-conversion`'s `do_swap_exact_credit_tokens_for_tokens` skips its minimum-output `ensure!` check whenever `amount_out_min` is `None`, the refund swap executes at whatever price the pool happens to be at, with no lower bound and no post-swap verification by the caller.

## Finding Description
`SwapFirstAssetTrader::buy_weight` swaps the user's asset into `Target` using `swap_tokens_for_exact_tokens`, whose "exact output, bounded input" semantics inherently protects the trader/user from unfavorable pricing on that leg [1](#0-0) . In contrast, `refund_weight` swaps the unused `Target` back to the originally-paid asset via `swap_exact_tokens_for_tokens` with `amount_out_min` fixed to `None` [2](#0-1) . Passing `None` causes `do_swap_exact_credit_tokens_for_tokens` to bypass the `amount_out >= amount_out_min` check entirely (`amount_out_min.map_or(true, |a| amount_out >= a)` evaluates to `true` when `amount_out_min` is `None`) [3](#0-2) . The subsequent code path on success simply wraps whatever `credit_out`/`refund_in_target` came back into the refund asset without any independent sanity check on the amount received [4](#0-3) . This confirms the claim's description of the exact code path, root cause, and absence of a caller-side check.

The trader is not merely theoretical scaffolding — it is actually wired into production runtime XCM configurations, confirmed by usage matches in `cumulus/parachains/runtimes/assets/asset-hub-rococo/src/xcm_config.rs`, `cumulus/parachains/runtimes/assets/asset-hub-westend/src/xcm_config.rs`, `cumulus/parachains/runtimes/testing/penpal/src/xcm_config.rs`, and `substrate/frame/staking-async/runtimes/parachain/src/xcm_config.rs`, so the vulnerable path is reachable by any unprivileged user submitting XCM messages that overpay fees in a non-`Target` asset through those runtimes' asset-conversion pools.

## Impact Explanation
This is a genuine missing-slippage-bound defect: an attacker capable of shifting the `Target`/`refund_swap_asset` constant-product pool's reserves immediately before a victim's refund swap executes can cause the refund to be settled at a manipulated price, extracting value from the fee-payer/pool at the fee-payer's expense. The loss is inherently bounded by the size of the unused-weight refund (a small fraction of the total prepaid fee), which limits severity relative to a full-balance-draining bug, but the missing bound is a real, exploitable accounting gap distinct from the intentionally-bounded `buy_weight` leg.

## Likelihood Explanation
Exploitation requires an attacker to execute a pool-skewing swap (and its reversal) around the same block/pool-state in which the victim's refund executes — i.e., a sandwich/front-run against the shared AMM pool, which is feasible for any capital-holding, unprivileged actor able to submit ordinary swap extrinsics against `pallet-asset-conversion`, though it requires liquidity and timing precision. Reachability is confirmed for at least Asset Hub Rococo/Westend and the Penpal test parachain, where `SwapFirstAssetTrader` is actually configured as part of the XCM fee-payment trader stack.

## Recommendation
Compute a `amount_out_min` for the `refund_weight` swap (e.g., via `QuotePrice::quote_price_exact_tokens_for_tokens` at refund time with a configurable slippage tolerance) instead of passing `None`, and treat a swap failure or below-minimum result the same way the existing `Err` branch already handles it — falling back to crediting `total_fee` and skipping the refund rather than accepting an unbounded-slippage result.

## Proof of Concept
1. Configure a runtime (mirroring Asset Hub Rococo/Westend or Penpal) with `SwapFirstAssetTrader` as an XCM `WeightTrader` and a `pallet-asset-conversion` pool between `Target` and a `refund_swap_asset`.
2. An unprivileged actor swaps a large amount against that pool to skew reserves immediately before a victim's XCM message (which overpays fees in `refund_swap_asset`) is processed in the same block/pool state.
3. `refund_weight` executes `swap_exact_tokens_for_tokens(..., None)`; since `amount_out_min` is `None`, `do_swap_exact_credit_tokens_for_tokens`'s minimum-output check is a no-op, so the refund is credited at the skewed price.
4. The attacker reverses the pool-skewing swap, netting the value differential (minus AMM fees) at the fee-payer's expense — a fork/integration test asserting refund value before/after an interleaved pool-skewing swap-and-reverse would demonstrate the loss.
