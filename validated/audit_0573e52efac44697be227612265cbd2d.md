### Title
Arbitrary-call `ops[]` in `EmporiumUpgradeable.runAction` lets an attacker drain any ERC20 balance the contract holds by simply excluding that token from the caller's own `circomData.erc20TokenAddresses` - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction` only computes `balancesBefore`/`balancesAfter` and enforces `balanceChange >= 0` for the token addresses listed in the caller-supplied `circomData.erc20TokenAddresses` array, while the `ops[]` array executed inside the same call can make an arbitrary `op.endpoint.call(op.callData)` — with `Emporium` itself as `msg.sender` — against **any** address, including any ERC20 token Emporium happens to hold that is not in that array. This lets any unprivileged caller move out balances of undeclared tokens with zero accounting, zero UTXO minted, and zero nullifier/root check.

### Finding Description
The claimed invariant is: `tokens leaving Emporium via ops == -deltaAmountChanges[i]` for every token Emporium holds. This does not hold, because the accounting loop is scoped strictly to the attacker's own declared token list.

- `Hinkal.transact` lets any caller supply their own `CircomData`/`Dimensions` and their own proof for their own UTXOs (`contracts/Hinkal.sol:30-65`).
- `HinkalHelper.dimensionsCheck` only requires `circomData.erc20TokenAddresses.length == dimensions.tokenNumber` [1](#0-0) . There is no requirement that this list include every token an external action contract currently holds — it is entirely attacker-chosen for a given call.
- In `EmporiumUpgradeable.runAction`, `balancesBefore`/`balancesAfter` are computed only via `getBalancesForArray(circomData.erc20TokenAddresses)`, and the `balanceChange < 0` revert / `handleOut` UTXO-minting logic only iterates over that same array [2](#0-1) .
- Inside the same function, `stack.ops[]` (decoded from `circomData.externalActionData.externalActionMetadata`, fully attacker-controlled and unconstrained by the circuit) is executed with `op.endpoint.call{value: op.value}(op.callData)` for any `op.endpoint`/`op.callData`, the only restriction being a selector check against `IHinkalWallet.callHinkalWallet`/`doSendToRelay` [3](#0-2) . Because this call is made directly from `EmporiumUpgradeable`, `msg.sender` for that call is `Emporium`.

Exploit: attacker calls `Hinkal.transact()` with `externalActionId` = Emporium's id, a valid proof for their own (possibly zero-value) UTXOs, and `circomData.erc20TokenAddresses` that does **not** include `strandedToken` (the ERC20 whose balance Emporium currently holds, e.g., left-over dust from any prior action, partial-fill remainder from any other user, or fee-token residue). Their `EmporiumStack.ops` contains one operation: `endpoint = strandedToken`, `callData = abi.encodeWithSelector(IERC20.transfer.selector, attacker, amount)`. Since `strandedToken` is absent from `erc20TokenAddresses`, `balancesBefore`/`balancesAfter` never observe it, `handleOut` never runs for it, and no UTXO/nullifier is ever created for the stolen `amount`. `verifyWallet` only checks/marks `usedMessages` and, when `stack.signerAddress == address(0)`, performs no signature validation of `ops` at all [4](#0-3) , so an attacker acting on their own behalf (no wallet, `signerAddress = address(0)`) can freely choose `ops` with no signature check to bypass at all.

None of `performHinkalChecks` (originalSender/relay check, `dimensionsCheck`, `checkOnchainCreation`), `verifyProof`, `rootHashExists`, or the circuit's `inTotal + amountChanges === outTotal` constraint prevent this, because they all operate over the attacker's self-chosen `erc20TokenAddresses`/`amountChanges` for their own UTXOs — none of them are aware of, or constrain, balances of tokens absent from that list, nor do they constrain the content of `ops[]`.

### Impact Explanation
This is direct, repeatable theft of ERC20 balances held by `EmporiumUpgradeable` that belong to other parties (other users' in-flight/residual funds, protocol/relay fee balances, or leftover swap remainders) with no nullifier ever spent and no UTXO ever created to represent the stolen value — i.e., value leaves the contract that was never accounted for anywhere in the Hinkal ledger. This matches the Critical category ("direct theft of shielded or in-flight user funds").

### Likelihood Explanation
Precondition: `EmporiumUpgradeable` must hold a non-zero balance of some ERC20 token at the time of the attack — plausible any time it acts as an intermediary for swaps/multi-step DeFi ops, or through any dust/remainder left by prior calls. No privileged role is required; the attacker only needs to generate a valid proof for their own (possibly trivial/zero) UTXO set and craft `EmporiumStack.ops` themselves. Cost is a single `transact()` call; repeatable every time Emporium holds any drainable balance not referenced in the attacker's chosen `erc20TokenAddresses`.

### Recommendation
Do not allow `ops[]` to target arbitrary endpoints/tokens unconstrained by the declared token set. Either (a) restrict `op.endpoint` to a fixed allow-list of routers/wallets (never raw ERC20 token contracts of tokens Emporium custodies), or (b) snapshot and diff balances for the full set of tokens Emporium can ever hold (not just the caller-declared subset) before/after `ops` execution, or (c) require that any token whose balance changes during `ops` execution must be present in `circomData.erc20TokenAddresses`, reverting otherwise (e.g. via a global registry of tracked tokens checked post-hoc, or ERC20 transfer hooks/allowance-based execution only).

### Proof of Concept
Foundry test plan:
1. Seed `EmporiumUpgradeable` with a nonzero balance of `TokenX` via a legitimate two-tx sequence (e.g., a prior `transact()` call whose `ops` leave a small unspent remainder of `TokenX`, or simply `TokenX.transfer` to Emporium simulating dust from a partial swap fill by another user).
2. As `attacker` (unprivileged EOA), build `circomData` with `erc20TokenAddresses` containing only an unrelated `TokenY` (or empty/zero-value UTXOs), `amountChanges = [0]`, generate a valid proof for a no-op transaction (`inTotal == outTotal`, `amountChanges[i] = 0`).
3. Set `circomData.externalActionData.externalActionId` to Emporium's id and `externalActionMetadata` to an `EmporiumStack` with `signerAddress = address(0)` and one `EmporiumOperation{ endpoint: address(TokenX), invokeWallet: false, value: 0, callData: abi.encodeWithSelector(IERC20.transfer.selector, attacker, amount) }`.
4. Call `Hinkal.transact(a, b, c, dimensions, circomData)`.
5. Assert: `TokenX.balanceOf(attacker)` increased by `amount`; `TokenX.balanceOf(Emporium)` decreased by `amount`; no nullifier for `TokenX` was inserted (`insertNullifiers` untouched for that token) and no commitment/UTXO of `TokenX` with `amount` was ever created — i.e., total shielded ledger value for `TokenX` is unchanged while actual token balance dropped by `amount`, proving the divergence.
