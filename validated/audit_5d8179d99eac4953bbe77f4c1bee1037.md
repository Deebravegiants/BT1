### Title
Webhook `shop` tenant identity is trusted from an unauthenticated header while only the raw body is HMAC-verified - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook by HMAC-validating only the raw request body, then dispatches the handler using a `shop` value read straight from an unauthenticated HTTP header. This breaks the intended binding `HMAC-authenticated bytes == shop identity acted upon`, letting anyone who can produce one valid `(body, hmac)` pair signed with the app's secret (e.g., a webhook legitimately delivered to their own installed shop) replay it while swapping the `x-shopify-shop-domain` header to any other tenant, causing the app to process attacker-controlled data under a victim shop's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` values are all pulled directly from HTTP headers, which are not part of the signed content: [2](#0-1) 

`HmacValidator.validate` calls `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the received HMAC — for a `Request`, that signable string is the body alone, so the `shop` header is never covered by the signature: [3](#0-2) 

`Registry.process` only checks this body-only HMAC, then immediately builds `WebhookMetadata` using `request.shop` — the unauthenticated header value — and hands it to the app's registered handler: [4](#0-3) 

The documented handler contract explicitly tells host apps to treat `data.shop` as the "shop domain of the webhook" and to key their business logic (e.g., background jobs, per-tenant records) off it: [5](#0-4) 

Because the `api_secret_key` is shared across all shops for a given app (it's an app-level secret, not a per-shop secret), any merchant who installs the app can capture a legitimate `(raw_body, x-shopify-hmac-sha256)` pair for their own shop — a value validly signed with the app's secret. That same attacker can then submit that unchanged `(body, hmac)` to the app's webhook endpoint while setting `x-shopify-shop-domain` to a victim shop's domain. `HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` will invoke the handler with `shop` equal to the victim's domain and `body` equal to attacker-controlled content, i.e., cross-tenant data injection under Shopify's own trust signal.

### Impact Explanation
This is a cross-tenant identity confusion: the gem's own verification step (`HmacValidator.validate`) gives host applications a false assurance that the entire request — including the shop attribution — came from Shopify for that specific shop, when in fact only the body bytes are authenticated. Any host application that follows the gem's documented pattern (trust `data.shop` from `WebhookMetadata`) is exposed to attacker-controlled webhook payloads being attributed to and processed against a different merchant's tenant/session, satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Likelihood is moderate-to-high for apps with any multi-merchant install base: the attacker needs only to be a legitimate (even trial) merchant of the target app to obtain one valid signed webhook body/hmac pair, then can freely relabel the `shop-domain` header on replay — no knowledge of `api_secret_key` is required, and no privileged access is needed.

### Recommendation
Include the tenant-identifying fields (`shop`, `topic`, `webhook_id`, `api_version`) inside the HMAC-signed material, or otherwise cryptographically bind the header-derived `shop` to the verified body (e.g., derive/validate `shop` from a value that is itself covered by the signature) so that `HmacValidator.validate` cannot succeed unless the reported shop matches the actual signed request.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and captures a legitimate webhook delivery: raw body `B` and header `x-shopify-hmac-sha256: H` (valid, since it was really sent by Shopify and signed with the app's `api_secret_key`), along with `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker POSTs to the app's webhook endpoint reusing body `B` and header `x-shopify-hmac-sha256: H` unchanged, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers, `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only and it matches `H` → validation passes.
4. `Registry.process` builds `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)` and invokes the app's handler, which acts on `B` as if it were legitimately delivered for `victim-shop.myshopify.com`. [4](#0-3)

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
