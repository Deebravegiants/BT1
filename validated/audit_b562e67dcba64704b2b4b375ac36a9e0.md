### Title
Webhook `shop`/`topic`/`webhook_id` identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then dispatches the handler using `shop`, `topic`, `webhook_id`, and `api_version` values that are read straight from HTTP headers and are never included in the signed payload. This breaks the identity binding: **bytes verified by the HMAC ≠ bytes the handler trusts as the tenant identity**.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

All the other attributes exposed by `Request` — `shop`, `topic`, `webhook_id`, `api_version` — are parsed directly from headers with no cryptographic binding to the HMAC: [2](#0-1) 

`Registry.process` validates only the body signature, then immediately hands off the unverified header-derived `shop`/`topic`/`webhook_id` to the app's handler: [3](#0-2) 

Because `HmacValidator.validate` calls `verifiable_query.to_signable_string` (body only) to compute the signature, the `hmac` check does not authenticate which shop or topic the body belongs to — only that the given body bytes were HMAC'd with the app's secret at some point: [4](#0-3) 

An attacker who has ever legitimately received a webhook for their **own** shop/install (a normal, unprivileged installer of the app) holds a body+HMAC pair that will pass `validate()` unconditionally, regardless of the `shopify-shop-domain`/`shopify-topic`/`shopify-webhook-id` headers sent alongside it. They can replay that same body with forged `shop-domain`/`topic`/`webhook-id` headers pointed at a different, victim tenant, and `Registry.process` will invoke the handler as if the (forged) victim shop sent that (forged) topic's data — i.e., `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built from attacker-controlled, unauthenticated header values.

### Impact Explanation
This is a cross-tenant identity confusion: the gem asserts to consuming applications that a webhook "came from shop X for topic Y" while cryptographically only proving "this body was HMAC'd correctly," with no guarantee that X or Y are authentic. Applications that key their persistence/authorization decisions off `WebhookMetadata#shop` (as the gem's own docs instruct) can be made to apply another tenant's webhook body under an attacker-chosen shop domain, or process one topic's payload as another — a cross-tenant access vector.

### Likelihood Explanation
Exploitation requires only: (1) the ability to obtain one valid signed webhook body for any shop (trivial for any legitimate/attacker-controlled shop that installs the app and receives one webhook), and (2) delivering a POST to the app's own webhook endpoint with attacker-controlled headers, which the gem's `Request.new` accepts from raw headers with no origin/IP restriction. No `api_secret_key`, access token, or privileged account is required beyond running one's own shop install — this fits the "unprivileged internet user" threat model.

### Recommendation
Bind the tenant/topic identity into the signed material, or otherwise cryptographically tie the header-derived `shop`, `topic`, and `webhook_id` to the HMAC before they are trusted by `Registry.process`/`WebhookMetadata`. At minimum, document and enforce that `shop`, `topic`, and `webhook_id` must be treated as unauthenticated hints unless cross-checked against an out-of-band source (e.g., confirm the `shop` is one which the recipient app has an active, matching session/installation for that specific webhook subscription id), and consider incorporating these header values into `to_signable_string`'s comparison surface where feasible.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com`; capture one legitimate webhook delivery — raw body `B` and header `x-shopify-hmac-sha256: H` (valid for `B` under the app's `client_secret`).
2. Send a POST to the app's webhook endpoint with body `B` and header `H` unchanged, but set `x-shopify-shop-domain: victim-shop.myshopify.com` and/or `x-shopify-topic: orders/create` (a higher-value topic than originally received).
3. `Utils::HmacValidator.validate(request)` ( [5](#0-4) ) succeeds because it only checks `B` against `H`.
4. `Registry.process` dispatches the handler with `shop: "victim-shop.myshopify.com"` and the forged `topic`, both taken verbatim from attacker-supplied headers ( [6](#0-5) ), causing the app to process attacker-supplied data under the victim's tenant identity.
