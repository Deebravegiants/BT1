### Title
Cross-chain replayable calldata authorization signature in `HyperFungibleToken::on_accept` due to missing domain binding - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`on_accept` executes an attacker/relayer-supplied `runtime_call` on behalf of `beneficiary` if the embedded `SubstrateCalldata.signature` verifies over `(nonce, runtime_call).encode()`. This signed payload contains no chain-specific domain separator (no genesis hash, no spec/tx version, no state-machine/chain id, no pallet instance identifier), unlike normal Substrate extrinsic signing which binds `SignedExtra` data including the genesis hash and spec version. The only "freshness" input is `frame_system::account_nonce(beneficiary)`.

### Finding Description
In `on_accept` [1](#0-0) , when `message.data` is non-empty the pallet decodes `SubstrateCalldata` from the ISMP request body and, if a `signature` is present, verifies it against the message `payload = (nonce, substrate_data.runtime_call.clone()).encode()` for Ed25519/Sr25519, or against a keccak256/Ethereum-prefixed digest of the same payload for Ecdsa. On success it dispatches `runtime_call` as `RawOrigin::Signed(beneficiary)`.

Because the signed payload is exactly `(account_nonce, call_bytes)` — with no genesis hash, chain/state-machine identifier, source contract address, or pallet-instance salt folded in — the message is indistinguishable to the signer's cryptographic scheme between any two deployments of this pallet (or any other consumer that hashes `(nonce, call).encode()` the same way) that share the same `AccountId` and happen to have the same account nonce. Substrate `AccountId32`/`AccountId20` values are portable across chains (derived purely from the public key), and the hyper-fungible-token pallet is designed to be embedded by many different parachains bridging via Hyperbridge, all built from the same runtime/pallet code. A signature a user creates to authorize a call on one deployment (e.g., a testnet, or a second chain running the identical pallet + call-index layout) is fully valid should the same `(nonce, call)` bytes reach `on_accept` on a different chain deployment where the beneficiary account exists with a matching nonce — the ISMP transport layer (source/dest/commitment binding) protects the *transport* of the request, but nothing in the *signed payload itself* ties the authorization to a specific chain instance. This is the same root-cause pattern as the OctoberCMS advisory: an encrypted/signed value is not bound to the specific context (cookie name ↔ chain/pallet identity) it is meant to authorize, so a value valid in one context can be replayed in another where the underlying primitive (signature/decryption) still succeeds.

Additionally, unlike a normal signed extrinsic (which frame_system's `CheckNonce`/`CheckGenesis`/`CheckSpecVersion` SignedExtensions bind together), this bespoke authorization path is hand-rolled and omits all chain-binding data, relying solely on the account nonce as replay protection — which is only unique per-account-per-chain, not globally unique across the many chains this pallet may be deployed to.

### Impact Explanation
An attacker/relayer who observes (or is handed) a valid `SubstrateCalldata` (nonce, call, signature) tuple destined for one hyper-fungible-token deployment can craft an ISMP `PostRequest` body with the identical `data` field addressed to any other chain running the same pallet where the beneficiary's `AccountId` and current nonce coincide. If accepted, this results in an unauthorized dispatched call under `RawOrigin::Signed(beneficiary)` — i.e., forged message delivery / unauthorized app action executed against a user's account on a chain/context they never intended to interact with, potentially moving funds or invoking other privileged-for-that-account dispatchables. This satisfies "unauthorized app action" / "forged message delivery" impact criteria.

### Likelihood Explanation
Reachable by any relayer or unprivileged party who can construct/submit an ISMP `PostRequest` whose body decodes into `HftMessage`/`SubstrateCalldata` — this is exactly the "unprivileged... token bridger" surface named in scope. The main precondition (same `AccountId` + matching nonce present on a second deployment of the identical pallet) is realistic given key reuse across Substrate chains and that this pallet is shipped as a reusable SDK component intended for multiple parachain deployments.

### Recommendation
Bind the signed payload to the specific chain/pallet instance and message: include the local genesis hash (or state-machine identifier), a pallet-instance-specific domain separator, and ideally the ISMP request's `source`/`from` (originating contract) and commitment hash in the data hashed/signed, mirroring the fix pattern from the referenced advisory (bind the encrypted/signed value to the context it authorizes).

### Proof of Concept
1. On chain A (running `pallet-hyper-fungible-token`), user with keypair K signs `payload = (nonce=5, call=Balances::transfer_keep_alive{dest, value}).encode()`, producing `SubstrateCalldata { signature: Some(sig), runtime_call: call_bytes }`, embedded in an ISMP `PostRequest.body` as `Message.data`.
2. This request is delivered and executed on chain A: `on_accept` verifies `sig` against `(5, call_bytes)` and dispatches the call as `beneficiary` (K's `AccountId`), then increments the nonce.
3. Chain B runs the identical pallet/runtime layout and the same `AccountId` (same public key) happens to also be at nonce 5 there (e.g., a fresh/parallel deployment, testnet mirroring mainnet state, or any scenario where nonces align).
4. A relayer copies the exact same `data` bytes (nonce=5, call_bytes, sig) into a `PostRequest` body destined for chain B's HFT contract/pallet mapping.
5. `on_accept` on chain B verifies the same signature against the same `(5, call_bytes)` payload — which passes, since nothing in the signed bytes differentiates chain A from chain B — and dispatches the call as `beneficiary` on chain B without the user's consent for that chain.
