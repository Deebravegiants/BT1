### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant payload injection - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` from HTTP headers, but `to_signable_string` (used by `Utils::HmacValidator.validate`) signs only the raw request body. The identity binding "HMAC covers the same bytes that are trusted as the tenant identifier" is broken: `hmac_valid ⇏ shop == authenticated_shop`.

### Finding Description
`Webhooks::Request#hmac` reads the `X-Shopify-Hmac-Sha256` header, and `Webhooks::Request#to_signable_string` returns `@raw_body` only [5](#0-4) . `Utils::HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it to the supplied `hmac` value [6](#0-5) . This proves the shop-domain header is never part of the signed material.

`Webhooks::Registry.process` gates on this same HMAC check and then unconditionally trusts `request.shop` to build the `WebhookMetadata` handed to the app's handler: `raise ... unless Utils::HmacValidator.validate(request)` followed by `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` [3](#0-2) . Because `shop` (and `topic`/`webhook_id`) are pulled straight from headers that sit outside the HMAC's protected scope, a party who possesses one authentic signed webhook body (e.g., a merchant who installed the app and received a legitimately-signed webhook for their own shop) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header. `HmacValidator.validate` will still pass because it only re-derives the HMAC from `@raw_body`, and the app-level handler will process the (genuinely signed) payload under an attacker-chosen tenant identity, since the gem hands `request.shop` to the handler as the trusted tenant key.

### Impact Explanation
This breaks the tenant/identity boundary the gem is responsible for: the gem's own `Registry.process` is the code that asserts "HMAC valid ⇒ safe to trust `request.shop`/`request.topic`" to the handler, when in fact only the body bytes are authenticated. Any downstream host application that uses `data.shop` (as documented/intended by this gem's `WebhookMetadata`) to select which tenant's records to write to is exposed to cross-tenant data injection/corruption using a single legitimately-obtained signed webhook. This matches the Critical impact category of cross-tenant access, since the gem itself supplies the ostensibly-verified tenant identifier without it being covered by the signature it validates.

### Likelihood Explanation
Exploitation requires the attacker to have received at least one genuine webhook (any topic) for a shop they control — a normal outcome of installing the app as an ordinary merchant, no special privilege, no leaked secret needed. They only need to resend the same raw body/HMAC to the app's public webhook endpoint with a different `shop-domain` header, which is trivial HTTP header manipulation. Likelihood is High/Medium depending on whether the host app keys any state off `data.shop` (which the gem's documented `WebhookMetadata` design encourages).

### Recommendation
Include the trusted identity fields (at minimum `shop`, and ideally `topic`) inside `to_signable_string`'s protected material, or otherwise cryptographically bind the header-derived `shop` value to the payload before trusting it in `Registry.process`. Since Shopify's own HMAC scheme signs only the body, the gem should instead treat `request.shop`/`request.topic` as unauthenticated until corroborated — e.g., by only accepting shop values for webhooks that the host application registered per-shop, or by validating that `request.shop`'s registered webhook subscription id matches `request.webhook_id`. At minimum, this trust boundary should be explicitly documented so host applications know `data.shop` is not covered by the HMAC and must be independently corroborated before being used as a tenant key.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker-shop.myshopify.com` and lets Shopify send a legitimate webhook (e.g., `orders/create`) to the app's endpoint; attacker records the raw body and the `X-Shopify-Hmac-Sha256` header value (both are visible to them as the shop owner/network intermediary of their own store, no secret needed).
2. Attacker replays the exact same `raw_body` and `hmac` header to the same webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Webhooks::Request.new` parses the headers, `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, raw_body)` — unchanged — and passes [7](#0-6) .
4. `handler.handle` receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body, despite the payload never having been signed for that shop [8](#0-7) .
