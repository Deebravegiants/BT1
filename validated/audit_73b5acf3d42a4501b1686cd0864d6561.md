Confirmed: `Session.from` derives `session.id` deterministically from public data — `"offline_#{shop}"` for offline tokens or `"#{shop}_#{associated_user.id}"` for online tokens [1](#0-0) . That id is used verbatim as the `SessionCookie` value in `Oauth.validate_auth_callback` for non-embedded apps [2](#0-1) , and `SessionCookie` is a plain `T::Struct` with no digest, HMAC, or signature field [3](#0-2) . `SessionUtils.cookie_session_id` then returns whatever the caller-supplied cookie hash contains for that key, with no validation against the request's shop or any cryptographic check [4](#0-3) , and for non-embedded apps this is the sole credential path (`current_session_id`'s `else` branch only checks presence of the cookie, never its integrity) [5](#0-4) .

### Title
Predictable, unsigned cookie session id enables cross-tenant session hijack - (File: lib/shopify_api/utils/session_utils.rb)

### Summary
For non-embedded apps, `SessionUtils.cookie_session_id` returns the raw `shopify_app_session` cookie value as the trusted session-store lookup key with no MAC, signature, or shop binding. Because `Session#id` (the value placed in that cookie) is deterministically derived from public data (`offline_#{shop}` or `#{shop}_#{user_id}`), an attacker who knows or guesses a victim shop's domain can set that exact string as their own cookie and cause the host app to resolve and use the victim's stored session/access token.

### Finding Description
The broken binding: `cookie_session_id(cookies) == cookies['shopify_app_session']` should imply `cookies['shopify_app_session']` was issued by this app's server to the requesting party for their own shop; instead the function simply returns the attacker-supplied bytes unchanged [4](#0-3) . There is no MAC/signature check anywhere in the call path: `current_session_id`'s non-embedded branch (and the embedded fallback branch) only verifies the cookie key is *present*, not that its value is authentic [6](#0-5) .

Root cause: the session id placed in this cookie by `Oauth.validate_auth_callback` (`session.id`) is not a random opaque token — it is deterministically computed as `"offline_#{shop}"` or `"#{shop}_#{associated_user.id}"` from the OAuth response [1](#0-0) , and this exact string is written to the plaintext `SessionCookie` sent back to the browser [2](#0-1) . `SessionCookie` is a bare struct with `name`, `value`, `expires` and no cryptographic field [3](#0-2) , and the documented integration pattern sets it as a plain (non-Rails-signed/encrypted) `secure, http_only` cookie [7](#0-6) . `http_only`/`secure` only block JS access and require TLS in transit — they do not stop the cookie's owner (the attacker, using their own browser or HTTP client) from setting an arbitrary literal value for their own request.

Exploit flow: Attacker installs the app on their own shop (or simply learns a victim's public `*.myshopify.com` domain and, for online sessions, a guessable Shopify staff user id). Attacker sends a request to any authenticated route with `Cookie: shopify_app_session=offline_victim-shop.myshopify.com`. `cookie_session_id` returns this string verbatim as the session id; per this library's documented model, the host app (as instructed by `docs/usage/oauth.md`, since this gem's session persistence is deprecated and delegated entirely to the app) looks up its session store by this id and retrieves the victim's stored `Session` (including `access_token`), then uses it to serve the attacker's request. `Session#expired?`, `AuthScopes#covers?`, and the OAuth `state` comparison are irrelevant here — they gate the *initial* OAuth handshake and per-scope checks on a session already resolved, not the trustworthiness of the id used to resolve which merchant's session to load in the first place [8](#0-7) .

### Impact Explanation
An attacker who can send an HTTP request with an attacker-chosen `shopify_app_session` cookie value can cause the host app to resolve and act using another merchant's stored session/access token — reading or mutating that merchant's Shopify data. This is a full cross-tenant compromise limited only by the attacker's ability to guess/know the victim's shop domain (public) and, for online sessions, the associated user id. It is repeatable against any victim shop whose offline (or online) session id can be derived, and matches the Critical cross-tenant access class.

### Likelihood Explanation
Preconditions: app configured `is_embedded: false` (or embedded app falling back to cookie auth) and following the documented cookie-based non-embedded flow, which is the flow explicitly documented and supported by this gem. Attacker cost is trivial — no secrets, no MITM, just knowledge of a target shop domain. Offline session ids require no guessing beyond the shop's public domain name; online session ids additionally require a guessable numeric associated-user id, which lowers but does not eliminate feasibility.

### Recommendation
Do not use a deterministic, human-readable string derived purely from `shop`/`user_id` as the bearer value stored in the client cookie. Either (a) sign/MAC the cookie value (e.g., HMAC with `api_secret_key`, verified before use) so `cookie_session_id` rejects tampered/forged values, or (b) issue a cryptographically random opaque session identifier (e.g., `SecureRandom.uuid`, as already used as the default in `Session#initialize`) as the cookie value while keeping the derived `offline_#{shop}` id only as an internal storage key never exposed to the client, and additionally bind the cookie to the shop being requested.

### Proof of Concept
```ruby
# test/utils/session_utils_test.rb (new test, WebMock not required)
def test_cookie_session_id_returns_predictable_attacker_supplied_id_unverified
  ShopifyAPI::Context.stubs(:embedded?).returns(false)

  victim_shop = "victim-shop.myshopify.com"
  forged_offline_id = "offline_#{victim_shop}"

  attacker_supplied_cookies = {
    ShopifyAPI::Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME => forged_offline_id,
  }

  # Binding under test: cookie_session_id(cookies) should equal the value the
  # *server* legitimately issued to the requester for their own shop, not an
  # attacker-chosen literal for a different shop.
  resolved_id = ShopifyAPI::Utils::SessionUtils.current_session_id(nil, attacker_supplied_cookies, false)

  # No MAC/signature check anywhere rejects this — it is returned verbatim.
  assert_equal(forged_offline_id, resolved_id)

  # Demonstrate id predictability from Session.from without any secret:
  access_token_response = ShopifyAPI::Auth::Oauth::AccessTokenResponse.from_hash(
    { access_token: "victim-token", scope: "read_products" },
  )
  victim_session = ShopifyAPI::Auth::Session.from(shop: victim_shop, access_token_response: access_token_response)

  # Attacker could derive this id purely from the public shop domain, no secret needed.
  assert_equal(victim_session.id, resolved_id)
end
```
This shows the id an attacker can forge with zero secrets (`offline_#{public_shop_domain}`) matches exactly the id/key a legitimate victim session would be stored/looked up under, and that `cookie_session_id`/`current_session_id` perform no verification before trusting it.
