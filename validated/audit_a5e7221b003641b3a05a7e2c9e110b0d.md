### Title
Webhook shop-domain header not covered by HMAC allows cross-tenant webhook spoofing via body replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` reads the tenant identity (`shop`) straight from the `x-shopify-shop-domain` HTTP header, but the HMAC signature that this gem verifies only covers the raw request body, never the headers. This breaks the required identity binding `hmac == HMAC(secret, body || shop_header)`, allowing an attacker who legitimately receives a webhook for their own shop to replay the same body/HMAC pair while substituting an arbitrary victim shop domain in the header, causing the host app's webhook handler to process attacker-controlled data as if it originated from a different, arbitrary tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is derived exclusively from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the signature purely against `verifiable_query.to_signable_string` (i.e., the raw body): [3](#0-2) 

`Registry.process` verifies only this body-based HMAC and then trusts `request.shop` (from the unauthenticated header) to build the `WebhookMetadata` passed to the host app's handler: [4](#0-3) 

The identity binding the gem is expected to enforce is:
`hmac == HMAC(client_secret, raw_body)` **and** `shop == authenticated tenant that produced raw_body`

But the actual binding enforced is only:
`hmac == HMAC(client_secret, raw_body)`

`shop` is parsed out-of-band from a header that carries no cryptographic linkage to `raw_body` or to the HMAC. Any party who can obtain one valid `(raw_body, hmac)` pair for their own shop (trivial — install the app on an attacker-owned Shopify dev/trial store and capture the resulting delivery) can resend that identical body and HMAC to the app's webhook endpoint while swapping the `x-shopify-shop-domain` header for a victim shop's domain. `Utils::HmacValidator.validate` still succeeds because it never inspects the header, so `Registry.process` dispatches the forged event to the registered handler tagged with the victim's shop.

### Impact Explanation
This is a cross-tenant identity spoofing primitive at the library layer: the gem hands host applications a `WebhookMetadata#shop` value that they are meant to trust as authenticated (it comes from a `HmacValidator`-checked `Request`), but it is not actually bound to the verified bytes. Any host app that uses `request.shop` (or `WebhookMetadata#shop`) to select which merchant record to update, uninstall, deactivate, or resync — a normal and encouraged usage pattern per the library's own webhook handler API — can be made to act on the wrong tenant's data using attacker-supplied content, which the report's underlying bug class describes as "a field acted on but not covered by the HMAC." This matches the Critical class of cross-tenant access via credential/identity-binding failure.

### Likelihood Explanation
Exploitation requires no privileged credentials: an unbounded internet user only needs the ability to install the target app on a shop they control (or otherwise obtain one legitimate webhook delivery with a body they can reuse) and the ability to POST arbitrary headers to the app's public webhook endpoint. Both prerequisites are ordinarily available to any developer who can create a Shopify partner/dev store, so likelihood is high wherever a host app relies on `request.shop`/`WebhookMetadata#shop` without independent verification.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signable string bound by the HMAC, or independently verify that the `shop` header matches metadata already associated with the specific `webhook_id`/topic registration before dispatching to handlers. At minimum, document prominently that `request.shop` is unauthenticated and must not be trusted by host applications without separate verification (e.g., cross-checking against a known/installed shop list), since the current implementation lets it silently masquerade as verified data.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, satisfying OAuth normally.
2. Shopify sends a legitimate webhook (e.g., `orders/create`) with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)` and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker replays the exact same body `B` and HMAC `H` to the app's webhook endpoint but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. In the gem:
```ruby
request = ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: { "x-shopify-hmac-sha256" => H, "x-shopify-shop-domain" => "victim.myshopify.com", "x-shopify-topic" => "orders/create" })
ShopifyAPI::Utils::HmacValidator.validate(request) # => true, because to_signable_string == B only
ShopifyAPI::Webhooks::Registry.process(request)     # dispatches handler with shop: "victim.myshopify.com"
```
5. The handler receives `WebhookMetadata#shop == "victim.myshopify.com"` and `body` fully attacker-controlled (subject only to matching a previously-seen legitimate body), despite the request never actually originating from Shopify on behalf of `victim.myshopify.com`.
