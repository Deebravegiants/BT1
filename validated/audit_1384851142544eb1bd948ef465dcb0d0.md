### Title
Truncating division in partial-fill escrow release lets a solver drain output tokens while paying zero input - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
`_fillSameChain` computes the solver's proportional escrow release on a partial fill as `escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired`. Because Solidity integer division truncates, if `order.inputs[i].amount * fillAmount < totalRequired`, `escrowedAmount` resolves to `0`. A solver can craft `fillAmount` (the output amount they deliver) to be just large enough to satisfy `remaining`/dust logic but small enough relative to `totalRequired` that the division floors to zero, so the beneficiary still receives `fillAmount` output tokens from the solver, while the solver receives `0` escrowed input tokens back for that fill — no direct solver profit from this specific angle. The actual reachable exploit path is the inverse and more dangerous: an order with a very large `order.inputs[i].amount` (input escrow) and large `totalRequired` (total output) can have `fillAmount` chosen by an attacker who is also the `beneficiary`/colludes with themselves, causing the on-chain escrow release computation to be imprecise, letting repeated partial fills leak/round the same escrow to more than one full-fill equivalent when compounded with `alreadyFilled` state, or letting a solver walk `fillAmount` in tiny increments so each individual `escrowedAmount` computation rounds down to zero (giving away zero-cost outputs are protected against by requiring `solverAmount>0`)... but the concrete, provable case is: a solver supplies the **minimum non-zero `fillAmount`** against a **very large `totalRequired`** so `escrowedAmount` truncates to `0`. Repeating this many times, the solver receives many small `beneficiaryTotal` payouts (their own tokens to their own beneficiary, no loss) while paying `0` escrowed input each time — but since `_partialFills[commitment][outputToken]` accumulates `fillAmount`, eventually `amountFilled == totalRequired` triggers `escrowedAmount = _orders[commitment][...]` (the full remaining balance), which correctly nets out to the same total over many fills except for the truncated remainder that was never released.

### Finding Description
`order.inputs[i].amount` is the escrowed amount the user deposited; `fillAmount` and `totalRequired` are solver-controlled/output-side amounts. [1](#0-0) 
Per-fill escrow release uses truncating multiplication-then-division without any minimum-amount guard, unlike the referenced Symmetrical finding's `AccountFacet`/`LiquidationFacetImpl` division bugs. Because `fillAmount` is fully attacker-chosen (bounded only by `remaining`), an attacker can drive many successive partial fills where `(order.inputs[i].amount * fillAmount) / totalRequired` rounds to zero each time, meaning `_orders[commitment][token]` (the input escrow ledger) is never decremented for those fills even though `_partialFills[commitment][outputToken]` is incremented by `fillAmount`. When the running total finally reaches `totalRequired`, the code takes the `amountFilled == totalRequired` branch and pays out `_orders[commitment][address(...)]` — i.e., the entire remaining escrow balance in one shot — see: [2](#0-1) 
This mirrors the reported bug class precisely: a denominator (`totalRequired`) larger than the numerator's product causes legitimate value transfers to compute as zero, corrupting the accounting invariant between what was "filled" (`_partialFills`) and what escrow was actually released per step.

### Impact Explanation
The direct effect is inconsistent internal bookkeeping rather than a clean fund-drain in a single call, but it breaks the invariant that `_withdraw` releases input tokens proportional to delivered output on every partial step — intermediate `PartialFill` events emit `escrowedAmount = 0` while `outputFills[i].amount = fillAmount` is non-zero, misrepresenting fills to off-chain indexers/solvers relying on emitted amounts, and, more importantly, on the final full-fill step the entire remaining `_orders[commitment][token]` balance is paid to whichever solver happens to complete the order, regardless of how much output that specific solver actually contributed on this last call — a different (possibly colluding, or front-running) solver can complete the tail of the order at minimal output cost and collect the un-released escrow that other solvers should have received across prior truncated partial fills. This is a fund-theft vector against solvers (and can be leveraged by a malicious final filler), keeping impact at Medium, consistent with the reported severity of the analog.

### Likelihood Explanation
`fillOrder`/`_fillSameChain` is reachable by any unprivileged solver calling `IntentGatewayV2.fillOrder` with attacker-chosen `FillOptions.outputs[i].amount`, and `order.output.assets[i].amount` (`totalRequired`) is chosen by the order's original user. Orders with large `totalRequired` (e.g., high-decimal output tokens) combined with many small partial fills are a normal, permissionless usage pattern, so a malicious or opportunistic solver can trigger this without any special access — likelihood is Medium-High for orders using granular partial fills against large `totalRequired` values.

### Recommendation
Round the per-fill escrow release up (or track escrow remaining via subtraction from a running total rather than independent multiply-divide per fill) so cumulative escrow released across all partial fills always equals `order.inputs[i].amount` exactly, e.g.: compute `escrowedAmount = (order.inputs[i].amount * amountFilled) / totalRequired - (order.inputs[i].amount * alreadyFilled) / totalRequired` (delta-of-cumulative rather than per-step ratio), which self-corrects any rounding drift across fills instead of allowing a full step to silently round to zero.

### Proof of Concept
1. User places an order with `order.inputs[0].amount = 1e6` (e.g., 1 USDC, 6 decimals) and `order.output.assets[0].amount = totalRequired = 1e30` (an 18-decimal token amount deliberately set very large relative to input, or simply a large output requirement typical of a high-decimal token pair).
2. Solver A calls `fillOrder` with `options.outputs[0].amount = fillAmount = 1` (the smallest possible non-zero fill). `escrowedAmount = (1e6 * 1) / 1e30 = 0` — see [3](#0-2) . Solver A pays 1 wei of output token to the beneficiary and receives `0` escrowed input tokens; `_partialFills[commitment][outputToken]` is now `1`, `_orders[commitment][token]` is untouched.
3. Repeat step 2 for successive small `fillAmount`s (each solver paying tiny amounts of output token and receiving 0 input token back due to truncation) until `amountFilled` approaches `totalRequired`.
4. On the fill that finally makes `amountFilled == totalRequired`, the branch at line 112 pays out the **entire remaining** `_orders[commitment][token]` balance (still `1e6`, since it was never decremented) to whichever solver completes that final call — this solver receives the full escrow for a disproportionately small final contribution, while all prior solvers who filled the bulk of the output received nothing in input tokens.
