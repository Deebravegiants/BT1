### Title
Zero-length `erc20TokenAddresses` lets attacker force `EmporiumUpgradeable` to execute unconstrained arbitrary calls, draining pooled Emporium funds with no proof, nullifier, or balance-diff coverage - (File: contracts/CircomDataBuilder.sol, contracts/HinkalHelper.sol, contracts/Hinkal.sol, contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
When `circomData.externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `circomData.erc20TokenAddresses.length == 0`, `CircomDataBuilder.formInputForCircom` routes to `formInputEmporiumMin`, and every downstream array-driven safety check in `HinkalHelper.dimensionsCheck`, `Hinkal.transact`'s balance/slippage loop, and `insertNullifiers` becomes a no-op because they are all indexed by `circomData.erc20TokenAddresses.length`. Meanwhile `EmporiumUpgradeable.runAction` still executes `stack.ops` — fully attacker-controlled `{endpoint, callData, value}` triples decoded from `circomData.externalActionData.externalActionMetadata` — as direct calls from the Emporium contract's own context, with no correlation whatsoever to `erc20TokenAddresses`. Setting `EmporiumStack.signerAddress = address(0)` also skips ECDSA signature verification in `verifyWallet`. The combination lets an unprivileged attacker force the Emporium contract to call `transfer`/`transferFrom`/any function on any token or send ETH it holds to an attacker-chosen address, with zero circuit constraint, zero nullifier spend, and zero balance-diff check anywhere in the call path.

### Finding Description
The broken equality is: *value moved out of Emporium via `stack.ops[].endpoint.call{value: op.value}(op.callData)`* should equal *value proven-owned by the caller via `inNullifiers`/`rootHashHinkal` (circuit) or bounded by `slippageValues`/`balanceDif` (Solidity)*. With `erc20TokenAddresses = []`:

- `CircomDataBuilder.formInputForCircom` (`contracts/CircomDataBuilder.sol:134-148`) selects `formInputEmporiumMin`, whose 3-signal public input `[emporiumMessage, timeStamp, calldataHash]` matches `MainEVMCircuitMin.circom:6-17`, which only constrains `message <== Poseidon(1)([messageSeed])` — zero constraints on any token, amount, nullifier, or root hash. Note the "normal" `MainEVMCircuit` instantiated with `tokenCount=0` is equally unconstrained for tokens (`circuits/MainEVMCircuit.circom:100-169` loop body never executes), so the min/normal routing itself is not the unique root cause — the real gap is that the *Solidity* side treats `erc20TokenAddresses.length == 0` as "nothing to check" everywhere.
- `HinkalHelper.dimensionsCheck` (`contracts/HinkalHelper.sol:64-171`) only asserts internal array-length equalities against `dimensions.tokenNumber`; with `tokenNumber = 0` every check is `0 == 0` and passes trivially.
- `Hinkal.transact`'s post-execution balance/slippage/nullifier-insertion block (`contracts/Hinkal.sol:96-166`) is a `for (uint64 i; i < circomData.erc20TokenAddresses.length; i++)` loop — it does not execute at all when the array is empty, so `balanceDif >= slippageValues[i]` and `insertNullifiers(circomData.inputNullifiers, ...)` never run for any token actually moved.
- `EmporiumUpgradeable.runAction` (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:76-160`) decodes `stack` from `circomData.externalActionData.externalActionMetadata` (attacker-supplied, only self-consistently hashed into `calldataHash` by the attacker themselves via `getHashedCalldata`), and its `balancesBefore`/`balancesAfter`/UTXO-out loop is also keyed by `circomData.erc20TokenAddresses` (empty). The `stack.ops` loop (`EmporiumUpgradeable.sol:91-118`) is *not* gated by `erc20TokenAddresses` at all: `(success, err) = op.endpoint.call{value: op.value}(op.callData);` executes fully attacker-controlled calls as `msg.sender == EmporiumUpgradeable`.
- `verifyWallet` (`EmporiumUpgradeable.sol:302-349`) only enforces the EIP-712 signature check `if (stack.signerAddress == address(0)) { return; }` — an attacker who sets `signerAddress = address(0)` skips signature verification entirely, needing only to avoid replaying a used `emporiumMessage`.

Exploit flow: attacker calls `Hinkal.transact(a,b,c,dimensions={tokenNumber:0,nullifierAmount:0,outputAmount:0}, circomData)` where `circomData.erc20TokenAddresses=[]`, `externalActionId=HINKAL_EMPORIUM_ACTION_ID`, `externalActionData.externalActionMetadata` encodes an `EmporiumStack{signerAddress:address(0), ops:[{endpoint: <token or victim contract>, invokeWallet:false, value:0, callData: abi.encodeWithSelector(IERC20.transfer.selector, attacker, allTokenBalance)}]}`, `feeStructure.flatFee=0` (to skip the `foundToken` revert path), and a locally-generated trivial `MainEVMCircuitMin` proof. `performHinkalChecks` passes (self-consistent `calldataHash`, trivial `dimensionsCheck`), `verifyProof` succeeds against the 3-signal min verifier, `rootHashExists` passes with any historical root, `_externalTransact` calls `EmporiumUpgradeable.runAction` with `deltaAmountChanges=[]`, which executes the attacker's op as the Emporium contract, transferring out any ERC20/ETH balance the Emporium contract holds (protocol/relay fees, stranded prior deposits) to the attacker. No nullifier is spent, no balance-diff check occurs anywhere in `Hinkal.transact`.

### Impact Explanation
Any ERC20 tokens or ETH sitting in `EmporiumUpgradeable`'s own balance (accrued protocol/relay fees, stranded deposits, or balances left over from legitimate flows that didn't fully clear in one transaction) can be stolen by an unprivileged attacker in a single transaction, repeatable until the contract balance is exhausted. This is a proof/nullifier verification bypass — the attacker proves nothing about ownership of the funds moved — matching the Critical category ("proof or nullifier verification bypass") and/or High ("theft ... of protocol/relay fees").

### Likelihood Explanation
Preconditions are minimal and fully attacker-controlled: any EOA can call `Hinkal.transact` with `erc20TokenAddresses=[]`, craft `EmporiumStack` with `signerAddress=address(0)` to skip signature checks, and generate their own valid `MainEVMCircuitMin` (or even `MainEVMCircuit` with `tokenCount=0`) proof locally, since the circuit only proves knowledge of a self-chosen `messageSeed`. The only external dependency is that `EmporiumUpgradeable` must hold a non-zero balance of some asset (a realistic condition for any active protocol accruing relay/protocol fees or receiving stray transfers). No relay, admin, or victim cooperation is required, and the attack is fully repeatable.

### Recommendation
Do not let any array-length equal to zero bypass all downstream checks for external actions that can move funds. Specifically: (1) require `circomData.erc20TokenAddresses.length > 0` whenever `externalActionId != 0` and any `stack.ops[i].value > 0` or `stack.ops` contains calls to token contracts, or otherwise track and bound *all* value movable by `stack.ops` against tokens explicitly listed (and proven) in `circomData.erc20TokenAddresses`; (2) in `EmporiumUpgradeable.runAction`, restrict `op.endpoint` to an allow-list of external routers/DEXes and forbid direct calls to arbitrary addresses with attacker-chosen calldata unless `invokeWallet` and a verified `signerAddress` scope the action to the signer's own funds; (3) never allow `EmporiumStack.signerAddress == address(0)` to skip signature verification when `stack.ops` contains value-moving or arbitrary calldata; (4) make `Hinkal.transact`'s balance/slippage/nullifier checks unconditional on there being at least one token acted upon whenever `externalActionId != 0`, rather than looping over `circomData.erc20TokenAddresses` which the attacker fully controls including its length.

        CircomData calldata circomData,
        int256[] calldata deltaAmountChanges

                    selector == IHinkalWallet.doSendToRelay.selector

                    revert UnauthorizedWalletCall();

            }

            if (!success) {
                revert CallFailed(err);
            }

        );
