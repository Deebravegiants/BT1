### Title
Unbounded free mint via per-address rate limit bypass in `TokenFaucet.drip` — ([File: evm/src/utils/TokenFaucet.sol])

### Summary
`TokenFaucet.drip()` mints 1000 fee tokens to `msg.sender`, gated only by a "once per day per address" check keyed on `msg.sender`. Exactly like the DUCKVADER exploit — where the attacker deployed disposable `AttackContract2` instances to call `buyTokens()` from a fresh address each time and bypass any per-caller limiting — an attacker can deploy an unlimited number of throwaway contracts (or use fresh EOAs) to call `drip()` repeatedly in the same block/timeframe, since the rate limit has no Sybil resistance and no cap on the number of distinct callers.

### Finding Description
`drip()` tracks the last claim time per `msg.sender` in the `consumers` mapping and only blocks a *repeat* call from the *same* address within 24 hours: [1](#0-0) 

There is no cap on the total number of distinct addresses that can call `drip()`, no cost associated with obtaining a new address (deploying a minimal contract costs only gas), and `HyperFungibleTokenImpl(token).mint()` is called unconditionally once the (trivially bypassable) time check passes: [2](#0-1) 

The faucet is granted `MINTER_ROLE` on the real fee token used by the deployed `EvmHost` in the non-mainnet deployment path, meaning every fresh caller can mint 1000 tokens of the protocol's actual fee-token supply, an unbounded number of times, by generating new `msg.sender` addresses (e.g., spinning up new contracts the way `AttackContract2` does in the DUCKVADER PoC): [3](#0-2) 

This is the same root cause as DUCKVADER's `buyTokens` bug: a bonus/free-allocation function whose anti-abuse control is keyed on `msg.sender` identity rather than any real cost or uniqueness guarantee, trivially defeated by deploying fresh contract callers.

### Impact Explanation
The minted asset is the network's `feeToken`, which is used to pay dispatch/relayer fees on `EvmHost` and to fund actions like `BandwidthManager` purchases. Since minting is unbounded (limited only by gas cost of deploying new caller contracts), an attacker can mint arbitrary amounts of the fee token for free, inflating supply and enabling free consumption of paid protocol resources (message dispatch, bandwidth) that are supposed to be backed by real payment.

### Likelihood Explanation
High for any deployment where `TokenFaucet` is wired with `MINTER_ROLE` on a fee token that has real utility/value (as scripted in `DeployIsmp.s.sol`). The attack requires no privileges — only the ability to submit transactions and deploy contracts, which is exactly the class of unprivileged actor these findings are scoped to.

### Recommendation
Remove or strictly cap the faucet's minting ability in any deployment where the fee token carries real value, or replace the per-address gate with a genuine Sybil-resistant control (e.g., a fixed global mint cap, an allowlist, or tying `MINTER_ROLE` revocation to production/mainnet-adjacent testnets where the token has economic significance).

### Proof of Concept
Analogous to the DUCKVADER PoC's `AttackContract2.buy()` loop:
```solidity
contract FaucetDrainer {
    function drain(address faucet, address token) external {
        TokenFaucet(faucet).drip(token); // mints 1000e18 to this fresh contract
    }
}

// attacker loop:
for (uint i = 0; i < N; i++) {
    FaucetDrainer d = new FaucetDrainer();
    d.drain(faucetAddr, feeTokenAddr);
    // each fresh contract address bypasses the per-msg.sender daily limit
}
```
Each iteration deploys a new contract (a fresh `msg.sender`), so `consumers[msg.sender]` is always zero on first call, and `drip()` mints 1000 tokens with no aggregate cap.

```text
contract TokenFaucet {
    mapping(address => uint256) private consumers;

    // @dev Will only drip tokens, once per day
    function drip(address token) public {
        uint256 lastDrip = consumers[msg.sender];
        uint256 delay = block.timestamp - lastDrip;

        if (delay < 1 days) {
            revert("Can only request tokens once daily");
        }

        consumers[msg.sender] = block.timestamp;
        HyperFungibleTokenImpl(token).mint(msg.sender, 1000 * 1e18);
    }
```
