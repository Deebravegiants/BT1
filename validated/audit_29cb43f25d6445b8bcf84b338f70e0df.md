Confirmed: the shop identity binding in the webhook flow is broken. `Registry.process` verifies only `Utils::HmacValidator.validate(request)`, whose signable string is `to_signable_string => @raw_body` [1](#0-0) . The `shop` value that gets passed to the app's handler comes straight from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is not part of the HMAC-signed bytes at all [2](#0-1) [3](#0-2) .

### Title
Webhook `shop` tenant identifier is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating an HMAC over the raw request body. The `shop` field — which downstream `WebhookHandler` implementations use as the tenant identifier — is read from an HTTP header that is completely outside the HMAC-signed data, so it can be forged with a validly-signed body.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines `to_signable_string` to return only `@raw_body` [1](#0-0) . `shop` is a separate accessor pulled from the `shopify-shop-domain` header, with no cryptographic relationship to the signed body [2](#0-1) .

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, which computes `HMAC-SHA256(api_secret_key, request.to_signable_string)` and compares it to the `hmac` header — again, `shop` never enters this computation [4](#0-3) . After that single check passes, `request.shop` (still attacker-controllable) is forwarded verbatim into `WebhookMetadata` and handed to the app's handler as the trusted tenant identifier [3](#0-2) .

The binding that should hold is: `shop_header == shop_bound_by_hmac`. In reality the HMAC binds only the body bytes, so `shop_header` is unauthenticated relative to the signature: an attacker who has captured (or can generate) any single valid `(raw_body, hmac)` pair signed with the app's `api_secret_key` — for example by installing the app on their own shop and triggering a webhook of the topic they want to abuse, which Shopify signs using the same per-app `client_secret` for every shop — can replay that exact body/HMAC pair while substituting an arbitrary `shopify-shop-domain` header value. `Registry.process` will accept it as authentic and dispatch it to the handler tagged with the attacker-chosen `shop`.

This matches the "field acted on but not covered by the HMAC" analog class: the trust boundary the gem is supposed to enforce (this event genuinely originates from shop X) is broken because the identifying field (`shop`) is not part of what is verified.

### Impact Explanation
Applications built on this gem are documented to use `data.shop` directly as the tenant/session key when processing webhook payloads (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` per the gem's own webhook documentation) [5](#0-4) . Since `shop` is trusted without being bound to the HMAC, an attacker who can obtain one valid signed webhook body for any topic (trivially, by installing the app themselves and receiving a real webhook) can forge the `shop-domain` header to make the app record/act on that data under a victim shop's identity — a cross-tenant data confusion/injection vector rooted entirely in this gem's verification logic (`Registry.process` / `HmacValidator`), which is the component responsible for authenticating "this webhook came from shop X."

### Likelihood Explanation
Any developer who has installed the app (a normal, unprivileged action for a public app) can trigger real webhooks for their own shop and capture valid `(body, hmac)` pairs signed with the app's shared `client_secret` — no access token, `api_secret_key`, or victim credentials are required. Spoofing the shop header on a replayed request is trivial for anyone who can reach the app's public webhook endpoint.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) values in the HMAC-signable string, or otherwise cryptographically bind them to the signed body, so `HmacValidator.validate` fails if the shop header has been altered independent of the signed payload. At minimum, `Registry.process` should treat `request.shop` as untrusted metadata unless it can be proven consistent with the signed contents.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com` and trigger a webhook of a subscribed topic (e.g. `orders/create`); capture the raw POST body and its `x-shopify-hmac-sha256` header — both are valid per Shopify's own signing since the same `client_secret` signs webhooks for every shop of that app.
2. Replay this exact body and `hmac` header to the app's webhook endpoint, but replace `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `@raw_body` [1](#0-0)  — validation succeeds despite the spoofed shop header.
4. `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` is invoked with `shop == "victim-shop.myshopify.com"` [6](#0-5) , so the host application processes attacker-supplied webhook content as if it originated from the victim shop.
