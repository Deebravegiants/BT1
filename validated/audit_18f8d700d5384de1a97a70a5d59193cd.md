Audit Report

## Title
OIDC ClientSecret written to debug log via `%#v` before validation - ([File: core/sessions/oidcauth/oidc.go])

## Summary
`NewOIDCAuthenticator` unconditionally logs the entire `oidcCfg` argument with `lggr.Debugf("OIDC CFG:\n %#v\n", oidcCfg)` before any field validation occurs, meaning the OIDC client secret is passed into `fmt`'s Go-syntax formatter as part of the node's startup path whenever `Log.Level = 'debug'` and OIDC auth is configured. [1](#0-0)  The concrete type behind the `config.OIDC` interface is `*oidcConfig{c toml.WebServerOIDC, s toml.WebServerOIDCSecrets}`, where `s.ClientSecret` is a `*commonconfig.SecretString` holding the real secret value, and `ClientSecret()` returns the plain string. [2](#0-1) [3](#0-2) 

## Finding Description
The debug statement runs on every call to `NewOIDCAuthenticator`, prior to the required-field checks for `ClientID`, `ClientSecret`, `ProviderURL`, etc. [4](#0-3)  Elsewhere the codebase relies on `commonconfig.SecretString`'s custom TOML marshalling to redact secrets as `'xxxxx'`, as demonstrated by `Secrets.TOMLString()` and the CLI `validate` golden-file tests showing `Keystore = 'xxxxx'` / `URL = 'xxxxx'` output. [5](#0-4) [6](#0-5) 

However, `%#v` does not go through that TOML marshalling path — it uses Go's `fmt` reflection-based Go-syntax representation. Whether the client secret's actual value would be exposed depends entirely on whether `commonconfig.SecretString` (defined in the external `chainlink-common` dependency) implements a `GoString() string` method. This repository does not vendor or otherwise expose that type's source, and no such method could be located via `grep_search` across the indexed repo. [7](#0-6)  Without confirming that implementation detail in the actual dependency version pinned by `go.mod`, it cannot be conclusively proven that the raw secret string is emitted rather than a redacted placeholder — this is an unresolved verification gap acknowledged in the original report itself, and I was unable to close it given the tools available (no access to the `chainlink-common` module source or a live build/run environment to reproduce the log output).

## Impact Explanation
If confirmed, this would expose the OIDC client secret used to authenticate the node against its identity provider (Keycloak/Okta/etc.) in debug logs, which could be leveraged to impersonate the node as an OAuth client. This maps to a legitimate "secret exfiltration via logs" impact category. However, the claim's core technical premise — that `%#v` actually renders the plaintext secret rather than a redacted value — is not verified against the actual `SecretString` implementation, and the report itself flags this as unconfirmed.

## Likelihood Explanation
Triggering the log line requires no attacker action beyond normal node startup with `Log.Level = 'debug'` and OIDC configured — this is an operator configuration choice, not something exploitable by an unprivileged remote actor. The report's own PoC section explicitly states the secret's exposure "could not be verified from the indexed code and should be checked directly against the `chainlink-common` dependency version in use," meaning the claim is speculative rather than demonstrated. This does not meet the bar of a concrete, reproducible finding — it hinges on an assumption about external dependency behavior that was not validated, and even if true, it requires an operator/deployment configuration choice (debug logging) rather than exploitation by an unprivileged remote client against the node API, which is outside the scope of accepted impact classes for this program (no operator-only/misconfiguration-dependent issues).

## Recommendation
Regardless of whether `SecretString` redacts `%#v` output, remove the raw `%#v` debug log of the entire config struct in `core/sessions/oidcauth/oidc.go` and replace it with explicit, non-sensitive field logging (`ClientID`, `ProviderURL`, `RedirectURL`, claim names), or log `oidcCfg.ClientSecret()` only through a type whose `String()`/`GoString()` is confirmed to redact. Add a unit test asserting that constructing the authenticator with a known secret value does not produce that value in captured log output, confirming/denying the `SecretString.GoString()` behavior directly.

## Proof of Concept
Not independently reproducible from the available tooling: reproducing this requires either (a) inspecting the pinned `github.com/smartcontractkit/chainlink-common/pkg/config.SecretString` source for a `GoString()` method, or (b) running `chainlink node` with `Log.Level = 'debug'` and a configured `[WebServer.OIDC]` block and inspecting stdout for the literal secret value — neither of which could be performed in this read-only indexed environment. A definitive Go unit test would call `oidcauth.NewOIDCAuthenticator` with a test logger capturing output and assert the configured secret string does not appear in the captured log line.

type oidcConfig struct {
	c toml.WebServerOIDC
	s toml.WebServerOIDCSecrets

	if l.c.ClientID == nil {
		return ""
	}
	return *l.c.ClientID
}

func (l *oidcConfig) ClientSecret() string {
	if l.s.ClientSecret == nil {
		return ""
	}
	return string(*l.s.ClientSecret)
}
