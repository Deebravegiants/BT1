## Finding: Webhook shop/topic identity is not bound by the HMAC signature, enabling cross-tenant spoofing [1](#0-0) [2](#0-1) 

### Title
Webhook `shop`/`topic` attribution is unauthenticated (not covered by HMAC), enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable string as the raw HTTP body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC over the body and then unconditionally trusts `request.shop` for tenant attribution, without that field ever being part of the signed data.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [3](#0-2) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read directly from HTTP headers, which are not part of the signed payload: [4](#0-3) 

`Registry.process` validates the HMAC against the body via `Utils::HmacValidator.validate(request)`, then immediately hands `request.shop` (and `request.topic`) to the handler as trusted tenant identity, with no further check binding shop to the signed content: [2](#0-1) 

`HmacValidator.validate` simply recomputes the HMAC over `verifiable_query.to_signable_string` (the raw body in this case) and compares it to the received signature — it never inspects or incorporates `shop`, `topic`, or other headers into the signed string: [5](#0-4) 

The binding that should hold is:
`authenticated(shop_used_by_handler) == shop_that_produced_the_signed_body`

But because the signature only covers the body bytes, an attacker who legitimately owns/operates their own installed shop can:
1. Trigger a genuine event in their own store (e.g. create an order), causing Shopify to POST a validly-signed webhook (`raw_body` + `shopify-hmac-sha256`) to the app's public webhook endpoint.
2. Capture that body+HMAC pair.
3. Replay it to the same public endpoint with the `shopify-shop-domain` (and optionally `shopify-topic`) header rewritten to name a *different, victim* shop.

`HmacValidator.validate` still succeeds because it only checks the (unmodified) body against the (unmodified) HMAC. `Registry.process` then dispatches the handler with `WebhookMetadata.shop` set to the attacker-chosen victim shop domain, even though the body content actually originated from the attacker's own store. Any app logic that uses `shop` as a tenant/session key (e.g. to look up the victim's access token/session, write into per-shop storage, or otherwise scope side effects) is misled into treating attacker-supplied data as belonging to the victim tenant — this is precisely a "shop authenticated (by the signature) versus shop stored/used as the tenant key" identity-binding break, structurally the same class of tally-vs-enforcement mismatch flagged in the report (a value trusted for downstream decisions that isn't actually validated against the thing decided).

### Impact Explanation
This allows cross-tenant identity confusion in a merchant-facing app built on this gem: an attacker-controlled shop's webhook body can be attributed to an arbitrary victim shop domain, causing the host app to process/store attacker data under the victim's tenant context. Depending on how the host app uses `WebhookMetadata.shop` (commonly as a lookup/foreign key for stored sessions or triggered actions), this can lead to cross-tenant data corruption or unauthorized actions being taken against a victim's shop.

### Likelihood Explanation
The webhook endpoint is a public, unauthenticated-by-network-controls HTTP endpoint (security relies entirely on gem-level HMAC verification). Any actor who can install the app on their own shop and observe/trigger webhook deliveries can obtain valid body+HMAC pairs and freely manipulate the shop header, since headers are outside the signed payload. No secrets or privileged access are required beyond normal, unprivileged merchant use of their own store.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the value verified against the HMAC — either by having the app cross-check the header-derived shop against an independently authenticated source (e.g., the shop tied to the session/access token the webhook is meant to act on) before trusting `WebhookMetadata.shop`, or by documenting/enforcing that consumers must not use `request.shop` as a sole tenant key without additional verification. At minimum, `Registry.process` should not treat `request.shop` as validated merely because `HmacValidator.validate(request)` returned true.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger an event (e.g., create an order) to receive a genuine webhook POST with valid `shopify-hmac-sha256` for the JSON body.
2. Capture the raw body and HMAC header.
3. Re-send the identical body and HMAC header to the app's webhook endpoint, but replace `shopify-shop-domain` with `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes (body unchanged), then calls the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker's body>, ...)` — the app now processes attacker-controlled data as if it belongs to the victim tenant.
