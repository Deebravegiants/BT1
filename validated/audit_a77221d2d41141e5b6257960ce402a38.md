Audit Report

## Title
Missing sender/workflow allowlist check before forwarding `web_api_trigger` messages to all DON nodes - (File: `core/services/gateway/handlers/capabilities/handler.go`)

## Summary
`HandleLegacyUserMessage` validates message structure, timestamp freshness, and method name, but the explicit `TODO: apply allowlist and rate-limiting here` marks a genuinely missing authorization step before the request is broadcast to every DON member. Importantly, the message *is* cryptographically authenticated: `Message.Validate()` recovers the signer address from the ECDSA signature via `ExtractSigner()` and sets `m.Body.Sender` to that recovered address before `HandleLegacyUserMessage` is ever invoked, so an attacker cannot spoof another party's `Sender` value. However, no code path checks whether that (correctly authenticated) sender/workflow is actually permitted to invoke `MethodWebAPITrigger` for the target DON, and the request is unconditionally sent to all `h.donConfig.Members`.

## Finding Description
`gateway.ProcessRequest` calls `msg.Validate()` for legacy DonID-bearing requests, which performs structural checks and recovers/sets `msg.Body.Sender` from the signature: [1](#0-0) . `HandleLegacyUserMessage` then validates the payload, timestamp, and method name, but skips any allowlist check on the now-authenticated `Sender`/workflow before converting the message to a request and unconditionally broadcasting it to every DON member: [2](#0-1) . Unlike Vault's `GatewayHandler`, which wires an explicit `Authorizer`/allowlist before processing requests, this legacy trigger path has no equivalent per-sender or per-workflow authorization gate: [3](#0-2) .

This differs materially from the Allora `OnRecvPacket` analog cited in the claim: in that case the *sender identity itself* was unauthenticated/unchecked (a commented-out `if data.Sender != AxelarGMPAcc` check was skipping verification of who the sender was). Here, the sender identity is cryptographically verified via signature recovery before the handler runs — the gap is that the DON-facing trigger flow does not additionally check whether that verified sender is on a permitted allowlist for the specific DON/workflow being targeted. This is a real, acknowledged code gap (the `TODO` is genuine and unresolved in this codebase) but it is a narrower authorization gap than an authentication bypass — any request reaching the DON nodes carries a real, verifiable sender address, not an impersonated one.

## Impact Explanation
Since any address with a valid keypair can sign and send a `web_api_trigger` message that will be forwarded to all DON nodes without a workflow/sender allowlist check at the gateway layer, this could allow an unprivileged (but identifiable) actor to trigger workflow-run requests broadcast to the full DON, and to consume node-side rate-limit/resource budget, before any downstream node/workflow-registry-level authorization (if any) rejects it. Whether this results in unauthorized job execution depends on whether the DON-side workflow engine (`core/services/workflows/v2/engine.go`, `core/services/workflows/syncer/v2/workflow_registry.go`) independently validates that the sender is the registered owner/allowed trigger-caller for the targeted workflow before executing — this downstream check exists in the codebase (workflow ownership/allowlist logic is present in `core/services/workflows/syncer/v2/`), but I was unable to fully trace whether it specifically covers this legacy `web_api_trigger` gateway path before running out of investigation budget.

## Likelihood Explanation
The path is reachable by any client capable of generating a signed message (i.e., anyone holding an ECDSA keypair, which is a low bar and does not require any privileged Chainlink role) and sending it to the gateway's HTTP-facing endpoint. The `TODO` comment confirms the gap is real and unaddressed in the current code, and the broadcast to `h.donConfig.Members` happens unconditionally once basic structural/timestamp checks pass.

## Recommendation
Implement the missing allowlist check flagged by the `TODO` in `HandleLegacyUserMessage`, verifying that the cryptographically-recovered `msg.Body.Sender` (and associated workflow/topic) is permitted to invoke `MethodWebAPITrigger` for the target DON before broadcasting to `h.donConfig.Members`, following the `Authorizer`/allowlist pattern in `core/capabilities/vault/gw_handler.go`, and apply per-sender rate limiting prior to dispatch.

## Proof of Concept
1. Generate a valid ECDSA keypair not registered/authorized for any workflow on the target DON.
2. Construct and sign a legacy `api.Message` with `Body.Method = "web_api_trigger"`, a valid `DonID`, and a fresh `Timestamp` in the payload, using `Message.Sign()`.
3. Submit the message to the gateway's user-facing endpoint; `gateway.ProcessRequest` validates the signature (setting `Body.Sender` to the caller's own address) and routes to `HandleLegacyUserMessage`.
4. Observe that `HandleLegacyUserMessage` performs no allowlist check on `Sender` and forwards the request via `don.SendToNode` to every member in `h.donConfig.Members`.
5. Confirm via handler-level unit/integration test that no error/rejection occurs for a sender not present in any workflow-registry allowlist at this layer, only at (if at all) a later stage in the workflow engine.
