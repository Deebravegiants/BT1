### Title
Webhook HMAC does not bind `shop`/`topic` headers, allowing cross-tenant impersonation via request replay - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` computes the HMAC-verifiable payload from the raw body only, while the tenant-identifying `shop` (and `topic`) values are read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates only that HMAC-over-body, then forwards the header-derived `shop` value to the app's handler as the trusted tenant identifier. This breaks the intended binding `shop_in_signed_payload == shop_used_for_tenant_resolution`.

### Finding Description
`Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all sourced from HTTP headers that are never included in the signed string: [2](#0-1) 

`Registry.process` validates the HMAC over the request (i.e., over the body only), and then immediately trusts `request.topic` for handler dispatch and `request.shop` as the tenant identifier passed into the app-level handler via `WebhookMetadata`: [3](#0-2) 

Because the HMAC only proves "this body was signed with the app's secret at some point," and not "this body was delivered for shop X," an HTTP request with a genuine `(raw_body, hmac)` pair captured from one legitimate webhook delivery can be replayed to the same webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a different shop. `HmacValidator.validate` will still pass because it only recomputes the signature over `raw_body`: [4](#0-3) 

The gem's own documentation confirms this is the intended (and only) verification step exposed to consuming apps — "This will verify the request did indeed come from Shopify" — with no mention that `shop`/`topic` are unauthenticated: [5](#0-4) 

This is analogous to the reported bug class: a field (`shop`) that is acted upon (used to route/attribute webhook data to a tenant) is not covered by the message authentication code that gates trust in the request.

### Impact Explanation
If an attacker installs the target app on a shop they control, they will receive genuinely-signed webhook deliveries `(raw_body, valid HMAC)` for their own shop. If they can obtain even one such raw request/response pair (e.g., by controlling infrastructure that fronts their own webhook callback, common in multi-tenant SaaS setups where the webhook endpoint is a shared path keyed by the `shop` header), they can replay it against the shared webhook endpoint with the `shop-domain` header rewritten to a victim shop's domain. Since `Registry.process` never checks that the signed body's origin matches the claimed `shop`, the app will process attacker-controlled data as if it originated from the victim tenant — a cross-tenant data integrity/confusion issue reachable purely through the gem's documented `Registry.process`/`Request` API, without needing the victim's or app's credentials.

### Likelihood Explanation
Exploitation requires the attacker to have legitimate app access on their own shop (a normal unprivileged capability for anyone who can install a public Shopify app) and the ability to replay a previously-observed valid `(body, hmac)` pair with a modified header to the app's public webhook endpoint. No secret material is needed since the signature check in this gem never binds `shop`, `topic`, or `webhook_id` to the signature.

### Recommendation
Extend `Request#to_signable_string` (or add a secondary check in `Registry.process`) to bind the `shop-domain`, `topic`, and `webhook_id` header values into the authenticated payload, or otherwise cryptographically verify that these values match what Shopify actually signed, before they are handed to the app-level handler as trusted tenant/topic identifiers.

### Proof of Concept
1. Install the app on attacker-owned shop `attacker.myshopify.com`; capture one legitimate webhook POST, including its raw body and the `X-Shopify-Hmac-Sha256` header value.
2. Re-send that exact `raw_body` and `X-Shopify-Hmac-Sha256` to the app's shared webhook endpoint, but change `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only [6](#0-5)  — validation succeeds because `raw_body` and its HMAC are unchanged.
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` even though the payload was actually generated for `attacker.myshopify.com`, as seen in the call site [7](#0-6) .

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
