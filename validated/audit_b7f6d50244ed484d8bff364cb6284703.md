### Title
Local-auth login endpoint leaks distinct error text for unknown-email vs wrong-password, enabling user enumeration - (File: core/sessions/localauth/orm.go)

### Summary
The Chainlink node's local-auth `CreateSession` flow, exposed via `POST /sessions`, returns three textually distinct error strings depending on whether the email exists, whether the email comparison fails, or whether the password fails — and these raw Go error messages are echoed verbatim to the unauthenticated caller in the HTTP response body. This is the same bug class as the Shopware advisory: an unprivileged, unauthenticated actor can distinguish "unknown account" from "wrong password" via observable response differences on the login endpoint.

### Finding Description
`orm.CreateSession` (local auth) first calls `FindUser`/`findUser`, and if the email doesn't exist in the `users` table, the underlying SQL "no rows" error is returned unmodified: `return "", err` [3](#0-2) . If the email is found but somehow fails the constant-time compare, `"Invalid email"` is returned [4](#0-3) . If the password check fails, `"Invalid password"` is returned [5](#0-4) .

These three distinguishable error paths propagate unchanged up through `AuthenticationProvider.CreateSession` to `SessionsController.Create`, which does no unification and forwards the raw `err` directly to the client:
```go
sid, err := sc.App.AuthenticationProvider().CreateSession(ctx, sr)
if err != nil {
    jsonAPIError(c, http.StatusUnauthorized, err)
    return
}
``` [2](#0-1) 

`jsonAPIError` then serializes `err.Error()` verbatim into the JSON response when the error isn't already a `*models.JSONAPIErrors` [1](#0-0) . Because Postgres/sql "no rows in result set" wording differs completely from `"Invalid password"`, an attacker probing `/sessions` with a candidate email/password pair receives a directly observable, distinguishable message confirming whether an account with that email exists — analogous to Shopware's `CHECKOUT__CUSTOMER_NOT_FOUND` vs `CHECKOUT__CUSTOMER_AUTH_BAD_CREDENTIALS` split.

This mirrors the LDAP and OIDC local-fallback implementations of `CreateSession`/`localLoginFallback`, which have the identical `"invalid email"` vs `"invalid password"` pattern [6](#0-5) [7](#0-6) , all reachable through the same unauthenticated `SessionsController.Create` HTTP endpoint.

### Impact Explanation
An unauthenticated attacker hitting the node's `/sessions` login endpoint (used by the Operator UI) can enumerate valid operator/admin account emails on a Chainlink node by observing whether the returned error text is a SQL "no rows" style message versus `"Invalid password"`. Confirmed emails can be used to target credential stuffing or phishing against node operators, who typically hold elevated privileges (admin/edit roles controlling job specs, keys, and fund-moving operations). This is a lower-severity information-disclosure issue (matches CWE-204, comparable CVSS to the source advisory: local, network-reachable, no privileges required, confidentiality-only impact), not a direct authentication bypass.

### Likelihood Explanation
High likelihood of exploitability if the endpoint is network-reachable: no authentication or special conditions are required, a single request per candidate email suffices (as in the Shopware report), and there is no indication of rate limiting or generic error unification at this endpoint. However, exploitability depends on whether `/sessions` is exposed beyond a trusted operator network, which is deployment-specific and not verifiable from the code alone.

### Recommendation
Unify all three failure paths in `orm.CreateSession` (and the LDAP/OIDC `localLoginFallback` equivalents) into a single generic error (e.g., `errors.New("invalid email or password")`) before returning, matching the constant-time-compare intent already used for `constantTimeEmailCompare`. Additionally, avoid forwarding raw internal `error` values to `jsonAPIError` from authentication endpoints — wrap them in a fixed, generic message at the controller level in `SessionsController.Create` regardless of the underlying provider's error text.

### Proof of Concept
1. `POST /sessions` with `{"email":"unknown@example.com","password":"x"}` → response body contains the raw SQL "no rows in result set" (or equivalent) error text via `models.NewJSONAPIErrorsWith(err.Error())`.
2. `POST /sessions` with `{"email":"<confirmed-real-admin-email>","password":"wrong"}` → response body contains `"Invalid password"`.
3. The two responses are trivially distinguishable, allowing enumeration of valid node account emails without any credentials or rate-limit bypass required beyond one request per candidate.

func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}

// localLoginFallback tests the credentials provided against the 'local' authentication method
// This covers the case of local CLI API calls requiring local login separate from the LDAP server
func (l *ldapAuthenticator) localLoginFallback(ctx context.Context, sr sessions.SessionRequest) (sessions.User, error) {
	var user sessions.User
	sql := "SELECT * FROM users WHERE lower(email) = lower($1)"
	err := l.ds.GetContext(ctx, &user, sql, sr.Email)
	if err != nil {
		return user, err
	}
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		l.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return user, errors.New("invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		l.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return user, errors.New("invalid password")
	}

	return user, nil
}
