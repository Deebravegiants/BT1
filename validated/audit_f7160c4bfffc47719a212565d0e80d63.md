### Title
Excess native token (`msg.value`) overpayment in Tron `IntentGatewayV2.placeOrder` is never refunded and cannot be rescued - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` (`evm/tron/contracts/apps/IntentGatewayV2.sol`, lines 338-506) tracks a running `msgValue` counter as it consumes native-token legs for predispatch assets, order inputs, and fee swaps, but — unlike the canonical EVM implementation in `evm/src/apps/IntentGatewayV2.sol` — it never refunds the leftover `msgValue` to the caller at the end of the function. Any native-token overpayment a user sends with `placeOrder{value: ...}` is silently retained by the contract with no code path to recover it.

### Finding Description
In `evm/src/apps/IntentGatewayV2.sol` the reference implementation explicitly refunds unused `msg.value` after all native-token legs (predispatch, inputs, fee swap) have been consumed: [1](#0-0) 

This is exercised by tests such as `testPlaceOrder_RefundsExcessNativeToken` and `testPlaceOrder_FeeSwap_RefundsExcessNativeToken`, confirming the intended behavior is that overpaid ETH is always sent back to `msg.sender`: [2](#0-1) 

The Tron variant of the same function duplicates the exact `msgValue` decrement logic for predispatch assets, plain inputs, and the fee-token swap: [3](#0-2) [4](#0-3) 

but the function terminates immediately after emitting `OrderPlaced` — there is no `if (msgValue > 0) { _sendValue(msg.sender, msgValue); }` step, and no `receive()`/rescue function exists elsewhere in the contract to recover stray native balance (the only other native-fund-moving path, `SweepDust`, is a privileged, Hyperbridge-governance-triggered sweep, not a self-service rescue): [5](#0-4) 

Any user who overestimates the native amount needed (e.g. sending `value = inputAmount + buffer` for a native-input order, or overestimating the ETH needed for the `swapETHForExactTokens` fee swap, exactly as covered by the reference contract's tests) permanently loses the difference — it accumulates in the gateway contract with no withdrawal mechanism reachable by the user or by governance for this specific purpose.

### Impact Explanation
This is a direct, permanent loss of user funds reachable from a single unprivileged `placeOrder` call — the same class of impact as the reported `RootBridgeRelay` issue (native tokens trapped in a contract with no rescue path). Because `placeOrder` is the primary unprivileged entry point for the intents flow, and overpayment is a normal/expected user behavior explicitly supported and tested in the sibling EVM contract, any Tron-chain user overpaying (even by a small buffer, or via slippage in the `swapETHForExactTokens` fee-swap step) loses the excess ETH/TRX permanently.

### Likelihood Explanation
High. Overpaying `msg.value` beyond the exact required amount is a common, realistic user/integrator behavior (e.g. buffer for gas-price/slippage estimation, or wallet UIs rounding up), and the sibling EVM contract's own test suite demonstrates this scenario is expected to occur in normal operation. No special preconditions, privileged roles, or malicious actors are required — a single legitimate `placeOrder{value: X}()` call with `X` slightly greater than required is sufficient to trigger permanent fund loss.

### Recommendation
Add the same unspent-native-token refund step present in `evm/src/apps/IntentGatewayV2.sol` to the Tron `placeOrder` implementation, immediately before/after escrowing fees and emitting `OrderPlaced`:
```solidity
// Refund any unspent native tokens to the user.
if (msgValue > 0) {
    (bool sent, ) = msg.sender.call{value: msgValue}("");
    if (!sent) revert InsufficientNativeToken();
}
```
Additionally, audit all other Tron-specific app contracts for the same divergence from their EVM counterparts, since the Tron port appears to be a manually-forked copy that can silently drop safety fixes present upstream.

### Proof of Concept
1. User calls `IntentGatewayV2.placeOrder{value: inputAmount + overpayment}(order, graffiti)` on the Tron deployment, where `order.inputs[0] = {token: address(0), amount: inputAmount}` (native input) and `order.fees == 0`.
2. Inside `placeOrder`, the `else` branch (no predispatch) executes: `msgValue -= order.inputs[i].amount;`, leaving `msgValue == overpayment`.
3. Because `order.fees == 0`, the fee-escrow block is skipped entirely, leaving `msgValue` unused.
4. `OrderPlaced` is emitted and the function returns; `overpayment` remains stuck in the contract's native balance.
5. There is no user-callable or automatic path to move that balance back to the user — `withdraw()` (internal) only releases amounts recorded in `_orders[commitment][token]`, and `SweepDust` is a Hyperbridge-governance-only path unrelated to this specific stuck balance, and not guaranteed to ever target it.
