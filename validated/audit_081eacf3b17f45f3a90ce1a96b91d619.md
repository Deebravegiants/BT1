### Title
Attacker-inflated vault balance can permanently panic `calc_take_pnl` and brick `Deposit`/`Withdraw`/`WithdrawPnl` - (File: `program/src/processor.rs`, `program/src/math.rs`)

### Summary
The CVE describes an unprivileged, single-crafted-message DoS caused by an unchecked assertion inside a stateful accounting path (FlashMQ's retain-message handling). The analogous bug class in this AMM is an unprivileged, single-instruction-reachable arithmetic panic (`unwrap()`/`checked_sub().unwrap()`) inside the pnl accounting routine `calc_take_pnl`, which is invoked from `process_deposit`, `process_withdraw`, and `process_withdrawpnl`. Because token vault balances feeding this routine can be inflated by anyone via a plain SPL `transfer` directly to the AMM's `coin_vault`/`pc_vault` (no AMM-owned signature required), an attacker can desynchronize the vault's live balance from the `TargetOrders.calc_pnl_x/calc_pnl_y` bookkeeping fields, driving the routine's internal subtraction into underflow.

### Finding Description
`calc_take_pnl` in `program/src/processor.rs:167-281` computes `x2`/`y2` via `Calculator::calc_x_power` and an integer square root, then does:
```
let diff_x = U128::from(x1.checked_sub(x2).unwrap().as_u128());
let diff_y = U128::from(y1.checked_sub(y2).unwrap().as_u128());
``` [1](#0-0) 

`x1`/`y1` are derived every call from the *live* vault token balances via `Calculator::calc_total_without_take_pnl_no_orderbook` and `normalize_decimal_v2`, called from `process_deposit`, `process_withdraw`, and `process_withdrawpnl`: [2](#0-1) [3](#0-2) 

`x2`/`y2` are computed relative to the persisted `TargetOrders.calc_pnl_x`/`calc_pnl_y` (last recorded pnl-adjusted reserves) and the *current* `x1`/`y1` via `calc_x_power`: [4](#0-3) 

Both `Deposit` and `Withdraw` account lists include the AMM's `coin_vault`/`pc_vault` token accounts as plain SPL token accounts owned by the AMM authority PDA — any unprivileged holder of coin/pc mint tokens can call `spl_token::instruction::transfer` to send tokens directly into these vaults in a preceding or same transaction, without invoking any Raydium instruction at all. This inflates the live vault balance (and thus `x1`/`y1`) independent of the bookkeeping in `TargetOrders`. The guard at line 190 (`pool_pc*pool_coin >= calc_pc*calc_coin`) only checks the product, not whether `x2 <= x1` and `y2 <= y1` individually; a sufficiently skewed single-sided donation can make the ratio-preserving `x2`/`y2` computed from the *old* target ratio exceed the actual/new `x1`/`y1` for one side, causing `x1.checked_sub(x2).unwrap()` (or the `y` variant) to underflow and panic. [5](#0-4) 

The same routine's callers (`process_deposit` at lines 1352-1371, `process_withdraw` at lines 1818-1838, `process_withdrawpnl` at lines 1531-1532) also perform further unguarded `checked_sub().unwrap()` operations combining `x1`/`y1` with `delta_x`/`delta_y` returned from `calc_take_pnl`, compounding the same underflow risk: [6](#0-5) [7](#0-6) 

### Impact Explanation
A Rust panic aborts the transaction and does not commit any state, so a single triggering transaction alone is not "permanent" damage. The permanent-freeze risk arises because a *successful* (non-panicking) `Deposit`/`Withdraw`/`WithdrawPnl` call — executed while the attacker's donation has only partially skewed the ratio — will still write a new `calc_pnl_x`/`calc_pnl_y` into `TargetOrders` that is now inconsistent with the live vault balances. Once that inconsistent state is persisted on-chain, every subsequent legitimate `Deposit`, `Withdraw`, or `WithdrawPnl` call recomputes `x1`/`y1` from the (now permanently skewed) vault balances against the stale `calc_pnl_x`/`calc_pnl_y`, and can deterministically re-hit the same underflow, permanently reverting on every call. This would deny liquidity providers and the pnl owner the ability to withdraw funds or add liquidity through this pool — a permanent freezing of LP funds, matching the required impact category (permanent freezing of user/LP funds via an unauthorized state-corruption path reachable from unprivileged accounts).

### Likelihood Explanation
Medium-High. The prerequisite action — transferring extra coin/pc tokens directly into the AMM's vault token accounts — requires only an SPL `transfer` instruction with no privileged signer, and vault addresses are public (`amm.coin_vault`/`amm.pc_vault`, verified only by `check_assert_eq!` against the `AmmInfo` struct, not by ownership restriction on who may fund them). Reaching the exact underflow boundary requires precise sizing of the donation relative to the pool's current `TargetOrders` state, which raises the bar from "trivial" to "requires calculation," but this is well within reach of an attacker who can read on-chain pool/target-orders state before crafting the donation amount and follow-up `Deposit`/`Withdraw` call in the same or a subsequent transaction.

### Recommendation
- Replace the unchecked `checked_sub(...).unwrap()` calls in `calc_take_pnl` (`program/src/processor.rs:213-214`) and in the callers' `calc_pnl_x`/`calc_pnl_y` updates (`processor.rs:1352-1371`, `1818-1838`, `1531-1532`) with `checked_sub(...).ok_or(AmmError::CalcPnlError)?` so a would-be underflow returns a clean program error instead of panicking, and — more importantly — instead of silently reverting the offending transaction, treat detection of `x2 > x1` or `y2 > y1` as evidence of desynchronized state and fail closed with a dedicated error rather than allow a value that is "just under" the panic boundary to be persisted.
- Consider deriving `x1`/`y1` from an amount that cannot be donated to directly (e.g., track deposits/withdrawals internally rather than trusting live token-account balances), or reconcile/cap donated excess before it affects `calc_pnl_x`/`calc_pnl_y` accounting.

### Proof of Concept
1. Attacker reads the target pool's `AmmInfo`/`TargetOrders` to learn `calc_pnl_x`, `calc_pnl_y`, and current vault balances.
2. Attacker computes a donation amount `d` to `amm_coin_vault` (or `amm_pc_vault`) such that, after the transfer, recomputed `x1`/`y1` combined with the stale `calc_pnl_x`/`calc_pnl_y` make `Calculator::calc_x_power`'s resulting `x2` (or `y2`) exceed the new `x1` (or `y1`).
3. Attacker issues a plain `spl_token::instruction::transfer` from any token account they control to `amm_coin_vault_info`/`amm_pc_vault_info` — no Raydium instruction, no privileged signer.
4. Attacker (or any user) subsequently calls `Deposit`, `Withdraw`, or `WithdrawPnl`; `calc_take_pnl` is invoked and `x1.checked_sub(x2).unwrap()` (or `y` analog) panics, reverting that transaction.
5. If a preceding call (with a smaller/adjacent donation size) persisted a `calc_pnl_x`/`calc_pnl_y` value inconsistent with the vault balance before the boundary was crossed, all subsequent calls to these three instructions deterministically panic, permanently freezing LP withdrawals/deposits and pnl withdrawal for that pool.

    pub fn calc_x_power(last_x: U256, last_y: U256, current_x: U256, current_y: U256) -> U256 {
        // must be use u256, because u128 may be overflow
        let x_power = last_x
            .checked_mul(last_y)
            .unwrap()
            .checked_mul(current_x)
            .unwrap()
            .checked_div(current_y)
            .unwrap();
        x_power
    }

    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
