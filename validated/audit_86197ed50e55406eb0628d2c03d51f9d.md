### Title
LP share dilution via direct balance donation before first `add_liquidity` call - ([File: substrate/frame/asset-conversion/src/lib.rs])

### Summary
`Pallet::do_add_liquidity` computes pool reserves via `Self::get_balance(&pool_account, asset)`, which reads the pool account's raw, unaccounted asset balance rather than an internally tracked reserve that is only mutated through pool bookkeeping. An attacker can inflate this raw balance by transferring assets directly to the pool account before making a minimal first legitimate `add_liquidity` call, then a later depositor's LP-token allocation is computed against the inflated reserves and total supply derived only from the attacker's small deposit, producing a severe share dilution that the attacker can redeem via `remove_liquidity`.

### Finding Description
`do_add_liquidity` reads reserves as raw balances: [1](#0-0) 

The zero-reserve check that decides whether to use the full desired amounts is an `OR`, so an attacker only needs to donate to *both* assets to skip the "empty pool" branch and instead go through the quote-based branch that is normally reserved for non-empty pools: [2](#0-1) 

Crucially, whether LP tokens are minted using the zero-supply formula or the proportional formula is gated on `T::PoolAssets::total_issuance`, *not* on the raw reserve values: [3](#0-2) 

This means: (1) attacker donates `X1`/`X2` directly to `pool_account` (via `Balances::transfer_allow_death` / `Assets::transfer`), bypassing `do_add_liquidity` entirely; total supply of the LP token is still 0 since no `add_liquidity` has ever executed. (2) Attacker calls `add_liquidity` with a modest amount whose ratio matches the donated reserves so the `quote` check passes; because `total_supply.is_zero()` is still true, `lp_token_amount` is computed from `calc_lp_amount_for_zero_supply(amount1, amount2)` using only the attacker's real transferred amount — enough to clear `T::MintMinLiquidity::get()`. `total_supply` after this call becomes `sqrt(real_amount1 * real_amount2)`, small relative to the donated `X1`/`X2`. (3) When the victim later calls `add_liquidity` with a large legitimate amount, reserves used in the proportional mint formula (`mul_div(amount, total_supply, reserve)`, lines 869-871) are the *inflated* raw balances (donation + attacker's real deposit), while `total_supply` reflects only the attacker's small real contribution. The victim is credited a disproportionately small `lp_token_amount` for a large real deposit. (4) Attacker then calls `remove_liquidity`, which also derives withdrawal amounts from `get_reserves` (raw balances) and `total_supply` (`mul_div(lp_redeem_amount, reserve, total_supply)`), letting the attacker — who holds nearly all real LP tokens outstanding — redeem a share of the pool that includes the victim's newly-added assets: [4](#0-3) 

The `get_reserves` view function used elsewhere for quoting has the identical raw-balance read pattern: [5](#0-4) 

No check anywhere compares the raw pool-account balance to an independently-tracked "backed" reserve, so a direct token transfer to the pool account (a normal, unprivileged `transfer` extrinsic) permanently corrupts the ratio used for LP minting/redemption until the pool is drained and effectively re-seeded.

### Impact Explanation
A victim who calls `add_liquidity` after the donation receives far fewer LP tokens than proportional to their contribution, while their real assets are pooled into `pool_account`. The attacker, holding the vast majority of the LP token supply (their small deposit plus the untouched donation now backing the pool), can call `remove_liquidity` to withdraw a share of the pool that includes the victim's contributed assets — a direct theft of a second liquidity provider's deposit, matching the scoped impact exactly.

### Likelihood Explanation
The precondition is simply a freshly created, still-empty pool — a state that exists briefly after every `create_pool` call and can be targeted by monitoring `PoolCreated` events (or front-running via mempool visibility) before the first `add_liquidity` transaction lands. All actions used (`Balances::transfer_allow_death`, `Assets::transfer`, `add_liquidity`, `remove_liquidity`) are ordinary unprivileged extrinsics with no special origin, proxy, or governance requirement, making the attack fully reproducible and repeatable against any newly created pool.

### Recommendation
Track pool reserves internally (e.g., in the `PoolInfo` storage item, updated exclusively by `do_add_liquidity`, `do_remove_liquidity`, and swap functions) instead of reading the pool account's raw balance via `Self::get_balance` in the LP-mint/redeem accounting path. Alternatively, reconcile/ignore any balance surplus over the tracked reserve so that unsolicited direct transfers cannot influence LP token minting or redemption ratios.

### Proof of Concept
Rust integration test (in `substrate/frame/asset-conversion/src/tests.rs` style, using the mock runtime):
1. `create_pool(asset1, asset2)`.
2. Attacker: directly `Assets::transfer`/`Balances::transfer_allow_death` a large `donation1`, `donation2` into `PoolLocator::address(&pool_id)` (bypassing `do_add_liquidity`).
3. Attacker: `AssetConversion::add_liquidity(attacker, asset1, asset2, small_amount1, small_amount2, 0, 0, attacker)` chosen so `small_amount2 ≈ quote(small_amount1, donation1, donation2)` and `sqrt(small_amount1*small_amount2) > MintMinLiquidity`; assert it succeeds and mints `lp_token_amount_attacker`.
4. Victim: `AssetConversion::add_liquidity(victim, asset1, asset2, large_amount1, large_amount2, 0, 0, victim)`; assert `lp_token_amount_victim` returned is far smaller than `large_amount1 / (small_amount1 + donation1) * total_supply` (i.e., non-proportional / negligible compared to deposit size).
5. Attacker: `AssetConversion::remove_liquidity(attacker, asset1, asset2, lp_token_amount_attacker, 0, 0, attacker)`; assert the amounts returned to attacker include a large portion of `large_amount1`/`large_amount2` originally deposited by the victim (i.e., `withdrawn_amount1 > small_amount1 + donation1`), proving fund extraction from the victim's deposit.

		pub fn get_reserves(
			asset1: T::AssetKind,
			asset2: T::AssetKind,
		) -> Result<(T::Balance, T::Balance), Error<T>> {
			let pool_account = T::PoolLocator::pool_address(&asset1, &asset2)
				.map_err(|_| Error::<T>::InvalidAssetPair)?;

			let balance1 = Self::get_balance(&pool_account, asset1);
			let balance2 = Self::get_balance(&pool_account, asset2);

			if balance1.is_zero() || balance2.is_zero() {
				Err(Error::<T>::PoolEmpty)?;
			}

			Ok((balance1, balance2))
		}
