### Title
Webhook HMAC does not bind `x-shopify-topic`, allowing topic-forged replay to route to a different handler - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `#topic` reads the unauthenticated `x-shopify-topic`/`shopify-topic` header directly. `Registry.process` validates the HMAC over the raw body only, then dispatches to a handler keyed purely by `request.topic`, so the equality `hmac-signed bytes == data acted on by the topic-specific handler` does not hold: a valid `(raw_body, hmac)` pair obtained for one topic can be replayed with a forged topic header and will still pass HMAC validation while being routed to a different handler, including a `MANDATORY_TOPICS` compliance handler such as `customers/data_request`.

### Finding Description
The claimed binding is: `HMAC-SHA256(api_secret_key, raw_body) == received hmac` should imply that `request.topic` (used to select the handler in `Registry.process`) faithfully describes `raw_body`'s content/schema. In fact:

- `Request#to_signable_string` returns `@raw_body` only [1](#0-0) .
- `Request#topic` is read straight from the header dictionary with no cryptographic tie to the body [2](#0-1) .
- `HmacValidator.validate`/`validate_signature` compute and compare the signature strictly against `to_signable_string` (the body), never touching topic, shop, or webhook id [3](#0-2) .
- `Registry.process` checks only `Utils::HmacValidator.validate(request)`, then looks up `@registry[request.topic]` and hands `request.parsed_body` to that handler [4](#0-3) .

Because Shopify signs app webhooks with the app-level `client_secret` (`Context.api_secret_key`), which is identical for every shop that installs the app, an attacker who installs the app on their own development shop can trigger a genuine webhook (e.g. `app/uninstalled`) and capture the real `raw_body` and its valid `hmac`. They can then submit an HTTP request to the app's webhook endpoint with the same `raw_body`/`hmac` but with `x-shopify-topic` set to `customers/data_request` (a `MANDATORY_TOPICS` entry). `HmacValidator.validate` still passes because it only checks body bytes against the secret; `Registry.process` then dispatches to the `customers/data_request` handler with the `app/uninstalled` body as `parsed_body`. None of the existing guards (`ShopValidator`, `Context.setup?`, Sorbet typing) inspect or bind topic to the signed payload, so nothing prevents this divergence.

### Impact Explanation
This is a genuine authentication-bypass pattern: the HMAC check is treated as "this whole webhook, including its topic, is verified," but topic is unauthenticated and swappable. The attacker can force any registered handler (including mandatory GDPR/compliance handlers) to run with attacker-chosen, replayed content that does not match the schema/semantics the handler expects for that topic. Concretely this could cause compliance handlers to act on malformed/attacker-shaped data or non-compliance handlers to fire outside their intended trigger, and in general breaks the invariant that a positively-verified webhook truthfully represents the topic Shopify actually sent. It is repeatable at will by the same attacker against the app's own endpoint, since the underlying secret is app-wide, not shop-specific, so any topic for which the attacker can obtain one valid signed body can be replayed under any other topic's header. This matches "Critical – authentication bypass (forged webhook accepted as if verified for a different topic)."

### Likelihood Explanation
Preconditions are minimal and fully attacker-controlled: create a free development shop, install the target app (a normal, documented flow), trigger any webhook topic the app subscribes to (e.g. uninstall the app to get `app/uninstalled`), capture `raw_body` + `x-shopify-hmac-sha256`, then POST to the app's webhook receiver with a forged `x-shopify-topic` header set to any `MANDATORY_TOPICS` value or any other registered topic. No secrets, tokens, or victim interaction are required. This is fully feasible and repeatable using only tools available to an unprivileged attacker per the threat model.

### Recommendation
Bind the topic (and ideally shop domain / webhook id) into the value that is HMAC-verified, or independently authenticate that the header topic matches metadata Shopify signs, e.g., by including `topic`/`shop-domain`/`webhook-id` in `to_signable_string`, or by validating the topic against the registered subscription for the delivery address rather than trusting a header value derived purely from an unauthenticated HTTP header. At minimum, `Registry.process` should reject processing if the topic cannot be attested as bound to the verified body.

### Proof of Concept
```ruby
# test/webhooks/registry_topic_confusion_test.rb (illustrative, no live shop, no WebMock needed)
require "test_helper"

class RegistryTopicConfusionTest < Test::Unit::TestCase
  def setup
    ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", ...)
    ShopifyAPI::Webhooks::Registry.clear
  end

  def test_forged_topic_header_reuses_hmac_from_different_topic
    raw_body = '{"id":123,"domain":"attacker-shop.myshopify.com"}' # genuine app/uninstalled body

    real_hmac = Base64.strict_encode64(
      OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
    )

    called_with = nil
    handler = Class.new do
      define_method(:handle) { |data:| called_with = data }
    end.new

    ShopifyAPI::Webhooks::Registry.add_registration(
      topic: "customers/data_request", delivery_method: :http, path: "/wh", handler: handler
    )

    forged_request = ShopifyAPI::Webhooks::Request.new(
      raw_body: raw_body,
      headers: {
        "x-shopify-topic" => "customers/data_request", # forged
        "x-shopify-hmac-sha256" => real_hmac,            # valid for app/uninstalled body, unrelated to topic
        "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
      },
    )

    ShopifyAPI::Webhooks::Registry.process(forged_request) # does not raise InvalidWebhookError

    assert_equal "customers/data_request", called_with.topic
    assert_equal 123, called_with.body["id"] # app/uninstalled payload processed as data_request
  end
end
```
Assertion set demonstrates both sides of the claimed binding diverge: `HmacValidator.validate(forged_request)` returns `true` (body-only signature holds) while `request.topic` used for dispatch does not correspond to the actual signed webhook topic Shopify would have sent for that body, and `Registry.process` completes successfully instead of raising `Errors::InvalidWebhookError`.
