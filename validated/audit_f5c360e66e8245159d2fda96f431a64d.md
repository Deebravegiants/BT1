## Analysis Result

### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authenticated for a specific shop once its HMAC check passes, but the HMAC signature only covers the raw request body — not the `shop-domain` header that the gem hands to the app's handler as the authoritative tenant identifier.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines `to_signable_string` as returning only `@raw_body`, while `shop` is read independently from the `shopify-shop-domain`/`x-shopify-shop-domain` header: [1](#0-0) [2](#0-1) 

`Utils::HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (the body) and compares it to the `hmac` field, never incorporating the shop header: [3](#0-2) 

`Registry.process` uses this HMAC result as the sole authenticity gate, then forwards `request.shop` — the unauthenticated header value — directly to the app's handler as the trusted tenant key: [4](#0-3) 

The gem's own documentation tells integrators that `Registry.process` "will verify the request did indeed come from Shopify" and that `data.shop` is "The shop domain of the webhook," implying it's a verified value app code can key business logic/storage on.

The broken binding, as an equality: the gem asserts `hmac_valid(body) == shop_is_authentic(header)`, but the actual invariant enforced is only `hmac_valid(body)`; `shop` is parsed independently from an unsigned header and is never checked to match the HMAC-protected content or any known-registered shop for that webhook subscription.

### Impact Explanation
An unprivileged internet user who legitimately installs the app on their own shop receives real webhook deliveries (valid body + HMAC signed by Shopify using the app's secret) addressed to their own shop. Because the signature covers only the body, that attacker can replay the exact same body and HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header (e.g., a victim shop's domain). `HmacValidator.validate` still returns true (body/HMAC pair is untouched and valid), so `Registry.process` calls the handler with `WebhookMetadata` claiming the forged shop. Any app that uses `data.shop` for tenant-scoped writes, cache keys, notifications, or record attribution will process attacker-supplied webhook content under a victim shop's identity — a cross-tenant data-integrity/confusion issue reachable purely through this gem's documented API, without needing the app's `client_secret` or an access token.

### Likelihood Explanation
Any user who can install the app on a shop they control can capture a legitimate signed webhook (body + HMAC) for a topic they can trigger (e.g., `orders/create` on their own store) and replay it with a modified shop header to the same public webhook endpoint. No secrets, tokens, or privileged access are required beyond having installed the app once, making this straightforward to exploit for a malicious merchant/tester.

### Recommendation
Bind the `shop-domain` header into the HMAC-verified signable content (or otherwise cryptographically tie it to the verified webhook subscription/shop) before exposing it via `WebhookMetadata`, and/or require callers to cross-check `request.shop` against a known/registered shop before trusting it for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., creates an order), capturing the raw POST body and the `x-shopify-hmac-sha256` header Shopify sent to the app's callback URL.
2. Attacker resends this exact body and HMAC header to the same webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged shop header; `Utils::HmacValidator.validate` succeeds because it only checks `OpenSSL::HMAC.hexdigest(secret, raw_body)` against the untouched HMAC value (`lib/shopify_api/utils/hmac_validator.rb:26-31`).
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: attacker_body, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the app to process attacker-controlled data under the victim shop's identity.
