### Title
Webhook shop-domain header is trusted for tenant routing but is not covered by the HMAC signature - (File: lib/shopify_api/webhooks/registry.rb, lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [2](#0-1) , while `shop` is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header with no cryptographic binding to that body [3](#0-2) . `Registry.process` validates the HMAC of the request and then immediately trusts `request.shop` to build the `WebhookMetadata` handed to the host app's webhook handler [1](#0-0) .

### Finding Description
The identity binding that should hold is: `hmac == HMAC(secret, body || shop || topic)`, i.e. the tenant identifier used for routing/processing should be part of the signed material. Instead the binding actually enforced is `hmac == HMAC(secret, body)` only, and `shop` is taken from an unauthenticated header, exactly the class of bug in the report: a field that is *acted upon* (here, used to attribute the webhook to a specific merchant/tenant) but *not covered* by the integrity check (here, the HMAC). Because all shops served by a single Shopify app share the same `client_secret`, a valid `(raw_body, hmac)` pair legitimately produced by Shopify for Shop A's webhook remains cryptographically valid when replayed with the `shop-domain` header rewritten to Shop B — `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` will still pass because it never inspects `shop`.

### Impact Explanation
If a host application relies on `request.shop` (or `WebhookMetadata#shop`) from a Shopify-verified webhook request to select which merchant's session/access token/data to load or mutate, an attacker who can trigger delivery of (or capture and replay) a legitimately-signed webhook body can attribute it to an arbitrary other shop known to the same app, producing cross-tenant data confusion — data or actions intended for Shop A get applied under Shop B's identity. This matches the Critical "cross-tenant access" impact category, since the tenant boundary (`shop`) is not actually authenticated even though the request as a whole appears verified.

### Likelihood Explanation
Exploitability requires the attacker to control or replay the raw HTTP request reaching the app's webhook endpoint with a header they can set (many web frameworks let any caller set arbitrary headers on requests reaching the endpoint, and Shopify's delivery does not encrypt or authenticate headers independently of the HMAC), and requires the app's handler to make tenant-scoping decisions based on `request.shop`/`WebhookMetadata.shop` as this gem's own API encourages (`Registry.process` passes it straight through). This is a plausible, gem-level design flaw rather than a theoretical one, since the gem itself performs the "validated, therefore trust `shop`" step in `Registry.process`.

### Recommendation
Include `shop` (and ideally `topic`) in the signable string used for `Utils::HmacValidator`, or independently verify that `request.shop` matches the shop associated with the session under which the webhook was expected, before dispatching to handlers.

### Proof of Concept
1. Shopify sends a legitimate webhook for `shop-a.myshopify.com` with raw body `B` and `X-Shopify-Hmac-Sha256` computed as `HMAC(secret, B)`.
2. Capture `(B, hmac)`.
3. Replay a request to the app's webhook endpoint with the same `B` and `hmac`, but set `shopify-shop-domain: shop-b.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` in `lib/shopify_api/utils/hmac_validator.rb` returns `true` because it only checks `to_signable_string` (the body), never `shop`.
5. `Registry.process` at [4](#0-3)  proceeds to call the host handler with `WebhookMetadata.new(... shop: "shop-b.myshopify.com", body: <shop-a's data> ...)`, causing shop-a's webhook payload to be processed under shop-b's tenant context.
