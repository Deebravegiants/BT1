The Tron variant of `IntentGatewayV2` performs raw low-level `.call()` invocations of the ERC-20 `transfer` selector and checks only that the call did not revert, not that the token's returned boolean succeeded. This is the exact "unchecked ERC-20 return value" bug class from the report, and it sits on the critical escrow-payout path (`RedeemEscrow`/`RefundEscrow`/`SweepDust`) reachable by any relayer delivering a valid cross-chain message.

### Title
Escrow withdrawal accepts failed (returns-false) ERC-20 transfers as success, permanently losing user/solver funds - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.withdraw()` and the `SweepDust` branch of `onAccept()` on Tron settle escrowed ERC-20 tokens using a raw low-level call to the `transfer` selector, checking only that the call itself did not revert (`success`), never decoding/validating the boolean return value that `IERC20.transfer` is supposed to produce.

### Finding Description
In `withdraw()`, escrowed balances are decremented unconditionally right after the raw call, based solely on `success`: [1](#0-0) 

The same unchecked pattern appears in the `SweepDust` handling of `onAccept()`: [2](#0-1) 

`onAccept()` is the `onlyHost` entry point invoked whenever the `EvmHost`/handler delivers a relayed POST request; `RedeemEscrow`/`RefundEscrow` kinds are dispatched from the fill/select/cancel flows of any user or solver and can be delivered by any relayer once the corresponding proof is valid: [3](#0-2) 

Contrast this with the fixed, `SafeERC20`-based implementation used elsewhere in the codebase for the same escrow-release logic (`_withdraw` in `IntentsBase.sol`), which properly uses `safeTransfer`: [4](#0-3) 

For any ERC-20 token that returns `false` on failure instead of reverting (a known class of "weird" tokens; also relevant on Tron, where TRC-20 token behavior can vary), `token.call(...)` succeeds (`success == true`) even though the actual transfer did not occur, because the low-level `call` only reports whether execution reverted — it does not inspect the ABI-encoded return data for the boolean result the ERC-20 standard specifies.

### Impact Explanation
Because `_orders[body.commitment][token]` (and, for `TRANSACTION_FEES`, the accumulated relayer fee) is decremented/deleted regardless of whether the token transfer actually moved funds, a beneficiary can be marked as paid while the tokens remain stuck in the `IntentGatewayV2` contract. This is a permanent loss of user or solver funds for the affected token, with no path to re-claim since escrow state has already been erased (`UnknownOrder` will revert any retry). This satisfies the "permanent freezing/loss of funds" bar for a valid finding.

### Likelihood Explanation
Exploitation requires only that the escrowed input token behave non-standardly (return `false` rather than revert on failure) — a documented occurrence among real-world ERC-20/TRC-20 tokens. No privileged role is needed; any solver/user whose order settles in such a token, or any relayer delivering the corresponding `RedeemEscrow`/`RefundEscrow`/`SweepDust` message, can trigger the code path. Likelihood is token-dependent but realistic given IntentGatewayV2 is designed to be token-agnostic for arbitrary escrowed assets.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` and the `SweepDust` branch with OpenZeppelin's `SafeERC20.safeTransfer`, which is already imported and used (`using SafeERC20 for IERC20;`) elsewhere in this same contract, ensuring both call-success and return-value truthiness are checked before escrow accounting is finalized.

### Proof of Concept
1. An order is created and filled using a non-standard ERC-20 token `T` that returns `false` instead of reverting when, e.g., the recipient is blacklisted or the transfer otherwise fails internally, as the escrowed input token on the source chain deployment of `IntentGatewayV2` (Tron).
2. The destination fill completes and a `RedeemEscrow` POST request is dispatched back to the source chain, or a solver directly triggers `RefundEscrow`/`SweepDust` after expiry.
3. `onAccept()` is invoked by the host with the relayed request; `withdraw()` calls `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` on `T`.
4. `T.transfer` internally fails and returns `false` without reverting; `success` is `true` because the call itself didn't revert.
5. `_orders[commitment][token] -= amount` executes, permanently marking the tokens as withdrawn even though `beneficiary`'s balance never increased — the tokens are now unrecoverably stuck in the contract.
