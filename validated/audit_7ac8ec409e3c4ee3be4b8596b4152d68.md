### Title
Spot-price venue pricing lets flash-loan pool manipulation drain a Simplex solver's Uniswap V4 LP position - (File: sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts)

### Summary
Simplex's Uniswap V4 funding venue prices "exotic" tokens directly from the pool's current `sqrtPriceX96` (spot price), then uses that same manipulable price to size how much liquidity to withdraw from the solver's LP position to fund an intent fill. This mirrors the Cyrus Finance bug class: a spot price read from an AMM pool is trusted as an oracle input to a fund-extraction function, letting a flash-loan price manipulation attacker force an outsized withdrawal from an LP position.

### Finding Description
`UniswapV4FundingPlanner.getExoticTokenPrice` computes the USD price of an exotic token straight from the pool's live state: [1](#0-0) 

This is documented as reading "the raw pool mid derived from `sqrtPriceX96`" with "no size or impact term," and the only protection, `checkPriceGuard`, checks deviation from a static reference — not execution cost or manipulation resistance: [2](#0-1) 

That price feeds `resolveLegRates` in the fill-sizing strategy (`FXFiller`), which computes `targetOutput`/`policyMaxOutput` for an intent order leg and then, if the solver's wallet balance is short, requests a withdrawal from `UniswapV4FundingPlanner.planWithdrawalForToken`: [3](#0-2) 

The withdrawal planner reads live pool `slot0`/liquidity on every plan (`UniswapV4LiquidityState.refresh`) and uses that same spot price to compute the amount of liquidity to decrease from the solver's LP position to cover the deficit: [4](#0-3) [5](#0-4) 

Because both the price used to size the payout owed to the order and the price used to size how much LP inventory to burn come from the same instantaneous pool tick with no TWAP, and `checkPriceGuard`'s only defense is a static-reference deviation band (configured per-position, optional, and bounded in basis points rather than tied to trade/withdrawal size or executable liquidity), an attacker who moves the pool's tick within that tolerated band via a flash loan can make the solver believe the exotic token is worth more (or less) than it is. An unprivileged user submits an intent order sized to exploit that mispricing; Simplex's `evaluateOrder` prices and funds the fill by decreasing the solver's Uniswap V4 LP position at the manipulated tick, over-crediting the withdrawal relative to the true, unmanipulated value. The attacker profits the spread between the manipulated valuation and the pool's post-manipulation reverted price, extracted at the solver's LP position's expense — the same "flash-loan spot-price manipulation triggers over-extraction from an LP position" pattern as `CyrusTreasury.withdrawUSDTFromAny`.

### Impact Explanation
This is a real, unprivileged-reachable path: any address can place an IntentGateway order and, in the same or a preceding transaction, manipulate the referenced Uniswap V4 pool's spot price via a flash loan before Simplex's off-chain evaluator prices and funds the fill from its LP position. The result is theft of value from the solver's on-chain liquidity position (economic loss backing real cross-chain intent fills), matching a Medium-severity classification consistent with the Cyrus Finance analog ($516,840 loss via the same bug class). It does not directly corrupt Hyperbridge consensus, message delivery, or escrow accounting, which keeps it below Critical/High for the core protocol, but it is a concrete, exploitable fund-extraction vector against a production Hyperbridge component (the reference Simplex solver).

### Likelihood Explanation
Medium-to-high likelihood wherever a `[vault.uniswapV4]` position is configured without a tight `referencePrice`/`maxDeviationBps` guard, or where the guard's tolerance band is wide enough (or the pool thin enough) for a flash loan to move the tick within it. The mechanism (`getExoticTokenPrice` → `checkPriceGuard` → `planWithdrawalForToken`) runs on every fill needing venue funding, requires no privileged access, and is triggerable by simply placing an order against a pool the attacker can also flash-loan.

### Recommendation
- Replace the instantaneous `sqrtPriceX96` read in `computeDirectPoolPriceUsd` with a TWAP (or otherwise manipulation-resistant) price, or require deviation checks against multiple independent price sources.
- Make `checkPriceGuard`'s reference/deviation configuration mandatory (not optional) for any pair using venue pricing, and size the tolerance to the position's actual liquidity depth/impact rather than a flat bps band.
- Add a same-block/same-transaction manipulation defense (e.g., reject pricing derived from a pool whose price changed materially within the last N blocks, or require the price used for LP withdrawal sizing to be re-verified against a longer window immediately before `modifyLiquidities` is executed).
- Consider capping the fraction of a position's liquidity that can be withdrawn in service of a single order regardless of quoted price, bounding worst-case loss per fill.

### Proof of Concept
1. Attacker identifies a Simplex solver configured with `[vault.uniswapV4]` funding a pair (e.g., USDC/CNGN) priced purely from the pool (no curve), per `docs/content/developers/evm/simplex/pricing.mdx`.
2. Attacker takes a flash loan and swaps against the Uniswap V4 pool backing the solver's LP position to move `sqrtPriceX96`/tick such that `computeDirectPoolPriceUsd` reports an inflated USD value for the exotic token, while staying within any configured `maxDeviationBps` (or where no guard is configured).
3. Attacker places an IntentGateway order requesting the exotic token, sized so the solver's wallet balance is insufficient and `planWithdrawalForToken` must decrease the solver's V4 position.
4. `UniswapV4FundingPlanner` refreshes pool state (still reflecting the manipulated tick), computes `liquidityRemoval`, and withdraws liquidity credited at the manipulated price, funding an oversized payout to the attacker's order.
5. Attacker reverses the flash-loan swap, restoring the true pool price, and keeps the surplus extracted from the solver's LP position.

Note: this analysis is based on the reference/example Simplex solver shipped in `sdk/packages/simplex`; actual exploitability depends on a given operator's live `[vault.uniswapV4]` configuration (whether `referencePrice`/`maxDeviationBps` is set and how tightly), which could not be further verified from the indexed code alone.
