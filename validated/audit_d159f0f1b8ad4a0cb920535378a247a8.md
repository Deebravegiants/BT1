## Title
Overpaid native ETH sent to `EvmHost.dispatch()`/`fundRequest()` for the Uniswap fee-swap is permanently lost to the user instead of being refunded - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` let a caller pay the relayer fee in native token by swapping `msg.value` for an exact amount of `feeToken` via `swapETHForExactTokens`. None of these functions capture the swap's return value or refund any leftover native token to the caller, so any ETH sent above what the swap actually consumes is trapped in the contract, recoverable only by cross-chain governance.

### Finding Description
In `dispatch(DispatchPost)`: [1](#0-0) 

and identically in `dispatch(DispatchGet)`: [2](#0-1) 

and in `fundRequest`: [3](#0-2) 

All three call `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, ...)` without capturing the returned `amounts` array, and without any subsequent refund logic for `msg.value - amountSpent`. The standard Uniswap V2 router's `swapETHForExactTokens` refunds unspent ETH to `msg.sender` of that call — but since `EvmHost` itself calls the router, the refund target is `address(this)` (the `EvmHost` contract), not the original transaction sender. This is explicitly acknowledged in the codebase's own comment on `EvmHost`'s `receive()`: [4](#0-3) 

Once that dust lands in the Host's balance, the only way to move it out is `withdraw()`, which is restricted to the `hostManager` (cross-chain governance), not to the overpaying user: [5](#0-4) 

This is the same bug class as the referenced report: a payment-collecting function accepts `msg.value` greater than what's actually required, and the excess is not returned to the payer, but instead becomes effectively permanent protocol revenue recoverable only by a privileged party — exactly analogous to the deprecated/owner-only withdrawal path described in the report.

Notably, other apps in this same codebase implement the correct pattern by capturing the swap output and refunding the remainder to the caller (e.g. `IntentGatewayV2._fillCrossChain`/`placeOrder`, which computes `msgValue -= amounts[0]` and calls `_sendValue(msg.sender, msgValue)`): [6](#0-5) [7](#0-6) 

This shows the pattern is known and applied elsewhere, but is missing from the core `EvmHost` dispatch/fund paths.

Because on-chain fee estimation is inherently approximate for native-token payments (per protocol docs: "Fee Calculation: Approximate (subject to slippage)"; users are told to over-send and expect exactness only from `feeToken` payments), users routing native ETH through `dispatch`/`fundRequest` are structurally incentivized to overpay slightly to avoid a revert, and any overpayment is siphoned into the Host's balance instead of returning to them.

### Impact Explanation
Any unprivileged user or integrating app dispatching a `PostRequest`/`GetRequest` or funding a pending request with native token, who supplies `msg.value` even slightly above what the Uniswap swap consumes, permanently loses that excess ETH. It accrues in the `EvmHost` contract and can only be extracted by cross-chain governance via `withdraw()` — the user has no self-service recovery path. Given native-token fee estimation is explicitly documented as approximate, this is a reachable and repeatable loss-of-funds condition across every EVM deployment of `EvmHost`, satisfying "concrete theft or permanent freezing of funds" for a single submitted transaction.

### Likelihood Explanation
High. Any caller of `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, or `fundRequest()` who pays with native token and doesn't send the exact minimal wei amount (which requires an off-chain, sandwich-attack-vulnerable `quote()` call per the docs' own warning) will trigger this loss. This is the default/expected usage pattern for native-token payment, not an edge case.

### Recommendation
Capture the `amounts` returned by `swapETHForExactTokens` in all three functions (`dispatch(DispatchPost)`, `dispatch(DispatchGet)`, `fundRequest`) and refund `msg.value - amounts[0]` back to `_msgSender()` (or `post.payer`/`get.payer` as appropriate), mirroring the pattern already used in `IntentGatewayV2`/`ExtrinsicIntents.sol`.

### Proof of Concept
1. User calls `EvmHost.dispatch(DispatchPost)` with `post.fee = 10e18` (feeToken units) and sends `msg.value = quote(fee) + extra` (e.g. due to slippage buffer).
2. Inside `dispatch`, `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` executes: the Uniswap router spends only enough ETH to acquire exactly `post.fee` feeToken, then refunds the unspent ETH to its caller — `address(this)`, i.e. `EvmHost`.
3. `EvmHost`'s `receive()` accepts this refund silently; no logic in `dispatch` forwards it back to the user.
4. The `extra` ETH now sits in `EvmHost`'s balance. The user cannot retrieve it; only `withdraw()`, gated by `restrict(_hostParams.hostManager)`, can move native balance out, and only to a beneficiary chosen by governance. [1](#0-0) [5](#0-4)

     * @param params, the parameters for withdrawal

    function withdraw(WithdrawParams memory params) external restrict(_hostParams.hostManager) {
        if (params.token == address(0)) {
            // this is safe because re-entrancy is mitigated before dispatching requests
            (bool sent,) = params.beneficiary.call{value: params.amount}("");
            if (!sent) revert WithdrawalFailed();
        } else {
            IERC20(params.token).safeTransfer(params.beneficiary, params.amount);
        }
        emit HostWithdrawal({beneficiary: params.beneficiary, amount: params.amount, token: params.token});
    }
