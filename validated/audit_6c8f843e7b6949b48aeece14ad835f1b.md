### Title
Stale `Account.owner` authorizes the previous NFT holder after position transfer - (File: contracts/controller/src/account.rs)

### Summary
The controller caches the owner address inside the stored `Account` struct at account creation and authenticates spenders against that cached value, while a second ownership source — the live position-NFT owner — exists and is used by `require_account_owner`. After a `position-nft` transfer moves the account to a new owner, the stored `Account.owner` is not restamped, so `require_owner_or_delegate` still accepts the prior owner (and that owner's stale delegate list) on `borrow`, `withdraw`, `swap_collateral`, `repay_debt_with_collateral`, `multiply`, `flash_position`, `swap_debt`, and `migrate_from_blend`. A seller/transferrer of a position NFT retains full spending authority over collateral and borrowing power they no longer own — the direct analog of insufficient validation of authentication parameters letting an attacker act with a credential that should no longer be valid.

### Finding Description
`create_account` writes `owner` into the `Account` struct once, at mint time, and `storage::set_account_meta` records only `spoke_id`/`mode` — there is no owner field in `AccountMeta` and no path that rewrites `Account.owner` (contracts/controller/src/account.rs:64-71). All value-moving flows authenticate with `require_owner_or_delegate(env, account_id, caller, &account.owner)`, where `account` comes from `storage::get_account` — i.e., the cached owner (contracts/controller/src/positions/debt.rs:42-43; contracts/controller/src/strategies/repay_debt_with_collateral.rs:50-51). `is_owner_or_delegate` then checks `caller == owner` against that stale value and consults `storage::get_delegates(env, account_id, owner)` keyed by the stale owner, so delegates of the *previous* owner also keep authority (contracts/controller/src/account.rs:115-127).

By contrast, `require_account_owner` — used only by `renew_account`, `add_delegate`, and `remove_delegate` — resolves ownership live via `storage::account_owner(env, account_id)` (the position-NFT owner) and compares it to the caller (contracts/controller/src/account.rs:143-148). This proves the codebase has two distinct notions of "owner": the live NFT owner and the cached `Account.owner`. The spend-authority gate uses the cached one, and nothing in the transfer path updates it. `add_delegate`/`remove_delegate` write delegate sets keyed under the live NFT owner, so after a transfer the *new* owner's `add_delegate` writes under their own key while the *old* owner's delegates remain active under `Account.owner` — and the new owner cannot even revoke them, since `set_account_delegate` authenticates the caller against the live NFT owner but the delegate list is keyed by the stale owner (contracts/controller/src/account.rs:242-264).

### Impact Explanation
Theft of user funds. An unprivileged attacker sells or transfers a position NFT, then — as the recorded `Account.owner` — calls `withdraw(account_id, withdrawals, to: attacker)` or `borrow(account_id, borrows, to: attacker)` to drain the account's collateral and take protocol debt against it, paying out to an arbitrary `to` recipient that `require_external_recipient` only checks is not the controller/pool (contracts/controller/src/positions/debt.rs:45-47). Alternatively the attacker uses `repay_debt_with_collateral` with `close_position: true` to sweep all remaining collateral to themselves (contracts/controller/src/strategies/repay_debt_with_collateral.rs:81-89). A delegated position manager of the previous owner likewise retains authority it should have lost.

### Likelihood Explanation
High for any account whose NFT is transferred: position NFTs are explicitly transferable (`position-nft` transfer/approve is an in-scope unprivileged entrypoint), and every borrow/withdraw/strategy path reaches the vulnerable check with a single signed call from the stale owner. No privileged role, oracle manipulation, or timing condition is needed — only an account that changed hands after creation. Note: I was unable to fully verify the position-nft `transfer` implementation or confirm whether any hook restamps `Account.owner` on transfer (index coverage limits); the finding stands if no such restamp exists, which the code reviewed does not show.

### Recommendation
Authenticate spending authority against the live NFT owner: in `require_owner_or_delegate` (or at every call site), resolve `storage::account_owner(env, account_id)` instead of `account.owner`, and key `get_delegates`/`add_delegate`/`remove_delegate` by that live owner. Alternatively, hook the position-NFT transfer to rewrite `Account.owner` and migrate/clear the delegate set atomically. Remove the cached `Account.owner` field or assert it equals the live owner as an invariant.

### Proof of Concept
1. Alice calls `supply` with `account_id = 0`, creating account `A` owned by Alice; `Account.owner = Alice` is persisted.
2. Alice supplies collateral and transfers the position NFT for `A` to Bob (`position-nft::transfer`). The stored `Account.owner` remains `Alice`.
3. Alice calls `controller::withdraw(caller: Alice, account_id: A, withdrawals: [XLM, 0 for all], to: attacker)`. `require_authorized_caller` passes (Alice signs), `require_owner_or_delegate` compares `caller` to stale `Account.owner = Alice` and returns; funds are sent to the attacker's `to` address.
4. Variant: Alice's previously added delegate `D` calls `borrow(caller: D, account_id: A, borrows, to: D)` — `get_delegates(A, Alice)` still contains `D`, so the stale delegate steals borrowing power against Bob's collateral.
