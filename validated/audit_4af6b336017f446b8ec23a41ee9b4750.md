Confirmed: `WebhookMetadata` passes `shop` straight to the handler [1](#0-0)  and `Request#to_signable_string` returns only `@raw_body`, never the shop header, so the HMAC computed in `HmacValidator.validate` never covers `shop` [2](#0-1) [3](#0-2) .

### Title
Webhook shop identity is unauthenticated by the HMAC, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking that the HMAC over the raw body matches, then dispatches the handler using the `shop` value taken from an HTTP header that is never included in that HMAC computation. Because the same `client_secret`/`api_secret_key` is shared across all shops that install a given app, a valid `(body, hmac)` pair obtained for one shop can be replayed with a different `x-shopify-shop-domain` (or `shopify-shop-domain`) header value, and the library will accept it as authentic for that other shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`:
```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [4](#0-3) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e., only the body) and compares it to the received `hmac-sha256` header [5](#0-4) . The `shop` accessor, however, is read from a separate, unauthenticated header:
```ruby
sig { returns(String) }
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [6](#0-5) 

`Registry.process` only checks the HMAC before trusting `request.shop` and forwarding it to the app's handler:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [7](#0-6) 

This breaks the intended identity binding: `verified_hmac_scope == shop_used_for_tenant_routing`. In reality, `verified_hmac_scope` covers only the body bytes, while `shop_used_for_tenant_routing` is an arbitrary, attacker-controlled header. Since a given app's `api_secret_key` is identical for every shop that installs the app, any legitimate webhook body+signature pair obtained by an attacker (for example, by installing the same app on their own store and capturing a webhook it receives — an action requiring no special privilege) remains a valid HMAC no matter which `shop-domain` header is attached to the replay. The library's own documentation reinforces the false guarantee, stating that `Registry.process` "will verify the request did indeed come from Shopify" [8](#0-7) , without noting that the shop identity itself is unauthenticated.

### Impact Explanation
This is a cross-tenant confusion vulnerability. Any consumer of this gem that uses `WebhookMetadata#shop` to route webhook data to per-shop storage, trigger per-shop background jobs, or make authorization decisions (exactly as shown in the gem's own documented usage example: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` [9](#0-8) ) can be made to process attacker-supplied data under a victim shop's identity, or have data from a victim shop attributed by the host app to an attacker-supplied `shop` value. This crosses a tenant boundary without any credential belonging to the victim, satisfying the "cross-tenant access" impact criterion.

### Likelihood Explanation
Likelihood is high for any app with more than one merchant install (the common case for any public Shopify app): an unprivileged attacker only needs to install the target app on their own store (a normal, unprivileged action) to receive a legitimately-signed `(body, hmac)` pair for any topic they can trigger (e.g., `orders/create` by placing an order in their own store), then replay that exact body and HMAC to the app's public webhook endpoint while substituting the `shop-domain` header for the victim's shop domain.

### Recommendation
Bind the `shop` (and ideally `topic`, `api_version`) header values into the signable content used for HMAC verification, or independently verify that the `shop-domain` header corresponds to a shop with an active, known session/installation for this app before trusting it. At minimum, `Request#to_signable_string` should incorporate the shop domain so that a signature computed for one tenant cannot be replayed against another.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, triggering a webhook (e.g., `orders/create`). The app's server receives:
   - Headers: `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid-hmac>`, `x-shopify-shop-domain: attacker.myshopify.com`
   - Body: `{"id":123,...}`
2. Attacker computes/observes that `hmac-sha256` is valid for that exact raw body (they don't need the secret key — they simply captured a real webhook delivery).
3. Attacker replays the identical raw body and `x-shopify-hmac-sha256` value to the same webhook endpoint, but changes the header to `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over the (unchanged) body and it matches, so `Registry.process` in `lib/shopify_api/webhooks/registry.rb` accepts the request.
5. The host app's handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker's body>, ...)` and processes/stores it as data belonging to `victim.myshopify.com`, achieving cross-tenant data injection/confusion despite the attacker never possessing any credential for the victim shop.
