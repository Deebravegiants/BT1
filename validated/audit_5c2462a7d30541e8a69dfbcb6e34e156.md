### Title
Webhook `shop`, `topic`, and `webhook_id` fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely via `Utils::HmacValidator.validate(request)`, which validates the HMAC against `request.to_signable_string`. For `Webhooks::Request`, `to_signable_string` returns only the raw JSON body, while `shop`, `topic`, `webhook_id`, and `api_version` are read from unauthenticated HTTP headers and passed unchecked into the handler.

### Finding Description
`Webhooks::Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are extracted directly from HTTP headers with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` only checks the HMAC before dispatching to the handler, and forwards the unauthenticated `shop`, `topic`, and `webhook_id` fields as trusted metadata: [3](#0-2) 

`HmacValidator.validate_signature` computes the signature purely from `verifiable_query.to_signable_string` (i.e., the raw body) and the shared `api_secret_key`, comparing it against the received `hmac`: [4](#0-3) 

Because the `api_secret_key` used to compute the HMAC is the **app's** secret — shared across every shop that installs the app — and not a per-shop secret, any merchant who has installed the app and legitimately receives a real, validly-signed webhook (raw body + HMAC) for their own shop can replay that exact same `(raw_body, hmac)` pair to the app's webhook endpoint while freely rewriting the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, and `X-Shopify-Webhook-Id` headers to arbitrary values. The signature check will still pass because those headers are never part of `to_signable_string`, breaking the intended binding: `shop asserted-by-header == shop the merchant actually owns`.

This lets a malicious but otherwise unprivileged (from the perspective of other tenants) merchant forge webhook events that the host application will process as if they originated from a **different shop**, since `WebhookMetadata.shop` (derived purely from the spoofable header) is what host applications typically use to look up the tenant session/record to act on.

### Impact Explanation
This breaks the tenant-identity binding the HMAC is meant to enforce and enables cross-tenant confusion/injection: an app that uses `WebhookMetadata#shop` to select which tenant's data to mutate (e.g., process an order, redact data, update a subscription record, disable/enable features) can be tricked into applying attacker-supplied webhook body content under a victim shop's identity, without ever compromising `api_secret_key` beyond what any installed merchant already legitimately possesses access to via genuine webhook traffic to their own endpoint. This matches the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is realistic for any app with more than one installed merchant: the attacker needs no privileged credentials — only to have installed the app once (standard, unprivileged onboarding) and observed one authentic webhook delivery. The `X-Shopify-*` headers are attacker/replay-controlled from the point of view of this gem's verification logic, since `Registry.process` does not re-derive or bind `shop`/`topic`/`webhook_id` to the signed payload.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or otherwise cryptographically bind them) in the HMAC-covered signable string for webhook requests, or independently verify that the `shop` header value matches an actively registered/expected session for that shop before dispatching to handlers. At minimum, document and enforce that host applications must cross-check `request.shop` against the session/tenant context they expect, rather than trusting it as authenticated metadata.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and registers a webhook (e.g., `orders/create`).
2. Shopify delivers a legitimate webhook to the app's endpoint:
   - Body: `{"id":1,...}` (raw body signed correctly)
   - Headers: `X-Shopify-Hmac-Sha256: <valid_hmac_of_body>`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: orders/create`
3. Attacker replays the exact same request but modifies only the headers:
   - `X-Shopify-Shop-Domain: victim.myshopify.com`
   - (optionally) `X-Shopify-Topic`, `X-Shopify-Webhook-Id`
   - Body and `X-Shopify-Hmac-Sha256` unchanged.
4. `ShopifyAPI::Utils::HmacValidator.validate` recomputes the HMAC from the unchanged raw body and the shared `api_secret_key`, matches the unchanged received HMAC, and returns `true`: [5](#0-4) 
5. `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, even though the payload never touched Shopify's servers for `victim.myshopify.com`: [3](#0-2)
