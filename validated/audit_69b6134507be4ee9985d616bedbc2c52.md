### Title
Unbounded Solver Loss from Uniswap V4 Pool-Price Manipulation in Simplex Venue Pricing (Flash-Loan Oracle Attack) - ([File: sdk/packages/simplex/src/strategies/fx.ts])

### Summary
The reported JulSwap exploit is a classic single-block AMM reserve manipulation: the attacker used a flash swap to move a pool's reported price and then round-tripped it against a protocol that trusted that live price as ground truth, extracting far more value than deposited. Hyperbridge's Simplex intent-solver has the same shape of vulnerability: for "venue-priced" pairs it reads the *current* spot price straight off a Uniswap V4 pool (`sqrtPriceX96`) and uses it, unclamped, to size how much of the solver's own inventory to hand out for a fill.

### Finding Description
For curveless (venue-priced) trading pairs, `FXFiller.resolveLegRates` obtains the fill rate from `venuePriceMemo()` → `getVenueUsdPrice` → `UniswapV4FundingPlanner.getExoticTokenPrice`, which is derived from `computeDirectPoolPriceUsd`, the **raw pool mid** taken directly from the pool's live `sqrtPriceX96`/tick state [1](#0-0) . As the flow documentation states, this price is extended **linearly across the whole priced quantity with no size or impact term**, and the pool's own fee tier is never applied to the quote [2](#0-1) .

The only defense against a manipulated quote is `checkPriceGuard`, which compares the live venue price to a **static** operator-configured `referencePrice` within `maxDeviationBps` [3](#0-2) . This guard is explicitly optional — a chain with no configured `referencePrice`/`maxDeviationBps` pair is left completely unguarded [4](#0-3) , and even when configured it only bounds deviation from a fixed number, not from a TWAP or recent history, so an attacker can move the pool with a flash loan to any price within that static band.

Critically, the second layer of defense — an overfill ceiling that used to cap payout at `(1 + maxOverfillBps) × user-requested` — has been intentionally disabled. The code comment states this outright: *"the clamp is DISABLED, so the filler fills the full computed amount even when it exceeds ... including venue-priced legs (e.g. Uniswap V4). NOTE: this removes the per-leg loss bound that previously protected against a bug / stale cache / **manipulated venue price**. Output is no longer capped; we only emit a warning."* [5](#0-4) 

So the chain is: attacker flash-manipulates the V4 pool → `computeDirectPoolPriceUsd` reads the skewed mid → `checkPriceGuard` either isn't configured or the manipulation is kept inside the static band → `calculateProfitability` computes `policyMaxOutput` from the skewed rate → the disabled overfill clamp lets that full, unbounded amount be paid out from the solver's wallet balance and Uniswap V4 LP position withdrawals (`UniswapV4FundingPlanner.planWithdrawalForToken`), all funded atomically via ERC-7821 batched calls in the same fill transaction [6](#0-5) .

### Impact Explanation
An attacker who can transiently move a thin/manipulable Uniswap V4 pool's price (flash loan or large same-block swap) can induce the Simplex solver to fill an intent order at a distorted rate and pay out solver-held inventory (wallet balance plus withdrawn LP funds) far in excess of fair value, with no output ceiling to bound the loss. This is concrete theft of solver-controlled funds, directly analogous to the JulSwap flash-loan exploit's reserve manipulation → mispriced swap → drain pattern.

### Likelihood Explanation
Requires: (1) a venue-priced pair configured without a `referencePrice`/`maxDeviationBps` guard, or a pool cheap enough to move price within the configured band; and (2) the attacker to be the order placer (or coordinate with one) so the manipulated-price fill lands in the same window as the price move. Both preconditions are realistic — the guard is opt-in per chain, and Uniswap V4 pools backing exotic/thin tokens (the documented use case, e.g. cNGN) are typically shallow and cheap to move. The explicit developer comment confirms the team is aware the clamp removal reopens exactly this "manipulated venue price" risk.

### Recommendation
Re-enable an unconditional overfill/output ceiling for venue-priced legs (not just a warning), derive the venue price from a manipulation-resistant source (TWAP/oracle rather than instantaneous `sqrtPriceX96`), and make the price guard (`referencePrice`/`maxDeviationBps`) mandatory rather than optional whenever a pair has no static curve.

### Proof of Concept
1. Operator configures a venue-priced pair (e.g. USDC/CNGN) funded by a Uniswap V4 position on a thin pool, without setting `referencePrice`/`maxDeviationBps` (both optional) [7](#0-6) .
2. Attacker flash-loans and swaps in the underlying V4 pool to push `sqrtPriceX96` to a rate favorable to itself.
3. In the same block, attacker (or an accomplice) places/fills an IntentGateway order sized against the exotic token; `FXFiller.calculateProfitability` reads the skewed price via `computeDirectPoolPriceUsd`, computes an inflated `policyMaxOutput`, and — because the overfill clamp is disabled — pays out the full unclamped amount, sourcing the deficit from the solver's V4 LP position via `planWithdrawalForToken` [8](#0-7) .
4. Attacker reverses the flash-loan swap, restoring the pool to its original price, keeping the excess output token extracted from the solver.

	/**
	 * Validates a live venue quote against the static reference price for the chain.
	 * Returns true (pass) when no guard is configured, or no reference exists for the
	 * chain. Returns false when the quote (token1 per USD) deviates from the reference
	 * by more than `maxDeviationBps`, in which case the order must not be filled.
	 */
	private checkPriceGuard(orderId: string | undefined, chain: string, venueToken1PerUsd: Decimal): boolean {
		const guard = this.priceGuard?.get(chain)
		if (!guard || guard.reference.lte(0)) return true

		const deviationBps = venueToken1PerUsd.minus(guard.reference).abs().div(guard.reference).mul(10000)
		if (deviationBps.gt(guard.maxDeviationBps)) {
			this.logger.warn(
				{
					orderId,
					chain,
					venuePrice: venueToken1PerUsd.toString(),
					referencePrice: guard.reference.toString(),
					deviationBps: deviationBps.toFixed(2),
					maxDeviationBps: guard.maxDeviationBps,
				},
				"Rejecting order: Uniswap venue quote outside price-guard band",
			)
			return false
		}
		return true
	}

## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.
