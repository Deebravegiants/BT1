Looking at the webhook processing path, the shop identity is not bound to the cryptographic signature — this is a concrete instance of the "field acted on but not covered by the HMAC" bug class.### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the `X-Shopify-Shop-Domain` header, but the HMAC signature validated by `Utils::HmacValidator` only covers the raw request body. This breaks the intended binding of "the shop that produced the signed bytes" == "the shop the app trusts and acts on," letting an attacker who possesses one validly-signed webhook body reuse it against a different shop identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `Request#shop` is read from an unauthenticated header that plays no part in that signable string: [2](#0-1) 

`Registry.process` validates the HMAC over this body-only string, and — once validation passes — immediately trusts `request.shop` to build the `WebhookMetadata` handed to the app's handler, without any additional check that the shop matches the signed payload: [3](#0-2) 

`Utils::HmacValidator.validate` confirms this: it only compares an HMAC computed from `verifiable_query.to_signable_string` (the raw body, in this case) against the received signature; it has no knowledge of or binding to the `shop-domain` header: [4](#0-3) 

This is the same bug class as the report: an identity field (`token_mint`/here `shop`) is *used* to determine trust/routing but is not *cryptographically bound* to the artifact that was validated (the deposit record/here the HMAC-signed body). The equality that should hold is:

`shop_that_produced_the_signed_bytes == shop_trusted_by_the_handler`

but nothing enforces it — the second side of the equation is taken from an arbitrary, unsigned header.

### Impact Explanation
Any unprivileged party who can install the app on their own store (or otherwise obtain one legitimately Shopify-signed webhook body+HMAC for any topic) can capture that raw body and its valid `X-Shopify-Hmac-Sha256` value, then replay the exact same bytes to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `Utils::HmacValidator.validate` still succeeds because it never inspects the domain, and `Registry.process` dispatches the payload to the app's handler tagged as belonging to the victim shop. If the host application's webhook handler uses `WebhookMetadata#shop` to select the tenant record to update (which is exactly the documented purpose of that field), the attacker can inject data attributable to another merchant's shop, or overwrite/act on data scoped to that shop — a cross-tenant access breach. This matches the "Critical – cross-tenant access" impact bucket in the rules.

### Likelihood Explanation
The attacker does not need `api_secret_key`, an access token, or any privileged credential — only a normal, unprivileged installation of the app on their own store (which yields legitimately signed webhook traffic they can capture and later replay with modified headers), fully consistent with the "unprivileged internet user" threat model in scope. The vulnerable code path (`Request#shop`, `to_signable_string`, `Registry.process`) is exercised on every webhook delivery and is part of this gem's own, in-scope logic (`lib/shopify_api/webhooks/**`), not a resource excluded by the rules.

### Recommendation
Bind the shop identity to the HMAC-verified artifact instead of trusting a free header:
- Extend `Request#to_signable_string` (or add a companion signed context) to incorporate the `shop-domain` header (and ideally `webhook-id`/`topic`) into the value that is HMAC-verified, so tampering with those headers invalidates the signature.
- Alternatively, cross-check `request.shop` against a known/authorized shop list (e.g., a shop with an existing, valid session/installation) before dispatching to the handler, rejecting the webhook if the header doesn't correspond to a store that legitimately installed the app.
- Document explicitly (and enforce in code, not merely in docs) that consumers must not treat `WebhookMetadata#shop` as authenticated unless the library itself is binding it to the signature.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (unprivileged, self-service).
2. Shopify sends a legitimate webhook (e.g., `orders/create`) to the app's endpoint:
   - Headers: `X-Shopify-Topic: orders/create`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`
   - Body: `{"id": 1, ...}` (attacker fully controls the content of orders/products/etc. in their own shop, so they can shape the JSON payload).
3. Attacker captures the raw body and the valid HMAC header value.
4. Attacker resends an HTTP POST to the same webhook endpoint, keeping body and `X-Shopify-Hmac-Sha256` identical, but replacing `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) succeeds because it only checks the (unchanged) body against the (unchanged) HMAC.
6. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) calls the app's handler with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body, even though that payload was never actually sent by or about `victim-shop`.
