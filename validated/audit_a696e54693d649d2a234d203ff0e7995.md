Confirmed: the OAuth `AuthQuery#to_signable_string` includes `shop` in the signed payload (so the OAuth callback path binds `shop` to the HMAC), but `Webhooks::Request#to_signable_string` returns only `@raw_body` — none of the `shop`, `topic`, `webhook-id`, or `api-version` headers are covered by the HMAC computed in `HmacValidator.validate`.### Title
Webhook shop identity is not bound by the HMAC, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body via `Utils::HmacValidator.validate(request)`. The `shop` (and `topic`, `webhook-id`, `api-version`) values used to route and attribute the webhook to a tenant are taken from HTTP headers that are never included in the signed payload, so the equality the code implicitly relies on — "HMAC-verified sender == `request.shop`" — does not actually hold.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, and its `to_signable_string` returns only the raw body: [1](#0-0) 

The `shop` accessor is derived from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never part of the signed string: [2](#0-1) 

`Registry.process` validates only the HMAC (body integrity/authenticity), then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build `WebhookMetadata` and dispatch to the app's handler: [3](#0-2) [4](#0-3) 

This is a direct contrast with the OAuth callback path in the same gem, which does bind `shop` into the signed payload before trusting it: [5](#0-4) 

Because `HmacValidator.validate` only proves "the body was signed with the app's secret at some point," and does not prove which shop or topic that signature was originally issued for, any party capable of sending an HTTP POST to the app's public webhook endpoint (webhook endpoints are unauthenticated public URLs by design) can take a `(raw_body, hmac)` pair from a webhook that was genuinely delivered for shop A, and resend it with the `shop-domain` header changed to shop B's domain (or the `topic`/`webhook-id` headers changed). `HmacValidator.validate` will still return `true`, because the HMAC only covers `@raw_body`, which is unchanged. `Registry.process` will then invoke the app's handler with `WebhookMetadata(shop: "shop-b.myshopify.com", ...)` even though the payload was never actually generated for shop B.

The equality being broken:
`HMAC-authenticated field-set == {shop, topic, webhook_id, api_version}` is assumed by `Registry.process`, but in reality `HMAC-authenticated field-set == {raw_body}` only.

An attacker only needs access to one legitimately-delivered webhook body+HMAC (e.g., by installing the target app on their own store and receiving webhooks for their own tenant, or by observing a body/HMAC pair through any non-privileged channel), which does not require the app's `client_secret`, an access token, or any privileged credential.

### Impact Explanation
This breaks a tenant/shop identity binding, letting an attacker cause the host application to process attacker-supplied webhook data under a different shop's identity (cross-tenant confusion). Depending on the app's webhook handlers, this can range from injecting/associating fake data (orders, products, customer PII) with a victim shop, to more severe consequences if handlers act on mandatory topics (e.g., `shop/redact`, `customers/redact`, `customers/data_request`) or `app/uninstalled`-style flows that mutate stored session/tenant state for the shop named in the (unauthenticated) header. This matches the "cross-tenant access" Critical impact category, since a completely unprivileged internet actor can make the app act on behalf of, or misattribute data to, a tenant they do not control.

### Likelihood Explanation
Likelihood is High for reachability: webhook endpoints are inherently public HTTP endpoints, `HmacValidator.validate`/`Registry.process` are exactly the code paths exercised by all Shopify apps built on this gem, and no secret material is required to replay a body/HMAC pair with a different shop header — only network access. The main precondition is that the attacker must first obtain one valid `(raw_body, hmac)` pair, which is easily satisfied by an attacker who installs the target app on their own shop (a normal, unprivileged action) and simply captures webhooks delivered to their own endpoint before replaying them with a spoofed shop header.

### Recommendation
- Include `shop`, `topic`, and `webhook_id` in the signable/verified payload for webhooks (or otherwise cryptographically bind them to the body before verification), not just the raw body.
- Alternatively, require host applications to cross-check `request.shop` against a shop the topic's payload itself asserts (e.g. a `shop_id`/`domain` field in the JSON body) rather than trusting the header alone.
- At minimum, document prominently that `HmacValidator.validate` on webhook requests only authenticates the body and does not bind `shop`/`topic`/`webhook_id`, and that callers must not treat `request.shop` as authenticated without additional checks.

### Proof of Concept
1. Install the target app (built on this gem) on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook topic the app subscribes to (e.g. `orders/create`). Capture the raw POST body and the `x-shopify-hmac-sha256` header Shopify sent — both are visible to the attacker as the receiving party.
2. Resend an HTTP POST to the app's webhook endpoint with:
   - The same raw body and the same `x-shopify-hmac-sha256` value captured in step 1.
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (any target shop domain).
   - `x-shopify-topic` optionally changed as well, since it also isn't covered by the signature.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)` — this succeeds because it only checks the (unmodified) raw body against the HMAC: [6](#0-5) 
4. `Registry.process` dispatches to the handler with `shop: request.shop` set to `victim-shop.myshopify.com`, even though the payload was generated for `attacker.myshopify.com`: [7](#0-6)
