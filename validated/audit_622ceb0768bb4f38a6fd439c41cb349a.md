### Title
Malicious swap routes can attach unauthorized wallet-token transfers to a caller's signed authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary

Strategy entrypoints accept caller-supplied route bytes and invoke the configured router under the account caller's root authorization, while route instructions select arbitrary pool addresses without an on-chain pool allowlist. [1](#0-0) [2](#0-1) [3](#0-2)  A malicious route can therefore place attacker-controlled code below the signed strategy invocation and request a token transfer from the caller to an attacker; if the victim signs the simulated authorization tree containing that child transfer, the protocol operation and unrelated wallet-token theft both execute atomically. [4](#0-3) [5](#0-4) 

### Finding Description

`swap_collateral` authenticates `caller` and verifies account ownership or delegation, but then forwards unvalidated user-provided `swap` bytes into `withdraw_and_swap_from_supply`. [6](#0-5)  `swap_tokens` authorizes only the controller's exact input transfer to the configured router, yet passes the entire caller-controlled payload to `router.execute_strategy` inside that same transaction. [7](#0-6)  The router decodes payload-selected pool addresses and dispatches each hop to the venue adapter, with no production-code check that the pool belongs to a known or approved deployment. [3](#0-2) [8](#0-7)  Because the venue call runs below `sender.require_auth()` initiated by the controller call, a malicious pool contract can invoke `transfer(caller, attacker, amount)` on any unrelated token; the host records that request as a child of the caller's strategy authorization and executes it when the returned authorization tree is signed. [9](#0-8) [10](#0-9)  The post-swap checks only measure controller-held `token_in` and `token_out` balances, so they cannot detect or bound a transfer from the caller's wallet in a different token. [11](#0-10) 

### Impact Explanation

A victim who signs a poisoned route can lose arbitrary balances of unrelated wallet tokens in the same transaction, while the requested collateral operation can still produce valid output and pass the controller's post-swap checks. [12](#0-11) [11](#0-10)  The theft is not limited to the swapped protocol collateral because the malicious venue can request a transfer from the account caller rather than from the router or controller. [13](#0-12) [2](#0-1) 

### Likelihood Explanation

The attacker needs to get a victim to sign a crafted strategy transaction, so this is a user-interaction exploit rather than an unauthenticated remote drain. [4](#0-3)  Once signed, execution requires no privileged key, leaked credential, oracle manipulation, failed market state, or special protocol permission: the controller forwards arbitrary `Bytes`, and the router resolves the payload's pool address directly. [1](#0-0) [14](#0-13)  The same reachable pattern applies to every route-bearing strategy—`multiply`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral`—because they share the `swap_tokens` router path. [15](#0-14) [16](#0-15) 

### Recommendation

Constrain route execution to governance-approved or venue-verified pool addresses before dispatching a hop, so route bytes cannot place arbitrary contract code below the caller's authorization root. [3](#0-2)  Keep the controller's exact input authorization and measured-output checks, but additionally require wallets and quote integrations to decode the simulated authorization tree and reject any child invocation other than the expected token pull for the selected operation. [17](#0-16) [10](#0-9) 

### Proof of Concept

1. Victim owns a valid account and calls `swap_collateral(caller=victim, account_id, current=USDC, amount=A, new=ETH, swap=route)`; the existing checks authenticate the victim and validate the account before routing. [6](#0-5) 
2. The attacker-crafted `route` names an attacker-deployed contract as the hop `pool`, while setting a positive `min_out` so the router can settle normally. [18](#0-17) [12](#0-11) 
3. During dispatch, that malicious pool's venue-compatible function calls `Token.transfer(victim, attacker, victim_balance)` for an unrelated token held in the victim's wallet. [3](#0-2) 
4. Simulation returns a `swap_collateral` authorization tree containing that transfer as a child invocation; signing it satisfies both the strategy call and the unrelated token transfer. [4](#0-3) [9](#0-8) 
5. The pool returns or routes enough output for the swap checks to succeed, causing the unrelated wallet-token theft and the collateral swap to commit in one transaction. [19](#0-18) [20](#0-19)

/// Passes matching assets through only with an empty route; otherwise swaps.
pub(crate) fn swap_tokens_or_passthrough(
    env: &Env,
    refund_to: &Address,
    token_in: &Address,
    amount_in: i128,
    token_out: &Address,
    swap: &StrategySwap,
) -> i128 {
    if token_in == token_out {
        assert_with_error!(env, swap.is_empty(), GenericError::InvalidPayments);
        amount_in
    } else {
        swap_tokens(env, refund_to, token_in, amount_in, token_out, swap)
    }
}

/// Returns the output balance increase; rejects zero or negative receipts.
fn verify_router_output(env: &Env, token_out: &Address, balance_before: i128) -> i128 {
    let received = balance_delta_since(
        env,
        token_out,
        &env.current_contract_address(),
        balance_before,
    );
    assert_with_error!(env, received > 0, StrategyError::NoSwapOutput);
    received
}

/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
}
