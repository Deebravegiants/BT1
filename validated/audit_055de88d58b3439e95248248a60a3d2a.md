Found a concrete analog to the CVE's bug class (an unbounded loop driven by attacker-controlled/untrusted data with unclear termination bounds) in the GRANDPA ancestry-walk used to verify BEEFY/GRANDPA finality justifications.

### Title
Infinite/DoS loop in `AncestryChain::ancestry` walk when a precommit target has a cyclic parent-hash chain in attacker-supplied `votes_ancestries` - (File: `modules/consensus/grandpa/primitives/src/justification.rs`)

### Summary
`GrandpaJustification::verify_with_voter_set` builds an `AncestryChain` from the untrusted, relayer-supplied `votes_ancestries` header list and then walks it with `ancestry()` to prove that each precommit target routes back to the finality base hash [1](#0-0) . The walk itself is an unbounded `while` loop that follows `parent_hash()` pointers taken directly from the untrusted header set until it reaches `base`, with no depth limit and no cycle detection [2](#0-1) .

### Finding Description
`AncestryChain::new` indexes the submitted headers by their own hash into a `BTreeMap` [3](#0-2) . Nothing prevents a submitter from crafting a set of headers whose `parent_hash` pointers form a cycle that never reaches `base_hash` (e.g., header A's parent points to header B, and header B's parent points back to header A, or more generally a long/circular chain reachable from a precommit's `target_hash`). Because `route.push(current_hash)` unconditionally appends on every iteration and the loop condition is only `current_hash != base`, a cyclic or sufficiently long chain drives the loop (and the `route` vector) to grow without the intended termination — this is architecturally the same defect class as CVE-2017-9346, where a protocol parser trusted an attacker-controlled structure to eventually satisfy a loop-exit condition instead of bounding the loop independently (e.g., against `votes_ancestries.len()`).

This routine is reached from the GRANDPA consensus client's `verify_consensus` path, which is invoked by any relayer submitting a consensus update/justification for verification — an unprivileged, permissionless entry point in Hyperbridge's ISMP consensus pipeline.

### Impact Explanation
An attacker-controlled `votes_ancestries` list can drive `ancestry()` into an effectively unbounded loop (bounded only by the size of the supplied header vector via `BTreeMap` lookups failing, but a crafted cycle among the submitted headers can loop for as many iterations as there are cyclic hops before eventually failing to find the next hash — worst case this is proportional to the attacker-chosen ancestry list size, which can be made very large within extrinsic/proof size limits). This ties up computation during consensus-client processing, which is on the hot path used to import parachain/relay-chain headers and update BEEFY/GRANDPA-relayed state commitments. If it can be made to consume disproportionate resources relative to the fee paid, it degrades or blocks timely delivery of legitimate consensus updates and therefore blocks the relaying of ISMP messages that depend on that state root being updated (a "route unable to deliver messages" condition).

### Likelihood Explanation
Medium: the `votes_ancestries` field, the precommit `target_hash` values, and the header contents are all supplied directly in the untrusted consensus proof passed to `verify_consensus`; a submitter fully controls the shape of the ancestry map and can attempt to construct a cycle or a maximal-length non-terminating chain. It does require crafting header hashes that self-reference (or a long dangling chain) which is straightforward since header hashing here is over attacker-supplied header contents rather than a chain that must match real chain state until the final signature/commit check.

### Recommendation
Bound the `ancestry()` walk independently of the data it is walking — e.g., limit the number of iterations to `self.ancestry.len() + 1` (the walk can never legitimately need more hops than there are distinct headers) and return `finality_grandpa::Error::NotDescendent` once that bound is exceeded, mirroring the loop-bound fix applied for CVE-2017-9346 in the SoulSeek dissector (make the bound explicit rather than relying on eventually reaching `base`).

### Proof of Concept
1. A relayer submits a `GrandpaJustification` whose `commit.precommits` contains a precommit with `target_hash = H1`.
2. `votes_ancestries` includes crafted headers `H1 -> parent H2`, `H2 -> parent H1` (a 2-cycle), none of which equal `base_hash`.
3. `verify_with_voter_set` calls `ancestry_chain.ancestry(base_hash, H1)`, which enters the `while current_hash != base` loop in `ancestry()` and toggles between `H1` and `H2` indefinitely (or for as many iterations as the attacker pads the cycle with distinct headers before failing), consuming CPU disproportionate to the extrinsic's declared complexity before ultimately failing lookups only when the map is exhausted.

**Caveat:** I was not able to fully verify the exact worst-case iteration bound in the current Substrate weight/gas metering for this specific extrinsic path (i.e., whether the runtime's benchmarked weight already caps total execution here), because that requires tracing the pallet dispatch weight annotations, which I did not locate in the indexed content. This is a limitation of the fix's severity, not of the vulnerable code path itself — the loop shown at [4](#0-3)  lacks the explicit bound that this class of bug (CVE-2017-9346) is defined by lacking.

	fn ancestry(
		&self,
		base: H::Hash,
		block: H::Hash,
	) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
		let mut route = vec![block];
		let mut current_hash = block;
		while current_hash != base {
			match self.ancestry.get(&current_hash) {
				Some(current_header) => {
					current_hash = *current_header.parent_hash();
					route.push(current_hash);
				},
				_ => return Err(finality_grandpa::Error::NotDescendent),
			};
		}
		Ok(route)
	}
