### Title
Webhook tenant identity (`shop`) is not covered by the HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authenticated for a given shop once `Utils::HmacValidator.validate` succeeds, but the HMAC signature only covers the raw request body — never the `shop`, `topic`, `webhook_id`, or `api_version` values, which are all read directly from unauthenticated HTTP headers. This breaks the identity binding `shop authenticated == shop used as tenant key`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is parsed straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the signed body: [2](#0-1) 

`Utils::HmacValidator.validate_signature` computes the HMAC exclusively over `verifiable_query.to_signable_string` (i.e., the body) and compares it to the `hmac` header value: [3](#0-2) 

`Registry.process` performs only this body-HMAC check, then immediately trusts `request.shop` as the tenant identity and forwards it to the app's handler: [4](#0-3) 

The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify" and describes `data.shop` as "The shop domain of the webhook," instructing consuming apps to key work off it (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`): [5](#0-4) 

Because the app's `client_secret` (used to compute the HMAC) is shared across *all* shops that have installed the app, and the signature never binds the `shop` header, an attacker who legitimately controls one tenant (Shop A) of a multi-tenant app can:
1. Trigger a genuine webhook with attacker-chosen body content (e.g., by creating an order/product with attacker-controlled fields), which Shopify signs correctly with the app's `client_secret` over that body.
2. Capture that HTTP request and resend it to the app's webhook endpoint, only replacing the `X-Shopify-Shop-Domain` header with a victim tenant's domain (Shop B), leaving the body and its valid HMAC untouched.
3. `HmacValidator.validate` still passes (body unchanged), `Registry.process` builds `WebhookMetadata` with `shop: "shop-b.myshopify.com"`, and the handler processes attacker-controlled data as if it belongs to Shop B.

### Impact Explanation
This allows cross-tenant data injection/corruption: an attacker-controlled payload is delivered to the app's business logic tagged with a victim shop's identity, since the library provides no mechanism (and the docs give false assurance) that the `shop` value has been authenticated. This matches the Critical "cross-tenant access" impact category, since the tenant boundary that the gem is documented to enforce via HMAC validation is not actually enforced for the `shop` field.

### Likelihood Explanation
Any developer building a multi-tenant app on this gem who follows the documented pattern (using `data.shop` from `WebhookMetadata` as the trusted tenant key, as shown in the gem's own docs) is exposed. The only prerequisite is that the attacker be a legitimate (if malicious) installer of the app on their own shop — no access to `api_secret_key`, access tokens, or other tenants' credentials is required, and no TLS interception or social engineering is needed.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header values in the signed material, or otherwise cryptographically bind the shop identity to the HMAC-validated payload, e.g. by validating that `request.shop` matches an out-of-band-verified value (such as the shop associated with the specific webhook subscription/registration) rather than trusting the raw header. At minimum, update the documentation to explicitly warn that `data.shop` is not covered by the HMAC and must not be treated as authenticated without additional verification (e.g., cross-checking against a known list of installed shops).

### Proof of Concept
```ruby
# Attacker owns Shop A (installed the target app) and captures/produces a genuine webhook:
body = '{"id":1,"note":"malicious payload"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_client_secret, body)

# Attacker resends the same body+hmac but swaps the shop-domain header to the victim tenant:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate passes (body unchanged); handler receives
# WebhookMetadata(shop: "victim-shop.myshopify.com", body: attacker-controlled JSON)
```
