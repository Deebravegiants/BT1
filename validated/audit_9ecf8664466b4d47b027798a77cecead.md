### Title
Timelock override_threshold can be silently invalidated by later `num_signatures_required` updates, allowing owners to bypass the configured multisig timelock - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
The multisig timelock feature is meant to force a waiting period before a transaction can execute unless an elevated `override_threshold` of approvals is reached. `upsert_timelock_internal` enforces `override_threshold > num_signatures_required` only at the moment the timelock is set [1](#0-0) . However, `num_signatures_required` can later be changed independently via `update_signatures_required` / `add_owners_and_update_signatures_required` / `swap_owners_and_update_signatures_required`, all of which funnel into `update_owner_schema`, which updates `num_signatures_required` with no re-validation against the existing timelock's `override_threshold` [2](#0-1) .

### Finding Description
`can_execute_with_timelock` allows immediate execution, bypassing the timelock wait, whenever `num_approvals >= override_threshold` [3](#0-2) . The invariant the whole timelock feature depends on is `override_threshold > num_signatures_required`, guaranteeing that reaching normal quorum (`num_signatures_required`) alone is never enough to skip the wait — an attacker/majority coalition must also gather the higher override count.

That invariant is enforced only inside `upsert_timelock_internal` at configuration time [4](#0-3) , and it is never re-checked afterward. `update_owner_schema` is the single choke point for all owner/threshold-changing operations (`add_owners_and_update_signatures_required`, `remove_owners`, `swap_owner(s)`, `swap_owners_and_update_signatures_required`, `update_signatures_required`) [5](#0-4) . When `optional_new_num_signatures_required` is set, it is applied unconditionally: `multisig_account_ref_mut.num_signatures_required = new_num_signatures_required;` with only a `>0` check, no comparison to any active `MultisigAccountTimeLock.override_threshold` [6](#0-5) .

Consequently, once a timelock has been configured (e.g. `override_threshold = 4`, `num_signatures_required = 2`), the owners (via the normal proposal flow, requiring only the pre-update `num_signatures_required` quorum) can pass a self-update transaction raising `num_signatures_required` to `4` or higher (up to the owner count) — or removing owners so the existing `num_signatures_required` now exceeds/equals `override_threshold`. After this, `override_threshold <= num_signatures_required`, so any future transaction that reaches ordinary quorum (`num_approvals >= num_signatures_required`) automatically also satisfies `num_approvals >= override_threshold`, and `can_execute_with_timelock` returns `true` immediately regardless of elapsed time — nullifying the timelock's delay protection for all subsequent pending and future transactions on that multisig account, including transfers of APT/coins/objects the multisig account (a resource account) custodies.

### Impact Explanation
The timelock is a custody control meant to give owners/monitors a mandatory window to detect and react to a malicious pending transaction (e.g. a fund-draining payload) before it can execute, unless a supermajority overrides it. By silently degrading `override_threshold` relative to `num_signatures_required` through an ordinary, lower-quorum administrative transaction, a coalition of owners meeting only the normal `num_signatures_required` threshold can permanently and silently remove the intended stronger protection, then immediately execute a transaction that moves any APT, coin, or object-held assets controlled by the multisig account — defeating the entire purpose of the timelock without ever reaching the supposedly-required override quorum. This breaks the custody invariant that asset-moving execution requires either full elapsed timelock or the higher override quorum.

### Likelihood Explanation
This requires no external inputs or admin privilege beyond what a normal multisig owner already has: any owner set that can already muster `num_signatures_required` approvals (which they must be able to do to operate the account at all) can pass an `update_signatures_required` (or equivalent) transaction. No special timing, race condition, or privileged network position is needed — it's reachable through ordinary transaction flow of the multisig module itself.

### Recommendation
When updating `num_signatures_required` (or removing owners such that the owner count changes) in `update_owner_schema`, re-validate any existing `MultisigAccountTimeLock` for the account and either: (a) abort the update if it would make `override_threshold <= new_num_signatures_required` or `override_threshold > new_owner_count`, or (b) automatically clear/require an explicit re-confirmation of the timelock configuration whenever the owner/threshold schema changes.

### Proof of Concept
1. Owner set `{A,B,C,D}` creates a multisig account with `create_with_owners_and_timelock`: `num_signatures_required = 2`, `timelock_period = 1 day`, `override_threshold = Some(4)` (validated `4 > 2` and `4 <= 4` at line 944-951).
2. `A` and `B` (meeting the `2`-of-`4` quorum) create and approve a transaction calling `update_signatures_required(multisig_signer, 4)` via the normal proposal flow — this passes with only 2 approvals since it is itself just a normal multisig transaction subject to the pre-existing `num_signatures_required = 2`.
3. `update_owner_schema` sets `num_signatures_required = 4` with no check against `MultisigAccountTimeLock.override_threshold` [6](#0-5) .
4. Now `override_threshold (4) <= num_signatures_required (4)`. Any subsequent transaction that only reaches ordinary quorum (`4` approvals, now required anyway) will also satisfy `can_execute_with_timelock`'s override branch immediately (`num_approvals >= override_threshold`), so `elapsed >= timelock` is never actually needed — the timelock's delay is void for every future transaction, including a value-draining payload transferring the multisig's custodied APT/coins/objects.

    inline fun can_execute_with_timelock(multisig_account: address, sequence_number: u64, num_approvals: u64): bool {
        if (exists<MultisigAccountTimeLock>(multisig_account)) {
            let multisig_account_resource = &MultisigAccountTimeLock[multisig_account];
            let timelock = multisig_account_resource.timelock_period;
            let override_threshold = multisig_account_resource.override_threshold;

            // Get the pending transaction to check if the timelock has expired
            // Assume that the transaction has already been checked to exist and is valid
            let pending_transaction = get_transaction(multisig_account, sequence_number);

            // Use subtraction to avoid overflow (now_seconds() >= creation_time_secs is always true)
            let elapsed = now_seconds() - pending_transaction.creation_time_secs;

            // If the number of approvals meets the override threshold, or the timelock has expired, allow execution
            (override_threshold.is_some() && &num_approvals >= override_threshold.borrow()) || elapsed >= timelock
        } else {
            true
        }
    }
