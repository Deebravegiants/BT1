### Title
Donated LT permanently stranded in a graduated Pair with no recovery mechanism - ([File: packages/contracts/src/Router.sol], [File: packages/contracts/src/Pair.sol])

### Summary
LT donated directly to a curve `Pair` (via a bare `IERC20.transfer`) is intentionally excluded from graduation's LP-seeding math, but once graduation completes there is no function anywhere in scope that can ever move that LT back out of the `Pair`. This mirrors the reported bug class: an asset that becomes unreachable once the contract's normal lifecycle moves past the point where it was handled.

### Finding Description
`Bonding._prepareGraduationLiquidity` computes `ltFromPair = assetReserve - _launchTimeVirtualLtReserve(...)`, i.e. exactly the *stored* reserve, deliberately excluding any LT sent directly to the pair via `transfer` (which only bumps the live ERC20 balance, not `_pool.assetReserve`) [1](#0-0) . That exact `ltFromPair` amount is drained via `Router.graduate(token, ltFromPair)`, which is the only function in `Router` that calls `Pair.transferAsset` outside of the `sell` swap path [2](#0-1) .

`Pair.transferAsset` is gated `onlyRouter`, and `Router.graduate`/`Router.sell` are the only two callers, both gated by `BONDING_ROLE` which only `Bonding` holds [3](#0-2) [4](#0-3) . Once `Bonding.finalizeGraduation` sets `info.lifecycle = Lifecycle.Graduated` and clears `pendingGraduation`, the token's curve state can never re-enter `Lifecycle.Curve`, so `_prepareGraduationLiquidity`/`graduate` can never be invoked again for that pair [5](#0-4) . `Bonding.sell` (which is the other path to `Pair.transferAsset`) is also gated to `Lifecycle.Curve` tokens. There is no admin rescue function on `Pair`, `Router`, or `Bonding` that can pull residual `assetToken` (LT) balance out of a `Pair` after graduation.

The code's own comment acknowledges this is a deliberate but unenforced trust assumption, not an on-chain safety net: *"'Locked' here is a trust-assumption claim, not an on-chain guarantee... the leftover is unreachable as long as (a) BONDING_ROLE is not granted to any other address, and (b) future Bonding upgrades preserve the lifecycle gate."* [6](#0-5) . This is precisely the "removed collateral can't be accessible" bug class from the reference report generalized to alt.fun: an asset (LT donated to a `Pair`) becomes permanently unreachable once the container object's lifecycle advances past the phase where the code path to release it exists, with no swap-to-another-asset or admin-sweep mechanism ever provided.

The documentation itself confirms this is an accepted, real, permanent lock: *"Donated LT remains in the curve pair, reachable only via `Pair.transferAsset` which is gated by Router's `BONDING_ROLE`."* [7](#0-6) , and the invariant doc states assetBalance() only reaches 0 "when no donations occurred" — donated LT is explicitly excluded from LP seeding and left behind [8](#0-7) .

### Impact Explanation
Any unprivileged wallet can send any amount of the reserve LT directly to a `Pair` contract address (a simple ERC20 `transfer`) at any point before graduation. This LT never enters the LP, never gets refunded, and after `finalizeGraduation` runs there is permanently no code path capable of retrieving it — it is frozen forever inside the `Pair` contract. This satisfies "permanent freezing of trader/creator/LP funds": the donor's own LT (and, since anyone can donate to any live curve pair, an attacker could also donate to grief a legitimate holder's funds if such funds were routed through the pair) becomes unrecoverable. The magnitude is bounded only by how much LT a caller chooses to send before the pair graduates.

### Likelihood Explanation
Trivial to trigger: the only action required is a plain ERC20 `transfer(pairAddr, amount)` of the LT token to a live, ungraduated curve `Pair`, callable by any address with LT balance, no special permissions or timing needed beyond "before that token's graduation finalizes." This can happen accidentally (a user mistakenly sending LT to the pair address instead of using `Zap.buy`) or deliberately.

### Recommendation
Add a permissionless or owner-gated sweep function reachable after `Lifecycle.Graduated` (e.g., on `Bonding` or `Router`, guarded to only ever move `assetBalance() - 0` residual after graduation) that transfers any leftover LT sitting in a graduated `Pair` to a recoverable destination — e.g., `FeeVault`, the token's creator, or back to donors via a tracked-donation mechanism — instead of leaving it permanently locked with no code path.

### Proof of Concept
1. Attacker/user calls `IERC20(lt).transfer(pairAddr, X)` on a live curve pair (`Lifecycle.Curve`), directly increasing `Pair.assetBalance()` by `X` without touching `_pool.assetReserve`.
2. The curve trades normally and eventually graduates via `Bonding._graduate`/`finalizeGraduation`. `_prepareGraduationLiquidity` computes `ltFromPair` strictly from `_pool.assetReserve` (excluding the donation) and only that amount is drained through `Router.graduate` [1](#0-0) .
3. `info.lifecycle` becomes `Lifecycle.Graduated`; `pendingGraduation` is deleted [9](#0-8) .
4. `X` LT remains in `pairAddr`. No function in `Bonding`, `Router`, or `Pair` can be called to move it out: `Router.graduate`/`sell` both require `BONDING_ROLE` + `Lifecycle.Curve` state, which is now permanently unreachable for this token [10](#0-9) . The `X` LT is permanently frozen.

    /// @notice Tokens in → LT out.
    function sell(
        uint256 amountIn,
        address token,
        address to
    ) external onlyRole(BONDING_ROLE) returns (uint256 tokensIn, uint256 assetOut) {
        if (amountIn == 0) revert ZeroAmount();

        address asset = assetTokenFor(token);
        address pairAddr = factory.getPair(token, asset);
        if (pairAddr == address(0)) revert PairNotFound();
        tokensIn = amountIn;

        IERC20(token).safeTransferFrom(to, pairAddr, amountIn);

        assetOut = _computeSell(pairAddr, amountIn);

        IPair(pairAddr).transferAsset(to, assetOut);

        IPair(pairAddr).swap(amountIn, 0, 0, assetOut);
    }

    function _computeSell(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 assetOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        uint256 newReserveToken = reserveToken + amountIn;
        assetOut = reserveAsset - (k / newReserveToken);
    }

    /// @notice Transfer exactly `amount` of LT out of the pair to the caller.
    ///         Called by `Bonding._prepareGraduationLiquidity` during graduation
    ///         with `amount = stored assetReserve - virtualLtReserve` (i.e. the
    ///         real LT raised by the curve, excluding the virtual seed).
    /// @dev    Donation-resistant: passing an explicit `amount` instead of
    ///         draining `assetBalance()` ensures any LT that was donated
    ///         directly to the pair via `IERC20.transfer` is left behind and
    ///         excluded from LP seeding.
    ///
    ///         "Locked" here is a trust-assumption claim, not an on-chain
    ///         guarantee. `Pair.transferAsset` is gated by `onlyRouter`, and
    ///         `Router` only exposes it via this function and `sell`. Both
    ///         require `BONDING_ROLE`, which only `Bonding` holds. `Bonding`
    ///         in turn only calls `graduate` from
    ///         `_prepareGraduationLiquidity` — which is unreachable once the
    ///         token's lifecycle has flipped past `Curve`. So the leftover
    ///         is unreachable as long as (a) `BONDING_ROLE` is not granted
    ///         to any other address, and (b) future `Bonding` upgrades
    ///         preserve the lifecycle gate.
    function graduate(
        address token,
        uint256 amount
    ) external onlyRole(BONDING_ROLE) {
        address asset = assetTokenFor(token);
        address pairAddr = factory.getPair(token, asset);
        if (pairAddr == address(0)) revert PairNotFound();
        IPair(pairAddr).transferAsset(msg.sender, amount);
    }
