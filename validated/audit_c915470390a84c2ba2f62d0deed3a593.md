This confirms the vulnerability. The webhook `hmac-sha256` signature is computed only over `@raw_body` [1](#0-0) , while `shop` is read straight from an attacker-controllable HTTP header with no cryptographic binding to the signed bytes [2](#0-1) . `Registry.process` verifies only the body's HMAC and then dispatches the handler using that unverified `shop` value [3](#0-2) .

### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating that the HMAC-SHA256 signature matches the raw request body [4](#0-3) . The `shop` identity attached to the webhook, however, comes from the `X-Shopify-Shop-Domain` HTTP header, a value that is never included in the signed bytes [2](#0-1) [1](#0-0) . This is structurally the same class of bug as the `CurveSubject` honeypot report: an action-relevant field (`referralFeeDestination`/`shop`) is used by downstream logic without being covered by the integrity check (`_transferFees`'s implicit call/`HmacValidator.validate`).

### Finding Description
`Utils::HmacValidator.validate` computes `HMAC-SHA256(api_secret_key, verifiable_query.to_signable_string)` and compares it against the supplied `hmac` value [5](#0-4) . For webhooks, `to_signable_string` returns only `@raw_body` [1](#0-0) ; the `topic`, `api_version`, `webhook_id` and — critically — `shop` are all read directly from HTTP headers with no participation in the signature [6](#0-5) .

`Registry.process` checks `Utils::HmacValidator.validate(request)` and, if it passes, immediately builds `WebhookMetadata` using `request.shop`, which is passed unmodified to the app's handler: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [3](#0-2) .

The identity binding that should hold is:
`bytes verified by HMAC` == `bytes the handler treats as belonging to a specific shop`

In this gem, that equality is broken: HMAC verification only proves the request body wasn't tampered with; it proves nothing about which shop the body originated from, because `shop` is parsed from an unauthenticated header. Because the API secret key (`api_secret_key`) is shared across every store that installs a given app (it's a per-app, not per-shop, secret), any store owner who installs the app can obtain a genuinely-signed `(raw_body, hmac)` pair simply by triggering a real webhook delivery to their own endpoint from their own store. That attacker can then replay the exact same `raw_body`/`hmac-sha256` pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header value (e.g. a victim's shop domain). `HmacValidator.validate` still succeeds because it never inspects the header, and `Registry.process` dispatches the handler believing the payload originated from the victim shop.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook authenticity: an unprivileged merchant who can install the app on their own store (no special privilege, no access token, no leaked credentials) can forge webhook deliveries that the host application will process as if they came from a different, victim shop. Depending on how the host app's webhook handler acts on `WebhookMetadata#shop` (updating shop records, revoking access on `app/uninstalled`, writing merchant-scoped data, etc.), this enables cross-tenant data corruption or state manipulation attributed to an arbitrary shop identity — matching the Critical "cross-tenant access" impact category, since the gem itself hands the (falsifiable) shop identity to the handler as if it were authenticated.

### Likelihood Explanation
Any developer/merchant can install the target app on their own store to legitimately receive a webhook (obtaining a valid `raw_body` + `hmac-sha256` pair for free, since HMAC only covers the body). Replaying that pair to the app's public webhook endpoint with a modified `shop-domain` header requires nothing beyond basic HTTP tooling — no secret material, no session, and no interaction with Shopify's servers is required beyond the attacker's own store. This makes the finding directly and cheaply reachable by any unprivileged internet user who can install the app once.

### Recommendation
Include `shop` (and ideally `topic`) in the HMAC-verified material for webhooks, or otherwise cryptographically bind the shop identity to the signed payload — e.g. verify the `shop` header value against a shop known to have that specific webhook subscription/`webhook_id` registered (looked up via the Admin API) before dispatching the handler, rather than trusting the header as-is once the body-only HMAC passes.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and registers a webhook (e.g. `orders/create`).
2. Attacker triggers that webhook and captures the legitimate `X-Shopify-Hmac-Sha256` header and raw body Shopify sent to the app's webhook endpoint.
3. Attacker POSTs the exact same raw body and `X-Shopify-Hmac-Sha256` value to the same webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. In `ShopifyAPI::Webhooks::Request.new`, all required headers are present, so construction succeeds [7](#0-6) .
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(api_secret_key, raw_body)` — identical to the value from step 2 — and passes [4](#0-3) .
6. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)`, causing the host app to process attacker-controlled data as belonging to the victim shop [8](#0-7) .
