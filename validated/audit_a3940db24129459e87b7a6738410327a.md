### Title
Webhook `shop`/`topic` identity headers are not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and exposes an HMAC that is verified only over the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values used by `ShopifyAPI::Webhooks::Registry.process` are taken directly from unauthenticated HTTP headers. The identity binding "the shop that the HMAC actually authenticates" == "the shop the gem hands to the app's webhook handler" is broken, allowing a shop's own signed webhook body to be replayed with a forged `shop` header and accepted as valid.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read straight from HTTP headers with no relation to the HMAC at all: [2](#0-1) 

`Utils::HmacValidator.validate` only calls `to_signable_string`/`hmac` for the equality check, so it validates that "this body was produced by someone possessing `api_secret_key`" but never validates "this body belongs to this shop": [3](#0-2) 

`Registry.process` performs the HMAC check and then unconditionally forwards `request.shop` (the unauthenticated header) to the app's handler as the tenant identifier: [4](#0-3) 

Because the signature is computed over `@raw_body` only, any attacker who controls a shop where the app is installed (an ordinary, unprivileged merchant) will legitimately receive HMAC-valid webhook deliveries for their own store. That same attacker can capture such a delivery and resend it to the app's public webhook endpoint with the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header rewritten to name a victim shop. The gem's `HmacValidator.validate` still succeeds, because it only checks the untouched body against the shared secret — it never binds the signature to the shop header. `Registry.process` then calls the handler with `WebhookMetadata` carrying the attacker-chosen `shop`, so the equality "authenticated shop == shop acted upon" does not hold: the request is authenticated as coming from *a* valid webhook sender holding the shared secret, but the shop identity attached to it is attacker-controlled.

### Impact Explanation
Any app that uses `data.shop` from `WebhookMetadata` (the documented, intended use of this API) to select which merchant's records to update, insert, or delete is exposed to cross-tenant data injection/corruption: an unprivileged user who merely installed the app on their own store can produce a body+signature pair that is valid per this gem, then attach any other shop's domain to it. This crosses a tenant boundary using only the capabilities of an ordinary merchant, matching the "cross-tenant access" impact class.

### Likelihood Explanation
Likelihood is high for any app that installs on multiple merchants (which is the standard model for this gem) since obtaining one genuinely-signed webhook body only requires installing the app once, and the forgery step is a trivial header rewrite that this gem does nothing to detect.

### Recommendation
Include the identity fields (`shop`, `topic`, `webhook_id`, `api_version`) in the signable content that `HmacValidator` verifies, or otherwise cryptographically bind the shop header to the signed payload before handing it to `Registry.process`/the app's handler, so the HMAC check enforces "authenticated shop == acted-upon shop."

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com`; Shopify sends a legitimately HMAC-signed webhook: headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid>`, body `{"id":1}`.
2. Attacker captures this request and resends it to the app's webhook endpoint, changing only `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body as usual; `Utils::HmacValidator.validate` recomputes the HMAC over `@raw_body` only — identical to step 1 — and passes: [5](#0-4) 
4. The app's handler receives `WebhookMetadata` with `shop == "victim.myshopify.com"` and a body the attacker fully controls, even though the signature never certified that shop value.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
