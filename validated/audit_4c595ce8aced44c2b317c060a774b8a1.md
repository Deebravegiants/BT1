### Title
Webhook shop identity spoofing via unauthenticated `shop-domain` header not covered by HMAC — ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by HMAC-verifying the raw request body, then hands the caller-supplied `shop-domain` header straight through to the application handler as if it were part of the verified payload. The `shop` field is never included in the HMAC-signed material, so it is not bound to the signature that was just validated.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the HMAC only over `verifiable_query.to_signable_string`, and for webhook requests that string is defined as just the raw body: [1](#0-0) 

`shop` is read from a separate, unsigned HTTP header: [2](#0-1) 

`Registry.process` verifies the HMAC and, once it passes, immediately constructs `WebhookMetadata` using `request.shop` — a value that played no part in the signature check just performed: [3](#0-2) 

The identity binding that should hold is: `shop bound by HMAC == shop delivered to handler`. In reality the equality is: `shop covered by HMAC == {}` (nothing) while `shop delivered to handler == request.shop` (attacker-controlled header). This is structurally the same class of bug as the reported `ForeignContract`/`redeemer_config` issue: a field that participates in downstream trust decisions (there, the registered foreign address; here, the tenant/shop identity) is not covered by the cryptographic binding (there, missing uniqueness constraint; here, missing HMAC coverage) that the rest of the code assumes protects it.

Concretely: an attacker who operates their own shop with the target app installed receives a legitimate webhook delivery from Shopify — a real `(raw_body, hmac)` pair signed with the app's `client_secret`/`api_secret_key` for their own shop. Because the HMAC never covered the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers, the attacker can replay that exact body+HMAC pair directly to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop. `HmacValidator.validate` will still return `true` (the body is unchanged), and `Registry.process` will call the app's handler with `WebhookMetadata#shop` set to the victim's shop domain alongside attacker-supplied body content.

### Impact Explanation
If the host application uses the `shop` value from `WebhookMetadata` to key data writes, cache invalidation, mandatory-compliance actions (e.g., `customers/redact`, `shop/redact`), or session lookups — which is the intended and documented use of the field returned by this gem — an attacker can inject data or trigger actions attributed to a shop they do not control. This is a cross-tenant identity confusion rooted entirely in this gem's webhook verification code, matching the Critical/High bar for cross-tenant access.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the app on a shop they control (or otherwise obtain one genuine webhook delivery) — no access token, `api_secret_key`, or privileged access is needed. Replaying a captured body+HMAC with a modified `shop-domain` header against the app's public webhook endpoint is straightforward for any internet-reachable unprivileged party.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) header values in the HMAC-signable string for webhook requests, or otherwise cryptographically bind the shop identity to the signed payload, so that `to_signable_string` in `lib/shopify_api/webhooks/request.rb` cannot be satisfied by mixing a genuine body/HMAC pair from one shop with headers from another.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and receives a genuine webhook, e.g. for `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's secret), plus `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker sends a POST to the app's webhook endpoint with the same raw body `B` and same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers/body; `Utils::HmacValidator.validate` recomputes the HMAC over `B` only and it matches `H`, so `Registry.process` does not raise `Errors::InvalidWebhookError`.
4. The registered handler is invoked with `WebhookMetadata#shop == "victim.myshopify.com"` and `WebhookMetadata#body` from the attacker's own event — a cross-tenant identity mismatch the app cannot detect using data provided by this gem.
