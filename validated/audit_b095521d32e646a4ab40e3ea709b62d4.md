### Title
Bridging to a recipient blacklisted on the underlying token permanently locks escrowed funds in `WrappedHyperFungibleToken` — ([File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol])

### Summary
`HyperFungibleToken.send()` lets any caller burn their tokens on a remote chain and freely choose an arbitrary destination-chain recipient (`params.to`) with no validation. When the destination is `WrappedHyperFungibleToken` on the home chain (where the underlying is a real, blacklist-capable ERC20 such as USDC), `onAccept` unconditionally attempts `safeTransfer(beneficiary, amount)` to that address. If the chosen recipient is (or later becomes) blacklisted on the underlying token, every delivery attempt reverts, and `EvmHost.dispatchIncoming` is written to swallow that revert and leave the message permanently retryable rather than failing terminally — so the underlying tokens, already burned on the source chain, can never be released.

### Finding Description
Any user can call `send()` and set `params.to` to an arbitrary address of their choosing, then burn their own tokens on the remote chain: [1](#0-0) 

On the home chain, `WrappedHyperFungibleToken.onAccept` decodes that address as `beneficiary` and unconditionally pushes the underlying ERC20 to it via `safeTransfer`, with no blacklist or recipient-liveness check: [2](#0-1) 

If that underlying token blacklists the recipient (e.g. USDC-style tokens), `safeTransfer` reverts, so `onAccept` reverts. `EvmHost.dispatchIncoming` is explicitly built to swallow this: it deletes the request receipt and returns without reverting the batch, "so that it can be retried" — meaning the message stays permanently un-deliverable rather than failing conclusively: [3](#0-2) 

The only recovery path for a burned-but-undeliverable transfer is a timeout, which re-mints the burned amount back to the original sender on the source chain: [4](#0-3) 

But `timeout` is a caller-supplied field in `SendParams`, and the codebase's own tests dispatch transfers with `timeout: 0`: [5](#0-4) 

If a message is dispatched with `timeoutTimestamp == 0` (no expiry), it never becomes eligible for the timeout path, so a permanently-reverting `onAccept` (blacklisted recipient) leaves the underlying escrow permanently stuck in `WrappedHyperFungibleToken` with no route to either complete delivery or trigger a refund.

This mirrors the reported bug class exactly: the "recipient" of a cross-chain transfer is freely chosen and not validated against the destination token's blacklist, the delivery step that performs the real token movement can revert due to that blacklist, and the fallback/refund path (here, timeout-triggered re-mint) does not reliably cover the case (specifically when `timeout == 0`).

### Impact Explanation
Underlying tokens held in custody by `WrappedHyperFungibleToken` for a specific bridged transfer become permanently frozen: they cannot be delivered to the blacklisted beneficiary, and — if the message carries no timeout — the burn on the source chain cannot be refunded either. This is a permanent freezing-of-funds condition for the amount involved, matching the required Medium/High severity bar (concrete, permanent loss of access to escrowed value), even though no attacker profits directly.

### Likelihood Explanation
Reachable by any single unprivileged caller of `send()` who sets `to` to an address they know (or expect) is/will be blacklisted on the underlying token, and sets `timeout = 0`. No special privileges, governance, or malicious relayer/operator behavior are required — only a standard user-initiated bridge transfer. The likelihood of the address actually being blacklisted, and the exact on-chain semantics of `timeoutTimestamp == 0` in the handler (whether the host/handler ever independently permits the timeout path to be exercised regardless of the caller-supplied value), could not be fully confirmed from the available files; this should be verified against `HandlerV2`'s timeout-check logic before treating this as fully unconditional.

### Recommendation
- Do not allow the destination-chain module to be the sole gate against terminal delivery failure; consider giving `EvmHost.dispatchIncoming` (or the app) a way to convert a persistently-reverting delivery into an explicit, refundable failure state rather than silent infinite-retry.
- Disallow (or strongly discourage/flag) `timeout == 0` for token-transfer dispatches in `HyperFungibleToken`/`WrappedHyperFungibleToken`, or enforce a maximum default timeout so every burn always has a guaranteed refund path.
- Consider a `try/catch` around the underlying `safeTransfer` in `WrappedHyperFungibleToken.onAccept`, falling back to crediting an internal claimable balance for the beneficiary (pull-payment pattern) instead of reverting the whole delivery, so one bad recipient cannot block final settlement of an otherwise-valid message.

### Proof of Concept
1. On remote chain R, attacker (or any user) holds `HyperFungibleToken` balance.
2. Attacker calls `send({ dest: HOME_CHAIN, to: BLACKLISTED_ADDR, amount, timeout: 0, relayerFee, data: "" })`. `_burn(msg.sender, amount)` executes; a POST request commits to deliver `amount` to `BLACKLISTED_ADDR` on the home chain.
3. Relayer submits the message; `EvmHost.dispatchIncoming` calls `WrappedHyperFungibleToken.onAccept`, which attempts `IERC20(_underlying).safeTransfer(BLACKLISTED_ADDR, amount)` — this reverts because the underlying token's blacklist blocks transfers to `BLACKLISTED_ADDR`.
4. `EvmHost.dispatchIncoming` catches the failed call, deletes the receipt, and returns without reverting the batch (see cited lines 812-816) — the message is now permanently "retryable" but can never succeed.
5. Because `timeout == 0`, the message never becomes eligible for `handlePostRequestTimeouts`, so `HyperFungibleToken.onPostRequestTimeout` on chain R is never invoked, and the burned tokens are never refunded.
6. Net effect: `amount` of the underlying token is permanently held by `WrappedHyperFungibleToken` on the home chain, unreachable by any party.

```text
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.

                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
```

```text
    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
```
