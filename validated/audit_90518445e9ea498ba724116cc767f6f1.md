### Title
Missing Shop Domain Validation in `TokenExchange.exchange_token` Sends `client_secret` to an Unsanitized Host - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the destination shop from a JWT's `dest` claim via `JwtPayload#shop` and uses it, unsanitized, to build the base URI of an outbound HTTP POST that carries the app's `client_id` and `client_secret`. Every sibling method in the same file/module (`migrate_to_expiring_token`, `refresh_access_token` in `refresh_token.rb`, `client_credentials` in `client_credentials.rb`) passes the caller-supplied shop through `Utils::ShopValidator.sanitize!` before using it to build the request host, but `exchange_token` does not apply this same check to the shop value it derives from the token.

### Finding Description
`Utils::ShopValidator.sanitize!` exists specifically to guarantee that a shop string used to build a request URL is one of the `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.com`, `myshopify.io`, `spin.dev`, `shop.dev`) before it is used as an HTTP request host: [1](#0-0) [2](#0-1) 

This validator is consistently applied before constructing a `Session` used for the OAuth token endpoints in the other three grant flows: [3](#0-2) [4](#0-3) [5](#0-4) 

However, `exchange_token` takes a different path: it decodes the session token, reads `jwt_payload.shop` (the `dest` claim with only the literal `"https://"` prefix stripped, no domain allow-list check), and builds the `shop_session`/request host directly from that value without ever calling `ShopValidator.sanitize!`: [6](#0-5) [7](#0-6) 

That `shop_session` is then handed to `HttpClient`, which builds the destination host directly from `session.shop` when `api_host` is not configured, and the request body (built in `exchange_token`) contains `client_id` and `client_secret`: [8](#0-7) [9](#0-8) 

The binding that should hold is: `host receiving client_secret == a domain in TRUSTED_SHOPIFY_DOMAINS`. Every other grant-type method enforces this equality via `sanitize!`. `exchange_token` does not, so the equality can be broken by anything that influences the `dest` claim without being constrained to a trusted suffix (the code only strips a literal prefix, it does not verify the suffix at all).

### Impact Explanation
If the `dest` value reaching `JwtPayload#shop` is not constrained to `*.myshopify.com`/`myshopify.io`/etc. (unlike every sibling flow, which is explicitly hardened with `sanitize!`), the app's `client_id`/`client_secret` — the most sensitive long-lived credential this gem manages — is sent via an outbound POST to whatever host string results from stripping `"https://"` off `dest`. This is precisely the "host validated vs. host that receives client_secret" credential class called out as in-scope: sibling code paths correctly bind the host to the trusted allow-list before it is used to route the credential-bearing request, while `exchange_token` skips that binding entirely.

### Likelihood Explanation
The `dest` claim itself only becomes attacker-influenced if the process that issues the session token is compromised in some way, or if downstream code composing the token (something the app trusts as coming from Shopify) does not itself constrain `dest` to a `myshopify` suffix; regardless, this gem's own `token_exchange.rb` is the one file in the OAuth-credential family of methods that omits the standard domain-allow-list defense that the library authors themselves added everywhere else specifically to guard the client_secret-carrying request. That asymmetry is a code-level correctness gap regardless of how strong the JWT signature guarantee is assumed to be.

### Recommendation
Apply `Utils::ShopValidator.sanitize!(dest_shop)` in `TokenExchange.exchange_token` before constructing `shop_session`, exactly as is already done in `migrate_to_expiring_token`, `refresh_access_token`, and `client_credentials`, so the host that ultimately receives `client_id`/`client_secret` is always constrained to `Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

### Proof of Concept
```ruby
# lib/shopify_api/auth/token_exchange.rb (current behavior)
jwt_payload = ShopifyAPI::Auth::JwtPayload.new(session_token)
dest_shop = jwt_payload.shop            # only "https://" prefix is stripped, no domain allow-list check
shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)
client = Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")
# HttpClient builds "https://#{dest_shop}" as base_uri and POSTs client_id + client_secret to it,
# with no call to Utils::ShopValidator.sanitize! anywhere in this path — unlike every sibling method:
#   ClientCredentials.client_credentials      -> Utils::ShopValidator.sanitize!(shop)
#   RefreshToken.refresh_access_token         -> Utils::ShopValidator.sanitize!(shop)
#   TokenExchange.migrate_to_expiring_token   -> Utils::ShopValidator.sanitize!(shop)
```
