### Title
Webhook `shop-domain` Header Is Not Covered by HMAC Verification, Allowing Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, while the `shop` value that identifies which tenant the webhook data belongs to is read from an unsigned HTTP header. This breaks the identity binding: `shop asserted to the handler == shop actually covered by the HMAC signature`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `shop` is read from the `shopify-shop-domain` / `x-shopify-shop-domain` header via `shopify_header` [2](#0-1) . `Registry.process` validates the request using `Utils::HmacValidator.validate(request)`, which signs/verifies only `to_signable_string` (the raw body) [3](#0-2) [4](#0-3) . After that single check passes, `request.shop` (from the unsigned header) is passed straight into `WebhookMetadata` and forwarded to the app's handler [5](#0-4) , and the docs confirm consuming apps use `data.shop` to route/attribute the webhook to a specific merchant [6](#0-5) .

Because `topic`, `shop-domain`, `webhook-id`, and `api-version` headers are excluded from the signed content, an unprivileged internet user who is themselves a merchant using the app (and therefore legitimately receives real, correctly-HMAC-signed webhook deliveries for their own shop) can capture one such delivery and replay it to the app's webhook endpoint with the `shopify-shop-domain` header swapped to a victim shop's domain (or any other topic/webhook-id header value), while leaving the body and HMAC untouched. `HmacValidator.validate` will still pass because it only checks the raw body bytes, and the gem will hand the (attacker-chosen) `shop` to the app's handler as if it were authenticated.

### Impact Explanation
This is a cross-tenant identity confusion: an app relying on `data.shop`/`data.topic` from `ShopifyAPI::Webhooks::WebhookHandler#handle` to select the tenant's stored session/access token, persist data, or route logic can be tricked into associating the attacker-supplied body with an arbitrary shop domain of the attacker's choosing. Depending on how the consuming app uses this value (e.g., looking up per-shop session/access token by `shop` and performing further Admin API actions "for" that shop, or writing data under the wrong tenant record), this can lead to cross-tenant data corruption or actions being taken against a victim shop's stored credentials — matching the report's "single trusted entity can take over/impersonate the whole trust group" class, here manifesting as any webhook holder impersonating any other tenant.

### Likelihood Explanation
Any external user who is a legitimate merchant/installer of the app already receives real signed webhook bodies for their own shop and can freely replay them with modified headers to the app's public webhook endpoint — no `api_secret_key`, access token, or privileged access is required, only observation of one's own webhook traffic (achievable with a basic HTTP proxy). This is a straightforward, unauthenticated-boundary attack fully reachable through the gem's own `Registry.process`/`Request` API as documented.

### Recommendation
Bind the identity fields into the signed content, or otherwise independently authenticate them:
- Verify `shop-domain` against the shop associated with the app's known/registered sessions before trusting it, or
- Require that `shop`, `topic`, and `webhook-id` be included in the HMAC-signed payload (or independently confirmed via a separate authenticated channel, e.g., cross-checking against Shopify's `X-Shopify-Webhook-Id` id when fetching the corresponding subscription), and
- At minimum, document prominently that `shop`/`topic`/`webhook-id` headers are NOT covered by HMAC verification so consuming apps do not treat them as trusted identifiers without additional validation (e.g., confirming the shop has an active, matching session before acting).

### Proof of Concept
```ruby
# Attacker is a legitimate merchant of the app, receiving real webhooks for "attacker-shop.myshopify.com"
# They capture a genuine delivery:
raw_body = '{"id":123,"note":"legit order for attacker-shop"}'
real_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_secret, raw_body) # produced by Shopify, captured by attacker

headers = {
  "shopify-topic" => "orders/create",
  "shopify-hmac-sha256" => Base64.encode64(real_hmac),
  "shopify-shop-domain" => "victim-shop.myshopify.com", # <-- swapped, NOT covered by HMAC
  "shopify-webhook-id" => "spoofed-id",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) still passes (only checks raw_body),
# handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)) is invoked
# -- the app now processes/attributes this data as belonging to "victim-shop.myshopify.com".
```

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
