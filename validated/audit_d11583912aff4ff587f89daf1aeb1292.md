### Title
Attacker-planted unpriceable dust collateral leg bricks `liquidate` and `clean_bad_debt` for the account — (`File: contracts/controller/src/positions/liquidation/math.rs`)

### Summary
The bug class from the Kintsu report — one reverting element inside a forced batch loop DoS-ing the whole operation — maps directly onto XOXNO Lending's pro-rata seizure. `liquidate` does not let the liquidator choose which collateral to seize: `calculate_seized_collateral` iterates **every** supply position of the liquidated account and calls `cache.cached_price(&hub_asset.asset)` on each leg [1](#0-0) . If any single leg's price feed is stale/unpriceable, `cached_price` panics and the entire liquidation reverts — and the same totals computation is required by `clean_bad_debt`, so the bad debt cannot even be socialized. An unprivileged borrower can plant such a leg on their own account before going underwater, making the account permanently unliquidatable while the feed stays stale.

### Finding Description
`build_liquidation_plan` computes `risk::calculate_account_risk_totals` over all supply positions (each priced) and then `calculate_seized_collateral` loops all supply legs again, each requiring a fresh strict price [2](#0-1) [3](#0-2) . There is no skip-or-continue path: a leg that cannot be priced aborts the transaction.

The attacker path is fully unprivileged:

1. Attacker opens an account, supplies normal collateral, borrows.
2. Attacker additionally `supply`s a dust amount of an asset whose oracle feed is already stale (or becomes stale). `supply` accepts it — the repo's own test proves this: `try_supply(borrower, "WBTC", 0.001)` succeeds with a WBTC price timestamped 3,600 s in the past [4](#0-3) .
3. Once HF < 1, every `liquidate` reverts with `PriceFeedStale`, and `clean_bad_debt` also reverts with `PriceFeedStale` because eligibility needs risk totals over all legs [5](#0-4) .
4. Only a fresh price for that asset restores liquidation — confirmed by the same test [6](#0-5) .

The same one-leg-bricks-all structure is acknowledged elsewhere in the codebase: a `no_seize` flag on any collateral aborts the whole liquidation (`SpokeAssetSeizureHalted`), and an untransferable collateral token leg bricks the whole liquidation in `poc_untransferable_collateral_leg_bricks_whole_liquidation` — but those rely on privileged flags or token semantics. The stale-feed dust leg is the variant reachable by an ordinary borrower alone.

### Impact Explanation
Temporary-to-prolonged freezing of the liquidation mechanism for the account, plus blocked bad-debt cleanup. The borrower can keep an underwater position unliquidatable for as long as any held collateral asset's feed is stale, letting interest accrue into insolvency while `clean_bad_debt` is also reverted by the same unpriceable leg. Cost to the attacker is one dust deposit; the freeze lasts until the external feed updates, which for a rarely-updated or abandoned feed can be indefinite. Even if judged temporary per-account, it directly defeats the protocol's only two resolution paths (`liquidate`, `clean_bad_debt`).

### Likelihood Explanation
Low setup cost (one dust `supply`), fully permissionless, and benefits the attacker directly by shielding their debt. Triggering requires a listed collateral asset whose feed can be stale while `supply` still accepts the deposit — demonstrated working in the repo's own harness test. Feeds that update on deviation thresholds routinely go stale for low-volatility assets, so the window is realistic rather than exotic.

### Recommendation
Two options, mirroring the report's fixes:

- Skip unpriceable legs: in `calculate_seized_collateral` and in the risk-totals pass used by `liquidate`/`clean_bad_debt`, treat a leg whose `cached_price` fails as zero-value (or exclude it from `total_collateral` and the seizure loop) instead of reverting — a dust leg contributes ~nothing anyway.
- Gate entry: reject `supply` into a market whose price feed is currently stale, so a fresh unpriceable leg cannot be planted on an account that already carries debt. This does not help for feeds that go stale after deposit, so the first option is the robust fix; ideally apply both.

### Proof of Concept
Already encoded in the repo: `tests/test-harness/tests/controller/audit_liquidate_and_clean_stale_leg.rs::audit_liquidate_and_clean_bricked_by_unpriceable_dust_leg` [7](#0-6) :

1. Borrower supplies 10,000 USDC and borrows 3 ETH (healthy).
2. WBTC feed timestamp is set 3,600 s in the past; `supply(borrower, WBTC, 0.001)` succeeds.
3. USDC price crashes → HF < 1.
4. `try_liquidate(LIQUIDATOR, borrower, ETH, 1.0)` → `PRICE_FEED_STALE`.
5. `try_clean_bad_debt_by_id` → `PRICE_FEED_STALE`.
6. Refreshing WBTC unblocks the identical liquidation — the revert was caused solely by the planted leg inside the forced pro-rata loop.

fn audit_liquidate_and_clean_bricked_by_unpriceable_dust_leg() {
    let mut t = LendingTest::new()
        .three_asset_usdc_eth_wbtc()
        .with_dust_disabled_all_markets()
        .build();

    t.set_oracle_single_spot("WBTC");

    t.supply(LIQUIDATOR, "USDC", 50_000.0);
    let borrower = test_harness::ALICE;
    t.supply(borrower, "USDC", 10_000.0);
    t.borrow(borrower, "ETH", 3.0);

    let fresh = t.try_liquidate(LIQUIDATOR, borrower, "ETH", 1.0);
    test_harness::assert_contract_error(fresh, errors::HEALTH_FACTOR_TOO_HIGH);

    t.advance_time(5_000);
    let now = t.env.ledger().timestamp();
    let wbtc = t.resolve_asset("WBTC");
    t.mock_reflector_client()
        .set_price_at(&wbtc, &usd(60_000), &(now - 3_600));

    let plant = t.try_supply(borrower, "WBTC", 0.001);
    assert!(
        plant.is_ok(),
        "supply must accept the fragile leg with a stale feed: {plant:?}"
    );

    t.set_price("USDC", usd_cents(50));

    let borrower_id = t.resolve_account_id(borrower);

    let liq = t.try_liquidate(LIQUIDATOR, borrower, "ETH", 1.0);
    test_harness::assert_contract_error(liq, errors::PRICE_FEED_STALE);

    let clean = t.try_clean_bad_debt_by_id(borrower_id);
    test_harness::assert_contract_error(clean, errors::PRICE_FEED_STALE);

    t.set_price("WBTC", usd(60_000));
    let recovered = t.try_liquidate(LIQUIDATOR, borrower, "ETH", 1.0);
    assert!(
        recovered.is_ok(),
        "once WBTC is fresh, the identical liquidation must succeed: {recovered:?}"
    );
    assert!(
        t.borrow_balance(borrower, "ETH") < 3.0,
        "post-recovery liquidation must reduce the borrower's debt"
    );
}
