### Title
Unauthenticated route spoofing can poison a signed lending transaction to steal wallet assets - (File: contracts/controller/src/strategies/swap.rs) [1](#0-0) 

### Summary
Controller strategy entrypoints accept opaque route bytes and forward them unchanged to the configured swap router without decoding or restricting the venues encoded inside the route. [2](#0-1)  Although the controller authorizes only one exact input transfer from itself to the router, that authorization does not constrain the caller's broader transaction authorization tree. [3](#0-2)  A crafted route can therefore simulate as a seemingly valid swap while adding an attacker-chosen nested token transfer from the victim; signing that poisoned tree authorizes the theft alongside the strategy. [1](#0-0) 

### Finding Description
`swap_collateral(caller, account_id, current, amount, new, swap)` requires the account owner or delegate and accepts `swap` as arbitrary `Bytes`. [4](#0-3) [5](#0-4)  The withdrawn collateral and opaque `swap` bytes are passed to the shared strategy router path. [6](#0-5)  `swap_tokens` rejects only an empty route, loads the configured router, authorizes the router to pull exactly `amount_in`, and passes the original bytes to `execute_strategy`. [2](#0-1) 

The router ABI treats those bytes as caller-supplied `swap_xdr`; there is no controller-level allowlist or validation binding the payload to known venue contracts. [7](#0-6) [2](#0-1)  The exact `authorize_transfer_as_current` entry protects only the controller's own input transfer and contains no sub-invocations, so it cannot prevent a route venue from requesting a separate victim-signed invocation. [3](#0-2) 

### Impact Explanation
An unprivileged attacker can deploy a contract that impersonates a supported route venue and craft a profitable-looking strategy route through it. [2](#0-1)  When the victim's transaction is simulated, the venue's unauthorized-looking `transfer(victim -> attacker, amount)` can be included as a nested authorization beneath the victim's signed top-level invocation; signing that tree executes the extra transfer while the strategy also settles normally. [7](#0-6) [8](#0-7)  This can steal arbitrary wallet assets held by the victim, not merely the collateral amount committed to the strategy. [9](#0-8) 

### Likelihood Explanation
The attacker needs no privileged role because `swap_collateral` accepts the route from the account caller and forwards it to the router unchanged. [5](#0-4) [2](#0-1)  Exploitation requires victim interaction: a wallet or interface must present the crafted strategy and the victim must sign the poisoned authorization tree. [5](#0-4)  The venue must still make the measured router swap succeed, which the attacker can arrange by funding the malicious venue or using its own liquidity. [10](#0-9) 

### Recommendation
Decode and validate strategy route bytes in the controller before calling `execute_strategy`, including enforcing a governed venue-contract allowlist for every route hop. [2](#0-1)  The validation should cover every strategy path that reaches `swap_tokens` or `swap_tokens_or_passthrough`, including `multiply`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral`. [11](#0-10) [6](#0-5)  Client interfaces should additionally reject simulated authorization trees containing any victim token transfer beyond the expected lending payment. [3](#0-2) 

### Proof of Concept
1. The attacker deploys a contract that exposes the ABI expected by a router venue and funds it with enough output token to return a positive swap result. [10](#0-9) 
2. For a victim holding a lending account with `current` collateral, the attacker crafts route bytes that reference the malicious contract while declaring `token_in = current.asset` and `token_out = new.asset`. [6](#0-5) [7](#0-6) 
3. The victim is induced to invoke `swap_collateral(victim, victim_account_id, current, amount, new, poisoned_swap)`. [4](#0-3) 
4. The controller withdraws the victim's collateral and forwards `poisoned_swap` to the configured router without venue validation. [6](#0-5) [12](#0-11) 
5. During the venue call, the malicious contract invokes `token.transfer(victim, attacker, wallet_balance)`; simulation surfaces that invocation in the victim's authorization tree. [7](#0-6) 
6. If the victim signs that tree, the router receives a valid output and the controller's measured-output checks can pass, while the unrelated wallet-token transfer to the attacker also executes. [10](#0-9)

```rust
/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
```
