### Title
Webhook shop attribution is not bound by the HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates only the request body via HMAC, then dispatches the handler using a `shop` value taken from an unauthenticated header. The equality the gem should guarantee — "shop attributed to the event" == "shop covered by the HMAC" — does not hold.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`HmacValidator.validate` computes/compares the HMAC exclusively over that signable string: [2](#0-1) 

Meanwhile `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed material: [3](#0-2) 

`Registry.process` validates the HMAC and then trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler, without any cross-check that the shop header is consistent with anything cryptographically bound to the signature: [4](#0-3) 

Because the HMAC secret (`api_secret_key`) is shared across every shop that has installed the app, an unprivileged user who installs the app on their own store can capture a genuinely-signed webhook for their own shop (valid HMAC over the body) and resubmit it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` still succeeds because it never looks at the shop header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the (attacker-controlled) body came from the victim shop.

### Impact Explanation
This breaks the tenant-isolation guarantee the gem's webhook API is expected to provide: an authenticated body from tenant A can be replayed and attributed to tenant B purely because the shop identifier is unauthenticated. Any host application that keys off `WebhookMetadata#shop` to load per-shop state, apply data, or select context (which is the entire purpose of exposing `shop` on `WebhookMetadata`) is exposed to cross-tenant data corruption/confusion — an attacker with only a benign install of the app on their own store can inject attacker-controlled payloads attributed to a victim merchant.

### Likelihood Explanation
Likelihood is high: the attacker only needs to be a legitimate, unprivileged installer of the app (no special access to the victim, to `api_secret_key`, or to any token). Capturing one's own valid webhook and replaying it with a modified header requires no cryptographic material beyond what the attacker already legitimately possesses via their own install.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) into the HMAC-covered material, or otherwise validate that `request.shop` corresponds to a shop actually authorized to have produced this exact body/signature (e.g., require the webhook body to embed/be checked against the shop domain, or reject/flag when the shop header cannot be tied to the signed payload). At minimum, document this gap prominently and require host apps to independently verify shop-webhook binding before this data reaches the version used in `Registry.process`.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, triggering a legitimate webhook (e.g. `orders/create`) signed by Shopify with the app's `api_secret_key`.
2. Attacker intercepts/replays this webhook to the app's webhook endpoint, keeping the raw body and `x-shopify-hmac-sha256` header identical, but changes `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only compares the HMAC of the raw body (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
4. The handler is invoked with `WebhookMetadata.new(shop: request.shop, ...)` set to `victim.myshopify.com` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though the payload actually originated from `attacker.myshopify.com`.
