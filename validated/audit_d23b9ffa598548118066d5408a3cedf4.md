Based on my research, I found a concrete analog: the nexus runtime explicitly hardcodes a defensive deny-list for deprecated TokenGateway EVM contracts, confirming these legacy contracts are still live, reachable, and considered a threat vector — mirroring the Transit Finance scenario of a deprecated 2022-era contract remaining exploitable.

### Title
Deprecated TokenGateway contracts remain a trusted, unauthenticated message source outside the nexus runtime's deny-list - (File: `parachain/runtimes/nexus/src/ismp.rs`)

### Summary
Nexus's `ProxyModule::on_accept`/`on_timeout` unconditionally reject any ISMP `PostRequest` whose `from` field matches one of three hardcoded, deprecated EVM `TokenGateway` addresses <cite repo="Alyssadaypin/hyperbridge--001" path="parachain/runtimes/nexus/src/ismp.rs" start="49="61" /> before any dispatch, bandwidth, or module routing occurs <cite repo="Alyssadaypin/hyperbridge--001" path="parachain/runtimes/nexus/src/ismp.rs" start="362="373" />. This is a targeted patch that only exists in the nexus runtime.

### Finding Description
The deprecated on-chain `TokenGateway` EVM contracts are still deployed and live on multiple chains per the contract-address docs (`TokenGateway (Deprecated)` entries) [1](#0-0) , and `pallet-token-gateway` itself is still shipped and documented for third-party runtimes to configure via `set_token_gateway_addresses`, which registers these exact contract addresses as **trusted message sources** for validating incoming cross-chain mint/unlock messages [2](#0-1) . Any parachain running `pallet-token-gateway` with these addresses configured trusts `from == configured TokenGateway address` as sufficient authorization to mint or unlock escrowed assets.

Nexus's own `ProxyModule` demonstrates that Polytope Labs considers these specific deprecated addresses dangerous enough to warrant a permanent, unconditional reject — applied to `on_accept` and `on_timeout` before the pallet-routing logic runs [3](#0-2) . This defensive check is scoped to the nexus runtime file alone; it is not part of `pallet-token-gateway`'s own `on_accept` logic, so any other Polkadot-SDK chain (parachain or solochain) that integrates `pallet-token-gateway` per the published integration guide and has these deprecated addresses configured as trusted sources has no equivalent protection, because that check was added ad hoc to nexus rather than to the shared pallet.

This mirrors the Transit Finance pattern precisely: a 2022-era, deprecated contract remains reachable by an unprivileged relayer/attacker, is still trusted by parts of the live system, and requires a bespoke, out-of-band patch (a hardcoded address blocklist bolted onto one specific runtime) rather than being disabled at the protocol layer.

### Impact Explanation
If any production Polkadot-SDK chain still runs `pallet-token-gateway` with a deprecated TokenGateway address registered as a trusted EVM source (which is exactly the deployment pattern the docs describe), and the deprecated EVM `TokenGateway` contract carries the same class of vulnerability that let the Transit Finance attacker drain funds from its legacy TRON contract (e.g., an access-control gap letting an attacker force it to emit an ISMP dispatch it should not have), an attacker could forge or trigger an incoming request from that address to mint/unlock assets on the destination chain — an unbacked mint / permanent freezing-of-funds class impact reachable by a single relayed message, exactly the category the deny-list in nexus was built to stop.

### Likelihood Explanation
Medium. This requires (a) a production chain other than nexus still trusting the deprecated TokenGateway address via `pallet-token-gateway`, and (b) the deprecated EVM TokenGateway contract itself having an exploitable defect analogous to the Transit Finance bug. I could not locate the deprecated `TokenGateway.sol` source in this repository (it predates the current EVM app set and is not present under `evm/src` or `evm/tron`), so the underlying EVM-side vulnerability cannot be directly confirmed here — this is a structural/deployment-topology gap (missing deny-list outside nexus), not a proven code-level bug in the deprecated contract itself.

### Recommendation
Move the deprecated-TokenGateway rejection logic out of the nexus-specific `ProxyModule` and into `pallet-token-gateway`'s shared `on_accept`/`on_timeout` implementation (or publish the deny-list as a shared constant that every integrating runtime is required to wire in), so protection does not depend on each downstream chain replicating nexus's ad hoc patch. Independently, confirm whether any currently-live production chain still has the deprecated TokenGateway addresses configured as trusted sources and remove that trust if so.

### Proof of Concept
Not independently verifiable without: (1) the deprecated `TokenGateway.sol` bytecode/source to confirm an analogous access-control defect exists, and (2) confirmation that a production chain besides nexus still has these deprecated addresses registered via `set_token_gateway_addresses`. Both are structural gaps identifiable from the repository (missing shared deny-list, deprecated contracts still listed as live deployments) rather than a demonstrated exploit chain in this codebase.

The pallet needs to know the addresses of the token gateway contracts on EVM chains so it can validate the source of incoming messages.
