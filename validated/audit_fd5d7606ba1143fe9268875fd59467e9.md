### Title
Unrestricted swap routes can attach unrelated victim token transfers to a signed strategy authorization - (File: contracts/controller/src/strategies/swap.rs)

### Summary
An attacker can craft a swap route that causes venue code to request an unrelated `token.transfer` from the caller while the controller executes a strategy, allowing theft of wallet assets beyond the routed amount if the caller signs the resulting authorization tree. [1](#0-0) [2](#0-1) 

### Finding Description
`swap_collateral` accepts caller-supplied `StrategySwap` data, authorizes the account owner or delegate, withdraws collateral, and forwards the opaque route to the configured swap aggregator. [3](#0-2) [4](#0-3) 

The shared router boundary grants the router one exact input transfer and invokes `execute_strategy`, but it does not constrain which pool or token contracts the payload causes the router to call. [5](#0-4) 

Afterward, the controller checks only that its input balance did not increase, that spending did not exceed `amount_in`, and that its output-token balance increased. [6](#0-5) 

Those checks do not bound a nested venue call that invokes a different token's `transfer(victim, attacker, amount)` under the victim's transaction authorization. [7](#0-6) 

### Impact Explanation
A malicious route can steal arbitrary wallet tokens held by the victim while still returning enough output to satisfy the router and controller balance checks. [6](#0-5) 

The stolen asset does not need to be the strategy input, output, collateral, debt, or even an asset listed by the protocol, because the controller's measurements cover only `token_in` and `token_out`. [8](#0-7) [6](#0-5) 

### Likelihood Explanation
Exploitation requires the victim to submit or accept an attacker-crafted route and authorize the transaction containing the additional transfer, so it is not a purely unilateral theft. [9](#0-8) 

However, the route is an opaque caller argument and the protocol provides no contract-level venue allowlist or child-authorization ceiling at the point where it executes the swap. [10](#0-9) [1](#0-0) 

### Recommendation
Restrict swap execution to a governance-approved pool or venue registry, or replace the opaque route with a structured route whose pool addresses are validated before invocation. [11](#0-10) 

Until contract-level venue admission exists, clients must simulate, decode, and display every nested authorization and reject trees containing anything other than the expected strategy call and input transfer. [1](#0-0) 

### Proof of Concept
1. The attacker deploys a pool-compatible contract whose swap function pays a normal `token_out` amount to the router and additionally calls `victim_token.transfer(victim, attacker, victim_balance)`. [12](#0-11) 
2. The attacker supplies a `StrategySwap` route that selects that pool and convinces the victim to call `swap_collateral(victim, account_id, current, amount, new, route)`. [3](#0-2) [2](#0-1) 
3. The controller authorizes only its exact input transfer to the configured router, then executes the route under the flash guard. [1](#0-0) 
4. During route execution, the malicious pool requests the unrelated victim-token transfer; transaction simulation records it as an additional authorization beneath the victim's strategy invocation. [12](#0-11) 
5. If the victim signs that tree, the unrelated transfer succeeds, while the fair `token_out` payment lets the controller's spend and positive-output checks pass. [6](#0-5)
