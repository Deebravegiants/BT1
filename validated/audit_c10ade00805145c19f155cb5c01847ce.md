### Title
Extreme hostile pre-seed of the HyperSwap V2 pair can round `finalizeGraduation`'s LP deposit to zero and permanently brick graduation via `LPLock.recordLock`'s `ZeroAmount` guard - (File: `packages/contracts/src/Bonding.sol`)

### Summary
`Bonding.finalizeGraduation`'s hostile-pre-seed defense is designed around one explicit, load-bearing invariant: *"Phase 2 must never revert under any pre-seed shape"* [1](#0-0) . That invariant is enforced not by an authoritative floor but by an arithmetic margin — `_swapBudget` reserving 1% of the swap-side budget — layered on top of a router-mediated `addLiquidity` call whose optimal-split rounding is outside `Bonding`'s control. Because the true enforcement of "never zero, never revert" lives in this soft margin rather than in a hard guarantee, an attacker who can freely create and pre-seed the not-yet-existing HyperSwap pair (permissionless `factory.createPair` + `transfer` + `mint`, exactly like an unprivileged sandboxed guest manipulating a flag it shouldn't authoritatively control) can drive the post-rebalance deposit to a degenerate near-zero amount on one side, causing `_routerDepositAndDispose`/`_seedUniswapV2Direct` to return `liquidity == 0`, which then reverts inside `LPLock.recordLock`'s `ZeroAmount` check — permanently bricking that token in `Lifecycle.Graduating`.

### Finding Description
`finalizeGraduation` is fully permissionless and callable by anyone once a token is `Lifecycle.Graduating` [2](#0-1) . Between phase 1 (`_enterGraduating`, which freezes curve trading and caches `(tokensForLP, ltFromPair)`) and phase 2, the HyperSwap V2 (TOKEN/LT) pair does not yet need to exist, and an attacker can pre-create it and mint hostile-ratio LP into it before anyone calls `finalizeGraduation` — this is the documented "mint pre-seed" (Regime 3) attack [3](#0-2) .

The defense computes a rebalance swap via `_noFeeSwapInput`, capped by `_swapBudget` at 99% of the available inventory [4](#0-3) , explicitly because *"an extreme hostile pre-seed... drives the unconstrained `_noFeeSwapInput` past our per-side budget... `_routerDepositAndDispose` then skips `addLiquidity`... `LPLock.recordLock(...)` records a zero-sized lock"* — the contract's own comment names exactly this failure mode as the thing the 1% margin is supposed to prevent. The remaining 1% is then handed to `router.addLiquidity(remToken, remLT, 1, 1, lpLock, ...)` [5](#0-4) , whose internal `quote()`-based optimal-split can still round one side down to zero for sufficiently skewed ratios — a rounding behavior the `Bonding` contract does not control and cannot guarantee against.

If `remToken == 0` or `remLT == 0` after this split, `addLiquidity` is skipped entirely (`if (remToken > 0 && remLT > 0)`), so `liquidity` returned by `_routerDepositAndDispose` is `0`. `finalizeGraduation` then calls `LPLock($.lpLock).recordLock(tokenAddress, lpPair, liquidity)` unconditionally [6](#0-5) , and `recordLock` reverts with `ZeroAmount` whenever `amount == 0` [7](#0-6) . Because `finalizeGraduation` has no try/catch around this call, the entire transaction reverts. Every subsequent call to `finalizeGraduation` for that token hits the identical state (same cached `pendingGraduation`, same hostile pair reserves) and reverts the same way — there is no retry path that changes the outcome, and `LPLock` documents that it has **no rescue/withdraw path in v1**, so the only fix would be a UUPS upgrade [8](#0-7) .

This is the exact CAP_SYS_ADMIN-style pattern from the source report: a security-critical invariant ("phase 2 never reverts") is supposed to be authoritative, but its real enforcement point is a soft, attacker-influenceable margin (the router's rounding behavior against an attacker-chosen pre-seed ratio) rather than a hard guarantee — just as boxlite's read-only contract was nominally enforced by the guest's own `MS_RDONLY` flag instead of the hypervisor.

### Impact Explanation
A successful trigger permanently freezes:
- The curve's real LT raised (`ltFromPair`, drained into `Bonding` via `Router.graduate` during phase 1) — stuck in `Bonding` with `Lifecycle.Graduating` set forever, unrecoverable by any on-chain path.
- The 250M `LP_RESERVE` tokens (`tokensForLP`) that were supposed to seed/lock the LP — never minted into a locked LP, never burned, permanently orphaned inside `Bonding`.
- All curve holders of that token, who can neither sell on the curve (frozen at `Lifecycle.Graduating`) nor trade on the never-created/never-fixed LP.

This is a permanent freeze of trader and protocol funds reachable purely from unprivileged transactions (pair creation, ERC20 transfers, `mint`), matching the "permanent freezing of trader, creator or LP funds" acceptance criterion.

### Likelihood Explanation
Reaching the underlying `Lifecycle.Graduating` state and pre-seeding a HyperSwap pair is already a documented, exercised attack surface (Regime 3, "the actual exploit") requiring only a small self-funded token+LT budget to create the pair, `transfer`, and `mint`. What is uncertain — and not verifiable from the index alone — is the exact numeric ratio/skew needed to push the router's `quote()`-based `addLiquidity` split to round a side fully to zero even after the 1% margin, since that depends on the live HyperSwap router's integer-division behavior on mainnet reserves, which is outside this repository (only a test mock is available, `test/mocks/MockHyperswapRouter.sol`). The `_swapBudget` comment's own framing ("It only kicks in for catastrophic pre-seeds beyond our budget capacity") suggests the authors believe this is only reachable at extreme skew, but does not prove it is unreachable — and the dedicated end-to-end regression suite that once tested exactly these leftover-recovery / attacker-no-profit properties (`test/HostilePreSeed.t.sol`) was removed and is explicitly flagged in `AGENTS.md` as no longer enforced by automated tests [9](#0-8) , so this exact class of edge case currently has no regression coverage.

### Recommendation
- Make `finalizeGraduation` tolerant of a zero-liquidity deposit outcome instead of allowing `LPLock.recordLock`'s `ZeroAmount` guard to revert the whole transaction — e.g., skip the lock step (and instead route the entire inventory through the burn/sweep disposal path already used for off-ratio remainders) when `liquidity == 0`, so the lifecycle can still advance to `Graduated` and funds are not orphaned.
- Alternatively/additionally, widen the reserved margin in `_swapBudget` dynamically based on the pre-seed skew, or require `_routerDepositAndDispose` to fall back to a direct `pair.mint` (bypassing the router's `quote()` rounding) whenever the router-computed split would otherwise be zero on either side.
- Restore or re-add targeted regression tests (replacing the removed `test/HostilePreSeed.t.sol`) specifically covering catastrophic/extreme pre-seed ratios that stress the `_swapBudget` 1% margin and the router's `addLiquidity` rounding, to confirm `finalizeGraduation` truly never reverts.

### Proof of Concept
1. Launch a token via `Bonding`/`Zap.createToken` and drive it to `Lifecycle.Graduating` (buy through the USD or supply trigger, e.g. via `Zap.buy`/`Bonding.triggerGraduation`), which caches `(tokensForLP, ltFromPair)` in `pendingGraduation[token]` [10](#0-9) .
2. Before anyone calls `finalizeGraduation`, as an unprivileged attacker: call `IUniswapV2Factory.createPair(token, lt)`, `transfer` an extreme, deliberately skewed amount of TOKEN and LT into the pair (sized so that after `_pairRebalance`'s capped swap the remaining post-swap inventory drives the router's `addLiquidity` optimal-split computation to round one side to `0`), then call `pair.mint(attacker)`.
3. Call `Bonding.finalizeGraduation(token)`. `_seedUniswapV2Direct` → `_seedRebalancing` → `_pairRebalance` executes the capped rebalance swap; `_routerDepositAndDispose` computes `remToken`/`remLT` and skips `addLiquidity` because one side is `0`, returning `liquidity = 0` [5](#0-4) .
4. `finalizeGraduation` calls `LPLock.recordLock(token, lpPair, 0)`, which reverts with `ZeroAmount` [7](#0-6) , reverting the whole `finalizeGraduation` transaction.
5. Every future call to `finalizeGraduation(token)` hits the identical cached state and hostile pair reserves and reverts identically — the token is permanently stuck in `Lifecycle.Graduating`, with its raised LT and 250M reserved tokens frozen inside `Bonding` and no on-chain recovery path (per `LPLock`'s own documentation of having no rescue mechanism in v1).

Note: I was not able to fully determine, from the available code/tests, the precise numeric skew required to force the router's `addLiquidity` split to round to exactly zero on HyperSwap's real (non-mock) V2 router — this depends on live on-chain integer-division behavior not captured in the indexed test mocks, and the dedicated end-to-end test suite that once probed this class of edge case has been removed. A Devin session with full repo/tooling access would be needed to simulate the exact reserve ratios against the real router bytecode (or a faithful fork) to confirm the precise trigger conditions.

### The exploit

A vanilla UniswapV2 pair is deployable by anyone: `factory.createPair(token, lt)` is permissionless, and after creation anyone can call `pair.mint(to)` against pre-transferred tokens. So between phase 1 (`_enterGraduating` flips lifecycle to `Graduating` and caches `tokensForLP / ltFromPair`) and phase 2 (`finalizeGraduation` mints LP via `pair.mint(lpLock)`), an attacker can:

1. Front-run by calling `factory.createPair(token, lt)` themselves
2. `transfer(pair, smallToken)` and `transfer(pair, smallLT)` at any ratio they choose
3. Call `pair.mint(attacker)` — they now own LP at a hostile reserve ratio

When our `pair.mint(lpLock)` runs in phase 2 against this non-empty pair, V2's mint formula picks up the existing reserves:

```
liquidity = min(amount0 · totalSupply / reserve0, amount1 · totalSupply / reserve1)
```

The `min(...)` arm whose denominator is bigger relative to its numerator wins, and the OTHER arm's "excess" deposit is donated pro-rata to existing LP holders — i.e. to the attacker. Two harms:

- **Wrong opening price.** Post-mint reserves are `(R_attacker + T_a, R_attacker + T_b)`, so the LP opens at `(R_a + T_a) / (R_b + T_b)`, NOT at the curve close `T_a / T_b`. A `$15` LT pre-seed at 50% off curve close opens the pool ~454 bps off.
- **LP capture.** The wasted-side excess goes to the attacker's LP claim. A `1 wei + 1 LT` pre-seed (~`$1` attack budget) captures ~34 bps of LP.

A cheaper variant skips step 3 entirely: `transfer(pair, dust) + pair.sync()` forces the stored reserves to the dust ratio without minting any LP, leaving the pair at `reserves > 0 && totalSupply == 0`. Regime 1 below covers both shapes by keying on supply rather than reserves.

    function finalizeGraduation(
        address tokenAddress
    ) external nonReentrant {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[tokenAddress];
        if (info.lifecycle != Lifecycle.Graduating) revert NotGraduating();

        address lt = info.ltAddress;
        PendingGraduation memory p = $.pendingGraduation[tokenAddress];

        // Anything in this contract beyond `p.ltFromPair` belongs to a
        // concurrent graduation on the same LT (Phase 1 transferred it
        // via `Router.graduate`) or to stray dust. Either way it is
        // off-limits to this graduation's deposit and sweep — see
        // `_routerDepositAndDispose` and `_sweepLTToOwner`.
        // Saturating subtract: a balance below `p.ltFromPair` shouldn't
        // be reachable in normal operation, but we keep finalize from
        // bricking on a Panic if any future code path or non-canonical
        // LT briefly violates the invariant.
        uint256 ltBalance = IERC20(lt).balanceOf(address(this));
        uint256 protectedLT = ltBalance > p.ltFromPair ? ltBalance - p.ltFromPair : 0;

        address lpPair = _ensureUniswapV2Pair(tokenAddress, lt);
        uint256 liquidity = _seedUniswapV2Direct(tokenAddress, lt, lpPair, p.tokensForLP, p.ltFromPair, protectedLT);

        _sweepLTToOwner(lt, protectedLT);

        info.lifecycle = Lifecycle.Graduated;
        $.graduatedPair[tokenAddress] = lpPair;
        delete $.pendingGraduation[tokenAddress];

        LPLock($.lpLock).recordLock(tokenAddress, lpPair, liquidity);

        emit TokenGraduated(tokenAddress, lpPair, liquidity, p.tokensForLP, p.lpBurned, p.unsoldBurned);
    }

    /// @dev Cap the rebalance swap at 99% of the available side's budget,
    ///      so the subsequent `addLiquidity` always has a non-zero amount
    ///      of BOTH sides to deposit. Without this, an extreme hostile
    ///      pre-seed (massively imbalanced reserves) drives the
    ///      unconstrained `_noFeeSwapInput` past our per-side budget,
    ///      `_pairRebalance` clamps to the full budget, and the swap
    ///      consumes 100% of one side. `_routerDepositAndDispose` then
    ///      skips `addLiquidity` (`remToken == 0` or `remLT == 0`),
    ///      `finalizeGraduation` returns `liquidity = 0`, and
    ///      `LPLock.recordLock(...)` records a zero-sized lock — the
    ///      attacker's pre-existing LP becomes 100% of the pool. Reserving
    ///      1% guarantees the deposit leg always lands AND mints non-zero
    ///      LP at the post-swap ratio. The 1% comes off the swap, not the
    ///      deposit — for any realistic pre-seed `s_unconstrained` is
    ///      orders of magnitude below `maxSwap`, so the cap doesn't bind
    ///      and behaviour is unchanged. It only kicks in for catastrophic
    ///      pre-seeds beyond our budget capacity, where the alternative
    ///      is bricking.
    function _swapBudget(
        uint256 budget
    ) internal pure returns (uint256) {
        return (budget * 99) / 100;
    }

    function recordLock(
        address token,
        address lpPair,
        uint256 amount
    ) external {
        LPLockStorage storage $ = _s();
        if (!$.isLocker[msg.sender]) revert NotAuthorized();
        if (lpPair == address(0)) revert ZeroAddress();
        if (amount == 0) revert ZeroAmount();
        // `lockedAt` is the one-shot sentinel: it is always set to a non-zero
        // timestamp on the first lock, so the guard holds for any `amount`.
        if ($.locks[token].lockedAt != 0) revert AlreadyLocked();
        if (IERC20(lpPair).balanceOf(address(this)) < amount) revert InsufficientLPBalance();
        $.locks[token] = LockInfo({lpPair: lpPair, amount: amount, lockedAt: block.timestamp});
        emit LPLocked(token, lpPair, amount);
    }
