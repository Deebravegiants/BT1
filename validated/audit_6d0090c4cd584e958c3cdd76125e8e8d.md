### Title
Unbounded Wasmtime guest gas-global seeding for view calls allows unbounded CPU exhaustion via pure-Wasm loop - ([File: runtime/near-vm-runner/src/logic/gas_counter.rs])

### Summary
`GasCounter::new` unconditionally widens `prepaid_gas` to `Gas::MAX` whenever `is_view` is true, and the Wasmtime backend seeds the in-guest finite-wasm gas global from `GasCounter::remaining_gas()`, which is computed directly from this unbounded `prepaid_gas` field rather than from the `max_gas_burnt` cap. For a pure-Wasm loop with no host imports, the finite-wasm instrumentation only calls back into host code (where `max_gas_burnt`/`max_gas_burnt_view` is actually enforced) when the guest gas global underflows a per-block constant, so seeding it near `u64::MAX` lets the loop run for an enormous number of iterations before the cap is ever checked.

### Finding Description
The attacker-reachable path is: RPC `call_function` query → `ViewRuntimeAdapter::call_function` (`chain/chain/src/runtime/mod.rs`) → `TrieViewer::call_function` (`runtime/runtime/src/state_viewer/mod.rs:322`) → `execute_function_call` → Wasmtime `PreparedContract::run` (`runtime/near-vm-runner/src/wasmtime_runner/mod.rs:1001`).

`TrieViewer::call_function` builds a synthetic `FunctionCallAction` whose `gas` field is set from `self.max_gas_burnt_view(...)` [1](#0-0) , and constructs a `ViewConfig { max_gas_burnt: max_gas_burnt_view }` passed down as `view_config` [2](#0-1) . `VMContext::make_gas_counter` uses this `max_gas_burnt` and calls `GasCounter::new(..., self.prepaid_gas, self.is_view())` [3](#0-2) .

Inside `GasCounter::new`, the `prepaid_gas` field used for `remaining_gas()` is unconditionally overwritten to `Gas::MAX` for view calls: [4](#0-3) 

While `fast_counter.gas_limit` is correctly derived as `min(max_gas_burnt, prepaid_gas)` (= `max_gas_burnt` since `prepaid_gas=Gas::MAX`), the `prepaid_gas` *field itself* stays at `Gas::MAX`. `remaining_gas()` is defined purely in terms of that field: [5](#0-4) 

The Wasmtime backend uses exactly this `remaining_gas()` value — not `fast_counter.gas_limit` — to seed and refresh the in-guest gas global on every host/wasm boundary transition, via `store.call_hook`: [6](#0-5) 

The finite-wasm instrumentation injects gas-checking code only at the start of each "metered block" (function entry / after `if`/`loop`), decrementing the guest `GAS_GLOBAL` and only calling back into the host (`GAS_INSTRUMENTATION_FN`/`finite_wasm_gas`, where `consume_gas`/`GasCounter::burn_gas` is invoked and the real `max_gas_burnt` limit is enforced) when the local subtraction would underflow: [7](#0-6) 

For a pure-Wasm contract method with no host imports at all (e.g., `(func (export "burn") (loop $l br $l))`), the very first `CallHook::CallingWasm` transition (entering the exported method from the host) seeds `GAS_GLOBAL` with `remaining_gas()` ≈ `Gas::MAX` (since `used_gas()` is 0 and `prepaid_gas` is `Gas::MAX`). The loop then executes purely in-guest, decrementing this near-`u64::MAX` counter locally per metered block, without ever calling back into the host to have `max_gas_burnt_view` checked — until the counter (seeded at ~`u64::MAX`) actually underflows, which for a cheap loop body can take on the order of `u64::MAX / per_block_cost` iterations (minutes to hours of wall-clock CPU), completely bypassing the intended `max_gas_burnt_view` cap that `TrieViewer::call_function` set up.

This is a concrete divergence between two representations of the same "budget" inside `GasCounter`: `fast_counter.gas_limit` (correctly bounded to `max_gas_burnt` for view calls) versus the `prepaid_gas` field / `remaining_gas()` (left unbounded at `Gas::MAX` for view calls), and only the latter is used to seed the Wasmtime guest gas global that gates pure-Wasm execution absent host calls.

### Impact Explanation
An unprivileged attacker who deploys a trivial contract with a host-import-free busy loop and issues a single anonymous `call_function` RPC query (view calls carry no `prepaid_gas`/signature and are unauthenticated) can pin an RPC/validator worker thread in unbounded CPU-bound execution for a very long time, well beyond the configured `max_gas_burnt_view` limit that operators rely on to bound view-call cost. This is a liveness / resource-exhaustion issue against RPC and validator nodes serving view queries (matches NEAR bounty class: node crash/hang or unbounded resource use via unprivileged input), not a state-transition or funds-loss bug since view calls never commit state changes.

### Likelihood Explanation
Feasible and fully repeatable by any account holder: deploy a Wasm contract containing a function with a `loop`/`br` construct and no host-function calls, then issue a `call_function` RPC query for it. No special privileges, gas payment, or protocol version gating are needed since `call_function` queries are anonymous/free and only require a state root and the contract already deployed. The bug is deterministic given the current `GasCounter::new` and `remaining_gas()` implementation and does not depend on race conditions.

### Recommendation
Bound the `prepaid_gas` field itself (not just `fast_counter.gas_limit`) by `max_gas_burnt` when constructing the view-mode `GasCounter`, e.g., `let prepaid_gas = if is_view { max_gas_burnt } else { prepaid_gas };` in `GasCounter::new`, so that `remaining_gas()` — and therefore the value seeded into the Wasmtime in-guest gas global — reflects the real cap. Add a watchdog-based regression test (already scaffolded as `runtime/near-vm-runner/src/tests/view_call_gas_limit.rs::view_call_gas_is_bounded_for_pure_wasm_loop`) to CI to prevent regression, and audit any other call sites relying on `GasCounter::remaining_gas()`/`prepaid_gas` for similar view/is_view divergence from `fast_counter.gas_limit`.

### Proof of Concept
Use/verify the existing test `runtime/near-vm-runner/src/tests/view_call_gas_limit.rs::view_call_gas_is_bounded_for_pure_wasm_loop`:
- Contract: `(module (func (export "burn") (loop $l br $l)))` (no host imports).
- `cap = Gas::from_teragas(1)`, `view_config = ViewConfig { max_gas_burnt: cap }`, `is_view = true`.
- Run the call on a watchdog thread with `recv_timeout(Duration::from_secs(60))`.
- Expected (post-fix) assertions: the call returns within timeout, `outcome.aborted` is `Some(FunctionCallError::HostError(GasLimitExceeded | GasExceeded))`, and `outcome.burnt_gas <= cap`.
- Given the current `GasCounter::new` code (`prepaid_gas = Gas::MAX` when `is_view`), this test is expected to either time out or burn dramatically more gas than `cap` before erroring, demonstrating the bypass. Extend with fuzzed loop-body shapes (varying block/instruction counts) to confirm the divergence is generic, not specific to the trivial loop.

    if matches!(gas, Fee::ZERO) {
        return Ok(());

        // expected to reinterpret the argument back to u64.

            .i64_lt_u()

            .if_(we::BlockType::Empty)

            .global_get(globals + GAS_GLOBAL)
            .i64_const(gas.constant as i64)
            .i64_sub()
            // $gas - $constant
            .global_set(globals + GAS_GLOBAL)
            .end();
        return Ok(());
    }
