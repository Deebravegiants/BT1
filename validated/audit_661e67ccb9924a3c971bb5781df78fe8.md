### Title
Webhook shop-domain and topic identity spoofing via fields excluded from HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while the `shop` and `topic` values used by `ShopifyAPI::Webhooks::Registry.process` to dispatch the event are read directly from unauthenticated HTTP headers. An attacker who possesses any single valid `(raw_body, hmac)` pair (e.g., from a webhook delivered to their own store after installing the target app) can replay it to the app's webhook endpoint while spoofing the `X-Shopify-Shop-Domain` and `X-Shopify-Topic` headers. `Utils::HmacValidator.validate` still passes because it only checks the untouched body against the signature, so the handler receives attacker-chosen `shop`/`topic` values bound to a legitimately-signed body.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop` and `topic` (and `webhook_id`/`api_version`) are pulled straight from request headers, which are never included in the signable string: [2](#0-1) 

`HmacValidator.validate` computes the HMAC over `to_signable_string` (the body) and compares it to the `hmac` header using a secure compare, without any reference to `shop`/`topic`: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.topic` and `request.shop` to look up the handler and build the metadata object passed to app code: [4](#0-3) 

This breaks the intended identity binding: `shop (verified by HMAC as the sender) == shop (acted on by the handler)`. In reality, only the body bytes are bound by the HMAC; the shop/topic headers are not. Since Shopify signs webhooks per-delivery with the app's shared secret, and an unprivileged user can freely install the target app on their own store to receive a legitimately-signed webhook, they can capture one `(raw_body, hmac)` pair and replay it with forged `shop-domain`/`topic` headers to make the app process it as if it originated from — or pertains to — a different shop or a different (potentially mandatory/destructive) topic such as `shop/redact` or `customers/redact`.

### Impact Explanation
This is a cross-tenant identity-binding bypass entirely within the gem's own webhook verification logic (`Webhooks::Request` + `Webhooks::Registry`), not a misuse of a documented API by the host app: the gem itself asserts that a request whose HMAC validates is a trustworthy webhook and exposes `.shop`/`.topic` as verified fields, when in fact those fields carry zero cryptographic binding. Any app that keys behavior off `WebhookMetadata#shop` or `#topic` (the very fields the gem hands the handler after "validating" the webhook) can be made to attribute events to the wrong shop or trigger the wrong topic handler, which qualifies as cross-tenant access under the Critical impact bucket.

### Likelihood Explanation
Moderate-to-high: no `api_secret_key`, access token, or privileged account is required — an ordinary internet user can install the target app on a store they control (a normal, unprivileged action against a public app) to receive at least one legitimately HMAC-signed webhook delivery, capture the raw body and `hmac` header, and replay it against the app's public webhook endpoint with forged `shop-domain`/`topic` headers.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable string used for HMAC verification (or otherwise cryptographically bind them), so that any tampering with these headers invalidates the signature — mirroring how the OAuth `AuthQuery#to_signable_string` binds `shop`, `host`, `code`, `state`, and `timestamp` together: [5](#0-4) 

### Proof of Concept
1. Install the target app on an attacker-controlled store `attacker.myshopify.com`; capture a legitimate webhook delivery, e.g. for topic `orders/create`, including its raw JSON body and the `X-Shopify-Hmac-Sha256` header value.
2. Send a new POST request to the app's webhook endpoint with the exact same raw body and `X-Shopify-Hmac-Sha256` header, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and, if desired, `X-Shopify-Topic: shop/redact`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (the unchanged raw body) and finds it matches — validation passes: [6](#0-5) 
4. The handler is invoked with `WebhookMetadata.new(topic: "shop/redact", shop: "victim-shop.myshopify.com", body: <attacker's captured body>, ...)`, i.e., the app processes an event as if it were a verified, on-topic webhook for `victim-shop.myshopify.com`, despite the HMAC never having covered either the shop or the topic.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
