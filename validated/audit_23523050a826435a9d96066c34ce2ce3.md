Confirmed: `Zap.buy`/`buyWithPermit` and `Zap.sell`/`sellWithPermit` take only a slippage bound (`minTokensOut` / `minUsdcOut`) and never a `deadline` parameter, exactly the pattern flagged in the external report.

### Title
Missing `deadline` parameter on `Zap.buy`/`sell` (and their permit variants) allows stale-price execution protected only by slippage - (File: packages/contracts/src/Zap.sol)

### Summary
`Zap.buy`, `Zap.buyWithPermit`, `Zap.sell`, and `Zap.sellWithPermit` accept a slippage bound (`minTokensOut` or `minUsdcOut`) but no `deadline` argument, so a signed/broadcast transaction can sit in the mempool (or be resubmitted after a long delay for the permit variants) and later execute against whatever curve/LT price exists at inclusion time. Slippage alone does not protect a user from executing at a stale, unfavourable reference price the user never intended to trade at — this is the exact bug class described in the external report for `BadDebtProcessor::uniswapV3FlashCallback()`.

### Finding Description
`Zap.buy` / `Zap.sell` compute output amounts from the live curve state (`Router.buy`/`Router.sell` against `Pair` reserves) or, post-graduation, from the live HyperSwap pool, and from the LT's live `exchangeRate()` via `mint`/`redeem`. No deadline is checked anywhere in `_buyInternal` or `_sellInternal`, and the public entry points don't take one: [3](#0-2) 
This mirrors the reported flaw: slippage bounds are computed relative to the price *at the time the user signed the transaction*, but they only check the price at *execution* time relative to itself — they cannot detect that the whole reference point (curve reserves, or the LT's `exchangeRate`) has moved substantially between signing and inclusion. A `minTokensOut`/`minUsdcOut` calculated off a stale quote can still pass while giving the user a far worse fill than intended, because the check only bounds "how bad is this trade relative to its own on-chain state right now," not "was this trade meant to execute now at all."

### Impact Explanation
A trader's `buy`/`sell` transaction that is delayed (stuck in a congested mempool, deliberately held back by a validator/searcher, or simply resubmitted much later by a wallet with the same signature/nonce logic — particularly relevant for `buyWithPermit`/`sellWithPermit`, where the permit signature itself carries its own independent deadline that is unrelated to the trade's price freshness) can be executed at a materially different curve price or LT `exchangeRate()` than the user expected. Because the `minTokensOut`/`minUsdcOut` slippage figure is typically computed client-side from a quote taken well before signing, a sufficiently wide slippage tolerance (or one computed against a now-stale price) does not prevent the trade from executing at a bad, though technically "within-slippage," price — this is direct loss of funds to the trader, matching the report's medium-severity impact class (loss to the user due to delayed execution with stale slippage protection).

### Likelihood Explanation
Medium. Exploiting this requires either network congestion/mempool delay, a malicious block-builder/validator deliberately holding the transaction, or a UI/wallet flow that lets a signed trade linger — none of which require any special privilege, and all are realistically reachable by an ordinary trader's transaction sitting unmined during volatility. The LT's `exchangeRate()` and the curve/pool reserves can move meaningfully during any such delay, especially given the leveraged nature of the reserve asset noted throughout the docs (`packages/contracts/AGENTS.md`).

### Recommendation
Add a `deadline` parameter to `Zap.buy`, `Zap.buyWithPermit`, `Zap.sell`, and `Zap.sellWithPermit` and revert (e.g. `if (block.timestamp > deadline) revert Expired();`) at the top of `_buyInternal`/`_sellInternal` before any state-changing calls, mirroring the deadline pattern already used elsewhere in the codebase for `IUniswapV2Router02.addLiquidity` calls (`block.timestamp` deadline in `_routerDepositAndDispose`).

### Proof of Concept
1. A trader calls `Zap.buy(tokenAddress, usdcAmount, minTokensOut, referrer)` with `minTokensOut` computed off the current curve/LT quote, then signs and broadcasts the transaction.
2. The transaction is delayed in the mempool (network congestion, MEV searcher delay, or simply low gas price) while the curve price or the LT's `exchangeRate()` moves unfavourably for the trader (e.g., other buys/sells shift `Pair` reserves, or BounceTech's rate drifts).
3. The transaction is eventually included. `_buyInternal` only checks `tokensOut < minTokensOut` at line 256 — it has no way to know the trade is stale, so it executes as long as the (now much worse) fill still clears the slippage bound.
4. The trader receives a technically "within-slippage" but objectively much worse fill than intended when they signed, with no on-chain mechanism (deadline) available to have prevented the trade from executing at all.
