The reported bug class is a native-token (`msg.value`) double-spend that occurs specifically because `XProvider.xTransferToController` forwards `msg.value` twice across two independent cross-chain send paths (`xTransfer` and `pushFeedbackToXController → xSend`) when `relayerFee == 0`. This requires a cross-chain messaging layer with a relayer-fee-in-native-currency pattern.

alt.fun's in-scope contracts (`Zap.sol`, `Bonding.sol`, `Router.sol`, `Pair.sol`, `FeeVault.sol`, `LPLock.sol`) have no cross-chain messaging, no relayer fee mechanism, and no `msg.value`/native-currency handling at all — every fee and value flow is denominated in USDC or the LT, moved via `IERC20.safeTransfer`/`safeTransferFrom` [1](#0-0) [2](#0-1) . A grep for `msg.value` across `packages/contracts/src` returns zero matches; it only appears in vendored OpenZeppelin/forge-std library code unrelated to alt.fun's business logic.

There is no analogous "two independent code paths spend the same externally-supplied value" pattern reachable by an unprivileged trader/creator in alt.fun's fee/accrual flow (`Zap._accrueFee` → `FeeVault.accrue`, which is guarded by an underfunding check against the vault's actual USDC balance) [3](#0-2) , nor in the bonding-curve buy/sell fee math. Since the root cause (native-currency relayer fee double-counted across two cross-chain send calls) has no structural counterpart in this codebase, this analog does not stand on alt.fun's own code.
