## Title
Webhook `shop` identity is trusted from an unsigned header while the HMAC only covers the raw body, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the merchant identity (`shop`), `topic`, `api_version`, and `webhook_id` from HTTP headers, but the HMAC signature that `Utils::HmacValidator` checks is computed only over the raw request body. Any attacker who possesses one valid `(body, hmac)` pair for their own shop (trivial to obtain, since they can trigger webhooks on their own store) can replay that exact body/HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop. The signature still validates, and the forged shop identity is passed unverified into the app's webhook handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `shop` (and `topic`, `webhook_id`, `api_version`) are pulled straight from attacker-controllable headers with no cryptographic binding to that body: [2](#0-1) 

`Utils::HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (the body) and compares it against the `hmac-sha256` header: [3](#0-2) 

`Registry.process` then trusts `request.shop` as the authenticated tenant identity and forwards it into the handler's `WebhookMetadata` without any further check: [4](#0-3) 

The broken identity-binding equality is:
`HMAC-verified bytes (raw_body)` ≠ `bytes used to establish shop identity (shop-domain header)`

Because the header is outside the signed data, HMAC validity over the body says nothing about the authenticity of the `shop` value the handler receives.

### Impact Explanation
This is a cross-tenant identity-binding break: an unprivileged internet user who controls any shop (including a free development store) can capture a legitimate `(body, hmac)` pair generated by their own store's real webhook delivery, then POST it to the app's public webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim merchant's domain. `Utils::HmacValidator.validate` still returns `true` because the body is unchanged, so `Registry.process` dispatches the handler believing the payload originated from the victim shop (`data.shop` in `WebhookMetadata`). Any app logic that keys session/token lookups, database writes, or downstream Shopify API calls off `data.shop` can be tricked into attributing attacker-supplied data to the victim tenant — a cross-tenant confusion/injection primitive.

### Likelihood Explanation
Likelihood is moderate to high in practice for apps that expose a public webhook endpoint: the attacker only needs their own shop (which anyone can create), the ability to trigger a webhook topic they've subscribed to, and access to intercept/replay their own HTTP request — no access to the app's `client_secret`, no privileged account on the victim shop, and no TLS interception of the victim's traffic are required.

### Recommendation
Bind the shop (and other identity-bearing headers such as topic/webhook-id) into the signed material verified by `HmacValidator`, or otherwise cryptographically tie the header values to the payload (e.g., require the consuming app to cross-check `shop` against a value obtained through an authenticated channel, such as a previously stored session for that shop, before trusting the webhook as belonging to that tenant) instead of trusting `x-shopify-shop-domain` on its own as the tenant identity in `WebhookMetadata`.

### Proof of Concept
1. Attacker owns `attacker.myshopify.com` and subscribes it to a webhook topic handled by the target app.
2. Shopify delivers a legitimate webhook: `raw_body = B`, headers include `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's `client_secret`) and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker replays the exact same request to the app's webhook endpoint, only changing the header to `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes HMAC over `B` (per `Request#to_signable_string`, `lib/shopify_api/webhooks/request.rb:35-38`) — matches `H`, so validation passes.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) builds `WebhookMetadata` with `shop: "victim.myshopify.com"` and dispatches it to the app's handler, which now processes attacker-controlled data as if it came from the victim shop.
