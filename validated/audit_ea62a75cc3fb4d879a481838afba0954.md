### Title
Webhook Shop Identity Not Bound to HMAC-Verified Bytes Enables Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating an HMAC over the raw request body, computed with the app-level `client_secret` shared across every shop that installs the app. The `shop` identity attribute that is handed to the app's webhook handler, however, is read from an HTTP header that is never included in the signed bytes. Any unprivileged user who installs the app on their own store receives genuinely-signed webhooks and can replay them against the app's webhook endpoint while substituting the `shop-domain`/`x-shopify-shop-domain` header for a victim shop, producing a request that passes HMAC validation but is attributed to the wrong tenant.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all sourced from HTTP headers that are outside the signed material: [2](#0-1) 

`Registry.process` validates only the HMAC via `Utils::HmacValidator.validate(request)` (which checks `request.hmac` against `HMAC-SHA256(client_secret, raw_body)`), then immediately trusts `request.shop` when constructing the metadata passed to the app-supplied handler: [3](#0-2) 

The HMAC secret is the app's single `Context.api_secret_key` (client_secret), identical for all merchant shops that install the app — not a per-shop secret: [4](#0-3) 

The equality that should hold is: `shop attributed to the webhook == shop whose data actually produced/authorized the signed bytes`. Because `shop` is parsed from an unsigned header while only the body bytes are verified, an attacker can decouple these two values: a body legitimately signed for the attacker's own shop can be paired with an arbitrary `shop-domain` header naming a victim tenant, and `HmacValidator.validate` will still return `true` because it only checks the body bytes against the shared client secret — it never checks that the header-derived `shop` matches anything cryptographically bound to the payload.

### Impact Explanation
This is a cross-tenant authentication/identity-binding failure (High/Critical depending on handler logic): a host application that keys its per-shop database updates, order/customer records, or app installation state off `WebhookMetadata#shop` can be tricked into applying attacker-controlled webhook payloads (e.g., `orders/create`, `customers/update`, `app/uninstalled`) to a victim shop's tenant record, since the gem asserts nothing that binds the header-derived shop to the signed body. This satisfies "cross-tenant access" in the accepted impact categories, driven purely by the gem's own verification logic (`HmacValidator` + `Webhooks::Request`/`Registry`), with no privileged credentials, leaked secrets, or social engineering required beyond the attacker installing the app on their own store (an action available to any unprivileged Shopify merchant/developer).

### Likelihood Explanation
Likelihood is high for any app relying on `ShopifyAPI::Webhooks::Registry.process` with the shipped `Webhooks::Request`: the attacker only needs (1) to install the target app on a store they control, which is normal, unprivileged self-service action, and (2) the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with a modified `shop-domain` header and the intercepted, still-valid `hmac-sha256` header and body from their own legitimate webhook delivery. No knowledge of `api_secret_key` or any victim credential is required.

### Recommendation
Bind the trusted shop identity to the verified payload instead of an independent header: include the `shop` (and ideally `topic`/`webhook_id`) in the signed material used to compute/verify the HMAC, or require the host application to cross-check `request.shop` against a shop the app has an active installation/session for using a value derived from data that is itself authenticated (e.g., verify the shop domain embedded in the JSON body against the header before trusting `WebhookMetadata#shop`). At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated header data and must not be trusted for tenant selection without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`, receiving a legitimate webhook, e.g. body `{"id":1,"note":"x"}` with header `x-shopify-hmac-sha256: <valid hmac of that body under the shared client_secret>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker replays the exact same body and `hmac-sha256` header to the app's webhook endpoint but changes the header to `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally the `topic` header to target a different handler).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(client_secret, raw_body)` — unaffected by the header change — and returns `true`.
4. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: ..., ...)`, causing the host application to apply the attacker's payload as if it originated from `victim-shop.myshopify.com`. [5](#0-4)
