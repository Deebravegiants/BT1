### Title
Webhook `shop`, `topic`, `webhook_id` and `api_version` headers are trusted without being covered by the HMAC, allowing header-spoofed webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used for tenant identification and handler dispatch are read straight from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` verifies only the body HMAC and then trusts these header-derived fields, breaking the intended binding between "bytes verified" and "fields acted on."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read from HTTP headers that are not part of the signed payload: [2](#0-1) 

`Registry.process` validates the request using only the HMAC over the body, then immediately dispatches based on the unauthenticated header fields: [3](#0-2) 

This is the exact bug class named in the rules: "a field acted on but not covered by the HMAC." The equality the code implicitly assumes is:
`bytes_verified_by_hmac == identity_fields_used_for_routing`
but in reality:
`bytes_verified_by_hmac (raw_body) ⊄ {shop, topic, webhook_id, api_version}` (all header-derived, unsigned).

Because `HmacValidator.validate` (via `VerifiableQuery`) only ever checks `to_signable_string`, which for `Request` is `@raw_body`, any header can be freely modified after a legitimately-signed webhook body is obtained, and the signature will still validate: [4](#0-3) 

### Impact Explanation
An unprivileged internet user who owns any shop with the target app installed will legitimately receive real, HMAC-signed webhook deliveries from Shopify (addressed to the app's public webhook endpoint) for their own shop. Because the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are outside the HMAC's protected scope, that user can replay the identical body+HMAC pair to the app's endpoint while substituting a different shop's domain (or a different topic) in the headers. `Registry.process` will accept the request as valid — the signature check passes — and hand the handler a `WebhookMetadata` object whose `shop` and `topic` are attacker-controlled: [5](#0-4) 

Any host application that uses `data.shop` to select the tenant record to update (the documented usage pattern of this gem) will process attacker-supplied webhook content under the identity of a shop the attacker does not control, i.e., cross-tenant data injection/confusion.

### Likelihood Explanation
The attacker only needs to run the app on their own store to obtain a genuine signed webhook, then resend it to the app's public webhook URL with a modified `shop-domain`/`topic` header using a normal HTTP client — no `api_secret_key`, access token, or any privileged access is required.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signable payload that the HMAC is computed and verified over (or otherwise cryptographically bind them to the signed body), so that spoofing any of these header values invalidates the signature.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a real webhook (e.g., `orders/create`), capturing the raw POST including `x-shopify-hmac-sha256`, `x-shopify-topic`, `x-shopify-shop-domain`, `x-shopify-webhook-id`, `x-shopify-api-version` headers and body.
2. Attacker resends the exact same body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim.myshopify.com` (a shop that also has the app installed).
3. `Request.new` accepts the headers, `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the body HMAC — validation succeeds.
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", topic: ..., body: attacker's body, ...)` and, per the documented handler pattern, updates data under the victim shop's tenant using attacker-controlled content.
