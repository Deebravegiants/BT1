Audit Report

## Title
Cross-workflow HTTP response cache poisoning in gateway HTTP capability handler due to missing `WorkflowID` scoping in cache key - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

## Summary
The gateway's v2 HTTP capability handler caches outbound `OutboundHTTPResponse` values (including cacheable 4xx bodies) keyed solely by `req.Hash()`, and the project's own test suite proves this hash is insensitive to `WorkflowID` while being sensitive to `WorkflowOwner`. This directly contradicts the documented isolation guarantee in `README.md` ("Cache entries are scoped by workflow ID to prevent cross-workflow data leakage"), allowing two workflows sharing the same `WorkflowOwner` to collide on the same cache entry.

## Finding Description
`responseCache.Set` and `responseCache.Fetch`/`isExpiredOrNotCached` both key the cache map exclusively by `req.Hash()`, with no additional namespacing by `WorkflowID`: [1](#0-0) [2](#0-1) [3](#0-2) 

The dispatch path in `http_handler.go`'s `makeOutgoingRequest` unmarshals a node-relayed `OutboundHTTPRequest` (originating from workflow execution) and calls `Fetch`/`Set` using this same `req` value, without any separate workflow-scoping key: [4](#0-3) 

The repository's own unit tests confirm the cache key ignores `WorkflowID` but does honor `WorkflowOwner`: [5](#0-4) 

This directly contradicts the component's documented design intent: [6](#0-5) 

`isCacheableStatusCode` also caches 4xx client-error bodies, expanding the range of poisoned/leaked content: [7](#0-6) 

No middleware, redaction, or per-workflow namespace exists anywhere in this handler to compensate — `WorkflowOwner` is the only scoping dimension actually enforced by `Hash()`, and it is coarser than the documented "per-workflow" isolation.

## Impact Explanation
Two distinct workflows sharing a `WorkflowOwner` (e.g., a single owner/address operating multiple independent workflow deployments, or a marketplace-style multi-workflow account) that issue outbound HTTP requests with matching method/URL/headers/body can read or overwrite each other's cached HTTP response, including cached 4xx error bodies. This matches the "cross-user response corruption" impact category: a workflow can inject a stale or attacker-influenced response that a differently-scoped workflow later consumes as if it were a fresh external HTTP result, or can observe response data intended for another workflow's cache slot. Severity is bounded by the fact that `WorkflowOwner` isolation is still enforced (no cross-owner leakage is possible), limiting blast radius to workflows under the same owner.

## Likelihood Explanation
Exploitation requires the attacker to control a workflow deployed under the same `WorkflowOwner` as the target workflow and to predict/match the victim's exact outbound request shape (method, URL, headers, body), plus the victim using `CacheSettings.Store=true`/`MaxAgeMs > 0`. This is realistic for CRE deployments where a single owner account runs several workflows making calls to well-known, predictable external APIs. The bug is deterministically reproducible via the existing unit tests in `response_cache_test.go`, which explicitly assert the vulnerable behavior (`hash1 == hash2` for differing `WorkflowID`).

## Recommendation
Include `WorkflowID` (or an equivalent immutable per-workflow identifier) in the cache key alongside `req.Hash()`, e.g., by composing the map key as `fmt.Sprintf("%s:%s", req.WorkflowID, req.Hash())` in `response_cache.go`, so cache entries are strictly isolated per workflow as documented in `README.md`. Correct the misleading test at `response_cache_test.go:139-149` to assert that differing `WorkflowID` produces differing cache keys once fixed. Consider also gating caching of 4xx bodies behind an explicit opt-in to reduce exposure of potentially sensitive reflected request data.

## Proof of Concept
1. Two workflows A and B share `WorkflowOwner = "0xabc"` with different `WorkflowID`s (`workflow-123` vs `workflow-456`).
2. Workflow A issues `OutboundHTTPRequest{Method:"GET", URL:"https://api.example.com/data", CacheSettings:{Store:true}}`; `makeOutgoingRequest` calls `h.responseCache.Set(req, outboundResp)`, storing under `req.Hash()` (`http_handler.go:439-441`, `response_cache.go:110-120`).
3. Workflow B issues an identical request (same method/URL/headers/body, different `WorkflowID`) with `CacheSettings.MaxAgeMs > 0`; `Fetch` computes the same `req.Hash()` and returns Workflow A's previously cached response instead of performing a fresh fetch.
4. This is directly demonstrated by the existing unit test `TestRequestHash/having different workflowID results in same Hash` at `response_cache_test.go:139-149`, which can be run as-is (`go test ./core/services/gateway/handlers/capabilities/v2/... -run TestRequestHash`) to confirm the colliding hash behavior.

```go
func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

	// Slow path: singleflight deduplicates concurrent fetches per key.
	// Cache check + store happen inside the flight so the key isn't released
	// until the result is cached, closing the race window between singleflight
	// completion and cache write.
	result, _, _ := rc.flight.Do(cacheKey, func() (any, error) {
		// Re-check cache: a previous flight may have just stored the result.
		rc.cacheMu.RLock()
		cachedResp, exists := rc.cache[cacheKey]
		rc.cacheMu.RUnlock()
		if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
			rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
			return cachedResp.response, nil
		}

		response := fetchFn()

		if storeOnFetch && isCacheableStatusCode(response.StatusCode) {
			rc.cacheMu.Lock()
			rc.cache[cacheKey] = &cachedResponse{
				response: response,
				storedAt: time.Now(),
			}
			rc.cacheMu.Unlock()
		}

		return response, nil
	})

	return result.(gateway.OutboundHTTPResponse)
}
```

```go
// Set caches a response if it is cacheable (2xx or 4xx and cache is empty or expired for the given request)
func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}
```
