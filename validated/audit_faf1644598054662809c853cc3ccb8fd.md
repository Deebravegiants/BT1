### Title
Webhook `shop` (tenant) identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop`, `topic`, `webhook_id`, and `api_version` fields entirely from HTTP headers, while the HMAC signature verified by `Utils::HmacValidator` only covers the raw request body. This breaks the binding `hmac == HMAC(secret, shop || body)` that a tenant-identifying webhook payload should have; effectively `hmac == HMAC(secret, body)` regardless of `shop`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the signature purely from `to_signable_string` (the body) and compares it against the `hmac` header: [2](#0-1) 

Meanwhile, `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are read straight from headers that are never part of the signed material: [3](#0-2) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` before trusting `request.shop` (and the other header-derived fields) and forwarding them, unauthenticated as to tenant, into the app's handler via `WebhookMetadata`: [4](#0-3) [5](#0-4) 

Because the app's `client_secret` is shared across every shop that installs the app, any shop owner (an "unprivileged internet user" with respect to other tenants) can install the app on their own store, capture a genuine webhook delivery (valid body + valid HMAC for their own shop), and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to point at a victim shop. Since the signature check never touches the `shop` header, the forged request passes `HmacValidator.validate` and `Registry.process` hands `WebhookMetadata(shop: "victim-shop.myshopify.com", ...)` to the host application's handler as if it were an authentic event from the victim's store.

The binding that should hold is:
`request.shop (trusted tenant identity) == request.shop (bytes actually covered by the HMAC)`
but in this implementation the left side is taken from an unauthenticated header while the right side is the empty set — the shop is never part of the signed bytes.

### Impact Explanation
This is a cross-tenant identity confusion at the webhook layer: an attacker who legitimately controls one shop/installation can cause the app to process forged data attributed to a different, victim shop. Any host application logic that keys off `WebhookMetadata#shop` (e.g., updating order/inventory state, revoking access, triggering per-shop side effects, looking up sessions/access tokens by shop) can be tricked into acting on the victim tenant using attacker-controlled body content, since only the body's authenticity (not its shop attribution) is verified. This matches "cross-tenant access" impact.

### Likelihood Explanation
Exploitation only requires an attacker to be able to install the app on their own shop (a normal, unprivileged action any Shopify merchant/developer can take), capture one legitimate webhook HTTP request for that shop, and resend it to the app's public webhook endpoint with a modified `shop-domain`/`x-shopify-shop-domain` header. No access to another merchant's credentials, the `client_secret`, or TLS interception is required — likelihood is high for any app that relies on `WebhookMetadata#shop` as a trusted tenant identifier.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signed material verified against the HMAC, or otherwise cryptographically/contextually bind the `shop-domain` header to the specific installation the webhook endpoint expects (e.g., cross-check `request.shop` against the shop associated with the destination endpoint/session before trusting it), rather than trusting an unauthenticated header value directly in `WebhookMetadata`.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and has installed the target app.
# Shopify delivers a genuine webhook to the app's endpoint:
headers = {
  "shopify-topic" => "orders/create",
  "shopify-hmac-sha256" => genuine_hmac_from_shopify, # valid HMAC of raw_body with shared client_secret
  "shopify-shop-domain" => "attacker-shop.myshopify.com",
}
raw_body = '{"id":1,"note":"hello"}'

# Attacker replays the exact same body + hmac, only changing the shop header:
forged_headers = headers.merge("shopify-shop-domain" => "victim-shop.myshopify.com")

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => Utils::HmacValidator.validate(request) still returns true, because it only hashes raw_body.
# => The app's handler receives WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
#    even though the payload never originated from, nor was authorized for, that shop.
```
