### Title
Webhook shop-domain identity spoofing due to HMAC coverage gap - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
The report describes an access-control bypass rooted in trusting an unverified identity field. The analogous flaw here is in `ShopifyAPI::Webhooks::Request`: the HMAC signature covers only the raw request body, while the `shop` (tenant identity) is read from an HTTP header that is never included in the signed material. `Registry.process` then dispatches to the app's handler using this unauthenticated `shop` value as if it were verified.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is parsed directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the signature: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)` — i.e., body-only: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` to construct `WebhookMetadata`, which is handed to the app's handler as the tenant identifier: [4](#0-3) 

The identity binding that should hold is: `shop authenticated == shop acted upon`. Here, `shop` is never part of the HMAC-signed payload, so `shop verified-by-signature` ≠ `shop used-for-dispatch`. Since a single app-level `client_secret` signs webhooks for *every* shop that installs the app, any valid `(raw_body, hmac)` pair obtained from a legitimately delivered webhook (e.g., via Shopify's webhook delivery logs/replay tooling, which expose the exact bytes and signature sent) remains valid when replayed to the app's public webhook endpoint with the `shop-domain` header swapped to a different, victim shop that also has the app installed. `HmacValidator.validate` will still pass because it only checks the body against the shared secret, and `Registry.process` will invoke the handler believing the event originated from the victim's tenant.

### Impact Explanation
This breaks the tenant boundary the gem is expected to preserve: an unprivileged user who has installed the app on their own shop (or otherwise obtains a valid signed payload) can make the app process a forged event under another shop's identity. Any host application logic that keys off `WebhookMetadata#shop` to look up/act on per-tenant session or data (a documented and expected usage pattern) can be induced into cross-tenant data corruption or context confusion, since the gem itself provides no mechanism to bind `shop` to the signature.

### Likelihood Explanation
Moderate: the attacker needs a legitimately signed `(body, hmac)` pair, which is obtainable from their own shop's real webhook traffic (e.g., via delivery logs/debug tooling that surfaces the exact signed bytes), plus knowledge that the target shop also has the app installed. No secret material needs to be recovered — only replay of already-valid signed bytes with a substituted header.

### Recommendation
- Short term: In `Registry.process`/`Request`, require host apps to cross-check `request.shop` against an independently trusted record (e.g., an existing stored session for that shop and topic) before acting, and document this prominently.
- Long term: Extend `to_signable_string`/HMAC computation (or add a secondary check) to bind the `shop` domain into the verified identity, or expose a dedicated verification API that returns a shop only after confirming it against the app's known installed-shop registry, rather than relying solely on an unauthenticated header parsed by `Request#shop`.

### Proof of Concept
1. App developer registers webhook handler `X` for topic `orders/create`.
2. Attacker installs the app onto `attacker.myshopify.com` and triggers an `orders/create` event; Shopify delivers a POST to the app's shared webhook endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(secret, B)`.
3. Attacker retrieves the exact delivered bytes (`B`, `H`) via Shopify's webhook delivery inspection tooling.
4. Attacker sends their own POST to the same public webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged), but `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only hashes `B` [1](#0-0) ; `Registry.process` invokes the handler with `data.shop == "victim.myshopify.com"` [5](#0-4) , causing the app to act as though the event came from the victim tenant.
