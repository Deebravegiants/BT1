### Title
Webhook `shop` (and `topic`/`webhook_id`) headers are trusted without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC signature over the raw request body. The `shop`, `topic`, and `webhook_id` values that are handed to the app's `WebhookHandler` as trusted tenant/routing identifiers are read from HTTP headers that are completely outside the scope of what the HMAC signs, so they can be freely modified by anyone able to submit a request with a validly-signed body.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop`, `#topic`, and `#webhook_id` are all read from HTTP headers, independent of the signed body: [2](#0-1) 

`Registry.process` validates the HMAC and, if it passes, unconditionally trusts `request.topic`, `request.shop`, and `request.webhook_id` to build `WebhookMetadata`, which is passed to the app's handler as the authenticated identity of the sending shop: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` computes the signature purely from `verifiable_query.to_signable_string` (i.e., the body) and compares it to the `hmac` header — it never incorporates `shop`, `topic`, or `webhook_id`: [4](#0-3) 

The equality the gem implicitly claims to guarantee is: `HMAC-valid request` ⇒ `header.shop == the shop that actually generated this body`. In reality the guarantee only is `HMAC-valid request` ⇒ `body was generated by some shop using this app's secret`. Because Shopify signs webhooks with the single app-wide `client_secret` (not a per-shop secret), any merchant who installs the app on their own store is an "unprivileged internet user" relative to every other tenant of the app, yet can obtain a body+HMAC pair that is valid for the shared secret. That merchant can then replay the exact same `raw_body`/`hmac-sha256` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header with a victim shop's domain. `Registry.process` still finds `Utils::HmacValidator.validate(request)` to be `true` (it only checked the body), and dispatches to the handler with `WebhookMetadata.shop` set to the attacker-chosen victim domain.

This breaks the identity binding: **HMAC-covered bytes ("raw_body") ≠ bytes the application authenticates as belonging to a shop ("shop-domain" header)**.

### Impact Explanation
If a host application uses `WebhookMetadata#shop` (as documented in `docs/usage/webhooks.md`) to key into per-tenant session/data storage — the exact pattern this gem's docs recommend (`perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) — an attacker-controlled webhook body (with attacker's own data) can be attributed to and processed under any victim shop's tenant context, e.g. writing to the victim's local order/customer records, or triggering privileged shop-specific side effects (uninstall/redact handling, GDPR data requests, etc.) using the attacker's chosen `shop`. This is cross-tenant data confusion/injection driven purely by a request that satisfies this gem's own authenticity check.

### Likelihood Explanation
Any threat actor can become a legitimate (if minimal) install of the target app by installing it on a free development/trial shop — no privileged credentials, leaked secrets, or the app's `client_secret` are required. Once installed, Shopify itself will deliver a validly-HMAC-signed webhook to the app for actions the attacker performs in their own store. Capturing that raw body/HMAC pair and replaying it with a spoofed `shop-domain` header is a low-effort HTTP-level manipulation, entirely within reach of an unprivileged internet user who can create a Shopify dev store.

### Recommendation
Bind the tenant/routing identity into the authenticated payload, not just headers. Options:
- Require and verify that the `shop-domain` header matches a shop endpoint the app expects to receive webhooks for (e.g. compare to a shop already registered/known to have installed with an active session before dispatching), and/or
- Compute/require the HMAC over headers + body (Shopify does not support this natively, so at minimum add a secondary validation step) so `shop`, `topic`, and `webhook_id` cannot be swapped independently of the signed body, or
- Have `Registry.process` cross-check `request.shop` against the shop referenced inside the parsed webhook body/GraphQL id where available, rejecting mismatches.

At minimum, the gem's documentation and `WebhookMetadata` should clearly warn that `shop`, `topic`, and `webhook_id` are NOT authenticated by the HMAC check and must not be used as the sole tenant-identity source for sensitive operations.

### Proof of Concept
1. Attacker installs the target Shopify app on their own dev store `attacker.myshopify.com`, obtaining a legitimate installation and thus real webhook deliveries signed with the app's shared `client_secret`.
2. Attacker triggers an event (e.g. `orders/create`) in their store, capturing the exact `raw_body` and `X-Shopify-Hmac-Sha256` header Shopify sends to the app's webhook endpoint.
3. Attacker replays the identical `raw_body` and `X-Shopify-Hmac-Sha256` value to the same app endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. In `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-199`), `Utils::HmacValidator.validate(request)` returns `true` because it only checks `raw_body` against the HMAC, which is unchanged and still valid.
5. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built with `shop == "victim.myshopify.com"` and handed to the app's `WebhookHandler#handle`, causing the app to process attacker-supplied data under the victim's tenant identity.
