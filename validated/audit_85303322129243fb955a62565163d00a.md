### Title
Webhook shop/topic identity spoofing via unsigned headers - (File: lib/shopify_api/webhooks/request.rb)

### Summary
The webhook HMAC validation in this gem only covers the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` fields — which are taken from HTTP headers and handed to the application's webhook handler as trusted, verified metadata — are never included in the HMAC computation. An attacker who can obtain any valid `(body, hmac)` pair signed with the app's shared `client_secret` (e.g. from a webhook fired to their own store, since Shopify apps use one `client_secret` shared across all installs) can replay it with an arbitrary `x-shopify-shop-domain` header, and `Registry.process` will accept it as authentic for that victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are parsed straight from headers and are never part of the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` only checks the signature over `verifiable_query.to_signable_string`, i.e. the body, using `Context.api_secret_key` (the app's single, shop-independent secret): [3](#0-2) 

`Registry.process` treats HMAC success as full authentication of the request and then constructs `WebhookMetadata` directly from the unauthenticated `shop`/`topic`/`webhook_id` headers, passing them to the app's handler with no additional binding check between the verified body and the claimed shop: [4](#0-3) 

This breaks the intended identity binding `hmac_signed_content == (body, shop)`. In reality the equality only holds for `hmac_signed_content == body`; `shop` is asserted, not verified. Because `Context.api_secret_key` is the same secret across every shop that has installed the app, any attacker with a store running the app can generate a valid `(body, hmac)` pair (via their own store's genuine webhook deliveries) and then submit a forged HTTP request straight to the app's webhook endpoint with the same body/hmac but a different `x-shopify-shop-domain` (and/or `x-shopify-topic`) header. `Registry.process` will accept it, and the handler will act on data believing it originated from the victim shop.

### Impact Explanation
This crosses a tenant boundary: apps commonly use the `shop` field from `WebhookMetadata` to look up/mutate per-merchant records (billing state, inventory sync, order records, uninstall/app-uninstalled handling, etc.). An attacker can inject fabricated events attributed to an arbitrary victim shop domain that also uses the app, causing cross-tenant data corruption or state changes keyed by a shop the attacker does not own. This matches the "cross-tenant access" criterion for Critical impact.

### Likelihood Explanation
Exploitation only requires: (1) the attacker's own store installs the target app (trivial for public apps), giving them a genuine `(body, hmac)` pair signed with the same shared `client_secret`; and (2) the ability to send a raw HTTP POST to the app's public webhook endpoint with modified headers — no access token, TLS interception, or social engineering is needed. This is a straightforward, repeatable network-level forgery against the gem's own webhook-processing logic.

### Recommendation
Include the identity-relevant headers (`shop`, `topic`, `webhook_id`, `api_version`) in the value that is HMAC-verified, or otherwise cryptographically bind them to the signed body (e.g., concatenate them into the signable string, mirroring how OAuth's `AuthQuery#to_signable_string` binds `shop`/`state`/etc.). At minimum, `Registry.process` should not trust `request.shop`/`request.topic` for authorization decisions unless they are covered by the verified signature.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, triggering Shopify to send a genuine webhook: body `B`, headers including `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the shared `client_secret`) and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker replays this exact request directly to the app's webhook endpoint, but replaces the header with `x-shopify-shop-domain: victim.myshopify.com` (and optionally a different `x-shopify-topic`), keeping body `B` and HMAC `H` unchanged.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `request.to_signable_string` (`B`) — this still matches `H`, so validation passes: [4](#0-3) 
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` even though the request was never actually authorized by or for that shop, and the app processes it as a legitimate event for the victim's tenant.
