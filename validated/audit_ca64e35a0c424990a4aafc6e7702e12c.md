The scenario described is exactly the case this code is designed to prevent, and the existing implementation already handles it correctly.

**How the protection works:**

Transactions within a batch are processed strictly sequentially in a single-threaded loop inside `load_and_execute_sanitized_transactions`, not concurrently: `for (tx, check_result) in sanitized_txs.iter().zip(check_results) { ... }`. [1](#0-0) 

For each transaction, `validate_transaction_nonce_and_fee_payer` derives `next_durable_nonce` once from the shared batch blockhash, then calls `validate_transaction_nonce`, which loads the nonce account via `account_loader.load_transaction_account(nonce_address, true)` — reading from the shared `AccountLoader` cache, not directly from accounts-db each time. [2](#0-1) [3](#0-2) 

The comment directly above this logic explains the intent: "When SIMD83 is enabled, if the nonce has been used in this batch already, we must drop the transaction. This is the same as if it was used in different batches in the same slot." [4](#0-3) 

After transaction A succeeds (advances the nonce), the batch loop immediately calls `account_loader.update_accounts_for_successful_tx`, writing the new (already-advanced) nonce account state into the shared `AccountLoader.loaded_accounts` map before moving on to transaction B. [5](#0-4) 

When transaction B is then validated, `load_transaction_account` for the nonce address returns this already-advanced state (via `do_load`, which checks `self.loaded_accounts` first). [6](#0-5) 

`verify_nonce_account` compares the account's stored `durable_nonce` against B's stale `recent_blockhash`; since A's execution already advanced it, they no longer match, so `verify_nonce_account` returns `None` and B fails with `TransactionError::BlockhashNotFound` before it can reach the "already used" branch — matching exactly the `AlreadyUsed` test case that exists for this function. [7](#0-6) [8](#0-7) 

**Why the attack fails:** the premise that B's `load_transaction_account` would see stale (pre-advance) state is incorrect — the `AccountLoader` is explicitly a batch-scoped, sequentially-updated cache designed to obviate re-reading from accounts-db and to propagate mid-batch state changes exactly to prevent this double-spend, as documented in the type's own comment: "it effectively wraps an `impl TransactionProcessingCallback` type... but also returning up-to-date account states mid-batch." [9](#0-8) 

Additionally, account locking at the scheduler level prevents two transactions writing the same nonce account from being scheduled for truly parallel execution across threads; ordering within any single processed batch is sequential and preserved in the ledger, per the comment: "transactions must be executed in order, because transactions in the same batch may modify the same accounts." [10](#0-9) 

There is no path by which B observes A's pre-advance state; the design guarantees the opposite (post-advance visibility), which is precisely what prevents the double-spend the question hypothesizes.

    fn do_load(&self, account_key: &Pubkey) -> (Option<(AccountSharedData, Slot)>, bool) {
        if let Some((account, slot)) = self.loaded_accounts.get(account_key) {
            // If lamports is 0, a previous transaction deallocated this account.
            // We return None instead of the account we found so it can be created fresh.
            // We *never* remove accounts, or else we would fetch stale state from accounts-db.
            let option_account = if account.lamports() == 0 {
                None
            } else {
                Some((account.clone(), *slot))
            };

            (option_account, false)
        } else if let Some((account, slot)) = self.callbacks.get_account_shared_data(account_key) {
            (Some((account, slot)), true)
        } else {
            (None, true)
        }
