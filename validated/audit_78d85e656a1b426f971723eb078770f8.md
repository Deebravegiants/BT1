Based on my research, I found a concrete structural analog to the reported EAS `SchemaResolverUpgradeable` issue inside `pallet-revive`'s builtin precompiles.

### Title
Native value sent to stateless builtin precompiles becomes permanently stranded - (File: `substrate/frame/revive/src/precompiles/builtin/*.rs`)

### Summary
`pallet-revive`'s builtin precompiles (`EcRecover`, `Sha256`, `Ripemd160`, `Identity`, `Modexp`, `Bn128Add/Mul/Pairing`, `Blake2F`, etc.) are pure, stateless functions with `HAS_CONTRACT_INFO = false` [1](#0-0) . Because the low-level EVM `CALL` opcode allows attaching a nonzero native `value` to any callee address — including these fixed precompile addresses — a caller (an ordinary contract or an EOA-originated transaction) can accidentally or mistakenly send value to addresses `0x1`–`0x9`. This exactly mirrors the disclosed EAS issue: a "payable" entry point exists where the protocol never intended value transfers to be usable/recoverable, so accidentally sent funds get stuck.

### Finding Description
The `CallType::Call` path in the PVM interpreter reads an arbitrary `value` and forwards it to `self.ext.call(...)` without restricting it based on whether the target is a stateless precompile [2](#0-1) . The EVM interpreter's `charge_call_gas` similarly only distinguishes precompiles for gas accounting, not for rejecting value [3](#0-2) .

In `exec.rs`, the value transfer into the callee account happens unconditionally for any non-delegate call before invoking the executable/precompile body [4](#0-3) . Only precompiles that opt into `has_contract_info()` get an account created via `mint_into`/`inc_consumers` [5](#0-4) ; stateless precompiles like `EcRecover` (`HAS_CONTRACT_INFO = false`) never get contract logic capable of forwarding, refunding, or otherwise using that balance — their `call()` implementations are pure functions (hashing, EC recovery, arithmetic) with zero notion of balance handling [6](#0-5) .

This is confirmed by the existing test `pure_precompile_works`, which deliberately sends `value = 100` to each of the fixed precompile addresses (`0x1`..`0x9`) and asserts the value lands on that address as EVM balance (`Pallet::<Test>::evm_balance(&precompile_addr) == U256::from(100)`) [7](#0-6) . None of these precompiles expose any function to move that balance elsewhere — there is no "withdraw," no owner, and no code path since the precompile logic is fixed and hardcoded.

### Impact Explanation
Just like ETH accidentally sent to a `SchemaResolverUpgradeable` resolver becomes permanently stuck because the resolver contract has no path to move it out, native currency value sent to a stateless precompile address in pallet-revive becomes permanently unrecoverable — there is no governance key, no withdrawal function, and no owner for these fixed, hardcoded precompiles. Any contract or dApp that constructs a low-level `call{value: x}(...)` to one of these addresses (e.g., due to a coding mistake, address confusion, or a malicious/buggy delegate contract passing an attacker-influenced target address along with value) permanently loses those funds.

### Likelihood Explanation
The precondition is narrow: an ordinary user/contract must issue a `CALL` with nonzero `value` to one of the fixed low addresses (`0x1`–`0x9`), which are conventionally reserved/well-known precompile slots in the EVM ecosystem. This can happen via:
- A misconfigured or buggy Solidity contract that computes a callee address incorrectly and also forwards `msg.value`.
- Tooling/wallet mistakes where a user manually crafts a raw `eth_call`/`eth_sendTransaction` with value to a low address (a known real-world EVM footgun — precompile addresses are commonly targeted by naive/incorrect address derivation bugs).

This does not require any privileged role and is fully reachable by an unprivileged user through the standard `call` opcode, matching the "reachable attacker-controlled entry path" requirement. The likelihood of *accidental* triggering is realistic (this is a known class of mistake in the Ethereum ecosystem), though it typically results in self-inflicted loss rather than attacker profit — consistent with how the original EAS report was scored (protocol design flaw enabling stuck funds, not a direct fund-theft exploit).

### Recommendation
Reject non-zero native `value` transfers to stateless (non-`has_contract_info`) precompiles, mirroring the `notPayable` modifier fix applied to `SchemaResolverUpgradeable`. Concretely:
- In `substrate/frame/revive/src/exec.rs`, before performing `transfer_from_origin` for a precompile target, check `!precompile.has_contract_info() && !value.is_zero()` and return an error (e.g., a new `Error::<T>::PrecompileValueNotSupported`) instead of allowing the transfer.
- Alternatively, enforce this check earlier in both the PVM (`vm/pvm.rs::call`) and EVM (`vm/evm/instructions/contract/call_helpers.rs::charge_call_gas`) call dispatch paths so the transaction reverts cleanly rather than silently stranding value.

### Proof of Concept
The existing test `pure_precompile_works` in `substrate/frame/revive/src/tests/pvm.rs` (lines 4690-4782) already demonstrates the mechanics: it calls each fixed precompile address (`0x1` through `0x9`) with `value = 100` and asserts the value persists as that address's EVM balance with no mechanism to move it. Running this scenario against a live/production `pallet-revive` deployment (e.g., a contract executing `address(0x1).call{value: 1 ether}("")`) would strand the ether permanently, since `EcRecover`/`Sha256`/etc. have no logic referencing `Ext::transfer` or any balance-moving primitive.

**Note on confidence**: I was unable to fully trace the `evm_balance`/dust-accounting implementation in `substrate/frame/revive/src/lib.rs` within the available iterations (grep found matches but I could not read the surrounding logic before running out of tool calls). This means I cannot 100% confirm whether some background/administrative sweep or dust-collection mechanism exists that could recover such stranded balances; the test evidence above shows the balance is retained at the precompile address immediately after the call, but long-term recoverability via runtime governance was not verified.

	interpreter: &mut Interpreter<'a, E>,
	callee: H160,
	scheme: CallScheme,
	input_len: usize,
	value: U256,
) -> ControlFlow<Halt, ()> {
	let precompile = <AllPrecompiles<E::T>>::get::<E>(&callee.as_fixed_bytes());

	match precompile {
		Some(precompile) => {
			// Base cost depending on contract info
			interpreter.ext.frame_meter_mut().charge_or_halt(
				if precompile.has_contract_info() {
					RuntimeCosts::PrecompileWithInfoBase
				} else {
					RuntimeCosts::PrecompileBase
				},
			)?;

			// Cost for decoding input
			interpreter
				.ext
				.frame_meter_mut()
				.charge_or_halt(RuntimeCosts::PrecompileDecode(input_len as u32))?;
		},
		None => {
			// Regular CALL / DELEGATECALL base cost / CALLCODE not supported
			interpreter.ext.charge_or_halt(if scheme.is_delegate_call() {
				RuntimeCosts::DelegateCallBase
			} else {
				RuntimeCosts::CallBase
			})?;

			interpreter
				.ext
				.frame_meter_mut()
				.charge_or_halt(RuntimeCosts::CopyFromContract(input_len as u32))?;
		},
	};
	if !value.is_zero() {
		interpreter
			.ext
			.frame_meter_mut()
			.charge_or_halt(RuntimeCosts::CallTransferSurcharge {
				dust_transfer: Pallet::<E::T>::has_dust(value),
			})?;
	}

impl<T: Config> PrimitivePrecompile for Sha256<T> {
	type T = T;
	const MATCHER: BuiltinAddressMatcher = BuiltinAddressMatcher::Fixed(NonZero::new(0x2).unwrap());
	const HAS_CONTRACT_INFO: bool = false;

	fn call(
		_address: &[u8; 20],
		input: Vec<u8>,
		env: &mut impl Ext<T = Self::T>,
	) -> Result<Vec<u8>, Error> {
		env.frame_meter_mut()
			.charge_weight_token(RuntimeCosts::HashSha256(input.len() as _))?;
		let data = sp_io::hashing::sha2_256(&input).to_vec();
		Ok(data)
	}
}
