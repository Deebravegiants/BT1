Webhook `shop` domain is not covered by HMAC verification, allowing tenant-identity spoofing in `ShopifyAPI::Webhooks::Registry.process` - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` documents itself as verifying "the request did indeed come from Shopify," and hands the app's handler a `WebhookMetadata` struct whose `shop` field is meant to identify the tenant the webhook belongs to. However, the HMAC signature computed by `Utils::HmacValidator` only covers the raw request body — the `shop-domain` header is never part of the signed material. Any party able to produce a validly-signed webhook body/HMAC pair for one tenant can freely substitute the `shop-domain` header value to make the library attribute that webhook to a *different* tenant, breaking the equality that should hold: `hmac-verified(body) == hmac-verified(shop)`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from an unauthenticated header with no cryptographic binding: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature strictly from `to_signable_string` (i.e., the body) and compares it to the `hmac` header — it never incorporates `shop`: [3](#0-2) 

`Registry.process` calls `HmacValidator.validate(request)` and, once it passes, unconditionally trusts `request.shop` as the tenant identity forwarded to the app's handler: [4](#0-3) 

The `WebhookMetadata` struct passed to every app-defined handler carries this unauthenticated `shop` field as if it were verified: [5](#0-4) 

The library's own documentation states that `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify," with no caveat that `shop` is excluded from that verification, and lists `shop` in `WebhookMetadata` as simply "The shop domain of the webhook" without qualification: [6](#0-5) [7](#0-6) 

Because the `api_secret_key` is a single per-app secret shared across every merchant/tenant that installs the app (not a per-shop key), any merchant who has genuinely installed the app receives real, correctly-signed webhooks for their own shop. Since the HMAC never covers the `shop-domain` header, that merchant (an "unprivileged internet user" from the perspective of any *other* tenant) can capture one of their own legitimate webhook deliveries and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header changed to point at a victim shop. `HmacValidator.validate` still returns `true` (the body/HMAC pair is unmodified and correct), and `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain.

### Impact Explanation
If a host application (as the documented, intended usage pattern shows) uses `data.shop` from `WebhookMetadata` to select which tenant's records to create/update/delete (a normal and expected usage, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)` as shown in the gem's own webhook doc example), an attacker with only their own legitimate app installation can inject or misattribute webhook-derived data into a target shop's context — a cross-tenant data integrity/confusion issue. This satisfies the "cross-tenant access" Critical-impact category, since the boundary broken is precisely the per-shop tenant boundary the library is supposed to establish via HMAC-verified `Registry.process`.

### Likelihood Explanation
Likelihood is high for any app that follows the gem's documented pattern of trusting `data.shop`: the attacker needs only their own valid app installation (any developer/merchant can install a public app) and the ability to send an HTTP POST to the app's webhook endpoint with a modified header — no access to `api_secret_key`, no privileged account, and no interception of TLS is required. The only "special" step is capturing one legitimate webhook delivery for their own shop and replaying it with a different domain header, which is a trivial HTTP replay.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the HMAC-signed material, or independently verify the `shop-domain` header against the shop the current session/handler is authorized to act on before trusting it. At minimum, `Utils::HmacValidator`/`Webhooks::Request` should not present `shop` in `WebhookMetadata` as verified data without covering it in `to_signable_string`, and the documentation should explicitly warn that `shop` is unauthenticated and must be independently checked by the host application against its own store of installed shops.

### Proof of Concept
1. App merchant "attacker.myshopify.com" installs the app and receives a legitimate webhook: body `{"id":123}"`, headers include `x-shopify-hmac-sha256: <valid hmac of body>` and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker resends the exact same POST to the app's webhook endpoint but changes only `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses this; `HmacValidator.validate` recomputes HMAC over the unchanged body and it matches (`OpenSSL.secure_compare` passes) since `shop` was never part of the signed string: [1](#0-0) 
4. `Registry.process` invokes the app handler with `WebhookMetadata#shop == "victim.myshopify.com"`, even though Shopify never sent this webhook for that shop: [4](#0-3)
