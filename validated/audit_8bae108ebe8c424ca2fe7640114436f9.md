### Title
Governance updating per-chain token precision after `send()` breaks pending in-flight message refunds/mints in `pallet-hyper-fungible-token` - ([File: modules/pallets/hyper-fungible-token/src/module.rs])

### Summary
`pallet-hyper-fungible-token`'s `send()` embeds a cross-chain amount computed from the **currently stored** `Precisions` entry, but the corresponding `on_accept`/`on_timeout` handlers re-read `Precisions` **again, at delivery/timeout time**, rather than using the value that was in effect when the tokens were escrowed/burned. If the `CreateOrigin` updates an asset's decimal precision (`update_token`/`register_token`) while a message is still in flight, the amount recovered on delivery or timeout diverges from the amount originally locked, producing either a permanent freeze of the escrowed/burned funds or an over/under-scaled refund — mirroring the reported `AdvancedDistributor.setVoteFactor()` class of bug where a mid-flight parameter change makes the burn/mint accounting inconsistent with what was actually escrowed.

### Finding Description
`send()` computes the outbound ERC20-scaled amount using the precision configured **at send time**: [1](#0-0) 

Tokens are burned (non-native) or escrowed (native) for the user's `params.amount` immediately, and `erc20_amount = convert_to_erc20(amount, erc_decimals, decimals)` (using the *current* `Precisions::<T>::get(asset_id, destination)`) is embedded into the dispatched `Message` and sent via ISMP.

Later, when the request is delivered on the destination (`on_accept`) or times out on the source (`on_timeout`), the pallet re-derives the local amount from the embedded `message.amount` by looking up `Precisions` **again, at that later point in time**: [2](#0-1) 

then attempts to release/mint that recomputed amount: [3](#0-2) 

`Precisions` is a governance-mutable storage map, updatable at any time via `update_token`/`register_token`: [4](#0-3) [5](#0-4) 

There is no snapshotting of the precision that was actually used to compute the outbound `erc20_amount` at `send()` time. `convert_to_balance` scales by `10^(erc_decimals.saturating_sub(local_decimals))`: [6](#0-5) 

If governance changes the recorded `erc_decimals` for `(asset_id, dest)` between `send()` and the eventual `on_timeout`/`on_accept`, the scaling divisor used to convert `message.amount` back to local balance changes, so the recovered amount no longer equals the amount that was actually burned/escrowed at `send()` time.

### Impact Explanation
- If the newly configured precision is **lower** relative to local decimals (or the `saturating_sub` collapses to 0), the divisor shrinks and the recomputed refund/mint amount becomes **larger** than what was actually escrowed/burned. For native assets this makes the `NativeCurrency::transfer`/`Assets::transfer` refund in `on_timeout` attempt to move more than the pallet's custody account actually holds, causing the transfer to fail with an insufficient-balance error — the exact "burn/transfer amount exceeds balance" revert pattern from the referenced report. Because `on_timeout` is invoked by an ordinary relayer submitting the ISMP timeout message, this revert **permanently blocks** that timeout from ever being processed, freezing the user's escrowed funds indefinitely (Denial of Service on refunds, matching the reported bug class). For non-native (mint/burn) assets, the same divergence instead causes the receiving side to **mint more tokens than were burned**, an unbacked-mint/insolvency condition.
- If the new precision is **higher**, the divisor grows, the recomputed amount **undershoots** the original, and users are refunded/credited less than what was actually locked — a partial, permanent loss of funds.

Either direction breaks the atomicity that cross-chain lock/burn-then-unlock/mint accounting depends on, exactly as the vote-factor example breaks the mint/burn symmetry in `AdvancedDistributor`.

### Likelihood Explanation
This requires the `CreateOrigin` to call `update_token`/`register_token` while at least one `send()` message for the affected `(asset_id, chain)` pair is still in flight (i.e., before delivery/timeout). This is a realistic operational scenario — decimals corrections, redeployments, or peer-chain reconfiguration are legitimate governance actions that pallet operators are expected to perform, and the pallet provides no mechanism to prevent this from breaking pending transfers, nor does it version/snapshot the precision used per-message. Given cross-chain challenge/finality periods can span many blocks, the window during which an update could race with in-flight messages is non-trivial.

### Recommendation
Embed the precision (or the fully-scaled, already-locked local amount) used at `send()` time into the outbound `Message`/request metadata so that `on_accept` and `on_timeout` recover the exact original amount regardless of later `Precisions` updates, instead of re-reading mutable storage. Alternatively, disallow updating an asset's precision for a chain while there are unresolved in-flight requests for that `(asset_id, chain)` pair, or maintain a per-request snapshot of the precision that was current when the request was dispatched.

### Proof of Concept
1. Register asset `A` (non-native) with `Precisions::<T>::insert(A, ChainD, 18)` via `register_token`.
2. User calls `send(SendParams { asset_id: A, destination: ChainD, amount: 100, timeout: T, ... })`. `100` local units of `A` are burned; `erc20_amount = convert_to_erc20(100, 18, local_decimals)` is embedded in the dispatched `Message` and sent as a `DispatchPost`. [7](#0-6) 
3. Before the request is delivered or times out, `CreateOrigin` calls `update_token` to change the precision for `(A, ChainD)` to `6` (e.g., correcting a misconfigured decimals value for a redeployed contract). [8](#0-7) 
4. The request times out (e.g., no relayer delivered it within `T`). A relayer submits the ISMP timeout extrinsic, invoking `on_timeout`, which now reads `Precisions::<T>::get(A, ChainD) == 6` instead of the original `18`, and recomputes the refund amount from the same raw `message.amount` using the wrong divisor — refunding an amount vastly different (larger, in this direction) from the `100` units originally burned. [9](#0-8) 
5. For the native-asset variant, this recomputed (inflated) refund exceeds what the pallet's custody account holds, so the transfer errors out and `on_timeout` reverts every time it is retried — permanently freezing the escrowed funds and blocking that message's timeout resolution, the same denial-of-service pattern as the reported `setVoteFactor()` issue. For the mint/burn variant, the mismatch instead mints more tokens than were burned.

			let chains: Vec<StateMachine> = registration.chains.keys().cloned().collect();
			for (chain, config) in registration.chains {
				// This pallet bridges substrate <-> EVM only; reject non-EVM peers.
				if !matches!(chain, StateMachine::Evm(_)) {
					return Err(Error::<T>::NonEvmPeerChain.into());

					config.decimals >= local_decimals,
					Error::<T>::ErcDecimalsBelowLocal

					registration.local_id.clone(),
					token_contract.clone(),
				);
				ContractToAsset::<T>::insert(
					chain,
					token_contract,
					registration.local_id.clone(),
				);
				Precisions::<T>::insert(registration.local_id.clone(), chain, config.decimals);

pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
