### Title
Webhook `Registry.process` trusts unauthenticated `shop`/`topic`/`webhook-id` headers that are not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the **raw body**, then dispatches to a handler using `shop`, `topic`, `webhook_id`, and `api_version` values that are pulled straight from HTTP headers and are never included in the signed material. The identity fields the handler relies on to attribute the payload to a tenant are therefore not bound to the cryptographic check that is supposed to authenticate the request.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string`. For webhooks, `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

All the other attributes exposed by `Request` — `shop`, `topic`, `webhook_id`, `api_version` — are read directly from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` validates only the HMAC (i.e., only the body) and then immediately trusts these unauthenticated header-derived fields to select the handler and to build the metadata handed to application code: [3](#0-2) 

The equality that is broken: **`shop` (and `topic`/`webhook_id`) used to authenticate/attribute the request ≠ `shop` (and `topic`/`webhook_id`) actually covered by the HMAC**. Any entity that can obtain one genuine signed body+HMAC pair (trivially available to any developer who installs the app on their own store and observes/replays a webhook delivery) can resubmit that exact body and HMAC header to the app's public webhook endpoint while swapping the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers to arbitrary values. `HmacValidator.validate` still returns `true` because it only checked the body, so `Registry.process` will call the handler registered for the attacker-chosen `topic` with `WebhookMetadata.shop` set to any value the attacker wants (e.g. a victim shop domain), even though that data never touched Shopify's servers under that shop's identity.

### Impact Explanation
This crosses the tenant boundary the HMAC check is meant to enforce: an app's webhook handler indexes/authorizes work by `shop`, trusting `Registry.process`'s claim that "this payload legitimately came from shop X" because "the HMAC passed." Since `shop` and `topic` are not part of the signed bytes, an attacker can make the app process (and potentially persist, sync, or act on) attacker-supplied body content under a victim shop's identity, or trigger a sensitive topic handler (e.g. `app/uninstalled`, `shop/redact`, `customers/data_request`) for a shop that never sent that event. This is a cross-tenant identity-binding break, matching the report's bug class of "a field acted on but not covered by the HMAC."

### Likelihood Explanation
Exploitation requires only: (1) capturing one legitimate raw-body+HMAC pair (attainable by any unprivileged actor who installs the target app on any store, including a free/dev store, and observes the resulting webhook POST — no `api_secret_key`, access token, or privileged account required), and (2) sending an HTTP POST with modified headers to the app's public webhook endpoint. Both steps are available to an ordinary internet user with no special credentials.

### Recommendation
Bind the identity/topic metadata to the same signature used to authenticate the body, e.g., include `shop`, `topic`, `webhook_id`, and `api_version` in the bytes that are HMAC-verified (or require the calling application to additionally verify the `shop` header against the shop that owns the currently active app installation/session before dispatching), and reject the request if these fields cannot be tied to the verified payload. At minimum, `Registry.process` should not select a handler or construct `WebhookMetadata` from header values until an authenticated shop/topic binding has been established.

### Proof of Concept
1. Install/register the target app on shop `attacker.myshopify.com` (any free store); trigger any webhook topic the app subscribes to. Capture the raw POST: body `B`, and header `x-shopify-hmac-sha256: H` (valid HMAC of `B` with the app's shared secret), as computed in `HmacValidator.validate_signature`: [4](#0-3) 
2. Resend the same body `B` and the same `x-shopify-hmac-sha256: H` header to the app's public webhook endpoint, but replace `x-shopify-shop-domain` with `victim-shop.myshopify.com` and (optionally) `x-shopify-topic` with a different registered topic.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only recomputes the HMAC over `B` (`to_signable_string` returns `@raw_body`): [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the attacker-controlled header values, even though the body `B` never originated from `victim-shop.myshopify.com`: [6](#0-5)

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
