## Title
Webhook `Registry.process` trusts the `shop` identity header, which is not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/registry.rb`)

### Summary
The equality that should hold is: `shop bound by HMAC signature == shop acted upon by the handler`. In `Registry.process`, the HMAC is verified only over the raw request body, while the `shop` value that identifies the tenant and is handed to the app's webhook handler comes from an HTTP header that is not part of the signed payload. An attacker who controls the request (i.e., anyone who can reach the app's webhook endpoint and knows/guesses a valid `hmac`/body pair, or replays a legitimately-signed body against a different `shop-domain` header) can make the handler act under an attacker-chosen tenant identity while HMAC validation still passes.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, entirely independent of the signed body: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)`, which internally calls `verifiable_query.to_signable_string` (i.e., only the body) and compares it against the `hmac` header using `OpenSSL.secure_compare`: [3](#0-2) 

After that check passes, the handler is invoked with `shop: request.shop` taken straight from the unauthenticated header, with no cross-check against anything the HMAC covers: [4](#0-3) 

Because the HMAC only binds the body bytes to the secret, and the `shop-domain` header sits outside that signed scope, the binding `HMAC-verified bytes == identity acted upon` does not hold: the `shop` field is acted on (passed to the handler as the tenant identity) but not covered by the HMAC.

### Impact Explanation
This falls under the "field acted on but not covered by the HMAC" bug class from the report analogy. If a body/HMAC pair for one shop's webhook is ever observed or replayed with a substituted `shop-domain` header (e.g., via webhook forwarding infrastructure, logging/replay tooling, or a misconfigured/multi-tenant proxy in front of the app that does not itself bind the header to the signature), `Registry.process` will accept it as valid and dispatch it to the handler tagged with the attacker-chosen shop. Depending on how the host application uses `WebhookMetadata#shop` (e.g., to look up or scope data, credentials, or side effects), this can enable cross-tenant action under the wrong shop identity — matching the High-impact category "cross-tenant access" analog to the interest-rate/HMAC-binding class in the source report.

### Likelihood Explanation
Exploitability depends on an attacker being able to influence the `shop-domain` header independently of the signed body while still supplying a body/HMAC pair that passes validation. This is a real gap in the gem's own binding logic (the library computes/verifies the HMAC over the body only, and never asserts that the header-derived `shop` corresponds to anything cryptographically bound), even though the likelihood of surfacing it depends on how the host application terminates and forwards HTTP requests to this code. This is a genuine root-cause gap in the library, not solely a host-application misuse of a documented API, since `Webhooks::Request`/`Registry.process` never validate `shop` at all.

### Recommendation
Include the `shop` domain (and ideally `topic`, `api_version`, `webhook_id`) in the HMAC-signable payload, or otherwise verify that the header-provided shop matches a value the app already trusts (e.g., a shop the app has an active session/access token for) before dispatching to the handler. At minimum, `Webhooks::Request#to_signable_string` should not be limited to the raw body alone when other unauthenticated header fields are subsequently trusted for tenant-identity decisions.

### Proof of Concept
Conceptual PoC (illustrating the binding gap, based on the gem's own test fixtures):
```ruby
raw_body = "{}"
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# Valid signature for shop-a is computed purely from raw_body, independent of shop header.
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "shop-a.myshopify.com", # legitimate shop
}
req_a = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(req_a) # passes HMAC check, handler runs with shop-a

# Same raw_body/hmac pair, but shop-domain header swapped to a different tenant:
headers_b = headers.merge("x-shopify-shop-domain" => "shop-b.myshopify.com")
req_b = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers_b)
ShopifyAPI::Webhooks::Registry.process(req_b)
# HmacValidator.validate(req_b) still returns true, because it only checks raw_body/hmac.
# handler.handle(... shop: "shop-b.myshopify.com" ...) is invoked despite the shop header
# never having been covered by the signature.
```
This demonstrates that `Registry.process` cannot distinguish a legitimate webhook for `shop-a` from the same signed body relabeled for `shop-b`, because `shop` is never part of the HMAC-covered bytes.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
