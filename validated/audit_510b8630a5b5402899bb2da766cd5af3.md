### Title
Unbounded router approval + unvalidated calldata forwarding lets any swap drain another swap's stranded input-token dust from the shared `LifiExternalAction`/`ExternalActionSwap` contract - (File: contracts/external-actions/swaps/LifiExternalAction.sol, contracts/external-actions/swaps/ExternalActionSwap.sol)

### Summary
`LifiExternalAction`/`ExternalActionSwap` is a single shared contract instance through which every user's swap passes. Each call grants the LI.FI router an unlimited (`type(uint256).max`) standing approval on the input token and then forwards attacker/user-controlled `externalActionMetadata` to the router verbatim, with no on-chain check that the router only pulls the `inputAmount` that was moved in for that specific call. If any dust or unconsumed input token is ever left behind in the contract from a prior swap (a partial-fill route, rounding, or a route that under-consumes the approved amount), that balance is not tracked by any UTXO and is not swept back to its owner — it simply sits in the shared contract, fully approved to the router. A later caller can supply `externalActionMetadata` that instructs the router to pull more than their own `inputAmount` (up to the full unlimited allowance and current balance), sweeping out value that belongs to a different user's transaction and crediting it to their own `swappedAmount`/output UTXO.

### Finding Description
- `Hinkal._externalTransact` transfers exactly `uint256(-deltaAmountChanges[i])` of the input token into the external action contract before calling `runAction` [5](#0-4) . This amount is derived from the caller's own committed `amountChanges`/nullifiers, i.e. it is exactly this transaction's contribution.
- `ExternalActionSwap.swap` takes `inputAmount` from `deltaAmounts[0]` and calls `callRouter(inputToken, inputAmount, outputToken, circomData.externalActionData.externalActionMetadata)`, where `externalActionMetadata` is arbitrary, attacker-chosen calldata that is only bound to `calldataHash` (i.e., it is faithfully what the prover claimed it would be, but its *effect* on the router is never constrained to `inputAmount`) [6](#0-5) .
- `LifiExternalAction.callRouter` calls `approveUnlimited(inputToken, router)` (which only refreshes allowance when it drops below `type(uint256).max/2`, and otherwise leaves the existing unlimited approval in place) and then does `router.call(externalActionMetadata)` — the router executes with whatever asset-pulling logic is encoded in that calldata, not confined to `inputAmount` [3](#0-2) .
- After the call, `swappedAmount` is computed purely as the delta of the **output** token balance; there is no check that the **input** token balance decreased by exactly `inputAmount`, and any leftover input token is neither returned to the depositor nor represented by any UTXO/commitment — it is simply stranded in the shared contract [7](#0-6) .

This mirrors the UnistreetLaunchpad root cause: a shared custodial contract forwards attacker-controlled calldata verbatim to a downstream contract "as itself" under a standing, unscoped authorization (there: `setApprovalForAll` over all custodied NFTs; here: unlimited ERC20 `approve` over the shared token balance), and the only implicit "authorization" check (the factory's own custody / the swap's `inputAmount`) is exactly what the unvalidated calldata can be crafted to bypass. Because the contract balance and the router's authorization scope are not 1:1 tied to the specific `inputAmount` committed for that transaction, whatever balance from prior/other transactions is sitting in the shared contract is fair game for any single caller's `externalActionMetadata`.

This breaks the implicit balance equation Hinkal relies on for external actions: value custodied by the shared external-action contract that originated from Hinkal's own transfers, but that is not the current caller's committed `inputAmount`, can be pulled out and credited to an unrelated caller's output UTXO — i.e. shielded value moved by Hinkal but not accounted for in the balance equation of the transaction that owns it.

### Impact Explanation
This is theft of other users'/protocol-custodied in-flight funds (temporary/permanent freezing turned into outright theft): dust or stranded input tokens belonging to one shielded transaction can be swept by a completely unrelated, unprivileged caller simply by choosing router calldata that draws on the unlimited approval. Given the shared, persistent nature of the contract and its approval, any stuck balance (which is plausible with aggregator/multi-route swaps that don't fully consume the approved amount) is a standing bounty available to attackers, without requiring any admin/relay/owner privilege — satisfying the Critical/High bar of "temporary/permanent freezing of user funds" and "theft ... of shielded funds" / "executing calls or moving assets a wallet owner or prover never authorised" (the calldata is authorized for the caller's *own* `inputAmount`, not for other users' residual balances).

### Likelihood Explanation
Likelihood depends on stranded balance actually accumulating in the shared `ExternalActionSwap` contract (e.g., via LI.FI multi-route/partial-fill swaps, or rounding), which is plausible given `swap()` never verifies input-token balance depletion or sweeps residue. Once any dust exists, exploitation only requires one unprivileged call with crafted `externalActionMetadata` — no signer/relay/owner key needed, since the attacker only needs their own valid Hinkal proof for their own nullifiers, with a manipulated router payload.

### Recommendation
- After `callRouter`, assert that the input-token balance of the external action contract decreased by exactly `inputAmount` (or is zero afterward for the case of "exact input" swaps), reverting otherwise.
- Never grant unlimited/standing approvals from a shared, multi-tenant custodial contract to an externally-controlled router; instead approve exactly `inputAmount` immediately before the call and reset to zero after, so the router can never move more than what belongs to the current transaction.
- Sweep any unconsumed input-token residue back into a UTXO owned by the depositing user (or revert the whole transaction) rather than leaving it in the shared contract.

### Proof of Concept
1. User A executes a Hinkal swap through `LifiExternalAction`: `inputAmount` of `USDC` is transferred into the contract and approved unlimited to the router; the crafted `externalActionMetadata` (LI.FI route) only partially fills, consuming less than `inputAmount` of `USDC` and leaving e.g. 50 USDC stuck in the contract (no revert, since `swap()` only checks the output-token delta).
2. Attacker B, using their own valid Hinkal proof for their own (unrelated, possibly dust-sized) nullifiers, calls Hinkal's external-action swap through the same `LifiExternalAction` contract with `inputToken = USDC`, `inputAmount = 1` and a hand-crafted `externalActionMetadata` payload that instructs the router to pull `51` USDC (the attacker's own 1 + User A's stranded 50) using the pre-existing unlimited approval, and swap it all to `outputToken`.
3. `swappedAmount` reflects the full proceeds of 51 USDC worth of output token; attacker B's UTXO is minted for `amountToSendToHinkal` derived from that inflated `swappedAmount`, while User A's 50 USDC is permanently gone with no corresponding UTXO ever created for it.

    function swap(
        CircomData calldata circomData,
        int256[] calldata deltaAmounts
    ) internal returns (UTXO[] memory utxoSet) {
        address inputToken = circomData.erc20TokenAddresses[0];
        uint256 inputAmount = uint256(-deltaAmounts[0]);

        if (inputToken == circomData.feeStructure.feeToken) {
            inputAmount -= circomData.feeStructure.flatFee;
        }

        address outputToken = circomData.erc20TokenAddresses[1];

        require(
            circomData.slippageValues[1] != 0,
            "swap output slippage floor not set"
        );

        require(
            block.timestamp <= circomData.timeStamp + SWAP_DEADLINE_WINDOW,
            "swap expired"
        );

        uint256 swappedAmount = callRouter(
            inputToken,
            inputAmount,
            outputToken,
            circomData.externalActionData.externalActionMetadata
        );

        uint256 relayFee = circomData.feeStructure.flatFee;

        uint256 hinkalFee = hinkalHelper.calculateRelayFee(
            swappedAmount,
            0,
            circomData.feeStructure.variableRate
        );

        if (circomData.feeStructure.feeToken == outputToken) {
            sendToRelay(circomData.relay, relayFee + hinkalFee, outputToken);
        } else {
            sendToRelay(
                circomData.relay,
                relayFee,
                circomData.feeStructure.feeToken
            );
            sendToRelay(circomData.relay, hinkalFee, outputToken);
        }

        uint256 totalFee = hinkalFee +
            (outputToken == circomData.feeStructure.feeToken ? relayFee : 0);
        uint256 amountToSendToHinkal = swappedAmount - totalFee;

        transferERC20TokenOrETH(outputToken, msg.sender, amountToSendToHinkal);

        utxoSet = new UTXO[](1);
        utxoSet[0] = UTXO({
            amount: amountToSendToHinkal,
            erc20Address: outputToken,
            stealthAddressStructure: circomData.stealthAddressStructure,
            timeStamp: block.timestamp
        });
    }
