### Title
Webhook `shop`, `topic`, `webhook-id`, and `api-version` fields are trusted from unauthenticated HTTP headers, not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop`, `topic`, `api_version`, and `webhook_id` values used by the app's webhook handler entirely from raw HTTP headers, while the HMAC signature validated by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body. This breaks the intended identity binding `verified_bytes == acted_upon_bytes`: the gem proves the body is unmodified and came from a Shopify-secret holder, but it does nothing to prove that the accompanying `shop-domain` header actually belongs to the shop that generated that body.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` computes the HMAC exclusively over `to_signable_string`, i.e., the JSON body: [2](#0-1) 

Meanwhile, `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all pulled straight out of attacker-controllable HTTP headers with no cryptographic binding to the body or to each other: [3](#0-2) 

`Registry.process` validates only the HMAC of the body, then passes the header-derived `request.shop` (and `topic`) straight to the app's handler as the authoritative tenant identifier: [4](#0-3) 

The documented handler contract explicitly tells integrators to trust `data.shop` as "The shop domain of the webhook" without any further verification step, and the gem provides no API to detect a mismatch between the shop that signed the body and the shop header value: [5](#0-4) 

The equality that should hold is: `shop_header == shop_that_the_HMAC-signed_body_originated_from`. Because the HMAC only certifies bytes-of-body, not bytes-of-headers, this equality is never checked by the library — an attacker who possesses one *valid* (body, hmac) pair signed with the app's shared `api_secret_key` (e.g., from any webhook legitimately delivered to their own installed shop) can resend that exact body/hmac pair while substituting an arbitrary victim shop's domain in the `x-shopify-shop-domain` header. `Registry.process` will accept it (HMAC checks out because the body is untouched) and route it to the handler tagged as coming from the victim shop, achieving cross-tenant webhook injection/spoofing.

### Impact Explanation
This is a cross-tenant identity-binding failure: an unprivileged user who has legitimate access to their own shop's webhook stream (and thus a valid signed body for their own tenant) can forge webhook events attributed to a shop they do not control, by replaying the signed body under a different `shop-domain` header. Depending on how a host app keys its data/state off `data.shop` (which the docs instruct it to do), this enables cross-tenant data confusion/injection — matching the "Critical: cross-tenant access" impact bucket, since the tenant boundary (`shop`) is not actually authenticated by the primitive the gem exposes as verification.

### Likelihood Explanation
Exploitation requires the attacker to already possess at least one genuine (body, hmac) pair — trivially obtainable by any developer/attacker who has installed the app on their own shop and captured one of their own legitimate webhook deliveries (no `api_secret_key` or access-token theft needed, since the body/hmac pair is delivered to them directly by Shopify for their own shop). They then only need to be able to POST to the app's public webhook endpoint with a modified `shop-domain` header — a normal unauthenticated HTTP request. This is a realistic, low-effort scenario for any app that keys per-tenant behavior off `WebhookMetadata#shop` as instructed by the gem's own documentation.

### Recommendation
Bind the `shop` (and ideally `topic`, `webhook_id`, `api_version`) to the signed payload rather than trusting bare headers:
- Prefer validating against the app's own known/expected shop list per registration when available, and/or
- Extend the signable string used for verification to include the identity-critical headers (as Shopify's newer webhook standards effectively require via header-plus-body binding), so that any headers acted upon by the handler are part of the HMAC-verified content.
- At minimum, document loudly and provide a helper for host apps to cross-check `data.shop` against an install record before trusting it, since currently the gem's contract implies the value is already verified.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook delivery for, e.g., `orders/create`, with headers:
   - `x-shopify-shop-domain: attacker.myshopify.com`
   - `x-shopify-hmac-sha256: <valid-hmac-for-body>`
   - body: `{"id":123,...}`
2. Attacker replays the exact same raw body and HMAC header to the app's public webhook endpoint, but changes:
   - `x-shopify-shop-domain: victim.myshopify.com`
3. Server code:
   ```ruby
   ShopifyAPI::Webhooks::Registry.process(
     ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
   )
   ```
4. `HmacValidator.validate` succeeds (body/hmac untouched): [6](#0-5) 

5. `Registry.process` invokes the handler with `WebhookMetadata#shop == "victim.myshopify.com"`, even though the signed body never originated from that shop: [7](#0-6) 

The app now processes attacker-controlled data under the victim tenant's identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
