Based on my investigation, I found a concrete analog: `verify_state_proof` returns a `BTreeMap<Vec<u8>, Option<Vec<u8>>>`, which is inherently ordered by raw key bytes, not by the order the requesting application specified them in `GetRequest.keys`. The response handler then converts this map directly into the `StorageValue` array delivered to the destination application without re-ordering it to match the original request's key order.

### Title
Get-response values delivered out of request order due to BTreeMap re-sorting of keys - (File: modules/ismp/core/src/handlers/response.rs)

### Summary
The GHSA-hvv8-5v86-r45x report describes a case where the matrix-js-sdk processes application-level event payloads whose internal structure doesn't match consumer expectations, resulting in the SDK silently excluding or corrupting data returned to the consumer while otherwise appearing to function normally. The reachable analog in this codebase is the GET-response path: `handle` in `modules/ismp/core/src/handlers/response.rs` builds the values delivered to destination modules from a `BTreeMap`, which reorders entries by lexicographic key value rather than preserving the caller-specified `keys` order in the `GetRequest`.

### Finding Description
`GetRequest.keys` is `Vec<Vec<u8>>`, an explicitly ordered list of storage keys chosen by the dispatching application [1](#0-0) . When a relayer submits a `ResponseMessage`, the handler calls:

```rust
let values = state_machine
    .verify_state_proof(host, keys, state.state_root, &proof)?
    .into_iter()
    .map(|(key, value)| StorageValue { key, value })
    .collect();
``` [2](#0-1) 

`verify_state_proof` is documented and typed to return `BTreeMap<Vec<u8>, Option<Vec<u8>>>` [3](#0-2) . A `BTreeMap<Vec<u8>, _>` iterates in ascending byte-lexicographic order of its keys — not in the order the caller inserted them and not in the order they appear in `request.keys`. Any relayer submitting a syntactically valid `GetResponse` proof for a `GetRequest` whose `keys` are not already lexicographically sorted (a very common, entirely legitimate case, e.g., account address key before/after a storage-slot key) will cause the resulting `values: Vec<StorageValue>` delivered to the destination module's `on_response`/`onGetResponse` callback to be silently permuted relative to the `keys` the application dispatched.

This is a genuine input-validation/logic gap (CWE-20 analog): the handler does not validate or restore the response ordering to match the request before dispatching to the untrusted-input-consuming application layer. Consuming applications that assume `values[i]` corresponds to `keys[i]` (a natural and encouraged assumption per the documentation, e.g. `GetResponse.values | StorageValue[] | Retrieved storage values in same order as requested keys` [4](#0-3) ) will silently misinterpret which value corresponds to which key, corrupting the data delivered to the app without any error, exactly mirroring the "SDK can appear to be operating normally but be excluding or corrupting runtime data" theme of the original advisory.

### Impact Explanation
Any application built on top of Hyperbridge's GET-request flow that relies on positional correspondence between `keys` and `values` (as the documentation explicitly promises) can silently receive corrupted or misattributed data for any multi-key `GetRequest` whose keys aren't already sorted. Depending on the consuming application's logic (e.g., balance reads, price oracle reads, cross-chain state checks feeding a bridge/intent-settlement decision), this can result in incorrect on-chain decisions being made from silently mismatched data — a data-integrity/availability issue reachable by any relayer simply delivering a legitimate response, without needing to forge anything.

### Likelihood Explanation
High likelihood of triggering unintentionally: this occurs on every valid `GetResponse` for a `GetRequest` with more than one key that isn't already sorted in ascending byte order — no malicious intent or malformed proof is required, just normal usage with multiple storage keys in a natural, non-sorted order (e.g., an account key followed by an unrelated slot key).

### Recommendation
Preserve the original `request.keys` order when constructing `StorageValue`s: instead of `.into_iter()` over the returned map, iterate over `request.keys` and look up each key in the returned map (`map.get(&key)`), building the `values` vector in the same order as `request.keys`. Apply the analogous fix everywhere a `BTreeMap`/`HashMap` result from `verify_state_proof` is converted into an ordered `Vec<StorageValue>` (state-coprocessor's `dispatch_get_response`-adjacent paths should be checked as well).

### Proof of Concept
1. Dispatch a `GetRequest` with `keys = [key_B, key_A]` where `key_A < key_B` lexicographically (e.g. `key_B = 0xff...`, `key_A = 0x00...`).
2. A relayer submits a valid `ResponseMessage`/proof for both keys; `verify_state_proof` returns a `BTreeMap` that iterates as `{key_A: val_A, key_B: val_B}`.
3. `handle` in `modules/ismp/core/src/handlers/response.rs` produces `values = [StorageValue{key_A, val_A}, StorageValue{key_B, val_B}]` — but the request's `keys` order was `[key_B, key_A]`.
4. The destination module's `on_response`/`onGetResponse`, if it assumes `values[0]` corresponds to `keys[0]` (as documented), receives `val_A` where it expected `val_B`, and vice versa — a silent data-corruption case delivered to the app layer for a perfectly legitimate, honestly-relayed message.
