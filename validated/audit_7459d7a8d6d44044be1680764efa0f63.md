### Title
Raw-balance sweep in Tron `IntentGatewayV2.placeOrder` predispatch path lets stuck/mismatched token dust be swept into an unrelated order's escrow - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The bug class in the MigratorZap report is: a function performs a withdraw/transfer whose actual output can diverge from what the caller declared, and instead of measuring the *delta* the contract owns before/after that external interaction, it reads the contract's *raw* balance. Any token left over from a prior mis-executed/partial interaction is silently folded into whatever the next caller does, letting funds that don't belong to anyone be claimed or misattributed by an unrelated, later transaction.

The Tron variant of `IntentGatewayV2.placeOrder`'s predispatch-sweep step reproduces exactly this pattern, in contrast to the canonical EVM contract (`evm/src/apps/IntentGatewayV2.sol`), which snapshots balances before the predispatch call and computes a before/after delta.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder` (lines 389–450), after the untrusted `order.predispatch.call` is executed via the shared, persistent `CallDispatcher` singleton, the amount to sweep back into escrow is computed from the dispatcher's **raw current balance**, not a before/after delta: [1](#0-0) 

```
ICallDispatcher(dispatcher).dispatch(order.predispatch.call);

for (uint256 i; i < inputsLen;) {
    address token = address(uint160(uint256(order.inputs[i].token)));
    uint256 requiredAmount = order.inputs[i].amount;
    uint256 balance;
    ...
    balance = IERC20(token).balanceOf(dispatcher);
    if (balance < requiredAmount) revert InvalidInput();
    transferCalls[i] = Call({ to: token, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance) });
    ...
    uint256 dust = balance - requiredAmount;
    if (dust > 0) emit DustCollected(token, dust);
    _orders[commitment][token] += reducedInputs[i].amount;
```

Contrast this with the fixed, delta-based version in the canonical EVM app, which explicitly snapshots `balancesBefore` prior to the predispatch call and later computes `received = IERC20(token).balanceOf(address(this)) - balancesBefore[i]`: [2](#0-1) 

The `CallDispatcher` referenced by `_params.dispatcher` is a shared, long-lived contract used by every `placeOrder` call from every user (`evm/src/utils/CallDispatcher.sol`), not a fresh per-call proxy: [3](#0-2) 

Because the Tron path reads `balanceOf(dispatcher)` directly rather than a delta, any token balance that is stranded on the `CallDispatcher` — e.g. left behind because a prior order's predispatch call under- or over-delivered relative to what that order declared (a token/amount "mismatch" between what the predispatch call actually produced and what `order.inputs[i]` claims), a fee-on-transfer/rebasing quirk, or any other operator/user mistake that leaves tokens sitting on the dispatcher without being fully swept back — is transferred wholesale into the *next* unrelated caller's `placeOrder` invocation. That caller's escrow entry is only credited with their own declared `reducedInputs[i].amount`; the surplus is only emitted as a `DustCollected` event and otherwise disappears into the Gateway's own balance, uncredited to any commitment. This mirrors the MigratorZap flaw precisely: a caller-controlled/derived amount is checked against the *contract's own current balance* rather than an isolated, attributable delta, so value belonging to no specific order becomes fungible with whatever the very next order happens to do, and it is not clawed back to the party who actually owns it.

### Impact Explanation
Funds that should be attributable to a specific user's stuck/mismatched predispatch outcome are not tracked per-order; they are swept as generic "dust" that ends up on the Gateway's own balance rather than being recoverable by (or returned to) the party whose transaction actually produced them. This is a fund-tracking/accounting break directly analogous to the reported class (medium severity, low likelihood, high value at risk): it requires an unusual precondition (a stuck/mismatched predispatch outcome or non-standard token behavior) but when it occurs, the resulting balance is absorbed into the wrong place instead of being safely recoverable, and any surplus above declared escrow amounts is not owned by any commitment, so it can only be recovered by governance's `SweepDust` action rather than by the affected user, and is fungible with the next placeOrder's sweep in the interim.

### Likelihood Explanation
Low likelihood: exploitation requires a specific mis-execution or mismatch during the predispatch phase (e.g., predispatch swap output diverging from what `order.inputs` declares, non-standard token transfer semantics, or an operational mistake) that leaves a token balance stranded on the shared `CallDispatcher` before the next `placeOrder` call sweeps it. This matches the report's "operational mistake"-triggered class rather than a directly, cheaply repeatable exploit.

### Recommendation
Bring the Tron `IntentGatewayV2.placeOrder` predispatch-sweep logic in line with the canonical `evm/src/apps/IntentGatewayV2.sol` implementation: snapshot each input token's `balanceOf(dispatcher)` (and native balance) *before* invoking `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)`, and compute the swept/credited amount from the *delta* (`balanceAfter - balanceBefore`) rather than the raw post-call balance. This ensures each order's escrow credit and dust accounting reflect only what that specific transaction actually produced, preventing pre-existing/stranded dispatcher balances from one order leaking into another's accounting.

### Proof of Concept
Not independently verified end-to-end in this pass — I was unable to confirm within available tool calls whether a concrete token/predispatch call combination in the current codebase can reliably leave a nonzero balance stranded on `CallDispatcher` between two `placeOrder` transactions (e.g., via a predispatch call that legitimately under-delivers relative to `order.inputs`, or a token that behaves non-standardly on `transfer`). The structural flaw — raw `balanceOf(dispatcher)` read instead of a before/after delta on a shared, persistent dispatcher contract — is confirmed by direct comparison of `evm/tron/contracts/apps/IntentGatewayV2.sol` (lines 413–450) against the delta-based `evm/src/apps/IntentGatewayV2.sol` (lines 260–299). A background engineering session with test-execution access would be needed to construct a concrete Foundry PoC demonstrating cross-order dust leakage.

contract CallDispatcher is ICallDispatcher {
    /**
     * @dev error thrown when the target is not a contract.
     */
    error NotContract(address target);

    /**
     * @dev error thrown when a call fails.
     */
    error CallFailed(address target, bytes result);

    /**
     * @dev Receive function to accept ETH transfers
     */
    receive() external payable {}

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
