### Title
Webhook `shop` identity is taken from an unauthenticated HTTP header, not from the HMAC-covered payload - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the `X-Shopify-Shop-Domain` HTTP header, while the HMAC signature validated by `Utils::HmacValidator` only covers the raw request body. This breaks the binding: `shop used by handler == shop authenticated by HMAC`, analogous to the H-7 pattern of "a field acted on but not covered by the signature check."

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` with: [1](#0-0) 

`to_signable_string` (the only material verified against the HMAC) returns solely `@raw_body`: [2](#0-1) 

But `shop` (and `topic`, `webhook_id`, `api_version`) are read directly from HTTP headers that are never mixed into the signable string: [3](#0-2) [4](#0-3) 

`Registry.process` validates the HMAC only against the body, then passes `request.shop` (the unauthenticated header value) straight into the metadata handed to the app's handler: [5](#0-4) 

`WebhookMetadata.shop` is a plain, trusted field consumed by any handler implementing `WebhookHandler#handle`: [6](#0-5) 

The equality that should hold is: `shop authenticated by HMAC(payload, api_secret_key) == shop used to select tenant/session for the handler`. Because the HMAC only signs `raw_body`, an attacker who can produce a body with a *valid HMAC for their own shop* (e.g. by triggering a genuine webhook delivery from a shop they control, or via any body/shop combination the signature scheme does not bind together) can present a `shop-domain` header value belonging to a different, victim shop. `HmacValidator.validate` will still return `true` because it never inspects headers: [7](#0-6) 

This is the direct analog of H-7's root cause: a value used downstream for a security-relevant decision (`totalBPTSupply` there, tenant `shop` here) is not the value that was actually integrity-checked (`virtualSupply` there, HMAC-signed body here).

### Impact Explanation
Any host application that trusts `WebhookMetadata#shop` to select which merchant's session/access token/data record to update — the exact intended use case for webhook processing in a multi-tenant app — can be made to attribute a cryptographically-valid webhook to the wrong shop. This crosses the tenant boundary: it is a cross-tenant confusion where an HMAC-valid webhook (signed with the app's shared `api_secret_key`, valid for any installed shop) can be replayed/labeled with an arbitrary `shop-domain` header to write attacker-controlled webhook body content into another merchant's per-tenant state. This matches the "cross-tenant access" Critical impact category, since the gem provides no integrity binding between the authenticated payload and the shop identity it reports to the application.

### Likelihood Explanation
Exploitation requires only the ability to send HTTP requests with a body/HMAC pair that passes `HmacValidator.validate` (e.g. by using a webhook payload/HMAC pair generated from the attacker's own installed shop, since HMAC uses the single shared `api_secret_key` across all shops using the app) combined with an arbitrary `X-Shopify-Shop-Domain` header of the attacker's choosing. No access token, refresh token, or `client_secret` is needed — only a topic/body/HMAC triple obtainable from the attacker's own shop's webhook deliveries and an unauthenticated header field. This is exploitable by any unprivileged internet user who has (or can register) their own installed shop for the app.

### Recommendation
Bind the `shop` (and `topic`, `webhook_id`, `api_version`) values into the signed material, or otherwise cryptographically verify the shop-domain header against the shop that legitimately produced the signature (e.g., require the caller to also verify shop via a separate authenticated channel, or include the header values in the HMAC input string mirroring Shopify's documented webhook verification, which in practice ties HMAC validity to a specific shop's secret when using per-shop secrets). At minimum, document/require the host app not to trust `WebhookMetadata#shop` for tenant selection without independent verification, or extend `to_signable_string` to include the shop/topic headers so `HmacValidator` covers them.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; capture a legitimate webhook delivery (`raw_body`, `X-Shopify-Hmac-Sha256`) — this HMAC is valid because it's computed with the app's single `api_secret_key`, not scoped per shop-domain header.
2. Replay this exact `raw_body` + `X-Shopify-Hmac-Sha256` to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` returns `true` (only `raw_body` is checked): [8](#0-7) 
4. `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled>, ...)`: [9](#0-8) 
5. Any host application logic keyed off `data.shop` (e.g., "find session/access token for this shop and update state from `data.body`") now operates on the victim shop's tenant using attacker-supplied body content, despite the HMAC never having verified that binding.
