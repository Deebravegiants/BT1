### Title
`fund_message` lets anyone add relayer fees to an already-delivered or timed-out request/response, permanently losing the funds - ([File: modules/pallets/ismp/src/lib.rs])

### Summary
`pallet-ismp`'s `fund_message` extrinsic increases the fee stored in `RequestCommitments`/`ResponseCommitments` for a given message and transfers the caller's tokens into `RELAYER_FEE_ACCOUNT`. It only checks that a commitment entry exists in storage; it does not check whether the request/response has already been delivered or timed-out. The function's own doc comment admits this: "Should not be called on a message that has been completed (delivered or timed-out) as those funds will be lost forever." This is the exact same bug class as the FantiumClaiming analog: funds sent to a "closed" (completed) message id cannot ever be attributed to a relayer or refunded to the sender.

### Finding Description

```rust
/// Add more funds to a message (request or response) to be used for delivery and execution.
///
/// Should not be called on a message that has been completed (delivered or timed-out) as
/// those funds will be lost forever.
pub fn fund_message(
    origin: OriginFor<T>,
    message: FundMessageParams<T::Balance>,
) -> DispatchResult {
    let account = ensure_signed(origin)?;

    let metadata = match message.commitment {
        MessageCommitment::Request(commitment) => RequestCommitments::<T>::get(commitment),
        MessageCommitment::Response(commitment) =>
            ResponseCommitments::<T>::get(commitment),
    };

    let Some(mut metadata) = metadata else {
        return Err(Error::<T>::MessageNotFound.into());
    };

    T::Currency::transfer(
        &account,
        &RELAYER_FEE_ACCOUNT.into_account_truncating(),
        message.amount,
        Preservation::Expendable,
    )?;

    match message.commitment {
        MessageCommitment::Request(commiment) => {
            metadata.fee.fee += message.amount;
            RequestCommitments::<T>::insert(commiment, metadata);
        },
        MessageCommitment::Response(commiment) => {
            metadata.fee.fee += message.amount;
            ResponseCommitments::<T>::insert(commiment, metadata);
        },
    };

    Ok(())
} [1](#0-0)
```

The only guard against a stale/invalid target is `MessageNotFound`, which fails only if the commitment key is absent from `RequestCommitments`/`ResponseCommitments` storage. There is no additional state field distinguishing "pending" from "delivered"/"timed-out" that is checked here — the function's own comment concedes this omission is unsafe. This is structurally identical to the `FantiumClaimingV1.addDistributionAmount()` bug: a caller can send funds against an identifier that has already reached a terminal state, and the protocol has no mechanism to recover them afterward (relayer fee accumulation via `pallet-ismp-relayer::accumulate_fees` only credits relayers for proofs of *delivery*, which has already happened and been claimed, so this extra deposit is never picked up by anyone) [2](#0-1) .

Any user or application (a relayer, dApp, or ordinary account holder acting on the pallet-ismp extrinsic surface) can trigger this by submitting a `fund_message` transaction with a commitment for a request/response that has already been executed or expired — a single unprivileged extrinsic, well within the analog scope (pallet-ismp handle/dispatch surface reachable by any submitted extrinsic).

### Impact Explanation
Funds transferred via `fund_message` targeting a completed message are permanently and irrecoverably locked in `RELAYER_FEE_ACCOUNT`: no relayer is incentivized to "deliver" a message that has already been delivered, and there is no withdrawal/refund path back to the depositor. This is a straightforward permanent freezing-of-funds bug, matching the "Accept only concrete theft or permanent freezing of funds" validation criterion. It can happen either accidentally (a relaying application funds a request slightly late, after another relayer already delivered it, or after a timeout fires) or be triggered/observed by an attacker to cause reliable loss of user funds by racing delivery/timeout against the funding transaction.

### Likelihood Explanation
Likelihood is realistic rather than purely theoretical: dispatchers and applications routinely call `fund_message` to top up relayer incentives for slow-to-deliver messages, and delivery/timeout races are common in cross-chain messaging (network latency, congestion, or the destination processing the message concurrently with the funding transaction being submitted). No special privileges are needed — it's a signed extrinsic anyone (including automated relayer-fee top-up bots) can call, and the existing code provides no protection, only a comment warning developers of the risk.

### Recommendation
Add an explicit check in `fund_message` that the referenced request/response commitment has not already been completed (delivered or timed-out) before accepting additional funds — e.g., verify against whatever receipt/completion storage (`RequestReceipts`/`ResponseReceipts` or equivalent completion markers) pallet-ismp maintains, and reject the call (refunding nothing needed since the transfer hasn't happened yet) if the message is already finalized. This mirrors the recommended fix for the original FantiumClaiming report: check that the target of a deposit is not already closed before accepting funds.

### Proof of Concept
1. Application A dispatches a cross-chain POST request via `pallet-ismp`, creating a `RequestCommitments` entry with some initial relayer fee.
2. A relayer delivers the request to the destination chain before the funding top-up lands; delivery is recorded (e.g., in `RequestReceipts`) and the relayer subsequently claims/accumulates the fee via `pallet-ismp-relayer`.
3. Concurrently, or slightly after, a user (or the same application, expecting the message still to be pending) submits `fund_message` with `MessageCommitment::Request(commitment)` and a nonzero `amount`.
4. Because `RequestCommitments::<T>::get(commitment)` still returns `Some(metadata)` (the storage entry for a delivered request is not necessarily purged, or persists long enough for the race), the check only tests for absence, not completion state; the transfer to `RELAYER_FEE_ACCOUNT` succeeds and `metadata.fee.fee` is incremented in storage.
5. Since the request is already delivered, no relayer will ever claim this additional fee increment, and there is no extrinsic to withdraw it back to the depositor — the funds are permanently stuck in `RELAYER_FEE_ACCOUNT`, exactly as the function's own doc comment predicts ("those funds will be lost forever") [3](#0-2) .
