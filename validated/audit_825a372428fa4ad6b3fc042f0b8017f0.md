**Rationale:**

The premise of this finding misreads what the `aggregator_v2::read` documentation means by "sequentializing." The comment on `read<IntElement>` at [1](#0-0)  states that calling `read` inside a transaction with read/write conflicts on the aggregator "will sequentialize that transaction," meaning Block-STM's optimistic concurrency control will detect the conflict and re-execute/serialize the transaction relative to conflicting writers — it does not mean the value returned is inconsistent. This is a performance characteristic (loss of parallelism), not a correctness weakening: Block-STM's validation phase guarantees that any transaction which commits has read values consistent with some valid serialization order; if a read would observe an inconsistent value due to a conflicting concurrent write, the transaction is aborted and re-executed rather than committed with the wrong value.

`balance_impl` in `fungible_asset.move` calls `balance_resource.balance.read()` directly on the `ConcurrentFungibleBalance` aggregator to compute the reported balance [2](#0-1) , and this same pattern is exercised by dispatchable balance hooks. Since `read()`'s semantics are defined precisely to prevent divergent/stale values from being observed by a committed transaction (at the cost of sequentialization, not at the cost of correctness), there is no mechanism by which an unprivileged caller invoking a custom `derived_balance` hook could cause `read()` to return a value that differs from the aggregator's true state once the transaction commits.

This is a question about Block-STM's execution-engine correctness guarantees (conflict detection causing abort-and-retry, not corrupted reads), not a Move-level custody bug. No unprivileged input crosses a custody boundary or changes any owner/holder/authority state — the finding does not meet the review's Decision Standard.
