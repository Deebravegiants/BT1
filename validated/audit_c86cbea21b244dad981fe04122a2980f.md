### Title
Webhook `shop-domain` header is trusted for tenant identity without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) that is handed to the application's webhook handler directly from the unauthenticated `x-shopify-shop-domain` header, while the HMAC signature that `Utils::HmacValidator` verifies is computed only over the raw request body. This breaks the identity binding `shop authenticated by HMAC == shop dispatched to handler`, allowing an attacker who controls a legitimately-installed shop to replay a genuinely-signed webhook body under a different shop's identity.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic tie to the signature: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the HMAC solely against `to_signable_string` (the body), never incorporating headers: [3](#0-2) 

`Registry.process` verifies the HMAC and then trusts `request.shop` (from the header) as the tenant identity forwarded to the app's handler: [4](#0-3) 

Because the signature only binds the body bytes, an attacker who owns their own legitimately-installed shop ("Shop A") receives real webhooks with a valid `hmac-sha256` for a given body (e.g., an `orders/create` webhook body they control the content of, or any webhook whose body content the attacker can produce/predict, such as `app/uninstalled` with no shop-specific fields, or a webhook whose body they replay verbatim). The attacker can then re-POST the exact same `raw_body` + `hmac-sha256` value to the app's webhook endpoint while substituting `x-shopify-shop-domain: shop-b.myshopify.com` (a victim tenant). `HmacValidator.validate` recomputes the same HMAC over the same body and it matches, so `Registry.process` accepts the request and calls the handler with `shop: "shop-b.myshopify.com"` even though the request never actually originated from Shopify for that shop. There is no per-shop secret in this gem (the `api_secret_key` is shared across all shops that install the app), so any tenant that can generate one valid signed webhook can forge the shop-identity of any other tenant for the same body content.

This is the same class of bug called out in the report: a field that is *acted upon* (here, `shop`, used as the tenant/session key for downstream dispatch) is not covered by the integrity check (the HMAC), letting the caller substitute the covered artifact into a different context and get a different, unintended trust decision — analogous to how `_from == _recipient` let `transferFrom` be driven into an unintended state despite passing its input checks.

### Impact Explanation
This is a cross-tenant identity forgery: an attacker-controlled installation can cause the application's webhook handler to execute application logic under the belief that the action came from a different, victim shop. Depending on how the host application's `WebhookHandler` uses `WebhookMetadata#shop` (e.g., to look up/update per-shop records, cache invalidation, provisioning, mandatory `shop/redact`/`customers/redact` handling), this can lead to cross-tenant data corruption or unauthorized actions attributed to a shop the attacker does not control. This matches the Critical "cross-tenant access" impact category since the tenant boundary enforced by the shop-domain claim is not actually authenticated.

### Likelihood Explanation
Exploitation requires the attacker to control at least one legitimate app installation (any developer/merchant account that installs the target app), which is a realistic bar for "any internet user who can install a public app," and does not require the `api_secret_key`, an access token, or any privileged Shopify access — only the ability to receive one genuine signed webhook and replay its body with a different header value against the app's public webhook endpoint. The main constraint is that the replayed body's fields (whatever the handler inspects, e.g., an object id) must make sense for the victim shop context, which narrows the practically useful payloads but does not eliminate the identity-forgery primitive itself.

### Recommendation
Bind the tenant identity into the verified data rather than trusting an unauthenticated header for authorization decisions:
- Include the `shop-domain` header (and ideally `topic`, `webhook-id`) in the HMAC signable string in `Webhooks::Request#to_signable_string`, so any tampering with the shop header invalidates the signature, mirroring how `Oauth::AuthQuery#to_signable_string` binds `shop` into its signed payload (`lib/shopify_api/auth/oauth/auth_query.rb`).
- Alternatively/additionally, cross-validate that `request.shop` matches the shop associated with the session/credentials expected to have sent the webhook before dispatching to the handler in `Registry.process`.

### Proof of Concept
1. Install the target app on attacker-controlled "Shop A" (`shop-a.myshopify.com`); the app's api_secret_key is shared across all installs.
2. Trigger a webhook whose body content is attacker-controllable/predictable (e.g., an event on Shop A) and capture the exact `raw_body` and its `x-shopify-hmac-sha256` value that Shopify legitimately sent.
3. Replay this exact `raw_body` + `hmac-sha256` to the app's webhook endpoint, changing only `x-shopify-shop-domain` to `shop-b.myshopify.com` (a victim shop that also has the app installed).
4. In `Webhooks::Request`, `to_signable_string` still returns the same `raw_body`; `HmacValidator.validate` recomputes the same signature and it matches, so `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(topic: ..., shop: "shop-b.myshopify.com", body: parsed_body, ...)` — i.e., the app processes attacker-supplied body content as if it were an authentic event from Shop B.
