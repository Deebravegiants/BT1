### Title
Shared, unauthenticated `CallDispatcher` allows escrow-crediting collision between interleaved orders in `IntentGatewayV2._placeOrder` - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2._placeOrder` computes the "actual received" amount of escrowed input tokens for an order by snapshotting the gateway's own token balance, running arbitrary user-supplied `predispatch.call` data through a single, protocol-wide `CallDispatcher` instance, then sweeping the *entire* current token balance held by that dispatcher back to the gateway and taking the balance delta as the order's escrowed amount. This mirrors the root cause in the external report: a balance-delta computed around an attacker-reachable external callback, where a shared account's balance can be inflated by unrelated in-flight activity before the delta is measured, causing accounting meant for one flow to be credited to another.

### Finding Description
In `_placeOrder`, when an order carries `predispatch` calldata, the flow is:

1. Transfer the order's `predispatch.assets` to a single shared `dispatcher` contract (`_params.dispatcher`) — the same `CallDispatcher` instance used by *every* order and by post-dispatch execution (`IntentsBase._execute`).
2. Execute attacker/user-controlled arbitrary calls via `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)`. [1](#0-0) 
3. Snapshot the gateway's own balance (`balancesBefore[i]`) and build sweep calls that transfer the dispatcher's **entire current balance** (`balance`, not `requiredAmount`) of each input token back to the gateway. [2](#0-1) 
4. Execute the sweep, then compute `received = balanceAfter - balancesBefore[i]` and use it directly as `order.inputs[i].amount`, the amount that becomes escrowed/committed for that order. [3](#0-2) 

`CallDispatcher.dispatch` has **no access control** — it is a bare external function callable by anyone, executing arbitrary `to.call{value}(data)` for whatever calldata is supplied: [4](#0-3) 

Because (a) the dispatcher is a single shared contract instance across all orders/users, (b) its `dispatch` entrypoint is fully unauthenticated, and (c) the sweep step credits the *entire* balance sitting on the dispatcher (not just the amount belonging to the current order) to whichever order is currently executing its sweep — any interleaving of a second order's predispatch flow inside the first order's `predispatch.call` execution window (step 2, before the snapshot/sweep of the first order) lets tokens staged by one order be swept and credited to a different order's `received`/escrowed amount. This is structurally identical to the Bunni report's bug: a balance-delta computation that spans an attacker-reachable external callback, where the "before" snapshot is taken only after arbitrary code has already run, but the "pool" being measured (the dispatcher's aggregate balance) is shared and not order-scoped.

### Impact Explanation
An order's escrowed `order.inputs[i].amount` — the value later paid out to a solver via `withdraw()`/`RedeemEscrow` — can be inflated with tokens that actually belong to a different, concurrently-processed order's predispatch stage. This can result in: (1) theft, where an attacker's order is credited with another user's staged funds sitting on the shared dispatcher, later redeemable by the attacker (or their controlled solver) via `fillOrder`/settlement; and (2) freezing/DoS of the victim order, which subsequently finds insufficient balance on the dispatcher and reverts with `InsufficientNativeToken`/`InvalidInput`, since its own funds were already swept away. Both are within the accepted impact categories (concrete theft of funds / freezing of funds via unsound state commitment of escrow accounting).

### Likelihood Explanation
Exploitability requires the attacker's `order.predispatch.call` (fully attacker-controlled calldata routed through the unauthenticated `CallDispatcher`) to trigger a second, interleaved `placeOrder`/predispatch flow that also stages assets on the same shared dispatcher before the first order's balance snapshot and sweep complete. Whether this succeeds in a single transaction depends on whether `placeOrder` (or the broader intents surface) is protected by a reentrancy guard that would block a nested `placeOrder` call reached via the dispatcher's callback; this could not be conclusively confirmed from the available context — `nonReentrant` appears elsewhere in `IntentGatewayV2.sol`, but its exact placement on `placeOrder` was not verified. If `placeOrder` is not itself reentrancy-guarded (or if the collision can be triggered without directly re-entering `placeOrder`, e.g., via any other unauthenticated call to `CallDispatcher.dispatch` that moves tokens onto/off the shared dispatcher balance mid-flight), the likelihood is Medium-to-High since the callback surface (`predispatch.call`) is entirely attacker-defined and the dispatcher has zero access control by design.

### Recommendation
- Scope the balance measurement to the specific order rather than the dispatcher's total balance: sweep only `requiredAmount` (or the amount actually attributable to this order's predispatch assets) instead of `IERC20(token).balanceOf(dispatcher)`/`address(dispatcher).balance` in full.
- Add reentrancy protection around the entire `placeOrder` execution (including the predispatch dispatch-and-sweep sequence) so that no other order's escrow flow can interleave with an in-flight predispatch/sweep window, consistent with the CEI fix already applied to `_fillSameChain`/`_fillCrossChain` in `IntrinsicIntents.sol`/`ExtrinsicIntents.sol`.
- Consider deploying a per-order (or per-call) ephemeral dispatcher/escrow account instead of a single global `CallDispatcher`, eliminating the shared-balance collision surface entirely.

### Proof of Concept
Conceptual PoC (mirrors the structure of the external report's `test_outputExcessiveBidTokensDuringRebalanceAndRefund`):
1. Attacker calls `placeOrder(orderA)` with `predispatch.assets` transferred to the shared `dispatcher`, and `predispatch.call` containing a call sequence that (directly or via an intermediate contract) triggers `placeOrder(orderB)` — also using `predispatch.assets` sent to the same `dispatcher` — from within `orderA`'s `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` step.
2. `orderB`'s flow runs to completion first (nested call), snapshotting the gateway balance, sweeping the dispatcher's *entire* current token balance (which now includes `orderA`'s staged predispatch assets, since `orderA` transferred them to `dispatcher` before invoking the nested call) and crediting all of it as `orderB.inputs[i].amount`.
3. Control returns to `orderA`'s frame, which now finds the dispatcher's balance for that token depleted, and either reverts (freezing `orderA`) or receives a much smaller `received` amount than intended.
4. Attacker later fills/redeems `orderB` (as solver or via a colluding fill), extracting value that includes `orderA`'s stolen escrow contribution.

This could not be executed against the live repository within the available tooling (read-only code search); the analysis is based on static reading of `evm/src/apps/IntentGatewayV2.sol` and `evm/src/utils/CallDispatcher.sol`, and confirmation of whether an existing reentrancy guard fully blocks the nested-`placeOrder` path was not possible with the tools available in this session.
