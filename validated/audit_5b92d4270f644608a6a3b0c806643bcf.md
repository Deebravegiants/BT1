### Title
Missing chain-ID whitelist/enforcement when signing Ethereum-family transactions on Ledger — (`File: features/hw-ledger/src/module/assets/ethereum.ts`)

### Summary
The Ledger Ethereum transaction handler enforces the correct EIP-155 `chainId` only for a hardcoded subset of asset names (`ethereum`, `matic`, `basemainnet`). Any other Ethereum-compatible asset registered against this same handler (e.g. `ethereumsepolia`, which is explicitly mapped to the same `ethereum` handler) falls through the `switch` with no `default` case, and the `chainId` embedded in the raw `signableTransaction` bytes is trusted as-is and signed by the hardware wallet.

### Finding Description
In `createHandler`'s `signTransaction` method, the code parses the caller-supplied `signableTransaction` and then attempts to force the correct chain ID based on `params.assetName`: [1](#0-0) 

Only three cases are whitelisted/enforced (`ethereum` → 1, `matic` → 137, `basemainnet` → 8453). There is no `default` branch, and the code even has a `// No default` comment acknowledging this. `assetApplications` in the same feature registers `ethereumsepolia` (and any future EVM asset) against this exact `ethereum` handler: [2](#0-1) 

Because `ethereumsepolia` is not one of the three whitelisted names, its transactions skip the `chainId` override entirely, and whatever `chainId` value is present in the raw `signableTransaction` (constructed upstream and passed through `tx-signer`'s hardware-signing path) is what actually gets serialized, resolved via `ledgerService.resolveTransaction`, and sent to the Ledger device for signing: [3](#0-2) 

This mirrors the reported bug class exactly: instead of validating/whitelisting the chain ID against the asset actually being displayed/approved on-device, the code trusts an unvalidated, attacker/caller-influenced field for all but three enumerated cases.

### Impact Explanation
`chainId` is baked into the EIP-155 signature. If the enforcement gap allows a transaction whose `chainId` does not match the asset/network the user believes they are approving (e.g. a `ethereumsepolia` flow carrying a mainnet `chainId=1`, or any newly added EVM asset not added to the switch), the resulting signature is a valid, broadcastable mainnet (or other unintended chain) transaction signed by the user's real key — a direct wallet-compromise/unauthorized-signing outcome, potentially causing loss of funds, exactly analogous to the "loss of tokens / invalid state" impact described in the original report for un-whitelisted chain IDs.

### Likelihood Explanation
The gap is triggered whenever `params.assetName` is anything other than the three hardcoded strings, which today includes `ethereumsepolia` (already registered against this handler) and any future EVM chain integration. Since the enforcement logic is an explicit allowlist with a documented `// No default` fallthrough, this is a structural, always-reachable code path rather than a hypothetical edge case — new EVM assets are silently unprotected until someone remembers to add a case to this switch.

### Recommendation
Replace the assetName-based `switch`/no-default pattern with an authoritative, complete mapping (or explicit chain-ID whitelist) covering every EVM asset registered in `assetApplications`, and fail closed (throw) for any `assetName` not present in that whitelist rather than silently trusting the caller-supplied `chainId`.

### Proof of Concept
1. Register/support an EVM asset (e.g. `ethereumsepolia`) that routes through `createHandler` in `features/hw-ledger/src/module/assets/ethereum.ts`.
2. Call `signTransaction` with `params.assetName = 'ethereumsepolia'` and `params.signableTransaction` containing a serialized transaction whose embedded `chainId` is `1` (mainnet) instead of Sepolia's `11155111`.
3. Because `'ethereumsepolia'` does not match `'ethereum'`, `'matic'`, or `'basemainnet'` in the `switch` at lines 112-131, the `chainId` is never overwritten; the transaction is serialized and sent to the Ledger device as-is.
4. The device signs a transaction with `chainId=1`. The resulting signed payload is a valid mainnet transaction, even though the user/dapp context intended a testnet operation — demonstrating unauthorized, unwhitelisted chain-ID signing.
