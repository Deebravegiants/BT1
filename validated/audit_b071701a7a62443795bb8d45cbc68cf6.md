## Title
Consensus relayer reward miscalculated when `update_cost_per_block` changes mid-span rate - (File: `modules/pallets/consensus-incentives/src/lib.rs`, `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`pallet-consensus-incentives::update_cost_per_block` changes the per-block reward rate for a state machine without first settling (checkpointing) any pending, unrewarded block span at the *old* rate. The reward payout logic in `calculate_reward`/`process_message` always applies whatever `block_cost` is currently stored to the *entire* unpaid span `(baseline, latest_height]`, exactly mirroring the FraxlendPair `changeFee()` bug where a rate change is applied retroactively across a time window that spans both the old and new rate.

### Finding Description
`update_cost_per_block` simply overwrites the stored rate with no interaction with the reward/accrual state: [1](#0-0) 

The reward calculation, triggered later by `FeeHandler::on_executed` whenever a relayer submits a `ConsensusMessage`, computes the unpaid span from `LastRewardedHeight` (the watermark of the last reward) up to the latest committed height, then multiplies that whole span by whatever `block_cost` is stored **at the time of calculation**: [2](#0-1) 

`process_message` then transfers the computed `reward` from the treasury to the relayer and advances the watermark: [3](#0-2) 

This is the same root cause as the Frax `changeFee()` finding: a time-weighted accrual (`blocks × rate`) is computed lazily, and governance's rate-change call does not first flush/settle the pending accrual at the old rate. Concretely:

- At height `H1` (time `T1`), `StateMachinesCostPerBlock = C1`, and `LastRewardedHeight = B` (some baseline, e.g. from a while ago — relayers are not required to submit consensus updates promptly).
- At `T2`, governance calls `update_cost_per_block` and changes the rate to `C2`.
- At `T3`, a relayer submits (or a consensus message that was already in-flight lands) a `ConsensusMessage` proving the state machine has advanced to height `H2 > H1`.
- `calculate_reward` computes `reward = (H2 - B) × C2`, i.e., it applies the **new** rate `C2` to the *entire* span `B → H2`, even though blocks `B → H1` should have earned `C1` and only `H1 → H2` should earn `C2`.

### Impact Explanation
Because `IsmpDispatcher`/consensus message delivery is permissionless and reward-eligible relayers control exactly *when* they submit a given consensus proof, this bug is directly exploitable, not merely accidental:

- A relayer who observes (or anticipates) that governance is about to raise `cost_per_block` for a state machine can **withhold** submitting an already-available consensus proof that advances the state machine height, wait for the rate increase, then submit it. The entire backlog of blocks (which should have been paid at the old, lower rate) is paid out at the new, higher rate, draining `TreasuryAccount` for more BRIDGE/reputation than governance intended.
- Conversely, if governance lowers the rate, honest relayers who happen to have accumulated a large unpaid backlog get underpaid for work already performed at the previous higher rate, which is a fairness/incentive-alignment issue and can silently reduce reward outlay below what governance actually configured for the period the blocks were produced in.

This is a fund-leakage bug reachable from a fully unprivileged actor (any relayer submitting a normal consensus datagram), consistent with the reachable-analog criteria (relayer fee/reward accounting via consensus verification delivery).

### Likelihood Explanation
`StateMachinesCostPerBlock` is expected to be periodically retuned by governance as block-cost economics change, and relayers do not always submit consensus updates on every block — the existing rollback-handling logic in this same pallet demonstrates that unpaid spans of many blocks (thousands) can accumulate before a reward is claimed. Combined with the fact that any relayer can choose the timing of their `ConsensusMessage` submission, the conditions for triggering the overpayment (large backlog + a rate change occurring mid-backlog) are realistic and can be intentionally engineered by a profit-seeking relayer.

### Recommendation
Before applying a new `cost_per_block` in `update_cost_per_block`, settle the pending reward for any state machine(s) whose rate is changing at the **current** rate — i.e., snapshot `latest_commitment_height` and pay out (or explicitly checkpoint) the reward owed for the span up to that point at the old rate, advancing `LastRewardedHeight` to that height, before writing the new `cost_per_block`. Alternatively, disallow rate updates for a state machine while it has any unpaid backlog (`LastRewardedHeight < latest_commitment_height`), forcing settlement first.

### Proof of Concept
1. Governance sets `StateMachinesCostPerBlock[SM] = C1` and the chain currently sits at `LastRewardedHeight = B`, `latest_commitment_height = H1` (unpaid backlog exists, e.g. because no relayer has claimed for a while).
2. A relayer holding a valid consensus proof that would advance `SM` to `H1` deliberately does not submit it.
3. Governance calls `update_cost_per_block(SM, C2)` with `C2 > C1` for unrelated reasons (e.g. gas price increase).
4. The relayer now submits the withheld consensus proof (plus any newer one, advancing to `H2 >= H1`).
5. `on_executed` → `process_message` → `calculate_reward` computes `reward = (H2 - B) * C2`, paying the relayer (and minting reputation) for the entire span `B..H2` at `C2`, even though the sub-span `B..H1` was produced while the rate was `C1`. [4](#0-3)

	fn process_message(
		state_machine_height: StateMachineHeight,
		state_machine_id: StateMachineId,
		relayer_account: T::AccountId,
	) -> Result<(), Error<T>> {
		if let Some(block_cost) = StateMachinesCostPerBlock::<T>::get(state_machine_id) {
			let reward = Self::calculate_reward(&state_machine_id, block_cost)?;

			if reward.is_zero() {
				return Ok(());
			}

			T::Currency::transfer(
				&T::TreasuryAccount::get().into_account_truncating(),
				&relayer_account,
				reward,
				Preservation::Expendable,
			)
			.map_err(|_| Error::<T>::RewardTransferFailed)?;

			Self::deposit_event(Event::<T>::RelayerRewarded {
				relayer: relayer_account.clone(),
				amount: reward,
				state_machine_height,
			});

			T::ReputationAsset::mint_into(&relayer_account, reward.saturated_into())
				.map_err(|_| Error::<T>::ReputationMintFailed)?;

			LastRewardedHeight::<T>::mutate(state_machine_id, |watermark| {
				*watermark = Some(watermark.unwrap_or_default().max(state_machine_height.height));
			});
		}
		Ok(())
	}

	/// Calculate the reward for a message based on the state machine id
	fn calculate_reward(
		state_machine_id: &StateMachineId,
		block_cost: <T as pallet_ismp::Config>::Balance,
	) -> Result<<T as pallet_ismp::Config>::Balance, Error<T>> {
		let host = <T::IsmpHost>::default();
		let latest_height = host
			.latest_commitment_height(state_machine_id.clone())
			.map_err(|_| Error::<T>::CouldNotGetStateMachineHeight)?;
		let previous_height =
			host.previous_commitment_height(state_machine_id.clone()).unwrap_or_default();

		// Use the rewarded watermark as the baseline and fall back to the previous height until
		// the first reward is recorded for this chain. The watermark only moves forward, so a
		// height that is rolled back and later resubmitted is not paid for a second time.
		let baseline = LastRewardedHeight::<T>::get(state_machine_id).unwrap_or(previous_height);

		let blocks = latest_height.saturating_sub(baseline);

		let blocks_as_balance: <T as pallet_ismp::Config>::Balance = blocks.saturated_into();
		let reward = blocks_as_balance.saturating_mul(block_cost);

		Ok(reward)
	}
