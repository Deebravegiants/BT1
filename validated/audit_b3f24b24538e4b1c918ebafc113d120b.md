### Title
Webhook shop/topic identity spoofing — HMAC signs only the raw body, not the `shop`/`topic` headers relied upon for tenant attribution - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values that `Registry.process` hands to the app's handler as "verified" webhook identity come from HTTP headers that are never part of the signed bytes. This breaks the identity binding: `shop authenticated == shop that produced the signed bytes`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from headers, none of which are included in the signed string: [2](#0-1) 

`HmacValidator.validate` only checks the HMAC over `to_signable_string` (the raw body) against the app's shared secret: [3](#0-2) 

`Registry.process` treats a passing HMAC check as full authentication of the request, then forwards the *unauthenticated* `request.shop` (and topic/webhook_id/api_version) straight to the app-supplied handler: [4](#0-3) 

The gem's own documentation asserts that `Registry.process` "will verify the request did indeed come from Shopify" and that the resulting `data.shop` is the authoritative "shop domain of the webhook":


But the HMAC secret (`client_secret`) is shared across every shop that installs the same app — it is not shop-specific. Any shop that legitimately installs the app receives real webhooks from Shopify containing a valid `X-Shopify-Hmac-Sha256` computed over that shop's raw body with the shared secret. Because the header carrying `shop`/`topic` is outside the signed bytes, that exact (raw_body, hmac) pair remains valid if replayed with a different `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header pointed at a victim shop.

### Impact Explanation
This is a cross-tenant identity-binding break analogous to the withdrawal-batch bug: a value the gem treats as authenticated (`shop`) is never covered by the cryptographic check that supposedly authenticates the whole request. An attacker who is merely an unprivileged installer of the target app on their own store can:
1. Capture one legitimate webhook delivery (raw body + valid HMAC) for their own shop.
2. Replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`, e.g. `shop/redact`/`customers/redact`) header rewritten to a victim's domain.
3. `HmacValidator.validate` passes because the body bytes and secret are unchanged, and `Registry.process` invokes the app handler with `WebhookMetadata#shop == victim_domain`.

Any host app that follows the gem's documented contract and keys business logic (session lookups, per-tenant data writes, mandatory GDPR redaction flows) off `data.shop` will now attribute attacker-controlled data/events to a victim shop — a cross-tenant data-integrity/spoofing break.

### Likelihood Explanation
Requires only that the attacker control a shop that installs the same app (a normal, unprivileged action for any public/OAuth app) and be able to POST to the app's public webhook callback route — no access token, `api_secret_key`, or privileged account is needed. This is directly reachable through the gem's documented `Registry.process` / `Request` API.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` (or otherwise bind them cryptographically, e.g. via a MAC over headers+body, or validate them against the caller's IP/known Shopify infra plus a shop-allowlist maintained by the host app) in the value covered by `to_signable_string`/`HmacValidator`, so that a change to any of these identity fields invalidates the HMAC. At minimum, document prominently that `data.shop`/`data.topic` are NOT part of the authenticated payload and must be independently cross-checked by the host application before being trusted for tenant attribution.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com`; attacker triggers e.g. an `orders/create` webhook and captures the raw POST: body `B` and header `X-Shopify-Hmac-Sha256: H = HMAC_SHA256(client_secret, B)`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker resends the identical request to the app's webhook endpoint, changing only `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and, if desired, `X-Shopify-Topic: shop/redact`).
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` → `Utils::HmacValidator.validate` recomputes `HMAC_SHA256(client_secret, B)` = `H`, matches, returns `true`.
4. `Registry.process` calls the app's handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, and the app treats this as an authentic event for `victim-shop`.
