### Title
Unsolicited token deposits to the liquidity pool are permanently unrecoverable - ([File: contracts/pool/src/cache/mod.rs])

### Summary
The pool maintains a separate `cash` accounting book instead of deriving available liquidity from its live token balance. [1](#0-0)  An unprivileged user can call the token contract's `transfer(donor, pool_address, amount)`, but no pool accounting entry is created because the pool contract is never invoked. [2](#0-1) 

### Finding Description
`supply` credits `cash` only for the `amount` specified in a controller-issued `PoolSupplyEntry`; it does not reconcile the entry against unsolicited balance increases. [3](#0-2)  Withdrawals are constrained by the stored cash book, which is checked and debited before transferring tokens. [4](#0-3)  Revenue withdrawal likewise burns only claimable revenue shares and debits the corresponding booked amount. [5](#0-4)  The pool's public mutators provide market operations such as `supply`, `borrow`, `withdraw`, `repay`, `recapitalize`, `flash_loan`, `seize_positions`, `net_settle`, and `claim_revenue`, but no function transfers an unbooked token surplus to the depositor or another account. [6](#0-5) 

### Impact Explanation
Tokens sent directly to the pool become an unbooked surplus: they increase `token.balance(pool)` without increasing any market's `cash`, supply shares, or claimable revenue. [7](#0-6)  Because all ordinary outbound transfers are tied to booked cash or booked revenue, the donation remains after all recorded balances are withdrawn. [8](#0-7)  This permanently freezes the donor's funds in the contract.

### Likelihood Explanation
The likelihood is low because it requires a user to bypass the controller's measured `supply` or `recapitalize` flow and transfer assets directly to the pool address. [9](#0-8)  Nevertheless, any token holder can perform the direct transfer without protocol privileges.

### Recommendation
Add an owner- or governance-controlled recovery entrypoint that transfers only `token.balance(pool) - sum_of_booked_cash_for_that_asset`, ensuring it cannot withdraw user-backed liquidity. Alternatively, implement a public donation-recovery function restricted to the unbooked surplus for the donated asset.

### Proof of Concept
1. Deploy a listed market whose pool has booked `cash = C` and token balance `C`.
2. An unprivileged donor calls `token.transfer(donor, pool, D)` directly.
3. `token.balance(pool)` becomes `C + D`, while the market cache still loads the stored `cash = C`, because direct token transfers do not invoke pool accounting. [7](#0-6) 
4. `controller.withdraw(caller, account_id, [(hub_asset, amount)], to)` cannot return `D` to the donor because the donor has no supply position and withdrawals are limited by booked cash. [10](#0-9) 
5. After all legitimate suppliers withdraw their booked `C`, the pool still holds `D`, and `claim_revenue` cannot release it because it pays only claimable booked revenue. [5](#0-4)

```rust
pub(crate) fn apply(
    env: &Env,
    entry: &PoolSupplyEntry,
) -> (PoolPositionMutation, MarketStateSnapshot) {
    let (mut cache, mut position) = ops::load_leg(env, &entry.action);
    let amount = entry.action.amount;

    guards::require_backed_market(env, &cache);

    let minted = cache.calculate_scaled_supply(amount);
    assert_with_error!(
        env,
        amount == 0 || minted.raw() > 0,
        GenericError::SupplyRoundsToZeroShares
    );

    position = position.checked_add(env, minted);
    cache.mint_supply(minted);

    cache.credit_cash(amount);

    let snapshot = cache.commit();
```
