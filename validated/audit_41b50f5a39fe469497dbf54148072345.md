### Title
Unmetered CPU work during `pre.instantiate` (active table/memory segment initialization) before gas call_hook is installed - ([File: runtime/near-vm-runner/src/wasmtime_runner/mod.rs])

### Summary
In `PreparedContract::run`, `pre.instantiate(&mut store)` (`runtime/near-vm-runner/src/wasmtime_runner/mod.rs:1036`) is executed to materialize the wasmtime `Instance` — running active table/element and data segment initializers and global initializer expressions — before the gas-tracking `call_hook` is installed at `runtime/near-vm-runner/src/wasmtime_runner/mod.rs:1064`. The only gas charged for the loading/instantiation phase is `before_loading_executable`/`after_loading_executable` (`runtime/near-vm-runner/src/logic/gas_counter.rs:225-272`), which charges strictly proportional to `wasm_code_bytes` (`contract_loading_base + contract_loading_bytes * code_len`), not to the number/size of active segments or table/memory sizes touched during instantiation.

### Finding Description
`with_compiled_and_loaded` charges `before_loading_executable`/`after_loading_executable`, both of which call `add_contract_loading_fee(wasm_code_bytes)` (`gas_counter.rs:224-227`), a fee that is a pure linear function of the compiled WASM byte size [1](#0-0) . This fee is charged once during `with_compiled_and_loaded`, before `pre.instantiate` is ever invoked [2](#0-1) .

Separately, in `PreparedContract::run`, the actual `pre.instantiate(&mut store)` call happens at line 1036, and only *after* it succeeds does the code resolve the memory export and install the `call_hook` gas-synchronization closure (lines 1044-1088) [3](#0-2) . Wasmtime's `Instance` instantiation runs active element-segment table initialization and active data-segment memory initialization (and global initializer expressions/`start` semantics per the Wasm spec) as part of `instantiate`, and this work is proportional to segment count/size, not to `wasm_code_bytes`.

`LimitConfig` bounds `max_elements_per_contract_table` and `max_memory_pages` (`core/parameters/src/vm.rs:141-143`, `:73`), meaning a contract's table can have up to that many elements and memory up to that many pages, but these limits bound *what is allowed*, not what is *charged for*. Since `wasm_code_bytes` used for the loading fee is the compiled/serialized module byte count, and active segment initializer bytecode can be extremely compact per unit of runtime work (e.g., a single active element segment expression targeting a large table, or table `.fill`/init driven by module structure with attacker-controlled repeated small segments spanning up to `max_elements_per_contract_table`), the actual instantiation-time cost is not proportional to `wasm_code_bytes`.

### Impact Explanation
If instantiation time genuinely scales with segment/table/memory size in a way disproportionate to the code-size-based loading fee, an attacker can submit `FunctionCall` receipts against a deployed contract that consume node CPU far beyond what was charged, enabling a gas-metering-completeness bypass ("free execution") and a CPU-based denial-of-service vector against validators/RPC nodes executing the receipt (matches NEAR bounty impact classes: gas metering bypass / unbounded resource use / node degradation).

### Likelihood Explanation
This is plausible in principle (unmetered work is a real category of NEAR VM issues, as evidenced by the historical `fix_contract_loading_cost` protocol feature that exists specifically because "This cost does not consider the structure of the contract code, only the size" — see the comment at `gas_counter.rs:216-222`), but I could not confirm from the available code that active-segment instantiation cost in wasmtime is actually super-linear or unbounded relative to `max_elements_per_contract_table`/`max_memory_pages`, nor could I find or rule out an additional charge elsewhere (e.g., in `prepare_v3`/`instrument_v3`) that might account for segment-driven instantiation cost. The `prepare_v3.rs`/`instrument_v3.rs` passes were only partially inspected here; a full read of those files (and the wasmtime `instantiate` cost model) is needed to determine whether segment count/size is already bounded tightly enough (via `max_elements_per_contract_table`, `max_memory_pages`, `max_tables_per_contract`, `max_contract_size`) that worst-case instantiation cost remains within a safe constant-factor bound of the charged loading fee, which is the standard mitigation NEAR uses for this class of issue elsewhere.

### Recommendation
Verify empirically (via the PoC below) whether `pre.instantiate` cost for a maximal active-segment/table/memory contract is disproportionate to `wasm_code_bytes`-based `contract_loading_base`/`contract_loading_bytes` charge. If disproportionate, either (a) charge instantiation cost proportional to declared table/memory/segment sizes before calling `pre.instantiate` (an additional pre-charge similar to `add_contract_loading_fee` but keyed on segment/table/memory size derived from the parsed module, not raw `wasm_bytes`), or (b) tighten `max_elements_per_contract_table`/`max_memory_pages`/segment-count limits in `LimitConfig` so that worst-case instantiation work is bounded to a value consistent with the existing per-byte loading fee.

### Proof of Concept
Unit/benchmark test in `runtime/near-vm-runner/src/tests/`:
1. Construct two WAT/WASM modules of near-identical `wasm_bytes` size (pad the "minimal" one with an inert custom/data section to match): (a) minimal module with a small table (1 element) and no data segments, (b) worst-case module with a table sized at `max_elements_per_contract_table` (from `LimitConfig`) populated by one or more active element segments, and/or memory sized at `max_memory_pages` populated by active data segments.
2. Deploy both via `vm_kind.runtime(config).prepare(...).run(...)`, wrapping the call in `Instant::now()`/`elapsed()` around the `run` invocation (or instrument specifically around `pre.instantiate` if test hooks allow).
3. Assert `outcome.used_gas` is equal (or near-equal, since both share the same `wasm_code_bytes`) between the two cases (expected, since `before_loading_executable`/`after_loading_executable` charge only by `wasm_code_bytes`).
4. Assert wall-clock instantiation time for case (b) is not disproportionately larger than case (a) beyond what the shared gas charge would justify at the network's target gas-to-wallclock ratio; if it is significantly larger (e.g., orders of magnitude), this confirms the unmetered-work vulnerability.
5. Repeat the call multiple times to amplify and confirm the CPU cost is repeatable per-call (not one-time compile/cache cost) by ensuring the compiled-contract cache is warm before timing (i.e., instantiation, not compilation, is what's measured), isolating the segment-initialization-only cost from `compile_and_cache`.
