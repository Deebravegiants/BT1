### Title
Webhook `shop` (and `topic`/`webhook_id`) header is trusted without being covered by the HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) and other dispatch-critical fields (`topic`, `webhook_id`, `api_version`) purely from HTTP headers, while the HMAC signature that `Utils::HmacValidator` checks only covers the raw request body. This breaks the identity binding `verified_bytes == acted_upon_bytes`: the bytes cryptographically verified (body) are not the bytes used to determine which shop/tenant the event is attributed to (headers).

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read from HTTP headers, which are never part of the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` calls `validate_signature`, which computes the HMAC over `verifiable_query.to_signable_string` (the body only) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build `WebhookMetadata` passed to the app's handler, with no cross-check that these header values are consistent with anything cryptographically verified: [4](#0-3) 

Because a shop's app secret (`client_secret`) is shared across all shops/stores that install the same app, any store that installs the app receives genuinely-signed webhooks from Shopify for its own events. An attacker who controls (or creates) their own installed store can capture a real, validly-signed webhook body+HMAC pair from Shopify for their own shop, then replay that exact body/HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` (and/or `shopify-topic`/`shopify-webhook-id`) header with a victim shop's domain. `HmacValidator.validate` will still return `true`, because the signature check never examined those headers, and `Registry.process` will dispatch the event to the handler labeled as coming from the victim shop.

The identity binding that should hold is:
`shop_header_used_by_handler == shop_that_produced_the_signed_body`

but the code only enforces:
`hmac_header == HMAC(body, secret)`

with `shop` entirely outside that equation.

### Impact Explanation
If a host application (following this gem's own documented pattern in `docs/usage/webhooks.md` of trusting `WebhookMetadata#shop` from a "verified" webhook to key merchant data, update state, or attribute the event) receives a forged/spoofed shop header, an attacker-controlled event body can be attributed to and processed under a victim shop's identity — a cross-tenant confusion/injection primitive achieved purely by manipulating an unauthenticated header on top of a genuinely-signed body. This satisfies the Critical impact category of cross-tenant access, since data belonging to (or acted upon on behalf of) one tenant can be forced into another tenant's context without any privileged credential beyond having one's own legitimate app installation.

### Likelihood Explanation
Likelihood is High: no `access_token`, `api_secret_key`, or privileged account is required — only a standard, unprivileged installation of the target app on any shop (including a free development store the attacker controls), which is achievable by any internet user who can install a public Shopify app. Capturing one's own genuine webhook body+HMAC and replaying it with a substituted `shop`/`topic` header is straightforward HTTP manipulation.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header values in the signable string used for HMAC verification, or otherwise cryptographically bind the shop domain to the signed payload before `HmacValidator.validate` returns `true`, so that `to_signable_string` covers all fields the handler subsequently trusts (mirroring how `Auth::Oauth::AuthQuery#to_signable_string` includes the full query set, not just a subset).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, unprivileged action).
2. Shopify sends a legitimately signed webhook to the app, e.g. body `{"id":123,...}` with header `x-shopify-shop-domain: attacker-shop.myshopify.com` and a valid `x-shopify-hmac-sha256`.
3. Attacker captures this raw body + HMAC header pair.
4. Attacker replays the identical body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` returns `true` because it only hashes `@raw_body`; the header substitution is invisible to it.
6. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` builds `WebhookMetadata.new(... shop: request.shop ...)` using the spoofed `victim-shop.myshopify.com` value and dispatches it to the handler, which now processes attacker-supplied data under the victim's tenant identity. [5](#0-4)

      end

      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

      private

      sig { params(name: String).returns(T.untyped) }
      def shopify_header(name)
        @headers["shopify-#{name}"] || @headers["x-shopify-#{name}"]
      end
    end
  end
