### Title
Unauthenticated `address` field in `GetRequestsWithProof` lets any submitter mint themselves reputation for work done by the real relaying party - ([File: modules/pallets/state-coprocessor/src/impls.rs])

### Summary
`pallet-state-coprocessor::handle_unsigned` is submitted as an unsigned extrinsic (`ensure_none(origin)`), so it is reachable by any unprivileged submitter who can construct a valid state proof (a relayer, or anyone re-broadcasting/racing a relayer's message). The reward-attribution field, `address`, is taken verbatim from the submitted payload rather than being cryptographically bound to the entity that produced the proof, mirroring the Shardus bug class where the field determining "who gets credited" is trusted from caller-supplied data instead of being independently derived/verified.

### Finding Description
`GetRequestsWithProof` carries `address: Vec<u8>` documented as "Address that should be credited with fees" [1](#0-0) . The call entry point is unsigned: [2](#0-1) 

Inside `handle_get_requests`, all the cryptographic verification (source membership proof, destination state proof) is performed correctly on `requests`/`source`/`response` — but `address` itself is never checked against any signature, proof, or the transaction's submitter. It flows straight into the reputation-minting logic: [3](#0-2) 

Contrast this with the sibling `pallet-messaging-incentives` `FeeHandler`, which recovers the relayer identity by verifying a signature over the message (`relayer_for`) rather than trusting a caller-supplied address: [4](#0-3) 

For `GetRequestsWithProof`, no equivalent recovery exists — `address` is copied straight from the wire into the mint destination and into `store_response_receipt`/dispatch attribution: [5](#0-4) 

Because the extrinsic is unsigned, `validate_unsigned` only needs to see a structurally valid message with correct proofs — proofs which are public and can be copied from the mempool or from a relayer's already-broadcast (but not yet included) transaction. An attacker can take a proof that a legitimate relayer produced (or wait for one to appear in the pool / an intermediate node) and resubmit an equivalent `GetRequestsWithProof` with their own `address`, racing to get it included first and stealing the reputation-mint reward. This is directly analogous to the root cause in the referenced report: a field that should be independently derived/re-verified (there: `appData`/staking info; here: the credited relayer address) is instead trusted as supplied by an untrusted party in an unsigned/gossiped message.

### Impact Explanation
This lets an unprivileged party steal `ReputationMinted` rewards that should accrue to the relayer who actually did the work of fetching/proving state for a `GetRequestsWithProof` batch — a direct "steal other node's/relayer's rewards" impact, the same impact class flagged as critical in the reference report. While the amount minted is bounded by governance-set `MintPerByte` and is a reputation asset (not necessarily a directly transferable financial asset), if `ReputationAsset` has economic value (staking weight, fee-token convertibility, or governance weight), this becomes a genuine value-transfer/theft vector and could also be used to unfairly inflate a Sybil's reputation for collator selection or similar mechanisms that key off this asset.

### Likelihood Explanation
High reachability: `handle_unsigned` is exposed to any unsigned extrinsic submitter; the only barrier is possessing a valid state proof, which is public information once a legitimate relayer has fetched it (or even the same proof data independently re-fetched by the attacker, since `GetRequest`s and their proofs are not relayer-specific secrets). Front-running/racing an honest relayer's unsigned submission is a standard and cheap attack in a permissionless mempool for unsigned transactions of this type.

### Recommendation
Bind the credited `address` cryptographically to the actual submitter/proof-producer instead of trusting the wire-supplied field, mirroring `pallet-messaging-incentives::relayer_for`: e.g., require a signature over the request/proof payload and recover the relayer's account from it, or otherwise derive attribution from data the submitter cannot forge (such as a `ValidateUnsigned::validate_unsigned` binding to the signer field of the message itself), and reject the extrinsic entirely if the recovered identity doesn't match the claimed `address`.

### Proof of Concept
1. Honest relayer R constructs a valid `GetRequestsWithProof { requests, source, response, address: R }` and broadcasts it as an unsigned extrinsic.
2. Attacker A observes this in the transaction pool (or independently reconstructs the same `requests`/`source`/`response` from public chain data, since nothing in the proof is relayer-specific).
3. A crafts `GetRequestsWithProof { requests, source, response, address: A }` — identical proof data, only `address` swapped — and submits it with higher priority/faster propagation.
4. `handle_get_requests` verifies the (unchanged, still-valid) proofs successfully and executes `ReputationAsset::mint_into(&A, amount)` at `modules/pallets/state-coprocessor/src/impls.rs:166-178`, crediting A instead of R for R's work.
5. R's original submission, once/if included, is rejected as a duplicate (`DuplicateResponse`) since the response commitment mirrors `response_receipt`, so R receives nothing.

	/// Recover the relayer's account from the sr25519 signature on a
	/// `Message`'s `signer` field. Returns `None` if the message has
	/// no signer (e.g. consensus messages) or the signature is bad.
	fn relayer_for(message: &Message) -> Option<T::AccountId> {
		let (signer, signed) = match message {
			Message::Request(msg) =>
				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
			Message::Response(msg) =>
				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
			_ => return None,
		};
		Signature::decode(&mut &signer[..])
			.ok()?
			.verify_and_get_sr25519_pubkey(&signed, None)
			.ok()
			.map(T::AccountId::from)
	}
