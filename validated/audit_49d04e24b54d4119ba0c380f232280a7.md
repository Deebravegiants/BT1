### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [1](#0-0) , and `HmacValidator.validate` checks the HMAC only against that signable string [2](#0-1) . The `shop-domain` header, which `Registry.process` passes on as the tenant identity to the app's handler, is never part of the signed bytes [3](#0-2) [4](#0-3) .

### Finding Description
The identity binding that should hold is: `shop that generated the signed body == shop attributed to the webhook by the app`. Because `to_signable_string` only returns `@raw_body` [1](#0-0) , and the HMAC comparison in `HmacValidator.validate_signature` only checks `verifiable_query.to_signable_string` against the computed digest [2](#0-1) , the `shop-domain` header used to build `WebhookMetadata` in `Registry.process` [4](#0-3)  is not bound to the signature at all. An attacker who controls (or has ever received) a validly-signed webhook body+HMAC pair for the shared app secret (e.g. by installing the target app on their own shop and capturing one of their own legitimate webhook deliveries) can resend that exact `raw_body` + `hmac-sha256` header to the app's webhook endpoint while substituting an arbitrary `shop-domain` header. `Registry.process` will accept it as valid (`Utils::HmacValidator.validate(request)` passes because only the body is checked) and dispatch it to the handler with `shop: request.shop` set to the attacker-chosen value [5](#0-4) .

This contrasts with `Auth::Oauth::AuthQuery#to_signable_string`, which explicitly includes `shop` in the signed parameters [6](#0-5) , showing that in the OAuth flow the shop is correctly bound into the HMAC, but in the webhook flow it is not.

### Impact Explanation
Apps commonly key their per-tenant persistence/session lookup, redaction/compliance handling, and business logic off `WebhookMetadata#shop` (this is the entire purpose of `Registry.process` passing `shop: request.shop` to the handler [7](#0-6) ). Because the shop attribution is unauthenticated relative to the signed payload, an attacker who is a legitimate merchant of the app (and thus can generate real signed webhook traffic for their own store) can forge webhook events that the host app will process as belonging to a different, victim shop — i.e., cross-tenant data/event injection using only their own valid install, not the app's `client_secret`. This satisfies the "cross-tenant access" criteria.

### Likelihood Explanation
Requires the attacker to be (or become) an installed merchant of the target app in order to obtain at least one genuinely-signed webhook body/HMAC pair, then replay it with a modified `shop-domain` header against the app's webhook receiver endpoint. Any developer using this gem exactly as documented (feeding headers/body from the HTTP request into `Webhooks::Request.new` and calling `Registry.process`) is affected, since the gem never validates that the `shop-domain` header corresponds to the entity whose secret produced the HMAC.

### Recommendation
Include the shop domain (and other trust-relevant headers, such as topic/webhook-id) in the bytes verified by the HMAC, or otherwise separately assert that `request.shop` corresponds to a shop with a known/expected relationship to the signing secret before dispatching to handlers. At minimum, document that host applications must independently validate `shop-domain` against session/install data before trusting it, since the HMAC does not cover it.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, using the app's real (shared) `client_secret`.
2. A legitimate webhook fires: body `B`, header `x-shopify-hmac-sha256: HMAC(secret, B)`, header `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker resends the same `B` and same HMAC header to the app's webhook endpoint, but with `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B)` — it passes [8](#0-7) .
5. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)` [7](#0-6) , causing the app to process attacker-controlled data under the victim shop's tenant context.
