I found a strong custody analog. The Aptos `account` module's signer-capability delegation message is missing the `chain_id` domain separator that its sibling rotation-capability message explicitly added to prevent exactly this kind of replay.

### Title
`offer_signer_capability`'s `SignerCapabilityOfferProofChallengeV2` omits `chain_id`, enabling cross-chain replay of account-takeover authorizations - (File: `aptos-move/framework/aptos-framework/sources/account/account.move`)

### Summary
`account::offer_signer_capability` authorizes granting a `SignerCapability` (full signing control over an account, and everything it owns — FA stores, objects, resource-account controllers, etc.) to a `recipient_address` based on a signature over `SignerCapabilityOfferProofChallengeV2`. Unlike its sibling `RotationCapabilityOfferProofChallengeV2`, which was explicitly upgraded to include `chain_id` "to prevent replaying the challenge message," the signer-capability challenge struct was never given the same fix.

### Finding Description [1](#0-0) 

The doc comment for `RotationCapabilityOfferProofChallengeV2` states explicitly:
> "This V2 struct adds the `chain_id` and `source_address` to the challenge message, which prevents replaying the challenge message." [2](#0-1) 

But the analogous `SignerCapabilityOfferProofChallengeV2`, used by `offer_signer_capability` — the function that hands out a `SignerCapability` (i.e., the ability to mint a `signer` for the victim account at will) — only carries `sequence_number`, `source_address`, and `recipient_address`; `chain_id` is absent: [3](#0-2) 

The signing/verification path confirms no chain binding is ever mixed in: [4](#0-3) [5](#0-4) 

`verify_signed_message` only checks the auth key and signature over the raw BCS-serialized struct; there is no chain-specific data anywhere in the digest.

### Impact Explanation
`SignerCapability` grants the holder the ability to call `account::create_signer_with_capability` and obtain an unrestricted `signer` for the victim account at any future time — this is full custody takeover: draining `CoinStore`/`FungibleStore` balances, transferring or burning owned objects, controlling any resource account or module that was built on top of that signer capability (e.g. `resource_account::retrieve_resource_account_cap` flows, `shared_account`, `common_account`, or any DeFi protocol's resource-account-held treasury). Because the same account address and sequence number can validly exist on more than one Aptos chain (deterministically-derived resource accounts via `account::create_resource_address` use no chain-specific input at all, and devnets/testnets are periodically reset to a fresh genesis), a signature authorizing a signer-capability grant on one chain can be replayed verbatim on another chain where the corresponding account (same address, same sequence number, same auth key) also exists, granting the attacker control of that account's assets without the owner's consent on that chain.

### Likelihood Explanation
Likelihood is constrained to specific but realistic scenarios: it requires the source account to exist with an identical address, sequence number, and authentication key on two distinct chain IDs. This is most plausible for (a) deterministically-derived resource accounts, since `create_resource_address` (`aptos-move/framework/aptos-framework/sources/account/account.move` lines ~1140-1145) is a pure function of the creator address and seed with no chain-id mixed in, and (b) devnet/testnet resets where fresh accounts are recreated from genesis. It does not require any privileged access — only a previously-published, validly-signed offer message from another chain instance of the same account.

### Recommendation
Add a `chain_id: u8` field to `SignerCapabilityOfferProofChallengeV2` (mirroring `RotationCapabilityOfferProofChallengeV2`), populate it with `chain_id::get()` in `offer_signer_capability`, and bump to a `V3` struct/migration path since this is a wire-format change consumed by off-chain signers (wallets/SDKs constructing the BCS message to sign).

### Proof of Concept
1. On Chain A (chain_id = 4), create account `S` deterministically via `account::create_resource_account(origin, seed)` so that `S`'s address depends only on `origin` and `seed`. `S` has `sequence_number = 0`.
2. `S`'s owner signs `SignerCapabilityOfferProofChallengeV2 { sequence_number: 0, source_address: S, recipient_address: attacker }` and submits `offer_signer_capability` — intended only for use on Chain A.
3. Suppose Chain B (chain_id = 2, e.g. a testnet reset to genesis, or another deployment of the same dApp with the same `origin` account and `seed`) also has an account at the same address `S` with `sequence_number = 0` (fully plausible since `create_resource_address` never mixes in chain id).
4. The attacker resubmits the exact same signed bytes (`signer_capability_sig_bytes`, `account_scheme`, `account_public_key_bytes`, `recipient_address`) to `offer_signer_capability` on Chain B. `verify_signed_message` succeeds because the BCS-serialized `SignerCapabilityOfferProofChallengeV2` is byte-for-byte identical across both chains — there is no `chain_id` in the struct to differentiate them.
5. The attacker now holds a valid signer-capability offer for `S` on Chain B and can call `account::create_authorized_signer`/hold custody-equivalent control, despite the owner never intending to authorize anything on Chain B.

    public entry fun offer_signer_capability(
        account: &signer,
        signer_capability_sig_bytes: vector<u8>,
        account_scheme: u8,
        account_public_key_bytes: vector<u8>,
        recipient_address: address
    ) acquires Account {
        let source_address = signer::address_of(account);
        ensure_resource_exists(source_address);
        assert!(exists_at(recipient_address), error::not_found(EACCOUNT_DOES_NOT_EXIST));

        // Proof that this account intends to delegate its signer capability to another account.
        let proof_challenge = SignerCapabilityOfferProofChallengeV2 {
            sequence_number: get_sequence_number(source_address),
            source_address,
            recipient_address,
        };
        verify_signed_message(
            source_address, account_scheme, account_public_key_bytes, signer_capability_sig_bytes, proof_challenge);

        // Update the existing signer capability offer or put in a new signer capability offer for the recipient.
        let account_resource = &mut Account[source_address];
        account_resource.signer_capability_offer.for.swap_or_fill(recipient_address);
    }

    public fun verify_signed_message<T: drop>(
        account: address,
        account_scheme: u8,
        account_public_key: vector<u8>,
        signed_message_bytes: vector<u8>,
        message: T,
    ) acquires Account {
        let auth_key = get_authentication_key(account);
        // Verify that the `SignerCapabilityOfferProofChallengeV2` has the right information and is signed by the account owner's key
        if (account_scheme == ED25519_SCHEME) {
            let pubkey = ed25519::new_unvalidated_public_key_from_bytes(account_public_key);
            let expected_auth_key = ed25519::unvalidated_public_key_to_authentication_key(&pubkey);
            assert!(
                auth_key == expected_auth_key,
                error::invalid_argument(EWRONG_CURRENT_PUBLIC_KEY),
            );

            let signer_capability_sig = ed25519::new_signature_from_bytes(signed_message_bytes);
            assert!(
                ed25519::signature_verify_strict_t(&signer_capability_sig, &pubkey, message),
                error::invalid_argument(EINVALID_PROOF_OF_KNOWLEDGE),
            );
        } else if (account_scheme == MULTI_ED25519_SCHEME) {
            let pubkey = multi_ed25519::new_unvalidated_public_key_from_bytes(account_public_key);
            let expected_auth_key = multi_ed25519::unvalidated_public_key_to_authentication_key(&pubkey);
            assert!(
                auth_key == expected_auth_key,
                error::invalid_argument(EWRONG_CURRENT_PUBLIC_KEY),
            );

            let signer_capability_sig = multi_ed25519::new_signature_from_bytes(signed_message_bytes);
            assert!(
                multi_ed25519::signature_verify_strict_t(&signer_capability_sig, &pubkey, message),
                error::invalid_argument(EINVALID_PROOF_OF_KNOWLEDGE),
            );
        } else {
            abort error::invalid_argument(EINVALID_SCHEME)
        };
    }
