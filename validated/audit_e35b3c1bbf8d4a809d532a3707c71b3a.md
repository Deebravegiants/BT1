### Title
Unbounded recursive `remove_ref` in `MemTrieNodeId` can stack-overflow the validator process during memtrie GC on attacker-shaped deep tries - ([File: core/store/src/trie/mem/node/encoding.rs])

### Finding Description
`MemTrieNodeId::remove_ref` decrements a node's refcount and, on reaching zero, deallocates the node and recursively calls itself on every child obtained from `node_ptr.view().iter_children()` (backed by `ChildrenView::iter`/`get`/`to_children` in `core/store/src/trie/mem/flexible_data/children.rs`): [1](#0-0) 

This is plain, non-tail, unbounded recursion: the call stack depth equals the length of the longest still-referenced chain of nodes from the deleted root down to leaves. `iter_children()` is implemented per node kind (`Leaf`→empty, `Extension`→one child, `Branch`/`BranchWithValue`→`ChildrenView::iter`) in `core/store/src/trie/mem/node/view.rs`: [2](#0-1) 

This recursive unref path is reached from `MemTries::delete_root`, which is invoked by `MemTries::delete_until_height` during normal GC of expired memtrie roots: [3](#0-2) 

`delete_until_height` in turn is called from block-processing GC logic (`ShardTries::delete_memtrie_roots_up_to_height`) after every finalized block, which is fully attacker-reachable in normal transaction/block processing, not an operator action: [4](#0-3) [5](#0-4) 

Regarding recursion depth in practice: because branch children are unreffed in a sequential loop (`for child in &children_to_unref { ... remove_ref(arena) }`), the recursion does not fan out multiplicatively per branch — each child's whole subtree is fully unwound (recursed into and returned from) before moving to the next sibling. So worst-case stack depth is bounded by the length of the single deepest root-to-leaf chain of nodes with a to-be-zeroed refcount, not by `NUM_CHILDREN^depth`. For a nibble-based Patricia-Merkle trie with extension-node compression, a chain of unique-prefix keys collapses shared prefixes into single `Extension` nodes, which somewhat mitigates (but does not eliminate) depth growth from key length; the worst case for depth is still driven by the number of nibble positions where keys diverge (i.e., the trie's structural depth, bounded above by max key length in nibbles). I was not able to conclusively determine the current value of `max_length_storage_key` (searches were truncated/inconclusive within available budget) or how deeply an attacker can practically force divergence at every nibble to defeat extension compression, so I cannot definitively bound the achievable recursion depth or the resulting stack usage relative to `neard`'s stack size.

### Impact Explanation
If achievable, the impact is a validator process crash via unbounded call-stack growth (denial of service) during GC of an attacker-shaped deep trie — this matches NEAR's "node panic / unbounded resource use" bounty class. However, this affects GC, which happens for every validator/node running memtries, not exclusively via attacker's direct trigger; the crash would occur on any node applying blocks past the relevant height, making it a shared-fate DoS if truly reachable at practical depths.

### Likelihood Explanation
Feasibility is uncertain without being able to confirm: (1) the actual value of `max_length_storage_key` (protocol parameter) that bounds attacker-controlled key length, (2) how much extension-node prefix compression reduces effective recursion depth versus raw key-length-driven nibble depth, and (3) the actual configured/default thread stack size for the block-processing/apply thread (only the `rayon` global pool's 8MB stack size in `neard/src/main.rs` was found; the main chain-processing thread's stack size was not confirmed). Without these values, I cannot establish that an attacker can force a recursion depth sufficient to exhaust a typical 8MB (or larger, OS-default) stack, which for simple recursive frames (tens to low hundreds of bytes each) generally requires depths in the tens of thousands to overflow. Given `max_length_storage_key` is very likely on the order of a few KB (implying at most a few thousand nibbles of raw depth, further reduced by extension compression), a stack overflow triggered purely by trie depth appears unlikely to be practically achievable, but this cannot be confirmed with the available evidence.

### Recommendation
Regardless of exploitability confirmation, converting `MemTrieNodeId::remove_ref`'s recursive child-unref traversal into an explicit iterative work-stack (as is already done elsewhere in the codebase, e.g. `state_parts.rs`'s `traverse_all_nodes` using an explicit `Vec` stack) would eliminate any dependency on call-stack depth and remove this entire class of risk, independent of key-length limits or extension-compression behavior.

### Proof of Concept
Given the inability to confirm `max_length_storage_key` and the actual worst-case recursion depth achievable under it, a definitive PoC cannot be constructed with confidence from the available context. A recommended validation plan for a follow-up investigation:
1. Confirm `max_length_storage_key` value in the active runtime config (`core/parameters/res/runtime_configs/parameters.yaml`).
2. Build an integration test using `MemTries` directly (as in `core/store/src/trie/mem/memtrie_update.rs` test helpers `insert_changes_to_memtrie`/`TestTries`) inserting a very large number of keys that maximize nibble-divergence depth (e.g., keys differing in every nibble at maximal allowed length) to build a deep un-compressible branch chain.
3. Call `tries.mem.delete_until_height(...)` to trigger the recursive `remove_ref` unwind, running the test under a constrained-stack thread (`std::thread::Builder::new().stack_size(N)`) matching production stack sizes, asserting no crash/stack overflow.
4. If overflow is observed at attacker-achievable depths, this elevates to a confirmed finding; if not, the recursion, while architecturally fragile, is not a practically exploitable DoS under current protocol limits.

    pub fn delete_until_height(&mut self, block_height: BlockHeight) {
        let to_delete = self
            .heights
            .extract_if(.., |height, _| *height < block_height)
            .flat_map(|(_, state_roots)| state_roots)
            .collect_vec();
        for state_root in to_delete {
            self.delete_root(&state_root);
        }
    }

    /// Bumps the refcount of the in-memory root for `state_root`. Returns
    /// an error if the root is not currently present in this memtrie.
    /// Pair every successful call with exactly one [`Self::delete_root`].
    pub(crate) fn add_root_ref(&mut self, state_root: &CryptoHash) -> Result<(), StorageError> {
        let ids = self.roots.get(state_root).ok_or_else(|| {
            StorageError::StorageInconsistentState(format!(
                "failed to find root node {:?} in memtrie when adding ref",
                state_root
            ))
        })?;
        let last_id = *ids.last().unwrap();
        last_id.add_ref(self.arena.memory_mut());
        Ok(())
    }

    pub fn delete_root(&mut self, state_root: &CryptoHash) {
        if let Some(ids) = self.roots.get_mut(state_root) {
            let last_id = ids.last().unwrap();
            let new_ref = last_id.remove_ref(&mut self.arena);
            if new_ref == 0 {
                ids.pop();
                if ids.is_empty() {
                    self.roots.remove(state_root);
                }
            }
        } else {
            debug_assert!(false, "Deleting non-existent root: {}", state_root);
        }
        MEMTRIE_NUM_ROOTS
            .with_label_values(&[&self.shard_uid.to_string()])
            .set(self.roots.len() as i64);
    }
