## Title
Unsanitized cross-chain calldata is decoded and dispatched as a privileged `RuntimeCall` with an attacker-selectable origin in `pallet-hyper-fungible-token` - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`pallet-hyper-fungible-token`'s `on_accept` handler decodes an optional `data` field from an incoming ISMP `Message` body into a `SubstrateCalldata { signature: Option<Vec<u8>>, runtime_call: Vec<u8> }` and unconditionally dispatches `runtime_call` as a live, privileged extrinsic on the destination chain. The only gate against arbitrary dispatch is the runtime's `BaseCallFilter`; the `origin` used for dispatch is derived directly from attacker-supplied bytes in the same untrusted message when no signature is supplied. This mirrors the wicked CVE-2026-44932 pattern: an untrusted external payload (there, DHCP options; here, the ISMP message `data` field carried by a relayed cross-chain request) is trusted and fed straight into a privileged execution sink without adequate binding/sanitization.

### Finding Description
In `modules/pallets/hyper-fungible-token/src/module.rs`, `on_accept` decodes the incoming request body into a `Message` and, if `message.data` is non-empty, decodes it as `SubstrateCalldata`: [1](#0-0) 

The origin used to dispatch the embedded `runtime_call` is chosen based on whether a signature was supplied: [2](#0-1) 

and the call is then decoded and dispatched with only a `BaseCallFilter` check: [3](#0-2) 

Two properties make this analogous to the wicked bug class:
1. **Untrusted external data reaches a privileged execution sink.** `runtime_call` is arbitrary, attacker-chosen SCALE-encoded bytes originating from a message relayed over ISMP — a relayer, not a privileged party, can permissionlessly submit this via `pallet_ismp::handle_unsigned`, as documented for the pallet (unsigned extrinsic, free execution, `AdminOrigin` not required): [4](#0-3) .
2. **The authorization/sanitization is optional and self-selected by the same untrusted payload.** When `substrate_data.signature` is `None`, the code trusts `message.from` — a field embedded in the very message it is trying to authorize — to select the dispatch origin, with no independent verification that the owner of that derived account authorized this specific `runtime_call`. Compare the signed branch, which at least binds signature to `(nonce, runtime_call)`, to the unsigned branch, which performs no equivalent binding.

This is the direct analog of `wicked` passing unsanitized DHCP option strings into a locally-executed script: here, unsanitized message bytes are passed into `Dispatchable::dispatch`, gated only by a call filter, not by a cryptographic proof that the resulting origin actually authorized that specific call.

### Impact Explanation
Successful exploitation lets a party who can drive traffic through the paired HFT contract on a source chain (a normal permissionless action — `send()` is public) cause execution of arbitrary, filter-permitted `RuntimeCall`s on the destination chain, with the dispatch origin selected from data inside the same message. This is "unauthorized app action" per the validation criteria: destination-chain dispatchables (governance-adjacent transfers, asset operations, etc., anything not excluded by `BaseCallFilter`) can be triggered without a call-specific signature, undermining the assumption that `RawOrigin::Signed(account)` implies that `account`'s owner authorized the specific call being executed.

### Likelihood Explanation
`send()` on the token bridge is a completely permissionless, low-cost action (just needs a small token transfer and a relayer fee), and delivery is achieved through the standard unsigned `handle_unsigned` message-execution path, requiring only a valid state/consensus proof — something any relayer can supply once the request is genuinely dispatched. No governance or privileged role is required to trigger the flow, making this a High-likelihood path once a peer HFT deployment is registered.

### Recommendation
Require the `SubstrateCalldata.signature` to always be present and to cryptographically bind `(nonce, runtime_call)` to the account that will be used as origin — remove the no-signature fallback that derives an origin straight from `message.from` without validating that its owner authorized this specific call. Additionally, tie `message.from` cryptographically to the entity relaying/originating the request rather than trusting raw bytes embedded in the message body.

### Proof of Concept
1. An attacker calls `send()` on the paired `HyperFungibleToken`/`pallet-hyper-fungible-token` deployment on a registered source chain, setting `SendParams.call_data` to an ABI/SCALE-encoded `SubstrateCalldata { signature: None, runtime_call: <arbitrary encoded RuntimeCall not excluded by BaseCallFilter> }` (as exercised, minus the malicious payload, in `modules/pallets/testsuite/src/tests/pallet_hyper_fungible_token.rs:255-322` which shows the full signed flow's mechanics working end-to-end via `on_accept`).
2. A relayer submits the resulting ISMP request through `pallet_ismp::handle_unsigned` with a valid state proof.
3. `HyperFungibleToken::on_accept` in `modules/pallets/hyper-fungible-token/src/module.rs:119-203` decodes `SubstrateCalldata`, takes the `signature: None` branch, derives `origin` from `message.from` via `EvmToSubstrate::convert`, and dispatches `runtime_call` under `RawOrigin::Signed(origin)` with no signature ever having authorized that specific call.
