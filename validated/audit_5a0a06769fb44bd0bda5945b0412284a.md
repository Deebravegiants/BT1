### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw request body, while the `shop` (and `topic`) values consumed by the registry/handler are read from separate, unauthenticated HTTP headers. This mirrors the root cause pattern in the referenced report: a value that is *acted upon* (there, the `exchangeRate` scale used in `withdrawCarry`'s accounting; here, the `shop` identity used to route/attribute webhook data) is not the value that is actually *covered/verified* by the security check (there, the wrong scaling constant; here, the HMAC only signs the body, not the shop header).

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw body: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from HTTP headers that are entirely outside the HMAC computation: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant identity passed to the handler: [4](#0-3) 

The equality being broken: `shop authenticated by HMAC == shop attributed to the processed data`. In fact only `raw_body == HMAC(raw_body, secret)` is verified; `shop` (the header value) is never part of that equality. An attacker who can obtain **any** valid `(raw_body, hmac)` pair signed with the app's secret — trivially, by triggering a legitimate webhook to their **own** installed shop (a webhook subscription they control, since `client_secret` is not required for this) — can then replay that exact body+HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain. `Utils::HmacValidator.validate` still returns true because it only checks the body bytes, and `Registry.process` will call the handler with `shop: <victim shop>` alongside the attacker-controlled body.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook delivery: it enables `cross-tenant access` — an attacker can inject data that a legitimate integrator's handler will process and persist/act upon *as if it originated from the victim's shop* (e.g., an app that syncs webhook payloads keyed by `data.shop` into that shop's tenant record). This matches the Critical/High criterion "cross-tenant access" in this gem's own verification code path (`Utils::HmacValidator` + `Webhooks::Registry`), not merely a downstream app oversight, because the gem itself supplies `shop` from the same `Request` object whose `hmac` check it exposes as the trust boundary.

### Likelihood Explanation
Requires only: (1) the attacker's own app installation with a legitimate webhook subscription (unprivileged, self-service), to obtain one valid `(body, hmac)` pair signed by the app's real `client_secret` without ever learning the secret itself, and (2) the ability to POST an HTTP request with arbitrary headers to the app's public webhook endpoint. No access token, no leaked credentials, and no privileged account are required — only a normal merchant/developer install of the app being attacked. This is a realistic and repeatable exploit path.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`) header values in the signable content used for webhook HMAC verification, or otherwise cryptographically bind them to the body before comparison, so that `Utils::HmacValidator.validate` fails if these header values are altered independently of the body. At minimum, document and/or enforce that `Registry.process` cross-checks `request.shop` against the caller's own record of installed shops before invoking the handler, and update `Webhooks::Request#to_signable_string` so the identity fields are part of the verified bytes.

### Proof of Concept
1. Install the target app as an attacker-controlled shop `attacker.myshopify.com` and register a webhook subscription (e.g., `orders/create`) with a callback pointed at your own capture endpoint, or via existing app functionality that emits webhooks.
2. Capture one legitimate delivery: raw body `B` and header `x-shopify-hmac-sha256: H`, where `H = Base64(HMAC-SHA256(client_secret, B))`, sent with `x-shopify-shop-domain: attacker.myshopify.com`.
3. Replay a POST to the app's webhook endpoint using the same body `B` and same `H`, but replace the shop-domain header with `x-shopify-shop-domain: victim.myshopify.com`.
4. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `request.to_signable_string` (== `B`) — this still matches `H`, so validation succeeds: [4](#0-3) 
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and attacker-chosen body content, despite the request never having been sent by or for `victim.myshopify.com`.
