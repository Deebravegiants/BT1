### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook shop-spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC that `Utils::HmacValidator.validate` checks in `Webhooks::Registry.process` authenticates the request body bytes only. The `shop` attribute (read from the `x-shopify-shop-domain` / `shopify-shop-domain` header) is never part of the signed data, yet it is passed straight into `WebhookMetadata` and handed to the app's webhook handler as the tenant identity for that payload. This breaks the intended binding `hmac_valid(body) == shop_is_authentic`.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

`hmac` is derived purely from the `hmac-sha256` header, and `to_signable_string` returns `@raw_body` — nothing else. `shop` is read independently from `shop-domain`/`x-shopify-shop-domain` header, which is not included anywhere in the signed content.

`HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it against the `hmac` field: [2](#0-1) 

`Registry.process` treats a passing HMAC check as authenticating the *entire* webhook, including the shop, and forwards `request.shop` (attacker-controlled header, unauthenticated) to the handler as the tenant key: [3](#0-2) 

Because Shopify signs webhooks for an app with the single, app-wide `api_secret_key` (the same secret is used across every shop that has the app installed — confirmed by `HmacValidator` using only `Context.api_secret_key`/`old_api_secret_key`, with no shop-specific key), any merchant who has legitimately installed the app on their own store can capture one authentic `(raw_body, hmac)` pair delivered to their webhook endpoint. Because `shop` is excluded from `to_signable_string`, that same `(raw_body, hmac)` pair remains valid for *any* `shop-domain` header value. The attacker can replay the captured request to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still returns `true`, and `Registry.process` calls the handler with `WebhookMetadata#shop` set to the victim's domain even though the payload actually originated from (and pertains to) the attacker's own shop.

This is the exact class of bug called out by the rules: a field acted on (`shop`, used as the tenant identity for dispatched webhook data) is not covered by the HMAC that is supposed to authenticate the request.

### Impact Explanation
An app that (as documented/intended by this gem's API) trusts `WebhookMetadata#shop` to select which tenant's data store or business logic to run against will process attacker-supplied body content under a different, victim shop's identity. This is a cross-tenant boundary violation: data belonging to/created by one shop can be attributed to and applied against another shop's session/records purely by forging one HTTP header, with no need for the victim's credentials, access token, or `client_secret`. This matches the Critical "cross-tenant access" impact category defined by the rules.

### Likelihood Explanation
Likelihood is realistic, not theoretical: any internet user can freely install a public app on their own development/trial store (a normal, unprivileged action), thereby receiving at least one genuine `(body, hmac)` pair for a webhook topic they control (e.g. `app/uninstalled`, `orders/create` with attacker-supplied order data). Because the webhook endpoint is a public HTTP endpoint that accepts headers as provided by the caller, and the gem performs no validation whatsoever tying `shop` to the signed content or to request origin (e.g. Shopify IP allow-listing), replaying the captured request with a modified `shop-domain` header is trivial and entirely within the gem's own webhook-verification code path — no host-application misconfiguration required.

### Recommendation
Include the `shop` (and ideally `topic`, `api_version`, `webhook_id`) in the HMAC-signed content, or otherwise cryptographically bind them to the request before trusting `request.shop`, e.g. by:
- Changing `Webhooks::Request#to_signable_string` to incorporate the shop/topic headers alongside the raw body (note: this requires coordinating with how Shopify computes the signature server-side, since Shopify only signs the raw body today — so at minimum, the gem should document/emit a strong warning that `shop` is unauthenticated and must not be used as a sole tenant-selection key), or
- Requiring host applications to cross-check `request.shop` against an independently verified value (e.g., a registered, expected shop for that specific webhook subscription/ID) before using it, and exposing an API to make that check easy and mandatory rather than optional.

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker.myshopify.com`.
2. Trigger a webhook delivery (e.g. update a product) and capture the raw POST body `B` and header `X-Shopify-Hmac-Sha256: H` sent to the app's webhook endpoint.
3. Replay to the same endpoint:
   ```
   POST /webhooks HTTP/1.1
   X-Shopify-Topic: products/update
   X-Shopify-Hmac-Sha256: H
   X-Shopify-Shop-Domain: victim-shop.myshopify.com   <-- forged
   X-Shopify-Webhook-Id: <any>
   X-Shopify-Api-Version: 2024-01

   B
   ```
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: ...)` is constructed by the host app from these headers; `Utils::HmacValidator.validate(request)` returns `true` because `to_signable_string` only hashes `B`, unaffected by the forged `Shop-Domain` header.
5. `Registry.process(request)` calls the registered handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, even though the payload content actually belongs to `attacker.myshopify.com`. [4](#0-3) [3](#0-2) [5](#0-4)
