### Title
Webhook `shop` attribution is not covered by the HMAC, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload from the raw body only, while the `shop-domain` header — the value used by `ShopifyAPI::Webhooks::Registry.process` to attribute the webhook to a specific merchant — is never included in the signed material. Anyone who can obtain one valid `(body, hmac)` pair for the app (e.g. by installing the app on their own store) can replay that exact body with a different `shop-domain` header to the app's webhook endpoint, and the signature will still validate, causing the app to process attacker-controlled data under a victim shop's identity.

### Finding Description
`Request#to_signable_string` returns only the raw request body: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cross-check against the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC strictly over `to_signable_string`, i.e. only the body: [3](#0-2) 

`Registry.process` accepts the request once the body-only HMAC passes, then dispatches to the topic handler using the unauthenticated `shop` value from the header: [4](#0-3) 

This breaks the intended identity binding: `hmac == HMAC(secret, body)` is verified, but the code actually *acts on* `shop`, which is not part of the signed material. In other words, the binding the code relies on (`shop` is authentic because the whole request is HMAC-verified) does not hold — only `body` is authentic. Since a single app's `client_secret` is shared across every merchant that installs it, any store owner can generate a legitimately-signed `(body, hmac)` pair for their own shop and then present that same pair to the app's webhook endpoint with the `shop-domain` header rewritten to a different, victim tenant. The signature check still succeeds because it never examined the header, and `WebhookMetadata.new(shop: request.shop, ...)` propagates the attacker-chosen shop into the app's handler logic.

### Impact Explanation
This is a cross-tenant identity confusion inside the gem's own webhook-processing code: the shop attribution that host applications key their per-merchant side effects on (e.g., updating that merchant's order/subscription/inventory records, or deciding which merchant's access token/session to use for follow-up API calls) can be forged by any party who has a valid app installation of their own. This can lead to processing/attributing another merchant's data or state changes under an attacker-chosen shop identity — a cross-tenant access issue.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the target app on some shop (an "unprivileged" action any merchant can do) to obtain one legitimately-signed webhook body/HMAC pair, and then send an HTTP request to the app's public webhook endpoint with a forged `shop-domain` header carrying the same body/HMAC. No access to `api_secret_key`, access tokens, or the victim's credentials is needed.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header values in the signed material checked by `HmacValidator`, or otherwise cryptographically bind the asserted shop to the verified body (e.g., require the caller to independently confirm that the request's `shop` corresponds to a shop with an active, matching installation/access token before trusting `request.shop`). At minimum, document that `request.shop` is unauthenticated and must not be trusted for tenant attribution without an additional binding check.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com`, triggering a legitimate webhook delivery with body `B` and header `x-shopify-hmac-sha256: H = HMAC(secret, B)`.
2. Attacker captures this `(B, H)` pair.
3. Attacker sends a POST to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged, still valid because HMAC only signs `B`), and header `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` returns `true` (it only checks `B` against `H`).
5. `Registry.process` invokes the topic handler with `shop: "victim.myshopify.com"`, causing the host application to act on/attribute attacker-controlled event data as if it originated from the victim tenant.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
