## Analog Found: `pallet-assets::do_approve_transfer` does not check the owner account's `AccountStatus` (blocked/frozen)

### Title
`approve_transfer`/`do_approve_transfer` in `pallet-assets` allows creating a delegated approval for an owner account that is individually blocked, without checking `AccountStatus` - (File: `substrate/frame/assets/src/functions.rs`)

### Summary
This mirrors the KUMA `approve()` finding: an "approve" style entry point checks a *global* state flag but not the *per-account* block/blacklist flag of the actual asset owner, creating the same class of inconsistency the C4 judge flagged.

### Finding Description
`pallet-assets` tracks two independent freeze concepts:
- Asset-level: `AssetDetails.status: AssetStatus` (Live/Frozen/Destroying).
- Account-level: `AssetAccount.status: AccountStatus` with `Liquid`, `Frozen`, and `Blocked` variants, where `Blocked` accounts "cannot receive and transfer the assets" [1](#0-0) .

`do_approve_transfer`, which backs the `approve_transfer` extrinsic and `approve()` in the ERC-20 precompile, only checks the **asset-level** status: [2](#0-1) 
It never inspects the `owner`'s `AssetAccount.status` (i.e., whether the owner has been individually `Blocked`/`Frozen` via `T::Freezer`/`block`), before creating or topping up an `Approvals` entry and reserving/adjusting a deposit [3](#0-2) .

This is structurally identical to the KUMA bug: `approve()`/`approve_transfer()` only validates a coarse-grained condition (asset-wide `Live` status, analogous to checking `msg.sender`/`to` blacklist) but omits the fine-grained, owner-specific block check that the actual money-movement path (`do_transfer_approved` / `transfer_and_die`) is expected to enforce.

### Impact Explanation
Functionally low: because `do_transfer_approved` ultimately calls `transfer_and_die`, which goes through the standard balance-mutation path that consults `AccountStatus`/`T::Freezer` for the owner, an actual value transfer by the delegate should still be rejected even though the approval itself succeeded [4](#0-3) . This is exactly the same situation the C4 judge described for KUMA: "a transfer would still be broken... I agree with Medium Severity" purely due to the *inconsistency* in enforcement, not because funds can actually move. The only observable consequences here are: an `ApprovedTransfer` event/state entry is created for a blocked account, and a deposit is reserved from a blocked owner's `Currency` balance, which is a bookkeeping/consistency issue rather than a fund-theft vector.

### Likelihood Explanation
Requires an owner to have pre-authorized a delegate (via `approve_transfer`) before being blocked, then have any account (owner, delegate, or third party depending on config) call `approve_transfer` again — this is a normal, unprivileged, permissionless call path (`Self::do_approve_transfer` is reachable directly via the `approve_transfer` extrinsic and via the revive ERC-20 precompile's `approve()`) [5](#0-4) [6](#0-5) .

### Recommendation
Add an explicit check in `do_approve_transfer` that the `owner`'s `AssetAccount.status` is not `Blocked` (and possibly not `Frozen`), mirroring how `Frozen`/`Live` is enforced for the asset overall, e.g. `ensure!(!Account::<T,I>::get(&id, owner).map(|a| a.status.is_blocked()).unwrap_or(false), Error::<T,I>::AccountBlocked)`.

### Proof of Concept
1. Owner `A` calls `approve_transfer(asset_id, delegate=B, amount)` while `A`'s asset account is `Liquid`.
2. `A`'s asset account is later set to `Blocked` (e.g., via a permissioned block/freeze call using `T::Freezer` semantics).
3. `B` (or `A`) calls `approve_transfer(asset_id, delegate=C, amount)` again (top-up) — this succeeds because `do_approve_transfer` only checks `d.status == AssetStatus::Live`, never `A`'s per-account `Blocked` status [7](#0-6) .
4. An `ApprovedTransfer` event is emitted and a deposit is reserved from the blocked account, despite the account being administratively blocked — an inconsistency, though the follow-up `transfer_approved` should still fail at the balance-movement stage.

**Caveat:** I could not fully verify within this session whether `transfer_and_die`/`can_withdraw` definitively rejects `Blocked` accounts in all code paths (the `block` extrinsic implementation in `substrate/frame/assets/src/lib.rs` and its interaction with `AccountStatus::Blocked` enforcement in the transfer path were not fully traced). If `do_transfer_approved` also fails to check `AccountStatus::Blocked` for the *owner* specifically (as opposed to relying on `T::Freezer`), the impact could be higher than "inconsistency only." This would need confirmation via a full read of `substrate/frame/assets/src/lib.rs` `block`/`freeze` extrinsics and `functions.rs::transfer_and_die`/`can_withdraw`.

/// The status of an asset account.
#[derive(Clone, Encode, Decode, Eq, PartialEq, Debug, MaxEncodedLen, TypeInfo)]
pub enum AccountStatus {
	/// Asset account can receive and transfer the assets.
	Liquid,
	/// Asset account cannot transfer the assets.
	Frozen,
	/// Asset account cannot receive and transfer the assets.
	Blocked,
}
impl AccountStatus {
	/// Returns `true` if frozen or blocked.
	pub fn is_frozen(&self) -> bool {
		matches!(self, AccountStatus::Frozen | AccountStatus::Blocked)
	}
	/// Returns `true` if blocked.
	pub fn is_blocked(&self) -> bool {
		matches!(self, AccountStatus::Blocked)
	}
