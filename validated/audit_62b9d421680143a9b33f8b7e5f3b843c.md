### Title
Webhook `shop` (and `topic`/`webhook-id`) attribution is not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body. The shop that the webhook is attributed to, however, is read from an HTTP header that is not part of the signed payload. Because the HMAC secret (`Context.api_secret_key`/`old_api_secret_key`) is a single app-level secret shared across every shop that has installed the app, any party who can legitimately obtain one valid `(raw_body, hmac)` pair (e.g., by installing the app on their own store and receiving a genuine webhook) can replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` (or `x-shopify-shop-domain`) header value. The HMAC check still succeeds, and the webhook handler is invoked with attacker-chosen `shop` (and `webhook_id`, `topic` via header swap on the appropriate body) — breaking the tenant binding that host applications rely on when routing/handling webhook data.

### Finding Description
`Registry.process` validates the request with: [1](#0-0) 

`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only the raw body — none of the Shopify headers are included in the signed material: [3](#0-2) 

Yet `shop`, `topic`, and `webhook_id` — all read directly from unauthenticated headers — are what get passed to the app's handler as the tenant/context identity: [4](#0-3) 

This is the same identity-binding-break class as the analog report: the field that downstream logic *acts on* (the `shop` used to attribute and dispatch the webhook payload) is not the field that the HMAC actually *authenticates* (only `raw_body`). Compare this to `Auth::Oauth::AuthQuery`, where `shop` IS included in `to_signable_string` and thus is properly bound to the signature: [5](#0-4) 

Because the app-level `api_secret_key` is identical for every shop using the app (it's not a per-shop secret), a valid `(body, hmac)` pair obtained from a legitimate webhook delivered to attacker's own shop remains valid HMAC-wise no matter which `shop-domain` header accompanies it.

### Impact Explanation
This breaks tenant isolation (cross-tenant access), which is a Critical-severity outcome under the given rubric. Any unprivileged merchant who has installed the target app (and therefore legitimately receives real webhook deliveries with valid HMACs) can:
- Replay a captured `(raw_body, hmac)` webhook pair while swapping the `shop-domain` header to a victim shop's domain, causing the app to process/store attacker-controlled data as if it came from the victim tenant.
- This is especially damaging for mandatory compliance webhooks (`shop/redact`, `customers/redact`, `customers/data_request`) or lifecycle webhooks (`app/uninstalled`) — an attacker could trigger data-deletion or de-provisioning logic against a shop they do not own/control, since the handler trusts `data.shop` from `WebhookMetadata` without any cryptographic binding to that value.

### Likelihood Explanation
Likelihood is realistic but requires the attacker to be an app user themselves (install the app on their own/any shop to receive at least one genuine webhook delivery and its HMAC), which is an "unprivileged internet user" scenario consistent with the given threat model (no `api_secret_key`, no access token, and no privileged account of the *victim* shop is needed — only attacker's own valid install). The victim shop domain is often guessable/known (`{shop}.myshopify.com`), and any of the mandatory/standard webhook topics can be leveraged if the target app's handler logic keys off `data.shop` for authorization or attribution decisions, which is the documented/expected usage pattern of `WebhookMetadata`.

### Recommendation
Bind the shop (and ideally topic/webhook id/api-version) into the signed material that is verified, or otherwise cryptographically tie the header-derived shop to the authenticated request:
- At minimum, document and enforce that `Registry.process` must validate `request.shop` against an expected/known shop context supplied by the caller (not solely trust the header), or
- Extend `to_signable_string` to include the relevant Shopify headers (topic, shop-domain, webhook-id, api-version) so that tampering with any of them invalidates the HMAC, mirroring how `AuthQuery#to_signable_string` binds `shop` into the OAuth callback HMAC.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`, and legitimately receives a real webhook, e.g., `customers/redact`, with headers:
   - `X-Shopify-Topic: customers/redact`
   - `X-Shopify-Hmac-Sha256: <valid-base64-hmac-of-body>`
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - raw body: `{"shop_id":123,"shop_domain":"attacker-shop.myshopify.com", ...}`
2. Attacker resends the exact same raw body and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds a request object; `to_signable_string` returns only `raw_body`, so `Utils::HmacValidator.validate(request)` at `lib/shopify_api/webhooks/registry.rb:190` succeeds (same body/secret as before).
4. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic: "customers/redact", shop: "victim-shop.myshopify.com", body: ..., ...))`, causing the app to execute redaction/compliance logic attributed to `victim-shop.myshopify.com`, a shop the attacker never legitimately received a webhook for.
