### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing shop-spoofed replay of legitimately-signed webhook payloads - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw request body, while the `shop` (tenant) identifier is read from an HTTP header that is never part of the signed material. `ShopifyAPI::Webhooks::Registry.process` validates only that signable string, then hands the *unauthenticated* header-derived `shop` value to the app's webhook handler as if it were verified. Because a single `client_secret` (and thus a single HMAC key) is shared by an app across all shops that install it, any shop that legitimately receives real webhooks for that app can capture a validly-signed body/HMAC pair and replay it to the host application with an arbitrary `shop-domain` header, causing the host app to process attacker-controlled data under a victim shop's identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cross-check against the signed body: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then immediately trusts `request.shop` (and other headers) to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

The equality that should hold — "the shop bound by the HMAC" == "the shop the handler acts on" — does not: `HmacValidator.validate(request)` only proves `HMAC(client_secret, raw_body)` matches, using the same `Context.api_secret_key` for every shop that has installed the app: [4](#0-3) 

Since the key is shared across tenants and the signed content excludes `shop-domain`, `topic`, and `webhook-id`, any party who can obtain one authentic `(raw_body, hmac)` pair (e.g., an unprivileged user who installs the app on their own store and receives real webhooks) can resend that exact body/HMAC pair to the app's webhook endpoint with a forged `shop-domain` header naming a different, victim shop. `HmacValidator.validate` still returns `true`, and the handler is invoked believing the event originated from the victim shop.

### Impact Explanation
This breaks the tenant/shop identity binding that host applications rely on to attribute webhook data to the correct merchant. Depending on how a host app uses the `shop` field from `WebhookMetadata` (e.g., to look up/update per-shop records, trigger `app/uninstalled` cleanup, process `shop/redact` or `customers/redact` compliance actions, or update billing/subscription state), this can result in cross-tenant data corruption or spoofed compliance/administrative actions against a shop the attacker does not control — this falls under "cross-tenant access," which the rules classify as Critical impact.

### Likelihood Explanation
Exploitation requires only an "unprivileged internet user" capability explicitly in scope: the attacker installs the target app on their own (attacker-controlled) shop, which is a normal, self-service action requiring no privileged credentials, TLS interception, or leaked secrets. They then capture one authentic webhook delivery (raw body + `X-Shopify-Hmac-SHA256`) sent by Shopify for their own shop, and replay that exact body/HMAC to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. No knowledge of `client_secret` or the victim's credentials is needed. This is straightforward and repeatable for any webhook topic the attacker's own shop can trigger.

### Recommendation
Bind the tenant identity to the verified content instead of trusting an unauthenticated header:
- Include `shop-domain` (and ideally `topic`/`webhook-id`) in the HMAC-signable string, or
- Cross-validate `request.shop` against per-shop expectations before invoking the handler (e.g., require the host app to verify the shop has an active, matching session/webhook registration id before trusting the header), and
- Document prominently that `Request#shop` is derived from an unauthenticated header and must not be used as the sole tenant key without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`.
2. Shopify sends a real webhook to the app's endpoint with body `B` and header `X-Shopify-Hmac-SHA256: H`, where `H = Base64(HMAC_SHA256(client_secret, B))`. Attacker captures `(B, H)`.
3. Attacker crafts a new HTTP POST to the same webhook endpoint:
   - Body: `B` (unchanged)
   - Header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid since only body is signed)
   - Header `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (forged)
   - Header `X-Shopify-Topic`: attacker's choice (also unsigned, e.g. `app/uninstalled` or `shop/redact`)
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(client_secret, B) == H`: [5](#0-4) 
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host app to act as though the event came from the victim shop.
