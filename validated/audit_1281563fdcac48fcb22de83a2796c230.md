### Title
Webhook Shop-Domain Header Not Covered by HMAC Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` identifier used to attribute an inbound webhook to a specific merchant from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature validated by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body. The shop identity is therefore not bound to the cryptographic signature, allowing a low-privileged actor who possesses one genuine, validly-signed webhook (e.g., delivered to their own installed shop) to replay the same body/HMAC pair while substituting an arbitrary `shop-domain` header, causing the app to process the webhook as if it originated from a different tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read directly from an unauthenticated header with no cryptographic binding to the signed payload: [2](#0-1) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the raw body) and the app's `api_secret_key`, using `OpenSSL.secure_compare` against the received HMAC — it never incorporates `shop`, `topic`, or `webhook_id`: [3](#0-2) 

`Registry.process` trusts this validation and then forwards `request.shop` straight into the `WebhookMetadata` passed to the app's handler, without any secondary check that the shop matches the body/signature pairing: [4](#0-3) 

Because the HMAC is computed with the app-wide `api_secret_key` and does not incorporate the shop domain, **any** valid `(raw_body, hmac)` pair produced for one shop remains cryptographically valid when replayed with a different `shop-domain` header. This breaks the identity binding: `shop asserted by the header == shop actually authenticated by the HMAC` does not hold, since the HMAC authenticates only the body's integrity/origin (i.e., that Shopify produced it), not the tenant to which it was addressed.

### Impact Explanation
A merchant who has installed the app (an unprivileged actor relative to other merchants' data) receives real, validly-signed webhooks for their own shop. They can capture such a payload and replay it against the app's public webhook endpoint with a forged `X-Shopify-Shop-Domain` header naming a victim shop. Since `ShopifyAPI` reports the signature as valid, the host application will process the event as authentic and attribute it to the victim tenant — e.g., invoking `customers/data_request`, `customers/redact`, `shop/redact`, or any subscribed topic's handler keyed by `data.shop`, potentially causing cross-tenant data operations, incorrect redaction/compliance actions, or business-logic execution against the wrong merchant. This constitutes cross-tenant access facilitated entirely by this gem's webhook verification primitive, which does not bind the asserted shop to the authenticated bytes.

### Likelihood Explanation
Exploitation requires no access to `api_secret_key`: only capture/replay of one legitimately-delivered webhook (which any app-installing merchant naturally receives) and the ability to send an HTTP POST with modified headers to the app's public webhook endpoint — both squarely within reach of an unprivileged/low-privileged actor.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signable content verified against the HMAC, or otherwise cryptographically bind `request.shop` to the validated signature (e.g., require the host application to independently confirm the shop against a known/expected tenant before using `request.shop`, and document this requirement prominently). At minimum, `Registry.process` should not treat HMAC validity as proof of the `shop` header's authenticity.

### Proof of Concept
1. As a merchant, install the app on `attacker-shop.myshopify.com` and capture a real webhook delivery: raw body `B` with header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the app's shared `api_secret_key`) and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Replay the identical `B` and `H` to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and matches `H` — validation succeeds: [4](#0-3) 
4. The handler is invoked with `WebhookMetadata` whose `shop` is `victim-shop.myshopify.com`, even though the payload/signature originated from `attacker-shop`, causing the app to process the event as belonging to the victim tenant.
