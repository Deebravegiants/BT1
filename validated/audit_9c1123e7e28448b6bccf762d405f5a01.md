### Title
Missing shop-domain validation in `Oauth.validate_auth_callback` allows `client_secret` exfiltration to attacker-controlled host - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds a session from the raw, unvalidated `auth_query.shop` value and uses it to construct the base URI for the server-to-server `POST /admin/oauth/access_token` request that carries `Context.api_secret_key`, without ever routing `shop` through `Utils::ShopValidator.sanitize!`, unlike every sibling OAuth entry point in the same module tree.

### Finding Description
`Oauth.validate_auth_callback` takes an `AuthQuery` and, after HMAC verification, does: [1](#0-0) 
It never calls `Utils::ShopValidator.sanitize!`/`sanitize_shop_domain` on `auth_query.shop` before using it to build `null_session = Auth::Session.new(shop: auth_query.shop)`, which is then handed to `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")`.

`HttpClient` derives the outbound request host directly from `session.shop`: [2](#0-1) 
That request body contains `client_secret: Context.api_secret_key`: [3](#0-2) 

Compare this to every other OAuth code path in the gem, which explicitly sanitizes `shop` before it is used to build the host that receives `client_secret`: [4](#0-3) [5](#0-4) 
`ShopValidator.sanitize!` exists specifically to guard against attacker-controlled domains (`TRUSTED_SHOPIFY_DOMAINS` allow-list, lookalike domain rejection, userinfo/`@`-injection rejection, path-suffix tricks, etc.): [6](#0-5) [7](#0-6) 

The binding that should hold is: `hmac-authenticated shop bytes == host that receives client_secret`. `validate_auth_callback` does verify the HMAC over the exact `shop` string via `AuthQuery#to_signable_string`/`HmacValidator`, so in the documented flow (where the app constructs `AuthQuery` strictly from Shopify's own signed redirect parameters and nothing else) the HMAC does bind `shop` to a value Shopify itself signed with `Context.api_secret_key`. Under that narrow assumption, forging an arbitrary `shop` requires knowing `api_secret_key`, which is out of scope.

However, this only holds if the *entire* `AuthQuery` payload — including `shop` — is taken verbatim, byte-for-byte, from Shopify's redirect and never merged with other request parameters. The gem's own documented usage pattern builds `AuthQuery` from **all** symbolized request parameters (`request.parameters.symbolize_keys.except(:controller, :action)`), the exact bytes of which are controlled by whatever routing/param-merging behavior the host framework performs: [8](#0-7) 
This makes `shop` the one field in the callback that is both (a) required to exactly equal what Shopify signed, and (b) used unsanitized to pick the destination host for a request carrying `client_secret` — with no independent defense-in-depth check inside the gem itself, unlike the client-credentials/refresh-token/token-exchange paths which all call `ShopValidator.sanitize!` regardless of any other signature check.

### Impact Explanation
If `shop` bytes used for HMAC verification and `shop` bytes used to pick the access-token exchange host can ever diverge (e.g., due to host-application param merging/duplicate-key handling before constructing `AuthQuery`, or via `URI.encode_www_form`/`CGI.parse` canonicalization differences between how the HMAC is verified and how the value is later consumed as a `Host`), the app's `client_secret` — together with the authorization `code` — would be POSTed to an attacker-controlled host, granting the attacker the ability to redeem the code for a merchant's real access token. This is Critical: exfiltration of the app's `client_secret`/access token via SSRF-style credential leakage to a non-Shopify host.

### Likelihood Explanation
Low-to-Medium. Exploitation requires a discrepancy between the bytes HMAC-verified by `HmacValidator`/`AuthQuery#to_signable_string` and the bytes actually stored as `auth_query.shop` when constructed by the host application from raw request parameters (e.g., duplicate `shop` params, array-vs-scalar parsing differences, or framework param merging), since a single well-formed callback cannot be forged without `api_secret_key`. It is a real, code-level gap — this is the only OAuth entry point in the gem that skips `ShopValidator.sanitize!` on `shop` before using it to route a `client_secret`-bearing request — but it is contingent on how the surrounding web framework parses/merges query parameters, which the gem does not control.

### Recommendation
Call `Utils::ShopValidator.sanitize!(auth_query.shop)` in `Oauth.validate_auth_callback` before constructing `null_session`/`Session.from`, exactly as is already done in `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and `TokenExchange.exchange_token`, so the host that receives `client_secret` is always constrained to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` regardless of any upstream parameter-handling ambiguity.

### Proof of Concept
Conceptual (cannot be fully demonstrated without a host application's exact param-merging behavior, since a standalone forged HMAC is not feasible without `api_secret_key`):
1. Attacker submits a callback request to the app's OAuth callback route with duplicate/ambiguous `shop`-like parameters such that the value the host framework uses to populate `AuthQuery#shop` differs from the exact bytes Shopify signed and that were used during `HmacValidator.validate` (this depends on the framework's parameter parsing, e.g. `request.parameters.symbolize_keys`, `CGI.parse`, or Rack query-string handling with repeated keys).
2. `Utils::HmacValidator.validate(auth_query)` succeeds because it recomputes over `auth_query.shop` (the manipulated value), matching what the attacker crafted to still equal the originally-signed string, if the divergence is introduced only at the point of populating `AuthQuery#shop` vs. what `to_signable_string` re-serializes.
3. `validate_auth_callback` builds `null_session = Auth::Session.new(shop: auth_query.shop)` with the attacker-influenced `shop`, and `Clients::HttpClient` sends `POST https://#{attacker_shop}/admin/oauth/access_token` with `client_secret: Context.api_secret_key` and the authorization `code` in the body: [9](#0-8) [2](#0-1) 
4. The attacker-controlled host receives the app's `client_secret` and can subsequently redeem the `code` itself against Shopify's real token endpoint to obtain the merchant's access token.

      TRUSTED_SHOPIFY_DOMAINS = T.let(
        [
          "shopify.com",
          "myshopify.io",
          "myshopify.com",
          "spin.dev",
          "shop.dev",
        ].freeze,
        T::Array[String],
      )

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
