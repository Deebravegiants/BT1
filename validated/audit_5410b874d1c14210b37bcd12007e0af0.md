### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) identity fields are trusted from unauthenticated headers while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`), `topic`, `webhook_id`, and `api_version` entirely from HTTP headers, but `Utils::HmacValidator.validate` only verifies the HMAC over `to_signable_string`, which returns just `@raw_body`. The headers that determine *which shop* the webhook is attributed to are never covered by the signature check.

### Finding Description
`Registry.process` gates webhook handling on HMAC validity: [1](#0-0) 

`Utils::HmacValidator.validate` computes/compares the HMAC using `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`: [3](#0-2) 

Yet `shop`, `topic`, `webhook_id`, and `api_version` — the values that identify *which merchant/tenant* and *which event* the payload belongs to — are pulled straight from request headers with no cryptographic binding to the signed body: [4](#0-3) 

The equality this breaks is: `shop authenticated by HMAC == shop used to dispatch/process the webhook`. In reality, the gem only proves `HMAC(secret, raw_body) == received_hmac`; it does **not** prove `HMAC(secret, raw_body) == received_hmac` *for the specific (shop, topic) pair* — those fields are attacker-controllable header values that ride along unchecked.

### Impact Explanation
A user who legitimately installs the app on their own store (an ordinary, unprivileged action) will receive genuine webhook deliveries — real `raw_body` + real `hmac-sha256` — signed with the app's shared `api_secret_key`. Because the signature covers only the body, that same attacker can replay the identical `raw_body`/`hmac-sha256` pair to the app's shared webhook endpoint while substituting the `shopify-shop-domain` (and/or `shopify-topic`, `shopify-webhook-id`) header for a different, victim shop. `HmacValidator.validate` will still pass (body and HMAC still match each other), and `Registry.process` will dispatch the handler with `shop: request.shop` set to the attacker-chosen victim domain: [1](#0-0) 

Any downstream app logic that trusts `WebhookMetadata#shop`/`topic` to select which tenant's session/data to read or write (a normal pattern, since this is the only tenant signal the gem exposes for webhooks) can be tricked into acting on data mislabeled as belonging to another shop — i.e., cross-tenant confusion driven entirely by an unauthenticated header value. This matches the Critical "cross-tenant access" bucket in scope, since the identity binding (shop ↔ signed payload) that the app relies on for tenant isolation is not actually enforced by the gem.

### Likelihood Explanation
Any user can create a Shopify development/test store, install the app, and trigger a webhook to capture one valid `(raw_body, hmac)` pair for a topic they control (e.g., `orders/create` with attacker-supplied order content). No access to `api_secret_key`, access tokens, or privileged accounts is needed — only the ability to POST to the app's public webhook endpoint with modified headers, which any internet user can do. The only constraint is that the *topic* and *body shape* must match something the attacker can produce from their own store, but the `shop` field itself is completely unauthenticated, so likelihood of exploiting the identity-binding gap is high wherever an app keys logic off `WebhookMetadata#shop` or `#topic`.

### Recommendation
Bind the routing-critical fields (`shop`, `topic`, at minimum) into the signable content, or otherwise avoid trusting the header-derived `shop`/`topic` for anything security-relevant unless independently corroborated (e.g., cross-check against the actual authenticated session/shop domain, and validate that the topic in the payload matches the topic asserted in headers). At minimum, document/enforce that `WebhookMetadata#shop` and `#topic` must never be used to select tenant context without an additional server-side check that the `shop` domain matches an app-known, previously-authorized shop for which this exact `topic`/webhook subscription was registered.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate `orders/create` webhook: raw body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the shared `api_secret_key`), `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker POSTs the same `B` and `H` to the app's shared webhook endpoint, but replaces the header with `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and compares to `H` — this succeeds because neither the shop header nor topic is part of `to_signable_string`: [3](#0-2) 
4. The handler is invoked with `shop: "victim-shop.myshopify.com"` even though the payload content actually originated from the attacker's own store, demonstrating the broken binding between the authenticated bytes (`raw_body`+HMAC) and the tenant identity used by the app. [5](#0-4)

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
