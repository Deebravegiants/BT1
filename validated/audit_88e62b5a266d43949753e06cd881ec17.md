### Title
Webhook `shop` domain is trusted from an unauthenticated header while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` (used for HMAC verification) returns only `@raw_body`, while `Request#shop` reads the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header directly, a field that is never part of the signed bytes. `Registry.process` verifies the HMAC over the body only and then forwards `request.shop` straight to the handler's `WebhookMetadata`, so the tenant identity used by the host application is not actually bound to the cryptographic authentication check.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to `verifiable_query.hmac`: [1](#0-0) 

For webhooks, `to_signable_string` is defined as simply the raw request body: [2](#0-1) 

`shop` (the tenant identifier) is instead derived from the `shopify-shop-domain` HTTP header, which is not included anywhere in the signable string: [3](#0-2) 

`Registry.process` verifies the HMAC (over the body only), then immediately trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` — none of which are HMAC-covered — and passes them to the registered handler: [4](#0-3) 

This is the exact bug class described in the external report generalized to this gem's webhook path: an identity-binding field (`shop`) is acted upon (passed to the handler as the tenant context) but is not covered by the same authentication mechanism (HMAC) that is used to prove the request is genuinely from Shopify. The equality that should hold — "the shop whose secret authenticated this payload" == "the shop the application acts on behalf of" — is not enforced. Anyone who can present a body+HMAC pair that verifies for their own shop (e.g., any merchant who installed the app and captured/replayed one of their own legitimate webhook deliveries) can swap in a different `shopify-shop-domain` header value and the HMAC check will still pass, because the header is never hashed.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` (as populated by this gem) to determine which tenant's data/session to act on — which is the gem's documented and intended usage pattern (see `docs/usage/webhooks.md` and `WebhookHandler`) — an attacker with legitimate access to their own shop's genuine webhook deliveries can forge the shop-domain header to have the application process, store, or act on webhook data under a different (victim) shop's identity. This is a cross-tenant data/identity confusion vulnerability arising directly from this gem's own `Request`/`Registry` implementation, not from host-application misuse, since the gem itself performs the HMAC verification and hands back an unauthenticated `shop` value as if it were verified.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one genuinely-signed webhook body+HMAC pair for a shop they control (any real or trial merchant installing the app can obtain this by triggering webhooks for their own store) and the ability to replay an HTTP request to the app's webhook endpoint with a modified `shopify-shop-domain` header. No access to `api_secret_key`, access tokens, or Shopify's own infrastructure is required. This is a realistic, low-barrier attack path for any developer/merchant who has installed the app being defended.

### Recommendation
Include the shop domain (and ideally topic/webhook-id/api-version) inside the HMAC-signed material, or otherwise cryptographically bind the header-derived `shop` value to the verified payload before it is exposed via `WebhookMetadata`. At minimum, `Request#to_signable_string` should not be the sole basis of trust for `Request#shop`; `Registry.process` should reject/flag any webhook whose header-provided identity cannot be corroborated against the HMAC-covered content, matching Shopify's actual webhook verification guidance to treat header values as unauthenticated until independently confirmed.

### Proof of Concept
1. Attacker installs the target app on a shop they control, `attacker-shop.myshopify.com`, and receives a real webhook: body `B`, header `shopify-shop-domain: attacker-shop.myshopify.com`, header `shopify-hmac-sha256: HMAC(secret, B)`.
2. Attacker resends this exact HTTP request to the app's webhook endpoint but changes only the header `shopify-shop-domain` to `victim-shop.myshopify.com` (body `B` and `hmac-sha256` header untouched).
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` — this still matches because `to_signable_string` only returns `@raw_body`: [5](#0-4) 
4. Validation succeeds; `request.shop` now returns `"victim-shop.myshopify.com"` and is forwarded to the handler as the authenticated tenant, even though the HMAC never covered that value: [6](#0-5) 
5. The application's webhook handler processes attacker-controlled body content under the victim shop's identity — a cross-tenant confusion made possible entirely by this gem's own (mis)binding of the `shop` header outside the HMAC scope.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
