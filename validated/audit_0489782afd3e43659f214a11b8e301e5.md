### Title
Webhook `shop-domain` Header Is Not Covered by HMAC Signature, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates its HMAC signature over the raw request body only, while the `shop` (and `topic`, `webhook_id`, `api_version`) values used by `Registry.process` to attribute and dispatch the webhook are taken from unauthenticated HTTP headers [1](#0-0) . This mirrors the reported bug class: a field that is *acted on* (the shop domain used for tenant attribution) is not covered by the cryptographic check (the HMAC), so it can be forged independently of a valid signature.

### Finding Description
`Utils::HmacValidator.validate` verifies the HMAC using `verifiable_query.to_signable_string`, and for webhooks `to_signable_string` returns only `@raw_body` [2](#0-1) , [3](#0-2) . The `shop`, `topic`, `webhook_id`, and `api_version` fields, however, are read straight from HTTP headers via `shopify_header`, which are never included in the signed content [4](#0-3) , [5](#0-4) .

`Registry.process` validates only the HMAC and then dispatches to the handler using `request.shop` (and other header-derived fields) as the identity used to route/attribute the event to a merchant [6](#0-5) .

The binding that is broken: `HMAC-verified(body) == tenant-attribution(shop header)` is assumed to hold, but the equality never holds structurally — the HMAC only proves `body` was signed with the app's shared secret; it proves nothing about which `shop-domain` header accompanies that body.

Crucially, a Shopify app's webhook HMAC secret (`Context.api_secret_key` / `client_secret`) is **shared across every shop that has the app installed** — it is not per-tenant. Any unprivileged party who installs the app on their own store (a normal, unprivileged action) will receive legitimately-signed webhooks for their own shop's events. Because the signature covers only the body, that attacker can:
1. Capture a legitimate `(raw_body, hmac)` pair delivered to their own webhook endpoint for their own shop.
2. Replay that exact `(raw_body, hmac)` pair to the target app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value naming a *different* victim shop.
3. `HmacValidator.validate` still succeeds (the body/HMAC pair is legitimately signed), and `Registry.process` dispatches the handler with `WebhookMetadata` claiming the victim shop's domain [7](#0-6) .

Any host application that uses `request.shop` from the validated webhook to look up/act on merchant-specific state (as the library's own documentation and the `WebhookHandler`/`WebhookMetadata` pattern encourage) will process attacker-controlled data under a victim shop's identity — a cross-tenant confusion entirely within this gem's validation contract, since the gem presents `Registry.process` as having already validated the authenticity of `request.shop`.

### Impact Explanation
This breaks the tenant boundary the HMAC check is meant to enforce: an unprivileged attacker (a normal merchant with an app install) can make the app process forged webhook payloads under an arbitrary victim shop's identity, meeting the "cross-tenant access" Critical impact bar, since the whole purpose of `Utils::HmacValidator.validate` gating `Registry.process` is to let host apps trust the resulting `shop` field as authentic.

### Likelihood Explanation
Likelihood is high for any attacker who can install the target app on their own (or a trial) shop — a standard, unprivileged action for any public Shopify app — and then send a raw HTTP POST with copied body/HMAC and a forged `shopify-shop-domain` header to the app's webhook endpoint.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook_id`) header values as part of the signed/verified content in `to_signable_string`, or otherwise cryptographically bind the shop domain to the payload before `Registry.process` attributes the event to that shop and dispatches it to handlers.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and registers a webhook subscription for a topic (e.g. `orders/create`), pointed at an endpoint they control.
2. Shopify sends the webhook with a valid `x-shopify-hmac-sha256` computed over the JSON body using the app's shared `client_secret`, and header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures `raw_body` and the `hmac` header verbatim.
4. Attacker sends a new HTTP POST to the app's real webhook endpoint with the identical `raw_body` and `hmac` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against `hmac` [8](#0-7) .
6. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON>, ...)`, and the host application processes attacker-controlled data as if it originated from `victim-shop.myshopify.com` [7](#0-6) .
