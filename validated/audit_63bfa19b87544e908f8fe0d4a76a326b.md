### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw body, then trusts the `x-shopify-shop-domain` header — which is completely outside the HMAC's coverage — as the tenant identity passed to the app's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` verifies the HMAC exclusively against that signable string [2](#0-1) . The `shop` accessor, however, is read directly from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` header with no cryptographic binding to the signature [3](#0-2) .

`Registry.process` performs only the HMAC check and then immediately forwards `request.shop` into `WebhookMetadata`, which is the tenant-identifying field passed to the app's `WebhookHandler#handle` implementation [4](#0-3) . `WebhookMetadata.shop` is documented as "The shop domain of the webhook" and is the field apps are expected to use to route/attribute webhook data to a specific tenant [5](#0-4) , per the gem's own documentation [6](#0-5) .

This breaks the intended identity binding: `HMAC-valid(body)` should imply `shop == the-shop-that-actually-generated-body`, but the equality the code actually enforces is only `HMAC(body, secret) == received_hmac`, independent of `shop`. Because the app's `client_secret` is shared across every shop that has installed the app (it is not shop-specific), any tenant with a legitimate install can capture one authentic, validly-signed webhook (topic + raw body + HMAC) delivered to them by Shopify, then replay that exact byte-identical body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value naming a different (victim) shop. The signature still validates because the header is not part of the signed material, so `Registry.process` will call the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain.

### Impact Explanation
This is a cross-tenant identity-binding break: an unprivileged tenant of a multi-tenant app can cause the app to process/attribute webhook data under another shop's identity. Depending on how the host app keys its data store or triggers side effects off `data.shop` (e.g. writing per-shop records, triggering `shop/redact`/`customers/redact` compliance flows for the mandatory topics, or driving billing/entitlement logic), this can lead to cross-tenant data corruption, false GDPR-redaction triggers against a victim shop, or bypass of shop-scoped authorization checks that rely on the webhook's asserted shop.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate installer of the target app on their own shop (no special privileges, no access to `client_secret` or access tokens) — satisfying the "unprivileged internet user" bar. The only additional requirement is the ability to capture one raw webhook delivery (already something the attacker legitimately receives at their own registered endpoint) and replay it with a modified header to the shared webhook endpoint, which is straightforward.

### Recommendation
Bind the `shop` identity into the material verified by the HMAC, or independently authenticate it — e.g., require host apps to cross-check `request.shop`/`WebhookMetadata#shop` against the shop associated with the specific `webhook_id`/subscription (via a stored mapping from registration to shop) before trusting it, and document this requirement prominently. Alternatively, have `HmacValidator`/`Request` incorporate the shop-domain header into the value that is validated, or expose a stronger API that forces callers to supply and check an expected shop before `Registry.process` will report a match.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and also on `victim-shop.myshopify.com`.
2. Shopify sends a legitimate webhook to the attacker's endpoint for `attacker-shop.myshopify.com`:
   - Headers: `x-shopify-hmac-sha256: <valid-hmac-for-body>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`
   - Body: `{"id": 1, ...}`
3. Attacker replays the identical body and `x-shopify-hmac-sha256` value to the same app endpoint, but changes only the header: `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` still succeeds because it only checks `raw_body` against the HMAC [2](#0-1) .
5. `Registry.process` invokes the app's handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"` [4](#0-3) , even though the data actually originated from the attacker's own shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
