Audit Report

## Title
Unbounded HTTP action response cache in gateway allows memory-exhaustion DoS - (File: `core/services/gateway/handlers/capabilities/v2/response_cache.go`)

## Summary
The gateway's HTTP Action `responseCache` stores every cacheable outbound-HTTP response in an in-memory map keyed only by a request hash, with no cap on the number of entries or aggregate cached bytes, unlike the sibling `requestCache` implementation which explicitly bounds size via `maxCacheSize`. A workflow owner who issues many distinct cacheable HTTP Action requests with `CacheSettings.Store=true` can grow this cache without bound until the next TTL-based cleanup, allowing memory exhaustion in the gateway process.

## Finding Description
`responseCache` is defined as a plain map protected by a mutex and TTL, with no size limit: [1](#0-0) . Every cacheable response (2xx/4xx) is unconditionally inserted into the map when `storeOnFetch`/`CacheSettings.Store` is true, with no check on current map size before insertion: [2](#0-1) . The only reclamation mechanism is `DeleteExpired`, which removes only TTL-expired entries and runs on a periodic interval (`CleanUpPeriodMs`, default 10 minutes per the README's default table), never rejecting insertion based on size: [3](#0-2) . In contrast, the sibling `requestCache` in `common/requestcache.go` explicitly enforces `maxCacheSize` and rejects new entries once full, showing the pattern for size-bounded caching is known and used elsewhere in the same package family but not applied here: [4](#0-3) . The cache key is derived from `req.Hash()` (method, URL, headers, body, workflow owner) as invoked from `makeOutgoingRequest`, so any workflow issuing HTTP actions with distinct URLs/bodies/headers and `CacheSettings.Store=true` creates a new permanent-until-TTL entry: [5](#0-4) .

## Impact Explanation
This is an uncontrolled resource consumption (CWE-400) issue. A workflow owner — an unprivileged caller relative to the gateway operator — can deploy a workflow that issues HTTP Action calls with `CacheSettings.Store=true` and continuously varying request parameters (query strings, bodies, headers) to defeat cache-key deduplication, each producing a distinct cached entry that persists until the periodic TTL cleanup. Because insertion is never gated on aggregate cache size, sustained variation can grow gateway memory usage in proportion to the number of distinct cached keys, degrading or crashing the gateway process shared by all workflows on that node — a denial of service affecting the availability of the CRE gateway. Note that the per-response size is bounded by `MaxResponseBytes` (default ~26.4KB per `network/httpclient.go`), which mitigates but does not eliminate the growth vector, since the number of distinct keys is effectively attacker-controlled and unbounded within the TTL window.

## Likelihood Explanation
The HTTP Action capability is a normal, documented feature reachable by any workflow a workflow owner deploys and that a DON node executes; the README explicitly documents `CacheSettings.Store` and TTL-based cleanup as the sole cache-management mechanism, with no size cap mentioned. No privilege beyond ordinary workflow authoring is required to set `CacheSettings.Store=true` and vary request parameters. The default TTL/cleanup interval (10 minutes) and per-response byte cap slow the rate of growth but do not prevent it, since the workflow can continuously generate new unique cache keys faster than expiration reclaims memory.

## Recommendation
Add an explicit maximum size (entry count and/or total byte budget) to `responseCache`, mirroring the `maxCacheSize` enforcement pattern already used in `common/requestcache.go`, and reject or evict (e.g., LRU) once the limit is reached. Consider scoping capacity per-workflow-owner so no single workflow can exhaust cache capacity for others sharing the gateway process.

## Proof of Concept
1. Deploy a workflow invoking the HTTP Action capability repeatedly with `CacheSettings.Store=true` and `CacheSettings.MaxAgeMs>0`, using a unique query parameter or body value on each call.
2. Point requests at a controlled endpoint returning 200 responses near the `MaxResponseBytes` limit configured for the client.
3. Repeat across many distinct keys within the default 10-minute `OutboundRequestCacheTTLMs`/`CleanUpPeriodMs` window faster than `DeleteExpired` can reclaim entries.
4. Observe `responseCache.cache` (and gateway process memory) grow unbounded with the number of distinct cached responses, confirmable via a unit test that calls `responseCache.Fetch`/`Set` in a loop with unique `OutboundHTTPRequest` values and asserts `len(cache)` grows without limit.

func (rc *responseCache) DeleteExpired(ctx context.Context) int {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	now := time.Now()
	var expiredCount int
	for key, cachedResp := range rc.cache {
		if now.After(cachedResp.storedAt.Add(rc.ttl)) {
			delete(rc.cache, key)
			expiredCount++
		}
	}
	rc.lggr.Debugw("Removed expired cached HTTP responses", "count", expiredCount, "remaining", len(rc.cache))
	rc.metrics.IncrementCacheCleanUpCount(ctx, int64(expiredCount), rc.lggr)
	rc.metrics.RecordCacheSize(ctx, int64(len(rc.cache)), rc.lggr)
	return expiredCount
}

	responseData *T
	timeoutTimer *time.Timer
	mu           sync.Mutex
}

func NewRequestCache[T any](timeout time.Duration, maxCacheSize uint32) RequestCache[T] {
	return &requestCache[T]{cache: make(map[globalID]*pendingRequest[T]), timeout: timeout, maxCacheSize: maxCacheSize}
}

func (c *requestCache[T]) NewRequest(lggr logger.Logger, request *api.Message, callback handlers.Callback, responseData *T) error {
	if request == nil {
		return errors.New("request is nil")
	}
	if responseData == nil {
		return errors.New("responseData is nil")
	}
	key := globalID{request.Body.Sender, request.Body.MessageID}
	c.mu.Lock()
	defer c.mu.Unlock()
	_, ok := c.cache[key]
	if ok {
		return errors.New("request already exists")
	}
	if len(c.cache) >= int(c.maxCacheSize) {
		return errors.New("request cache is full")
	}
