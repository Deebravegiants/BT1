### Title
Unallowlisted route hops let a crafted swap payload steal arbitrary tokens from the caller's wallet via auth-tree injection - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The controller and its swap aggregator place no restriction on which pool/venue contracts a route may invoke. A malicious `swap` payload can name an attacker-deployed "pool" contract that calls `token.transfer(victim, attacker, amount)` for any token in the victim's wallet. That transfer is recorded as a sub-invocation under the caller's own `require_auth` root and executes if the caller signs the simulated authorization tree — exactly the "policy bypass via crafted content" shape of CVE-2023-5483 (CSP bypass via a crafted HTML page, requiring user interaction). The repository already ships a working PoC of the theft path in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` (lines 194–269).

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs` (lines 13–55) guards the router call only with `with_flash_guard` and an exact input-transfer authorization for `token_in`; it never inspects which contracts the route will touch. The aggregator dispatcher (`contracts/swap-aggregator/src/venues/mod.rs`, `dispatch_hop`, lines 23–59) likewise calls whatever `hop.pool` address the attacker-controlled `swap` bytes name, with no pool/venue/token allowlist. `docs/explanation/threat-model.md` lines 154–165 confirm: "The router calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization."

The reachable entrypoints are `swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral` (`contracts/controller/src/lib.rs`, lines 255–303), all callable by any account owner/delegate. The victim's `require_auth` on the root call covers the entire tree; a crafted route's rogue pool executes a `transfer` out of the victim's wallet that a signing wallet/client may approve as part of the simulated tree.

### Impact Explanation
Theft of user funds. The loss is the victim's whole wallet balance of an arbitrary, even never-listed, token — `docs/explanation/threat-model.md` line 160: "The loss is then the caller's wallet, not the routed amount, and neither the payload minimum nor the final risk gate bounds it." The measured-output check (`verify_router_output`, lines 75–84) and final health-factor gates are fully satisfied because the rogue pool can still pay fair output; the stolen transfer is orthogonal to the swap accounting.

### Likelihood Explanation
Requires user interaction, matching the CVE's UI:R vector: the victim must submit (or be tricked into signing) a route containing the malicious hop. The adversarial test proves the enforced-auth path executes when the simulated tree is signed (`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`, lines 258–268: `the poisoned tree authorizes the rogue transfer`; Alice's wallet goes to 0, attacker's to `WALLET_BALANCE`). The honest tree is refused (lines 239–256), so exploitation depends on a wallet/client that signs the tree simulation returns — which honest simulation does emit (lines 199–222). Medium: real theft, but gated on the victim approving a poisoned auth tree.

### Recommendation
Bind the authorization scope to honest routes:
- Maintain an allowlist of approved hop pool addresses (governance-managed, like the Blend pool approval in `INV-STRAT-03`) and reject routes naming unlisted pools in `dispatch_hop` / `execute_strategy`; or
- Execute hop pools in a context where the caller's auth cannot be inherited (e.g., have the router pre-pull all funds and call venues without exposing a `require_auth`-satisfiable path for the caller); or
- At minimum, the controller should refuse routes whose simulation records any authorization child beyond the single `token_in.transfer(controller, router, amount_in)` that `INV-STRAT-01` promises.

### Proof of Concept
Already present in-tree: `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`.
- `RogueHopPool::swap` (lines 62–71) transfers `WALLET_BALANCE` of an unlisted token from `alice` to `attacker`.
- `UnlistedPoolRouter::execute_strategy` (lines 39–47) invokes whatever `hop_pool` the payload names.
- `simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry` (lines 194–227) shows simulation emits the poisoned tree and drains Alice's wallet.
- `enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer` (lines 229–269) shows the theft executes on-chain when the signed tree includes the rogue transfer.

Attack: attacker crafts a `swap_collateral`/`multiply` route whose only hop points to `RogueHopPool` seeded with `(victim, victim's token, attacker, amount)`; the victim's wallet signs the simulated auth tree; the rogue transfer drains the token while the swap still returns fair output and all controller risk gates pass.
