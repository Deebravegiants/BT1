### Title
Webhook shop-tenant identity is taken from an HTTP header that is not covered by the HMAC signature, allowing shop-spoofed webhook replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the `shop` value taken from the `X-Shopify-Shop-Domain` HTTP header — a field that is never included in the signed material. This breaks the identity binding `bytes_covered_by_hmac == bytes_used_to_identify_tenant`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `#hmac` is likewise derived purely from the `X-Shopify-Hmac-Sha256` header, decoded and compared against a signature computed over that same raw body: [2](#0-1) 

The `shop`, `topic`, and `webhook_id` values, however, are pulled directly from separate, unsigned HTTP headers: [3](#0-2) 

`Registry#process` validates only the body HMAC, then immediately uses the unsigned `request.shop` header to build the `WebhookMetadata` handed to the application's handler as the tenant identifier: [4](#0-3) 

Because `X-Shopify-Shop-Domain` is not part of the signable string, `OpenSSL.secure_compare` in `HmacValidator.validate_signature` only proves the *body* was produced with the app's secret — it proves nothing about which shop that body belongs to: [5](#0-4) 

Equality that should hold: `shop_bytes_verified_by_hmac == shop_bytes_used_for_tenant_lookup`. In this code it is actually `shop_bytes_verified_by_hmac == "" (never checked)` while `shop_bytes_used_for_tenant_lookup == header value, fully attacker-controlled on replay`.

### Impact Explanation
An unprivileged internet user who can install the app on their own store receives genuine, validly-signed webhooks (raw body + `X-Shopify-Hmac-Sha256`) for their own shop. Because the shop identity is carried out-of-band in a header that is excluded from the signature, that same attacker can resend the identical raw body/HMAC pair to the app's shared webhook endpoint while substituting `X-Shopify-Shop-Domain` (or `X-Shopify-Webhook-Id`/topic) with a victim shop's domain. `HmacValidator.validate` still returns `true` (the body signature is untouched), so `Registry#process` dispatches the attacker-authored payload to the handler tagged as coming from the victim shop. Any app logic that uses `WebhookMetadata#shop` to select the tenant's access token, update tenant-scoped records, or otherwise take shop-scoped action will act on a different shop than the one that actually sent the data — a cross-tenant identity-binding break.

### Likelihood Explanation
Requires no possession of the app's `client_secret`/access token: the attacker only needs their own legitimate install (to obtain one valid signed payload) and the ability to POST to the app's public webhook endpoint with custom headers, both of which are available to any unprivileged internet user/merchant. The main constraint is that the replayed body's *content* is fixed to whatever the attacker's own store generated, limiting the payload but not the tenant-attribution confusion.

### Recommendation
Include the shop domain (and ideally topic/webhook id/api-version) in the HMAC-signed material, or otherwise cryptographically bind the header-derived shop value to the signed body before it is trusted by `Registry#process` — e.g., resolve the shop independently (via the API version + known shop registration) rather than trusting `X-Shopify-Shop-Domain` verbatim, or reject the webhook if the header-derived shop cannot be corroborated against out-of-band shop state established during OAuth.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; capture a genuine webhook delivery: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because Shopify signed it with the real `client_secret`).
2. POST to the app's webhook endpoint with the same body `B` and header `H`, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `HmacValidator.validate` (lib/shopify_api/utils/hmac_validator.rb) succeeds because it only checks `B` against `H`.
4. `Registry#process` (lib/shopify_api/webhooks/registry.rb#188-199) builds `WebhookMetadata` with `shop: "victim.myshopify.com"` and dispatches attacker-controlled body `B` to the handler as if it came from the victim shop.
