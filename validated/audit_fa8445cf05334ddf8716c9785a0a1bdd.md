### Title
Same-token batch withdrawals status is misattributed across destinations (wrong-index txHash/status) - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` (and its internal-utils counterpart `waitForWithdrawalCompletion`) determines the on-chain outcome of a specific withdrawal in a batch by matching the PoA Bridge API's returned withdrawal list solely by `assetId`, ignoring the withdrawal's index/destination/amount. When a caller batches two or more withdrawals of the **same token** (same `assetId`) to **different destination addresses** in one `signAndSendWithdrawalIntent`/`processWithdrawal` call, the SDK will report the status/`txHash` of whichever matching entry the (unsorted) API happens to return first for every one of those withdrawals — breaking the equality "the txHash/status reported for withdrawal N is the on-chain outcome of withdrawal N".

### Finding Description
`PoaBridge.createWithdrawalIntents` builds one `ft_withdraw` intent per withdrawal param and multiple such withdrawals can be included in a single signed/published intent via `sdk.ts`'s batch mode (`signAndSendWithdrawalIntent`, `processWithdrawal` accepting `WithdrawalParams[]`) — see [1](#0-0) . Each withdrawal gets a `WithdrawalIdentifier` with its own `index`, computed by `createWithdrawalIdentifier` at [2](#0-1) .

When later polling completion, `describeWithdrawal` fetches the whole withdrawal list from the PoA Bridge API for the batch's NEAR tx hash and calls `findMatchingWithdrawal`, which matches purely by `assetId`: [3](#0-2) [4](#0-3) 

The code comment explicitly acknowledges the limitation: "multiple withdrawals of the same token in a single transaction are not supported." Because `Array.prototype.find` returns the same unsorted-list-first-match regardless of which `index`/destination the caller is asking about, calling `describeWithdrawal` for withdrawal index 0 (destination A) and withdrawal index 1 (destination B) of the same `assetId` in the same batch tx will both resolve against the same matched entry (whichever the API lists first), so at least one of them is reported with a `txHash`/`status` that belongs to the *other* withdrawal's on-chain outcome. The identical matcher exists in `internal-utils`'s `waitForWithdrawalCompletion`: [5](#0-4) .

The SDK's own test suite documents that matching is index-independent by design ("matches withdrawal by assetId, not by index"): [6](#0-5) , but that test only exercises distinct assets per index, not two same-asset withdrawals within one batch, so the multi-same-asset collision case is not covered/guarded against, letting `watchWithdrawal`/`waitForWithdrawalCompletion` ( [7](#0-6) ) surface an incorrect `completed`/`txHash` for the wrong destination's withdrawal to the caller of `processWithdrawal`.

### Impact Explanation
An integrator relying on `processWithdrawal`/`waitForWithdrawalCompletion` to confirm that a specific withdrawal (by index) reached its intended destination can receive a `txHash` that actually corresponds to a different destination's transfer within the same batch. Because the reported status is "completed" with an on-chain hash for the *wrong* leg of the batch, this is a status/hash misreport that can cause an integrator to prematurely credit a user for a withdrawal that has not actually completed for that specific destination (or to associate the wrong transfer hash with a withdrawal), i.e., "a status or hash misreport making an integrator credit or refund twice" per the accepted impact list.

### Likelihood Explanation
Triggering this requires nothing more than an unprivileged, ordinary caller of the public SDK batching two or more withdrawals of the same `assetId` (e.g., same POA-bridged token) to different destination addresses in a single `processWithdrawal`/`signAndSendWithdrawalIntent` call — a normal usage pattern for batch payouts (e.g., paying out the same token to several users at once). No privileged access, malicious relayer, or bridge-operator cooperation is needed; the bug is purely in client-side result matching against the PoA Bridge API's unsorted response list.

### Recommendation
`findMatchingWithdrawal` in both `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` and `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts` must disambiguate withdrawals with identical `assetId` within the same transaction. Until the PoA Bridge API supports index-correlated results, either (a) sort both the API-returned withdrawals and the local withdrawal params deterministically (e.g., by `destinationAddress`+`amount`) and pair by position, and reject/guard batches with same-asset+same-amount+same-destination ambiguity, or (b) explicitly detect and throw/flag when more than one withdrawal in a batch shares the same `assetId`, refusing to report a "completed" status for those specific entries until an unambiguous match can be made.

### Proof of Concept
1. Call `sdk.processWithdrawal` (or `signAndSendWithdrawalIntent`) with a batch of two `withdrawalParams`, both using the same POA-bridged `assetId` (e.g., `nep141:usdt.omft.near`) but two different `destinationAddress` values (Alice and Bob) — this produces a single NEAR tx containing two `ft_withdraw` intents.
2. After publishing, call `waitForWithdrawalCompletion`/`describeWithdrawal` for withdrawal index 0 (Alice) and index 1 (Bob) once the PoA API reports both entries.
3. Since `findMatchingWithdrawal` filters only on `nep141:${near_token_id} === assetId` (packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:418-427), both calls resolve to the same array entry (whichever the API lists first) — the caller polling for Bob's withdrawal (index 1) can observe `status: "completed"` with the `transfer_tx_hash` that actually corresponds to Alice's transfer (index 0), before Bob's own transfer has settled (or vice versa).

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
