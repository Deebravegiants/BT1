This confirms the finding: the gem's own documentation states `Registry.process` "will verify the request did indeed come from Shopify" [1](#0-0)  and instructs the host app to trust `data.shop` for tenant identification (`perform_later(topic: data.topic, shop_domain: data.shop, ...)`) [2](#0-1) , but the HMAC computed by `HmacValidator` only signs `Request#to_signable_string`, which is just the raw body, and never the `shop`, `topic`, `webhook_id`, or `api_version` header values.

### Title
Shop identity spoofing in webhook processing due to HMAC not covering the shop-domain header - (File: lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates only the HMAC of the raw request body before dispatching `WebhookMetadata` (which includes an unauthenticated `shop` value taken from a header) to the app's handler. Because the shared app-level `client_secret` produces the same HMAC for identical body content regardless of which shop the webhook originated from, and the `shop` header is completely outside the signed payload, an attacker who can obtain one genuine Shopify webhook (e.g., by installing the app on their own store, which is available to any internet user) can replay that exact `raw_body`/HMAC pair while substituting the `x-shopify-shop-domain` header with an arbitrary victim shop domain. `Registry.process` will accept it as valid and hand the handler a `WebhookMetadata` claiming to be from the victim shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body` [3](#0-2) , and `shop`, `topic`, `webhook_id`, and `api_version` are all read straight out of unauthenticated HTTP headers [4](#0-3) .

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` header using a constant-time comparison [5](#0-4) . This proves that the header fields — most importantly `shop` — are never part of the value that is cryptographically bound to the secret.

`Registry.process` only checks `Utils::HmacValidator.validate(request)` and then immediately builds `WebhookMetadata` using `request.shop` (the unauthenticated header) as the tenant identifier passed to the app's handler [6](#0-5) .

The identity binding that should hold is: `hmac_valid ⇒ (body, shop) both authentic`. In reality the binding is only `hmac_valid ⇒ body authentic`; `shop` is asserted, not verified. Since Shopify's webhook `client_secret` is a single per-app secret shared across every installed shop (not shop-specific), a valid `(body, hmac)` pair obtained from any shop — including one the attacker controls by installing the app themselves — remains valid HMAC-wise no matter what `x-shopify-shop-domain` value is attached to the replayed request.

### Impact Explanation
This breaks the tenant boundary the gem is documented to provide: the gem's own webhook docs tell developers to trust `data.shop` as the shop identity for further per-tenant processing (loading a session, writing to the tenant's data store, enqueuing tenant-scoped jobs) [7](#0-6) . An attacker with a legitimate (self-installed) instance of the target app can forge webhooks that appear to originate from any other merchant, injecting attacker-chosen `body` content (crafted via actions on their own store) tagged with an arbitrary victim `shop` domain. Depending on how the host application uses `data.shop` (e.g., to key session/data lookups), this enables cross-tenant data injection or corruption — classified as cross-tenant access.

### Likelihood Explanation
Any internet user can install the target app on a free/dev Shopify store to obtain one legitimate, validly-signed webhook payload, since the HMAC secret (`client_secret`) is shared across all shops for a given app rather than shop-specific. Replaying the request with a modified `shop-domain` header requires no cryptographic material beyond what a normal integrator/attacker can already access by installing the app once, making this readily reachable without needing the API secret directly.

### Recommendation
Bind the shop identity (and other trusted metadata such as topic/webhook_id) into the value that is HMAC-verified, or otherwise cross-check the header-derived `shop` against a value that is itself authenticated (for example, verifying the webhook's shop against Shopify by resolving the `webhook_id`/topic through an authenticated API call, or including the shop domain as part of the signed payload before comparison). At minimum, document loudly and enforce in-library that `request.shop` is unauthenticated so host apps do not use it as a sole tenant key without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and registers for a webhook topic (e.g. `orders/create`).
2. Shopify sends a legitimate webhook request with `raw_body` = B and `x-shopify-hmac-sha256` = HMAC(secret, B), where `secret` is the app's single `client_secret`.
3. Attacker replays this exact request to the app's webhook endpoint but rewrites `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which recomputes HMAC(secret, B) — matching, since B is unchanged — and accepts the request [8](#0-7) .
5. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker-controlled>, ...)` and processes it as if it were a genuine event from the victim's store [9](#0-8) .

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
