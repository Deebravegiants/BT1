### Title
Node crash via nil `Params` dereference in unauthenticated vault `PublicKeyGet` gateway message - (File: core/capabilities/vault/gw_handler.go)

### Summary
`GatewayHandler.HandleGatewayMessage` in `core/capabilities/vault/gw_handler.go` routes `vaulttypes.MethodPublicKeyGet` requests directly to `handlePublicKeyGet` without going through `GatewayVaultRequestProcessor`, the component that otherwise enforces `req.Params == nil` checks for every other vault method. `handlePublicKeyGet` unconditionally dereferences `*req.Params`, causing a nil-pointer panic if a caller omits or nulls the params field, closely paralleling the missing-NULL-check crash pattern in CVE-2018-7336.

### Finding Description
In `HandleGatewayMessage` [1](#0-0) , only `MethodSecretsCreate`, `MethodSecretsUpdate`, `MethodSecretsDelete`, and `MethodSecretsList` are routed through `h.requestProcessor.ProcessRequest`, which validates structure and authorization before use. `MethodPublicKeyGet` is handled separately: `response = h.handlePublicKeyGet(ctx, gatewayID, req)` [2](#0-1) , bypassing that pipeline entirely (the code comment even notes public key requests intentionally skip authorization).

`handlePublicKeyGet` itself does not defend against a nil `Params` pointer: [3](#0-2) 
```go
func (h *GatewayHandler) handlePublicKeyGet(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) *jsonrpc.Response[json.RawMessage] {
	r := &vaultcommon.GetPublicKeyRequest{}
	if err := json.Unmarshal(*req.Params, r); err != nil {
```

This is in stark contrast to every other request path in `GatewayVaultRequestProcessor`, each of which explicitly guards against nil params before dereferencing, e.g.: [4](#0-3) 

On the gateway (internet-facing) side, `HandleJSONRPCUserMessage` in `core/services/gateway/handlers/vault/handler.go` also special-cases `MethodPublicKeyGet` and forwards the request to `handlePublicKeyGet`/nodes without validating `req.Params` [5](#0-4) , so an unauthenticated client's request with a missing/null `params` field for `vault_publicKeyGet` propagates unchanged to the node, where the nil dereference occurs.

### Impact Explanation
A nil-pointer dereference here is unrecoverable within the goroutine handling the gateway message and results in a process panic/crash on the Chainlink node processing vault requests — a denial-of-service triggerable by any unauthenticated actor able to reach the gateway's vault endpoint, since `PublicKeyGet` is explicitly exempted from authorization.

### Likelihood Explanation
High: the request requires no authentication, no allowlisting, and no special privileges — only a syntactically valid JSON-RPC envelope for `vault_publicKeyGet` with `params` omitted or set to `null`.

### Recommendation
Add an explicit nil check for `req.Params` in `handlePublicKeyGet` (`core/capabilities/vault/gw_handler.go`) before calling `json.Unmarshal(*req.Params, r)`, mirroring the pattern used in `GatewayVaultRequestProcessor.process*Request` methods, and apply the same guard on the gateway-side `handlePublicKeyGet`/`handlePublicKeyGetSynchronously` code path in `core/services/gateway/handlers/vault/handler.go`.

### Proof of Concept
1. Send a JSON-RPC request to the gateway's vault endpoint with method `vault_publicKeyGet` and either omit `params` or set `"params": null`.
2. The gateway forwards the un-validated request to the node via `SendToNode`.
3. The node's `GatewayHandler.HandleGatewayMessage` routes it to `handlePublicKeyGet`, which executes `json.Unmarshal(*req.Params, r)` with `req.Params == nil`, causing a nil-pointer dereference panic and crashing the node's request-handling goroutine/process.
