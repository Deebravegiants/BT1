### Title
POA Bridge withdrawal status is matched only by `assetId`, ignoring withdrawal index, causing wrong completion status/tx hash to be reported for batched same-token withdrawals - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` and the shared helper `waitForWithdrawalCompletion` resolve the on-chain outcome of a specific withdrawal by looking up the POA Bridge indexer's withdrawal list for a NEAR transaction hash and picking the entry whose `near_token_id` matches the requested `assetId`. The lookup ignores the `index` that uniquely identifies which withdrawal intent inside the transaction is being queried. When a single NEAR transaction contains two or more withdrawal intents of the same asset (a supported and expected case — `WithdrawalIdentifier.index` exists precisely to disambiguate multiple withdrawals in one transaction), the code returns whichever matching record `Array.prototype.find` happens to hit first, regardless of which withdrawal it actually corresponds to.

### Finding Description
`describeWithdrawal` in `poa-bridge.ts` receives a `WithdrawalIdentifier` that includes an `index` (created by `createWithdrawalIdentifier`, `poa-bridge.ts:295-311`) explicitly to distinguish multiple withdrawals batched in the same NEAR transaction: [1](#0-0) 

However, the actual status resolution discards `index` and matches purely by asset identifier: [2](#0-1) 

The equivalent low-level helper used for polling completion has the identical flaw, and the authors' own comment confirms the root cause — it is a known but unhandled ambiguity: [3](#0-2) 

The equality that should hold is: *the completion status/`transfer_tx_hash` reported for withdrawal N must be the on-chain outcome of withdrawal N specifically*. Because matching only checks `nep141:${w.data.near_token_id} === assetId` and not the record's position/index/amount, when two withdrawals of the same token exist in one transaction (e.g., a user withdraws USDC to address A and USDC to address B in a single batched NEAR call), calling `describeWithdrawal`/`waitForWithdrawalCompletion` for index 1 can return the withdrawal record that actually belongs to index 0 (or vice versa), whichever the indexer lists first / `Array.find` hits first.

### Impact Explanation
This breaks the "status reported must equal the on-chain outcome" invariant explicitly called out as an in-scope impact class. An integrator that drives crediting/refund/reconciliation logic off `describeWithdrawal`'s returned `{status, txHash}` for each `WithdrawalIdentifier` (indexed per withdrawal) can be told that withdrawal #1 is `"completed"` with a `transfer_tx_hash` that in fact belongs to withdrawal #0. Consequences:
- An integrator may credit/mark-settled a withdrawal that hasn't actually landed on the destination chain, based on another withdrawal's transaction hash.
- Two different withdrawals (different destination addresses) can be reported as sharing the same completion proof, enabling a double-credit / reconciliation error for one of the legitimate withdrawals while the other's actual completion is missed.
This matches the "High" impact bucket: "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
No malicious actor coordination is required beyond a legitimate user (or an automated flow built on this SDK) batching two withdrawals of the same token in a single NEAR transaction — an operation the SDK's own data model (`WithdrawalIdentifier.index`, multiple intents per tx) is designed to support. The bug is deterministic once such a batch occurs and the indexer returns more than one record for the same `near_token_id`; it is not dependent on adversarial input manipulation, only on a common usage pattern (batched same-asset withdrawals) that the code fails to disambiguate.

### Recommendation
Match withdrawal records by a criterion that uniquely identifies the specific withdrawal within the transaction — e.g., correlate by `amount` (adjusted for fee) and destination `address`/`destinationMemo` in addition to `near_token_id`, or request that the POA Bridge indexer return records in submission order and match by `index` position once ordering is guaranteed. At minimum, when more than one candidate record matches the same `assetId` for a given `tx_hash`, the SDK should refuse to resolve (return `pending`/throw an ambiguity error) rather than silently picking the first match, to avoid misreporting completion for the wrong withdrawal.

### Proof of Concept
1. A user submits a single NEAR transaction containing two `mt_withdraw` intents for the same `assetId` (e.g., `nep141:eth-...omft.near`), one to `destinationAddress` A and one to `destinationAddress` B — this is a valid batched call the SDK builds via `createWithdrawalIntents`.
2. The integrator obtains two `WithdrawalIdentifier`s from `createWithdrawalIdentifier` for the same `tx.hash`, differing only by `index` (0 and 1).
3. The integrator calls `poaBridge.describeWithdrawal(...)` for `index: 1`. Internally this calls `getWithdrawalStatusWithRetry({ withdrawal_hash: tx.hash })`, which returns both withdrawal records for that tx hash.
4. `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)` (`poa-bridge.ts:319-322`) matches on `near_token_id === assetId` only, ignoring `index`, and returns the **first** matching record — which may correspond to the withdrawal to address A (index 0), not B (index 1).
5. The integrator receives `{status: "completed", txHash: <A's transfer hash>}` for the withdrawal it queried as index 1, and treats withdrawal to address B as settled using address A's completion proof, even though B's actual transfer may still be pending or use a different hash.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}
