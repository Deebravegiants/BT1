## Title
Webhook HMAC only signs the request body while shop/topic/webhook_id used for dispatch and tenant attribution come from unsigned headers, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload from only the raw request body, but the values that the `Registry` uses to route and attribute the webhook — `shop`, `topic`, `webhook_id`, `api_version` — are read straight from HTTP headers that are never included in the signed bytes. This is the same class of bug as the reported oracle issue: the verification (`hmac` over `to_signable_string`) covers a narrower set of bytes than what is actually acted upon (headers used for tenant/topic dispatch), so trusting the overall webhook as "belonging to shop X, topic Y" is wrong.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `api_version`, and `webhook_id` are pulled from headers that are not part of the signable string at all: [2](#0-1) 

`HmacValidator.validate` only ever checks `verifiable_query.hmac` against `HMAC(secret, to_signable_string)`, i.e. against the raw body bytes: [3](#0-2) 

`Registry.process` then dispatches purely on the unsigned `request.topic`, and builds the `WebhookMetadata` handed to the app's handler using the unsigned `request.shop`, `request.webhook_id`, and `request.api_version`, alongside the (separately, correctly) HMAC-verified body: [4](#0-3) 

Because the app's `client_secret` (and thus the HMAC key) is shared across every shop that installs the app, any merchant who installs the app can receive a genuine, validly-signed webhook for their own store. Since the signature only covers the body, that attacker can replay the same `(body, hmac)` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, `X-Shopify-Webhook-Id`, and `X-Shopify-Api-Version` headers with arbitrary values. `HmacValidator.validate` will still pass (body/HMAC pair is untouched), and `Registry.process` will invoke the handler as if the event came from a different shop and/or topic, feeding it attacker-chosen `shop` and body content.

This breaks the equality the app is implicitly relying on: `shop-that-produced-a-valid-HMAC == shop attributed to the processed webhook`. In fact only `body-that-produced-a-valid-HMAC == body attributed to the processed webhook` holds; `shop`/`topic`/`webhook_id` are unauthenticated.

### Impact Explanation
This is a cross-tenant data/identity confusion: an unprivileged app-installing user (any merchant who can install the app and thus receive a genuine webhook of their own) can cause the host application to process attacker-supplied body content under a victim shop's identity and/or under a topic of the attacker's choosing (e.g. relabeling a benign topic's payload as `app/uninstalled`, `shop/update`, `customers/redact`, etc.), depending on how the host app's handlers use `WebhookMetadata#shop`/`#topic`. Any downstream logic that keys state, deletes data, or grants/revokes access based on `WebhookMetadata.shop` or `.topic` can be manipulated cross-tenant.

### Likelihood Explanation
Requires only that the attacker be a legitimate (even trial) installer of the target app so they can capture one valid `(raw_body, hmac)` pair from their own store's webhook delivery, then replay it directly to the app's public webhook endpoint with modified headers — no access to `client_secret`, access tokens, or victim credentials is needed.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` (or at minimum `shop` and `topic`) in the bytes that are HMAC-verified, or otherwise cryptographically bind headers to the body (e.g., derive/verify a signature over a canonical concatenation of headers + body) so that `to_signable_string` cannot be satisfied while headers are altered independently of the body.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Shopify sends a webhook to the app's endpoint, e.g. topic `orders/create`, with headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`, and a body `B`, signed as `HMAC = HMAC-SHA256(client_secret, B)`.
3. Attacker replays the exact same body `B` and `X-Shopify-Hmac-Sha256: HMAC` to the app's webhook endpoint, but swaps `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` and/or `X-Shopify-Topic` to a different registered topic.
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:13`) succeeds because it only checks `@raw_body` against the HMAC.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-199`) dispatches to the handler registered for the spoofed topic and calls it with `WebhookMetadata` carrying the spoofed `shop`, letting the attacker inject data attributed to `victim-shop.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
