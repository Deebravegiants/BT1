### Title
Signup proceeds to completion using a one-time-validated operator authorization that is never re-checked before the biometric enrollment submission - ([File: src/plans/mod.rs])

### Summary
`MasterPlan::do_signup` validates the operator's QR-code authorization (and its expiration) exactly once, at the very start of the signup transaction, via `scan_remaining_qr_codes`. After that single check, the flow proceeds through a series of lengthy, asynchronous steps (artificial UX delays, face detection, biometric capture with timeouts of up to `self_serve_biometric_capture_timeout`/`BIOMETRIC_CAPTURE_TIMEOUT`, and the biometric pipeline) before the same, now-stale `operator_data`/`operator_qr_code` is finally used to submit the enrollment to the backend. No re-validation of operator authorization occurs immediately before this security-relevant final action, mirroring the Perennial finding where an account's health was validated against only the *current* state rather than the state that will exist once the action executes.

### Finding Description
The operator authorization/expiration check happens in `scan_remaining_qr_codes`: [1](#0-0) 

This function matches on `operator_data.timestamp.elapsed() < operator_qr_expiration_time` a single time and returns a `ResolvedQrCodes` containing the frozen `operator_data`. Immediately afterwards, `do_signup` uses this resolved, one-time-checked data to drive the rest of the signup pipeline: [2](#0-1) 

Between the single authorization check and the actual enrollment submission, the code executes a fixed UX delay, face detection, and the full biometric capture routine (which can legitimately run for the duration configured by `self_serve_biometric_capture_timeout`), plus the biometric pipeline stage: [3](#0-2) 

Only the elapsed-time check against `operator_qr_expiration_time` guards operator authorization; there is no re-verification against the backend (`backend::operator_status::request`) performed again before the enrollment request is finally sent using the frozen `operator_qr_code`: [4](#0-3) 

The authorization decision is therefore made against the operator's *current* state at scan time, not against the state that will hold once the sensitive action (submitting the enrollment tied to that operator) actually executes minutes later — the same root-cause pattern as the M-15 report, where liquidation validity was checked against current (not next) state, creating an exploitable window between check and action.

### Impact Explanation
If an operator's authorization is invalidated or revoked on the backend during the (potentially multi-minute) capture/pipeline window — analogous to the "unpause" window in the original report — the orb will still complete and submit the enrollment tied to that operator, since no re-check occurs. This can result in a signup being misattributed to (or completed under) an operator whose authorization was no longer valid at the time the enrollment was actually submitted, a form of unauthorized/misattributed signup.

### Likelihood Explanation
The window is bounded only by the sum of the UX delay, face-detection timeout, and biometric-capture timeout (which can be tens of seconds to minutes in self-serve mode), well beyond a typical processing latency. Because operator authorization is checked exactly once and is not re-verified via the backend right before the enrollment is submitted, any change in the operator's authorization state during this window is silently ignored, making exploitation dependent only on natural elapsed time rather than any additional attacker action.

### Recommendation
Re-validate the operator's authorization/expiration (ideally with a fresh backend check, not just a local timestamp comparison) immediately before the enrollment request is submitted in `do_signup`/`enroll_user::Plan`, rather than relying solely on the single check performed in `scan_remaining_qr_codes` at the start of the flow.

### Proof of Concept
1. Operator scans/validates their QR code; `operator_qr_expiration_time` check passes in `scan_remaining_qr_codes` [1](#0-0) .
2. Signup proceeds through the UX delay, face detection, and the full biometric-capture phase, which can take up to `self_serve_biometric_capture_timeout` [3](#0-2) .
3. During this window, the operator's authorization is revoked/expired on the backend side (out-of-band), but no code path re-checks this.
4. `enroll_user::Plan::run` submits the enrollment using the original, now-stale `operator_qr_code` [4](#0-3) , completing a signup under an operator authorization that was no longer valid at submission time.
