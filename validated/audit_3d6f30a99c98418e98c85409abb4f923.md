### Title
Webhook `shop-domain` header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The Merkle-library report describes a general bug class: a verification mechanism authenticates a data blob, but a value the application later trusts is not actually inside the verified blob, so an attacker can present a value that never went through the verification step. The same class of bug exists in `ShopifyAPI::Webhooks::Request` / `ShopifyAPI::Webhooks::Registry`: the HMAC only signs the raw webhook body, but the `shop` (tenant identifier) that gets propagated to the app's handler is read straight from an unauthenticated HTTP header.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`#shop`, however, is pulled straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header with no cryptographic binding at all: [2](#0-1) 

`HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string` (the body) and compares it against the `hmac` header: [3](#0-2) 

`Registry.process` checks that HMAC and then forwards `request.shop` — the unverified header value — directly into `WebhookMetadata`, which is the tenant-identifying field the host application's `WebhookHandler#handle` implementation is expected to use to select the correct shop/session to act on: [4](#0-3) [5](#0-4) 

The binding that should hold is:
`hmac == HMAC(api_secret_key, body || shop)`
but the actual check only enforces:
`hmac == HMAC(api_secret_key, body)`

Because `api_secret_key` is a single app-wide secret shared by every shop that installs the app (it is not shop-specific — see `Context.setup`, `@api_secret_key`), any merchant who installs the app can legitimately trigger a webhook whose body content they control (e.g. by creating an order or updating a resource on their own store), receive that webhook with a valid HMAC over the body, then replay the identical `raw_body` + `hmac-sha256` pair to the app's webhook endpoint while substituting an arbitrary value in the `shop-domain` header. `HmacValidator.validate` still succeeds (it never inspected the shop header), and `Registry.process` hands the forged shop identity to the handler as if the event genuinely originated from that shop. [6](#0-5) 

### Impact Explanation
This breaks the tenant boundary the whole webhook mechanism is supposed to provide: `shop_verified_by_hmac == shop_used_for_tenant_scoping` is false. Any application that uses `WebhookMetadata#shop` (as instructed by this gem's own `WebhookHandler` interface and documentation) to select the session/tenant record to update will process attacker-supplied body data under an arbitrary victim shop's identity. This is a cross-tenant access vulnerability — an unprivileged app-installer can inject attacker-controlled webhook payloads into a completely different, victim tenant's data path, satisfying the "Critical – cross-tenant access" bar.

### Likelihood Explanation
Likelihood is high for any real-world integrator: the only prerequisite is installing the app on one's own store (an unprivileged, standard onboarding action available to any internet user who can install a public Shopify app), then capturing one legitimate webhook and replaying it with a modified header — no secrets, tokens, or privileged access are required, and the gem provides no server-side protection against it.

### Recommendation
Bind the shop identity into the signed material, or otherwise cryptographically tie the `shop-domain` header to the HMAC before trusting it. Concretely:
- Have `Request#to_signable_string` (or a wrapper used specifically for header trust decisions) include the `shop-domain`, `api-version`, and `webhook-id` headers in the signed content, matching what Shopify actually signs, or
- Document explicitly, and preferably enforce in `Registry.process`, that `request.shop` must be cross-checked against the destination endpoint/tenant context (e.g., matching against a known/expected shop from the URL path or session store) before being handed to the handler, rather than trusted as authenticated tenant information solely because the body HMAC matched.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`.
2. Attacker triggers a real webhook (e.g., `orders/create`) with attacker-controlled body content `B`. Shopify sends:
   - `x-shopify-hmac-sha256: HMAC(api_secret_key, B)`
   - `x-shopify-shop-domain: attacker.myshopify.com`
   - `x-shopify-topic: orders/create`
3. Attacker replays the exact same request to the app's webhook endpoint, changing only the header:
   - `x-shopify-shop-domain: victim.myshopify.com`
   - HMAC header and body `B` unchanged.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, B)` and matches successfully because the shop header was never part of the signed input (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:12-31`).
5. `WebhookMetadata.new(... shop: request.shop ...)` is constructed with `shop == "victim.myshopify.com"` and passed to the host app's handler, which processes attacker-controlled body `B` as if it were a genuine event from `victim.myshopify.com`.
