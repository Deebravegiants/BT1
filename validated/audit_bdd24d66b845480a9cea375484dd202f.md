## Title
Webhook shop and topic identity are not covered by the HMAC signature, enabling cross-tenant webhook forgery - (`File: lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook's authenticity by validating the HMAC over the raw body only, yet it dispatches and attributes the webhook using the `shop` and `topic` values taken from unsigned HTTP headers. This breaks the equality that should hold between "bytes verified by the HMAC" and "bytes used to determine identity/handler," letting any attacker who possesses one valid `(raw_body, hmac)` pair (e.g., from a webhook legitimately delivered to their own, attacker-controlled shop after installing the app) replay it with a forged `x-shopify-shop-domain` and/or `x-shopify-topic` header to make the app process attacker-controlled data as if it originated from a different, victim shop or a different webhook topic.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are pulled straight from the (attacker-controllable, unauthenticated at the transport level) HTTP headers: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string`, i.e. only the raw body for webhooks: [3](#0-2) 

`Registry.process` validates the HMAC, then immediately uses the unsigned `request.topic` to select a handler and the unsigned `request.shop` to construct the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The identity binding that should hold is:
`shop/topic authenticated by HMAC == shop/topic acted upon by the handler`

In this gem, that equality does not hold — the HMAC only binds the body bytes, not the `shop-domain` or `topic` headers. Since a given app uses one shared `api_secret_key` across all shops that install it (this is inherent to Shopify's per-app webhook HMAC scheme, not per-shop), any unprivileged user who installs the app on their own store can trigger webhook deliveries with attacker-chosen body content (e.g., via `orders/create`, `customers/redact`, `shop/redact`, etc. against their own shop) and thereby obtain a validly-signed `(raw_body, hmac)` pair. They can then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain and/or the `x-shopify-topic` header for a different topic, and the gem's `Registry.process` will accept it as authentic and hand it to the handler labeled with the forged shop/topic.

### Impact Explanation
This crosses a tenant boundary: an attacker who only controls their own shop's installation of the app can inject data that the app attributes to another merchant's shop, or route arbitrary attacker-chosen payloads into a different handler than the one Shopify actually signed it for (e.g., feeding fabricated data into a `customers/redact`/GDPR handler, or spoofing `app/uninstalled` / order events for a victim shop). Depending on how the host app uses `data.shop` (session lookup, per-tenant data writes, compliance actions), this can lead to cross-tenant data corruption or unauthorized actions being taken against a shop the attacker does not control — matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Likelihood is realistic but requires two things the reported analog also required: (1) the attacker must be able to obtain at least one legitimately-signed `(body, hmac)` pair, which is achievable by installing the app on an attacker-owned shop and triggering a webhook event with body content of the attacker's choosing, and (2) the receiving app must derive meaningful behavior from `data.shop`/`data.topic` without independently re-verifying shop identity (e.g., against a known-installed session) — which is exactly what the gem's own documented `WebhookController` example does, since it only calls `Registry.process` and never re-checks `shop`.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the HMAC-verified signable string (or otherwise cryptographically tie them to the signed payload), consistent with the same design principle Sablier was asked to adopt for Permit2 witness data: the verifier should validate exactly the fields that will later be acted upon. At minimum, `Webhooks::Request#to_signable_string` should incorporate the shop domain and topic headers so that a replayed body cannot be re-attributed to a different shop or topic, and `Registry.process` documentation should explicitly warn integrators that `WebhookMetadata#shop` is not itself an authenticated value.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Attacker triggers a webhook (e.g. `orders/create`) with body content of their choosing; Shopify sends a request signed with the app's shared `api_secret_key`:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC over raw_body>
   x-shopify-shop-domain: attacker.myshopify.com
   { ...attacker-chosen order JSON... }
   ```
3. Attacker replays the exact same raw body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets:
   ```
   x-shopify-shop-domain: victim.myshopify.com
   ```
4. `Utils::HmacValidator.validate` in `hmac_validator.rb` recomputes HMAC over the (unchanged) raw body and it matches, so `Registry.process` in `registry.rb` proceeds and calls the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, even though Shopify never issued this webhook for `victim.myshopify.com`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
