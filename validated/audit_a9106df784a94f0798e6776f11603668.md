Audit Report

## Title
CORS Origin Wildcard Bypass via Suffix-Matching Instead of Subdomain-Boundary Check - (File: core/services/gateway/network/httpserver.go)

## Summary
`isAllowedOrigin` implements wildcard CORS origin matching by stripping the `*.` prefix from an allowed entry and then checking `strings.HasSuffix(originHost, allowedHost)`, with no verification that the match occurs at a `.`-delimited label boundary. As a result, a wildcard entry like `*.ethereum.org` also matches unrelated attacker-controlled hosts such as `evilethereum.org`, which merely share the trailing character sequence but are not subdomains.

## Finding Description
The vulnerable logic is confirmed exactly as described: [1](#0-0) 

This function is invoked directly from `handleRequest`, which is wired as the handler for the gateway's public, unauthenticated user-facing path: [2](#0-1) [3](#0-2) 

For an allowed entry `https://*.ethereum.org`, `allowedHost` becomes `ethereum.org` after stripping the prefix, and `strings.HasSuffix("evilethereum.org", "ethereum.org")` returns `true`, so `evilethereum.org` (or `notethereum.org`, `xethereum.org`, etc.) is treated as authorized even though it is not a subdomain of `ethereum.org`. The existing test suite exercises the "doesn't end with suffix" negative case (`ethereum.remix.org`) and positive subdomain cases (`another.valid.domain.com`), but does not test — and the code does not defend against — a hostile domain that shares the raw suffix without a `.` boundary: [4](#0-3) 

No other authentication, redaction, or boundary check exists in this path before the CORS headers are set — the check runs unconditionally on every request when `CORSEnabled` is true, based solely on the unauthenticated `Origin` header.

## Impact Explanation
This is a genuine allowlist-bypass bug in the CORS validation logic (an in-scope class: "allowlist or subscription bypass"). If successfully exploited it would let an attacker-registered domain receive `Access-Control-Allow-Origin` reflection for the gateway's public JSON-RPC endpoint, letting a browser on that attacker domain read cross-origin responses that were only meant to be readable by genuine subdomains of the configured base domain.

However, the practical severity is constrained: the codebase does not set `Access-Control-Allow-Credentials` anywhere (confirmed via search — no matches), so browsers will not attach cookies/credentials to these cross-origin requests, and the reflected origin alone does not grant access to any session, cookie-based auth, or victim-specific data unless the gateway's own request handling already treats all callers equivalently (which is the normal case for this public gateway endpoint per its design — it processes JSON-RPC requests authenticated via a JWT extracted from the `Authorization` header, not cookies). This significantly limits the "cross-user response confusion" impact, since the attacker would only be able to have a victim's browser relay requests that don't carry any credential the attacker doesn't already control themselves (JWTs are read from the `Authorization` header, not implicitly attached by the browser like cookies).

## Likelihood Explanation
Exploitation requires no privileges: any actor can send an HTTP request with a crafted `Origin` header to the gateway's public endpoint. It does, however, require: (1) the operator has configured a wildcard entry in `CORSAllowedOrigins` (not the default — no wildcard entries exist in the default/sample configs found), and (2) a victim's browser must visit and execute script from the attacker's domain to actually perform the cross-origin fetch and leverage the bypass, since CORS is a browser-enforced same-origin policy relaxation — the server-side header alone does nothing without a browser context making the read. This narrows real-world exploitability but does not eliminate it; it is a legitimate CORS-validation logic defect.

## Recommendation
Replace the raw suffix check with a boundary-aware comparison, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    baseDomain := allowedHost[2:]
    if originHost == baseDomain || strings.HasSuffix(originHost, "."+baseDomain) {
        return true
    }
}
```
This ensures a match only succeeds for the exact base domain or a proper subdomain delimited by a `.`, preventing sibling/attacker domains such as `evilethereum.org` from matching `*.ethereum.org`.

## Proof of Concept
1. Configure `CORSAllowedOrigins = ["https://*.ethereum.org"]` and enable `CORSEnabled`.
2. Send `POST /<gateway path>` with header `Origin: https://evilethereum.org`.
3. Observe the response includes `Access-Control-Allow-Origin: https://evilethereum.org`, confirming `isAllowedOrigin` incorrectly returns `true` for `strings.HasSuffix("evilethereum.org", "ethereum.org")`.
4. This can be added as a Go unit test analogous to `TestHTTPServer_HandleRequest_CORSEnabled_FromNotAllowedOriginWildcards` in `core/services/gateway/network/httpserver_test.go`, asserting that `Access-Control-Allow-Origin` is empty for origin `https://evilethereum.org` against allowed `https://*.ethereum.org` — the current implementation would fail this assertion.
