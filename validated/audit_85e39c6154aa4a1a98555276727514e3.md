### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the unauthenticated `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, while `HmacValidator` only verifies the raw request body against `X-Shopify-Hmac-Sha256`. The shop domain is never part of the signed material, so any caller who can obtain one valid `(body, hmac)` pair for their own shop can replay it against the app's webhook endpoint with an arbitrary `shop` header, and `Registry.process` will attribute the attacker-supplied body to that spoofed shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0)  and `Request#shop` is read straight from the (attacker-controlled, unsigned) header: [2](#0-1) .

`HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it only to the received `hmac` value — it never binds the shop domain into the signed content: [3](#0-2) .

`Registry.process` accepts the request once `HmacValidator.validate` passes, and then constructs the webhook metadata using `request.shop` (the unauthenticated header) as the tenant identifier passed to the app's handler: [4](#0-3) .

This is precisely the "field acted on but not covered by the HMAC" bug class from the report analog: the signature only binds the body, but the code trusts an unrelated, unsigned field (`shop`) as the authoritative tenant identity for the downstream handler call — exactly analogous to `ResourceLockValidator` signing only `ResourceLock` while letting other unchecked fields (target/value/execution count) drive the actual execution.

An unprivileged attacker who installs the app on their own store (a normal, unprivileged action requiring no special access) can trigger any webhook topic and receive from Shopify a legitimately-signed `(raw_body, hmac)` pair for their own shop. Because `shop` is excluded from the signable string, the attacker can then send a forged HTTP request directly to the app's public webhook endpoint reusing that valid `(raw_body, hmac)` pair but substituting `x-shopify-shop-domain` with an arbitrary victim shop domain. `HmacValidator.validate` still succeeds (it never looked at the shop header), and `Registry.process` invokes the app's handler with `shop: <victim-domain>` and `body: <attacker-controlled JSON>`.

### Impact Explanation
This crosses a tenant boundary without any credential belonging to the victim: the app's webhook handler is made to believe attacker-controlled data (order records, customer records, mandatory `customers/redact`/`customers/data_request`/`shop/redact` payloads, etc.) originates from a different merchant's shop. Depending on how the host application uses `WebhookMetadata#shop` (most Shopify apps key their persistence, redaction, and business logic by shop domain), this enables cross-tenant data injection/corruption or forced execution of GDPR-mandatory redaction flows against a shop the attacker doesn't own — a cross-tenant access/authentication-bypass class issue arising directly from this gem's `Webhooks::Request`/`Registry` implementation, not from host misuse.

### Likelihood Explanation
High: no secrets, tokens, or privileged access are required. The only precondition is that the attacker can install the target app on a store they control (the normal onboarding flow for any Shopify app) and that the app's public webhook endpoint is reachable, which is required by design for Shopify to deliver webhooks.

### Recommendation
Bind the shop domain (and topic, api-version) into the material that is HMAC-verified, or otherwise cryptographically tie the claimed shop header to the signed body before it is trusted by `Registry.process`/`WebhookMetadata`. At minimum, cross-check `request.shop` against a shop domain that was independently established (e.g., via the app's own session/installation record) instead of trusting the header value as-is once only the body's HMAC has been verified.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `products/create`) so Shopify delivers a POST to the app's webhook endpoint with:
   - body: `{"id":123,...}` (attacker fully controls the product content)
   - header `x-shopify-hmac-sha256: <valid HMAC over that body>`
   - header `x-shopify-shop-domain: attacker-shop.myshopify.com`
2. Attacker captures this exact `(body, hmac)` pair.
3. Attacker sends a new POST directly to the same public webhook endpoint, reusing the identical `body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes the HMAC over the (unchanged) body and it matches — validation passes.
5. `Registry.process` calls the handler with `shop: "victim-shop.myshopify.com"` and the attacker's chosen body, causing the app to process attacker-controlled data as if it belongs to `victim-shop`.

          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
