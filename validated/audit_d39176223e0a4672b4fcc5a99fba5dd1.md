### Title
Fixed `RELAYER_MESSAGE_GAS` budget can under-fund the RedeemEscrow relayer fee, permanently stranding cross-chain escrow — ([File: sdk/packages/sdk/src/protocols/intents/GasEstimator.ts])

### Summary
The Polynomial report describes an economic-invariant failure: `LiquidityPool` computed its Synthetix margin from a hardcoded assumption (`futuresLeverage`) instead of the live, externally-mutable minimum required by `PerpsV2MarketSettings.liquidationBufferRatio()`. When the external parameter moved past what the hardcoded assumption anticipated, the pool's position became under-margined, orders could not execute, and the position risked liquidation.

Hyperbridge's cross-chain `IntentGateway` has the same shape of bug in the sizing of the ISMP relayer fee that pays for delivering the `RedeemEscrow` settlement message: the fee is derived from a flat, hardcoded gas constant (`RELAYER_MESSAGE_GAS = 1_000_000n`) rather than the actual, chain-dependent cost of proof verification (BEEFY/consensus-client verification + state-membership proof + `handlePostRequests` execution), which is externally determined by each destination consensus client and can exceed the hardcoded budget.

### Finding Description
`GasEstimator.estimateCrossChainFees` prices the relayer fee for the `RedeemEscrow` POST purely as `RELAYER_MESSAGE_GAS` (a flat 1,000,000 gas units) converted to fee-token terms: [1](#0-0) 

The comment on the constant itself acknowledges the assumption is not measured against the real cost and cannot track per-chain differences: [2](#0-1) 

This fixed budget flows directly into `order.fees` (what the user pays, capturing `totalGasInFeeToken + relayerFeeInSourceFeeToken`, with only a flat +5% buffer) and into the solver's `options.relayerFee` passed at fill time to the on-chain dispatch: [3](#0-2) 

On the contract side, `_fillCrossChain` uses exactly the solver-supplied `options.relayerFee` (bounded only by the flat off-chain estimate above) when dispatching the `RedeemEscrow` request back to the source chain: [4](#0-3) 

The actual cost to relay and deliver a POST request is not a static constant analogous to Synthetix's `liquidationBufferRatio` — it is governed externally by the destination `EvmHost`/consensus client's verification cost (BEEFY authority-set size, sync-committee update cost, GRANDPA justification size, etc.), which can grow independently of this SDK-side assumption, exactly like `liquidationBufferRatio` could be raised independently of Polynomial's hardcoded `futuresLeverage`.

### Impact Explanation
If the real gas required to verify consensus proofs and execute `handlePostRequests` for the `RedeemEscrow` message exceeds the flat `RELAYER_MESSAGE_GAS` budget the fee was sized against (e.g. the destination chain's consensus verification becomes materially more expensive, or a costlier verification path is used), no relayer is economically incentivized to deliver the message — the same failure mode as the original report's "delay orders of the pool not being executed." Because cross-chain intent fills are strictly all-or-nothing (`_fillCrossChain` already delivered outputs to the beneficiary), the escrowed input tokens on the source chain become permanently unrecoverable through the normal settlement path — they can only be recovered via the deadline-based cancellation/GET-proof flow, and even that requires the solver not to have already filled. This is a permanent freezing-of-funds risk reachable from a single unprivileged cross-chain `fillOrder` dispatch.

### Likelihood Explanation
Likelihood is lower than the certainty of on-chain math, since it depends on an external, dynamic cost (consensus proof verification gas) diverging materially from a flat estimate; the code's own comment marks this as a known, deliberate simplification ("TODO: replace this flat budget with a measured estimate ... A flat number can't track per-chain differences like L1 data costs"). It is nonetheless a live, unaddressed gap on any chain whose verification cost profile is not conservatively covered by the 1M-gas assumption, and requires no privileged action to trigger — any user placing, or solver filling, a cross-chain order is exposed.

### Recommendation
Replace the flat `RELAYER_MESSAGE_GAS` constant with a measured estimate of the actual `handlePostRequests` execution cost for the specific destination consensus client (as the code comment itself proposes), or at minimum expose/track the current verification-cost parameters per state machine and fail closed (refuse the fill / require a larger relayer fee) when the flat budget is insufficient for the live cost, mirroring how the referenced report recommends deriving margin requirements from the live external parameter rather than a fixed assumption.

### Proof of Concept
1. A user places a cross-chain order via `IntentGateway`, with `order.fees` computed by `quoteOrderFees()`, which prices `relayerFeeInSourceFeeToken` solely from `RELAYER_MESSAGE_GAS = 1_000_000n` [5](#0-4) .
2. A solver fills the order cross-chain via `_fillCrossChain`, supplying `options.relayerFee` sized from the same flat estimate, and dispatches the `RedeemEscrow` POST to the source chain [6](#0-5) .
3. If the destination chain's true consensus-verification + execution cost for delivering that POST (via BEEFY/GRANDPA/sync-committee proof verification in `handlePostRequests`) exceeds the gas the flat 1,000,000-unit budget priced, no relayer profitably delivers the message.
4. The solver has already paid out the order's outputs to the beneficiary, but the source-chain escrow release depends entirely on delivery of the undelivered `RedeemEscrow` message — the escrowed input tokens remain locked with no automatic recovery path, since fills of cross-chain orders cannot be partially retried or re-filled.

    /// @dev Posts `body` to the gateway on the order's source chain, paying `nativeFee` in native
    /// tokens when non-zero and in the fee token otherwise.
    function _post(Order calldata order, bytes memory body, uint256 relayerFee, uint256 nativeFee) internal {
        DispatchPost memory request = DispatchPost({
            dest: order.source,
            to: abi.encodePacked(_instance(order.source)),
            body: body,
            timeout: 0,
            fee: relayerFee,
            payer: msg.sender
        });
        if (nativeFee > 0) {
            IDispatcher(host()).dispatch{value: nativeFee}(request);
        } else {
            dispatchWithFeeToken(request);
        }
    }

    /**
     * @dev Fills a cross-chain order on the destination chain. The solver provides output
     * tokens directly to the beneficiary, and a Hyperbridge post request is dispatched
     * back to the source chain to release the escrowed input tokens to the solver.
     *
     * Unlike same-chain fills, cross-chain fills are all-or-nothing — partial fills
     * are not supported. The solver must provide at least the full required amount
     * for every output asset.
     *
     * Surplus handling (when solver overpays):
     * - If the order has attached calldata, all surplus goes to the protocol.
     * - Otherwise, surplus is split between beneficiary and protocol per `surplusShareBps`.
     *
     * After transferring tokens and executing any attached calldata, dispatches a
     * RedeemEscrow message to the source chain gateway via Hyperbridge.
     *
     * @param order The cross-chain order to fill.
     * @param options Fill options including output amounts, relayer fee, and native dispatch fee.
     * @param commitment The keccak256 hash of the ABI-encoded order.
     */
    function _fillCrossChain(Order calldata order, FillOptions calldata options, bytes32 commitment) internal {
        uint256 outputsLen = order.output.assets.length;

        _filled[commitment] = msg.sender;

        uint256 msgValue = msg.value;
        address beneficiary = address(uint160(uint256(order.output.beneficiary)));
        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {
            bytes32 outputToken = order.output.assets[i].token;
            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            if (solverAmount < totalRequired) revert InvalidInput();

            (uint256 protocolShare, uint256 beneficiaryShare) =
                _splitSurplus(solverAmount - totalRequired, order.output.call.length > 0);

            if (token == address(0)) {
                if (msgValue < solverAmount) revert InsufficientNativeToken();
                uint256 beneficiaryTotal = totalRequired + beneficiaryShare;
                _sendValue(beneficiary, beneficiaryTotal);
                msgValue -= (beneficiaryTotal + protocolShare);
            } else {
                IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare);
                if (protocolShare > 0) {
                    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
                }
            }
            if (protocolShare > 0) emit DustCollected(token, protocolShare);
            outputFills[i] = TokenInfo({token: outputToken, amount: totalRequired});
        }

        _execute(order, outputsLen);

        // Native dispatch fee only if the solver sent enough to cover it; else the fee token.
        uint256 nativeFee = options.nativeDispatchFee;
        if (nativeFee > msgValue) nativeFee = 0;
        msgValue -= nativeFee;
        _post(
            order,
            _body(RequestKind.RedeemEscrow, commitment, order.inputs, bytes32(uint256(uint160(msg.sender)))),
            options.relayerFee,
            nativeFee
        );

        // Refund any unspent native tokens to the solver.
        if (msgValue > 0) {
            _sendValue(msg.sender, msgValue);
        }

        emit OrderFilled({commitment: commitment, filler: msg.sender, outputs: outputFills, inputs: order.inputs});
