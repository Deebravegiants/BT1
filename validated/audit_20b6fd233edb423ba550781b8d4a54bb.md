### Title
Unchecked-length `from` field trusted for cross-chain call dispatch and origin derivation - ([File: modules/pallets/hyper-fungible-token/src/module.rs])

### Summary
`pallet-hyper-fungible-token`'s `on_accept` handler decodes an ABI-encoded cross-chain `Message` and, for the optional-calldata "no signature" path, converts the message's `from` field directly into a dispatch origin without the same length validation that is applied to the equivalent `to`/beneficiary field, then dispatches an attacker-influenced `RuntimeCall` under that unverified origin.

### Finding Description
`on_accept` in [1](#0-0)  decodes the incoming ABI `Message` and, for the recipient (`to`) conversion, explicitly validates the byte length (20 or 32 bytes) and returns `HftError::InvalidRecipientLength` otherwise.

By contrast, the optional-calldata execution path that derives the *dispatch origin* when no signature is supplied performs no such validation: [2](#0-1) 

- If `source.is_evm()`, it does `&from_bytes[from_bytes.len() - 20..]` with no check that `from_bytes.len() >= 20`; a shorter `from` value causes a `usize` subtraction underflow / out-of-bounds slice panic.
- Otherwise it does `account.copy_from_slice(from_bytes)` into a `[u8; 32]` buffer with no check that `from_bytes.len() == 32`; any other length panics (`copy_from_slice` panics on length mismatch), exactly the same unchecked-length pattern the codebase's own test suite documents as dangerous elsewhere: [3](#0-2) .

Beyond the panic risk, this branch also encodes a deserialization/authorization gap analogous to the report's root cause (untrusted data is trusted to select behavior without validating its provenance/shape before it drives execution): when `SubstrateCalldata.signature` is `None`, the pallet skips all cryptographic verification of the encoded `runtime_call` [4](#0-3)  and instead trusts the raw `message.from` bytes — which travel inside the attacker-influenced ABI body rather than being independently authenticated — to select the dispatch origin, then immediately calls `runtime_call.dispatch(RawOrigin::Signed(origin.clone()).into())` [5](#0-4) . Only `BaseCallFilter` gates which calls are reachable; there is no re-validation that `origin` (derived from `from`) matches any account that actually authorized the specific `runtime_call` payload, unlike the signed branch, which cryptographically binds `runtime_call` to the signing key via `(nonce, runtime_call).encode()` [6](#0-5) .

### Impact Explanation
- A malformed-length `from` field reaching this code path causes a Rust panic during `on_accept`, which executes inside ISMP message delivery (an unsigned, fee-less extrinsic path per `pallet-ismp`'s `handle_unsigned`/`validate_unsigned` design, see [7](#0-6) ). A panic during block-body execution of a dispatched message can abort the runtime call, and depending on WASM executor behavior, repeatedly delivering the same malformed message can make the (registered source, dest, `to`=pallet) message route un-deliverable — a "route unable to deliver messages" outcome explicitly in scope.
- Separately, dispatching an arbitrary decoded `RuntimeCall` under an origin derived purely from an unauthenticated `from` byte string (rather than a value cryptographically tied to that specific call, as the signed branch requires) weakens the intended authorization model for calldata execution and is an unauthorized-app-action risk if any registered source contract's encoding of `from` can ever diverge from the hard-coded `msg.sender` value the official Solidity contracts always emit.

### Likelihood Explanation
Reachability depends on the actual byte length/content of `message.from` as embedded by the *registered* source-chain contract for a given asset (validated via `ContractToAsset::get(source, &from)` on the ISMP `PostRequest.from` field, which is the source contract address — not the inner ABI `message.from`). The known official Solidity contracts (`HyperFungibleTokenUpgradeable.sol`, `WrappedHyperFungibleToken.sol`) always set `from: abi.encodePacked(msg.sender)`, i.e., exactly 20 bytes, so under the currently-deployed apps the panic is not directly triggerable. However, this pallet is designed to be paired with any registered EVM/Substrate contract implementing this ABI, and nothing in `on_accept` enforces the length invariant at the trust boundary the way the parallel `to` field does — making this fragile to any future or third-party integration, or to a bug in a peer implementation, and inconsistent with the "reject-at-the-boundary" pattern the codebase applies elsewhere (see `ByteVector::decode` and `as_utf8_string`).

### Recommendation
Add the same explicit length validation used for the `to`/beneficiary conversion to the `from`-derived origin path: require `from_bytes.len() == 20` before the EVM slice, and `from_bytes.len() == 32` before `copy_from_slice`, returning a typed `HftError` (e.g., a new `InvalidSenderLength` variant, mirroring the one already used in `on_timeout`) instead of panicking. Additionally, consider requiring a valid signature for calldata execution unconditionally, or otherwise binding the unsigned origin cryptographically to the specific `runtime_call` payload, rather than trusting an unauthenticated byte field to select the dispatch identity.

### Proof of Concept
1. Register (or compromise) a source contract/pallet for a given asset in `ContractToAsset` whose emitted `Message.from` value is not exactly 20 bytes (EVM source) or 32 bytes (non-EVM source) — e.g., a buggy or malicious peer implementation of the bridge ABI, or any future integration that does not hard-code `msg.sender`.
2. Have that source dispatch a `PostRequest` to the `pallet-hyper-fungible-token` module with `Message.data` containing an ABI-encoded `SubstrateCalldata { signature: None, runtime_call: <encoded call> }` and `Message.from` of an invalid length (e.g., 5 bytes).
3. When the message is delivered via `pallet-ismp::handle_unsigned`, `on_accept` reaches the unsigned branch at [2](#0-1)  and panics on `copy_from_slice`/slice indexing, demonstrated already for the analogous fixed-length decode boundary in [8](#0-7) .
