### Title
Untracked ERC4626 share balances left in `EmporiumUpgradeable` can be redeemed and stolen by a later attacker via arbitrary `op.endpoint.call` - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`runAction`'s balance-diff loop only iterates over `circomData.erc20TokenAddresses` [1](#0-0) , so if a victim's op deposits into an ERC4626 vault whose share token is omitted from that array, the minted shares are left stranded in the Emporium contract with no accounting and no UTXO minted. A later, unrelated attacker can then submit their own `runAction` call whose `circomData.erc20TokenAddresses` includes the vault share token and whose op is an arbitrary `op.endpoint.call(op.callData)` (CASE 2, stateless interaction) invoking `vault.redeem(shares, attacker, address(this))`, sending the underlying assets directly to `attacker` and completely bypassing `handleOut`/UTXO minting.

### Finding Description
Broken equality: `underlying_received_by(attacker)` should equal `attacker's own deltaAmountChanges contribution` (i.e., only funds the attacker's own proof authorized should leave the protocol on the attacker's behalf). Instead, `underlying_received_by(attacker) == victim's stranded principal`, with zero corresponding debit in the attacker's own `deltaAmountChanges`/nullifiers.

Root cause and path:
- CASE 2 in `runAction` executes fully attacker-controlled `op.endpoint.call{value: op.value}(op.callData)` with only `callHinkalWallet`/`doSendToRelay` selectors blocked [2](#0-1) . Nothing constrains the call's recipient of any resulting token transfer to `address(this)` (Emporium) or to `msg.sender`.
- The only accounting mechanism, `balancesBefore`/`balancesAfter`/`handleOut`, is computed strictly over `circomData.erc20TokenAddresses` [3](#0-2) [4](#0-3) . If the victim's transaction deposits into a vault but omits the vault share token from `erc20TokenAddresses`, the minted shares remain in Emporium's balance untracked and un-swept — no `UTXO` is created for them, and no check reverts.
- Since `Emporium` is a shared, stateful contract (not per-transaction escrow), any subsequent, unrelated caller's `runAction` invocation will see this leftover balance via `getBalancesForArray` as its own `balancesBefore` for that token [3](#0-2) .
- The attacker's op calls `vault.redeem(sharesHeldByEmporium, attacker, address(this))`. This directly transfers underlying assets to `attacker`, an address entirely outside of `handleOut`'s `msg.sender`-only transfer path [5](#0-4) . Because the shares are burned via `redeem`, the post-call share balance in `circomData.erc20TokenAddresses[i]` for the attacker's tx correctly goes to `0`; `balanceChange` for the share token computes to a large negative number, but since the attacker's own `deltaAmountChanges[i]` for the share token is not required to be negative to match (or the attacker just omits the share token from the accounted array once shares are fully drained), no revert path in `BalanceChangeShouldBePositive` catches theft that has already occurred out-of-band via the direct `redeem` transfer to `attacker`.
- No proof-side constraint (`inTotal + amountChanges === outTotal`, `OverflowPreventer`, etc.) protects this because the circuit only constrains the attacker's own UTXO in/out totals; it has no visibility into unrelated leftover contract-level ERC20/ERC4626 balances belonging to a different, unrelated prior transaction.

### Impact Explanation
This is direct theft of another user's (victim's) funds by an unprivileged attacker: the victim's deposited principal (converted to vault shares) is extracted to the attacker's own wallet with no debit against the attacker's shielded balance and no UTXO ever minted for the victim to redeem. This matches the "Critical - direct theft of shielded or in-flight user funds" category. It is repeatable against any vault/token whose share token is left out of a prior transaction's `erc20TokenAddresses` array, and does not require any privileged role — only the ability to submit a normal `runAction` transaction through the (permissionless from the attacker's proof-generation perspective) whitelisted-relay call path.

### Likelihood Explanation
Preconditions: (1) at least one prior transaction (victim's, or even the attacker's own earlier transaction) that deposits into an ERC4626 vault while omitting the share token from `circomData.erc20TokenAddresses`, leaving shares stuck in Emporium; (2) attacker observes this leftover balance (trivially, via `vault.balanceOf(Emporium)`, a public on-chain read) and crafts a follow-up `runAction` with the share token included and a `redeem`-style op targeting themselves as recipient. Both are within attacker capabilities as defined (craft `CircomData`/op fields freely, deploy own proof, choose ordering). Cost is a single transaction; the gain is the entire stranded balance. This is repeatable every time a token is left off the array by any user of the shared Emporium contract.

### Recommendation
- Require that any token/asset that could be created or moved by an op (e.g., ERC4626 share tokens received from a `deposit`/`mint` call) be explicitly included in `circomData.erc20TokenAddresses` so it is accounted for and swept out via `handleOut`, or enforce a strict allow-list/whitelist of callable `op.endpoint` targets and permitted function selectors so arbitrary `redeem`/`transfer`-style calls with attacker-controlled recipients cannot be crafted.
- Alternatively, sweep and revert if any tracked-token-adjacent balance (e.g., known vault shares associated with whitelisted vault endpoints) remains nonzero and unaccounted for at the end of `runAction`, or disallow the Emporium contract from persisting any balance between transactions at all (i.e., enforce zero end-of-call surplus for every token the contract can plausibly hold).
- Ensure `op.callData`'s destination-of-funds parameter cannot resolve to any address other than `address(this)` for calls performed on behalf of a stateless op, e.g., by decoding/validating standard `redeem`/`withdraw` signatures' recipient argument against `address(this)`.

### Proof of Concept
Hardhat fork/test plan:
1. Deploy a `MockERC4626` vault wrapping a mock ERC20 underlying, and register Emporium as an allowed recipient in `ExternalActionBaseUpgradeable`.
2. Victim transaction: submit `runAction` with `circomData.erc20TokenAddresses = [underlying]` (vault share token omitted) and an op calling `vault.deposit(amount, address(this))`. Assert: `vault.balanceOf(Emporium) > 0` after the call, and no `UTXO` for the share token was returned/minted (`utxoSet` length reflecting only underlying's zero-or-negative change, i.e., no share-token UTXO).
3. Attacker transaction: submit a separate `runAction` with `circomData.erc20TokenAddresses = [shareToken]`, `deltaAmountChanges = [0]`, and an op calling `vault.redeem(vault.balanceOf(Emporium), attacker, address(this))`.
4. Assert both sides of the broken equality:
   - Before: `vault.balanceOf(Emporium) == sharesHeldByEmporium > 0`, `underlying.balanceOf(attacker) == 0`.
   - After: `vault.balanceOf(Emporium) == 0`, `underlying.balanceOf(attacker) == redeemedUnderlyingAmount == victim's stranded principal`, while the attacker's `deltaAmountChanges` and nullifier set show no corresponding debit for that amount — proving `underlying_received_by(attacker) != attacker's own deltaAmountChanges contribution`, and that it instead equals the victim's stolen principal.

    function handleOut(
        int256 balanceChange,
        CircomData calldata circomData,
        uint256 i
    ) internal returns (UTXO memory outUtxo) {
        // total change can be less than zero if there was some balance before the call -> that's why we have <=
        if (balanceChange <= 0) {
            return outUtxo;
        }

        transferERC20TokenOrETH(
            circomData.erc20TokenAddresses[i],
            msg.sender,
            uint256(balanceChange)
        );

        outUtxo = UTXO(
            uint256(balanceChange),
            circomData.erc20TokenAddresses[i],
            circomData.stealthAddressStructure,
            circomData.timeStamp
        );
    }
