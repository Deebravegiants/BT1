### Title
Seed overwrite before verification in `Wallet#setSeed` can permanently brick a wallet with no recovery path - ([File: features/wallet/module/wallet.js])

### Summary
The external report describes a class of bug where a value (`rootHash`) is committed to persistent state via an update path, and only afterwards is validity checked — by which point there is no way to undo the write, bricking the account with no recovery mechanism. The Hydra wallet SDK has a structurally identical pattern in `Wallet#setSeed`: the seed is written to storage first, and only *after* the write does the code read it back and assert correctness, with no rollback or backup of the previous value.

### Finding Description
`#setSeed` in [1](#0-0)  writes the new seed to `walletStorage` under `SEED_KEY` immediately, then re-reads it and validates equality afterward:
```js
await this.walletStorage.set(SEED_KEY, seed, { passphrase })
const storedSeed = await this.walletStorage.get(SEED_KEY, { passphrase })
assert(storedSeed.seed.equals(seed.seed), safeString`setSeed failed`)
```
This is the write-then-validate pattern that caused the original Keystore.sol issue: the commit to durable state happens before its correctness is confirmed, and no previous good state is preserved to fall back to. If the write is corrupted, partially applied, or interrupted (e.g., storage failure, race condition, app crash between the `set` and the verifying `get`, or a bug in an underlying storage/encryption adapter), the assertion throws — but the previous encrypted seed value has already been overwritten and is unrecoverable. `SEED_KEY` is the sole persisted secret backing the entire wallet (`exists()`, `#getSeed`, and `unlock()` all depend solely on this key at [2](#0-1)  and [3](#0-2) ), so a corrupted or mismatched value here means the wallet can never be unlocked or its mnemonic recovered again through the normal application flow.

This code path is directly reachable by an unprivileged, ordinary user through two calls:
- `create()`/`import()` at [4](#0-3) , which calls `#setSeed` when generating or importing a wallet.
- `changePassphrase()` at [5](#0-4) , which calls `#setSeed({ seed, passphrase: newPassphrase })` to re-encrypt the existing seed under a new passphrase — overwriting the only copy of the passphrase-protected seed before verifying the new copy is valid.

There is no evidence in the reachable code of a staged/two-phase write (write-to-temp-then-swap), a backup of the prior encrypted blob, or a recovery/re-derivation mechanism if the post-write assertion fails.

### Impact Explanation
If the write fails to persist correctly (partial write, storage corruption, encryption/passphrase mismatch bug, concurrent access, or an interrupted app/process), the user's seed becomes permanently inaccessible: `unlock()` would fail with "Wrong password" or throw at `#getSeed`, and there is no path in this module to recover the previous seed since it was already overwritten. This is a direct, concrete wallet-compromise-class impact (total, irreversible loss of access to funds), matching the "Permanent lock/freeze/unrecoverable corruption" impact class from the original Keystore.sol finding — it is not just a self-XSS/no-impact scenario, since the trigger conditions (storage layer inconsistency, interrupted writes, or passphrase-change race) are plausible in real client/mobile storage backends the module runs on (mobile keychain, encrypted file storage, etc., per adapters like `keystore-mobile` and `secure-container` seen elsewhere in this repo).

### Likelihood Explanation
The overwrite-before-verify pattern is unconditionally executed on every `create()`, `import()`, and `changePassphrase()` call — these are core, frequently used user flows, not edge cases. The underlying trigger (a write that "succeeds" from the storage adapter's perspective but is not faithfully round-trippable, or an interruption between `set()` and `get()`) is a realistic failure mode for any persistent storage layer, especially given this SDK explicitly supports mobile devices where processes can be killed mid-operation and where multiple concrete storage backends (encrypted files, OS keychains) are used across adapters in this monorepo. The comment at line 110-111 ("Restoring a seedless backup restarts the app immediately... wait a bit longer to ensure the data is fully stored before restarting") shows the developers were already aware that write completion/persistence timing is a real concern for this exact code path, but only added a delay, not a safe write ordering.

### Recommendation
Change `#setSeed` to a write-then-verify-then-commit pattern that never destroys the last known-good value until the new value is confirmed durable and correct:
1. Write the new seed under a temporary/staging key (or keep the old key intact) before touching `SEED_KEY`.
2. Read back and validate the staged value.
3. Only after validation succeeds, atomically promote/rename the staged value to `SEED_KEY` (and only then delete/update dependent keys like `HAS_USER_SET_PASSPHRASE_KEY`/`GENERATED_PASSPHRASE_KEY`).
4. If validation fails, leave the original `SEED_KEY` untouched and surface a recoverable error instead of bricking the wallet.

### Proof of Concept
1. Call `wallet.changePassphrase({ currentPassphrase, newPassphrase })`.
2. Internally this calls `#setSeed({ seed, passphrase: newPassphrase })`, which executes `await this.walletStorage.set(SEED_KEY, seed, { passphrase: newPassphrase })` — overwriting the only persisted, passphrase-encrypted seed.
3. Simulate a storage-layer fault on the immediately following `get` (e.g., underlying storage adapter returns stale/corrupted/partial data, or the process is killed between `set` and `get`, as acknowledged by the "wait a bit longer" comment for the related seedless-restore flow).
4. `assert(storedSeed.seed.equals(seed.seed), ...)` throws `setSeed failed`, but `SEED_KEY` in storage has already been overwritten with the new (unverified) value.
5. Subsequent `wallet.unlock({ passphrase: newPassphrase })` or `unlock({ passphrase: currentPassphrase })` both fail because neither the old nor a verified new seed exists in storage — the wallet is permanently unusable through this module, exactly mirroring the Keystore.sol "no way to do any more updates or validations" bricking scenario.
