No dedup validation exists anywhere in the withdrawal pipeline that would prevent two withdrawal legs with the same `assetId` in a single batch. The bug is real, reachable, and explicitly acknowledged (but not fixed) in the code comment itself.

### Title
`findMatchingWithdrawal` in POA bridge mismatches same-asset withdrawals within a batch, causing status/txHash misreporting - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal` resolves the withdrawal to report by matching only on `assetId` via `findMatchingWithdrawal`, ignoring `args.index`, so when a single NEAR intent tx contains two withdrawals of the same asset to different destinations, both `WithdrawalIdentifier`s (index 0 and index 1) can resolve to the same unsorted API record. This causes an integrator to observe the same `(status, txHash)` for two distinct withdrawal legs.

### Finding Description
The broken equality is: STATUS TRUTH — the `(status, txHash)` returned by `describeWithdrawal({index: i, ...})` should correspond to withdrawal leg `i`'s actual on-chain outcome. In [1](#0-0) , `describeWithdrawal` fetches all withdrawals for the NEAR tx hash and calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which is defined at [2](#0-1)  to `.find()` the first withdrawal in an admittedly-unsorted array whose `near_token_id` matches the assetId — `args.index` (i.e., `WithdrawalIdentifier.index`) is never consulted.

`createWithdrawalIdentifiers` in [3](#0-2)  assigns per-bridge-route sequential indices (0, 1, 2...) to each withdrawal leg sharing a route, without any dedup or same-asset check. `watchWithdrawal` in [4](#0-3)  then polls `describeWithdrawal` independently per identifier and reports back whatever `(status, txHash)` it gets.

Attacker input: an ordinary user signs one intent with two `transfer`-style withdrawal legs, both `nep141:btc.omft.near` (or any identical asset), to two different `destinationAddress` values, batched in one NEAR transaction. When both `describeWithdrawal` calls run (index 0 and index 1), each calls `getWithdrawalStatusWithRetry` with the same `args.tx.hash`, returning the same `response.withdrawals` array containing two `COMPLETED` records with distinct `transfer_tx_hash`. Because matching uses only `assetId`, `Array.prototype.find` returns the same first-matching element for both calls — both indices report the same status/txHash (or, worse, non-deterministic pairing that could invert which leg maps to which hash).

None of the existing guards catch this: `validateWithdrawal` and `supports()` validate per-leg parameters (address format, min amount) but never check for asset collisions across legs in the same batch; `FeeExceedsAmountError`/`getUnderlyingFee` are per-leg fee checks unrelated to this matching; the intents contract's own signature/nonce verification only ensures the batch was authorized as signed, not that off-chain status reporting is accurate post-execution. The code's own comment at lines 409-416 explicitly documents this as a known, unhandled limitation ("multiple withdrawals of the same token in a single transaction are not supported").

### Impact Explanation
An integrator relying on `sdk.waitForWithdrawalCompletion` / `createWithdrawalCompletionPromises` to credit or confirm each withdrawal leg by its returned `txHash` can attribute the wrong destination-chain transaction to a leg, or receive the identical txHash for both legs. This can lead to double-crediting one destination while leaving the other leg's actual completion/txHash unaccounted for — a status/hash misreport that causes an integrator to credit incorrectly, matching the High severity category ("a status or hash misreport making an integrator credit or refund twice"). This is repeatable on every batch containing two-or-more same-asset legs to different destinations, at zero cost to the attacker (an ordinary user simply constructs such a batch withdrawal, which the SDK permits).

### Likelihood Explanation
Preconditions are minimal and fully attacker-controlled: use PoA-bridge-eligible assets, submit ≥2 withdrawal legs with the same `assetId` in one `signAndSendWithdrawalIntent` batch call (the SDK's public batch API, e.g. `processWithdrawal`/`signAndSendWithdrawalIntent`, imposes no uniqueness constraint on assetId across legs — see `createWithdrawalIdentifiers` and `signAndSendWithdrawalIntent` at [5](#0-4) ). No special permissions, timing, or solver cooperation is needed; any ordinary user submitting a normal batch withdrawal triggers this. It is fully repeatable.

### Recommendation
Have `findMatchingWithdrawal`/`describeWithdrawal` disambiguate multiple same-asset withdrawals within one tx — e.g., sort both the API's `withdrawals` list and the local per-route same-asset legs by amount (as the code comment suggests) and pair by rank, or require the POA bridge API to return a stable per-leg identifier (e.g., output index) that the SDK can match against `args.index` instead of relying solely on `assetId`. Until then, the SDK should detect and reject (or explicitly warn/disallow) batches containing multiple PoA-bridge legs with the same `assetId`, rather than silently returning ambiguous status.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function watchWithdrawal(args: {
	bridge: Bridge;
	wid: WithdrawalIdentifier;
	signal?: AbortSignal;
	logger?: ILogger;
}): Promise<TxInfo | TxNoInfo> {
	const stats = getWithdrawalStatsForChain({
		chain: args.wid.landingChain,
		bridgeRoute: args.bridge.route,
	});
	let consecutiveErrors = 0;

	try {
		return await poll(
			async () => {
				try {
					const status = await args.bridge.describeWithdrawal({
						...args.wid,
						logger: args.logger,
					});

					consecutiveErrors = 0;

					if (status.status === "completed") {
						return status.txHash != null
							? { hash: status.txHash }
							: { hash: null };
					}

					if (status.status === "failed") {
						throw new WithdrawalFailedError(status.reason);
					}

					return POLL_PENDING;
				} catch (err: unknown) {
					if (err instanceof WithdrawalFailedError) {
						throw err;
					}

					consecutiveErrors++;
					if (consecutiveErrors >= MAX_CONSECUTIVE_ERRORS) {
						throw new WithdrawalWatchError(err);
					}

					args.logger?.warn(
						`Transient error (${consecutiveErrors}/${MAX_CONSECUTIVE_ERRORS}): ${err}`,
					);
					return POLL_PENDING;
				}
			},
			{ stats, signal: args.signal },
		);
	} catch (err: unknown) {
		if (err instanceof PollTimeoutError) {
			throw new WithdrawalWatchError(err);
		}
		throw err;
	}
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
