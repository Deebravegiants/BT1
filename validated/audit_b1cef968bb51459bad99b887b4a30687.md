### Title
Webhook `Registry.process` trusts the unsigned `shop-domain`/`topic` headers, allowing cross-tenant webhook spoofing after HMAC validation - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw HTTP body [1](#0-0) . The `shop`, `topic`, and `webhook_id` values that the handler subsequently trusts and acts on are parsed straight from HTTP headers and are never part of the signed content [2](#0-1) . This is the same class of bug as the referenced Juicebox finding: a value that is *acted on* (here, the tenant identifier `shop`) is not covered by the same integrity check (`HMAC`) that protects the body, so verifying the HMAC does not verify the shop-header binding.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [3](#0-2) . `hmac` is likewise extracted purely from the `hmac-sha256` header [4](#0-3) . `HmacValidator.validate` then simply recomputes `HMAC-SHA256(client_secret, raw_body)` and compares it to the received value [5](#0-4) .

Crucially, `shop`, `topic`, and `webhook_id` are read from the `shop-domain`, `topic`, and `webhook-id` headers, respectively [6](#0-5) , none of which are included in `to_signable_string`. `Registry.process` uses the unsigned `request.topic` to select the handler and passes the unsigned `request.shop` straight into `WebhookMetadata`, which the host application treats as the authenticated tenant identity for the event [1](#0-0) [7](#0-6) . The gem's own documentation instructs developers to trust `data.shop` as "The shop domain of the webhook" and to key business logic on it (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) [8](#0-7) , so this is the gem's documented, intended usage — not host-application misuse.

The identity binding that should hold is:
`shop header used by handler == shop that actually produced the HMAC-signed body`

But the gem only proves:
`HMAC(client_secret, raw_body) == received_hmac`

It never proves that the `shop-domain` header presented alongside that body is the shop that generated it. Because `client_secret` is a single secret shared by the app across *every* merchant that installs it (it is not shop-specific), any unprivileged internet user who installs the target app on their own (even free/dev) store can:
1. Trigger a real webhook from their own store to obtain a validly-signed `(raw_body, hmac)` pair, where they control much of `raw_body` (e.g., product/order fields they created).
2. Replay that exact `raw_body` and `hmac` value directly to the app's public webhook endpoint (the same endpoint receives events for all merchants), while substituting the `Shopify-Shop-Domain` header (or `X-Shopify-Shop-Domain`) with a victim shop's domain.
3. `HmacValidator.validate` still succeeds, because the header substitution never touched `to_signable_string`.
4. `Registry.process` calls the handler with `WebhookMetadata.shop` = the forged victim domain and attacker-influenced `body`, impersonating an event from the victim tenant.

### Impact Explanation
This breaks the cross-tenant boundary the webhook subsystem is meant to enforce: the host application, following the gem's documented usage, will attribute attacker-controlled webhook data to an arbitrary victim `shop` value, since nothing in the gem binds the header-derived `shop` to the HMAC-verified body. Depending on how the host app uses `data.shop` (e.g., updating per-shop records, triggering GDPR `shop/redact`/`customers/redact`/`customers/data_request` compliance flows, enqueueing shop-scoped jobs), this enables spoofed events "from" a shop the attacker does not control — a cross-tenant identity/authorization bypass.

### Likelihood Explanation
Likelihood is high in principle for any app that is installable by the public (dev stores, free-tier installs) because obtaining a legitimately signed `(body, hmac)` pair only requires installing the app on an attacker-owned store, no access to `client_secret`, access tokens, or victim credentials required. The main constraint is how much of `raw_body` the attacker can influence for the topics they care about, and how strictly the host app's `WebhookHandler#handle` implementation depends on `data.shop` for authorization-sensitive logic — this varies by app and could not be fully confirmed without a specific host application's handler code.

### Recommendation
Bind the transported identity to the signed payload rather than trusting header fields independently of the HMAC:
- Include `shop`, `topic`, and `webhook_id` in the value that is HMAC-verified (e.g., verify an HMAC over `headers + body`, or require the host app to cross-check `request.shop` against the shop associated with the specific `webhook_id`/subscription that was registered via `Registry.register`), and/or
- Document explicitly that `WebhookMetadata.shop`/`topic` are **not** cryptographically bound to the signed body and must be independently corroborated (e.g., against the app's own webhook subscription records) before being used for tenant-scoped actions.

### Proof of Concept
Given `Registry.process`'s only check [9](#0-8) :
```ruby
# Attacker installs the target app on their own store "attacker.myshopify.com"
# and triggers, e.g., an orders/create webhook, capturing:
raw_body = '{"id":123,"note":"hi"}'   # legitimately signed by Shopify using the app's shared client_secret
hmac_b64 = "..."                       # the real, valid signature for raw_body

# Attacker POSTs directly to the app's public webhook endpoint, replaying the
# exact body/hmac pair but forging the shop header:
headers = {
  "shopify-topic"        => "orders/create",
  "shopify-hmac-sha256"  => hmac_b64,        # still valid for raw_body
  "shopify-shop-domain"  => "victim.myshopify.com",  # forged, unsigned
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (HMAC only covers raw_body)
# => handler.handle(data: WebhookMetadata.new(shop: "victim.myshopify.com", ...))
```
`request.shop` is derived solely from the header [10](#0-9) , and `to_signable_string` never includes it [3](#0-2) , so the forged `shop-domain` value passes through unchanged into the handler.

```markdown
If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
```
