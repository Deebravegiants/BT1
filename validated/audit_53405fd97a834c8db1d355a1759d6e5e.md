### Title
Unchecked ERC20 return value in `IntentGatewayV2.withdraw()`/`SweepDust` allows escrow accounting to finalize without an actual token transfer, permanently freezing user funds - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron `IntentGatewayV2` contract manually invokes `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only checks that the low-level `call` succeeded, but never decodes/validates the boolean return value of `transfer()`. This is the exact "use safeTransfer()" bug class from the referenced report: a non-reverting ERC20 that returns `false` on failure will make `success == true` even though no tokens moved, yet the code proceeds to permanently finalize escrow state.

`success` here only reflects whether the external call itself did not revert — it does not decode the ABI-encoded `bool` that a compliant `transfer()` implementation returns. A non-standard, non-reverting ERC20 (one that signals failure by returning `false` rather than reverting — e.g. old-style tokens such as ZRX, or a token that simply fails silently under some edge condition like insufficient balance) will cause `success` to be `true` even though the beneficiary received nothing.

Despite this, immediately after the unchecked call, the escrow accounting is decremented and the order marked terminal: [4](#0-3) 
and `_filled[body.commitment] = beneficiary;` is set at the top of the function, so the order can never be retried through `withdraw()` again — a second attempt reverts with `UnknownOrder()` because `_orders[body.commitment][token]` is already zero: [5](#0-4) 

By contrast, the canonical (non-Tron) implementation of the same escrow-release logic correctly uses OpenZeppelin's `SafeERC20.safeTransfer`, which decodes the return value and reverts on `false`: [6](#0-5) 

The Tron contract even imports `SafeERC20`/`IERC20` and uses `safeTransferFrom` on the deposit path, but deliberately bypasses `safeTransfer` on the payout path in favor of the unchecked raw `.call`: [7](#0-6) 

### Impact Explanation
If a token used in an order's inputs/outputs returns `false` instead of reverting on a failed transfer (a well-known non-standard-but-common ERC20 behavior), the escrow's internal ledger (`_orders[commitment][token]`) is nonetheless zeroed and the order is marked filled/refunded, permanently finalizing state as if the beneficiary was paid. Since `IntentGatewayV2` allows arbitrary user/solver-specified ERC20 tokens for order inputs/outputs, an attacker (order creator, solver, or filler) can construct an order that references such a token. The tokens then remain stuck in the contract with no state pointing to them (the escrow entry is deleted), resulting in a permanent freeze/loss of the beneficiary's funds. This satisfies "permanent freezing of funds" impact criteria.

### Likelihood Explanation
This is reachable from a single relayed/verified message: an ISMP POST request carrying a `RedeemEscrow`/`RefundEscrow` body (authenticated via `authenticate(incoming.request)`), or a GET response processed by `onGetResponse`, both of which are standard, permissionless relayer-delivered flows in Hyperbridge's intents system — no privileged role is required beyond choosing which ERC20 token to place in the order, which is fully attacker/solver controlled.

### Recommendation
Replace the manual `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` and the `SweepDust` handler with `SafeERC20.safeTransfer` (already imported via `using SafeERC20 for IERC20;`), consistent with the deposit-side `safeTransferFrom` calls and with the canonical `IntentsBase.sol` implementation, so that non-standard `false`-returning tokens cause a revert instead of silently finalizing escrow state.

### Proof of Concept
1. An order is created (or a solver fills an order) whose output/input token is a non-reverting ERC20 that returns `false` on failed `transfer()` (e.g., low balance or blacklist condition it silently rejects instead of reverting).
2. A relayer delivers a valid `RedeemEscrow` POST request to `onAccept`, which calls `withdraw(body, false)`.
3. Inside `withdraw`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `success = true` (the call executed) even though the token's internal logic returned `false` and moved no funds.
4. `_orders[body.commitment][token] -= amount;` zeroes the escrow entry and `_filled[body.commitment] = beneficiary;` finalizes the order; `EscrowReleased` is emitted.
5. The beneficiary never received the tokens, and `_orders[body.commitment][token]` being zero means no other function path can now claim or recover them — the tokens are permanently stuck in the `IntentGatewayV2` contract.

        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
