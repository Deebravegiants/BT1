### Title
Inconsistent identity-binding verification across QR-code format branches allows unverified signup identity binding - (File: src/backend/user_status.rs)

### Summary
The `request` function in `src/backend/user_status.rs` decides whether to accept a scanned user QR-code and the associated `UserData` (public keys, identity commitment, custody settings) that will drive the rest of the signup flow. Depending on which branch of a conditional is taken, the code either cryptographically verifies the backend-issued `authenticated_app_data` against the QR-code's `user_data_hash`, or skips verification entirely and falls back to defaults. This mirrors the structure of the reported bug class: a binary decision point where one branch enforces an extra integrity check and the other silently omits it, creating an inconsistency that can be exploited to influence the outcome (here, signup identity binding) depending on which branch is reached.

### Finding Description
`backend::user_status::request` fetches `backend_keys` and `authenticated_app_data` from the backend and then branches on whether both are present: [2](#0-1) 

In this branch, the code requires a `user_data_hash` from the QR-code and calls `user_data.verify(user_data_hash)` before trusting `identity_commitment`, `self_custody_public_key`, and the backend-provided cryptographic keys — this is the path that binds the physically-scanned QR-code to the backend-asserted identity/keys.

However, when `backend_keys`/`authenticated_app_data` are absent, execution falls into the `else` branch ("Using an old QR-code format"): [3](#0-2) 

Here the only check performed is that the QR-code itself must not carry a `user_data_hash` (`if qr_code.user_data_hash.is_some() { ...return Ok(None) }`). If the QR-code has no hash, the function unconditionally returns a `UserData` with `id_commitment: None`, `self_custody_user_public_key: None`, and no backend keys at all — i.e., no cryptographic binding is performed at all, and the outcome (`Some(UserData)`, i.e., "valid") is returned exactly like the verified branch, without the equivalent of the `verify()` step being applied to anything (there being nothing to verify in this legacy path).

This exactly parallels the `getPriorVotes` binary-search flaw: one branch (`center` hit) returns a value while skipping the additional `getUnclaimedVotes` component that every other branch includes, producing an inconsistent, exploitable result. Here, one branch (new QR format) enforces `verify()` before returning `Some(UserData)`; the other branch (legacy format) returns `Some(UserData)` unconditionally as long as a superficial precondition (`user_data_hash.is_none()`) holds, without any equivalent cryptographic assurance that the returned identity data actually corresponds to the operator/backend session that was validated. Because the branch selection is driven only by whether the backend chooses to populate `backend_keys`/`authenticated_app_data` (not by anything the orb can independently verify from the QR-code alone before this call), this inconsistency in enforcement is structurally identical to the reported bug class.

### Impact Explanation
If the "old"/legacy branch can be reached for a session where identity-binding is expected to be enforced (e.g., a compromised or misbehaving backend response for a given `user_id` that omits `backend_keys`/`authenticated_app_data`), the orb will proceed with a `UserData` that has no `id_commitment` and no self-custody public key bound to the scanned QR-code, i.e., unauthenticated. This can result in a signup being processed as an old-format flow where no verification linking the physical QR scan to the identity data occurs, undermining the identity-binding guarantee that the new-format path is specifically designed to enforce, and potentially enabling misattributed signup / identity-binding bypass.

### Likelihood Explanation
Reaching the unverified branch does not require compromising the orb; it only requires the backend response for `/api/v1/user/{id}/status` (or v2 variants) to omit `backendKeys`/`authenticatedAppData`, which is exactly the legacy/back-compat code path already wired into production logic and reachable by any user-controlled signup session whose QR-code lacks a `user_data_hash`. No special privileges are needed beyond running a normal signup with a legacy-format QR-code.

### Recommendation
Make identity-binding verification handling consistent across both branches: either require an explicit backend-signed attestation that legacy/unauthenticated user data is intentionally allowed for that session, or perform an equivalent integrity check in the legacy branch (e.g., verifying a signed statement that no additional identity data is expected for this `user_id`) so that a discrepancy in the two code paths cannot be leveraged to skip identity-binding checks that the new-format path enforces.

### Proof of Concept
1. Trigger a signup where `backend::user_status::request` is called with a `qr_scan::user::Data` whose `user_data_hash` is `None` (a "v2" or legacy-format QR-code, per `Data::from_v2` in `src/plans/qr_scan/user.rs`, which leaves `user_data_hash: None`). [4](#0-3) 
2. Have the backend (or an attacker able to influence the backend's response for that endpoint) return `valid: true` while omitting `backendKeys` and `authenticatedAppData`.
3. Observe that `request` falls into the `else` branch and returns `Ok(Some(UserData { id_commitment: None, self_custody_user_public_key: None, ... }))` without performing any cryptographic verification analogous to `user_data.verify(user_data_hash)`, in contrast to the branch used when `backendKeys`/`authenticatedAppData` are present.
