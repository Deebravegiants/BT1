### Title
Webhook shop/topic/webhook_id/api_version headers are unauthenticated and not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` (plus `topic`, `webhook_id`, `api_version`) directly from HTTP headers, but the HMAC signature validated in `ShopifyAPI::Webhooks::Registry.process` only covers the raw request body, not these header values.

### Finding Description
The bug class from the report is "a fake/unauthenticated actor can cause privileged code to act on data that is not covered by the integrity check." In `Splitter.sol` the missing check was on the caller; here the missing binding is between the HMAC signature and the header-derived identity fields.

`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, `#api_version` are all read straight from attacker-controlled HTTP headers with no cryptographic binding to the body or to the HMAC: [2](#0-1) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` (i.e., the raw body only) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` accepts the request once this body-only HMAC check passes, and then trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` as authenticated metadata handed to the app's handler: [4](#0-3) 

The equality this breaks: `shop_header == shop_the_HMAC_actually_authenticates_for`. The library implicitly presents `request.shop` as verified (it passed `Registry.process`, which raises `InvalidWebhookError` on bad HMAC), but the HMAC only proves "this body, once, was signed with `client_secret`" — it says nothing about which shop, topic, or webhook_id that signature is bound to.

### Impact Explanation
An unprivileged attacker who controls (or has installed) a shop with the app, or who otherwise obtains one legitimate `(raw_body, hmac)` pair for any webhook topic that shares a body shape across shops (e.g., topics with an empty or attacker-influenced body, or a topic whose body the attacker fully controls, such as a custom app-created resource), can replay that exact body+hmac pair to the app's webhook endpoint while substituting a different `x-shopify-shop-domain` (or `x-shopify-topic` / `x-shopify-webhook-id`) header. Because `Registry.process` only verifies the body against the HMAC and never verifies the header values are part of the signed content, the request passes validation and the handler receives `WebhookMetadata` with a forged `shop`/`topic`/`webhook_id`. Any host application that uses `data.shop` from this gem's `Registry.process` output to decide which merchant's data/session to act on (the officially documented pattern, see `docs/usage/webhooks.md`) can be tricked into cross-tenant actions — e.g., processing a `shop/redact` or app-uninstall style webhook against a shop the attacker doesn't own, or having order/product data attributed to the wrong tenant. This satisfies the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only an internet-reachable webhook endpoint (which every app that follows the documented `Registry.process` usage exposes) and one legitimate/replayable `(body, hmac)` pair, obtainable by an attacker who installs the app on their own shop (a normal, credential-free action for any Shopify user) and captures a webhook Shopify sends them. No access token, `client_secret`, or privileged account is required — only the ability to send an HTTP POST to the app's public webhook route with modified headers and a captured body/hmac. This is a low-effort, no-privilege attack path, though it depends on the host app trusting the shop field for tenant routing, which is exactly what the gem's documented API encourages.

### Recommendation
Include the identity-relevant fields (`shop`, `topic`, `webhook_id`, `api_version`) in the signed payload used by `to_signable_string`, or otherwise cryptographically bind them to the HMAC (e.g., by validating that these header values match values embedded/signed within the body, or documenting explicitly and enforcing that consuming apps must independently re-verify `shop` against their own installed-shop registry before trusting `WebhookMetadata`). At minimum, the gem should not implicitly present `WebhookMetadata.shop`/`topic`/`webhook_id` as verified/authenticated when only the raw body was checked.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (no special privileges needed) and triggers a webhook whose body content is attacker-controlled or predictable (e.g., a topic with an empty JSON body `{}` as used in the test fixtures).
2. Attacker captures the resulting `(raw_body="{}", x-shopify-hmac-sha256=<valid HMAC over "{}">)` pair — trivially reproducible since `HmacValidator` accepts any raw body signed with the app's known `client_secret`-derived HMAC for `{}` (illustrated in `test/webhooks/registry_test.rb` lines 16-20 where the same `{}`-body HMAC is reused across differing header sets).
3. Attacker POSTs to the app's public webhook endpoint with:
   - `raw_body = "{}"`
   - `x-shopify-hmac-sha256 = <the captured valid HMAC>`
   - `x-shopify-shop-domain = victim-shop.myshopify.com` (forged)
   - `x-shopify-topic = <any registered topic>` (forged)
4. `HmacValidator.validate` recomputes HMAC over `"{}"`, which matches, so `Registry.process` proceeds and invokes the handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, even though Shopify never sent this webhook for that shop. [4](#0-3) [5](#0-4)

module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end

      sig { returns(String) }
      def topic
        T.cast(shopify_header("topic"), String)
      end

      sig { returns(String) }
      def shop
        T.cast(shopify_header("shop-domain"), String)
      end

      sig { returns(String) }
      def api_version
        T.cast(shopify_header("api-version"), String)
      end

      sig { returns(String) }
      def webhook_id
        T.cast(shopify_header("webhook-id"), String)
      end

      sig { override.returns(String) }
      def to_signable_string
        @raw_body
      end

      sig { returns(T::Hash[String, T.untyped]) }
      def parsed_body
        JSON.parse(@raw_body)
      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate(verifiable_query)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
