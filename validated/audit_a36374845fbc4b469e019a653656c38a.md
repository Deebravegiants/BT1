### Title

RAY value overflow during interest accrual permanently freezes a high-utilization market - ([File: contracts/pool/src/cache/scale.rs](contracts/pool/src/cache/scale.rs))

### Summary

A market with sufficiently large scaled balances can reach an `i128` RAY-value overflow before its borrow-index ceiling engages. Because the pool accrues interest before processing subsequent operations, the resulting `MathOverflow` panic blocks later withdrawals, repayments, liquidations, and index updates for that market. [1](#0-0) 

### Finding Description

Market balances are stored as scaled shares and converted through RAY indexes. In the demonstrated failure, an 18-decimal market holding `1_000_000_000` whole units is driven to 98% utilization. Repeated accrual eventually makes `scaled_to_original` overflow even though `borrow_index` remains below `MAX_BORROW_INDEX_RAY`. [2](#0-1) 

The strongest unprivileged path is:

1. `supply(caller, account_id, spoke_id, assets)` with a very large amount of the selected market asset.
2. `borrow(caller, account_id, borrows, to)` to establish sustained high utilization.
3. Allow interest accrual to advance the borrow index.
4. Any later `update_indexes`, `withdraw`, `repay`, `borrow`, `liquidate`, or `flash_loan` touching that market loads the cache and accrues first.
5. Accrual reaches `scaled_to_original` and aborts with `MathOverflow`; the failed call cannot recover the market because every recovery path performs the same accrual first. [3](#0-2) 

The same panic is not limited to the attacker’s transaction: it is caused by persisted market balances and indexes, so subsequent unrelated callers encounter it when interacting with the same market.

### Impact Explanation

This permanently freezes supplier and borrower funds in the affected market. Suppliers cannot withdraw, borrowers cannot repay normally, liquidators cannot liquidate through the controller, and keeper-initiated `update_indexes` cannot restore operability because those paths all perform the overflowing accrual before their state changes. [4](#0-3) 

The failure therefore satisfies permanent freezing of funds and can leave existing debt uncollectible through the ordinary liquidation path.

### Likelihood Explanation

The attack is conditional rather than one-call practical: it requires a listed market capable of accepting a very large position, enough real tokens to fund it, and sustained high utilization long enough for the scaled RAY value to reach the `i128` ceiling. Those requirements reduce likelihood, but no privileged action is needed after governance has listed the market; the unprivileged supplier/borrower controls the position size and utilization that create the state.

The condition is also silent until the first accrual after the bound is crossed. At that point the panic is deterministic and cannot be avoided by changing call arguments, because the panic occurs before the requested operation executes.

### Recommendation

Bound the scaled-to-underlying conversion itself, not only the borrow index. In particular:

- Detect when `scaled_amount * index` would exceed the supported `i128` RAY-value domain before multiplication.
- Clamp or otherwise safely cap accrual at the largest representable underlying value instead of panicking.
- Add a pre-accrual invariant that markets remain below the conversion ceiling, including revenue and borrow-share calculations.
- Reject supply or borrow that would put the market too close to the value ceiling, accounting for future index growth.
- Add a recovery-safe accrual path or explicit saturated-market state so repayment and withdrawal remain possible after the bound is reached.
- Extend the existing regression around `scaled_to_original` to assert that the index cap engages before conversion overflow.

### Proof of Concept

The repository already contains a deterministic harness reproduction:

```rust
// tests/test-harness/tests/controller/large_positions_and_long_horizons.rs

let mut t = LendingTest::new()
    .with_market(big("BIG18", 18, xlm_curve()))
    .with_market(col())
    .with_max_utilization_disabled_all_markets()
    .build();

lift_caps(&t, "BIG18", 18);
lift_caps(&t, "COL", 7);

let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);

let debt = principal / 100 * 98;
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);

loop {
    t.advance_time(YEAR_SECS);
    if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
        break;
    }
}
```

The test then observes `MathOverflow` while `borrow_index < MAX_BORROW_INDEX_RAY`, proving that the value ceiling is reached before the intended index cap. Subsequent `withdraw` and `repay` calls fail with the same overflow. [5](#0-4)

```rust
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```
