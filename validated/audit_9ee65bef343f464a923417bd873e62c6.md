### Title
`Webhooks::Registry.process` trusts the `shop`/`topic` headers without covering them by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating `Utils::HmacValidator.validate(request)`, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` — all of which are read straight from unauthenticated HTTP headers and are never included in the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are pulled from headers that are never part of the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` only recomputes `HMAC(secret, verifiable_query.to_signable_string)` and compares it against the received `hmac`: [3](#0-2) 

`Registry.process` uses this validation result as the sole authentication gate, then dispatches to the handler using the unauthenticated header-derived `shop`/`topic`/`webhook_id`: [4](#0-3) 

This is exactly the bug class in the report: a downstream consumer trusts a decoded/parsed field without recomputing or verifying that field against the authenticated commitment. Here, the intended invariant is `HMAC_valid(body) ⟹ shop/topic headers are authentic for that body`, but the implementation only proves `HMAC_valid(body)`; the `shop` and `topic` headers are never cryptographically bound to the signature. Because the app's webhook HMAC key (`Context.api_secret_key`, i.e., the app's `client_secret`) is identical across every shop that installs the app, any store owner who installs the app can capture a genuinely-signed `(body, hmac)` pair delivered to their own store, then replay that exact body and HMAC to the app's single shared webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header for a victim tenant's values. The signature still validates because it only covers the body, so the handler executes with `shop: "victim-shop.myshopify.com"` even though the payload never actually originated from that shop.

### Impact Explanation
This breaks the tenant identity binding `HMAC_valid(body) == (shop_header is authentic)`, allowing an unprivileged merchant who has merely installed the app on their own store to forge webhook deliveries attributed to a different, victim tenant. Depending on how the host application's webhook handlers key business logic off `WebhookMetadata#shop` (e.g., syncing state, revoking access, updating billing/customer records, or reacting to `app/uninstalled`/`shop/redact` for a shop the attacker doesn't own), this enables cross-tenant data corruption or cross-tenant side effects — matching the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Requires only that the attacker be able to install the target app on a store they control (a standard, unprivileged action available to any Shopify merchant) and capture one legitimate webhook delivery to their own endpoint — no access to `api_secret_key`, access tokens, or any victim credential is needed. The replay itself is a straightforward HTTP request with modified headers, since `Registry.process` never re-derives or cross-checks the `shop`/`topic` against anything bound to the signature.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signable material (or otherwise cryptographically bind them, e.g., via a per-shop signing key or by validating the header `shop` against the shop stored for the session/installation that owns the webhook subscription) before dispatching to handlers, mirroring how `decodeRctSimple()` recomputes and compares the commitment rather than trusting the decoded tuple.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and registers a webhook (e.g., `customers/create`).
2. Shopify delivers a webhook to the app's endpoint with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)`; attacker records `(B, HMAC)`.
3. Attacker sends `POST` to the same shared webhook endpoint with body `B`, the same `x-shopify-hmac-sha256` header, but `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`).
4. `HmacValidator.validate` passes because it only checks `B` against `HMAC`; `Registry.process` invokes the handler with `shop: "victim-shop.myshopify.com"`, causing the app to process attacker-controlled data as if it originated from the victim tenant.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end
