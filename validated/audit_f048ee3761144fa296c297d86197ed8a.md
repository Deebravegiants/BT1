### Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` are trusted without being covered by the HMAC, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop`, `topic`, `webhook_id`, and `api_version` values that the app actually acts on are read straight from unauthenticated HTTP headers and are never part of the signed bytes. Any entity capable of obtaining one genuine, HMAC-valid webhook delivery (i.e. any merchant who installs the app on their own store) can replay that exact body/HMAC pair while substituting an arbitrary `shop-domain` header, and the registry will accept it as authentic data belonging to that spoofed shop.

### Finding Description
The webhook signature is computed and checked only over the raw body: [1](#0-0) 

`Utils::HmacValidator.validate` verifies exactly that signable string against the app's `api_secret_key`: [2](#0-1) 

But the values that identify *whose* webhook this is — `shop`, `topic`, `webhook_id`, `api_version` — are pulled directly from HTTP headers that are not part of the signed payload: [3](#0-2) 

`Registry.process` verifies only the body HMAC and then forwards these unauthenticated header values straight to the app's handler as trusted metadata: [4](#0-3) 

The broken identity binding, stated as an equality that should hold but doesn't:
`HMAC_verified(bytes) == bytes_the_app_uses_to_identify_the_tenant`
In reality: `HMAC_verified(bytes) = raw_body` while `tenant_identity_used_by_handler = headers[shop-domain]`, and the latter is never included in the former. Since the webhook HMAC secret (`api_secret_key`) is the same for every shop that has the app installed (it is the app's own secret, not a per-shop secret), any merchant who installs the app on their own store can obtain a genuinely-signed `(body, hmac)` pair for their own shop, then re-send that identical body/HMAC to the app's webhook endpoint with the `shop-domain` (and `topic`/`webhook_id`/`api_version`) header rewritten to point at a different, victim shop. `Utils::HmacValidator.validate` still returns `true` because it never looked at those headers, and `Registry.process` will dispatch the attacker-controlled body to the handler labeled as data belonging to the victim shop.

### Impact Explanation
This breaks the tenant boundary the host application relies on: `WebhookMetadata#shop` is the field apps use to decide which merchant's records to update, delete, or resync in response to a webhook. An attacker who is merely a legitimate, unprivileged merchant of the app (no leaked secrets, no privileged account, no host cooperation needed) can cause the app to process attacker-chosen webhook content under another tenant's identity — a cross-tenant access/confusion primitive, matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Likelihood is high for any multi-tenant app built on this gem: obtaining a genuine webhook delivery only requires installing the app on one's own shop (the normal, unprivileged onboarding flow), and replaying it with a modified header is a trivial HTTP request. No secret material, TLS interception, or social engineering is required.

### Recommendation
Bind the header-derived identity fields (`shop`, `topic`, `webhook_id`, `api_version`) into the HMAC-verified surface, e.g. by including the `shop-domain` header (and other routing headers the handler trusts) in `to_signable_string`, or by independently verifying that the `shop-domain` header corresponds to a shop/session the app actually expects for the given webhook subscription before dispatching to the handler.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and triggers a webhook event (e.g. `orders/create`), receiving a genuine `POST` with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and body `B`.
2. Attacker resends the exact same body `B` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `@raw_body` only (`request.rb:35-38`, `hmac_validator.rb:26-31`) — it matches, since the body and secret are unchanged.
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` (`registry.rb:198-199`) using the spoofed `victim.myshopify.com`, and the host app's handler processes attacker-controlled data as if it originated from the victim shop.
