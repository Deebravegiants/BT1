Based on my investigation, I found a strong analog to the funding-rate identity-binding bug.

### Title
Webhook `shop`/`topic` identity is trusted from unauthenticated headers while HMAC only binds the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by verifying an HMAC over the raw request body, then hands the handler an unauthenticated `shop` (and `topic`) value taken straight from HTTP headers, without ever binding those header values into the signature that was checked.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`, and `hmac` is derived from the `hmac-sha256` header — no other header participates in the signable string: [1](#0-0) 

`Utils::HmacValidator.validate` recomputes `HMAC(secret, signable_string)` and secure-compares it to the received HMAC: [2](#0-1) 

`Registry.process` uses this validation as the sole authenticity gate, then dispatches to the handler using `request.shop` and `request.topic`, both parsed straight out of headers that were never part of the signed material: [3](#0-2) [4](#0-3) 

The equality that should hold is: **the shop whose secret produced a valid HMAC == the shop attributed to the processed event**. Because `shop-domain` (and `topic`, `webhook-id`, `api-version`) are outside the HMAC's signable string, that equality is never enforced. Any request carrying a `raw_body`/`hmac` pair that is valid for the app's `client_secret` — including a stale/legitimately-received webhook that the attacker (as one of the app's own installed merchants) previously captured for their own shop — will still pass `HmacValidator.validate` even after the `shop-domain` header is swapped to an arbitrary value (e.g. a victim shop already installed on the same app), or the `topic` header is swapped to any topic the app has registered a handler for.

This is the direct analog of the audited bug: the check (HMAC over body) answers a narrower question ("is this body byte-for-byte something the app secret once signed?") than the question the code treats it as having answered ("did this event genuinely originate from and describe shop X on topic Y?"). The `bytes verified versus bytes parsed` / `shop authenticated versus shop attributed` binding is broken exactly the way `overbalancedValue` was used to stand in for the unrelated "amount of imbalance Float actually covered."

### Impact Explanation
An attacker who is a merchant of the target app (or otherwise obtains one valid `raw_body`+`hmac` pair, e.g. via mandatory GDPR webhooks sent to every installed shop, or via any endpoint that echoes a previously delivered payload) can replay that exact body/HMAC to the app's webhook endpoint with a forged `shop-domain` header pointing at a different, victim shop already using the same app, and/or a forged `topic` header selecting any registered handler. `WebhookHandler#handle` receives `data.shop` and `data.topic` as attacker-controlled values while `data.body` still validates against `Utils::HmacValidator`, so the app's business logic (order processing, redact/uninstall flows, metafield sync, etc.) will act on the victim shop's tenant record using attacker-supplied content. This is cross-tenant data injection scoped to shops installed on the same app — the impact category the rules classify as Critical (cross-tenant access).

### Likelihood Explanation
Any app author following the documented pattern in `docs/usage/webhooks.md` (`ShopifyAPI::Webhooks::Registry.process(ShopifyAPI::Webhooks::Request.new(raw_body: ..., headers: ...))`) is exposed, since the gem performs no additional binding and gives no indication that `shop`/`topic` require independent authentication. Obtaining one valid signed payload requires only having a shop installed on the target app (mandatory compliance webhooks are delivered to every install), making this reachable by an unprivileged, otherwise-legitimate merchant of the app — no leaked secrets or privileged access required.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC's signable material, or otherwise re-derive/verify the shop identity from data covered by the signature (e.g. from the body payload itself where Shopify includes shop-level identifiers) before trusting `request.shop`/`request.topic` for dispatch. At minimum, document prominently that `HmacValidator` only authenticates body integrity/provenance and that callers must independently verify `shop`/`topic` headers are consistent with an expected/installed shop before acting on them.

### Proof of Concept
1. App A has two installed shops: `attacker.myshopify.com` and `victim.myshopify.com`.
2. Shopify sends a mandatory webhook (e.g. `customers/data_request`) to App A for `attacker.myshopify.com`; the attacker (owner of that shop, or anyone with access to their webhook endpoint logs) captures `raw_body` and the `x-shopify-hmac-sha256` header value.
3. Attacker POSTs to the same webhook endpoint with headers `x-shopify-shop-domain: victim.myshopify.com`, `x-shopify-topic: <any registered topic>`, and the identical `raw_body` + `x-shopify-hmac-sha256`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `raw_body` against the HMAC — validation succeeds: [5](#0-4) 
5. The handler executes with `data.shop == "victim.myshopify.com"` and `data.topic` set to the attacker's chosen topic, even though nothing about this specific request was ever authenticated for that shop or topic.

          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
