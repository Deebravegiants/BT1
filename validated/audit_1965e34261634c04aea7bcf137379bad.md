## Analysis

Tracing the flow: `Hinkal.transact` → `_externalTransact` transfers `-deltaAmountChanges[i]` (for negative deltas) from `Hinkal` to the Emporium contract *before* calling `runAction` [1](#0-0) . Inside `EmporiumUpgradeable.runAction`, `balancesBefore` is snapshotted *after* that deposit already landed, then arbitrary ops run, `payRelayFees` executes, and `balancesAfter` is snapshotted; `balanceChange` is adjusted by `-deltaAmountChanges[i]` only when negative, and the entire resulting positive `balanceChange` for each token is sent to `msg.sender` (the current caller) via `handleOut` [2](#0-1) .

The critical fact is that `balancesBefore`/`balancesAfter` are the Emporium contract's *global* on-chain token balances, not funds earmarked to this specific caller. The comment at line 141 even acknowledges "the only case when balanceChange can be < 0, when there were some funds on emporium before the call" — confirming the design intentionally tolerates residual/stranded balances sitting in the shared Emporium contract across transactions (e.g., from multi-step/limit-order-style flows).

The "Stateless Interaction" branch executes attacker-fully-controlled `op.endpoint.call(op.callData)` from the Emporium contract's own context (`address(this)` = Emporium) [3](#0-2) . The only restriction is blocking `callHinkalWallet`/`doSendToRelay` selectors [4](#0-3) . Nothing prevents an attacker from setting `op.endpoint = <any ERC20 token in erc20TokenAddresses>` and `op.callData = approve(attackerAddress, type(uint256).max)`. Since `approve` doesn't move balance, `balanceChange` for that token is unaffected by this op and the attacker's own `runAction` call completes and passes all checks cleanly (an `approve()` call doesn't violate the `balanceChange >= 0` or balance-diff invariants in `Hinkal.transact` either, since `approve` doesn't change balances) [5](#0-4) .

This leaves a persistent, unlimited ERC20 `approve` from the Emporium contract to an attacker-controlled address, permanently outstanding on-chain. Because Emporium is a shared contract whose balance can legitimately hold other users' in-flight/parked funds between transactions (per the design comment above, and per multi-step Emporium op flows), the attacker can later call `token.transferFrom(emporium, attacker, amount)` directly against the ERC20 contract — completely bypassing `Hinkal.transact`, `performHinkalChecks`, proof verification, nullifier insertion, and the `-deltaAmountChanges` accounting equality entirely, since this withdrawal never goes through `runAction` or `Hinkal.transact` at all.

This satisfies the stated invariant violation: tokens leave the Emporium/protocol with `-deltaAmountChanges == 0` for that attacker transaction (or any transaction at all), i.e., value leaves the system that was never counted by Hinkal's balance/UTXO accounting.

### Title
Unrevoked ERC20 approvals granted by attacker-controlled Emporium ops enable theft of any funds later held by EmporiumUpgradeable - (contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction`'s stateless op path executes fully attacker-controlled `endpoint.call(callData)` from the Emporium contract's own address, with no restriction against calling `approve()` on any token in `erc20TokenAddresses`. Because `approve` doesn't move balances, this passes all existing accounting checks in the same transaction, but leaves a permanent unlimited allowance to an attacker-controlled address that can later be redeemed via a plain `transferFrom` call, completely outside Hinkal's proof/nullifier/accounting system.

### Finding Description
The broken equality: tokens leaving Emporium in a given (attacker) transaction should equal `-deltaAmountChanges` Hinkal sent it that transaction. An attacker submits `Hinkal.transact` → `_externalTransact` → `EmporiumUpgradeable.runAction` with `externalActionMetadata` encoding an `EmporiumStack` containing one stateless `EmporiumOperation` where `op.endpoint = <token address present in erc20TokenAddresses>` and `op.callData = abi.encodeCall(IERC20.approve, (attackerControlled, type(uint256).max))`. This call is executed via `op.endpoint.call{value: op.value}(op.callData)` [6](#0-5) , with `address(this)` (the token owner in the `approve` call) being the Emporium contract itself. Nothing in `runAction`, `handleOut`, or `Hinkal.transact`'s balance-diff checks detects or prevents this because `approve` leaves `balanceChange == 0` for that token in that transaction, satisfying `balanceChange >= 0` and the `Hinkal.transact` slippage/balance-diff equalities trivially. Later — in a completely separate transaction that never touches `Hinkal.transact`, `verifyProof`, `insertNullifiers`, or any Hinkal check — the attacker calls `token.transferFrom(emporiumAddress, attacker, amount)` directly on the ERC20 contract, draining whatever balance the shared Emporium contract holds of that token at that time (e.g., funds another user deposited via a negative `deltaAmountChanges` leg for a multi-step Emporium operation, or residual/stranded balance the code's own comments acknowledge can exist: "the only case when balanceChange can be < 0, when there were some funds on emporium before the call").

### Impact Explanation
Direct theft of other users' in-flight/shielded funds that are temporarily held by the shared `EmporiumUpgradeable` contract, entirely bypassing Hinkal's proof and nullifier system — this is a Critical impact (direct theft of shielded or in-flight user funds). The attack is repeatable: a single approval, once planted, remains a standing threat that can be exercised any number of times whenever new balance appears in the contract, at zero marginal cost beyond gas.

### Likelihood Explanation
The attacker needs no special role — any unprivileged EOA can call `Hinkal.transact` with a self-generated proof to reach `EmporiumUpgradeable.runAction` (the function is only gated by `onlyAllowedRecipient`, checking `msg.sender == Hinkal`, not restricting the attacker's own `externalActionMetadata` content). The precondition is simply that at some point the Emporium contract's balance of the targeted token becomes non-zero (from any other legitimate user's Emporium operation, deposit, or slippage residue). Given Emporium's design explicitly tolerates non-zero pre-existing balances across calls, this condition is realistic and not attacker-dependent — the attacker only needs to wait/monitor for balance to appear and then front-run with `transferFrom`.

### Recommendation
Restrict which functions/selectors `op.callData` may invoke in the stateless branch (e.g., disallow `approve`/`increaseAllowance`/`permit`-style selectors on the tokens tracked in `erc20TokenAddresses`, or on any ERC20 entirely), or require any allowance granted during an op to be reset to zero within the same `runAction` call before returning. More robustly, avoid holding cross-transaction token balances in a shared, permissionlessly-callable contract at all, or enforce that `handleOut`/balance checks account for and neutralize any approvals set during the op sequence before the transaction completes.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable` (as allowed recipient), a test ERC20 token registered in `erc20TokenAddresses`.
2. Victim transaction: call `Hinkal.transact` with a valid proof/`CircomData` that performs an Emporium op with `deltaAmountChanges[i] < 0` for the token, leaving funds parked in the Emporium contract balance (simulate multi-step flow, or simply have `runAction`'s op deliberately not consume the full deposited amount, leaving residual balance in Emporium after `handleOut` due to a UTXO not created because `utxoOut.amount == 0` edge case, or a subsequent legitimate op that intentionally parks value).
3. Attacker transaction: call `Hinkal.transact` with an `EmporiumStack` whose single op is `{endpoint: tokenAddress, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.approve, (attacker, type(uint256).max))}`, with `deltaAmountChanges` all zero. Assert this transaction succeeds and passes all `Hinkal.transact` balance/slippage checks.
4. Assert `token.allowance(emporiumAddress, attacker) == type(uint256).max`.
5. In a new transaction from `attacker` (not through Hinkal at all), call `token.transferFrom(emporiumAddress, attacker, victimResidualAmount)`.
6. Assert `token.balanceOf(attacker) == victimResidualAmount` and `token.balanceOf(emporiumAddress)` decreased by that amount, while no corresponding `-deltaAmountChanges` was ever sent to the attacker by Hinkal for that withdrawal — proving the invariant "tokens leaving an action in a tx == -deltaAmountChanges Hinkal sent it that tx" is broken.
