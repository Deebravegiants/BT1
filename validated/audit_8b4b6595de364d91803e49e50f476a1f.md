### Title
Webhook shop-domain and topic headers are not covered by the HMAC signature, allowing cross-tenant spoofing of the acted-upon shop - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable payload from only the raw HTTP body, while the `shop`, `topic`, `webhook_id`, and `api_version` used to route and scope the webhook are read straight from unauthenticated HTTP headers. `Registry.process` accepts the request as valid whenever `Utils::HmacValidator.validate(request)` succeeds against that body-only signature, then dispatches to a handler using `request.shop` as the tenant identifier. This mirrors the reported bug class: an operation is performed (webhook processing scoped to a shop) using a field (`shop-domain` header) that is not covered by the cryptographic check (HMAC) that is meant to prove request authenticity.

### Finding Description
`Utils::HmacValidator.validate` calls `verifiable_query.to_signable_string` and HMACs that string with `Context.api_secret_key`: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw request body: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from HTTP headers that are never included in the signable string: [3](#0-2) 

`Registry.process` validates the HMAC and, on success, immediately trusts `request.shop` and `request.topic` to build `WebhookMetadata` and dispatch to the registered handler: [4](#0-3) 

The identity binding that should hold is: `bytes verified by HMAC == bytes that determine which shop the webhook is attributed to`. Here that equality does not hold — the HMAC only proves the body came from Shopify for *some* topic/shop, but the header fields that select *which* topic and *which* shop are unauthenticated and can be swapped independently of the signed body.

### Impact Explanation
An attacker who legitimately receives (or can trigger, e.g. by installing/uninstalling the app on their own store, or triggering GDPR webhooks like `customers/redact`, `shop/redact`, `customers/data_request`) a real webhook delivery for their own shop obtains a `(raw_body, valid HMAC)` pair signed by Shopify's shared `api_secret_key` for that app. Because the HMAC never covers the `shopify-shop-domain` / `shopify-topic` headers, the attacker can replay that exact body and signature to the app's webhook endpoint while substituting a victim shop's domain in the `shop-domain` header. `HmacValidator.validate` still returns `true` (the body bytes are unchanged), so `Registry.process` will invoke the handler with `WebhookMetadata` claiming the victim's shop. Any handler logic keyed off `data.shop` (e.g. GDPR data deletion, uninstall cleanup, subscription/plan changes) would then execute against the wrong tenant — a cross-tenant integrity violation caused entirely by this gem's webhook-verification design.

### Likelihood Explanation
Exploitation requires only: (1) ability to receive one legitimate webhook for an attacker-controlled shop (trivial — free development/trial stores can install any public or custom app), and (2) the ability to send an arbitrary HTTP request to the app's public webhook endpoint with modified headers but the original body — no access token, `client_secret`, or privileged account is required. The only constraint is that the replayed body's contents must make sense for the target handler's logic (e.g., an `app/uninstalled` or `shop/redact` payload is largely shop-domain-independent), which is realistic for several mandatory GDPR topics that carry little or no shop-specific data in the body itself.

### Recommendation
Include the security-relevant headers (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed material, or otherwise cryptographically bind them to the body (e.g., verify the header-declared shop against a shop known to be associated with this app installation before processing), instead of trusting header values that are outside the scope of `to_signable_string`.

### Proof of Concept
1. Attacker installs the target app on their own development store `attacker.myshopify.com`; Shopify sends a legitimate webhook, e.g. topic `customers/redact`, with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw_body>`, and some `raw_body`.
2. Attacker captures `(raw_body, hmac)`.
3. Attacker sends a new POST to the app's webhook endpoint with the identical `raw_body` and `hmac` headers, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses `shop` as `victim.myshopify.com` [5](#0-4) 
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only (unchanged) and returns `true` [6](#0-5) 
6. The registered handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and executes its tenant-scoped logic against the victim shop, despite the request never being authenticated for that shop.

Note: I was unable to locate a `WebhookMetadata` source file directly in the index (only its usage in `registry.rb`); its exact field list could not be independently confirmed beyond what is shown at the `handler.handle` call site.
