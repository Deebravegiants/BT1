## Title
Webhook HMAC only covers the request body, not the shop/topic headers, enabling cross-tenant webhook spoofing - (`File: lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, and `webhook_id` are read straight from HTTP headers that are never included in the HMAC-signed payload. `Registry.process` validates the HMAC and then trusts these unsigned headers to build the `WebhookMetadata` that is handed to the host application's handler, breaking the binding between "the HMAC-authenticated bytes" and "the shop/topic the application acts on."

### Finding Description
`Webhooks::Request#to_signable_string` is defined as: [1](#0-0) 

only the raw body is fed into `HmacValidator.validate`: [2](#0-1) 

but `shop`, `topic`, and `webhook_id` are pulled from `x-shopify-*` headers that are not part of the signed string: [3](#0-2) 

`Registry.process` validates only the HMAC and then unconditionally trusts these header-derived values to build `WebhookMetadata` for the handler: [4](#0-3) 

Because the HMAC only proves "this exact JSON body was signed with the app's secret at some point" and says nothing about which shop or topic that body is currently being claimed for, an attacker who obtains one valid `(raw_body, hmac)` pair (e.g., by installing the app on their own store and capturing a real webhook delivery for `orders/create`) can replay that exact body/HMAC to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` and/or `x-shopify-topic` headers with an arbitrary victim shop and topic of their choosing. `HmacValidator.validate` still succeeds because it only checks the (unchanged) body against the (unchanged) hmac; the (changed) shop/topic headers are never covered by the signature.

This breaks the identity binding: shop authenticated by HMAC (nothing, since HMAC signs only body) ≠ shop acted upon by the handler (`request.shop`, an unauthenticated header). Any host application that uses `WebhookMetadata#shop`/`#topic` to route data updates to a specific merchant's records (the documented, expected usage pattern) can be made to process attacker-supplied event data under an arbitrary victim shop's identity.

### Impact Explanation
This allows an unprivileged internet user (any merchant who can install the app once to capture a legitimate webhook) to inject fabricated webhook events attributed to any other shop using the app, without needing `api_secret_key`, an access token, or any other credential. Since host applications key their per-tenant processing off `WebhookMetadata#shop`, this is a cross-tenant data/state injection vector, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
The prerequisite is trivial: the attacker only needs to be a legitimate merchant (or trial/dev store owner) of the app once to capture a genuine `(body, hmac)` pair for any topic, then can replay it indefinitely against the app's public webhook endpoint with arbitrary `shop`/`topic` headers. No secret material or elevated privilege is required.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (all Shopify-controlled header values) as part of the HMAC-signed material verified in `Utils::HmacValidator.validate`, or otherwise cryptographically bind them to the signed body (e.g., verify them against Shopify's own webhook metadata service, or require they match values embedded/signed inside the payload) so that a captured, valid `(body, hmac)` pair cannot be replayed under a different shop or topic.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and lets Shopify deliver a genuine webhook, capturing the raw body `B` and its valid `hmac-sha256` header `H` (computed by Shopify over `B` with the app's real secret).
2. Attacker sends a POST request directly to the app's public webhook endpoint with:
   - Body: `B` (unchanged)
   - `x-shopify-hmac-sha256`: `H` (unchanged)
   - `x-shopify-shop-domain`: `victim-shop.myshopify.com` (attacker-chosen)
   - `x-shopify-topic`: any registered topic of choice
3. `ShopifyAPI::Webhooks::Request.new` accepts the request; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `B` against `H` — validation succeeds because the body/hmac pair is untouched.
4. The host app's handler receives `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: B, ...)` and processes attacker-supplied data as if it originated from `victim-shop`, even though `victim-shop` never sent any webhook and the app never installed there.
