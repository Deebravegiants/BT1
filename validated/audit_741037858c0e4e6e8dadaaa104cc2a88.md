This confirms the vulnerability: `Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` [1](#0-0) , but `Request#to_signable_string` returns only `@raw_body`, excluding the `shop`, `topic`, `webhook_id`, and `api_version` fields that are all sourced from unauthenticated HTTP headers [2](#0-1) . The `shop` value taken straight from that header is then passed to the app's webhook handler as the tenant identifier via `WebhookMetadata` [3](#0-2) [4](#0-3) , and documentation instructs apps to key business/data logic off `data.shop` directly [5](#0-4) .

### Title
Webhook `shop` (tenant identity) header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw JSON body. The `shop` (and `topic`, `webhook_id`, `api_version`) values that the handler is given to identify *which tenant* the webhook belongs to are read straight from HTTP headers that are never included in the signed material.

### Finding Description
`Request#to_signable_string` is defined as just `@raw_body` [6](#0-5) , and `HmacValidator.validate` computes/compares the HMAC only over that signable string [7](#0-6) . Meanwhile `Request#shop` is read unauthenticated from the `shopify-shop-domain`/`x-shopify-shop-domain` header [8](#0-7) .

`Registry.process` only gates on `HmacValidator.validate(request)` before dispatching to the handler with `shop: request.shop` [1](#0-0) . Since a given app uses one shared `api_secret_key` across every merchant that installs it, an attacker who has legitimately installed the app on their own shop will receive genuine Shopify webhooks with valid HMACs signed over a JSON body they fully control the identity binding of (the shop domain is *not* in that body/signature). They can replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop. The HMAC still validates (it only checked the body), but `request.shop` now reports the victim's domain to the handler.

This breaks the intended binding: `hmac_valid == true` should imply `shop == the tenant that Shopify actually sent this webhook for`, but here `hmac_valid` only proves `body` integrity, not `shop` integrity.

### Impact Explanation
Per `docs/usage/webhooks.md`, apps are told to key logic (e.g., background jobs, data mutations, session/tenant lookups) directly off `data.shop` [9](#0-8) . Any app that follows this documented pattern is exposed to cross-tenant data confusion/injection: an attacker-controlled webhook body (fully attacker-authored, since they own the source shop that generated it) gets attributed to a victim shop of the attacker's choosing. Depending on how the app processes `mandatory` topics like `customers/redact`, `shop/redact`, or ordinary business topics (`orders/create`, etc.), this can lead to unauthorized data deletion/mutation attributed to, or data leakage about, a shop the attacker does not control — a cross-tenant boundary violation.

### Likelihood Explanation
Exploitation only requires the attacker to be an ordinary merchant who has installed the app themselves (no special privilege, no access to `api_secret_key`, no access to a victim's token) — they merely capture one legitimate webhook delivery destined for their own shop and replay it with a modified `shop-domain` header value.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-covered signable string (or otherwise separately authenticate the shop domain, e.g. by cross-checking it against a known/registered shop for that webhook subscription) rather than trusting `shopify-shop-domain` verbatim, i.e. update `Request#to_signable_string` in `lib/shopify_api/webhooks/request.rb` to bind the header-derived identity fields into what `HmacValidator` verifies.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and registers for a webhook topic (e.g. `orders/create`).
2. Shopify delivers a webhook to the app with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(secret, B)` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker intercepts this request (it targets their own server/app instance) and resends it to the app's webhook endpoint, keeping `B` and the HMAC header identical but changing `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `@raw_body` = `B`, so it validates successfully [10](#0-9) .
5. The registered handler executes with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: B, ...)` [4](#0-3) , causing the app to process attacker-controlled data as if it originated from the victim shop.
