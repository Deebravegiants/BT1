### Title
Webhook HMAC only signs the raw body, not the `shop-domain`/`topic`/`webhook-id` headers, allowing cross-tenant webhook impersonation - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw HTTP body. The `shop`, `topic`, `api_version`, and `webhook_id` values are read straight from unauthenticated HTTP headers and are never included in the signed payload. This breaks the identity binding `shop authenticated == shop used to identify the tenant`, allowing a webhook payload legitimately signed for one shop to be replayed with a forged `shop-domain` header claiming to belong to a different shop, while the HMAC still validates.

### Finding Description
`Utils::HmacValidator.validate` computes the expected signature over `verifiable_query.to_signable_string` and compares it (via `OpenSSL.secure_compare`) to the `hmac` supplied by the caller: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw request body: [2](#0-1) 

But `shop`, `topic`, `api_version`, and `webhook_id` are parsed directly out of HTTP headers, which are not part of the signed material at all: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`) to build the `WebhookMetadata` passed to the host application's handler, with no additional check that the `shop` header corresponds to the body that was actually signed for that shop: [4](#0-3) 

Because every merchant/shop using a given app shares the same `Context.api_secret_key` used to compute all webhook HMACs, a `(raw_body, hmac)` pair that is valid for shop A's webhook remains cryptographically valid no matter what `shop-domain` header accompanies it — the HMAC computation never consumes the shop value. An unprivileged user who merely installs/uses the app on their own store (shop A) can legitimately receive real, correctly-signed webhooks for shop A. They can then replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting a different `x-shopify-shop-domain` header (shop B, the victim). `HmacValidator.validate` will report success (it only checks the body bytes against the secret), and `Registry.process` will hand the handler a `WebhookMetadata` claiming `shop: "shop-B.myshopify.com"` even though the payload was never generated by or for shop B.

### Impact Explanation
This is a cross-tenant identity confusion at the authentication boundary the gem is responsible for: the whole purpose of `HmacValidator`/`Registry.process` is to let host applications trust `data.shop` as the tenant the webhook body pertains to. Because the header is unauthenticated, an attacker who legitimately controls one tenant (shop A) can make the app process crafted/replayed webhook bodies under an arbitrary target tenant's (shop B) identity. Depending on how the host app uses `WebhookMetadata#shop` (e.g., looking up/mutating the corresponding shop's local records, using it to select which merchant's session/data to update), this enables cross-tenant data corruption or disclosure — satisfying the "cross-tenant access" Critical impact criterion, since the boundary crossed is the shop/tenant identity that this gem is chartered to authenticate via HMAC.

### Likelihood Explanation
The attacker only needs to be a legitimate, unprivileged user of the app on their own store (no leaked secrets, no privileged account, no TLS interception required) to obtain a validly-signed `(body, hmac)` pair, and then send an HTTP request to the app's public webhook endpoint with a modified `shop-domain` header. This requires no cryptographic break — the vulnerability is structural (headers are outside the signed scope) — making it straightforward to exploit for anyone who can trigger at least one real webhook delivery for their own shop.

### Recommendation
Include the identity-critical headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable material, or otherwise cryptographically bind them to the body before trusting them, e.g.:
```ruby
def to_signable_string
  "#{shop}\n#{topic}\n#{webhook_id}\n#{@raw_body}"
end
```
and validate/recompute the HMAC using that expanded string, or require host applications to independently corroborate the `shop-domain` header against a known/expected value (e.g., the shop tied to the session/subscription that registered the webhook) before acting on `WebhookMetadata#shop`.

### Proof of Concept
1. App is installed on attacker-controlled shop `attacker.myshopify.com`; attacker triggers an `orders/create` webhook and captures the raw POST: body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(secret, B)`.
2. Attacker sends the same body `B` and the same `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com` instead.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `H` against `HMAC-SHA256(secret, B)` — this still passes because `B` and `H` are unchanged: [5](#0-4)  and [2](#0-1) .
4. `handler.handle` is invoked with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, even though the payload body was never produced for or about `victim.myshopify.com`: [6](#0-5) .
