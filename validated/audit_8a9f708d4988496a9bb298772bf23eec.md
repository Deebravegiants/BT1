### Title
Webhook HMAC only covers the request body, not the `shop`/`topic` headers, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body alone, while `shop`, `topic`, and `webhook_id` are read directly from HTTP headers that are never included in the signed payload. `ShopifyAPI::Webhooks::Registry.process` validates only that the body's HMAC is correct and then trusts the unauthenticated header values to route and tag the payload to a specific merchant. An unprivileged internet user who has captured (or legitimately received, e.g. from their own store) one validly signed webhook body/HMAC pair can replay it with an arbitrary `shop-domain` header, causing the app to process attacker-controlled data as if it came from a victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `shop`, `topic`, and `webhook_id` are pulled straight from headers with no cryptographic binding to that body: [2](#0-1) 

`HmacValidator.validate` verifies the signature strictly against `verifiable_query.to_signable_string` (i.e., the body only): [3](#0-2) 

`Registry.process` performs this single HMAC check and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the metadata handed to the app's webhook handler: [4](#0-3) 

The identity binding that should hold is: `shop authenticated == shop the HMAC actually attests to`. Because `to_signable_string` only ever contains the body bytes, the equality that the code actually checks is `HMAC(body) == HMAC(body)`, which is independent of the `shop`/`topic`/`webhook_id` headers. This lets those headers be swapped for any value on replay of a validly-signed body — precisely the "field acted on but not covered by the HMAC" identity-binding failure described in the reference report (there, the bucket value acted on was not the one actually reset/covered by the update; here, the shop/topic acted on is not the one the signature covers).

### Impact Explanation
This qualifies as Critical/High impact: an attacker who can obtain any one valid `(raw_body, hmac)` pair signed with the target app's `client_secret` for their own shop (which any merchant/developer installing the app can trivially do, with no special privilege) can replay that pair to the app's webhook endpoint while forging the `X-Shopify-Shop-Domain` and `X-Shopify-Topic` headers to name a victim shop and any registered topic. `Registry.process` will accept it as authentic and invoke the app's handler with `WebhookMetadata` claiming it is data from the victim shop — a cross-tenant data/trust confusion that can trigger shop-scoped business logic (e.g., data updates, deletion/GDPR handlers, uninstall flows) attributed to a shop the attacker doesn't control, all without ever possessing the victim's or even the app's `api_secret_key`.

### Likelihood Explanation
Likelihood is high: no secret, token, or privileged account is required beyond being any installer/merchant of the target app (to obtain one legitimately signed webhook), and HTTP headers are trivially replayable/forgeable by the caller of the app's own public webhook endpoint. The vulnerable code path (`Registry.process` → `HmacValidator.validate`) is the exact, documented mechanism apps are told to use to authenticate every inbound webhook.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, and ideally `webhook_id`) in the signed/verified material, or otherwise cryptographically bind them to the body before trusting them — e.g., verify that the topic/shop pair matches metadata independently confirmed via the Admin API for that specific webhook id, or extend `to_signable_string` (and the validator) to canonicalize and include these headers, rejecting the request if they don't match what Shopify actually signed for.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, or otherwise triggers any registered webhook topic (e.g. `orders/create`) to be delivered to the app's `path`.
2. Attacker captures the delivered `raw_body` and its `X-Shopify-Hmac-Sha256` header (a valid HMAC over that exact body computed with the app's `client_secret`, which Shopify computed — not the attacker).
3. Attacker replays the same body + hmac to the app's webhook endpoint, but sets:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   - `X-Shopify-Topic: customers/data_request` (or any topic registered by the app)
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC only over `raw_body` — it matches, since the body is unchanged. See [5](#0-4) .
5. The registered handler is invoked with `WebhookMetadata.new(topic: "customers/data_request", shop: "victim-shop.myshopify.com", body: <attacker's body>, ...)`, so the app processes attacker data as an authenticated action for `victim-shop.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
