### Title
Webhook shop/topic identity spoofing due to HMAC covering only the raw body — ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable string from the raw HTTP body only, while `shop`, `topic`, and `webhook_id` are read directly from unauthenticated HTTP headers and are never included in the HMAC-verified content. `ShopifyAPI::Webhooks::Registry.process` accepts the request as authentic once `Utils::HmacValidator.validate(request)` succeeds, then dispatches the handler using these unverified header values as tenant/event identity.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `shop`, `topic`, and `webhook_id` are pulled straight from headers with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` validates only the HMAC (i.e., only the body) and then trusts `request.shop`, `request.topic`, and `request.webhook_id` to construct the dispatched `WebhookMetadata`: [3](#0-2) 

Because the HMAC secret (`Context.api_secret_key`) is the app's single `client_secret`, shared across every shop that installs the app, any body signed for one shop is validly signed for all shops. Any unprivileged internet user can therefore:
1. Install the app on their own shop (or otherwise legitimately receive one webhook delivery), capturing a genuine `(raw_body, hmac)` pair.
2. Replay that exact body/HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain`, `shopify-topic`, and/or `shopify-webhook-id` headers with values belonging to another merchant.
3. `Utils::HmacValidator.validate` still returns `true` because it only re-computes the HMAC over `@raw_body`, and `Registry.process` dispatches the handler with the attacker-controlled `shop`/`topic`/`webhook_id` fields as if they were authentic.

This breaks the identity binding the report's rule calls out directly: "a field acted on but not covered by the HMAC" — here, `shop` (the tenant identity) and `topic`/`webhook_id` are acted upon by the handler dispatch logic but are not part of the HMAC-protected content.

### Impact Explanation
A host application that keys any per-shop logic (e.g., looking up the corresponding `Session`/access token, writing tenant-scoped data, or triggering tenant-specific side effects) off `WebhookMetadata#shop` as delivered by this gem can be tricked into attributing a webhook event to the wrong merchant, i.e., cross-tenant confusion, purely because this gem's `HmacValidator`/`Registry.process` present the (unverified) header-derived `shop` as if it were authenticated alongside the body. This matches the Critical "cross-tenant access" impact category, since the vulnerable trust boundary (HMAC "validates this request/shop") lives entirely inside this gem's `Webhooks::Request` and `Webhooks::Registry`.

### Likelihood Explanation
Exploitation only requires the ability to install the target app on an attacker-controlled shop (or otherwise obtain one legitimate webhook delivery) and the ability to send arbitrary HTTP headers to the app's webhook endpoint — no access token, `client_secret`, or privileged account is needed. Likelihood is moderate-to-high for any app author who reasonably assumes that a passing `Utils::HmacValidator.validate` implies the accompanying `shop`/`topic` metadata is equally trustworthy, since the gem exposes no separate authenticity guarantee for those fields.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the value verified by `Utils::HmacValidator` (e.g., include them in `to_signable_string`, or require callers to separately authenticate the shop domain against a known/installed-shop list before trusting `WebhookMetadata#shop`). At minimum, document prominently that `Registry.process`'s HMAC check does not authenticate `shop`/`topic`/`webhook_id`, and provide a supported mechanism to bind them safely.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook: body `B`, header `shopify-hmac-sha256: H` (H = HMAC(app_secret, B)), `shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker POSTs to the app's webhook endpoint with the same body `B` and same `H`, but headers rewritten to `shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` builds `to_signable_string` from `B` only; `Utils::HmacValidator.validate` recomputes HMAC over `B` and matches `H` — validation passes. [4](#0-3) 
4. `Registry.process` calls the registered handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)`, where `request.shop` is `"victim-shop.myshopify.com"` — attacker-controlled and never covered by the HMAC. [5](#0-4)
