### Title
Bitcoin Bech32 case-insensitivity bypasses `compareAddresses`, allowing withdrawal to the token's own address - (File: `packages/intents-sdk/src/lib/compareAddresses.ts`)

### Summary
`compareAddresses` for Bitcoin (and BCH/Dogecoin/Litecoin/etc.) performs a raw `a === b` string comparison instead of canonicalising the address, while `validateAddress`'s Bech32 validator accepts both all-lowercase and all-uppercase encodings of the same witness program as per BIP-173. An attacker can submit the token's own Bech32 address in uppercase as `destinationAddress`; it passes `validateAddress`, but `compareAddresses` treats it as different from the lowercase `destTokenAddress`, so `DestinationAddressMatchesTokenAddressError` never fires and the withdrawal is routed to the token contract's own address.

### Finding Description
The claimed equality is: for every destination `d` accepted by `validateAddress(d, Bitcoin)` and token address `t`, if `d` and `t` denote the same on-chain account, then `compareAddresses(t, d, 'bip122:000000000019d6689c085ae165831e93')` must be `true`.

In `packages/intents-sdk/src/lib/compareAddresses.ts` line 60, Bitcoin falls into the default case that just does `a === b`: [1](#0-0) 

Meanwhile `validateBtcBech32Address` in `packages/intents-sdk/src/lib/validateAddress.ts` decodes the address with `@scure/base`'s `bech32`/`bech32m` codecs, which accept an address encoded entirely in uppercase (BIP-173 permits all-lowercase or all-uppercase, and both decode to the exact same witness program): [2](#0-1) 

In `OmniBridge.validateWithdrawal` (`packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts`), `validateAddress` gate passes first (line 358-365), then `compareAddresses(destTokenAddress, args.destinationAddress, assetInfo.blockchain)` is used to block self-sends (line 384-396): [3](#0-2) 

Exploit flow: the attacker calls `IntentsSDK.processWithdrawal`/`createWithdrawalIntents` for a Bitcoin-routed nep141 token, setting `destinationAddress` to the token's own Bech32 address but re-cased to all-uppercase (e.g. `BC1Q...` instead of `bc1q...`). `validateAddress` accepts it because uppercase Bech32 is valid per spec. `compareAddresses` performs a byte-for-byte string comparison (`a === b`) rather than decoding both sides to their witness program, so `"bc1q..." !== "BC1Q..."` even though they resolve to the identical scriptPubKey on the Bitcoin network. `DestinationAddressMatchesTokenAddressError` is therefore never thrown, `validateWithdrawal` succeeds, and `createWithdrawalIntents` builds a withdrawal sending funds to the token contract's own address — where they are unrecoverable.

This is not a thrown-exception path as speculated in the question's exploit idea, but it satisfies the exact same broken invariant: a Bitcoin destination address that `validateAddress` accepts and that is semantically identical to the token address, for which `compareAddresses` returns `false`.

### Impact Explanation
Funds withdrawn are delivered on-chain to the Bitcoin token bridge contract's own address rather than the user's intended destination, with no on-chain recovery path — this is a direct, permanent loss of user funds and matches the "Critical: funds delivered to a wrong address/chain/contract with no recovery" category. Each affected withdrawal call permanently burns the withdrawn amount; it is repeatable across every Bitcoin-routed OmniBridge withdrawal call an attacker (or an integrator relaying attacker-controlled input) makes.

### Likelihood Explanation
Preconditions: a Bitcoin-routed asset via OmniBridge whose on-chain token/bridge address uses a Bech32 (`bc1...`) form (SegWit v0/v1). The attacker only needs to know that Bech32 addresses are case-insensitive and re-case the known token address in uppercase — no privileged access, no reliance on malicious infrastructure. Cost is a single SDK call; the bug is fully reachable through the documented public API (`processWithdrawal`/`createWithdrawalIntents`), with no additional guard preventing it, since `validateAddress` explicitly accepts the case-flipped form and the self-address guard uses naive string equality.

### Recommendation
In `compareAddresses.ts`, canonicalise UTXO-chain addresses (Bitcoin, Bitcoin Cash, Litecoin, Dogecoin, Dash, Zcash) before comparison instead of doing raw string equality: for Bech32/Bech32m addresses, decode via `bech32`/`bech32m` and compare `(prefix, witnessVersion, program)`; for Base58Check addresses, decode and compare the raw payload bytes (as is already done for Tron/TON). Apply the same canonicalisation used in `validateAddress` so accepted-but-differently-cased/encoded forms of the same address are correctly recognized as equal.

function validateBtcBech32Address(address: string): boolean {
	let decoded: { prefix: string; words: number[] };
	let isBech32m = false;

	try {
		decoded = bech32.decode(address as `${string}1${string}`);
	} catch {
		try {
			decoded = bech32m.decode(address as `${string}1${string}`);
			isBech32m = true;
		} catch {
			return false;
		}
	}

	if (decoded.prefix.toLowerCase() !== "bc") return false;

	const { words } = decoded;
	if (!words || words.length < 1) return false;

	const witnessVersion = words[0];
	if (witnessVersion === undefined || witnessVersion < 0 || witnessVersion > 16)
		return false;

	const program = bech32.fromWords(words.slice(1));
	const progLen = program.length;

	if (progLen < 2 || progLen > 40) return false;

	// v0: Bech32 only — 20 bytes (P2WPKH) or 32 bytes (P2WSH)
	if (witnessVersion === 0) {
		if (isBech32m) return false;
		return progLen === 20 || progLen === 32;
	}

	// v1: Bech32m only — 32 bytes (P2TR / Taproot)
	if (witnessVersion === 1) {
		if (!isBech32m) return false;
		return progLen === 32;
	}

	return false;
}
