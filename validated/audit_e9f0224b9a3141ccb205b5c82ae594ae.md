### Title
Webhook `shop` identity is read from an unauthenticated header not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identifier (`shop`) from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, while the HMAC signature that `Registry.process` validates covers only the raw request body. An attacker who controls the webhook delivery request (e.g. replays or forges a POST to the app's webhook endpoint with a body/HMAC pair captured from a legitimate webhook, or races the timing of any endpoint that accepts attacker-controllable headers) can supply an arbitrary `shop-domain` header while keeping the body+HMAC valid, causing the gem to attribute the webhook payload to a shop it did not originate from.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) 

Only `@raw_body` is fed into the HMAC computation (`to_signable_string`), and `HmacValidator.validate` recomputes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac-sha256` header: [2](#0-1) 

The `shop` field returned by `Request#shop` — read straight from the `shop-domain` header — is never included in the signed bytes: [3](#0-2) 

`Registry.process` validates only the HMAC over the body, then uses the unauthenticated `request.shop` value directly as the tenant identity passed to the app's webhook handler: [4](#0-3) 

The identity binding that should hold is:
`shop (used by handler as tenant key) == shop (covered by the HMAC that Shopify computed)`

but the actual binding enforced by the gem is:
`shop (used by handler as tenant key) == shop (attacker-controlled HTTP header, unauthenticated)`

Because the HMAC only proves the integrity of `@raw_body`, and Shopify's real webhook payloads for many topics do not embed the shop domain inside the JSON body (topic-dependent), an attacker who can get any valid `(body, hmac)` pair signed by the shared secret — for example by replaying an app's own genuine webhook that they received for their own shop, or via a body/HMAC obtained through any means — can then swap the `shop-domain` header to a victim shop id when delivering to the app's webhook endpoint. `Registry.process` will pass this forged shop identity to the app's handler as `WebhookMetadata#shop`, breaking the tenant binding this gem is supposed to guarantee (`Utils::HmacValidator.validate(request)` is the only check performed before dispatch, and it never checks `request.shop`).

### Impact Explanation
This crosses a tenant boundary: an app built on this gem trusts `WebhookMetadata#shop` from `Registry.process` as the authenticated origin shop for the webhook event. If that value can be forged independent of the HMAC, an attacker can cause the app to process/act on webhook data under an arbitrary victim shop's identity (cross-tenant data confusion), satisfying the "cross-tenant access" criterion for High/Critical impact.

### Likelihood Explanation
Exploitability depends on the attacker obtaining at least one valid `(raw_body, hmac)` pair signed with the app's `api_secret_key` for the same body content it wants delivered (e.g., from a legitimate webhook to their own controlled shop, or any topic whose HMAC-signed body is public/predictable/re-usable) and then delivering it to the app's public webhook endpoint with a forged `shop-domain` header. This gem provides no defense-in-depth binding of the shop header into the signature, so the security guarantee rests entirely on the host app not trusting `request.shop`/`WebhookMetadata#shop` — which is the exact protection the gem's own `Registry.process` claims to provide via `HmacValidator.validate`.

### Recommendation
Include the `shop-domain` header (and ideally `topic`, `api-version`, `webhook-id`) as part of the signable string used for HMAC verification, or independently verify that the `shop-domain` header matches a shop value embedded in the verified payload before dispatching to handlers in `Registry.process`.

### Proof of Concept
1. App receives (or attacker obtains) a genuine webhook `POST` with headers `X-Shopify-Hmac-Sha256: <hmac>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`, and body `B`.
2. Attacker resends the identical body `B` and `hmac` header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `OpenSSL::HMAC.hexdigest(..., @raw_body)` against the `hmac` header — this still passes because `@raw_body` is unchanged.
4. `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` is invoked with `shop = "victim-shop.myshopify.com"`, even though the payload was never actually signed for that shop. [4](#0-3)

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
