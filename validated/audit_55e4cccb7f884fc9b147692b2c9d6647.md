### Title
`EvmHost.dispatch`/`fundRequest` ignore the Uniswap router's return value, permanently trapping any ETH overpayment - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch` and `EvmHost.fundRequest` swap native ETH for the fee token via `IUniswapV2Router02.swapETHForExactTokens` but discard the returned `amounts` array and never reconcile `msg.value` against what was actually spent, mirroring the "ignored external call return value" pattern from the reported analog.

### Finding Description
Both `dispatch` [1](#0-0)  and `fundRequest` [2](#0-1)  call:
```solidity
IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
```
`swapETHForExactTokens` is documented to return `uint256[] memory amounts` (ETH actually spent vs. tokens received), and real UniswapV2Router implementations refund any unspent ETH back to `msg.sender` — which in this call is `EvmHost` itself, not the original transaction sender (`_msgSender()`). `EvmHost` neither captures the return value nor forwards any refunded ETH back to the caller who supplied `msg.value`. Any excess ETH beyond `post.fee`'s cost is silently absorbed into the host contract's balance with no accounting or user-facing recovery path in either function.

This is the same root-cause pattern as the external report: an external call's return data is dropped instead of being used to reconcile state or refund the caller, and here the contract also fails to test that the amount spent matches the amount supplied.

### Impact Explanation
Users calling `dispatch{value: ...}` or `fundRequest{value: ...}` with any ETH amount exceeding the router's actual spend (which is the normal case, since callers must estimate slippage and typically over-provide) permanently lose the difference — a real fund-freezing bug reachable by any unprivileged caller in a single transaction. Unlike the wrapper wrappers in the repo (`UniV3UniswapV2Wrapper`, `UniV4UniswapV2Wrapper`, `GnosisUniswapV2Wrapper`), which explicitly capture `spent`/`refundETH` and forward the difference back to `msg.sender` [3](#0-2) , `EvmHost` itself performs no such reconciliation.

### Likelihood Explanation
High likelihood of occurrence in normal usage: any caller who cannot predict the exact ETH cost of the swap (due to price movement) and supplies a safety margin in `msg.value` will lose the excess on every call to `dispatch` or `fundRequest` with `msg.value > 0`.

### Recommendation
Capture the `amounts` return value from `swapETHForExactTokens`, compute `refund = msg.value - amounts[0]`, and forward it back to `_msgSender()` (with a low-level call and success check), consistent with how the other Uniswap wrapper contracts in this codebase already handle refunds.

### Proof of Concept
1. Caller invokes `EvmHost.dispatch{value: 5 ether}(post)` where `post.fee` only requires a fraction of an ETH to acquire via the router.
2. The real `UniswapV2Router02.swapETHForExactTokens` spends only what's needed and refunds the rest to `msg.sender`, i.e., to `EvmHost`.
3. `EvmHost.dispatch` ignores the returned `amounts` and never forwards the refunded ETH to the caller; the excess ETH is now stuck inside `EvmHost` with no corresponding accounting or withdrawal path exposed to that caller. `evm/tests/foundry/IntentGatewayV2Test.sol`'s `testPlaceOrder_FeeSwap_RefundsExcessNativeToken` [4](#0-3)  demonstrates the expected refund behavior exists at the `IntentGatewayV2` layer for its own swap call, underscoring that `EvmHost.dispatch`/`fundRequest` lack the equivalent, unlike its own analogous code path.
