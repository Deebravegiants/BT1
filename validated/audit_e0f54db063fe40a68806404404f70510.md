### Title
Fee-on-transfer tokens cause escrow over-crediting in `IntentGatewayV2.placeOrder` — Tron deployment lacks the balance-diff fix present in the main EVM contract - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` credits the internal escrow ledger `_orders[commitment][token]` using the user-supplied/fee-reduced input amount instead of the amount actually received by the contract. If any input token used for an order is (or becomes) fee-on-transfer, the contract will hold strictly less of that token than the escrow accounting believes, exactly mirroring the reported `CrabNetting.depositUSDC()` bug class.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, the non-predispatch escrow path pulls tokens with `safeTransferFrom` and unconditionally credits the pre-computed `reducedInputs[i].amount` (derived from `order.inputs[i].amount`, the amount the user *specified*, minus protocol fee) — it never checks the gateway's actual token balance before/after the transfer: [1](#0-0) 

Compare this to the fixed main EVM implementation (`evm/src/apps/IntentGatewayV2.sol`), which explicitly snapshots the balance before/after `safeTransferFrom` and mutates `order.inputs[i].amount` to the actual received amount before it is used to compute the commitment/escrow: [2](#0-1) 

The Tron contract's commitment/`reducedInputs` are also computed *before* any transfer occurs, straight from the caller-supplied `order.inputs[i].amount`: [3](#0-2) 

So for any fee-on-transfer ERC20 input (present now or enabled later, e.g. a deflationary/tax token, or USDC/USDT if such a mechanism is ever activated), the gateway will:
1. Receive `amount - fee` tokens via `safeTransferFrom`.
2. Record `_orders[commitment][token] += reducedInputs[i].amount`, where `reducedInputs[i].amount` is derived from the full pre-fee `amount`, not the actual amount received.

This inflates the ledger relative to the contract's real token balance for that specific token, contract-wide (since `_orders` is a shared mapping across all orders/commitments for the pooled token balance). This is analogous to the `CrabNetting.depositUSDC()` bug: `usdBalance[msg.sender]` (there) / `_orders[commitment][token]` (here) is credited with the pre-fee amount rather than what was actually transferred in.

The predispatch branch is comparatively safer because it explicitly measures `IERC20(token).balanceOf(dispatcher)` and reverts via `InvalidInput` if `balance < requiredAmount` — but it still stores `reducedInputs[i].amount` (computed from `order.inputs[i].amount`, not the measured `balance`) into escrow, so any successful predispatch sweep will still register the *requested* amount, not the swept amount, whenever a fee-on-transfer token is later moved out of the dispatcher/gateway itself (double-hop fee scenario is not accounted for even when the initial sweep amount checks pass).

### Impact Explanation
Because `_orders[commitment][token]` overstates the gateway's real token holdings for that token, subsequent legitimate operations that pay out from escrow — solver `fillOrder` same-chain settlement, and cross-chain `RedeemEscrow`/`RefundEscrow` withdrawals driven by `onAccept` — will attempt to transfer out more of the token than the contract actually holds for that specific escrow slot. Since all escrowed balances for a token are pooled in the same ERC20 balance of the contract, this either:
- Causes reverts (denial of service) for withdrawals once the deficit accumulates and the contract's true balance is insufficient to cover legitimate claims, freezing funds for later orders, or
- Allows one order's inflated escrow entry to be satisfied by drawing down token balance that rightfully belongs to other users' orders, effectively socializing the fee-on-transfer shortfall across all users of that token and potentially leaving the last claimant's transfer to permanently revert (frozen funds) — a fund-safety/accounting break in the pooled escrow.

This qualifies as a Medium-severity accounting/fund-freezing issue reachable by any unprivileged user calling `placeOrder` with a fee-on-transfer token as input.

### Likelihood Explanation
Likelihood depends on whether a fee-on-transfer token is ever whitelisted/used as an order input on the Tron deployment (same precondition as the original USDC report — the fee mechanism must be enabled/available on the token). Given IntentGatewayV2 accepts arbitrary ERC20 tokens as `order.inputs[i].token` with no token-safety allowlist enforced in this code path, and the main EVM contract's authors clearly recognized and already patched this exact class of bug (as shown by the balance-diff fix and dedicated `FeeOnTransferToken` test suite), it is very likely that the Tron fork was simply not updated with the same fix, making this a real regression/inconsistency between deployments rather than a purely theoretical issue.

### Recommendation
Apply the same fix used in `evm/src/apps/IntentGatewayV2.sol` to `evm/tron/contracts/apps/IntentGatewayV2.sol`: measure the gateway's token balance before and after each `safeTransferFrom` in the non-predispatch branch, and use that measured delta (not the caller-specified `order.inputs[i].amount`) to (a) mutate `order.inputs[i].amount` prior to protocol-fee reduction and commitment hashing, and (b) credit `_orders[commitment][token]`. The predispatch branch should likewise base `reducedInputs[i].amount`/escrow crediting on the swept `balance` actually received by the gateway, not on the originally requested `order.inputs[i].amount`.

### Proof of Concept
1. Governance/admin (or a future protocol upgrade) enables a fee-on-transfer mechanism on an ERC20 token accepted as an intent input on the Tron `IntentGatewayV2` (e.g., USDC's dormant fee switch, or any newly listed token with an active transfer tax).
2. A user calls `placeOrder` with `order.inputs[0] = {token: FEE_TOKEN, amount: 1000}` and no `predispatch`.
3. `IERC20(token).safeTransferFrom(msg.sender, address(this), 1000)` executes; due to the transfer fee, the gateway's actual token balance increases by only `990` (evm/tron/contracts/apps/IntentGatewayV2.sol:459).
4. The contract nonetheless executes `_orders[commitment][token] += reducedInputs[i].amount`, crediting the full `1000` (minus protocol fee if any) — i.e., `990` less than expected is missing but the ledger still shows the full amount (evm/tron/contracts/apps/IntentGatewayV2.sol:463).
5. When a solver fills the order or a `RedeemEscrow`/`RefundEscrow` cross-chain message attempts to pay out the recorded escrow amount, the payout transfer can revert with insufficient balance, or succeed by draining tokens belonging to other users' escrowed orders of the same token, leaving a later claimant unable to be paid.
