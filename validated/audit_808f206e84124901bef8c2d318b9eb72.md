### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw request body via HMAC-SHA256, but the `shop` identifier that the library hands to application webhook handlers is read from the unauthenticated `X-Shopify-Shop-Domain` header. Because `api_secret_key` is a single, app-wide secret shared across every shop that installs the app, any merchant who installs the app can capture a genuinely-signed webhook delivery to their own shop and later replay that same body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header. The library will treat the forged shop identity as authentic.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the signature only over `to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns solely the raw HTTP body: [2](#0-1) 

However, the `shop` accessor used downstream is derived purely from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is never included in the signed payload: [3](#0-2) 

`Webhooks::Registry.process` validates the HMAC once (against the body only) and then unconditionally trusts `request.shop` when constructing the data passed to the application's webhook handler: [4](#0-3) 

This breaks the intended binding: `HMAC-verified bytes == body` but `shop used by the handler == unauthenticated header`. Because the same `api_secret_key` is used to sign webhooks for every shop that installs a given app (it is a per-app secret, not a per-shop secret), an attacker only needs to install the app on their own store — a wholly unprivileged action — to receive a validly-signed webhook delivery. They can then replay that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while setting the `shop-domain` header to an arbitrary victim shop domain. `HmacValidator.validate` will still succeed (it never looks at the header), and `Registry.process` will dispatch the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain.

This is the same bug class as the ERC820/1820 issue cited in the report: a verification routine that checks less data than what is subsequently trusted and acted upon (the EIP fix widened the `insize` actually inspected by `staticcall`; here the fix would be to bind `shop` into the signed payload actually verified).

### Impact Explanation
Any application built on this gem that keys per-shop state, GDPR/redact processing, order/inventory updates, or authorization decisions off `WebhookMetadata#shop` (as documented and demonstrated in `test/webhooks/registry_test.rb`) can be made to process attacker-supplied webhook bodies under an arbitrary victim shop's identity. This is a cross-tenant integrity/data-injection vector: attacker-controlled data (e.g., a forged `orders/create`, `app/uninstalled`, or `shop/redact` payload) is attributed to a shop the attacker does not control, which can corrupt victim-tenant state, trigger unauthorized actions (e.g., data deletion via `shop/redact`), or pollute per-tenant records that other code paths trust as coming from Shopify for that specific shop.

### Likelihood Explanation
The only prerequisite is being able to install the app once (as any unprivileged merchant can do) to obtain one genuinely HMAC-signed webhook body/signature pair, since the signing key (`api_secret_key`) is shared across all shops for the app rather than per-tenant. No access token, `client_secret`, or privileged credential belonging to the victim is required, and no TLS interception or host misconfiguration is needed — only that the host application dispatches on `request.shop` / `WebhookMetadata#shop`, which is the gem's documented usage pattern.

### Recommendation
Bind the shop identity into the value that is actually HMAC-verified, e.g. include the normalized `shop-domain` header (and ideally `topic`/`webhook-id`) in `to_signable_string`, or independently verify that the `shop` header matches an expected/allow-listed shop domain associated with the session before dispatching to handlers. At minimum, document/require callers to cross-check `request.shop` against a known-installed-shop list rather than trusting it as authenticated solely because `Utils::HmacValidator.validate` returned `true`.

### Proof of Concept
1. Install the target app on an attacker-owned development store; Shopify delivers a legitimate webhook, e.g. `POST /webhooks` with body `B`, header `X-Shopify-Hmac-Sha256: H` (computed over `B` with the app's shared `api_secret_key`), and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker replays the identical request to the same endpoint, keeping body `B` and header `X-Shopify-Hmac-Sha256: H` unchanged, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this successfully; `Utils::HmacValidator.validate(request)` returns `true` because it only recomputes the HMAC over `@raw_body`, matching `H`.
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)`, as shown in the handler dispatch at: [5](#0-4) 
   causing the host application to process attacker-controlled data under the victim shop's identity.
