### Title
Webhook `shop-domain`, `topic`, and `webhook-id` headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity by HMAC-signing only the raw request body, while the `shop`, `topic`, and `webhook_id` values used to route and attribute the webhook are read from unauthenticated HTTP headers. This breaks the intended binding of `hmac ⇒ (body, shop, topic)` down to `hmac ⇒ body` only, letting anyone in possession of one validly-signed webhook body (e.g., a webhook for their own, attacker-controlled shop) replay it with a forged `shop-domain`/`topic` header to make the app process the event as if it belonged to a different, victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . Meanwhile `shop`, `topic`, and `webhook_id` are all pulled from HTTP headers that are never part of the signed material: [2](#0-1) .

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (the body only) and compares it to the `hmac-sha256` header: [3](#0-2) , [4](#0-3) . Once that check passes, the (unauthenticated) `request.shop` and `request.topic` values are forwarded directly into `WebhookMetadata` and dispatched to the app's registered handler: [3](#0-2) .

Because Shopify signs webhooks with a single `client_secret` shared across all shops that installed the app, and the signature never covers `shop-domain`/`topic`/`webhook-id`, any party that can obtain one authentic, validly-signed webhook body (trivially, by triggering an event on a shop they themselves install the app on) can resend that exact body to the app's webhook endpoint while substituting an arbitrary `shop-domain` (and/or `topic`) header. `HmacValidator.validate` will still return `true` because it only checks the body against the shared secret, and the app's handler will process the payload attributed to the victim shop.

The binding that should hold is:
`hmac_valid ⇒ (body, shop, topic) authentically originated together`
What the code actually guarantees is only:
`hmac_valid ⇒ body authentically originated (signed with the app secret)`
`shop` and `topic` are asserted, not verified.

### Impact Explanation
This is a cross-tenant integrity break: an attacker-controlled request can cause the app's webhook handler to execute business logic (e.g., create/update local records, trigger redactions, sync inventory) under the identity of a victim shop, using attacker-chosen body content signed for a different, attacker-owned installation. Depending on what the host application's `WebhookHandler` does with `WebhookMetadata#shop` (typically used as the tenant key for database writes), this can lead to cross-tenant data corruption or injection of forged events into a victim shop's records — satisfying the "cross-tenant access" Critical impact category, since the shop attribution used by downstream tenant-scoped logic is not authenticated.

### Likelihood Explanation
Likelihood is moderate-to-high for any app that has more than one installed shop: obtaining one authentic signed webhook only requires installing the app on an attacker-controlled development/test store (a normal, unprivileged action), then replaying the captured body with a modified `Shopify-Shop-Domain`/`X-Shopify-Shop-Domain` header value to the same public webhook endpoint. No secrets, tokens, or privileged access to the victim shop are required.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable string (or otherwise cryptographically bind them to the HMAC-covered payload) before accepting them for routing/attribution, or independently verify that the `shop` header corresponds to a shop with an active installation before dispatching to handlers. At minimum, document that `WebhookMetadata#shop`/`#topic` are not covered by the HMAC and must not be trusted as the sole tenant key without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a shop they control) and triggers a webhook event (e.g., `orders/create`) with attacker-chosen order data.
2. Attacker's endpoint (or a proxy they control) captures the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sent — this signature is valid because Shopify signed it with the app's shared `client_secret`, which is fixed per-app.
3. Attacker resends the exact same raw body and `hmac-sha256` header value to the app's public webhook endpoint, but replaces `X-Shopify-Shop-Domain: attacker-shop.myshopify.com` with `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` in `lib/shopify_api/utils/hmac_validator.rb` returns `true` because it only re-hashes `@raw_body`.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` dispatches `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` with `shop == "victim-shop.myshopify.com"`, causing the app's handler to process attacker-controlled order data as if it originated from the victim shop.
