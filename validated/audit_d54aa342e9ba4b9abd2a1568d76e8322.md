## Title
Webhook shop/topic/webhook_id headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw HTTP body for HMAC verification, while the `shop`, `topic`, `webhook_id`, and `api_version` values that `Registry.process` uses to route and attribute the webhook are taken directly from unauthenticated HTTP headers. Anyone who can obtain one genuine `(body, hmac)` pair — e.g. by installing the app on their own store and receiving a real webhook — can replay that exact body/HMAC pair to the app's public webhook endpoint while freely rewriting the `shop-domain`, `topic`, and `webhook-id` headers, and the signature check will still pass.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from request headers with no cryptographic binding to the body: [2](#0-1) 

`HmacValidator.validate` computes the signature purely over `verifiable_query.to_signable_string` (i.e., the raw body) and compares it against the `hmac` header: [3](#0-2) 

`Registry.process` trusts this HMAC check as proof of authenticity for the whole request, then dispatches the handler using the unauthenticated header-derived `topic` and `shop`: [4](#0-3) 

The identity binding that should hold is:
`hmac_valid(body) == true` should imply `shop_header == authentic_shop AND topic_header == authentic_topic`.

In reality, `hmac_valid(body)` is a property of the body alone, so the equality does not hold: any attacker who receives one legitimate webhook delivery (by simply installing the public app on a store they control) obtains a `(body, hmac)` pair which remains valid under `HmacValidator.validate` no matter what `shop-domain`, `topic`, or `webhook-id` headers are sent alongside it. This lets the attacker cause the app to process a webhook that is falsely attributed to a victim shop and/or a different topic than the one that was actually signed.

### Impact Explanation
This crosses a tenant boundary: the app's own webhook processing pipeline can be made to believe a webhook event happened for shop X's tenant when it actually did not, using only credentials/relationships the attacker legitimately possesses (their own store's install). Depending on the host application's handler logic, this can be used to spoof events such as `app/uninstalled`, `shop/redact`, or `customers/redact` for a victim shop's `shop` value, causing the app to delete or invalidate session/access-token data for a shop the attacker does not control, or otherwise take tenant-scoped action attributed to the wrong shop — a cross-tenant access impact.

### Likelihood Explanation
Any user can install a publicly listed app (or a dev store) to receive at least one legitimate webhook delivery with a valid `(body, hmac)` pair, then POST that same body/HMAC to the app's public webhook endpoint with arbitrary `shop-domain`/`topic`/`webhook-id` headers. No secret material or privileged access is required beyond the ability to install the app once, which is achievable by any unprivileged internet user for public apps.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signed content that `to_signable_string` returns (or otherwise cryptographically bind them, e.g. by having `Registry.process` re-derive/validate these fields against the signed payload rather than trusting raw headers), so that a valid HMAC can only be produced for a specific combination of body and header metadata.

### Proof of Concept
1. Attacker installs the target app on their own (attacker-controlled) shop `attacker.myshopify.com` and receives a legitimate webhook, capturing:
   - `x-shopify-hmac-sha256: <valid_hmac>`
   - `x-shopify-shop-domain: attacker.myshopify.com`
   - `x-shopify-topic: app/uninstalled`
   - raw body `B`
2. Attacker resends the exact same body `B` and `x-shopify-hmac-sha256` header to the app's public webhook endpoint, but changes:
   - `x-shopify-shop-domain: victim.myshopify.com`
3. `Utils::HmacValidator.validate` in `Registry.process` recomputes HMAC over body `B` only, matches the supplied HMAC, and passes validation as shown at: [5](#0-4) 
4. The registered `app/uninstalled` handler is invoked with `WebhookMetadata.shop == "victim.myshopify.com"`, causing the app to act (e.g., delete stored session/access token) on behalf of a shop the attacker never installed on or authenticated as.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
