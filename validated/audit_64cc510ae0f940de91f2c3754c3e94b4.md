### Title
Webhook tenant identity (`shop`) is trusted from an unsigned header, not bound to the HMAC that authenticates the payload - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then hands off a `shop` value taken from the `X-Shopify-Shop-Domain` header — a field that is never included in the signed material — to the app's handler as the tenant identifier.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Utils::HmacValidator.validate` computes/compares the HMAC exclusively against that signable string [2](#0-1) . The `shop` accessor, however, is read directly and unauthenticated from the `shop-domain`/`x-shopify-shop-domain` HTTP header [3](#0-2) .

`Registry.process` validates the HMAC and then immediately constructs `WebhookMetadata` using `request.shop` from that unauthenticated header, passing it to the app-registered handler as the identified tenant [4](#0-3) .

The equality that should hold is: `shop bound by HMAC == shop delivered to handler`. In this implementation that equality is never enforced — the HMAC only binds the body bytes, while the shop identity used for downstream tenant routing/authorization comes from a header outside that signature. Since the app's `api_secret_key` (the webhook signing secret) is a single, shared secret used to sign webhooks for *every* shop that installs the app, an attacker who controls their own shop installation receives genuine, correctly-signed webhook deliveries for their own tenant. Because the `shop-domain` header is not part of the signed payload, that same valid `(raw_body, hmac)` pair remains valid if replayed with the `shop-domain` header rewritten to a victim shop's domain — `Utils::HmacValidator.validate` will still return `true` [5](#0-4) , and the handler will process the (attacker-controlled) body as if it belonged to the victim shop.

### Impact Explanation
This breaks the tenant/shop identity binding that host applications rely on to scope data per merchant. An app that uses `WebhookMetadata#shop` to decide which merchant's records to read, mutate, or return (a standard pattern) can be made to attribute attacker-supplied webhook data to an arbitrary victim shop, i.e., cross-tenant data injection/corruption through a properly-authenticated (HMAC-valid) request. This matches the Critical "cross-tenant access" impact category — the confidentiality/integrity boundary between merchants is defeated using only a legitimate app installation on the attacker's own shop, no leaked credentials or privileged access required.

### Likelihood Explanation
Reaching this requires only: (1) installing the target app on a shop the attacker controls (an ordinary, unprivileged action), (2) triggering/receiving a legitimate webhook delivery for that shop to obtain a valid `(raw_body, hmac)` pair, and (3) replaying that request to the app's webhook endpoint with the `shop-domain` header swapped to a different shop. No knowledge of `api_secret_key`, access tokens, or any other credential is required. The library provides no mechanism binding `shop` to the signature, so any host app that trusts `WebhookMetadata#shop` as authenticated is affected. `Registry.process` itself performs no shop cross-check [6](#0-5) .

### Recommendation
Include the shop identifier (and other tenant-scoping headers such as topic/api-version if used for authorization) inside the HMAC-covered signable string, or otherwise cryptographically bind the `shop-domain` header to the payload before trusting it. At minimum, `Registry.process`/`Webhooks::Request` should document and/or enforce that `shop` must be cross-validated by the host application against session/installation records rather than treated as authenticated solely because the body HMAC passed.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Shopify delivers a legitimate webhook to the app's endpoint:
   - Headers: `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`
   - Body: attacker-controlled JSON (attacker fully controls the content of orders/products/etc. in their own shop).
3. Attacker captures this exact `(raw_body, hmac)` pair.
4. Attacker resends the identical body and HMAC header to the same endpoint, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate` recomputes the HMAC over `raw_body` only and it matches, so `Registry.process` proceeds and invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON>, ...)` [7](#0-6) .
6. Any host application logic keyed on `data.shop` (e.g., "look up victim-shop's session/store and update its local order record") now acts on attacker-supplied data under the victim shop's identity.

          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
