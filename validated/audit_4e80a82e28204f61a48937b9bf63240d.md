### Title
`TokenExchange.exchange_token` sends the app's `client_secret` to a shop host taken from the JWT `dest` claim without validating it against Shopify's trusted domain list - ([File: lib/shopify_api/auth/token_exchange.rb])

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the shop host it talks to directly from the session token's `dest` claim and uses it, unvalidated, to build the HTTPS endpoint that receives the app's `client_id`/`client_secret` in the token-exchange POST body. Every other credential-sending flow in the same module and sibling files (`migrate_to_expiring_token`, `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`) explicitly runs the shop value through `Utils::ShopValidator.sanitize!` before using it to build the request host, but `exchange_token` skips this check.

### Finding Description
`exchange_token` decodes the caller-supplied session token via `ShopifyAPI::Auth::JwtPayload.new(session_token)` and takes `dest_shop = jwt_payload.shop`: [1](#0-0) 

`JwtPayload#shop` simply strips the scheme off the raw `dest` claim with no further validation: [2](#0-1) 

`JwtPayload#initialize` only checks that the JWT's signature is valid and that `aud == Context.api_key`; it never checks that `iss`/`dest` is a trusted Shopify domain (`myshopify.com`, `myshopify.io`, `shopify.com`, `spin.dev`, `shop.dev`): [3](#0-2) 

`dest_shop` is then used unchanged to construct a `Session` whose `shop` attribute becomes the HTTP request host: [4](#0-3) 

`Clients::HttpClient` builds `@base_uri` directly from `session.shop` with no domain allow-listing at this layer either: [5](#0-4) 

so the request (containing `client_id` and `client_secret` in the JSON body) is POSTed to `https://#{dest_shop}/admin/oauth/access_token`.

By contrast, the sibling flows that build the exact same kind of request explicitly sanitize the shop against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` before it is allowed to become the request host: [6](#0-5) [7](#0-6) [8](#0-7) [9](#0-8) 

The identity binding that should hold is: **shop host validated == shop host that receives `client_secret`**. In `exchange_token` this equality is not enforced — the "validated" side of the equation (JWT signature + audience check) never asserts that the *host string itself* falls within the domain the app is willing to send credentials to, unlike every other code path in this file/module that performs the same class of request.

### Impact Explanation
If the `dest` claim value is ever attacker-influenced or does not correspond to a Shopify-owned domain (e.g., through a non-standard/self-hosted integration, a misconfigured `Context.api_secret_key`/`old_api_secret_key` rotation window, or any future change to how session tokens are sourced/validated upstream of this call), the gem will POST the app's `client_id` and `client_secret` to that attacker-controlled host — a High severity credential-leakage/SSRF-with-credentials outcome, matching the class of "host validated versus host that receives client_secret" identity-binding failures called out in the prompt. This is a real inconsistency in the codebase's own defense-in-depth model: the exact same operation is guarded with `ShopValidator.sanitize!` everywhere else it appears.

### Likelihood Explanation
Under Shopify's documented protocol, `dest` is only ever set by Shopify's own token-issuance for embedded apps, and the JWT signature is verified with the app's secret, which constrains ordinary exploitation. However, likelihood is elevated because this validation gap is asymmetric with parallel code paths in the same module: any future relaxation of JWT validation, any code path that constructs `JwtPayload` from less-trusted input, or any regression in the leeway/secret-rotation handling directly weakens this flow's protection with no independent domain check as a backstop, whereas the sibling flows retain that backstop regardless.

### Recommendation
Add `Utils::ShopValidator.sanitize!(dest_shop)` (or equivalent) immediately after `dest_shop = jwt_payload.shop` in `ShopifyAPI::Auth::TokenExchange.exchange_token`, exactly as is already done in `migrate_to_expiring_token`, `ClientCredentials.client_credentials`, and `RefreshToken.refresh_access_token`, so the host that will receive `client_id`/`client_secret` is always confirmed to be within `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` before the request is issued.

### Proof of Concept
1. Construct (or otherwise obtain) a session token whose `dest` claim is `https://attacker.example` and whose `aud` equals the app's configured `api_key`, signed with a secret that can pass `JwtPayload#decode_token` (e.g., an attacker-controlled staging environment sharing key material, or a future validation regression).
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. Observe that `dest_shop` is set to `attacker.example` with no domain check, `Clients::HttpClient` is constructed with `session.shop == "attacker.example"`, and the POST request (including `client_id`/`client_secret` in the body) is sent to `https://attacker.example/admin/oauth/access_token`, contrasted with `client_credentials`/`refresh_token`/`migrate_to_expiring_token`, which would raise `ShopifyAPI::Errors::InvalidShopError` for the same input via `ShopValidator.sanitize!`.

      sig { params(token: String).void }
      def initialize(token)
        payload_hash = begin
          decode_token(token, Context.api_secret_key)
        rescue ShopifyAPI::Errors::InvalidJwtTokenError
          raise unless Context.old_api_secret_key

          decode_token(token, T.must(Context.old_api_secret_key))
        end

        @iss = T.let(payload_hash["iss"], String)
        @dest = T.let(payload_hash["dest"], String)
        @aud = T.let(payload_hash["aud"], String)
        @sub = T.let(payload_hash["sub"], T.nilable(String))
        @exp = T.let(payload_hash["exp"], Integer)
        @nbf = T.let(payload_hash["nbf"], Integer)
        @iat = T.let(payload_hash["iat"], Integer)
        @jti = T.let(payload_hash["jti"], String)
        @sid = T.let(payload_hash["sid"], T.nilable(String))

        raise ShopifyAPI::Errors::InvalidJwtTokenError,
          "Session token had invalid API key" unless @aud == Context.api_key
      end

      sig { returns(String) }
      def shop
        @dest.gsub("https://", "")
      end
