### Title
`Bonding.transferCreator` performs a single-step transfer of the creator role with no acceptance step, permanently freezing future creator fees if sent to an uncontrolled address - (File: `packages/contracts/src/Bonding.sol`)

### Summary
`Bonding.transferCreator(tokenAddress, newCreator)` reassigns a token's `creator` role in one transaction with no confirmation step from `newCreator`, mirroring the exact bug class in the external report (single-step `Ownable.transferOwnership`). If the current creator mistypes `newCreator` or points it at an address they don't control, the creator role — and all future fee attribution tied to it — is lost irrecoverably, since only the (now uncontrolled) `info.creator` can call `transferCreator` again to fix it.

### Finding Description
`transferCreator` sets `info.creator = newCreator` directly, gated only by `msg.sender == info.creator`, with no `pendingCreator` staging or `acceptCreator` step: [1](#0-0) 

This `creator` field is the sole source of truth for future fee attribution — every buy/sell fee accrual reads `Bonding.tokenInfo(token).creator` and forwards it into `FeeVault.accrue(token, creator, creatorAmount, protocolAmount, isBuy)`: [2](#0-1) 

`FeeVault.accrue` credits `creatorAmount` into `creatorBalance[creator]`, which only `creator` itself can withdraw via `claim()`: [3](#0-2) 

Notably, the codebase's own developers were aware of exactly this bug class and mitigated it elsewhere: `FeeVault`'s admin `owner` explicitly uses `Ownable2StepUpgradeable` "so a bad `transferOwnership` can be cancelled ... before it takes effect — single-step transfer to a fat-fingered or contract-incompatible address would otherwise brick every owner-only path": [4](#0-3) 

`transferCreator`, however, was not built with the same two-step safeguard, despite being the analogous role-transfer function reachable by any unprivileged token creator.

### Impact Explanation
Once `transferCreator` sends the role to an address the creator does not control (typo, wrong-chain address, non-interactive contract, etc.), every subsequent buy/sell fee accrual on that token permanently credits `creatorBalance[newCreator]` in `FeeVault` to an address that can never call `claim()`. This is a permanent freezing of the token's ongoing creator-fee stream (0.25% of every future buy/sell), with no recovery path: `transferCreator` can only be re-invoked by the current (uncontrolled) `info.creator`, and there is no owner/admin override to reassign it back.

### Likelihood Explanation
This is a self-inflicted, one-transaction mistake by the token creator (an unprivileged, permissionless role — anyone can become a creator via `Bonding.launch`/`Zap.createToken`), so likelihood scales with normal user error (typos, wrong clipboard paste, wrong-checksum/wrong-chain address) rather than an attacker exploiting another party. It requires no privileged access and is directly reachable from a standard transaction.

### Recommendation
Convert `transferCreator` into a two-step process: `transferCreator(tokenAddress, newCreator)` should stage `newCreator` in a `pendingCreator` mapping, and a new `acceptCreator(tokenAddress)` function — callable only by the pending address — should finalize the role change by setting `info.creator = pendingCreator[tokenAddress]`. This mirrors the `Ownable2StepUpgradeable` pattern already used for `FeeVault`'s owner in this codebase.

### Proof of Concept
1. `creator` launches `tokenAddr` via `Zap.createToken`, becoming `Bonding.tokenInfo(tokenAddr).creator`.
2. `creator` calls `bonding.transferCreator(tokenAddr, newCreator)` where `newCreator` is mistyped or is an address with no known private key / an incompatible contract.
3. `info.creator` is now permanently `newCreator`; see `test_transferCreator` in the test suite showing the one-call, no-confirmation semantics: [5](#0-4) 
4. Every subsequent trade on `tokenAddr` accrues creator fees into `FeeVault.creatorBalance[newCreator]` via `accrue`, which nobody can ever `claim()`, and `transferCreator` can no longer be called (`msg.sender != info.creator` for anyone else), permanently freezing all future creator fees for that token.

```text
    function transferCreator(
        address tokenAddress,
        address newCreator
    ) external {
        if (newCreator == address(0)) revert ZeroAddress();
        TokenInfo storage info = _s().tokenInfo[tokenAddress];
        if (msg.sender != info.creator) revert NotCreator();
        if (newCreator == info.creator) revert InvalidInput();
        info.creator = newCreator;
        emit CreatorTransferred(tokenAddress, msg.sender, newCreator);
    }
```

```text
    function accrue(
        address token,
        address creator,
        uint256 creatorAmount,
        uint256 protocolAmount,
        bool isBuy
    ) external onlyDepositor {
        FeeVaultStorage storage $ = _s();
        if (creatorAmount > 0) {
            if (creator == address(0)) revert ZeroAddress();
            $.creatorBalance[creator] += creatorAmount;
            $.totalAccruedCreator += creatorAmount;
            $.lifetimeCreatorEarned[creator] += creatorAmount;
        }
        if (protocolAmount > 0) {
            $.protocolBalance += protocolAmount;
            $.lifetimeProtocolEarned += protocolAmount;
        }
        if ($.usdc.balanceOf(address(this)) < $.totalAccruedCreator + $.protocolBalance) {
            revert UnderfundedAccrual();
        }
        emit FeeAccrued(token, creator, creatorAmount, protocolAmount, isBuy);
    }

    // ─── Claims ──────────────────────────────────────────────────────────

    function claim() external nonReentrant returns (uint256 amount) {
        FeeVaultStorage storage $ = _s();
        amount = $.creatorBalance[msg.sender];
        if (amount == 0) revert NothingToClaim();
        $.creatorBalance[msg.sender] = 0;
        $.totalAccruedCreator -= amount;
        $.usdc.safeTransfer(msg.sender, amount);
        emit CreatorFeesClaimed(msg.sender, amount);
    }
```
