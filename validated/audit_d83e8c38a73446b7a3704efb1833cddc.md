### Title
Webhook shop-domain and topic headers are trusted for tenant identification without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used by `ShopifyAPI::Webhooks::Registry.process` to route and label the webhook come from unauthenticated HTTP headers. This breaks the binding: `hmac_verified_bytes == bytes_the_app_acts_on`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are all read straight from HTTP headers, none of which are included in the HMAC computation: [2](#0-1) 

`Registry.process` validates only the body-derived HMAC via `HmacValidator.validate(request)`, then uses the *header*-derived `request.topic` to select a handler and passes the *header*-derived `request.shop` straight into `WebhookMetadata` without any additional cross-check that this shop is the one actually expected for this payload: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` recompute the HMAC purely over `verifiable_query.to_signable_string` (i.e., the raw body for webhook requests) and compare it to the `hmac` header: [4](#0-3) 

Because the `shop-domain` header is not part of the signed material, the identity binding the gem needs — "the shop this webhook is HMAC-verified for" == "the shop the handler acts on" — does not hold. Any request whose body produces a valid HMAC for the app's secret (trivially obtainable by an app-installing attacker on their **own** shop, since the fee/topic-independent body such as `{}` or any captured legitimate webhook payload/HMAC pair is portable) can be replayed with an arbitrary `x-shopify-shop-domain` (and `x-shopify-topic`) header, and the library will pass that spoofed shop/topic straight to the registered handler as if it were an authentic message about that tenant.

### Impact Explanation
This lets an unprivileged internet user who has the app installed on any shop they control forge webhook deliveries that appear to originate from a **different**, victim shop (cross-tenant confusion) or under a different topic than what was actually signed. Depending on how the host application's handler consumes `WebhookMetadata#shop`/`#topic` (e.g., looking up/mutating stored per-shop state, processing `app/uninstalled` or GDPR mandatory webhooks, or reconciling billing/subscription state), this can lead to cross-tenant data manipulation or logic being executed against the wrong tenant, satisfying the "cross-tenant access" impact bar for this analog class.

### Likelihood Explanation
Exploitation requires the attacker to be able to deliver an HTTP request to the app's webhook endpoint with a body+HMAC pair valid for the real `api_secret_key`. The most trivial route: an attacker who installs the app on their own store (a normal, unprivileged action) receives real Shopify webhooks with real valid HMACs for arbitrary/known bodies (e.g., many webhook payloads are highly predictable or even empty in some topics), then replays that exact `raw_body`+`hmac` pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain`/`x-shopify-topic` headers. No secret material or victim credentials are needed, only the ability to send arbitrary headers, which any internet client (or the attacker's own shop's genuine webhook delivery, replayed) can do.

### Recommendation
Include the tenant/topic identifying values in the material that is authenticated, or otherwise bind the header-derived `shop`/`topic` to a value that can't be spoofed independent of the signature:
- If Shopify's real HMAC covers only the body (as documented), do not treat header-derived `shop`/`topic`/`webhook_id` as trusted identifiers by themselves; require applications to independently verify that the `shop` header corresponds to a shop with an active session/registration for that specific `webhook_id`/topic before acting, or fetch/confirm the topic and shop via a signed source (e.g., cross-check against the registered webhook subscription registered via GraphQL, keyed by `webhook_id`).
- At minimum, document loudly (and ideally enforce in code) that `WebhookMetadata#shop` and `#topic` are unauthenticated header values not covered by the HMAC and must not be used as the sole tenant/topic determination for privileged or destructive operations.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Shopify sends a real webhook to the app's public endpoint with:
   - body: `{}` (or any observed real payload)
   - header `x-shopify-hmac-sha256`: valid HMAC of that body under the app's `api_secret_key`
   - header `x-shopify-shop-domain`: `attacker-shop.myshopify.com`
   - header `x-shopify-topic`: `orders/create` (for example)
3. Attacker captures this raw body + HMAC pair.
4. Attacker (or anyone) sends a new HTTP request directly to the app's public webhook route reusing the same raw body and `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and/or a different `x-shopify-topic`).
5. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks the (unchanged) body against the (unchanged, still-valid) HMAC.
6. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` dispatches to the handler registered for the spoofed topic and calls it with `WebhookMetadata.new(topic: <spoofed>, shop: "victim-shop.myshopify.com", ...)`, causing the app to process/act as though this event genuinely originated from `victim-shop.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
