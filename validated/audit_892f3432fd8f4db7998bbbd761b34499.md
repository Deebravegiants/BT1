This confirms the vulnerability. In `test_staker_can_switch_operator` (lines 1614-1624), the stale distribution to `operator_1` is paid directly to `operator_1_address` without any `beneficiary_for_operator` check — because at that point `distribute_internal` is called with `operator = operator_2_address` (the new operator), so `recipient == operator` fails for `operator_1` even though `operator_1` is the actual shareholder owed commission. In that specific test no beneficiary was set for `operator_1`, so the bug is masked (paying directly to `operator_1` looks "correct" only because `beneficiary_for_operator(operator_1) == operator_1` by default). But if `operator_1` had set a beneficiary via `set_beneficiary_for_operator`, that beneficiary would never receive the stale share — it would go straight to `operator_1` instead, which is exactly the bug in `distribute_internal` at `aptos-move/framework/aptos-framework/sources/staking_contract.move:896`. ### Title
Stale operator shares in `distribution_pool` bypass `beneficiary_for_operator` redirection after `switch_operator` - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`distribute_internal` (line 896) redirects a payout to an operator's beneficiary only when `recipient == operator`, comparing against the single `operator` parameter passed into the call — which is always the *current* operator address for that `StakingContract`. After `switch_operator` runs, `request_commission_internal` can leave an un-redeemed share for the `old_operator` inside the same `distribution_pool` (buy-in happens for `old_operator` right before the operator field is overwritten to `new_operator`). When those shares are later paid out via `distribute()`/`distribute_internal(staker, new_operator, ...)`, `recipient` will be `old_operator`, which never equals `operator` (`new_operator`), so the beneficiary redirect is skipped and the funds are sent directly to `old_operator`'s address instead of `beneficiary_for_operator(old_operator)`.

### Finding Description
`switch_operator` (lines 762-805) does the following in order:
1. Removes the `StakingContract` for `old_operator` from the map.
2. Calls `distribute_internal(staker, old_operator, &mut staking_contract)` to flush any already-inactive stake (correctly using `old_operator` as the redirect key at that point).
3. Calls `request_commission_internal(old_operator, &mut staking_contract)`, which invokes `add_distribution` → `distribution_pool.buy_in(old_operator, commission_amount)`. This creates a new, unredeemed share for `old_operator` in the pool, representing commission accrued up to the switch but not yet withdrawable from the stake pool (pending lockup).
4. Only after that does it call `stake::set_operator_with_cap(..., new_operator)` and re-insert the contract under `new_operator`.

Once the lockup expires and someone calls `distribute(staker, new_operator)`, `distribute_internal` iterates `distribution_pool.shareholders()`, which still contains `old_operator`. The redirect check at line 896, `if (recipient == operator)`, compares `old_operator` against the `operator` parameter which is now `new_operator`. Since they differ, the redirect to `beneficiary_for_operator(old_operator)` never executes, and `old_operator`'s stale commission is deposited straight to `old_operator`'s own address via `aptos_account::deposit_coins(recipient, ...)` at line 899-901.

`BeneficiaryForOperator` is a global per-operator-account resource (line 362-368), independent of any specific staker relationship, so a beneficiary set for `old_operator` before the switch remains valid and is expected to receive any commission attributable to `old_operator`, including this stale, pending distribution left over from before the switch. The existing invariant documented at line 807-809 ("An operator can set one beneficiary... any existing unpaid commission rewards will be paid to the new beneficiary") is violated for this specific residual-share case.

### Impact Explanation
The beneficiary mechanism exists specifically so operators can redirect commission payouts to a different address without changing keys on the stake pool. This bug allows commission funds legitimately owed to `old_operator`'s designated beneficiary to instead be deposited into `old_operator`'s own account. Since `distribute()` is a public, unprivileged entry function callable by anyone, an unprivileged caller (or even the operator itself, accidentally or intentionally) can trigger this misrouting simply by waiting for the lockup and calling `distribute(staker, new_operator)`. This is a custody-relevant redirection of value away from the intended beneficiary/recipient, changing "who can own" a portion of unlocked stake-pool commission.

### Likelihood Explanation
This requires the specific sequence: staker calls `switch_operator`/`switch_operator_with_same_commission` while there is unpaid commission pending for `old_operator` that becomes withdrawable only after the operator switch, and `old_operator` has set (or later sets) a beneficiary. This is a realistic and plausible operational sequence in production (operators change frequently and setting beneficiaries is a supported feature), so likelihood is moderate, gated by the staker's own switch action plus timing of lockup expiry — the payout itself is triggerable by anyone once conditions exist.

### Recommendation
In `distribute_internal`, redirect to the beneficiary based on the actual shareholder's own beneficiary mapping rather than comparing against the `operator` parameter, e.g. change the check to attempt `beneficiary_for_operator(recipient)` redirection whenever `recipient` has (or could have) a `BeneficiaryForOperator` entry, or more precisely, track which shareholders are "operator-type" recipients (current or historical) explicitly rather than relying on equality with the single current `operator` value.

### Proof of Concept
1. `setup_staking_contract(staker, operator1, ...)`, join validator set, `stake::end_epoch()` to accrue rewards.
2. `set_beneficiary_for_operator(operator1, beneficiary1)`.
3. Do **not** fully distribute/settle before switching — ensure `request_commission_internal` inside `switch_operator` creates a fresh, unredeemed distribution for `operator1` (i.e., rewards exist that haven't yet passed through a lockup cycle).
4. Call `switch_operator(staker, operator1, operator2, new_commission)`. This adds an `operator1` share into the pool while the map key is now `operator2`.
5. `stake::fast_forward_to_unlock(pool_address)`.
6. Call `distribute(staker_address, operator2_address)` (callable by any unprivileged account).
7. Assert `coin::balance<AptosCoin>(operator1_address)` increased by the stale commission amount, and `coin::balance<AptosCoin>(beneficiary1_address)` did **not** increase — demonstrating the beneficiary redirection was bypassed for `operator1`'s stale share, contrary to the intent shown by the analogous, already-passing beneficiary redirection test at [4](#0-3) .
