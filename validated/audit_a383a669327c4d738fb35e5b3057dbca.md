### Title
Unallowlisted route venues can execute attacker contracts under a caller’s signed authorization tree - (contracts/swap-aggregator/src/execute/mod.rs)

### Summary
A user-controlled swap route can name an arbitrary pool contract, which the swap aggregator then invokes during controller strategies such as `swap_collateral`. That contract can add an unrelated token transfer from the caller to the attacker beneath the caller’s authorized invocation; if the simulated authorization tree is signed, the transfer executes and drains unrelated wallet funds. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`swap_collateral(caller, account_id, current, from_amount, new, swap)` accepts caller-supplied opaque `swap` bytes after authenticating the account owner or delegate. [4](#0-3)  The controller forwards those bytes to the configured aggregator as `execute_strategy(controller, amount_in, swap)` while authorizing only the exact input-token transfer. [5](#0-4) 

The aggregator decodes a `Swap` instruction’s pool address directly from the payload’s `assets` registry and dispatches it to the selected venue adapter. [1](#0-0)  Program validation bounds the pool index but does not verify that the resolved address is an approved venue contract. [6](#0-5)  The venue dispatcher then invokes whichever concrete pool implementation corresponds to the encoded venue, while only measuring the router’s token balances afterward. [7](#0-6) 

A malicious pool can therefore execute arbitrary contract code beneath the caller’s root authorization. The regression test’s `RogueHopPool.swap` calls `token.transfer(victim, attacker, amount)` for an unrelated wallet token. [8](#0-7)  Transaction simulation records that transfer as a child of Alice’s `swap_collateral` authorization, and enforcing mode executes it when Alice signs the generated tree. [9](#0-8) [3](#0-2) 

### Impact Explanation
An attacker can steal arbitrary wallet tokens from a user who signs the simulated authorization tree, including tokens unrelated to the lending position and unbounded by the routed amount or route minimum output. [10](#0-9)  This is theft of user funds: the test moves Alice’s entire 77,770-unit unrelated-token balance to the attacker while the apparent collateral swap still succeeds. [11](#0-10) [12](#0-11) 

### Likelihood Explanation
Exploitation requires the victim to invoke a malicious route and sign the extra authorization produced by simulation; an unsigned rogue transfer is rejected and the whole transaction rolls back. [13](#0-12)  Nevertheless, route bytes are opaque inputs supplied to ordinary unprivileged strategy entrypoints, and the wallet-facing authorization tree is the only boundary preventing the additional transfer. [14](#0-13) [10](#0-9) 

### Recommendation
Do not allow route payloads to select arbitrary venue contract addresses for calls made beneath a lending authorization. Maintain an on-chain allowlist of approved pool/venue contracts, or otherwise cryptographically bind executable routes to trusted route producers. Clients should also decode every route and reject any simulated authorization tree containing children beyond the expected strategy input transfer. [6](#0-5) [10](#0-9) 

### Proof of Concept
1. The attacker deploys a contract whose `swap` function calls `token::Client::transfer(victim, attacker, amount)` on a token held by the victim. [8](#0-7) 
2. The attacker encodes that contract as a hop-pool address in `swap` and induces the victim to call `swap_collateral(caller, account_id, usdc_market, amount, eth_market, swap)`. [15](#0-14) 
3. The controller invokes the router with the route. [14](#0-13) 
4. The router resolves and invokes the attacker’s pool address. [1](#0-0) 
5. Simulation records `token.transfer(victim → attacker)` as a child authorization of the victim’s `swap_collateral` call. [16](#0-15) 
6. If the victim signs that tree, the unrelated wallet balance reaches zero and the attacker receives it. [3](#0-2)

**File:** docs/explanation/threat-model.md (L154-164)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
```
