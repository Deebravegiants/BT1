### Title
Fraud detection is permanently disabled, forcing all signups to `SignupReason::Normal` regardless of pipeline anomalies - (File: src/plans/fraud_check.rs, src/plans/mod.rs)

### Summary
`Report::fraud_checks_strict` in `src/plans/fraud_check.rs` is hard-coded to an empty array because `N_FRAUD_CHECKS = 0`, making `Report::fraud_detected()` unconditionally return `false`. `MasterPlan::detect_fraud` in `src/plans/mod.rs` independently also just returns `Ok(false)` with a comment stating all fraud checks were deleted, so no signup can ever be flagged as fraudulent through this path, no matter what the biometric pipeline output looks like.

### Finding Description
`FraudChecks::run()` returns an empty `Report {}` [1](#0-0) , and `Report::fraud_detected()` iterates over `fraud_checks_strict()`, which maps over the empty `fraud_checks()` array (`N_FRAUD_CHECKS = 0`) and therefore is always `[]`, so `.any(|&v| v)` is vacuously `false` [2](#0-1) [3](#0-2) [4](#0-3) . Separately, `MasterPlan::detect_fraud` — the actual call site invoked from the signup flow after the biometric pipeline runs — never even constructs a `Report`; it unconditionally returns `Ok(false)` for any `Some(pipeline)`, with an explicit comment "FOSS: WE HAVE DELETED ALL FRAUD CHECKS" [5](#0-4) . The `skip_fraud_checks` config flag is also unrelated/dead in this respect — it is only gated behind the `allow-plan-mods` feature and returns `false` in production builds anyway, but it does not matter since `detect_fraud` never uses fraud-check results in the first place [6](#0-5) . As a result, the invariant "missing/anomalous fraud signals must fail closed" is violated: this is not a fail-closed default (`unwrap_or(true)` logic exists in `fraud_checks_strict` and `Report::fraud_detected` in `fraud-engine/src/report.rs`, showing the *intended* semantics), but that logic is bypassed entirely because there are zero checks to run and the call site short-circuits to `Ok(false)` regardless of the pipeline's actual content.

### Impact Explanation
Every signup that completes the biometric pipeline is unconditionally classified as `SignupReason::Normal`, since `detect_fraud` never returns `true`. This means the custody-package tagging, alerting, and any downstream backend-side handling that depend on the orb-side fraud verdict as a first-line signal receive no information — capture sessions with clearly anomalous/error pipeline output are enrolled and uploaded exactly like clean signups. This matches an Orb bounty impact of "liveness/fraud detection bypass," though the severity is limited by the fact that this is a "FOSS" build path (explicitly labeled as intentionally stripped for the open-source release) rather than a subtle logic bug, and by whatever independent backend-side fraud verification exists outside this repo (not visible/verifiable from this codebase).

### Likelihood Explanation
Preconditions are trivial: any successful signup that reaches `detect_fraud` with `Some(pipeline)`, i.e., any normal signup flow. This is deterministic and reproducible 100% of the time in this build configuration — no attacker action beyond a normal signup attempt is needed.

### Recommendation
Restore actual fraud-check implementations (currently zeroed out via `N_FRAUD_CHECKS = 0`) or, if this is an intentional FOSS/open-source stripped build, ensure that: (1) `MasterPlan::detect_fraud` does not silently claim "no fraud" when checks are absent — it should either fail-closed (mark unknown/missing checks as fraud, consistent with the `unwrap_or(true)` semantics already present in `Report::fraud_detected`) or explicitly document/gate that fraud detection is disabled in this build variant so downstream consumers of `SignupReason` are aware detection is inert, and (2) any production (non-FOSS) build must re-enable real fraud checks before deployment.

### Proof of Concept
Unit test in `src/plans/fraud_check.rs`:
```rust
#[test]
fn fraud_detected_should_reflect_anomalous_pipeline_state() {
    // Construct or mock a biometric_pipeline::Pipeline with clearly
    // anomalous/error fields (e.g., missing iris codes, low quality flags).
    let pipeline = /* anomalous pipeline fixture */;
    let mut checks = FraudChecks::new(&pipeline);
    let report = checks.run();
    // Expected (currently fails): fraud_detected() should be true for
    // anomalous input.
    assert!(report.fraud_detected());
}
```
This currently fails because `Report {}.fraud_detected()` always returns `false` regardless of `pipeline` content, and `MasterPlan::detect_fraud` never inspects the pipeline before returning `Ok(false)` [7](#0-6) .
