### Title
Untrusted route code can abuse the caller’s signed authorization tree to steal unrelated wallet assets - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
Controller strategy routes execute payload-selected external pool contracts beneath the user-authorized `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, or `multiply` invocation. [1](#0-0)  The controller constrains only its own exact input transfer to the router and measures only the controller’s token balances afterward. [2](#0-1)  A malicious route venue can therefore request the victim’s authorization for an unrelated token transfer; Soroban simulation records it as a child of the strategy authorization, and it executes if the victim signs that returned tree. [3](#0-2) 

### Finding Description
`swap_tokens` passes the user-supplied `StrategySwap` payload to the configured router without binding execution to trusted venue or pool addresses. [4](#0-3)  In the router, each decoded swap selects its `pool`, `token_in`, and `token_out` from the caller-controlled `assets` registry and dispatches to that pool. [5](#0-4)  The venue dispatch measures only the router’s input and output balance deltas and does not prevent the selected contract from making additional calls that require the strategy caller’s authorization. [6](#0-5) 

Because the strategy entrypoint was authorized by the victim, a token `transfer(victim, attacker, amount)` performed by the malicious venue is represented as a child invocation under that authorization tree. [7](#0-6)  An honest authorization tree rejects the extra transfer, but the poisoned simulated tree succeeds and moves the victim’s unrelated wallet balance. [8](#0-7) 

### Impact Explanation
An attacker can steal arbitrary token balances held by the victim, including assets that were never supplied to XOXNO Lending and are not part of the strategy input. [9](#0-8)  The route can simultaneously return enough output token to satisfy router settlement and the controller’s positive-output check, so neither the payload minimum nor the final account-risk gate bounds the wallet loss. [10](#0-9)  The demonstrated result is direct theft of user funds. [11](#0-10) 

### Likelihood Explanation
The attacker can deploy a malicious pool contract, encode it as a route hop, and present the resulting strategy to a victim through a malicious or compromised quoting interface. [12](#0-11)  The attack requires the victim to sign the authorization tree containing the extra token transfer, analogous to requiring a user to click malicious stored content in the reference issue. [13](#0-12)  Wallets or clients that display only the requested strategy and do not fully decode every recorded child authorization make this practical. [14](#0-13) 

### Recommendation
Do not allow arbitrary payload-selected pool contracts to execute beneath a user-authorized strategy unless their addresses are governance-allowlisted or otherwise constrained to known-safe venue contracts. [15](#0-14)  Clients must independently decode `swap` payloads and reject any simulated authorization tree containing children beyond the expected controller/router input transfer. [14](#0-13)  Wallet-facing tooling should render every child invocation—including token, sender, recipient, and amount—before signature collection. [7](#0-6) 

### Proof of Concept
1. Deploy a rogue pool implementing the venue interface; its swap function pays the expected output to the router and additionally calls `token::transfer(victim, attacker, wallet_balance)` on an unrelated token held by the victim. [16](#0-15) 
2. Encode a route whose asset registry names the rogue pool and whose swap operation uses the victim’s input token and a valid output token. [17](#0-16) 
3. Ask the victim to execute `swap_collateral(caller=victim, account_id, current, amount, new, swap=malicious_route)`. [18](#0-17) 
4. Simulation records `token.transfer(victim, attacker, wallet_balance)` as a child of the victim’s `swap_collateral` authorization. [7](#0-6) 
5. If the victim signs that tree, the unrelated wallet balance is transferred to the attacker while the strategy still receives the expected output collateral. [11](#0-10)

**File:** docs/explanation/threat-model.md (L154-164)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
```
