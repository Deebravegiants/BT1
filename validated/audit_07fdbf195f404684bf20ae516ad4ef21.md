### Title
Webhook HMAC signature only covers the request body, not the `shop-domain`/`topic` headers used for tenant identification - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` verifies only that the body matches the HMAC and then forwards the header-derived `shop` value to the app's handler as if it were an authenticated tenant identifier. The identity binding `HMAC(secret, body) ≡ (shop, topic, body) authenticated for this shop` does not hold; only the body bytes are bound.

### Finding Description
`HmacValidator.validate` computes `HMAC-SHA256(api_secret_key, verifiable_query.to_signable_string)` and compares it to the `hmac` accessor: [1](#0-0) 

For webhooks, `to_signable_string` returns solely `@raw_body`, while `shop`, `topic`, `api_version`, and `webhook_id` are extracted straight from HTTP headers with no cryptographic relation to the HMAC: [2](#0-1) 

`Registry.process` validates the HMAC and, on success, immediately trusts `request.shop`/`request.topic`/`request.webhook_id` to build the metadata handed to the app's handler: [3](#0-2) 

Because the signable string is body-only, a `(body, hmac)` pair that is valid for shop A's webhook (e.g., captured from a webhook the attacker's own store legitimately received, since the same app-level `api_secret_key` signs every merchant's webhooks) remains a valid `(body, hmac)` pair when replayed with a different `shopify-shop-domain` / `shopify-topic` / `shopify-webhook-id` header value. `HmacValidator.validate` will accept the tampered request because it never inspects the headers, so the app processes the payload as an authentic event for whatever shop the attacker names in the header.

### Impact Explanation
This breaks tenant isolation: an unprivileged internet user who has ever received one legitimately signed webhook (e.g., by installing the app on a shop they control, which is a normal, non-privileged capability for any public app) can forge a request that the library certifies as an authentic webhook "from" any other shop domain of the attacker's choosing, because the shop identity is never covered by the signature. Any handler logic that keys off `WebhookMetadata#shop` (e.g., to select which merchant's stored offline session/access token to act on, revoke, or update) can be tricked into acting on the wrong tenant. This matches the Critical "cross-tenant access" bucket.

### Likelihood Explanation
Medium-High. The attacker only needs a single valid `(raw_body, hmac)` sample for the app's global `api_secret_key` — trivially obtainable by installing the app on any store, including their own, and capturing one webhook delivery. No access to the app's `client_secret`, TLS interception, or privileged account is required; only header manipulation on a POST to the app's own webhook endpoint.

### Recommendation
Include the header-derived identity fields (`shop-domain`, `topic`, and ideally `webhook_id`/`api_version`) in the signable material that `HmacValidator` verifies for webhooks, or otherwise cryptographically bind the header values to the signed body (e.g., verify Shopify's HMAC scheme is still body-only per Shopify's design, but require the consuming app to independently confirm the shop via a trusted, separately-authenticated channel — such as looking up an existing session by shop and rejecting unknown shops — before trusting `WebhookMetadata#shop`). At minimum, document loudly that `request.shop`/`request.topic` are NOT covered by HMAC verification and must not be trusted for tenant-scoping decisions without additional validation.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook delivery with body `B` and header `shopify-hmac-sha256: H` (valid because `H = HMAC(secret, B)`).
2. Attacker replays the exact same body `B` and signature `H` to the app's webhook endpoint, but sets `shopify-shop-domain: victim.myshopify.com` (and optionally a different `shopify-topic`).
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: tampered_headers)` builds successfully (header presence checks pass) and `Utils::HmacValidator.validate(request)` succeeds, since it only recomputes `HMAC(secret, B)`: [4](#0-3) 
4. The registered handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", topic: ..., body: parsed(B), ...)` and performs whatever tenant-scoped action it takes for `victim.myshopify.com`, even though the payload never originated from Shopify for that shop.

          return false unless verifiable_query.hmac

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
