### Title
Unaccounted native-ETH drain via `EmporiumOperation.value` when `erc20TokenAddresses` omits the ETH sentinel `address(0)` - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction` only reconciles balance changes for tokens listed in `circomData.erc20TokenAddresses`, using `address(0)` as the sentinel for native ETH via `getERC20OrETHBalance`/`getBalancesForArray` [1](#0-0) . Because `erc20TokenAddresses` is attacker-crafted `CircomData` whose only on-chain constraint is length equality to `dimensions.tokenNumber` and pairwise distinctness in-circuit [2](#0-1) , an attacker can simply exclude `address(0)` from that array. Any `EmporiumOperation` in the signed `EmporiumStack` with `op.value > 0` then moves ETH out of the Emporium contract via `op.endpoint.call{value: op.value}(op.callData)` [3](#0-2)  with zero visibility to the before/after balance-conservation loop, which iterates strictly over `circomData.erc20TokenAddresses` [4](#0-3) .

### Finding Description
Equality that should hold: for every asset the Emporium contract holds, `balancesAfter[i] - balancesBefore[i] + (deltaAmountChanges[i]<0 ? -deltaAmountChanges[i] : 0) >= 0` must be enforced for **all** assets that can leave the contract during `ops` execution. In practice this equality is only computed for indices `i` present in `circomData.erc20TokenAddresses` [5](#0-4) . Native ETH is represented in this scheme by the sentinel `address(0)` (see `getERC20OrETHBalance`) [6](#0-5) , but nothing forces `address(0)` to be a member of `erc20TokenAddresses` whenever an `EmporiumOperation.value` is nonzero.

Exploit path:
1. Emporium accumulates ETH over time via its bare `receive() external payable {}` [7](#0-6) , from unrelated deposit/swap flows.
2. Attacker submits their own transaction through the normal Hinkal flow with a `CircomData` whose `erc20TokenAddresses` array (fixed length = `dimensions.tokenNumber`, only constrained to be pairwise-distinct in-circuit) contains some ERC-20 addresses the attacker actually owns/uses, but deliberately omits `address(0)`.
3. The `EmporiumStack` decoded from `externalActionMetadata` sets `stack.signerAddress = address(0)`. In `verifyWallet`, when `signerAddress == address(0)` the function returns immediately after marking `usedMessages`, **without any EIP-712 signature check** [8](#0-7) . This means the whole `ops` array (including `op.value`) is attacker-controlled with no signer authorization required for this branch.
4. Because `signerAddress == address(0)`, the `op.invokeWallet && stack.signerAddress != address(0)` condition is always false, so every op runs the "Case 2: Stateless Interaction" branch: `op.endpoint.call{value: op.value}(op.callData)` is executed directly by `EmporiumUpgradeable` itself, funded from the contract's own ETH balance [3](#0-2) .
5. `op.endpoint` is an attacker-deployed contract that simply accepts ETH (or does nothing and returns success).
6. `getBalancesForArray`/`getERC20OrETHBalance` is only invoked over `circomData.erc20TokenAddresses`, which the attacker chose to exclude `address(0)`; hence the ETH balance drop is never observed, `deltaAmountChanges`/`balanceChange`/`utxoSet` accounting never sees it, and `revert BalanceChangeShouldBePositive()` never fires [9](#0-8) .
7. The circuit-side `calldataHash` check only verifies that `circomData` (including the `EmporiumStack`) matches what was proven, but the circuit has no constraint that ties `op.value`/`op.endpoint` to `erc20TokenAddresses`/`amountChanges` — those signals are opaque bytes to the circuit; only the ERC20 legs (`inTotal + amountChanges === outTotal`) are constrained [10](#0-9) . Nothing in `performHinkalChecks`/`dimensionsCheck` requires `address(0)` inclusion either [2](#0-1) .

Existing guards fail because: (a) `verifyWallet`'s signature check is skippable via `signerAddress = address(0)`, which is an intentionally supported "relay pays own gas token, no wallet" mode, not a bug by itself; (b) the balance-conservation loop is scoped to a caller-chosen token list that has no mandatory ETH entry; (c) `dimensionsCheck` only checks array *lengths* match `dimensions.tokenNumber`, never that `address(0)` must be present when native value is moved.

### Impact Explanation
An attacker can steal all native ETH sitting in the Emporium contract's balance (from any prior deposits/flows/other users) in a single transaction, redirecting it to a contract they control, with no requirement to burn any UTXO or have any claim on that ETH. This is direct theft of pooled/in-flight user funds — Critical severity per the given rubric. It is repeatable every time the Emporium contract holds a nonzero ETH balance (e.g., after partial/leftover ETH from swap or deposit flows that route through `receive()`), and each execution only costs one valid Hinkal external-action transaction plus gas.

### Likelihood Explanation
Preconditions: Emporium must hold nonzero ETH balance (plausible given deposit/swap flows funnel ETH through Emporium and it exposes a `receive()` fallback). The attacker needs no privileged role, no valid UTXO backing the drained amount, and no `signerAddress` at all (uses the `address(0)` unsigned branch that the protocol already supports for relay-paid flows). The only "cost" is crafting a normal-looking Emporium action with an unrelated ERC20 leg (to satisfy `dimensionsCheck`/circuit shape) while omitting `address(0)` from `erc20TokenAddresses`, and deploying a trivial ETH-receiving endpoint contract. This is fully within reach of an unprivileged EOA as scoped by the rules, is deterministic (no gas-griefing or oracle assumptions), and can be repeated whenever ETH balance is present.

### Recommendation
Enforce that `address(0)` (the ETH sentinel) is always part of the balance-reconciliation set for the Emporium action, regardless of whether the caller included it in `erc20TokenAddresses` — e.g., always additionally snapshot and re-check `address(this).balance` before/after the `ops` loop, treating any decrease not covered by a corresponding negative `deltaAmountChanges` entry as a revert condition, exactly mirroring the existing ERC20 logic. Alternatively/additionally, require `dimensionsCheck` (or a new check in `runAction`) to reject any `EmporiumStack` containing `op.value > 0` unless `address(0)` is present in `circomData.erc20TokenAddresses` with a matching `deltaAmountChanges` entry.

### Proof of Concept
Foundry fork/unit test plan:
1. Deploy `EmporiumUpgradeable` (or its proxy) and fund it with ETH via a call to its `receive()` (simulating a legitimate but unrelated prior deposit) — assert `address(emporium).balance == X`.
2. Deploy a minimal `AttackerSink` contract with a `receive() external payable {}`.
3. Build a `CircomData` with `erc20TokenAddresses = [someERC20]` (excluding `address(0)`), `amountChanges` balanced for that one ERC20 leg only, and `externalActionData.externalActionMetadata` = ABI-encoded `EmporiumStack{ signerAddress: address(0), ops: [{ endpoint: AttackerSink, invokeWallet: false, value: X, callData: "" }] }`.
4. Generate a locally valid proof for this `CircomData` (satisfying `inTotal + amountChanges === outTotal` for the single ERC20 leg, distinct-address check trivially true with one token) and call the normal Hinkal entrypoint that dispatches to `EmporiumUpgradeable.runAction`.
5. Assert both sides of the equality:
   - Before: `address(emporium).balance == X`, `AttackerSink.balance == 0`.
   - After: `address(emporium).balance == 0`, `AttackerSink.balance == X`.
   - Assert `runAction` did NOT revert with `BalanceChangeShouldBePositive` even though ETH left the contract uncompensated.
   - Assert the returned `utxoSet` and `deltaAmountChanges` contain no entry accounting for the `X` ETH moved (only the unrelated ERC20 leg is represented), proving the value-conservation equality was silently violated.
