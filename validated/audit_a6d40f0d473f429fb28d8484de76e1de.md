Audit Report

## Title
LDAP unauthenticated ("empty password") bind allows authentication bypass in `ldapAuthenticator.CreateSession` - (File: `core/sessions/ldapauth/ldap.go`)

## Summary
`ldapAuthenticator.CreateSession` passes the client-supplied `sr.Password` directly to `conn.Bind(searchBaseDN, sr.Password)` without first rejecting empty passwords. Per RFC 4513 §5.1.2, a simple bind with a non-empty DN and zero-length password is defined as an "unauthenticated bind," which many LDAP server configurations (e.g., default OpenLDAP) treat as successful without validating any credential, allowing an unauthenticated network attacker who knows a valid user's email to obtain a fully authenticated session with that user's role.

## Finding Description
The public, unauthenticated `POST /sessions` endpoint routes to `SessionsController.Create`, which binds the JSON body into `clsessions.SessionRequest` with no check that `Password` is non-empty [1](#0-0) , and `SessionRequest.Password` carries no required/length validation tag [2](#0-1) . This request is routed without authentication middleware to `sc.Create` [6](#0-5) .

For the LDAP provider, `CreateSession` binds directly with the attacker-controlled password: `conn.Bind(searchBaseDN, sr.Password)`. If `sr.Password` is empty, and the target LDAP server permits unauthenticated binds for that DN (RFC 4513-defined default behavior unless explicitly disabled), `err` is `nil`, so `returnErr` is never set from the bind step. The code proceeds to call `l.FindUser(ctx, escapedEmail)` to resolve the role and issues a full `ldap_sessions` row and session ID for that user/role, with no further password verification [3](#0-2) . The identical unguarded pattern exists in `TestPassword` [5](#0-4) .

This differs meaningfully from the local/OIDC-local path, which always compares against a stored bcrypt hash via `utils.CheckPasswordHash`, so an empty password cannot succeed there in practice [4](#0-3) . No middleware, input validator, or LDAP-client-side guard in the codebase rejects empty passwords before the bind call — the code relies entirely on the LDAP server's own configuration to reject unauthenticated binds, which is not guaranteed and is a well-documented pitfall called out explicitly by RFC 4513 §6.3.1.

## Impact Explanation
If exploitable against a given LDAP deployment, an attacker with no credentials who knows or guesses a valid mapped user's email (often a predictable corporate email) can obtain a legitimate authenticated session cookie with that user's role by submitting an empty password to `POST /sessions`. If the targeted account has `admin` role, this is a full node compromise vector, since role-gated endpoints (`RequiresAdminRole`, `RequiresEditRole`) would then be reachable [7](#0-6) . This maps to the in-scope "node API authentication or role bypass" impact category.

## Likelihood Explanation
Exploitability is conditional on the deployed LDAP server permitting unauthenticated/anonymous binds for the configured base DN. This is the RFC-defined default simple-bind behavior for a non-empty DN with an empty password, and remains a realistic and commonly-overlooked LDAP server misconfiguration in the wild. The chainlink codebase applies no defensive empty-password check before delegating trust to the bind call, which is a missing input-validation control that any secure LDAP client should implement regardless of server-side hardening, per RFC 4513 §6.3.1 guidance. Given LDAP auth is an opt-in enterprise feature, the population of affected deployments is a subset of installs, but the code-level gap is unconditional and reproducible whenever the backing LDAP server allows unauthenticated binds.

## Recommendation
In both `ldapAuthenticator.CreateSession` and `TestPassword`, reject any empty `Password`/`password` value immediately (returning an authentication failure) before calling `conn.Bind`, so that a zero-length password can never be interpreted as a successful "unauthenticated bind" credential check.

## Proof of Concept
1. Configure a chainlink node with LDAP auth enabled (`ldap.CreateSession` path) pointed at an LDAP server that permits unauthenticated binds for the configured `UsersDN()`/`BaseDN()` (default OpenLDAP behavior unless `olcDisallows: bind_anon` is set).
2. As an unauthenticated attacker, send:
   ```
   POST /sessions
   Content-Type: application/json

   {"email":"admin@example.com","password":""}
   ```
3. `ldapAuthenticator.CreateSession` calls `conn.Bind(searchBaseDN, "")`; the LDAP server returns success (`err == nil`) per unauthenticated-bind semantics.
4. `FindUser` resolves the role, an `ldap_sessions` row is inserted, and a valid session cookie for `admin@example.com`'s role is returned in the HTTP response — completing the bypass with no knowledge of the real password.

func (l *ldapAuthenticator) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	conn, err := l.ldapClient.CreateEphemeralConnection()
	if err != nil {
		return "", errors.New("unable to establish connection to LDAP server with provided URL and credentials")
	}
	defer conn.Close()

	var returnErr error

	// Attempt to LDAP Bind with user provided credentials
	escapedEmail := ldap.EscapeFilter(strings.ToLower(sr.Email))
	searchBaseDN := fmt.Sprintf("%s=%s,%s,%s", l.config.BaseUserAttr(), escapedEmail, l.config.UsersDN(), l.config.BaseDN())
	if err = conn.Bind(searchBaseDN, sr.Password); err != nil {
		l.lggr.Infof("Error binding user authentication request in LDAP Bind: %v", err)
		returnErr = errors.New("unable to log in with LDAP server. Check credentials")
	}

	// Bind was successful meaning user and credentials are present in LDAP directory
	// Reuse FindUser functionality to fetch user roles used to create ldap_session entry
	// with cached user email and role
	foundUser, err := l.FindUser(ctx, escapedEmail)
	if err != nil {
		l.lggr.Infof("Successful user login, but error querying for user groups: user: %s, error %v", escapedEmail, err)
		returnErr = errors.New("log in successful, but no assigned groups to assume role")
	}

	isLocalUser := false
	if returnErr != nil {
		// Unable to log in against LDAP server, attempt fallback local auth with credentials, case of local CLI Admin account
		// Successful local user sessions can not be managed by the upstream server and have expiration handled by the reaper sync module
		foundUser, returnErr = l.localLoginFallback(ctx, sr)
		isLocalUser = true
	}

	// If err is still populated, return
	if returnErr != nil {
		return "", returnErr
	}

	l.lggr.Infof("Successful LDAP login request for user %s - %s", sr.Email, foundUser.Role)

	// Save session, user, and role to database. Given a session ID for future queries, the LDAP server will not be queried
	// Sessions are set to expire after the duration + creation date elapsed, and are synced on an interval against the upstream
	// LDAP server
	session := sessions.NewSession()
	_, err = l.ds.ExecContext(
		ctx,
		"INSERT INTO ldap_sessions (id, user_email, user_role, localauth_user, created_at) VALUES ($1, $2, $3, $4, now())",
		session.ID,
		strings.ToLower(sr.Email),
		foundUser.Role,
		isLocalUser,
	)
	if err != nil {
		l.lggr.Errorf("unable to create new session in ldap_sessions table %v", err)
		return "", fmt.Errorf("error creating local LDAP session: %w", err)
	}

	l.auditLogger.Audit(audit.AuthLoginSuccessNo2FA, map[string]any{"email": sr.Email})

	return session.ID, nil
}
