Confirmed root cause: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop` is read directly from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header [2](#0-1) . `Registry.process` validates only the HMAC over the body via `Utils::HmacValidator.validate(request)` and then dispatches `request.shop` straight into the handler's `WebhookMetadata` without any additional cross-check [3](#0-2) .

### Title
Webhook shop identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes/validates the HMAC over the raw body only, but the `shop` (and `topic`/`webhook_id`/`api_version`) values used by `Registry.process` to attribute the event to a tenant come from unauthenticated HTTP headers.

### Finding Description
The equality that should hold is: `shop_used_for_dispatch == shop_covered_by_hmac`. In this gem, `to_signable_string` returns `@raw_body` only [1](#0-0) , so `Utils::HmacValidator.validate` in `Registry.process` [4](#0-3)  only proves that the body bytes were signed by `Context.api_secret_key` — it says nothing about which shop the header claims. `shop` is derived from `shopify_header("shop-domain")` [2](#0-1) , which is fully attacker-controlled at the transport layer and not part of the signed payload. Because all shops installing the same app share the same `api_secret_key`, any tenant that receives a legitimately HMAC-signed webhook for their own shop can replay that exact body to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop. The HMAC check still passes (body unchanged), and `Registry.process` forwards `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` [5](#0-4)  to the handler with the forged `shop` value, so the host application's handler processes/stores data under the wrong tenant.

### Impact Explanation
This breaks tenant isolation (cross-tenant confusion/spoofing): a merchant who owns a legitimate installation of the app can trigger the app to process attacker-supplied webhook data (including mandatory GDPR topics like `customers/data_request`, `customers/redact`, `shop/redact`) as if it originated from a different, victim shop, since the shop binding is never cryptographically verified. This matches the Critical-tier "cross-tenant access" impact category.

### Likelihood Explanation
Any existing app installer (an "unprivileged internet user" relative to other tenants) can capture one legitimate webhook delivery to their own shop (webhooks are delivered over plain HTTP(S) POST to a developer-controlled endpoint, so the body/HMAC pair is fully visible to the receiving app) and replay it with a modified shop-domain header. No access token, `client_secret`, or privileged credential is required — only knowledge of one's own valid webhook body+HMAC pair, which is delivered to the app owner as a normal part of using the app.

### Recommendation
Bind the shop (and topic/webhook id) into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived shop to the request, e.g., include the `shop-domain` header in `to_signable_string`, or cross-check `request.shop` against a shop already associated with the specific session used to look up/register that webhook subscription before dispatching to the handler.

### Proof of Concept
1. App installed on `shop-a.myshopify.com`; Shopify sends a legitimate webhook with `X-Shopify-Hmac-Sha256` computed over the raw body using the shared `api_secret_key`, and header `X-Shopify-Shop-Domain: shop-a.myshopify.com`.
2. The shop-a owner (an unprivileged actor with respect to shop-b) captures this raw body and HMAC value.
3. They replay the identical body and HMAC to the app's webhook endpoint but set `X-Shopify-Shop-Domain: shop-b.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` in `Registry.process` [4](#0-3)  succeeds because it only checks the body bytes.
5. `request.shop` returns `"shop-b.myshopify.com"` [2](#0-1) , and the handler receives `WebhookMetadata` attributing the attacker's body to shop-b, causing cross-tenant data confusion in the host application.
