### Title
Router executes hop pool addresses from the swap payload with no containment/allowlist, letting attacker-chosen contracts run under the caller's authorization tree - (File: contracts/swap-aggregator/src/venues/mod.rs)

### Summary
The CakePHP advisory (GHSA-wpvj-hjcr-h3p2) is a missing path-containment check: `View::_getElementFileName()` resolves a user-supplied element name without verifying it stays inside the allowed template paths, so crafted input reaches arbitrary files. The direct analog in XOXNO Lending is the swap router's hop dispatch: every `SwapHop` carries a `pool` address taken verbatim from the caller-supplied route XDR, and `dispatch_hop` invokes whatever contract that address names. There is no venue allowlist — the only whitelist in storage is a fee-side token whitelist (`DataKey::WhitelistedTokens`), not a pool registry. A rogue pool therefore runs on the call stack beneath the router, and any `require_auth` it performs (e.g. `token.transfer(victim, attacker, N)`) is recorded by simulation as a child of the caller's authorization entry, so a victim who signs the simulated tree authorizes the theft. This bypasses every measured-delta guard in the router because the stolen token never touches the vault ledger.

### Finding Description
`dispatch_hop` at `contracts/swap-aggregator/src/venues/mod.rs:23-40` builds a `HopContext` from `hop.pool` and invokes the venue adapter, which calls `env.invoke_contract(&ctx.hop.pool, "swap", ...)` (e.g. `contracts/swap-aggregator/src/venues/phoenix.rs:23-25`, `contracts/swap-aggregator/src/venues/comet.rs:30-34`). The `pool` field is decoded from attacker-controlled route bytes with no check that it is a real DEX pool — `grep` for allowlist/whitelist in the router shows only the fee whitelist. The controller path (`contracts/controller/src/strategies/swap.rs:33-38`) authorizes only an exact input transfer to the router, so the controller's own funds are safe — but the *caller* (`sender.require_auth()` in `execute_strategy`, and the account owner in `swap_collateral`/`swap_debt`/`multiply`) is the signer whose auth tree the rogue pool can populate. The host records a child `token.transfer(victim, attacker, amount)` under the victim's `swap_collateral`/`execute_strategy` entry; the harness test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` proves both halves: recording mode attaches the theft to the caller's entry, and enforcing mode executes it iff the signed tree lists it. The threat model acknowledges this at `docs/explanation/threat-model.md:154-165` and defers mitigation to clients ("a client must decode the route it signs"), which is contract-level absence of containment, not a fix.

### Impact Explanation
Theft of user funds. A rogue pool can drain any token balance of any user the attacker convinces to sign a poisoned route — including tokens the protocol never listed — bounded only by the victim's wallet balances, not by `amount_in`, `min_out`, or the residual cap. The measured-delta settlement, `RouterOverspend`/`NoSwapOutput` checks, and `residual_allowance` all pass because the stolen flow is orthogonal to the routed tokens.

### Likelihood Explanation
Requires phishing: the victim must sign an authorization tree containing the extra child transfer (simulation surfaces it). Standard signing flow signs what simulation returns, so a malicious quote/route source can poison it; no privileged access, leaked key, or contract bug beyond the missing containment is needed. Reachable through `execute_strategy` directly and through `swap_collateral`/`swap_debt`/`repay_debt_with_collateral`/`multiply` on the controller. Medium: high impact gated by a signature-phishing precondition that the protocol explicitly delegates to off-chain client hygiene.

### Recommendation
Maintain an owner-managed venue-pool allowlist (or venue factory/registry verification) and reject hops whose `pool` is not registered for the declared venue — i.e., apply the containment check CakePHP added: the resolved target must come from the expected set, not from user input. Short-term, surface a machine-readable "expected auth children" contract so wallets can refuse extra children; the current threat-model note does not stop contract-level execution.

### Proof of Concept
`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` is an executable PoC: `RogueHopPool::swap` calls `token.transfer(victim, attacker, WALLET_BALANCE)`; `simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry` shows Alice's auth tree gains the theft child while her USDC→ETH swap still succeeds, and `enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer` shows signing the simulated tree moves her full unlisted-token balance to the attacker while the swap itself remains valid.
