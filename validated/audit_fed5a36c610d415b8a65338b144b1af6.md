No shop-format validator exists in the library (`lib/shopify_api/**`): the `shop` string is used verbatim to build the OAuth authorize URL and, after HMAC validation, the access-token request host — there's no regex/domain check comparable to `valid_shop?` seen in other Shopify SDKs. This confirms `Auth::Oauth.begin_auth`/`auth_base_uri` and `HttpClient#initialize` trust whatever shop string is supplied, but since the callback's `shop` is itself covered by the HMAC in `AuthQuery#to_signable_string`, this path is bound correctly and isn't independently exploitable without the app's secret. That closes off the OAuth/host-SSRF avenue I was evaluating.

The clearest identity-binding break in this gem is in the webhook verification path.

### Title
Webhook shop/topic identity spoofing via unsigned headers - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used by `Registry.process` to route and attribute the event are read from HTTP headers that are never included in that signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Utils::HmacValidator.validate` computes/compares the HMAC exclusively over that signable string [2](#0-1) . Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers with no cryptographic binding to the HMAC at all [3](#0-2) . `Registry.process` validates only the HMAC, then dispatches `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` straight into `WebhookMetadata` for the host app's handler [4](#0-3) .

The identity binding that should hold is: `bytes_verified_by_HMAC == bytes_the_app_attributes_the_event_to`. Here, `bytes_verified_by_HMAC = raw_body` but `bytes_attributed = raw_body + shop_header + topic_header + webhook_id_header`. Only the body is inside the equality; the shop/topic/id are outside it, breaking the binding the report's bug class targets ("a field acted on but not covered by the HMAC").

### Impact Explanation
Any entity capable of installing the app on their own store (an unprivileged self-service action, no victim credentials needed) will legitimately receive real webhook deliveries with a valid HMAC computed with the app's `client_secret` over a body they fully control the shape of (e.g. an `orders/create` payload from their own store). Because the HMAC never covers the `shopify-shop-domain`/`shopify-topic`/`shopify-webhook-id` headers, that same (body, HMAC) pair can be replayed directly against the app's public webhook endpoint with those headers rewritten to name an arbitrary victim shop domain, topic, or webhook id. `Registry.process` will accept it (`Utils::HmacValidator.validate(request)` only checks the body) and hand the host app's handler data claiming to be from the victim shop. If the host app uses `WebhookMetadata#shop` to key into per-tenant state (session lookup, data writes, redact/GDPR actions, etc.) — which is the documented intended use of this field — this crosses a tenant boundary using only the attacker's own legitimately-issued webhook body/HMAC, i.e. cross-tenant access without the victim's or the app's credentials.

### Likelihood Explanation
High reachability: the webhook endpoint is public HTTP, the attacker only needs one genuine (body, HMAC) pair from their own installation (trivial to obtain by installing any development app), and swapping unsigned headers requires no cryptography. The only friction is that the app must actually key sensitive per-tenant behavior off `request.shop`/`request.topic`, which is the pattern this gem's `WebhookMetadata` API explicitly encourages.

### Recommendation
Extend `Request#to_signable_string` (or add a parallel binding check in `Registry.process`) so the identifying headers actually consumed by handlers — at minimum `shop`, `topic`, and `webhook_id` — are cryptographically bound to the same HMAC that authenticates the body, e.g. by validating the HMAC against `raw_body` plus a canonical, delimiter-safe encoding of those header values, and rejecting the request if that combined HMAC does not match. Short of changing the signature scheme, the gem should at minimum document loudly that `shop`/`topic`/`webhook_id` are unauthenticated and must not be trusted for tenant attribution without an independent cross-check (e.g., confirming the shop has an active session/installation) — but the safer fix is binding them into the verified bytes.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; trigger any subscribed event (e.g. update a product) so Shopify delivers a real webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: products/update`, `x-shopify-hmac-sha256: <valid HMAC of raw_body>`.
2. Capture the exact `raw_body` and `x-shopify-hmac-sha256` value from that delivery.
3. POST directly to the app's public webhook endpoint with the identical `raw_body` and `x-shopify-hmac-sha256`, but replace `x-shopify-shop-domain` with `victim-shop.myshopify.com` (and/or `x-shopify-topic`/`x-shopify-webhook-id` with a different mandatory topic such as `customers/data_request`).
4. `ShopifyAPI::Webhooks::Registry.process` passes HMAC validation (unchanged body/HMAC pair) and invokes the handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, `topic` and `webhook_id` fully attacker-chosen, despite the request never having been authenticated for that shop/topic.
