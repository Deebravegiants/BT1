## Title
Escrow accounting in IntentGatewayV2 (Tron) credits nominal input amounts instead of actually-received token amounts, causing under-collateralized escrow and stuck/frozen withdrawals - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`placeOrder()` in the Tron fork of `IntentGatewayV2` computes the order commitment and credits the `_orders` escrow ledger using the **nominal, requested** input amounts (minus protocol fee), without ever verifying that the contract actually received that amount from the token transfer. The primary EVM contract (`evm/src/apps/IntentGatewayV2.sol`) was explicitly hardened against this exact class of bug — it snapshots balances before/after every transfer and mutates `order.inputs`/the commitment to the *actually received* amount — but this fix is absent from the Tron variant.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder`, the commitment is computed from `reducedInputs`, which is derived purely from `order.inputs[i].amount` (the caller-supplied nominal amount) reduced by the protocol fee: [1](#0-0) 

In the non-predispatch branch, tokens are pulled with `safeTransferFrom` for the nominal amount and the escrow ledger is incremented by the nominal (fee-reduced) amount, with **no balance-before/after check**: [2](#0-1) 

In the predispatch branch, the code only compares the *dispatcher's* pre-sweep balance against `requiredAmount` (the nominal amount) and emits dust only for the excess; it does not verify what the gateway (`address(this)`) actually ends up holding after the sweep `transfer` call, and credits escrow with the nominal `reducedInputs[i].amount` regardless: [3](#0-2) 

This is the same root-cause pattern as the referenced report: a threshold/accounting check is performed against the *intended* amount, while the actual external transfer can deliver less (fee-on-transfer tokens, deflationary/rebasing tokens, or any non-standard ERC20 — a class the protocol explicitly designs for, as shown by the sibling EVM contract's fee-on-transfer test suite), and the resulting on-chain state (the escrow ledger that governs future payouts) is derived from the unproven nominal value rather than the proven actual value.

The sibling, patched implementation in the primary EVM contract shows exactly what is missing here — it measures `balanceOf` before and after every transfer and mutates the order/commitment to the actual received amount before crediting escrow: [4](#0-3) [5](#0-4) 

### Impact Explanation
Because `_orders[commitment][token]` is incremented by the nominal amount while the contract's actual token balance can be strictly less, the aggregate escrow liabilities recorded across all orders for a given token can exceed the contract's real balance of that token. When a solver later fills the order and the `withdraw()` path attempts to pay out the escrowed (nominal) amount: [6](#0-5) 

the low-level `token.call(transfer, beneficiary, amount)` will revert if the contract's real balance can't cover it, permanently freezing that order's withdrawal (and any other order sharing the same token pool once the shortfall is realized) — meeting the "permanent freezing of funds" bar. Alternatively, if the contract holds surplus balance from other unrelated deposits of the same token, an under-collateralized order can still be paid out of that surplus, which is effectively fund commingling/theft between unrelated users' escrows.

### Likelihood Explanation
Any user can trigger this by placing an order (`placeOrder`) whose input token is fee-on-transfer, deflationary, or otherwise delivers less than the requested `transferFrom`/sweep amount — a token class the protocol's own EVM implementation explicitly tests and defends against. No privileged role is required; a single `placeOrder` transaction is sufficient to create an unbacked escrow credit.

### Recommendation
Port the EVM fix to the Tron contract: measure `balanceOf(address(this))` before and after each token pull (and after the predispatch sweep), mutate `order.inputs`/`reducedInputs` to the actually-received amount, recompute/derive the commitment from that actual amount, and only credit `_orders[commitment][token]` with the verified received amount.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 (e.g., 1% fee) as an intent input token on the Tron gateway.
2. Call `placeOrder` with `inputs[0].amount = 1000e18` for that token; the user approves and the contract calls `safeTransferFrom(user, address(this), 1000e18)`, but the gateway's actual balance only increases by `990e18` due to the transfer fee.
3. `_orders[commitment][token]` is nonetheless credited with `reducedInputs[0].amount` derived from `1000e18` (minus protocol fee), i.e., more than the `990e18` actually held.
4. When a solver fills the order and the corresponding `RedeemEscrow`/`RefundEscrow` message triggers `withdraw()`, the contract attempts to transfer out the full recorded escrow amount, exceeding its real token balance — the transfer reverts (`TransferFailed`), permanently freezing that withdrawal, or succeeds by drawing down balance belonging to other users' escrowed orders of the same token.

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
