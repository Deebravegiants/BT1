## Analysis

The Solidity report's bug class is "an identity/state check is enforced somewhere, but a different value is actually acted upon" — i.e., a binding between what's verified and what's used gets broken. Searching `lib/shopify_api/**` (excluding generated REST resources) for the closest analog — "a field acted on but not covered by the HMAC" — leads directly to the webhook processing pipeline. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

`Webhooks::Request#to_signable_string` returns only `@raw_body`, and `HmacValidator.validate` computes/compares the HMAC exclusively over that raw body. `Registry.process` gates entirely on `Utils::HmacValidator.validate(request)`, then hands the handler `request.shop`, which is read straight from the unauthenticated `X-Shopify-Shop-Domain`/`shopify-shop-domain` header — a value never included in the signed bytes.

### Title
Webhook shop identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`Webhooks::Registry.process` authenticates a webhook solely by verifying an HMAC over the raw request body. The `shop` value that the library passes to the app's handler (used to determine which merchant/tenant the webhook belongs to) comes from a plaintext HTTP header that is never part of the signed data. Since a single `api_secret_key` is shared by the app across every installed shop, any unprivileged user who has installed the app on their own shop can capture one legitimately-signed webhook and replay it to the app's public webhook endpoint with the `shop-domain` header rewritten to a victim shop, and the request will still pass HMAC verification.

### Finding Description
`HmacValidator.validate` computes the equality `computed_signature(secret, verifiable_query.to_signable_string) == hmac`. For a webhook `Request`, `to_signable_string` returns just `@raw_body` [2](#0-1) , so the signature only proves "this body was produced with our secret," not "this body/shop pair came from Shopify for shop X." `Request#shop` is derived independently from the `shopify-shop-domain` / `x-shopify-shop-domain` header [1](#0-0) , which is ordinary request metadata with no cryptographic binding to the HMAC at all.

`Registry.process` then trusts this unauthenticated header value directly for tenant identification when dispatching to the app's handler: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [4](#0-3) . The documented usage pattern explicitly relies on this: apps are told that a successful `Registry.process` call means "the request did indeed come from Shopify," and the resulting `WebhookMetadata.shop` is the value host apps scope their side effects to.

Because the same `api_secret_key` signs webhooks for every shop that installs the app, an attacker only needs to install the app on their own store (an ordinary, unprivileged action) to obtain one validly-signed `(raw_body, hmac)` pair. They can then POST that exact body/HMAC pair to the app's public webhook endpoint while substituting any other shop domain in the `shop-domain` header. `HmacValidator.validate` still succeeds (it never looks at the header), and `Registry.process` calls the handler claiming the payload belongs to the victim shop.

### Impact Explanation
This breaks the tenant-isolation guarantee the gem's own documentation promises ("this will verify the request did indeed come from Shopify"): `Registry.process` verifying successfully does not establish which shop the payload is for. A host application that (as documented) trusts `WebhookMetadata#shop` to select which tenant's records to update/delete (e.g., `app/uninstalled`, `shop/update`, `customers/redact`) can be driven to perform cross-tenant actions using an attacker-controlled shop label attached to attacker-supplied body content, which meets the "cross-tenant access" Critical impact bar.

### Likelihood Explanation
Likelihood is Low/Medium: the attacker must operate their own genuine installation of the target app (unprivileged, freely available) to obtain one valid signed body, and must know/guess the webhook endpoint URL (which is typically a fixed, discoverable route). No secrets, tokens, or privileged access are required — only sending a plain HTTP POST with a modified header.

### Recommendation
Bind the shop identity into the authenticated material: either compute/compare the HMAC over `shop-domain + raw_body` (or otherwise incorporate the header into `to_signable_string`), or cross-check `request.shop` against a shop the app has an active session/installation record for before dispatching to handlers, instead of trusting the header verbatim once the body-only HMAC passes.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and registers a webhook (e.g., `orders/create`).
2. Shopify delivers a legitimately HMAC-signed webhook to the app's endpoint:
   ```
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid HMAC of raw_body>
   X-Shopify-Shop-Domain: attacker-shop.myshopify.com
   Body: {...attacker-controlled order payload...}
   ```
3. Attacker replays this exact `raw_body` and `X-Shopify-Hmac-Sha256` to the same public endpoint, only changing:
   ```
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   ```
4. `Utils::HmacValidator.validate` recomputes the HMAC over `raw_body` only, matches, and `Webhooks::Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's payload>, ...)`, causing the host app to act on attacker-controlled data attributed to a shop the attacker does not own.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
