### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, excluding the `shop-domain` header. `HmacValidator.validate` therefore only proves that the body bytes were signed with the app's shared `api_secret_key` — it proves nothing about which shop the webhook claims to be from. Any holder of one validly-signed webhook (obtainable by installing the app on any shop, since the same `api_secret_key` signs webhooks for every tenant of the app) can replay that signed body while substituting an arbitrary `shop-domain` header, and the registry will accept it and dispatch it to the handler as if it came from that other shop.

### Finding Description
`Registry.process` validates the inbound webhook exclusively via HMAC over the body: [1](#0-0) 

The HMAC check itself uses `verifiable_query.to_signable_string`, and for `Webhooks::Request` that method returns only `@raw_body`: [2](#0-1) [3](#0-2) 

The `shop` value read from the (unsigned) `shopify-shop-domain` / `x-shopify-shop-domain` header is then forwarded, unauthenticated, straight into the data handed to the app's webhook handler: [1](#0-0) [4](#0-3) 

The identity binding that should hold is: `hmac-verified bytes == bytes that determine tenant attribution`. Here, the verified bytes are `raw_body` only, while the tenant attribution (`shop`) is read from a header that is not part of `to_signable_string`. Since `api_secret_key` is one value per app shared across every shop that installs the app (not per-tenant), any unprivileged internet user can install the target app on their own shop, receive a legitimately HMAC-signed webhook for their own tenant, and then replay that exact signed body to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` still returns `true` because it only checks the body against the shared secret; the forged `shop` value passes through to `WebhookMetadata.shop` untouched, per the documented handler contract: [5](#0-4) 

### Impact Explanation
This breaks the tenant/identity boundary the HMAC is supposed to enforce and lets an attacker who is merely an installer of the app (an unprivileged, un-vetted action) inject attacker-chosen webhook bodies attributed to an arbitrary victim shop into the app's own webhook processing pipeline. Depending on how the host app's handler uses `data.shop` (e.g., to look up which merchant's data/session/queue to update), this is a cross-tenant data-integrity/consumption issue — the host application has no way, using this gem's API, to detect the forgery, because the gem itself does not bind `shop` to the signature.

### Likelihood Explanation
High likelihood: any user can install a public app on their own store for free, capture one real webhook (topic/body/hmac), and replay it against the app's webhook endpoint with a different `shop-domain` header. No secrets, tokens, or privileged access are required — only the ability to become an app installer, which is the baseline unprivileged capability for any Shopify app.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, or otherwise cryptographically tie the claimed shop to the verified payload (e.g., compare `request.shop` against the shop recorded when the webhook subscription for `webhook_id`/`topic` was created via the Admin API, or require host apps to independently confirm shop identity before trusting `data.shop`). At minimum, `Request#to_signable_string` should not be the sole basis for trusting `Request#shop`, and this limitation should be explicitly documented so host apps do not treat `WebhookMetadata#shop` as authenticated.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`. Shopify sends a legitimate webhook, e.g. for `orders/create`, with body `{"id":1}` and header `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>` and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Capture the raw body and the `hmac-sha256` header value.
3. Send a new POST to the app's webhook endpoint with the same body/topic/hmac, but with header `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` builds a `Request` from these headers/body; `HmacValidator.validate` succeeds because it only hashes `raw_body`, per: [6](#0-5) 
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and `body: {"id":1}`, processing attacker-supplied data as if it originated from the victim tenant.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
