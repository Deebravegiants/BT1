### Title
`Webhooks::Request#shop` is read from an unauthenticated header and never bound to the HMAC-verified payload - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`Webhooks::Registry.process` verifies only the HMAC over the raw request body (`request.to_signable_string` → `@raw_body`) and then builds `WebhookMetadata` using `request.shop`, `request.topic`, and `request.webhook_id`, all of which are read straight from HTTP headers that are never included in the signed bytes. Because the app's `api_secret_key` is shared across every shop that installs the app, an attacker who installs the app on their own development store can capture one genuinely-signed `(body, hmac)` pair and replay it to the same endpoint with a forged `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header naming a victim shop, and the gem will accept it as valid.

### Finding Description
The claimed binding is: `WebhookMetadata#shop == the shop that produced/authorized the HMAC-signed bytes`. Tracing the code shows this equality never holds, independent of any JSON duplicate-key trick:

- `Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) .
- `Webhooks::Request#shop` reads `shopify_header("shop-domain")` directly — a raw header value, never derived from the body or from `parsed_body` [2](#0-1) .
- `HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` header — it never touches `shop`, `topic`, or `webhook_id` headers [3](#0-2) .
- `Registry.process` trusts the HMAC check alone, then forwards `request.shop`, `request.topic`, and `request.webhook_id` verbatim into `WebhookMetadata`, which the host app uses to decide whose tenant record to touch [4](#0-3) .
- `WebhookMetadata` is a plain `T::Struct` with no cross-check between `shop`/`topic` and the signed body content [5](#0-4) .

Note: the specific "duplicate JSON key" mechanism from the question does not actually apply here — `shop` is read from `shopify_header("shop-domain")`, not from `parsed_body`, so a repeated key inside the JSON body has zero effect on which shop value is delivered to the handler. The real defect is broader and doesn't need JSON trickery at all: since `shop` (and `topic`) headers are outside the HMAC's signed byte range, they are fully attacker-controllable on any request that carries a validly-signed body. Because `api_secret_key` is shared by the app across all installing shops (not per-shop), an attacker with their own dev-store install can obtain one legitimately-signed `(body, hmac)` pair from Shopify, then POST that same body+hmac to the app's webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header. `HmacValidator.validate` still passes because the bytes it hashes are unchanged; `WebhookMetadata#shop` becomes the forged value, so the host app processes attacker-supplied body content under an arbitrary victim shop identity — violating the "single identity" invariant (the shop used for authorization and the shop bound to the signed bytes are different values).

None of the existing guards catch this: `HmacValidator.validate` only checks body bytes; there is no `ShopValidator.sanitize!` or equivalent applied to the webhook `shop` header; `JwtPayload`/OAuth's `aud`/`state` checks are unrelated to the webhook code path; Sorbet's `sig { returns(String) }` on `shop` only enforces type, not provenance.

### Impact Explanation
The host app derives which merchant's records to create/update/delete purely from `WebhookMetadata#shop`, an unauthenticated header. An attacker can make an app process attacker-chosen webhook payloads (e.g., fake `orders/create`, `app/uninstalled`, `shop/redact`) as if they belonged to any victim shop known to have installed the app, causing cross-tenant data corruption or triggering privileged data-handling logic (e.g., GDPR redaction, app uninstall cleanup) against a shop the attacker does not control. This matches "cross-tenant access," a Critical-class impact under the stated rubric.

### Likelihood Explanation
The attacker needs only: (1) their own development shop with the target app installed (freely obtainable, matches the stated attacker capability), (2) the ability to receive at least one webhook delivery from Shopify to capture a valid `(body, hmac)` pair, and (3) the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with custom headers — all explicitly permitted attacker capabilities. No secret material is needed since the signature is reused unmodified. This is fully repeatable against any shop identifier the attacker chooses to put in the header.

### Recommendation
Bind `shop`/`topic`/`webhook_id` into the signed material (or otherwise cryptographically verify them), e.g., include the relevant headers in the HMAC computation, or require the host app to independently confirm `request.shop` against a known/authorized session/shop record before dispatching to a handler. At minimum, document that `WebhookMetadata#shop` is unauthenticated and instruct implementers to cross-check it against their own installed-shop registry before trusting it for tenant-scoped operations.

### Proof of Concept
```ruby
# test/webhooks/registry_shop_spoof_test.rb
require_relative "../test_helper"

class RegistryShopSpoofTest < Test::Unit::TestCase
  def setup
    super
    ShopifyAPI::Webhooks::Registry.clear
    @captured = nil
    handler = Class.new do
      include ShopifyAPI::Webhooks::WebhookHandler
      def self.handle(data:)
        @@last = data
      end
      def self.last
        @@last
      end
    end
    @handler = handler
    ShopifyAPI::Webhooks::Registry.add_registration(
      topic: "orders/create", delivery_method: :http, path: "/webhooks", handler: handler,
    )
  end

  def test_shop_header_is_not_covered_by_hmac
    raw_body = '{"id":1,"note":"attacker-controlled"}'
    hmac = OpenSSL::HMAC.base64digest(
      OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body,
    )

    request = ShopifyAPI::Webhooks::Request.new(
      raw_body: raw_body,
      headers: {
        "X-Shopify-Topic" => "orders/create",
        "X-Shopify-Hmac-Sha256" => hmac,
        "X-Shopify-Shop-Domain" => "victim-shop.myshopify.com", # forged, attacker's real shop is different
        "X-Shopify-Api-Version" => "2023-01",
        "X-Shopify-Webhook-Id" => "1",
      },
    )

    assert(ShopifyAPI::Utils::HmacValidator.validate(request)) # passes: hmac only covers raw_body

    ShopifyAPI::Webhooks::Registry.process(request)

    assert_equal("victim-shop.myshopify.com", @handler.last.shop) # unauthenticated value reached the handler
  end
end
```
This demonstrates that a request whose `X-Shopify-Shop-Domain` header names an arbitrary shop still passes `HmacValidator.validate` and is dispatched with that forged shop identity in `WebhookMetadata`, confirming the header is outside the HMAC-verified byte range.
