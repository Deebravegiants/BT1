## Title
Webhook `shop` field is trusted by host apps but not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` attribute that is read directly from the unauthenticated `x-shopify-shop-domain` HTTP header, while the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` validates only covers the raw request body. Because the same `api_secret_key` is shared by every merchant installation of an app, an attacker who controls one shop (their own low-privilege installation) can obtain a validly-signed webhook body and then submit that body to the app's webhook endpoint with an arbitrary `shop-domain` header, causing the host application to process/store the payload under a victim tenant's identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is parsed straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never included in the signed material: [2](#0-1) 

`Registry.process` validates only that HMAC (i.e., only the body), and then forwards `request.shop` unchanged to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the HMAC using `verifiable_query.to_signable_string` (the body only) and `Context.api_secret_key`, which is identical for every shop that has installed the app: [4](#0-3) 

The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify," and shows the handler trusting `data.shop` to route/store the payload (`shop_domain: data.shop`): [5](#0-4) [6](#0-5) 

The identity binding broken is: `shop` used by the handler for tenant attribution ≠ `shop` actually authenticated by the HMAC (which authenticates only the byte content of the body, not its origin shop). Since the signing secret (`client_secret`) is shared across all shops on the app, `HMAC(body, secret)` is identical regardless of which shop produced that body. An attacker who is a legitimate merchant on their own store can:
1. Cause a webhook to fire for their own shop with attacker-chosen body content (e.g., via an app proxy/product update that lands in the body, or via any topic where body content is attacker-influenced).
2. Capture the valid `x-shopify-hmac-sha256` value Shopify computed for that body.
3. Replay the identical body + HMAC directly to the app's public webhook endpoint, but with the `x-shopify-shop-domain` header set to a victim shop domain.
4. `HmacValidator.validate` succeeds (body+secret match), `Registry.process` calls the handler with `WebhookMetadata.shop` set to the victim's domain, and the host application processes/stores attacker data under the victim tenant.

### Impact Explanation
This breaks the tenant boundary the gem is documented to enforce ("verify the request did indeed come from Shopify"), letting one merchant inject data attributed to another merchant's shop into any app that stores or acts on `data.shop` from webhook payloads (as documented and recommended by this gem). This is a cross-tenant access/data-integrity issue in a multi-tenant SaaS app built on this gem — matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Exploitation requires only that the attacker be a merchant able to install the app or otherwise trigger a webhook body of their choosing on their own store, and the ability to POST directly to the app's public webhook URL (which is, by design, a public unauthenticated HTTP endpoint) — no access token or `client_secret` is needed. This is a realistic capability for an "unprivileged internet user" who has installed the target app on any shop.

### Recommendation
Bind the `shop` (and other routing-relevant metadata like `topic`/`webhook_id`) into the HMAC-signed material, or otherwise cryptographically bind the shop-domain header to the signed body (e.g., include it in the canonical string that is signed) so that `HmacValidator.validate` fails if the shop header has been altered relative to what Shopify actually signed for. At minimum, document loudly that `data.shop` in `WebhookMetadata` is not authenticated by the HMAC and must be cross-checked against a shop known to have an active, valid installation before being trusted for tenant-scoped writes.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker.myshopify.com` (a shop they control) and registers/receives a webhook whose body they can influence (e.g., a topic where they control the resource content).
2. Attacker captures the raw POST body `B` and the corresponding `x-shopify-hmac-sha256` header value `H` that Shopify sent for `attacker.myshopify.com`.
3. Attacker sends a new POST request directly to the app's webhook route with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256`: `H` (unchanged)
   - Header `x-shopify-shop-domain`: `victim.myshopify.com` (forged)
   - Header `x-shopify-topic`: unchanged
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(B, api_secret_key) == H`, both of which are unchanged.
5. The host application's handler receives `WebhookMetadata` with `shop == "victim.myshopify.com"` and processes/stores attacker-supplied data `B` as if it originated from the victim shop.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
