Audit Report

## Title
Reward accrual decoupled from actual pool funding can cause `harvest_rewards` to permanently revert for unprivileged stakers - (File: `substrate/frame/asset-rewards/src/lib.rs`)

## Summary
`pallet-asset-rewards` computes staker rewards just-in-time (`reward_rate_per_block × elapsed_blocks`) via `update_pool_and_staker_rewards`, with no on-chain check that the pool account actually holds enough of the reward asset to cover accrued amounts before `harvest_rewards` attempts to pay out. This confirmed lack of an invariant means an underfunded pool causes `T::Assets::transfer` to fail and the extrinsic to revert, blocking legitimate stakers from claiming rewards.

## Finding Description
`harvest_rewards` at [1](#0-0)  computes `staker_info.rewards` from `update_pool_and_staker_rewards` and then unconditionally calls `T::Assets::transfer(pool_info.reward_asset_id, &pool_info.account, &staker, staker_info.rewards, Preservation::Expendable)?`. There is no balance check against the pool account's actual reward-asset holdings prior to this transfer.

Funding of the pool account is a separate, optional step performed via `deposit_reward_tokens`, confirmed at [2](#0-1) , which simply transfers whatever `amount` the caller specifies into the pool account — it performs no reconciliation with the reward rate, expiry, or number of stakers, and does not enforce that the deposited amount covers the full remaining accrual runway. The module doc explicitly warns of this at [3](#0-2) , confirming this is a known, unmitigated operational hazard in the code as written, not something structurally prevented.

Rate increases via `set_pool_reward_rate_per_block` at [4](#0-3)  similarly do not require a corresponding balance top-up, so accrual can be raised without any funding guarantee.

Unlike `pallet-nomination-pools`, whose reward accounting derives claimable amounts directly from the reward account's actual current balance (as cited in the report), `pallet-asset-rewards` has no equivalent invariant. This is a genuine root-cause gap: accrual state (`staker_info.rewards`) and actual token balance in `pool_info.account` are two independently-evolving quantities with no reconciliation until transfer time.

## Impact Explanation
If accrued rewards exceed the pool account's actual reward-asset balance (e.g., admin sets a high rate but under-funds the runway, or multiple stakers accrue faster than top-ups, or an earlier harvester drains the account), a later staker's `harvest_rewards` call reverts due to the failed `T::Assets::transfer`. This is a denial-of-service on reward claims affecting unprivileged, legitimate stakers through the normal `harvest_rewards` extrinsic path — no privileged action or attacker exploit is required beyond ordinary usage patterns. Because state mutations occur only after the transfer succeeds, this is not a fund-loss bug; the extrinsic reverts atomically and the staker's accrued reward entitlement is preserved in storage for a later, successful harvest attempt once the pool is topped up. The impact is therefore a temporary availability/griefing issue for reward claims, not fund loss or insolvency.

## Likelihood Explanation
This can occur under realistic, non-malicious operating conditions: a pool admin sets a reward rate and funds the pool with less than what is needed to cover the full remaining runway across all stakers, which the code does not prevent. This matches a plausible operational misconfiguration rather than requiring privilege escalation or attacker action against the protocol itself.

## Recommendation
Tie reward payout to the pool account's actual current reward-asset balance — e.g., cap the transferable amount at `min(accrued, pool_balance)`, track any shortfall as a deficit to be settled on the staker's next successful harvest, or require `deposit_reward_tokens`/rate-setting extrinsics to enforce that the funded balance covers the projected runway. This avoids hard-reverting `harvest_rewards` for stakers whose rewards have legitimately accrued but temporarily exceed the pool's current balance.

## Proof of Concept
1. Admin calls `create_pool` with `reward_rate_per_block = R` and a distant `expiry`.
2. Admin calls `deposit_reward_tokens` (`substrate/frame/asset-rewards/src/lib.rs:673`) with an amount smaller than `R × (expiry - now)`.
3. Staker A stakes; time passes; `update_pool_and_staker_rewards` accrues rewards based on `R × elapsed`.
4. Staker A calls `harvest_rewards` (`substrate/frame/asset-rewards/src/lib.rs:569`); once accrued rewards across stakers exceed the pool account's actual reward-asset balance, `T::Assets::transfer` at line 588 fails and the call reverts, blocking the staker from claiming their accrued reward until the pool is topped up.

A unit test could be added to `substrate/frame/asset-rewards/src/tests.rs` that creates a pool, deposits an insufficient amount relative to the rate/expiry, advances blocks, and asserts `harvest_rewards` returns an error rather than succeeding, confirming this DoS condition is reproducible.
