### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the `X-Shopify-Shop-Domain` HTTP header, while the HMAC signature used to authenticate the webhook is computed only over the raw request body. The `shop` field is never included in `to_signable_string`, so it is not bound by the signature that `Utils::HmacValidator` checks.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Request#shop` reads the tenant identity purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header [2](#0-1) . `Utils::HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest` over `verifiable_query.to_signable_string` and compares it against `verifiable_query.hmac` [3](#0-2) . Because `to_signable_string` never includes the shop-domain header, the equality the gem actually proves is:

`HMAC(client_secret, raw_body) == received_hmac`

but the equality the host application needs (and that this gem's `shop` accessor implicitly claims to provide) is:

`shop_that_signed_the_body == shop_reported_by_Request#shop`

These are not the same binding. A webhook whose body and HMAC were legitimately generated by Shopify for tenant A's shop can be replayed with the `X-Shopify-Shop-Domain` header rewritten to tenant B's shop domain, and `HmacValidator.validate` will still return `true`, while `Request#shop` will report tenant B. Note that the gem's own `AuthQuery` for the OAuth callback does the correct thing by comparison — it explicitly includes `shop` in `to_signable_string` [4](#0-3)  so the OAuth `shop` is bound to the HMAC. The webhook `Request` class breaks this same pattern by omitting `shop` (and `topic`) from the signed material entirely.

### Impact Explanation
Any application built on this gem that trusts `ShopifyAPI::Webhooks::Request#shop` (after `HmacValidator.validate` passes) to select which merchant/tenant record a webhook payload applies to is exposed to cross-tenant data confusion: an attacker who controls or has intercepted one legitimately-signed webhook (e.g., from their own installed shop) can resubmit it with a forged `shop-domain` header pointing at a victim tenant, and the gem will report it as authentic and originating from the victim shop. This matches the Critical "cross-tenant access" impact category, since the identity binding that the app relies on for tenant isolation is not actually enforced by this gem.

### Likelihood Explanation
Exploitation requires the attacker to control the raw HTTP request delivered to the host application's webhook endpoint (headers and body), which is generally true for any unprivileged internet user who can POST directly to the app's public webhook URL — they don't need `api_secret_key`, a leaked token, or TLS interception. They do need one previously-observed valid `(raw_body, hmac)` pair (e.g., from their own shop's traffic, which any app developer/tester naturally has), then only the header is altered. This is a realistic, low-effort attack path entirely within the boundary of "unprivileged internet user."

### Recommendation
Bind the shop identity into the verified material for webhook requests: either include the `shop-domain` (and ideally `topic`/`webhook-id`) header value in `to_signable_string`, or independently validate that the shop domain reported in the header matches shop-identifying data contained within the verified `raw_body` payload, before trusting `Request#shop` for tenant routing. At minimum, document prominently that `Request#shop` is unauthenticated and must not be used for tenant identification without additional verification.

### Proof of Concept
1. Attacker owns/operates `attacker-shop.myshopify.com`, which has the target app installed, and receives a legitimate webhook `POST` with body `B` and header `X-Shopify-Hmac-SHA256: H` where `H = HMAC_SHA256(client_secret, B)`.
2. Attacker resends this exact request to the app's webhook endpoint, changing only the header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com` to `X-Shopify-Shop-Domain: victim-shop.myshopify.com`, leaving body `B` and `H` untouched.
3. The host app calls `ShopifyAPI::Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`= B`) and compares it to `H` — validation succeeds [5](#0-4) .
4. The host app then calls `request.shop`, which returns `"victim-shop.myshopify.com"` taken straight from the forged header [2](#0-1) , causing the app to process attacker-controlled webhook content as if it belongs to the victim tenant.
