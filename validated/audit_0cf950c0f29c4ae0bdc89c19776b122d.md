### Title
Webhook `shop`/`topic` headers are not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook-id`, and `api-version` are all pulled from unauthenticated HTTP headers. `Webhooks::Registry.process` validates the HMAC over the body only, then trusts `request.topic` (to select the handler) and `request.shop` (to attribute the event to a tenant) straight from those headers.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

and `shop`/`topic` are read directly from headers with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` validates only the body via `HmacValidator.validate`, and then dispatches strictly using the unauthenticated `request.topic` header, forwarding the unauthenticated `request.shop` header as the tenant identity to the handler: [3](#0-2) 

`HmacValidator.validate` in turn only ever hashes `verifiable_query.to_signable_string`, i.e., the raw body — never the headers: [4](#0-3) 

The identity binding that should hold is: `hmac_valid(shop_header, topic_header, body) == true` implies `(shop_header, topic_header)` were the values Shopify actually attached when generating that HMAC. In this implementation that equality does not hold — the HMAC only binds `body`, so `(shop_header, topic_header)` can be swapped by anyone who possesses one valid `(body, hmac)` pair without invalidating the signature check.

This mirrors the audited bug class ("field acted on but not covered by the signature check"): the `Twav._getTwav()` bug used `timestamp` (a value that could be zero/misleading) in an `if` guard instead of the always-reliable `cumulativeValuation`; here, `Registry.process` uses attacker-controlled headers (`shop`, `topic`) to make trust/routing decisions instead of restricting itself to data actually covered by the verified signature.

### Impact Explanation
Any shop that has installed the app (and therefore legitimately receives real webhook deliveries signed with the app's single, app-wide `api_secret_key`) can capture one valid `(raw_body, hmac)` pair from its own webhook traffic, then replay that exact body+HMAC to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain and the `X-Shopify-Topic` header with any topic the app has registered a handler for. Because `HmacValidator.validate` never inspects these headers, the forged request passes verification (`InvalidWebhookError` is not raised), and `Registry.process` invokes the victim-topic's handler with `shop: <victim-shop>` — i.e., cross-tenant event injection using data the attacker fully controls in terms of routing/attribution, even though the body content itself came from a signature the attacker legitimately obtained. This satisfies the "cross-tenant access" high/critical impact criterion since a merchant boundary is crossed purely by header manipulation.

### Likelihood Explanation
Any merchant who installs the app receives real webhook payloads carrying a genuine `hmac-sha256` computed with the app's `api_secret_key` (shared across all installs of that app, not per shop). Capturing at least one such pair only requires normal, unprivileged use of the app as a legitimate customer — no leaked secrets, tokens, or elevated access are required. The forged replay is a single crafted HTTP POST to the app's public webhook route with modified headers.

### Recommendation
Include the values the application relies on for routing/attribution — at minimum `shop` and `topic` (and ideally `webhook-id`) — in the signed payload used for HMAC verification, or otherwise cryptographically bind them (e.g., re-derive/verify shop and topic from a signed envelope rather than raw headers) before they are used in `Registry.process`. If per-header binding cannot be added because the wire format is fixed by Shopify, downstream applications must be required to independently confirm that `request.shop` corresponds to a shop that actually has an active subscription for `request.topic` before trusting the payload — this check does not currently exist in `Registry.process`.

### Proof of Concept
1. Install the app on shop A; receive a genuine webhook, e.g. `orders/create` with raw body `B` and header `x-shopify-hmac-sha256: H` (valid for `H = HMAC(api_secret_key, B)`).
2. Replay a request to the app's webhook endpoint with the same raw body `B` and header `x-shopify-hmac-sha256: H`, but set:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: app/uninstalled` (or any topic registered by the app)
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which recomputes HMAC over `B` only and matches `H`, so validation succeeds: [5](#0-4) 
4. The registered handler for `app/uninstalled` is invoked with `shop: "victim-shop.myshopify.com"`, even though the victim shop never sent this webhook.
