### Title
Webhook shop-domain identity spoofing via unauthenticated header not covered by HMAC - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook by checking only the HMAC of the raw request body, but the `shop` field that is handed to the app's webhook handler is read directly from the `X-Shopify-Shop-Domain` header, which is never included in the signed content. This breaks the identity binding `hmac_covers(shop) == true` that a webhook consumer is entitled to assume from the library's documented guarantee ("this will verify the request did indeed come from Shopify").

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes/compares the HMAC exclusively over `verifiable_query.to_signable_string` using the app's single, shop-agnostic `Context.api_secret_key`: [2](#0-1) 

`Registry.process` treats a passing HMAC check as full proof of an authentic, correctly-attributed Shopify webhook, then immediately forwards `request.shop` — which is read straight from the unauthenticated `x-shopify-shop-domain` header — into `WebhookMetadata`, the struct the documented handler API is built around: [3](#0-2) [4](#0-3) [5](#0-4) 

Because `api_secret_key` is a single per-app secret shared across every merchant/tenant using the app (not a per-shop key), any legitimate, unprivileged merchant who has installed the app can obtain a validly-signed webhook body+HMAC pair for their own shop (e.g., by triggering `orders/create` on their own store). That merchant can then replay the exact same body and HMAC to the app's webhook endpoint while substituting an arbitrary value for the `X-Shopify-Shop-Domain` header. `HmacValidator.validate` will still succeed, because it only re-computes the HMAC over the raw body — which the attacker did not alter — and never incorporates the shop header into the signable string. `Registry.process` then calls the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain, even though the payload never actually originated for that shop.

This is exactly the class of bug the report describes for the analogous system: an identity/binding attribute (there: validator core-set membership; here: which tenant a signed message belongs to) is not actually enforced by the mechanism that is supposed to guarantee it, so an actor holding only a small, legitimately-obtained credential (a single shop's own webhook secret exposure) can impersonate a much larger scope (any other tenant) that the verification was believed to cover.

### Impact Explanation
Any handler written against the documented contract ("`process` will verify the request did indeed come from Shopify") and that uses `data.shop` to select which tenant record to create/update/delete (the officially recommended pattern, since `WebhookMetadata#shop` is the only tenant identifier exposed) can be tricked into writing attacker-supplied webhook body content against a victim shop's data. This is a cross-tenant data injection/corruption primitive reachable by any unprivileged existing merchant of the app, satisfying the "cross-tenant access" Critical-impact category, since the attacker crosses a tenant boundary using only credentials they already legitimately hold for their own tenant.

### Likelihood Explanation
Likelihood is high for any app that installs the gem's documented webhook flow as-is: no access token, `client_secret`, or privileged access is required — only the ability to be an installed merchant of the target app (or otherwise obtain one valid signed webhook/HMAC pair for the shared app secret) and the ability to POST to the app's public webhook endpoint with modified headers, both of which are available to an ordinary internet-reachable actor interacting with the app's webhook route.

### Recommendation
Include the shop domain (and other identity-relevant headers such as `webhook_id`/`api_version` if used for authorization decisions) in the signable string that is HMAC-verified, or independently verify that `request.shop` corresponds to a shop for which the app holds an active installation/session before dispatching to the handler. At minimum, document prominently that `WebhookMetadata#shop` is *not* authenticated by `Registry.process` and must be independently validated by consuming applications against their own installed-shop records before being trusted for tenant-scoped actions.

### Proof of Concept
```ruby
# Attacker is a legitimate merchant of the app, "attacker-shop.myshopify.com".
# Shopify sends a real, validly-signed webhook to the attacker's own endpoint:
raw_body = '{"id":1,"note":"pwned"}'
real_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# Attacker replays the SAME body + SAME hmac, but swaps the shop-domain header
# to a victim shop that also uses the same app:
forged_headers = {
  "x-shopify-topic"        => "orders/create",
  "x-shopify-hmac-sha256"  => Base64.encode64(real_hmac), # unchanged, still valid
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com", # attacker-controlled, unsigned
  "x-shopify-webhook-id"   => "any-id",
  "x-shopify-api-version"  => "2024-01",
}

forged_request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# HMAC validation succeeds (body unchanged), and the handler receives
# WebhookMetadata#shop == "victim-shop.myshopify.com":
ShopifyAPI::Webhooks::Registry.process(forged_request)
```
Because `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) never inspects `shop-domain`, this call does not raise `Errors::InvalidWebhookError`, and the handler is invoked believing the (attacker-authored) body legitimately belongs to `victim-shop.myshopify.com`.
