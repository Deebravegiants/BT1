### Title
Webhook `shop`, `topic`, and `webhook-id` fields are not covered by HMAC verification, enabling cross-tenant webhook spoofing — (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then dispatches the handler using the `shop`, `topic`, and `webhook_id` values taken directly from unauthenticated HTTP headers. Because those tenant-identifying fields are never included in the signed payload, any party who can obtain one validly-signed webhook body (e.g., by triggering a webhook on their own, attacker-controlled shop where the app is installed) can replay that body to the app's public webhook endpoint while forging the `x-shopify-shop-domain` header to impersonate a different, victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and the HMAC verification performed in `Registry.process` validates only this signable string: [2](#0-1) 

However, `Request#shop`, `#topic`, and `#webhook_id` are all read straight from attacker-suppliable HTTP headers with no cryptographic binding to the HMAC-covered bytes: [3](#0-2) 

`Registry.process` then forwards these unauthenticated values directly to the app's webhook handler as the authoritative tenant identity for the request: [4](#0-3) 

The `client_secret` used to sign webhooks (`Context.api_secret_key`) is the app's single shared credential — every shop that installs the app has its webhooks signed with the *same* secret. Consequently:
- **Before the attack**: the equality the app relies on is `hmac(raw_body, api_secret_key) == received_hmac` combined with an implicit but unenforced assumption that `request.shop == the tenant whose real webhook produced that body/hmac pair`.
- **The attack**: an unprivileged user who installs the app on their own (attacker-controlled) shop can capture a genuine, validly-signed webhook body+HMAC pair sent by Shopify to the app's endpoint (they own the shop, so they can trigger any webhook topic they like, e.g. `app/uninstalled`, `shop/redact`, `customers/data_request`). They then POST that exact `(raw_body, x-shopify-hmac-sha256)` pair to the app's public webhook URL again, but with `x-shopify-shop-domain`, `x-shopify-topic`, and `x-shopify-webhook-id` headers changed to identify a victim shop.
- **After the attack**: `Utils::HmacValidator.validate` still succeeds (it only checks `raw_body` against the secret), and the handler executes business logic (e.g., data purge, uninstall cleanup, session revocation) attributed to the victim shop — a full break of the shop-identity binding that the HMAC was supposed to enforce.

This is exactly the pattern described in the prompt as an accepted analog: "a field acted on but not covered by the HMAC."

### Impact Explanation
This allows any unprivileged internet user who can install the app on a shop they control (a normal, unprivileged action) to make the app act on behalf of an arbitrary victim tenant for any registered webhook topic, without ever obtaining `api_secret_key` or an access token. Depending on the app's handlers, this enables cross-tenant actions such as forcing `app/uninstalled` cleanup, GDPR `shop/redact`/`customers/redact` data deletion, or other tenant-scoped state changes attributed to a shop the attacker does not own — a cross-tenant access impact.

### Likelihood Explanation
Likelihood is high for any app that: (a) is installable by the public (standard Shopify app model), and (b) has a publicly reachable webhook endpoint (required by design). The attacker only needs to install the app on their own store to obtain a genuinely-signed body/HMAC pair and can then freely vary the identifying headers, since nothing in `Request` or `Registry.process` binds `shop`/`topic`/`webhook_id` to the signed bytes.

### Recommendation
Bind the tenant-identifying fields to the HMAC verification, e.g., include `shop`, `topic`, and `webhook_id` in the signable string (or otherwise cryptographically bind them), or cross-check the asserted `shop` header against a shop known to be associated with the specific `webhook_id`/subscription before dispatching to handlers.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook topic on their own shop (e.g., updates an order), causing Shopify to POST a validly-signed payload `(body_A, hmac_A)` to the app's `/webhook` endpoint.
3. Attacker captures `body_A` and `hmac_A` (they control the network path to their own app's endpoint, or can simply reuse a webhook replay tool).
4. Attacker sends a new POST to the same public endpoint with:
   - Body: `body_A`
   - Header `x-shopify-hmac-sha256`: `hmac_A` (unchanged, still valid since only body is signed)
   - Header `x-shopify-shop-domain`: `victim-shop.myshopify.com`
   - Header `x-shopify-topic`: any registered topic
5. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` because only `raw_body` is checked.
6. `ShopifyAPI::Webhooks::Registry.process` invokes the handler with `shop: "victim-shop.myshopify.com"`, causing the app to perform tenant-scoped actions against the victim shop that were never authorized by Shopify or the victim.
