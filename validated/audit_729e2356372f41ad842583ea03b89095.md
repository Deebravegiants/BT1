### Title
Order placer can hold a solver's signed bid indefinitely and execute it once price moves favorably, extracting risk-free value from the solver on gateways predating `FillOptions.validUntil` - ([File: evm/src/apps/IntentGatewayV2.sol / sdk/packages/sdk/src/protocols/intents/fillOrderCodec.ts])

### Summary
The `updateTp()`/`updateSl()` bug class describes a party that can hold a pending, price-committed action open until market conditions turn favorable and only then trigger settlement at the originally-committed (now stale) price, extracting risk-free value from the counterparty. In Hyperbridge's `IntentGatewayV2` coprocessor-bidding flow, the analogous role is played by the order placer versus the solver: a solver signs a `fillOrder` UserOperation with fixed output amounts (its quoted price), and the *comment trail in the codebase itself* documents that, absent a bound, "the order's `deadline` is chosen by the placer with no ceiling... the placer holds the session key... a signed bid stayed executable indefinitely and was taken up only once the rate had moved against the solver" [1](#0-0) .

### Finding Description
`fillOrder` is called with an `Order` (placer-controlled, including `order.deadline` with no upper bound) and `FillOptions` containing the solver's fixed output amounts [2](#0-1) . In the coprocessor-bidding flow, a solver signs a `PackedUserOperation` embedding a `fillOrder` call at a quoted price and submits it as a public bid on Hyperbridge's `pallet-intents-coprocessor` [3](#0-2) . The order placer (who controls the session key) decides when to execute the selected bid via `select()` + `fillOrder()` — the codebase acknowledges this is "the placer holds the session key, so without a bound here they may sit on a signed bid and execute it whenever the price has moved in their favour" [4](#0-3) .

The protocol mitigated this with `FillOptions.validUntil`, enforced by `fillOrder`: `if (options.validUntil != 0 && blockNumber > options.validUntil) revert FillExpired();` [5](#0-4) . However, this bound is **not enforced on gateways predating the field** — a v1 `fillOrder(Order, FillOptions)` shape exists with no `validUntil` member at all, and the SDK explicitly documents: "On a v1 gateway `validUntil` is dropped — there is nowhere to put it and no check on the other side. That is a real loss of protection" [6](#0-5) . The indexer/simplex test comments confirm this is not a hypothetical: "every mainnet gateway still predates `validUntil`, so this is the shape actually on the wire today" [7](#0-6) , and `CHAINS_WITHOUT_VALID_UNTIL` lists multiple live chains still running the legacy implementation [8](#0-7) . Simplex's own filler warns operators at runtime: "IntentGateway predates FillOptions.validUntil — bids on this chain carry no expiry and stay executable until the order's own deadline" [9](#0-8) .

Root cause: on these legacy-implementation gateways, a solver's signed bid (fixed output price) remains valid for execution at any block up to the placer-chosen, unbounded `order.deadline`, and the placer alone decides the execution moment. This mirrors the reported bug class exactly: the party in control of triggering execution (the trader in the original report; the order placer here) can wait until the market has moved in their favor before finalizing a price-committed action, at the counterparty's (solver's) expense.

### Impact Explanation
An order placer on any chain still running the legacy `IntentGatewayV2` implementation can obtain a solver's signed quote for a favorable swap and simply not execute it until the reference market price moves further in the placer's favor, then submit `select()` + `fillOrder()` to force the solver to deliver the stale, now-unprofitable quote. This directly transfers value from solvers (unbacked economic loss on every stale fill) and is a form of the exact "risk-free trade" pattern in the source report, since the placer bears none of the market risk a normal quote-then-fill window would impose. Because affected chains are explicitly enumerated and acknowledged as still live (`CHAINS_WITHOUT_VALID_UNTIL`), the exposure is concrete, not theoretical.

### Likelihood Explanation
Likelihood is high on any affected chain: exploiting it requires only that a placer solicit a bid through the normal, permissionless coprocessor bidding flow (any unprivileged order-placer transaction) and delay calling `fillOrder` until conditions are favorable — no special privileges, collusion, or off-chain infrastructure beyond price monitoring are needed. The vulnerability is self-acknowledged in the codebase's changelog/decision docs as the exact issue `validUntil` was created to close, and it remains unclosed wherever the legacy implementation is still deployed.

### Recommendation
Complete the rollout of `FillOptions.validUntil` to every remaining `IntentGatewayV2` deployment (all chains currently listed in `CHAINS_WITHOUT_VALID_UNTIL` and any proxy still pointing at the legacy implementation `0x976b268b06f545c4a2bf44866aa2465bd8b3c67d`) so that `fillOrder` uniformly reverts once a solver-signed quote goes stale, removing the placer's ability to indefinitely hold and later force execution of a favorable-but-stale quote. Until upgraded, solvers should treat bids on those chains as carrying no expiry protection and price in the corresponding staleness risk, or refuse to bid through the coprocessor on unupgraded gateways.

### Proof of Concept
1. Solver observes an `OrderPlaced` event on a chain still running the pre-`validUntil` gateway (member of `CHAINS_WITHOUT_VALID_UNTIL` or delegating to `0x976b...c67d`) [10](#0-9) .
2. Solver signs and submits a `place_bid` UserOperation embedding `fillOrder(order, {relayerFee, nativeDispatchFee, outputs})` (v1 shape, no `validUntil`) via `pallet-intents-coprocessor` [3](#0-2) .
3. Order placer, who controls the session key, withholds execution while monitoring the market.
4. Once the reference price for the output asset moves in the placer's favor, the placer signs the `SelectSolver` message and submits `select()` + `fillOrder()` in one transaction, forcing the solver to deliver the now-mispriced (stale) output amount at `order.deadline` (bounded only by the placer-chosen, uncapped deadline) [2](#0-1) .
5. Solver's bid executes exactly as signed, with no `FillExpired` check available on the legacy gateway, realizing a guaranteed loss for the solver and a risk-free gain for the placer — the precise scenario the codebase's own changelog identifies `validUntil` as fixing, but which remains open wherever the upgrade has not shipped [1](#0-0) .

    function fillOrder(Order calldata order, FillOptions calldata options) public payable nonReentrant {
        uint256 blockNumber = _blockNumber();
        if (order.deadline < blockNumber) revert Expired();
        // The solver's own bound on how long its quoted price stands. Zero means unbounded,
        // which is the right default for a solver filling directly — it is only at risk from
        // its own staleness. It matters for a bid signed through the coprocessor, where the
        // order placer chooses the moment of execution and nothing else caps the wait.
        if (options.validUntil != 0 && blockNumber > options.validUntil) revert FillExpired();

		pub fn place_bid(
			origin: OriginFor<T>,
			commitment: H256,
			user_op: BoundedVec<u8, ConstU32<1_048_576>>,
		) -> DispatchResult {
			let filler = ensure_signed(origin)?;

			// Validate user_op is not empty
			ensure!(!user_op.is_empty(), Error::<T>::InvalidUserOp);

			// Phantom orders have stricter rules: one bid per filler, no updates, and only
			// within the configured acceptance window after the order was registered. Every
			// chain's active order is checked, not just the most recently generated one.
			if let Some(active) = CurrentPhantomOrder::<T>::get() {
				if let Some((_, info)) = active.iter().find(|(c, _)| *c == commitment) {
					let window: BlockNumberFor<T> = Self::phantom_bid_window().into();
					ensure!(
						frame_system::Pallet::<T>::block_number() <= info.created_at_block + window,
						Error::<T>::PhantomOrderBidWindowClosed
					);
					ensure!(
						!Bids::<T>::contains_key(&commitment, &filler),
						Error::<T>::DuplicatePhantomBid
					);
				}
			}

			// If a bid already exists, unreserve the old deposit first
			if let Some(old_deposit) = Bids::<T>::get(&commitment, &filler) {
				<T as Config>::Currency::unreserve(&filler, old_deposit);
			}

			let deposit = Self::storage_deposit_fee();

			// Reserve the new deposit
			<T as Config>::Currency::reserve(&filler, deposit)
				.map_err(|_| Error::<T>::InsufficientBalance)?;

			// Store the bid in offchain storage
			let bid = Bid { filler: filler.clone(), user_op: user_op.to_vec() };
			let offchain_key = Self::offchain_bid_key(&commitment, &filler);
			offchain_index::set(&offchain_key, &bid.encode());

			// Store deposit amount in onchain storage for discoverability and accurate refunds
			Bids::<T>::insert(&commitment, &filler, deposit);

			Self::deposit_event(Event::BidPlaced { filler, commitment, deposit });

			Ok(())
		}
