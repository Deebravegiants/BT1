## Title
Escrow release/refund and dust-sweep silently succeed on failed ERC20 `transfer()`, permanently burning escrowed intent funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` performs ERC20 payouts with a raw low-level `.call()` to `transfer()` and only checks that the call itself did not revert, never inspecting the ABI-decoded boolean return value. Tokens that signal failure by returning `false` instead of reverting (the exact bug class from the referenced Teller report) will cause the gateway to treat a failed payout as successful, decrement/clear escrow accounting, and emit `EscrowReleased`/`EscrowRefunded` — permanently losing the escrowed funds with no path to reclaim them.

### Finding Description
In `withdraw()`, escrowed tokens are paid out like this: [1](#0-0) 

and: [2](#0-1) 

`(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` only reports whether the external call reverted, not whether the token's `transfer()` actually moved funds. For a no-revert-on-failure ERC20 (returns `false` on failure instead of reverting), `success` is `true` even though `beneficiary` received nothing. Immediately after, the code unconditionally does `_orders[body.commitment][token] -= amount;`, sets `_filled[body.commitment] = beneficiary`, and emits `EscrowReleased`/`EscrowRefunded` — finalizing the order as fulfilled.

The same unchecked pattern also appears in the admin-triggered `SweepDust` path inside `onAccept()`: [3](#0-2) 

`withdraw()` is reached from two unprivileged-relay paths:
- `onAccept()` for `RedeemEscrow`/`RefundEscrow` requests, authenticated only by `authenticate()` (i.e. any relayer can deliver a validly-authored cross-chain message from the peer gateway): [4](#0-3) 
- `onGetResponse()`, reached after any user dispatches a cancel/refund GET request: [5](#0-4) 

Contrast this with the non-Tron `IntentGatewayV2`/`IntentsBase`, which correctly uses OpenZeppelin's `SafeERC20.safeTransfer`, reverting on both call failure and a `false` return value: [6](#0-5) 

The Tron contract's manual `.call()` + `success`-only check strips away exactly the protection `SafeERC20` provides, reintroducing the "no-revert-on-failure token" class of bug.

### Impact Explanation
Once escrow accounting is decremented and the order is marked filled/refunded/redeemed despite the beneficiary receiving zero tokens, the escrowed funds are permanently stuck in the `IntentGatewayV2` contract with no code path to re-claim them for that commitment (the escrow slot for the order/token pair is already reduced or zeroed, and `_filled` is set). This is a permanent freezing/loss of user and solver funds for any escrowed token whose `transfer()` can return `false` rather than revert (a documented and common non-standard-ERC20 behavior, and one that is even more prevalent on TRC20 tokens deployed on Tron, which frequently deviate from the strict ERC20 ABI). It also breaks the atomicity assumption relayers/solvers rely on when filling or cancelling cross-chain intents, since the on-chain event history states the escrow was released even though value transfer failed.

### Likelihood Explanation
Likelihood is Medium: it requires an input/output/fee token used with the gateway to be a no-revert-on-failure token (or one that returns `false` under specific conditions, e.g. blacklisting, pausing, or insufficient allowance/balance edge cases introduced after escrow). Given the gateway is designed to be permissionless for arbitrary `token` addresses supplied in `Order.inputs`/`Order.output.assets`, and Tron's TRC20 ecosystem includes many such non-conforming tokens, this is a realistic operational condition rather than a purely theoretical one, and does not require any privileged actor — only a relayer delivering an otherwise legitimate, authenticated cross-chain redeem/refund message, or a normal user's cancel flow completing through `onGetResponse`.

### Recommendation
Replace every raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` payout in `evm/tron/contracts/apps/IntentGatewayV2.sol` (`withdraw()` for escrow, transaction fees, and the `SweepDust` branch of `onAccept()`) with `SafeERC20.safeTransfer`, mirroring the pattern already used in `evm/src/apps/intentsv2/IntentsBase.sol`. If low-level calls must be retained for compatibility with non-standard tokens that don't return data, decode and check the boolean return value when data is present, in addition to checking `success`, before mutating escrow accounting or emitting finalization events.

### Proof of Concept
1. A user places a cross-chain order on the source chain, escrowing token `T` — a no-revert-on-failure token whose `transfer()` returns `false` on failure instead of reverting (e.g. it becomes unable to pay out due to an internal condition, or is deliberately crafted/compromised to return `false` intermittently).
2. A relayer delivers a valid `RedeemEscrow` (or `RefundEscrow`) `PostRequest` for that commitment; `onAccept()` authenticates the source and calls `withdraw(body, ...)`.
3. Inside `withdraw()`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `success = true` (the call didn't revert) but the token internally returned `false` and moved no funds.
4. `_orders[body.commitment][token] -= amount` executes, `_filled[body.commitment] = beneficiary` is set, and `EscrowReleased`/`EscrowRefunded` is emitted.
5. The beneficiary never received `amount` of token `T`, and the contract's escrow bookkeeping for that commitment no longer reflects the actual token balance held — the funds are stranded in the contract with no remaining accounting path to redeem them.
