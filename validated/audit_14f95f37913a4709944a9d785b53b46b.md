### Title
Direct LT/Token donations to `FeeVault` are permanently unrecoverable — (File: `packages/contracts/src/FeeVault.sol`)

### Summary
`FeeVault` only has a recovery mechanism for its designated asset, USDC (`sweepDonations`); any other ERC20 — including a launched `Token` or a BounceTech LT — sent to the vault has no claim, sweep, or rescue path and is permanently stuck, mirroring the "DAO cannot handle tokens other than SALT" class of bug from the source report where non-native-asset balances become unrecoverable.

### Finding Description
`FeeVault` is designed to hold and account for exactly one asset, USDC, via `accrue`/`claim`/`claimProtocol`/`sweepDonations`: [1](#0-0) 

`sweepDonations` explicitly computes `balance = $.usdc.balanceOf(address(this))` and only ever moves the *USDC* delta above `backed` accrual state to `feeTo`: [2](#0-1) 

There is no `IERC20(token).safeTransfer` escape hatch, owner rescue function, or any other code path in `FeeVault.sol` that can move a non-USDC ERC20 balance out of the contract. This is a stark contrast with `Bonding.sol`, which explicitly anticipates and handles exactly this class of problem for LT and Token balances it might hold: `_sweepLTToOwner` sweeps any LT above the per-graduation earmark to the owner, and `_prepareGraduationLiquidity`/`unsoldBurned` burns stray Token donations sitting in the curve pair: [3](#0-2) [4](#0-3) 

`FeeVault` has no analogous logic. Any unprivileged wallet can call `IERC20(launchedToken).transfer(address(feeVault), amount)` or `IERC20(lt).transfer(address(feeVault), amount)` directly — this requires no privileged role and is explicitly one of the permitted analog paths ("direct ERC20 transfers of a launched Token or an LT into … FeeVault"). Once landed, those tokens sit in the vault's balance with zero code path capable of moving them anywhere: `claim()` and `claimProtocol()` only read/zero the internal USDC-denominated `creatorBalance`/`protocolBalance` mappings and call `$.usdc.safeTransfer`, and `sweepDonations()` is hard-coded to the `$.usdc` token as well.

### Impact Explanation
Any launched `Token` or LT accidentally or deliberately sent to `FeeVault` (e.g., a wallet mistakenly using the vault address as a recipient, a UI bug, or a griefer wanting to permanently burn value for optics) is frozen forever with no owner or permissionless recovery mechanism — a permanent freezing of funds. This matches the accepted-impact class in the source finding (permanent loss of non-native tokens held by a contract that only understands one asset type). The blast radius is bounded to whatever is sent to that specific address (creators' launched tokens or LT balances), but the freeze is total and irreversible since there is no owner-only sweep for arbitrary ERC20s in `FeeVault`, unlike the parallel design already present in `Bonding` for the same asset class.

### Likelihood Explanation
Likelihood is driven entirely by user/integration error rather than an economic incentive to exploit, since sending value to `FeeVault` gives the sender nothing back. However, `FeeVault`'s address is a normal, publicly known, permissionless-fee-forwarding contract that end users and front-ends interact with regularly (`claim`/`claimProtocol` are public entry points), which raises the chance of a stray transfer (e.g., copy-pasted vault address, a bot resending LT/Token dust, or a griefer intentionally stranding a competitor's LT there) compared to an obscure internal contract.

### Recommendation
Add an owner-gated (or `sweepDonations`-style permissionless-but-`feeTo`-directed) rescue function to `FeeVault` for non-USDC ERC20 tokens, mirroring `Bonding._sweepLTToOwner`: e.g. `function sweepToken(address token) external { require(token != address(usdc)); IERC20(token).safeTransfer(feeTo, IERC20(token).balanceOf(address(this))); }`, guarding against sweeping the vault's own accounted USDC.

### Proof of Concept
1. Any address (griefer or accidental sender) calls `Token(launchedTokenAddr).transfer(address(feeVault), 1000e18)` or `IBounceLeveragedToken(lt).transfer(address(feeVault), 1000e18)` — both are plain unprivileged ERC20 transfers, no approval or role needed on the recipient side.
2. Confirm `IERC20(launchedTokenAddr).balanceOf(address(feeVault)) == 1000e18`.
3. Attempt recovery: `feeVault.claim()` / `feeVault.claimProtocol()` only ever move `$.usdc`, and `feeVault.sweepDonations()` only computes/sweeps the `usdc` balance delta over `backed` — neither touches the Token/LT balance.
4. There is no other external function in `FeeVault.sol` capable of transferring the stranded ERC20 out; the balance is permanently unrecoverable. [5](#0-4) [2](#0-1)

    /// @notice Sweep unbacked USDC (donations) to `feeTo`. Required because
    ///         direct USDC transfers would otherwise inflate `balanceOf` above
    ///         the accrual tally and silently mask the `accrue` underfund
    ///         check. Permissionless — funds always go to the admin-set `feeTo`.
    function sweepDonations() external nonReentrant returns (uint256 amount) {
        FeeVaultStorage storage $ = _s();
        uint256 backed = $.totalAccruedCreator + $.protocolBalance;
        uint256 balance = $.usdc.balanceOf(address(this));
        if (balance <= backed) revert NothingToClaim();
        amount = balance - backed;
        address feeTo_ = $.feeTo;
        $.usdc.safeTransfer(feeTo_, amount);
        emit DonationsSwept(feeTo_, amount);
    }
