## Analog Found

### Title
Unchecked low-level ERC20 `transfer` return value lets a malicious order token silently "fake" escrow payout while marking the order finalized - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` redeems escrowed order funds using a raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only checks that the call itself did not revert (`success`), never decoding/validating the returned boolean. This is exactly the bug class described in the Cooler report: ERC20 tokens that signal failure by returning `false` instead of reverting will cause the contract to believe a transfer succeeded when it did not, while all downstream accounting proceeds as if payment were made.

### Finding Description
In `withdraw()`, called from `onAccept` when handling `RedeemEscrow`/`RefundEscrow` ISMP messages, and from `onGetResponse` for cancellations, escrowed ERC20 tokens are paid out like this: [1](#0-0) 

The same unchecked pattern is used for transaction fee payout and in the `SweepDust` handler: [2](#0-1) [3](#0-2) 

Crucially, the accounting proceeds unconditionally regardless of whether the token actually transferred value: `_filled[body.commitment] = beneficiary` is set before the loop, and `_orders[body.commitment][token] -= amount` executes right after the `.call`, with no check on the decoded return data.

This is inconsistent with the non-Tron EVM implementation, which correctly uses OpenZeppelin's `SafeERC20.safeTransfer`, reverting on both call failure and a `false` return: [4](#0-3) 

### Impact Explanation
A user who places an order (`placeOrder`) fully controls which ERC20 token is escrowed as an input asset — this is a permissionless, unprivileged path. If that token's `transfer()` implementation returns `false` (without reverting) when the recipient is the solver/beneficiary (while behaving normally for the depositor), then:
1. The solver fills the order and transfers real output assets to the beneficiary via `safeTransferFrom` (properly checked, so this leg always succeeds).
2. When the escrow is redeemed to the solver via `withdraw()`, the malicious token's `transfer` silently returns `false`; the low-level `.call` still reports `success = true` since it doesn't revert.
3. `_orders[...] -= amount` still executes and `_filled[...]` is set, permanently finalizing the order as fulfilled — the solver receives nothing and has no way to reclaim the escrow, while the malicious order creator effectively obtained the solver's real assets for free.

This is a direct theft of solver/relayer funds analogous to the Cooler "lender steals collateral" pattern, reachable from a single unprivileged `placeOrder` + `fillOrder` sequence, and it also affects the fee-token and `SweepDust` payout paths, which could similarly desynchronize accounted vs. actual balances.

### Likelihood Explanation
The prerequisite is a token whose `transfer()` returns `false` on failure rather than reverting — a well-known, non-trivial-but-real ERC20 deviation (and Tron's TRC20 ecosystem has a documented history of such non-standard token implementations). An attacker fully controls the token contract used for their own order's input asset, making this trivially triggerable at will against any solver who fills the order.

### Recommendation
Replace the raw `.call` + `success`-only checks in `withdraw()`, `SweepDust` handling, and the fee-token payout with `SafeERC20.safeTransfer` (as already used correctly in the non-Tron `IntentsBase.sol`), ensuring both call failure and a `false` boolean return cause a revert.

### Proof of Concept
1. Attacker deploys a malicious ERC20 token `EvilToken` whose `transfer(to, amount)` returns `false` (no revert) whenever `to != attacker`, and returns `true` normally otherwise.
2. Attacker calls `placeOrder` on `IntentGatewayV2` (Tron) using `EvilToken` as the sole input asset, requesting a real-value output token from a solver.
3. A solver calls `fillOrder`, transferring real output tokens to the attacker via `safeTransferFrom` (succeeds normally).
4. The cross-chain `RedeemEscrow` message triggers `onAccept` → `withdraw()`, which calls `EvilToken.transfer(solver, amount)`; this returns `false` but the low-level `.call` reports `success = true`, so `TransferFailed` is never reverted.
5. `_orders[...] -= amount` executes and `_filled[commitment] = solver` is recorded — the order is marked fulfilled and escrow accounting zeroed out, but the solver never actually received any `EvilToken`, while the attacker keeps the solver's real output assets. [1](#0-0)

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
