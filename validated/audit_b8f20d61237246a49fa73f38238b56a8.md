### Title
Webhook `shop` (and `topic`/`webhook-id`/`api-version`) identity fields are not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, then trusts the `shop` (and `topic`/`webhook_id`/`api_version`) values taken from unauthenticated HTTP headers when building the `WebhookMetadata` handed to the host application's handler. The `shop` field is the tenant-identity binding a multi-tenant app relies on to route data/actions to the correct merchant, but it is never included in the signed material.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate_signature` computes/compares the HMAC exclusively against that signable string: [2](#0-1) 

`Registry.process` gates on this HMAC check and then immediately constructs `WebhookMetadata` using `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` — all four pulled straight from HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, `shopify-api-version`) that are never part of `to_signable_string`: [3](#0-2) [4](#0-3) 

This is the same bug class as `TOKE-21`: a value used downstream by security-sensitive logic (`currentSafeTotalSupply` there, `shop` here) is accepted without verifying it corresponds to the authenticated context (the `periodFinish`/snapshot there, the HMAC-signed payload here). The identity binding that should hold is:

`shop used to route/attribute the webhook == shop over which the HMAC was computed`

but the implementation only guarantees:

`hmac(raw_body) == hmac(raw_body)`,

with `shop` entirely outside that equation. `WebhookMetadata.shop` is a plain, unauthenticated header echo: [5](#0-4) 

**Attack path:** Any endpoint exposed by a Shopify app implementing `WebhookHandler#handle` receives `data.shop` as the tenant identifier. Because the header is unsigned, an attacker who can trigger any legitimately-signed webhook delivery for a body they control (e.g., they run their own dev/test store subscribed to the app, or replay any webhook whose body content is attacker-influenced/predictable) can resend the same body+valid-HMAC pair to the app's webhook endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header rewritten to a victim merchant's domain. `HmacValidator.validate` still returns `true` because it only checks `raw_body`, and `Registry.process` will pass the attacker-chosen `shop` value straight to the host application's handler as if it were the authenticated tenant, since nothing in this gem cross-checks that the signature actually vouches for that particular shop.

### Impact Explanation
This crosses the tenant boundary this gem exists to protect: the `shop` value the host app receives inside `WebhookMetadata` — and treats as authenticated — can be forged independently of the HMAC that is supposed to authenticate the whole message. In a multi-tenant SaaS app, this is a Critical-class **cross-tenant access** vector: handlers commonly use `data.shop` to look up the merchant's session/access token and perform actions on the merchant's behalf, or to write incoming data (e.g., `orders/create`) into the wrong tenant's records, or to trigger reprocessing/deletion attributed to a shop that never actually sent the webhook.

### Likelihood Explanation
Exploitability depends only on network access to the app's public webhook endpoint and the ability to obtain one genuinely-signed body+HMAC pair (trivial for an attacker who owns any store, even a free development store, that installs the target app) plus the ability to set an arbitrary `shop` header — nothing privileged (API secret, access token, TLS interception) is required, matching the "unpriviledged internet user" threat model. The `body` bound by the HMAC (e.g., an `orders/create` payload) is largely attacker/merchant controlled to begin with, so crafting a useful spoofed payload for a chosen victim domain is straightforward.

### Recommendation
Bind the identity fields into the signed material, not just the body:
- Compute/verify the HMAC over a canonical string that includes `shop`, `topic`, and `webhook_id` in addition to `raw_body` (mirroring how Shopify signs webhooks is not sufficient — the gem should defense-in-depth verify these headers separately), or
- At minimum, require the host application to cross-check `WebhookMetadata.shop` against the shop stored for the session/tenant context that owns the endpoint before trusting it, and document this gap prominently, since currently `Registry.process` implicitly presents `shop` as verified when it is not.
- Consider deriving `shop` only from data actually inside the HMAC-covered payload where the webhook topic includes it, rather than the header.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and lets it subscribe an `orders/create` webhook.
2. Shopify sends a webhook to the app: headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw body>`, plus the JSON body.
3. Attacker captures this raw body + valid HMAC (the HMAC is computed only over `raw_body`, per `Request#to_signable_string`).
4. Attacker resends the identical raw body and HMAC header to the app's public webhook endpoint, but replaces `x-shopify-shop-domain` with `victim.myshopify.com`.
5. `HmacValidator.validate` recomputes the HMAC over `raw_body` only and it matches, so `Registry.process` proceeds: [3](#0-2) 
6. The app's `WebhookHandler#handle` receives `data.shop == "victim.myshopify.com"` and performs its logic (e.g., updates local order records, triggers actions using the victim's stored session) even though `victim.myshopify.com` never sent this webhook — a cross-tenant impersonation.
