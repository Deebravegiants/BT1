### Title
Missing reentrancy guard on Tron `IntentGatewayV2.placeOrder`/`withdraw` allows escrow double-crediting via malicious ERC-20 callback - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron fork of `IntentGatewayV2` reimplements `placeOrder` and the internal `withdraw` settlement routine without the `nonReentrant` guard and without the checks-effects-interactions (CEI) ordering that the primary EVM contract (`evm/src/apps/IntentGatewayV2.sol` and `evm/src/apps/intentsv2/IntentsBase.sol`) already received as a fix for exactly this bug class. This mirrors the reported Bond.sol issue: an externally-controlled token's `transferFrom`/`transfer` call is executed before critical escrow state is updated, letting a malicious token re-enter the gateway and manipulate escrow accounting.

### Finding Description
In the primary EVM `IntentGatewayV2.sol`, `placeOrder` is guarded with `nonReentrant`: [1](#0-0) 

and its escrow-release routine `_withdraw` in `IntentsBase.sol` follows CEI — the `_orders` mapping is decremented *before* the external token transfer: [2](#0-1) 

The Tron fork's `placeOrder`, however, has no `nonReentrant` modifier at all: [3](#0-2) 

and its `withdraw()` internal function performs the raw external token call *before* decrementing the corresponding escrow balance: [4](#0-3) 

The check preceding the transfer only verifies `_orders[commitment][token] == 0` (i.e., "escrow exists at all"), not that the specific amount is available, and the decrement `_orders[body.commitment][token] -= amount;` happens only after the low-level `.call` to the token contract returns. A token contract with any transfer-time callback (ERC-777-style hooks, or a bespoke malicious token exactly like the PoC in the external report) can use that callback to re-enter the gateway while the pre-transfer escrow balance is still intact, before it is decremented.

Additionally, `placeOrder`'s own token-intake loop calls `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` without any reentrancy guard: [5](#0-4) 

Because `_orders[commitment][token] += reducedInputs[i].amount;` is credited within this same unguarded function, and `_nonce` and `commitment` derivation depend on mutable contract state (`_nonce++`), a malicious input token's `transferFrom` callback can re-enter `placeOrder` (or other unguarded state-mutating entry points) mid-execution, producing commitments/escrow credits that are inconsistent with the tokens actually transferred — directly analogous to the "call again to withdraw/credit more than intended" mechanism described in the external Bond.sol report.

### Impact Explanation
This allows an attacker who controls (or picks) the input token used in `placeOrder`, or a solver/beneficiary controlling a malicious output/beneficiary contract during `withdraw()`, to manipulate escrow bookkeeping via reentrancy and extract more value from the `IntentGatewayV2` (Tron) escrow than was actually deposited — an unbacked/duplicated escrow credit or a double-withdrawal of escrowed funds. This is a direct fund-theft / accounting-integrity vulnerability reachable from a single, unprivileged `placeOrder`/order-settlement transaction, matching the Medium severity of the analogous, already-acknowledged Bond.sol finding.

### Likelihood Explanation
Likelihood is Medium: exploitation requires the attacker to supply (or have listed) a token with transfer-time callback behavior as an order input/output token, which is plausible given `IntentGatewayV2` explicitly supports arbitrary ERC-20s (including fee-on-transfer tokens, per its own fee-on-transfer handling logic), and the entry points (`placeOrder`, `cancelOrder` same-chain path, `withdraw` via `onAccept`) are reachable by ordinary users/solvers without any privileged role.

### Recommendation
Port the fixes already applied to the primary EVM `IntentGatewayV2`/`IntentsBase` contracts to the Tron fork:
1. Add `nonReentrant` to `placeOrder`, `cancelOrder`, and any other externally reachable state-mutating entry point in `evm/tron/contracts/apps/IntentGatewayV2.sol`.
2. In `withdraw()`, decrement `_orders[body.commitment][token]` (and the `TRANSACTION_FEES` accounting) *before* performing the external `.call`/native-value transfer, matching the CEI ordering used in `IntentsBase.sol::_withdraw`.

### Proof of Concept
Not independently executable from the index alone (Tron-specific test harness not located in the indexed code), but the exploit follows the same pattern verified by the existing Foundry PoC for the primary contract's pre-fix behavior (`evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol`), where a malicious beneficiary/token re-enters the fill/withdraw path during the token transfer before escrow state is updated: [6](#0-5) 
Applying the same `ReentrantBeneficiary`/malicious-token technique against `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw` (which still calls external `token.call` before decrementing `_orders`) would reproduce the double-withdrawal.
