### Title
Webhook `shop-domain` header not bound to HMAC allows cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content as only the raw request body [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates only that the HMAC matches the body, then trusts `request.shop` (and `request.topic`) verbatim when constructing the `WebhookMetadata` passed to the app's handler [3](#0-2) .

### Finding Description
The equality that should hold is: `shop authenticated by the HMAC == shop the handler acts on`. In this code that equality does not hold — the HMAC only proves "this body byte-sequence was signed with this app's shared `api_secret_key`" [4](#0-3) ; it says nothing about which shop's domain header accompanies that body.

Because a single app has one `api_secret_key` shared by every installed shop/tenant, any shop that has the app installed will legitimately receive webhook deliveries (with a body + valid `hmac-sha256` header) addressed to itself. An attacker who controls a shop with the app installed (an "unprivileged internet user" with respect to other tenants of the same app) can capture one of their own legitimately-received webhook requests (raw body + valid HMAC over that body) and replay it to the app's webhook endpoint with the `shopify-shop-domain` (or `x-shopify-shop-domain`) header changed to point at a victim shop. `Registry.process` runs `Utils::HmacValidator.validate(request)`, which recomputes the HMAC purely from `to_signable_string` (the raw body) [4](#0-3)  — the forged `shop` header does not affect this check and validation still succeeds. The handler is then invoked with `WebhookMetadata` carrying the attacker-chosen `shop` value [3](#0-2) .

Any app logic that uses `WebhookMetadata#shop` to look up the tenant's stored session/access token or to write data scoped to "the shop in the webhook" will act on behalf of, or against, the wrong tenant — a direct cross-tenant boundary break rooted in the missing binding between the HMAC and the `shop` field.

### Impact Explanation
This is a cross-tenant access vulnerability (Critical per the given impact classes): a party legitimately controlling one tenant of a multi-tenant app can forge webhook events attributed to a different, victim tenant, since the field the app acts on (`shop`) is never part of the value the HMAC actually authenticates.

### Likelihood Explanation
Likelihood is high for any app that installs on multiple shops (the normal Shopify app model) and uses the `shop` field from `WebhookMetadata` for tenant-scoped logic, since obtaining one authentic (body, hmac) pair for the attacker's own shop is trivial (they just receive their own webhooks), and the header spoofing requires no secret knowledge.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the HMAC-signed material, or otherwise cryptographically verify that the `shop-domain` header matches the store the webhook subscription was created for (e.g., compare against a per-shop secret/session lookup, not just the shared app secret) before constructing `WebhookMetadata` in `Registry.process` [3](#0-2) .

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a genuine webhook delivery: raw body `B`, header `shopify-hmac-sha256: H` (valid HMAC of `B` under the app's `api_secret_key`), `shopify-shop-domain: attacker.myshopify.com`.
2. Attacker replays the request to the app's webhook endpoint, keeping body `B` and header `shopify-hmac-sha256: H` unchanged, but sets `shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(B, api_secret_key) == H` [5](#0-4)  — this passes since `B` and `H` are unmodified.
4. The registered handler is invoked with `WebhookMetadata.new(..., shop: "victim.myshopify.com", ...)` [6](#0-5) , causing the app to process attacker-controlled data as if it originated from the victim shop.
