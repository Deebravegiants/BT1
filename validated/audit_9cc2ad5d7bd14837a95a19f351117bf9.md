### Title
Attacker-controlled `spec.PreemptionPolicy` persists on CompositePodGroup when resolved PriorityClass has `PreemptionPolicy=nil` - ([File: plugin/pkg/admission/priority/admission.go])

### Summary
`Plugin.admitCompositePodGroup` resolves priority/preemption policy from the referenced (or default) `PriorityClass` and is meant to overwrite `cpg.Spec.PreemptionPolicy` with the authoritative value. When the resolved `PriorityClass.PreemptionPolicy` is `nil`, the guard `preemptionPolicy != nil` at line 267 causes the entire enforcement block to be skipped, leaving any attacker-supplied `cpg.Spec.PreemptionPolicy` (e.g. `PreemptNever`) untouched and persisted verbatim. This mirrors the identical bug in `admitPodGroup` for `PodGroup`.

### Finding Description
`admitCompositePodGroup` (plugin/pkg/admission/priority/admission.go:245-282) calls `p.establishPriority` to compute `priorityClassName, priority, preemptionPolicy` from the referenced `PriorityClass` [1](#0-0) . It then only reconciles `cpg.Spec.PreemptionPolicy` inside the block gated by `preemptionPolicy != nil`: [2](#0-1) 

If the `PriorityClass` object referenced by the attacker (or the cluster default `PriorityClass`) has `PreemptionPolicy == nil` (this is valid/common — `PriorityClass.PreemptionPolicy` is optional and commonly unset), `preemptionPolicy` returned by `establishPriority` is `nil`, so the whole `if` block is skipped entirely and `cpg.Spec.PreemptionPolicy` is never touched by admission.

Because `dropDisabledCompositePodGroupFields`/`dropDisabledPreemptionPolicyField` in `pkg/registry/scheduling/compositepodgroup/strategy.go` only clears the field when the `PodGroupPreemptionPolicy` feature gate is disabled (and does not clear it when enabled) [3](#0-2) , and no other consistency check exists to force `cpg.Spec.PreemptionPolicy` to match the resolved `PriorityClass`, an attacker who can create a `CompositePodGroup` in their own namespace (referencing any `PriorityClass` with `PreemptionPolicy` unset, including the implicit default when no `priorityClassName` is given) can set `spec.PreemptionPolicy: PreemptNever` directly in their create request and have it persist unmodified.

This is the exact same nil-guard flaw already present in `admitPodGroup` (lines 224-238), just duplicated for the `CompositePodGroup` code path.

### Impact Explanation
A workload marked `PreemptionPolicy: PreemptNever` is treated by the scheduler/preemption logic as immune from being preempted by higher-priority pending workloads. An attacker with only namespace-scoped create permission on `compositepodgroups` can forge this immunity flag without it being derived from (or validated against) any `PriorityClass`, letting low-trust workloads resist preemption indefinitely and starve higher-priority, quota-limited tenants — a control-plane/API-server-enforced denial-of-service against the scheduler's preemption fairness guarantees.

### Likelihood Explanation
- Requires only the `CompositePodGroup` (v1alpha3) and `PodGroupPreemptionPolicy` feature gates to be enabled (both alpha features under active development in this repo).
- Requires only namespace-scoped RBAC to create `compositepodgroups.scheduling.k8s.io` — no elevated privileges, no PriorityClass creation rights needed (the attacker can rely on the cluster's existing default `PriorityClass`, or any pre-existing `PriorityClass` with `PreemptionPolicy` unset, which is the common/default case).
- Fully deterministic and repeatable: every create of a `CompositePodGroup` with `spec.PreemptionPolicy: PreemptNever` against a `PriorityClass` lacking an explicit `PreemptionPolicy` will pass through admission unmodified.

### Recommendation
In `admitCompositePodGroup`, always reconcile `cpg.Spec.PreemptionPolicy` against the value derived from the resolved `PriorityClass`, treating `nil` from `establishPriority` as an explicit "no preemption policy" (or a defined default) rather than skipping enforcement — analogous to how `pod.Spec.PreemptionPolicy` is unconditionally set based on `corePolicy` in `admitPod`. Concretely: move the reconciliation logic outside the `preemptionPolicy != nil` short-circuit, and reject (or clear) any attacker-supplied `cpg.Spec.PreemptionPolicy` when the resolved policy is `nil`. Apply the same fix to `admitPodGroup`.

### Proof of Concept
Unit test in `plugin/pkg/admission/priority/admission_test.go` (mirroring the `PodGroup` case):
1. Create a `PriorityClass` "no-preempt-policy" with `Value: 1000` and `PreemptionPolicy: nil`.
2. Enable `CompositePodGroup` and `PodGroupPreemptionPolicy` feature gates.
3. Build a `CompositePodGroup` object with `Spec.PriorityClassName: "no-preempt-policy"` and `Spec.PreemptionPolicy: &scheduling.PreemptNever` set directly by the "attacker".
4. Call `plugin.Admit(ctx, admission.NewAttributesRecord(cpg, nil, ..., "create", ...), nil)`.
5. Assert `err == nil` and `cpg.Spec.PreemptionPolicy != nil && *cpg.Spec.PreemptionPolicy == scheduling.PreemptNever`, proving the attacker-controlled value survived admission unvalidated (expected/fixed behavior: admission should either overwrite it to a value derived from the PriorityClass or reject the mismatch).
