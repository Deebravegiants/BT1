### Title
Webhook `shop`/`topic` identity fields are not covered by the HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw request body, while the shop identity (`x-shopify-shop-domain`), `topic`, `api-version` and `webhook-id` headers are read directly from unauthenticated HTTP headers and are never included in the HMAC computation. `ShopifyAPI::Webhooks::Registry.process` validates only the body/HMAC pair and then unconditionally trusts `request.shop` to build the `WebhookMetadata` handed to the app's handler, breaking the intended binding `HMAC(secret, signed_bytes) == HMAC(secret, actually_processed_identity)`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all pulled straight from HTTP headers that are not part of the signed payload: [2](#0-1) 

`HmacValidator.validate` / `validate_signature` verify only `verifiable_query.to_signable_string` (the raw body) against the `hmac` header: [3](#0-2) 

`Registry.process` gates on this body-only HMAC check and then trusts `request.shop` as the tenant identity passed to the app's handler: [4](#0-3) 

Because the `shop-domain` header sits outside the signed bytes, the equality the gem is supposed to enforce — `hmac == HMAC(secret, body_bound_to(shop))` — actually reduces to `hmac == HMAC(secret, body)`, with `shop` unbound. Any HTTP client that can reach the app's public webhook endpoint (which is exposed on the internet for Shopify to call) can take a **legitimately-signed webhook body+HMAC pair for shop A** (obtainable simply by installing the app on an attacker-controlled shop, which Shopify will then deliver real signed webhooks for) and replay it to the same endpoint with the `x-shopify-shop-domain` header rewritten to shop B. `HmacValidator.validate` still succeeds because it only checks the untouched body against the HMAC, and `Registry.process` forwards `shop: "B"` to the handler unmodified.

### Impact Explanation
This is a cross-tenant integrity break: an attacker who legitimately controls one shop that has the app installed (and therefore legitimately receives valid HMAC-signed webhooks for their own store) can forge webhook events attributed to an arbitrary victim shop, without ever needing `api_secret_key`, an access token, or any other stolen credential. Any host application logic that keys work off `WebhookMetadata#shop` (e.g., updating per-tenant records, revoking access, or writing to a merchant's data store) can be tricked into processing attacker data under a victim's identity, meeting the "cross-tenant access" bar.

### Likelihood Explanation
Webhook endpoints are, by design, public HTTP endpoints reachable by anyone on the internet (Shopify calls them directly, with no additional network-layer authentication provided by this gem). Getting a validly-signed body+HMAC pair only requires installing the app on a shop the attacker controls — a normal, low-privilege action for anyone who can install a public/test app. Forging the header is a trivial HTTP replay. No secrets, tokens, or privileged access are required.

### Recommendation
Bind the shop (and ideally topic) identity into the verified payload rather than trusting the raw header:
- Include `shop-domain` (and topic/webhook-id) in the value that is HMAC-verified, or
- Require the caller to independently confirm the `shop` header matches a shop known to have an active session/installation before dispatching to the handler, or
- Document/enforce that host apps must not treat `WebhookMetadata#shop` as authenticated by `HmacValidator.validate` alone, and provide a helper that fails closed if these fields are used for tenant-sensitive dispatch without additional verification (e.g., checking against Shopify's published webhook IP ranges or mandatory mTLS).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`; Shopify sends a legitimate webhook, e.g.
```
POST /webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <valid HMAC of raw body B>
x-shopify-shop-domain: attacker.myshopify.com
<raw body B>
```
2. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: ...)` is constructed by the app; `HmacValidator.validate` passes because it only re-hashes `B`.
3. Attacker replays the exact same body `B` and `hmac` value, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `Registry.process` again calls `Utils::HmacValidator.validate(request)`, which still returns `true` (see `lib/shopify_api/utils/hmac_validator.rb:26-31`, only body bytes are hashed), then builds `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed_body, ...)` and invokes the app's handler as if the event genuinely originated from `victim.myshopify.com`.
