### Title
Escrow release/refund permanently reverts and locks funds for beneficiaries that cannot accept native ETH - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentGatewayV2`'s escrow-release path (`_withdraw`, called from `onAccept` for `RedeemEscrow`/`RefundEscrow` messages) pushes native ETH to a fixed beneficiary using a low-level `.call` that reverts on failure. If that beneficiary cannot accept ETH (a contract without a `receive`/payable `fallback`), the release permanently reverts, and because `EvmHost.dispatchIncoming` treats a failed `onAccept` as "retry later" rather than dropping it, the request is retried forever with the same doomed outcome — permanently freezing the escrowed native ETH (and any attached fee-token amount bundled in the same call).

### Finding Description
`IntentsBase._withdraw` transfers escrowed native ETH to `beneficiary` via `_sendValue`, which reverts the entire call if the push fails: [1](#0-0) [2](#0-1) 

This function is invoked from `onAccept` on `RedeemEscrow`/`RefundEscrow` request kinds (mirrored in the Tron variant at `evm/tron/contracts/apps/IntentGatewayV2.sol`), and also directly from `_cancelSameChain`: [3](#0-2) [4](#0-3) 

For the cross-chain `RefundEscrow` case, `beneficiary` is `order.user` — an address fixed at order-creation time and signed by the user, which the contract cannot substitute or retry with a different destination: [5](#0-4) 

Crucially, when `onAccept` reverts, `EvmHost.dispatchIncoming` does not drop the message — it deletes the request receipt "so that it can be retried" and returns without propagating the revert to the batch: [6](#0-5) 

Since the failure condition (the beneficiary contract's inability to accept ETH) is deterministic and does not change, every retry of the same `RefundEscrow`/`RedeemEscrow` message will fail identically forever. There is no fallback path in `_withdraw`/`withdraw` to deliver ERC-20/WETH instead of raw ETH (unlike `WrappedHyperFungibleToken.onAccept`, which explicitly falls back to wrapping and delivering an ERC-20 transfer when the native push fails): [7](#0-6) 

This is the exact analog of the referenced Gitcoin bug: a payout function performs an unconditional native-ETH push to a caller-supplied/user-fixed address and reverts the whole distribution if that address cannot receive ETH.

### Impact Explanation
Escrowed native ETH inputs for a cancelled/refunded or filled cross-chain order become permanently unrecoverable if the order's `user` (refund case) or solver (redeem case) address is a contract that cannot accept plain ETH transfers. Because the request is perpetually retryable but never succeeds, and there is no governance/admin escape hatch analogous to `WrappedHyperFungibleToken`'s WETH-fallback, the escrowed funds are permanently frozen inside `IntentGatewayV2`. This satisfies the "permanent freezing of funds" and "route unable to deliver messages" criteria — the ISMP message can never be delivered successfully for this order.

### Likelihood Explanation
Likelihood is moderate: it requires the order's `user` (or the filling solver) to be a smart-contract wallet/account (e.g., a Safe module, vault, or other contract) lacking a payable `receive`/`fallback`, and for the order's input token to be native ETH (`token == address(0)`). This is a realistic scenario for smart-contract accounts, vaults, or intent-routing contracts placing orders with native ETH inputs, and requires no malicious actor — a normal, functionally-correct contract without a `receive()` function is sufficient to trigger the freeze.

### Recommendation
- In `IntentsBase._withdraw` (and the Tron `withdraw`), do not let a failed native-ETH push permanently revert the whole `onAccept`/withdrawal. Mirror the fallback pattern used in `WrappedHyperFungibleToken.onAccept`: if the raw ETH push fails, wrap the ETH (e.g., into WETH) and deliver it as an ERC-20 transfer to the beneficiary, or credit the beneficiary's balance for pull-based withdrawal instead of push-based transfer.
- Alternatively, adopt a pull-payment pattern for native ETH escrow release: on failure to push ETH, record the amount in an internal ledger keyed by beneficiary, emit an event, and let the beneficiary (or anyone) later call a `claim()` function that retries the push, rather than looping the identical failing push through the ISMP retry mechanism forever.

### Proof of Concept
1. User places a cross-chain order with `inputs[0] = {token: address(0), amount: 1 ether}` and `order.user` set to a smart-contract address `C` that has no `receive()`/payable `fallback()` (e.g., a strict multisig wallet).
2. The order is later cancelled/timed out, causing the destination chain to dispatch a `RefundEscrow` `PostRequest` back to the source chain with `beneficiary = order.user = C`.
3. A relayer delivers the message; `EvmHost.dispatchIncoming` calls `IntentGatewayV2.onAccept`, which calls `withdraw(body, true)` → `_sendValue(C, 1 ether)` → the low-level call to `C` fails (no payable fallback) → reverts with `InsufficientNativeToken`.
4. `EvmHost.dispatchIncoming` catches the revert, deletes the request receipt ("so it can be retried") and returns without emitting `PostRequestHandled`.
5. Any relayer resubmitting the identical message triggers the same revert indefinitely; the 1 ETH remains escrowed in `IntentGatewayV2` with no code path to ever release it to `C`, permanently freezing the funds.

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
