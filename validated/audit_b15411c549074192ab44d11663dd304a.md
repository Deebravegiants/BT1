### Title
Webhook shop-domain identity is not bound to the HMAC, enabling cross-tenant webhook forgery via replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` treats `x-shopify-shop-domain` as an authenticated tenant identifier when handing data off to app webhook handlers, but the HMAC signature that `Utils::HmacValidator` verifies only covers the raw request body — not the shop-domain header. This breaks the identity binding `shop authenticated == shop the handler is told owns the event`.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

`Request#shop` is read independently from the `shopify-shop-domain` / `x-shopify-shop-domain` header, with no cryptographic relationship to the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the HMAC purely against `verifiable_query.to_signable_string` (i.e., the body), never mixing in the shop header: [3](#0-2) 

`Registry.process` validates only this body-bound HMAC, then forwards `request.shop` straight to the app's handler as the authoritative tenant identity: [4](#0-3) 

Because the shop-domain header is excluded from the signed bytes, any request carrying a body + HMAC pair that is valid for *some* shop (e.g., the attacker's own installed shop, which legitimately receives correctly-signed webhooks from Shopify for its own events) remains HMAC-valid if only the `x-shopify-shop-domain` header is swapped to a different, victim shop domain while body and HMAC are left untouched. The library performs no comparison between the header-derived shop and any value covered by the signature, so `Registry.process` will happily dispatch the handler with `shop: "victim.myshopify.com"` even though the HMAC only proves the body originated from Shopify for the attacker's own shop's event.

### Impact Explanation
This crosses a tenant boundary: an app that keys webhook side effects (e.g. record lookups/updates, session selection) off `WebhookMetadata#shop` will act on the wrong tenant's data because the gem hands the host application an unauthenticated shop identity alongside a signature that was never bound to it. This matches "cross-tenant access" impact — a shop that has installed the app (an ordinary, unprivileged app installer) can cause victim-shop-attributed data to be injected into the host's system without ever obtaining the app's `client_secret`.

### Likelihood Explanation
Any shop that installs the app can generate a legitimately HMAC-signed webhook of its choosing (by performing actions in its own store that trigger subscribed webhook topics), then intercept/resend that exact body+HMAC pair to the app's webhook endpoint with a modified `x-shopify-shop-domain` header. No secret material or privileged access is required — only the ability to send an HTTP request to the app's public webhook receiver endpoint, which is by design internet-reachable.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the signed material verified by `HmacValidator`, or otherwise cryptographically bind the header-derived shop to the verified payload before it is exposed via `WebhookMetadata`. At minimum, document/require host applications to independently verify that the `shop` in the webhook payload matches an active, expected installation before trusting it for tenant selection — but the safer fix belongs in this gem's `Request`/`HmacValidator`, since it is the one asserting a validated identity binding.

### Proof of Concept
1. Attacker's own shop `attacker.myshopify.com` has installed the app and receives a legitimate webhook: body `B`, header `x-shopify-hmac-sha256 = HMAC(B, secret)`, header `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker replays this exact body and HMAC header to the app's webhook receiver, changing only `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers/body; `Utils::HmacValidator.validate` recomputes HMAC over `B` only — validation succeeds because `B` and the HMAC are unmodified.
4. `Registry.process` dispatches the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: B, ...)`, even though nothing about `B` or its signature was ever tied to `victim.myshopify.com`.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
