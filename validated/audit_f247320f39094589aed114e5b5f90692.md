### Title
Missing reentrancy guard on Tron `IntentGatewayV2.placeOrder` allows external-callback reentrancy before escrow state is finalized - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The external report's bug class — a state-changing accounting update (`_orders`/`emissionBalances`) occurring *after* an external callback that an untrusted party controls — reproduces on the Tron deployment of `IntentGatewayV2`. Unlike the audited mainline EVM contract, the Tron variant's `placeOrder` has no reentrancy guard while dispatching attacker-supplied `predispatch.call` calldata through `ICallDispatcher` before finalizing escrow accounting.

### Finding Description
The canonical EVM `IntentGatewayV2.placeOrder` is protected with `nonReentrant`: [1](#0-0) . It also uses transient-storage (`tload`/`tstore`) duplicate-output checks that are only safe under a reentrancy guard [2](#0-1) .

The Tron port of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, contains an equivalent `placeOrder` flow — it stamps `order.nonce = _nonce++`, executes attacker-supplied `order.predispatch.call` via `ICallDispatcher(dispatcher).dispatch(...)`, sweeps balances back, and only afterwards increments the `_orders[commitment][token]` escrow accounting: [3](#0-2) . However, a repo-wide search for `nonReentrant`/`ReentrancyGuard` in this file returns zero matches, confirming the Tron contract lacks the reentrancy protection present in the mainline EVM contract.

This is the same root-cause shape as the reported issue: an externally-triggerable callback (`ICallDispatcher.dispatch`, analogous to the ERC1155 `_doSafeTransferAcceptanceCheck` callback) executes attacker-controlled code *before* critical bookkeeping (`_orders[commitment][token] += reducedInputs[i].amount`, `_nonce`, dust/fee accounting) is finalized. Because `ICallDispatcher.dispatch` performs arbitrary calls with the gateway/dispatcher's context, a callback can reenter `placeOrder`, `fillOrder`, or `cancelOrder` mid-execution, observing/mutating shared state (`_nonce`, `_orders`, `TRANSACTION_FEES` escrow, dust-collection totals) while the outer call's escrow entry has not yet been written — mirroring the "callback before state update" defect class flagged in the source report.

### Impact Explanation
On the Tron deployment, reentrancy during `placeOrder`'s predispatch dispatch can be used to interleave calls that read/write the shared `_orders` mapping, `_nonce` counter, and protocol dust/fee accounting mid-flight, producing inconsistent escrow bookkeeping (e.g., double-counted or lost escrow bookkeeping entries, nonce collisions across interleaved orders, or fee/dust totals computed against stale balances). Depending on how `_orders` desynchronizes from actual on-contract token balances, this can enable a subsequent `fillOrder`/withdraw path to release more tokens than were actually escrowed, i.e. a direct path to loss of user/protocol funds through corrupted escrow accounting — a Medium/High-severity accounting-integrity issue analogous to the reported class, reachable by any unprivileged order submitter who crafts `predispatch.call`.

### Likelihood Explanation
`predispatch.call` and `predispatch.assets` are attacker-supplied fields of the `Order` struct submitted directly to `placeOrder` by any caller — no privileged role is required. The `ICallDispatcher.dispatch` call executes this payload with full external-call semantics, and nothing in the Tron contract prevents reentrant calls into `placeOrder`/`fillOrder`/`cancelOrder` during that window. This is a directly reachable, single-transaction attack surface for any user who can construct a malicious `predispatch.call` target.

### Recommendation
- Add a reentrancy guard (`nonReentrant`, matching the mainline EVM `IntentGatewayV2.sol`) to `placeOrder`, `fillOrder`, and `cancelOrder` in `evm/tron/contracts/apps/IntentGatewayV2.sol`.
- Follow checks-effects-interactions: finalize `_orders[commitment][token]` escrow increments, `_nonce`, and fee/dust accounting before invoking `ICallDispatcher.dispatch` with attacker-controlled calldata, or restructure so the dispatcher call cannot observe/mutate gateway state mid-flight.
- Audit all other Tron-specific contracts for the same missing-guard drift versus their EVM mainline counterparts, since this appears to be a porting omission rather than an intentional design difference.

### Proof of Concept
1. Attacker crafts an `Order` with `predispatch.call` pointing to a malicious contract deployed as the effective `dispatcher` target (or a contract reachable through the `ICallDispatcher` dispatch flow).
2. Attacker calls `IntentGatewayV2.placeOrder(order, graffiti)` on the Tron deployment.
3. Execution reaches `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` at [4](#0-3) , before `_orders[commitment][token] += reducedInputs[i].amount` executes.
4. Because no `nonReentrant` modifier guards `placeOrder` (confirmed by the absence of any `nonReentrant`/`ReentrancyGuard` reference in this file), the malicious callback re-enters `placeOrder` (or `fillOrder`/`cancelOrder`), reading/writing `_orders`, `_nonce`, and fee accounting while the outer order's escrow bookkeeping is still stale/incomplete, corrupting the escrow ledger relative to actual token balances.
