### Title
Unauthorized ERC-20 Approval via Permissionless `superApprove` in HyperFungibleTokenImpl - (File: evm/src/utils/HyperFungibleTokenImpl.sol)

### Summary
`HyperFungibleTokenImpl.superApprove` is a public, unauthenticated function that calls the internal `_approve(owner, spender, type(uint256).max)`, allowing any caller to grant unlimited ERC-20 allowance from an arbitrary `owner` to an arbitrary `spender`, bypassing the normal invariant that only the token owner (`msg.sender`) can set their own allowance.

### Finding Description
Standard ERC-20 `approve` only allows `msg.sender` to set their own allowance. `HyperFungibleTokenImpl` breaks this invariant: `superApprove(address owner, address spender)` is `public` with no access control, and directly invokes OpenZeppelin's internal `_approve(owner, spender, type(uint256).max)`. [1](#0-0) 
This mirrors the `buyBack` bug class: a state-mutating function that accepts an arbitrary address parameter (here, `owner`) and acts on behalf of that address without verifying `msg.sender == owner` or any signature/permit from the owner. The doc comment ("Helper function for tests") suggests test-only intent, but the function was left `public` in the production contract shipped from `evm/src/utils/`, and this contract is instantiated by the production deployment script `evm/script/DeployIsmp.s.sol`, confirming it is not confined to a test harness. [2](#0-1) 

### Impact Explanation
Any address can call `superApprove(victim, attacker)` to grant itself (or any address) an unlimited (`type(uint256).max`) allowance over any `HyperFungibleTokenImpl` holder's balance. Combined with `transferFrom`, this results in a direct and complete drain of any holder's token balance — full loss of funds for every holder of this fungible token, with no signature or prior consent required from the victim. This is a critical unbacked-approval / theft primitive, distinct from and more severe than the "buyBack" report (which only enabled *unwanted* buy-backs assuming pre-existing approval); here the contract itself grants the malicious approval.

### Likelihood Explanation
Trivial to exploit: a single unauthenticated transaction (`superApprove(owner, attacker)`) followed by `transferFrom(owner, attacker, balance)` drains funds. No proof, consensus, or relayer interaction is needed — it is reachable directly by any EOA or contract that can submit a transaction to the deployed token.

### Recommendation
Remove `superApprove` entirely from the production contract, or restrict it strictly to test builds (e.g., move it to a test-only mock contract that is never deployed via `DeployIsmp.s.sol`). If a "gasless approve for tests" helper is required, gate it behind `onlyRole(DEFAULT_ADMIN_ROLE)` at minimum, and never allow it to target an arbitrary `owner` unless the caller is the owner itself or provides an EIP-2612-style signed permit from the owner.

### Proof of Concept
```solidity
// Attacker contract or EOA calling directly against the deployed HyperFungibleTokenImpl
HyperFungibleTokenImpl token = HyperFungibleTokenImpl(TOKEN_ADDRESS);

// victim never approved anything
address victim = 0xVictim...;
address attacker = msg.sender;

// 1. Attacker grants itself unlimited allowance over victim's balance
token.superApprove(victim, attacker);

// 2. Attacker drains victim's full balance
uint256 bal = token.balanceOf(victim);
token.transferFrom(victim, attacker, bal);
```
