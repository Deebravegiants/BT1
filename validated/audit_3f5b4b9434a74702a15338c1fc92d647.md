## Title
Open Redirect via Unvalidated `host` Parameter in `ShopifyAPI::Auth.embedded_app_url` - (File: `lib/shopify_api/auth.rb`)

### Summary
`ShopifyAPI::Auth.embedded_app_url` decodes the caller-supplied `host` parameter and builds a redirect URL from it without checking the decoded value against `ShopifyAPI::Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS`, unlike every other place in the gem that turns a shop/host value into a request target (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, both of which call `Utils::ShopValidator.sanitize!`). This breaks the identity binding "host redirected to == host that is a genuine Shopify admin surface," letting an unprivileged attacker redirect the merchant's browser at the end of the embedded-app / OAuth flow to an attacker-chosen domain.

### Finding Description
`embedded_app_url` is documented (per `CHANGELOG.md` entry for PR #1002: "Add new method to construct the host app URL for an embedded app, allowing for safer redirect to app inside appropriate shop admin") as the safe way to build the URL an app redirects a merchant's browser to after completing auth inside Shopify Admin. Its implementation is: [1](#0-0) 

It simply base64-decodes the `host` argument and concatenates it into `https://#{decoded_host}/apps/#{Context.api_key}` — there is no call to `Utils::ShopValidator.sanitize!`/`sanitize_shop_domain`, and no check against `TRUSTED_SHOPIFY_DOMAINS`: [2](#0-1) 

Compare this to the two other flows in the gem that turn a `shop` string into a network destination, both of which explicitly sanitize first: [3](#0-2) [4](#0-3) 

The `host` value used by `embedded_app_url` originates from the `host` URL/query parameter that Shopify (and any link to the embedded app) passes to the app, and is not protected by any HMAC or JWT signature the way `AuthQuery#shop` is (`AuthQuery#to_signable_string` covers `shop`, but the app-supplied `host` used here has no equivalent integrity check). Because `host` is base64-encoded free text supplied on the URL, an attacker only needs to get a merchant to open a link (or the merchant's own browser tab) with a crafted `host` value; the gem will happily build and return a redirect target on an arbitrary domain.

### Impact Explanation
This falls under "forced OAuth completion" / redirect hijacking during the embedded-app authorization flow (High impact per rubric): the app is expected to send the merchant's top-level browser to `embedded_app_url(host)` once install/auth has proceeded, so it can land back inside the correct shop's Shopify Admin. Since the destination host is never checked against the trusted Shopify domain list, an attacker can force that final redirect to their own domain, enabling phishing pages that impersonate the Shopify Admin embed and can attempt to capture whatever the merchant subsequently submits (including re-authenticating into a fake "Install app" page), or simply hijack the completion of the flow to a domain the attacker controls.

### Likelihood Explanation
Likelihood is High for reachability (no secret or credential needed — just control of the `host` query parameter value, which is standard, attacker-observable input for embedded Shopify apps) but the ultimate damage depends on how the host application uses the returned URL (typically as an HTTP redirect target). Given the method's own stated purpose ("safer redirect ... to appropriate shop admin"), most integrators will trust its output implicitly.

### Recommendation
Validate the decoded `host` in `ShopifyAPI::Auth.embedded_app_url` using `Utils::ShopValidator.sanitize!`/`sanitize_shop_domain` (restricting it to `TRUSTED_SHOPIFY_DOMAINS`, mirroring `ClientCredentials` and `RefreshToken`) before using it to build the redirect URL, and raise `Errors::InvalidShopError` (or similar) if it doesn't resolve to a trusted Shopify Admin domain.

### Proof of Concept
```ruby
malicious_host = Base64.strict_encode64("evil.example.com")
ShopifyAPI::Auth.embedded_app_url(malicious_host)
# => "https://evil.example.com/apps/<api_key>"
```
No sanitization occurs, so the app will happily construct (and, if used as documented, redirect the merchant's browser to) an attacker-controlled URL. [5](#0-4)

      def embedded_app_url(host)
        unless Context.setup?
          raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
        end

        unless host
          raise Errors::MissingRequiredArgumentError, "host argument is required"
        end

        decoded_host = Base64.decode64(host)
        "https://#{decoded_host}/apps/#{Context.api_key}"
      end
