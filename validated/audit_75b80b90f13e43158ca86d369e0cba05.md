### Title
Webhook `shop-domain` header is trusted for tenant identity but is not covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0)  , so `Utils::HmacValidator.validate` in `Registry.process` only proves the request body was signed with the app's single, app-wide `api_secret_key` [2](#0-1)  . The tenant identity (`shop`) that gets handed to the app's webhook handler is read straight from the `x-shopify-shop-domain` header, which is never part of the signed bytes [3](#0-2)  .

### Finding Description
The equality that should hold is: **bytes verified by HMAC == bytes used to decide which shop/tenant the event belongs to**. Here that breaks down:

- HMAC is computed over `verifiable_query.to_signable_string`, which for `Webhooks::Request` is just `@raw_body` [1](#0-0)  and validated with `HmacValidator.validate_signature` via `OpenSSL.secure_compare` against `Context.api_secret_key` [4](#0-3)  .
- `Context.api_secret_key` is a single value set once for the whole app via `Context.setup`, shared across every shop that installs the app [5](#0-4)  . It proves "this body was signed by Shopify for my app," not "this body/shop pairing is authentic."
- `Registry.process` validates the HMAC and then immediately trusts `request.shop` (from the unauthenticated header) as the tenant identifier passed to the handler, with no cross-check against anything inside the signed body [6](#0-5)  .
- `request.shop` is read from `shopify-shop-domain` / `x-shopify-shop-domain`, a plain header not covered by `to_signable_string` [3](#0-2)  .

Because the same `api_secret_key` signs webhooks for every shop that has installed the app, an unprivileged internet user who controls one installed shop (e.g., a free/dev store) can capture a legitimate `(raw_body, hmac)` pair that Shopify sent them, then replay it to the app's webhook endpoint while substituting `x-shopify-shop-domain` (and `x-shopify-webhook-id`/`topic`, also unsigned) for a victim shop's domain. `HmacValidator.validate` still passes because the body bytes are unchanged, and `Registry.process` forwards `WebhookMetadata` with `shop: request.shop` (attacker-chosen) to the handler [7](#0-6)  . Any host application that scopes storage/side effects by `data.shop` (the documented and expected usage pattern) will process attacker-controlled body content under the wrong tenant's identity.

### Impact Explanation
This breaks the shop/tenant identity binding and enables cross-tenant data injection: an attacker who is a legitimate but unprivileged merchant of their own shop can make the app record or act on arbitrary webhook payload content as if it originated from a different, victim shop, corrupting or spoofing that victim's data inside the host application. This matches the Critical "cross-tenant access" impact category — the gem hands the host application an identity claim (`shop`) that was never authenticated, only a body payload that was.

### Likelihood Explanation
Any developer/merchant can install the target app on a store they control and thus obtain valid `(body, hmac)` pairs signed with the app's real `api_secret_key`. No leaked credentials, TLS interception, or social engineering is required — only the ability to intercept/replay one's own legitimately received webhook HTTP request with modified headers, which is trivial for anyone who can install the app.

### Recommendation
Bind the shop (and topic/webhook id/api version) into the signed material, or otherwise verify that the `shop-domain` header is consistent with an authenticated identifier before trusting it. Concretely, `VerifiableQuery#to_signable_string` for webhooks should not be limited to `@raw_body`; alternatively, `Registry.process` should independently verify `request.shop` against a value obtained through an authenticated channel (e.g., look up the webhook subscription by `webhook_id` via an authenticated API call, or require the host app to reconcile the shop against its own session store) rather than trusting the unauthenticated header outright.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker.myshopify.com` and registers a webhook.
2. Shopify sends a webhook POST to the app's endpoint with body `{"id":123,...}` and header `x-shopify-shop-domain: attacker.myshopify.com`, signed with the app's `api_secret_key` and passed to `Webhooks::Request.new(raw_body:, headers:)`.
3. Attacker captures this raw HTTP request (body + `x-shopify-hmac-sha256` value unchanged).
4. Attacker replays the exact same request to the app's webhook endpoint, but rewrites `x-shopify-shop-domain` to `victim.myshopify.com`.
5. `Registry.process` calls `Utils::HmacValidator.validate(request)` [8](#0-7)  — this still succeeds because it only hashes `@raw_body`, which is unchanged.
6. The handler receives `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: attacker's parsed_body, ...)` [7](#0-6)  and the host app processes attacker-controlled data under the victim shop's identity.
