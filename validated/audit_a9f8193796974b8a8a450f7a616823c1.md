I found a valid analog. The webhook HMAC verification in this gem only covers the raw request body, while the `shop` (and `topic`, `webhook_id`, `api_version`) values are read from unauthenticated HTTP headers and are never included in the signed payload.

### Title
Webhook `shop` identity is trusted without being covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , while `shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header [2](#0-1) . `Registry.process` validates only that HMAC before forwarding `request.shop` to the app's handler as the authoritative tenant identity [3](#0-2) . Because the `shop` header is never part of the signed bytes, the binding "HMAC validated for shop X" == "body actually originated from shop X" does not hold.

### Finding Description
`HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest(sha256, secret, verifiable_query.to_signable_string)` and compares it against the `hmac` accessor [4](#0-3) . For `Webhooks::Request`, `to_signable_string` is just `@raw_body` [5](#0-4) . The `shop`, `topic`, `webhook_id`, and `api_version` accessors all come from HTTP headers that are outside the signed content [6](#0-5) .

The app's own `api_secret_key` is shared across every shop that has the app installed — it is not per-shop. Any entity that can install the app on a store they control (an "unprivileged internet user" in the sense of a self-serve public-app install, no special privilege needed) legitimately receives webhooks whose body+HMAC pair is valid under the app's secret. Nothing prevents that entity from re-sending the exact same `raw_body`/`hmac-sha256` pair to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop's domain. `Registry.process` re-validates the HMAC (which still matches, since it only covers the body) and then calls the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` [7](#0-6) , so the handler believes the payload came from the victim shop.

This is validated by the equality that should hold but does not:
`HMAC-verified(body)` == `shop header value used by the handler`

Before the attack: HMAC is computed and verified over `body` for a request genuinely tied to the attacker's own shop's headers.
After the attack: the same valid `(body, hmac)` pair is replayed with an arbitrary `shop-domain` header; verification still succeeds because `shop` was never part of the signed input.

### Impact Explanation
Any handler that uses `WebhookMetadata#shop` to select which merchant's data/session to act on (e.g., updating billing state, disabling a subscription, revoking access, writing to a per-shop record keyed by `shop`) can be made to act on an arbitrary victim shop chosen by the attacker, purely by forging the `shop-domain` header on a replayed, still-HMAC-valid webhook body. This is a cross-tenant access primitive — one tenant (the attacker's own shop) can cause the app to process an action tagged as belonging to a different tenant.

### Likelihood Explanation
Likelihood is high for any app that has at least one public/self-serve install path (typical for apps distributed on the Shopify App Store) and any webhook handler that trusts `data.shop` for tenant-scoping without independently confirming the sender's identity (e.g. re-deriving shop from an authenticated session). No secret material needs to be known beyond what a legitimate (if low-privilege) merchant/install already has.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signable string used for webhook HMAC validation, or otherwise cryptographically bind the shop domain to the signed payload (e.g., re-derive the shop only from data validated as being emitted for that specific webhook subscription, not from an unauthenticated header). At minimum, document that `WebhookMetadata#shop` must not be treated as authenticated unless the header is included in HMAC verification, and update `Webhooks::Request#to_signable_string` accordingly.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` (a store they control) and receives a legitimate webhook, e.g. topic `app/uninstalled` with raw body `{}` and a valid `x-shopify-hmac-sha256` computed by Shopify with the app's `api_secret_key`.
2. Attacker replays this exact `raw_body` and `hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only signs `@raw_body` [5](#0-4) .
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", topic: "app/uninstalled", ...)` and performs whatever tenant-scoped action the app implements for that topic against the victim shop's data, even though the victim shop never sent this webhook.
