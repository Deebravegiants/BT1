I found a concrete identity-binding gap in the webhook handling path: the `shop` (tenant) identity used by the host application to route webhook data is derived from an HTTP header that is never covered by the HMAC signature — only the raw request body is signed.

## Title
Webhook tenant identity (`shop-domain` header) is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, while `shop`, `topic`, `webhook_id`, and `api_version` are all read from unauthenticated headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC against the body only, then unconditionally trusts `request.shop` as the tenant identity passed into the host app's handler via `WebhookMetadata`.

### Finding Description
`Utils::HmacValidator.validate` computes and checks the signature only over `verifiable_query.to_signable_string`: [1](#0-0) 
For webhooks, `to_signable_string` is defined as just the raw body: [2](#0-1) 
Meanwhile `shop`, `topic`, and `webhook_id` are all pulled straight from HTTP headers with no cryptographic binding to the signed body: [3](#0-2) 
`Registry.process` validates the HMAC, then immediately uses the (unauthenticated) `request.shop` to build the `WebhookMetadata` handed to the app's business logic — the value the host application relies on to know *which merchant/tenant* the payload belongs to: [4](#0-3) 

The binding the gem should enforce is: `hmac == HMAC(secret, body ‖ shop ‖ topic)` (or equivalent), i.e. the tenant-identifying metadata must be authenticated together with the payload. Instead the code enforces only `hmac == HMAC(secret, body)`, independent of `shop`.

Because every shop that installs a given app shares the same `client_secret`/`api_secret_key` for webhook signing (Shopify signs webhooks with the app's secret, not a per-shop secret), any party that can obtain one validly-signed webhook body+HMAC pair (e.g., a merchant using the app who receives webhooks to their own endpoint, or an attacker who can capture one webhook delivery) can replay that exact body/HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and `Topic`/`Webhook-Id`) headers of a *different* shop. `Utils::HmacValidator.validate` will still return `true`, because it never inspected those headers, and `Registry.process` will hand the forged `shop` value straight to the app's handler as if it were authentic.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook consumers: the host application's webhook handler is designed to trust `WebhookMetadata#shop` as an authenticated statement of "this event happened for this shop." An attacker who can produce (or replay) one validly HMAC-signed body can cause the app to process/attribute that payload to an arbitrary target shop domain of their choosing, since `shop` is uncorrelated with the signature. Depending on how the host app's handler uses `data.shop` (e.g., to look up the shop's session/config, update per-shop state, or select which tenant's data to act on), this enables cross-tenant confusion/access — data belonging to shop A can be injected and misattributed to shop B purely by manipulating headers, which is a cross-tenant impact within scope.

### Likelihood Explanation
Requires only the capabilities of an unprivileged actor able to send an HTTP POST to the app's public webhook endpoint plus knowledge of one legitimate `(body, hmac)` pair for the same app (trivially obtainable by installing the app on a shop the attacker controls and observing the webhook it receives, since the HMAC secret is identical for all shops using the app). No access to `api_secret_key`, tokens, or the shop's session is needed — only replay of previously observed bytes with modified headers.

### Recommendation
Include the tenant-identifying fields (`shop`, and ideally `topic`/`webhook_id`) in the signed material verified by `HmacValidator`, or otherwise cryptographically bind them to the body before trusting them in `WebhookMetadata`. At minimum, `Webhooks::Request#to_signable_string` should incorporate `shop`, `topic`, and `webhook_id` (matching what Shopify actually signs, or independently re-deriving/verifying the shop from the registered app installation) rather than trusting these values solely from unauthenticated headers.

### Proof of Concept
1. App developer installs their own app on `attacker-shop.myshopify.com` and configures a webhook endpoint they control; they capture one legitimate webhook delivery: raw body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for `HMAC(secret, B)`), `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`.
2. Attacker replays the exact same request to the app's public webhook endpoint but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` (and optionally `X-Shopify-Webhook-Id`/`X-Shopify-Topic` if desired for another registered topic).
3. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present), and `Utils::HmacValidator.validate(request)` returns `true` because it only recomputes `HMAC(secret, B)` and compares — it never looks at the `shop` header: [5](#0-4) 
4. `Registry.process` proceeds to call the app's handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body_of_B, ...)`, causing the host application to process attacker-controlled/replayed data as if it genuinely originated from `victim-shop.myshopify.com`.
