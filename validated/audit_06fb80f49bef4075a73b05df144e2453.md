### Title
Webhook shop identity not bound to HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as "verified" once the HMAC signature check passes, but the HMAC signature only covers the raw request body. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values that the handler receives as trusted, verified metadata are taken straight from unauthenticated HTTP headers and are never part of the signed bytes.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled from headers that are never fed into the signature computation: [2](#0-1) 

`Utils::HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the received `hmac` value using `OpenSSL.secure_compare`: [3](#0-2) 

`Registry.process` gates on that check and then constructs `WebhookMetadata` using the unauthenticated `request.shop`/`request.topic`/`request.webhook_id` values, dispatching them to the app's handler as if they were verified: [4](#0-3) 

The broken identity binding, expressed as an equality that the code should enforce but doesn't:
`HMAC(secret, raw_body ‖ shop ‖ topic) == received_signature`
what is actually checked is only:
`HMAC(secret, raw_body) == received_signature`

The HMAC secret (`Context.api_secret_key`, the app's `client_secret`) is the same for every shop that has installed the app — it is not per-tenant. Any merchant/tenant that has installed the app can receive a genuine, validly-signed webhook for their own shop (their own body + valid signature), then replay that exact body/signature pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or topic) header for a victim shop's domain. Because the header is outside the signed data, `Utils::HmacValidator.validate` still returns `true`, and `Registry.process` calls the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain, `body: request.parsed_body` from the attacker's own (legitimately signed) payload.

### Impact Explanation
This breaks the tenant boundary that `Registry.process` is documented to enforce ("verify the request did indeed come from Shopify"). A malicious but legitimate tenant of the app can make the app believe a webhook came from an arbitrary other shop, causing any handler logic keyed off `WebhookMetadata#shop` (e.g., looking up a per-shop session/access token, updating per-shop state, mandatory GDPR webhooks) to act under the wrong tenant's identity. This is a cross-tenant identity confusion inside the gem's own "verified" webhook API surface, not a case of the host ignoring documented behavior — the host is using `Registry.process` exactly as documented and is told the request "did indeed come from Shopify" for the shop given in the metadata.

### Likelihood Explanation
Exploitation requires only that the attacker be an installed/authenticated merchant of the target app (an "unprivileged internet user" relative to other tenants) — no access to `api_secret_key` or any victim credentials is needed. The attacker just needs to capture one genuine webhook delivery to their own endpoint (trivial, since it's their own shop) and replay it with a modified `shop-domain` header, which any HTTP client can do.

### Recommendation
Include the identity fields that the application relies on (at minimum `shop-domain`, and ideally `topic`/`webhook-id`) in the signed/verified data, or explicitly document and enforce that `WebhookMetadata#shop`/`topic` must never be trusted for authorization decisions without an independent verification (e.g., cross-checking against the shop that Shopify is expected to send for that specific registered endpoint). At the very least, `Utils::HmacValidator`/`Registry.process` should not imply that headers such as `shop-domain` are verified by the HMAC check when they are not.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and registers a webhook (e.g., `orders/create`).
2. Shopify sends a legitimately signed webhook to the app's endpoint:
   - Headers: `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid signature over body>`
   - Body: attacker-controlled order JSON (since it's the attacker's own store).
3. Attacker captures this raw request and resends it to the same endpoint, changing only the `x-shopify-shop-domain` header to `victim-shop.myshopify.com`, leaving body and `x-shopify-hmac-sha256` untouched.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because the check only covers `raw_body`: [4](#0-3) 
5. The app's handler receives `WebhookMetadata` with `shop == "victim-shop.myshopify.com"` and attacker-controlled `body`, and performs whatever tenant-scoped action it takes on webhook receipt (e.g., token lookup, order sync) under the victim's identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
