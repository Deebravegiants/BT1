### Title
Unbounded slot-index memory read in Pharos `hash_internal_node` allows relayer-triggered panic — ([File: modules/consensus/pharos/primitives/src/spv.rs])

### Summary
`hash_internal_node` indexes into an attacker-supplied proof node byte slice using compile-time constant offsets without first checking that the slice is actually `INTERNAL_NODE_LEN` bytes long, unlike the ELF `elf_rs` bug where a header-derived offset was trusted without bounds validation.

### Finding Description
`compute_node_hash` dispatches purely on `proof_node.len()` and calls `hash_internal_node(proof_node)` only when `proof_node.len() == INTERNAL_NODE_LEN` [1](#0-0) , so the top-level entry point is length-guarded. However, `hash_internal_node` itself performs unchecked slicing:

```rust
fn hash_internal_node(proof_node: &[u8]) -> [u8; 32] {
	let mut data = Vec::with_capacity(INTERNAL_NODE_LEN);
	data.extend_from_slice(&proof_node[..INTERNAL_NODE_HEADER]);
	for i in 0..INTERNAL_NODE_SLOTS {
		let start = INTERNAL_NODE_HEADER + i * INTERNAL_NODE_SLOT_SIZE;
		let slot = &proof_node[start..start + INTERNAL_NODE_SLOT_SIZE];
``` [2](#0-1) 

This function has no internal length assertion of its own — it is only safe because every current caller (`compute_node_hash`, and the SkipEmpty demonstration in tests) happens to pre-check `proof_node.len() == INTERNAL_NODE_LEN`. This mirrors the ELF `elf_rs` root cause: a helper that computes an offset/pointer into a buffer and trusts the caller to have validated the length, without the callee independently enforcing the invariant. The same file elsewhere shows the project is aware of exactly this failure mode and has hardened other slot accesses with `.get(start..start+SIZE).ok_or(...)` instead of raw indexing (see `verify_proof_walk`'s `parent.proof_node.get(start..start + INTERNAL_NODE_SLOT_SIZE).ok_or(Error::SlotOutOfBounds)?`) [3](#0-2)  — but `hash_internal_node` was not converted to the same defensive pattern, leaving it reliant on caller discipline.

### Impact Explanation
Today the length check in `compute_node_hash` happens to prevent a panic, so this is not currently exploitable through `verify_proof`, `verify_non_existence_proof`, or `verify_membership_proof`, all of which route through `compute_node_hash` first [4](#0-3) . However, `hash_internal_node` is a `pub(crate)`-visible, reusable primitive with no self-contained safety invariant; any future caller (or refactor) that invokes it directly on attacker/relayer-controlled proof bytes without replicating the exact length check reintroduces a reachable panic (denial of service on the ISMP state-machine verification path for Pharos, callable by any relayer submitting a state proof). This is the same "trust the caller" pattern the ELF advisory flags as the root cause of unsafe reads.

### Likelihood Explanation
Low-to-medium as currently written, because the one call site is guarded. The function should be treated as unsafe-by-convention and hardened defensively, since Pharos proof structures (`PharosProofNode.proof_node: Vec<u8>`) are fully attacker/relayer supplied and decoded via SCALE with no independent length assertion at decode time.

### Recommendation
Add an explicit length assertion (or `debug_assert!`/early return) inside `hash_internal_node` itself, e.g. `if proof_node.len() != INTERNAL_NODE_LEN { return ZERO_HASH; }` or make it fallible like `compute_node_hash`, so the invariant is enforced at the point of use rather than depending on every caller replicating the same pre-check — consistent with the `.get(..).ok_or(...)` pattern already used in `verify_proof_walk`.

### Proof of Concept
Not directly triggerable today since `compute_node_hash` gates the call; the risk is latent/defense-in-depth rather than a live exploit path. A hypothetical PoC would require a code path calling `hash_internal_node` on a `proof_node` slice shorter than `INTERNAL_NODE_LEN` (e.g., a future direct call bypassing `compute_node_hash`), which would panic with an out-of-bounds slice index inside `data.extend_from_slice(&proof_node[..INTERNAL_NODE_HEADER])` or the subsequent slot slicing.
